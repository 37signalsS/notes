# gRPC: Высокопроизводительный фреймворк для удаленных вызовов

## Определения

**gRPC (gRPC Remote Procedure Calls)** — это современный, высокопроизводительный фреймворк с открытым исходным кодом, разработанный Google. Он позволяет клиентскому приложению напрямую вызывать методы на серверном приложении, как если бы это был локальный объект. gRPC является ключевым компонентом в архитектуре микросервисов и облачных приложений.

**Статус (2026):** gRPC продолжает развиваться. Появилась экспериментальная поддержка **HTTP/3** (QUIC) для снижения задержек и устранения head-of-line blocking на уровне транспорта. Google также участвует в интеграции gRPC в **Model Context Protocol (MCP)** для взаимодействия с AI-моделями.

## Основные концепции

### Protocol Buffers (Protobuf)

По умолчанию gRPC использует **Protocol Buffers** в качестве языка описания интерфейсов (IDL - Interface Definition Language).

* **Контракт в `.proto` файлах:** Вы описываете структуру данных (сообщения) и сервисы (методы) в специальных файлах с расширением `.proto`. Этот файл является единым источником правды для API.
* **Эффективная сериализация:** Данные сериализуются в компактный бинарный формат. Это делает их передачу значительно быстрее и экономичнее по сравнению с текстовым JSON.
* **Строгая типизация:** Protobuf требует явного определения типов данных, что снижает количество ошибок во время выполнения.
* **Генерация кода:** Из `.proto` файла можно автоматически сгенерировать клиентские и серверные заготовки на множестве языков программирования (Go, Java, Python, C++, etc.), что упрощает разработку и обеспечивает консистентность.

**Пример `.proto` файла:**

```protobuf
// Указываем версию синтаксиса
syntax = "proto3";

// Определяем сервис Greeter
service Greeter {
  // Определяем метод SayHello
  rpc SayHello (HelloRequest) returns (HelloReply);
}

// Сообщение-запрос с одним полем
message HelloRequest {
  string name = 1;
}

// Сообщение-ответ с одним полем
message HelloReply {
  string message = 1;
}
```

### HTTP/2 и HTTP/3

gRPC изначально построен поверх протокола **HTTP/2**, что дает ему фундаментальные преимущества перед HTTP/1.1:

* **Мультиплексирование:** HTTP/2 может отправлять несколько запросов и получать несколько ответов параллельно в рамках одного TCP-соединения. Это решает проблему "блокировки начала очереди" (head-of-line blocking) на уровне приложения.
* **Двунаправленная потоковая передача (Streaming):** HTTP/2 изначально поддерживает потоки, позволяя клиенту и серверу одновременно отправлять и получать данные в рамках одного запроса/ответа.
* **Сжатие заголовков (HPACK/QPACK):** Эффективно сжимает метаданные запросов, уменьшая накладные расходы.
* **Бинарный протокол:** В отличие от текстового HTTP/1.1, HTTP/2 является бинарным, что делает его более эффективным и менее подверженным ошибкам парсинга.

**HTTP/3 (QUIC) — экспериментальная поддержка (2025+):**
Новые версии gRPC добавляют поддержку HTTP/3 поверх QUIC. Преимущества:

* **0-RTT / 1-RTT соединение:** Быстрее установка соединения благодаря TLS 1.3.
* **Устранение HOL-blocking на транспортном уровне:** Потеря пакета не блокирует другие потоки.
* **Миграция соединения:** Соединение сохраняется при смене сети (например, переход с Wi-Fi на мобильную сеть).

> **Примечание:** Поддержка HTTP/3 находится в стадии активной разработки. Для production рекомендуется использовать HTTP/2.

### Потоковая передача (Streaming)

Благодаря HTTP/2, gRPC нативно поддерживает потоковую передачу данных. Существует четыре типа методов:

1. **Unary RPC (Унарный вызов):** Классический запрос-ответ. Клиент отправляет один запрос и получает один ответ.
    `rpc SayHello(HelloRequest) returns (HelloReply);`
2. **Server Streaming RPC (Потоковая передача с сервера):** Клиент отправляет один запрос и получает в ответ поток сообщений от сервера.
    `rpc LotsOfReplies(HelloRequest) returns (stream HelloReply);`
3. **Client Streaming RPC (Потоковая передача от клиента):** Клиент отправляет на сервер поток сообщений. После завершения потока сервер отправляет один ответ.
    `rpc LotsOfGreetings(stream HelloRequest) returns (HelloReply);`
4. **Bidirectional Streaming RPC (Двунаправленная потоковая передача):** Клиент и сервер могут отправлять друг другу потоки сообщений независимо друг от друга.
    `rpc BidiHello(stream HelloRequest) returns (stream HelloReply);`

## Практические сценарии

* **Внутреннее общение микросервисов:** Это основной юзкейс. Высокая производительность и строгие контракты делают gRPC идеальным для быстрых и надежных вызовов между сервисами в бэкенде.
* **Мобильные клиенты и бэкенд:** Эффективный бинарный протокол экономит трафик и заряд батареи, что критично для мобильных устройств.
* **Real-time приложения:** Двунаправленный стриминг отлично подходит для приложений, требующих обмена данными в реальном времени (чаты, IoT, игровые сервисы).
* **API для разных языков:** Когда у вас есть полиглотная система (сервисы на Go, Java, Python), gRPC упрощает их интеграцию благодаря автоматической генерации кода.
* **Observability:** gRPC используется в [OpenTelemetry Protocol (OTLP)](../../OpenTelemetry/otlp_protocol.md) для передачи телеметрии (трассировки, метрики, логи) в Collector.
* **Docker и Kubernetes:** [Docker](../../Docker/docker_overview.md) использует gRPC для взаимодействия `dockerd` с `containerd`. [Kubernetes](../../Kubernetes/Architecture/components.md) использует gRPC через CRI для управления контейнерами.
* **Service Mesh:** [Consul](../../Consul/consul_health_checks.md) использует gRPC для health checks сервисов.

**Когда REST может быть лучше:**

* **Публичные API:** Если вам нужен API, который легко вызывать из браузера или с помощью простых инструментов вроде `curl`, REST остается стандартом де-факто.
* **Простые CRUD-сервисы:** Для простых операций с ресурсами сложность gRPC может быть избыточной.

### gRPC-Web

**gRPC-Web** — это адаптация gRPC для работы в браузерах. Поскольку браузеры не поддерживают полный HTTP/2 (особенно raw TCP streams), gRPC-Web использует прокси-сервер (например, [Envoy](../../WebServers/Envoy/envoy_overview.md)), который транслирует запросы между браузером и gRPC-сервером.

* **Сценарий использования:** Прямое взаимодействие SPA-приложений (React, Vue, Angular) с gRPC-бэкендом.
* **Ограничения:** Не поддерживает все типы стриминга (только client streaming и unary).

## Дополнительная информация

### Безопасность gRPC

* **mTLS (Mutual TLS):** Рекомендуется для аутентификации клиентов и серверов в микросервисной архитектуре.
* **Авторизация:** Реализуется через интерцепторы (interceptors) и JWT-токены.
* **Rate Limiting:** Ограничение количества вызовов через интерцепторы или прокси (Envoy).
* **Валидация входных данных:** Protobuf не валилизирует данные автоматически — требуется дополнительная валидация на уровне приложения.

### Сравнение: gRPC vs. REST

| Характеристика | **gRPC** | **REST** |
| :--- | :--- | :--- |
| **Протокол** | HTTP/2 (HTTP/3 — экспериментально) | HTTP/1.1 (чаще всего), HTTP/2 |
| **Формат данных** | Protocol Buffers (бинарный) | JSON (текстовый), XML, др. |
| **Контракт API** | Строгий, определяется в `.proto` файле | Гибкий, часто описывается через OpenAPI/Swagger |
| **Производительность** | Очень высокая, низкие задержки | Ниже, чем у gRPC, из-за текстового формата |
| **Потоковая передача** | Встроена (клиентская, серверная, двунаправленная) | Реализуется через WebSocket, SSE или Long Polling |
| **Генерация кода** | Встроена в инструментарий | Зависит от сторонних инструментов (e.g., Swagger Codegen) |
| **Поддержка браузерами**| Требуется gRPC-Web + прокси (Envoy) | Нативная, полная поддержка |
| **Безопасность** | mTLS, интерцепторы для авторизации | HTTPS, OAuth2, JWT, API Keys |
