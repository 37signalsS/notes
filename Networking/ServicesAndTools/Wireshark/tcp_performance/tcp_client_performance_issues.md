# Диагностика проблем производительности клиента TCP

## Определения

**TCP Zero Window** — состояние, при котором получатель объявляет нулевой размер окна (window = 0), сигнализируя отправителю о невозможности принимать данные.

**TCP Window Full** — событие в Wireshark, означающее, что отправитель заполнил доступное окно получателя и вынужден приостановить передачу.

**Bytes in Flight** — количество байт, отправленных но ещё не подтверждённых ACK. Рост до границы окна указывает на заполнение буфера получателя.

---

## Basic Concepts

### Механизм проблемы «тормозит клиент»

Когда клиент не успевает обрабатывать входящие данные, происходят следующие события:

1. **Заполнение буфера приема** — приложение медленно читает из сокета → данные накапливаются в `SO_RCVBUF`
2. **Уменьшение advertised window** — клиент объявляет всё меньший размер окна: `64KB → 46KB → 32KB → 19KB → 0KB`
3. **Zero Window** — окно достигает нуля, сервер останавливает передачу
4. **Window Probe** — сервер периодически проверяет, освободился ли буфер
5. **Возобновление** — клиент освобождает буфер → объявляет ненулевое окно → передача возобновляется

### Причины недостаточной производительности клиента

| Причина | Описание |
| :--- | :--- |
| **Приложение не успевает** | Медленное чтение из сокета, блокирующие операции |
| **CPU клиента загружен** | Нехватка процессорного времени на обработку TCP-стека |
| **Недостаточный буфер** | Малый размер `SO_RCVBUF`, ограничение `tcp_rmem` |

### Связь с настройками Linux

Размер буфера приема контролируется параметрами `net.ipv4.tcp_rmem` и `net.core.rmem_max`. Приложения могут переопределять размер через `SO_RCVBUF`, но не выше `rmem_max`. Подробности — в [Оптимизация буферов TCP](../../../../Linux/Networking/Concepts/tcp_tuning/tcp_buffer_tuning.md).

## Practical Scenarios

### Сценарий: Тормозит клиент

**Симптомы:**

- Большой RTT (миллисекунды вместо микросекунд)
- Уменьшение Window Size со стороны клиента
- События **TCP Zero Window** или **TCP Window Full** в Wireshark

### Диагностика в Wireshark

#### 1. Проверить Expert Information

```
Analyze → Expert Information → Искать "tcp zero window"
```

#### 2. Анализ Window Size

- Добавить столбец `Calculated Window Size`
- Отслеивать уменьшение окна от клиента:

  ```
  64KB → 46KB → 32KB → 19KB → 0KB (Zero Window)
  ```

#### 3. График Window Scaling

```
Statistics → TCP Stream Graphs → Window Scaling
```

- Зелёная линия — размер окна клиента
- Резкое падение до 0 → клиент не успевает обрабатывать

#### 4. Проверить Bytes in Flight

- Рост до границы окна → остановка передачи
- Клиент не подтверждает → буфер заполнен

### Пример диагностики

```
Сервер отправляет 14KB → Клиент подтверждает через 18μs
Сервер отправляет ещё 14KB → Окно клиента: 89KB → 76KB
...
Сервер отправляет 19KB → Клиент: Window = 19KB (Window Full)
Пауза 32ms → Клиент: Window = 0 (Zero Window)
Пауза 20ms → Клиент: Window = 93KB (освободил буфер)
```

### Решение

**На стороне Linux — увеличить буфер приема:**

```bash
# Проверка текущих значений
sysctl net.ipv4.tcp_rmem
sysctl net.core.rmem_max

# Увеличение буфера
sysctl -w net.core.rmem_max=16777216
sysctl -w net.ipv4.tcp_rmem='4096 87380 16777216'
```

Подробная документация по настройке — [Оптимизация буферов TCP](../../../../Linux/Networking/Concepts/tcp_tuning/tcp_buffer_tuning.md).

**Настройка приложения (Python):**

```python
import socket

sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, 16 * 1024 * 1024)
```

**Оптимизация приложения:**

- Убрать блокирующие операции в обработчике сокета
- Использовать асинхронный I/O (epoll, io_uring)
- Увеличить приоритет процесса (`nice`, `ionice`)
