# Диагностика проблем производительности клиента TCP

## Определения

**TCP Zero Window** — состояние, при котором получатель (клиент) объявляет размер окна равным нулю. Это сигнал отправителю о том, что буфер приема переполнен и прием новых данных невозможен до освобождения места.

**TCP Window Full** — событие в Wireshark, означающее, что отправитель заполнил всё доступное окно получателя и вынужден приостановить передачу в ожидании подтверждения (ACK).

**Bytes in Flight (Байты в полете)** — количество данных, которые были отправлены, но еще не подтверждены. Достижение этим значением предела `Window Size` указывает на полное заполнение буфера получателя.

**Window Scaling (Масштабирование окна)** — опция TCP (RFC 7323), позволяющая увеличить максимальный размер окна с 64 КБ до 1 ГБ. Если опция не согласована при установке соединения, скорость в сетях с высоким RTT будет искусственно ограничена.

## Основные концепции

### Механизм возникновения задержек на стороне клиента

Проблема «тормозит клиент» обычно связана с тем, что приложение медленнее считывает данные из сокета, чем сеть их доставляет.

1. **Заполнение буфера приема**: Данные накапливаются в системном буфере `SO_RCVBUF`.
2. **Снижение анонсированного окна (Advertised Window)**: Клиент в каждом ACK-пакете сообщает серверу о всё меньшем свободном месте.
3. **Zero Window**: Окно достигает нуля, сервер прекращает передачу и запускает **Persist Timer**.
4. **Window Probe**: Сервер периодически отправляет проверочные пакеты (1 байт), чтобы вынудить клиента прислать актуальное значение окна.
5. **Window Update**: Когда приложение вычитывает данные, клиент отправляет пакет с обновленным окном для возобновления передачи.

### Проблема отсутствия Window Scaling (LFN)

В сетях с большой задержкой и высокой пропускной способностью (LFN — Long Fat Networks) отсутствие масштабирования окна является критической проблемой.
- Без `wscale` максимальное окно — 64 КБ.
- При RTT 100 мс максимальная скорость будет: `65535 байт / 0.1 сек = 5.2 Мбит/с`, независимо от того, что канал имеет 1 Гбит/с.
- **Диагностика:** Ищите отсутствие `Window Scale` в пакетах SYN и SYN-ACK.

## Практические сценарии

### Диагностика в Wireshark

#### 1. Использование фильтров отображения

Для быстрого поиска проблемных пакетов:
- `tcp.analysis.zero_window` — поиск всех событий нулевого окна.
- `tcp.analysis.window_full` — поиск моментов, когда отправитель уперся в лимит клиента.
- `tcp.analysis.window_update` — поиск пакетов, возобновляющих передачу.

#### 2. Настройка столбцов для мониторинга

Добавьте поля как столбцы (`Apply as Column`):
- `tcp.window_size_value` — «сырое» значение окна из заголовка.
- `tcp.window_size` — вычисленное значение (с учетом масштабирования).
- `tcp.analysis.bytes_in_flight` — текущая нагрузка на буфер.

#### 3. Визуализация через графики

Используйте `Statistics → TCP Stream Graphs → Window Scaling`.
- Линия графика должна быть стабильной. Резкие падения к нулю — признак того, что приложение не справляется с потоком данных.

### Методы решения проблемы

#### Настройка операционной системы (Linux)

Увеличьте лимиты автотюнинга буферов:
```bash
# Максимальный размер буфера (16 МБ)
sudo sysctl -w net.core.rmem_max=16777216
# Параметры: min, default, max
sudo sysctl -w net.ipv4.tcp_rmem='4096 87380 16777216'
```

#### Оптимизация приложения

- **Zero-copy:** Использование `sendfile` или `splice` для уменьшения копирования данных в памяти.
- **Async I/O:** Переход на `epoll`, `io_uring` или библиотеки (libuv, Netty) для неблокирующего чтения.
- **Batching:** Вычитывание данных из сокета большими порциями (Chunks).
