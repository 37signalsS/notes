# Wireshark: Диагностика производительности TCP — Обзор

## Определения

**Диагностика производительности TCP в Wireshark** — метод анализа сетевого трафика для выявления узких мест передачи данных на стороне сервера, клиента или сети.

**Ключевые метрики:**

- **RTT (Round Trip Time)** — время от отправки пакета до получения подтверждения (ACK)
- **Delta Time** — временной интервал между пакетами
- **Throughput** — скорость передачи данных в единицу времени
- **Window Size** — размер TCP-окна (объём данных, которые можно отправить без подтверждения)
- **Bytes in Flight** — количество байт, отправленных но ещё не подтверждённых
- **Retransmit** — повторная отправка пакета из-за потери или тайм-аута
- **DupACK (Duplicate ACK)** — повторное подтверждение, указывающее на потерю пакета

## Основные концепции

### Механизм определения скорости TCP

Скорость передачи данных по TCP изначально неизвестна ни клиенту, ни серверу и определяется динамически в процессе передачи:

1. **Начальная скорость** — определяется алгоритмом Slow Start
2. **Динамическая адаптация** — скорость меняется в зависимости от:
   - Подтверждений получения (ACK)
   - Потерь пакетов
   - Задержек в сети (RTT)
3. **Направление** — скорость может отличаться в разных направлениях

**Факторы влияния:**

- Ограничения провайдера (шейперы)
- Физические помехи (для Wi-Fi)
- Загруженность сети
- Производительность клиента/сервера

### TCP-флаги

| Флаг | Название | Описание |
| :--- | :--- | :--- |
| **SYN** | Synchronize | Установка соединения (первый пакет handshake) |
| **ACK** | Acknowledgement | Подтверждение получения пакета |
| **FIN** | Finish | Штатное завершение соединения |
| **RST** | Reset | Аварийный обрыв соединения |
| **PSH** | Push | Передача полезных данных приложению |

### Процесс установки и завершения соединения

```
Клиент                          Сервер
   |                               |
   |---------- SYN --------------->|  (Хочу подключиться)
   |                               |
   |<------- SYN, ACK -------------|  (Готов, подтверждаю твой SYN)
   |                               |
   |---------- ACK --------------->|  (Подтверждаю твой SYN)
   |                               |
   |======= Соединение установлено ======|
   |                               |
   |<-------- Данные -------------|  (Передача данных)
   |---------- ACK --------------->|  (Подтверждение)
   |                               |
   |---------- FIN --------------->|  (Хочу завершить)
   |<------- ACK -----------------|  (Подтверждаю FIN)
   |<------- FIN -----------------|  (Я тоже хочу завершить)
   |---------- ACK --------------->|  (Подтверждаю)
   |                               |
   |====== Соединение закрыто =======|
```

**Важно:** после установки соединения роли «клиент» и «сервер» условны — обе стороны могут передавать данные равноправно.

### In-flight пакеты и TCP-окно

**In-flight пакеты** — пакеты, отправленные но ещё не подтверждённые получателем.

**TCP-окно (Window)** — минимальное из двух значений:

- **cwnd (congestion window)** — окно перегрузки (определяется отправителем на основе состояния сети)
- **rwnd (receiver window)** — окно получателя (свободное место в буфере получателя)

```
Effective Window = min(cwnd, rwnd)
```

**Принцип работы:**

1. При установке соединения стороны анонсируют MSS (Maximum Segment Size) — максимальный размер сегмента
2. Получатель указывает, сколько байт он готов принять (rwnd)
3. Отправитель отправляет данные в пределах окна
4. При получении ACK окно «сдвигается» и можно отправлять новые данные

### Алгоритмы контроля перегрузки

#### Slow Start (Медленный старт)

Несмотря на название, рост скорости **экспоненциальный**:

- Начальное значение: `initcwnd = 10 MSS` (~14 КБ)
- На каждый ACK: удвоение количества пакетов
- Завершается при достижении `ssthresh` или потере пакета

#### Congestion Avoidance (Избегание перегрузки)

После Slow Start режим переключается на линейный рост:

- **Additive Increase** — +1 MSS на RTT
- **Multiplicative Decrease** — при потере `cwnd = cwnd / 2`

**Современные алгоритмы:**

- **CUBIC** — по умолчанию в Linux, Windows (агрессивный рост через кубическую функцию)
- **BBR** — от Google, основан на измерении пропускной способности и RTT (не потерь)

### Потери пакетов и восстановление

**Сценарий потери:**

```
Сервер                         Клиент
  |                               |
  |--- Байты 0-100 -------------->|  (Получил, ACK до 100)
  |<-- ACK 100 -------------------|
  |                               |
  |--- Байты 101-200 -------------X  (ПОТЕРЯНЫ)
  |                               |
  |--- Байты 201-300 ------------>|  (Получил, но дырка 101-200)
  |<-- DupACK 100 ----------------|  (Повторный ACK до 100)
  |                               |
  |--- Байты 301-400 ------------>|  (Ещё дырка)
  |<-- DupACK 100 ----------------|
  |                               |
  |--- Байты 401-500 ------------>|
  |<-- DupACK 100 ----------------|  (3-й DupACK — триггер Fast Retransmit)
  |                               |
  |--- Байты 101-200 ------------>|  (Retransmit — повторная отправка)
  |<-- ACK 500 -------------------|  (Теперь всё получено)
```

**Правила:**

- **1-2 DupACK** — возможна пересортировка пакетов, ждём
- **3+ DupACK** — потеря подтверждена, Fast Retransmit
- **Тайм-аут** — скорость падает до 0, перезапуск Slow Start

**Допустимый уровень потерь:**

- **< 0,1%** — норма, случайные потери
- **> 1%** — проблема, скорость будет плавать

## Практические сценарии

### Подготовка к анализу

#### Добавление столбцов для анализа производительности

Для эффективного анализа добавьте следующие столбцы:

1. **Delta Time (отображаемого пакета)**:
   - Поле: `frame.time_delta_displayed`
   - Показывает разницу между **отображёнными** пакетами (учитывает фильтры)
   - **Важно:** нельзя сортировать при >20k пакетов

2. **Delta Time (захваченного пакета)**:
   - Поле: `frame.time_delta`
   - Показывает разницу между **всеми захваченными** пакетами
   - Можно сортировать при любом количестве

3. **TCP Segment Len**:
   - Поле: `tcp.len`
   - Размер полезных данных в сегменте

4. **Calculated Window Size**:
   - Поле: `tcp.window_size_value`
   - Размер окна, объявленный стороной

5. **Bytes in Flight**:
   - Поле: `tcp.analysis.bytes_in_flight`
   - Байты отправленные но ещё не подтверждённые

**Как добавить:**

```
Packet Details → Transmission Control Protocol →
Правая кнопка на поле → Apply as Column
```

#### Переименование IP-адресов

Для удобства анализа:

```
Правая кнопка на IP → Edit Resolved Name → Ввести имя (например, "client", "server")
```

#### Поиск наиболее активного потока

```
Statistics → Conversations → TCP →
Сортировка по Bytes → Правая кнопка → Apply as Filter → Selected → On Stream ID
```

## Дополнительная информация

### Формулы

**Максимальная пропускная способность:**

```
Throughput ≤ Window Size / RTT

Пример:
Window = 64 KB, RTT = 100 ms
Throughput ≤ 65536 / 0.1 = 655 KB/s ≈ 5.2 Мбит/с
```

**Требуемый размер окна:**

```
Window ≥ Throughput × RTT

Пример:
Throughput = 1 Гбит/с, RTT = 50 ms
Window ≥ 125 MB/s × 0.05 = 6.25 MB
```

**Bandwidth-Delay Product (BDP):**

```
BDP = Bandwidth × RTT

Пример:
Bandwidth = 1 Гбит/с, RTT = 50 ms
BDP = 125 MB/s × 0.05 = 6.25 MB
```

### Предупреждения

1. **Offloading может создавать ложные ошибки** — всегда проверяйте Throughput
2. **Delta Time не сортируется при >20k пакетов** — используйте `frame.time_delta`
3. **Захват на одной стороне может быть недостаточен** — для диагностики сети нужен захват с двух сторон
4. **Современные алгоритмы (BBR, CUBIC) сложнее старых** — поведение может отличаться от классического AIMD
