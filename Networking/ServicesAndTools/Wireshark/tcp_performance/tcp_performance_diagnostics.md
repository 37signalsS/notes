# Wireshark: диагностика производительности TCP — обзор

## Определения

**Диагностика производительности TCP** — комплексный метод анализа сетевого трафика в Wireshark, направленный на выявление причин замедления передачи данных на стороне сервера, клиента или в сетевой инфраструктуре.

**Ключевые метрики:**
- **RTT (Round-Trip Time)** — время кругового обхода; интервал от отправки сегмента до получения подтверждения (ACK) на него.
- **Delta Time** — временной интервал между пакетами (позволяет увидеть задержки на конкретной стороне).
- **Throughput (Пропускная способность)** — фактическая скорость передачи полезных данных в единицу времени.
- **Window Size (Размер окна)** — объем данных, которые приемник готов принять без подтверждения.
- **Bytes in Flight** — объем данных, которые уже отправлены, но еще не подтверждены приемником.
- **Retransmit (Повторная передача)** — переотправка пакета из-за его потери или истечения тайм-аута ожидания.
- **DupACK (Duplicate ACK)** — повторное подтверждение одного и того же сегмента, часто указывающее на потерю последующего пакета.

## Основные концепции

### Механизмы адаптации скорости TCP

Протокол TCP динамически подстраивается под состояние канала связи. Скорость передачи ограничена двумя факторами:

1.  **Окно перегрузки (cwnd — congestion window)**: Определяется отправителем на основе задержек и потерь в сети. Подробнее в **[управлении перегрузкой](../../Protocols/TCP/congestion/tcp_congestion_control_overview.md)**.
2.  **Окно получателя (rwnd — receiver window)**: Определяется свободным местом в буфере приложения на приемной стороне. Подробнее в **[Flow Control](../../Protocols/TCP/Flow_Control/index.md)**.

Эффективное окно (объем данных, который можно отправить) всегда равно минимальному из этих двух значений.

### Потери пакетов и их влияние

TCP обнаруживает потери двумя основными способами:
- **Fast Retransmit**: При получении трех одинаковых DupACK отправитель немедленно переотправляет потерянный сегмент. Это «здоровая» реакция на единичные потери.
- **RTO (Retransmission Timeout)**: Если подтверждения не приходят долго, срабатывает тайм-аут. Это приводит к резкому падению скорости (сброс окна до 1 MSS — Maximum Segment Size) и перезапуску алгоритма Slow Start.

**Нормативы потерь:**
- **< 0.1%**: Нормальная работа.
- **0.1% – 1%**: Требуется анализ (возможны периодические деградации скорости).
- **> 1%**: Критическая проблема, требующая исправления на физическом или канальном уровне.

### Влияние технологий разгрузки (Offloading)

Технологии TSO (TCP Segmentation Offload), GRO (Generic Receive Offload) и LRO (Large Receive Offload) переносят обработку пакетов на сетевую карту (NIC — Network Interface Card). 

В Wireshark это создает **ложные аномалии**:
- Пакеты, размер которых значительно превышает MSS.
- Сообщения о неверных контрольных суммах (Checksum Errors).
- Ложные уведомления о повторных передачах.

При анализе всегда проверяйте график Throughput: если скорость стабильна и высока, ошибки в Expert Info, скорее всего, вызваны offloading. Подробнее в разделе **[диагностика offloading](./tcp_network_losses_and_offloading.md)**.

## Практические сценарии

### Настройка интерфейса для глубокого анализа

Для эффективной диагностики добавьте следующие поля в качестве столбцов (`Apply as Column`):
- `frame.time_delta_displayed` — время между отображаемыми пакетами.
- `tcp.analysis.bytes_in_flight` — текущий объем неподтвержденных данных.
- `tcp.window_size_value` — объявленное окно приемника.

### Чек-лист экспресс-диагностики

| Симптом | Вероятная причина | Место поиска |
| :--- | :--- | :--- |
| Паузы при низком RTT (микросекунды) | **Сервер** медленно обрабатывает запросы | [Проблемы сервера](./tcp_server_performance_issues.md) |
| Паузы при высоком RTT (миллисекунды) | **Сеть** перегружена или велики задержки | [Сетевые потери](./tcp_network_losses_and_offloading.md) |
| События `TCP Window Full` или `Zero Window` | **Клиент** не успевает забирать данные из буфера | [Проблемы клиента](./tcp_client_performance_issues.md) |
| Регулярные провалы скорости до нуля | **Потери пакетов** и срабатывание тайм-аутов RTO | [Управление перегрузкой](../../Protocols/TCP/congestion/tcp_congestion_control_overview.md) |

### Поиск самого активного потока

1. Перейдите в `Statistics → Conversations`.
2. Выберите вкладку `TCP` и отсортируйте список по колонке `Bytes`.
3. Нажмите правой кнопкой мыши на топ-потоке → `Apply as Filter → Selected → On Stream ID`.
4. Теперь весь интерфейс Wireshark сфокусирован только на этом соединении.

## Дополнительная информация

### Математические зависимости

**Максимальная теоретическая скорость (Throughput):**
`Throughput ≤ (Window Size / RTT)`

**Требуемый размер окна для полной загрузки канала (BDP — Bandwidth-Delay Product):**
`Window ≥ (Target Bandwidth × RTT)`

Пример: для канала 1 Гбит/с и RTT 50 мс требуется окно не менее 6.25 Мбайт. Если буферы ОС ограничены 64 Кбайт, скорость не превысит 10 Мбит/с независимо от ширины канала. Оптимизация описана в **[настройке буферов TCP](../../../../Linux/Networking/Concepts/tcp_tuning/tcp_buffer_tuning.md)**.
