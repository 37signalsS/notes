# Диагностика проблем производительности сервера TCP

## Определения

**Задержка на стороне сервера (Server-Side Latency)** — временные интервалы между отправкой последовательных порций данных сервером при условии, что клиент подтверждает получение практически мгновенно (низкий RTT).

**Троттлинг ресурсов (Resource Throttling)** — принудительное ограничение скорости обработки данных из-за достижения лимитов по CPU (процессор), I/O (ввод-вывод) или квот в контейнеризованных средах (Docker, Kubernetes).

## Основные концепции

### Признаки замедления работы сервера

Когда сервер становится «бутылочным горлышком» в передаче данных, в трафике наблюдаются следующие паттерны:

1.  **Длительные паузы в отправке**: Сервер задерживает отправку следующего сегмента на 10–100+ мс, в то время как сеть позволяет передавать данные за микросекунды.
2.  **Быстрые подтверждения (ACK)**: Клиент отправляет подтверждения немедленно, RTT (Round-Trip Time) остается стабильно низким.
3.  **Нестабильная пропускная способность**: График скорости имеет «пилообразный» вид с резкими провалами в моменты внутренних задержек сервера.

### Типичные причины задержек

-   **Лимиты CPU**: Ограничения cgroups в Docker-контейнерах приводят к приостановке процесса при превышении квоты.
-   **Блокирующий ввод-вывод**: Приложение ожидает завершения чтения с диска или ответа от базы данных перед отправкой следующей порции данных в сокет.
-   **Сборка мусора (Garbage Collection — GC)**: Паузы «Stop-the-world» в Java, Go или Python полностью останавливают выполнение бизнес-логики.
-   **Конкуренция за ресурсы**: Другие процессы на том же хосте потребляют ресурсы, необходимые для обработки сетевого стека.

## Практические сценарии

### Диагностика в Wireshark

Для подтверждения того, что задержка происходит именно на сервере, используйте следующий алгоритм:

#### 1. Анализ графика Time-Sequence (Stevens)
Перейдите в `Statistics → TCP Stream Graphs → Time-Sequence (Stevens)`.
- Горизонтальные линии на графике означают периоды простоя, когда новые данные не отправлялись.

#### 2. Проверка стабильности RTT
Используйте `Statistics → TCP Stream Graphs → Round Trip Time Graph`.
- Если RTT стабилен и мал (например, < 1 мс), а паузы между отправками велики — проблема однозначно на стороне отправителя (сервера).

#### 3. Сортировка по Delta Time
Добавьте столбец `frame.time_delta` и отсортируйте пакеты по убыванию.
- Если в топе списка находятся пакеты, отправленные сервером, это указывает на внутренние задержки приложения или ОС сервера.

### Поиск причин на стороне ОС сервера

Если анализ трафика подтвердил вину сервера, выполните следующие проверки на хосте:

-   **Загрузка CPU**: Команда `top -H` (просмотр нагрузки по потокам).
-   **Лимиты контейнера**: `docker stats` для проверки потребления ресурсов относительно лимитов.
-   **Дисковая активность**: `iostat -x 1` (высокое значение `%util` указывает на перегрузку дисковой подсистемы).
-   **Логи приложения**: Поиск записей о медленных запросах или длительных паузах GC.

### Методы устранения

-   **CPU**: Увеличение лимитов в Kubernetes (CPU shares/quota) или оптимизация алгоритмов.
-   **I/O**: Переход на SSD (Solid State Drive — твердотельный накопитель) или использование асинхронных методов записи.
-   **Сеть**: Проверка параметров `tcp_wmem` (буферы отправки) в настройках ядра Linux.
