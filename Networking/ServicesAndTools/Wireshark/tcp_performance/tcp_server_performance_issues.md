# Диагностика проблем производительности сервера TCP

## Определения

**Серверная задержка (Server-Side Latency)** — паузы в отправке данных со стороны сервера при быстром подтверждении от клиента (низкий RTT).

**Троттлинг ресурсов** — искусственное ограничение скорости передачи из-за нехватки CPU, I/O или ограничений контейнеризации (cgroups, Docker limits).

---

## Basic Concepts

### Механизм проблемы «тормозит сервер»

Когда сервер не успевает обрабатывать запросы, происходят следующие события:

1. **Пауза в отправке** — сервер задерживает пакеты на 10–100+ ms вместо микросекунд
2. **Клиент подтверждает быстро** — RTT от клиента в микросекундах, проблема не на его стороне
3. **Throughput падает** — «пилообразный» график с периодическими провалами
4. **Причина** — сервер не успевает генерировать/читать данные для отправки

### Типичные причины

| Причина | Описание |
| :--- | :--- |
| **Ограничение CPU** | Docker container, cgroups ограничивают процессорное время |
| **Блокировка приложения** | I/O операции, блокировки (locks), сборка мусора (GC) |
| **Нехватка ресурсов** | Недостаточно CPU, памяти, дискового I/O |
| **Блокирующие вызовы** | Синхронные операции в обработчике запросов |

## Practical Scenarios

### Сценарий: Тормозит сервер

**Симптомы:**

- Большие задержки между пакетами **на стороне сервера**
- Клиент подтверждает быстро (RTT в микросекундах)
- Паузы в передаче данных без видимых причин

### Диагностика в Wireshark

#### 1. Построить график Time-Sequence (Stevens)

```
Statistics → TCP Stream Graphs → Time-Sequence (Stevens)
```

- Паузы видны как горизонтальные линии
- По одному графику неясно, на чьей стороне проблема

#### 2. Проверить RTT

```
Statistics → TCP Stream Graphs → Round Trip Time Graph
```

- Стабильный низкий RTT (микросекунды) → клиент работает быстро
- Если RTT высокий → проблема на стороне получателя

#### 3. Отсортировать по Delta Time

- Сортировка по убыванию (`frame.time_delta`)
- Если в топе пакеты с задержкой от сервера → проблема на сервере

#### 4. Проверить Throughput

```
Statistics → TCP Stream Graphs → Throughput
```

- «Пилообразный» график с паузами → троттлинг ресурсов

### Пример диагностики

```
Сервер отправляет пакет → Пауза 82ms → Отправляет следующий
Клиент подтверждает через 125μs (быстро)
RTT стабильный на уровне микросекунд
Вывод: сервер тормозит
```

### Диагностика на стороне сервера

**1. Проверить использование CPU:**

```bash
top -H -p <pid_приложения>
```

**2. Проверить ограничения Docker:**

```bash
docker stats <container>
docker inspect <container> | grep -i cpu
```

**3. Проверить I/O:**

```bash
iostat -x 1
iotop
```

**4. Проверить логи приложения** — поиск блокирующих операций, долгих запросов к БД, GC-пауз.

### Решение

- **CPU bottleneck** — увеличить лимиты cgroups/Docker, оптимизировать код
- **I/O bottleneck** — перейти на SSD, использовать асинхронный I/O
- **Блокировки** — профилирование приложения (pprof, async-profiler)
- **GC-паузы** — настройка GC, уменьшение allocation rate
