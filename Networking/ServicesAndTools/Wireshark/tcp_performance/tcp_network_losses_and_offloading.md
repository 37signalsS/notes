# Диагностика потерь в сети и влияние offloading на анализ TCP

## Определения

**Retransmission (Retransmit)** — повторная отправка TCP-сегмента из-за потери пакета или истечения тайм-аута.

**Fast Retransmission** — повторная отправка после получения 3 Duplicate ACK, без ожидания тайм-аута.

**Duplicate ACK (DupACK)** — повторное подтверждение, указывающее на получение пакетов не по порядку; множественные DupACK сигнализируют о потере.

**Out-Of-Order (OOO)** — пакеты прибыли не в порядке отправки, что может указывать на мультипатную маршрутизацию или ретрансмиты.

**Offloading** — делегирование обработки TCP (TSO, GRO, LRO, Checksum) сетевой карте или драйверу. Подробности — в [Network Offloading: GRO/LRO/TSO](../../../../Linux/Networking/Concepts/offloading.md).

## Basic Concepts

### Механизм потерь в сети

TCP обнаруживает потери двумя способами:

1. **Timeout-based Retransmit** — тайм-аут RTO истекает без ACK → повторная отправка через ~200ms–1s
2. **Fast Retransmit** — 3 DupACK → немедленная повторная отправка без ожидания тайм-аута

После обнаружения потери TCP снижает скорость через механизм **Congestion Avoidance** (уменьшение congestion window).

### Влияние offloading на анализ в Wireshark

Wireshark захватывает пакеты **до** обработки offloading на уровне драйвера/NIC, что приводит к ложным артефактам:

| Артефакт | Причина | Как распознать |
| :--- | :--- | :--- |
| **Пакеты > MSS (64KB)** | TSO/GSO — сегментация ещё не выполнена | TCP Segment Len > 1460 байт |
| **Неверные контрольные суммы** | Checksum Offloading — NIC ещё не вычислила | Bad checksum в Wireshark, но трафик идёт |
| **Ложные Retransmit** | GRO/LRO — агрегация пакетов на RX | «Ретрансмиты» без падения throughput |

### Процент потерь — интерпретация

| Процент потерь | Статус |
| :--- | :--- |
| **< 0,1%** | Норма, случайные потери |
| **0,1–1%** | Допустимо, но требует наблюдения |
| **> 1%** | Проблема сети, требуется диагностика |

### Сценарии offloading в контексте Wireshark

- **Отключить offloading** для «чистого» захвата: `ethtool -K eth0 tso off gso off gro off`
- **Включить обратно** после тестов — обязательно для производительности
- Некоторые NIC позволяют захватывать **после** offloading (режим промискуитета)

## Practical Scenarios

### Сценарий 1: Потери в сети

**Симптомы:**

- Много ретрансмитов и DupACK
- Скорость передачи периодически падает до нуля
- RTT нестабильный

#### Диагностика

**1. Проверить Expert Information:**

```
Analyze → Expert Information
```

Искать: `Retransmission`, `Fast Retransmission`, `Out-Of-Order`, `DupACK`. Подсчитать процент ошибок:

```
(Retransmits / Total Packets) × 100%
```

**2. IO Graph для визуализации потерь:**

```
Statistics → IO Graphs
```

- Добавить фильтр: `tcp.analysis.retransmission`
- Красная линия — ошибки, чёрная — все пакеты
- Axis Factor: ×10 или ×100, Interval: 100ms

**3. Пример диагностики:**

```
Всего пакетов: 10 000
Retransmissions: 1 300 (13%)
График IO Graph: регулярные провалы до 0
Вывод: серьёзные потери в сети
```

#### Причины и решения

| Причина | Решение |
| :--- | :--- |
| **Плохой сигнал Wi-Fi** | Проверить уровень сигнала, переключиться на 5 ГГц |
| **Перегруженность канала** | Проверить загрузку канала, сменить частоту |
| **Повреждение кабеля** | Заменить кабель, проверить коннекторы |
| **Ошибки оборудования** | Проверить логи свитчей/роутеров |

---

### Сценарий 2: Ограничение скорости сети

**Симптомы:**

- Нет потерь (< 0,1%)
- Скорость стабильная, но низкая
- RTT в норме

#### Диагностика

**1. Сравнить трафик с двух сторон:**

- Захват на клиенте и сервере одновременно
- Сравнить Delta Time

**2. Анализ задержек:**

- Клиент видит задержку получения ответа: 136ms
- Сервер видит задержку отправки: 34ms
- Разница (102ms) — задержка в сети

**3. Throughput график:**

```
Statistics → TCP Stream Graphs → Throughput
```

- Стабильная линия без провалов → скорость ограничена на постоянном уровне

#### Причины

| Причина | Описание |
| :--- | :--- |
| **Ограничение провайдера** | Шейперы на стороне ISP |
| **Низкая пропускная способность** | Физическое ограничение канала |
| **QoS политики** | Приоритизация трафика |

---

### Сценарий 3: Ложные ошибки из-за offloading

**Симптомы:**

- Expert Information показывает много Retransmit/DupACK
- Throughput стабильный, без провалов до 0
- Пакеты больше MSS (например, 64KB вместо 1460 байт)

#### Диагностика

**1. Проверить размер сегментов:**

Добавить столбец `TCP Segment Len`. Если размер > MSS (1460 байт) → offloading включён.

**2. Сравнить с Expert Information:**

- Много ошибок в Expert Info
- Но throughput не падает → ложные ошибки

**3. Проверить статус offloading:**

```bash
# Проверка
ethtool -k eth0 | grep offload

# Отключение для чистого захвата
ethtool -K eth0 tso off gso off gro off
```

> **Важно:** после тестов включить обратно! Offloading критичен для производительности.
