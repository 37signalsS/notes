# Методы расшифровки TLS-трафика

## Определения

**Расшифровка TLS (Transport Layer Security)** — процесс получения доступа к содержимому защищенного соединения с использованием ключей сессии или промежуточных секретов, полученных на этапе установления связи (handshake).

**SSLKEYLOGFILE** — стандартный текстовый формат файла для записи TLS-ключей. Поддерживается браузерами (Chrome, Firefox), приложениями на базе Electron и инструментами перехвата трафика (Mitmproxy).

**SSL Pinning** — механизм безопасности, при котором приложение проверяет соответствие сертификата сервера заранее заданному отпечатку (хешу). Это блокирует работу классических MITM-прокси.

**PFS (Perfect Forward Secrecy — совершенная прямая секретность)** — свойство протоколов шифрования, гарантирующее, что компрометация долгосрочного приватного ключа сервера не позволит расшифровать прошлые сессии захваченного трафика.

## Основные концепции

### Различия между TLS 1.2 и TLS 1.3

Процесс расшифровки существенно зависит от версии протокола. Подробный разбор механики — в разделе **[Протокол TLS](../../Protocols/tls.md)**.

| Аспект | TLS 1.2 | TLS 1.3 |
| :--- | :--- | :--- |
| **Алгоритмы обмена** | RSA и (EC)DHE | Только (EC)DHE (PFS по умолчанию) |
| **Расшифровка ключом сервера** | Возможна для RSA-шифров | Невозможна (RSA удален) |
| **Формат логов ключей** | Одна запись `CLIENT_RANDOM` | Множество записей для разных фаз сессии |
| **Шифрование Handshake** | Частично открытый | Почти полностью зашифрован |

### MITM (Man-in-the-Middle — человек посередине)

Метод анализа, при котором между клиентом и сервером устанавливается прокси-сервер, подменяющий сертификат целевого ресурса на свой собственный. Это позволяет прокси-серверу расшифровывать, просматривать и модифицировать трафик на лету.

### Ограничения анализа

- **Эфемерные ключи**: При использовании PFS (ECDHE) ключи действительны только для текущей сессии. Их необходимо захватывать в реальном времени.
- **SSLKEYLOGFILE**: Работает только для приложений, которые явно поддерживают экспорт ключей через переменную окружения.
- **Доверие сертификатам**: Для работы MITM-прокси необходимо вручную установить корневой сертификат прокси в хранилище доверенных сертификатов ОС или браузера.

## Практические сценарии

### Сценарий 1: Расшифровка трафика браузера через SSLKEYLOGFILE

Это основной метод для отладки веб-приложений.

1. **Настройка окружения**: Создайте переменную `SSLKEYLOGFILE`.

    ```bash
    export SSLKEYLOGFILE=~/tls-debug.log
    ```

2. **Запуск приложения**: Запустите браузер (Chrome, Firefox) или Electron-приложение из того же терминала.
3. **Настройка Wireshark**:
    - `Edit → Preferences → Protocols → TLS`.
    - В поле `(Pre)-Master-Secret log filename` укажите путь к `~/tls-debug.log`.
4. **Результат**: В списке пакетов появятся расшифрованные данные HTTP/2 или WebSocket.

### Сценарий 2: Использование Mitmproxy для мобильных приложений

Используется, если приложение не поддерживает `SSLKEYLOGFILE`.

1. Запустите `mitmproxy` на рабочей станции.
2. Настройте на смартфоне прокси-сервер, указав IP адрес компьютера.
3. Перейдите на смартфоне на страницу `mitm.it` и установите предложенный сертификат.
4. Включите экспорт ключей в Mitmproxy: `mitmproxy --set sslkeylogfile=~/mitm-keys.log`.
5. Используйте полученный лог в Wireshark для детального разбора протоколов.

### Сценарий 3: Обход SSL Pinning через Frida

Если приложение отказывается работать через прокси из-за проверки сертификата:

1. Используйте фреймворк **Frida** для динамического внедрения в процесс приложения.
2. Загрузите скрипт обхода (unpinning), который подменяет функции проверки сертификата в памяти процесса.

    ```bash
    frida -U -f com.example.app -l universal-unpinning.js
    ```

3. После этого трафик станет доступен для перехвата через Mitmproxy или Wireshark.

### Сценарий 4: Расшифровка с использованием приватного ключа сервера

Метод применим только для старых систем (TLS 1.2 с RSA-обменом ключами) или если вы полностью контролируете серверную часть.

1. Скопируйте приватный ключ сервера (`.key` или `.pem`).
2. В Wireshark: `Edit → Preferences → Protocols → TLS → RSA keys list`.
3. Добавьте запись в формате: `IP,Порт,Протокол,Путь_к_ключу`.
4. **Ограничение**: Если сервер использует алгоритмы семейства Diffie-Hellman (PFS), расшифровка этим методом не сработает.

## Дополнительная информация

### Формат файла логов (TLS 1.3)

Современные логи ключей содержат несколько типов записей:

- `CLIENT_HANDSHAKE_TRAFFIC_SECRET`: для расшифровки этапа установления связи.
- `CLIENT_TRAFFIC_SECRET_0`: для расшифровки данных, отправленных клиентом.
- `SERVER_TRAFFIC_SECRET_0`: для расшифровки данных, отправленных сервером.
