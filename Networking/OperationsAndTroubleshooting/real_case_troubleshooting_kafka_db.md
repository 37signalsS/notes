# Реальный пример траблшутинга: заказ не доходит до склада

## 1. Вводная информация

**Проблема:** Пользователи создают заказы на посадочной странице, но склад их не видит.
**Стек:** Неизвестен.
**Симптомы:**
-   Пользователь видит, что заказ успешно создан (получает код 200).
-   На стороне склада заказ не появляется.

## 2. План действий и пошаговый разбор

### Шаг 1: Анализ на стороне клиента

**Действие:** Открыть сайт в браузере, открыть инструменты разработчика (F12) и посмотреть, куда уходит запрос при создании заказа.
**Результат:**
-   Уходит `POST` запрос на эндпоинт `/orders` одного из серверов компании.
-   IP-адрес сервера известен.

### Шаг 2: Исследование первого сервера (Nginx)

**Действие:** Подключиться к серверу по SSH.
**Результат:**
-   На сервере запущен только `Nginx`. Вероятно, это балансировщик нагрузки или прокси-сервер.

**Действие:** Изучить конфигурацию Nginx (`/etc/nginx/nginx.conf` и `sites-available/*`).
**Результат:**
-   Найден `proxy_pass`, который перенаправляет запросы на `upstream` с несколькими серверами.

**Действие:** Проверить логи Nginx (`/var/log/nginx/access.log` и `error.log`).
**Результат:**
-   В `access.log` виден `POST` запрос на `/orders` с кодом ответа 200. Ошибок в `error.log` нет.
-   Это подтверждает, что Nginx отрабатывает корректно и проблема дальше по цепочке.

### Шаг 3: Исследование второго сервера (Application)

**Действие:** Подключиться по SSH к одному из серверов из `upstream`.
**Результат:**
-   На сервере запущено приложение на Python (Gunicorn/Flask).
-   Код приложения лежит в `/home/application`.

**Действие:** Изучить код приложения.
**Результат:**
-   В `requirements.txt` найден `Flask`.
-   В коде найдена функция, обрабатывающая эндпоинт `/orders`.
-   Функция отправляет сообщение в `Kafka`.

**Действие:** Найти креды для подключения к Kafka.
**Результат:**
-   Найден `docker-compose.yml`, в котором прописаны переменные окружения для подключения к Kafka (адрес брокера, топик).
-   Приложение работает как `producer`.

### Шаг 4: Исследование Kafka

**Действие:** Проверить состояние топика в Kafka.
**Результат:**
-   Используя дашборд Grafana для Kafka, видно, что **лага в топике нет**.
-   Это означает, что сообщения успешно отправляются в топик и кто-то их читает (есть `consumer`).

**Действие:** Найти консьюмеров этого топика.
**Результат:**
-   В Wiki найдено несколько консьюмеров: `Store`, `Manager` и др.
-   Логичный кандидат — `Store` (склад).

**Действие:** Проверить состояние консьюмера `Store`.
**Результат:**
-   В дашборде видно, что консьюмер пытается читать сообщения, но, судя по графику, безуспешно.

### Шаг 5: Исследование третьего сервера (Consumer)

**Действие:** Найти логи консьюмера `Store` в [Elasticsearch](../Elasticsearch/elasticsearch_sharding_replication_cluster.md).
**Результат:**
-   В логах найдены ошибки: **"не могу подключиться к базе данных"**.
-   В сообщении об ошибке указан хост базы данных.

### Шаг 6: Исследование четвертого сервера (Database)

**Действие:** Подключиться по SSH к серверу базы данных.
**Результат:**
-   На сервере запущена база данных `PostgreSQL` в `Docker`-контейнере.

**Действие:** Проверить статус контейнера с базой данных.
**Результат:**
-   Контейнер **упал**.

**Действие:** Посмотреть логи контейнера (`docker logs <container_id>`).
**Результат:**
-   Первоначальная ошибка: **"порт занят"** (`Port is already allocated`).
-   После попытки перезапуска ошибка изменилась на **"ошибка, связанная с диском"**.

**Действие:** Проверить права доступа к директории, которую использует контейнер (`/var/lib/postgresql/data`).
**Результат:**
-   Права доступа в порядке.

**Действие:** Проверить наличие свободного места и айнодов (inodes) на диске.
**Результат:**
-   `df -h`: Место на диске есть.
-   `df -i`: **Айноды закончились (100% использование)**.

### Шаг 7: Локализация и решение проблемы

**Причина:** На хосте с базой данных закончились свободные айноды. Это произошло из-за другого тестового контейнера, который писал огромное количество мелких лог-файлов, исчерпав все доступные айноды на файловой системе. Из-за этого PostgreSQL не мог создать свои служебные файлы и запуститься.

**Решение:**
1.  Остановить тестовый контейнер, который генерировал логи.
2.  Удалить ненужные лог-файлы, чтобы освободить айноды.
3.  Запустить контейнер с базой данных. Он успешно стартовал.

**Финальные действия:**
-   Проблема решена, но заказы, которые были отправлены в Kafka, пока база была недоступна, "потерялись" для склада.
-   **Необходимо сбросить offset для консьюмера `Store` в Kafka**, чтобы он перечитал сообщения из топика, которые не смог обработать.

## 3. Выводы

-   Проблема не всегда там, где кажется на первый взгляд.
-   Важно последовательно проверять всю цепочку прохождения запроса.
-   Мониторинг (логи, метрики) — ключ к быстрому обнаружению аномалий.
-   Нехватка айнодов — неочевидная, но реальная проблема, особенно при использовании Docker и неправильной настройке логирования.
