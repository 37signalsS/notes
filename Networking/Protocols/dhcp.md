# DHCP (Dynamic Host Configuration Protocol)

### Определения

**DHCP (Dynamic Host Configuration Protocol / Протокол динамической конфигурации хоста)** — протокол прикладного уровня (уровень 7 модели OSI/ISO), предназначенный для автоматической конфигурации сетевых параметров устройств в IP-сетях. Описан в **RFC 2131**.

Для корректной работы хоста в сети необходимы:

- Собственный IP-адрес и маска подсети
- Адрес шлюза по умолчанию (gateway)
- Адреса DNS-серверов

Ключевые компоненты архитектуры DHCP:

- **DHCP-сервер:** Центральный узел (часто выделенный сервер или функция на маршрутизаторе), который управляет пулом IP-адресов и отвечает на запросы клиентов.
- **DHCP-клиент:** Программное обеспечение на любом устройстве (компьютер, смартфон, принтер), которое запрашивает сетевые настройки у сервера.
- **DHCP Relay Agent (Агент ретрансляции):** Маршрутизатор или хост, который пересылает DHCP-сообщения между клиентами и серверами, находящимися в разных широковещательных доменах (подсетях).

**Транспортный уровень:** DHCP использует протокол **UDP**:
- **DHCP-сервер** слушает порт **67/UDP**
- **DHCP-клиент** слушает порт **68/UDP**

Разные порты используются для того, чтобы DHCP-клиент не обрабатывал сообщения, предназначенные для сервера, и наоборот.

### Основные концепции

#### Принцип работы (процесс DORA)

Взаимодействие между клиентом и сервером описывается последовательностью из четырех шагов, известной как **DORA**: **D**iscover, **O**ffer, **R**equest, **A**cknowledge.

1. **Discovery (Обнаружение)**:
    - **Действие:** Клиент, еще не имея IP-адреса, отправляет в свою локальную сеть широковещательное сообщение `DHCPDISCOVER`.
    - **Цель:** Найти все доступные DHCP-серверы в своем широковещательном домене.
    - **Детали:**
        - Запрос отправляется на канальном уровне на MAC-адрес `FF:FF:FF:FF:FF:FF` и на сетевом уровне на IP-адрес `255.255.255.255`. В качестве обратного IP-адреса указывается `0.0.0.0`
        - **Поле `chaddr` (Client Hardware Address):** содержит MAC-адрес клиента. Это поле критично: DHCP-сервер использует его для отправки ответа, так как у клиента ещё нет IP-адреса. Без этого поля сервер не знал бы, куда отправлять `DHCPOFFER`
        - **Поле `op`:** установлено в `1` (Boot Request)
        - **Опция Message Type:** Discover
        - Почти все остальные поля заполнены нулями
        - Сообщение получают и обрабатывают все хосты в сети

2. **Offer (Предложение):**
    - **Действие:** Все DHCP-серверы, получившие `DHCPDISCOVER`, отвечают клиенту сообщением `DHCPOFFER`.
    - **Цель:** Предложить клиенту IP-адрес и другие сетевые параметры (маску, шлюз, DNS и т.д.).
    - **Детали:**
        - **ICMP Echo Request перед OFFER (ping check):** Перед формированием `DHCPOFFER` сервер отправляет в сеть ICMP Echo Request на IP-адрес, который собирается предложить клиенту. Если ответа не последует в течение таймаута, сервер считает адрес свободным и включает его в предложение. Это защита от выдачи уже занятого адреса
        - Ответ отправляется на MAC-адрес клиента
        - **IP-адрес получателя (Destination):** равен предлагаемому IP-адресу (например, `10.10.10.108`). DHCP-сервер ставит предлагаемый IP в качестве адреса получателя, так как у клиента ещё нет своего IP, а отправлять на `0.0.0.0` нельзя
        - **Поле `yiaddr` (Your IP Address):** содержит предлагаемый клиенту IP-адрес (например, `10.10.10.108`)
        - **Поле `siaddr` (Server IP Address):** содержит IP-адрес следующего сервера для конфигурации (например, `10.10.10.1` — адрес TFTP-сервера для PXE)
        - **Bootp flags (Unicast/Broadcast):** Поле флагов в сообщении `DHCPOFFER` определяет способ доставки ответа:
          - **Unicast:** Сервер отправляет ответ напрямую на MAC-адрес клиента (поле `Bootp flags` = Unicast). Используется по умолчанию, если клиент может принимать unicast-трафик до получения IP
          - **Broadcast:** Сервер отправляет ответ на широковещательный адрес `255.255.255.255` (поле `Bootp flags` = Broadcast). Используется, если клиент не способен принимать unicast-пакеты без IP-адреса
        - Клиент может получить несколько предложений, если в сети работает более одного DHCP-сервера
        - **Важно:** В сообщении `DHCPOFFER` сервер только предлагает настройки — они ещё никому не выданы

3. **Request (Запрос):**
    - **Действие:** Клиент выбирает одно из предложений (обычно первое полученное) и отправляет широковещательное сообщение `DHCPREQUEST`.
    - **Цель:** Сообщить выбранному серверу о принятии его предложения и уведомить все остальные DHCP-серверы об отказе от их предложений.
    - **Детали:**
        - **Широковещательная рассылка:** Сообщение отправляется на адреса `255.255.255.255` (IP) и `FF:FF:FF:FF:FF:FF` (канальный уровень), даже если клиент уже знает IP и MAC-адрес DHCP-сервера
        - **Причина широковещания:** В сети могут работать несколько DHCP-серверов. Клиент мог получить несколько `DHCPOFFER`. Широковещательное сообщение позволяет всем DHCP-серверам увидеть выбор клиента и освободить зарезервированные IP-адреса
        - **ARP-проверка перед REQUEST (gratuitous ARP):** Перед отправкой запроса многие клиенты выполняют самообращенный ARP-запрос на предложенный IP-адрес, чтобы обнаружить конфликт IP-адресов. Если другой хост откликается, клиент отправляет `DHCPDECLINE` и начинает процесс заново
        - Сообщение `DHCPREQUEST` содержит идентификатор выбранного сервера
        - **Опции в DHCP REQUEST:**
            - **DHCP Server Identifier:** указывает на выбранный DHCP-сервер (например, `10.10.10.1`)
            - **DHCP Message Type:** равен `Request`
            - **Client Identifier:** содержит MAC-адрес клиента
            - **Requested IP Address:** равен IP-адресу из `DHCPOFFER` (поле `yiaddr`), например `10.10.10.108`

4. **Acknowledgement (Подтверждение):**
    - **Действие:** Выбранный сервер финализирует процесс, отправляя клиенту сообщение `DHCPACK`.
    - **Цель:** Подтвердить выделение IP-адреса и передать полный набор сетевых параметров, включая время аренды (Lease Time).
    - **Детали:**
        - После получения `DHCPACK` клиент применяет настройки и может полноценно работать в сети
        - Сервер помечает IP-адрес как занятый
        - **Поле `yiaddr`:** содержит выдаваемый клиенту IP-адрес
        - **Опции в DHCP ACK:**
            - **Subnet Mask:** маска подсети (например, `255.255.255.0`)
            - **Domain Name Server (DNS):** IP-адрес DNS-сервера для разрешения имён (например, `yandex.ru`) в IP-адреса
            - **Router:** маршрутизатор по умолчанию (шлюз), например `10.10.10.1`
            - **IP Address Lease Time:** время аренды в секундах (например, `186400` секунд)
            - **Renewal Time Value (T1):** время, через которое клиент должен продлить аренду (обычно 50% от Lease Time, например `93200` секунд)
            - Другие параметры (NTP, domain name и т.д.)

#### Время аренды (Lease Time)

**Время аренды (Lease Time)** — это срок, на который DHCP-сервер выдает IP-адрес клиенту. Это ключевой механизм, позволяющий эффективно управлять пулом адресов.

- **Принцип работы:** Если бы адреса выдавались навсегда, они бы быстро закончились, особенно в сетях с высокой текучестью устройств (например, гостевые Wi-Fi сети). Аренда позволяет автоматически возвращать неиспользуемые адреса в пул.
- **Пример:** Клиент подключился к Wi-Fi в кафе, выпил кофе, проверил почту и ушёл. Выданный IP-адрес ему больше не нужен, и сервер должен иметь возможность выдать его другому клиенту.
- **Продление аренды:** Клиент не ждет окончания срока. По истечении 50% времени аренды (T1) он пытается продлить ее, отправляя `DHCPREQUEST` своему серверу. Если сервер недоступен, по истечении 87.5% времени (T2) клиент пытается связаться с любым DHCP-сервером.
- **Механизм обновления:**
  - DHCP-сервер через опции передаёт клиенту два параметра: **IP Address Lease Time** (время аренды) и **Renewal Time Value** (время обновления аренды)
  - Время обновления аренды обычно равно половине времени аренды (T1 = 50%)
  - После истечения T1 клиент отправляет `DHCPREQUEST` серверу для продления аренды
  - При получении `DHCPACK` аренда продлевается без прерывания сетевого подключения
  - Если сервер недоступен, у клиента остаётся время до T2 (87.5%) для попытки обновления у любого сервера
  - Если клиент не продлит аренду, через полное время Lease Time DHCP-сервер освободит IP-адрес и сможет выдать его другому хосту
- **Пример:** При аренде на 186 400 секунд (~52 часа), время обновления составляет 93 200 секунд (~26 часов). После 26 часов клиент начинает попытки продления, но текущий IP остаётся за ним.
- **Практические рекомендации:**
  - **Гостевые сети:** Короткое время аренды (например, от 1 до 8 часов), чтобы адреса быстрее освобождались.
  - **Корпоративные сети:** Длинное время аренды (например, от нескольких дней до месяцев), чтобы устройства сохраняли свои IP-адреса при перезагрузках или временных отключениях.

#### Способы назначения IP-адресов

DHCP поддерживает три основных способа выделения IP-адресов:

- **Динамическое назначение (Dynamic Allocation):** DHCP-сервер выдает клиенту первый свободный IP-адрес из заранее определенного пула (scope) на ограниченное время (срок аренды). Это самый распространенный способ.
- **Автоматическое назначение (Automatic Allocation):** Сервер назначает IP-адрес клиенту на неограниченный срок, запоминая выданный адрес. Похоже на динамическое назначение, но без ограничения времени аренды.
- **Статическое назначение (Static Allocation / DHCP Reservation):** Администратор вручную создает на DHCP-сервере привязку конкретного IP-адреса к MAC-адресу устройства. Этот "зарезервированный" адрес выделяется устройству при каждом запросе. Используется для серверов, принтеров и других устройств, требующих постоянного адреса.

#### Другие типы сообщений

Помимо DORA, существуют и другие сообщения:

- `DHCPNAK` (Negative Acknowledgement): Сервер отправляет отказ в ответ на `DHCPREQUEST`. Возможные причины:
  - Клиент запрашивает некорректный или уже занятый IP-адрес
  - Клиент переместился в другую подсеть, но пытается использовать старый адрес
  - Клиент в `DHCPREQUEST` запрашивает другой адрес, чем был предложен в `DHCPOFFER`
  
  После получения `DHCPNAK` клиент обязан освободить текущий адрес и заново запустить процесс DORA.

- `DHCPDECLINE`: Клиент сообщает серверу, что предложенный IP-адрес уже используется другим устройством в сети (обнаружен конфликт IP-адресов после ARP-проверки).
- `DHCPRELEASE`: Клиент информирует сервер о досрочном освобождении IP-адреса (например, при корректном выключении). Подтверждение не требуется.
- `DHCPINFORM`: Клиент, у которого уже есть IP-адрес (например, настроенный вручную), запрашивает у сервера дополнительные сетевые параметры (например, адрес DNS, NTP-сервера).

#### DHCP Relay (Ретранслятор DHCP)

**DHCP Relay** (ретранслятор DHCP) — механизм, позволяющий DHCP-клиентам и серверам находиться в разных сегментах сети. Маршрутизаторы не передают широковещательные сообщения между подсетями, поэтому для доставки DHCP-запросов используется ретранслятор.

**Сценарий использования:** В организации несколько офисов, каждый в своей IP-подсети за маршрутизатором. Вместо развертывания DHCP-сервера в каждом офисе, настраивается один центральный сервер, а на маршрутизаторах включается DHCP Relay.

**Принцип работы:**

1. **Клиент отправляет DHCP DISCOVER:**
   - Хост подключается к сети и отправляет широковещательное сообщение `DHCPDISCOVER`
   - Сообщение не выходит за пределы локального широковещательного домена

2. **DHCP Relay получает сообщение:**
   - Ретранслятор (обычно на маршрутизаторе) перехватывает широковещательный запрос
   - Добавляет свой IP-адрес в поле `giaddr` (gateway IP address)
   - Увеличивает поле `hops` (счетчик прыжков)
   - Отправляет `DHCPDISCOVER` напрямую на DHCP-сервер (unicast)

3. **DHCP-сервер обрабатывает запрос:**
   - Использует поле `giaddr` для определения подсети клиента
   - Выбирает свободный IP-адрес из пула, соответствующего подсети
   - Формирует сообщение `DHCPOFFER`
   - Отправляет ответ напрямую на ретранслятор (используя `giaddr`)

4. **DHCP Relay пересылает ответ:**
   - Получает `DHCPOFFER` от сервера
   - Пересылает сообщение клиенту в локальную подсеть

Аналогичным образом ретранслятор обрабатывает сообщения `DHCPREQUEST` и `DHCPACK`.

**Ключевые поля:**

| Поле | Описание |
|------|----------|
| `giaddr` | IP-адрес ретранслятора, указывает серверу на подсеть клиента |
| `hops` | Счетчик пройденных ретрансляторов (защита от петель) |

**Настройка:** На маршрутизаторе указывается IP-адрес DHCP-сервера, на который необходимо ретранслировать сообщения.

### Практические сценарии

#### Анализ DHCP-трафика в Wireshark

**Цель:** Изучить процесс взаимодействия DHCP-клиента и DHCP-сервера с помощью анализа сетевого трафика.

**Шаг 1: Запуск захвата трафика**

1. Запустите **Wireshark** от имени администратора
2. Выберите основной сетевой интерфейс (например, `Ethernet` или `Wi-Fi`)
3. Начните захват пакетов

**Шаг 2: Генерация DHCP-трафика**

| ОС | Команды |
|----|---------|
| **Windows** | 1. Откройте командную строку от имени администратора<br>2. `ipconfig /release` — освободить текущий IP<br>3. `ipconfig /renew` — получить новый IP |
| **macOS** | 1. Откройте терминал<br>2. `sudo ipconfig set en0 none` — освободить IP<br>3. `sudo ipconfig set en0 dhcp` — получить новый IP |
| **Linux** | 1. `sudo dhclient -r eth0` — освободить IP<br>2. `sudo dhclient eth0` — получить новый IP |

**Шаг 3: Анализ захваченных пакетов**

1. Остановите захват в Wireshark
2. Примените фильтр: `dhcp` или `bootp`
3. Изучите последовательность DORA:
   - **DHCP Discover** — широковещательный запрос от клиента
   - **DHCP Offer** — предложение от сервера
   - **DHCP Request** — запрос выбранного предложения
   - **DHCP Ack** — подтверждение выдачи адреса

**Что наблюдать:**

| Пакет | Поля для анализа |
|-------|------------------|
| **DHCP Discover** | `op=1`, `chaddr` (MAC клиента), `ciaddr=0.0.0.0`, Message Type=Discover |
| **DHCP Offer** | `op=2`, `yiaddr` (предлагаемый IP), `siaddr` (TFTP сервер), Message Type=Offer, Bootp flags (Unicast/Broadcast) |
| **DHCP Request** | Requested IP Address, DHCP Server Identifier, Message Type=Request |
| **DHCP Ack** | `yiaddr` (выданный IP), Subnet Mask, Router, DNS, Lease Time, Renewal Time (T1) |

**Пример вывода Wireshark:**


#### Освобождение и обновление DHCP-аренды

При изменении конфигурации DHCP-сервера или при возникновении проблем с подключением может потребоваться принудительное обновление аренды на клиенте. Процесс включает два этапа:

1. **Освобождение (Release):** Клиент отправляет `DHCPRELEASE` серверу, досрочно освобождая текущий IP-адрес
2. **Обновление (Renew):** Клиент инициирует новый процесс DORA для получения актуальных сетевых настроек

**Применение:**
- После изменения пула адресов на сервере
- При смене DNS-серверов или шлюза
- При устранении конфликтов IP-адресов
- После исправления ошибок в конфигурации DHCP

**Команды для освобождения адреса по ОС:**

| ОС | Команда |
|----|---------|
| **Windows** | `ipconfig /release` (в командной строке от имени администратора) |
| **macOS** | `sudo ipconfig set en0 none` (в терминале) |
| **Linux** | `sudo ifdown eth0` или `sudo dhclient -r eth0` (для интерфейса eth0) |

**Команды для обновления адреса по ОС:**

| ОС | Команда |
|----|---------|
| **Windows** | `ipconfig /renew` |
| **macOS** | `sudo ipconfig set en0 DHCP` |
| **Linux** | `sudo ifup eth0` или `sudo dhclient eth0` |

#### Авторитативный и неавторитативный DHCP-сервер

Опция `authoritative` в конфигурации DHCP-сервера определяет его поведение при обработке некорректных запросов.

- **Авторитативный (Authoritative) сервер:** Считается "главным" для данной подсети. Если такой сервер получает от клиента `DHCPREQUEST` с IP-адресом, который не принадлежит его пулу или некорректен для данной сети, он отправит клиенту сообщение `DHCPNAK`. Это заставит клиента прекратить использование неверного адреса и заново запустить процесс DORA для получения корректного адреса.
  - *Пример:* Сотрудник приносит рабочий ноутбук из дома. Ноутбук пытается использовать свой домашний IP-адрес в корпоративной сети. Авторитативный DHCP-сервер немедленно отправит `DHCPNAK`, и ноутбук получит новый, корпоративный IP.

- **Неавторитативный (Non-authoritative) сервер:** Если сервер не является авторитативным, он просто проигнорирует некорректный `DHCPREQUEST`. Клиент будет продолжать использовать неверный адрес до истечения его срока аренды, и все это время не сможет нормально работать в сети.

В каждой подсети должен быть только один авторитативный DHCP-сервер.

#### Безопасность DHCP: Атаки на протокол

Протокол DHCP уязвим для двух основных типов атак: **DHCP Starvation** (истощение пула адресов) и **Rogue DHCP** (поддельный DHCP-сервер).

---

##### DHCP Starvation (Истощение DHCP-сервера)

**DHCP Starvation** — это атака типа DoS, направленная на исчерпание пула доступных IP-адресов DHCP-сервера.

**Механизм атаки:**
1. DHCP-сервер резервирует IP-адрес при получении `DHCPDISCOVER` запроса
2. Для идентификации клиента сервер запоминает MAC-адрес
3. Злоумышленник отправляет множество `DHCPDISCOVER` запросов с поддельными MAC-адресами
4. Сервер резервирует адреса для каждого запроса, пока пул не будет исчерпан

**Последствия:**
- Легитимные клиенты не могут получить IP-адрес
- Отказ в обслуживании (DoS) для новых устройств в сети
- Нарушение доступности сетевых ресурсов

**Методы защиты:**
- **Port Security:** Ограничение количества MAC-адресов на одном порту коммутатора
- **DHCP Snooping:** Блокировка некорректных DHCP-запросов на недоверенных портах
- **Rate Limiting:** Ограничение количества DHCP-запросов с одного порта
- **Monitoring:** Мониторинг скорости выдачи адресов и заполненности пула

---

##### Rogue DHCP Server (Поддельный DHCP-сервер)

**Rogue DHCP** (он же **DHCP Spoofing**) — атака, при которой злоумышленник разворачивает поддельный DHCP-сервер, выдающий клиентам неверные сетевые настройки.

**Механизм атаки:**
1. Клиент отправляет широковещательный `DHCPDISCOVER`
2. Все DHCP-серверы в сети отвечают `DHCPOFFER`
3. Клиент принимает **первый полученный** `DHCPOFFER`
4. Злоумышленник настраивает свой сервер для максимально быстрой отправки ответов

**Варианты атаки:**
- **DoS:** Выдача нерабочих сетевых параметров (неверный шлюз, DNS)
- **Man-in-the-Middle:** Выдача параметров, где шлюз по умолчанию — сервер атакующего
- **Перехват трафика:** Перенаправление DNS-запросов на подконтрольный DNS-сервер

**Признаки атаки:**

1. **Получение неожиданного IP-адреса:** Клиенты получают IP-адреса из другой подсети, не соответствующей ожидаемой конфигурации.
2. **Проблемы с доступом к сети:** Клиенты не могут выйти в интернет, получить доступ к локальным ресурсам или работают с перебоями, несмотря на получение IP-адреса.
3. **Неверные сетевые параметры:** Клиенты получают неверные адреса шлюза, DNS-серверов или других опций.
4. **Двойные DHCP-предложения:** При анализе сетевого трафика (например, с помощью Wireshark) видно несколько `DHCPOFFER` сообщений от разных серверов на один `DHCPDISCOVER` от клиента.

**Как найти и отключить несанкционированный DHCP-сервер:**

1. **Использование сетевых анализаторов:**
    - **Wireshark/tcpdump:** Захват трафика на порту клиента или коммутатора. Идентификация IP-адресов и MAC-адресов всех DHCP-серверов, отвечающих на `DHCPDISCOVER`. Сравнение их с легитимными серверами.
    - **Инструменты для поиска Rogue DHCP:** Существуют специализированные утилиты (например, `dhcp-discover` в Linux, `Rogue Detector` в некоторых сетевых анализаторах), которые активно сканируют сеть на предмет несанкционированных DHCP-ответов.
2. **Проверка коммутационного оборудования:**
    - **Журналы (логи) коммутаторов:** Некоторые управляемые коммутаторы могут логировать активность DHCP-серверов или оповещать о попытках запуска несанкционированных DHCP.
    - **Таблица MAC-адресов коммутатора:** После обнаружения IP и MAC-адреса несанкционированного сервера, можно найти, к какому порту коммутатора он подключен.
3. **Физическое отключение/Блокировка:**
    - После идентификации порта на коммутаторе, к которому подключен несанкционированный сервер, можно физически отключить устройство или административно заблокировать порт на коммутаторе.
    - Если несанкционированный сервер является легитимным устройством, но некорректно настроен (например, роутер, который был включен пользователем в режим маршрутизатора вместо точки доступа), его следует правильно перенастроить.

**Методы защиты от несанкционированных DHCP-серверов:**

1. **DHCP Snooping:** Это функция безопасности, доступная на управляемых коммутаторах [канального уровня (L2)](../OSI_TCP_IP_Model/data_link_layer.md).
    - **Принцип работы:** Коммутатор отслеживает DHCP-трафик и строит базу данных доверенных DHCP-серверов и их ответов. Порты коммутатора классифицируются как:
        - **Доверенные (Trusted):** Порты, к которым подключены легитимные DHCP-серверы или другие доверенные устройства (например, аплинки к другим коммутаторам). На этих портах разрешены все типы DHCP-сообщений.
        - **Недоверенные (Untrusted):** Порты, к которым подключены конечные пользователи. На этих портах блокируются входящие `DHCPOFFER`, `DHCPACK`, `DHCPNAK` сообщения (т.е. ответы от серверов). Разрешены только исходящие `DHCPDISCOVER` и `DHCPREQUEST` от клиентов.
    - **Эффект:** Любой `DHCPOFFER` или `DHCPACK` от несанкционированного DHCP-сервера, подключенного к недоверенному порту, будет заблокирован коммутатором, предотвращая получение клиентами некорректных конфигураций.
2. **Port Security (Безопасность портов):** Настраивается на коммутаторах для ограничения количества MAC-адресов, которые могут быть изучены на одном порту. Это может предотвратить подключение несанкционированных устройств или ограничить их влияние.
3. **Dynamic ARP Inspection (DAI):** Связанная с DHCP Snooping функция, которая проверяет достоверность ARP-сообщений на основе базы данных DHCP Snooping. Предотвращает ARP-спуфинг, который часто используется после получения клиентом IP-адреса от несанкционированного DHCP-сервера.
4. **Физическая безопасность:** Ограничение физического доступа к сетевому оборудованию и розеткам для предотвращения подключения несанкционированных устройств.
5. **802.1X (Network Access Control):** Более комплексное решение, требующее аутентификации устройств перед предоставлением им сетевого доступа, что также помогает предотвратить подключение несанкционированных DHCP-серверов.

> **Рекомендация по безопасности:** Будьте особенно внимательны при использовании DHCP в публичных местах (кафе, аэропорты, отели). В таких сетях риск атак Rogue DHCP и Man-in-the-Middle значительно выше.

### Дополнительная информация

- **Порты:** DHCP-сервер использует порт **67/UDP**, а клиент — порт **68/UDP**.
- **DHCP и L2:** Процесс DORA происходит на канальном уровне (L2). Хотя в пакетах передается информация об IP-адресах, сами пакеты инкапсулируются в Ethernet-кадры и адресуются по MAC-адресам. Именно поэтому DHCP-трафик по умолчанию не выходит за пределы своего широковещательного домена (VLAN).
- **BOOTP (Bootstrap Protocol):** Предшественник DHCP. Протокол прикладного уровня (7-й уровень OSI), используемый для автоматического получения IP-адреса и ссылки на загрузочный образ. Разработан для бездисковых рабочих станций (тонких клиентов). Описан в **RFC 951**. Использует UDP порты 67 (сервер) и 68 (клиент). DHCP является расширением BOOTP с добавлением времени аренды и дополнительных опций. В спецификации DHCP можно встретить ссылки на поля BOOTP (например, `bootp flags`) — это наследие совместимости.

#### Поля DHCP-сообщений (наследие BOOTP)

DHCP-сообщения используют формат BOOTP и содержат следующие ключевые поля:

| Поле | Название | Описание |
|------|----------|----------|
| `op` | Operation Code | Тип сообщения: `1` = Boot Request (клиент → сервер), `2` = Boot Reply (сервер → клиент) |
| `htype` | Hardware Type | Тип аппаратного адреса. Значение `1` используется для Ethernet. DHCP может работать не только в Ethernet, поэтому клиент сообщает тип используемого аппаратного адреса |
| `hlen` | Hardware Length | Длина аппаратного адреса. Значение `6` для Ethernet (MAC-адрес = 6 байт) |
| `hops` | Hops | Количество пройденных ретрансляторов. DHCP-клиент устанавливает в `0`. DHCP Relay Agent увеличивают счётчик на `1` при пересылке. Защита от петель маршрутизации |
| `xid` | Transaction ID | Идентификатор транзакции. Случайное число, однозначно определяющее диалог между клиентом и сервером. Сервер копирует значение из запроса в ответ |
| `secs` | Seconds Elapsed | Время, прошедшее с начала процесса получения или обновления адреса (указывается клиентом) |
| `flags` | Flags | Флаги. Например, флаг широковещания (Broadcast flag) для клиентов, не способных принимать unicast до получения IP |
| `ciaddr` | Client IP Address | Текущий IP-адрес клиента. Заполняется, если клиент уже имеет адрес и выполняет запрос на обновление/освобождение. Также означает, что клиент может отвечать на ARP-запросы |
| `yiaddr` | Your IP Address | IP-адрес, предлагаемый/выдаваемый клиенту (заполняется сервером в OFFER/ACK) |
| `siaddr` | Server IP Address | IP-адрес следующего сервера для конфигурации. Обычно используется для загрузки образов по сети (PXE, TFTP) |
| `giaddr` | Gateway IP Address | IP-адрес ретранслятора (DHCP Relay Agent), который переслал сообщение. Указывает серверу на подсеть клиента |
| `chaddr` | Client Hardware Address | Аппаратный адрес клиента. DHCP-клиент записывает свой MAC-адрес при отправке запросов. Сервер использует для отправки ответа |
| `sname` | Server Host Name | Опциональное имя сервера (null-terminated строка) |
| `file` | Boot File Name | Полный путь к файлу для загрузки по сети. Используется для бездисковых рабочих станций и автоматической установки ОС |
| `options` | Options | Список параметров (тип-длина-значение). Содержит маску подсети, маршрутизатор по умолчанию, DNS и другие сетевые параметры. Полный список опций — около 200, см. [IANA](https://www.iana.org/assignments/bootp-dhcp-parameters/bootp-dhcp-parameters.xhtml) |

**Важные опции DHCP:**

| Код | Название | Описание |
|-----|----------|----------|
| 1 | Subnet Mask | Маска подсети |
| 3 | Router | Шлюз по умолчанию |
| 6 | Domain Name Server | DNS-серверы |
| 12 | Host Name | Имя хоста клиента |
| 15 | Domain Name | Доменное имя |
| 51 | IP Address Lease Time | Время аренды (секунды) |
| 53 | DHCP Message Type | Тип сообщения (DISCOVER, OFFER, REQUEST, ACK, NAK, etc.) |
| 54 | DHCP Server Identifier | IP-адрес DHCP-сервера |
| 55 | Parameter Request List | Список запрашиваемых опций |
| 58 | Renewal Time Value (T1) | Время обновления аренды (обычно 50% от Lease Time) |
| 59 | Rebinding Time Value (T2) | Время перепривязки (обычно 87.5% от Lease Time) |

## DHCPv6 (Dynamic Host Configuration Protocol for IPv6)

DHCPv6 — это протокол для автоматической конфигурации IPv6-адресов и сетевых параметров в сетях IPv6.

### Отличия от DHCPv4

| Критерий | DHCPv4 | DHCPv6 |
|----------|--------|--------|
| **Транспорт** | UDP (сервер 67, клиент 68) | UDP (сервер 547, клиент 546) |
| **Широковещание** | Использует broadcast (255.255.255.255) | Использует multicast (ff02::1:2 для всех агентов) |
| **DORA процесс** | Четырехэтапный (Discover → Offer → Request → Ack) | Двухэтапный (Solicit → Advertise → Request → Reply) или четырехэтапный при использовании Relay |
| **Адресация** | Выдает IPv4-адреса с маской | Выдает IPv6-адреса с префиксами |
| **Резервирование** | Привязка по MAC-адресу (DUID в DHCPv6) | Использует DUID (DHCP Unique Identifier) + IAID |
| **Совместимость с SLAAC** | Нет | Может работать вместе со SLAAC (Stateless Address Autoconfiguration) |

### Режимы работы DHCPv6

1. **Stateful DHCPv6:**
    - DHCPv6-сервер полностью управляет выделением IPv6-адресов
    - Клиент получает адрес, префикс, DNS и другие параметры от сервера
    - Аналогичен DHCPv4

2. **Stateless DHCPv6:**
    - IPv6-адреса назначаются через SLAAC (Router Advertisement)
    - DHCPv6 предоставляет только дополнительные параметры (DNS, NTP, domain name)
    - Клиент отправляет `Information-Request`, сервер отвечает `Reply` с опциями

### Типы сообщений DHCPv6

- **Solicit (1):** Клиент ищет DHCPv6-серверы
- **Advertise (2):** Серверы предлагают свои услуги
- **Request (3):** Клиент запрашивает параметры у конкретного сервера
- **Confirm (4):** Клиент проверяет валидность своего адреса
- **Renew (5):** Обновление аренды адреса
- **Rebind (6):** Попытка обновления у других серверов
- **Reply (7):** Ответ сервера на запрос клиента
- **Release (8):** Освобождение адреса
- **Decline (9):** Отказ от адреса (конфликт)
- **Reconfigure (10):** Сервер требует обновления конфигурации
- **Information-Request (11):** Запрос только опций (для stateless режима)

### DUID (DHCP Unique Identifier)

Уникальный идентификатор клиента DHCPv6, который сохраняется при смене сетевого интерфейса:

- **DUID-LLT:** На основе MAC + времени создания
- **DUID-EN:** Enterprise Number + идентификатор производителя
- **DUID-LL:** Только на основе MAC-адреса
- **DUID-UUID:** На основе UUID системы

### Идентификаторы Identity Association (IA)

- **IAID (Identity Association Identifier):** Идентификатор, назначаемый клиентом для каждого интерфейса
- **IA_NA (Non-temporary Address):** Ассоциация для обычных IPv6-адресов
- **IA_TA (Temporary Address):** Ассоциация для временных адресов (privacy extensions)
- **IA_PD (Prefix Delegation):** Делегирование префикса для маршрутизаторов
