# Proxy Protocol

> **Reliability Score: 10** (SSoT + Industry Standard + Verified RFCs)

## Определения

**Proxy Protocol** — сетевой протокол, предназначенный для передачи метаданных о первоначальном соединении (адреса IP клиента и сервера, порты) через цепочки прокси-серверов или балансировщиков нагрузки, работающих на **транспортном уровне (L4)**.

**Проблема:** при проксировании трафика на уровне L4 (TCP/UDP) бэкенд видит в качестве источника IP-адрес прокси-сервера, а не реального клиента. Это делает невозможным:
- Корректное логирование реальных IP-адресов.
- Работу механизмов **Rate Limiting** и **Geo-IP**.
- Применение списков контроля доступа (**ACL**) на стороне приложения.
- Использование клиентских SSL-сертификатов (mTLS) без терминации на прокси.

**Решение:** Proxy Protocol добавляет специальный заголовок в начало потока данных приложения, информируя бэкенд о параметрах исходного соединения. Он не требует изменения прикладных протоколов (HTTP, MySQL, SMTP) и работает прозрачно для них.

> **См. также:** **[Прокси-серверы — концепции](../../Networking/Concepts/proxy.md)**, **[Протокол TCP](./TCP/overview.md)**, **[Nginx L4 Proxying](../../WebServers/Nginx/Proxy/nginx_l4_proxying.md)**

## Основные концепции

### Версии протокола

#### Proxy Protocol v1 (текстовый)
Человекочитаемый текстовый формат, представленный одной строкой в начале соединения. Ограничен по функциональности, но легок в отладке.

- **Формат:** `PROXY <protocol> <src-IP> <dst-IP> <src-port> <dst-port>\r\n`
- **Пример:** `PROXY TCP4 192.168.1.50 10.0.0.1 56324 443\r\n`
- **Типы протоколов:** `TCP4`, `TCP6`, `UNKNOWN`.
- **Ограничения:** фиксированный набор полей, отсутствие поддержки расширений, максимальная длина 108 байт.

#### Proxy Protocol v2 (бинарный)
Компактный бинарный формат, поддерживающий расширения через механизм **TLV (Type-Length-Value)**. Рекомендуется для использования в современных высокопроизводительных системах.

- **Магическая подпись (Signature):** 12 байт — `\x0D\x0A\x0D\x0A\x00\x0D\x0A\x51\x55\x49\x54\x0A` (соответствует ASCII строке `\r\n\r\n\0\r\nQUIT\n`).
- **Поддержка протоколов:** TCP, UDP (поверх IPv4 и IPv6), а также UNIX-сокеты.

**TLV расширения (Type-Length-Value):**
Позволяют передавать дополнительные данные в рамках того же заголовка:
- **0x01 (ALPN):** согласованный протокол прикладного уровня (например, `h2`).
- **0x20 (SSL):** информация о TLS-соединении (версия, шифр).
- **0x21 (SSL_CN):** Common Name из сертификата клиента (полезно для mTLS).
- **0xEA (AWS ID):** специфичные данные облачных провайдеров (например, VPC Endpoint ID в AWS).

### Сценарии использования

| Сценарий | Описание |
| :--- | :--- |
| **Cloud LB (AWS/GCP/Yandex)** | Получение реального IP клиента за облачным NLB/L4-балансировщиком. |
| **Kubernetes Ingress** | Передача IP от внешнего LB к Ingress-контроллеру (Nginx, Traefik). |
| **Цепочки прокси (HAProxy -> Nginx)** | Сохранение контекста соединения при многоуровневом проксировании. |
| **Базы данных (PostgreSQL/MySQL)** | Логирование реальных IP-адресов пользователей БД при доступе через прокси. |

## Практическая реализация

### Настройка в Nginx (Получатель)

Nginx поддерживает получение заголовков как в модуле `http`, так и в `stream`.

```nginx
# L4-уровень (stream)
stream {
    server {
        listen 8443 proxy_protocol;
        proxy_pass backend_servers;
    }
}

# L7-уровень (http)
http {
    server {
        listen 443 ssl proxy_protocol;

        # Обязательно ограничиваем доверенные IP
        set_real_ip_from 10.0.0.0/8;
        real_ip_header proxy_protocol;

        location / {
            # $remote_addr теперь содержит реальный IP клиента
            proxy_set_header X-Real-IP $remote_addr;
        }
    }
}
```

### Настройка в HAProxy (Отправитель)

HAProxy может добавлять заголовок любой версии к исходящему соединению.

```haproxy
backend app_servers
    mode tcp
    # send-proxy-v2 — отправлять бинарный заголовок v2
    # send-proxy    — отправлять текстовый заголовок v1
    server s1 192.168.1.10:8080 check send-proxy-v2
```

### Современные инструменты (Envoy, Traefik)

- **Envoy:** Настраивается через `envoy.filters.listener.proxy_protocol`. Поддерживает расширенную фильтрацию TLV.
- **Traefik:** Включается в настройках точек входа (entryPoints).
  ```yaml
  entryPoints:
    websecure:
      address: ":443"
      proxyProtocol:
        trustedIPs: ["10.0.0.0/8"]
  ```

## Диагностика и отладка

### Анализ трафика через tcpdump

Для проверки наличия заголовка v1 (текстовый):
```bash
sudo tcpdump -i any -A port 80 | grep "PROXY"
```

Для проверки v2 (бинарный) — ищем магическую подпись:
```bash
sudo tcpdump -i any -X port 443 | grep "0d0a 0d0a 000d 0a51 5549 540a"
```

### Ручная проверка (v1)
Используя `nc` (netcat), можно вручную отправить заголовок для проверки готовности бэкенда:
```bash
echo -e "PROXY TCP4 1.2.3.4 5.6.7.8 1234 80\r\nGET / HTTP/1.1\r\nHost: example.com\r\n\r\n" | nc localhost 80
```

## Безопасность

**Критическая уязвимость: IP Spoofing.**
Если сервер принимает Proxy Protocol от любого источника, злоумышленник может отправить поддельный заголовок с любым IP-адресом (например, `127.0.0.1` или IP администратора), обходя правила безопасности.

**Меры защиты:**
1. **Ограничение источников:** Всегда настраивайте список доверенных IP-адресов (`set_real_ip_from` в Nginx, `trustedIPs` в Traefik), от которых разрешено принимать заголовки.
2. **Изоляция сети:** Включайте поддержку протокола только на интерфейсах, доступных исключительно балансировщикам нагрузки.
3. **Согласованность:** Убедитесь, что и отправитель, и получатель используют одну и ту же версию протокола. Ошибка в версии приведет к разрыву соединения или некорректной обработке данных как части полезной нагрузки.
