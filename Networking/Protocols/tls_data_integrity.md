# Целостность данных в протоколе TLS

Помимо [шифрования](./tls_encryption.md), протокол [TLS](./tls_protocol.md) решает еще две важные задачи: обеспечение **целостности данных** и **аутентификации**. В этой заметке рассматривается, как TLS гарантирует, что данные не были изменены в процессе передачи.

## Проблема целостности данных

**Целостность данных** — это гарантия того, что полученные данные в точности соответствуют отправленным. При передаче данных по сети злоумышленник может перехватить сообщение, изменить его и отправить измененную версию получателю. Механизмы обеспечения целостности призваны обнаруживать такие манипуляции.

## Простое решение: Контрольные суммы

Простейший механизм для проверки целостности — это **контрольная сумма**, используемая, например, в протоколе [UDP](./udp_protocol.md). Получатель рассчитывает контрольную сумму для полученных данных и сравнивает ее со значением в заголовке. Если они совпадают, данные считаются неповрежденными.

Однако этот метод не защищает от целенаправленной атаки. Злоумышленник может изменить данные, пересчитать для них контрольную сумму и подставить новое значение в заголовок.

## Криптографические хеш-функции

Для более надежной защиты используются **криптографические хеш-функции** (например, SHA-256).

*   **Хеш-функция** преобразует массив данных произвольной длины в строку фиксированной длины (хеш).
*   **Свойства:**
    *   По хешу невозможно восстановить исходные данные.
    *   Даже незначительное изменение в исходных данных приводит к кардинальному изменению хеша.

Если просто добавлять хеш к сообщению, проблема не решается: злоумышленник все так же может изменить данные и пересчитать для них новый хеш.

## Решение в TLS: Код аутентификации сообщения (MAC)

Для решения этой проблемы TLS использует **код аутентификации сообщения (Message Authentication Code, MAC)**. MAC — это хеш, который вычисляется не только на основе самих данных, но и с использованием **секретной информации**, известной только клиенту и серверу. В контексте TLS в качестве этой информации выступает **общий сессионный ключ**, согласованный на этапе рукопожатия.

### Схема работы MAC

1.  **Отправка:**
    *   Клиент берет исходные данные и добавляет к ним общий секретный ключ.
    *   От этой объединенной информации вычисляется криптографический хеш (MAC).
    *   Клиент отправляет серверу исходные данные вместе с вычисленным MAC.

2.  **Получение и проверка:**
    *   Сервер получает данные и MAC.
    *   Сервер выполняет ту же операцию: берет полученные данные, добавляет к ним свой экземпляр общего секретного ключа и заново вычисляет MAC.
    *   Сервер сравнивает вычисленный им MAC со значением, полученным от клиента.
        *   **Если значения совпадают:** Данные не были изменены в пути.
        *   **Если значения не совпадают:** Данные были изменены, и пакет отбрасывается.

Поскольку у злоумышленника нет общего секретного ключа, он не может сгенерировать корректный MAC для измененных данных, и его атака будет обнаружена.

## Шифры аутентифицированного шифрования (AEAD)

Ранее в TLS для шифрования и для обеспечения целостности использовались разные алгоритмы. Современные версии протокола перешли на **шифры аутентифицированного шифрования с присоединенными данными (Authenticated Encryption with Associated Data, AEAD)**.

AEAD-шифры — это алгоритмы, которые одновременно выполняют обе операции:
1.  **Шифруют** данные (обеспечивают приватность).
2.  **Генерируют** аутентификационный тег (MAC) для проверки целостности.

Этот подход более эффективен и безопасен. Примеры таких шифров, используемых в TLS 1.3:
*   `TLS_AES_256_GCM_SHA384`
*   `TLS_CHACHA20_POLY1305_SHA256`

## Заключение

Целостность данных в TLS обеспечивается с помощью кода аутентификации сообщения (MAC), который вычисляется на основе данных и общего секретного ключа. Это не позволяет злоумышленнику незаметно изменять передаваемую информацию.

**Важно:** Механизм MAC защищает от подмены данных, но не от атаки "человек посередине", если изначально было установлено соединение не с легитимным сервером, а с сервером злоумышленника. Проблему проверки подлинности сервера решает **аутентификация**, которая рассматривается в следующей лекции.
