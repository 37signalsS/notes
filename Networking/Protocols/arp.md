# ARP — протокол разрешения адресов

## Определения

**ARP (Address Resolution Protocol)** — протокол разрешения адресов, используемый для сопоставления IP-адресов (сетевой уровень, L3) с MAC-адресами (канальный уровень, L2) в сетях IPv4. ARP инкапсулируется непосредственно в Ethernet-кадры (EtherType `0x0806`) и фактически работает на уровне 2.5 модели OSI, обеспечивая взаимодействие между сетевым и канальный уровнями.

Когда устройству необходимо отправить данные другому хосту в той же локальной сети, оно отправляет широковещательный ARP-запрос. Хост с искомым IP отвечает unicast-сообщением, сообщая свой MAC-адрес, после чего начинается обмен данными.

> **Важно:** В сетях **IPv6** протокол ARP отсутствует. Его функции (разрешение адресов, обнаружение соседей) выполняет **NDP (Neighbor Discovery Protocol)** на базе ICMPv6. См.: **[Обзор IPv6](./ipv6_overview.md)**.

> **См. также:** [Модель OSI](../OSI_TCP_IP_Model/osi_model.md), [Ethernet](./ethernet.md), [IP](./IP_addressing/ip_overview.md), [ip neighbour](../../Linux/Networking/Tools/iproute2/ip_neighbour.md)

## Основные концепции

### Назначение ARP

Пакеты в IP-сети маршрутизируются на основе IP-адресов, но на канальном уровне (Ethernet) доставка осуществляется по MAC-адресам. Для «упаковки» IP-пакета в Ethernet-кадр отправителю необходимо знать MAC-адрес получателя. ARP связывает логическую IP-адресацию с физической MAC-адресацией.

### Формат ARP-пакета (Ethernet/IPv4)

Протокол работает по принципу запрос-ответ. ARP-пакет содержит следующие ключевые поля:

| Поле | Расшифровка | Описание |
| :--- | :--- | :--- |
| **HTYPE** | Hardware Type | Тип сетевого протокола (Ethernet = `1`) |
| **PTYPE** | Protocol Type | Тип межсетевого протокола (IPv4 = `0x0800`) |
| **HLEN** | Hardware Size | Длина MAC-адреса (для Ethernet = `6`) |
| **PLEN** | Protocol Size | Длина IP-адреса (для IPv4 = `4`) |
| **Opcode** | Operation Code | `1` для Request (запрос), `2` для Reply (ответ) |
| **SHA** (Sender Hardware Address) | MAC-адрес отправителя | Физический адрес отправителя |
| **SPA** (Sender Protocol Address) | IP-адрес отправителя | Сетевой адрес отправителя |
| **THA** (Target Hardware Address) | MAC-адрес назначения | Искомый MAC-адрес (в запросе заполнен нулями) |
| **TPA** (Target Protocol Address) | IP-адрес назначения | IP-адрес, для которого требуется найти MAC |

### Алгоритм работы

1. **Проверка ARP-кэша:** хост ищет IP назначения в локальной таблице. Если запись есть, используется сохранённый MAC.
2. **ARP-запрос (ARP Request):** при отсутствии записи формируется широковещательный запрос на адрес `FF:FF:FF:FF:FF:FF`.
3. **Обработка запроса:** все устройства в сегменте получают запрос, но отвечает только хост, чей IP совпадает с полем TPA.
4. **ARP-ответ (ARP Reply):** целевой хост отправляет unicast-ответ со своим MAC-адресом.
5. **Обновление кэша:** запросивший хост сохраняет запись и начинает передачу IP-пакетов.

### Тайм-ауты и отсутствие ответа

При отсутствии ответа хост повторяет запрос (обычно до 3 раз с интервалом 1–3 секунды). Если ответ так и не получен, протоколы верхнего уровня (TCP/UDP) получают ошибку доставки.
**Последствия:** TCP-соединения не устанавливаются, трафик теряется, приложения выдают ошибки таймаута (`No route to host` или `Host unreachable`).

### ARP-таблица (кэш) и состояния NUD

Временное хранилище сопоставлений IP ↔ MAC. В современных ОС (особенно в Linux) используется механизм **NUD (Neighbor Unreachability Detection)** для отслеживания актуальности соседей.

**Типы записей:**

| Тип | Описание | Время жизни |
| :--- | :--- | :--- |
| **Динамический** | Создаётся автоматически через ARP-протокол | Удаляется при бездействии (в Linux ~30-60с) |
| **Статический** | Добавляется вручную администратором | Сохраняется до перезагрузки или ручного удаления |

**Состояния записи в Linux:**

- **REACHABLE:** Связь подтверждена (узел ответил на ARP или пришел TCP ACK).
- **STALE:** Запись есть, но давно не использовалась. При отправке пакета будет использована, но параллельно начнется проверка.
- **DELAY / PROBE:** Промежуточные состояния активной проверки доступности (отправка unicast-проб).
- **FAILED:** Сосед не ответил на запросы.
- **INCOMPLETE:** Запрос отправлен, ответ еще не получен.

Подробное описание утилиты управления: **[ip neighbour](../../Linux/Networking/Tools/iproute2/ip_neighbour.md)**.

**Команды просмотра:**

- **Linux:** `ip n` (современный метод) или `arp -n` (устаревший)
- **Windows / macOS:** `arp -a`

> **Диагностика (Host Discovery):** если IP не пингуется, но вы находитесь в одном L2-сегменте, проверьте локальную ARP-таблицу. Если запись для искомого IP присутствует и имеет MAC-адрес (состояние `REACHABLE` или `STALE`), значит, хост **включен и работает**, но его фаервол полностью блокирует входящий ICMP-трафик.

> **См. также:** [Диагностика ping](../../Linux/Diagnostics/Networking/ping.md).

### Визуализация процесса ARP

```
┌─────────────┐                              ┌─────────────┐
│   Хост A    │                              │   Хост B    │
│ IP: 10.0.1.5│                              │ IP: 10.0.1.10│
│MAC:AA:BB:CC │                              │MAC:DD:EE:FF │
└──────┬──────┘                              └──────┬──────┘
       │                                           │
       │ 1. ARP Request (Broadcast)                │
       │ "Who has 10.0.1.10? Tell 10.0.1.5"       │
       │ ─────────────────────────────────────────>│
       │    dst: FF:FF:FF:FF:FF:FF                 │
       │                                           │
       │        2. ARP Reply (Unicast)             │
       │ <─────────────────────────────────────────│
       │ "10.0.1.10 is at DD:EE:FF"                │
       │    src: DD:EE:FF                           │
       │                                           │
       │ 3. Данные (Unicast)                       │
       │ ─────────────────────────────────────────>│
       │    dst: DD:EE:FF                           │
```

## Практические сценарии

### Переполнение ARP-таблицы

Проблема часто возникает на гипервизорах (KVM, LXC) с большим количеством виртуальных сущностей или при ARP-флуде. При переполнении хост перестаёт добавлять новые записи, что приводит к частичной потере связности.

**Симптомы:**
- Сетевой «хаос»: часть узлов доступна, часть — нет без видимой системы.
- Рандомные задержки и обрывы соединений.
- Физические линки и маршруты в порядке.
- Сообщения в `dmesg`: `neighbor table overflow`.

#### Диагностика
1. **Проверка статусов:** `ip -s neigh` (ищем большое количество `INCOMPLETE` или `FAILED`).
2. **Подсчёт записей:** `ip neigh show | wc -l`.
3. **Проверка лимитов ядра:** `cat /proc/sys/net/ipv4/neigh/default/gc_thresh3`.
4. **Системные логи:** `dmesg | grep -i arp`.

#### Решение
Увеличение лимитов ARP-кэша через `sysctl`:
```bash
sysctl -w net.ipv4.neigh.default.gc_thresh1=4096
sysctl -w net.ipv4.neigh.default.gc_thresh2=8192
sysctl -w net.ipv4.neigh.default.gc_thresh3=16384
```
- `gc_thresh1` — минимум, до которого очистка не запускается.
- `gc_thresh2` — порог, после которого очистка запускается через 5 секунд.
- `gc_thresh3` — жёсткий предел, новые записи не добавляются.

**Сохранение изменений (автозагрузка):**
```bash
# Добавить в /etc/sysctl.d/99-arp.conf
net.ipv4.neigh.default.gc_thresh1=4096
net.ipv4.neigh.default.gc_thresh2=8192
net.ipv4.neigh.default.gc_thresh3=16384

# Применить
sudo sysctl --system
```

**Верификация:**
```bash
sysctl net.ipv4.neigh.default.gc_thresh3
# → 16384
```

### Проблема ARP Flux (Multi-homed хосты)

Возникает на Linux-серверах с несколькими интерфейсами в одной подсети. По умолчанию Linux рассматривает IP-адреса как принадлежащие всему хосту, а не строго конкретному интерфейсу. В результате приходящий ARP-запрос для одного IP может быть answered через другой интерфейс, если ядро считает этот путь доступным. Это сбивает с толку коммутаторы (MAC flapping) и нарушает симметрию трафика.

#### Как это происходит

Допустим, `eth0` имеет адрес `192.168.1.10`, а `eth1` — `192.168.1.20`.

Сосед спрашивает: «Кому принадлежит `192.168.1.10?». Запрос приходит на `eth1`, и Linux может ответить MAC-адресом `eth1`, хотя нужный IP назначен на `eth0`. В результате ARP-таблица соседа неожиданно меняется, а трафик начинает приходить не на тот интерфейс.

**Механизм:** параметр `net.ipv4.conf.all.arp_ignore` по умолчанию равен `0`, что означает, что ядро отвечает на ARP для любого локального IP, независимо от интерфейса, на который пришёл запрос (см. [документацию ядра](https://www.kernel.org/doc/Documentation/networking/ip-sysctl.txt)).

#### Проверяем настройки

```bash
sysctl net.ipv4.conf.all.arp_ignore
sysctl net.ipv4.conf.all.arp_announce
```

При `arp_ignore=0` Linux может отвечать на ARP-запросы за локальные IP независимо от интерфейса, на который пришёл запрос.

**Симптомы:**
- MAC-адрес «прыгает» между интерфейсами в ARP-таблице коммутатора.
- Нестабильная связность, особенно при работе с several сервисами на одном хосте.
- Логи коммутатора содержат сообщения о MAC flapping.

#### Ограничиваем ARP-ответы

```bash
# Отвечать на запрос только если целевой IP настроен на интерфейсе приема
sysctl -w net.ipv4.conf.all.arp_ignore=1
# Всегда использовать IP-адрес интерфейса вылета для анонса в запросе
sysctl -w net.ipv4.conf.all.arp_announce=2
```

`arp_ignore=1` разрешает отвечать только за адреса, назначенные входящему интерфейсу.
`arp_announce=2` помогает избежать объявления неподходящего исходного IP в исходящих ARP-запросах.

**Сохранение изменений:**
```bash
# Добавить в /etc/sysctl.d/99-arp.conf
net.ipv4.conf.all.arp_ignore=1
net.ipv4.conf.all.arp_announce=2

# Применить
sudo sysctl --system
```

**Верификация:**
```bash
sysctl net.ipv4.conf.all.arp_ignore net.ipv4.conf.all.arp_announce
# → 1
# → 2
```

### ARP в контейнерах и виртуализации

В средах Docker и Kubernetes ARP-трафик проходит через виртуальные сущности:
- **Veth-пары:** Контейнер отправляет ARP-запрос, который через veth-пару попадает на мост хоста (`docker0`, `br0`). Подробная схема прохождения трафика через veth-пары в Docker приведена в заметке **[Packet Flow в Docker Bridge](../../Docker/Docker_network/drivers/bridge.md#жизненный-цикл-пакета-packet-flow)**.
- **Bridge Learning:** Мост хоста обучается MAC-адресам контейнеров аналогично физическому коммутатору.
- **ARP Suppression (VXLAN/SDN):** В облачных сетях (VXLAN с BGP EVPN) широковещательный ARP подавляется. VTEP-терминалы перехватывают запросы и отвечают на них сами (Proxy ARP), используя информацию из распределенной базы данных, что предотвращает "штормы" в туннелях.

**Диагностика ARP в Docker:**
```bash
# Просмотр ARP-таблицы на хосте (видны контейнеры)
ip neigh show

# Просмотр ARP-таблицы внутри контейнера
docker exec <container> ip neigh show

# Проверка veth-пары
bridge fdb show dev <veth_interface>

# Мониторинг ARP-трафика на мосте
tcpdump -i docker0 -e arp
```

**Диагностика ARP в Kubernetes:**
```bash
# Просмотр ARP-таблицы на узле
ip neigh show

# Проверка MAC-адресов подов
kubectl get pods -o wide | grep <node>
ip neigh show | grep <pod_ip>

# Мониторинг ARP на конкретном интерфейсе
tcpdump -i <interface> -e arp
```

### ARP-флуд и диагностика таймаутов

**Диагностика флуда:**
```bash
# Просмотр статистики ARP (количество запросов и ответов)
ip -s neigh

# Мониторинг ARP-трафика в реальном времени с выводом MAC (-e)
tcpdump -i eth0 -e arp

# Фильтрация запросов к конкретному IP
tcpdump -i eth0 arp and dst host 192.168.1.1

# Подсчет ARP-пакетов в секунду
tcpdump -i eth0 arp -c 1000 | wc -l

# Анализ только ARP-запросов (без ответов)
tcpdump -i eth0 'arp[6:2] == 1'

# Анализ только ARP-ответов
tcpdump -i eth0 'arp[6:2] == 2'
```

**Wireshark фильтры для анализа ARP:**
```
# Все ARP-пакеты
arp

# Только ARP-запросы
arp.opcode == 1

# Только ARP-ответы
arp.opcode == 2

# ARP-запросы к конкретному IP
arp.dst.hw_mac == ff:ff:ff:ff:ff:ff && arp.dst.proto == 192.168.1.1

# ARP-ответы от конкретного IP
arp.src.proto == 192.168.1.10

# Поиск потенциальных атак (много ARP-ответов от одного IP)
arp.opcode == 2 && arp.src.proto == 192.168.1.100
```

### Диагностика микро-фризов и ARP Resolve Timeout

Когда «всё работает», но периодически интерактивные сессии (SSH, VoIP) замирают на несколько секунд, причиной часто является **ARP Resolve Timeout**. Хост теряет MAC-адрес соседа и блокирует отправку трафика до завершения нового цикла резолвинга.

**1. Отслеживание частоты запросов и таймаутов**
Если узел часто «теряется», хост начинает слать повторяющиеся запросы.
- **Linux:** `tcpdump -ni eth0 arp`
  *Подозрительный признак:* 2–3 повторных ARP Request подряд без немедленного ARP Reply.
- **Cisco:** `debug arp` (включать с осторожностью!) или `show arp`.

**2. Корреляционный анализ (Ping + ARP)**
Отслеживание отсутствия ответов в момент задержки:
```bash
# Мониторинг ARP и ICMP одновременно
tcpdump -ni eth0 "arp or icmp"
```
*Интерпретация:* Если `ping` висит, а в дампе видны ARP Requests без ответов — таймаут найден.

**3. Анализ «флапающих» состояний NUD**
Вinux записи могут часто менять состояние, что указывает на нестабильность L2.
- **Команда:** `ip -s neigh`
- **Признаки проблемы:**
  - Резкий рост счетчиков в колонке `FAILED`.
  - Записи часто переходят по циклу `FAILED` → `REACHABLE` → `STALE` → `FAILED`.
  - Состояние `INCOMPLETE` держится дольше 1 сек.

**4. Проверка L2-кэша на коммутаторе (Cisco)**
Если хост шлет запросы, а коммутатор «забывает» MAC или шлет фреймы не в тот порт:
```cisco
show mac address-table dynamic | include <MAC_адрес_соседа>
```
Если MAC постоянно пропадает или «прыгает» между портами — проблема в сегментации, петлях L2 или нестабильном линке.

**5. Резюме диагностики**
Если в дампе видны ARP-запросы без ARP-ответов, а `ip n` показывает `FAILED` — проблема локализована на уровне L2 (неправильный VLAN, изоляция портов (Private VLAN), выключен узел или перегрузка CPU на стороне ответчика).

**Пошаговый алгоритм диагностики:**
1. `ip neigh show` — проверить состояние записей (FAILED, INCOMPLETE).
2. `tcpdump -i <intf> arp` — перехватить ARP-трафик.
3. Сравнить: есть ли ARP-ответы на отправленные запросы.
4. Проверить физику: `ethtool <intf>`, кабель, порт коммутатора.
5. Проверить VLAN: `bridge vlan show`, `show vlan brief`.
6. Проверить файрвол: `nft list ruleset`, `iptables -L -v -n`.

### Отслеживание пути пакетов на L2 (MAC-level)

Для диагностики проблем на канальном уровне (неправильная VLAN-конфигурация, потеря трафика между коммутаторами) используется комбинация `arping` и `tcpdump`:

```bash
# Отправка ARP-запроса с L2-заголовками
arping -I eth0 -f 192.168.1.10

# Прослушивание кадров с выводом Ethernet-заголовков
tcpdump -i eth0 -e arp
```
Опция `-e` позволяет увидеть source/destination MAC, что критично для отладки "невидимых" на IP-уровне проблем.

**Практические примеры использования arping:**
```bash
# Проверка доступности хоста на L2 (в обход файрвола)
arping -I eth0 -c 3 192.168.1.10

# Проверка дубликатов IP (Duplicate Address Detection)
arping -D -I eth0 -c 3 192.168.1.10
# → Если exit code 0 — конфликт обнаружен

# Определение MAC-адреса по IP
arping -I eth0 192.168.1.10 | grep "reply from"

# Проверка связности через конкретный интерфейс
arping -I eth1 -c 3 10.0.0.1
```

**Опции arping:**
| Опция | Описание |
| :--- | :--- |
| `-I <interface>` | Интерфейс для отправки |
| `-c <count>` | Количество запросов |
| `-f` | Остановиться после первого ответа |
| `-D` | Режим обнаружения дубликатов IP (DAD) |
| `-w <deadline>` | Таймаут в секундах |
| `-s <source>` | Исходный IP-адрес |

## Дополнительная информация

### Разновидности ARP

- **Proxy ARP (RFC 1027):** Маршрутизатор отвечает своим MAC на запросы для узлов в другом сегменте. Используется для объединения сетей без перенастройки хостов или в VPN/туннелях. Подробнее: **[Proxy ARP](../Concepts/nat/proxy_arp.md)**.
- **Gratuitous ARP (GARP):** Анонс собственного IP/MAC без явного запроса. Устройство отправляет ARP-пакет самостоятельно, не дожидаясь ARP-запроса от соседа. В результате соседние хосты обновляют свой ARP-кэш и перенаправляют трафик на новый MAC-адрес без задержек на повторный резолвинг.
  - **Механизм:** обычно ARP работает по схеме запрос-ответ: Host A отправляетbroadcast-запрос «Who has IP?», и Owner отвечает unicast-сообщением со своим MAC. При Gratuitous ARP владелец IP-адреса отправляет broadcast- или unicast-ответ без предварительного запроса, proactively оповещая сегмент о смене привязки IP → MAC.
  - **Сценарий VIP failover:** виртуальный IP переезжает между узлами:
    - до переезда: `10.0.0.10 → aa:aa:aa:aa:aa:aa`
    - после переезда: `10.0.0.10 → bb:bb:bb:bb:bb:bb`
    - новый узел-владелец рассылает объявление: `10.0.0.10 is-at bb:bb:bb:bb:bb:bb`
    - соседи получают его и немедленно обновляют ARP-кэш, поэтому трафик на `10.0.0.10` начинает идти на новый MAC практически мгновенно — без того, чтобы каждый клиент самостоятельно выполнял ARP lookup и проходил тайм-аут stale-записи.
  - **Критические сценарии применения:**
    - **Failover виртуального IP (VRRP/Keepalived/HAProxy):** при переключении MASTER → BACKUP новый владелец VIP рассылает GARP, и коммутаторы/хосты обновляют MAC-таблицы.
    - **Миграция виртуальной машины** (vMotion, Live Migration): VM перемещается между физическими хостами; её MAC и IP остаются прежними, но владелец MAC меняется, поэтому для быстрого возобновления трафика отправляется GARP.
    - **Переключение кластера на резервный узел:** после восстановления MASTER или при плановом обслуживании новый активный узел оповещает сеть.
  - **Важно:** после переноса сервиса между хостами может измениться не DNS, не маршрут и не IP-адрес — меняется только MAC, связанный с уже известным IP, и сеть быстро узнаёт об этом именно через Gratuitous ARP.
  - **Команды диагностики:**
    - Просмотр анонсов в реальном времени:
      ```bash
      tcpdump -ni eth0 arp
      ```
      В выводе ищите ARP-ответы (`arp[6:2] == 2`), где sender protocol address совпадает с анонсируемым IP, а target hardware address заполнен нулями или совпадает с sender hardware address.
    - Текущая ARP-таблица соседей:
      ```bash
      ip neigh show
      ```
      После успешного GARP запись для соответствующего IP должна перейти в состояние `REACHABLE` или `STALE` с новым MAC-адресом.
  - **Failover и задержки:** без GARP клиенты обнаруживают смену MAC только по истечению тайм-аута ARP-кэша (обычно 30–60 секунд в Linux), что приводит к потерям пакетов и таймаутам соединений (TCP retransmit, SSH freeze). GARP сокращает это время до нескольких миллисекунд.
  - **Связанные параметры ядра:**
    - `net.ipv4.conf.all.arp_ignore` и `net.ipv4.conf.all.arp_announce` — управляют условиями, при которых хост отвечает на ARP и как формирует sender IP в ARP-пакете (важно при multi-homed).
    - В Keepalived: `vrrp_garp_master_delay` — задержка перед отправкой первого GARP после становления MASTER (избегает шторма при старте).
  - **Обнаружение и отладка:**
    - Перехват только GARP:
      ```bash
      tcpdump -ni eth0 'arp[6:2] == 2 && arp.src.proto == 10.0.0.10'
      ```
    - Проверка, что MAC обновился:
      ```bash
      ip neigh show | grep 10.0.0.10
      ```
  - **RFC:** RFC 5227 — IPv4 Address Conflict Detection (использует GARP для проверки уникальности IP).
  - **См. также:** [ARP в отказоустойчивых системах (HA)](#arp-в-отказоустойчивых-системах-ha), [Proxy ARP](../Concepts/nat/proxy_arp.md).
- **Inverse ARP (InARP):** Определение IP по MAC (использовалось в Frame Relay).
- **Reverse ARP (RARP):** Устаревший протокол получения IP по MAC. Заменён на [DHCP](./DHCP/dhcp_overview.md).

### Критические параметры ядра Linux (sysctl)

| Параметр | Рекомендуемое значение | Описание |
| :--- | :--- | :--- |
| **arp_ignore** | `1` | Отвечать на ARP-запрос только если целевой IP настроен на интерфейсе приема. |
| **arp_announce** | `2` | При отправке ARP-запроса использовать IP-адрес интерфейса вылета. |
| **arp_filter** | `1` | Позволяет иметь несколько сетевых интерфейсов в одной подсети и корректно отвечать на ARP. |
| **proxy_arp** | `1` (при необходимости) | Включить Proxy ARP на интерфейсе. |

**Полный список параметров ARP:**
```bash
# Просмотр всех параметров ARP для интерфейса
sysctl -a | grep arp

# Просмотр для конкретного интерфейса
sysctl -a | grep net.ipv4.conf.eth0.arp
```

### ARP в отказоустойчивых системах (HA)

#### Bonding и ARP Monitoring
В Linux Bonding (режимы 0, 1, 5, 6) используется **ARP Monitoring** (`arp_interval` и `arp_ip_target`) для проверки живой связности. В отличие от MII-мониторинга (проверяет только линк), ARP-мониторинг гарантирует прохождение трафика через вышестоящий коммутатор.

**Настройка ARP Monitoring в Bonding:**
```bash
# Просмотр текущей конфигурации bonding
cat /proc/net/bonding/bond0

# Настройка ARP-мониторинга
echo "arp_interval=100" > /sys/class/net/bond0/bonding/arp_interval
echo "arp_ip_target=192.168.1.1,192.168.1.2" > /sys/class/net/bond0/bonding/arp_ip_target
```

#### Обнаружение дубликатов IP (DAD)
Для предотвращения конфликтов используется `arping`:
```bash
# Проверка: ответит ли кто-нибудь на этот IP (Duplicate Address Detection)
arping -D -I eth0 192.168.1.10
# → Если exit code 0 — конфликт обнаружен.
```

**Автоматическая проверка DAD при запуске интерфейса:**
```bash
# Добавить в /etc/network/interfaces (Debian/Ubuntu)
auto eth0
iface eth0 inet static
    address 192.168.1.10
    netmask 255.255.255.0
    pre-up arping -D -I eth0 $address || exit 1
```

### Безопасность: ARP Spoofing

Атака, при которой злоумышленник рассылает поддельные ARP-ответы, связывая свой MAC с IP жертвы (обычно шлюза) для реализации MITM.

**Схема атаки:**
```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   Жертва    │     │Злоумышленник│     │    Шлюз     │
│ IP: 10.0.1.5│     │ IP: 10.0.1.100│   │ IP: 10.0.1.1│
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                   │
       │ 1. ARP Spoofing   │                   │
       │ "10.0.1.1 is at   │                   │
       │  AA:BB:CC:DD:EE:FF"│                  │
       │ <─────────────────│                   │
       │                   │                   │
       │ 2. ARP Spoofing   │                   │
       │ "10.0.1.5 is at   │                   │
       │  AA:BB:CC:DD:EE:FF"│                  │
       │                   │ <─────────────────│
       │                   │                   │
       │ 3. Трафик идет через злоумышленника   │
       │ ─────────────────>│ ─────────────────>│
```

**Обнаружение и защита:**
1. **Мониторинг:** использование `arpwatch` или анализ через `tcpdump -e arp`.
   ```bash
   # Установка и запуск arpwatch
   sudo apt install arpwatch
   sudo arpwatch -i eth0 -f /var/lib/arpwatch/arp.dat

   # Просмотр логов
   tail -f /var/log/syslog | grep arpwatch
   ```

2. **Dynamic ARP Inspection (DAI):** Функция коммутаторов, проверяющая ARP-пакеты на соответствие базе DHCP Snooping. См. **[DHCP Security](./DHCP/dhcp_security.md)**.

3. **Фильтрация:** `arptables` или `nftables` для ограничения ARP-трафика на уровне хоста.
   ```bash
   # Пример arptables: разрешить ARP только от известного MAC шлюза
   arptables -A INPUT --src-mac ! 00:11:22:33:44:55 -j DROP

   # Пример nftables: фильтрация ARP
   nft add table arp filter
   nft add chain arp filter input { type filter hook input priority 0 \; policy accept \; }
   nft add rule arp filter input ether saddr != 00:11:22:33:44:55 drop
   ```

4. **Статические ARP-записи** для критичных хостов:
   ```bash
   # Добавление статической записи
   sudo ip neigh add 192.168.1.1 lladdr 00:11:22:33:44:55 dev eth0 permanent

   # Проверка
   ip neigh show | grep 192.168.1.1
   ```

**Признаки ARP Spoofing:**
- MAC-адрес шлюза в ARP-таблице часто меняется.
- Один MAC-адレス отвечает за несколько IP (особенно шлюз и другие хосты).
- Дублирование IP в логах `arpwatch`.
- Нестабильная связность, особенно при доступе к внешним ресурсам.

### Типичные ошибки и решения

| Проблема | Вероятная причина | Решение |
| :--- | :--- | :--- |
| Хост не отвечает на ARP | Файрвол блокирует ARP | Разрешить ARP в файрволе хоста |
| ARP-таблица переполнена | Много хостов в сегменте | Увеличить `gc_thresh3` |
| MAC-адрес «прыгает» | ARP Flux (multi-homed) | Настроить `arp_ignore` и `arp_announce` |
| Микро-фризы SSH | ARP Resolve Timeout | Проверить NUD-состояния, статические ARP |
| Нет связности после миграции | Возможна устаревшая запись IP → MAC | [Диагностический сброс таблицы соседей](../../Linux/Networking/Tools/iproute2/ip_neighbour.md#диагностический-сброс-таблицы-соседей) |
| ARP Spoofing | Злоумышленник в сегменте | DAI, статические ARP, мониторинг |

## Пошаговая диагностика ARP-проблем

### Алгоритм диагностики

```
1. Определите проблему
   ├── Нет связности с хостом
   │   ├── Проверьте ARP-таблицу: ip neigh show
   │   ├── Если запись есть → проблема выше L2 (файрвол, маршрутизация)
   │   └── Если записи нет → отправьте ARP-запрос вручную
   ├── Микро-фризы/задержки
   │   ├── Проверьте NUD-состояния: ip -s neigh
   │   ├── Ищите циклы REACHABLE → STALE → FAILED
   │   └── Проверьте стабильность линка: ethtool <intf>
   └── MAC flapping
       ├── Проверьте ARP-таблицу коммутатора
       ├── Ищите дублирующиеся MAC
       └── Проверьте VLAN-конфигурацию
```

### Базовые команды диагностики

```bash
# 1. Просмотр ARP-таблицы
ip neigh show                    # Краткий формат
ip -s neigh show                 # Со статистикой
ip -br neigh show                # Компактный формат

# 2. Проверка конкретного IP
ip neigh show | grep 192.168.1.10

# 3. Принудительный запрос ARP
arping -I eth0 -c 3 192.168.1.10

# 4. Мониторинг ARP-трафика
tcpdump -i eth0 -e arp -n

# 5. Проверка физического уровня
ethtool eth0
ip -s link show eth0

# 6. Проверка статистики ошибок
ip -s link show eth0 | grep -E "errors|dropped|overruns"
```

### Диагностика特定ных проблем

#### Проблема: Хост не пингуется, но должен работать

```bash
# Шаг 1: Проверьте ARP-таблицу
ip neigh show | grep 192.168.1.10
# → Если запись есть с MAC → проблема не в ARP

# Шаг 2: Отправьте ARP-запрос вручную
arping -I eth0 -c 3 192.168.1.10
# → Если ответов нет → проблема на L2

# Шаг 3: Проверьте файрвол на целевом хосте
ssh 192.168.1.10 "iptables -L -v -n | grep -E 'ICMP|ARP'"

# Шаг 4: Проверьте VLAN
bridge vlan show dev eth0
```

#### Проблема: Периодические разрывы SSH-сессий

```bash
# Шаг 1: Мониторинг ARP + ICMP
tcpdump -ni eth0 "arp or icmp" -c 1000

# Шаг 2: Проверка NUD-состояний в реальном времени
watch -n 1 "ip -s neigh show | grep 192.168.1.10"

# Шаг 3: Проверка стабильности линка
ethtool eth0 | grep -E "Speed|Duplex|Link detected"
dmesg | grep -i eth0 | tail -20
```

#### Проблема: ARP Spoofing атака

```bash
# Шаг 1: Поиск дублирующихся MAC
ip neigh show | awk '{print $5}' | sort | uniq -d

# Шаг 2: Мониторинг ARP-ответов
tcpdump -i eth0 'arp[6:2] == 2' -e | awk '{print $NF, $(NF-1)}' | sort | uniq -c | sort -rn

# Шаг 3: Проверка arpwatch
grep "flip flop" /var/log/syslog

# Шаг 4: Временная защита (statik ARP)
sudo ip neigh change 192.168.1.1 lladdr 00:11:22:33:44:55 dev eth0 permanent
```
