# ARP (Address Resolution Protocol)

## Определения

**ARP (Address Resolution Protocol)** — протокол для преобразования IP-адресов (сетевой уровень, L3) в MAC-адреса (канальный уровень, L2) в сетях TCP/IP. ARP инкапсулируется непосредственно в Ethernet-кадры ([EtherType](#дополнительная-информация) `0x0806`) и функционирует на уровне 2,5 модели OSI.

Когда устройству нужно отправить данные другому хосту в той же локальной сети, оно отправляет широковещательный ARP-запрос на MAC-адрес `FF:FF:FF:FF:FF:FF`. Хост с искомым IP отвечает unicast, сообщая свой MAC-адрес, после чего начинается обмен данными.

Фактически ARP связывает логическую IP-адресацию с физической MAC-адресацией, позволяя пакетам сетевого уровня доставляться в Ethernet-кадрах канального уровня.

> **См. также:** [Модель OSI](../OSI_TCP_IP_Model/osi_model.md), [Ethernet](./ethernet.md), [IP](./IP_addressing/ip_overview.md)

## Основные концепции

### Зачем нужен ARP

Пакеты в IP-сети маршрутизируются на основе IP-адресов, но на канальном уровне в пределах одной локальной сети (например, Ethernet) доставка осуществляется по MAC-адресам. Для «упаковки» IP-пакета в Ethernet-кадр отправителю необходимо знать MAC-адрес получателя — эту задачу решает ARP.

### Формат ARP-пакета

Протокол работает по принципу запрос-ответ. ARP-пакет содержит следующие поля:

| Поле | Расшифровка | Описание |
| :--- | :--- | :--- |
| **SHA** (Sender Hardware Address) | MAC-адрес отправителя | Физический адрес устройства, отправившего запрос/ответ |
| **SPA** (Sender Protocol Address) | IP-адрес отправителя | Сетевой адрес устройства, отправившего запрос/ответ |
| **THA** (Target Hardware Address) | MAC-адрес назначения | Искомый MAC-адрес (в запросе `00:00:00:00:00:00`) |
| **TPA** (Target Protocol Address) | IP-адрес назначения | IP-адрес, для которого требуется найти MAC |

**Пример ARP-запроса:**

- SHA: `00:00:00:00:00:01` (MAC отправителя)
- SPA: `10.0.0.1` (IP отправителя)
- THA: `00:00:00:00:00:00` (неизвестен)
- TPA: `10.0.0.2` (искомый IP)

ARP-запрос отправляется на broadcast-адрес `FF:FF:FF:FF:FF:FF`. Обрабатывает только хост, чей IP совпадает с TPA.

**Пример ARP-ответа:**

- SHA: `00:00:00:00:00:02` (MAC отвечающего)
- SPA: `10.0.0.2` (IP отвечающего)
- THA: `00:00:00:00:00:01` (MAC запросившего)
- TPA: `10.0.0.1` (IP запросившего)

Ответ отправляется unicast на MAC из поля SHA запроса.

### Алгоритм работы ARP

1. **Проверка ARP-кэша:** хост ищет IP назначения в локальной ARP-таблице. При наличии записи используется сохранённый MAC-адрес.
2. **ARP-запрос (ARP Request):** при отсутствии записи формируется broadcast-запрос на `FF:FF:FF:FF:FF:FF`.
3. **Обработка запроса:** все устройства получают запрос, но отвечает только хост с совпавшим TPA.
4. **ARP-ответ (ARP Reply):** целевой хост отправляет unicast-ответ с MAC-адресом.
5. **Обновление кэша:** запросивший хост сохраняет запись и отправляет IP-пакет.

### Таймауты и отсутствие ответа

При отсутствии ARP-ответа хост повторяет запрос с интервалом 1–3 секунды до 3 раз. После исчерпания попыток протоколы верхнего уровня (TCP, UDP) получают ошибку доставки.

**Последствия:**

- Пакеты не доставляются
- TCP-соединение не устанавливается или разрывается
- UDP-трафик теряется

### Обработка множественных ARP-ответов

Поведение зависит от реализации ОС:

- Некоторые принимают только первый ответ
- Другие могут принять последний полученный ответ
- Отдельные системы принимают ответ даже без предварительного запроса (unsolicited ARP reply)

Отправка беспричинных ARP-ответов может блокировать назначение IP-адресов другим хостам — это один из методов атаки на сеть.

### ARP-таблица (кэш)

Временное хранилище сопоставлений IP ↔ MAC. Записи имеют ограниченный срок жизни для актуальности данных.

**Типы записей:**

| Тип | Описание | Время жизни |
| :--- | :--- | :--- |
| **Динамический** | Добавляется автоматически через ARP-протокол | Удаляется при бездействии (Windows: 30–45 с, Linux: настраивается через `gc_thresh*`) |
| **Статический** | Добавляется вручную администратором | Сохраняется до перезагрузки ОС |

**Алгоритм использования кэша:**

1. При отправке пакета ОС ищет IP назначения в ARP-кэше
2. Запись найдена → используется сохранённый MAC
3. Записи нет → ARP-запрос → ответ добавляется в кэш

**Команды просмотра:**

- **Linux:** `ip n` или `ip neighbour` (рекомендуется), устаревшая `arp -n`
- **Windows:** `arp -a`
- **macOS:** `arp -a`

> **Диагностика:** наличие ARP-записи при неработающем `ping` указывает на проблему сетевого уровня (файервол блокирует ICMP). Подробнее: [Диагностика ping](../../Linux/Diagnostics/Networking/ping.md#диагностика-ping-ne-prohodit-request-timed-out).

## Практические сценарии

### Переполнение ARP-таблицы

Встречается на LXC/KVM-нодах с большим количеством виртуальных машин (или при ARP-флуде). Когда хост переполняет таблицу, он перестаёт добавлять новые записи, что со стороны выглядит как хаотичная деградация сети.

**Симптомы:**

- **Сетевой «хаос»:** одни IP пингуются, другие — нет.
- **Рандомные потери:** пакеты то проходят, то «теряются» без видимой причины.
- **Падение сервисов:** приложения ведут себя нестабильно, запросы отваливаются по таймауту.
- **Сеть жива:** физический линк и маршрутизация в порядке, проблема именно в невозможности сопоставить IP и MAC.

#### Диагностика

- `ip -s neigh` — ищем статусы `INCOMPLETE` (ответ не получен) и `FAILED` (не удалось разрешить).
- `ip neigh show | wc -l` — текущее количество реальных записей в таблице.
- `cat /proc/sys/net/ipv4/neigh/default/gc_thresh3` — максимальный допустимый размер ARP-кэша.
- `dmesg | grep -i arp` — ищем явные предупреждения ядра о переполнении.

#### Решение

**1. Увеличить лимиты ARP-кэша через sysctl:**

```bash
sysctl -w net.ipv4.neigh.default.gc_thresh1=4096
sysctl -w net.ipv4.neigh.default.gc_thresh2=8192
sysctl -w net.ipv4.neigh.default.gc_thresh3=16384
```

- `gc_thresh1` — минимальное количество записей (очистка не запускается).
- `gc_thresh2` — мягкий предел (очистка запускается через 5 секунд после превышения).
- `gc_thresh3` — жёсткий предел (новые записи не добавляются).

**2. Дополнительные меры:**

- Проверить, не генерирует ли лишний ARP-флуд конкретный контейнер или сетевой мост.
- Перезапустить «шумящий» namespace или виртуальную машину, если таблица заполняется слишком быстро.

## Дополнительная информация

### Разновидности ARP

#### Proxy ARP

Техника, позволяющая маршрутизатору отвечать на ARP-запросы своим MAC-адресом для узлов в разных канальных сегментах, но в одной логической IP-сети.

**Принцип работы:**

1. Хост A отправляет ARP-запрос для Хоста B (ошибочно считая его локальным)
2. Маршрутизатор отвечает своим MAC-адресом
3. Хост A отправляет пакеты на MAC маршрутизатора, тот пересылает их Хосту B

**Сценарии использования:**

- Объединение физических сегментов без перенастройки хостов
- Миграция подсетей
- Резервирование шлюза

#### Gratuitous ARP

ARP-ответ (или запрос) о собственном IP-адресе без получения запроса.

**Назначение:**

1. **Уведомление соседей** — обновление ARP-кэшей при смене сетевой карты или IP
2. **Обнаружение конфликтов IP** — ответ другого хоста сигнализирует о конфликте
3. **Проверка уникальности IP** (RFC 5227, IPv4 Address Conflict Detection) — ОС отправляет ARP-запрос с собственным IP в TPA перед применением настроек

**ARP announcement:**

- SPA = TPA (хост ищет себя)
- Отправляется на broadcast `FF:FF:FF:FF:FF:FF`
- Получение ответа означает конфликт IP

**Пример:**

```
SHA: 00:1A:2B:3C:4D:5E
SPA: 192.168.1.100
THA: 00:00:00:00:00:00
TPA: 192.168.1.100  ← совпадает с SPA
```

Ответ на announcement означает, что IP уже занят в сети.

#### Reverse ARP (RARP)

Устаревший протокол для получения IP по известному MAC. Использовался бездисковыми рабочими станциями при загрузке. Заменён на BOOTP, затем на [DHCP](./DHCP/dhcp_overview.md).

#### Inverse ARP (InARP)

Используется в сетях Frame Relay и ATM для получения IP-адреса по адресу канального уровня (DLCI).

### ARP Spoofing (ARP Cache Poisoning)

**ARP Spoofing** — это атака на локальную сеть, при которой злоумышленник отправляет поддельные ARP-ответы, связывая свой MAC-адрес с IP-адресом другого устройства (например, шлюза). В результате трафик начинает проходить через атакующего (MITM — Man-in-the-Middle).

#### Как это работает

1. В локальной сети устройства используют ARP для сопоставления IP ↔ MAC.
2. Протокол ARP не имеет встроенной аутентификации, поэтому таблица ARP может быть «отравлена» (poisoned) без ведома легитимных участников.
3. Атакующий рассылает ложные ARP-ответы (unsolicited replies), подменяя записи в кэше жертв.
4. Жертва считает MAC-адрес атакующего адресом шлюза и отправляет ему весь исходящий трафик.

#### Симптомы атаки (как проявляется в системе)

- **Нестабильный интернет:** обрывы соединений, внезапные задержки или редиректы на незнакомые ресурсы.
- **Неожиданная смена MAC шлюза:** при проверке `ip n` или `arp -n` MAC-адрес шлюза меняется на другой.
- **Дублирующиеся IP в сети:** сообщения в системных логах (`dmesg`) о конфликтах IP-адресов.
- **Записи с одинаковым MAC:** несколько разных IP-адресов в ARP-таблице указывают на один и тот же MAC-адрес (адрес атакующего).

#### Обнаружение в Linux

1. **Мониторинг соседей:**

   ```bash
   ip neigh show
   # Ищем подозрительные смены MAC-адресов
   ```

2. **Использование arping:**

   ```bash
   # Проверка на наличие дубликатов IP (Duplicate Address Detection)
   arping -I eth0 -D 192.168.1.1
   # Если получен ответ — IP занят другим MAC-адресом
   ```

3. **Автоматический мониторинг:**
   - **arpwatch** — демон, который отслеживает ARP-активность и отправляет уведомления о смене привязок IP-MAC.
   - **tcpdump:**

     ```bash
     sudo tcpdump -v -i eth0 arp
     # Анализ аномального количества ARP-ответов
     ```

#### Методы защиты в Linux

1. **Статические ARP-записи:**
   Для критически важных узлов (шлюз, сервер БД) можно задать соответствие вручную:

   ```bash
   # Добавить перманентную запись
   ip neigh add 192.168.1.1 lladdr 00:11:22:33:44:55 dev eth0 nud permanent
   ```

2. **Фильтрация через arptables:**
   Позволяет блокировать подозрительные ARP-пакеты на уровне ядра:

   ```bash
   # Разрешить ARP-ответы только от доверенного MAC шлюза
   arptables -A INPUT --source-ip 192.168.1.1 --source-mac ! 00:11:22:33:44:55 -j DROP
   ```

3. **Настройки sysctl:**
   - `net.ipv4.conf.all.arp_ignore=1` — отвечать на ARP-запросы только если IP-адрес настроен на входящем интерфейсе.
   - `net.ipv4.conf.all.arp_announce=2` — использовать наиболее подходящий локальный адрес для генерации ARP-запросов.
4. **Сетевые меры (вне хоста):**
   - **Dynamic ARP Inspection (DAI)** на коммутаторах.
   - **Port Security** — ограничение количества MAC-адресов на порту.
