# Петли перенаправления DNS (DNS Forwarding Loops)

## Определения

**Петля перенаправления DNS (DNS Forwarding Loop)** — критическая ошибка конфигурации, при которой DNS-запрос бесконечно циркулирует между серверами или возвращается к исходному серверу, не получая окончательного ответа. Это приводит к исчерпанию ресурсов (CPU, RAM, дескрипторы файлов) и резкому росту задержек (Latency) или полному отказу в обслуживании.

**Форвардер (Forwarder)** — DNS-сервер, которому делегируется выполнение рекурсивного поиска для зон, за которые локальный сервер не является авторитетным.

**tsuNAME** — уязвимость и тип циклической зависимости на уровне DNS-зон (authoritative level), возникающий из-за взаимных ссылок в записях **NS (Name Server)** между разными зонами (например, `.com` ссылается на сервер в `.nl`, который, в свою очередь, ссылается на сервер в `.com`). В 2026 году остается актуальной для частных DNS-инфраструктур.

**Бесконечная рекурсия (Infinite Recursion)** — состояние, при котором резолвер не может завершить поиск из-за циклической цепочки CNAME или NS-записей, превышая лимит глубины запроса (обычно 20–50 шагов).

**systemd-resolved** — системная служба Linux для разрешения имен, использующая локальные заглушки (stub-resolvers) на адресах `127.0.0.53` (стандарт) и `127.0.0.54` (расширенные функции в современных дистрибутивах).

## Основные концепции

### Механизмы возникновения петли

В классической конфигурации (BIND, CoreDNS, Unbound) сервер, не найдя ответа в локальном кэше или авторитетных зонах, обращается к списку `forwarders`. Цикл возникает, если один из адресов указывает на сам сервер (напрямую или косвенно).

**Типовые причины (2026):**
1.  **Прямое зацикливание:** Указание собственного IP (или `127.0.0.1`) в секции `forwarders` (например, в `named.conf`).
2.  **Симбиотическая петля с резолвером ОС:** CoreDNS в Kubernetes наследует `/etc/resolv.conf` узла, где прописан `nameserver 127.0.0.53`. CoreDNS шлет запрос на `127.0.0.53`, а `systemd-resolved` пересылает его обратно в CoreDNS.
3.  **Петля между серверами (Cross-Loop):** Сервер А пересылает запросы серверу Б, а сервер Б — серверу А.
4.  **Петли в гибридных сетях (VPN/SD-WAN):** Возникают, когда VPN-клиент (например, Tailscale или AWS VPN) добавляет свой виртуальный интерфейс в список апстримов `systemd-resolved`, создавая конфликт с физическим интерфейсом.
5.  **Подмена адреса (Evasion):** Современные серверы сравнивают адрес запроса и форвардера. Однако, если запрос уходит с одного интерфейса, а принимается на другом (или через NAT/DNAT), стандартный Loop Detection может не сработать.

### Влияние на производительность

Петля вызывает каскадную деградацию системы:
- **Экспоненциальный рост Latency:** Запрос проходит через цикл, пока не сработает таймаут (обычно 2–5 сек) или лимит шагов рекурсии.
- **Исчерпание файловых дескрипторов:** Каждый виток петли занимает сокет/дескриптор. Приводит к ошибке `too many open files` и отказу в обслуживании других сервисов.
- **CPU/RAM Spikes:** Непрерывная обработка одних и тех же пакетов потребляет 100% ресурсов процессора.
- **Маскировка ошибки (Fallback Latency):** В режиме `forward first` сервер после таймаута в петле может попытаться выполнить рекурсию самостоятельно, что дает правильный ответ, но с огромной задержкой.
- **DDoS-эффект (tsuNAME):** В случае циклов на авторитативном уровне резолверы могут генерировать в 10–20 раз больше трафика к корневым серверам, пытаясь разрешить зависимость.

## Практические сценарии

### 1. Петля в BIND (named.conf)

**Симптомы:** В логах сообщения `maximum number of recursions exceeded` или `too many open files`.

**Ошибочная конфигурация:**
```conf
options {
    recursion yes;
    forward first;
    forwarders {
        127.0.0.1; // ОШИБКА: Сервер шлет запрос сам себе
    };
};
```

### 2. Петля CoreDNS и systemd-resolved (Kubernetes / Ubuntu)

Наиболее распространенный сценарий в современных облачных средах.

**Цепочка:**
1.  **Хост:** `/etc/resolv.conf` содержит `nameserver 127.0.0.53`.
2.  **CoreDNS:** Плагин `forward . /etc/resolv.conf` отправляет внешние запросы на `127.0.0.53`.
3.  **systemd-resolved:** Принимает запрос и, если upstream настроен обратно на CoreDNS (или через DNAT в iptables), возникает цикл.

**Критическая уязвимость (Март 2026):**
В плагине `loop` обнаружена уязвимость к DoS-атакам. Злоумышленник может предугадать проверочный запрос (HINFO) из-за слабого PRNG и отправить 3+ аналогичных пакета. CoreDNS воспримет это как петлю и немедленно завершит процесс (`log.Fatalf`), вызывая отказ сервиса.

**Диагностика:** Поды CoreDNS в статусе `CrashLoopBackOff`, в логах: `plugin/loop: Loop detected`.

### 3. Петли в гибридных и VPN-сетях (Amazon Linux 2023 / Tailscale)

На Amazon Linux 2023 и Fedora 43+ часто возникает петля при использовании VPN-туннелей. `systemd-resolved` может автоматически добавить DNS-адрес VPN-интерфейса в список глобальных резолверов, создавая конфликт маршрутизации для DNS-трафика между физическим и туннельным интерфейсом.

### 4. Диагностика через tcpdump и ngrep

Для выявления петли анализируйте трафик на всех интерфейсах. Признак петли — повторяющиеся запросы с одним Transaction ID и уменьшающимся TTL.

```bash
# Захват трафика DNS на всех интерфейсах
sudo tcpdump -i any -n -vvv port 53 -w dns-debug.pcap

# Анализ в реальном времени через ngrep (ищите шторм одинаковых имен)
sudo ngrep -d any . port 53

# Проверка текущих апстримов systemd-resolved
resolvectl status
```

### 5. Проверка через dig и анализ таймаутов

В режиме `forward only` петля проявляется мгновенно как ошибка `SERVFAIL`.

```bash
# Проверка времени ответа и цепочки (анализ RTT)
dig @127.0.0.1 google.com
# → Если время > 2-5 секунд, это признак fallback после таймаута в петле.
```

## Дополнительная информация

### Исправление и профилактика

1.  **Исключение локальных адресов:** Никогда не указывайте `127.0.0.1`, `::1` или собственные IP сервера в списке форвардеров.
2.  **Чистый resolv.conf в Kubernetes:** Используйте путь к файлу без заглушек:
    `--resolv-conf /run/systemd/resolve/resolv.conf` (параметр kubelet).
3.  **NodeLocal DNSCache:** Использование локального кэширующего агента на каждом узле Kubernetes радикально снижает вероятность возникновения петель за счет жестко заданной иерархии апстримов.
4.  **Валидация зон:** Инструменты типа **CycleHunter** помогают обнаружить циклы `tsuNAME` на этапе проектирования инфраструктуры.
5.  **Политика Forward Only:** В критических средах используйте `forward only;`. Это делает ошибки конфигурации явными, предотвращая скрытые задержки.

### Инструментарий

- **named-checkconf:** Валидация синтаксиса BIND.
- **Colasoft Capsa (2026 Edition):** Анализатор трафика с автоматическим обнаружением DNS Loop.
- **Prometheus Metrics:** Отслеживайте метрику `coredns_loop_hits_total` для CoreDNS.
- **resolvectl:** Управление и диагностика резолвера в современных Linux-системах.
