# Процесс разрешения имён в DNS

## Определения

**DNS-резолвинг (Resolution)** — многоэтапный процесс преобразования доменного имени в сетевой адрес (IP) или другие данные. Является центральным механизмом DNS, без которого невозможно функционирование HTTP, SMTP, SIP и большинства других интернет-протоколов.

*   **Рекурсивный запрос (Recursive Query):** запрос, при котором клиент перекладывает всю работу по поиску ответа на резолвер (флаг `RD=1`). Резолвер обязан вернуть либо готовый ответ, либо ошибку. Используется при взаимодействии Stub Resolver с рекурсивным резолвером.
*   **Итеративный запрос (Iterative Query):** запрос, при котором сервер возвращает лучший известный ему ответ (Referral — ссылку на вышестоящий или нижестоящий сервер), а клиент (резолвер) продолжает поиск самостоятельно. Используется при взаимодействии рекурсивного резолвера с корневыми, TLD и авторитетными серверами.
*   **Реферал (Referral):** DNS-ответ, указывающий на список авторитетных серверов (NS) для следующего уровня иерархии (например, корень ссылается на серверы `.com`). Содержит NS-записи и Glue Records (при необходимости).
*   **Happy Eyeballs (RFC 8305):** алгоритм параллельного разрешения имён (одновременный запрос A и AAAA записей) и выбора наиболее быстрого протокола (IPv6 или IPv4) для минимизации задержек. Современные реализации (glibc, браузеры) используют сдвиг 150–300 мс в пользу IPv6 перед запуском IPv4-запроса.
*   **Негативное кэширование (RFC 2308):** механизм сохранения в кэше информации о несуществующих доменах (NXDOMAIN) для предотвращения повторных запросов к авторитетным серверам. Время жизни негативного кэша определяется полем Minimum TTL в записи SOA зоны.
*   **Рекурсивный резолвер (Recursive Resolver):** сервер, выполняющий всю цепочку итеративных запросов от корня до авторитетного сервера от имени клиента. Кэширует ответы и возвращает клиенту готовый результат. Примеры: Google Public DNS (8.8.8.8), Cloudflare (1.1.1.1), Quad9 (9.9.9.9).
*   **Stub Resolver (Заглушка):** минимальная библиотека на стороне клиента (например, `getaddrinfo` в `glibc`), которая только передаёт запрос рекурсивному резолверу. Не выполняет итеративный поиск самостоятельно. В Linux запрашивает серверы из `/etc/resolv.conf`.
*   **Авторитетный ответ (Authoritative Answer):** ответ от сервера, владеющего зоной (флаг `AA` в заголовке). Считается наиболее достоверным, так как получен непосредственно из файла зоны.
*   **Неавторитетный ответ (Non-Authoritative Answer):** ответ, извлечённый из кэша промежуточного рекурсивного сервера. Не гарантирует актуальности данных сверх TTL, но значительно быстрее.

## Базовые концепции

### Типы запросов и взаимодействие

| Характеристика | Рекурсивный | Итеративный |
| :--- | :--- | :--- |
| **Участники** | Клиент (Stub) ↔ Рекурсивный резолвер | Рекурсивный резолвер ↔ Авторитетные серверы |
| **Флаг** | `RD=1` (Recursion Desired) | `RD=0` |
| **Результат** | Окончательный ответ (IP/CNAME/Error) | Ссылка на другой сервер (Referral) |
| **Нагрузка** | Высокая (ресурс резолвера) | Распределённая (между уровнями иерархии) |
| **Пример** | `dig example.com` (через системный резолвер) | `dig +trace example.com` (прямые запросы к серверам) |

### Кэширование на нескольких уровнях

Ответ DNS-резолвера кэшируется на нескольких уровнях системы, что критично для производительности:

| Уровень | Механизм | Управление кэшем |
| :--- | :--- | :--- |
| **Браузер** | Встроенный DNS-кэш Chrome/Firefox (обычно 60 сек для misses) | `chrome://net-internals/#dns` (Chrome), `about:networking#dns` (Firefox) |
| **ОС (systemd-resolved)** | `systemd-resolved` на `127.0.0.53` с TTL-кэшем | `resolvectl flush-caches` |
| **ОС (nscd)** | Устаревший демон; часто игнорирует TTL | `sudo nscd -i hosts` |
| **Рекурсивный резолвер** | Публичные серверы (8.8.8.8 и др.) обслуживают миллионы клиентов | TTL-кэш (определяется владельцем зоны) |
| **Авторитетный сервер** | Ответ из файла зоны (не является кэшем в строгом смысле) | Управление через SOA-запись |

**Коллективная выгода:** рекурсивный резолвер обслуживает тысячи пользователей одновременно. Если кто-то уже запрашивал `google.com`, ответ уже лежит в памяти резолвера и отдается мгновенно всем остальным. Именно поэтому популярные сайты открываются быстрее малоизвестных.

### Разрешение через /etc/hosts

Приоритет файловой таблицы зависит от конфигурации NSS (`/etc/nsswitch.conf`):

```bash
# Типичная конфигурация:
hosts: files resolve dns

# Порядок:
# 1. files → /etc/hosts (если имя найдено — DNS не запрашивается)
# 2. resolve → systemd-resolved (через D-Bus API)
# 3. dns → /etc/resolv.conf (классические UDP/TCP запросы)
```

**Важно:** утилиты `dig` и `nslookup` обходят NSS и `/etc/hosts`, обращаясь напрямую к DNS-серверам. Для проверки разрешения «глазами системы» используйте `getent hosts` или `getent ahosts`.

### Современные оптимизации

*   **QNAME Minimization (RFC 7816):** на каждом этапе итеративного запроса резолвер отправляет только ту часть имени, которая нужна текущему серверу (например, при поиске `a.b.c.com` корню отправляется только запрос про `.com`). Это повышает приватность, так как каждый сервер видит только минимально необходимую часть имени.
*   **Happy Eyeballs v2/v3:** современные браузеры и системные библиотеки (glibc) не ждут ответа AAAA, прежде чем запросить A. Они запускают оба процесса параллельно с небольшим сдвигом (обычно 150–300 мс в пользу IPv6). Если IPv6 отвечает быстрее, используется IPv6; если нет — автоматически переключается на IPv4.
*   **Агрессивное кэширование (RFC 8198):** рекурсивные резолверы могут возвращать устаревшие записи (stale answers) из кэша, одновременно запрашивая актуальные данные у авторитетного сервера. Снижает задержку для пользователя при сохранении актуальности данных.

## Практические сценарии

### Предусловия

Для работы с командами diagnostic DNS необходимы следующие инструменты:

```bash
# Debian/Ubuntu
sudo apt install dnsutils          # dig, nslookup, host

# RHEL/CentOS
sudo yum install bind-utils        # dig, nslookup, host

# Проверка наличия dig
dig -v
# → DiG 9.18.18-0ubuntu0.22.04.2-Ubuntu

# Проверка systemd-resolved
resolvectl --version
```

### Полный алгоритм разрешения (example.com)

При пустом кэше процесс выглядит следующим образом:

1.  **Локальная проверка (System Check):** система сначала ищет соответствие в локальном файле **hosts** (наследник исторического `hosts.txt`). Если имя найдено там, запрос во внешнюю сеть не отправляется. Это часто используется разработчиками для перенаправления домена на `localhost`.
2.  **Браузер (Happy Eyeballs):** если в `hosts` пусто, инициирует параллельный резолвинг `A` и `AAAA` записей через системную библиотеку (Stub Resolver).
3.  **Stub Resolver → Рекурсивный резолвер (UDP/53, RD=1):** отправляет рекурсивный запрос провайдеру или публичному DNS-серверу.
4.  **Резолвер → Root (Итерация 1):** спрашивает корень `.` про `example.com`. Получает реферал на серверы TLD `.com`.
5.  **Резолвер → TLD (Итерация 2):** спрашивает серверы `.com` про `example.com`. Получает реферал на авторитетные серверы владельца (например, `ns1.example.com`).
6.  **Резолвер → Authoritative (Итерация 3):** спрашивает `ns1.example.com` адрес хоста. Получает авторитетный ответ (`AA=1`) с IP-адресом.
7.  **Резолвер → Клиент:** возвращает IP и сохраняет его в кэш согласно TTL.

**Схема взаимодействия:**

```
Клиент          Резолвер        Root Server     TLD Server      Authoritative
  |                |                |               |                |
  |---RD=1-------->|                |               |                |
  |                |---Iterative--->|               |                |
  |                |<--Referral-----|               |                |
  |                |---Iterative-------------------->|                |
  |                |<--Referral----------------------|                |
  |                |---Iterative------------------------------------->|
  |                |<--AA=1, A-record--------------------------------|
  |<--IP address---|                |               |                |
```

### Эффекты кэширования

*   **Коллективная выгода:** рекурсивный резолвер обслуживает тысячи пользователей одновременно. Если кто-то уже запрашивал `google.com`, ответ уже лежит в памяти резолвера и отдается мгновенно всем остальным. Именно поэтому популярные сайты открываются быстрее малоизвестных.
*   **Негативное кэширование (Отрицательный ответ):** если домена не существует, резолвер запоминает этот факт.
    *   **Пример с опечаткой:** если вы опечатались в новом поддомене (`ww.example.com`), резолвер получит ответ "NXDOMAIN" и закэширует его. Даже если вы сразу исправите ошибку, домен может не открываться до истечения срока негативного кэша (задается в записи SOA зоны).
    *   **Практическое значение:** негативное кэширование защищает от «DNS-штормов» при массовых запросах к опечаткам, но может отсрочить появление newly created DNS-записей.

### Диагностика этапов через dig

**1. Трассировка пути (эмуляция итераций):**

```bash
# Просмотр всей цепочки от корня до хоста
dig +trace example.com

# Ожидаемый вывод:
# .                     518400  IN  NS  a.root-servers.net.
# com.                  172800  IN  NS  a.gtld-servers.net.
# example.com.          172800  IN  NS  ns1.example.com.
# example.com.          3600    IN  A   93.184.216.34
```

**2. Проверка авторитетности и кэша:**

```bash
# Запрос к резолверу: флаг aa отсутствует (ответ из кэша или рекурсии)
dig @8.8.8.8 example.com
# → ;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
#    (aa отсутствует — неавторитетный ответ)

# Прямой запрос к авторитетному серверу: флаг aa присутствует
dig @ns1.example.com example.com
# → ;; flags: qr aa rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
#    (aa присутствует — авторитетный ответ)
```

**3. Замер времени разрешения (latency):**

```bash
# Поле "Query time" показывает задержку резолвинга
dig example.com | grep "Query time"
# → ;; Query time: 45 msec
```

**4. Изучение цепочки CNAME:**

```bash
# Если имя является CNAME, dig автоматически следует за цепочкой
dig www.example.com A +short
# → www.example.com.  300  IN  CNAME  cdn.example.net.
# → cdn.example.net.  300  IN  A      198.51.100.1

# Без следования за CNAME (только прямая запись)
dig www.example.com A +short +norecurse
```

**5. Проверка TTL и динамики кэша:**

```bash
# Первый запрос: TTL максимальный (из авторитетного источника)
dig @ns1.example.com example.com A +noall +answer
# → example.com.  3600  IN  A  93.184.216.34

# Повторный запрос через 5 минут: TTL уменьшился
dig @8.8.8.8 example.com A +noall +answer
# → example.com.  3300  IN  A  93.184.216.34
```

**6. Очистка конкретных записей из кэша (systemd-resolved):**

```bash
# Очистка кэша для конкретного имени
resolvectl flush-caches

# Проверка, что кэш пуст
resolvectl statistics | grep "Current Cache Size"
# → Current Cache Size: 0
```

### Проверка через systemd-resolved

```bash
# Просмотр текущей конфигурации DNS
resolvectl status
# → Global
# →          Protocols: +LLMNR +mDNS -DNSOverTLS DNSSEC=no/unsupported
# → resolv.conf mode: stub

# Проверка того, как имя разрешается через службу
resolvectl query example.com
# → example.com: 93.184.216.34
# → (example.com)

# Проверка DNS-серверов для конкретного домена
resolvectl domain example.com
# → example.com: 1.1.1.1 8.8.8.8

# Очистка кэша (при подозрении на устаревшие записи)
resolvectl flush-caches

# Просмотр статистики кэша
resolvectl statistics
# → Transactions: ...
# → Cache Statistics: 1234 hits, 567 misses
```

### Проверка NSS (порядок разрешения имён)

```bash
# getent показывает итоговый результат с учётом /etc/nsswitch.conf
getent hosts example.com
# → 93.184.216.34    example.com

# Если имя найдено в /etc/hosts, оно будет возвращено
# независимо от состояния DNS-сервера

# Проверка всех адресов (включая IPv6)
getent ahosts example.com
# → 93.184.216.34    STREAM
# → 93.184.216.34    DGRAM
# → 2606:2800:220:1:248:1893:25c8:1946 STREAM
```

## Типичные ошибки и их решение

### Ошибка: SERVFAIL (код 2)

**Симптом:** `dig` возвращает `status: SERVFAIL`.

**Причины и решение:**
1.  **Проблемы с вышестоящими серверами:** авторитетный сервер зоны недоступен. Проверьте доступность NS-серверов: `dig NS example.com` → `dig @<NS-IP> example.com`.
2.  **DNSSEC-валидация провалилась:** если на резолвере включён DNSSEC, повреждённые подписи вызовут SERVFAIL. Проверьте через `dig +dnssec +cd example.com` (флаг `cd` отключает проверку).
3.  **Петли перенаправления:** DNS-сервер пересылает запрос самому себе. Подробнее: [Петли перенаправления DNS](./dns_forwarding_loops.md).

### Ошибка: NXDOMAIN (код 3)

**Симптом:** `dig` возвращает `status: NXDOMAIN`.

**Причины и решение:**
1.  **Домен не существует:** имя не зарегистрировано или было удалено. Проверьте через `whois example.com`.
2.  **Нет делегирования:** NS-записи для поддомена не настроены в родительской зоне.
3.  **Негативное кэширование:** резолвер запомнил NXDOMAIN на время Minimum TTL. Подождите или очистите кэш: `resolvectl flush-caches`.

### Ошибка: REFUSED (код 5)

**Симптом:** `dig` возвращает `status: REFUSED`.

**Причины и решение:**
1.  **Recursion отключена:** сервер не выполняет рекурсию для вашего IP. Проверьте ACL в конфигурации BIND (`allow-query`, `allow-recursion`).
2.  **Запрос к авторитетному серверу:** вы отправляете рекурсивный запрос авторитетному серверу, который не поддерживает рекурсию. Используйте публичный рекурсивный резолвер (8.8.8.8, 1.1.1.1).

### Медленный DNS-резолв (задержки 5 секунд)

**Симптом:** приложение «зависает» на 5 секунд при обращении к новым именам.

**Причины и решение:**
1.  **Проблема ndots:** в Kubernetes и контейнерах параметр `ndots:5` заставляет систему сначала пытаться разрешить имя как absolute (с приставкой search domain). Решение: используйте FQDN с точкой на конце (`example.com.`) или установите `ndots:1`.
2.  **Параллельные A/AAAA запросы (musl):** в Alpine Linux (musl libc) запросы A и AAAA отправляются параллельно. Если IPv6-запрос «зависает» из-за проблем с сетью, общая задержка достигает 5 секунд. Решение: `options single-request-reopen` в `/etc/resolv.conf` или настройка `dnsConfig` в Kubernetes.
3.  **Системный резолвер недоступен:** `systemd-resolved` не запущен или порт 53 занят другим процессом. Проверьте: `resolvectl status` и `ss -ulnp | grep :53`.

### Конфликт systemd-resolved и BIND

**Симптом:** BIND не может запуститься, так как порт 53 занят.

**Решение:**
```bash
# 1. Остановить и отключить systemd-resolved
sudo systemctl stop systemd-resolved
sudo systemctl disable systemd-resolved

# 2. Настроить /etc/resolv.conf на указание самого себя или внешних DNS
echo "nameserver 127.0.0.1" | sudo tee /etc/resolv.conf

# 3. Запустить BIND
sudo systemctl start named
```

### Цепочка CNAME: неожиданное поведение

**Симптом:** `dig` разрешает имя через 2+ прыжка CNAME, приложение получает другой IP.

**Причина:** CNAME перенаправляет на другое имя, которое может указывать на другой IP (CDN, балансировщик). Резолвер следует за всей цепочкой до A/AAAA-записи.

**Диагностика:**
```bash
# Показать всю цепочку CNAME
dig www.example.com A +noall +answer
# → www.example.com.  300  IN  CNAME  cdn.provider.com.
# → cdn.provider.com. 60   IN  A      198.51.100.1

# Проверить, куда ведёт CNAME
dig cdn.provider.com A +short
# → 198.51.100.1
```

**Решение:** если нужен прямой IP (например, для firewall правил), разрешайте конечное имя из CNAME-цепочки, а не промежуточное.

### Запрос к несуществующему поддомену с wildcard

**Симптом:** `dig sub.example.com` возвращает IP, хотя для `sub.example.com` нет прямой A-записи.

**Причина:** настроена wildcard-запись `*.example.com`, которая отвечает на все несуществующие имена.

**Важно:** wildcard работает **только для несуществующих** имён — если для `sub.example.com` есть прямая A-запись, wildcard не используется.

## Лучшие практики

*   **Используйте FQDN с точкой** при работе с DNS-инструментами (`dig`, `nslookup`), чтобы исключить влияние локальных суффиксов поиска.
*   **Проверяйте разрешение через `getent hosts`** вместо `dig` при диагностике приложений — `getent` учитывает NSS и `/etc/hosts`, как это делает само приложение.
*   **Очищайте кэш** при подозрении на устаревшие записи: `resolvectl flush-caches` (systemd-resolved), `sudo nscd -i hosts` (nscd).
*   **Не опускайте TTL ниже 60 секунд** без крайней необходимости — это создает экстремальную нагрузку на DNS-серверы.
*   **Для Kubernetes:** используйте `ndots:1` и FQDN с точкой (`example.com.`) для внешних доменов, чтобы избежать 5-секундных задержек.
*   **В контейнерах (Alpine/musl):** добавляйте `options single-request-reopen` в `/etc/resolv.conf` для предотвращения блокировки при параллельных A/AAAA запросах.
*   **Для высоконагруженных сред:** рассмотрите NodeLocal DNSCache для кэширования DNS на уровне узлов и снижения нагрузки на CoreDNS.
*   **`getaddrinfo()` блокирует поток:** Стандартный glibc-резолвер является блокирующим. Приложение не может выполнять другие операции пока DNS-запрос не завершится. Для асинхронного резолвинга используйте `c-ares` (C/C++), `Go net.Resolver` (Go), или `dns` модуль (Node.js).
*   **glibc vs musl:** glibc учитывает `/etc/nsswitch.conf` и поддерживает NSS (NSS, LDAP, SSSD), musl (Alpine) игнорирует NSS и читает только `/etc/resolv.conf`. В Alpine-контейнерах `getent hosts` может не работать для кастомных NSS-источников.
