# Процесс разрешения имён в DNS

## Определения

**Рекурсивный запрос (Recursive Query)** — запрос, при котором DNS-сервер (резолвер) берёт на себя полную работу по поиску ответа и возвращает клиенту окончательный результат (IP-адрес или сообщение об ошибке).

**Итеративный запрос (Iterative Query)** — запрос, при котором сервер возвращает лучший известный ему ответ (часто — ссылку на другой авторитетный сервер), а клиент продолжает поиск самостоятельно.

**Реферал (Referral)** — ответ DNS-сервера, который не содержит искомых данных, но указывает на другой DNS-сервер, обладающий полномочиями для запрашиваемой зоны или поддомена.

## Базовые концепции

### Сравнение типов запросов

| Характеристика | Рекурсивный | Итеративный |
| :--- | :--- | :--- |
| **Кто выполняет** | Клиент → Резолвер | Резолвер → Другие серверы |
| **Требование** | Флаг `RD=1` (Recursion Desired) | Флаг `RD=0` |
| **Ответ** | Окончательный (IP или ошибка) | Лучший известный (Referral) |
| **Нагрузка** | Высокая нагрузка на резолвер | Распределённая нагрузка |
| **Кэширование** | Да | Нет (или минимальное) |

### Механизм кэширования

После получения ответа от авторитетного сервера, рекурсивный резолвер сохраняет результат в кэше на время, указанное в поле **TTL (Time To Live — время жизни)** записи. Это позволяет мгновенно отвечать на повторные запросы к тому же домену, снижая нагрузку на иерархию DNS и время ожидания для клиента.

## Практические сценарии

### Алгоритм разрешения example.com

Процесс поиска IP-адреса для домена `example.com` при отсутствии записи в кэше резолвера:

1. **Клиент → Резолвер (Рекурсивный запрос, `RD=1`)**
   Клиент (например, браузер через системный резолвер) спрашивает DNS-сервер провайдера или публичный резолвер (`8.8.8.8`): "Где находится `example.com`?".

2. **Резолвер → Корневой сервер (Итеративный запрос)**
   Резолвер обращается к одному из 13 корневых серверов (Root Servers).
   - **Ответ:** "Я не знаю IP `example.com`, но за зону `.com` отвечают TLD-серверы (Top-Level Domain — домен верхнего уровня). Вот их адреса".

3. **Резолвер → TLD-сервер (.com) (Итеративный запрос)**
   Резолвер спрашивает сервер зоны `.com`.
   - **Ответ:** "Я не знаю IP `example.com`, но за этот домен отвечают авторитетные серверы `ns1.example.com`. Вот их адреса".

4. **Резолвер → Авторитетный сервер (Итеративный запрос)**
   Резолвер спрашивает сервер, указанный владельцем домена.
   - **Ответ:** "`example.com` находится по адресу `93.184.216.34`. Это авторитетный ответ (установлен флаг `AA=1`)".

5. **Резолвер → Клиент**
   Резолвер кэширует результат и передаёт его клиенту.

### Диагностика с помощью dig

Утилита `dig` позволяет эмулировать работу рекурсивного резолвера и анализировать этапы разрешения.

**1. Трассировка разрешения (+trace):**
```bash
dig +trace example.com
```
Команда показывает последовательную цепочку ответов от корневых, TLD и авторитетных серверов.

**2. Проверка авторитетности ответа:**
```bash
# Прямой запрос к авторитетному серверу (флаг aa присутствует в секции flags)
dig @ns1.example.com example.com

# Запрос к публичному резолверу (флаг aa отсутствует, ответ взят из кэша)
dig @8.8.8.8 example.com
```

**3. Проверка TTL записи:**
```bash
dig +noall +answer +ttlid example.com
# → example.com. 3600 IN A 93.184.216.34
```
Число `3600` указывает, сколько секунд запись будет считаться актуальной в кэше резолвера перед повторным запросом.
