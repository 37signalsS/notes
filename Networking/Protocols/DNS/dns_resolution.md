# Процесс разрешения имён в DNS

## Определения

**DNS-резолвинг (Resolution)** — многоэтапный процесс преобразования доменного имени в сетевой адрес (IP) или другие данные.

*   **Рекурсивный запрос (Recursive Query):** запрос, при котором клиент перекладывает всю работу по поиску ответа на резолвер (флаг `RD=1`). Резолвер обязан вернуть либо готовый ответ, либо ошибку.
*   **Итеративный запрос (Iterative Query):** запрос, при котором сервер возвращает лучший известный ему ответ (Referral — ссылку на вышестоящий или нижестоящий сервер), а клиент (резолвер) продолжает поиск самостоятельно.
*   **Реферал (Referral):** DNS-ответ, указывающий на список авторитетных серверов (NS) для следующего уровня иерархии (например, корень ссылается на серверы `.com`).
*   **Happy Eyeballs (RFC 8305):** алгоритм параллельного разрешения имен (одновременный запрос A и AAAA записей) и выбора наиболее быстрого протокола (IPv6 или IPv4) для минимизации задержек.
*   **Негативное кэширование (RFC 2308):** механизм сохранения в кэше информации о несуществующих доменах (NXDOMAIN) для предотвращения повторных запросов к авторитетным серверам.

## Базовые концепции

### Типы запросов и взаимодействие

| Характеристика | Рекурсивный | Итеративный |
| :--- | :--- | :--- |
| **Участники** | Клиент (Stub) ↔ Рекурсивный резолвер | Рекурсивный резолвер ↔ Авторитетные серверы |
| **Флаг** | `RD=1` (Recursion Desired) | `RD=0` |
| **Результат** | Окончательный ответ (IP/CNAME/Error) | Ссылка на другой сервер (Referral) |
| **Нагрузка** | Высокая (ресурс резолвера) | Распределённая (между уровнями иерархии) |

### Жизненный цикл кэша

1.  **TTL (Time To Live):** авторитетный сервер определяет время (в секундах), в течение которого ответ считается достоверным.
2.  **Позитивное кэширование:** сохранение найденных IP-адресов.
3.  **Негативное кэширование:** сохранение ответов `NXDOMAIN` (домен не найден) на время, указанное в поле `Minimum TTL` записи SOA зоны. Это критично для защиты от "DNS-штормов" при массовых запросах к опечаткам.

### Современные оптимизации

*   **QNAME Minimization (RFC 7816):** на каждом этапе итеративного запроса резолвер отправляет только ту часть имени, которая нужна текущему серверу (например, при поиске `a.b.c.com` корню отправляется только запрос про `.com`). Это повышает приватность.
*   **Happy Eyeballs v2/v3:** современные браузеры и системные библиотеки (glibc) не ждут ответа AAAA, прежде чем запросить A. Они запускают оба процесса параллельно с небольшим сдвигом (обычно 150-300 мс в пользу IPv6).

## Практические сценарии

### Полный алгоритм разрешения (example.com)

При пустом кэше процесс выглядит следующим образом:

1.  **Браузер (Happy Eyeballs):** инициирует параллельный резолвинг `A` и `AAAA` записей через системную библиотеку (Stub Resolver).
2.  **Stub Resolver → Рекурсивный резолвер (UDP/53, RD=1):** отправляет рекурсивный запрос.
3.  **Резолвер → Root (Итерация 1):** спрашивает корень `.` про `example.com`. Получает реферал на серверы TLD `.com`.
4.  **Резолвер → TLD (Итерация 2):** спрашивает серверы `.com` про `example.com`. Получает реферал на авторитетные серверы владельца (например, `ns1.example.com`).
5.  **Резолвер → Authoritative (Итерация 3):** спрашивает `ns1.example.com` адрес хоста. Получает авторитетный ответ (`AA=1`) с IP-адресом.
6.  **Резолвер → Клиент:** возвращает IP и сохраняет его в кэш согласно TTL.

### Диагностика этапов через dig

**1. Трассировка пути (эмуляция итераций):**
```bash
# Просмотр всей цепочки от корня до хоста
dig +trace google.com
```

**2. Проверка авторитетности и кэша:**
```bash
# Запрос к резолверу: флаг aa отсутствует (ответ из кэша или рекурсии)
dig @8.8.8.8 google.com

# Прямой запрос к авторитетному серверу: флаг aa присутствует в секции flags
dig @ns1.google.com google.com
```

**3. Замер времени разрешения (latency):**
```bash
# Поле "Query time" показывает задержку резолвинга
dig example.com | grep "Query time"
# -> ;; Query time: 45 msec
```
