# Процесс разрешения имен в DNS

## Определения

**Рекурсивный запрос (Recursive Query)** — запрос, при котором DNS-сервер берёт на себя полную работу по поиску ответа и возвращает клиенту окончательный результат.

**Итеративный запрос (Iterative Query)** — запрос, при котором сервер возвращает лучший известный ответ (часто — ссылку на другой сервер), а клиент продолжает поиск самостоятельно.

**DNS-резолвер** — сервер, выполняющий рекурсивные запросы от клиентов (например, `8.8.8.8`, `1.1.1.1`).

**Авторитетный сервер** — сервер, хранящий оригинальные записи зоны и отвечающий за неё.

## Основные концепции

### Сравнение типов запросов

| Характеристика | Рекурсивный | Итеративный |
|----------------|-------------|-------------|
| **Кто выполняет** | Клиент → резолвер | Резолвер → другие серверы |
| **Требование** | Флаг `RD=1` (Recursion Desired) | Флаг `RD=0` |
| **Ответ** | Окончательный (IP или ошибка) | Лучший известный (часто referral) |
| **Нагрузка** | На сервере резолвера | Распределённая |
| **Кэширование** | Да | Нет (или минимальное) |

### Флаги в DNS-заголовке

| Флаг | Название | Описание |
|------|----------|----------|
| **RD** | Recursion Desired | `1` — клиент хочет рекурсивный запрос |
| **RA** | Recursion Available | `1` — сервер поддерживает рекурсию |
| **AA** | Authoritative Answer | `1` — ответ от авторитетного сервера |

## Практические сценарии

### Полный путь разрешения `example.com`

**Шаг 1: Клиент → Локальный DNS-резолвер (рекурсивный)**

```
Клиент (192.168.1.10) → Резолвер (8.8.8.8)
Запрос: "Где example.com?" (RD=1)
```

Клиент устанавливает флаг `RD=1`, требуя окончательный ответ.

**Шаг 2: Резолвер → Корневой сервер (итеративный)**

```
Резолвер → a.root-servers.net
Запрос: "Где example.com?"
Ответ: "Спроси у TLD для .com: a.gtld-servers.net (192.5.6.30)"
```

Корневой сервер не знает ответа, но возвращает ссылку на TLD-сервер.

**Шаг 3: Резолвер → TLD-сервер (итеративный)**

```
Резолвер → a.gtld-servers.net
Запрос: "Где example.com?"
Ответ: "Спроси у ns1.example.com (93.184.216.34)"
```

TLD-сервер возвращает адрес авторитетного сервера зоны.

**Шаг 4: Резолвер → Авторитетный сервер (итеративный)**

```
Резолвер → ns1.example.com
Запрос: "Где example.com?"
Ответ: "example.com = 93.184.216.34" (AA=1)
```

Авторитетный сервер возвращает окончательный ответ с флагом `AA=1`.

**Шаг 5: Резолвер → Клиент (ответ на рекурсивный)**

```
Резолвер → Клиент
Ответ: "example.com = 93.184.216.34"
```

Резолвер кэширует ответ (на время TTL) и возвращает клиенту.

### Диагностика с `dig +trace`

Команда `dig +trace` показывает полный путь итеративных запросов:

```bash
dig +trace example.com

# Вывод (сокращённо):
.   518400  IN  NS  a.root-servers.net.
...
com.  172800  IN  NS  a.gtld-servers.net.
...
example.com.  172800  IN  NS  ns1.example.com.
...
example.com.  3600  IN  A  93.184.216.34
```

### Проверка авторитетности ответа

```bash
# Авторитетный ответ (AA=1)
dig @ns1.example.com example.com
# В заголовке: flags: qr aa rd ra

# Неавторитетный ответ из кэша (AA=0)
dig @8.8.8.8 example.com
# В заголовке: flags: qr rd ra (без aa)
```

### Влияние TTL на кэширование

```bash
# Проверка TTL записи
dig +noall +answer +ttlid example.com
; example.com.    3600    IN    A    93.184.216.34
```

TTL=3600 означает, что резолвер будет кэшировать запись 1 час.

## Дополнительная информация

- **Корневые серверы:** 13 кластеров (a.root-servers.net – m.root-servers.net)
- **Время разрешения:** Обычно 20–100 мс (без учёта кэша)
- **Кэширование:** Резолверы кэшируют ответы на время TTL
- **RFC 1035** — базовая спецификация DNS
- **См. также:** [Формат DNS-сообщения](./dns_message_format.md)
