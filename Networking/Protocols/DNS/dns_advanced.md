# Продвинутые сценарии использования DNS

## Определения

**Anycast** — метод сетевой адресации и маршрутизации, при котором один и тот же IP-адрес назначен нескольким физическим серверам в разных точках сети. Запросы автоматически направляются к топологически ближайшему узлу.

**Geo-DNS (Географический DNS)** — технология управления трафиком, позволяющая возвращать разные IP-адреса для одного доменного имени в зависимости от географического положения (IP-адреса) клиента.

**CDN (Content Delivery Network)** — географически распределённая сетевая инфраструктура, предназначенная для оптимизации доставки контента пользователям.

**Split-horizon DNS (Split DNS)** — конфигурация DNS-сервера, при которой он выдаёт разные наборы данных (обычно разные IP для одних и тех же имен) в зависимости от источника запроса.

## Базовые концепции

### Anycast в DNS

Anycast является фундаментом для работы современных глобальных DNS-резолверов и корневых серверов.

* **Принцип работы:** Один IP (например, `8.8.8.8`) анонсируется через протокол BGP из множества точек присутствия (PoP) по всему миру. Маршрутизаторы выбирают кратчайший путь к ближайшему анонсу.
* **Преимущества:**
  * **Снижение задержки:** Пользователь автоматически попадает на географически ближайшую копию сервера за считанные миллисекунды.
  * **Масштабируемость:** Нагрузка размывается между всеми узлами Anycast-группы.
  * **Отказоустойчивость:** Если один узел выходит из строя, BGP перестаёт анонсировать маршрут через него, и трафик автоматически перенаправляется в следующую ближайшую точку. Пользователь этого не замечает.
  * **Защита от DDoS:** Атака локализуется в пределах ближайших к источнику узлов, не позволяя "уронить" весь сервис целиком.
* **Примеры:** Корневые серверы (A-M), Cloudflare (`1.1.1.1`), Google Public DNS (`8.8.8.8`).

### Geo-DNS и балансировка (Geo Steering)

Geo-DNS работает на уровне приложения (DNS-сервера), в отличие от Anycast, который работает на уровне сети (маршрутизации).

* **Принцип работы:** Авторитативный DNS-сервер выступает как точка принятия решения. Он анализирует IP-адрес запроса и возвращает разные записи (разные IP-адреса) разным пользователям в зависимости от их географии.
* **Сравнение с Anycast:**
    * **Geo-DNS:** Отдаёт разные адреса; решение на уровне DNS-ответа.
    * **Anycast:** Держит один адрес; решение на уровне маршрутизации BGP.
* **Применение:** Направление пользователей на региональные CDN-ноды или зеркала сайтов.
* **Техническая проблема:** Авторитативный сервер видит IP-адрес резолвера, а не самого клиента. Если клиент использует публичный резолвер в другом регионе (например, в Сингапуре), он может получить адрес "сингапурского" сервера, находясь во Вьетнаме.

### EDNS Client Subnet (ECS)

Расширение (RFC 7871), решающее проблему точности Geo-DNS при использовании публичных резолверов.

* **Механизм:** Резолвер добавляет в DNS-запрос часть IP-адреса клиента (обычно первые три октета). Это позволяет авторитативному серверу "увидеть" подсеть клиента и подобрать ближайшую к нему точку.
* **Компромисс (Скорость vs Приватность):** 
    * ECS раскрывает часть сетевого адреса пользователя сторонним серверам.
    * Из соображений приватности некоторые резолверы (например, Cloudflare) принципиально не передают ECS.
* **Практические последствия:** Из-за отсутствия ECS могут возникать конфликты. Например, сервис `archive.today` намеренно блокирует запросы от резолвера Cloudflare, так как без ECS не может корректно определить локацию пользователя для предоставления контента.

### Split-horizon DNS

Используется для разделения внутреннего и внешнего сетевого пространства организации.

* **Назначение:** Позволяет внутренним клиентам получать локальные IP-адреса ресурсов (например, `10.0.0.5`), минуя внешние шлюзы и NAT, в то время как внешние клиенты получают публичный IP.
* **Реализация:** В BIND реализуется через механизмы `Views` и `ACL`. Подробнее: [Настройка Views в BIND](../../../Linux/Networking/Services/BIND/advanced_topics.md#1-split-horizon-dns-разделение-внутреннего-и-внешнего-dns).
* **Риски:** Возможна рассинхронизация записей между внутренней и внешней зонами, что затрудняет отладку.

### Интеграция DNS и CDN

CDN активно использует DNS для управления трафиком (Global Server Load Balancing — GSLB).

* **Сценарий с CNAME:**
  1. Клиент запрашивает `static.example.com`.
  2. DNS возвращает `CNAME` на `example.cdnprovider.net`.
  3. DNS-сервер CDN-провайдера, используя Anycast или Geo-DNS, возвращает IP-адрес ближайшего кэш-сервера.
* **Преимущества:** Гибкость управления трафиком без необходимости менять записи в основной зоне при изменении инфраструктуры провайдера.

## Практические сценарии

### Бесшовная миграция сервиса (Управление TTL)

Для смены IP-адреса сервиса с минимальным временем простоя используется стратегия постепенного снижения TTL (Time To Live).

| Этап | Действие | Рекомендуемое время |
| :--- | :--- | :--- |
| **Подготовка** | Снизить TTL записи (например, с 86400 до 300 сек) | За 24–48 часов до миграции |
| **Переключение** | Изменить IP-адрес в A-записи | В момент миграции |
| **Проверка** | Мониторинг логов нового сервера и остаточного трафика на старом | 1–2 часа после переключения |
| **Завершение** | Вернуть TTL к исходному значению (86400 сек) | Через 24 часа после миграции |

### Проверка Split-horizon DNS с клиента

Для диагностики проблем разрешения имен в сетях со Split DNS используются различные инструменты.

1. **Проверка через системный резолвер (NSS/glibc):**

   ```bash
   getent ahosts example.com
   ```

   Показывает, какой IP видит ОС с учетом `/etc/hosts` и системного кэша.

2. **Проверка через локальный резолвер (systemd-resolved):**

   ```bash
   resolvectl query example.com
   ```

3. **Прямой опрос конкретного DNS-сервера:**

   ```bash
   # Опрос внутреннего сервера напрямую
   dig @10.0.0.1 example.com
   ```

   Позволяет убедиться, что конкретный view отдаёт ожидаемые данные.
