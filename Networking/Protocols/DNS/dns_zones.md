# Зоны DNS и SOA-запись

## Определения

**Зона DNS (DNS Zone)** — логическая часть пространства доменных имён, за которую отвечает конкретный DNS-сервер (или группа серверов). Зона представляет собой административную границу внутри иерархии DNS.

**Прямая зона (Forward Zone)** — преобразует доменные имена в IP-адреса (записи типа A, AAAA).

**Обратная зона (Reverse Zone)** — преобразует IP-адреса в доменные имена (записи типа PTR). Использует специальный домен `in-addr.arpa` для IPv4 и `ip6.arpa` для IPv6.

**SOA-запись (Start of Authority)** — обязательная ресурсная запись, которая находится в начале каждого файла зоны. Она содержит метаданные о зоне и параметры её синхронизации между серверами. Подробнее: [Типы DNS-записей](./dns_records.md).

## Базовые концепции

### Типы зон по назначению

| Тип | Назначение | Пример |
| :--- | :--- | :--- |
| **Прямая** | Разрешение имён в IP | `example.com` → `93.184.216.34` |
| **Обратная** | Обратное разрешение (IP → имя) | `34.216.184.93.in-addr.arpa` → `example.com` |
| **Делегированная** | Подзона, управление которой передано другим NS | `sub.example.com` → `ns1.other-provider.net` |

### Роли DNS-серверов в контексте зон

1. **Master (Primary):** основной сервер, содержащий эталонный файл зоны. Все изменения вносятся только на этом сервере.
2. **Secondary (Slave):** вторичный сервер, получающий копию зоны от Master-сервера через механизм зонной передачи. Обеспечивает отказоустойчивость.
3. **Stealth Master:** Master-сервер, который не указан в NS-записях зоны. Используется для повышения безопасности — изменения вносятся на нём, а публичные Secondary-серверы забирают данные.

Подробности реализации на BIND: [Master-сервер](../../../Linux/Networking/Services/BIND/master_server_local_zone.md).

### Механизм делегирования и Glue-записи

Делегирование — это передача ответственности за часть доменного дерева другому набору серверов имён.

**Glue-записи (склеивающие записи)** необходимы, когда NS-сервер подзоны находится внутри самой этой подзоны. Без них возникает циклическая зависимость: чтобы найти адрес `ns1.sub.example.com`, нужно опросить сервер `ns1.sub.example.com`.

*Решение:* Родительская зона (`example.com`) передаёт не только NS-записи подзоны, но и их IP-адреса (A/AAAA) в секции `ADDITIONAL` ответа.

| Ситуация | Нужны ли Glue-записи |
| :--- | :--- |
| NS-сервер `ns1.sub.test.ru` обслуживает зону `sub.test.ru` | **Да** |
| NS-сервер `ns1.external.com` обслуживает зону `sub.test.ru` | **Нет** |

### Делегирование (NS) vs Псевдоним (CNAME)

| Характеристика | Делегирование (NS) | Псевдоним (CNAME) |
| :--- | :--- | :--- |
| **Область действия** | Вся подзона и всё, что под ней | Одно конкретное имя (хост) |
| **Управление** | Передаётся другим серверам | Остаётся в текущей зоне |
| **Пример** | `shop.ru. NS ns1.provider.ru.` | `www.shop.ru. CNAME shop.ru.` |

## Практические сценарии

### Структура и параметры SOA-записи

Запись SOA определяет политику обновления зоны. Пример формата BIND:

```dns
@   IN  SOA    ns1.example.com. admin.example.com. (
    2024060601  ; Serial (YYYYMMDDNN)
    7200        ; Refresh (интервал проверки обновлений)
    3600        ; Retry (повтор при неудаче)
    1209600     ; Expire (срок годности данных без Master)
    3600        ; Negative TTL (кэширование NXDOMAIN)
)
```

| Поле | Назначение | Рекомендации |
| :--- | :--- | :--- |
| **Master NS** | Имя первичного сервера зоны | Должно разрешаться в IP |
| **Admin Email** | Email администратора (`@` заменяется на `.`) | `admin.example.com.` |
| **Serial** | Номер версии зоны | Увеличивать при каждом изменении |
| **Refresh** | Как часто Secondary проверяет Serial на Master | 2–24 часа |
| **Retry** | Как скоро повторить попытку при сбое связи | 15–60 минут |
| **Expire** | Через сколько времени Secondary перестанет отвечать, если Master недоступен | 1–4 недели |
| **Negative TTL** | Время кэширования ответов "домен не найден" | 1–3 часа |

### Синхронизация зон (Зонная передача)

Синхронизация между Master и Secondary происходит по протоколу TCP/53:

1. **AXFR (Full Zone Transfer):** полная передача всех записей зоны. Используется при первой синхронизации или если Serial значительно изменился.
2. **IXFR (Incremental Zone Transfer):** передача только изменённых записей. Экономит трафик (RFC 1995).
3. **NOTIFY:** механизм, при котором Master немедленно уведомляет Secondary об изменении Serial, не дожидаясь наступления интервала `Refresh` (RFC 1996).

### Диагностика зон

```bash
# Проверка SOA-записи и серийного номера
dig example.com SOA

# Проверка списка NS-серверов
dig example.com NS

# Проверка обратной записи (PTR)
dig -x 93.184.216.34

# Попытка запроса полной зоны (AXFR) — обычно закрыта в целях безопасности
dig @ns1.example.com example.com AXFR
```

Подробнее об утилитах: [Диагностика DNS](../../../Linux/Diagnostics/Networking/dns/overview.md).

## Дополнительная информация

- **Reverse DNS:** Настройка PTR-записей обычно выполняется на стороне провайдера, выделившего IP-адрес.
- **Минимум 2 NS:** Стандарт RFC 1034 требует наличия как минимум двух независимых NS-серверов для каждой зоны.
- **Lame Delegation:** Ситуация, когда NS-запись указывает на сервер, который не является авторитетным для данной зоны (ошибка конфигурации).
