# Зоны DNS и запись SOA

## Определения

**Зона DNS** — управляемая часть пространства доменных имён, за которую отвечает конкретный DNS-сервер (или группа серверов).

**Прямая зона (Forward Zone)** — сопоставляет доменные имена → IP-адреса (A, AAAA).

**Обратная зона (Reverse Zone)** — сопоставляет IP-адреса → доменные имена (PTR). Использует зону `in-addr.arpa`.

**SOA (Start of Authority)** — обязательная запись в начале каждой зоны, определяющая основные параметры и правила синхронизации.

## Базовые концепции

### Типы зон

| Тип | Назначение | Пример |
|-----|------------|--------|
| **Прямая** | Разрешение имён в IP | `example.com` → `93.184.216.34` |
| **Обратная** | Обратное разрешение (IP → имя) | `34.216.184.93.in-addr.arpa` → `example.com` |
| **Делегированная** | Подзона, переданная другим NS | `sub.example.com` → другие NS |

### Делегирование зон

**Делегирование зоны** — передача полномочий по управлению поддоном другому набору NS-серверов. Родительская зона хранит только NS-записи, указывающие на авторитативные серверы подзоны.

#### Механизм делегирования

Делегирование происходит через NS-записи в родительской зоне:

```
example.com.       NS   ns1.example.com.
example.com.       NS   ns2.example.com.

sub.example.com.   NS   ns1.sub.example.com.   ; Делегирование подзоны
sub.example.com.   NS   ns2.sub.example.com.
```

#### Glue-записи (A/AAAA для NS)

Если NS-сервер делегированной зоны находится **внутри самой делегируемой зоны**, возникает циклическая зависимость: для разрешения `ns1.sub.example.com` нужно знать IP, но IP хранится в зоне `sub.example.com`, которую ещё некуда запросить.

Решение — **Glue-записи**: родительская зона хранит A/AAAA-записи NS-серверов делегированной зоны в секции ADDITIONAL ответа.

```
sub.example.com.       NS     ns1.sub.example.com.
ns1.sub.example.com.   A      203.0.113.10    ; Glue-запись
ns2.sub.example.com.   A      203.0.113.11    ; Glue-запись
```

**Когда нужны Glue-записи:**

| Ситуация | Glue нужен? | Пример |
|----------|-------------|--------|
| NS внутри делегируемой зоны | Да | `ns1.sub.example.com` в зоне `sub.example.com` |
| NS вне делегируемой зоны | Нет | `ns1.cloudprovider.com` в зоне `sub.example.com` |

#### Алгоритм разрешения при делегировании

Запрос `host.sub.example.com` через рекурсивный резолвер:

1. Резолвер запрашивает корневые серверы → получает NS для `.com`
2. Запрашивает `.com` → получает NS для `example.com`
3. Запрашивает `example.com` → получает **делегирование**: NS для `sub.example.com` + Glue (IP)
4. Запрашивает NS `sub.example.com` напрямую → получает A-запись `host.sub.example.com`

Резолвер **не возвращается** к родительской зоне для запросов внутри подзоны — все запросы идут напрямую к делегированным NS.

#### Делегирование vs CNAME

| Параметр | Делегирование (NS) | CNAME |
|----------|-------------------|-------|
| **Что делает** | Передаёт управление поддоном другим NS | Алиас одного имени на другое |
| **Кто управляет записями** | Владелец делегированных NS | Владелец исходной зоны |
| **Уровень** | Вся подзона (`sub.example.com` и все вложенные) | Одно конкретное имя |
| **Пример** | `sub.example.com NS ns1.external.com` | `www.example.com CNAME cdn.provider.net` |

**Нельзя** использовать CNAME для делегирования управления зоной — CNAME только перенаправляет запрос, но не передаёт полномочия.

#### Типы делегирования

| Тип | Описание | Пример использования |
|-----|----------|---------------------|
| **Публичное** | NS-записи в родительской зоне через регистратора | Делегирование `example.com` на NS хостинг-провайдера |
| **Внутреннее** | NS-записи внутри корпоративной зоны | Делегирование `dev.corp.local` на внутренние DNS-серверы команды разработки |
| **Частичное (Stealth)** | Подзона обслуживается серверами, не указанными в NS родительской зоны | Тестовый DNS-сервер, невидимый извне |

### Роли серверов

| Роль | Описание | Права |
|------|----------|-------|
| **Master (Primary)** | Основной сервер зоны | Чтение/запись |
| **Secondary (Slave)** | Вторичный сервер (реплика) | Только чтение |
| **Stealth** | Скрытый master (не в NS) | Чтение/запись |

**Требование:** Минимум 2 NS-сервера для отказоустойчивости (RFC 1034).

## Практические сценарии

### Структура SOA-записи (BIND)

```dns
$TTL 86400
@   IN  SOA    ns1.example.com. admin.example.com. (
    2024010101  ; Serial (YYYYMMDDNN)
    7200        ; Refresh (2 часа)
    3600        ; Retry (1 час)
    1209600     ; Expire (2 недели)
    3600        ; Negative TTL (1 час)
)
```

### Поля SOA-записи

| Поле | Описание | Рекомендуемое значение |
|------|----------|------------------------|
| **Master** | Основной DNS-сервер зоны | `ns1.example.com.` |
| **Admin** | Email администратора (`@` → `.`) | `admin.example.com.` |
| **Serial** | Версия зоны (увеличивать при изменениях) | `YYYYMMDDNN` |
| **Refresh** | Интервал проверки обновлений (сек) | 7200 (2 часа) |
| **Retry** | Интервал повторной попытки при ошибке | 3600 (1 час) |
| **Expire** | Макс. время работы без связи с master | 1209600 (2 недели) |
| **Negative TTL** | Кэширование ошибок (NXDOMAIN) | 3600 (1 час) |

### Настройка обратной зоны

Для IP `93.184.216.34` создаётся обратная зона:

```dns
; Зона: 216.184.93.in-addr.arpa
34  IN  PTR  example.com.
```

**Важно:** PTR-записи настраиваются у владельца IP (хостинг, провайдер), не у регистратора домена.

### Синхронизация Master → Secondary

**Процесс:**

1. Secondary запрашивает SOA у Master каждые `Refresh` секунд
2. Сравнивает серийный номер
3. Если Serial > локального → выполняет зонную передачу (AXFR)
4. Зона обновляется

**Пример настройки BIND:**

```conf
// Master
zone "example.com" {
    type master;
    file "/etc/bind/zones/example.com.zone";
    allow-transfer { 192.168.1.2; };  // IP Secondary
};

// Secondary
zone "example.com" {
    type slave;
    file "/etc/bind/zones/example.com.zone";
    masters { 192.168.1.1; };  // IP Master
};
```

### Диагностика зон

```bash
# Проверка SOA-записи
dig example.com SOA

# Проверка NS-серверов
dig example.com NS

# Проверка обратной зоны
dig -x 93.184.216.34

# Зонная передача (если разрешена)
dig @ns1.example.com example.com AXFR
```

## Дополнительная информация

- **Формат Serial:** `YYYYMMDDNN` (дата + номер изменения за день)
- **Зонная передача:** AXFR (полная), IXFR (инкрементальная)
- **RFC 1035** — базовая спецификация зон
- **RFC 1996** — уведомление об изменениях (NOTIFY)
- **Минимум 2 NS:** Требуется регистраторами для делегирования
