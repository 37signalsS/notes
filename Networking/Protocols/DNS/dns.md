# Протокол DNS (Domain Name System)

## Определения

**DNS (Domain Name System — система доменных имён)** — иерархическая распределённая база данных для преобразования человекочитаемых доменных имён в IP-адреса и обратно.

*   **Резолвер (Resolver):** программный компонент, выполняющий процесс разрешения имени.
    *   **Stub Resolver (Заглушка):** минимальная библиотека на стороне клиента (например, `getaddrinfo` в `glibc`), которая только передаёт запрос рекурсивному серверу.
    *   **Recursive Resolver (Рекурсивный резолвер):** сервер, который выполняет всю цепочку запросов от корня до авторитетного сервера от имени клиента.
    *   **Forwarding Resolver (Пересылающий резолвер):** посредник, который перенаправляет запросы другому рекурсивному серверу (часто используется в домашних роутерах).
*   **Ресурсная запись (Resource Record, RR):** базовая единица данных в DNS (A, MX, CNAME и др.).
*   **Авторитетный ответ (Authoritative Answer):** ответ от сервера, владеющего зоной (флаг `AA` в заголовке).
*   **Неавторитетный ответ (Non-Authoritative Answer):** ответ, извлечённый из кэша промежуточного сервера.
*   **TTL (Time To Live):** время актуальности записи в кэше (в секундах).
*   **RCODE (Response Code):** код результата выполнения запроса (например, `NOERROR`, `NXDOMAIN`).

## Базовые концепции

### Роли серверов

*   **Авторитетный сервер (Authoritative DNS Server):** хранит оригинальные файлы зон и несёт ответственность за точность данных в них. Бывает первичным (Master/Primary) и вторичным (Slave/Secondary).
*   **Рекурсивный резолвер (Recursive DNS Resolver):** "интеллектуальный" посредник, который кэширует ответы для ускорения последующих запросов и выполняет итеративный поиск.

### Транспортные протоколы и порты

Традиционно DNS работает на порту **53 (UDP/TCP)**, но современные стандарты (2022–2025) значительно расширяют этот список:

*   **UDP/53:** основной транспорт для быстрых и коротких запросов. Рекомендуется ограничение размера пакета в **1232 байта** для предотвращения IP-фрагментации (RFC 9715).
*   **TCP/53:** используется при превышении лимита размера UDP-пакета (флаг `TC` — Truncated) и для трансфера зон (AXFR/IXFR).
*   **DoT (DNS over TLS) — Порт 853:** шифрование DNS-трафика поверх TCP. Обеспечивает строгую приватность между клиентом и резолвером.
*   **DoH (DNS over HTTPS) — Порт 443:** инкапсуляция DNS-запросов в HTTPS-трафик. Позволяет обходить блокировки на уровне протокола и использовать HTTP-возможности (например, кэширование и приоритизация).
*   **ODoH (Oblivious DoH) — RFC 9230:** расширение DoH, скрывающее IP-адрес клиента от резолвера через промежуточное прокси-звено.
*   **DoQ (DNS over QUIC) — Порт 853 (или 784):** современный стандарт (RFC 9250), обеспечивающий шифрование и устраняющий проблему блокировки начала очереди (Head-of-Line blocking) благодаря UDP/QUIC.

### Расширения протокола (EDNS)

**EDNS0 (Extension Mechanisms for DNS, RFC 6891)** — механизм обратной совместимости для добавления новых полей (например, расширенного RCODE) и флагов в DNS-пакет.
*   Позволяет увеличить размер UDP-пакета свыше классических 512 байт.
*   Добавляет поддержку **ECS (EDNS Client Subnet)** — передача части IP-адреса клиента авторитетному серверу для более точного Geo-DNS (RFC 7871).
*   **DNS Cookies (RFC 7873):** защита от атак типа DNS-амплификации и подмены пакетов.

### Иерархия и структура

Система организована в виде перевёрнутого дерева:
1.  **Корень (`.`):** управляется 13 группами корневых серверов (Root Servers).
2.  **TLD (Top-Level Domain):** домены верхнего уровня (`.com`, `.ru`, `.org`). Делятся на gTLD (общие) и ccTLD (национальные).
3.  **SLD (Second-Level Domain):** домены второго уровня (`google.com`, `yandex.ru`).

Подробности и роль ICANN: [Основные концепции DNS](./dns_concepts.md).

### Механизмы оптимизации и приватности

*   **QNAME Minimization (RFC 7816):** резолвер отправляет только ту часть имени, которая необходима на текущем этапе (например, при запросе к Root серверу спрашивается только `.com`, а не `www.example.com`). Снижает утечку данных.
*   **Негативное кэширование (RFC 2308):** сохранение информации об отсутствии записи (`NXDOMAIN`) или отсутствии типа (`NODATA`) на определённое время. Уменьшает нагрузку на серверы при повторных запросах к несуществующим именам.
*   **Локальное кэширование:** использование TTL для хранения ответов. Современные системы часто используют агрессивное кэширование (RFC 8198) для защиты от DNS-флуда.

### Формат сообщения и типы записей

DNS-пакет состоит из заголовка (Header), секции запроса (Question) и секций ответов (Answer, Authority, Additional).
*   [Формат DNS-сообщения](./dns_message_format.md) — структура, флаги (RD, RA, AA, TC) и опции.
*   [Типы DNS-записей](./dns_records.md) — обзор A, AAAA, MX, CNAME, SRV, TXT (SPF/DKIM).
*   **Современные записи (RFC 9460):**
    *   **HTTPS (тип 65):** позволяет браузеру узнать о поддержке HTTP/3 и ECH (Encrypted Client Hello) до начала TLS-соединения.
    *   **SVCB (Service Binding, тип 64):** универсальный механизм для привязки сервисов к домену, поддерживающий Apex-домены (альтернатива CNAME).

### Процесс разрешения имён

Включает итеративные и рекурсивные обращения. Резолвер последовательно опрашивает Root → TLD → Authoritative сервера для получения окончательного ответа.
Детальный разбор процесса: [Процесс разрешения имён в DNS](./dns_resolution.md).

### Коды ответов (RCODE)

Понимание кодов ответов критично для диагностики:
*   **NOERROR (0):** запрос успешно выполнен.
*   **FORMERR (1):** ошибка формата запроса.
*   **SERVFAIL (2):** сервер не смог обработать запрос из-за внутренней ошибки или проблем с вышестоящими серверами.
*   **NXDOMAIN (3):** запрашиваемое доменное имя не существует.
*   **REFUSED (5):** сервер отказался выполнять запрос (например, из-за настроек ACL).

### Настройка DNS-клиента в ОС

В Linux конфигурация управляется через `/etc/resolv.conf`, `/etc/hosts` и системные службы.
Подробности: [DNS-клиент в Linux](../../../Linux/Networking/Concepts/dns_client.md).

### Диагностика протокола

Основные инструменты для проверки и отладки:
*   `dig` — промышленный стандарт для глубокого анализа ответов и флагов.
*   `resolvectl` — утилита для взаимодействия с `systemd-resolved` в современных дистрибутивах Linux.
*   `nslookup` / `host` — простые утилиты для быстрой проверки разрешения имён.

#### Пример вывода `dig` и расшифровка
```bash
dig example.com
# →
# ;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12345
# ;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
```
*   **qr (Query Response):** ответ на запрос.
*   **rd (Recursion Desired):** клиент просит рекурсию (режим "сделай всё за меня").
*   **ra (Recursion Available):** сервер подтверждает, что поддерживает рекурсию.
*   **aa (Authoritative Answer):** ответ получен напрямую от владельца зоны (не из кэша).
*   **tc (Truncated):** пакет был обрезан, требуется переход на TCP.

Примеры использования: [Диагностика DNS](../../../Linux/Diagnostics/Networking/dns/overview.md).

    *   **RFC 9460 (SVCB/HTTPS):** новые типы записей для HTTP/3 и ECH.
    *   **RFC 9715 (IP Fragmentation):** рекомендации по размеру пакетов (1232 байта).
