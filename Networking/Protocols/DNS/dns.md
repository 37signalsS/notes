# Протокол DNS (Domain Name System)

## Определения

**DNS (Domain Name System — система доменных имён)** — иерархическая распределённая база данных для преобразования человекочитаемых доменных имён в IP-адреса и обратно. Является фундаментальным протоколом прикладного уровня (L7), без которого невозможно функционирование HTTP, SMTP, SIP и большинства других интернет-протоколов.

*   **FQDN (Fully Qualified Domain Name):** полное доменное имя, однозначно определяющее узел в иерархии DNS. Заканчивается точкой, указывающей на корень (например, `www.example.com.`). В пользовательских интерфейсах точка часто опускается, но протокольно она обязательна.
*   **Резолвер (Resolver):** программный компонент, выполняющий процесс разрешения имени.
    *   **Stub Resolver (Заглушка):** минимальная библиотека на стороне клиента (например, `getaddrinfo` в `glibc`), которая только передаёт запрос рекурсивному серверу. Не выполняет итеративный поиск самостоятельно.
    *   **Recursive Resolver (Рекурсивный резолвер):** сервер, который выполняет всю цепочку запросов от корня до авторитетного сервера от имени клиента. Кэширует ответы и выполняет итеративный поиск по иерархии.
    *   **Forwarding Resolver (Пересылающий резолвер):** посредник, который перенаправляет запросы другому рекурсивному серверу. Часто используется в домашних роутерах и корпоративных сетях для централизованного управления DNS-трафиком.
    *   **Caching-only Resolver:** сервер, который не является авторитетным ни за одну зону и не выполняет зонные передачи. Его единственная роль — кэширование ответов от других серверов для ускорения последующих запросов.
*   **Ресурсная запись (Resource Record, RR):** базовая единица данных в DNS (A, MX, CNAME и др.). Каждая запись состоит из имени (NAME), типа (TYPE), класса (CLASS), TTL и данных (RDATA). Подробнее: [Типы DNS-записей](./dns_records.md).
*   **Зона DNS (DNS Zone):** административная граница пространства имён, за которую отвечает конкретный сервер. Не следует путать с доменом — один домен может быть разбит на несколько зон. Подробнее: [Зоны DNS и SOA-запись](./dns_zones.md).
*   **Делегирование (Delegation):** передача управления поддоменом другому набору NS-серверов. Реализуется через NS-записи в родительской зоне.
*   **Glue Records (Склеивающие записи):** A или AAAA-записи, предоставляемые вместе с NS-записью для предотвращения циклической зависимости. Необходимы, если сервер имён находится внутри делегируемой зоны (например, `ns1.example.com` для зоны `example.com`).
*   **Авторитетный ответ (Authoritative Answer):** ответ от сервера, владеющего зоной (флаг `AA` в заголовке). Считается наиболее достоверным.
*   **Неавторитетный ответ (Non-Authoritative Answer):** ответ, извлечённый из кэша промежуточного рекурсивного сервера. Не гарантирует актуальности данных сверх TTL.
*   **TTL (Time To Live):** время актуальности записи в кэше (в секундах). Определяется владельцем зоны. После истечения TTL запись считается устаревшей и должна быть запрошена заново.
*   **RCODE (Response Code):** код результата выполнения запроса (например, `NOERROR`, `NXDOMAIN`). Располагается в заголовке DNS-ответа.
*   **Registrar (Регистратор):** организация, аккредитованная ICANN (или национальным регистратором), через которую можно зарегистрировать доменное имя. Регистратор вносит делегирующие NS-записи в родительскую зону TLD.
*   **Registry (Реестр):** оператор зоны верхнего уровня (TLD). Хранит авторитетные данные о делегировании доменов в своей зоне (NS-записи и DS-записи для DNSSEC). Например, Verisign управляет зонами `.com` и `.net`.

## Базовые концепции

### Роли серверов

*   **Авторитетный сервер (Authoritative DNS Server):** хранит оригинальные файлы зон и несёт ответственность за точность данных в них. Бывает первичным (Primary) и вторичным (Secondary). Подробнее об архитектуре Master/Slave: [Зоны DNS и SOA-запись](./dns_zones.md).
    *   **Primary (Первичный):** источник истины. Все изменения вносятся только здесь (ручные или через динамические обновления RFC 2136).
    *   **Secondary (Вторичный):** получает копию зоны через зонную передачу (AXFR/IXFR) по TCP/53. Обеспечивает отказоустойчивость и балансировку нагрузки.
    *   **Hidden Primary (Скрытый первичный):** сервер, не указанный в публичных NS-записях. Используется для повышения безопасности, взаимодействуя только с доверенными вторичными серверами.
*   **Рекурсивный резолвер (Recursive DNS Resolver):** «интеллектуальный» посредник, который кэширует ответы для ускорения последующих запросов и выполняет итеративный поиск по иерархии DNS. Публичные рекурсивные серверы (8.8.8.8, 1.1.1.1, 9.9.9.9) обслуживают миллионы пользователей.
*   **Корневой сервер (Root Server):** сервер верхнего уровня иерархии (символ `.`). Существует 13 логических адресов (A–M), за которыми стоят более 2000 физических площадок по всему миру, использующих Anycast для маршрутизации к ближайшему узлу.

### Транспортные протоколы и порты

Традиционно DNS работает на порту **53 (UDP/TCP)**, но современные стандарты значительно расширяют этот список:

| Протокол | Порт | Транспорт | Назначение | RFC |
| :--- | :--- | :--- | :--- | :--- |
| **DNS (классический)** | 53 | UDP / TCP | Основной транспорт. UDP — для быстрых запросов (до 1232 байт), TCP — для трансферов зон и больших ответов. | RFC 1035 |
| **DoT (DNS over TLS)** | 853 | TCP + TLS | Шифрование DNS-трафика. Строгая приватность между клиентом и резолвером. | RFC 7858 |
| **DoH (DNS over HTTPS)** | 443 | TCP + HTTPS | Инкапсуляция DNS в HTTPS-трафик. Позволяет обходить блокировки и использовать HTTP-возможности (кэширование, приоритизация). | RFC 8484 |
| **ODoH (Oblivious DoH)** | 443 | TCP + HTTPS + Proxy | Расширение DoH, скрывающее IP-адрес клиента от резолвера через промежуточное прокси-звено. | RFC 9230 |
| **DoQ (DNS over QUIC)** | 853 / 784 | UDP + QUIC | Современный стандарт. Шифрование + устранение Head-of-Line blocking + 0-RTT установка соединения. | RFC 9250 |

**Почему UDP首选 для DNS:**
*   Минимальный заголовок (8 байт vs 20+ байт у TCP).
*   Не требуется установка соединения (handshake), что снижает задержку на один RTT.
*   DNS-запрос и ответ помещаются в один дейтаграмму (при размере до 1232 байт по рекомендации RFC 9715).

**Когда нужен TCP:**
*   Ответ превышает лимит UDP (флаг `TC` — Truncated в заголовке).
*   Зонные передачи (AXFR/IXFR) — всегда по TCP.
*   DNSSEC-подписи могут увеличивать размер ответа свыше 1232 байт.

### Расширения протокола (EDNS)

**EDNS0 (Extension Mechanisms for DNS, RFC 6891)** — механизм обратной совместимости для добавления новых полей и флагов в DNS-пакет без нарушения работы старых серверов.

Реализуется через псевдо-запись **OPT** в секции Additional:
*   Позволяет увеличить размер UDP-пакета свыше классических 512 байт (до 4096 байт, рекомендуется 1232 для предотвращения фрагментации).
*   Добавляет поддержку расширенных RCODE (биты EXTENDED-RCODE в заголовке OPT).
*   **ECS (EDNS Client Subnet, RFC 7871):** передача части IP-адреса клиента авторитетному серверу для более точного Geo-DNS. Позволяет CDN направлять пользователя на ближайший узел даже при использовании публичных резолверов. Имеет ограничения приватности — раскрывает подсеть сторонним серверам.
*   **DNS Cookies (RFC 7873):** защита от атак типа DNS-амплификации и подмены пакетов. Клиент и сервер обмениваются 64-битными токенами, что позволяет отсеивать поддельные запросы.

### Иерархия и структура

Система организована в виде перевёрнутого дерева:
1.  **Корень (`.`):** управляется 13 группами корневых серверов (Root Servers). Организация ICANN координирует управление корневой зоной. Подробнее: [Основные концепции DNS](./dns_concepts.md).
2.  **TLD (Top-Level Domain):** домены верхнего уровня (`.com`, `.ru`, `.org`). Делятся на gTLD (общие) и ccTLD (национальные). Управляются реестрами (Registry), например Verisign для `.com`.
3.  **SLD (Second-Level Domain):** домены второго уровня (`google.com`, `yandex.ru`). Регистрируются через регистраторов (Registrar).
4.  **Поддомены (Subdomains):** ветки иерархии, создаваемые владельцем SLD (`api.example.com`, `stage.api.example.com`).

**Жизненный цикл доменного имени:** регистрация через Registrar → делегирование NS-записей в TLD → настройка авторитетных серверов → эксплуатация → истечение срока → период Grace Period (удержание) → Redemption Period (восстановление за плату) → удаление и освобождение имени.

### Механизмы оптимизации и приватности

*   **QNAME Minimization (RFC 7816):** резолвер отправляет только ту часть имени, которая необходима на текущем этапе (например, при запросе к Root серверу спрашивается только `.com`, а не `www.example.com`). Снижает утечку данных о полном имени пользователя на каждом уровне иерархии.
*   **Негативное кэширование (RFC 2308):** сохранение информации об отсутствии записи (`NXDOMAIN`) или отсутствии типа (`NODATA`) на время, указанное в поле Minimum TTL записи SOA. Уменьшает нагрузку на серверы при повторных запросах к несуществующим именам и защищает от «DNS-штормов».
*   **Локальное кэширование:** использование TTL для хранения ответов на нескольких уровнях: браузер, ОС (systemd-resolved), локальный DNS-сервер. Современные системы используют агрессивное кэширование (RFC 8198) для защиты от DNS-флуда.
*   **Happy Eyeballs v2/v3 (RFC 8305):** алгоритм параллельного разрешения A и AAAA записей с небольшим сдвигом (150–300 мс в пользу IPv6) для минимизации задержек при Dual Stack.

### Формат сообщения и типы записей

DNS-пакет состоит из заголовка (Header, 12 байт), секции запроса (Question) и секций ответов (Answer, Authority, Additional). Детальный разбор структуры:
*   [Формат DNS-сообщения](./dns_message_format.md) — структура, флаги (RD, RA, AA, TC), опции EDNS0 и Name Compression.
*   [Типы DNS-записей](./dns_records.md) — обзор A, AAAA, MX, CNAME, NS, PTR, SOA, SRV, TXT (SPF/DKIM/DMARC).

**Краткий обзор основных типов записей:**

| Тип | Назначение | Ключевая особенность |
| :--- | :--- | :--- |
| **A** | IPv4-адрес | Может быть несколько записей для Round Robin DNS. |
| **AAAA** | IPv6-адрес | Используется параллельно с A (Dual Stack). |
| **CNAME** | Псевдоним | Указывает на другое каноническое имя. **Не может** быть на Apex-домене (нарушает RFC из-за наличия NS/SOA). |
| **MX** | Почтовый сервер | Формат: `[priority] [hostname]`. Hostname должен указывать на A/AAAA (CNAME запрещён RFC). |
| **NS** | Сервер имён | Определяет авторитетные серверы для зоны. Используется для делегирования. |
| **TXT** | Произвольный текст | SPF, DKIM, DMARC (защита почты), верификация домена. |
| **SRV** | Сервис | Формат: `_service._proto.name TTL IN SRV priority weight port target`. |
| **PTR** | Обратное разрешение | IP → FQDN. Работает в зонах `in-addr.arpa` (IPv4) и `ip6.arpa` (IPv6). |
| **SOA** | Метаданные зоны | Serial, Refresh, Retry, Expire, Minimum TTL. Обязательная запись в начале каждой зоны. |

**Современные записи (RFC 9460):**
*   **HTTPS (тип 65):** позволяет браузеру узнать о поддержке HTTP/3 и ECH (Encrypted Client Hello) до начала TLS-соединения. Ускоряет установку соединения за счёт Early Data.
*   **SVCB (Service Binding, тип 64):** универсальный механизм для привязки сервисов к домену, поддерживающий Apex-домены (альтернатива CNAME с параметрами ALPN, порта и шифрования).

### Процесс разрешения имён

Включает итеративные и рекурсивные обращения. При пустом кэше процесс выглядит следующим образом:
1.  **Локальная проверка:** система сначала ищет соответствие в `/etc/hosts`. Если имя найдено, запрос во внешнюю сеть не отправляется.
2.  **Stub Resolver → Рекурсивный резолвер (UDP/53, RD=1):** отправляет рекурсивный запрос.
3.  **Резолвер → Root (Итерация 1):** спрашивает корень `.` про `example.com`. Получает реферал на серверы TLD `.com`.
4.  **Резолвер → TLD (Итерация 2):** спрашивает серверы `.com` про `example.com`. Получает реферал на авторитетные серверы владельца.
5.  **Резолвер → Authoritative (Итерация 3):** спрашивает `ns1.example.com`. Получает авторитетный ответ (`AA=1`) с IP-адресом.
6.  **Резолвер → Клиент:** возвращает IP и сохраняет его в кэш согласно TTL.

Детальный разбор процесса: [Процесс разрешения имён в DNS](./dns_resolution.md).

### Коды ответов (RCODE)

Понимание кодов ответов критично для диагностики. Полная таблица основных RCODE:

| Код | Имя | Описание | Типичная причина |
| :--- | :--- | :--- | :--- |
| **0** | NOERROR | Запрос успешно выполнен | Нормальная работа |
| **1** | FORMERR | Ошибка формата запроса | Повреждённый пакет, несовместимый клиент |
| **2** | SERVFAIL | Внутренняя ошибка сервера | Проблемы с вышестоящими серверами, истечение таймаута рекурсии |
| **3** | NXDOMAIN | Имя не существует | Домен не зарегистрирован или удалён |
| **4** | NOTIMP | Функция не поддерживается | Сервер не реализует запрошенную операцию (например, определённый Opcode) |
| **5** | REFUSED | Сервер отказал в обслуживании | ACL блокирует запрос, recursion отключена для данного клиента |
| **6** | YXDOMAIN | Имя существует (при попытке создания) | Используется в динамических обновлениях (RFC 2136) |
| **7** | YXRRSet | RRset существует | Попытка создать запись, которая уже есть (для DNS Update) |
| **8** | NXRRSet | RRset не существует | Попытка удалить несуществующую запись |
| **9** | NOTAUTH | Сервер не авторитетен | Сервер не является авторитетным для запрашиваемой зоны |
| **10** | NOTZONE | Имя не находится в зоне | Имя находится за пределами управляемой зоны |
| **16** | BADVERS / BADSIG | Неверная версия EDNS / неверная подпись | Неподдерживаемая версия EDNS или ошибка DNSSEC-валидации |

**Extended DNS Errors (EDE, RFC 8914):** расширенные коды ошибок, передаваемые в секции OPT. Позволяют серверу уточнить причину отказа (например, «DNSSEC Signature Failed», «Blocked by Response Policy», «Stale Answer»). Особенно полезны для диагностики_SPLIT-horizon DNS и RPZ-политик.

### Настройка DNS-клиента в ОС

В Linux конфигурация управляется через несколько уровней:
1.  **`/etc/nsswitch.conf`** — определяет порядок источников (hosts: files resolve dns).
2.  **`/etc/hosts`** — статические переопределения (полезно для локальной разработки и блокировки).
3.  **`/etc/resolv.conf`** — параметры транспортного слоя (nameserver, search, ndots).
4.  **`/etc/systemd/resolved.conf`** — глобальные настройки кэширования, DoT, DoH, DNSSEC.

Подробности: [DNS-клиент в Linux](../../../Linux/Networking/Concepts/dns_client.md).

### Диагностика протокола

Основные инструменты для проверки и отладки:
*   `dig` — промышленный стандарт для глубокого анализа ответов и флагов.
*   `resolvectl` — утилита для взаимодействия с `systemd-resolved` в современных дистрибутивах Linux.
*   `nslookup` / `host` — простые утилиты для быстрой проверки разрешения имён.
*   `delv` — инструмент для глубокой валидации DNSSEC (проверка цепочки доверия).
*   `getent hosts` — проверка NSS: показывает итоговый результат резолвинга «глазами системы».

Подробная диагностика: [Диагностика DNS](../../../Linux/Diagnostics/Networking/dns/overview.md).

## Практические сценарии

### Проверка разрешения имени через dig

```bash
# Базовый запрос A-записи
dig example.com A
# → ;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12345
# → ;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
# → ;; ANSWER SECTION:
# → example.com.    3600    IN    A    93.184.216.34
```

Расшифровка флагов в заголовке:
*   **qr (Query Response):** `1` — это ответ на запрос.
*   **rd (Recursion Desired):** клиент просит рекурсию (режим «сделай всё за меня»).
*   **ra (Recursion Available):** сервер подтверждает, что поддерживает рекурсию.
*   **aa (Authoritative Answer):** ответ получен напрямую от владельца зоны (не из кэша).
*   **tc (Truncated):** пакет был обрезан, требуется переход на TCP.

```bash
# Запрос конкретного DNS-сервера (в обход системного резолвера)
dig @8.8.8.8 example.com A

# Запрос с трассировкой (показывает каждый шаг итеративного поиска)
dig +trace example.com

# Запрос MX-записей (для проверки почтовой инфраструктуры)
dig example.com MX
# → ;; ANSWER SECTION:
# → example.com.    3600    IN    MX    10 mail.example.com.

# Проверка DNSSEC-подписей
dig +dnssec example.com A

# Проверка TTL записи (поле refresh в ANSWER SECTION)
dig +ttlunits example.com A

# Обратное разрешение (IP → имя)
dig -x 93.184.216.34
```

### Проверка через nslookup и host

```bash
# nslookup: быстрая проверка
nslookup example.com
# → Server:    127.0.0.53
# → Address:   127.0.0.53#53
# → Non-authoritative answer:
# → Name:      example.com
# → Address:   93.184.216.34

# nslookup: проверка特定ного типа записи
nslookup -type=MX example.com

# host: краткий вывод
host example.com
# → example.com has address 93.184.216.34
# → example.com mail is handled by 10 mail.example.com.
```

### Проверка через systemd-resolved

```bash
# Просмотр текущей конфигурации DNS
resolvectl status
# → Global
# →          Protocols: +LLMNR +mDNS -DNSOverTLS DNSSEC=no/unsupported
# → resolv.conf mode: stub

# Проверка того, как имя разрешается через службу
resolvectl query example.com
# → example.com: 93.184.216.34
# → (example.com)

# Очистка кэша (при подозрении на устаревшие записи)
resolvectl flush-caches

# Просмотр статистики кэша
resolvectl statistics
```

## Типичные ошибки и их решение

### Ошибка: SERVFAIL (код 2)

**Симптом:** `dig` возвращает `status: SERVFAIL`.

**Причины и решение:**
1.  **Проблемы с вышестоящими серверами:** авторитетный сервер зоны недоступен. Проверьте доступность NS-серверов: `dig NS example.com` → `dig @<NS-IP> example.com`.
2.  **DNSSEC-валидация провалилась:** если на резолвере включён DNSSEC, повреждённые подписи вызовут SERVFAIL. Проверьте через `dig +dnssec +cd example.com` (флаг `cd` отключает проверку).
3.  **Петли перенаправления:** DNS-сервер пересылает запрос самому себе. Подробнее: [Петли перенаправления DNS](./dns_forwarding_loops.md).

### Ошибка: NXDOMAIN (код 3)

**Симптом:** `dig` возвращает `status: NXDOMAIN`.

**Причины и решение:**
1.  **Домен не существует:** имя не зарегистрировано или было удалено. Проверьте через `whois example.com`.
2.  **Нет делегирования:** NS-записи для поддомена не настроены в родительской зоне.
3.  **Негативное кэширование:** резолвер запомнил NXDOMAIN на время Minimum TTL. Подождите или очистите кэш: `resolvectl flush-caches`.

### Ошибка: REFUSED (код 5)

**Симптом:** `dig` возвращает `status: REFUSED`.

**Причины и решение:**
1.  **Recursion отключена:** сервер не выполняет рекурсию для вашего IP. Проверьте ACL в конфигурации BIND (`allow-query`, `allow-recursion`).
2.  **Запрос к авторитетному серверу:** вы отправляете рекурсивный запрос авторитетному серверу, который не поддерживает рекурсию. Используйте публичный рекурсивный резолвер (8.8.8.8, 1.1.1.1).

### Медленный DNS-резолв (задержки 5 секунд)

**Симптом:** приложение «зависает» на 5 секунд при обращении к новым именам.

**Причины и решение:**
1.  **Проблема ndots:** в Kubernetes и контейнерах параметр `ndots:5` заставляет систему сначала пытаться разрешить имя как absolute (с приставкой search domain). Решение: используйте FQDN с точкой на конце (`example.com.`) или установите `ndots:1`.
2.  **Параллельные A/AAAA запросы (musl):** в Alpine Linux (musl libc) запросы A и AAAA отправляются параллельно. Если IPv6-запрос «зависает» из-за проблем с сетью, общая задержка достигает 5 секунд. Решение: `options single-request-reopen` в `/etc/resolv.conf` или настройка `dnsConfig` в Kubernetes.
3.  **Системный резолвер недоступен:** `systemd-resolved` не запущен или порт 53 занят другим процессом. Проверьте: `resolvectl status` и `ss -ulnp | grep :53`.

### Конфликт systemd-resolved и BIND

**Симптом:** BIND не может запуститься, так как порт 53 занят.

**Решение:**
```bash
# 1. Остановить и отключить systemd-resolved
sudo systemctl stop systemd-resolved
sudo systemctl disable systemd-resolved

# 2. Настроить /etc/resolv.conf на указание самого себя или внешних DNS
echo "nameserver 127.0.0.1" | sudo tee /etc/resolv.conf

# 3. Запустить BIND
sudo systemctl start named
```

### Очистка кэша на разных уровнях

В Linux кэширование может происходить в нескольких местах:
```bash
# 1. systemd-resolved (самый частый случай)
resolvectl flush-caches

# 2. nscd (если установлен)
sudo nscd -i hosts

# 3. Локальный DNS-сервер (BIND/unbound)
sudo rndc flush    # для BIND
sudo unbound-control flush_zone .    # для unbound

# 4. Проверка, что кэш очищен
resolvectl statistics | grep "Current Cache Size"
```
