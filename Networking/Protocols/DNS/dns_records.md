# Типы DNS-записей

## Определения

**Ресурсная запись (Resource Record, RR)** — атомарная единица данных в системе DNS, определяющая конкретный атрибут домена. Формат записи строго регламентирован (RFC 1035).

*   **NAME:** доменное имя, к которому относится запись.
*   **TYPE:** двухбайтовое поле, определяющее формат данных (A, MX, TXT и др.).
*   **CLASS:** класс сети (почти всегда `IN` — Internet).
*   **TTL (Time To Live):** время в секундах, в течение которого запись может храниться в кэше резолверов.
*   **RDATA:** данные, специфичные для конкретного типа записи (например, IP-адрес или имя хоста).

**Приклеенные записи (Glue Records)** — A или AAAA-записи, предоставляемые вместе с NS-записью для предотвращения циклической зависимости. Необходимы, если сервер имен (NS) находится внутри делегируемой зоны (например, `ns1.example.com` для зоны `example.com`). Без них резолвер не смог бы найти IP-адрес NS-сервера, чтобы спросить у него этот же IP.

**Wildcard-записи (Символы подстановки)** — записи, использующие символ `*` (например, `*.example.com`). Позволяют отвечать на запросы для любых несуществующих поддоменов одним набором данных. Символ `*` работает только как крайний левый элемент имени.

## Базовые концепции

### Общие типы записей

| Тип | Назначение | Технические нюансы |
| :--- | :--- | :--- |
| **A** | IPv4-адрес | Связывает имя с 32-битным адресом. Может быть несколько записей для одного имени (Round Robin DNS для балансировки L7). |
| **AAAA** | IPv6-адрес | Связывает имя с 128-битным адресом. Используется параллельно с A (Dual Stack). Современные резолверы отдают приоритет IPv6 (Алгоритм Happy Eyeballs). |
| **CNAME** | Псевдоним (Alias) | Указывает на другое каноническое имя. **Apex Restriction:** не может быть установлен для корня домена (например, `example.com`), так как RFC запрещает CNAME сосуществовать с любыми другими записями (а корень всегда имеет SOA и NS). |
| **ALIAS / ANAME** | Псевдо-запись | Внутренний механизм провайдеров (Route53, Cloudflare). Провайдер резолвит CNAME на стороне своего сервера и отдает клиенту итоговую A/AAAA-запись. Это решает проблему Apex-ограничения. |
| **MX** | Почтовый сервер | Формат: `[priority] [hostname]`. Приоритет от 0 до 65535, чем меньше число, тем выше приоритет. Hostname должен указывать на A/AAAA-запись, использование CNAME в MX запрещено RFC. |
| **NS** | Сервер имён | Указывает авторитетные серверы для зоны. Делегирование подзоны происходит через NS-записи в родительской зоне. |
| **PTR** | Указатель (Pointer) | Обратное разрешение IP → FQDN. Работает в специальных зонах `in-addr.arpa` (IPv4) и `ip6.arpa` (IPv6). Критично для проверок почтовыми серверами. См. [Обратная зона DNS](../../../Linux/Networking/Services/BIND/reverse_zone_configuration.md). |
| **SOA** | Начало зоны | Метаданные о зоне (Serial, Refresh, Retry, Expire, Minimum/Negative Cache TTL). |

### Записи для настройки почты и безопасности (TXT)

Записи типа **TXT** хранят произвольные текстовые данные. Сегодня их главная роль — верификация домена и защита от спама.

*   **SPF (Sender Policy Framework):** определяет список серверов и IP, которым разрешено отправлять почту от имени домена.
    *   Пример: `v=spf1 mx include:_spf.google.com ~all`.
*   **DKIM (DomainKeys Identified Mail):** содержит селектор и открытый ключ для проверки цифровой подписи писем. Имя записи выглядит как `selector._domainkey`.
*   **DMARC:** политика, указывающая почтовым серверам получателя, что делать с письмами, не прошедшими проверку SPF/DKIM.
    *   Пример: `v=DMARC1; p=quarantine; rua=mailto:reports@example.com`.

### Записи для сервисов и протоколов

*   **SRV (Service Record):** определяет хост и порт для служб (LDAP, SIP, XMPP, Consul).
    *   Формат: `_service._proto.name TTL IN SRV priority weight port target`.
    *   `priority`: как в MX (ниже = лучше).
    *   `weight`: пропорциональное распределение нагрузки между серверами с одинаковым приоритетом.
*   **SVCB / HTTPS (RFC 9460):** современные расширения для ускорения HTTPS-соединений и Service Binding.
    *   **Параметры:** передают ALPN (поддержка HTTP/2, HTTP/3), ECH (Encrypted Client Hello) и позволяют избежать редиректов с порта 80 на 443. Также работают как CNAME для Apex-доменов.

### Записи безопасности и DNSSEC

*   **CAA (Certification Authority Authorization):** ограничение списка CA, имеющих право выпускать сертификаты. Защищает от несанкционированного выпуска сертификатов взломанным или халатным удостоверяющим центром.
*   **TLSA (DANE):** хеш сертификата для проверки через DNSSEC. Позволяет полностью отказаться от публичных CA.
*   **SSHFP:** отпечаток SSH-ключа сервера. Позволяет клиенту автоматически проверять подлинность сервера при первом подключении.
*   **Записи DNSSEC:** 
    *   **DNSKEY:** Публичный ключ для проверки подписей.
    *   **DS (Delegation Signer):** Хеш ключа дочерней зоны, хранящийся у родителя (основа цепочки доверия).
    *   **RRSIG:** Цифровая подпись данных.
    *   **NSEC / NSEC3:** Доказательство отсутствия имени (Negative Proof). NSEC3 использует хеширование для защиты зоны от перебора. См. [Безопасность DNS](./dns_security.md).

### Нюансы TTL и кэширования

*   **TTL (Time To Live):** определяет время нахождения записи в кэше рекурсивного резолвера.
    *   *Низкий TTL (60-300с):* используется для GSLB, балансировки или при подготовке к миграции сервера на новый IP.
    *   *Высокий TTL (3600с+):* для стабильных записей (MX, TXT). Снижает нагрузку на DNS-серверы и ускоряет резолвинг для пользователей.
*   **Negative Caching (RFC 2308):** кэширование отрицательного ответа (NXDOMAIN). Время жизни такого кэша берется из последнего поля (Minimum TTL) записи SOA.

## Практические сценарии

### 1. Настройка CAA для Let's Encrypt

Ограничение выпуска сертификатов только одним центром (Let's Encrypt), включая запрет на Wildcard:

```dns
example.com.  IN  CAA  0 issue "letsencrypt.org"
example.com.  IN  CAA  0 issuewild ";"
example.com.  IN  CAA  0 iodef "mailto:security@example.com"
```

### 2. Настройка безопасности почтового домена

Базовый комплект записей для предотвращения попадания в спам:

```dns
; SPF: разрешить почтовые серверы из MX и Google Workspace, остальных помечать подозрительными (~all)
@   IN  TXT  "v=spf1 mx include:_spf.google.com ~all"

; DMARC: строгая политика отклонения писем без цифровой подписи
_dmarc  IN  TXT  "v=DMARC1; p=reject; aspf=s; adkim=s;"
```

### 3. Делегирование поддомена с Glue Records

Ситуация: `ns1.sub.example.com` отвечает за `sub.example.com`.

```dns
; В родительской зоне example.com (управляется регистратором)
sub     IN  NS      ns1.sub.example.com.
ns1.sub IN  A       203.0.113.10  ; Это и есть Glue Record
```

### 4. Диагностика специфических записей через dig

Для отладки сложных записей используйте фильтрацию типа:

```bash
# Проверка HTTPS-записи (поддержка HTTP/3 h3)
dig example.com HTTPS +short
# -> 1 . alpn="h3,h2" ipv4hint="198.51.100.1"

# Проверка SOA для определения параметров кэширования ошибок (Negative TTL)
dig example.com SOA
```
