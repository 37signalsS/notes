# Типы DNS-записей

## Определения

**Ресурсная запись (Resource Record, RR)** — атомарная единица данных в системе DNS, определяющая конкретный атрибут домена.

*   **NAME:** доменное имя, к которому относится запись.
*   **TYPE:** двухбайтовое поле, определяющее формат данных (A, MX, TXT и др.).
*   **CLASS:** класс сети (почти всегда `IN` — Internet).
*   **TTL (Time To Live):** время в секундах, в течение которого запись может храниться в кэше резолверов.
*   **RDATA:** данные, специфичные для конкретного типа записи (например, IP-адрес или имя хоста).

## Базовые концепции

### Общие типы записей

| Тип | Назначение | Особенности |
| :--- | :--- | :--- |
| **A** | IPv4-адрес | Связывает имя с 32-битным адресом IPv4. |
| **AAAA** | IPv6-адрес | Связывает имя с 128-битным адресом IPv6. |
| **CNAME** | Псевдоним (Alias) | Указывает на другое каноническое имя. **Ограничение:** не может сосуществовать с другими записями для одного имени (кроме DNSSEC). |
| **ALIAS / ANAME** | Псевдо-запись | Позволяет использовать функционал CNAME на корневом домене (apex). Реализуется на стороне DNS-провайдера (не является стандартом RFC). |
| **MX** | Почтовый сервер | Указывает на узлы, принимающие почту. Содержит приоритет. |
| **NS** | Сервер имён | Определяет авторитетные серверы для зоны или делегированной подзоны. |
| **PTR** | Указатель (Pointer) | Обратное разрешение IP → Имя. Используется в зонах `in-addr.arpa`. |
| **SOA** | Начало зоны | Метаданные о зоне. См. [Зоны DNS](./dns_zones.md). |

### Записи для настройки почты и безопасности (TXT)

Записи типа **TXT** используются для хранения произвольных данных, которые интерпретируются прикладными протоколами.

*   **SPF (Sender Policy Framework):** список IP-адресов, которым разрешено отправлять почту от имени домена.
    *   *Примечание:* отдельный тип записи SPF (Type 99) устарел (RFC 7208), используйте только TXT.
*   **DKIM (DomainKeys Identified Mail):** содержит открытый ключ для проверки цифровой подписи электронных писем.
*   **DMARC:** политика обработки писем, не прошедших проверку SPF или DKIM.

### Записи для сервисов и протоколов

*   **SRV (Service Record):** определяет местоположение (имя хоста и порт) конкретных служб (SIP, XMPP, LDAP).
    *   Формат: `_service._proto.name. TTL IN SRV priority weight port target.`
*   **SVCB / HTTPS (RFC 9460):** современные записи для ускорения веб-соединений. Позволяют передать параметры ALPN (HTTP/3), ключи шифрования (ECH) и приоритеты до установки TLS-соединения.

### Записи безопасности и инфраструктуры

*   **CAA (Certification Authority Authorization):** указывает, каким центрам сертификации (CA) разрешено выпускать SSL-сертификаты для данного домена.
*   **TLSA (DANE):** связывает сертификат или публичный ключ сервера напрямую с DNS (требует DNSSEC).
*   **SSHFP:** содержит отпечаток (fingerprint) публичного ключа SSH-сервера для предотвращения MitM-атак.
*   **DNSSEC-записи (DS, DNSKEY, NSEC, RRSIG):** используются для обеспечения целостности и аутентичности данных DNS. См. [Безопасность DNS](./dns_security.md).

## Практические сценарии

### 1. Настройка безопасности почтового домена

Пример записей в файле зоны:
```dns
; SPF: разрешить только почтовый сервер и конкретный IP
@   IN  TXT  "v=spf1 mx ip4:1.2.3.4 -all"

; DMARC: отправлять отчеты об ошибках и отклонять нелегитимные письма
_dmarc  IN  TXT  "v=DMARC1; p=reject; rua=mailto:admin@example.com"
```

### 2. Ограничение выпуска сертификатов (CAA)

Запретить всем, кроме Let's Encrypt и ZeroSSL, выпускать сертификаты:
```dns
@   IN  CAA  0 issue "letsencrypt.org"
@   IN  CAA  0 issue "zerossl.com"
@   IN  CAA  0 iodef "mailto:security@example.com"
```

### 3. Диагностика специфических записей через dig

```bash
# Проверка SRV-записи для Kerberos
dig _kerberos._udp.example.com SRV

# Проверка HTTPS-записи (ALPN h3)
dig example.com HTTPS

# Проверка отпечатка SSH (SSHFP)
dig example.com SSHFP
```

## Дополнительная информация

*   **Синтаксис зонного файла:** формат регламентирован RFC 1035.
*   **Краткие имена:** если имя в файле зоны не заканчивается точкой, к нему автоматически добавляется имя текущей зоны (Origin).
*   **Apex CNAME:** использование CNAME для корня домена (например, `example.com`) запрещено стандартами, так как это скрывает записи MX и SOA. Используйте записи типа ALIAS или ANAME, если ваш провайдер их поддерживает.
