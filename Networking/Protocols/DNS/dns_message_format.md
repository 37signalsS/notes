# Формат DNS-сообщения

## Определения

**DNS-сообщение (DNS Message)** — атомарная единица обмена данными в протоколе DNS, имеющая фиксированную бинарную структуру для запросов и ответов. Сообщения передаются в сетевом порядке байтов (Big-Endian). Максимальный размер ограничивается транспортным протоколом: 512 байт по UDP без EDNS, до 65535 байт по TCP, и до ~4096 байт по UDP с EDNS0 (зависит от согласованного размера буфера).

*   **Transaction ID (Идентификатор транзакции):** 16-битное число, генерируемое клиентом для сопоставления ответа с конкретным запросом. Служит первичной защитой от подмены ответов (спуфинга). Современные реализации также используют **Source Port Randomization** (случайный исходный порт UDP) для усиления защиты.
*   **Label (Метка):** часть доменного имени, ограниченная точками. В бинарном виде предваряется байтом длины (0–63). Длина метки не может превышать 63 байта, а общее имя — 255 байт (RFC 1035 §3.1).
*   **Name Compression (Сжатие имен):** метод уменьшения размера пакета путём замены повторяющихся частей имен 14-битными указателями (Pointers). Сжатие работает только для имён, уже встречавшихся ранее в пакете. Запросы (секция Question) обычно не сжимаются, так как содержат только запрашиваемое имя.
*   **EDNS0 (Extension Mechanisms for DNS, RFC 6891):** механизмы расширения, позволяющие передавать данные > 512 байт по UDP и новые управляющие флаги через псевдо-запись **OPT**. Является стандартом для современных DNS-имплементаций.
*   **TSIG (Transaction Signature, RFC 8945):** механизм аутентификации DNS-сообщений на основе общих секретных ключей. Добавляет в сообщение дополнительную секцию с HMAC-подписью для защиты от подмены. Используется для трансфера зон (AXFR/IXFR) и динамических обновлений.
*   **TTL (Time To Live):** 32-битное поле в Resource Record, определяющее максимальное время (в секундах), в течение которого запись может храниться в кэше промежуточных резолверов. После истечения TTL запись считается устаревшей и подлежит повторному запросу.

## Базовые концепции

### Общая структура пакета

Сообщение DNS состоит из заголовка фиксированной длины (12 байт) и четырех секций переменной длины. Порядок секций строго определён:

```text
+---------------------+
|      Header         | (Фиксировано: 12 байт)
+---------------------+
|      Question       | (Запрашиваемые имена и типы)
+---------------------+
|       Answer        | (Ресурсные записи ответов)
+---------------------+
|      Authority      | (Записи о серверах имен)
+---------------------+
|      Additional     | (Дополнительные данные, включая OPT RR)
+---------------------+
```

**Ключевое правило:** секции Answer, Authority и Additional имеют идентичный формат (Resource Record), а секция Question имеет собственный формат (без полей TTL/RDLENGTH/RDATA).

### Структура заголовка (Header)

| Поле | Размер | Назначение |
| :--- | :--- | :--- |
| **Transaction ID** | 16 бит | Идентификатор сессии. Клиент генерирует случайное число; сервер возвращает его в ответе. |
| **Flags** | 16 бит | Управляющие биты и код ответа. Детализация — ниже. |
| **QDCOUNT** | 16 бит | Количество записей в секции Question (обычно 1). |
| **ANCOUNT** | 16 бит | Количество записей в секции Answer. |
| **NSCOUNT** | 16 бит | Количество записей в секции Authority. |
| **ARCOUNT** | 16 бит | Количество записей в секции Additional (включает OPT RR для EDNS0). |

### Детализация флагов (Flags, 16 бит)

Флаги — центральный элемент управления поведением протокола:

| Бит(ы) | Имя | Описание | Контекст использования |
| :--- | :--- | :--- | :--- |
| 0 | **QR** | Query/Response: `0` — запрос, `1` — ответ. | Определяет роль сообщения. |
| 1-4 | **Opcode** | Тип операции: `0` (QUERY), `1` (IQUERY), `2` (STATUS), `4` (NOTIFY), `5` (UPDATE). | Opcode `0` используется в 99% случаев. NOTIFY (4) — Push-уведомление при изменении зоны. UPDATE (5) — динамическое обновление зоны (RFC 2136). |
| 5 | **AA** | Authoritative Answer: `1` — ответ от владельца зоны. | Устанавливается только в ответах. Присутствие `aa` означает, что ответ получен из авторитетного источника, а не из кэша. |
| 6 | **TC** | TrunCation: `1` — пакет обрезан (превышен лимит UDP). | При установке TC клиент обязан повторить запрос по TCP. Для DNSSEC-ответов может возникать при bufsize < 4096. |
| 7 | **RD** | Recursion Desired: `1` — клиент просит сервер выполнить рекурсию. | Клиент устанавливает в запросе. Сервер копирует в ответ. Если рекурсия не поддерживается — игнорируется. |
| 8 | **RA** | Recursion Available: `1` — сервер поддерживает рекурсию. | Устанавливается только в ответах. Позволяет клиенту узнать, может ли сервер выполнять рекурсию. |
| 9 | **Z** | Reserved: зарезервировано, всегда `0`. | Исторически использовался для опроса (IQUERY), но вышел из употребления. |
| 10 | **AD** | Authenticated Data: `1` — данные проверены через DNSSEC. | Устанавливается рекурсивным резолвером при успешной DNSSEC-валидации. Важно: AD не устанавливается авторитетными серверами — только рекурсивными. |
| 11 | **CD** | Checking Disabled: `1` — отключить проверку DNSSEC. | Клиент может установить CD, чтобы получить данные даже при провале DNSSEC-валидации (например, для диагностики). Рекурсивный резолвер должен выполнить запрос без проверки подписей. |
| 12-15 | **RCODE** | Response Code: код результата (см. таблицу RCODE ниже). | Расширяется до 12 бит через Extended RCODE в OPT RR. |

### Полная таблица RCODE (Response Codes)

| Код | Имя | Описание | Типичная причина |
| :--- | :--- | :--- | :--- |
| 0 | **NOERROR** | Успешное выполнение. | Запрос обработан корректно. |
| 1 | **FORMERR** | Ошибка формата запроса. | Сервер не смог распознать сообщение (несовместимая версия протокола, повреждённые данные). |
| 2 | **SERVFAIL** | Внутренняя ошибка сервера. | Проблемы с рекурсией, таймаут вышестоящего сервера, провал DNSSEC-валидации, ошибки в конфигурации зоны. |
| 3 | **NXDOMAIN** | Доменное имя не существует. | Опечатка в имени, делегирование не настроено, домен удалён. Кэшируется на время Minimum TTL из SOA. |
| 4 | **NOTIMP** | Функциональность не реализована. | Сервер не поддерживает запрошенную операцию (например, IQUERY). |
| 5 | **REFUSED** | Запрос отклонён. | ACL блокирует запрос, recursion отключена для данного клиента, RPZ политика. |
| 6 | **YXDOMAIN** | Имя существует (при попытке создания). | Динамическое обновление (RFC 2136): запись уже существует. |
| 7 | **YXRRSet** | RRset существует. | Динамическое обновление: набор записей уже есть. |
| 8 | **NXRRSet** | RRset не существует. | Динамическое обновление: пытаемся удалить несуществующий набор. |
| 9 | **NOTAUTH** | Сервер не авторитетен. | Запрос к авторитетному серверу для чужой зоны, или TSIG-проверка не пройдена. |
| 10 | **NOTZONE** | Имя вне зоны. | Динамическое обновление: имя не принадлежит указанной зоне. |
| 16 | **BADVERS** | Неподдерживаемая версия EDNS. | Сервер не поддерживает версию EDNS, указанную в OPT RR. |
| 16 | **BADSIG** | Неверная TSIG-подпись. | HMAC-подпись не совпадает (неверный ключ, повреждённое сообщение, несинхронизированные часы). |

**Примечание:** коды 16+ являются расширенными (Extended RCODE). Код 16 используется одновременно как BADVERS (для EDNS) и BADSIG (для TSIG) — различие определяется контекстом (наличие OPT RR или TSIG RR).

### Структура секции Question

Каждый вопрос состоит из трех полей (фиксированный размер 4 байта + переменное имя):

1.  **QNAME:** доменное имя в формате меток (переменная длина). Каждая метка предваряется байтом длины; имя завершается нулевым байтом (`0x00`).
2.  **QTYPE:** тип запрашиваемой записи (16 бит). Стандартные значения: `1` (A), `28` (AAAA), `5` (CNAME), `15` (MX), `255` (ANY), `252` (AXFR), `43` (DS), `46` (RRSIG).
3.  **QCLASS:** класс сети (16 бит). `1` (IN — Internet) является практически единственным используемым классом. Класс `255` (ANY) используется для запроса всех классов.

**Пример бинарного представления** `example.com` в QNAME:

```text
07 65 78 61 6d 70 6c 65 03 63 6f 6d 00
│  │                            │  │  │
│  └─ "example" (7 байт)        │  └─ "com" (3 байта)
│                               └─ Точка-разделитель
└─ Длина метки (7 = 0x07)
```

### Структура секций данных (Resource Record)

Все секции Answer, Authority и Additional содержат ресурсные записи (RR) единого формата:

| Поле | Размер | Описание |
| :--- | :--- | :--- |
| **NAME** | Переменная | Доменное имя (с использованием сжатия). Для ответов — это имя из запроса или его часть. |
| **TYPE** | 16 бит | Тип записи (A=1, NS=2, CNAME=5, SOA=6, MX=15, TXT=16, AAAA=28, OPT=41, DS=43, RRSIG=46, NSEC=47, DNSKEY=48, SVCB=64, HTTPS=65). |
| **CLASS** | 16 бит | Класс (обычно `IN` = 1). Для OPT RR поле CLASS используется как UDP Payload Size. |
| **TTL** | 32 бита | Время жизни в кэше (секунды). Для OPT RR — биты Extended RCODE + EDNS Flags. Для SOA — Minimum TTL (негативное кэширование). |
| **RDLENGTH** | 16 бит | Длина поля RDATA в байтах. |
| **RDATA** | Переменная | Данные записи. Формат зависит от TYPE. |

**Форматы RDATA для основных типов:**

*   **A:** 4 байта (IPv4-адрес).
*   **AAAA:** 16 байт (IPv6-адрес).
*   **NS/CNAME/PTR/DNAME:** доменное имя (сжатое, переменная длина).
*   **MX:** 2 байта (приоритет) + доменное имя.
*   **SOA:** 5 × имя (MNAME, RNAME) + 5 × 32 бита (Serial, Refresh, Retry, Expire, Minimum).
*   **TXT:** 1 байт (длина) + строка данных (UTF-8, до 255 байт на segment).

### Механизм сжатия имен (Name Compression)

Для экономии места DNS использует указатели. Если имя или его часть (например, `.example.com`) уже встречались в пакете:

*   Первые два бита байта устанавливаются в `11` (значение `0xC0`).
*   Оставшиеся 14 бит указывают на **смещение (offset)** в байтах от начала пакета, где это имя описано впервые.
*   Пример: `0xC00C` — указатель на имя, начинающееся с 12-го байта пакета.

**Бинарный пример сжатия:**

```text
Исходное имя в Question:   07 65 78 61 6d 70 6c 65 03 63 6f 6d 00
                            └── "example.com" ─────────────────────┘

Имя в Answer (использует Pointer): C0 0C
                                    │  │
                                    │  └─ Смещение 12 (0x0C) — начало "example.com" в Question
                                    └─ Префикс 0xC0 = Pointer
```

**Ограничения сжатия:**

*   Указатель не может указывать на указатель (запрещена цепочка указателей, RFC 1035 §4.1.4).
*   Сжатие работает только «назад» (на ранее встретившиеся имена).
*   Максимальное смещение — 16383 байта (14 бит).
*   DNSSEC-записи (RRSIG, NSEC, DNSKEY) не сжимают внутренние имены, чтобы обеспечить целостность подписей.

### Расширенный DNS (EDNS0, RFC 6891)

Так как заголовок DNS фиксирован, EDNS использует псевдо-запись типа **OPT** в секции `Additional`:

| Поле OPT RR | Соответствие в стандартном RR | Значение |
| :--- | :--- | :--- |
| NAME | — | Всегда `.` (корень, 1 байт: `0x00`). |
| TYPE | — | `41` (OPT). |
| CLASS | UDP Payload Size | Максимальный размер UDP-пакета, который клиент готов принять (например, 1232, 4096). |
| TTL | Extended RCODE + Flags | Старшие 8 бит TTL = Extended RCODE (расширяет RCODE до 12 бит). Младшие 8 бит = EDNS Flags (DO, NSEC3). |
| RDATA | Опции | Список EDNS-опций (DNSSEC OK, Cookie, NSID, Client Subnet и др.). |

**Ключевые EDNS-опции:**

*   **DNSSEC OK (DO, бит 15 в EDNS Flags):** клиент запрашивает DNSSEC-подписи (RRSIG). Без установки DO сервер не возвращает DNSSEC-записи.
*   **NSID (Name Server Identifier, RFC 5001):** запрос идентификатора сервера (полезно для диагностики Anycast-кластеров).
*   **Client Subnet (ECS, RFC 7871):** передача подсети клиента для GeoDNS. Позволяет серверу вернуть IP, оптимизированный для региона клиента.
*   **Padding (RFC 7830):** дополнение сообщения до фиксированного размера для защиты от анализа размера пакета (traffic analysis).

**Нegotiation:** клиент объявляет поддержку EDNS в OPT-записи. Если сервер не поддерживает EDNS, он просто игнорирует OPT-секцию и отвечает без неё. Если клиент не отправляет OPT, сервер ограничивается 512 байтами UDP.

### Аутентификация транзакций (TSIG, RFC 8945)

TSIG добавляет в сообщение дополнительную секцию (Additional) с HMAC-подписью:

```text
+---------------------+
|      Header         |
+---------------------+
|      Question       |
+---------------------+
|       Answer        |
+---------------------+
|      Authority      |
+---------------------+
|      Additional     | (включая OPT)
+---------------------+
|      TSIG RR        | ← Последняя запись в Additional
+---------------------+    (подпись всего сообщения)
```

**Поля TSIG RR:**
*   **Algorithm Name:** имя алгоритма (например, `hmac-sha256.`).
*   **Time Signed:** временная метка (UTC).
*   **Fudge:** допустимое отклонение времени (обычно 300 сек).
*   **MAC:** HMAC-подпись всего DNS-сообщения (включая заголовок, но с обнулёнными полями ARCOUNT и Transaction ID в подписываемой копии).
*   **Original ID:** оригинальный Transaction ID (так как поле может быть изменено при форвардинге).
*   **Error:** код ошибки TSIG (0 = NOERROR, 16 = BADSIG, 17 = BADKEY, 18 = BADTIME).

**Порядок TSIG-хэндшейка:**
1.  Клиент отправляет запрос с TSIG-подписью.
2.  Сервер проверяет подпись и отвечает с TSIG.
3.  Последующие сообщения в сессии (например, AXFR) переподписывают TSIG.
4.  При ошибке TSIG сервер возвращает `NOTAUTH` + `BADSIG (16)`.

### Различия UDP и TCP

| Характеристика | UDP | TCP |
| :--- | :--- | :--- |
| **Лимит размера** | 512 байт (без EDNS), до 4096 байт (с EDNS) | 65535 байт (теоретический максимум) |
| **Флаг TC** | Устанавливается при превышении лимита → клиент переключается на TCP | Не применяется |
| **Фрагментация** | Возможно (но не рекомендуется) | Нет (TCP обеспечивает сегментацию) |
| **Соединение** | Stateless (каждый пакет независим) | Stateful (3-way handshake) |
| **Использование** | 90%+ DNS-трафика (маленькие ответы) | Зоны传送 (AXFR/IXFR), большие ответы, DNSSEC |
| **Порядок байтов** | Big-Endian | Big-Endian + 2-байтовая длина в начале каждого сообщения |
| **Timeout (типичный)** | 2–5 секунд | 5–30 секунд (зависит от round-trip) |

**Когда TCP обязателен:**
*   Ответ превышает UDP Payload Size (флаг TC=1).
*   Трансфер зоны (AXFR/IXFR).
*   DNSSEC (запросы DNSKEY, DS, подписи RRSIG могут быть большими).
*   Динамические обновления (RFC 2136) с TSIG.

**TCP DNS-сообщение** имеет 2-байтовую длину перед заголовком:

```text
+------------------+---------------------+
| Длина (2 байта)  |      DNS Message    |
+------------------+---------------------+
```

### Механизм TSIG ( детально )

TSIG защищает целостность и аутентичность DNS-сообщений:

*   **Алгоритмы:** `hmac-md5.sig-alg.reg.int`, `hmac-sha1`, `hmac-sha256`, `hmac-sha384`, `hmac-sha512`.
*   **Синхронизация времени:** TSIG требует синхронизации часов между клиентом и сервером (typically NTP). Параметр `fudge` определяет допустимое отклонение (по умолчанию 300 сек).
*   **Счётчик сообщений:** для сессий (AXFR) TSIG использует счётчик TSIG Timers для предотвращения атак replay.

### Практический пример: полный цикл dig-ответа

Для的理解 того, как выглядит реальный ответ DNS, рассмотрим вывод `dig` и его соответствие структуре сообщения:

```bash
dig @8.8.8.8 example.com A +dnssec
```

```text
; <<>> DiG 9.18.18 <<>> @8.8.8.8 example.com A +dnssec
; (1 server found)
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41234
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags: do; udp: 512
;; QUESTION SECTION:
;example.com.                   IN      A

;; ANSWER SECTION:
example.com.            3600    IN      A       93.184.216.34
example.com.            3600    IN      RRSIG   A 13 2 3600 (
                                20260915000000 20260801000000 12345 example.com.
                                abc123... )

;; Query time: 23 msec
;; SERVER: 8.8.8.8#53(8.8.8.8) (UDP)
;; WHEN: Mon Aug 25 12:00:00 UTC 2026
;; MSG SIZE  rcvd: 168
```

**Соответствие секций:**

| Секция dig | Поле DNS-сообщения | Содержимое |
| :--- | :--- | :--- |
| `->>HEADER<<-` | Header (12 байт) | `opcode: QUERY`, `status: NOERROR`, `id: 41234`, флаги `qr rd ra ad` |
| `OPT PSEUDOSECTION` | Additional (OPT RR) | EDNS version 0, flags: `do` (DNSSEC OK), UDP size 512 |
| `QUESTION SECTION` | Question | `example.com. IN A` |
| `ANSWER SECTION` | Answer (2 RR) | A-запись + RRSIG (подпись) |
| `Query time: 23 msec` | Статистика | Задержка резолвинга |
| `MSG SIZE rcvd: 168` | Статистика | Общий размер ответа в байтах |

### Влияние флагов на поведение резолвера

Флаги в заголовке определяют, как сервер обрабатывает запрос и как клиент интерпретирует ответ:

| Ситуация | Флаги запроса | Флаги ответа | Поведение |
| :--- | :--- | :--- | :--- |
| Обычный рекурсивный запрос | `RD=1` | `RD=1, RA=1` | Сервер выполняет полную рекурсию и возвращает готовый ответ. |
| Запрос к авторитетному серверу | `RD=0` | `RD=0, AA=1` | Сервер возвращает авторитетный ответ из зоны (без рекурсии). |
| DNSSEC-валидация | `RD=1, CD=1` | `RD=1, RA=1, AD=1` | Клиент запрещает проверку (CD=1); резолвер выполняет проверку и устанавливает AD=1 при успехе. |
| Ответ обрезан | `RD=1` | `RD=1, RA=1, TC=1` | Ответ превысили лимит UDP. Клиент обязан повторить запрос по TCP. |
| Запрос от non-recursive клиента | `RD=0` | `RD=0, RA=1` | Сервер может вернуть реферал (ссылку на NS) вместо полного ответа. |

### Предусловия

Для анализа DNS-сообщений необходимы следующие инструменты:

```bash
# Debian/Ubuntu
sudo apt install dnsutils tcpdump

# RHEL/CentOS
sudo yum install bind-utils tcpdump

```

### 1. Анализ заголовка через dig (полный вывод)

```bash
# Запрос с отображением всех секций и флагов
dig example.com A +noall +header +question +answer +stats
```

```text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 58921
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; QUESTION SECTION:
;example.com.                   IN      A

;; ANSWER SECTION:
example.com.            3600    IN      A       93.184.216.34

;; Query time: 12 msec
;; SERVER: 1.1.1.1#53(1.1.1.1) (UDP)
;; MSG SIZE  rcvd: 56
```

**Интерпретация:**
*   `opcode: QUERY` → Opcode = 0 (стандартный запрос).
*   `status: NOERROR` → RCODE = 0 (успех).
*   `id: 58921` → Transaction ID (сопоставляется с запросом).
*   `qr rd ra` → QR=1 (ответ), RD=1 (был запрос с рекурсией), RA=1 (сервер поддерживает рекурсию).
*   `AD отсутствует` → DNSSEC не проверялся (клиент не запрашивал).

### 2. Интерпретация OPT PSEUDOSECTION (EDNS)

```bash
# Запрос с DNSSEC (провоцирует OPT-секцию)
dig example.com A +dnssec
```

```text
;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags: do; udp: 512
```

| Поле | Значение | Расшифровка |
| :--- | :--- | :--- |
| `version: 0` | Версия EDNS | 0 = EDNS0 (единственная широко используемая версия). |
| `flags: do` | EDNS Flags | `do` = DNSSEC OK (бит 15 установлен). Клиент запрашивает RRSIG. |
| `udp: 512` | UDP Payload Size | Клиент готов принять до 512 байт по UDP. Сервер может установить свой размер (обычно 1232 или 4096). |

```bash
# Запрос с явным указанием размера буфера
dig example.com A +dnssec +bufsize=4096

# Результат:
;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags: do; udp: 4096
```

### 3. Анализ TC (Truncation) и переключение на TCP

```bash
# Провокация большого ответа (DNSSEC для корневой зоны)
dig . NS +dnssec +bufsize=512 +noall +header
# → ;; flags: qr rd ra tc; QUERY: 1, ANSWER: 13, AUTHORITY: 0, ADDITIONAL: 1
#    (флаг tc=1 — ответ обрезан)

# Принудительный TCP для получения полного ответа
dig . NS +dnssec +tcp +noall +answer
# → . 518400 IN NS a.root-servers.net.
#    (полный ответ без обрезки)
```

**Почему возникает TC:** DNSSEC-ответы содержат RRSIG-записи, которые значительно увеличивают размер. Корневая зона с DNSSEC имеет ~4KB ответов — это превышает стандартный лимит UDP 512 байт.

### 7. Интерпретация размера сообщения

```bash
# Проверка размера ответа

#    (56 байт: заголовок 12 + Question 17 + Answer 17 + OPT 11)
```

**Формула расчёта размера DNS-ответа:**

```text
Header (12) + Question (имя + 4) + Answer × N (имя + 10 + RDATA) + OPT (11)
```

| Компонент | Размер | Пример |
| :--- | :--- | :--- |
| Header | 12 байт | Фиксировано |
| Question (example.com A) | 17 байт | 1+7+1+3+1+1 + 2(QTYPE) + 2(QCLASS) = 17 |
| Answer (A-запись) | 17 байт | 1+7+1+3+1+1 + 2(TYPE) + 2(CLASS) + 4(TTL) + 2(RDLENGTH) + 4(IP) = 28... |

### 9. Wireshark GUI: визуальный анализ пакетов DNS

Wireshark предоставляет графическое представление DNS-сообщений, разделённое на две панели:
- **Левая панель (Packet Details):** расшифровка полей протокола (дерево).
- **Правая панель (Packet Bytes):** raw-данные в шестнадцатеричном и ASCII-виде.

В отличие от HTTP, данные в DNS передаются в бинарном виде. Текстовые элементы ограничены доменным именем в секции Question; всё остальное (заголовок, счётчики, флаги, RDATA) представлено числами.

#### 9.1 Захват и фильтрация

```bash
# Запуск Wireshark с фильтром DNS
wireshark -i any -f "udp port 53" -k

# Или через GUI: в строке Display Filter введите:
dns
```

Для генерации DNS-трафика используйте `nslookup` (встроен в Windows/macOS/Linux):

```bash
# Простой запрос A-записи
nslookup example.com

# Запрос к конкретному серверу (обходим локальный кэш)
nslookup example.com 8.8.8.8
```

#### 9.2 DNS-запрос в Wireshark

При выполнении `nslookup example.com` в Wireshark отображается UDP-пакет с порта клиента (ephemeral-порт, назначается ОС автоматически) на порт 53.

**Заголовок (первые 12 байт):**

| Поле в Wireshark | Значение | Расшифровка |
| :--- | :--- | :--- |
| `dns.id` | `0x0002` (или другой случайный ID) | Transaction ID — клиент генерирует случайное число для сопоставления запроса и ответа. |
| `dns.flags` | `0x0100` | QR=0 (запрос), Opcode=0 (QUERY), AA=0, TC=0, RD=1 (рекурсия желательна), RA=0, Z=0, AD=0, CD=0, RCODE=0. |
| `dns.count.queries` | `1` | QDCOUNT — один вопрос в секции Question. |
| `dns.count.answers` | `0` | ANCOUNT — ответов нет (это запрос). |
| `dns.count.auth_rr` | `0` | NSCOUNT — авторитетных записей нет. |
| `dns.count.add_rr` | `0` | ARCOUNT — дополнительных записей нет (в примере без EDNS). |

**Секция Question:**

В левой панели Wireshark раскрывает `DNS → Query`:

| Поле | Значение | Расшифровка |
| :--- | :--- | :--- |
| `dns.qry.name` | `example.com.` | QNAME — доменное имя в текстовом виде (с точкой в конце). |
| `dns.qry.type` | `A (1)` | QTYPE — запрашиваемый тип записи (A = IPv4-адрес). |
| `dns.qry.class` | `IN (1)` | QCLASS — класс Internet. |

В правой панели бинарное представление имени:

```text
07 65 78 61 6d 70 6c 65 03 63 6f 6d 00
│  └─ "example" (7 байт)
│                            └─ "com" (3 байта)
└─ Длина метки
```

**Транспортный уровень (UDP):**

| Поле IP | Значение | Расшифровка |
| :--- | :--- | :--- |
| `ip.src` | `192.168.1.100` | IP-адрес источника (локальный компьютер). |
| `ip.dst` | `192.168.1.1` | IP-адрес DNS-сервера (локальный резолвер). |
| `udp.srcport` | `54321` | Эфемерный порт, назначенный ОС (случайное значение). |
| `udp.dstport` | `53` | Порт DNS-сервера. |

#### 9.3 DNS-ответ в Wireshark

Ответ имеет тот же Transaction ID, что и запрос. Wireshark автоматически сопоставляет запрос и ответ по полю `dns.id`.

**Кэшированный ответ (неавторитетный):**

Если локальный резолвер возвращает ответ из кэша:

| Поле | Значение | Расшифровка |
| :--- | :--- | :--- |
| `dns.flags.response` | `1` | QR=1 — это ответ. |
| `dns.flags.authoritative` | `0` | AA=0 — ответ неавторитетный (взят из кэша). |
| `dns.flags.recursion_avail` | `1` | RA=1 — сервер поддерживает рекурсию. |
| `dns.flags.recursion_desired` | `1` | RD=1 — скопирован из запроса. |
| `dns.count.answers` | `1` | ANCOUNT — один ответ в секции Answer. |

**Секция Answer:**

| Поле | Значение | Расшифровка |
| :--- | :--- | :--- |
| `dns.a` | `93.184.216.34` | RDATA — IPv4-адрес, соответствующий запрошенному имени. |
| `dns.a.ttl` | `524` | TTL — время жизни в кэше (секунды). После истечения TTL запись подлежит повторному запросу. |

**Авторитетный ответ:**

При запросе напрямую к серверу, отвечающему за зону (например, через `nslookup example.com ns1.example.com`):

| Поле | Значение | Расшифровка |
| :--- | :--- | :--- |
| `dns.flags.authoritative` | `1` | AA=1 — сервер является владельцем зоны. Ответ получен из конфигурационных файлов, а не из кэша. |
| `dns.flags.recursion_avail` | `0` | RA=0 — авторитетный сервер обычно не поддерживает рекурсию для внешних запросов (ограничение ресурсов). |

Wireshark отображает такой ответ как **"Non-authoritative answer"**, если AA=0, несмотря на то, что данные корректны. Это означает лишь происхождение данных (кэш), а не их достоверность.

#### 9.4 Множественные A-записи (Round-Robin DNS)

Если домен имеет несколько IPv4-адресов, в ответе несколько Resource Record в секции Answer. ANCOUNT соответствует количеству записей:

```bash
# Запрос к домену с несколькими A-записями
nslookup www.yandex.ru
```

В Wireshark:
- `dns.count.answers` = `3` (три IPv4-адреса)
- В секции Answer повторяется QNAME, затем три записи типа A с разными RDATA
- Каждая запись имеет собственный TTL

**Достоинства Round-Robin DNS:**
- Простое распределение нагрузки между серверами.
- Не требует специального оборудования (работает на уровне DNS).

**Ограничения:**
- Не учитывает текущую нагрузку или состояние серверов.
- Клиенты кэшируют ответы, поэтому перераспределение происходит только после истечения TTL.
- При отказе одного сервера часть клиентов продолжает получать его адрес до истечения TTL.

#### 9.5 Сравнение кэшированного и авторитетного ответов

| Характеристика | Кэшированный ответ (локальный резолвер) | Авторитетный ответ (сервер зоны) |
| :--- | :--- | :--- |
| **Флаг AA** | `0` | `1` |
| **Флаг RA** | `1` | `0` (обычно) |
| **Источник данных** | Память резолвера (кэш) | Диск/конфигурация сервера |
| **TTL** | Уменьшается с момента загрузки в кэш | Исходное значение из зоны |
| **Скорость ответа** | Миллисекунды (кэш) | Зависит от RTT до сервера |
| **Актуальность** | Зависит от TTL и времени в кэше | Актуально на момент запроса |

**Практический совет:** для диагностики проблем с DNS сначала выполните запрос к локальному резолверу, затем к авторитетному серверу. Если локальный резолвер возвращает неверный IP, а авторитетный — корректный, проблема в кэше резолвера (сбросьте кэш: `resolvectl flush-caches` или `systemd-resolve --flush-caches`).

#### 9.6 Наблюдение типов записей в Wireshark

Разные типы DNS-записей визуализируются в Wireshark по-разному. Ниже — практические примеры захвата запросов и ответов для основных типов записей.

##### 9.6.1 Запись A (IPv4-адрес)

```bash
# Явный запрос A-записи
nslookup -type=A www.yandex.ru
```

**В Wireshark:**
- **Запрос:** `dns.qry.type = A (1)`, QNAME = `www.yandex.ru.`
- **Ответ:** секция Answer содержит одну или несколько записей типа A с RDATA в виде IPv4-адресов.
- Если у домена несколько IPv4-адресов (Round Robin), ANCOUNT > 1, и в Answer повторяется QNAME для каждого IP.

##### 9.6.2 Запись AAAA (IPv6-адрес)

```bash
# Явный запрос AAAA-записи
nslookup -type=AAAA www.yandex.ru
```

**В Wireshark:**
- **Запрос:** `dns.qry.type = AAAA (28)`, QNAME = `www.yandex.ru.`
- **Ответ:** секция Answer содержит запись типа AAAA с 128-битным IPv6-адресом в RDATA.
- AAAA-записи часто передаются параллельно с A-записями (Dual Stack).

##### 9.6.3 Запись CNAME (каноническое имя)

```bash
# Запрос CNAME-записи
nslookup -type=CNAME www.ru
```

**В Wireshark:**
- **Запрос:** `dns.qry.type = CNAME (5)`, QNAME = `www.ru.`
- **Ответ:** секция Answer содержит запись типа CNAME. RDATA — каноническое имя (FQDN), на которое указывает псевдоним.
- **Важно:** если ответ содержит CNAME, он всегда один для данного имени (RFC 1034). Другие записи для того же имени не могут существовать.

##### 9.6.4 Запись MX (почтовый сервер)

```bash
# Запрос MX-записей
nslookup -type=MX gmail.com
```

**В Wireshark:**
- **Запрос:** `dns.qry.type = MX (15)`, QNAME = `gmail.com.`
- **Ответ:** секция Answer содержит несколько записей MX. Каждая запись имеет:
  - **RDATA Preference** (приоритет): число от 0 до 65535, чем меньше, тем выше приоритет.
  - **RDATA Exchange** (hostname): FQDN почтового сервера.
- **Логика обработки:** почтовый клиент обращается к серверам по порядку возрастания Preference. При одинаковом приоритете — случайный выбор (Round Robin).
- **TTL:** MX-записи обычно имеют высокий TTL (3600–86400 секунд), так как меняются редко.

##### 9.6.5 Запись NS (авторитетный сервер имён)

```bash
# Запрос NS-записей
nslookup -type=NS hub.com
```

**В Wireshark:**
- **Запрос:** `dns.qry.type = NS (2)`, QNAME = `hub.com.`
- **Ответ:** секция Answer содержит несколько записей NS (обычно 2–4). Количество ответов (`dns.count.answers`) равно количеству NS-серверов.
- **Ключевое наблюдение:** если в заголовке DNS указано `dns.count.queries = 1`, а `dns.count.answers = 3` — это означает, что один запрос получил три ответа (три NS-сервера обслуживают зону).
- **TTL:** NS-записи имеют высокий TTL (часто 86400+ секунд), так как зоны делегируются на долгие периоды.

##### 9.6.6 Запись PTR (обратное разрешение)

```bash
# Обратный запрос по IP-адресу
nslookup 77.88.44.55
```

**В Wireshark:**
- **Запрос:** `dns.qry.type = PTR (12)`, QNAME строится по схеме обратной зоны:
  - Для IPv4: `<reversed-IP>.in-addr.arpa.`
  - Для IPv6: `<reversed-IP>.ip6.arpa.`
  - Пример: IP `77.88.44.55` → QNAME = `55.44.88.77.in-addr.arpa.`
- **Ответ:** секция Answer содержит запись типа PTR. RDATA — FQDN, соответствующий IP-адресу.
- **Назначение:** используется для идентификации хоста по IP, проверки почтовых серверов (PTR обязателен для внешней почты), диагностики сетевых проблем.

##### 9.6.7 Сводная таблица типов записей в Wireshark

| Тип | QTYPE | RDATA в ответе | Особенности отображения |
| :--- | :--- | :--- | :--- |
| **A** | `1` | IPv4-адрес (4 байта) | ANCOUNT = числу A-записей |
| **AAAA** | `28` | IPv6-адрес (16 байт) | Часто вместе с A (Dual Stack) |
| **CNAME** | `5` | FQDN (доменное имя) | Всегда одна запись для имени |
| **MX** | `15` | Preference + Exchange | Несколько записей с разными Preference |
| **NS** | `2` | FQDN сервера имён | ANCOUNT = числу NS-серверов |
| **PTR** | `12` | FQDN | QNAME в обратной зоне (in-addr.arpa) |

**Практическое наблюдение:** при захвате DNS-трафика фильтр `dns` в Wireshark показывает все запросы и ответы. Для фильтрации по конкретному типу используйте `dns.qry.type == 1` (A), `dns.qry.type == 15` (MX) и т.д.

## Типичные ошибки и их решение

### Ошибка: FORMERR (RCODE 1)

**Симптом:** сервер возвращает ошибку формата.

**Причины:**
1.  **Несовместимая версия EDNS:** клиент отправляет OPT RR с неподдерживаемой версией (version > 0). Решение: установите `version:0` или отключите EDNS (`+edns=0`).
2.  **Повреждённое сообщение:** сетевая проблема (бит-перекос, обрезка). Решение: повторите запрос через TCP (`+tcp`).
3.  **Неверная кодировка имени:** нестандартные символы в имени. Решение: проверьте DNS-имя на корректность.

### Ошибка: SERVFAIL (RCODE 2) — детальная диагностика

**Симптом:** сервер не может обработать запрос.

**Диагностика по этапам:**
```bash
# 1. Проверить доступность авторитетных серверов
dig NS example.com +short
# → ns1.example.com.

# 2. Опросить авторитетный сервер напрямую
dig @ns1.example.com example.com +noall +header
# → Если status: SERVFAIL — проблема на авторитетном сервере.
# → Если status: NOERROR — проблема в рекурсивном резолвере.

# 3. Проверить DNSSEC-валидацию
dig example.com +dnssec +cd
# → Флаг cd=1 отключает проверку DNSSEC.
# → Если ответ при cd=1 корректен — проблема в DNSSEC-цепочке.

# 4. Проверить другим резолвером
dig @1.1.1.1 example.com +noall +header
dig @8.8.8.8 example.com +noall +header
```

### Ошибка: BADSIG / NOTAUTH (TSIG)

**Симптом:** TSIG-подпись не проходит проверку.

**Причины и решение:**
1.  **Неверный ключ:** проверьте имя ключа и HMAC в конфигурации BIND/клиента.
2.  **Рассинхронизация часов:** TSIG требует синхронизации (fudge=300 сек по умолчанию). Проверьте: `date` на обоих серверах.
3.  **Повреждённое сообщение:** изменение сообщения после подписи (например, промежуточный прокси модифицирует заголовок).
4.  **Повторное использование одного ключа:** для сессий TSIG использует счётчик; повторный MAC с тем же значением отклоняется.

### Ошибка: Неверный размер сообщения (MSG SIZE rcvd: 0)

**Симптом:** `dig` возвращает `MSG SIZE rcvd: 0` при ответе.

**Причина:** сервер возвращает ответ с размером 0 (ошибка конфигурации, повреждение зоны). Проверьте логи сервера: `journalctl -u named -n 50`.

### Проблема: Ответ не содержит ожидаемых записей

**Симптом:** `dig` возвращает `NOERROR` с пустой секцией ANSWER.

**Диагностика:**
```bash
# Проверить, что домен существует (NS-записи)
dig NS example.com +short

# Проверить другие типы записей
dig example.com ANY +short

# Проверить CNAME-цепочку
dig www.example.com CNAME +short

# Если домен содержит только MX, а вы запрашиваете A — ANSWER будет пуст
dig example.com MX +short
# → 10 mail.example.com.  ← вот они
```

## Лучшие практики

*   **Используйте EDNS0** всегда — это современный стандарт. Установите `edns` в конфигурации BIND/CoreDNS.
*   **Для DNSSEC:** устанавливайте `bufsize=4096` в клиенте и `max-udp-size=4096` на сервере для предотвращения TC-обрезки.
*   **Для TSIG:** используйте `hmac-sha256` или `hmac-sha512` (никогда `hmac-md5`). Ротируйте ключи каждые 90 дней.
*   **Для трансфера зон:** используйте TSIG + XoT (Zone Transfer over TLS) для защиты confidentiality и integrity.
*   **Для диагностики:** начинайте с `dig +noall +header +question +answer +stats` — это показывает только релевантные данные.
*   **Для TCP DNS:** увеличивайте таймауты (5–30 сек) по сравнению с UDP (2–5 сек) из-за стоимости TCP-рукопожатия.
*   **Для GeoDNS:** используйте `+client=<subnet>` для проверки ответов для разных регионов.
*   **Избегайте ANY-запросов:** многие серверы ограничивают или блокируютANY (RFC 8482).
