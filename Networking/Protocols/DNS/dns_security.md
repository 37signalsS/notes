# Безопасность DNS

## Определения

**DNSSEC (Domain Name System Security Extensions)** — набор расширений (RFC 4033, 4034, 4035), обеспечивающих аутентификацию источника и целостность данных в DNS с помощью цифровых подписей. Защищает от подмены ответов (Spoofing), но не обеспечивает конфиденциальность (данные передаются в открытом виде).

**DoT (DNS over TLS, RFC 7858)** — шифрование DNS-запросов через TLS на выделенном порту 853. Обеспечивает приватность канала между клиентом и резолвером.

**DoH (DNS over HTTPS, RFC 8484)** — инкапсуляция DNS в HTTPS-трафик (порт 443). Скрывает DNS-активность за стандартным веб-трафиком, что затрудняет фильтрацию и цензуру.

**DoQ (DNS over QUIC, RFC 9250)** — современный стандарт, использующий QUIC (UDP) для шифрования. Устраняет проблему Head-of-Line Blocking (характерную для TCP/TLS) и ускоряет установку соединения за счет 0-RTT.

**ODoH (Oblivious DoH, RFC 9230)** — расширение DoH, использующее промежуточный прокси-сервер для разделения IP-адреса клиента и содержания его DNS-запросов. Резолвер видит запрос, но не знает автора; прокси знает автора, но не видит запрос.

**TSIG (Transaction Signature, RFC 2845)** — механизм аутентификации сообщений DNS на основе общих секретных ключей (Shared Secrets). Используется для защиты трансфера зон (AXFR) и динамических обновлений.

**DANE (DNS-based Authentication of Named Entities, RFC 6698)** — протокол, позволяющий привязывать сертификаты TLS (или их хеши) к доменным именам через DNSSEC, уменьшая зависимость от публичных удостоверяющих центров (CA).

## Базовые концепции

### Векторы атак на DNS

| Угроза | Описание | Метод защиты |
| :--- | :--- | :--- |
| **Cache Poisoning** | Внедрение ложных записей в кэш резолвера (атака Каминского). | DNSSEC, Source Port Randomization. |
| **DNS Amplification** | DDoS-атака: запрос с поддельным IP жертвы к открытому резолверу вызывает огромный ответ. | RRL (Response Rate Limiting), закрытие Open Resolvers. |
| **DNS Water Torture** | Атака на резолвер путем массовых запросов случайных несуществующих поддоменов (`abc123.example.com`). | Агрессивное кэширование NSEC, лимиты на итерации. |
| **DNS Tunneling** | Передача данных (например, команд C2) внутри TXT или других записей для обхода Firewall. | Анализ энтропии имен, DPI, лимиты на длину имен. |
| **DNS Rebinding** | Перехват контроля над локальными сервисами браузером через быструю смену IP в DNS-ответе. | Проверка заголовка `Host`, запрет приватных IP в ответах внешних DNS. |

### Механизмы DNSSEC: Цепочка доверия

DNSSEC не шифрует данные, а подписывает их. Ключевые компоненты:
*   **RRset:** группа записей одного типа (например, все A-записи для `example.com`), которая подписывается как единое целое.
*   **RRSIG (Resource Record Signature):** цифровая подпись для RRset.
*   **DNSKEY:** открытый ключ сервера, используемый для проверки RRSIG.
    *   **ZSK (Zone Signing Key):** ключ для подписи данных зоны. Часто ротируется.
    *   **KSK (Key Signing Key):** ключ для подписи самих ключей DNSKEY. Ротируется редко.
*   **DS (Delegation Signer):** хеш KSK дочерней зоны, размещенный в родительской зоне. Это связующее звено создает **Цепочку доверия (Chain of Trust)** от корня `.` до конечного имени.
*   **NSEC / NSEC3:** записи для подтверждения отсутствия данных. NSEC3 (RFC 5155) использует хеширование для защиты от **Zone Walking** (перебора всех имен в зоне).

### Механизмы повышения приватности

*   **QNAME Minimization (RFC 7816):** резолвер отправляет на каждом этапе иерархии только необходимую часть имени. При запросе `foo.bar.example.com` корень получит только запрос про `.com`.
*   **DNS Cookies (RFC 7873):** защита от IP-спуфинга и некоторых видов DDoS за счет обмена токенами между клиентом и сервером.
*   **Padding (RFC 8467):** выравнивание размера зашифрованных (DoH/DoT) пакетов для предотвращения анализа трафика по размеру сообщений.

## Практические сценарии

### 1. Hardening (укрепление) сервера BIND

Базовые меры защиты для авторитативного сервера:

```conf
# /etc/bind/named.conf.options
options {
    # Запрет рекурсии для публичных серверов (защита от амплификации)
    recursion no;
    allow-query { any; };

    # Ограничение частоты ответов (RRL)
    rate-limit {
        responses-per-second 5;
        window 5;
    };

    # Скрытие версии сервера
    version "none";

    # Поддержка DNSSEC
    dnssec-policy default;
};
```

### 2. Настройка TSIG для трансфера зон

Защита AXFR между Master и Slave серверами:

```conf
# 1. Генерация ключа: tsig-keygen -a HMAC-SHA256 transfer-key
key "transfer-key" {
    algorithm hmac-sha256;
    secret "BASE64_SECRET_STRING==";
};

# 2. Применение в конфигурации зоны
zone "example.com" {
    type master;
    file "/var/lib/bind/db.example.com";
    allow-transfer { key "transfer-key"; };
};
```

### 3. Глубокая валидация DNSSEC через delv

Утилита `delv` автоматически строит цепочку доверия и проверяет подписи.

```bash
# Проверка с явным указанием корневого ключа (обычно встроен)
delv @8.8.8.8 example.com A +rdata

# Результат: ; fully validated означает, что все подписи от корня до хоста верны.
```

### 4. Настройка записи TLSA (DANE)

Пример записи для подтверждения сертификата почтового сервера (Usage 3: Domain Issued Certificate):

```dns
; Формат: _port._proto.name TLSA usage selector matching_type data
_25._tcp.mail.example.com. IN TLSA 3 1 1 (
    E3B0C44298FC1C149AFBF4C8996FB92427AE41E4649B934CA495991B7852B855 )

# 3 - Usage (DANE-EE): сертификат должен совпадать с указанным
# 1 - Selector (SPKI): хешируется только публичный ключ
# 1 - Matching Type (SHA-256): алгоритм хеширования
```
