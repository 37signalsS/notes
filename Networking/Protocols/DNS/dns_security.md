# Безопасность DNS

## Определения

**DNSSEC (Domain Name System Security Extensions)** — набор расширений, обеспечивающих аутентификацию и целостность данных в DNS с помощью цифровых подписей. Защищает от подмены ответов, но не обеспечивает конфиденциальность.

**DoT (DNS over TLS, RFC 7858)** — шифрование DNS-запросов через TLS на порту 853. Обеспечивает приватность канала между клиентом и резолвером.

**DoH (DNS over HTTPS, RFC 8484)** — инкапсуляция DNS в HTTPS-трафик (порт 443). Скрывает DNS-активность за стандартным веб-трафиком.

**DoQ (DNS over QUIC, RFC 9250)** — современный стандарт, использующий QUIC (UDP) для шифрования. Устраняет проблему Head-of-Line Blocking и ускоряет установку соединения.

**ODoH (Oblivious DoH, RFC 9230)** — расширение DoH, использующее прокси-сервер для разделения IP-адреса клиента и его DNS-запросов (резолвер видит запрос, но не знает, кто его отправил).

**Cache Poisoning (Отравление кэша)** — атака по внедрению вредоносных записей в кэш резолвера для перенаправления пользователей на фишинговые ресурсы.

## Базовые концепции

### Векторы атак на DNS

| Угроза | Описание | Метод защиты |
| :--- | :--- | :--- |
| **MitM (Man-in-the-Middle)** | Перехват и модификация запросов в открытом виде (UDP/53). | DoT, DoH, DoQ. |
| **Spoofing / Hijacking** | Ответ поддельным пакетом раньше легитимного сервера. | DNSSEC, DNS Cookies (RFC 7873). |
| **DNS-амплификация** | Использование открытых резолверов для усиления DDoS-атак. | Response Rate Limiting (RRL), закрытие Open Resolvers. |
| **NXDOMAIN Attack** | DDoS через массовые запросы несуществующих имен, перегружающих резолвер. | Кэширование негативных ответов (RFC 2308). |
| **DNS Tunneling** | Передача данных внутри DNS-запросов для обхода Firewall. | Анализ энтропии имен, IDS/IPS. |

### Механизмы повышения приватности

*   **QNAME Minimization (RFC 7816):** резолвер отправляет вышестоящему серверу только минимально необходимую часть имени (например, при запросе `a.b.c.com` корень получает только запрос про `.com`).
*   **DNS Cookies (RFC 7873):** легковесный механизм аутентификации между клиентом и сервером для защиты от IP-спуфинга.
*   **Padding (RFC 8467):** добавление фиктивных байтов в зашифрованные DNS-сообщения, чтобы скрыть реальный размер запроса от анализа трафика.

### Сравнение защищённых протоколов

| Протокол | Транспорт | Порт | Главное преимущество |
| :--- | :--- | :--- | :--- |
| **DNSSEC** | UDP/TCP | 53 | Гарантия подлинности данных от владельца. |
| **DoT** | TCP/TLS | 853 | Чистый зашифрованный канал, легко фильтруется. |
| **DoH** | HTTPS/2 | 443 | Маскировка под веб-трафик, обход цензуры. |
| **DoQ** | QUIC/UDP | 853/443 | Высокая скорость, отсутствие блокировок очереди. |

## Практические сценарии

### 1. Глубокая валидация DNSSEC

Для проверки всей цепочки доверия (от корня `.` до конкретного домена) используется утилита `delv` (DNS Lookup and Validation).

```bash
# Проверка домена с выводом статуса валидации
delv example.com
# -> ; fully validated (данные подлинны)

# Проверка конкретного типа записи с флагом доверия
delv google.com A +rdata
```

### 2. Настройка DNS-over-QUIC (DoQ)

В 2024–2025 годах DoQ становится предпочтительным протоколом для мобильных устройств. Пример настройки в современном резолвере (например, AdGuard Home или Bind 9.20+):

*   **Порт по умолчанию:** 853 (UDP).
*   **Сертификат:** Требуется валидный TLS-сертификат (Let's Encrypt).
*   **Преимущество:** Быстрое восстановление соединения при переключении между Wi-Fi и LTE.

### 3. Проверка записи TLSA (DANE)

DANE позволяет подтвердить валидность SSL-сертификата через DNSSEC, минуя CA.

```bash
# Поиск записи TLSA для SMTP (порт 25)
dig _25._tcp.mail.example.com TLSA

# Расшифровка RDATA: (Usage, Selector, Matching Type, Certificate Association Data)
```

### 4. Настройка QNAME Minimization (BIND/Unbound)

Для повышения приватности пользователей включите минимизацию имен в рекурсивном резолвере:

```conf
# BIND (named.conf.options)
qname-minimization relaxed;

# Unbound (unbound.conf)
qname-minimization: yes
```
