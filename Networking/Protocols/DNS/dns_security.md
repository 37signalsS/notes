# Безопасность DNS

## Определения

**DNSSEC (Domain Name System Security Extensions)** — набор расширений протокола DNS, обеспечивающих проверку подлинности и целостности данных с помощью криптографических подписей. Защищает от атак, связанных с подменой ответов, но не обеспечивает конфиденциальность трафика.

**DoH (DNS over HTTPS)** — протокол передачи DNS-запросов через зашифрованное HTTPS-соединение (порт 443). Позволяет маскировать DNS-трафик под обычный веб-трафик и обходить цензуру/фильтрацию на уровне провайдера.

**DoT (DNS over TLS)** — протокол шифрования DNS-запросов через TLS на выделенном порту (853). Обеспечивает конфиденциальность и целостность трафика между клиентом и резолвером.

**Cache Poisoning (Отравление кэша)** — атака, при которой в кэш DNS-резолвера внедряются поддельные данные. В результате пользователи перенаправляются на вредоносные IP-адреса вместо легитимных.

## Базовые концепции

### Уязвимости стандартного DNS (UDP/53)

| Уязвимость | Описание | Метод защиты |
| :--- | :--- | :--- |
| **Отсутствие шифрования** | Трафик передаётся в открытом виде, доступен для перехвата и анализа (MitM) | DoH, DoT |
| **Отсутствие проверки подлинности** | Клиент не может быть уверен, что ответ пришёл от владельца зоны | DNSSEC |
| **Уязвимость к подмене (Spoofing)** | Возможность отправки поддельного UDP-пакета с ответом раньше легитимного | DNSSEC, случайные порты запроса |
| **Уязвимость к BGP Hijacking** | Злоумышленник может угнать маршрут к DNS-серверу и подменить ответы на уровне всей сети | RPKI, DNSSEC |
| **DNS-амплификация (Amplification)** | Использование открытых резолверов для генерации мощного потока трафика на жертву (DDoS) | Rate Limiting, закрытие открытых рекурсоров |

### 4. Атаки через BGP Hijacking (Кейс MyEtherWallet 2018)

Перехват DNS может происходить не только через уязвимости самого протокола DNS, но и через манипуляции с маршрутизацией в Интернете.

* **Сценарий атаки (2018):** Злоумышленники через BGP Hijack перенаправили часть трафика к DNS-серверам Amazon (Route 53). Когда пользователи запрашивали адрес криптокошелька `myetherwallet.com`, подконтрольные хакерам DNS-серверы возвращали IP-адрес сайта-клона.
* **Результат:** Было украдено около 17 млн долларов в эквиваленте Ethereum.
* **Защита и "Человеческий фактор":** Техническая защита в виде TLS (HTTPS) сработала — браузеры выдавали предупреждение о невалидном сертификате на поддельном сайте. Однако многие пользователи проигнорировали это предупреждение ("Всё равно продолжить"), что привело к потере средств.
* **Вывод:** Самый последний рубеж защиты (TLS) эффективен только до тех пор, пока человек не принимает решение обойти его вручную.

### Сравнение защищённых протоколов

| Протокол | Шифрование | Целостность | Маскировка | Порт |
| :--- | :--- | :--- | :--- | :--- |
| **DNSSEC** | Нет | Да | Нет | 53 |
| **DoT** | Да | Да | Нет | 853 |
| **DoH** | Да | Да | Да | 443 |

**DNSSEC** решает проблему доверия к данным (что мы получили то, что отправил владелец зоны), в то время как **DoH/DoT** решают проблему приватности канала связи (что никто не видит, какие сайты мы посещаем).

## Практические сценарии

### 1. Проверка поддержки DNSSEC доменом

С помощью `dig` можно проверить наличие подписей `RRSIG` и флага `ad` (Authentic Data) в ответе.

```bash
dig +dnssec example.com

# В выводе ищем секцию ANSWER:
# example.com. 3600 IN RRSIG A 13 3 3600 ...
```

Для проверки всей цепочки доверия (Chain of Trust) от корня до домена используется утилита `delv` (DNS Lookup and Validation):

```bash
delv example.com
# Результат: ; fully validated
```

### 2. Настройка DNS-over-TLS (systemd-resolved)

В современных дистрибутивах Linux (Ubuntu 20.04+, RHEL 8+) поддержка DoT включается через `systemd-resolved`.

```ini
# /etc/systemd/resolved.conf
[Resolve]
DNS=1.1.1.1 8.8.8.8
DNSOverTLS=yes
DNSSEC=yes
```

**Применение настроек:**

```bash
sudo systemctl restart systemd-resolved
resolvectl status
```

### 3. Настройка DNSSEC-валидации в BIND

Чтобы сервер BIND проверял подписи при выполнении рекурсивных запросов:

```conf
// /etc/bind/named.conf.options
options {
    dnssec-validation auto;
};
```

Подробнее о настройке BIND и подписи собственных зон: [BIND — расширенные возможности](../../../Linux/Networking/Services/BIND/advanced_topics.md).

### 4. Использование DANE (запись TLSA)

DNSSEC позволяет использовать запись **TLSA**, которая связывает сертификат сервера (или его публичный ключ) напрямую с DNS. Это избавляет от зависимости от центров сертификации (CA).
Пример проверки записи:

```bash
dig _443._tcp.google.com TLSA
```

Подробнее о записях: [Типы DNS-записей](./dns_records.md).
