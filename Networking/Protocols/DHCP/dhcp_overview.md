# DHCP — Обзор протокола

> **Надёжность: 10/10** (SSoT + Web Verification)
> **Актуальность: 2026-07** (Статус: Актуально, проверено)

## Определения

**DHCP (Dynamic Host Configuration Protocol — протокол динамической настройки узла)** — сетевой протокол прикладного уровня (L7), предназначенный для автоматической конфигурации сетевых параметров устройств. DHCP избавляет администраторов от ручного назначения IP-адресов, предотвращая конфликты и минимизируя ошибки конфигурации.

**Основные версии:**
- **DHCPv4 (RFC 2131):** Используется для сетей IPv4. Основан на широковещательных (broadcast) запросах.
- **DHCPv6 (RFC 8415):** Используется для сетей IPv6. Основан на многоадресной рассылке (multicast) и тесно взаимодействует с протоколом ICMPv6.

**Архитектурные компоненты:**
- **DHCP-сервер** — управляет пулом адресов и базой данных аренды (leases).
- **DHCP-клиент** — устройство, запрашивающее настройки (ПК, сервер, IoT-устройство).
- **DHCP Relay Agent (Ретранслятор)** — устройство (обычно маршрутизатор), которое пересылает запросы между разными подсетями. Подробности — [DHCP Relay](./dhcp_relay.md).

**Транспортные порты:**
- **IPv4:** Сервер — `67/UDP`, Клиент — `68/UDP`.
- **IPv6:** Сервер — `547/UDP`, Клиент — `546/UDP`.

## Основные концепции

### DHCPv4: Процесс DORA
Классическое взаимодействие клиента и сервера в IPv4 состоит из четырёх этапов: **D**iscover → **O**ffer → **R**equest → **A**cknowledge.

1. **Discover (Обнаружение):** Клиент отправляет широковещательный пакет (`255.255.255.255`) для поиска серверов.
2. **Offer (Предложение):** Сервер резервирует адрес и отправляет клиенту параметры (IP, шлюз, DNS).
3. **Request (Запрос):** Клиент выбирает одно предложение (обычно первое) и уведомляет сеть о своём выборе.
4. **Acknowledgement (Подтверждение):** Сервер фиксирует аренду и отправляет финальное подтверждение.

### DHCPv6: Процесс SARR
В IPv6 процесс аналогичен, но использует другие термины и механизмы: **S**olicit → **A**dvertise → **R**equest → **R**eply.

1. **Solicit (Поиск):** Клиент ищет серверы через multicast-адрес `ff02::1:2`.
2. **Advertise (Объявление):** Серверы сообщают о своей готовности предоставить адрес.
3. **Request (Запрос):** Клиент запрашивает конкретные параметры у выбранного сервера.
4. **Reply (Ответ):** Сервер подтверждает назначение адреса.

> **Примечание:** В DHCPv6 существует режим **Rapid Commit**, позволяющий сократить обмен до двух сообщений (Solicit → Reply).

### Сравнение DHCPv4 и DHCPv6

| Характеристика | DHCPv4 | DHCPv6 |
| :--- | :--- | :--- |
| **Адресация** | IPv4 (32 бит) | IPv6 (128 бит) |
| **Метод поиска** | Broadcast (`255.255.255.255`) | Multicast (`ff02::1:2`) |
| **Идентификатор клиента** | MAC-адрес (`chaddr`) | DUID (DHCP Unique Identifier) |
| **Настройка шлюза** | Опция 3 (Router) | Через Router Advertisements (RA) |
| **Маска подсети** | Опция 1 (Subnet Mask) | Через Router Advertisements (RA) |

## Ключевые опции DHCP (SRE & DevOps)

Опции позволяют передавать специфические параметры, критически важные для автоматизации инфраструктуры:

- **Option 60 (Vendor Class ID):** Позволяет серверу идентифицировать тип устройства (например, "PXEClient"). Используется для передачи разных настроек разному оборудованию.
- **Option 66/67 (Boot Server / Bootfile):** Основа для **PXE Boot**. Указывают IP TFTP-сервера и имя файла загрузчика (например, `ipxe.efi`). См. [PXE Boot](../../../Linux/Networking/Concepts/pxe_boot.md).
- **Option 82 (Relay Agent Information):** Вставляется коммутатором или ретранслятором. Содержит информацию о физическом порте или VLAN, откуда пришёл запрос. Позволяет выдавать "привязанные" к месту IP.
- **Option 121 (Classless Static Routes):** Позволяет передавать клиенту таблицу статических маршрутов, не меняя основной шлюз по умолчанию.

## Современные реализации: Kea DHCP

Классический **ISC DHCP** (dhcpd) признан устаревшим (EOL в 2022 году). В современной инфраструктуре стандартом стал **Kea DHCP**.

**Преимущества Kea перед ISC DHCP:**
- **Модульность:** Возможность подключать только нужные функции (hooks).
- **API-first:** Полноценный REST API для управления арендой и конфигурацией без перезагрузки.
- **Хранение данных:** Поддержка баз данных (PostgreSQL, MySQL, Cassandra) вместо текстовых файлов.
- **Производительность:** Многопоточная обработка запросов, подходящая для высоконагруженных сетей.

Практические аспекты настройки Kea описаны в [Обзоре современных DHCP-серверов](../../../Linux/Networking/Services/DHCP/isc_dhcp_server_overview.md).

## Практические сценарии

| Сценарий | Рекомендация |
| :--- | :--- |
| **Пользовательские устройства** | Динамическое распределение с умеренным временем аренды (8–24 часа). |
| **Серверы и инфраструктура** | Статическое резервирование (Reservation) на основе MAC/DUID. |
| **Гостевые сети (Wi-Fi)** | Короткое время аренды (30–60 мин) для экономии пула. |
| **Автоматизация Bare-metal** | Комбинация Option 60 и 67 для загрузки образов ОС. |
