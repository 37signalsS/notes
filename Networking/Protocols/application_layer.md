#### DHCP

DHCP (Dynamic Host Configuration Protocol) — протокол динамической настройки узла. Он предназначен для автоматической выдачи устройствам IP-адресов и других сетевых параметров (маска подсети, шлюз по умолчанию).

**Способы назначения IP-адресов**
*   **Статическое назначение:** IP-адрес вручную закрепляется за MAC-адресом конкретного устройства. Используется в небольших сетях для устройств, требующих постоянного адреса.
*   **Динамическое назначение:** DHCP-сервер выдает IP-адрес из пула свободных адресов на определенное время (срок аренды).
*   **Автоматическое назначение:** Похоже на динамическое, но срок аренды не ограничен. IP остается за клиентом, пока он сам от него не откажется.

**Архитектура протокола DHCP**

DHCP использует архитектуру «клиент-сервер».
*   **Сервер DHCP:** Раздает IP-адреса и следит за их уникальностью.
*   **Клиент DHCP:** Любое устройство, запрашивающее сетевые настройки.
*   **Агенты ретрансляции DHCP:** Позволяют DHCP работать через несколько подсетей, пересылая запросы между ними.

**Принцип работы протокола DHCP (DORA)**

1.  **Discovery (DHCPDISCOVER)**: Клиент (еще без IP) отправляет широковещательное сообщение `DHCPDISCOVER` для поиска DHCP-сервера. Этот запрос отправляется на MAC-адрес, состоящий из одних единиц (широковещательный адрес), так как клиент еще не знает MAC-адресов других устройств в сети. Сообщение содержит MAC-адрес клиента и запрос на присвоение IP-адреса.
2.  **Offer (DHCPOFFER)**: DHCP-сервер (или несколько) отвечает сообщением `DHCPOFFER`, предлагая IP-адрес в аренду. Этот ответ также содержит IP-адрес шлюза по умолчанию, IP-адреса одного или нескольких DNS-серверов и маску подсети.
3.  **Request (DHCPREQUEST)**: Клиент выбирает одно из предложений и отправляет `DHCPREQUEST`, сообщая всем, что адрес принят. Этот запрос также широковещательный, чтобы другие DHCP-серверы знали, что их предложения были отклонены.
4.  **Acknowledgement (DHCPACK)**: Сервер подтверждает выделение адреса сообщением `DHCPACK`, передавая также срок аренды и другие настройки. Этот ответ является окончательным подтверждением.

**Другие сообщения DHCP:**
*   `DHCPNAK`: Отказ в аренде IP-адреса.
*   `DHCPINFORM`: Запрос на получение дополнительных настроек сети (когда IP уже есть).
*   `DHCPRELEASE`: Досрочное освобождение IP-адреса клиентом.
*   `DHCPDECLINE`: Сообщение от клиента, если предложенный IP-адрес уже занят.

**Срок аренды IP-адреса**

IP-адрес выдается на определенное время. По умолчанию — 24 часа, но это настраивается. По истечении половины срока аренды клиент пытается его продлить.

#### HTTP (HyperText Transfer Protocol)

**Методы HTTP**

| Метод | Описание |
|---|---|
| **GET** | Запрашивает представление указанного ресурса. Запросы с использованием GET должны только извлекать данные. |
| **POST** | Используется для отправки сущности на указанный ресурс, часто вызывая изменение состояния или побочные эффекты на сервере. |
| **PUT** | Заменяет все текущие представления целевого ресурса данными запроса. |
| **DELETE** | Удаляет указанный ресурс. |
| **PATCH** | Используется для применения частичных модификаций к ресурсу. |
| **HEAD** | Запрашивает ответ, идентичный ответу на GET-запрос, но без тела ответа. |
| **OPTIONS** | Используется для описания параметров связи для целевого ресурса. |
| **CONNECT** | Устанавливает туннель к серверу, идентифицированному по целевому ресурсу. |
| **TRACE** | Выполняет тест обратной связи сообщения по пути к целевому ресурсу. |

| Код | Категория | Описание |

**Сравнение версий HTTP**

| Характеристика | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| :--- | :--- | :--- | :--- | :--- |
| **Транспортный протокол** | TCP | TCP | TCP | **QUIC (UDP)** |
| **Соединения** | Новое на каждый запрос | Постоянные (Keep-Alive) | Одно на домен | Одно на домен |
| **Параллелизм** | Нет | Конвейеризация (Pipelining) | **Мультиплексирование** | **Мультиплексирование** |
| **Блокировка "Head-of-Line"** | Да | Да | На уровне TCP | **Нет** |
| **Сжатие заголовков** | Нет | Нет | **HPACK** | **QPACK** |
| **Инициатива сервера** | Нет | Нет | **Server Push** | Нет (убрано) |
| **Шифрование** | Нет | Опционально | **Обязательно ([TLS](./tls_protocol.md))** | **Обязательно ([TLS](./tls_protocol.md))** |
| **Влияние RTT на установление соединения** | Высокое (много RTT на каждый ресурс) | Высокое (несколько RTT на соединение) | Умеренное (1-2 RTT на соединение) | Низкое (1-RTT или 0-RTT) |

**HTTP/1.0 (1996)**

-   Проблема: Медлительность. На каждый запрос (например, за HTML-файл, картинку, CSS) открывалось новое TCP-соединение, что создавало большие накладные расходы.

**HTTP/1.1 (1997)**

Ключевые улучшения, направленные на решение проблем производительности:

-   Постоянные соединения (Keep-Alive): Позволили браузеру отправлять несколько запросов в рамках одного TCP-соединения, что значительно сократило задержки. Приняв от сервера HTML-документ, браузер находит в нем ссылки на необходимые ресурсы (картинки, скрипты) и запрашивает каждый из них в отдельных HTTP-запросах, используя одно и то же соединение.
-   Конвейеризация (Pipelining): Дала возможность отправлять следующий запрос, не дожидаясь ответа на предыдущий. Однако на практике эта функция работала плохо из-за блокировки "Head-of-Line" (HOL Blocking): если первый запрос в очереди "зависал", все последующие ждали его завершения.
-   Chunked Transfer Encoding: Сервер может передавать данные постепенно, частями (чанками), не зная заранее полного размера ответа. Для этого он указывает заголовок `Transfer-Encoding: chunked` и отправляет чанки, в начале каждого из которых указывается его размер. В конце передается нулевой чанк. Это помогает распределить нагрузку на оперативную память сервера.

**HTTP/2 (2015)**

Революционное обновление, основанное на протоколе SPDY от Google:

-   **Мультиплексирование:** Главное нововведение. Позволяет передавать множество запросов и ответов одновременно в рамках одного TCP-соединения, разбивая их на бинарные "кадры" (frames). Это полностью решило проблему HOL-блокировки (Head-of-Line Blocking) на уровне приложения, так как потеря одного пакета в одном потоке не блокирует другие потоки. Загрузка разных ресурсов может приоритизироваться, а браузер может останавливать отдельные потоки.
-   **Бинарный протокол:** В отличие от текстового HTTP/1.1, стал более эффективным и менее подверженным ошибкам. Заголовки передаются в бинарном виде.
-   **Сжатие заголовков (HPACK):** Значительно уменьшило размер передаваемых заголовков, заменяя повторяющуюся информацию указателями на ранее полученные блоки данных.
-   **Server Push:** Позволял серверу отправлять ресурсы (например, CSS и JS) клиенту еще до того, как он их запросит, предугадывая его потребности. На практике функция оказалась сложной в реализации и не всегда давала выигрыш, поэтому в HTTP/3 от нее отказались.
-   **Обязательное шифрование:** В большинстве браузеров HTTP/2 работает только поверх TLS (HTTPS).

**HTTP/3 (2022)**

Новейший стандарт, который решает последнюю оставшуюся проблему — блокировку Head-of-Line на уровне транспортного протокола (TCP).

-   **Переход на QUIC (UDP):** HTTP/3 работает поверх протокола QUIC, который, в свою очередь, использует UDP. QUIC реализует мультиплексирование на транспортном уровне, надежность соединения, проверку сертификатов и криптографическую защиту. Если один из потоков данных (например, загрузка картинки) теряет пакет, это не влияет на остальные потоки. Другие ресурсы продолжают загружаться без задержек. Это ключевое отличие от HTTP/2, где HOL-блокировка все еще могла возникать на уровне TCP при потере пакетов.
-   **Более быстрое установление соединения:** QUIC объединяет в себе установку соединения и TLS-рукопожатие, что сокращает время на установку безопасного соединения (1-RTT или даже 0-RTT). Это значительно уменьшает задержки при первом подключении.
-   **Улучшенная работа при смене сети (Connection Migration):** Соединение привязывается не к паре IP:порт, а к уникальному идентификатору соединения. Это позволяет, например, без разрыва связи переключаться с Wi-Fi на мобильную сеть, сохраняя активные соединения.
-   **Обновление протокола в пользовательском пространстве:** Поскольку QUIC работает поверх UDP, его реализация находится в пользовательском пространстве, а не в ядре ОС. Это позволяет быстрее внедрять новые функции и исправления, не требуя обновления операционной системы.

**Отправка HTTP-запроса**

После установки безопасного соединения клиент (браузер, `curl`) отправляет HTTP-запрос. Запрос и ответ имеют строго определенную минимальную структуру.

**Минимальный HTTP-запрос**

Для протокола **HTTP/1.1** минимальный запрос должен содержать три элемента:

1.  **Стартовая строка (Request Line):**
    *   **Метод:** `GET` (самый простой).
    *   **URI (путь):** `/` (корень ресурса).
    *   **Версия протокола:** `HTTP/1.1`.
2.  **Заголовок `Host`:** Обязателен в HTTP/1.1. Указывает, к какому сайту на сервере мы обращаемся, так как один IP-адрес может обслуживать множество доменов. Передают дополнительную информацию: User-Agent, Accept-Language, Cookies и т.д.
3.  **Пустая строка (CRLF):** Сигнал о том, что заголовки закончились.

**Минимальный HTTP-ответ**

Минимальный успешный ответ содержит:

1.  **Строка состояния (Status Line):**
    *   **Версия протокола:** `HTTP/1.1`.
    *   **Код состояния:** `200` (успех).
    *   **Пояснение:** `OK`.
2.  **Заголовки:** Для ответа с телом обязателен заголовок `Content-Length`, чтобы клиент знал, сколько байт данных ему нужно прочитать.
3.  **Пустая строка (CRLF):** Разделяет заголовки и тело ответа.
4.  **Тело ответа (Response Body):** Сами данные (могут быть пустыми).
