# RPF и uRPF (Reverse Path Forwarding)

## Определения

**RPF (Reverse Path Forwarding)** — механизм проверки пути к источнику пакета. Используется для предотвращения образования петель в мультикаст-рассылках и для защиты от подмены IP-адресов (IP Spoofing) в одноадресном трафике (**uRPF**).

**uRPF (Unicast Reverse Path Forwarding)** — расширение RPF для обычного одноадресного трафика. Роутер проверяет, является ли интерфейс, на который пришел пакет, «правильным» интерфейсом для достижения адреса отправителя (Source IP).

## Механизм работы

Логика RPF проста: легитимный трафик должен приходить с той стороны, куда роутер отправил бы ответный пакет (согласно таблице маршрутизации).

1. Роутер получает пакет с Source IP `10.0.0.1` на интерфейс `eth1`.
2. Роутер выполняет поиск по таблице маршрутизации (FIB) для адреса `10.0.0.1`.
3. Если маршрут к `10.0.0.1` указывает на интерфейс `eth1` — пакет проходит проверку.
4. Если маршрут указывает на другой интерфейс (или отсутствует) — пакет считается подозрительным и может быть отброшен.

## Режимы работы

| Режим | Название | Логика проверки | Применение |
|:---|:---|:---|:---|
| **Strict Mode** | Строгий | Маршрут к Source IP должен указывать **строго** на тот же интерфейс, на который пришел пакет. | Максимальная безопасность; ломается при асимметричном роутинге. |
| **Loose Mode** | Свободный | Маршрут к Source IP должен **просто существовать** в таблице маршрутизации через любой интерфейс. | Защита от пакетов с несуществующими адресами; допускает асимметрию. |
| **VRF Mode** | — | Аналогичен Loose mode, но проверка выполняется в контексте конкретной таблицы маршрутизации VRF. | Сегментированные сети, MPLS. |

## Почему RPF дропает валидный трафик

Основная причина ложных срабатываний — **асимметричная маршрутизация**.

**Сценарий:**
- Пакет от `10.0.0.1` пришел на `eth1` (например, через резервный аплинк).
- Основной маршрут до `10.0.0.1` в таблице роутера указывает через `eth0`.
- **Результат:** В режиме *Strict* проверка провалится, и легитимный пакет будет отброшен.

Это типичная ситуация для сетей с использованием **ECMP**, нескольких провайдеров (Multihoming) или сложной топологии дата-центров.

## Практическая настройка и диагностика

### Cisco IOS

**Включение uRPF:**
```cisco
interface GigabitEthernet0/0
 # Strict Mode (rx)
 ip verify unicast source reachable-via rx
 
 # Loose Mode (any)
 ip verify unicast source reachable-via any
```

**Диагностика:**
```cisco
# Проверка настроек на интерфейсе
show ip interface Gi0/0 | include verify

# Просмотр счетчиков дропов
show ip traffic | include unicast RPF
show cef interface Gi0/0 | include RPF
```

### Linux (rp_filter)

В Linux RPF настраивается через параметры ядра `sysctl`.

**Значения параметров:**
- `0` — Отключено.
- `1` — Strict mode.
- `2` — Loose mode (рекомендуется для серверов с несколькими интерфейсами/PBR).

**Настройка:**
```bash
# Временная настройка
sudo sysctl -w net.ipv4.conf.eth0.rp_filter=2

# Постоянная настройка (/etc/sysctl.conf)
net.ipv4.conf.all.rp_filter = 2
net.ipv4.conf.default.rp_filter = 2
```

**Диагностика:**
```bash
# Просмотр статистики
cat /proc/net/stat/rt_cache | grep rpf
```
