# RPF и uRPF — проверка обратного пути

## Определения

**RPF (Reverse Path Forwarding)** — механизм проверки пути к источнику пакета. Первоначально разработан для предотвращения петель и дублирования трафика в мультикаст-рассылках, позже адаптирован для защиты от подмены IP-адресов (**IP Spoofing**) в одноадресном трафике.

**uRPF (Unicast Reverse Path Forwarding)** — расширение RPF для одноадресного трафика (Unicast). Маршрутизатор проверяет, является ли интерфейс, на который пришел пакет, «допустимым» интерфейсом для достижения IP-адреса отправителя (Source IP) согласно таблице маршрутизации.

Механизм является практической реализацией рекомендаций **BCP 38** (Network Ingress Filtering).

## Принцип работы

Логика RPF инвертирует процесс обычной маршрутизации: вместо того чтобы смотреть, *куда* отправить пакет, маршрутизатор проверяет, *откуда* он пришел.

1. Пакет с Source IP `S` приходит на интерфейс `EthX`.
2. Маршрутизатор выполняет поиск в таблице маршрутизации (FIB) для адреса `S`.
3. В зависимости от режима, маршрутизатор сверяет найденный выходной интерфейс для `S` с входным интерфейсом `EthX`.
4. Если проверка провалена, пакет отбрасывается на входе.

## Режимы работы uRPF

| Режим | Описание | Применение |
| :--- | :--- | :--- |
| **Strict (Строгий)** | Пакет принимается только если Source IP достижим через тот же интерфейс, на который он пришел (лучший путь). | Абонентские сети (Access), где нет асимметрии. |
| **Loose (Свободный)** | Пакет принимается, если Source IP существует в таблице маршрутизации через **любой** активный интерфейс. | Магистральные сети (Core), ISP-аплинки, защита от спуфинга с несуществующих IP. |
| **Feasible Path** | Пакет принимается, если интерфейс входа является одним из возможных путей к Source IP (проверка всех записей в RIB, а не только лучших в FIB). | Сети с резервированием и ограниченной асимметрией. |

### Нюансы и опции

1. **Default Route (allow-default):** По умолчанию uRPF игнорирует маршрут по умолчанию при проверке. Если опция `allow-default` включена, любой Source IP, попадающий под 0.0.0.0/0, будет считаться валидным (что фактически обесценивает Strict режим, но может быть полезно в Loose).
2. **VRF-Aware uRPF:** В современных сетях проверка uRPF выполняется в контексте конкретного VRF (Virtual Routing and Forwarding). Пакет из VRF 'A' проверяется по таблице маршрутизации VRF 'A'.
3. **ACL Logging:** Маршрутизаторы позволяют логировать пакеты, не прошедшие проверку uRPF, для анализа атак.

## RPF в мультикаст-рассылках


В мультикасте RPF критически важен для работы протоколов **PIM (Protocol Independent Multicast)**.

- **Предотвращение петель:** Мультикаст-пакет принимается и пересылается дальше только в том случае, если он пришел через интерфейс, который является кратчайшим путем к **источнику** (Source) дерева рассылки.
- **Интерфейс RPF:** Это единственный интерфейс, с которого маршрутизатор готов принимать мультикаст от конкретного источника. Если пакет приходит на другой интерфейс — он немедленно отбрасывается (RPF Failure).

## Проблемы и асимметричная маршрутизация

Основная причина проблем с uRPF (особенно в режиме *Strict*) — **асимметричная маршрутизация**.

Типичные среды, где асимметрия является нормой и Strict mode регулярно ломает трафик:
- несколько uplink (multihoming);
- ECMP-балансировка;
- Policy-Based Routing;
- VRF;
- балансировщики нагрузки и firewall-кластеры (трафик входит на один узел, выходит с другого).

**Сценарий возникновения:**
- Трафик от клиента к серверу идет через провайдера А.
- Ответный трафик от сервера к клиенту (или через резервный канал) идет через провайдера Б.
- Если на входе провайдера Б включен uRPF Strict, пакеты будут отброшены, так как маршрут к клиенту у провайдера Б указывает в сторону магистрали, а не на интерфейс с клиентом.

Эквивалент на сервере с двумя интерфейсами: вход `Internet → eth1 → server`, ответ `server → eth0 → Internet`. Маршрутизация формально работает, но обратный путь не совпадает с входящим — strict-проверка отбрасывает входящие пакеты.

**Решение:** использование режима **Loose** или настройка **PBR** для управления обратным путем.

## Практическая настройка

### Cisco IOS (IPv4 и IPv6)

**Для IPv4:**
```cisco
interface GigabitEthernet0/0
 ! Режим Strict
 ip verify unicast source reachable-via rx
 ! Режим Loose
 ip verify unicast source reachable-via any
```

**Для IPv6:**
```cisco
interface GigabitEthernet0/0
 ipv6 verify unicast source reachable-via {rx|any}
```

### Linux (rp_filter)

В Linux поддержка RPF реализована только для IPv4 через параметр `rp_filter`.

**Значения `rp_filter`:**
- `0`: Проверка отключена.
- `1`: **Strict Mode** (RFC 3704).
- `2`: **Loose Mode**. Рекомендуется для сложных топологий, ECMP и PBR.

**Настройка через sysctl:**
```bash
# Включить Loose mode для всех интерфейсов
sudo sysctl -w net.ipv4.conf.all.rp_filter=2
sudo sysctl -w net.ipv4.conf.default.rp_filter=2
```

**Взаимодействие параметров `all`, `default` и интерфейса.** Итоговый режим для конкретного интерфейса определяется как **максимум** из значений `net.ipv4.conf.all.rp_filter` и `net.ipv4.conf.<iface>.rp_filter`. Это уникальная семантика (у многих других sysctl-параметров `all` работает иначе): выставить `all=0` и тем самым отключить проверку на интерфейсе со значением `1` нельзя — strict продолжит действовать. Параметр `net.ipv4.conf.default.rp_filter` применяется только к интерфейсам, созданным **после** его изменения, и не влияет на уже существующие.

Поэтому при диагностике и перед изменением проверять нужно не только `all`, но и каждый задействованный интерфейс:
```bash
sysctl net.ipv4.conf.all.rp_filter
sysctl net.ipv4.conf.default.rp_filter
sysctl net.ipv4.conf.eth0.rp_filter
sysctl net.ipv4.conf.eth1.rp_filter
# → net.ipv4.conf.eth1.rp_filter = 1
```

### uRPF для IPv6 в Linux (nftables)

Для IPv6 в ядре Linux нет прямого аналога `rp_filter`. Проверка реализуется через выражения `fib` в **nftables**.

**Пример реализации Strict mode:**
```bash
# Пакет отбрасывается, если путь к источнику указывает на другой интерфейс
nft add rule inet filter input iifname "eth0" ip6 saddr . iif fib saddr . iif oif != "eth0" drop
```

**Пример реализации Loose mode:**
```bash
# Пакет отбрасывается, если в таблице маршрутизации вообще нет пути к источнику
nft add rule inet filter input fib saddr . iif type != { unicode, unicast } drop
```

## Диагностика

### Cisco
```cisco
# Просмотр счетчиков дропов uRPF
show ip traffic | include unicast RPF
# Проверка настроек интерфейса
show ip interface Gi0/0 | include verify
```

### Linux
Статистика в `/proc/net/stat/rt_cache` устарела. Используйте `nstat` (пакет `iproute2`):

```bash
# Просмотр счетчиков сброшенных пакетов (IPReversePathFilter)
nstat -az | grep -i filter
# → IpReversePathFilter 1234
```

Если пакеты дропаются при использовании PBR или ECMP:
1. Убедитесь, что установлен `rp_filter = 2`.
2. Используйте `ip route get <SOURCE_IP> iif <INCOMING_IFACE>` для эмуляции проверки ядром.
3. Проверьте `journalctl -k` на наличие сообщений "martian source".

**Классический симптом RPF-дропа:** маршрут до сервера есть, интерфейс поднят, `tcpdump -ni eth1 host 10.20.30.50` показывает входящие пакеты — но соединение не устанавливается и приложение ничего не получает. Пакет проходит драйвер и виден на захвате, но отбрасывается ядром до доставки сокету. Порядок проверки:

```bash
# 1. Куда ядро отправит ответ источнику
ip route get 10.20.30.50
# → 10.20.30.50 via 192.0.2.1 dev eth0 (вход был на eth1 — признак асимметрии)

# 2. Фактический входящий трафик на интерфейсе
tcpdump -ni eth1 host 10.20.30.50

# 3. Счетчики ядра и текущий режим фильтра (см. max(all, iface) выше)
nstat -az | grep -i filter
sysctl net.ipv4.conf.eth1.rp_filter
```

Если пакет виден на интерфейсе, но не достигает приложения, а обратный маршрут указывает на другой интерфейс — причина в strict-фильтрации, а не в маршрутизации как таковой.
