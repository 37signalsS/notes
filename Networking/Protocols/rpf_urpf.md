# RPF и uRPF — проверка обратного пути

> **Reliability Score: 10** (SSoT + Verified RFCs + Industry Standard)

## Определения

**RPF (Reverse Path Forwarding)** — механизм проверки пути к источнику пакета. Первоначально разработан для предотвращения петель и дублирования трафика в мультикаст-рассылках, позже адаптирован для защиты от подмены IP-адресов (**IP Spoofing**) в одноадресном трафике.

**uRPF (Unicast Reverse Path Forwarding)** — расширение RPF для одноадресного трафика (Unicast). Маршрутизатор проверяет, является ли интерфейс, на который пришел пакет, «допустимым» интерфейсом для достижения IP-адреса отправителя (Source IP) согласно таблице маршрутизации.

Механизм является практической реализацией рекомендаций **BCP 38** (Network Ingress Filtering).

## Принцип работы

Логика RPF инвертирует процесс обычной маршрутизации: вместо того чтобы смотреть, *куда* отправить пакет, маршрутизатор проверяет, *откуда* он пришел.

1. Пакет с Source IP `S` приходит на интерфейс `EthX`.
2. Маршрутизатор выполняет поиск в таблице маршрутизации (FIB) для адреса `S`.
3. В зависимости от режима, маршрутизатор сверяет найденный выходной интерфейс для `S` с входным интерфейсом `EthX`.
4. Если проверка провалена, пакет отбрасывается на входе.

## Режимы работы uRPF

| Режим | Описание | Применение |
| :--- | :--- | :--- |
| **Strict (Строгий)** | Пакет принимается только если Source IP достижим через тот же интерфейс, на который он пришел. | Абонентские сети (Access), где нет асимметрии. |
| **Loose (Свободный)** | Пакет принимается, если Source IP существует в таблице маршрутизации через **любой** активный интерфейс. | Магистральные сети (Core), ISP-аплинки, защита от атак с несуществующих IP. |
| **Feasible Path** | Пакет принимается, если интерфейс входа является одним из возможных путей к Source IP (проверка всех записей в RIB). | Сети с резервированием и ограниченной асимметрией. |

## RPF в мультикаст-рассылках

В мультикасте RPF критически важен для работы протоколов **PIM (Protocol Independent Multicast)**.

- **Предотвращение петель:** Мультикаст-пакет принимается и пересылается дальше только в том случае, если он пришел через интерфейс, который является кратчайшим путем к **источнику** (Source) дерева рассылки.
- **Интерфейс RPF:** Это единственный интерфейс, с которого маршрутизатор готов принимать мультикаст от конкретного источника. Если пакет приходит на другой интерфейс — он немедленно отбрасывается (RPF Failure).

## Проблемы и асимметричная маршрутизация

Основная причина проблем с uRPF (особенно в режиме *Strict*) — **асимметричная маршрутизация**.

**Сценарий возникновения:**
- Трафик от клиента к серверу идет через провайдера А.
- Ответный трафик от сервера к клиенту (или через резервный канал) идет через провайдера Б.
- Если на входе провайдера Б включен uRPF Strict, пакеты будут отброшены, так как маршрут к клиенту у провайдера Б указывает в сторону магистрали, а не на интерфейс с клиентом.

**Решение:** использование режима **Loose** или настройка **PBR** для управления обратным путем.

## Практическая настройка

### Cisco IOS (IPv4 и IPv6)

**Для IPv4:**
```cisco
interface GigabitEthernet0/0
 ! Режим Strict
 ip verify unicast source reachable-via rx
 ! Режим Loose
 ip verify unicast source reachable-via any
```

**Для IPv6:**
```cisco
interface GigabitEthernet0/0
 ipv6 verify unicast source reachable-via {rx|any}
```

### Linux (rp_filter)

В Linux поддержка RPF реализована только для IPv4 через параметр `rp_filter`. Для IPv6 проверка выполняется средствами `nftables` или `iptables`.

**Значения `rp_filter`:**
- `0`: Проверка отключена.
- `1`: **Strict Mode** (RFC 3704).
- `2`: **Loose Mode**. Рекомендуется для сложных топологий, ECMP и PBR.

**Настройка через sysctl:**
```bash
# Включить Loose mode для всех интерфейсов
sudo sysctl -w net.ipv4.conf.all.rp_filter=2
sudo sysctl -w net.ipv4.conf.default.rp_filter=2

# Постоянная конфигурация в /etc/sysctl.d/99-networking.conf
net.ipv4.conf.all.rp_filter = 2
```

## Диагностика

### Cisco
```cisco
# Просмотр счетчиков дропов uRPF
show ip traffic | include unicast RPF
# Проверка настроек интерфейса
show ip interface Gi0/0 | include verify
```

### Linux
Статистика в `/proc/net/stat/rt_cache` устарела. Используйте `nstat` (пакет `iproute2`):

```bash
# Просмотр счетчиков сброшенных пакетов (IPReversePathFilter)
nstat -az | grep -i filter
# → IpReversePathFilter 1234
```

Если пакеты дропаются, но причина не ясна, используйте `tcpdump` для анализа входящего трафика на соответствие таблице маршрутов:
```bash
ip route get <SOURCE_IP>
# Сравните dev в выводе с интерфейсом, на который фактически пришел пакет.
```
