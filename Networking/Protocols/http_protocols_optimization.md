# Оптимизация производительности HTTP

## 1. Определения

**Оптимизация производительности HTTP** — это процесс выбора и настройки версий протокола HTTP и сопутствующих технологий для минимизации задержек (latency) и ускорения доставки контента. Основная цель — улучшение пользовательского опыта за счет более быстрой загрузки ресурсов.

Для детального сравнения версий протокола (HTTP/1.1, HTTP/2, HTTP/3) и их ключевых особенностей обратитесь к основному документу: **[Протокол HTTP](./http.md)**.

## 2. Основные концепции

Ключевые проблемы, которые решают современные HTTP-протоколы:

### Head-of-Line (HOL) Blocking (Блокировка начала очереди)

Это явление, при котором один медленный или потерянный пакет данных задерживает все последующие пакеты.

* **На уровне приложения (HTTP/1.1):** Браузер может отправить только один запрос за раз по одному TCP-соединению. Следующий запрос ждет ответа на предыдущий. Частично решается созданием нескольких TCP-соединений.
* **На транспортном уровне (TCP):** [HTTP/2](./http.md#http2-2015) решает проблему на уровне приложения с помощью мультиплексирования, но остается уязвимым на уровне транспорта. Потеря одного TCP-пакета останавливает *все* потоки данных (стримы) внутри одного соединения до его повторной передачи.
* **Решение в [HTTP/3](./http.md#http3-2022):** Использование протокола **[QUIC](./http.md#переход-на-quic-udp)** (на базе UDP) решает проблему на транспортном уровне. Потеря пакета в одном стриме не влияет на остальные.

### Затраты на установку соединения

Каждое новое TCP-соединение требует значительных затрат времени (RTT - Round-Trip Time):

1. **TCP Handshake:** 1 RTT для установки TCP-соединения.
2. **TLS Handshake:** 1-2 RTT для установки шифрованного соединения ([подробнее о TLS](./tls.md)).

**Решения:**

* **HTTP Keep-Alive & Connection Pooling:** Переиспользование установленных ("тёплых") TCP+TLS соединений для нескольких последовательных запросов, что амортизирует начальные затраты на их установку.
* **QUIC (HTTP/3):** Объединяет установку соединения и TLS-рукопожатие (TLS 1.3), сокращая процесс до 1 RTT или даже 0-RTT для повторных подключений.

## 3. Практические сценарии и рекомендации

### Сценарий 1: Веб-сайт/API для публичного доступа

**Цель:** Обеспечить быструю загрузку для всех пользователей, включая мобильных.

**Рекомендации:**

1. **Включите HTTP/2 и HTTP/3 на сервере.** Это обеспечит наилучшую производительность для современных браузеров. Для примеров настройки см. **[Конфигурация HTTP/2 и HTTP/3 в Nginx](../../WebServers/Nginx/Performance/nginx_http_versions.md)**.
2. **Активируйте TLS 1.3.** Он быстрее и безопаснее, чем предыдущие версии, и является обязательным для HTTP/3.
3. **Используйте HTTP Keep-Alive.** Настройте разумные таймауты для повторного использования соединений (`keepalive_timeout` в Nginx).

### Сценарий 2: Взаимодействие микросервисов (внутри дата-центра)

**Цель:** Минимизировать задержки при интенсивном обмене данными между сервисами в доверенной, низколатентной сети.

**Рекомендации:**

1. **Используйте пулы соединений (Connection Pooling).** Держите постоянные "тёплые" соединения между сервисами, чтобы избежать затрат на установку новых.
2. **gRPC поверх HTTP/2:** Для внутренней коммуникации gRPC является отличным выбором, так как он эффективно использует мультиплексирование и потоковую передачу данных HTTP/2.
3. **Используйте Circuit Breaker:** Внедряйте паттерн "автоматического выключателя" для быстрого обнаружения недоступных сервисов и предотвращения каскадных сбоев, вместо ожидания таймаута соединения.

### Сценарий 3: Мобильные клиенты

**Цель:** Обеспечить стабильную работу приложения в условиях нестабильной сети (переключение между Wi-Fi и сотовой связью, потери пакетов).

**Рекомендации:**

1. **Предпочитайте HTTP/3.** Его ключевая возможность — **миграция соединений (Connection Migration)** — позволяет сохранить сессию при смене IP-адреса клиента без необходимости переустанавливать соединение.
2. **Настройте более агрессивный Keep-Alive,** если HTTP/3 недоступен, чтобы поддерживать соединение активным во время коротких пауз в сетевой активности.
