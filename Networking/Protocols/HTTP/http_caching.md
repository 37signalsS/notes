# HTTP Кэширование

## Definitions

**HTTP-кэширование** — механизм сохранения копий HTTP-ресурсов (HTML, CSS, JS, изображения, API-ответы) на промежуточных узлах (браузер, прокси, CDN) для ускорения последующих запросов и снижения нагрузки на сервер-источник.

**Ключевые заголовки кэширования:**

- **`Cache-Control`** — основной заголовок, управляющий поведением кэша через директивы (`max-age`, `public`, `private`, `no-cache`, `no-store`).
- **`Expires`** — устаревший заголовок, указывающий точную дату/время устаревания ресурса.
- **`ETag` (Entity Tag)** — уникальный идентификатор версии ресурса (обычно хэш содержимого), используемый для валидации кэша.
- **`Last-Modified`** — дата и время последнего изменения ресурса, используемые для условных запросов.

**Типы кэшей:**

- **Частный кэш (Private Cache):** Кэш браузера пользователя, хранит данные для конкретного клиента.
- **Разделяемый кэш (Shared Cache):** Прокси-сервер, CDN или обратный прокси (например, [Nginx Proxy Cache](../../../WebServers/Nginx/Performance/Caching/proxy_caching.md)), обслуживающий多个 клиентов.

## Basic Concepts

### Кэширование на основе срока годности (Expiration)

Сервер указывает, как долго ресурс можно считать "свежим" (fresh) и использовать из кэша без обращения к источнику.

**Механизмы:**

- **`Expires`:** Указывает точную дату и время устаревания в формате RFC 1123. Недостаток: требует синхронизации времени между клиентом и сервером.
- **`Cache-Control: max-age=<секунды>`:** Современный механизм, задающий время жизни ресурса в секундах с момента получения. Имеет приоритет над `Expires`.

**Пример:**

```http
Cache-Control: max-age=3600
```

Ресурс будет считаться свежим в течение 1 часа (3600 секунд) после получения.

### Кэширование с валидацией (Validation)

Когда срок годности истекает (resource becomes stale), браузер выполняет **условный запрос (Conditional GET)**, чтобы проверить актуальность ресурса на сервере.

**Методы валидации:**

- **На основе ETag:** Сервер отдаёт ресурс с заголовком `ETag: "abc123"`. При повторном запросе клиент отправляет `If-None-Match: "abc123"`. Сервер сравнивает идентификаторы.
- **На основе даты (Last-Modified):** Сервер отдаёт `Last-Modified: Tue, 18 Nov 2025 15:00:00 GMT`. Клиент отправляет `If-Modified-Since: Tue, 18 Nov 2025 15:00:00 GMT`.

**Ответ сервера на условный запрос:**

- **`304 Not Modified`:** Ресурс не изменился. Ответ без тела — экономия трафика. Браузер использует кэшированную версию.
- **`200 OK`:** Ресурс изменился. Сервер присылает полную новую версию с обновлёнными заголовками кэширования.

Подробнее о модели "запрос-ответ" и условных GET-запросах см. в [базовых концепциях HTTP](./http_basics.md) и описании [HTTP-методов](./http_methods.md).

### Директивы `Cache-Control`

| Директива | Описание |
| :--- | :--- |
| `public` | Ответ может кэшироваться любым кэшем, включая разделяемые (прокси, CDN). |
| `private` | Ответ предназначен для одного пользователя, кэшируется только браузером. |
| `no-cache` | Ресурс можно кэшировать, но перед использованием требуется валидация на сервере (условный запрос). |
| `no-store` | Запрещает любое кэширование. Каждый запрос идёт на сервер. |
| `max-age=<сек>` | Время жизни ресурса в секундах. |
| `s-maxage=<сек>` | Переопределяет `max-age` только для разделяемых кэшей (прокси). |
| `immutable` | Указывает, что ресурс не будет изменяться в течение `max-age` (оптимизация для перезагрузок страницы). |

### Стратегии кэширования для разных типов контента

**Статические ресурсы (CSS, JS, изображения с хэш-версионированием):**

```http
Cache-Control: public, max-age=31536000, immutable
```

Кэширование на 1 год с флагом `immutable` — ресурс не изменится, т.к. при обновлении изменится имя файла (хэш).

**Динамический контент (HTML-страницы, API-ответы):**

```http
Cache-Control: private, no-cache
```

Кэширование разрешено, но требуется валидация перед использованием.

**Конфиденциальные данные (банковские операции, персональные данные):**

```http
Cache-Control: no-store
```

Полный запрет кэширования.

## Practical Scenarios

### Сценарий 1: Анализ кэш-заголовков через curl

```bash
curl -I https://example.com/static/app.abc123.js
```

Пример ответа:

```http
HTTP/1.1 200 OK
Content-Type: application/javascript
Cache-Control: public, max-age=31536000, immutable
ETag: "abc123"
Last-Modified: Mon, 01 Apr 2025 10:00:00 GMT
```

Проверка валидации (повторный запрос с If-None-Match):

```bash
curl -I -H 'If-None-Match: "abc123"' https://example.com/static/app.abc123.js
```

Ответ сервера при неизменённом ресурсе:

```http
HTTP/1.1 304 Not Modified
ETag: "abc123"
```

### Сценарий 2: Настройка кэширования статики

Конфигурация заголовков на стороне веб-сервера (например, Nginx) позволяет автоматизировать управление кэшем для тысяч файлов.

Подробная настройка и примеры конфигурации для Nginx приведены в разделе **[Клиентское кэширование в Nginx](../../WebServers/Nginx/Performance/Caching/client_caching.md)**.

### Сценарий 3: Отладка проблем с кэшированием

**Проблема:** Пользователи видят старую версию CSS/JS после деплоя.

**Диагностика:**

1. Проверить заголовки ответа сервера: `curl -I https://example.com/style.css`
2. Убедиться, что `Cache-Control` установлен корректно.
3. Проверить наличие `ETag` или `Last-Modified` для валидации.

**Решение:**

- Добавить версионирование файлов: `style.css?v=1.2.3` или `style.abc123.css` (хэш в имени).
- Для версионированных файлов: `Cache-Control: public, max-age=31536000, immutable`.
- Для HTML: `Cache-Control: private, no-cache` (валидация при каждой загрузке).

### Сценарий 4: Очистка кэша CDN

При использовании CDN (Cloudflare, AWS CloudFront) кэш может храниться на edge-серверах даже после обновления контента на origin-сервере.

**Методы инвалидации:**

1. **Purge (принудительная очистка):** API-запрос к CDN для удаления конкретных URL из кэша.

   ```bash
   curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache" \
     -H "Authorization: Bearer {token}" \
     -H "Content-Type: application/json" \
     --data '{"files":["https://example.com/style.css"]}'
   ```

2. **Версионирование:** Изменение URL ресурса (`/v2/style.css`) автоматически отдаст новый ресурс, т.к. это новая запись в кэше.

3. **TTL-истечение:** Настройка `max-age` определяет максимальное время устаревания до автоматической инвалидации.

## Additional Information

### Роль HTTP-кэширования в DevOps

- **Производительность:** Правильное кэширование снижает время загрузки страниц на 40-60%, уменьшает нагрузку на бэкенды.
- **CDN:** CDN-провайдеры используют `Cache-Control` для определения политик хранения на edge-серверах. Подробнее см. [обзор Edge Computing](../../../Concepts/edge_computing_overview.md).
- **Инвалидация в CI/CD:** При деплое новых версий статических активов необходимо автоматически инвалидировать кэш CDN (через API или изменение URL).
- **Мониторинг:** Ключевые метрики — hit ratio кэша, процент `304 Not Modified` ответов, экономия трафика.

### Связь с общими паттернами кэширования

HTTP-кэширование — частный случай общего механизма кэширования. Паттерны вроде Cache-Aside, Read-Through, политики вытеснения (LRU, LFU) описаны в [общем обзоре кэширования](../../../Concepts/Caching/caching_overview.md).

### Серверное кэширование (Proxy Cache)

Обратные прокси-серверы (Nginx, Varnish) кэшируют ответы бэкендов, снижая нагрузку на приложение. Директива `s-maxage` в `Cache-Control` управляет поведением именно разделяемых кэшей. Конфигурация прокси-кэша в Nginx — в [документации Proxy Cache](../../../WebServers/Nginx/Performance/Caching/proxy_caching.md).

### Best Practices

- **Статика с хэшами:** `max-age=31536000, immutable` (кэшировать на год).
- **Динамический контент:** `no-cache` или `max-age` с коротким TTL (минуты/часы).
- **Конфиденциальные данные:** `no-store` (запрет кэширования).
- **Версионирование:** Изменять URL при обновлении ресурса для гарантированной доставки новой версии.
- **Vary заголовок:** Указывать, от каких параметров зависит ответ (например, `Vary: Accept-Encoding` для кэширования разных кодировок отдельно).
