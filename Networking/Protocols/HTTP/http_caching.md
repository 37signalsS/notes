# HTTP-кэширование: Механизмы и управление

## Определения

**HTTP-кэширование** — механизм сохранения копий HTTP-ресурсов (HTML, CSS (Cascading Style Sheets), JS (JavaScript), изображения, API-ответы) на промежуточных узлах для ускорения последующих запросов и снижения нагрузки на сервер-источник. Современные стандарты кэширования определены в **RFC 9111**.

**Типы кэшей:**

- **Частный кэш (Private Cache / Browser Cache):** Расположен на стороне клиента (браузера), хранит данные только для одного пользователя.
- **Разделяемый кэш (Shared Cache):** Находится между сервером и клиентом (прокси-серверы, CDN (Content Delivery Network)), обслуживает множество пользователей.

**Ключевые механизмы управления:**

- **Свежесть (Freshness):** Определение времени, в течение которого ресурс можно отдавать из кэша без обращения к серверу.
- **Валидация (Validation):** Проверка актуальности ресурса на сервере после истечения срока его свежести.

## Основные концепции

### Управление сроком годности

Сервер указывает, как долго ресурс можно использовать из кэша без обращения к источнику.

- **`Cache-Control: max-age=<секунды>`:** Современный стандарт. Задает время жизни ресурса в секундах с момента получения. Имеет приоритет над устаревшим заголовком `Expires`.
- **`Expires`:** Содержит точную дату и время устаревания. Недостаток: требует синхронизации времени между клиентом и сервером.

### Валидация кэша

Когда срок годности истекает, клиент выполняет **условный запрос**, чтобы проверить, изменился ли ресурс.

1. **По идентификатору (ETag):** Сервер выдает уникальный хэш контента (`ETag: "v1.2"`). При повторном запросе клиент отправляет его в `If-None-Match`.
2. **По дате изменения (Last-Modified):** Сервер указывает время последней правки. Клиент проверяет его через `If-Modified-Since`.

**Результаты валидации:**

- **304 Not Modified:** Ресурс не изменился. Сервер не присылает тело ответа, клиент использует версию из кэша.
- **200 OK:** Ресурс обновился. Сервер присылает новые данные и новые заголовки кэширования.

### Директивы Cache-Control

| Директива | Описание |
| :--- | :--- |
| `public` | Разрешает кэширование любым кэшам (включая CDN и прокси). |
| `private` | Запрещает кэширование на промежуточных узлах (только в браузере). |
| `no-cache` | Кэширование разрешено, но перед использованием **обязательна** валидация на сервере. |
| `no-store` | **Полный запрет** на сохранение ответа в любом кэше. |
| `s-maxage` | Аналог `max-age`, но только для разделяемых кэшей (CDN/Proxy). Переопределяет `max-age` для них. |
| `immutable` | Указывает, что ресурс никогда не изменится (исключает запросы на валидацию). |
| `must-revalidate` | Обязывает кэш проверить статус ресурса после его устаревания и запрещает отдачу старой версии при сбое связи. |
| `stale-while-revalidate` | Позволяет отдавать устаревший ресурс, пока в фоне идет его обновление на сервере. |
| `stale-if-error` | Разрешает отдавать устаревший ресурс, если сервер-источник вернул ошибку (5xx). |

### Заголовок Vary

**`Vary`** — критически важный заголовок, который сообщает кэшу, какие заголовки запроса (помимо URL) должны учитываться при формировании **ключа кэша (Cache Key)**.

**Зачем это нужно:** Если сервер отдает разный контент по одному URL в зависимости от заголовков (например, сжатый или несжатый), кэш должен хранить разные копии.

- **`Vary: Accept-Encoding`:** Кэширует отдельные копии для `gzip`, `br` и `zstd`. Без этого заголовка клиент, не поддерживающий сжатие, может получить из кэша бинарный `gzip`-поток.
- **`Vary: *`:** Фактически отключает кэширование, так как каждый запрос считается уникальным.

### Стратегии кэширования по типам контента

1. **Статика с хэшами в именах (app.abc123.js):**
   `Cache-Control: public, max-age=31536000, immutable` (кэшировать на 1 год).
2. **Динамические HTML-страницы:**
   `Cache-Control: no-cache` или `max-age=0, must-revalidate` (всегда проверять актуальность).
3. **Конфиденциальные API-ответы:**
   `Cache-Control: no-store, private`.

## Практические сценарии

### Анализ заголовков через curl

Для проверки того, как сервер управляет кэшем, используйте `curl -I`:

```bash
curl -I https://example.com/static/style.css
# → Результат:
# HTTP/1.1 200 OK
# Cache-Control: public, max-age=604800
# ETag: "5d8c72a5edda8"
```

Проверка работы валидации (имитация запроса браузера):

```bash
curl -I -H 'If-None-Match: "5d8c72a5edda8"' https://example.com/static/style.css
# → Результат:
# HTTP/1.1 304 Not Modified
```

### Решение проблемы "Кэш не обновляется"

Если после деплоя пользователи видят старую версию сайта, используйте технику **Cache Busting**:

- Добавляйте хэш контента в имя файла: `style.css` → `style.v123.css`.
- При изменении файла изменится его URL (Uniform Resource Locator), что заставит кэш загрузить новую версию, так как старая запись в кэше привязана к старому пути.

### Инвалидация кэша CDN

При использовании CDN (Cloudflare, Akamai) ресурсы хранятся на edge-серверах. Для немедленного обновления контента без смены URL используется **Purge API**:

```bash
# Пример очистки конкретного файла в Cloudflare
curl -X POST "https://api.cloudflare.com/client/v4/zones/{ID}/purge_cache" \
     -H "Authorization: Bearer {TOKEN}" \
     -H "Content-Type: application/json" \
     --data '{"files":["https://example.com/index.html"]}'
```

## Дополнительная информация

> **Надёжность: 10/10** (Соответствие стандарту RFC 9111)
> **Актуальность: 2026-07**

### Роль в DevOps и SRE

- **Снижение нагрузки:** Эффективное кэширование на уровне CDN может снять до 90% трафика с origin-серверов.
- **Производительность:** Снижение задержки (Latency) для конечного пользователя за счет отдачи контента из ближайшего узла.
- **Мониторинг:** Ключевая метрика — **Hit Ratio** (отношение попаданий в кэш к общему числу запросов). Оптимальное значение для статики — выше 95%.
