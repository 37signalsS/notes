# HTTP-кэширование: Механизмы и управление

## Определения

**HTTP-кэширование** — механизм сохранения копий HTTP-ресурсов (HTML, CSS, JS, изображения, API-ответы) на промежуточных узлах или клиенте для исключения повторных загрузок по сети. Современные стандарты кэширования определены в **RFC 9111**.

**Типы кэшей:**

- **Частный кэш (Private Cache):** Кэш на стороне одного клиента (браузер, мобильное приложение). Хранит данные, специфичные для пользователя.
- **Разделяемый кэш (Shared Cache):** Кэш, обслуживающий множество пользователей. Находится между сервером и клиентом.
  - **Proxy Cache:** Локальный прокси в сети организации.
  - **Managed Cache (CDN/Reverse Proxy):** Инфраструктура владельца ресурса (например, [Nginx](../../../WebServers/Nginx/Performance/Caching/proxy_caching.md)).

## Основные концепции

### Механизмы свежести (Freshness)

Кэш определяет, является ли ответ «свежим» (fresh) или «устаревшим» (stale).

- **`Cache-Control: max-age=<N>`:** Основной метод. Ресурс считается свежим в течение N секунд с момента генерации ответа сервером.
- **`Expires`:** Устаревший заголовок с абсолютной датой. Игнорируется, если есть `max-age`.
- **Заголовок `Age`:** Содержит время в секундах, которое ресурс уже провел в разделяемых кэшах. Клиент вычисляет реальную свежесть как `max-age - Age`.
- **Эвристическое кэширование (Heuristic Caching):** Если сервер не прислал явных инструкций (`Cache-Control` или `Expires`), но указал `Last-Modified`, кэш имеет право сохранить ресурс на время, равное 10% от интервала между датой генерации ответа и датой последнего изменения (согласно RFC 9111).

### Валидация кэша

Когда ресурс устаревает, кэш обязан проверить его актуальность на сервере через **условный запрос** (Conditional Request).

#### Типы валидаторов

1.  **Strong Validator (Сильный):** Гарантирует побайтовое совпадение контента.
    - **`ETag` (Entity Tag):** Уникальный идентификатор версии (хэш). Пример: `ETag: "68689769"`.
2.  **Weak Validator (Слабый):** Гарантирует семантическую эквивалентность, но не гарантирует побайтовое совпадение.
    - **Weak ETag:** Имеет префикс `W/`. Пример: `ETag: W/"v1.0"`. Используется, когда микро-изменения (например, дата в футере) не должны инвалидировать кэш.
    - **`Last-Modified`:** Дата изменения. Считается слабым валидатором, так как имеет точность до секунды.

**Результаты валидации:**

- **304 Not Modified:** Ресурс актуален. Сервер обновляет только заголовки (метаданные), тело не передается.
- **200 OK:** Ресурс изменился. Передается новое тело и новые валидаторы.

### Директивы Cache-Control

Директивы могут передаваться как сервером (в ответе), так и клиентом (в запросе).

#### Директивы ответа (Server to Client)

| Директива | Описание |
| :--- | :--- |
| `public` | Разрешает кэширование любым кэшам (включая CDN и прокси). |
| `private` | Ресурс только для частного кэша (браузера). Разделяемые кэши обязаны игнорировать ответ. |
| `no-cache` | Кэширование разрешено, но **обязательна** валидация на сервере перед каждым использованием. |
| `no-store` | **Полный запрет** на сохранение. Кэш не должен записывать данные на диск или в память. |
| `s-maxage` | Аналог `max-age`, но только для разделяемых кэшей (CDN/Proxy). |
| `proxy-revalidate` | Аналог `must-revalidate`, но только для разделяемых кэшей. |
| `immutable` | Ресурс не изменится до истечения `max-age`. Исключает условные запросы при перезагрузке страницы. |
| `stale-while-revalidate` | Позволяет отдать `stale` ответ, пока в фоне идет запрос на обновление (фоновая валидация). |
| `stale-if-error` | Разрешает отдавать устаревший ресурс, если сервер-источник вернул ошибку (5xx). |

#### Директивы запроса (Client to Server)

Клиент может требовать от кэша определенного поведения:
- **`no-cache`:** Требовать от кэша обязательной валидации ресурса на origin-сервере.
- **`max-age=0`:** Заставить кэш выполнить валидацию (аналог нажатия F5 в браузере).
- **`only-if-cached`:** Клиент согласен получить ответ только из кэша. Если данных в кэше нет — вернуть `504 Gateway Timeout`.

### Заголовок Vary и нормализация ключа кэша

**Cache Key (Ключ кэша)** — это уникальная строка, по которой кэш находит ресурс. По умолчанию это `Method + URI`.

Заголовок **`Vary`** добавляет выбранные заголовки запроса в ключ кэша.
- **`Vary: Accept-Encoding`:** Кэш хранит разные версии для `gzip`, `br` и несжатого контента.
- **Проблема:** Если клиенты присылают `Accept-Encoding: gzip, deflate` и `Accept-Encoding: deflate, gzip`, кэш может посчитать их разными ключами.
- **Решение:** Промежуточные узлы (Nginx, CDN) выполняют **нормализацию** (приводят заголовки к единому виду) перед поиском в кэше.
- **`Vary: *`:** Фактически отключает кэширование, так как каждый запрос считается уникальным.

### Кэширование и Range-запросы

HTTP позволяет запрашивать части ресурса (`Range: bytes=0-1023`).

- Кэш может сохранять частичные ответы (`206 Partial Content`).
- Если клиент запрашивает полный ресурс, а в кэше есть только части, кэш может докачать недостающее или склеить части (зависит от реализации).
- Для корректного кэширования частей критически важен `ETag` или `Last-Modified`, чтобы гарантировать, что части принадлежат одной версии файла.

### Стратегии кэширования по типам контента

1.  **Статика с Fingerprinting (имя файла меняется при изменении):**
    `Cache-Control: public, max-age=31536000, immutable`.
2.  **Динамический контент (частые изменения):**
    `Cache-Control: no-cache` (сохранять, но всегда проверять).
3.  **Конфиденциальные данные (Личный кабинет):**
    `Cache-Control: private, no-store`.
4.  **Микросервисные API (кратковременное кэширование):**
    `Cache-Control: public, s-maxage=1, stale-while-revalidate=5`.

## Практические сценарии

### Анализ жизненного цикла кэша через curl

```bash
# Первый запрос - промах (MISS)
curl -v -I https://example.com/api/data
# < X-Cache: MISS
# < Age: 0

# Второй запрос через 10 секунд - попадание (HIT)
curl -v -I https://example.com/api/data
# < X-Cache: HIT
# < Age: 10
```

### Решение проблемы "Double Caching"

Иногда браузер и CDN кэшируют ресурс с одинаковым `max-age`. Это может привести к тому, что обновление на CDN не дойдет до пользователя, так как браузер не делает запрос.

**Решение:** Устанавливать меньший `max-age` для браузера и больший `s-maxage` для CDN.
`Cache-Control: public, max-age=600, s-maxage=3600` (10 мин в браузере, 1 час на CDN).

### Инвалидация кэша CDN

При использовании CDN (Cloudflare, Akamai) ресурсы хранятся на edge-серверах. Для немедленного обновления контента без смены URL используется **Purge API**:

```bash
# Пример очистки конкретного файла в Cloudflare
curl -X POST "https://api.cloudflare.com/client/v4/zones/{ID}/purge_cache" \
     -H "Authorization: Bearer {TOKEN}" \
     -H "Content-Type: application/json" \
     --data '{"files":["https://example.com/index.html"]}'
```

## Дополнительная информация

### Роль в DevOps и SRE

- **Offload Ratio:** Процент запросов, обработанных кэшем. Рост Offload напрямую снижает затраты на облачные вычисления и БД.
- **Cache Purging:** Процесс удаления данных из разделяемых кэшей. Должен быть интегрирован в CI/CD пайплайн (например, очистка путей после деплоя фронтенда).
- **Сжатие и кэш:** Всегда используйте `Vary: Accept-Encoding`, чтобы избежать отдачи сжатого контента клиентам, которые его не понимают (и наоборот).
