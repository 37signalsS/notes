# HTTP-кэширование: Механизмы и управление

## Определения

**HTTP-кэширование** — механизм сохранения копий HTTP-ресурсов (HTML, CSS, JS, изображения, API-ответы) на промежуточных узлах или клиенте для исключения повторных загрузок по сети. Современные стандарты кэширования определены в **RFC 9111**.

**Типы кэшей:**

- **Частный кэш (Private Cache):** Кэш на стороне одного клиента (браузер, мобильное приложение). Хранит данные, специфичные для пользователя.
- **Разделяемый кэш (Shared Cache):** Кэш, обслуживающий множество пользователей. Находится между сервером и клиентом.
  - **Proxy Cache:** Локальный прокси в сети организации.
  - **Managed Cache (CDN/Reverse Proxy):** Инфраструктура владельца ресурса (например, [Nginx](../../../WebServers/Nginx/Performance/Caching/proxy_caching.md)).

## Основные концепции

### Механизмы свежести (Freshness)

Кэш определяет, является ли ответ «свежим» (fresh) или «устаревшим» (stale).

- **`Cache-Control: max-age=<N>`:** Основной метод. Ресурс считается свежим в течение N секунд с момента генерации ответа сервером.
- **`Expires`:** Устаревший заголовок с абсолютной датой. Игнорируется, если есть `max-age`.
- **Заголовок `Age`:** Содержит время в секундах, которое ресурс уже провел в разделяемых кэшах. Клиент вычисляет реальную свежесть как `max-age - Age`.
- **Эвристическое кэширование (Heuristic Caching):** Если сервер не прислал явных инструкций (`Cache-Control` или `Expires`), но указал `Last-Modified`, кэш имеет право сохранить ресурс на время, равное 10% от интервала между датой генерации ответа и датой последнего изменения (согласно RFC 9111).

### Валидация кэша

Когда ресурс устаревает, кэш обязан проверить его актуальность на сервере через **условный запрос** (Conditional Request).

#### Типы валидаторов

1.  **Strong Validator (Сильный):** Гарантирует побайтовое совпадение контента.
    - **`ETag` (Entity Tag):** Уникальный идентификатор версии (хэш). Пример: `ETag: "68689769"`.
2.  **Weak Validator (Слабый):** Гарантирует семантическую эквивалентность, но не гарантирует побайтовое совпадение.
    - **Weak ETag:** Имеет префикс `W/`. Пример: `ETag: W/"v1.0"`. Используется, когда микро-изменения (например, дата в футере) не должны инвалидировать кэш.
    - **`Last-Modified`:** Дата изменения. Считается слабым валидатором, так как имеет точность до секунды.

**Результаты валидации:**

- **304 Not Modified:** Ресурс актуален. Сервер обновляет только заголовки (метаданные), тело не передается.
- **200 OK:** Ресурс изменился. Передается новое тело и новые валидаторы.

### Директивы Cache-Control

Директивы могут передаваться как сервером (в ответе), так и клиентом (в запросе).

#### Директивы ответа (Server to Client)

| Директива | Описание |
| :--- | :--- |
| `public` | Разрешает кэширование любым кэшам (включая CDN и прокси). |
| `private` | Ресурс только для частного кэша (браузера). Разделяемые кэши обязаны игнорировать ответ. |
| `no-cache` | Кэширование разрешено, но **обязательна** валидация на сервере перед каждым использованием. |
| `no-store` | **Полный запрет** на сохранение. Кэш не должен записывать данные на диск или в память. |
| `s-maxage` | Аналог `max-age`, но только для разделяемых кэшей (CDN/Proxy). |
| `proxy-revalidate` | Аналог `must-revalidate`, но только для разделяемых кэшей. |
| `immutable` | Ресурс не изменится до истечения `max-age`. Исключает условные запросы при перезагрузке страницы. |
| `stale-while-revalidate` | Позволяет отдать `stale` ответ, пока в фоне идет запрос на обновление (фоновая валидация). |
| `stale-if-error` | Разрешает отдавать устаревший ресурс, если сервер-источник вернул ошибку (5xx). |

#### Директивы запроса (Client to Server)

Клиент может требовать от кэша определенного поведения:
- **`no-cache`:** Требовать от кэша обязательной валидации ресурса на origin-сервере.
- **`max-age=0`:** Заставить кэш выполнить валидацию (аналог нажатия F5 в браузере).
- **`only-if-cached`:** Клиент согласен получить ответ только из кэша. Если данных в кэше нет — вернуть `504 Gateway Timeout`.

### Заголовок Vary и нормализация ключа кэша

**Cache Key (Ключ кэша)** — это уникальная строка, по которой кэш находит ресурс. По умолчанию это `Method + URI`.

Заголовок **`Vary`** добавляет выбранные заголовки запроса в ключ кэша.
- **`Vary: Accept-Encoding`:** Кэш хранит разные версии для `gzip`, `br` и несжатого контента.
- **Проблема:** Если клиенты присылают `Accept-Encoding: gzip, deflate` и `Accept-Encoding: deflate, gzip`, кэш может посчитать их разными ключами.
- **Решение:** Промежуточные узлы (Nginx, CDN) выполняют **нормализацию** (приводят заголовки к единому виду) перед поиском в кэше.
- **`Vary: *`:** Фактически отключает кэширование, так как каждый запрос считается уникальным.

### Кэширование и Range-запросы

HTTP позволяет запрашивать части ресурса (`Range: bytes=0-1023`).

- Кэш может сохранять частичные ответы (`206 Partial Content`).
- Если клиент запрашивает полный ресурс, а в кэше есть только части, кэш может докачать недостающее или склеить части (зависит от реализации).
- Для корректного кэширования частей критически важен `ETag` или `Last-Modified`, чтобы гарантировать, что части принадлежат одной версии файла.

### Стратегии кэширования по типам контента

1.  **Статика с Fingerprinting (имя файла меняется при изменении):**
    `Cache-Control: public, max-age=31536000, immutable`.
2.  **Динамический контент (частые изменения):**
    `Cache-Control: no-cache` (сохранять, но всегда проверять).
3.  **Конфиденциальные данные (Личный кабинет):**
    `Cache-Control: private, no-store`.
4.  **Микросервисные API (кратковременное кэширование):**
     `Cache-Control: public, s-maxage=1, stale-while-revalidate=5`.

### Кэширование в разных версиях HTTP

**Почему поведение меняется от версии к версии:** HTTP/1.1 использует текстовые заголовки и открывает отдельное TCP-соединение на каждый ресурс (или Keep-Alive), поэтому кэш должен аккуратно управлять соединениями и валидацией. HTTP/2 вводит бинарный фрейминг и мультиплексирование, что позволяет эффективнее агрегировать валидационные запросы, но сохраняет семантику кэширования HTTP/1.1. HTTP/3 (QUIC) переносит кэширование на уровень транспортных соединений (0-RTT), что ускоряет повторные запросы, но заголовки кэширования остаются теми же.

- **HTTP/1.1:** Один запрос на соединение (или pipeline с HOL-блокировкой). Кэш критичен для снижения количества TCP-handshake.
- **HTTP/2:** Мультиплексирование позволяет валидировать несколько ресурсов в одном соединении. HPACK сжимает заголовки, но семантика `Cache-Control` не меняется.
- **HTTP/3 (QUIC):** Поддержка 0-RTT позволяет клиенту отправлять данные сразу при установке соединения, что ускоряет условные запросы. QPACK управляет заголовками, но правила кэширования идентичны RFC 9111.

### Заголовок Cache-Status (RFC 9211) и CDN-Cache-Control (RFC 9213)

**Cache-Status** — стандартный заголовок ответа, заменяющий проприетарные `X-Cache`/`X-Cache-Status`. Обеспечивает детальную прозрачность обработки запроса кэшем:

```http
Cache-Status: Cloudflare-CDN; hit; ttl=345; key=a1b2c3d4; detail=mismatch-encoding
```

**Компоненты:**
- **hit** — объект найден в кэше, TTL не истёк.
- **miss** — объект не найден, запрос ушёл к Origin.
- **stale** — TTL истёк, выполняется валидация (или отдаётся устаревший контент по `stale-while-revalidate`).
- **expired** — объект помечен как удалённый.
- **bypass** — кэширование пропущено (Edge Rule, `no-cache`).
- **revalidated** — валидация на Origin вернула `304 Not Modified`.
- **error** — ошибка обработки кэшем.
- **forward** — запрос проксируется без кэширования.

**CDN-Cache-Control** (RFC 9213) позволяет задавать политики специально для CDN, не затрагивая браузер. Это критично, когда `s-maxage` недостаточно для разделения TTL:

```http
CDN-Cache-Control: s-maxage=86400, stale-while-revalidate=3600, stale-if-error=86400
Cache-Control: no-cache
```

### Негативное кэширование (Negative Caching)

Кэширование ответов с ошибками (404, 500, 503) на короткий срок. Защищает Origin от DoS-атак через запросы к несуществующим или временно недоступным ресурсам.

**Механизм:**
1. Клиент запрашивает несуществующий URL.
2. Origin возвращает `404 Not Found`.
3. Разделяемый кэш сохраняет ответ на время `negative-ttl` (например, 10 секунд).
4. Последующие запросы к тому же URL за этот период обслуживаются из кэша.

**Важно:** Negative Caching работает только для разделяемых кэшей (CDN, прокси). Браузеры обычно не кэшируют 404.

### Cache Busting и инвалидация

**Почему Cache Busting предпочтительнее Purge:** Инвалидация через API (Purge) требует времени на распространение изменений по всему кластеру CDN (от 200 мс до 15 минут). Cache Busting (изменение URL) исключает необходимость в инвалидации — старый URL остаётся в кэше, но новые запросы идут по новому URL.

**Методы:**
- **Hash-имя файла:** `style.abc123.css` (Webpack, Vite, esbuild).
- **Query-параметр версии:** `/api/data?v=2.1.0` (для API без сборщика).
- **Directory-based:** `/v2/static/style.css` (мажорные версии API).

### Типичные антипаттерны (протокольный уровень)

- **Cache Stampede (Thundering Herd):** При истечении TTL популярного объекта множество клиентских кэшей одновременно валидируют его на Origin. Решается через джиттер TTL и `stale-while-revalidate`.
- **Cache Avalanche:** Одновременный сброс кэша у большого числа объектов (например, после деплоя). Решается через Jitter TTL.
- **Cache Penetration:** Запросы к уникальным URL, которые никогда не кэшируются. Решается через Negative Caching и Rate Limiting на уровне CDN/Proxy.

### Партиционирование кэша браузера (Cache Partitioning)

С 2024–2026 годов браузеры (Chrome, Safari, Firefox) используют **двойной ключ** кэширования: `Top-level Site + Resource URL`. Это означает, что общие библиотеки с публичных CDN (например, jQuery) кэшируются отдельно для каждого сайта. Преимущество использования общих CDN для кэширования практически аннулировано. Рекомендация: размещать статику на собственном домене с `immutable` и fingerprinting.

## Практические сценарии

### Сценарий 1: Анализ жизненного цикла кэша через curl

```bash
# Первый запрос — промах (MISS)
curl -v -I https://example.com/api/data
# < X-Cache: MISS
# < Age: 0
# < cache-control: public, max-age=3600

# Второй запрос через 10 секунд — попадание (HIT)
curl -v -I https://example.com/api/data
# < X-Cache: HIT
# < Age: 10
# < cache-control: public, max-age=3600
```

**Валидация:**
- Первый запрос должен вернуть `Age: 0` и статус MISS (или пустой `Cache-Status: miss`).
- Второй запрос должен показать `Age: 10` (или другой возраст) и HIT.
- Если `Age` превышает `max-age`, кэш считается устаревшим (stale).

### Сценарий 2: Проверка условного запроса (Conditional Request)

Когда ресурс устаревает, клиент отправляет валидатор для проверки актуальности.

```bash
# Шаг 1: Получить ETag и max-age
ETAG=$(curl -sI https://example.com/api/data | grep -i etag | tr -d '\r' | awk '{print $2}')
MAX_AGE=$(curl -sI https://example.com/api/data | grep -i cache-control | sed 's/.*max-age=\([0-9]*\).*/\1/')
echo "ETag: $ETAG"
echo "max-age: $MAX_AGE"
# → ETag: "6868976968.0"
# → max-age: 3600

# Шаг 2: Отправить условный запрос (имитация кэша)
curl -sI -H "If-None-Match: $ETAG" https://example.com/api/data
# → HTTP/1.1 304 Not Modified  (ресурс не изменился)
# ИЛИ
# → HTTP/1.1 200 OK            (ресурс изменился, передано новое тело)
```

**Валидация:**
- При `304` тело ответа отсутствует, обновляются только заголовки (новый `ETag`/`Age`).
- При `200` передаётся новое тело и новые валидаторы.

### Сценарий 3: Валидация заголовка Vary

```bash
# Запрос без указания Accept-Encoding
curl -sI https://example.com/style.css | grep -i vary
# → vary: Accept-Encoding

# Запрос с gzip
curl -sI -H "Accept-Encoding: gzip" https://example.com/style.css | grep -i "content-encoding\|vary"
# → content-encoding: gzip
# → vary: Accept-Encoding

# Запрос с brotli
curl -sI -H "Accept-Encoding: br" https://example.com/style.css | grep -i "content-encoding\|vary"
# → content-encoding: br
```

**Валидация:**
- Ответы с разным `Content-Encoding` должны иметь одинаковый `Vary: Accept-Encoding`.
- Без `Vary` кэш может отдать сжатый контент клиенту, который его не поддерживает.

### Сценарий 4: Проверка реального TTL и возраста объекта

```bash
# Получение Age и Cache-Control
curl -sI https://example.com/style.css | grep -iE "age|cache-control"
# → age: 300
# → cache-control: public, max-age=3600

# Вычисление реального TTL
# Real TTL = max-age - Age = 3600 - 300 = 3300 сек
```

**Валидация:**
- Если `Age` > `max-age` — объект устарел (stale), кэш должен выполнить валидацию.
- Отрицательный или отсутствующий `Age` означает MISS или прямой ответ от Origin.

### Сценарий 5: Решение проблемы "Double Caching"

Иногда браузер и CDN кэшируют ресурс с одинаковым `max-age`. Это может привести к тому, что обновление на CDN не дойдёт до пользователя, так как браузер не делает запрос.

**Решение:** Устанавливать меньший `max-age` для браузера и больший `s-maxage` для CDN.

```http
Cache-Control: public, max-age=600, s-maxage=3600
# Браузер: 10 минут
# CDN/Proxy: 1 час
```

**Валидация:**
```bash
# Проверка заголовков
curl -sI https://cdn.example.com/resource | grep -i cache-control
# → cache-control: public, max-age=600, s-maxage=3600

# Проверка Age на CDN
curl -sI https://cdn.example.com/resource | grep -i age
# → age: 1800
```

### Сценарий 6: Инвалидация кэша CDN

При использовании CDN (Cloudflare, Akamai) ресурсы хранятся на edge-серверах. Для немедленного обновления контента без смены URL используется **Purge API**:

```bash
# Пример очистки конкретного файла в Cloudflare
curl -X POST "https://api.cloudflare.com/client/v4/zones/{ID}/purge_cache" \
     -H "Authorization: Bearer {TOKEN}" \
     -H "Content-Type: application/json" \
     --data '{"files":["https://example.com/index.html"]}'
# → {"success":true,"errors":[],"messages":[],"result":{"id":"..."}}
```

**Валидация:**
- Убедитесь, что ответ содержит `"success": true`.
- Проверьте статус через `curl -sI` — `Age` должен сброситься.

### Сценарий 7: Очистка кэша по Surrogate Keys (тегам)

Для массовой инвалидации (E-commerce, CMS) используются теги:

```bash
# Cloudflare: очистка по тегам
curl -X POST "https://api.cloudflare.com/client/v4/zones/{ID}/purge_cache" \
     -H "Authorization: Bearer {TOKEN}" \
     -H "Content-Type: application/json" \
     --data '{"tags":["product_laptops","brand_apple"]}'
# → {"success":true,"errors":[],"messages":[],"result":{"id":"..."}}
```

**Валидация:**
- Запрос с Surrogate-Key должен вернуть `Cache-Status: miss` после purge (если CDN поддерживает Cache-Status).
- Для безSurrogate-Key CDN проверьте `Age: 0` на нескольких URL с одинаковыми тегами.

## Типичные проблемы и диагностика

### Проблемы с кэшированием

| Проблема | Симптом | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Низкий Cache Hit Ratio** | Много `MISS` в `Cache-Status`, высокая нагрузка на Origin | `curl -sI URL \| grep -iE "cache-status\|age"` | Увеличить TTL, включить `stale-while-revalidate`, проверить Cache Key и нормализацию `Vary` |
| **Stale Content** | Пользователи видят устаревший контент | `curl -sI URL \| grep age` — возраст превышает `max-age` | Уменьшить TTL, настроить SWR, использовать Purge API |
| **Thundering Herd** | Всплеск нагрузки на Origin после истечения TTL | Мониторинг Origin (CPU, RPS) | Включить `stale-while-revalidate`, добавить Jitter TTL, использовать Cache Lock на прокси |
| **Incorrect Cache Key** | Один URL кэшируется под разными ключами | Проверить заголовок `Vary` и параметры запроса | Нормализовать query-параметры, унифицировать `Accept-Encoding` |
| **Cache Poisoning** | CDN отдает вредоносный контент | Проверить HTTP-заголовки ответа | Включить Strict URL Normalization, исключить нерелевантные заголовки из Cache Key |
| **Double Caching** | Обновление на CDN не доходит до браузера | Сравнить `max-age` в браузере и CDN | Использовать `s-maxage` для CDN, `max-age` для браузера |

### Проблемы с инвалидацией

| Проблема | Симптом | Причина | Решение |
| :--- | :--- | :--- | :--- |
| **Purge не работает** | Контент не обновляется после API-запроса | Неправильный URL, таймаут, проблемы с API | Проверить статус API-ответа, URL, повторить запрос |
| **Медленная инвалидация** | Контент обновляется через минуты | Провайдер не гарантирует <200 мс (CloudFront 5–15 мин) | Перейти на Cloudflare/Fastly или использовать Cache Busting |
| **Инвалидация не доходит до всех PoP** | Часть пользователей видит старый контент | Локальная проблема PoP, маршрутизация | Проверить географию PoP, повторить Purge |
| **Wildcard Purge перегружает Origin** | Высокая нагрузка после массовой очистки | Все PoP одновременно запрашивают контент | Использовать Tiered Caching, Staggered Purge |

### Проблемы с валидацией

| Проблема | Симптом | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Слабый ETag при сжатии** | `ETag` имеет префикс `W/` | `curl -sI URL \| grep -i etag` | Использовать статическое сжатие (precompressed), чтобы сохранить strong ETag |
| **304 без тела** | Клиент ожидает тело, получает пустой ответ | `curl -v URL` показывает `304` с `Content-Length: 0` | Это нормальное поведение — клиент должен использовать локальную копию |
| **Last-Modified не точный** | Частые изменения ресурса (>1 раз/сек) | `curl -sI URL \| grep -i last-modified` | Перейти на `ETag` как на primary валидатор |

## Граничные случаи и ограничения

1. **Cache Partitioning:** Браузеры используют двойной ключ (`Top-level Site + URL`). Общие CDN-библиотеки кэшируются отдельно для каждого сайта. Для внутренней статики используйте fingerprinting + `immutable`.
2. **URI Length:** Очень длинные query-параметры могут вызывать `414 URI Too Long` и нарушать нормализацию Cache Key у CDN.
3. **Заголовок Host:** В HTTP/1.1 `Host` обязателен. При использовании CDN убедитесь, что он корректно передаётся на Origin.
4. **Cookie размером >4КБ:** Браузеры ограничивают размер одной cookie (~4КБ) и количество на домен (~180). Для хранения больших данных используйте `localStorage` или серверные сессии.
5. **Метод CONNECT:** Используется для туннелирования. При кэшировании через CDN убедитесь, что туннелируемый трафик не попадает в кэш.
6. **Партиционирование кэша (Cache Partitioning):** В Chrome 111+ и Safari 16.4+ кэш изолирован по top-level site. Это снижает эффективность общих CDN, но повышает безопасность.
7. **Слабые ETag при динамическом сжатии:** Nginx/Angie автоматически превращают сильный ETag в слабый (`W/`) при `gzip on`. Для сохранения strong ETag используйте precompressed файлы.
8. **HTTP/3 и 0-RTT:** Кэш может отдавать устаревший контент при повторном соединении 0-RTT, если сервер не валидировал состояние. Используйте `max-age` с запасом.
9. **Range-запросы и кэш:** При кэшировании частичных ответов (`206 Partial Content`) критически важно использовать `ETag` или `Last-Modified`, чтобы гарантировать, что части принадлежат одной версии файла.
10. **Vary: \*** Фактически отключает кэширование, так как каждый запрос считается уникальным.

## Лучшие практики

1. **Используйте `Cache-Control` вместо `Expires`:** `Expires` устарел и игнорируется, если есть `max-age`.
2. **Разделяйте TTL для браузера и CDN:** `max-age` для браузера (короткий), `s-maxage` для CDN (длинный).
3. **Версионируйте статику:** Используйте fingerprinting (хеш в имени файла) + `Cache-Control: public, max-age=31536000, immutable`.
4. **Обязательно добавляйте `Vary: Accept-Encoding`:** Без него кэш может отдать сжатый контент клиенту, который его не поддерживает.
5. **Используйте strong ETag для статики:** Это позволяет эффективно валидировать ресурсы без повторной передачи тела.
6. **Настройте `stale-while-revalidate` и `stale-if-error`:** Это обеспечивает отзывчивость при обновлениях и отказоустойчивость при сбоях Origin.
7. **Кэшируйте ошибки:** `proxy_cache_valid 404 10s;` защищает Origin от повторных запросов к несуществующим ресурсам.
8. **Нормализуйте Cache Key:** Исключайте из ключа нерелевантные заголовки (Cookie, User-Agent), сортируйте query-параметры.
9. **Избегайте `Cache-Control: no-store` для чувствительных данных там, где можно использовать `private`:** `no-store` полностью блокирует кэш, `private` разрешает кэширование только в браузере.
10. **Валидируйте внутренние ссылки:** После изменения `Cache-Control` проверьте, что пользователи видят актуальный контент, а метрики (CHR, TTFB) улучшились.

### Роль в DevOps и SRE

- **Offload Ratio:** Процент запросов, обработанных кэшем. Рост Offload напрямую снижает затраты на облачные вычисления и БД.
- **Cache Purging:** Процесс удаления данных из разделяемых кэшей. Должен быть интегрирован в CI/CD пайплайн (например, очистка путей после деплоя фронтенда).
- **Сжатие и кэш:** Всегда используйте `Vary: Accept-Encoding`, чтобы избежать отдачи сжатого контента клиентам, которые его не понимают (и наоборот).
