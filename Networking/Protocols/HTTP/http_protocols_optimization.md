# Оптимизация производительности HTTP

## Определения

**HTTP-оптимизация** — комплекс архитектурных и конфигурационных мер, направленных на снижение задержек (**Latency**) и повышение эффективной пропускной способности при передаче данных. Современная оптимизация базируется на стандартах **RFC 911x** (HTTP/2, HTTP/3), механизмах управления приоритетами (**RFC 9218**) и современных алгоритмах сжатия.

Подробное описание версий протокола приведено в руководстве по **[эволюции HTTP](./http_versions.md)**.

## Основные концепции

### Проблема блокировки очереди (Head-of-Line Blocking)

Ситуация, при которой задержка одного фрагмента данных останавливает обработку всей последующей очереди.

- **Уровень приложения (HTTP/1.1):** Один активный запрос на одно TCP-соединение. Обходится через **Domain Sharding** (открытие до 6 соединений на хост), что в 2026 году считается **антипаттерном**, так как мешает эффективной приоритизации и перегружает TCP-стек.
- **Транспортный уровень (TCP):** В **HTTP/2** мультиплексирование позволяет передавать запросы параллельно, но потеря одного TCP-пакета блокирует все потоки в рамках этого соединения.
- **Решение в HTTP/3:** Протокол **QUIC (UDP)** изолирует потоки. Потеря пакета влияет только на конкретный ресурс (например, один фрагмент изображения), не мешая доставке остальных данных.

### Приоритизация ресурсов (RFC 9218)

В отличие от сложного механизма HTTP/2, современная приоритизация использует заголовок **`Priority`**.

- **Параметры:** `u` (urgency, 0–7) и `i` (incremental, boolean).
- **Принцип:** Клиент сообщает серверу, какие ресурсы критичны для отрисовки (например, CSS — `u=0`), а какие можно подгружать постепенно (изображения — `i=?1`). Это позволяет серверу оптимально планировать отправку данных в условиях ограниченного канала.

### Ускорение предварительной загрузки (103 Early Hints)

**RFC 8297** полностью заменил механизм Server Push, который был признан неэффективным.

- **Механизм:** Сервер отправляет промежуточный статус `103 Early Hints` с заголовками `Link` сразу после получения запроса, пока бэкенд генерирует основной ответ.
- **Эффект:** Браузер начинает загрузку критических CSS/JS и установку соединений с CDN на 100–500 мс раньше.

### Минимизация сетевых задержек (RTT)

- **TCP Fast Open (TFO):** Данные запроса передаются в первом пакете `SYN`. Экономит 1 RTT. Подробнее: **[TCP Fast Open](../../../Linux/Networking/Concepts/tcp_tuning/tcp_fast_open.md)**.
- **TLS 1.3 0-RTT:** Позволяет отправлять данные в первом пакете при повторном подключении.
- **QUIC (HTTP/3):** Объединяет рукопожатия транспорта и TLS, обеспечивая установку защищённого соединения за 0-1 RTT.
- **ECH (Encrypted Client Hello):** Шифрует SNI, предотвращая задержки, связанные с инспекцией трафика промежуточными узлами, и повышая приватность. См. **[Протокол TLS](../tls.md#ключевые-компоненты)**.

### Современные алгоритмы сжатия и словари

- **Zstandard (Zstd, RFC 9659):** Основной стандарт 2026 года для динамических данных. Обеспечивает баланс между высокой скоростью и степенью сжатия, превосходя Gzip и Brotli на API-ответах.
- **Shared Dictionaries (RFC 9509):** Механизм `Use-As-Dictionary`. Позволяет браузеру использовать предыдущие ответы сервера как «словарь» для сжатия последующих. Это радикально снижает объем передаваемых данных при обновлении SPA-приложений.
- **Brotli:** Оптимален для статического контента (сжатие на максимальном уровне `11`).

### Контроль перегрузки и L4S

- **BBRv3 (Bottleneck Bandwidth and RTT):** Алгоритм от Google, максимизирующий скорость в сетях с потерями пакетов и буферизацией (Bufferbloat). Критичен для QUIC/HTTP-3.
- **L4S (RFC 9330):** Технология «Low Latency, Low Loss, Scalable throughput». Позволяет сети и серверу взаимодействовать через ECN-метки, поддерживая сверхнизкую задержку (Jitter < 10 мс) даже при полной загрузке канала.

## Практические сценарии

### Сценарий 1: Глобальная оптимизация веб-платформы

**Цель:** Достижение максимальных показателей Core Web Vitals (LCP, INP).

**Рекомендации:**
1. **Активация HTTP/3 + BBRv3:** Снижает количество прерываний на нестабильных (мобильных) сетях.
2. **Внедрение Early Hints:** Настройка Nginx/Angie для отправки ссылок на критические шрифты и стили до обработки PHP/Python-кода.
3. **Настройка HTTPS-записи DNS:** Информирование о поддержке `h3` и параметрах ECH.
   ```dns
   example.com. 3600 IN HTTPS 1 . alpn="h3,h2" ipv4hint="1.2.3.4" ech="<config>"
   ```

### Сценарий 2: Оптимизация высоконагруженных JSON API

**Цель:** Минимизация TTFB и нагрузки на CPU.

**Рекомендации:**
1. **Zstandard (Zstd):** Настройка динамического сжатия.
2. **kTLS (Kernel TLS):** Использование системного вызова `sendfile` для передачи статики и кэшированных ответов. См. **[kTLS в Nginx](../../../WebServers/Nginx/Performance/nginx_performance_tuning.md#kernel-tls-ktls)**.
3. **Initial Congestion Window (initcwnd):** Увеличение до 30 сегментов для доставки небольших API-ответов за 1 RTT. См. **[Настройка initcwnd](../../../Linux/Networking/Tools/iproute2/ip_route.md)**.

### Сценарий 3: Оптимизация межсервисных коммуникаций (M2M)

**Цель:** Минимизация накладных расходов в рамках Service Mesh.

**Рекомендации:**
1. **gRPC (HTTP/2):** Бинарный формат обмена данными.
2. **Prioritization (RFC 9218):** Использование заголовка `Priority: u=0` для системных вызовов управления и `u=4` для фоновых задач (логи, метрики).
3. **TCP Fast Open:** Безопасное использование TFO внутри доверенного периметра.
