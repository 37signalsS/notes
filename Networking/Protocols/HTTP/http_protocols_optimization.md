# Оптимизация производительности HTTP

## Определения

**HTTP-оптимизация** — процесс выбора и настройки версий протокола **HTTP**, механизмов транспорта (TCP/UDP) и алгоритмов сжатия для минимизации задержек (Latency) и ускорения доставки контента. Современные стандарты оптимизации опираются на серию **RFC 911x**.

Подробное описание версий протокола приведено в руководстве по [эволюции HTTP](./http_versions.md).

## Основные концепции

### Проблема блокировки начала очереди (Head-of-Line Blocking)

Явление, при котором задержка или потеря одного пакета данных блокирует обработку всей последующей очереди запросов или пакетов.

- **Уровень приложения (HTTP/1.1):** Ограничение на один активный запрос в рамках одного соединения. Решается открытием нескольких параллельных **TCP (Transmission Control Protocol — протокол управления передачей)** соединений (обычно до 6).
- **Транспортный уровень (TCP):** В **HTTP/2** мультиплексирование позволяет передавать данные параллельно, но потеря одного TCP-пакета все равно блокирует все потоки внутри соединения.
- **Решение в HTTP/3:** Использование транспортного протокола **QUIC (Quick UDP Internet Connections — быстрые интернет-соединения UDP)** на базе **UDP (User Datagram Protocol — протокол пользовательских датаграмм)** позволяет изолировать потоки — потеря пакета влияет только на конкретный ресурс, не затрагивая остальные.

### Минимизация сетевых задержек (RTT)

Каждое новое соединение требует времени на сетевые рукопожатия (**RTT — Round-Trip Time**). Оптимизация направлена на сокращение их количества:

- **TCP Fast Open (TFO):** Позволяет передавать данные (HTTP-запрос) уже в первом пакете SYN. Экономит 1 RTT. Подробнее: **[TCP Fast Open](../../../Linux/Networking/Concepts/tcp_tuning/tcp_fast_open.md)**.
- **TLS 1.3 0-RTT:** Позволяет клиенту отправлять зашифрованные данные при повторном подключении без ожидания завершения рукопожатия.
- **QUIC (HTTP/3):** Нативно поддерживает 0-RTT и объединяет транспортный и криптографический слои, достигая минимально возможной задержки установки связи.

### Оптимизация серверной нагрузки

- **Kernel TLS (kTLS):** Перенос шифрования в ядро Linux. Позволяет использовать системный вызов `sendfile`, что радикально ускоряет отдачу тяжелых файлов по HTTPS (до 30% прироста пропускной способности). См. **[kTLS в Nginx](../../../WebServers/Nginx/Performance/nginx_performance_tuning.md#kernel-tls-ktls)**.
- **Connection Pooling:** Переиспользование установленных сессий для исключения затрат на повторные рукопожатия.

### Стратегия сжатия контента

Эффективное сжатие сокращает время передачи данных, но увеличивает нагрузку на CPU:

- **Brotli:** Стандарт для статического контента (JS, CSS, HTML). Дает на 15–20% лучшее сжатие, чем Gzip.
- **Zstandard (Zstd):** Оптимальный выбор для динамических JSON API. Обеспечивает высокую скорость сжатия при сохранении отличного коэффициента сжатия.
- **Правило 14 КБ (initcwnd):** Первая порция данных в TCP-соединении ограничена 10 сегментами (~14.6 КБ). Если критический путь страницы (HTML + CSS) укладывается в этот объем, пользователь увидит сайт на 1 RTT быстрее. См. **[Настройка initcwnd](../../../Linux/Networking/Tools/iproute2/ip_route.md)**.

## Практические сценарии

### Сценарий 1: Стратегия для публичных веб-сайтов и API

**Цель:** Обеспечить минимальное время загрузки для разнородной аудитории, включая мобильных пользователей.

**Рекомендации:**
1. **Внедрение HTTP/3:** Решает проблему блокировки на уровне транспорта и критически важно для мобильных клиентов.
2. **Активация Zstandard (Zstd):** Использование `zstd` (RFC 9659) для динамических API-ответов снижает нагрузку на CPU сервера по сравнению с Brotli при сопоставимом сжатии.
3. **Настройка DNS-записи типа HTTPS:** Позволяет браузерам узнать о поддержке протоколов (ALPN) и ключах шифрования (ECH) до начала установки соединения.
   ```dns
   example.com HTTPS 1 . alpn="h3,h2"
   ```

### Сценарий 2: Оптимизация межсервисного взаимодействия (M2M)

**Цель:** Минимизировать задержки внутри закрытой сети (ЦОД).

**Рекомендации:**

1. **gRPC поверх HTTP/2:** Использование бинарного Protobuf и долгоживущих потоков (streams) для минимизации оверхеда на парсинг.
2. **TCP Fast Open:** Во внутренней сети риск атак повтора ниже, что позволяет безопасно использовать TFO для экономии RTT.
3. **Keep-Alive Tuning:** Настройка агрессивных таймаутов (`keepalive_requests 10000`) для предотвращения частого пересоздания соединений под нагрузкой.

### Сценарий 3: Оптимизация для мобильных клиентов

**Цель:** Стабильная работа при частой смене IP-адресов и нестабильном качестве связи.

**Рекомендации:**

1. **Приоритет HTTP/3:** Механизм **Connection Migration** в QUIC позволяет сохранять активную сессию при переключении между Wi-Fi и мобильной сетью (LTE/5G) без разрыва соединения.
2. **Агрессивный Keep-Alive:** Если HTTP/3 недоступен, настройка длительных таймаутов удержания соединения помогает избежать повторных рукопожатий при кратковременных обрывах связи.
