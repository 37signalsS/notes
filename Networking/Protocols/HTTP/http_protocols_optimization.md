# Оптимизация производительности HTTP

## Определения

**HTTP-оптимизация** — комплекс архитектурных и конфигурационных мер, направленных на снижение задержек (**Latency**), повышение эффективной пропускной способности и минимизацию накладных расходов при передаче данных. Современная оптимизация базируется на стандартах **RFC 911x** (HTTP/2, HTTP/3), механизмах управления приоритетами (**RFC 9218**), алгоритмах контроля перегрузки (**BBRv3**, RFC 9002) и современных алгоритмах сжатия (**Zstandard**, RFC 9659).

**Совокупная задержка (Total Latency)** — сумма времени на DNS-разрешение, TCP/TLS-рукопожатие, передачу запроса, обработку на сервере и доставку ответа. В условиях мобильных сетей (RTT 50–300 мс) оптимизация на протокольном уровне даёт больший эффект, чем увеличение пропускной способности.

Подробное описание версий протокола приведено в руководстве по **[эволюции HTTP](./http_versions.md)**.

## Основные концепции

### Сравнительная таблица оптимизационных характеристик

| Характеристика | HTTP/1.1 | HTTP/2 | HTTP/3 |
| :--- | :--- | :--- | :--- |
| **Мультиплексирование** | Нет (Domain Sharding — антипаттерн) | Да (TCP-потоки) | Да (QUIC-потоки) |
| **HOL Blocking** | Уровень соединения | Уровень TCP-пакета | **Устранён** |
| **Рукопожатие** | 1–2 RTT (TCP + TLS) | 2–3 RTT | **1 RTT / 0-RTT** |
| **Сжатие заголовков** | Нет | HPACK | QPACK |
| **Миграция сессии** | Нет | Нет | **Да (Connection ID)** |
| **Приоритизация** | Нет | Деревья зависимостей | **RFC 9218 (u, i)** |
| **Early Hints** | Нет | Да (103) | Да (103) |
| **Контроль перегрузки** | TCP CUBIC/Reno | TCP CUBIC/Reno | **BBRv3 / Cubic** |
| **Защита от replay** | Нет | Нет | **0-RTT Anti-Replay** |

### Проблема блокировки начала очереди (Head-of-Line Blocking)

Ситуация, при которой задержка одного фрагмента данных останавливает обработку всей последующей очереди.

- **Уровень приложения (HTTP/1.1):** Один активный запрос на одно TCP-соединение. Обходится через **Domain Sharding** (открытие до 6 соединений на хост), что в 2026 году считается **антипаттерном**, так как мешает эффективной приоритизации и перегружает TCP-стек.
- **Транспортный уровень (TCP):** В **HTTP/2** мультиплексирование позволяет передавать запросы параллельно, но потеря одного TCP-пакета блокирует все потоки в рамках этого соединения.
- **Решение в HTTP/3:** Протокол **QUIC (UDP)** изолирует потоки. Потеря пакета влияет только на конкретный ресурс (например, один фрагмент изображения), не мешая доставке остальных данных.

### Приоритизация ресурсов (RFC 9218)

В отличие от сложного механизма HTTP/2, современная приоритизация использует упрощённый заголовок **`Priority`**.

- **Параметры:** `u` (urgency, 0–7) и `i` (incremental, boolean).
- **Принцип:** Клиент сообщает серверу, какие ресурсы критичны для отрисовки (например, CSS — `u=0`), а какие можно подгружать постепенно (изображения — `i=?1`). Это позволяет серверу оптимально планировать отправку данных в условиях ограниченного канала.
- **Влияние на Core Web Vitals:** Корректная приоритизация напрямую влияет на LCP и INP, гарантируя, что критический контент доставляется раньше фоновых задач.

### Ускорение предварительной загрузки (103 Early Hints)

**RFC 8297** полностью заменил механизм Server Push, который был признан неэффективным.

- **Механизм:** Сервер отправляет промежуточный статус `103 Early Hints` с заголовками `Link` сразу после получения запроса, пока бэкенд генерирует основной ответ.
- **Эффект:** Браузер начинает загрузку критических CSS/JS и установку соединений с CDN на 100–500 мс раньше.
- **Отличие от Server Push:** Early Hints не принуждает браузер принимать ресурсы и не конфликтует с кэшем. Сервер только советует, а браузер решает, что загружать.

### Минимизация сетевых задержек (RTT)

- **TCP Fast Open (TFO):** Данные запроса передаются в первом пакете `SYN`. Экономит 1 RTT. Подробнее: **[TCP Fast Open](../../../Linux/Networking/Concepts/tcp_tuning/tcp_fast_open.md)**.
- **TLS 1.3 0-RTT:** Позволяет отправлять данные в первом пакете при повторном подключении. См. **[Оптимизация TLS для производительности](../../../WebServers/Concepts/web_performance/tls_optimization.md)**.
- **QUIC (HTTP/3):** Объединяет рукопожатия транспорта и TLS, обеспечивая установку защищённого соединения за 0-1 RTT.
- **ECH (Encrypted Client Hello):** Шифрует SNI, предотвращая задержки, связанные с инспекцией трафика промежуточными узлами, и повышая приватность. См. **[TLS-шифрование и сертификаты для HTTP](./http_tls_hardening.md#дополнительная-информация)**.
- **Connection Migration:** В HTTP/3 приввязка к Connection ID (не к 4-tuple) позволяет сохранять соединение при смене сети (Wi-Fi → LTE). Процесс включает Path Validation для подтверждения нового маршрута.

### Современные алгоритмы сжатия и словари

- **Zstandard (Zstd, RFC 9659):** Основной стандарт 2026 года для динамических данных. Обеспечивает баланс между высокой скоростью и степенью сжатия, превосходя Gzip и Brotli на API-ответах. Подробнее: **[Сжатие контента на веб-сервере](../../../WebServers/Concepts/web_performance/server_compression.md)**.
- **Shared Dictionaries (RFC 9509):** Механизм `Use-As-Dictionary`. Позволяет браузеру использовать предыдущие ответы сервера как «словарь» для сжатия последующих. Это радикально снижает объем передаваемых данных при обновлении SPA-приложений.
- **Brotli:** Оптимален для статический контента (сжатие на уровне `11`). Подробнее: **[Сжатие контента на веб-сервере](../../../WebServers/Concepts/web_performance/server_compression.md)**.
- **QPACK (HTTP/3) vs HPACK (HTTP/2):** QPACK адаптирован для неупорядоченной доставки QUIC, исключая блокировку декодера при потери пакетов. HPACK требует упорядоченной доставки TCP, что создаёт зависимость между потоками.

### Подсказки ресурсов (Resource Hints)

Механизмы, позволяющие браузеру заранее начинать загрузку критических ресурсов:

- **`preload`:** Обязательная загрузка ресурса с высоким приоритетом (шрифты, критические CSS). Заменил Server Push в 2026 году.
- **`preconnect`:** Раннее установление TCP/TLS-соединения с доменом. Экономит RTT для CDN/шрифтов.
- **`dns-prefetch`:** Раннее разрешение DNS-имени. Используется, когда точное время соединения неизвестно.
- **`prefetch`:** Фоновая загрузка ресурса, который может понадобиться при следующем навигации. Низкий приоритет.
- **`prerender`:** Полная отрисовка страницы в скрытом фоне. Используется через Speculation Rules API. Высокие накладные расходы.

### Контроль перегрузки и L4S

- **BBRv3 (Bottleneck Bandwidth and RTT):** Алгоритм от Google, максимизирующий скорость в сетях с потерями пакетов и буферизацией (Bufferbloat). Критичен для QUIC/HTTP-3.
- **L4S (RFC 9330):** Технология «Low Latency, Low Loss, Scalable throughput». Позволяет сети и серверу взаимодействовать через ECN-метки, поддерживая сверхнизкую задержку (Jitter < 10 мс) даже при полной загрузке канала.
- **ECN (Explicit Congestion Notification):** Механизм, позволяющий роутерам сигнализировать о перегрузке до потери пакетов. В 2026 году является обязательным для L4S-сетей.

## Практические сценарии

### Сценарий 1: Глобальная оптимизация веб-платформы

**Цель:** Достижение максимальных показателей Core Web Vitals (LCP, INP).

**Рекомендации:**
1. **Активация HTTP/3 + BBRv3:** Снижает количество прерываний на нестабильных (мобильных) сетях.
2. **Внедрение Early Hints:** Настройка Nginx/Angie для отправки ссылок на критические шрифты и стили до обработки PHP/Python-кода.
3. **Настройка HTTPS-записи DNS:** Информирование о поддержке `h3` и параметрах ECH.

    ```dns
    example.com. 3600 IN HTTPS 1 . alpn="h3,h2" ipv4hint="1.2.3.4" ech="<config>"
    ```

**Валидация:**
- Lighthouse: LCP < 2.5s, INP < 200ms.
- `curl --http3 -I https://example.com` → `HTTP/3 200`.
- `dig example.com HTTPS` → содержит `alpn="h3,h2"`.

### Сценарий 2: Оптимизация высоконагруженных JSON API

**Цель:** Минимизация TTFB и нагрузки на CPU.

**Рекомендации:**
1. **Zstandard (Zstd):** Настройка динамического сжатия. Подробнее: **[Сжатие контента на веб-сервере](../../../WebServers/Concepts/web_performance/server_compression.md)**.
2. **kTLS (Kernel TLS):** Использование системного вызова `sendfile` для передачи статики и кэшированных ответов. См. **[kTLS в Nginx](../../../WebServers/Nginx/Performance/nginx_performance_tuning.md#kernel-tls-ktls)**.
3. **Initial Congestion Window (initcwnd):** Увеличение до 30 сегментов для доставки небольших API-ответов за 1 RTT. См. **[Настройка initcwnd](../../../Linux/Networking/Tools/iproute2/ip_route.md)**.
4. **Управление соединениями:** Настройка `keepalive_requests` и `keepalive_timeout` для переиспользования TCP-соединений.

**Валидация:**
- `curl -s -o /dev/null -w "TTFB: %{time_starttransfer}\n" https://api.example.com/data` → TTFB < 100ms.
- Мониторинг CPU: `htop` показывает снижение нагрузки на 15–25% после включения kTLS.

### Сценарий 3: Оптимизация межсервисных коммуникаций (M2M)

**Цель:** Минимизация накладных расходов в рамках Service Mesh.

**Рекомендации:**
1. **gRPC (HTTP/2):** Бинарный формат обмена данными. Подробнее: **[gRPC — обзор фреймворка](../../../Networking/ServicesAndTools/grpc_overview.md)**.
2. **Prioritization (RFC 9218):** Использование заголовка `Priority: u=0` для системных вызовов управления и `u=4` для фоновых задач (логи, метрики).
3. **TCP Fast Open:** Безопасное использование TFO внутри доверенного периметра.
4. **Сжатие тела:** Zstd (уровень 1) для JSON-сообщений. Brotli (уровень 5) для статичных ответов.

**Валидация:**
- `grpcurl -plaintext localhost:50051 list` → сервисы доступны.
- Wireshark: анализ кадров HTTP/2 (HEADERS/DATA) в рамках одного TCP-соединения.
- Снижение латенси на 20–30% по сравнению с REST/JSON через HTTP/1.1.

### Сценарий 4: Внедрение HTTP/3 в мобильном приложении

**Цель:** Обеспечение стабильной загрузки в условиях нестабильных мобильных сетей (переключение Wi-Fi → LTE).

**Рекомендации:**
1. **QUIC-сервер:** Nginx 1.26+ или Angie 1.4.0+ с `listen 443 quic reuseport`.
2. **Connection Migration:** Настройка `quic_bpf on;` для сохранения сессий при смене сети.
3. **0-RTT:** Включение `ssl_early_data on;` только для идемпотентных операций (GET).
4. **Клиентская часть:** Использование curl с поддержкой ngtcp2 или библиотеки HTTP/3 (например, `aiohttp` с `aioquic`).

**Валидация:**
```bash
# Проверка поддержки H3
curl -v --http3 https://api.example.com/users
# → ALPN, server accepted h3

# Проверка миграции соединения
# 1. Подключиться по Wi-Fi
curl --http3 https://api.example.com/users
# 2. Отключить Wi-Fi, включить LTE
# 3. Повторить запрос — соединение не должно разрываться
ss -u -a | grep :443
```

### Сценарий 5: Настройка Nginx/Angie для максимальной производительности

**Цель:** Полное использование возможностей современного HTTP-стека.

**Рекомендации:**
1. **HTTP/2 + TLS 1.3:** Обязательная конфигурация для всех HTTPS-серверов.
2. **HTTP/3 (опционально):** Включение после валидации поддержки UDP 443 в целевых сетях.
3. **Сжатие:** Zstd (уровень 3) для динамики, Brotli (уровень 11) для статики.
4. **Кэширование:** `stale-while-revalidate` + `stale-if-error` для повышения отказоустойчивости.

```nginx
http {
    # Основные оптимизации
    keepalive_timeout 60s;
    keepalive_requests 1000;
    
    # Сжатие
    gzip on;
    gzip_static on;
    brotli on;
    brotli_static on;
    
    # Кэширование
    proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=STATIC:10m inactive=24h max_size=1g;
    
    server {
        listen 443 ssl http2;
        listen 443 quic reuseport;
        http3 on;
        
        ssl_certificate /etc/nginx/ssl/fullchain.pem;
        ssl_certificate_key /etc/nginx/ssl/privkey.key;
        ssl_protocols TLSv1.2 TLSv1.3;
        
        # Анонсирование HTTP/3
        add_header Alt-Svc 'h3=":443"; ma=86400';
        
        # Оптимизация QUIC
        quic_bpf on;
        quic_gso on;
        
        location / {
            proxy_pass http://backend;
            proxy_set_header Host $host;
            
            # Кэширование
            proxy_cache STATIC;
            proxy_cache_valid 200 1h;
            proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
        }
    }
}
```

**Валидация:**
- `nginx -t` → синтаксис корректен.
- `curl -I --http2 https://example.com` → `HTTP/2 200`.
- `curl -I --http3 https://example.com` → `HTTP/3 200`.
- `ab -n 10000 -c 100 https://example.com/` → RPS соответствует ожиданиям.

### Сценарий 6: Валидация производительности QUIC в условиях потерь пакетов

**Цель:** Подтверждение преимуществ HTTP/3 в сетях с высоким процентом потерь (>2%).

**Методология:**
1. **Создание тестового стенда:** Nginx/Angie с включённым HTTP/3, бэкенд-приложение, возвращающее статический JSON-ответ.
2. **Эмуляция потерь:** Использование `tc` (traffic control) для имитации потерь пакетов.
3. **Сравнение:** Измерение LCP и TTFB для HTTP/2 и HTTP/3 при разных уровнях потерь.

```bash
# Эмуляция 5% потерь пакетов
sudo tc qdisc add dev eth0 root netem loss 5%

# Тест HTTP/2
curl -s -o /dev/null -w "HTTP/2 TTFB: %{time_starttransfer}\n" --http2 https://example.com/api/data

# Тест HTTP/3
curl -s -o /dev/null -w "HTTP/3 TTFB: %{time_starttransfer}\n" --http3 https://example.com/api/data

# Очистка
sudo tc qdisc del dev eth0 root
```

**Ожидаемый результат:**
- При 0% потерь: HTTP/2 и HTTP/3 показывают comparable TTFB.
- При 5% потерь: HTTP/3 TTFB на 30–50% ниже HTTP/2 за счёт отсутствия TCP HOL-блокировки.
- При 10%+ потерь: разница становится критичной, HTTP/2 может не доставлять контент вообще.

### Сценарий 7: Мониторинг и алертинг производительности HTTP

**Цель:** Постоянный контроль ключевых метрик в продакшене.

**Инструменты и метрики:**
1. **Real User Monitoring (RUM):** Chrome UX Report (CrUX), собственные метрики.
2. **Synthetic Monitoring:** Lighthouse CI, WebPageTest API.
3. **Server-side:** Nginx/Angie logs, Prometheus exporters.

**Пример конфигурации Nginx для логирования:**
```nginx
log_format main '$remote_addr - $remote_user [$time_local] '
                '"$request" $status $body_bytes_sent '
                '"$http_referer" "$http_user_agent" '
                'rt=$request_time uct="$upstream_connect_time" '
                'uht="$upstream_header_time" urt="$upstream_response_time"';

access_log /var/log/nginx/access.log main;
```

**Ключевые метрики для мониторинга:**
- **TTFB (Time To First Byte):** Должно быть < 200ms для API, < 500ms для HTML.
- **LCP (Largest Contentful Paint):** < 2.5s (хороший), < 4s (требует улучшения).
- **Cache Hit Ratio:** > 90% для статики, > 60% для HTML.
- **HTTP/3 Adoption:** Процент клиентов, использующих QUIC (через ALPN в логах).

**Валидация:**
- Prometheus + Grafana дашборды показывают тренды по всем метрикам.
- Алерты при падении Cache Hit Ratio ниже порога или росте TTFB.

## Типичные проблемы и диагностика

### 1. Высокий TTFB при включённом HTTP/2

**Симптом:** TTFB вырос после перехода на HTTP/2.

**Причины и диагностика:**
```bash
# Проверка эффективности multiplexing
curl -v --http2 https://example.com/ | grep "x-mod"

# Проверка наличия HPACK Bomb
nginx -T | grep max_headers

# Проверка session cache
curl -v https://example.com/ | grep "session ticket"
```

**Решение:**
- Включить `ssl_session_cache shared:SSL:10m;`
- Отключить динамическое сжатие: `gzip off;` или использовать `gzip_static`
- Установить `max_headers 100;` для защиты от HPACK-атак

### 2. HTTP/3 не работает за корпоративным файрволом

**Симптом:** `curl --http3` возвращает таймаут или `Connection refused`.

**Причина:** UDP-порт 443 закрыт или ограничен Deep Packet Inspection (DPI).

**Решение:**
```bash
# Проверка доступности UDP-порта
nc -zvu example.com 443

# Проверка MTU (QUIC чувствителен к фрагментации)
ping -M do -s 1400 example.com
```

### 3. Replay-атака при использовании 0-RTT

**Симптом:** Дублирование запросов на оплату или создание ресурсов.

**Причина:** Клиент отправил данные через 0-RTT, злоумышленник перехватил и повторил запрос.

**Решение:**
```bash
# Проверка конфигурации
nginx -T | grep early_data

# Включение только для безопасных методов
# ssl_early_data on;  # Только для GET/HEAD
```

### 4. Cache Stampede при истечении TTL

**Симптом:** Всплеск нагрузки на Origin после истечения TTL популярного объекта.

**Решение:**
```nginx
# Включение stale-while-revalidate
proxy_cache_valid 200 1h;
proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;

# Jitter TTL (случайное отклонение)
proxy_cache_key "$request_uri$random_jitter";
```

### 5. HPACK-бомба / Flood

**Симптом:** Высокое потребление CPU и памяти на прокси/сервере.

**Решение:**
```bash
# Nginx/Angie 1.25.1+
max_headers 100;

# Ограничение размера динамической таблицы HPACK
# (vendor-specific, проверьте документацию)
```

### 6. Domain Sharding остаётся в кодеbase

**Симптом:** Использование нескольких поддоменов для статики (`static1.`, `static2.`).

**Решение:**
- Удалить разделение по поддоменам. В 2026 году это антипаттерн.
- Использовать один домен с HTTP/2 multiplexing.
- Для CDN использовать один CNAME.

### 7. Отсутствие приоритизации критических ресурсов

**Симптом:** Медленный LCP, фоновые изображения загружаются раньше критического CSS.

**Решение:**
```html
<!-- Критический CSS -->
<link rel="preload" href="/css/critical.css" as="style" fetchpriority="high">

<!-- Фоновые изображения -->
<img src="/img/hero.jpg" fetchpriority="high">
<img src="/img/gallery/1.jpg" loading="lazy" fetchpriority="low">
```

## Лучшие практики

1. **Использовать HTTP/2+ для браузерного трафика:** Включите HTTP/2 на всех HTTPS-серверах. Для HTTP/3 используйте только после валидации поддержки UDP 443 на целевых сетях.
2. **Включать HTTP/3 только после валидации:** Проверьте поддержку UDP 443 на целевых сетях (мобильные, корпоративные). Используйте Alt-Svc с разумным `ma` (86400–604800).
3. **Отключать Domain Sharding:** Используйте один домен с HTTP/2 multiplexing. Разделение по поддоменам вредит производительности в 2026 году.
4. **Настраивать TLS 1.3:** Уберите TLS 1.0/1.1. TLS 1.3 сокращает handshake до 1 RTT и необходим для HTTP/3.
5. **Использовать Connection Migration:** Для мобильных приложений и API настройте `reuseport` и `quic_bpf` для сохранения сессий при смене сети.
6. **Настраивать ECH для приватности SNI:** Шифруйте SNI через Encrypted Client Hello, если целевая аудитория требует приватности от пассивного наблюдения.
7. **Применять Resource Hints вместо Server Push:** Используйте `preload`, `preconnect`, `dns-prefetch` вместо Server Push. Server Push удалён из HTTP/3 и игнорируется браузерами.
8. **Мониторить QUIC-потоки:** Используйте `ss -u -a` для мониторинга UDP-соединений. Отслеживайте `stateless reset` и `connection close` в логах.
9. **Использовать 0-RTT только для идемпотентных операций:** Разрешайте Early Data только для GET/HEAD. Настройте `max_early_data_size` и проверку тикетов.
10. **Настраивать Alt-Svc с разумным `ma`:** Слишком долгий `ma` (недели) приведёт к распространению устаревшей конфигурации при изменении серверов. Сутки (`86400`) — оптимально.
11. **Применять Happy Eyeballs:** Если поддерживаете dual-stack, настройте Happy Eyeballs v2/v3 для быстрого переключения между IPv4 и IPv6.
12. **Включать BBRv3:** Для серверов с высокой пропускной способностью и сетями с потерями пакетов. Проверьте поддержку в ядре: `sysctl net.ipv4.tcp_congestion_control`.

## Граничные случаи и ограничения

1. **HTTP/2 с очень старыми клиентами:** Windows XP, Android < 4.3 не поддерживают ALPN. Для таких клиентов автоматически используется HTTP/1.1.
2. **UDP-фрагментация и MTU:** QUIC-пакеты превышают стандартный MTU (1500), что приводит к фрагментации на IP-уровне. Настройте PMTU discovery (PLPMTUD, RFC 8899).
3. **0-RTT и Replay Attacks:** Даже для GET-запросов 0-RTT может быть опасен (например, повторная отправка формы через JavaScript API). Используйте Anti-Replay механизмы на уровне приложения.
4. **Connection ID exhausting:** При очень большом количестве уникальных клиентов (millions) может исчерпаться пространство Connection ID. Мониторьте метрики.
5. **HPACK Bomb:** Динамическая таблица HPACK может быть переполнена вредоносными запросами. Ограничьте количество заголовков (`max_headers`) и размер тела запроса.
6. **NAT rebinding и QUIC:** При изменении NAT-таблицы провайдера (смена порта) QUIC-соединение может быть разорвано. Connection Migration помогает, но требует Path Validation.
7. **Версионная несовместимость QUIC:** Разные версии QUIC (draft-29, v1, v2) несовместимы. Убедитесь, что клиент и сервер используют совместимые версии через Version Negotiation.
8. **TLS session resumption across versions:** Тикеты TLS 1.2 не работают для TLS 1.3 и QUIC. Настройте отдельное кэширование тикетов для TLS 1.3 (`ssl_session_cache`).
9. **Редиректы с HTTP/3:** При 301/302 редиректе клиент может вернуться на HTTP/2. Настройте сервер для приёма Alt-Svc на всех версиях.
10. **gRPC и HTTP/2 flow control:** gRPC использует HTTP/2 с большими сообщениями. Настройте `SETTINGS_MAX_FRAME_SIZE` и мониторьте `WINDOW_UPDATE`, чтобы избежать зависаний потоков.
11. **Shared Dictionaries и кэширование:** Словари сжатия (RFC 9509) не должны кэшироваться как обычные статические файлы. Настройте `Cache-Control: no-store` для файлов словарей.
12. **L4S и устаревшее оборудование:** L4S требует поддержки ECN на всех маршрутизаторах в пути. Устаревшее оборудование может сбрасывать пакеты с установленным ECN-битом.
