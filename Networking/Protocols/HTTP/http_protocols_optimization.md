# Оптимизация производительности HTTP

## Определения

**HTTP-оптимизация** — процесс выбора и настройки версий протокола **HTTP (Hypertext Transfer Protocol — протокол передачи гипертекста)** и сопутствующих технологий для минимизации задержек и ускорения доставки контента пользователю.

Подробное описание и сравнение версий протокола приведено в руководстве по [эволюции HTTP](./http_versions.md).

## Основные концепции

### Проблема блокировки начала очереди (Head-of-Line Blocking)

Явление, при котором задержка или потеря одного пакета данных блокирует обработку всей последующей очереди запросов или пакетов.

- **Уровень приложения (HTTP/1.1):** Ограничение на один активный запрос в рамках одного соединения. Решается открытием нескольких параллельных **TCP (Transmission Control Protocol — протокол управления передачей)** соединений (обычно до 6).
- **Транспортный уровень (TCP):** В **HTTP/2** мультиплексирование позволяет передавать данные параллельно, но потеря одного TCP-пакета все равно блокирует все потоки внутри соединения.
- **Решение в HTTP/3:** Использование транспортного протокола **QUIC (Quick UDP Internet Connections — быстрые интернет-соединения UDP)** на базе **UDP (User Datagram Protocol — протокол пользовательских датаграмм)** позволяет изолировать потоки — потеря пакета влияет только на конкретный ресурс, не затрагивая остальные.

### Затраты на установку соединения

Каждое новое соединение требует времени на выполнение сетевых рукопожатий (**RTT — Round-Trip Time**, время кругового обхода):

1. **TCP Handshake:** 1 RTT.
2. **TLS Handshake:** 1–2 RTT (подробнее см. [Протокол TLS](../tls.md)).

**Методы оптимизации:**

- **HTTP Keep-Alive и Connection Pooling:** Переиспользование уже установленных соединений для серии последовательных запросов, что исключает затраты на повторные рукопожатия.
- **QUIC (HTTP/3):** Объединяет установку соединения и шифрование (TLS 1.3) в единый процесс. Позволяет достичь 1 RTT для новых и 0-RTT для повторных подключений.

## Практические сценарии

### Сценарий 1: Стратегия для публичных веб-сайтов и API

**Цель:** Обеспечить минимальное время загрузки для разнородной аудитории, включая мобильных пользователей.

**Рекомендации:**

1. **Внедрение HTTP/2 и HTTP/3:** Позволяет использовать мультиплексирование и современный транспорт. Примеры настройки приведены в разделе [Конфигурация HTTP/2 и HTTP/3 в Nginx](../../../WebServers/Nginx/Performance/nginx_http_versions.md).
2. **Активация TLS 1.3:** Сокращает время рукопожатия и является обязательным требованием для HTTP/3.
3. **Настройка DNS-записи типа HTTPS:** Позволяет браузерам узнать о поддержке протоколов (ALPN — Application-Layer Protocol Negotiation) до начала установки соединения, решая проблему «холодного старта» для QUIC.

   ```dns
   example.com HTTPS 1 . alpn="h2,h3"
   ```

### Сценарий 2: Оптимизация межсервисного взаимодействия (Microservices)

**Цель:** Минимизировать задержки при интенсивном обмене данными внутри дата-центра.

**Рекомендации:**

1. **Connection Pooling:** Использование пулов соединений между сервисами для избежания накладных расходов на создание новых TCP-сессий.
2. **Использование gRPC:** Работает поверх HTTP/2, эффективно используя бинарный формат и мультиплексирование для передачи структурированных данных.
3. **Автоматизация через Service Mesh:** Использование решений вроде Istio или Linkerd для централизованного управления политиками ретраев, таймаутов и балансировки.

### Сценарий 3: Оптимизация для мобильных клиентов

**Цель:** Стабильная работа при частой смене IP-адресов и нестабильном качестве связи.

**Рекомендации:**

1. **Приоритет HTTP/3:** Механизм **Connection Migration** в QUIC позволяет сохранять активную сессию при переключении между Wi-Fi и мобильной сетью (LTE/5G) без разрыва соединения.
2. **Агрессивный Keep-Alive:** Если HTTP/3 недоступен, настройка длительных таймаутов удержания соединения помогает избежать повторных рукопожатий при кратковременных обрывах связи.
