# HTTP API и REST

## API и REST API

**API (Application Programming Interface)** — это набор правил и протоколов, который позволяет различным программным приложениям взаимодействовать друг с другом. Это способ взаимодействия между приложениями и серверами, предоставляющий эндпоинты с их собственными URL, на которые клиент или другой сервер может делать CRUD-запросы для взаимодействия.

**REST (Representational State Transfer)** — это архитектурный стиль программного обеспечения, который применяется для создания распределённых систем, таких как веб-службы. Он определяет набор принципов и ограничений, которым должна соответствовать система для обеспечения масштабируемости, гибкости и надежности.

Этот подход предложил Рой Филдинг, один из разработчиков [HTTP-протокола](./http_basics.md), в начале 2000-х, как способ описания архитектуры Всемирной паутины.

## Основные концепции REST API

RESTFul-сервисы позволяют работать с ресурсами (данными) через унифицированный интерфейс, основываясь на простых и понятных HTTP-методах:

* **Ресурсы:** Каждая единица данных (например, пользователь, товар) рассматривается как ресурс, идентифицируемый уникальным универсальным идентификатором ресурса (URL/URI).
  * **Примеры URL-адресов ресурсов:**
    * Книга в библиотеке: `/books/2`
    * Страница книги: `/books/2/pages/145`
* **Унифицированный интерфейс:** Для взаимодействия с ресурсами используются стандартные HTTP-методы (CRUD — Create, Read, Update, Delete):
  * **GET** – получение данных о ресурсе. Является идемпотентным (многократное выполнение не меняет состояние на сервере) и безопасным (не вызывает побочных эффектов).
  * **POST** – создание нового ресурса или отправка данных для обработки. Не является идемпотентным.
  * **PUT** – полная замена существующего ресурса или создание ресурса, если его нет. Является идемпотентным.
  * **PATCH** – частичное обновление существующего ресурса.
  * **DELETE** – удаление ресурса. Является идемпотентным.
* **Отсутствие состояния (Stateless):** Как и сам HTTP, REST является архитектурой без сохранения состояния. Подробнее см. раздел [Stateless-протокол](./http_basics.md#stateless-протокол-протокол-без-сохранения-состояния).
* **Кэширование:** Клиенты могут кэшировать ответы, что сокращает задержку и нагрузку на сервер.

## Ключевые преимущества REST

* **Простота:** Легко понять и использовать. Модель взаимодействия интуитивно понятна, так как основана на стандартных HTTP-методах.
* **Лёгкость (Lightweight):** Отсутствие дополнительных протокольных слоёв и использование текстовых форматов данных (JSON, XML) упрощает обработку данных и снижает накладные расходы.
* **Гибкость (Flexibility):** Работает с любыми клиентами (веб-браузеры, мобильные приложения, десктопные программы) и серверами, поддерживающими HTTP.
* **Масштабируемость:** Отсутствие состояния на сервере (statelessness) упрощает горизонтальное масштабирование.

## Примеры типичных REST-запросов

1. **GET `/books/`** – возвращает список всех книг.
2. **GET `/books/2`** – предоставляет информацию о книге с ID 2.
3. **POST `/books/`** – добавляет новую книгу в коллекцию. Тело запроса содержит данные новой книги.
4. **PUT `/books/2`** – полностью обновляет информацию о книге с ID 2. Тело запроса содержит новые данные для книги.
5. **PATCH `/books/2`** – частично обновляет информацию о книге с ID 2 (например, меняет только заголовок).
6. **DELETE `/books/2`** – удаляет книгу с ID 2.

## HTTP API

HTTP широко используется для взаимодействия программ (Application Programming Interface).

* **Структура:** Клиент отправляет HTTP-запрос на определенный **endpoint** (URL), а сервер возвращает данные, чаще всего в формате **JSON**.
* **CRUD:** Операции с данными (Create, Read, Update, Delete) принято сопоставлять с методами HTTP:
  * **C**reate → `POST`
  * **R**ead → `GET`
  * **U**pdate → `PUT` / `PATCH`
  * **D**elete → `DELETE`
* **Инструменты:** Для работы с API используются [Postman](https://www.postman.com/), [cURL](../../Linux/Networking/Tools/http_clients/curl.md), [HTTPie](../../Linux/Networking/Tools/http_clients/httpie.md).
