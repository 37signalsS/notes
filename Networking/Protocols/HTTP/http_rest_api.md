# HTTP API и REST

## Определения

**API (Application Programming Interface)** — набор правил и протоколов, позволяющий программным компонентам взаимодействовать друг с другом. В контексте веба API предоставляют эндпоинты (endpoints), идентифицируемые через URI.

**REST (Representational State Transfer)** — архитектурный стиль для создания распределённых систем, предложенный Роем Филдингом в 2000 году. Определяет набор ограничений (constraints), следование которым обеспечивает масштабируемость, независимость развертывания компонентов и надежность.

**RESTful API** — веб-сервис, реализующий архитектурные ограничения REST и использующий стандартную семантику протокола HTTP (методы, заголовки, статусы).

**Ресурс (Resource)** — ключевая абстракция REST. Любая сущность (пользователь, заказ, коллекция), идентифицируемая уникальным **URI (Uniform Resource Identifier)**. REST оперирует *представлениями* (Representations) ресурсов в различных форматах (JSON, XML).

## Основные концепции

### Принципы REST (Architectural Constraints)

REST основывается на шести архитектурных ограничениях:

1. **Клиент-сервер (Client-Server):** Жесткое разделение ответственности. Интерфейс пользователя и бизнес-логика развиваются независимо.
2. **Отсутствие состояния (Stateless):** Сервер не хранит контекст сессии клиента. Каждый запрос должен содержать всю информацию (включая авторизацию), необходимую для его выполнения. Упрощает горизонтальное масштабирование.
3. **Кэшируемость (Cacheability):** Ответы сервера должны явно указывать свою кэшируемость (через заголовки `Cache-Control`, `ETag`).
4. **Единообразие интерфейса (Uniform Interface):** Строгое следование стандартам (URI для идентификации, HTTP-методы для действий, HATEOAS).
5. **Слоистая система (Layered System):** Клиент не может определить, взаимодействует он напрямую с конечным сервером или с промежуточными узлами (API Gateway, Load Balancer, CDN).
6. **Код по требованию (Code on Demand — опционально):** Сервер может передавать исполняемый код (например, JavaScript-скрипты) для выполнения на стороне клиента.

### Модель зрелости Ричардсона (Richardson Maturity Model)

Шкала оценки соответствия API архитектурному стилю REST:

- **Уровень 0: ХАОС (The Swamp of POX).** Использование HTTP только как транспортного туннеля. Единый эндпоинт (например, `/api`) и один метод (обычно `POST`). Действие передается в теле запроса (RPC-стиль: SOAP, gRPC).
- **Уровень 1: Ресурсы (Resources).** Введение множества уникальных URI для разных сущностей ( `/users`, `/books`), но все действия выполняются через один HTTP-метод (обычно `GET` или `POST`).
- **Уровень 2: HTTP-методы (HTTP Verbs).** Строгое и семантически корректное использование методов (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`) и стандартизированных [HTTP-кодов ответа](./http_status_codes.md). *Большинство современных бизнес-API находятся на этом уровне.*
- **Уровень 3: HATEOAS (Hypermedia Controls).** Ответ сервера включает гипермедиа-ссылки, указывающие клиенту на возможные дальнейшие действия. API становится самодокументируемым.

### Проектирование API (API Design)

#### Структура URI

Ресурсы идентифицируются через URI. Главное правило: **Существительные вместо глаголов.**

- **Антипаттерн:** `POST /create_user` или `GET /get_books`.
- **RESTful:** `POST /users` или `GET /books`.
- **Иерархия:** `/users/123/orders` (получить заказы пользователя 123).

#### Пагинация (Pagination)

Обязательный механизм для коллекций, предотвращающий деградацию производительности (OOM/Timeouts):

1.  **Offset Pagination (Смещение):** Использование `?limit=20&offset=40`.
    - *Плюсы:* Простота реализации, возможность перехода на конкретную страницу.
    - *Минусы:* Проблемы с консистентностью при добавлении/удалении записей во время листания; замедление запросов базы данных при больших `offset`.
2.  **Cursor/Keyset Pagination (Курсорная):** Использование указателя на последнюю полученную запись `?limit=20&after_id=1054`.
    - *Плюсы:* Максимальная производительность БД (использует индексы `WHERE id > X`), нет сдвигов данных.
    - *Минусы:* Нельзя перепрыгнуть сразу на N-ую страницу (только Next/Prev). Стандарт для лент новостей и высоконагруженных API.

#### Стандартизация ошибок (Error Handling)

Возврат ошибок должен иметь предсказуемую структуру. Современный стандарт де-факто — **RFC 9457 (Problem Details for HTTP APIs)**, описывающий структуру JSON-ответа при ошибке:

```json
{
  "type": "https://api.example.com/errors/out-of-credit",
  "title": "You do not have enough credit.",
  "status": 403,
  "detail": "Your current balance is 30, but that costs 50.",
  "instance": "/account/12345/logs?id=987"
}
```

### Форматы данных

REST API использует текстовые и бинарные форматы для передачи представлений ресурсов:

- **JSON (application/json):** Стандарт де-факто. Легкий, читаемый и поддерживается всеми языками.
- **XML (application/xml):** Используется в legacy-системах и enterprise-решениях.
- **Protobuf / MessagePack:** Бинарные форматы для высоконагруженных систем, обеспечивающие минимальный размер сообщений.

### HATEOAS и форматы гипермедиа

**HATEOAS (Hypermedia as the Engine of Application State)** — принцип, согласно которому клиент взаимодействует с API через ссылки, предоставляемые сервером динамически. Это уменьшает жесткое зацепление (coupling) — клиенту не нужно знать структуру URI заранее.

**Пример (JSON-HAL):**
```json
{
  "order_id": 456,
  "status": "processing",
  "_links": {
    "self": { "href": "/orders/456" },
    "cancel": { "href": "/orders/456/cancel", "method": "POST" },
    "customer": { "href": "/customers/123" }
  }
}
```

### Версионирование API (API Versioning)

Необходимо для внесения ломающих изменений (Breaking Changes) без остановки старых клиентов.

1.  **URI Versioning:** `https://api.example.com/v1/users`.
    - *Плюсы:* Легко тестировать, кэшировать и отлаживать. Самый популярный метод.
    - *Минусы:* Нарушает принцип «один ресурс — один URI».
2.  **Header Versioning:** `X-API-Version: 2`.
    - *Плюсы:* Чистые URI.
    - *Минусы:* Сложность кэширования (требуется `Vary: X-API-Version`).
3.  **Media Type Versioning (Accept Header):** `Accept: application/vnd.example.v2+json`.
    - *Плюсы:* Самый «RESTful» способ.
    - *Минусы:* Трудности с тестированием через браузер, сложность реализации.

#### Эволюция и Deprecation

Для плавного вывода версий из эксплуатации используются заголовки:
- **`Deprecation` (RFC 8594):** Сообщает клиенту, что эндпоинт устарел.
- **`Sunset`:** Указывает дату окончательного отключения ресурса.

### Безопасность и управление трафиком

1.  **Аутентификация и Авторизация:**
    - **OAuth 2.0 / OpenID Connect:** Стандарт для делегирования доступа.
    - **JWT (JSON Web Token):** Stateless-способ передачи данных пользователя между клиентом и микросервисами.
2.  **Rate Limiting (Ограничение скорости):** Защита от DoS и перегрузки. Сервер возвращает `429 Too Many Requests` и заголовки `X-RateLimit-Limit`, `X-RateLimit-Remaining`.
3.  **API Gateway:** Централизует безопасность, логирование и маршрутизацию. Подробнее см. **[Обзор API Gateway](../../../Concepts/api_gateway_overview.md)**.

### Стандарты и инструменты (OpenAPI)

**OpenAPI Specification (Swagger):** Обязательный стандарт описания контрактов. Позволяет генерировать документацию, SDK и проводить контрактное тестирование.
- **API-First Approach:** Проектирование контракта в YAML/JSON *до* написания кода.

## Практические сценарии

### Сценарий 1: Реализация идемпотентности

Для критических операций (платежи, заказы) необходимо предотвращать дубликаты при повторных запросах (сетевые сбои).
1. Клиент генерирует `Idempotency-Key: UUID` и отправляет в заголовке.
2. Сервер сохраняет ключ и результат первой обработки в кэше (Redis) на короткий срок (например, 24 часа).
3. При повторе с тем же ключом — сервер возвращает сохраненный результат (200/201), не выполняя бизнес-логику повторно.

### Сценарий 2: Выбор стратегии пагинации

- Используйте **Offset**, если пользователю важно видеть общее количество страниц и переходить в конец списка (каталоги).
- Используйте **Cursor**, если важна скорость и отсутствие дублей/пропусков при динамическом изменении данных (ленты соцсетей, логи транзакций).

### Сценарий 3: Фильтрация и сложный поиск

Для запросов с множеством условий:
1. Стандартные параметры: `GET /books?author=King&sort=-year`.
2. Для очень сложных поисков (десятки полей) допустимо использовать `POST /books/search` или современный метод **`QUERY` (RFC 9421)**.

### Сценарий 4: Инструменты разработки

- **[cURL](../../../Linux/Networking/Tools/http_clients/curl.md)** — универсальный CLI-клиент.
- **[HTTPie](../../../Linux/Networking/Tools/http_clients/httpie.md)** — современная альтернатива с подсветкой синтаксиса.
- **Postman / Bruno** — графические среды для тестирования и коллекций.

## Дополнительная информация

### REST vs Альтернативы

- **gRPC:** Высокопроизводительный RPC на базе HTTP/2 и Protobuf. Идеален для внутренней связи микросервисов.
- **GraphQL:** Позволяет клиенту точно указывать необходимые поля, решая проблему Over-fetching.
- **WebSockets:** Для двусторонней связи в реальном времени (REST работает только по циклу «запрос-ответ»).
