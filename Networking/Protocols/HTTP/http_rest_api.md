# HTTP API и REST

## Definitions

**API (Application Programming Interface)** — набор правил и протоколов, позволяющий программным приложениям взаимодействовать друг с другом через эндпоинты с уникальными URL.

**REST (Representational State Transfer)** — архитектурный стиль для создания распределённых систем, предложенный Роем Филдингом (одним из разработчиков [HTTP-протокола](./http_basics.md)) в начале 2000-х. Определяет принципы, обеспечивающие масштабируемость, гибкость и надёжность веб-сервисов.

**RESTful API** — веб-сервис, реализующий архитектурный стиль REST и использующий HTTP-методы для выполнения CRUD-операций (Create, Read, Update, Delete) с ресурсами.

**Ресурс** — любая сущность (пользователь, заказ, документ), идентифицируемая уникальным URI. Примеры: `/users/123`, `/orders/456/items`.

## Basic Concepts

### Принципы REST

REST основывается на шести архитектурных ограничениях:

1. **Клиент-сервер:** Разделение ответственности между клиентом (UI, логика приложения) и сервером (данные, бизнес-логика). Позволяет развивать компоненты независимо.
2. **Отсутствие состояния (Stateless):** Каждый запрос клиента содержит всю необходимую информацию для его обработки. Сервер не хранит состояние сессии между запросами. Подробнее см. [stateless-протокол в HTTP](./http_basics.md#22-stateless-протокол-протокол-без-сохранения-состояния).
3. **Кэшируемость:** Ответы сервера должны явно указывать, можно ли их кэшировать. Это снижает задержку и нагрузку на сервер. Принципы HTTP-кэширования описаны в [документации по кэшированию](./http_caching.md).
4. **Единообразие интерфейса:** Унифицированный способ взаимодействия с ресурсами через стандартные HTTP-методы.
5. **Слоистая система:** Клиент не должен различать, подключён ли он напрямую к серверу или к промежуточному узлу (прокси, балансировщик, CDN).
6. **Код по запросу (опционально):** Сервер может передавать исполняемый код клиенту (например, JavaScript).

### HTTP-методы и CRUD-операции

Взаимодействие с ресурсами в REST осуществляется через стандартные [HTTP-методы](./http_methods.md), которые сопоставляются с CRUD-операциями:

| CRUD | HTTP-метод | Назначение | Идемпотентный |
| :--- | :--- | :--- | :--- |
| **C**reate | `POST` | Создание нового ресурса | ❌ Нет |
| **R**ead | `GET` | Получение ресурса | ✅ Да |
| **U**pdate | `PUT` | Полная замена ресурса | ✅ Да |
| **U**pdate | `PATCH` | Частичное обновление | ❌ Зависит от реализации |
| **D**elete | `DELETE` | Удаление ресурса | ✅ Да |

### Именование ресурсов (URI Design)

Ресурсы идентифицируются через URI. Хороший URI должен быть:

- **Иерархичным:** `/users/123/orders/456` (заказ 456 пользователя 123).
- **На основе существительных:** `/books/2` (не `/getBook/2` — метод GET уже указывает на получение).
- **Во множественном числе:** `/users`, `/orders` (общепринятая конвенция).
- **Без глаголов:** Глагол определяется HTTP-методом.

**Примеры:**

| Операция | Метод | URI | Описание |
| :--- | :--- | :--- | :--- |
| Получить все книги | `GET` | `/books` | Список всех книг |
| Получить книгу | `GET` | `/books/2` | Книга с ID 2 |
| Создать книгу | `POST` | `/books` | Добавление новой книги |
| Обновить книгу | `PUT` | `/books/2` | Полная замена книги |
| Частично обновить | `PATCH` | `/books/2` | Обновление одного поля |
| Удалить книгу | `DELETE` | `/books/2` | Удаление книги |
| Страницы книги | `GET` | `/books/2/pages/145` | Вложенный ресурс |

### Форматы данных

REST API использует текстовые форматы для передачи данных:

- **JSON** (application/json) — наиболее распространённый формат, лёгкий и читаемый.
- **XML** (application/xml) — используется в enterprise-системах и legacy-API.
- **Protobuf, MessagePack** — бинарные форматы для высокопроизводительных систем.

### Коды ответа HTTP в REST API

REST API использует [HTTP-коды ответа](./http_status_codes.md) для индикации результата операции:

| Код | Значение | Типичное использование в REST |
| :--- | :--- | :--- |
| **200 OK** | Успех | `GET`, `PUT`, `PATCH` выполнены |
| **201 Created** | Создано | `POST` успешно создал ресурс (заголовок `Location` указывает URI нового ресурса) |
| **204 No Content** | Успех без тела | `DELETE` выполнен, тело ответа отсутствует |
| **400 Bad Request** | Ошибка клиента | Невалидный JSON, отсутствуют обязательные поля |
| **401 Unauthorized** | Не авторизован | Отсутствует или невалидный токен авторизации |
| **403 Forbidden** | Запрещено | Токен валиден, но нет прав на операцию |
| **404 Not Found** | Не найдено | Ресурс с указанным ID не существует |
| **409 Conflict** | Конфликт | Нарушение уникальности (дубликат) |
| **500 Internal Server Error** | Ошибка сервера | Необработанное исключение на сервере |

## Practical Scenarios

### Сценарий 1: REST API для управления библиотекой

**Получение списка книг:**

```bash
curl -X GET https://api.library.com/books \
  -H "Accept: application/json"
```

Ответ:

```json
[
  {"id": 1, "title": "1984", "author": "George Orwell"},
  {"id": 2, "title": "Dune", "author": "Frank Herbert"}
]
```

**Создание новой книги:**

```bash
curl -X POST https://api.library.com/books \
  -H "Content-Type: application/json" \
  -d '{"title": "The Great Gatsby", "author": "F. Scott Fitzgerald"}'
```

Ответ:

```http
HTTP/1.1 201 Created
Location: https://api.library.com/books/3
```

**Частичное обновление (только заголовок):**

```bash
curl -X PATCH https://api.library.com/books/2 \
  -H "Content-Type: application/json" \
  -d '{"title": "Dune: Updated Edition"}'
```

**Удаление:**

```bash
curl -X DELETE https://api.library.com/books/2
# Ответ: 204 No Content
```

### Сценарий 2: Фильтрация, пагинация и сортировка

REST API поддерживаетет дополнительные параметры запроса:

```bash
# Пагинация
GET /books?page=2&limit=20

# Фильтрация
GET /books?author=Orwell&year=1949

# Сортировка
GET /books?sort=-year&sort=title

# Поиск
GET /books?q=dystopia
```

### Сценарий 3: Версионирование API

При изменении структуры ответа необходимо версионировать API, чтобы не сломать существующих клиентов:

**Через URL (наиболее распространено):**

```
https://api.example.com/v1/books
https://api.example.com/v2/books
```

**Через заголовок:**

```bash
curl -X GET https://api.example.com/books \
  -H "Accept: application/vnd.library.v2+json"
```

### Сценарий 4: Обработка ошибок

REST API должен возвращать структурированную информацию об ошибках:

```json
{
  "error": {
    "code": 400,
    "message": "Validation failed",
    "details": [
      {"field": "email", "issue": "Invalid email format"},
      {"field": "age", "issue": "Must be a positive integer"}
    ]
  }
}
```

### Сценарий 5: Инструменты для работы с REST API

- **[cURL](../../../Linux/Networking/Tools/http_clients/curl.md)** — универсальная CLI-утилита для отправки HTTP-запросов.
- **[HTTPie](../../../Linux/Networking/Tools/http_clients/httpie.md)** — удобная альтернатива cURL с подсветкой синтаксиса.
- **[Postman](https://www.postman.com/)** — GUI-приложение для тестирования API с коллекциями запросов.
- **Swagger/OpenAPI** — спецификации для документирования REST API.

## Additional Information

### Преимущества REST

- **Простота:** Интуитивная модель на основе стандартных HTTP-методов.
- **Лёгкость:** Отсутствие дополнительных протокольных слоёв, использование JSON/XML.
- **Гибкость:** Совместимость с любыми клиентами (браузеры, мобильные приложения, серверы).
- **Масштабируемость:** Stateless-архитектура упрощает горизонтальное масштабирование.

### Ограничения REST

- **Over-fetching / Under-fetching:** Клиент получает больше или меньше данных, чем нужно. Решается через GraphQL или специализированные эндпоинты.
- **Отсутствие стандартизации запросов:** Нет единого способа фильтрации, пагинации, сортировки — каждая команда реализует самостоятельно.
- **Не для реального времени:** REST не подходит для push-уведомлений, стриминга. Используются WebSocket или Server-Sent Events (SSE).

### REST и микросервисы

REST — доминирующий стиль коммуникации в микросервисных архитектурах. Каждый микросервис предоставляет REST API для взаимодействия с другими сервисами и API Gateway.

### Альтернативы REST

- **GraphQL:** Язык запросов, позволяющий клиенту выбирать нужные поля. Решает проблемы over-fetching.
- **gRPC:** Высокопроизводительный RPC-фреймворк на базе HTTP/2 и Protobuf. Используется для service-to-service коммуникации.
- **WebSocket:** Двусторонняя связь в реальном времени (чаты, уведомления, стриминг).
