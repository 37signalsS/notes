# HTTP API и REST

## Определения

**API (Application Programming Interface — программный интерфейс приложения)** — набор правил и протоколов, позволяющий программным приложениям взаимодействовать друг с другом через эндпоинты с уникальными URL (Uniform Resource Locator).

**REST (Representational State Transfer — передача состояния представления)** — архитектурный стиль для создания распределённых систем, предложенный Роем Филдингом. Определяет принципы, обеспечивающие масштабируемость, гибкость и надёжность веб-сервисов. Уровень зрелости системы часто оценивается по **модели Ричардсона (Richardson Maturity Model)**.

**RESTful API** — веб-сервис, реализующий принципы REST и использующий стандартные HTTP-методы для управления ресурсами.

**Ресурс** — любая сущность (пользователь, заказ, документ), идентифицируемая уникальным URI (Uniform Resource Identifier). Примеры: `/users/123`, `/orders/456/items`.


## Основные концепции

### Принципы REST

REST основывается на шести архитектурных ограничениях:

1. **Клиент-сервер:** Разделение ответственности между клиентом (интерфейс, логика приложения) и сервером (данные, бизнес-логика). Позволяет развивать компоненты независимо.
2. **Отсутствие состояния (Stateless):** Каждый запрос клиента содержит всю необходимую информацию для его обработки. Сервер не хранит состояние сессии между запросами. Подробнее см. [stateless-протокол в HTTP](./http_basics.md).
3. **Кэшируемость:** Ответы сервера должны явно указывать, можно ли их кэшировать. Это снижает задержку и нагрузку на сервер. Принципы HTTP-кэширования описаны в [руководстве по кэшированию](./http_caching.md).
4. **Единообразие интерфейса:** Унифицированный способ взаимодействия с ресурсами через стандартные HTTP-методы.
5. **Слоистая система:** Клиент не должен знать, подключён ли он напрямую к серверу или к промежуточному узлу (прокси, балансировщик, CDN).
6. **Код по запросу (опционально):** Сервер может временно расширять функциональность клиента, передавая исполняемый код (например, JavaScript).

### Модель зрелости Ричардсона (Richardson Maturity Model)

Путь к "истинному" REST разделен на 4 уровня:

- **Уровень 0: ХАОС (The Swamp of POX).** Использование HTTP только как транспорта. Один эндпоинт (например, `/api`) и один метод (обычно `POST`). Пример: SOAP или XML-RPC.
- **Уровень 1: Ресурсы.** Введение множества URI для разных сущностей (`/users`, `/books`), но использование одного метода.
- **Уровень 2: HTTP-методы.** Правильное использование семантики методов (`GET`, `POST`, `PUT`, `DELETE`) и статус-кодов. Большинство современных API находятся на этом уровне.
- **Уровень 3: HATEOAS.** Гипермедиа как двигатель состояния приложения. Ответ сервера содержит не только данные, но и ссылки на возможные дальнейшие действия.

### HATEOAS (Hypermedia as the Engine of Application State)

Принцип, согласно которому клиент взаимодействует с API полностью через гиперссылки, предоставляемые сервером динамически. Клиенту не нужно жестко прописывать все URI.

**Пример ответа (JSON-HAL):**

```json
{
  "order_id": 456,
  "status": "shipped",
  "_links": {
    "self": { "href": "/orders/456" },
    "customer": { "href": "/customers/123" },
    "track": { "href": "/orders/456/tracking" }
  }
}
```

### HTTP-методы и CRUD-операции

Взаимодействие с ресурсами в REST осуществляется через стандартные [HTTP-методы](./http_methods.md), которые сопоставляются с CRUD-операциями:

| CRUD | HTTP-метод | Назначение | Идемпотентность |
| :--- | :--- | :--- | :--- |
| **C**reate | `POST` | Создание нового ресурса | Нет |
| **R**ead | `GET` | Получение ресурса | Да |
| **U**pdate | `PUT` | Полная замена ресурса | Да |
| **U**pdate | `PATCH` | Частичное обновление | Нет* |
| **D**elete | `DELETE` | Удаление ресурса | Да |

*\* Подробнее об идемпотентности и безопасности см. в **[Методы HTTP](./http_methods.md)**.*

### Проектирование URI (URI Design)

Ресурсы идентифицируются через URI. Рекомендации по именованию:

- **Иерархичность:** `/users/123/orders/456` (заказ 456 пользователя 123).
- **Существительные вместо глаголов:** Используйте `/books/2` вместо `/getBook/2`. Действие определяется HTTP-методом.
- **Множественное число:** Используйте `/users`, `/orders` для коллекций.

**Примеры:**

| Операция | Метод | URI | Описание |
| :--- | :--- | :--- | :--- |
| Получить все книги | `GET` | `/books` | Список всех книг |
| Получить книгу | `GET` | `/books/2` | Книга с идентификатором 2 |
| Создать книгу | `POST` | `/books` | Добавление новой книги |
| Обновить книгу | `PUT` | `/books/2` | Полная замена данных книги |
| Частично обновить | `PATCH` | `/books/2` | Изменение отдельных полей |
| Удалить книгу | `DELETE` | `/books/2` | Удаление книги |

### Форматы данных

REST API использует текстовые форматы для передачи данных:

- **JSON (application/json)** — основной формат, легкий и читаемый.
- **XML (application/xml)** — часто встречается в enterprise-системах.
- **Protobuf, MessagePack** — бинарные форматы для высоконагруженных систем.

### Стандарты и инструменты (OpenAPI)

**OpenAPI Specification (ранее Swagger)** — стандарт описания структуры REST API. Позволяет генерировать документацию, клиентские библиотеки и серверные заглушки.

- **OpenAPI 3.1:** Текущая версия стандарта (совместима с JSON Schema 2020-12).
- **API-first подход:** Стратегия разработки, при которой проектирование контракта API (в формате YAML/JSON) предшествует написанию кода. Это позволяет командам фронтенда и бэкенда работать параллельно.

### Коды ответа HTTP в REST API

REST API использует стандартные [HTTP-коды ответа](./http_status_codes.md) для индикации результата операции:

| Код | Значение | Использование в REST |
| :--- | :--- | :--- |
| **200 OK** | Успех | Результат успешного `GET`, `PUT` или `PATCH`. |
| **201 Created** | Создано | Результат `POST`. Заголовок `Location` содержит URI нового ресурса. |
| **204 No Content** | Нет содержимого | Результат `DELETE`. Тело ответа отсутствует. |
| **400 Bad Request** | Некорректный запрос | Ошибка валидации данных клиента. |
| **401 Unauthorized** | Не авторизован | Отсутствует или невалидный токен авторизации. |
| **403 Forbidden** | Запрещено | Недостаточно прав для выполнения операции. |
| **404 Not Found** | Не найдено | Ресурс с указанным идентификатором не существует. |
| **409 Conflict** | Конфликт | Например, попытка создать дубликат уникального ресурса. |
| **429 Too Many Requests** | Слишком много запросов | Превышение лимитов (Rate Limiting). |
| **500 Internal Error** | Ошибка сервера | Необработанное исключение в коде сервера. |

## Практические сценарии

### Сценарий 1: Управление ресурсами через cURL

**Получение списка:**

```bash
curl -X GET https://api.example.com/books \
  -H "Accept: application/json"
```

**Создание ресурса:**

```bash
curl -X POST https://api.example.com/books \
  -H "Content-Type: application/json" \
  -d '{"title": "1984", "author": "George Orwell"}'
```

**Удаление:**

```bash
curl -X DELETE https://api.example.com/books/2
```

### Сценарий 2: Фильтрация и пагинация

Для работы с большими коллекциями используются параметры запроса:

```bash
# Пагинация: страница 2, по 20 элементов на страницу
GET /books?page=2&limit=20

# Фильтрация по автору и году
GET /books?author=Orwell&year=1949

# Сортировка по убыванию года
GET /books?sort=-year
```

### Сценарий 3: Версионирование API

При изменении структуры данных необходимо версионировать API, чтобы сохранить работоспособность старых клиентов.

**Методы реализации:**

- **В URL:** `https://api.example.com/v1/books`
- **В заголовках:** `Accept: application/vnd.example.v2+json`

### Сценарий 4: Рекомендации по проектированию

1. **Использование POST для сложных фильтров:** Если количество параметров в `GET` слишком велико, используйте `POST` с телом запроса в формате JSON.
2. **Возврат объекта вместо массива:** Всегда возвращайте объект в корне ответа (например, `{"items": [...]}`), чтобы иметь возможность добавить метаданные (total_count, page) без нарушения обратной совместимости.
3. **Идемпотентность:** Для критических операций (например, платежей) используйте заголовок `Idempotency-Key`. Сервер сохраняет результат первого запроса и при повторном обращении с тем же ключом просто возвращает его, предотвращая дублирование действий.
4. **Безопасность:** Весь трафик должен идти через HTTPS. Для централизованной проверки авторизации и защиты внутренних сервисов используйте **[API Gateway](../../../Concepts/api_gateway_overview.md)**.

### Сценарий 5: Обработка ошибок

API должен возвращать понятную структуру ошибки при кодах 4xx и 5xx:

```json
{
  "error": {
    "code": 400,
    "message": "Validation failed",
    "details": [
      {"field": "email", "issue": "Invalid format"}
    ]
  }
}
```

### Сценарий 6: Инструменты разработки и тестирования

- **[cURL](../../../Linux/Networking/Tools/http_clients/curl.md)** — основной CLI-инструмент для запросов.
- **[HTTPie](../../../Linux/Networking/Tools/http_clients/httpie.md)** — более читаемая альтернатива cURL.
- **Postman** — графическая среда для тестирования и документирования.
- **Swagger / OpenAPI** — стандарты описания структуры API.

### Преимущества REST

- **Масштабируемость:** Благодаря отсутствию состояния на сервере запросы легко балансировать.
- **Гибкость:** Поддержка различных форматов данных и независимость от платформы клиента.
- **Простота:** Использование стандартных механизмов HTTP делает протокол понятным для разработчиков.

### Ограничения REST

- **Over-fetching / Under-fetching:** Клиент может получать лишние данные или вынужден делать несколько запросов для сбора полной информации.
- **Отсутствие стандарта пагинации:** Каждая реализация может иметь свои правила фильтрации и постраничного вывода.
- **Не подходит для Real-time:** Для мгновенных уведомлений лучше использовать WebSocket или gRPC.

### Альтернативные подходы

- **GraphQL:** Позволяет клиенту точно указывать необходимые поля в запросе.
- **gRPC:** Высокопроизводительный фреймворк на базе HTTP/2 и Protobuf для внутренней связи микросервисов.
- **WebSocket:** Протокол для двусторонней связи в реальном времени.

Подробности использования HTTP-методов и кодов ответов доступны в соответствующих разделах: **[Методы HTTP](./http_methods.md)** и **[Коды ответа HTTP](./http_status_codes.md)**.
