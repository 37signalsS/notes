# Методы HTTP: Типы и характеристики

## Определения

**HTTP-метод (HTTP Method)** — это команда, указывающая серверу, какое действие необходимо выполнить над конкретным ресурсом. Семантика методов определена в стандарте **RFC 9110** (HTTP Semantics). Метод является частью [стартовой строки (Request Line)](./http_basics.md) HTTP-запроса.

**Безопасный метод (Safe Method)** — метод, предназначенный только для получения информации (только чтение). По определению, безопасные методы не должны изменять состояние сервера. Клиент не несет ответственности за побочные эффекты, которые могут возникнуть на сервере при выполнении безопасного метода (например, запись в логи или сбор статистики).

**Идемпотентный метод (Idempotent Method)** — метод, многократное выполнение которого с теми же параметрами приводит к тому же состоянию ресурса на сервере, что и однократное выполнение. Подробнее о механизмах реализации см. **[Идемпотентность](../../../Concepts/idempotency.md)**.

## Основные концепции

### Стандартизация методов

Семантика методов определяется в серии RFC:

| Метод | RFC | Год | Ключевые ограничения |
| :--- | :--- | :--- | :--- |
| **GET** | RFC 9110 §9.3.1 | 2022 | Без тела запроса; только чтение |
| **HEAD** | RFC 9110 §9.3.2 | 2022 | Без тела запроса; безопасный |
| **POST** | RFC 9110 §9.3.3 | 2022 | Тело обрабатывается по схеме ресурса |
| **PUT** | RFC 9110 §9.3.4 | 2022 | Полная замена; тело — полное представление |
| **DELETE** | RFC 9110 §9.3.5 | 2022 | Идемпотентен; тело не определено |
| **CONNECT** | RFC 9110 §9.3.6 | 2022 | Туннелирование; только для Origin-сервера |
| **OPTIONS** | RFC 9110 §9.3.7 | 2022 | Без тела или опциональное |
| **TRACE** | RFC 9110 §9.3.8 | 2022 | Без тела; для диагностики |
| **PATCH** | RFC 5789 | 2015 | Частичное изменение; требует Content-Type |
| **QUERY** | RFC 9421 | 2023 | Безопасный, идемпотентный, с телом |

### Сводная таблица методов

| Метод | Назначение | CRUD | Идемпотентность | Безопасность | Тело запроса |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **GET** | Получение данных | Read | Да | Да | Нет |
| **HEAD** | Только заголовки | — | Да | Да | Нет |
| **OPTIONS** | Параметры связи | — | Да | Да | Опционально |
| **TRACE** | Эхо-запрос | — | Да | Да | Нет |
| **QUERY** | Сложный поиск | — | Да | Да | **Да** |
| **PUT** | Полная замена | Update | Да | Нет | Да |
| **DELETE** | Удаление | Delete | Да | Нет | Опционально |
| **POST** | Обработка данных | Create | Нет | Нет | Да |
| **PATCH** | Частичное обновление | Update | Нет* | Нет | Да |

*\* PATCH может быть идемпотентным в зависимости от формата (например, JSON Patch при определенных условиях).*

### Детальный разбор методов

#### GET — Получение ресурса

Запрашивает представление ресурса. Не должен иметь тела запроса. Параметры передаются в URI через [Query Parameters](./http_basics.md).

**Почему без тела:** RFC 9110 явно запрещает тело в GET, так как оно игнорируется большинством серверов и промежуточных узлов. Это исключает неоднозначность семантики.

**Content Negotiation:** GET часто используется вместе с заголовками `Accept` и `Accept-Encoding` для согласования формата и кодировки ответа. Например, клиент может запросить JSON вместо XML без изменения URI.

**Использование:** Загрузка страниц, API-запросы списков/объектов.

**Особенность:** GET часто кэшируется браузером и прокси. Кэш-ключ включает URI и заголовки, влияющие на ответ (`Vary`).

#### HEAD — Получение только заголовков

Эквивалентен GET, но сервер возвращает только заголовки ответа без тела. Используется для предварительной проверки перед скачиванием или проверки доступности ресурса.

**Почему безопасный и идемпотентный:** HEAD не изменяет состояние и имеет те же побочные эффекты, что и соответствующий GET.

**Использование:**
- Проверка размеров файла перед скачиванием (`Content-Length`).
- Проверка актуальности кэша (`ETag`, `Last-Modified`).
- Мониторинг доступности эндпоинтов без нагрузки на сеть.

#### POST — Создание или обработка данных

Используется для отправки сущности к ресурсу, что часто вызывает изменение состояния или побочные эффекты на сервере. Метод не идемпотентен: каждый вызов создает новый ресурс или выполняет отдельную операцию.

**Почему не идемпотентен:** POST обрабатывает тело как команду, а не как состояние. Семантика зависит от содержимого тела и бизнес-логики сервера.

**Использование:** Отправка форм, создание записей в БД, выполнение сложных операций.

**Важно:** При сетевых сбоях клиент не может безопасно повторить POST без механизма идемпотентности (Idempotency-Key).

#### PUT — Замена ресурса

Заменяет все текущее представление ресурса данными запроса. Если ресурса нет, может создать его (если это разрешено API). Тело запроса должно содержать полное представление ресурса.

**Почему идемпотентный:** Повторная отправка того же тела на тот же URI приводит к тому же состоянию ресурса.

**Использование:** Обновление профиля пользователя целиком, загрузка файлов.

**Особенность:** PUT требует, чтобы клиент знал полную структуру ресурса. Частичные обновления через PUT нежелательны.

#### PATCH — Частичное изменение (RFC 5789)

Применяет частичные изменения к ресурсу. В отличие от PUT, передаются только изменяемые поля.

**Почему обычно не идемпотентен:** Семантика зависит от формата. JSON Merge Patch перезаписывает поля, но порядок операций в JSON Patch может создавать зависимость от предыдущего состояния.

**Основные форматы PATCH:**
1.  **JSON Merge Patch (RFC 7396):** Простой JSON, который накладывается на текущий ресурс. Если значение поля `null`, оно удаляется. Удобно для простых объектов, но не позволяет работать с массивами (они заменяются целиком).
2.  **JSON Patch (RFC 6902):** Массив операций (`add`, `remove`, `replace`, `move`, `copy`, `test`). Позволяет выполнять точные манипуляции с глубоко вложенными структурами и массивами. **Может быть идемпотентным**, если используется операция `test` для проверки состояния перед изменением.

#### QUERY — Безопасный запрос с телом (RFC 9421)

Современный метод для выполнения поисковых запросов, параметры которых слишком велики для URI.

**Характеристики:** Безопасный, идемпотентный, имеет тело запроса.
**Преимущество:** Решает проблему использования POST для поиска (который не является ни безопасным, ни идемпотентным, и плохо кэшируется).

**Использование:** Сложная фильтрация с десятками параметров, полнотекстовый поиск с большим телом запроса.

#### DELETE — Удаление

Удаляет указанный ресурс. Повторный вызов DELETE того же ресурса вернет тот же результат (ресурс удален), поэтому метод идемпотентен. Важно: `DELETE` может иметь тело запроса (хотя это редко используется и не рекомендуется некоторыми серверами).

**Идемпотентность:** Первый вызов удаляет ресурс, последующие возвращают `404 Not Found` или `204 No Content` — состояние системы не меняется.

#### CONNECT — Туннелирование

Создает прозрачный TCP-туннель через прокси-сервер к целевому хосту. Изначально разработан для HTTPS-туннелей (CONNECT + TLS).

**Механизм:**
1.  Клиент отправляет `CONNECT host:port HTTP/1.1`.
2.  Прокси устанавливает TCP-соединение с указанным хостом.
3.  Прокси возвращает `200 Connection Established`.
4.  Дальнейший обмен данными происходит в сыром виде (tunneled), без HTTP-интерпретации.

**Использование:** HTTPS через прокси, VPN, WebSocket через HTTP-прокси.

**Ограничение:** CONNECT разрешен только для Origin-сервера (Section 9.3.6 RFC 9110). Прокси должны ограничивать порты для предотвращения злоупотреблений.

#### OPTIONS — Параметры связи

Запрашивает доступные методы и параметры для указанного ресурса. Ответ содержит заголовок `Allow` со списком методов или `Access-Control-Allow-Methods` для CORS.

**Использование:**
- Обнаружение возможностей API (Capability Discovery).
- CORS Preflight (браузер отправляет OPTIONS перед actual-запросом).
- Проверка поддержки HTTP/2 или HTTP/3 через ALPN/NPN.

**Важно:** Preflight-запросы (OPTIONS) инициируются браузером автоматически и кэшируются на стороне клиента на несколько секунд до нескольких минут (согласно заголовку `Access-Control-Max-Age` ответа). Поэтому при отладке CORS OPTIONS-запросы могут не появляться в логах сервера — браузер использует закешированный результат и не отправляет запрос повторно.

#### TRACE — Эхо-запрос

Возвращает полученный запрос без изменений. Используется для диагностики цепочки прокси.

**Безопасность (XST — Cross-Site Tracing):** TRACE может раскрыть конфиденциальные заголовки (Cookies, Authorization). В 2026 большинство серверов отключают TRACE по умолчанию. Рекомендуется блокировать TRACE на уровне веб-сервера или прокси.

### Дополнительные концепции

#### Условные запросы (Conditional Requests)

Методы часто используются совместно с заголовками валидации для предотвращения «потери обновлений» (Lost Updates):

- **GET + If-None-Match:** Кэширование (получить данные, только если ETag изменился).
- **GET + If-Modified-Since:** Получить данные, только если ресурс был изменен после указанной даты.
- **PUT/PATCH + If-Match:** Оптимистическая блокировка (обновить ресурс, только если его текущая версия совпадает с той, что у клиента).
- **PUT/PATCH + If-Unmodified-Since:** Обновить, только если ресурс не изменялся после указанной даты.
- **DELETE + If-Unmodified-Since:** Удалить, только если в файл не вносились правки после определенной даты.

#### Переопределение методов (Method Overriding)

Некоторые старые клиенты, прокси или HTML-формы поддерживают только `GET` и `POST`. Для использования всей семантики REST используется переопределение:

1.  **Заголовок:** `X-HTTP-Method-Override: PUT`
2.  **Параметр запроса:** `POST /users/1?_method=DELETE`

Это позволяет серверу обрабатывать запрос как `PUT` или `DELETE`, даже если он пришел как `POST`.

**Важно:** Переопределение не изменяет безопасность/идемпотентность оригинального метода. Сервер должен обрабатывать переопределенный метод с соответствующей семантикой.

#### Семантика тела запроса по методам

| Метод | Размер тела | Content-Type | Обработка |
| :--- | :--- | :--- | :--- |
| **GET** | Запрещен | Нет | Сервер должен игнорировать |
| **HEAD** | Запрещен | Нет | Сервер должен игнорировать |
| **POST** | Ограничен сервером | Обязателен | Обработка по схеме ресурса |
| **PUT** | Ограничен сервером | Обязателен | Полная замена ресурса |
| **PATCH** | Ограничен сервером | Обязателен (application/json-patch+json, application/merge-patch+json) | Частичное изменение |
| **DELETE** | Не рекомендуется | Нет | Игнорируется большинством серверов |
| **CONNECT** | Нет | Нет | Туннелирование |
| **OPTIONS** | Опционально | Нет | Обычно без тела |
| **TRACE** | Нет | Нет | Эхо-ответ |

## Практические сценарии

### Сценарий 1: Проверка разрешенных методов через OPTIONS

С помощью `curl` можно узнать, какие действия разрешены для URL:

```bash
curl -X OPTIONS -i https://api.example.com/users
```

**Ожидаемый результат:**

```http
HTTP/1.1 204 No Content
Allow: GET, POST, PUT, DELETE, OPTIONS
Content-Length: 0
```

**Валидация:**
```bash
# Проверить наличие заголовка Allow
curl -s -X OPTIONS -I https://api.example.com/users | grep -i "Allow"
# → Allow: GET, POST, PUT, DELETE, OPTIONS
```

### Сценарий 2: Использование QUERY для сложной фильтрации

Метод `QUERY` (RFC 9421) позволяет передавать большие тела запроса для поиска, что невозможно через Query Parameters из-за ограничений длины URI.

```http
QUERY /api/v1/search HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "filter": {
    "status": "active",
    "tags": ["devops", "sre"],
    "created_after": "2026-01-01T00:00:00Z"
  }
}
```

**Валидация через curl:**

```bash
curl -X QUERY https://api.example.com/api/v1/search \
  -H "Content-Type: application/json" \
  -d '{"filter":{"status":"active","tags":["devops","sre"],"created_after":"2026-01-01T00:00:00Z"}}' \
  -i
# → 200 OK с результатами поиска
```

**Преимущество перед POST /search:** Кэшируемость (Cache-Control может работать с идемпотентными запросами), безопасность (не изменяет состояние), идемпотентность (безопасный повтор).

### Сценарий 3: Атомарное обновление через JSON Patch (PATCH)

```http
PATCH /users/123 HTTP/1.1
Content-Type: application/json-patch+json

[
  { "op": "test", "path": "/version", "value": 5 },
  { "op": "replace", "path": "/email", "value": "new@example.com" },
  { "op": "add", "path": "/tags/-", "value": "vip" }
]
```

**Ожидаемый результат:**

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 123,
  "version": 5,
  "email": "new@example.com",
  "tags": ["devops", "sre", "vip"]
}
```

**Валидация:**

```bash
curl -X PATCH https://api.example.com/users/123 \
  -H "Content-Type: application/json-patch+json" \
  -d '[{"op":"test","path":"/version","value":5},{"op":"replace","path":"/email","value":"new@example.com"}]' \
  -i
# → 200 OK при совпадении version, или 412 Precondition Failed
```

**Обработка ошибки:** Если `version` не равна 5, запрос вернет `412 Precondition Failed`.

### Сценарий 4: Обеспечение идемпотентности для POST

Если клиент отправит `POST` дважды, на сервере могут создаться дубликаты. Решение — **ключи идемпотентности**:

**Алгоритм:**
1.  Клиент генерирует `Idempotency-Key: <UUID>` и отправляет его в заголовке.
2.  Сервер сохраняет ключ и результат первой обработки.
3.  При повторном запросе сервер возвращает сохраненный результат (200/201), не выполняя операцию снова.

```bash
# Первый запрос — создание ресурса
curl -X POST https://api.example.com/payments \
  -H "Idempotency-Key: a1b2c3d4-e5f6-7890-abcd-ef1234567890" \
  -H "Content-Type: application/json" \
  -d '{"amount": 1000, "currency": "USD"}' \
  -i
# → 201 Created с данными платежа

# Повторный запрос с тем же ключом
curl -X POST https://api.example.com/payments \
  -H "Idempotency-Key: a1b2c3d4-e5f6-7890-abcd-ef1234567890" \
  -H "Content-Type: application/json" \
  -d '{"amount": 1000, "currency": "USD"}' \
  -i
# → 201 Created с ТЕМ ЖЕ телом ответа (кэшировано сервером)
```

### Сценарий 5: Условное обновление через PUT с If-Match

```bash
# Получить текущий ETag ресурса
curl -i https://api.example.com/users/123
# → ETag: "abc123"

# Обновить только если ETag совпадает
curl -X PUT https://api.example.com/users/123 \
  -H "If-Match: \"abc123\"" \
  -H "Content-Type: application/json" \
  -d '{"name":"Ivan","email":"ivan@example.com"}' \
  -i
# → 200 OK при совпадении, или 412 Precondition Failed при изменении ресурса
```

### Сценарий 6: Диагностика прокси через TRACE

```bash
curl -X TRACE -i https://api.example.com/users
# → 200 OK с телом, содержащим весь запрос
```

**Ожидаемый результат (TRACE response):**

```http
HTTP/1.1 200 OK
Content-Type: message/http
Content-Length: 150

TRACE /users HTTP/1.1
Host: api.example.com
User-Agent: curl/8.5.0
Accept: */*
```

**Важно:** На большинстве production-серверов TRACE отключен из соображений безопасности (XST).

### Сценарий 7: Удаление ресурса с подтверждением

```bash
# Мягкое удаление (PATCH /users/123 с active=false)
curl -X PATCH https://api.example.com/users/123 \
  -H "Content-Type: application/json" \
  -d '{"active": false}' \
  -i
# → 200 OK

# Жесткое удаление
curl -X DELETE https://api.example.com/users/123 \
  -i
# → 204 No Content (ресурс удален)
# Повторный запрос вернет → 404 Not Found (идемпотентность подтверждена)
```

## Типичные проблемы и диагностика

| Проблема | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| `405 Method Not Allowed` | Метод не поддерживается ресурсом | `OPTIONS /resource` для проверки `Allow` | Изменить метод или настроить сервер |
| `411 Length Required` | Отсутствует `Content-Length` для метода с телом | Проверить заголовки запроса | Добавить `Content-Length` или `Transfer-Encoding: chunked` |
| `415 Unsupported Media Type` | Неверный `Content-Type` для PATCH/PUT | Проверить заголовок `Content-Type` | Использовать правильный MIME-type |
| `501 Not Implemented` | Сервер не поддерживает метод (например, TRACE) | Проверить конфигурацию сервера | Отключить метод или использовать прокси |
| `408 Request Timeout` при PUT/POST | Таймаут при передаче большого тела | `curl --trace-ascii -` для логов | Увеличить `timeout` на клиенте/сервере |
| Дубликаты при POST | Отсутствие идемпотентности | Проверить логи сервера | Добавить `Idempotency-Key` |
| `412 Precondition Failed` при PATCH | Несовпадение версии в `If-Match`/`test` | Проверить текущую версию ресурса | Обновить клиентский ETag/version |

## Лучшие практики

1.  **Строгое соблюдение семантики:** Используйте `GET` только для чтения, `POST` для создания, `PUT` для полной замены, `PATCH` для частичных изменений.
2.  **Идемпотентность для критичных операций:** Для `POST`, создающего платежи или заказы, всегда используйте `Idempotency-Key`.
3.  **Content-Type для PATCH:** Явно указывайте формат патча (`application/json-patch+json` или `application/merge-patch+json`).
4.  **Conditional Requests:** Используйте `If-Match`/`If-None-Match` для предотвращения Lost Updates и оптимизации кэширования.
5.  **Отключение TRACE:** Отключите `TRACE` на всех production-серверах для защиты от XST.
6.  **Контроль тела GET:** Убедитесь, что промежуточные узлы (proxy, CDN) не блокируют тело в GET — RFC 9110 запрещает его, но некорректные клиенты могут отправлять.
7.  **Валидация метода:** Используйте `OPTIONS` для реализации Capability Discovery в API.
8.  **QUERY вместо POST для поиска:** Предпочитайте `QUERY` (RFC 9421) для сложных поисковых запросов вместо `POST /search`.
9.  **DELETE идемпотентен:** Повторный `DELETE` того же ресурса должен возвращать `404`, а не `500`.
10. **PUT vs PATCH:** Используйте `PUT` для полной замены (клиент знает итоговое состояние), `PATCH` для частичных изменений (клиент знает только delta).

## Граничные случаи и ограничения

1.  **Тело в GET:** RFC 9110 §9.3.1 явно запрещает тело в GET. Серверы и прокси могут игнорировать или отклонять такие запросы. Клиенты не должны полагаться на тело GET.
2.  **Тело в DELETE:** RFC 9110 не определяет семантику тела в DELETE. Многие серверы игнорируют тело, некоторые отклоняют запрос. Рекомендуется избегать тела в DELETE.
3.  **CONNECT и Origin:** RFC 9110 §9.3.6 разрешает CONNECT только для Origin-сервера. Прокси могут ограничивать порты (например, блокировать порты 25, 465, 587 для SMTP).
4.  **JSON Patch идемпотентность:** Только при использовании `test` для проверки состояния. Простые последовательности `replace` не идемпотентны.
5.  **QUERY поддержка:** Метод QUERY (RFC 9421) поддерживается не всеми прокси и балансировщиками. Проверяйте поддержку в инфраструктуре.
6.  **OPTIONS и CORS:** Preflight-запросы (OPTIONS) кэшируются браузером (`Access-Control-Max-Age`), но не кэшируются промежуточными узлами.
7.  **Method Override и безопасность:** Не ограничивайте `X-HTTP-Method-Override` только безопасными методами — сервер должен проверять права на переопределяемый метод.
8.  **PUT и создание:** Сервер может вернуть `201 Created` вместо `200/204` при PUT к несуществующему URI, если поддержано создание.
9.  **PATCH и атомарность:** Все операции в JSON Patch должны применяться атомарно. При ошибке в середине массива сервер должен вернуть `409 Conflict` или `422 Unprocessable Entity`.
10. **Idempotency-Key TTL:** Ключ должен жить дольше, чем максимальное время ретрая клиента (обычно 24–48 часов).
