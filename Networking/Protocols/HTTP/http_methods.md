# Методы HTTP: Типы и характеристики

## Определения

**HTTP-метод (HTTP Method)** — это команда, указывающая серверу, какое действие необходимо выполнить над конкретным ресурсом. Семантика методов определена в стандарте **RFC 9110**. Метод является частью [стартовой строки (Request Line)](./http_basics.md) HTTP-запроса.

**Безопасный метод (Safe Method)** — метод, предназначенный только для получения информации, который не должен изменять состояние сервера (только чтение).

**Идемпотентный метод (Idempotent Method)** — метод, повторное выполнение которого с теми же параметрами приводит к тому же результату, что и однократное выполнение, не вызывая дополнительных изменений состояния сервера.


## Основные концепции

### Сводная таблица методов

| Метод | Назначение | CRUD | Идемпотентность | Безопасность | Кэширование |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **GET** | Получение данных | Read | Да | Да | Да |
| **POST** | Создание/обработка | Create | Нет | Нет | Нет |
| **PUT** | Полное обновление | Update | Да | Нет | Нет |
| **PATCH** | Частичное обновление | Update | Нет* | Нет | Нет |
| **DELETE** | Удаление ресурса | Delete | Да | Нет | Нет |
| **HEAD** | Только заголовки | — | Да | Да | Да |
| **OPTIONS** | Параметры связи | — | Да | Да | Нет |
| **TRACE** | Эхо-запрос | — | Да | Да | Нет |
| **CONNECT** | Туннелирование | — | Нет | Нет | Нет |

*\* PATCH (RFC 5789) может быть идемпотентным в зависимости от логики обработки (например, использование JSON Merge Patch).*

### Детальный разбор методов

#### GET — Получение ресурса

Запрашивает представление ресурса. Не должен иметь тела запроса. Параметры передаются в URI через [Query Parameters](./http_basics.md).

- **Использование:** Загрузка страниц, API-запросы списков/объектов.

#### POST — Создание или обработка данных

Используется для отправки сущности к ресурсу, что часто вызывает изменение состояния или побочные эффекты на сервере.

- **Использование:** Отправка форм, создание записей в БД, выполнение сложных операций.

#### PUT — Замена ресурса

Заменяет все текущее представление ресурса данными запроса. Если ресурса нет, может создать его (если это разрешено API).

- **Использование:** Обновление профиля пользователя целиком.

#### PATCH — Частичное изменение

Применяет частичные изменения к ресурсу. В отличие от PUT, передаются только изменяемые поля.

- **Использование:** Смена статуса заказа или обновление одного поля настройки.

#### DELETE — Удаление

Удаляет указанный ресурс. Повторный вызов DELETE того же ресурса вернет тот же результат (ресурс удален), поэтому метод идемпотентен.

- **Использование:** Удаление файла или пользователя.

#### HEAD — Проверка без загрузки

Аналогичен GET, но сервер возвращает ответ без тела. Используется для проверки доступности или размера файла.

- **Использование:** Проверка `Content-Length` перед загрузкой большого архива.

#### OPTIONS — Исследование возможностей

Используется для определения параметров соединения или доступных методов для ресурса.

- **Использование:** Предварительные запросы (Preflight) в [CORS (Cross-Origin Resource Sharing)](./http_basics.md#безопасность-и-заголовки-security-headers) для проверки разрешений браузером.

#### TRACE — Диагностическая петля

Сервер возвращает клиенту полученный запрос «как есть» (эхо). Позволяет увидеть, какие изменения вносят промежуточные серверы (прокси) в заголовки.

- **Безопасность:** Рекомендуется отключать на production-серверах (директива `TraceEnable off` в Apache), так как метод может быть использован для кражи куки через атаку **XST (Cross-Site Tracing)**.

#### CONNECT — Установление туннеля

Используется преимущественно для установления защищенного (HTTPS) соединения через прокси-сервер. Прокси создает TCP-соединение с целевым сервером и просто передает данные в обе стороны.

## Практические сценарии

### Сценарий 1: Проверка разрешенных методов через OPTIONS

С помощью `curl` можно узнать, какие действия разрешены для URL:

```bash
curl -X OPTIONS -i https://api.example.com/users
# → Результат в заголовке Allow: GET, POST, HEAD, OPTIONS
```

### Сценарий 2: Использование HEAD для проверки обновлений

Проверка, изменился ли файл на сервере без его скачивания:

```bash
curl -I https://example.com/data.zip
# → Проверяем заголовки ETag или Last-Modified
```

### Сценарий 3: Обеспечение идемпотентности для POST

Если клиент отправит `POST` дважды (например, из-за сетевого сбоя и повторной попытки), на сервере могут создаться два одинаковых заказа. Для решения этой проблемы используются **ключи идемпотентности** (Idempotency Key).

1. Клиент генерирует уникальный UUID и отправляет его в заголовке: `Idempotency-Key: 550e8400-e29b...`.
2. Сервер сохраняет ключ и результат первой успешной обработки.
3. При повторном запросе с тем же ключом сервер возвращает сохраненный результат без повторного выполнения операции.

### Выбор метода в REST API

Проектирование систем в стиле REST (Representational State Transfer) требует строгого соблюдения семантики методов. Подробные примеры сопоставления методов и URI см. в **[REST API](./http_rest_api.md)**.

### Безопасность и методы

Методы `TRACE` и `CONNECT` часто отключают на веб-серверах (Nginx, Angie) из соображений безопасности, чтобы предотвратить атаки типа Cross-Site Tracing (XST).
