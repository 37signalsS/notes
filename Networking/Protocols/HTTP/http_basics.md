# HTTP: Базовые концепции

## 1. Определения

**HTTP (Hypertext Transfer Protocol)** — протокол прикладного уровня для передачи гипертекста, являющийся основой Всемирной паутины (World Wide Web). Определяет правила взаимодействия веб-клиентов (браузеров, API-клиентов) и веб-серверов для обмена запросами и ответами.

**Ключевые характеристики:**

- Работает поверх [TCP](../TCP/overview.md) (транспортный уровень, надёжная доставка).
- Стандартные порты: **80** (HTTP), **443** (HTTPS).
- Следует модели «запрос-ответ» — сервер не инициирует соединения.

## 2. Основные концепции

### 2.1. Модель «Запрос-Ответ»

Протокол HTTP работает по модели «запрос-ответ»:

1. **Клиент** отправляет HTTP-запрос на сервер.
2. **Сервер** обрабатывает запрос и возвращает HTTP-ответ.

Сервер не может инициировать взаимодействие (за исключением технологий вроде [HTTP/2 Server Push](./http_versions.md), который устарел в HTTP/3). Для серверной инициации коммуникации используются альтернативные протоколы (WebSocket, Server-Sent Events).

### 2.2. Stateless-протокол (Протокол без сохранения состояния)

**HTTP является stateless-протоколом.** Каждый запрос рассматривается сервером как независимая транзакция — информация о предыдущих запросах не сохраняется.

**Преимущества:**

- **Масштабируемость:** Любой сервер в кластере может обработать запрос, так как нет привязки к сессии. Это упрощает горизонтальное масштабирование.
- **Надёжность:** Отказ одного сервера не влияет на пользователя — следующий запрос обработает другой сервер.
- **Простота:** Отсутствие управления состоянием упрощает архитектуру сервера.

**Недостатки:**

- **Избыточность:** Клиент вынужден передавать повторяющуюся информацию (данные аутентификации, предпочтения) с каждым запросом.

Для эмуляции состояния используются механизмы [Cookies](http_authentication.md#cookies), заголовки авторизации (`Authorization: Bearer ...`) или токены. Подробный анализ stateful/stateless в разных доменах см. в **[Stateful vs Stateless](../../../Concepts/stateful_vs_stateless.md)**.

### 2.3. Структура HTTP-сообщения

**Минимальный HTTP-запрос (HTTP/1.1):**

```http
GET / HTTP/1.1
Host: example.com

```

1. **Стартовая строка (Request Line):** `GET / HTTP/1.1` — метод, URI, версия протокола.
2. **Заголовки:** `Host: example.com` — обязателен в HTTP/1.1, указывает целевой хост.
3. **Пустая строка (CRLF):** Сигнал окончания заголовков.
4. **Тело (опционально):** В GET-запросах отсутствует; передаётся в POST/PUT/PATCH.

**Минимальный HTTP-ответ (HTTP/1.1):**

```http
HTTP/1.1 200 OK
Content-Length: 1234
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>...
```

1. **Строка состояния (Status Line):** `HTTP/1.1 200 OK` — версия, [код ответа](./http_status_codes.md), текстовое описание.
2. **Заголовки:** `Content-Length`, `Content-Type`, `Set-Cookie` и другие.
3. **Пустая строка (CRLF):** Разделяет заголовки и тело.
4. **Тело ответа (Response Body):** Сами данные (HTML, JSON, бинарные данные).

### 2.4. HTTP-методы

HTTP определяет набор методов (глаголов), указывающих на желаемое действие с ресурсом. Основные методы:

| Метод | Назначение | Идемпотентность | Безопасный |
| :--- | :--- | :--- | :--- |
| **GET** | Получение ресурса | ✅ Да | ✅ Да |
| **POST** | Создание ресурса | ❌ Нет | ❌ Нет |
| **PUT** | Полное обновление ресурса | ✅ Да | ❌ Нет |
| **PATCH** | Частичное обновление | ❌ Зависит от реализации | ❌ Нет |
| **DELETE** | Удаление ресурса | ✅ Да | ❌ Нет |

Подробное описание всех методов и их семантики см. в **[Методы HTTP](./http_methods.md)**.

### 2.5. Коды ответа HTTP

Сервер возвращает числовой код ответа, указывающий на результат обработки запроса. Коды разделены на 5 классов:

| Класс | Диапазон | Значение | Пример |
| :--- | :--- | :--- | :--- |
| **1xx** | 100–199 | Информационные | `100 Continue` |
| **2xx** | 200–299 | Успех | `200 OK`, `201 Created`, `204 No Content` |
| **3xx** | 300–399 | Перенаправление | `301 Moved Permanently`, `304 Not Modified` |
| **4xx** | 400–499 | Ошибка клиента | `400 Bad Request`, `401 Unauthorized`, `404 Not Found` |
| **5xx** | 500–599 | Ошибка сервера | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable` |

Полная таблица кодов с описаниями — в **[Коды ответа HTTP](./http_status_codes.md)**.

### 2.6. Версии HTTP

Протокол HTTP эволюционировал для решения проблем производительности и безопасности:

| Версия | Особенности |
| :--- | :--- |
| **HTTP/1.0** | Одно соединение на запрос, нет Keep-Alive по умолчанию |
| **HTTP/1.1** | Keep-Alive, pipelining, обязательный `Host`, chunked transfer |
| **HTTP/2** | Мультиплексирование, сжатие заголовков (HPACK), server push |
| **HTTP/3** | Основа на QUIC вместо TCP, решение Head-of-Line blocking |

Детальная эволюция и сравнение версий — в **[Эволюция HTTP](./http_versions.md)**.

## 3. Практические сценарии

### Сценарий 1: Просмотр структуры HTTP-запроса через curl

```bash
curl -v http://example.com/
```

Вывод покажет:

- Стартовую строку запроса: `> GET / HTTP/1.1`
- Заголовки: `> Host: example.com`, `> User-Agent: curl/...`
- Строку состояния ответа: `< HTTP/1.1 200 OK`
- Заголовки ответа: `< Content-Type: text/html`, `< Content-Length: ...`

### Сценарий 2: Stateless-архитектура REST API

При проектировании REST API каждый запрос должен содержать всю необходимую информацию:

```http
GET /api/v1/users/123 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Accept: application/json
```

Сервер не хранит состояние между запросами — токен авторизации передаётся каждый раз. Это позволяет балансировщику направлять запросы на любой инстанс API без привязки к сессии.

### Сценарий 3: Анализ кодов ответа при отладке

```bash
curl -s -o /dev/null -w "%{http_code}" https://api.example.com/resource
```

- **200** — ресурс найден и возвращён.
- **301/302** — ресурс перемещён, проверить `Location` в заголовках.
- **401** — требуется авторизация (см. [HTTP-аутентификация](./http_authentication.md)).
- **403** — авторизация прошла, но нет прав доступа.
- **404** — ресурс не существует.
- **500** — внутренняя ошибка сервера, смотреть логи приложения.

## 4. Дополнительная информация

### Роль HTTP в стеке протоколов

HTTP работает на **прикладном уровне (Layer 7)** модели OSI/TCP/IP:

- **Уровень приложений:** REST API, веб-сервисы, микросервисная коммуникация.
- **Зависит от:** [TCP](../TCP/overview.md) (транспорт), [TLS/SSL](../tls.md) (шифрование в HTTPS), [DNS](../DNS/dns.md) (разрешение имён).
- **Используется:** [Nginx/Angie](../../../WebServers/Nginx/Core/nginx_overview.md), балансировщики нагрузки, CDN, API Gateway.

### HTTP и DevOps

- **Health checks:** Балансировщики и оркестраторы используют HTTP-запросы (`GET /healthz`) для проверки работоспособности сервисов.
- **Мониторинг:** HTTP-метрики (латентность, коды ответа, RPS) — ключевой источник данных для SRE.
- **CI/CD:** Webhook'и (GitHub, GitLab) используют HTTP POST для триггеров пайплайнов.
- **Инфраструктура как код:** Terraform, Ansible взаимодействуют с API облачных провайдеров по HTTP.
