# HTTP: Базовые концепции

## 1. Определения

**HTTP (Hypertext Transfer Protocol)** — протокол прикладного уровня для передачи гипертекста, являющийся основой Всемирной паутины (World Wide Web). Определяет правила взаимодействия веб-клиентов (браузеров, API-клиентов) и веб-серверов для обмена запросами и ответами.

**Ключевые характеристики:**

- Работает поверх [TCP](../TCP/overview.md) (транспортный уровень, надёжная доставка).
- Стандартные порты: **80** (HTTP), **443** (HTTPS).
- Следует модели «запрос-ответ» — сервер не инициирует соединения.

## 2. Основные концепции

### 2.1. Модель «Запрос-Ответ»

Протокол HTTP работает по модели «запрос-ответ»:

1. **Клиент** отправляет HTTP-запрос на сервер.
2. **Сервер** обрабатывает запрос и возвращает HTTP-ответ.

Сервер не может инициировать взаимодействие (за исключением технологий вроде [HTTP/2 Server Push](./http_versions.md), который устарел в HTTP/3). Для серверной инициации коммуникации используются альтернативные протоколы (WebSocket, Server-Sent Events).

### 2.2. Stateless-протокол (Протокол без сохранения состояния)

**HTTP является stateless-протоколом.** Каждый запрос рассматривается сервером как независимая транзакция — информация о предыдущих запросах не сохраняется.

**Преимущества:**

- **Масштабируемость:** Любой сервер в кластере может обработать запрос, так как нет привязки к сессии. Это упрощает горизонтальное масштабирование.
- **Надёжность:** Отказ одного сервера не влияет на пользователя — следующий запрос обработает другой сервер.
- **Простота:** Отсутствие управления состоянием упрощает архитектуру сервера.

**Недостатки:**

- **Избыточность:** Клиент вынужден передавать повторяющуюся информацию (данные аутентификации, предпочтения) с каждым запросом.

Для идентификации клиента между запросами и эмуляции состояния используются механизмы [Cookies](http_authentication.md#cookies), заголовки авторизации (`Authorization: Bearer ...`) или токены. Подробный анализ stateful/stateless в разных доменах см. в **[Stateful vs Stateless](../../../Concepts/stateful_vs_stateless.md)**.

### 2.3. Управление соединением (Connection Management)

Открытие TCP-соединения — дорогостоящая операция. В HTTP существует два основных подхода к управлению соединениями:

- **Short-lived (Connection: close):** Соединение открывается для одного запроса, передаётся ответ, и соединение сразу закрывается.
  - **Маркер завершения:** Для клиента сигналом окончания данных служит само закрытие TCP-соединения сервером.
  - **Минус:** Огромная нагрузка на сервер при загрузке страниц с множеством ресурсов (картинки, стили), так как на каждый файл тратится время на TCP-handshake.
- **Persistent Connections (Keep-Alive):** Соединение удерживается открытым в течение некоторого времени (обычно несколько секунд) после отправки ответа.
  - **Зачем это нужно:** Современная веб-страница может содержать 100+ элементов. Keep-Alive позволяет клиенту последовательно запросить все ресурсы в рамках одного и того же соединения.
  - **Маркер завершения (Content-Length):** В этом режиме соединение не закрывается, поэтому клиент не может ориентироваться на разрыв связи. Он обязан прочитать ровно столько байт, сколько указано в заголовке `Content-Length`. Если заголовок отсутствует или неверен, клиент может "зависнуть", ожидая продолжения данных.
  - Управляется заголовком `Connection: keep-alive` (по умолчанию в HTTP/1.1).

### 2.4. Механизм Cookies и сессии

Так как HTTP является stateless, сервер не "узнает" клиента при втором запросе. Для решения этой проблемы используются Cookies:

1. **Установка (Set-Cookie):** При первом запросе (например, логине) сервер генерирует уникальный ID и отправляет его в заголовке ответа `Set-Cookie: session_id=abc12345`.
2. **Хранение:** Браузер сохраняет этот ID локально.
3. **Идентификация (Cookie):** При всех последующих запросах к этому домену браузер автоматически добавляет заголовок `Cookie: session_id=abc12345`.
4. **Результат:** Сервер получает ID, находит связанные с ним данные в своей базе и "вспоминает" клиента (его корзину, настройки темы и т.д.).

### 2.5. Параметры запроса (Query Parameters)

Данные могут передаваться серверу прямо в URI после знака вопроса `?`.

**Формат:** `?key1=value1&key2=value2`

- **`?`** — начало строки параметров.
- **`&`** — разделитель пар ключ-значение.
- **`=`** — разделитель ключа и значения.

**Важная особенность:** Параметры в HTTP всегда передаются как **текст**. Если приложению нужны числа, оно должно самостоятельно выполнить преобразование (например, распарсить строку `"10"` в тип `int`).

### 2.6. Структура HTTP-сообщения

Каждая строка в HTTP-сообщении (за исключением последней в теле) обязана заканчиваться двумя спецсимволами: **CR** (Carriage Return) и **LF** (Line Feed). В коде это выглядит как `\r\n`.

**Минимальный HTTP-запрос (HTTP/1.1):**

```http
GET /index.html?user=alex HTTP/1.1
Host: example.com
Connection: keep-alive

```

1. **Стартовая строка (Request Line):** `МЕТОД ЮРАЙ ВЕРСИЯ`. Пример: `GET /index.html HTTP/1.1`.
2. **Заголовки:** Набор пар `Ключ: Значение`.
3. **Пустая строка (CRLF):** Критически важный маркер (2 байта `\r\n`), отделяющий заголовки от тела.
4. **Тело (опционально):** Данные запроса (например, JSON в POST-запросе).

**Минимальный HTTP-ответ (HTTP/1.1):**

```http
HTTP/1.1 200 OK
Content-Length: 46
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>...
```

1. **Строка состояния (Status Line):** `ВЕРСИЯ КОД ТЕКСТ`. Пример: `HTTP/1.1 200 OK`.
2. **Заголовки:**
   - `Content-Type`: указывает тип содержимого (`text/html`, `application/json`, `image/png`).
   - **`Content-Length`:** Размер тела в байтах.
3. **Пустая строка (CRLF):** Сигнал начала тела.
4. **Тело ответа (Response Body):** Может содержать HTML-страницу, JSON-объект, картинку или бинарный файл. Если браузер получает файл, который не умеет отображать (например, `.docx`), он предложит его скачать. Для принудительного скачивания используется заголовок `Content-Disposition: attachment; filename="file.txt"`.

### 2.7. Отдача статических файлов

В простейшем виде веб-сервер работает как «маппер» (отражение) URI на файловую систему сервера:

1. Клиент запрашивает ресурс, например `GET /images/logo.png`.
2. Сервер берет путь из URI и ищет соответствующий файл в своей корневой директории статики (например, в `/var/www/html/` ищет файл `images/logo.png`).
3. Если файл найден, сервер считывает его содержимое как поток байтов и отправляет их в теле ответа.
4. При этом сервер сам устанавливает правильный `Content-Type` (на основе расширения файла) и `Content-Length` (на основе размера файла на диске).
5. Если файла на диске нет — сервер формирует ответ `404 Not Found`.

Современные браузеры при загрузке HTML-страницы автоматически анализируют её содержимое и инициируют дополнительные HTTP-запросы для всех вложенных ресурсов (картинок, скриптов), указанных в тегах `<img>`, `<script>`, `<link>`.

### 2.5. Коды ответа HTTP

Сервер возвращает числовой код ответа, указывающий на результат обработки запроса. Коды разделены на 5 семейств:

| Класс | Диапазон | Значение | Описание из транскрипта |
| :--- | :--- | :--- | :--- |
| **1xx** | 100–199 | Информационные | Служебная информация |
| **2xx** | 200–299 | Успех | Успешные коды, все нормально |
| **3xx** | 300–399 | Перенаправление | Редиректы |
| **4xx** | 400–499 | Ошибка клиента | Ошибка на стороне клиента (не удалось попасть на сайт) |
| **5xx** | 500–599 | Ошибка сервера | Сервер сломался |

Полная таблица кодов с описаниями — в **[Коды ответа HTTP](./http_status_codes.md)**.

### 2.6. HTTP-методы

В HTTP есть специальные методы для указания типа действия. Самые популярные:

- **GET** — получить данные (например, файл `index.html`).
- **POST** — отправить данные на сервер.
- **PUT** — обновить существующие данные.
- **DELETE** — удалить данные.

Подробное описание всех методов и их семантики см. в **[Методы HTTP](./http_methods.md)**.

### 2.7. Проблема безопасности HTTP

Сам по себе HTTP передает все **открытым текстом**. Любое промежуточное звено (провайдер, оператор) видит трафик: страницы, данные форм и пароли. Эту проблему решает **TLS**, оборачивающий HTTP в шифрованный туннель, образуя **HTTPS**.

### 2.6. Версии HTTP

Протокол HTTP эволюционировал для решения проблем производительности и безопасности:

| Версия | Особенности |
| :--- | :--- |
| **HTTP/1.0** | Одно соединение на запрос, нет Keep-Alive по умолчанию |
| **HTTP/1.1** | Keep-Alive, pipelining, обязательный `Host`, chunked transfer |
| **HTTP/2** | Мультиплексирование, сжатие заголовков (HPACK), server push |
| **HTTP/3** | Основа на QUIC вместо TCP, решение Head-of-Line blocking |

Детальная эволюция и сравнение версий — в **[Эволюция HTTP](./http_versions.md)**.

## 3. Практические сценарии

### Сценарий 1: Просмотр структуры HTTP-запроса через curl

```bash
curl -v http://example.com/
```

Вывод покажет:

- Стартовую строку запроса: `> GET / HTTP/1.1`
- Заголовки: `> Host: example.com`, `> User-Agent: curl/...`
- Строку состояния ответа: `< HTTP/1.1 200 OK`
- Заголовки ответа: `< Content-Type: text/html`, `< Content-Length: ...`

### Сценарий 2: Stateless-архитектура REST API

При проектировании REST API каждый запрос должен содержать всю необходимую информацию:

```http
GET /api/v1/users/123 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Accept: application/json
```

Сервер не хранит состояние между запросами — токен авторизации передаётся каждый раз. Это позволяет балансировщику направлять запросы на любой инстанс API без привязки к сессии.

### Сценарий 3: Анализ кодов ответа при отладке

```bash
curl -s -o /dev/null -w "%{http_code}" https://api.example.com/resource
```

- **200** — ресурс найден и возвращён.
- **301/302** — ресурс перемещён, проверить `Location` в заголовках.
- **401** — требуется авторизация (см. [HTTP-аутентификация](./http_authentication.md)).
- **403** — авторизация прошла, но нет прав доступа.
- **404** — ресурс не существует.
- **500** — внутренняя ошибка сервера, смотреть логи приложения.

## 4. Дополнительная информация

### Роль HTTP в стеке протоколов

HTTP работает на **прикладном уровне (Layer 7)** модели OSI/TCP/IP:

- **Уровень приложений:** REST API, веб-сервисы, микросервисная коммуникация.
- **Зависит от:** [TCP](../TCP/overview.md) (транспорт), [TLS/SSL](../tls.md) (шифрование в HTTPS), [DNS](../DNS/dns.md) (разрешение имён).
- **Используется:** [Nginx/Angie](../../../WebServers/Nginx/Core/nginx_overview.md), балансировщики нагрузки, CDN, API Gateway.

### HTTP и DevOps

- **Health checks:** Балансировщики и оркестраторы используют HTTP-запросы (`GET /healthz`) для проверки работоспособности сервисов.
- **Мониторинг:** HTTP-метрики (латентность, коды ответа, RPS) — ключевой источник данных для SRE.
- **CI/CD:** Webhook'и (GitHub, GitLab) используют HTTP POST для триггеров пайплайнов.
- **Инфраструктура как код:** Terraform, Ansible взаимодействуют с API облачных провайдеров по HTTP.
