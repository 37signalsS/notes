# HTTP: Базовые концепции

## Определения

**HTTP (Hypertext Transfer Protocol)** — протокол прикладного уровня для передачи гипертекста, являющийся основой Всемирной паутины (World Wide Web). Современные спецификации протокола консолидированы в серии **RFC 911x** (в частности, **RFC 9110** определяет общую семантику и архитектуру). HTTP определяет правила взаимодействия веб-клиентов (User Agents), серверов (Origin Servers) и промежуточных узлов (Intermediaries) для обмена ресурсами.

**Ключевые характеристики:**

- **Прикладной уровень:** Работает поверх [TCP](../TCP/overview.md) (порт 80 для HTTP, 443 для HTTPS) или [QUIC](./http_versions.md#http3-2022) (в HTTP/3).
- **Модель «Запрос-Ответ»:** Клиент инициирует соединение, сервер отвечает.
- **Расширяемость:** Заголовки позволяют легко добавлять новые возможности (кэширование, авторизация, сжатие).

## Основные концепции

### Структура URI (Uniform Resource Identifier)

Ресурс в HTTP идентифицируется с помощью URI. Типичный HTTP URL (Subset URI) состоит из следующих частей:

`https://user:pass@example.com:8080/path/to/resource?query=value#fragment`

1.  **Scheme (Схема):** Протокол (`http`, `https`).
2.  **Authority (Власть):**
    - **UserInfo:** Необязательные данные пользователя (`user:pass`).
    - **Host:** Доменное имя или IP-адрес (`example.com`).
    - **Port:** Необязательный порт (`8080`).
3.  **Path (Путь):** Иерархический путь к ресурсу (`/path/to/resource`).
4.  **Query (Запрос):** Необязательные параметры (`?query=value`).
5.  **Fragment (Фрагмент):** Ссылка на часть внутри ресурса (`#fragment`). Не передаётся серверу в HTTP-запросе, обрабатывается клиентом.

### Модель «Запрос-Ответ»

Протокол HTTP работает по модели «запрос-ответ»:

1. **Клиент** отправляет HTTP-запрос на сервер.
2. **Сервер** обрабатывает запрос и возвращает HTTP-ответ.

Сервер не может инициировать взаимодействие (за исключением технологий вроде [HTTP/2 Server Push](./http_versions.md), который устарел в HTTP/3). Для серверной инициации коммуникации используются альтернативные протоколы (WebSocket, Server-Sent Events).

### Протокол без сохранения состояния (Stateless)

**HTTP является stateless-протоколом.** Каждый запрос рассматривается сервером как независимая транзакция — информация о предыдущих запросах не сохраняется.

**Преимущества:**

- **Масштабируемость:** Любой сервер в кластере может обработать запрос, так как нет привязки к сессии. Это упрощает горизонтальное масштабирование.
- **Надёжность:** Отказ одного сервера не влияет на пользователя — следующий запрос обработает другой сервер.
- **Простота:** Отсутствие управления состоянием упрощает архитектуру сервера.

**Недостатки:**

- **Избыточность:** Клиент вынужден передавать повторяющуюся информацию (данные аутентификации, предпочтения) с каждым запросом.

Для идентификации клиента между запросами и эмуляции состояния используются механизмы [Cookies](http_authentication.md#куки-и-сессии-cookies-and-sessions), заголовки авторизации (`Authorization: Bearer ...`) или токены. Подробный анализ stateful/stateless в разных доменах см. в **[Stateful vs Stateless](../../../Concepts/stateful_vs_stateless.md)**.

### Управление соединением

Открытие TCP-соединения — дорогостоящая операция. В HTTP существует два основных подхода к управлению соединениями:

- **Short-lived (Connection: close):** Соединение открывается для одного запроса, передаётся ответ, и соединение сразу закрывается.
  - **Маркер завершения:** Для клиента сигналом окончания данных служит само закрытие TCP-соединения сервером.
  - **Минус:** Огромная нагрузка на сервер при загрузке страниц с множеством ресурсов (картинки, стили), так как на каждый файл тратится время на TCP-handshake.
- **Постоянные соединения (Keep-Alive):** Соединение удерживается открытым в течение некоторого времени (обычно несколько секунд) после отправки ответа.
  - **Зачем это нужно:** Современная веб-страница может содержать 100+ элементов. Keep-Alive позволяет клиенту последовательно запросить все ресурсы в рамках одного и того же соединения.
  - **Маркеры завершения сообщения:** Так как соединение не закрывается, клиент должен знать, где заканчивается один ответ и начинается другой. Используется два основных механизма:
    1. **`Content-Length`:** Указывает точный размер тела в байтах. Если заголовок отсутствует или неверен, клиент может "зависнуть".
    2. **`Transfer-Encoding: chunked`:** Позволяет серверу отправлять данные по мере их генерации, разделяя их на блоки (чанки). Последний пустой блок сигнализирует об окончании передачи. Это критично для динамического контента, размер которого заранее неизвестен.
  - Управляется заголовком `Connection: keep-alive` (по умолчанию в HTTP/1.1).

### Механизм Cookies и сессии

Так как HTTP является stateless, сервер не "узнает" клиента при втором запросе. Для решения этой проблемы используются Cookies:

1. **Установка (Set-Cookie):** При первым запросе (например, логине) сервер генерирует уникальный ID и отправляет его в заголовке ответа `Set-Cookie: session_id=abc12345`.
2. **Хранение:** Браузер сохраняет этот ID локально.
3. **Идентификация (Cookie):** При всех последующих запросах к этому домену браузер автоматически добавляет заголовок `Cookie: session_id=abc12345`.
4. **Результат:** Сервер получает ID, находит связанные с ним данные в своей базе и "вспоминает" клиента (его корзину, настройки темы и т.д.).

### Параметры запроса (Query Parameters)

Данные могут передаваться серверу прямо в URI после знака вопроса `?`.

**Формат:** `?key1=value1&key2=value2`

- **`?`** — начало строки параметров.
- **`&`** — разделитель пар ключ-значение.
- **`=`** — разделитель ключа и значения.

**Важная особенность:** Параметры в HTTP всегда передаются как **текст**. Если приложению нужны числа, оно должно самостоятельно выполнить преобразование (например, распарсить строку `"10"` в тип `int`).

### Структура HTTP-сообщения

HTTP-сообщения являются текстовыми (в HTTP/1.1) и имеют четкую структуру. Каждая строка (кроме последней в теле) заканчивается последовательностью **CRLF** (`\r\n`).

**Минимальный HTTP-запрос:**

```http
GET /index.html HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html

```

1.  **Стартовая строка (Request Line):** `Method Request-Target HTTP-Version`. Пример: `GET /index.html HTTP/1.1`.
2.  **Заголовки (Headers):** Набор пар `Field-Name: Field-Value`.
3.  **Пустая строка (CRLF):** Обязательный разделитель заголовков и тела.
4.  **Тело (Payload):** Данные (JSON, форма, бинарный поток). Отсутствует в большинстве GET-запросов.

**Минимальный HTTP-ответ:**

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 46

<!DOCTYPE html>...
```

1.  **Строка состояния (Status Line):** `HTTP-Version Status-Code Reason-Phrase`. Пример: `HTTP/1.1 200 OK`.
2.  **Заголовки:** Метаданные ответа.
3.  **Пустая строка (CRLF):** Разделитель.
4.  **Тело (Response Body):** Содержимое ресурса.

#### Классификация заголовков (RFC 9110)

В современных спецификациях заголовки делятся на:
-   **Request Fields:** Только в запросах (`Accept`, `User-Agent`).
-   **Response Fields:** Только в ответах (`Server`, `Allow`).
- **Representation Fields:** Описывают формат ресурса (`Content-Type`, `Content-Encoding`).

#### Content-Type и восприятие тела запроса сервером

**Content-Type** — критически важный заголовок для запросов с телом (POST, PUT, PATCH). Он указывает серверу, как интерпретировать переданные данные.

**Распространенные значения:**

| Content-Type | Применение | Пример тела |
|:---|:---|:---|
| `application/json` | REST API, JSON-данные | `{"name": "test"}` |
| `application/x-www-form-urlencoded` | HTML-формы | `name=test&value=123` |
| `multipart/form-data` | Загрузка файлов | Бинарные данные с границами |
| `text/plain` | Простой текст | Любой текст |
| `application/xml` | SOAP, XML API | `<root><item>1</item></root>` |

**Проблема отсутствующего Content-Type:**

Многие серверные фреймворки (Spring Boot, Express, Flask) полагаются на заголовок `Content-Type` для определения способа парсинга тела запроса:

1. Если `Content-Type: application/json` — сервер парсит тело как JSON.
2. Если `Content-Type` отсутствует — сервер может:
   - Вернуть `400 Bad Request` (Spring Boot по умолчанию).
   - Вернуть `415 Unsupported Media Type`.
   - Попытаться парсить как form-data и получить пустые данные.

**Разница между curl и Postman:**

- **curl** по умолчанию НЕ устанавливает `Content-Type` для POST-запросов с `-d`:
  ```bash
  curl -X POST http://api.example.com/data -d '{"key":"value"}'
  # Content-Type отсутствует → сервер может вернуть 400
  ```
  
  Явное указание:
  ```bash
  curl -X POST http://api.example.com/data \
    -H "Content-Type: application/json" \
    -d '{"key":"value"}'
  ```

- **Postman** автоматически определяет тип контента по содержимому тела и устанавливает соответствующий `Content-Type`:
  - Если в теле JSON — ставит `application/json`.
  - Если форма — `application/x-www-form-urlencoded`.

**Диагностика проблем с Content-Type:**

```bash
# Проверка заголовков запроса
curl -v -X POST http://api.example.com/data -d '{"key":"value"}'
# Обратить внимание на строку:
# > Content-Type: application/x-www-form-urlencoded  (по умолчанию для -d)

# Явное указание JSON
curl -v -X POST http://api.example.com/data \
  -H "Content-Type: application/json" \
  -d '{"key":"value"}'
```

**Важно:** При использовании `--data-binary` в curl заголовок НЕ устанавливается автоматически. При использовании `-d` curl ставит `application/x-www-form-urlencoded`, если не указан другой тип явно.
-   **Payload Fields:** Описывают само тело сообщения (`Content-Length`, `Content-Range`).

### Промежуточные узлы (Intermediaries)

HTTP спроектирован для работы через цепочку узлов:

1.  **Proxy (Прокси):** Агент, действующий от имени клиента.
    - **Forward Proxy:** Скрывает клиента от сервера (используется для обхода ограничений или кеширования в локальной сети).
    - **Reverse Proxy:** Скрывает группу серверов от клиента (используется для балансировки нагрузки, терминации SSL). Пример: [Nginx](../../../WebServers/Nginx/Core/nginx_overview.md).
2.  **Gateway (Шлюз):** Сервер, действующий как посредник для другого сервера. В отличие от прокси, шлюз получает запросы так, будто он сам является целевым сервером (Origin Server).
3.  **CDN (Content Delivery Network):** Распределенная сеть кеширующих серверов, доставляющая контент из ближайшей к пользователю точки.

### Отдача статических файлов

В простейшем виде веб-сервер работает как «маппер» (отражение) URI на файловую систему сервера:

1. Клиент запрашивает ресурс, например `GET /images/logo.png`.
2. Сервер берет путь из URI и ищет соответствующий файл в своей корневой директории статики (например, в `/var/www/html/` ищет файл `images/logo.png`).
3. Если файл найден, сервер считывает его содержимое как поток байтов и отправляет их в теле ответа.
4. При этом сервер сам устанавливает правильный `Content-Type` (на основе расширения файла) и `Content-Length` (на основе размера файла на диске).
5. Если файла на диске нет — сервер формирует ответ `404 Not Found`.

Современные браузеры при загрузке HTML-страницы автоматически анализируют её содержимое и инициируют дополнительные HTTP-запросы для всех вложенных ресурсов (картинок, скриптов), указанных в тегах `<img>`, `<script>`, `<link>`.

### Согласование контента (Content Negotiation)

Механизм, позволяющий серверу отдавать разные представления одного и того же ресурса в зависимости от предпочтений клиента.

- **Client-driven:** Клиент указывает предпочтения в заголовках `Accept` (формат), `Accept-Language` (язык), `Accept-Encoding` (сжатие).
- **Server-driven:** Сервер выбирает оптимальный вариант и сообщает о выборе через `Content-Type`, `Content-Language` и заголовок `Vary` (указывает, какие заголовки повлияли на выбор, что критично для кеширования).

### Кэширование (Базовые принципы)

Кеширование позволяет избегать повторной передачи данных, экономя время и ресурсы. Основные механизмы:

1.  **Управление свежестью (Freshness):** Заголовок `Cache-Control` (например, `max-age=3600`) указывает, как долго ответ считается «свежим» и может быть отдан из кеша без запроса к серверу.
2.  **Валидация (Validation):** Если срок свежести истек, клиент отправляет запрос с заголовками `If-None-Match` (проверка [ETag](./http_caching.md)) или `If-Modified-Since`.
3.  **Ответ сервера:**
    - `304 Not Modified`: Ресурс не изменился, используйте версию из кеша.
    - `200 OK`: Ресурс обновился, передано новое тело.

Подробности см. в **[HTTP-кэширование](./http_caching.md)**.

### Коды ответа HTTP

Сервер возвращает числовой код ответа, указывающий на результат обработки запроса. Коды разделены на 5 семейств:

| Класс | Диапазон | Значение | Описание |
| :--- | :--- | :--- | :--- |
| **1xx** | 100–199 | Информационные | Служебная информация (например, **103 Early Hints** для предварительной загрузки ресурсов) |
| **2xx** | 200–299 | Успех | Запрос успешно обработан |
| **3xx** | 300–399 | Перенаправление | Ресурс перемещен (редиректы) |
| **4xx** | 400–499 | Ошибка клиента | Некорректный запрос или отсутствие прав доступа |
| **5xx** | 500–599 | Ошибка сервера | Проблема на стороне сервера |

Полная таблица кодов с описаниями — в **[Коды ответа HTTP](./http_status_codes.md)**.

### Методы HTTP

В HTTP есть специальные методы для указания типа действия. Самые популярные:

- **GET** — получить данные.
- **POST** — отправить данные на сервер.
- **PUT** — обновить существующие данные.
- **DELETE** — удалить данные.

Подробное описание всех методов и их семантики см. в **[Методы HTTP](./http_methods.md)**.

### Безопасность HTTP и HTTPS

Сам по себе HTTP передает все **открытым текстом**. Любое промежуточное звено (провайдер, оператор) видит трафик: страницы, данные форм и пароли. Эту проблему решает **TLS**, оборачивающий HTTP в шифрованный туннель, образуя **HTTPS**.

**Как работает HTTPS (кратко):**

1. **Запрос соединения:** Клиент инициирует HTTPS-соединение (порт 443).
2. **Проверка сертификата (Handshake):** Сервер отправляет свой публичный ключ и **SSL/TLS-сертификат**, подтвержденный Доверенным Центром Сертификации (CA). Клиент проверяет подлинность сертификата.
3. **Обмен ключами:** Клиент и сервер договариваются об общем «сессионном ключе» с помощью асимметричного шифрования.
4. **Шифрование данных:** Все последующие HTTP-сообщения шифруются этим сессионным ключом (симметричное шифрование), который известен только клиенту и серверу.

Подробности: **[Протокол TLS](../tls.md)**.

### Версии HTTP

Протокол HTTP эволюционировал для решения проблем производительности и безопасности:

| Версия | Особенности | Спецификация |
| :--- | :--- | :--- |
| **HTTP/1.1** | Keep-Alive, чанки (`chunked`), обязательный `Host`. | RFC 9112 |
| **HTTP/2** | Бинарный протокол, мультиплексирование, HPACK. | RFC 9113 |
| **HTTP/3** | Базируется на QUIC (UDP), убирает HOL-блокировку, QPACK. | RFC 9114 |

Детальная эволюция и сравнение версий — в **[Эволюция HTTP](./http_versions.md)**.

## Практические сценарии

### Сценарий 1: Просмотр структуры HTTP-запроса через curl

```bash
curl -v http://example.com/
```

Вывод покажет:

- Стартовую строку запроса: `> GET / HTTP/1.1`
- Заголовки: `> Host: example.com`, `> User-Agent: curl/...`
- Строку состояния ответа: `< HTTP/1.1 200 OK`
- Заголовки ответа: `< Content-Type: text/html`, `< Content-Length: ...`

### Сценарий 2: Stateless-архитектура REST API

При проектировании REST API каждый запрос должен содержать всю необходимую информацию:

```http
GET /api/v1/users/123 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Accept: application/json
```

Сервер не хранит состояние между запросами — токен авторизации передаётся каждый раз. Это позволяет балансировщику направлять запросы на любой инстанс API без привязки к сессии.

### Сценарий 3: Анализ кодов ответа при отладке

```bash
curl -s -o /dev/null -w "%{http_code}" https://api.example.com/resource
```

- **200** — ресурс найден и возвращён.
- **301/302** — ресурс перемещён, проверить `Location` в заголовках.
- **401** — требуется авторизация (см. [HTTP-аутентификация](./http_authentication.md)).
- **403** — авторизация прошла, но нет прав доступа.
- **404** — ресурс не существует.
- **500** — внутренняя ошибка сервера, смотреть логи приложения.

### Сценарий 4: Оптимизация с использованием 103 Early Hints

Если серверу требуется время на генерацию ответа (например, сложный запрос к БД), он может отправить код `103 Early Hints` со списком ресурсов, которые браузер может начать загружать заранее.

```http
HTTP/1.1 103 Early Hints
Link: </style.css>; rel=preload; as=style
Link: </script.js>; rel=preload; as=script

HTTP/1.1 200 OK
Content-Type: text/html
...
```

Это значительно сокращает время отрисовки страницы (LCP — Largest Contentful Paint).

## Дополнительная информация

### Сжатие контента

Для экономии трафика и ускорения загрузки HTTP поддерживает сжатие тела ответа. Клиент сообщает о поддержке алгоритмов в заголовке `Accept-Encoding: gzip, br, zstd`.

- **Gzip:** Самый старый и универсальный метод.
- **Brotli (`br`):** Обеспечивает лучшее сжатие для статических файлов (JS, CSS) по сравнению с Gzip.
- **Zstandard (`zstd`):** Современный стандарт (RFC 9659), предлагающий оптимальный баланс между скоростью сжатия и его качеством, особенно эффективен для динамических API.

### Безопасность и заголовки (Security Headers)

Помимо шифрования TLS, современный HTTP использует специальные заголовки для защиты от атак:

- **HSTS (Strict-Transport-Security):** Предписывает браузеру использовать только HTTPS.
- **CSP (Content-Security-Policy):** Ограничивает источники, из которых могут загружаться ресурсы (скрипты, стили), защищая от XSS.
- **CORS (Cross-Origin Resource Sharing):** Механизм, позволяющий браузеру запрашивать ресурсы с другого домена. Использует метод `OPTIONS` для предварительной проверки разрешений.

### Роль HTTP в стеке протоколов

HTTP работает на **прикладном уровне (Layer 7)** модели OSI/TCP/IP:

- **Уровень приложений:** REST API, веб-сервисы, микросервисная коммуникация.
- **Зависит от:** [TCP](../TCP/overview.md) (транспорт), [TLS/SSL](../tls.md) (шифрование в HTTPS), [DNS](../DNS/dns.md) (разрешение имён).
- **Используется:** [Nginx/Angie](../../../WebServers/Nginx/Core/nginx_overview.md), балансировщики нагрузки, CDN, API Gateway.

### HTTP и DevOps

- **Health checks:** Балансировщики и оркестраторы используют HTTP-запросы (`GET /healthz`) для проверки работоспособности сервисов.
- **Мониторинг:** HTTP-метрики (латентность, коды ответа, RPS) — ключевой источник данных для SRE.
- **CI/CD:** Webhook'и (GitHub, GitLab) используют HTTP POST для триггеров пайплайнов.
- **Инфраструктура как код:** Terraform, Ansible взаимодействуют с API облачных провайдеров по HTTP.
