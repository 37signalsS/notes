# HTTP-коды ответа

## Определения

**HTTP-код ответа (Status Code)** — трёхзначное число в первой строке HTTP-ответа сервера, указывающее на результат обработки запроса. Семантика стандартных кодов определена в **RFC 9110**. Код является частью [строки состояния (Status Line)](./http_basics.md) формата `HTTP/<версия> <код> <текст>`.

**Структура кода:**

- **Первая цифра** — класс ответа (1–5), определяющий общую категорию результата.
- **Вторая и третья цифры** — спецификация конкретного состояния внутри класса.
- **Reason Phrase** — текстовое описание, несущественное для протокола (RFC 9110 §15.4.2), но сохраняемое для обратной совместимости.

**Пример:** `HTTP/1.1 200 OK` — версия HTTP/1.1, код 200 (успех), текст OK (Reason Phrase).

## Основные концепции

### Классы кодов ответа

HTTP-коды разделены на 5 классов:

| Класс | Диапазон | Значение | Описание (DevOps/SRE перспектива) |
| :--- | :--- | :--- | :--- |
| **1xx** | 100–199 | Информационные | Протокольные уведомления (Upgrade, Early Hints). |
| **2xx** | 200–299 | Успешные | Основная метрика успеха. |
| **3xx** | 300–399 | Перенаправления | Влияют на Latency из-за дополнительных RTT. |
| **4xx** | 400–499 | Ошибки клиента | Ошибки интеграции, безопасности или Rate Limits. |
| **5xx** | 500–599 | Ошибки сервера | Критический показатель (Error Budget). Требуют немедленной реакции. |

### 1xx — Информационные коды

Используются для обмена служебной информацией до передачи основного тела ответа.

| Код | Название | RFC | Описание |
| :--- | :--- | :--- | :--- |
| **100** | Continue | RFC 9110 §15.2.1 | Сигнал клиенту, что заголовки приняты и можно отправлять тело (заголовок `Expect: 100-continue`). Полезно перед загрузкой больших файлов. |
| **101** | Switching Protocols | RFC 9110 §15.2.2 | Смена протокола (например, апгрейд до WebSocket). В ответе должен быть заголовок `Upgrade`. |
| **102** | Processing | RFC 2518 §10.1 | Используется в WebDAV для предотвращения таймаута клиента при долгих операциях (batch, lock). |
| **103** | Early Hints | RFC 8297 | Позволяет браузеру начать загрузку ресурсов (CSS/JS) пока сервер генерирует основной ответ. В ответе заголовки `Link`. |

### 2xx — Успешные коды

Указывают на то, что запрос был получен, понят и успешно обработан.

| Код | Название | RFC | Описание | Применение |
| :--- | :--- | :--- | :--- | :--- |
| **200** | OK | RFC 9110 §15.3.1 | Стандарт для успешных запросов. Тело ответа содержит результат операции. | `GET`, `PUT`, `PATCH`. |
| **201** | Created | RFC 9110 §15.3.2 | Ресурс создан. | `POST`. Заголовок `Location` содержит URI нового ресурса. |
| **202** | Accepted | RFC 9110 §15.3.3 | Принято в обработку. | Асинхронные задачи (очереди, webhook'и). Клиент должен периодически опрашивать статус. |
| **203** | Non-Authoritative Information | RFC 9110 §15.3.4 | Транзакция успешна, но метаинформация (заголовки) получена из локального или стороннего источника, а не напрямую от Origin. |
| **204** | No Content | RFC 9110 §15.3.5 | Успех без передачи тела. | `DELETE` или `PUT` без возврата данных (экономит трафик). |
| **205** | Reset Content | RFC 9110 §15.3.6 | Успех; клиент должен сбросить форму/представление. |
| **206** | Partial Content | RFC 9110 §15.3.7 | Частичное содержимое. | Range-запросы (стриминг видео, докачка файлов). Заголовки `Content-Range`. |
| **226** | IM Used | RFC 3229 | Ресурс изменен согласно правилам дельты (Delta encoding). |

### 3xx — Перенаправления

Клиент должен выполнить дополнительный запрос. Влияют на TTFB (Time to First Byte).

**Важное отличие:** Старые коды (301, 302) исторически реализованы браузерами с ошибкой — они могут менять метод `POST` на `GET` при редиректе. Новые коды (307, 308) строго **гарантируют сохранение исходного метода и тела запроса**.

| Код | Название | RFC | Описание | Сохранение метода | Кэшируемость |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **300** | Multiple Choices | RFC 9110 §15.4.1 | Несколько представлений ресурса (форматы, языки). | — | Да |
| **301** | Moved Permanently | RFC 9110 §15.4.2 | Постоянный редирект (смена домена, HTTP → HTTPS). | Нет (POST → GET) | **Да** (навсегда) |
| **302** | Found | RFC 9110 §15.4.3 | Временный редирект. | Нет (POST → GET) | Нет |
| **303** | See Other | RFC 9110 §15.4.4 | Временный редирект после `POST` на ресурс, доступный только через `GET`. | Нет (POST → GET) | Нет |
| **305** | Use Proxy | RFC 9110 §15.4.5 | Редирект через прокси. | — | Нет |
| **307** | Temporary Redirect | RFC 9110 §15.4.7 | Временный редирект (API endpoints, платежи). | **Да** (POST → POST) | Нет |
| **308** | Permanent Redirect | RFC 9110 §15.4.8 | Постоянный редирект. Замена для 301 в API. | **Да** (POST → POST) | **Да** |

### 4xx — Ошибки клиента

Запрос содержит ошибку. Для исправления требуется изменение на стороне клиента.

| Код | Название | RFC | Причина/Диагностика |
| :--- | :--- | :--- | :--- |
| **400** | Bad Request | RFC 9110 §15.5.1 | Синтаксическая ошибка (невалидный JSON, отсутствующий обязательный заголовок). |
| **401** | Unauthorized | RFC 9110 §15.5.2 | Требуется аутентификация (`Authorization` header отсутствует или токен просрочен). |
| **402** | Payment Required | RFC 9110 §15.5.3 | Зарезервирован для будущего использования. В настоящее время используется в экосистеме Stripe и других платежных API для индикации неуспешной оплаты. |
| **403** | Forbidden | RFC 9110 §15.5.4 | Аутентификация успешна (клиент известен), но прав недостаточно (RBAC/ACL). |
| **404** | Not Found | RFC 9110 §15.5.5 | Ресурс не существует. Проверить эндпоинт или ID. |
| **405** | Method Not Allowed | RFC 9110 §15.5.6 | Метод (например, `POST`) запрещен для этого URI. В ответе должен быть заголовок `Allow`. |
| **406** | Not Acceptable | RFC 9110 §15.5.7 | Сервер не может предоставить ресурс в формате, указанном в `Accept` заголовке. |
| **407** | Proxy Authentication Required | RFC 9110 §15.5.8 | Требуется аутентификация на прокси. Аналогично 401, но для промежуточного прокси. |
| **408** | Request Timeout | RFC 9110 §15.5.9 | Клиент не передал полный запрос за отведенное сервером время. |
| **409** | Conflict | RFC 9110 §15.5.10 | Конфликт состояния (например, создание дубликата уникального ID или модификация старой версии). |
| **410** | Gone | RFC 9110 §15.5.11 | Ресурс существовал, но удален навсегда. Браузеры не должны кэшировать ответ. |
| **412** | Precondition Failed | RFC 9110 §15.5.12 | Условие в заголовках `If-Match`/`If-None-Match` не выполнено. |
| **413** | Payload Too Large | RFC 9110 §15.5.13 | Тело запроса превышает лимит сервера (`client_max_body_size` в Nginx). |
| **414** | URI Too Long | RFC 9110 §15.5.14 | URI превышает максимальную длину сервера (часто в GET-запросах с длинными query-параметрами). |
| **415** | Unsupported Media Type | RFC 9110 §15.5.15 | Отсутствует или неверный заголовок `Content-Type` в `POST`/`PUT`/`PATCH`. |
| **416** | Range Not Satisfiable | RFC 9110 §15.5.16 | Запрошенный диапазон (`Range`) не может быть удовлетворен (ресурс короче запрошенного). |
| **417** | Expectation Failed | RFC 9110 §15.5.17 | Условие `Expect` (например, `100-continue`) не может быть выполнено. |
| **418** | I'm a teapot | RFC 2324 §2.3.2 | Эaster egg (1998). В современном использовании — мета-код для индикации «невозможности» операции в тестовых средах. |
| **421** | Misdirected Request | RFC 9110 §15.5.19 | Специфично для HTTP/2 и HTTP/3. Запрос направлен на сервер, который не настроен для обслуживания этого SNI/домена (часто возникает при connection coalescing). |
| **422** | Unprocessable Entity | RFC 4918 §11.2 | Семантическая ошибка (синтаксис JSON верен, но логическая валидация полей провалена). Изначально для WebDAV. |
| **423** | Locked | RFC 4918 §11.3 | Ресурс заблокирован. Используется в WebDAV. |
| **425** | Too Early | RFC 8470 | Сервер отказывается обрабатывать запрос, так как он отправлен через **0-RTT (Early Data)** и может быть подвержен Replay Attack (не является идемпотентным). |
| **426** | Upgrade Required | RFC 9110 §15.5.20 | Сервер требует перехода на другой протокол (например, TLS). В ответе заголовок `Upgrade`. |
| **428** | Precondition Required | RFC 6585 §3 | Сервер требует условия `If-Match` или `If-None-Match` для предотвращения паралленых конфликтов. |
| **429** | Too Many Requests | RFC 6585 §4 | Rate Limit. Слишком много запросов. Сервер должен возвращать заголовок `Retry-After`. |
| **431** | Request Header Fields Too Large | RFC 6585 §5 | Заголовки запроса превышают лимит сервера (часто при атаке header bombing). |
| **451** | Unavailable For Legal Reasons | RFC 7725 | Ресурс недоступен из-за юридических ограничений (GDPR, санкции, блокировка по закону). |

### 5xx — Ошибки сервера

Критические ошибки, влияющие на SLA и надежность системы.

| Код | Название | RFC | Техническая суть |
| :--- | :--- | :--- | :--- |
| **500** | Internal Server Error | RFC 9110 §15.6.1 | «Крах» приложения: необработанное исключение (Exception), Segfault в коде, неверная конфигурация (.htaccess). |
| **501** | Not Implemented | RFC 9110 §15.6.2 | Метод не поддерживается сервером. В ответе должен быть заголовок `Allow`. |
| **502** | Bad Gateway | RFC 9110 §15.6.3 | Reverse Proxy (Nginx) получил некорректный ответ от бэкенда (upstream) или TCP-соединение было разорвано (RST). |
| **503** | Service Unavailable | RFC 9110 §15.6.4 | Сервер перегружен или выключен. Часто — `maintenance mode`. В ответе должен быть заголовок `Retry-After`. |
| **504** | Gateway Timeout | RFC 9110 §15.6.5 | Бэкенд не ответил балансировщику в заданный таймаут (приложение зависло, Deadlock БД). |
| **505** | HTTP Version Not Supported | RFC 9110 §15.6.6 | Сервер не поддерживает версию HTTP, указанную в запросе. |
| **506** | Variant Also Negotiates | RFC 2295 §8.1 | Ошибка конфигурации Content Negotiation (цикл). |
| **507** | Insufficient Storage | RFC 4918 §11.5 | WebDAV: не хватает места на сервере для сохранения ресурса. |
| **508** | Loop Detected | RFC 5842 §7.2 | WebDAV: обнаружен бесконечный цикл при обработке запроса (часто при аварийном копировании ресурса). |
| **511** | Network Authentication Required | RFC 6585 §6 | Требуется авторизация на сетевом уровне (например, Captive Portal в публичном Wi-Fi). |

## Практические сценарии

### Сценарий 1: Диагностика через curl

Проверка кода ответа без загрузки тела ответа:

```bash
curl -s -o /dev/null -w "%{http_code}" https://api.example.com/resource
# → 200
```

Расширенная диагностика с отображением заголовков:

```bash
curl -v https://api.example.com/resource 2>&1 | grep -E "< HTTP|< Location|< Content"
# → < HTTP/1.1 200 OK
# → < Content-Type: application/json
```

**Ожидаемый вывод:**
- **200** — ресурс найден и возвращён.
- **301/302** — ресурс перемещён, проверить `Location` в заголовках.
- **401** — требуется авторизация (см. [HTTP-аутентификация](./http_authentication.md)).

**Валидация:**
```bash
for code in 200 301 404 500; do
  echo -n "$code → "
  curl -s -o /dev/null -w "%{http_code}" "https://httpbin.org/status/$code"
done
# → 200 → 200
# → 301 → 301
# → 404 → 404
# → 500 → 500
```

### Сценарий 2: Анализ логов Nginx

Подсчёт количества запросов по кодам ответа за последний час:

```bash
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
# →  1520 200
# →   430 301
# →    85 404
# →    12 502
```

Поиск эндпоинтов, вызывающих ошибку **499 (Client Closed Request)**:

```bash
awk '$9 == 499 {print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
# →    45 /api/slow-endpoint
# →    12 /api/download
```

Поиск 500-ошибок с временем:

```bash
awk '$9 ~ /^50[0-9]$/ {print $4,$7,$9}' /var/log/nginx/access.log | tail -20
# → [26/Aug/2026:12:00:01 +0300] /api/checkout 500
```

### Сценарий 3: Диагностика ошибки 429 (Too Many Requests)

При получении 429 важно определить, какой именно лимит был превышен.

1. **Заголовок Retry-After:** Проверить, сообщает ли сервер, через сколько секунд можно повторить запрос.
2. **Анализ заголовков X-RateLimit:** Многие API передают текущее состояние лимитов (например, `X-RateLimit-Remaining`).
3. **Локализация:** Если ошибка возникла внезапно, проверить не изменился ли IP клиента (например, выход через новый VPN) или не возросла ли интенсивность фоновых задач (кроны).

```bash
curl -v https://api.example.com/endpoint 2>&1 | grep -iE "retry-after|x-ratelimit|429"
# → < Retry-After: 60
# → < X-RateLimit-Remaining: 0
```

**Валидация:**
```bash
# Нагрузочный тест с фиксированным интервалом
for i in $(seq 1 20); do
  code=$(curl -s -o /dev/null -w "%{http_code}" https://httpbin.org/status/429)
  echo "Request $i: $code"
  sleep 0.1
done
# → Request 1: 429
# → Request 2: 429
```

### Сценарий 4: Диагностика 502 vs 504 в микросервисах

В микросервисной архитектуре (K8s) различие критично для поиска виновного:

- **502 Bad Gateway:** Означает, что «визави» (например, Sidecar или Service) существует, но он сразу сбросил соединение или ответил бредом. Причина: сервис упал, OOMKill, ошибка в коде на старте.
- **504 Gateway Timeout:** Означает, что «визави» принял запрос, но не ответил вовремя. Причина: сервис «задумался», долгий запрос к БД, Deadlock.

```bash
# Диагностика 502 в Nginx
tail -f /var/log/nginx/error.log | grep "upstream"
# → 2026/08/26 12:00:01 [error] 12345#0: *1 upstream prematurely closed connection while reading response header from upstream

# Диагностика 504
# → 2026/08/26 12:00:02 [error] 12345#0: *2 upstream timed out (110: Connection timed out) while reading response header from upstream
```

**Валидация:**
```bash
# Проверка доступности upstream
curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/health
# → 200 (если сервис жив)

# Проверка timeout через curl с таймаутом
curl -s -o /dev/null -w "%{http_code}" --max-time 2 http://localhost:8080/slow
# → 0 (timeout) или 504 (если через прокси)
```

### Сценарий 5: Обнаружение 451 (Unavailable For Legal Reasons)

При блокировке ресурса по юридическим причинам важно определить, является ли блокировка ошибкой конфигурации CDN или законным требованием:

```bash
curl -v https://blocked-resource.example.com/file.zip 2>&1 | grep -E "< HTTP|< Link"
# → < HTTP/1.1 451 Unavailable For Legal Reasons
# → < Link: <https://legal.example.com/notice>; rel="blocked-by"
```

**Валидация:**
```bash
# Проверка заголовка blocked-by
for url in \
  "https://httpbin.org/status/451" \
  "https://httpbin.org/status/200"; do
  code=$(curl -s -o /dev/null -w "%{http_code}" "$url")
  echo "$url → $code"
done
# → https://httpbin.org/status/451 → 451
# → https://httpbin.org/status/200 → 200
```

### Сценарий 6: Диагностика 413/414 (Payload Too Large / URI Too Long)

При превышении лимитов запроса:

```bash
# 413: отправка большого тела
curl -s -o /dev/null -w "%{http_code}" -X POST \
  -H "Content-Type: application/json" \
  -d '{"data":"'"$(python3 -c "print('A'*5000000)")"'"}' \
  https://api.example.com/upload
# → 413

# 414: слишком длинный URI
curl -s -o /dev/null -w "%{http_code}" "https://api.example.com/search?q=$(python3 -c "print('A'*20000)")"
# → 414
```

**Валидация:**
```bash
# Проверка лимита Nginx
grep client_max_body_size /etc/nginx/nginx.conf
# → client_max_body_size 1m;

# Проверка лимита Apache
grep LimitRequestBody /etc/httpd/conf/httpd.conf
# → LimitRequestBody 1048576
```

### Сценарий 7: Мониторинг 5xx и SLO (Error Budget)

Интеграция статус-кодов в мониторинг и SLO:

```bash
# Подсчёт 5xx за последний час (Prometheus exporter или log-based)
awk -v cutoff="26/Aug/2026:11" '$4 ~ cutoff && $9 ~ /^5[0-9][0-9]$/ {print}' /var/log/nginx/access.log | wc -l
# → 3 (количество 5xx за последний час)

# Расчёт Error Rate
total=$(awk -v cutoff="26/Aug/2026:11" '$4 ~ cutoff {print}' /var/log/nginx/access.log | wc -l)
errors=$(awk -v cutoff="26/Aug/2026:11" '$4 ~ cutoff && $9 ~ /^5[0-9][0-9]$/ {print}' /var/log/nginx/access.log | wc -l)
rate=$(awk "BEGIN {print ($errors/$total)*100}")
echo "Error Rate: ${rate}%"
# → Error Rate: 0.2%
```

**Валидация:**
```bash
# Проверка SLO порога (например, 99.9% доступности)
if (( $(awk "BEGIN {print ($rate > 0.1)}") )); then
  echo "ALERT: Error Budget расходуется"
else
  echo "OK: Error Rate в норме"
fi
# → OK: Error Rate в норме
```

## Дополнительная информация

### Использование в REST API

При проектировании REST API важно соблюдать семантическую точность кодов:

- **Создание:** `201 Created` вместо `200 OK`.
- **Удаление:** `204 No Content` для успешного удаления без возврата данных.
- **Ошибки валидации:** `422 Unprocessable Entity` вместо `400 Bad Request`.
- **Структура ошибки:** Рекомендуется использовать стандарт **RFC 9457 (Problem Details)** для формирования тела ответа с ошибкой (содержит поля `type`, `title`, `status`, `detail`). Подробнее в **[REST API](./http_rest_api.md)**.

### Влияние на кэширование

Различные коды ответов обрабатываются кэширующими прокси (CDN, Nginx) по-разному:

- **Кэшируемые (Heuristically Cacheable):** 200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414, 501 (если не запрещено заголовком `Cache-Control`).
- **Не кэшируемые (по умолчанию):** 302, 307.
- **Валидация:** 304 указывает клиенту на актуальность версии ресурса в его локальном кэше.

Подробнее в **[HTTP-кэширование](./http_caching.md)**.

### Специфичные коды для WebDAV

Протокол WebDAV (расширение HTTP) использует собственные коды:

| Код | Назначение |
| :--- | :--- |
| **102** | Processing (долгие операции) |
| **207** | Multi-Status (несколько операций) |
| **422** | Unprocessable Entity (смешанное использование) |
| **423** | Locked |
| **507** | Insufficient Storage |
| **508** | Loop Detected |

### RFC, определяющие семантику

| RFC | Название | Темы |
| :--- | :--- | :--- |
| **RFC 9110** | HTTP Semantics | Все базовые коды (1xx–5xx) |
| **RFC 7231** | HTTP/1.1 Semantics and Content | Устаревший, заменён на RFC 9110 |
| **RFC 4918** | WebDAV | 102, 207, 422, 423, 507, 508 |
| **RFC 6585** | Additional HTTP Status Codes | 428, 429, 431, 511 |
| **RFC 7725** | 451 Unavailable For Legal Reasons | Юридические блокировки |
| **RFC 8470** | 425 Too Early | 0-RTT защита |

### Ключевые метрики SRE (Golden Signals / RED Method)

Для инженера по надежности (SRE) статус-коды формируют основу мониторинга:

- **Error Rate (Ошибки):** Процент 5xx-ответов относительно общего числа запросов. Является главным индикатором расхода Error Budget. Всплески 4xx (особенно 401/403) отслеживаются как аномалии безопасности.
- **Saturation (Насыщение):** Рост 503-ошибок или 429-ответов указывает на исчерпание ресурсов сервера (CPU, соединения к БД, лимиты API).
- **Latency (Задержка):** Измеряется только для успешных запросов (2xx).

## Типичные проблемы и диагностика

### 1. Превышение размера запроса (413/414)

**Симптом:** Клиент получает `413 Payload Too Large` или `414 URI Too Long`.

**Причина:** Превышен лимит размера тела запроса (`client_max_body_size` в Nginx, `LimitRequestBody` в Apache) или длина URI.

**Решение:**

```bash
# Nginx: увеличение лимита
client_max_body_size 50m;

# Перезагрузка
nginx -s reload
```

### 2. Юридическая блокировка (451)

**Симптом:** Ресурс возвращает `451` без явного технического сбоя.

**Причина:** Блокировка по закону (GDPR, авторские права, санкции). В ответе должен быть заголовок `Link` с указанием причины.

**Решение:** Проверить политики CDN и прокси (например, Cloudflare `451 — Unavailable For Legal Reasons`).

### 3. Всплеск 429 (Rate Limit)

**Симптом:** Всплеск `429` после деплоя или масштабирования фоновых задач.

**Причина:** Слишком агрессивный cron, отсутствие `Retry-After`, отсутствие экспоненциальной задержки.

**Решение:**

```bash
# Проверка Retry-After
curl -v https://api.example.com/endpoint 2>&1 | grep Retry-After
# → < Retry-After: 60
```

### 4. 502 Bad Gateway в Kubernetes

**Симптом:** Ingress или Service Mesh возвращает `502`.

**Причина:** Pod завершился (OOMKill, crash), неверный `readinessProbe`, Sidecar не инициализирован.

**Диагностика:**

```bash
# Проверка статуса подов
kubectl get pods -n namespace
# → NAME                     READY   STATUS    RESTARTS
# → api-7d9f8b6c5-x2z4k     1/2     Running   3 (OOMKilled 2m ago)

# Проверка логов
kubectl logs api-7d9f8b6c5-x2z4k -c app --previous
# → Killed
```

### 5. Таймаут шлюза (504)

**Симптом:** `504` от Nginx/ALB/Cloudflare.

**Причина:** Бэкенд «завис» (дедлок БД, утечка памяти, внешний API не отвечает).

**Диагностика:**

```bash
# Проверка timeout в Nginx
grep proxy_read_timeout /etc/nginx/conf.d/*.conf
# → proxy_read_timeout 60s;

# Проверка доступности бэкенда
curl -s -o /dev/null -w "%{time_total}" http://localhost:8080/health
# → 0.045
```

### 6. Обнаружен цикл WebDAV (508)

**Симптом:** `508` при синхронизации WebDAV или работе с Nextcloud/ownCloud.

**Причина:** Бесконечный цикл при копировании ресурса на самого себя или через рекурсивные связи.

**Решение:** Проверить правила маршрутизации и исключить рекурсивные пути.

### 7. Требуется сетевая аутентификация (511)

**Симптом:** Браузер перенаправляет на страницу входа Wi-Fi, но CLI-клиент получает `511`.

**Причина:** Captive Portal требует аутентификации перед предоставлением дохода в Интернет.

**Решение:** Пройти аутентификацию через браузер или API портала.

## Лучшие практики

1. **Никогда не возвращайте `200 OK` для ошибок.** Используйте семантически корректные коды 4xx/5xx. Это ломает мониторинг, кэширование и автоматизацию.
2. **Используйте `Retry-After` для `503` и `429`.** Это уважает клиентские пулы соединений и предотвращает stampede.
3. **Для REST API используйте `308` вместо `301`.** Это гарантирует сохранение метода `POST` при постоянном редиректе.
4. **Для временных редиректов после `POST` используйте `303`.** Это предотвращает повторную отправку данных при обновлении страницы (PRG pattern).
5. **Для разрыва соединения используйте `444` (Nginx) или `425`.** `444` — нестандартный код Nginx для закрытия соединения без ответа. `425` — для отказа от 0-RTT.
6. **Логируйте `5xx` с полным Request ID.** Это позволяет связать логи сервиса, прокси и балансировщика при distributed tracing.
7. **Для `4xx` не повторяйте попытки автоматически.** Только `408`, `429` и `5xx` допускают retry с экспоненциальной задержкой.
8. **Используйте `RFC 9457 (Problem Details)` для тел ошибок 4xx/5xx.** Это стандартизирует структуру ответа для API-клиентов.
9. **Для Rate Limiting используйте заголовки `X-RateLimit-*`.** Это позволяет клиентам адаптировать нагрузку без получения `429`.
10. **В CDN/Nginx настраивайте отдельные страницы для `502`/`503`/`504`.** Это уменьшает негативный UX при технических работах.

## Граничные случаи и ограничения

1. **301 и 302 в браузерах:** Исторически браузеры меняют `POST` на `GET` при 301/302, что нарушает идемпотентность. Используйте `307`/`308` для API.
2. **499 — нестандартный код:** `499` является неофициальным кодом Nginx. В стандарте RFC 9110 его нет. Не используйте в собственном API.
3. **418 — easter egg:** `I'm a teapot` (RFC 2324) не является реальным кодом протокола. Используйте только в тестовых средах.
4. **0-RTT Replay:** `425 Too Early` защищает от повторной отправки запроса через 0-RTT, но требует строгой идемпотентности на уровне приложения.
5. **203 Non-Authoritative:** Используется прокси и CDN, которые модифицируют тело или заголовки. Не должно возвращаться Origin-сервером.
6. **451 и CDN:** Некоторые CDN возвращают `451` для блокировки по IP или геолокации, что может быть ошибочно воспринято как юридическая блокировка.
7. **ECMAScript fetch и 308:** Старые версии Node.js не обрабатывали `308` корректно. Проверьте поддержку в runtime.
8. **WebDAV и 422:** `422` был перенесён из WebDAV в основную семантику (RFC 4918 → RFC 9110), но некоторые прокси всё ещё обрабатывают его специфично.
9. **ALPN и 421:** В HTTP/2 `421 Misdirected Request` возникает при coalescing соединений. Это нормально, если клиент корректно обрабатывает реконнект.
10. **RFC 9110 и Reason Phrase:** Современные серверы (например, Nginx 1.25+) могут отключать Reason Phrase. Клиенты не должны полагаться на него.
