# HTTP-коды ответа

## Определения

**HTTP-код ответа (Status Code)** — трёхзначное число в первой строке HTTP-ответа сервера, указывающее на результат обработки запроса. Семантика стандартных кодов определена в **RFC 9110**. Код является частью [строки состояния (Status Line)](./http_basics.md) формата `HTTP/<версия> <код> <текст>`.

**Структура кода:**

- **Первая цифра** — класс ответа (1–5), определяющий общую категорию результата.
- **Вторая и третья цифры** — спецификация конкретного состояния внутри класса.

**Пример:** `HTTP/1.1 200 OK` — версия HTTP/1.1, код 200 (успех), текст OK.

## Основные концепции

### Классы кодов ответа

HTTP-коды разделены на 5 классов:

| Класс | Диапазон | Значение | Описание (DevOps/SRE перспектива) |
| :--- | :--- | :--- | :--- |
| **1xx** | 100–199 | Информационные | Протокольные уведомления (Upgrade, Early Hints). |
| **2xx** | 200–299 | Успешные | Основная метрика успеха. |
| **3xx** | 300–399 | Перенаправления | Влияют на Latency из-за дополнительных RTT. |
| **4xx** | 400–499 | Ошибки клиента | Ошибки интеграции или безопасности. Обычно не требуют алерта. |
| **5xx** | 500–599 | Ошибки сервера | Критический показатель (Error Budget). Требуют немедленной реакции. |

### 1xx — Информационные коды

Используются для обмена служебной информацией до передачи основного тела ответа.

| Код | Название | Описание |
| :--- | :--- | :--- |
| **100** | Continue | Сигнал клиенту, что заголовки приняты и можно отправлять тело (заголовок `Expect`). |
| **101** | Switching Protocols | Смена протокола (например, апгрейд до WebSocket или HTTP/2). |
| **102** | Processing | Используется в длительных операциях (WebDAV) для предотвращения таймаута клиента. |
| **103** | Early Hints | Позволяет браузеру начать загрузку ресурсов (CSS/JS) пока сервер генерирует ответ. |

### 2xx — Успешные коды

Указывают на то, что запрос был получен, понят и успешно обработан.

| Код | Название | Описание | Применение |
| :--- | :--- | :--- | :--- |
| **200** | OK | Стандарт для успешных запросов. | `GET`, `PUT`, `PATCH`. |
| **201** | Created | Ресурс создан. | `POST`. Заголовок `Location` содержит URI. |
| **202** | Accepted | Принято в обработку. | Асинхронные задачи (очереди). |
| **204** | No Content | Успех без передачи тела. | `DELETE` или `PUT` без возврата данных. |
| **206** | Partial Content | Частичное содержимое. | Range-запросы (стриминг, докачка). |

### 3xx — Перенаправления

Клиент должен выполнить дополнительный запрос. Влияют на TTFB и общее время загрузки.

| Код | Название | Описание | Кэшируемость |
| :--- | :--- | :--- | :--- |
| **301** | Moved Permanently | Постоянный редирект. | Да, браузер запоминает навсегда. |
| **302** | Found | Временный редирект. | Нет, метод может измениться на GET. |
| **304** | Not Modified | Ресурс не изменился. | Используется для валидации кэша (ETag). |
| **307** | Temporary Redirect | Временный редирект. | Метод запроса сохраняется (POST → POST). |
| **308** | Permanent Redirect | Постоянный редирект. | Метод запроса сохраняется (POST → POST). |

### 4xx — Ошибки клиента

Запрос содержит ошибку. Для исправления требуется изменение на стороне клиента.

| Код | Название | Причина/Диагностика |
| :--- | :--- | :--- |
| **400** | Bad Request | Синтаксическая ошибка (невалидный JSON, кривой заголовок). |
| **401** | Unauthorized | Требуется аутентификация (`Authorization` header). |
| **403** | Forbidden | Аутентификация успешна, но прав недостаточно (RBAC/ACL). |
| **404** | Not Found | Ресурс не существует. Проверить эндпоинт. |
| **405** | Method Not Allowed | Метод (например, `POST`) запрещен для этого URI. |
| **409** | Conflict | Конфликт состояния (например, создание дубликата ID). |
| **421** | Misdirected Request | Запрос попал на сервер, не умеющий обрабатывать этот домен (HTTP/2). |
| **422** | Unprocessable Entity | Семантическая ошибка (валидация полей данных). |
| **425** | Too Early | Сервер не хочет обрабатывать запрос, который может быть атакой повтора (0-RTT). |
| **429** | Too Many Requests | Rate Limit. Слишком много запросов. |
| **451** | Unavailable For Legal Reasons | Доступ закрыт по юридическим причинам (цензура, требования властей). |
| **499** | Client Closed Request | Клиент закрыл соединение до ответа (Nginx-specific). |

### 5xx — Ошибки сервера

Критические ошибки, влияющие на SLA и надежность системы.

| Код | Название | Техническая суть |
| :--- | :--- | :--- |
| **500** | Internal Server Error | «Крах» приложения: необработанное исключение, Segfault. |
| **502** | Bad Gateway | Бэкенд (upstream) вернул мусор или TCP-разрыв. |
| **503** | Service Unavailable | Сервер перегружен или выключен. Часто — `maintenance mode`. |
| **504** | Gateway Timeout | Бэкенд не ответил в заданный таймаут (приложение зависло). |
| **511** | Network Authentication Required | Требуется авторизация в сети (Captive Portal). |

## Практические сценарии

### Сценарий 1: Диагностика через curl

Проверка кода ответа без загрузки тела ответа:

```bash
curl -s -o /dev/null -w "%{http_code}" https://api.example.com/resource
```

Расширенная диагностика с отображением заголовков:

```bash
curl -v https://api.example.com/resource 2>&1 | grep -E "< HTTP|< Location|< Content"
```

### Сценарий 2: Анализ логов Nginx

Подсчёт количества запросов по кодам ответа за последний час:

```bash
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
```

### Сценарий 3: Диагностика ошибки 429 (Too Many Requests)

При получении 429 важно определить, какой именно лимит был превышен.

1. **Заголовок Retry-After:** Проверить, сообщает ли сервер, через сколько секунд можно повторить запрос.
2. **Анализ заголовков X-RateLimit:** Многие API передают текущее состояние лимитов (например, `X-RateLimit-Remaining`).
3. **Локализация:** Если ошибка возникла внезапно, проверить не изменился ли IP клиента (например, выход через новый VPN) или не возросла ли интенсивность фоновых задач (кроны).

### Сценарий 4: Диагностика 502 vs 504 в микросервисах

В микросервисной архитектуре (K8s) различие критично для поиска виновного:

- **502 Bad Gateway:** Означает, что «визави» (например, Sidecar или Service) существует, но он сразу сбросил соединение или ответил бредом. Причина: сервис упал, OOMKill, ошибка в коде на старте.
- **504 Gateway Timeout:** Означает, что «визави» принял запрос, но не ответил вовремя. Причина: сервис «задумался», долгий запрос к БД, Deadlock.

## Дополнительная информация

> **Надёжность: 10/10** (Соответствие стандарту RFC 9110)
> **Актуальность: 2026-07**

### Использование в REST API

При проектировании REST (Representational State Transfer) API важно соблюдать семантическую точность кодов:

- **Создание:** `201 Created` вместо `200 OK`.
- **Удаление:** `204 No Content` для успешного удаления без возврата данных.
- **Ошибки:** `422 Unprocessable Entity` для ошибок бизнес-валидации.

### Влияние на кэширование

Различные коды ответов обрабатываются кэширующими прокси (CDN, Nginx) по-разному:

- **Кэшируемые:** 200, 206, 301, 308 (зависит от заголовка `Cache-Control`).
- **Не кэшируемые:** 302, 307 (по умолчанию).
- **Валидация:** 304 указывает клиенту на актуальность версии в его кэше.

### Ключевые метрики SRE

Для инженера по надежности (SRE) критически важны следующие показатели:

- **Error Rate:** Процент 5xx-ответов.
- **Saturation:** Рост 503-ошибок при перегрузке ресурсов.
- **Latency p99:** Время ответа для успешных запросов (200 OK).
