# Эволюция HTTP и HTTPS

## Определения

**HTTP (Hypertext Transfer Protocol)** — протокол прикладного уровня, эволюционировавший для решения проблем производительности и безопасности. Современные спецификации консолидированы в серии **RFC 911x**. Базовая семантика (методы, статусы, заголовки) определена в **RFC 9110** и является общей для всех версий транспорта.

**HTTPS (HTTP Secure)** — использование HTTP поверх протокола шифрования **TLS (Transport Layer Security)**. Обеспечивает конфиденциальность, целостность и аутентификацию. В современных реализациях (TLS 1.3) скрывает SNI (Server Name Indication) через механизм **ECH (Encrypted Client Hello)**.

**QUIC (Quick UDP Internet Connections)** — транспортный протокол (RFC 9000) на базе UDP. Объединяет функции TCP (надежность, контроль перегрузок) и TLS 1.3 (безопасность) в единый слой. Фундамент для HTTP/3.

**Head-of-Line (HOL) Blocking (Блокировка начала очереди)** — задержка обработки данных из-за потери или медленной обработки первого пакета в очереди. 
- В HTTP/1.1 возникает на уровне HTTP-сообщений.
- В HTTP/2 решена на уровне HTTP, но остается на уровне TCP-пакетов.
- В HTTP/3 полностью устранена благодаря независимым потокам QUIC.

## Основные концепции

### Сравнительная таблица версий HTTP

| Характеристика | HTTP/0.9 | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Спецификация** | RFC 1945 (унаследовано) | RFC 1945 | RFC 9112 | RFC 9113 | RFC 9114 |
| **Транспорт** | TCP | TCP | TCP | TCP | **QUIC (UDP)** |
| **Формат передачи** | Текстовый (Plain Text) | Текстовый (Plain Text) | Текстовый (Plain Text) | Бинарные кадры (Binary Frames) | Бинарные кадры |
| **Мультиплексирование** | Нет | Нет | Нет (Pipelining не прижился) | Да (TCP-потоки) | Да (QUIC-потоки) |
| **HOL Blocking** | Уровень соединения | Уровень соединения | Уровень соединения | Уровень TCP-пакета | **Устранена** |

### Протокол HTTP/0.9 (1991)

Первая реализация протокола, созданная Тимом Бернерсом-Ли для проектирования World Wide Web. Опубликована как RFC в 1993 году, но никогда не имела официального номера RFC.

**Особенности:**

- Только метод **GET**.
- Отсутствие заголовков запроса и ответа.
- Отсутствие кодов статуса (1xx, 2xx, 3xx и т.д.).
- Ответ — только тело документа (обычно HTML).
- Сервер закрывал соединение после передачи документа.

**Проблемы:**

- Отсутствие поддержки других методов (POST, HEAD).
- Невозможность передачи метаинформации (тип контента, кодировка).
- Нет поддержки виртуальных хостов.
- Нет кэширования.

### Протокол HTTP/1.0 (1996)

Первая стандартизированная версия HTTP (RFC 1945).

**Ключевые особенности:**

- **Заголовки запроса и ответа:** Введена структура заголовков, аналогичная MIME (Multipurpose Internet Mail Extensions).
- **Методы:** GET, HEAD, POST.
- **Коды статуса:** Введена трёхзначная система кодов (1xx, 2xx, 3xx, 4xx, 5xx).
- **Версия в стартовой строке:** `HTTP/1.0`.
- **Content-Type:** Обязательный заголовок ответа для указания MIME-типа тела.
- **Прокси-поддержка:** Формирование запросов к прокси-серверам через абсолютные URI.

**Проблемы:**

- Новое TCP-соединение на каждый ресурс (HTML, CSS, JS, изображения).
- Большие накладные расходы на рукопожатия TCP (Transmission Control Protocol).
- Отсутствие кэширования соединений.
- Отсутствие поддержки виртуальных хостов (Host header).

### HTTP/1.1 (1997, обновления 2014)

Стандарт более чем на 15 лет (RFC 2068 → RFC 2616 → RFC 7230-7237).

**Ключевые улучшения:**

- **Постоянные соединения (Keep-Alive):** Несколько запросов в рамках одного TCP-соединения, что сократило задержки.
- **Chunked Transfer Encoding:** Сервер передаёт данные частями (чанками), не зная полный размер ответа заранее.
- **Pipeline (ограниченно):** Возможность отправлять запросы, не дожидаясь ответов. Работала плохо из-за HOL-блокировки — ответы должны приходить строго по порядку.
- **Обязательный заголовок `Host`:** Поддержка виртуальных хостов (несколько доменов на одном IP-адресе).
- **Content Negotiation (Согласование контента):** Клиент может запрашивать конкретный формат через заголовки `Accept`, `Accept-Language`, `Accept-Encoding`.
- **Кэширование:** Введены директивы `Cache-Control`, `ETag`, `Last-Modified`.

**Ограничения:**

- HOL-блокировка на уровне TCP.
- Браузеры ограничивали до 6 параллельных соединений на домен.
- Текстовый протокол — сложен для парсинга и менее эффективен.

### Протокол HTTP/2 (2015)

Революционное обновление на базе протокола SPDY от Google (RFC 7540 → RFC 9113).

**Архитектура:**

HTTP/2 вводит **бинарный фреймируемый слой** между транспортным уровнем и семантическим HTTP-уровнем. Все данные разбиваются на кадры (frames):

- **HEADERS** — заголовки запроса/ответа.
- **DATA** — тело сообщения.
- **SETTINGS** — параметры соединения.
- **PRIORITY** — приоритет потока.
- **RST_STREAM** — отмена потока.
- **GOAWAY** — graceful shutdown соединения.
- **WINDOW_UPDATE** — управление потоком (flow control).
- **PUSH_PROMISE** — анонс ресурса для push (устарело).

**Ключевые улучшения:**

- **Мультиплексирование:** Множество запросов и ответов передаются одновременно в одном TCP-соединении. Сообщения разбиваются на **бинарные кадры (frames)**, которые перемешиваются в потоке и собираются на другой стороне. Это решает HOL-блокировку на прикладном уровне.
- **Сжатие заголовков (HPACK):** Использование статических и динамических словарей (индексов) для устранения избыточности при передаче повторяющихся заголовков (Cookie, User-Agent). Статическая таблица содержит 61 предопределённый заголовок. Huffman-кодирование снижает объём передаваемых данных.
- **Приоритизация:** Клиент указывает вес потока (stream dependency), позволяя серверу отдавать критичный контент (CSS) раньше менее важного (картинки). В RFC 9218 введён упрощённый механизм Extensible Prioritization с параметрами `u` (Urgency) и `i` (Incremental).
- **Server Push (Устарело):** Позволяло серверу отправлять ресурсы до запроса. На практике оказалось неэффективным (конфликты с браузерным кэшем) и удалено из спецификаций HTTP/3. Современные браузеры игнорируют `PUSH_PROMISE`.

**Практические аспекты:**

- Де-факто требует TLS (браузеры поддерживают HTTP/2 только поверх HTTPS через расширение ALPN).
- Сделало антипаттернами "спрайты" (image sprites) и конкатенацию JS/CSS — теперь выгоднее отдавать множество мелких файлов параллельно.
- Минимальный размер окна TCP влияет на все потоки HTTP/2 (WINDOW_UPDATE).

### Протокол HTTP/3 (2022)

Новейший стандарт (RFC 9114), полностью меняющий транспортный уровень для решения оставшихся проблем TCP.

**Архитектура:**

HTTP/3 работает поверх **QUIC**, который сам по себе объединяет TLS 1.3, надежную доставку и управление перегрузками в User-space.

**Ключевые улучшения:**

- **Переход на QUIC (UDP):** Мультиплексирование, контроль перегрузок и шифрование реализованы поверх UDP. Потеря одного UDP-пакета влияет только на конкретный поток (stream), не блокируя остальные (полное устранение HOL Blocking).
- **Сжатие заголовков (QPACK):** Эволюция HPACK. Учитывает возможность доставки пакетов не по порядку, исключая блокировку декодера. Использует статическую таблицу, динамическую таблицу и Huffman-кодирование, но адаптировано для неупорядоченной доставки QUIC.
- **Сверхбыстрое рукопожатие:**
  - **1-RTT:** Объединяет транспортное и криптографическое (TLS 1.3) рукопожатие.
  - **0-RTT (Early Data):** Позволяет клиенту, уже общавшемуся с сервером, отправлять данные (например, GET-запрос) в самом первом пакете.
  - *Безопасность 0-RTT:* Уязвимо для **Replay Attacks** (атак повторного воспроизведения). Серверы должны принимать в Early Data только идемпотентные безопасные запросы (GET) и отклонять POST/PUT. Используется `max_early_data_size` и проверка свежести тикетов.
- **Connection Migration (Миграция соединений):** Соединение привязано к криптографическому **Connection ID**, а не к 4-tuple (Source IP, Source Port, Dest IP, Dest Port). При переключении с Wi-Fi на LTE скачивание не прерывается. Процесс включает Path Validation для подтверждения новой маршрутизации.

**Механизмы обнаружения (Alt-Svc):**
Так как HTTP исторически использует TCP:443, клиент сначала подключается по HTTP/2 и получает от сервера заголовок, сообщающий о наличии QUIC:
`Alt-Svc: h3=":443"; ma=86400`
Современные клиенты также используют DNS-записи типа `HTTPS` для мгновенного обнаружения.

### HTTPS — Шифрование HTTP

HTTPS не является отдельным протоколом, это HTTP, работающий поверх протокола **TLS (Transport Layer Security)**. В HTTP/3 шифрование является неотъемлемой частью QUIC (TLS 1.3).

**Что шифруется:**

- Стартовая строка запроса и все заголовки (включая `Host`, `Cookie`, пути к API).
- Тело сообщения (Payload).

**Что не шифруется:**

- IP-адреса источника и назначения.
- **SNI (Server Name Indication):** Имя домена видно в открытом виде (в TLS 1.2 и ниже), что позволяет провайдерам блокировать ресурсы по домену.
- **Решение (ECH):** В TLS 1.3 внедрен механизм **Encrypted Client Hello (ECH)**, который шифрует даже SNI, полностью скрывая целевой домен от пассивного наблюдения (требует поддержки DNS и провайдера).

## Практические сценарии

### Сценарий 1: Проверка версии HTTP через curl

```bash
# Проверка поддержки HTTP/2
curl -v -I --http2 https://example.com/
# → ищем в выводе: ALPN, server accepted h2

# Проверка поддержки HTTP/3 (требуется curl с поддержкой ngtcp2)
curl -v -I --http3 https://example.com/
# → ищем в выводе: ALPN, server accepted h3

# Проверка версии через verbose вывод
curl -s -o /dev/null -w "Protocol: HTTP/%{http_version}\n" https://example.com/
# → Protocol: HTTP/2
# → Protocol: HTTP/3
```

**Валидация:**

- Для HTTP/2: наличие `ALPN, server accepted h2` в выводе `curl -v`.
- Для HTTP/3: наличие `ALPN, server accepted h3` в выводе `curl -v --http3`.
- Если версия не совпадает с запрошенной — проверьте, поддерживает ли сервер указанную версию и включён ли ALPN.

### Сценарий 2: Диагностика поддержки HTTP/3

Если сайт не загружается по HTTP/3, необходимо выполнить проверку по следующим шагам:

1. **Проверка доступности UDP-порта 443 (часто блокируется корпоративными файрволами):**

    ```bash
    nc -zvu example.com 443
    # → Connection to example.com 443 port [udp/http-alt] succeeded!
    ```

2. **Проверка заголовка Alt-Svc:**

    ```bash
    curl -s -I https://example.com/ | grep -i Alt-Svc
    # → alt-svc: h3=":443"; ma=86400
    ```

3. **Проверка DNS-записи HTTPS:**

    ```bash
    dig example.com HTTPS +short
    # → 1 . alpn="h3,h2" ipv4hint=93.184.216.34
    ```

4. **Проверка поддержки QUIC через официальный тест:**

    ```bash
    curl -s -o /dev/null -w "HTTP Version: %{http_version}\n" --http3 https://example.com/
    # → HTTP Version: 3
    ```

**Валидация:**

- Если `nc` не может подключиться — UDP 443 заблокирован. Необходимо открыть порт на файрволе.
- Если Alt-Svc отсутствует — сервер не анонсирует HTTP/3. Проверьте конфигурацию веб-сервера.
- Если DNS HTTPS-запись отсутствует — клиент будет полагаться только на Alt-Svc, что замедляет обнаружение.

### Сценарий 3: Настройка HTTPS-редиректа и Alt-Svc в Nginx

```nginx
# В контексте http{} для Angie/Nginx 1.25+
quic_bpf on;

server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;         # Для HTTP/1.1 и HTTP/2
    listen 443 quic reuseport; # Для HTTP/3 (QUIC)
    
    server_name example.com;

    ssl_certificate     /etc/nginx/ssl/cert.crt;
    ssl_certificate_key /etc/nginx/ssl/cert.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;

    # Информируем браузеры о поддержке HTTP/3 на сутки
    add_header Alt-Svc 'h3=":443"; ma=86400';

    # Приоритизация HTTP/3 (RFC 9218)
    # http3_recv_priority on; # Angie-specific

    location / {
        root   /var/www/html;
        index  index.html index.htm;
    }
}
```

**Валидация:**

- Проверка синтаксиса: `nginx -t`.
- Проверка поддержки HTTP/2: `curl -I --http2 https://example.com/` → должно содержать `HTTP/2 200`.
- Проверка поддержки HTTP/3: `curl -I --http3 https://example.com/` → должно содержать `HTTP/3 200`.
- Проверка UDP: `nc -zvu example.com 443` → `succeeded!`.

### Сценарий 4: Анализ трафика HTTP/2 и HTTP/3 в Wireshark

Для глубокого анализа протоколов используйте Wireshark с фильтрами:

```bash
# Захват на интерфейсе (требует sudo)
sudo tcpdump -i eth0 -w /tmp/http_traffic.pcap port 443

# Открыть в Wireshark и применить фильтры:
# HTTP/2: http2
# QUIC: quic
# TLS: tls
```

**Ожидаемые артефакты:**

- Для HTTP/2: кадры `HEADERS` и `DATA` в рамках одного TCP-потока. Без дешифровки TLS видны только метаданные TLS.
- Для HTTP/3: кадры QUIC с типами `CRYPTO`, `STREAM`, `ACK`. Для дешифровки экспортируйте ключи через `SSLKEYLOGFILE`.

**Валидация:**

- Убедитесь, что TLS handshake использует TLS 1.3 (для HTTP/3).
- Проверьте, что после handshake идут QUIC-кадры с типом `STREAM` (данные) и `CRYPTO` (рукопожатие).
- При наличии `SSLKEYLOGFILE` в Wireshark видны расшифрованные заголовки HTTP.

### Сценарий 5: Тестирование 0-RTT (Early Data)

```bash
# Включение 0-RTT на сервере (Nginx/Angie):
# ssl_early_data on;

# Проверка 0-RTT с curl (требует поддержку ngtcp2 и TLS 1.3):
curl -v --http3 --data-early https://example.com/ \
  -H "Early-Data: 1" \
  -d "test"
```

**Ожидаемый вывод (сервер принял Early Data):**

```http
> GET / HTTP/3
> Host: example.com
> Early-Data: 1
< HTTP/3 200
< early-data: 1
```

**Валидация:**

- Если сервер вернул `425 Too Early` — Early Data отклонён (тикет просрочен или сервер не настроен на приём 0-RTT).
- Убедитесь, что запрос идемпотентный (GET/HEAD). Отправка POST через 0-RTT может привести к дублированию данных.

### Сценарий 6: Сравнение Server Push и Resource Hints (Preload)

**Server Push (HTTP/2, устарело):**

```nginx
# Nginx (работало в HTTP/2, игнорируется в HTTP/3)
http2_push /static/style.css;
http2_push /static/app.js;
```

**Resource Hints (современный стандарт):**

```html
<link rel="preload" href="/static/style.css" as="style">
<link rel="preconnect" href="https://fonts.example.com">
<link rel="dns-prefetch" href="https://fonts.example.com">
```

**Ожидаемый результат:**

- Server Push: браузер получает ресурсы до явного запроса. В HTTP/3 игнорируется.
- Preload: браузер запрашивает ресурс с высоким приоритетом после парсинга HTML.
- Preconnect/DNS-prefetch: ускоряет установку TCP/TLS-соединения к сторонним доменам.

**Валидация:**

- Проверьте сетевую панель DevTools: Server Push ресурсы отображаются как `Push` в HTTP/2.
- Preload ресурсы отображаются с высокой приоритизацией.
- Рекомендуется использовать Preload вместо Server Push — он работает во всех версиях HTTP и не конфликтует с кэшем.

### Сценарий 7: Валидация Alt-Svc и HTTPS DNS-записи

```bash
# Проверка Alt-Svc заголовка
curl -s -I https://example.com/ | grep -i alt-svc
# → alt-svc: h3=":443"; ma=86400, h3-29=":443"; ma=86400

# Проверка HTTPS DNS-записи (RFC 9460)
dig example.com HTTPS +short
# → 1 . alpn="h3,h2" ipv4hint=93.184.216.34 ipv6hint=2606:2800:220:1:248:1893:25c8:1946

# Проверка с принудительным использованием Alt-Svc
curl --alt-svc /tmp/alt-svc-cache --http3-only https://example.com/
# → HTTP/3 200 OK
```

**Валидация:**

- `ma=86400` — время жизни записи в секундах (сутки).
- `h3-29` — поддержка версии QUIC с конкретным номером варианта (для совместимости).
- Если DNS-запись HTTPS содержит `alpn="h3,h2"` — клиент узнаёт о поддержке HTTP/3 до первого TCP-соединения (быстрее Alt-Svc).

## Типичные проблемы и диагностика

### 1. HTTP/3 не работает за корпоративным файрволом

**Симптом:** `curl --http3` возвращает таймаут или `Connection refused`.

**Причина:** UDP-порт 443 закрыт или ограничен Deep Packet Inspection (DPI).

**Решение:**

```bash
# Проверка доступности UDP-порта
nc -zvu example.com 443

# Проверка MTU (QUIC чувствителен к фрагментации)
ping -M do -s 1400 example.com
```

### 2. HTTP/2 работает медленнее HTTP/1.1

**Симптом:** Рост TTFB и снижение RPS после включения HTTP/2.

**Причина:** 
- Отсутствие reuse TCP-соединений (Connection: close).
- Тяжёлые TLS handshakes без session resumption.
- Динамическое сжатие блокирует воркер (Head-of-Line на уровне приложения).

**Решение:**

```bash
# Включение session tickets
ssl_session_cache shared:SSL:10m;
ssl_session_timeout 10m;

# Отключение динамического сжатия для HTTP/2 (если используется)
gzip off;  # или использование gzip_static
```

### 3. HPACK-бомба / Flood

**Симптом:** Высокое потребление CPU и памяти на прокси/сервере, исчерпание ресурсов декодера HPACK.

**Причина:** Вредоносный клиент отправляет запросы с огромным количеством динамических заголовков, переполняя таблицу HPACK.

**Решение:**

```bash
# Nginx/Angie 1.25.1+
max_headers 100;
```

### 4. 0-RTT отклоняется сервером

**Симптом:** `425 Too Early` или игнорирование Early Data.

**Причина:**
- Тикет сессии истёк (`max_early_data_size` превышен).
- Сервер не настроен на приём 0-RTT (`ssl_early_data off`).

**Решение:**

```bash
# Проверка конфигурации
nginx -T | grep early_data

# Включение (осторожно — только для GET/HEAD)
ssl_early_data on;
ssl_conf_command Options no_ticket;  # или настройка Tickets
```

### 5. Connection Migration не работает при смене сети

**Симптом:** Соединение разрывается при переключении с Wi-Fi на LTE.

**Причина:** Отсутствует Path Validation или Connection ID меняется при reload.

**Решение:**

```bash
# Проверка поддержки CID
ss -u -a | grep :443

# Включение quic_bpf для сохранения воркеров (Angie/Nginx)
quic_bpf on;
```

### 6. Server Push кэширует устаревшие ресурсы

**Симптом:** Клиент получает устаревший CSS/JS из pushed ресурсов, игнорируя актуальный кэш.

**Причина:** Server Push игнорирует кэш-контроль и приоритизирует pushed ресурсы.

**Решение:** Отключить Server Push, использовать Resource Hints (`preload`, `preconnect`).

### 7. Сбой согласования ALPN

**Симптом:** Клиент использует HTTP/1.1 вместо HTTP/2/HTTP/3.

**Причина:** ALPN не настроен или клиент не поддерживает указанные протоколы.

**Решение:**

```bash
# Проверка ALPN через OpenSSL
openssl s_client -connect example.com:443 -alpn h2,h3 -servername example.com
# → ALPN protocol: h2 (или h3)
```

## Лучшие практики

1. **Использовать HTTP/2+ для браузерного трафика:** Включите HTTP/2 на всех HTTPS-серверах. Для HTTP/3 используйте только после валидации пользовательской базы.
2. **Включать HTTP/3 только после валидации:** Проверьте поддержку UDP 443 на целевых сетях (мобильные, корпоративные). Используйте Alt-Svc с разумным `ma` (86400–604800).
3. **Отключать Server Push:** Используйте Resource Hints (`preload`, `preconnect`, `dns-prefetch`) вместо Server Push. Server Push удалён из HTTP/3 и игнорируется браузерами.
4. **Настраивать TLS 1.3:** Уберите TLS 1.0/1.1. TLS 1.3 сокращает handshake до 1 RTT и необходим для HTTP/3.
5. **Использовать Connection Migration:** Для мобильных приложений и API настройте `reuseport` и `quic_bpf` для сохранения сессий при смене сети.
6. **Настраивать ECH для приватности SNI:** Шифруйте SNI через Encrypted Client Hello, если целевая аудитория требует приватности от пассивного наблюдения.
7. **Мониторить QUIC-потоки:** Используйте `ss -u -a` для мониторинга UDP-соединений. Отслеживайте `stateless reset` и `connection close` в логах.
8. **Использовать 0-RTT только для идемпотентных операций:** Разрешайте Early Data только для GET/HEAD. Настройте `max_early_data_size` и проверку тикетов.
9. **Настраивать Alt-Svc с разумным `ma`:** Слишком долгий `ma` (недели) приведёт к распространению устаревшей конфигурации при изменении серверов. Сутки (`86400`) — оптимально.
10. **Применять Happy Eyeballs:** Если поддерживаете dual-stack, настройте Happy Eyeballs v2/v3 для быстрого переключения между IPv4 и IPv6.

## Граничные случаи и ограничения

1. **HTTP/2 с очень старыми клиентами:** Windows XP, Android < 4.3 не поддерживают ALPN. Для таких клиентов автоматически используется HTTP/1.1.
2. **UDP-фрагментация и MTU:** QUIC-пакеты превышают стандартный MTU (1500), что приводит к фрагментации на IP-уровне. Настройте PMTU discovery (PLPMTUD, RFC 8899).
3. **0-RTT и Replay Attacks:** Даже для GET-запросов 0-RTT может быть опасен (например, повторная отправка формы через JavaScript API). Используйте `Anti-Replay` механизмы на уровне приложения.
4. **Connection ID exhausting:** При очень большом количестве уникальных клиентов (millions) может исчерпаться пространство Connection ID. Мониторьте метрики.
5. **HPACK Bomb:** Динамическая таблица HPACK может быть переполнена вредоносными запросами. Ограничьте количество заголовков (`max_headers`) и размер тела запроса.
6. **NAT rebinding и QUIC:** При изменении NAT-таблицы провайдера (смена порта) QUIC-соединение может быть разорвано. Connection Migration помогает, но требует Path Validation.
7. **Версионная несовместимость QUIC:** Разные версии QUIC (draft-29, v1, v2) несовместимы. Убедитесь, что клиент и сервер используют совместимые версии через Version Negotiation.
8. **TLS session resumption across versions:** Тикеты TLS 1.2 не работают для TLS 1.3 и QUIC. Настройте отдельное кэширование тикетов для TLS 1.3 (`ssl_session_cache`).
9. **Редиректы с HTTP/3:** При 301/302 редиректе клиент может вернуться на HTTP/2. Настройте сервер для приёма Alt-Svc на всех версиях.
10. **gRPC и HTTP/2 flow control:** gRPC использует HTTP/2 с большими сообщениями. Настройте `SETTINGS_MAX_FRAME_SIZE` и мониторьте `WINDOW_UPDATE`, чтобы избежать зависаний потоков.

## Дополнительная информация

### Выбор версии протокола

- **HTTP/1.1:** Используется для межсервисного взаимодействия (microservices) в закрытых контурах (где TCP-соединения постоянны и накладные расходы минимальны), для обратной совместимости или при использовании аппаратных балансировщиков.
- **HTTP/2:** Стандарт де-факто для браузерного веба и gRPC.
- **HTTP/3:** Оптимален для сетей с высокими потерями пакетов (мобильные сети, спутниковый интернет).

### Безопасность и HSTS

**HSTS (HTTP Strict Transport Security)** — заголовок ответа, предписывающий браузеру принудительно использовать HTTPS для домена, даже если пользователь ввел `http://`.

Пример:
`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`
