# Эволюция HTTP и HTTPS

## Definitions

**HTTP (Hypertext Transfer Protocol)** — протокол прикладного уровня для передачи гипертекста, эволюционировавший с 1996 года для решения проблем производительности, безопасности и функциональности.

**HTTPS (HTTP Secure)** — комбинация HTTP с протоколом шифрования [TLS (Transport Layer Security)](../tls.md), обеспечивающая конфиденциальность, целостность и аутентификацию данных.

**QUIC (Quick UDP Internet Connections)** — транспортный протокол на базе UDP, разработанный Google и стандартизированный в RFC 9000. Лежит в основе HTTP/3, обеспечивая мультиплексирование, надёжность и шифрование.

**Head-of-Line (HOL) Blocking** — проблема, при которой потеря или задержка одного пакета блокирует обработку всех последующих данных в том же соединении.

## Basic Concepts

### Сравнительная таблица версий HTTP

| Характеристика | HTTP/1.0 (1996) | HTTP/1.1 (1997) | HTTP/2 (2015) | HTTP/3 (2022) |
| :--- | :--- | :--- | :--- | :--- |
| **Транспорт** | TCP | TCP | TCP | **QUIC (UDP)** |
| **Соединения** | Новое на запрос | Keep-Alive | Одно на домен | Одно на домен |
| **Параллелизм** | Нет | Pipelining | **Мультиплексирование** | **Мультиплексирование** |
| **HOL Blocking** | Да (TCP) | Да (TCP) | Да (TCP) | **Нет** |
| **Формат** | Текстовый | Текстовый | **Бинарный** | **Бинарный** |
| **Сжатие заголовков** | Нет | Нет | **HPACK** | **QPACK** |
| **Server Push** | Нет | Нет | Да (устарел) | Нет (убрано) |
| **Шифрование** | Нет | Опционально | Де-факто обязательно (TLS) | Обязательно (TLS в QUIC) |
| **Установление соединения** | 3 RTT | 3 RTT | 3 RTT | **1 RTT (0-RTT)** |
| **Connection Migration** | Нет | Нет | Нет | **Да** |

### HTTP/1.0 (1996)

Первая стандартизированная версия HTTP (RFC 1945).

**Проблемы:**

- Новое TCP-соединение на каждый ресурс (HTML, CSS, JS, изображения).
- Большие накладные расходы на рукопожатия TCP.
- Отсутствие кэширования соединений.

### HTTP/1.1 (1997, обновления 2014)

Стандарт более чем на 15 лет (RFC 2068 → RFC 2616 → RFC 7230-7237).

**Ключевые улучшения:**

- **Постоянные соединения (Keep-Alive):** Несколько запросов в рамках одного TCP-соединения, что сократило задержки.
- **Chunked Transfer Encoding:** Сервер передаёт данные частями (чанками), не зная полный размер ответа заранее.
- **Pipeline (ограниченно):** Возможность отправлять запросы, не дожидаясь ответов. Работала плохо из-за HOL-блокировки — ответы должны приходить строго по порядку.
- **Обязательный заголовок `Host`:** Поддержка виртуальных хостов (несколько доменов на одном IP).

**Ограничения:**

- HOL-блокировка на уровне TCP.
- Браузеры ограничивали до 6 параллельных соединений на домен.
- Текстовый протокол — сложен для парсинга и менее эффективен.

### HTTP/2 (2015)

Революционное обновление на базе протокола SPDY от Google (RFC 7540 → RFC 9113).

**Ключевые улучшения:**

- **Мультиплексирование:** Множество запросов/ответов передаются одновременно в одном TCP-соединении через бинарные кадры (frames). Решает HOL-блокировку на уровне приложения.
- **Бинарный протокол:** Более эффективный парсинг, меньше ошибок.
- **Сжатие заголовков (HPACK):** Значительное уменьшение размера заголовков за счёт таблицы индексации.
- **Server Push:** Сервер отправлял ресурсы до запроса клиента (например, CSS/JS вместе с HTML). На практике оказался сложным, в HTTP/3 убран.
- **Приоритизация:** Клиент указывает приоритеты для потоков (streams), сервер отдаёт предпочтение важным ресурсам.

**Практические аспекты:**

- Одно TCP-соединение на домен (вместо 6 в HTTP/1.1).
- Де-факто требует TLS для браузерной поддержки.
- Накладные расходы сервера: +20-30% CPU/RAM по сравнению с HTTP/1.1.
- **Антипаттерны, ставшие неактуальными:**
  - Доменный шардинг (создание поддоменов для обхода лимита соединений).
  - Конкатенация CSS/JS файлов (мультиплексирование позволяет загружать множество мелких файлов параллельно).

### HTTP/3 (2022)

Новейший стандарт (RFC 9114), решающий HOL-блокировку на транспортном уровне.

**Ключевые улучшения:**

- **Переход на QUIC (UDP):** Мультиплексирование, надёжность и шифрование поверх UDP. Потеря одного пакета влияет только на свой поток, не блокируя остальные.
- **Быстрое установление соединения:** QUIC объединяет TCP-рукопожатие и TLS в один процесс (1-RTT, или 0-RTT для повторных соединений).
- **Connection Migration:** Соединение привязано к уникальному ID, а не к IP-адресу. Переключение между Wi-Fi и мобильной сетью без разрыва.

**Практические аспекты:**

- Одно UDP-соединение на домен.
- Требует поддержку GSO (Generic Segmentation Offload) на сетевом адаптере.
- **Обнаружение клиентами:**
  - Заголовок `Alt-Svc: h3=":443"; ma=86400` (проблема «холодного старта» — браузер узнаёт о поддержке HTTP/3 только после первого ответа).
  - DNS-запись типа HTTPS: `example.com HTTPS 1 . alpn="h2,h3"` (предпочтительный вариант, браузер узнаёт до соединения).

**Сравнение времени установления соединения:**

- HTTP/1.1: 3 RTT (DNS + TCP + TLS)
- HTTP/2: 3 RTT (DNS + TCP + TLS)
- HTTP/3: 1-2 RTT (DNS + QUIC+TLS объединены)

### HTTPS — Шифрование HTTP

HTTPS — это не отдельный протокол, а HTTP поверх [TLS (Transport Layer Security)](../tls.md). TLS обеспечивает три столпа безопасности: шифрование, аутентификацию и целостность.

**Что шифруется:**

- Стартовая строка запроса (`GET /page HTTP/1.1`).
- Все HTTP-заголовки (`Host`, `User-Agent`, `Cookie`).
- Тело сообщения (payload).

**Что НЕ шифруется:**

- IP-адреса источника и назначения (видны на сетевом уровне).
- SNI (Server Name Indication) в TLS < 1.3 (домен виден при рукопожатии). В TLS 1.3 поддерживается Encrypted SNI (ESNI).

## Practical Scenarios

### Сценарий 1: Проверка версии HTTP через curl

```bash
curl -I --http2 https://example.com/
```

Ответ покажет использованную версию:

```http
HTTP/2 200
server: nginx
content-type: text/html
```

Проверка поддержки HTTP/3:

```bash
curl -I --http3 https://example.com/
```

### Сценарий 2: Проверка версии HTTP в браузере

Открыть Developer Tools (F12) → вкладка **Network** → колонка **Protocol**.

Значения:

- `h2` — HTTP/2
- `h3` — HTTP/3
- `http/1.1` — HTTP/1.1

Если колонки Protocol нет — кликнуть правой кнопкой на заголовки таблицы → включить «Protocol».

### Сценарий 3: Диагностика проблем с HTTP/3

**Симптомы:** Сайт не загружается по HTTP/3, fallback на HTTP/2.

**Алгоритм диагностики:**

1. **Проверить UDP-порт 443:**

   ```bash
   nc -zvu example.com 443
   ```

2. **Проверить заголовок Alt-Svc:**

   ```bash
   curl -I https://example.com/ | grep Alt-Svc
   ```

   Ожидаемый вывод: `alt-svc: h3=":443"; ma=86400`

3. **Проверить DNS-запись HTTPS:**

   ```bash
   dig example.com HTTPS
   ```

   Ожидаемый вывод: `alpn="h2,h3"`

4. **Проверить поддержку QUIC в Nginx/Angie:**

   ```bash
   nginx -V 2>&1 | grep -o with-http_v3_module
   ```

### Сценарий 4: Миграция с HTTP/1.1 на HTTP/2

**Шаги:**

1. **Настроить HTTPS:** HTTP/2 требует TLS. Получить сертификат (Let's Encrypt, Certbot).

2. **Включить HTTP/2 в Nginx:**

   ```nginx
   server {
       listen 443 ssl http2;
       server_name example.com;
       # ... TLS конфигурация
   }
   ```

3. **Убрать антипаттерны:**
   - Отключить доменный шардинг (убрать `cdn1.`, `cdn2.`, `cdn3.`).
   - Разделить конкатенированные CSS/JS файлы (опционально).

4. **Протестировать:**

   ```bash
   curl -I --http2 https://example.com/
   ```

5. **Мониторить метрики:** Ожидать рост производительности на клиенте, но +20-30% нагрузки на сервер.

### Сценарий 5: Настройка HTTPS-редиректа

Все HTTP-запросы должны перенаправляться на HTTPS с кодом `301 Moved Permanently`:

```nginx
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name example.com;
    # SSL конфигурация...
}
```

## Additional Information

### RFC и стандартизация

| Версия | RFC | Год |
| :--- | :--- | :--- |
| HTTP/1.0 | RFC 1945 (исторический) | 1996 |
| HTTP/1.1 | RFC 7230-7237 → RFC 9112 | 1997 / 2022 |
| HTTP/2 | RFC 7540 → RFC 9113 | 2015 / 2022 |
| HTTP/3 | RFC 9114 | 2022 |
| QUIC | RFC 9000 | 2022 |

### Выбор версии HTTP для DevOps

**HTTP/1.1:**

- Legacy-системы, внутренние сервисы без TLS.
- Отдача больших файлов с kTLS (на 30% быстрее HTTP/2).

**HTTP/2:**

- Стандарт для публичных веб-сайтов и API.
- Мультиплексирование ускоряет загрузку множества мелких ресурсов.
- Требует +20-30% ресурсов сервера.

**HTTP/3:**

- Оптимален для мобильных пользователей (нестабильная сеть, переключение Wi-Fi ↔ LTE).
- Решает HOL-блокировку на транспортном уровне.
- Требует Nginx 1.25.0+ или Angie, поддержку GSO, открытый UDP 443.

### HTTPS и DevOps

- **HSTS (HTTP Strict Transport Security):** Заголовок `Strict-Transport-Security: max-age=31536000; includeSubDomains` указывает браузеру использовать только HTTPS.
- **Let's Encrypt:** Бесплатные TLS-сертификаты, автоматическое продление через Certbot.
- **TLS 1.3:** Современная версия TLS, быстрее рукопожатие (1-RTT), безопасные шифры.
