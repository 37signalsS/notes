# Эволюция HTTP и HTTPS

## Определения

**HTTP (Hypertext Transfer Protocol)** — протокол прикладного уровня, эволюционировавший для решения проблем производительности и безопасности. Современные спецификации консолидированы в серии **RFC 911x**. Базовая семантика (методы, статусы, заголовки) определена в **RFC 9110** и является общей для всех версий транспорта.

**HTTPS (HTTP Secure)** — использование HTTP поверх протокола шифрования **TLS (Transport Layer Security)**. Обеспечивает конфиденциальность, целостность и аутентификацию. В современных реализациях (TLS 1.3) скрывает SNI (Server Name Indication) через механизм **ECH (Encrypted Client Hello)**.

**QUIC (Quick UDP Internet Connections)** — транспортный протокол (RFC 9000) на базе UDP. Объединяет функции TCP (надежность, контроль перегрузок) и TLS 1.3 (безопасность) в единый слой. Фундамент для HTTP/3.

**Head-of-Line (HOL) Blocking (Блокировка начала очереди)** — задержка обработки данных из-за потери или медленной обработки первого пакета в очереди. 
- В HTTP/1.1 возникает на уровне HTTP-сообщений.
- В HTTP/2 решена на уровне HTTP, но остается на уровне TCP-пакетов.
- В HTTP/3 полностью устранена благодаря независимым потокам QUIC.

## Основные концепции

### Сравнительная таблица версий HTTP

| Характеристика | HTTP/1.1 | HTTP/2 | HTTP/3 |
| :--- | :--- | :--- | :--- |
| **Спецификация** | RFC 9112 | RFC 9113 | RFC 9114 |
| **Транспорт** | TCP | TCP | **QUIC (UDP)** |
| **Формат передачи** | Текстовый (Plain Text) | Бинарные кадры (Binary Frames) | Бинарные кадры |
| **Мультиплексирование** | Нет (Pipelining не прижился) | Да (TCP-потоки) | Да (QUIC-потоки) |
| **HOL Blocking** | Уровень соединения | Уровень TCP-пакета | **Устранена** |
| **Сжатие заголовков** | Нет | HPACK (Статический/Динамический словари) | QPACK (Адаптирован для UDP) |
| **Рукопожатие (Handshake)** | 3 RTT (TCP + TLS) | 3 RTT | **1 RTT / 0-RTT (Early Data)** |
| **Миграция сессии** | Нет | Нет | **Да (Connection ID)** |
| **Шифрование** | Опционально | Опционально (Де-факто обязательно) | **Встроено (TLS 1.3)** |

### HTTP/1.0 (1996)

Первая стандартизированная версия HTTP (RFC 1945).

**Проблемы:**

- Новое TCP-соединение на каждый ресурс (HTML, CSS, JS, изображения).
- Большие накладные расходы на рукопожатия TCP (Transmission Control Protocol).
- Отсутствие кэширования соединений.

### HTTP/1.1 (1997, обновления 2014)

Стандарт более чем на 15 лет (RFC 2068 → RFC 2616 → RFC 7230-7237).

**Ключевые улучшения:**

- **Постоянные соединения (Keep-Alive):** Несколько запросов в рамках одного TCP-соединения, что сократило задержки.
- **Chunked Transfer Encoding:** Сервер передаёт данные частями (чанками), не зная полный размер ответа заранее.
- **Pipeline (ограниченно):** Возможность отправлять запросы, не дожидаясь ответов. Работала плохо из-за HOL-блокировки — ответы должны приходить строго по порядку.
- **Обязательный заголовок `Host`:** Поддержка виртуальных хостов (несколько доменов на одном IP-адресе).

**Ограничения:**

- HOL-блокировка на уровне TCP.
- Браузеры ограничивали до 6 параллельных соединений на домен.
- Текстовый протокол — сложен для парсинга и менее эффективен.

### HTTP/2 (2015)

Революционное обновление на базе протокола SPDY от Google (RFC 7540 → RFC 9113).

**Ключевые улучшения:**

- **Мультиплексирование:** Множество запросов и ответов передаются одновременно в одном TCP-соединении. Сообщения разбиваются на **бинарные кадры (frames)** (например, `HEADERS`, `DATA`, `SETTINGS`), которые перемешиваются в потоке и собираются на другой стороне. Это решает HOL-блокировку на прикладном уровне.
- **Сжатие заголовков (HPACK):** Использование статических и динамических словарей (индексов) для устранения избыточности при передаче повторяющихся заголовков (Cookie, User-Agent).
- **Приоритизация:** Клиент указывает вес потока (stream dependency), позволяя серверу отдавать критичный контент (CSS) раньше менее важного (картинки).
- **Server Push (Устарело):** Позволяло серверу отправлять ресурсы до запроса. На практике оказалось неэффективным (конфликты с браузерным кэшем) и удалено из спецификаций HTTP/3.

**Практические аспекты:**

- Де-факто требует TLS (браузеры поддерживают HTTP/2 только поверх HTTPS через расширение ALPN).
- Сделало антипаттернами "спрайты" (image sprites) и конкатенацию JS/CSS — теперь выгоднее отдавать множество мелких файлов параллельно.

### HTTP/3 (2022)

Новейший стандарт (RFC 9114), полностью меняющий транспортный уровень для решения оставшихся проблем TCP.

**Ключевые улучшения:**

- **Переход на QUIC (UDP):** Мультиплексирование, контроль перегрузок и шифрование реализованы поверх UDP. Потеря одного UDP-пакета влияет только на конкретный поток (stream), не блокируя остальные (полное устранение HOL Blocking).
- **Сжатие заголовков (QPACK):** Эволюция HPACK. Учитывает возможность доставки пакетов не по порядку, исключая блокировку декодера.
- **Сверхбыстрое рукопожатие:**
  - **1-RTT:** Объединяет транспортное и криптографическое (TLS 1.3) рукопожатие.
  - **0-RTT (Early Data):** Позволяет клиенту, уже общавшемуся с сервером, отправлять данные (например, GET-запрос) в самом первом пакете.
  - *Безопасность 0-RTT:* Уязвимо для **Replay Attacks** (атак повторного воспроизведения). Серверы должны принимать в Early Data только идемпотентные безопасные запросы (GET) и отклонять POST/PUT.
- **Connection Migration (Миграция соединений):** Соединение привязано к криптографическому **Connection ID**, а не к 4-tuple (Source IP, Source Port, Dest IP, Dest Port). При переключении с Wi-Fi на LTE скачивание не прерывается.

**Механизмы обнаружения (Alt-Svc):**
Так как HTTP исторически использует TCP:443, клиент сначала подключается по HTTP/2 и получает от сервера заголовок, сообщающий о наличии QUIC:
`Alt-Svc: h3=":443"; ma=86400`
Современные клиенты также используют DNS-записи типа `HTTPS` для мгновенного обнаружения.

### HTTPS — Шифрование HTTP

HTTPS не является отдельным протоколом, это HTTP, работающий поверх протокола **TLS (Transport Layer Security)**. В HTTP/3 шифрование является неотъемлемой частью QUIC (TLS 1.3).

**Что шифруется:**

- Стартовая строка запроса и все заголовки (включая `Host`, `Cookie`, пути к API).
- Тело сообщения (Payload).

**Что не шифруется:**

- IP-адреса источника и назначения.
- **SNI (Server Name Indication):** Имя домена видно в открытом виде (в TLS 1.2 и ниже), что позволяет провайдерам блокировать ресурсы по домену.
- **Решение (ECH):** В TLS 1.3 внедрен механизм **Encrypted Client Hello (ECH)**, который шифрует даже SNI, полностью скрывая целевой домен от пассивного наблюдения (требует поддержки DNS и провайдера).

## Практические сценарии

### Сценарий 1: Проверка версии HTTP через curl

```bash
# Проверка поддержки HTTP/2
curl -v -I --http2 https://example.com/
# В выводе ищем ALPN: server accepted h2

# Проверка поддержки HTTP/3 (требуется curl с поддержкой ngtcp2)
curl -v -I --http3 https://example.com/
# В выводе ищем ALPN: server accepted h3
```

### Сценарий 2: Диагностика поддержки HTTP/3

Если сайт не загружается по HTTP/3, необходимо выполнить проверку по следующим шагам:

1. **Проверка доступности UDP-порта 443 (часто блокируется корпоративными файрволами):**

   ```bash
   nc -zvu example.com 443
   ```

2. **Проверка заголовка Alt-Svc:**

   ```bash
   curl -s -I https://example.com/ | grep -i Alt-Svc
   ```

3. **Проверка DNS-записи HTTPS:**

   ```bash
   dig example.com HTTPS +short
   ```

### Сценарий 3: Настройка HTTPS-редиректа и Alt-Svc в Nginx

```nginx
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;         # Для HTTP/1.1 и HTTP/2
    listen 443 quic reuseport; # Для HTTP/3 (QUIC)
    
    server_name example.com;

    # Информируем браузеры о поддержке HTTP/3 на сутки
    add_header Alt-Svc 'h3=":443"; ma=86400';
}
```

## Дополнительная информация

### Выбор версии протокола

- **HTTP/1.1:** Используется для межсервисного взаимодействия (microservices) в закрытых контурах (где TCP-соединения постоянны и накладные расходы минимальны), для обратной совместимости или при использовании аппаратных балансировщиков.
- **HTTP/2:** Стандарт де-факто для браузерного веба и gRPC.
- **HTTP/3:** Оптимален для сетей с высокими потерями пакетов (мобильные сети, спутниковый интернет).

### Безопасность и HSTS

**HSTS (HTTP Strict Transport Security)** — заголовок ответа, предписывающий браузеру принудительно использовать HTTPS для домена, даже если пользователь ввел `http://`.

Пример:
`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`
