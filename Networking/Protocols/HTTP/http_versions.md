# Эволюция HTTP и HTTPS

## Определения

**HTTP (Hypertext Transfer Protocol — протокол передачи гипертекста)** — протокол прикладного уровня для передачи гипертекста, эволюционировавший с 1996 года для решения проблем производительности, безопасности и функциональности.

**HTTPS (HTTP Secure)** — комбинация HTTP с протоколом шифрования **TLS (Transport Layer Security — безопасность транспортного уровня)**, обеспечивающая конфиденциальность, целостность и аутентификацию данных.

**QUIC (Quick UDP Internet Connections — быстрые интернет-соединения UDP)** — транспортный протокол на базе UDP (User Datagram Protocol — протокол пользовательских датаграмм), разработанный Google и стандартизированный в RFC 9000. Лежит в основе HTTP/3, обеспечивая мультиплексирование, надёжность и шифрование.

**Head-of-Line (HOL) Blocking (блокировка начала очереди)** — проблема, при которой потеря или задержка одного пакета данных блокирует обработку всех последующих данных в рамках одного и того же соединения.

**RFC (Request for Comments — запрос комментариев)** — документы, содержащие технические спецификации и стандарты, широко используемые во Всемирной паутине.

## Основные концепции

### Сравнительная таблица версий HTTP

| Характеристика | HTTP/1.0 (1996) | HTTP/1.1 (1997) | HTTP/2 (2015) | HTTP/3 (2022) |
| :--- | :--- | :--- | :--- | :--- |
| **Транспорт** | TCP | TCP | TCP | **QUIC (UDP)** |
| **Соединения** | Новое на запрос | Keep-Alive | Одно на домен | Одно на домен |
| **Параллелизм** | Нет | Pipelining | **Мультиплексирование** | **Мультиплексирование** |
| **HOL Blocking** | Да (TCP) | Да (TCP) | Да (TCP) | **Нет** |
| **Формат** | Текстовый | Текстовый | **Бинарный** | **Бинарный** |
| **Сжатие заголовков** | Нет | Нет | **HPACK** | **QPACK** |
| **Server Push** | Нет | Нет | Да (устарел) | Нет (убрано) |
| **Шифрование** | Нет | Опционально | Де-факто обязательно (TLS) | Обязательно (TLS в QUIC) |
| **Установление соединения** | 3 RTT | 3 RTT | 3 RTT | **1 RTT (0-RTT)** |
| **Connection Migration** | Нет | Нет | Нет | **Да** |

### HTTP/1.0 (1996)

Первая стандартизированная версия HTTP (RFC 1945).

**Проблемы:**

- Новое TCP-соединение на каждый ресурс (HTML, CSS, JS, изображения).
- Большие накладные расходы на рукопожатия TCP (Transmission Control Protocol).
- Отсутствие кэширования соединений.

### HTTP/1.1 (1997, обновления 2014)

Стандарт более чем на 15 лет (RFC 2068 → RFC 2616 → RFC 7230-7237).

**Ключевые улучшения:**

- **Постоянные соединения (Keep-Alive):** Несколько запросов в рамках одного TCP-соединения, что сократило задержки.
- **Chunked Transfer Encoding:** Сервер передаёт данные частями (чанками), не зная полный размер ответа заранее.
- **Pipeline (ограниченно):** Возможность отправлять запросы, не дожидаясь ответов. Работала плохо из-за HOL-блокировки — ответы должны приходить строго по порядку.
- **Обязательный заголовок `Host`:** Поддержка виртуальных хостов (несколько доменов на одном IP-адресе).

**Ограничения:**

- HOL-блокировка на уровне TCP.
- Браузеры ограничивали до 6 параллельных соединений на домен.
- Текстовый протокол — сложен для парсинга и менее эффективен.

### HTTP/2 (2015)

Революционное обновление на базе протокола SPDY от Google (RFC 7540 → RFC 9113).

**Ключевые улучшения:**

- **Мультиплексирование:** Множество запросов и ответов передаются одновременно в одном TCP-соединении через бинарные кадры (frames). Решает HOL-блокировку на уровне приложения.
- **Бинарный протокол:** Более эффективный парсинг, меньше ошибок.
- **Сжатие заголовков (HPACK):** Значительное уменьшение размера заголовков за счёт таблицы индексации.
- **Server Push:** Сервер мог отправлять ресурсы до явного запроса клиента. На практике механизм оказался сложным и в HTTP/3 был удален.
- **Приоритизация:** Клиент указывает приоритеты для потоков (streams), сервер отдаёт предпочтение важным ресурсам.

**Практические аспекты:**

- Одно TCP-соединение на домен (вместо 6 в HTTP/1.1).
- Де-факто требует TLS для браузерной поддержки.
- **Антипаттерны, ставшие неактуальными:**
  - Доменный шардинг (создание поддоменов для обхода лимита соединений).
  - Конкатенация CSS/JS файлов (мультиплексирование позволяет загружать множество мелких файлов параллельно).

### HTTP/3 (2022)

Новейший стандарт (RFC 9114), решающий проблему HOL-блокировки на транспортном уровне.

**Ключевые улучшения:**

- **Переход на QUIC (UDP):** Мультиплексирование, надёжность и шифрование поверх UDP. Потеря одного пакета влияет только на свой поток, не блокируя остальные.
- **Быстрое установление соединения:** QUIC объединяет TCP-рукопожатие и TLS в один процесс (1-RTT, или 0-RTT для повторных соединений). **RTT (Round Trip Time)** — время, необходимое для передачи сигнала от отправителя к получателю и обратно.
- **Connection Migration:** Соединение привязано к уникальному идентификатору (ID), а не к IP-адресу. Это позволяет переключаться между Wi-Fi и мобильной сетью без разрыва соединения.

**Механизмы обнаружения:**

- Заголовок `Alt-Svc: h3=":443"; ma=86400`.
- DNS-запись типа HTTPS: `example.com HTTPS 1 . alpn="h2,h3"`.

### HTTPS — Шифрование HTTP

HTTPS не является отдельным протоколом, это HTTP, работающий поверх протокола **TLS (Transport Layer Security)**.

**Что шифруется:**

- Стартовая строка запроса.
- Все HTTP-заголовки (Host, Cookie и другие).
- Тело сообщения.

**Что не шифруется:**

- IP-адреса источника и назначения.
- **SNI (Server Name Indication — указание имени сервера)** в TLS версий ниже 1.3 (имя домена видно при рукопожатии).

## Практические сценарии

### Сценарий 1: Проверка версии HTTP через curl

```bash
# Проверка поддержки HTTP/2
curl -I --http2 https://example.com/

# Проверка поддержки HTTP/3 (требуется поддержка в curl)
curl -I --http3 https://example.com/
```

### Сценарий 2: Диагностика поддержки HTTP/3

Если сайт не загружается по HTTP/3, необходимо выполнить проверку по следующим шагам:

1. **Проверка доступности UDP-порта 443:**

   ```bash
   nc -zvu example.com 443
   ```

2. **Проверка заголовка Alt-Svc:**

   ```bash
   curl -I https://example.com/ | grep -i Alt-Svc
   ```

3. **Проверка DNS-записи HTTPS:**

   ```bash
   dig example.com HTTPS
   ```

### Сценарий 3: Настройка HTTPS-редиректа в Nginx

Для обеспечения безопасности все HTTP-запросы должны перенаправляться на HTTPS с кодом `301 Moved Permanently`.

```nginx
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}
```

## Дополнительная информация

### Выбор версии протокола

- **HTTP/1.1:** Используется для обратной совместимости, в legacy-системах или для передачи очень больших файлов (с использованием kTLS).
- **HTTP/2:** Стандарт для большинства современных веб-сайтов и API. Эффективен для загрузки большого количества мелких ресурсов.
- **HTTP/3:** Рекомендуется для мобильных приложений и пользователей с нестабильным интернет-соединением.

### Безопасность и HSTS

**HSTS (HTTP Strict Transport Security — строгая транспортная безопасность HTTP)** — заголовок ответа, который сообщает браузеру, что к данному сайту следует обращаться только по HTTPS.

Пример заголовка:
`Strict-Transport-Security: max-age=31536000; includeSubDomains`
