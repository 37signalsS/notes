# HTTP-аутентификация: Протоколы и механизмы

## Определения

**HTTP-аутентификация** — механизм протокола **HTTP**, позволяющий серверу запрашивать у клиента учетные данные (логин и пароль, токен, сертификат) для проверки личности перед предоставлением доступа к защищённым ресурсам.

**Основные заголовки:**

- **`WWW-Authenticate`** — заголовок ответа сервера, указывающий поддерживаемый метод аутентификации и область доступа (**`realm`**).
- **`Authorization`** — заголовок запроса клиента, содержащий учетные данные.
- **`Proxy-Authenticate` / `Proxy-Authorization`** — аналогичные заголовки для аутентификации на промежуточном прокси-сервере.

## Основные концепции

### Базовая аутентификация (Basic Authentication)

Простейший метод, встроенный непосредственно в протокол HTTP.

**Принцип работы:**

1. Клиент отправляет запрос к защищённому ресурсу.
2. Сервер отвечает кодом **`401 Unauthorized`** с заголовком `WWW-Authenticate: Basic realm="Restricted Area"`.
3. Браузер отображает системное окно ввода логина и пароля.
4. Клиент повторно отправляет запрос с заголовком `Authorization: Basic <данные_в_Base64>`.

**Безопасность:** Данные кодируются в Base64, но не шифруются. Метод допустим только при использовании **HTTPS (HTTP Secure — безопасный HTTP)**. Без шифрования канала учетные данные могут быть легко перехвачены.

### Токен Bearer (Bearer Token)

Метод передачи токена доступа, обычно полученного в результате внешней авторизации (например, через **OAuth 2.0 (Open Authorization)**).

**Особенности:**

- Клиент передает токен в заголовке `Authorization: Bearer <token>`.
- Часто используются **JWT (JSON Web Token — веб-токен JSON)**, которые позволяют серверу проверять права без обращения к базе данных (**stateless** подход).
- Токены имеют ограниченный срок жизни и четко определенную область действия (**scope**).
- Широко применяется в **REST API (Representational State Transfer Application Programming Interface)** и микросервисной архитектуре.

### Куки и сессии (Cookies and Sessions)

Механизм эмуляции состояния в stateless-протоколе HTTP.

**Принцип:**

1. Пользователь проходит аутентификацию (обычно через веб-форму).
2. Сервер создает сессию в базе данных и отправляет клиенту заголовок `Set-Cookie: session_id=abc12345`.
3. Клиент (браузер) **обязан** сохранять куки и автоматически прикреплять их в заголовке `Cookie` ко всем последующим запросам к этому домену.
4. Сервер идентифицирует пользователя по идентификатору сессии.

**Атрибуты безопасности куки:**

- **`HttpOnly`** — запрещает доступ к куки со стороны **JavaScript**, защищая от **XSS (Cross-Site Scripting — межсайтовый скриптинг)** атак.
- **`Secure`** — разрешает передачу куки только по шифрованному каналу HTTPS.
- **`SameSite`** — ограничивает отправку куки при запросах с других сайтов, защищая от **CSRF (Cross-Site Request Forgery — межсайтовая подделка запроса)** атак.

### Дайджест-аутентификация (Digest Authentication)

Более безопасная альтернатива Basic-аутентификации, при которой пароль не передается в открытом виде.

**Принцип:** Сервер отправляет случайное значение (**`nonce`**). Клиент вычисляет хэш пароля, объединяя его с `nonce` и другими параметрами запроса.

**Статус:** В современных системах используется редко, так как алгоритм MD5 считается устаревшим, а внедрение полноценного TLS делает Basic-аутентификацию достаточно безопасной.

### Взаимная TLS-аутентификация (mTLS)

Метод аутентификации на транспортном уровне, где не только клиент проверяет сервер, но и сервер требует от клиента валидный TLS-сертификат.

- **Применение:** Межсерверное взаимодействие (M2M), микросервисы в [Service Mesh](../../../Service_Mesh/service_mesh_concepts.md), критически важные API.
- **Преимущество:** Максимальная безопасность, так как учетные данные (закрытый ключ) никогда не передаются по сети.
- **Подробности:** См. **[mTLS в протоколе TLS](../tls.md#взаимная-аутентификация-mtls)**.

### API-ключи (API Keys)

Простейший способ аутентификации программных клиентов через передачу статического секрета в заголовке.

- **Формат:** Обычно используется кастомный заголовок, например `X-API-Key: <secret>`.
- **Использование:** Публичные API для ограничения лимитов (Rate Limiting) и идентификации приложений.
- **Безопасность:** Ключи легко скомпрометировать при логировании или перехвате трафика (требуют обязательного HTTPS).

### Единый вход (Single Sign-On — SSO)

Технология, позволяющая пользователю аутентифицироваться один раз для доступа к множеству независимых систем.

**Реализация:**

- **OIDC (OpenID Connect):** Современный стандарт на базе OAuth 2.0. Использует **PKCE (Proof Key for Code Exchange)** для защиты авторизационных кодов в браузерных и мобильных приложениях.
- **SAML 2.0:** XML-стандарт, широко распространенный в корпоративных средах (ADFS, Okta).

## Практические сценарии

### Использование Basic Auth в командной строке

Для тестирования или автоматизации часто используется утилита **curl**:

```bash
# Автоматическая кодировка в Base64
curl -u "user:password" https://api.example.com/data

# Ручная передача заголовка
curl -H "Authorization: Basic dXNlcjpwYXNzd29yZA==" https://api.example.com/data
```

### Жизненный цикл JWT в веб-приложении

1. **Вход:** Пользователь вводит учетные данные в интерфейсе **SPA (Single Page Application — одностраничное приложение)**.
2. **Выдача:** Сервер проверяет данные и возвращает `access_token` и `refresh_token`.
3. **Запросы:** Фронтенд добавляет `Authorization: Bearer <access_token>` к каждому вызову API.
4. **Обновление:** При истечении срока действия токена приложение использует `refresh_token` для получения новой пары ключей без участия пользователя.

### Настройка безопасности куки на стороне сервера

Пример настройки заголовка в веб-сервере для защиты сессии:

```http
Set-Cookie: session_id=xyz789; HttpOnly; Secure; SameSite=Strict; Max-Age=3600
```

### Сравнение методов аутентификации

| Метод | Уровень безопасности | Состояние (Stateful/Stateless) | Основная сфера применения |
| :--- | :--- | :--- | :--- |
| **Basic** | Низкий (требует HTTPS) | Stateless | Простые API, внутренние системы |
| **Bearer (JWT)** | Высокий | Stateless | Микросервисы, мобильные приложения |
| **Куки/Сессии** | Высокий | Stateful | Традиционные веб-сайты |
| **Digest** | Средний | Stateless | Устаревшие системы |
| **OIDC / SAML** | Очень высокий | Зависит от реализации | Корпоративные среды, SSO |
