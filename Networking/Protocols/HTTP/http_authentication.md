# HTTP-аутентификация

## Definitions

**HTTP-аутентификация** — механизм протокола HTTP, позволяющий серверу запрашивать у клиента учетные данные (логин/пароль, токен, сертификат) для проверки личности пользователя перед предоставлением доступа к защищённым ресурсам.

**Основные заголовки:**

- **`WWW-Authenticate`** — заголовок ответа сервера, указывающий метод аутентификации и область (`realm`).
- **`Authorization`** — заголовок запроса клиента, содержащий учетные данные в формате, соответствующем выбранному методу.

## Basic Concepts

### Basic Authentication

**Принцип работы:**

1. Клиент отправляет запрос без учетных данных.
2. Сервер отвечает `401 Unauthorized` с заголовком `WWW-Authenticate: Basic realm="<область>"`, где `realm` — описание защищённой области, отображаемое пользователю.
3. Браузер показывает встроенную форму ввода.
4. Клиент повторно отправляет запрос с заголовком `Authorization: Basic <base64(логин:пароль)>`.

**Безопасность:** Учетные данные кодируются в Base64, но **не шифруются**, поэтому их легко перехватить и декодировать. Basic-аутентификация допустима **только** в сочетании с [HTTPS](./http_versions.md#https), обеспечивающим шифрование канала связи.

### Digest Authentication

**Принцип:** Сервер отправляет клиенту случайное значение (`nonce`). Клиент хеширует пароль с помощью MD5, объединяя его с `nonce`, HTTP-методом и URI запроса. Результат передаётся в заголовке `Authorization: Digest ...`. Это позволяет доказать знание пароля без его передачи по сети.

**Безопасность:** Устойчивее Basic к перехвату, но MD5 считается криптографически слабым. Редко используется на практике.

### Form-based Authentication

**Принцип:** Пользователь вводит учетные данные в HTML-форму, которая отправляется `POST`-запросом на сервер. Сервер проверяет данные и создаёт сессию, обычно возвращая клиенту cookie с идентификатором сессии.

**Особенности:** Не является частью стандарта HTTP-аутентификации, но широко применяется в веб-приложениях. Позволяет использовать кастомные формы входа вместо встроенного браузерного диалога.

### Bearer Token

**Принцип:** После успешной аутентификации (например, через [OAuth 2.0](../../../Security/Concepts/oauth2_overview.md)) сервер выдаёт временный токен (часто JWT). Клиент передаёт токен в каждом запросе: `Authorization: Bearer <токен>`.

**Особенности:**

- Токены имеют ограниченный срок действия и область действия (scope).
- Не требуют хранения сессии на сервере (stateless-подход, подробнее в [HTTP stateless](./http_basics.md)).
- Широко используются в REST API и микросервисной архитектуре.

### Cookies

**Принцип:** Сервер устанавливает cookie через заголовок `Set-Cookie`, который браузер автоматически отправляет в последующих запросах к этому домену.

**Атрибуты безопасности:**

- **`HttpOnly`** — запрещает доступ к cookie из JavaScript, защищая от XSS-атак.
- **`Secure`** — гарантирует передачу cookie только по HTTPS.
- **`SameSite`** — контролирует отправку cookie при кросс-доменных запросах, защищая от CSRF-атак.

### Single Sign-On (SSO)

**Принцип:** Пользователь проходит аутентификацию один раз и получает доступ ко множеству приложений без повторного ввода учетных данных. Реализуется через федеративную идентификацию (SAML, [OpenID Connect](../../../Security/Concepts/authentication_vs_authorization.md#Протоколы-и-стандарты)).

## Practical Scenarios

### Защита API с помощью Basic Auth

```bash
curl -u username:password https://api.example.com/resource
# Эквивалентно:
curl -H "Authorization: Basic $(echo -n 'username:password' | base64)" https://api.example.com/resource
```

**Применение:** Внутренние API, staging-окружения, быстрая защита административных панелей.

### JWT-аутентификация в SPA-приложении

1. Пользователь вводит логин/пароль в React-приложении.
2. Фронтенд отправляет `POST /auth/login` на сервер авторизации.
3. Сервер возвращает `{ access_token: "eyJ...", refresh_token: "..." }`.
4. Фронтенд сохраняет токены в `localStorage` или `HttpOnly` cookie.
5. Каждый запрос к API включает заголовок `Authorization: Bearer eyJ...`.
6. При истечении `access_token` фронтенд использует `refresh_token` для получения нового.

### Сессионная аутентификация через Cookies

1. Пользователь заполняет HTML-форму входа.
2. Сервер проверяет учетные данные и устанавливает `Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax`.
3. Браузер автоматически прикрепляет cookie ко всем запросам к домену.
4. Сервер идентифицирует пользователя по `session_id`, сверяя с хранилищем сессий (Redis, база данных).

## Additional Information

### Сравнительная таблица методов

| Метод | Безопасность | Stateless | Типичное применение |
| :--- | :--- | :--- | :--- |
| **Basic** | Низкая (только с HTTPS) | Да | Внутренние API, базовая защита |
| **Digest** | Средняя (MD5 устарел) | Да | Устаревшие системы |
| **Form-based + Session** | Высокая | Нет | Традиционные веб-приложения |
| **Bearer Token (JWT)** | Высокая | Да | SPA, мобильные приложения, микросервисы |
| **SSO (SAML/OIDC)** | Высокая | Зависит от реализации | Корпоративные среды, множественные приложения |

### Рекомендации по выбору

- **Внутренние инструменты:** Basic Auth + HTTPS (простота настройки).
- **Публичные API:** Bearer Token с OAuth 2.0 / OIDC (масштабируемость, делегирование доступа).
- **Традиционные веб-приложения:** Form-based + Secure HttpOnly Cookies (совместимость, UX).
- **Корпоративные порталы:** SSO через SAML или OpenID Connect (единый вход, централизованное управление).
