# ICMP Destination Unreachable (Type 3)

## Определения

**Destination Unreachable (Type 3)** — ICMP-сообщение, уведомляющее отправителя о невозможности доставки пакета до цели.

**Параметры:**
- **Type:** 3 (Destination Unreachable)
- **Code:** 0-15 (детализация причины недостижимости)

## Практические сценарии

### Net Unreachable (Type 3, Code 0)

**Назначение:** Маршрутизатор не знает маршрута до сети назначения.

**Механизм возникновения:**

1. **Исходные условия:**
   - Хост 1 пытается отправить TCP-пакет (например, SYN для установки соединения) на IP-адрес 8.8.4.4
   - Хост 1 находится в локальной сети 192.168.1.0/24
   - IP-адрес назначения 8.8.4.4 находится в другой сети
   - Хост 1 отправляет пакет на шлюз по умолчанию (маршрутизатор)

2. **Процесс:**
   - Маршрутизатор получает пакет от хоста 1
   - Проверяет таблицу маршрутизации для IP-адреса 8.8.4.4
   - В таблице маршрутизации отсутствует маршрут до сети, которой принадлежит 8.8.4.4
   - Маршрутизатор не знает, куда переслать пакет дальше

3. **Результат:**
   - Маршрутизатор отбрасывает пакет
   - Генерирует ICMP-сообщение **Destination Unreachable, Code 0 (Net Unreachable)**
   - Отправляет ICMP-сообщение обратно хосту 1

4. **Реакция TCP:**
   - TCP на хосте 1 получает ICMP-сообщение Net Unreachable
   - **Немедленно прекращает попытки установки соединения**
   - Без этого ICMP-сообщения TCP продолжил бы бесконечные попытки отправки SYN-пакетов

**Сценарий:**

| Компонент | Описание |
|-----------|----------|
| Хост 1 | 192.168.1.10/24, отправляет TCP SYN на 8.8.4.4:53 |
| Маршрутизатор | Шлюз по умолчанию для 192.168.1.0/24 |
| Таблица маршрутизации | Нет маршрута до 8.8.4.4 (Google DNS) |
| Результат | ICMP Type 3 Code 0 → TCP прерывает соединение |

**Диагностика:**
```bash
# tcpdump покажет ICMP-сообщение
tcpdump -i eth0 'icmp[0] = 3 and icmp[1] = 0'
```

### Host Unreachable (Type 3, Code 1)

**Назначение:** Маршрутизатор знает сеть назначения, но хост не отвечает (выключен, отключен от сети, блокирует трафик).

**Механизм возникновения:**

1. **Исходные условия:**
   - Хост 1 (192.168.1.10/24) пытается подключиться к хосту 172.16.12.22:5555
   - Маршрутизатор знает про сеть 172.16.12.0/24 (есть маршрут)
   - Хост 172.16.12.22 физически отсутствует или выключен

2. **Процесс:**
   - Хост 1 отправляет TCP-пакет на 172.16.12.22
   - Так как адрес в другой сети, пакет отправляется на маршрутизатор
   - Маршрутизатор определяет, что сеть 172.16.12.0/24 достижима
   - Для доставки пакета требуется MAC-адрес получателя
   - Маршрутизатор отправляет **ARP-запросы** для определения MAC-адреса 172.16.12.22
   - После **3 попыток** ARP-запросов ответа не получено

3. **Результат:**
   - Маршрутизатор делает вывод: хост 172.16.12.22 не отвечает
   - Генерирует ICMP-сообщение **Destination Unreachable, Code 1 (Host Unreachable)**
   - Отправляет ICMP хосту 1

**Особенность:** Если за время поиска MAC-адреса маршрутизатор получил несколько пакетов для одного хоста, он отправит **несколько ICMP-сообщений** (по одному на каждый полученный пакет).

**Сценарий:**

| Компонент | Описание |
|-----------|----------|
| Хост 1 | 192.168.1.10/24, отправляет TCP на 172.16.12.22:5555 |
| Маршрутизатор | Знает сеть 172.16.12.0/24, делает ARP-запрос |
| Хост 2 | 172.16.12.22 — выключен или отсутствует |
| ARP-запросы | 3 попытки без ответа |
| Результат | ICMP Type 3 Code 1 (может быть отправлено 3 раза) |

**Диагностика:**
```bash
# Наблюдение ARP-запросов и ICMP-ответов
tcpdump -i eth0 -nn 'arp or icmp'
# Видно: arp who-has 172.16.12.22 tell 192.168.1.1 (x3)
# Затем: ICMP 172.16.12.22 unreachable (core)
```

### Protocol Unreachable (Type 3, Code 2)

**Назначение:** Хост назначения не поддерживает протокол, указанный в IP-пакете.

**Механизм возникновения:**

1. Отправитель создаёт IP-пакет с полем **Protocol**, отличным от TCP (6), UDP (17), ICMP (1)
2. Пакет доставляется до хоста назначения
3. Хост получает пакет, но не поддерживает указанный протокол
4. Хост генерирует ICMP **Protocol Unreachable**

**Примеры:**
- IP-пакет с Protocol=47 (GRE) на хост без поддержки GRE
- IP-пакет с Protocol=50 (ESP/IPsec) на хост без IPsec
- IP-пакет с Protocol=132 (SCTP) на хост без поддержки SCTP

**На практике:** Встречается редко, так как большинство ОС поддерживают основные протоколы (TCP, UDP, ICMP).

### Port Unreachable (Type 3, Code 3)

**Назначение:** Хост получил UDP-датаграмму на порт, который никто не слушает.

**Ключевая особенность:** Это сообщение **генерируется только для UDP**. Для TCP несуществующий порт обрабатывается иначе (отправка RST).

**Механизм возникновения:**

1. **Исходные условия:**
   - UDP-клиент отправляет датаграмму на порт 5555 удалённого хоста
   - На хосте назначения нет приложения, слушающего порт 5555

2. **Процесс:**
   - Хост получает UDP-датаграмму
   - Проверяет, есть ли приложение, слушающее порт 5555
   - Приложение не найдено
   - Хост генерирует ICMP **Port Unreachable**

3. **Результат:**
   - Отправитель получает ICMP-сообщение
   - Понимает, что порт закрыт (аналог TCP RST для UDP)

**Почему это важно для UDP:**
- UDP не устанавливает соединение (нет handshake)
- Без ICMP Port Unreachable отправитель не узнает, доставлена ли датаграмма
- Это **некоторый аналог установки соединения в TCP**, но ICMP приходит только при ошибке

**Сценарий:**

| Компонент | Описание |
|-----------|----------|
| Хост 1 | Отправляет UDP-датаграмму на порт 5555 |
| Сервер 1 | 192.168.1.2 — порт 5555 закрыт → **ICMP Port Unreachable** |
| Сервер 2 | 192.168.1.3 — порт 5555 открыт → **Обработка без ответа** |

**Диагностика:**
```bash
# Отправка UDP на закрытый порт
echo "test" | nc -u 192.168.1.2 5555

# Наблюдение ICMP-ответа
tcpdump -i eth0 -nn 'icmp[0] = 3 and icmp[1] = 3'
# Видно: ICMP 192.168.1.2 udp port 5555 unreachable
```

**Использование в сканировании портов:**
- UDP-сканеры используют ICMP Port Unreachable для определения закрытых портов
- Отсутствие ответа может означать: порт открыт ИЛИ пакет потерян ИЛИ ICMP заблокирован файрволом

### Fragmentation Needed but DF set (Type 3, Code 4)

**Назначение:** Уведомление отправителя о том, что пакет не может быть доставлен без фрагментации, но в IP-заголовке установлен флаг **DF (Don't Fragment)**.

**Параметры:**
- **Type:** 3 (Destination Unreachable)
- **Code:** 4 (Fragmentation Needed)
- **ICMP-сообщение:** содержит MTU следующего звена в поле **Next-Hop MTU** (в старых реализациях — 0)

**Механизм возникновения:**

1. **Исходные условия:**
   - Хост 1 отправляет пакет размером 9000 байт (Jumbo Frame)
   - MTU между Хостом 1 и маршрутизатором: 9000 байт
   - MTU между маршрутизатором и Хостом 2: 1500 байт (стандартный Ethernet)
   - В IP-заголовке установлен флаг **DF (Don't Fragment)**

2. **Процесс:**
   - Маршрутизатор получает пакет размером 9000 байт
   - При попытке отправить пакет дальше, маршрутизатор обнаруживает, что MTU следующего звена (1500 байт) меньше размера пакета
   - Флаг DF запрещает фрагментацию
   - Маршрутизатор отбрасывает пакет и генерирует ICMP-сообщение **Destination Unreachable, Code 4**

3. **Результат:** Хост 1 получает ICMP-сообщение и понимает, что пакет был отброшен из-за несоответствия MTU.

**Сценарий с Jumbo Frames:**

| Сегмент сети | MTU | Описание |
|--------------|-----|----------|
| Хост 1 → Маршрутизатор | 9000 | Jumbo Frame (слоновый фрейм) |
| Маршрутизатор → Хост 2 | 1500 | Стандартный Ethernet |

**Диагностика на практике:**

**Windows:**
```cmd
ping -l 2000 -f 77.88.8.8
```
- `-l 2000` — устанавливает размер пакета 2000 байт
- `-f` — запрещает фрагментацию (устанавливает флаг DF)

**Linux:**
```bash
ping -s 2000 -M do 8.8.8.8
# или
ping -s 2000 -D 8.8.8.8
```
- `-s 2000` — размер пакета 2000 байт
- `-M do` — установить флаг DF (Don't Fragment)

**Результат при превышении MTU:**
```
Pinging 8.8.8.8 with 2000 bytes of data:
Packet needs to be fragmented but DF set.
Packet needs to be fragmented but DF set.
```

**Использование для Path MTU Discovery:**

Это ICMP-сообщение является ключевым элементом механизма **Path MTU Discovery (PMTUD)**:

1. Отправитель устанавливает флаг DF во всех пакетах
2. При получении ICMP "Fragmentation Needed" отправитель уменьшает размер пакета
3. Процесс повторяется до нахождения оптимального MTU пути

Подробнее см. [MTU и Path MTU Discovery](../../OSI_TCP_IP_Model/Network_layer/mtu_and_vpn.md#path-mtu-discovery-pmtud).

**Пример ping для определения Path MTU:**
```bash
# Постепенное увеличение размера пакета для поиска максимального MTU
ping -s 1472 -M do example.com  # 1500 байт (1472 + 28 заголовков)
ping -s 1473 -M do example.com  # Ошибка: требуется фрагментация
```

**Проблемы безопасности:**

- **PMTUD Black Hole:** Если файрвол блокирует ICMP Type 3 Code 4, PMTUD не работает
- **Решение:** Разрешить ICMP Type 3 Code 4 на файрволе для входящих соединений

## Диагностика Destination Unreachable

**Проверка по кодам:**

```bash
# Net Unreachable (Code 0) — нет маршрута
tcpdump -i eth0 'icmp[0] = 3 and icmp[1] = 0'

# Host Unreachable (Code 1) — хост не отвечает
tcpdump -i eth0 'icmp[0] = 3 and icmp[1] = 1'

# Port Unreachable (Code 3) — UDP порт закрыт
tcpdump -i eth0 'icmp[0] = 3 and icmp[1] = 3'

# Fragmentation Needed (Code 4) — требуется фрагментация
tcpdump -i eth0 'icmp[0] = 3 and icmp[1] = 4'
```

**Интерпретация:**

| Код | Возможная причина | Решение |
|-----|-------------------|---------|
| 0 (Net Unreachable) | Нет маршрута в таблице маршрутизации | Проверить маршруты на шлюзе |
| 1 (Host Unreachable) | Хост выключен, ARP не отвечает | Проверить доступность хоста |
| 3 (Port Unreachable) | UDP порт закрыт | Проверить службу на хосте |
| 4 (Fragmentation Needed) | Пакет > MTU, флаг DF | Включить PMTUD или уменьшить MTU |
