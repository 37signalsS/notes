# ICMP Time Exceeded (Type 11)

## Определения

**ICMP Time Exceeded (Type 11)** — уведомление об истечении времени жизни пакета или времени сборки фрагментов.

**Параметры:**
- **Type:** 11
- **Code:** 0 или 1

| Code | Название | Описание |
|------|----------|----------|
| **0** | Time To Live exceeded in transit | Время пересылки истекло (TTL = 0) |
| **1** | Fragment reassembly time exceeded | Время сборки фрагментов истекло |

**Важно:** ICMP Time Exceeded (Code 0) — классический пример **постоянной ошибки**. Если пакет попадает в циклическую маршрутизацию или имеет слишком низкое начальное TTL, каждая повторная отправка будет приводить к той же ошибке. Проблема не решится сама собой — требуется изменение конфигурации маршрутизации или увеличение TTL.

## Time To Live exceeded in transit (Type 11, Code 0)

### Механизм работы TTL

В IP-заголовке есть поле **TTL (Time To Live)** размером 1 байт (8 бит). Каждый раз, когда IP-пакет проходит через маршрутизатор, значение TTL уменьшается на 1. Когда TTL становится равным 0, пакет отбрасывается.

**Назначение TTL:**
- Защита от вечной пересылки пакетов по сети (например, при циклической маршрутизации)
- Ограничение времени жизни пакета в сети

### Процесс генерации ICMP Time Exceeded

1. Отправитель создаёт пакет с TTL=N (например, TTL=5)
2. Каждый маршрутизатор на пути уменьшает TTL на 1
3. Когда маршрутизатор получает пакет с TTL=1:
   - Уменьшает TTL до 0
   - Отбрасывает пакет
   - Отправляет отправителю ICMP **Time Exceeded** (Type 11, Code 0)

**Примечание:** Это сообщение иногда называют «похоронка».

### Сценарий с циклической маршрутизацией

| Компонент | Описание |
|-----------|----------|
| Хост 1 | Отправитель (TTL=5) |
| Маршрутизатор 1 | Уменьшает TTL до 4 |
| Маршрутизатор 2 | Уменьшает TTL до 3 |
| Маршрутизатор 3 | Уменьшает TTL до 2 |
| Маршрутизатор 1 (повторно) | Уменьшает TTL до 1 |
| Маршрутизатор 2 (повторно) | Уменьшает TTL до 0 → **ICMP Time Exceeded** |

## Практический пример: защита от зацикливания пакета

**Цель:** Продемонстрировать работу механизма TTL в сети с циклической маршрутизацией.

**Топология сети:**

```
                    ┌─────────────────┐
                    │ Маршрутизатор 1 │
                    │  10.0.0.1/24    │
                    └────────┬────────┘
                             │ 169.254.1.0/24
                    ┌────────┴────────┐
                    │ Маршрутизатор 3 │
                    │ 192.168.1.1/24  │
                    └────────┬────────┘
                             │ 192.168.1.0/24
                    ┌────────┴────────┐
                    │ Маршрутизатор 2 │
                    │ 172.16.12.1/24  │
                    └────────┬────────┘
                             │ 172.16.12.0/24
                    ┌────────┴────────┐
                    │ Маршрутизатор 1 │
                    │  (возврат)      │
                    └─────────────────┘
```

**Конфигурация маршрутизации:**

| Компонент | Сеть | Шлюз по умолчанию |
|-----------|------|-------------------|
| Хост 1 | 10.0.0.0/24 | Маршрутизатор 1 (10.0.0.1) |
| Маршрутизатор 1 | 172.16.12.0/24 | Маршрутизатор 2 |
| Маршрутизатор 2 | 192.168.1.0/24 | Маршрутизатор 3 |
| Маршрутизатор 3 | 169.254.1.0/24 | Маршрутизатор 1 |

**Сценарий:**

1. На хосте 1 выполняется команда:
   ```bash
   # Linux/macOS
   ping -c 1 -t 5 12.34.45.67

   # Windows
   ping -n 1 -i 5 12.34.45.67
   ```
   - Флаг `-t 5` (Linux) или `-i 5` (Windows) устанавливает TTL=5
   - IP `12.34.45.67` выбран как несуществующий, чтобы все маршрутизаторы отправляли пакет на шлюз по умолчанию

2. Пакет начинает циркулировать по кольцу:
   - Хост 1 → Маршрутизатор 1 (TTL=4)
   - Маршрутизатор 1 → Маршрутизатор 2 (TTL=3)
   - Маршрутизатор 2 → Маршрутизатор 3 (TTL=2)
   - Маршрутизатор 3 → Маршрутизатор 1 (TTL=1)
   - Маршрутизатор 1 → Маршрутизатор 2 (TTL=0)

3. Когда TTL становится 0 на Маршрутизаторе 2:
   - Пакет отбрасывается
   - Генерируется ICMP **Time Exceeded** (Type 11, Code 0)
   - Сообщение отправляется обратно хосту 1

**Результат:**

```bash
# Вывод ping (Linux)
ping: Warning: source address might be selected on device other than: eth0
PING 12.34.45.67 (12.34.45.67) 56(84) bytes of data.
From 172.16.12.2 icmp_seq=1 Time to live exceeded

--- 12.34.45.67 ping statistics ---
1 packets transmitted, 0 received, +1 errors, 100% packet loss
```

**Вывод:** Поле TTL в IP-протоколе защищает сеть от вечно циркулирующих пакетов. Без этого механизма пакет продолжал бы бесконечно пересылаться по кольцу, потребляя ресурсы сети.

## Практическое применение: traceroute

**Использование в traceroute:**

Утилита `traceroute` использует этот механизм для определения пути пакета:

```bash
# Linux
traceroute -n 8.8.8.8

# Windows
tracert -d 8.8.8.8
```

**Принцип работы traceroute:**

1. Отправляет 3 пакета с TTL=1 → получает Time Exceeded от 1-го маршрутизатора
2. Отправляет 3 пакета с TTL=2 → получает Time Exceeded от 2-го маршрутизатора
3. Постепенно увеличивает TTL, пока не достигнет цели
4. Цель отвечает Echo Reply (для ICMP) или Port Unreachable (для UDP)

**Пример вывода traceroute:**
```bash
$ traceroute -n 8.8.8.8
 1  192.168.1.1  2.345 ms  2.123 ms  2.456 ms
 2  10.0.0.1     5.678 ms  5.432 ms  5.789 ms
 3  203.0.113.1  8.901 ms  8.765 ms  9.012 ms
 4  8.8.8.8      12.34 ms   11.98 ms   12.01 ms
```

**Определение количества хопов до хоста:**

Играясь с опцией TTL, можно выяснить, сколько маршрутизаторов между вами и конечным хостом:

```bash
# Постепенное увеличение TTL для определения пути
ping -c 1 -t 1 example.com  # Первый хоп
ping -c 1 -t 2 example.com  # Второй хоп
ping -c 1 -t 3 example.com  # Третий хоп
# ...
ping -c 1 -t 15 example.com # Достижение цели

# Или использовать специализированную утилиту
traceroute example.com
```

## Fragment Reassembly Time Exceeded (Type 11, Code 1)

### Механизм возникновения

1. Отправитель создаёт пакет, превышающий MTU пути
2. Пакет фрагментируется на несколько фрагментов
3. Фрагменты передаются независимо и могут идти разными маршрутами
4. Если один или несколько фрагментов теряются:
   - Получатель ждёт все фрагменты в течение таймаута (15-60 секунд)
   - По истечении времени получатель отправляет **Fragment Reassembly Time Exceeded**

**Причины потери фрагментов:**
- Перегрузка сети
- Ошибки маршрутизации
- Проблемы с оборудованием
- Фрагментация на разных участках пути с разным MTU

**На практике:** Встречается редко в современных сетях благодаря:
- Механизмам Path MTU Discovery (PMTUD)
- Корректной настройке сетевого оборудования
- Использованию TCP MSS Clamping
