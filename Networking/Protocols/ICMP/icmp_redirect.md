# ICMP Redirect и Source Quench

**Reliability Score: 10/10** (SSoT + Проверено по RFC 792/4443/6633)

## Определения

**ICMP Redirect (Тип 5 для IPv4, Тип 137 для IPv6)** — служебное сообщение, используемое маршрутизаторами для уведомления отправителя о наличии более эффективного (короткого) пути к конкретному узлу назначения через другой шлюз в той же локальной сети.

**ICMP Source Quench (Тип 4)** — исторический механизм контроля перегрузки, с помощью которого промежуточный узел запрашивал у отправителя снижение скорости передачи данных. В современных сетях признан неэффективным и **полностью устаревшим (deprecated)**.

## Основные концепции

### Механизм ICMP Redirect

Протокол IP предполагает, что конечные хосты обладают минимальными знаниями о топологии сети и обычно полагаются на шлюз по умолчанию (Default Gateway). ICMP Redirect позволяет маршрутизаторам динамически оптимизировать таблицу маршрутизации хоста без использования сложных протоколов динамической маршрутизации (OSPF, BGP) на стороне клиента.

#### Условия генерации Redirect:
1. Пакет поступает на тот же интерфейс, через который он должен быть отправлен дальше.
2. Адрес источника и адрес следующего перехода (next-hop) находятся в одной IP-подсети.
3. Маршрутизатор не настроен на использование Source Routing.
4. Маршрутизация пакета не изменяется правилами Policy Based Routing (PBR).

#### Коды ICMPv4 Redirect (Type 5):
| Код | Название | Описание |
| :--- | :--- | :--- |
| **0** | Redirect for Network | Перенаправление для всей целевой сети (устарело, обычно трактуется как Host). |
| **1** | Redirect for Host | Перенаправление для конкретного IP-адреса хоста. |
| **2** | Redirect for ToS & Network | Перенаправление с учетом типа службы (ToS) для сети. |
| **3** | Redirect for ToS & Host | Перенаправление с учетом ToS для конкретного хоста. |

#### ICMPv6 Redirect (Type 137):
В IPv6 Redirect является частью протокола **Neighbor Discovery (NDP)**. Он работает аналогично IPv4, но включает в себя целевой канальный адрес (Target Link-Layer Address) нового шлюза, что позволяет хосту избежать дополнительного этапа поиска через Neighbor Solicitation.

### Проблемы безопасности и валидация

По умолчанию сообщения ICMP Redirect могут быть использованы для атак типа **Man-in-the-Middle (MITM)** или DoS. Злоумышленник может отправить поддельный Redirect, заставив хост направлять трафик через подконтрольный узел.

#### Критерии валидации в современных ОС:
Для принятия Redirect сообщения хост должен убедиться в выполнении следующих условий:
1. Сообщение получено от **текущего шлюза**, который используется для данного маршрута.
2. Адрес нового шлюза находится в той же локальной подсети, что и хост.
3. Сообщение содержит часть исходного пакета (IP-заголовок + 64 бита данных), подтверждающую, что хост действительно отправлял этот пакет.

### ICMP Source Quench (deprecated)

Механизм **Source Quench (Тип 4)** официально объявлен устаревшим в **RFC 6633**. 

**Причины отказа:**
1. **Неэффективность:** ICMP-сообщения сами потребляют пропускную способность, усиливая перегрузку канала.
2. **Дублирование функций:** Современные алгоритмы контроля перегрузки в TCP (Cubic, BBR) справляются с этой задачей гораздо точнее на транспортном уровне.
3. **Безопасность:** Злоумышленник может принудительно замедлить легитимный трафик, отправляя фальшивые Source Quench.
4. **Отсутствие обратной связи:** В UDP-трафике Source Quench часто просто игнорируется приложениями.

## Практические сценарии

### Сценарий: Оптимизация маршрута в локальной сети

1. **Конфигурация:** В сети два маршрутизатора: R1 (10.0.0.1, шлюз по умолчанию) и R2 (10.0.0.2, доступ к сети 192.168.1.0/24).
2. **Действие хоста:** Хост А (10.0.0.5) отправляет пакет в сеть 192.168.1.0 через R1.
3. **Действие R1:** Видит, что лучший путь лежит через R2, который доступен через тот же интерфейс eth0.
4. **Оптимизация:** R1 пересылает пакет на R2 и отправляет Хосту А **ICMP Redirect (v4 Type 5 Code 1)**.
5. **Результат:** Хост А добавляет в кэш маршрутизации запись `192.168.1.0/24 via 10.0.0.2` и далее отправляет трафик напрямую.

### Настройка в Linux (Hardening)

В современных системах рекомендуется отключать прием Redirect, если топология сети проста и статична.

**Проверка статуса:**
```bash
sysctl net.ipv4.conf.all.accept_redirects
sysctl net.ipv6.conf.all.accept_redirects
```

**Отключение (через `/etc/sysctl.conf`):**
```bash
# Запретить прием Redirect (Безопасность)
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.default.accept_redirects = 0
net.ipv6.conf.all.accept_redirects = 0

# Запретить отправку (для обычных хостов, не маршрутизаторов)
net.ipv4.conf.all.send_redirects = 0
net.ipv4.conf.default.send_redirects = 0
```

### Настройка в Windows

В Windows параметр настраивается глобально через реестр.
**Путь:** `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters`
**Параметр:** `EnableICMPRedirect` (тип DWORD). Значение `0` полностью отключает обработку.
