# ICMP Redirect и Source Quench

## Определения

**ICMP Redirect (Type 5)** — служебное сообщение, используемое маршрутизаторами для уведомления хоста о наличии более оптимального шлюза для конкретного маршрута.

**ICMP Source Quench (Type 4)** — устаревший механизм контроля перегрузки, с помощью которого узел запрашивал у отправителя снижение скорости передачи пакетов.

## Основные концепции

### ICMP Redirect

Протокол IP предполагает, что хосты имеют минимальную информацию о маршрутизации (обычно только шлюз по умолчанию). ICMP Redirect позволяет маршрутизаторам динамически оптимизировать пути трафика без настройки сложных протоколов маршрутизации на конечных узлах.

**Коды ICMP Redirect (Type 5):**

| Code | Название | Описание |
|------|----------|----------|
| **0** | Redirect for Network | Перенаправление для всей IP-сети |
| **1** | Redirect for Host | Перенаправление для конкретного хоста |
| **2** | Redirect for ToS & Network | Перенаправление для типа службы и сети |
| **3** | Redirect for ToS & Host | Перенаправление для типа службы и хоста |

### Безопасность ICMP Redirect

По умолчанию многие операционные системы доверяют сообщениям ICMP Redirect и обновляют свою таблицу маршрутизации. Это создает серьезные риски:
- **MITM (Man-in-the-Middle):** злоумышленник может отправить ложный Redirect, чтобы направить трафик через свой узел для перехвата.
- **DDoS:** перенаправление трафика на несуществующий узел или в "петлю" для отказа в обслуживании.

### ICMP Source Quench (deprecated)

Механизм **Source Quench (Type 4)** использовался, когда буферы маршрутизатора или хоста переполнялись. В современных сетях этот протокол признан неэффективным и **устаревшим** (RFC 6633) по следующим причинам:
- Контроль перегрузки теперь выполняется на транспортном уровне (TCP Congestion Control).
- ICMP-сообщения сами по себе потребляют пропускную способность, усугубляя перегрузку.
- Легко используется для DoS-атак на легитимные соединения.

## Практические сценарии

### Сценарий: Оптимизация маршрута

1. **Исходная ситуация:** Хост А (10.0.0.5) хочет отправить пакет Хосту Б (192.168.1.10). Шлюз по умолчанию для Хоста А — Маршрутизатор R1 (10.0.0.1).
2. **Проблема:** Пакет приходит на R1, но R1 видит, что Хост Б доступен через Маршрутизатор R2 (10.0.0.2), который находится в той же локальной сети, что и Хост А.
3. **Действие:** R1 пересылает пакет на R2 и одновременно отправляет Хосту А сообщение **ICMP Redirect (Type 5, Code 1)**, указывая R2 как лучший шлюз для Хоста Б.
4. **Результат:** Хост А добавляет временный маршрут в свою таблицу и последующие пакеты отправляет напрямую на R2, минуя лишний "прыжок" через R1.

### Настройка и защита в Linux

Для обеспечения безопасности рекомендуется отключать обработку ICMP Redirect, если в сети нет явной необходимости в такой оптимизации.

**Проверка текущих настроек:**
```bash
sysctl net.ipv4.conf.all.accept_redirects
```

**Отключение через sysctl:**
```bash
# Отключить прием сообщений
sysctl -w net.ipv4.conf.all.accept_redirects=0
sysctl -w net.ipv4.conf.default.accept_redirects=0

# Отключить отправку (для маршрутизаторов)
sysctl -w net.ipv4.conf.all.send_redirects=0
```

**Блокировка на уровне файрвола (iptables):**
```bash
iptables -A INPUT -p icmp --icmp-type redirect -j DROP
```

### Настройка в Windows

В Windows параметр настраивается через реестр.
**Путь:** `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters`
**Параметр:** `EnableICMPRedirect` (тип DWORD). Установка в `0` отключает обработку.
