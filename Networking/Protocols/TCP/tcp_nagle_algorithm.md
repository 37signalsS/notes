# Алгоритм Нагла (Nagle Algorithm)

## Определения

**Алгоритм Нагла (Nagle Algorithm)** — механизм в протоколе TCP, предназначенный для повышения эффективности использования пропускной способности сети путем предотвращения «проблемы маленьких пакетов» (Small Packet Problem). Он объединяет множество мелких вызовов `write` от приложения в один сегмент перед отправкой.

**Цель:** Снижение накладных расходов (заголовков L2–L4) при передаче интерактивного или мелко-блочного трафика. Без этого алгоритма каждый байт данных мог бы генерировать пакет размером в 41 байт (20 IP + 20 TCP + 1 Data), что на 10 Гбит/с канале привело бы к перегрузке CPU обработкой заголовков и снижению полезной пропускной способности.

**Стандарты:** Описан в **RFC 896** (1984) и является обязательным к реализации согласно **RFC 1122**.

---

## Основные концепции

### Формальный алгоритм

Нagle работает по принципу **«одного пакета в полете»**. Отправитель может немедленно отправить данные, только если выполняется **хотя бы одно** из условий:

```text
Если (данные >= MSS) ИЛИ (нет неподтвержденных данных) ИЛИ (TCP_NODELAY включен):
    → Отправить немедленно
Иначе:
    → Буферизовать данные до получения ACK или накопления MSS
```

**Детализация условий:**

| # | Условие | Описание |
| :--- | :--- | :--- |
| 1 | `bytes >= MSS` | В буфере накопилось достаточно данных для формирования сегмента максимального размера (**Maximum Segment Size**). Отправка происходит без ожидания. |
| 2 | `unack_data == 0` | Все ранее отправленные сегменты уже подтверждены получателем (ACK получен). В «полете» нет неподтвержденных данных. |
| 3 | `TCP_NODELAY` | Алгоритм явно отключен для данного сокета. Данные отправляются немедленно независимо от размера. |
| 4 | `FIN sent` | Соединение в процессе закрытия (отправлен FIN). Ограничение снимается для корректного завершения передачи остатков. |
| 5 | `urgent mode` | Установлен флаг URG в заголовке. Срочные данные отправляются немедленно. |

**RFC 896 — первоначальная формулировка:**

> «In an internet environment with mixed packet sizes, the simple strategy of holding back small segments until a full one can be sent has proven its worth. The algorithm is: if there is any unacknowledged data, do not transmit new small segments. Instead, accumulate data in the send buffer until either a full segment can be formed or an ACK arrives.»

### Проблема маленьких пакетов (Small Packet Problem)

Без алгоритма Нагла каждый вызов `write()` немедленно генерирует TCP-сегмент:

```text
Приложение: write("A")    → сегмент 41 байт (20 IP + 20 TCP + 1)
Приложение: write("B")    → сегмент 41 байт
Приложение: write("C")    → сегмент 41 байт
Приложение: write("Hello")→ сегмент 46 байт

Итого: 4 пакета, 169 байт из которых 160 — заголовки
```

С алгоритмом Нагла (без ACK на первые данные):

```text
Приложение: write("A")    → буферизовано (0 в полете, нет ACK — отправляем)
Приложение: write("B")    → буферизовано (ожидание ACK)
Приложение: write("C")    → буферизовано (ожидание ACK)
Приложение: write("Hello")→ буферизовано

// Получен ACK на "A":
→ "B" отправляется (один сегмент с "BC")
→ "Hello" буферизовано

// Получен ACK на "BC":
→ "Hello" отправляется

Итого: 3 пакета, 123 байта
```

**Ключевой эффект:** На медленных каналах (modem, satellite) экономия может быть кратной. На быстрых LAN-каналах эффект минимален, но проблема задержек (см. ниже) сохраняется.

### Конфликт с Delayed ACK (TCP Deadlock)

Наиболее критическая проблема алгоритма — взаимодействие с механизмом **Delayed ACK** (RFC 1122, §4.2.3.2) на стороне получателя. Delayed ACK задерживает отправку подтверждения на **40–200 мс** (по умолчанию в Linux: 40 мс minimum, до 200 мс), надеясь «приклеить» его к ответным данным (**Piggybacking**).

**Сценарий «тупика» (Deadlock):**

```text
Клиент (Nagle)                           Сервер (Delayed ACK)
    |                                        |
    |  1. "GET /api" (9 байт) ─────────────> |  Принято, но ACK отложен
    |     [Nagle: ждет ACK на 9 байт]       |  [Delayed ACK: ждет данные для piggyback]
    |                                        |
    |  ... 40–200 мс ...                     |
    |                                        |
    |  <─────── ACK (только ACK) ────────── |  Сработал таймер Delayed ACK
    |                                        |
    |  2. "GET /api" (9 байт) ─────────────> |  Ответ
    |     [Отправка: все неподтв. доставлены]|
```

**Результат:** Каждый request-response проходит с задержкой ровно на время таймера Delayed ACK. При 40 мс minimum это 80 мс RTT overhead (2 × 40 мс), при 200 мс — 400 мс.

**Почему возникает deadlock:**
1. Отправитель не может отправить вторую порцию данных (Nagle: есть неподтвержденные данные).
2. Получатель не может отправить ACK немедленно (Delayed ACK: надеется объединить с ответом).
3. Если ответных данных нет (или ответ отправляется только после полного запроса) — возникает взаимное ожидание.

### Взаимодействие с флагом PSH (Push)

Флаг **PSH** (Push Function) в заголовке TCP указывает получателю: «немедленно доставь эти данные приложению, не буферизуй». Он тесно связан с Нagle:

- **При Nagle включен:** PSH не снимает ограничение на отправку. PSH влияет только на поведение получателя (немедленная доставка приложению), но отправитель все равно буферизует мелкие данные до ACK или MSS.
- **При TCP_NODELAY:** PSH отправляется с каждым сегментом автоматически, обеспечивая минимальную задержку.
- **В HTTP/1.1:** Сервер устанавливает PSH на последний сегмент ответа (заголовки + тело), чтобы клиент немедленно обработал ответ.
- **В HTTP/2:** PSH используется для каждого фрейма (DATA, HEADERS), так как протокол требует немедленной обработки.

### Nagle vs TCP_CORK vs TCP_NODELAY

В Linux существует три взаимоисключающих режима управления буферизацией отправки:

| Параметр | Поведение | Использование |
| :--- | :--- | :--- |
| **По умолчанию (Nagle)** | Мелкие данные буферизуются до ACK или MSS. Отправка возможна при пустом «полете». | Общее назначение, баланс между эффективностью и задержкой. |
| **TCP_NODELAY** | Данные отправляются немедленно независимо от размера. Никакой буферизации. | Low-latency: SSH, игры, RPC (gRPC), WebSocket, online trading. |
| **TCP_CORK** | Полностью запрещает отправку любых сегментов меньше MSS. Отправка только при `TCP_UNCORK` или заполнении MSS. | Сборка сложных ответов из нескольких `write()`/`sendfile()`: HTTP-ответ с заголовками и телом. |

**TCP_CORK — детали:**
```text
setsockopt(fd, IPPROTO_TCP, TCP_CORK, &one, sizeof(one));  // "вставляем пробку"
write(fd, header, header_len);      // буферизовано
write(fd, body, body_len);          // буферизовано
setsockopt(fd, IPPROTO_TCP, TCP_CORK, &zero, sizeof(zero)); // "вытаскиваем пробку"
// → Один сегмент с header + body отправляется немедленно
```

**TCP_CORK + TCP_NODELAY:** Невозможно установить одновременно — ядро возвращает `EINVAL`. При установке одного флаг автоматически сбрасывается другой.

**Сравнение с Sendfile:**
- `sendfile()` + `TCP_CORK` = оптимально для статических файлов (zero-copy + агрегация).
- `write()` + `TCP_NODELAY` = оптимально для интерактивных приложений.

### Взаимодействие с другими socket options

| Опция | Взаимодействие с Nagle |
| :--- | :--- |
| **SO_SNDBUF** | Размер буфера отправки. Если `SO_SNDBUF < MSS`, Nagle не может накопить полный сегмент — отправка будет откладываться до ACK. |
| **SO_RCVBUF** | Не влияет напрямую на Nagle, но опосредованно: маленький rwnd получателя замедляет ACK, увеличивая задержку Nagle. |
| **TCP_DEFER_ACCEPT** | Соединение остается в `SYN_RECV` до поступления первых данных. Не влияет на Nagle напрямую, но снижает нагрузку на сервер при пустых соединениях. |
| **TCP_QUICKACK** | Отключает Delayed ACK для конкретного соединения. Решает конфликт Nagle + DelayED ACK (см. раздел «Решения конфликта»). |
| **TCP_LINGER** | Управляет поведением `close()`. Не влияет на Nagle, но может вызвать блокировку `close()` при большом буфере. |
| **SO_BUSY_POLL** | Активный опрос NIC. Снижает задержку получения ACK, что ускоряет снятие ограничения Nagle. |

### Non-blocking sockets и Nagle

При работе с **non-blocking socket** (`O_NONBLOCK` / `fcntl`) Nagle может вызвать неожиданное поведение:

```text
// Non-blocking write с Nagle:
result = write(fd, small_data, 5);
// result = 5 (данные записаны в буфер ядра)
// НО: они НЕ отправлены в сеть — Nagle буферизует
// Реальная отправка произойдет после ACK на предыдущие данные
```

**Проблема:** Приложение считает, что данные «отправлены» (write вернул 5), но в сети их нет. Это затрудняет диагностику задержек.

**Решение:** Для non-blocking sockets всегда используйте `TCP_NODELAY`, если критична задержка.

### Исторический контекст (RFC 896)

Алгоритм был предложен John Nagle в 1984 году для решения проблемы «конгестии» в раннем Internet. Тогда:
- Скорости каналов: 56 Кбит/с – 1.5 Мбит/с
- Проблема: telnet-сессии генерировали пакеты по 1 байту данных + 40 байт заголовков (97.5% overhead)
- Решение: буферизация мелких данных до ACK или MSS

В 2026 году relevance алгоритма изменилась:
- **LAN (1–100 Гбит/с):** Проблема маленьких пакетов неактуальна (overhead <0.03%), но проблема задержек с Delayed ACK сохраняется.
- **WAN (1–100 Мбит/с):** Буферизация по-прежнему полезна для экономии полосы.
- **5G/satellite:** С высоким RTT (20–600 мс) проблема задержек Nagle + Delayed ACK катастрофична.

## Решения конфликта Nagle + Delayed ACK

### Решение 1: TCP_NODELAY на отправителе (основное)

Отключение алгоритма Нагла для конкретного сокета:

```c
// C / POSIX
int flag = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));
```

```python
# Python
import socket
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
```

```go
// Go
conn, _ := net.Dial("tcp", "host:port")
tcpConn := conn.(*net.TCPConn)
tcpConn.SetNoDelay(true) // по умолчанию true в Go
```

```java
// Java
Socket socket = new Socket();
socket.setTcpNoDelay(true);
```

**Эффект:** Данные отправляются немедленно. Проблема задержек решается полностью. Однако увеличивается количество пакетов (Potential for overhead на медленных каналах).

### Решение 2: TCP_QUICKACK на получателе

Отключение Delayed ACK для конкретного соединения:

```c
int flag = 1;
setsockopt(fd, IPPROTO_TCP, TCP_QUICKACK, &flag, sizeof(flag));
```

**Важно:** `TCP_QUICKACK` — **одноразовый** флаг в Linux. После отправки ACK он сбрасывается. Необходимо устанавливать его после каждого `recv()` или в цикле.

**Применение:** Когда невозможно изменить код отправителя (например, клиент — стороннее приложение).

### Решение 3: Прикладное объединение данных

Агрегация мелких данных на уровне приложения перед вызовом `write()`:

```python
# Вместо двух write:
write(header)
write(body)

# Одна операция:
write(header + body)
```

**Применение:** HTTP-серверы (nginx, Apache) агрегируют заголовки и тело ответа в один вызов `writev()` / `sendfile()`.

### Решение 4: HTTP/2 и HTTP/3 (протокольное)

Современные протоколы отключают Nagle по умолчанию:
- **HTTP/2:** Управление мультиплексированием встроено в протокол. Фреймы HEADERS и DATA отправляются немедленно.
- **HTTP/3 (QUIC):** Работает поверх UDP, алгоритм Нагла не применяется.

#### Проверка через ss (Socket Statistics)

```bash
# Просмотр состояния Nagle для конкретного соединения
ss -tin dst 8.8.8.8

# → rcvmss:1460 advmss:1460 cwnd:10 ssthresh:7
# → send 7.6Mbps retrans:0/0 nagle
```

**Ключевые индикаторы:**

| Флаг в выводе | Значение |
| :--- | :--- |
| `nagle` | Алгоритм Нагла **активен** (стандартное поведение) |
| `nodelay` | Алгоритм Нагла **отключен** (`TCP_NODELAY`) |
| `ato:40` | Acknowledgment Timeout — текущая задержка Delayed ACK (мс) |

**Быстрый поиск всех соединений с Nagle:**
```bash
# Соединения с активным Nagle

```

### Реальные сценарии конфликта

#### Сценарий 1: SSH-лаags при вводе текста

**Симптом:** Задержка ~40 мс при нажатии клавиш в SSH.

**Причина:** SSH-клиент отправляет каждый нажатие клавиши (1 байт), Nagle буферизует, сервер ждет Delayed ACK.

**Решение:** SSH по умолчанию отключает Nagle (`TCP_NODELAY`). Проверка:
```bash
ss -tin dst $(ssh -G remote.host | grep destination | awk '{print $2}')
# → должен показывать nodelay
```

#### Сценарий 2: HTTP/1.0 с keep-alive

**Симптом:** Задержка ~200 мс между запросами в keep-alive соединении.

**Причина:** Клиент отправляет headers и body отдельными write(), Nagle буферизует headers до ACK.

**Решение:**
```python
# Неправильно:
sock.send(headers)     # Nagle буферизует
sock.send(body)        # Ожидание ACK

# Правильно:
sock.send(headers + body)  # Один write
# Или:
sock.sendmsg([headers, body])  # scatter/gather I/O
```

#### Сценарий 3: gRPC с высокой задержкой

**Симптом:** p99 латентности gRPC-вызовов 50+ мс вместо ожидаемых 5–10 мс.

**Причина:** gRPC использует HTTP/2, но при fallback на HTTP/1.1 или при использовании unbuffered channels Nagle может активироваться.

**Решение:**
```go
// Go: отключение Nagle для gRPC-клиента
conn, _ := net.Dial("tcp", "server:50051")
tcpConn := conn.(*net.TCPConn)
tcpConn.SetNoDelay(true)

// Или через gRPC-опции:
grpc.WithInitialWindowSize(1024*1024),
grpc.WithInitialConnWindowSize(1024*1024),
```

#### Сценарий 4: WebSocket в реальном времени

**Симптом:** Задержка ~40 мс при доставке сообщений в чате.

**Причина:** WebSocket-фреймы маленькие, Nagle буферизует до ACK.

**Решение (C#/.NET):**
```csharp
var socket = new Socket(AddressFamily.InterNetwork, SocketType.Stream, ProtocolType.Tcp);
socket.SetSocketOption(SocketOptionLevel.Tcp, SocketOptionName.NoDelay, true);
```

### Связь с L4S, BBR и ECN (2024–2026)

Алгоритм Нагла работает **независимо** от алгоритмов контроля перегрузки (CC), но их взаимодействие может быть непредсказуемым:

| Взаимодействие | Описание |
| :--- | :--- |
| **Nagle + BBR** | BBR моделирует RTT и пропускную способность. Nagle добавляет латентность, которую BBR не учитывает (ожидание ACK не связано с перегрузкой). Результат: BBR может передавать данные с задержкой, которая не отражает реальное состояние сети. |
| **Nagle + ECN** | ECN снижает потери (маркировка вместо отбрасывания), но Nagle не зависит от потерь — он зависит от ACK. ECN не решает проблему задержек Nagle. |
| **Nagle + L4S** | L4S (RFC 9330) требует сверхнизких задержек (<10 мс). Nagle с Delayed ACK добавляет 40–200 мс — это **несовместимо** с требованиями L4S. В L4S-контексте Nagle должен быть отключен. |
| **TCP_CORK + BBR** | TCP_CORK может вызвать всплески (burst), которые BBR интерпретирует как перегрузку. Не рекомендуется использовать TCP_CORK с BBR без осторожности. |

## Рекомендации по настройке

### Когда отключать (TCP_NODELAY)

| Сценарий | Причина | Приоритет |
| :--- | :--- | :--- |
| **SSH / Telnet** | Интерактивный ввод, критична задержка отклика | Обязательно |
| **Онлайн-игры** | Каждый пакет — действие игрока, задержка = лаг | Обязательно |
| **gRPC / RPC** | Высокочастотные вызовы, p99 критична | Рекомендуется |
| **WebSocket (real-time)** | Мгновенная доставка сообщений | Рекомендуется |
| **金融 / Trading** | Каждый микросекундный-counts | Обязательно |
| **DNS-резолвер** | Малые запросы, задержка критична | Рекомендуется |
| **HTTP/2 и HTTP/3** | Протокол управляет мультиплексированием | По умолчанию |

### Когда НЕ отключать (Nagle полезен)

| Сценарий | Причина |
| :--- | :--- |
| **Bulk-передача файлов** | Данные идут большими блоками, Nagle не активируется (сразу MSS). |
| **Telnet через спутник** | Высокий RTT + медленный канал = критична экономия пакетов. |
| **Терминальные сессии через VPN** | Малые нажатия клавиш + шифрование overhead = Nagle экономит полосу. |
| **Логирование по сети** | Малые сообщения могут объединяться в один пакет. |

### Комбинирование с TCP_CORK

**Паттерн «оптимального HTTP-ответа»:**
```c
// 1. Включить CORK для агрегации заголовков и тела
int one = 1;
setsockopt(fd, IPPROTO_TCP, TCP_CORK, &one, sizeof(one));

// 2. Записать заголовки и тело
write(fd, headers, headers_len);
write(fd, body, body_len);

// 3. Выключить CORK — данные отправляются одним сегментом
int zero = 0;
setsockopt(fd, IPPROTO_TCP, TCP_CORK, &zero, sizeof(zero));
```

**Результат:** Один пакет с заголовками + тело вместо двух. Экономия 40 байт заголовков TCP/IP.

### Паттерн «sendfile + CORK»

```c
// Статический файл: zero-copy + агрегация
int one = 1;
setsockopt(fd, IPPROTO_TCP, TCP_CORK, &one, sizeof(one));

// HTTP-заголовки
write(fd, response_headers, headers_len);

// Файл — напрямую из страниц кэша в NIC
sendfile(fd, file_fd, &offset, file_size);

// Снять CORK
int zero = 0;
setsockopt(fd, IPPROTO_TCP, TCP_CORK, &zero, sizeof(zero));
```
