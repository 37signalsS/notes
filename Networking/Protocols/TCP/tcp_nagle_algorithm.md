# Алгоритм Нагла (Nagle Algorithm)

## Определения

**Алгоритм Нагла (Nagle Algorithm)** — это механизм в протоколе TCP, предназначенный для повышения эффективности использования пропускной способности сети путем уменьшения количества мелких пакетов (так называемая «проблема маленьких пакетов»). Алгоритм объединяет мелкие порции данных в один более крупный сегмент перед отправкой.

**Цель:** снижение накладных расходов сетевых протоколов (L2-L4 заголовков) при передаче небольших объемов полезной нагрузки.

**Автор:** Джон Нагл (John Nagle), описан в **RFC 896** (1984).

---

## Основные концепции

### Проблема малых пакетов (Small Packet Problem)

При передаче интерактивных данных (например, в сессиях Telnet или SSH) приложение может генерировать данные по одному байту. Каждый такой байт упаковывается в полноценный сегмент TCP/IP.

**Пример накладных расходов для 1 байта данных (Ethernet):**

| Компонент | Размер (байт) |
| :--- | :--- |
| Ethernet Header | 14 |
| IP Header | 20 |
| TCP Header | 20 |
| **Полезная нагрузка** | **1** |
| **Итого** | **55** |

В данном случае служебная информация составляет 54 байта на 1 байт данных (эффективность ~1.8%). Алгоритм Нагла предотвращает замусоривание сети такими пакетами.

### Принцип работы алгоритма

Алгоритм Нагла накладывает ограничение на отправку сегментов, размер которых меньше **MSS** (Maximum Segment Size).

**Правила отправки:**

1. Если в очереди накопилось данных на целый сегмент (**размер данных ≥ MSS**) — отправить немедленно.
2. Если все ранее отправленные пакеты получили подтверждение (**ACK**) — отправить немедленно (даже если данных мало).
3. Если установлен флаг **TCP_NODELAY** — отправить немедленно (алгоритм отключен).
4. В остальных случаях — накапливать данные в буфере до получения ACK или достижения размера MSS.

### Сравнение поведения

#### Без алгоритма Нагла

Каждая операция записи в сокет порождает отдельный пакет. Для слова "HELLO" (отправляемого побайтово) будет создано 5 пакетов.

#### С алгоритмом Нагла

Первый байт ("H") улетает сразу. Пока ожидается подтверждение (ACK) от сервера, остальные байты ("ELLO") накапливаются в буфере отправителя и уходят одним вторым пакетом сразу после получения ACK.

## Практические сценарии

### Когда алгоритм полезен

- **Передача файлов (FTP, HTTP):** позволяет объединять мелкие «хвосты» данных.
- **Пакетная передача:** снижает нагрузку на сетевое оборудование и процессоры хостов за счет уменьшения количества прерываний.

### Когда алгоритм вреден (Latency-sensitive приложения)

- **SSH и удаленные терминалы:** вводимые символы отображаются с задержкой, равной RTT (Round-Trip Time), что делает интерфейс «вязким».
- **Онлайн-игры:** критически важна немедленная передача данных о действиях игрока.
- **Микросервисы (RPC):** последовательные мелкие запросы могут существенно замедляться.

### Отключение алгоритма (TCP_NODELAY)

Для отключения алгоритма используется опция сокета `TCP_NODELAY`.

**Пример на Python:**

```python
import socket
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
```

**Проверка состояния в Linux:**

```bash
# Проверка наличия флага 'nagle' (если есть — алгоритм включен) или 'nodelay' (если отключен)
ss -tin dst <IP> | grep -i nagle

# Устаревший способ через 'ss -tno' (флаг 'nodelay' указывает на отключение)
ss -tno state established
```

### Отключение алгоритма

#### На уровне приложения (Рекомендуется)
Используется опция сокета `TCP_NODELAY`. Это точечное решение, не затрагивающее другие приложения.

**Пример на Python:**
```python
import socket
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
```

**Пример на C:**
```c
int flag = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));
```

#### Глобально через sysctl (Грубый метод)
Можно заставить ядро отдавать приоритет низкой латентности, но это может негативно сказаться на пропускной способности всей системы.

```bash
# Глобальное включение режима низкой латентности
sysctl -w net.ipv4.tcp_low_latency=1
```

### Конфликт с Delayed ACK

Алгоритм Нагла часто конфликтует с механизмом **Delayed ACK** (отложенное подтверждение) на стороне получателя. Это классическая проблема "тупика" (deadlock) по таймеру.

- **Нагла (отправитель):** ждет ACK, чтобы отправить следующую порцию мелких данных.
- **Delayed ACK (получатель):** ждет вторую порцию данных, чтобы объединить ACK, или ждет срабатывания таймера (обычно **200 мс**).

**Симптомы:**
- Стабильные паузы ровно **200 мс** между пакетами.
- Команды в SSH «залипают», особенно на каналах с высоким RTT.

**Диагностика через tcpdump:**
```bash
# Поиск пауз около 200мс между PSH и ACK
tcpdump -i eth0 -nn host <IP> | grep -E "ACK|PSH"
```

## Дополнительная информация

### Рекомендации по использованию

| Сценарий | Рекомендация | Обоснование |
| :--- | :--- | :--- |
| **Стриминг / Загрузка данных** | Оставить включенным | Максимальная пропускная способность. |
| **SSH / Telnet / RDP** | Отключить | Требуется минимальный отклик (интерактивность). |
| **HTTP/1.1 (Keep-Alive)** | Отключить | Ускоряет доставку мелких ресурсов. |
| **Базы данных / Файловые серверы** | **Оставить включенным** | Высокий PPS (пакетов в секунду) при отключении создаст избыточную нагрузку на CPU и сеть. |

### Последствия неоправданного отключения
В высокопроизводительных системах, где приложение делает много мелких вызовов `write()`, отключение Нагла приводит к взрывному росту количества пакетов. Это увеличивает нагрузку на сетевой стек ядра и процессор, что может снизить общую производительность системы.
