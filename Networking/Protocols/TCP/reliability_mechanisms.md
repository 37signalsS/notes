# Механизмы обеспечения надежности в TCP

## Определения

**Надежность TCP** — гарантия доставки данных без потерь, дублирования и нарушений порядка, несмотря на ненадежность базовой сети.

**Ключевые механизмы:**
- **Sequence Numbers** — нумерация байт для упорядочивания
- **Acknowledgments (ACK)** — подтверждения получения
- **Retransmission** — повторная передача при потерях
- **Checksum** — контроль целостности

---

## Основные концепции

### Нумерация последовательности (Sequence Numbers)

**Принцип:** TCP нумерует **байты**, а не сегменты.

**Initial Sequence Number (ISN):**
- Случайное 32-битное число при установке соединения
- Защищает от старых дубликатов сегментов
- Обменивается в [handshake](./connection_management.md#установка-соединения-tcp-handshake)

**Пример:**
```
Отправитель                         Получатель
     |                                    |
     |  SYN, seq=1000 ------------------> |  ISN клиента = 1000
     |  <---------------- SYN, seq=2000 --|  ISN сервера = 2000
     |  ACK, ack=2001 ------------------> |  Ожидается байт 2001
     |                                    |
     |  Данные [1001-2000], seq=1001 ---> |  Байты 1001-2000
     |  Данные [2001-3000], seq=2001 ---> |  Байты 2001-3000
     |  <---------------- ACK, ack=3001 --|  Ожидается байт 3001
```

**Назначение:**
- Восстановление порядка (reordering)
- Обнаружение дубликатов
- Точное подтверждение полученных данных

---

### Подтверждения (Acknowledgments)

**Типы подтверждений:**

#### 1. Кумулятивное подтверждение (Cumulative ACK)

**Принцип:** ACK подтверждает **все байты до указанного номера**.

```
Отправлено: [1-1000] [1001-2000] [2001-3000]
Получено:   [1-1000] [1001-2000] [2001-3000] (все)
ACK:        ack=3001 (ожидается байт 3001)
```

**Преимущество:** простой механизм, меньше служебного трафика.

**Недостаток:** при потере одного сегмента отправитель не знает о полученных после него.

---

#### 2. Выборочное подтверждение (Selective Acknowledgment, SACK)

**Принцип:** получатель явно указывает полученные блоки данных.

**Сценарий без SACK:**
```
Отправлено: [1-1000] [1001-2000] [2001-3000] [3001-4000]
Потерян:            [1001-2000]
Получено:   [1-1000]             [2001-3000] [3001-4000]
ACK:        ack=1001 (кумулятивно)
Проблема: отправитель не знает о полученных [2001-4000]
Ретрансмиссия: [1001-2000] [2001-3000] [3001-4000] (избыточно!)
```

**Сценарий с SACK:**
```
Отправлено: [1-1000] [1001-2000] [2001-3000] [3001-4000]
Потерян:            [1001-2000]
Получено:   [1-1000]             [2001-3000] [3001-4000]
ACK:        ack=1001
SACK:       blocks=[2001-4000]
Ретрансмиссия: только [1001-2000] (точно!)
```

**Опция TCP:** [SACK в заголовке](./header_format.md#выборочное-подтверждение-selective-acknowledgment-sack)

**SACK block format:**
```
Kind=5, Length=N, Left Edge, Right Edge
```

**Пример:**
```
SACK: left=2001, right=3001  (получено [2001-3000])
SACK: left=3001, right=4001  (получено [3001-4000])
```

**Включение SACK:**
- Обе стороны должны поддержать опцию `SACK permitted` в handshake
- В Linux включено по умолчанию (`net.ipv4.tcp_sack=1`)

---

### Повторная передача (Retransmission)

**Триггеры ретрансмиссии:**

#### 1. Тайм-аут (RTO — Retransmission Timeout)

**Механизм:**
1. Отправка сегмента → запуск таймера
2. Если ACK не получен до истечения RTO → ретрансмиссия
3. RTO удваивается после каждой ретрансмиссии (exponential backoff)

**Расчет RTO (RFC 6298):**
```
SRTT (Smoothed RTT) = (1 - α) × SRTT + α × RTT
RTTVAR (RTT Variance) = (1 - β) × RTTVAR + β × |SRTT - RTT|
RTO = SRTT + max(4, 4 × RTTVAR)

где:
  α = 1/8 (сглаживание SRTT)
  β = 1/4 (сглаживание RTTVAR)
  Начальное RTO = 1 секунда
```

**Минимальное RTO:** 1 секунда (RFC 6298), в Linux может быть меньше.

---

#### 2. Быстрая ретрансмиссия (Fast Retransmit)

**Триггер:** получение **3 дубликатов ACK** (DupACK).

**Логика:**
- DupACK означает, что получатель получил данные **после** потерянного сегмента
- 3 DupACK = высокая уверенность в потере (не просто reordering)
- Ретрансмиссия **без ожидания тайм-аута**

```
Отправитель                         Получатель
     |                                    |
     |  [1-1000] -----------------------> |  Получен, ACK=1001
     |  <---------------- ACK=1001 -------|
     |                                    |
     |  [1001-2000] --------------------> |  ПОТЕРЯН!
     |                                    |
     |  [2001-3000] --------------------> |  Получен, но ожидается 1001
     |  <---------------- ACK=1001 -------|  DupACK #1
     |                                    |
     |  [3001-4000] --------------------> |  Получен, но ожидается 1001
     |  <---------------- ACK=1001 -------|  DupACK #2
     |                                    |
     |  [4001-5000] --------------------> |  Получен, но ожидается 1001
     |  <---------------- ACK=1001 -------|  DupACK #3 → Fast Retransmit!
     |                                    |
     |  [1001-2000] (ретрансмиссия) ----> |  Получен!
     |  <---------------- ACK=5001 -------|  Подтверждение всех данных
```

**Преимущество перед RTO:**
- Быстрее (не нужно ждать тайм-аут)
- Выше пропускная способность

---

### Скользящее окно (Sliding Window)

**Концепция:** отправитель может передавать несколько сегментов без ожидания ACK.

**Параметры:**
```
LastByteAcked — последний подтвержденный байт
LastByteSent  — последний отправленный байт
LastByteWritten — последний записанный в сокет байт

Effective Window = LastByteAcked + Window - LastByteSent
```

**Ограничения:**
```
LastByteSent - LastByteAcked ≤ cwnd (congestion window)
LastByteSent - LastByteAcked ≤ rwnd (receiver window)
```

**«Скольжение»:** при получении ACK левая граница сдвигается вправо.

---

### Контрольная сумма (Checksum)

**Назначение:** обнаружение ошибок в заголовке и данных.

**Особенности:**
- Обязательно для TCP (в отличие от UDP)
- Включает **pseudo-header** (IP-адреса, протокол, длина)
- Если ошибка — сегмент отбрасывается без ACK

**Структура pseudo-header:**
```
 0      7 8     15 16    23 24    31
+--------+--------+--------+--------+
|          Source Address           |
+--------+--------+--------+--------+
|        Destination Address        |
+--------+--------+--------+--------+
|  Zero  |Protocol|       Length    |
+--------+--------+--------+--------+
```

## Практические сценарии

### Диагностика ретрансмиссий

```bash
# Статистика TCP
netstat -s | grep -i retrans

# Пример вывода:
#     1234567 segments retransmitted (0.5% of total)
#     8901 retransmits due to timeout
#     234567 fast retransmits
```

**Интерпретация:**
- `retransmits due to timeout` — потери, обнаруженные по RTO (серьезно)
- `fast retransmits` — потери, обнаруженные по DupACK (нормально при высокой нагрузке)

---

### Анализ через ss

```bash
# Детальная информация о сокетах
ss -tmo

# Пример вывода:
# cubic wscale:7,7 rto:204 rtt:0.5/0.25
# ato:40 mss:1460 cwnd:10
# bytes_acked:10000 bytes_received:5000
# segs_out:100 segs_in:50
# retrans: 5
```

**Поля:**
- `rto:204` — текущий RTO (204 мс)
- `rtt:0.5/0.25` — RTT среднее/отклонение (0.5 ± 0.25 мс)
- `retrans: 5` — количество ретрансмиссий для этого сокета

---

### Мониторинг потерь в реальном времени

```bash
# Счетчики TCP-событий
watch -n1 'netstat -s | grep -E "segments retrans|retransmits due"'

# Через ss (пер-сокет)
watch -n1 'ss -tmo | grep -c "retrans:"'
```

---

### tcpdump для анализа потерь

```bash
# Перехват TCP с последовательностями
tcpdump -i eth0 -nn 'tcp port 80' -v

# Пример вывода:
# 10:15:30.123 IP 192.168.1.10.54321 > 93.184.216.34.80: seq 1001:2000
# 10:15:30.130 IP 192.168.1.10.54321 > 93.184.216.34.80: seq 2001:3000
# 10:15:30.135 IP 93.184.216.34.80 > 192.168.1.10.54321: ack 2001
# 10:15:30.140 IP 192.168.1.10.54321 > 93.184.216.34.80: seq 3001:4000
# 10:15:30.150 IP 93.184.216.34.80 > 192.168.1.10.54321: ack 2001  # DupACK!
# 10:15:30.155 IP 93.184.216.34.80 > 192.168.1.10.54321: ack 2001  # DupACK!
# 10:15:30.160 IP 93.184.216.34.80 > 192.168.1.10.54321: ack 2001  # DupACK!
# 10:15:30.165 IP 192.168.1.10.54321 > 93.184.216.34.80: seq 2001:3000  # Fast Retransmit
```

**Анализ:**
- seq 2001:3000 потерян (нет ACK 3001)
- 3 DupACK → Fast Retransmit
- Ретрансмиссия через 25 мс (быстрее RTO)

### Настройка параметров RTO

```bash
# Минимальное RTO (мс), по умолчанию 200
sysctl -w net.ipv4.tcp_rto_min=200

# Количество SYN-ретрансмиссий перед отказом
sysctl -w net.ipv4.tcp_syn_retries=5

# Количество ретрансмиссий установленных соединений
# (устарело, используется динамический расчет)
```

**Важно:** уменьшение `tcp_rto_min` может вызвать избыточные ретрансмиссии в сетях с высокой задержкой.

## Взаимодействие с Congestion Control

**Потеря пакета → реакция:**

| Механизм обнаружения | Действие cwnd | Алгоритм |
| :--- | :--- | :--- |
| **3 DupACK (Fast Retransmit)** | `cwnd = cwnd / 2` | Fast Recovery |
| **RTO (тайм-аут)** | `cwnd = 1 MSS` | Slow Start |

**Важно:** RTO — более серьезное событие, означает значительную перегрузку или потерю связи.

### Проблемы и решения

| Проблема | Симптом | Решение |
| :--- | :--- | :--- |
| **Высокий % ретрансмиссий** | >1% сегментов ретранслируется | Проверить сеть, перегрузку, MTU |
| **Частые RTO** | Много `retransmits due to timeout` | Серьезная перегрузка, потеря связи |
| **SACK не работает** | Нет SACK blocks в tcpdump | Проверить `net.ipv4.tcp_sack=1` |
| **Дубликаты сегментов** | Получатель отбрасывает дубликаты | Нормально, Sequence Numbers фильтруют |

### Формулы

**Расчет RTO (RFC 6298):**
```
SRTT = (7/8) × SRTT + (1/8) × RTT
RTTVAR = (3/4) × RTTVAR + (1/4) × |SRTT - RTT|
RTO = SRTT + max(1, 4 × RTTVAR)
```

**Пример:**
```
Измеренный RTT = 100 мс
SRTT = 100 мс (после нескольких измерений)
RTTVAR = 10 мс
RTO = 100 + 4 × 10 = 140 мс
```

**Эффективная пропускная способность при потерях:**
```
Throughput ≈ MSS / (RTT × √p)

где p — вероятность потери пакета

Пример:
MSS = 1460 байт, RTT = 50 мс, p = 0.01 (1% потерь)
Throughput ≈ 1460 / (0.05 × √0.01) ≈ 2.9 МБ/с ≈ 23 Мбит/с
```
