# Повторная передача в TCP (Retransmission)

## Определения

**Повторная передача (Retransmission)** — механизм обеспечения надежности, заключающийся в повторной отправке данных, получение которых не было подтверждено. Это основной способ восстановления данных при их потере в IP-сетях.

**Retransmission Timeout (RTO)** — время ожидания подтверждения, по истечении которого сегмент считается официально потерянным.

**Spurious Retransmission (Ложная ретрансмиссия)** — повторная отправка данных, которые на самом деле не были потеряны, а лишь задержались в сети или подтверждение на них не успело дойти.

---

## Основные концепции

### 1. Тайм-аут повторной передачи (RTO)
TCP динамически рассчитывает RTO на основе текущей задержки в сети (**RTT**).
- **Алгоритм (RFC 6298):** `RTO = SRTT + 4 * RTTVAR`. Значение RTO всегда немного больше RTT, чтобы избежать ложных срабатываний.
- **Экспоненциальный рост (Backoff):** При повторных потерях одного и того же сегмента RTO удваивается (1с -> 2с -> 4с...). Это механизм «предохранителя», предотвращающий перегрузку канала, который и так испытывает проблемы.
- **RTO Restart (RFC 7765):** Логика перезапуска таймера при отправке новых данных или получении ACK, предотвращающая преждевременные тайм-ауты в интерактивном трафике.

### 2. Быстрая ретрансмиссия (Fast Retransmit)
Позволяет восстановить данные гораздо быстрее, не дожидаясь медленного таймера RTO.
- **Триггер:** Получение **3 дублирующих подтверждений (DupACK)**.
- **Логика:** Если отправитель получает три ACK с одним и тем же номером, это означает, что пакеты, отправленные *после* «дыры», дошли до получателя. Сеть жива, но один сегмент выпал.
- **Взаимодействие:** Немедленно переотправляется только потерянный сегмент, и TCP переходит в фазу **Fast Recovery** (снижение окна перегрузки без сброса в 1 MSS).

### 3. Современные механизмы оптимизации (RACK и TLP)
Современные стеки (Linux, Windows) используют более точные методы обнаружения потерь, закрепленные в **RFC 8985**.

- **Tail Loss Probe (TLP):** Решает проблему «потери в хвосте» (когда данных больше нет и DupACK прийти не могут). Отправитель передает один «пробный» пакет перед истечением RTO, чтобы спровоцировать DupACK или SACK.
- **RACK (Recent Acknowledgment):** Использует время (timestamp) вместо номеров последовательности для обнаружения потерь. Это делает TCP устойчивым к переупорядочиванию пакетов (reordering), которое часто вызывает ложные Fast Retransmit.

### 4. Выборочное восстановление (SACK-based Recovery)
При использовании опции SACK (**RFC 6675**), TCP может восстанавливать несколько потерянных сегментов за один RTT. Отправитель точно знает, какие блоки данных дошли, и переотправляет только отсутствующие фрагменты.

### 5. Борьба с ложными ретрансмиссиями
Если задержка в сети внезапно выросла, TCP может ошибочно решить, что пакет потерян.
- **Eifel Algorithm (RFC 3522):** Использует TCP Timestamps, чтобы определить, пришло ли подтверждение на исходный пакет или на ретрансмитированный.
- **F-RTO (Forward RTO-Recovery, RFC 5682):** Алгоритм для обнаружения ложных RTO (например, при переключении соты в мобильных сетях). Если после RTO приходит ACK на новые данные, TCP понимает, что тайм-аут был ложным, и не сбрасывает окно перегрузки.

## Практические сценарии

### Сценарий 1: Тюнинг RTO в Linux
В высокоскоростных сетях (ЦОД) с RTT < 1мс стандартный минимум RTO (обычно 200мс) слишком велик.

```bash
# Установка минимального RTO (rto_min) для конкретного маршрута
sudo ip route change default via 192.168.1.1 dev eth0 rto_min 5ms
```

### Сценарий 2: Глобальные лимиты повторных передач
Параметр `tcp_retries2` определяет, сколько раз TCP будет пытаться переотправить данные перед разрывом соединения.

```bash
# Уменьшение времени до разрыва «повисшего» соединения (по умолчанию 15)
sudo sysctl -w net.ipv4.tcp_retries2=8
# → net.ipv4.tcp_retries2 = 8
```

### Сценарий 3: Мониторинг ретрансмиссий через ss
Просмотр детальной статистики для активного сокета:

```bash
ss -ti dst 1.2.3.4
# → cubic rto:204 rtt:15.2/0.5 cwnd:10 retrans:0/52 sack_retrans:12
```
- `retrans:0/52`: 0 активных, 52 всего за сессию.
- `sack_retrans`: количество сегментов, переотправленных на основе SACK-блоков.
- `backoff`: текущий уровень экспоненциального ожидания (если > 0, соединение «зависло»).
