# Диагностика надежности TCP

## Определения

**Диагностика надежности TCP** — это процесс мониторинга и анализа механизмов восстановления данных после потерь, повреждений или нарушения порядка следования сегментов. Она направлена на выявление причин снижения производительности, связанных с качеством сетевого канала или некорректной настройкой параметров повторной передачи.

**Ключевые показатели:**
- **Retransmission Rate:** процент повторно отправленных сегментов от общего объема трафика.
- **Fast Retransmit:** количество ретрансмиссий, инициированных по получении трех дублирующих подтверждений (DupACK).
- **RTO Retransmits:** количество ретрансмиссий по истечении тайм-аута (Retransmission Timeout).
- **SACK Efficiency:** эффективность использования выборочных подтверждений для минимизации объема лишних данных при восстановлении.

## Основные концепции

### Инструментарий

Для анализа надежности в Linux используются следующие инструменты:
- **`ss -ti` / `ss -tmo`:** детальная статистика по конкретным сокетам (RTT, RTO, количество ретрансмиссий).
- **`nstat -az`:** просмотр глобальных счетчиков стека TCP (более современная замена `netstat -s`).
- **`tcpdump`:** захват трафика для визуального анализа DupACK, SACK-блоков и последовательностей номеров (Seq).

### Типы потерь и их признаки

| Тип события | Признак в инструментах | Степень серьезности |
| :--- | :--- | :--- |
| **DupACK / Fast Retransmit** | `fast retransmits` в nstat, `retrans` в ss | Умеренная (нормально при высокой нагрузке) |
| **RTO Timeout** | `retransmits due to timeout` в nstat | Высокая (критическая перегрузка или обрыв связи) |
| **SACK Recovery** | Наличие блоков `SACK` в выводе tcpdump | Низкая (эффективное восстановление) |
| **Checksum Error** | `cksum incorrect` в tcpdump | Аппаратная проблема или ошибки offloading |

## Практические сценарии

### Сценарий 1: Глобальный мониторинг ретрансмиссий в системе

Для оценки общего качества связи на сервере используйте `nstat`:
```bash
# Просмотр счетчиков ретрансмиссий
nstat -az | grep -E 'TcpRetransSegs|TcpOutSegs'

# Расчет Retransmission Rate (%)
# (TcpRetransSegs / TcpOutSegs) * 100
```
*Нормальным считается показатель < 1%. Значения выше 3-5% требуют расследования состояния сетевого оборудования.*

### Сценарий 2: Поиск «проблемных» соединений через ss

Если жалоба поступает на конкретный сервис, можно найти сокеты с наибольшим количеством потерь:
```bash
# Соединения с активными ретрансмиссиями
ss -tmo | awk '/retrans: [1-9]/'

# Пример вывода:
# cubic rto:204 rtt:0.5/0.25 cwnd:10 retrans:5/12
# (5 текущих ретрансмиссий из 12 общего числа за сессию)
```

### Сценарий 3: Анализ процесса восстановления в tcpdump

Для глубокого понимания того, почему пакеты теряются, используйте захват с флагами:
```bash
# Захват трафика с анализом SACK
tcpdump -i eth0 -nn 'tcp' -vvv | grep -i sack
```
**На что смотреть:**
- Идут ли `SACK`-блоки? Если нет, проверьте настройку `net.ipv4.tcp_sack=1`.
- Сколько `DupACK` приходит до начала ретрансмиссии? (Должно быть 3).

### Сценарий 4: Проверка аппаратного ускорения (Offloading)

Иногда неверные контрольные суммы в дампах являются ложными из-за выноса вычислений на сетевую карту.
```bash
# Проверка и временное отключение для чистоты эксперимента
ethtool -k eth0 | grep checksum
sudo ethtool -K eth0 tx-checksumming off rx-checksumming off
```
