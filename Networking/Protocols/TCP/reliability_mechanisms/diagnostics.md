# Диагностика надежности TCP

## Определения

**Диагностика надежности TCP** — процесс мониторинга и анализа механизмов восстановления данных (ретрансмиссий, подтверждений, тайм-аутов) для выявления деградации сетевого канала, аппаратных сбоев или ошибок конфигурации стека ОС.

**Ключевые метрики:**
- **Retransmission Rate:** Процент повторно отправленных сегментов от общего исходящего трафика (норма < 1%).
- **RTO Retransmits:** Потери, восстановленные по тайм-ауту (признак серьезных заторов или обрывов).
- **Fast Retransmits:** Потери, восстановленные через 3-DupACK (норма при высокой нагрузке).
- **TLP (Tail Loss Probe):** Пробные сегменты для обнаружения потерь в конце транзакции, когда Duplicate ACKs невозможны.

## Основные инструменты

### 1. Глобальная статистика (nstat)
Утилита `nstat` (замена `netstat -s`) показывает агрегированные счетчики стека TCP с момента загрузки.

```bash
# Просмотр критических счетчиков надежности
nstat -az | grep -E 'TcpRetransSegs|TcpOutSegs|TcpExtTCPTimeouts|TcpExtTCPTailLossProbe'
# → TcpRetransSegs                   50                 0.0
# → TcpOutSegs                      5000                0.0
# → TcpExtTCPTimeouts                5                  0.0
# → TcpExtTCPTailLossProbe           12                 0.0
```
**Формула Retransmission Rate:** `(TcpRetransSegs / TcpOutSegs) * 100`.

### 2. Детальный анализ сокетов (ss)
Инструмент `ss -ti` показывает внутренние метрики конкретных соединений.

```bash
ss -ti dst 1.2.3.4
# → cubic rto:204 rtt:15.2/0.5 cwnd:10 retrans:0/12 backoff:0
```
- `retrans:текущие/всего`: Статистика потерь за всю сессию сокета.
- `backoff`: Счетчик экспоненциального ожидания. Если > 0 — соединение "зависло" на тяжелых потерях.

### 3. eBPF Трассировка (2026)
Современный метод анализа без захвата трафика (tcpdump), минимизирующий нагрузку на CPU.

- **tcpretrans:** Выводит каждую ретрансмиссию с указанием IP и типа (RTO/Fast).
- **tcpdrop:** Показывает пакеты, отброшенные самим ядром (например, из-за неверной контрольной суммы).

```bash
sudo tcpretrans
# → TIME     PID    LADDR:LPORT          DADDR:DPORT          STATE       TYPE
# → 12:00:01 123    1.1.1.1:443       >  2.2.2.2:54321        ESTABLISHED RTO
```

## Типы инцидентов и диагностика

| Симптом | Вероятная причина | Инструмент проверки |
| :--- | :--- | :--- |
| **Высокий Retrans Rate (>5%)** | Проблемы L1/L2 (кабель, дуплекс), перегрузка. | `nstat`, `ethtool -S` |
| **Рост счетчика Timeouts** | Превышен лимит ретрансмиссий (15 попыток). Сессия принудительно закрыта ядром. | `nstat -az TcpExtTCPTimeouts` |
| **Checksum Error** | Ошибки памяти (ECC), проблемы с NIC Offloading. | `tcpdump -v`, `ethtool -k` |
| **Рост TailLossProbe** | Потери на коротких HTTP-запросах (конец данных). | `nstat -az TcpExtTCPTailLossProbe` |

## Практические сценарии

### Сценарий 1: Дифференциация потерь
Если `retrans` в `ss` растет, но RTT стабилен — это **случайные потери** (помехи на Wi-Fi/LTE). Если RTT растет вместе с потерями — это **перегрузка очередей** (Bufferbloat).

### Сценарий 2: Поиск дропов на стороне приложения
Если пакеты доходят до системы, но отбрасываются до попадания в приложение:
```bash
nstat -az TcpExtListenDrops
# → TcpExtListenDrops                100                0.0
```
**Решение:** Увеличение `backlog` в приложении или `net.core.somaxconn` в ядре.
