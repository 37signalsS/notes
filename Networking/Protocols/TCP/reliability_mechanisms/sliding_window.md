# Скользящее окно в TCP (Sliding Window)

## Определения

**Скользящее окно (Sliding Window)** — фундаментальный механизм протокола TCP, обеспечивающий управление потоком данных (Flow Control) и оптимизацию пропускной способности. Он позволяет отправителю передавать несколько сегментов подряд (пакетами "в полете"), не дожидаясь подтверждения (ACK) для каждого из них. 

**Bandwidth-Delay Product (BDP)** — произведение пропускной способности канала (Bandwidth) на время кругового обхода (RTT). BDP определяет максимальный объем данных, который физически может находиться в сети в любой момент времени («в трубе»). Если размер скользящего окна меньше BDP, канал связи будет недоиспользован.

## Базовые концепции

### Структура окна отправителя (Sender Window)
Окно представляет собой логический буфер, разделенный указателями на 4 зоны:

```text
               ◄────────────── Окно (Window) ──────────────►
               ┌───────────────────────┬───────────────────┐
 подтверждено  │      в полете         │  можно отправить  │  нельзя
 (отброшено)   │ (отправлено, без ACK) │ (в рамках лимита) │ (вне окна)
               └───────────────────────┴───────────────────┘
               ▲                       ▲                   ▲
               │                       │                   │
         LastByteAcked           LastByteSent        LastByteAcked + Win
```

- **Левая граница (Left Edge):** Сдвигается вправо при получении новых подтверждений (ACK).
- **Правая граница (Right Edge):** Рассчитывается как `Левая граница + Эффективное окно`. Сдвигается вправо, открывая возможность для отправки новых данных.

### Взаимодействие cwnd и rwnd
Реальное количество данных, которое TCP разрешает отправить в сеть (**Effective Window**), жестко ограничено двумя факторами:
1. **rwnd (Receiver Window):** Защищает **получателя**. Указывает на свободное место в приемном буфере партнера. Значение передается в 16-битном поле `Window Size` заголовка каждого ACK-пакета.
2. **cwnd (Congestion Window):** Защищает **сеть**. Это оценка пропускной способности маршрутизаторов на пути следования, рассчитываемая алгоритмами управления перегрузкой (CUBIC, BBR).

**Формула расчета:**
```text
Effective Window = min(cwnd, rwnd)
В полете можно держать: (LastByteSent - LastByteAcked) ≤ min(cwnd, rwnd)
```

### Масштабирование окна (Window Scale)
В классическом TCP 16-битное поле `Window Size` ограничивает максимальное окно значением 65 535 байт. На каналах с высокой пропускной способностью и задержкой (например, 1 Гбит/с и RTT 100 мс, где BDP ~ 12.5 МБ) это станет "узким горлышком" (bottleneck).
- **Решение (RFC 7323):** Введена опция **Window Scale (WSCALE)**. Она передает множитель сдвига (степень двойки от 0 до 14). Истинное окно получателя рассчитывается как `Window Size * 2^wscale`, что расширяет максимальный размер окна до ~1 ГБ. Согласовывается **только** при 3-way Handshake.

## Проблема «глупого окна» (Silly Window Syndrome)

**SWS (Silly Window Syndrome)** — ситуация деградации производительности, когда из-за медленного чтения приложением или медленной генерации данных, сегменты отправляются микроскопическими порциями (например, по 1 байту). При этом накладные расходы (40 байт заголовков IP/TCP) превышают полезную нагрузку в 40 раз.

### Решение на стороне получателя (Алгоритм Кларка)
Получатель (алгоритм Дэвида Кларка) не должен объявлять увеличение окна (`rwnd`), пока свободное место в его буфере не достигнет:
- Либо размера **MSS** (Maximum Segment Size).
- Либо половины от общего размера буфера приема.
До достижения этого порога получатель должен анонсировать старое (меньшее) значение окна, либо `rwnd = 0`, заставляя отправителя копить данные.

### Решение на стороне отправителя (Алгоритм Нагла)
Отправитель (алгоритм Джона Нагла) предотвращает отправку множества мелких пакетов. Он задерживает отправку данных, меньших чем MSS, если в сети уже есть неподтвержденные данные (unacknowledged data). 
- *Подробнее:* Описание конфликтов с Delayed ACK см. в [Алгоритм Нагла](../tcp_nagle_algorithm.md).

## Практические сценарии

### Сценарий 1: Обработка Zero Window и Persist Timer
Если приложение-получатель зависло и буфер заполнился, оно отправляет ACK с `rwnd = 0`. Отправитель останавливает передачу.
- **Проблема Deadlock:** Если получатель освободит буфер и пошлет ACK с `rwnd > 0`, но этот пакет потеряется, соединение зависнет навсегда.
- **Решение:** Отправитель запускает **Persist Timer**. Периодически он отправляет **Zero Window Probe** (сегмент из 1 байта данных). Получатель обязан ответить на него, указав текущий размер окна.

### Сценарий 2: Анализ согласованного окна через ss
Диагностика ограничений скорости на сервере Linux:

```bash
ss -ti dst 1.2.3.4
# → cubic wscale:7,7 rto:204 rtt:15.2/0.5 cwnd:1000 rcv_space:14600
```
- **wscale:7,7:** Окно масштабируется умножением на $2^7$ (128). Если `wscale` отсутствует на высокоскоростных линках, скорость будет катастрофически низкой.
- **cwnd:1000:** Сеть позволяет отправить 1000 * MSS (обычно ~1.4 МБ).
- **rcv_space:** Размер окна, который этот узел в данный момент анонсирует партнеру.
