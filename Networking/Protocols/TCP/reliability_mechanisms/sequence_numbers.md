# Порядковые номера в TCP (Sequence Numbers)

## Определения

**Порядковый номер (Sequence Number)** — 32-битное беззнаковое целое число в заголовке TCP, идентифицирующее позицию первого байта данных конкретного сегмента в общем потоке. TCP рассматривает передаваемые данные как непрерывную ленту байтов, где каждому байту присвоен уникальный номер.

**Начальный порядковый номер (Initial Sequence Number, ISN):** Значение, выбираемое каждой стороной (клиентом и сервером) при установке соединения (флаг SYN). Согласно **RFC 6528**, ISN генерируется с использованием криптографически стойкого PRNG, чтобы предотвратить атаки предсказания номеров (Session Hijacking).

## Базовые концепции

### 1. Правила инкрементации (Виртуальные байты)
Порядковый номер увеличивается пропорционально количеству переданных байтов полезной нагрузки. Однако управляющие флаги также потребляют номерное пространство:
- **SYN:** Занимает 1 виртуальный байт. Если SYN отправлен с `seq = X`, то следующий сегмент начнется с `seq = X + 1`.
- **FIN:** Занимает 1 виртуальный байт. Это гарантирует, что сигнал о закрытии будет подтвержден кумулятивным ACK.
- **Данные:** Если сегмент содержит 1460 байт (MSS) и начинается с `seq = 100`, то следующий сегмент будет иметь `seq = 1560`.

### 2. Проблема переполнения счетчика (Wrap-around)
Поскольку поле `Sequence Number` ограничено 32 битами (макс. 4 294 967 295), при непрерывной передаче номер возвращается к 0.
- В гигабитных сетях (10 Gbps) «заворот» счетчика происходит менее чем за 4 секунды.
- Это создает риск того, что «старый» пакет, задержавшийся в сети, будет принят как «новый» с тем же номером порядковой последовательности.

### 3. Механизм PAWS (RFC 7323)
**PAWS (Protection Against Wrapped Sequence numbers)** — защита от наложения номеров.
- **Условие:** Требует обязательного использования опции **TCP Timestamps**.
- **Логика:** Каждый сегмент несет метку времени отправителя. Если входящий пакет имеет `seq`, попадающий в текущее окно, но его метка времени (`TSval`) меньше, чем последняя принятая метка для этого соединения, пакет отбрасывается как устаревший дубликат.

### 4. SYN Cookies и порядковые номера
При защите от SYN-флуда сервер не выделяет ресурсы под сокет до получения финального ACK. Он кодирует параметры соединения (MSS, секретный ключ) внутри самого **Sequence Number** в пакете SYN-ACK.
- При получении ACK от клиента сервер проверяет: `ack_seq - 1 == hash(параметры)`.
- Если проверка успешна, соединение восстанавливается из «воздуха».

## Практические сценарии

### Сценарий 1: Проверка абсолютных номеров в tcpdump
По умолчанию анализаторы показывают относительные номера (начиная с 0). Флаг `-S` позволяет увидеть реальные значения.

```bash
sudo tcpdump -i any -S -nn tcp port 80
# → IP 1.1.1.1.54321 > 2.2.2.2.80: Flags [S], seq 3845612348
# → IP 2.2.2.2.80 > 1.1.1.1.54321: Flags [S.], seq 1098234567, ack 3845612349
```
# → Результат: Номер ACK в ответе на 1 больше, чем SYN Seq, что подтверждает потребление виртуального байта.

### Сценарий 2: Мониторинг срабатываний PAWS
Если в логах или при диагностике наблюдаются потери без видимых причин, проверьте счетчик отброшенных пакетов:

```bash
nstat -az TcpExtPAWSEstab
# → TcpExtPAWSEstab                   142                0.0
```
# → Результат: Ненулевое значение указывает на то, что PAWS защитил сессию от некорректных старых пакетов.
