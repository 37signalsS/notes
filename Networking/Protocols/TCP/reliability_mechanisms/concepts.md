# Механизмы надежности TCP

## Определения

**Надежность TCP (TCP Reliability)** — комплекс архитектурных решений и протокольных механизмов, гарантирующих безошибочную, упорядоченную и полную доставку потока байтов между приложениями через потенциально ненадежную IP-сеть.

**Ключевые гарантии (RFC 9293):**
- **Целостность (Integrity):** Обнаружение поврежденных данных и их отбрасывание.
- **Упорядоченность (Ordering):** Восстановление исходной последовательности байт на стороне получателя.
- **Отсутствие дубликатов:** Распознавание и игнорирование повторно отправленных сегментов.
- **Гарантированная доставка:** Использование системы подтверждений и повторных передач для устранения потерь.

## Архитектура механизмов надежности

TCP реализует модель надежности через взаимодействие пяти ключевых компонентов. Каждый механизм решает конкретную задачу, но **все они работают совместно** — выход из строя одного приводит к деградации остальных.

```text
┌─────────────────────────────────────────────────────────────┐
│                    ПРИЛОЖЕНИЕ (Application)                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │  Sequence    │  │Acknowledgment│  │Retransmission│      │
│  │  Numbers     │  │   (ACK)      │  │  (RTO/Fast)  │      │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘      │
│         │                 │                 │               │
│         └────────┬────────┴────────┬────────┘               │
│                  │                 │                        │
│  ┌──────────────┐│  ┌──────────────┐│  ┌──────────────┐    │
│  │  Checksum    ││  │Flow Control  ││  │Congestion    │    │
│  │  (Integrity) ││  │(Sliding Win) ││  │Control       │    │
│  └──────────────┘│  └──────────────┘│  └──────────────┘    │
│                  │                 │                        │
├──────────────────┼─────────────────┼────────────────────────┤
│              TCP Segment (Заголовок + Payload)              │
├─────────────────────────────────────────────────────────────┤
│                    IP (Network Layer)                        │
└─────────────────────────────────────────────────────────────┘
```

### 1. Порядковые номера (Sequence Numbers)
Каждый байт в TCP-потоке имеет свой уникальный номер. Это позволяет получателю:
- Правильно собрать данные, прибывшие не по порядку.
- Определить границы сегментов.
- Выявить пропуски («дыры») в данных.

*Подробнее:* [Порядковые номера в TCP](./sequence_numbers.md).

### 2. Подтверждения (Acknowledgments)
TCP использует схему положительных подтверждений:
- **Cumulative ACK:** Подтверждает получение всех байтов до указанного номера включительно.
- **SACK (Selective ACK):** Позволяет подтвердить получение разрозненных блоков данных, минимизируя лишние ретрансмиссии при множественных потерях.
- **ACK Clocking:** Подтверждения служат «метрономом» для отправителя — каждый ACK открывает окно (`cwnd`) и позволяет отправить новые данные (self-clocking).

*Подробнее:* [Подтверждения (ACK) в TCP](./acknowledgments.md).

### 3. Механизмы восстановления (Retransmission)
Реакция на потерю данных инициируется тремя способами:
- **По таймеру (RTO):** Если ACK не получен в течение расчетного времени. Формула: `RTO = SRTT + max(G, 4 * RTTVAR)` (RFC 6298).
- **Быстрая ретрансмиссия (Fast Retransmit):** При получении трех дублирующих ACK. Не дожидается RTO, восстанавливает данные на ~300 мс быстрее.
- **RACK-TLP (RFC 8985):** Современный алгоритм (стандарт в Linux с 4.15+). RACK обнаруживает потери по **времени доставки** (устойчив к переупорядочиванию), TLP отправляет пробный сегмент перед RTO для обнаружения «хвостовых» потерь.

*Подробнее:* [Механизмы ретрансмиссии](./retransmission.md).

### 4. Контрольная сумма (Checksum)
16-битное поле, защищающее заголовок и данные от случайных битовых ошибок. TCP применяет механизм **Silent Drop**: сегмент с неверной суммой отбрасывается без уведомления отправителя, что приводит к срабатыванию RTO.

**Свойства:**
- Обязательна для каждого сегмента (в отличие от UDP в IPv4).
- Рассчитывается по псевдозаголовку (IP-адреса + Protocol + TCP Length), заголовку и payload.
- Идемпотентна: повторное суммирование всех слов (включая checksum) дает `0xFFFF` при целостности данных.

*Подробнее:* [Контрольная сумма в TCP](./checksum.md).

### 5. Управление потоком (Flow Control)
Механизм «Скользящего окна» (Sliding Window) предотвращает переполнение буфера получателя, динамически ограничивая объем данных, который отправитель может передать без подтверждения.

- **rwnd (Receiver Window):** Значение из поля `Window Size` ACK-пакета. Защищает получателя.
- **Window Scale (RFC 7323):** Множитель `2^wscale` (0–14), согласуемый при handshake. Расширяет максимальное окно с 64 КБ до ~1 ГБ.
- **Silly Window Syndrome (SWS):** Деградация при отправке микроскопических сегментов. Решается алгоритмом Кларка (получатель) и алгоритмом Нагла (отправитель).

*Подробнее:* [Скользящее окно](./sliding_window.md).

## Взаимодействие механизмов

Механизмы надежности **не работают изолированно**. Понимание их взаимодействия критично для диагностики проблем:

### Цепочка: Checksum → Silent Drop → RTO → Retransmission
```
Пакет с неверной checksum
    ↓ Silent Drop (без ICMP/RST)
Отправитель не получает ACK
    ↓ Таймер RTO истекает
RTO × 2^n (экспоненциальный backoff)
    ↓ 
Ретрансмиссия (или Fast Retransmit при DupACK)
```

### Цепочка: Sequence Number → Ordering → ACK → Window
```
Отправитель: seq=100, len=1000
    ↓ Данные в полете
Получатель: seq=100–1000 получены
    ↓ ACK 1100 (кумулятивное)
Отправитель: сдвигает левую границу окна
    ↓ Открывается新的 пространство
Отправитель: отправляет seq=1100, len=1000
```

### Конфликт: Delayed ACK + Nagle
Когда приложение использует алгоритм Нагла (отправка мелких пакетов задерживается) И получатель применяет Delayed ACK (ACK задерживается до 200 мс), возникает **лишняя задержка ровно в 200 мс**:

```text
Отправитель: [Пакет 1] ──→ получатель
                  ↓ (Nagle ждет ACK)
Получатель:      ──→ [Delayed ACK] ──→ отправитель (через 200 мс)
                  ↓
Отправитель: [Пакет 2] ──→ получатель  (только ПОСЛЕ ACK)
```

**Решение:** Отключить Nagle (`TCP_NODELAY`) или использовать `TCP_QUICKACK` на стороне получателя. Подробнее: [Алгоритм Нагла](../tcp_nagle_algorithm.md).

### Конфликт: Flow Control vs Congestion Control
Эффективное окно发送者的受限 обоими механизмами:
```text
Effective Window = min(rwnd, cwnd)
```

- Если `rwnd > cwnd`: сеть перегружена, отправитель адаптируется через congestion control (CUBIC, BBR).
- Если `rwnd < cwnd`: получатель не справляется с приемом, отправитель ограничен его буфером.
- Если оба малы: проблема на двух уровнях (и сеть, и получатель).

## Сравнение с QUIC (HTTP/3)

В 2026 году механизмы надежности TCP часто сравниваются с протоколом **QUIC**, который решает фундаментальные ограничения TCP:

| Характеристика | TCP (RFC 9293) | QUIC (RFC 9000) |
| :--- | :--- | :--- |
| **Базовый протокол** | IP (Protocol 6) | UDP (Port 443) |
| **Head-of-Line Blocking** | Присутствует (потеря одного пакета блокирует весь поток). | Отсутствует (независимая доставка в разных потоках). |
| **Установка соединения** | 3-way Handshake (1 RTT) | 0-RTT / 1-RTT (совместно с TLS 1.3). |
| **Шифрование** | TLS поверх TCP (опционально). | Встроено по умолчанию (защищает даже метаданные). |
| **Механизм надежности** | Checksum + Seq/Ack + RTO | Checksum UDP + Packet Protection + Stream-level ACK |
| **Управление потоком** | rwnd (1 соединение) | Flow Control на уровне потоков и соединения |
| **Обнаружение потерь** | RACK-TLP (по времени) | Packet Numbers + Time Threshold |
| **Ретрансмиссия** | Весь сегмент (вплоть до MSS) | Только потерянные байты ( stream-level) |

**Почему QUIC эффективнее:**
- **Нет HOL Blocking:** Потеря пакета в одном HTTP/2-потоке не блокирует остальные (TCP блокирует весь поток).
- **Stream-level ACK:** QUIC подтверждает каждый поток отдельно, отправитель знает какие данные были потеряны именно в этом потоке.
- **0-RTT:** Повторное соединение не требует handshake (сравните: TCP требует 1 RTT минимум).

**Однако TCP всё ещё доминирует:**
- Поддерживается ядром ОС (не требует пользовательского пространства).
- Более зрелые алгоритмы управления перегрузкой (CUBIC, BBR v2).
- Аппаратная разгрузка (TSO, GRO, checksum offload)广泛 поддерживается NIC.

## Практические сценарии

### Сценарий 1: Обнаружение ретрансмиссий в Linux
Для диагностики проблем надежности в активной сессии используйте утилиту `ss`.

```bash
ss -ti dst 8.8.8.8
# → cubic rto:204 rtt:15.2/0.5 cwnd:10 retrans:0/5
```
- `retrans:0/5` — 5 ретрансмиссий за время соединения, на данный момент потерь нет.
- `rto:204` — текущий RTO = 204 мс.
- `cwnd:10` — окно перегрузки = 10 MSS.
- `rtt:15.2/0.5` — RTT = 15.2 мс, jitter = 0.5 мс.

### Сценарий 2: Идентификация Silent Drop
Если приложение испытывает задержки ровно в 200–1000 мс (стандартные значения RTO), это часто указывает на потерю пакета из-за ошибки контрольной суммы или перегрузки очереди.

```bash
# Шаг 1: Проверка системных счетчиков ошибок
nstat -az | grep -iE "Csum|Drop|Retrans"
# → TcpExtTCPInCsumErrors    23   0.0   ← ошибки checksum
# → TcpExtRetransSegs        156  0.0   ← ретрансмиссии

# Шаг 2: Мониторинг в реальном времени
watch -n 1 'nstat -az | grep -iE "Csum|Retrans"'

# Шаг 3: Захват трафика для детального анализа
sudo tcpdump -i eth0 -w /tmp/drop_debug.pcap 'host 8.8.8.8' &
# ... воспроизвести проблему ...
sudo kill %1

# Шаг 4: Анализ дампа
tshark -r /tmp/drop_debug.pcap -Y "tcp.analysis.retransmission" | head -10
tshark -r /tmp/drop_debug.pcap -Y "tcp.analysis.duplicate_ack" | head -10
```

### Сценарий 3: Диагностика Delayed ACK + Nagle через ss
Если соединение показывает задержки ровно 200 мс между пакетами:

```bash
ss -ti dst server.example.com
# → ato:200  ← Delayed ACK активен (200 мс)

# Проверка, использует ли приложение TCP_NODELAY
ss -tnpe | grep -A 2 "server.example.com"
# → users:(("app",pid=1234,fd=5)) timer:(on,200ms,0) ...
# → Если.timer = on,200ms → Delayed ACK активен
```

**Решение:**
```bash
# На стороне сервера (отключить Nagle)
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &(int){1}, sizeof(int));

# На стороне клиента (отключить Delayed ACK)
setsockopt(fd, IPPROTO_TCP, TCP_QUICKACK, &(int){1}, sizeof(int));
# Примечание: TCP_QUICKACK — одностраничный, нужно устанавливать перед каждым recv/send
```

### Сценарий 4: Мониторинг Window Size через nstat
Если приложение经常 тормозит, проверьте state of flow control:

```bash
# Проверка zero-window situations
nstat -az | grep -i "ZeroWindow\|Win"
# → TcpExtTCPWindowFull  42  0.0  ← полное окно (отправитель заблокирован)
# → TcpExtTCPRecvQueueFull  5  0.0  ← получатель не успевает читать

# Мониторинг в реальном времени
watch -n 1 'nstat -az | grep -iE "Window|Queue"'
```

### Сценарий 5: Полная диагностика надежности соединения
Комплексный скрипт для проверки всех механизмов:

```bash
#!/bin/bash
# diagnose_tcp_reliability.sh <destination_ip> [interval_sec]

DST=${1:-8.8.8.8}
INTERVAL=${2:-5}

echo "=== TCP Reliability Diagnostics for $DST ==="
echo "Press Ctrl+C to stop"
echo

while true; do
    echo "--- $(date) ---"

    # 1. RTO и ретрансмиссии
    echo "[1] Retransmission Stats:"
    ss -ti dst "$DST" 2>/dev/null | head -3
    echo

    # 2. Счетчики ошибок
    echo "[2] Error Counters:"
    nstat -az 2>/dev/null | grep -iE "Csum|Retrans|Drop|Zero|Queue" | head -10
    echo

    # 3. Window stats
    echo "[3] Window Stats:"
    ss -tnpe dst "$DST" 2>/dev/null | awk '{print $4}' | sort | uniq -c
    echo

    sleep "$INTERVAL"
done
```
