# Подтверждения в TCP (Acknowledgments)

## Определения

**Подтверждение (Acknowledgment, ACK)** — это механизм уведомления отправителя о том, что данные успешно достигли получателя. Поле `Acknowledgment Number` в заголовке TCP указывает на порядковый номер следующего байта, который получатель ожидает увидеть в потоке.

**Кумулятивное подтверждение (Cumulative ACK)** — схема, при которой один сегмент ACK подтверждает получение всех предшествующих байтов данных без разрывов.

**Выборочное подтверждение (Selective Acknowledgment, SACK)** — расширение TCP, позволяющее получателю сообщать об успешно принятых блоках данных, находящихся за пределами непрерывной последовательности (за «дырами» в потоке).

---

## Основные концепции

### Механизм кумулятивного ACK

TCP подтверждает не сегменты, а **байты**. Номер подтверждения всегда указывает на «левую границу» окна получателя — первый байт, который еще не был принят.

- Если получены байты 1–1000 и 1001–2000, получатель отправляет `ACK=2001`.
- Если получен байт 1–1000, а затем 2001–3000 (пакет 1001–2000 потерян), получатель продолжает отправлять `ACK=1001`, указывая на разрыв.

### Выборочные подтверждения (SACK)

SACK решает проблему избыточных ретрансмиссий при множественных потерях. Получатель сообщает отправителю о «островах» данных, полученных не по порядку.

- **Опция SACK:** передается в поле опций заголовка TCP.
- **Принцип:** отправитель ретранслирует только те данные, которые не попали ни в кумулятивный ACK, ни в блоки SACK.
- *Подробнее об опции:* [Опции TCP](../Header_Format/options.md#выборочное-подтверждение-selective-acknowledgment-sack).

### Отложенные подтверждения (Delayed ACK)

Механизм оптимизации трафика, при котором получатель не отправляет ACK мгновенно на каждый входящий сегмент.

- **Цель:** дождаться данных от собственного приложения для отправки ACK вместе с ними (Piggybacking) или подтвердить сразу два сегмента одним пакетом.
- **Ограничения (RFC 1122):** задержка не должна превышать 500 мс (в Linux обычно до 200 мс).
- **Конфликт:** может приводить к задержкам при взаимодействии с [Алгоритмом Нагла](../tcp_nagle_algorithm.md#конфликт-с-delayed-ack).

### Дублирующие подтверждения (Duplicate ACK)

ACK считается дубликатом (DupACK), если он имеет тот же номер подтверждения, что и предыдущий, при этом в соединении есть данные «в полете».

- **Причина:** получение сегмента вне очереди (сигнал о возможной потере предыдущего сегмента).
- **Реакция:** получение 3-х DupACK подряд инициирует механизм [Быстрой ретрансмиссии](./retransmission.md#2-быстрая-ретрансмиссия-fast-retransmit).

## Практические сценарии

### Сценарий 1: Расчет номера подтверждения

Пример передачи сообщения "HELLO" (5 байт):

1. Отправитель посылает сегмент с `Sequence Number = 100` и 5 байтами данных.
2. Получатель принимает байты 100, 101, 102, 103, 104.
3. Получатель формирует `Acknowledgment Number = 105` (следующий ожидаемый байт).

### Сценарий 2: Анализ SACK в Wireshark

Если в дампе трафика видны сегменты с заголовком `SLE` (SACK Left Edge) и `SRE` (SACK Right Edge):

- Это означает, что в сети есть потери или переупорядочивание пакетов.
- Стек TCP успешно восстанавливает данные, не сбрасывая скорость передачи до минимума.

### Сценарий 3: Настройка в Linux

Проверка и включение SACK:

```bash
# Проверка статуса (1 - включено)
sysctl net.ipv4.tcp_sack

# Включение в реальном времени
sudo sysctl -w net.ipv4.tcp_sack=1
```
