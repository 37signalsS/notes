# Подтверждения в TCP (Acknowledgments)

## Определения

**Подтверждение (Acknowledgment, ACK)** — основной механизм обратной связи в TCP, уведомляющий отправителя об успешном приеме данных. Поле `Acknowledgment Number` в заголовке TCP содержит порядковый номер следующего байта, который получатель ожидает увидеть. Все байты с номерами меньше этого значения считаются успешно принятыми.

**Кумулятивное подтверждение (Cumulative ACK):** Схема, при которой один ACK-сегмент подтверждает получение непрерывного потока байтов. Если в последовательности возникает «дыра» (пропущенный сегмент), ACK перестает расти, пока недостающие данные не будут получены.

## Основные концепции

### 1. Механизм кумулятивного подтверждения
TCP подтверждает байты, а не пакеты. Если отправлены сегменты 1–1000 и 1001–2000, получатель отвечает `ACK 2001`. Если же сегмент 1–1000 потерян, но 1001–2000 доставлен, получатель обязан отвечать `ACK 1` (или номер последнего подтвержденного байта), генерируя **Duplicate ACK**.

### 2. Отложенные подтверждения (Delayed ACK)
Механизм оптимизации трафика для исключения передачи «пустых» ACK-пакетов (RFC 1122).
- **Piggybacking:** Получатель задерживает отправку ACK на короткое время (в Linux обычно до **200 мс**, минимум **40 мс**), надеясь прикрепить подтверждение к ответному пакету данных прикладного уровня.
- **Двойное подтверждение:** Если данных для отправки нет, получатель ждет прихода второго сегмента, чтобы подтвердить сразу два пакета одним ACK.
- **Конфликт:** Delayed ACK часто конфликтует с [Алгоритмом Нагла](../tcp_nagle_algorithm.md), вызывая задержки (тупики), которые критичны для интерактивного трафика и микросервисов.

### 3. Режим QuickACK в Linux
В начале соединения или после обнаружения потери Linux переводит сокет в режим **QuickACK**. В этом режиме подтверждения отправляются немедленно на каждый сегмент, чтобы позволить отправителю быстрее наращивать окно перегрузки (`cwnd`) в фазе Slow Start.

### 4. Выборочные подтверждения (SACK)
При множественных потерях в одном окне кумулятивный ACK неэффективен. Опция **SACK (Selective ACK, RFC 2018)** позволяет получателю сообщить об «островах» данных, полученных за пределами разрыва.
- **DSACK (Duplicate SACK):** Расширение SACK (RFC 2883), используемое для информирования отправителя о получении дубликата сегмента. Это помогает отправителю понять, что произошла ложная ретрансмиссия (например, из-за внезапного скачка задержки в сети).

### 5. Сжатие подтверждений (ACK Compression)
Явление, возникающее в перегруженных сетях или при использовании функций разгрузки (Offloading), когда группа ACK-пакетов «склеивается» или прибывает к отправителю одновременно. Это может вызвать резкие всплески (bursts) трафика со стороны отправителя, что негативно влияет на стабильность канала.

## Практические сценарии

### Сценарий 1: Диагностика SACK и DSACK в tcpdump
Наличие SACK-блоков в дампе — верный признак потерь или переупорядочивания пакетов в сети.

```bash
sudo tcpdump -ni any 'tcp' -vvv
# → ... ack 1001, options [nop,nop,sack 1 {2001:3001}]
# Интерпретация: Ждем байт 1001, но блок 2001-3000 уже получен.

# → ... ack 1001, options [nop,nop,sack 1 {501:1001}]
# Интерпретация (DSACK): Подтвержден кумулятивный 1001, 
# и дополнительно сообщается, что блок 500-1000 был получен повторно.
```

### Сценарий 2: Мониторинг статистики ACK в Linux
Использование `nstat` (замена `netstat -s`) для анализа эффективности подтверждений:

```bash
# Просмотр счетчиков сжатия и задержек ACK
nstat -az TcpExtTCPACKCompressed TcpExtTCPACKDelayed
# → TcpExtTCPACKDelayed               5230         0.0
# → TcpExtTCPACKCompressed            142          0.0
```

### Сценарий 3: Проверка состояния QuickACK через ss
Утилита `ss` позволяет увидеть, находится ли сокет в режиме QuickACK (`ato` — ACK timeout):

```bash
ss -ti dst 1.2.3.4
# → cubic rto:204 rtt:15.2/0.5 ato:40 mss:1448 ...
```
- `ato:40`: Сокет готов отправить быстрый ACK через 40 мс (стандарт для QuickACK).
- `ato:200`: Сокет использует классический Delayed ACK.
