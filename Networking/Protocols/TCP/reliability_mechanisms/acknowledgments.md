# Подтверждения в TCP (Acknowledgments)

## Определения

**Подтверждение (Acknowledgment, ACK)** — основной механизм обратной связи в протоколе TCP, уведомляющий отправителя об успешном приеме потока байтов. Реализуется через установку битового флага **ACK** в заголовке и указание 32-битного **Acknowledgment Number**.

**Кумулятивное подтверждение (Cumulative ACK):** Схема, при которой `Acknowledgment Number` указывает на порядковый номер следующего байта, который получатель ожидает увидеть. Все байты с номерами меньше этого значения официально считаются принятыми и могут быть удалены из буфера отправителя.

---

## Базовые концепции

### 1. Механизм подтверждения байтов
TCP подтверждает порядковые номера байтов, а не пакеты.
- Если получены байты 1–1000 и 1001–2000, получатель отвечает `ACK 2001`.
- Если сегмент 1–1000 потерян, но 1001–2000 доставлен, получатель обязан отвечать `ACK 1` (или номер последнего подтвержденного байта), генерируя **Duplicate ACK** (дублирующее подтверждение).

### 2. Отложенные подтверждения (Delayed ACK)
Механизм оптимизации (RFC 1122), снижающий накладные расходы на передачу мелких ACK-пакетов.
- **Piggybacking:** Получатель задерживает отправку ACK (в Linux по умолчанию до **200 мс**, минимум **40 мс**), надеясь «прикрепить» подтверждение к ответному пакету данных (например, HTTP-ответу).
- **Порог подтверждения:** Если данных для отправки нет, получатель обязан отправить ACK после получения каждого второго сегмента размера MSS.
- **Конфликт с алгоритмом Нагла:** Сочетание Delayed ACK и Nagle может приводить к задержкам ровно в 200 мс. Подробнее см. [Алгоритм Нагла](../tcp_nagle_algorithm.md).

### 3. Режим QuickACK в Linux
В определенных ситуациях Linux отключает задержку и переходит в режим немедленных подтверждений:
- Во время трехэтапного рукопожатия (**3-way Handshake**).
- Сразу после обнаружения потери (для ускорения Fast Retransmit).
- Если приложение явно запросило это через опцию сокета `TCP_QUICKACK`.

### 4. Выборочные подтверждения (SACK)
При множественных потерях в одном окне кумулятивный ACK неэффективен, так как отправитель не знает, какие данные за пределами разрыва дошли до цели.
- **SACK (RFC 2018):** Опция в заголовке TCP, содержащая до 4-х блоков (Left/Right Edge) успешно принятых нецелостных данных.
- **DSACK (Duplicate SACK):** Сообщает отправителю, что получен дубликат сегмента. Позволяет отличить реальную потерю от переупорядочивания или ложной ретрансмиссии.

### 5. ACK Clocking (Синхронизация по подтверждениям)
Подтверждения служат «метрономом» для отправителя. Приход каждого нового ACK открывает окно (`cwnd`) и позволяет отправить новые данные, что поддерживает стабильный темп передачи (self-clocking).

## Практические сценарии

### Сценарий 1: Анализ SACK в tcpdump
Наличие SACK-блоков в дампе — признак потерь в сети.

```bash
sudo tcpdump -ni any 'tcp' -v
# → ... ack 1001, options [nop,nop,sack 1 {2001:3001}]
```
# → Результат: Получатель подтверждает получение блока 2001–3000, но все еще ждет байт 1001 (разрыв в данных).

### Сценарий 2: Мониторинг задержек ACK через ss
Утилита `ss` показывает параметр `ato` (Acknowledgment Timeout).

```bash
ss -ti dst 8.8.8.8
# → cubic rto:204 rtt:15.2/0.5 ato:40 cwnd:10
```
- **ato:40:** Сокет в режиме QuickACK (малая задержка).
- **ato:200:** Сокет использует стандартный Delayed ACK.

### Сценарий 3: Глобальная статистика через nstat
Анализ эффективности работы механизмов подтверждения:

```bash
nstat -az TcpExtTCPACKCompressed TcpExtTCPACKDelayed
# → TcpExtTCPACKDelayed               5230         0.0
# → TcpExtTCPACKCompressed            142          0.0
```
- **TCPACKCompressed:** Количество «склеенных» подтверждений (ACK Compression), признак высокой нагрузки на CPU или сеть.
