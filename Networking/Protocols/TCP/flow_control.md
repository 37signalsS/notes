# Управление потоком в TCP (Flow Control)

## Определения

**Управление потоком (Flow Control)** — механизм TCP, предотвращающий переполнение буфера получателя путём ограничения скорости передачи данных отправителем.

**Ключевое отличие от Congestion Control:**
- **Flow Control:** защита **получателя** (receiver-centric)
- **Congestion Control:** защита **сети** (network-centric)

**Реализация:** поле [Window Size](./header_format.md#7-размер-окна-window-size-16-бит) в заголовке TCP.

---

## Основные концепции

### Механизм работы

**Принцип:** получатель явно указывает, сколько данных он готов принять.

```
Отправитель                          Получатель
     |                                    |
     |  Данные (1000 байт) -------------> |  Буфер: 4000/5000 байт
     |                                    |  Свободно: 1000 байт
     |  <--- ACK, Window = 1000 --------- |  (указывает свободное место)
     |                                    |
     |  Данные (1000 байт) -------------> |  Буфер: 5000/5000 байт
     |                                    |  Свободно: 0 байт
     |  <--- ACK, Window = 0 ------------ |  (STOP!)
     |                                    |
     |  [Ожидание]                        |  [Чтение приложением]
     |                                    |  Буфер: 3000/5000 байт
     |  <--- ACK, Window = 2000 --------- |  Свободно: 2000 байт
     |                                    |
     |  Данные (2000 байт) -------------> |
```

### Receiver Window (rwnd)

**rwnd (receiver window)** — текущий размер окна, объявленный получателем.

**Формула доступного окна:**
```
Доступное окно = min(cwnd, rwnd)

где:
  cwnd — окно перегрузки (congestion window)
  rwnd — окно получателя (receiver window)
```

**В заголовке TCP:**
- Поле `Window Size` = 16 бит → максимум 65535 байт
- С опцией [Window Scale](./header_format.md#масштаб-окна-window-scale) → до 1 ГБ

---

### Zero Window (нулевое окно)

**Сценарий:** буфер получателя полностью заполнен.

**Действия получателя:**
- Отправляет `ACK` с `Window = 0`
- Отправитель **прекращает** передачу данных

**Проблема:** если следующий ACK с ненулевым окном потерян, отправитель будет ждать вечно.

---

### Зондаж нулевого окна (Zero-Window Probe)

**Механизм предотвращения deadlock:**

1. Отправитель запускает **persist timer** при получении `Window = 0`
2. По истечении таймера отправляет **probe-сегмент** (1 байт данных)
3. Получатель обязан ответить `ACK` с актуальным размером окна
4. Если окно всё ещё 0 — таймер перезапускается (экспоненциальное увеличение)

```
Отправитель                          Получатель
     |                                    |
     |  <--- ACK, Window = 0 ------------ |
     |  [Persist Timer: 60 сек]           |
     |                                    |
     |  Probe (1 байт) -----------------> |  Буфер: 5000/5000
     |  <--- ACK, Window = 0 ------------ |  (всё ещё полно)
     |  [Persist Timer: 120 сек]          |
     |                                    |  [Приложение читает данные]
     |                                    |  Буфер: 3000/5000
     |  Probe (1 байт) -----------------> |
     |  <--- ACK, Window = 2000 --------- |
     |  [Возобновление передачи]          |
```

**Настройка в Linux:**
```bash
# Минимальный интервал probe (по умолчанию 1 сек)
net.ipv4.tcp_probe_interval

# Максимальный интервал (экспоненциальный backoff)
net.ipv4.tcp_probe_threshold
```

---

### Скользящее окно (Sliding Window)

**Концепция:** отправитель может передавать несколько сегментов без ожидания ACK.

**Параметры окна:**
```
                    Скользящее окно
         ◄─────────────────────────────►
         ┌─────────────────────────────┐
         │  Отправлено, не подтверждено│
         ├─────────────────────────────┤
         │  Можно отправить           │
         ├─────────────────────────────┤
         │  Нельзя (за границей окна) │
         └─────────────────────────────┘
Last ACK ◄───► Last Sent            ◄───► Last ACK + Window
```

**Пример:**
```
Поток байт:  0    1000   2000   3000   4000   5000   6000
             │------│------│------│------│------│------│
                    ▲                       ▲
                    │                       │
              Last ACK (1000)         Last Sent (5000)
              
Window = 4000 байт
Можно отправить: 5000 → 5000+4000 = 9000
```

**«Скольжение»:** при получении ACK левая граница сдвигается вправо.

## Взаимосвязь Flow Control и Congestion Control

**Важно:** это **разные механизмы** с разными целями.

| Характеристика | Flow Control | Congestion Control |
| :--- | :--- | :--- |
| **Цель** | Защита получателя | Защита сети |
| **Параметр** | rwnd (receiver window) | cwnd (congestion window) |
| **Кто контролирует** | Получатель | Отправитель |
| **Причина ограничения** | Мало буфера у получателя | Перегрузка в сети |
| **Механизм** | Window Size в ACK | Алгоритмы (Slow Start, AIMD) |

**Итоговое окно отправки:**
```
Effective Window = min(cwnd, rwnd)
```

**Сценарии:**

| Ситуация | cwnd | rwnd | Effective Window | Ограничитель |
| :--- | :--- | :--- | :--- | :--- |
| Быстрый получатель, свободная сеть | 50000 | 100000 | 50000 | Congestion |
| Медленный получатель, свободная сеть | 50000 | 10000 | 10000 | Flow |
| Быстрый получатель, перегрузка | 5000 | 100000 | 5000 | Congestion |
| Медленный получатель, перегрузка | 5000 | 1000 | 1000 | Flow |

## Практические сценарии

### Диагностика через ss

```bash
# Показать окна отправителя и получателя
ss -tmo

# Пример вывода:
# ESTAB  0  0  192.168.1.10:443  10.0.0.5:54321
#   cubic wscale:7,7 rto:204 rtt:0.5/0.25
#   ato:40 mss:1460 pmtu:1500 rcvmss:1460 advmss:1460 cwnd:10
#   bytes_acked:1000 bytes_received:2000
#   segs_out:10 segs_in:5
#   send 100.0Mbps  rcvspace:262640  rcv_rtt:0.5
```

**Поля:**
- `rcvspace` — размер receive buffer (влияет на rwnd)
- `cwnd` — текущее окно перегрузки
- `advmss` — объявленный MSS

---

### Zero Window в production

**Симптом:** приложение медленно читает данные, TCP-окно падает до 0.

**Диагностика:**
```bash
# Поиск сокетов с нулевым окном
ss -tmo | grep 'window:0'

# Мониторинг в реальном времени
watch -n1 'ss -tmo | grep -c "window:0"'
```

**Причины:**
- Приложение не успевает читать из сокета
- Блокировка на уровне приложения (GC, locks, I/O)
- Недостаточный размер буфера (`SO_RCVBUF`)

**Решение:**
1. Оптимизировать приложение (быстрее читать)
2. Увеличить буфер:
   ```bash
   sysctl -w net.ipv4.tcp_rmem='4096 87380 16777216'
   ```

---

### Настройка буферов TCP

**Параметры Linux:**

```bash
# Максимальный размер receive buffer
sysctl -w net.core.rmem_max=16777216

# Максимальный размер send buffer
sysctl -w net.core.wmem_max=16777216

# Min, default, max для TCP receive
sysctl -w net.ipv4.tcp_rmem='4096 87380 16777216'

# Min, default, max для TCP send
sysctl -w net.ipv4.tcp_wmem='4096 65536 16777216'
```

**Автотюнинг:** современные ядра Linux автоматически настраивают размер буфера в пределах указанных значений.

### Window Scaling в действии

**Проверка поддержки:**
```bash
# Проверка wscale на активных соединениях
ss -tno | grep wscale

# Пример:
# wscale:7,7  (отправитель:7, получатель:7)
```

**Расчет реального окна:**
```
Window Size в заголовке: 65535
Window Scale: 7 (2^7 = 128)
Реальное окно: 65535 × 128 = 8 388 480 байт (~8 МБ)
```

**Без window scaling:**
```
Максимум: 65535 байт (~64 КБ)
При RTT=100ms: 64KB / 0.1s = 640 KB/s (~5 Мбит/с)
```

**С window scaling:**
```
Максимум: ~1 ГБ
При RTT=100ms: 1GB / 0.1s = 10 GB/s (~80 Гбит/с)
```

### Проблемы и решения

| Проблема | Симптом | Решение |
| :--- | :--- | :--- |
| **Zero Window** | Остановка передачи, `window:0` в ss | Оптимизировать чтение приложения |
| **Малое окно** | Низкая пропускная способность | Увеличить `tcp_rmem`, включить window scaling |
| **Deadlock** | Вечное ожидание при Window=0 | Zero-window probe (автоматически) |

### Формулы

**Максимальная пропускная способность:**
```
Throughput ≤ Window Size / RTT

Пример:
Window = 64 KB, RTT = 100 ms
Throughput ≤ 65536 / 0.1 = 655360 байт/с ≈ 5.2 Мбит/с
```

**Требуемый размер окна для заданной пропускной способности:**
```
Window ≥ Throughput × RTT

Пример:
Throughput = 1 Гбит/с, RTT = 50 ms
Window ≥ 125000000 × 0.05 = 6 250 000 байт (~6 МБ)
```
