# Управление перегрузкой в TCP (Congestion Control)

## Определения

**Congestion Control** — механизм TCP для предотвращения перегрузки сети путём адаптации скорости передачи к доступной пропускной способности канала.

**Ключевое отличие от [Flow Control](./flow_control.md):**
- **Congestion Control:** защита **сети** (network-centric), параметр `cwnd`
- **Flow Control:** защита **получателя** (receiver-centric), параметр `rwnd`

**Итоговое окно отправки:**
```
Effective Window = min(cwnd, rwnd)
```

---

## Основные концепции

### Окно перегрузки (Congestion Window, cwnd)

**cwnd** — переменная состояния TCP на стороне отправителя, ограничивающая объём данных, которые могут быть отправлены без подтверждения.

**Принцип работы:**
```
Отправитель                          Сеть                           Получатель
     |                                |                                 |
     |  cwnd = 10 MSS                 |  Пропускная способность: ?      |
     |  [Отправка 10 сегментов] ----->|                                 |
     |                                |                                 |
     |  <---- ACK (10 сегментов) -----|                                 |
     |  cwnd = 20 MSS (Slow Start)    |                                 |
     |  [Отправка 20 сегментов] ----->|                                 |
     |                                |                                 |
     |  <---- ACK (потеря 1 пакет) ---|  Перегрузка! Потеря пакета      |
     |  cwnd = 10 MSS (AIMD)          |                                 |
```

**Единицы:** измеряется в **MSS (Maximum Segment Size)**.

---

### Ключевые алгоритмы

#### 1. Медленный старт (Slow Start)

**Цель:** быстро определить доступную пропускную способность при старте соединения.

**Механизм:**
- **Начальное значение:** `initcwnd = 10 MSS` (RFC 5681, ~14.6 КБ)
- **Рост:** экспоненциальный (+1 MSS на каждый ACK)
- **Завершение:** при достижении `ssthresh` или потере пакета

**Динамика роста:**
```
RTT 0:  cwnd = 10 MSS   (отправка 10 сегментов)
RTT 1:  cwnd = 20 MSS   (получено 10 ACK, +10 MSS)
RTT 2:  cwnd = 40 MSS   (получено 20 ACK, +20 MSS)
RTT 3:  cwnd = 80 MSS   (получено 40 ACK, +40 MSS)
...
```

**Почему «медленный»:** название историческое, на самом деле рост быстрый (экспоненциальный).

---

#### 2. Избегание перегрузки (Congestion Avoidance, AIMD)

**AIMD (Additive Increase Multiplicative Decrease)** — алгоритм работы после достижения порога `ssthresh`.

**Механизм:**
- **Additive Increase:** +1 MSS на RTT (линейный рост)
- **Multiplicative Decrease:** при потере пакета `cwnd = cwnd / 2`

**Динамика:**
```
cwnd
  │
  │     ╱│       ╱───
  │    ╱ │      ╱
  │   ╱  │     ╱
  │  ╱   │    ╱
  │ ╱    │   ╱
  │╱     │  ╱
  └──────┴─┴─────────────► время
         │  │
         │  потеря (cwnd/2)
         ssthresh
         (Slow Start → AIMD)
```

**Порог ssthresh (slow start threshold):**
- Начальное значение: обычно 65535 байт
- При потере пакета: `ssthresh = cwnd / 2`

---

#### 3. Быстрое восстановление (Fast Recovery)

**Цель:** избежать полного сброса `cwnd` при единичных потерях.

**Триггер:** получение **3 дубликатов ACK** (DupACK).

**Алгоритм (RFC 5681):**
1. `ssthresh = cwnd / 2`
2. `cwnd = ssthresh + 3 MSS` (учитываем 3 сегмента, вышедшие из сети)
3. Переход в режим Congestion Avoidance (не Slow Start!)
4. При получении ACK для новых данных — выход из Fast Recovery

**Сравнение с тайм-аутом:**
| Событие | Реакция cwnd | Режим после |
| :--- | :--- | :--- |
| **3 DupACK** | `cwnd = cwnd / 2` | Congestion Avoidance |
| **RTO (тайм-аут)** | `cwnd = 1 MSS` | Slow Start |

---

### Алгоритмы Congestion Control

#### CUBIC (по умолчанию в Linux)

**Особенности:**
- Алгоритм по умолчанию в Linux, Windows, FreeBSD
- Функция роста зависит от **времени с момента последней потери**
- Агрессивнее AIMD на длинных каналах с большой задержкой

**Формула роста:**
```
W(t) = C × (t - K)³ + W_max

где:
  t — время с момента последней потери
  K — время до достижения W_max
  W_max — cwnd перед последней потерей
  C — константа масштабирования
```

**Преимущества:**
- Высокая утилизация каналов с большим BDP (Bandwidth-Delay Product)
- Стабильность в гетерогенных сетях

**Недостатки:**
- Может создавать очереди в буферах маршрутизаторов (bufferbloat)
- Менее эффективен в мобильных сетях с потерями

---

#### BBR (Bottleneck Bandwidth and Round-trip time)

**Разработчик:** Google (2016)

**Принцип:** модель сети на основе **пропускной способности** и **RTT**, а не потерь.

**Ключевые метрики:**
- **BDP (Bandwidth-Delay Product):** `max_bandwidth × min_rtt`
- **Target cwnd:** `BDP × gain`

**Фазы работы:**
1. **Startup:** агрессивный рост (как Slow Start, но быстрее)
2. **Drain:** очистка очереди, если создана
3. **ProbeBW:** циклическое изменение скорости для поиска оптимума
4. **ProbeRTT:** периодическое снижение cwnd для измерения min_rtt

**BBR версии:**

| Версия | Год | Улучшения |
| :--- | :--- | :--- |
| **BBRv1** | 2016 | Базовая версия |
| **BBRv2** | 2020 | Улучшена公平性 (fairness), ECN support |
| **BBRv3** | 2023+ | Дальнейшая оптимизация fairness |

**Включение BBR в Linux:**
```bash
# Проверка доступных алгоритмов
sysctl net.ipv4.tcp_available_congestion_control

# Включение BBR
sysctl -w net.ipv4.tcp_congestion_control=bbr

# Для ядра 4.9+ требуется модуль
modprobe tcp_bbr

# Проверка активного алгоритма
ss -ti | grep bbr
```

**Требования:**
- Ядро Linux ≥ 4.9 (BBRv1)
- Ядро Linux ≥ 5.18 (BBRv2/v3, зависит от дистрибутива)

#### Другие алгоритмы

| Алгоритм | Описание | Использование |
| :--- | :--- | :--- |

## «Правило 14 КБ»: Slow Start на практике

### Расчет initcwnd

**Стандарт (RFC 5681):** `initcwnd = 10 MSS`

**Для Ethernet:**
```
MTU = 1500 байт
IP Header = 20 байт
TCP Header = 20 байт
MSS = 1500 - 20 - 20 = 1460 байт

initcwnd = 10 × 1460 = 14 600 байт (~14.3 КБ)
```

### Влияние на загрузку веб-страниц

**Сценарий 1: Ресурс ≤ 14 КБ**

```
RTT 0: TCP Handshake (SYN, SYN-ACK, ACK)
RTT 1: Отправка всего ресурса (14 КБ ≤ initcwnd)
       Получение ACK
       
Итого: 2 RTT до полной загрузки
```

**Сценарий 2: Ресурс > 14 КБ (например, 15 КБ)**

```
RTT 0: TCP Handshake
RTT 1: Отправка 14 КБ, ожидание ACK
RTT 2: Отправка оставшегося 1 КБ, получение ACK

Итого: 3 RTT (на 50% дольше!)
```

**Вывод:** даже 1 лишний килобайт удваивает время загрузки после handshake.

### Оптимизация initcwnd

**Увеличение на сервере:**
```bash
# Проверка текущего значения
ip route show | grep initcwnd

# Установка initcwnd = 30 для маршрута по умолчанию
GATEWAY=$(ip route | grep default | awk '{print $3}')
DEVICE=$(ip route | grep default | awk '{print $5}')
ip route change default via $GATEWAY dev $DEVICE initcwnd 30
```

**Постоянная настройка:** добавить в `/etc/network/interfaces` или скрипт сети.

**CDN-провайдеры:**
- **Cloudflare:** initcwnd ≈ 30-40 MSS (~43-58 КБ)
- **Fastly:** initcwnd ≈ 30 MSS
- **Google:** использует BBR с адаптивным initcwnd

## Взаимодействие с другими протоколами

### TLS и задержка

**TLS 1.2:**
```
RTT 0: TCP Handshake
RTT 1: TLS ClientHello → ServerHello, Certificate
RTT 2: TLS ClientKeyExchange, Finished
RTT 3: Отправка данных (ограничена initcwnd)

Итого: 3 RTT до данных
```

**TLS 1.3:**
```
RTT 0: TCP Handshake
RTT 1: TLS ClientHello (с ключами) → ServerHello, Certificate, Finished
       Отправка данных (ограничена initcwnd)

Итого: 2 RTT до данных
```

**TLS 1.3 0-RTT (повторное подключение):**
```
RTT 0: Клиент отправляет данные сразу с ClientHello
       Сервер отвечает

Итого: 1 RTT (но есть риск replay-атак)
```

См. также: [TLS Handshake](../tls.md#процесс-рукопожатия-tls-handshake)

---

### HTTP/2 и HTTP/3

**HTTP/2 (поверх TCP):**
- Мультиплексирование запросов в одном соединении
- Устраняет head-of-line blocking на уровне приложения
- **Но:** первое соединение всё ещё ограничено TCP Slow Start

**HTTP/3 (QUIC поверх UDP):**
- Собственный congestion control (аналогичен TCP cwnd)
- Устраняет head-of-line blocking на транспортном уровне
- 0-RTT handshake (как TLS 1.3)
- Быстрее при потерях пакетов

## Практические сценарии

### Диагностика congestion control

```bash
# Показать активный алгоритм
sysctl net.ipv4.tcp_congestion_control

# Показать доступные алгоритмы
sysctl net.ipv4.tcp_available_congestion_control

# Детальная информация о сокетах
ss -tmo

# Пример вывода:
# cubic wscale:7,7 rto:204 rtt:0.5/0.25 cwnd:10
```

**Поля:**
- `cubic` — активный алгоритм
- `cwnd:10` — текущее окно перегрузки (10 MSS)
- `rtt:0.5/0.25` — RTT (среднее/отклонение)

---

### Выбор алгоритма

**Рекомендации:**

| Сценарий | Рекомендуемый алгоритм | Обоснование |
| :--- | :--- | :--- |
| **Веб-сервер (общий)** | `bbr` | Низкая задержка, хорошая пропускная способность |
| **ЦОД (data center)** | `dctcp` | Оптимизирован для низких задержек ЦОД |
| **Мобильные сети** | `bbr` или `westwood` | Устойчивость к потерям |
| **Высокоскоростные каналы (>1 Гбит/с)** | `bbr` | Лучшая утилизация BDP |
| **Совместимость (старые ядра)** | `cubic` | По умолчанию, стабилен |

**Настройка:**
```bash
# Включение BBR
echo "net.core.default_qdisc = fq" >> /etc/sysctl.conf
echo "net.ipv4.tcp_congestion_control = bbr" >> /etc/sysctl.conf
sysctl -p
```

### Packet Pacing

**Проблема:** отправка всех 10 пакетов `initcwnd` одной очередью вызывает краткосрочную перегрузку.

**Решение:** равномерная отправка пакетов во времени.

**Включение (BBR автоматически использует pacing):**
```bash
# Проверка
ethtool -k eth0 | grep pacing

# BBR автоматически включает pacing с ядром 4.x+
```

### Формулы

**Bandwidth-Delay Product (BDP):**
```
BDP = Bandwidth × RTT

Пример:
Bandwidth = 1 Гбит/с = 125 МБ/с
RTT = 50 мс = 0.05 с
BDP = 125 × 0.05 = 6.25 МБ
```

**Требуемое cwnd для полной утилизации:**
```
cwnd ≥ BDP / MSS

Пример:
BDP = 6.25 МБ = 6 553 600 байт
MSS = 1460 байт
cwnd ≥ 6 553 600 / 1460 ≈ 4489 MSS
```

**Максимальная пропускная способность при заданном cwnd:**
```
Throughput = (cwnd × MSS) / RTT

Пример:
cwnd = 100, MSS = 1460, RTT = 10 мс
Throughput = (100 × 1460) / 0.01 = 14 600 000 байт/с ≈ 117 Мбит/с
```

### Проблемы и решения

| Проблема | Симптом | Решение |
| :--- | :--- | :--- |
| **Низкая пропускная способность** | cwnd растёт медленно | Увеличить `initcwnd`, включить BBR |
| **Bufferbloat** | Высокая задержка при загрузке | BBR вместо CUBIC, fq_codel |
| **Частые потери** | cwnd постоянно падает | Проверить сеть, ECN |
| **Неравномерная скорость** | «Пиловидный» график cwnd | Нормально для AIMD, рассмотреть BBR |
