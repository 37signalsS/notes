# Управление TCP-соединением

## Определения

**Управление соединением (Connection Management)** — механизмы TCP для установки, поддержания и завершения надежного соединения между двумя узлами.

**Ключевые процессы:**
- **Handshake (трёхэтапное рукопожатие)** — установка соединения
- **Data Transfer** — двусторонняя передача данных
- **Termination (четырёхэтапное завершение)** — корректный разрыв соединения

**Состояния соединения:** 11 состояний конечного автомата TCP.

---

## Основные концепции

### Установка соединения: TCP Handshake

**Цель handshake:**
1. Убедиться, что обе стороны существуют и готовы к обмену данными
2. Согласовать начальные параметры (Sequence Numbers, MSS, Window Scale)
3. Выделить ресурсы (буферы, управляющие структуры)

**Процесс:** 3 сегмента (three-way handshake)

```
   Клиент                                     Сервер
     |                                            |
     |  SYN (seq=x) ----------------------------> |  LISTEN
     |      (Состояние: SYN_SENT)                 |      ↓
     |                                            |  SYN-RCVD
     |  <---------------------------- SYN-ACK ----|
     |           (seq=y, ack=x+1)                 |
     |                                            |
     |  ACK (seq=x+1, ack=y+1) -----------------> |
     |      (Состояние: ESTABLISHED)              |  (Состояние: ESTABLISHED)
     |                                            |
     |◄══════════ Передача данных ══════════════►|
```

#### Детальный алгоритм

**Шаг 1: SYN от клиента**

| Параметр | Значение |
| :--- | :--- |
| **Флаги** | `SYN=1` |
| **Sequence Number** | `seq=x` (случайный ISN) |
| **Опции** | MSS, Window Scale, SACK permitted, Timestamps |
| **Состояние клиента** | `SYN_SENT` |

**Назначение:** инициация соединения, отправка клиентских параметров.

---

**Шаг 2: SYN-ACK от сервера**

| Параметр | Значение |
| :--- | :--- |
| **Флаги** | `SYN=1, ACK=1` |
| **Sequence Number** | `seq=y` (случайный ISN сервера) |
| **Acknowledgment Number** | `ack=x+1` (подтверждение SYN клиента) |
| **Опции** | MSS, Window Scale, SACK permitted, Timestamps |
| **Состояние сервера** | `SYN_RECEIVED` |

**Варианты реакции сервера:**

| Ситуация | Реакция |
| :--- | :--- |
| **Порт открыт, ресурсы есть** | Отправить `SYN-ACK`, перейти в `SYN_RECEIVED` |
| **Порт закрыт** | Отправить `RST` |
| **Нет ресурсов** | Отправить `RST` или игнорировать |
| **SYN-cookie включен** | Отправить `SYN-ACK` без выделения памяти |

---

**Шаг 3: ACK от клиента**

| Параметр | Значение |
| :--- | :--- |
| **Флаги** | `ACK=1` |
| **Sequence Number** | `seq=x+1` |
| **Acknowledgment Number** | `ack=y+1` (подтверждение SYN сервера) |
| **Состояние клиента** | `ESTABLISHED` |

**Реакция сервера:**
- Получение `ACK` → переход в `ESTABLISHED`
- Тайм-аут без `ACK` → переход в `CLOSED`, сокет удаляется

---

#### Почему 3 этапа, а не 2?

**Проблема 2-этапного handshake:**
```
1. Клиент → SYN → Сервер
2. Сервер → SYN-ACK → Клиент
```

**Недостаток:** сервер не знает, получил ли клиент его `SYN-ACK`. Если `SYN-ACK` потерян, клиент будет ждать вечно, а сервер выделит ресурсы.

**Решение (3 этапа):**
- Третий `ACK` подтверждает, что клиент получил `SYN-ACK`
- Обе стороны уверены в готовности к передаче данных

---

### Завершение соединения

**Особенность:** TCP — полнодуплексный протокол, каждая сторона закрывается независимо.

**Процесс:** 4 сегмента (four-way termination)

```
   Сторона A                                Сторона B
     |                                            |
     |  FIN (seq=u) --------------------------->  |  ESTABLISHED
     |      (Состояние: FIN_WAIT_1)               |      ↓
     |                                            |  CLOSE_WAIT
     |  <---------------------- ACK (ack=u+1) ----|
     |      (Состояние: FIN_WAIT_2)               |  (Состояние: LAST_ACK)
     |                                            |
     |  ◄════ Данные от B к A ещё могут ════════► |
     |           передаваться                     |
     |                                            |
     |  <--------------------- FIN (seq=v) -------|
     |      (Состояние: TIME_WAIT)                |
     |                                            |
     |  ACK (ack=v+1) --------------------------> |
     |      (Состояние: TIME_WAIT)                |  (Состояние: CLOSED)
     |                                            |
     |  [Ожидание 2×MSL]                          |
     |      ↓                                     |
     |  CLOSED                                    |
```

#### Детальный алгоритм

**Шаг 1: FIN от инициатора закрытия**

| Параметр | Значение |
| :--- | :--- |
| **Флаги** | `FIN=1` |
| **Sequence Number** | `seq=u` (номер последнего байта + 1) |
| **Состояние** | `FIN_WAIT_1` |

**Важно:** `FIN` потребляет 1 номер последовательности (как SYN).

---

**Шаг 2: ACK от получателя FIN**

| Параметр | Значение |
| :--- | :--- |
| **Флаги** | `ACK=1` |
| **Acknowledgment Number** | `ack=u+1` |
| **Состояние инициатора** | `FIN_WAIT_2` |
| **Состояние получателя** | `CLOSE_WAIT` |

**Состояние CLOSE_WAIT:**
- Получатель FIN может ещё отправлять данные
- Приложение должно вызвать `close()` для отправки своего FIN
- **Проблема:** если приложение не закрывает сокет → зависание в `CLOSE_WAIT`

---

**Шаг 3: FIN от получателя**

| Параметр | Значение |
| :--- | :--- |
| **Флаги** | `FIN=1` |
| **Sequence Number** | `seq=v` |
| **Состояние** | `LAST_ACK` |

---

**Шаг 4: ACK от инициатора**

| Параметр | Значение |
| :--- | :--- |
| **Флаги** | `ACK=1` |
| **Acknowledgment Number** | `ack=v+1` |
| **Состояние** | `TIME_WAIT` |

---

### Состояния TCP-соединений

#### Полная таблица состояний

| Состояние | Описание | Кто переходит | Как выйти |
| :--- | :--- | :--- | :--- |
| **LISTEN** | Ожидание входящих подключений на порту | Сервер | Получение `SYN` → `SYN_RECEIVED` |
| **SYN_SENT** | Отправлен `SYN`, ожидание `SYN-ACK` | Клиент | Получение `SYN-ACK` → `ESTABLISHED` |
| **SYN_RECEIVED** | Отправлен `SYN-ACK`, ожидание `ACK` | Сервер | Получение `ACK` → `ESTABLISHED` |
| **ESTABLISHED** | Соединение установлено, передача данных | Обе стороны | Отправка `FIN` → `FIN_WAIT_1` или `CLOSE_WAIT` |
| **FIN_WAIT_1** | Отправлен `FIN`, ожидание `ACK` | Инициатор закрытия | Получение `ACK` → `FIN_WAIT_2` |
| **FIN_WAIT_2** | Получение `ACK` на `FIN`, ожидание `FIN` от другой стороны | Инициатор закрытия | Получение `FIN` → `TIME_WAIT` |
| **CLOSE_WAIT** | Получен `FIN` от удалённой стороны, ожидание закрытия приложения | Получатель FIN | Приложение вызывает `close()` → `LAST_ACK` |
| **CLOSING** | Одновременная отправка `FIN`, ожидание `ACK` | Обе стороны | Получение `ACK` → `TIME_WAIT` |
| **LAST_ACK** | Отправлен `FIN`, ожидание `ACK` | Получатель FIN | Получение `ACK` → `CLOSED` |
| **TIME_WAIT** | Завершение закрытия, ожидание истечения таймера | Инициатор закрытия | Истечение 2×MSL → `CLOSED` |
| **CLOSED** | Соединение закрыто, ресурсы освобождены | — | — |

---

#### Диаграмма состояний

```
                          +--------+
                          | CLOSED |
                          +---+----+
                              |
         +--------------------+--------------------+
         | (passive open)    | (active open)       |
         v                   v                     |
     +-------+           +--------+                |
     | LISTEN|           | SYN_SENT|               |
     +---+---+           +----+---+                |
         | (recv SYN)        | (recv SYN-ACK)      |
         v                   v                     |
     +-----------+       +--------+                |
     | SYN_RECEIVED|<----| SYN_SENT|               |
     +-----+-----+       +--------+                |
           | (recv ACK)    | (recv ACK)            |
           v               v                       |
       +-------------+     +-------------+         |
       | ESTABLISHED |<----| ESTABLISHED |         |
       +------+------+     +------+------+         |
              | (app close)      | (recv FIN)      |
              v                  v                 |
       +------------+      +------------+          |
       | FIN_WAIT_1 |      | CLOSE_WAIT |          |
       +-----+------+      +-----+------+          |
             | (recv ACK)        | (app close)     |
             v                   v                 |
       +------------+      +------------+          |
       | FIN_WAIT_2 |      | LAST_ACK   |          |
       +-----+------+      +-----+------+          |
             | (recv FIN)      | (recv ACK)        |
             v                 v                   |
       +------------+      +------------+          |
       | TIME_WAIT  |<-----| CLOSING    |----------+
       +-----+------+      +------------+
             | (2×MSL timeout)
             v
         +--------+
         | CLOSED |
         +--------+
```

#### Критичные состояния для диагностики

**1. CLOSE_WAIT (проблема на стороне сервера)**

**Симптом:** много сокетов в `CLOSE_WAIT`

**Причина:**
- Приложение не вызывает `close()` после получения FIN
- Утечка сокетов, исчерпание портов

**Диагностика:**
```bash
# Посчитать сокеты в CLOSE_WAIT
ss -tan 'state close-wait' | wc -l

# Найти процесс, владеющий сокетами
ss -tanp 'state close-wait'
```

**Решение:** исправить приложение (закрывать сокеты).

---

**2. TIME_WAIT (нормальное состояние)**

**Назначение:**
- Гарантия доставки последнего `ACK`
- Защита от старых дубликатов сегментов

**Длительность:** `2 × MSL (Maximum Segment Lifetime)`
- MSL = 120 секунд (рекомендация RFC)
- TIME_WAIT = 240 секунд (4 минуты)
- В Linux: `net.ipv4.tcp_fin_timeout` (по умолчанию 60 сек)

**Проблема:**
- На серверах с короткими соединениями (веб-серверы) порты быстро заканчиваются
- Диапазон эфемерных портов: 1024–65535 (~64K портов)

**Решение:**
```bash
# Разрешить reuse TIME_WAIT-сокетов (для исходящих соединений)
sysctl -w net.ipv4.tcp_tw_reuse=1

# Уменьшить таймер (не рекомендуется без необходимости)
sysctl -w net.ipv4.tcp_fin_timeout=15

# Расширить диапазон портов
sysctl -w net.ipv4.ip_local_port_range="1024 65535"
```

> **Важно:** `tcp_tw_recycle` удалён в ядре 4.12+ из-за проблем с NAT.

---

**3. SYN_RECV (возможная SYN-флуд атака)**

**Симптом:** много сокетов в `SYN_RECEIVED`

**Причина:**
- DDoS-атака (SYN flood)
- Клиенты не отправляют финальный `ACK`

**Диагностика:**
```bash
ss -tan 'state syn-recv' | wc -l
```

**Защита:**
```bash
# SYN cookies (включено по умолчанию)
sysctl -w net.ipv4.tcp_syncookies=1

# Увеличить SYN backlog
sysctl -w net.core.somaxconn=4096
sysctl -w net.ipv4.tcp_max_syn_backlog=4096
```

См. также: [SYN-флуд](../../Concepts/dos_ddos_overview.md#syn-флуд)

### Одновременное закрытие (Simultaneous Close)

**Сценарий:** обе стороны отправляют `FIN` одновременно

```
Сторона A                               Сторона B
     | (app close)                         | (app close)
     | FIN --------------------------------| FIN
     | FIN_WAIT_1                          | FIN_WAIT_1
     |                                     |
     | <---------------------------------  |
     | FIN                                 | FIN
     | CLOSING                             | CLOSING
     |                                     |
     | ACK ------------------------------->| ACK
     | TIME_WAIT                           | TIME_WAIT
     |                                     |
```

**Результат:** обе стороны переходят в `TIME_WAIT`.

## Практические сценарии

### Диагностика состояний через ss

```bash
# Все TCP-соединения с состояниями
ss -tan

# Состояния с процессами
ss -tanp

# Подсчёт по состояниям
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c

# Пример вывода:
#   1500 ESTAB
#     50 TIME-WAIT
#     10 CLOSE-WAIT
#      5 SYN-RECV
```

### Анализ handshake через tcpdump

```bash
# Перехват TCP-handshake
tcpdump -i eth0 -nn 'tcp port 80' -v

# Пример вывода handshake:
# 10:15:30.123456 IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [S], seq 1234567890
# 10:15:30.130000 IP 93.184.216.34.80 > 192.168.1.10.54321: Flags [S.], seq 987654321, ack 1234567891
# 10:15:30.135000 IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [.], ack 987654322
```

**Обозначения флагов:**
- `[S]` — SYN
- `[S.]` — SYN-ACK
- `[.]` — ACK
- `[F.]` — FIN-ACK
- `[R]` — RST

### TIME_WAIT на клиенте vs сервере

| Сценарий | Кто в TIME_WAIT | Почему |
| :--- | :--- | :--- |
| **Браузер загружает страницу** | Клиент | Клиент инициирует закрытие |
| **HTTP-сервер отдаёт файл** | Сервер (при active close) | Сервер закрывает после отдачи |
| **Keep-alive соединения** | Реже | Соединение переиспользуется |

**Оптимизация для клиентских соединений:**
```bash
# Для исходящих соединений (клиенты)
sysctl -w net.ipv4.tcp_tw_reuse=1
```

### Проблемы и решения

| Проблема | Симптом | Решение |
| :--- | :--- | :--- |
| **Утечка CLOSE_WAIT** | Много `CLOSE_WAIT` сокетов | Исправить приложение (закрывать сокеты) |
| **Исчерпание портов** | Ошибки `Cannot assign requested address` | `tcp_tw_reuse=1`, расширить `ip_local_port_range` |
| **SYN-флуд** | Много `SYN_RECV`, отказы | `tcp_syncookies=1`, увеличить backlog |
| **Долгий handshake** | Высокий RTT, потери | Увеличить `tcp_syn_retries`, проверить сеть |

| :--- | :--- | :--- |
| **MSL** | 120 сек (RFC) | — |

| **SYN retries** | 5 попыток | `tcp_syn_retries` |
| **FIN timeout** | 60 сек | `tcp_fin_timeout` |
