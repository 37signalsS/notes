# Диагностика управления перегрузкой TCP

## Определения

**Диагностика управления перегрузкой (Congestion Control Diagnostics)** — процесс мониторинга и анализа состояния TCP-соединений для выявления ограничений пропускной способности, вызванных состоянием сетевых узлов или работой алгоритмов управления окном перегрузки.

**Ключевые метрики:**

- **cwnd (Congestion Window):** окно перегрузки, определяющее количество сегментов, которые отправитель может передать без подтверждения. Ограничивает объем данных «в полете» (Inflight).
- **ssthresh (Slow Start Threshold):** порог, при котором алгоритм переходит из фазы экспоненциального роста (Slow Start) в фазу линейного избегания перегрузки (Congestion Avoidance).
- **RTT (Round-Trip Time) и mdev:** среднее время круговой задержки и его дисперсия. Резкий рост RTT под нагрузкой указывает на накопление очередей (Bufferbloat).
- **Delivery Rate / Bandwidth (BW):** реальная скорость доставки данных, измеренная на основе полученных ACK. Критично для алгоритмов BBR.
- **Retransmissions (Ретрансмиссии):** количество повторных передач. Включает как быстрые ретрансмиссии (Fast Retransmit), так и таймауты (RTO).

## Основные концепции

### Анализ состояния через утилиту ss

Основным инструментом диагностики в Linux является команда `ss` (Socket Statistics). Для детального анализа перегрузки используются флаги `-ti` (TCP info).

**Интерпретация вывода для анализа перегрузок:**

| Поле в ss | Описание | Диагностическое значение |
| :--- | :--- | :--- |
| **`cwnd`** | Текущее окно в MSS | Если `cwnd` мал при высоком RTT — сеть ограничивает поток. |
| **`ssthresh`** | Порог медленного старта | Если `cwnd < ssthresh`, идет фаза Slow Start (быстрый разгон). |
| **`retrans`** | `текущие/всего` | Высокое значение указывает на потери в канале. |
| **`rto`** | Retransmission Timeout | Значение > 200мс в локальных сетях — признак серьезных потерь. |
| **`app_limited`** | Индикатор простоя | TCP-стек может слать быстрее, но приложение не отдает данные. |
| **`backoff`** | Экспоненциальный откат | Признак серии неудачных попыток ретрансмиссии (полная потеря связи). |

**Пример анализа BBR (v3):**
```bash
ss -ti dst 1.2.3.4
# → bbr wscale:7,7 rto:204 rtt:15.2/0.5 cwnd:120 delivery_rate 120Mbps bw:125Mbps min_rtt:14.8 pacing_rate 130Mbps
```
*   `min_rtt` — базовая задержка канала без очередей.
*   `pacing_rate` — скорость, с которой ядро выпускает пакеты (требует дисциплины `fq`).

### Диагностика Bufferbloat

**Bufferbloat** — деградация латентности из-за раздутых буферов на промежуточном оборудовании.
- **Метод обнаружения:** Сравнение `rtt` и `min_rtt` (или `rtt` в покое).
- **Критерий:** Если под нагрузкой `rtt` вырастает в 5–10 раз относительно базового (напр. 20мс → 200мс), при этом потерь пакетов мало — это классический Bufferbloat.
- **Решение:** Использование BBR, который игнорирует наполнение буферов, или внедрение AQM (`fq_codel`, `cake`).

### Сигналы L4S и ECN (2026)

В современных сетях (RFC 9330) диагностика включает проверку флагов **ECN (Explicit Congestion Notification)**.
- **Сигнал:** Вместо потери пакета коммутатор выставляет бит **CE (Congestion Experienced)**.
- **Диагностика в ss:** Поле `ecn_ce` в выводе `ss -ti` (если поддерживается ядром) показывает количество сегментов, помеченных как «перегруженные».
- **Результат:** Алгоритм (напр. DCTCP или BBRv3) плавно снижает скорость, не дожидаясь отбрасывания пакетов.

## Практические сценарии

### Сценарий 1: Низкая скорость передачи («Потолок» cwnd)

**Симптом:** Скорость передачи стабильно низкая, канал недогружен.
**Диагностика:**
1.  Выполните `ss -ti`.
2.  Если `cwnd` застыл на значении 10 (initcwnd) — возможно, соединение постоянно переходит в режим простоя. Проверьте параметр `tcp_slow_start_after_idle`.
3.  Если `unacked` (неподтвержденные данные) равен `cwnd` — отправитель уперся в лимит окна перегрузки.
4.  Если `cwnd` растет, но скорость нет — проверьте `rcv_space` (окно приема).

### Сценарий 2: Пилообразная скорость на беспроводных каналах

**Симптом:** Скорость постоянно падает и медленно восстанавливается (на Wi-Fi/LTE).
**Диагностика:**
1.  Отследите `retrans` и `ssthresh`.
2.  Если `ssthresh` резко падает после каждой небольшой потери — алгоритм (CUBIC/Reno) принимает помехи за перегрузку сети.
**Решение:** Переключение на BBR, который более толерантен к случайным потерям, не связанным с переполнением буферов.

### Сценарий 3: Проверка эффективности Pacing

**Симптом:** Микро-всплески (bursts) трафика вызывают потери на коммутаторах с мелкими буферами.
**Диагностика:**
```bash
# Проверка, включен ли pacing_rate и соответствует ли он delivery_rate
ss -ti | grep pacing_rate

# Проверка дисциплины очереди (qdisc)
tc qdisc show dev eth0
```
Если используется BBR, но в `tc qdisc` нет `fq` (или `fq_codel` с поддержкой pacing), BBR будет работать неэффективно, отправляя пакеты пачками.

### Сценарий 4: Трассировка через eBPF (2026)

Для анализа причин изменения `cwnd` в реальном времени используются инструменты eBPF:
```bash
# Отслеживание ретрансмиссий с указанием функции ядра и причины
sudo tcpretrans

# Мониторинг RTT в виде гистограммы для выявления Tail Latency
sudo tcprtt -i 1 -d

# Трассировка изменений окна перегрузки
sudo tcpcongestion -c
```
