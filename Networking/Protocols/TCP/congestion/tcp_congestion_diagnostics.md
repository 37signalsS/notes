# Диагностика управления перегрузкой TCP

## Определения

**Диагностика управления перегрузкой (Congestion Control Diagnostics)** — процесс мониторинга и анализа состояния TCP-соединений для выявления ограничений пропускной способности, вызванных состоянием сетевых узлов или работой алгоритмов управления окном перегрузки.

**Ключевые метрики:**

- **cwnd (Congestion Window):** окно перегрузки, определяющее количество сегментов, которые отправитель может передать без подтверждения. Измеряется в MSS.
- **ssthresh (Slow Start Threshold):** порог, при котором алгоритм переходит из фазы Slow Start в фазу Congestion Avoidance.
- **RTT (Round-Trip Time):** время круговой задержки. Резкий рост RTT под нагрузкой указывает на накопление очередей (Bufferbloat).
- **Delivery Rate / Bandwidth (BW):** реальная скорость доставки данных, измеренная алгоритмом (особенно важно для BBR).
- **Retransmissions:** количество повторных передач. В `ss` отображается как `retrans:текущие/всего`.

## Основные концепции

### Анализ состояния через утилиту ss

Основным инструментом диагностики в Linux является команда `ss` (Socket Statistics).

**Пример для алгоритма CUBIC:**
```bash
ss -ti dst 1.2.3.4
# → cubic wscale:7,7 rto:204 rtt:15.2/0.5 cwnd:10 ssthresh:50 retrans:0/12
```

**Пример для алгоритма BBR (v1/v2/v3):**
```bash
ss -ti dst 1.2.3.4
# → bbr wscale:7,7 rto:204 rtt:15.2/0.5 cwnd:120 delivery_rate 120Mbps bw:125Mbps min_rtt:14.8
```

**Интерпретация специфичных полей BBR:**
- `bw`: Максимальная пропускная способность, измеренная за последний период.
- `min_rtt`: Минимальная задержка без учета очередей.
- `pacing_rate`: Скорость, с которой ядро «выпускает» пакеты. Должна быть близка к `bw`.

### Сигналы перегрузки

- **Loss-based (CUBIC, Reno):** реагируют на потерю пакетов. Если `retrans` растет, CUBIC резко уменьшает `cwnd` (мультипликативное уменьшение).
- **Model-based (BBR):** реагирует на изменение `delivery_rate` и `RTT`. BBR игнорирует случайные потери до определенного порога, стараясь работать на уровне BDP.

### Проблема Bufferbloat

**Bufferbloat** — избыточное накопление пакетов в буферах промежуточных устройств.
- **Диагностика:** Сравнение `rtt` и `min_rtt` в выводе `ss`. Если `rtt` значительно выше `min_rtt` (например, 150 мс против 20 мс), буферы переполнены.
- **Решение:** Переход на BBR или использование AQM-дисциплин (`fq_codel`, `cake`).

## Практические сценарии

### Сценарий 1: Низкая скорость при малом cwnd

**Симптом:** Скорость значительно ниже лимита, но потерь нет.
**Диагностика:**
1. Проверить `cwnd` в `ss -ti`. Если он замер на 10, возможно, соединение простаивает и сбрасывается к `initcwnd`.
2. Проверить `rwnd` (Receive Window) клиента: в `ss` это поле `rcv_space`. Если оно мало — ограничивает клиент.
**Решение:** Тюнинг `tcp_rmem` на клиенте или `tcp_wmem` на сервере.

### Сценарий 2: Диагностика случайных потерь

**Симптом:** «Пилообразный» график скорости на Wi-Fi или 4G/5G.
**Диагностика:**
```bash
ss -ti | grep -E "cubic|retrans"
# → cubic ... retrans:0/150
```
Если `retrans` растет, а RTT стабилен — это не перегрузка, а помехи. CUBIC ошибочно считает это перегрузкой и режет скорость.
**Решение:** Использование BBR, который устойчив к потерям до 20% (BBRv3).

### Сценарий 3: Проверка Pacing и FQ

**Симптом:** Высокий уровень потерь на входе в коммутаторы с маленькими буферами.
**Диагностика:**
Проверить, используется ли `fq` (Fair Queuing), без которого pacing неэффективен:
```bash
tc qdisc show dev eth0
# → qdisc fq 8001: root refcnt 2 limit 10000 nodes 1024 packets_per_tree 64
```
**Решение:** Установить `net.core.default_qdisc = fq` в `sysctl`.

### Сценарий 4: eBPF-мониторинг (2026)

Для глубокой диагностики без захвата трафика (tcpdump) используются инструменты eBPF:
```bash
# Мониторинг RTT в реальном времени
sudo tcprtt -i 1
# → msecs : count | distribution |

# Мониторинг причин изменения cwnd
sudo tcpcongestion
```
