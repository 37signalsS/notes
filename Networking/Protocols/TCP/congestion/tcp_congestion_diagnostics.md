# Диагностика управления перегрузкой TCP

## Определения

**Диагностика управления перегрузкой (Congestion Control Diagnostics)** — процесс мониторинга и анализа состояния TCP-соединений для выявления ограничений пропускной способности, вызванных состоянием сетевых узлов или работой алгоритмов управления окном перегрузки.

**Ключевые метрики:**

- **cwnd (Congestion Window):** окно перегрузки, определяющее количество сегментов, которые отправитель может передать без подтверждения.
- **ssthresh (Slow Start Threshold):** порог, при котором алгоритм переходит из фазы Slow Start в фазу Congestion Avoidance.
- **RTT (Round-Trip Time):** время круговой задержки. Резкий рост RTT под нагрузкой часто указывает на наличие очереди в буферах.
- **Pacing Rate:** скорость, с которой пакеты «выталкиваются» в сеть для предотвращения всплесков трафика (bursts).

## Основные концепции

### Анализ состояния через утилиту ss

Основным инструментом диагностики в Linux является команда `ss` с ключами `-ti` (подробная информация о TCP) или `-tmo` (с таймерами и параметрами оптимизации).

```bash
ss -tmo
# Пример вывода:
# cubic wscale:7,7 rto:204 rtt:0.5/0.25 cwnd:10 ssthresh:50 pacing_rate 1.2Gbps
```

**Интерпретация полей:**

- `cubic` / `bbr`: активный алгоритм управления перегрузкой.
- `cwnd:10`: текущее окно (в MSS). Маленькое значение при высоком RTT ограничивает скорость.
- `rtt:0.5/0.25`: среднее время задержки и его отклонение.
- `pacing_rate`: расчетная скорость передачи. Если она значительно ниже пропускной способности канала, возможна перегрузка.

### Сигналы перегрузки

Разные алгоритмы реагируют на разные сигналы:

- **Loss-based (CUBIC, Reno):** реагируют на потерю пакетов (ретрансмиссии). Если в выводе `ss` растёт счётчик `retrans`, это прямой сигнал для CUBIC уменьшить `cwnd`.
- **Delay-based / Model-based (BBR):** реагируют на рост RTT и изменение пропускной способности. BBR старается удерживать скорость чуть ниже уровня возникновения очередей.

### Проблема Bufferbloat

**Bufferbloat** — ситуация, когда сетевые буферы (на роутерах, свитчах) переполняются, что приводит к огромным задержкам RTT при сохранении высокой пропускной способности.

- **Признак:** RTT в покое составляет 10-20 мс, а при загрузке канала вырастает до 200-500 мс.
- **Решение:** использование BBR или настройка дисциплин очередей (AQM) типа `fq_codel` или `cake`.

## Практические сценарии

### Сценарий 1: Низкая скорость при «пустом» канале

**Симптом:** Пропускная способность сервера значительно ниже физического лимита, потерь пакетов нет.
**Диагностика:**

1. Проверить `cwnd` через `ss -ti`.
2. Если `cwnd` мал и не растёт, проверить `ssthresh`.
3. Возможно, соединение ограничено параметром `initcwnd` (см. [Оптимизация initcwnd](./tcp_initcwnd_and_optimization.md)).
4. Проверить `rwnd` (Receive Window) на стороне клиента — возможно, ограничение на стороне получателя (Flow Control).

### Сценарий 2: Диагностика Bufferbloat

**Симптом:** Интерактивные приложения (SSH, VoIP) начинают «лагать» при запуске тяжелой загрузки.
**Диагностика:**

```bash
# Запустить пинг параллельно с нагрузочным тестом
ping -i 0.2 <target_ip>
# Если время ответа резко возрастает — буферы переполнены.
```

**Решение:** Переключиться на BBR и использовать дисциплину очереди `fq`. Подробнее в [Алгоритмы в Linux](../../../../Linux/Networking/Concepts/tcp_tuning/tcp_congestion_algorithms.md).

### Сценарий 3: Анализ потерь и «пилообразного» графика

**Симптом:** Скорость передачи постоянно колеблется («пила» на графике).
**Диагностика:**

1. Посмотреть количество ретрансмиссий: `ss -ti | grep retrans`.
2. Если ретрансмиссии частые — CUBIC постоянно сбрасывает окно.
3. Проверить стабильность RTT. Если RTT стабилен, а потери есть — это могут быть случайные потери (характерно для Wi-Fi/LTE).
**Решение:** Для сетей со случайными потерями рекомендуется переход на BBR.

### Сценарий 4: Проверка работы Pacing

**Симптом:** Всплески трафика вызывают потери на промежуточном оборудовании с маленькими буферами.
**Диагностика:**

```bash
# Проверить, активен ли pacing для сокета
ss -ti | grep pacing_rate
```

**Решение:** Убедиться, что используется qdisc `fq`. Без `fq` параметр `pacing_rate` в `ss` может отображаться, но фактического сглаживания может не происходить (зависит от версии ядра).
