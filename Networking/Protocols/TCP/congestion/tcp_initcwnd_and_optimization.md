# Правило 14 КБ и оптимизация initcwnd

## Определения

**initcwnd (Initial Congestion Window)** — начальное окно перегрузки TCP, определяющее объём данных (в сегментах MSS), который отправитель может передать сразу после установления соединения, не дожидаясь подтверждений (ACK).

**Правило 14 КБ** — концепция оптимизации веб-производительности, основанная на стандарте `initcwnd = 10 MSS` (RFC 6928). Для стандартного Ethernet (MTU 1500) это составляет ~14.6 КБ. Если критически важные данные (HTML, Critical CSS) превышают этот лимит, для их доставки потребуется дополнительный цикл приема-передачи (RTT), что увеличивает время отрисовки страницы.

---

## Основные концепции

### Теоретический расчет

Размер `initcwnd` измеряется в MSS (Maximum Segment Size).

**Для стандартного Ethernet-канала:**
- **MTU:** 1500 байт.
- **Заголовки (IPv4 + TCP):** 40 байт.
- **MSS:** 1500 - 40 = 1460 байт.
- **initcwnd (10 MSS):** 10 × 1460 = 14 600 байт (~14.25 КБ).

### Влияние на Web Performance

При оптимальном размере ресурса (до 14 КБ) загрузка происходит за 1 RTT (после хендшейка):
1. **RTT 0:** TCP Handshake.
2. **RTT 1:** Отправка всего ресурса целиком.

Если ресурс больше лимита (например, 16 КБ), время загрузки удваивается:
1. **RTT 0:** TCP Handshake.
2. **RTT 1:** Отправка первых 14.6 КБ, ожидание ACK.
3. **RTT 2:** Отправка остатка данных.

### Особенности современных протоколов (2026)

- **TLS 1.3:** Сокращает время до начала передачи данных (1-RTT handshake). В сочетании с оптимизацией `initcwnd` позволяет доставить контент практически мгновенно.
- **HTTP/3 (QUIC):** Имеет собственный параметр `initial_window`. Хотя QUIC не использует TCP, логика «правила 14 КБ» сохраняется. В современных реализациях QUIC начальное окно часто устанавливается в 10–20 MSS по умолчанию.
- **BBRv3:** Алгоритм BBR более агрессивно оценивает пропускную способность, но `initcwnd` всё равно определяет объем данных в **первом** вылете. При использовании BBR рекомендуется устанавливать `initcwnd` в пределах 10–20 MSS, чтобы избежать переполнения буферов (bursting) при старте.

### Клиентская часть: initrwnd

Оптимизация на стороне сервера бесполезна, если клиент (браузер или мобильное устройство) имеет маленькое **Initial Receive Window (initrwnd)**. Если клиент сообщает `window size` меньше, чем серверный `initcwnd`, сервер будет ограничен значением клиента.

## Практические сценарии

### Сценарий 1: Оптимизация критического пути (Critical Path)

**Проблема:** Веб-страница отрисовывается медленно, так как основной CSS-бандл (18 КБ) не влезает в первый пакет.

**Решение:**
- Использование современных алгоритмов сжатия (**Brotli** на уровне 11) для уменьшения размера бандла до <14 КБ.
- Если сжатие недостаточно — увеличение `initcwnd` на сервере до 15–20 MSS.

### Сценарий 2: Настройка в Linux

Просмотр текущих настроек:
```bash
ip route show
# → default via 192.168.1.1 dev eth0 proto dhcp metric 100 
```

Проверка `initcwnd` для конкретного маршрута (через `ss` для активного сокета):
```bash
ss -ti
# → ... cwnd:10 ssthresh:50 ...
```

Временное изменение (сбросится после перезагрузки):
```bash
# Необходимо заменить <GW> и <DEV> на значения из 'ip route show'
sudo ip route change default via 192.168.1.1 dev eth0 initcwnd 20 initrwnd 20
```

### Сценарий 3: Масштабируемость и Pacing

При установке экстремально высоких значений `initcwnd` (например, 50–100 MSS для CDN), необходимо обязательное включение **Pacing**. Это сглаживает всплеск трафика, распределяя пакеты во времени, что предотвращает потери на промежуточных коммутаторах.
