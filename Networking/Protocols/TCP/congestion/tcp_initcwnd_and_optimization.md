# Правило 14 КБ и оптимизация initcwnd

## Определения

**initcwnd (Initial Congestion Window)** — начальное окно перегрузки TCP, определяющее объём данных (в сегментах MSS), который отправитель может передать сразу после установления соединения, не дожидаясь подтверждений (ACK) от получателя.

**Правило 14 КБ** — концепция оптимизации производительности веб-приложений, основанная на стандарте `initcwnd = 10 MSS` (RFC 6928). Поскольку один сегмент MSS в стандартном Ethernet-канале составляет 1460 байт, 10 таких сегментов позволяют передать ~14.26 КБ полезной нагрузки в первом «вылете». Если критические ресурсы (HTML, инлайновый CSS) укладываются в этот лимит, страница начинает отрисовываться на один RTT быстрее.

---

## Основные концепции

### Теоретический расчет и «Магия 14 КБ»

Размер `initcwnd` измеряется в единицах MSS (Maximum Segment Size), которые зависят от MTU канала.

**Расчет для стандартного Ethernet (MTU 1500):**
1. **MTU:** 1500 байт.
2. **Заголовки (IPv4 + TCP):** 40 байт (без учета опций).
3. **MSS:** 1500 - 40 = 1460 байт.
4. **initcwnd (10 MSS):** 10 × 1460 = **14 600 байт** (~14.25 КБ).

### Влияние на время отрисовки (TTFP)

Влияние `initcwnd` наиболее заметно на первом этапе загрузки страницы, когда TCP-соединение находится в фазе **Slow Start** (Медленный старт).

- **Ресурс < 14 КБ:** Передается за **1 RTT** (после завершения Handshake).
- **Ресурс > 14 КБ (например, 20 КБ):**
  1. Сервер отправляет первые 14.6 КБ.
  2. Сервер **останавливается** и ждет ACK от клиента.
  3. Получив ACK, сервер удваивает окно (согласно Slow Start) и досылает остаток.
  4. Итог: **2 RTT** на передачу критического контента.

### Контекст современных протоколов (2026)

- **TLS 1.3:** В сочетании с TLS 1.3 (0-RTT или 1-RTT Handshake), оптимизация `initcwnd` позволяет доставить первый байт данных (TTFB) и полезную нагрузку практически одновременно.
- **HTTP/3 (QUIC):** Хотя QUIC работает поверх UDP, он заимствует механизмы контроля перегрузки TCP. Параметр `initial_window` в QUIC также рекомендуется устанавливать в пределах 10–20 MSS (около 14–28 КБ), чтобы сбалансировать скорость старта и риск потери пакетов.
- **BBRv3:** Алгоритм BBR более эффективно использует полосу пропускания, но `initcwnd` по-прежнему критичен для первого пакета данных. При использовании BBRv3 высокие значения `initcwnd` (более 20) требуют обязательного включения **Pacing** на уровне ядра для предотвращения пакетных всплесков (bursts).

### Влияние Pacing на высокие значения initcwnd

При установке `initcwnd` выше 20–32 MSS сервер генерирует мощный всплеск трафика (burst). Если промежуточное оборудование имеет малые буферы, это приведет к мгновенным потерям.

**Решение:** Использование дисциплины очередей `fq` (Fair Queueing), которая реализует **Pacing** (равномерное распределение пакетов во времени). В современных ядрах Linux 6.x+ это является стандартом при использовании BBR.

### Параметр tcp_slow_start_after_idle

По умолчанию Linux сбрасывает окно перегрузки обратно к `initcwnd`, если соединение простаивало (один RTO). Для HTTP/1.1 с Keep-Alive или долгоживущих API-соединений это снижает производительность.

**Настройка:** `net.ipv4.tcp_slow_start_after_idle = 0` (через `sysctl`) предотвращает этот сброс.

## Практические сценарии

### Сценарий 1: Оптимизация критического пути отрисовки

**Проблема:** Веб-страница отрисовывается медленно, так как критический CSS весит 17 КБ.
**Диагностика:** Анализ через DevTools (Waterfall) показывает задержку (gap) в середине загрузки HTML/CSS, равную одному RTT.
**Решение:**
1.  **Сжатие:** Использование Brotli (уровень 11) для упаковки CSS в лимит 14 КБ.
2.  **Inlining:** Разделение CSS на критический (инлайнится в HTML до 14 КБ) и второстепенный (загружается асинхронно).
3.  **Серверный тюнинг:** Увеличение `initcwnd` до 15–20 MSS, если аудитория имеет качественные каналы связи.

### Сценарий 2: Ограничение со стороны клиента (initrwnd)

**Проблема:** Сервер настроен на `initcwnd 20`, но данные все равно приходят частями по 10 сегментов.
**Причина:** Параметр **initrwnd (Initial Receive Window)** на стороне клиента (браузера или мобильной ОС).
**Механизм:** TCP выбирает минимальное из двух окон: `Send Window = min(cwnd, rwnd)`. Если старое мобильное устройство или специфичный клиент заявляет `rwnd` в 10 MSS, серверный тюнинг будет игнорироваться.

### Сценарий 3: Настройка в высокопроизводительных сетях (CDN)

Для CDN и внутренних API, работающих в сетях с очень низким процентом потерь, `initcwnd` может быть увеличен до 32 MSS (стандарт 2026 года для некоторых вендоров). Это позволяет отдавать большинство современных JSON-ответов и небольших иконок за 1 RTT.

### Сценарий 4: Диагностика ограничения initrwnd на клиенте

**Проблема:** Сервер настроен на высокий `initcwnd`, но клиент получает данные частями по 10 сегментов.

**Диагностика:**
```bash
# На сервере — проверка установленных соединений
ss -tin state established dst <client_ip>

# Вывод покажет: cwnd:32 rwnd:10
# rwnd:10 означает, что клиент заявляет маленькое окно приема
```

**Решение:**
- Обновить прошивку/ОС на клиентском устройстве
- Настроить `initrwnd` на сервере (влияет только на собственные соединения клиента)
- Для серверов, обслуживающих старые клиенты — оставить `initcwnd 10` для совместимости

## Настройка initcwnd в Linux

### Ключевая особенность реализации

В Linux `initcwnd` настраивается не через глобальные параметры `sysctl`, а индивидуально для каждого маршрута (route). Это позволяет задавать разные окна для разных интерфейсов или направлений (например, локальная сеть vs интернет).

### Проверка текущего значения

Если параметр не указан явно, ядро использует дефолт (10 MSS):

```bash
# Просмотр параметров маршрутов
ip route show

# Детальный просмотр для конкретного интерфейса
ip route show dev eth0
# → default via 192.168.1.1 dev eth0 proto dhcp metric 100 initcwnd 32 initrwnd 32
```

### Временная настройка (iproute2)

Изменения вступают в силу немедленно для новых соединений:

```bash
# Автоматическое определение шлюза и интерфейса
GATEWAY=$(ip route | grep default | awk '{print $3}')
DEVICE=$(ip route | grep default | awk '{print $5}')

# Установка initcwnd=32 и initrwnd=32 (стандарт для широкополосных сетей 2026 года)
sudo ip route change default via "$GATEWAY" dev "$DEVICE" initcwnd 32 initrwnd 32

# Настройка для IPv6
sudo ip -6 route change default via fe80::1 dev eth0 initcwnd 32 initrwnd 32
```

### Постоянное сохранение настроек

#### Через Netplan (Ubuntu 24.04+)

```yaml
# /etc/netplan/01-netcfg.yaml
network:
  version: 2
  ethernets:
    enp1s0:
      dhcp4: true
      routes:
        - to: default
          via: 192.168.1.1
          congestion-window: 32
          advertised-receive-window: 32
```

#### Через systemd-networkd

```ini
# /etc/systemd/network/10-eth0.network
[Match]
Name=eth0

[Network]
DHCP=ipv4

[Route]
Gateway=_dhcp4
InitialCongestionWindow=32
InitialAdvertisedReceiveWindow=32
```

#### Через NetworkManager (nmcli)

```bash
# Изменение существующего соединения
sudo nmcli connection modify "Wired connection 1" \
    +ipv4.routes "0.0.0.0/0 192.168.1.1 initcwnd=32 initrwnd=32"

# Применение
sudo nmcli connection up "Wired connection 1"
```

### Мониторинг активных сессий

```bash
# Просмотр cwnd и rtt для установленных соединений
ss -tin state established

# Фильтрация конкретных значений
ss -tin state established | grep -oE 'cwnd:[0-9]+|rtt:[0-9.]+'

# Проверка статистики перегрузок
nstat -az | grep -i cwnd
```

### Рекомендуемые значения initcwnd

| Значение | Эквивалент | Сценарий применения |
| :--- | :--- | :--- |
| **10 MSS** | ~14.6 КБ | Стандарт RFC. Идеально для мобильных сетей и спутниковых каналов. |
| **32 MSS** | ~46.7 КБ | Стандарт 2026 года. Покрывает большинство Web/API запросов за 1 RTT. |
| **64 MSS** | ~93.4 КБ | Высокоскоростные линки (1Гбит+) с RTT > 20мс. Требует Pacing. |
| **100+ MSS** | > 146 КБ | Экстремальные значения. Могут вызвать переполнение буферов на старых роутерах. |

### Взаимодействие с BBR (v3)

Алгоритм **BBR (Bottleneck Bandwidth and RTT)** использует собственную оценку полосы, но `initcwnd` всё равно определяет объем данных в **первом** вылете пакетов. В современных облачных сетях сочетание `BBRv3` + `initcwnd 32` + `fq` (Pacing) дает наилучшие результаты для минимизации Time To First Byte (TTFB).

### Стандарты (RFC)

- **RFC 6928:** Increasing TCP's Initial Window (основной стандарт IW10).
- **RFC 9000:** QUIC: A UDP-Based Multiplexed and Secure Transport (начальные окна в QUIC).
- **RFC 3390:** Increasing TCP's Initial Window (устаревший стандарт IW3-4).
- **RFC 5681:** TCP Congestion Control (фундаментальный стандарт управления перегрузкой).
