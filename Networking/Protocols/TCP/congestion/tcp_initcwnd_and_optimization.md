# Правило 14 КБ и оптимизация initcwnd

## Определения

**initcwnd (Initial Congestion Window)** — начальное окно перегрузки TCP, определяющее объём данных, который отправитель может передать сразу после установления соединения, не дожидаясь подтверждений (ACK) и не проходя начальные фазы экспоненциального роста Slow Start.

**Правило 14 КБ** — концепция, основанная на стандарте `initcwnd = 10 MSS` (RFC 5681). Для сетей Ethernet с MTU 1500 байт это составляет примерно 14.6 КБ. Если критически важная часть веб-страницы (например, начальный HTML и встроенный CSS) превышает этот размер даже на 1 байт, для её доставки потребуется дополнительный цикл приема-передачи (RTT).

---

## Основные концепции

### Теоретический расчет

Стандарт RFC 5681 устанавливает начальное окно в 10 сегментов MSS (Maximum Segment Size).

**Для стандартного Ethernet-канала:**
- **MTU:** 1500 байт.
- **Заголовки (IP + TCP):** 40 байт (без учета опций).
- **MSS:** 1500 - 40 = 1460 байт.
- **Итоговый initcwnd:** 10 × 1460 = 14 600 байт (~14.25 КБ).

### Влияние на скорость загрузки (Web Performance)

При оптимальном размере ресурса (до 14 КБ) загрузка происходит максимально быстро:
1. **RTT 0:** TCP Handshake (SYN -> SYN-ACK -> ACK).
2. **RTT 1:** Отправка всего ресурса целиком, получение подтверждения.

Если ресурс больше 14 КБ (например, 16 КБ), время загрузки увеличивается на 50% и более:
1. **RTT 0:** TCP Handshake.
2. **RTT 1:** Отправка первых 14.6 КБ, ожидание подтверждения.
3. **RTT 2:** Отправка оставшихся данных, получение подтверждения.

### Взаимодействие с протоколами TLS и HTTP

`initcwnd` ограничивает данные прикладного уровня, которые могут быть отправлены сразу после завершения рукопожатия.

- **TLS 1.2:** требует 2 дополнительных RTT для согласования ключей до начала передачи данных.
- **TLS 1.3:** сокращает задержку до 1 RTT, позволяя начать передачу данных одновременно с завершением рукопожатия.
- **HTTP/3 (QUIC):** использует механизмы управления перегрузкой, аналогичные TCP, но интегрирует рукопожатие TLS 1.3 непосредственно в транспортный уровень, что минимизирует влияние `initcwnd` на старт соединения.

### Практика CDN-провайдеров

Крупные сети доставки контента часто используют увеличенные значения `initcwnd` для минимизации задержек:
- **Cloudflare:** обычно 30–40 MSS.
- **Fastly:** около 30 MSS.
- **Google:** использует алгоритм BBR, который может динамически адаптировать параметры передачи.

## Практические сценарии

### Сценарий 1: Оптимизация доставки критического пути (Critical Path)

**Проблема:** Основной HTML-файл имеет размер 18 КБ, что вызывает лишний RTT на мобильных сетях с высокой задержкой.

**Решение:**
- Оптимизация и сжатие (Gzip/Brotli) для возврата в лимит 14 КБ.
- Если сжатие не помогает — увеличение `initcwnd` на стороне сервера до 20–30 MSS.

### Сценарий 2: Настройка initcwnd в Linux

Для изменения значения на работающей системе используется утилита `ip route`.

```bash
# Проверка текущего значения для маршрута по умолчанию
ip route show | grep initcwnd

# Увеличение до 30 MSS
# Необходимо указать шлюз и интерфейс из вывода 'ip route show default'
sudo ip route change default via <GATEWAY> dev <DEVICE> initcwnd 30
```

*Подробные инструкции по сохранению настроек и диагностике в Linux приведены в разделе [Настройка initcwnd в Linux](../../../../Linux/Networking/Concepts/tcp_tuning/tcp_initcwnd.md).*

### Сценарий 3: Использование Pacing при больших окнах

**Проблема:** Увеличение `initcwnd` до 50+ MSS может вызвать резкий всплеск трафика (burst), приводящий к потере пакетов на промежуточном оборудовании с маленькими буферами.

**Решение:** Включение механизма Pacing (равномерное распределение пакетов во времени), что является стандартным поведением при использовании алгоритма BBR.
