# Алгоритмы управления перегрузкой TCP

## Определения

**Алгоритм управления перегрузкой (Congestion Control Algorithm)** — программная реализация логики управления окном перегрузки (`cwnd`) в протоколе TCP. Он определяет, как отправитель должен изменять скорость передачи данных в ответ на сигналы о состоянии сети (потери пакетов, изменение задержки или явные уведомления о перегрузке).

**Ключевые подходы:**

- **Loss-based (Reno, CUBIC):** используют потерю пакетов (Duplicate ACK или таймаут) как основной сигнал для уменьшения скорости.
- **Delay-based (Vegas, Vegas+):** используют рост задержки RTT для проактивного обнаружения перегрузки до возникновения потерь.
- **Model-based (BBR):** строят динамическую модель сети, измеряя максимальную пропускную способность и минимальную задержку.
- **ECN-based (DCTCP):** используют явные уведомления от сетевого оборудования (Explicit Congestion Notification) для точной регулировки окна.

**Справочная информация:** базовые механизмы Slow Start, AIMD и Fast Recovery описаны в [Обзоре управления перегрузкой](./tcp_congestion_control_overview.md).

## Основные концепции

### Эволюция алгоритмов

| Поколение | Алгоритмы | Сигнал перегрузки | Период доминирования |
| :--- | :--- | :--- | :--- |
| **1-е (классические)** | Tahoe, Reno, NewReno | Потеря пакетов (RTO / DupACK) | 1988–2003 |
| **2-е (гибридные)** | CUBIC, HTCP, Westwood | Потеря + время с момента последней потери | 2004–2015 |
| **3-е (модельные)** | BBR, Vegas | Доступная пропускная способность + RTT | 2016 – наст. время |

### CUBIC

CUBIC является алгоритмом по умолчанию в современных ОС: Linux (с 2.6.19), FreeBSD (с 10+), Windows (10 1709+, Server 2019+).

**Особенности:**

- **RTT-fairness:** Функция роста окна зависит от **времени с момента последней потери**, а не от RTT. Это позволяет потокам с разными задержками получать справедливую долю канала.
- **Агрессивность:** Эффективно использует пропускную способность в сетях с высоким BDP (Bandwidth-Delay Product), где классический Reno работает слишком медленно.

**Формула роста:**

```text
W(t) = C × (t - K)³ + W_max

где:
  t — время с момента последней потери;
  K — время, необходимое для достижения W_max в отсутствие потерь;
  W_max — размер окна перед последним событием перегрузки;
  C — константа масштабирования (обычно 0.4).
```

### BBR (Bottleneck Bandwidth and Round-trip time)

Разработан Google. В отличие от классических алгоритмов, BBR не считает потерю пакета обязательным признаком перегрузки.

**Принципы работы:**

- **Зондирование (Probing):** BBR постоянно измеряет Max BW (пропускную способность) и Min RTT.
- **Pacing (Равномерность):** BBR требует обязательного использования **Pacing** (через дисциплину очереди `fq` в Linux). Это предотвращает пакетные всплески (bursts), которые вызывают микро-очереди на коммутаторах.
- **Минимизация Bufferbloat:** BBR удерживает объём данных в полёте (Inflight) на уровне BDP, не допуская заполнения буферов промежуточных узлов.

**Версии BBR:**

- **BBRv1 (2016):** Первая версия. Проблема: была слишком агрессивной по отношению к CUBIC потокам.
- **BBRv2 (2020):** Улучшена «справедливость» (fairness) и добавлена поддержка ECN.
- **BBRv3 (2023–2026):** Стандарт 2026 года. Оптимизирован для 400G+ сетей, значительно исправлены ошибки сосуществования с Loss-based алгоритмами.

### Прочие алгоритмы

| Алгоритм | Описание | Применение |
| :--- | :--- | :--- |
| **Reno** | Классический AIMD. Очень чувствителен к потерям. | Эталон для сравнения, учебные цели. |
| **Westwood** | Оценивает полосу по ACK. Эффективен при случайных потерях. | Мобильные и беспроводные сети (Wi-Fi/LTE). |
| **Hybla** | Компенсирует штраф за длинный RTT. | Спутниковая связь, межконтинентальные линки. |
| **DCTCP** | Использует ECN (маркировку CE) для тонкого управления окном. | Внутри ЦОД, где задержка критична. |
| **Vegas** | Реагирует на рост RTT до появления потерь. | Сети с фиксированной топологией. |

## Практические сценарии

### Выбор алгоритма в зависимости от условий

| Сценарий | Рекомендуемый алгоритм | Обоснование |
| :--- | :--- | :--- |
| **Веб-сервер (Интернет)** | `BBRv3` | Максимальная скорость при случайных потерях и большом RTT. |
| **Внутренний API / Microservices** | `DCTCP` или `CUBIC` | Низкая задержка в контролируемой среде. |
| **Спутниковые каналы** | `Hybla` или `BBR` | Устойчивость к экстремально высоким задержкам. |
| **Универсальное применение** | `CUBIC` | Предсказуемость и совместимость со всеми типами очередей. |

### Проверка в Linux

В Linux управление алгоритмами осуществляется через `sysctl`. Подробные инструкции по настройке и выбору дисциплины очередей (qdisc) приведены в разделе [Алгоритмы управления перегрузкой в Linux](../../../../Linux/Networking/Concepts/tcp_tuning/tcp_congestion_algorithms.md).

**Основные команды для проверки:**

```bash
# Просмотр текущего алгоритма
sysctl net.ipv4.tcp_congestion_control
# → net.ipv4.tcp_congestion_control = bbr

# Просмотр доступных в системе алгоритмов
sysctl net.ipv4.tcp_available_congestion_control
# → net.ipv4.tcp_available_congestion_control = reno cubic bbr dctcp
```
