# Алгоритмы управления перегрузкой TCP

## Определения

**Алгоритм управления перегрузкой (Congestion Control Algorithm)** — программная реализация логики управления окном перегрузки (`cwnd`) в протоколе TCP. Он определяет, как отправитель должен изменять скорость передачи данных в ответ на сигналы о состоянии сети (потери пакетов, изменение задержки или явные уведомления о перегрузке).

**Ключевые параметры:**

- **cwnd (Congestion Window):** Окно перегрузки, вычисляемое отправителем. Определяет максимальный объем данных (в байтах или MSS), который может находиться «в полете» (inflight) без подтверждения. Реальное окно отправки ограничено также окном получателя (`rwnd`): `Send Window = min(cwnd, rwnd)`.
- **ssthresh (Slow Start Threshold):** Порог перехода из фазы экспоненциального роста (Slow Start) в фазу линейного избегания перегрузки (Congestion Avoidance). При потере пакета устанавливается в `cwnd / 2` (с учетом корректировок в разных алгоритмах).
- **Inflight:** Количество байтов, отправленных, но еще не подтвержденных получателем.
- **Pacing Rate:** Целевая скорость отправки пакетов, вычисляемая алгоритмом (например, BBR) для предотвращения всплесков трафика (bursts).
- **AIMD (Additive Increase Multiplicative Decrease):** Базовый принцип классических алгоритмов: линейное увеличение окна при отсутствии потерь и резкое (многократное) уменьшение при обнаружении перегрузки.
- **MSS (Maximum Segment Size):** Максимальный размер сегмента данных в TCP-кадре. Стандартное значение для Ethernet: 1460 байт (при MTU 1500).

**Ключевые подходы:**

- **Loss-based (Основанные на потерях):** используют потерю пакетов (Duplicate ACK или таймаут) как основной сигнал для уменьшения скорости. Примеры: Reno, CUBIC.
- **Delay-based (Основанные на задержке):** используют рост задержки RTT для проактивного обнаружения перегрузки до возникновения потерь. Примеры: Vegas, Vegas+.
- **Model-based (Основанные на модели):** строят динамическую математическую модель канала, измеряя максимальную пропускную способность (Bottleneck Bandwidth) и минимальную задержку (Min RTT). Пример: BBR.
- **ECN-based (Основанные на явном уведомлении):** используют явные маркеры перегрузки от сетевого оборудования (Explicit Congestion Notification, флаг CE) для точной и заблаговременной регулировки окна. Пример: DCTCP.

## Основные концепции

### Эволюция алгоритмов

| Поколение | Алгоритмы | Основной сигнал перегрузки | Период доминирования |
| :--- | :--- | :--- | :--- |
| **1-е (Классические)** | Tahoe, Reno, NewReno | Потеря пакетов (RTO / DupACK) | 1988–2003 |
| **2-е (Гибридные)** | CUBIC, HTCP, Westwood | Потеря + время с последней потери | 2004–2015 |
| **3-е (Модельные)** | BBR, Vegas | Доступная пропускная способность + RTT | 2016 – наст. время |
| **4-е (L4S / Data Center)**| DCTCP, BBRv3 (с L4S) | Телеметрия от коммутаторов (ECN/CE) | 2020 – наст. время |

### Tahoe

Tahoe — исходная реализация управления перегрузкой в BSD UNIX (1988), предложенная Ван Якобсоном. Стала прототипом для всех последующих алгоритмов.

**Фазы:**
1. **Slow Start:** `cwnd` начинает с 1 MSS и удваивается каждый RTT до достижения `ssthresh` или потери.
2. **Congestion Avoidance:** После превышения `ssthresh` окно растет линейно (+1 MSS за RTT).
3. **Fast Retransmit:** При 3 дублирующих ACK происходит немедленная ретрансмиссия.
4. **Восстановление:** При любой потере (RTO или Fast Retransmit) `cwnd` сбрасывается до 1 MSS, `ssthresh` устанавливается в `cwnd / 2`. Соединение возвращается в Slow Start.

**Недостатки:** Слишком агрессивный сброс при любом событии потери, что резко снижает утилизацию канала. Не отличается случайные потери от реальной перегрузки.

### Reno

Reno (модифицированный Tahoe, 1990) — первое улучшение, которое ввело механизм **Fast Recovery**, позволяющий не возвращаться в Slow Start после потери, обнаруженной по DupACK.

**Особенности:**
- **Fast Retransmit:** При 3 DupACK переотправляется утерянный сегмент немедленно.
- **Fast Recovery:**
  - `ssthresh = max(cwnd / 2, 2 * MSS)`
  - `cwnd = ssthresh + 3 * MSS`
  - При каждом новом DupACK `cwnd` увеличивается на 1 MSS (чтобы поддерживать инфлайт и реагировать на новые данные).
  - При получении нового ACK (подтверждающего новые данные) `cwnd` устанавливается в `ssthresh`, и соединение переходит в Congestion Avoidance.
- **При потере по таймауту (RTO):** `cwnd = 1 MSS`, возврат в Slow Start.

**Недостатки:** При множественных потерях в одном окне Fast Recovery может завершиться неудачей, инициируя таймаут.

### NewReno

NewReno (RFC 6582) — улучшенная версия Reno, решающая проблему множественных потерь в одном окне.

**Ключевое улучшение:** Вместо выхода из Fast Recovery при получении Partial ACK (подтверждающего часть данных до потери) алгоритм продолжает ожидать подтверждения данных после потери. При получении Partial ACK:
- Переотправляются все потерянные сегменты (а не только первый).
- `ssthresh` и `cwnd` корректируются с учетом всех обнаруженных потерь.

**Итог:** Более эффективное использование канала при нескольких потерях в одном RTT, меньшее количество таймаутов.

### CUBIC

CUBIC является наиболее распространенным loss-based алгоритмом (стандарт для большинства ОС с середины 2000-х годов: Linux 2.6.19+, FreeBSD 10+, Windows 10/Server 2019+).

**Особенности:**

- **RTT-fairness:** В отличие от Reno, функция роста окна `cwnd` в CUBIC зависит от **времени с момента последней потери**, а не от количества полученных ACK (который напрямую связан с RTT). Это позволяет потокам с разными задержками (RTT) получать справедливую долю пропускной способности.
- **Кубическая функция роста:** Алгоритм быстро восстанавливает окно до значения, при котором произошла предыдущая потеря (`W_max`), затем рост замедляется (плато) для избежания перегрузки, и если потерь нет, снова начинает агрессивно расти для поиска новой верхней границы пропускной способности.
- **Высокий BDP (Bandwidth-Delay Product):** Эффективно утилизирует высокоскоростные каналы с большой задержкой, где классический линейный AIMD (как в Reno) восстанавливал бы окно слишком долго.

**Формула роста:**

```text
W(t) = C × (t - K)³ + W_max

где:
  t — время (в секундах) с момента последней потери;
  K — время, необходимое для достижения W_max в отсутствие потерь (вычисляется динамически);
  W_max — размер окна непосредственно перед последним событием перегрузки;
  C — константа масштабирования (обычно 0.4).
```

**Поведение при потере:**
- `ssthresh = cwnd × (1 - β)` где β = 0.2 (потеря 20% от текущего окна, альтернатива делению на 2 в Reno).
- `cwnd` корректируется до `ssthresh`, затем следует кубический рост.

**Ограничения:**
- На сетях с естественным фоном потерь (Wi-Fi, 4G/5G) CUBIC снижает скорость при единичных потерях, что приводит к деградации утилизации канала.
- При высоких скоростях (10 Gbps+) и больших BDP на мелких буферах может возникать «нестабильность» (синусоидальные колебания окна).

### BBR (Bottleneck Bandwidth and Round-trip time)

Разработан компанией Google. BBR представляет собой фундаментальный сдвиг парадигмы: от реагирования на потери к проактивному моделированию сети. BBR не считает единичную потерю пакета обязательным признаком перегрузки, что критично для сетей с естественным фоном потерь (Wi-Fi, 4G/5G).

**Принципы работы:**

- **Зондирование (Probing):** BBR непрерывно выполняет фазы `ProbeBW` (поиск максимальной пропускной способности) и периодически `ProbeRTT` (поиск минимальной задержки сети, снижая объем данных в полете).
- **Равномерность (Pacing):** Вместо классического «оконного» управления (вызывающего всплески трафика — bursts), BBR вычисляет целевую скорость передачи (Pacing Rate) и отправляет пакеты строго по таймеру. В Linux это требует использования механизма EDT (Earliest Departure Time) и дисциплины очереди `fq` (Fair Queueing).
- **Минимизация Bufferbloat:** BBR удерживает объем данных в полете (Inflight) точно на уровне рассчитанного BDP канала. Это предотвращает переполнение буферов промежуточных маршрутизаторов, минимизируя задержки.

**Версии BBR:**

- **BBRv1 (2016):** Первая экспериментальная версия. Проблема: была слишком агрессивной и вытесняла (starving) потоки CUBIC при совместном использовании узкого канала. Возникали проблемы на мелких буферах.
- **BBRv2 (2020):** Существенно улучшена «справедливость» (fairness) по отношению к loss-based потокам. Добавлена реакция на ECN и границы потерь (loss limits), заставляющие снижать скорость при высоких потерях.
- **BBRv3 (2023–2026):** Актуальный стандарт. Включает оптимизации для сетей 400G+, глубокую интеграцию с инициативой L4S (Low Latency, Low Loss, Scalable throughput) и оптимизированное сосуществование с алгоритмами предыдущих поколений.

**Фазы ProbeBW:**
1. **Drain:** Снижение inflight для ухода из заполненного буфера.
2. **Cycle:** Последовательные фазы для зондирования пропускной способности:
   - `Startup` — быстрый экспоненциальный рост до обнаружения瓶颈.
   - `Drain` — снижение inflight.
   - `ProbeBW_up` — увеличение pacing rate для зондирования верхней границы.
   - `ProbeBW_down` — снижение pacing rate для проверки устойчивости.
   - `ProbeBW_cruise` — поддержание текущей пропускной способности.
   - `ProbeBW_refill` — попытка полностью заполнить трубу.

**Фаза ProbeRTT:**
- Периодически (каждые ~10 секунд) BBR снижает inflight до минимума (обычно 4 MSS) для измерения `min_rtt` без влияния очередей.
- В течение ProbeRTT pacing rate снижается, но не ниже доли `cwnd`.

**Важно:** BBRv3 в ядре Linux 6.x использует дополнительные счетчики и флаги, видимые в `ss -ti` (например, `bbr2` в поле `cc` для некоторых конфигураций, хотя обычно видно просто `bbr`).

### Vegas

TCP Vegas (1994) — один из первых delay-based алгоритмов. Вместо реакции на потерь пакета Vegas измеряет разницу между ожидаемой и реальной пропускной способностью канала, определяя перегрузку до возникновения потерь.

**Принцип работы:**
- **Ожидаемый inflight:** `Expected = cwnd / min_rtt`
- **Реальный inflight:** измеряется по частоте поступления ACK.
- **Разница:** `Diff = Expected — Actual`
- Если `Diff` превышает порог `α` — начинается уменьшение `cwnd`. Если `Diff` ниже порога `β` — `cwnd` увеличивается.

**Регулировка:**
- `cwnd = cwnd — 1` при `Diff > α`
- `cwnd = cwnd + 1` при `Diff < β`
- Обычно α = 1, β = 3 (в MSS).

**Преимущества:**
- Проактивное управление: предотвращает перегрузку до потери пакетов.
- Стабильность: RTT остается предсказуемым, Bufferbloat не возникает.

**Недостатки:**
- Низкая утилизация канала при совместном использовании с loss-based алгоритмами: Vegas снижает скорость при росте очереди, а CUBIC продолжает наращивать окно, «вытесняя» Vegas из канала.
- Зависимость от точного измерения `min_rtt`, что сложно в гетерогенных сетях.

### Westwood / Westwood+

TCP Westwood (1998) и Westwood+ (2003) — алгоритмы, оптимизированные для мобильных и беспроводных сетей, где потери часто вызваны радиопомехами, а не перегрузкой.

**Принцип работы:**
- **Оценка доступной полосы:** Анализирует частоту поступления ACK (ACK compression). Если ACK приходят быстрее — доступная полоса выше.
- **Westwood+:** Использует более точный метод оценки на основе среднего размера сегмента и интервала между ACK.
- **Реакция на потерю:** При потере пакета `ssthresh` устанавливается в значение **оцененной доступной полосы**, а не в половину `cwnd` (как в Reno/CUBIC). Если потеря случайная, окно остается почти неизменным.

**Результат:** Значительно выше утилизация канала в условиях нестабильной связи по сравнению с классическими loss-based алгоритмами.

**Ограничения:** Требует доработки в стеке (не включен по умолчанию во всех дистрибутивах Linux; доступен как модуль `tcp_westwood`).

### Hybla

Hybla (2007) — алгоритм, разработанный для компенсации штрафа за очень длинный RTT в классических loss-based алгоритмах.

**Проблема:** В Reno/CUBIC окно растет линейно (+1 MSS за RTT). При RTT = 500 мс скорость роста в 5 раз ниже, чем при RTT = 100 мс, даже при идентичной пропускной способности канала. Длинные линки (спутниковая связь, межконтинентальные каналы) оказываются «штрафованными».

**Решение Hybla:**
- Нормирует скорость роста окна по `RTT_ratio = RTT_actual / RTT_ref` (где `RTT_ref` — минимальный RTT соединения или эталонное значение, например 25 мс).
- Линейный рост: `cwnd = cwnd + 1 / (RTT_ratio)²` за каждый ACK.
- При потере: `ssthresh = cwnd × (1 - β)` где β = 0.875 (агрессивнее, чем у CUBIC).

**Результат:** Потоки с длинным RTT достигают той же утилизации канала, что и короткие, при условии идентичного BDP.

### DCTCP (Data Center TCP)

DCTCP — алгоритм, созданный для изолированных ЦОД с жесткими требованиями к микро-задержкам. Вместо резкого снижения `cwnd` при перегрузке DCTCP плавно масштабирует окно пропорционально доле помеченных ECN пакетов.

**Принцип работы:**
1. **Маркировка ECN:** Коммутаторы в сети (с поддержкой DCTCP AQM) выставляют флаг **CE (Congestion Experienced)** при любом росте очереди (не только при переполнении).
2. **Оценка перегрузки:** Получатель подсчитывает долю помеченных пакетов за окно: `P = помеченные / всего`.
3. **Масштабирование окна:**
   - `cwnd = cwnd × (1 - P/2)` — при получении ACK.
   - Это дает плавное уменьшение, а не резкое деление на 2.
4. **Результат:** Высокая утилизация пропускной способности с минимальными задержками в очередях.

**Требования:**
- Поддержка ECN на всех коммутаторах в пути (включая виртуальные коммутаторы в гипервизорах для контейнеров).
- Включение ECN на конечных хостах: `net.ipv4.tcp_ecn = 1`.
- Загрузка модуля: `sudo modprobe tcp_dctcp`.

## Практические сценарии

### Выбор алгоритма в зависимости от условий

| Сценарий | Рекомендуемый алгоритм | Техническое обоснование |
| :--- | :--- | :--- |
| **Web-сервер, CDN, стриминг (Интернет)** | **BBRv3** | Высокая пропускная способность при случайных потерях пакетов и минимизация задержки до первого байта (TTFB). |
| **Внутренний API / Microservices (ЦОД)** | **DCTCP** или **CUBIC** | В контролируемой среде ЦОД случайные потери минимальны, приоритет отдается минимизации задержек в очередях. |
| **Спутниковые и космические каналы** | **Hybla** или **BBR** | Устойчивость алгоритмов к экстремально высоким значениям RTT (500мс+) без деградации скорости роста окна. |
| **Универсальное применение** | **CUBIC** | Предсказуемость, стабильность и встроенная совместимость со всеми типами промежуточного оборудования. |

### Проверка и выбор алгоритма в Linux

В операционных системах Linux управление алгоритмами осуществляется через параметры ядра (`sysctl`). Детальные инструкции по настройке, тюнингу параметров и выбору правильной дисциплины очередей (qdisc) приведены в руководстве: **[Алгоритмы управления перегрузкой в Linux](../../../../Linux/Networking/Concepts/tcp_tuning/tcp_congestion_algorithms.md)**.

**Основные команды для проверки:**

```bash
# Просмотр алгоритма, используемого по умолчанию для новых соединений
sysctl net.ipv4.tcp_congestion_control
# → net.ipv4.tcp_congestion_control = bbr

# Просмотр списка алгоритмов, загруженных в память ядра
sysctl net.ipv4.tcp_available_congestion_control
# → net.ipv4.tcp_available_congestion_control = reno cubic bbr dctcp

# Просмотр алгоритма для конкретного сокета (поле 'cong:' в ss)
ss -tin state established '( dport = :443 )'
# → bbr wscale:7,7 rto:204 rtt:15.2/0.5 cwnd:120 pacing_rate 130Mbps
```

### Сценарий 1: Включение BBRv3 на высоконагруженном сервере

**Применимость:** Веб-серверы, API, CDN, любые сервисы с высоким объемом исходящего трафика.

**Шаг 1. Создание конфигурации sysctl:**

```bash
sudo tee /etc/sysctl.d/99-tcp-bbr3.conf << 'EOF'
# Обязательная дисциплина очереди для реализации Pacing (EDT)
net.core.default_qdisc = fq

# Установка BBRv3 по умолчанию для новых соединений
net.ipv4.tcp_congestion_control = bbr

# Включение ECN (требуется для BBRv2/v3 и поддержки L4S)
net.ipv4.tcp_ecn = 1

# Разрешение использования BBR непривилегированными процессами
net.ipv4.tcp_allowed_congestion_control = bbr cubic reno
EOF
```

**Шаг 2. Применение конфигурации:**

```bash
# Проверка на синтаксические ошибки перед применением
sudo sysctl -p /etc/sysctl.d/99-tcp-bbr3.conf
# → net.core.default_qdisc = fq
# → net.ipv4.tcp_congestion_control = bbr
# → net.ipv4.tcp_ecn = 1

# Применение всех файлов в /etc/sysctl.d/
sudo sysctl --system
```

**Шаг 3. Валидация через `ss`:**

```bash
# Проверка выбранного алгоритма для активных соединений
ss -tin state established | head -n 5
# → bbr wscale:7,7 rto:204 rtt:15.2/0.5 cwnd:120 pacing_rate 130Mbps

# Проверка, что ECN активен
ss -ti dst <целевой_IP>
# Поля для проверки: ecn_ce, ecn_ect0, ecn_ect1
```

**Типичные ошибки и решения:**
- **Ошибка:** `ss` показывает `cwnd: 10`, скорость низкая.
  - **Причина:** `tcp_slow_start_after_idle = 1` (по умолчанию) сбрасывает окно при простое.
  - **Решение:** Отключить или установить в 0: `net.ipv4.tcp_slow_start_after_idle = 0`.
- **Ошибка:** BBR не работает, pacing_rate отсутствует в выводе `ss`.
  - **Причина:** Отсутствует дисциплина `fq` в `tc qdisc`.
  - **Решение:** `sudo tc qdisc replace dev eth0 root fq`.

### Сценарий 2: Настройка DCTCP в Data Center

**Применимость:** ЦОД, кластеры Kubernetes, внутренние сети с полным контролем над коммутаторами.

**Шаг 1. Загрузка модуля DCTCP:**

```bash
# Проверка доступности модуля
lsmod | grep dctcp

# Загрузка модуля
sudo modprobe tcp_dctcp

# Постоянная загрузка при загрузке системы
echo "tcp_dctcp" | sudo tee /etc/modules-load.d/dctcp.conf
```

**Шаг 2. Включение ECN на интерфейсе:**

```bash
# Проверка текущего состояния ECN
ethtool -k eth0 | grep ecn

# Включение ECN (если драйвер поддерживает)
sudo ethtool -K eth0 ecn enable
```

**Шаг 3. Настройка sysctl для DCTCP:**

```bash
sudo tee /etc/sysctl.d/99-tcp-dctcp.conf << 'EOF'
# Использование DCTCP по умолчанию
net.ipv4.tcp_congestion_control = dctcp

# Включение ECN
net.ipv4.tcp_ecn = 1

# Для DCTCP: доли помеченных пакетов пороговых значений нет (все помеченные считаются)
net.core.tcp_ecn_fallback = 0
EOF

sudo sysctl -p /etc/sysctl.d/99-tcp-dctcp.conf
```

**Шаг 4. Настройка маршрута для конкретного бэкенда:**

```bash
# Привязка DCTCP к трафику к подсети бэкендов
sudo ip route add 10.0.0.0/24 via 192.168.1.1 dev eth0 congctl dctcp

# Проверка маршрута
ip route show 10.0.0.0/24
# → 10.0.0.0/24 via 192.168.1.1 dev eth0 congctl dctcp
```

**Валидация:**

```bash
# Проверка ECN-счетчиков в nstat
nstat -az | grep -i ecn
# → TcpExtTCPECN0ece: 0
# → TcpExtTCPECN0ect1: 12456
# → TcpExtTCPECN0ect0: 0
# → TcpExtTCPECNSuccess: 12456

# Проверка статистики DCTCP
sudo nstat -az | grep -i dctcp
# → DctcpStatsCE: 4523
# → DctcpStatsDupAck: 0
# → DctcpStatsDropped: 0
```

### Сценарий 3: Настройка для спутниковых/межконтинентальных каналов (Hybla)

**Применимость:** RTT > 300 мс, спутниковая связь, морские кабели с высокой задержкой.

**Шаг 1. Загрузка и проверка Hybla:**

```bash
# Hybla доступен как модуль ядра в большинстве дистрибутивов
lsmod | grep hybla || sudo modprobe tcp_hybla
```

**Шаг 2. Конфигурация sysctl:**

```bash
sudo tee /etc/sysctl.d/99-tcp-hybla.conf << 'EOF'
# Установка Hybla по умолчанию
net.ipv4.tcp_congestion_control = hybla

# Для длинных RTT: отключение сброса окна при простое
# (важно для спутниковых каналов с большими RTT)
net.ipv4.tcp_slow_start_after_idle = 0

# Увеличение таймаута для очень длинных каналов
net.ipv4.tcp_keepalive_time = 300
net.ipv4.tcp_keepalive_intvl = 30
net.ipv4.tcp_keepalive_probes = 3
EOF

sudo sysctl -p /etc/sysctl.d/99-tcp-hybla.conf
```

**Шаг 3. Валидация:**

```bash
# Проверка окна для соединения с высоким RTT
ss -tin dst <спутниковый_IP>
# → hybla wscale:7,7 rto:1200 rtt:620/15 cwnd:450 pacing_rate 50Mbps

# Ожидаемое: cwnd должен расти пропорционально BDP, несмотря на высокий RTT
# BDP = bandwidth (bps) × RTT (sec)
# Например, при 50 Mbps и RTT 620 мс: BDP ≈ 3.87 МБ ≈ 2650 MSS
```

### Сценарий 4: Переключение алгоритма для отдельного соединения (runtime)

**Применимость:** Тестирование производительности конкретного сервиса без изменения глобальных настроек.

```bash
# Для нового соединения можно указать алгоритм через setsockopt (в коде приложения).
# Для существующих соединений: через ip route.

# Привязка алгоритма к маршруту (IPv4)
sudo ip route change default via 192.168.1.1 dev eth0 congctl bbr

# Привязка алгоритма к маршруту (IPv6)
sudo ip -6 route change default via 2001:db8::1 dev eth0 congctl bbr

# Удаление привязки (возврат к глобальному алгоритму)
sudo ip route change default via 192.168.1.1 dev eth0

# Проверка:
ip route show default
# → default via 192.168.1.1 dev eth0 proto static metric 100 congctl bbr
```

### Сценарий 5: Сосуществование алгоритмов в одной сети

**Проблема:** При смешении loss-based и model-based потоков в одном буфере происходит «голодание» (starving) медленных алгоритмов.

**Диагностика:**

```bash
# Мониторинг счетчиков BBR
nstat -az | grep -i bbr
# → BbrBwProbe: 145
# → BbrBwProbeSamplePhase: 78
# → BbrBwProbeUp: 0
# → BbrBwProbeDown: 67

# Мониторинг потерь
nstat -az | grep -E 'TcpExtTCPRetrans|TcpExtTCPSynRetrans'
```

**Решение:**
- Использовать BBRv3 (имеет встроенные механизмы «справедливости» и `loss_limits`).
- На маршрутизаторах внедрить AQM (`fq_codel` или `cake`), который обеспечивает честное обслуживание независимо от алгоритма источника.
- На серверах с BBRv3 убедиться, что `qdisc = fq` (не `fq_codel`, так как `fq_codel` может скрывать pacing_rate от BBR в некоторых конфигурациях).

### Сценарий 6: Диагностика Bufferbloat и выбор AQM

**Шаг 1. Измерение базового RTT:**

```bash
# Без нагрузки
ping -c 20 8.8.8.8
# → rtt min/avg/max/mdev = 12.345/13.456/18.901/1.234 ms
```

**Шаг 2. Измерение RTT под нагрузкой:**

```bash
# Параллельный flood через iperf3
iperf3 -c <сервер> -t 60 -P 4 &

# В другом окне — ping
ping -c 60 8.8.8.8
# → rtt min/avg/max/mdev = 12.345/145.678/892.123/189.456 ms
```

**Оценка:** Если RTT под нагрузкой растет в 5–10+ раз — классический Bufferbloat.

**Шаг 3. Проверка поведения алгоритма:**

```bash
# Если используется CUBIC и есть Bufferbloat — переключиться на BBR
# или настроить AQM на роутере.

# Для роутера (OpenWrt/Ubiquito):
# tc qdisc replace dev wan root fq_codel

# Для хоста Linux:
sudo tc qdisc replace dev eth0 root fq_codel
```

**Валидация:** Повторить шаг 2. RTT под нагрузкой должен оставаться близким к базовому (±20–30%).

### Типичные ошибки и их устранение

| Симптом | Возможная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Низкая скорость на высокоскоростном канале | `cwnd` ограничен малым значением | `ss -ti`: `cwnd: 10`, `app_limited` | Увеличить `initcwnd` до 32 MSS, отключить `tcp_slow_start_after_idle` |
| Резкие всплески трафика при BBR | Отсутствует дисциплина `fq` | `tc qdisc show dev eth0` | `sudo tc qdisc replace dev eth0 root fq` |
| Постоянные ретрансмиссии на Wi-Fi | CUBIC/Reno воспринимают помехи как перегрузку | `nstat -az | grep Retrans` | Переключить на BBR или Westwood |
| Высокий RTT только под нагрузкой | Bufferbloat | `ss -ti`: `rtt` vs `min_rtt` | BBRv3 или `fq_codel` на маршрутизаторе |
| DCTCP не снижает задержку | ECN отклющен на коммутаторе | `nstat -az | grep ECN` | Включить ECN на всех узлах маршрута |
| Длинный RTT, низкая скорость | Используется Reno/CUBIC без компенсации RTT | `ss -ti`: `rtt: 500+`, `cwnd` мал | Переключить на Hybla |

### Инструменты мониторинга

- **ss:** Socket Statistics — первичный инструмент для просмотра `cwnd`, `ssthresh`, `rtt`, `pacing_rate`, `app_limited` в реальном времени.
- **nstat:** Агрегированные счетчики протокола (`nstat -az | grep TcpExtTCP*`).
- **tcpretrans:** eBPF-трассировка ретрансмиссий с указанием причины и функции ядра.
- **tcprtt:** eBPF-гистограмма RTT для выявления Tail Latency.
- **tcpcongestion:** eBPF-трассировка изменений алгоритма перегрузки.
- **Wireshark:** Sequence Graphs для визуализации динамики окна на захваченном трафике.

### Известные ограничения и edge cases

- **BBR и синтетические сети:** В виртуализированных средах с большим внутренним RTT (например, VPN-туннели) BBR может недооценивать пропускную способность. Рекомендуется ручная калибровка `BtlBw` через `sysctl` в ядрах, поддерживающих такие параметры, или использование CUBIC.
- **CUBIC и экзопонические сети:** При RTO < 1 секунда CUBIC может генерировать всплески, не успев завершить ProbeBW. В таких средах рекомендуется увеличить `tcp_slow_start_after_idle` или использовать BBRv3.
- **DCTCP и гетерогенные сети:** Если хотя бы один коммутатор в пути не поддерживает ECN, DCTCP работает в режиме fallback (похожем на Reno), теряя преимущества. Обязательно проверять ECN-статистику (`nstat -az | grep ECN`) на всех узлах пути.
- **Hybla и Windows:** Hybla не является стандартным алгоритмом в Windows. Для гибридных сред (Linux ↔ Windows) лучше использовать BBRv3 или CUBIC на стороне Linux.
