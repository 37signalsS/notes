# Алгоритмы управления перегрузкой TCP

## Определения

**Алгоритм управления перегрузкой (Congestion Control Algorithm)** — программная реализация логики управления окном перегрузки (`cwnd`) в протоколе TCP. Он определяет, как отправитель должен изменять скорость передачи данных в ответ на сигналы о состоянии сети (потери пакетов, изменение задержки или явные уведомления о перегрузке).

**Ключевые подходы:**

- **Loss-based (Основанные на потерях):** используют потерю пакетов (Duplicate ACK или таймаут) как основной сигнал для уменьшения скорости. Примеры: Reno, CUBIC.
- **Delay-based (Основанные на задержке):** используют рост задержки RTT для проактивного обнаружения перегрузки до возникновения потерь. Примеры: Vegas, Vegas+.
- **Model-based (Основанные на модели):** строят динамическую математическую модель канала, измеряя максимальную пропускную способность (Bottleneck Bandwidth) и минимальную задержку (Min RTT). Пример: BBR.
- **ECN-based (Основанные на явном уведомлении):** используют явные маркеры перегрузки от сетевого оборудования (Explicit Congestion Notification, флаг CE) для точной и заблаговременной регулировки окна. Пример: DCTCP.

## Основные концепции

### Эволюция алгоритмов

| Поколение | Алгоритмы | Основной сигнал перегрузки | Период доминирования |
| :--- | :--- | :--- | :--- |
| **1-е (Классические)** | Tahoe, Reno, NewReno | Потеря пакетов (RTO / DupACK) | 1988–2003 |
| **2-е (Гибридные)** | CUBIC, HTCP, Westwood | Потеря + время с последней потери | 2004–2015 |
| **3-е (Модельные)** | BBR, Vegas | Доступная пропускная способность + RTT | 2016 – наст. время |
| **4-е (L4S / Data Center)**| DCTCP, BBRv3 (с L4S) | Телеметрия от коммутаторов (ECN/CE) | 2020 – наст. время |

### CUBIC

CUBIC является наиболее распространенным loss-based алгоритмом (стандарт для большинства ОС с середины 2000-х годов: Linux 2.6.19+, FreeBSD 10+, Windows 10/Server 2019+).

**Особенности:**

- **RTT-fairness:** В отличие от Reno, функция роста окна `cwnd` в CUBIC зависит от **времени с момента последней потери**, а не от количества полученных ACK (которое напрямую связано с RTT). Это позволяет потокам с разными задержками (RTT) получать справедливую долю пропускной способности.
- **Кубическая функция роста:** Алгоритм быстро восстанавливает окно до значения, при котором произошла предыдущая потеря (`W_max`), затем рост замедляется (плато) для избежания перегрузки, и если потерь нет, снова начинает агрессивно расти для поиска новой верхней границы пропускной способности.
- **Высокий BDP (Bandwidth-Delay Product):** Эффективно утилизирует высокоскоростные каналы с большой задержкой, где классический линейный AIMD (как в Reno) восстанавливал бы окно слишком долго.

**Формула роста:**

```text
W(t) = C × (t - K)³ + W_max

где:
  t — время (в секундах) с момента последней потери;
  K — время, необходимое для достижения W_max в отсутствие потерь (вычисляется динамически);
  W_max — размер окна непосредственно перед последним событием перегрузки;
  C — константа масштабирования (обычно 0.4).
```

### BBR (Bottleneck Bandwidth and Round-trip time)

Разработан компанией Google. BBR представляет собой фундаментальный сдвиг парадигмы: от реагирования на потери к проактивному моделированию сети. BBR не считает единичную потерю пакета обязательным признаком перегрузки, что критично для сетей с естественным фоном потерь (Wi-Fi, 4G/5G).

**Принципы работы:**

- **Зондирование (Probing):** BBR непрерывно выполняет фазы `ProbeBW` (поиск максимальной пропускной способности) и периодически `ProbeRTT` (поиск минимальной задержки сети, снижая объем данных в полете).
- **Равномерность (Pacing):** Вместо классического "оконного" управления (вызывающего всплески трафика — bursts), BBR вычисляет целевую скорость передачи (Pacing Rate) и отправляет пакеты строго по таймеру. В Linux это требует использования механизма EDT (Earliest Departure Time) и дисциплины очереди `fq` (Fair Queueing).
- **Минимизация Bufferbloat:** BBR удерживает объем данных в полете (Inflight) точно на уровне рассчитанного BDP канала. Это предотвращает переполнение буферов промежуточных маршрутизаторов, минимизируя задержки.

**Версии BBR:**

- **BBRv1 (2016):** Первая экспериментальная версия. Проблема: была слишком агрессивной и вытесняла (starving) потоки CUBIC при совместном использовании узкого канала. Возникали проблемы на мелких буферах.
- **BBRv2 (2020):** Существенно улучшена «справедливость» (fairness) по отношению к loss-based потокам. Добавлена реакция на ECN и границы потерь (loss limits), заставляющие снижать скорость при высоких потерях.
- **BBRv3 (2023–2026):** Актуальный стандарт. Включает оптимизации для сетей 400G+, глубокую интеграцию с инициативой L4S (Low Latency, Low Loss, Scalable throughput) и оптимизированное сосуществование с алгоритмами предыдущих поколений.

### Алгоритмы для специфичных задач (Data Center и другие)

| Алгоритм | Описание и принцип работы | Типовое применение |
| :--- | :--- | :--- |
| **DCTCP (Data Center TCP)** | Опирается на маркировку ECN коммутаторами (CE - Congestion Experienced) при малейшем росте очереди. Масштабирует окно пропорционально доле маркированных пакетов, а не сбрасывает его вдвое. Требует поддержки ECN на всех узлах. | Изолированные ЦОД, сети с жесткими требованиями к микро-задержкам. |
| **Reno / NewReno** | Классическая реализация AIMD. При потере пакета уменьшает окно в 2 раза, растет линейно. Очень чувствителен к случайным потерях. NewReno улучшил обработку множественных потерь в одном окне (Fast Recovery). | Эталон для сравнения, академические исследования. |
| **Westwood / Westwood+** | Оценивает доступную полосу пропускания, анализируя частоту поступления ACK. Эффективно отличает реальную перегрузку сети от случайной потери радиосигнала. | Мобильные и нестабильные беспроводные сети. |
| **Hybla** | Разработан для компенсации штрафа за очень длинный RTT. Модифицирует правило роста окна, чтобы длинные линки получали ту же скорость разгона, что и короткие. | Спутниковая связь, межконтинентальные каналы. |

## Практические сценарии

### Выбор алгоритма в зависимости от условий

| Сценарий | Рекомендуемый алгоритм | Техническое обоснование |
| :--- | :--- | :--- |
| **Web-сервер, CDN, стриминг (Интернет)** | **BBRv3** | Высокая пропускная способность при случайных потерях пакетов и минимизация задержки до первого байта (TTFB). |
| **Внутренний API / Microservices (ЦОД)** | **DCTCP** или **CUBIC** | В контролируемой среде ЦОД случайные потери минимальны, приоритет отдается минимизации задержек в очередях. |
| **Спутниковые и космические каналы** | **Hybla** или **BBR** | Устойчивость алгоритмов к экстремально высоким значениям RTT (500мс+) без деградации скорости роста окна. |
| **Универсальное применение** | **CUBIC** | Предсказуемость, стабильность и встроенная совместимость со всеми типами промежуточного оборудования. |

### Проверка в Linux

В операционных системах Linux управление алгоритмами осуществляется через параметры ядра (`sysctl`). Детальные инструкции по настройке, тюнингу параметров и выбору правильной дисциплины очередей (qdisc) приведены в руководстве: **[Алгоритмы управления перегрузкой в Linux](../../../../Linux/Networking/Concepts/tcp_tuning/tcp_congestion_algorithms.md)**.

**Основные команды для проверки:**

```bash
# Просмотр алгоритма, используемого по умолчанию для новых соединений
sysctl net.ipv4.tcp_congestion_control
# → net.ipv4.tcp_congestion_control = bbr

# Просмотр списка алгоритмов, загруженных в память ядра
sysctl net.ipv4.tcp_available_congestion_control
# → net.ipv4.tcp_available_congestion_control = reno cubic bbr dctcp
```
