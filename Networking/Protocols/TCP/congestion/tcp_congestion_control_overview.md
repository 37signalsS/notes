# Управление перегрузкой TCP — Обзор и базовые механизмы

## Определения

**Управление перегрузкой (Congestion Control)** — комплекс механизмов транспортного уровня, предназначенных для адаптации скорости передачи данных к текущей пропускной способности сети. В отличие от управления потоком, которое защищает получателя, управление перегрузкой защищает промежуточные узлы (маршрутизаторы, коммутаторы) от переполнения их очередей.

**Ключевое отличие от [управления потоком (Flow Control)](../Flow_Control/index.md):**

- **Congestion Control (Окно перегрузки — `cwnd`):** Ограничение со стороны **сети**. Отправитель оценивает, сколько данных может «переварить» канал.
- **Flow Control (Окно получателя — `rwnd`):** Ограничение со стороны **получателя**. Получатель сообщает, сколько места осталось в его буфере.

**Итоговое окно отправки (Send Window):**
Реальное количество данных, которое TCP разрешает отправить без подтверждения, определяется как минимум из двух ограничителей:
```text
Send Window = min(cwnd, rwnd)
```

## Основные концепции

### Зачем нужно управление перегрузкой?

Без управления перегрузкой отправители могли бы наводнить сеть трафиком, превышающим пропускную способность самого узкого места (**Bottleneck**). Это привело бы к массовой потере пакетов, бесконечным ретрансмиссиям и «коллапсу перегрузки».

Для эффективного использования канала необходимо заполнить его данными («заполнить трубу»). Объем данных, необходимый для этого, называется **BDP (Bandwidth-Delay Product)**.
`BDP = Пропускная способность (бит/с) × RTT (сек)`.

### Базовые фазы алгоритмов (RFC 5681)

Стандартные алгоритмы (Reno, NewReno, CUBIC) проходят через четыре основные фазы:

#### 1. Медленный старт (Slow Start)
Используется при установке нового соединения или после длительного простоя.
- **Цель:** Быстро найти предел пропускной способности.
- **Логика:** Начинается с `initcwnd` (10 MSS). На каждый полученный ACK окно `cwnd` увеличивается на 1 MSS.
- **Рост:** Экспоненциальный (удвоение каждый RTT).
- **Выход:** При достижении порога `ssthresh` или при потере пакета.

#### 2. Избегание перегрузки (Congestion Avoidance)
Начинается, когда `cwnd >= ssthresh`.
- **Логика:** Механизм **AIMD** (Additive Increase Multiplicative Decrease).
- **Рост:** Линейный (+1 MSS за один полный RTT). Окно растет осторожно, стараясь не вызвать переполнение.

#### 3. Быстрая ретрансмиссия (Fast Retransmit)
Если отправитель получает **3 дублирующих подтверждения (Duplicate ACK)**, он не ждет таймаута (RTO), а немедленно переотправляет сегмент, следующий за подтвержденным. Это сигнализирует о том, что сеть доставляет пакеты, но один из них «выпал».

#### 4. Быстрое восстановление (Fast Recovery)
Механизм, позволяющий не возвращаться к Slow Start после потери, обнаруженной через DupACK.
- **ssthresh:** Устанавливается в значение `max(Inflight / 2, 2 * MSS)`.
- **cwnd:** В классическом Reno устанавливается равным `ssthresh + 3 * MSS`.
- **Результат:** Соединение продолжает работу в фазе Congestion Avoidance с уменьшенной вдвое скоростью.

### Современные механизмы обратной связи

В современных сетях (стандарты 2024–2026 гг.) TCP использует дополнительные сигналы:

1.  **SACK (Selective Acknowledgments):** Позволяет получателю подтверждать конкретные блоки данных. Отправитель точно знает, какие сегменты потеряны, и может переотправить только их за один цикл.
2.  **ECN (Explicit Congestion Notification):** Сетевое оборудование помечает пакеты флагом `CE`, если их очереди начинают расти. TCP-отправитель снижает скорость до того, как пакеты будут физически отброшены.
3.  **L4S (Low Latency, Low Loss, Scalable throughput):** Новейший стандарт (RFC 9330), позволяющий достичь сверхнизких задержек в очередях за счет очень частой и точной маркировки ECN.
4.  **TLP (Tail Loss Probe):** Механизм для быстрой отправки «пробного» пакета, если подтверждения перестали приходить в конце передачи, что экономит время на ожидании RTO.

## Практические сценарии

### Сценарий 1: Расчет необходимого окна (BDP)

Для утилизации канала 1 Гбит/с при задержке 100 мс (межконтинентальный линк):
1. **Bandwidth:** 1,000,000,000 бит/с.
2. **RTT:** 0.1 сек.
3. **BDP:** 1,000,000,000 × 0.1 = 100,000,000 бит (~12.5 МБ).
4. **В MSS:** 12,500,000 / 1460 ≈ **8561 MSS**.

Если системные буферы или окно `cwnd` ограничены меньшим значением, сервер никогда не достигнет скорости 1 Гбит/с, даже если канал свободен.

### Сценарий 2: Реакция на потерю пакета (CUBIC vs BBR)

| Событие | Реакция CUBIC (Loss-based) | Реакция BBR (Model-based) |
| :--- | :--- | :--- |
| **Случайная потеря (Wi-Fi)** | Резкое снижение `cwnd` (-30%). Скорость падает. | Игнорирует единичные потери. Скорость стабильна. |
| **Переполнение буфера** | Снижает `cwnd`, предотвращая коллапс. | Снижает скорость, минимизируя задержки в очереди. |
| **Тайм-аут (RTO)** | Сброс `cwnd = 1 MSS`, переход в Slow Start. | Сброс состояния, повторное зондирование канала. |

### Сценарий 3: Проблема Bufferbloat

Если промежуточный роутер имеет слишком глубокие буферы, классические алгоритмы (CUBIC, Reno) будут продолжать наращивать окно, пока не заполнят весь буфер.
- **Симптом:** Потерь нет, но RTT вырастает с 20 мс до 500 мс под нагрузкой.
- **Диагностика:** Сравнение `rtt` и `min_rtt` в выводе `ss -ti`.
- **Лечение:** Переход на BBR или настройка AQM-дисциплин (`fq_codel`, `cake`) на маршрутизаторе.
