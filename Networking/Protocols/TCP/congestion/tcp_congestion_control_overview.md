# Управление перегрузкой TCP — Обзор и базовые алгоритмы

## Определения

**Congestion Control** — механизм TCP для предотвращения перегрузки сети путём адаптации скорости передачи к доступной пропускной способности канала.

**Ключевое отличие от [Flow Control](../../../../Ansible/PlaybookStructure/flow_control.md):**
- **Congestion Control:** защита **сети** (network-centric), параметр `cwnd`
- **Flow Control:** защита **получателя** (receiver-centric), параметр `rwnd`

**Итоговое окно отправки:**

```
Effective Window = min(cwnd, rwnd)
```

---

## Основные концепции

### Проблема скорости передачи данных

Передача данных по одному пакету с ожиданием подтверждения надёжна, но крайне неэффективна на больших расстояниях. Решение — механизм **скользящего окна**, позволяющий отправлять несколько пакетов до получения подтверждения.

**Пример расчета для соединения Владивосток—Калининград:**

```
Расстояние: ~7 500 км (туда и обратно: 15 000 км)
Скорость света: ~300 000 км/сек
RTT: 15 000 / 300 000 = 0.05 сек (50 мс)
Количество циклов в секунду: 1 / 0.05 = 20 раз/сек

Максимальный размер пакета: 1500 байт
  - IP заголовок: 20 байт
  - TCP заголовок: 20 байт
  - Полезные данные: 1460 байт (MSS)

Скорость при передаче по 1 пакету:
  1460 байт × 20 = 29 200 байт/сек ≈ 28 Кбайт/сек
```

Такая скорость неприемлема для современных приложений — отсюда необходимость в скользящем окне и congestion control.

### Окно перегрузки (Congestion Window, cwnd)

**cwnd** — переменная состояния TCP на стороне отправителя, ограничивающая объём данных, которые могут быть отправлены без подтверждения. Измеряется в **MSS (Maximum Segment Size)**.

**Принцип работы:**

```
Отправитель                          Сеть                           Получатель
     |                                |                                 |
     |  cwnd = 10 MSS                 |  Пропускная способность: ?      |
     |  [Отправка 10 сегментов] ----->|                                 |
     |                                |                                 |
     |  <---- ACK (10 сегментов) -----|                                 |
     |  cwnd = 20 MSS (Slow Start)    |                                 |
     |  [Отправка 20 сегментов] ----->|                                 |
     |                                |                                 |
     |  <---- ACK (потеря 1 пакет) ---|  Перегрузка! Потеря пакета      |
     |  cwnd = 10 MSS (AIMD)          |                                 |
```

### Ключевые алгоритмы

#### 1. Медленный старт (Slow Start)

**Цель:** быстро определить доступную пропускную способность при старте соединения.

**Механизм:**
- **Начальное значение:** `initcwnd = 10 MSS` (RFC 5681, ~14.6 КБ)
- **Рост:** экспоненциальный (+1 MSS на каждый ACK)
- **Завершение:** при достижении `ssthresh` или потере пакета

**Динамика роста:**

```
RTT 0:  cwnd = 10 MSS   (отправка 10 сегментов)
RTT 1:  cwnd = 20 MSS   (получено 10 ACK, +10 MSS)
RTT 2:  cwnd = 40 MSS   (получено 20 ACK, +20 MSS)
RTT 3:  cwnd = 80 MSS   (получено 40 ACK, +40 MSS)
```

Название «медленный» — историческое, на самом деле рост быстрый (экспоненциальный).

#### 2. Избегание перегрузки (Congestion Avoidance, AIMD)

**AIMD (Additive Increase Multiplicative Decrease)** — алгоритм работы после достижения порога `ssthresh`.

**Механизм:**
- **Additive Increase:** +1 MSS на RTT (линейный рост)
- **Multiplicative Decrease:** при потере пакета `cwnd = cwnd / 2`

**Динамика:**

```
cwnd
  │
  │     ╱│       ╱───
  │    ╱ │      ╱
  │   ╱  │     ╱
  │  ╱   │    ╱
  │ ╱    │   ╱
  │╱     │  ╱
  └──────┴─┴─────────────► время
         │  │
         │  потеря (cwnd/2)
         ssthresh
         (Slow Start → AIMD)
```

**Порог ssthresh (slow start threshold):**
- Начальное значение: обычно 65535 байт
- При потере пакета: `ssthresh = cwnd / 2`

#### 3. Быстрое восстановление (Fast Recovery)

**Цель:** избежать полного сброса `cwnd` при единичных потерях.

**Триггер:** получение **3 дубликатов ACK** (DupACK).

**Алгоритм (RFC 5681):**
1. `ssthresh = cwnd / 2`
2. `cwnd = ssthresh + 3 MSS` (учитываем 3 сегмента, вышедшие из сети)
3. Переход в режим Congestion Avoidance (не Slow Start!)
4. При получении ACK для новых данных — выход из Fast Recovery

**Сравнение с тайм-аутом:**

| Событие | Реакция cwnd | Режим после |
| :--- | :--- | :--- |
| **3 DupACK** | `cwnd = cwnd / 2` | Congestion Avoidance |
| **RTO (тайм-аут)** | `cwnd = 1 MSS` | Slow Start |

## Практические сценарии

### Сценарий 1: Новое TCP-соединение

При установке соединения отправитель не знает пропускную способность сети. Алгоритм:

1. **Slow Start:** `cwnd = initcwnd` (10 MSS) → экспоненциальный рост
2. При достижении `ssthresh` → переход в **Congestion Avoidance**
3. Линейный рост до первого сигнала перегрузки

### Сценарий 2: Обнаружение перегрузки через потерю пакета

Потеря пакета — основной сигнал перегрузки в loss-based алгоритмах:

1. **3 DupACK** → Fast Recovery: `cwnd = cwnd / 2`, продолжение передачи
2. **RTO (тайм-аут)** → жёсткий сброс: `cwnd = 1 MSS`, возврат в Slow Start
3. `ssthresh` обновляется на половину текущего `cwnd`

### Сценарий 3: Расчёт оптимального cwnd через BDP

Для полной утилизации канала необходимо:

```
BDP = Bandwidth × RTT
cwnd ≥ BDP / MSS
```

**Пример для канала 1 Гбит/с и RTT 50 мс:**

```
BDP = 1 000 000 000 бит/с × 0.05 с = 50 000 000 бит = 6.25 МБ
cwnd ≥ 6 250 000 / 1460 ≈ 4280 MSS
```

При стандартном Slow Start (10 MSS) потребуется ~9 RTT для достижения этого значения.

## Дополнительная информация

### RFC и стандарты

| RFC | Описание |
| :--- | :--- |
| **RFC 5681** | Congestion Control (Slow Start, AIMD, Fast Recovery) |
| **RFC 6675** | SACK-based loss recovery |
| **RFC 7323** | Window Scaling, Timestamps |

### Формулы

**Bandwidth-Delay Product (BDP):**

```
BDP = Bandwidth × RTT
```

**Требуемое cwnd для полной утилизации:**

```
cwnd ≥ BDP / MSS
```

**Максимальная пропускная способность:**

```
Throughput = (cwnd × MSS) / RTT
```
