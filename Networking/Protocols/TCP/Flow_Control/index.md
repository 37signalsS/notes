# Управление потоком в TCP (Flow Control)

## Определения

**Управление потоком (Flow Control)** — это механизм протокола TCP, предназначенный для предотвращения переполнения буфера на стороне получателя. Он гарантирует, что отправитель не будет передавать данные быстрее, чем приложение-получатель успевает их обрабатывать.

**Основные термины:**

- **Receiver Window (rwnd):** размер свободного места в приемном буфере, о котором получатель сообщает отправителю.
- **Zero Window (нулевое окно):** состояние, когда `rwnd = 0`, и отправитель обязан приостановить передачу данных.
- **Silly Window Syndrome (SWS):** проблема «глупого окна», при которой данные передаются крайне мелкими порциями, что неэффективно использует ресурсы сети.

---

## Основные концепции

### Механизм скользящего окна (Sliding Window)

Получатель динамически изменяет значение `rwnd` в заголовке ACK-сегментов.

```text
Отправитель                          Получатель
     |                                    |
     |  Данные (1000 байт) -------------> |  Буфер: 1000/5000 заполнено
     |  <--- ACK, Win=4000 -------------- |  (rwnd = 4000)
     |                                    |
     |  Данные (4000 байт) -------------> |  Буфер: 5000/5000 (FULL)
     |  <--- ACK, Win=0 ----------------- |  (STOP!)
```

### Масштабирование окна (Window Scaling)

Поле `Window Size` в заголовке TCP ограничено 16 битами (64 КБ). Опция **Window Scale** (RFC 7323) задает множитель (степень 2), позволяющий расширить окно до 1 ГБ.
- **Пример:** Если `Window Size = 1000` и `wscale = 7`, реальное окно равно $1000 \times 2^7 = 128,000$ байт.

### Проблема Silly Window Syndrome (SWS)

Ситуация, когда приложение читает данные по 1 байту, и стек TCP немедленно объявляет `rwnd = 1`, провоцируя отправку крошечных пакетов.
- **Решение на стороне получателя (Clark's Solution):** Не объявлять увеличение окна, пока в буфере не освободится место размером хотя бы в 1 MSS или 50% от всего буфера.
- **Решение на стороне отправителя:** [Алгоритм Нейгла (Nagle)](../tcp_nagle_algorithm.md).

## Реализация в Linux

### Автотюнинг приемного окна

В Linux размер `rwnd` рассчитывается на основе свободной памяти в сокете (`sk_rmem_alloc`), но не равен ей напрямую. Часть памяти резервируется под метаданные структур ядра.

**Параметры управления:**
- `net.ipv4.tcp_rmem`: Задает (min, default, max) границы буфера приема.
- `net.ipv4.tcp_adv_win_scale`: Определяет долю буфера, выделяемую под `rwnd`.
  - Формула: $rwnd = Buffer / 2^{tcp\_adv\_win\_scale}$.
  - По умолчанию (значение 1) под окно отдается 50% буфера, остальное — под метаданные.

### Диагностика через ss

Параметры окна для активного сокета:
```bash
ss -tmo dst 1.2.3.4
# → State  Recv-Q Send-Q Local Address:Port  Peer Address:Port
# → ESTAB  0      0      10.0.0.1:443        1.2.3.4:54321  
# →   wscale:7,7 rto:204 rtt:15.2/0.5 cwnd:1000 rcv_space:14600
```
- `rcv_space`: Текущий размер `rwnd`, который сервер готов объявить клиенту.
- `wscale:7,7`: Согласованные множители масштабирования.

## Практические сценарии

### Сценарий 1: Диагностика Zero Window

**Симптом:** Передача данных замирает, в дампе Wireshark видны пакеты «TCP Zero Window».
**Анализ:**
1. Если `Recv-Q` в `ss` растет — приложение не успевает вычитывать данные (проблема в коде приложения).
2. Если `Recv-Q` мал, но окно нулевое — возможно, достигнут лимит системной памяти или некорректно работает автотюнинг.

### Сценарий 2: Зондирование (Zero-Window Probe)

Если `rwnd` стал ненулевым, но ACK с этим обновлением потерялся, наступит тупик (deadlock). Чтобы этого избежать, отправитель посылает сегменты в 1 байт (**Persist Timer**), заставляя получателя прислать актуальный ACK с размером окна.
