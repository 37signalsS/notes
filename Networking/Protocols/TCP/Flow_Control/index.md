# Управление потоком в TCP (Flow Control)

## Определения

**Управление потоком (Flow Control)** — это механизм протокола TCP, предназначенный для предотвращения переполнения буфера на стороне получателя путем ограничения объема данных, который отправитель может передать без подтверждения.

**Основные термины:**

- **Receiver Window (rwnd):** текущий размер свободного буфера, объявленный получателем.
- **Zero Window (нулевое окно):** состояние, при котором буфер получателя полностью заполнен, и передача данных временно приостанавливается.
- **Zero-Window Probe:** контрольный сегмент, отправляемый для проверки изменения состояния нулевого окна.
- **Скользящее окно (Sliding Window):** фундаментальный механизм передачи, границы которого определяются подтвержденными данными и объявленным размером окна. Подробнее: [Скользящее окно в TCP](../reliability_mechanisms/sliding_window.md).

**Главное отличие:** Управление потоком защищает **получателя** (receiver-centric), в то время как [Управление перегрузкой](../congestion/tcp_congestion_control_overview.md) защищает **сеть** (network-centric).

## Основные концепции

### Механизм работы (Window Advertisement)

Получатель информирует отправителя о наличии свободного места в своем буфере через поле `Window Size` в каждом сегменте ACK.

```text
Отправитель                          Получатель
     |                                    |
     |  Данные (1000 байт) -------------> |  Буфер: 4000/5000 байт
     |                                    |  Свободно: 1000 байт
     |  <--- ACK, Window = 1000 --------- |  (объявление окна)
     |                                    |
     |  Данные (1000 байт) -------------> |  Буфер: 5000/5000 байт
     |                                    |  Свободно: 0 байт
     |  <--- ACK, Window = 0 ------------ |  (STOP!)
     |                                    |
     |  [Ожидание]                        |  [Приложение читает данные]
     |                                    |  Буфер: 3000/5000 байт
     |  <--- ACK, Window = 2000 --------- |  Свободно: 2000 байт
     |                                    |
     |  Данные (2000 байт) -------------> |
```

### Формула доступного окна передачи

Общий объем данных, который отправитель может держать «в полете» (in-flight), ограничен двумя значениями:

```text
Effective Window = min(cwnd, rwnd)

где:
  cwnd — окно перегрузки (congestion window), состояние сети.
  rwnd — окно получателя (receiver window), состояние буфера.
```

### Масштабирование окна (Window Scaling)

По умолчанию поле `Window Size` в заголовке TCP имеет размер 16 бит, что ограничивает максимальное окно значением 65 535 байт (64 КБ). Для современных высокоскоростных сетей этого недостаточно (проблема LFN — Long Fat Networks).

Опция **Window Scale** (RFC 7323) позволяет использовать множитель (степень 2), увеличивая эффективный размер окна до 1 ГБ.

### Скользящее окно (Sliding Window)

Механизм позволяет отправлять несколько сегментов подряд, не дожидаясь ACK для каждого из них.

**Границы окна:**

1. **Левая граница:** последний байт, подтвержденный получателем.
2. **Указатель отправки:** последний байт, физически отправленный в сеть.
3. **Правая граница:** `Левая граница + Window Size`.

При получении ACK левая граница сдвигается («скользит») вправо, открывая возможность для отправки новых данных.

## Практические сценарии

### Зондаж нулевого окна (Zero-Window Probe)

Если получатель объявил `Window = 0`, а затем его ACK с новым ненулевым окном потерялся в сети, возникнет взаимная блокировка (deadlock). Чтобы этого избежать:

1. Отправитель запускает **persist timer**.
2. По истечении таймера отправляется **Zero-Window Probe** (сегмент в 1 байт).
3. Получатель обязан ответить актуальным значением окна.

### Диагностика через утилиту ss

В Linux параметры окна можно увидеть с помощью команды `ss -tmo`:

```bash
ss -tmo
# Поля для анализа:
# rcvspace — текущий размер буфера приема (влияет на rwnd).
# cwnd — текущее окно перегрузки.
# wscale — коэффициенты масштабирования.
```

### Проблема Zero Window в нагруженных системах

**Симптом:** Соединение «зависает» при передаче больших объемов данных, в дампе трафика (tcpdump/Wireshark) видны пакеты `TCP ZeroWindow`.

**Причины:**

- Приложение-получатель читает данные слишком медленно (блокировки, GC, высокая нагрузка на CPU).
- Слишком малый размер системных буферов TCP.

**Решение:**

1. Оптимизировать производительность приложения (быстрое чтение из сокета).
2. Настроить автотюнинг буферов в ядре Linux. Подробнее в разделе [Оптимизация буферов TCP](../../../../Linux/Networking/Concepts/tcp_tuning/tcp_buffer_tuning.md).

## Дополнительная информация

### Взаимосвязь Flow Control и Congestion Control

| Характеристика | Управление потоком (Flow) | Управление перегрузкой (Congestion) |
| :--- | :--- | :--- |
| **Цель** | Защита получателя | Защита сети |
| **Параметр** | `rwnd` | `cwnd` |
| **Кто управляет** | Получатель (через ACK) | Отправитель (через алгоритмы) |
| **Механизм** | `Window Size` в заголовке | Алгоритмы (CUBIC, BBR, Reno) |

### Расчет пропускной способности

**Максимальная теоретическая скорость:**

```text
Throughput ≤ Window Size / RTT
```

Для канала 1 Гбит/с и задержки 50 мс требуется окно:

```text
Window ≥ 125 000 000 байт/с × 0.05 с = 6 250 000 байт (~6 МБ).
```
