# Отказ в установке TCP-соединения

## Определения

**Отказ в установке TCP-соединения (TCP Connection Refusal)** — это ситуация, при которой сетевое соединение не может быть установлено по одной из двух основных причин: либо удаленный узел явно отклонил запрос (флаг RST), либо запрос был проигнорирован, что привело к истечению времени ожидания (тайм-аут SYN).

**Основные типы отказа:**

| Тип отказа | Механизм | Ошибка приложения | Основная причина |
| :--- | :--- | :--- | :--- |
| **RST (Reset)** | Стек TCP присылает пакет с флагом RST. | `Connection refused` | Порт закрыт, либо правило REJECT на файрволе. |
| **SYN Timeout** | Стек TCP не получает ответа на SYN-пакеты. | `Connection timed out` | Хост выключен, либо правило DROP на файрволе. |

---

## Основные концепции

### Механизм RST (Reset)

Флаг RST используется для немедленного разрыва соединения или отклонения запроса на установку нового соединения. Если на удаленном хосте нет процесса, прослушивающего указанный порт, ядро ОС обязано ответить сегментом RST на входящий SYN.

**Особенности:**
- Происходит мгновенно (в пределах RTT).
- Не требует повторных попыток со стороны клиента.
- Освобождает ресурсы на обеих сторонах немедленно.

### Механизм SYN Timeout (Тайм-аут)

Если пакет SYN достигает узла, но тот его игнорирует (или пакет теряется в сети/отбрасывается файрволом с действием DROP), клиентский стек TCP переходит в режим ретрансмиссий.

**Алгоритм экспоненциального ожидания (Backoff):**
1. Отправка первого SYN.
2. Ожидание (обычно 1 сек).
3. Повторная отправка SYN.
4. Ожидание x2 (2 сек).
5. Повторная отправка SYN...
...и так далее до достижения лимита попыток (параметр `net.ipv4.tcp_syn_retries` в Linux).

### Сравнение REJECT и DROP в файрволах

Настройка сетевого экрана напрямую влияет на то, как клиент «увидит» отказ:

| Действие | Реакция клиента | Обоснование применения |
| :--- | :--- | :--- |
| **REJECT** | Получает `RST` (или ICMP Unreachable). | Вежливый отказ внутри доверенной сети для быстрой отладки. |
| **DROP** | Ждет по тайм-ауту. | Скрытие присутствия хоста от сканеров в публичных сетях. |

## Практические сценарии

### Сценарий 1: Диагностика «Connection refused»

**Симптом:** Ошибка возникает мгновенно при попытке подключения.

**Действия по поиску причины:**
1. **Проверить статус сервиса:** Убедиться, что приложение запущено на целевом сервере.
2. **Проверить Bind Address:** Убедиться, что сервис слушает нужный IP (например, `0.0.0.0` или конкретный адрес, а не только `127.0.0.1`).
   ```bash
   # Поиск процесса на порту 80
   ss -tlnp | grep :80
   ```
3. **Проверить локальный файрвол:** Убедиться, что правила `iptables`/`nftables` не возвращают `REJECT`.

### Сценарий 2: Диагностика «Connection timed out»

**Симптом:** Приложение «зависает» на 7–60 секунд перед выдачей ошибки.

**Действия по поиску причины:**
1. **Проверить доступность хоста:** Утилита `ping` (если ICMP разрешен) или `traceroute`.
2. **Сетевой захват (tcpdump):** Увидеть, уходят ли SYN-пакеты и приходят ли ответы.
   ```bash
   # Наблюдение за попытками SYN на порт 443
   tcpdump -i eth0 -nn 'port 443 and tcp[tcpflags] & tcp-syn != 0'
   ```
3. **Анализ пути:** Проверить промежуточные узлы (NAT, VPN-шлюзы), которые могут отбрасывать пакеты из-за неправильной маршрутизации.
