# Отказ в установке TCP-соединения

## Определения

**Отказ в установке TCP-соединения (TCP Connection Refusal)** — ситуация, при которой сетевое соединение не может быть установлено. Это происходит либо из-за явного отклонения запроса (флаг RST или ICMP Error), либо из-за игнорирования запроса (тайм-аут SYN).

**Основные типы отказа:**

| Тип отказа | Механизм | Ошибка приложения | Основная причина |
| :--- | :--- | :--- | :--- |
| **RST (Reset)** | Стек TCP присылает пакет с флагом RST. | `Connection refused` | Порт закрыт, либо правило REJECT на файрволе. |
| **ICMP Error** | Приходит ICMP Type 3 (Unreachable). | `No route to host` / `Refused` | Маршрутизация или фильтрация (Admin Prohibited). |
| **SYN Timeout** | Стек TCP не получает ответа на SYN-пакеты. | `Connection timed out` | Хост выключен, либо правило DROP на файрволе. |

---

## Основные концепции

### Механизм RST (Reset)

Флаг **RST** используется для немедленного отклонения запроса. Если на хосте нет процесса, прослушивающего порт, ядро ОС отвечает сегментом RST.

**Особенности:**
- Происходит мгновенно (в пределах RTT).
- Не требует повторных попыток со стороны клиента.
- Информирует отправителя, что хост активен, но сервис недоступен.

### Механизм ICMP Unreachable (Type 3)

Сетевое оборудование или файрволы могут отправлять сообщения ICMP для уточнения причины отказа:
- **Code 3 (Port Unreachable):** Обычно отправляется UDP-стеком, но может использоваться и для TCP.
- **Code 10/13 (Admin Prohibited):** Прямой сигнал от файрвола (ACL), что доступ запрещен.

### Механизм SYN Timeout и Backoff

Если SYN-пакет игнорируется (DROP), клиентский стек TCP переходит в режим ретрансмиссий с экспоненциальным ожиданием (**Binary Exponential Backoff**).

**Стандартный цикл в Linux (при `tcp_syn_retries = 6`):**
1. Отправка SYN #1 → ожидание 1 сек.
2. Отправка SYN #2 → ожидание 2 сек.
3. Отправка SYN #3 → ожидание 4 сек.
4. Отправка SYN #4 → ожидание 8 сек.
5. Отправка SYN #5 → ожидание 16 сек.
6. Отправка SYN #6 → ожидание 32 сек.
7. Итоговый тайм-аут (суммарно ~63 сек) → ошибка `ETIMEDOUT`.

## Практические сценарии

### Сценарий 1: Диагностика «Connection refused»

**Симптом:** Ошибка возникает мгновенно.

**Диагностика:**
1. Проверить, слушает ли сервис нужный интерфейс:
   ```bash
   ss -tlnp | grep :80
   # → LISTEN 0 128 0.0.0.0:80 0.0.0.0:* users:(("nginx",pid=123,fd=6))
   ```
   *Если в выводе только `127.0.0.1:80`, внешние подключения будут отклоняться с RST.*

2. Проверить локальные правила (REJECT):
   ```bash
   sudo iptables -S | grep REJECT
   # → -A INPUT -p tcp --dport 80 -j REJECT --reject-with tcp-reset
   ```

### Сценарий 2: Диагностика SYN-тайм-аута (DROP)

**Симптом:** Приложение «зависает» на минуту.

**Диагностика через tcpdump:**
```bash
sudo tcpdump -i eth0 -nn 'port 443 and tcp[tcpflags] & tcp-syn != 0'
# → 12:00:01.100 IP 1.1.1.1.54321 > 2.2.2.2.443: Flags [S], seq 1000
# → 12:00:02.105 IP 1.1.1.1.54321 > 2.2.2.2.443: Flags [S], seq 1000 (retrans)
# → ... (отсутствие входящих SYN-ACK или RST)
```

### Сценарий 3: Использование eBPF для поиска «тихих» дропов (2026)

Современный способ увидеть, где именно ядро или файрвол отбрасывает пакеты:
```bash
# Мониторинг отброшенных TCP-пакетов через tcpdrop (из bcc-tools)
sudo tcpdrop
# → TIME     PID     IP  SADDR:SPORT          > DADDR:DPORT          STATE
# → 12:01:00 0       4   1.1.1.1:54321        > 2.2.2.2:443          SYN_SENT
```
