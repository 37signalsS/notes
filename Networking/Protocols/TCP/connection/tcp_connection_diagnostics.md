# Диагностика TCP-соединений

## Определения

**Диагностика TCP-соединений** — это совокупность методов анализа состояния TCP-сокетов и сетевого трафика для выявления проблем при установке соединений, обнаружения потерь пакетов и выявления ошибок конфигурации сетевого стека.

**Основные инструменты:**

- `ss` — утилита для анализа состояния сокетов (современная и быстрая замена `netstat`). Подробная документация: [**ss**](../../../../Linux/Diagnostics/Networking/ss.md).
- `tcpdump` — инструмент для перехвата и анализа сетевого трафика в реальном времени.

---

## Основные концепции

### TCP-флаги в выводе tcpdump

При анализе дампов трафика используются сокращенные обозначения флагов. Полная таблица флагов и их комбинаций приведена в руководстве по [**tcpdump**](../../../../Linux/Diagnostics/Networking/tcpdump.md#tcp-флаги-в-выводе-tcpdump).

### Состояния TCP для диагностики

Критически важные состояния, на которые следует обращать внимание:

- **ESTAB:** активное соединение, идет обмен данными.
- **TIME_WAIT:** соединение закрыто инициатором, ожидание периода 2×MSL для очистки сети от дубликатов.
- **CLOSE_WAIT:** удаленная сторона закрыла соединение, но локальное приложение еще не вызвало закрытие сокета (возможная утечка).
- **SYN_RECV:** получено SYN, отправлено SYN-ACK, ожидается финальный ACK (возможна атака SYN-флуд).

*Полная таблица всех состояний:* [Состояния TCP](./tcp_connection_states.md).

## Практические сценарии

### Сценарий 1: Анализ состояний сокетов через ss

```bash
# Список всех TCP-соединений с их текущими состояниями
ss -tan

# Список соединений с указанием процессов (владельцев сокетов)
ss -tanp

# Группировка и подсчет соединений по состояниям
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c

# Пример вывода:
#   1500 ESTAB
#     50 TIME_WAIT
#     10 CLOSE_WAIT
#      5 SYN_RECV
```

**Интерпретация:**

- Большое количество `CLOSE_WAIT` указывает на то, что приложение не закрывает сокеты корректно.
- Всплеск `SYN_RECV` может свидетельствовать о начале DDoS-атаки типа SYN-флуд.
- Большое количество `TIME_WAIT` на сервере при высокой нагрузке может потребовать включения `tcp_tw_reuse`.

### Сценарий 2: Анализ процесса Handshake через tcpdump

```bash
# Перехват процесса установки соединения на порту 80
tcpdump -i eth0 -nn 'tcp port 80' -v

# Пример вывода (3-way handshake):
# 10:15:30.123456 IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [S], seq 1234567890
# 10:15:30.130000 IP 93.184.216.34.80 > 192.168.1.10.54321: Flags [S.], seq 987654321, ack 1234567891
# 10:15:30.135000 IP 192.168.1.10.54321 > 93.184.216.34.80: Flags [.], ack 987654322
```

**Анализ задержек:**

- Время между `SYN` и `SYN-ACK` соответствует RTT (Round-Trip Time) до сервера.
- Отсутствие `SYN-ACK` означает, что сервер недоступен, либо пакеты отбрасываются (DROP) сетевым экраном.

### Сценарий 3: Диагностика аварийного сброса (RST)

Флаг RST означает мгновенное прерывание соединения без прохождения стандартной процедуры закрытия.

```bash
# Перехват только пакетов с установленным флагом RST
tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-rst != 0'
```

| Причина RST | Описание | Решение |
| :--- | :--- | :--- |
| **Порт закрыт** | Сервер отвечает RST на попытку SYN. | Запустить приложение или проверить порт. |
| **Приложение упало** | Соединение было ESTABLISHED, но сервер прислал RST на данные. | Проверить логи и состояние сервиса. |
| **Фаервол (REJECT)** | Правило REJECT на сетевом экране. | Проверить правила iptables/nftables. |
