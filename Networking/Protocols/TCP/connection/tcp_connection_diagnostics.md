# Диагностика TCP-соединений

## Определения

**Диагностика TCP-соединений** — процесс анализа жизненного цикла сокетов (установка, передача данных, закрытие) для выявления проблем с производительностью, надежностью или безопасностью сетевого взаимодействия.

---

## Основные инструменты

### 1. Утилита ss (Socket Statistics)

Современная замена `netstat`. Позволяет быстро просматривать состояния сокетов и детальные метрики стека TCP.

**Базовые команды:**
```bash
# Список всех TCP-соединений с их текущими состояниями
ss -tan
# → State      Recv-Q Send-Q Local Address:Port  Peer Address:Port
# → ESTAB      0      0      192.168.1.10:443    1.2.3.4:54321

# Группировка и подсчет соединений по состояниям
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c
# →   1500 ESTAB
# →     50 TIME_WAIT
# →     10 CLOSE_WAIT
```

**Глубокая диагностика (`ss -ti`):**
Позволяет увидеть внутренние параметры алгоритмов управления перегрузкой.
```bash
ss -ti dst 1.2.3.4
# → cubic rto:204 rtt:15.2/0.5 cwnd:120 ssthresh:50 retrans:0/125 delivery_rate 120Mbps
```
- `rtt:15.2/0.5`: Среднее RTT и его отклонение (jitter). Высокое отклонение указывает на нестабильность канала.
- `retrans:текущие/всего`: Общая статистика потерь за сессию.
- `cwnd`: Текущее окно перегрузки (в MSS).

### 2. Захват пакетов (tcpdump)

Используется для анализа аномалий на уровне протокола (некорректные флаги, дубликаты ACK).

```bash
# Захват только этапа установления соединения (SYN)
sudo tcpdump -i any -nn 'tcp[tcpflags] & tcp-syn != 0'
# → 12:00:01 IP 1.1.1.1.54321 > 2.2.2.2.80: Flags [S], seq 1000, win 65535, options [mss 1460,sackOK]
```
*Подробнее:* [tcpdump в Linux](../../../../Linux/Diagnostics/Networking/tcpdump.md).

### 3. eBPF Мониторинг (2026)

Современные инструменты мониторинга позволяют отслеживать жизненный цикл соединений без захвата трафика.

- **tcpstates:** Показывает переходы состояний FSM в реальном времени.
- **tcplife:** Выводит сводку по каждому завершенному соединению (длительность, переданные байты).

```bash
sudo tcplife
# → PID   COMM       LADDR           LPORT RADDR           RPORT TX_KB RX_KB MS
# → 1234  nginx      192.168.1.10    443   1.2.3.4         54321 150   200   1050
```

## Критические состояния сокетов

| Состояние | Признак проблемы | Сценарий диагностики |
| :--- | :--- | :--- |
| **SYN_RECV** | Рост количества (>10-20) | Возможный SYN-флуд или переполнение `backlog`. |
| **CLOSE_WAIT** | Стабильное наличие у одного процесса | Утечка сокетов: приложение не вызывает `close()`. |
| **TIME_WAIT** | Тысячи соединений с одного IP | Исчерпание эфемерных портов на прокси/клиенте. |
| **ESTABLISHED** | Высокий `Send-Q` | Получатель не успевает вычитывать данные или канал перегружен. |

## Практические сценарии

### Сценарий 1: Поиск «медленного» приложения

Если клиент жалуется на задержки, проверьте `rtt` и `cwnd` для его IP:
```bash
ss -ti dst 1.2.3.4
```
Если `cwnd` велик, а `rtt` мал — проблема в логике приложения (Application Latency). Если `cwnd` мал при высоком RTT — проблема в сети.

### Сценарий 2: Идентификация утечки сокетов

Если количество `CLOSE_WAIT` растет:
```bash
ss -tanp state close-wait
# → CLOSE-WAIT 0 0 127.0.0.1:8080 127.0.0.1:54321 users:(("python3",pid=1234,fd=5))
```
*Флаг `-p` показывает процесс-владелец, что позволяет связаться с разработчиками для исправления `close()`.*
