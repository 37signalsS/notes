# Состояния TCP-соединений

## Определения

Протокол TCP является **конечным автоматом (Finite State Machine, FSM)**. Это означает, что любое TCP-соединение в каждый момент времени находится в одном из 11 строго определенных состояний. Переход из одного состояния в другое происходит в ответ на определенные события: системные вызовы приложения (открытие, закрытие), получение сегментов с определенными флагами (SYN, ACK, FIN, RST) или истечение таймеров.

---

## Основные концепции

### Полная таблица состояний

| Состояние | Описание | Роль | Переход в следующее состояние |
| :--- | :--- | :--- | :--- |
| **CLOSED** | Исходное состояние: соединение отсутствует. | — | Приложение открывает порт (LISTEN) или инициирует SYN. |
| **LISTEN** | Ожидание входящих запросов на соединение. | Сервер | Получен SYN -> переход в SYN_RECEIVED. |
| **SYN_SENT** | Отправлен SYN-запрос, ожидание SYN-ACK. | Клиент | Получен SYN-ACK -> переход в ESTABLISHED. |
| **SYN_RECEIVED** | Отправлен SYN-ACK, ожидание финального ACK. | Сервер | Получен ACK -> переход в ESTABLISHED. |
| **ESTABLISHED** | Соединение установлено, идет активный обмен данными. | Обе | Приложение инициирует закрытие (FIN) или получен FIN. |
| **FIN_WAIT_1** | Отправлен FIN, ожидание ACK или FIN от партнера. | Инициатор | Получен ACK -> переход в FIN_WAIT_2. |
| **FIN_WAIT_2** | Получен ACK на наш FIN, ожидание FIN от партнера. | Инициатор | Получен FIN -> отправка ACK -> переход в TIME_WAIT. |
| **CLOSE_WAIT** | Получен FIN от партнера, ожидание закрытия в приложении. | Получатель | Приложение вызывает `close()` -> переход в LAST_ACK. |
| **CLOSING** | Редкий случай одновременного закрытия с обеих сторон. | Обе | Получен ACK на наш FIN -> переход в TIME_WAIT. |
| **LAST_ACK** | Отправлен FIN после CLOSE_WAIT, ожидание финального ACK. | Получатель | Получен ACK -> переход в CLOSED. |
| **TIME_WAIT** | Ожидание 2×MSL для очистки сети от дубликатов. | Инициатор | Истечение таймера -> переход в CLOSED. |

### Диаграмма состояний

```text
                          +--------+
                          | CLOSED |
                          +---+----+
                              |
         +--------------------+--------------------+
         | (passive open)    | (active open)       |
         v                   v                     |
     +-------+           +--------+                |
     | LISTEN|           | SYN_SENT|               |
     +---+---+           +----+---+                |
         | (recv SYN)        | (recv SYN-ACK)      |
         v                   v                     |
     +-----------+       +--------+                |
     | SYN_RECV  |<----| SYN_SENT|               |
     +-----+-----+       +--------+                |
           | (recv ACK)    | (recv ACK)            |
           v               v                       |
       +-------------+     +-------------+         |
       | ESTABLISHED |<----| ESTABLISHED |         |
       +------+------+     +------+------+         |
              | (app close)      | (recv FIN)      |
              v                  v                 |
       +------------+      +------------+          |
       | FIN_WAIT_1 |      | CLOSE_WAIT |          |
       +-----+------+      +-----+------+          |
             | (recv ACK)        | (app close)     |
             v                   v                 |
       +------------+      +------------+          |
       | FIN_WAIT_2 |      | LAST_ACK   |          |
       +-----+------+      +-----+------+          |
             | (recv FIN)      | (recv ACK)        |
             v                 v                   |
       +------------+      +------------+          |
       | TIME_WAIT  |<-----| CLOSING    |----------+
       +-----+------+      +------------+
             | (2×MSL timeout)
             v
         +--------+
         | CLOSED |
         +--------+
```

## Практические сценарии

### Анализ проблемных состояний

#### 1. CLOSE_WAIT (Проблема на стороне приложения)

**Симптом:** Большое количество сокетов в состоянии `CLOSE_WAIT`.
**Причина:** Удаленная сторона закрыла соединение, но локальное приложение не вызвало функцию `close()`. Это типичная «утечка сокетов».
**Диагностика:**

```bash
# Группировка и подсчет соединений по состояниям
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c
# →   1500 ESTAB
# →     10 CLOSE_WAIT

# Найти процессы, не закрывающие сокеты
ss -tanp state close-wait
# → CLOSE-WAIT 0 0 127.0.0.1:8080 127.0.0.1:54321 users:(("python3",pid=1234,fd=5))
```

**Решение:** Исправление логики приложения для обязательного закрытия сокетов после завершения обработки данных (например, использование `try-finally` или `with` в Python).

#### 2. TIME_WAIT (Проблема при высокой частоте соединений)

**Симптом:** Исчерпание эфемерных портов на клиенте или прокси-сервере.
**Причина:** Состояние `TIME_WAIT` является нормальным и длится 2×MSL (60 секунд в Linux). При огромном количестве коротких соединений порты не успевают освобождаться.
**Решение:**

- **Connection Pooling:** Использование постоянных соединений (Keepalive).
- **net.ipv4.tcp_tw_reuse = 1:** Позволяет безопасно переиспользовать сокеты в `TIME_WAIT` для новых исходящих соединений.
- **Масштабирование IP:** Использование нескольких IP-адресов для исходящего трафика (увеличивает количество возможных 5-tuple).
*Подробнее:* [Управление TIME_WAIT в Linux](../../../../Linux/Networking/Concepts/tcp_tuning/tcp_time_wait_management.md).

#### 3. SYN_RECV (Признак атаки или перегрузки)

**Симптом:** Резкий рост количества сокетов в состоянии `SYN_RECV`.
**Причина:** SYN-флуд или переполнение очереди `backlog` сервера.
**Диагностика:**
```bash
ss -tan state syn-recv | wc -l
# → 500 (при норме < 5)
```
**Решение:** Включение SYN cookies (`net.ipv4.tcp_syncookies = 1`) и увеличение `net.ipv4.tcp_max_syn_backlog`.
*См. также:* [SYN-флуд и защита](../../../Concepts/Security/ddos_overview.md#syn-флуд).

### Переходы при получении RST (Reset)

Сегмент с флагом **RST** вызывает немедленный переход сокета в состояние `CLOSED` из любого текущего состояния.

| Текущее состояние | Причина получения RST | Последствие |
| :--- | :--- | :--- |
| **SYN_SENT** | Порт закрыт на сервере | Ошибка «Connection refused». |
| **ESTABLISHED** | Сбой процесса или перезагрузка узла | Аварийный разрыв сессии. |
| **FIN_WAIT** | Удаленная сторона уже удалила сокет | Ускоренное освобождение ресурсов. |

*Подробнее:* [Отказ в установке соединения](./tcp_connection_refusal.md).
