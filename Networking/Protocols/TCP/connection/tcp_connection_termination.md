# Завершение TCP-соединения

## Определения

**Завершение TCP-соединения (Connection Termination)** — процесс упорядоченного разрыва двустороннего канала связи, гарантирующий доставку всех данных, находящихся «в полете», перед закрытием сокетов. В отличие от установки, стандартное завершение требует обмена четырьмя сегментами (4-way handshake).

---

## Основные концепции

### Стандартная процедура (4-way Handshake)

TCP-соединение является полнодуплексным, поэтому каждая сторона должна закрыть свою часть канала независимо.

```text
Инициатор (Active Close)                 Партнер (Passive Close)
     |                                        |
     |  1. FIN (seq=A) ---------------------> |  Переход в CLOSE_WAIT
     |  Переход в FIN_WAIT_1                  |  (Приложение уведомлено)
     |                                        |
     |  2. <---------------- ACK (ack=A+1) ---|
     |  Переход в FIN_WAIT_2                  |
     |                                        |
     |  [Возможна досылка данных от Партнера] |
     |                                        |
     |  3. <---------------- FIN (seq=B) -----|  Приложение вызвало close()
     |                                        |  Переход в LAST_ACK
     |                                        |
     |  4. ACK (ack=B+1) -------------------> |
     |  Переход в TIME_WAIT                   |  Переход в CLOSED
     |                                        |
     |  (Ожидание 2×MSL)                      |
     v                                        v
  CLOSED                                   CLOSED
```

### Одновременное закрытие (Simultaneous Close)

Редкая ситуация, когда оба узла отправляют FIN одновременно. В этом случае соединение проходит через состояние **CLOSING**, после чего оба узла переходят в **TIME_WAIT**.

### Полузакрытое состояние (Half-Close)

TCP позволяет закрыть поток данных только в одном направлении. Это происходит, когда одна сторона отправляет FIN, а вторая продолжает слать данные.
- **Механизм:** Системный вызов `shutdown(s, SHUT_WR)` отправляет FIN, переводя локальный сокет в `FIN_WAIT_1`, но оставляет его открытым для чтения.
- **Применение:** Передача файлов или запросов, где отправитель должен сигнализировать об окончании данных, но ожидает финальный ответ (например, HTTP-запросы в некоторых реализациях).

### Опция сокета SO_LINGER

Управляет поведением функции `close()` при наличии данных в буфере отправки.
- **Linger Off (по умолчанию):** `close()` возвращается немедленно, ядро пытается отправить данные в фоновом режиме.
- **Linger On (timeout > 0):** `close()` блокируется до тех пор, пока данные не будут подтверждены или не истечет таймаут.
- **Linger On (timeout = 0):** Соединение разрывается немедленно через **RST**. Состояние `TIME_WAIT` пропускается, данные в буферах отбрасываются. Используется для предотвращения накопления `TIME_WAIT` в специфических высоконагруженных сценариях (с осторожностью).

### Состояние TIME_WAIT и его роль

Состояние **TIME_WAIT** длится $2 \times MSL$ (Maximum Segment Lifetime). В Linux этот интервал составляет 60 секунд.
**Назначение:**
1.  **Гарантия доставки ACK:** Если последний ACK (шаг 4) потеряется, партнер переотправит свой FIN. Инициатор должен быть в состоянии ответить.
2.  **Очистка сети:** Предотвращение ситуации, когда задержавшиеся пакеты старого соединения будут ошибочно приняты новым соединением с теми же портами (5-tuple).

### Orphan Sockets (Сокеты-сироты)

Когда приложение вызывает `close()`, сокет переходит в ведение ядра и становится «сиротой». 
- **Лимит:** Ограничивается параметром `net.ipv4.tcp_max_orphans`.
- **Тайм-аут:** Сокеты в состоянии `FIN_WAIT_2` без активного приложения закрываются через время, указанное в `net.ipv4.tcp_fin_timeout` (обычно 60 сек).
- **Ретрансмиссии:** Параметр `net.ipv4.tcp_orphan_retries` определяет, сколько раз ядро будет пытаться отправить FIN для "осиротевшего" сокета перед его принудительным закрытием.

## Практические сценарии

### Сценарий 1: Мониторинг завершающихся соединений

Для анализа «зависших» в процессе закрытия сокетов используется `ss`.

```bash
# Список сокетов в состояниях закрытия
ss -tan state fin-wait-1 state fin-wait-2 state close-wait
# → State      Recv-Q Send-Q Local Address:Port  Peer Address:Port
# → FIN-WAIT-2 0      0      192.168.1.10:443    1.2.3.4:54321

# Просмотр статистики сокетов-сирот (orphans)
ss -s
# → Total: 156 (kernel 160)
# → TCP:   45 (estab 10, closed 5, orphaned 2, timewait 28)
```

### Сценарий 2: Диагностика CLOSE_WAIT

Если сокеты массово копятся в **CLOSE_WAIT**, это означает, что партнер закрыл соединение, но локальное приложение «забыло» вызвать `close()`.

```bash
# Найти процесс, удерживающий сокеты в CLOSE_WAIT
ss -tanp state close-wait
# → CLOSE-WAIT 0 0 127.0.0.1:8080 127.0.0.1:54321 users:(("java",pid=999,fd=14))
```

### Сценарий 3: Аварийный разрыв (RST)

Если приложению нужно немедленно разорвать соединение без 4-way handshake (например, при критической ошибке), оно отправляет сегмент с флагом **RST**. Это немедленно переводит обе стороны в состояние **CLOSED** без фазы TIME_WAIT.
