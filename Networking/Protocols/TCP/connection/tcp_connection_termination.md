# Завершение TCP-соединения

## Определения

**Завершение TCP-соединения (Connection Termination)** — процесс упорядоченного разрыва двустороннего логического канала связи. В отличие от установки соединения (3-way handshake), стандартное закрытие требует обмена четырьмя сегментами (**4-way handshake**). Это связано с тем, что TCP-канал является полнодуплексным, и каждая сторона должна независимо подтвердить завершение передачи данных в своем направлении.

---

## Основные концепции

### Стандартная процедура (4-way Handshake)

```text
Инициатор (Active Close)                 Партнер (Passive Close)
     |                                        |
     |  1. FIN (seq=A) ---------------------> |  Переход в CLOSE_WAIT
     |  Переход в FIN_WAIT_1                  |  (Приложение уведомлено)
     |                                        |
     |  2. <---------------- ACK (ack=A+1) ---|
     |  Переход в FIN_WAIT_2                  |
     |                                        |
     |  [Возможна досылка данных от Партнера] |
     |                                        |
     |  3. <---------------- FIN (seq=B) -----|  Приложение вызвало close()
     |                                        |  Переход в LAST_ACK
     |                                        |
     |  4. ACK (ack=B+1) -------------------> |
     |  Переход в TIME_WAIT                   |  Переход в CLOSED
     |                                        |
     |  (Ожидание 2×MSL)                      |
     v                                        v
  CLOSED                                   CLOSED
```

1. **FIN 1:** Инициатор вызывает `close()` и отправляет сегмент с флагом `FIN`, уведомляя, что больше не будет посылать данные.
2. **ACK 1:** Партнер подтверждает получение `FIN`. На этом этапе соединение закрыто наполовину. Партнер все еще может отправлять данные инициатору.
3. **FIN 2:** Когда приложение партнера заканчивает отправку своих данных, оно также вызывает `close()`, генерируя свой `FIN`.
4. **ACK 2:** Инициатор подтверждает финальный `FIN` и переходит в состояние ожидания `TIME_WAIT`.

### Полузакрытое состояние (Half-Close)

TCP позволяет закрыть поток данных только в одном направлении, оставляя его открытым для приема.
- **Механизм:** Использование системного вызова `shutdown(socket, SHUT_WR)`. Он отправляет `FIN`, переводя локальный сокет в `FIN_WAIT_1`, но оставляет дескриптор открытым для чтения.
- **Применение:** Передача запросов, где отправитель сигнализирует об окончании данных (EOF), но готов долго ожидать финальный ответ от сервера.

### Одновременное закрытие (Simultaneous Close)

Редкая ситуация, при которой оба узла отправляют `FIN` одновременно, не успев получить `FIN` от партнера. В этом случае оба переходят в состояние **CLOSING**, подтверждают `FIN` друг друга отправкой `ACK` и переходят сразу в **TIME_WAIT**.

### Состояние TIME_WAIT

Длится $2 \times MSL$ (Maximum Segment Lifetime), что в Linux жестко зафиксировано на уровне **60 секунд**.
**Критические задачи:**
1.  **Гарантия доставки последнего ACK:** Если финальный `ACK` (шаг 4) потеряется, партнер переотправит свой `FIN`. Инициатор, находясь в `TIME_WAIT`, корректно ответит новым `ACK`. Если бы сокет удалялся немедленно, ядро ответило бы `RST`, что считается ошибкой.
2.  **Защита от старых дубликатов:** Ожидание гарантирует, что "заблудившиеся" в сети пакеты от текущей сессии погибнут и не вмешаются в новую сессию, если порты будут переиспользованы.

### Опция сокета SO_LINGER

Управляет поведением системного вызова `close()`, если в буфере сокета еще остались неотправленные данные.
- **Linger Off (по умолчанию):** `close()` возвращает управление приложению немедленно. Ядро берет на себя фоновую отправку остатков данных и `FIN`.
- **Linger On (timeout > 0):** `close()` блокирует поток приложения до тех пор, пока данные не будут отправлены и подтверждены, либо пока не истечет указанный таймаут.
- **Linger On (timeout = 0):** Соединение немедленно разрывается сегментом **RST** (Abortive Close). Состояние `TIME_WAIT` игнорируется, неотправленные данные отбрасываются. Используется в высоконагруженных прокси для агрессивного освобождения портов (сопряжено с риском).

### Сиротские сокеты (Orphan Sockets)

После вызова `close()` сокет больше не привязан к процессу (у него нет дескриптора в User Space). Ядро должно самостоятельно довести процесс закрытия до конца.
- **`net.ipv4.tcp_max_orphans`:** Лимит на количество сокетов-сирот. Если превышен, ядро удаляет сокет и отправляет `RST` (спасет от исчерпания памяти при атаках).
- **`net.ipv4.tcp_orphan_retries`:** Количество повторных попыток отправки `FIN` для сиротских сокетов (по умолчанию часто 8).
- **`net.ipv4.tcp_fin_timeout`:** Определяет, сколько времени (в секундах) сокет будет ожидать `FIN` от партнера в состоянии `FIN_WAIT_2` перед принудительным уничтожением (по умолчанию 60с).

## Практические сценарии

### Сценарий 1: Мониторинг процесса завершения

Для диагностики зависших в памяти соединений используйте утилиту `ss`.

```bash
# Просмотр сокетов в стадиях активного разрыва
ss -tan state fin-wait-1 state fin-wait-2 state close-wait
# → State      Recv-Q Send-Q Local Address:Port  Peer Address:Port
# → FIN-WAIT-2 0      0      192.168.1.10:443    1.2.3.4:54321

# Проверка количества сокетов-сирот, обрабатываемых ядром
ss -s
# → Total: 156 (kernel 160)
# → TCP:   45 (estab 10, closed 5, orphaned 2, timewait 28)
```
*Если значение `orphaned` приближается к лимиту `tcp_max_orphans`, сервер может начать неконтролируемо сбрасывать соединения.*

### Сценарий 2: Аварийный разрыв (RST)

Если приложение аварийно падает (например, OOM Killer завершает процесс), ядро закрывает все открытые им файловые дескрипторы. Если в буфере приема были непрочитанные данные, вместо отправки `FIN` ядро отправит `RST`.
Это позволяет партнеру немедленно узнать, что часть переданных им данных так и не была обработана приложением.
