# Завершение TCP-соединения

## Определения

**Завершение TCP-соединения (Connection Termination)** — процесс упорядоченного разрыва двустороннего логического канала связи. В отличие от установки соединения (3-way handshake), стандартное закрытие требует обмена четырьмя сегментами (**4-way handshake**). Это связано с тем, что TCP-канал является полнодуплексным, и каждая сторона должна независимо подтвердить завершение передачи данных в своем направлении.

**Ключевые характеристики завершения:**
- **FIN потребляет 1 Sequence Number:** В отличие от ACK, сегмент с флагом `FIN` занимает один виртуальный байт в последовательности, что гарантирует его подтверждение кумулятивным ACK (RFC 9293).
- **Асимметричность ролей:** Инициатор закрытия (тот, кто первый вызвал `close()`) перейдет в `TIME_WAIT` и будет удерживать сокет 60 секунд. Партнер перейдет в `CLOSED` сразу после получения ACK на свой FIN.
- **Гарантия доставки:** TCP не может позволить себе \"потерять\" FIN, так как это приведет к зависанию соединения навсегда. Поэтому используются таймеры и повторные передачи.

---

## Методология диагностики (Bottom-up)

Диагностика проблем завершения должна следовать иерархии:

1. **Уровень 1: Определение роли** — кто инициатор закрытия (Active Close), а кто Passive Close?
2. **Уровень 2: Определение состояния** — в каком FSM состоянии находится каждый сокет?
3. **Уровень 3: Анализ поведения** — есть ли утечки (CLOSE_WAIT), зависания (FIN_WAIT_2), или исчерпание (TIME_WAIT)?
4. **Уровень 4: Прикладной анализ** — корректно ли приложение обрабатывает события закрытия?

**Принцип \"Исключения\":** Начинайте с проверки самых простых причин (сервис запущен? соединение established?), прежде чем углубляться в анализ таймеров и FSM-состояний.

## Основные концепции

### Стандартная процедура (4-way Handshake)

```text
Инициатор (Active Close)                 Партнер (Passive Close)
     |                                        |
     |  1. FIN (seq=A) ---------------------> |  Переход в CLOSE_WAIT
     |  Переход в FIN_WAIT_1                  |  (Приложение уведомлено)
     |                                        |
     |  2. <---------------- ACK (ack=A+1) ---|
     |  Переход в FIN_WAIT_2                  |
     |                                        |
     |  [Возможна досылка данных от Партнера] |
     |                                        |
     |  3. <---------------- FIN (seq=B) -----|  Приложение вызвало close()
     |                                        |  Переход в LAST_ACK
     |                                        |
     |  4. ACK (ack=B+1) -------------------> |
     |  Переход в TIME_WAIT                   |  Переход в CLOSED
     |                                        |
     |  (Ожидание 2×MSL)                      |
     v                                        v
  CLOSED                                   CLOSED
```

**Детальный разбор каждого шага:**

1. **FIN 1:** Инициатор вызывает `close()` и отправляет сегмент с флагом `FIN`, уведомляя, что больше не будет посылать данные. FIN **потребляет 1 Sequence Number** (RFC 9293). Переход в `FIN_WAIT_1`.
2. **ACK 1:** Партнер подтверждает получение `FIN` кумулятивным ACK (ack=A+1). На этом этапе соединение закрыто наполовину (half-close). Партнер все еще может отправлять данные инициатору. Инициатор переходит в `FIN_WAIT_2`.
3. **FIN 2:** Когда приложение партнера заканчивает отправку своих данных, оно также вызывает `close()`, генерируя свой `FIN`. FIN также потребует 1 Sequence Number. Партнер переходит в `LAST_ACK`.
4. **ACK 2:** Инициатор подтверждает финальный `FIN` (ack=B+1) и переходит в состояние ожидания `TIME_WAIT`. Партнер, получив ACK, переходит в `CLOSED`.

### Правила генерации RST (Reset)

TCP-стек ядра Linux генерирует сегменты RST в следующих случаях (влияют на завершение):

| Ситуация | Типичная ошибка | Описание |
| :--- | :--- | :--- |
| **Сокет в CLOSED** | — | Получен пакет для несуществующего соединения. Ядро отвечает RST. |
| **Ожидание ACK на FIN** | — | Приложение закрылось, но ACK не пришел в течение `tcp_orphan_retries`. |
| **Accept Queue переполнен** | — | `tcp_abort_on_overflow=1` — отправка RST вместо игнорирования. |
| **SO_LINGER timeout=0** | — | `close()` с `l_linger=0` вызывает RST вместо FIN (Abortive Close). |
| **OOM Killer** | — | Процесс убит, непрочитанные данные в буфере — RST вместо FIN. |
| **Порт не слушает** | ECONNREFUSED | Получен SYN на закрытый порт — ответ RST. |
| **Файрвол REJECT** | — | `iptables -j REJECT --reject-with tcp-reset` — отправка RST. |

**Важно:** RST **не требует** подтверждения (ACK). Получив RST, сокет немедленно переходит в `CLOSED` из любого состояния. Состояние `TIME_WAIT` для RST **не создается**.

### Полузакрытое состояние (Half-Close)

TCP позволяет закрыть поток данных только в одном направлении, оставляя его открытым для приема.

- **Механизм через `shutdown()`:** Использование системного вызова `shutdown(socket, SHUT_WR)` отправляет `FIN`, переводя локальный сокет в `FIN_WAIT_1`, но оставляет дескриптор открытым для чтения.
- **Механизм через `close()`:** Если приложение вызывает `close()` для дескриптора с двумя направлениями, ядро отправит `FIN` и для чтения, и для записи (если нет дублирующих дескрипторов).
- **Применение:** Передача запросов, где отправитель сигнализирует об окончании данных (EOF), но готов долго ожидать финальный ответ от сервера (например, request-response протоколы).

**SHUT_RD (только чтение):** Вызов `shutdown(socket, SHUT_RD)` не отправляет FIN и не влияет на партнера. Он лишь указывает ядру, что приложение больше не хочет читать данные. Данные продолжают поступать в буфер, пока не заполнится `SO_RCVBUF`. При следующем вызове `read()` будет возвращен 0 (EOF). **Важно:** `SHUT_RD` не является частью протокола и не виден удаленной стороне.

### Одновременное закрытие (Simultaneous Close)

Редкая ситуация, при которой оба узла отправляют `FIN` одновременно, не успев получить `FIN` от партнера. В этом случае оба переходят в состояние **CLOSING**.

```text
     Узел A                                Узел B
     |                                      |
     |  FIN (seq=A) ----------------------> |
     |  (переход в CLOSING)                 |
     |                                      |  FIN (seq=B)
     | <----------------------------------- |
     |              (переход в CLOSING)      |
     |                                      |
     |  ACK (ack=B+1) -------------------> |
     |              (переход в TIME_WAIT)    |
     |                                      |
     | <----------------------------------- ACK (ack=A+1)
     |  (переход в TIME_WAIT)               |
     v                                      v
```

### Состояние TIME_WAIT

Длится $2 \times MSL$ (Maximum Segment Lifetime), что в Linux жестко зафиксировано на уровне **60 секунд** (RFC 9293 рекомендует 120 секунд, но Linux использует 60).

**Критические задачи:**
1.  **Гарантия доставки последнего ACK:** Если финальный `ACK` (шаг 4) потеряется, партнер переотправит свой `FIN`. Инициатор, находясь в `TIME_WAIT`, корректно ответит новым `ACK`. Если бы сокет удалялся немедленно, ядро ответило бы `RST`, что считается ошибкой (партнер не смог бы отличить потерю FIN от потери ACK).
2.  **Защита от старых дубликатов:** Ожидание гарантирует, что \"заблудившиеся\" в сети пакеты от текущей сессии погибнут и не вмешаются в новую сессию, если порты будут переиспользованы (TCP Timestamps подтверждают уникальность пакета).

**Почему именно 2×MSL:**
- 1 MSL — время жизни пакета в сети (отправка + доставка)
- 1 MSL — время жизни ответа (ACK) на обратном пути
- Итого: 2 MSL гарантирует, что все пакеты текущей сессии погибнут

### Опция сокета SO_LINGER

Управляет поведением системного вызова `close()`, если в буфере сокета еще остались неотправленные данные.

| Режим | Параметры | Поведение `close()` | Результат |
| :--- | :--- | :--- | :--- |
| **Linger Off** (по умолчанию) | `l_onoff=0` | Немедленный возврат | Ядро отправляет FIN в фоне; данные отправляются асинхронно |
| **Linger On (timeout > 0)** | `l_onoff=1, l_linger=N` | Блокировка на N секунд | Данные отправляются и подтверждаются; если таймаут — ошибка `EWOULDBLOCK` |
| **Linger On (timeout = 0)** | `l_onoff=1, l_linger=0` | Немедленный возврат | **Abortive Close:** RST вместо FIN, `TIME_WAIT` не создается, неотправленные данные отбрасываются |

**Важно:** Abortive Close с `SO_LINGER(0)` опасен, так как удаленная сторона получит `Connection reset by peer` без возможности корректного завершения. Используется в высоконагруженных прокси для агрессивного освобождения портов (сопряжено с риском потери данных).

### Сиротские сокеты (Orphan Sockets)

После вызова `close()` сокет больше не привязан к процессу (у него нет дескриптора в User Space). Ядро должно самостоятельно довести процесс закрытия до конца.

- **`net.ipv4.tcp_max_orphans`:** Лимит на количество сиротских сокетов (по умолчанию 16384). Если превышен, ядро удаляет сокет и отправляет `RST` (спасет от исчерпания памяти при атаках). Рекомендация: 8192 для экономии памяти.
- **`net.ipv4.tcp_orphan_retries`:** Количество повторных попыток отправки `FIN` для сиротских сокетов (по умолчанию 0, что эквивалентно 8 таймаутам RTO). Рекомендация: 3 для ускорения закрытия.
- **`net.ipv4.tcp_fin_timeout`:** Определяет, сколько времени (в секундах) сокет будет ожидать `FIN` от партнера в состоянии `FIN_WAIT_2` перед принудительным уничтожением (по умолчанию 60с). Рекомендация: 15 для интерактивных приложений.

**Механизм работы сиротских сокетов:**
1. Приложение вызывает `close()` → сокет теряет дескриптор в User Space
2. Ядро пытается завершить соединение (отправить FIN или дождаться FIN от партнера)
3. Если сокет не может быть закрыт (например, нет FIN от партнера) — сиротский сокет остается в памяти
4. При превышении `tcp_max_orphans` — принудительное удаление с RST

### net.ipv4.tcp_max_tw_buckets

Параметр, ограничивающий максимальное количество сокетов в `TIME_WAIT` (по умолчанию 180000 для 64-битных систем). При превышении новые `TIME_WAIT` уничтожаются и создаются с RST.

**Внимание:** Этот параметр **не рекомендуется** изменять в сторону уменьшения. Вместо этого используйте `tcp_tw_reuse=1` для безопасного переиспользования `TIME_WAIT`.

### tcp_tw_recycle (УСТАРЕЛ)

Параметр `net.ipv4.tcp_tw_recycle` был **удален из ядра Linux 4.12** (2017). Он позволял агрессивно переиспользовать `TIME_WAIT`, но ломал работу за NAT (конфликт Timestamps у разных клиентов за NAT). **Никогда не используйте** этот параметр — он не существует в современных ядрах.

## Практические сценарии

### Сценарий 1: Мониторинг процесса завершения

Для диагностики зависших в памяти соединений используйте утилиту `ss`.

```bash
# Просмотр сокетов в стадиях активного разрыва
ss -tan state fin-wait-1 state fin-wait-2 state close-wait
# → State      Recv-Q Send-Q Local Address:Port  Peer Address:Port
# → FIN-WAIT-2 0      0      192.168.1.10:443    1.2.3.4:54321

# Проверка количества сокетов-сирот, обрабатываемых ядром
ss -s
# → Total: 156 (kernel 160)
# → TCP:   45 (estab 10, closed 5, orphaned 2, timewait 28)
```
*Если значение `orphaned` приближается к лимиту `tcp_max_orphans`, сервер может начать неконтролируемо сбрасывать соединения.*

### Сценарий 2: Аварийный разрыв (RST)

Если приложение аварийно падает (например, OOM Killer завершает процесс), ядро закрывает все открытые им файловые дескрипторы. Если в буфере приема были непрочитанные данные, вместо отправки `FIN` ядро отправит `RST`.
Это позволяет партнеру немедленно узнать, что часть переданных им данных так и не была обработана приложением.

### Сценарий 3: Анализ завершения через tcpdump

**Задача:** Убедиться, что соединение корректно завершается через 4-way handshake.

```bash
# Захват FIN и ACK пакетов для конкретного соединения
sudo tcpdump -i eth0 -nn 'port 443 and (tcp[tcpflags] & (tcp-fin|tcp-ack) != 0)' -tt
# → 12:00:01.000 IP 10.0.0.1.54321 > 10.0.0.2.443: Flags [F.], seq 1000, ack 2000
# → 12:00:01.001 IP 10.0.0.2.443 > 10.0.0.1.54321: Flags [.], seq 2000, ack 1001
# → 12:00:05.000 IP 10.0.0.2.443 > 10.0.0.1.54321: Flags [F.], seq 2000, ack 1001
# → 12:00:05.001 IP 10.0.0.1.54321 > 10.0.0.2.443: Flags [.], seq 1001, ack 2001

# Анализ RST-пакетов (аварийные закрытия)
sudo tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-rst != 0'
# → 12:00:10.000 IP 10.0.0.1.54321 > 10.0.0.2.443: Flags [R], seq 1001
```

**Интерпретация:**
- `Flags [F.]` — FIN-ACK (корректное завершение)
- `Flags [R]` — RST (аварийное закрытие)
- Наличие RST после FIN указывает на проблему (OOM Killer, crash, SO_LINGER)

### Сценарий 4: Анализ через strace при закрытии соединения

**Задача:** Определить, как приложение обрабатывает закрытие соединения.

```bash
# Мониторинг системных вызовов, связанных с закрытием
sudo strace -e trace=close,shutdown -p <PID>
# → shutdown(5, SHUT_WR) = 0         # Приложение инициирует half-close
# → close(5) = 0                     # Полное закрытие дескриптора

# Мониторинг с фильтрацией по дескриптору
sudo strace -e trace=close,shutdown,write -p <PID> 2>&1 | grep -E 'shutdown|close'
```

**Типичные ошибки через strace:**
- `EBADF`: Попытка закрыть уже закрытый дескриптор (двойной close)
- `ENOTCONN`: Попытка shutdown для несуществующего соединения
- `EPIPE`: Попытка записи в закрытый удаленной стороной сокет

### Сценарий 5: Диагностика утечки сокетов (CLOSE_WAIT)

**Проблема:** Количество сокетов в `CLOSE_WAIT` постоянно растет.

```bash
# Подсчет количества CLOSE_WAIT по процессам
ss -tanp state close-wait | awk '{print $NF}' | sort | uniq -c | sort -rn
# → 120 users:(("nginx",pid=1234,fd=5))
# →  25 users:(("java",pid=5678,fd=14))

# Мониторинг через lsof
lsof -i TCP:80 -sTCP:CLOSE-WAIT
# → COMMAND  PID  USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
# → nginx   1234 root   14u  IPv4 123456      0t0  TCP server:80->client:54321 (CLOSE_WAIT)

# Анализ файловых дескрипторов процесса
ls -la /proc/1234/fd | grep socket | wc -l
# → 120 (все дескрипторы — сокеты в CLOSE_WAIT)
```

**Решение:** Анализ кода приложения на предмет корректного освобождения ресурсов (блоки `try-with-resources`, `finally`, `defer`).

### Сценарий 6: Диагностика исчерпания портов (TIME_WAIT)

**Проблема:** Ошибка `Cannot assign requested address` при попытке установить новое соединение.

```bash
# Проверка количества TIME_WAIT
ss -tan state time-wait | wc -l
# → 28000 (при диапазоне портов 32768-60999 = 28232 порта — критически много)

# Проверка лимитов портов
sysctl net.ipv4.ip_local_port_range
# → net.ipv4.ip_local_port_range = 32768 60999

# Включение переиспользования TIME_WAIT
sudo sysctl -w net.ipv4.tcp_tw_reuse=1

# Увеличение диапазона портов
sudo sysctl -w net.ipv4.ip_local_port_range="1024 65535"
```

### Сценарий 7: Диагностика FIN_WAIT_2 (Зависшее закрытие)

**Проблема:** Сокеты в `FIN_WAIT_2` не закрываются в течение длительного времени.

```bash
# Просмотр соединений в FIN_WAIT_2
ss -tan state fin-wait-2
# → FIN-WAIT-2 0 0 10.0.0.1:80 10.0.0.5:54321

# Подсчет количества FIN_WAIT_2
ss -tan state fin-wait-2 | wc -l
# → 25 — проблема, если больше 100

# Просмотр времени в состоянии FIN_WAIT_2
ss -tin state fin-wait-2 | grep -oE 'timer:[^\)]+'
# → timer:(TIME-WAIT,60sec,0)
```

**Решение:**
```bash
# Сокращение времени удержания FIN_WAIT_2 (по умолчанию 60 сек)
sudo sysctl -w net.ipv4.tcp_fin_timeout=15

# Принудительное закрытие соединений в FIN_WAIT_2
ss -tan state fin-wait-2 | awk '{print $4, $5}' | while read local remote; do
    ss -K dst $(echo $remote | cut -d: -f1) dport = $(echo $remote | cut -d: -f2)
done
```

### Сценарий 8: Диагностика LAST_ACK (Ожидание подтверждения закрытия)

**Проблема:** Соединение в `LAST_ACK` не закрывается.

```bash
# Просмотр соединений в LAST_ACK
ss -tan state last-ack
# → LAST-ACK 0 0 10.0.0.1:80 10.0.0.5:54321

# Подсчет количества LAST_ACK
ss -tan state last-ack | wc -l
# → 5 — проблема, если больше 10
```

**Решение:**
```bash
# Увеличение времени повторной отправки FIN
sudo sysctl -w net.ipv4.tcp_orphan_retries=3

# Принудительное закрытие соединений в LAST_ACK
ss -tan state last-ack | awk '{print $4, $5}' | while read local remote; do
    ss -K dst $(echo $remote | cut -d: -f1) dport = $(echo $remote | cut -d: -f2)
done
```

## Диагностические команды (агрегированная секция)

### Мониторинг состояний завершения

```bash
# Подсчет всех соединений по состояниям
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c

# Просмотр только завершающихся соединений
ss -tan state fin-wait-1 state fin-wait-2 state close-wait state last-ack state closing

# Просмотр TIME_WAIT
ss -tan state time-wait | wc -l

# Просмотр с процессами
ss -tanp state close-wait
ss -tanp state fin-wait-2
```

### Глобальная статистика (nstat)

```bash
# Счетчики завершения соединений
nstat -az | grep -E 'TcpExt(TCPTimeouts|TCPAbortOn|TCPTimeWait|TCPFastClose)'
# → TcpExtTCPTimeouts              120                 0.0    # RTO-таймауты
# → TcpExtTCPAbortOnTimeout         8                 0.0    # Аварийное закрытие
# → TcpExtTCPTimeWaitOverflow       0                 0.0    # TIME_WAIT переполнен

# Счетчики CLOSE_WAIT (утечки)
nstat -az | grep -E 'TcpExt(TCPBacklogDrop|ListenOverflows|ListenDrops)'
# → TcpExtListenOverflows          150                 0.0    # Accept Queue переполнен
# → TcpExtListenDrops              150                 0.0    # SYN отброшен
```

### Захват пакетов

```bash
# FIN-пакеты (для анализа завершения)
sudo tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-fin != 0'

# RST-пакеты (для обнаружения аварийных закрытий)
sudo tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-rst != 0'

# Конкретное соединение
sudo tcpdump -i eth0 -nn 'host 10.0.0.1 and port 443'
```

### eBPF и трассировка

## Типичные ошибки при завершении

| Симптом | Состояние | Вероятная причина | Решение |
| :--- | :--- | :--- | :--- |
| **CLOSE_WAIT растет** | `CLOSE_WAIT` | Приложение не вызывает `close()` после получения FIN. | Исправить код приложения (try-with-resources, finally). |
| **TIME_WAIT исчерпан** | `TIME_WAIT` | Слишком много коротких соединений. | `tcp_tw_reuse=1`, connection pooling, расширение `ip_local_port_range`. |
| **FIN_WAIT_2 зависает** | `FIN_WAIT_2` | Партнер не отправляет свой FIN. | `tcp_fin_timeout=15`, принудительное закрытие через `ss -K`. |
| **LAST_ACK не закрывается** | `LAST_ACK` | Потеря ACK или зависание партнера. | `tcp_orphan_retries=3`, проверка доступности партнера. |
| **RST вместо FIN** | `CLOSED` | OOM Killer, crash, `SO_LINGER(0)`. | Проверка логов, увеличение памяти, изменение `SO_LINGER`. |
| **Connection reset by peer** | `CLOSED` | Партнер отправил RST. | Анализ причин RST на стороне партнера. |

## Sysctl-параметры для тюнинга завершения

| Параметр | Значение по умолчанию | Описание | Рекомендация |
| :--- | :--- | :--- | :--- |
| `net.ipv4.tcp_fin_timeout` | 60 | Таймаут FIN_WAIT_2 (сек) | 15 для интерактивных приложений |
| `net.ipv4.tcp_tw_reuse` | 0 | Переиспользование TIME_WAIT | 1 для высоконагруженных серверов |
| `net.ipv4.tcp_max_orphans` | 16384 | Максимум сиротских сокетов | 8192 для экономии памяти |
| `net.ipv4.tcp_orphan_retries` | 0 (8) | Повторные отправки FIN | 3 для ускорения закрытия |
| `net.ipv4.tcp_max_tw_buckets` | 180000 | Максимум TIME_WAIT | Не уменьшать |
| `net.ipv4.ip_local_port_range` | 32768 60999 | Диапазон эфемерных портов | 1024 65535 для расширения |

**Примечание:** `tcp_tw_recycle` удалён из ядра Linux 4.12 и не должен использоваться.

## Docker и Kubernetes

### Docker

```bash
# Проверка параметров в контейнере
docker exec <container> sysctl net.ipv4.tcp_tw_reuse
docker exec <container> sysctl net.ipv4.tcp_fin_timeout

# Установка оптимальных параметров (на хосте)
sudo tee /etc/sysctl.d/99-tcp-termination.conf << 'EOF'
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 15
net.ipv4.tcp_max_orphans = 8192
net.ipv4.tcp_orphan_retries = 3
EOF
sudo sysctl --system
```

### Kubernetes

```yaml
# Настройка через SecurityContext (если разрешено)
apiVersion: v1
kind: Pod
metadata:
  name: tcp-termination-tuning
spec:
  containers:
  - name: app
    image: nginx
    securityContext:
      capabilities:
        add: ["NET_ADMIN"]
    command: ["sysctl", "-w", "net.ipv4.tcp_tw_reuse=1"]
```
