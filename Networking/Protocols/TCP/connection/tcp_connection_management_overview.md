# Управление TCP-соединением — Обзор и установка соединения

## Определения

**Управление соединением (Connection Management)** — механизмы TCP для установки, поддержания и завершения надежного соединения между двумя узлами.

**Ключевые процессы:**

- **Handshake (трёхэтапное рукопожатие)** — установка соединения
- **Data Transfer** — двусторонняя передача данных
- **Termination (четырёхэтапное завершение)** — корректный разрыв соединения

**Состояния соединения:** 11 состояний конечного автомата TCP.

---

## Основные концепции

### Установка соединения: TCP Handshake

**Цель handshake:**

1. Убедиться, что обе стороны существуют и готовы к обмену данными
2. Согласовать начальные параметры (Sequence Numbers, MSS, Window Scale)
3. Выделить ресурсы (буферы, управляющие структуры)

**Аналогия с телефонным звонком:**

Установка TCP-соединения похожа на звонок по телефону:

- **SYN** — вы набираете номер и слышите гудок
- **SYN-ACK** — абонент поднимает трубку и говорит «Алло»
- **ACK** — вы начинаете разговор

Если абонент не поднимает трубку (нет приложения на порту) — соединение не устанавливается, и нет смысла говорить «в пустоту».

**Процесс:** 3 сегмента (three-way handshake)

```
   Клиент                                     Сервер
     |                                            |
     |  SYN (seq=x) ----------------------------> |  LISTEN
     |      (Состояние: SYN_SENT)                 |      ↓
     |                                            |  SYN-RCVD
     |  <---------------------------- SYN-ACK ----|
     |           (seq=y, ack=x+1)                 |
     |                                            |
     |  ACK (seq=x+1, ack=y+1) -----------------> |
     |      (Состояние: ESTABLISHED)              |  (Состояние: ESTABLISHED)
     |                                            |
     |◄══════════ Передача данных ══════════════►|
```

#### Детальный алгоритм

**Шаг 1: SYN от клиента**

| Параметр | Значение |
| :--- | :--- |
| **Флаги** | `SYN=1` |
| **Sequence Number** | `seq=x` (случайный ISN) |
| **Опции** | MSS, Window Scale, SACK permitted, Timestamps |
| **Состояние клиента** | `SYN_SENT` |

**Назначение:** инициация соединения, отправка клиентских параметров.

---

**Шаг 2: SYN-ACK от сервера**

| Параметр | Значение |
| :--- | :--- |
| **Флаги** | `SYN=1, ACK=1` |
| **Sequence Number** | `seq=y` (случайный ISN сервера) |
| **Acknowledgment Number** | `ack=x+1` (подтверждение SYN клиента) |
| **Опции** | MSS, Window Scale, SACK permitted, Timestamps |
| **Состояние сервера** | `SYN_RECEIVED` |

**Варианты реакции сервера:**

| Ситуация | Реакция |
| :--- | :--- |
| **Порт открыт, ресурсы есть** | Отправить `SYN-ACK`, перейти в `SYN_RECEIVED` |
| **Порт закрыт** | Отправить `RST` |
| **Нет ресурсов** | Отправить `RST` или игнорировать |
| **SYN-cookie включен** | Отправить `SYN-ACK` без выделения памяти |

---

**Шаг 3: ACK от клиента**

| Параметр | Значение |
| :--- | :--- |
| **Флаги** | `ACK=1` |
| **Sequence Number** | `seq=x+1` |
| **Acknowledgment Number** | `ack=y+1` (подтверждение SYN сервера) |
| **Состояние клиента** | `ESTABLISHED` |

**Реакция сервера:**

- Получение `ACK` → переход в `ESTABLISHED`
- Тайм-аут без `ACK` → переход в `CLOSED`, сокет удаляется

---

#### Почему 3 этапа, а не 2?

**Проблема 2-этапного handshake:**

```
1. Клиент → SYN → Сервер
2. Сервер → SYN-ACK → Клиент
```

**Недостаток:** сервер не знает, получил ли клиент его `SYN-ACK`. Если `SYN-ACK` потерян, клиент будет ждать вечно, а сервер выделит ресурсы.

**Решение (3 этапа):**

- Третий `ACK` подтверждает, что клиент получил `SYN-ACK`
- Обе стороны уверены в готовности к передаче данных

### Сценарии отказа в установке соединения

#### 1. Закрытый порт: ответ RST

Если на хосте нет приложения, слушающего указанный порт, TCP отправляет пакет с флагом **RST (Reset)** в ответ на SYN:

```
   Клиент                                     Сервер
     |                                            |
     |  SYN (seq=x) ----------------------------> |  Порт закрыт
     |      (Состояние: SYN_SENT)                 |
     |  <---------------------------- RST --------|  Немедленный сброс
     |                                            |
     |  Получен RST → соединение не установлено   |
```

**Назначение RST:**

- Немедленно уведомить клиента о недоступности сервиса
- Позволяет приложению быстро обработать ошибку (вместо ожидания тайм-аута)
- Экономит ресурсы сети и хоста

**Диагностика:**

```bash
# Проверка закрытых портов
nmap -p 80,443,5555 target.host

# Ответ RST в tcpdump
tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-rst != 0'
```

**Причины RST:**

- Порт не слушается (нет приложения)
- Приложение завершилось аварийно
- Соединение отклонено политикой безопасности

---

#### 2. Хост не отвечает: тайм-ауты SYN

Если удаленная сторона не отвечает на SYN-пакет (сервер выключен, фаервол блокирует пакеты), TCP использует механизм повторных попыток:

```
   Клиент                                     Сервер
     |                                            |
     |  SYN #1 --------------------------------> |  (нет ответа)
     |      (等待 1 секунду)                       |
     |  SYN #2 --------------------------------> |  (нет ответа)
     |      (等待 2 секунды)                       |
     |  SYN #3 --------------------------------> |  (нет ответа)
     |      (等待 4 секунды)                       |
     |  SYN #4 --------------------------------> |  (нет ответа)
     |                                            |
     |  Тайм-аут → ошибка соединения              |
```

**Алгоритм экспоненциального backoff:**

| Попытка | Задержка перед следующей | Кумулятивное время |
| :--- | :--- | :--- |
| 1 | 1 сек | 0 сек |
| 2 | 2 сек | 1 сек |
| 3 | 4 сек | 3 сек |
| 4 | — | 7 сек |

**Параметры:**

- **Количество попыток:** 4 в современных системах (настраивается)
- **Задержка:** экспоненциально возрастает (1, 2, 4 сек)
- **Общее время ожидания:** ~7 секунд до отказа

**Настройка в Linux:**

```bash
# Количество SYN-ретрансмиссий (по умолчанию 5)
sysctl -w net.ipv4.tcp_syn_retries=4

# Просмотр текущего значения
sysctl net.ipv4.tcp_syn_retries
```

**Почему приложение «зависает»:**

Если в ответ нет ни `SYN-ACK`, ни `RST`, TCP считает пакет потерянным и ожидает подтверждения. Приложение блокируется на время всех попыток (~7 сек), что воспринимается как «зависание».

**Причины отсутствия ответа:**

- Сервер выключен или недоступен
- Фаервол блокирует пакеты (DROP, не REJECT)
- Маршрут до хоста отсутствует

**Разница между RST и DROP:**

| Реакция | Поведение | Время ошибки |
| :--- | :--- | :--- |
| **RST (REJECT)** | Мгновенный ответ | ~0 мс |
| **DROP (игнор)** | Нет ответа | ~7 сек (тайм-аут) |

### Передача данных

#### Поток байт (Byte Stream)

TCP — протокол **потоковой передачи данных**, а не датаграмм:

- TCP передает непрерывный **поток байт**, а не готовые сообщения
- Отправитель записывает байты в сокет, получатель читает поток
- TCP самостоятельно решает, сколько данных поместить в один сегмент
- Получатель собирает байты в правильном порядке благодаря [Sequence Numbers](../reliability_mechanisms/sequence_numbers.md)

**Пример:**

```
Приложение отправляет: "HELLO" (5 байт) + "WORLD" (5 байт)
TCP может отправить:
  Вариант 1: один сегмент 10 байт
  Вариант 2: два сегмента по 5 байт
  Вариант 3: пять сегментов по 2 байта
```

**Результат:** получатель получит те же 10 байт в том же порядке, независимо от количества сегментов.

---

#### Флаг PSH (Push)

**Назначение:** указывает на необходимость немедленной доставки данных приложению.

| Параметр | Значение |
| :--- | :--- |
| **Флаг** | `PSH=1` |
| **В заголовке** | 1 бит в поле флагов |
| **Использование** | Редко, обычно для интерактивных данных |

**Когда устанавливается:**

- Интерактивные данные (терминал, SSH)
- Конец логического сообщения (HTTP-запрос)
- Требование немедленной доставки

**Поведение получателя:**

- Без `PSH`: данные могут буферизоваться до заполнения буфера
- С `PSH`: немедленная передача приложению без ожидания заполнения буфера

**Диагностика:**

```bash
# PSH-пакеты в tcpdump
tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-push != 0'
```

---

#### Sequence Number и Acknowledgment Number

**Sequence Number (номер последовательности, 32 бита):**

- Номер **первого байта данных** в сегменте
- Позволяет получателю восстановить порядок байт
- Защищает от дубликатов и перепутанных пакетов

**Acknowledgment Number (номер подтверждения, 32 бита):**

- Номер **следующего ожидаемого байта**
- Действует только при флаге `ACK=1`
- Кумулятивное подтверждение: подтверждает все байты до указанного

**Пример передачи 2800 байт:**

```
Отправитель                         Получатель
     |                                    |
     |  Пакет 1: seq=0, 1000 байт ------> |  Байты 0–999
     |  <---------------- ACK=1000 -------|  Ожидается байт 1000
     |                                    |
     |  Пакет 2: seq=1000, 800 байт ----> |  Байты 1000–1799
     |  <---------------- ACK=1800 -------|  Ожидается байт 1800
     |                                    |
     |  Пакет 3: seq=1800, 1000 байт ---> |  Байты 1800–2799
     |  <---------------- ACK=2800 -------|  Все данные получены
```

**Подробнее:** [Sequence Numbers](../reliability_mechanisms/sequence_numbers.md), [Acknowledgments](../reliability_mechanisms/acknowledgments.md)
