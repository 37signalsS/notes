# Протокол TCP (Transmission Control Protocol)

TCP (Transmission Control Protocol) — это один из основных протоколов транспортного уровня (L4) в стеке протоколов TCP/IP. 

## Определения

### Сервисная модель: надежный поток байт

В отличие от UDP, который работает с независимыми сообщениями (дейтаграммами), TCP предоставляет приложению сервис **надежной передачи потока байт (reliable byte stream)**.

Это означает, что:
1.  Приложение-отправитель передает TCP непрерывный поток данных (например, содержимое файла).
2.  TCP на стороне отправителя разделяет этот поток на части, называемые **сегментами**, и отправляет их по сети.
3.  TCP на стороне получателя собирает эти сегменты, восстанавливает из них исходный поток байт и передает его приложению-получателю.

При этом приложение-получатель получит в точности тот же самый поток байт, который был отправлен, без искажений, потерь и в правильном порядке.

### Ключевые характеристики

*   **Надежность:** Гарантирует доставку данных.
*   **Упорядоченность:** Гарантирует, что данные будут получены в том же порядке, в котором были отправлены.
*   **Ориентация на соединение:** Требует установки соединения перед началом обмена данными.
*   **Управление потоком (Flow Control):** Механизм, предотвращающий "переполнение" буфера получателя, если отправитель шлет данные слишком быстро.
*   **Управление перегрузкой (Congestion Control):** Механизм, позволяющий снижать интенсивность передачи при возникновении перегрузок в сети.

## Базовые концепции

### Формат заголовка TCP

Заголовок протокола TCP является одним из самых сложных в стеке TCP/IP. Его структура необходима для реализации всех функций надёжной передачи данных, которые заложены в протокол.

Заголовок состоит из обязательной части (20 байт) и опциональных параметров.

1.  **Порт источника (Source Port, 16 бит):**
    *   Адрес приложения-отправителя на транспортном уровне.

2.  **Порт назначения (Destination Port, 16 бит):**
    *   Адрес приложения-получателя на транспортном уровне.

3.  **Порядковый номер (Sequence Number, 32 бита):**
    *   TCP представляет поток данных как последовательность байт. Это поле содержит порядковый номер **первого байта данных** в текущем сегменте.
    *   Используется для правильной сборки сегментов и защиты от дубликатов.
    *   При установке соединения стороны договариваются о случайных начальных номерах последовательности (ISN).

4.  **Номер подтверждения (Acknowledgment Number, 32 бита):**
    *   Используется, если установлен флаг `ACK`.
    *   Содержит номер **следующего байта**, который получатель ожидает от отправителя. Это является кумулятивным подтверждением — оно означает, что все байты до этого номера (не включая его) были успешно получены.

5.  **Длина заголовка (Data Offset, 4 бита):**
    *   Указывает размер заголовка TCP в 32-битных словах (по 4 байта).
    *   Это поле необходимо, так как заголовок имеет переменную длину из-за наличия опциональных параметров.
    *   Минимальное значение — 5 (5 * 4 = 20 байт, обязательная часть), максимальное — 15 (15 * 4 = 60 байт).

6.  **Зарезервировано (Reserved, 3 бита):**
    *   Зарезервировано для будущего использования, должно быть установлено в ноль.

7.  **Флаги (Flags, 9 бит):**
    *   Набор из девяти однобитовых флагов, которые управляют состоянием соединения и обработкой сегмента.

| Флаг | Название | Описание |
| :--- | :--- | :--- |
| **NS** | Nonce Sum | Экспериментальный флаг для защиты от случайных, злонамеренных сокрытий пакетов. |
| **CWR**| Congestion Window Reduced | Уведомляет, что отправитель уменьшил свое окно перегрузки. |
| **ECE**| ECN-Echo | Указывает, что узел получил сегмент с установленным флагом `CE` (сигнал о перегрузке). |
| **URG**| Urgent | Указывает, что поле "Указатель срочности" является валидным. На практике почти не используется. |
| **ACK**| Acknowledgment | Указывает, что поле "Номер подтверждения" является валидным. Установлен для всех сегментов, кроме самого первого. |
| **PSH**| Push | Просит получателя "протолкнуть" данные приложению немедленно, не дожидаясь заполнения буфера. На практике не используется. |
| **RST**| Reset | Немедленно разрывает соединение в обе стороны. Используется при ошибках или отказе от соединения. |
| **SYN**| Synchronize | Используется для инициации соединения и синхронизации порядковых номеров. |
| **FIN**| Finish | Используется для корректного завершения соединения (закрытия одной стороны). |

8.  **Размер окна (Window Size, 16 бит):**
    *   Используется для управления потоком.
    *   Получатель указывает в этом поле, сколько байт данных он готов принять (размер свободного места в своем буфере).

9.  **Контрольная сумма (Checksum, 16 бит):**
    *   Используется для обнаружения ошибок в заголовке и данных сегмента.

10. **Указатель срочности (Urgent Pointer, 16 бит):**
    *   Используется совместно с флагом `URG` для указания на "срочные" данные внутри сегмента. На практике эта функциональность почти не используется.

#### Параметры (Options)

Это необязательная часть заголовка, которая позволяет расширять функциональность TCP.

*   **Максимальный размер сегмента (Maximum Segment Size, MSS):**
    *   Стороны договариваются о максимальном размере данных, который может содержаться в одном TCP-сегменте.
*   **Масштаб окна (Window Scale):**
    *   Позволяет увеличить максимальный размер окна TCP с 64 КБ до 1 ГБ. Необходимо для эффективной работы на высокоскоростных каналах с большой задержкой.
*   **Выборочное подтверждение (Selective Acknowledgment, SACK):**
    *   Позволяет получателю подтверждать получение отдельных блоков данных, а не только непрерывной последовательности. Очень полезно при большом размере окна, когда теряются единичные сегменты.
*   **Метки времени (Timestamps):**
    *   Позволяют более точно измерять время кругового обхода (Round-Trip Time, RTT). Это критически важно для корректной настройки таймеров повторной передачи.

### Управление соединением

#### Установка соединения: TCP Handshake (Тройное рукопожатие)

Перед началом обмена данными TCP должен установить соединение. Этот процесс гарантирует, что обе стороны существуют, готовы к обмену данными, и позволяет им согласовать начальные параметры, такие как номера последовательности. Процесс называется «трёхэтапным рукопожатием» (англ. three-way handshake), так как для экономии времени и ресурсов два шага (подтверждение от сервера и его собственный запрос на синхронизацию) объединяются в один, используя три сегмента вместо четырёх.

**Схематично это выглядит так:**
```text
   Клиент                                     Сервер
     |                                            |
     |  SYN (seq=x) ----------------------------> |
     |      (Состояние: SYN_SENT)                 |
     |                                            |
     |  <---------------------------- SYN-ACK (seq=y, ack=x+1)
     |                                            | (Состояние: SYN_RECEIVED)
     |  ACK (seq=x+1, ack=y+1) -----------------> |
     |      (Состояние: ESTABLISHED)              | (Состояние: ESTABLISHED)
     |                                            |
```

**Подробный алгоритм:**

1.  **Шаг 1: `SYN` от клиента**
    *   **Действие:** Клиент, намеревающийся установить соединение, посылает серверу сегмент с флагом `SYN` (Synchronize) и своим начальным, случайно сгенерированным номером последовательности (`Sequence Number`, `seq=x`).
    *   **Назначение:** Этот пакет синхронизации позволяет сторонам согласовать начальные номера для отслеживания потока данных.
    *   **Состояние клиента:** Переходит в `SYN_SENT`.

2.  **Шаг 2: `SYN-ACK` от сервера**
    *   **Действие сервера:**
        *   Сервер получает сегмент `SYN`, запоминает номер последовательности `x` и пытается создать сокет (буферы и управляющие структуры в памяти) для обслуживания нового клиента.
        *   **В случае успеха:** Сервер посылает клиенту в ответ сегмент с двумя флагами:
            *   `SYN`: Сервер передаёт свой собственный начальный порядковый номер (`seq=y`).
            *   `ACK`: Сервер подтверждает получение пакета от клиента, устанавливая номер подтверждения в `ack=x+1`.
        *   **В случае неудачи** (например, порт закрыт или нет ресурсов): Сервер посылает клиенту сегмент с флагом `RST` (Reset), отказывая в соединении.
    *   **Состояние сервера (при успехе):** Переходит в `SYN_RECEIVED`.

3.  **Шаг 3: `ACK` от клиента**
    *   **Действие клиента:**
        *   Получив `SYN-ACK`, клиент запоминает номер последовательности сервера `y` и посылает ответный сегмент с флагом `ACK`. Номер подтверждения устанавливается в `ack=y+1`.
        *   Если клиент вместо `SYN-ACK` получает `RST`, он прекращает попытки соединиться.
        *   Если клиент не получает ответа в течение установленного тайм-аута, он повторяет попытку соединения.
    *   **Состояние клиента (при успехе):** Переходит в `ESTABLISHED`.

**Завершение установки соединения:**

*   Когда сервер в состоянии `SYN_RECEIVED` получает от клиента финальный сегмент `ACK`, он также переходит в состояние `ESTABLISHED`.
*   С этого момента соединение считается установленным, и обе стороны могут начать двустороннюю передачу данных.

Если сервер не получает финальный `ACK` от клиента, по истечении тайм-аута он закрывает созданный сокет и переходит в состояние `CLOSED`.

#### Завершение соединения

После окончания передачи данных соединение должно быть корректно разорвано. Каждая сторона закрывает соединение независимо, что обычно приводит к "четырехэтапному рукопожатию" с использованием флагов `FIN` (Finish) и `ACK`.

### Механизмы обеспечения надежности

TCP изначально спроектирован для работы поверх **ненадежных** сетей, в которых пакеты могут теряться, дублироваться или приходить в неправильном порядке. Для борьбы с этими проблемами TCP использует несколько ключевых механизмов.

#### Нумерация последовательности (Sequence Numbers)

*   **Нумерация байтов:** В TCP номер присваивается не каждому сегменту, а **каждому байту** в потоке данных.
*   **Как работает:**
    *   При установке соединения стороны обмениваются случайными начальными номерами последовательности (Initial Sequence Number, ISN).
    *   Каждый отправляемый сегмент содержит в заголовке поле `Sequence Number`, равное номеру первого байта данных в этом сегменте.

Это позволяет получателю:
*   **Восстановить порядок:** Если сегменты приходят не по порядку, получатель может расставить их правильно, ориентируясь на `Sequence Number`.
*   **Обнаружить дубликаты:** Если приходит сегмент с уже полученными номерами байтов, он отбрасывается.

#### Подтверждения (Acknowledgements)

*   **Принцип:** Получив сегмент с данными, получатель отправляет в ответ сегмент с установленным флагом **ACK** (Acknowledgment).
*   **Кумулятивное подтверждение:** В поле `Acknowledgment Number` получатель указывает **номер следующего байта, который он ожидает получить**. Например, если были получены байты с 0 по 1023, `Acknowledgment Number` будет установлен в `1024`. Это означает "я успешно получил все байты до 1023 включительно и жду следующий".

#### Повторная передача (Retransmission)

Если данные или подтверждение теряются в сети, TCP выполняет повторную передачу.
*   **Таймер:** Отправив сегмент, отправитель запускает таймер ожидания (Retransmission Timeout, RTO).
*   **Потеря данных:** Если подтверждение не приходит до истечения таймера, отправитель считает сегмент утерянным и **отправляет его заново**.
*   **Потеря подтверждения:** Если теряется ACK-пакет, отправитель также не получает подтверждения и выполняет повторную передачу. Получатель, благодаря нумерации последовательности, поймет, что это дубликат, и просто отправит еще одно подтверждение.

#### Скользящее окно (Sliding Window)

Для повышения производительности TCP не ждет подтверждения после отправки каждого сегмента. Вместо этого он отправляет сразу несколько сегментов в пределах так называемого "окна" (`window`).

**Размер окна** — это количество байтов данных, которые могут быть переданы в сеть без получения подтверждения. Окно "скользит" по потоку данных по мере того, как приходят подтверждения о получении предыдущих сообщений.

*   **Пример:** Если получатель подтвердил доставку ещё четырёх сегментов, скользящее окно сдвигается. Его начало теперь находится там, где данные уже подтверждены. Часть данных уже находится в сети, и новые сегменты, которые ещё не были переданы, но уже находятся в окне, могут быть отправлены.

**Типы подтверждений в TCP**

1.  **Кумулятивное подтверждение (Cumulative Acknowledgment):**
    *   Это тип подтверждения используется по умолчанию. Оно говорит о том, что получены **все предыдущие байты** до указанного номера.
2.  **Выборочное подтверждение (Selective Acknowledgment, SACK):**
    *   Используется для окон большого размера, когда может быть потерян один сегмент посреди большой порции данных. Позволяет отправителю явно указать диапазоны тех частей данных, которые получены. Отправителю останется передать только ту часть данных, которая была реально потеряна.
    *   SACK не используется по умолчанию. Стороны должны договориться о его использовании в процессе установки соединения.

### Состояния TCP-соединений

*   **LISTEN**: Сервер ожидает входящих подключений на определенном порту.
*   **SYN_SENT**: Клиент отправил пакет SYN и ожидает SYN-ACK от сервера.
*   **SYN_RECEIVED**: Сервер получил SYN от клиента, отправил SYN-ACK и ожидает ACK от клиента (часть [TCP-рукопожатия](#установка-соединения-tcp-handshake-тройное-рукопожатие)).
*   **ESTABLISHED**: Соединение установлено и готово к передаче данных.
*   **FIN_WAIT1**: Одна сторона инициировала закрытие соединения и отправила FIN-пакет.
*   **FIN_WAIT2**: Первая сторона получила ACK на свой FIN-пакет.
*   **CLOSE_WAIT**: Удаленная сторона инициировала закрытие, а локальная сторона получила FIN-пакет.
*   **CLOSING**: Обе стороны одновременно отправили FIN-пакеты.
*   **LAST_ACK**: Локальная сторона отправила FIN и ожидает ACK от удаленной стороны.
*   **TIME_WAIT**: Локальная сторона закрыла соединение и ожидает истечения таймера, чтобы убедиться, что все пакеты были получены и обработаны. Это состояние необходимо для предотвращения проблем с задержавшимися сегментами старых соединений.

## Практические сценарии

### Управление потоком (Flow Control)

**Управление потоком** — это механизм, который не позволяет быстрому отправителю переполнить буфер медленного получателя.

Для этого в заголовке TCP используется поле **Размер окна (Window Size)**.
*   В этом поле получатель сообщает отправителю, сколько свободного места в байтах осталось в его буфере.
*   Отправитель не может передавать больше данных, чем указано в этом поле.

Если буфер получателя заполнится, он отправит подтверждение с **размером окна, равным нулю**. Это сигнал для отправителя полностью прекратить передачу данных.

#### Зондаж нулевого окна (Zero-Window Probe)

Если подтверждение с обновленным ненулевым размером окна потеряется, отправитель будет вечно ждать. Чтобы этого избежать, по истечении таймера ожидания, отправитель отправляет небольшой сегмент с одним байтом данных (**Zero-Window Probe**), чтобы "вынудить" получателя отправить в ответ подтверждение с актуальным размером окна.

### Управление перегрузкой (Congestion Control)

Помимо управления потоком, которое решает проблему на стороне получателя, TCP использует механизм **управления перегрузкой**, чтобы не "затопить" саму сеть.

Для этого вводится **окно перегрузки (`cwnd`)**. Итоговый размер отправляемых данных всегда равен **минимальному** из `cwnd` и окна управления потоком (`rwnd`).

#### Алгоритмы управления `cwnd`

1.  **Медленный старт (Slow Start):** В начале соединения `cwnd` растёт экспоненциально, чтобы быстро занять доступную полосу пропускания.
2.  **Избегание перегрузки (Congestion Avoidance / AIMD):** После достижения порога (`ssthresh`) рост `cwnd` становится линейным (Additive Increase). При обнаружении перегрузки (потере пакета) `cwnd` резко сокращается (Multiplicative Decrease).
3.  **Быстрое восстановление (Fast Recovery):** Механизм, позволяющий быстрее восстановиться после единичных потерь пакетов без полного сброса окна.
