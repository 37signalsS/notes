# Протокол TCP: Управление потоком (Flow Control)

**Управление потоком (Flow Control)** — это одна из ключевых функций протокола TCP, предназначенная для предотвращения "затопления" медленного получателя данными от быстрого отправителя.

В сети могут работать устройства с совершенно разной производительностью. Например, мощный сервер может отправлять данные гораздо быстрее, чем их способен обработать смартфон. Если отправитель передаст слишком большую порцию данных, буфер приема на стороне получателя быстро переполнится. Все последующие сегменты будут отброшены, и отправителю придется передавать их заново. Управление потоком решает эту проблему.

## Механизм управления потоком

Процесс происходит следующим образом:
1.  Данные, поступающие по протоколу TCP, сначала попадают в специальный буфер в операционной системе получателя.
2.  Приложение, для которого предназначены эти данные, читает их из буфера.
3.  Проблема в том, что приложение не обязано читать данные мгновенно. Оно может быть занято другими задачами (например, вычислениями), и данные будут накапливаться в буфере.

Если буфер заполнится, все новые поступающие TCP-сегменты будут отбрасываться.

### Поле "Размер окна" (Window Size)

Для решения этой проблемы в [заголовке TCP](./tcp_header_format.md) используется поле **Размер окна (Window Size)**.
*   В этом поле получатель сообщает отправителю, сколько свободного места в байтах осталось в его буфере.
*   Отправителю нет смысла передавать больше данных, чем указано в этом поле, так как они, скорее всего, будут отброшены.

### Пример работы

1.  Получатель имеет буфер на уровне ОС. Приложение читает данные из этого буфера.
2.  Приходит TCP-сегмент. Данные записываются в буфер.
3.  Получатель отправляет подтверждение (ACK), в котором указывает:
    *   Номер следующего ожидаемого байта.
    *   Текущий **размер окна** (свободное место в буфере).
4.  Отправитель получает эту информацию и отправляет новую порцию данных, не превышающую объявленный размер окна.
5.  Данные снова записываются в буфер получателя. Получатель отправляет новое подтверждение, но на этот раз с **меньшим размером окна**, так как буфер заполнился еще больше.
6.  Отправитель снова отправляет данные, соответствующие новому, меньшему размеру окна.

### Ситуация с нулевым окном (Zero Window)

Предположим, приложение на стороне получателя занято и не читает данные из буфера. Буфер полностью заполняется.

1.  Получатель отправляет подтверждение, в котором указывает **размер окна, равный нулю**.
2.  Это сигнал для отправителя полностью прекратить передачу данных.
3.  Получив сообщение с нулевым окном, отправитель запускает специальный **таймер ожидания (persist timer)**.
4.  Через некоторое время приложение на стороне получателя считывает часть данных, и в буфере освобождается место.
5.  Получатель отправляет новое подтверждение (даже если новых данных не было) с тем же порядковым номером, но уже с **ненулевым размером окна**.
6.  Получив это обновление, отправитель возобновляет передачу данных.

#### Проблема потерянного подтверждения и Zero-Window Probe

Что если подтверждение с обновленным размером окна потеряется в сети? В этом случае отправитель будет вечно ждать, думая, что окно равно нулю.

Для решения этой проблемы, по истечении таймера ожидания, отправитель инициирует **"зондаж" нулевого окна (Zero-Window Probe)**. Он отправляет небольшой сегмент с одним байтом данных. Цель этого сегмента — "вынудить" получателя отправить в ответ подтверждение с актуальным размером окна.

*   Если окно все еще равно нулю, получатель подтвердит полученный байт, но снова объявит нулевое окно. Отправитель сбросит таймер и будет ждать дальше.
*   Если место в буфере появилось, получатель в ответном подтверждении укажет новый, ненулевой размер окна, и передача данных возобновится.

## Выводы

*   **Управление потоком** — это механизм, который не позволяет быстрому отправителю переполнить буфер медленного получателя.
*   Для этого получатель использует поле **"Размер окна" (Window Size)** в заголовке TCP, сообщая, сколько байт данных он готов принять.
*   Если получатель сообщает о нулевом окне, отправитель приостанавливает передачу и периодически проверяет состояние получателя с помощью **Zero-Window Probe**.
