# Протокол HTTP (Hypertext Transfer Protocol)

## Определения

HTTP (Hypertext Transfer Protocol) — протокол передачи гипертекста, который является основой Всемирной паутины (World Wide Web). Он определяет правила, по которым веб-клиенты (например, браузеры) и веб-серверы взаимодействуют для обмена информацией.

## Базовые концепции

### Модель "Запрос-Ответ"

Протокол HTTP работает по модели "запрос-ответ":

* **Клиент** (веб-браузер) отправляет запрос на сервер.
* **Сервер** обрабатывает запрос и отправляет ответ.

Сервер не может инициировать взаимодействие. HTTP использует протокол [TCP](./TCP/overview.md) на транспортном уровне, что гарантирует надежную доставку. Веб-серверы обычно используют порт **80** для HTTP и **443** для HTTPS.

### Stateless-протокол (Протокол без сохранения состояния)

**HTTP является stateless-протоколом.** Это означает, что сервер не хранит никакой информации о предыдущих запросах от клиента. Каждый запрос рассматривается как независимая транзакция и должен содержать всю информацию, необходимую для его выполнения.

* **Преимущества:**
  * **Масштабируемость:** Любой сервер в кластере может обработать запрос клиента, так как нет привязки к состоянию сессии на конкретном сервере. Это упрощает горизонтальное масштабирование.
  * **Надежность:** Отказ одного сервера не влияет на сессию пользователя, так как следующий запрос может быть успешно обработан другим сервером.
  * **Простота:** Отсутствие управления состоянием упрощает дизайн сервера.

* **Недостатки:**
  * **Избыточность:** Клиенту может потребоваться отправлять повторяющуюся информацию (например, данные аутентификации) с каждым запросом.

Для обхода этого ограничения и создания "сессий" используются такие механизмы, как [Cookies](#cookies) или токены в заголовках (`Authorization`).

### Структура HTTP-сообщения

**Минимальный HTTP-запрос (HTTP/1.1)**

1. **Стартовая строка (Request Line):** `GET / HTTP/1.1` (Метод, URI, Версия).
2. **Заголовок `Host`:** `Host: example.com` (Обязателен в HTTP/1.1).
3. **Пустая строка (CRLF):** Сигнал окончания заголовков.

**Минимальный HTTP-ответ (HTTP/1.1)**

1. **Строка состояния (Status Line):** `HTTP/1.1 200 OK` (Версия, Код, Пояснение).
2. **Заголовки:** `Content-Length: 1234` (Обязателен для ответа с телом).
3. **Пустая строка (CRLF):** Разделяет заголовки и тело.
4. **Тело ответа (Response Body):** Сами данные.

### Методы HTTP

| Метод | Описание |
|---|---|
| **GET** | Запрашивает представление указанного ресурса. Запросы с использованием GET должны только извлекать данные. Может быть закэширован, остается в истории браузера, может быть закладкой. Не должен использоваться при работе с крайне важными данными. Имеет ограниченную длину. |
| **POST** | Используется для отправки сущности на указанный ресурс, часто вызывая изменение состояния или побочные эффекты на сервере. Не кэшируется, не может быть закладкой в браузере, не остаётся в истории браузера. Нет ограничений по длине запроса. |
| **PUT** | Заменяет все текущие представления целевого ресурса данными запроса. |
| **DELETE** | Удаляет указанный ресурс. |
| **PATCH** | Используется для применения частичных модификаций к ресурсу. |
| **HEAD** | Запрашивает ответ, идентичный ответу на GET-запрос, но без тела ответа. |
| **OPTIONS** | Используется для описания параметров связи для целевого ресурса. |
| **CONNECT** | Устанавливает туннель к серверу, идентифицированному по целевому ресурсу. |
| **TRACE** | Выполняет тест обратной связи сообщения по пути к целевому ресурсу. |

### Эволюция протокола: от HTTP/1.0 до HTTP/3

| Характеристика | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| :--- | :--- | :--- | :--- | :--- |
| **Транспортный протокол** | TCP | TCP | TCP | **QUIC (UDP)** |
| **Соединения** | Новое на каждый запрос | Постоянные (Keep-Alive) | Одно на домен | Одно на домен |
| **Параллелизм** | Нет | Конвейеризация (Pipelining) | **Мультиплексирование** | **Мультиплексирование** |
| **Блокировка "Head-of-Line"** | Да | Да | На уровне TCP | **Нет** |
| **Сжатие заголовков** | Нет | Нет | **HPACK** | **QPACK** |
| **Инициатива сервера** | Нет | Нет | **Server Push** | Нет (убрано) |
| **Шифрование** | Нет | Опционально | **Обязательно ([TLS](./tls.md))** | **Обязательно ([TLS](./tls.md))** |
| **Влияние RTT на установление соединения** | Высокое (много RTT на каждый ресурс) | Высокое (несколько RTT на соединение) | Умеренное (1-2 RTT на соединение) | Низкое (1-RTT или 0-RTT) |

#### HTTP/1.0 (1996)

* Проблема: Медлительность. На каждый запрос (например, за HTML-файл, картинку, CSS) открывалось новое TCP-соединение, что создавало большие накладные расходы.

#### HTTP/1.1 (1997)

Ключевые улучшения, направленные на решение проблем производительности:

* **Постоянные соединения (Keep-Alive):** Позволили браузеру отправлять несколько запросов в рамках одного TCP-соединения, что значительно сократило задержки.
* **Конвейеризация (Pipelining):** Дала возможность отправлять следующий запрос, не дожидаясь ответа на предыдущий. Однако на практике эта функция работала плохо из-за блокировки "Head-of-Line" (HOL Blocking).
* **Chunked Transfer Encoding:** Сервер может передавать данные постепенно, частями (чанками), не зная заранее полного размера ответа.

#### HTTP/2 (2015)

Революционное обновление, основанное на протоколе SPDY от Google:

* **Мультиплексирование:** Главное нововведение. Позволяет передавать множество запросов и ответов одновременно в рамках одного TCP-соединения, разбивая их на бинарные "кадры" (frames). Это решает проблему HOL-блокировки на уровне приложения.
* **Бинарный протокол:** Более эффективный и менее подверженный ошибкам.
* **Сжатие заголовков (HPACK):** Значительно уменьшило размер передаваемых заголовков.
* **Server Push:** Позволял серверу отправлять ресурсы клиенту еще до того, как он их запросит. На практике функция оказалась сложной, и в HTTP/3 от нее отказались.
* **Обязательное шифрование:** В большинстве браузеров HTTP/2 работает только поверх TLS (HTTPS).

#### HTTP/3 (2022)

Новейший стандарт, который решает последнюю оставшуюся проблему — блокировку Head-of-Line на уровне транспортного протокола (TCP).

* **Переход на QUIC (UDP):** HTTP/3 работает поверх протокола QUIC, который реализует мультиплексирование, надежность и шифрование поверх UDP. Потеря одного пакета в одном потоке данных не влияет на остальные.
* **Более быстрое установление соединения:** QUIC объединяет установку соединения и TLS-рукопожатие (1-RTT или даже 0-RTT).
* **Улучшенная работа при смене сети (Connection Migration):** Соединение привязывается к уникальному идентификатору, что позволяет без разрыва связи переключаться между Wi-Fi и мобильной сетью.

### HTTPS (Hypertext Transfer Protocol Secure)

HTTPS — это не отдельный протокол, а комбинация HTTP с протоколом шифрования **[TLS (Transport Layer Security)](./tls.md)**. TLS "оборачивает" весь HTTP-трафик, обеспечивая три столпа безопасности: шифрование, аутентификацию и целостность.

* **Что шифруется?** После успешного установления TLS-соединения (рукопожатия), **весь HTTP-запрос и ответ полностью шифруются**. Это включает в себя:
  * Стартовую строку запроса (`GET /page HTTP/1.1`).
  * **Все HTTP-заголовки** (например, `Host`, `User-Agent`, `Cookie`).
  * Тело сообщения (payload).

* **Что не шифруется?** Шифрование происходит на транспортном уровне. Метаданные на более низких уровнях, такие как **IP-адреса источника и назначения**, остаются видимыми. Наблюдатель может видеть, что вы подключились к `IP-адресу` сервера, но не может видеть, какую именно страницу вы запросили или какие данные передали.

## Практические сценарии

### Кэширование в HTTP

**1. Кэширование на основе срока годности (Expiration)**
Сервер указывает, как долго ресурс можно считать "свежим" и использовать из кэша.

* **`Expires`:** Указывает точную дату и время устаревания. Недостаток: требует синхронизации времени.
* **`Cache-Control: max-age=<секунды>`:** Более современный механизм, указывающий время жизни ресурса в секундах с момента получения. Имеет приоритет над `Expires`.

**2. Кэширование с валидацией (Validation)**
Когда срок годности истекает, браузер выполняет **условный запрос (`Conditional GET`)**, чтобы проверить, изменился ли ресурс.

* **На основе версии (`ETag`):** Сервер отдает ресурс с заголовком `ETag: "уникальный-идентификатор"`. При следующем запросе клиент отправляет этот идентификатор в заголовке `If-None-Match`.
* **На основе даты (`Last-Modified`):** Сервер отдает ресурс с датой последнего изменения `Last-Modified`. Клиент при следующем запросе отправляет эту дату в `If-Modified-Since`.

**Ответ сервера на условный запрос:**

* **`304 Not Modified`**: Если ресурс не изменился. Ответ не содержит тела, что экономит трафик. Браузер использует версию из кэша.
* **`200 OK`**: Если ресурс изменился. Сервер присылает полную новую версию ресурса.

**Директивы `Cache-Control`**

| Директива | Описание |
| :--- | :--- |
| `public` | Ответ может кэшироваться любым кэшем, включая разделяемые (прокси). |
| `private` | Ответ предназначен для одного пользователя и может кэшироваться только частным кэшем (браузером). |
| `no-cache` | Ресурс можно кэшировать, но перед каждым использованием необходима валидация на сервере. |
| `no-store` | Запрещает любое кэширование. Запрос всегда отправляется на сервер. |
| `max-age` | Устанавливает время жизни ресурса в секундах. |

**Типы кэшей**

* **Частный кэш (Private Cache):** Кэш браузера.
* **Разделяемый кэш (Shared Cache):** Прокси-сервер или обратный прокси-сервер (Reverse Proxy).

### HTTP-аутентификация

#### 1. Базовая аутентификация (Basic Authentication)

**Принцип работы:**

1. **Первоначальный запрос:**
    * Клиент делает запрос к защищенному ресурсу без учетных данных.
2. **Ответ сервера:**
    * Сервер отвечает статусом `401 Unauthorized`.
    * В ответ добавляется заголовок `WWW-Authenticate: Basic realm="<Имя области защиты>"`, где `realm` — это описание защищенной области, которое браузер показывает пользователю.
3. **Ответ клиента:**
    * Браузер отображает встроенную форму для ввода логина и пароля.
    * После ввода данных формируется новый запрос с заголовком `Authorization`.
    * Учетные данные кодируются в формате `base64(имя_пользователя:пароль)`, и значение заголовка выглядит так: `Authorization: Basic <закодированная_строка>`.

**Безопасность:** Данные передаются в закодированном, но **не в зашифрованном** виде, поэтому их легко перехватить и декодировать. Использовать базовую аутентификацию можно **только** в сочетании с HTTPS, который обеспечивает шифрование всего канала связи.

#### 2. Дайджест-аутентификация (Digest Authentication)

* **Принцип:** Использует алгоритм MD5 для хеширования пароля, случайного значения (`nonce`) от сервера и других данных. Это позволяет доказать знание пароля, не передавая его по сети.

#### 3. Аутентификация на основе форм (Form-based Authentication)

* **Принцип:** Пользователь вводит учетные данные в HTML-форму. Данные отправляются `POST`-запросом на сервер, который проверяет их и, в случае успеха, создает сессию (обычно с помощью Cookies).

#### 4. Токены (Bearer Token)

* **Принцип:** После успешного входа сервер выдает временный **токен** (например, JWT). Клиент должен передавать этот токен с каждым последующим запросом в заголовке `Authorization: Bearer <токен>`.

#### 5. Cookies

Сервер может использовать куки для хранения сессионной информации. Атрибут `HttpOnly` защищает куки от доступа через JavaScript, что повышает безопасность.

#### 6. Single Sign-On (SSO)

Механизм, позволяющий пользователю проходить аутентификацию один раз для доступа ко множеству приложений. Подробнее см. [SSO (Single Sign-On)](../../Security/Concepts/authentication_vs_authorization.md#федеративная-идентификация-federated-identity-и-sso-single-sign-on).

### API и REST API

**API (Application Programming Interface)** — это набор правил и протоколов, который позволяет различным программным приложениям взаимодействовать друг с другом. Это способ взаимодействия между приложениями и серверами, предоставляющий эндпоинты с их собственными URL, на которые клиент или другой сервер может делать CRUD-запросы для взаимодействия.

**REST (Representational State Transfer)** — это архитектурный стиль программного обеспечения, который применяется для создания распределённых систем, таких как веб-службы. Он определяет набор принципов и ограничений, которым должна соответствовать система для обеспечения масштабируемости, гибкости и надежности.
Этот подход предложил Рой Филдинг, один из разработчиков [HTTP-протокола](./http.md), в начале 2000-х, как способ описания архитектуры Всемирной паутины.

**Основные концепции REST API:**

RESTFul-сервисы позволяют работать с ресурсами (данными) через унифицированный интерфейс, основываясь на простых и понятных HTTP-методах:

* **Ресурсы:** Каждая единица данных (например, пользователь, товар) рассматривается как ресурс, идентифицируемый уникальным универсальным идентификатором ресурса (URL/URI).
  * **Примеры URL-адресов ресурсов:**
    * Книга в библиотеке: `/books/2`
    * Страница книги: `/books/2/pages/145`
* **Унифицированный интерфейс:** Для взаимодействия с ресурсами используются стандартные HTTP-методы (CRUD — Create, Read, Update, Delete):
  * **GET** – получение данных о ресурсе. Является идемпотентным (многократное выполнение не меняет состояние на сервере) и безопасным (не вызывает побочных эффектов).
  * **POST** – создание нового ресурса или отправка данных для обработки. Не является идемпотентным.
  * **PUT** – полная замена существующего ресурса или создание ресурса, если его нет. Является идемпотентным.
  * **PATCH** – частичное обновление существующего ресурса.
  * **DELETE** – удаление ресурса. Является идемпотентным.
* **Отсутствие состояния (Stateless):** Как и сам HTTP, REST является архитектурой без сохранения состояния. Подробнее см. раздел [Stateless-протокол](#stateless-протокол-протокол-без-сохранения-состояния).
* **Кэширование:** Клиенты могут кэшировать ответы, что сокращает задержку и нагрузку на сервер.

**Ключевые преимущества REST:**

* **Простота:** Легко понять и использовать. Модель взаимодействия интуитивно понятна, так как основана на стандартных HTTP-методах.
* **Лёгкость (Lightweight):** Отсутствие дополнительных протокольных слоёв и использование текстовых форматов данных (JSON, XML) упрощает обработку данных и снижает накладные расходы.
* **Гибкость (Flexibility):** Работает с любыми клиентами (веб-браузеры, мобильные приложения, десктопные программы) и серверами, поддерживающими HTTP.
* **Масштабируемость:** Отсутствие состояния на сервере (statelessness) упрощает горизонтальное масштабирование.

### Примеры типичных REST-запросов (с использованием HTTP-методов)

1. **GET `/books/`** – возвращает список всех книг.
2. **GET `/books/2`** – предоставляет информацию о книге с ID 2.
3. **POST `/books/`** – добавляет новую книгу в коллекцию. Тело запроса содержит данные новой книги.
4. **PUT `/books/2`** – полностью обновляет информацию о книге с ID 2. Тело запроса содержит новые данные для книги.
5. **PATCH `/books/2`** – частично обновляет информацию о книге с ID 2 (например, меняет только заголовок).
6. **DELETE `/books/2`** – удаляет книгу с ID 2.

### HTTP API

HTTP широко используется для взаимодействия программ (Application Programming Interface).

* **Структура:** Клиент отправляет HTTP-запрос на определенный **endpoint** (URL), а сервер возвращает данные, чаще всего в формате **JSON**.
* **CRUD:** Операции с данными (Create, Read, Update, Delete) принято сопоставлять с методами HTTP:
  * **C**reate → `POST`
  * **R**ead → `GET`
  * **U**pdate → `PUT` / `PATCH`
  * **D**elete → `DELETE`
* **Инструменты:** Для работы с API используются [Postman](https://www.postman.com/), [cURL](../../Linux/Networking/Tools/http_clients/curl.md), [HTTPie](../../Linux/Networking/Tools/http_clients/httpie.md).
