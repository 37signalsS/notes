# Протокол TLS (Transport Layer Security)

## 1. Определения

**TLS (Transport Layer Security)** — это криптографический протокол, обеспечивающий защищённую передачу данных между узлами в сети. Его предшественником является устаревший протокол **SSL (Secure Sockets Layer)**.

TLS гарантирует три ключевых аспекта безопасности:

1. **Конфиденциальность (Confidentiality):** Данные шифруются и недоступны для прочтения третьими лицами.
2. **Целостность (Integrity):** Данные защищены от модификации в процессе передачи.
3. **Аутентификация (Authentication):** Позволяет убедиться, что вы общаетесь именно с тем сервером, с которым намеревались, предотвращая атаки "человек посередине" (Man-in-the-Middle).

### Ключевые компоненты

* **Центр сертификации (CA - Certificate Authority):** Доверенная организация (например, Let's Encrypt), которая выпускает и подписывает цифровые сертификаты. Подробнее об инфраструктуре см. в [Инфраструктура открытых ключей (PKI)](../../Security/Concepts/pki_overview.md).
* **TLS/SSL Сертификат (X.509):** Цифровой "паспорт", который связывает доменное имя (например, `example.com`) с открытым ключом сервера. Подпись от доверенного CA подтверждает подлинность этого "паспорта".
* **Набор шифров (Cipher Suite):** Комбинация криптографических алгоритмов, о которой договариваются клиент и сервер для защиты сессии (например, `TLS_AES_128_GCM_SHA256` в TLS 1.3).
* **SNI (Server Name Indication):** Расширение TLS, которое позволяет клиенту указать имя хоста (домен) в самом начале рукопожатия. Это критически важно для хостинга нескольких HTTPS-сайтов на одном IP-адресе.

## 2. Основные концепции

### Гибридное шифрование

TLS использует комбинацию двух типов шифрования:

* **Асимметричное шифрование (с открытым/закрытым ключами):** Используется на начальном этапе **рукопожатия (Handshake)** для безопасного обмена сессионным ключом. Оно медленное, но решает проблему безопасной передачи ключа.
* **Симметричное шифрование (с одним общим ключом):** Используется для шифрования всех данных *после* рукопожатия. Оно очень быстрое.

#### Механизм RSA (Rivest-Shamir-Adleman)

Это классический механизм обмена ключами, используемый в ранних версиях TLS:

1. **Сервер отправляет свой публичный ключ** клиенту (в составе сертификата).
2. **Клиент генерирует премастер-секрет** (premaster secret) — случайный набор данных, который станет основой для симметричного ключа.
3. **Клиент шифрует премастер-секрет публичным ключом сервера** и отправляет на сервер.
4. **Только сервер может расшифровать** это сообщение своим приватным ключом.
5. **Обе стороны** вычисляют из премастер-секрета общий **сессионный ключ** для симметричного шифрования.

> **Недостаток RSA:** Если приватный ключ сервера будет скомпрометирован в будущем, злоумышленник сможет расшифровать весь ранее перехваченный трафик (при условии, что он записывал сессии). Для защиты от этого используется **Perfect Forward Secrecy (PFS)**.

#### Механизм Диффи-Хеллмана (Diffie-Hellman) и ECDHE

Алгоритм **Диффи-Хеллмана** позволяет двум сторонам безопасно обменяться общими секретными данными по открытому каналу, даже если злоумышленник перехватывает все сообщения.

**Принцип работы:**

1. Обе стороны генерируют пары **эфемерных** (временных) ключей.
2. Стороны обмениваются публичными частями ключей.
3. Каждая сторона комбинирует свой приватный ключ с публичным ключом другой стороны.
4. В результате обе стороны получают **одинаковый общий секрет**, который никогда не передавался по сети напрямую.

**В TLS используется ECDHE (Elliptic Curve Diffie-Hellman)** — более современная и эффективная версия на основе эллиптических кривых.

> **Преимущество:** Даже если приватный ключ сервера будет украден, злоумышленник **не сможет** расшифровать старые сессии, так как для каждой сессии использовались уникальные эфемерные ключи. Это свойство называется **Perfect Forward Secrecy (PFS)**.

### Процесс рукопожатия (TLS Handshake)

Это процесс переговоров между клиентом и сервером в начале сессии.

#### Упрощенный TLS 1.2 Handshake (2-RTT)

1. **ClientHello:** Клиент отправляет список поддерживаемых шифров и генерирует случайные данные.
2. **ServerHello + Certificate:** Сервер выбирает шифр, отправляет свой сертификат и генерирует свои случайные данные.
3. **Проверка и обмен ключами:** Клиент проверяет сертификат сервера. Затем стороны используют асимметричное шифрование (например, на основе алгоритма ECDHE) для безопасного вычисления общего секретного ключа сессии.
4. **Finished:** Стороны обмениваются зашифрованными сообщениями для подтверждения, что ключ совпадает и рукопожатие успешно.

#### Упрощенный TLS 1.3 Handshake (1-RTT)

Процесс был значительно оптимизирован:

1. **ClientHello:** Клиент сразу отправляет свои параметры для обмена ключами, предполагая, какой алгоритм выберет сервер.
2. **ServerHello + Certificate + Finished:** Сервер отправляет все необходимое (сертификат, свои параметры ключа и сообщение `Finished`) в одном бандле.
3. **Finished:** Клиент отправляет свое сообщение `Finished`.

Это сокращает количество "поездок" данных туда-обратно (Round-Trip Time, RTT) и ускоряет установку соединения.

### Perfect Forward Secrecy (PFS)

Это свойство, гарантирующее, что компрометация долгосрочного закрытого ключа сервера не позволит расшифровать перехваченные в прошлом сессии. В TLS 1.2 и 1.3 это достигается за счет использования эфемерных (временных) ключей для каждой сессии (например, с помощью алгоритма **ECDHE**). В TLS 1.3 поддержка PFS является обязательной.

### Возобновление сессии (Session Resumption)

Чтобы избежать полного рукопожатия при повторных подключениях, TLS использует механизмы возобновления:

* **TLS 1.2:** Session IDs или Session Tickets.
* **TLS 1.3:** **PSK (Pre-Shared Key)**. Сервер выдает клиенту специальный тикет, который клиент может предъявить при следующем подключении для быстрого возобновления сессии (**1-RTT**).

### 0-RTT (Zero Round-Trip Time)

Эксклюзивная функция TLS 1.3, которая позволяет клиенту при повторном подключении отправлять зашифрованные данные уже в первом `ClientHello` сообщении. Это еще больше ускоряет соединение, но создает риски **атак повторного воспроизведения (replay attacks)**, поэтому его следует использовать с осторожностью и только для определенных типов запросов (например, идемпотентных GET-запросов).

### ALPN (Application-Layer Protocol Negotiation)

Расширение TLS, которое позволяет согласовать протокол прикладного уровня (например, **h2** для HTTP/2) в рамках TLS-рукопожатия, избегая дополнительного раунда переговоров.

## 3. Практические сценарии

### Сценарий 1: Защита веб-сервера (HTTPS)

Это самый распространенный случай использования TLS.

1. Вы получаете SSL-сертификат для вашего домена (например, с помощью **[Certbot и Let's Encrypt](../../WebServers/Concepts/https_with_certbot.md)**).
2. Настраиваете ваш веб-сервер (например, Nginx) для использования этого сертификата и прослушивания порта 443.
3. Сервер выполняет TLS-терминацию: принимает зашифрованный трафик от клиента, расшифровывает его и передает приложению в незашифрованном виде.

* **Руководство по настройке:** **[Оптимальная настройка TLS/SSL в Nginx](../../WebServers/Nginx/Security/TLS_SSL/nginx_tls_ssl_overview.md)**.

### Сценарий 2: Взаимная аутентификация (mTLS)

**Задача:** Обеспечить безопасное взаимодействие между микросервисами, где не только клиент проверяет сервер, но и сервер проверяет клиента.

**Решение:** Настройка **Mutual TLS (mTLS)**.

* Каждый сервис-клиент имеет свой собственный сертификат.
* При подключении сервер запрашивает и проверяет сертификат клиента.
* Это гарантирует, что к сервису могут подключаться только доверенные приложения, обладающие валидным сертификатом.
* **Пример реализации:** **[Аутентификация по клиентским SSL-сертификатам (mTLS) в Nginx](../../WebServers/Nginx/Security/TLS_SSL/nginx_mtls_configuration.md)**.

### Сценарий 3: Устранение распространенных ошибок

* **Ошибка: "Certificate Expired" / "Сертификат истек"**
  * **Причина:** Срок действия SSL-сертификата закончился.
  * **Решение:** Перевыпустить сертификат. Инструменты вроде Certbot автоматизируют этот процесс.
* **Ошибка: "Cipher Mismatch" / "Несоответствие шифров"**
  * **Причина:** Клиент и сервер не смогли договориться об общем наборе шифров. Часто бывает, если сервер настроен на поддержку только современных шифров, а клиент — устаревший.
  * **Решение:** Проверить и согласовать списки поддерживаемых шифров на сервере и клиенте.
* **Ошибка: "Certificate not trusted" / "Недоверенный сертификат"**
  * **Причина:** Либо используется самоподписанный сертификат, либо в цепочке доверия отсутствует промежуточный сертификат (intermediate certificate).
  * **Решение:** Убедиться, что сервер отдает полную цепочку сертификатов (fullchain.pem), а не только сертификат домена.

### Безопасность TLS: Векторы атак

Несмотря на надежность TLS, существуют векторы атак, которые могут поставить под угрозу безопасность соединения:

1. **Взлом сервера:**
   * Когда данные поступают на сервер, они расшифровываются для обработки.
   * Если сервер скомпрометирован, злоумышленник может получить доступ к расшифрованным данным.
   * Защита зависит от безопасности сервера и администраторов.

2. **Взлом соединения (перехват трафика):**
   * Злоумышленник пытается расшифровать передаваемые данные.
   * Периодически обнаруживаются уязвимости в протоколах SSL/TLS.
   * Использование устаревших версий (SSLv3, TLS 1.0, 1.1) делает атаки более вероятными.
   * **Защита:** Использовать TLS 1.2+ и алгоритмы с PFS (ECDHE).

3. **Взлом клиента (атака на пользователя):**
   * Установка вредоносного ПО (шпионского ПО, корневых сертификатов) на устройство пользователя.
   * Позволяет перехватывать данные до шифрования или после расшифровки на стороне клиента.
   * Этот метод часто используется компаниями для мониторинга трафика сотрудников (законность зависит от юрисдикции).

4. **Анализ трафика с расшифровкой:**
   * Использование SSLKEYLOGFILE для записи ключей сессии
   * MITM-прокси (Mitmproxy, Burp Suite) с установкой доверенного сертификата
   * Ядерная отладка для извлечения ключей из памяти (lsass.exe в Windows)
   * **Защита:** SSL Pinning, PFS, мониторинг процессов

> **Важно понимать:** TLS защищает канал передачи данных, но не защищает конечные точки (сервер и клиент). Компрометация любой из сторон сводит на нет защиту шифрования.

### TLS 1.2 vs TLS 1.3: влияние на расшифровку

**TLS 1.2**:

* Последовательная генерация ключей: `premaster secret → master secret → session keys`
* При использовании RSA ключи можно восстановить из приватного ключа сервера
* Перехват на ранних этапах handshake позволяет расшифровать сессию

**TLS 1.3**:

* Упрощённый handshake (1-RTT)
* Ключи генерируются из множества промежуточных значений, «разбросанных» по разным сообщениям
* Нет явного premaster/master secret в памяти
* Прямое извлечение ключей из памяти затруднено
* Требуется мониторинг процесса на уровне ОС (например, отладка SChannel/SSPI в Windows)

> **Практическое руководство:** См. **[Методы расшифровки TLS-трафика](../ServicesAndTools/Wireshark/tls_decryption_methods.md)** для подробного описания сценариев анализа.

### Доверие к Центрам Сертификации (CA)

Браузеры и операционные системы доверяют определенным **Центрам Сертификации (CA)**, публичные ключи которых встроены в них. Это создает **цепочку доверия**:

1. Владелец сайта генерирует пару ключей и отправляет **CSR (запрос на подпись сертификата)** в CA.
2. CA проверяет право владения доменом (через DNS, HTTP-challenge или email).
3. CA подписывает сертификат своим приватным ключом и выдает его владельцу сайта.
4. При подключении клиента к сайту, сервер отправляет свой сертификат.
5. Клиент проверяет подпись CA, используя встроенный публичный ключ CA.

**Риски:**

* Если CA скомпрометирован или выпустит сертификат для мошеннического сайта — доверие будет нарушено (были прецеденты).
* Некоторые организации используют собственные (корпоративные) CA для внутренних нужд.

> Подробное описание PKI-инфраструктуры, иерархии CA и механизмов отзыва сертификатов см. в [Инфраструктура открытых ключей (PKI)](../../Security/Concepts/pki_overview.md).

## 4. Дополнительная информация

* **Порт по умолчанию для HTTPS:** 443/TCP.
* **Тестирование конфигурации:** Используйте онлайн-сервис **[SSL Labs Server Test](https://www.ssllabs.com/ssltest/)** для глубокого анализа и оценки безопасности вашей TLS-конфигурации.
* **Связанные протоколы:** TLS используется для обеспечения безопасности многих протоколов, включая [HTTP (создавая HTTPS)](./http_protocols_optimization.md), FTP, SMTP и др.
