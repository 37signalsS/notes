# Протокол TLS (Transport Layer Security)

## Определения

**TLS (Transport Layer Security)** — криптографический протокол, обеспечивающий защищённую передачу данных между узлами в сети. Предшественник — устаревший протокол **SSL (Secure Sockets Layer)**.

TLS гарантирует три ключевых аспекта безопасности:

1. **Конфиденциальность (Confidentiality):** данные шифруются и недоступны для чтения третьими лицами.
2. **Целостность (Integrity):** данные защищены от модификации при передаче.
3. **Аутентификация (Authentication):** подтверждение подлинности сервера, предотвращение атак типа Man-in-the-Middle.

### Ключевые компоненты

* **Центр сертификации (CA — Certificate Authority):** доверенная организация (например, Let's Encrypt), выпускающая и подписывающая цифровые сертификаты. Инфраструктура PKI: [Инфраструктура открытых ключей (PKI)](../../Security/Concepts/pki_overview.md).
* **TLS/SSL-сертификат (X.509):** цифровой «паспорт», связывающий доменное имя с открытым ключом сервера. Подпись доверенного CA подтверждает подлинность.
* **Набор шифров (Cipher Suite):** комбинация криптографических алгоритмов, согласуемая клиентом и сервером для защиты сессии (например, `TLS_AES_128_GCM_SHA256` в TLS 1.3).
* **SNI (Server Name Indication):** расширение TLS, позволяющее клиенту указать имя хоста в начале рукопожатия. Критически важно для хостинга нескольких HTTPS-сайтов на одном IP-адресе.

## Основные концепции

### Гибридное шифрование

TLS комбинирует два типа шифрования:

* **Асимметричное шифрование (с открытым/закрытым ключами):** используется на этапе **рукопожатия (Handshake)** для безопасного обмена сессионным ключом. Медленное, но решает проблему безопасной передачи ключа.
* **Симметричное шифрование (с одним общим ключом):** используется для шифрования данных *после* рукопожатия. Быстрое.

#### Механизм RSA (Rivest–Shamir–Adleman)

Классический механизм обмена ключами в ранних версиях TLS:

1. Сервер отправляет публичный ключ клиенту (в составе сертификата).
2. Клиент генерирует **premaster secret** — случайный набор данных, основу симметричного ключа.
3. Клиент шифрует premaster secret публичным ключом сервера и отправляет на сервер.
4. Только сервер может расшифровать сообщение своим приватным ключом.
5. Обе стороны вычисляют из premaster secret общий **сессионный ключ** для симметричного шифрования.

> **Недостаток RSA:** при компрометации приватного ключа сервера злоумышленник сможет расшифровать весь ранее перехваченный трафик. Защита — **Perfect Forward Secrecy (PFS)**.

#### Механизм Диффи–Хеллмана (Diffie–Hellman) и ECDHE

Алгоритм **Диффи–Хеллмана** позволяет двум сторонам безопасно выработать общий секрет по открытому каналу.

**Принцип работы:**

1. Обе стороны генерируют пары **эфемерных** (временных) ключей.
2. Стороны обмениваются публичными частями ключей.
3. Каждая сторона комбинирует свой приватный ключ с публичным ключом другой стороны.
4. Результат — **одинаковый общий секрет**, никогда не передававшийся по сети напрямую.

**В TLS используется ECDHE (Elliptic Curve Diffie–Hellman)** — версия на основе эллиптических кривых.

> **Преимущество:** даже при краже приватного ключа сервера расшифровать старые сессии невозможно — для каждой использовались уникальные эфемерные ключи. Свойство называется **Perfect Forward Secrecy (PFS)**.

### Процесс рукопожатия (TLS Handshake)

Переговоры клиента и сервера в начале сессии.

#### Упрощённый TLS 1.2 Handshake (2-RTT)

1. **ClientHello:** клиент отправляет список поддерживаемых шифров и случайные данные.
2. **ServerHello + Certificate:** сервер выбирает шифр, отправляет сертификат и свои случайные данные.
3. **Проверка и обмен ключами:** клиент проверяет сертификат, затем стороны используют асимметричное шифрование (например, ECDHE) для вычисления общего секретного ключа сессии.
4. **Finished:** стороны обмениваются зашифрованными сообщениями для подтверждения совпадения ключей.

#### Упрощённый TLS 1.3 Handshake (1-RTT)

1. **ClientHello:** клиент сразу отправляет параметры для обмена ключами, предполагая выбор сервера.
2. **ServerHello + Certificate + Finished:** сервер отправляет сертификат, параметры ключа и `Finished` в одном пакете.
3. **Finished:** клиент отправляет своё сообщение `Finished`.

Сокращение RTT ускоряет установку соединения.

### Perfect Forward Secrecy (PFS)

Свойство, гарантирующее, что компрометация долгосрочного закрытого ключа сервера не позволит расшифровать прошлые сессии. В TLS 1.2 и 1.3 достигается эфемерными ключами для каждой сессии (например, ECDHE). В TLS 1.3 поддержка PFS обязательна.

### Возобновление сессии (Session Resumption)

Механизмы избежания полного рукопожатия при повторных подключениях:

* **TLS 1.2:** Session IDs или Session Tickets.
* **TLS 1.3:** **PSK (Pre-Shared Key)** — сервер выдаёт клиенту тикет для быстрого возобновления сессии (**1-RTT**).

### 0-RTT (Zero Round-Trip Time)

Функция TLS 1.3, позволяющая клиенту при повторном подключении отправлять зашифрованные данные уже в первом `ClientHello`. Ускоряет соединение, но создаёт риски **атак повторного воспроизведения (replay attacks)** — использовать с осторожностью и только для идемпотентных запросов (например, GET).

### ALPN (Application-Layer Protocol Negotiation)

Расширение TLS для согласования протокола прикладного уровня (например, **h2** для HTTP/2) в рамках рукопожатия, без дополнительного раунда переговоров.

## Практические сценарии

### Сценарий 1: Защита веб-сервера (HTTPS)

Наиболее распространённый случай использования TLS.

1. Получение SSL-сертификата для домена (например, **[Certbot и Let's Encrypt](../../WebServers/Concepts/https_with_certbot.md)**).
2. Настройка веб-сервера (Nginx) для использования сертификата и прослушивания порта 443.
3. Сервер выполняет TLS-терминацию: принимает зашифрованный трафик, расшифровывает и передаёт приложению в незашифрованном виде.

* **Руководство по настройке:** **[Оптимальная настройка TLS/SSL в Nginx](../../WebServers/Nginx/Security/TLS_SSL/nginx_tls_ssl_overview.md)**.

### Сценарий 2: Взаимная аутентификация (mTLS)

**Задача:** обеспечить безопасное взаимодействие между микросервисами, где сервер проверяет клиента.

**Решение:** настройка **Mutual TLS (mTLS)**.

* Каждый сервис-клиент имеет собственный сертификат.
* Сервер запрашивает и проверяет сертификат клиента.
* Только доверенные приложения с валидным сертификатом получают доступ.
* **Пример реализации:** **[Аутентификация по клиентским SSL-сертификатам (mTLS) в Nginx](../../WebServers/Nginx/Security/TLS_SSL/nginx_mtls_configuration.md)**.

### Сценарий 3: Устранение распространённых ошибок

* **Ошибка: «Certificate Expired» / «Сертификат истёк»**
  * **Причина:** срок действия SSL-сертификата закончился.
  * **Решение:** перевыпустить сертификат. Certbot автоматизирует процесс.
* **Ошибка: «Cipher Mismatch» / «Несоответствие шифров»**
  * **Причина:** клиент и сервер не смогли согласовать общий набор шифров.
  * **Решение:** согласовать списки шифров на сервере и клиенте.
* **Ошибка: «Certificate not trusted» / «Недоверенный сертификат»**
  * **Причина:** самоподписанный сертификат или отсутствие промежуточного сертификата в цепочке.
  * **Решение:** сервер должен отдавать полную цепочку (`fullchain.pem`).
  * **Диагностика:** [SSL Certificate Diagnostics](../../Security/Tools/ssl_certificate_diagnostics.md).

### Безопасность TLS: векторы атак

1. **Взлом сервера:** данные расшифровываются при обработке на сервере. Защита зависит от безопасности сервера.
2. **Взлом соединения (перехват трафика):** уязвимости в протоколах SSL/TLS, устаревшие версии (SSLv3, TLS 1.0, 1.1). **Защита:** TLS 1.2+ и алгоритмы с PFS (ECDHE).
3. **Взлом клиента (атака на пользователя):** вредоносное ПО, корневые сертификаты на устройстве пользователя. Перехват данных до шифрования или после расшифровки.
4. **Анализ трафика с расшифровкой:** SSLKEYLOGFILE, MITM-прокси (Mitmproxy, Burp Suite), ядерная отладка (lsass.exe в Windows). **Защита:** SSL Pinning, PFS, мониторинг процессов.

> **Важно:** TLS защищает канал передачи данных, но не конечные точки. Компрометация любой из сторон сводит защиту на нет.

Подробное описание методов расшифровки TLS: **[Методы расшифровки TLS-трафика](../ServicesAndTools/Wireshark/tls_decryption_methods.md)**.
