# Протокол TLS (Transport Layer Security)

## Определения

**TLS (Transport Layer Security)** — это криптографический протокол, обеспечивающий защищённую передачу данных между узлами в сети Интернет. Он **основан на протоколе SSL** (Secure Sockets Layer), изначально разработанном в Netscape. Чаще всего TLS используется для защиты веб-трафика ([[../http.md|HTTPS]]), но может применяться с любыми протоколами прикладного уровня.

Ключевые задачи TLS:

1.  **Шифрование (Confidentiality / Приватность):** Защита данных от прочтения посторонними. Весь трафик между клиентом и сервером шифруется.
2.  **Аутентификация (Authentication / Подлинность):** Проверка подлинности сторон. Клиент может быть уверен, что общается с настоящим сервером, а не с мошенническим сайтом.
3.  **Целостность (Integrity):** Гарантия того, что данные не были изменены в процессе передачи.

## Базовые концепции

### Шифрование и обеспечение приватности

Для обеспечения приватности (конфиденциальности) TLS использует **гибридную схему шифрования**, комбинируя симметричное и асимметричное шифрование:

*   **Симметричное шифрование:**
    *   **Принцип:** Используется **один и тот же ключ** как для шифрования, так и для расшифровки данных.
    *   **Преимущество:** Очень быстрое.
    *   **Недостаток:** Проблема безопасной передачи общего ключа.
    *   **Алгоритмы в TLS:** AES, ChaCha20.

*   **Асимметричное шифрование:**
    *   **Принцип:** Используется **пара ключей** (открытый и закрытый). Один ключ используется для шифрования данных, а другой — для их дешифрования. То, что зашифровано открытым ключом, может быть расшифровано только соответствующим закрытым ключом, и наоборот.
    *   **Преимущество:** Решает проблему безопасного обмена ключами (открытый ключ можно передавать незашифрованным).
    *   **Недостаток:** Значительно медленнее симметричного.
    *   **Алгоритмы в TLS:** RSA, алгоритмы на эллиптических кривых (ECDH).

**Гибридная схема в TLS:**
1.  **Асимметричное шифрование** используется на этапе **рукопожатия (handshake)** для безопасного согласования общего **сессионного ключа**.
2.  **Симметричное шифрование** используется для шифрования всех остальных данных в рамках сессии с помощью этого быстрого сессионного ключа.

**Обмен ключами и Perfect Forward Secrecy (PFS):**
Современные версии TLS (1.2 и 1.3) используют алгоритмы **Диффи-Хеллмана на эллиптических кривых (ECDHE)**. Ключевое преимущество этого подхода — **Perfect Forward Secrecy (PFS)**.
*   **Принцип:** Для каждой сессии генерируется **новая, временная (эфемерная) пара ключей**, которая уничтожается после завершения сессии.
*   **Гарантия:** Даже если злоумышленник в будущем украдет долгосрочный закрытый ключ сервера, он **не сможет** расшифровать перехваченный трафик прошлых сессий.
Обмен ключами на основе RSA, использовавшийся ранее, не обладал свойством PFS и **запрещен в TLS 1.3**.

### Целостность данных

**Целостность** — это гарантия того, что полученные данные в точности соответствуют отправленным. TLS обеспечивает целостность данных с помощью следующих механизмов:

*   **Код аутентификации сообщения (Message Authentication Code, MAC):**
    *   MAC — это криптографический хеш (например, SHA-256), который вычисляется на основе **данных и общего секретного ключа**.
    *   **Схема работы:** Отправитель вычисляет `MAC = HASH(данные + секретный_ключ)` и отправляет `[данные, MAC]`. Получатель пересчитывает `MAC'` и сравнивает с полученным `MAC`. Несовпадение указывает на изменение данных.
    *   Поскольку у злоумышленника нет секретного ключа, он не может подделать корректный MAC.

*   **Шифры аутентифицированного шифрования (AEAD):**
    *   Современные версии TLS используют **AEAD-шифры** (например, `AES-GCM`), которые **одновременно** выполняют шифрование и проверку целостности. Это более эффективно и безопасно.

### Аутентификация и защита от MitM-атак

**Аутентификация** в TLS отвечает на вопрос: "Я точно общаюсь с тем, с кем думаю?". Без нее асимметричное шифрование уязвимо для атаки **"человек посередине" (Man-in-the-Middle, MitM)**, где злоумышленник перехватывает трафик и выдает себя за легитимный сервер.

Проблема MitM решается с помощью **инфраструктуры открытых ключей (PKI)** и **TLS-сертификатов**:
*   **TLS-сертификат** — это цифровой документ, связывающий доменное имя (например, `google.com`) с открытым ключом сервера. Сертификат подписывается **Центром сертификации (Certificate Authority, CA)** — доверенной организацией (например, Let's Encrypt, DigiCert).
*   **Цепочка доверия:** Браузер или ОС доверяет предустановленным корневым сертификатам CA. При подключении к сайту браузер проверяет цифровую подпись сертификата сервера, используя открытый ключ CA. Если подпись верна, сертификату и открытому ключу сервера можно доверять.

### Процесс рукопожатия (TLS Handshake)

Рукопожатие — это серия сообщений в начале сессии, в ходе которой клиент и сервер:
1.  Договариваются о версии протокола TLS.
2.  Выбирают общий **набор шифров (Cipher Suite)**.
3.  Аутентифицируют сервер (и, опционально, клиента) с помощью сертификатов.
4.  Безопасно генерируют общий сессионный ключ.

**Этапы рукопожатия (упрощенно, на примере TLS 1.2 с ECDHE):**

| Шаг | Сообщение | Отправитель | Действие и цель |
| :-- | :--- | :--- | :--- |
| 1 | `ClientHello` | Клиент | **"Привет!"**<br>- Поддерживаемые версии TLS и наборы шифров.<br>- Случайное число (`Client Random`).<br>- Свой эфемерный открытый ключ для ECDHE. |
| 2 | `ServerHello` | Сервер | **"Привет! Договорились."**<br>- Выбранные версия TLS и набор шифров.<br>- Свой сертификат.<br>- Свой эфемерный открытый ключ для ECDHE, подписанный долгосрочным ключом.<br>- Случайное число (`Server Random`). |
| 3 | Проверка и генерация ключа | Клиент | 1. **Проверяет сертификат** сервера.<br>2. **Проверяет подпись** эфемерного ключа сервера.<br>3. Используя свой эфемерный закрытый ключ и открытый ключ сервера, **вычисляет общий сессионный ключ**. |
| 4 | Генерация ключа | Сервер | Используя свой эфемерный закрытый ключ и открытый ключ клиента, **вычисляет тот же самый сессионный ключ**. |
| 5 | `Finished` | Оба | **"Готово!"**<br>Стороны обмениваются сообщениями `Finished`, зашифрованными новым сессионным ключом. Это подтверждает, что рукопожатие завершено успешно и ключи совпадают. |

После этого весь дальнейший обмен данными шифруется с помощью быстрого симметричного сессионного ключа.

### Набор шифров (Cipher Suite)

Набор шифров — это согласованная комбинация алгоритмов, используемых для конкретного TLS-соединения. Пример для TLS 1.2:
`TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`
*   `ECDHE`: Алгоритм обмена ключами.
*   `RSA`: Алгоритм, которым подписан сертификат сервера (для аутентификации).
*   `AES_128_GCM`: Алгоритм симметричного шифрования (AEAD-шифр).
*   `SHA256`: Хеш-функция, используемая для генерации ключей и проверки целостности.

## Практические сценарии

### Server Name Indication (SNI)

**SNI** (Server Name Indication) — это расширение протокола TLS, позволяющее клиенту указать имя хоста, к которому он пытается подключиться, **на этапе TLS-рукопожатия** (в сообщении `ClientHello`).

**Практический смысл:** Если на одном IP-адресе размещено несколько [[WebServers/Nginx/Scenarios/nginx_as_reverse_proxy_for_grafana.md|HTTPS-сайтов]], веб-сервер, используя SNI, может определить, какой именно домен запрашивается, и предоставить соответствующий TLS-сертификат. Без SNI хостинг нескольких HTTPS-сайтов на одном IP-адресе был бы невозможен, так как сервер не смог бы выбрать правильный сертификат до начала зашифрованной связи.
