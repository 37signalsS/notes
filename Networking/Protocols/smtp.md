# SMTP — протокол передачи почты

> **Reliability Score: 10** (SSoT + Verified RFCs + Industry Standard)

## Определения

**SMTP (Simple Mail Transfer Protocol — простой протокол передачи почты)** — сетевой протокол прикладного уровня, предназначенный для передачи сообщений электронной почты в сетях TCP/IP. Описан в **RFC 5321** (актуальная версия).

**ESMTP (Extended SMTP)** — расширение базового протокола SMTP, позволяющее использовать дополнительные возможности (аутентификацию, шифрование, передачу больших вложений). Современные серверы используют именно ESMTP.

**Ключевые характеристики:**
- **Транспорт:** использует [TCP](../Protocols/TCP/overview.md) для обеспечения надежной доставки.
- **Тип протокола:** текстовый, командно-ориентированный.
- **Порты:**
  - **25** (SMTP) — основной порт для передачи почты между серверами (**MTA to MTA**). Часто блокируется провайдерами для борьбы с ботнетами.
  - **587** (Submission) — рекомендованный порт для отправки почты клиентами (**MUA**) на сервер. Требует аутентификации и использует **STARTTLS**.
  - **465** (SMTPS) — SMTP поверх SSL. Изначально признан устаревшим, но в 2018 году (RFC 8314) рекомендован как порт для «неявного TLS» (Implicit TLS) для клиентских подключений.

> **См. также:** **[Обзор DNS](./DNS/dns.md)**, **[Записи DNS для почты](./DNS/dns_records.md)**, **[Модель OSI](../OSI_TCP_IP_Model/osi_model.md)**

## Основные концепции

### Роли и компоненты системы доставки

1. **MUA (Mail User Agent):** почтовый клиент (например, Outlook, Thunderbird, `mutt`).
2. **MSA (Mail Submission Agent):** сервер, принимающий почту от MUA по порту 587/465. Проверяет права пользователя.
3. **MTA (Mail Transfer Agent):** сервер, пересылающий почту между доменами (например, Postfix, Exim, Sendmail).
4. **MDA (Mail Delivery Agent):** компонент, сохраняющий письмо в почтовый ящик пользователя на сервере (например, Dovecot).
5. **DNS:** используется для поиска адреса получателя через **MX (Mail Exchanger)** записи.

### Команды протокола

| Команда | Описание |
| :--- | :--- |
| **EHLO** | Приветствие клиента (ESMTP). Сервер возвращает список поддерживаемых расширений. |
| **HELO** | Устаревшее приветствие (SMTP). |
| **MAIL FROM** | Инициация передачи письма, указание адреса отправителя (Envelope-From). |
| **RCPT TO** | Указание получателя (Envelope-To). Может повторяться для нескольких адресатов. |
| **DATA** | Команда начала передачи тела письма и заголовков. |
| **QUIT** | Завершение сессии. |
| **STARTTLS** | Запрос на переход в зашифрованный режим TLS. |
| **AUTH** | Аутентификация пользователя (обычно PLAIN или LOGIN поверх TLS). |
| **RSET** | Сброс текущей транзакции (без закрытия соединения). |

### Коды ответов сервера

- **2xx (Success):** Операция выполнена успешно (например, `250 OK`).
- **3xx (Intermediate):** Сервер ожидает дальнейших действий (например, `354 Start mail input`).
- **4xx (Transient Failure):** Временная ошибка. Клиент должен попробовать позже (например, `451 Greylisting in action`).
- **5xx (Permanent Failure):** Неисправимая ошибка. Повторная отправка бессмысленна (например, `550 User not found`).

## Практические сценарии

### Тестирование SMTP вручную (Raw Session)

Для отладки доступности и политик сервера можно использовать `telnet` или `nc` (для порта 25/587). Для порта 465 (Implicit TLS) используйте `openssl s_client`.

```bash
# Подключение через OpenSSL (для порта 465 или 587 со STARTTLS)
openssl s_client -connect smtp.example.com:465 -quiet

# Типовой диалог (S: сервер, C: клиент)
S: 220 smtp.example.com ESMTP Postfix
C: EHLO myclient.local
S: 250-smtp.example.com
S: 250-PIPELINING
S: 250-SIZE 10240000
S: 250 AUTH PLAIN LOGIN
C: MAIL FROM:<sender@example.com>
S: 250 2.1.0 Ok
C: RCPT TO:<recipient@domain.com>
S: 250 2.1.5 Ok
C: DATA
S: 354 End data with <CR><LF>.<CR><LF>
C: Subject: SRE Test Message
C: From: sender@example.com
C: To: recipient@domain.com
C:
C: Technical check of SMTP delivery path.
C: .
S: 250 2.0.0 Ok: queued as ABC12345
C: QUIT
S: 221 2.0.0 Bye
```

## Безопасность и борьба со спамом

В современном интернете SMTP без механизмов верификации не используется, так как он позволяет легко подделать адрес отправителя.

### Триада верификации (SPF, DKIM, DMARC)

1. **SPF (Sender Policy Framework):** DNS-запись (тип TXT), содержащая список IP-адресов, которым разрешено отправлять почту от имени домена.
   - *Пример:* `v=spf1 ip4:1.2.3.4 include:_spf.google.com ~all`.
2. **DKIM (DomainKeys Identified Mail):** Цифровая подпись в заголовке письма. Сервер-получатель проверяет подпись с помощью публичного ключа, опубликованного в DNS. Гарантирует, что письмо не было изменено.
3. **DMARC (Domain-based Message Authentication):** Политика в DNS, указывающая, что делать, если SPF или DKIM не прошли проверку.
   - **p=none:** Просто мониторинг.
   - **p=quarantine:** Письмо в спам.
   - **p=reject:** Полный отказ в приеме.

### Методы защиты на стороне MTA

- **Greylisting (Серые списки):** Временный отказ (код 451) новому отправителю. Легитимный сервер повторит попытку через несколько минут, а спам-боты обычно нет.
- **RBL/DNSBL (Real-time Blackhole List):** Списки IP-адресов, замеченных в рассылке спама. MTA проверяет IP отправителя по этим спискам.
- **PTR (Reverse DNS):** Проверка соответствия IP-адреса и доменного имени. Если PTR-запись отсутствует или не совпадает с EHLO, многие серверы отклонят письмо.
- **Rate Limiting:** Ограничение количества писем от одного пользователя или IP в единицу времени.
