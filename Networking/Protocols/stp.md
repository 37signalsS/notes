# Spanning Tree Protocol (STP)

## Определения

**Сетевая петля (Network Loop)** — ситуация в коммутируемых сетях L2, когда между двумя устройствами существует более одного активного физического пути, что приводит к широковещательным штормам и нестабильности MAC-таблиц.

**Широковещательный шторм (Broadcast Storm)** — экспоненциальный рост широковещательного/мультивещательного трафика из-за петель, вызывающий полную загрузку пропускной способности и отказ сети.

**STP (Spanning Tree Protocol, IEEE 802.1D)** — протокол канального уровня (L2) для обнаружения и логической блокировки избыточных путей, предотвращающий петли при сохранении физической отказоустойчивости.

**Ключевая идея:** STP строит **логическое дерево** (spanning tree) с одним корневым коммутатором, блокируя избыточные порты и разрывая петли.

## Основные концепции

### Почему возникают петли

**Сценарий возникновения:**

```
    [Switch A]
     /        \
    /          \
[Switch B]──[Switch C]
```

1. **Источник:** Хост отправляет **broadcast-кадр** (например, [ARP-запрос](./arp.md))
2. **Flooding:** Коммутаторы рассылают broadcast во все порты, кроме входного
3. **Петля:** Кадр циркулирует по кругу A→B→C→A→...
4. **Экспоненциальный рост:** Каждый коммутатор копирует кадр → сеть перегружается

**Последствия:**

- Отказ сети (вся полоса занята "мусорным" трафиком)
- Нестабильность MAC-таблиц (один MAC виден с разных портов)
- Высокая нагрузка на CPU коммутаторов и хостов

### Принцип работы STP

**Алгоритм STP:**

1. **Выбор корневого коммутатора (Root Bridge)**
   - Выбирается коммутатор с наименьшим **Bridge ID** (приоритет + MAC)
   - Приоритет по умолчанию: 32768
   - Рекомендуется вручную назначать главный и резервный корневые коммутаторы

2. **Выбор корневых портов (Root Ports)**
   - На каждом не-корневом коммутаторе выбирается один порт с лучшим путём к корню

3. **Выбор назначенных портов (Designated Ports)**
   - На каждом сегменте выбирается один порт, который будет передавать трафик

4. **Блокировка избыточных портов (Blocked/Alternate Ports)**
   - Все остальные порты переводятся в состояние **blocking**

**Состояния портов STP (802.1D):**

| Состояние | Передача данных | Обучение MAC | Время |
|-----------|----------------|--------------|-------|
| **Blocking** | Нет | Нет | 20 сек (Max Age) |
| **Listening** | Нет | Да | 15 сек (Forward Delay) |
| **Learning** | Нет | Да | 15 сек (Forward Delay) |
| **Forwarding** | Да | Да | — |
| **Disabled** | Нет | Нет | — |

**Время конвергенции классического STP:** 30-50 секунд (недостаточно для современных сетей)

### Эволюция STP

| Протокол | Стандарт | Время конвергенции | Особенности |
|----------|----------|-------------------|-------------|
| **STP** | IEEE 802.1D | 30-50 сек | Классический, медленный |
| **RSTP** | IEEE 802.1w | 1-10 сек | Быстрая конвергенция, новые роли портов |
| **MSTP** | IEEE 802.1s | 1-10 сек | Несколько экземпляров STP для VLAN |
| **PVST+** | Cisco proprietary | 1-10 сек | STP на каждый VLAN (требует много CPU) |

**RSTP (Rapid STP) улучшения:**

- Новые роли портов: **Alternate**, **Backup**
- Быстрый переход в **forwarding** на edge-портах (PortFast)
- Активная отправка BPDU (каждые 2 сек вместо hello timer)
- Механизм **proposal/agreement** для быстрой конвергенции

**Рекомендация (2025):** Используйте **RSTP** или **MSTP** вместо классического STP.

## Практические сценарии

### Проверка статуса STP в Linux

Для мостов в Linux:

```bash
# Показать статус мостов
brctl show

# Пример вывода:
bridge name     bridge id               STP enabled     interfaces
br0             8000.0242ac110002       yes             eth0
                                                        eth1
docker0         8000.0242ac110003       no              veth12345
```

**Настройка STP на Linux bridge:**

```bash
# Включить STP на мосту
brctl stp br0 on

# Показать параметры STP
brctl showstp br0

# Установить приоритет моста
brctl setbridgeprio br0 4096
```

> **Примечание:** Docker по умолчанию отключает STP на `docker0`, так как управление сетью осуществляется на более высоком уровне.

### Настройка STP на коммутаторе (концептуально)

**Сценарий:** Отказоустойчивая сеть с двумя коммутаторами и сервером с двумя NIC.

```
    [Server with 2 NICs]
         /       \
        /         \
  [Switch A]──[Switch B]
       |          |
    [Uplink to Core/Router]
```

**Конфигурация:**

1. **Root Bridge:** Назначьте Switch A как корневой (приоритет 4096)
2. **Backup Root:** Switch B с приоритетом 8192
3. **PortFast:** Включите на портах, подключённых к серверам (мгновенный переход в forwarding)
4. **BPDU Guard:** Запретите получение BPDU на пользовательских портах (защита от петель)

**Пример (Cisco IOS):**

```cisco
spanning-tree mode rapid-pvst
spanning-tree vlan 1 priority 4096
interface GigabitEthernet0/1
  spanning-tree portfast
  spanning-tree bpduguard enable
```

### Диагностика проблем STP

**Симптомы проблем:**

- Периодические потери связи (1-2 минуты)
- Высокая загрузка CPU на коммутаторах
- Частые изменения топологии (TCN — Topology Change Notification)

**Команды диагностики:**

```bash
# На Cisco
show spanning-tree summary
show spanning-tree detail
show logging | include STP|SPAN

# На Juniper
show spanning-tree bridge
show spanning-tree interface
```

**Частые причины проблем:**

1. **Неправильный Root Bridge** — корнем становится слабый коммутатор
2. **Односторонняя связь (unidirectional link)** — UDLD может помочь
3. **Петля из-за misconfigured порта** — BPDU Guard должен блокировать
4. **Медленная конвергенция** — перейдите на RSTP

### Безопасность STP

**Атаки на STP:**

- **Root Bridge Attack:** Злоумышленник отправляет BPDU с лучшим приоритетом и становится корнем → весь трафик идёт через атакующего
- **BPDU Spoofing:** Подделка BPDU для изменения топологии

**Защита:**

| Функция | Описание | Где включать |
|---------|----------|--------------|
| **BPDU Guard** | Блокирует порт при получении BPDU | Access-порты |
| **Root Guard** | Запрещает порту становиться корневым | Uplink-порты |
| **Loop Guard** | Обнаруживает односторонние ссылки | Designated-порты |
| **BPDU Filter** | Полностью игнорирует BPDU | Edge-порты (с осторожностью) |

## Дополнительная информация

### Связь STP и VLAN

**Проблема:** Классический STP работает для всех VLAN одинаково → субоптимальное использование путей.

**Решения:**

- **PVST+ (Per-VLAN STP):** Отдельный экземпляр STP на каждый VLAN (Cisco)
- **MSTP (Multiple STP):** Группы VLAN привязываются к экземплярам STP (стандарт)

**Пример MSTP:**

```
Instance 1: VLAN 10, 20 → Root: Switch A
Instance 2: VLAN 30, 40 → Root: Switch B
```

Это позволяет балансировать трафик по разным физическим путям.
