# Балансировка нагрузки между локациями с HAProxy

**Актуально для:** HAProxy 2.0+ / 3.x

Материал основан на докладе Максима Куприянова «Использование HAProxy для балансировки нагрузки между локациями». Доклад записан, когда актуальной стабильной версией была 3.0; описанные механики (stick table, peers, конвертеры, `track`) неизменны в линейках 2.x и 3.x. Базовый справочник по HAProxy — в [обзоре HAProxy](../haproxy_overview.md).

## Определения

**RPS** (requests per second) — число запросов в секунду. Главный показатель нагрузки при работе с доставкой трафика; все остальные характеристики связаны с качеством работы сервиса.

**Stick Table** — хранилище состояний в оперативной памяти HAProxy (key-value). Используется для rate limiting, sticky sessions и защиты от перегрузов/DDoS.

**Sticky counter (`sc0`/`sc1`/`sc2`)** — переменная, связывающая текущий запрос с записью в stick table. До 8 параллельных счётчиков на запрос (в HAProxy Enterprise — до 12), число настраивается сборочным параметром `MAX_SESS_STKCTR`.

**ACL** (Access Control List) — механизм условий, по которым выполняются действия (маршрутизация, сброс, изменение заголовков).

**Peers** — секция конфигурации, объединяющая инстансы HAProxy для multi-master синхронизации stick tables по TCP.

**Вероятностное сбрасывание (probabilistic shedding)** — техника ограничения нагрузки: при превышении ёмкости отбрасывается случайная доля запросов, пропорциональная перегрузу, а не все запросы подряд.

**`track`** — параметр директивы `server`, позволяющий разделить состояние health check между бэкендами: сервер проверяется в одном бэкенде, а используется в другом.

## Основные концепции

### Зачем внешний балансировщик между локациями

Внешний балансировщик в режиме reverse proxy решает задачи, которые не покрывает ingress controller Kubernetes или один облачный провайдер:

- **Мобильность между провайдерами.** Вместо одного крупного облака — несколько сервис-провайдеров (в том числе российских). Бюджет и провайдер могут меняться; сервис должен быстро разворачиваться и так же быстро «сдуваться» при экономии ресурсов.
- **Масштабирование на новые локации.** Если завтра нужно запустить серверы в новой локации (пример из доклада — Владивосток), а у текущего провайдера нет площадки — серверы запускаются у другого провайдера, и внешний балансировщик перенаправляет на них часть трафика.
- **Отказоустойчивость.** У облачного провайдера может быть несколько дата-центров, но точка управления, как правило, одна; атака на неё рушит всё (такие случаи известны, особенно для сетевых инцидентов). Резервная локация плюс внешний балансировщик повышают отказоустойчивость.
- **Безопасность.** На внешнем балансировщике выполняется TLS-терминация, защита от DDoS и ограничение потока при всплесках интереса (новости, выборы).

Внешний балансировщик стоит над любыми бэкендами: отдельными серверами, kube-кластерами, их гибридом.

### Профиль HAProxy

- **Производительность.** Официальный тест (апрель 2021, AWS c6gn.16xlarge, 64-core ARM Graviton2): HAProxy 2.3 достиг 2.04 млн HTTPS-запросов в секунду, версия 2.4-dev — 2.07–2.08 млн, и 100 Gbps для проксируемого трафика (92 Gbps HTTP-пэйлоада на объектах 30 kB). Источник: haproxy.org и блог Willy Tarreau от 2021-04-08.
- **История и поддержка.** Проект существует с начала 2000-х, написан на C. Автор — Willy Tarreau, мейнтейнер Linux kernel stable tree. Поддержкой занимается большая команда, есть коммерческая реализация (HAProxy Enterprise); по данным доклада — более миллиарда загрузок образа на Docker Hub.
- **Бережное отношение к памяти.** Пример из исходного кода, приведённый в докладе: переменная sticky counter (структура `stkctr`) хранит составной адрес — указатель на запись таблицы, в двух младших битах которого упакованы два флага. Указатели выровнены по границе 4 байт минимум (x86, ARM), поэтому два младших бита всегда нулевые и пригодны для хранения флагов. Два булевых поля добавили бы 2 байта, а с учётом выравнивания структура выросла бы с 16 до 20 байт. Три таких переменных на запрос по умолчанию — при миллионах RPS экономятся мегабайты оперативной памяти. (Источник: комментарий «Composite address manipulation» в `include/haproxy/stick_table.h`.)

### Теория защиты от перегруза

Простейшая защита — жёсткий лимит на клиента. Проблемы: за одним IP может скрываться множество пользователей (NAT/CGNAT), а один пользователь может мигрировать между IP; при кратковременном всплеске блокируются все запросы клиента, хотя нужно отбросить только излишек.

**Вероятностное сбрасывание** решает обе проблемы на уровне всей системы:

1. Система имеет ёмкость `C` (например, 100 RPS — суммарно на все бэкенды).
2. Измеряется текущий суммарный RPS (`R`).
3. Для каждого запроса генерируется равномерное случайное число `U` в диапазоне `[0, R)`.
4. Если `U >= C` — запрос «неудачный» и сбрасывается (429); иначе обслуживается как обычно.

Доля сбрасываемых запросов равна `(R − C) / R`: при `R = 150` сбрасывается 1/3 запросов, сервис продолжает обслуживать ~100 RPS. При `R <= C` ничего не сбрасывается. Деградация плавная и пропорциональна перегрузу, состояние на клиенте не требуется.

### Синхронизация stick tables через peers

- Секция `peers` объединяет инстансы; таблицы объявляются директивой `table` внутри секции (HAProxy 2.0+) и адресуются как `<имя_peers>/<имя_таблицы>`. Альтернатива — `stick-table ... peers <имя_секции>` в frontend/backend.
- Протокол multi-master: инстанс, обновивший таблицу, уведомляет всех пиров; принимающая сторона **перезаписывает** значение — агрегации (суммирования) нет. Следствие: если два инстанса пишут в одну таблицу, они перезаписывают друг друга. Поэтому для подсчёта суммарного RPS каждый инстанс пишет в **свою** таблицу, а читает все.
- Одна stick table на frontend/backend секцию. Таблицы в секции `peers` снимают это ограничение: несколько таблиц живут в одной секции `peers`.
- Stick tables живут в пределах процесса: peers не синхронизируют таблицы между процессами на одной машине. Используйте `nbthread` вместо `nbproc` (`nbproc` удалён в 2.5).
- При graceful reload старый процесс передаёт все записи новому через peers-соединение.
- Локальный пир определяется по имени хоста, ключу `-L` при запуске или `localpeer` в секции `global`. Рекомендуется держать секцию `peers` идентичной на всех инстансах.

### Архитектура мультилокационной балансировки

- Несколько сайтов (локаций) в разных регионах, под каждым — свои бэкенды одного типа.
- Трафик предпочитает локальный сайт: пользователям из Москвы не идти во Владивосток и наоборот.
- При перегрузе локального сайта (или при выключении его серверов) трафик автоматически уходит на соседние локации и далее — на все серверы обоих сайтов.
- Бэкенды могут деградировать под нагрузкой, если знают текущий RPS системы целиком: балансировщик добавляет к запросу заголовок с нагрузкой, бэкенд отключает «рюшечки», снижает частоту опросов или логирует момент повышенной нагрузки.
- Полезно держать три уровня бэкендов: локальный пул, соседние (недалёкие) локации, все серверы.

## Практические сценарии

### Сценарий 1: Глобальная защита от перегруза (один инстанс)

**Наивный конфиг из документации** — ограничение по IP:

```haproxy
frontend http_frontend
    bind *:80
    mode http

    stick-table type ip size 1m expire 10s store http_req_rate(10s)
    http-request track-sc0 src
    http-request deny if { sc_http_req_rate(0) gt 100 }

    default_backend http_backend
```

Проблемы: ключ — IP (один IP скрывает многих пользователей, пользователь мигрирует между IP); при всплеске блокируются все запросы клиента, а не только излишек; таблица на 1M записей избыточна для защиты от перегруза.

**Вероятностное сбрасывание** — глобальный счётчик в единственной записи таблицы:

```haproxy
frontend fe_main
    bind *:80
    mode http

    # Единственная запись: глобальный счётчик запросов
    # http_req_rate(1s) — запросы за 1 секунду, т.е. RPS
    stick-table type integer size 1 expire 1s store http_req_rate(1s)

    # Каждый запрос попадает в одну и ту же запись (ключ — константа)
    http-request track-sc0 int(1)

    # Текущий суммарный RPS
    http-request set-var(txn.rps) sc_http_req_rate(0)

    # Случайное число в диапазоне [0, rps):
    # rand (fetch) — случайное целое от 0 до 2^32 по умолчанию;
    # mod (converter) — остаток от деления, аргумент может быть переменной
    http-request set-var(txn.rand) rand
    http-request set-var(txn.shed) var(txn.rand),mod(txn.rps)

    # Система перегружена: RPS выше ёмкости (100 — пример)
    acl overload var(txn.rps) gt 100
    # Запрос «неудачный»: случайное число не меньше ёмкости
    acl unlucky var(txn.shed) ge 100

    use_backend be_overload if overload unlucky
    default_backend be_app

backend be_overload
    mode http
    http-request return status 429

backend be_app
    mode http
    server app1 10.0.0.1:8080 check
    server app2 10.0.0.2:8080 check
```

Разбор:

- `stick-table type integer size 1 expire 1s store http_req_rate(1s)` — таблица из одной записи, устаревающей каждую секунду; `http_req_rate(1s)` — среднее число запросов за период 1 с, то есть RPS. `expire` должен совпадать с периодом rate-счётчика: счётчики обнуляются одновременно с истечением периода.
- `http-request track-sc0 int(1)` — `int(1)` — fetch, возвращающий константу; все запросы попадают в одну запись.
- `set-var(txn.rps) sc_http_req_rate(0)` — переменная в scope `txn` (транзакция целиком); переменные бывают также в scope `req`, `sess`, `proc`.
- `rand` — fetch (не converter), возвращает случайное целое в `[0, 2^32)`; `mod(<value>)` — converter, возвращает остаток от деления, аргумент может быть именем переменной.
- При `R = 150`: `shed` равномерно в `[0, 150)`, `P(shed >= 100) = 50/150` — сбрасывается треть запросов.

**Порядок правил.** Официальные примеры ставят `track-sc0` до проверки — текущий запрос уже включён в счётчик. Сообщество также использует обратный порядок (проверка до `track-sc0`): запрос оценивается против текущего значения до внесения вклада в счётчик. Для данной техники разница пренебрежима.

Отдельный `be_overload` позволяет вернуть кастомную страницу, перенаправить на другой сайт, попросить клиента подождать или записать информацию в лог — а не просто отдать 429.

### Сценарий 2: Два инстанса HAProxy (peers-синхронизация)

Один балансировщик — ненадёжно: машина может выйти из строя или потребоваться технологическое окно. Конфигурация для двух инстансов:

```haproxy
peers mypeers
    peer lb1 10.0.0.1:10000
    peer lb2 10.0.0.2:10000

    # Каждый инстанс пишет в свою таблицу:
    # синхронизация multi-master перезаписывает значения без агрегации
    table tb1_s1 type integer size 1 expire 5s store http_req_rate(5s)
    table tb2_s1 type integer size 1 expire 5s store http_req_rate(5s)

frontend fe_main
    bind *:80
    mode http

    # Инстанс 1 пишет в tb1_s1; на инстансе 2 эта строка — table mypeers/tb2_s1
    http-request track-sc0 int(1) table mypeers/tb1_s1

    # http_req_rate(5s) — запросы за 5 секунд; делим на 5, получаем RPS
    http-request set-var(txn.rps_local) sc_http_req_rate(0,mypeers/tb1_s1),div(5)
    http-request set-var(txn.rps_remote) sc_http_req_rate(0,mypeers/tb2_s1),div(5)

    # Суммарный RPS кластера
    http-request set-var(txn.rps) var(txn.rps_local),add(var(txn.rps_remote))

    http-request set-var(txn.rand) rand
    http-request set-var(txn.shed) var(txn.rand),mod(txn.rps)

    acl overload var(txn.rps) gt 100
    acl unlucky var(txn.shed) ge 100

    use_backend be_overload if overload unlucky
    default_backend be_app
```

Ключевые моменты:

- **Период 5s вместо 1s** — усреднение снижает эффект задержки синхронизации между инстансами; деление на 5 возвращает значение к RPS.
- **Две таблицы в одной секции `peers`** — отдельная секция `peers` на каждую таблицу не требуется.
- **Конфигурация генерируется** (Ansible, Jinja или иное): адреса пиров и «свою» таблицу в строке `track-sc0` не прописывают руками; секция `peers` при этом идентична на всех инстансах.
- Всегда указывайте таблицу явно (`table mypeers/tb1_s1`, `sc_http_req_rate(0,mypeers/tb1_s1)`) — при нескольких таблицах это избавляет от неопределённости.
- Обмен между балансировщиками в примере проходит в собственном формате без шифрования: если балансировщики вне локальной/доверенной сети — включите TLS для peers-трафика (см. документацию).

### Сценарий 3: Два сайта в разных регионах

Схема: два сайта (например, Санкт-Петербург и Владивосток), под каждым — бэкенды одного типа, по два инстанса HAProxy на сайт. Трафик обслуживается локальным сайтом, пока его средняя нагрузка на живой сервер ниже порога; при перегрузе — уходит на все серверы обоих сайтов.

```haproxy
peers mypeers
    peer lb1 10.0.0.1:10000
    peer lb2 10.0.0.2:10000
    peer lb3 10.0.0.3:10000
    peer lb4 10.0.0.4:10000

    table tb1_s1 type integer size 1 expire 5s store http_req_rate(5s)
    table tb2_s1 type integer size 1 expire 5s store http_req_rate(5s)
    table tb1_s2 type integer size 1 expire 5s store http_req_rate(5s)
    table tb2_s2 type integer size 1 expire 5s store http_req_rate(5s)

# Все серверы обоих сайтов: здесь проверяется доступность
backend be_all_sites
    mode http
    default-server check inter 3s fall 3 rise 2

    server app1_s1 10.1.0.1:80
    server app2_s1 10.1.0.2:80
    server app1_s2 10.2.0.1:80
    server app2_s2 10.2.0.2:80

# Локальные серверы сайта 1: состояние health check разделяется с be_all_sites
backend be_local_s1
    mode http

    server app1_s1 10.1.0.1:80 track be_all_sites/app1_s1
    server app2_s1 10.1.0.2:80 track be_all_sites/app2_s1

frontend fe_main
    bind *:80
    mode http

    # RPS каждого из четырёх инстансов (первая таблица — текущего инстанса)
    http-request track-sc0 int(1) table mypeers/tb1_s1
    http-request set-var(txn.rps_i1) sc_http_req_rate(0,mypeers/tb1_s1),div(5)
    http-request set-var(txn.rps_i2) sc_http_req_rate(0,mypeers/tb2_s1),div(5)
    http-request set-var(txn.rps_i3) sc_http_req_rate(0,mypeers/tb1_s2),div(5)
    http-request set-var(txn.rps_i4) sc_http_req_rate(0,mypeers/tb2_s2),div(5)

    # RPS на локальный сайт и суммарный RPS системы целиком
    http-request set-var(txn.rps_site) var(txn.rps_i1),add(var(txn.rps_i2))
    http-request set-var(txn.rps_all) var(txn.rps_site),add(var(txn.rps_i3)),add(var(txn.rps_i4))

    # Заголовок с нагрузкой на систему целиком — бэкенды деградируют под нагрузкой
    http-request set-header X-HAProxy-Rps var(txn.rps_all)

    # Число живых серверов локального сайта и средний RPS на один живой сервер
    http-request set-var(txn.live_local) srv_is_up(be_local_s1/app1_s1),add(srv_is_up(be_local_s1/app2_s1))
    http-request set-var(txn.avg_local) var(txn.rps_site),div(var(txn.live_local))

    # Локальный сайт перегружен (50 — пример порога) — уходим на все серверы
    acl overloaded var(txn.avg_local) ge 50

    use_backend be_all_sites if overloaded
    default_backend be_local_s1
```

Разбор:

- **`be_all_sites`** — перечисляет все серверы обоих сайтов и включает проверки доступности (`default-server check`). Секция идентична на всех инстансах HAProxy обоих сайтов; её назначение — знать, сколько серверов живо. Проверки настраиваются множеством способов: HTTP-проверки (статус или текст ответа), кастомные агенты (SPOE) произвольной сложности и частоты.
- **`track be_all_sites/app1_s1`** — параметр `track [<proxy>/]<server>`: сервер проверяется только в `be_all_sites`, а в `be_local_s1` его статус привязывается автоматически. Не нужно опрашивать серверы дважды — экономия особенно заметна при десятках тысяч серверов на один инстанс.
- **Заголовок `X-HAProxy-Rps`** (имя произвольное; в докладе — заглушка) — каждый запрос несёт текущий RPS системы целиком. Бэкенд, увидев высокую нагрузку, может отключить необязательные функции, пореже опрашивать downstream-сервисы или залогировать момент повышенной нагрузки.
- **`srv_is_up([<backend>/]<server>)`** — fetch, возвращает 1, если сервер доступен. Средний RPS на живой сервер: `rps_site / live_local`.
- **Деление на ноль безопасно:** `div` при нулевом делителе возвращает максимальное целое (2^63−1), поэтому при падении всех локальных серверов `avg_local` становится огромным и трафик автоматически уходит на `be_all_sites`.
- Порог 50 RPS на сервер и ёмкость 100 RPS — примеры; значения определяются нагрузочным тестированием ваших бэкендов.
- Секций бэкендов может быть больше двух (локальный пул, соседние локации, все серверы) — распределение по уровням задаётся `use_backend` с несколькими ACL.
- Все вычисленные метрики можно отправлять в логи (HAProxy поддерживает разные форматы, включая JSON) — так видно текущую нагрузку на систему целиком и её распределение между сайтами.

**Вариант по конкретным URL.** Вместо глобального счётчика можно считать RPS по конкретным тяжёлым ручкам: ключом таблицы служит path (например, `http-request track-sc0 path` или составной ключ `url32+src`), и ограничение применяется только к атакуемому эндпоинту, не трогая остальной трафик.

## Устранение неисправностей

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| Инстансы перезаписывают таблицы друг друга | Оба инстанса пишут в одну таблицу — синхронизация multi-master перезаписывает значения без агрегации | Каждый инстанс пишет в свою таблицу (`tb1_s1` / `tb2_s1`), читает все; «свою» таблицу задаёт генерация конфига |
| Синхронизация не работает | Имя локального пира (hostname / `-L` / `localpeer`) не совпадает со строкой `peer`; закрыт порт peers (в примерах 10000); секция `peers` различается на инстансах | Проверить имя пира (`haproxy -vv`, `show info`), открыть порт, привести секцию `peers` к идентичному виду |
| 5xx при перегрузе после перехода на `be_all_sites` | Сценарий 3 сам по себе не сбрасывает излишек запросов — он только расширяет пул | Добавить вероятностное сбрасывание из сценария 1 (домашнее задание докладчика) |
| Сервис полностью остановился при перегрузе | Все серверы динамически снизили свой вес до 0 | Не полагаться на автоматическое обнуление веса при массовой перегрузке; использовать shedding |
| ACL по заголовкам/path не срабатывает | Фронтенд в `mode tcp` | Использовать `mode http` для L7-условий |
| Счётчик «убегает» при высокой нагрузке | Проверка стоит после `track-sc0`, и текущий запрос уже включён в счётчик | Для точного учёта ставить проверку до `track-sc0` |

## Лучшие практики

- **Генерируйте конфигурации** (Ansible/Jinja и т. п.): адреса пиров и «свои» таблицы не правятся руками; секция `peers` остаётся идентичной на всех инстансах.
- **Явно указывайте таблицу** в `track-sc0 ... table <peers>/<table>` и в `sc_http_req_rate(0,<peers>/<table>)`.
- **TLS для peers-трафика**, если балансировщики находятся вне доверенной сети.
- **Комбинируйте механики:** локальный приоритет (сценарий 3) + глобальное вероятностное сбрасывание (сценарий 1) + заголовок нагрузки для деградации бэкендов.
- **`expire` = периоду rate-счётчика** — счётчики обнуляются синхронно с истечением периода.
- **Health checks:** HTTP-проверки по статусу/тексту ответа, кастомные агенты (SPOE); веса серверов могут меняться динамически (в том числе через проверки), но автоматическое обнуление веса всеми серверами при массовой перегрузе — путь к полной остановке сервиса.
- **Логируйте метрики нагрузки** (JSON-форматы) — распределение трафика между сайтами видно только по логам/метрикам.
