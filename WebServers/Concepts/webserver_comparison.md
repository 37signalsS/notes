# Сравнение веб-серверов и обратных прокси для продакшена

**Актуально для:** Nginx 1.26+ / Angie 1.8+ / Apache 2.4.60+ / HAProxy 3.0+ / Traefik 3.x / Lighttpd 1.4.x / Linux Kernel 5.15+ / 6.x

## Определения

**Веб-сервер (Web Server)** — программное обеспечение, принимающее входящие HTTP/HTTPS-запросы от сетевых клиентов и возвращающее ответы (статические файлы, сгенерированные шлюзовыми интерфейсами ответы или перенаправления).

**Обратный прокси (Reverse Proxy)** — сервер-посредник, размещаемый перед пулом внутренних сервисов (бэкендов). Принимает запросы от внешних клиентов, изолирует топологию внутренней сети, выполняет терминацию TLS, кэширование, модификацию заголовков и распределение нагрузки.

**L4-балансировка (Transport Layer Load Balancing)** — распределение трафика на транспортном уровне модели OSI (TCP/UDP, порты, IP-адреса, SNI) без дешифрования содержимого сессии и анализа прикладных данных.

**L7-балансировка (Application Layer Load Balancing)** — распределение трафика на прикладном уровне модели OSI с полным разбором HTTP-пакетов (URI, HTTP-методы, заголовки, cookies, тело запроса, gRPC-фреймы).

**Событийно-ориентированная архитектура (Event-Driven / Reactor Pattern)** — модель обработки соединений, при которой ограниченное число рабочих процессов или потоков мультиплексирует тысячи одновременных сетевых сокетов через системные вызовы ядра (`epoll` в Linux, `kqueue` в BSD), не выделяя отдельный поток или процесс на каждого клиента.

**Проблема C10k / C1000k** — инженерная задача по одновременному обслуживанию десятков тысяч (C10k) и сотен тысяч (C1000k) конкурентных клиентских соединений на одном физическом сервере без экспоненциальной деградации по памяти и процессорным ресурсам.

**MPM (Multi-Processing Module)** — модульная подсистема веб-сервера Apache HTTP Server, определяющая архитектуру привязки сетевых сокетов к системным процессам и потокам (`prefork`, `worker`, `event`).

**Zero-Downtime Reload (Hitless / Seamless Reload)** — применение обновленной конфигурации демона без прерывания активных TCP-сессий, без сброса соединений в очереди ядра (backlog) и без потери обрабатываемых запросов.

**Upstream Keepalive (Connection Pooling)** — пул постоянно открытых TCP/TLS-соединений между обратным прокси и бэкендами, устраняющий задержки на повторные трехсторонние рукопожатия (TCP handshake) и согласование ключей TLS при каждом запросе.

**Липкие сессии (Sticky Sessions / Session Affinity)** — механизм привязки запросов конкретного клиента к одному и тому же целевому бэкенду на протяжении всей сессии (через cookies, IP hash или TLS Session ID).

**Активные и пассивные проверки доступности (Health Checks)**:
- *Пассивные (Passive / Circuit Breaker):* оценка доступности бэкенда на основе анализа кодов ответов и таймаутов реального клиентского трафика.
- *Активные (Active / Synthetic Probing):* генерация периодических синтетических диагностических запросов к бэкендам по выделенному расписанию независимо от наличия клиентского трафика.

**Zero-Copy (sendfile, splice)** — системные вызовы ядра Linux, позволяющие передавать данные между файловым дескриптором диска и сетевым сокетом напрямую в пространстве ядра (kernel-space), минуя копирование буферов в пространство пользователя (user-space) и переключение контекста.

## Основные концепции и архитектурные различия

### Модели обработки соединений (I/O & Concurrency Models)

Производительность, утилизация оперативной памяти и поведение веб-серверов под пиковой нагрузкой определяются их базовой архитектурой параллелизма:

1. **Process-per-connection (Apache `prefork`):**
   - На каждое входящее клиентское соединение выделяется отдельный процесс ОС.
   - *Плюсы:* абсолютная изоляция (сбой в обработчике или утечка памяти не затрагивают другие запросы); поддержка потоконебезопасных модулей (устаревшие версии `mod_php`).
   - *Минусы:* колоссальный расход оперативной памяти (от 10 до 50 МБ на процесс); высочайшие накладные расходы ядра на context switching; непригодность для решения проблемы C10k.

2. **Thread-per-connection / Hybrid (Apache `worker`, Apache `event`):**
   - Модель `worker`: пул процессов, каждый из которых запускает фиксированное число потоков (`ThreadsPerChild`). Поток блокируется на чтении и записи сокета.
   - Модель `event`: оптимизация `worker`, где выделенный поток-слушатель (listener thread) отслеживает сокеты в состоянии Keepalive через системный селектор ядра и передает их рабочим потокам только при поступлении фактических данных запроса.

3. **Single-threaded Event Loop с архитектурой Master-Worker (Nginx OSS, Lighttpd):**
   - Master-процесс выполняет чтение конфигурации, управление правами и оркестрацию воркеров.
   - Каждый Worker-процесс выполняется в одном потоке, привязан к ядру CPU и крутит неблокирующий цикл обработки событий (Event Loop) через `epoll`.
   - Тысячи соединений обрабатываются асинхронно конечным автоматом. Расход памяти предсказуем и минимален (~2–4 МБ на 10 000 неактивных соединений).

4. **Multi-threaded Event Loop (HAProxy с `nbthread`, Envoy):**
   - Многопоточный асинхронный событийный цикл. Все потоки одного процесса разделяют сетевые структуры данных, опрашивая события ядра через `epoll`.
   - HAProxy распределяет соединения между потоками ядра, минимизируя межъядерные блокировки lock-free структурами и обеспечивая предельную пропускную способность сетевых пакетов на L4/L7.

5. **Go Runtime Goroutines / Network Poller (Traefik, Caddy):**
   - На каждое соединение или запрос создается легковесная горутина Go (начальный стек ~2–4 КБ).
   - Внутренний Network Poller среды выполнения Go транслирует операции ввода-вывода горутин в неблокирующие вызовы `epoll`.
   - *Плюсы:* простота разработки сложной логики маршрутизации и middleware.
   - *Минусы:* более высокое потребление памяти по сравнению с C (Nginx/HAProxy) и периодические задержки (jitter) сборщика мусора (GC pause) под экстремальной нагрузкой.

### Сравнительный анализ механизмов маршрутизации, аутентификации и протоколов

#### 1. Маршрутизация и сопоставление URL (Location Matching)
Принципы сопоставления входящих URL кардинально различаются между веб-серверами:
* **Nginx / Angie:** Используется детерминированный многофазный поиск: точные совпадения (`=`), префиксное дерево с остановкой регулярных выражений (`^~`), последовательный перебор регулярных выражений (`~`, `~*`) и общий префикс. Детальный разбор алгоритма: [Директива location: основы и приоритеты](../Nginx/Core/Location/basics.md).
* **Apache HTTP Server:** Иерархическое слияние контекстов (`<Directory>`, `<Location>`, `<Files>`) с возможностью децентрализованной перегрузки правил через `.htaccess`. Порядок вычисления зависит от порядка следования секций в конфигурационных файлах.
* **Traefik:** Декларативная маршрутизация через правила роутеров (`PathPrefix`, `Path`, `Host`, `HeadersRegexp`). Роутер с наибольшим приоритетом (вычисляемым по длине правила) обрабатывает запрос первым.
* **Caddy:** Порядок директив строго предопределен внутренним конвейером middleware; директива `route` позволяет принудительно задавать пользовательский порядок вычислений.

#### 2. Делегирование аутентификации на периметре (Forward Auth / Subrequests)
Вынос проверки прав на обратный прокси для защиты внутренних сервисов:
* **Nginx / Angie:** Модуль `auth_request` (`ngx_http_auth_request_module`) отправляет синхронный неблокирующий подзапрос в сервис авторизации до фазы передачи бэкенду. Возврат статуса `2xx` разрешает доступ, `401`/`403` прерывает запрос. Заголовки пользователя транслируются через `auth_request_set`. Подробнее: [Внутренняя маршрутизация и subrequests в Nginx](../Nginx/Core/Location/internal_routing.md).
* **Traefik:** Middleware `ForwardAuth` делегирует аутентификацию внешнему HTTP-сервису, автоматически копируя возвращенные им заголовки (`authResponseHeaders`) в запрос к upstream.
* **Apache:** Модули `mod_authnz_ldap`, `mod_auth_openidc` или `mod_auth_form` выполняют аутентификацию непосредственно внутри процесса воркера без внешних субреквестов.
* **HAProxy:** Проверка JWT-токенов на лету через `http-request auth` или lua-скрипты проверки сессий в памяти.

#### 3. Проксирование двунаправленных протоколов: WebSockets, SSE, gRPC
Особенности обработки долгоживущих и потоковых сессий:
* **Hop-by-Hop заголовки и Upgrade:** Обратный прокси обязан удалить пошаговые заголовки (`Connection`, `Keep-Alive`). Для установления WebSocket требуется явная инструкция переключения: `proxy_http_version 1.1; proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade";`.
* **Server-Sent Events (SSE):** Для потоковой доставки событий требуется принудительное отключение буферизации ответа (`proxy_buffering off;` или заголовок `X-Accel-Buffering: no`), иначе события накапливаются в буферах и задерживаются на минуты.
* **gRPC-проксирование:** Требует поддержки HTTP/2 между прокси и бэкендом (директива `grpc_pass` в Nginx/Angie) для передачи бинарных фреймов Protobuf и завершающих метаданных (trailers). Подробнее: [Проксирование WebSocket, SSE и gRPC в Angie](../Angie/angie-websocket-sse-grpc.md) и [Буферизация и стриминг в Nginx](../Nginx/Proxy/nginx_buffering_and_streaming.md).

#### 4. Продвинутые механизмы балансировки и ловушки Failover
* **Power of Two Choices (P2C / `random two least_conn`):** Случайный выбор двух узлов с направлением запроса наименее загруженному решает проблему «стадного эффекта» (thundering herd), характерную для стандартного `least_conn` под пиковой нагрузкой.
* **Консистентное хеширование (Consistent Hashing):** Применяется для кэш-серверов для минимизации сброса кэша при масштабировании пула.
* **Ловушка `proxy_next_upstream`:** Ретраи при ошибках бэкенда по умолчанию выполняются только для идемпотентных запросов (`GET`, `HEAD`). Включение повтора для неидемпотентных методов (`POST`, `PATCH`) без поддержки идемпотентных ключей на бэкенде приводит к двойным списаниям средств или дублированию записей в БД при сетевых сбоях. Детальный разбор: [Алгоритмы балансировки нагрузки Nginx и Angie](../Nginx/Proxy/Load_Balancing/algorithms.md).

#### 5. Идентификация клиента: Real-IP, X-Forwarded-For и PROXY Protocol
* **PROXY Protocol v1/v2:** L4-балансировщик передает IP и порт клиента в начале TCP-потока без терминации TLS. Поддерживается в HAProxy (`send-proxy`), Nginx (`proxy_protocol`) и Traefik.
* **Защита от IP Spoofing:** Слепое доверие заголовку `X-Forwarded-For` позволяет клиенту подделать любой адрес. Истинный адрес должен восстанавливаться только от доверенных прокси через `set_real_ip_from` и `real_ip_recursive on`. Детали: [Proxy Protocol в сетевой архитектуре](../../Networking/Protocols/proxy_protocol.md) и [Типовые уязвимости и ошибки конфигурации веб-серверов](./webserver_security_misconfigurations.md).

### Критические вопросы для SRE и системных администраторов

| Вопрос | Техническое обоснование |
| :--- | :--- |
| **Почему Nginx и HAProxy потребляют значительно меньше памяти, чем Apache?** | В Nginx и HAProxy используется событийный мультиплексор ввода-вывода (`epoll`). Одному соединению соответствует только структура сокета и компактный буфер в ядре и приложении. В Apache (даже с `event` MPM) для активной фазы требуется выделение системного потока со своим стеком памяти (от 1 до 8 МБ по умолчанию в Linux). |
| **В чем разница между L4 и L7 балансировкой с точки зрения вычислительных ресурсов?** | L4 работает с заголовками TCP/IP, не дешифрует TLS и не читает тело запроса. Это позволяет ядру использовать Zero-Copy (`splice`) с минимальной утилизацией CPU. L7 требует полной терминации TLS, буферизации, парсинга HTTP-заголовков, проверки ACL и сжатия контента, что повышает нагрузку на CPU в 5–10 раз. |
| **Как Nginx реализует Zero-Copy при отдаче статики?** | Через системный вызов ядра `sendfile(2)`. Nginx передает дескриптор открытого файла и дескриптор сетевого сокета ядру. Страницы из файлового page cache ядра пересылаются в сетевую карту напрямую через DMA (Direct Memory Access), минуя копирование данных в буфер пользовательского процесса. |
| **Что происходит при graceful reload в Nginx (`nginx -s reload`)?** | Master-процесс валидирует новый конфигурационный файл. При успехе он запускает новое поколение worker-процессов с новой конфигурацией, а старым воркерам отправляет сигнал `SIGQUIT`. Старые воркеры прекращают прием новых подключений (выходят из `epoll_wait` на слушающих сокетах), дорабатывают текущие активные запросы и штатно завершаются по истечении `worker_shutdown_timeout`. |
| **Почему HAProxy считается эталоном L7-балансировщика для высоконагруженных API?** | Архитектура HAProxy сфокусирована исключительно на перекладывании и анализе пакетов без дискового I/O. Оптимизированные алгоритмы разбора HTTP, структуры поиска соответствий (Elastic Binary Trees), нативный пул буферов памяти без фрагментации heap и механизм `nbthread` обеспечивают минимальную задержку (p99 latency < 1 ms при сотнях тысяч RPS). |

## Практические сценарии выбора и архитектурные матрицы

### Сценарий 1: Высоконагруженная интернет-выпуклость (DMZ Edge)

**Условия задачи:**
- От 20 000 до 100 000 входящих RPS на публичном периметре.
- Обязательная терминация TLS 1.3 / HTTP/2 / HTTP/3.
- Отдача большого объема медиа-статики (изображения, фронтенд-сборки).
- Необходимость защиты от ботов, гео-блокировки и rate limiting.

**Оптимальное решение:**
**Nginx** или **Angie** в качестве фронтального шлюза.
*Обоснование:* Поддержка `sendfile` и дискового `proxy_cache` разгружает бэкенды. Встроенные модули `limit_req`, `limit_conn`, а также гибкие таблицы `map` позволяют фильтровать вредоносный трафик на периметре с минимальными накладными расходами. В случае Angie дополнительно доступны нативный HTTP/3 и встроенные Prometheus-метрики без установки сторонних экспортеров.

---

### Сценарий 2: Модернизация legacy-приложений с поддержкой `.htaccess`

**Условия задачи:**
- Парк корпоративных веб-сервисов (PHP/Perl/Python CGI), исторически зависящих от директив переопределения конфигурации на уровне каталогов (`.htaccess`).
- Требование повысить устойчивость к пиковым нагрузкам без полного переписывания правил маршрутизации.

**Оптимальное решение:**
Двухуровневая архитектура: **Nginx/Angie (фронтенд)** + **Apache с `event` MPM (бэкенд)**.
*Обоснование:*
- Nginx принимает клиентские соединения, держит медленных клиентов (защита от Slowloris), выполняет TLS-терминацию и напрямую отдает статические файлы через `sendfile`.
- Запросы к динамике проксируются по локальной сети (`proxy_pass http://127.0.0.1:8080`) на Apache.
- Apache освобождается от удержания соединений и выполняет только генерацию ответа, сохраняя полную совместимость с локальными правилами `.htaccess` и модулями авторизации.

---

### Сценарий 3: Высоконагруженный внутренний API Gateway для микросервисов

**Условия задачи:**
- 50 000+ RPS межузлового RPC/REST-трафика.
- Критичны задержки p99 (не более 1–2 мс).
- Необходимы детальная телеметрия по каждому узлу, продвинутые ACL, зеркалирование трафика и динамическое отключение сбойных узлов (Circuit Breaking).

**Оптимальное решение:**
**HAProxy** с включенным `nbthread`.
*Обоснование:*
- Отсутствие накладных расходов на дисковый ввод-вывод.
- Продвинутые алгоритмы балансировки (`leastconn`, `roundrobin` с весами, `uri depth`).
- Нативные активные проверки (`check inter 1s fall 2 rise 3`).
- Управление состоянием узлов и весами на лету через Runtime Socket (`/run/haproxy/admin.sock`) без перезагрузки процессов.
- Нативная отдача Prometheus-метрик через директиву `http-request use-service prometheus-exporter`.

---

### Сценарий 4: Динамическое локальное микросервисное окружение на хосте

**Условия задачи:**
- Автономный хост или группа серверов с десятками сервисов, развернутых через Docker Compose, Podman или локальный Nomad/Consul.
- Частые деплои, динамическое изменение портов и контейнеров.
- Необходимость маршрутизации по доменным именам без ручного редактирования конфигурационных файлов и перезагрузки демонов.

**Оптимальное решение:**
**Traefik (3.x)**.
*Обоснование:*
- Нативная интеграция с Docker API и локальными провайдерами Service Discovery (Consul, Nomad).
- Автоматическое обнаружение маршрутов на основе метаданных (labels контейнеров).
- Мягкое динамическое перестроение графа маршрутизации в памяти без перезагрузки процессов и без потери сетевых пакетов.
- Встроенное автоматическое получение и ротация TLS-сертификатов через ACME/Let's Encrypt.

---

### Сценарий 5: Ресурсоограниченные серверы, VPS и Edge-узлы (IoT / Minimal Hardware)

**Условия задачи:**
- Физический сервер или виртуальная машина с объемом оперативной памяти 256–512 МБ.
- Отдача документации, статических файлов мониторинга или простой веб-интерфейс на FastCGI/CGI.
- Минимальное фоновое потребление CPU и памяти.

**Оптимальное решение:**
**Lighttpd** или компактный профиль **Nginx OSS**.
*Обоснование:* Базовая установка Lighttpd или Nginx с отключенными неиспользуемыми модулями потребляет менее 5–10 МБ RAM в активном состоянии. Lighttpd идеален для автономных контроллеров и одноплатных компьютеров благодаря простой модульной архитектуре и оптимизированному FastCGI-конвейеру.

---

### Сценарий 6: Отказоустойчивое L4-проксирование баз данных и очередей сообщений

**Условия задачи:**
- Балансировка и проксирование пула реплик СУБД (PostgreSQL read-only replicas, MySQL) или брокеров сообщений (RabbitMQ, Redis).
- Протоколы, отличные от HTTP (чистый TCP/TLS).
- Требуется проверка реального состояния репликации (проверка отставания реплики или статуса `pg_isready`).

**Оптимальное решение:**
**HAProxy** в режиме `mode tcp` или **Angie / Nginx Stream**.
*Обоснование:*
- HAProxy поддерживает специализированные проверки работоспособности СУБД: `pgsql-check`, `mysql-check`, `redis-check`, позволяя исключать рассинхронизированные узлы из пула чтения.
- Передача реального IP-адреса клиента на бэкенд через `send-proxy-v2` (Proxy Protocol).

## Диагностика и устранение неполадок

Сравнительный анализ типовых сбоев и различий в поведении веб-серверов. Методология общей пошаговой диагностики приведена в [Диагностика веб-серверов (Troubleshooting)](./webserver_troubleshooting.md).

### 1. Конфликт портов и ошибка `Address already in use`

- **Симптом:** Демон не запускается после установки или перезагрузки. В логе: `bind() to 0.0.0.0:80 failed (98: Address already in use)`.
- **Причина:** Порт 80 или 443 уже занят другим веб-сервером (например, дефолтный Apache был установлен как зависимость и запустился автоматически, блокируя Nginx/HAProxy) или зависшим воркером старого процесса.
- **Диагностика и устранение:**
  ```bash
  # Определение PID и имени процесса, удерживающего порт
  ss -tlpn 'sport = :80'
  # → LISTEN 0 128 0.0.0.0:80 0.0.0.0:* users:(("apache2",pid=854,fd=4))

  # Остановка конфликтующего сервиса и отключение автозапуска
  systemctl stop apache2
  systemctl disable apache2
  systemctl restart nginx
  ```

---

### 2. Разрыв соединений при Graceful Reload (In-Flight Connection Drops)

- **Симптом:** Мониторинг фиксирует всплеск сетевых ошибок `502 Bad Gateway` или сбросов TCP (`RST`) в момент применения конфигурации (`systemctl reload`).
- **Сравнение поведения:**
  - *Nginx / Angie:* При некорректно настроенном `worker_shutdown_timeout` старые воркеры принудительно убиваются по сигналу ядра, разрывая долгие клиентские загрузки или WebSocket-сессии.
    *Решение:* Задать достаточный интервал дренажа: `worker_shutdown_timeout 30s;`.
  - *HAProxy:* В старых конфигурациях без master-worker режима (`-W`) перезапуск через `kill -USR2` мог приводить к короткому окну race condition на сокете `SO_REUSEPORT`.
    *Решение:* Использовать режим master-worker (`-Ws`) с поддержкой передачи дескрипторов сокетов (Seamless Reload / Hitless Reload).

---

### 3. Исчерпание файловых дескрипторов (`Too many open files`)

- **Симптом:** Сервер перестает принимать новые соединения. В логах:
  - Nginx: `24: Too many open files while connecting to upstream` или `accept4() failed (24: Too many open files)`.
  - HAProxy: `Out of available sockets`.
- **Причина:** Одно клиентское L7-соединение потребляет как минимум 2 файловых дескриптора (клиентский сокет + upstream-сокет к бэкенду) плюс дескрипторы лог-файлов и статических файлов.
- **Устранение:**
  1. Увеличить лимит процесса на уровне systemd-юнита:
     ```ini
     # /etc/systemd/system/nginx.service.d/override.conf
     [Service]
     LimitNOFILE=65535
     ```
  2. Задать лимит воркера в конфигурации сервера:
     - Nginx / Angie: `worker_rlimit_nofile 65535;` в глобальном контексте.
     - HAProxy: `maxconn 60000` в секции `global`.
  3. Проверить текущий лимит запущенного процесса:
     ```bash
     cat /proc/$(pgrep -o -x nginx)/limits | grep "Max open files"
     # → Max open files  65535  65535  files
     ```

---

### 4. Различия кодов ошибок 502 / 503 / 504 между серверами

| Ситуация | Nginx / Angie | HAProxy | Apache (`mod_proxy`) |
| :--- | :--- | :--- | :--- |
| **Бэкенд не запущен (`Connection refused`)** | `502 Bad Gateway` | `503 Service Unavailable` (`s-down`, `NOSRV`) | `503 Service Unavailable` |
| **Бэкенд завис и не отвечает по таймауту** | `504 Gateway Timeout` | `504 Gateway Timeout` (`s-timeout`) | `504 Gateway Timeout` |
| **Бэкенд разорвал TCP соединение во время передачи** | `502 Bad Gateway` | `502 Bad Gateway` (`s-broken-pipe`) | `502 Bad Gateway` |
| **Все узлы группы upstream исключены health-check** | `502 Bad Gateway` | `503 Service Unavailable` | `503 Service Unavailable` |

---

### 5. Исчерпание портов источника (Ephemeral Port Exhaustion)

- **Симптом:** При высокой нагрузке на upstream-прокси в логах появляются ошибки `Cannot assign requested address` (ошибка 99) при попытке проксирования на бэкенд.
- **Причина:** При закрытии TCP-соединений сокеты переходят в состояние `TIME_WAIT` (по умолчанию удерживаются ядром 60 секунд). При отсутствии Keepalive к бэкендам пул эфемерных портов диапазона `ip_local_port_range` исчерпывается.
- **Устранение:**
  1. Настроить Upstream Keepalive в веб-сервере (см. раздел "Рекомендации").
  2. Включить переиспользование сокетов в ядре Linux:
     ```bash
     sysctl -w net.ipv4.tcp_tw_reuse=1
     sysctl -w net.ipv4.ip_local_port_range="10240 65535"
     ```

## Рекомендации и Best Practices

### 1. Архитектурная топология: разделение уровней ответственности

В зрелой корпоративной инфраструктуре рекомендуется разделять роли:
- **Уровень 1 (L4 VIP):** Отказоустойчивая пара балансировщиков с Keepalived / VRRP для распределения входящих пакетов. Детали реализации описаны в [Отказоустойчивость и предотвращение Split-Brain](./ha_split_brain_fencing.md).
- **Уровень 2 (L7 Edge / Ingress):** **Nginx** или **Angie** для терминации TLS, кэширования статики, фильтрации ботов и базового rate limiting. Практика защиты описана в [Rate Limiting для веб-серверов](./webserver_rate_limiting.md).
- **Уровень 3 (L7 Service Mesh / Core Balancer):** **HAProxy** для маршрутизации трафика между внутренними микросервисами с контролем задержек и детальным распределением нагрузки.
- **Уровень 4 (Application):** Бэкенды приложений (PHP-FPM, UWSGI, Go, Node.js) или Apache для legacy-сервисов с `.htaccess`.

---

### 2. Базовый тюнинг ядра Linux для серверов обратного прокси

Перед запуском любого веб-сервера под нагрузкой необходимо оптимизировать сетевой стек в `/etc/sysctl.d/99-webserver-performance.conf`:

```ini
# Максимальный размер очереди не принятых соединений (backlog сокета)
net.core.somaxconn = 65535

# Максимальный размер очереди незавершенных TCP-рукопожатий (SYN backlog)
net.ipv4.tcp_max_syn_backlog = 65535

# Разрешение переиспользования сокетов в состоянии TIME_WAIT для исходящих подключений
net.ipv4.tcp_tw_reuse = 1

# Расширение диапазона эфемерных локальных портов
net.ipv4.ip_local_port_range = 10240 65535

# Максимальное количество открытых файловых дескрипторов в системе
fs.file-max = 2097152

# Увеличение буферов TCP для высокоскоростных интерфейсов
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216
```

Применение параметров без перезагрузки:
```bash
sysctl --system
# → Applying /etc/sysctl.d/99-webserver-performance.conf ...
```

---

### 3. Обязательная настройка Upstream Keepalive

Отсутствие пула постоянных соединений к бэкенду заставляет прокси открывать новое TCP-соединение на каждый входящий HTTP-запрос. Это приводит к задержкам на TCP-handshake и быстрой деградации производительности.

**Пример конфигурации Upstream Keepalive в Nginx / Angie:**
```nginx
upstream backend_cluster {
    server 127.0.0.1:8080 max_fails=3 fail_timeout=10s;
    server 127.0.0.1:8081 max_fails=3 fail_timeout=10s;

    # Максимальное количество неактивных постоянных соединений к бэкендам на один воркер
    keepalive 64;
}

server {
    listen 80;
    server_name api.internal.local;

    location / {
        proxy_pass http://backend_cluster;
        # Обязательное включение протокола HTTP/1.1 и сброс заголовка Connection
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
    }
}
```

---

### 4. Базовое усиление безопасности (Hardening)

- **Сокрытие версий и баннеров серверов:**
  - Nginx / Angie: `server_tokens off;`
  - Apache: `ServerTokens Prod` и `ServerSignature Off`
  - HAProxy: Удаление заголовка через директиву в секции frontend: `http-response del-header Server`
  - Lighttpd: `server.tag = ""`
- **Запуск от непривилегированного пользователя:** Ни один рабочий процесс не должен исполняться от суперпользователя `root`. Всегда проверяйте директивы `user nginx;`, `user www-data;` или `user haproxy;`.
- **Изоляция на уровне systemd:** Включайте директивы `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true` и `NoNewPrivileges=true` в unit-файлах сервисов.
