# Сравнение веб-серверов и обратных прокси для продакшена

## Определения

**Веб-сервер** — программное обеспечение, принимающее HTTP/HTTPS-запросы от клиентов и возвращающее ответы (статический контент, перенаправление, проксирование).

**Обратный прокси (Reverse Proxy)** — посредник между клиентами и внутренними сервисами, скрывающий инфраструктуру, распределяющий нагрузку и выполняющий терминацию TLS.

**L4-балансировка** — распределение на транспортном уровне (IP, порт, TCP/UDP, SNI).

**L7-балансировка** — распределение на прикладном уровне (HTTP-заголовки, URI, cookies, тело запроса).

**Event loop / Событийная архитектура** — модель обработки запросов, при которой один процесс обслуживает множество соединений асинхронно без создания отдельного потока/процесса на каждое соединение.

**MPM (Multi-Processing Module)** — слой Apache, определяющий модель обработки соединений (`prefork`, `worker`, `event`).

**Sticky Session / Session Affinity** — привязка клиента к конкретному бэкенду на протяжении всей сессии.

**Upstream Keepalive** — пул открытых соединений между прокси и бэкендами, снижающий накладные расходы на TLS/TCP handshake.

**Health Check** — проверка доступности бэкендов (пассивная на основе реальных запросов или активная специальными проверками).

## Основные концепции

### Архитектурное сравнение

| Характеристика | Apache HTTP Server | Nginx / Angie | HAProxy | Traefik | Lighttpd |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Модель обработки** | Процессы или потоки на запрос (event MPM ближе к event loop). | Событийный цикл (epoll/kqueue). Минимальное потребление RAM. | Событийный цикл + многопоточность (`nbthread`). | Событийный цикл (Go runtime). | Событийный цикл. Легковесный. |
| **Статика** | Медленнее при высокой нагрузке. | `sendfile`, Zero-Copy. Лучшая скорость отдачи статики. | Нет встроенного кэширования статики. | Средняя скорость отдачи статики. | Хорошая скорость отдачи статики при низкой нагрузке. |
| **Конфигурация** | Поддержка `.htaccess` (распределенная). | Централизованная, считывается один раз при старте. | Централизованная. | Динамическая без перезагрузки. | Централизованная. |
| **Масштабируемость** | Деградирует при росте соединений. | Линейная при добавлении ядер CPU. | Линейная при добавлении ядер CPU. | Зависимость от Go runtime и provider API. | Деградирует при высокой нагрузке. |
| **Модули** | Динамическая загрузка. | Статическая компиляция (меньше поверхность атаки). | Статическая компиляция. | Плагины / Middlewares. | Модули. |
| **Service Discovery** | Нет нативно. | Нет нативно. | Нет нативно. | Docker, Nomad, Consul, Kubernetes. | Нет нативно. |
| **Активные проверки** | Нет нативно. | Angie и Nginx Plus да. | Да нативно. | Да нативно. | Нет нативно. |
| **TLS-терминация** | Да. | Да. | Да. | Да. | Да. |
| **HTTP/2** | Да. | Да. | Да. | Да. | Да. |
| **HTTP/3 (QUIC)** | Экспериментально. | Да (1.27+). | Да (3.0+). | Да (3.x). | Нет. |
| **L4-проксирование** | Да (`mod_proxy`). | Да (`ngx_stream_proxy_module`). | Да (`mode tcp`). | Да (`entryPoints.tcp`). | Да. |
| **WAF** | Нет нативно (третий модуль). | Нет нативно (третий модуль). | Нет нативно (третий модуль). | Нет нативно (третий модуль). | Нет нативно. |
| **Потребление памяти** | Высокое при большом числе соединений. | Низкое (~2 MB на 10 000 соединений). | Низкое. | Среднее. | Низкое. |
| **Роль в инфраструктуре** | Legacy-приложения, shared-хостинг, `.htaccess`. | Edge, терминация TLS, статика, универсальный прокси. | Высокоточный балансировщик, L4/L7. | Динамический маршрутизатор, контейнеры. | Легковесный Edge для малых нагрузок. |

### Критерии выбора

| Сценарий | Рекомендуемый инструмент | Обоснование |
| :--- | :--- | :--- |
| **Edge / Интернет-выпуклость** | Nginx / Angie / HAProxy | Лучшая производительность, TLS-терминация, защита. |
| **Legacy-приложения с `.htaccess`** | Apache | Необходимость динамической конфигурации. |
| **Классические монолиты** | Apache / Nginx | Широкая экосистема, совместимость. |
| **Высоконагруженный L7 балансировщик** | HAProxy | Экстремальная производительность, продвинутые ACL. |
| **L4-балансировка (TCP/UDP, БД)** | HAProxy / Nginx stream | Максимальная производительность на транспортном уровне. |
| **Динамический Service Discovery** | Traefik | Автоматическое обнаружение сервисов без перезагрузки. |
| **Контейнеры / Kubernetes** | Traefik / Nginx Ingress | Интеграция с оркестраторами. |
| **Маленький сайт / VPS с ограниченным RAM** | Lighttpd / Nginx | Низкое потребление памяти. |
| **Shared-хостинг** | Apache / Nginx | Поддержка виртуальных хостов, `.htaccess`. |
| **Микросервисы / API Gateway** | HAProxy / Traefik / Nginx | Гибкость маршрутизации, observability. |

### Сравнительная таблица: производительность и лимиты

| Характеристика | Apache (`event` MPM) | Nginx | HAProxy | Traefik | Lighttpd |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Соединения на процесс** | Зависит от `ThreadsPerChild`. | До 10 000+ на воркер. | До 10 000+ на воркер. | Зависимость от Go scheduler. | До нескольких тысяч на процесс. |
| **Потребление RAM на 10 000 соединений** | ~100–300 MB | ~2–10 MB | ~2–10 MB | ~20–50 MB | ~2–10 MB |
| **Макс. соединения по умолчанию** | 150 (RHEL), 256 (Debian) | Нет жесткого лимита. | `maxconn 4096` (обычно). | Зависит от OS и ulimit. | Зависит от конфигурации. |
| **Graceful reload** | `apachectl graceful` | `nginx -s reload` | `systemctl reload haproxy` | Автоматически при изменении конфигурации provider. | `service lighttpd reload` |
| **Graceful shutdown** | Да | Да (`worker_shutdown_timeout`) | Да (`grace` на уровне backend) | Да (`graceTimeout`) | Ограниченный. |

### Критические отличия для собеседований

| Вопрос | Ответ |
| :--- | :--- |
| **Почему Nginx потребляет меньше памяти, чем Apache?** | Событийная архитектура: один воркер обрабатывает тысячи соединений асинхронно, без создания потока/процесса на каждое соединение. |
| **В чем разница между L4 и L7 балансировкой?** | L4 работает с IP/портом/TCP, не видит содержимого трафика. L7 анализирует HTTP-заголовки, URI, cookies и может принимать решения на основе контента. |
| **Что такое C10k и как его решают?** | Задача одновременного обслуживания 10 000 соединений. Решается event loop (`epoll`, `kqueue`) и неблокирующим I/O. |
| **Почему Apache уступает Nginx в статике?** | Apache передает файлы через потоки, Nginx использует `sendfile` и асинхронный I/O (Zero-Copy). |
| **Что такое graceful reload vs graceful shutdown?** | Reload: подгрузка новой конфигурации без разрыва соединений. Shutdown: остановка процесса после завершения активных соединений. |
| **В чем преимущество HAProxy перед Nginx как балансировщика?** | Высокая точность L7-ACL, продвинутые алгоритмы, нативные метрики Prometheus, меньшая задержка. |
| **Когда выбирать Traefik?** | Когда нужен динамический Service Discovery в контейнерах и автоматическая конфигурация без перезагрузки. |

## Практические сценарии

### Сценарий 1: Выбор балансировщика для интернет-выпуклости

**Условия:**
- 1 млн запросов в день.
- TLS-терминация.
- Статика + REST API.
- Необходимость WAF.

**Решение:**
Nginx или HAProxy как L7 балансировщик на Edge. Traefik — если инфраструктура полностью в Docker/Kubernetes и требуется автоматическое обнаружение сервисов. Lighttpd не рекомендуется из-за ограниченной экосистемы.

### Сценарий 2: Выбор прокси для legacy-приложения

**Условия:**
- PHP-приложение с `.htaccess`.
- Shared-хостинг.
- Требуется модульная система Apache.

**Решение:**
Apache HTTP Server с `event` MPM. `.htaccess` позволяет распределять конфигурацию между директориями без централизованного управления.

### Сценарий 3: Выбор прокси для высоконагруженного API

**Условия:**
- 50 000 RPS.
- Минимальная задержка.
- Необходимость продвинутых ACL.

**Решение:**
HAProxy как L7 балансировщик. `leastconn` или `first` алгоритм. Нативные метрики Prometheus. Отсутствие встроенного кэширования не критично для API.

### Сценарий 4: Выбор прокси для микросервисов в Kubernetes

**Условия:**
- 20 микросервисов.
- Автоматическое масштабирование.
- Service Discovery.

**Решение:**
Traefik или Nginx Ingress Controller. Traefik автоматически обнаруживает сервисы через Kubernetes API. Nginx Ingress — если требуется статическая конфигурация с динамическими обновлениями через ConfigMap.

### Сценарий 5: Выбор прокси для маленького VPS

**Условия:**
- 256 MB RAM.
- Один сайт на WordPress.
- Необходимость PHP-FPM.

**Решение:**
Nginx или Lighttpd как обратный прокси для PHP-FPM. Lighttpd потребляет меньше памяти, но имеет меньшую экосистему. Nginx — более универсальный выбор.
