# Комплексный анализ и оптимизация производительности веб-приложений

## 1. Основы производительности веб-приложений

### 1.1. Аспекты производительности

*   **Клиентская производительность (Client-Side Performance):**
    *   **Загрузка кода приложения:** Получение HTML-документа, стилей (CSS), скриптов (JS), изображений, шрифтов и других ресурсов.
    *   **Исполнение кода:** Обработка и выполнение JavaScript в браузере, рендеринг страницы. Современные веб-приложения часто содержат большое количество JS-кода, что может значительно влиять на интерактивность.

*   **Серверная производительность (Server-Side Performance):**
    *   **Фронт-сервер (Nginx, Angie):** Обработка входящих запросов, терминирование TLS, компрессия контента, кэширование, балансировка нагрузки.
    *   **Бэкенд:** Производительность серверных приложений, баз данных, промежуточных сервисов.

*   **Сетевые ограничения (Network Limitations):**
    *   **Задержка (Latency/RTT - Round Trip Time):** Время, необходимое для прохождения сигнала от клиента к серверу и обратно. Является критическим фактором для сетевых соединений.
    *   **Пропускная способность (Throughput):** Объем данных, который может быть передан за единицу времени.
    *   **Потери пакетов (Loss Rate):** Процент потерянных пакетов, что негативно сказывается на скорости передачи данных, особенно для TCP-соединений.

### 1.2. Среда и принципы тестирования

*   **Реальный браузер:** Тестирование должно проводиться в реальном браузере. Основные движки: **Blink** (Chrome, Edge, Яндекс Браузер), **Gecko** (Firefox), **WebKit** (Safari). В первую очередь следует ориентироваться на Blink-подобные браузеры из-за их максимальной доли на рынке.
*   **Сетевые условия:** Необходимо эмулировать реалистичные, но не идеальные условия сети. Стандартным профилем является **"Fast 3G"** (или "4G Slow"):
    *   Пропускная способность: ~1.5-1.6 Mbps (downlink), ~0.75-0.8 Mbps (uplink)
    *   Задержка (RTT): ~150 мс. Этот параметр критичен, так как напрямую влияет на время установки соединений (DNS, TCP, TLS). Такой жесткий профиль позволяет выявить узкие места производительности современных сайтов, делая сетевую составляющую более наглядной для анализа.
*   **Эмуляция мобильных устройств:** Большинство тестов следует проводить в режиме эмуляции мобильного устройства, что включает уменьшенный viewport и замедление CPU (CPU throttling, обычно в 4-6 раз).
*   **Повторяемость:** Обеспечение повторяемости сетевых условий и среды тестирования абсолютно необходимо для сравнения результатов "до" и "после" оптимизации. Без этого тестирование скорости бесполезно.
*   **Чистота теста:**
    *   **Отключение кэша:** Всегда отключайте кэш браузера для симуляции "холодной" загрузки.
    *   **Режим инкогнито:** Запускайте тесты в режиме инкогнито, чтобы исключить влияние сторонних расширений.
    *   **Вынос DevTools:** Рекомендуется выносить панель DevTools в отдельное окно, чтобы она не влияла на viewport тестируемой страницы.

## 2. Ключевые метрики производительности

**Web Vitals** — это инициатива Google для оценки пользовательского опыта.

*   **Largest Contentful Paint (LCP):** Время отрисовки самого большого видимого элемента (изображения или текстового блока) на первом экране. Отражает скорость загрузки основного контента.
    *   *Хорошо:* < 2.5 с
    *   *Требует улучшения:* 2.5 - 4.0 с
    *   *Плохо:* > 4.0 с
*   **Interaction to Next Paint (INP):** Измеряет задержку между взаимодействием пользователя (клик, касание) и визуальным обновлением страницы. INP — новая метрика, заменившая FID (First Input Delay).
    *   *Хорошо:* < 200 мс
    *   *Что измеряет:* Отзывчивость страницы. Лучше всего измерять на реальных пользователях (RUM). 100 мс считается порогом, ниже которого реакция воспринимается как мгновенная.
*   **Cumulative Layout Shift (CLS):** Совокупный сдвиг макета. Оценивает визуальную стабильность страницы (насколько сильно "прыгают" элементы во время загрузки), предотвращая неожиданные перемещения, которые могут привести к ошибкам пользователя (например, случайный клик).
    *   *Хорошо:* < 0.1
    *   *Требует улучшения:* 0.1 - 0.25
    *   *Плохо:* > 0.25
*   **First Contentful Paint (FCP):** Время до отрисовки первого элемента контента.
*   **Time to Interactive (TTI):** Время, когда страница становится полностью интерактивной.
*   **Total Blocking Time (TBT):** Суммарное время, когда основной поток браузера был заблокирован, что мешало обработке пользовательского ввода.
*   **Speed Index:** Интегральный показатель скорости рендеринга, отражающий, насколько быстро контент визуально отображается.

**"Попугаи" (баллы):** Общая оценка производительности, часто используемая в Lighthouse. Хотя это и "самая бесполезная штука", если нет других метрик, то лучше она. Существует калькулятор, показывающий, как формируется балл и вес каждой метрики (который может меняться).

## 3. Инструменты для анализа производительности

### 3.1. Chrome DevTools

#### 3.1.1. Вкладка `Network`

*   **Анализ документа (Doc):** Начните с анализа основного HTML-документа. Проверьте время ответа сервера (**TTFB - Time To First Byte**), заголовки кэширования и сжатия.
*   **Анализ ресурсов (CSS, JS, Fonts, Img):**
    *   **Рендер-блокирующие ресурсы:** CSS и JS в `<head>` без `async`/`defer` блокируют отрисовку. Их следует минимизировать.
    *   **Приоритет загрузки:** Браузер назначает внутренние приоритеты ресурсам (High, Low) для оптимизации их загрузки.
    *   **Сторонние ресурсы:** Загрузка критически важных ресурсов с других доменов (например, jQuery с CDN) требует установки нового соединения (DNS, TCP, TLS), что добавляет минимум 3 RTT и замедляет процесс. Размещение блокирующего JS с другого домена в `<head>` — это **"EpicFail"** с точки зрения скорости. Для оценки RTT можно использовать `ping`.
    *   **Форматы:** Используйте современные форматы: **WOFF2** для шрифтов, **WebP/AVIF** для изображений.
    *   **Waterfall:** График для просмотра последовательности и длительности загрузки ресурсов.
*   **Статус внизу вкладки:** Показывает общее количество запросов и объем данных (скачанный и распакованный). 5 МБ распакованного JS — это серьезная проблема.

#### 3.1.2. Вкладка `Lighthouse`

*   Автоматический аудит сайта по категориям (Performance, SEO, Best Practices).
*   Дает оценку в баллах и рекомендации (Opportunities), например: "Удалите неиспользуемый CSS/JS".
*   **Важно:** Рекомендации Lighthouse нужно интерпретировать с осторожностью. Например, инлайнинг всего CSS, чтобы "убрать блокирующие ресурсы", может ухудшить кэширование и увеличить вес страниц. Lighthouse эмулирует сеть путем пересчета, а не реального ограничения скорости, что делает его эмуляцию менее точной, чем у WebPageTest.

#### 3.1.3. Вкладка `Performance`

*   Самый детальный инструмент для анализа. Позволяет записать профиль загрузки и увидеть подробный **flame graph** активности основного потока.
*   **Анализ Flame Graph:** Помогает найти конкретные функции JS, которые вызывают долгие блокировки (Long Tasks). Желтые блоки — активность JavaScript, фиолетовые — рендеринг (layout, paint).
*   **Синхронизация:** Все события (CPU, сеть, рендеринг) синхронизированы по времени, что позволяет точно определить причину задержек.

### 3.2. PageSpeed Insights

*   **Два типа данных:**
    1.  **Field Data (Полевые данные, CrUX):** Агрегированные данные от реальных пользователей Chrome за последние 28 дней. **Это самые важные и точные данные**, так как они показывают реальный опыт пользователей и влияют на ранжирование.
    2.  **Lab Data (Лабораторные данные):** Результат одного синтетического запуска Lighthouse с серверов Google. Результаты могут быть нестабильны из-за неконтролируемой точки тестирования, и на них следует смотреть с осторожностью.

### 3.3. WebPageTest

*   Наиболее мощный и профессиональный инструмент для анализа.
*   **Распределенная архитектура:** Позволяет тестировать сайт из разных географических точек с полным контролем над средой.
*   **Ключевые преимущества:**
    *   **Контролируемая среда:** Выбор локации, браузера, скорости соединения (включая **эмуляцию потери пакетов**, что является уникальной возможностью).
    *   **Стабильность:** Возможность проводить несколько прогонов (рекомендуется 3-5) для получения медианного результата.
    *   **Детальный отчет:**
        *   **Waterfall:** Подробный и наглядный график загрузки.
        *   **Filmstrip View:** Покадровая раскадровка процесса рендеринга, синхронизированная с Waterfall. Позволяет точно увидеть, какой ресурс задерживает отрисовку.
        *   **Видео:** Запись видео загрузки страницы.
    *   **Автоматизация:** Наличие API для интеграции в CI/CD.
    *   **SPOF (Single Point of Failure):** Инструмент для блокировки ресурсов для оценки их влияния.
    *   **Интерпретация:** Важно не слепо доверять цифрам. Динамический контент (например, **слайдеры**) может "обманывать" инструменты, завышая LCP и время загрузки, так как каждый новый слайд воспринимается как изменение контента. Анализируйте Filmstrip View, чтобы понять реальный опыт пользователя.

## 4. Оптимизация на стороне веб-сервера (Nginx/Angie)

### 4.1. Компрессия контента

Сжатие текстового контента (HTML, CSS, JS, SVG) — один из самых эффективных способов уменьшения объема данных.

*   **Алгоритмы:**
    *   **Gzip:** Старый, но широко поддерживаемый.
    *   **Brotli:** Современный, обеспечивает лучшее сжатие (особенно для статики).
    *   **ZSTD (Zstandard):** Очень высокая скорость сжатия/распаковки, идеален для динамической компрессии.

*   **Типы компрессии:**
    *   **Статическая:** Файлы сжимаются заранее (во время сборки). Идеальный вариант для статических ресурсов.
    *   **Динамическая:** Контент сжимается "на лету" при каждом запросе.

*   **Сравнение производительности (динамическое сжатие):**

    | Алгоритм | Уровень сжатия | Размер файла (КБ) | RPS (запросов/сек) | Примечания |
    | :------- | :------------- | :---------------- | :----------------- | :--------- |
    | Gzip     | 1              | 159               | 130                | Медленнее ZSTD, хуже сжатие, чем Brotli |
    | Gzip     | 4              | 135               | 100                | Умеренный баланс, но уступает современным |
    | Brotli   | 3              | 125               | 125                | Хорошее сжатие, приемлемая скорость |
    | Brotli   | 11             | 94                | 1                  | Максимальное сжатие, очень медленно (только для статики) |
    | ZSTD     | 1              | 140               | 240                | Самый быстрый для динамики, хорошее сжатие |
    | ZSTD     | 3              | 132               | 215                | Отличный баланс скорости и сжатия для динамики |

*   **Рекомендации:**
    *   Для **статического контента** используйте **Brotli** с максимальной степенью сжатия.
    *   Для **динамического контента** используйте **ZSTD** на низких уровнях сжатия.
    *   **Gzip** как запасной вариант.

### 4.2. Оптимизация TLS

Оптимизация TLS сокращает время установки безопасного соединения, которое может занимать до 4 RTT.

*   **Версии TLS:** Используйте **TLS 1.2** и **TLS 1.3**. TLS 1.3 значительно сокращает количество RTT для установки соединения (до 1 RTT или 0-RTT).
*   **Сертификаты:** Используйте **ECDSA-сертификаты** вместо RSA для меньшей нагрузки. Рекомендуется использовать пары сертификатов RSA и ECDSA.
*   **Кэширование сессий:** Включите **Session Cache** или **Session Tickets**.
*   **HSTS (HTTP Strict Transport Security):** Заголовок, заставляющий браузеры всегда использовать HTTPS. **Внимание:** HSTS — очень жесткий кэш, включайте его только после полной уверенности в корректности настройки HTTPS.
*   **Инструменты:** **Mozilla TLS Configurator**, **SSL Labs Server Test**.

**Пример конфигурации Nginx/Angie для TLS:**

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384';
ssl_prefer_server_ciphers on;
ssl_dhparam /etc/nginx/dhparam.pem; # openssl dhparam -out /etc/nginx/dhparam.pem 2048

ssl_session_cache shared:SSL:10m;
ssl_session_timeout 1d;
ssl_session_tickets off;

add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
```

### 4.3. HTTP/2 и HTTP/3

*   **HTTP/2:**
    *   **Мультиплексирование:** Устраняет проблему "блокировки начала очереди" (head-of-line blocking) на уровне приложения, позволяя отправлять несколько запросов по одному TCP-соединению.
    *   **Сжатие заголовков (HPACK).**
*   **HTTP/3:**
    *   **Основан на QUIC (UDP):** Решает проблему Head-of-Line Blocking на транспортном уровне.
    *   **Встроенный TLS:** Ускоряет установление соединения (0-RTT или 1-RTT).
    *   **"Холодный старт":** Браузер узнает о поддержке HTTP/3 через заголовок `Alt-Svc`.

**Пример конфигурации Nginx/Angie для HTTP/3:**

```nginx
# Требует Nginx 1.25.0+ или современную Angie
listen 443 ssl quic reuseport; # Слушаем UDP порт 443 для QUIC
listen 443 ssl http2;         # Слушаем TCP порт 443 для HTTP/2 и HTTP/1.1

http3 on;
add_header Alt-Svc 'h3=":443"; ma=86400';
```

### 4.4. Кэширование

*   **Клиентское кэширование (Browser Caching):** Управляется заголовками `Cache-Control` (например, `max-age`, `immutable`), `Expires`, `ETag`.
*   **Серверное кэширование (Nginx Proxy Cache):** Кэширование ответов от бэкенд-серверов. Значительно снижает нагрузку на бэкенд. Подробно этот механизм рассмотрен в заметке о [[../Nginx/Performance/nginx_proxy_caching.md|кэшировании в Nginx]].
    *   Настраивается с помощью `proxy_cache_path`, `proxy_cache`, `proxy_cache_valid`.
    *   `proxy_use_stale` и `proxy_background_update` позволяют отдавать устаревший контент при проблемах с бэкендом и плавно обновлять кэш.
    *   **Ограничение:** Стандартный Nginx не имеет встроенных средств для точечной инвалидации кэша.

**Пример конфигурации Nginx Proxy Cache:**

```nginx
# Определение зоны кэширования в http-блоке
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m inactive=60m max_size=1g;

# Использование кэша в location
location / {
    proxy_pass http://my_backend;
    proxy_cache my_cache;
    proxy_cache_valid 200 302 1h;
    proxy_cache_valid 404 1m;
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
    proxy_cache_background_update on;
    proxy_cache_lock on;
    add_header X-Proxy-Cache $upstream_cache_status;
}
```

## 5. Распространенные проблемы и предостережения

*   **Блокирующие ресурсы в `<head>`:** Каждый CSS и синхронный JS откладывает начало отрисовки.
*   **Большое количество или объем JS:** Длительное выполнение JavaScript блокирует основной поток, делая страницу неинтерактивной.
*   **Неоптимизированные изображения:** Старые форматы и отсутствие сжатия увеличивают время загрузки.
*   **Динамические элементы (слайдеры):** Могут "обманывать" инструменты тестирования, завышая LCP, так как каждый новый слайд воспринимается как изменение контента.
*   **Отсутствие Lazy Loading:** Загрузка всех изображений, даже тех, что находятся за пределами видимой области, замедляет первоначальную загрузку (`loading="lazy"` в помощь).
*   **Сторонние скрипты (счетчики, аналитика, реклама):** Могут значительно влиять на производительность. Их код часто раздут и требует много ресурсов. Например, Google Tag Manager может быть "злым" с точки зрения влияния на интерактивность.
*   **Осторожность с CDN и автоматическими сервисами:**
    *   Загрузка критичных ресурсов с медленных CDN или использование сервисов "ускорения в один клик" (включая некоторые функции популярных CDN, например, Cloudflare) может замедлить сайт.
    *   Часто автоматические сервисы применяют общие, неоптимальные методики.
    *   **Никогда не доверяйте маркетинговым заявлениям.** Эффективность любого инструмента или сервиса необходимо проверять с помощью детального тестирования (например, через WebPageTest), сравнивая метрики "до" и "после" внедрения.
