# Оптимизация веб-приложений: Обзор

Оптимизация веб-приложений — это комплексный процесс, направленный на улучшение скорости загрузки, отзывчивости и общего пользовательского опыта. Она охватывает как клиентскую, так и серверную стороны, а также сетевые аспекты взаимодействия.

## 1. Аспекты производительности веб-приложений

Производительность веб-приложений можно разделить на три основных аспекта:

*   **Клиентская производительность (Client-Side Performance):**
    *   **Загрузка кода приложения:** Получение HTML-документа, стилей (CSS), скриптов (JS), изображений, шрифтов и других ресурсов.
    *   **Исполнение кода:** Обработка и выполнение JavaScript в браузере, рендеринг страницы. Современные веб-приложения часто содержат большое количество JS-кода, что может значительно влиять на интерактивность.

*   **Серверная производительность (Server-Side Performance):**
    *   **Фронт-сервер (Nginx, Angie):** Обработка входящих запросов, терминирование TLS, компрессия контента, кэширование, балансировка нагрузки.
    *   **Бэкенд:** Производительность серверных приложений, баз данных, промежуточных сервисов.

*   **Сетевые ограничения (Network Limitations):**
    *   **Задержка (Latency/RTT - Round Trip Time):** Время, необходимое для прохождения сигнала от клиента к серверу и обратно. Является критическим фактором для сетевых соединений.
    *   **Пропускная способность (Throughput):** Объем данных, который может быть передан за единицу времени.
    *   **Потери пакетов (Loss Rate):** Процент потерянных пакетов, что негативно сказывается на скорости передачи данных, особенно для TCP-соединений.

## 2. Тестирование скорости веб-приложений

Для оценки производительности используются различные метрики и инструменты:

### 2.1. Метрики производительности

Метрики можно классифицировать по стадиям загрузки и интерактивности:

*   **Метрики загрузки:**
    *   **Время загрузки страницы:** Общее время, необходимое для полной загрузки всех ресурсов.
    *   **Time To First Byte (TTFB):** Время от начала запроса до получения первого байта ответа от сервера.
*   **Метрики рендеринга:**
    *   **Start Render:** Время, когда на экране начинает что-то отрисовываться (отличный от белого экран).
    *   **Speed Index:** Метрика, показывающая, насколько быстро контент страницы становится визуально завершенным.
    *   **Largest Contentful Paint (LCP):** Время рендеринга самого большого видимого элемента контента на первом экране. Ключевая метрика для оценки скорости загрузки.
*   **Метрики интерактивности:**
    *   **Total Blocking Time (TBT):** Общее время, в течение которого основной поток заблокирован, предотвращая реагирование на пользовательский ввод.
    *   **Interaction to Next Paint (INP):** Метрика, измеряющая задержку между взаимодействием пользователя (клик, касание) и визуальным обновлением страницы.
    *   **Cumulative Layout Shift (CLS):** Измеряет сумму всех неожиданных сдвигов макета страницы, которые происходят во время загрузки.

### 2.2. Web Vitals

**Web Vitals** — это набор метрик, продвигаемых Google для оценки пользовательского опыта. Они включают:
*   **Largest Contentful Paint (LCP):** Скорость загрузки.
*   **Interaction to Next Paint (INP):** Интерактивность.
*   **Cumulative Layout Shift (CLS):** Визуальная стабильность.

Эти метрики используются в инструментах Google для анализа скорости и могут влиять на ранжирование в поиске.

### 2.3. Инструменты тестирования

*   **DevTools (Chrome Lighthouse):** Встроенный в браузер инструмент для синтетического тестирования. Позволяет получить отчет по Web Vitals и рекомендации по улучшению. Эмулирует сетевые условия и производительность CPU. **Важно:** Lighthouse эмулирует сетевые условия путем пересчета параметров, а не реального ограничения скорости, что делает его эмуляцию менее точной, чем у WebPageTest. Рекомендации Lighthouse нужно интерпретировать с осторожностью.
*   **PageSpeed Insights:** Облачный инструмент от Google, который запускает Lighthouse с серверов Google и предоставляет как лабораторные данные (синтетический тест), так и полевые данные (Real User Monitoring - RUM), если сайт имеет достаточный трафик. **RUM-данные отражают реальный пользовательский опыт и являются наиболее ценными для оценки скорости сайта.**
*   **WebPageTest:** Мощный инструмент для синтетического тестирования с распределенной архитектурой. Позволяет тестировать сайт из разных географических точек с различными сетевыми профилями.
    *   **Профиль "3G Fast":** Рекомендуемый профиль для тестирования, эмулирующий реальные, но пессимистичные условия (например, 1.6 Мбит/с пропускной способности, 150 мс задержки). Использование такого профиля помогает выявить узкие места и обеспечивает повторяемость результатов.
    *   **Film Strip View:** Визуальное представление процесса рендеринга страницы по кадрам, что позволяет наглядно оценить, когда появляется первый контент и когда страница становится интерактивной.
    *   **Waterfall Chart:** Подробная диаграмма загрузки всех ресурсов, показывающая последовательность запросов, время ответа сервера (TTFB), время загрузки и рендеринга.
    *   **Time To First Byte (TTFB):** Ключевая метрика, показывающая время от начала запроса до получения первого байта ответа от сервера. Высокий TTFB может указывать на проблемы с производительностью бэкенда или сетевые задержки.
    *   **Синтетические тесты vs. RUM:** Синтетические тесты (Lighthouse, WebPageTest) полезны для выявления проблем и оптимизации в контролируемых условиях. Однако **наиболее важной является скорость сайта для реальных пользователей (RUM)**, так как она отражает фактический опыт взаимодействия.


## 3. Оптимизация веб-серверов (Nginx/Angie)

### 3.1. Компрессия контента

Сжатие текстового контента (HTML, CSS, JS, SVG) является одним из самых эффективных способов уменьшения объема передаваемых данных.

*   **Алгоритмы сжатия:**
    *   **Gzip:** Старый, но широко поддерживаемый алгоритм.
    *   **Brotli:** Современный алгоритм, разработанный Google, обеспечивает лучшее сжатие для веб-контента, особенно при статической компрессии.
    *   **ZSTD (Zstandard):** Алгоритм, разработанный Facebook, отличается очень высокой скоростью сжатия/распаковки, что делает его привлекательным для динамической компрессии.

*   **Типы компрессии:**
    *   **Статическая компрессия:** Файлы сжимаются заранее (например, во время сборки) и сохраняются рядом с оригиналом (например, `file.css.gz`, `file.js.br`). Веб-сервер просто отдает уже сжатую версию, не тратя CPU на сжатие "на лету". Это идеальный вариант для статических ресурсов.
    *   **Динамическая компрессия:** Контент сжимается веб-сервером "на лету" при каждом запросе. Требует баланса между степенью сжатия и нагрузкой на CPU.

*   **Настройка в Nginx/Angie:**
    *   Включение модулей для Brotli и ZSTD (в Angie это часто проще благодаря готовым пакетам, например, `apt install ngx-module-brotli` и `apt install ngx-module-zstd`).
    *   Конфигурация `gzip`, `brotli`, `zstd` директив с указанием `mime.types` и `compression_level`.
    *   Использование `Accept-Encoding` заголовка для согласования поддерживаемых браузером алгоритмов.

    **Примеры конфигурации:**

    ```nginx
    # Общие настройки Gzip
    gzip on;
    gzip_vary on;
    gzip_proxied any;
    gzip_comp_level 5; # Уровень сжатия от 1 (быстро, меньше сжатие) до 9 (медленно, больше сжатие)
    gzip_buffers 16 8k;
    gzip_http_version 1.1;
    gzip_min_length 1000; # Минимальный размер ответа для сжатия
    gzip_types text/plain text/css application/json application/javascript application/x-javascript text/xml application/xml application/xml+rss text/javascript application/atom+xml image/svg+xml;
    ```

    ```nginx
    # Настройки Brotli (требуется ngx_brotli модуль)
    brotli on;
    brotli_static on; # Включает отдачу предварительно сжатых .br файлов
    brotli_comp_level 5; # Уровень сжатия от 1 до 11
    brotli_buffers 16 8k;
    brotli_min_length 1000;
    brotli_types text/plain text/css application/json application/javascript application/x-javascript text/xml application/xml application/xml+rss text/javascript application/atom+xml image/svg+xml;
    brotli_vary on;
    ```

    ```nginx
    # Настройки ZSTD (требуется ngx_http_zstd_filter_module модуль)
    zstd on;
    zstd_static on; # Включает отдачу предварительно сжатых .zst файлов (менее актуально, чем Brotli static)
    zstd_comp_level 3; # Уровень сжатия от 1 до 22 (рекомендуется 1-5 для динамики)
    zstd_buffers 16 8k;
    zstd_min_length 1000;
    zstd_types text/plain text/css application/json application/javascript application/x-javascript text/xml application/xml application/xml+rss text/javascript application/atom+xml image/svg+xml;
    zstd_vary on;
    ```

    **Сравнение производительности алгоритмов сжатия (на примере большого CSS-файла, динамическое сжатие):**

    | Алгоритм | Уровень сжатия | Размер файла (КБ) | RPS (запросов/сек) | Примечания |
    | :------- | :------------- | :---------------- | :----------------- | :--------- |
    | Gzip     | 1              | 159               | 130                | Медленнее ZSTD, хуже сжатие, чем Brotli |
    | Gzip     | 4              | 135               | 100                | Умеренный баланс, но уступает современным |
    | Gzip     | 9              | 120               | 30                 | Очень медленно, мало выигрыша в размере |
    | ZSTD     | 1              | 140               | 240                | Самый быстрый для динамики, хорошее сжатие |
    | ZSTD     | 3              | 132               | 215                | Отличный баланс скорости и сжатия для динамики |
    | Brotli   | 1              | 172               | 150                | Медленнее ZSTD, но лучше Gzip |
    | Brotli   | 3              | 125               | 125                | Хорошее сжатие, приемлемая скорость |
    | Brotli   | 11             | 94                | 1                  | Максимальное сжатие, очень медленно (только для статики) |

    **Рекомендации:**
    *   Для **статического контента** (CSS, JS, шрифты) используйте **Brotli** с максимальной степенью сжатия (например, `brotli_comp_level 11`) путем предварительного сжатия файлов.
    *   Для **динамического контента** (HTML, JSON API) используйте **ZSTD** на низких уровнях сжатия (например, `zstd_comp_level 3-5`) для оптимального баланса между скоростью и эффективностью. Если ZSTD недоступен, используйте Brotli на умеренных уровнях (`brotli_comp_level 5-6`).
    *   **Gzip** можно использовать как запасной вариант для браузеров, не поддерживающих Brotli или ZSTD, или для контента, который не выигрывает значительно от более продвинутых алгоритмов.

### 3.2. Оптимизация TLS

TLS (Transport Layer Security) является основой безопасного веб-соединения. Его оптимизация направлена на сокращение времени установки соединения, которое может занимать до 2-3 RTT (Round Trip Time) в худшем случае, что в сумме с TCP Handshake (1 RTT) дает до 4 RTT.

*   **Версии TLS:** Использование современных версий (TLS 1.2, TLS 1.3) для повышения безопасности и производительности. TLS 1.3 значительно сокращает количество RTT для установки соединения (до 1 RTT или 0-RTT при возобновлении).
*   **Наборы шифров (Cipher Suites):** Выбор современных и эффективных шифров.
*   **Сертификаты:** Использование ECDSA-сертификатов (эллиптическая криптография) вместо RSA для меньшей нагрузки на сервер. Рекомендуется использовать пары сертификатов RSA и ECDSA для максимальной совместимости и производительности.
*   **Кэширование сессий:**
    *   **Session Tickets:** Механизм на стороне клиента для быстрого возобновления TLS-сессии.
    *   **Session Cache:** Кэширование информации о сессиях на стороне сервера.
*   **HSTS (HTTP Strict Transport Security):** Заголовок, который заставляет браузеры всегда использовать HTTPS для данного домена, предотвращая атаки понижения версии протокола. **Внимание:** HSTS — очень жесткий кэш, его нельзя легко сбросить. Убедитесь в корректности настройки HTTPS перед его включением.

**Примеры конфигурации Nginx/Angie для TLS:**

```nginx
# Общие настройки keep-alive соединений
keepalive_timeout 120s; # Время поддержания соединения
keepalive_requests 10000; # Максимальное количество запросов на одно соединение

# Настройки TLS
ssl_protocols TLSv1.2 TLSv1.3; # Разрешенные версии протоколов
ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384'; # Современные и безопасные шифры
ssl_prefer_server_ciphers on; # Сервер выбирает шифр из предложенных клиентом
ssl_dhparam /etc/nginx/dhparam.pem; # Путь к файлу с параметрами Диффи-Хеллмана (генерируется командой `openssl dhparam -out /etc/nginx/dhparam.pem 2048`)

# Кэширование TLS-сессий
ssl_session_cache shared:SSL:10m; # Общий кэш для сессий (10MB)
ssl_session_timeout 1d; # Время жизни сессии (1 день)
ssl_session_tickets off; # Отключение Session Tickets (может быть рекомендовано по соображениям безопасности)

# HSTS
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
```

**Инструменты для проверки конфигурации TLS:**
*   **Mozilla TLS Configurator:** Позволяет сгенерировать безопасную конфигурацию TLS для различных веб-серверов.
*   **SSL Labs Server Test:** Проводит глубокий анализ TLS-конфигурации сервера и выставляет оценку безопасности.


### 3.3. HTTP/2 и HTTP/3

Эти протоколы значительно улучшают производительность по сравнению с HTTP/1.1.

*   **HTTP/2:**
    *   **Мультиплексирование:** Позволяет отправлять несколько запросов и получать несколько ответов по одному TCP-соединению, устраняя проблему "блокировки начала очереди" (head-of-line blocking). Это значительно сокращает задержки, так как не нужно ждать завершения одного запроса для отправки следующего.
    *   **Бинарный протокол:** Более эффективен, чем текстовый HTTP/1.1, что уменьшает накладные расходы на парсинг.
    *   **Сжатие заголовков (HPACK):** Уменьшает объем передаваемых данных за счет эффективного сжатия HTTP-заголовков.
    *   Требует TLS для большинства реализаций в браузерах.

    **Пример конфигурации Nginx/Angie для HTTP/2:**
    ```nginx
    # Для Nginx 1.25.0+ или современной Angie
    listen 443 ssl http2;
    # Для более старых версий Nginx
    # listen 443 ssl;
    # http2 on;
    ```

*   **HTTP/3:**
    *   **Основан на QUIC:** Использует UDP вместо TCP, что позволяет решить проблемы блокировки начала очереди на транспортном уровне (Head-of-Line Blocking на уровне TCP). Если один пакет теряется, это не блокирует доставку других потоков данных.
    *   **Встроенный TLS:** Шифрование является неотъемлемой частью QUIC, что упрощает и ускоряет установление безопасного соединения.
    *   **Быстрое установление соединения:** QUIC объединяет установку соединения и TLS-рукопожатие, сокращая RTT для установки безопасного соединения (1-RTT или 0-RTT при возобновлении).
    *   Переход на UDP позволяет обновлять протокол на уровне пользовательского пространства, не затрагивая ядро ОС, что ускоряет внедрение новых функций и исправлений.
    *   **"Холодный старт" HTTP/3:** Браузеры не знают заранее, поддерживает ли сервер HTTP/3. Поэтому первый запрос обычно отправляется по HTTP/2 (или HTTP/1.1). Сервер отвечает заголовком `Alt-Svc`, указывая поддержку HTTP/3, после чего последующие запросы могут использовать QUIC.

    **Пример конфигурации Nginx/Angie для HTTP/3:**
    ```nginx
    # Требует Nginx 1.25.0+ или современную Angie с модулем HTTP/3
    listen 443 ssl quic reuseport; # Слушаем UDP порт 443 для QUIC
    listen 443 ssl http2;         # Слушаем TCP порт 443 для HTTP/2 и HTTP/1.1 (для обратной совместимости)

    http3 on; # Включаем HTTP/3
    add_header Alt-Svc 'h3=":443"; ma=86400'; # Указываем клиентам, что сервер поддерживает HTTP/3 (ma=Max-Age в секундах)
    ```

### 3.4. Кэширование

Кэширование позволяет избежать повторных вычислений или передачи данных, значительно ускоряя ответы.

*   **Клиентское кэширование (Browser Caching):**
    *   Браузер сохраняет статические ресурсы (CSS, JS, изображения) на диске или в памяти.
    *   Управляется заголовками `Cache-Control` (например, `max-age`, `public`, `immutable`), `Expires`, `Last-Modified`, `ETag`.
    *   `Cache-Control: immutable` — указывает, что ресурс никогда не изменится, что позволяет браузеру не отправлять запросы на сервер для проверки актуальности.
*   **Серверное кэширование (Server-Side Caching):**
    *   **Nginx Proxy Cache:** Кэширование ответов от бэкенд-серверов на диске веб-сервера.
    *   Позволяет значительно снизить нагрузку на бэкенд и ускорить отдачу контента.
    *   Настраивается с помощью директив `proxy_cache_path`, `proxy_cache`, `proxy_cache_valid`.
    *   Опции `proxy_use_stale` и `proxy_background_update` позволяют отдавать устаревший контент в случае проблем с бэкендом или плавно обновлять кэш.

    **Примеры конфигурации Nginx Proxy Cache:**

    ```nginx
    # Определение зоны кэширования в http-блоке
    # /var/cache/nginx - путь к кэшу
    # levels=1:2 - двухуровневая иерархия каталогов для хранения кэша
    # keys_zone=my_cache:10m - имя зоны (my_cache) и размер в ОЗУ для хранения ключей кэша (10MB)
    # inactive=60m - элементы, не запрашиваемые в течение 60 минут, удаляются
    # max_size=1g - максимальный размер кэша на диске (1GB)
    proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m inactive=60m max_size=1g;
    ```

    ```nginx
    # Использование кэша в server/location блоке
    location / {
        proxy_pass http://my_backend;
        proxy_cache my_cache; # Использование определенной зоны кэширования
        proxy_cache_valid 200 302 1h; # Кэшировать ответы с кодами 200 и 302 на 1 час
        proxy_cache_valid 404 1m;     # Кэшировать ответы с кодом 404 на 1 минуту
        proxy_cache_min_uses 1;       # Кэшировать ответ только после 1 запроса

        # Отдавать устаревший контент из кэша, если бэкенд недоступен или отвечает с ошибкой
        proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
        # Позволяет Nginx отдавать устаревший контент из кэша, пока в фоновом режиме обновляется свежий контент с бэкенда
        proxy_cache_background_update on;
        # Блокировать запросы, пока кэш обновляется (только один запрос идет на бэкенд)
        proxy_cache_lock on;
        proxy_cache_lock_timeout 5s;

        # Добавление заголовка для отладки кэша
        add_header X-Proxy-Cache $upstream_cache_status;
    }
    ```

    **Ограничения:**
    *   Стандартный Nginx не предоставляет встроенных механизмов для точечной инвалидации кэша (удаления отдельных элементов). Для этого требуются сторонние модули (например, `nginx-cache-purge`) или ручное удаление файлов из директории кэша.
    *   При обновлении контента на бэкенде кэш может оставаться устаревшим до истечения `proxy_cache_valid` или ручной очистки.


## 4. Angie: Альтернатива Nginx

Angie — это форк Nginx, разработанный бывшими сотрудниками Nginx, Inc. Он предлагает:
*   Дополнительные фичи, включая расширенный мониторинг и консоль.
*   Улучшенные возможности балансировки нагрузки (некоторые из которых доступны только в платной версии Nginx).
*   Упрощенную установку сторонних модулей (например, Brotli, ZSTD) благодаря готовым бинарным пакетам, что избавляет от необходимости ручной пересборки.
*   Активную поддержку со стороны разработчиков.
