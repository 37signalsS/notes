# Оптимизация производительности веб-приложений: Обзор

## Определения

**Производительность веб-приложений (Web Performance)** — комплексная дисциплина, направленная на минимизацию времени доставки ресурсов, ускорение рендеринга и обеспечение мгновенной реакции на действия пользователя. В 2026 году производительность рассматривается не только как технический параметр, но и как критический фактор бизнес-успеха и экологической устойчивости (Carbon Intensity).

**Core Web Vitals** — стандартизированные метрики Google для оценки качества пользовательского опыта:
*   **LCP (Largest Contentful Paint):** Скорость загрузки основного контента.
*   **INP (Interaction to Next Paint):** Отзывчивость интерфейса (заменила FID).
*   **CLS (Cumulative Layout Shift):** Визуальная стабильность.
*   *Подробнее:* [web_vitals.md](./web_vitals.md).

## Основные концепции

### Клиентская производительность

Сфокусирована на том, как браузер обрабатывает полученные данные и управляет ресурсами устройства пользователя.

| Компонент | Описание |
| :--- | :--- |
| **Критический путь рендеринга (CRP)** | Построение DOM → Построение CSSOM → Render Tree → Layout → Paint. Оптимизация CRP минимизирует время до первой отрисовки (FCP). |
| **Исполнение JavaScript** | Основной потребитель ресурсов CPU. В 2026 году акцент смещен на минимизацию Long Tasks (>50ms) и использование Off-main-thread вычислений через Web Workers. |
| **Приоритизация ресурсов** | Управление очередью загрузки через `fetchpriority` (Resource Hints) и `loading="lazy"` (Native Lazy Loading). |

**Современные методы оптимизации (2026):**
*   **Speculation Rules API:** Пришел на смену классическому `prefetch`. Позволяет декларативно описывать условия для фонового рендеринга (Prerender) страниц, на которые пользователь с большой вероятностью перейдет.
*   **Priority Hints:** Использование `fetchpriority="high"` для LCP-изображений (например, LCP-картинка в первом экране), чтобы браузер начал их загрузку раньше других ресурсов.
*   **Partytown / Workerize:** Технологии выноса тяжелых сторонних скриптов (GTM, аналитика, чаты) в Web Workers, чтобы освободить основной поток (Main Thread) для взаимодействия с пользователем.

### Серверная производительность

Эффективность генерации и доставки ответа сервером (Nginx, Angie, Бэкенд-приложения).

*   **Протоколы:** Повсеместное использование **HTTP/3 (QUIC)** для устранения блокировок очереди (HOL Blocking) на уровне транспорта и **TLS 1.3** для минимизации задержек на хендшейк (1-RTT/0-RTT).
*   **Сжатие:** Стандартное использование **Zstandard (ZSTD)** для динамического контента и **Brotli** для статики. ZSTD обеспечивает высокую скорость сжатия при коэффициентах, близких к Brotli, что снижает нагрузку на CPU сервера.
*   **Кэширование:** Применение стратегий `stale-while-revalidate` (SWR) для мгновенной отдачи контента с фоновым обновлением. Подробнее — [caching.md](./caching.md).
*   **Оптимизация TLS:** Использование OCSP Stapling, сессионных тикетов и алгоритмов на эллиптических кривых для ускорения установки защищенного соединения. См. [tls_optimization.md](./tls_optimization.md).

### Сетевая производительность

Минимизация влияния физических ограничений среды передачи данных и топологии сети.

*   **Latency (RTT):** Главный ограничитель скорости. Решается через **CDN (Content Delivery Network)** и перемещение логики на Edge (Edge Computing), что сокращает физическое расстояние до пользователя.
*   **Early Hints (103):** Позволяет серверу отправить заголовки `Link` с критическими ресурсами (CSS, шрифты) до того, как основной HTML будет полностью сгенерирован. Браузер начинает загрузку этих ресурсов параллельно работе бэкенда.
*   **Оптимизация размера (Payload):** Использование современных форматов изображений (AVIF, WebP v2) и видео (AV1). Минификация и «встряхивание дерева» (Tree Shaking) для JS/CSS бандлов.

## Практические сценарии

### Методология анализа

1.  **Сбор полевых данных (RUM — Real User Monitoring):** Анализ реального опыта пользователей (Field Data) через Chrome User Experience Report (CrUX) или собственные системы телеметрии. Отражает влияние реальных устройств и сетевых условий.
2.  **Лабораторное тестирование (Lab Data):** Диагностика в контролируемой среде с эмуляцией устройств и троттлингом сети. Инструменты: [Chrome DevTools](./chrome_devtools.md) и [WebPageTest](./webpagetest.md).
3.  **Автоматизированный аудит:** Интеграция Lighthouse CI в CI/CD для предотвращения регрессий производительности при каждом коммите.

### Стратегия приоритизации (Impact vs Effort)

| Проблема | Метрика | Приоритет | Решение |
| :--- | :--- | :--- | :--- |
| Медленный TTFB | LCP, FCP | **Критический** | CDN, серверное кэширование, оптимизация запросов к БД. |
| Блокирующий JS | INP, TBT | **Высокий** | Code splitting, `async/defer`, вынос в Web Workers (Partytown). |
| Нестабильная верстка | CLS | **Высокий** | Явные размеры для медиа (aspect-ratio), `font-display: swap`. |
| Большой вес страницы | LCP, TTFB | **Средний** | Адаптивные изображения, Brotli/ZSTD сжатие, удаление неиспользуемого кода. |

### Устойчивая производительность (Eco-performance)

В 2026 году оптимизация производительности напрямую связана с экологией. Быстрый код потребляет меньше циклов CPU, что снижает энергопотребление дата-центров и устройств пользователей. Цель DevOps-инженера — минимизировать «цифровой углеродный след» за счет исключения избыточных вычислений и неэффективной передачи данных.

```
Пользователь ←→ Edge (CDN) ←→ Фронтенд (Nginx) ←→ Бэкенд
     ↑              ↑                ↑               ↑
 Рендеринг      Кэширование      Сжатие/TLS      Логика/БД
 (INP, CLS)     (Latency)       (TTFB, FCP)      (Processing)
```
