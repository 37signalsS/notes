# Zero-Downtime Deployment и Graceful Reload для веб-производительности

**Актуально для:** Nginx 1.26.x / Angie 1.12.x / HAProxy 3.0.x / Linux Kernel 5.10+ / 6.x

## Определения

- **Zero-Downtime Deployment (Развертывание без простоя)** — архитектурный и эксплуатационный процесс обновления исполняемого кода, схем баз данных или конфигураций инфраструктуры без прерывания обслуживания пользователей, без роста числа сетевых ошибок (5xx, TCP RST) и без деградации времени отклика (TTFB).
- **Graceful Reload (Плавная перезагрузка)** — процедура применения новой конфигурации сервиса без разрыва установленных клиентских соединений: master-процесс проверяет синтаксис, открывает новые слушающие сокеты, запускает воркеры нового поколения и инициирует плавное завершение воркеров старого поколения.
- **Graceful Shutdown (Плавная остановка)** — процесс контролируемого вывода процесса или узла из эксплуатации: процесс прекращает прием новых входящих запросов (`listen`-сокеты закрываются для новых `accept`), но продолжает обслуживать уже принятые сетевые транзакции в пределах отведенного тайм-аута.
- **Binary Upgrade (Горячее обновление бинарного файла)** — замена исполняемого файла демона (Nginx, Angie, HAProxy) на диске и запуск нового master-процесса на лету с передачей файловых дескрипторов слушающих сокетов от старого мастера без потери входящего трафика.
- **Connection Draining (Graceful Drain / Слив трафика)** — перевод узла upstream на уровне балансировщика нагрузки (L7 Reverse Proxy) в состояние, при котором на него перестают направляться новые пользовательские сессии, но дается время на корректное завершение активных транзакций.
- **Worker Shutdown Timeout (`worker_shutdown_timeout`)** — директива веб-сервера, жестко ограничивающая максимальное время ожидания завершения старых рабочих процессов при Graceful Shutdown/Reload. Защищает систему от вечно зависших воркеров с утечками ресурсов.
- **SO_REUSEPORT** — опция сокета в ядре Linux (начиная с 3.9), позволяющая нескольким независимым процессам или потокам выполнять `bind()` на один и тот же IP и порт с распределением входящих SYN-пакетов средствами ядра.
- **Kernel Accept Queue (Очередь входящих соединений ядра)** — внутренняя системная очередь TCP-соединений, завершивших трехстороннее рукопожатие (SYN-ACK-ACK), ожидающих вызова системного вызова `accept()` приложением. Размер регулируется системным параметром `net.core.somaxconn` и параметром `backlog` функции `listen()`.
- **Socket Passing (Передача файловых дескрипторов)** — механизм операционной системы (через Unix Domain Sockets и управляющее сообщение `SCM_RIGHTS`), позволяющий передать открытый слушающий файловый дескриптор сокета от одного процесса другому.
- **Systemd Socket Activation** — механизм инициализации сокетов демоном systemd: systemd открывает сетевой порт, держит сокет в ядре и передает его файловый дескриптор запускаемому сервису через переменную окружения `LISTEN_FDS`.
- **Blue-Green Deployment (Сине-зеленое развертывание)** — стратегия развертывания с разделением инфраструктуры на два идентичных продуктивных контура: активный (**Blue**), обслуживающий весь реальный трафик, и пассивный (**Green**), принимающий релиз. После прогрева и проверок сетевой слой мгновенно переключает трафик.
- **Canary Rollout (Канареечный релиз)** — техника постепенного развертывания, при которой новая версия приложения получает небольшую фиксированную долю реального трафика (1-5%), контролируемую по метрикам ошибок и задержек, перед полным раскатом на все серверы.
- **Rolling Update (Последовательное обновление)** — поочередное обновление экземпляров сервиса в пуле балансировки (Drain → Обновление → Прогрев → Ввод в строй) с сохранением минимальной необходимой суммарной емкости кластера.
- **Expand-and-Contract Pattern (Паттерн расширения и сжатия)** — шаблон параллельного изменения схемы базы данных и логики приложений, гарантирующий одновременную обратную совместимость версий $N$ и $N+1$ приложения с базой данных во время деплоя.
- **Pre-warming (Тепловой прогрев)** — процесс искусственной инициализации внутренних ресурсов сервиса (пулы соединений с БД, кэши в оперативной памяти, JIT-компиляция, прогрев дискового кэша Nginx) до открытия входящего пользовательского трафика.
- **TCP RST (TCP Reset)** — пакет аварийного сброса TCP-соединения со стороны ОС или сервера, приводящий к мгновенному падению пользовательского запроса без получения HTTP-ответа (браузер отображает ошибку `ERR_CONNECTION_RESET`).
- **HTTP/2 GOAWAY Frame** — служебный фрейм протокола HTTP/2, информирующий клиента о завершении работы соединения и запрещающий открытие новых потоков (streams), позволяя завершить все обрабатываемые запросы.
- **eBPF Socket Dispatching (`quic_bpf`)** — механизм ядра Linux для маршрутизации UDP-датаграмм протокола HTTP/3 (QUIC) по идентификаторам Connection ID (CID) на конкретные worker-процессы при перезагрузке веб-сервера.

## Основные концепции и архитектура

### 1. Сетевой стек Linux и уровень сокетов ядра

Для реализации истинного Zero-Downtime критично понимать поведение ядра Linux при работе с сетевыми очередями.

```
                  [ Клиентские TCP SYN ]
                            │
                            ▼
              ┌───────────────────────────┐
              │ SYN Queue (Half-open)     │ ◄── net.ipv4.tcp_max_syn_backlog
              └─────────────┬─────────────┘
                            │ (3-Way Handshake: SYN-ACK / ACK)
                            ▼
              ┌───────────────────────────┐
              │ Accept Queue (ESTABLISHED)│ ◄── net.core.somaxconn & listen(backlog)
              └─────────────┬─────────────┘
                            │ sys_accept()
                            ▼
                 [ Worker-процесс веб-сервера ]
```

#### Механика очередей сокетов: SYN Queue и Accept Queue
1. **SYN Queue (Очередь полуоткрытых соединений):** фиксирует входящие пакеты `SYN`. Размер лимитируется `net.ipv4.tcp_max_syn_backlog`. Если очередь переполнена, ядро отбрасывает SYN-пакеты (или переходит на TCP SYN Cookies).
2. **Accept Queue (Очередь готовых соединений):** соединения, завершившие 3-way handshake (`ESTABLISHED`), ожидают, пока приложение вызовет системный вызов `accept()` или `accept4()`. Размер очереди определяется как:
   $$\text{Queue Size} = \min(\text{backlog in listen()}, \text{net.core.somaxconn})$$
3. **Поведение при закрытии сокета:** когда старый процесс завершает работу и закрывает listening сокет через `close()`, любые соединения, оставшиеся в Accept Queue и не принятые приложением, сбрасываются ядром с отправкой клиенту пакета **TCP RST**. Чтобы избежать этого, процесс должен прекратить прием новых соединений, но обработать все накопившиеся соединения из Accept Queue перед вызовом `close()`.

#### Особенности и ловушки `SO_REUSEPORT` в Linux
Опция `SO_REUSEPORT` позволяет нескольким процессам слушать один порт, при этом ядро выполняет балансировку входящих SYN-пакетов по хэшу 4-tuple (IP источника/назначения, порт источника/назначения).
- **Архитектурный риск при Reload:** когда один из процессов с сокетом `SO_REUSEPORT` завершается (например, старый воркер при деплое), ядро удаляет его сокет из группы. Однако в очереди этого сокета уже могут находиться соединения, завершившие handshake! При закрытии дескриптора эти клиенты мгновенно получают **TCP RST**.
- **Инженерное решение:**
  1. В Nginx/Angie сокеты открываются master-процессом один раз и наследуются воркерами через `fork()`. Слушающий сокет не закрывается в ядре во время reload — меняются только воркеры, читающие из общей очереди.
  2. Использование eBPF-программ (`BPF_PROG_TYPE_SK_REUSEPORT`), которые динамически перенаправляют соединения с закрывающегося сокета на активные сокеты новых процессов.

#### Socket Passing и Systemd Socket Activation
Для изоляции жизненного цикла сетевого порта от жизненного цикла приложения применяется системная передача дескрипторов:
- **Systemd Socket Activation:** юнит `app.socket` открывает порт при старте ОС и держит его в ядре. При старте `app.service` systemd передает дескриптор сокета (дескриптор 3) через переменные `LISTEN_FDS=1` и `LISTEN_PID`. При перезапуске приложения (`systemctl restart app.service`) порт остается открытым в systemd, входящие клиенты буферизуются в Accept Queue ядра без отказов, а новое приложение мгновенно забирает их после старта.
- **Socket Passing (SCM_RIGHTS):** передача дескриптора через вспомогательное сообщение `sendmsg()` по Unix Domain сокету от старого процесса к новому (паттерн, используемый HAProxy и специализированными менеджерами процессов вроде `tableflip` или `endless`).

### 2. Архитектура процессов веб-сервера и системные сигналы

Веб-серверы промышленного уровня (Nginx, Angie) используют многопроцессную модель Master/Worker, гарантирующую бесшовную перезагрузку.

```
                           [ Master Process (PID 1201, root) ]
                                  │ (Контроль поколений)
            ┌─────────────────────┴─────────────────────┐
            ▼                                           ▼
   [ Поколение 1 (Старое) ]                    [ Поколение 2 (Новое) ]
   ├── Worker #1 (дообслуживание)              ├── Worker #3 (accepting)
   └── Worker #2 (дообслуживание)              └── Worker #4 (accepting)
```

#### Матрица сигналов POSIX для управления жизненным циклом

| Сигнал | Назначение в Nginx/Angie | Поведение подсистемы |
| :--- | :--- | :--- |
| `SIGHUP` | Graceful Reload | Master перечитывает конфигурацию, запускает воркеры поколения $N+1$, шлет `SIGQUIT` воркерам поколения $N$. |
| `SIGQUIT` | Graceful Shutdown | Процесс закрывает listening-сокеты, обслуживает текущие запросы и корректно завершается. |
| `SIGUSR2` | Live Binary Upgrade | Master запускает новый бинарный файл веб-сервера с новым PID, передавая listening-сокеты по наследству. |
| `SIGWINCH` | Graceful Stop Workers | Отправляется старому master-процессу при бинарном обновлении для мягкого останова его воркеров. |
| `SIGTERM` / `SIGINT` | Fast Shutdown | Немедленное принудительное завершение всех процессов с разрывом открытых сетевых соединений. |
| `SIGUSR1` | Reopen Log Files | Переоткрытие файлов логов без остановки воркеров (для logrotate). |

#### Жизненный цикл смены поколений (Generation Shift)
1. Администратор или скрипт деплоя отправляет сигнал `SIGHUP` главному процессу (`systemctl reload nginx`).
2. Master проверяет синтаксис файлов конфигурации (`nginx -t`). Если найдены ошибки, reload отклоняется, старые воркеры продолжают работу без простоя.
3. Master создает новые зоны разделяемой памяти (shm zones) и открывает новые порты, если они появились в конфигурации.
4. Master порождает воркеры нового поколения (Generation инкрементируется: $1 \to 2$). Новые воркеры начинают вызывать `accept()` на слушающих сокетах.
5. Master отправляет воркерам старого поколения сигнал `SIGQUIT`.
6. Старые воркеры выходят из цикла обработки событий прослушивания сокетов (удаляют listening fd из `epoll`), но сохраняют сокеты активных клиентов.
7. По мере завершения обработки активных запросов старые воркеры закрывают клиентские сокеты и завершают процесс.

#### Роль `worker_shutdown_timeout`
- **Проблема вечных воркеров:** по умолчанию в Nginx директива `worker_shutdown_timeout` равна `0` (время ожидания бесконечно). Если клиент держит открытый WebSocket, поток gRPC, Server-Sent Events (SSE) или подвисшее HTTP keepalive соединение, старый воркер останется в памяти навсегда. При частых деплоях это вызывает исчерпание RAM и дескрипторов.
- **Рекомендация:** жестко задавать `worker_shutdown_timeout 15s;` (или `30s`–`60s` для систем с длинными стримами). По истечении таймаута master отправляет зависшим воркерам сигнал `SIGKILL`.

### 3. L7 Reverse Proxy и Connection Draining на upstream

Когда веб-сервер выступает в роли обратного прокси к пулу серверов приложений (Node.js, Go, Python, PHP-FPM), простой рестарт бэкенда приводит к тому, что прокси пытается отправить запрос в закрытый сокет, генерируя ошибки **502 Bad Gateway**.

```
                   [ Клиентский запрос ]
                             │
                             ▼
                  [ L7 Reverse Proxy / LB ]
                 (Nginx / Angie / HAProxy)
                   │                     │
      (Активный трафик)                  │ (Состояние DRAIN)
                   ▼                     ▼
             [ Backend #1 ]        [ Backend #2 ]
             Status: READY         Status: DRAINING
             - Принимает новые     - Новые запросы НЕ идут
             - Обрабатывает active - Дообслуживает активные
                                   - Готовится к рестарту
```

#### Механизм Connection Draining (Graceful Drain)
1. **Фаза 1: Перевод в Drain.** Балансировщик прекращает распределять новые TCP/HTTP-сессии на обновляемый узел.
2. **Фаза 2: Ожидание опустошения очереди (Drain Window).** Балансировщик и автоматизация отслеживают количество активных соединений (`scur` в HAProxy, активные сокеты в метриках).
3. **Фаза 3: Обновление и локальный старт.** После падения активных сессий до 0 сервис безопасно останавливается, обновляется и запускается.
4. **Фаза 4: Health Check Gate и Warm-up.** Балансировщик выполняет активные проверки состояния (`/healthz`). При получении статуса `200 OK` и завершении прогрева узел возвращается в боевой пул.

#### Поведение Keepalive соединений к Upstream (TCP Race Condition)
Nginx поддерживает пул постоянных TCP-соединений к бэкендам (`keepalive 32;` внутри блока `upstream`).
- **Гонка пакетов (Race Condition):** бэкенд начинает завершаться и отправляет пакет `FIN`. Одновременно Nginx выбирает это же idle-соединение из пула и отправляет в него новый HTTP-запрос клиента. Запрос сталкивается с `FIN` или `RST`, вызывая ошибку передачи.
- **Защита через `proxy_next_upstream`:** Nginx обязан иметь директиву:
  ```nginx
  proxy_next_upstream error timeout invalid_header http_502 http_503;
  proxy_next_upstream_tries 3;
  ```
  При столкновении со сброшенным соединением Nginx прозрачно для клиента повторяет идемпотентный запрос на следующий узел в пуле upstream, предотвращая появление 502 у клиента.

### 4. Особенности протоколов: HTTP/1.1, HTTP/2 и HTTP/3 (QUIC)

Различные версии HTTP требуют индивидуальной обработки на фазе завершения воркера:

1. **HTTP/1.1:**
   - Сервер обязан выставить в ответе заголовок `Connection: close`, сигнализируя браузеру о необходимости разорвать TCP-соединение и открыть новое для следующих ресурсов.
2. **HTTP/2 (Мультиплексирование потоков):**
   - В рамках одного TCP-соединения передаются десятки параллельных запросов (streams). Принудительный разрыв TCP уничтожит все активные транзакции.
   - **Двухэтапный GOAWAY:** веб-сервер отправляет клиенту первый фрейм `GOAWAY` с идентификатором стрима $2^{31}-1$. Это сообщает клиенту, что сервер скоро закроется, и запрещает создавать новые потоки. После выдержки одного RTT сервер шлет финальный `GOAWAY` с точным номером последнего обработанного стрима (`last_stream_id`) и спокойно дожидается завершения открытых потоков.
3. **HTTP/3 и QUIC (UDP и eBPF):**
   - QUIC работает поверх UDP и идентифицирует соединения через Connection ID (CID), а не по 4-tuple IP/Port.
   - При reload воркер закрывает слушающий UDP-сокет. Входящие UDP-датаграммы существующих сессий придут на порт, где слушает уже новый воркер. Без специальной диспетчеризации новый воркер не узнает чужой CID и сбросит сессию пакетом `Stateless Reset`.
   - **Решение:** ядро Linux 5.7+ с модулем eBPF и директива `quic_bpf on;` в Nginx/Angie. eBPF-программа перехватывает входящие UDP-пакеты в ядре и направляет их по таблице CID именно в тот воркер (старый или новый), которому принадлежит соединение.

### 5. Архитектурные стратегии развертывания (On-premise / Bare-metal)

В корпоративных средах без облачных оркестраторов используются четыре классических паттерна:

```
1. Blue-Green:
   [ L7 LB / Floating VIP ] ──► [ Green (Active 100%) ]
                            └──  [ Blue (Standby / Deploying) ]

2. Rolling Update:
   Node 1 (Drain -> Update) ──► Node 2 (Serving) ──► Node 3 (Serving)

3. Canary (Statistical / Header):
   [ L7 LB ] ──┬── 95% ──► [ Stable Upstream ]
               └──  5%  ──► [ Canary Upstream ]

4. Symlink Switch (Single-node):
   /srv/app/current ──► symlink ──► /srv/app/releases/v2 (Atomic mv -Tf)
```

#### Сравнение стратегий в On-premise окружении

| Стратегия | Избыточность ресурсов | Скорость отката | Риск для пользователей (Blast Radius) | Основной инструмент управления |
| :--- | :--- | :--- | :--- | :--- |
| **Blue-Green** | Требуется 2x емкость | Мгновенно (<1 сек) | 100% при ошибке переключения | HAProxy Runtime API, Nginx Upstream, Keepalived VIP |
| **Rolling Update** | Требуется запас $\ge 1$ узла | Медленно (пошаговый реверс) | $\frac{1}{N}$ от общего пула | Ansible, Bash, HAProxy Socket Drain |
| **Canary** | Минимальная (+5-10%) | Быстро (отключение канарейки) | 1-5% пользователей | Nginx `split_clients`, cookie/header routing |
| **Symlink Switch** | На одном хосте (1x) | Мгновенно (возврат symlink) | 100% на данном хосте | POSIX `ln -sfn`, `mv -Tf`, `systemctl reload` |

### 6. Базы данных: паттерн Expand-and-Contract для Zero-Downtime

Наиболее частая причина простоев при деплое — деструктивные или блокирующие миграции реляционных СУБД (PostgreSQL / MariaDB). Если новая версия кода требует новой структуры таблицы, а старая версия еще работает, остановка неизбежна, если не соблюдать паттерн **Expand-and-Contract (Параллельное сосуществование)**.

#### Фазы жизненного цикла миграции
1. **Фаза 1: Расширение (Expand):**
   - Добавляются новые колонки или таблицы без изменения старых.
   - Колонки создаются как `NULLABLE` либо с безопасными константными значениями по умолчанию.
   - Приложение версии $N$ продолжает читать и писать старые колонки.
2. **Фаза 2: Двойная запись и миграция данных (Dual Run & Backfill):**
   - Развертывается приложение версии $N+1$, которое умеет писать данные одновременно в старую и новую колонки, а читать из новой (с фоллбэком на старую).
   - Фоновым процессом (пачками / batches) запускается утилита backfilling для переноса исторических данных из старых полей в новые без удержания транзакционных локов.
3. **Фаза 3: Сжатие (Contract):**
   - После успешного переключения и валидации выпускается миграция, удаляющая старые неиспользуемые колонки, триггеры или временные индексы.

#### Блокировки DDL в PostgreSQL и защита от отказа в обслуживании
В PostgreSQL операции изменения структуры (`ALTER TABLE`) требуют эксклюзивной блокировки таблицы `ACCESS EXCLUSIVE`.
- **Ловушка очереди блокировок (Lock Queue Starvation):** запрос `ALTER TABLE` встает в очередь ожидания за длинным `SELECT`. Все последующие даже быстрые `SELECT` встают в очередь *за* запросом `ALTER TABLE`. За секунды пул соединений приложения исчерпывается, вызывая полный отказ сервиса.
- **Инженерные правила безаварийного DDL:**
  1. Жесткий лимит ожидания блокировки в сессии миграции:
     ```sql
     SET lock_timeout = '2s';
     SET statement_timeout = '10s';
     ```
  2. Создание индексов исключительно в конкурентном режиме:
     ```sql
     CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
     ```
  3. В PostgreSQL 11+ добавление колонки с константным дефолтом (`DEFAULT 'active'`) происходит мгновенно на уровне метаданных каталога без перезаписи строк таблицы на диске.

### 7. Влияние на веб-производительность и Core Web Vitals

Деплой без простоя обязан предотвращать деградацию пользовательских метрик производительности:

| Метрика | Причина деградации при деплое | Эксплуатационное решение |
| :--- | :--- | :--- |
| **TTFB (Time to First Byte)** | Холодный старт воркеров (неинициализированные пулы БД, JIT-компиляция, пустой системный page cache). | Warm-up скрипты перед переводом трафика; `keepalive` к бэкендам; предварительный прогрев пулов соединений. |
| **Ошибки 5xx / Отказы** | Разрыв соединений при остановке старых воркеров или неотловленные ошибки 502 от перезапускаемых бэкендов. | Адекватный `worker_shutdown_timeout` (15-30s); настройка `proxy_next_upstream`; постепенный connection drain. |
| **LCP (Largest Contentful Paint)** | Очистка дискового кэша Nginx/Angie при деплое статики приводит к росту времени отдачи ключевого контента. | Использование директивы `proxy_cache_path ... file=` (Angie) для сохранения индекса кэша на диске между рестартами. |
| **INP (Interaction to Next Paint)** | Обрыв фоновых AJAX-запросов и долгих WebSocket/SSE сессий, вызывающий зависание UI-интерфейсов. | Корректная обработка `GOAWAY` в HTTP/2, плавная деградация сессий в WebSocket с переподключением клиента с backoff. |

### Сценарий 1: Graceful reload Nginx/Angie без потери пакетов под нагрузкой

**Контекст:** веб-сервер обслуживает непрерывный трафик 5000+ RPS. Требуется применить изменения конфигурации с нулевым процентом сетевых сбоев.

#### Шаг 1. Предварительная валидация синтаксиса
Перед отправкой любого сигнала процессу обязательна проверка конфигурационных файлов:
```bash
sudo nginx -t
# → nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
# → nginx: configuration file /etc/nginx/nginx.conf test is successful
```

#### Шаг 2. Безопасная перезагрузка через systemd или сигналы
```bash
# Рекомендуемый способ через systemd (посылает SIGHUP основному процессу)
sudo systemctl reload nginx

# Альтернативный прямой вызов сигнала через PID-файл
sudo kill -HUP $(cat /run/nginx.pid)
```

Для доказательства нулевого простоя запускается генератор нагрузки `hey` или `wrk` на 30 секунд, во время которого выполняется reload:

```bash
# В терминале 1: запуск генератора нагрузки

# →   [200] 30000 responses
# → Error distribution: (отсутствует — 0 ошибок)
```

#### Шаг 4. Проверка поколений воркеров
В Angie статус поколений доступен через Status API:

```bash
curl -s http://127.0.0.1:8888/api/status/angie/ | jq '{generation: .generation, load_timestamp: .load_timestamp}'
# → {
# →   "generation": 3,
# →   "load_timestamp": "2026-10-14T17:45:00Z"
# → }
```

### Сценарий 2: Live Binary Upgrade веб-сервера без простоя

**Контекст:** обновление исполняемого файла Nginx/Angie (например, при выходе security-патча) без остановки службы.

#### Шаг 1. Обновление пакета или замена бинарника на диске
```bash
# Обновление пакета в системе
sudo apt-get update && sudo apt-get --only-upgrade install nginx -y
# → Setting up nginx (1.26.2-1~bookworm) ...
```

#### Шаг 2. Запуск нового master-процесса (сигнал USR2)
Сигнал `USR2` заставляет старый master переименовать свой PID-файл в `/run/nginx.pid.oldbin` и запустить новый бинарник, передав ему сокеты.
```bash
sudo kill -USR2 $(cat /run/nginx.pid)
sleep 2

# Проверка наличия двух master-процессов
ps -eo pid,ppid,cmd | grep "nginx: master"
# →  1205     1 nginx: master process /usr/sbin/nginx -g daemon on;
# →  8940  1205 nginx: master process /usr/sbin/nginx -g daemon on;
```

#### Шаг 3. Мягкая остановка воркеров старого мастера (сигнал WINCH)
Старый master остается активным, но его воркеры мягко останавливаются.
```bash
sudo kill -WINCH $(cat /run/nginx.pid.oldbin)
sleep 2

# Проверка: старые воркеры исчезли, работают только воркеры нового мастера
ps -eo pid,ppid,cmd | grep "nginx: worker"
# →  8941  8940 nginx: worker process
# →  8942  8940 nginx: worker process
```

#### Шаг 4. Валидация работоспособности нового сервиса
```bash
curl -s -o /dev/null -w "%{http_code}\n" https://example.com/
# → 200
```

#### Шаг 5. Финализация обновления (сигнал QUIT старому мастеру)
Если новый бинарник работает стабильно, старый master завершается:
```bash
sudo kill -QUIT $(cat /run/nginx.pid.oldbin)
```

#### Аварийный откат (Rollback):
Если на шаге 4 обнаружены сбои:
```bash
# 1. Возврат воркеров старого мастера
sudo kill -HUP $(cat /run/nginx.pid.oldbin)

# 2. Немедленная остановка нового мастера
sudo kill -TERM $(cat /run/nginx.pid)
# → Система возвращается в исходное состояние на старом бинарнике
```

### Сценарий 3: Zero-downtime rolling update бэкендов через HAProxy Runtime API

**Контекст:** пул из трех бэкендов Node.js/Go за HAProxy на одном или нескольких хостах. Требуется обновить сервис `app01` без 502 ошибок.

#### Конфигурация сокета управления HAProxy (`/etc/haproxy/haproxy.cfg`)
```haproxy
global
    stats socket /run/haproxy/admin.sock mode 660 level admin expose-fd listeners

backend be_api
    balance roundrobin
    option httpchk GET /healthz
    default-server check inter 2s fall 3 rise 2
    server app01 127.0.0.1:8001 check
    server app02 127.0.0.1:8002 check
    server app03 127.0.0.1:8003 check
```

#### Скрипт безопасной ротации узла (Bash)
```bash
#!/usr/bin/env bash
set -euo pipefail

SOCKET="/run/haproxy/admin.sock"
BACKEND="be_api"
SERVER="app01"
SYSTEMD_UNIT="app@8001.service"

echo "=== [1/5] Перевод ${SERVER} в режим DRAIN ==="
echo "set server ${BACKEND}/${SERVER} state drain" | sudo socat stdio "${SOCKET}"
# → Empty output on success

echo "=== [2/5] Ожидание завершения активных соединений (Connection Draining) ==="
while true; do
    # Извлечение scur (текущие активные сессии)
    ACTIVE_CONNS=$(echo "show stat" | sudo socat stdio "${SOCKET}" | awk -F',' -v b="$BACKEND" -v s="$SERVER" '$1==b && $2==s {print $5}')
    echo "Активных сессий на ${SERVER}: ${ACTIVE_CONNS}"
    if [ "${ACTIVE_CONNS}" -le 0 ]; then
        break
    fi
    sleep 1
done

echo "=== [3/5] Перезапуск сервиса приложения ==="
sudo systemctl restart "${SYSTEMD_UNIT}"

echo "=== [4/5] Smoke-тестирование локального порта ==="
curl --fail --silent --show-error http://127.0.0.1:8001/healthz > /dev/null
# → 200 OK

echo "=== [5/5] Возврат ${SERVER} в продуктивную ротацию ==="
echo "set server ${BACKEND}/${SERVER} state ready" | sudo socat stdio "${SOCKET}"
echo "Сервер ${SERVER} успешно обновлен и введен в строй."
```

### Сценарий 4: Blue-Green переключение трафика на уровне Nginx/Angie

**Контекст:** развернуты два независимых изолированных кластера приложений: Blue (порт 9001) и Green (порт 9002). Требуется переключить трафик без сброса сессий.

#### Конфигурация Nginx с разделяемым upstream файлом (`/etc/nginx/conf.d/upstream.conf`)
```nginx
# Текущий активный upstream (управляется симлинком или перезаписью)
upstream backend_production {
    server 127.0.0.1:9001 max_fails=2 fail_timeout=10s; # Blue
    # server 127.0.0.1:9002 max_fails=2 fail_timeout=10s; # Green (standby)
    keepalive 32;
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    location / {
        proxy_pass http://backend_production;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_next_upstream error timeout invalid_header http_502 http_503;
        proxy_connect_timeout 2s;
        proxy_read_timeout 30s;
    }
}
```

#### Bash-скрипт атомарного переключения Cutover
```bash
#!/usr/bin/env bash
set -euo pipefail

TARGET_PORT="9002" # Переключаем на Green

echo "[1] Валидация готовности Green-окружения..."
HTTP_STATUS=$(curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:${TARGET_PORT}/healthz)
if [ "${HTTP_STATUS}" != "200" ]; then
    echo "ОШИБКА: Green-окружение вернуло статус ${HTTP_STATUS}, переключение отменено!"
    exit 1
fi

echo "[2] Прогрев кэшей и пулов Green (Warm-up)..."
for i in {1..20}; do
    curl -s http://127.0.0.1:${TARGET_PORT}/api/warmup > /dev/null
done

echo "[3] Атомарная генерация конфигурации upstream..."
cat <<EOF | sudo tee /etc/nginx/conf.d/upstream.conf.new > /dev/null
upstream backend_production {
    server 127.0.0.1:${TARGET_PORT} max_fails=2 fail_timeout=10s;
    keepalive 32;
}
EOF

sudo mv -f /etc/nginx/conf.d/upstream.conf.new /etc/nginx/conf.d/upstream.conf

echo "[4] Проверка синтаксиса и Graceful Reload Nginx..."
sudo nginx -t
sudo systemctl reload nginx

echo "Переключение на порт ${TARGET_PORT} выполнено без простоя."
```

### Сценарий 5: Атомарный деплой через Symlink и systemd

**Контекст:** развертывание монолитных сервисов (Go, Node.js, Python, PHP) на выделенном сервере без внешнего балансировщика с мгновенным переключением версий.

#### Структура директорий
```
/srv/app/
├── releases/
│   ├── 20261014-120000/
│   └── 20261014-130000/
└── current -> /srv/app/releases/20261014-130000/
```

#### Скрипт атомарного переключения симлинка
Обычный `ln -sfn` не является полностью атомарным в некоторых версиях Linux (существует окно в несколько микросекунд, когда симлинк удален). Для 100% атомарности используется связка `ln` во временный файл и системный вызов `rename()` через `mv -Tf`:
```bash
#!/usr/bin/env bash
set -euo pipefail

RELEASE_DIR="/srv/app/releases/$(date +%Y%m%d-%H%M%S)"
CURRENT_LINK="/srv/app/current"
TMP_LINK="/srv/app/current_tmp_$$"

mkdir -p "${RELEASE_DIR}"
tar -xzf /tmp/artifact.tar.gz -C "${RELEASE_DIR}"

# Атомарная замена ссылки
ln -sfn "${RELEASE_DIR}" "${TMP_LINK}"
mv -Tf "${TMP_LINK}" "${CURRENT_LINK}"

# Перезагрузка сервиса (Graceful reload процесса)
sudo systemctl reload app.service
# → systemd посылает SIGHUP основному процессу, который переоткрывает файлы
```

### Сценарий 6: Прогрев кэша (Cache Warming) и сохранение кэша в Angie

**Контекст:** после перезагрузки сервиса или инвалидации кэшей пустой кэш вызывает всплеск нагрузки на БД и деградацию TTFB на 200–500 мс.

#### Конфигурация persistent cache в Angie (`angie.conf`)
Директива `file=` в параметре `proxy_cache_path` сохраняет индекс кэша на диске при остановке и мгновенно загружает его в память без длительного сканирования `Cache Loader`:
```nginx
http {
    proxy_cache_path /var/cache/angie/proxy
                     levels=1:2
                     keys_zone=my_cache:64m
                     max_size=10g
                     inactive=24h
                     use_temp_path=off
                     file=/var/cache/angie/cache.index; # Сохранение структуры кэша
    
    server {
        listen 443 ssl http2;
        location / {
            proxy_pass http://backend_production;
            proxy_cache my_cache;
            proxy_cache_valid 200 302 10m;
            proxy_cache_use_stale error timeout updating http_500 http_502 http_503;
        }
    }
}
```

#### Скрипт синтетического прогрева критических URL
```bash
#!/usr/bin/env bash
set -euo pipefail

BASE_URL="http://127.0.0.1:9002"
URLS=(
    "/api/v1/config"
    "/catalog/top"
    "/healthz"
)

echo "Запуск предварительного прогрева..."
for path in "${URLS[@]}"; do
    curl -s -o /dev/null -w "%{url_effective} - Status: %{http_code} - TTFB: %{time_starttransfer}s\n" "${BASE_URL}${path}"
done
# → http://127.0.0.1:9002/api/v1/config - Status: 200 - TTFB: 0.012s
# → http://127.0.0.1:9002/catalog/top - Status: 200 - TTFB: 0.045s
# → http://127.0.0.1:9002/healthz - Status: 200 - TTFB: 0.001s
```

## Диагностика и устранение неполадок

| Проблема | Симптом | Первопричина | Диагностика | Решение |
| :--- | :--- | :--- | :--- | :--- |
| **502 Bad Gateway при перезапуске бэкенда** | Всплеск ошибок 502 в access-логах в момент деплоя бэкенда. | Nginx отправляет запрос в закрывающийся сокет бэкенда из idle-пула keepalive. | `grep "502" /var/log/nginx/access.log`<br>Ошибка в error.log: `Connection reset by peer while reading response header from upstream`. | 1. Настроить `proxy_next_upstream error timeout invalid_header http_502;`<br>2. Реализовать Graceful Drain перед выключением бэкенда. |
| **Обрыв сессий при Graceful Reload Nginx** | Клиенты мобильных приложений и WebSocket получают `ECONNRESET` при `systemctl reload`. | `worker_shutdown_timeout` не задан (равен 0), либо равен слишком малому значению. | Проверить длительность жизни соединений; проверить наличие директивы в `nginx.conf`. | Выставить `worker_shutdown_timeout 30s;`<br>Для WebSocket настроить клиентский backoff при переподключении. |
| **Старые воркеры Nginx не завершаются (Lingering Workers)** | После нескольких reload процессы `worker process is shutting down` висят часами. | Долгоживущие соединения (gRPC, SSE, WebSocket) удерживают воркер. | `ps -eo pid,cmd \| grep "shutting down"` | Задать жесткий лимит `worker_shutdown_timeout 15s;` в блоке `main`. По истечении времени воркер будет принудительно убит ядром. |
| **Разрыв сессий HTTP/3 при reload** | Пользователи на протоколе QUIC получают сброс соединения при перезагрузке Nginx. | Отсутствует привязка входящих UDP-пакетов по Connection ID (CID) к старому воркеру. | Проверить версию ядра Linux (`uname -r`) и наличие `quic_bpf on;`. | Включить `quic_bpf on;` в блоке `events` или `http`. Требуется ядро Linux 5.7+ с поддержкой BPF. |
| **Всплеск TTFB после переключения трафика** | p95/p99 задержки ответа подскакивают с 40 мс до 600 мс на 1-2 минуты после деплоя. | Холодный старт: пустые пулы БД, холодный кэш Nginx, ненагретый JIT-компилятор. | Мониторинг метрики `$upstream_response_time` в Nginx. | Внедрить обязательный synthetic warm-up перед Cutover; использовать `file=` для кэша в Angie. |
| **Отказ сервиса при миграции схемы БД** | Запросы встают в очередь, пул соединений исчерпан (`too many clients`), 504 Gateway Timeout. | DDL-запрос встал в Lock Queue в ожидании `ACCESS EXCLUSIVE`, заблокировав все последующие чтение/запись. | `SELECT pid, query, state, age(clock_timestamp(), query_start) FROM pg_stat_activity WHERE state != 'idle';` | 1. Всегда выполнять `SET lock_timeout = '2s';` перед DDL.<br>2. Создавать индексы только через `CONCURRENTLY`.<br>3. Паттерн Expand-and-Contract. |
| **Переполнение очередей ячеек сокетов** | Клиенты получают `Connection timed out` или `Connection refused` в пике деплоя. | Размер backlog в `listen()` меньше интенсивности входящих рукопожатий. | `ss -lnt` показывает `Recv-Q > 0` и равным `Send-Q`; `netstat -s \| grep overflowed`. | Увеличить `net.core.somaxconn = 65535` в `sysctl.conf` и выставить `listen 443 ssl backlog=65535;` в веб-сервере. |

## Рекомендации и лучшие практики

### 1. Чек-лист SRE для развертывания без простоя

1. **Pre-flight Syntax Validation:**
   Любой автоматизированный скрипт деплоя обязан первым шагом выполнять `nginx -t` или `haproxy -c -f /etc/haproxy/haproxy.cfg`. Никакой перезапуск не инициируется при наличии синтаксических ошибок.
2. **Изоляция DDL-миграций от релизов кода:**
   Миграция схемы БД и раскатка нового кода приложения должны выполняться как независимые последовательные этапы. Код версии $N$ обязан без ошибок работать на схеме версии $N+1$.
3. **Двухфазное исключение узлов (Drain before Kill):**
   Никогда не отправлять `SIGTERM` или `systemctl stop` работающему инстансу приложения без предварительного перевода в режим `DRAIN` на балансировщике и паузы для сброса активных сессий.
4. **Конфигурация повторных попыток на прокси:**
   Обязательно наличие `proxy_next_upstream error timeout invalid_header http_502 http_503;` с разумным лимитом попыток (`proxy_next_upstream_tries 3;`). Это нивелирует единичные сетевые гонки между прокси и бэкендами.
5. **Тепловой прогрев (Warm-up Gate):**
   Новая среда (Green или узел в Rolling Update) не должна получать боевых пользователей до тех пор, пока синтетические запросы не подтвердят заполнение внутренних структур и прогрев кэшей.
6. **Настройка системных лимитов ядра (Sysctl Tuning):**
   В файле `/etc/sysctl.d/99-network-performance.conf` должны быть заданы параметры:
   ```ini
   net.core.somaxconn = 65535
   net.ipv4.tcp_max_syn_backlog = 65535
   net.ipv4.tcp_abort_on_overflow = 0
   net.ipv4.tcp_fin_timeout = 15
   ```
7. **Автоматизированный мониторинг и Runbook отката:**
   Во время деплоя автоматика обязана отслеживать три ключевых сигнала:
   - Rate ошибок 5xx (порог отката: рост > 0.5% за 1 минуту);
   - p95/p99 задержки TTFB (порог: рост > 50% относительно базовой линии);
   - Количество активных воркеров веб-сервера.
