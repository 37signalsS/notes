# Кэширование как инструмент веб-производительности

## Определения

**Кэширование в веб-производительности** — стратегия снижения времени загрузки и уменьшения количества сетевых запросов за счёт сохранения копий ресурсов на промежуточных узлах: в браузере клиента, на CDN (Content Delivery Network) или обратном прокси-сервере (Nginx/Angie).

Кэширование является частным случаем общей стратегии оптимизации хранения данных — см. [обзор кэширования](../../../Concepts/Caching/caching_overview.md). Правильно настроенное кэширование способно снизить время загрузки страниц на 40–60%.

## Основные концепции

### Типы кэширования

| Тип | Уровень | Что кэширует | Заголовки / Директивы |
| :--- | :--- | :--- | :--- |
| **Клиентское (Browser Cache)** | Браузер | Статика (CSS, JS, изображения) | `Cache-Control`, `ETag`, `Expires` |
| **Серверное (Proxy Cache)** | Обратный прокси | Ответы бэкенда | `proxy_cache`, `proxy_cache_valid` |
| **CDN Cache** | Edge-серверы | Статический и динамический контент | `Cache-Control: s-maxage`, CDN API |

### Влияние на Web Vitals

Кэширование напрямую влияет на ключевые метрики Core Web Vitals (подробнее см. [web_vitals.md](./web_vitals.md)):

- **LCP (Largest Contentful Paint):** Кэширование LCP-элемента (например, главного изображения или шрифта) критически ускоряет его отрисовку при повторных визитах.
- **INP (Interaction to Next Paint):** Быстрая доставка JS-бандлов и CSS из кэша ускоряет выполнение скриптов и рендеринг, снижая задержки интерактивности.
- **CLS (Cumulative Layout Shift):** Кэширование критических стилей и шрифтов предотвращает задержки их загрузки, которые часто являются причиной сдвигов макета.

### Ключевые стратегии

- **Вечное кэширование статики** — использование `max-age=31536000, immutable` в сочетании с *cache busting* (уникальный хэш в имени файла).
- **Валидационное кэширование динамики** — использование `no-cache` или короткого TTL (Time-To-Live), чтобы HTML-документ всегда содержал актуальные ссылки на ресурсы.
- **Stale-while-revalidate** — стратегия отдачи устаревшего контента из кэша с его одновременным фоновым обновлением.

## Практические сценарии

### Сценарий: повторный визит пользователя

При первом визите браузер загружает все ресурсы с сервера (`MISS`). При повторном визите:

1. **Статика с `immutable`:** браузер не отправляет запрос — ресурс мгновенно загружается из локального дискового кэша.
2. **HTML с `no-cache`:** браузер отправляет условный запрос (`If-None-Match`). Сервер отвечает `304 Not Modified`, что экономит трафик и время на передачу тела ответа.
3. **API-ответы с TTL:** могут кэшироваться на стороне прокси-сервера (proxy cache), снижая нагрузку на базу данных и бэкенд.

### Сценарий: защита бэкенда от нагрузки

Директива `proxy_cache_lock` предотвращает эффект "стада бизонов" (thundering herd) — при массовых одновременных запросах к одному некэшированному ресурсу только один запрос уходит на бэкенд, а остальные ожидают ответа и получают его уже из сформированного кэша. Подробнее — [proxy_caching.md](../../Nginx/Performance/Caching/proxy_caching.md).

### Сценарий: деплой новой версии

При обновлении статики изменяется хэш в имени файла (например, `app.a1b2c3.js` → `app.d4e5f6.js`). Браузер воспринимает это как абсолютно новый ресурс и загружает его, игнорируя старый кэш. При этом HTML-страница с новыми ссылками отдаётся с заголовком `no-cache`, что гарантирует получение пользователем актуальной версии приложения.
