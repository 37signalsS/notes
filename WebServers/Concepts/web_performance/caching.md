## Определения

**Кэширование в веб-производительности** — стратегия снижения времени загрузки и минимизации сетевого трафика за счёт сохранения копий ресурсов (HTML, CSS — Cascading Style Sheets, JS — JavaScript, изображения, шрифты) на промежуточных узлах. 

Это фундаментальный механизм оптимизации, позволяющий сократить время до отрисовки контента и снизить нагрузку на серверную инфраструктуру. Кэширование является частным случаем общей стратегии оптимизации хранения — см. [обзор кэширования](../../../Concepts/Caching/caching_overview.md).

## Основные концепции

### Уровни и типы кэширования

В 2026 году кэширование разделяется на четыре основных уровня:

| Тип | Уровень | Механизм / Хранилище | Особенности |
| :--- | :--- | :--- | :--- |
| **Браузерный кэш (Browser Cache)** | Клиент | HTTP Cache (Диск/RAM) | Управляется заголовками `Cache-Control`. Подвержен партиционированию (изоляции). |
| **Service Worker (Cache API)** | Клиент | Программный кэш (IndexedDB) | Позволяет реализовывать кастомные стратегии (Offline-first, Background sync). |
| **Серверный кэш (Proxy Cache)** | Прокси | Nginx/Angie (Диск/Shared Memory) | Снижает нагрузку на бэкенд, агрегирует запросы (`proxy_cache_lock`). |
| **CDN Cache** | Edge | Распределенная сеть (PoP) | Доставляет контент из ближайшей к пользователю географической точки. |

### Влияние на Web Vitals

Эффективное кэширование критически важно для метрик Core Web Vitals (подробнее — [web_vitals.md](./web_vitals.md)):

*   **LCP (Largest Contentful Paint):** Мгновенная отдача LCP-ресурса (например, Hero-image) из кэша исключает фазу загрузки по сети, что часто дает выигрыш в 500мс–2000мс.
*   **INP (Interaction to Next Paint):** Быстрая доставка JS-бандлов и шрифтов снижает время блокировки основного потока (Main Thread), ускоряя реакцию на ввод пользователя.
*   **CLS (Cumulative Layout Shift):** Кэширование критического CSS и шрифтов предотвращает "прыжки" контента при поздней загрузке стилей.

### Современные механизмы и ограничения

1.  **Партиционирование кэша (Cache Partitioning):**
    Браузеры используют двойной ключ кэширования (Top-level Site + Resource URL). Это означает, что общие библиотеки (например, jQuery с публичного CDN) будут скачиваться отдельно для каждого сайта. Преимущество использования общих CDN для кэширования в 2026 году практически аннулировано.
2.  **Fetch Priority (Приоритеты):**
    Атрибут `fetchpriority="high"` для критических ресурсов заставляет браузер быстрее отправлять проверочные запросы (`If-None-Match`) для кэшированных, но просроченных элементов.
3.  **Гибкие стратегии перевалидации:**
    - `stale-while-revalidate`: позволяет мгновенно отдать устаревший ресурс, обновляя его в фоне.
    - `stale-if-error`: дает возможность браузеру или прокси использовать старый кэш, если основной сервер недоступен.

## Практические сценарии

### Сценарий: Вечное кэширование с Cache Busting

Для статических файлов (JS, CSS, изображения), имена которых содержат хэш контента.
- **Заголовок:** `Cache-Control: public, max-age=31536000, immutable`
- **Результат:** Браузер даже не пытается проверить файл на сервере в течение года. При обновлении кода меняется имя файла, что браузер воспринимает как новый ресурс.

### Сценарий: Отказоустойчивый кэш (Resilient Cache)

Защита пользователя от временных сбоев бэкенда.
- **Заголовок:** `Cache-Control: max-age=3600, stale-if-error=86400`
- **Результат:** Если сервер упал (5xx error) или недоступен, браузер будет использовать кэшированную копию еще в течение суток, обеспечивая непрерывность работы.

### Сценарий: Защита от "эффекта толпы" (Thundering Herd)

Настройка обратного прокси (Nginx/Angie) при массовом запросе к некэшированному тяжелому API.
- **Директива:** `proxy_cache_lock on;`
- **Результат:** Только первый запрос уходит на бэкенд для формирования кэша, остальные ждут и получают ответ уже из кэша, предотвращая перегрузку БД и CPU.
