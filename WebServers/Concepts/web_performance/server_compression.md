# Компрессия контента на веб-сервере

## Определения

**Компрессия (сжатие) контента** — процесс уменьшения объема передаваемых текстовых данных (HTML, CSS, JS, SVG, JSON) перед их отправкой клиенту по сети. Это один из наиболее эффективных методов оптимизации веб-производительности, позволяющий существенно сократить время загрузки страниц за счет уменьшения объема трафика.

**Основные алгоритмы сжатия:**

- **Gzip:** классический алгоритм, основанный на DEFLATE. Обладает универсальной поддержкой всеми современными и устаревшими браузерами. Используется как надежный запасной вариант.
- **Brotli:** современный алгоритм сжатия от Google, использующий словарь. Обеспечивает на 15–20% лучшую степень сжатия по сравнению с Gzip при сопоставимой скорости декомпрессии.
- **Zstd (Zstandard):** высокопроизводительный алгоритм от Facebook. Отличается исключительной скоростью сжатия и декомпрессии при высокой степени сжатия. Оптимален для динамического контента.

## Основные концепции

### Типы компрессии

| Тип | Описание | Применение |
| :--- | :--- | :--- |
| **Статическая** | Файлы сжимаются один раз заранее (на этапе сборки или деплоя) и сохраняются на диске. | Статические ресурсы: CSS, JavaScript, шрифты, SVG-иконки. |
| **Динамическая** | Контент сжимается «на лету» веб-сервером в момент обработки запроса. | Динамические данные: HTML-страницы, JSON-ответы API. |

### Согласование контента (Content Negotiation)

Процесс выбора алгоритма сжатия происходит через HTTP-заголовки:

1. **Запрос клиента:** Браузер сообщает о поддержке алгоритмов в заголовке `Accept-Encoding: gzip, br, zstd`.
2. **Ответ сервера:** Сервер выбирает наиболее эффективный из поддерживаемых алгоритмов, сжимает данные и указывает его в заголовке `Content-Encoding: br`.
3. **Заголовок Vary:** Сервер должен отправлять заголовок `Vary: Accept-Encoding`, чтобы промежуточные прокси-серверы и CDN (Content Delivery Network) кэшировали разные версии контента (сжатую и несжатую) отдельно.

### Метрики и формула эффективности

Эффективность сжатия для конечного пользователя определяется суммарным временем обработки ресурса (**Total Time**), которое складывается из трех стадий:

1. **Компрессия (T_compression):** Время, затраченное процессором сервера на сжатие. Зависит от алгоритма и выбранного уровня сжатия (compression level).
2. **Передача (T_transfer):** Время передачи данных по сети. Зависит от итогового размера сжатого файла и пропускной способности канала.
3. **Декомпрессия (T_decompression):** Время, затраченное процессором клиента на распаковку.

**Формула оптимальности:**
`Total Time = T_compression + T_transfer + T_decompression`

Для статических ресурсов стадия `T_compression` выполняется один раз, поэтому можно использовать максимальные уровни сжатия. Для динамики критически важно минимизировать `T_compression`, используя быстрые алгоритмы (Zstd) или низкие уровни сжатия.

## Практические сценарии

### Выбор алгоритма и стратегии

- **Для статики:** Рекомендуется предварительное сжатие алгоритмом **Brotli** (уровень 11) с созданием Gzip-копии (уровень 6) для обратной совместимости.
- **Для динамики:** Рекомендуется **Zstd** (уровни 3–5), так как он обеспечивает высокую скорость при хорошем сжатии, не блокируя надолго рабочие процессы сервера.
