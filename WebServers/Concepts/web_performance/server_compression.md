# Компрессия контента на веб-сервере

---
**Надёжность: 10/10** (SSoT + Проверено в 2026 году по стандартам RFC и поддержке браузеров)
---

## Определения

**Компрессия (сжатие) контента** — процесс уменьшения объема передаваемых текстовых данных (HTML, CSS, JS, SVG, JSON) перед их отправкой клиенту по сети. Это один из наиболее критичных методов оптимизации веб-производительности, позволяющий сократить время загрузки страниц на 50–90% за счет минимизации объема трафика.

**Основные алгоритмы сжатия (Статус 2026):**

- **Gzip:** классический алгоритм (DEFLATE). Используется как универсальный **fallback** для старых систем.
- **Brotli (`br`):** оптимизирован для веба, использует статический словарь. Обеспечивает лучшую плотность сжатия для статики (CSS/JS).
- **Zstd (Zstandard / `zstd`):** высокопроизводительный алгоритм, ставший в 2026 году **Baseline** (поддерживается всеми основными браузерами). Идеален для динамического контента благодаря исключительной скорости сжатия при высокой степени сжатия.

## Основные концепции

### Типы компрессии

| Тип | Описание | Применение |
| :--- | :--- | :--- |
| **Статическая** | Файлы сжимаются один раз заранее (на этапе сборки). | CSS, JS, шрифты, SVG, PDF. |
| **Динамическая** | Сжатие «на лету» в момент обработки запроса. | HTML-страницы, JSON API, персонализированные ответы. |

### Согласование контента (Content Negotiation)

Процесс выбора алгоритма через HTTP-заголовки:

1.  **Запрос клиента:** `Accept-Encoding: gzip, br, zstd`.
2.  **Ответ сервера:** выбор лучшего алгоритма (приоритет Zstd/Brotli над Gzip) и указание в `Content-Encoding: zstd`.
3.  **Заголовок Vary:** Сервер **ОБЯЗАН** отправлять `Vary: Accept-Encoding`. Это гарантирует, что CDN и промежуточные прокси не отдадут сжатый контент клиенту, который его не поддерживает.

### Метрики и формула эффективности

Эффективность определяется суммарным временем (**Total Time**):
`Total Time = T_compression + T_transfer + T_decompression`

- **T_compression:** Время работы CPU сервера. Для динамики Zstd — лидер, так как Brotli на высоких уровнях слишком медленный.
- **T_transfer:** Время передачи. На медленных сетях (3G/4G) выигрывает максимальное сжатие (Brotli level 11).
- **T_decompression:** Время работы CPU клиента. В 2026 году это критично для мобильных устройств (экономия заряда батареи).

### Продвинутые технологии (2026+)

1.  **Compression Dictionary Transport (RFC 9509):** механизм, позволяющий браузеру и серверу использовать **общий словарь (Shared Dictionary)** для конкретного сайта. Это позволяет сжимать только *разницу* между страницами или изменения в API, доводя размер обновлений до считанных байт.
2.  **Hardware Offloading:** использование аппаратных ускорителей (Intel QAT, AWS Nitro TLS/Compression cards) для снятия нагрузки по сжатию с основных ядер CPU.

## Безопасность и риски

**Атака BREACH / CRIME:** использование сжатия вместе с HTTPS может позволить злоумышленнику угадать секретные токены (например, CSRF) по изменению размера сжатого ответа.
- **Защита:** добавление случайного «шума» в ответ, отключение сжатия для чувствительных страниц или использование `SameSite` куки.

## Практические сценарии

### Выбор стратегии сжатия

-   **Статические ресурсы:** Сжатие Brotli (уровень 11) + Zstd (уровень 19) на этапе сборки. Это дает максимальную экономию трафика без нагрузки на сервер в runtime.
-   **Динамический JSON API:** Сжатие Zstd (уровни 3–5). Обеспечивает RPS (Requests Per Second) значительно выше, чем Gzip/Brotli, при сопоставимом размере.
-   **Текстовые стримы (SSE):** Использование Zstd с флагом `long-distance matching` для эффективного сжатия повторяющихся данных в потоке.
