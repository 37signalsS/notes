# Оптимизация TLS для производительности

## Определения

**Оптимизация TLS (Transport Layer Security)** — совокупность настроек и архитектурных решений, направленных на минимизацию времени установки защищенного соединения (Handshake Latency), снижение вычислительной нагрузки на сервер (CPU Overhead) и уменьшение объема передаваемых служебных данных.

**Ключевые показатели эффективности (KPI):**

- **Handshake RTT:** количество раундов обмена данными до начала передачи полезной нагрузки (1-RTT в TLS 1.3 против 2-RTT в TLS 1.2).
- **TTFB (Time To First Byte):** время до получения первого байта данных, на которое напрямую влияет скорость TLS-рукопожатия.
- **CPU Usage:** нагрузка на процессор при выполнении криптографических операций (шифрование, расшифровка, подпись).

## Основные концепции

### Минимизация Handshake Latency

Основной задержкой при установке HTTPS-соединения является TLS-рукопожатие.

1. **Использование TLS 1.3:** современный стандарт, который сокращает рукопожатие до 1-RTT. Также поддерживает режим **0-RTT** для мгновенного возобновления сессий.
   - Подробнее: **[Процесс рукопожатия TLS](../../../Networking/Protocols/tls.md#процесс-рукопожатия-ssl-tls-handshake)**.
2. **Возобновление сессии (Session Resumption):** использование Session IDs, Session Tickets или PSK (в TLS 1.3) для исключения этапа обмена ключами при повторных подключениях.
   - Подробнее: **[Механизмы возобновления сессии](../../../Networking/Protocols/tls.md#возобновление-сессии-session-resumption)**.
3. **OCSP Stapling:** позволяет серверу доставлять клиенту подтверждение валидности сертификата в рамках TLS-рукопожатия, избавляя клиента от дополнительного DNS-запроса и TCP-соединения к OCSP-ответчику.
   - Подробнее: **[Механизмы отзыва сертификатов](../../../Security/Concepts/pki_overview.md#механизмы-отзыва-сертификатов)**.

### Оптимизация вычислительной нагрузки

1. **Сертификаты ECDSA:** использование эллиптических кривых (ECC) вместо RSA позволяет уменьшить размер сертификата и ускорить операции подписи/проверки при той же стойкости ключа.
   - Подробнее: **[ECDSA против RSA](../../../WebServers/Nginx/Security/TLS_SSL/nginx_tls_virtual_host_config.md#использование-ec-и-rsa-сертификатов-одновременно)**.
2. **Наборы шифров (Cipher Suites):** использование алгоритмов с аппаратной поддержкой (AES-GCM) или оптимизированных для мобильных устройств (ChaCha20-Poly1305).
   - Подробнее: **[Настройка шифров в Nginx](../../../WebServers/Nginx/Security/TLS_SSL/nginx_tls_global_parameters.md#ssl_ciphers-tls-12-и-ниже)**.
   
   **Производительность симметричных шифров (бенчмарк OpenSSL speed, Ubuntu 26.04, OpenSSL 3.5.5):**
   
   | Шифр | Пропускная способность |
   |:-----|:-----------------------|
   | AES-256-GCM | ~1.5 GB/s |
   | AES-128-GCM | <1 GB/s |
   | ChaCha20-Poly1305 | ~0.76 GB/s |
   
   > Важно: AES-256-GCM может опережать AES-128-GCM на современных процессорах с AES-NI за счёт особенностей оптимизации в конкретной версии библиотеки. Выбор шифра требует тестирования на целевой платформе.
3. **Kernel TLS (kTLS):** перенос шифрования в ядро ОС для повышения производительности при отдаче статических файлов (использование `sendfile`).
   - SSoT по kTLS: **[Kernel TLS в Nginx](../../../WebServers/Nginx/Performance/nginx_performance_tuning.md#kernel-tls-ktls)**.

### Безопасность и производительность

- **HSTS (HTTP Strict Transport Security):** заголовок, заставляющий браузер всегда использовать HTTPS, исключая лишний HTTP-редирект (301/302) и защищая от атак SSL Stripping.
  - Подробнее: **[Настройка HSTS](../../../WebServers/Nginx/Security/TLS_SSL/nginx_tls_virtual_host_config.md#базовая-конфигурация-https)**.
- **ALPN (Application-Layer Protocol Negotiation):** позволяет согласовать протокол прикладного уровня (например, HTTP/2) во время TLS-рукопожатия.
  - Подробнее: **[ALPN в TLS](../../../Networking/Protocols/tls.md#alpn-application-layer-protocol-negotiation)**.

## Практические сценарии

### Сценарий 1: Конфигурация Nginx для высокой производительности

Для достижения наилучших показателей рекомендуется настроить глобальные параметры TLS в `nginx.conf`:

```nginx
http {
    # Кэширование сессий для TLS 1.2
    ssl_session_cache shared:SSL:20m;
    ssl_session_timeout 1d;
    
    # Отключение билетов сессий для обеспечения PFS (зависит от модели угроз)
    ssl_session_tickets off;
    
    # Современные протоколы
    ssl_protocols TLSv1.2 TLSv1.3;
    
    # Оптимальный размер буфера для снижения TTFB
    ssl_buffer_size 4k;
    
    # Включение OCSP Stapling
    ssl_stapling on;
    ssl_stapling_verify on;
    resolver 8.8.8.8 8.8.4.4 valid=300s;
}
```

Полное описание параметров: **[Глобальные параметры TLS в Nginx](../../../WebServers/Nginx/Security/TLS_SSL/nginx_tls_global_parameters.md)**.

### Сценарий 2: Переход на HTTP/3 (QUIC)

HTTP/3 объединяет транспортный уровень и шифрование, обеспечивая 1-RTT соединение по умолчанию и устраняя проблему HOL-блокировки.

Подробнее: **[HTTP/2 и HTTP/3](./http2_http3.md)**.

### Сценарий 3: Выбор TLS-библиотеки (OpenSSL vs AWS-LC)

Разные TLS-библиотеки могут существенно влиять на производительность сервера. В тестах сравнивались три варианта сборки nginx:

- **OpenSSL (системная):** версия из репозитория дистрибутива (Ubuntu 24.04 — OpenSSL 3.0.13, Ubuntu 26.04 — OpenSSL 3.5.5)
- **OpenSSL (кастомная):** самосборная версия (OpenSSL 4.0.1 на базе 1.1.1w)
- **AWS-LC:** библиотека на основе BoringSSL (форк OpenSSL от Google), версия 5.0

**Параметры тестовой конфигурации nginx:**

- `worker_processes 1` — нагрузка на одно ядро CPU для чистоты измерений
- `ssl_session_cache shared:SSL:10m; ssl_session_timeout 2m;`
- `ssl_protocols TLSv1.2 TLSv1.3;`
- `tcp_nodelay on; tcp_nopush on;`
- Сжатие контента (gzip) отключено для изоляции влияния TLS
- Специальный endpoint `/zero` возвращает `200 OK` без тела — для тестирования производительности handshake

**Результаты тестирования (wrkx, изолированный нагрузчик на хосте, KVM):**

**Handshake (соединений/с):**

| Конфигурация | TLS 1.3 + ECDSA | TLS 1.3 + RSA | TLS 1.2 + ECDSA | TLS 1.2 + RSA |
|:-------------|:---------------:|:--------------:|:----------------:|:--------------:|
| AWS-LC | ~9500 | ~8700 | ~7000 | ~5700 |
| OpenSSL 4.0.1 | ~7300 | ~7000 | ~8600 | ~6300 |
| OpenSSL 3.5.5 | ~7000 | ~6500 | ~9100 | ~6000 |

> AWS-LC значительно опережает OpenSSL в TLS 1.3 handshake (EC: +30%, RSA: +25%). Однако в TLS 1.2 OpenSSL показывает лучшие или сопоставимые результаты. Выбор библиотеки зависит от преобладающего протокола в среде.

**RPS (Requests Per Second, однокибайтный файл, TLS 1.3 + ECDSA):**

- OpenSSL 3.5.5: ~73 700 RPS
- OpenSSL 4.0.1: ~72 100 RPS
- AWS-LC: ~68 100 RPS

**Пропускная способность (стомегабайтный файл, AES-256-GCM):**

- AWS-LC: ~1.5 GB/s
- OpenSSL 3.5.5: ~1.45 GB/s
- OpenSSL 4.0.1: ~1.45 GB/s

> На пропускной способности разница между библиотеками минимальна — определяющим фактором выступает выбранный симметричный шифр.

**Ограничения совместимости:**

- Управление шифрами TLS 1.3 через `ssl_conf_command Ciphersuites` работает в OpenSSL, но не поддерживается в AWS-LC и других форках BoringSSL
- `ssl_log_params` (логирование согласованного шифра) — полезно для верификации при тестировании
