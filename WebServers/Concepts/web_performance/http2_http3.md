# Протоколы HTTP/2 и HTTP/3 в веб-производительности

Полное сравнение версий протоколов доступно в руководстве [эволюция HTTP](../../../Networking/Protocols/HTTP/http_versions.md), а детали настройки серверов — в статье [конфигурация HTTP/2 и HTTP/3 в Nginx/Angie](../../Nginx/Performance/nginx_http_versions.md).

## Определения

**HTTP/2 (Hypertext Transfer Protocol Version 2)** — бинарная версия протокола HTTP (RFC 9113), основанная на мультиплексировании потоков данных в рамках одного TCP-соединения. Она вводит фреймирование данных и сжатие заголовков (HPACK).

**HTTP/3 (Hypertext Transfer Protocol Version 3)** — версия протокола на базе транспорта **QUIC** (RFC 9114), работающая поверх UDP. QUIC интегрирует в себя функции TLS 1.3 и реализует собственные механизмы надежной доставки и контроля потока, устраняя ограничения TCP.

**Блокировка начала очереди (Head-of-Line Blocking, HOL)** — задержка в обработке пакетов данных, когда один потерянный или задержанный пакет останавливает всю последующую очередь.
*   В **HTTP/2** HOL-блокировка сохраняется на уровне TCP: если один пакет TCP потерян, все мультиплексированные потоки внутри этого соединения ждут его переотправки.
*   В **HTTP/3** HOL-блокировка на уровне транспорта полностью устранена: потеря UDP-пакета блокирует только те потоки, к которым принадлежали содержащиеся в нем данные.

**0-RTT (Zero Round Trip Time)** — функция возобновления сессии в TLS 1.3 и QUIC, позволяющая клиенту отправить полезную нагрузку (HTTP-запрос) в первом же пакете установки соединения.

## Основные концепции

### Техническое сравнение протоколов (Статус 2026)

| Характеристика | HTTP/2 | HTTP/3 |
| :--- | :--- | :--- |
| **Транспортный протокол** | TCP (с обязательным TLS 1.2+ для браузеров) | **QUIC (UDP)** со встроенным TLS 1.3 |
| **Механизм надежности** | Реализован в ядре ОС (TCP Stack) | **Реализован в User-space** (QUIC Stack) |
| **HOL Blocking** | Присутствует на уровне TCP | **Отсутствует** (потоки независимы) |
| **Идентификация сессии** | Пятикомпонентный кортеж (Src IP, Src Port, Dst IP, Dst Port, Proto) | **Connection ID (CID)** — независим от IP-адреса |
| **Сжатие заголовков** | HPACK (статические и динамические таблицы) | **QPACK** (устойчиво к неупорядоченной доставке) |
| **Приоритезация** | Деревья зависимостей и веса (RFC 7540) | **Extensible Prioritization** (RFC 9218) |
| **Хендшейк (Latency)** | 2-3 RTT (TCP + TLS) | **1 RTT** (совмещенный хендшейк) или **0-RTT** |

### Влияние на производительность и оптимизация

1.  **Сетевая устойчивость:**
    В мобильных сетях и сетях с потерями пакетов (>1%) HTTP/3 обеспечивает снижение LCP (Largest Contentful Paint) до 40-60%. Это достигается не только за счет устранения HOL-блокировки, но и благодаря более совершенным алгоритмам контроля перегрузки. В 2026 году стандартом является **BBRv3**, который максимизирует пропускную способность, избегая переполнения буферов (Bufferbloat).

2.  **Миграция соединений (Connection Migration):**
    Уникальная особенность HTTP/3. При смене сети (например, переключение смартфона с Wi-Fi на 4G) QUIC-соединение не разрывается, так как сервер и клиент продолжают узнавать друг друга по Connection ID (CID). Для пользователя это выглядит как мгновенное переключение без зависания стриминга или загрузки страницы.

3.  **Оптимизация UDP-стека (High Load):**
    Обработка QUIC в пространстве пользователя (User-space) создает высокую нагрузку на CPU (в 2-3 раза выше, чем TCP). Для масштабирования в 2026 году применяются:
    *   **Generic Segmentation Offload (GSO):** Снижает количество системных вызовов, позволяя передавать группы UDP-пакетов ядру одним вызовом.
    *   **eBPF (quic_bpf):** Директива, позволяющая ядру Linux направлять пакеты определенного Connection ID тому же воркеру Nginx/Angie, который начал сессию. Без этого `reload` конфигурации привел бы к разрыву всех HTTP/3 соединений.

4.  **Безопасность и 0-RTT:**
    Использование 0-RTT (`ssl_early_data`) сокращает TTFB до минимума, но вводит риск **Replay-атак** (повторной отправки запроса злоумышленником).
    *   **Защита:** Серверы должны разрешать 0-RTT только для идемпотентных методов (GET, HEAD) и проверять свежесть тикетов. В Angie/Nginx для этого используется `ssl_early_data on;`.

### Приоритезация ресурсов (RFC 9218)

В отличие от сложной системы HTTP/2, в 2026 году используется упрощенная схема:
*   **Параметр `u` (Urgency):** Приоритет от 0 (наивысший) до 7.
*   **Параметр `i` (Incremental):** Булево значение, указывающее, можно ли обрабатывать ресурс по частям (например, прогрессивные изображения).
Это позволяет браузерам более эффективно управлять полосой пропускания, гарантируя, что критический CSS (Urgency=0) не будет заблокирован фоновыми изображениями.

## Практические сценарии

### Механизмы обнаружения HTTP/3

Так как первый запрос всегда идет по TCP (так как клиент не знает о поддержке UDP), используются механизмы анонсирования:

1.  **Заголовок `Alt-Svc`:**
    ```http
    Alt-Svc: h3=":443"; ma=86400, h3-29=":443"; ma=86400
    ```
    Сообщает браузеру о наличии HTTP/3. `ma` (max-age) кэширует эту информацию.
2.  **HTTPS Resource Record (DNS):**
    Самый быстрый метод (RFC 9460). Позволяет браузеру узнать о поддержке h3 еще до отправки первого запроса.
    ```dns
    example.com. HTTPS 1 . alpn="h3,h2"
    ```

### Настройка на стороне сервера (Angie/Nginx)

Пример конфигурации с использованием eBPF и GSO для максимальной производительности:

```nginx
# В основном контексте (main) для Angie/Nginx 1.25+
quic_bpf on; 

http {
    server {
        # Стандартные порты TCP
        listen 443 ssl;
        http2 on;

        # Порты для HTTP/3 (UDP)
        listen 443 quic reuseport;
        
        # Оптимизация производительности UDP
        quic_gso on;
        quic_retry on; # Защита от UDP Flood/Reflection

        # Анонсирование протокола
        add_header Alt-Svc 'h3=":443"; ma=86400';

        # TLS 1.3 обязателен для HTTP/3
        ssl_protocols TLSv1.3;
        ssl_early_data on; # Включение 0-RTT
        
        # ... остальные настройки SSL
    }
}
```

## Дополнительная информация

### Стратегии оптимизации фронтенда

*   **Антипаттерн: Domain Sharding.** В 2026 году разделение ресурсов по поддоменам (`static1.`, `static2.`) **запрещено**. Оно мешает мультиплексированию, заставляет заново проходить хендшейки и препятствует эффективной работе алгоритма BBR.
*   **103 Early Hints:** Механизм, пришедший на смену Server Push. Позволяет серверу отправить заголовки `Link: </style.css>; rel=preload` мгновенно, пока бэкенд (PHP/Python/Go) еще формирует тело HTML. Это сокращает LCP на сотни миллисекунд.
