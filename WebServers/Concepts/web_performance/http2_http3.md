# Протоколы HTTP/2 и HTTP/3 в веб-производительности

Полное сравнение версий протоколов доступно в руководстве [эволюция HTTP](../../../Networking/Protocols/HTTP/http_versions.md), а детали настройки серверов — в статье [конфигурация HTTP/2 и HTTP/3 в Nginx](../../Nginx/Performance/nginx_http_versions.md).

## Определения

**HTTP/2 (Hypertext Transfer Protocol Version 2)** — вторая мажорная версия протокола HTTP (стандарт RFC 9113), разработанная для повышения производительности веб-приложений за счёт мультиплексирования запросов и сжатия заголовков поверх протокола TCP (Transmission Control Protocol).

**HTTP/3 (Hypertext Transfer Protocol Version 3)** — третья мажорная версия протокола (стандарт RFC 9114), использующая транспортный протокол QUIC на базе UDP (User Datagram Protocol) для устранения проблемы блокировки начала очереди на транспортном уровне.

**Head-of-Line (HOL) Blocking (блокировка начала очереди)** — проблема, при которой потеря или задержка одного пакета данных блокирует обработку всех последующих данных в рамках одного соединения.

**HPACK / QPACK** — специализированные алгоритмы сжатия HTTP-заголовков. HPACK применяется в HTTP/2, а QPACK используется в HTTP/3 для устранения зависимости сжатия от строгого порядка доставки пакетов.

## Основные концепции

### Сравнение HTTP/2 и HTTP/3

| Характеристика | HTTP/2 | HTTP/3 |
| :--- | :--- | :--- |
| **Транспортный уровень** | TCP | QUIC поверх UDP |
| **Блокировка очереди (HOL)** | Решена на уровне приложения, остается на уровне TCP | Полностью устранена на всех уровнях |
| **Сжатие заголовков** | HPACK | QPACK |
| **Миграция соединения** | Отсутствует | Поддерживается (привязка к ID, а не к IP-адресу) |
| **Server Push** | Поддерживается (считается устаревшим) | Исключен из стандарта |

Более детальное сравнение характеристик всех версий протокола приведено в файле [эволюция HTTP](../../../Networking/Protocols/HTTP/http_versions.md).

### Влияние на производительность

- **Мультиплексирование в HTTP/2:** позволяет использовать одно TCP-соединение для загрузки множества ресурсов вместо ограничения в 6 соединений (как в HTTP/1.1). Однако потеря одного TCP-пакета все еще блокирует все параллельные потоки до момента его повторной передачи.
- **Преимущества HTTP/3:** сокращает время установления соединения до 1–2 RTT (Round Trip Time — время туда-обратно) за счет объединения рукопожатий QUIC и TLS (Transport Layer Security). Поддержка 0-RTT позволяет отправлять данные при повторных подключениях мгновенно (директива `ssl_early_data`), но требует защиты от атак повторного воспроизведения (replay attacks).
- **Ресурсоемкость:** использование современных версий протокола увеличивает нагрузку на центральный процессор и оперативную память сервера примерно на 20–30% по сравнению с HTTP/1.1.

### Механизмы обнаружения HTTP/3 клиентами

1. **Заголовок `Alt-Svc` (Alternative Services):**

   ```http
   Alt-Svc: h3=":443"; ma=86400
   ```

   Этот заголовок сообщает браузеру о поддержке протокола. Существует проблема «холодного старта»: при первом посещении браузер еще не знает о поддержке и начинает работу по HTTP/2.

2. **DNS-запись типа HTTPS:**

   ```dns
   example.com HTTPS 1 . alpn="h2,h3"
   ```

   Позволяет браузеру узнать о поддержке протоколов до момента установки соединения с сервером. Подробнее см. [записи DNS HTTPS/SVCB](../../../Networking/Protocols/DNS/dns_records.md).

## Практические сценарии

### Проверка используемой версии протокола

Для проверки в командной строке используются ключи `curl`:

```bash
# Проверка HTTP/2
curl -I --http2 https://example.com/

# Проверка HTTP/3
curl -I --http3 https://example.com/
```

В браузере (например, Chrome): откройте инструменты разработчика (Developer Tools) → вкладка Network → колонка **Protocol**. Обозначения: `h2` для HTTP/2 и `h3` для HTTP/3.

### Диагностика и настройка

Алгоритм проверки доступности UDP-портов, настройки заголовков и модуля QUIC подробно описан в разделе [диагностика HTTP/3](../../Nginx/Performance/nginx_http_versions.md#практические-сценарии). ## Дополнительная информация

### Влияние на стратегии оптимизации фронтенда

- **Доменный шардинг (Domain Sharding):** является антипаттерном для HTTP/2 и HTTP/3, так как создание множества соединений с разными поддоменами мешает эффективному мультиплексированию.
- **Объединение ресурсов (Concatenation):** конкатенация CSS и JS файлов становится менее критичной и иногда даже вредной, так как мультиплексирование позволяет загружать мелкие файлы параллельно без задержек на установку новых соединений.
- **Динамическое сжатие:** медленные алгоритмы сжатия на сервере могут блокировать процесс обработки, что особенно заметно при использовании HTTP/2. Подробности см. в разделе [сжатие в Nginx](../../Nginx/Performance/nginx_compression.md).
