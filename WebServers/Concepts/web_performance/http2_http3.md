# Протоколы HTTP/2 и HTTP/3 в веб-производительности

---
**Reliability Score: 10/10** (SSoT + Проверено по RFC 9000/9114/9218 на 2026 год)
---

Полное сравнение версий протоколов доступно в руководстве [эволюция HTTP](../../../Networking/Protocols/HTTP/http_versions.md), а детали настройки серверов — в статье [конфигурация HTTP/2 и HTTP/3 в Nginx](../../Nginx/Performance/nginx_http_versions.md).

## Определения

**HTTP/2 (Hypertext Transfer Protocol Version 2)** — бинарная версия протокола HTTP (RFC 9113), решающая проблемы HTTP/1.1 через мультиплексирование потоков в рамках одного TCP-соединения.

**HTTP/3 (Hypertext Transfer Protocol Version 3)** — версия протокола на базе транспорта **QUIC** (RFC 9114), работающая поверх UDP. Устраняет задержки на уровне транспорта и обеспечивает мгновенное восстановление соединений.

**Head-of-Line (HOL) Blocking (блокировка начала очереди)** — ситуация, когда задержка одного пакета тормозит всю очередь. В HTTP/2 сохраняется на уровне TCP, в HTTP/3 — полностью устранена.

**0-RTT (Zero Round Trip Time)** — механизм QUIC, позволяющий клиенту отправлять данные (запрос) одновременно с пакетом установки соединения, если они ранее уже взаимодействовали.

## Основные концепции

### Сравнение HTTP/2 и HTTP/3 (Статус 2026)

| Характеристика | HTTP/2 | HTTP/3 |
| :--- | :--- | :--- |
| **Транспорт** | TCP + TLS 1.2/1.3 | **QUIC (UDP)** + TLS 1.3 |
| **Блокировка очереди (HOL)** | Только на уровне TCP | **Отсутствует** |
| **Идентификация** | IP-адрес + Порт | **Connection ID** (Connection Migration) |
| **Сжатие заголовков** | HPACK | QPACK |
| **Приоритезация** | Сложная (деревья весов) | **RFC 9218** (Extensible Prioritization) |
| **Оптимизация загрузки** | Server Push (Deprecated) | **103 Early Hints** |

### Влияние на производительность

- **Устранение HOL-блокировки в HTTP/3:** В сетях с потерями пакетов (Wi-Fi, Mobile) HTTP/3 значительно превосходит HTTP/2. Потеря пакета в одном потоке не влияет на доставку данных в других потоках.
- **Ускорение рукопожатия:** HTTP/3 объединяет транспортное и криптографическое рукопожатие, обеспечивая 1-RTT соединение. Использование **0-RTT** позволяет достичь "мгновенной" загрузки, однако требует настройки защиты от **Replay-атак** на стороне сервера (`ssl_early_data`).
- **Контроль перегрузки:** Современные реализации QUIC (например, в Angie или Nginx) используют алгоритм **BBRv3**, который лучше адаптируется к изменениям пропускной способности, чем традиционный CUBIC в TCP.
- **Производительность UDP:** Обработка QUIC требует больше ресурсов CPU. Для оптимизации в 2026 году массово применяются **eBPF** (директива `quic_bpf`) и **Generic Segmentation Offload (GSO)** для снижения нагрузки на ядро Linux при обработке UDP-пакетов.

### Механизмы обнаружения HTTP/3

1. **Заголовок `Alt-Svc` (Alternative Services):**
   ```http
   Alt-Svc: h3=":443"; ma=86400
   ```
   Основной метод уведомления браузера о поддержке QUIC.
2. **HTTPS RR (Resource Record) в DNS:**
   ```dns
   example.com HTTPS 1 . alpn="h2,h3"
   ```
   Позволяет избежать "холодного старта" (первого запроса по HTTP/2), сразу инициируя QUIC-соединение.

## Практические сценарии

### Проверка версии протокола

Для диагностики используйте современные версии `curl` (8.x+):

```bash
# Проверка поддержки HTTP/3 (QUIC)
curl -I --http3 https://example.com/

# Проверка времени рукопожатия и версии
curl -s -o /dev/null --http3 -w "Protocol: %{http_version}\nHandshake: %{time_appconnect}s\n" https://example.com/
```

В Chrome DevTools: вкладка **Network** → колонка **Protocol** (`h3` означает HTTP/3).

### Настройка на стороне сервера

Современная конфигурация требует одновременного слушания портов:
```nginx
server {
    listen 443 ssl;         # TCP для HTTP/1.1 и HTTP/2
    listen 443 quic reuseport; # UDP для HTTP/3
    
    add_header Alt-Svc 'h3=":443"; ma=86400';
    
    # Включение eBPF для маршрутизации QUIC (Angie/Nginx 1.25+)
    quic_bpf on;
}
```

## Дополнительная информация

### Стратегии оптимизации фронтенда (2026+)

- **Отказ от Domain Sharding:** Теперь это критическая ошибка. Создание множества соединений с поддоменами (`static1.`, `static2.`) лишает протоколы возможности эффективно приоритизировать ресурсы и использовать одно окно перегрузки.
- **103 Early Hints:** Вместо нестабильного Server Push используйте код ответа `103`. Он позволяет серверу отправить заголовки `Link: <...>; rel=preload` сразу, пока он генерирует основной HTML-ответ.
- **Миграция соединений (Connection Migration):** В HTTP/3 пользователь может перейти с Wi-Fi на 4G без разрыва сессии, так как соединение привязано к **Connection ID**, а не к IP-адресу. Это критично для мобильных приложений и стриминга.
