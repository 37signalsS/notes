# Web Vitals — ключевые метрики пользовательского опыта

## Definitions

**Web Vitals** — инициатива Google по стандартизации ключевых метрик, отражающих качество пользовательского опыта при загрузке и взаимодействии с веб-страницей.

**Core Web Vitals** — подмножество Web Vitals, используемое Google как сигнал ранжирования в поисковой выдаче. Включает три метрики: LCP, INP, CLS.

**RUM (Real User Monitoring)** — сбор метрик от реальных пользователей в продакшене. Противопоставляется синтетическим тестам (Lab Data).

## Basic Concepts

### Core Web Vitals (основные метрики)

#### Largest Contentful Paint (LCP)

**Что измеряет:** время от начала загрузки до отрисовки самого большого видимого элемента контента (изображение, видео-постер, текстовый блок) в области просмотра. Отражает воспринимаемую скорость загрузки основного содержимого.

**Пороговые значения:**

| Оценка | Значение |
| :--- | :--- |
| Хорошо | < 2.5 с |
| Требует улучшения | 2.5 – 4.0 с |
| Плохо | > 4.0 с |

**Ключевые факторы влияния:** медленный ответ сервера (TTFB), рендер-блокирующие CSS/JS, неоптимизированные изображения, отсутствие кэширования LCP-элемента.

**Оптимизация:** preload критических ресурсов, server-side rendering, HTTP-кэширование, устранение блокирующих ресурсов, оптимизация шрифтов.

#### Interaction to Next Paint (INP)

**Что измеряет:** задержку между взаимодействием пользователя (клик, касание, нажатие клавиши) и следующим визуальным обновлением страницы (paint). Отражает отзывчивость страницы на протяжении всего сеанса, а не только при первом взаимодействии.

**Пороговые значения:**

| Оценка | Значение |
| :--- | :--- |
| Хорошо | < 200 мс |
| Требует улучшения | 200 – 500 мс |
| Плохо | > 500 мс |

**История:** INP заменила FID (First Input Delay) в марте 2024 года. FID измеряла только первое взаимодействие, INP измеряет все взаимодействия на протяжении сеанса и берёт наихудший результат (обычно 98-й перцентиль).

**Порог восприятия:** задержка < 100 мс воспринимается пользователем как мгновенная реакция.

**Ключевые факторы влияния:** длительные задачи JavaScript (Long Tasks > 50 мс), тяжёлый основной поток, сложные пересчёты макета (layout thrashing).

**Оптимизация:** разделение Long Tasks, web workers для тяжёлых вычислений, debouncing/throttling обработчиков событий, минимизация layout thrashing.

#### Cumulative Layout Shift (CLS)

**Что измеряет:** совокупную величину всех неожиданных сдвигов элементов макета за время жизни страницы. Оценивает визуальную стабильность — насколько сильно «прыгают» элементы во время загрузки и работы.

**Пороговые значения:**

| Оценка | Значение |
| :--- | :--- |
| Хорошо | < 0.1 |
| Требует улучшения | 0.1 – 0.25 |
| Плохо | > 0.25 |

**Расчёт:** каждый сдвиг оценивается как произведение доли сдвинутой области экрана на расстояние сдвига. CLS — сумма всех индивидуальных оценок сдвигов.

**Ключевые факторы влияния:** изображения/видео без явных размеров `width`/`height`, динамически подгружаемый контент (реклама, встраивания, баннеры), шрифты с FOIT/FOUT, анимации, меняющие layout.

**Оптимизация:** явные размеры для медиа-элементов, резервирование места для динамического контента, `font-display: optional` или `swap`, анимации через `transform`/`opacity` вместо изменения геометрии.

### Дополнительные метрики (Lab Data)

#### First Contentful Paint (FCP)

Время от начала загрузки до отрисовки первого элемента контента (текст, изображение, SVG, не-белый `<canvas>`). Отражает начальное восприятие скорости загрузки.

**Пороговые значения:** хорошо < 1.8 с, требует улучшения 1.8 – 3.0 с, плохо > 3.0 с.

#### Total Blocking Time (TBT)

Суммарное время блокировки основного потока между FCP и Time to Interactive. Блокировкой считается участок выполнения задачи свыше 50 мс (Long Task). TBT = сумма (длительность задачи − 50 мс) для всех Long Tasks.

**Пороговые значения:** хорошо < 200 мс, требует улучшения 200 – 600 мс, плохо > 600 мс.

**Связь с INP:** высокий TBT коррелирует с высоким INP — оба показателя страдают от Long Tasks JavaScript.

#### Time to Interactive (TTI)

Время от начала загрузки до момента, когда страница становится полностью интерактивной: отображается видимый контент, обработчики событий зарегистрированы, страница отвечает на взаимодействия в пределах 50 мс.

TTI — лабораторная метрика, не входит в Core Web Vitals. Не измеряется в RUM.

#### Speed Index

Интегральный показатель, отражающий скорость визуального заполнения области просмотра контентом во время загрузки. Рассчитывается на основе видеозаписи загрузки страницы: чем быстрее контент заполняет экран, тем ниже (лучше) Speed Index.

**Пороговые значения:** хорошо < 3.4 с, требует улучшения 3.4 – 5.8 с, плохо > 5.8 с.

### Оценка производительности («попугаи» / Performance Score)

Обобщённая оценка от 0 до 100, рассчитываемая Lighthouse как взвешенная сумма метрик. Веса метрик могут меняться между версиями Lighthouse.

**Влияние метрик на оценку (Lighthouse 12+):**

| Метрика | Вес |
| :--- | :--- |
| LCP | 22% |
| INP | 22% |
| CLS | 15% |
| TBT | 15% |
| FCP | 10% |
| Speed Index | 10% |
| Остальные | 6% |

Калькулятор весов метрик доступен в репозитории Lighthouse. Оценка полезна для быстрого сравнения, но не заменяет анализ отдельных метрик.

## Practical Scenarios

### Измерение метрик в продакшене (RUM)

1. **Chrome UX Report (CrUX)** — публичный датасет реальных метрик пользователей Chrome. Доступен через BigQuery и [PageSpeed Insights API](./pagespeed_insights.md).
2. **web-vitals JS-библиотека** — отправка метрик в вашу аналитику:

```javascript
import {onLCP, onINP, onCLS} from 'web-vitals';

onLCP(console.log);
onINP(console.log);
onCLS(console.log);
```

1. **Google Analytics 4** — встроенная поддержка Web Vitals через web-vitals library + GA4 custom events.

### Локальная диагностика через Chrome DevTools

1. Откройте DevTools (`F12`) → вкладка **Performance** → включите **Disable Cache** и **CPU Throttling 4x**.
2. Нажмите **Record**, перезагрузите страницу, выполните сценарий взаимодействия.
3. Остановите запись — в верхней части профиля отображаются метрики Web Vitals (LCP, CLS, FCP, INP, TTI).
4. Кликните по метрике — DevTools подсветит соответствующий элемент на таймлайне.

Подробно: [Chrome DevTools — вкладка Performance](./chrome_devtools.md).

### Приоритизация исправлений

| Проблема | Влияние | Приоритет |
| :--- | :--- | :--- |
| LCP > 2.5 с | Восприятие загрузки | Высокий |
| INP > 200 мс | Интерактивность | Высокий |
| CLS > 0.1 | Визуальная стабильность | Высокий |
| TBT > 200 мс | Время до интерактивности | Средний |
| FCP > 1.8 с | Первичное восприятие | Средний |
| Speed Index > 3.4 с | Общая скорость рендеринга | Средний |

### Типичные проблемы и решения

| Проблема | Метрика | Решение |
| :--- | :--- | :--- |
| Медленный ответ сервера | LCP, FCP | Кэширование, CDN, оптимизация бэкенда |
| Рендер-блокирующий JS/CSS | LCP, FCP | `async`/`defer`, inline critical CSS |
| Неоптимизированные изображения | LCP | WebP/AVIF, responsive images, `preload` LCP-элемента |
| Long Tasks JavaScript | INP, TBT | Code splitting, web workers, оптимизация обработчиков |
| Сдвиги от рекламы/встраиваний | CLS | Резервирование места, `aspect-ratio` |
| Шрифты без резервирования | CLS, LCP | `font-display: swap`, `preload` шрифтов |

## Additional Information

### Взаимосвязь метрик

```
Загрузка:   FCP → LCP → TTI
                   ↓
Интерактив:        INP (на протяжении сеанса)
                   ↑
Блокировки:       TBT (влияет на INP)

Визуальная стабильность: CLS (независима, может происходить в любой момент)
```

### Lab Data vs Field Data

| Характеристика | Field Data (RUM) | Lab Data (синтетика) |
| :--- | :--- | :--- |
| Источник | Реальные пользователи | Один запуск с контролируемого окружения |
| Метрики | LCP, INP, CLS (Core Web Vitals) | LCP, INP, CLS, FCP, TBT, TTI, Speed Index |
| Воспроизводимость | Нет (агрегированные данные) | Да (повторяемый тест) |
| Влияние на SEO | Да (CrUX) | Нет (но помогает диагностике) |
| Инструменты | CrUX, RUM-системы | Lighthouse, DevTools, [WebPageTest](./webpagetest.md) |

### Рекомендации

- **Ориентируйтесь на Field Data** для оценки реального пользовательского опыта и SEO.
- **Используйте Lab Data** для диагностики и проверки исправлений до деплоя.
- **Пороги могут обновляться** — отслеживайте публикации на [web.dev/blog](https://web.dev/blog/).
- **Динамический контент** (слайдеры, бесконечная лента) может искажать LCP — каждый новый слайд воспринимается как новый LCP-элемент.
