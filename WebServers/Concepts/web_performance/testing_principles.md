# Принципы тестирования производительности

## Определения

**Синтетическое тестирование производительности (Synthetic Testing / Lab Data)** — метод оценки скорости загрузки и интерактивности веб-страниц в контролируемой, воспроизводимой среде. Основная цель — получение стабильных результатов для сравнения различных конфигураций или версий кода.

**RUM (Real User Monitoring / Field Data)** — сбор метрик производительности непосредственно от реальных пользователей в продуктивной среде. Отражает реальный опыт, но зависит от множества неконтролируемых факторов (устройство, сеть, кэш).

**Холодная загрузка (Cold Load)** — первая загрузка страницы без использования кэша браузера. Демонстрирует «худший случай» и является основным сценарием для тестирования оптимизаций.

**Тёплая загрузка (Warm Load)** — повторная загрузка с использованием закэшированных ресурсов. Используется для оценки эффективности стратегий кэширования и работы Service Workers.

## Основные концепции

### Использование реальных браузеров

Тестирование должно проводиться в реальных браузерах или на движках, максимально приближенных к пользовательским.

* **Blink (Chrome, Edge, Brave):** приоритетный движок из-за доминирующей доли рынка и развитых инструментов отладки.
* **Gecko (Firefox):** необходим для проверки кроссбраузерной совместимости производительности.
* **WebKit (Safari):** критичен для мобильного сегмента (iOS).

### Эмуляция сетевых условий

Для выявления узких мест необходимо эмулировать реалистичные, а не идеальные условия сети. Использование «безлимитного» гигабитного канала скрывает задержки, связанные с установкой соединений и размером ресурсов.

**Стандартный профиль "Fast 3G" (или "4G Slow"):**

| Параметр | Значение |
| :--- | :--- |
| Downlink (загрузка) | ~1.6 Mbps |
| Uplink (отдача) | ~0.75 Mbps |
| RTT (задержка) | ~150 мс |

Этот профиль делает наглядными задержки при установке DNS, TCP и TLS-соединений, а также влияние количества HTTP-запросов.

### Тестирование мобильных устройств

Большинство современных пользователей заходят с мобильных устройств, которые значительно слабее десктопов.

* **Viewport:** уменьшенный размер области просмотра влияет на то, какие ресурсы браузер считает критическими.
* **CPU Throttling:** искусственное замедление процессора (обычно в 4–6 раз) необходимо для имитации устройств среднего и бюджетного сегментов. Без замедления JavaScript-метрики (например, INP или TBT) на мощных рабочих станциях разработчиков всегда будут выглядеть «зелёными».

### Обеспечение повторяемости результатов

Без повторяемости результатов тестирование бесполезно для сравнения. Факторы, вносящие шум:

* Фоновые процессы в ОС, потребляющие CPU или сеть.
* Динамический контент на странице (слайдеры, сторонние виджеты).
* Нестабильное время ответа бэкенда (TTFB).

**Рекомендация:** проводить серию из 3–5 прогонов и использовать медианный результат (Median), а не среднее арифметическое, чтобы исключить влияние случайных выбросов.

### Условия «чистого» тестирования

| Требование | Обоснование |
| :--- | :--- |
| **Отключение кэша** | Гарантирует симуляцию холодной загрузки. |
| **Режим инкогнито** | Исключает влияние браузерных расширений (AdBlock и др.), которые могут искажать метрики. |
| **Изоляция DevTools** | Вынос панели инструментов в отдельное окно предотвращает её влияние на размер Viewport страницы. |
| **Отключение сторонних скриптов** | Счётчики аналитики и рекламные пиксели могут блокировать основной поток и искажать результаты отладки. |

## Практические сценарии

### Сценарий 1: Базовый аудит перед релизом

1. Открыть Chrome DevTools (`F12`), вынести панель в отдельное окно.
2. Включить эмуляцию мобильного устройства (Device Toolbar).
3. Установить Network Throttling на **Fast 3G** и CPU Throttling на **4x**.
4. Включить опцию **Disable Cache** во вкладке Network.
5. Выполнить перезагрузку и зафиксировать метрики Core Web Vitals (LCP, INP, CLS).
6. Сравнить полученные данные с установленными порогами: **[Метрики Web Vitals](./web_vitals.md)**.

### Сценарий 2: Сравнение эффективности оптимизаций

1. Провести замер «До» изменений (3–5 прогонов, взять медиану).
2. Применить оптимизацию (например, включить сжатие Brotli или оптимизировать изображения).
3. Провести замер «После» в **строго идентичных условиях**.
4. Оценить изменение метрик: ΔLCP (время), ΔSize (объем данных), ΔRPS (нагрузка на сервер).

### Сценарий 3: Тестирование отказоустойчивости (SPOF)

**SPOF (Single Point of Failure)** — единая точка отказа.

1. Идентифицировать критические внешние зависимости (CDN со шрифтами, JS-библиотеки).
2. Заблокировать запрос к домену зависимости через `Network Request Blocking` в Chrome DevTools.
3. Проверить, остается ли страница функциональной и не блокируется ли отрисовка основного контента.

## Дополнительная информация

### Ограничения синтетического тестирования

* **Не заменяет RUM:** лабораторный тест показывает контролируемый сценарий, но не учитывает разнообразие устройств реальных пользователей.
* **Эмуляция против реальности:** Lighthouse эмулирует сетевые ограничения через пересчёт, что менее точно, чем реальное ограничение канала в [WebPageTest](./webpagetest.md).
* **Интерпретация советов:** рекомендации автоматических инструментов (Lighthouse) требуют критического осмысления. Например, инлайнинг всего CSS ускоряет первый запуск, но убивает кэширование при повторных визитах.

### Сравнение инструментов

| Инструмент | Преимущества | Ограничения |
| :--- | :--- | :--- |
| **[Chrome DevTools](./chrome_devtools.md)** | Быстрая локальная отладка, полный контроль. | Привязка к локальной машине и провайдеру. |
| **[WebPageTest](./webpagetest.md)** | Географически распределенные тесты, реальные устройства. | Более сложная настройка. |
| **[PageSpeed Insights](./pagespeed_insights.md)** | Быстрый доступ к данным CrUX (RUM) и Lighthouse. | Один запуск в облаке Google без гибких настроек. |
