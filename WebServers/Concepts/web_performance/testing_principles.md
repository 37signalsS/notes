# Принципы тестирования производительности

## Definitions

**Синтетическое тестирование производительности** — метод оценки скорости загрузки и интерактивности веб-страниц в контролируемой, воспроизводимой среде. Отличается от RUM (Real User Monitoring) — сбора метрик от реальных пользователей.

**Холодная загрузка (cold load)** — первая загрузка страницы без использования кэша браузера. Основной сценарий для тестирования, так как демонстрирует худший случай.

**Тёплая загрузка (warm load)** — повторная загрузка с использованием кэшированных ресурсов. Используется для оценки эффективности стратегий кэширования.

## Basic Concepts

### Реальный браузер

Тестирование должно проводиться в реальном браузере. Основные движки:

* **Blink** (Chrome, Edge, Яндекс Браузер) — приоритетный из-за максимальной доли рынка.
* **Gecko** (Firefox)
* **WebKit** (Safari)

### Сетевые условия

Необходимо эмулировать реалистичные, но не идеальные условия сети. Стандартный профиль — **"Fast 3G"** (или "4G Slow"):

| Параметр | Значение |
| :--- | :--- |
| Downlink | ~1.5–1.6 Mbps |
| Uplink | ~0.75–0.8 Mbps |
| RTT (задержка) | ~150 мс |

Этот профиль делает сетевую составляющую наглядной, выявляя узкие места: время установки соединений (DNS, TCP, TLS), размер ресурсов, количество запросов.

### Эмуляция мобильных устройств

Большинство тестов следует проводить в режиме эмуляции мобильного устройства:

* **Уменьшенный viewport** — влияет на приоритизацию загрузки ресурсов браузером.
* **CPU throttling** — замедление процессора в 4–6 раз, симулирующее слабые мобильные устройства.

### Повторяемость

Обеспечение идентичных сетевых условий и среды тестирования критично для сравнения результатов «до» и «после» оптимизации. Без повторяемости тестирование бесполезно.

**Факторы, снижающие повторяемость:**

* Фоновые процессы, потребляющие CPU/сеть.
* Изменения в контенте страницы (динамический контент, слайдеры).
* Варьирующееся время ответа бэкенда.

**Рекомендация:** проводить 3–5 прогонов и использовать медианный результат.

### Чистота теста

| Требование | Причина |
| :--- | :--- |
| **Отключение кэша** | Симуляция холодной загрузки |
| **Режим инкогнито** | Исключение влияния сторонних расширений |
| **Вынос DevTools в отдельное окно** | Панель DevTools не влияет на viewport тестируемой страницы |
| **Отключение сторонних скриптов** | Счётчики аналитики искажают метрики (блокируют основной поток, добавляют сетевые запросы) |

## Practical Scenarios

### Сценарий: базовый аудит перед релизом

1. Откройте Chrome DevTools (`F12`), вынесите в отдельное окно.
2. Включите эмуляцию мобильного устройства (Device Toolbar).
3. Установите Network Throttling: **Fast 3G**, CPU Throttling: **4x**.
4. Включите **Disable Cache**.
5. Перезагрузите страницу, зафиксируйте метрики: LCP, FCP, CLS, INP.
6. Повторите 3 раза, запишите медианные значения.
7. Сравните с целевыми показателями ([Web Vitals](./web_vitals.md)).

### Сценарий: сравнение «до» и «после» оптимизации

1. Зафиксируйте текущие метрики (медиана из 3 прогонов).
2. Внесите изменения (сжатие изображений, code splitting, кэширование).
3. Проведите тест в **идентичных условиях** (тот же профиль сети, CPU throttling, отключённый кэш).
4. Сравните метрики: ΔLCP, ΔFCP, ΔCLS, общий объём загруженных данных.
5. Задокументируйте результат для команды.

### Сценарий: выявление проблемы на сервере (высокий TTFB)

1. Откройте вкладку Network, отсортируйте по Waterfall.
2. Найдите документ (type: Doc), проверьте TTFB.
3. Если TTFB > 600 мс — проблема на стороне бэкенда (медлый запрос к БД, отсутствие кэша, перегруженный сервер).
4. Подтвердите диагностику на сервере (логи, метрики CPU/памяти, slow query log).
5. После оптимизации бэкенда повторите тест.

### Сценарий: тестирование отказоустойчивости (SPOF)

1. Определите критические сторонние ресурсы (CDN, аналитика, рекламные скрипты).
2. Заблокируйте домен ресурса (Network Request Blocking в DevTools или hosts-файл).
3. Перезагрузите страницу — сайт остаётся функциональным?
4. Если нет — выявлена критическая зависимость, требующая fallback-механизма.

## Additional Information

### Ограничения синтетического тестирования

* **Не заменяет RUM.** Синтетика показывает контролируемый сценарий, а не реальный опыт пользователей с разнообразными устройствами и сетями.
* **Lighthouse эмулирует сеть пересчётом**, а не реальным ограничением — результаты менее точны, чем у [WebPageTest](./webpagetest.md).
* **Динамический контент** (слайдеры, бесконечная прокрутка) может искажать метрики LCP.
* **Рекомендации Lighthouse требуют интерпретации:** инлайнинг всего CSS ухудшает кэширование; не все «opportunities» дают реальный выигрыш.

### Инструменты и их роль

| Инструмент | Сильные стороны | Ограничения |
| :--- | :--- | :--- |
| [Chrome DevTools](./chrome_devtools.md) | Локальная отладка, реальный контроль над ресурсами | Одна локация, один браузер |
| [WebPageTest](./webpagetest.md) | Множество локаций, эмуляция потери пакетов, API для CI/CD | Требует настройки, сложнее в использовании |
