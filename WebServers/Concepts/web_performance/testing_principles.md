# Принципы тестирования производительности веб-приложений

## Определения

**Синтетическое тестирование (Synthetic Testing / Lab Data)** — оценка производительности в контролируемой, изолированной среде (лабораторные данные). Позволяет воспроизводить условия, выявлять регрессии и сравнивать версии кода или конфигурации серверов без влияния внешнего «шума». Основные инструменты: Lighthouse, WebPageTest, Chrome DevTools.

**Мониторинг реальных пользователей (Real User Monitoring, RUM / Field Data)** — сбор метрик непосредственно из браузеров реальных посетителей (полевые данные). Отражает реальный опыт с учетом разнообразия устройств, качества связи (от 3G до 5G/Fiber) и географии. Основной источник: Chrome User Experience Report (CrUX) или кастомные JS-агенты.

**Холодная загрузка (Cold Load)** — загрузка страницы при полностью очищенном кэше (браузера, DNS, сокетов). Критична для оценки первого впечатления нового пользователя.

**Тёплая загрузка (Warm Load)** — повторная загрузка с использованием ресурсов из локального кэша и Service Workers. Позволяет проверить эффективность политик кэширования и мультиплексирования HTTP/2/3.

**TBT (Total Blocking Time)** — время, в течение которого основной поток (Main Thread) заблокирован длинными задачами (Long Tasks > 50 мс), что мешает реакции на ввод пользователя. Ключевая лабораторная метрика, коррелирующая с INP.

## Основные концепции

### Лабораторные vs Полевые данные (Lab vs Field)

Эффективная стратегия тестирования 2026 года требует комбинирования обоих подходов:
- **Lab Data:** используется для отладки и предотвращения регрессий в CI/CD. Показывает *потенциальную* скорость.
- **Field Data:** используется для принятия бизнес-решений и оценки влияния на SEO (Core Web Vitals). Показывает *реальный* опыт.

### Эмуляция условий (Throttling)

Тестирование на мощных рабочих станциях без ограничений искажает реальную картину. Необходимо использовать механизмы замедления:

1.  **Сетевой троттлинг (Network Throttling):**
    - **Browser-level (DevTools):** Имитация задержек на уровне прикладного уровня. Проста в использовании, но не учитывает особенности TCP/QUIC.
    - **Packet-level (WebPageTest):** Формирование трафика (Traffic Shaping) на уровне сетевых пакетов. Максимально точно имитирует потерю пакетов и реальный RTT.

2.  **Процессорный троттлинг (CPU Throttling):**
    - Имитация бюджетных устройств путем замедления CPU в **4x** (средний сегмент) или **6x** (low-end). Это критично для выявления проблем парсинга DOM и выполнения JavaScript, которые незаметны на десктопах.

**Стандартные профили 2026:**
| Профиль | RTT | Downlink | Назначение |
| :--- | :--- | :--- | :--- |
| **Good 5G / Fiber** | < 20 мс | 100+ Mbps | Идеальные условия. |
| **Fast 4G** | 40 мс | 9 Mbps | Городской мобильный интернет. |
| **Slow 4G / 3G** | 150+ мс | 1.6 Mbps | Нестабильное покрытие, роуминг. |

### Повторяемость и статистическая значимость

Результаты одиночного теста нестабильны из-за фоновых процессов ОС и вариативности сети.
- **Серии прогонов:** Минимум 3–5 последовательных тестов.
- **Медиана (Median):** Использование медианного значения вместо среднего арифметического позволяет исключить влияние аномальных выбросов.
- **Изоляция:** При локальном тестировании необходимо закрывать посторонние вкладки, мессенджеры и отключать расширения браузера (использовать режим Incognito).

### Профессиональная диагностика через Performance API

Современные браузеры предоставляют низкоуровневые данные через `window.performance`:
- **Navigation Timing API:** Точные метрики фаз (DNS lookup, TCP handshake, Request/Response time).
- **Resource Timing API:** Детальная информация о загрузке каждого ресурса.
- **User Timing API:** Возможность размечать пользовательские события в коде (`performance.mark()`), которые отображаются в профилировщике.

## Практические сценарии

### Сценарий 1: Проверка TTFB и серверной задержки

Для понимания, на какой стороне (Back-end или Network) происходит задержка, используйте заголовок **Server-Timing**.

1.  Бэкенд отправляет заголовок: `Server-Timing: db;dur=52.3, app;dur=27.2`.
2.  В Chrome DevTools (вкладка **Network**) при клике на ресурс в разделе **Timing** отобразятся эти серверные метрики.
3.  **Анализ:** Если TTFB высокий, а `Server-Timing` показывает низкие значения — проблема в сетевой инфраструктуре или TLS-хендшейке.

### Сценарий 2: Тестирование единой точки отказа (SPOF)

Зависимость от сторонних CDN (шрифты, скрипты аналитики) может заблокировать отрисовку страницы при их сбое.

1.  Используйте функцию **Network Request Blocking** в DevTools.
2.  Заблокируйте домены внешних ресурсов (например, `fonts.googleapis.com`).
3.  Перезагрузите страницу и проверьте: не «зависла» ли она белым экраном до таймаута (30+ секунд).
4.  **Решение:** Настройка локального хостинга критичных ресурсов или использование `font-display: swap`.

### Сценарий 3: Автоматизация в CI/CD (Lighthouse CI)

Для предотвращения попадания медленного кода в продакшн:

1.  Настройте **Lighthouse CI** в пайплайне.
2.  Установите пороги (assertions) для Core Web Vitals.
3.  **Пример конфигурации (`.lighthouserc.js`):**
```javascript
module.exports = {
  ci: {
    assert: {
      assertions: {
        'categories:performance': ['error', {minScore: 0.9}],
        'largest-contentful-paint': ['error', {maxNumericValue: 2500}],
      },
    },
  },
};
```
