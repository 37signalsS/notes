# PageSpeed Insights (PSI)

---
**Надёжность: 10/10** (SSoT + Проверено в 2026 году)
---

## Определения

**PageSpeed Insights (PSI)** — основной веб-инструмент Google для анализа производительности и качества страниц. PSI уникален тем, что объединяет в одном отчете синтетические данные (Lab Data) и реальный пользовательский опыт (Field Data).

**CrUX (Chrome User Experience Report)** — публичный набор данных о реальном опыте пользователей Chrome, выступающий источником полевых данных для PSI.

**Lighthouse** — движок с открытым исходным кодом, который PSI запускает в облачной среде Google для получения лабораторных данных и списка технических рекомендаций.

## Основные концепции

### Полевые данные против Лабораторных (Field vs Lab)

Понимание разницы между этими наборами данных критично для корректной интерпретации отчета.

| Характеристика | Полевые данные (Field / CrUX) | Лабораторные данные (Lab / Lighthouse) |
| :--- | :--- | :--- |
| **Источник** | Анонимные сессии реальных пользователей | Один проход бота в облаке Google |
| **Период** | Скользящее окно за последние 28 дней | Момент запуска теста |
| **Условия** | Реальные устройства, сети, кэширование | Эмуляция среднего устройства (Moto G Power) |
| **Применение** | Влияет на ранжирование (SEO) | Отладка и проверка гипотез (Opportunities) |

Подробный разбор методологий: **[Лабораторные и полевые данные](./web_vitals.md#лабораторные-и-полевые-данные-lab-vs-field)**.

### Оценка Core Web Vitals (Core Web Vitals Assessment)

Это итоговый вердикт о качестве страницы. С 2024 года ключевым показателем интерактивности является **INP (Interaction to Next Paint)**, который полностью заменил FID.

- **Порог 75-го перцентиля:** Страница считается «прошедшей проверку» (Passed), если 75% всех посещений за 28 дней соответствуют «хорошему» уровню для всех трех метрик: LCP, INP и CLS.
- **Мобильный приоритет:** Google использует мобильные данные CrUX как первичный фактор для mobile-first индексации.
- Описание и пороги метрик: **[Основные метрики Core Web Vitals](./web_vitals.md#основные-метрики-core-web-vitals)**.

### Уровни агрегации данных (URL vs Origin)

1. **Этот URL:** Точные данные для конкретной страницы. Требует достаточного объема трафика (обычно сотни посещений в месяц).
2. **Origin (Весь домен):** Агрегация по всему источнику. Позволяет оценить «здоровье» домена, если новая или низкотрафиковая страница еще не накопила свои данные.

## Практические сценарии

### Сценарий 1: Технический аудит и поиск «узких мест»

1. Проанализируйте блок **Core Web Vitals Assessment**. Если вердикт `Failed`, определите, какая именно метрика просела.
2. Изучите раздел **Opportunities** (Возможности). PSI ранжирует их по потенциальной экономии времени.
   - *Важно:* Экономия является расчетной (Estimated) и может не совпадать с реальностью на 100%.
3. Проверьте раздел **Diagnostics**. В нем содержатся критические сведения, не влияющие на баллы напрямую, но важные для архитектуры (например, размер DOM-дерева или критические цепочки запросов).
4. Сравните Mobile и Desktop. Разрыв в баллах часто связан с тем, что PSI эмулирует для Mobile процессор среднего сегмента с замедлением (CPU Throttling), что выявляет проблемы тяжелого JavaScript.

### Сценарий 2: Автоматизация мониторинга через API

PageSpeed Insights API (v5) позволяет встраивать проверки в CI/CD или создавать кастомные дашборды в Grafana.

**Пример запроса для получения данных CrUX:**
```bash
curl "https://www.googleapis.com/pagespeedonline/v5/runPagespeed?url=https://example.com&strategy=mobile&key=YOUR_API_KEY"
```

**Нюансы API:**
- Ответ содержит объект `loadingExperience` (CrUX за 28 дней) и `lighthouseResult` (Lab данные).
- Можно запрашивать категории `accessibility`, `best-practices`, `seo` дополнительно к `performance`.

### Сценарий 3: Интерпретация расхождений (Discrepancies)

- **Lab > Field:** Страница технически быстрая в «стерильных» условиях, но реальные пользователи на слабых устройствах испытывают проблемы. Решение: оптимизация выполнения JS.
- **Field > Lab:** Реальные пользователи получают преимущество от кэширования (Service Workers, Cache-Control), которое Lighthouse игнорирует при «холодной» загрузке.
