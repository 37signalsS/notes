# Диагностика веб-серверов (Troubleshooting)

## Определения

**Troubleshooting (Поиск и устранение неисправностей)** — систематический процесс выявления, анализа и устранения причин, препятствующих корректной работе веб-сервера (Nginx, Angie, Apache) или связанных с ним сервисов.

**Post-reboot failure (Сбой после перезагрузки)** — частный случай Troubleshooting, при котором сервис работал до перезагрузки ОС, но не запустился после неё из-за проблем с автозапуском, монтированием дисков или зависимостями.

## Основные концепции

### Универсальный алгоритм диагностики

При возникновении проблем с веб-сервером следуйте методу «от простого к сложному»:

1.  **Локализация и проверка статуса:** Запущен ли процесс и на каком узле проблема?
2.  **Валидация конфигурации:** Нет ли синтаксических ошибок в файлах настроек?
3.  **Анализ логов:** Что сообщает сам сервер в `error.log` и системный журнал `journalctl`?
4.  **Проверка системных ресурсов:** Хватает ли памяти, места на диске и свободных дескрипторов?
5.  **Проверка сетевой связности:** Слушает ли сервер порт и не блокирует ли трафик файрвол?
6.  **Проверка прав и безопасности:** Разрешен ли доступ к файлам на уровне ФС и политик SELinux/AppArmor?

> **Предупреждение:** преждевременный `restart` сервиса стирает часть диагностических следов (состояние процессов, открытые сокеты, содержимое памяти) и может превратить частичную аварию в полную. Сначала локализуйте стадию сбоя, соберите состояние (`status`, логи, сокеты) и применяйте `reload` после проверки конфигурации — он перечитывает конфиг без остановки старых воркеров.

### Локализация стадии сбоя (со стороны клиента)

Жалоба «сайт не открывается» не локализует проблему. Сначала проверьте сайт из другой сети: если проблема воспроизводится только с одного места, причина может быть в локальном DNS-кеше, записи в `/etc/hosts`, блокировке адреса или маршруте провайдера. Если жалуются все — воспроизводите с клиента через `curl`:

```bash
curl -v --connect-timeout 5 --max-time 15 https://example.com/
```

`--connect-timeout 5` ограничивает ожидание TCP-соединения, `--max-time 15` — общее время запроса. Вывод показывает последнюю успешно пройденную стадию, что сразу сужает область поиска:

| Наблюдение в выводе | Стадия обрыва | Где искать |
| :--- | :--- | :--- |
| `Could not resolve host` | DNS | Резолверы, A/AAAA-записи, `/etc/resolv.conf`. |
| Нет строки `Connected to` | TCP | Маршрут, файрвол, недоступность хоста. |
| TCP установлен, висит handshake | TLS | Сертификаты, версии/наборы TLS, SNI. |
| Запрос ушел, ответа нет до `--max-time` | Приложение | Прокси, приложение, его зависимости, БД. |

Дополнительные различения:

- **Мгновенный `Connection refused`** — на порту никто не слушает, либо фильтр ответил отказом (REJECT).
- **Тайм-аут** — чаще DROP-правило, проблема маршрута или зависание на поздней стадии. Одной строки ошибки мало — анализируйте весь вывод.
- **HTTP-коды** также сужают поиск: `502` — шлюз получил некорректный ответ от upstream; `504` — не дождался ответа вовремя; `503` — временная недоступность или перегрузка (может прийти как от прокси, так и от приложения). Подробнее: [Коды состояния HTTP](../../Networking/Protocols/HTTP/http_status_codes.md).

Отдельно сравните протоколы — расхождение указывает на сломанную AAAA-запись, маршрутизацию IPv6 или неслушающий сокет:

```bash
curl -4 -v --connect-timeout 5 --max-time 15 https://example.com/
curl -6 -v --connect-timeout 5 --max-time 15 https://example.com/
```

## Практические сценарии

### Сценарий 1: Синтаксис и конфигурация

Любые изменения должны проверяться перед применением. Если сервер не стартует после правки конфига, это первое, что нужно проверить.

```bash
# Nginx / Angie
sudo nginx -t

# Apache
sudo apachectl configtest
```

### Сценарий 2: Ошибки памяти (OOM-killer)

Если процесс веб-сервера внезапно исчезает или падает с ошибкой `Out of memory`, возможно, его завершил механизм защиты ядра.

**Диагностика:**
```bash
# Поиск событий OOM в системном логе
sudo dmesg -T | grep -i oom
# Или через journalctl
sudo journalctl -k | grep -i oom
```
**Решение:** Оптимизировать потребление памяти (например, уменьшить количество worker-процессов) или добавить RAM/Swap.

### Сценарий 3: Ресурсы ОС (Диск и дескрипторы)

Веб-сервер может работать некорректно, если не может записывать логи или создавать временные файлы.

**1. Переполнение диска или Inodes:**
```bash
df -h    # Проверка места
df -i    # Проверка свободных inodes (актуально при обилии мелких файлов)
```

Если закончились inode, свободное место на диске не поможет — система не сможет создать новый файл. Типичная причина — каталоги с множеством мелких файлов: кэш, сессии, очереди.

При заполненной ФС выясните, какой каталог занял место:

```bash
sudo du -xhd1 /var 2>/dev/null | sort -h
```

`-x` не дает `du` переходить на другие файловые системы, `-d1` ограничивает анализ каталогами первого уровня; далее изучите самый крупный каталог.

Расхождение показаний `df` и `du` возникает, когда файл удален из каталога, но процесс продолжает держать его открытым: имени у файла больше нет и `du` его не видит, однако блоки учитываются в `df`. Найти такие файлы:

```bash
sudo lsof +L1
```

Место освободится, когда процесс закроет файл; завершать процесс вслепую не стоит. Подробнее: [Диагностика дискового пространства](../../Linux/FileSystems/disk_space_troubleshooting.md).

**2. Лимиты на открытые файлы (Too many open files):**
При высокой нагрузке сервер может упереться в системные лимиты.
```bash
# Проверка текущих лимитов процесса
cat /proc/$(pgrep -n nginx)/limits | grep "Max open files"
```
**Решение:** Настроить `worker_rlimit_nofile` в конфиге Nginx или `LimitNOFILE` в unit-файле systemd.

**3. Память и I/O:** Если процессы на месте, но запросы висят:
```bash
free -h        # прежде всего available
vmstat 1 5     # si/so: постоянный свопинг при низком available = нехватка RAM
# Первая строка vmstat — средние с момента загрузки, актуальную картину дают последующие

# Поиск OOM-событий (-g доступен с systemd 237)
sudo journalctl -k -g 'oom|out of memory|killed process'
# На старых systemd:
sudo journalctl -k --no-pager | grep -Ei 'oom|out of memory|killed process'
```
Записи `Killed process` подтверждают работу OOM Killer (подробнее: [Диагностика OOM Killer](../../Linux/Core/processes/oom_killer_diagnostics.md)).

Высокий load average при свободном CPU чаще связан не с вычислениями, а с процессами в состоянии **D**, ожидающими диск, NFS или другой I/O (диагностика: [Практические сценарии мониторинга процессов](../../Linux/Core/processes/practical_scenarios.md)). На виртуальной машине проверяйте `%st` в `top`: высокие значения означают, что гипервизор регулярно забирает процессорное время у гостевой системы (CPU steal).

### Сценарий 4: Права доступа и SELinux (403 Forbidden)

Если права на файлы (`chmod 644`) и владельцы (`chown`) верны, но сервер выдает 403 ошибку, причина может быть в системе безопасности.

**Диагностика SELinux:**
```bash
# Проверка текущего режима
getenforce

# Просмотр логов аудита (если SELinux в режиме Enforcing)
sudo ausearch -m avc -ts recent
```
**Решение:** Использовать `restorecon` для исправления контекстов или `setsebool` для разрешения сетевых соединений.

> **Подробнее:** [Почему chmod 777 не всегда решает проблему](../../Linux/Security/Concepts/File_Permissions/overview_definitions.md#диагностика-почему-chmod-777-не-всегда-решает-проблему) — глубокая диагностика и чек-лист.

### Сценарий 5: Сбои после перезагрузки

Если после рестарта сервер не работает:

**1. Проверка автозагрузки:**
```bash
systemctl is-enabled nginx
# Если disabled, включить:
sudo systemctl enable nginx
```

**2. Проверка монтирования дисков:**
Если корень сайта или логи находятся на внешнем томе, проверьте `/etc/fstab`.
```bash
sudo mount -a    # Попытка примонтировать все из fstab
```

**3. Отложенный старт зависимостей:**
Если веб-сервер стартует раньше базы данных или сетевого хранилища, используйте директивы `After=` и `Requires=` в unit-файле systemd.

### Сценарий 6: Сверка DNS и проверка нужного origin

Частый случай: SSH открывают на новый сервер по IP, а домен всё еще указывает на старый адрес; A-запись исправили, AAAA забыли; резолверы держат старый ответ в пределах TTL.

```bash
dig +short A example.com
dig +short AAAA example.com
```

Сравните адреса с реальной схемой: за NAT публичного IP внутри виртуалки его может не быть, а домен за CDN не должен указывать напрямую на origin. Проверить конкретный сервер без правок DNS можно подменой адреса на стороне клиента:

```bash
curl -v \
  --connect-timeout 5 \
  --max-time 15 \
  --resolve example.com:443:203.0.113.10 \
  https://example.com/
```

`--resolve` подменяет IP, сохраняя доменное имя в заголовке `Host` и в SNI. Если обычный запрос падает, а запрос к origin проходит — проблема в DNS, CDN или балансировщике. Обратная оговорка: сервер, принимающий трафик только с адресов CDN, должен отклонить прямой запрос — такой сервер проверяют из разрешенного источника либо через сам CDN.

### Сценарий 7: Разделение аварии — локально работает, снаружи нет

Локальный запрос изолирует веб-сервер от внешнего маршрута. Для HTTP передайте правильный `Host`, для HTTPS — еще и SNI:

```bash
# HTTP: loopback + правильный Host
curl -v --noproxy '*' --max-time 15 http://127.0.0.1/ -H 'Host: example.com'

# HTTPS: SNI через подмену адреса
curl -v --noproxy '*' --max-time 15 --resolve example.com:443:127.0.0.1 https://example.com/
```

`--noproxy '*'` исключает влияние прокси из окружения. Если сертификат заведомо проблемный, разово допустим `-k`; переносить его в мониторинг и рабочие скрипты не следует.

Локальный `200` или ожидаемый редирект означает: веб-сервер корректно обработал запрос с нужными `Host` и SNI через loopback, а проблема находится между клиентом и сервером. Проверка по цепочке:

**1. Файрвол самого сервера.** Сначала определите используемый backend:

```bash
# nftables
sudo nft list ruleset

# iptables: -S показывает только filter текущего семейства,
# для полной картины дампите все таблицы
sudo iptables-save
sudo ip6tables-save
```

Оговорка про Docker: он создает собственные правила для bridge-сетей и публикации портов ([Packet filtering and firewalls](https://docs.docker.com/engine/network/packet-filtering-firewalls/)), и опубликованный порт способен обойти логику `ufw`. Уточните сетевой режим и firewall backend Docker, прежде чем делать выводы о правилах.

**2. Сетевой экран хостера, балансировщик, allowlist origin.** Они находятся за пределами гостевой ОС и в локальном наборе правил не появятся.

**3. Fail2ban.** Правила сгруппированы по jail (отдельные наборы фильтров для SSH, nginx и других сервисов):

```bash
sudo fail2ban-client status            # список активных jail
sudo fail2ban-client status ИМЯ_JAIL   # заблокированные адреса в jail
```

**4. Захват пакетов.** Параллельно с внешним `curl`:

```bash
sudo tcpdump -ni any 'tcp port 80 or tcp port 443'
```

Интерпретация: нет SYN на origin — запрос потерялся раньше или ушел на другой IP; SYN есть, SYN-ACK не уходит — файрвол, policy routing или сокет; SYN-ACK ушел, но клиент его не видит — обратный маршрут или провайдер.

### Сценарий 8: Фронтенд отвечает, приложение нет (502/504)

Если nginx принимает запрос, но возвращает `502`/`504` (или статика открывается, а динамика — нет), проблема чаще всего между веб-сервером и приложением. Найдите в активной конфигурации директиву передачи запросов дальше:

```bash
sudo nginx -T | grep -E 'proxy_pass|fastcgi_pass|uwsgi_pass'
```

Затем обратитесь к upstream напрямую с теми же протоколом, адресом, портом, `Host` и путем, что указаны в конфигурации:

```bash
sudo ss -ltnp 'sport = :8000'
curl -v --max-time 10 http://127.0.0.1:8000/health -H 'Host: example.com'
```

Порт `8000` и путь `/health` приведены для примера — подставьте значения из конфигурации; если отдельного healthcheck-маршрута нет, запросите рабочий динамический.

HTTP-upstream может работать и через Unix-сокет:

```bash
curl --unix-socket /run/myapp/app.sock http://localhost/health
```

Сокеты из `fastcgi_pass` и `uwsgi_pass` работают не по HTTP, обычным `curl` их не проверить: проверьте наличие сокета и права на него, статус PHP-FPM и журналы; для полноценного запроса нужен FastCGI-клиент (например, `cgi-fcgi`) с параметрами конкретного приложения.

Для контейнеров:

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
docker logs --since 30m --tail 200 myapp
docker inspect --format '{{json .State.Health}}' myapp
docker port myapp
```

Пустой вывод `docker port` — норма, если прокси в той же Docker-сети или используется host network. Статус `Up` означает лишь, что жив PID 1; поле `Health` появляется только при настроенном healthcheck.

Базу проверяйте по тому же адресу и порту, которые использует приложение:

```bash
pg_isready -h 127.0.0.1 -p 5432 -d appdb
mysqladmin --host=127.0.0.1 --port=3306 ping
```

При `504` смотрите также блокировки, медленные запросы и пул соединений. Имена юнитов зависят от пакета: `postgresql.service` бывает мета-юнитом, MySQL может называться `mysql`.

### Сценарий 9: Проверка TLS-цепочки

Для OpenSSL 1.1.1+/3.x цепочку и соответствие имени проверяют так:

```bash
openssl s_client \
  -connect 203.0.113.10:443 \
  -servername example.com \
  -verify_hostname example.com \
  -verify_return_error \
  -brief </dev/null
```

`-servername` передает SNI, `-verify_hostname` проверяет имя в сертификате, `-verify_return_error` прерывает работу при ошибке проверки, `-brief` дает компактную сводку handshake. Все сертификаты, присланные сервером, выводит `-showcerts`:

```bash
openssl s_client \
  -connect 203.0.113.10:443 \
  -servername example.com \
  -showcerts </dev/null
```

На старых системах сначала проверьте `openssl version` — часть ключей может отсутствовать. Сертификат конкретного IP проще всего проверить через `curl --resolve` (см. Сценарий 6). Подробнее: [Диагностика SSL-сертификатов](../../Security/Tools/ssl_certificate_diagnostics.md) и [Диагностика TLS/SSL в Nginx](../Nginx/Security/TLS_SSL/nginx_tls_troubleshooting_and_compatibility.md).

## Дополнительная информация

### Основной инструментарий диагностики

-   **`ss -tlpn`** — проверка прослушиваемых портов и процессов. Точечный фильтр: `sudo ss -ltnp 'sport = :443'`. Пустой вывод означает, что в текущем network namespace порт никто не слушает.
-   **Анализ привязки сокета:** `127.0.0.1:443` доступен только с самого сервера; `0.0.0.0:443` принимает IPv4 на всех интерфейсах; запись `[::]:443` относится к IPv6 — принимает ли такой сокет также IPv4-соединения, зависит от параметра `IPV6_V6ONLY` и настроек приложения (проверяется раздельными запросами `curl -4`/`curl -6`).
-   **`lsof -i :80`** — кто именно занял порт.
-   **`tail -f /var/log/nginx/error.log`** — мониторинг ошибок в реальном времени.
-   **`strace -p <PID>`** — трассировка системных вызовов процесса (крайняя мера при "зависании").
-   **`systemd-analyze critical-chain nginx.service`** — анализ цепочки зависимостей при старте.

Состояние сервиса и конфигурация:

```bash
sudo systemctl status nginx --no-pager -l
sudo nginx -t
sudo journalctl -u nginx --since '-30 minutes' --no-pager
```

`Active: active (running)` подтверждает, что процесс жив, но не гарантирует правильность виртуального хоста и upstream. После успешного `nginx -t` конфиг перечитывается без остановки воркеров: `sudo systemctl reload nginx`. Для Apache: `sudo apachectl configtest`; юнит называется `apache2` в Debian-подобных системах и `httpd` в RHEL-подобных.

### Проверка после починки

- Настройте внешний мониторинг, ротацию логов и алерты на диск, inode, память и сервисы.
- При использовании Certbot прогоните `certbot renew --dry-run`.
- Автозагрузку проверяйте по реальным именам юнитов: `systemctl is-enabled nginx`, `systemctl is-enabled myapp`, `systemctl is-enabled postgresql@16-main` (имя кластера и версия — свои).
- Не закрывайте последнюю SSH-сессию, пока не проверите новое подключение и запасную консоль хостера: к упавшему сайту легко добавить вторую аварию — уже на порту 22.
