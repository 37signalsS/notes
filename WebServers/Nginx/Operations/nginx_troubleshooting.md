# Диагностика и устранение неисправностей Nginx

## Определения

### Диагностика Nginx

Процесс выявления, анализа и устранения проблем в работе веб-сервера Nginx. Включает проверку сетевой доступности, валидацию конфигурационных файлов, анализ системных ресурсов и интерпретацию логов.

Ключевые определения компонентов (master process, worker process, server block, location) подробно описаны в заметке **[Обзор Nginx](../Core/nginx_overview.md)**.

## Основные концепции

Эффективный поиск неисправностей строится на послойном анализе системы:

1.  **Локализация проблемы** — определение границы ответственности: клиент, сеть или сервер.
2.  **Проверка доступности** — подтверждение того, что процесс Nginx запущен и принимает соединения на ожидаемых портах.
3.  **Валидация конфигурации** — исключение синтаксических ошибок в файлах настроек перед применением изменений.
4.  **Анализ логов** — глубокое изучение `error.log` и `access.log` для поиска специфических ошибок и кодов ответов.
5.  **Контроль ресурсов** — проверка состояния аппаратных ресурсов сервера (диск, память, процессор) и внутренних лимитов процесса.

Методология системного поиска неисправностей приведена в SSoT: **[Диагностика веб-серверов (Troubleshooting)](../../Concepts/webserver_troubleshooting.md)**.

## Практические сценарии

### Сетевая диагностика

#### 1. Проверка DNS

Убедитесь, что доменное имя разрешается в корректный **IP-адрес (Internet Protocol — межсетевой протокол)** сервера с помощью **DNS (Domain Name System — система доменных имён)**.

```bash
dig your-domain.com
```

Подробнее об анализе вывода: **[Диагностика DNS](../../../Linux/Diagnostics/Networking/dns/overview.md)**.

#### 2. Проверка доступности портов

Используйте `telnet` или `nc` для проверки портов 80 (**HTTP — HyperText Transfer Protocol**) и 443 (**HTTPS — HyperText Transfer Protocol Secure**).

```bash
# Проверка открытия сокета процессом
ss -lnpt | grep nginx

# Проверка доступности извне (через loopback или внешний IP)
nc -zv your-domain.com 80
```

-   **Connected:** Соединение установлено, Nginx слушает порт.
-   **Connection timed out:** Запрос блокируется файрволом (на сервере или сетевом узле). См. **[Настройка файрвола](../../../Linux/Networking/Settings/Persistent_Network/systemd_networkd.md)**.
-   **Connection refused:** Процесс Nginx не запущен или слушает другой порт/интерфейс.

### Проверка состояния сервиса

Для управления процессом в современных системах используется **systemd**.

```bash
# Проверка статуса службы и последних строк лога
sudo systemctl status nginx

# Анализ времени запуска и зависимостей (выявление задержек при старте)
systemd-analyze critical-chain nginx.service

# Проверка наличия процессов в системе и их владельцев
ps aux | grep nginx
```

Подробнее об управлении: **[Управление службами systemd](../../../Linux/Core/systemd/service_management.md)**.

### Валидация конфигурации

Nginx не применит изменения и может не запуститься, если в конфигурации есть синтаксические ошибки.

```bash
# Проверка синтаксиса и наличия необходимых файлов
sudo nginx -t

# Проверка + вывод финального объединённого конфига (полезно при множественных include)
sudo nginx -T

# Graceful reload (перечитывание конфига без обрыва текущих соединений)
sudo nginx -s reload
```

Результат `syntax is ok` и `test is successful` подтверждает готовность конфигурации. При наличии ошибок Nginx укажет конкретный файл и номер строки.

> **Важно:** Всегда выполняйте `nginx -t` перед `reload`. Ошибка в синтаксисе не затрагивает уже работающий Nginx — он продолжит работать со старой конфигурацией.

### Анализ логов

Логирование — основной инструмент диагностики. Подробное описание переменных и форматов приведено в заметке **[Логирование в Angie/Nginx](../../Angie/angie_logging.md)**.

-   **Лог ошибок:** `/var/log/nginx/error.log` (путь по умолчанию).
-   **Лог доступа:** `/var/log/nginx/access.log`.

#### Мониторинг логов в реальном времени

```bash
tail -f /var/log/nginx/error.log
```

#### Использование Debug Log (глубокая отладка)

Для детального анализа (например, проблем с SSL-рукопожатием или сложными rewrite) требуется поддержка `debug` на уровне сборки (`nginx -V` должен содержать `--with-debug`).

**Включение в конфиге:**
```nginx
error_log /var/log/nginx/error.log debug;
```
*Внимание: это создает огромную нагрузку на диск и CPU. Используйте только для точечной отладки.*

### Типовые ошибки и способы решения

#### Ошибка 403 — Доступ запрещён (Forbidden)

**Причина:** У воркера Nginx (обычно пользователь `www-data` или `nginx`) нет прав на чтение файлов или выполнение (вход) для директорий.

**Решение:**
1.  Проверьте владельца: `sudo chown -R www-data:www-data /path/to/site`.
2.  Установите права: директории — `755`, файлы — `644`.
3.  Проверьте **SELinux (Security-Enhanced Linux)** или **AppArmor**, если права верны, но доступ закрыт.

#### Ошибка 404 — Ресурс не найден (Not Found)

1.  **Локализация:** Проверьте **URL (Uniform Resource Locator — унифицированный указатель ресурса)** на опечатки.
2.  **Access Log:** Проверьте, какой `server_name` обработал запрос (часто запрос уходит в `default_server`).
3.  **Error Log:** Проверьте путь, который Nginx пытался открыть: `ls -l /path/from/log`.
4.  **Конфигурация:** Проверьте директивы `root` и `alias`. Если используется `try_files`, убедитесь, что последний параметр корректен.

#### Ошибка 413 — Тело запроса слишком велико (Payload Too Large)

**Причина:** Размер загружаемого файла превышает лимит `client_max_body_size`.
**Решение:** Увеличьте лимит в блоке `http`, `server` или `location`:
```nginx
client_max_body_size 100M;
```

#### Ошибка 499 — Соединение закрыто клиентом (Client Closed Request)

**Причина:** Клиент закрыл соединение до того, как Nginx успел передать ответ от бэкенда.
**Диагностика:** Сравните `$request_time` и `$upstream_response_time`. Если бэкенд отвечает дольше 60с, а клиент уходит через 30с — проблема в таймауте клиента.

#### Ошибка 500 — Внутренняя ошибка сервера (Internal Server Error)

**Причина:** Обычно связана с ошибками конфигурации (например, циклы `rewrite`), нехваткой прав на запись в `client_body_temp_path` или сбоем бэкенда.
**Диагностика:** Проверьте `error.log`. Если ошибка `rewrite or internal redirection cycle`, исправьте логику перенаправлений.

#### Ошибка 502 — Ошибка шлюза (Bad Gateway)

**Причина:** Nginx как прокси не может получить ответ от бэкенда (процесс упал, не слушает порт или сбросил соединение).
**Решение:**
1.  Проверьте статус бэкенда (`systemctl status php-fpm`, `node`, и т.д.).
2.  Проверьте сокеты/порты: `ss -lnp | grep 9000`.
3.  **SELinux:** Проверьте разрешение на сетевые соединения для Nginx: `getsebool httpd_can_network_connect`.

#### Ошибка 504 — Таймаут шлюза (Gateway Timeout)

**Причина:** Бэкенд принял запрос, но не успел ответить в течение таймаута Nginx.
**Решение:** Увеличьте таймауты проксирования:
```nginx
proxy_read_timeout 300s;
proxy_connect_timeout 75s;
```

### Диагностика Upstream и буферизации

#### Ошибки в работе прокси

-   **"upstream sent too big header"**: Бэкенд прислал слишком много заголовков (например, большие Cookies). Нужно увеличить `proxy_buffer_size`.
-   **"an upstream response is buffered to a temporary file"**: Ответ бэкенда не помещается в память. Если это замедляет работу, увеличьте `proxy_buffers`.

### Проверка системных ресурсов и лимитов

Нехватка ресурсов (диска, памяти, дескрипторов) часто маскируется под ошибки приложения. Общая методология и команды проверки (`df`, `free`, `oom-killer`) описаны в SSoT: **[Диагностика веб-серверов (Troubleshooting)](../../Concepts/webserver_troubleshooting.md)**.

#### Лимиты процесса (RLIMIT)

Если в логах Nginx появляется ошибка `worker_connections are not enough` или `too many open files`, необходимо увеличить лимиты в конфигурации.

```bash
# Проверка текущих лимитов работающего воркера Nginx
cat /proc/$(pgrep -n nginx)/limits | grep "Max open files"
```

**Настройка в nginx.conf:**
```nginx
worker_rlimit_nofile 65535; # Лимит на файловые дескрипторы
events {
    worker_connections 16384; # Максимальное количество соединений на воркер
}
```

#### Проблемы с разделяемой памятью (Shared Memory)

Ошибка `could not allocate ... in shared memory zone` возникает, когда зона (например, для `limit_req` или `ssl_session_cache`) переполнена.
**Решение:** Увеличьте размер зоны в конфигурации.

### Мониторинг состояния (Stub Status и Angie API)

Для оперативной диагностики используйте модули статистики.

#### Nginx Open Source (stub_status)
```nginx
location /nginx_status {
    stub_status;
    allow 127.0.0.1;
    deny all;
}
```

#### Angie (Console и HTTP API)
Angie предоставляет более детальную информацию (метрики апстримов, зоны разделяемой памяти) через встроенный API.
Подробнее: **[Мониторинг Angie](../../Angie/angie_monitoring.md)**.

## Дополнительная информация

### Статистика кодов ответа (awk)

```bash
# Подсчет количества каждого HTTP-кода в логе (9-я колонка в стандартном формате)
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
```

### Фильтрация ошибок 5xx (sed)

```bash
# Вывод строк, содержащих коды 500-599
sed -n '/HTTP\/[0-9.]*" 5[0-9][0-9] /p' /var/log/nginx/access.log
```
