# Диагностика и устранение неисправностей Nginx

## Определения

### Диагностика Nginx (Troubleshooting)

Процесс выявления, анализа и устранения проблем в работе веб-сервера Nginx. Включает проверку сетевой доступности, валидацию конфигурационных файлов, анализ системных ресурсов и интерпретацию логов.

Ключевые определения компонентов (master process, worker process, server block, location) подробно описаны в заметке **[Обзор Nginx](../Core/nginx_overview.md)**.

## Основные концепции

Эффективный поиск неисправностей строится на послойном анализе системы:

1. **Локализация проблемы** — определение границы ответственности: клиент, сеть или сервер.
2. **Проверка доступности** — подтверждение того, что процесс Nginx запущен и принимает соединения на ожидаемых портах.
3. **Валидация конфигурации** — исключение синтаксических ошибок в файлах настроек перед применением изменений.
4. **Анализ логов** — глубокое изучение `error.log` и `access.log` для поиска специфических ошибок и кодов ответов.
5. **Контроль ресурсов** — проверка состояния аппаратных ресурсов сервера (диск, память, процессор).

## Практические сценарии

### Сетевая диагностика

#### 1. Проверка DNS

Убедитесь, что доменное имя разрешается в корректный IP-адрес сервера.

```bash
dig your-domain.com
```

Подробнее об анализе вывода: **[Диагностика DNS](../../../Linux/Diagnostics/Networking/dns/overview.md)**.

#### 2. Проверка доступности портов

Используйте `telnet` или `nc` для проверки портов 80 (HTTP) и 443 (HTTPS).

```bash
telnet your-domain.com 80
```

- **Connected:** Соединение установлено, Nginx слушает порт.
- **Connection timed out:** Запрос блокируется файрволом (на сервере или сетевом узле). См. **[Настройка файрвола](../../../Linux/Networking/Settings/Persistent_Network/systemd_networkd.md)**.
- **Connection refused:** Процесс Nginx не запущен или слушает другой порт/интерфейс.

### Проверка состояния сервиса

Для управления процессом в современных системах используется **systemd**.

```bash
# Проверка статуса службы
sudo systemctl status nginx

# Проверка наличия процессов в системе
ps aux | grep nginx
```

Подробнее об управлении: **[Управление службами systemd](../../../Linux/Core/systemd/service_management.md)**.

### Валидация конфигурации

Nginx не применит изменения и может не запуститься, если в конфигурации есть синтаксические ошибки.

```bash
# Проверка синтаксиса и ссылок на файлы
sudo nginx -t

# Проверка + вывод финального объединённого конфига
sudo nginx -T

# Graceful reload (применяет конфиг без разрыва соединений)
sudo nginx -s reload

# Через systemd
systemctl reload nginx
```

Результат `syntax is ok` и `test is successful` подтверждает готовность конфигурации. При наличии ошибок Nginx укажет конкретный файл и номер строки.

> **Важно:** Всегда выполняйте `nginx -t` перед `reload`. Ошибка в синтаксисе не затрагивает уже работающий Nginx — он продолжит работать со старой конфигурацией. Это делает `nginx -t` безопасной операцией проверки.

### Анализ логов

Логирование — основной инструмент диагностики. Подробное описание переменных и форматов приведено в заметке **[Логирование в Angie/Nginx](../../Angie/angie_logging.md)**.

- **Лог ошибок:** `/var/log/nginx/error.log`
- **Лог доступа:** `/var/log/nginx/access.log`

#### Мониторинг логов в реальном времени

```bash
tail -f /var/log/nginx/error.log
```

### Типовые ошибки и способы решения

#### Ошибка 403 (Forbidden) — Permission denied

**Причина:** У воркера Nginx (обычно пользователь `www-data`) нет прав на чтение файлов или выполнение (вход) для директорий.

**Решение:**

1. Проверьте владельца: `sudo chown -R www-data:www-data /path/to/site`.
2. Установите права: директории — `755`, файлы — `644`.

#### Ошибка 404 (Not Found) — Алгоритм решения

1. **Локализация:** Проверьте URL на опечатки. Попробуйте запросить статический файл (например, `favicon.ico`).
2. **Access Log:** Найдите запрос по пути: `grep "GET /path" /var/log/nginx/access.log`. Проверьте, какой `server_name` обработал запрос.
3. **Error Log:** Nginx часто пишет полный путь на диске, который он пытался открыть: `ls -l /path/from/log`.
4. **Конфигурация:** Проверьте директивы `root` и `alias`. Если используется `try_files`, убедитесь, что последний параметр корректен.

#### Ошибка 502 (Bad Gateway) — Проблемы с бэкендом

**Причина:** Nginx как прокси не может получить ответ от апстрима (Node.js, PHP-FPM, Python).

1. **Апстрим недоступен:** Проверьте статус бэкенда (`systemctl status app`).
2. **Ошибка под нагрузкой:** Очередь соединений (`backlog`) переполнена.
   - Увеличьте лимит на уровне ядра: `sysctl -w net.core.somaxconn=4096`.
   - Увеличьте `backlog` в настройках приложения (например, в PHP-FPM `listen.backlog = 4096`).

#### Ошибка 499 (Client Closed Request)

**Причина:** Клиент (браузер или мобильное приложение) закрыл соединение до того, как Nginx успел передать ответ от бэкенда.

**Диагностика:** Сравните `$request_time` и `$upstream_response_time` (требуется расширенный формат логов в `nginx.conf`).

- Если оба велики — бэкенд работает слишком медленно.
- Если бэкенд успел ответить, но клиент ушел — возможно, занижен таймаут на стороне клиента.

### Проверка системных ресурсов

Нехватка ресурсов часто маскируется под ошибки приложения.

- **Диск (место и inodes):** `df -h`, `df -i`.
- **Память:** `free -m`.
- **Нагрузка:** `htop`.

## Дополнительная информация

### Инструменты анализа логов

Для быстрой обработки больших объемов данных используются стандартные утилиты shell.

#### Использование awk для статистики кодов ответа

```bash
# Подсчет количества каждого HTTP-кода в логе
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
```

#### Использование sed для фильтрации 5xx ошибок

```bash
# Вывод строк, содержащих коды 500-599
sed -n '/HTTP\/[0-9.]*" 5[0-9[0-9] /p' /var/log/nginx/access.log
```

### Сравнение инструментов обработки текста

| Характеристика | awk | sed |
| :--- | :--- | :--- |
| **Назначение** | Разбор по колонкам, вычисления | Потоковое редактирование, замена |
| **Логика** | Работа с полями (`$1`, `$9`) | Работа со строками и шаблонами |
