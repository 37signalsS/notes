# Диагностика и устранение неисправностей Nginx

**Актуально для:** Nginx 1.26.x (Stable) / 1.27.x (Mainline)

---

## Определения

- **Диагностика Nginx (Troubleshooting)** — систематический процесс выявления, локализации и устранения причин отказов или деградации производительности веб-сервера. Охватывает сетевой уровень ядра Linux, пространство процессов Nginx, дисковый ввод-вывод, взаимодействие с upstream-бэкендами и валидацию конфигурации.
- **MTTR (Mean Time To Repair)** — среднее время восстановления штатного функционирования сервиса после возникновения инцидента. В SRE-практиках снижение MTTR достигается заблаговременной разработкой runbook-инструкций, автоматизацией проверки конфигурации и стандартизацией алгоритмов локализации сбоев.
- **Runbook (Операционный регламент)** — формализованное пошаговое руководство для дежурного инженера (DevOps/SRE/SysAdmin) по идентификации, диагностике, купированию и устранению конкретного инцидента.
- **Master-процесс** — привилегированный управляющий процесс Nginx (обычно запускаемый от пользователя `root`), отвечающий за чтение конфигурации, открытие сетевых сокетов, управление жизненным циклом worker-процессов и обработку системных POSIX-сигналов.
- **Worker-процесс** — непривилегированный рабочий процесс (по умолчанию запускается от пользователя `www-data` или `nginx`), исполняющий неблокирующий цикл обработки событий (event loop) на базе системного вызова `epoll` в Linux.
- **Listen Backlog (Очередь прослушивания сокета)** — системная очередь сокета в ядре Linux для входящих TCP-соединений, завершивших 3-way handshake, но еще не извлеченных процессом Nginx через вызов `accept()`. Размер регулируется директивой `backlog` в строке `listen` и параметром ядра `net.core.somaxconn`.
- **Ephemeral Port Exhaustion (Исчерпание динамических портов)** — состояние ОС, при котором исчерпан пул локальных TCP-портов (`net.ipv4.ip_local_port_range`), выделяемых для исходящих соединений к upstream-серверам, чаще всего вызванное скоплением сокетов в состоянии `TIME_WAIT`.
- **Core Dump (Дамп аварийной памяти)** — снимок адресного пространства процесса в момент аварийного завершения (например, при получении сигнала `SIGSEGV` / signal 11), используемый для пошаговой отладки в `gdb`.
- **Graceful Reload** — операция обновления конфигурации без разрыва установленных соединений: master-процесс перечитывает файлы, запускает новое поколение worker-процессов и отправляет старому поколению сигнал `SIGQUIT` на завершение после обработки текущих запросов.
- **Stub Status** — встроенный модуль (`ngx_http_stub_status_module`), предоставляющий базовую оперативную телеметрию: число активных соединений, общее количество принятых/обработанных запросов и состояние сетевых буферов.

## Основные концепции и архитектура

### Послойная модель прохождения запроса и точки отказа

Nginx функционирует на стыке сетевого стека ядра Linux и прикладных upstream-сервисов. Для быстрой локализации инцидентов применяется послойный метод диагностики по цепочке движения пакетов:

```text
[ Клиентский трафик ]
         │
         ▼
┌────────────────────────────────────────────────────────┐
│ 1. Сетевой уровень ядра Linux                          │
│    - Сетевой интерфейс, драйвер, очереди RX/TX         │
│    - Фильтрация пакетов: nftables / iptables           │
│    - SYN Backlog (net.ipv4.tcp_max_syn_backlog)        │
│    - Listen Backlog (net.core.somaxconn, backlog)      │
└────────────────────────┬───────────────────────────────┘
                         │ accept()
                         ▼
┌────────────────────────────────────────────────────────┐
│ 2. Процессное пространство Nginx                       │
│    - Master-процесс: чтение конфигов, bind портов      │
│    - Worker-процессы: неблокирующий epoll event loop   │
│    - Системные лимиты: LimitNOFILE, worker_rlimit      │
│    - Shared Memory: slab-аллокатор (limit_req, SSL)    │
└────────────────────────┬───────────────────────────────┘
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
┌────────────────────────┐    ┌──────────────────────────┐
│ 3. Локальные ресурсы   │    │ 4. Upstream-подсистема   │
│  - Права DAC (chown)   │    │  - Unix Domain Sockets   │
│  - MAC (SELinux,       │    │  - TCP Loopback/LAN сокет│
│    AppArmor)           │    │  - Пул keepalive         │
│  - Дисковый I/O,       │    │  - Буферы proxy_buffers  │
│    client_body_temp    │    │  - Таймауты connect/read │
└────────────────────────┘    └──────────────────────────┘
```

Каждый архитектурный уровень определяет свой класс симптомов и методов локализации:

1. **Сетевой уровень ядра:**
   - Переполнение `SYN Backlog` или `Listen Backlog` приводит к тому, что ядро молча отбрасывает новые пакеты `SYN` или возвращает клиенту пакет `RST`. Со стороны клиента это выглядит как задержка на этапе подключения или ошибка `Connection reset by peer`.
   - Ошибки пакетного фильтра или исчерпание таблицы `conntrack` блокируют трафик до попадания в сокет Nginx (`Connection timed out`).
2. **Пространство процессов Nginx:**
   - Падение worker-процесса по сигналу `SIGSEGV` (signal 11) мгновенно обрывает все клиентские соединения, мультиплексированные в данном воркере. Master-процесс немедленно перезапускает воркер, но активные сессии теряются.
   - Исчерпание лимита файловых дескрипторов (`worker_rlimit_nofile` или systemd `LimitNOFILE`) блокирует вызовы `accept()` и открытие соединений к бэкендам.
   - Переполнение зон разделяемой памяти (`shared memory zones`) приводит к невозможности записи новых ключей в `limit_req` или кэш TLS-сессий.
3. **Локальная файловая система:**
   - Ограничения прав доступа (DAC/MAC) приводят к ошибкам `403 Forbidden` при обращении к статике или `500 Internal Server Error` при невозможности записи во временные каталоги (`client_body_temp_path`, `proxy_temp_path`).
   - Переполнение диска или нехватка свободных индексных дескрипторов (inodes) блокирует запись логов и сброс тел тяжелых запросов.
4. **Upstream-подсистема:**
   - Задержки генерации ответа бэкендом приводят к ошибкам `504 Gateway Timeout` или обрывам со стороны нетерпеливых клиентов (`499 Client Closed Request`).
   - Аварийная остановка upstream-сервиса или отказ в приеме соединения вызывает ошибку `502 Bad Gateway`.

### Управление процессами через POSIX-сигналы

Взаимодействие с Nginx строится на отправке стандартных сигналов master-процессу. Понимание семантики каждого сигнала исключает случайные простои сервиса:

| Сигнал | Команда CLI | Действие Master-процесса | Практическое назначение |
| :--- | :--- | :--- | :--- |
| `SIGHUP` | `nginx -s reload` / `systemctl reload` | Валидирует конфигурацию, запускает новые worker-процессы с новым конфигом, отправляет старым воркерам сигнал на плавное завершение | Безопасное применение изменений без разрыва соединений |
| `SIGQUIT` | `nginx -s quit` | Закрывает слушающие сокеты, ожидает завершения обработки активных запросов всеми воркерами, затем завершает процесс | Плавная остановка перед выводом ноды из балансировки |
| `SIGTERM` / `SIGINT` | `nginx -s stop` | Немедленно завершает все worker-процессы, разрывая текущие TCP-соединения | Экстренная остановка сервиса |
| `SIGUSR1` | `nginx -s reopen` | Переоткрывает файлы журналов (`access.log`, `error.log`) без остановки процессов | Ротация логов утилитой `logrotate` |
| `SIGUSR2` | `kill -USR2 <pid>` | Запускает новый master-процесс с обновленным бинарным файлом, передавая дескрипторы открытых слушающих сокетов | Бесшовное обновление исполняемого файла Nginx |
| `SIGWINCH` | `kill -WINCH <pid>` | Отправляет сигнал плавного завершения дочерним worker-процессам старого master-процесса | Этап бесшовного обновления бинарника |

## Практические сценарии диагностики

### 1. Первичная сетевая локализация и проверка портов

При недоступности сайта проверка начинается с подтверждения сетевой связности и прослушивания портов:

```bash
# 1. Проверка разрешения DNS-имени сервера
dig +short your-domain.com
# → 192.0.2.10

# 2. Проверка открытия сокетов процессом Nginx
sudo ss -lnpt | grep nginx
# → LISTEN 0 511 0.0.0.0:80  0.0.0.0:* users:(("nginx",pid=1234,fd=6))
# → LISTEN 0 511 0.0.0.0:443 0.0.0.0:* users:(("nginx",pid=1234,fd=7))

# 3. Проверка прослушивания UDP-сокетов (для HTTP/3 / QUIC)
sudo ss -ulpn | grep nginx
# → UNCONN 0 0 0.0.0.0:443 0.0.0.0:* users:(("nginx",pid=1234,fd=8))

# 4. Проверка доступности порта извне или локально
nc -zv 127.0.0.1 80
# → Connection to 127.0.0.1 80 port [tcp/http] succeeded!
```

**Интерпретация сетевых ошибок:**
- **`Connection refused`:** Процесс Nginx не запущен, упал либо слушает другой интерфейс (например, привязан только к `127.0.0.1` вместо `0.0.0.0`).
- **`Connection timed out`:** Пакеты отбрасываются межсетевым экраном хоста или промежуточным оборудованием. См. **[Межсетевые экраны Linux](../../../Linux/Networking/Settings/tools/firewall_common.md)**.
- Подробный анализ логики DNS приведен в заметке **[Диагностика DNS](../../../Linux/Diagnostics/Networking/dns/overview.md)**.

### 2. Проверка состояния службы systemd

Управление Nginx на современных Linux-дистрибутивах осуществляется через `systemd`:

```bash
# Проверка текущего статуса службы и кода завершения
sudo systemctl status nginx.service

# Просмотр логов запуска службы в журнале systemd
sudo journalctl -u nginx.service --since "-1 hour" --no-pager

# Анализ задержек при старте службы в дереве зависимостей
systemd-analyze critical-chain nginx.service
```

> [!IMPORTANT]
> Если служба находится в состоянии `failed` с ошибкой `code=exited, status=1/FAILURE`, ключевая причина фиксируется в первых строках `journalctl` непосредственно перед остановкой процесса. Подробнее об управлении службами: **[Управление службами systemd](../../../Linux/Core/systemd/service_management.md)**.

### 3. Валидация и безопасное обновление конфигурации

Ошибки в синтаксисе директив или неверные пути к файлам сертификатов приводят к аварийной остановке при перезапуске.

```bash
# Базовая проверка синтаксиса всех включенных файлов
sudo nginx -t
# → nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
# → nginx: configuration file /etc/nginx/nginx.conf test is successful

# Проверка с выводом финального объединенного конфига (раскрывает все директивы include)
sudo nginx -T
```

**Регламент атомарного применения изменений в production:**
1. Не редактируйте рабочий файл `nginx.conf` напрямую "по живому".
2. Создайте копию конфигурационного файла или используйте Git-репозиторий.
3. Проверьте валидность файла: `sudo nginx -t`.
4. Примените изменения командой плавного перечитывания: `sudo systemctl reload nginx`. В случае ошибки синтаксиса `reload` гарантированно не затронет работающие процессы.

### 4. Диагностика падений worker-процессов и анализ Core Dump

Аварийное завершение воркера с записью в `error.log`:
`worker process 12345 exited on signal 11 (core dumped)` свидетельствует об ошибке сегментации памяти (`SIGSEGV`), вызванной некорректным сторонним модулем (Lua, njs, модуль фильтрации), сбоем в скомпилированных библиотеках (OpenSSL, PCRE2) или внутренней ошибкой Nginx.

**Настройка генерации Core Dump:**

1. Создайте защищенную директорию для записи дампов памяти:
   ```bash
   sudo mkdir -p /var/log/nginx/cores
   sudo chown www-data:www-data /var/log/nginx/cores
   sudo chmod 700 /var/log/nginx/cores
   ```

2. Добавьте директивы в глобальный блок `nginx.conf`:
   ```nginx
   # /etc/nginx/nginx.conf (main context)
   worker_rlimit_core 2G;
   working_directory /var/log/nginx/cores;
   ```

3. Настройте разрешения ядра Linux и systemd:
   ```bash
   # Разрешить сброс дампов памяти для процессов, сменивших UID/GID
   sudo sysctl -w fs.suid_dumpable=2
   
   # Переопределите лимит дампов в юните systemd
   sudo systemctl edit nginx.service
   ```
   В drop-in конфигурацию добавьте:
   ```ini
   [Service]
   LimitCORE=infinity
   ```
   Примените настройки: `sudo systemctl daemon-reload && sudo systemctl restart nginx`.

4. Анализ упавшего процесса через `coredumpctl` или `gdb`:
   ```bash
   # Поиск последних дампов Nginx в системе
   coredumpctl list /usr/sbin/nginx
   
   # Вызов gdb для последнего дампа
   coredumpctl gdb /usr/sbin/nginx
   
   # В консоли gdb запросите стек вызовов:
   # (gdb) bt full
   ```
   Стек вызовов (`backtrace`) указывает на точный модуль и функцию ядра Nginx, вызвавшую сбой.

### 5. Диагностика переполнения сокетных очередей ядра (Listen Backlog)

При резком всплеске трафика или зависании worker-процессов новые входящие TCP-соединения скапливаются в очереди прослушивания сокета (`Listen Backlog`). Если очередь заполняется, ядро Linux отбрасывает новые запросы.

```bash
# Проверка состояния очереди сокетов Nginx
ss -lnt 'sport = :80 or sport = :443'
# → State  Recv-Q Send-Q Local Address:Port  Peer Address:Port
# → LISTEN 512    511    0.0.0.0:80          0.0.0.0:*
```

> [!NOTE]
> В выводе `ss -lnt` для сокетов в состоянии **LISTEN**:
> - **Send-Q** — максимально допустимый размер очереди соединений (определяется параметром `backlog`).
> - **Recv-Q** — текущее количество соединений, ожидающих вызова `accept()` от worker-процесса.
> Если `Recv-Q > Send-Q`, очередь переполнена, и ядро отбрасывает входящие пакеты `SYN`.

**Проверка системных счетчиков отброшенных соединений:**
```bash
# Проверка счетчиков переполнения очередей ядра
netstat -s | grep -i "listen"
# → 1240 times the listen queue of a socket overflowed
# → 1240 SYNs to LISTEN sockets dropped
```

**Решение проблемы переполнения очередей:**
1. Увеличьте лимит очереди в ядре Linux (`/etc/sysctl.conf`):
   ```ini
   net.core.somaxconn = 65535
   net.ipv4.tcp_max_syn_backlog = 16384
   ```
   Примените: `sudo sysctl -p`.
2. Явно укажите размер очереди в блоке `listen` виртуального хоста Nginx:
   ```nginx
   server {
       listen 80 default_server backlog=16384;
       listen 443 ssl default_server backlog=16384;
       ...
   }
   ```

### 6. Диагностика исчерпания эфемерных портов (Ephemeral Port Exhaustion)

При проксировании огромного потока коротких HTTP/1.0 или HTTP/1.1 запросов без повторного использования соединений Nginx быстро исчерпывает доступный диапазон исходящих клиентских портов для связи с upstream.

**Симптом в `error.log`:**
`connect() to 10.0.0.5:8080 failed (99: Cannot assign requested address) while connecting to upstream`

**Диагностика сокетов в состоянии TIME_WAIT:**
```bash
# Подсчет количества сокетов в состоянии TIME_WAIT
ss -s
# → TCP: 58210 (estab 1200, closed 56900, orphaned 10, timewait 56840)

# Проверка доступного диапазона портов ядра
sysctl net.ipv4.ip_local_port_range
# → net.ipv4.ip_local_port_range = 32768 60999
```

**Решение:**
1. **Включите постоянные keepalive-соединения к апстриму (главная мера):**
   ```nginx
   upstream app_backend {
       server 10.0.0.5:8080;
       keepalive 64; # Пул свободных постоянных соединений на каждый воркер
   }

   server {
       location / {
           proxy_pass http://app_backend;
           proxy_http_version 1.1;
           proxy_set_header Connection ""; # Очистка заголовка закрытия
       }
   }
   ```
2. **Оптимизируйте параметры ядра Linux (`/etc/sysctl.conf`):**
   ```ini
   # Расширение диапазона доступных исходящих портов
   net.ipv4.ip_local_port_range = 10240 65535

   # Разрешить повторное использование сокетов в состоянии TIME_WAIT для исходящих TCP-соединений
   net.ipv4.tcp_tw_reuse = 1
   ```
   Примените: `sudo sysctl -p`.

### 7. Диагностика лимитов процессов (RLIMIT) и файловых дескрипторов

Каждое клиентское соединение и каждое проксируемое соединение к бэкенду занимает как минимум один файловый дескриптор сокета.

**Симптомы в `error.log`:**
- `worker_connections are not enough (7111: Connection refused)` — достигнут предел внутренних соединений воркера.
- `open() "/var/www/..." failed (24: Too many open files)` — процесс достиг системного лимита файловых дескрипторов.

**Проверка текущих лимитов работающего воркера:**
```bash
# Получение PID воркера и просмотр таблицы лимитов ядра
cat /proc/$(pgrep -f "nginx: worker process" | head -n 1)/limits | grep "open files"
# → Max open files   1024   4096   files
```

**Решение:**
1. Настройте директиву `worker_rlimit_nofile` в блоке `main` конфигурации `/etc/nginx/nginx.conf`:
   ```nginx
   worker_rlimit_nofile 65535;
   events {
       worker_connections 16384;
       multi_accept on;
       use epoll;
   }
   ```
   > **Правило расчета:** Значение `worker_rlimit_nofile` должно как минимум в 2–3 раза превышать `worker_connections`, так как воркер одновременно удерживает сокеты клиентов, сокеты апстримов, дескрипторы открытых статических файлов и сокеты логов.

2. Настройте ограничение дескрипторов на уровне службы `systemd`:
   ```ini
   # /etc/systemd/system/nginx.service.d/limits.conf
   [Service]
   LimitNOFILE=65535
   ```
   Примените: `sudo systemctl daemon-reload && sudo systemctl restart nginx`.

### 8. Диагностика прав доступа и временных каталогов (DAC / MAC)

При приеме больших запросов (файлы, загружаемые клиентом) или получении тяжелых ответов от бэкенда Nginx буферизует данные на локальный диск во временные каталоги.

**Симптом в `error.log`:**
`open() "/var/lib/nginx/body/0000000001" failed (13: Permission denied)`

**Диагностика прав доступа (DAC):**
```bash
# Проверка пользователя, под которым работают воркеры Nginx
ps aux | grep "nginx: worker"
# → www-data 1235 ... nginx: worker process

# Проверка прав на временные каталоги буферизации
ls -ld /var/lib/nginx /var/lib/nginx/*
# → drwx------ 2 www-data www-data 4096 /var/lib/nginx/body
# → drwx------ 2 www-data www-data 4096 /var/lib/nginx/proxy
```
Если каталоги принадлежат другому пользователю (например, `root`), воркер Nginx не сможет создать временный файл и вернет ошибку `500 Internal Server Error`.

**Решение:**
```bash
sudo chown -R www-data:www-data /var/lib/nginx
sudo chmod 700 /var/lib/nginx/body /var/lib/nginx/proxy /var/lib/nginx/fastcgi
```

**Диагностика ограничений SELinux (RHEL/CentOS/Rocky Linux):**
Если стандартные права `755` выставлены корректно, но Nginx возвращает `403` или `502`, причиной являются ограничения MAC:
```bash
# Проверка блокировок SELinux в журнале аудита
sudo ausearch -m avc -ts recent

# Разрешить Nginx устанавливать сетевые соединения к upstream-серверам
sudo setsebool -P httpd_can_network_connect 1

# Восстановление правильного контекста безопасности для файлов сайта
sudo restorecon -Rv /var/www/html
```
Подробно системный харденинг и политики MAC описаны в руководстве **[Харденинг Nginx: systemd, SELinux, AppArmor](../Security/nginx_systemd_selinux_hardening.md)**.

### 9. Бесшовное обновление исполняемого файла Nginx (Zero-Downtime Binary Upgrade)

При обновлении версии пакета или компиляции нового бинарника недопустимо выполнять `systemctl restart`, так как это обрывает активные сессии. Nginx поддерживает процедуру горячей замены master-процесса:

1. **Запуск нового master-процесса:**
   ```bash
   # Отправка сигнала USR2 текущему master-процессу
   sudo kill -USR2 $(cat /run/nginx.pid)
   ```
   Master-процесс переименовывает текущий PID-файл в `/run/nginx.pid.oldbin`, запускает новый исполняемый файл Nginx с новым master- и worker-процессами, передавая им открытые слушающие сокеты. В этот момент работают два master-процесса.

2. **Плавная остановка старых воркеров:**
   ```bash
   # Остановка воркеров старого master-процесса
   sudo kill -WINCH $(cat /run/nginx.pid.oldbin)
   ```
   Старые воркеры корректно завершают обслуживание текущих сессий и останавливаются. Новый трафик полностью обрабатывается новыми процессами.

3. **Верификация работоспособности:**
   Убедитесь в отсутствии ошибок в `error.log` и корректности отдачи трафика.

4. **Завершение процедуры (успех):**
   ```bash
   # Завершение старого master-процесса
   sudo kill -QUIT $(cat /run/nginx.pid.oldbin)
   ```

5. **Откат при возникновении сбоя (Rollback):**
   Если новый бинарник работает некорректно:
   ```bash
   # 1. Перезапуск воркеров старого master
   sudo kill -HUP $(cat /run/nginx.pid.oldbin)
   # 2. Принудительное завершение нового master
   sudo kill -QUIT $(cat /run/nginx.pid)
   ```

### 10. Мониторинг телеметрии через stub_status

Для оценки текущей нагрузки и выявления аномалий используется модуль `ngx_http_stub_status_module`.

**Конфигурация изолированного доступа:**
```nginx
server {
    listen 127.0.0.1:8080;
    server_name localhost;

    location = /nginx_status {
        stub_status;
        allow 127.0.0.1;
        deny all;
        access_log off;
    }
}
```

**Снятие метрик и расшифровка значений:**
```bash
curl -s http://127.0.0.1:8080/nginx_status
```
```text
Active connections: 291 
server accepts handled requests
 16630948 16630948 31070653 
Reading: 6 Writing: 179 Waiting: 106 
```

**Интерпретация полей для SRE/DevOps инженера:**
- **`Active connections`** — суммарное текущее количество открытых соединений (включая клиентские и upstream-соединения).
- **`accepts`** — общее число принятых входящих TCP-соединений с момента старта.
- **`handled`** — число успешно обработанных соединений. Если `handled < accepts`, разница указывает на соединения, отброшенные из-за исчерпания `worker_connections`.
- **`requests`** — общее число обработанных HTTP-запросов. Отношение `requests / handled` показывает среднее число запросов в одном keepalive-соединении.
- **`Reading`** — количество соединений, в которых Nginx считывает заголовок клиентского запроса. Всплеск этого числа указывает на Slowloris-атаку или проблемы в клиентской сети.
- **`Writing`** — количество соединений, в которых Nginx передает данные клиенту, ожидает ответа от upstream или обрабатывает запрос. Высокое значение указывает на медленные бэкенды или отдачу тяжелых файлов медленным клиентам.
- **`Waiting`** — праздные (idle) клиентские соединения, ожидающие следующего запроса в режиме keepalive (`keepalive_timeout`).

## Устранение неисправностей

### Матрица HTTP-ошибок и runtime-сбоев

| Симптом / Ошибка в логе | Вероятная первопричина | Метод верификации | Способ устранения |
| :--- | :--- | :--- | :--- |
| **`400 Bad Request`** | Размер строки или заголовков превышает буфер; спецсимволы в URI; отсутствие заголовка `Host` | Анализ запроса в `access.log`; проверка `error.log` | Увеличить `client_header_buffer_size` и `large_client_header_buffers` |
| **`403 Forbidden`** | Нет прав на чтение файла/каталога воркеру; отсутствует индексный файл при `autoindex off`; блокировка SELinux | `ls -la /path/to/file`; `ausearch -m avc` | `chmod 644 /path/*`; `chmod 755 /dir`; создать `index.html`; настроить SELinux |
| **`404 Not Found`** | Ошибка в пути `root`/`alias`; неверный fallback в `try_files`; запрос ушел в дефолтный виртуальный хост | Проверка `$server_name` и пути в `error.log` | Исправить слэши в директиве `alias`; проверить заголовок `Host` и блок `server_name` |
| **`408 Request Timeout`** | Клиент не передал тело или заголовки в отведенное время из-за медленного канала или атаки | Проверка таймингов в `access.log` (`$request_time`) | Увеличить `client_body_timeout` и `client_header_timeout` для тяжелых клиентов |
| **`413 Payload Too Large`** | Размер тела POST/PUT запроса превышает ограничение `client_max_body_size` | Сообщение `client intended to send too large body` в `error.log` | Увеличить `client_max_body_size 50M;` в контексте `http`, `server` или `location` |
| **`414 Request-URI Too Large`** | Слишком длинный URL (массивные GET-параметры запроса) | Анализ строки запроса в логе доступа | Увеличить размер и число буферов `large_client_header_buffers 4 16k;` |
| **`499 Client Closed Request`** | Клиент разорвал TCP-соединение до получения ответа из-за тайм-аута или нажатия кнопки "Стоп" | `$status = 499` при высоком значении `$upstream_response_time` | Оптимизировать бэкенд; включить `proxy_ignore_client_abort on;` при необходимости |
| **`500 Internal Server Error`** | Зацикливание внутренних перенаправлений (`rewrite`); нет прав на каталоги временных файлов | `rewrite or internal redirection cycle` или `Permission denied` в `error.log` | Исправить терминирующие условия в `rewrite` / `try_files`; проверить права на `/var/lib/nginx/*` |
| **`502 Bad Gateway`** | Upstream-процесс не запущен; сброс соединения бэкендом; превышение буфера заголовка | `connect() failed (111: Connection refused)` или `upstream sent too big header` | Запустить службу бэкенда; проверить сокет; увеличить `proxy_buffer_size` |
| **`503 Service Unavailable`** | Срабатывание лимитов частоты запросов (`limit_req`) или числа соединений (`limit_conn`) | Записи `limiting requests, excess: ... by zone` в `error.log` | Скорректировать burst и rate в `limit_req_zone`; защитить критичные API |
| **`504 Gateway Timeout`** | Бэкенд не успел вернуть ответ в течение заданного интервала времени | Запись `upstream timed out (110: Connection timed out)` в `error.log` | Оптимизировать запросы к БД; увеличить `proxy_read_timeout` и `proxy_connect_timeout` |
| **`98: Address already in use`** | Порт уже занят другим процессом (Apache, старый Nginx, сторонний сервис) | `sudo ss -lptn 'sport = :80'` | Завершить процесс, занимающий порт, или изменить порт в `listen` |
| **`worker_connections are not enough`** | Исчерпан пул допустимых одновременных соединений рабочего процесса | Запись `[alert] ... worker_connections are not enough` в `error.log` | Увеличить `worker_connections` в `events {}` и поднять `worker_rlimit_nofile` |
| **`upstream sent too big header`** | Заголовки ответа бэкенда (большие cookies, JWT-токены) не поместились в буфер | Запись `upstream sent too big header while reading response header` в `error.log` | Увеличить `proxy_buffer_size 16k;` и `proxy_busy_buffers_size 32k;` |

### Детальный анализ типовых проблем

#### 1. Ошибка 499 — клиент закрыл соединение до ответа сервера

Код `499` является внутренним статусом Nginx. Он фиксируется, когда клиент инициирует закрытие TCP-сокета (`FIN` или `RST`), не дождавшись передачи ответа от веб-сервера.

**Анализ причин через декомпозицию таймингов в access-логе:**
Для локализации настройте расширенный формат логирования:
```nginx
log_format upstream_timing '$remote_addr - [$time_local] "$request" '
                           'status=$status req_time=$request_time '
                           'up_time=$upstream_response_time up_addr=$upstream_addr';
```
- **Сценарий А:** `$request_time` велик (например, 15 секунд), а `$upstream_response_time` составляет те же 15 секунд.  
  *Причина:* Бэкенд завис при выполнении медленного SQL-запроса или внешнего HTTP-вызова. Клиентский браузер или мобильное приложение прервало соединение по собственному таймауту.  
  *Решение:* Профилирование и оптимизация upstream-приложения.
- **Сценарий Б:** `$request_time` мал (0.5 секунды), `$upstream_response_time` равен `-` или меньше `$request_time`.  
  *Причина:* Пользователь быстро обновил страницу (F5) или перешел по другой ссылке. Это естественное поведение пользователей, не требующее вмешательства.
- **Сценарий В:** Необходимость гарантированного выполнения транзакции на бэкенде:
  ```nginx
  location /api/payment/ {
      proxy_pass http://payment_backend;
      # Запретить Nginx обрывать соединение с бэкендом при уходе клиента
      proxy_ignore_client_abort on;
  }
  ```

#### 2. Ошибка 502 — Bad Gateway при переполнении буфера заголовков

Если приложение возвращает массивный заголовок `Set-Cookie`, заголовок авторизации OAuth или отладочные метаданные, Nginx обрывает соединение с кодом `502`.

**Симптом в `error.log`:**
`[error] 1234#1234: *5678 upstream sent too big header while reading response header from upstream, client: 198.51.100.1, server: api.example.com, request: "POST /auth HTTP/1.1", upstream: "http://127.0.0.1:8000/auth"`

**Решение:**
Увеличьте размер первичного буфера заголовка ответа upstream (`proxy_buffer_size`) и буфера занятых страниц (`proxy_busy_buffers_size`):
```nginx
location / {
    proxy_pass http://backend;
    
    # Размер буфера для чтения строки статуса и HTTP-заголовков бэкенда
    proxy_buffer_size 16k;
    
    # Буферы для тела ответа
    proxy_buffers 8 16k;
    
    # Максимальный размер буферов, занятых отправкой ответа клиенту
    proxy_busy_buffers_size 32k;
}
```

#### 3. Предупреждение о буферизации ответа на диск

**Симптом в `error.log`:**
`[warn] 1234#1234: *8901 an upstream response is buffered to a temporary file /var/lib/nginx/proxy/1/00/0000000001 while reading upstream`

**Причина:**
Размер ответа от бэкенда превысил суммарную емкость буферов в оперативной памяти (`proxy_buffers 8 8k = 64k`). Nginx вынужден сбрасывать остаток ответа во временный файл на диске, что снижает скорость отдачи и нагружает дисковую подсистему.

**Решение:**
1. Если сервер располагает достаточным объемом RAM и отдает динамические документы среднего размера (например, JSON-ответы по 200–500 КБ), увеличьте объем буферов в памяти:
   ```nginx
   proxy_buffers 16 64k;
   proxy_buffer_size 64k;
   proxy_busy_buffers_size 128k;
   ```
2. Для отдачи тяжелых файлов и потокового видео отключите буферизацию полностью, переключив Nginx в режим прямого проксирования:
   ```nginx
   proxy_buffering off;
   ```

#### 4. Ошибка привязки к порту (Address already in use)

**Симптом:**
`nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)`

**Диагностика:**
```bash
# Поиск процесса, захватившего порт 80
sudo ss -lptn 'sport = :80'
# → LISTEN 0 128 0.0.0.0:80 0.0.0.0:* users:(("apache2",pid=8542,fd=4))
```

**Решение:**
1. Если порт занят другим веб-сервером (например, `apache2`):
   ```bash
   sudo systemctl stop apache2
   sudo systemctl disable apache2
   ```
2. Если порт удерживается "зависшим" процессом старого Nginx, не закрывшим сокет:
   ```bash
   sudo killall -9 nginx
   sudo systemctl start nginx
   ```

#### 5. Ошибки переполнения зон разделяемой памяти (Shared Memory)

**Симптомы в `error.log`:**
- `could not allocate new session in SSL session shared cache "SSL"`
- `could not allocate ... in shared memory zone "req_limit_per_ip"`

**Причина:**
Зона памяти, выделенная под таблицу состояний ограничения частоты запросов (`limit_req_zone`) или кэш TLS-сессий (`ssl_session_cache`), заполнена уникальными ключами (IP-адресами клиентов). Аллокатор памяти (slab allocator) исчерпал свободные страницы.

**Решение:**
Увеличьте объем выделяемой разделяемой памяти в директиве объявления зоны:
```nginx
# Увеличение зоны для кэширования TLS-сессий (10 МБ хранит ~40 000 сессий)
ssl_session_cache shared:SSL:20m;

# Увеличение зоны для лимитов запросов (1 МБ хранит ~16 000 IP-адресов)
limit_req_zone $binary_remote_addr zone=req_limit_per_ip:32m rate=10r/s;
```

## Рекомендации и лучшие практики

### Эксплуатация и управление конфигурацией (DevOps / SRE)

1. **Контроль версий и автоматическая валидация:**
   Всегда храните файлы конфигурации Nginx в системе контроля версий (Git). Внедрите pre-commit хуки и шаги CI/CD, выполняющие валидацию синтаксиса `nginx -t` в изолированном контейнере перед деплоем на серверы.
2. **Атомарность внесения изменений:**
   Исключите прямое редактирование файлов в рабочей директории `/etc/nginx/sites-enabled/`. Формируйте обновленные файлы во временной папке, валидируйте их через `nginx -t -c <новый_файл>` и атомарно подменяйте через команду `mv`.
3. **Graceful Reload в пайплайнах:**
   При автоматизированном деплое используйте только `systemctl reload nginx` (или `nginx -s reload`). Команду `restart` применяйте исключительно при обновлении бинарных зависимостей, смене `worker_rlimit_nofile` или параметров разделяемой памяти ядра.
4. **Конфигурация дефолтного виртуального хоста (Catch-All):**
   Всегда настраивайте явный виртуальный хост с флагом `default_server`, отсекающий некорректный мусорный трафик и сканеры уязвимостей, обращающиеся напрямую по IP-адресу:
   ```nginx
   server {
       listen 80 default_server;
       listen 443 ssl default_server;
       server_name _;
       ssl_reject_handshake on; # Nginx 1.19.4+ отклоняет TLS-рукопожатие для неизвестных SNI
       return 444; # Сброс соединения без отправки HTTP-ответа
   }
   ```

### Системный харденинг и безопасность

1. **Принцип минимальных привилегий:**
   Worker-процессы обязаны работать от непривилегированного пользователя (`user www-data www-data;` или `user nginx nginx;`). Запретите пользователю Nginx доступ к командной оболочке (`usermod -s /usr/sbin/nologin www-data`).
2. **Скрытие версий и служебных заголовков:**
   Отключите трансляцию номера версии веб-сервера в ответах и стандартных страницах ошибок: `server_tokens off;`.
3. **Изоляция служебных метрик:**
   Закрывайте доступ к эндпоинтам `stub_status` директивами `allow 127.0.0.1; deny all;` либо выносите их на отдельный закрытый порт, привязанный к loopback-интерфейсу (`127.0.0.1:8080`).

### Производительность сетевого стека ядра Linux

Для предотвращения сетевых блокировок под высокой нагрузкой зафиксируйте параметры в `/etc/sysctl.d/99-nginx.conf`:

```ini
# Максимальный размер очереди прослушивания сокетов
net.core.somaxconn = 65535

# Максимальное количество соединений в очереди неполного рукопожатия (SYN queue)
net.ipv4.tcp_max_syn_backlog = 16384

# Разрешить повторное использование сокетов в состоянии TIME_WAIT
net.ipv4.tcp_tw_reuse = 1

# Расширение диапазона локальных портов для исходящих upstream-соединений
net.ipv4.ip_local_port_range = 10240 65535

# Максимальное число пакетов в очереди сетевого интерфейса до обработки ядром
net.core.netdev_max_backlog = 16384
```
