# Nginx: Правила Rewrite, Redirect и Директива try_files

Этот документ описывает основные принципы работы с правилами перезаписи URL (rewrite), перенаправления (redirect) и директивой `try_files` в Nginx.

## 1. Директива `rewrite`

Директива `rewrite` используется для изменения URI запроса. Она работает на основе регулярных выражений (PCRE) и позволяет манипулировать запросом до того, как Nginx начнет искать соответствующий `location`.

**Синтаксис:**
`rewrite regex replacement [flag];`

*   `regex`: Регулярное выражение для сопоставления с URI.
*   `replacement`: URI, на который будет перезаписан запрос. Захваченные группы из `regex` доступны как `$1`, `$2` и т.д.
*   `flag`: Определяет дальнейшее поведение Nginx.

### Флаги `rewrite`

1.  **`last` (внутренний редирект):**
    *   После перезаписи URI Nginx прекращает обработку текущего набора `rewrite` правил и начинает новый поиск `location` для нового URI.
    *   Браузер не узнает об изменении URI.
    *   **Пример:**
        ```nginx
        location / {
            rewrite ^/2/(.*)$ /1/$1 last;
            # ...
        }
        ```
        Запрос `/2/file.txt` будет внутренне перезаписан в `/1/file.txt`.

2.  **`redirect` (временный внешний редирект 302):**
    *   Nginx отправляет клиенту ответ с кодом `302 Found` и новым URI в заголовке `Location`.
    *   Браузер выполняет новый запрос по указанному URI.
    *   Используется для временных перенаправлений, не кэшируется браузерами надолго.
    *   **Пример:**
        ```nginx
        location / {
            rewrite ^/2/(.*)$ /1/$1 redirect;
            # ...
        }
        ```
        Запрос `/2/file.txt` приведет к редиректу на `http://your_domain/1/file.txt`.

3.  **`permanent` (постоянный внешний редирект 301):**
    *   Nginx отправляет клиенту ответ с кодом `301 Moved Permanently` и новым URI.
    *   Браузер кэширует этот редирект и в дальнейшем будет сразу обращаться по новому адресу.
    *   Используется для постоянных изменений URL. **Будьте крайне осторожны:** `301` редиректы агрессивно кэшируются браузерами и могут значительно усложнить отладку и тестирование. Если вы не уверены в постоянстве изменения, лучше использовать `302` (`redirect`) или `307` (`temporary`).
    *   **Пример:**
        ```nginx
        location / {
            rewrite ^/2/(.*)$ /1/$1 permanent;
            # ...
        }
        ```

## 2. Директива `return`

Директива `return` используется для немедленного завершения обработки запроса и отправки ответа клиенту с указанным кодом состояния. Она более эффективна, чем `rewrite`, когда нужно просто вернуть код ответа или перенаправить на другой URL без сложной логики регулярных выражений.

**Синтаксис:**
`return code [text];`
`return code URL;`

*   `code`: HTTP-код ответа (например, `200`, `301`, `302`, `403`, `404`, `500`).
*   `text`: Необязательный текст для ответа.
*   `URL`: URL для перенаправления (используется с кодами `301`, `302`, `303`, `307`, `308`).

**Пример: Редирект с HTTP на HTTPS (рекомендуемый способ):**
```nginx
server {
    listen 80;
    server_name your_domain.com www.your_domain.com;
    return 301 https://$host$request_uri;
}
```
Этот подход предпочтительнее использования `rewrite` для простых редиректов, так как он не задействует механизм регулярных выражений и работает быстрее.

## 3. Директива `try_files`

Директива `try_files` позволяет Nginx проверять существование файлов или директорий в указанном порядке и отдавать первый найденный. Если ничего не найдено, выполняется последнее действие (обычно внутренняя переадресация или возврат кода ошибки).

Это мощный инструмент для реализации "красивых" URL, страниц-заглушек или обработки запросов к динамическим приложениям.

**Синтаксис:**
`try_files file ... uri;`
`try_files file ... =code;`

*   `file`: Путь к файлу или директории, который Nginx будет пытаться найти.
    *   `$uri`: Текущий URI запроса.
    *   `$uri/`: Текущий URI запроса с добавленным слешем (для проверки директорий).
*   `uri`: Внутренний редирект на указанный URI, если ни один файл не найден.
*   `=code`: Возврат указанного HTTP-кода, если ни один файл не найден.

**Примеры использования `try_files`:**

1.  **Отдача статики с fallback на 404:**
    ```nginx
    location / {
        root /var/www/site;
        try_files $uri $uri/ =404;
    }
    ```
    Nginx сначала попытается найти файл, соответствующий `$uri`. Если не найдет, попробует найти директорию `$uri/` (и в ней индексный файл). Если и это не удастся, вернет ошибку `404 Not Found`.

2.  **Отдача статики с fallback на PHP-скрипт (типично для WordPress):**
    ```nginx
    location / {
        root /var/www/wordpress;
        try_files $uri $uri/ /index.php?$args;
    }
    ```
    Если запрошенный файл или директория не найдены, запрос внутренне перенаправляется на `index.php` с сохранением всех аргументов.

3.  **Использование с именованными `location`:**
    `try_files` может перенаправлять на именованный `location` (начинающийся с `@`), что полезно для более сложной логики.
    ```nginx
    location /admin/ {
        auth_basic "Admin Area";
        auth_basic_user_file /etc/nginx/htpasswd;
        try_files $uri @admin_content;
    }

    location @admin_content {
        # Здесь будет обрабатываться контент после успешной аутентификации
        return 200 "Secret admin content";
    }
    ```
    В этом случае `auth_basic` гарантированно отработает до того, как управление будет передано в `location @admin_content`.

## 4. Условная логика с `if`

Директива `if` позволяет выполнять действия на основе условий. Однако её использование в Nginx **крайне не рекомендуется** из-за сложности, потенциальных проблем с производительностью и отладкой (известна как "If is Evil"). По возможности следует использовать `try_files` или `map`, которые являются более безопасными и предсказуемыми альтернативами.

**Синтаксис:**
`if (condition) { ... }`

**Примеры условий:**
*   `-f` или `!-f`: Проверка существования файла.
*   `-d` или `!-d`: Проверка существования директории.
*   `-e` или `!-e`: Проверка существования файла или директории.
*   `~` или `~*`: Сопоставление с регулярным выражением.

**Пример (не рекомендуется, но встречается):**
```nginx
location / {
    if (!-f $request_filename) {
        rewrite ^(.*)$ /index.php?$1 last;
    }
}
```
Этот пример проверяет, существует ли запрошенный файл. Если нет, то запрос перезаписывается на `index.php`.

## 5. Директива `map`

Директива `map` позволяет создавать переменные, значения которых зависят от значений других переменных. Это более безопасная и производительная альтернатива `if` для создания условной логики. `map` объявляется в блоке `http`.

**Синтаксис:**
```nginx
map string $variable {
    default value;
    string1 value1;
    regex value2;
    ...
}
```

**Пример: Определение переменной для логирования редиректов:**
```nginx
http {
    map $status $loggable_redirect {
        ~^3   1;
        default 0;
    }

    # ...
}
```
Здесь, если код статуса (`$status`) начинается с `3` (т.е. `301`, `302` и т.д.), переменная `$loggable_redirect` будет `1`, иначе `0`.

## 6. Логирование редиректов

Для отслеживания редиректов можно настроить специальный формат лога и использовать условное логирование.

**Пример конфигурации в `nginx.conf` (в блоке `http`):**

```nginx
http {
    # ...
    log_format redirect_log '$remote_addr - $remote_user [$time_local] "$request" '
                            '$status $body_bytes_sent "$http_referer" '
                            '"$http_user_agent" "$http_x_forwarded_for" '
                            '"$sent_http_location"'; # Куда произошел редирект

    map $status $loggable_redirect {
        ~^3   1;
        default 0;
    }

    # ...
    server {
        # ...
        access_log /var/log/nginx/redirects.log redirect_log if=$loggable_redirect;
        # ...
    }
}
```
В этом примере создается специальный формат лога `redirect_log`, который включает поле `$sent_http_location` (содержит URL, на который был выполнен редирект). Затем, с помощью `map`, определяется переменная `$loggable_redirect`, которая становится `1` для всех 3xx статусов. Директива `access_log` с условием `if=$loggable_redirect` будет записывать в `redirects.log` только те запросы, которые привели к редиректу.
