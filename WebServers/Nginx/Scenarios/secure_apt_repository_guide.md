# Создание защищенного Apt-репозитория с помощью Nginx и mTLS

## 1. Определения

**Защищенный Apt-репозиторий** — это репозиторий пакетов, доступ к которому ограничен и возможен только для клиентов, обладающих валидным SSL-сертификатом, выданным собственным центром сертификации (CA).

Для реализации используются следующие технологии:

* `reprepro` для управления репозиторием.
* `OpenSSL` для создания и управления CA и сертификатами.
* `Nginx` для публикации репозитория и принудительной аутентификации клиентов по принципу **mTLS** (взаимной аутентификации).

---

## 2. Основные концепции

Общая схема работы выглядит следующим образом:

1. **Создается инфраструктура открытых ключей (PKI):** Настраивается собственный CA, выпускается сертификат для Nginx-сервера и по одному сертификату для каждого клиента.
2. **Создается Apt-репозиторий:** С помощью `reprepro` создается репозиторий и в него добавляются пакеты.
3. **Настраивается Nginx:** Конфигурируется Nginx для раздачи статических файлов репозитория и включается обязательная проверка клиентских сертификатов (mTLS).
4. **Настраивается клиент:** Клиентская машина настраивается для использования защищенного репозитория, для чего `apt` предоставляется клиентский сертификат и ключ.

---

## 3. Практический сценарий

### 3.1. Создание центра сертификации (CA)

Первым делом необходимо создать свой центр сертификации. Он будет использоваться для подписи всех сертификатов, обеспечивая единую точку доверия.

Вам понадобятся:

* Корневой сертификат CA (`ca.crt`).
* Сертификат для сервера Nginx (`nginx.crt` и `nginx.key`), подписанный вашим CA.
* Сертификат для клиента (`client.crt` и `client.key`), подписанный вашим CA.
* Список отозванных сертификатов (`crl.pem`).

> **Подробное руководство: [Управление собственным CA с помощью OpenSSL](../../../Security/Tools/openssl_ca/single_tier/overview.md)**

### 3.2. Создание приватного Apt-репозитория

Далее, создадим сам репозиторий с помощью `reprepro` и подпишем его GPG-ключом.

> **Подробное руководство: [Создание приватного Apt-репозитория с reprepro](../../../Linux/PackageManagement/deb_private_apt_repository_reprepro/practical_scenarios.md**

На этом же этапе вы можете создать и добавить в репозиторий свои собственные пакеты.

> **Подробное руководство: [Создание простого .deb пакета](../../../Linux/PackageManagement/package_build/definitions.md)**

После выполнения этого шага у вас должна быть директория (например, `/var/www/my-repo`), содержащая структуру репозитория `reprepro`.

### 3.3. Настройка Nginx для раздачи и защиты репозитория

Это ключевой шаг, где мы объединяем Nginx и PKI. Мы настроим Nginx так, чтобы он раздавал GPG-ключ по HTTP, а сам репозиторий — только по HTTPS с обязательной проверкой сертификата клиента.

```nginx
# Сервер для раздачи GPG-ключа и редиректа на HTTPS
server {
    listen 80;
    server_name repo.your.domain;

    root /var/www/my-repo;

    # Раздаем публичный GPG-ключ без аутентификации
    # (предполагается, что ключ лежит в корне репозитория как repo.key)
    location /repo.key {
        try_files $uri =404;
    }

    # Все остальные запросы перенаправляем на HTTPS
    location / {
        return 301 https://$host$request_uri;
    }
}

# Основной сервер, раздающий репозиторий по HTTPS с mTLS
server {
    listen 443 ssl http2;
    server_name repo.your.domain;

    root /var/www/my-repo; # Путь к директории reprepro

    # --- Сертификаты сервера ---
    ssl_certificate /path/to/your/nginx.crt;
    ssl_certificate_key /path/to/your/nginx.key;

    # --- Настройка mTLS для защиты репозитория ---
    # Корневой сертификат для проверки клиентов
    ssl_client_certificate /path/to/your/ca.crt;
    # Включаем обязательную проверку
    ssl_verify_client on;
    # Список отозванных сертификатов
    ssl_crl /path/to/your/crl.pem;

    location / {
        autoindex on; # Для удобства просмотра в браузере
        # Запрещаем доступ к конфиденциальным директориям
        location ~ /(db|conf)/ {
            deny all;
            return 404;
        }
    }
}
```

> **Подробное руководство: [Аутентификация по клиентским SSL-сертификатам в Nginx](../Security/TLS_SSL/nginx_tls_ssl_overview.md#7-Аутентификация-по-клиентским-ssl-сертификатам-mtls)**

### 3.4. Настройка Apt-клиента

#### 3.4.1. Настройка источника и GPG-ключа

```bash
# Создаем файл списка источников
echo "deb [arch=amd64] https://repo.your.domain focal main" | sudo tee /etc/apt/sources.list.d/my-repo.list

# Скачиваем GPG-ключ и кладем его в доверенные
# (используем HTTP, так как этот эндпоинт не требует аутентификации)
sudo wget -O /etc/apt/trusted.gpg.d/my-repo.asc http://repo.your.domain/repo.key
```

#### 3.4.2. Установка корневого сертификата CA

Чтобы система клиента доверяла сертификату нашего Nginx-сервера, необходимо добавить корневой сертификат CA (`ca.crt`) в системное хранилище.

```bash
# Копируем корневой сертификат на клиентскую машину
sudo cp ca.crt /usr/local/share/ca-certificates/my-ca.crt

# Обновляем хранилище сертификатов
sudo update-ca-certificates
```

#### 3.4.3. Настройка Apt для использования клиентского сертификата

Теперь нужно указать `apt`, где брать клиентский сертификат и ключ для аутентификации на сервере `repo.your.domain`.

Создайте файл `/etc/apt/apt.conf.d/99-my-repo-auth`:

```
# /etc/apt/apt.conf.d/99-my-repo-auth
Acquire::https::repo.your.domain {
    SslCert "/etc/apt/ssl/client.crt";
    SslKey "/etc/apt/ssl/client.key";
};
```

* Замените `repo.your.domain` на имя вашего сервера.
* Скопируйте `client.crt` и `client.key` в `/etc/apt/ssl/` на клиентской машине и убедитесь, что права доступа к ключу ограничены (`sudo chmod 600 /etc/apt/ssl/client.key`).

#### 3.4.4. Проверка

Обновите список пакетов. Если все настроено правильно, команда выполнится без ошибок.

```bash
sudo apt-get update
```

Если вы попытаетесь выполнить `apt-get update` без правильной конфигурации SSL в `apt.conf.d`, вы получите ошибку, так как Nginx отклонит соединение.

## 4. Дополнительная информация

### Настройка приоритетов пакетов

После добавления приватного репозитория может возникнуть ситуация, когда пакеты в нем конфликтуют с пакетами из официальных репозиториев. Чтобы управлять, какая версия пакета будет установлена, используется механизм приоритетов (pinning).

Например, вы можете захотеть, чтобы пакеты из вашего репозитория всегда предпочитались, даже если их версия ниже.

> **Подробное руководство: [Управление приоритетами пакетов в Apt (Pinning)](../../../Linux/PackageManagement/deb_apt_pinning.md)**
