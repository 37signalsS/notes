# Установка и базовая настройка Nginx

## Установка

Для установки Nginx в дистрибутивах на базе Debian/Ubuntu используется команда:
```bash
apt update && apt -y install nginx
```
После установки сервис обычно запускается автоматически. Проверить его статус можно командой:
```bash
systemctl status nginx
```

### Проверка состояния Nginx и открытых портов

Для более глубокой проверки работы Nginx и используемых им портов, а также для диагностики возможных проблем, можно использовать следующие команды:

*   **Просмотр запущенных процессов Nginx:**
    ```bash
    ps aux | grep nginx
    ```
    Эта команда покажет мастер-процесс Nginx и его воркер-процессы. Если Nginx запущен, вы увидите примерно такую картину:
    ```
    root      1234  0.0  0.0  xxxxx  xxxx ?        Ss   HH:MM   0:00 nginx: master process /usr/sbin/nginx -g daemon on;
    www-data  1235  0.0  0.0  xxxxx  xxxx ?        S    HH:MM   0:00 nginx: worker process
    www-data  1236  0.0  0.0  xxxxx  xxxx ?        S    HH:MM   0:00 nginx: worker process
    ...
    ```
    (PID и другие параметры будут отличаться)

*   **Проверка открытых портов и слушающих сервисов:**
    ```bash
    ss -ntlp
    ```
    Эта команда покажет все открытые сетевые сокеты (TCP), их состояние, а также процессы, которые их слушают. Вы должны увидеть Nginx, слушающий на 80-м (HTTP) и/или 443-м (HTTPS) портах:
    ```
    Netid State  Recv-Q Send-Q Local Address:Port   Peer Address:Port Process
    tcp   LISTEN 0      128    0.0.0.0:80           0.0.0.0:*       users:(("nginx",pid=1234,fd=6))
    tcp   LISTEN 0      128    [::]:80              [::]:*          users:(("nginx",pid=1234,fd=7))
    ...
    ```
    (Порты и PID будут зависеть от вашей конфигурации)

    Если вы устанавливали Apache, то при его запуске на другом порту (например, 8080), вы увидите и его:
    ```
    Netid State  Recv-Q Send-Q Local Address:Port   Peer Address:Port Process
    tcp   LISTEN 0      128    0.0.0.0:8080         0.0.0.0:*       users:(("apache2",pid=5678,fd=4))
    ...
    ```
    Эти команды крайне полезны для быстрой диагностики, например, если веб-сервер не отвечает или вы подозреваете конфликт портов.
## Структура конфигурационных файлов

Понимание структуры конфигурации — ключ к работе с Nginx.

*   **Главный файл:** `/etc/nginx/nginx.conf`. Это точка входа, с которой Nginx начинает чтение конфигурации.
*   **Директива `include`:** Внутри `nginx.conf` активно используется директива `include`, которая позволяет подключать другие файлы, делая конфигурацию модульной и чистой.
*   **Фрагменты конфигурации:**
    *   `/etc/nginx/conf.d/*.conf`: Часто используется для подключения глобальных настроек или конфигураций, не относящихся к конкретным сайтам.
    *   `/etc/nginx/sites-available/` и `/etc/nginx/sites-enabled/`: Классический подход в Debian/Ubuntu.
        *   `sites-available`: Содержит файлы конфигурации для всех возможных сайтов.
        *   `sites-enabled`: Содержит символические ссылки на файлы в `sites-available`. Nginx читает только эту директорию для загрузки сайтов. Это позволяет легко "включать" и "выключать" сайты, создавая или удаляя симлинки. В Ubuntu принято, что директории с суффиксом `enabled` содержат символические ссылки на файлы из директорий с суффиксом `available`.

### Основные директивы в `nginx.conf`

*   `user www-data;`: Указывает, от имени какого пользователя будут работать рабочие процессы.
*   `worker_processes auto;`: Определяет количество рабочих процессов. Значение `auto` (рекомендовано) автоматически устанавливает его равным количеству ядер процессора. Это оптимально, так как каждый рабочий процесс Nginx является однопоточным и может эффективно утилизировать одно ядро CPU. Чтобы распределить нагрузку между всеми ядрами процессора, Nginx запускает несколько таких воркеров.
*   `pid /run/nginx.pid;`: Путь к файлу, где хранится PID мастер-процесса.
*   `events { ... }`: Блок для настроек, связанных с обработкой соединений (например, `worker_connections`).
*   `http { ... }`: Основной блок для конфигурации веб-сервера. Большинство настроек (включая `server` блоки) находятся здесь.

## Управление сервисом и конфигурацией

Nginx считывает конфигурацию только при запуске. Чтобы изменения вступили в силу, необходимо дать ему сигнал перечитать файлы.

**Правильная процедура применения изменений:**

1.  **Проверка синтаксиса (Обязательно!):**
    Всегда проверяйте конфигурацию на наличие ошибок перед ее применением. Это защитит работающий сервер от сбоев из-за опечаток.
    ```bash
    sudo nginx -t
    ```
    Если все в порядке, вы увидите `syntax is ok` и `test is successful`.

2.  **Грациозная перезагрузка (Graceful Reload):**
    Эта команда плавно применяет новую конфигурацию, обеспечивая **нулевое время простоя (zero downtime)**. Мастер-процесс запускает новые рабочие процессы с обновленной конфигурацией и ожидает, пока старые процессы завершат обработку текущих запросов, после чего отключает их.
    ```bash
    sudo nginx -s reload
    ```
    Это сокращенная команда. Альтернатива в системах с `systemd` (считается более "идеологически верной" и полной командой):
    ```bash
    sudo systemctl reload nginx
    ```
    **Важно:** Всегда выполняйте `sudo nginx -t` перед `reload`. Если конфигурация уже поломана, `reload` не сработает, и вы не узнаете об ошибке. `nginx -t` обязательно перед `reload`.
    **Никогда не используйте `restart`** для применения изменений конфигурации, так как это приводит к полной остановке и перезапуску сервера, обрывая текущие соединения.

## Настройка нескольких сайтов (Virtual Hosts / Server Blocks)

Виртуальные хосты (в терминологии Nginx — "server blocks") позволяют одному серверу Nginx обслуживать множество сайтов (доменов) на одном IP-адресе и порту.

### Принцип работы

1.  **DNS-разрешение:** Браузер пользователя через DNS преобразует доменное имя сайта (например, `site.ru`) в IP-адрес сервера.
2.  **TCP-соединение:** Браузер устанавливает TCP-соединение с сервером по полученному IP-адресу и стандартному порту (80 для HTTP, 443 для HTTPS).
3.  **HTTP-запрос с заголовком `Host`:** После установки соединения браузер отправляет HTTP-запрос. Ключевым элементом этого запроса является заголовок `Host`, в котором передается исходное доменное имя (например, `Host: site.ru`). Несмотря на то, что подключение к серверу происходит по IP-адресу и порту, именно заголовок `Host` позволяет Nginx определить, какой из множества сайтов, размещенных на одном сервере, должен обработать запрос.
4.  **Выбор Server Block в Nginx:** Nginx принимает запрос и на основе значения заголовка `Host` ищет соответствующий `server` блок, у которого директива `server_name` совпадает с этим значением.
5.  **Обработка запроса:** Найденный `server` блок обрабатывает запрос согласно своей конфигурации (отдает статику, проксирует на бэкенд и т.д.).

Таким образом, заголовок `Host` является основой механизма, позволяющего "разделять" сайты на одном сервере, обеспечивая мультисайтовость.

### Пример конфигурации

Создайте файл конфигурации для вашего сайта в `/etc/nginx/sites-available/` и создайте на него символическую ссылку в `/etc/nginx/sites-enabled/`.

```nginx
# /etc/nginx/sites-available/example.com
server {
  listen 80;
  server_name example.com www.example.com;
  root /var/www/example.com;
  index index.html index.htm;

  location / {
    # Пытается найти файл, соответствующий URI.
    # 1. $uri: Проверяет наличие файла (для /about.html ищет /var/www/example.com/about.html).
    # 2. $uri/: Если файл не найден, проверяет наличие директории и ищет в ней индексный файл.
    # 3. =404: Если ничего не найдено, возвращает ошибку 404.
    try_files $uri $uri/ =404;
  }

  # Блокируем доступ к скрытым файлам (например, .htaccess)
  location ~ /\.ht {
      deny all;
  }
}
```

## Порядок обработки `server` блоков

Когда приходит HTTP-запрос, Nginx выбирает подходящий `server` блок по **двум этапам**:

### **ЭТАП 1: Выбор по `listen`**

Nginx сначала выбирает **все `server` блоки**, у которых директива `listen` соответствует паре IP-адрес:порт, на которую пришел запрос.

*   `listen 80;` — слушает порт 80 на всех IP-адресах.
*   `listen 192.168.1.10:80;` — слушает порт 80 только на конкретном IP. Эта конфигурация считается **более специфичной**.

### **ЭТАП 2: Выбор по `server_name`**

Среди выбранных на первом этапе блоков, Nginx ищет **наиболее подходящее значение `server_name`**, сравнивая его с заголовком `Host` из запроса.

**Правила приоритета:**

1.  **Точное совпадение** с `server_name` — приоритет №1.
2.  **Маска с `*` в начале** (`*.example.com`) — менее приоритетны.
3.  **Маска с `*` в конце** (`www.example.*`) — еще менее приоритетны.
4.  **Регулярные выражения (`~`)** — ещё ниже.
5.  **Если ничего не подошло** — используется **сервер по умолчанию**.

### Сервер по умолчанию (`default_server`)

Сервером по умолчанию становится:
1.  Блок, явно помеченный флагом `default_server` в директиве `listen` для данной пары IP:порт.
    ```nginx
    listen 80 default_server;
    ```
2.  Если `default_server` не указан, то **первый** `server` блок в конфигурации для данного порта.

Это важно: если запрос приходит по IP-адресу или на домен, не прописанный ни в одном `server_name`, он будет обработан сервером по умолчанию.

**Нюанс со специфичностью `listen`:**
Nginx всегда отдает приоритет наиболее специфичной директиве `listen`. Рассмотрим пример:
У вас есть два `server` блока:
*   Один с `listen 80 default_server;` (слушает порт 80 на всех IP-адресах как сервер по умолчанию).
*   Второй с `listen 192.168.1.10:80;` (слушает порт 80 только на конкретном IP-адресе).

Если запрос приходит на `192.168.1.10:80` без совпадающего `Host` (например, по прямому IP-адресу), он будет обработан **вторым блоком**. Это происходит потому, что его директива `listen` (`192.168.1.10:80`) является более специфичной, чем `listen 80` первого блока, даже если первый помечен как `default_server` для всех адресов.

Чтобы первый блок был главным по умолчанию и для этого конкретного IP, ему также нужно добавить специфичную директиву `listen 192.168.1.10:80 default_server;`. Таким образом, Nginx сначала выбирает наиболее специфичный `listen`, а затем уже применяет правила `default_server` и `server_name` внутри этого выбора.

### HTTPS и SNI

С TLS (порт 443) выбор `server` работает так же, **но только после того, как завершено TLS-рукопожатие**. Используется **SNI (Server Name Indication)** — клиент сообщает имя хоста ещё до расшифровки HTTPS, что позволяет Nginx выбрать правильный сертификат и `server` блок.

## Диагностика и локальное тестирование

### 1. Проверка сети на сервере
*   **Слушает ли Nginx нужный порт?**
    ```bash
    # ss - современная утилита
    ss -tlpn | grep nginx
    # netstat - устаревшая, но все еще встречается
    netstat -tlpn | grep nginx
    ```
    Убедитесь, что Nginx слушает нужную комбинацию IP-адреса и порта. `0.0.0.0` означает "все IP-адреса".

*   **Какие IP-адреса есть на сервере?**
    ```bash
    ip a
    ```
    Если вы видите только приватные IP (например, `192.168.x.x`, `10.x.x.x`), возможно, ваш сервер находится за NAT, и вам нужно использовать внешний ("белый") IP-адрес для настройки DNS.

### 2. Проверка DNS
*   **Куда указывает домен?**
    ```bash
    # Утилита host
    host example.com
    # Утилита ping (даже если пинги закрыты, IP-адрес будет показан)
    ping example.com
    ```
    Убедитесь, что домен разрешается в правильный IP-адрес вашего сервера.

### 3. Локальное тестирование с файлом `hosts`
Чтобы протестировать сайт на сервере до изменения глобальных DNS-записей, вы можете "обмануть" свой локальный компьютер (клиент), прописав соответствие домена и IP-адреса в файле `hosts`. Это особенно полезно, когда вы работаете с виртуальными машинами или тестируете новый сайт, не затрагивая публичные DNS-записи.

*   **Важно:** Изменения вносятся на **клиентской машине** (там, где установлен ваш браузер), а не на сервере Nginx. Для Nginx на сервере не имеет значения, как работает DNS на клиенте, он лишь обрабатывает входящие запросы с заголовком `Host`.

*   **Путь к файлу:**
    *   **Linux/macOS:** `/etc/hosts`
    *   **Windows:** `C:\Windows\System32\drivers\etc\hosts` (требуются права администратора для редактирования)

*   **Пример записи:**
    Добавьте в конец файла строку:
    ```
    11.22.33.44   example.com www.example.com test.example.com
    ```
    Где `11.22.33.44` — IP-адрес вашего сервера.

После сохранения файла `hosts` ваш браузер будет направлять запросы к `example.com` напрямую на указанный IP, минуя публичный DNS. Файл `hosts` имеет приоритет над DNS-записями.

> **Важно: Очистка кэша DNS браузера**
> Браузеры активно кэшируют DNS-записи. Если после изменения файла `hosts` изменения не применяются, необходимо очистить кэш DNS браузера. Это можно сделать, полностью закрыв и снова открыв браузер, используя режим инкогнито, или вручную очистив кэш DNS в настройках браузера (например, для Chrome: `chrome://net-internals/#dns`).

## Пример: Nginx как обратный прокси (Reverse Proxy)

Это одна из самых частых задач для Nginx. Он принимает запросы от клиентов и перенаправляет их на бэкенд-серверы (Apache, Node.js, Python-приложения и т.д.).

**Пример конфигурации для проксирования на Apache, работающий на `localhost:8080`:**

```nginx
server {
    listen 80;
    server_name example.com;

    location / {
        # Основная директива, перенаправляет запрос на бэкенд
        proxy_pass http://127.0.0.1:8080;

        # Передача реальных заголовков бэкенду, чтобы он "видел" клиента, а не прокси
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```
*   `proxy_pass`: Указывает адрес бэкенд-сервера.
*   `proxy_set_header`: Модифицирует заголовки, отправляемые на бэкенд. Это критически важно, чтобы бэкенд-приложение знало оригинальный домен запроса (`Host`), реальный IP клиента (`X-Real-IP`) и исходный протокол (`X-Forwarded-Proto`, http или https).

## Пример: Nginx + PHP-FPM

Для выполнения PHP-скриптов Nginx использует внешний обработчик — PHP-FPM (FastCGI Process Manager), взаимодействуя с ним по протоколу FastCGI.

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/example.com;
    index index.php index.html;

    location / {
        try_files $uri $uri/ /index.php?$args;
    }

    # Эта секция перехватывает все запросы к файлам, заканчивающимся на .php
    location ~ \.php$ {
        include snippets/fastcgi-php.conf;

        # Передаем запрос на обработку PHP-FPM через unix-сокет
        # Путь к сокету зависит от версии PHP, проверьте актуальный в /run/php/
        fastcgi_pass unix:/run/php/php8.1-fpm.sock;
        
        # Также можно использовать TCP-сокет, если PHP-FPM настроен слушать порт
        # fastcgi_pass 127.0.0.1:9000;
    }
}
> ➡️ **Подробное руководство: [Правила Rewrite, Redirect и Директива try_files в Nginx](./nginx_rewrite_rules_and_try_files.md)**
```
*   `fastcgi_pass`: Аналог `proxy_pass`, но для FastCGI-протокола. Указывает, куда отправлять PHP-скрипты на выполнение.
*   `include snippets/fastcgi-php.conf;`: В Debian/Ubuntu этот файл содержит стандартный набор необходимых `fastcgi_param`.

## Директивы `root` и `alias`

Обе директивы определяют, где на диске искать файлы, но делают это по-разному.

### `root`

-   **Как работает:** Добавляет URI запроса к пути, указанному в `root`.
-   **Пример:**
    ```nginx
    location /static/ {
        root /var/www/app;
    }
    ```
    -   Запрос: `/static/img/logo.png`
    -   Реальный путь: `/var/www/app` + `/static/img/logo.png` = `/var/www/app/static/img/logo.png`

### `alias`

-   **Как работает:** **Заменяет** часть URI, совпадающую с `location`, на путь, указанный в `alias`.
-   **Пример:**
    ```nginx
    location /static/ {
        alias /var/www/app/assets/;
    }
    ```
    -   Запрос: `/static/img/logo.png`
    -   Реальный путь: `/var/www/app/assets/` + `img/logo.png` = `/var/www/app/assets/img/logo.png`

**Ключевое отличие:** `alias` "отбрасывает" префикс `location` из пути.

**Когда использовать `alias`:**
-   Когда физический путь на диске не соответствует структуре URI.
-   Особенно полезен с регулярными выражениями и именованными группами.

**Пример с регулярным выражением:**
```nginx
location ~ ^/image1/(?<file>.+\.jpg)$ {
    alias /var/www/images/$file;
}
```
-   Запрос: `/image1/cats/kitty.jpg`
-   `$file` становится `cats/kitty.jpg`.
-   Реальный путь: `/var/www/images/cats/kitty.jpg`.

## Разбор регулярного выражения в `location`

Рассмотрим выражение `~ ^/image1/(?<file>.+\.jpg)$`.

1.  **`~`**
    -   Указывает, что это регулярное выражение с учетом регистра.

2.  **`^`**
    -   **Начало строки**. Указывает, что URI должен начинаться со следующего за ним шаблона.

3.  **`/image1/`**
    -   **Буквальный текст**: URI должен содержать `/image1/`.

4.  **`(?<file>.+\.jpg)`**
    -   Это **именованная группа захвата (named capture group)**.
    -   `(?<file>...)`: Все, что совпадет с шаблоном внутри скобок, будет сохранено в переменную `$file`.
    -   `.+`: Точка (`.`) означает любой символ (кроме новой строки), а плюс (`+`) — один или более раз. То есть, захватываем любую последовательность символов.
    -   `\.jpg`: Экранированная точка (`\.`) означает буквальный символ точки, за которым следует `jpg`.
    -   Вместе это означает: захватить любую последовательность символов, заканчивающуюся на `.jpg`, и сохранить ее в переменную `$file`.

5.  **`$`**
    -   **Конец строки**. Указывает, что после `.jpg` в URI больше ничего не должно быть.
