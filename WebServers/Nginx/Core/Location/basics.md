# Директива location: основы и приоритеты

## Определения

**Директива `location`** — контекстная директива Nginx, определяющая блок обработки входящего HTTP-запроса на основе сопоставления URI (Uniform Resource Identifier — унифицированный идентификатор ресурса) с заданным паттерном. Это центральный механизм маршрутизации запросов внутри блока `server`.

**HTTP (Hypertext Transfer Protocol — протокол передачи гипертекста)** — протокол прикладного уровня для передачи документов (HTML, CSS, изображений) и выполнения API-вызовов.

**URI (Uniform Resource Identifier — унифицированный идентификатор ресурса)** — строковый адрес, идентифицирующий ресурс в сети. В контексте Nginx используется для маршрутизации запросов.

**PCRE (Perl Compatible Regular Expressions — Перл-совместимые регулярные выражения)** — библиотека регулярных выражений, используемая Nginx для обработки `location` с модификаторами `~` и `~*`.

**JIT (Just-In-Time — компиляция «на лету»)** — режим компиляции регулярных выражений PCRE в машинный код при запуске Nginx, ускоряющий их выполнение.

**merge_slashes** — директива Nginx (по умолчанию `on`), управляющая схлопыванием двух и более идущих подряд слэшей в URI в один. Отключение (`off`) используется для контроля обхода путей атакующими.

**FastCGI (Fast Common Gateway Interface)** — бинарный протокол для взаимодействия веб-сервера с приложениями (преимущественно PHP через PHP-FPM).

**PHP-FPM (PHP FastCGI Process Manager — менеджер процессов FastCGI для PHP)** — менеджер процессов, реализующий FastCGI для PHP-приложений.

**Статика** — неизменяемые ресурсы (HTML, CSS, JS, изображения), отдаваемые Nginx напрямую без участия бэкенд-приложений.

**Префиксное дерево (Trie)** — структура данных, используемая Nginx для быстрого поиска префиксных `location` без последовательного перебора всех паттернов.

**Именованный location (`@name`)** — блок `location`, идентифицируемый именем после символа `@`, не участвующий в стандартном сопоставлении URI и вызываемый только явно через `try_files`, `error_page` или `X-Accel-Redirect`.

**Внутренний запрос** — запрос, генерируемый самим Nginx (через `rewrite`, `try_files`, `error_page`, `X-Accel-Redirect`, `auth_request`, `mirror`), без участия внешнего клиента.

**Subrequest (подзапрос)** — внутренний запрос Nginx к другому `location`, выполняемый параллельно или последовательно основному запросу.

## Базовые концепции

### Алгоритм выбора location и нормализация URI

#### Нормализация URI

Перед началом сопоставления Nginx выполняет **нормализацию URI**. Этот процесс включает три обязательных шага:

1.  **Декодирование percent-encoding:** Декодирование текста, закодированного в формате `%XX`. Например, `%2F` декодируется в `/`, `%20` — в пробел. Декодирование применяется многократно (рекурсивно), поэтому `%252F` декодируется до `%2F`, а затем до `/`. Это предотвращает обход ограничений через двойное кодирование.
2.  **Разрешение относительных путей:** Замена ссылок на относительные каталоги `.` и `..`. Nginx нормализует пути, например `/foo/../bar` становится `/bar`. Это предотвращает Directory Traversal через относительные пути в URI.
3.  **Схлопывание слэшей:** Замена двух или более идущих подряд слэшей на один (например, `//path//` → `/path/`). Это поведение контролируется директивой `merge_slashes` (по умолчанию `on`). Отключение (`merge_slashes off`) позволяет различать `//path` и `/path`, что используется для контроля обхода путей.

> **Важно:** Нормализация происходит до сопоставления с `location`. Любые директивы `rewrite` в контексте `server` выполняются ДО нормализации и могут изменить URI до неё.

#### Алгоритм сопоставления (N=1.0+)

Nginx использует следующий четкий алгоритм для выбора наиболее подходящего блока `location`:

1.  **Поиск точного совпадения (`=`):** Nginx ищет `location` с модификатором `=`. Если нормализованный URI запроса в точности совпадает, этот `location` используется немедленно, и поиск прекращается. Этот шаг имеет наивысший приоритет и выполняется до любых других проверок.
2.  **Поиск префиксных `location`:** Nginx проверяет все префиксные `location` (с модификатором `^~` и без него) и запоминает **самый длинный** из совпавших. Префиксные `location` хранятся в префиксном дереве (trie), что обеспечивает скорость поиска O(L), где L — длина URI.
3.  **Проверка на приоритетный префикс (`^~`):** Если самый длинный префикс, найденный на шаге 2, имел модификатор `^~`, Nginx немедленно использует его, **пропуская проверку регулярных выражений**. Это критически важно для производительности статических ресурсов.
4.  **Поиск по регулярным выражениям:** Если на шаге 3 поиск не был остановлен, Nginx проверяет все `location` с регулярными выражениями (`~` и `~*`) **в порядке их появления в файле конфигурации**. Первый же совпавший `location` используется, и поиск прекращается. Для ускорения PCRE с включенным JIT компилирует выражения в машинный код.
5.  **Использование сохраненного префикса:** Если ни одно регулярное выражение не совпало, Nginx использует **самый длинный префиксный `location`**, который он запомнил на шаге 2.

**Приоритет в целом:** `=` (точное совпадение) > `^~` (самое длинное префиксное совпадение, прекращает поиск) > `~` / `~*` (первое совпадение по порядку в файле) > без модификатора (самое длинное префиксное совпадение, если регулярные выражения не совпали).

### Модификаторы location и их поведение

Nginx различает `location` по наличию или отсутствию специальных модификаторов.

#### Префиксный location (без модификатора)

Это самый простой и распространенный тип. Префиксные `location` хранятся в префиксном дереве (trie), что обеспечивает высокую скорость сопоставления даже при большом количестве правил.

```nginx
location / { 
    # Основной блок: срабатывает для "посадочной страницы" (landing page) 
    # и как корень домена, если другие блоки не совпали.
}
```

- **Принцип работы:** Совпадает, если нормализованный URI запроса *начинается* с указанного префикса. Поиск осуществляется по префиксному дереву (trie), что эффективнее последовательного перебора.
- **Чувствительность к регистру:** На Linux/Unix-системах префиксное совпадение **чувствительно к регистру**, так как URI в этих системах обычно рассматривается с учетом регистра. На Windows и macOS (с файловыми системами HFS+/APFS по умолчанию) префиксное совпадение нечувствительно к регистру.
- **Правило выбора:** Среди всех совпавших префиксных `location`, Nginx выбирает тот, у которого **самый длинный префикс**. Порядок их объявления в конфигурационном файле **не имеет значения**. Если два префиксных `location` имеют одинаковую длину (что возможно при использовании регулярных выражений в префиксе), выбирается тот, который определен первым.
- **Регулярные выражения в префиксе:** Если префикс содержит регулярное выражение (например, `location ~ ^/api/v[12]/`), он обрабатывается как regex-блок, и его порядок в файле важен.

**Пример:**

```nginx
location / { ... }       # Конфигурация A
location /index/ { ... } # Конфигурация B
```

- Запрос `/index.html` → `location /index/` (Конфигурация B), так как префикс `/index/` длиннее.
- Запрос `/about.html` → `location /` (Конфигурация A).
- **`location /` (блок по умолчанию):** Если ничего другого не подошло, используется этот блок. Он является обязательным catch-all для большинства конфигураций.

> **Примечание:** `location = /` (точное совпадение) и `location /` (префикс) — это разные блоки с разным приоритетом. `location = /` имеет наивысший приоритет и используется только для корневого URI `/` без аргументов.

#### Точное совпадение (`=`)

Этот модификатор задает `location`, который сработает только при полном и точном совпадении URI.

```nginx
location = /exact.html { ... }
```

- **Принцип работы:** URI запроса должен быть в точности равен `/exact.html`.
- **Правило выбора:** Имеет **наивысший приоритет**. Если найдено точное совпадение, поиск немедленно прекращается, и используется этот `location`. Это повышает производительность для часто запрашиваемых путей (например, `/` или `/favicon.ico`).

#### [Регулярные выражения](../../../../Linux/Shell/regular_expressions.md) (`~` и `~*`)

Эти модификаторы позволяют задавать `location` с помощью регулярных выражений PCRE. Они обрабатываются **последовательно** в порядке объявления в конфигурационном файле, что делает порядок критически важным.

- `~`: регулярное выражение с учетом регистра.
- `~*`: регулярное выражение без учета регистра (case-insensitive). Эквивалентно использованию флага `(?i)` внутри выражения с `~`.

```nginx
# Перехватит запросы к изображениям, без учета регистра расширения
location ~* \.(gif|jpg|jpeg|png)$ { ... }

# Перехватит запросы к XML (Extensible Markup Language — расширяемый язык разметки) файлам, с учетом регистра
location ~ \.xml$ { ... }
```

- **Принцип работы:** Нормализованный URI запроса проверяется на соответствие регулярному выражению. Сопоставление выполняется с помощью `pcre_exec()` из библиотеки PCRE.
- **Правило выбора:** Регулярные выражения проверяются **в том порядке, в котором они указаны в конфигурационном файле**. Первый же совпавший `location` используется для обработки запроса, и дальнейший поиск прекращается. Это означает, что более общий паттерн, объявленный раньше, перехватит запрос, который должен был быть обработан более специфичным паттерном, объявленным позже.
- **Производительность:** При включенном `pcre_jit on;` (рекомендуется) регулярные выражения компилируются в машинный код при запуске Nginx, что ускоряет их выполнение в десятки раз. Без JIT регулярные выражения обрабатываются медленнее, чем префиксные `location`.

> **Важно:** Порядок следования `location` с регулярными выражениями критически важен. Неправильный порядок может привести к тому, что более специфичные правила никогда не будут выполнены.

#### Приоритетный префиксный location (`^~`)

Этот модификатор работает как обычный префиксный `location`, но с одним важным отличием, критичным для производительности.

```nginx
location ^~ /uploads/ { ... }
```

- **Принцип работы:** Совпадение по префиксу, аналогично префиксному `location` без модификатора.
- **Правило выбора:** Если этот `location` оказывается самым длинным совпавшим префиксом, Nginx **не будет проверять регулярные выражения**. Он немедленно использует этот `location`, завершая поиск на шаге 3 алгоритма. Это исключает накладные расходы на последовательную проверку всех regex-`location` в конфигурации.
- **Производительность:** Для больших конфигураций с десятками regex-`location` использование `^~` для статических директорий может снизить latency обработки запроса на 10–30% за счет сокращения количества проверок.
- **Назначение:** Используется, чтобы "запретить" проверку регулярных выражений для определенного пути. Например, если у вас есть `location ~* \.php$` для обработки PHP (Hypertext Preprocessor — препроцессор гипертекста), но вы хотите, чтобы запросы к `/uploads/` отдавались как [статика](../../Performance/Caching/client_caching.md), даже если они заканчиваются на `.php`.

> **Важно:** Если есть другой префиксный `location` БЕЗ `^~`, но с более длинным префиксом, он будет иметь приоритет над `^~`-`location`. Модификатор `^~` работает только для самого длинного совпавшего префикса.

#### Именованные location (`@name`)

Именованные `location` не участвуют в основном процессе сопоставления URI. Они предназначены для внутреннего использования внутри Nginx и могут быть вызваны только явно через другие директивы.

```nginx
location / {
    try_files $uri $uri/ @fallback;
}

location @fallback {
    proxy_pass http://backend;
}
```

- **Синтаксис:** `location @имя { ... }` — имя начинается с символа `@`.
- **Принцип работы:** Именованный `location` вызывается только через директивы `try_files`, `error_page`, `rewrite ... last`, `X-Accel-Redirect` и `auth_request`. Прямой HTTP-запрос к `@имя` от клиента вернет `404 Not Found`.
- **Переменные:** Переменная `$uri` в именованном `location` сохраняет значение URI **исходного запроса**, а не путь именованного блока. Это важно при использовании `try_files`.
- **Ограничения:** В именованных `location` нельзя использовать директивы, создающие ответ напрямую (например, `return` в старых версиях), хотя в актуальных версиях Nginx это разрешено.

Подробности см. в разделе **[Внутренняя маршрутизация](./internal_routing.md)**.

## Продвинутые аспекты и ограничения

### Ограничения использования переменных

В версиях Nginx до 1.31.5 в строке описания `location` **запрещено использовать переменные**. Например, конструкция `location /$variable { ... }` являлась невалидной и вызывала ошибку при проверке конфигурации. Пути в `location` должны были быть статическими строками или статическими регулярными выражениями.

Это ограничение существовало из-за архитектуры Nginx: `location` выбирался до того, как становились доступны переменные запроса (такие как `$uri`, `$host`). Директивы `location` обрабатывались на этапе конфигурации, а не на этапе выполнения запроса.

Начиная с Nginx 1.31.5, переменные можно использовать в `location` в качестве **предикатов**. Подробнее — в **[Предикатные локейшены и продвинутая маршрутизация API-трафика](./predicate_locations.md)**.

### Директива internal

Директива `internal` ограничивает доступ к `location` только внутренними запросами Nginx.

```nginx
location /internal_only/ {
    internal;
    # Доступ возможен только через rewrite, try_files, error_page 
    # или X-Accel-Redirect от бэкенда.
}
```

Внешний запрос к такому пути вернет ошибку `404 Not Found` (начиная с Nginx 1.25.x; в более старых версиях мог возвращаться `403 Forbidden`). Это поведение изменилось по соображениям безопасности: ранее злоумышленники могли использовать `403` для подтверждения существования защищенного пути.

### Ограничение методов через limit_except

Внутри `location` можно ограничить использование определенных HTTP-методов.

```nginx
location /api/ {
    limit_except GET POST {
        allow 192.168.1.0/24;
        deny  all;
    }
}
```

В данном примере методы GET и POST будут разрешены всем (согласно другим правилам), а для всех остальных методов доступ будет разрешен только из указанной подсети. `limit_except` полезен для защиты API от нежелательных методов (PUT, DELETE, PATCH) без внешнего брандмауэра.

### Особенности обработки завершающего слэша (Trailing Slash)

Если `location` задан префиксом, заканчивающимся слэшем (например, `location /dir/`), и запрос обрабатывается модулями `ngx_http_proxy_module`, `ngx_http_fastcgi_module` и др., то запрос к `/dir` (без слэша) может быть автоматически перенаправлен на `/dir/` с кодом `301 Moved Permanently`.

> **Важно:** Это поведение не применяется при использовании `try_files` — в этом случае `/dir` и `/dir/` обрабатываются как два отдельных пути, и редирект не выполняется.

### Взаимодействие с rewrite в контексте server

Директивы `rewrite` в контексте `server` выполняются **до** выбора `location`. Если rewrite изменяет URI, поиск `location` производится уже по новому значению. Это означает, что rewrite на уровне `server` может изменить приоритет сопоставления:

```nginx
server {
    # Этот rewrite выполняется ДО выбора location
    rewrite ^/old-api/(.*)$ /new-api/$1 permanent;

    location /new-api/ { ... }  # Будет выбран после rewrite
}
```

### Семантика `proxy_pass` с URI и без URI (подмена пути)

Классический вопрос на собеседованиях: «что произойдёт с URI при `proxy_pass`, если в нём указан путь (URI) и если его нет». Поведение различается принципиально:

**1. `proxy_pass http://backend;` (без URI)**

`location`-префикс **не** удаляется из запроса — апстриму уходит исходный URI целиком:

```nginx
location /api/ {
    proxy_pass http://app_backend;      # без URI
    # GET /api/users → backend получает GET /api/users
}
```

**2. `proxy_pass http://backend/;` (с URI, включая `/`)**

Часть пути, совпавшая с `location-префиксом`, **заменяется** на URI из `proxy_pass`:

```nginx
location /api/ {
    proxy_pass http://app_backend/;     # с URI "/"
    # GET /api/users → backend получает GET /users
}
```

Правило подмены: `location`-префикс (включая `/`) вырезается и заменяется URI из `proxy_pass`. Пример с заменой на `/v2/`:

```nginx
location /legacy/ {
    proxy_pass http://backend/v2/;
    # GET /legacy/users → backend получает GET /v2/users
}
```

Тот же принцип действует для `fastcgi_pass`, `uwsgi_pass`, `scgi_pass`, `grpc_pass`.

**Важно про локейшены с регулярными выражениями и `@`:**

- Если `location` задан **регулярным выражением** (`~`/`~*`) или именованным (`@name`) — `proxy_pass` с URI **не подставляет** часть по match rules: Nginx использует URI из `proxy_pass` как есть, а совпавшая часть **не** заменяется, и правило подмены **не** применяется. Для префиксных локаций подмена работает, для regex-локаций — нет.
- Если при regex-локации нужна подмена — используйте `rewrite ... break;` до `proxy_pass`, либо переменные в `proxy_pass` (тогда Nginx не применяет подмену и передаёт URI как есть).

Пример канонизации через `rewrite`:

```nginx
location ~ ^/api/(.*)$ {
    rewrite ^/api/(.*)$ /$1 break;
    proxy_pass http://backend;
    # GET /api/users → backend получает GET /users
}
```

**Проксирование с переменными:** если значение `proxy_pass` содержит переменные (например, для динамического выбора бэкенда), подмена URI **не выполняется**, и апстриму уходит исходный URI. При этом для имени хоста требуется директива `resolver`:

```nginx
location /api/ {
    resolver 127.0.0.11 valid=10s;
    proxy_pass http://$upstream_host:8080;
    # backend получает исходный /api/... (подмена не работает с переменными)
}
```

Подробнее про `resolver` и динамические апстримы — в [динамическом DNS-резолвинге](../../Proxy/Load_Balancing/dynamic_dns_resolution.md).

### Вложенные location

Nginx поддерживает вложенность блоков `location` в определенных контекстах. Вложенный `location` наследует большинство директив родительского блока. Однако вложенность создает сложные цепочки наследования, которые трудно отлаживать, и считается антипаттерном. В качестве альтернативы используйте `include` для выноса повторяющихся настроек.

## Практические сценарии

### Сценарий 1: Базовый веб-сайт с PHP

```nginx
# Точное совпадение для главной страницы — наивысший приоритет
location = / {
    root /var/www/html;
    index index.html;
}

# Приоритетный префикс для статики — пропускаем регулярные выражения
location ^~ /assets/ {
    root /var/www/html;
    expires 30d;
}

# Регулярное выражение для PHP-файлов
location ~ \.php$ {
    include fastcgi_params;
    fastcgi_pass unix:/var/run/php/php-fpm.sock; # Соединение с PHP-FPM (PHP FastCGI Process Manager — менеджер процессов FastCGI для PHP)
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
}

# Префиксный location по умолчанию
location / {
    root /var/www/html;
    try_files $uri $uri/ =404;
}
```

**Порядок обработки запросов:**

- `/` → `location = /` (точное совпадение, шаг 1 алгоритма)
- `/assets/style.css` → `location ^~ /assets/` (префикс с `^~`, шаг 3)
- `/index.php` → `location ~ \.php$` (регулярное выражение, шаг 4)
- `/about.html` → `location /` (префикс по умолчанию, шаг 5)

### Сценарий 2: API (Application Programming Interface — программный интерфейс приложения) с версионированием

```nginx
# Точный редирект для устаревшего endpoint
location = /api/v1/legacy {
    return 301 /api/v2/legacy;
}

# Приоритетный префикс для API v2 — без проверки регулярных выражений
location ^~ /api/v2/ {
    proxy_pass http://backend_api_v2;
    proxy_set_header Host $host;
}

# Префикс для API v1
location /api/v1/ {
    proxy_pass http://backend_api_v1;
    proxy_set_header Host $host;
}
```

**Почему `^~` для `/api/v2/`?** Если в конфигурации есть другие регулярные выражения (например, для обработки файлов), `^~` гарантирует, что все запросы к `/api/v2/` попадут на правильный backend без риска совпадения с regex.

### Сценарий 3: Запрет доступа к скрытым файлам

```nginx
# Регулярное выражение для скрытых файлов (начинаются с точки)
location ~ /\. {
    deny all;
    access_log off;
    log_not_found off;
}
```

Этот `location` заблокирует доступ к `.htaccess`, `.env`, `.git` и другим скрытым файлам. Поскольку это регулярное выражение, оно будет проверено до префиксных locations без `^~`.

### Сценарий 4: Эндпоинт для health check (мониторинг)

Для систем мониторинга (Prometheus с Blackbox Exporter, Zabbix, Nagios, Consul Health Checks) требуется отдельный эндпоинт, доступный только из подсети мониторинга.

```nginx
# Точное совпадение для health check — высокий приоритет, защита по IP
location = /nginx_status {
    stub_status on;         # Модуль ngx_http_stub_status_module
    access_log off;
    allow 10.0.0.0/8;       # Подсеть мониторинга
    allow 127.0.0.1;        # Локальный доступ
    deny  all;               # Все остальные — запрещено
}
```

**Верификация:**

```bash
# Запрос из подсети мониторинга
curl -s http://localhost/stub_status 2>/dev/null || curl -s http://localhost/nginx_status
# → Active connections: 1
#   server accepts handled requests
#   10 10 20
#   Reading: 0 Writing: 1 Waiting: 0

# Запрос из внешней сети
curl -s http://localhost/stub_status 2>/dev/null || curl -s http://localhost/nginx_status
# → 403 Forbidden
```

> **Важно:** Используйте `location = /nginx_status` (точное совпадение), чтобы избежать совпадения с более общими префиксными `location`. Модуль `ngx_http_stub_status_module` должен быть скомпилирован в Nginx (в стандартных сборках Ubuntu/Debian/CentOS включен по умолчанию).

> **Примечание:** Полное описание maintenance-режима, включая подходы через `include` и симлинк, `map` с внешним файлом, отдельный серверный блок и сценарии с health check, см. в **[Maintenance-режим в Nginx](../../Scenarios/nginx_maintenance_mode.md)**.

### Сценарий 6: gRPC-проксирование

Nginx 1.13.10+ поддерживает gRPC через HTTP/2. Используется отдельный `server` блок с SSL и `grpc_pass`:

```nginx
server {
    listen 443 ssl http2;
    server_name grpc.example.com;

    ssl_certificate     /etc/ssl/certs/example.com.crt;
    ssl_certificate_key /etc/ssl/private/example.com.key;

    # gRPC требует HTTP/2 — использование http2 в listen обязательно
    location / {
        grpc_pass grpc://backend_grpc:50051;
        grpc_set_header Host $host;
    }

    # Точка входа для проверки работоспособности gRPC-сервиса
    location = /healthz {
        access_log off;
        return 200 "OK";
    }
}
```

> **Важно:** HTTP/2 с включенным TLS (`http2`) обязателен для работы `grpc_pass`. Чистый HTTP/2 без TLS работает только для локальных бэкендов и требует `grpc_pass h2c://...`.

### Сценарий 7: Canary-развертывание (Canary Release) по заголовкам

Для постепенного развертывания новой версии приложения часть трафика (например, 10%) направляется на новую версию. Используется связка `map` + `location`:

```nginx
# В контексте http: распределение по заголовку X-Canary
map $http_x_canary $backend_target {
    default         "http://stable_backend:8080";
    "true"          "http://canary_backend:8080";
    "1"             "http://canary_backend:8080";
}

server {
    listen 80;
    server_name app.example.com;

    location / {
        proxy_pass $backend_target;
        proxy_set_header Host $host;
    }
}
```

Для проверки: `curl -H "X-Canary: true" http://app.example.com/api/health` → маршрут на canary_backend.

## Операции и команды

### Валидация конфигурации

Перед применением любых изменений проверяйте синтаксис:

```bash
# Проверка синтаксиса (dry-run)
nginx -t
# → nginx: configuration file /etc/nginx/nginx.conf test is successful

# Graceful reload — перезагрузка без разрывов соединений
nginx -s reload
# → signal processed
```

`nginx -t` проверяет только синтаксис. Для проверки конфликтов `location` и валидации путей используйте `nginx -T`.

### Диагностика выбранного location

```bash
# Показать полную конфигурацию Nginx с подстановкой include
nginx -T
# → полный объединенный конфиг — полезен для проверки фактического порядка location

# Включение debug-лога для отслеживания выбора location
# В секции events или http:
error_log /var/log/nginx/error.log debug;

# После этого в логе появятся записи вида:
# → *12345 using location "/api/v1/" for "/api/v1/users"
# → *12345 http script var: "$uri" = "/api/v1/users"
```

> **Примечание:** `debug` уровень логирования сильно увеличивает объем логов и снижает производительность. Используйте его только для диагностики и отключайте после решения проблемы.

### Проверка через curl

```bash
# Проверить, какой location обработал запрос (через кастомный заголовок)
curl -sI http://nginx-host/assets/style.css
# → X-Debug-Match: /assets/  (если добавлен add_header в location)

# Проверить заголовки ответа
curl -sI http://nginx-host/healthz
# → HTTP/1.1 200 OK
# → X-Cache-Status: MISS
```

## Устранение неполадок

### Проблема 1: Запрос попадает в неожиданный location

**Диагностика:**

```bash
# 1. Проверить валидность конфигурации
nginx -t

# 2. Просмотреть полную конфигурацию и найти все location
nginx -T | grep -n "location"

# 3. Проверить, есть ли server_name в нужном server блоке
nginx -T | grep -A 20 "server_name example.com"
```

**Частые причины:**
- `location /api/` без `^~` перехвачен regex `location ~ \.php$`, если запрос содержит `.php`.
- `location = /path` объявлен в другом `server` блоке с более подходящим `server_name`.
- `merge_slashes off` и запрос содержит лишние слэши, которые не совпадают с префиксом.

**Решение:** Используйте `location ^~ /static/` для приоритета префикса или переупорядочите regex-локации.

### Проблема 2: 403 Forbidden при запросе статики

**Диагностика:**

```bash
# Проверить права на файл и каталог
ls -la /var/www/html/path/to/file

# Проверить SELinux (RHEL/CentOS/Fedora)
getsebool -a | grep httpd
# → httpd_read_user_content --> off
```

**Частые причины:**
- Пользователь, от имени которого работает Nginx (`www-data`, `nginx`), не имеет прав на чтение файла.
- SELinux блокирует доступ (исправить: `chcon -t httpd_sys_content_t /var/www/html/...` или `setsebool -P httpd_read_user_content on`).

### Проблема 3: Регулярное выражение перехватывает неожиданные запросы

**Пример ошибки:**

```nginx
# Общий regex объявлен первым
location ~* \.(php|jpg|png)$ { ... }

# Специфичный regex объявлен вторым, но никогда не выполнится
location ~* \.php$ { ... }  # ← никогда не сработает
```

**Решение:** Объявите более специфичные паттерны первыми:

```nginx
location ~* \.php$ { ... }       # Сначала PHP
location ~* \.(jpg|png)$ { ... } # Потом изображения
```

### Проблема 4: 404 для существующих файлов из-за alias

**Причина:** В `location /static/ { alias /data/files/; }` запрос `/static/file.txt` ищет файл по пути `/data/files/file.txt`. Если в `alias` нет завершающего слэша (`alias /data/files;`), путь искажается.

**Решение:** Убедитесь, что `alias` заканчивается слэшем, если `location` заканчивается слэшем.

### Проблема 5: Циклические внутренние перенаправления

**Симптом:** В логе: `rewrite or internal redirection cycle while internal redirection to "/index.html"`

**Причина:** `try_files $uri $uri/ /index.html` вызывает `/index.html`, который в свою очередь снова вызывает `try_files`.

**Решение:** Добавьте `index` директиву в блок `location /` или используйте `try_files $uri $uri/ @fallback` с именованным `location`.
