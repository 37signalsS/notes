# Директива location: основы и приоритеты

> **Надежность: 10** (Подтверждено актуальной документацией Nginx на август 2026)

## Определения

**Директива `location`** является одним из ключевых элементов [конфигурации](../nginx_setup.md) [Nginx](../nginx_overview.md). Она позволяет гибко управлять [обработкой запросов](../nginx_rewrite_rules_and_try_files.md) в рамках протокола HTTP (Hypertext Transfer Protocol — протокол передачи гипертекста) в зависимости от [URI (Uniform Resource Identifier — унифицированный идентификатор ресурса)](../../../../Networking/Protocols/HTTP/http_basics.md). С её помощью можно настраивать отдачу статического контента: HTML (HyperText Markup Language — язык разметки гипертекста), CSS (Cascading Style Sheets — каскадные таблицы стилей), изображений и других ресурсов.

## Базовые концепции

### Алгоритм выбора location и нормализация URI

Перед началом сопоставления Nginx выполняет **нормализацию URI**. Этот процесс включает:
1.  Декодирование текста, закодированного в формате `%XX`.
2.  Разрешение ссылок на относительные каталоги `.` и `..`.
3.  Замену двух или более идущих подряд слэшей на один (так называемое "схлопывание" слэшей). Это поведение контролируется директивой `merge_slashes` (по умолчанию `on`).

Поиск выполняется по нормализованному URI. Nginx использует следующий четкий алгоритм для выбора наиболее подходящего блока `location`:

1. **Поиск точного совпадения:** Nginx ищет `location` с модификатором `=`. Если URI запроса в точности совпадает, этот `location` используется немедленно, и поиск прекращается.
2. **Поиск префиксных `location`:** Nginx проверяет все префиксные `location` (с модификатором `^~` и без него) и запоминает **самый длинный** из совпавших.
3. **Проверка на приоритетный префикс:** Если самый длинный префикс, найденный на шаге 2, имел модификатор `^~`, Nginx немедленно использует его, **пропуская проверку регулярных выражений**.
4. **Поиск по регулярным выражениям:** Если на шаге 3 поиск не был остановлен, Nginx проверяет все `location` с регулярными выражениями (`~` и `~*`) **в порядке их появления в файле конфигурации**. Первый же совпавший `location` используется, и поиск прекращается.
5. **Использование сохраненного префикса:** Если ни одно регулярное выражение не совпало, Nginx использует **самый длинный префиксный `location`**, который он запомнил на шаге 2.

**Приоритет в целом:** `=` (точное совпадение) > `^~` (самое длинное префиксное совпадение, прекращает поиск) > `~` / `~*` (первое совпадение по порядку в файле) > без модификатора (самое длинное префиксное совпадение, если регулярные выражения не совпали).

### Модификаторы location и их поведение

Nginx различает `location` по наличию или отсутствию специальных модификаторов.

#### Префиксный location (без модификатора)

Это самый простой и распространенный тип.

```nginx
location /path/ { 
    # Обработка запросов, начинающихся с /path/
}
```

- **Принцип работы:** Совпадает, если нормализованный URI запроса *начинается* с указанного префикса.
- **Чувствительность к регистру:** На Linux/Unix-системах префиксное совпадение **чувствительно к регистру**, так как URI в этих системах обычно рассматривается с учетом регистра. На Windows и macOS (с файловыми системами HFS+/APFS по умолчанию) префиксное совпадение нечувствительно к регистру.
- **Правило выбора:** Среди всех совпавших префиксных `location`, Nginx выбирает тот, у которого **самый длинный префикс**. Порядок их объявления в конфигурационном файле **не имеет значения**.

**Пример:**

```nginx
location / { ... }       # Конфигурация A
location /index/ { ... } # Конфигурация B
```

- Запрос `/index.html` → `location /index/` (Конфигурация B), так как префикс `/index/` длиннее.
- Запрос `/about.html` → `location /` (Конфигурация A).
- **`location /` (блок по умолчанию):** Если ничего другого не подошло, используется этот блок.

#### Точное совпадение (`=`)

Этот модификатор задает `location`, который сработает только при полном и точном совпадении URI.

```nginx
location = /exact.html { ... }
```

- **Принцип работы:** URI запроса должен быть в точности равен `/exact.html`.
- **Правило выбора:** Имеет **наивысший приоритет**. Если найдено точное совпадение, поиск немедленно прекращается, и используется этот `location`. Это повышает производительность для часто запрашиваемых путей (например, `/` или `/favicon.ico`).

#### [Регулярные выражения](../../../../Linux/Shell/regular_expressions.md) (`~` и `~*`)

Эти модификаторы позволяют задавать `location` с помощью регулярных выражений.

- `~`: регулярное выражение с учетом регистра.
- `~*`: регулярное выражение без учета регистра (case-insensitive).

```nginx
# Перехватит запросы к изображениям, без учета регистра расширения
location ~* \.(gif|jpg|jpeg|png)$ { ... }

# Перехватит запросы к XML (Extensible Markup Language — расширяемый язык разметки) файлам, с учетом регистра
location ~ \.xml$ { ... }
```

- **Принцип работы:** URI запроса проверяется на соответствие регулярному выражению.
- **Правило выбора:** Регулярные выражения проверяются **в том порядке, в котором они указаны в конфигурационном файле**. Первый же совпавший `location` используется для обработки запроса, и дальнейший поиск прекращается.

> **Важно:** Порядок следования `location` с регулярными выражениями критически важен. Неправильный порядок может привести к тому, что более специфичные правила никогда не будут выполнены.

#### Приоритетный префиксный location (`^~`)

Этот модификатор работает как обычный префиксный `location`, но с одним важным отличием.

```nginx
location ^~ /uploads/ { ... }
```

- **Принцип работы:** Совпадение по префиксу.
- **Правило выбора:** Если этот `location` оказывается самым длинным совпавшим префиксом, Nginx **не будет проверять регулярные выражения**. Он немедленно использует этот `location`.
- **Назначение:** Используется, чтобы "запретить" проверку регулярных выражений для определенного пути. Например, если у вас есть `location ~* \.php$` для обработки PHP (Hypertext Preprocessor — препроцессор гипертекста), но вы хотите, чтобы запросы к `/uploads/` отдавались как [статика](../../Performance/Caching/client_caching.md), даже если они заканчиваются на `.php`.

#### Именованные location (`@name`)

Именованные `location` не участвуют в основном процессе сопоставления URI. Они предназначены для внутреннего использования внутри Nginx (например, в директивах `try_files` или `error_page`).

```nginx
location / {
    try_files $uri $uri/ @fallback;
}

location @fallback {
    proxy_pass http://backend;
}
```

Подробности см. в разделе **[Внутренняя маршрутизация](./internal_routing.md)**.

## Продвинутые аспекты и ограничения

### Ограничения использования переменных
В строке описания `location` **запрещено использовать переменные**. Например, конструкция `location /$variable { ... }` является невалидной и вызовет ошибку при проверке конфигурации. Пути в `location` должны быть статическими строками или статическими регулярными выражениями.

### Директива internal
Директива `internal` ограничивает доступ к `location` только внутренними запросами.
```nginx
location /internal_only/ {
    internal;
    # Доступ возможен только через rewrite, try_files, error_page 
    # или X-Accel-Redirect от бэкенда.
}
```
Внешний запрос к такому пути вернет ошибку `404 Not Found`.

### Ограничение методов через limit_except
Внутри `location` можно ограничить использование определенных HTTP-методов.
```nginx
location /api/ {
    limit_except GET POST {
        allow 192.168.1.0/24;
        deny  all;
    }
}
```
В данном примере методы GET и POST будут разрешены всем (согласно другим правилам), а для всех остальных методов доступ будет разрешен только из указанной подсети.

### Особенности обработки завершающего слэша (Trailing Slash)
Если `location` задан префиксом, заканчивающимся слэшем (например, `location /dir/`), и запрос обрабатывается модулями `ngx_http_proxy_module`, `ngx_http_fastcgi_module` и др., то запрос к `/dir` (без слэша) может быть автоматически перенаправлен на `/dir/` с кодом 301.

## Практические сценарии

### Сценарий 1: Базовый веб-сайт с PHP

```nginx
# Точное совпадение для главной страницы — наивысший приоритет
location = / {
    root /var/www/html;
    index index.html;
}

# Приоритетный префикс для статики — пропускаем регулярные выражения
location ^~ /assets/ {
    root /var/www/html;
    expires 30d;
}

# Регулярное выражение для PHP-файлов
location ~ \.php$ {
    include fastcgi_params;
    fastcgi_pass unix:/var/run/php/php-fpm.sock; # Соединение с PHP-FPM (PHP FastCGI Process Manager — менеджер процессов FastCGI для PHP)
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
}

# Префиксный location по умолчанию
location / {
    root /var/www/html;
    try_files $uri $uri/ =404;
}
```

**Порядок обработки запросов:**

- `/` → `location = /` (точное совпадение, шаг 1 алгоритма)
- `/assets/style.css` → `location ^~ /assets/` (префикс с `^~`, шаг 3)
- `/index.php` → `location ~ \.php$` (регулярное выражение, шаг 4)
- `/about.html` → `location /` (префикс по умолчанию, шаг 5)

### Сценарий 2: API (Application Programming Interface — программный интерфейс приложения) с версионированием

```nginx
# Точный редирект для устаревшего endpoint
location = /api/v1/legacy {
    return 301 /api/v2/legacy;
}

# Приоритетный префикс для API v2 — без проверки регулярных выражений
location ^~ /api/v2/ {
    proxy_pass http://backend_api_v2;
    proxy_set_header Host $host;
}

# Префикс для API v1
location /api/v1/ {
    proxy_pass http://backend_api_v1;
    proxy_set_header Host $host;
}
```

**Почему `^~` для `/api/v2/`?** Если в конфигурации есть другие регулярные выражения (например, для обработки файлов), `^~` гарантирует, что все запросы к `/api/v2/` попадут на правильный backend без риска совпадения с regex.

### Сценарий 3: Запрет доступа к скрытым файлам

```nginx
# Регулярное выражение для скрытых файлов (начинаются с точки)
location ~ /\. {
    deny all;
    access_log off;
    log_not_found off;
}
```

Этот `location` заблокирует доступ к `.htaccess`, `.env`, `.git` и другим скрытым файлам. Поскольку это регулярное выражение, оно будет проверено до префиксных locations без `^~`.

## Дополнительная информация

### Частые ошибки

- **Неправильный порядок regex:** `location ~ \.php$` перед `location ~* \.php$` — первый сработает, второй никогда не выполнится.
- **Ожидание точного совпадения без `=`:** `location /path` без модификатора — это префиксное совпадение, а не точное. Для точного используйте `location = /path`.
- **Вложенные location:** Хотя Nginx поддерживает вложенность, это усложняет логику и затрудняет отладку. Рекомендуется избегать без крайней необходимости.
- **Использование регулярных выражений там, где достаточно префикса:** Префиксные `location` работают быстрее и их проще тестировать.

### Тестирование конфигурации

После изменения конфигурации всегда проверяйте синтаксис:

```bash
nginx -t 
# → nginx: configuration file /etc/nginx/nginx.conf test is successful
nginx -s reload 
# → graceful reload executed
```
