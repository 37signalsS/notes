# Nginx location: Best Practices и отладка

## Определения

**Best practices** — набор проверенных рекомендаций по конфигурации директив [`location`](./basics.md), направленных на повышение производительности, безопасности и удобства сопровождения конфигурации Nginx.

**Отладка location** — процесс определения, какой именно блок `location` обрабатывает входящий запрос, и верификация соответствия фактического поведения ожидаемому.

## Базовые концепции

### Префиксные location предпочтительнее регулярных выражений

Префиксные `location` (без модификатора и с `^~`) работают быстрее, чем regex (`~` / `~*`), поскольку не требуют вычисления регулярного выражения на каждый запрос.

> Подробный алгоритм выбора location и описание модификаторов — в [Основы и приоритеты location](./basics.md).

**Рекомендации:**

- Используйте регулярные выражения только когда без них не обойтись (обработка файлов по расширению, специфичные паттерны)
- Для статических ресурсов применяйте `^~` — это прекращает поиск после первого совпадения и исключает проверку regex
- `~*` (case-insensitive) предпочтительнее `~` (case-sensitive) для расширений файлов — пользователь может запросить `Image.PNG` вместо `image.png`

### Вложенные location — избегать

Nginx поддерживает вложенность блоков `location`, но это:

- Усложняет логику обработки запросов
- Затрудняет отладку и понимание конфигурации
- Может приводить к неожиданным результатам при наследовании директив

**Рекомендация:** используйте плоскую структуру `location` без вложенности.

> Подробнее о вложенных location — в разделе «Частые ошибки» файла [Основы и приоритеты location](./basics.md#частые-ошибки).

### Централизация общих директив через `include`

Для повторяющихся конфигурационных блоков (заголовки кэширования, CORS, proxy-параметры) используйте `include`:

```nginx
# /etc/nginx/conf.d/static_headers.conf
expires 30d;
add_header Cache-Control "public, immutable";
```

```nginx
location ^~ /assets/ {
    root /var/www/html;
    include conf.d/static_headers.conf;
}
```

**Преимущества:**

- Единая точка изменения — обновить заголовки в одном файле вместо поиска по всем `location`
- Уменьшение дублирования и риска расхождения конфигураций
- Улучшение читаемости основного конфига

### Мониторинг location через status_zone

Директива `status_zone` позволяет собирать статистику по запросам для конкретного `location`:

```nginx
location /api/v2/ {
    status_zone api_v2;
    proxy_pass http://backend_api_v2;
}
```

Метрики доступны через API Nginx (модуль `ngx_http_api_module`) и используются для мониторинга трафика и выявления аномалий.

> `status_zone` также применяется в блоках `server` и `upstream`. Подробней — в [Настройка мониторинга L4-проксирования](../../Proxy/nginx_l4_proxying.md#мониторинг-и-статистика).

## Практические сценарии

### Сценарий 1: Отладка location через return

Для проверки того, какой `location` обрабатывает запрос, временно добавьте директиву `return`:

```nginx
location ~ \.php$ {
    # Временно для отладки:
    return 200 "Location: Regexp PHP\n";

    # Основная конфигурация (раскомментировать после проверки):
    # root           /var/www/html;
    # fastcgi_pass   unix:/var/run/php/php7.4-fpm.sock;
    # fastcgi_index  index.php;
    # include        fastcgi_params;
    # fastcgi_param  SCRIPT_FILENAME $document_root$fastcgi_script_name;
}
```

Проверка через `curl`:

```bash
curl http://localhost/test.php
# → Location: Regexp PHP
```

После подтверждения правильного срабатывания — удалите или закомментируйте строку `return`.

**Важно:** не забывайте убрать `return` перед перезагрузкой — иначе клиенты будут получать текстовый ответ вместо ожидаемого контента.

### Сценарий 2: Исключение директории из обработки regex

Задача: директория `/uploads/` должна отдаваться как статика, даже если файлы имеют расширение `.php`.

```nginx
# Regex для обработки PHP — проверяется после ^~
location ~ \.php$ {
    fastcgi_pass unix:/var/run/php/php-fpm.sock;
    include fastcgi_params;
}

# Приоритетный префикс — пропускает проверку regex
location ^~ /uploads/ {
    root /var/www/html;
    expires 7d;
}
```

Запрос `/uploads/image.php` будет обработан `location ^~ /uploads/`, а не regex `location ~ \.php$`.

> Аналогичный пример с `/assets/` и полный алгоритм — в [Основы и приоритеты location](./basics.md#практические-сценарии).

### Сценарий 3: Безопасная перезагрузка конфигурации

После любого изменения конфигурации:

```bash
nginx -t   # → nginx: configuration file /etc/nginx/nginx.conf test is successful
nginx -s reload  # graceful reload без прерывания соединений
```

**Порядок действий:**

1. Всегда запускайте `nginx -t` перед `reload` — ошибка в синтаксисе при `reload` может привести к падению worker-процессов
2. Если `nginx -t` прошёл — выполняйте `nginx -s reload`
3. Проверяйте error log после reload на наличие ошибок: `tail -f /var/log/nginx/error.log`

## Дополнительные сведения

### Чек-лист лучших практик

| Практика | Когда применять |
| :--- | :--- |
| Префиксный `location` без модификатора | Базовая маршрутизация по URI |
| `^~` для статических директорий | Исключение из проверки regex |
| `=` для точных совпадений | Главная страница, health-check, favicon |
| `~` / `~*` для расширений файлов | Обработка по типу файла (css, js, php) |
| `include` для общих директив | Повторяющиеся блоки конфигов |
| `status_zone` для мониторинга | Критичные API и endpoints |
| `return` для отладки | Временная проверка маршрутизации |
