# Директива location: Маршрутизация запросов по URI в Nginx

## 1. Определения и базовые концепции

**Директива `location`** является одним из ключевых элементов [[./nginx_setup.md|конфигурации]] [[./nginx_overview.md|Nginx]]. Она позволяет гибко управлять [[./nginx_rewrite_rules_and_try_files.md|обработкой запросов]] в зависимости от [[../../../Networking/Protocols/http.md|URI (Uniform Resource Identifier)]].

## 2. Приоритеты и алгоритм выбора location

Nginx использует следующий четкий алгоритм для выбора наиболее подходящего блока `location` для обработки запроса:

1.  **Поиск точного совпадения:** Nginx ищет `location` с модификатором `=`. Если URI запроса в точности совпадает, этот `location` используется немедленно, и поиск прекращается.

2.  **Поиск префиксных `location`:** Nginx проверяет все префиксные `location` (с модификатором `^~` и без него) и запоминает **самый длинный** из совпавших.

3.  **Проверка на приоритетный префикс:** Если самый длинный префикс, найденный на шаге 2, имел модификатор `^~`, Nginx немедленно использует его, **пропуская проверку регулярных выражений**.

4.  **Поиск по регулярным выражениям:** Если на шаге 3 поиск не был остановлен, Nginx проверяет все `location` с регулярными выражениями (`~` и `~*`) **в порядке их появления в файле конфигурации**. Первый же совпавший `location` используется, и поиск прекращается.

5.  **Использование сохраненного префикса:** Если ни одно регулярное выражение не совпало, Nginx использует **самый длинный префиксный `location`**, который он запомнил на шаге 2.

**Приоритет в целом:** `=` (точное совпадение) > `^~` (самое длинное префиксное совпадение, прекращает поиск) > `~` / `~*` (первое совпадение по порядку в файле) > без модификатора (самое длинное префиксное совпадение, если регулярные выражения не совпали).

## 3. Модификаторы location и их поведение (Практические сценарии)

Nginx различает `location` по наличию или отсутствию специальных модификаторов.

### 3.1. Префиксный location (без модификатора)

Это самый простой и распространенный тип.
```nginx
location /path/ { ... }
```
-   **Принцип работы:** Совпадает, если URI запроса *начинается* с указанного префикса.
-   **Правило выбора:** Среди всех совпавших префиксных `location`, Nginx выбирает тот, у которого **самый длинный префикс**. Порядок их объявления в конфигурационном файле **не имеет значения**.

**Пример:**
```nginx
location / { ... }       # Конфигурация A
location /index/ { ... } # Конфигурация B
```
-   Запрос `/index.html` будет обработан `location /index/` (конфигурация B), так как префикс `/index/` длиннее, чем `/`.
-   Запрос `/about.html` будет обработан `location /` (конфигурация A).
-   **`location /` (блок по умолчанию):** Если ничего другого не подошло, используется этот блок.

### 3.2. Точное совпадение (`=`)

Этот модификатор задает `location`, который сработает только при полном и точном совпадении URI.
```nginx
location = /exact.html { ... }
```
-   **Принцип работы:** URI запроса должен быть в точности равен `/exact.html`.
-   **Правило выбора:** Имеет **наивысший приоритет**. Если найдено точное совпадение, поиск немедленно прекращается, и используется этот `location`.

**Практический пример: редирект для старого адреса**

Точное совпадение идеально подходит для перенаправления конкретных, устаревших URL.

```nginx
location = /old-contacts {
    return 301 /contacts;
}

```
*   Этот блок сработает **только** для запроса `http://site.local/old-contacts`.
*   Директива `return 301` немедленно останавливает обработку и отправляет браузеру и поисковым системам сигнал, что страница навсегда переехала на новый адрес `/contacts`. Подробнее о редиректах в файле о **[[./nginx_rewrite_rules_and_try_files.md|правилах rewrite и redirect]]**.

### 3.3. [[../../../Linux/Shell/regular_expressions.md|Регулярные выражения]] (`~` и `~*`)

Эти модификаторы позволяют задавать `location` с помощью регулярных выражений.

-   `~`: регулярное выражение с учетом регистра.
-   `~*`: регулярное выражение без учета регистра (case-insensitive).

```nginx
# Перехватит запросы к изображениям, без учета регистра расширения
location ~* \.(gif|jpg|jpeg|png)$ { ... }

# Перехватит запросы к XML-файлам, с учетом регистра
location ~ \.xml$ { ... }
```
-   **Принцип работы:** URI запроса проверяется на соответствие регулярному выражению.
-   **Правило выбора:** Регулярные выражения проверяются **в том порядке, в котором они указаны в конфигурационном файле**. Первый же совпавший `location` используется для обработки запроса, и дальнейший поиск прекращается.

> **Важно:** Порядок следования `location` с регулярными выражениями критически важен. Неправильный порядок может привести к тому, что более специфичные правила никогда не будут выполнены.

### 3.4. Приоритетный префиксный location (`^~`)

Этот модификатор работает как обычный префиксный `location`, но с одним важным отличием.
```nginx
location ^~ /uploads/ { ... }
```
-   **Принцип работы:** Совпадение по префиксу.
-   **Правило выбора:** Если этот `location` оказывается самым длинным совпавшим префиксом, Nginx **не будет проверять регулярные выражения**. Он немедленно использует этот `location`.
-   **Назначение:** Используется, чтобы "запретить" проверку регулярных выражений для определенного пути. Например, если у вас есть `location ~* \.php$` для обработки PHP, но вы хотите, чтобы запросы к `/uploads/` отдавались как [[../Performance/nginx_static_file_caching.md|статика]], даже если они заканчиваются на `.php`.

## 4. Дополнительные практические сценарии

### 4.1. Работа с файловой системой: `root` и `alias`

Директивы `root` и `alias` определяют, как Nginx сопоставляет URI запроса с файлами на диске.

#### 4.1.1. Директива `root`

`root` определяет корневой каталог для запросов. Nginx добавляет полный URI запроса к значению `root` для формирования пути к файлу.

*   **Пример:**
    ```nginx
    server {
        root /var/www/html;
        location /images/ {
            # Запрос /images/pic.jpg будет искать файл по пути /var/www/html/images/pic.jpg
        }
        location = /test.html {
            root /var/www/special_tests;
            # Запрос /test.html будет искать файл по пути /var/www/special_tests/test.html
            # Это позволяет отдавать специфические файлы из других директорий.
        }
    }
    ```
*   `root` может быть определен на уровне `http`, `server` или `location`. Если `root` не указан в `location`, он наследуется от родительского блока.

#### 4.1.2. Директива `alias`

`alias` используется для замены части URI запроса на указанный путь в файловой системе. `alias` может использоваться только внутри `location`.

*   **Пример:**
    ```nginx
    location /static/ {
        alias /opt/data/static_files/;
        # Запрос /static/css/style.css будет искать файл по пути /opt/data/static_files/css/style.css
        # Часть "/static/" из URI заменяется на "/opt/data/static_files/"
    }
    location /foot/ {
        alias /var/www/special_content/;
        # Запрос /foot/test.html будет искать файл по пути /var/www/special_content/test.html
        # Здесь "/foot/" из URI заменяется на "/var/www/special_content/".
        # Важно: если location заканчивается слэшем, alias также должен заканчиваться слэшем.
    }
    location /images/ {
        alias /var/www/site1.local/images/;
        # Этот блок "ловит" все запросы, URI которых начинается с /images/.
        # Директива alias говорит Nginx: "возьми ту часть запроса, которая совпала с location (/images/),
        # отбрось её и вместо неё используй указанный путь (/var/www/site1.local/images/)".
    }
    ```
*   **Важное отличие от `root`:** `alias` заменяет префикс URI, соответствующий `location`, тогда как `root` добавляет весь URI к корневому пути.
*   При использовании `alias` важно, чтобы путь `alias` заканчивался слэшем, если `location` также заканчивается слэшем, чтобы избежать некорректного формирования пути.

### 4.2. Обработка статических файлов и `try_files`

Директива `try_files` позволяет Nginx проверять существование файлов или директорий в указанном порядке и выполнять внутреннее перенаправление, если ни один из них не найден. Более подробно о `try_files`, а также о правилах rewrite и redirect можно узнать в [Nginx: Правила Rewrite, Redirect и Директива try_files](../Nginx/nginx_rewrite_rules_and_try_files.md).

*   **Синтаксис:** `try_files file ... uri;` или `try_files file ... =code;`
*   **Пример:**
    ```nginx
    location / {
        root /var/www/html;
        try_files $uri $uri/ /index.html =404;
        # 1. Пробует найти файл, соответствующий URI ($uri).
        # 2. Если не найден, пробует найти директорию ($uri/).
        # 3. Если и директория не найдена, делает внутреннее перенаправление на /index.html.
        # 4. Если /index.html также не найден, возвращает ошибку 404.
    }
    ```
*   `try_files` часто используется для обработки "красивых" URL (pretty URLs) в CMS, где все запросы, не соответствующие существующим файлам или директориям, перенаправляются на основной скрипт (например, `index.php`).

### 4.3. Именованные `location` и `internal`

#### 4.3.1. Именованные `location` (`@name`)

Именованные `location` не могут быть вызваны напрямую клиентом. Они используются для внутренних перенаправлений внутри Nginx, например, с помощью `try_files` или `error_page`.

*   **Пример:**
    ```nginx
    location / {
        try_files $uri @backend;
    }

    location @backend {
        proxy_pass http://my_backend_servers;
    }
    ```
    В этом примере, если Nginx не находит статический файл, он внутренне перенаправляет запрос на именованный `location @backend`, который затем проксирует запрос к бэкенд-серверам. Эта техника является основой для [[../Angie/angie_reverse_proxy.md|настройки Nginx в роли обратного HTTP-прокси]] и [[../Angie/angie_http_load_balancing.md|балансировки нагрузки HTTP(S)]]. (Ссылки адаптированы под Nginx)

#### 4.3.2. Директива `internal`

Директива `internal` внутри `location` делает этот `location` доступным только для внутренних запросов Nginx. Клиентские запросы к такому `location` будут отклонены (обычно с ошибкой 404 Not Found).

*   **Пример:**
    ```nginx
    location /private_data/ {
        internal;
        root /var/www/internal_files;
        # Этот location доступен только для внутренних перенаправлений Nginx.
        # Прямой запрос клиента к /private_data/ будет отклонен.
    }
    location /error_pages/ {
        internal;
        root /var/www/errors;
        # Если клиент попытается напрямую обратиться к /error_pages/404.html,
        # он получит ошибку 404 Not Found, несмотря на существование файла.
        # Этот location предназначен для использования с error_page директивой.
    }
    ```
*   Это полезно для защиты конфиденциальных ресурсов или для организации внутренних API, которые не должны быть доступны извне.

### 4.4. Обработка PHP-скриптов

Для обработки PHP-скриптов Nginx обычно использует FastCGI-протокол, взаимодействуя с PHP-FPM.

*   **Пример конфигурации для PHP:**
    ```nginx
    location ~ \.php$ {
        root           /var/www/html;
        fastcgi_pass   unix:/var/run/php/php7.4-fpm.sock; # Путь к сокету PHP-FPM
        fastcgi_index  index.php;
        include        fastcgi_params; # Включает стандартные параметры FastCGI
        fastcgi_param  SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }
    ```
*   Здесь используется регулярное выражение `~ \.php$` для сопоставления всех запросов, заканчивающихся на `.php`.
*   `fastcgi_pass` указывает адрес FastCGI-сервера (часто Unix-сокет).
*   `fastcgi_param SCRIPT_FILENAME` передает PHP-FPM полный путь к исполняемому скрипту.

### 4.5. Кастомные страницы ошибок (error_page)

Директива `error_page` позволяет определить, что увидит пользователь при возникновении ошибки (например, 404 Not Found). Хоть она и не является частью `location`, ее работа напрямую связана с результатом обработки запроса в `location`.

*   **Синтаксис:** `error_page code ... [=[response]] uri;`
*   **Пример:**
    ```nginx
    server {
        root /var/www/html;

        # Если try_files вернет ошибку 404, будет выполнен
        # внутренний редирект на /404.html
        error_page 404 /404.html;

        location / {
            try_files $uri $uri/ =404;
        }

        # Важно: для /404.html тоже нужен location, чтобы Nginx смог его найти.
        # Этот location должен быть доступен для внутренних запросов.
        location = /404.html {
            internal;
        }
    }
    ```
*   **Объяснение:**
    *   `error_page 404 /404.html;`: Настраивает обработку ошибки 404. Если Nginx не может найти ресурс (например, `try_files` завершается с `=404`), он не показывает стандартную страницу "404 Not Found". Вместо этого он выполняет **внутреннее перенаправление** и отдает пользователю содержимое файла `/404.html`.
    *   `location = /404.html { internal; }`: Этот блок предназначен для обработки запросов к странице 404. Специальная директива `internal;` делает этот `location` доступным только для внутренних запросов Nginx (например, от `error_page`). Это означает, что пользователь не сможет напрямую перейти по адресу `http://site1.local/404.html` и увидеть страницу ошибки. Это хорошая практика для предотвращения индексации страниц ошибок поисковыми системами.

## 5. Оптимизация, отладка и лучшие практики

**Общие рекомендации:**

*   **Предпочитайте префиксные `location`:** Они проще для понимания и работают быстрее, чем регулярные выражения. Используйте регулярные выражения только тогда, когда без них не обойтись.
*   **Остерегайтесь вложенных `location`:** Они усложняют логику и могут сделать конфигурацию трудной для отладки. Старайтесь избегать их без крайней необходимости.
*   **Помните о производительности:** Регулярные выражения требуют значительно больше ресурсов CPU для обработки, чем простые префиксные сравнения. Большое количество сложных регулярных выражений может негативно сказаться на [[../Performance/nginx_performance_tuning.md|производительности сервера]] под высокой нагрузкой.
*   **Используйте `^~` для исключений:** Если вам нужно, чтобы определенный каталог всегда отдавался как статика, и на него не действовали общие правила для динамических скриптов (например, `location ~ \.php$`), используйте `location ^~ /path/to/static/`.
*   **Используйте `^~` для статических файлов:** Для статических ресурсов, которые не требуют обработки регулярными выражениями, используйте `^~` для повышения производительности, так как это прекращает поиск `location` после первого совпадения.
*   **Централизованное управление заголовками:** Для общих заголовков (например, для кэширования статики) используйте `include` для вынесения их в отдельный файл, чтобы избежать дублирования и упростить управление.
*   **Мониторинг `location`:** Используйте встроенные средства мониторинга Nginx (например, `ng console.light` или кастомные метрики) для отслеживания того, какие `location` обрабатывают запросы, чтобы убедиться в корректности конфигурации и выявить неожиданное поведение. Для более детального мониторинга каждого `location` можно использовать "статус зоны" (status zones), которые позволяют собирать статистику по запросам, обрабатываемым конкретным `location`.

**Отладка `location` с помощью `return`:**

Для быстрой проверки того, какой `location` обрабатывает запрос, можно временно использовать директиву `return` внутри `location`. Это позволяет Nginx немедленно вернуть указанный HTTP-код и/или текст, прекратив дальнейшую обработку запроса.

*   **Пример:**
    ```nginx
    location ~ \.php$ {
        # Временно для отладки:
        return 200 "Location: Regexp PHP";
        # После отладки раскомментировать основную конфигурацию:
        # root           /var/www/html;
        # fastcgi_pass   unix:/var/run/php/php7.4-fpm.sock;
        # fastcgi_index  index.php;
        # include        fastcgi_params;
        # fastcgi_param  SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }
    ```
    Используя `curl` или браузер, можно увидеть ответ "Location: Regexp PHP", что подтверждает попадание запроса в этот `location`.

**Тестирование конфигурации:**

Всегда проверяйте синтаксис конфигурации Nginx (`nginx -t`) и перезагружайте его (`nginx -s reload`) после внесения изменений.

## 6. Примеры конфигурации (WordPress)

Типичная конфигурация `location` для WordPress часто включает:

*   Перенаправление HTTP на HTTPS. Подробная информация доступна в [[../Angie/angie_tls_setup.md|Настройка TLS в Nginx: безопасность и скорость]]. (Ссылка адаптирована под Nginx)
*   `location /` с `try_files` для обработки статики и перенаправления на `index.php` для динамического контента.
*   `location ~ \.php$` для обработки PHP-скриптов через FastCGI.
*   `location` для защиты конфиденциальных файлов (например, `.htaccess`, `wp-config.php`).
*   Специальные `location` для статических ресурсов WordPress (например, `/wp-content/`).

```nginx
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name example.com;
    root /var/www/wordpress;
    index index.php index.html index.htm;

    # Защита конфиденциальных файлов начинающиейся с точки (запрет всех файлов с точки кроме .well-known - location ~ /\.(?!well-known).* например /.well-known/acme-challenge/...)
    location ~ /\. {
        deny all; # запрещает доступ все клиентам
    }
    location ~ /(wp-config\.php|wp-trackback\.php|xmlrpc\.php) {
        deny all;
    }

    # Обработка статических файлов и перенаправление на index.php
    location / {
        try_files $uri $uri/ /index.php?$args;
    }

    # Обработка PHP-скриптов
    location ~ \.php$ {
        include snippets/fastcgi-php.conf; # Или полный набор fastcgi_params
        fastcgi_pass unix:/var/run/php/php7.4-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }

    # Специальный location для статики wp-content
    location ~* \.(js|css|png|jpg|jpeg|gif|ico)$ {
        expires max;
        log_not_found off; # Не писать ошибки “файл не найден”
    }
}
