# Перенаправления и перезапись URI в Nginx

## Определения

Манипуляция URI — одна из центральных задач Nginx при обработке входящих запросов. Для изменения пути запроса, перенаправления клиента или организации fallback-механизмов используются директивы `rewrite`, `return` и `try_files`.

- **Rewrite (перезапись):** изменение URI запроса внутри сервера. Процесс прозрачен для клиента: браузер продолжает отображать оригинальный URL, в то время как Nginx обрабатывает запрос по новому пути.
- **Redirect (редирект):** внешнее перенаправление. Сервер отправляет клиенту HTTP-ответ с кодом `3xx` и новым URL в заголовке `Location`. Браузер выполняет новый запрос по указанному адресу.
- **Try_files (проверка):** механизм последовательной проверки существования файлов или директорий на диске с последующим выполнением внутреннего перенаправления или возвратом кода ошибки.

## Базовые концепции

### Порядок выполнения (Execution Order)

Понимание того, когда выполняются директивы перезаписи, критично для настройки сложной маршрутизации:

1.  **Контекст `server`:** Директивы `rewrite`, находящиеся непосредственно в блоке `server`, выполняются ПЕРЕД тем, как Nginx начнет поиск подходящего блока `location`. Если такая директива изменяет URI, поиск локации будет производиться уже по новому значению.
2.  **Контекст `location`:** Директивы выполняются последовательно сверху вниз при попадании запроса в данный блок.

### Директива `rewrite`

Использует регулярные выражения PCRE для изменения URI.

**Синтаксис:** `rewrite regex replacement [flag];`

#### Флаги управления
Выбор флага определяет дальнейшую логику обработки внутри Nginx:

| Флаг | Контекст | Поведение |
| :--- | :--- | :--- |
| **`last`** | `server`, `location` | Прекращает обработку текущего набора правил. Nginx инициирует новый цикл поиска подходящего блока `location` с измененным URI. |
| **`break`** | `location` | Прекращает обработку правил `rewrite` внутри текущего блока. Nginx продолжает обработку запроса в этом же `location` без повторного поиска. |
| **`redirect`** | любой | Возвращает временный редирект (`302 Found`). |
| **`permanent`** | любой | Возвращает постоянный редирект (`301 Moved Permanently`). |

> **Предупреждение:** Nginx ограничивает количество внутренних перенаправлений до **10**. Циклы, вызванные некорректными правилами `last`, приводят к ошибке `500 Internal Server Error`.

#### Аргументы запроса (Query String)
Если строка `replacement` содержит аргументы, они объединяются с исходными. Чтобы полностью заменить аргументы или избавиться от них, в конце строки замены ставится `?`:
```nginx
# Исходный: /users/123?src=web -> Результат: /profile/123 (без аргументов)
rewrite ^/users/(.*)$ /profile/$1? permanent;
```

### Директива `return`

Самый быстрый и предпочтительный способ выполнения редиректов или немедленной отправки ответа. Работает эффективнее `rewrite`, так как не требует обработки регулярных выражений.

**Синтаксис:**
- `return 301 https://example.com$request_uri;` — постоянный редирект всего трафика.
- `return 403 "Access Denied";` — возврат кода ошибки с текстовым телом.

### Директива `try_files`

Основа работы современных SPA и PHP-фреймворков. Проверяет пути относительно корня (`root` или `alias`).

**Синтаксис:** `try_files file ... uri | =code;`

- **Проверка файлов:** `try_files $uri $uri/` — сначала ищет файл по точному пути, затем директорию.
- **Fallback на URI:** Последний параметр — это URI внутреннего перенаправления (например, `/index.php`).
- **Именованные локации:** Позволяет передать управление в специальный блок:
  ```nginx
  location / {
      try_files $uri $uri/ @fallback;
  }
  location @fallback {
      proxy_pass http://backend;
  }
  ```

## Условная логика: map и if

### Директива `map`

Создает переменные на основе значений других переменных. Используется в блоке `http`.

- **Производительность:** Значения в `map` вычисляются только в момент обращения к переменной.
- **Регулярные выражения:** Если используются регулярные выражения (`~` или `~*`), они проверяются в том порядке, в котором указаны в блоке. Первое совпадение выигрывает.

```nginx
map $http_user_agent $device_type {
    default        "desktop";
    "~*iphone"     "mobile";
    "~*android"    "mobile";
}
```

### Предостережение «If is Evil»

Использование `if` внутри `location` — частая причина непредсказуемого поведения (проблемы с `alias`, `try_files`).

**Рекомендации:**
1.  По возможности заменяйте `if` на `try_files` или `map`.
2.  Внутри `if` в `location` безопасно использовать только `return` или `rewrite ... last/break`. Любые другие директивы могут работать некорректно.

## Практические сценарии

### Сценарий 1: Обработка SPA и Frontend-маршрутизации

Для приложений (React, Vue, Angular), где маршрутизацией занимается браузер, Nginx должен отдавать `index.html` для всех несуществующих путей.

```nginx
location / {
    root /var/www/frontend;
    try_files $uri $uri/ /index.html;
}
```

### Сценарий 2: Перенос API с сохранением обратной совместимости

Внутреннее перенаправление запросов со старой версии API на новую без изменения URL для клиента.

```nginx
location /api/v1/ {
    # /api/v1/users -> /api/v2/users
    rewrite ^/api/v1/(.*)$ /api/v2/$1 last;
}
```

### Сценарий 3: Защита статических файлов (Hotlinking)

Запрет на использование изображений вашего сайта на сторонних ресурсах.

```nginx
location ~* \.(jpg|jpeg|png|gif)$ {
    valid_referers none blocked example.com *.example.com;
    if ($invalid_referer) {
        return 403;
    }
}
```

## Дополнительная информация

### Отладка правил Rewrite

При возникновении проблем с циклами или некорректными путями включите расширенное логирование:

```nginx
server {
    # Записывает детали перезаписи в error_log на уровне notice
    rewrite_log on;
    error_log /var/log/nginx/rewrite_debug.log notice;
}
```
