# Перенаправления и перезапись URI в Nginx

## Определения

Манипуляция URI — одна из центральных задач Nginx при обработке входящих запросов. Для изменения пути запроса, перенаправления клиента или организации fallback-механизмов используются директивы `rewrite`, `return` и `try_files`.

- **Rewrite (перезапись)** — внутреннее изменение URI запроса сервером. Процесс прозрачен для клиента: браузер продолжает отображать оригинальный URL, но Nginx обрабатывает запрос по новому пути.
- **Redirect (редирект)** — внешнее перенаправление. Сервер возвращает ответ с кодом `3xx` (например, `301 Moved Permanently` или `302 Found`) и заголовком `Location`, заставляя браузер выполнить новый запрос по другому адресу.
- **Try_files (проверка)** — механизм последовательной проверки существования файлов или директорий на диске с последующим выполнением внутреннего перенаправления или возвратом кода ошибки.
- **Internal redirect (внутренний редирект)** — перенаправление запроса внутри Nginx без участия клиента. URL в браузере остается неизменным.
- **Internal redirect cycle (цикл внутренних перенаправлений)** — ошибка `500 Internal Server Error`, возникающая при превышении лимита внутренних перенаправлений (10 в Nginx).
- **`$uri`** — текущий нормализованный URI запроса. Изменяется при выполнении `rewrite` или внутреннего редиректа.
- **`$request_uri`** — оригинальный URI запроса, полученный от клиента. Неизменяем на протяжении всего жизненного цикла.
- **Именованный `location` (`@name`)** — блок `location`, идентифицируемый именем после символа `@`, не участвующий в стандартном сопоставлении URI и вызываемый только явно через `try_files`, `error_page`, `rewrite ... last` или `X-Accel-Redirect`.

## Базовые концепции

### Порядок выполнения и жизненный цикл запроса

Понимание того, когда выполняются директивы перезаписи, критично для настройки сложной маршрутизации и предотвращения циклов.

Nginx обрабатывает запрос, содержащий `rewrite`, `return` или `try_files`, в следующем порядке:

1. **Прием запроса:** сервер определяет блок `server` по заголовку `Host` и порту.
2. **Server-level rewrite:** если `rewrite` объявлен в контексте `server`, выполняется до выбора `location`. Если URI изменен, поиск локации производится по новому значению.
3. **Выбор location:** по нормализованному URI выбирается наиболее специфичный блок `location`. Подробности алгоритма — в **[Директива location: основы и приоритеты](./Location/basics.md)**.
4. **Location-level rewrite:** выполнение `rewrite`, `return` или `try_files` внутри найденного `location`.
5. **Внутреннее перенаправление:** при флаге `last` или срабатывании `try_files` инициируется новый цикл выбора `location` по измененному URI.
6. **Ответ клиенту:** при флагах `redirect`/`permanent` клиент получает `3xx` с заголовком `Location`. При `break` запрос продолжает обработку в текущем `location`.

> **Лимит итераций:** Nginx ограничивает количество внутренних перенаправлений до **10** на один запрос. При превышении возвращается ошибка `500 Internal Server Error` с сообщением в логе: `rewrite or internal redirection cycle while internally redirecting to "<uri>"`.

### Директива `rewrite`

Использует регулярные выражения PCRE для изменения URI.

**Синтаксис:** `rewrite regex replacement [flag];`

Директивы `rewrite` выполняются последовательно в порядке их объявления в конфигурации.

#### Флаги управления

Выбор флага определяет дальнейшую логику обработки внутри Nginx:

| Флаг | Контекст | Поведение |
| :--- | :--- | :--- |
| **`last`** | `server`, `location` | Прекращает обработку текущего набора правил. Nginx инициирует новый цикл поиска подходящего блока `location` с измененным URI. |
| **`break`** | `location` | Прекращает обработку правил `rewrite` внутри текущего блока. Nginx продолжает обработку запроса в этом же `location` без повторного поиска. |
| **`redirect`** | любой | Возвращает временный редирект (`302 Found`). |
| **`permanent`** | любой | Возвращает постоянный редирект (`301 Moved Permanently`). |

> **Важно:** При отсутствии флага поведение зависит от строки замены:
> - Если `replacement` начинается с `http://`, `https://` или `$scheme` — Nginx возвращает временный редирект (`302`).
> - Если `replacement` — локальный URI — выполняется внутренняя перезапись с продолжением обработки оставшихся правил в текущем контексте.
> Это поведение является частой причиной непреднамеренных внутренних циклов. Всегда указывайте флаг явно.

#### Аргументы запроса (Query String)

Если строка `replacement` содержит аргументы, они объединяются с исходными. Чтобы полностью заменить аргументы или избавиться от них, в конце строки замены ставится `?`:

```nginx
# Исходный: /users/123?src=web -> Результат: /profile/123 (без аргументов)
rewrite ^/users/(.*)$ /profile/$1? permanent;

# Исходный: /old?foo=bar -> Результат: /new?foo=bar (аргументы сохранены)
rewrite ^/old$ /new permanent;
```

### Директива `return`

Самый быстрый и предпочтительный способ выполнения редиректов или немедленной отправки ответа. Работает эффективнее `rewrite`, так как не требует обработки регулярных выражений и завершает фазу return сразу после выполнения.

**Синтаксис:**

```nginx
# Постоянный редирект всего трафика на HTTPS
return 301 https://example.com$request_uri;

# Временный редирект
return 302 /new-location;

# Возврат кода ошибки с текстовым телом
return 403 "Access Denied";

# Nginx-specific: разорвать соединение без ответа
return 444;
```

> **Рекомендация:** Для простых редиректов (HTTP → HTTPS, канонизация домена, удаление/добавление www) используйте `return`. Директиву `rewrite` применяйте, только когда необходимы регулярные выражения или захват групп.

### Директива `try_files`

Основа работы современных SPA и PHP-фреймворков. Проверяет пути относительно корня (`root` или `alias`).

**Синтаксис:** `try_files file ... uri | =code | @name;`

- **Проверка файлов:** `try_files $uri $uri/` — последовательная проверка ресурсов.
  - `$uri` — проверяет существование конкретного файла (например, `/images/logo.png`).
  - `$uri/` — проверяет существование директории (ищет индексный файл внутри).
  - Если файл или директория не найдены, управление передается последнему параметру (fallback).
- **Fallback на URI:** Последний параметр — это URI внутреннего перенаправления (например, `/index.php` или `=404`).
- **Именованные локации:** Позволяет передать управление в специальный блок и избежать циклических редиректов:

```nginx
location / {
    root /var/www/app;
    try_files $uri $uri/ @fallback;
}

location @fallback {
    proxy_pass http://backend;
}
```

> **Предупреждение:** `try_files` передает в fallback только URI, строка запроса (query string) отбрасывается. Для её сохранения используйте `$is_args$args` при проксировании или явно добавляйте в fallback-URI.

### Переменные `$uri` и `$request_uri`

| Переменная | Значение | Изменяется при rewrite |
| :--- | :--- | :--- |
| **`$request_uri`** | Оригинальный URI запроса от клиента, включая query string (например, `/search?q=nginx`). | Нет |
| **`$uri`** | Текущий нормализованный URI запроса (например, `/search`). Изменяется при `rewrite`, `try_files` или внутреннем редиректе. | Да |

При построении редиректов:
- Используйте `$request_uri`, если нужно сохранить оригинальный путь и query string: `return 301 https://example.com$request_uri;`
- Используйте `$uri`, если нужно сослаться на уже измененный путь.

### Предостережение «If is Evil»

Использование `if` внутри `location` — частая причина непредсказуемого поведения (проблемы с `alias`, `try_files`, конфликты с другими директивами).

**Рекомендации:**
1. По возможности заменяйте `if` на `try_files`, `map` или отдельные блоки `location`.
2. Внутри `if` в `location` безопасно использовать только `return` или `rewrite ... last/break`. Любые другие директивы могут работать некорректно.

## Операции и команды

### Валидация и применение конфигурации

```bash
# Проверка синтаксиса перед применением
nginx -t
# → nginx: configuration file /etc/nginx/nginx.conf test is successful

# Грациозная перезагрузка без потери соединений
nginx -s reload
# → signal reload started

# Принудительная остановка (разрывает активные соединения)
nginx -s stop

# Просмотр работающих процессов
ps aux | grep nginx
```

### Отладка rewrite и внутренних редиректов

```bash
# Включение логирования rewrite (только в контексте server)
# В конфигурации:
# server {
#     rewrite_log on;
#     error_log /var/log/nginx/rewrite_debug.log notice;
# }

# Пример вывода в логе:
# → *1 rewrite: /users/123 -> /profile/123, redirect=301

# Глубокая отладка (требует сборки с --with-debug)
# error_log /var/log/nginx/error.log debug;
# В логе появляются записи о выборе location и обработке переменных:
# → *12345 using location "/api/v1/" for "/api/v1/users"
# → *12345 http script var: "$uri" = "/api/v1/users"
```

> **Внимание:** `rewrite_log` работает только в контексте `server`. Директива `error_log` с уровнем `debug` создает значительную нагрузку на диск и CPU. Используйте её только для точечной диагностики в нерабочее время.

### Диагностика с curl

```bash
# Проверка заголовка Location при редиректе
curl -I http://example.com/old-path
# → HTTP/1.1 301 Moved Permanently
# → Location: https://example.com/new-path

# Проверка с принудительным отключением Following redirects
curl -I -L http://example.com/old-path

# Проверка переменной document_root для отладки
# В конфигурации:
# location /test/ {
#     default_type text/plain;
#     return 200 "document_root: $document_root\nuri: $uri\n";
# }
curl http://localhost/test/page.html

# Проверка работы try_files
curl -I https://example.com/nonexistent
# → 404 или fallback-код
```

## Практические сценарии

### Сценарий 1: HTTP → HTTPS редирект

Использование `return` — самый производительный метод, так как он не задействует механизм регулярных выражений.

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;

    # Постоянный редирект для сохранения SEO-веса
    return 301 https://$host$request_uri;
}
```

**Проверка:**

```bash
curl -I http://example.com/
# → HTTP/1.1 301 Moved Permanently
# → Location: https://example.com/
```

### Сценарий 2: Обработка SPA и Frontend-маршрутизации

Для приложений (React, Vue, Angular), где маршрутизацией занимается браузер, Nginx должен отдавать `index.html` для всех несуществующих путей.

**Безопасный паттерн (с именованной локацией):**

```nginx
location / {
    root /var/www/frontend;
    try_files $uri $uri/ @spa;
}

location @spa {
    # index index.html; работает здесь только в современных версиях Nginx
    # Надежнее — явное внутреннее перенаправление
    rewrite ^ /index.html break;
}
```

**Паттерн с директивой `index` (если используется Nginx ≥ 1.3.9):**

```nginx
location / {
    root /var/www/frontend;
    index index.html;
    try_files $uri $uri/ /index.html;
}
```

> **Предупреждение:** `try_files $uri $uri/ /index.html` внутри `location /` вызывает `/index.html`, который снова попадает в тот же `location` и снова вызывает `try_files`. Без директивы `index` или именованного `location @fallback` это приводит к циклу и ошибке `500`. Подробнее — в разделе диагностики.

### Сценарий 3: Перенос API с сохранением обратной совместимости

Внутреннее перенаправление запросов со старой версии API на новую без изменения URL для клиента.

```nginx
location /api/v1/ {
    # /api/v1/users -> /api/v2/users
    rewrite ^/api/v1/(.*)$ /api/v2/$1 last;
}
```

> **Примечание:** Детальное описание maintenance-режима, включая подходы через `include` и симлинк, `map` с внешним файлом, отдельный серверный блок и сценарии с health check, см. в **[Maintenance-режим в Nginx](../../Scenarios/nginx_maintenance_mode.md)**.

### Сценарий 5: Защита статических файлов (Hotlinking)

Запрет на использование изображений вашего сайта на сторонних ресурсах.

```nginx
location ~* \.(jpg|jpeg|png|gif|ico|svg)$ {
    valid_referers none blocked server_names *.example.com example.com;
    if ($invalid_referer) {
        return 403;
    }

    # Кэширование статики для снижения нагрузки
    expires 7d;
    add_header Cache-Control "public, no-transform";
}
```

## Диагностика и устранение неполадок

### Типичные ошибки

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `500 Internal Server Error` | Цикл внутренних перенаправлений (`rewrite`/`try_files`/`error_page`) | Проверить `error.log`; убедиться, что `try_files` не вызывает тот же `location`; использовать именованный `location @fallback` |
| `500 Internal Server Error` | Ошибка в синтаксисе `rewrite` или неверное регулярное выражение | Проверить `nginx -t`; включить `rewrite_log on` |
| `404 Not Found` при существующем файле | Неверный `root`/`alias` или off-by-slash | Проверить `$document_root` через `return`; проверить права доступа |
| `404` после `try_files` с query string | `try_files` отбросил query string, а fallback ожидал его | Добавить `$is_args$args` в `proxy_pass` или явно прописать аргументы |
| Бесконечный редирект SPA | `try_files $uri $uri/ /index.html` без `index` или именованного `location` | Добавить `index index.html;` или перейти на `@fallback` |
| Неожиданное поведение `if` | `if` внутри `location` конфликтует с `try_files`/`alias` | Заменить на `map`, отдельный `location` или оставить только `return`/`rewrite` внутри `if` |

### Диагностические команды

```bash
# Поиск циклических редиректов в логе
grep -E "rewrite or internal redirection cycle" /var/log/nginx/error.log

# Определить фактический порядок location после include
nginx -T | grep -n "location"

# Проверить переменную document_root для отладки
# В конфигурации:
# location /test/ {
#     default_type text/plain;
#     return 200 "document_root: $document_root\nuri: $uri\n";
# }

# Просмотр логов доступа для статики
tail -f /var/log/nginx/access.log | grep "\.\(css\|js\|png\|jpg\)"

# Анализ ошибок доступа
grep "denied" /var/log/nginx/error.log
```

## Лучшие практики

### Производительность

1. **Используйте `return` вместо `rewrite`** для простых редиректов. `return` не задействует PCRE и завершается на этапе return, что быстрее.
2. **Включайте `pcre_jit on;`** в контексте `main` для ускорения обработки регулярных выражений в `rewrite` и `location`.
3. **Используйте `break` вместо `last`** внутри `location`, если перезаписанный URI должен обрабатываться в том же блоке. Это избавляет от повторного поиска `location`.
4. **Предпочитайте `map` вместо `if`** для условной логики. `map` вычисляется лениво и не инициирует неожиданных побочных эффектов внутри `location`.

### Безопасность

1. **Никогда не используйте `if` с `proxy_pass`** или другими генераторами ответов внутри `location`. Это documented anti-pattern.
2. **Явно указывайте флаг** в `rewrite`. Отсутствие флага с локальным URI приводит к неочевидному продолжению обработки и потенциальным циклам.
3. **Ограничьте область действия `rewrite`** в `server` блоке. Server-level `rewrite` влияет на выбор `location` и может быть неожиданным для новых блоков, добавленных позже.
4. **Не полагайтесь на `try_files` как на механизм безопасности.** Он проверяет только существование файлов на диске, но не права доступа. Для контроля доступа используйте `internal` или `auth_request`.

### Эксплуатация (SRE)

1. **Ведение логов:** Настройте отдельный `error_log` для rewrite-правил при рефакторинге:

   ```nginx
   server {
       rewrite_log on;
       error_log /var/log/nginx/rewrite_debug.log notice;
   }
   ```

2. **Мониторинг циклов:** Добавьте в алертинг проверку на `500` ошибки с сообщением `rewrite or internal redirection cycle` в `error.log`. Это указывает на некорректную конфигурацию.
3. **Канонизация URL:** Используйте `return 301` для постоянных изменений структуры URL. Избегайте каскадов `rewrite ... last` для канонизации — они потребляют CPU на каждом запросе.
4. **Резервное копирование конфигурации:** Перед массовым рефакторингом правил `rewrite` создайте бэкап конфигурации и проверяйте изменения через `nginx -t`.
5. **Тестирование в staging:** Используйте `curl -I` для проверки цепочки редиректов перед деплоем в production:

   ```bash
   curl -I http://staging.example.com/old-path
   # → HTTP/1.1 301 Moved Permanently
   # → Location: https://staging.example.com/new-path
   ```
