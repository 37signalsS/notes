# Обзор Nginx

**Актуально для:** Nginx 1.26.x (Stable) / 1.27.x (Mainline)

---

## Определения

**Nginx** (произносится как «engine-x») — высокопроизводительный веб-сервер, обратный прокси-сервер (reverse proxy), почтовый прокси и универсальный балансировщик нагрузки сетевых уровней L4 (TCP/UDP) и L7 (HTTP), распространяемый под лицензией 2-clause BSD. Разработан для обслуживания сверхвысоких сетевых нагрузок при минимальном потреблении оперативной памяти и процессорного времени.

Основные роли Nginx в инфраструктуре системного администрирования и SRE:

- **Веб-сервер статического контента:** аппаратная отдача статики (HTML, CSS, JS, медиафайлы) с использованием системных вызовов ядра Linux без копирования в пространство пользователя (Zero-Copy).
- **Обратный прокси-сервер (Reverse Proxy):** единая точка входа (Inbound Gateway) для веб-приложений (PHP-FPM, Python WSGI/ASGI, Go, Node.js, Java). Обеспечивает изоляцию внутренней сети, согласование протоколов, буферизацию медленных клиентов и разгрузку бэкендов.
- **Балансировщик нагрузки (Load Balancer):** распределение сетевого трафика между пулами целевых серверов (upstreams) на прикладном (HTTP/HTTPS) и транспортном (TCP/UDP через модуль `stream`) уровнях с контролем доступности.
- **Кэширующий прокси (Proxy Cache):** локальное сохранение ответов бэкендов на быстрых накопителях сервера для мгновенной отдачи повторных запросов без обращения к вычислительным узлам и СУБД.
- **Терминатор TLS/SSL:** централизованная разгрузка шифрования (SSL Offloading), управление сертификатами, реализация современных шифров, OCSP Stapling, поддержка HTTP/2 и HTTP/3 (QUIC).
- **Периметровая защита (Security Shield / Rate Limiting):** защита внутренней инфраструктуры от перегрузок и атак типа DoS за счет жестких лимитов частоты запросов (`limit_req`), параллельных соединений (`limit_conn`) и фильтрации невалидных HTTP-методов.
- **Сжатие и потоковая оптимизация:** динамическое и статическое сжатие контента (Gzip, Brotli) и фрагментированная передача данных (Chunked Transfer Encoding) для минимизации утилизации сетевой полосы.

### Редакции Nginx

1. **Nginx Open Source (Community):** свободно распространяемая версия с открытым исходным кодом. Развивается в двух ветках:
   - **Mainline (основная):** содержит самые свежие функции, оптимизации протоколов (включая HTTP/3) и исправления ошибок. Рекомендуется для большинства современных production-систем.
   - **Stable (стабильная):** получает исключительно исправления критических уязвимостей и серьезных багов. Новая функциональность не добавляется.
   Официальный ресурс документации и исходного кода: [nginx.org](https://nginx.org).
2. **Nginx Plus:** коммерческая закрытая версия от компании F5. Включает специализированные корпоративные модули: динамическое конфигурирование upstream без перезагрузки через HTTP API, активные проверки доступности (active health checks), встроенный Web Application Firewall (WAF) и расширенную отдачу телеметрии в реальном времени. Официальный ресурс: [nginx.com](https://nginx.com).

### Родственные проекты и форки

- **Angie:** независимый форк Nginx от команды оригинальных разработчиков (Web Server LLC). Включает в Open Source редакцию возможности, доступные ранее только в Nginx Plus (динамическое управление апстримами через API, встроенный Prometheus-совместимый статус-интерфейс, автоматический ACME-клиент для TLS-сертификатов). Подробнее см. в **[обзоре Angie](../../Angie/angie_overview.md)**.
- **OpenResty:** специализированная платформа, объединяющая ядро Nginx, модуль LuaJIT и набор библиотек для исполнения высоконагруженной логики маршрутизации, аутентификации и манипуляции трафиком непосредственно в цикле событий веб-сервера.

## Основные концепции и архитектура

### Архитектура: решение проблемы C10k

Nginx был спроектирован для преодоления **проблемы C10k** (одновременное обслуживание 10 000 и более активных клиентских сетевых соединений на одном физическом сервере).

#### Сравнение с традиционной моделью серверов (Apache MPM Prefork / Worker)

Традиционные веб-серверы 1990-х и начала 2000-х годов (например, Apache HTTP Server с модулем MPM Prefork) использовали синхронную модель:
- На каждое входящее клиентское TCP-соединение операционная система выделяет отдельный процесс или поток выполнения (thread).
- Каждый поток требует собственной стековой памяти (обычно от 2 до 8 МБ). При десятках тысяч соединений память сервера исчерпывается лавинообразно.
- Ядро операционной системы тратит львиную долю процессорного времени не на полезную работу (обработку данных), а на постоянное переключение контекста (context switching) между тысячами заблокированных потоков, ожидающих сетевого ввода-вывода от медленных клиентов (Keep-Alive, медленная передача по мобильным сетям).

Nginx принципиально отказывается от создания потоков на каждое соединение в пользу **асинхронной, событийно-ориентированной архитектуры (Event-Driven Non-blocking Architecture)**:
- Небольшое фиксированное количество рабочих процессов (обычно 1 процесс на физическое ядро CPU) обрабатывает абсолютно все клиентские запросы.
- Потребление памяти на одно активное соединение составляет всего несколько килобайт (структуры `ngx_connection_t` и `ngx_http_request_t`).
- Переключение контекста между задачами происходит внутри одного пространства пользователя в цикле обработки событий без дорогостоящих системных прерываний ядра.

### Процессная модель: Master, Worker и вспомогательные процессы

Nginx использует многопроцессную модель с разделением привилегий:

```text
                  ┌───────────────────────────────┐
                  │    Master Process (root)      │
                  │   Чтение конфига, сокеты,     │
                  │   управление процессами       │
                  └──────────────┬────────────────┘
                                 │
         ┌───────────────────────┼───────────────────────┐
         │ fork()                │ fork()                │ fork()
         ▼                       ▼                       ▼
┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│  Worker Process  │    │  Worker Process  │    │  Cache Manager   │
│ (nginx/www-data) │    │ (nginx/www-data) │    │ (nginx/www-data) │
│  Event Loop L7/L4│    │  Event Loop L7/L4│    │ Ротация кэша     │
└──────────────────┘    └──────────────────┘    └──────────────────┘
```

1. **Мастер-процесс (Master Process):**
   - Запускается с правами суперпользователя `root` (чтобы открыть привилегированные сетевые порты 80, 443 и прочитать приватные ключи сертификатов).
   - Не обрабатывает клиентские сетевые пакеты и не парсит HTTP-запросы (что обеспечивает безопасность).
   - Считывает и валидирует конфигурационные файлы.
   - Инициализирует слушающие сокеты (`bind()`, `listen()`) и передает их файловые дескрипторы дочерним процессам.
   - Отслеживает состояние рабочих процессов через сигналы ОС (`SIGCHLD`), перезапускает аварийно завершившиеся воркеры и управляет плавным обновлением конфигурации и бинарных файлов.

2. **Рабочие процессы (Worker Processes):**
   - Запускаются от имени непривилегированного системного пользователя (например, `nginx` или `www-data`).
   - Количество задается директивой `worker_processes` в главном контексте. Значение `auto` автоматически создает по одному воркеру на каждое доступное ядро CPU, что исключает конкуренцию за процессорное время.
   - Привязка воркеров к физическим ядрам через директиву `worker_cpu_affinity` повышает локальность процессорного кэша (L1/L2/L3) и снижает накладные расходы в многосокетных NUMA-системах.
   - Каждый рабочий процесс выполняет однопоточный неблокирующий цикл обработки событий (Event Loop).
   - Предельное число одновременных сетевых дескрипторов, обслуживаемых одним воркером, задается директивой `worker_connections`. Общая теоретическая емкость соединений сервера: `worker_processes * worker_connections`.

3. **Вспомогательные процессы кэширования (Cache Loader и Cache Manager):**
   - **Cache Loader:** кратковременно запускается при старте сервера для считывания метаданных кэша с диска в оперативную память (shared memory zone), после чего корректно завершается.
   - **Cache Manager:** периодически просыпается в фоне для проверки объема дискового кэша (`proxy_cache_path`) и удаления устаревших файлов при превышении установленного лимита `max_size`.

### Механизмы ввода-вывода ядра ОС и Event Loop

Эффективность Nginx базируется на системных интерфейсах мультиплексирования ввода-вывода современных ОС:
- **epoll (Linux):** масштабируемый механизм уведомления о готовности файловых дескрипторов с вычислительной сложностью $O(1)$. В отличие от устаревших системных вызовов `select()` и `poll()` с линейной сложностью $O(N)$, `epoll_wait()` сообщает приложению только те дескрипторы, на которых реально произошли события (прием данных, готовность к записи, закрытие сокета).
- **kqueue (FreeBSD / OpenBSD / macOS):** высокоэффективный аналог epoll для BSD-систем.
- **Zero-Copy (`sendfile`):** системный вызов `sendfile()`, позволяющий ядру передавать данные из дискового кэша страниц (Page Cache) напрямую в буфер сетевой карты (Tx Ring Buffer). Данные не копируются в пространство памяти Nginx, что снижает нагрузку на шину памяти и процессор практически до нуля при отдаче статики.
- **Сетевые оптимизации сокетов:**
  - `tcp_nopush on;` (в Linux активирует опцию сокета `TCP_CORK`): заставляет ядро накапливать заголовки ответа и порции данных из `sendfile`, отправляя их полными сетевыми пакетами MSS (Maximum Segment Size).
  - `tcp_nodelay on;` (деактивирует алгоритм Нагла через `TCP_NODELAY`): отправляет мелкие пакеты без ожидания подтверждения (ACK), что критично для интерактивного HTTP/2, HTTP/3 и быстрых транзакций Keep-Alive.

### 11 фаз обработки HTTP-запроса

При поступлении HTTP-запроса Nginx проводит его через строгую цепочку из 11 внутренних фаз (phases). Понимание этих фаз критично для инженера SRE, так как директивы конфигурации выполняются в строгом порядке фаз, а не в порядке их написания в файле:

1. **`NGX_HTTP_POST_READ_PHASE`:** первичное чтение заголовков запроса из сокета. Здесь работает модуль `ngx_http_realip_module`, восстанавливающий реальный IP клиента из заголовков балансировщиков.
2. **`NGX_HTTP_SERVER_REWRITE_PHASE`:** выполнение директив перезаписи URI (`rewrite`), объявленных на уровне блока `server` (до выбора конкретного location).
3. **`NGX_HTTP_FIND_CONFIG_PHASE`:** выбор наиболее подходящего блока `location` на основе сопоставления URI с префиксами и регулярными выражениями.
4. **`NGX_HTTP_REWRITE_PHASE`:** исполнение директив манипуляции URI (`rewrite`, `set`, `if`) внутри выбранного `location`.
5. **`NGX_HTTP_POST_REWRITE_PHASE`:** постобработка изменений URI. Если директива `rewrite` изменила адрес, цикл обработки может вернуться на фазу `FIND_CONFIG` (до 10 внутренних перенаправлений).
6. **`NGX_HTTP_PREACCESS_PHASE`:** предварительный контроль доступа и защита от перегрузок. Проверяются зоны ограничения частоты запросов (`limit_req`) и числа соединений (`limit_conn`).
7. **`NGX_HTTP_ACCESS_PHASE`:** проверка прав клиента на доступ к ресурсу (`allow`, `deny`, `auth_basic`, `auth_request`).
8. **`NGX_HTTP_POST_ACCESS_PHASE`:** проверка агрегированного решения модулей доступа (директива `satisfy all|any`).
9. **`NGX_HTTP_PRECONTENT_PHASE`:** подготовительные операции перед генерацией контента (модули `mirror`, `try_files`).
10. **`NGX_HTTP_CONTENT_PHASE`:** непосредственная генерация ответа. Запрос отдается ровно одному генератору контента: статическому файловому обработчику, модулю `proxy_pass`, `fastcgi_pass`, `uwsgi_pass` или директиве `return`.
11. **`NGX_HTTP_LOG_PHASE`:** фиксация информации о запросе в журналах (`access_log`) после полной отправки ответа клиенту.

### Иерархия контекстов конфигурации

Конфигурационный файл Nginx состоит из директив, сгруппированных в древовидные блоки (контексты). Область видимости и наследование определяются положением контекста:

- **Main (Global):** корневой контекст конфигурационного файла. Содержит параметры уровня ОС: имя пользователя процесса (`user`), число воркеров (`worker_processes`), пути к PID-файлу (`pid`) и главному логу ошибок (`error_log`).
- **Events:** контекст настройки сетевого движка рабочих процессов (`worker_connections`, `use epoll`, `multi_accept`).
- **HTTP:** глобальный контейнер веб-сервера. Содержит типы MIME, общие настройки таймаутов, форматы логирования, зоны кэширования и лимитов.
- **Server:** контекст описания виртуального хоста (виртуального сервера). Определяет слушающие порты (`listen`) и доменные имена (`server_name`).
- **Location:** правила маршрутизации конкретных URI внутри виртуального хоста. Может содержать вложенные блоки `location`.
- **Upstream:** описание пула бэкенд-серверов для балансировки нагрузки и отказоустойчивости (объявляется внутри контекста `http` или `stream`).
- **Stream:** независимый от `http` контекст для проксирования и балансировки чистого транспортного трафика L4 (TCP и UDP).

**Правило наследования директив:** дочерние контексты наследуют скалярные директивы родительских контекстов. Однако при объявлении блочных директив или директив-массивов (например, `proxy_set_header`) значения родительского уровня полностью перезаписываются, если в дочернем контексте объявлен хотя бы один одноименный блок.

### Управление процессами через POSIX-сигналы

Мастер-процесс Nginx управляется отправкой стандартных сигналов Unix:

| Сигнал | Команда CLI | Действие мастер-процесса |
| :--- | :--- | :--- |
| **`SIGHUP`** | `nginx -s reload` | Плавная перезагрузка конфигурации: мастер перечитывает файлы, проверяет синтаксис, запускает новых воркеров со свежей конфигурацией и отправляет старым воркерам сигнал на плавное завершение после отдачи открытых запросов. |
| **`SIGQUIT`** | `nginx -s quit` | Плавная остановка (Graceful Shutdown): прекращается прием новых соединений, воркеры дожидаются окончания обработки текущих клиентов и штатно завершаются. |
| **`SIGTERM` / `SIGINT`** | `nginx -s stop` | Немедленная остановка: принудительный обрыв всех активных соединений и завершение процессов. |
| **`SIGUSR1`** | `nginx -s reopen` | Переоткрытие файлов журналов (используется утилитой `logrotate` без перезапуска сервера). |
| **`SIGUSR2`** | — | Запуск параллельного нового мастер-процесса со свежим бинарным файлом без простоя (Zero-Downtime Upgrade). |
| **`SIGWINCH`** | — | Плавная остановка рабочих процессов старого мастера (применяется в связке с `SIGUSR2`). |

#### Сценарий Zero-Downtime обновления бинарного файла сервера

При обновлении пакетов или замене скомпилированного бинарника Nginx недопустимо выполнять `systemctl restart`, так как это обрывает существующие соединения. Штатный механизм обновления без простоя:

```bash
# 1. Проверить синтаксис текущей конфигурации новым бинарником
/usr/sbin/nginx -t
# → nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
# → nginx: configuration file /etc/nginx/nginx.conf test is successful

# 2. Отправить старому мастер-процессу сигнал на запуск нового бинарника
kill -USR2 $(cat /run/nginx.pid)

# Старый мастер переименовывает свой PID-файл в /run/nginx.pid.oldbin
# и запускает новый экземпляр /usr/sbin/nginx с новым PID в /run/nginx.pid.
# Теперь параллельно работают два мастер-процесса, слушающих одинаковые сокеты.

# 3. Отправить сигнал WINCH старому мастеру для остановки его воркеров
kill -WINCH $(cat /run/nginx.pid.oldbin)

# Новые соединения теперь принимаются только новыми воркерами.
# Старые воркеры завершаются по мере обслуживания клиентов.

# 4. Фиксация результата: завершить старый мастер-процесс
kill -QUIT $(cat /run/nginx.pid.oldbin)
# → Старый мастер завершается, обновление успешно выполнено без потери пакетов.
```

**Откат в случае обнаружения сбоя в новом бинарнике (до шага 4):**
```bash
# Перезапустить рабочие процессы старого мастера
kill -HUP $(cat /run/nginx.pid.oldbin)

# Принудительно остановить новый мастер
kill -TERM $(cat /run/nginx.pid)
```

#### Защита от зависания воркеров при Graceful Reload

При обработке долгих сетевых соединений (WebSocket, серверные события SSE, потоковые выгрузки gRPC) старые воркеры могут оставаться в памяти часами, накапливаясь после каждого reload.

Для предотвращения деградации ресурсов в контексте `main` обязательно задается директива принудительного завершения:

```nginx
worker_shutdown_timeout 30s;
```
По истечении указанного времени воркер принудительно разрывает оставшиеся сокеты и завершает процесс. Подробный разбор тюнинга соединений приведен в руководстве по **[оптимизации производительности Nginx](../Performance/nginx_performance_tuning.md)**.

## Практические сценарии и базовая конфигурация

### Базовый эталонный конфигурационный скелет (Production Baseline)

Ниже приведен эталонный минимальный файл `/etc/nginx/nginx.conf` для bare-metal и виртуальных серверов под управлением Linux, реализующий рекомендации по безопасности и масштабируемости:

```nginx
# /etc/nginx/nginx.conf
user nginx nginx;
worker_processes auto;
worker_cpu_affinity auto;
worker_rlimit_nofile 65535;
pid /run/nginx.pid;
error_log /var/log/nginx/error.log warn;

# Ограничение времени дожития старых процессов при reload
worker_shutdown_timeout 30s;

events {
    worker_connections 8192;
    use epoll;
    multi_accept on;
}

http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    # Скрытие версии Nginx в заголовках ответов и страницах ошибок
    server_tokens off;

    # Оптимизация сетевого ввода-вывода ядра
    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;

    # Таймауты поддержания соединений и защиты от медленных атак
    keepalive_timeout 65;
    keepalive_requests 1000;
    client_body_timeout 15;
    client_header_timeout 15;
    send_timeout 15;

    # Буферы клиентских запросов
    client_max_body_size 16m;
    client_body_buffer_size 128k;
    client_header_buffer_size 1k;
    large_client_header_buffers 4 8k;

    # Формат структурированного JSON-логирования для SIEM и сборщиков логов
    log_format json_combined escape=json
      '{"time_local":"$time_iso8601",'
      '"client_ip":"$remote_addr",'
      '"remote_user":"$remote_user",'
      '"request_method":"$request_method",'
      '"request_uri":"$request_uri",'
      '"status":$status,'
      '"body_bytes_sent":$body_bytes_sent,'
      '"request_time":$request_time,'
      '"upstream_response_time":"$upstream_response_time",'
      '"upstream_addr":"$upstream_addr",'
      '"http_referrer":"$http_referer",'
      '"http_user_agent":"$http_user_agent"}';

    access_log /var/log/nginx/access.log json_combined;

    # Зоны ограничения частоты запросов для защиты от перегрузок
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;
    limit_conn_zone $binary_remote_addr zone=addr_limit:10m;

    # Подключение изолированных виртуальных хостов
    include /etc/nginx/conf.d/*.conf;
}
```

### Сценарий 1: Обратный прокси (Reverse Proxy) с Upstream Keep-Alive

Классическая конфигурация проксирования HTTP-трафика на группу внутренних прикладных серверов без использования внешних облачных балансировщиков.

Файл конфигурации виртуального хоста `/etc/nginx/conf.d/app_proxy.conf`:

```nginx
# Описание группы локальных бэкендов
upstream backend_cluster {
    # Метод балансировки по умолчанию: round-robin
    server 192.168.10.11:8080 max_fails=3 fail_timeout=10s;
    server 192.168.10.12:8080 max_fails=3 fail_timeout=10s;

    # Пул постоянных TCP-соединений между Nginx и бэкендами
    # Предотвращает исчерпание эфемерных портов при высоких RPS
    keepalive 32;
}

server {
    listen 80;
    server_name app.internal.domain;

    # Принудительное перенаправление HTTP -> HTTPS
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name app.internal.domain;

    # TLS-сертификаты
    ssl_certificate /etc/ssl/certs/app.crt;
    ssl_certificate_key /etc/ssl/private/app.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;
    ssl_prefer_server_ciphers on;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    # Корневой маршрут проксирования
    location / {
        proxy_pass http://backend_cluster;

        # Обязательные директивы для работы upstream keepalive
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        # Проброс реальных клиентских реквизитов бэкенду
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Таймауты межсерверного взаимодействия
        proxy_connect_timeout 5s;
        proxy_send_timeout 30s;
        proxy_read_timeout 30s;

        # Буферизация ответов бэкенда для защиты медленных клиентов
        proxy_buffering on;
        proxy_buffers 8 16k;
        proxy_buffer_size 16k;
    }

    # Изолированный маршрут API с ограничением скорости
    location /api/ {
        limit_req zone=api_limit burst=20 nodelay;
        limit_conn addr_limit 10;

        proxy_pass http://backend_cluster;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### Сценарий 2: Высокопроизводительный сервер статических файлов

Оптимизированная отдача медиа-ресурсов, архивов и фронтенд-ассетов с клиентским кэшированием и механизмом сжатия:

```nginx
server {
    listen 80;
    server_name static.internal.domain;
    root /var/www/static;

    # Запрет отдачи скрытых системных файлов (.git, .env)
    location ~ /\. {
        deny all;
        access_log off;
        log_not_found off;
    }

    # Раздача статических ассетов с долгосрочным кэшированием браузера
    location ~* \.(css|js|jpg|jpeg|png|gif|ico|svg|woff2|webp)$ {
        expires 30d;
        add_header Cache-Control "public, no-transform";
        access_log off;

        # Кэширование дескрипторов файлов в памяти воркера
        open_file_cache max=10000 inactive=30s;
        open_file_cache_valid 60s;
        open_file_cache_min_uses 2;
        open_file_cache_errors on;
    }

    # Обслуживание SPA или базовых страниц
    location / {
        try_files $uri $uri/ /index.html =404;
    }
}
```

### Сценарий 3: Балансировка L4 (TCP/UDP) через контекст Stream

Используется для балансировки входящих соединений СУБД (PostgreSQL, MySQL), очередей сообщений или сквозного проксирования TLS (SNI Proxy) без расшифровки трафика на Nginx:

```nginx
# /etc/nginx/conf.d/stream_db.conf (подключается внутри блока stream {})
stream {
    upstream postgres_read_pool {
        # Балансировка по наименьшему числу активных соединений
        least_conn;
        server 192.168.20.11:5432 max_fails=2 fail_timeout=5s;
        server 192.168.20.12:5432 max_fails=2 fail_timeout=5s;
    }

    server {
        listen 5433;
        proxy_pass postgres_read_pool;
        proxy_connect_timeout 2s;
        proxy_timeout 10m;
    }
}
```

Подробный разбор конфигурации L4-проксирования доступен в заметке **[L4-проксирование и балансировка в Nginx](../Proxy/nginx_l4_proxying.md)**.

### Сценарий 4: Отказоустойчивый кластер High Availability (Keepalived + VRRP)

Одиночный экземпляр Nginx на физическом сервере или виртуальной машине является единой точкой отказа (SPOF). В локальных ЦОД и на bare-metal стандартным SRE-решением для создания HA-пары является использование двух узлов Nginx под управлением демона **Keepalived** с плавающим виртуальным IP-адресом (VIP):

```text
               Клиентский трафик
                       │
                       ▼
            VIP: 192.168.1.100 (VRRP)
                       │
         ┌─────────────┴─────────────┐
         ▼                           ▼
┌──────────────────┐        ┌──────────────────┐
│  nginx-node-01   │        │  nginx-node-02   │
│  Keepalived      │  VRRP  │  Keepalived      │
│  State: MASTER   │◄──────►│  State: BACKUP   │
│  Priority: 101   │        │  Priority: 100   │
└────────┬─────────┘        └────────┬─────────┘
         │                           │
         └─────────────┬─────────────┘
                       ▼
                 Пул бэкендов
```

1. **Принцип работы:** мастер-узел удерживает VIP и принимает входящие пакеты. Узлы обмениваются периодическими VRRP-анонсами по локальной сети. При физическом падении мастера или сбое процесса Nginx резервный узел (BACKUP) перехватывает VIP за 1–2 секунды через Gratuitous ARP.
2. **Скрипт проверки жизнеспособности (Health Check):** Keepalived выполняет локальный опрос сервиса:
   ```bash
   /usr/bin/curl -sf http://127.0.0.1:80/healthz > /dev/null
   ```
   В случае недоступности эндпоинта приоритет узла снижается, инициируя автоматический фейловер на второй узел.

Пошаговая настройка демона и конфигурации отказоустойчивости приведена в **[обзоре Keepalived](../../../Networking/ServicesAndTools/keepalived_overview.md)** и **[HA-конфигурации Angie с Keepalived](../../Angie/angie_ha_with_keepalived.md)**.

## Эксплуатация и управление

### Параметры командной строки бинарного файла Nginx

Бинарный файл `/usr/sbin/nginx` поддерживает набор управляющих ключей:

```bash
# Проверка синтаксиса конфигурационных файлов без применения изменений
nginx -t
# → nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
# → nginx: configuration file /etc/nginx/nginx.conf test is successful

# Проверка синтаксиса и вывод полной собранной конфигурации (включая все include) в stdout
nginx -T

# Отправка сигнала работающему мастер-процессу
nginx -s reload    # перечитать конфигурацию (HUP)
nginx -s quit      # корректно завершить работу (QUIT)
nginx -s stop      # немедленно остановить сервер (TERM)
nginx -s reopen    # переоткрыть файлы журналов (USR1)

# Вывод краткой версии сервера
nginx -v
# → nginx version: nginx/1.26.2

# Вывод версии, компилятора и полных сборочных аргументов (configure arguments)
nginx -V

nginx -c /etc/nginx/test_nginx.conf

# Запуск или тестирование с переопределением глобальных директив
nginx -g "daemon off;"
```

## Диагностика и устранение неисправностей

Ниже представлены наиболее частые критические сбои Nginx на уровне операционной системы и архитектуры, причины их возникновения и регламент локализации:

| Симптом / Ошибка в логе | Первопричина | Метод локализации и устранение |
| :--- | :--- | :--- |
| `[emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)` | Порт 80 или 443 уже занят другим процессом (Apache, старый зависший экземпляр Nginx, HAProxy). | Выполнить `ss -tulpn '( sport = :80 or sport = :443 )'` для выявления конфликтующего PID. Остановить сторонний сервис (`systemctl stop apache2`) либо завершить зависший процесс `kill -9 <PID>`. |
| `[alert] ... worker_connections are not enough` в `error.log` | Исчерпан лимит одновременных сетевых соединений на воркер при всплеске входящего трафика или подвисании бэкендов. | 1. Проверить текущее число соединений через `ss -s`.<br>2. Увеличить директиву `worker_connections` (например, с 1024 до 8192).<br>3. Убедиться, что `worker_rlimit_nofile` вдвое превышает `worker_connections`. |
| `open() ".../index.html" failed (13: Permission denied)` | Пользователь, под которым запущены воркеры (`nginx`), не имеет прав на чтение файла либо прав выполнения (`+x`) на одну из родительских директорий пути. | 1. Проверить дерево разрешений утилитой `namei -m /var/www/static/index.html`.<br>2. Установить владельца и права: `chown -R nginx:nginx /var/www/static && chmod 755 /var/www/static`.<br>3. В дистрибутивах с SELinux проверить контекст безопасности: `ls -Z` и применить `restorecon -Rv /var/www`. |
| `502 Bad Gateway` (в логе: `connect() failed (111: Connection refused)`) | Nginx не может установить TCP-соединение с upstream-сервером: сервис бэкенда не запущен, слушает другой порт или заблокирован локальным фаерволом (iptables/nftables). | 1. Проверить статус службы бэкенда: `systemctl status php8.2-fpm` (или целевого сервиса).<br>2. Проверить доступность сокета/порта локально с сервера Nginx: `curl -I http://127.0.0.1:8080` или `nc -zv 127.0.0.1 8080`. |
| `504 Gateway Time-out` (в логе: `upstream timed out (110: Connection timed out)`) | Бэкенд принял соединение, но не успел вернуть ответ за время, определенное директивой `proxy_read_timeout` (по умолчанию 60с). | 1. Проанализировать длительность выполнения медленных запросов/транзакций СУБД на стороне бэкенда.<br>2. При необходимости временно увеличить таймаут: `proxy_read_timeout 120s;`. |
| `[emerg] could not build server_names_hash, you should increase server_names_hash_bucket_size` | В конфигурации задано большое количество виртуальных хостов или длинные доменные имена, превышающие размер хэш-корзины в памяти. | Добавить в блок `http` директиву `server_names_hash_bucket_size 64;` (или `128;`). |

### SRE-чеклист первичной диагностики при аварии

При получении алерта о деградации сервиса на Nginx дежурный инженер выполняет последовательную локализацию:
1. **Валидация конфигурации:** выполнить `nginx -t` для исключения битых конфигов после недавних правок.
2. **Проверка состояния процесса:** выполнить `systemctl status nginx` и убедиться, что мастер-процесс не находится в состоянии перезапуска (crash-loop).
3. **Анализ системных ресурсов:** выполнить `free -m` (проверка свободной памяти и отсутствия работы OOM Killer), `df -h` (проверка наличия свободного места на дисках для логов и временных файлов кэша) и `top` / `htop` (утилизация CPU).
4. **Анализ системного журнала и логов ошибок:**
   ```bash
   journalctl -u nginx.service -n 50 --no-pager
   tail -n 100 /var/log/nginx/error.log
   ```
5. **Проверка сетевых очередей:** убедиться, что очередь `Recv-Q` команды `ss -tln` для портов 80/443 не переполнена (переполнение свидетельствует о нехватке воркеров или блокировке event loop).

Полный сборник сценариев диагностики, профилирования и устранения инцидентов представлен в профильном руководстве: **[Диагностика и устранение неисправностей Nginx](../Operations/nginx_troubleshooting.md)**.

## Рекомендации и лучшие практики

### Стандарты надежности и безопасности в Production

1. **Принцип наименьших привилегий (Least Privilege):**
   - Никогда не запускайте рабочие процессы от имени пользователя `root`. Директива `user nginx;` обязательна в `nginx.conf`.
   - Ограничивайте права доступа к конфигурационным директориям: права на `/etc/nginx` должны быть `0750` с владельцем `root:nginx`.
   - Приватные ключи TLS-сертификатов (`/etc/ssl/private/`) должны иметь права `0400` или `0600` и принадлежать пользователю `root`.

2. **Автоматизация и CI/CD валидация:**
   - Любое изменение конфигурационных файлов в репозитории инфраструктурного кода (IaC) должно проходить обязательный линтинг и проверку `nginx -t` в изолированном контейнере перед выкаткой на серверы.
   - Запрещено выполнять `systemctl restart nginx` в автоматизированных скриптах раскатки. Применяется исключительно `systemctl reload nginx` (отправка `SIGHUP`) после обязательной проверки `nginx -t`.

3. **Синхронизация системных лимитов (File Descriptors):**
   - На каждое проксируемое клиентское соединение Nginx расходует минимум 2 файловых дескриптора (дескриптор входящего клиентского сокета и дескриптор исходящего сокета к бэкенду).
   - Значение директивы `worker_rlimit_nofile` должно рассчитываться по формуле:
     $$\text{worker\_rlimit\_nofile} \ge 2 \times \text{worker\_connections} \times \text{worker\_processes}$$
   - Системный лимит в `/etc/security/limits.conf` или в systemd unit-файле (`LimitNOFILE=65535`) должен быть достаточным для запуска процесса с повышенными лимитами.

4. **Защита периметра и скрытие идентификации:**
   - Обязательно отключайте трансляцию версии Nginx: директива `server_tokens off;` в контексте `http`.
   - Настраивайте жесткие лимиты на размер тела запроса (`client_max_body_size`) во избежание переполнения диска и оперативной памяти большими бинарными выгрузками.
   - Используйте таймауты `client_body_timeout 10s;` и `client_header_timeout 10s;` для автоматического сброса соединений от медленных клиентов (защита от атак класса Slowloris).

5. **Мониторинг и наблюдаемость (Observability):**
   - Настройте сбор метрик производительности (активные соединения, RPS по кодам статусов 2xx/3xx/4xx/5xx) с помощью модуля `ngx_http_stub_status_module` или специализированных экспортеров.
   - Подробная инструкция по развертыванию метрик приведена в руководстве по **[мониторингу с модулем VTS](../Operations/nginx_vts_monitoring_setup.md)**.
   - Настройте регулярную ротацию журналов через демон `logrotate` с отправкой сигнала `USR1` мастер-процессу, исключая переполнение дискового пространства `/var/log`.
