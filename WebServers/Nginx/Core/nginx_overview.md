# Обзор Nginx

## Определения

**Nginx** (произносится как "engine-x") — это высокопроизводительный веб-сервер, обратный прокси-сервер, кэширующий прокси и балансировщик нагрузки с открытым исходным кодом. Он спроектирован для обеспечения максимальной стабильности и производительности при низком потреблении ресурсов.

Основные роли Nginx в инфраструктуре:

- **Веб-сервер:** высокоэффективная отдача статического контента (HTML, изображения, файлы).
- **Обратный прокси-сервер (Reverse Proxy):** точка входа для приложений на PHP, Python, Go, Node.js. Действует как "консьерж", принимая запросы от клиентов и распределяя их между бэкендами.
- **Балансировщик нагрузки:** распределение трафика между узлами бэкенда на уровнях L7 (HTTP) и L4 (TCP/UDP).
- **Кэширующий прокси:** ускорение ответов за счет сохранения результатов запросов к бэкендам. Позволяет не нагружать бэкенд и базу данных для статических или редко меняющихся данных.
- **Терминатор TLS/SSL:** централизованное управление сертификатами и шифрованием трафика.
- **Обеспечение безопасности (Shield):** уменьшение поверхности атаки за счет единой публичной точки входа, скрывающей внутренние серверы.
- **Сжатие и оптимизация:** сжатие тяжелых файлов (Gzip) и передача данных частями (Chunked transfer) для экономии пропускной способности.

### Nginx Open Source vs Nginx Plus

Nginx поставляется в двух основных редакциях:
- **Nginx Open Source (Community):** свободно распространяемая версия. Документация доступна на [nginx.org](https://nginx.org).
- **Nginx Plus:** коммерческая версия с дополнительными функциями (активные проверки состояния, WAF, расширенный мониторинг). Документация доступна на [nginx.com](https://nginx.com).

### Nginx и его форки

- **Nginx (F5):** Отраслевой стандарт. Версия Mainline (1.27+) активно развивает поддержку HTTP/3 и QUIC.
- **Angie:** Форк от оригинальной команды разработчиков (Web Server LLC). Включает функции, ранее доступные только в Nginx Plus (динамические апстримы, расширенный мониторинг). Подробнее см. в **[обзоре Angie](../../Angie/angie_overview.md)**.
- **OpenResty:** Сборка Nginx с интегрированным языком Lua для создания высокопроизводительных веб-приложений внутри сервера.

## Базовые концепции

### Архитектура: решение проблемы C10k

Nginx был создан для решения **"проблемы C10k"** — эффективной обработки 10 000 и более одновременных соединений.

#### Сравнение с традиционными серверами

Традиционные веб-серверы, такие как **Apache** или **IIS** (версий 90-х годов), используют линейную модель: для каждого входящего запроса создается отдельный процесс или поток (thread). Это приводит к высокому потреблению ресурсов CPU и оперативной памяти, так как при росте числа соединений система тратит ресурсы на переключение контекста.

Nginx использует событийно-ориентированный (event-driven) и асинхронный подход. Один процесс может обслуживать тысячи запросов одновременно в неблокирующем режиме.

#### Процессная модель: Master и Worker

Для понимания архитектуры Nginx эффективна аналогия с рестораном:

1.  **Мастер-процесс (Master Process):**
    - Роль: **Управляющий (Supervisor)**.
    - Не обрабатывает запросы напрямую. Отвечает за чтение конфигурации и управление жизненным циклом рабочих процессов.
2.  **Рабочие процессы (Worker Processes):**
    - Роль: **Шеф-повара (Chefs)**.
    - Чем больше воркеров, тем больше запросов сервер может обрабатывать параллельно (аналогия с несколькими кассами в супермаркете). Управляется директивой **`worker_processes`** (обычно устанавливается по количеству ядер CPU или в `auto`).
    - Внутри каждого воркера работает **Event Loop (Официант)**. Официант не стоит у одного столика, ожидая выбора клиента. Он принимает заказ, передает его шефу и сразу идет к следующему столу.
    - Максимальное количество одновременных соединений на один воркер задается директивой **`worker_connections`** в контексте `events`. Увеличение этого значения позволяет обрабатывать больше трафика, но повышает потребление памяти.

#### Жизненный цикл запроса в Event Loop

Процесс обработки события в Nginx можно разбить на четыре шага:
1.  **Прием запроса (Incoming Request):** клиент инициирует HTTP/HTTPS соединение.
2.  **Регистрация события (Event Loop):** "Официант" (воркер) фиксирует запрос в очереди и переходит к проверке других событий, не дожидаясь завершения обработки текущего.
3.  **Обработка события (Processing Event):** "Шеф-повар" выполняет задачу. Если требуется ожидание данных (например, от базы), воркер не простаивает, а переключается на другие задачи (повар может резать овощи, пока закипает вода).
4.  **Отправка ответа (Response Sent):** как только данные готовы, воркер возвращает ответ клиенту.

Такая модель позволяет Nginx обрабатывать огромные объемы трафика с минимальными задержками.

#### Основные сценарии использования и их аналогии

- **Обратный прокси (Reverse Proxy):** Действует как посредник между клиентом и бэкенд-серверами. Скрывает внутреннюю структуру сети, обеспечивает безопасность, балансировку и SSL-терминацию.
- **Прямой прокси (Forward Proxy):** Контролирует исходящий трафик. Аналогия — **библиотека**, которая фильтрует доступ к определенным ресурсам для своих посетителей.
- **Кэширующий сервер (Caching):** Позволяет избежать повторного выполнения тяжелых задач. Аналогия — **кофейня**, которая готовит кофе большими порциями (batch brew). Когда приходит клиент, ему просто наливают готовую порцию из термоса, вместо того чтобы варить каждую чашку с нуля. Это экономит время и ресурсы бэкенда.
- **Балансировщик нагрузки:** Распределяет заказы между несколькими официантами или поварами, чтобы никто не был перегружен.

#### Асинхронная модель на базе событий

Рабочие процессы (Worker processes) не ждут завершения операций ввода-вывода (диск или сеть), что делает Nginx неблокирующим. Вместо этого он использует системные механизмы мультиплексирования:
- **epoll (Linux):** эффективная обработка миллионов дескрипторов.
- **kqueue (BSD/macOS):** аналог epoll.

Механизм **sendfile (Zero-Copy)** позволяет передавать данные из файлового кэша ядра напрямую в сетевой сокет, минуя копирование в пространство пользователя (User Space).

### Иерархия контекстов конфигурации

Конфигурация Nginx строится на вложенных контекстах, определяющих область видимости директив:

- **Main (Global):** верхний уровень (пользователь, количество воркеров).
- **Events:** настройки сетевых соединений (worker_connections).
- **HTTP:** глобальные настройки веб-сервера.
- **Server:** параметры конкретного виртуального хоста.
- **Location:** правила обработки конкретных URI внутри сервера.
- **Upstream:** описание групп бэкенд-серверов для балансировки.
- **Stream:** настройки для L4 (TCP/UDP) трафика (на том же уровне, что и HTTP).

### Управление процессами (Сигналы)

Nginx управляется через сигналы, посылаемые мастер-процессу:

- **HUP (Reload):** перечитывание конфигурации. Мастер запускает новых воркеров, старые плавно завершают обработку текущих соединений.
- **QUIT (Graceful Stop):** плавное завершение работы.
- **TERM/INT:** немедленная остановка.
- **USR1:** переоткрытие лог-файлов (используется для ротации).
- **USR2:** обновление бинарного файла сервера на лету без остановки соединений.
- **WINCH:** после USR2 — постепенное завершение старых воркеров (завершает грациозную замену бинарника).

#### Zero-downtime обновление бинарника (USR2/WINCH)

Стандартный `systemctl restart` рвёт активные соединения. Для бесшовного обновления исполняемого файла Nginx используется сигнальный сценарий:

```bash
# 1. Подготовить новый бинарник (не перезапуская nginx)
cp -a /usr/sbin/nginx /usr/sbin/nginx.old
install -m 755 /usr/local/src/nginx-1.27.3/objs/nginx /usr/sbin/nginx

# 2. Запустить новый master рядом (старый продолжает работать)
kill -USR2 $(cat /run/nginx.pid)
# Появится nginx.pid.oldbin (старый PID) и новый master

# 3. Постепенно перевести трафик на новые воркеры
kill -WINCH $(cat /run/nginx.pid.oldbin)
# Старые воркеры завершаются после обработки текущих запросов

# 4. Проверить новый процесс и зафиксировать состояние
nginx -V && kill -QUIT $(cat /run/nginx.pid.oldbin)
# Старый master полностью останавливается
```

Откат в случае проблем с новым бинарником:

```bash
kill -HUP $(cat /run/nginx.pid.oldbin)   # перезапустить старые воркеры
kill -TERM $(cat /run/nginx.pid)         # остановить новый master
```

Механика идентична в Angie — детальный разбор сигналов и примеры см. в [обзоре Angie](../../Angie/angie_overview.md).

#### Graceful shutdown и долгие соединения

При плавном завершении воркеры могут «висеть» на долгоживущих соединениях (WebSocket, gRPC, HTTP/3). Для ограничения времени дожития используется `worker_shutdown_timeout` (рекомендуется `10s`–`30s` в прод). Подробнее — в [тюнинге производительности](../Performance/nginx_performance_tuning.md).

## Практические сценарии

### Использование переменных

Nginx предоставляет богатый набор встроенных переменных для гибкой логики:

- `$host`: имя хоста из запроса.
- `$uri`: текущий нормализованный URI.
- `$remote_addr`: IP-адрес клиента.
- `$proxy_add_x_forwarded_for`: цепочка IP-адресов при проксировании.
- `$request_method`: метод HTTP (GET, POST и т.д.).

Переменные можно объявлять через `set`, а «словари» сопоставлений — строить на `map` (например, региональная маршрутизация, белые списки, канареечные веса). Полный разбор `set`/`map`/`geo` — в **[переменных, map и гео в Angie](../../Angie/angie_variables.md)** (директивы идентичны для Nginx OSS).

### Логирование

Nginx поддерживает два типа логов:
1.  **Error Log:** ошибки сервера и конфигурации. Уровни: `debug`, `info`, `notice`, `warn`, `error`, `crit`, `alert`, `emerg`.
2.  **Access Log:** запись каждого обработанного запроса. Настраивается через `log_format` для интеграции с SIEM или системами аналитики (например, в формате JSON).

Разбор access-логов (GoAccess, CLI-анализ, request_id, JSON) — в [анализе access-логов](../Operations/nginx_log_analysis.md).

### Высокая доступность (High Availability)

Один экземпляр Nginx — точка отказа. Классический пассивный HA-сценарий в bare-metal/VM: два (или более) узла Nginx объединяются плавающим IP (**VIP**) через **keepalived** (VRRP). Обычный Nginx не умеет синхронизировать `limit_req_zone`/`limit_conn_zone` между узлами — для «честных» лимитов в кластере используйте Angie (`sync`) или внешний распределённый кэш.

```text
Client → VIP 10.0.0.10 (active: nginx-1, backup: nginx-2)
                 │ VRRP (vrrp_instance nginx_ha)
                 ├─ nginx-1  (MASTER, priority 150)
                 └─ nginx-2  (BACKUP, priority 100) → принимает при сбое nginx-1
```

- **keepalived** управляет VIP: при падении мастера/сервиса BACKUP становится MASTER и захватывает VIP (фейловер за секунды).
- **Проверка здоровья:** скрипт проверки (`/usr/bin/curl -sf http://127.0.0.1/healthz`) в `vrrp_script`, при фейле — `weight`-понижение приоритета.
- Альтернативы на L7: DNS round-robin (деградация), актив-актив кластеры, LTE-решения облачных LB.

Пошаговая настройка nginx+keepalived — в [HA-конфигурации Angie с keepalived](../../Angie/angie_ha_with_keepalived.md) (directives идентичны для Nginx OSS) и [обзоре keepalived](../../../Networking/ServicesAndTools/keepalived_overview.md). Общая модель HA/DR — в [Concepts HA](../../../Concepts/High_Availability/ha_overview.md).

### Современные технологии (2026)

- **HTTP/3 (QUIC):** Nginx полностью поддерживает транспорт на базе UDP, обеспечивая более быстрое установление соединений и устойчивость к потере пакетов.
- **eBPF (Extended Berkeley Packet Filter):** интеграция с ядром для ускорения обработки UDP (QUIC) и продвинутой фильтрации трафика на ранних этапах.
- **njs (Nginx JavaScript):** возможность писать сложную логику обработки запросов на подмножестве JavaScript без потери производительности.
