# Балансировка нагрузки L7 (HTTP/HTTPS) с помощью Nginx

## 1. Определения и базовые концепции

**Балансировка нагрузки** — это способ распределения запросов к приложению (сетевого трафика) между несколькими бэкенд-серверами. Это ключевой компонент для построения масштабируемых и отказоустойчивых систем.

**Роли Nginx:**
-   Веб-сервер;
-   **Реверс-прокси и балансировщик нагрузки;**
-   Почтовый прокси-сервер;
-   Кэширующий прокси.

**Upstream** — это именованная группа бэкенд-серверов в конфигурации Nginx, между которыми распределяется нагрузка.

---

## 2. Концепция: Stateless-архитектура для масштабирования

Простая балансировка нагрузки — это только часть решения. Чтобы система была действительно масштабируемой и отказоустойчивой, бэкенд-серверы должны быть спроектированы как **stateless** (не хранящие состояние).

Это означает, что любой запрос от одного и того же клиента может быть обработан любым из бэкенд-серверов без потери данных или сессии. Состояние приложения (сессии, кэш, загруженные файлы) должно быть вынесено на отдельные, общие для всех бэкендов сервисы.

### Ключевые компоненты stateless-архитектуры:

1.  **Балансировщик нагрузки (Nginx):**
    *   Принимает трафик.
    *   **Терминирует TLS (SSL):** Расшифровка HTTPS-трафика происходит здесь, а к бэкендам запросы идут по внутреннему, незашифрованному HTTP, что снижает с них нагрузку.
    *   **Выполняет Health Checks:** Периодически опрашивает бэкенды, чтобы убедиться, что они работают. Если бэкенд не отвечает, балансировщик временно исключает его из ротации.
    *   Проксирует запросы к работающим бэкендам.

2.  **Бэкенд-серверы (веб-приложение):**
    *   Не хранят никаких данных локально (ни сессий, ни загруженных пользователем файлов).
    *   Все экземпляры содержат идентичный код.
    *   Могут быть легко добавлены или удалены для горизонтального масштабирования.

3.  **База данных (например, PostgreSQL, MySQL):**
    *   Хранит все основные данные приложения. Все бэкенды подключаются к одной и той же базе данных (или кластеру баз данных).

4.  **Кэш и сессии (например, Redis, Memcached):**
    *   Хранит временные данные: кэш страниц, результаты тяжелых запросов и, что очень важно, **пользовательские сессии**. Когда пользователь логинится на одном бэкенде, информация о его сессии сохраняется в Redis, и любой другой бэкенд может ее оттуда прочитать.

5.  **Файловое хранилище (например, S3, MinIO, GlusterFS):**
    *   Все файлы, загружаемые пользователями (аватары, документы), должны сохраняться не на локальный диск бэкенд-сервера, а в общее сетевое хранилище. Это гарантирует, что файлы будут доступны независимо от того, какой бэкенд обработает следующий запрос.

## 3. Практические сценарии и конфигурация

### 3.1. Определение Upstream-группы

Ключевой элемент балансировки — директива `upstream`, которая объявляет именованную группу бэкенд-серверов.

```nginx
upstream apache_backend {
    # Зона разделяемой памяти для хранения состояния группы и динамической конфигурации.
    # Необходима для работы `least_conn`, `least_time`, `health_check`, `sticky` и др.
    zone backend_zone 64k;

    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
}
```

Здесь `apache_backend` — это произвольное имя для группы серверов, которое будет использоваться в директиве `proxy_pass`.

### 3.2. Настройка проксирования (`proxy_pass`)

Теперь отредактируйте конфигурацию вашего сайта, чтобы он перенаправлял запросы на созданную upstream-группу.

```nginx
location / {
    # Перенаправляем запрос на группу серверов
    proxy_pass http://apache_backend;

    # Рекомендуемые заголовки для передачи информации о клиенте бэкенду
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```
Директива `proxy_pass` указывает Nginx установить новое HTTP-соединение с одним из серверов из группы `apache_backend` и перенаправить ему исходный запрос.

## 4. Продвинутые детали

### 4.1. Алгоритмы балансировки

Nginx поддерживает несколько алгоритмов распределения запросов, которые можно указать в блоке `upstream`.

1.  **Round Robin (по умолчанию):** Запросы распределяются по серверам поочередно. Это самый простой метод.
    *   **Weighted Round Robin:** Запросы распределяются по серверам пропорционально их весу (`weight`). Сервер с большим весом получает больше запросов.

2.  **Least Connections (`least_conn`):** Новый запрос отправляется на сервер с наименьшим количеством активных соединений. Этот метод эффективен, когда сессии могут быть длительными, а запросы занимают разное время на обработку.
    *   **Возможная аномалия:** Этот алгоритм может работать некорректно, если один из бэкендов неисправен, но очень быстро отдает пустые ответы с кодом 200 OK. Такой сервер будет иметь минимальное количество активных соединений и "притянет" на себя большую часть трафика, в то время как пользователи будут видеть неработающий сервис.

3.  **IP Hash (`ip_hash`):** Запросы от одного и того же клиента (на основе его IP-адреса) всегда отправляются на один и тот же сервер, если он доступен. Это необходимо для "липких сессий" (sticky sessions), когда приложение хранит состояние сессии локально.
    ```nginx
    upstream backend {
        ip_hash;
        server 127.0.0.1:9000;
        server 127.0.0.1:9001;
    }
    ```
    *   **Недостатки:**
        *   **Неравномерное распределение:** Если большое количество клиентов приходит из одной подсети (например, за одним корпоративным [NAT](../../Networking/Concepts/nat.md)), они все могут быть направлены на один и тот же бэкенд, вызывая его перегрузку.
        *   **Проблема с IPv4:** Алгоритм использует только первые три октета IPv4-адреса для расчета хеша, что усугубляет проблему неравномерного распределения.
        *   Для более гибкого и предсказуемого "прилипания" рекомендуется использовать алгоритм `hash`.

4.  **Hash (`hash`):** Распределяет запросы на основе хеша указанной переменной (например, `$request_uri`, `$remote_addr`). Это обеспечивает "прилипание" клиента к одному и тому же бэкенду для одного и того же значения хеша. Использование параметра `consistent` минимизирует перераспределение клиентов между серверами в случае изменения состава группы (добавление или удаление серверов).
    ```nginx
    upstream backend {
        hash $request_uri consistent; # consistent для минимизации перераспределения
        server 127.0.0.1:9000;
        server 127.0.0.1:9001;
    }
    ```

5.  **Random (`random`):** Распределяет запросы случайным образом. Полезен, когда есть несколько балансировщиков перед одной группой бэкендов, и они не обмениваются информацией о нагрузке. В таком сценарии случайное распределение с каждого балансировщика обеспечивает более равномерную нагрузку на весь пул бэкендов.
    *   **`random two least_conn`:** Комбинация методов: Nginx выбирает два случайных сервера и направляет запрос на тот из них, у которого меньше активных соединений. Это один из самых эффективных методов с точки зрения распределения.
    ```nginx
    upstream backend {
        random two least_conn;
        server 127.0.0.1:9000;
        server 127.0.0.1:9001;
        server 127.0.0.1:9002;
    }
    ```

### 4.2. Параметры серверов в `upstream`

-   `weight=N`: **Вес сервера.** Чем выше значение, тем большую долю запросов будет получать сервер. По умолчанию `1`. Позволяет направлять больше трафика на более мощные машины.
-   `max_fails=N`: **Максимальное количество неудач.** Количество неудачных попыток соединения, после которого сервер считается временно недоступным. По умолчанию `1`.
-   `fail_timeout=T`: **Тайм-аут.** Время (в секундах), на которое сервер будет исключен из балансировки после достижения `max_fails`. Также это время, в течение которого учитываются `max_fails`. По умолчанию `10s`.
-   `backup`: **Резервный сервер.** Помечает сервер как резервный. Он будет использоваться только в том случае, если все остальные (основные) серверы в группе недоступны.
-   `down`: **Отключен.** Сервер полностью исключен из балансировки. Полезно для вывода на длительное обслуживание.
-   `slow_start=T`: (**Angie / Nginx Plus**) Плавное наращивание нагрузки на сервер, который был восстановлен после сбоя или добавлен в группу. Его вес постепенно увеличивается от 0 до номинального значения в течение заданного времени `T`. Это позволяет серверу "прогреть" кэши и избежать перегрузки.
-   `drain`: (**Angie / Nginx Plus R22**) Плавный вывод сервера из эксплуатации. Nginx перестает направлять на него новые запросы (кроме "прилипших" сессий), позволяя ему доработать текущие и безопасно отключиться.

```nginx
upstream backend {
    server 10.0.0.1:80 weight=3;
    server 10.0.0.2:80 max_fails=2 fail_timeout=15s slow_start=30s;
    server 10.0.0.3:80 backup;
    server 10.0.0.4:80 down;
    server 10.0.0.5:80 drain;
}
```

### 4.3. Sticky Sessions (Прилипание сессий)

В некоторых случаях, особенно при использовании stateful-приложений, необходимо, чтобы запросы от одного клиента всегда попадали на один и тот же бэкенд-сервер. Для этой цели, помимо метода `ip_hash`, можно использовать более гибкие механизмы "прилипания".

> **Примечание:** В Nginx Open Source описанная ниже функциональность (`sticky`) доступна через сторонний модуль [ngx_http_upstream_sticky_module](https://bitbucket.org/nginx-goodies/nginx-sticky-module-ng/src/master/). В форке Nginx [Angie](../Angie/angie_overview.md) и в коммерческой версии Nginx Plus этот функционал является встроенным.

#### Режим `cookie`

Nginx устанавливает специальную куку в браузере клиента, которая содержит информацию о выбранном бэкенде.

```nginx
upstream backend {
    sticky cookie srv_id expires=1h path=/; # srv_id - имя куки, expires - время жизни
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
}
```

-   `sticky cookie <name> [expires=time] [domain=domain] [path=path] [secure] [httponly]`: Включает прилипание на основе куки.
-   `sticky secret <string>`: Добавляет "соль" к значению идентификатора сервера перед хешированием. Это защищает от атак, направленных на угадывание хеша и принудительную привязку к определенному бэкенду.
-   `sticky strict`: Если привязанный сервер недоступен, Nginx немедленно вернет ошибку (например, 502 Bad Gateway). Если эта директива отключена, запрос будет прозрачно для клиента перенаправлен на другой доступный сервер в группе `upstream`.

#### Режим `route`

Привязка происходит на основе значения переменной, которая передается в запросе.

```nginx
upstream backend {
    sticky route $arg_route; # Привязка на основе значения параметра 'route' из URL
    server 127.0.0.1:9000 route=green;
    server 127.0.0.1:9001 route=blue;
}
```

-   `sticky route <variable>`: Указывает переменную, по которой будет определяться маршрут. Например, `$arg_route` для параметра `route` в URL (`?route=green`).
-   `server ... route=<string>`: Определяет строковый идентификатор маршрута для конкретного сервера.

**Пример использования и риски:**
Если клиент сделает запрос `http://example.com/?route=green`, он будет направлен на сервер `127.0.0.1:9000`. Однако этот метод может быть небезопасен, так как позволяет клиенту напрямую выбирать бэкенд, что может быть использовано для DoS-атаки на конкретный сервер. Для защиты от подобных атак следует использовать `sticky secret`.

### 4.4. Динамическое разрешение DNS в Upstream

По умолчанию Nginx разрешает [доменные имена](../../Networking/Protocols/dns.md) серверов в блоке `upstream` только один раз при загрузке конфигурации. Если IP-адрес бэкенда изменится (например, в облачной среде или Docker), Nginx продолжит отправлять трафик на старый адрес.

Для динамического обновления DNS-записей используется директива `resolver`. Эта функция, ранее доступная только в Nginx Plus, со временем была перенесена в Open Source версии Angie, а затем и в Nginx.

```nginx
http {
    # Указываем DNS-сервер (например, локальный кэширующий DNS или DNS провайдера)
    resolver 1.1.1.1 valid=10s;
    
    upstream backend {
        # Nginx будет периодически перечитывать DNS-запись для этого хоста
        server backend.example.com resolve;
    }
}
```

-   `resolver <address> [valid=time]`: Определяет DNS-сервер для разрешения имен и время кэширования записей.
-   `server <hostname> resolve`: Указывает Nginx использовать `resolver` для периодического обновления IP-адреса. **Важно:** директива `resolver` в контексте `http` обязательна при использовании `resolve`, иначе Nginx выдаст ошибку конфигурации.

Эта возможность особенно важна при работе с динамическими окружениями, такими как Kubernetes, где IP-адреса подов (бэкендов) могут часто меняться.

## 5. Настройка производительности и надежности для Upstreams

### 5.1. Keep-alive соединения

По умолчанию Nginx открывает новое TCP-соединение для каждого запроса к бэкенду. Это неэффективно при высоких нагрузках. Включение keep-alive соединений позволяет Nginx поддерживать постоянный пул открытых соединений к бэкендам.

```nginx
upstream backend_servers {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;

    # Указываем, что нужно держать до 32 keep-alive соединений на каждый worker процесс Nginx
    keepalive 32;
}

server {
    location / {
        proxy_pass http://backend_servers;

        # Для работы keep-alive требуется HTTP/1.1 и сброс заголовка Connection
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        # ... другие proxy_set_header
    }
}
```
-   **Преимущества:** Снижает задержки (latency) и нагрузку на CPU как на сервере Nginx, так и на бэкендах, так как не тратится время на TCP/TLS handshake для каждого запроса.

### 5.2. Таймауты

Правильная настройка таймаутов критически важна для предотвращения "зависания" соединений, если бэкенд отвечает медленно или не отвечает вовсе.

```nginx
location / {
    proxy_pass http://backend_servers;

    # Таймаут на установку соединения с бэкендом
    proxy_connect_timeout 5s;

    # Таймаут на передачу запроса бэкенду
    proxy_send_timeout 10s;

    # Таймаут на чтение ответа от бэкенда
    proxy_read_timeout 15s;
}
```
-   `proxy_connect_timeout`: Если Nginx не сможет установить соединение с бэкендом за это время, попытка будет считаться неудачной.
-   `proxy_read_timeout`: Если бэкенд начал отправлять ответ, но потом "замолчал" на это время, Nginx разорвет соединение.

### 5.3. Буферизация

Nginx по умолчанию буферизует ответы от бэкенд-серверов. Это означает, что он сначала полностью считывает ответ от бэкенда во временный буфер, и только потом начинает отправлять его клиенту.

```nginx
location / {
    proxy_pass http://backend_servers;

    # Количество и размер буферов для ответа
    proxy_buffers 8 16k;

    # Размер буфера, в который считывается первая часть ответа (обычно заголовки)
    proxy_buffer_size 8k;
}
```
-   **Плюсы буферизации:** Освобождает бэкенд-сервер быстрее. Как только бэкенд отдал ответ Nginx, он может закрыть соединение и обрабатывать другие запросы. Nginx сам позаботится о медленной передаче данных медленному клиенту.
-   **Отключение буферизации (`proxy_buffering off;`):** Может быть полезно для long-polling запросов или потоковой передачи данных (Server-Sent Events), где важно минимизировать задержку между бэкендом и клиентом. Однако в большинстве случаев буферизацию рекомендуется оставлять включенной.

## 6. Проверки состояния (Health Checks)

### 6.1. Пассивная проверка

Эта проверка встроена в Nginx и работает по умолчанию. Если при попытке отправить запрос на бэкенд Nginx не может установить соединение (получает ошибку `Connection refused` или `Connection timed out`), он считает эту попытку неудачной.

-   После достижения `max_fails` (по умолчанию 1) неудачных попыток в течение `fail_timeout` (по умолчанию 10с), Nginx временно перестает отправлять запросы на этот сервер.
-   **Ограничение:** Эта проверка реагирует только на полную недоступность сервера на сетевом уровне. Она не спасет, если сервер "завис", отвечает медленно или возвращает ошибки `5xx`. Типы ошибок, которые учитываются, определяются директивой `proxy_next_upstream`.

### 6.2. Активная проверка

Для полноценной проверки состояния приложения (например, чтобы убедиться, что оно отвечает кодом `200 OK`, а не `503 Service Unavailable`) требуются расширенные возможности.

-   **Nginx Plus / Angie Pro:** В платных версиях есть встроенный механизм активных health checks (`health_check`).
-   **Nginx Open Source:** Для бесплатной версии Nginx можно использовать сторонний модуль, например, [nginx_upstream_check_module](https://github.com/yaoweibin/nginx_upstream_check_module).

Этот модуль позволяет настроить Nginx так, чтобы он периодически отправлял на бэкенды специальные запросы (например, `GET /status`) и анализировал ответ. Если ответ не соответствует ожиданиям (например, код ответа не `200`), сервер помечается как нерабочий и исключается из балансировки до тех пор, пока снова не начнет проходить проверку.

**Пример конфигурации с `check` модулем:**

```nginx
upstream backend {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;

    # Директива, включающая проверку
    # Проверять каждые 3с, 2 удачные попытки для возвращения в строй, 3 неудачные для исключения
    check interval=3000 rise=2 fall=3 timeout=1000 type=http;
    # URL для проверки
    check_http_send "GET /status HTTP/1.0\r\n\r\n";
    # Ожидаемый код ответа
    check_http_expect_alive http_2xx;
}
```

## 7. Мониторинг Upstream

Состояние `upstream` серверов можно отслеживать через API-интерфейсы (в Nginx Plus / Angie) или с помощью сторонних инструментов мониторинга, анализируя [логирование](../Nginx/nginx_logging.md) и метрики, которые отдает, например, [nginx-prometheus-exporter](../Prometheus/exporters.md#nginx-prometheus-exporter).

## 8. Проверка

Откройте браузер и перейдите по адресу вашего сервера (`http://<your_server_ip>`) или выполните команду в терминале:

```bash
curl http://127.0.0.1
```

При каждом обновлении страницы или повторном вызове `curl` вы должны видеть ответы от разных экземпляров Apache ("Response from Apache on port 8080", "Response from Apache on port 8081" и т.д.), так как Nginx по умолчанию использует алгоритм балансировки Round Robin.

## 9. Важные замечания

*   **Расширения `.conf`:** Для Apache крайне важно, чтобы файлы конфигурации сайтов в `sites-available` имели расширение `.conf`. В противном случае утилиты `a2ensite` и сам Apache могут их игнорировать. Для Nginx это не является строгим требованием, но является хорошей практикой.
*   **Директории Nginx:** В современных версиях Nginx рекомендуется создавать отдельные файлы для конфигураций в `/etc/nginx/conf.d/` (для глобальных настроек, таких как upstream) и `/etc/nginx/sites-enabled/` (для настроек конкретных сайтов/серверов).

## 10. Сравнение подходов к конфигурации: Apache vs. Nginx

### Apache: Децентрализованная конфигурация через `.htaccess`

Apache позволяет использовать файлы `.htaccess`, размещенные непосредственно в директориях сайтов.

*   **Принцип работы:** При каждом запросе Apache проверяет наличие `.htaccess` в текущей директории и во всех родительских директориях. Найденные директивы применяются "на лету".
*   **Преимущество:** Высокая гибкость. Владелец сайта может изменять его конфигурацию (например, правила `mod_rewrite`), не имея доступа к главному конфигурационному файлу сервера. Это идеально для shared-hosting.
*   **Изоляция ошибок:** Ошибка в `.htaccess` одного сайта вызовет `500 Internal Server Error` **только для этого сайта**. Остальные сайты на сервере продолжат работать без изменений.
*   **Недостаток:** Существенное снижение производительности из-за множественных обращений к файловой системе при каждом запросе.

### Nginx: Централизованная конфигурация

Nginx не поддерживает аналогов `.htaccess`. Вся конфигурация читается из центральных файлов (например, из `/etc/nginx/sites-enabled/`) один раз при старте или перезагрузке.

*   **Принцип работы:** Вся конфигурация загружается в память. При поступлении запроса Nginx применяет уже скомпилированные правила, не обращаясь к файловой системе.
*   **Преимущество:** Максимальная производительность и эффективность, особенно при отдаче статического контента.
*   **Безопасность конфигурации:** Перед применением новой конфигурации (`systemctl reload nginx`) необходимо выполнить проверку синтаксиса (`nginx -t`). Если в конфигурации любого из сайтов есть ошибка, Nginx не применит изменения, что предотвращает остановку всего веб-сервера.
*   **Недостаток:** Меньшая гибкость для конечного пользователя. Любое изменение требует доступа к серверу и перезагрузки конфигурации администратором.

## 11. Сравнение с HAProxy

Хотя Nginx является мощным инструментом для балансировки нагрузки, в некоторых сценариях [[../Haproxy/haproxy_overview.md|HAProxy]] может быть предпочтительнее, особенно когда требуется более тонкая настройка и расширенные возможности.

*   **Гибкость алгоритмов:** Бесплатная версия HAProxy предлагает значительно более широкий и гибкий набор алгоритмов балансировки по сравнению с бесплатной версией Nginx. HAProxy позволяет более точно управлять распределением трафика, учитывая различные параметры запросов и состояние бэкендов, включая привязку сессии к конкретному серверу на основе IP-адреса источника.
*   **Специализированные задачи:** HAProxy лучше справляется с некоторыми узкоспециализированными задачами балансировки, которые Nginx не умеет делать или делает с большими сложностями. Например, привязка сессии к конкретному серверу на основе IP-адреса источника (без сложных конфигураций) или более продвинутые проверки состояния (health checks) бэкендов.
*   **Производительность для балансировки:** HAProxy изначально разработан как высокопроизводительный балансировщик нагрузки и прокси, что делает его крайне эффективным для этой задачи с низким потреблением ресурсов. Nginx, будучи универсальным веб-сервером, также хорошо справляется, но HAProxy может быть более оптимизирован для чистой балансировки.
*   **Nginx Plus:** В то же время, платная версия **Nginx Plus** предлагает уникальные функции, которых нет в HAProxy, например, балансировку на основе скорости ответа сервера, динамическую реконфигурацию бэкендов и расширенный мониторинг. Это позволяет Nginx Plus выбирать самый быстрый отвечающий сервер, а не только наименее загруженный.

## Рекомендации по использованию

*   **Nginx:** Идеально подходит, если вы единственный администратор сервера и вам нужен универсальный инструмент (веб-сервер, реверс-прокси, балансировщик).
*   **Связка Apache + Nginx:** Рекомендуется для сред веб-хостинга, где конечным пользователям нужна гибкость `.htaccess` (которую предоставляет Apache), а Nginx используется как фронтенд для эффективной отдачи статики и проксирования.
