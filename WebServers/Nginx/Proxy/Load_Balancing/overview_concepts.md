# Балансировка нагрузки L7 (HTTP/HTTPS) с помощью Nginx: Обзор и Концепции

## Определения

* **Балансировка нагрузки** — это способ распределения запросов к приложению (сетевого трафика) между несколькими бэкенд-серверами. Это ключевой компонент для построения масштабируемых и отказоустойчивых систем.

* **Роли Nginx**:
  * Веб-сервер;
  * **Реверс-прокси и балансировщик нагрузки;**
  * Почтовый прокси-сервер;
  * Кэширующий прокси.

* **Upstream** — это именованная группа бэкенд-серверов в конфигурации Nginx, между которыми распределяется нагрузка.

## Основные концепции

### Stateless-архитектура для масштабирования

Простая балансировка нагрузки — это только часть решения. Чтобы система была действительно масштабируемой и отказоустойчивой, бэкенд-серверы должны быть спроектированы как **stateless** (не хранящие состояние).

Это означает, что любой запрос от одного и того же клиента может быть обработан любым из бэкенд-серверов без потери данных или сессии. Состояние приложения (сессии, кэш, загруженные файлы) должно быть вынесено на отдельные, общие для всех бэкендов сервисы.

#### Ключевые компоненты stateless-архитектуры

1. **Балансировщик нагрузки (Nginx):**
    * Принимает трафик.
    * **Терминирует TLS (SSL):** Расшифровка HTTPS-трафика происходит здесь, а к бэкендам запросы идут по внутреннему, незашифрованному HTTP, что снижает с них нагрузку.
    * **Выполняет Health Checks:** Периодически опрашивает бэкенды, чтобы убедиться, что они работают. Если бэкенд не отвечает, балансировщик временно исключает его из ротации.
    * Проксирует запросы к работающим бэкендам.

2. **Бэкенд-серверы (веб-приложение):**
    * Не хранят никаких данных локально (ни сессий, ни загруженных пользователем файлов).
    * Все экземпляры содержат идентичный код.
    * Могут быть легко добавлены или удалены для горизонтального масштабирования.

3. **База данных (например, PostgreSQL, MySQL):**
    * Хранит все основные данные приложения. Все бэкенды подключаются к одной и той же базе данных (или кластеру баз данных).

4. **Кэш и сессии (например, Redis, Memcached):**
    * Хранит временные данные: кэш страниц, результаты тяжелых запросов и, что очень важно, **пользовательские сессии**. Когда пользователь логинится на одном бэкенде, информация о его сессии сохраняется в Redis, и любой другой бэкенд может ее оттуда прочитать.

5. **Файловое хранилище (например, S3, MinIO, GlusterFS):**
    * Все файлы, загружаемые пользователями (аватары, документы), должны сохраняться не на локальный диск бэкенд-сервера, а в общее сетевое хранилище. Это гарантирует, что файлы будут доступны независимо от того, какой бэкенд обработает следующий запрос.
