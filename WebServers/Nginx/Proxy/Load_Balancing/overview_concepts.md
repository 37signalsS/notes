# Балансировка нагрузки L7 (HTTP/HTTPS) в Nginx: Обзор и концепции

## Определения

**Балансировка нагрузки (Load Balancing)** — способ распределения входящего сетевого трафика между группой бэкенд-серверов. Является ключевым компонентом для построения масштабируемых и отказоустойчивых систем. Общие принципы описаны в разделе [Кластеризация и балансировка для HA](../../../Concepts/High_Availability/ha_clustering_and_load_balancing.md).

**Upstream** — именованная группа бэкенд-серверов в конфигурации Nginx, между которыми распределяется нагрузка. Подробное описание алгоритмов и параметров приведено в файле [Алгоритмы балансировки](./algorithms.md).

**Реверс-прокси (Reverse Proxy)** — роль Nginx, в которой он терминирует клиентские соединения и перенаправляет запросы на бэкенды. Подробнее о ролях Nginx см. в [Обзоре Nginx](../Core/nginx_overview.md).

## Основные концепции

### Событийно-ориентированная архитектура L7

Nginx использует асинхронную, событийно-ориентированную модель (Event-driven), что позволяет одному рабочему процессу (worker) эффективно обрабатывать тысячи одновременных L7-соединений. В отличие от традиционных серверов, Nginx не создает отдельный поток (thread) или процесс на каждый запрос, что минимизирует накладные расходы на память и переключение контекста. Это критично при балансировке, где Nginx должен одновременно поддерживать соединения с клиентами и с группой бэкендов.

### Безсостоятельная (Stateless) архитектура

Для эффективного масштабирования бэкенд-серверы должны быть **stateless** (не хранящие состояние сессии локально). Это позволяет любому экземпляру приложения обработать запрос от любого клиента. Подробный разбор: [Stateful vs Stateless](../../../Concepts/stateful_vs_stateless.md).

В этой архитектуре Nginx выполняет задачи:
1. **Терминация TLS (SSL)** — расшифровка трафика, снимающая вычислительную нагрузку с бэкендов. Nginx поддерживает современные протоколы TLS 1.3, а также аппаратное ускорение шифрования.
2. **Проверки состояния (Health Checks)** — пассивные (OSS) или активные (Angie/Plus) проверки работоспособности. Подробнее: [Health Checks и мониторинг](./health_checks_and_monitoring.md).
3. **Персистентность сессий (Sticky Sessions)** — при необходимости сохранения привязки клиента (для legacy stateful систем) используются [Sticky Sessions](./sticky_sessions.md).

### Оптимизация соединений (Keepalive)

Без настройки `keepalive` в блоке `upstream` Nginx использует HTTP/1.0 для связи с бэкендами, закрывая соединение после каждого запроса. Это приводит к:
- Высокому потреблению CPU на постоянные TCP/TLS рукопожатия.
- Исчерпанию портов и накоплению сокетов в состоянии `TIME_WAIT`.

**Решение:** Директива `keepalive <N>` кэширует открытые соединения с бэкендами. Важно также настроить `keepalive_requests` (максимальное число запросов в одном соединении) и `keepalive_timeout` для предотвращения утечек и обеспечения свежести соединений.

### Управление потоком данных (Buffering)

Буферизация (`proxy_buffering`) — критический механизм защиты бэкендов от "медленных" клиентов.
- **Принцип:** Nginx считывает ответ от бэкенда максимально быстро в свои буферы (`proxy_buffer_size`, `proxy_buffers`) и немедленно освобождает воркер бэкенда.
- **Медленные клиенты:** Если клиент читает данные медленно, Nginx удерживает их в своей памяти (или на диске через `proxy_max_temp_file_size`), позволяя бэкенду заняться следующим запросом.
- **gRPC и WebSocket:** Для этих протоколов буферизация часто отключается (`proxy_buffering off`), так как они требуют потоковой передачи в реальном времени.

### Поддержка современных протоколов (HTTP/2, HTTP/3, gRPC)

Балансировка современных нагрузок требует понимания специфики протоколов:
- **HTTP/2 и HTTP/3:** Nginx может терминировать эти протоколы на стороне клиента и транслировать их в высокопроизводительный HTTP/1.1 (с keepalive) на сторону бэкендов.
- **gRPC:** Балансировка на уровне L7 через `grpc_pass` позволяет Nginx понимать структуру gRPC-запросов и эффективно распределять их даже внутри долгоживущих HTTP/2 соединений, что невозможно на уровне L4.

### Динамический Upstream и разрешение DNS

В Nginx Open Source имена серверов в `upstream` разрешаются в IP-адреса только при старте.
- **Проблема:** В облачных средах и Kubernetes IP-адреса подов постоянно меняются.
- **Решение в Angie:** Нативная поддержка `resolver` внутри блока `upstream` позволяет Angie обновлять IP-адреса согласно TTL из DNS без перезагрузки конфигурации.

## Сравнение уровней балансировки

| Уровень OSI | Название | Что анализирует Nginx | Применение |
| :--- | :--- | :--- | :--- |
| **L4** | Транспортный | IP, TCP/UDP порт | БД (MySQL, PG), DNS, Почта. [L4-проксирование](../nginx_l4_proxying.md) |
| **L7** | Прикладной | URI, Headers, Cookies, JSON, gRPC | Веб-приложения, API, микросервисы. |

## Практические сценарии

### Типовая схема L7-балансировки

1. **Балансировщик (Nginx/Angie)**: Терминация TLS 1.3, фильтрация заголовков, балансировка, сжатие (Gzip/Brotli).
2. **Пул приложений**: Stateless-серверы за `proxy_pass` или `grpc_pass`.
3. **Хранилище сессий**: Redis (внешнее состояние) для обеспечения полной независимости бэкендов.

Детальные примеры конфигурации: [Практическая конфигурация балансировки](./practical_configuration.md).

## Сравнение возможностей (Nginx vs Angie)

| :--- | :--- | :--- |
| Балансировка HTTP/HTTPS/gRPC | Да | Да |
| Активные Health Checks | Нет (нужен Plus) | **Да** |
| Динамический DNS в Upstream | Нет (нужен Plus) | **Да** |
| Мониторинг (JSON API) | Нет (нужен Plus) | **Да** |
| Sticky Sessions (Cookie) | Нет (нужен Plus) | **Да** |
