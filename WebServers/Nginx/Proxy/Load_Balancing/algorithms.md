# Алгоритмы балансировки нагрузки Nginx

## Определения

**Алгоритм балансировки** — правило, по которому Nginx выбирает сервер из группы upstream для обработки каждого входящего запроса.

**Upstream** — именованная группа бэкенд-серверов, между которыми распределяется нагрузка. Подробнее: [Обзор концепций балансировки](./overview_concepts.md).

## Основные концепции

Nginx поддерживает несколько алгоритмов распределения запросов, которые указываются в блоке `upstream`.

### Round Robin (по умолчанию)

Запросы распределяются по серверам поочередно. Это самый простой метод.

- **Weighted Round Robin**: запросы распределяются пропорционально весу (`weight`) сервера. Сервер с большим весом получает больше запросов.

### Least Connections (`least_conn`)

Новый запрос отправляется на сервер с наименьшим количеством активных соединений. Алгоритм эффективен, когда сессии могут быть длительными, а запросы занимают разное время на обработку.

При использовании данного алгоритма стоит учитывать, что если один из бэкендов неисправен, но быстро отдает пустые ответы с кодом 200 OK, он будет иметь минимум активных соединений и «притянет» большую часть трафика.

### IP Hash (`ip_hash`)

Запросы от одного клиента (на основе IP-адреса) всегда отправляются на один и тот же сервер, если он доступен. Используется для реализации «липких сессий» (sticky sessions), когда приложение хранит состояние сессии локально.

```nginx
upstream backend {
    ip_hash;
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
}
```

**Недостатки:**

- **Неравномерное распределение**: если большое количество клиентов находится за одним NAT, они могут быть направлены на один бэкенд.
- **Проблема с IPv4**: алгоритм использует только первые три октета IPv4-адреса для расчета хеша.
- Для более гибкого «прилипания» рекомендуется использовать алгоритм `hash` или специальную директиву `sticky`. Подробнее: [Sticky Sessions](./sticky_sessions.md).

### Hash (`hash`)

Распределяет запросы на основе хеша указанной переменной (например, `$request_uri`, `$remote_addr`). Обеспечивает привязку клиента к одному бэкенду для одного значения хеша. Параметр `consistent` (консистентное хеширование) минимизирует перераспределение клиентов при изменении состава группы.

```nginx
upstream backend {
    hash $request_uri consistent;
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
}
```

### Random (`random`)

Распределяет запросы случайным образом. Полезен, когда несколько балансировщиков работают перед одной группой бэкендов и не обмениваются информацией о нагрузке.

- **random two least_conn**: Nginx выбирает два случайных сервера и направляет запрос на тот, у которого меньше активных соединений.

```nginx
upstream backend {
    random two least_conn;
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
    server 127.0.0.1:9002;
}
```

## Практические сценарии

### Параметры серверов в upstream

Директива `server` внутри блока `upstream` поддерживает параметры, влияющие на работу алгоритмов и отказоустойчивость.

| Параметр | Описание | Значение по умолчанию |
|:---------|:---------|:----------------------|
| `weight=N` | Вес сервера. Чем выше, тем большую долю запросов получает сервер. | `1` |
| `max_fails=N` | Максимальное количество неудачных попыток соединения перед признанием сервера недоступным. | `1` |
| `fail_timeout=T` | Время, на которое сервер исключается из балансировки после достижения `max_fails`. | `10s` |
| `backup` | Резервный сервер. Используется только когда все основные серверы недоступны. | — |
| `down` | Сервер полностью исключен из балансировки. | — |
| `slow_start=T` | (**Angie / Nginx Plus**) Плавное наращивание нагрузки на восстановленный сервер. | — |
| `drain` | (**Angie / Nginx Plus**) Плавный вывод сервера из эксплуатации. | — |

При использовании `backup` следует учитывать, что Nginx определяет недоступность основного сервера только после провала попытки соединения. Рекомендуется снижать `proxy_connect_timeout` (например, до `1s`) для ускорения переключения.

### Пример конфигурации

```nginx
upstream backend {
    # Основные серверы
    server 10.0.0.1:80 weight=3;
    server 10.0.0.2:80 max_fails=2 fail_timeout=15s slow_start=30s;
    
    # Резервный сервер
    server 10.0.0.3:80 backup;
    
    # Сервер на обслуживании
    server 10.0.0.4:80 down;
}
```
