# Алгоритмы балансировки нагрузки Nginx и Angie

## Определения

**Алгоритм балансировки** — логика, по которой Nginx выбирает конкретный сервер из группы `upstream` для обработки каждого входящего запроса. Выбор метода зависит от характера нагрузки, типа приложения (stateful/stateless) и требований к отказоустойчивости.

**Upstream** — именованная группа бэкенд-серверов, между которыми распределяется нагрузка. Подробнее: [Обзор концепций балансировки](./overview_concepts.md).

## Основные алгоритмы (L7 и L4)

Nginx поддерживает несколько уровней распределения запросов, от простейшего циклического перебора до динамического анализа времени ответа. Большинство алгоритмов применимы как в контексте `http`, так и в модуле `stream` (TCP/UDP).

### Round Robin (Циклическое распределение)

Алгоритм по умолчанию. Запросы распределяются по серверам поочередно.

- **Weighted Round Robin**: Запросы распределяются пропорционально весу (`weight`) сервера. 
  - *Пример*: Если у Server A `weight=5`, а у Server B `weight=1`, то из 6 запросов 5 уйдут на Server A.
- **Механизм плавного взвешивания (Smooth Weighted Round-Robin)**: Nginx использует внутренний счетчик (`current_weight`), который увеличивается на значение `weight` при каждом выборе и уменьшается на сумму всех весов после выбора. Это предотвращает "взрывную" нагрузку на сервер с самым большим весом в начале цикла, распределяя запросы к нему более равномерно во времени.

### Least Connections (`least_conn`)

Запрос отправляется на сервер с наименьшим количеством **активных** соединений.

- **Сценарий**: Наиболее эффективен для сессий с разным временем обработки (например, тяжелые SQL-запросы vs легкая статика).
- **Особенности**: Учитывает веса серверов. При одинаковом соотношении соединений к весу используется Round Robin.
- **Предостережение**: Если один из бэкендов неисправен, но быстро отдает пустые ответы (например, ошибку 500 или 200 OK без контента), он будет иметь минимум активных соединений и «притянет» основной трафик.
- **Взаимодействие с `max_fails`**: Если сервер помечен как временно недоступный, он исключается из расчета соединений до истечения `fail_timeout`.

### IP Hash (`ip_hash`)

Привязка клиента к серверу на основе его IP-адреса. Доступно только в модуле `http`.

- **IPv4**: Использует первые три октета адреса (сеть /24). Это гарантирует, что клиенты из одной подсети (например, за офисным NAT) попадут на один бэкенд.
- **IPv6**: Использует весь адрес целиком.
- **Сценарий**: Реализация «липких сессий» (sticky sessions) без использования Cookie, когда состояние хранится в локальной памяти бэкенда.
- **Недостатки**: 
  - Дисбаланс, если много клиентов за одним корпоративным NAT.
  - Несовместим с параметром `weight` (до Nginx 1.21.0) и `backup` серверами.

```nginx
upstream backend {
    ip_hash;
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
}
```

### Hash (`hash`)

Распределяет запросы на основе хеша произвольной переменной (URI, куки, аргументы).

- **Консистентное хеширование (`consistent`)**: Использует алгоритм **Ketama**. При добавлении или удалении сервера из группы перераспределяется лишь малая часть запросов (1/N), что критично для эффективности кэширующих серверов. Параметр минимизирует перераспределение запросов при изменении upstream.
- **Примеры ключей**:
  - `$request_uri` — для кэширующих прокси.
  - `$arg_user_id` — привязка по GET-параметру.
  - `$cookie_jsessionid` — привязка по сессии приложения.

```nginx
upstream cache_cluster {
    # Балансировка по URI с сохранением привязки при изменении upstream
    hash $request_uri consistent;
    server cache1.local;
    server cache2.local;
}
```

### Random (`random`)

Выбор сервера случайным образом.

- **random two least_conn**: Балансировщик выбирает два случайных сервера и направляет запрос на тот, у которого меньше активных соединений. Это снижает эффект "стадного поведения" в распределенных системах, где несколько независимых балансировщиков работают с одной группой бэкендов.
- **random two least_time**: Аналогично, но выбор по минимальному времени ответа (только Angie/Plus).

## Расширенные алгоритмы (Angie / Nginx Plus)

Эти алгоритмы требуют наличия зоны разделяемой памяти (`zone`) в блоке `upstream`.

### Least Time (`least_time`)

Выбирает сервер с наименьшим средним временем ответа и минимальным количеством активных соединений.

- **header**: Время получения первого байта заголовков ответа.
- **last_byte**: Время получения полного ответа.
- **inflight** (Angie): Учитывает количество запросов, находящихся в обработке (самый точный метод для предотвращения перегрузки медленных узлов).

```nginx
upstream backend {
    # Выбор по минимальному времени получения заголовков (только Angie/Plus)
    least_time header;
    server 10.0.0.1;
    server 10.0.0.2;
}
```

### Feedback (`feedback`)

Эксклюзивный алгоритм **Angie** (v1.6.0+). Реализует интеллектуальное распределение на основе внешней обратной связи.

- **Принцип работы**: Angie может запрашивать файл (например, `/stats/feedback.json`) с бэкенда или получать данные через агент. В зависимости от текущей загрузки CPU или памяти бэкенда, Angie динамически меняет его вес. Требует поддержки на стороне приложения или агента.
- **Преимущество**: Позволяет балансировщику "чувствовать" реальное состояние сервера задолго до того, как он начнет отдавать ошибки по таймауту.

## Практические сценарии

### Управление очередью и лимитами (`max_conns`, `queue`)

Для защиты бэкендов от перегрузки используются параметры ограничения соединений.

- **`max_conns=N`**: Жесткий лимит одновременных соединений к серверу.
- **`queue`**: Очередь запросов в разделяемой памяти (Angie/Plus). Если все серверы достигли `max_conns`, запросы встают в очередь. В OSS Nginx запрос сразу вернет ошибку (обычно 503), если нет `backup`.

```nginx
upstream backend {
    zone upstream_zone 64k;
    server 10.0.0.1:80 max_conns=100;
    server 10.0.0.2:80 max_conns=100;
    
    # Очередь на 50 запросов с таймаутом ожидания 15с (Angie/Plus)
    queue 50 timeout=15s;
}
```

### Параметры серверов в upstream

| Параметр | Описание | Доступность |
|:---------|:---------|:------------|
| `weight=N` | Относительный вес сервера в балансировке. | Все версии |
| `max_fails=N` | Число ошибок до временного исключения сервера. | Все версии |
| `fail_timeout=T` | Время «штрафа» после `max_fails`. | Все версии |
| `max_conns=N` | Лимит одновременных соединений. | Все версии |
| `slow_start=T` | Плавный ввод сервера после восстановления. | Angie / Plus |
| `drain` | Плавный вывод из эксплуатации (завершение старых сессий). | Angie / Plus |
| `backup` | Резервный сервер (активен, если основные лежат). | Все версии |
| `down` | Ручное исключение сервера из ротации. | Все версии |

### Пример сложной конфигурации

```nginx
upstream api_cluster {
    zone api_zone 128k; # Зона для разделяемой памяти (нужна для least_conn и метрик)
    
    # Основные серверы с разным весом и плавным стартом
    server 10.5.0.10:8080 weight=3 max_conns=500;
    server 10.5.0.11:8080 weight=1 max_conns=200 slow_start=60s;
    
    # Использование консистентного хеширования по ID пользователя
    hash $arg_user_id consistent;
    
    # Резервный узел
    server 10.5.0.20:8080 backup;
    
    # Настройка очереди для Angie/Plus
    queue 50 timeout=10s;
}
```

## Сравнение возможностей версий

| Функция | Nginx OSS (1.26) | Nginx Plus | Angie (1.12) |
| :--- | :--- | :--- | :--- |
| Базовые алгоритмы (RR, Least Conn, Hash) | Да | Да | Да |
| Least Time (inflight) | Нет | Да | **Да** |
| Feedback (Dynamic weights) | Нет | Нет | **Да** |
| Queue (Очередь запросов) | Нет | Да | **Да** |
| Sticky Sessions (Cookie/Route) | Нет | Да | **Да** |
| API / Prometheus Metrics | Нет | Да | **Да** |
