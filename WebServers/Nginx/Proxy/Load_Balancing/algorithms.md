# Алгоритмы балансировки нагрузки Nginx и Angie

## Определения

**Алгоритм балансировки** — логика, по которой Nginx выбирает конкретный сервер из группы `upstream` для обработки каждого входящего запроса. Выбор метода зависит от характера нагрузки, типа приложения (stateful/stateless) и требований к отказоустойчивости.

**Upstream** — именованная группа бэкенд-серверов, между которыми распределяется нагрузка. Подробнее: [Обзор концепций балансировки](./overview_concepts.md).

**Активное соединение (active connection)** — TCP-соединение, которое в данный момент обрабатывает запрос или ожидает ответа от бэкенда. Используется алгоритмом `least_conn` для принятия решения о выборе сервера.

**Зона разделяемой памяти (`zone`)** — участок shared memory в блоке `upstream`, в котором хранится состояние серверов (текущие соединения, веса, статусы). Обязательна для работы `least_conn`, метрик и sticky-сессий в Nginx Plus/Angie.

**Консистентное хеширование (consistent hashing)** — алгоритм хеширования (чаще всего **Ketama**), при котором добавление или удаление серверов из группы приводит к перераспределению лишь малой части ключей (порядка 1/N). Критично для кэширующих прокси и stateful-сервисов.

## Основные концепции и архитектура

### Жизненный цикл запроса в upstream

При получении запроса, предназначенного для `proxy_pass http://backend`, Nginx выполняет следующие этапы:

1. **Выбор upstream-группы:** по имени в `proxy_pass` определяется блок `upstream`.
2. **Определение алгоритма:** если алгоритм не указан явно, используется Round Robin.
3. **Фильтрация серверов:** исключаются серверы в состоянии `down`, серверы, исчерпавшие `max_fails`, и серверы, достигшие `max_conns`.
4. **Выбор сервера:** применяется выбранный алгоритм среди оставшихся кандидатов.
5. **Установка соединения:** создается TCP-соединение с выбранным бэкендом (или берется из keepalive-пула).
6. **Проксирование:** запрос передается бэкенду, ответ возвращается клиенту.
7. **Обновление метрик:** увеличиваются счетчики соединений и запросов для выбранного сервера.

### Взаимодействие с failover

Nginx поддерживает прозрачное переключение между бэкендами при ошибках через `proxy_next_upstream`. Если запрос не удался на одном сервере, балансировщик выбирает следующий кандидат из той же upstream-группы и повторяет попытку. Лимиты повторений задаются `proxy_next_upstream_tries` и `proxy_next_upstream_timeout`.

### Ограничения на уровне версий

Nginx Open Source, Nginx Plus и Angie различаются набором доступных алгоритмов и параметров. Все ограничения явно помечены в таблице сравнения версий в конце файла.

## Алгоритмы балансировки

### Round Robin (Циклическое распределение)

Алгоритм по умолчанию. Запросы распределяются по серверам поочередно.

- **Weighted Round Robin:** Запросы распределяются пропорционально весу (`weight`) сервера.
  - *Пример:* Если у Server A `weight=5`, а у Server B `weight=1`, то из 6 запросов 5 уйдут на Server A.
- **Механизм плавного взвешивания (Smooth Weighted Round-Robin):** Nginx использует внутренний счетчик (`current_weight`), который увеличивается на значение `weight` при каждом выборе и уменьшается на сумму всех весов после выбора. Это предотвращает "взрывную" нагрузку на сервер с самым большим весом в начале цикла, распределяя запросы к нему более равномерно во времени.

### Least Connections (`least_conn`)

Запрос отправляется на сервер с наименьшим количеством **активных** соединений.

- **Сценарий:** Наиболее эффективен для сессий с разным временем обработки (например, тяжелые SQL-запросы vs легкая статика).
- **Особенности:** Учитывает веса серверов. При одинаковом соотношении соединений к весу используется Round Robin.
- **Предостережение:** Если один из бэкендов неисправен, но быстро отдает пустые ответы (например, ошибку 500 или 200 OK без контента), он будет иметь минимум активных соединений и «притянет» основной трафик.
- **Взаимодействие с `max_fails`:** Если сервер помечен как временно недоступный, он исключается из расчета соединений до истечения `fail_timeout`.

### IP Hash (`ip_hash`)

Привязка клиента к серверу на основе его IP-адреса. Доступно только в модуле `http`.

- **IPv4:** Использует первые три октета адреса (сеть /24). Это гарантирует, что клиенты из одной подсети (например, за офисным NAT) попадут на один бэкенд.
- **IPv6:** Использует весь адрес целиком.
- **Сценарий:** Реализация «липких сессий» (sticky sessions) без использования Cookie, когда состояние хранится в локальной памяти бэкенда.
- **Недостатки:**
  - Дисбаланс, если много клиентов за одним корпоративным NAT.
  - Несовместим с параметром `weight` (до Nginx 1.21.0) и `backup` серверами.

```nginx
upstream backend {
    ip_hash;
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
}
```

### Hash (`hash`)

Распределяет запросы на основе хеша произвольной переменной (URI, куки, аргументы).

- **Консистентное хеширование (`consistent`):** Использует алгоритм **Ketama**. При добавлении или удалении сервера из группы перераспределяется лишь малая часть запросов (1/N), что критично для эффективности кэширующих серверов. Параметр минимизирует перераспределение запросов при изменении upstream.
- **Примеры ключей:**
  - `$request_uri` — для кэширующих прокси.
  - `$arg_user_id` — привязка по GET-параметру.
  - `$cookie_jsessionid` — привязка по сессии приложения.

```nginx
upstream cache_cluster {
    # Балансировка по URI с сохранением привязки при изменении upstream
    hash $request_uri consistent;
    server cache1.local;
    server cache2.local;
}
```

### Random (`random`)

Выбор сервера случайным образом.

- **random two least_conn:** Балансировщик выбирает два случайных сервера и направляет запрос на тот, у которого меньше активных соединений. Это снижает эффект "стадного поведения" в распределенных системах, где несколько независимых балансировщиков работают с одной группой бэкендов.
- **random two least_time:** Аналогично, но выбор по минимальному времени ответа (только Angie/Plus).

## Расширенные алгоритмы (Angie / Nginx Plus)

Эти алгоритмы требуют наличия зоны разделяемой памяти (`zone`) в блоке `upstream`.

### Least Time (`least_time`)

Выбирает сервер с наименьшим средним временем ответа и минимальным количеством активных соединений.

- **header:** Время получения первого байта заголовков ответа.
- **last_byte:** Время получения полного ответа.
- **inflight** (Angie): Учитывает количество запросов, находящихся в обработке (самый точный метод для предотвращения перегрузки медленных узлов).

```nginx
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080 backup;
    keepalive 32;
}
```

### Feedback (`feedback`)

Эксклюзивный алгоритм **Angie** (v1.6.0+). Реализует интеллектуальное распределение на основе внешней обратной связи.

- **Принцип работы:** Angie может запрашивать файл (например, `/stats/feedback.json`) с бэкенда или получать данные через агент. В зависимости от текущей загрузки CPU или памяти бэкенда, Angie динамически меняет его вес. Требует поддержки на стороне приложения или агента.
- **Преимущество:** Позволяет балансировщику "чувствовать" реальное состояние сервера задолго до того, как он начнет отдавать ошибки по таймауту.

## Практические сценарии

### Сценарий 1: Базовая конфигурация upstream для HTTP-приложения

Создание группы бэкендов с весами и failover для типичного веб-приложения.

```nginx
http {
    upstream web_app {
        zone web_app_zone 64k;

        # Основные серверы с разным весом
        server 10.0.0.10:8080 weight=3 max_fails=3 fail_timeout=30s;
        server 10.0.0.11:8080 weight=1 max_fails=3 fail_timeout=30s;

        # Резервный узел (активируется только при падении основных)
        server 10.0.0.20:8080 backup;
    }

    server {
        listen 80;
        server_name app.example.com;

        location / {
            proxy_pass http://web_app;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }
    }
}
```

**Проверка:**

```bash
nginx -t
# → nginx: configuration file /etc/nginx/nginx.conf test is successful
nginx -s reload
# → signal reload started
```

### Сценарий 2: Управление очередью и лимитами (`max_conns`, `queue`)

Для защиты бэкендов от перегрузки используются параметры ограничения соединений.

- **`max_conns=N`:** Жесткий лимит одновременных соединений к серверу.
- **`queue`:** Очередь запросов в разделяемой памяти (Angie/Plus). Если все серверы достигли `max_conns`, запросы встают в очередь. В OSS Nginx запрос сразу вернет ошибку (обычно 503), если нет `backup`.

```nginx
upstream backend {
    zone upstream_zone 64k;
    server 10.0.0.1:80 max_conns=100;
    server 10.0.0.2:80 max_conns=100;

    # Очередь на 50 запросов с таймаутом ожидания 15с (Angie/Plus)
    queue 50 timeout=15s;
}
```

### Сценарий 3: Плавный старт и вывод из эксплуатации

Использование `slow_start` и `drain` для управления жизненным циклом серверов без прерывания обслуживания.

```nginx
upstream api_pool {
    zone api_pool_zone 64k;

    # Сервер только что восстановился: вес будет расти линейно в течение 60 секунд
    server 10.0.0.10:8080 weight=5 slow_start=60s;

    # Сервер плавно выводится: не принимает новых соединений, но завершает существующие
    server 10.0.0.20:8080 drain;

    # Обычный сервер
    server 10.0.0.30:8080 weight=5;
}
```

### Сценарий 4: Выбор алгоритма для кэширующего прокси

Использование консистентного хеширования для минимизации перераспределения кэша при изменении состава бэкендов.

```nginx
upstream cache_cluster {
    zone cache_zone 64k;
    hash $request_uri consistent;

    server cache1.example.com weight=3;
    server cache2.example.com weight=1;
    server cache3.example.com;
}
```

**Почему не `ip_hash`:** При добавлении нового сервера в группу `ip_hash` перераспределит все запросы от клиентов, чьи IP-адреса теперь попадают на новый узел, что приведет к промаху кэша. `hash ... consistent` перераспределяет только ~1/N запросов.

### Сценарий 5: Least Connections для API с неравномерной нагрузкой

Применение `least_conn` для API, где отдельные запросы могут занимать от миллисекунд до секунд.

```nginx
upstream api_backend {
    zone api_zone 64k;
    least_conn;

    server 10.0.0.10:8080 weight=2 max_fails=3 fail_timeout=30s;
    server 10.0.0.11:8080 weight=2 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:8080 weight=1 max_fails=3 fail_timeout=30s;
}
```

### Сценарий 6: Комплексная конфигурация с очередями и метриками

Современная конфигурация для high-load системы с ограничениями и резервированием.

```nginx
upstream api_cluster {
    zone api_zone 128k;

    # Основные серверы с разным весом и плавным стартом
    server 10.5.0.10:8080 weight=3 max_conns=500;
    server 10.5.0.11:8080 weight=1 max_conns=200 slow_start=60s;

    # Резервный узел
    server 10.5.0.20:8080 backup;

    # Очередь запросов (Angie/Plus)
    queue 50 timeout=10s;
}
```

## Операции и команды

### Валидация конфигурации upstream

```bash
# Проверка синтаксиса перед применением
nginx -t
# → nginx: configuration file /etc/nginx/nginx.conf test is successful

# Грациозная перезагрузка без потери соединений
nginx -s reload
# → signal reload started
```

### Диагностика балансировки и upstream

```bash
# Поиск ошибок upstream в логе (502, 504, переполнение очереди)
grep -E "upstream|502|504" /var/log/nginx/error.log | tail -n 50

# Анализ логов доступа: какой бэкенд получил запрос
tail -f /var/log/nginx/access.log | awk '{print $4}' | sort | uniq -c | sort -rn

# Проверка переменных upstream в логах
# В конфигурации:
# log_format upstream_debug '$remote_addr - [$time_local] '
#                           '$upstream_addr $upstream_status $upstream_response_time';
tail -f /var/log/nginx/access.log | grep upstream_debug

# Поиск записей о переключениях между бэкендами
grep "upstream sent too big header" /var/log/nginx/error.log

# Проверка времени ответа бэкендов
awk '$upstream_response_time > 1.0 {print $0}' /var/log/nginx/access.log | head -n 20
```

### Мониторинг состояния upstream

```bash
# Подсчет ошибок 502/504 по бэкендам (требуется $upstream_addr в логе)
awk '{print $NF}' /var/log/nginx/access.log | sort | uniq -c | sort -rn

# Проверка кэша DNS (если используется resolver в upstream)
systemd-resolve --statistics

# Мониторинг соединений к конкретному порту бэкенда
ss -tn state established '( daddr = 10.0.0.10 and sport = :8080 )' | wc -l

# Проверка keepalive-соединений upstream
ss -tn state established '( daddr = 10.0.0.10 and sport = :8080 )'
```

### Диагностика с curl

```bash
# Проверка, что Nginx проксирует на правильный бэкенд
curl -I http://app.example.com/health
# → HTTP/1.1 200 OK
# → X-Upstream-Addr: 10.0.0.10:8080  (если добавлен кастомный заголовок)

# Проверка заголовков при ошибках бэкенда
curl -v http://app.example.com/slow-endpoint 2>&1 | grep -E "< HTTP|X-Upstream|timed out"

# Проверка работы sticky-сессий (если настроен cookie)
curl -v http://app.example.com/ -c /tmp/cookies.txt
grep -i "upstream" /var/log/nginx/access.log
```

## Диагностика и устранение неполадок

### Типичные ошибки

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `502 Bad Gateway` на всех запросах | Все бэкенды недоступны или упали | Проверить доступность бэкендов: `curl http://10.0.0.10:8080`; убедиться, что `upstream` указан правильно; проверить firewall/SELinux |
| `502 Bad Gateway` на отдельных запросах | Один бэкенд недоступен, исчерпан `max_conns` или `fail_timeout` | Проверить `error.log`; проверить, не установлен ли флаг `down` вручную |
| `504 Gateway Timeout` | Бэкенд не ответил за `proxy_read_timeout` | Увеличить `proxy_read_timeout`; проверить нагрузку на бэкенд; проверить сетевую доступность |
| `503 Service Unavailable` при нагрузке | Все серверы достигли `max_conns`, очередь пуста или переполнена | Увеличить `max_conns`; добавить серверы; настроить `queue` (Angie/Plus) |
| Дисбаланс нагрузки | Неправильный `weight`, `ip_hash` с NAT, `least_conn` с быстрыми ошибками | Проверить веса; для NAT использовать `hash` вместо `ip_hash`; исключить неработающие бэкенды из `least_conn` через `max_fails` |
| Потеря сессий при росте кластера | Используется `ip_hash` или `hash` без `consistent` | Перейти на `hash ... consistent` для минимизации перераспределения |
| Бесконечные повторные запросы | `proxy_next_upstream` без ограничения `tries`/`timeout` | Установить `proxy_next_upstream_tries` и `proxy_next_upstream_timeout` |
| "upstream sent too big header" | Бэкенд прислал слишком много заголовков | Увеличить `proxy_buffer_size` и `proxy_buffers` |
| "an upstream response is buffered to a temporary file" | Ответ бэкенда не помещается в память | Увеличить `proxy_buffers` или `proxy_max_temp_file_size` |

### Диагностические команды

```bash
# Поиск ошибок upstream в логе
grep -E "upstream|502|504" /var/log/nginx/error.log | tail -n 50

# Анализ распределения запросов по бэкендам
awk '{print $NF}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -n 10

# Определение фактического списка upstream-серверов

# Проверка времени ответа бэкендов (требуется $upstream_response_time в логе)

# Поиск записей о слишком больших заголовках от бэкенда
grep "upstream sent too big header" /var/log/nginx/error.log

# Проверка переполнения временными файлами при буферизации
grep "buffered to a temporary file" /var/log/nginx/error.log
```

## Лучшие практики

### Производительность

1. **Используйте `zone` для всех upstream-групп с `least_conn` или sticky-сессиями.** Без `zone` Nginx не может сохранять состояние соединений между рабочими процессами, что приводит к некорректной балансировке.
2. **Включайте `keepalive` в `upstream` для высоконагруженных HTTP-сервисов.** Без keepalive Nginx использует HTTP/1.0 и закрывает соединение после каждого запроса, что создает избыточную нагрузку на CPU и порты.
3. **Используйте `hash ... consistent` для кэширующих прокси вместо `ip_hash`.** Консистентное хеширование минимизирует перераспределение ключей при изменении состава бэкендов.
4. **Избегайте `random` в production без явной необходимости.** Случайное распределение может привести к дисбалансу при малом числе серверов и затрудняет прогнозирование нагрузки.

### Безопасность

1. **Никогда не полагайтесь на балансировку как на механизм безопасности.** Для контроля доступа используйте `internal`, `auth_request` или WAF.
2. **Явно указывайте `max_fails` и `fail_timeout`** для каждого сервера. Без этих параметров Nginx по умолчанию использует `max_fails=1` и `fail_timeout=10s`, что может привести к частым переключениям при временных сбоях.
3. **Не используйте `backup`-серверы для активной нагрузки.** Они предназначены только для аварийного переключения и имеют более низкий приоритет.
4. **Изолируйте management-интерфейсы.** Если используете `status_zone` (Angie/Nginx Plus), ограничьте доступ к API метрик firewall-правилами или `allow/deny`.

### Эксплуатация (SRE)

1. **Логирование upstream-переменных:** Добавьте в `log_format` переменные `$upstream_addr`, `$upstream_status`, `$upstream_response_time` для трассировки запросов:

    ```nginx
    log_format upstream_debug '$remote_addr - [$time_local] '
                              '$upstream_addr $upstream_status $upstream_response_time';
    ```

2. **Мониторинг дисбаланса:** Регулярно проверяйте распределение запросов по бэкендам. Дисбаланс более чем на 20% при использовании Round Robin или `least_conn` указывает на проблему с весами или медленный бэкенд.
3. **Алертинг на 502/504:** Настройте оповещение на ошибки `502 Bad Gateway` и `504 Gateway Timeout` в `error.log`. Частые 502 указывают на падение бэкендов; частые 504 — на таймауты или перегрузку.
4. **Плановое изменение состава upstream:** При добавлении/удалении серверов из группы `hash ... consistent` перераспределение происходит автоматически. Для `ip_hash` без `consistent` ожидайте каскадный промах кэша.
5. **Тестирование failover:** Периодически проверяйте, что `proxy_next_upstream` корректно переключает трафик при отключении одного из бэкендов:

    ```bash
    # Выключить один бэкенд и проверить переключение
    systemctl stop app@node1
    curl -I http://app.example.com/health
    # Проверить, что запросы ушли на оставшиеся узлы
    ```

6. **Резервное копирование конфигурации:** Перед изменением алгоритмов или параметров upstream создайте бэкап и проверяйте конфигурацию через `nginx -t`.

### Примечания

- В Nginx Open Source базовый набор алгоритмов (Round Robin, Least Connections, Hash, IP Hash, Random) доступен без дополнительных модулей.
- Angie и Nginx Plus расширяют базовый функционал алгоритмами `least_time` и `feedback`, а также параметрами `slow_start`, `drain` и `queue`.
- Для stateful-приложений, требующих привязки сессий, в Nginx OSS используйте `ip_hash` или `hash`, а в Angie/Nginx Plus — встроенный метод `sticky`.
