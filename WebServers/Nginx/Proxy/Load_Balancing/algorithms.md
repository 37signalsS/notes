# Алгоритмы балансировки нагрузки Nginx

## Определения

- **Алгоритм балансировки** — правило, по которому Nginx выбирает сервер из группы `upstream` для обработки каждого входящего запроса.
- **Upstream** — именованная группа бэкенд-серверов, между которыми распределяется нагрузка. Подробнее: [Обзор концепций балансировки](./overview_concepts.md).

## Базовые концепции

Nginx поддерживает несколько алгоритмов распределения запросов, которые указываются в блоке `upstream`.

### Round Robin (по умолчанию)

Запросы распределяются по серверам поочередно. Это самый простой метод.

- **Weighted Round Robin:** Запросы распределяются пропорционально весу (`weight`) сервера. Сервер с большим весом получает больше запросов.

### Least Connections (`least_conn`)

Новый запрос отправляется на сервер с наименьшим количеством активных соединений. Эффективен, когда сессии могут быть длительными, а запросы занимают разное время на обработку.

> **Возможная аномалия:** алгоритм может работать некорректно, если один из бэкендов неисправен, но быстро отдаёт пустые ответы с кодом 200 OK. Такой сервер будет иметь минимум активных соединений и «притянет» большую часть трафика, тогда как пользователи увидят неработающий сервис.

### IP Hash (`ip_hash`)

Запросы от одного клиента (на основе IP-адреса) всегда отправляются на один и тот же сервер, если он доступен. Используется для «липких сессий» (sticky sessions), когда приложение хранит состояние сессии локально.

```nginx
upstream backend {
    ip_hash;
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
}
```

**Недостатки:**

- **Неравномерное распределение:** если большое количество клиентов находится за одним корпоративным [NAT](../../../../Networking/Concepts/nat/overview.md), они все могут быть направлены на один бэкенд, вызывая его перегрузку.
- **Проблема с IPv4:** алгоритм использует только первые три октета IPv4-адреса для расчёта хеша, что усугубляет неравномерность.
- Для более гибкого и предсказуемого «прилипания» рекомендуется использовать алгоритм `hash`. Подробнее: [Sticky Sessions](./sticky_sessions.md).

### Hash (`hash`)

Распределяет запросы на основе хеша указанной переменной (например, `$request_uri`, `$remote_addr`). Обеспечивает «прилипание» клиента к одному бэкенду для одного значения хеша. Параметр `consistent` минимизирует перераспределение клиентов при изменении состава группы.

```nginx
upstream backend {
    hash $request_uri consistent;
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
}
```

### Random (`random`)

Распределяет запросы случайным образом. Полезен, когда несколько балансировщиков работают перед одной группой бэкендов и не обмениваются информацией о нагрузке.

- **`random two least_conn`:** Nginx выбирает два случайных сервера и направляет запрос на тот, у которого меньше активных соединений. Один из самых эффективных методов распределения.

```nginx
upstream backend {
    random two least_conn;
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
    server 127.0.0.1:9002;
}
```

## Практические сценарии

### Параметры серверов в `upstream`

| Параметр | Описание | Значение по умолчанию |
|:---------|:---------|:----------------------|
| `weight=N` | Вес сервера. Чем выше, тем большую долю запросов получает сервер. Позволяет направлять больше трафика на мощные машины. | `1` |
| `max_fails=N` | Максимальное количество неудачных попыток соединения, после которого сервер считается недоступным. | `1` |
| `fail_timeout=T` | Время (в секундах), на которое сервер исключается из балансировки после достижения `max_fails`. Также это период, в течение которого учитываются `max_fails`. | `10s` |
| `backup` | Резервный сервер. Используется только когда все основные серверы недоступны. | — |
| `down` | Сервер полностью исключён из балансировки. Полезно для длительного обслуживания. | — |
| `slow_start=T` | (**Angie / Nginx Plus**) Плавное наращивание нагрузки на восстановленный сервер. Вес увеличивается от 0 до номинального за время `T`, позволяя «прогреть» кэши. | — |
| `drain` | (**Angie / Nginx Plus R22**) Плавный вывод сервера из эксплуатации. Nginx перестаёт направлять новые запросы (кроме «прилипших» сессий), позволяя доработать текущие. | — |

> **Важно для `backup`:** Nginx поймёт, что основной сервер недоступен, только после провала попытки соединения по таймауту. По умолчанию `proxy_connect_timeout` равен `60s`. Для быстрого ввода бэкап-сервера рекомендуется снижать это значение, например до `1s`.

### Пример конфигурации

```nginx
upstream backend {
    server 10.0.0.1:80 weight=3;
    server 10.0.0.2:80 max_fails=2 fail_timeout=15s slow_start=30s;
    server 10.0.0.3:80 backup;
    server 10.0.0.4:80 down;
    server 10.0.0.5:80 drain;
}
```
