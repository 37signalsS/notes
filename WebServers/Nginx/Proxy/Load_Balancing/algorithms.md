# Nginx Load Balancing: Алгоритмы и параметры Upstream

### Алгоритмы балансировки

Nginx поддерживает несколько алгоритмов распределения запросов, которые можно указать в блоке `upstream`.

1. **Round Robin (по умолчанию):** Запросы распределяются по серверам поочередно. Это самый простой метод.
    * **Weighted Round Robin:** Запросы распределяются по серверам пропорционально их весу (`weight`). Сервер с большим весом получает больше запросов.

2. **Least Connections (`least_conn`):** Новый запрос отправляется на сервер с наименьшим количеством активных соединений. Этот метод эффективен, когда сессии могут быть длительными, а запросы занимают разное время на обработку.
    * **Возможная аномалия:** Этот алгоритм может работать некорректно, если один из бэкендов неисправен, но очень быстро отдает пустые ответы с кодом 200 OK. Такой сервер будет иметь минимальное количество активных соединений и "притянет" на себя большую часть трафика, в то время как пользователи будут видеть неработающий сервис.

3. **IP Hash (`ip_hash`):** Запросы от одного и того же клиента (на основе его IP-адреса) всегда отправляются на один и тот же сервер, если он доступен. Это необходимо для "липких сессий" (sticky sessions), когда приложение хранит состояние сессии локально.

    ```nginx
    upstream backend {
        ip_hash;
        server 127.0.0.1:9000;
        server 127.0.0.1:9001;
    }
    ```

    * **Недостатки:**
        * **Неравномерное распределение:** Если большое количество клиентов приходит из одной подсети (например, за одним корпоративным [NAT](../../../../Networking/Concepts/nat/overview.md)), они все могут быть направлены на один и тот же бэкенд, вызывая его перегрузку.
        * **Проблема с IPv4:** Алгоритм использует только первые три октета IPv4-адреса для расчета хеша, что усугубляет проблему неравномерного распределения.
        * Для более гибкого и предсказуемого "прилипания" рекомендуется использовать алгоритм `hash`.

4. **Hash (`hash`):** Распределяет запросы на основе хеша указанной переменной (например, `$request_uri`, `$remote_addr`). Это обеспечивает "прилипание" клиента к одному и тому же бэкенду для одного и того же значения хеша. Использование параметра `consistent` минимизирует перераспределение клиентов между серверами в случае изменения состава группы (добавление или удаление серверов).

    ```nginx
    upstream backend {
        hash $request_uri consistent; # consistent для минимизации перераспределения
        server 127.0.0.1:9000;
        server 127.0.0.1:9001;
    }
    ```

5. **Random (`random`):** Распределяет запросы случайным образом. Полезен, когда есть несколько балансировщиков перед одной группой бэкендов, и они не обмениваются информацией о нагрузке. В таком сценарии случайное распределение с каждого балансировщика обеспечивает более равномерную нагрузку на весь пул бэкендов.
    * **`random two least_conn`:** Комбинация методов: Nginx выбирает два случайных сервера и направляет запрос на тот из них, у которого меньше активных соединений. Это один из самых эффективных методов с точки зрения распределения.

    ```nginx
    upstream backend {
        random two least_conn;
        server 127.0.0.1:9000;
        server 127.0.0.1:9001;
        server 127.0.0.1:9002;
    }
    ```

### Параметры серверов в `upstream`

* `weight=N`: **Вес сервера.** Чем выше значение, тем большую долю запросов будет получать сервер. По умолчанию `1`. Позволяет направлять больше трафика на более мощные машины.
* `max_fails=N`: **Максимальное количество неудач.** Количество неудачных попыток соединения, после которого сервер считается временно недоступным. По умолчанию `1`.
* `fail_timeout=T`: **Тайм-аут.** Время (в секундах), на которое сервер будет исключен из балансировки после достижения `max_fails`. Также это время, в течение которого учитываются `max_fails`. По умолчанию `10s`.
* `backup`: **Резервный сервер.** Помечает сервер как резервный. Он будет использоваться только в том случае, если все остальные (основные) серверы в группе недоступны.
    > **Важно:** Nginx поймет, что основной сервер недоступен, только после того, как попытка соединения с ним провалится по таймауту. По умолчанию `proxy_connect_timeout` равен `60s`. Чтобы бэкап-сервер вводился в работу быстрее, это значение рекомендуется снижать, например до `1s`.
* `down`: **Отключен.** Сервер полностью исключен из балансировки. Полезно для вывода на длительное обслуживание.
* `slow_start=T`: (**Angie / Nginx Plus**) Плавное наращивание нагрузки на сервер, который был восстановлен после сбоя или добавлен в группу. Его вес постепенно увеличивается от 0 до номинального значения в течение заданного времени `T`. Это позволяет серверу "прогреть" кэши и избежать перегрузки.
* `drain`: (**Angie / Nginx Plus R22**) Плавный вывод сервера из эксплуатации. Nginx перестает направлять на него новые запросы (кроме "прилипших" сессий), позволяя ему доработать текущие и безопасно отключиться.

```nginx
upstream backend {
    server 10.0.0.1:80 weight=3;
    server 10.0.0.2:80 max_fails=2 fail_timeout=15s slow_start=30s;
    server 10.0.0.3:80 backup;
    server 10.0.0.4:80 down;
    server 10.0.0.5:80 drain;
}
```
