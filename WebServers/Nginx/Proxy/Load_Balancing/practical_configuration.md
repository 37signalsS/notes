# Практическая конфигурация балансировки нагрузки Nginx

**Надёжность:** 10 (SSoT + Официальная документация Nginx 1.26/1.27)
**Свежесть:** Июль 2026 (Актуально для Nginx 1.26+, 1.27.3+)

## Определения

**Upstream-группа** — именованный пул бэкенд-серверов, между которыми распределяются запросы. Определяется директивой `upstream` в контексте `http`.

**Проксирование** — процесс приема запроса от клиента и его передачи бэкенду. В Nginx реализуется через семейство директив `proxy_*`.

**Keep-alive (Upstream)** — механизм кэширования TCP-соединений с бэкендами для их повторного использования в последующих запросах.

## Основные концепции

### Роль и структура Upstream

Upstream-группа отделяет логику распределения нагрузки от логики обработки запросов в блоках `server`. Это позволяет:
1. Использовать разные алгоритмы балансировки (см. **[Алгоритмы балансировки](./algorithms.md)**).
2. Настраивать отказоустойчивость на уровне пула.
3. Переиспользовать одну группу серверов в разных виртуальных хостах.

### Механизм передачи запроса

Директива `proxy_pass` инициирует создание нового HTTP-запроса к бэкенду. При этом Nginx выступает как клиент для бэкенда, что требует корректной передачи метаданных (IP клиента, протокол, хост) через HTTP-заголовки.

## Практические сценарии

### 1. Объявление группы серверов

Блок `upstream` должен находиться в контексте `http`.

```nginx
upstream app_cluster {
    # Зона разделяемой памяти (необходима для работы least_conn и метрик)
    zone cluster_zone 64k;

    # Основные узлы с параметрами
    server 10.0.0.1:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 weight=1 max_fails=3 fail_timeout=30s;

    # Резервный узел
    server 10.0.0.3:8080 backup;
}
```

### 2. Настройка проксирования и передача заголовков

Для корректной работы приложения бэкенд должен знать параметры исходного запроса.

```nginx
location / {
    proxy_pass http://app_cluster;

    # Обязательные заголовки для L7-проксирования
    proxy_set_header Host $host;                          # Передача имени хоста
    proxy_set_header X-Real-IP $remote_addr;               # Реальный IP клиента
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; # Цепочка прокси
    proxy_set_header X-Forwarded-Proto $scheme;            # http или https
    
    # Рекомендуется для предотвращения проблем с редиректами на бэкенде
    proxy_redirect off;
}
```

### 3. Оптимизация производительности (Keep-alive)

Без явной настройки Nginx использует HTTP/1.0 для бэкендов, что закрывает соединение после каждого запроса.

```nginx
upstream backend_pool {
    server 10.0.0.1:8080;
    
    # Количество простаивающих соединений в кэше каждого воркера
    keepalive 32;
    # Максимальное количество запросов на одно соединение
    keepalive_requests 1000;
}

server {
    location / {
        proxy_pass http://backend_pool;

        # Включение HTTP/1.1 и сброс заголовка Connection для работы keepalive
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

### 4. Обеспечение отказоустойчивости (Failover)

Директива `proxy_next_upstream` определяет, когда Nginx должен попробовать отправить запрос следующему серверу в группе.

```nginx
location / {
    proxy_pass http://app_cluster;

    # Передавать запрос дальше при ошибках, таймаутах или 5xx кодах
    proxy_next_upstream error timeout invalid_header http_500 http_502 http_503 http_504;
    
    # Ограничения, чтобы избежать «каскадного падения» всего кластера
    proxy_next_upstream_tries 3;      # Максимум 3 попытки на один запрос
    proxy_next_upstream_timeout 10s;  # Общее время на все попытки
}
```
*Важно:* По умолчанию Nginx не повторяет запросы с методами `POST`, `LOCK`, `PATCH`, если часть данных уже была отправлена бэкенду (защита от неидемпотентных операций).

### 5. Настройка таймаутов

Таймауты критичны для защиты Nginx от зависших бэкендов.

| Директива | Описание | Рекомендация |
| :--- | :--- | :--- |
| `proxy_connect_timeout` | Время на установку TCP-соединения. | 1s - 5s (снижать для быстрой балансировки) |
| `proxy_send_timeout` | Время на передачу данных бэкенду. | 30s - 60s |
| `proxy_read_timeout` | Время ожидания ответа после передачи запроса. | 30s - 60s (увеличивать для тяжелых API) |

### 6. Управление буферизацией

Буферизация (`proxy_buffering`) позволяет Nginx быстро прочитать ответ бэкенда и освободить его, отдавая данные клиенту самостоятельно.

```nginx
location / {
    proxy_pass http://app_cluster;
    
    proxy_buffering on;
    proxy_buffer_size 4k;         # Для заголовков ответа
    proxy_buffers 8 16k;          # Для тела ответа (8 буферов по 16к)
    proxy_busy_buffers_size 32k;  # Лимит данных, отправляемых клиенту в процессе чтения
}
```

## Дополнительная информация

### Безопасность заголовков

Для повышения безопасности можно скрывать или игнорировать заголовки, приходящие от бэкенда:
- `proxy_hide_header X-Powered-By;` — скрывает информацию о стеке технологий.
- `proxy_ignore_headers Cache-Control;` — заставляет Nginx игнорировать инструкции кэширования от приложения (если настроен `proxy_cache`).
