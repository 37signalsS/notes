# Балансировка нагрузки в Nginx: сравнение и дополнительные сведения

## Определения

**Обратный прокси (Reverse Proxy)** — сервер-посредник, принимающий запросы от внешних клиентов и распределяющий их между внутренними узлами (бэкендами). В отличие от прямого прокси, он защищает и абстрагирует внутреннюю инфраструктуру.

**Балансировка нагрузки (Load Balancing)** — способ распределения входящего сетевого трафика между группой бэкенд-серверов. Является ключевым компонентом для построения масштабируемых и отказоустойчивых систем. Общие принципы описаны в документе [Кластеризация и балансировка для HA](../../../../Concepts/High_Availability/ha_clustering_and_load_balancing.md).

**Upstream** — именованная группа бэкенд-серверов в конфигурации Nginx, между которыми распределяется нагрузка. Подробное описание алгоритмов и параметров приведено в файле [Алгоритмы балансировки](./algorithms.md).

**L4 / L7 балансировка** — распределение на транспортном (TCP/UDP, порт, IP) или прикладном (HTTP-заголовки, URI, cookies) уровне OSI. Nginx выполняет L7-балансировку в модуле `ngx_http_proxy_module` и L4 — в модуле `ngx_stream_proxy_module`. Подробнее: [L4-проксирование](../nginx_l4_proxying.md).

**Событийно-ориентированная архитектура (Event-driven)** — модель обработки запросов, при которой один рабочий процесс обслуживает тысячи одновременных соединений асинхронно, без создания отдельного потока на каждый запрос. Это исключает накладные расходы на переключение контекста.

**Проблема C10k** — историческая задача по одновременному обслуживанию 10 000 соединений одним сервером. Её успешное решение стало фундаментом популярности Nginx.

**Пассивная проверка (Passive Health Check)** — мониторинг доступности бэкендов на основе анализа реальных запросов клиентов. В Nginx OSS реализована через `max_fails` и `fail_timeout` в блоке `upstream`. Активные проверки в Nginx OSS требуют стороннего модуля; в Angie и Nginx Plus доступны нативно. Подробнее: [Health Checks и мониторинг](./health_checks_and_monitoring.md).

**Липкие сессии (Sticky Sessions / Session Affinity)** — механизм привязки клиента к конкретному бэкенду на протяжении всей сессии. Реализуется через `ip_hash`, `hash` или встроенные методы `sticky` (Angie/Nginx Plus). Подробнее: [Sticky Sessions](./sticky_sessions.md).

**Keepalive-пул (Upstream Keepalive)** — кэш открытых TCP/TLS-соединений между Nginx и бэкендами. Директива `keepalive <N>` в блоке `upstream` задает максимальное число соединений на каждый воркер, исключая накладные расходы на TCP/TLS handshake для каждого запроса.

**Прокси-протокол (Proxy Protocol)** — протокол для передачи реального IP-адреса клиента через балансировщик, работающий на L4. Используется, когда Nginx стоит за внешним L4-балансировщиком (HAProxy, ELB) и не может получить IP напрямую из TCP-соеединения. Подробнее: [Proxy Protocol](../../../../Networking/Protocols/proxy_protocol.md).

## Основные концепции и архитектура

### Архитектурное сравнение: Nginx против Apache HTTP Server

Apache HTTP Server (с модулями `prefork` или `worker`) долгое время был стандартом, но проигрывал Nginx в плотности соединений и потреблении памяти.

| Характеристика | Apache HTTP Server | Nginx / Angie |
| :--- | :--- | :--- |
| **Модель обработки** | Процессы или потоки на запрос (Thread-per-request). Высокое потребление RAM на каждое соединение. | Событийный цикл (Event loop). Минимальное потребление RAM (~2 MB на 10 000 соединений). |
| **Работа со статикой** | Передает файлы через потоки, что медленнее при высокой нагрузке. | Системные вызовы `sendfile` и асинхронный I/O (Zero-Copy). Лучшая скорость отдачи статики в индустрии. |
| **Конфигурация** | Поддержка `.htaccess` (распределенная). Снижает скорость из-за постоянных проверок ФС на каждый запрос. | Централизованная. Считывается и компилируется один раз при старте. |
| **Масштабируемость** | Деградирует при росте числа конкурентных соединений. | Линейная масштабируемость при добавлении ядер CPU. |
| **Модульная система** | Модули загружаются динамически. | Модули компилируются статически (меньше поверхность атаки, выше предсказуемость). |
| **Совместимость** | Широкая поддержка legacy-модулей (PHP как модуль, CGI). | Требует отдельного PHP-FPM/WSGI/gunicorn-процесса для динамики. |

**Вывод для SRE:** Nginx предпочтительнее как Edge-балансировщик и терминатор TLS. Apache остается актуальным для legacy-приложений с heavy модульной логикой, где требуется `.htaccess`.

### Балансировщики 2026 года: Nginx, Angie, HAProxy, Traefik

В 2026 году выбор инструмента зависит от архитектурного контекста инфраструктуры.

| Инструмент | Роль | Сильные стороны | Ограничения |
| :--- | :--- | :--- | :--- |
| **Nginx (1.27+)** | Универсальный комбайн | Статика, кэширование, L4/L7 балансировка, гибкий `rewrite`. Идеален для Edge. | Нет нативных активных проверок в OSS; нет `least_time`, `sticky`, `queue` без Plus. |
| **Angie (1.12+)** | Nginx OSS с функциями Plus | Активные проверки `check`, `least_time`, `sticky`, `queue`, REST API, Prometheus-метрики. Drop-in замена Nginx. | Меньше экосистемы, чем у Nginx; нужно тестировать совместимость с нестандартными модулями. |
| **HAProxy (3.4+)** | Высокоточный скальпель | Экстремальная производительность L4/L7, продвинутые ACL, нативный Prometheus `/metrics`, OTel. | Меньше гибкости для сложного `rewrite`; нет встроенного кэширования статики. |
| **Traefik (3.x)** | Динамический маршрутизатор | Автоматический Service Discovery (Docker, Nomad, Consul), встроенный ACME (SSL), динамическая конфигурация без перезагрузки. | Меньше контроля над низкоуровневыми параметрами по сравнению с Nginx; производительность ниже на статике. |

### Сравнение уровней балансировки

Nginx может работать на двух уровнях модели OSI, каждый из которых решает свой класс задач.

| Уровень OSI | Название | Что анализирует Nginx | Применение |
| :--- | :--- | :--- | :--- |
| **L4** | Транспортный | IP, TCP/UDP порт, SNI. Не видит содержимое трафика (SSL Passthrough). | БД (MySQL, PostgreSQL), DNS, почта, MQ, базовая отказоустойчивость. Подробнее: [L4-проксирование](../nginx_l4_proxying.md). |
| **L7** | Прикладной | URI, HTTP-заголовки, cookies, тело запроса, gRPC. | Веб-приложения, REST API, микросервисы, Sticky Sessions, WAF. |

### Архитектура процесса обработки запроса в Nginx

Понимание жизненного цикла запроса необходимо для диагностики проблем производительности.

1.  **Прием соединения:** Клиент открывает TCP/TLS-соединение с Nginx. Воркер регистрирует событие в Event Loop (epoll/kqueue).
2.  **Выбор `server` и `location`:** Nginx сопоставляет Host-заголовок с блоком `server`, а URI — с наиболее подходящим `location`.
3.  **Выбор upstream-сервера:** При наличии `proxy_pass http://backend` Nginx выбирает сервер из группы `upstream` по настроенному алгоритму (Round Robin, `least_conn` и др.).
4.  **Установка соединения с бэкендом:** Берется соединение из keepalive-пула или создается новое TCP/TLS-соединение.
5.  **Проксирование:** Nginx передает запрос бэкенду, модифицируя заголовки согласно `proxy_set_header`. Ответ буферизуется (`proxy_buffering on` по умолчанию) или передается потоком (`proxy_buffering off`).
6.  **Возврат клиенту:** Ответ отдается клиенту, соединение с ним либо закрывается, либо возвращается в пул (keepalive на стороне клиента).
7.  **Обновление счетчиков:** Увеличиваются счетчики для выбранного upstream-сервера (если настроена `zone`).

### Конфигурация и управление upstream-группами

Блок `upstream` отделяет логику распределения нагрузки от обработки запросов. Это дает:
- **Абстракцию:** Изменение состава серверов не требует правки каждого `location`.
- **Отказоустойчивость:** Автоматическое исключение неисправных узлов на основе пассивных проверок.
- **Оптимизацию:** Возможность тонкой настройки `keepalive`, `max_conns`, `slow_start`.

```nginx
http {
    upstream app_cluster {
        zone app_zone 128k;

        server 10.0.0.10:8080 weight=3 max_fails=3 fail_timeout=30s;
        server 10.0.0.11:8080 weight=1 max_fails=3 fail_timeout=30s;
        server 10.0.0.20:8080 backup;
    }

    server {
        listen 80;
        server_name app.example.com;

        location / {
            proxy_pass http://app_cluster;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
}
```

## Практические сценарии выбора инструмента

### 1. Традиционный веб-проект (Monolith / CMS)

- **Выбор:** **Nginx** или **Angie**.
- **Почему:** Требуется отдача статики, кэширование и простая балансировка в одном процессе. Angie даёт активные проверки и метрики без дополнительных модулей.

### 2. Высоконагруженный API / Финансовые системы

- **Выбор:** **HAProxy**.
- **Почему:** Минимальные задержки (low latency), мощные ACL на L4/L7, нативный экспорт метрик Prometheus и OTel-трейсинг. Подходит, когда критична каждая миллисекунда и требуется детализированный контроль над маршрутизацией.

### 3. Динамические контейнерные среды (Docker Compose / Swarm / Podman)

- **Выбор:** **Traefik**.
- **Почему:** Автоматически подхватывает новые контейнеры через labels и выпускает сертификаты Let's Encrypt без перезагрузки. Подходит, когда инфраструктура часто меняется.

### 4. Замена Nginx Plus без лицензирования

- **Выбор:** **Angie**.
- **Почему:** Drop-in замена Nginx OSS с функциями Nginx Plus (активные проверки, `least_time`, `sticky`, REST API, Prometheus-метрики). Не требует переобучения команды, так как конфигурация полностью совместима.

### 5. L4-балансировка (TCP/UDP сервисы)

- **Выбор:** **HAProxy** в `mode tcp` или **Nginx/Angie** в блоке `stream`.
- **Почему:** HAProxy обеспечивает более высокую производительность на чистом L4. Nginx/Angie удобны, если L4-балансировка требуется в дополнение к существующей L7-конфигурации на том же сервере.

## Технические особенности эксплуатации (2026)

### Поддержка HTTP/3 (QUIC)

В 2026 году поддержка HTTP/3 является обязательной стандартной практикой для Edge-балансировщиков.

- **Nginx 1.26+** и **Angie 1.4.0+**: поддержка через модуль `ngx_http_v3_module`. Требует OpenSSL 3.2+ (или BoringSSL/QuicTLS) и UDP-порт 443.
- **HAProxy 3.0+**: нативная поддержка QUIC через `bind *:443 quic4`.
- Основное преимущество: устранение Head-of-Line Blocking на транспортном уровне, устойчивость к нестабильным мобильным соединениям.

Полная конфигурация описана в документе [Конфигурация HTTP/2 и HTTP/3](../../Performance/nginx_http_versions.md).

### Мониторинг и наблюдаемость

Для SRE критично иметь детальную видимость состояния upstream-групп.

| Метод | Nginx OSS | Angie | Nginx Plus |
| :--- | :--- | :--- | :--- |
| Активные проверки | Нет (требует сторонний модуль) | Да (`check`) | Да (`health_check`) |
| Метрики по upstream | Нет | Да (REST API, Prometheus) | Да (REST API) |
| `stub_status` | Да (общая статистика) | Да | Да |

Angie и Nginx Plus предоставляют `status_zone` для детальной статистики по каждому виртуальному хосту и upstream-группе.

## Операции и команды

### Валидация конфигурации

```bash
# Проверка синтаксиса перед применением
nginx -t
# → nginx: configuration file /etc/nginx/nginx.conf test is successful

# Применение изменений без потери соединений (graceful reload)

# → signal reload started
```

### Диагностика upstream через переменные в логах

Добавьте в `log_format` upstream-переменные для трассировки запросов:

```nginx
log_format upstream_debug '$remote_addr - [$time_local] '
                          '$upstream_addr $upstream_status $upstream_response_time';
```

Ключевые переменные upstream:

| Переменная | Описание |
| :--- | :--- |
| `$upstream_addr` | IP и порт бэкенда, обработавшего запрос. |
| `$upstream_status` | HTTP-статус ответа от бэкенда. |
| `$upstream_response_time` | Время обработки запроса бэкендом (в секундах с дробной частью). |
| `$upstream_connect_time` | Время установки TCP/TLS-соединения с бэкендом. |
| `$upstream_first_byte_time` | Время до получения первого байта ответа от бэкенда. |
| `$upstream_cache_status` | Статус кэша (`HIT`, `MISS`, `EXPIRED`, `BYPASS`, `STALE`). |

### Анализ логов и статистики

```bash
# Распределение запросов по бэкендам (требуется $upstream_addr в логе)
awk '{print $NF}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -n 10
# → 1500 10.0.0.1:8080
# → 1480 10.0.0.2:8080

# Поиск ошибок upstream в логе ошибок
grep -E "upstream|502|504" /var/log/nginx/error.log | tail -n 50

# → ESTAB 0 0 10.0.0.5:54322 10.0.0.1:8080 users:(("nginx",pid=1234,fd=5))
```

## Диагностика и устранение неполадок

### Типичные ошибки upstream

| Симптом | Причина | Диагностика и решение |
| :--- | :--- | :--- |
| `502 Bad Gateway` на всех запросах | Все бэкенды недоступны; `upstream` указан с ошибкой | `curl http://10.0.0.10:8080` — проверить доступность бэкенда; `nginx -T \| grep upstream` — проверить конфигурацию; `ss -tlnp \| grep 8080` — порт слушается |
| `502 Bad Gateway` на отдельных запросах | Один бэкенд недоступен, исчерпан `max_conns` или сработал `fail_timeout` | `grep` в `error.log` за записи о маркировке `down`; проверить, не установлен ли флаг `down` вручную |
| `504 Gateway Timeout` | Бэкенд не ответил за `proxy_read_timeout`; или утечка соединений на бэкенде | Увеличить `proxy_read_timeout`; `ss -s` — проверить количество сокетов в `TIME_WAIT`; проверить нагрузку на бэкенд (`top`, `htop`) |
| `503 Service Unavailable` при нагрузке | Все серверы достигли `max_conns`, очередь пуста или переполнена | Увеличить `max_conns`; добавить серверы в `upstream`; настроить `queue` (Angie/Plus) |
| Дисбаланс нагрузки | Неправильный `weight`, `ip_hash` за NAT, `least_conn` с быстрыми ошибками | Проверить веса; для NAT использовать `hash` вместо `ip_hash`; исключить неработающие бэкенды через `max_fails` |
| Потеря сессий при росте кластера | Используется `ip_hash` или `hash` без `consistent` | Перейти на `hash ... consistent` для минимизации перераспределяции ключей |
| Бесконечные повторные запросы | `proxy_next_upstream` без ограничения `tries`/`timeout` | Установить `proxy_next_upstream_tries` и `proxy_next_upstream_timeout` |
| "upstream sent too big header" | Бэкенд прислал слишком много заголовков | Увеличить `proxy_buffer_size` и `proxy_buffers` |
| "an upstream response is buffered to a temporary file" | Ответ бэкенда не помещается в память | Увеличить `proxy_buffers` или `proxy_max_temp_file_size` |
| `client intended to send too large body` | `client_max_body_size` недостаточный для загружаемого файла | Увеличить `client_max_body_size` в соответствующем `location` |

### Диагностические команды

```bash
# Проверка, что Nginx слушает ожидаемые порты

```

## Лучшие практики

### Производительность

1.  **Настраивайте `worker_processes` по количеству ядер CPU.** Используйте `worker_processes auto;` и `worker_cpu_affinity auto;` для привязки воркеров к ядрам, что минимизирует переключения контекста и использует L1/L2 кэши процессора.
2.  **Устанавливайте `worker_rlimit_nofile` минимум в 2× `worker_connections`.** На каждое проксируемое соединение тратятся два дескриптора: клиент + бэкенд.
3.  **Используйте `zone` для всех upstream-групп с `least_conn` или sticky-сессиями.** Без `zone` Nginx не сохраняет состояние соединений между рабочими процессами, что приводит к некорректной балансировке.
4.  **Включайте `keepalive` в `upstream` для высоконагруженных HTTP-сервисов.** Без keepalive Nginx использует HTTP/1.0 и закрывает соединение после каждого запроса, создавая избыточную нагрузку на CPU и порты. Не забудьте `proxy_http_version 1.1;` и `proxy_set_header Connection "";`.
5.  **Используйте `hash ... consistent` для кэширующих прокси вместо `ip_hash`.** Консистентное хеширование минимизирует перераспределение ключей при изменении состава бэкендов.

### Эксплуатация (SRE)

1.  **Логируйте upstream-переменные.** Добавьте `$upstream_addr`, `$upstream_status`, `$upstream_response_time` в `log_format`. Это основа для трассировки запросов и расчета SLA.
2.  **Настраивайте алертинг на 502/504.** Частые 502 указывают на падение бэкендов; частые 504 — на таймауты или перегрузку бэкендов. Используйте `error.log` и access-логи.
3.  **Тестируйте failover регулярно.** Периодически проверяйте, что `proxy_next_upstream` корректно переключает трафик при отключении бэкенда. Документируйте RTO (Recovery Time Objective) для сценариев отказа.
4.  **Мониторите дисбаланс.** Дисбаланс более чем на 20% при использовании Round Robin или `least_conn` указывает на проблему с весами или медленный бэкенд. Регулярно проверяйте распределение запросов по серверам.
5.  **Резервное копирование конфигурации.** Перед изменением алгоритмов или параметров upstream создайте бэкап и проверяйте конфигурацию через `nginx -t`.
6.  **Изолируйте management-интерфейсы.** Если используете `stub_status`, REST API (Angie/Plus) или `status_zone`, ограничьте доступ к ним firewall-правилами или директивами `allow/deny`.

### Безопасность

1.  **Никогда не полагайтесь на балансировку как на механизм безопасности.** Для контроля доступа используйте `internal`, `auth_request` или WAF.
2.  **Явно указывайте `max_fails` и `fail_timeout`** для каждого сервера. Без этих параметров Nginx по умолчанию использует `max_fails=1` и `fail_timeout=10s`, что может привести к частым переключениям при временных сбоях.
3.  **Не используйте `backup`-серверы для активной нагрузки.** Они предназначены только для аварийного переключения и имеют более низкий приоритет.
4.  **Ограничивайте размер тела запроса.** Устанавливайте `client_max_body_size` в каждом `location`, чтобы предотвратить исчерпание диска и памяти при загрузке файлов.
5.  **Отключайте неиспользуемые методы.** Используйте `limit_except` для ограничения методов (GET, POST) в `location`, где это применимо.
