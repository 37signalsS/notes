# Динамическое разрешение DNS в Upstream — Nginx

**Надёжность:** 10 (SSoT + Официальная документация Nginx 1.26/1.27 / Angie 1.12)
**Свежесть:** Июль 2026 (Актуально для Nginx 1.27.3+, Angie 1.12.0+)

## Определения

**Динамическое разрешение DNS (Dynamic DNS Resolution)** — механизм, позволяющий Nginx периодически обновлять IP-адреса бэкендов в блоке `upstream` на основе DNS-записей без перезагрузки конфигурации (`reload`).

**resolver** — директива, определяющая DNS-серверы, которые Nginx будет использовать для разрешения имён в рантайме.

**resolve** — параметр директивы `server` в блоке `upstream`, указывающий Nginx периодически перечитывать DNS-запись для данного хоста.

## Основные концепции

### Проблема статического разрешения
По умолчанию Nginx разрешает доменные имена бэкендов **только один раз** в момент старта процесса. Если IP-адрес сервера изменится (что типично для Kubernetes, Docker или облачных балансировщиков), Nginx продолжит отправлять трафик на старый IP до выполнения команды `nginx -s reload`.

### Версионные ограничения и возможности
Долгое время параметр `resolve` был эксклюзивной функцией коммерческой версии Nginx Plus. Ситуация изменилась с появлением форка Angie и обновлений Nginx OSS.

| Версия / Дистрибутив | Параметр `resolve` в `upstream` | Поддержка SRV-записей |
| :--- | :--- | :--- |
| **Nginx OSS (до 1.27.2)** | **Нет** | Нет |
| **Nginx OSS (1.27.3+)** | **Да** | **Да** |
| **Angie (Open Source)** | **Да** | **Да** |
| **Nginx Plus** | **Да** | **Да** |

## Практические сценарии

### 1. Нативная динамика (Nginx 1.27.3+ / Angie / Plus)
Это наиболее эффективный метод, сохраняющий все преимущества блока `upstream` (keepalive, алгоритмы балансировки).

```nginx
http {
    # Указываем DNS-сервер (например, CoreDNS в K8s или 127.0.0.11 в Docker)
    resolver 127.0.0.11 valid=10s;

    upstream app_servers {
        # Зона разделяемой памяти обязательна для синхронизации между воркерами
        zone backend_zone 64k;

        # Периодическое обновление IP из DNS
        server backend.example.com resolve;
        
        # Поддержка Service Discovery через SRV-записи (Angie / Nginx 1.27.3+)
        # Извлекает IP, порты, веса и приоритеты автоматически
        server backend.local service=http resolve;
    }

    server {
        listen 80;
        location / {
            proxy_pass http://app_servers;
        }
    }
}
```

### 2. Обходной путь через переменные (Nginx OSS 1.26 и ниже)
Если вы используете стабильную ветку 1.26 и не можете обновиться, динамического разрешения можно добиться, используя переменную в `proxy_pass`.

```nginx
server {
    listen 80;
    # Резолвер обязателен для работы с переменными
    resolver 8.8.8.8 valid=30s;
    
    set $backend_host "api.external-service.com";

    location / {
        # Использование переменной заставляет Nginx переразрешать имя в рантайме
        proxy_pass http://$backend_host:8080;
    }
}
```
**Особенности метода:**
- **Плюсы**: Работает в бесплатном Nginx 1.26.
- **Минусы**: Игнорируются настройки `upstream` (алгоритмы `least_conn`, `keepalive` соединения). Nginx не запустится, если не указан `resolver`.

## Технические нюансы

### Зона разделяемой памяти (`zone`)
При использовании `resolve` наличие директивы `zone` обязательно. В ней хранится общая таблица соответствия имён и IP-адресов, доступная всем рабочим процессам Nginx. Без `zone` каждый воркер будет делать свои DNS-запросы независимо, что создаст лишнюю нагрузку и рассинхронизацию.

### Кэширование и TTL
Параметр `valid` в директиве `resolver` переопределяет TTL, пришедший от DNS-сервера. Если `valid` не указан, Nginx использует TTL из DNS-ответа. Рекомендуется устанавливать `valid` в соответствии с динамикой вашей среды (например, 5-10 секунд для Kubernetes).

### Поддержка IPv6
Если ваш DNS-сервер возвращает и A, и AAAA записи, Nginx по умолчанию будет разрешать обе. Для ограничения используйте параметр `ipv6=off` в директиве `resolver`.
