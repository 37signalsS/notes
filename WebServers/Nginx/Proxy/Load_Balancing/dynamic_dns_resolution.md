# Динамическое разрешение DNS в Upstream — Nginx

**Актуально для:** Nginx 1.27.3+ (Mainline) / 1.30.x+ (Stable), Angie 1.0+, Nginx Plus R7+

## Определения

**Динамическое разрешение DNS (Dynamic DNS Resolution)** — механизм, позволяющий веб-серверу Nginx асинхронно в рантайме опрашивать DNS-серверы и автоматически обновлять IP-адреса бэкендов в блоке `upstream` без перезагрузки рабочих процессов (`nginx -s reload`).

**resolver** — директива, задающая адреса DNS-серверов, параметры кэширования (`valid`) и таймауты (`resolver_timeout`). Начиная с Nginx 1.27.3, директива может размещаться как на уровне `http`, так и непосредственно внутри блока `upstream`.

**resolve** — параметр директивы `server` в блоке `upstream`, предписывающий Nginx отслеживать изменения DNS-записей для указанного доменного имени и динамически перестраивать список активных бэкендов в разделяемой памяти.

**service** — параметр директивы `server` (поддерживается в Angie и Nginx Plus), реализующий Service Discovery через DNS SRV-записи с автоматическим получением целевых портов, весов и приоритетов.

**zone** — директива, выделяющая сегмент разделяемой памяти (shared memory) для хранения динамического состояния upstream-группы (список пиров, их IP-адреса, счетчики соединений, статусы доступности), доступного всем рабочим процессам (`worker`).

**valid** — параметр директивы `resolver`, принудительно переопределяющий значение TTL (Time To Live), полученное из DNS-ответа.

**resolver_timeout** — время ожидания ответа от DNS-сервера (по умолчанию 30 секунд; в production-средах рекомендуется уменьшать до 2–5 секунд).

## Основные концепции и архитектура

### Проблема статического разрешения при старте

В базовой конфигурации Nginx Open Source (< 1.27.3) доменные имена бэкендов в блоке `upstream` разрешаются в IP-адреса **однократно** — на этапе синтаксического анализа конфигурации при запуске мастер-процесса или при выполнении команды `nginx -s reload`.

Полученные IP-адреса жестко фиксируются в C-структурах процесса:
- Если IP-адрес целевого бэкенда изменился (перенос виртуальной машины, перебалансировка сервисов, отказ хоста в локальной сети), Nginx продолжает отправлять запросы на устаревший IP.
- Клиенты получают ошибки `502 Bad Gateway` или `504 Gateway Time-out`.
- Единственным способом принудительного обновления адресов оставалась регулярная перезагрузка конфигурации (`reload`), что на высоконагруженных узлах создает паразитный всплеск нагрузки на CPU и риск накопления незавершенных воркеров при длинных keepalive-соединениях.

### Асинхронный механизм разрешения с параметром `resolve`

При указании параметра `resolve` Nginx переключается с блокирующего системного вызова `getaddrinfo(3)` на собственный встроенный неблокирующий DNS-клиент, интегрированный в цикл обработки событий (event loop):

1. **Инициализация:** При старте мастер-процесс парсит конфигурацию и инициирует первичное разрешение имен.
2. **Фоновый таймер:** Внутри worker-процесса регистрируется таймер на основе минимального полученного TTL (или значения `valid` директивы `resolver`).
3. **Неблокирующий DNS-запрос:** По истечении таймера Nginx асинхронно отправляет UDP- (или TCP-) запрос к настроенным DNS-серверам, не блокируя обработку клиентского трафика.
4. **Атомарная модификация пиров в shared memory:** При получении нового набора IP-адресов список серверов в `zone` обновляется атомарно с использованием блокировок спинлоков (spinlocks). Существующие активные соединения дорабатывают со старыми пирами до завершения запроса, а новые запросы маршрутизируются на актуальные адреса.
5. **Graceful Degradation:** Если DNS-сервер временно недоступен или возвращает ошибку `SERVFAIL`/таймаут, Nginx сохраняет в памяти последний успешный список бэкендов, предотвращая обвальный отказ сервиса.

### Роль зоны разделяемой памяти (`zone`)

Параметр `resolve` принципиально требует наличия директивы `zone` внутри `upstream`:
- Все worker-процессы Nginx функционируют в раздельных адресных пространствах операционной системы.
- Для синхронизации динамически изменяющегося списка бэкендов необходим общий сегмент оперативной памяти.
- В зоне разделяемой памяти хранятся: хэш-таблица пиров, IP-адреса, порты, веса, текущие счетчики активных соединений для алгоритма `least_conn`, а также таймстампы проверок.
- **Ограничение:** Если выделенный объем памяти в `zone` исчерпан, добавление новых серверов блокируется, и в `error.log` фиксируется критическое предупреждение `cannot add new server to upstream "..." in zone "..."`.

### Версионная матрица возможностей

| Функция / Возможность | Nginx OSS (< 1.27.3) | Nginx OSS (1.27.3+ / 1.30.x+) | Angie (OSS) | Nginx Plus |

### Кэширование, TTL и обработка отказов DNS

- **Параметр `valid`:** Директива `resolver ... valid=Xs` жестко переопределяет TTL, возвращаемый авторитативным DNS-сервером. Это критично для предотвращения перегрузки внутренних DNS-серверов частыми запросами, если TTL в зоне выставлен в 0 или 1 секунду.
- **Опция `ipv6=off`:** По умолчанию Nginx запрашивает как IPv4 (A), так и IPv6 (AAAA) записи. Если в локальной инфраструктуре IPv6 не используется, отсутствие настройки `ipv6=off` приведет к двойному объему DNS-запросов и задержкам при ожидании ответов AAAA.
- **NXDOMAIN:** Если домен перестал существовать, бэкенды переводятся в состояние недоступности (`down`), но остаются в структуре данных до восстановления валидного ответа или reload.

## Практические сценарии

### 1. Нативное динамическое разрешение в upstream (Nginx 1.27.3+ / Angie / Nginx Plus)

Рекомендуемый production-сценарий для инфраструктуры с локальными DNS-серверами (BIND9, dnsmasq, Unbound). Поддерживает пулы `keepalive` и алгоритмы балансировки `least_conn`.

```nginx
http {
    # Логирование для отслеживания разрешения и бэкендов
    log_format upstream_trace '$remote_addr - [$time_local] "$request" '
                              'upstream: $upstream_addr status: $upstream_status '
                              'rt: $upstream_response_time uct: $upstream_connect_time';

    upstream backend_app {
        # Зона разделяемой памяти обязательна для resolve
        zone backend_app_zone 128k;

        # Локальный DNS-резолвер инфраструктуры
        # ipv6=off исключает холостые AAAA-запросы в IPv4-only сетях
        resolver 127.0.0.53 10.10.0.2 valid=10s ipv6=off;
        resolver_timeout 3s;

        # Динамический бэкенд: перечитывается по истечении valid/TTL
        server app.internal.domain:8080 resolve max_fails=3 fail_timeout=10s;

        # Пул постоянных TCP-соединений к динамическим бэкендам
        keepalive 32;
    }

    server {
        listen 80;
        server_name api.company.local;

        access_log /var/log/nginx/api_upstream.log upstream_trace;

        location / {
            proxy_pass http://backend_app;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

            proxy_connect_timeout 2s;
            proxy_read_timeout 30s;
        }
    }
}
```

```bash
# Валидация синтаксиса
nginx -t
# → nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
# → nginx: configuration file /etc/nginx/nginx.conf test is successful

# Применение изменений без остановки обслуживания
nginx -s reload
```

### 2. Service Discovery через DNS SRV-записи (Angie / Nginx Plus)

Сценарий автоматического обнаружения сервисов (например, при интеграции с on-premise HashiCorp Consul или FreeIPA), где порт приложения назначается динамически.

```nginx
http {
    upstream consul_discovered_service {
        zone srv_zone 256k;

        # Внутренний DNS-сервер с поддержкой SRV (например, Consul DNS на порту 8600)
        resolver 127.0.0.1:8600 valid=5s ipv6=off;
        resolver_timeout 2s;

        # Автоматическое извлечение IP, порта и весов из SRV-записи _http._tcp.web.service.consul
        server web.service.consul service=http resolve;
    }

    server {
        listen 80;
        server_name service.local;

        location / {
            proxy_pass http://consul_discovered_service;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
        }
    }
}
```

```bash
# Проверка наличия SRV-записи через локальный DNS-сервер
dig @127.0.0.1 -p 8600 _http._tcp.web.service.consul SRV +short
# → 1 1 8081 node01.consul.
# → 1 1 8082 node02.consul.
```

### 3. Устаревший обходной путь через переменные (Nginx OSS < 1.27.3)

Сценарий для устаревших систем, где невозможно обновить Nginx до версии 1.27.3+. Использование переменной в `proxy_pass` заставляет Nginx выполнять runtime-разрешение имени через директиву `resolver`.

```nginx
http {
    # resolver задается на уровне http или server
    resolver 127.0.0.53 valid=15s ipv6=off;
    resolver_timeout 3s;

    server {
        listen 80;
        server_name legacy.local;

        location / {
            # Присваивание имени переменной инициирует вызов встроенного DNS-резолвера
            set $upstream_endpoint "http://node-pool.internal.local:8080";
            proxy_pass $upstream_endpoint;

            # Ограничения:
            # 1. Пул keepalive соединений НЕ работает (каждый запрос открывает новый TCP-сокет)
            # 2. Не работают балансировщики least_conn, random, sticky
            # 3. URI не транслируется автоматически при наличии URI в proxy_pass
        }
    }
}
```

### 4. Отказоустойчивое разрешение с несколькими DNS-серверами и статическим Backup

Конфигурация высокой доступности: Nginx перебирает несколько DNS-серверов и переключается на резервный статический узел при полном отказе DNS-инфраструктуры.

```nginx
http {
    upstream ha_backend {
        zone ha_zone 128k;

        # Список DNS-серверов: первичный, вторичный локальный кэш
        resolver 10.10.1.10 10.10.2.10 valid=10s ipv6=off;
        resolver_timeout 2s;

        # Основной динамический пул
        server app-cluster.internal.net:8080 resolve max_fails=2 fail_timeout=5s;

        # Аварийный статический бэкенд на случай недоступности динамического пула
        server 192.168.100.50:8080 backup;
    }

    server {
        listen 80;
        server_name core.internal;

        location / {
            proxy_pass http://ha_backend;
            proxy_next_upstream error timeout http_502 http_503 http_504;
        }
    }
}
```

## Диагностика и устранение неполадок

### Типичные ошибки и сбои

| Симптом / Ошибка | Первопричина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| `nginx: [emerg] "resolve" parameter is not supported in /etc/nginx/...` | Версия Nginx Open Source ниже 1.27.3. | `nginx -v` | Выполнить обновление Nginx до стабильной ветки 1.30.x+ или использовать обходной путь через переменную `$upstream_endpoint`. |
| `nginx: [emerg] resolving names at run time requires upstream to be in shared memory` | В блоке `upstream` с параметром `resolve` не объявлена директива `zone`. | Проверить блок `upstream` в файле конфигурации. | Добавить директиву `zone <имя_зоны> <размер>;` (например, `zone backend_zone 128k;`). |
| `nginx: [emerg] no resolver defined to resolve <hostname>` | Использован параметр `resolve` или переменная в `proxy_pass`, но директива `resolver` отсутствует. | `nginx -T \| grep resolver` | Задать директиву `resolver <ip_сервера>;` в блоке `http` или непосредственно внутри `upstream`. |
| Ошибки `502 Bad Gateway` в течение нескольких минут после смены IP бэкенда | Значение `valid` в `resolver` завышено или DNS-сервер отдает длинный TTL. | `dig <домен>` и проверка `valid` в `nginx.conf`. | Уменьшить параметр `valid` до `5s–10s` и сократить TTL в DNS-зоне. |
| Сообщения `... could not be resolved (3: Host not found)` в `error.log` | DNS-сервер возвращает ответ `NXDOMAIN` или указанный домен отсутствует в зоне. | `dig @<resolver_ip> <domain>` | Проверить запись в DNS-сервере, сетевую связность и настройки доменного суффикса. |
| Зависание обработки запросов и всплеск `upstream timed out` при сбоях DNS | Таймаут резолвера по умолчанию составляет 30 секунд. | Проверить `resolver_timeout` в конфиге. | Явно ограничить директиву `resolver_timeout 2s;` (максимум 5 секунд). |
| Отсутствие повторного использования соединений (высокий TIME_WAIT) | Применение устаревшего метода с переменной в `proxy_pass` вместо нативного `resolve`. | `ss -s` (число time-wait сокетов) | Перевести конфигурацию на Nginx 1.27.3+ с нативной директивой `upstream` и параметром `keepalive`. |
| Сброс сессионных данных клиентов | Модули сессионной привязки (`sticky`) теряют соответствие при динамическом перестроении списка пиров. | Проверить совместимость версии используемого модуля sticky. | Использовать нативную директиву `sticky` (поддерживается в Angie и Nginx 1.29.6+) или настраивать fallback на `ip_hash`. |

## Лучшие практики

### Производительность

1. **Расчет размера разделяемой памяти (`zone`):**
   - На каждый сервер в upstream-группе Nginx резервирует структуры хранения пира, счетчики метрик и таймеры (порядка 256–512 байт на узел).
   - Зона размером `64k` вмещает до 120–150 серверов.
   - Для надежной эксплуатации в динамических средах рекомендуется выделять `128k` на каждые 100 бэкендов во избежание ошибки переполнения памяти при частых ротациях IP.
2. **Оптимизация параметра `valid`:**
   - Не устанавливайте `valid` менее 2 секунд, чтобы не перегружать DNS-демон шквалом запросов от каждого воркера.
   - Оптимальный интервал для локальных сетей ЦОД составляет `5s–10s`.
3. **Отключение IPv6 резолвинга при отсутствии IPv6-маршрутизации:**
   - Всегда указывайте `ipv6=off` в директиве `resolver`, если инфраструктура функционирует исключительно на IPv4. Это сокращает объем DNS-трафика ровно вдвое и предотвращает ожидание таймаутов ответа на AAAA-запросы.
4. **Использование локального кэширующего демона:**
   - В качестве целевого IP в `resolver` предпочтительно указывать локальный интерфейс (`127.0.0.1` или `127.0.0.53` с Unbound, dnsmasq или systemd-resolved). Задержка разрешения через loopback составляет доли миллисекунды по сравнению с сетевыми запросами к удаленным серверам.
5. **Сохранение пула соединений (`keepalive`):**
   - Всегда совмещайте нативное динамическое разрешение (`resolve`) с директивой `keepalive` в `upstream`. Это исключает накладные расходы на TCP-handshake и TLS-handshake при каждом клиентском запросе.

### Безопасность

1. **Изоляция DNS-трафика:**
   - Никогда не используйте внешние публичные резолверы (`8.8.8.8`, `1.1.1.1`) для разрешения внутренних сервисов компании.
   - DNS-серверы должны быть изолированы во внутренней management-сети или на loopback-интерфейсе хоста.
2. **Защита от подмены DNS (Spoofing / Poisoning):**
   - Включайте валидацию DNSSEC на локальном кэширующем DNS-резолвере (Unbound/BIND9).
   - Разграничивайте зоны авторизации с помощью механизма Split-Horizon DNS (внутренние адреса доступны только внутренним балансировщикам).
3. **Контроль зацикливания и фиктивных доменов:**
   - Запрещайте регистрацию wildcard-записей для критических сервисов, чтобы предотвратить случайное перенаправление трафика на невалидные хосты.

### Эксплуатация и SRE

1. **Трассировка IP бэкендов в логах:**
   - Обязательно включайте переменную `$upstream_addr` в рабочий `log_format`. Это единственный способ ретроспективно определить, на какой именно IP-адрес был отправлен сбойный запрос при динамической ротации.
2. **Алертинг по метрикам доступности:**
   - Настраивайте триггеры мониторинга на появление кодов `502 Bad Gateway` и `504 Gateway Time-out` с группировкой по сервисам.
   - Отслеживайте метрику недоступности DNS-демона: если локальный резолвер не отвечает более `resolver_timeout`, балансировщик рискует остаться с устаревшими пирами.
3. **Резервирование через директиву `backup`:**
   - Для критически важных систем объявляйте резервный статический сервер с флагом `backup`. Если динамическое разрешение вернет пустой список или все динамические узлы откажут, трафик переключится на резервную площадку без прерывания обслуживания.
4. **Runbook при аварии DNS-сервера:**
   - При отказе внутреннего DNS Nginx продолжает передавать запросы на последние успешно разрешенные адреса. Не выполняйте `nginx -s reload` во время сбоя DNS, так как повторная инициализация завершится ошибкой и приведет к полной остановке маршрутизации.

### Примечания

- **История внедрения:** Параметр `resolve` и возможность размещения директивы `resolver` внутри блока `upstream` вошли в состав Nginx Open Source в версии 1.27.3 (ноябрь 2024 года). До этого функционал присутствовал исключительно в Nginx Plus и форке Angie.
- **Стандарты SRV:** При работе со Service Discovery через SRV-записи (Angie / Nginx Plus) убедитесь, что авторитативный сервер корректно генерирует поля `priority`, `weight` и `port` в соответствии со спецификацией [RFC 2782](https://datatracker.ietf.org/doc/html/rfc2782).
- **Размер зоны:** Минимальный поддерживаемый размер разделяемой памяти для директивы `zone` в большинстве дистрибутивов Linux составляет `32k` или `64k` (в зависимости от размера страницы памяти архитектуры).
