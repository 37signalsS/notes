# Динамическое разрешение DNS в Upstream — Nginx

## Определения

**Динамическое разрешение DNS (Dynamic DNS Resolution)** — механизм, позволяющий Nginx периодически обновлять IP-адреса бэкендов в блоке `upstream` на основе DNS-записей без перезагрузки конфигурации (`reload`). Используется в средах, где IP-адреса бэкендов меняются вследствие перераспределения нагрузки, масштабирования или сбоев.

**resolver** — директива, определяющая DNS-серверы, которые Nginx будет использовать для разрешения имён в рантайме. С версии Nginx 1.27.3 может располагаться непосредственно внутри блока `upstream`.

**resolve** — параметр директивы `server` в блоке `upstream`, указывающий Nginx периодически перечитывать DNS-запись для данного хоста и автоматически обновлять список серверов.

**service** — параметр директивы `server` (Angie/Nginx Plus), позволяющий разрешать имена через DNS SRV-записи с автоматическим получением портов, весов и приоритетов.

**zone** — директива, объявляющая участок разделяемой памяти (shared memory) для хранения состояния upstream-группы. Обязательна для работы параметра `resolve`, алгоритмов `least_conn` и sticky-сессий.

## Основные концепции и архитектура

### Проблема статического разрешения

По умолчанию Nginx разрешает доменные имена бэкендов **только один раз** в момент старта или `reload`. Если IP-адрес сервера изменится (например, при использовании виртуализации или динамической инфраструктуры), Nginx продолжит отправлять трафик на старый IP, что приведет к ошибкам (502/504) и простою сервиса.

Для сценариев, где IP-адреса меняются, требуется динамическое разрешение. Без него единственный способ обновления адресов — грациозная перезагрузка (`nginx -s reload`), что не гарантирует отсутствия потерь соединений.

### Жизненный цикл разрешения с параметром `resolve`

При использовании параметра `resolve` Nginx работает по следующему алгоритму:

1. **Инициализация:** при старте или `reload` происходит начальное разрешение домена.
2. **Фоновое обновление:** по истечении TTL DNS-записи (или значения `valid`) Nginx выполняет повторное разрешение в фоновом режиме.
3. **Обновление peer list:** при изменении IP-адресов список серверов в `upstream` обновляется атомарно без перезагрузки конфигурации.
4. **Graceful failover:** если разрешение не удалось, сервер помечается как `down`, и Nginx продолжает работу с оставшимися адресами.

### Версионные ограничения и возможности

До версии Nginx 1.27.3 параметр `resolve` был доступен только в коммерческих редакциях (Nginx Plus) и в Angie. В ноябре 2024 года функционал был перенесен в Nginx Open Source. Текущий стабильный релиз — 1.30.x, где динамическое разрешение работает нативно.

| Функция | Nginx OSS (< 1.27.3) | Nginx OSS (1.27.3+) | Angie (OSS) | Nginx Plus |
| :--- | :--- | :--- | :--- | :--- |
| **Параметр `resolve`** | Нет | **Да** | Да | Да |
| **Поддержка SRV (`service`)** | Нет | Нет | **Да** | Да |
| **`resolver` в `upstream`** | Нет | **Да** | Да | Да |
| **Авто-настройка из `resolv.conf`** | Нет | Нет | **Да (`resolver conf`)** | Нет |

### Зона разделяемой памяти (`zone`)

Директива `zone` определяет объем памяти, где хранится текущее состояние апстрима (список разрешенных IP, их статусы, веса, количество соединений). 

- **Рекомендуемый размер:** `64k`–`128k` достаточно для сотен бэкендов.
- **Важность:** без `zone` параметр `resolve` не работает — Nginx не сможет обновлять список серверов атомарно.
- **Ограничение:** если память в зоне закончится, Nginx не сможет добавлять новые адреса при изменении DNS.

### Кэширование и TTL

1. **Параметр `valid`** в директиве `resolver` переопределяет TTL от DNS-сервера. Если не указан, используется TTL из DNS-ответа. Для production-сред рекомендуется задавать значение меньше, чем реальный TTL в DNS, чтобы ускорить обнаружение изменений.
2. **`resolver_timeout`** — время ожидания ответа от DNS-сервера (по умолчанию 30с, рекомендуется снижать до 2–5с).
3. **NXDOMAIN и ошибки:** при получении NXDOMAIN Nginx повторяет попытку через 10 секунд. При постоянных ошибках сервер помечается как `down`.

## Практические сценарии

### 1. Нативная динамика (Nginx 1.27.3+ / Angie / Plus)

Наиболее эффективный метод. Поддерживает `keepalive` соединения и все алгоритмы балансировки. Резолвер указывается прямо внутри блока `upstream`.

```nginx
http {
    upstream app_servers {
        zone backend_zone 128k;

        resolver 127.0.0.11 valid=10s;
        resolver_timeout 5s;

        server backend.example.com resolve;
        
        # Angie/Plus: поддержка SRV-записей (Service Discovery)
        # server backend.local service=http resolve;
    }

    server {
        listen 80;
        location / {
            proxy_pass http://app_servers;
        }
    }
}
```

```bash
# Проверка синтаксиса перед применением
nginx -t
# → nginx: configuration file /etc/nginx/nginx.conf test is successful
```

### 2. Обходной путь через переменные (Nginx OSS 1.26 и ниже)

Если обновление до 1.27.3 невозможно, используется трюк с переменной в `proxy_pass`. Этот метод игнорирует настройки блока `upstream` и не поддерживает `keepalive` к бэкендам.

```nginx
server {
    listen 80;
    resolver 8.8.8.8 valid=30s;
    
    set $backend_host "api.external-service.com";

    location / {
        proxy_pass http://$backend_host:8080;
    }
}
```

```bash
# Проверка, что Nginx корректно разрешает домен
dig @8.8.8.8 api.external-service.com
# → ответ с IP-адресом и TTL
```

**Особенности метода:**
- **Плюсы:** работает во всех версиях Nginx OSS без пересборки.
- **Минусы:** не поддерживаются алгоритмы балансировки (`least_conn`, `random`), sticky-сессии и `keepalive` к бэкендам. При каждом запросе может происходить DNS-запрос, если TTL мал.

## Операции и команды

### Валидация конфигурации

Перед применением конфигурации с динамическим DNS необходимо убедиться, что директива `zone` объявлена и `resolver` доступен.

```bash
# Проверка синтаксиса
nginx -t

# Просмотр объявления zone и resolver в конфигурации
nginx -T 2>/dev/null | grep -E "zone|resolver|resolve"
# → upstream app_servers { zone backend_zone 128k; resolver 127.0.0.1 valid=10s; ... }
```

### Диагностика DNS

```bash
# Проверка разрешения домена через системный резолвер
dig backend.example.com @127.0.0.1 +short
# → 10.0.0.1

# Проверка TTL записи
dig backend.example.com @127.0.0.1
# → ANSWER SECTION с TTL

# Статистика системного резолвера (systemd-resolved)
systemd-resolve --statistics
```

### Проверка состояния upstream

```bash
# Подсчет ошибок 502/504 по бэкендам (требуется $upstream_addr в логе)
awk '{print $NF}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
# → 152 10.0.0.1:8080
# → 38  10.0.0.2:8080

# Мониторинг соединений к бэкендам
ss -tniop | grep nginx | grep 10.0.0.1
# → established соединения с keepalive
```

### Логирование upstream-переменных

Для трассировки работы динамического DNS добавьте в `log_format` upstream-переменные:

```nginx
log_format upstream_debug '$remote_addr - [$time_local] '
                          '$upstream_addr $upstream_status $upstream_response_time';

server {
    access_log /var/log/nginx/upstream_access.log upstream_debug;
}
```

```bash
# Поиск ошибок upstream в логе
grep "502\|504" /var/log/nginx/upstream_access.log | tail -20
# → IP бэкенда, который возвращает ошибку
```

## Диагностика и устранение неполадок

### Типичные ошибки

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `nginx: [emerg] "resolve" parameter is not supported` | Версия Nginx < 1.27.3 | Обновите Nginx или используйте обходной путь через переменные. |
| `resolving names at run time requires upstream to be in shared memory` | Отсутствует директива `zone` | Добавьте `zone upstream_zone 64k;` в блок `upstream`. |
| `no resolver defined to resolve` | Директива `resolver` не объявлена | Добавьте `resolver` в блок `http` или `upstream`. |
| 502 при изменении DNS | DNS-кэш не обновлен или TTL слишком большой | Уменьшите `valid` в `resolver` или проверьте работу DNS-сервера. |
| Постоянные 502 после изменения DNS | NXDOMAIN или таймаут резолвера | Проверьте доступность DNS-сервера (`dig`, `resolver_timeout`). |
| Потеря sticky-сессий при динамическом DNS | `resolve` несовместим с某些 sticky-модулями | Проверьте документацию модуля sticky. |

### Диагностические команды

```bash
# Проверка, что resolver работает
nginx -T 2>/dev/null | grep -A2 "resolver"
# → resolver 127.0.0.1 valid=10s;

# Проверка DNS-записи в реальном времени
watch -n 5 "dig +short backend.example.com @127.0.0.1"

# Проверка времени ответа DNS-сервера
dig @127.0.0.1 backend.example.com | grep "Query time"
# → Query time: 2 msec

# Анализ логов на предмет ошибок upstream
grep -E "upstream.*(502|504|timeout)" /var/log/nginx/error.log
```

## Лучшие практики

### Производительность

1. **Используйте `zone` достаточного размера:** выделяйте `128k` на каждые ~100 серверов в upstream. Мало памяти приводит к отказу от обновления DNS.
2. **Настраивайте `valid` осознанно:** значение должно быть меньше реального TTL в DNS, но не менее 5–10 секунд, чтобы избежать избыточных запросов.
3. **Размещайте resolver близко к серверу:** используйте локальный кеширующий резолвер (например, `systemd-resolved` или `dnsmasq`) вместо публичных DNS, чтобы снизить задержку.
4. **Комбинируйте с `keepalive`:** динамическое DNS работает с `keepalive` только при использовании нативного метода (`resolve`), а не через переменную `proxy_pass`.

### Безопасность

1. **Ограничьте доступ к DNS-серверам:** не используйте публичные резолверы без фильтрации. В production-средах резолвер должен находиться за firewall.
2. **Используйте внутренние DNS-серверы:** для внутренних сервисов настраивайте авторитативные зоны и Split-horizon DNS.
3. **Валидируйте ответы:** включите DNSSEC на DNS-сервере, если инфраструктура требует проверки подлинности записей.
4. **Мониторьте NXDOMAIN:** частые NXDOMAIN-ответы могут указывать на misconfiguration или атаку на DNS.

### Эксплуатация (SRE)

1. **Логируйте upstream-переменные:** добавьте `$upstream_addr`, `$upstream_status`, `$upstream_response_time` в `log_format` для возможности трассировки запросов через динамические адреса.
2. **Настройте алертинг:** оповещайте при превышении доли 502/504 ошибок, которые могут возникать при сбоях DNS.
3. **Тестируйте failover:** периодически проверяйте, что Nginx корректно переключается на backup-серверы при недоступности первичных адресов.
4. **Мониторьте зону `upstream`:** при приближении к лимиту shared memory увеличьте размер `zone`.
5. **Документируйте TTL:** поддерживайте актуальные записи о TTL DNS-записей и значениях `valid` в конфигурации Nginx в runbook.
6. **Проверяйте резолвер:** включайте в регулярные проверки доступность DNS-серверов, указанных в `resolver`.

### Примечания

- Версия Nginx 1.27.3 (ноябрь 2024) является mainline-веткой. Для production рекомендуется стабильная версия 1.30.x, где динамическое разрешение DNS присутствует и поддерживается.
- Параметр `resolve` требует, чтобы `resolver` был объявлен на уровне `http` или внутри соответствующего `upstream`. Без этого директивы не работают.
- При использовании SRV-записей (`service`) убедитесь, что DNS-сервер возвращает корректные приоритеты и веса согласно RFC 2782.
