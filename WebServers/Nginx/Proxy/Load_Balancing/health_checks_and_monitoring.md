# Nginx Load Balancing: Health Checks и Мониторинг

### Проверки состояния (Health Checks)

#### Пассивная проверка

Эта проверка встроена в Nginx и работает по умолчанию. Если при попытке отправить запрос на бэкенд Nginx не может установить соединение (получает ошибку `Connection refused` или `Connection timed out`), он считает эту попытку неудачной.

-   После достижения `max_fails` (по умолчанию 1) неудачных попыток в течение `fail_timeout` (по умолчанию 10с), Nginx временно перестает отправлять запросы на этот сервер.
-   **Ограничение:** Эта проверка реагирует только на полную недоступность сервера на сетевом уровне. Она не спасет, если сервер "завис", отвечает медленно или возвращает ошибки `5xx`. Типы ошибок, которые учитываются, определяются директивой `proxy_next_upstream`.

#### Активная проверка

Для полноценной проверки состояния приложения (например, чтобы убедиться, что оно отвечает кодом `200 OK`, а не `503 Service Unavailable`) требуются расширенные возможности.

-   **Nginx Plus / Angie Pro:** В платных версиях есть встроенный механизм активных health checks (`health_check`).
-   **Nginx Open Source:** Для бесплатной версии Nginx можно использовать сторонний модуль, например, [nginx_upstream_check_module](https://github.com/yaoweibin/nginx_upstream_check_module).

Этот модуль позволяет настроить Nginx так, чтобы он периодически отправлял на бэкенды специальные запросы (например, `GET /status`) и анализировал ответ. Если ответ не соответствует ожиданиям (например, код ответа не `200`), сервер помечается как нерабочий и исключается из балансировки до тех пор, пока снова не начнет проходить проверку.

**Пример конфигурации с `check` модулем:**

```nginx
upstream backend {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;

    # Директива, включающая проверку
    # Проверять каждые 3с, 2 удачные попытки для возвращения в строй, 3 неудачные для исключения
    check interval=3000 rise=2 fall=3 timeout=1000 type=http;
    # URL для проверки
    check_http_send "GET /status HTTP/1.0

";
    # Ожидаемый код ответа
    check_http_expect_alive http_2xx;
}
```

### Мониторинг Upstream

Состояние `upstream` серверов можно отслеживать через API-интерфейсы (в Nginx Plus / Angie) или с помощью сторонних инструментов мониторинга, анализируя логирование и метрики, которые отдает, например, [nginx-prometheus-exporter](../../Prometheus/exporters.md#nginx-prometheus-exporter).

### Проверка

Откройте браузер и перейдите по адресу вашего сервера (`http://<your_server_ip>`) или выполните команду в терминале:

```bash
curl http://127.0.0.1
```

При каждом обновлении страницы или повторном вызове `curl` вы должны видеть ответы от разных экземпляров Apache ("Response from Apache on port 8080", "Response from Apache on port 8081" и т.d.), так как Nginx по умолчанию использует алгоритм балансировки Round Robin.
