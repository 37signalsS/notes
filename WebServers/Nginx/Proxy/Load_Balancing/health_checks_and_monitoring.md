# Проверки состояния и мониторинг в Nginx Load Balancing

## Определения

**Проверка состояния (Health Check)** — механизм, позволяющий балансировщику нагрузки определять доступность бэкенд-серверов и исключать неисправные узлы из ротации. Это фундамент высокой доступности (HA).

**Пассивная проверка (Passive Health Check)** — мониторинг на основе анализа ответов бэкенда на реальные запросы пользователей. Выполняется «бесплатно» в процессе обычной работы прокси.

**Активная проверка (Active Health Check)** — периодическая отправка специальных запросов (проб) к бэкендам в фоновом режиме, независимо от клиентского трафика.

**Плавный старт (Slow Start)** — постепенное наращивание нагрузки на сервер, который только что вернулся в строй после сбоя или профилактики.

## Основные концепции

### Пассивная проверка (Nginx OSS / Plus / Angie)

Встроена во все версии и активна по умолчанию. Настраивается через параметры директивы `server` в блоке `upstream`.

- **`max_fails=N`**: Количество неудачных попыток за период времени, после которых сервер помечается как недоступный (по умолчанию 1).
- **`fail_timeout=T`**: Время, в течение которого должны произойти `max_fails`, и время, на которое сервер исключается из балансировки (по умолчанию 10с).

**Механизм `proxy_next_upstream`**:
Определяет, какие именно события считать «неудачной попыткой» для переключения на следующий сервер.
```nginx
location / {
    proxy_pass http://backend;
    # Передать запрос дальше при ошибках, таймаутах или 5xx кодах
    proxy_next_upstream error timeout http_502 http_503 http_504;
}
```

### Активная проверка

Позволяет обнаружить сбой до того, как его заметит первый клиент.

| Решение | Метод | Особенности |
| :--- | :--- | :--- |
| **Nginx OSS** | Сторонний модуль | Требует `nginx_upstream_check_module` и пересборки. |
| **Angie OSS** | Директива `check` | Встроено. Поддерживает HTTP, TCP, MySQL, FastCGI и др. |
| **Nginx Plus** | Директива `health_check` | Нативная поддержка. Настраивается в блоке `location`. |
| **Angie PRO** | Директива `upstream_probe` | Полный аналог Plus-функционала с расширенными тестами. |

## Практические сценарии

### 1. Активная HTTP-проверка в Angie OSS

В Angie модуль активных проверок включен по умолчанию. Проверка настраивается непосредственно в блоке `upstream`.

```nginx
upstream backend_cluster {
    zone backend_zone 128k; 
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;

    # Интервал 5с, 2 успеха для активации, 3 сбоя для исключения
    check interval=5000 rise=2 fall=3 timeout=2000 type=http;
    
    # Настройка параметров запроса
    check_http_send "GET /health HTTP/1.0\r\nHost: example.com\r\n\r\n";
    check_http_expect_alive http_2xx http_3xx;
}
```

### 2. Плавный старт (Angie / Nginx Plus)

Параметр `slow_start` предотвращает перегрузку сервера («шоковый старт»), который только что восстановился, постепенно увеличивая его вес от 0 до номинального.

```nginx
upstream app_pool {
    zone app_pool_zone 64k;
    # Вес сервера будет расти линейно в течение 30 секунд
    server 10.0.0.1:8080 slow_start=30s;
    server 10.0.0.2:8080 slow_start=30s;
}
```

### 3. Мониторинг через API (Angie / Plus)

Angie предоставляет встроенный REST API для получения детальных метрик в формате JSON.

```nginx
server {
    listen 8080;
    
    # Визуальная панель мониторинга (Console Light в Angie)
    location = /console.html {
        root /usr/share/angie-console-light;
    }

    # Эндпоинт для сбора данных (API)
    location /api/ {
        api /status/; 
        allow 127.0.0.1;
        deny all;
    }
}
```

## Технические нюансы

### Зоны статуса (`status_zone`)
В Angie и Nginx Plus директива `status_zone` активирует сбор детальной статистики для конкретных блоков. Без нее API будет показывать пустые значения.
```nginx
server {
    listen 80;
    status_zone site_frontend; # Метрики для виртуального хоста

    location /api/ {
        status_zone api_backend; # Метрики для пути
        proxy_pass http://api_upstream;
    }
}
```

### Особенности `proxy_next_upstream`
- **Неидемпотентные запросы:** По умолчанию Nginx не повторяет `POST/LOCK/PATCH` запросы, если часть данных уже была отправлена. Если это необходимо (и безопасно), добавьте параметр `non_idempotent`.
- **Таймауты:** Используйте `proxy_next_upstream_timeout` и `proxy_next_upstream_tries`, чтобы ограничить время поиска живого бэкенда и не создавать «лавину» запросов.

### Сравнение мониторинга

| Метрика | `stub_status` (OSS) | API (Angie/Plus) |
| :--- | :--- | :--- |
| **Активные соединения** | Да | Да |
| **Детализация по Upstream** | Нет | **Да** (IP, время ответа, ошибки) |
| **Детализация по Хостам** | Нет | **Да** (трафик, 2xx/4xx/5xx) |
| **Формат данных** | Текст (7 строк) | **JSON** (сотни метрик) |
