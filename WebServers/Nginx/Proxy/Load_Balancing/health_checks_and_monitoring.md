# Проверки состояния и мониторинг балансировщика Nginx

## Определения

**Проверка состояния (Health Check)** — механизм, позволяющий балансировщику нагрузки определять доступность бэкенд-серверов и исключать неисправные узлы из ротации. Это фундамент высокой доступности (HA) кластера.

**Пассивная проверка (Passive Health Check)** — мониторинг на основе анализа ответов бэкенда на реальные запросы пользователей. Выполняется «бесплатно» в процессе обычной работы прокси, без дополнительного сетевого трафика.

**Активная проверка (Active Health Check)** — периодическая отправка специальных запросов (проб) к бэкендам в фоновом режиме, независимо от клиентского трафика. Позволяет обнаружить сбой до того, как его заметит первый клиент.

**Плавный старт (Slow Start)** — постепенное наращивание нагрузки на сервер, который только что вернулся в строй после сбоя или профилактики. Предотвращает «шоковый старт», при котором холодный бэкенд получает полную нагрузку сразу.

**Upstream** — группа бэкенд-серверов, объединенных в логический пул для балансировки.

**Проба (Probe)** — отдельный запрос активной проверки, отправляемый на health-эндпоинт бэкенда.

**Graceful Degradation** — режим работы, при котором система продолжает функционировать с ограниченной производительностью при отказе части компонентов.

## Основные концепции и архитектура

### Пассивная проверка (Passive Health Check)

Встроена во все версии Nginx и Angie и активна по умолчанию. Настраивается через параметры директивы `server` в блоке `upstream`. Механизм работает на уровне обработки реальных запросов: Nginx считает попытку неудачной, если бэкенд вернул ошибку, превысил таймаут или был недоступен на уровне TCP.

**Параметры:**

- **`max_fails=N`**: количество неудачных попыток за период `fail_timeout`, после которых сервер помечается как недоступный (по умолчанию `1`).
- **`fail_timeout=T`**: время, в течение которого должны произойти `max_fails`, и время, на которое сервер исключается из балансировки (по умолчанию `10s`).

**Механизм `proxy_next_upstream`**:
Определяет, какие события считать «неудачной попыткой» для переключения на следующий сервер. Если все бэкенды в upstream недоступны, Nginx вернет клиенту ошибку (`502 Bad Gateway` или `504 Gateway Timeout`).

```nginx
location / {
    proxy_pass http://backend;
    proxy_next_upstream error timeout invalid_header http_502 http_503 http_504;
    proxy_next_upstream_tries 3;
    proxy_next_upstream_timeout 15s;
}
```

**Жизненный цикл запроса с пассивными проверками:**

1. Клиент отправляет запрос Nginx.
2. Nginx выбирает бэкенд из upstream по алгоритму балансировки.
3. Если бэкенд отвечает успешно — запрос завершен.
4. Если бэкенд возвращает ошибку, таймаут или закрывает соединение — Nginx считает это неудачей.
5. После `max_fails` неудач за `fail_timeout` сервер временно исключается из ротации.
6. Через `fail_timeout` Nginx пробует вернуть сервер в строй, отправив ему тестовый запрос.

### Активная проверка (Active Health Check)

Позволяет обнаружить сбой до того, как его заметит первый клиент. Отправляет специальные запросы (пробы) к бэкендам независимо от клиентского трафика.

| Решение | Метод | Особенности |
| :--- | :--- | :--- |
| **Nginx OSS** | Сторонний модуль | Требует `nginx_upstream_check_module` и пересборки. |
| **Angie OSS** | Директива `check` | Встроено. Поддерживает HTTP, TCP, MySQL, FastCGI и др. |
| **Nginx Plus** | Директива `health_check` | Нативная поддержка. Настраивается в блоке `location`. |
| **Angie PRO** | Директива `upstream_probe` | Полный аналог Plus-функционала с расширенными тестами. |

**Параметры активной проверки в Angie OSS:**

- **`interval=T`**: интервал между проверками в миллисекундах (например, `5000`).
- **`rise=N`**: количество успешных проверок подряд для перевода сервера в статус «доступен» (рекомендуется `>=2` для избежания флапинга).
- **`fall=N`**: количество неудачных проверок подряд для перевода сервера в статус «недоступен» (обычно `3`).
- **`timeout=T`**: таймаут ожидания ответа пробы в миллисекундах.
- **`type=TYPE`**: тип проверки (`http`, `tcp`, `mysql`, `fastcgi`).

**Особенности неидемпотентных запросов:**
По умолчанию Nginx не повторяет `POST`, `LOCK`, `PATCH` запросы при переключении бэкенда, если часть данных уже была отправлена. Если это необходимо (и безопасно для бизнес-логики), добавьте параметр `non_idempotent` в `proxy_next_upstream`.

```nginx
proxy_next_upstream error timeout http_502 http_503 http_504 non_idempotent;
```

## Практические сценарии

### 1. Активная HTTP-проверка в Angie OSS

В Angie модуль активных проверок включен по умолчанию. Проверка настраивается непосредственно в блоке `upstream`.

```nginx
upstream backend_cluster {
    zone backend_zone 128k;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;

    # Интервал 5с, 2 успеха для активации, 3 сбоя для исключения
    check interval=5000 rise=2 fall=3 timeout=2000 type=http;

    # Настройка параметров запроса пробы
    check_http_send "GET /health HTTP/1.0\r\nHost: example.com\r\n\r\n";
    check_http_expect_alive http_2xx http_3xx;
}
```

### 2. TCP-проверка (Angie OSS)

Для сервисов без HTTP-эндпоинта (базы данных, кэш, MQ) используйте TCP-проверку:

```nginx
upstream redis_cluster {
    zone redis_zone 64k;
    server 10.0.0.10:6379;
    server 10.0.0.11:6379;

    check interval=3000 rise=2 fall=3 timeout=1000 type=tcp;
}
```

### 3. Плавный старт (Angie / Nginx Plus)

Параметр `slow_start` предотвращает перегрузку сервера, который только что восстановился, постепенно увеличивая его вес от 0 до номинального в течение указанного времени.

```nginx
upstream app_pool {
    zone app_pool_zone 64k;
    # Вес сервера будет расти линейно в течение 30 секунд
    server 10.0.0.1:8080 slow_start=30s;
    server 10.0.0.2:8080 slow_start=30s;
}
```

**Рекомендация:** используйте `slow_start` для приложений с тяжелым прогреванием: JIT-компиляция, заполнение connection pool, прогрев кэша.

### 4. Мониторинг через API (Angie / Plus)

Angie предоставляет встроенный REST API для получения детальных метрик в формате JSON.

```nginx
server {
    listen 8080;

    # Визуальная панель мониторинга (Console Light в Angie)
    location = /console.html {
        root /usr/share/angie-console-light;
    }

    # Эндпоинт для сбора данных (API)
    location /api/ {
        api /status/;
        allow 127.0.0.1;
        deny all;
    }
}
```

### 5. Мониторинг через `stub_status` (Nginx OSS)

В стандартном Nginx OSS доступен упрощенный эндпоинт `stub_status`, показывающий общую статистику без детализации по upstream.

```nginx
server {
    listen 8080;
    location /nginx_status {
        stub_status;
        allow 127.0.0.1;
        deny all;
    }
}
```

### 6. Зоны статуса (`status_zone`)

В Angie и Nginx Plus директива `status_zone` активирует сбор детальной статистики для конкретных блоков. Без нее API будет показывать пустые значения для этих блоков.

```nginx
server {
    listen 80;
    status_zone site_frontend; # Метрики для виртуального хоста

    location /api/ {
        status_zone api_backend; # Метрики для пути
        proxy_pass http://api_upstream;
    }
}
```

### Сравнение методов мониторинга

| Метрика | `stub_status` (OSS) | API (Angie/Plus) |
| :--- | :--- | :--- |
| **Активные соединения** | Да | Да |
| **Детализация по Upstream** | Нет | **Да** (IP, время ответа, ошибки) |
| **Детализация по Хостам** | Нет | **Да** (трафик, 2xx/4xx/5xx) |
| **Формат данных** | Текст (7 строк) | **JSON** (сотни метрик) |

## Операции и команды

### Валидация конфигурации

Перед применением изменений всегда проверяйте синтаксис:

```bash
nginx -t
# → nginx: configuration file /etc/nginx/nginx.conf test is successful
```

### Проверка статуса upstream через API (Angie / Plus)

```bash
curl -s http://127.0.0.1:8080/api/6/http/upstreams/backend_cluster
# → JSON с метриками по каждому бэкенду: active connections, responses, 5xx errors
```

### Проверка `stub_status` (Nginx OSS)

```bash
curl -s http://127.0.0.1:8080/nginx_status
# → Active connections: 2
# → server accepts handled requests
# → 100 100 200
# → Reading: 0 Writing: 1 Waiting: 1
```

### Диагностика upstream через переменные в логах

Добавьте в `log_format` upstream-переменные для трассировки:

```nginx
log_format upstream_debug '$remote_addr - [$time_local] '
                          '$upstream_addr $upstream_status $upstream_response_time';
```

Пример использования:

```bash
# Поиск ошибок upstream в логе
grep -E "upstream|502|504" /var/log/nginx/error.log | tail -n 50
```

### Анализ распределения запросов по бэкендам

```bash
awk '{print $NF}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -n 10
# → 1500 10.0.0.1:8080
# → 1480 10.0.0.2:8080
```

### Проверка времени ответа бэкендов

```bash
awk '$upstream_response_time > 1.0 {print $0}' /var/log/nginx/access.log | head -n 20
```

### Проверка keepalive-соединений upstream

```bash
ss -tnp | grep nginx | grep :8080
# → ESTAB 0 0 10.0.0.5:54322 10.0.0.1:8080 users:(("nginx",pid=1234,fd=5))
```

### Тестирование health-эндпоинта бэкенда

```bash
curl -I http://10.0.0.1:8080/health
# → HTTP/1.1 200 OK
```

### Проверка переключения при отключении бэкенда (failover test)

```bash
systemctl stop app@node1
curl -I http://app.example.com/health
# → HTTP/1.1 200 OK
# Проверить в логах, что запрос ушел на оставшиеся узлы
```

## Диагностика и устранение неполадок

### Типичные ошибки

| Симптом | Причина | Решение | Диагностика |
| :--- | :--- | :--- | :--- |
| Сервер постоянно переключается между доступным/недоступным (flapping) | `fail_timeout` слишком мал, health endpoint нестабилен | Увеличить `fail_timeout`, стабилизировать endpoint | `grep` в `error.log` за циклические записи `mark down/up` |
| Активные проверки не отправляются | Отсутствует `zone`, ошибка синтаксиса | Добавить `zone`, проверить `nginx -t` | `nginx -t`, `error.log` |
| API возвращает пустые данные по upstream | Отсутствует `status_zone` в `server`/`location` | Добавить `status_zone` | Запрос к API, проверка конфигурации |
| `502 Bad Gateway` после возврата сервера из slow_start | `slow_start` слишком мал, приложение не прогрузилось | Увеличить `slow_start` по времени warmup | Мониторинг 502 после возврата сервера |
| `502 Bad Gateway` на отдельных запросах | Один бэкенд недоступен, исчерпан `max_conns` или `fail_timeout` | Проверить `error.log`; убедиться, что флаг `down` не установлен вручную | `grep "502" /var/log/nginx/error.log` |
| `504 Gateway Timeout` | Бэкенд не ответил за `proxy_read_timeout` | Увеличить `proxy_read_timeout`; проверить нагрузку на бэкенд; проверить сетевую доступность | `curl -w "%{time_total}" http://backend/health` |
| POST запросы падают при retry | `proxy_next_upstream` повторяет неидемпотентные запросы | Добавить `non_idempotent` или исключить `POST` из параметров retry | `error.log` с предупреждениями о неидемпотентных запросах |
| Дисбаланс нагрузки | Неправильный `weight`, `ip_hash` с NAT, `least_conn` с быстрыми ошибками | Проверить веса; для NAT использовать `hash` вместо `ip_hash`; исключить неработающие бэкенды через `max_fails` | Анализ распределения запросов по бэкендам |

### Диагностические команды

```bash
# Поиск ошибок upstream в логе
grep -E "upstream|502|504" /var/log/nginx/error.log | tail -n 50

# Анализ распределения запросов по бэкендам
awk '{print $NF}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -n 10

# Проверка времени ответа бэкендов
awk '$upstream_response_time > 1.0 {print $0}' /var/log/nginx/access.log | head -n 20

# Поиск записей о слишком больших заголовках от бэкенда
grep "upstream sent too big header" /var/log/nginx/error.log

# Проверка переполнения временными файлами при буферизации
grep "buffered to a temporary file" /var/log/nginx/error.log
```

## Лучшие практики

### Производительность

1. **Используйте `zone` для всех upstream-групп с sticky-сессиями или `least_conn`.** Без `zone` Nginx не может сохранять состояние соединений между рабочими процессами, что приводит к некорректной балансировке.
2. **Включайте `keepalive` в `upstream` для высоконагруженных HTTP-сервисов.** Без keepalive Nginx использует HTTP/1.0 и закрывает соединение после каждого запроса, что создает избыточную нагрузку на CPU и порты.
3. **Используйте `hash ... consistent` для кэширующих прокси вместо `ip_hash`.** Консистентное хеширование минимизирует перераспределение ключей при изменении состава бэкендов.

### Безопасность

1. **Никогда не полагайтесь на балансировку как на механизм безопасности.** Для контроля доступа используйте `internal`, `auth_request` или WAF.
2. **Явно указывайте `max_fails` и `fail_timeout`** для каждого сервера. Без этих параметров Nginx по умолчанию использует `max_fails=1` и `fail_timeout=10s`, что может привести к частым переключениям при временных сбоях.
3. **Не используйте `backup`-серверы для активной нагрузки.** Они предназначены только для аварийного переключения и имеют более низкий приоритет.
4. **Изолируйте management-интерфейсы.** Если используете `status_zone` (Angie/Nginx Plus) или `stub_status`, ограничьте доступ к ним firewall-правилами или директивами `allow/deny`.
5. **Скрывайте служебные заголовки:** используйте `proxy_hide_header` для `Server` и `X-Powered-By`, чтобы снизить поверхность атаки.

### Эксплуатация (SRE)

1. **Логирование upstream-переменных:** Добавьте в `log_format` переменные `$upstream_addr`, `$upstream_status`, `$upstream_response_time` для трассировки запросов:

    ```nginx
    log_format upstream_debug '$remote_addr - [$time_local] '
                              '$upstream_addr $upstream_status $upstream_response_time';
    ```

2. **Мониторинг дисбаланса:** Регулярно проверяйте распределение запросов по бэкендам. Дисбаланс более чем на 20% при использовании Round Robin или `least_conn` указывает на проблему с весами или медленный бэкенд.
3. **Алертинг на 502/504:** Настройте оповещение на ошибки `502 Bad Gateway` и `504 Gateway Timeout` в `error.log`. Частые 502 указывают на падение бэкендов; частые 504 — на таймауты или перегрузку.
4. **Тестирование failover:** Периодически проверяйте, что `proxy_next_upstream` корректно переключает трафик при отключении одного из бэкендов:

    ```bash
    systemctl stop app@node1
    curl -I http://app.example.com/health
    # Проверить, что запросы ушли на оставшиеся узлы
    ```

5. **Резервное копирование конфигурации:** Перед изменением алгоритмов или параметров upstream создайте бэкап и проверяйте конфигурацию через `nginx -t`.

6. **Алертинг на флапинг бэкендов:** Настройте оповещение, если сервер переключается между доступным/недоступным чаще одного раза в 5 минут. Флапинг часто указывает на проблему с самим бэкендом или сетью.
7. **Runbook для массового отказа:** Подготовьте инструкцию на случай отказа нескольких бэкендов одновременно: порядок отключения `max_fails`, временное переключение на `backup`-серверы, эскалация.
