# Проверки состояния и мониторинг в Nginx Load Balancing

## Определения

**Health Check (проверка состояния)** — механизм, позволяющий балансировщику нагрузки определять доступность и работоспособность бэкенд-серверов и временно исключать нерабочие узлы из ротации. Общие принципы отказоустойчивости описаны в разделе [Кластеризация и балансировка для HA](../../../Concepts/High_Availability/ha_clustering_and_load_balancing.md).

**Пассивная проверка (passive health check)** — метод мониторинга, основанный на анализе ответов бэкенда на реальные запросы клиентов.

**Активная проверка (active health check)** — метод мониторинга, при котором балансировщик периодически отправляет специальные запросы (пробы) к бэкендам независимо от клиентского трафика.

## Основные концепции

### Пассивная проверка

Механизм пассивной проверки встроен в Nginx и активен по умолчанию. Если при попытке отправить запрос на бэкенд Nginx получает сетевую ошибку (например, `Connection refused` или `Connection timed out`), он фиксирует неудачную попытку.

- При достижении лимита `max_fails` (по умолчанию 1) в течение периода `fail_timeout` (по умолчанию 10 секунд), Nginx временно прекращает отправку запросов на данный сервер.
- **Ограничения**: проверка реагирует только на сетевую доступность. Она не эффективна, если приложение работает, но возвращает ошибки уровня приложения (например, HTTP 500) или отвечает слишком медленно.

Для более гибкой обработки ошибок используется директива `proxy_next_upstream`. Она определяет условия, при которых запрос будет передан следующему серверу в группе upstream. Возможные значения: `error`, `timeout`, `http_500`, `http_502`, `http_503`, `http_504`, `invalid_header`.

### Активная проверка

Активные проверки позволяют контролировать состояние приложения более детально (например, проверять код ответа 200 OK на специфическом эндпоинте).

- **Nginx Plus и Angie Pro**: предоставляют встроенную директиву `health_check` для настройки периодических проб. Подробнее о форке: [Обзор Angie](../../../Angie/angie_overview.md).
- **Nginx Open Source**: требует использования сторонних модулей, таких как `nginx_upstream_check_module`.

Активный мониторинг позволяет выявлять проблемы на уровне бизнес-логики до того, как клиенты столкнутся с ошибками.

## Практические сценарии

### Настройка активной проверки с модулем check

Пример конфигурации для стороннего модуля `check`:

```nginx
upstream backend {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;

    # Интервал 3с, 2 успеха для активации, 3 сбоя для исключения, таймаут 1с
    check interval=3000 rise=2 fall=3 timeout=1000 type=http;
    
    # Запрос для проверки состояния
    check_http_send "GET /status HTTP/1.0\r\n\r\n";
    
    # Ожидаемый статус ответа
    check_http_expect_alive http_2xx;
}
```

**Параметры директивы check:**

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| `interval` | 3000 | Интервал между проверками в миллисекундах |
| `rise` | 2 | Порог успешных проверок для возврата в ротацию |
| `fall` | 3 | Порог неудачных проверок для исключения сервера |
| `timeout` | 1000 | Время ожидания ответа в миллисекундах |
| `type` | http | Протокол проверки (HTTP, TCP, MySQL и др.) |

### Мониторинг upstream-серверов

Сбор метрик о состоянии бэкендов может выполняться следующими способами:

- **Nginx Plus / Angie**: использование `status_zone` и встроенного API для получения данных в формате JSON.
- **Prometheus**: применение [nginx-prometheus-exporter](../../../../Prometheus/Exporters/other_exporters.md) для извлечения метрик из `stub_status` или логов.
- **Лог-анализ**: мониторинг переменной `$upstream_status` в логах доступа для выявления проблемных узлов.

### Проверка распределения трафика

Для подтверждения работы балансировки и механизмов исключения узлов можно использовать `curl`:

```bash
# Выполнение серии запросов для проверки ротации
for i in {1..10}; do curl -s http://127.0.0.1 | grep "Server ID"; done
```

Если один из серверов помечен как `unhealthy`, в выводе будут присутствовать только идентификаторы работающих узлов.
