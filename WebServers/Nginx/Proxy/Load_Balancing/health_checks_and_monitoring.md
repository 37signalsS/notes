# Проверки состояния и мониторинг в Nginx Load Balancing

## Определения

**Health Check (проверка состояния)** — механизм, позволяющий балансировщику нагрузки определять доступность и работоспособность бэкенд-серверов и временно исключать нерабочие из ротации.

Существует два типа проверок:
- **Пассивная (passive)** — реакция на ошибки при обработке реальных запросов клиентов
- **Активная (active)** — периодическая отправка специальных probe-запросов к бэкендам независимо от клиентского трафика

## Базовые понятия

### Пассивная проверка

Встроена в Nginx и работает по умолчанию. Если при попытке отправить запрос на бэкенд Nginx не может установить соединение (получает ошибку `Connection refused` или `Connection timed out`), он считает эту попытку неудачной.

- После достижения `max_fails` (по умолчанию 1) неудачных попыток в течение `fail_timeout` (по умолчанию 10 с), Nginx временно перестает отправлять запросы на этот сервер.
- **Ограничение:** эта проверка реагирует только на полную недоступность сервера на сетевом уровне. Она не спасёт, если сервер «завис», отвечает медленно или возвращает ошибки `5xx`.
- **`proxy_next_upstream`:** директива, определяющая, в каких случаях запрос будет передан на следующий сервер upstream-группы. По умолчанию срабатывает на `error` и `timeout`. Можно расширить: `http_500`, `http_502`, `http_503`, `http_504`, `invalid_header`, `non_idempotent`.

### Активная проверка

Для полноценной проверки состояния приложения (например, чтобы убедиться, что оно отвечает кодом `200 OK`, а не `503 Service Unavailable`) требуются расширенные возможности.

- **Nginx Plus / Angie Pro:** в платных версиях есть встроенный механизм активных health checks (`health_check`).
- **Nginx Open Source:** для бесплатной версии Nginx можно использовать сторонний модуль, например, [nginx_upstream_check_module](https://github.com/yaoweibin/nginx_upstream_check_module).

Этот модуль позволяет настроить Nginx так, чтобы он периодически отправлял на бэкенды специальные запросы (например, `GET /status`) и анализировал ответ. Если ответ не соответствует ожиданиям, сервер помечается как нерабочий и исключается из балансировки до тех пор, пока снова не начнёт проходить проверку.

## Практические сценарии

### Конфигурация активной проверки с модулем `check`

```nginx
upstream backend {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;

    # Проверка каждые 3 с, 2 удачные попытки для возвращения в строй, 3 неудачные для исключения
    check interval=3000 rise=2 fall=3 timeout=1000 type=http;
    # HTTP-запрос для проверки
    check_http_send "GET /status HTTP/1.0\r\n\r\n";
    # Ожидаемый код ответа
    check_http_expect_alive http_2xx;
}
```

**Параметры директивы `check`:**

| Параметр | Значение | Описание |
|----------|----------|----------|
| `interval` | 3000 | Интервал между проверками в миллисекундах (3 с) |
| `rise` | 2 | Количество успешных проверок для возврата сервера в ротацию |
| `fall` | 3 | Количество неудачных проверок для исключения сервера |
| `timeout` | 1000 | Таймаут ожидания ответа в миллисекундах (1 с) |
| `type` | http | Тип проверки: HTTP-запрос |

### Типы проверок в `check` модуле

- `http` — HTTP-запрос с анализом кода ответа
- `ssl_hello` — отправка SSL ClientHello (проверка доступности SSL-порта)
- `tcp` — проверка доступности TCP-порта (без HTTP)
- `mysql` — проверка MySQL-соединения
- `smtp` — проверка SMTP-сервера

### Мониторинг upstream-серверов

Состояние upstream-серверов можно отслеживать следующими способами:

- **Nginx Plus / Angie:** встроенный API статуса (`status_zone`), отдающий JSON с метриками по каждому бэкенду.
- **Prometheus:** [nginx-prometheus-exporter](../../../../Prometheus/Exporters/other_exporters.md) собирает метрики из стандартных логов Nginx и/или stub_status.
- **Внешние системы мониторинга:** Zabbix, Grafana и другие инструменты, анализирующие доступность endpoint'ов по HTTP/TCP.

### Проверка работы балансировки

Для убеждения в том, что балансировка работает и запросы распределяются между бэкендами, выполните:

```bash
curl http://127.0.0.1
```

При каждом вызове вы должны получать ответы от разных бэкенд-серверов (по умолчанию Nginx использует алгоритм Round Robin).

> **Примечание:** содержимое ответов зависит от реализации ваших бэкенд-сервисов. Для тестирования обычно настраивают endpoint `/status` или `/health`, возвращающий идентификатор сервера.
