# Балансировка нагрузки Nginx: Sticky Sessions (Прилипание сессий)

**Надёжность:** 10 (SSoT + Официальная документация Nginx 1.26 / Angie 1.12)
**Свежесть:** Июль 2026 (Актуально для Nginx 1.26+, Angie 1.12+)

## Определения

**Sticky Sessions (Прилипание сессий)** — механизм балансировщика нагрузки, обеспечивающий направление всех запросов от одного конкретного клиента на один и тот же бэкенд-сервер в течение всей сессии. Применяется для **stateful-приложений**, которые хранят данные сессии (корзины, авторизацию) в локальной памяти конкретного экземпляра сервера, а не в общем хранилище (Redis/Memcached).

> **Важное ограничение:** В Nginx Open Source (OSS) функциональность `sticky` отсутствует в базовой поставке. Она доступна либо через сторонние модули (например, `ngx_http_upstream_sticky_module`), либо в коммерческой версии Nginx Plus и открытом форке **[Angie](../../../Angie/angie_overview.md)**, где она является встроенной.

## Основные концепции

Метод `sticky` является более точным и гибким по сравнению с `ip_hash`, так как позволяет идентифицировать клиента даже при смене его IP-адреса (например, при переключении с Wi-Fi на мобильную сеть) или если тысячи клиентов приходят с одного NAT.

### Сравнение методов прилипания

| Метод | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **cookie** | Nginx сам вставляет новую куку в ответ сервера. | Самый простой в настройке, не зависит от логики приложения. | Клиент должен поддерживать куки. |
| **learn** | Nginx «изучает» ID сессии из кук приложения (PHPSESSID, JSESSIONID). | Не вносит лишних кук, работает прозрачно для приложения. | Требует выделения зоны разделяемой памяти. |
| **route** | Привязка к серверу по идентификатору в URI или заголовке. | Позволяет клиенту (или фронтенду) явно выбирать сервер. | Риск DoS-атаки на конкретный узел без использования `secret`. |

## Практические сценарии

### Настройка через метод cookie

Nginx создает собственную куку для отслеживания сессии.

```nginx
upstream backend_cluster {
    zone backend_zone 64k;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;

    # srv_id - имя куки, expires - время жизни, secure/httponly для безопасности
    sticky cookie srv_id expires=1h domain=.example.com path=/ secure httponly;
}
```

**Ключевые параметры:**
- `expires`: Время жизни куки в браузере.
- `secure` / `httponly`: Рекомендуемые флаги для защиты от XSS и перехвата сессии.
- `sticky secret <salt>`: Позволяет хешировать идентификаторы серверов с солью, скрывая их реальные IP/порты.

### Настройка через метод learn (отслеживание сессий приложения)

Используется, когда приложение уже генерирует идентификатор сессии (например, `PHPSESSID`). Nginx запоминает соответствие «ID сессии -> IP сервера» в таблице.

```nginx
upstream php_app {
    zone sessions_zone 1m;
    server 10.1.1.10:9000;
    server 10.1.1.11:9000;

    # Angie 1.3.0+ / Nginx Plus
    sticky learn
        zone=client_sessions:2m # Таблица на ~20 000 сессий
        create=$upstream_cookie_phpsessid
        lookup=$cookie_phpsessid
        timeout=1h;
}
```
*Разбор:*
- `create`: Переменная, в которой ищем ID при первом ответе сервера (`Set-Cookie`).
- `lookup`: Переменная для поиска ID в последующих запросах клиента.
- `timeout`: Время удаления записи из памяти после последнего обращения.

### Настройка через метод route (маршрутизация по переменной)

Обычно используется, когда идентификатор бэкенда передается в URL (`?route=server1`) или кастомном заголовке.

```nginx
upstream dynamic_route {
    sticky route $arg_route; # Ищем параметр ?route=...
    server 127.0.0.1:9000 route=a;
    server 127.0.0.1:9001 route=b;
}
```

## Дополнительная информация

### Режим вывода сервера (Drain)

В Angie и Nginx Plus можно перевести сервер в режим **drain**. В этом режиме сервер перестает принимать новых клиентов, но продолжает обслуживать тех, кто уже «прилип» к нему по идентификатору сессии.

```nginx
upstream backend {
    zone b_zone 64k;
    server 10.0.0.1:8080 drain; # Дождется завершения сессий
    server 10.0.0.2:8080;
}
```
