# Балансировка нагрузки Nginx: Sticky Sessions (Прилипание сессий)

## Определения

**Sticky Sessions (Прилипание сессий)** — механизм балансировщика нагрузки, обеспечивающий направление всех запросов от одного конкретного клиента на один и тот же бэкенд-сервер в течение всей сессии. Применяется для **stateful-приложений**, которые хранят данные сессии (корзины, авторизацию) в локальной памяти конкретного экземпляра сервера, а не в общем распределенном хранилище (Redis/Memcached).

> **Важное ограничение:** В Nginx Open Source (OSS) функциональность `sticky` отсутствует в базовой поставке. Она доступна либо через сторонние модули (например, `ngx_http_upstream_sticky_module`), либо в коммерческой версии Nginx Plus и открытом форке **[Angie](../../../Angie/angie_overview.md)**, где она является встроенной и расширенной.

## Основные концепции

Метод `sticky` является более точным и гибким по сравнению с `ip_hash`, так как позволяет идентифицировать клиента даже при смене его IP-адреса (например, при переключении с Wi-Fi на мобильную сеть) или если тысячи клиентов приходят с одного NAT (например, из корпоративной сети).

### Сравнение методов прилипания

| Метод | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **cookie** | Nginx сам вставляет новую куку в ответ сервера. | Самый простой в настройке, не зависит от логики приложения. | Требует поддержки кук на клиенте. |
| **learn** | Nginx «изучает» ID сессии из кук приложения (PHPSESSID, JSESSIONID). | Не вносит лишних кук, прозрачен для приложения. | Требует выделения зоны разделяемой памяти. |
| **route** | Привязка к серверу по идентификатору в URI или заголовке. | Позволяет клиенту или фронтенду явно выбирать сервер. | Риск DoS-атаки на конкретный узел без защиты. |

## Практические сценарии

### Настройка через метод cookie

Nginx создает собственную куку для отслеживания сессии.

```nginx
upstream backend_cluster {
    zone backend_zone 64k;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;

    # srv_id - имя куки, expires - время жизни, secure/httponly для безопасности
    sticky cookie srv_id expires=1h domain=.example.com path=/ secure httponly;
}
```

**Ключевые параметры:**
- `expires`: Время жизни куки. Если не указано, кука станет сессионной (удаляется при закрытии браузера).
- `secure` / `httponly`: Флаги безопасности для защиты от XSS и перехвата.
- `sticky secret <salt>`: Позволяет хешировать идентификаторы серверов с солью, скрывая их реальные IP/порты от клиента.

### Настройка через метод learn (отслеживание сессий приложения)

Используется, когда приложение уже генерирует идентификатор сессии (например, `PHPSESSID` в PHP или `JSESSIONID` в Java). Nginx запоминает соответствие «ID сессии -> IP сервера» в таблице разделяемой памяти.

```nginx
upstream php_app {
    zone sessions_zone 1m;
    server 10.1.1.10:9000;
    server 10.1.1.11:9000;

    # Доступно в Angie 1.3.0+ и Nginx Plus
    sticky learn
        zone=client_sessions:2m # Таблица на ~20 000 сессий
        create=$upstream_cookie_phpsessid
        lookup=$cookie_phpsessid
        timeout=1h;
}
```

**Особенности метода learn:**
- `create`: Переменная, из которой извлекается ID сессии при первом ответе бэкенда (обычно из заголовка `Set-Cookie`).
- `lookup`: Переменная, по которой ищется сессия в последующих запросах клиента (обычно из заголовка `Cookie`).
- `timeout`: Время неактивности сессии, после которого запись удаляется из памяти.

### Настройка через метод route (маршрутизация по переменной)

Обычно используется, когда идентификатор бэкенда передается в параметрах URL (`?route=server1`) или в кастомном заголовке.

```nginx
upstream dynamic_route {
    sticky route $arg_route; # Ищем параметр ?route=...
    server 127.0.0.1:9000 route=a;
    server 127.0.0.1:9001 route=b;
}
```

## Дополнительные параметры и нюансы

### Обработка отказов (директива strict)

По умолчанию, если сервер, к которому «прилип» клиент, становится недоступным, Nginx перенаправляет запрос на другой живой сервер. Однако в некоторых случаях (например, если сессия критически важна и не может быть воссоздана на другом узле) можно использовать параметр `strict`.

```nginx
sticky cookie srv_id expires=1h strict;
```
С параметром `strict` Nginx вернет ошибку `502 (Bad Gateway)`, если целевой сервер недоступен, вместо того чтобы сбросить сессию на другой узел.

### Режим вывода сервера (Drain)

В Angie и Nginx Plus поддерживается режим **drain**, который позволяет плавно вывести сервер из эксплуатации. В этом режиме сервер перестает принимать новых клиентов, но продолжает обслуживать тех, кто уже имеет установленную сессию.

```nginx
upstream backend {
    zone b_zone 64k;
    server 10.0.0.1:8080 drain; # Только существующие сессии
    server 10.0.0.2:8080;
}
```

### Взаимодействие с Keep-Alive

При использовании `sticky` соединение между клиентом и Nginx может удерживаться (`keepalive`), но это не гарантирует попадание на тот же бэкенд без сессионной привязки. Использование `sticky` гарантирует логическую связность сессии даже при переподключениях на уровне TCP.

### Сторонние модули для Nginx OSS

Если нет возможности использовать Angie или Plus, для Nginx OSS часто применяются модули:
- **`nginx-sticky-module-ng`**: Популярный модуль, реализующий метод `cookie`.
- **`ngx_http_upstream_session_sticky_module`**: Еще один аналог для реализации сессионной привязки.
