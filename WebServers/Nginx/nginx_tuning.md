## Ключевые директивы для тюнинга


Эти настройки обычно производятся в главном конфигурационном файле `nginx.conf`.

-   **`worker_processes`**: Определяет количество рабочих процессов Nginx.
    -   **Рекомендация:** `auto`. Nginx автоматически определит оптимальное количество, равное числу ядер процессора.
    ```nginx
    worker_processes auto;
    ```

-   **`worker_connections`**: Максимальное количество одновременных соединений, которое может обработать один рабочий процесс.
    -   **Рекомендация:** Устанавливается в зависимости от лимитов системы. Общее количество соединений = `worker_processes` * `worker_connections`.
    ```nginx
    events {
        worker_connections 1024;
    }
    ```

-   **`reuseport`**: Позволяет создавать отдельный слушающий сокет для каждого рабочего процесса. Это устраняет "узкое место" в виде одного сокета и позволяет ядру более эффективно распределять нагрузку.
    ```nginx
    listen 80 reuseport;
    ```

-   **`sendfile`**: Разрешает Nginx использовать системный вызов `sendfile()`, который копирует данные напрямую из одного файлового дескриптора в другой (например, с диска в сокет), минуя копирование в пространство пользователя. Значительно ускоряет отдачу статических файлов.
    ```nginx
    sendfile on;
    ```

-   **`keepalive_timeout`**: Время в секундах, в течение которого сервер не закрывает keep-alive соединение после обработки запроса. Позволяет клиенту выполнять несколько запросов в рамках одного соединения.
    ```nginx
    keepalive_timeout 65;
    ```

-   **`gzip`**: Включает сжатие ответов "на лету". Уменьшает объем передаваемого трафика, но создает дополнительную нагрузку на CPU.
    ```nginx
    gzip on;
    gzip_types text/plain text/css application/json application/javascript;
    ```

## Кэширование ответов бэкенда (Proxy Cache)

Кэширование ответов от бэкенд-серверов с помощью модуля `ngx_http_proxy_module` позволяет значительно снизить нагрузку на них и ускорить отдачу контента.

### 1. Основные директивы для настройки кэша

Настройка кэша состоит из двух частей: определение зоны кэширования в блоке `http` и использование этой зоны в блоке `server` или `location`.

#### В блоке `http` (обычно в `nginx.conf`):

*   **`proxy_cache_path`**: Определяет путь к директории, где будут храниться кэшированные файлы, и настраивает параметры зоны кэширования.
    ```nginx
    proxy_cache_path /var/cache/nginx/proxy_cache levels=1:2 keys_zone=my_cache:10m inactive=60m max_size=1g;
    ```
    *   `/var/cache/nginx/proxy_cache`: Путь к директории для хранения кэша. Убедитесь, что у пользователя Nginx есть права на запись в эту директорию.
    *   `levels=1:2`: Определяет двухуровневую иерархию поддиректорий для хранения кэша. Это улучшает производительность файловой системы при большом количестве файлов.
    *   `keys_zone=my_cache:10m`: Создает общую зону памяти `my_cache` размером 10 МБ для хранения ключей кэша и метаданных. 10 МБ достаточно для хранения метаданных примерно 80000 ключей.
    *   `inactive=60m`: Определяет время, после которого неактивные (не запрашиваемые) элементы кэша будут удалены.
    *   `max_size=1g`: Устанавливает максимальный размер кэша. При достижении этого лимита Nginx будет удалять наименее используемые файлы.

*   **`proxy_cache_key`**: Определяет ключ, по которому будет кэшироваться ответ. По умолчанию используется комбинация схемы, хоста и URI запроса. Можно расширить, добавив переменные Nginx.
    ```nginx
    proxy_cache_key "$scheme$proxy_host$request_uri";
    # Пример с добавлением куки:
    # proxy_cache_key "$scheme$proxy_host$request_uri$cookie_us";
    ```
    *   **Внимание:** Добавление уникальных переменных (например, куки сессии) в ключ кэша может привести к быстрому разрастанию кэша и снижению его эффективности, если для каждого пользователя будет создаваться отдельная копия. Используйте с осторожностью.

#### В блоке `server` или `location`:

*   **`proxy_cache`**: Включает кэширование для данного блока и указывает используемую зону кэширования.
    ```nginx
    proxy_cache my_cache;
    ```

*   **`proxy_cache_valid`**: Определяет время жизни кэша для различных кодов ответов HTTP.
    ```nginx
    proxy_cache_valid 200 302 10s; # Кэшировать ответы 200 и 302 на 10 секунд
    proxy_cache_valid 404 1m;      # Кэшировать ответы 404 на 1 минуту
    ```
    *   Если указано только время, оно применяется ко всем успешным ответам (200, 301, 302).

*   **`proxy_cache_lock`**: Защищает от "cache stampede" (когда множество клиентов одновременно запрашивают устаревший ресурс).
    ```nginx
    proxy_cache_lock on;
    ```
    *   При включении этой директивы, если кэш устарел, только первый запрос будет отправлен на бэкенд для обновления. Остальные запросы будут ожидать появления свежего ответа в кэше или истечения таймаута (`proxy_cache_lock_timeout`, по умолчанию 5с).

*   **`proxy_cache_min_uses`**: Устанавливает минимальное количество запросов к ресурсу, прежде чем он будет кэширован. По умолчанию `1`. Увеличение этого значения может помочь избежать кэширования редко используемых страниц.
    ```nginx
    proxy_cache_min_uses 2;
    ```

*   **`proxy_cache_use_stale` и `proxy_background_update`**: Директивы для повышения отказоустойчивости и отзывчивости.
    *   **`proxy_cache_use_stale`**: Разрешает Nginx отдавать устаревший (stale) контент из кэша, если бэкенд недоступен, отвечает с ошибкой или запрос таймаутится. Это лучше, чем показывать пользователю ошибку.
        ```nginx
        proxy_cache_use_stale error timeout invalid_header http_500 http_502 http_503 http_504;
        ```
    *   **`proxy_background_update`**: Позволяет Nginx отдать пользователю устаревший контент немедленно, а в это время отправить фоновый асинхронный запрос на бэкенд для обновления кэша. Это обеспечивает "нулевое время простоя" для пользователя при обновлении кэша и всегда быструю отдачу страницы. Для работы требует включения `proxy_cache_use_stale` с параметром `updating`.
        ```nginx
        proxy_cache_use_stale error timeout invalid_header http_500 http_502 http_503 http_504 updating;
        proxy_background_update on;
        ```

*   **`proxy_cache_bypass`**: Определяет условия, при которых Nginx будет обходить кэш и всегда обращаться к бэкенду. Используется для динамического контента или для отладки.
    ```nginx
    proxy_cache_bypass $cookie_nocache $arg_nocache;
    ```
    *   Если переменная `$cookie_nocache` или `$arg_nocache` не пуста и не равна "0", кэш будет обойден.

*   **`proxy_no_cache`**: Определяет условия, при которых ответ не будет кэшироваться.
    ```nginx
    proxy_no_cache $cookie_session;
    ```
    *   Если переменная `$cookie_session` не пуста и не равна "0", ответ не будет кэшироваться.

*   **`proxy_cache_purge`**: Директива для точечной очистки кэша. Доступна только в Nginx Plus или с использованием сторонних модулей. В Open Source версии Nginx для очистки кэша обычно требуется ручное удаление файлов или использование внешних скриптов.

### 2. Пример полной конфигурации кэширования

```nginx
# В блоке http в nginx.conf
http {
    # ...
    proxy_cache_path /var/cache/nginx/proxy_cache levels=1:2 keys_zone=my_cache:10m inactive=60m max_size=1g;
    proxy_cache_key "$scheme$proxy_host$request_uri"; # Ключ кэша по умолчанию

    # ...
    server {
        listen 80;
        server_name example.com;

        location / {
            proxy_pass http://backend_servers; # Предполагается, что backend_servers определен в upstream

            proxy_cache my_cache;
            proxy_cache_valid 200 302 10s; # Кэшировать успешные ответы на 10 секунд
            proxy_cache_valid 404 1m;      # Кэшировать 404 на 1 минуту

            proxy_cache_lock on;
            proxy_cache_min_uses 2; # Кэшировать только после 2 запросов
            proxy_cache_use_stale error timeout invalid_header http_500 http_502 http_503 http_504 updating;
            proxy_background_update on;

            # Обход кэша, если есть кука 'nocache' или параметр 'nocache' в URL
            proxy_cache_bypass $cookie_nocache $arg_nocache;
            # Не кэшировать, если есть кука 'session'
            proxy_no_cache $cookie_session;

            # ... другие директивы proxy_set_header
        }

        # Пример location, где кэширование отключено
        location /admin/ {
            proxy_pass http://backend_admin;
            proxy_cache off; # Отключаем кэширование для админки
        }
    }
}
```

### 3. Отладка и проверка кэша

Для проверки работы кэша можно добавить заголовки в ответ Nginx:

```nginx
add_header X-Proxy-Cache $upstream_cache_status;
```
*   `$upstream_cache_status` может принимать значения:
    *   `MISS`: Запрос не найден в кэше, Nginx обратился к бэкенду.
    *   `HIT`: Ответ был отдан из кэша.
    *   `EXPIRED`: Кэш устарел, Nginx обратился к бэкенду для обновления.
    *   `STALE`: Ответ отдан из устаревшего кэша (например, из-за недоступности бэкенда).
    *   `UPDATING`: Ответ отдан из устаревшего кэша, пока в фоне происходит обновление.
    *   `BYPASS`: Кэш был обойден (например, из-за `proxy_cache_bypass`).

### 4. Производительность дискового кэша

Часто возникают вопросы о том, не будет ли кэширование на диске медленным по сравнению с решениями в оперативной памяти (например, Memcached). На практике, производительность дискового кэша Nginx очень высока.

Современные операционные системы эффективно кэшируют часто запрашиваемые файлы в оперативной памяти (page cache). Это означает, что если файлы из кэша Nginx запрашиваются регулярно, они с большой вероятностью будут находиться в RAM, и Nginx будет отдавать их с минимальной задержкой, сопоставимой со скоростью работы памяти. Использование специализированных in-memory хранилищ не всегда дает значительный выигрыш в производительности, но усложняет архитектуру.

## Балансировка нагрузки с `upstream`

Блок `upstream` позволяет определить группу серверов (бэкендов), между которыми Nginx будет распределять запросы. Это основа для построения отказоустойчивых и масштабируемых систем.

> **Подробное руководство по настройке, алгоритмам (`least_conn`, `ip_hash`), параметрам серверов (`weight`, `max_fails` и др.) и проверкам состояния (Health Checks) находится в документе [Балансировка нагрузки с помощью Nginx](./nginx_load_balancing.md).**

Базовый пример:
```nginx
# Блок http
upstream backend_servers {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}

server {
    listen 80;
    server_name myapp.com;

    location / {
        proxy_pass http://backend_servers;
    }
}
```

-   **`upstream keepalive`**: При проксировании запросов, Nginx может поддерживать активные keep-alive соединения с бэкенд-серверами, что снижает задержки.
    ```nginx
    upstream backend {
        server backend.example.com;
        keepalive 16;
    }
    ```

-   **Использование `epoll`**: В Linux Nginx автоматически использует `epoll` — наиболее эффективный метод обработки сетевых событий. Убедитесь, что в секции `events` не указан другой, менее производительный метод.
    ```nginx
    events {
        use epoll; # Обычно включено по умолчанию
    }

## Кэширование статических файлов

Для ускорения загрузки сайта клиентами можно включить кэширование статических файлов в браузере с помощью заголовков `expires` и `Cache-Control`.

```nginx
location ~* ^.+\.(?:css|cur|js|jpe?g|gif|htc|ico|png|html|xml|otf|ttf|eot|woff|woff2|svg)$ {
    expires 30d;
    # public - ресурс может кэшироваться любым кэшем (браузером, прокси).
    # immutable - указывает, что ресурс не изменится в течение срока действия max-age.
    # Браузер не будет отправлять запросы на сервер для проверки актуальности.
    add_header Cache-Control "public, immutable";
}
```

### Заголовки кэширования

*   **`Last-Modified`**: Заголовок ответа сервера, указывающий дату и время последнего изменения ресурса. Браузер может использовать его для условных запросов (`If-Modified-Since`), чтобы проверить, изменился ли ресурс с момента последнего кэширования. Если ресурс не изменился, сервер отвечает статусом `304 Not Modified`, и браузер использует кэшированную версию.
*   **`ETag` (Entity Tag)**: Уникальный идентификатор версии ресурса, обычно хэш его содержимого. Браузер может использовать `ETag` для условных запросов (`If-None-Match`). Если `ETag` на сервере совпадает с тем, что есть у браузера, сервер также отвечает `304 Not Modified`. `ETag` более гибок, чем `Last-Modified`, так как позволяет обнаруживать изменения, не связанные со временем (например, изменение содержимого без изменения даты файла).
*   **`expires`**: Устанавливает дату и время, после которых кэшированный ресурс считается устаревшим. Директива `expires 1y;` является сокращением, которое также устанавливает заголовок `Cache-Control` с `max-age`, равным одному году.
*   **`Cache-Control`**: Более современный и гибкий заголовок для управления кэшированием.
    *   `public`: Разрешает кэширование ресурса любым кэшем, включая браузеры и промежуточные прокси-серверы.
    *   `private`: Ресурс может кэшироваться только конечным клиентом (браузером).
    *   `max-age=<seconds>`: Указывает максимальное время в секундах, в течение которого ресурс считается свежим.
    *   `immutable`: Указывает, что ресурс не изменится в течение срока действия `max-age`. Браузер не будет отправлять повторные запросы на сервер для проверки актуальности ресурса (условные запросы с `If-None-Match` или `If-Modified-Since`), что значительно повышает производительность.
    *   `no-transform`: Запрещает промежуточным прокси-серверам изменять ресурс (например, сжимать изображения).

### Стратегия "вечного" кэширования и сброс кэша

При использовании "вечного" кэширования (длительный `expires` и `immutable`), браузер не будет повторно запрашивать ресурс с сервера. Это создает проблему: как обновить ресурс, если он изменился?

**Решение — изменение URL ресурса.**

Если содержимое файла (например, `style.css`) изменилось, вы должны изменить его URL в HTML-коде. Это можно сделать несколькими способами:
1.  **Изменение имени файла:** `style.v2.css`
2.  **Добавление хэша в имя файла:** `style.a1b2c3d4.css` (наиболее надежный способ, используется современными сборщиками фронтенда, такими как Webpack).
3.  **Добавление query-параметра (версионирование):** `style.css?v=2`

Когда браузер видит новый URL, он воспринимает его как совершенно новый ресурс и загружает его с сервера. Старый ресурс со старым URL остается в кэше до истечения срока его действия, но больше не используется.

**Важно:** Эта логика должна поддерживаться вашим приложением или процессом сборки. Nginx только отдает заголовки, но не управляет версионированием файлов.

## Настройки таймаутов

Корректная настройка таймаутов помогает предотвратить длительное удержание соединений.

- `client_header_timeout 10;`: Таймаут для чтения заголовков запроса клиента.
- `client_body_timeout 10;`: Таймаут для чтения тела запроса клиента.
- `keepalive_timeout 10;`: Время, в течение которого keep-alive соединение остается открытым на стороне сервера.

## Оптимизация сжатия в Nginx/Angie (Gzip, Brotli, ZSTD)

Сжатие текста является одним из наиболее эффективных способов уменьшения объема передаваемых данных, что напрямую влияет на скорость загрузки веб-страниц. В Nginx (и его форке Angie) существуют два основных подхода к сжатию:

1.  **Динамическое сжатие (on-the-fly):** Контент сжимается веб-сервером в момент запроса клиента.
    *   **Плюсы:** Не требует предварительной подготовки файлов, всегда отдает актуальную версию.
    *   **Минусы:** Потребляет ресурсы CPU сервера на каждый запрос. Степень сжатия должна быть умеренной, чтобы не создавать излишнюю нагрузку. Является блокирующей операцией для воркера Nginx, что особенно критично для HTTP/2, где все запросы обрабатываются в рамках одного соединения (один воркер блокируется на каждое динамическое сжатие в рамках всего сайта). Это может привести к значительному снижению RPS (запросов в секунду) и увеличению времени ответа.
2.  **Статическое сжатие (pre-compressed):** Файлы сжимаются заранее (например, во время сборки проекта или при изменении файла) и сохраняются рядом с оригиналом (например, `style.css.gz`, `script.js.br`). Веб-сервер просто отдает уже сжатую версию, не тратя CPU на сжатие "на лету".
    *   **Плюсы:** Минимальная нагрузка на CPU сервера (сжатие происходит один раз), максимальная степень сжатия (можно использовать более медленные, но эффективные алгоритмы).
    *   **Минусы:** Требует предварительной подготовки файлов, может усложнить процесс деплоя и управления версиями.

Выбор между динамическим и статическим сжатием, а также алгоритма и его уровня, всегда является компромиссом между нагрузкой на CPU сервера, степенью сжатия (размером файла) и скоростью отдачи контента.

### Динамическое Gzip-сжатие

Gzip — старый, но универсально поддерживаемый алгоритм сжатия. Его динамическая настройка позволяет сжимать контент "на лету". В некоторых контекстах (например, в Angie) директивы Gzip могут быть обозначены с префиксом `xip_`.

```nginx
server {
    # Включает динамическое сжатие Gzip. В Angie аналогичная директива называется xip_on.
    gzip on;
    # Устанавливает степень сжатия (1-9). 3-4 - хороший компромисс между сжатием и нагрузкой на CPU для динамики.
    # В Angie аналогичная директива называется xip_comp_level.
    gzip_comp_level 3;
    # Отключает сжатие для старых браузеров IE, которые могут некорректно обрабатывать сжатый контент.
    gzip_disable "msie6";
    # Указывает, какие MIME-типы подвергать сжатию. В Angie аналогичная директива называется xip_types.
    # Важно: по умолчанию Nginx включает text/html. Все остальное нужно добавлять явно.
    # Также убедитесь, что указанные MIME-типы соответствуют вашим файлам.
    # Полезно проверить фактические MIME-типы, которые отдает ваш сервер, чтобы избежать ошибок.
    gzip_types text/plain text/css application/json application/javascript application/x-javascript text/xml application/xml application/xml+rss text/javascript application/atom+xml application/rss+xml application/vnd.ms-fontobject application/x-font-ttf application/x-web-font application/x-font-opentype image/svg+xml;
    # Добавляет заголовок Vary: Accept-Encoding к ответу, что важно для корректного кэширования прокси-серверами.
    # Это указывает прокси-серверам, что ответ может отличаться в зависимости от заголовка Accept-Encoding клиента.
    gzip_vary on;
    # Минимальная длина ответа в байтах, для которой будет применяться сжатие.
    # Предотвращает сжатие очень маленьких файлов, для которых накладные расходы на сжатие могут превысить выгоду.
    gzip_min_length 1000;
    # Буферы для сжатия. По умолчанию 4 8k.
    gzip_buffers 16 8k;
    # Минимальная версия HTTP-протокола, для которой будет применяться сжатие.
    gzip_http_version 1.1;
    # Включает сжатие для проксированных запросов.
    gzip_proxied any;
}
```

### Статическое Gzip-сжатие

Для статического Gzip-сжатия Nginx может отдавать предварительно сжатые файлы с расширением `.gz`. Для этого необходимо, чтобы файлы были сжаты заранее и лежали рядом с оригинальными. Например, для файла `style.css` должен существовать `style.css.gz`.

Директива `gzip_static on;` включает эту функциональность (аналогично `xip_static`).

```nginx
server {
    # ...
    location /static/ {
        gzip_static on; # Включает отдачу предварительно сжатых .gz файлов. В Angie аналогичная директива называется xip_static.
        # Важно: если gzip_static (или xip_static) используется в глобальном контексте, Nginx будет искать сжатые версии
        # для всех статических файлов, даже для изображений, что неэффективно.
        # Рекомендуется использовать gzip_static (или xip_static) внутри location,
        # где заведомо находятся сжимаемые статические файлы (CSS, JS).
        # ... другие настройки для статики ...
    }
    # ...
}
```

**Генерация статически сжатых Gzip файлов:**

Для создания `.gz` файлов можно использовать утилиту `gzip` или `zopfli`. `zopfli` обеспечивает лучшее сжатие, но работает медленнее.

```bash
# Установка zopfli: sudo apt install zopfli
# Использование gzip (быстро, хорошее сжатие)
gzip -k -9 original_file.css

# Использование zopfli (медленнее, но лучшее сжатие, совместимо с Gzip)
zopfli -k -9 original_file.css
# -k: сохранить оригинальный файл
# -9: максимальный уровень сжатия
# Важно: zopfli по умолчанию не сохраняет дату модификации. Если это критично для заголовков Last-Modified,
# дату нужно обновить вручную: touch -r original_file.css original_file.css.gz
```

### Переговоры о сжатии (Accept-Encoding)

Браузеры отправляют заголовок `Accept-Encoding` (например, `Accept-Encoding: gzip, deflate, br, zstd`), чтобы сообщить серверу, какие алгоритмы сжатия они поддерживают. Nginx выбирает наиболее предпочтительный из доступных и отправляет ответ с заголовком `Content-Encoding` (например, `Content-Encoding: br`).

**Важный нюанс с HTTPS:** Некоторые браузеры (особенно старые версии Chrome при доступе по HTTP) могут ограничивать список поддерживаемых алгоритмов сжатия при работе по HTTP, отдавая предпочтение только `gzip` и `deflate`. При доступе по HTTPS список обычно полный (`gzip, deflate, br, zstd`). Это стоит учитывать при тестировании. Более того, в некоторых случаях (например, при доступе по HTTP, а не HTTPS) браузер может существенно сократить список поддерживаемых кодеков, что может привести к тому, что Brotli или ZSTD не будут использоваться, даже если они настроены на сервере. Поэтому тестирование всегда следует проводить по HTTPS.

## Настройки Brotli-сжатия

Brotli — современный алгоритм сжатия, разработанный Google, который обеспечивает очень высокую степень сжатия для веб-контента (HTML, CSS, JS), особенно при статической компрессии. Он широко поддерживается современными браузерами.

**Важно:** Для использования Brotli в Nginx требуется установка модуля `ngx_brotli`. Это может потребовать пересборки Nginx с этим модулем или установки его как динамического модуля. В некоторых дистрибутивах или сборках (например, Angie) он может быть доступен из коробки (например, `apt install ngx-module-brotli`). Если модуль установлен как динамический, его необходимо загрузить в `nginx.conf` с помощью директивы `load_module`:
```nginx
load_module modules/ngx_http_brotli_filter_module.so;
load_module modules/ngx_http_brotli_static_module.so;
```

Brotli-сжатие, как и Gzip, может быть **динамическим** (сжатие "на лету") или **статическим** (отдача предварительно сжатых файлов).

```nginx
server {
    # Включает динамическое Brotli-сжатие
    brotli on;
    # Устанавливает степень сжатия (1-11). 5-6 - хороший компромисс для динамики.
    brotli_comp_level 5;
    # Указывает, какие MIME-типы подвергать сжатию.
    brotli_types text/plain text/css application/json application/javascript application/x-javascript text/xml application/xml application/xml+rss text/javascript application/atom+xml application/rss+xml application/vnd.ms-fontobject application/x-font-ttf application/x-web-font application/x-font-opentype image/svg+xml;
    # Добавляет заголовок Vary: Accept-Encoding.
    brotli_vary on;
    # Минимальная длина ответа для сжатия.
    brotli_min_length 1000;

    # Включает статический режим Brotli-сжатия.
    # Nginx будет искать предварительно сжатые файлы с расширением .br.
    # Для этого необходимо, чтобы файлы были сжаты заранее и лежали рядом с оригинальными.
    # Например, для файла `style.css` должен существовать `style.css.br`.
    brotli_static on;
}
```

**Генерация статически сжатых Brotli файлов:**

Для создания `.br` файлов можно использовать утилиту `brotli`.

```bash
# Установка brotli: sudo apt install brotli
brotli -k -q 11 original_file.css
# -k: сохранить оригинальный файл
# -q 11: максимальный уровень сжатия (от 1 до 11)
```

Brotli на максимальных уровнях сжатия (например, 11) обеспечивает наилучшее соотношение размера файла к качеству, но процесс сжатия может быть довольно медленным. Поэтому его рекомендуется использовать для статического контента, который сжимается один раз.


## Настройки ZSTD-сжатия

ZSTD (Zstandard) — алгоритм сжатия, разработанный Facebook, известный своей очень высокой скоростью сжатия и распаковки. Это делает его крайне привлекательным для динамической компрессии, где важна минимальная задержка. ZSTD также имеет широкую поддержку в современных браузерах.

Для использования ZSTD в Nginx требуется установка модуля `ngx_http_zstd_filter_module` (в Angie часто доступен из коробки, например, `apt install ngx-module-zstd`). Если модуль установлен как динамический, его необходимо загрузить в `nginx.conf` с помощью директивы `load_module`:
```nginx
load_module modules/ngx_http_zstd_filter_module.so;
```

```nginx
server {
    # Включает динамическое ZSTD-сжатие
    zstd on;
    # Устанавливает степень сжатия (1-22). 3-5 - хороший компромисс для динамики, обеспечивающий высокую скорость и хорошее сжатие.
    zstd_comp_level 3;
    # Указывает, какие MIME-типы подвергать сжатию.
    zstd_types text/plain text/css application/json application/javascript application/x-javascript text/xml application/xml application/xml+rss text/javascript application/atom+xml application/rss+xml application/vnd.ms-fontobject application/x-font-ttf application/x-web-font application/x-font-opentype image/svg+xml;
    # Добавляет заголовок Vary: Accept-Encoding.
    zstd_vary on;
    # Минимальная длина ответа для сжатия.
    zstd_min_length 1000;

    # Включает статический режим ZSTD-сжатия.
    # Nginx будет искать предварительно сжатые файлы с расширением .zst.
    # Обычно менее актуален, чем Brotli static, из-за меньшей степени сжатия для веб-контента.
    zstd_static on;
}
```

**Генерация статически сжатых ZSTD файлов:**

Для создания `.zst` файлов можно использовать утилиту `zstd`.

```bash
Установка zstd: sudo apt install zstd
zstd -k -19 original_file.css
# -k: сохранить оригинальный файл
# -19: уровень сжатия (от 1 до 22). Для статики можно использовать более высокие уровни.
```


## Оптимизация TLS

Настройка TLS-соединений для повышения безопасности и производительности.

```nginx
server {
    listen 443 ssl; # Обязательно для HTTPS

    # Поддерживаемые версии протокола TLS. TLSv1.2 и TLSv1.3 являются рекомендуемыми.
    ssl_protocols TLSv1.2 TLSv1.3;

    # Наборы шифров. Рекомендуется использовать современные и безопасные.
    # Пример из Mozilla SSL Configuration Generator (Intermediate compatibility):
    ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384';

    # Сервер предпочитает свои наборы шифров, а не клиентские.
    ssl_prefer_server_ciphers on;

    # Путь к файлу с параметрами Диффи-Хеллмана (генерируется командой `openssl dhparam -out /etc/nginx/dhparam.pem 2048`).
    # Увеличивает безопасность Perfect Forward Secrecy.
    ssl_dhparam /etc/nginx/dhparam.pem;

    # Кэширование TLS-сессий для ускорения повторных подключений.
    ssl_session_cache shared:SSL:10m; # 10MB кэша, примерно 40000 сессий
    ssl_session_timeout 1h; # Время жизни сессии в кэше

    # Включение Session Tickets (для TLSv1.2)
    ssl_session_tickets on;

    # HSTS (HTTP Strict Transport Security) - заголовок, который заставляет браузеры всегда использовать HTTPS.
    # max-age - время в секундах, в течение которого браузер будет помнить это правило.
    # includeSubDomains - применять правило ко всем поддоменам.
    # preload - включить домен в список HSTS Preload List (требует отдельной регистрации).
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload";

    # Пути к SSL-сертификату и приватному ключу.
    ssl_certificate /etc/nginx/ssl/your_domain.crt;
    ssl_certificate_key /etc/nginx/ssl/your_domain.key;

    # Опционально: для ECDSA-сертификатов (более производительные)
    # ssl_certificate /etc/nginx/ssl/your_domain_ecdsa.crt;
    # ssl_certificate_key /etc/nginx/ssl/your_domain_ecdsa.key;
}
```

## Конфигурация HTTP/2 и HTTP/3

Использование современных версий протокола HTTP значительно улучшает производительность за счет мультиплексирования, сжатия заголовков и перехода на UDP (для HTTP/3).

### HTTP/2

HTTP/2 работает поверх TCP и требует TLS.

```nginx
server {
    # Для Nginx 1.25.0 и выше:
    listen 443 ssl http2;
    # Для более старых версий Nginx:
    # listen 443 ssl;
    # http2 on; # Включается в блоке server

    # ... остальные настройки TLS ...
}
```

### HTTP/3 (QUIC)

HTTP/3 работает поверх UDP с использованием протокола QUIC и включает встроенный TLS. Требует Nginx версии 1.25.0+ (или Angie) и соответствующего модуля.

```nginx
server {
    # Слушаем UDP порт 443 для QUIC. reuseport обязателен.
    listen 443 ssl quic reuseport;
    # Слушаем TCP порт 443 для HTTP/2 и HTTP/1.1 (для обратной совместимости).
    listen 443 ssl http2;

    # Включаем HTTP/3
    http3 on;

    # Указываем клиентам, что сервер поддерживает HTTP/3.
    # ma (max-age) - время в секундах, в течение которого клиент будет помнить поддержку H3.
    add_header Alt-Svc 'h3=":443"; ma=86400';

    # ... остальные настройки TLS ...
}
```

## Настройки буферов

Оптимизация буферов для обработки клиентских запросов.

- `client_body_buffer_size 24k;`: Размер буфера для чтения тела запроса. Если тело запроса больше, оно будет записано во временный файл.
- `client_max_body_size 6m;`: Максимально допустимый размер тела запроса клиента.
- `client_header_buffer_size 1k;`: Размер буфера для чтения заголовков. Для большинства запросов 1 КБ достаточно, но запросы с длинными cookies могут требовать большего значения.

## Кэш открытых файлов

Nginx может кэшировать метаданные о файлах, что ускоряет доступ к ним.

```nginx
# Конфигурирует кэш для метаданных файлов
# max=5000: максимальное количество элементов в кэше
# inactive=20s: время, после которого элемент удаляется, если не используется
open_file_cache max=5000 inactive=20s;

# Время, через которое элементы кэша должны быть перепроверены
open_file_cache_valid 30s;

# Минимальное число обращений к файлу за время `inactive`, чтобы он оставался в кэше
open_file_cache_min_uses 2;

# Кэширование ошибок поиска файлов
open_file_cache_errors on;
```

## Адаптивная доставка изображений

Современные форматы изображений, такие как WebP или AVIF, обеспечивают лучшее сжатие при том же качестве по сравнению с JPEG или PNG. Однако не все браузеры их поддерживают. Nginx можно настроить так, чтобы он автоматически отдавал современный формат, если браузер его поддерживает, и стандартный формат в противном случае.

Это реализуется с помощью директивы `map` и переменной `$http_accept`.

1.  **Создайте карту (map) для определения поддержки WebP:**
    В блоке `http` файла `nginx.conf` добавьте:
    ```nginx
    map $http_accept $webp_suffix {
        default "";
        "~*webp" ".webp";
    }
    ```
    Эта карта проверяет заголовок `Accept`, который присылает браузер. Если в нем есть "webp", переменная `$webp_suffix` примет значение `.webp`, иначе — пустую строку.

2.  **Настройте `location` для отдачи изображений:**
    В блоке `server` используйте `try_files` для проверки наличия WebP-версии файла.
    ```nginx
    location ~* ^/path/to/images/(.+\.(jpe?g|png))$ {
        # Пытаемся отдать WebP-версию ($1.webp)
        # Если ее нет, отдаем оригинальный файл ($uri)
        try_files $1$webp_suffix $uri =404;
    }
    ```
    *   `$1` содержит имя файла с расширением (например, `my-image.jpg`).
    *   `$webp_suffix` будет либо `.webp`, либо пустым.
    *   `try_files` сначала попытается найти файл `my-image.jpg.webp`. Если он существует, Nginx отдаст его.
    *   Если файла с суффиксом `.webp` нет, `try_files` перейдет к следующему параметру — `$uri` (оригинальный файл `my-image.jpg`) и отдаст его.

**Рабочий процесс:**
1.  Вы заранее создаете WebP-версии всех ваших изображений и кладете их рядом с оригиналами, добавляя суффикс `.webp` (например, `my-image.jpg` и `my-image.jpg.webp`).
2.  Когда браузер запрашивает `my-image.jpg`, Nginx проверяет, поддерживает ли браузер WebP.
3.  Если да, Nginx отдает `my-image.jpg.webp`.
4.  Если нет, Nginx отдает `my-image.jpg`.

Этот подход позволяет значительно уменьшить размер изображений для современных браузеров без ущерба для совместимости.

## Сравнение алгоритмов сжатия и рекомендации

Выбор алгоритма сжатия и его уровня всегда является компромиссом между нагрузкой на CPU сервера, степенью сжатия (размером файла) и скоростью отдачи контента.

**Краткая сводка по Gzip, Brotli и ZSTD:**

*   **Gzip:**
    *   **Степень сжатия:** Хорошая, но уступает Brotli.
    *   **Скорость:** Умеренная.
    *   **Поддержка:** Универсальная (все браузеры).
    *   **Применение:** Подходит для общего сжатия, когда другие алгоритмы не поддерживаются или не настроены.

*   **Brotli:**
    *   **Степень сжатия:** Отличная, особенно для веб-контента (HTML, CSS, JS).
    *   **Скорость:** Сжатие медленнее, чем у Gzip и ZSTD на высоких уровнях, но распаковка очень быстрая.
    *   **Поддержка:** Широкая (большинство современных браузеров).
    *   **Применение:** Идеален для статического сжатия (предварительно сжатые файлы) и динамического сжатия на умеренных уровнях.

*   **ZSTD:**
    *   **Степень сжатия:** Хорошая, сопоставима с Gzip, но может быть лучше на высоких уровнях.
    *   **Скорость:** Исключительно высокая скорость сжатия и распаковки.
    *   **Поддержка:** Хорошая, но не такая универсальная, как Gzip (Safari отстает).
    *   **Применение:** Отлично подходит для динамического сжатия, где важна минимальная задержка и низкая нагрузка на CPU сервера.

**Рекомендации:**
*   Для **статического контента** (CSS, JS, шрифты) используйте **Brotli** с максимальной степенью сжатия (например, `brotli_comp_level 11`) путем предварительного сжатия файлов. Это обеспечивает наилучшее сжатие при минимальной нагрузке на сервер во время отдачи.
*   Для **динамического контента** (HTML, JSON API) используйте **ZSTD** на низких уровнях сжатия (например, `zstd_comp_level 3-5`) для оптимального баланса между скоростью и эффективностью. ZSTD значительно быстрее Gzip и Brotli при динамическом сжатии, что критично для HTTP/2 и HTTP/3.
*   Если ZSTD недоступен, используйте **Brotli** на умеренных уровнях (`brotli_comp_level 3-6`) для динамического сжатия.
*   **Gzip** можно использовать как запасной вариант для браузеров, не поддерживающих Brotli или ZSTD, или для контента, который не выигрывает значительно от более продвинутых алгоритмов.

### Влияние уровня сжатия на производительность

Увеличение уровня сжатия (например, `gzip_comp_level 9`, `brotli_comp_level 11`, `zstd_comp_level 22`) приводит к уменьшению размера файла, но значительно увеличивает нагрузку на CPU сервера и время, необходимое для сжатия. Для динамического сжатия это может привести к снижению RPS (запросов в секунду) и увеличению времени ответа.

**Пример (динамическое сжатие большого CSS-файла):**
*   **Gzip 9:** Очень медленно, RPS может упасть до 30.
*   **Brotli 11:** Максимальное сжатие, но крайне медленно, RPS может быть всего 1.
*   **ZSTD 3:** Отличный баланс скорости и сжатия, RPS может быть более 200.

Для динамического сжатия рекомендуется использовать низкие или средние уровни (Gzip до 3-4, Brotli до 5-6, ZSTD до 3-5), чтобы минимизировать нагрузку на CPU.

### Тестирование эффективности сжатия

Для проверки корректности работы сжатия и оценки его эффективности можно использовать следующие методы:

1.  **Браузерные DevTools:**
    *   Откройте панель разработчика (F12 или Ctrl+Shift+I).
    *   Перейдите на вкладку "Network".
    *   Проверьте столбец "Content-Encoding" (должен быть `gzip`, `br`, `zstd`).
    *   Сравните "Size" (переданный размер) и "Content" (оригинальный размер) для оценки степени сжатия.

2.  **Утилита `curl`:**
    *   Для тестирования сжатия необходимо явно указать заголовок `Accept-Encoding`.
    ```bash
    # Запрос с поддержкой Gzip, Brotli, ZSTD
    curl -H "Accept-Encoding: gzip, deflate, br, zstd" -I https://your-domain.com/path/to/resource.css

    # Проверка заголовка Content-Encoding в ответе
    ```

3.  **Бенчмаркинг (Apache Benchmark `ab`, `wrk`):**
    *   Для оценки влияния сжатия на RPS и время ответа сервера можно использовать утилиты для нагрузочного тестирования.
    *   **Apache Benchmark (ab):**
        ```bash
        # Пример: 1000 запросов, 100 одновременных соединений, с поддержкой Gzip
        ab -n 1000 -c 100 -H "Accept-Encoding: gzip" https://your-domain.com/path/to/resource.css
        ```
    *   **`wrk`:** Более современный инструмент для нагрузочного тестирования.

    При проведении бенчмарков важно тестировать на файлах, максимально приближенных к реальным, так как эффективность сжатия сильно зависит от типа контента. Также следует учитывать, что консольные утилиты (например, `curl` без `-H "Accept-Encoding: ..."` или `ab` без соответствующего флага) по умолчанию могут не передавать заголовок `Accept-Encoding`, поэтому его нужно указывать явно, чтобы сервер отдавал сжатый контент.


4.  **Онлайн-инструменты:**
    *   **Squash Compression Benchmark:** Позволяет сравнить различные алгоритмы и уровни сжатия для разных типов файлов и сетевых условий. Этот инструмент также позволяет визуализировать компромисс между временем сжатия и временем передачи данных для различных скоростей сети.
