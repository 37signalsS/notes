# Оптимальная настройка TLS/SSL в Nginx

## Определения

### Процесс установки соединения (Handshake)

1.  **TCP Handshake:** Устанавливается стандартное TCP-соединение.
2.  **[TLS Handshake](../../../Networking/Protocols/tls.md#5-процесс-рукопожатия-tls-handshake):**
    *   Сервер отправляет клиенту свой публичный сертификат.
    *   Клиент проверяет валидность сертификата (срок действия, цепочку доверия).
    *   Клиент и сервер договариваются о сессионном ключе (master key) с использованием **[асимметричного шифрования](../../../Networking/Protocols/tls.md#гибридная-схема-в-tls)**. Этот процесс вычислительно дорогой.
    *   Дальнейший обмен данными происходит с использованием **[симметричного шифрования](../../../Networking/Protocols/tls.md#гибридная-схема-в-tls)**, которое значительно быстрее и эффективнее для больших объемов трафика.

### Иерархия и цепочка сертификатов

Для успешной проверки подлинности сервера клиент должен иметь возможность проверить всю цепочку сертификатов.

*   **Корневой сертификат (Root CA):** Предустановлен в операционной системе или браузере. Является вершиной цепочки доверия.
*   **Промежуточный сертификат (Intermediate CA):** Сертификат, выданный корневым центром и используемый для подписи сертификатов конечных пользователей. Их может быть несколько.
*   **Серверный сертификат (Server Certificate):** Сертификат, выданный для вашего домена.

При настройке Nginx необходимо предоставить файл, содержащий **цепочку сертификатов**: сначала ваш серверный сертификат, затем все промежуточные. Корневой сертификат включать не нужно.

```plaintext
-----BEGIN CERTIFICATE-----
(Ваш серверный сертификат)
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----
(Промежуточный сертификат)
-----END CERTIFICATE-----
```

Для установки вам понадобятся два файла:

1.  **Файл цепочки сертификатов (`fullchain.pem`): Содержит ваш сертификат + все промежуточные.**
2.  **Приватный ключ (`privkey.pem`): Секретный ключ, сгенерированный вместе с запросом на сертификат (CSR).**

## Основные понятия 

### Perfect Forward Secrecy (PFS)

PFS обеспечивается эфемерными алгоритмами обмена ключами (например, ECDHE, DHE). Это означает, что для каждой сессии создается уникальный временной ключ. Если приватный ключ сервера будет скомпрометирован, злоумышленник не сможет расшифровать ранее перехваченный трафик, так как каждый сессионный ключ уникален и не может быть восстановлен из скомпрометированного долгосрочного ключа.

### Strict-Transport-Security (HSTS)

HSTS — это заголовок HTTP-ответа, который указывает браузеру взаимодействовать с сайтом только по HTTPS. Это предотвращает атаки понижения версии протокола и гарантирует, что даже при вводе `http://` в адресную строку браузер автоматически переключится на `https://`.

### OCSP Stapling

OCSP Stapling — это механизм, при котором сервер сам получает подписанный ответ от центра сертификации (CA) о текущем статусе своего сертификата и "прикрепляет" (staple) этот ответ к TLS-рукопожатию. Это избавляет клиент от необходимости делать отдельный запрос к OCSP-серверу CA, что ускоряет установку соединения и повышает приватность.

### HTTP/2 и HTTP/3 (QUIC)

Современные протоколы HTTP/2 и HTTP/3 (на базе QUIC) значительно ускоряют загрузку сайтов по сравнению с HTTP/1.1 благодаря мультиплексированию запросов по одному соединению, сжатию заголовков, приоритизации потоков и другим оптимизациям. HTTP/3 дополнительно использует UDP вместо TCP, что снижает задержки и улучшает устойчивость к потере пакетов.

### Mutual TLS (mTLS)

mTLS — это механизм взаимной аутентификации, при котором не только клиент проверяет сертификат сервера, но и сервер проверяет сертификат клиента. Это гарантирует, что к сервису могут подключаться только доверенные клиенты, имеющие валидный сертификат, выданный определенным центром сертификации (CA). mTLS является ключевым компонентом для обеспечения безопасной коммуникации между сервисами в архитектуре [Service Mesh](../../../Concepts/service_mesh_overview.md).
