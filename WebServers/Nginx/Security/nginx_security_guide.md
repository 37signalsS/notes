# Руководство по безопасности веб-сервера Nginx

## 1. Защита от DoS/DDoS-атак

### 1.1. Общие сведения об атаках

Защита от атак типа «отказ в обслуживании» (DoS/DDoS) — комплексная задача. Важно понимать их природу и почему защита на уровне одного веб-сервера имеет серьезные ограничения.

Подробный разбор типов атак (L3/L4, L7), их проблем и эффективных методов противодействия вынесен в основную заметку:
-   **[Обзор атак типа «Отказ в обслуживании» (DoS/DDoS)](../../../Networking/Concepts/dos_ddos_overview.md)**

Ключевой вывод заключается в том, что для защиты от масштабных атак необходимо использовать специализированные внешние сервисы.

### 1.2. Ограничение частоты запросов (`limit_req`)

Для защиты от **примитивных DoS-атак** (флуд с одного или нескольких IP) и подбора паролей (брутфорс) можно использовать встроенный в Nginx модуль `limit_req`.

1.  **Определение зоны (в блоке `http`):**
    ```nginx
    # Создаем зону 'one' размером 10МБ для хранения состояний по IP-адресам.
    # Разрешенная частота - 5 запросов в секунду.
    limit_req_zone $binary_remote_addr zone=one:10m rate=5r/s;
    ```
    -   `$binary_remote_addr`: Ключ для отслеживания (IP-адрес клиента в бинарном виде, занимает меньше памяти).

2.  **Применение ограничения (в блоке `location`):**
    ```nginx
    location /login {
        # Применяем зону 'one'.
        # burst=10: Позволяет обработать до 10 запросов, превышающих лимит.
        # nodelay: Запросы в рамках burst обрабатываются немедленно, а не с задержкой. Полезно для API.
        limit_req zone=one burst=10 nodelay;

        proxy_pass http://backend;
    }
    ```
-   **Как это работает:** Nginx пропустит 5 запросов в секунду от одного IP. Следующие 10 запросов (burst) будут обработаны немедленно, но все последующие запросы в этой секунде будут отклонены с ошибкой `503 Service Unavailable`.
-   **Ограничения:** Этот метод неэффективен против распределенных атак (DDoS) и может заблокировать легитимных пользователей, работающих из-под одного NAT (например, большой офис). Подробнее см. в [общем обзоре DoS/DDoS атак](../../../Networking/Concepts/dos_ddos_overview.md).

## 2. Контроль доступа

### 2.1. Ограничение доступа по IP-адресу

Для административных панелей, служебных каталогов и внутренних API следует ограничивать доступ по IP.

```nginx
location /admin {
    allow 192.168.1.10; # IP-адрес офиса
    allow 10.0.0.0/8;    # Локальная подсеть
    deny all;            # Запретить всем остальным

    # ...
}
```
Правила обрабатываются по порядку. Первое совпадение определяет действие.

### 2.2. Базовая аутентификация (`auth_basic`)

Nginx может защитить часть сайта паролем с помощью базовой HTTP-аутентификации. Это простой способ ограничить доступ к административным панелям или внутренним ресурсам.

#### Принцип работы

1.  При первом запросе к защищенному ресурсу Nginx отвечает кодом `401 Unauthorized` и заголовком `WWW-Authenticate`.
2.  Браузер отображает стандартное окно для ввода логина и пароля.
3.  После ввода данных браузер повторяет запрос, добавляя заголовок `Authorization` с закодированными учетными данными.
4.  Nginx проверяет эти данные по файлу с паролями.

#### Пример конфигурации

```nginx
location /admin/ {
    auth_basic "Admin Area";
    auth_basic_user_file /etc/nginx/htpasswd;

    # ... остальная конфигурация
}
```

-   `auth_basic "Admin Area"`: Текст, который увидит пользователь в окне аутентификации.
-   `auth_basic_user_file`: Путь к файлу с парами `логин:хэш_пароля`.

Файл с паролями создается с помощью утилиты `htpasswd` (обычно из пакета `apache2-utils`):

```bash
# Создать файл и добавить первого пользователя
sudo htpasswd -c /etc/nginx/htpasswd username

# Добавить следующих пользователей (без -c)
sudo htpasswd /etc/nginx/htpasswd another_user
```

> **Важно:** Базовая аутентификация передает логин и пароль в легко декодируемом виде (Base64), поэтому ее **необходимо** использовать только совместно с [настроенным TLS/SSL (HTTPS)](./nginx_tls_ssl_configuration.md), чтобы избежать перехвата учетных данных.

### 2.3. Защита конфиденциальных файлов и каталогов

```nginx
# Блокировка доступа к файлам систем контроля версий, конфигурационным файлам и т.д.
location ~ /\.(git|svn|ht|env) {
    deny all;
    return 404; # Можно вернуть 404, чтобы скрыть факт существования
}

# Блокировка доступа ко всем скрытым файлам (начинающимся с точки)
location ~ /\. {
    deny all;
    return 404;
}
```

### 2.4. Запрет на выполнение скриптов в каталогах загрузки

```nginx
location /uploads {
    # Отключаем выполнение PHP-скриптов
    location ~ \.php$ {
        return 403; # Или deny all;
    }

    # Можно также отключить другие типы исполняемых файлов
    location ~ \.(pl|py|sh|exe)$ {
        return 403;
    }
}
```

### 2.5. Отключение ненужных HTTP-методов

Каждый HTTP-метод, поддерживаемый веб-сервером, расширяет поверхность атаки. В большинстве случаев достаточно методов `GET`, `POST` и `HEAD`.

```nginx
if ($request_method !~ ^(GET|POST|HEAD)$) {
    return 405;
}
```
Это правило, размещенное в блоке `server`, будет отклонять все запросы с методами, отличными от разрешенных.

## 3. Усиление безопасности с помощью HTTP-заголовков

HTTP-заголовки безопасности — это инструкции для браузера, которые помогают защитить пользователей от атак на стороне клиента. Они добавляются с помощью директивы `add_header`.

> Для получения более полной информации по настройке HTTPS в Nginx, включая оптимизацию TLS-протоколов и шифров, см. [Оптимальная настройка TLS/SSL в Nginx](./nginx_tls_ssl_configuration.md).

```nginx
# Добавлять в блок server для HTTPS
server {
    listen 443 ssl;
    # ...

    # 1. Strict-Transport-Security (HSTS)
    # Заставляет браузер всегда использовать HTTPS. Включать только после полной отладки HTTPS.
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload";

    # 2. X-Frame-Options
    # Защищает от Clickjacking, запрещая встраивание страницы в iframe на других сайтах.
    add_header X-Frame-Options "SAMEORIGIN";

    # 3. X-Content-Type-Options
    # Предотвращает MIME-сниффинг, заставляя браузер доверять Content-Type от сервера.
    add_header X-Content-Type-Options "nosniff";

    # 4. X-XSS-Protection
    # Включает встроенный в старые браузеры фильтр XSS-атак.
    add_header X-XSS-Protection "1; mode=block";

    # 5. Content-Security-Policy (CSP)
    # Наиболее мощный заголовок, который определяет, с каких доменов можно загружать ресурсы.
    # Требует тщательной настройки.
    add_header Content-Security-Policy "default-src 'self'; script-src 'self' https://trusted.cdn.com;";
}
```

### Политика безопасности контента (CSP)

Content Security Policy (CSP) — это мощный инструмент защиты, позволяющий ограничивать источники контента (скриптов, стилей, изображений), который может загружать браузер. CSP особенно эффективна против атак типа Cross-Site Scripting (XSS), кражи данных и различных инъекций.

Механизм работает через HTTP-заголовок `Content-Security-Policy`, в котором сервер указывает браузеру, откуда можно загружать ресурсы. Если ресурс не разрешен политикой, браузер блокирует его.

**Примеры директив:**
-   `default-src 'self'`
: Правило по умолчанию. Разрешает загрузку ресурсов только с текущего домена.
-   `script-src 'self' https://trusted.cdn.com`
: Разрешает выполнение скриптов со своего домена и с `trusted.cdn.com`.
-   `object-src 'none'`
: Запрещает загрузку плагинов (например, Flash), что является хорошей практикой безопасности.
-   `upgrade-insecure-requests`
: Указывает браузерам автоматически преобразовывать HTTP-запросы в HTTPS для вашего домена.

**Важно:** Неправильно настроенная CSP может заблокировать работу вашего сайта. Начинайте с более мягкой политики и постепенно ужесточайте ее, используя директиву `Content-Security-Policy-Report-Only` для тестирования без реальной блокировки ресурсов.

## 4. Безопасная конфигурация и эксплуатация

### 4.1. Сокрытие версии сервера

По умолчанию Nginx указывает свою версию в заголовке `Server`. Эта информация полезна злоумышленникам: зная точную версию ПО, они могут подбирать эксплоиты под конкретные уязвимости. Сокрытие версии снижает риск эксплуатации автоматизированными сканерами и делает систему менее «заметной» для атакующих.

Чтобы скрыть версию, используйте директиву `server_tokens off;` в блоке `http` вашего `nginx.conf`. После этого сервер будет указывать только свое название (`nginx`), но не версию.

```nginx
# /etc/nginx/nginx.conf
http {
    server_tokens off;
    # ...
}
```
Для полного удаления заголовка `Server` требуются более сложные методы, например, использование модуля `ngx_http_headers_more_filter_module` или пересборка Nginx. При работе в режиме прокси, скрыть заголовок `Server` ответа бэкенда можно с помощью `proxy_hide_header Server;`.

### 4.2. Мониторинг и логирование

-   `access_log`: Фиксирует все запросы к серверу.
-   `error_log`: Записывает ошибки сервера.

Подробное руководство по настройке логирования в Nginx/Angie, включая форматы логов, условное логирование и ротацию, доступно в заметке: **[Логирование в Angie/Nginx](../../Angie/angie_logging.md)**.

```nginx
# В блоке http
access_log /var/log/nginx/access.log;
error_log /var/log/nginx/error.log warn; # Уровень warn, чтобы не пропустить важные события
```

### 4.3. Безопасные права доступа к файлам

Подробное описание принципов работы с правами доступа в Linux, командами `chown` и `chmod` доступно в заметке: **[Права доступа к файлам в Linux](../../../Linux/Security/Concepts/Linux_File_Permissions.md)**.

```bash
# Владельцем файлов Nginx должен быть root
sudo chown -R root:root /etc/nginx

# Ограничиваем права на запись
sudo chmod -R 750 /etc/nginx
sudo chmod 640 /etc/nginx/nginx.conf

# Владельцем файлов сайта должен быть отдельный пользователь, а группа — www-data (или nginx)
sudo chown -R myuser:www-data /var/www/mysite
sudo chmod -R 755 /var/www/mysite
```
