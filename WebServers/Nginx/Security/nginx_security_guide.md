# Руководство по безопасности веб-сервера Nginx

## Определения

* **DoS (Denial of Service — «отказ в обслуживании») / DDoS (Distributed Denial of Service — «распределённый отказ в обслуживании») — атаки**: Атаки, направленные на нарушение доступности сервисов.
* **Базовая аутентификация (`auth_basic`)**: Метод аутентификации в протоколе HTTP (HyperText Transfer Protocol), при котором учетные данные (логин:пароль) передаются в заголовке `Authorization` в кодировке Base64.
* **HTTP-заголовки безопасности**: Специальные заголовки протокола HTTP, предназначенные для защиты пользователей от различных атак на стороне клиента (например, XSS — Cross-Site Scripting, Clickjacking).
* **Content Security Policy (CSP)**: Мощный инструмент защиты, позволяющий ограничивать источники контента, который может загружать браузер, эффективно противодействуя XSS и другим инъекциям.
* **HSTS (HTTP Strict Transport Security)**: Механизм, предписывающий браузерам взаимодействовать с сайтом исключительно по безопасному протоколу HTTPS (HyperText Transfer Protocol Secure), предотвращая атаки понижения версии протокола.
* **SSL (Secure Sockets Layer) / TLS (Transport Layer Security)**: Протоколы шифрования, обеспечивающие безопасность передачи данных между клиентом и сервером. В современной практике под SSL обычно подразумевают его более защищенного преемника — TLS.

## Основные концепции

Защита веб-сервера Nginx включает в себя комплекс мер, направленных на предотвращение атак, контроль доступа и безопасную эксплуатацию.

### Защита от DoS/DDoS-атак

Защита от атак типа «отказ в обслуживании» — комплексная задача. Важно понимать их природу и почему защита на уровне одного веб-сервера имеет серьезные ограничения. Для защиты от масштабных атак необходимо использовать специализированные внешние сервисы.

Для защиты от **примитивных DoS-атак** (флуд с одного или нескольких IP — Internet Protocol) и подбора паролей (брутфорс) можно использовать встроенный в Nginx модуль `limit_req`. Он позволяет ограничивать частоту запросов от клиента.

Подробное руководство по настройке защиты от DoS и ограничению ресурсов:
> **[Защита от DoS-атак в Angie/Nginx](../../Angie/High_Load/dos_protection.md)**

### Контроль доступа

Механизмы контроля доступа позволяют ограничивать использование ресурсов сервера. Подробное руководство по всем методам контроля доступа (IP-фильтры, пароли, Auth Request, PAM) находится в профильной заметке:

> **[Контроль доступа в Angie/Nginx](../../Angie/angie_access_control.md)**

Основные методы включают:

* **Ограничение по IP-адресу**: разрешает доступ только доверенным сетям.
* **Базовая аутентификация (`auth_basic`)**: защита паролем (обязательно совместно с HTTPS).
* **Аутентификация через подзапрос**: делегирование проверки внешним сервисам.
* **Защита конфиденциальных файлов**: блокировка доступа к `.git`, `.env` и системным каталогам.
* **Отключение ненужных HTTP-методов**: снижение поверхности атаки.

### Усиление безопасности с помощью HTTP-заголовков

HTTP-заголовки безопасности — это инструкции для браузера, которые помогают защитить пользователей от атак на стороне клиента. Они добавляются с помощью директивы `add_header`. Параметр `always` гарантирует, что заголовок будет добавлен ко всем ответам, включая ошибки (например, 404, 500), а не только к успешным (коды 2xx, 3xx).

Наиболее мощный заголовок — **Content Security Policy (CSP)**, который определяет, с каких доменов можно загружать ресурсы.

### Безопасная конфигурация и эксплуатация

Этот раздел охватывает практики, направленные на снижение рисков, связанных с конфигурацией и повседневной эксплуатацией Nginx:

* **Сокрытие версии сервера**: По умолчанию Nginx указывает свою версию в заголовке `Server`. Эта информация полезна злоумышленникам для подбора эксплоитов. Сокрытие версии снижает риск эксплуатации автоматизированными сканерами.
* **Мониторинг и логирование**: `access_log` фиксирует все запросы к серверу, а `error_log` записывает ошибки. Это критически важно для обнаружения атак и устранения неполадок.
* **Безопасные права доступа к файлам**: Правильная настройка прав доступа к файлам и каталогам Nginx и веб-приложений предотвращает несанкционированный доступ и модификацию.

## Практические сценарии

### Ограничение частоты запросов (`limit_req`)

1. **Определение зоны (в блоке `http`):**

    ```nginx
    # Создаем зону 'one' размером 10МБ для хранения состояний по IP-адресам.
    # Разрешенная частота - 5 запросов в секунду.
    limit_req_zone $binary_remote_addr zone=one:10m rate=5r/s;
    ```

    * `$binary_remote_addr`: Ключ для отслеживания (IP-адрес клиента в бинарном виде, занимает меньше памяти).

2. **Применение ограничения (в блоке `location`):**

    ```nginx
    location /login {
        # Применяем зону 'one'.
        # burst=10: Позволяет обработать до 10 запросов, превышающих лимит.
        # nodelay: Запросы в рамках burst обрабатываются немедленно, а не с задержкой. Полезно для API (Application Programming Interface).
        limit_req zone=one burst=10 nodelay;

        proxy_pass http://backend;
    }
    ```

* **Как это работает:** Nginx пропустит 5 запросов в секунду от одного IP. Следующие 10 запросов (burst) будут обработаны немедленно, но все последующие запросы в этой секунде будут отклонены с ошибкой `503 Service Unavailable`.
* **Ограничения:** Этот метод неэффективен против распределенных атак (DDoS) и может заблокировать легитимных пользователей, работающих из-под одного NAT (Network Address Translation — например, большой офис). Подробнее см. в [общем обзоре DoS/DDoS атак](../../../Networking/Concepts/dos_ddos_overview.md).

### Ограничение количества HTTP-заголовков (`max_headers`)

Директива `max_headers` (добавлена в **nginx 1.29.8**) ограничивает максимальное количество HTTP-заголовков в запросе клиента. При превышении лимита сервер возвращает `400 Bad Request`.

```nginx
http {
    # Лимит количества заголовков (по умолчанию ~100)
    max_headers 100;
}
```

**Зачем это нужно:**

* **Защита от DoS:** Злоумышленник может отправить запрос с огромным количеством заголовков, вынуждая сервер тратить память и CPU (Central Processing Unit / центральный процессор) на их парсинг.
* **Предсказуемость ресурсов:** Ограничение гарантирует, что каждый запрос потребит не более ожидаемого объёма памяти на обработку заголовков.
* **Совместимость с реальным миром:** Подавляющее большинство легитимных запросов содержат менее 20 заголовков, поэтому лимит в 100 не влияет на нормальных пользователей.

### Защита конфиденциальных файлов и каталогов

Блокировка доступа к файлам систем контроля версий, конфигурационным файлам и другим скрытым ресурсам. Подробно о механизме `deny`: **[Контроль доступа в Angie/Nginx](../../Angie/angie_access_control.md)**.

```nginx
# Блокировка доступа к файлам систем контроля версий, конфигурационным файлам и т.д.
location ~ /\.(git|svn|ht|env) {
    deny all;
    return 404; # Можно вернуть 404, чтобы скрыть факт существования
}

# Блокировка доступа ко всем скрытым файлам (начинающимся с точки)
location ~ /\. {
    deny all;
    return 404;
}
```

### Запрет на выполнение скриптов в каталогах загрузки

```nginx
location /uploads {
    # Отключаем выполнение скриптов PHP (Hypertext Preprocessor)
    location ~ \.php$ {
        return 403; # Или deny all;
    }

    # Можно также отключить другие типы исполняемых файлов
    location ~ \.(pl|py|sh|exe)$ {
        return 403;
    }
}
```

### Отключение ненужных HTTP-методов

Каждый HTTP-метод, поддерживаемый веб-сервером, расширяет поверхность атаки. В большинстве случаев достаточно методов `GET`, `POST` и `HEAD`.

```nginx
if ($request_method !~ ^(GET|POST|HEAD)$) {
    return 405;
}
```

Это правило, размещенное в блоке `server`, будет отклонять все запросы с методами, отличными от разрешенных.

### Установка HTTP-заголовков безопасности

```nginx
# Добавлять в блок server для HTTPS
server {
    listen 443 ssl;
    # ...

    # 1. Strict-Transport-Security (HSTS)
    # Заставляет браузер всегда использовать HTTPS. Включать только после полной отладки HTTPS.
    
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload";

    # 2. X-Frame-Options
    # Защищает от Clickjacking, запрещая встраивание страницы в iframe на других сайтах.

    add_header X-Frame-Options "SAMEORIGIN" always;

    # 3. X-Content-Type-Options
    # Запрещает браузеру "угадывать" (MIME-сниффинг, MIME — Multipurpose Internet Mail Extensions) тип контента.

    add_header X-Content-Type-Options "nosniff" always;

    # 4. Referrer-Policy
    # Контролирует, какая информация о реферере (источнике перехода) будет отправлена при навигации.

    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    # 5. X-XSS-Protection
    # Отключает устаревший и небезопасный встроенный в браузеры XSS-фильтр.

    add_header X-XSS-Protection "0" always;

    # 6. Content-Security-Policy (CSP)
    # Наиболее мощный заголовок, который определяет, с каких доменов можно загружать ресурсы.
    add_header Content-Security-Policy "default-src 'self'; script-src 'self' https://trusted.cdn.com; style-src 'self'; object-src 'none';" always;
}
```

### Политика безопасности контента (CSP) - Примеры директив

* `default-src 'self'`: Правило по умолчанию. Разрешает загрузку ресурсов только с текущего домена.
* `script-src 'self' https://trusted.cdn.com`: Разрешает выполнение скриптов со своего домена и с доверенных сетей доставки контента (CDN — Content Delivery Network).
* `style-src 'self'`: Разрешает загрузку стилей CSS (Cascading Style Sheets) только со своего домена.
* `object-src 'none'`: Запрещает загрузку плагинов (например, Flash), что является хорошей практикой безопасности.
* `upgrade-insecure-requests`: Указывает браузерам автоматически преобразовывать HTTP-запросы в HTTPS для вашего домена.

**Важно:** Неправильно настроенная CSP может заблокировать работу вашего сайта. Начинайте с более мягкой политики и постепенно ужесточайте ее, используя директиву `Content-Security-Policy-Report-Only` для тестирования без реальной блокировки ресурсов.

### Сокрытие версии сервера

Чтобы скрыть версию, используйте директиву `server_tokens off;` в блоке `http` вашего `nginx.conf`. После этого сервер будет указывать только свое название (`nginx`), но не версию.

```nginx
# /etc/nginx/nginx.conf
http {
    server_tokens off;
    # ...
}
```

Для полного удаления заголовка `Server` требуются более сложные методы, например, использование модуля `ngx_http_headers_more_filter_module` или пересборка Nginx. При работе в режиме прокси, скрыть заголовок `Server` ответа бэкенда можно с помощью `proxy_hide_header Server;`.

### Настройка логирования

```nginx
# В блоке http
access_log /var/log/nginx/access.log;
error_log /var/log/nginx/error.log warn; # Уровень warn, чтобы не пропустить важные события
```

Подробное руководство по настройке логирования в Nginx/Angie, включая форматы логов, условное логирование и ротацию, доступно в заметке: [Логирование в Angie/Nginx](../../Angie/angie_logging.md).

### Настройка прав доступа к файлам

```bash
# Владельцем файлов Nginx должен быть root
sudo chown -R root:root /etc/nginx

# Ограничиваем права на запись
sudo chmod -R 750 /etc/nginx
sudo chmod 640 /etc/nginx/nginx.conf

# Владельцем файлов сайта должен быть отдельный пользователь, а группа — www-data (или nginx)
sudo chown -R myuser:www-data /var/www/mysite
sudo chmod -R 755 /var/www/mysite
```

Подробное описание принципов работы с правами доступа в Linux, командами `chown` и `chmod` доступно в заметке: [Права доступа к файлам в Linux](../../../Linux/Security/Concepts/File_Permissions/overview_definitions.md).
