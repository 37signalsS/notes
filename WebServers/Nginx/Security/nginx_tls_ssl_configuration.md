# Оптимальная настройка TLS/SSL в Nginx

## Определения

### Процесс установки соединения (Handshake)

1.  **TCP Handshake:** Устанавливается стандартное TCP-соединение.
2.  **[TLS Handshake](../../../Networking/Protocols/tls.md#5-процесс-рукопожатия-tls-handshake):**
    *   Сервер отправляет клиенту свой публичный сертификат.
    *   Клиент проверяет валидность сертификата (срок действия, цепочку доверия).
    *   Клиент и сервер договариваются о сессионном ключе (master key) с использованием **[асимметричного шифрования](../../../Networking/Protocols/tls.md#гибридная-схема-в-tls)**. Этот процесс вычислительно дорогой.
    *   Дальнейший обмен данными происходит с использованием **[симметричного шифрования](../../../Networking/Protocols/tls.md#гибридная-схема-в-tls)**, которое значительно быстрее и эффективнее для больших объемов трафика.

### Иерархия и цепочка сертификатов

Для успешной проверки подлинности сервера клиент должен иметь возможность проверить всю цепочку сертификатов.

*   **Корневой сертификат (Root CA):** Предустановлен в операционной системе или браузере. Является вершиной цепочки доверия.
*   **Промежуточный сертификат (Intermediate CA):** Сертификат, выданный корневым центром и используемый для подписи сертификатов конечных пользователей. Их может быть несколько.
*   **Серверный сертификат (Server Certificate):** Сертификат, выданный для вашего домена.

При настройке Nginx необходимо предоставить файл, содержащий **цепочку сертификатов**: сначала ваш серверный сертификат, затем все промежуточные. Корневой сертификат включать не нужно.

```plaintext
-----BEGIN CERTIFICATE-----
(Ваш серверный сертификат)
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----
(Промежуточный сертификат)
-----END CERTIFICATE-----
```

Для установки вам понадобятся два файла:

1.  **Файл цепочки сертификатов (`fullchain.pem`): Содержит ваш сертификат + все промежуточные.**
2.  **Приватный ключ (`privkey.pem`): Секретный ключ, сгенерированный вместе с запросом на сертификат (CSR).**

## Основные понятия 

### Perfect Forward Secrecy (PFS)

PFS обеспечивается эфемерными алгоритмами обмена ключами (например, ECDHE, DHE). Это означает, что для каждой сессии создается уникальный временной ключ. Если приватный ключ сервера будет скомпрометирован, злоумышленник не сможет расшифровать ранее перехваченный трафик, так как каждый сессионный ключ уникален и не может быть восстановлен из скомпрометированного долгосрочного ключа.

### Strict-Transport-Security (HSTS)

HSTS — это заголовок HTTP-ответа, который указывает браузеру взаимодействовать с сайтом только по HTTPS. Это предотвращает атаки понижения версии протокола и гарантирует, что даже при вводе `http://` в адресную строку браузер автоматически переключится на `https://`.

### OCSP Stapling

OCSP Stapling — это механизм, при котором сервер сам получает подписанный ответ от центра сертификации (CA) о текущем статусе своего сертификата и "прикрепляет" (staple) этот ответ к TLS-рукопожатию. Это избавляет клиент от необходимости делать отдельный запрос к OCSP-серверу CA, что ускоряет установку соединения и повышает приватность.

### HTTP/2 и HTTP/3 (QUIC)

Современные протоколы HTTP/2 и HTTP/3 (на базе QUIC) значительно ускоряют загрузку сайтов по сравнению с HTTP/1.1 благодаря мультиплексированию запросов по одному соединению, сжатию заголовков, приоритизации потоков и другим оптимизациям. HTTP/3 дополнительно использует UDP вместо TCP, что снижает задержки и улучшает устойчивость к потере пакетов.

### Mutual TLS (mTLS)

mTLS — это механизм взаимной аутентификации, при котором не только клиент проверяет сертификат сервера, но и сервер проверяет сертификат клиента. Это гарантирует, что к сервису могут подключаться только доверенные клиенты, имеющие валидный сертификат, выданный определенным центром сертификации (CA). mTLS является ключевым компонентом для обеспечения безопасной коммуникации между сервисами в архитектуре [Service Mesh](../../../Concepts/service_mesh_overview.md).

## Практические сценарии

### Практическая конфигурация Nginx

> **Важно:** Для полной поддержки TLS 1.3 и современных шифров убедитесь, что Nginx собран с OpenSSL версии 1.1.1 или выше. Проверить версию можно командой `nginx -V` (искать строку `built with OpenSSL ...`). Если используется старая версия, возможно, потребуется пересборка Nginx или использование PPA с более свежей сборкой.

Настройки могут располагаться как в основном файле `nginx.conf` (в секции `http`), так и в файле конкретного виртуального хоста.

### Глобальные параметры TLS (в `nginx.conf`)

Эти настройки применяются ко всему серверу и оптимизируют работу TLS. Их следует размещать в файле `nginx.conf` внутри блока `http`.

#### Keep-Alive соединения

Длительные keep-alive соединения позволяют клиентам повторно использовать одно TCP-соединение для нескольких HTTP-запросов, что значительно сокращает задержки, связанные с установкой новых соединений и TLS-рукопожатий (handshake).

```nginx
http {
    # ...
    keepalive_timeout 120s;
    keepalive_requests 10000;
    # ...
}
```
- `keepalive_timeout`: Устанавливает таймаут для keep-alive соединения.
- `keepalive_requests`: Максимальное количество запросов, которое можно сделать через одно keep-alive соединение.

#### Кэширование сессий TLS (Оптимизация производительности)

Полное "рукопожатие" TLS (handshake) — это ресурсоемкая операция. Директивы ниже позволяют кэшировать параметры сессии, чтобы ускорить повторные подключения от одного и того же клиента, позволяя ему выполнить быстрое, сокращенное рукопожатие.

##### Кэш на стороне сервера (`ssl_session_cache`)
Этот механизм используется для TLS 1.2 и ниже.

```nginx
http {
    # ...
    # Создает общую для всех worker-процессов Nginx зону в памяти
    # (названа SSL, размером 10 МБ), где хранятся параметры установленных сессий.
    # 10 МБ хватает примерно на 40 000 сессий.
    ssl_session_cache shared:SSL:10m;

    # Устанавливает время жизни сессии в кэше (у вас — 1 день).
    # Если клиент вернется в течение этого времени, сервер сможет выполнить быстрое,
    # сокращенное рукопожатие.
    ssl_session_timeout 1d;
    # ...
}
```

##### Билеты сессий (`ssl_session_tickets`)
Это альтернативный механизм возобновления сессий, при котором
зашифрованная информация о сессии хранится на стороне клиента.
Он является основным для TLS 1.3, но может использоваться и для TLS 1.2.

```nginx
# Рекомендуется отключать для повышения безопасности
ssl_session_tickets off;
```

> **Компромисс: `ssl_session_tickets off` vs `on`**
> Билеты сессий — это альтернативный механизм возобновления сессий, при котором зашифрованная информация о сессии хранится на стороне клиента. Хотя это может быть полезно в больших кластерах, этот механизм имел проблемы с безопасностью и может ослабить Perfect Forward Secrecy. Отключение (`off`) и использование кэша на стороне сервера является более безопасным и консервативным подходом.
>
> *   `on`: Улучшает производительность повторных подключений, так как позволяет восстановить сессию без полного handshake. Это поведение по умолчанию. Для работы в кластере можно настроить общий ключ шифрования билетов с помощью `ssl_session_ticket_key`.
> *   `off`: **(Рекомендуемый, более безопасный подход)**. Отключение этого механизма и использование кэша на стороне сервера (`ssl_session_cache`) является более консервативным подходом. `ssl_session_tickets` имели в прошлом проблемы с безопасностью и могут ослабить Perfect Forward Secrecy, так как при компрометации ключа шифрования билетов можно расшифровать все сессии, зашифрованные с его помощью.

#### Протоколы и шифры

##### `ssl_protocols`
Критически важная директива для безопасности. Она жестко ограничивает версии протоколов шифрования, которые сервер будет использовать.

```nginx
http {
    # ...
    # Разрешает только современные и безопасные версии — TLS 1.2 и TLS 1.3. От чего защищает: Запрещает использование устаревших и уязвимых протоколов (SSLv2, SSLv3, TLS 1.0, TLS 1.1), которые подвержены атакам вроде POODLE, BEAST и др.
    ssl_protocols TLSv1.2 TLSv1.3;
    # ...
}
```
Настройки шифров (`ssl_ciphers`) и порядка их предпочтения (`ssl_prefer_server_ciphers`) также имеют разумные значения по умолчанию. Для TLS 1.3 набор шифров стандартизирован и не требует настройки.

> **Наборы шифров (`ssl_ciphers`) для TLS 1.2 и ниже:**
>
> Эта длинная строка определяет набор шифров (cipher suite) — конкретные алгоритмы,
> которые будут использоваться для защиты соединения. Каждый шифр в списке — это
> комбинация из нескольких алгоритмов.
>
> Порядок важен, так как он задает приоритет, однако, если `ssl_prefer_server_ciphers on`, Nginx может игнорировать этот порядок и выбирать шифр из своего списка (часто AES256).
> Рекомендуется использовать комбинацию шифров для разной аппаратной поддержки:
> - AES (e.g., AES128-GCM): Имеет аппаратное ускорение на большинстве десктопных процессоров, обеспечивая высокую производительность.
> - ChaCha20 (e.g., CHACHA20-POLY1305): Показывает лучшую производительность на мобильных устройствах и процессорах без аппаратной поддержки AES.
> Данная строка является примером, для генерации актуальной конфигурации используйте Mozilla TLS Configurator.

```nginx
ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384';
```

> **`ssl_prefer_server_ciphers off` (современный подход)**: Эта настройка определяет, кто выбирает финальный шифр из списка — сервер или клиент.
> *   `on` (старый подход): Сервер сам выбирает первый подходящий шифр из своего списка `ssl_ciphers`, который поддерживается клиентом.
> *   `off` (современный подход): Сервер учитывает порядок предпочтений клиента. Современные браузеры умеют выбирать не только самый безопасный, но и самый производительный (для их устройства) шифр из тех, что предлагает сервер. Поэтому `off` сегодня считается хорошей практицией.
>
> Рекомендуется тестировать оба варианта для вашей конкретной нагрузки и клиентской базы.

> **`ssl_buffer_size`**: По умолчанию 16k. Это оптимальное значение для большинства случаев, так как оно соответствует размеру TLS-записи и позволяет избежать фрагментации, что повышает производительность. Изменение этого значения обычно не требуется. Уменьшение (например, до 8k) может улучшить отзывчивость (Time To First Byte), но незначительно увеличит нагрузку на CPU за счет большего числа пакетов.

```nginx
ssl_buffer_size 8k;
```

> **Параметры для обмена ключами Диффи-Хеллмана (`ssl_dhparam`)**
> Эта директива указывает путь к файлу с параметрами для алгоритма обмена ключами Диффи-Хеллмана (DHE, не ECDHE). Использование своих, заранее сгенерированных параметров достаточной длины (в вашем случае 2048 бит) значительно повышает безопасность по сравнению с стандартными, встроенными в OpenSSL. Это также необходимо
> для обеспечения Perfect Forward Secrecy.
>
> **Генерация файла:**
> ```bash
> openssl dhparam -out /etc/nginx/dhparam.pem 2048
> ```
> **Важно:** Эта директива не требуется для конфигураций, использующих только шифры на эллиптических кривых (ECDHE) и/или TLS 1.3.

```nginx
ssl_dhparam /etc/nginx/dhparam.pem;
```

> **Включает 0-RTT для TLS 1.3 (`ssl_early_data`)**, ускоряя повторные соединения:

```nginx
ssl_early_data on;
```

> **OCSP Stapling (`ssl_stapling`, `ssl_stapling_verify`, `resolver`)**

```nginx
ssl_stapling on;
ssl_stapling_verify on;
# Для работы ssl_stapling нужен DNS-резолвер
resolver 8.8.8.8 8.8.4.4 valid=300s;
resolver_timeout 5s;
```

### Настройка виртуального хоста (`server`)

Эти настройки применяются к конкретному сайту.

#### Базовая конфигурация HTTPS

```nginx
server {
    # Эта директива указывает Nginx слушать стандартный для HTTPS порт 443. Параметр `ssl`
    # активирует обработку протокола TLS (и его устаревшего предшественника SSL) на этом порту. Без него Nginx ожидал бы на этом порту обычный, нешифрованный HTTP-трафик.
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name your_domain.com;

    ssl_certificate /path/to/your_cert.pem;
    ssl_certificate_key /path/to/your_key.pem;

    # Это пара ключей, которые являются основой аутентификации сервера.
    # * `ssl_certificate`: Путь к публичному сертификату. Этот файл сервер отправляет каждому клиенту (браузеру) при установке соединения. Он содержит информацию о домене и публичный ключ. `fullchain.pem` обычно включает сам сертификат сервера и цепочку сертификатов удостоверяющих центров.
    # * `ssl_certificate_key`: Путь к приватному ключу. Этот файл — секрет вашего сервера. Он должен быть надежно защищен. С его помощью сервер доказывает, что именно он является владельцем публичного сертификата, и он используется в процессе шифрования.

    # Заголовок Strict-Transport-Security (HSTS), который дает браузеру команду общаться с сайтом только по HTTPS.
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;

    # ... остальная конфигурация сайта
    location / {
        # ...
    }
}
```
- `listen 443 ssl`: Указывает Nginx слушать порт 443 и использовать SSL/TLS.
- `ssl_certificate`: Путь к файлу сертификата (включая промежуточные).
- `ssl_certificate_key`: Путь к файлу приватного ключа.

### Перенаправление с HTTP на HTTPS

Для SEO и безопасности важно, чтобы основной версией сайта была HTTPS-версия. Все HTTP-запросы должны перенаправляться с кодом `301 Moved Permanently`.

```nginx
server {
    listen 80;
    server_name your_domain.com www.your_domain.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl; # ... и далее конфигурация HTTPS
    # ...
}
```
> **Примечание:** При отладке используйте `302` редирект, так как `301` агрессивно кэшируется браузерами.

### Включение HTTP/2 и HTTP/3

Nginx поддерживает HTTP/2 и HTTP/3 (QUIC) для повышения производительности веб-приложений. Подробную информацию о принципах их работы и тонкостях настройки можно найти в документе [Конфигурация HTTP/2 и HTTP/3 в Nginx](../Performance/nginx_http_versions.md).

#### Конфигурация HTTP/2

Для включения HTTP/2 достаточно добавить параметр `http2` к директиве `listen`:

```nginx
server {
    listen 443 ssl http2; # Включаем HTTP/2
    # ...
}
```

#### Конфигурация HTTP/3 (QUIC)

Настройка HTTP/3 требует использования UDP-порта и анонсирования поддержки QUIC. Пример базовой конфигурации:

```nginx
server {
    listen 443 ssl http2;
    listen 443 quic reuseport; # Включаем QUIC (HTTP/3)

    http3 on; # Включаем поддержку HTTP/3
    add_header Alt-Svc 'h3=":443"; ma=86400'; # Анонсируем поддержку HTTP/3

    # ...
}
```

#### DNS-запись типа HTTPS

Дополнительно можно использовать DNS-запись типа `HTTPS` для информирования клиентов о поддержке HTTP/2 и HTTP/3:

```dns
your_domain.com. IN HTTPS 1 . alpn="h2,h3"
```

### Использование EC и RSA сертификатов

Для максимальной производительности и совместимости рекомендуется использовать сертификаты на основе эллиптических кривых (ECDSA). Однако для поддержки очень старых клиентов может потребоваться RSA-сертификат. Nginx позволяет указать оба типа сертификатов одновременно.

```nginx
server {
    # ...
    # EC сертификат (предпочтительный)
    ssl_certificate /path/to/your_ec_cert.pem;
    ssl_certificate_key /path/to/your_ec_key.pem;

    # RSA сертификат (для совместимости)
    ssl_certificate /path/to/your_rsa_cert.pem;
    ssl_certificate_key /path/to/your_rsa_key.pem;
    # ...
}
```
Nginx автоматически выберет подходящий сертификат в зависимости от того, что поддерживает клиент.

### Аутентификация по клиентским SSL-сертификатам (mTLS)

Это руководство предполагает, что у вас уже есть:

1.  Созданный [центр сертификации (CA)](../../Security/Tools/openssl_ca_management.md) (корневой или промежуточный).
2.  Сертификат для вашего сервера (например, `server.crt`), подписанный вашим CA.
3.  Сертификат для клиента (например, `client.crt`), подписанный вашим CA.

#### Основные директивы

1.  `ssl_client_certificate`: Указывает путь к файлу с доверенными сертификатами CA. Этот файл используется для проверки подлинности сертификата клиента. Если у вас двухуровневая архитектура, здесь указывается цепочка `промежуточный_сертификат + корневой_сертификат`.
2.  `ssl_crl`: Указывает путь к файлу со списком отозванных сертификатов (Certificate Revocation List, CRL). Nginx будет отвергать клиентов с отозванными сертификатами.
3.  `ssl_verify_client`: Включает режим проверки сертификата клиента.
    *   `off`: (По умолчанию) Сертификат не запрашивается.
    *   `on`: Проверка обязательна. Если клиент не предоставляет валидный сертификат (доверенный и не отозванный), соединение немедленно разрывается.
    *   `optional`: Сертификат запрашивается, но не является обязательным. Результат проверки доступен в переменной `$ssl_client_verify`, что позволяет реализовать разную логику в `location` для аутентифицированных и анонимных пользователей.
    *   `optional_no_ca`: Запрашивать сертификат, но не проверять его по CA. Используется в редких случаях, когда проверка выполняется на уровне приложения.

#### Сценарий 1: Простая конфигурация с единым CA

Это базовый сценарий, когда и сервер, и клиенты используют сертификаты, подписанные одним и тем же корневым CA.

```nginx
server {
    listen 443 ssl http2;
    server_name my-service.local;

    # Сертификат и ключ сервера
    ssl_certificate         /path/to/my-service.crt;
    ssl_certificate_key     /path/to/my-service.key;

    # --- Настройки mTLS ---

    # 1. Корневой сертификат для проверки клиентов
    ssl_client_certificate  /path/to/ca/ca.crt;

    # 2. Файл со списком отозванных сертификатов
    ssl_crl                 /path/to/ca/crl.pem;

    # 3. Включить строгую проверку клиента
    ssl_verify_client       on;

    location / {
        # Дополнительная проверка на уровне location.
        # При ssl_verify_client on; эта проверка избыточна,
        # но она обязательна при режиме optional.
        if ($ssl_client_verify != "SUCCESS") {
            return 403;
        }

        proxy_pass http://backend;
    }
}
```

#### Сценарий 2: Конфигурация с промежуточным CA (рекомендуемый)

В production-среде из соображений безопасности корневой CA почти никогда не используется для подписи сертификатов конечных сущностей. Вместо этого он подписывает один или несколько промежуточных CA (Intermediate CA), которые, в свою очередь, уже подписывают сертификаты серверов и клиентов.

Сначала подготовим единый файл с сертификатом сервера и цепочкой до корневого CA. Это лучшая практика, так как избавляет клиент от необходимости самому искать промежуточный сертификат.

```bash
cat my-service.crt intermediate-ca/ca-chain.crt > my-service.fullchain.crt
```

Теперь настроим Nginx так, чтобы он требовал от клиентов валидный сертификат, подписанный нашим **Intermediate CA**.

```nginx
server {
    listen 443 ssl http2;
    server_name my-service.local;

    # Сертификат сервера, включающий цепочку до корневого CA
    ssl_certificate         /path/to/my-service.fullchain.crt;
    ssl_certificate_key     /path/to/my-service.key;

    # --- Клиентская аутентификация (mTLS) ---

    # 1. Цепочка доверенных сертификатов для проверки клиентов.
    # Nginx будет доверять всем клиентам, чьи сертификаты подписаны
    # любым CA из этой цепочки.
    ssl_client_certificate  /path/to/intermediate-ca/ca-chain.crt;

    # 2. Файл со списком отозванных сертификатов (генерируется Intermediate CA)
    ssl_crl                 /path/to/intermediate-ca/crl/crl.pem;

    # 3. Включить строгую проверку клиента
    ssl_verify_client       on;
    
    # 4. Глубина проверки цепочки сертификата клиента.
    # Nginx проверит, что сертификат клиента подписан Intermediate CA,
    # а тот, в свою очередь, подписан Root CA (который есть в ssl_client_certificate).
    # Глубина по умолчанию: 1. Для Intermediate CA нужно минимум 2.
    # Цепочка: a_client.crt -> intermediate.crt. Глубина 2.
    ssl_verify_depth        2;

    location / {
        if ($ssl_client_verify != "SUCCESS") {
            return 403;
        }
        proxy_pass http://backend;
    }
}
```

#### Тестирование с помощью `curl`

`curl` — отличный инструмент для проверки mTLS.

*   **Попытка подключения без сертификата (ожидается ошибка):**

```bash
curl https://your.domain.com
```
Nginx вернет ошибку, так как сертификат не был предоставлен. В логах Nginx вы увидите сообщение `no required SSL certificate was sent`.

*   **Успешное подключение с валидным сертификатом:**

```bash
curl https://your.domain.com \
  --cert /path/to/client.crt \
  --key /path/to/client.key \
  --cacert /path/to/ca.crt
```
*   `--cert`: Путь к сертификату клиента.
*   `--key`: Путь к приватному ключу клиента.
*   `--cacert`: (Опционально, но рекомендуется) Путь к корневому сертификату CA для проверки сервера.

Эта команда должна выполниться успешно.

#### Передача данных о сертификате клиента в бэкенд

Nginx предоставляет информацию из сертификата клиента бэкенд-сервисам через переменные. Это позволяет реализовать логику авторизации на уровне приложения.

Основные переменные:
*   `$ssl_client_verify`: Статус проверки (`SUCCESS`, `FAILED:reason`, `NONE`).
*   `$ssl_client_s_dn`: Полное `distinguished name` (DN) субъекта сертификата (например, `/C=RU/O=MyOrg/CN=client1`).
*   `$ssl_client_s_dn_cn`: Common Name (CN) из DN субъекта.
*   `$ssl_client_serial`: Серийный номер сертификата.

Пример передачи данных в FastCGI/proxy:

```nginx
location / {
    proxy_pass http://my_backend;
    proxy_set_header X-Client-Verify $ssl_client_verify;
    proxy_set_header X-Client-DN $ssl_client_s_dn;
    proxy_set_header X-Client-CN $ssl_client_s_dn_cn;
}
```

## Дополнительная информация

### Проверка конфигурации

-   **Проверка синтаксиса:**
    ```bash
    sudo nginx -t
    ```
-   **Проверка открытых портов:**
    ```bash
    # Проверка TCP и UDP портов 443
    sudo ss -tlpn | grep 443
    # Для UDP-портов (например, для HTTP/3 QUIC)
    # Обратите внимание, что при использовании 'reuseport' может быть несколько записей для одного порта,
    # по одной на каждый worker-процесс Nginx.
    sudo ss -ulpn | grep 443
    ```
-   **Проверка TLS-соединения:**
    ```bash
    openssl s_client -connect your_domain.com:443 -servername your_domain.com
    ```
    Эта команда покажет детали TLS-рукопожатия и информацию о сертификате.
    Параметр `-servername` (Server Name Indication, SNI) критически важен, если на одном IP-адресе размещено несколько HTTPS-сайтов, чтобы Nginx мог выбрать правильный сертификат.

#### Браузер

В инструментах разработчика (DevTools) на вкладке "Network" можно увидеть используемую версию протокола (HTTP/1.1, H2, H3) для каждого запроса. На вкладке "Security" можно посмотреть детали сертификата и TLS-соединения.

#### Глубокий анализ с помощью SSL Labs

Используйте сервис [SSL Labs](https://www.ssllabs.com/ssltest/) для всесторонней оценки конфигурации. После сканирования обратите внимание на:
*   **Общая оценка (Overall Rating):** Должна быть A или A+.
*   **Certificate:** Проверяет корректность цепочки сертификатов. Ищите "Chain issues". Если есть проблемы, значит, вы предоставили неполную или неверную цепочку в `ssl_certificate`.
*   **Protocol Support:** Список поддерживаемых версий TLS. Убедитесь, что небезопасные протоколы (SSLv2, SSLv3, TLS 1.0, 1.1) отключены.
*   **Handshake Simulation:** Эмулирует подключение с различных клиентов (ОС и браузеров). Помогает понять, какие старые устройства потеряют доступ при отключении устаревших протоколов.
*   **Vulnerabilities:** Тестирование на известные уязвимости (BEAST, POODLE и т.д.). Все пункты должны быть "No" (зеленые).

### Совместимость с клиентами

При отключении устаревших версий TLS (1.0, 1.1) и использовании современных шифров, важно понимать, какие клиенты будут поддерживаться, а какие могут потерять доступ. Современная конфигурация Nginx, использующая TLS 1.2 и 1.3, обеспечивает хорошую совместимость с большинством актуальных устройств и браузеров.

#### Поддерживаемые клиенты (примеры):

*   **Android:** Начиная с версии 4.4 (TLS 1.2), далее все версии. TLS 1.3 появляется с Android 8.1.
*   **Windows:** Windows 7, Windows 10 (и более новые).
*   **Браузеры:**
    *   Chrome (начиная с версии 49 на XP, далее все актуальные).
    *   Firefox (актуальные версии).
    *   Edge (актуальные версии).
    *   Safari (начиная с версии 9 на macOS и iOS).
*   **Java:** Начиная с версии 8.
*   **OpenSSL:** Начиная с версии 1.0.1.
*   **Боты:** Все современные поисковые боты (Googlebot и т.д.).

#### Неподдерживаемые клиенты (примеры):

*   **Android:** Версии 2.x - 4.3.
*   **Windows XP:** Internet Explorer 6.
*   **Windows Vista:** Internet Explorer 7.
*   **Windows 7:** Internet Explorer 8, 9, 10.
*   **Java:** Версии 6, 7.
*   **OpenSSL:** Версия 0.9.8.
*   **Safari:** Версии 6-8.

**Важно:** Перед внедрением такой конфигурации в production, рекомендуется проанализировать статистику вашей аудитории, чтобы убедиться, что отключение поддержки устаревших клиентов не повлияет на критически важные сегменты пользователей. В некоторых случаях, для обеспечения совместимости с очень старыми, но важными клиентами, может потребоваться более мягкая конфигурация или использование отдельных `server` блоков для них.
