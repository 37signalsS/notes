# Оптимальная настройка TLS/SSL в Nginx

Этот документ представляет собой руководство по настройке TLS/SSL в веб-сервере Nginx, основанное на анализе лучших практик.

## 1. Основы работы TLS

Протокол TLS (Transport Layer Security), современная версия SSL, обеспечивает шифрование трафика между клиентом и сервером.

### Процесс установки соединения (Handshake)

1.  **TCP Handshake:** Устанавливается стандартное TCP-соединение.
2.  **TLS Handshake:**
    *   Сервер отправляет клиенту свой публичный сертификат.
    *   Клиент проверяет валидность сертификата (срок действия, цепочку доверия).
    *   Клиент и сервер договариваются о сессионном ключе (master key) с использованием **асимметричного шифрования**. Этот процесс вычислительно дорогой.
    *   Дальнейший обмен данными происходит с использованием **симметричного шифрования**, которое значительно быстрее и эффективнее для больших объемов трафика.

## 2. Иерархия и цепочка сертификатов

Для успешной проверки подлинности сервера клиент должен иметь возможность проверить всю цепочку сертификатов.

*   **Корневой сертификат (Root CA):** Предустановлен в операционной системе или браузере. Является вершиной цепочки доверия.
*   **Промежуточный сертификат (Intermediate CA):** Сертификат, выданный корневым центром и используемый для подписи сертификатов конечных пользователей. Их может быть несколько.
*   **Серверный сертификат (Server Certificate):** Сертификат, выданный для вашего домена.

При настройке Nginx необходимо предоставить файл, содержащий **цепочку сертификатов**: сначала ваш серверный сертификат, затем все промежуточные. Корневой сертификат включать не нужно.

```plaintext
-----BEGIN CERTIFICATE-----
(Ваш серверный сертификат)
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----
(Промежуточный сертификат)
-----END CERTIFICATE-----
```

Для установки вам понадобятся два файла:
1.  **Файл цепочки сертификатов (`fullchain.pem`):** Содержит ваш сертификат + все промежуточные.
2.  **Приватный ключ (`privkey.pem`):** Секретный ключ, сгенерированный вместе с запросом на сертификат (CSR).

## 3. Конфигурация Nginx

Настройки могут располагаться как в основном файле `nginx.conf` (в секции `http`), так и в файле конкретного виртуального хоста.

### 3.1. Глобальные параметры TLS (в `nginx.conf`)

Эти параметры влияют на все серверы, использующие SSL.

> **Важно:** Для полной поддержки TLS 1.3 и современных шифров убедитесь, что Nginx собран с OpenSSL версии 1.1.1 или выше. Проверить версию можно командой `nginx -V` (искать строку `built with OpenSSL ...`). Если используется старая версия, возможно, потребуется пересборка Nginx или использование PPA с более свежей сборкой.



```nginx
# Включает использование серверных наборов шифров.
# Эта настройка спорна:
# `on` заставляет сервер выбирать шифр из своего списка. Это может привести к выбору более "тяжелого" шифра (например, AES256), даже если клиент предпочитает более легкий (например, AES128). В некоторых случаях это может увеличить время рукопожатия (до 2 RTT) и нагрузку на CPU как сервера, так и клиента. Порядок шифров в `ssl_ciphers` может быть проигнорирован.
# `off` позволяет клиенту выбрать предпочтительный шифр. Это может ускорить рукопожатие до 1 RTT (особенно для мобильных клиентов) и снизить нагрузку, если клиент выбирает более эффективный для него шифр (например, AES128 или ChaCha20, если есть аппаратная поддержка).
# Рекомендуется тестировать оба варианта для вашей конкретной нагрузки и клиентской базы.
ssl_prefer_server_ciphers off;

# Рекомендуемые протоколы. Отключение TLS 1.0 и 1.1 повышает безопасность,
# так как эти версии признаны небезопасными и содержат уязвимости.
# Это может привести к потере совместимости со старыми клиентами (например, Android 4.x, старые браузеры),
# но сегодня считается, что платформы, не поддерживающие TLS 1.2, являются устаревшими и их поддержка нецелесообразна.
ssl_protocols TLSv1.2 TLSv1.3; # Рекомендованный минимум
# Наборы шифров для TLS 1.2 и ниже. Порядок важен, так как он задает приоритет,
# однако, если `ssl_prefer_server_ciphers on`, Nginx может игнорировать этот порядок
# и выбирать шифр из своего списка (часто AES256).
# Рекомендуется использовать комбинацию шифров для разной аппаратной поддержки:
# - AES (e.g., AES128-GCM): Имеет аппаратное ускорение на большинстве десктопных процессоров, обеспечивая высокую производительность.
# - ChaCha20 (e.g., CHACHA20-POLY1305): Показывает лучшую производительность на мобильных устройствах и процессорах без аппаратной поддержки AES.
# Данная строка является примером, для генерации актуальной конфигурации используйте Mozilla TLS Configurator.
ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384';

# Размер буфера для отправки данных. Значение по умолчанию — 16k.
# Уменьшение (например, до 8k) может улучшить отзывчивость (Time To First Byte), 
# но незначительно увеличит нагрузку на CPU за счет большего числа пакетов.
ssl_buffer_size 8k;

# Кэширование сессий для ускорения повторных подключений.
# ssl_session_cache хранит параметры сессии на стороне сервера.
# ssl_session_tickets шифрует параметры сессии и отправляет их клиенту, что лучше работает в распределенных системах.
# Однако, использование session tickets может ухудшать безопасность из-за повторяемости ключей шифрования между сессиями.
# Отключение может повысить безопасность, но снизить производительность повторных подключений.
# Можно использовать оба метода (cache и tickets), но рекомендуется тестировать.
ssl_session_cache shared:SSL:10m;
ssl_session_timeout 1d; # 1 день
ssl_session_tickets off; # Рекомендация Mozilla для повышения безопасности.


# Параметры для обмена ключами Диффи-Хеллмана (требуется для Forward Secrecy в старых шифрах)
# Не требуется для конфигураций, использующих только TLS 1.3.
# Генерируется командой: openssl dhparam -out /etc/nginx/dhparam.pem 2048
ssl_dhparam /etc/nginx/dhparam.pem;

# Включает 0-RTT для TLS 1.3, ускоряя повторные соединения
ssl_early_data on;

# OCSP Stapling - прикрепление ответа о статусе сертификата для ускорения проверки.
# Это избавляет клиент от необходимости самому обращаться к серверу OCSP.
# Плюсы: экономия RTT (особенно на мобильных), так как браузеру не нужно делать отдельный запрос к OCSP-серверу.
# Минусы: увеличивает размер TLS Handshake, что может помешать достижению 1-RTT Handshake в TLS 1.3, если сервер ранее не видел клиента.
# Для сертификатов Let's Encrypt браузеры часто не обращаются к OCSP-серверу, поэтому включение stapling может быть менее критичным, но все равно полезным для экономии RTT.
# Рекомендуется тестировать, как OCSP Stapling влияет на время рукопожатия для вашей конфигурации.
ssl_stapling on;
ssl_stapling_verify on;
# Для работы ssl_stapling нужен DNS-резолвер
resolver 8.8.8.8 8.8.4.4 valid=300s;
resolver_timeout 5s;
```

**Генератор конфигураций:** Для получения актуальных и безопасных настроек рекомендуется использовать [Mozilla SSL Configuration Generator](https://ssl-config.mozilla.org/).

### 3.2. Настройка редиректа с HTTP на HTTPS

Всегда настраивайте перенаправление с незащищенной версии сайта.

```nginx
server {
    listen 80;
    server_name your_domain.com www.your_domain.com;

    # Постоянный редирект на HTTPS
    return 301 https://$host$request_uri;
}
```
> **Примечание:** При отладке используйте `302` редирект, так как `301` агрессивно кэшируется браузерами.

### 3.3. Конфигурация HTTPS сервера

Основная секция, где описывается работа сайта по HTTPS.

```nginx
server {
    # Прослушивание 443 порта с SSL. http2 включает поддержку HTTP/2.
    listen 443 ssl http2;
    listen [::]:443 ssl http2;

    server_name your_domain.com;

    # Пути к файлам сертификата и ключа
    ssl_certificate /etc/letsencrypt/live/your_domain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/your_domain.com/privkey.pem;

    # Заголовок Strict-Transport-Security (HSTS)
    # Заставляет браузер всегда использовать HTTPS для этого сайта.
    # Включать только после полной уверенности в корректной работе HTTPS.
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload";

    # ... остальная конфигурация вашего сайта (root, location, etc.)
    location / {
        # ...
    }
}
```

## 4. Проверка и тестирование

1.  **Проверка синтаксиса Nginx:**
    ```bash
    sudo nginx -t
    ```
2.  **Перезагрузка конфигурации:**
    ```bash
    sudo systemctl reload nginx
    ```
3.  **Проверка в браузере:**
    Откройте сайт и убедитесь, что в адресной строке отображается замок. Для получения деталей откройте инструменты разработчика (F12), перейдите на вкладку **Security** и перезагрузите страницу. Здесь можно увидеть используемый протокол (TLS 1.3, QUIC), алгоритм обмена ключами и шифр (например, `AES_128_GCM`).

4.  **Глубокий анализ с помощью SSL Labs:**
    Используйте сервис [SSL Labs](https://www.ssllabs.com/ssltest/) для всесторонней оценки конфигурации. После сканирования обратите внимание на:
    *   **Общая оценка (Overall Rating):** Должна быть A или A+.
    *   **Certificate:** Проверяет корректность цепочки сертификатов. Ищите "Chain issues". Если есть проблемы, значит, вы предоставили неполную или неверную цепочку в `ssl_certificate`.
    *   **Protocol Support:** Список поддерживаемых версий TLS. Убедитесь, что небезопасные протоколы (SSLv2, SSLv3, TLS 1.0, 1.1) отключены.
    *   **Handshake Simulation:** Эмулирует подключение с различных клиентов (ОС и браузеров). Помогает понять, какие старые устройства потеряют доступ при отключении устаревших протоколов.
    *   **Vulnerabilities:** Тестирование на известные уязвимости (BEAST, POODLE и т.д.). Все пункты должны быть "No" (зеленые).

## 5. Совместимость с клиентами

При отключении устаревших версий TLS (1.0, 1.1) и использовании современных шифров, важно понимать, какие клиенты будут поддерживаться, а какие могут потерять доступ. Современная конфигурация Nginx, использующая TLS 1.2 и 1.3, обеспечивает хорошую совместимость с большинством актуальных устройств и браузеров.

### Поддерживаемые клиенты (примеры):

*   **Android:** Начиная с версии 4.4 (TLS 1.2), далее все версии. TLS 1.3 появляется с Android 8.1.
*   **Windows:** Windows 7, Windows 10 (и более новые).
*   **Браузеры:**
    *   Chrome (начиная с версии 49 на XP, далее все актуальные).
    *   Firefox (актуальные версии).
    *   Edge (актуальные версии).
    *   Safari (начиная с версии 9 на macOS и iOS).
*   **Java:** Начиная с версии 8.
*   **OpenSSL:** Начиная с версии 1.0.1.
*   **Боты:** Все современные поисковые боты (Googlebot и т.д.).

### Неподдерживаемые клиенты (примеры):

*   **Android:** Версии 2.x - 4.3.
*   **Windows XP:** Internet Explorer 6.
*   **Windows Vista:** Internet Explorer 7.
*   **Windows 7:** Internet Explorer 8, 9, 10.
*   **Java:** Версии 6, 7.
*   **OpenSSL:** Версия 0.9.8.
*   **Safari:** Версии 6-8.

**Важно:** Перед внедрением такой конфигурации в production, рекомендуется проанализировать статистику вашей аудитории, чтобы убедиться, что отключение поддержки устаревших клиентов не повлияет на критически важные сегменты пользователей. В некоторых случаях, для обеспечения совместимости с очень старыми, но важными клиентами, может потребоваться более мягкая конфигурация или использование отдельных `server` блоков для них.

## 6. HTTP/3 (QUIC)

Для включения HTTP/3 (который работает поверх UDP) используется директива `listen` с опцией `quic`.

```nginx
listen 443 quic reuseport;
listen [::]:443 quic reuseport;

# Также необходимо добавить заголовок Alt-Svc для информирования клиентов
add_header alt-svc 'h3-29=":443"; ma=86400';
```
> Поддержка HTTP/3 может требовать свежей версии Nginx и может находиться в экспериментальном состоянии.
