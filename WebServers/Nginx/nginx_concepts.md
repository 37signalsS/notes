# Ключевые концепции Nginx

## Основы HTTP протокола для работы с Nginx

-   **HTTP/1.0:** Старая версия. После каждого запроса TCP-соединение разрывалось.
-   **HTTP/1.1:** Наиболее распространенная версия. Ввела **keep-alive** соединения (позволяет отправлять несколько запросов в рамках одного TCP-соединения) и обязательный заголовок `Host`.
-   **HTTP/2:** Бинарный протокол, поддерживает мультиплексирование (одновременная передача нескольких запросов и ответов). Значительно ускоряет загрузку сайтов. Nginx поддерживает HTTP/2.
-   **HTTP/3:** Новейшая версия, работает поверх UDP (протокол QUIC), что еще больше снижает задержки.

### Структура HTTP-запроса

Клиент (браузер) отправляет на сервер текстовый запрос вида:

```http
GET /path/to/document HTTP/1.1
Host: your-domain.com
User-Agent: Mozilla/5.0
Accept-Language: en-US,en;q=0.5
```

-   **Первая строка:** `Метод (GET)` `URI (/path/to/document)` `Версия (HTTP/1.1)`.
-   **Заголовки (Headers):** Пары `ключ: значение`, которые передают дополнительную информацию.
    -   **`Host`:** Обязательный заголовок в HTTP/1.1. Именно по нему Nginx понимает, для какого сайта предназначен запрос. Это основа механизма **виртуальных хостов**.

## Виртуальные хосты (Server Blocks)

Виртуальные хосты позволяют одному серверу Nginx обслуживать множество сайтов (доменов) на одном IP-адресе. В терминологии Nginx они называются `server` блоками.

**Принцип работы:**
Nginx принимает запрос, смотрит на заголовок `Host` и ищет `server` блок, у которого `server_name` совпадает с этим заголовком.

**Пример конфигурации для двух сайтов:**

```nginx
# /etc/nginx/sites-enabled/site1.com.conf
server {
    listen 80;
    server_name site1.com www.site1.com;

    location / {
        return 200 "This is Site 1";
    }
}

# /etc/nginx/sites-enabled/site2.com.conf
server {
    listen 80;
    server_name site2.com www.site2.com;

    location / {
        return 200 "This is Site 2";
    }
}
```

-   Запрос с `Host: site1.com` будет обработан первым `server` блоком.
-   Запрос с `Host: site2.com` будет обработан вторым.

## Обработка запросов с помощью `location`

Директива `location` позволяет определить, как обрабатывать запросы к различным URI внутри одного сайта. Nginx выбирает `location` на основе сложного набора правил, включая точные совпадения, префиксы и регулярные выражения.

**Пример:**

```nginx
server {
    listen 80;
    server_name site1.com;

    # Обрабатывает запросы к корню сайта
    location / {
        return 200 "Main page";
    }

    # Обрабатывает запросы, начинающиеся с /admin/
    location /admin/ {
        return 200 "Admin section";
    }
}
```

-   Запрос `http://site1.com/` попадет в `location /`.
-   Запрос `http://site1.com/admin/users` попадет в `location /admin/`.

> ➡️ **Подробное руководство: [Глубокое погружение в директиву location в Nginx](./nginx_location_directive.md)**

## Директива `try_files`

Эта директива позволяет проверить существование файлов в указанном порядке и отдать первый найденный. Если ничего не найдено, выполняется последнее действие (обычно внутренняя переадресация или возврат кода ошибки).

Это мощный инструмент для реализации "красивых" URL и страниц-заглушек.

> ➡️ **Подробное руководство: [Правила Rewrite, Redirect и Директива try_files в Nginx](./nginx_rewrite_rules_and_try_files.md)**

**Пример со страницей "техобслуживания":**

```nginx
server {
    root /var/www/site;

    location / {
        # 1. Искать файл /var/www/site/maintenance.html
        # 2. Если не найден, искать файл, соответствующий URI запроса ($uri)
        # 3. Если не найден, искать директорию, соответствующую URI ($uri/)
        # 4. Если ничего не найдено, вернуть ошибку 404
        try_files /maintenance.html $uri $uri/ =404;
    }
}
```

Чтобы "закрыть" сайт на техобслуживание, достаточно создать файл `/var/www/site/maintenance.html`. Nginx будет автоматически отдавать его на все запросы. После удаления файла сайт снова заработает.

## Базовая аутентификация (`auth_basic`)

Nginx может защитить часть сайта паролем с помощью базовой HTTP-аутентификации.

### Принцип работы

1.  **Первый запрос:** Клиент (браузер) запрашивает защищенный ресурс (например, `/admin`).
2.  **Ответ сервера:** Nginx, видя директиву `auth_basic`, останавливает обработку и немедленно отвечает клиенту кодом `401 Unauthorized`. Вместе с кодом он отправляет заголовок `WWW-Authenticate: Basic realm="..."`, где `realm` — это текст, который будет показан в окне входа.
3.  **Диалог в браузере:** Браузер, получив ответ `401` с этим заголовком, понимает, что требуется аутентификация, и отображает стандартное окно для ввода логина и пароля.
4.  **Повторный запрос с авторизацией:** После того как пользователь вводит данные, браузер кодирует строку `логин:пароль` в формат Base64 и повторяет исходный запрос, на этот раз добавляя в него заголовок `Authorization: Basic <закодированная_строка>`.
5.  **Проверка на сервере:** Nginx получает повторный запрос, видит заголовок `Authorization`, декодирует его и сверяет логин и хэш пароля с данными из файла, указанного в `auth_basic_user_file`. Если данные верны, Nginx продолжает обработку запроса и возвращает защищенный контент. В противном случае он снова вернет `401`.

### Пример конфигурации

```nginx
location /admin/ {
    auth_basic "Admin Area";
    auth_basic_user_file /etc/nginx/htpasswd;

    # ... другие директивы
}
```

-   `auth_basic`: Текст, который увидит пользователь в окне аутентификации.
-   `auth_basic_user_file`: Путь к файлу с парами `логин:хэш_пароля`. Файл создается утилитой `htpasswd`.

> **Важно:** Базовая аутентификация передает логин и пароль в легко декодируемом виде (Base64), поэтому ее **необходимо** использовать только совместно с TLS/SSL (HTTPS).

### Продвинутое использование: `auth_basic` и `try_files`

Директивы вроде `return` или `rewrite` имеют высокий приоритет и могут выполняться **до** проверки `auth_basic`, что приведет к некорректной работе. Например, если в `location` одновременно находятся `auth_basic` и `return`, аутентификация не будет запрошена.

Чтобы обойти это, можно использовать `try_files` и **именованный location**.

**Проблема:**
```nginx
location /admin/ {
    auth_basic "Admin Area";
    auth_basic_user_file /etc/nginx/htpasswd;

    # Этот return выполнится до auth_basic, и пароль не будет запрошен
    return 200 "Secret admin content";
}
```

**Решение с именованным location:**

```nginx
server {
    # ...

    location /admin/ {
        auth_basic "Admin Area";
        auth_basic_user_file /etc/nginx/htpasswd;

        # 1. Пытаемся найти несуществующий файл
        # 2. Если не найден, делаем внутреннее перенаправление на именованный location @admin_content
        try_files $uri @admin_content;
    }

    # Именованный location. На него нельзя попасть извне.
    location @admin_content {
        return 200 "Secret admin content";
    }
}
```
В этом случае `auth_basic` гарантированно отработает до того, как управление будет передано в `location @admin_content`.
