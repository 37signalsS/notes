# Балансировка нагрузки с помощью Nginx

**Балансировка нагрузки** — это способ распределения запросов к приложению (сетевого трафика) между некоторым количеством устройств.

**Nginx можно использовать как:**
-   Веб-сервер;
-   Реверс-прокси и балансировка нагрузки;
-   Почтовый прокси-сервер;
-   И многое другое.

В данном руководстве описывается настройка системы, в которой Nginx выступает в роли обратного прокси (reverse proxy) и балансировщика нагрузки для нескольких бэкенд-серверов Apache, работающих на одном хосте.

## Общая архитектура

- **Nginx:** Принимает все входящие HTTP-запросы на стандартном порту 80.
- **Apache2:** Запущены три экземпляра, каждый из которых слушает свой уникальный порт (8080, 8081, 8082).
- **Nginx (Load Balancer):** Распределяет входящие запросы между тремя экземплярами Apache.

Это обеспечивает как отказоустойчивость (если один экземпляр Apache упадет, Nginx перенаправит трафик на работающие), так и горизонтальное масштабирование.

---

## Архитектура современного веб-приложения для масштабирования

Простая балансировка нагрузки — это только часть решения. Чтобы система была действительно масштабируемой и отказоустойчивой, бэкенд-серверы (в данном примере — Apache) должны быть спроектированы как **stateless** (не хранящие состояние).

Это означает, что любой запрос от одного и того же клиента может быть обработан любым из бэкенд-серверов без потери данных или сессии. Состояние приложения должно быть вынесено на отдельные, общие для всех бэкендов сервисы.

### Ключевые компоненты stateless-архитектуры:

1.  **Балансировщик нагрузки (Nginx):**
    *   Принимает трафик.
    *   **Терминирует TLS (SSL):** Расшифровка HTTPS-трафика происходит здесь, а к бэкендам запросы идут по внутреннему, незашифрованному HTTP, что снижает с них нагрузку.
    *   **Выполняет Health Checks:** Периодически опрашивает бэкенды, чтобы убедиться, что они работают. Если бэкенд не отвечает, балансировщик временно исключает его из ротации.
    *   Проксирует запросы к работающим бэкендам.

2.  **Бэкенд-серверы (веб-приложение):**
    *   Не хранят никаких данных локально (ни сессий, ни загруженных пользователем файлов).
    *   Все экземпляры содержат идентичный код.
    *   Могут быть легко добавлены или удалены для горизонтального масштабирования.

3.  **База данных (например, PostgreSQL, MySQL):**
    *   Хранит все основные данные приложения. Все бэкенды подключаются к одной и той же базе данных (или кластеру баз данных).

4.  **Кэш и сессии (например, Redis, Memcached):**
    *   Хранит временные данные: кэш страниц, результаты тяжелых запросов и, что очень важно, **пользовательские сессии**. Когда пользователь логинится на одном бэкенде, информация о его сессии сохраняется в Redis, и любой другой бэкенд может ее оттуда прочитать.

5.  **Файловое хранилище (например, S3, MinIO, GlusterFS):**
    *   Все файлы, загружаемые пользователями (аватары, документы), должны сохраняться не на локальный диск бэкенд-сервера, а в общее сетевое хранилище. Это гарантирует, что файлы будут доступны независимо от того, какой бэкенд обработает следующий запрос.

Такая архитектура позволяет легко масштабировать веб-приложение, просто добавляя новые экземпляры бэкенд-серверов за балансировщиком.

## Настройка и запуск нескольких экземпляров Apache

### Прослушивание портов

Первым шагом необходимо указать Apache, какие порты он должен слушать.

```bash
# Откройте файл /etc/apache2/ports.conf
sudo nano /etc/apache2/ports.conf
```

Добавьте в конец файла следующие строки:

```apache
Listen 8080
Listen 8081
Listen 8082
```

### Создание конфигураций сайтов

Теперь для каждого порта нужно создать отдельный файл конфигурации виртуального хоста.

Скопируйте конфигурацию по умолчанию для каждого экземпляра:

```bash
cd /etc/apache2/sites-available/
sudo cp 000-default.conf 8080.conf
sudo cp 000-default.conf 8081.conf
sudo cp 000-default.conf 8082.conf
```

### 1.3. Редактирование конфигураций сайтов

Откройте каждый новый файл (`8080.conf`, `8081.conf`, `8082.conf`) и внесите два изменения:

1.  Измените директиву `<VirtualHost *:80>` на порт, соответствующий имени файла (например, `<VirtualHost *:8080>`).
2.  Измените `DocumentRoot` на новый путь (например, `/var/www/8080`).

**Пример для `8080.conf`:**

```apache
<VirtualHost *:8080>
    ServerAdmin webmaster@localhost
    DocumentRoot /var/www/8080
    ErrorLog ${APACHE_LOG_DIR}/error.log
    CustomLog ${APACHE_LOG_DIR}/access.log combined
</VirtualHost>
```

Проделайте аналогичные изменения для `8081.conf` и `8082.conf`.

### Создание контента для сайтов

Создайте директории и тестовые страницы, чтобы визуально определять, какой бэкенд отвечает.

```bash
# Создаем директории
sudo mkdir /var/www/8080 /var/www/8081 /var/www/8082

# Создаем index.html для каждого сайта
echo "Response from Apache on port 8080" | sudo tee /var/www/8080/index.html
echo "Response from Apache on port 8081" | sudo tee /var/www/8081/index.html
echo "Response from Apache on port 8082" | sudo tee /var/www/8082/index.html
```

### Активация сайтов и перезапуск Apache

Для активации сайтов можно использовать утилиту `a2ensite`.

```bash
sudo a2ensite 8080.conf
sudo a2ensite 8081.conf
sudo a2ensite 8082.conf
```

> **Примечание:** `a2ensite` (Apache2 Enable Site) создает символическую ссылку из `/etc/apache2/sites-available/` в `/etc/apache2/sites-enabled/`. Это стандартный и рекомендуемый способ управления сайтами в Apache на Debian-подобных системах.

После активации перезапустите Apache:

```bash
sudo systemctl restart apache2
```

Проверьте, что Apache слушает указанные порты: `curl http://127.0.0.1:8080`.

## Настройка Nginx

### 1. Определение Upstream-группы

Ключевой элемент балансировки — директива `upstream`, которая объявляет именованную группу бэкенд-серверов.

```bash
# Создайте новый файл, например /etc/nginx/conf.d/upstream.conf
sudo nano /etc/nginx/conf.d/upstream.conf
```

Добавьте в него следующее содержимое:

```nginx
upstream apache_backend {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
}
```

Здесь `apache_backend` — это произвольное имя для группы серверов, которое будет использоваться в директиве `proxy_pass`.

### 2. Настройка проксирования (`proxy_pass`)

Теперь отредактируйте конфигурацию вашего сайта, чтобы он перенаправлял запросы на созданную upstream-группу.

```bash
# Откройте файл конфигурации вашего сайта
sudo nano /etc/nginx/sites-available/default
```

Найдите блок `location / { ... }` и измените его следующим образом:

```nginx
location / {
    # Перенаправляем запрос на группу серверов
    proxy_pass http://apache_backend;

    # Рекомендуемые заголовки для передачи информации о клиенте бэкенду
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```
Директива `proxy_pass` указывает Nginx установить новое HTTP-соединение с одним из серверов из группы `apache_backend` и перенаправить ему исходный запрос.

### 3. Проверка и перезапуск Nginx

Проверьте синтаксис конфигурации Nginx и перезапустите сервис.

```bash
sudo nginx -t
sudo systemctl restart nginx
```

## Методы и параметры балансировки

### Алгоритмы балансировки

Nginx поддерживает несколько алгоритмов распределения запросов:

1.  **Round Robin (по умолчанию):** Запросы распределяются по серверам поочередно. Это самый простой метод.
    *   **Weighted Round Robin:** Запросы распределяются по серверам пропорционально их весу. Сервер с большим весом получает больше запросов.
2.  **Least Connections (`least_conn`):** Новый запрос отправляется на сервер с наименьшим количеством активных соединений. Этот метод эффективен, когда запросы могут занимать разное время на обработку.
3.  **IP Hash (`ip_hash`):** Запросы от одного и того же клиента (на основе его IP-адреса) всегда отправляются на один и тот же сервер. Это необходимо для "липких сессий" (sticky sessions), когда приложение хранит состояние локально и не использует общую базу сессий (например, Redis).
4.  **Source (`source`):** Аналогично `ip_hash`, но может быть более гибким в некоторых реализациях (например, в HAProxy). В Nginx `ip_hash` является основной реализацией привязки по источнику.

```nginx
upstream backend {
    least_conn;
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
}
```

### Параметры серверов в `upstream`

Поведением каждого сервера в группе можно управлять с помощью дополнительных параметров:

-   `weight=N`: **Вес сервера.** Чем выше значение, тем большую долю запросов будет получать сервер. По умолчанию `1`. Позволяет направлять больше трафика на более мощные машины.
-   `max_fails=N`: **Максимальное количество неудач.** Количество неудачных попыток соединения, после которого сервер считается временно недоступным. По умолчанию `1`.
-   `fail_timeout=T`: **Тайм-аут.** Время (в секундах), на которое сервер будет исключен из балансировки после достижения `max_fails`. По умолчанию `10s`.
-   `backup`: **Резервный сервер.** Помечает сервер как резервный. Он будет использоваться только в том случае, если все остальные (основные) серверы в группе недоступны.

```nginx
upstream backend {
    server 10.0.0.1:80 weight=3;
    server 10.0.0.2:80 max_fails=2 fail_timeout=15s;
    server 10.0.0.3:80 backup;
}
```

## Проверки состояния (Health Checks)

Health checks — это механизм, с помощью которого балансировщик проверяет, "жив" ли бэкенд-сервер, прежде чем отправлять на него трафик.

### 1. Встроенная (пассивная) проверка

По умолчанию Nginx выполняет пассивную проверку. Если при попытке отправить запрос на бэкенд Nginx не может установить TCP-соединение (получает ошибку `Connection refused` или `Connection timed out`), он считает эту попытку неудачной.

-   После достижения `max_fails` (по умолчанию 1) неудачных попыток, Nginx временно перестает отправлять запросы на этот сервер на `fail_timeout` секунд (по умолчанию 10).
-   **Ограничение:** Эта проверка реагирует только на полную недоступность сервера на сетевом уровне. Она не спасет, если сервер "завис", отвечает медленно или возвращает ошибки `5xx`.

### 2. Расширенные (активные) проверки

Для полноценной проверки состояния приложения (например, чтобы убедиться, что оно отвечает кодом `200 OK`, а не `503 Service Unavailable`) требуется использование дополнительных модулей.

-   **NGINX Plus:** В платной версии NGINX Plus есть встроенный механизм активных health checks.
-   **Open Source:** Для бесплатной версии Nginx можно использовать сторонний модуль, например, [nginx_upstream_check_module](https://github.com/yaoweibin/nginx_upstream_check_module).

Этот модуль позволяет настроить Nginx так, чтобы он периодически отправлял на бэкенды специальные запросы (например, `GET /status`) и анализировал ответ. Если ответ не соответствует ожиданиям (например, код ответа не `200`), сервер помечается как нерабочий и исключается из балансировки до тех пор, пока снова не начнет проходить проверку.

**Пример конфигурации с `check` модулем:**

```nginx
upstream backend {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;

    # Директива, включающая проверку
    # Проверять каждые 3с, 2 удачные попытки для возвращения в строй, 3 неудачные для исключения
    check interval=3000 rise=2 fall=3 timeout=1000 type=http;
    # URL для проверки
    check_http_send "GET /status HTTP/1.0\r\n\r\n";
    # Ожидаемый код ответа
    check_http_expect_alive http_2xx;
}
```

## Проверка

Откройте браузер и перейдите по адресу вашего сервера (`http://<your_server_ip>`) или выполните команду в терминале:

```bash
curl http://127.0.0.1
```

При каждом обновлении страницы или повторном вызове `curl` вы должны видеть ответы от разных экземпляров Apache ("Response from Apache on port 8080", "Response from Apache on port 8081" и т.д.), так как Nginx по умолчанию использует алгоритм балансировки Round Robin.

## Важные замечания

*   **Расширения `.conf`:** Для Apache крайне важно, чтобы файлы конфигурации сайтов в `sites-available` имели расширение `.conf`. В противном случае утилиты `a2ensite` и сам Apache могут их игнорировать. Для Nginx это не является строгим требованием, но является хорошей практикой.
*   **Директории Nginx:** В современных версиях Nginx рекомендуется создавать отдельные файлы для конфигураций в `/etc/nginx/conf.d/` (для глобальных настроек, таких как upstream) и `/etc/nginx/sites-enabled/` (для настроек конкретных сайтов/серверов).

## Сравнение подходов к конфигурации: Apache vs. Nginx

Ключевое различие в управлении конфигурацией сайтов заключается в архитектурной философии каждого веб-сервера.

### Apache: Децентрализованная конфигурация через `.htaccess`

Apache позволяет использовать файлы `.htaccess`, размещенные непосредственно в директориях сайтов.

*   **Принцип работы:** При каждом запросе Apache проверяет наличие `.htaccess` в текущей директории и во всех родительских директориях. Найденные директивы применяются "на лету".
*   **Преимущество:** Высокая гибкость. Владелец сайта может изменять его конфигурацию (например, правила `mod_rewrite`), не имея доступа к главному конфигурационному файлу сервера. Это идеально для shared-hosting.
*   **Изоляция ошибок:** Ошибка в `.htaccess` одного сайта вызовет `500 Internal Server Error` **только для этого сайта**. Остальные сайты на сервере продолжат работать без изменений.
*   **Недостаток:** Существенное снижение производительности из-за множественных обращений к файловой системе при каждом запросе.

### Nginx: Централизованная конфигурация

Nginx не поддерживает аналогов `.htaccess`. Вся конфигурация читается из центральных файлов (например, из `/etc/nginx/sites-enabled/`) один раз при старте или перезагрузке.

*   **Принцип работы:** Вся конфигурация загружается в память. При поступлении запроса Nginx применяет уже скомпилированные правила, не обращаясь к файловой системе.
*   **Преимущество:** Максимальная производительность и эффективность, особенно при отдаче статического контента.
*   **Безопасность конфигурации:** Перед применением новой конфигурации (`systemctl reload nginx`) необходимо выполнить проверку синтаксиса (`nginx -t`). Если в конфигурации любого из сайтов есть ошибка, Nginx не применит изменения, что предотвращает остановку всего веб-сервера.
*   **Недостаток:** Меньшая гибкость для конечного пользователя. Любое изменение требует доступа к серверу и перезагрузки конфигурации администратором.

## Сравнение с HAProxy

Хотя Nginx является мощным инструментом для балансировки нагрузки, в некоторых сценариях [[../Haproxy/haproxy_overview.md|HAProxy]] может быть предпочтительнее, особенно когда требуется более тонкая настройка и расширенные возможности.

*   **Гибкость алгоритмов:** Бесплатная версия HAProxy предлагает значительно более широкий и гибкий набор алгоритмов балансировки по сравнению с бесплатной версией Nginx. HAProxy позволяет более точно управлять распределением трафика, учитывая различные параметры запросов и состояние бэкендов, включая привязку сессии к конкретному серверу на основе IP-адреса источника.
*   **Специализированные задачи:** HAProxy лучше справляется с некоторыми узкоспециализированными задачами балансировки, которые Nginx не умеет делать или делает с большими сложностями. Например, привязка сессии к конкретному серверу на основе IP-адреса источника (без сложных конфигураций) или более продвинутые проверки состояния (health checks) бэкендов.
*   **Производительность для балансировки:** HAProxy изначально разработан как высокопроизводительный балансировщик нагрузки и прокси, что делает его крайне эффективным для этой задачи с низким потреблением ресурсов. Nginx, будучи универсальным веб-сервером, также хорошо справляется, но HAProxy может быть более оптимизирован для чистой балансировки.
*   **Nginx Plus:** В то же время, платная версия **Nginx Plus** предлагает уникальные функции, которых нет в HAProxy, например, балансировку на основе скорости ответа сервера, динамическую реконфигурацию бэкендов и расширенный мониторинг. Это позволяет Nginx Plus выбирать самый быстрый отвечающий сервер, а не только наименее загруженный.

## Рекомендации по использованию

*   **Nginx:** Идеально подходит, если вы единственный администратор сервера и вам нужен универсальный инструмент (веб-сервер, реверс-прокси, балансировщик).
*   **Связка Apache + Nginx:** Рекомендуется для сред веб-хостинга, где конечным пользователям нужна гибкость `.htaccess` (которую предоставляет Apache), а Nginx используется как фронтенд для эффективной отдачи статики и проксирования.
