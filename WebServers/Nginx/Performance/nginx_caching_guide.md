# Руководство по кэшированию в Nginx (и Angie)

Кэширование в [Nginx](../nginx_overview.md) (и его форке [Angie](../../Angie/angie_overview.md)) играет ключевую роль в оптимизации производительности веб-приложений и снижении нагрузки на бэкенд-серверы. Оно позволяет эффективно управлять хранением и доставкой контента как на стороне клиента (браузер), так и на стороне сервера (прокси-кэш).

Этот механизм — важная часть [комплексной оптимизации производительности веб-приложений](../../Concepts/web_performance_optimization_complete_guide.md).

---

## Часть 1. Клиентское кэширование (Browser Caching)

Клиентское кэширование — это механизм, позволяющий браузеру сохранять локальные копии ресурсов (CSS, JS, изображения), чтобы не запрашивать их повторно при последующих визитах. Это значительно ускоряет загрузку сайта, экономит трафик и снижает нагрузку на сервер.

Управление кэшированием осуществляется с помощью [HTTP-заголовков](../../../Networking/Protocols/http.md), которые сервер отправляет вместе с ресурсом.

### 1.1. Заголовки для валидации (Условные запросы)

Эти заголовки не предотвращают запросы к серверу, но позволяют ему ответить кодом `304 Not Modified`, если ресурс не изменился. Браузер в этом случае использует свою локальную копию.

#### 1.1.1. `ETag`

`ETag` (Entity Tag) — это уникальный идентификатор версии ресурса, обычно хэш его содержимого.

-   **Сервер отправляет:** `ETag: "abcdef12345"`
-   **Клиент при повторном запросе отправляет:** `If-None-Match: "abcdef12345"`

Если `ETag` совпадает, сервер возвращает `304 Not Modified` без тела ответа. В Nginx `ETag` для статических файлов включен по умолчанию.

#### 1.1.2. `Last-Modified`

`Last-Modified` — это заголовок, указывающий дату и время последнего изменения файла.

-   **Сервер отправляет:** `Last-Modified: Tue, 18 Nov 2025 15:00:00 GMT`
-   **Клиент при повторном запросе отправляет:** `If-Modified-Since: Tue, 18 Nov 2025 15:00:00 GMT`

Если файл не изменялся с указанной даты, сервер возвращает `304 Not Modified`.

### 1.2. Заголовки для "вечного" кэширования

Эти заголовки позволяют браузеру использовать кэшированные ресурсы в течение заданного времени вообще без отправки запросов на сервер. Это наиболее эффективный способ кэширования.

#### 1.2.1. `Expires` и `Cache-Control`

-   `expires <время>`: Устанавливает заголовки `Expires` и `Cache-Control: max-age=<seconds>`.
-   `add_header Cache-Control <значение>`: Позволяет более гибко настраивать `Cache-Control`.

**Основные директивы `Cache-Control`:**
-   `max-age=<seconds>`: Время жизни кэша в секундах.
-   `public`: Ресурс может кэшироваться любыми кэшами (браузер, CDN).
-   `private`: Ресурс предназначен для одного пользователя.
-   `no-cache`: Требует валидации с сервером перед каждым использованием.
-   `no-store`: Полностью запрещает кэширование.
-   `immutable`: Указывает, что ресурс не изменится. Лучшая практика при использовании техники *cache busting*.

#### 1.2.2. Пример конфигурации для статики

```nginx
# location для статических файлов с "вечным" кэшированием
location ~* \.(?:css|js|jpe?g|gif|png|ico|svg|woff|woff2|ttf|eot)$ {
    # 1. Устанавливаем длительный срок жизни кэша
    expires 1y;

    # 2. Добавляем директивы для улучшения кэширования
    add_header Cache-Control "public, immutable";

    # 3. Отключаем логирование для статики
    access_log off;
}
```

### 1.3. Стратегии сброса кэша (Cache Busting)

Когда используется "вечное" кэширование, возникает проблема обновления ресурсов. Решение — изменять URL ресурса при каждом его обновлении.

**Способы:**
1.  **Версионирование в query string:** `style.css?v=1.2`
2.  **Хэш в имени файла:** `style.a1b2c3d4.css` (предпочтительно)

Этот подход обычно реализуется на уровне сборочных инструментов (Webpack, Gulp).

### 1.4. Практические рекомендации по клиентскому кэшированию

-   **Для статики (JS, CSS, изображения):** Используйте "вечное" кэширование (`expires 1y;` и `add_header Cache-Control "public, immutable";`) и применяйте cache busting.
-   **Для динамического контента (HTML):** Используйте валидационное кэширование или отключите его (`Cache-Control: no-cache`), чтобы пользователь всегда получал актуальную версию страницы со ссылками на кэшированную статику.

## Часть 2. Серверное кэширование (Proxy Cache)

Серверное кэширование позволяет Nginx сохранять ответы от бэкенд-серверов и отдавать их клиентам напрямую. Это значительно снижает нагрузку на бэкенды, ускоряет отдачу контента и улучшает общую производительность системы.

### 2.1. Базовая конфигурация

#### 2.1.1. Определение зоны кэширования (`proxy_cache_path`)

Зона кэширования определяется в контексте `http` и указывает, где на диске будут храниться кэшированные файлы.

```nginx
# В http блоке (nginx.conf)
proxy_cache_path /var/cache/nginx/proxy_cache levels=1:2 keys_zone=my_cache:10m inactive=60m max_size=1g;
```

*   `levels=1:2`: Создает двухуровневую структуру директорий для хранения файлов, что предотвращает проблемы с производительностью ФС.
*   `keys_zone=my_cache:10m`: Определяет зону разделяемой памяти `my_cache` размером 10 МБ для хранения ключей кэша и метаданных.
*   `inactive=60m`: Элементы кэша, которые не запрашивались в течение 60 минут, будут удалены.
*   `max_size=1g`: Максимальный размер кэша на диске. При превышении лимита `cache manager` удаляет старые элементы.

#### 2.1.2. Ключ кэширования (`proxy_cache_key`)

Определяет, на основе каких параметров формируется уникальный ключ для кэширования. Правильный ключ гарантирует уникальность кэша для разных запросов.

```nginx
# Ключ состоит из схемы (http/https), метода запроса, хоста и полного URI
proxy_cache_key "$scheme$request_method$host$request_uri";
```
**Внимание:** Добавление в ключ уникальных для пользователя переменных (например, `$cookie_user_id`) может привести к раздуванию кэша и снижению его эффективности, так как для каждого пользователя будет создаваться своя копия кэша.

#### 2.1.3. Применение и валидность кэша (`proxy_cache` и `proxy_cache_valid`)

В блоке `server` или `location` включается кэш и задается время его жизни для разных кодов ответа.

```nginx
location / {
    proxy_pass http://my_backend;
    
    # 1. Включаем кэш, указывая ранее определенную зону
    proxy_cache my_cache;

    # 2. Устанавливаем время жизни для разных кодов ответа
    proxy_cache_valid 200 302 10m; # Ответы с кодом 200 и 302 считать валидными 10 минут
    proxy_cache_valid 404 1m;      # Ответы 404 кэшировать на 1 минуту, чтобы не нагружать бэкенд запросами к несуществующим ресурсам
    proxy_cache_valid any 5m;      # Все остальные коды - на 5 минут

    # 3. (Опционально) Условие для кэширования
    proxy_cache_min_uses 3; # Кэшировать объект только после 3-х запросов к нему

    # 4. Заголовок для отладки
    add_header X-Cache-Status $upstream_cache_status;
}
```

#### 2.1.4. Пример конфигурации для API с разбором директив

```nginx
location /api/v1/data {
    # Перенаправляет запросы на группу бэкенд-серверов
    proxy_pass http://backend_upstream;

    # Включает кеширование, используя зону api_cache
    proxy_cache api_cache;
    
    # Успешные ответы (200) кешируются на 5 минут
    proxy_cache_valid 200 5m;
    # Ответы "не найдено" (404) кешируются на 1 минуту
    proxy_cache_valid 404 1m;

    # Определяет ключ, по которому будет идентифицироваться кеш
    proxy_cache_key "$scheme$request_method$host$request_uri";

    # Передает на бэкенд-сервер оригинальный домен
    proxy_set_header Host $host;
    # Передает на бэкенд реальный IP-адрес клиента
    proxy_set_header X-Real-IP $remote_addr;

    # Добавляет в ответ клиенту заголовок со статусом кеша
    add_header X-Cache-Status $upstream_cache_status;
}
```

**Разбор директив из примера:**

*   `proxy_cache api_cache;`: Указывает использовать зону кэша с именем `api_cache` (определяется в `proxy_cache_path`).
*   `proxy_cache_valid 200 5m;`: Ответы с кодом 200 (успех) считать валидными в кэше в течение 5 минут.
*   `proxy_cache_valid 404 1m;`: Ответы с кодом 404 (не найдено) кэшировать на 1 минуту, чтобы не нагружать бэкенд повторными запросами к несуществующим ресурсам.
*   `proxy_cache_key ...;`: Определяет уникальный ключ для сохранения ответа в кэше.
*   `proxy_pass ...;`: Перенаправляет (проксирует) запрос на один из серверов из группы `backend_upstream`.
*   `proxy_set_header Host $host;`: Передаёт на бэкенд оригинальный заголовок `Host` от клиента.
*   `proxy_set_header X-Real-IP $remote_addr;`: Создаёт и передаёт на бэкенд заголовок `X-Real-IP` с реальным IP-адресом клиента.
*   `add_header X-Cache-Status $upstream_cache_status;`: Добавляет в ответ клиенту заголовок `X-Cache-Status`, который показывает, был ли ответ взят из кэша (`HIT`), не найден (`MISS`), или кэш истёк (`EXPIRED`). Очень полезно для отладки.

### 2.2. Обход и запрет кэширования

*   **`proxy_cache_bypass`**: Определяет условия, при которых Nginx **не будет брать** ответ из кэша, а напрямую обратится к бэкенду.
    ```nginx
    # Пример 1: Обходить кэш, если есть кука 'nocache' или GET-параметр 'nocache'
    proxy_cache_bypass $cookie_nocache $arg_nocache;

    # Пример 2: Обходить кэш, если в запросе есть заголовок X-No-Cache
    proxy_cache_bypass $http_x_no_cache;
    ```
*   **`proxy_no_cache`**: Определяет условия, при которых ответ **не будет сохранен** в кэш.
    ```nginx
    # Не сохранять в кэш, если есть кука сессии
    proxy_no_cache $cookie_session;
    ```

### 2.3. Повышение эффективности и отказоустойчивости

#### 2.3.1. `proxy_cache_lock` (Защита от "стада бизонов")

При большом количестве одновременных запросов к одному и тому же некэшированному ресурсу (эффект "стада бизонов", "thundering herd" или "собачья свадьба"), `proxy_cache_lock` предотвращает отправку всех этих запросов на бэкенд.

**Логика работы следующая:**

1.  **Первый запрос** на ресурс получает статус `MISS` от кэша.
2.  Nginx немедленно отправляет его на бэкенд и одновременно **ставит блокировку (`lock`)** на ключ этого кэша.
3.  **Все последующие запросы** к этому же ресурсу видят, что кэш "обновляется" (`UPDATING`), и ожидают снятия блокировки, не обращаясь к бэкенду.
4.  **Первый запрос** получает ответ от бэкенда, сохраняет его в кэш и **снимает блокировку**.
5.  **Ожидающие запросы** немедленно получают ответ из свежезаполненного кэша (`HIT`).

**Результат:** Вместо 1000 одновременных запросов на бэкенд отправляется только один. Это критически важно для защиты высоконагруженных сервисов.

**Примечание:** Полная функциональность доступна в Nginx Plus или [Angie](../../Angie/angie_overview.md).

```nginx
location / {
    # ...
    proxy_cache_lock on;
    proxy_cache_lock_timeout 5s; # Ограничивает время ожидания блокировки. Если за это время бэкенд не ответил, следующий запрос также будет пропущен на бэкенд.
}
```

#### 2.3.2. `proxy_cache_use_stale` (Отдача устаревшего ответа)

Разрешает Nginx отдавать клиенту устаревший (stale) кэш, если бэкенд недоступен (`error`, `timeout`), возвращает ошибки (`http_500`, `http_502` и т.д.) или во время фонового обновления кэша (`updating`). Это значительно повышает отказоустойчивость сайта.

```nginx
location / {
    # ...
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
}
```

#### 2.3.3. `proxy_cache_background_update` (Фоновое обновление)

Разрешает обновление кэша в фоновом режиме. Когда срок действия кэша истекает, Nginx отдаёт клиенту старую (устаревшую) версию, а сам в это время отправляет асинхронный запрос на бэкенд для обновления ресурса.

**Примечание:** Доступно в Nginx Plus или [Angie](../../Angie/angie_overview.md). Требует `proxy_cache_use_stale updating`.

```nginx
location / {
    # ...
    proxy_cache_background_update on;
    proxy_cache_use_stale updating;
}
```

### 2.4. Управление заголовками

#### 2.4.1. `proxy_ignore_headers`

Позволяет игнорировать заголовки от бэкенда, запрещающие кэширование (`Cache-Control: no-cache`, `Expires`, `Set-Cookie`).

```nginx
proxy_ignore_headers Cache-Control Expires Set-Cookie;
```

#### 2.4.2. Отладочный заголовок `X-Proxy-Cache`

Для отладки полезно видеть статус кэша в ответе.

```nginx
add_header X-Proxy-Cache $upstream_cache_status;
```
Возможные значения `$upstream_cache_status`:
-   `MISS`: Запрос не найден в кэше.
-   `HIT`: Ответ отдан из кэша.
-   `EXPIRED`: Запись в кэше устарела, запрос ушел на бэкенд.
-   `STALE`: Отдан устаревший ответ из-за недоступности бэкенда.
-   `UPDATING`: Отдан устаревший ответ, пока кэш обновляется в фоне.
-   `BYPASS`: Кэш был обойден.
-   `REVALIDATED`: Nginx успешно валидировал кэш у бэкенда (получил `304 Not Modified`).

### 2.5. Точечная очистка кэша (Cache Purge)

Для выборочной очистки кэша используется сторонний модуль `ngx_cache_purge` (входит в Angie, для Nginx требует отдельной установки).

1.  **Установка (если требуется):** Установите пакет `angie-module-cache-purge` или скомпилируйте Nginx с модулем.
2.  **Подключение модуля:** В `nginx.conf` добавьте: `load_module modules/ngx_http_cache_purge_module.so;`.
3.  **Настройка `location` для очистки:**

```nginx
# Блок location для обработки запросов на очистку кэша
location ~ /purge(/.*) {
    # Мера безопасности: разрешаем доступ только с доверенных IP
    allow 127.0.0.1;
    allow 192.168.77.0/24;
    deny all;

    # Основная директива, выполняющая очистку
    proxy_cache_purge api_cache "$scheme$host$1";
}
```

**Разбор конфигурации:**

*   `location ~ /purge(/.*)`: Блок для обработки запросов, начинающихся с `/purge/`. Например, `GET /purge/api/v1/data`.
    *   Переменная `$1` будет содержать часть URI, которая соответствует `(/.*)`, то есть `/api/v1/data`.
*   `allow / deny`: Директивы для ограничения доступа к этому `location`. Крайне важно использовать их, чтобы посторонние не могли очищать ваш кэш.
*   `proxy_cache_purge api_cache "$scheme$host$1";`: Основная команда, которая выполняет очистку.
    *   Она ищет в кэше `api_cache` запись, соответствующую ключу (в данном случае, построенному из схемы, хоста и запрошенного URI из переменной `$1`).
    *   Найденная запись удаляется из кэша.

**Пример использования:**

Чтобы удалить из кэша ресурс `/api/v1/data`, нужно отправить запрос (GET, POST или любой другой) на специальный URI:

```bash
curl -X GET "http://example.com/purge/api/v1/data"
```

### 2.6. Дополнительная информация

#### 2.6.1. Мониторинг кэша

Состояние кэша можно мониторить через **Angie Console** или с помощью **[Prometheus](../../../Prometheus/overview.md)** и **[Grafana](../../../Grafana/grafana_overview.md)**. Ключевые метрики: hit ratio, размер кэша на диске, количество `HIT`/`MISS`.

#### 2.6.2. Производительность дискового кэша

Производительность дискового кэша Nginx очень высока. Современные ОС эффективно кэшируют часто запрашиваемые файлы в оперативной памяти (page cache). Это означает, что "горячие" данные из кэша Nginx будут отдаваться со скоростью, близкой к скорости RAM, что делает использование внешних in-memory хранилищ (Redis, Memcached) для этой задачи не всегда оправданным и усложняющим архитектуру.
