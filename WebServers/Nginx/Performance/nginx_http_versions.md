# Конфигурация HTTP/2 и HTTP/3 в Nginx

## 1. Определения

**HTTP/2 (Hypertext Transfer Protocol Version 2)** — вторая мажорная версия протокола [[../../../Networking/Protocols/http.md|HTTP]], разработанная для повышения производительности веб-приложений за счет мультиплексирования и сжатия заголовков.

**HTTP/3 (Hypertext Transfer Protocol Version 3)** — следующая мажорная версия HTTP, использующая протокол **QUIC** вместо TCP для решения проблемы "Head-of-line blocking" на транспортном уровне.


## 2. Основные концепции: Сравнение версий

### HTTP/1.1
-   **Принцип:** Последовательная обработка запросов. Браузер открывает несколько TCP-соединений (обычно до 6 на хост) и отправляет по одному запросу на соединение.
-   **Проблема:** "Head-of-line blocking" (HOL) на уровне соединения. Если один запрос (например, на загрузку большого изображения) выполняется долго, он блокирует все последующие запросы в том же соединении.

### HTTP/2
-   **Принцип:** Вводит **мультиплексирование**. Все запросы к одному хосту отправляются асинхронно в рамках одного TCP-соединения. Это решает проблему HOL на уровне соединения, так как маленькие запросы не ждут завершения больших.
-   **Проблема:** "Head-of-line blocking" на уровне транспортного протокола (TCP). TCP требует строгой последовательности пакетов. Если один пакет теряется в сети, все потоки внутри TCP-соединения останавливаются и ждут повторной передачи этого пакета, даже если они не были им затронуты.
-   **Требования:** Работает поверх TCP и де-факто требует [[../Security/nginx_tls_ssl_configuration.md|TLS (шифрования)]].

### HTTP/3

-   **Принцип:** Работает поверх **QUIC** — нового транспортного протокола на базе [[../../../Networking/OSI_TCP_IP_Model/tcp_ip_model.md|UDP]]. QUIC реализует потоки независимо.
-   **Решение проблемы HOL:** Потеря одного UDP-пакета влияет только на тот поток, к которому он принадлежал. Остальные потоки в том же QUIC-соединении продолжают обрабатываться без задержек.
-   **Преимущества:** Особенно эффективен в сетях с потерями пакетов (например, мобильные сети). Также включает встроенный TLS (TLS 1.3) и ускоренное установление соединения (0-RTT).
-   **Требования:** Nginx версии 1.25.0+ (или Angie) с соответствующим модулем QUIC.

## 3. Практические сценарии

### 3.1. Настройка HTTP/2 в Nginx

Включить HTTP/2 очень просто: достаточно добавить параметр `http2` к директиве `listen` в блоке `server`. Для этого требуется настроенный [[../Security/nginx_tls_ssl_configuration.md|TLS/SSL]].

```nginx
server {
    # Для Nginx 1.25.1 и выше
    listen 443 ssl http2;
    listen [::]:443 ssl http2;

    # Для более старых версий Nginx (до 1.25.1):
    # listen 443 ssl;
    # http2 on; # Эта директива устарела

    # ... остальные настройки TLS ...
    ssl_certificate /path/to/your/fullchain.pem;
    ssl_certificate_key /path/to/your/privkey.pem;
}
```

### 3.2. Настройка HTTP/3 в Nginx

Настройка HTTP/3 сложнее, так как требует работы сервера по протоколу UDP и анонсирования поддержки QUIC.

**Требования:**
-   Nginx 1.25.0+ или Angie, собранный с поддержкой QUIC.
-   Открытый UDP-порт 443 на файрволе.

**Конфигурация:**
```nginx
server {
    # 1. Слушаем UDP порт 443 для QUIC. `reuseport` обязателен.
    listen 443 quic reuseport;
    listen [::]:443 quic reuseport;

    # 2. Слушаем TCP порт 443 для HTTP/2 и HTTP/1.1 (для обратной совместимости).
    listen 443 ssl http2;
    listen [::]:443 ssl http2;

    # 3. Включаем HTTP/3
    http3 on;

    # 4. Сообщаем клиентам через заголовок Alt-Svc, что сервер поддерживает HTTP/3.
    # Браузер, получив этот заголовок, попытается установить следующее соединение по QUIC.
    # ma (max-age) - время в секундах, в течение которого клиент будет помнить о поддержке H3.
    add_header Alt-Svc 'h3=":443"; ma=86400';

    # ... остальные настройки TLS ...
    ssl_certificate /path/to/your/fullchain.pem;
    ssl_certificate_key /path/to/your/privkey.pem;
}
```

## 4. Продвинутые детали

### `ssl_early_data` и 0-RTT

Директива `ssl_early_data on;` требуется для QUIC и позволяет реализовать `0-RTT` (Zero Round-Trip Time Resumption). Это означает, что клиент, который уже подключался к серверу, может отправлять данные в первом же пакете, не дожидаясь полного TLS-рукопожатия.

-   **Преимущество:** Значительно ускоряет повторные соединения.
-   **Риск:** Создает вектор для атак повторного воспроизведения (replay attacks), так как первый пакет может быть перехвачен и отправлен злоумышленником повторно. Используйте с осторожностью и только для запросов, которые являются идемпотентными (например, `GET`).

### Влияние на другие оптимизации

-   **Сжатие:** Мультиплексирование в HTTP/2 делает динамическое сжатие более чувствительным к производительности. Медленные алгоритмы сжатия могут блокировать воркер и замедлять обработку всех потоков. Подробнее в заметке про [[../nginx_compression.md|сжатие в Nginx]].
-   **Конкатенация файлов:** С приходом HTTP/2 практика объединения CSS и JS файлов в один большой бандл (конкатенация) стала менее критичной, а иногда и вредной, так как мультиплексирование позволяет эффективно загружать множество мелких файлов параллельно.
