# Конфигурация HTTP/2 и HTTP/3 в Nginx

## Определения

**HTTP/2 (Hypertext Transfer Protocol Version 2)** — вторая мажорная версия протокола [HTTP](../../../Networking/Protocols/HTTP/http_versions.md), разработанная для повышения производительности веб-приложений за счет мультиплексирования и сжатия заголовков.

**HTTP/3 (Hypertext Transfer Protocol Version 3)** — следующая мажорная версия HTTP, использующая протокол **QUIC** вместо TCP для решения проблемы "Head-of-line blocking" на транспортном уровне.

**QUIC (Quick UDP Internet Connections)** — новый транспортный протокол на базе [UDP](../../../Networking/OSI_TCP_IP_Model/tcp_ip_model.md), разработанный Google, который обеспечивает мультиплексирование потоков, надежность и шифрование.

## Базовые концепции

Протокол HTTP прошел долгий путь развития от HTTP/1.1 до современных HTTP/2 и HTTP/3, каждый из которых привносил значительные улучшения в производительность и эффективность веб-коммуникаций. Подробное сравнение эволюции протокола, его особенностей и принципов работы вы можете найти в [документации по протоколу HTTP](../../../Networking/Protocols/HTTP/http_versions.md).

### Эволюция протокола и проблемы Head-of-line blocking

Кратко рассмотрим ключевые особенности версий HTTP:

* **HTTP/1.1:** Обработка запросов происходит последовательно. Если один запрос блокируется (например, из-за медленной загрузки), он задерживает все последующие запросы в том же TCP-соединении. Это называется "Head-of-line blocking" (HOL) на уровне соединения.
* **HTTP/2:** Вводит **мультиплексирование**, позволяя отправлять множество запросов и ответов одновременно в рамках одного TCP-соединения. Это решает проблему HOL на уровне приложения, так как маленькие запросы не ждут завершения больших. Однако, проблема HOL-блокировки остаётся на уровне транспортного протокола (TCP): потеря одного пакета TCP приводит к остановке всех потоков в соединении до его повторной передачи.
* **HTTP/3:** Решает проблему HOL-блокировки на транспортном уровне, используя **QUIC** на базе [UDP](../../../Networking/OSI_TCP_IP_Model/tcp_ip_model.md). В QUIC потеря одного UDP-пакета влияет только на тот поток, к которому он принадлежал, позволяя остальным потокам обрабатываться без задержек.

### Требования к использованию HTTP/2 и HTTP/3

* **HTTP/2:** Работает поверх TCP и де-факто требует [TLS (шифрования)](../Security/TLS_SSL/nginx_tls_ssl_overview.md) для большинства браузеров. Требуется OpenSSL 1.0.2+.
* **HTTP/3:** Требует Nginx версии 1.25.0+ (или Angie) с соответствующим модулем QUIC, открытый UDP-порт 443 на файрволе и поддержку GSO (Generic Segmentation Offload) на сетевом адаптере.

### Производительность и накладные расходы

* **Серверная производительность:** HTTP/2 и HTTP/3 требуют больше ресурсов (CPU, RAM) по сравнению с HTTP/1.1 из-за сложности протоколов. Ожидайте снижение производительности сервера на 20-30%.
* **Клиентская производительность:** Ускорение загрузки сайта за счёт снижения времени рендеринга (до 1 секунды на первых экранах).
* **HTTP/2:**
  - Мультиплексирование запросов через стримы (виртуальные подключения в рамках одного TCP-соединения)
  - Значение по умолчанию для параллельных стримов — 128 (достаточно для большинства сайтов)
  - Сжатие заголовков HPACK включается автоматически
  - Приоритизация запросов через механизм weight (ограничена буфером TCP ядра)
* **HTTP/3:**
  - Отсутствие TCP-хендшейка (экономия 1 RTT)
  - Работа поверх UDP позволяет контролировать приоритеты на уровне приложения
  - Поддержка 0-RTT через `ssl_early_data` (требует OpenSSL 3.0.1+, риск replay-атак)

## Практические сценарии

### Настройка HTTP/2 в Nginx

Включить HTTP/2 очень просто: достаточно добавить параметр `http2` к директиве `listen` в блоке `server`. Для этого требуется настроенный [TLS/SSL](../Security/TLS_SSL/nginx_tls_ssl_overview.md).

```nginx
server {
    # Для Nginx 1.25.1 и выше
    listen 443 ssl http2;
    listen [::]:443 ssl http2;

    # Для более старых версий Nginx (до 1.25.1):
    # listen 443 ssl;
    # http2 on; # Эта директива устарела

    # ... остальные настройки TLS ...
    ssl_certificate /path/to/your/fullchain.pem;
    ssl_certificate_key /path/to/your/privkey.pem;
}
```

### Настройка HTTP/3 в Nginx

Настройка HTTP/3 сложнее, так как требует работы сервера по протоколу UDP и анонсирования поддержки QUIC.

**Требования:**

* Nginx 1.25.0+ или Angie, собранный с поддержкой QUIC.
* Открытый UDP-порт 443 на файрволе.
* Поддержка GSO (Generic Segmentation Offload) на сетевом адаптере (проверить: `ethtool -k <interface> | grep gso`).
* Ядро Linux с поддержкой eBPF для механизма `quic_bpf` (распределение подключений между воркерами).

**Конфигурация:**

```nginx
# Глобальный контекст (main)
quic_bpf on;              # Требуется ядро Linux с eBPF
quic_gso on;              # Generic Segmentation Offload (требует поддержки адаптера)
ssl_early_data on;        # 0-RTT (требует OpenSSL 3.0.1+, риск replay-атак)
http2_push off;           # HTTP/2 Push не рекомендуется

server {
    # 1. Слушаем UDP порт 443 для QUIC. `reuseport` обязателен.
    listen 443 quic reuseport;
    listen [::]:443 quic reuseport;

    # 2. Слушаем TCP порт 443 для HTTP/2 и HTTP/1.1 (для обратной совместимости).
    listen 443 ssl http2;
    listen [::]:443 ssl http2;

    # 3. Включаем HTTP/3
    http3 on;

    # 4. Сообщаем клиентам через заголовок Alt-Svc, что сервер поддерживает HTTP/3.
    # Браузер, получив этот заголовок, попытается установить следующее соединение по QUIC.
    # ma (max-age) - время в секундах, в течение которого клиент будет помнить о поддержке H3.
    # ВНИМАНИЕ: После установки длительного max-age отключение HTTP/3 будет болезненным
    # (клиенты не смогут подключиться до истечения срока кэширования).
    add_header Alt-Svc 'h3=":443"; ma=86400';

    # ... остальные настройки TLS ...
    ssl_certificate /path/to/your/fullchain.pem;
    ssl_certificate_key /path/to/your/privkey.pem;
}
```

**Важные замечания:**

* `quic_bpf` — редкая настройка, находится только в главном контексте (main).
* `reuseport` можно указывать только один раз для первого сокета.
* `http3 on;` включена по умолчанию в Nginx 1.25.0+, но рекомендуется указывать явно.
* `ssl_early_data` требует OpenSSL 3.0.1+ и осторожности из-за replay-атак.
* `http2_push` (HTTP/2 Push) — технология не взлетела, рекомендуется отключать.

## Дополнительная информация

### Механизм обнаружения HTTP/3 клиентами

Браузер узнаёт о поддержке HTTP/3 двумя способами:

**1. Заголовок `Alt-Svc` (Alternative Services):**

```http
Alt-Svc: h3=":443"; ma=86400
```

- `ma` (max-age) — время кэширования в секундах (86400 = 24 часа)
- **Проблема «холодного старта»:** при первой загрузке браузер ещё не получил заголовок, поэтому начинает с HTTP/2

**2. DNS-запись типа HTTPS:**

```dns
example.com HTTPS 1 . alpn="h2,h3"
```

Браузер запрашивает HTTPS-запись автоматически при первом обращении к домену (параллельно с A-записью). Это позволяет узнать о поддержке HTTP/3 до установки соединения.

**Ограничение:** даже при наличии HTTPS-записи браузеры (Chrome 2025) могут использовать гибридный сценарий — первые 1–2 запроса по HTTP/2 из-за возможной блокировки QUIC провайдером.

**Полное описание** механизмов обнаружения, поведения браузеров и примеры проверки DNS — в [эволюции HTTP](../../../Networking/Protocols/HTTP/http_versions.md#механизмы-обнаружения).

### `ssl_early_data` и 0-RTT

Директива `ssl_early_data on;` требуется для QUIC и позволяет реализовать `0-RTT` (Zero Round-Trip Time Resumption). Это означает, что клиент, который уже подключался к серверу, может отправлять данные в первом же пакете, не дожидаясь полного TLS-рукопожатия.

* **Преимущество:** Значительно ускоряет повторные соединения.
* **Риск:** Создает вектор для атак повторного воспроизведения (replay attacks), так как первый пакет может быть перехвачен и отправлен злоумышленником повторно. Используйте с осторожностью и только для запросов, которые являются идемпотентными (например, `GET`).

### Визуальное сравнение протоколов (Waterfall View)

Краткая сводка по RTT до первого запроса:

| Протокол | RTT до первого запроса | Соединений на домен | HOL-блокировка |
|:---------|:----------------------|:--------------------|:---------------|
| **HTTP/1.1** | 3 RTT (DNS + TCP + TLS) | 6 параллельных TCP | На уровне соединения |
| **HTTP/2** | 3 RTT (DNS + TCP + TLS) | 1 TCP | На уровне TCP (потеря пакета) |
| **HTTP/3** | 1–2 RTT (DNS + QUIC+TLS) | 1 UDP | Устранена |

**Инструменты анализа:** Chrome DevTools → Network → Waterfall → колонка Protocol (`h2` / `h3`).

Полные waterfall-диаграммы, описание приоритезации и сравнение поведения — в [эволюции HTTP](../../../Networking/Protocols/HTTP/http_versions.md#сравнение-протоколов).

### Влияние на другие оптимизации

* **Сжатие:** Мультиплексирование в HTTP/2 делает динамическое сжатие более чувствительным к производительности. Медленные алгоритмы сжатия могут блокировать воркер и замедлять обработку всех потоков. Подробнее в заметке про [сжатие в Nginx](nginx_compression.md).
* **Конкатенация файлов:** С приходом HTTP/2 практика объединения CSS и JS файлов в один большой бандл (конкатенация) стала менее критичной, а иногда и вредной, так как мультиплексирование позволяет эффективно загружать множество мелких файлов параллельно.
* **Доменный шардинг:** Искусственное создание множества доменов для обхода лимита в 6 соединений стало антипаттерном с появлением HTTP/2.
