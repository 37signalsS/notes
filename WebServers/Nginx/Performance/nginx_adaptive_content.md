# Адаптивная доставка изображений с помощью Nginx

## Определения

**Адаптивная (или условная) доставка изображений** — это техника из общего руководства по [оптимизации веб-производительности](../../../Concepts/web_performance_optimization_complete_guide.md), при которой сервер отдает различные версии одного и того же изображения в зависимости от возможностей браузера клиента. Чаще всего это используется для отправки изображений в современных форматах (например, **WebP** или **AVIF**) браузерам, которые их поддерживают, и стандартных форматов (JPEG, PNG) — всем остальным.

Это позволяет значительно уменьшить размер изображений для современных браузеров, ускоряя загрузку страниц и экономя трафик. Данный метод является частью общей стратегии [оптимизации производительности Nginx](../nginx_performance_tuning.md).

## Основные концепции

1.  **Подготовка изображений:** Вы заранее создаете версии изображений в современных форматах (например, `image.webp`) и кладете их рядом с оригиналами (`image.jpg`).
2.  **Запрос клиента:** Браузер при запросе ресурсов отправляет заголовок `Accept`, в котором перечисляет поддерживаемые им MIME-типы. Например, `Accept: image/avif,image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8`.
3.  **Логика на сервере:** [Nginx](../Core/nginx_overview.md) анализирует заголовок `Accept`. Если он видит поддержку, например, `webp`, он пытается отдать WebP-версию файла. Если поддержки нет или WebP-версии файла не существует, Nginx отдает оригинальный файл.

## Практические сценарии

### Реализация в Nginx

Это реализуется с помощью директивы `map` и переменной `$http_accept`.

#### 3.1. Создание карты (map)

В блоке `http` файла `nginx.conf` добавьте карту, которая будет проверять заголовок `Accept` и на основе этого выставлять переменную.

```nginx
# nginx.conf

http {
    # ...

    # Карта для определения поддержки WebP
    map $http_accept $webp_suffix {
        default "";
        "~*webp" ".webp";
    }

    # Карта для определения поддержки AVIF (более современный и эффективный формат)
    map $http_accept $avif_suffix {
        default "";
        "~*avif" ".avif";
    }

    # ...
}
```
-   `map $http_accept $webp_suffix`: Создаем карту на основе заголовка `Accept`.
-   `default "";`: Если в заголовке нет `webp`, переменная `$webp_suffix` будет пустой строкой.
-   `"~*webp" ".webp";`: Если в заголовке есть `webp` (регистронезависимый поиск), переменная `$webp_suffix` примет значение `.webp`.

Аналогично для AVIF.

#### 3.2. Настройка `location` для отдачи изображений

В блоке `server` используйте директиву `try_files` для проверки наличия версий файла в определенном порядке. Подробнее о `location` и `try_files` можно прочитать в соответствующих заметках:
-   [Глубокое погружение в директиву location](../Core/Location/basics.md)
-   [Правила Rewrite, Redirect и try_files](../Core/nginx_rewrite_rules_and_try_files.md)

```nginx
server {
    # ...

    # Универсальный location для всех изображений
    location ~* \.(jpe?g|png|gif)$ {
        # Сначала пытаемся отдать AVIF-версию
        # Если ее нет, пытаемся отдать WebP-версию
        # Если и ее нет, отдаем оригинальный файл ($uri)
        try_files $uri$avif_suffix $uri$webp_suffix $uri =404;

        # Добавляем заголовок, чтобы видеть, какой формат был отдан
        add_header X-Image-Format $avif_suffix$webp_suffix;
    }

    # ...
}
```
**Как это работает:**

Допустим, браузер запрашивает `/images/photo.jpg`.

-   `$uri` = `/images/photo.jpg`
-   Предположим, браузер поддерживает и AVIF, и WebP. Тогда:
    -   `$avif_suffix` = `.avif`
    -   `$webp_suffix` = `.webp`

`try_files` будет искать файлы в следующем порядке:
1.  `/images/photo.jpg.avif` — если найден, Nginx отдаст его и завершит обработку.
2.  `/images/photo.jpg.webp` — если первый не найден, Nginx попробует найти этот.
3.  `/images/photo.jpg` — если ни одной из современных версий нет, Nginx отдаст оригинальный файл.
4.  Если и оригинал не найден, вернется ошибка `404`.

**Важно:** Для такой схемы именования (`photo.jpg.webp`) в `location` нужно использовать `$uri`, а не `$1`. Если вы хотите использовать `$1` (часть URI, захваченная в регулярном выражении), то структура файлов и `try_files` будет немного другой:

```nginx
location ~* ^/path/to/images/(.+\.(jpe?g|png))$ {
    # $1 = my-image.jpg
    # try_files будет искать /path/to/images/my-image.jpg.webp
    try_files $uri$webp_suffix $uri =404;
}
```

Выбор между `$uri` и `$1` зависит от вашей структуры файлов. Использование `$uri` часто является более простым и универсальным.

## Дополнительная информация

### Важность заголовка `Vary`

При использовании условной доставки контента **критически важно** добавлять заголовок `Vary`. Он сообщает промежуточным кэширующим серверам (CDN, прокси) и браузерам, что ответ сервера зависит не только от URL, но и от других заголовков запроса.

```nginx
server {
    # ...

    location ~* \.(jpe?g|png|gif)$ {
        # ... try_files ...

        # Сообщаем, что ответ зависит от заголовка Accept
        add_header Vary "Accept";

        # ...
    }

    # ...
}
```

**Почему это необходимо?**

Без `Vary: Accept` может возникнуть серьезная проблема с кэшированием:
1.  Старый браузер (не поддерживающий WebP) запрашивает `image.jpg`. Nginx отдает ему `image.jpg`. Кэширующий прокси (например, на уровне провайдера) сохраняет этот `image.jpg` в кэше для данного URL.
2.  Современный браузер (поддерживающий WebP) запрашивает тот же `image.jpg`.
3  Кэширующий прокси, не зная о зависимости от `Accept`, видит совпадение по URL и немедленно отдает `image.jpg` из своего кэша, вместо того чтобы перенаправить запрос на Nginx, который мог бы отдать `image.webp`.

Заголовок `Vary: Accept` заставляет кэш создавать разные записи для одного и того же URL в зависимости от значения заголовка `Accept` в запросе, решая эту проблему.
