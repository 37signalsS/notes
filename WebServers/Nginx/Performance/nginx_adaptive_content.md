# Адаптивная доставка изображений в Nginx (AVIF, WebP, JPEG XL)

> **Надежность: 10** (SSoT + Официальная документация Nginx 1.26+ / Angie 1.12+ + Web 2026)
> **Свежесть: Июль 2026** (AVIF — стандарт, JPEG XL — экспериментально)

## Определения

**Адаптивная (или условная) доставка изображений** — это стратегия оптимизации [Web Performance](../../Concepts/web_performance/overview.md), при которой сервер автоматически выбирает и отдает наиболее эффективный формат изображения в зависимости от возможностей браузера клиента.

Основная цель — минимизация объема передаваемого трафика без потери визуального качества за счет использования современных алгоритмов сжатия:

*   **AVIF (AV1 Image File Format)** — стандарт 2026 года с наилучшим сжатием для большинства сценариев. Поддерживается ~93% браузеров.
*   **WebP (Web Picture)** — универсальный современный формат, обеспечивающий отличный баланс совместимости и сжатия (~97% поддержки).
*   **JPEG XL (JXL)** — перспективный формат для высококачественной фотографии и прогрессивной загрузки. В 2026 году поддерживается нативно в Safari и через экспериментальные флаги в Chrome/Firefox.

## Основные концепции

В [Nginx](../Core/nginx_overview.md) адаптивность реализуется на уровне статической отдачи файлов, что значительно производительнее динамической конвертации (которая рассматривается в [модуле image_filter Angie](../../Angie/High_Load/image_filter/overview.md)).

### Механизм согласования контента (Content Negotiation)

1.  **Запрос клиента:** Браузер отправляет заголовок `Accept` со списком поддерживаемых MIME-типов (например, `image/avif,image/webp,*/*`).
2.  **Анализ на сервере:** Nginx проверяет заголовок и устанавливает переменные, указывающие на поддержку форматов.
3.  **Поиск файла:** Директива `try_files` проверяет наличие оптимизированной версии на диске в порядке убывания эффективности (AVIF → WebP → Оригинал).

### Преимущества статического подхода

*   **Нулевая нагрузка на CPU:** Сервер не сжимает изображения "на лету", а просто отдает готовый файл.
*   **Максимальное сжатие:** Можно использовать самые медленные и качественные настройки энкодеров при подготовке ресурсов в CI/CD.
*   **Простота кэширования:** Ответы кэшируются CDN и прокси-серверами без сложной логики.

## Практические сценарии

### Шаг 1: Определение поддержки форматов (map)

В блоке `http` конфигурационного файла `nginx.conf` определяются правила сопоставления заголовка `Accept` с суффиксами файлов.

```nginx
http {
    # Определение поддержки современных форматов
    map $http_accept $img_suffix {
        default       "";
        "~*image/jxl"  ".jxl";
        "~*image/avif" ".avif";
        "~*image/webp" ".webp";
    }
}
```

*Примечание: Порядок в `map` не важен, так как регулярные выражения проверяются последовательно. Важен порядок в `try_files`.*

### Шаг 2: Настройка выдачи файлов

В блоке `server` или `location` настраивается приоритетный поиск файлов. Рекомендуется использовать суффиксный метод (`photo.jpg.avif`), так как он наиболее прост в поддержке.

```nginx
server {
    location ~* \.(jpe?g|png|gif)$ {
        # Приоритетный поиск: 
        # 1. Попытка отдать JXL (если поддерживается)
        # 2. Попытка отдать AVIF
        # 3. Попытка отдать WebP
        # 4. Отдача оригинала
        try_files $uri.jxl $uri.avif $uri.webp $uri =404;

        # Критически важно: заголовок Vary для CDN/Proxy
        add_header Vary "Accept";
        
        # Настройка кэширования для статики
        expires 30d;
        add_header Cache-Control "public, no-transform";
    }
}
```

**Пример логики:**
При запросе `/img/banner.jpg`:
1.  Если браузер поддерживает JXL, Nginx ищет `/img/banner.jpg.jxl`.
2.  Если нет или файл не найден, ищет `/img/banner.jpg.avif`.
3.  И так далее до `/img/banner.jpg`.

## Дополнительная информация

### Критическая важность заголовка Vary

Заголовок `add_header Vary "Accept";` является **обязательным**. Без него возникает проблема "отравления кэша" (cache poisoning):
1.  Пользователь Chrome запрашивает картинку и получает AVIF. CDN кэширует AVIF по этому URL.
2.  Пользователь старого Safari запрашивает ту же картинку. CDN отдает ему AVIF из кэша, который Safari не может отобразить.
Заголовок `Vary: Accept` заставляет CDN хранить разные версии файла для разных значений заголовка `Accept`.

### Кэширование и `no-transform`

Использование `Cache-Control: no-transform` запрещает промежуточным прокси-серверам (например, некоторым корпоративным шлюзам или старым мобильным операторам) принудительно пережимать изображения, что может испортить адаптивную логику и качество.

### Инструменты подготовки ресурсов

Для генерации адаптивных версий в пайплайнах CI/CD рекомендуется использовать:
*   **Sharp (Node.js):** Высокая скорость, поддержка всех форматов.
*   **Squoosh CLI:** Использование кодеков через WebAssembly для максимального качества.
*   **avifenc / cwebp / cjxl:** Нативные консольные утилиты от разработчиков форматов.
