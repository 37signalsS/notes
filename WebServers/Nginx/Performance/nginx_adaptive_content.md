# Адаптивная доставка изображений в Nginx (AVIF, WebP, JPEG XL)

## Определения

**Адаптивная (условная) доставка изображений** — стратегия оптимизации производительности веб-приложений, при которой Nginx на основе заголовка `Accept` выбирает и отдает наиболее эффективный формат изображения из предварительно сгенерированных копий на диске.

**Content Negotiation (согласование контента)** — механизм HTTP, при котором сервер выбирает представление ресурса (формат, кодировку) в зависимости от возможностей клиента, указанных в заголовках запроса.

**AVIF (AV1 Image File Format)** — современный формат на основе кодека AV1. Обеспечивает наилучшее соотношение размера файла и визуального качества для фотографий и сложных изображений. Поддерживается в Chrome 85+, Edge 121+, Firefox 93+, Safari 16.4+.

**WebP** — формат от Google, обеспечивающий хорошее сжатие с широкой совместимостью. Используется как основной fallback для браузеров, не поддерживающих AVIF. Поддерживается во всех актуальных браузерах, включая Chrome 32+, Firefox 65+, Safari 16+.

**JPEG XL (JXL)** — формат с поддержкой бездефектного сжатия (lossless), прогрессивной загрузки и HDR. В 2026 году поддержка остаётся фрагментированной: Safari 17+, Chrome 145+ (только по флагу `#enable-jxl-image-format`), Firefox 157+ (ожидается включение по умолчанию). Для production-сред рекомендуется использовать только при подтверждённой аудитории с поддержкой JXL.

**Vary: Accept** — HTTP-заголовок ответа, информирующий промежуточные кэши (CDN, reverse proxy) о том, что содержимое ответа зависит от заголовка `Accept` клиента. Без этого заголовка кэш может отдать неправильный формат другому браузеру.

**Cache Poisoning (отравление кэша)** — ситуация, при которой в промежуточном кэше сохраняется ответ, несовместимый с возможностями последующих клиентов (например, AVIF для браузера без поддержки AVIF).

**Статическая адаптивная доставка** — подход, при котором все варианты форматов генерируются на этапе сборки проекта или в CI/CD пайплайне, а Nginx только выбирает нужный файл на диске. В отличие от динамической конвертации (см. [модуль image_filter в Angie](../../Angie/High_Load/image_filter/overview.md)), статический подход не нагружает CPU во время запроса.

## Основные концепции

### Жизненный цикл запроса

1. **Генерация вариантов:** На этапе CI/CD из исходных JPEG/PNG создаются оптимизированные копии: `photo.avif`, `photo.webp`, `photo.jxl` (опционально) и оригинал `photo.jpg`.
2. **Запрос:** Браузер отправляет заголовок `Accept` со списком поддерживаемых MIME-типов (например, `image/avif,image/webp,image/jxl,image/*,*/*;q=0.8`).
3. **Анализ:** Директива `map` на уровне `http` сопоставляет содержимое заголовка с переменной `$img_suffix`, содержащей расширение оптимального формата.
4. **Поиск файла:** Директива `try_files` последовательно проверяет наличие файлов на диске в порядке приоритета. При совпадении возвращается файл с соответствующим `Content-Type`.
5. **Отдача:** Nginx использует системный вызов `sendfile` для передачи файла без лишнего копирования в пользовательское пространство.

### Почему статический подход

В Nginx OSS нет встроенного модуля для динамической конвертации изображений. Это архитектурное ограничение делает статическую подготовку файлов единственным способом адаптивной доставки в pure Nginx. Преимущества подхода:

*   **Производительность:** Отсутствие нагрузки на CPU во время запроса. `sendfile` обеспечивает минимальную латентность.
*   **Масштабируемость:** Ограничение только скоростью диска и сетью, а не кодеками.
*   **Кэшируемость:** Готовые файлы корректно кэшируются на любом уровне (браузер, CDN, reverse proxy).
*   **Предсказуемость:** Затраты на обработку фиксированы и переносятся на этап сборки.

### Требования к окружению

*   **Nginx 1.7.5+** для поддержки `add_header ... always`.
*   **Nginx 1.29+** рекомендуется для современных оптимизаций (HTTP/3, `add_header_inherit`).
*   В файле `mime.types` должны быть объявлены MIME-типы для всех используемых форматов:
    ```nginx
    image/avif  avif;
    image/webp  webp;
    image/jxl   jxl;
    ```
*   Оптимизированные копии изображений должны существовать на диске по пути `<оригинал>.<суффикс>`.

### Приоритет форматов

Рекомендуемый порядок для `try_files` в 2026 году:

1. **AVIF** — наилучшее сжатие, широко поддерживается.
2. **WebP** — универсальный fallback, поддерживается везде.
3. **JPEG XL** — опционально, только при наличии подтверждённой аудитории.
4. **Оригинал** — базовый формат (JPEG/PNG), поддерживается всегда.

Приоритет можно корректировать в зависимости от статистики User-Agent в вашей аудитории.

## Практические сценарии

### Сценарий 1: Базовая конфигурация

Настройка статической адаптивной доставки для стандартного сайта.

**Шаг 1.** Определите переменную `$img_suffix` в блоке `http`:

```nginx
http {
    # Обязательно: объявление MIME-типов в mime.types
    include       mime.types;
    default_type  application/octet-stream;

    # Сопоставление возможностей браузера с суффиксом файла
    map $http_accept $img_suffix {
        default       "";
        "~*image/jxl"  ".jxl";
        "~*image/avif" ".avif";
        "~*image/webp" ".webp";
    }

    server {
        listen       80;
        server_name  example.com;
        root         /var/www/html;

        # Оптимизация для множества файлов: кэширование дескрипторов
        open_file_cache max=10000 inactive=20s;
        open_file_cache_valid 30s;
        open_file_cache_min_uses 2;
        open_file_cache_errors on;

        location ~* \.(jpe?g|png)$ {
            # Поиск: оригинал.avif -> оригинал.webp -> оригинал.jxl -> оригинал
            try_files $uri$img_suffix $uri =404;

            # Обязательные заголовки
            add_header Vary "Accept" always;
            add_header Cache-Control "public, max-age=31536000, no-transform" always;

            # Кэширование на стороне клиента
            expires 365d;

            # Отключение логирования успешных отдач
            access_log off;
        }
    }
}
```

**Шаг 2.** Подготовьте варианты файлов. Структура на диске:

```
/var/www/html/images/
├── photo.jpg
├── photo.avif
├── photo.webp
└── photo.jxl
```

**Шаг 3.** Проверьте конфигурацию и примените:

```bash
nginx -t
# → test is successful
nginx -s reload
```

### Сценарий 2: Валидация конфигурации

Используйте `curl` для проверки работы Content Negotiation:

```bash
# Проверка AVIF
curl -I -H "Accept: image/avif,image/webp,*/*" https://example.com/images/photo.jpg
# → HTTP/1.1 200 OK
# → Content-Type: image/avif
# → Vary: Accept

# Проверка WebP (если AVIF отсутствует)
curl -I -H "Accept: image/webp,image/*,*/*" https://example.com/images/photo.jpg
# → Content-Type: image/webp

# Проверка оригинала (браузер без поддержки современных форматов)
curl -I -H "Accept: image/jpeg,image/*,*/*" https://example.com/images/photo.jpg
# → Content-Type: image/jpeg
```

### Сценарий 3: Интеграция с CI/CD

Генерацию оптимизированных копий рекомендуется вынести в пайплайн сборки. Пример для Node.js-проекта:

```bash
#!/bin/bash
# generate-variants.sh — генерация AVIF/WebP/JPEG XL из исходников
set -euo pipefail

SRC_DIR="/var/www/html/images/originals"
DEST_DIR="/var/www/html/images"

# AVIF (качество 60, скорость 6 — баланс размера и времени сборки)
cavif -q 60 -s 6 "$SRC_DIR"/*.jpg --output "$DEST_DIR"

# WebP (качество 80)
for f in "$SRC_DIR"/*.jpg; do
    cwebp -q 80 "$f" -o "${DEST_DIR}/$(basename "${f%.*}").webp"
done

# JPEG XL (опционально, только если требуется)
for f in "$SRC_DIR"/*.jpg; do
    cjxl -q 80 "$f" -o "${DEST_DIR}/$(basename "${f%.*}").jxl"
done
```

Инструменты:
*   **cavif / cjxl / cwebp** — нативные утилиты с максимальным контролем параметров.
*   **Sharp (Node.js CLI)** — удобен для массовой конвертации в пайплайнах.
*   **Squoosh CLI** — позволяет добиться наилучшего визуального качества при минимальном размере.

### Сценарий 4: Отключение адаптивности для отдельных location

Если необходимо отдавать оригиналы без конвертации (например, для API или авторизованных пользовательских загрузок):

```nginx
location ~* ^/uploads/ {
    # Отключаем суффикс — всегда оригинал
    try_files $uri =404;

    # Приватное кэширование, без no-transform, чтобы прокси могли сжимать
    add_header Cache-Control "private, max-age=3600" always;
    expires 1h;
}
```

## Устранение неполадок

### Отдается неправильный формат (Content-Type не соответствует Accept)

**Симптом:** При запросе с `Accept: image/avif` возвращается `Content-Type: image/jpeg`.

**Причины и диагностика:**

1. **Файл `.avif` отсутствует на диске:**
   ```bash
   ls -la /var/www/html/images/photo.avif
   # Если файл нет — проверьте CI/CD пайплайн
   ```

2. **`map` не срабатывает из-за опечатки в regex:**
   ```bash
   # Временная диагностика: добавить в location
   add_header X-Img-Suffix $img_suffix always;
   curl -I -H "Accept: image/avif,*/*" https://example.com/img/photo.jpg
   # Должен вернуть X-Img-Suffix: .avif
   ```

3. **MIME-тип не объявлен в `mime.types`:**
   ```bash
   grep avif /etc/nginx/mime.types
   # Если нет — добавить image/avif avif;
   ```

**Решение:** Убедитесь, что файл существует, `map` корректен, а MIME-тип объявлен.

### Отсутствует заголовок Vary: Accept

**Симптом:** `curl -I` не показывает `Vary: Accept`.

**Причина:** Отсутствует модификатор `always` в директиве `add_header`, или директива отсутствует в текущем `location`.

**Решение:**
```nginx
add_header Vary "Accept" always;
```

Модификатор `always` гарантирует отправку заголовка для всех кодов ответа, включая 404 и 500.

### CDN отдает неправильный формат другим клиентам

**Симптом:** Safari получает AVIF, который не может отобразить.

**Причина:** Отсутствует `Vary: Accept` или CDN настроен без учёта этого заголовка.

**Диагностика:**
```bash
# Проверка заголовка
curl -I -H "Accept: image/avif,*/*" https://example.com/img/photo.jpg
# Должен содержать Vary: Accept

# Проверка через CDN (если используется)
curl -I -H "Accept: image/jpeg,*/*" https://cdn.example.com/img/photo.jpg
# Должен вернуть JPEG, даже если AVIF запрашивался ранее
```

**Решение:** Добавьте `Vary: Accept`, убедитесь, что CDN не игнорирует этот заголовок. Для некоторых CDN требуется ручная настройка кэширования по `Accept`.

### 404 на оптимизированные файлы

**Симптом:** `try_files` возвращает `=404`, хотя оригинал существует.

**Причина:** Файл с суффиксом (`photo.avif`) отсутствует, но `try_files` в текущей конфигурации не имеет fallback на оригинал.

**Решение:** Убедитесь, что `try_files` содержит оригинал перед `=404`:
```nginx
try_files $uri$img_suffix $uri =404;
```

### Неверный Content-Type из-за отсутствия mime.types

**Симптом:** Браузер получает файл AVIF с `Content-Type: application/octet-stream`.

**Причина:** В конфигурации отсутствует `include mime.types;` или в самом файле `mime.types` нет строки `image/avif avif;`.

**Решение:**
```nginx
http {
    include       mime.types;
    # ...
}
```

## Рекомендации

1.  **Всегда используйте `always` с `add_header`:** Заголовки должны отправляться для всех кодов ответа. Без модификатора `always` заголовки `Vary` и `Cache-Control` не отправляются для 404/500, что приводит к некорректному кэшированию ошибок.
2.  **Генерируйте варианты в CI/CD:** Никогда не генерируйте изображения на лету в Nginx OSS — у него нет для этого модулей. Используйте `sharp`, `cavif`, `cwebp`, `cjxl` или аналоги.
3.  **Приоритет форматов:** В 2026 году оптимальный порядок — AVIF → WebP → JXL → Оригинал. Корректируйте порядок на основе статистики вашей аудитории.
4.  **Кэшируйте без трансформации:** Добавляйте `no-transform` в `Cache-Control`, чтобы мобильные операторы и прокси не пересжимали изображения повторно.
5.  **Используйте `open_file_cache`:** При большом количестве изображений включите кэширование дескрипторов файлов — это снижает нагрузку на файловую систему.
6.  **Версионируйте имена файлов:** Для HTML и API используйте `no-cache`, для статики с хэшем в имени — `immutable` с TTL 1 год. Подробнее о стратегиях см. в [Клиентское кэширование в Nginx и Angie](./Caching/client_caching.md).
7.  **Валидируйте на всех уровнях:** Проверяйте отдачу не только через `curl`, но и через реальные браузеры с отключённым кэшем.
8.  **Не дублируйте функционал Angie:** Если вам нужна динамическая конвертация, рассмотрите Angie с модулем `image_filter`. Nginx OSS подходит только для статически подготовленных файлов.

## Дополнительная информация

### Отличия Nginx и Angie для адаптивных изображений

Nginx OSS поддерживает только статическую адаптивную доставку через `map` + `try_files`. Angie добавляет модуль `image_filter`, который позволяет конвертировать изображения на лету. Выбор инструмента зависит от задачи:

*   **Nginx:** максимальная производительность, статический контент, предсказуемые затраты.
*   **Angie:** динамические размеры и форматы, сложная логика обработки, требуется резерв по CPU.
