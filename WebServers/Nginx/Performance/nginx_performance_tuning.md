# Оптимизация производительности Nginx

В этом документе собраны ключевые директивы и настройки для оптимизации производительности веб-сервера Nginx и операционной системы Linux для работы в условиях высоких нагрузок.

## 1. Тюнинг ядра Linux (sysctl)

Для высоконагруженных серверов рекомендуется использовать свежее ядро Linux, так как оно часто содержит хорошие настройки по умолчанию. Изменения следует вносить только при четком понимании их назначения.

Настройки применяются в файле `/etc/sysctl.conf` или в отдельных файлах в `/etc/sysctl.d/`.

-   **`net.ipv4.tcp_slow_start_after_idle=0`**: Не сбрасывать окно TCP-конгестии после простоя соединения. Полезно для долгоживущих keep-alive соединений, так как позволяет им не начинать передачу данных с минимальной скоростью после паузы.

-   **`net.core.netdev_max_backlog = 30000`**: Увеличить размер очереди пакетов, принимаемых от сетевой карты. Помогает не терять пакеты при кратковременных всплесках трафика, когда ядро не успевает их обработать.

-   **`net.ipv4.ip_local_port_range = 1024 65535`**: Расширить диапазон эфемерных портов для исходящих соединений. Это важно для прокси-серверов, которые устанавливают множество соединений с бэкендами.

-   **`net.ipv4.tcp_tw_reuse = 1`**: Разрешить повторное использование сокетов в состоянии `TIME-WAIT` для новых исходящих соединений. Может быть полезно, но используйте с осторожностью, так как может привести к проблемам при определенных условиях.

-   **`net.ipv4.tcp_congestion_control = bbr`**: Алгоритм контроля перегрузки BBR от Google. Он показывает хорошую производительность на каналах с потерями пакетов (например, мобильные сети) и может значительно улучшить пропускную способность.

## 2. Рабочие процессы и соединения Nginx

Эти настройки обычно производятся в главном конфигурационном файле `nginx.conf`.

-   **`worker_processes`**: Определяет количество рабочих процессов Nginx.
    -   **Рекомендация:** `auto`. Nginx автоматически определит оптимальное количество, равное числу ядер процессора. Это лучший выбор, так как каждый воркер однопоточный.
    ```nginx
    worker_processes auto;
    ```

-   **`worker_cpu_affinity`**: Привязывает каждый рабочий процесс к определенному ядру CPU.
    -   **Рекомендация:** `auto`. Это может улучшить производительность за счет лучшего использования кэша процессора (L1/L2), но снижает гибкость планировщика ОС. Тестируйте, чтобы понять, дает ли это преимущество для вашей нагрузки.
    ```nginx
    worker_cpu_affinity auto;
    ```

-   **`worker_rlimit_nofile`**: Увеличивает лимит на максимальное количество открытых файловых дескрипторов для одного рабочего процесса. Важно для высоконагруженных серверов, которые обслуживают много соединений.
    ```nginx
    worker_rlimit_nofile 100000;
    ```

-   **`worker_connections`**: Максимальное количество одновременных соединений, которое может обработать один рабочий процесс.
    -   Общее количество соединений = `worker_processes` * `worker_connections`.
    -   Значение должно быть достаточным для ожидаемой нагрузки.
    ```nginx
    events {
        worker_connections 20000;
    }
    ```

## 3. Сетевые настройки

Оптимизация сетевого стека Nginx для эффективной передачи данных.

-   **`listen ... reuseport`**: Позволяет каждому рабочему процессу создавать свой собственный слушающий сокет на одном и том же порту. Ядро ОС распределяет входящие соединения между воркерами, что устраняет "узкое место" в виде одного сокета и повышает производительность на многоядерных системах.
    ```nginx
    listen 80 reuseport;
    listen 443 ssl reuseport;
    ```

-   **`sendfile`**: Разрешает Nginx использовать системный вызов `sendfile()`, который копирует данные напрямую из одного файлового дескриптора в другой (с диска в сокет), минуя копирование в пространство пользователя. Значительно ускоряет отдачу статических файлов.
    -   **Важно:** `sendfile` не работает с TLS, если не включен Kernel TLS (`ssl_sendfile`). Для HTTP/2 использование `ssl_sendfile` может привести к деградации производительности.
    ```nginx
    sendfile on;
    ```

-   **`tcp_nopush` и `tcp_nodelay`**: Оптимизируют отправку пакетов.
    -   `tcp_nopush on;`: Позволяет Nginx накапливать данные перед отправкой, чтобы сформировать полные пакеты (работает только с `sendfile on`).
    -   `tcp_nodelay on;`: Отключает алгоритм Нейгла, разрешая отправку небольших пакетов без задержки. Важно для keep-alive соединений.
    ```nginx
    tcp_nopush on;
    tcp_nodelay on;
    ```

-   **`use epoll`**: В Linux Nginx автоматически использует `epoll` — наиболее эффективный метод обработки сетевых событий. Убедитесь, что в секции `events` не указан другой, менее производительный метод.
    ```nginx
    events {
        use epoll; # Обычно включено по умолчанию в Linux
    }
    ```

## 4. Настройки таймаутов

Корректная настройка таймаутов помогает предотвратить длительное удержание соединений неактивными клиентами и защищает от атак типа "медленный клиент".

### Для соединений с клиентом:
-   **`keepalive_timeout`**: Время в секундах, в течение которого сервер не закрывает keep-alive соединение после обработки запроса. Позволяет клиенту выполнять несколько запросов в рамках одного TCP-соединения.
    ```nginx
    keepalive_timeout 65;
    ```
-   **`client_header_timeout`**: Таймаут для чтения заголовков запроса клиента. Если клиент не передаст заголовки за это время, соединение закроется.
    ```nginx
    client_header_timeout 10s;
    ```
-   **`client_body_timeout`**: Таймаут для чтения тела запроса клиента.
    ```nginx
    client_body_timeout 10s;
    ```
-   **`reset_timedout_connection on;`**: Вместо того чтобы просто закрывать соединение по таймауту, Nginx будет сбрасывать его. Это освобождает ресурсы на сервере быстрее.

### Для соединений с бэкендом (Upstream):
-   **`proxy_connect_timeout`**: Таймаут на установку соединения с бэкенд-сервером.
-   **`proxy_read_timeout`**: Таймаут на чтение ответа от бэкенда.
-   **`proxy_send_timeout`**: Таймаут на передачу запроса бэкенду.

## 5. Настройки буферов

Оптимизация буферов для обработки клиентских запросов и ответов от бэкендов.

### Для запросов от клиента:
-   **`client_body_buffer_size`**: Размер буфера для чтения тела запроса. Если тело запроса больше, оно будет записано во временный файл на диск, что может замедлить обработку.
-   **`client_max_body_size`**: Максимально допустимый размер тела запроса клиента.
-   **`client_header_buffer_size`**: Размер буфера для чтения заголовков. Для большинства запросов 1 КБ достаточно, но запросы с длинными cookies могут требовать большего значения.

### Для ответов от бэкенда:
-   **`proxy_buffers`**: Количество и размер буферов для ответа от бэкенда.
-   **`proxy_buffer_size`**: Размер одного буфера.

## 6. Кэш открытых файлов

Nginx может кэшировать метаданные о файлах и открытые файловые дескрипторы, что ускоряет доступ к ним и снижает количество системных вызовов.

```nginx
# Конфигурирует кэш для метаданных файлов
# max=5000: максимальное количество элементов в кэше
# inactive=20s: время, после которого элемент удаляется, если не используется
open_file_cache max=5000 inactive=20s;

# Время, через которое элементы кэша должны быть перепроверены
open_file_cache_valid 30s;

# Минимальное число обращений к файлу за время `inactive`, чтобы он оставался в кэше
open_file_cache_min_uses 2;

# Кэширование ошибок поиска файлов (например, "file not found")
open_file_cache_errors on;
```

## 7. Оптимизация соединений с бэкендами (Upstream)

-   **`upstream keepalive`**: При проксировании запросов, Nginx может поддерживать активные keep-alive соединения с бэкенд-серверами. Это снижает задержки и нагрузку на CPU, так как не требуется устанавливать новое TCP-соединение для каждого запроса.
    ```nginx
    upstream backend {
        server backend.example.com;
        keepalive 16; # Количество keep-alive соединений на один воркер
    }

    server {
        location / {
            proxy_pass http://backend;
            proxy_http_version 1.1; # Для keep-alive требуется HTTP/1.1
            proxy_set_header Connection ""; # Сброс заголовка Connection
        }
    }
    ```

## 8. Оптимизация логирования

Интенсивная запись логов может создавать значительную нагрузку на дисковую подсистему.

-   **`access_log ... buffer=... flush=... gzip;`**:
    -   `buffer=...`: Логи будут записываться в буфер в памяти и сбрасываться на диск пачками, а не после каждого запроса.
    -   `flush=...`: Время, через которое буфер будет принудительно сброшен на диск.
    -   `gzip`: Сжатие логов "на лету" перед записью на диск.
    ```nginx
    access_log /var/log/nginx/access.log main buffer=32k flush=5s gzip;
    ```
