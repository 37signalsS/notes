# Оптимизация сжатия в Nginx (Gzip, Brotli, ZSTD)

## 1. Определения и базовые концепции

**Сжатие данных** — это процесс уменьшения объема передаваемых данных, что напрямую влияет на скорость загрузки веб-страниц и экономию трафика.

В Nginx существуют два основных подхода к сжатию:

1.  **Динамическое сжатие (on-the-fly):** Контент сжимается веб-сервером в момент запроса клиента.
    *   **Плюсы:** Не требует предварительной подготовки файлов, всегда отдает актуальную версию.
    *   **Минусы:** Потребляет ресурсы CPU сервера на каждый запрос. Степень сжатия должна быть умеренной, чтобы не создавать излишнюю нагрузку. Является блокирующей операцией для воркера Nginx, что особенно критично для HTTP/2, где все запросы обрабатываются в рамках одного соединения (один воркер блокируется на каждое динамическое сжатие в рамках всего сайта). Это может привести к значительному снижению RPS (запросов в секунду) и увеличению времени ответа.
2.  **Статическое сжатие (pre-compressed):** Файлы сжимаются заранее (например, во время сборки проекта или при изменении файла) и сохраняются рядом с оригиналом (например, `style.css.gz`, `script.js.br`). Веб-сервер просто отдает уже сжатую версию, не тратя CPU на сжатие "на лету".
    *   **Плюсы:** Минимальная нагрузка на CPU сервера (сжатие происходит один раз), максимальная степень сжатия (можно использовать более медленные, но эффективные алгоритмы).
    *   **Минусы:** Требует предварительной подготовки файлов, может усложнить процесс деплоя.

Выбор между динамическим и статическим сжатием, а также алгоритма и его уровня, всегда является компромиссом между нагрузкой на CPU сервера, степенью сжатия (размером файла) и скоростью отдачи контента.

## 2. Основные алгоритмы сжатия и их конфигурация

### 2.1. Gzip-сжатие (динамическое и статическое)

### Динамическое Gzip-сжатие

Gzip — старый, но универсально поддерживаемый алгоритм сжатия. Его динамическая настройка позволяет сжимать контент "на лету". В некоторых контекстах (например, в Angie) директивы Gzip могут быть обозначены с префиксом `xip_`.

```nginx
server {
    # Включает динамическое сжатие Gzip. В Angie аналогичная директива называется xip_on.
    gzip on;
    # Устанавливает степень сжатия (1-9). 3-4 - хороший компромисс между сжатием и нагрузкой на CPU для динамики.
    # В Angie аналогичная директива называется xip_comp_level.
    gzip_comp_level 3;
    # Отключает сжатие для старых браузеров IE, которые могут некорректно обрабатывать сжатый контент.
    gzip_disable "msie6";
    # Указывает, какие MIME-типы подвергать сжатию. В Angie аналогичная директива называется xip_types.
    # Важно: по умолчанию Nginx включает text/html. Все остальное нужно добавлять явно.
    # Также убедитесь, что указанные MIME-типы соответствуют вашим файлам.
    # Полезно проверить фактические MIME-типы, которые отдает ваш сервер, чтобы избежать ошибок.
    gzip_types text/plain text/css application/json application/javascript application/x-javascript text/xml application/xml application/xml+rss text/javascript application/atom+xml application/rss+xml application/vnd.ms-fontobject application/x-font-ttf application/x-web-font application/x-font-opentype image/svg+xml;
    # Добавляет заголовок Vary: Accept-Encoding к ответу, что важно для корректного кэширования прокси-серверами.
    # Это указывает прокси-серверам, что ответ может отличаться в зависимости от заголовка Accept-Encoding клиента.
    gzip_vary on;
    # Минимальная длина ответа в байтах, для которой будет применяться сжатие.
    # Предотвращает сжатие очень маленьких файлов, для которых накладные расходы на сжатие могут превысить выгоду.
    gzip_min_length 1000;
    # Буферы для сжатия. По умолчанию 4 8k.
    gzip_buffers 16 8k;
    # Минимальная версия HTTP-протокола, для которой будет применяться сжатие.
    gzip_http_version 1.1;
    # Включает сжатие для проксированных запросов.
    gzip_proxied any;
}
```

### Статическое Gzip-сжатие

Для статического Gzip-сжатия Nginx может отдавать предварительно сжатые файлы с расширением `.gz`. Для этого необходимо, чтобы файлы были сжаты заранее и лежали рядом с оригинальными. Например, для файла `style.css` должен существовать `style.css.gz`.

Директива `gzip_static on;` включает эту функциональность (аналогично `xip_static`).

```nginx
server {
    # ...
    location /static/ {
        gzip_static on; # Включает отдачу предварительно сжатых .gz файлов. В Angie аналогичная директива называется xip_static.
        # Важно: если gzip_static (или xip_static) используется в глобальном контексте, Nginx будет искать сжатые версии
        # для всех статических файлов, даже для изображений, что неэффективно.
        # Рекомендуется использовать gzip_static (или xip_static) внутри location,
        # где заведомо находятся сжимаемые статические файлы (CSS, JS).
        # ... другие настройки для статики ...
    }
    # ...
}
```

**Генерация статически сжатых Gzip файлов:**

Для создания `.gz` файлов можно использовать утилиту `gzip` или `zopfli`. `zopfli` обеспечивает лучшее сжатие, но работает медленнее.

```bash
# Установка zopfli: sudo apt install zopfli
# Использование gzip (быстро, хорошее сжатие)
gzip -k -9 original_file.css

# Использование zopfli (медленнее, но лучшее сжатие, совместимо с Gzip)
zopfli -k -9 original_file.css
# -k: сохранить оригинальный файл
# -9: максимальный уровень сжатия
# Важно: zopfli по умолчанию не сохраняет дату модификации. Если это критично для заголовков Last-Modified,
# дату нужно обновить вручную: touch -r original_file.css original_file.css.gz
```

### Переговоры о сжатии (Accept-Encoding)

Браузеры отправляют заголовок `Accept-Encoding` (например, `Accept-Encoding: gzip, deflate, br, zstd`), чтобы сообщить серверу, какие алгоритмы сжатия они поддерживают. Nginx выбирает наиболее предпочтительный из доступных и отправляет ответ с заголовком `Content-Encoding` (например, `Content-Encoding: br`).

**Важный нюанс с HTTPS:** Некоторые браузеры (особенно старые версии Chrome при доступе по HTTP) могут ограничивать список поддерживаемых алгоритмов сжатия при работе по HTTP, отдавая предпочтение только `gzip` и `deflate`. При доступе по HTTPS список обычно полный (`gzip, deflate, br, zstd`). Это стоит учитывать при тестировании. Более того, в некоторых случаях (например, при доступе по HTTP, а не HTTPS) браузер может существенно сократить список поддерживаемых кодеков, что может привести к тому, что Brotli или ZSTD не будут использоваться, даже если они настроены на сервере. Поэтому тестирование всегда следует проводить по HTTPS.

## Настройки Brotli-сжатия

Brotli — современный алгоритм сжатия, разработанный Google, который обеспечивает очень высокую степень сжатия для веб-контента (HTML, CSS, JS), особенно при статической компрессии. Он широко поддерживается современными браузерами.

**Важно:** Для использования Brotli в Nginx требуется установка модуля `ngx_brotli`. Это может потребовать пересборки Nginx с этим модулем или установки его как динамического модуля. В некоторых дистрибутивах или сборках (например, Angie) он может быть доступен из коробки (например, `apt install ngx-module-brotli`). Если модуль установлен как динамический, его необходимо загрузить в `nginx.conf` с помощью директивы `load_module`:
```nginx
load_module modules/ngx_http_brotli_filter_module.so;
load_module modules/ngx_http_brotli_static_module.so;
```

Brotli-сжатие, как и Gzip, может быть **динамическим** (сжатие "на лету") или **статическим** (отдача предварительно сжатых файлов).

```nginx
server {
    # Включает динамическое Brotli-сжатие
    brotli on;
    # Устанавливает степень сжатия (1-11). 5-6 - хороший компромисс для динамики.
    brotli_comp_level 5;
    # Указывает, какие MIME-типы подвергать сжатию.
    brotli_types text/plain text/css application/json application/javascript application/x-javascript text/xml application/xml application/xml+rss text/javascript application/atom+xml application/rss+xml application/vnd.ms-fontobject application/x-font-ttf application/x-web-font application/x-font-opentype image/svg+xml;
    # Добавляет заголовок Vary: Accept-Encoding.
    brotli_vary on;
    # Минимальная длина ответа для сжатия.
    brotli_min_length 1000;

    # Включает статический режим Brotli-сжатия.
    # Nginx будет искать предварительно сжатые файлы с расширением .br.
    # Для этого необходимо, чтобы файлы были сжаты заранее и лежали рядом с оригинальными.
    # Например, для файла `style.css` должен существовать `style.css.br`.
    brotli_static on;
}
```

**Генерация статически сжатых Brotli файлов:**

Для создания `.br` файлов можно использовать утилиту `brotli`.

```bash
# Установка brotli: sudo apt install brotli
brotli -k -q 11 original_file.css
# -k: сохранить оригинальный файл
# -q 11: максимальный уровень сжатия (от 1 до 11)
```

Brotli на максимальных уровнях сжатия (например, 11) обеспечивает наилучшее соотношение размера файла к качеству, но процесс сжатия может быть довольно медленным. Поэтому его рекомендуется использовать для статического контента, который сжимается один раз.


## Настройки ZSTD-сжатия

ZSTD (Zstandard) — алгоритм сжатия, разработанный Facebook, известный своей очень высокой скоростью сжатия и распаковки. Это делает его крайне привлекательным для динамической компрессии, где важна минимальная задержка. ZSTD также имеет широкую поддержку в современных браузерах.

Для использования ZSTD в Nginx требуется установка модуля `ngx_http_zstd_filter_module` (в Angie часто доступен из коробки, например, `apt install ngx-module-zstd`). Если модуль установлен как динамический, его необходимо загрузить в `nginx.conf` с помощью директивы `load_module`:
```nginx
load_module modules/ngx_http_zstd_filter_module.so;
```

```nginx
server {
    # Включает динамическое ZSTD-сжатие
    zstd on;
    # Устанавливает степень сжатия (1-22). 3-5 - хороший компромисс для динамики, обеспечивающий высокую скорость и хорошее сжатие.
    zstd_comp_level 3;
    # Указывает, какие MIME-типы подвергать сжатию.
    zstd_types text/plain text/css application/json application/javascript application/x-javascript text/xml application/xml application/xml+rss text/javascript application/atom+xml application/rss+xml application/vnd.ms-fontobject application/x-font-ttf application/x-web-font application/x-font-opentype image/svg+xml;
    # Добавляет заголовок Vary: Accept-Encoding.
    zstd_vary on;
    # Минимальная длина ответа для сжатия.
    zstd_min_length 1000;

    # Включает статический режим ZSTD-сжатия.
    # Nginx будет искать предварительно сжатые файлы с расширением .zst.
    # Обычно менее актуален, чем Brotli static, из-за меньшей степени сжатия для веб-контента.
    zstd_static on;
}
```

**Генерация статически сжатых ZSTD файлов:**

Для создания `.zst` файлов можно использовать утилиту `zstd`.

```bash
Установка zstd: sudo apt install zstd
zstd -k -19 original_file.css
# -k: сохранить оригинальный файл
# -19: уровень сжатия (от 1 до 22). Для статики можно использовать более высокие уровни.
```


## Сравнение алгоритмов сжатия и рекомендации

Выбор алгоритма сжатия и его уровня всегда является компромиссом между нагрузкой на CPU сервера, степенью сжатия (размером файла) и скоростью отдачи контента.

**Краткая сводка по Gzip, Brotli и ZSTD:**

*   **Gzip:**
    *   **Степень сжатия:** Хорошая, но уступает Brotli.
    *   **Скорость:** Умеренная.
    *   **Поддержка:** Универсальная (все браузеры).
    *   **Применение:** Подходит для общего сжатия, когда другие алгоритмы не поддерживаются или не настроены.

*   **Brotli:**
    *   **Степень сжатия:** Отличная, особенно для веб-контента (HTML, CSS, JS).
    *   **Скорость:** Сжатие медленнее, чем у Gzip и ZSTD на высоких уровнях, но распаковка очень быстрая.
    *   **Поддержка:** Широкая (большинство современных браузеров).
    *   **Применение:** Идеален для статического сжатия (предварительно сжатые файлы) и динамического сжатия на умеренных уровнях.

*   **ZSTD:**
    *   **Степень сжатия:** Хорошая, сопоставима с Gzip, но может быть лучше на высоких уровнях.
    *   **Скорость:** Исключительно высокая скорость сжатия и распаковки.
    *   **Поддержка:** Хорошая, но не такая универсальная, как Gzip (Safari отстает).
    *   **Применение:** Отлично подходит для динамического сжатия, где важна минимальная задержка и низкая нагрузка на CPU сервера.

**Рекомендации:**
*   Для **статического контента** (CSS, JS, шрифты) используйте **Brotli** с максимальной степенью сжатия (например, `brotli_comp_level 11`) путем предварительного сжатия файлов. Это обеспечивает наилучшее сжатие при минимальной нагрузке на сервер во время отдачи.
*   Для **динамического контента** (HTML, JSON API) используйте **ZSTD** на низких уровнях сжатия (например, `zstd_comp_level 3-5`) для оптимального баланса между скоростью и эффективностью. ZSTD значительно быстрее Gzip и Brotli при динамическом сжатии, что критично для HTTP/2 и HTTP/3.
*   Если ZSTD недоступен, используйте **Brotli** на умеренных уровнях (`brotli_comp_level 3-6`) для динамического сжатия.
*   **Gzip** можно использовать как запасной вариант для браузеров, не поддерживающих Brotli или ZSTD, или для контента, который не выигрывает значительно от более продвинутых алгоритмов.

### Влияние уровня сжатия на производительность

Увеличение уровня сжатия (например, `gzip_comp_level 9`, `brotli_comp_level 11`, `zstd_comp_level 22`) приводит к уменьшению размера файла, но значительно увеличивает нагрузку на CPU сервера и время, необходимое для сжатия. Для динамического сжатия это может привести к снижению RPS (запросов в секунду) и увеличению времени ответа.

**Пример (динамическое сжатие большого CSS-файла):**
*   **Gzip 9:** Очень медленно, RPS может упасть до 30.
*   **Brotli 11:** Максимальное сжатие, но крайне медленно, RPS может быть всего 1.
*   **ZSTD 3:** Отличный баланс скорости и сжатия, RPS может быть более 200.

Для динамического сжатия рекомендуется использовать низкие или средние уровни (Gzip до 3-4, Brotli до 5-6, ZSTD до 3-5), чтобы минимизировать нагрузку на CPU.

### Тестирование эффективности сжатия

Для проверки корректности работы сжатия и оценки его эффективности можно использовать следующие методы:

1.  **Браузерные DevTools:**
    *   Откройте панель разработчика (F12 или Ctrl+Shift+I).
    *   Перейдите на вкладку "Network".
    *   Проверьте столбец "Content-Encoding" (должен быть `gzip`, `br`, `zstd`).
    *   Сравните "Size" (переданный размер) и "Content" (оригинальный размер) для оценки степени сжатия.

2.  **Утилита `curl`:**
    *   Для тестирования сжатия необходимо явно указать заголовок `Accept-Encoding`.
    ```bash
    # Запрос с поддержкой Gzip, Brotli, ZSTD
    curl -H "Accept-Encoding: gzip, deflate, br, zstd" -I https://your-domain.com/path/to/resource.css

    # Проверка заголовка Content-Encoding в ответе
    ```

3.  **Бенчмаркинг (Apache Benchmark `ab`, `wrk`):**
    *   Для оценки влияния сжатия на RPS и время ответа сервера можно использовать утилиты для нагрузочного тестирования.
    *   **Apache Benchmark (ab):**
        ```bash
        # Пример: 1000 запросов, 100 одновременных соединений, с поддержкой Gzip
        ab -n 1000 -c 100 -H "Accept-Encoding: gzip" https://your-domain.com/path/to/resource.css
        ```
    *   **`wrk`:** Более современный инструмент для нагрузочного тестирования.

    При проведении бенчмарков важно тестировать на файлах, максимально приближенных к реальным, так как эффективность сжатия сильно зависит от типа контента. Также следует учитывать, что консольные утилиты (например, `curl` без `-H "Accept-Encoding: ..."` или `ab` без соответствующего флага) по умолчанию могут не передавать заголовок `Accept-Encoding`, поэтому его нужно указывать явно, чтобы сервер отдавал сжатый контент.


4.  **Онлайн-инструменты:**
    *   **Squash Compression Benchmark:** Позволяет сравнить различные алгоритмы и уровни сжатия для разных типов файлов и сетевых условий. Этот инструмент также позволяет визуализировать компромисс между временем сжатия и временем передачи данных для различных скоростей сети.
