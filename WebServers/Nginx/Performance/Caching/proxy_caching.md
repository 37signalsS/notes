# Серверное кэширование (Proxy Cache) в Nginx и Angie

> **Надежность: 10** (SSoT + Официальная документация Nginx 1.27 / Angie 1.12 + Best Practices 2026)
> **Свежесть: Июль 2026** (Актуально для Nginx 1.30+, Angie 1.12.x+)

## Определения

**Серверное кэширование (Proxy Cache)** — механизм, при котором Nginx сохраняет ответы от бэкенд-серверов в локальном хранилище, чтобы отдавать их последующим клиентам напрямую. Это радикально снижает нагрузку на приложение и базу данных, а также минимизирует TTFB (Time to First Byte).

**Кэш-зона (Cache Zone)** — именованная область в разделяемой памяти (`keys_zone`), где хранятся ключи кэшированных объектов и их метаданные (TTL, время доступа). Сами тела ответов хранятся на диске.

**Кэш-индекс (Cache Index)** — структура в RAM, позволяющая Nginx мгновенно определить наличие ресурса в кэше без обращения к файловой системе.

**Микрокэширование (Microcaching)** — стратегия кэширования динамического контента на очень короткий срок (например, 1 секунда), эффективная для защиты от пиковых нагрузок.

Общий обзор всех типов кэширования доступен в [обзоре кэширования](./overview.md).

## Основные концепции

### Двухуровневая архитектура

1.  **RAM (Shared Memory):** Зона `keys_zone` обеспечивает доступ всем воркерам к метаданным. 10 МБ памяти вмещают примерно 80 000 ключей.
2.  **Диск (Filesystem):** Файлы ответов. Использование системного Page Cache в Linux позволяет «горячим» файлам фактически отдаваться из оперативной памяти.

### Жизненный цикл объекта

*   **TTL (Time To Live):** Определяется директивой `proxy_cache_valid` или заголовками бэкенда (`X-Accel-Expires`, `Cache-Control`, `Expires`).
*   **Inactive:** Параметр в `proxy_cache_path`, удаляющий данные, к которым не было обращений, независимо от их TTL.
*   **Purge:** Принудительное удаление объекта по его ключу.

## Практические сценарии

### Шаг 1: Глобальное определение пути кэша

Настройка выполняется в контексте `http`.

```nginx
# Определение пути и параметров кэша
proxy_cache_path /var/cache/nginx/proxy_cache
                  levels=1:2
                  keys_zone=my_cache:100m
                  inactive=24h
                  max_size=10g
                  # Angie 1.9+: Сохранение индекса для быстрого старта (Persistence)
                  file=/var/lib/angie/my_cache.zone;
```

*   `levels=1:2`: Группировка файлов в подпапки (защита от замедления ФС при миллионах файлов).
*   `max_size=10g`: Nginx будет удалять старые данные при достижении лимита (Manager процесс).

### Шаг 2: Реализация паттерна Stale-While-Revalidate (2026)

Этот сценарий обеспечивает нулевую задержку для пользователей при обновлении кэша и отказоустойчивость при сбоях бэкенда.

```nginx
server {
    location /api/v1/ {
        proxy_pass http://backend_cluster;
        proxy_cache my_cache;
        
        # 1. Формирование ключа (важна уникальность)
        proxy_cache_key "$scheme$request_method$host$request_uri";

        # 2. Кэширование успешных ответов на 10 минут
        proxy_cache_valid 200 302 10m;

        # 3. ФОНОВОЕ ОБНОВЛЕНИЕ: отдавать старый кэш, пока идет запрос к бэкенду
        proxy_cache_use_stale updating error timeout http_500 http_502 http_503 http_504;
        proxy_cache_background_update on;

        # 4. ЗАЩИТА ОТ «СТАДА БИЗОНОВ»: только один запрос на бэкенд для обновления ключа
        proxy_cache_lock on;
        proxy_cache_lock_timeout 5s;

        # 5. Оптимизация трафика: условные GET-запросы при обновлении
        proxy_cache_revalidate on;

        add_header X-Cache-Status $upstream_cache_status;
    }
}
```

### Сценарий: Кэширование API при наличии Cookies

По умолчанию Nginx не кэширует ответы с `Set-Cookie`. Для API часто требуется принудительное игнорирование этих заголовков.

```nginx
location /api/public/ {
    proxy_cache my_cache;
    # Игнорировать инструкции приложения
    proxy_ignore_headers Cache-Control Expires Set-Cookie;
    # Скрывать куки от клиента, если они пришли от бэкенда
    proxy_hide_header Set-Cookie;
    
    proxy_cache_valid 200 1h;
}
```

### Сценарий: Очистка кэша (Purge)

В **Angie** функционал встроен в ядро. В **Nginx OSS** требуется сторонний модуль (например, `ngx_cache_purge`).

```nginx
# В Angie можно настроить прямо в основной локации
location / {
    proxy_cache my_cache;
    # Разрешить метод PURGE только из локальной сети
    proxy_cache_purge PURGE from 127.0.0.1 192.168.1.0/24;
    proxy_pass http://backend;
}
```
*Запрос: `curl -X PURGE https://example.com/data` удалит этот ресурс из кэша.*

### Рекомендации по безопасности

1.  **Cache Poisoning:** Всегда включайте переменные, влияющие на контент, в `proxy_cache_key` (например, `$img_suffix` для AVIF/WebP).
2.  **Заголовки Vary:** Если контент зависит от `Accept-Encoding` или других заголовков, убедитесь, что бэкенд шлет `Vary`, иначе Nginx может отдать Gzip-версию клиенту без поддержки сжатия.
3.  **Приватность:** Будьте осторожны с `proxy_ignore_headers Set-Cookie` в зонах с авторизацией, чтобы случайно не закэшировать персональные данные одного пользователя для другого.
