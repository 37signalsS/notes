# Серверное кэширование (Proxy Cache) в Nginx и Angie

## Определения

**Серверное кэширование (Proxy Cache)** — механизм, при котором Nginx сохраняет ответы от бэкенд-серверов в локальном хранилище, чтобы отдавать их последующим клиентам напрямую. Это радикально снижает нагрузку на приложение и базу данных, а также минимизирует TTFB (Time to First Byte).

**Кэш-зона (Cache Zone)** — именованная область в разделяемой памяти (`keys_zone`), где хранятся ключи кэшированных объектов и их метаданные (TTL, время доступа, счетчики). Сами тела ответов хранятся на диске.

**Кэш-индекс (Cache Index)** — структура в оперативной памяти (RAM), позволяющая Nginx мгновенно определить наличие ресурса в кэше без обращения к файловой системе.

**Микрокэширование (Microcaching)** — стратегия кэширования динамического контента на очень короткий срок (например, 1 секунда), эффективная для защиты от взрывного роста нагрузки.

Общий обзор всех типов кэширования доступен в [Обзоре кэширования](./overview.md).

## Основные концепции

### Двухуровневая архитектура

1.  **RAM (Shared Memory):** Зона `keys_zone` обеспечивает доступ всем воркерам к метаданным. 10 МБ памяти вмещают примерно 80 000 ключей.
2.  **Диск (Filesystem):** Файлы ответов. Использование системного Page Cache в Linux позволяет «горячим» файлам фактически отдаваться из оперативной памяти. Подробнее о взаимодействии с ОС см. в [Мониторинге кэширования](./monitoring.md).

### Жизненный цикл объекта

*   **TTL (Time To Live):** Определяется директивой `proxy_cache_valid` или заголовками бэкенда (`X-Accel-Expires`, `Cache-Control`, `Expires`).
*   **Inactive:** Параметр в `proxy_cache_path`, удаляющий данные, к которым не было обращений в течение указанного времени, независимо от их TTL.
*   **Purge:** Принудительное удаление объекта по его ключу.

## Практические сценарии

### Шаг 1: Глобальное определение пути кэша

Настройка выполняется в контексте `http`.

```nginx
# Определение пути и параметров кэша
proxy_cache_path /var/cache/nginx/proxy_cache
                  levels=1:2
                  keys_zone=my_cache:100m
                  inactive=24h
                  max_size=10g
                  # Оптимизация: избегать копирования между разделами
                  use_temp_path=off
                  # Angie 1.9+: Сохранение индекса для быстрого старта (Persistence)
                  file=/var/lib/angie/my_cache.zone;
```

*   **`levels=1:2`**: Группировка файлов в подпапки. Предотвращает замедление работы файловой системы (XFS/ext4) при наличии миллионов объектов.
*   **`use_temp_path=off`**: Рекомендуется отключать, чтобы Nginx писал файлы сразу в целевую директорию кэша, избегая лишнего копирования данных между разделами.
*   **`max_size=10g`**: Порог, при котором процесс `cache manager` начинает удалять наименее востребованные данные (LRU).

### Шаг 2: Реализация паттерна Stale-While-Revalidate

Этот сценарий обеспечивает нулевую задержку для пользователей при обновлении кэша и отказоустойчивость при сбоях бэкенда.

```nginx
server {
    location /api/v1/ {
        proxy_pass http://backend_cluster;
        proxy_cache my_cache;
        
        # 1. Формирование ключа. $request_uri включает аргументы.
        proxy_cache_key "$scheme$request_method$host$request_uri";

        # 2. Кэшировать только GET и HEAD (по умолчанию)
        proxy_cache_methods GET HEAD;
        
        # 3. Оптимизация: считать HEAD как GET для повышения попаданий
        proxy_cache_convert_head on;

        # 4. Не кэшировать редко запрашиваемый контент (от 3-го запроса)
        proxy_cache_min_uses 3;

        # 5. Кэширование успешных ответов
        proxy_cache_valid 200 302 10m;

        # 6. ФОНОВОЕ ОБНОВЛЕНИЕ: отдать старый кэш, пока идет запрос к бэкенду
        proxy_cache_use_stale updating error timeout http_500 http_502 http_503 http_504;
        proxy_cache_background_update on;

        # 7. ЗАЩИТА ОТ «СТАДА БИЗОНОВ» (Cache Stampede)
        proxy_cache_lock on;
        proxy_cache_lock_timeout 5s;

        # 8. Условные GET-запросы при обновлении (If-Modified-Since)
        proxy_cache_revalidate on;

        add_header X-Cache-Status $upstream_cache_status;
    }
}
```

### Сценарий: Кэширование API при наличии Cookies

По умолчанию Nginx не кэширует ответы с заголовком `Set-Cookie`. Для публичных API часто требуется принудительно игнорировать инструкции приложения.

```nginx
location /api/public/ {
    proxy_cache my_cache;
    # Игнорировать инструкции приложения по кэшированию
    proxy_ignore_headers Cache-Control Expires Set-Cookie;
    # Не передавать куки клиенту, если они пришли от бэкенда
    proxy_hide_header Set-Cookie;
    
    proxy_cache_valid 200 1h;
}
```

### Сценарий: Очистка кэша (Purge)

В **Angie** функционал встроен в ядро. В **Nginx OSS** требуется сторонний модуль (например, `ngx_cache_purge`).

```nginx
# В Angie можно настроить прямо в основной локации
location / {
    proxy_cache my_cache;
    # Разрешить метод PURGE только из доверенных сетей
    proxy_cache_purge PURGE from 127.0.0.1 10.0.0.0/8;
    proxy_pass http://backend;
}
```

### Рекомендации по безопасности и производительности

1.  **Cache Poisoning (Отравление кэша)**: Всегда включайте в `proxy_cache_key` переменные, влияющие на контент (например, `$http_x_forwarded_proto` при работе за балансировщиком).
2.  **Заголовки Vary**: Если бэкенд отдает разный контент по заголовку `Accept-Encoding` (gzip/brotli), убедитесь, что он шлет `Vary: Accept-Encoding`. Nginx корректно создаст разные копии в кэше.
3.  **Приватность**: Категорически запрещено использовать `proxy_ignore_headers Set-Cookie` в зонах с авторизацией (личные кабинеты), так как это приведет к кэшированию персональных данных.
4.  **IO Performance**: На высоконагруженных системах используйте `aio threads` вместе с кэшем, чтобы операции чтения с диска не блокировали воркеры Nginx. Подробнее см. в [Тюнинге производительности](../nginx_performance_tuning.md).
