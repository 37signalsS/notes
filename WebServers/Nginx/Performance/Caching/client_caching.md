# Клиентское кэширование в Nginx и Angie

## Определения

**Клиентское кэширование (Browser Caching)** — механизм, при котором браузер и промежуточные прокси сохраняют копии ресурсов локально, чтобы исключить или минимизировать сетевые запросы при повторных посещениях. Это критический фактор [производительности веб-приложений](../../../Concepts/web_performance/overview.md).

**Cache-Control** — основной HTTP-заголовок (RFC 9111), управляющий жизненным циклом кэша через набор директив (`max-age`, `immutable`, `no-cache` и др.).

**Валидация (Revalidation)** — процесс проверки актуальности закэшированного ресурса на сервере. Если ресурс не изменился, сервер возвращает статус `304 Not Modified` без передачи тела файла.

**Stale-While-Revalidate (SWR)** — директива, позволяющая браузеру мгновенно отображать устаревший контент из кэша, пока в фоновом режиме выполняется запрос на его обновление. Это исключает блокировку отрисовки при обновлении данных.

**Stale-If-Error** — директива, разрешающая использовать устаревший контент при недоступности бэкенда (ошибки 5xx, таймауты). Повышает отказоустойчивость клиентского опыта.

**Early Hints (HTTP 103)** — механизм предварительной загрузки ресурсов. Сервер отправляет список критических файлов (CSS, шрифты) до того, как будет полностью сформирован основной HTML-ответ. Поддерживается в Nginx 1.29+ и Angie 1.10+.

**Cache Busting** — стратегия принудительного обновления кэша путем изменения имени файла (добавление хэша контента: `style.abc123.css`), что делает старую копию невалидной. Подробнее о реализации в пайплайнах см. **[Стратегии Cache Busting в CI/CD](../../../../CI-CD/Frontend_CI_CD/frontend_pipeline_specifics.md#стратегии-cache-busting)**.

**No-Transform** — директива `Cache-Control`, запрещающая промежуточным прокси (в том числе мобильным операторам) изменять контент (например, повторно сжимать изображения). Гарантирует целостность передаваемых данных.

## Основные концепции

### Архитектура клиентского кэширования

Клиентское кэширование работает на трех уровнях:
1.  **Браузер (Private Cache):** Локальное хранилище устройства. Подчиняется `Cache-Control: private`.
2.  **Промежуточные прокси (Shared Cache):** Прокси-серверы операторов и корпоративных сетей. Хранят копии только для `public` ресурсов.
3.  **CDN / Reverse Proxy:** Инфраструктура владельца ресурса. Управляется отдельными заголовками и политиками.

### Жизненный цикл объекта

*   **Fresh (Свежий):** Ресурс находится в кэше, и его TTL (`max-age`) не истек. Браузер отдает его без запросов к серверу.
*   **Stale (Устаревший):** TTL истек, но директива `stale-while-revalidate` позволяет мгновенно отдать контент, пока идет фоновое обновление.
*   **Revalidation (Валидация):** При истечении TTL браузер отправляет условный GET (`If-None-Match` / `If-Modified-Since`). Если ресурс не изменился — `304 Not Modified`.
*   **Purge (Очистка):** Принудительное удаление объекта из кэша. В браузере выполняется пользователем (Ctrl+F5) или через API (`Clear-Site-Data`).

### Ключевые директивы Nginx и Angie

| Директива | Заголовок | Описание |
| :--- | :--- | :--- |
| **`expires`** | `Expires`, `Cache-Control: max-age` | Устанавливает TTL кэша. Может принимать абсолютное время (`expires @3h`) или относительное (`expires 1y`). |
| **`add_header`** | `Cache-Control` | Задает флаги (`immutable`, `stale-while-revalidate`, `no-transform`). Требует модификатор `always` для нетипичных кодов ответа. |
| **`early_hints`** | `Link: ...; rel=preload` | Активирует отправку HTTP 103. Поддерживается в Nginx 1.29+ и Angie 1.10+. |
| **`etag`** | `ETag` | Включает/выключает генерацию уникального идентификатора версии файла. |
| **`add_header`** | `Clear-Site-Data` | Очищает клиентские данные при выходе из системы (поддерживается в Chromium-based браузерах). |

### Механизмы валидации

1.  **Сильные валидаторы (ETag):** Уникальный хэш файла (INode-Size-MTime). Гарантирует байтовую идентичность. Если ответ сжимается «на лету» (модуль `gzip`), Nginx автоматически превращает сильный ETag в слабый (префикс `W/`), так как сжатый контент не идентичен оригиналу по байтам.
2.  **Слабые валидаторы (Last-Modified):** Проверка по дате изменения. Менее точна, если файл меняется чаще раза в секунду.
3.  **Vary:** Критически важный заголовок, указывающий браузеру, какие заголовки запроса влияют на ответ. Без него браузер может отдать Gzip-копию клиенту, который её не поддерживает.

### Важность модификатора `always`

Директива `add_header` в Nginx по умолчанию добавляет заголовки только для успешных ответов (200, 204, 301, 302). Для ошибок (404, 500, 503) заголовки не отправляются, что может привести к кэшированию ошибок промежуточными прокси. Модификатор `always` гарантирует отправку заголовка для всех кодов ответа:

```nginx
add_header Cache-Control "no-store, no-cache, must-revalidate" always;
add_header Retry-After "3600" always;
```

## Практические сценарии

### Сценарий 1: Версионированная статика (Immutable)

Для файлов, имена которых включают хэш контента. Это обеспечивает максимально быструю загрузку без повторных запросов к серверу.

```nginx
location ~* \.(?:css|js|woff2?|png|webp|avif)$ {
    # 1. Срок жизни — 1 год
    expires 1y;
    
    # 2. Immutable предотвращает отправку запросов If-None-Match при обновлении (F5)
    add_header Cache-Control "public, max-age=31536000, immutable" always;
    
    # 3. Запрет на трансформацию контента промежуточными прокси
    add_header Cache-Control "public, max-age=31536000, immutable, no-transform" always;
    
    # 4. Оптимизация производительности: не логировать успешные обращения
    access_log off;
    log_not_found off;
}
```

Ожидаемое поведение:
*   Первый запрос: `200 OK` с заголовками `Cache-Control: public, max-age=31536000, immutable, no-transform`
*   Повторный визит: `200 OK` (from disk cache) — нет сетевого запроса
*   F5/Refresh: браузер не отправляет `If-None-Match` из-за `immutable`

### Сценарий 2: HTML-документы и SWR

Обеспечивает мгновенную отрисовку страницы с фоновым обновлением данных и отказоустойчивость при сбоях бэкенда.

```nginx
server {
    # Включение Early Hints для ускорения загрузки критических ресурсов
    # Поддерживается в Nginx 1.29+ и Angie 1.10+
    early_hints on;

    location / {
        proxy_pass http://backend;

        # 1. Требовать проверку актуальности (no-cache) — браузер всегда валидирует
        # 2. Разрешить показ старого контента в течение 7 дней, пока идет обновление в фоне
        # 3. Разрешить использование кэша при сбоях сервера (stale-if-error)
        add_header Cache-Control "no-cache, stale-while-revalidate=604800, stale-if-error=86400" always;
        
        # Подсказка браузеру начать загрузку CSS немедленно
        add_header Link "</static/css/main.hash123.css>; rel=preload; as=style" always;
        
        # Обеспечение корректного кэширования для разных типов сжатия
        add_header Vary "Accept-Encoding" always;
    }
}
```

Ожидаемое поведение:
*   Повторный визит: браузер отправляет `If-None-Match` / `If-Modified-Since`
*   Если ресурс не изменился: `304 Not Modified` (без тела)
*   Если ресурс изменился: `200 OK` с новым телом
*   При сбое бэкенда: отдается устаревший контент из кэша (TTL 86400 сек)

### Сценарий 3: Чувствительные данные и безопасность

Полный запрет кэширования для личных кабинетов, форм оплаты и API с персональными данными.

```nginx
location /api/private/ {
    # Сброс TTL
    expires -1;
    
    # Запрет на сохранение в браузере и промежуточных прокси
    add_header Cache-Control "no-store, no-cache, must-revalidate, proxy-revalidate, private, max-age=0" always;
    
    # Очистка клиентских данных при выходе (поддерживается в Chromium-based браузерах)
    add_header Clear-Site-Data '"cache", "cookies", "storage"' always;
}
```

Важно: директива `private` разрешает кэширование только в браузере, но не в промежуточных прокси. `no-store` полностью запрещает сохранение данных.

### Сценарий 4: Maintenance-страница и отказоустойчивость

При включении режима обслуживания важно запретить кэширование страницы ошибки, чтобы браузер не сохранил её на случай восстановления сервиса.

```nginx
location = /maintenance.html {
    internal;
    root /var/www/html;

    add_header Cache-Control "no-store, no-cache, must-revalidate" always;
    add_header Retry-After "3600" always;
}

server {
    location / {
        include /etc/nginx/conf.d/maintenance.inc;
    }
}
```

Файл `/etc/nginx/conf.d/maintenance.inc`:
```nginx
# Обычный режим (пустой файл — Nginx продолжает proxy_pass)
# Режим обслуживания: return 503;
```

## Troubleshooting

### Заголовок Cache-Control не отправляется

**Симптом:** `curl -I` не показывает `Cache-Control` для определенных кодов ответа (404, 500).

**Причина:** Отсутствует модификатор `always` в директиве `add_header`.

**Диагностика:**
```bash
curl -I https://example.com/nonexistent
# Проверьте отсутствие Cache-Control в ответе 404
```

**Решение:**
```nginx
add_header Cache-Control "no-store, no-cache, must-revalidate" always;
```

### Устаревший контент после деплоя

**Симптом:** После обновления статические файлы не обновляются у пользователей, даже при hard refresh.

**Причина:** Отсутствует Cache Busting (хэши в именах файлов), или `max-age` слишком велик без `immutable`.

**Диагностика:**
```bash
# Проверка имени файла
curl -I https://example.com/static/app.js
# Если имя не содержит хэш — Cache Busting не настроен
```

**Решение:**
*   Настроить хэширование в пайплайне сборки (Webpack, Vite, esbuild)
*   Использовать `Cache-Control: public, max-age=31536000, immutable` только для файлов с хэшем в имени
*   Для HTML всегда использовать `no-cache`

### SWR не работает

**Симптом:** При истеченном TTL браузер не отображает устаревший контент, пока идет обновление.

**Причина:** Устаревший Nginx (<1.29), отсутствие `stale-while-revalidate` в заголовке, или бэкенд перезаписывает заголовок.

**Диагностика:**
```bash
nginx -v
# Должно быть >= 1.29.x (Nginx) или >= 1.10.x (Angie)
```

**Решение:**
```nginx
add_header Cache-Control "no-cache, stale-while-revalidate=604800" always;
proxy_pass http://backend;
```

Убедитесь, что бэкенд не перезаписывает заголовок `Cache-Control` без `stale-while-revalidate`.

### ETag меняется при каждом запросе

**Симптом:** Условные GET не возвращают `304`, каждый запрос получает `200 OK` с полным телом.

**Причина:** Nginx генерирует ETag на основе Inode-Size-Mtime. Если файл перезаписывается или Mtime меняется (например, при деплое через `rsync` без сохранения времени), ETag инвалидируется.

**Диагностика:**
```bash
curl -I https://example.com/static/file.js
# ETag меняется при повторных запросах к тому же файлу
```

**Решение:**
*   Использовать `etag off;` и полагаться на `Last-Modified`
*   Настроить деплой с сохранением Mtime (`rsync -t`, `tar --touch`)
*   Использовать предварительное сжание (gzip_static), чтобы ETag не превращался в слабый

### Кэширование чувствительных данных

**Симптом:** Персональные данные (личный кабинет, баланс) кэшируются в браузере или промежуточном прокси.

**Причина:** Отсутствует `private`/`no-store`, или заголовок применяется не для всех кодов ответа.

**Диагностика:**
```bash
curl -I -b "session=abc123" https://example.com/account/balance
# Проверьте Cache-Control
```

**Решение:**
```nginx
location /account/ {
    add_header Cache-Control "no-store, no-cache, must-revalidate, private, max-age=0" always;
    proxy_pass http://backend;
}
```

Категорически запрещено использовать кэширование для эндпоинтов с `Set-Cookie` и персональными данными.

### Ошибка 404 кэшируется как 200

**Симптом:** После исправления ошибки 404 браузер продолжает отдавать старую ошибку.

**Причина:** Промежуточный прокси или CDN кэширует 404 без учета `max-age=0` или `no-store`.

**Решение:**
```nginx
location / {
    proxy_intercept_errors on;
    error_page 404 = /custom_404.html;

    add_header Cache-Control "no-store, no-cache, must-revalidate" always;
}
```

## Best Practices

1.  **Модификатор `always`:** Всегда используйте `always` с `add_header`, чтобы заголовки отправлялись для всех кодов ответа, включая ошибки 4xx/5xx.
2.  **Версионирование:** Для артефактов сборки (JS, CSS, шрифты) используйте хэши в именах файлов. Это позволяет устанавливать `Cache-Control: immutable` с TTL 1 год без риска устаревшего контента.
3.  **Разделение стратегий:** Версионированная статика (`immutable`, 1 год) и HTML/API (`no-cache` + SWR/stale-if-error) должны иметь отдельные политики кэширования.
4.  **Запрет трансформации:** Используйте `no-transform` для статики, чтобы мобильные операторы и промежуточные прокси не пересжимали изображения или изменяли контент.
5.  **Безопасность:** Для личных кабинетов и API используйте `no-store, private, max-age=0`. Никогда не кэшируйте ответы с `Set-Cookie` и персональными данными.
6.  **Валидация:** Для HTML всегда используйте `no-cache` (не `no-store`), чтобы браузер выполнял условный GET и получал `304` при отсутствии изменений.
7.  **ETag и сжатие:** Если используется сжатие на лету (`gzip on`), ETag становится слабым (`W/`). Для критических ресурсов используйте `gzip_static` или `brotli_static` для сохранения сильного ETag.
8.  **Vary:** Всегда добавляйте `Vary: Accept-Encoding` (или `Vary: Accept` для адаптивных изображений), если контент varies по заголовкам запроса.
9.  **Clear-Site-Data:** Используйте на эндпоинтах logout для очистки клиентских данных. Помните о browser support (Chromium-based).
10. **Наблюдаемость:** Включите логирование `$sent_http_cache_control` в access log для аудита эффективности кэширования в production.
11. **Angie 1.10+:** Используйте `early_hints on;` для ускорения загрузки критических ресурсов. В Nginx требуется версия 1.29+.
12. **Capacity Planning:** Размер `keys_zone` должен покрывать максимальное количество уникальных объектов. Формула ориентировочная: 8 000 ключей на 1 МБ. Мониторьте `max_size` и `inactive` в соответствии с ростом контента.

### Проблема «слабого» ETag

Nginx автоматически превращает сильный ETag в слабый (префикс `W/`), если ответ сжимается «на лету» (модуль `gzip`). Это происходит потому, что сжатый контент не идентичен оригиналу по байтам.
*   **Влияние:** Некоторые прокси-серверы могут некорректно обрабатывать слабые ETag.
*   **Решение:** Используйте [предварительное сжание (Gzip Static)](../nginx_compression.md) для критических ресурсов. Это сохранит сильный ETag и обеспечит максимальную совместимость.

### Использование заголовка Vary

Всегда добавляйте `Vary: Accept-Encoding` (или `Vary: Accept` для адаптивных изображений). Это гарантирует, что браузер не закэширует версию ресурса (например, WebP), которая не поддерживается в другом контексте.
