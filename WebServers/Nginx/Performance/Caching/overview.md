# Кэширование в Nginx: Обзор и концепции

## Definitions

**Кэширование (Caching)** — процесс временного хранения копий данных, чтобы будущие запросы к этим данным выполнялись быстрее. Сокращает время ответа, уменьшает нагрузку на бэкенд и снижает потребление сетевого трафика.

В контексте Nginx/Angie различают два основных типа:

* **Клиентское кэширование (Browser Caching)** — браузер сохраняет локальные копии ресурсов; управление через заголовки `Cache-Control`, `ETag`, `Expires`.
* **Серверное кэширование (Proxy Cache)** — Nginx сохраняет ответы от бэкенд-серверов и отдаёт их клиентам напрямую.

**ETag (Entity Tag)** — уникальный идентификатор версии ресурса (обычно хэш содержимого). Используется для валидации кэша через условные запросы (`If-None-Match`).

**Last-Modified** — заголовок с датой последнего изменения файла. Используется для валидации через `If-Modified-Since`.

**Expires** — заголовок с точной датой устаревания ресурса. Устаревший подход, заменён на `Cache-Control: max-age`.

**Cache-Control** — основной HTTP-заголовок для управления кэшированием через директивы: `max-age`, `public`, `private`, `no-cache`, `no-store`, `immutable`.

Кэширование — важная часть [оптимизации производительности Nginx](../nginx_performance_tuning.md) и общей [стратегии кэширования](../../../../Concepts/Caching/caching_overview.md).

## Basic Concepts

Кэширование в [Nginx](../../Core/nginx_overview.md) играет ключевую роль в оптимизации производительности и снижении нагрузки на бэкенд-серверы. Оно позволяет управлять хранением и доставкой контента как на стороне клиента, так и на стороне сервера.

Общие принципы HTTP-кэширования описаны в [документации по протоколу HTTP](../../../../Networking/Protocols/HTTP/http_basics.md) и [специализированном файле по HTTP-кэшированию](../../../../Networking/Protocols/HTTP/http_caching.md).

### Клиентское кэширование (Browser Caching)

Управление кэшированием осуществляется через HTTP-заголовки, которые Nginx отправляет вместе с ресурсом. Два ключевых механизма:

1. **Валидация (условные запросы)** — `ETag` и `Last-Modified` позволяют серверу ответить `304 Not Modified`, если ресурс не изменился. Браузер использует локальную копию.
2. **"Вечное" кэширование** — `Cache-Control: max-age` + `immutable` позволяют браузеру использовать ресурс без запросов к серверу в течение заданного времени.

**Стратегии по типу контента:**

| Тип контента | Стратегия | Заголовки |
|:-------------|:----------|:----------|
| Статика с версионированием (CSS, JS) | «Вечное» кэширование | `expires 1y;` + `Cache-Control: public, immutable` |
| Изображения, медиа | Длительное кэширование | `expires 30d;` + `Cache-Control: public` |
| HTML-страницы | Валидационное кэширование | `Cache-Control: no-cache` |
| API-ответы, персонализированные данные | Без кэширования | `Cache-Control: private, no-store` |

Подробная документация с примерами конфигурации — [клиентское кэширование в Nginx](./client_caching.md).

### Серверное кэширование (Proxy Cache)

Nginx сохраняет ответы от бэкендов и отдаёт их клиентам напрямую. Ключевые директивы:

| Директива | Назначение |
|:----------|:-----------|
| `proxy_cache_path` | Определяет зону кэша на диске (в `http` блоке) |
| `proxy_cache` | Включает кэширование для `server`/`location` |
| `proxy_cache_valid` | Устанавливает TTL для разных кодов ответа |
| `proxy_cache_key` | Формирует уникальный ключ кэша |
| `proxy_cache_lock` | Защита от «стада бизонов» (thundering herd) |
| `proxy_cache_use_stale` | Отдача устаревшего кэша при недоступности бэкенда |
| `proxy_cache_background_update` | Фоновое обновление кэша |

**Основные сценарии использования:**

- **Кэширование API-ответов** — снижение нагрузки на бэкенд при повторяющихся запросах
- **Кэширование статического контента** — раздача без обращения к бэкенду
- **Защита от сбоев** — `proxy_cache_use_stale` отдаёт устаревший кэш при ошибках бэкенда
- **Предотвращение thundering herd** — `proxy_cache_lock` отправляет на бэкенд только первый запрос

Подробная документация с примерами конфигурации — [серверное кэширование в Nginx](./proxy_caching.md).

### Мониторинг кэширования

Эффективность кэширования измеряется через **Cache Hit Ratio** — отношение запросов, обработанных из кэша, к общему числу запросов. Целевой показатель — >90% для статического контента.

Ключевые инструменты мониторинга:

- **Логирование** — `$upstream_cache_status` в `access.log` (HIT, MISS, EXPIRED, STALE)
- **Prometheus + Grafana** — сбор и визуализация метрик через VTS-модуль
- **Специализированные дашборды** — встроенные инструменты Nginx Plus / сторонние решения

Подробная документация — [мониторинг кэширования](./monitoring.md).

## Practical Scenarios

### Сценарий 1: Выбор типа кэширования

| Задача | Решение |
|:-------|:--------|
| Ускорить загрузку статики (CSS, JS, изображения) | Клиентское кэширование (`expires` + `Cache-Control`) |
| Снизить нагрузку на бэкенд (API, динамический контент) | Серверное кэширование (`proxy_cache`) |
| Оба случая | Комбинация: `proxy_cache` на сервере + `Cache-Control` для браузера |

### Сценарий 2: Деплой новой версии приложения

Проблема: браузеры кэшировали статику, пользователи получали старые CSS/JS.

Решение — **cache busting**:

1. Сборщик (Webpack, Vite) добавляет хэш в имя файла: `style.a1b2c3.css` → `style.d4e5f6.css`
2. Статика кэшируется «навечно»: `Cache-Control: public, immutable`
3. HTML отдаётся с `no-cache` — браузер всегда получает актуальные ссылки на новые файлы

### Сценарий 3: Защита бэкенда от пиковой нагрузки

При одновременном сбросе кэша (или первом запуске) тысячи запросов могут обрушить бэкенд.

Решение — `proxy_cache_lock on;`:

- Первый запрос идёт на бэкенд (`MISS`)
- Остальные ожидают ответа из кэша
- После заполнения кэша все получают `HIT`

### Сценарий 4: Отказоустойчивость при недоступности бэкенда

Если бэкенд упал, сайт может продолжать работать за счёт кэша:

```nginx
proxy_cache_use_stale error timeout http_500 http_502 http_503 http_504;
proxy_cache_background_update on;
```

Nginx отдаёт устаревший кэш (`STALE`) и фоновом обновляет его при восстановлении бэкенда.
