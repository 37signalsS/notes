# Кэширование в Nginx и Angie: Обзор и концепции

## Определения

**Кэширование (Caching)** — процесс временного хранения копий данных для ускорения последующих запросов, снижения времени ответа (TTFB) и уменьшения нагрузки на вычислительные ресурсы (CPU, базу данных, дисковая подсистема). В экосистеме Nginx кэширование является ключевым инструментом оптимизации производительности [Оптимизация производительности Nginx и Angie](../nginx_performance_tuning.md).

**Клиентское кэширование (Browser Caching)** — механизм управления локальным хранилищем браузера и промежуточных прокси через HTTP-заголовки. Подробная настройка — в файле [Клиентское кэширование в Nginx](./client_caching.md).

**Серверное кэширование (Server-Side Caching)** — сохранение ответов бэкендов на стороне веб-сервера. Включает:
*   **Proxy Cache:** Для ответов от HTTP-бэкендов.
*   **FastCGI/UWSGI/SCGI Cache:** Для ответов от приложений (PHP-FPM, Python, и др.).
*   Детальная конфигурация — в файле [Серверное кэширование в Nginx](./proxy_caching.md).

**Кэш-индекс (Cache Index)** — база метаданных в оперативной памяти (`keys_zone`), содержащая ключи кэша (хэши) и информацию о расположении файлов на диске. 1 МБ зоны вмещает примерно 8 000 ключей. 10 МБ — примерно 80 000 ключей. В Angie 1.9+ параметр `file=` в директиве `proxy_cache_path` позволяет сохранять индекс на диск при выключении, исключая фазу сканирования диска (cache loader) при холодном старте.

**Кэш-загрузчик (Cache Loader)** — дочерний процесс, который при старте Nginx сканирует директорию кэша для наполнения `keys_zone`. На высоконагруженных системах это создает всплеск IOPS.

**Кэш-менеджер (Cache Manager)** — периодический процесс, который удаляет устаревшие или невостребованные данные при превышении `max_size` по алгоритму LRU (Least Recently Used).

**Согласование кэша (Cache Validation)** — проверка актуальности копии данных с помощью условных запросов (`If-None-Match`, `If-Modified-Since`).

**Микрокэширование (Microcaching)** — стратегия кэширования динамического контента на очень короткий срок (обычно 1–5 секунд) для защиты от всплесков нагрузки (Cache Stampede).

## Архитектура и принципы работы

Эффективная стратегия кэширования в Nginx и Angie строится на комбинации клиентских и серверных механизмов. Глубокое описание протокола доступно в [HTTP-кэшировании](../../../../Networking/Protocols/HTTP/http_caching.md).

### Клиентское кэширование

Управляет поведением браузера и промежуточных прокси через HTTP-заголовки:

*   **Cache-Control:** Основной заголовок. Современные стандарты включают `immutable` (для версионированной статики) и `stale-while-revalidate` (фоновое обновление при использовании устаревшего контента).
*   **Валидаторы:** `ETag` (контрольная сумма) и `Last-Modified`. Позволяют серверу вернуть `304 Not Modified`, экономя трафик.
*   **Приватность:** `public` позволяет кэширование на промежуточных прокси, `private` — только в браузере.

### Серверное кэширование

Nginx и Angie сохраняют ответы бэкендов на диске, используя оперативную память только для индекса:

*   **Разделяемая память (Shared Memory):** Зона `keys_zone` доступна всем рабочим процессам.
*   **Иерархия (levels):** Разделение файлов по подпапкам (например, `levels=1:2`) предотвращает замедление работы файловой системы из-за огромного количества файлов в одном каталоге.
*   **Взаимодействие с Page Cache:** Nginx не хранит тело ответа в своей оперативной памяти (только индекс в `keys_zone`). Тело файла кэшируется Page Cache ядра Linux. Если Page Cache эффективен, чтение с диска фактически происходит из RAM.
*   **Обход кэша:** Директивы `proxy_cache_bypass` (не брать из кэша) и `proxy_no_cache` (не сохранять в кэш) позволяют гибко управлять логикой для авторизованных сессий.

### Жизненный цикл объекта

*   **TTL (Time To Live):** Определяется директивой `proxy_cache_valid` или заголовками бэкенда (`X-Accel-Expires`, `Cache-Control`, `Expires`).
*   **Inactive:** Параметр в `proxy_cache_path`, удаляющий данные, к которым не было обращений в течение указанного времени, независимо от их TTL.
*   **Purge:** Принудительное удаление объекта по его ключу.

### Кэширование фрагментов (Slice Module)

Для работы с очень большими файлами (видео, ISO-образы) используется модуль `ngx_http_slice_module`. Он разбивает запрос на небольшие диапазоны (ranges), которые кэшируются как отдельные файлы. Это позволяет:
*   Начинать отдачу контента до полной загрузки файла в кэш.
*   Эффективно обрабатывать Range-запросы от клиентов.
*   Минимизировать нагрузку при прерывании закачки.

## Практические сценарии

### Выбор стратегии

| Задача | Решение |
| :--- | :--- |
| Ускорение повторных визитов | `expires`, `Cache-Control: immutable` |
| Снижение нагрузки на API | `proxy_cache` + `proxy_cache_lock` |
| Кэширование PHP/Python | `fastcgi_cache` / `uwsgi_cache` |
| Раздача тяжелого контента | `ngx_http_slice_module` + `proxy_set_header Range $slice_range` |
| Адаптивные изображения | `proxy_cache_key` + `$img_suffix` + `Vary: Accept` |
| Защита от всплесков | Микрокэширование (`proxy_cache_valid 200 1s`) + `proxy_cache_lock` |

### Защита от «стада бизонов» (Cache Stampede)

При истечении кэша популярного ресурса множество запросов могут одновременно уйти на бэкенд. Детали и конфигурация — в [Серверном кэшировании в Nginx](./proxy_caching.md).

*   **`proxy_cache_lock on;`** — отправляет только один запрос к бэкенду, остальные ждут появления данных в кэше.
*   **`proxy_cache_use_stale updating;`** — позволяет отдавать старую версию контента, пока первый запрос обновляет кэш в фоне.

### Оптимизация обновления (Background Update)

Директива `proxy_cache_background_update on;` в сочетании с `stale-while-revalidate` позволяет Nginx обновлять кэш в фоновом режиме, не заставляя клиента ждать ответа от бэкенда даже при истекшем TTL.

### Очистка кэша (Purge)

*   **Nginx OSS:** Требует сторонних модулей (например, `ngx_cache_purge`) или ручного удаления файлов с диска.
*   **Angie:** Имеет встроенную поддержку директивы `proxy_cache_purge`, что упрощает автоматизацию инвалидации через API.

## Установка и базовая конфигурация

### Предварительные требования

*   Nginx 1.28+ или Angie 1.9+ (рекомендуется Nginx 1.30+/Angie 1.11+ на момент 2026 года)
*   Достаточное место на диске для кэша (определяется параметром `max_size`)
*   Отдельный раздел или каталог для `/var/cache/nginx` или `/var/cache/angie` для предотвращения заполнения корневого раздела

### Базовая конфигурация

Конфигурация выполняется в контексте `http`:

```nginx
# Определение пути и параметров кэша
proxy_cache_path /var/cache/nginx/proxy_cache
                  levels=1:2
                  keys_zone=my_cache:100m
                  inactive=24h
                  max_size=10g
                  # Оптимизация: избегать копирования между разделами
                  use_temp_path=off;
```

Ключевые параметры:
*   **`levels=1:2`**: Группировка файлов в подпапки. Предотвращает замедление работы файловой системы (XFS/ext4) при наличии миллионов объектов.
*   **`use_temp_path=off`**: Рекомендуется отключать, чтобы Nginx писал файлы сразу в целевую директорию кэша, избегая лишнего копирования данных между разделами.
*   **`inactive=24h`**: Удаляет данные, к которым не было обращений в течение указанного времени, независимо от их TTL.
*   **`max_size=10g`**: Порог, при котором процесс `cache manager` начинает удалять наименее востребованные данные (LRU).

Активация кэша в location:

```nginx
server {
    location /api/v1/ {
        proxy_cache my_cache;
        proxy_cache_valid 200 10m;
        add_header X-Cache-Status $upstream_cache_status;
        proxy_pass http://backend_cluster;
    }
}
```

### Angie: Персистентность индекса

В Angie 1.9+ добавьте параметр `file=` для сохранения индекса на диск:

```nginx
proxy_cache_path /var/cache/angie/proxy_cache
                  levels=1:2
                  keys_zone=my_cache:100m
                  inactive=24h
                  max_size=10g
                  file=/var/lib/angie/my_cache.zone;
```

Это исключает фазу сканирования диска при перезапуске и позволяет серверу вернуться в работу практически мгновенно.

## Операции и команды

### Валидация конфигурации

```bash
# Проверка синтаксиса конфигурации
nginx -t
# → nginx: configuration file /etc/nginx/nginx.conf test is successful

# Применение конфигурации без потерь соединений
nginx -s reload
```

### Очистка кэша

```bash
# Полная очистка кэша (остановка сервера)
systemctl stop nginx
rm -rf /var/cache/nginx/proxy_cache/*
systemctl start nginx

# Частичная очистка по пути (Nginx OSS с ngx_cache_purge)
curl -X PURGE http://localhost/api/v1/resource

# Angie: встроенный PURGE
curl -X PURGE http://localhost/api/v1/resource
```

## Best Practices

1.  **Разделение кэшей:** Используйте отдельные зоны `keys_zone` для разных типов контента (API, статика, изображения). Это упрощает управление TTL и очистку.
2.  **Ключ кэша:** Всегда включайте в `proxy_cache_key` параметры, влияющие на ответ (язык, `Accept-Encoding`, протокол). Пример: `proxy_cache_key "$scheme$request_method$host$request_uri";`
3.  **Заголовки Vary:** Если бэкенд отдает разный контент по заголовку `Accept-Encoding` (gzip/brotli), убедитесь, что он шлет `Vary: Accept-Encoding`.
4.  **Защита от Stampede:** Для популярных ресурсов всегда используйте `proxy_cache_lock on;` с `proxy_cache_lock_timeout 5s;`.
5.  **Безопасность:** Категорически запрещено использовать `proxy_ignore_headers Set-Cookie` в зонах с авторизацией (личные кабинеты), так как это приведет к кэшированию персональных данных.
6.  **IO Performance:** На высоконагруженных системах используйте `aio threads` вместе с кэшем, чтобы операции чтения с диска не блокировали воркеры Nginx. Подробнее см. в [Оптимизации производительности Nginx](../nginx_performance_tuning.md).
7.  **Персистентность:** В Angie 1.9+ всегда используйте `file=` в `proxy_cache_path` для ускорения холодного старта.
8.  **Мониторинг:** Включите `add_header X-Cache-Status $upstream_cache_status;` для аудита эффективности кэширования.

## Дополнительная информация

### Безопасность и целостность

**Отравление кэша (Cache Poisoning):** Риск отдачи неверного контента из-за недостаточно точного ключа кэша.
*   Всегда включайте в `proxy_cache_key` параметры, влияющие на ответ (язык, формат сжатия, тип устройства).
*   Используйте заголовок `Vary`, чтобы уведомить промежуточные кэши о факторах вариативности.

### Мониторинг

Эффективность кэширования оценивается через **Cache Hit Ratio**.
*   Переменная `$upstream_cache_status` (HIT, MISS, EXPIRED, BYPASS, STALE, UPDATING, REVALIDATED).
*   **Status Zones (Angie):** Позволяют собирать статистику по кэш-зонам в реальном времени через API.
*   Подробности в [Мониторинге кэширования](./monitoring.md).
