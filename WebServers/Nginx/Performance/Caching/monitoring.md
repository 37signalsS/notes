# Мониторинг и производительность кэша в Nginx и Angie

> **Надежность: 10** (SSoT + Документация Nginx 1.27 / Angie 1.12 + OpenTelemetry 1.1+)
> **Свежесть: Июль 2026** (Включает нативный OTel и Key-based метрики)

## Определения

**Коэффициент попаданий в кэш (Cache Hit Ratio)** — ключевой показатель эффективности, выраженный в процентах ответов, отданных из кэша (`HIT`), относительно общего числа запросов.
*   **Целевые значения:** >95% для статики, >50% для динамики (API).

**`$upstream_cache_status`** — встроенная переменная, фиксирующая жизненный цикл запроса в подсистеме кэширования.

| Статус | Описание | Состояние Page Cache |
| :--- | :--- | :--- |
| **HIT** | Ответ отдан напрямую из кэша Nginx. | Чтение из RAM (горячий) или диска. |
| **MISS** | Запрос не найден, данные получены от бэкенда. | Запись нового файла на диск. |
| **EXPIRED** | TTL истек, Nginx запросил обновление у бэкенда. | Перезапись существующего файла. |
| **STALE** | Отдан устаревший ответ (бэкенд недоступен, настроен `use_stale`). | Чтение из диска/RAM. |
| **UPDATING** | Отдан старый ответ, пока идет фоновое обновление. | Чтение + фоновая запись. |
| **BYPASS** | Кэш намеренно обойден (токен в заголовке, `bypass`). | Прямое проксирование. |
| **REVALIDATED** | Бэкенд подтвердил актуальность (`304 Not Modified`). | Обновление метаданных TTL. |

## Основные концепции

Производительность кэша зависит от синергии Nginx и ядра Linux.

1.  **L7 (Прикладной уровень):** Анализ HTTP-статусов и заголовков. Позволяет понять логику: почему кэш не работает или почему он часто промахивается.
2.  **Page Cache (Системный уровень):** Nginx не хранит тело ответа в своей RAM (только индекс в `keys_zone`). Тело файла кэшируется Page Cache ядра Linux. Если Page Cache эффективен, "чтение с диска" фактически происходит из RAM.
3.  **IO Latency:** Мониторинг задержек дисковых операций. Высокий `EXPIRED` или `MISS` создает нагрузку на запись, что может замедлить `HIT` (чтение) из-за конкуренции за диск.

## Практические сценарии

### Анализ эффективности через логи

Для глубокого аудита необходимо включить переменную статуса в `log_format`.

```nginx
log_format cache_perf '$remote_addr [$time_local] "$request" '
                       '$status body_s=$body_bytes_sent '
                       'cache=$upstream_cache_status rt=$request_time '
                       'uct=$upstream_connect_time uht=$upstream_header_time';

access_log /var/log/nginx/cache_audit.log cache_perf;
```

**Быстрая диагностика (Bash):**
```bash
# Топ причин промахов кэша (MISS/BYPASS/EXPIRED)
awk -F'cache=' '{print $2}' /var/log/nginx/cache_audit.log | cut -d' ' -f1 | sort | uniq -c | sort -rn
```

### Нативный мониторинг OpenTelemetry (Nginx 1.27+)

В современных инсталляциях статус кэша передается как атрибут распределенного трейса (Span Attribute), что позволяет визуализировать Hit Ratio в системах типа Jaeger или Grafana Tempo.

```nginx
http {
    otel_exporter {
        endpoint otel-collector:4317;
    }
    otel_trace on;

    server {
        location /api/ {
            # Добавление статуса кэша в атрибуты спана
            otel_span_attr "http.cache.status" $upstream_cache_status;
            proxy_cache my_api_cache;
            proxy_pass http://backend;
        }
    }
}
```

### Key-based мониторинг в Angie 1.12

Angie позволяет собирать метрики кэша с детализацией по ключам (например, по домену или типу контента) без внешних экспортеров.

```nginx
http {
    # Определение зоны статуса с ключом (группировка по хосту)
    status_zone $host zone=cache_stats:10m;

    server {
        listen 8080;
        location /api/status {
            # Встроенная консоль и JSON API
            api /status/;
            allow 127.0.0.1;
            deny all;
        }
    }
}
```
*В Angie Console метрики Hit Ratio доступны в реальном времени во вкладке "Caches".*

### Мониторинг системного Page Cache

Чтобы понять, действительно ли ваши `HIT` читаются из RAM, используйте утилиту `cachestat` (из пакета `perf-tools` или `bcc-tools`).

```bash
# Мониторинг попаданий в Page Cache системы (общая картина)
cachestat 5
# → HITS: количество попаданий в кэш страниц
# → MISSES: реальные чтения с диска
```

## Дополнительная информация

### Узкие места мониторинга

*   **Cache Loader:** При старте Nginx процесс `cache loader` сканирует диск для наполнения `keys_zone`. В это время нагрузка на диск (I/O) может быть максимальной. В Angie 1.9+ используйте `file=` в `proxy_cache_path` для сохранения индекса и мгновенного старта.
*   **Thundering Herd:** Если мониторинг показывает всплеск `MISS` для одного и того же ресурса одновременно, проверьте настройку `proxy_cache_lock`.
