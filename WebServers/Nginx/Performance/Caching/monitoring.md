# Мониторинг и производительность кэша в Nginx и Angie

## Определения

**Коэффициент попаданий в кэш (Cache Hit Ratio)** — ключевой показатель эффективности, выраженный в процентах ответов, отданных из кэша (`HIT`), относительно общего числа запросов. 
*   **Целевые значения:** >95% для статических ресурсов, >50% для динамического API (в зависимости от бизнес-логики).

**`$upstream_cache_status`** — встроенная переменная, фиксирующая жизненный цикл запроса в подсистеме кэширования.

| Статус | Описание | Состояние Page Cache ОС |
| :--- | :--- | :--- |
| **HIT** | Ответ отдан напрямую из кэша. | Чтение из RAM (горячий) или диска. |
| **MISS** | Запрос не найден, данные получены от бэкенда. | Запись нового файла на диск. |
| **EXPIRED** | TTL истек, Nginx запросил обновление у бэкенда. | Перезапись существующего файла. |
| **STALE** | Отдан устаревший ответ (бэкенд недоступен или настроен `use_stale`). | Чтение из диска/RAM. |
| **UPDATING** | Отдан старый ответ, пока идет фоновое обновление. | Чтение + фоновая запись. |
| **BYPASS** | Кэш намеренно обойден (например, через `proxy_cache_bypass`). | Прямое проксирование. |
| **REVALIDATED** | Бэкенд подтвердил актуальность (`304 Not Modified`). | Обновление метаданных TTL в RAM. |

## Основные концепции

Производительность кэша зависит от синергии Nginx и ядра Linux.

1.  **Прикладной уровень (L7):** Анализ HTTP-статусов и заголовков. Позволяет понять логику: почему кэш не работает или почему он часто промахивается.
2.  **Системный уровень (Page Cache):** Nginx не хранит тело ответа в своей оперативной памяти (только индекс в `keys_zone`). Тело файла кэшируется Page Cache ядра Linux. Если Page Cache эффективен, «чтение с диска» фактически происходит из RAM.
3.  **Задержки ввода-вывода (IO Latency):** Высокий уровень статусов `EXPIRED` или `MISS` создает нагрузку на запись, что может замедлить операции `HIT` (чтение) из-за конкуренции за ресурсы дисковой подсистемы.

## Практические сценарии

### Анализ эффективности через логи

Для глубокого аудита рекомендуется использовать формат JSON, который легко парсится системами сбора логов (ELK, VictoriaMetrics Logs, Grafana Loki).

```nginx
log_format cache_json escape=json '{'
    '"time": "$time_iso8601", '
    '"remote_addr": "$remote_addr", '
    '"host": "$host", '
    '"request": "$request", '
    '"status": "$status", '
    '"cache_status": "$upstream_cache_status", '
    '"request_time": "$request_time", '
    '"upstream_response_time": "$upstream_response_time", '
    '"body_bytes_sent": "$body_bytes_sent"'
'}';

access_log /var/log/nginx/cache_access.json cache_json;
```

**Быстрая диагностика через консоль:**
```bash
# Подсчет статистики статусов кэша из JSON-лога
jq -r '.cache_status' /var/log/nginx/cache_access.json | sort | uniq -c | sort -rn
```

### Мониторинг через OpenTelemetry (Nginx 1.27+)

Начиная с версии 1.27, Nginx поддерживает нативную интеграцию с OpenTelemetry. Статус кэша можно передавать как атрибут пролета (Span Attribute).

```nginx
http {
    otel_exporter {
        endpoint otel-collector:4317;
    }
    otel_trace on;

    server {
        location /api/ {
            otel_span_attr "http.cache.status" $upstream_cache_status;
            proxy_cache my_api_cache;
            proxy_pass http://backend;
        }
    }
}
```

### Метрики в реальном времени в Angie

В Angie реализован расширенный мониторинг через встроенный API, позволяющий получать статистику по каждой кэш-зоне без сторонних модулей.

```nginx
http {
    # Группировка статистики по хосту
    status_zone $host zone=cache_stats:10m;

    server {
        listen 8080;
        location /status {
            api /status/;
            allow 127.0.0.1;
            deny all;
        }
    }
}
```
*В консоли Angie метрики Hit Ratio доступны во вкладке "Caches".*

### Интеграция с Prometheus

1.  **Angie:** Экспортирует метрики нативно в формате Prometheus через эндпоинт `/status/prometheus`.
2.  **Nginx OSS:** Требует использования экспортера (например, `nginx-vts-exporter` при наличии модуля VTS или `nginx-prometheus-exporter` для работы со `stub_status`).
    *   *Примечание:* `stub_status` в Nginx OSS предоставляет крайне ограниченные метрики и **не содержит** детальной информации о кэше.

### Мониторинг системного Page Cache

Чтобы убедиться, что `HIT` ответы действительно читаются из оперативной памяти, используйте инструменты eBPF.

```bash
# Мониторинг попаданий в системный Page Cache
cachestat 5
# → HITS: попадания в RAM
# → MISSES: реальные обращения к диску
```

## Дополнительная информация

### Узкие места мониторинга

*   **Процесс Cache Loader:** При старте Nginx сканирует диск для наполнения `keys_zone`. В это время нагрузка на диск (IOPS) может резко возрасти. В Angie 1.9+ используйте параметр `file=` в `proxy_cache_path` для сохранения индекса на диске и мгновенного старта без сканирования.
*   **Эффект «стада бизонов» (Thundering Herd):** Если мониторинг фиксирует резкие всплески `MISS` для одного и того же ресурса, необходимо проверить конфигурацию `proxy_cache_lock`.
