# Кэширование статических файлов на стороне клиента

Для ускорения загрузки сайта и снижения нагрузки на сервер, статичные ресурсы (CSS, JavaScript, изображения, шрифты) следует кэшировать в браузере клиента. Это достигается с помощью HTTP-заголовков, которые управляют поведением кэширования.

## 1. Заголовки для управления кэшем

### `expires`
Директива `expires` устанавливает заголовок `Expires`, который указывает дату и время, после которых кэшированный ресурс считается устаревшим.

### `Cache-Control`
`Cache-Control` — более современный и гибкий заголовок. Nginx автоматически добавляет `Cache-Control` с директивой `max-age` при использовании `expires`.
-   `public`: Разрешает кэширование ресурса любым кэшем, включая браузеры и промежуточные прокси-серверы.
-   `private`: Ресурс может кэшироваться только конечным клиентом (браузером).
-   `max-age=<seconds>`: Указывает максимальное время в секундах, в течение которого ресурс считается "свежим" и может быть использован без обращения к серверу.
-   `immutable`: Указывает, что ресурс не изменится в течение срока действия `max-age`. Браузер, поддерживающий эту директиву, не будет отправлять повторные запросы на сервер для проверки актуальности ресурса (условные запросы с `If-None-Match` или `If-Modified-Since`), что значительно повышает производительность.

### `Last-Modified` и `ETag`
Эти заголовки используются для валидации кэша.
-   **`Last-Modified`**: Заголовок ответа сервера, указывающий дату и время последнего изменения ресурса. Браузер может использовать его для условных запросов (`If-Modified-Since`).
-   **`ETag` (Entity Tag)**: Уникальный идентификатор версии ресурса, обычно хэш его содержимого. Браузер использует его для условных запросов (`If-None-Match`).

Если ресурс не изменился, сервер отвечает статусом `304 Not Modified`, и браузер использует кэшированную версию. Это экономит трафик, но не время на запрос (round-trip time).

## 2. Конфигурация Nginx

Типичная конфигурация для кэширования статики выглядит следующим образом:

```nginx
location ~* \.(?:css|js|jpe?g|gif|png|ico|svg|woff|woff2|ttf|eot)$ {
    # Кэшировать на 30 дней
    expires 30d;
    
    # Ресурс публичный и не будет меняться в течение срока действия
    add_header Cache-Control "public, immutable";
    
    # Можно отключить логирование для статики, чтобы уменьшить I/O
    access_log off;
}
```
-   `location ~* \.(?:...)` — регулярное выражение для всех распространенных расширений статичных файлов.
-   `expires 30d;` — устанавливает срок кэширования в 30 дней.
-   `add_header Cache-Control "public, immutable";` — добавляет важные директивы для `Cache-Control`.

## 3. Стратегия "вечного" кэширования и сброс кэша (Cache Busting)

При использовании "вечного" кэширования (длительный `expires` и `immutable`), браузер не будет повторно запрашивать ресурс с сервера. Это создает проблему: как обновить ресурс, если он изменился?

**Решение — изменение URL ресурса.**

Когда браузер видит новый URL, он воспринимает его как совершенно новый ресурс и загружает его с сервера. Старый ресурс со старым URL остается в кэше до истечения срока его действия, но больше не используется.

Этот процесс называется "cache busting" (сброс кэша) и реализуется несколькими способами:

1.  **Изменение имени файла:** `style.v2.css`
2.  **Добавление хэша в имя файла:** `style.a1b2c3d4.css`
3.  **Добавление query-параметра (версионирование):** `style.css?v=2`

Наиболее надежным способом является добавление хэша в имя файла, так как он гарантированно меняется при изменении содержимого. Этот подход используется практически всеми современными сборщиками фронтенда (Webpack, Vite, Rollup).

**Важно:** Эта логика должна поддерживаться вашим приложением или процессом сборки. Nginx только отдает заголовки, но не управляет версионированием файлов.
