# Кэширование ответов бэкенда (Proxy Cache)

Кэширование ответов от бэкенд-серверов с помощью модуля `ngx_http_proxy_module` является одним из самых эффективных способов снижения нагрузки на них и ускорения отдачи контента пользователям.

## 1. Принцип работы

Nginx сохраняет ответы от бэкенд-серверов на диск. Когда приходит повторный запрос на тот же ресурс, Nginx отдает его напрямую из кэша, не обращаясь к бэкенду. Это уменьшает время ответа и экономит ресурсы бэкенд-серверов.

## 2. Основные директивы для настройки кэша

Настройка кэша состоит из двух частей:
1.  **Определение зоны кэширования** в блоке `http` (обычно в `nginx.conf`).
2.  **Применение этой зоны** в блоке `server` или `location`.

### В блоке `http`:

*   **`proxy_cache_path`**: Определяет путь к директории, где будут храниться кэшированные файлы, и настраивает параметры зоны кэширования.
    ```nginx
    proxy_cache_path /var/cache/nginx/proxy_cache levels=1:2 keys_zone=my_cache:10m inactive=60m max_size=1g;
    ```
    *   `/var/cache/nginx/proxy_cache`: Путь к директории для хранения кэша. Убедитесь, что у пользователя Nginx есть права на запись в эту директорию.
    *   `levels=1:2`: Определяет двухуровневую иерархию поддиректорий для хранения кэша. Это улучшает производительность файловой системы при большом количестве файлов.
    *   `keys_zone=my_cache:10m`: Создает общую зону памяти `my_cache` размером 10 МБ для хранения ключей кэша и метаданных. 10 МБ достаточно для хранения метаданных примерно 80 000 ключей.
    *   `inactive=60m`: Определяет время, после которого неактивные (не запрашиваемые) элементы кэша будут удалены, даже если они еще не устарели.
    *   `max_size=1g`: Устанавливает максимальный размер кэша на диске. При достижении этого лимита специальный процесс `cache manager` будет удалять наименее используемые файлы.

*   **`proxy_cache_key`**: Определяет ключ, по которому будет кэшироваться ответ. По умолчанию используется комбинация схемы, хоста и URI запроса. Можно расширить, добавив переменные Nginx.
    ```nginx
    proxy_cache_key "$scheme$proxy_host$request_uri";
    # Пример с добавлением куки:
    # proxy_cache_key "$scheme$proxy_host$request_uri$cookie_user_id";
    ```
    *   **Внимание:** Добавление уникальных для каждого пользователя переменных (например, куки сессии) в ключ кэша может привести к быстрому разрастанию кэша и снижению его эффективности, так как для каждого пользователя будет создаваться отдельная копия страницы. Используйте с осторожностью.

### В блоке `server` или `location`:

*   **`proxy_cache`**: Включает кэширование для данного блока и указывает используемую зону кэширования.
    ```nginx
    proxy_cache my_cache;
    ```
    Для отключения кэширования в определенном `location`: `proxy_cache off;`.

*   **`proxy_cache_valid`**: Определяет время жизни кэша для различных кодов ответов HTTP.
    ```nginx
    proxy_cache_valid 200 302 10m; # Кэшировать ответы 200 и 302 на 10 минут
    proxy_cache_valid 404 1m;      # Кэшировать ответы 404 на 1 минуту
    proxy_cache_valid any 5m;      # Кэшировать любые другие ответы на 5 минут
    ```
    *   Если указано только время, оно применяется ко всем успешным ответам (200, 301, 302).

*   **`proxy_cache_min_uses`**: Устанавливает минимальное количество запросов к ресурсу, прежде чем он будет кэширован. По умолчанию `1`. Увеличение этого значения может помочь избежать кэширования редко используемых страниц.
    ```nginx
    proxy_cache_min_uses 3;
    ```

*   **`proxy_cache_bypass`**: Определяет условия, при которых Nginx будет обходить кэш (не будет брать из него ответ) и всегда обращаться к бэкенду.
    ```nginx
    # Не брать из кэша, если есть кука 'nocache' или параметр 'nocache' в URL
    proxy_cache_bypass $cookie_nocache $arg_nocache;
    ```
    *   Если хотя бы одна из переменных не пуста и не равна "0", кэш будет обойден.

*   **`proxy_no_cache`**: Определяет условия, при которых ответ не будет сохранен в кэш, даже если он был получен от бэкенда.
    ```nginx
    # Не сохранять в кэш, если есть кука 'session'
    proxy_no_cache $cookie_session;
    ```

## 3. Повышение отказоустойчивости и производительности

Эти директивы позволяют сделать кэш более "умным", улучшая пользовательский опыт.

*   **`proxy_cache_lock`**: Защищает от "cache stampede" (эффект "стада бизонов", когда множество клиентов одновременно запрашивают один и тот же устаревший ресурс).
    - **Примечание:** В Open Source версии Nginx эта директива имеет ограниченную функциональность. Полная поддержка доступна в Nginx Plus или его форке Angie.
    ```nginx
    proxy_cache_lock on;
    proxy_cache_lock_timeout 5s; # Таймаут ожидания обновления кэша
    ```
    *   При включении `proxy_cache_lock`, если кэш устарел, только первый запрос будет отправлен на бэкенд для обновления. Остальные запросы будут ожидать появления свежего ответа в кэше или истечения таймаута `proxy_cache_lock_timeout`.

*   **`proxy_cache_use_stale`**: Разрешает Nginx отдавать устаревший (stale) контент из кэша, если бэкенд недоступен, отвечает с ошибкой или запрос таймаутится. Это лучше, чем показывать пользователю ошибку.
    ```nginx
    proxy_cache_use_stale error timeout invalid_header http_500 http_502 http_503 http_504;
    ```

*   **`proxy_background_update`**: Позволяет Nginx немедленно отдать пользователю устаревший контент, а в это время отправить фоновый асинхронный запрос на бэкенд для обновления кэша. Это обеспечивает "нулевое время простоя" для пользователя при обновлении кэша.
    - **Примечание:** Доступно в Nginx Plus или Angie.
    - Для работы требует включения `proxy_cache_use_stale` с параметром `updating`.
    ```nginx
    proxy_cache_use_stale error timeout ... updating;
    proxy_background_update on;
    ```

## 4. Пример полной конфигурации кэширования

```nginx
# В блоке http в nginx.conf
http {
    # ...
    proxy_cache_path /var/cache/nginx/proxy_cache levels=1:2 keys_zone=my_cache:10m inactive=60m max_size=1g;
    proxy_cache_key "$scheme$proxy_host$request_uri";

    # ...
    server {
        listen 80;
        server_name example.com;

        location / {
            proxy_pass http://backend_servers;
            proxy_set_header Host $host;

            proxy_cache my_cache;
            proxy_cache_valid 200 302 10s;
            proxy_cache_valid 404 1m;

            # Защита от "стада бизонов" и отказоустойчивость
            proxy_cache_lock on;
            proxy_cache_min_uses 2;
            proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
            proxy_background_update on; # Для Nginx Plus / Angie

            # Обход кэша
            proxy_cache_bypass $cookie_nocache $arg_nocache;
            proxy_no_cache $cookie_session;

            # Заголовок для отладки
            add_header X-Proxy-Cache $upstream_cache_status;
        }

        # Пример location, где кэширование отключено
        location /admin/ {
            proxy_pass http://backend_admin;
            proxy_cache off; # Отключаем кэширование для админки
        }
    }
}
```

## 5. Отладка и проверка кэша

Для проверки работы кэша можно добавить заголовок в ответ Nginx, который покажет статус кэширования.

```nginx
add_header X-Proxy-Cache $upstream_cache_status;
```
*   `$upstream_cache_status` может принимать значения:
    *   `MISS`: Запрос не найден в кэше, Nginx обратился к бэкенду.
    *   `HIT`: Ответ был успешно отдан из кэша.
    *   `EXPIRED`: Запись в кэше устарела, Nginx обратился к бэкенду для обновления.
    *   `STALE`: Ответ отдан из устаревшего кэша (например, из-за недоступности бэкенда при `proxy_cache_use_stale`).
    *   `UPDATING`: Ответ отдан из устаревшего кэша, пока в фоне происходит обновление (`proxy_background_update`).
    *   `BYPASS`: Кэш был обойден (из-за `proxy_cache_bypass`).
    *   `REVALIDATED`: Nginx проверил актуальность кэшированного элемента у бэкенда (с помощью заголовка `If-Modified-Since`), и бэкенд ответил `304 Not Modified`.

## 6. Производительность дискового кэша

Часто возникают вопросы о том, не будет ли кэширование на диске медленным по сравнению с решениями в оперативной памяти (например, Memcached или Redis). На практике, производительность дискового кэша Nginx очень высока.

Современные операционные системы эффективно кэшируют часто запрашиваемые файлы в оперативной памяти (файловый кэш ОС, page cache). Это означает, что если файлы из кэша Nginx запрашиваются регулярно, они с большой вероятностью будут находиться в RAM, и Nginx будет отдавать их с минимальной задержкой, сопоставимой со скоростью работы памяти. Использование специализированных in-memory хранилищ не всегда дает значительный выигрыш в производительности для этой задачи, но усложняет архитектуру.
