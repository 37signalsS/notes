# Мониторинг PHP-FPM

## Определения

**PHP-FPM (FastCGI Process Manager)** — это альтернативная реализация PHP FastCGI с дополнительными функциями, предназначенная для высоконагруженных сайтов. Мониторинг PHP-FPM критичен для обеспечения стабильности веб-приложений, так как этот компонент является связующим звеном между веб-сервером (Nginx/Angie) и кодом приложения.

**PHP-FPM Status Page** — встроенный механизм самодиагностики, предоставляющий информацию о текущем состоянии пулов процессов, очередях и детальную статистику по каждому воркеру.

**OpenMetrics (PHP 8.4+)** — стандарт формата метрик, поддерживаемый PHP-FPM нативно начиная с версии 8.4, что позволяет интегрировать его с Prometheus/Grafana Alloy без использования сторонних экспортеров.

## Основные концепции

### Эшелонированный мониторинг
Эффективный мониторинг PHP-FPM строится на трех уровнях:
1.  **Инфраструктурный (Blackbox):** Проверка доступности порта/сокета и времени ответа FastCGI.
2.  **Внутренний (Whitebox):** Анализ страницы статуса (метрики пулов и воркеров).
3.  **Системный (Sidecar/Node):** Мониторинг потребления CPU/RAM конкретными процессами `php-fpm` через системные утилиты.

### Золотые сигналы SRE для PHP-FPM
*   **Latency:** Время обработки запроса (отслеживается через `slowlog` и метрики веб-сервера).
*   **Traffic:** Количество принятых соединений (`accepted conn`).
*   **Errors:** Ошибки конфигурации, таймауты и сегфолты (логи ошибок).
*   **Saturation:** Длина очереди (`listen queue`) и достижение лимита воркеров (`max children reached`).

## Ключевые метрики

### 1. Насыщение и очереди (КРИТИЧЕСКОЕ)
*   **`listen queue`**: Количество запросов, ожидающих в очереди на уровне сокета. Если > 0, приложение не справляется с нагрузкой.
*   **`max children reached`**: Счетчик того, сколько раз пул достигал лимита `pm.max_children`. Если значение растет, это прямой сигнал к увеличению лимита или оптимизации кода.
*   **`listen queue len`**: Максимально допустимый размер очереди (backlog). При достижении этого лимита Nginx вернет `502 Bad Gateway`.

### 2. Состояние пула воркеров
*   **`active processes`**: Воркеры, выполняющие код в данный момент. Приближение к `max_children` вызывает рост Latency.
*   **`idle processes`**: Воркеры в ожидании. Слишком большое число при `pm = dynamic` может указывать на избыточное потребление RAM в простое.
*   **`start since`**: Время работы мастера. Частые перезапуски могут свидетельствовать о нестабильности (падениях процесса).

### 3. Производительность и OPcache
*   **`slow requests`**: Количество запросов, превысивших `request_slowlog_timeout`. Рост метрики требует немедленного анализа `slowlog`.
*   **OPcache Hit Rate**: Процент попаданий в кэш скомпилированного байт-кода. Значение ниже 98% указывает на неэффективное использование памяти или слишком частую инвалидацию кэша.
*   **OPcache Memory Usage**: Заполнение памяти для байт-кода. При 100% заполнении PHP перестает кэшировать новые файлы, что резко снижает производительность.

### 4. Детальные метрики воркеров (Full Status)
При использовании `?full` доступны данные по каждому процессу:
*   **`last request memory`**: Потребление памяти последним запросом. Позволяет выявить «утечки» или тяжелые скрипты.
*   **`last request cpu`**: Затраты процессорного времени.
*   **`request uri`**: Путь скрипта, вызвавшего нагрузку.

## Практические сценарии

### Настройка безопасной страницы статуса

В 2026 году, после обнаружения **CVE-2026-6735**, критически важно ограничить доступ к странице статуса.

1.  **В конфигурации пула (`www.conf`):**
    ```ini
    pm.status_path = /fpm-status
    ping.path = /fpm-ping
    ```

2.  **В конфигурации Nginx/Angie:**
    ```nginx
    location ~ ^/(fpm-status|fpm-ping)$ {
        access_log off;
        # Доступ только для локального экспортера или систем мониторинга
        allow 127.0.0.1;
        allow 10.0.0.0/8; 
        deny all;

        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_pass unix:/run/php/php8.4-fpm.sock;
    }
    ```

### Использование нативных метрик PHP 8.4 (OpenMetrics)

Если используется PHP 8.4+, Prometheus может собирать данные напрямую:
```bash
# Проверка формата OpenMetrics через curl
curl "http://localhost/fpm-status?openmetrics"
```
Для получения детальной статистики по воркерам:
```bash
curl "http://localhost/fpm-status?openmetrics&full"
```

### Интеграция с Prometheus через экспортер
Для версий PHP < 8.4 используется `php-fpm-exporter` (рекомендуется версия v3.0+ с поддержкой OPcache).

**Пример запуска в Docker:**
```bash
docker run -d \
  --name phpfpm-exporter \
  -e PHP_FPM_SCRAPE_URI="unix:///run/php/php-fpm.sock;/fpm-status" \
  -p 9253:9253 \
  hipages/php-fpm_exporter:3.0
```

### Ключевые алерты (PromQL)

1.  **Пул переполнен:**
    ```promql
    phpfpm_max_children_reached_total > 0
    ```
2.  **Рост очереди запросов:**
    ```promql
    phpfpm_listen_queue > 0
    ```
3.  **Низкий Hit Rate OPcache:**
    ```promql
    (phpfpm_opcache_hits / (phpfpm_opcache_hits + phpfpm_opcache_misses)) < 0.98
    ```

### Диагностика утечек памяти (System Level)
Если мониторинг показывает рост `total processes` и RAM, используйте `pidstat` для поиска конкретного воркера:
```bash
# Мониторинг RSS памяти PHP-FPM воркеров каждые 5 сек
pidstat -r -C php-fpm 5
```
