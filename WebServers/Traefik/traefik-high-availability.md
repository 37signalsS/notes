# High Availability Traefik: несколько инстансов и zero-downtime

## Определения

**High Availability (HA)** — обеспечение непрерывности обслуживания при отказе одного или нескольких узлов: минимум 2 одинаковых инстанса за балансировщиком, отказоустойчивое хранилище конфигурации/сертификатов.

**Zero-downtime (нулевой даунтайм)** — обновление/рестарт трафика без разрыва обслуживания: пока один инстанс останавливается, остальные принимают запросы.

**Rolling update** — обновление реплик поочередно (одна за другой), при котором в каждый момент времени есть «живой» инстанс.

**Drain (слив трафика)** — перевод инстанса в режим «не принимать новые запросы, доработать активные» перед остановкой (реализуется через `transport.lifeCycle`).

**Stateless-природа Traefik** — инстансы не хранят общее состояние (нет кластера/лидер-элекции в OSS): безопасно запускать несколько реплик, куски состояния (сертификаты ACME, sticky-куки) привязаны к каждому инстансу отдельно.

## Базовые концепции

### Почему HA возможен без кластера

Traefik OSS **не имеет** собственного механизма кластеризации, лидер-элекции и общеинстансного состояния (shared config/raft — только в Traefik Hub Enterprise). Это осознанная модель: каждый инстанс — stateless-прокси конфигурации, рисуемой из общего источника (File+шаблоны, KV-store, Consul, Nomad). Горизонтальное масштабирование = просто «еще одна реплика» с одинаковым конфигом.

Следствия для проектирования HA:

1. **Источник конфигурации должен быть общим.** Если конфиг — файлы на хосте, синхронизируйте каталог (Git checkout, конфиг-менеджмент Puppet/Ansible, NFS с осторожностью из-за `fs.inotify`). Удобнее — KV-store или Consul Catalog (см. [Провайдеры конфигурации](./traefik-providers-advanced.md)), чтобы обновление конфига автоматически доходило до всех реплик.
2. **`acme.json` нельзя шарить между инстансами.** Два процесса, пишущих в один файл, → конфликт и повреждение хранилища сертификатов. Каждому инстансу — свой файл, и задача ACME решается отдельно (см. ниже).
3. **Sticky-сессии работают в пределах инстанса.** Кука выдается конкретным инстансом; при повторном попадании на другой инстанс привязка пересоздается. Для стабильных сессий с несколькими репликами либо используйте внешний LB с хэшированием по клиенту, либо сессионное хранилище на бэкенде (кэш, DB сессий).
4. **Метрики у каждой реплики свои.** Для алертов агрегируйте метрики реплик (тэг `instance`) и строить SLO надо по совокупности (см. [Наблюдаемость Traefik](./traefik-observability.md)).

### Health check инстанса для внешнего балансировщика

Встроенный endpoint `/ping` отдает `200` только когда инстанс способен принимать трафик:

```yaml
entryPoints:
  ping:
    address: ":8082"
ping:
  entryPoint: ping
```

- Внешний LB (keepalived/HAProxy/NLB) шлет `GET /ping` и в `200`/`503` понимает статус ноды.
- При рестарте или drain-периоде Traefik отвечает `503`, LB убирает ноду из пула (если настроен passive/health) — это ключ к rolling-обновлению без потерь.

### ACME в HA: варианты без шаринга acme.json

| Вариант | Как работает | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **DNS-01 API** | Каждый инстанс решает по своим креденшелам (DNS-провайдер), получает свой сертификат | Просто, независимо | Нужны права на DNS-зону; N сертификатов на каждый домен |
| **Отдельный обработчик ACME** | Внешний cert-manager/Pebble: выдает сертификаты в общее хранилище, Traefik их просто подхватывает (file/Certificate options) | Один источник сертификатов, без дублей | Лишний компонент |
| **Резервное копирование** | `acme.json` с одного инстанса периодически копируется на остальных (не в рантайме!) | Просто | Расхождение; риск конфликта записи |

В любом случае **не** ставьте несколько инстансов на один общий `acme.json`.

## Практические сценарии

### Сценарий 1: Две реплики за keepalived (ВИП, L4)

Классика bare-metal (паттерн keepalived описан в [OpenSearch HA keepalived](../../ELK_Stack/OpenSearch/opensearch_high_availability_keepalived.md), переносится и на Traefik):

- Два хоста `t1`, `t2`; общий виртуальный IP (VIP) на внешнем интерфейсе держит активная нода.
- Traefik слушает `:80/:443` на обоих; VIP направляет клиентов на активного.
- При отказе `t1` keepalived перекидывает VIP на `t2`; уже установленные TCP упадут (L4), но новые запросы пойдут на живого.
- Health-check через `/ping` использует external health-agent (keepalived `misc_check`/script + curl `/ping`).

### Сценарий 2: Rolling update сервиса из двух реплик (Docker Swarm/K8s/система)

```
┌─────────────┐   лба               ┌─────────────┐
│ клиент ─────┼──────────────────────▶   t1        │
└─────────────┘                      │   t2        │
                                     └─────────────┘
   конфиг: общий источник (file watch / KV / Consul)
```

Порядок нулевого даунтайма:

1. Убедитесь, что оба инстанса работают за LB с включенным health check `/ping`.
2. Обновите **первую** реплику: drain (`graceTimeout`), stop, старт с новой версией, подождите `200/PING`.
3. Проверьте даунтайм первой реплики: пока она выключена, `t2` обслуживает 100% трафика.
4. Повторите для второй реплики (в Swarm/Deployment это делает оркестратор по умолчанию чередующимся обновлением).
5. Только затем обновляйте шаблоны конфигурации (они должны оставаться совместимыми: при major-миграции смотрите [Миграция v2 → v3](./traefik-migration-v2-to-v3.md)).

Число одновременно отрабатывающих реплик задает допустимость: при N репликах отказ N-1 инстансов безвреден; обновление выдерживает отключение `ceil(N/2)` за раз.

### Сценарий 3: Drain конкретного инстанса

Без оркестратора делается вручную:

```bash
# 1) Переключить LB в PENDING/DRAIN либо обнулить вес ноды
# 2) Перевести ноду в maintenance (уменьшить вес/исключить из health)
# 3) Дать соединениям завершиться (graceTimeout ≥ ожидаемого времени запроса)
sleep   <grace_timeout>
# 4) Остановить Traefik
sudo systemctl stop traefik
# 5) После обновления: старт, дождаться /ping 200, вернуть вес
```

### Сценарий 4: Общий конфиг через HashiCorp Consul + Consul Catalog

Лучший bare-metal-паттерн HA: конфигурация живет в Consul, Traefik подписан на каталог и метки сервисов — правки достигают всех реплик без синхронизации файлов (см. [Провайдеры конфигурации](./traefik-providers-advanced.md)).

```yaml
providers:
  consulCatalog:
    endpoint:
      address: 10.0.0.10:8500
    exposedByDefault: false
```

### Сценарий 5: Capacity Planning (расчет ресурсов)

Traefik — stateless-прокси, поэтому основная нагрузка на него — это **throughput** и **открытые соединения**, а не хранение состояния.

#### Формула sizing

```
RPS_per_instance = (CPU_cores × 2000) / (1 + (avg_latency_ms / 100))
```

Где:
- `CPU_cores` — число vCPU на инстанс.
- `avg_latency_ms` — средняя латентность обработки запроса Traefik (включая сеть до бэкенда).
- Коэффициент `2000` — эмпирический для Go-рантайма на x86_64 с AES-NI.

Пример:
- 2 vCPU, латентность 20 ms → RPS_per_instance ≈ 2 × 2000 / 1.2 ≈ 3 300 req/s.
- При целевом RPS 10 000 req/s → минимум 3 инстанса (с запасом 20% → 4 инстанса).

#### Память

- Базовый RSS: ~30–50 MB на инстанс (зависит от числа роутеров и middleware).
- На каждый 10 000 активных соединений добавляется ~20 MB (keep-alive пулы).
- Для production: **лимит 128–256 MB** на инстанс (GOMAXPROCS × 64 MB минимум).

#### Файловые дескрипторы

```yaml
# systemd unit
[Service]
LimitNOFILE=65536
```

Или в Docker:

```yaml
services:
  traefik:
    ulimits:
      nofile:
        soft: 65536
        hard: 65536
```

Расчет: `max_open_files ≥ (max_connections × 2) + 1024`. Для 10 000 concurrent connections → лимит 21 000+.

#### Мониторинг для capacity planning

```bash
# Текущие открытые FD
cat /proc/$(pgrep -f traefik)/limits | grep 'open files'

# Активные соединения на entrypoint
curl -s localhost:8080/metrics | rg 'traefik_entrypoint_requests_total|traefik_service_open_connections'
```

Алерты:
- `traefik_service_open_connections` > 80% от расчетного capacity.
- `traefik_entrypoint_request_duration_seconds` p99 растет при росте RPS.

#### Методология load testing

```bash
# wrk — быстрый бенчмарк
wrk -t12 -c400 -d30s --latency https://app.example.com/
# → Latency p99, Requests/sec, Transfer

# autocannon — Node.js, похож на wrk
autocannon -c 100 -d 30 -p 10 https://app.example.com/
```

Критерии:
- p99 latency < SLA (обычно < 200 ms для edge).
- Ошибки 5xx < 0.1%.
- CPU < 70% sustained.
- FD exhaustion не достигается при максимальном RPS.

### Сценарий 6: Multi-cluster (активный-активный, Traefik Hub)

Traefik OSS **не имеет** встроенного multi-cluster контура. Для multi-cluster ingress рассмотрите:

1. **Traefik Hub Runtime Platform** (commercial) — centralized config, API, analytics для нескольких кластеров/инстансов. Замена самосборному стеку.
2. **Самосборный вариант:**
   - Каждый кластер имеет свой инстанс Traefik за локальным LB.
   - DNS-level multi-cluster: `app.example.com` резолвится в несколько VIP через GSLB/GeoDNS (TTL 60s).
   - Shared config: Consul Catalog или GitOps (ArgoCD/Flux) синхронизирует конфигурацию между кластерами.
   - ACME: DNS-01 с общим API-ключом провайдера (не шарите `acme.json`).
   - Session affinity: sticky-сессии на уровне GSLB не работают — используйте JWT/Redis для хранения сессий.

Ограничения:
- Multi-cluster active-active с session stickiness — нет из коробки.
- Failover через DNS: TTL 60s дает «незрячий» период до 60s при отказе кластера.
- Для L7 traffic management между кластерами используйте Service Mesh (Istio multi-cluster) или API Gateway (Kong, Envoy Gateway).

## Устранение неисправностей

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Sticky-сессии «теряются» между репликами** | Кука ушла на другой инстанс | Внешний LB с hash по клиенту ИЛИ кука на бэкенде; не полагаться на привязку Traefik между нодами |
| **Обе реплики отвечают на VIP на разных хостах** | keepalived split-brain | Настроить `unicast`/фикс-авторитеты, проверять multicast-линк |
| **ACME-сертификаты разъехались у реплик** | Каждый инстанс решил сам + код `429 too many certificates` | Перейти на DNS-01 или внешний ACME (см. выше) |
| **Редиректы/сервисы на одной реплике, но не на другой** | Конфиг не синхронизирован | Перевести конфиг на общий источник (KV/Consul/шаблон Git) |
| **Health check шлет 503 → LB дергает пул** | Инстанс в drain | Проверить `transport.lifeCycle`, метрики; LB-пул вернется сам после /ping 200 |

## Рекомендации

- Минимум для продакшена: **2 инстанса + общий источник конфигурации + health check `/ping`**. Один инстанс — это SPOF, его рестарт = даунтайм.
- Не шарите `acme.json`; выбирайте DNS-01 или внешний ACME.
- Внешний LB должен иметь passive/active health по `/ping`, а не по TCP-порту.
- Sticky и HA — антагонисты: при сессиях закрепляйте клиента на уровне внешнего LB.
- Для Docker-среды совместите HA с контейнерным запуском — [Traefik с Docker Compose](./traefik_with_docker_compose.md).
