# HAProxy

## Определения

HAProxy ([haproxy.org](https://www.haproxy.org/)) — высокопроизводительный балансировщик нагрузки и прокси-сервер для TCP/HTTP-приложений. Стандарт для распределения трафика в высоконагруженных системах. Обеспечивает отказоустойчивость, масштабирование и маршрутизацию запросов.

## Основные концепции

HAProxy распределяет входящие запросы между бэкенд-серверами, повышая производительность и отказоустойчивость. Для обеспечения высокой доступности балансировщика часто используется в связке с [Keepalived](../../Networking/ServicesAndTools/keepalived_overview.md).

### Основной функционал

- **L4/L7 Балансировка:** Работает на транспортном (TCP) и прикладном (HTTP/HTTPS) уровнях, поддерживает различные алгоритмы распределения (roundrobin, leastconn, source и др.).
- **Проверки доступности (Health Checks):** Регулярно опрашивает бэкенды, автоматически исключает отказавшие узлы и возвращает их при восстановлении.
- **Терминирование SSL:** Может расшифровывать HTTPS-трафик, снимая нагрузку с серверов приложений.

Схема работы:

1. Клиент отправляет запрос на виртуальный IP-адрес, который слушает HAProxy.
2. HAProxy, выступая в роли reverse proxy, принимает запрос.
3. На основе выбранного алгоритма балансировки, HAProxy перенаправляет запрос на один из доступных backend-серверов (например, [Nginx](../Nginx/Core/nginx_overview.md)).
4. Backend-сервер обрабатывает запрос и возвращает ответ HAProxy, который затем передает его клиенту.

### Режимы работы (mode)

HAProxy работает в двух основных режимах, определяющих уровень анализа трафика:

| Режим | Уровень | Что доступно | Ограничения |
| :--- | :--- | :--- | :--- |
| **`mode tcp`** | L4 (транспортный) | IP, порт, SNI, TLS-рукопожатие | Не анализирует HTTP |
| **`mode http`** | L7 (прикладной) | Заголовки, path, cookies, методы | Только HTTP/HTTPS трафик |

**Критично для ACL:** Если прокси работает в `mode tcp`, ACL по HTTP-заголовкам, path или cookies **не сработают**, так как HAProxy не анализирует содержимое HTTP-запросов.

### ACL (Access Control Lists) и маршрутизация

HAProxy — это не просто балансировщик, а движок правил маршрутизации. Основная логика происходит во `frontend`, где определяются ACL и правила `use_backend`.

**Синтаксис:**

```haproxy
frontend http_frontend
    bind *:80
    mode http
    
    # Объявление ACL
    acl is_api path_beg /api
    acl blocked_ip src 10.0.0.100
    
    # Правила маршрутизации
    http-request deny if blocked_ip
    use_backend api_backend if is_api
    default_backend web_backend
```

#### Порядок правил

HAProxy читает конфигурацию **сверху вниз**. Если правило раньше завершает обработку запроса — следующие правила уже не выполняются.

**Пример проблемы:**

```haproxy
frontend http_frontend
    bind *:80
    mode http
    
    acl blocked path_beg /admin
    http-request deny if blocked
    use_backend web_backend  # Никогда не выполнится для /admin
```

Если ACL `blocked` сработал — клиент получит 403, а `backend` вообще не будет выбран.

#### Распространённые ошибки с ACL

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| ACL не срабатывает | Неправильный `mode` (tcp вместо http) | Использовать `mode http` для L7-правил |
| Запрос уходит не в тот backend | Порядок правил нарушен | Размещать специфичные правила перед общими |
| `http-request` игнорируется | Правило после `use_backend` | `http-request` должны быть перед выбором backend |

### Алгоритмы балансировки нагрузки

HAProxy предоставляет широкий набор алгоритмов (методов) балансировки, позволяющих оптимизировать распределение трафика в зависимости от требований приложения:

- **`roundrobin`**: Запросы распределяются по серверам поочередно (по кругу). Это алгоритм по умолчанию. Поддерживает веса серверов, что позволяет направлять больше трафика на более мощные серверы.
- **`static-rr`**: Аналогичен `roundrobin`, но веса серверов могут быть изменены на лету.
- **`leastconn`**: Новый запрос направляется на сервер с наименьшим количеством активных соединений. Идеально подходит для длинных TCP-сессий (например, базы данных, FTP), где количество соединений является хорошим показателем загрузки сервера.
- **`first`**: Серверы заполняются соединениями по порядку до достижения максимального значения, после чего HAProxy переключается на следующий. Полезен, когда нужно максимально загрузить один сервер, прежде чем переходить к следующему.
- **`source`**: IP-адрес источника хэшируется и делится на вес серверов, чтобы определить, на какой сервер будет отправлен запрос. Это обеспечивает "липкость" сессий — клиент с одним и тем же IP-адресом будет всегда попадать на один и тот же сервер. Полезно для приложений, требующих сохранения состояния сессии на конкретном сервере.
- **`uri`**: Хэшируется левая часть URI запроса (или весь URI, если указано). Позволяет направлять запросы к одному и тому же ресурсу на один и тот же сервер.
- **`url_param`**: Ищет указанный параметр в URL и использует его значение для хэширования. Позволяет балансировать нагрузку на основе определенных параметров запроса.
- **`hdr`**: Хэширует указанный HTTP-заголовок. Позволяет балансировать нагрузку на основе значений HTTP-заголовков (например, `User-Agent`, `Cookie`).
- **`rdp-cookie`**: Используется для балансировки RDP-трафика на основе RDP-куки.
- **`random`**: Выбирает сервер случайным образом.
- **`least_time` (HAProxy Enterprise/ALOHA)**: Направляет запрос на сервер с наименьшим средним временем ответа.

Выбор алгоритма зависит от специфики приложения и требований к балансировке. Для большинства HTTP-приложений `roundrobin` или `leastconn` являются хорошим выбором. Для приложений, требующих сохранения состояния сессии, подходят `source` или `hdr` (с использованием куки).

## Практические сценарии

### Работа с SSL/TLS

HAProxy обладает мощными возможностями по работе с SSL/TLS трафиком, что позволяет ему выступать в роли точки терминирования SSL (SSL/TLS Termination) или просто пропускать зашифрованный трафик к бэкендам (SSL/TLS Passthrough).

#### SSL/TLS Termination (Терминирование SSL/TLS)

В этом режиме HAProxy расшифровывает входящий HTTPS-трафик, а затем перенаправляет его на бэкенд-серверы по обычному HTTP (или по HTTPS, если бэкенды также настроены на SSL). Это снижает нагрузку на бэкенды и позволяет HAProxy применять правила балансировки и инспекции трафика на прикладном уровне (L7).

**Пример конфигурации для SSL/TLS Termination:**

```haproxy
frontend https_frontend
    bind *:443 ssl crt /etc/haproxy/certs/your_domain.pem
    mode http
    default_backend http_backend

backend http_backend
    mode http
    balance leastconn
    server web01 192.168.131.33:8080 check
    server web02 192.168.131.34:8080 check
```

- `bind *:443 ssl crt /etc/haproxy/certs/your_domain.pem`: HAProxy слушает порт 443, терминирует SSL, используя указанный сертификат.
- `mode http`: Указывает, что HAProxy работает на HTTP-уровне.

#### SSL/TLS Passthrough (Проброс SSL/TLS)

В этом режиме HAProxy просто пробрасывает зашифрованный трафик напрямую к бэкенд-серверам, не расшифровывая его. Это полезно, когда SSL/TLS терминирование должно происходить непосредственно на бэкендах, или когда HAProxy используется только для балансировки TCP-соединений. В этом случае HAProxy работает на транспортном уровне (L4).

**Пример конфигурации для SSL/TLS Passthrough:**

```haproxy
frontend https_passthrough
    bind *:443
    mode tcp
    default_backend https_backend

backend https_backend
    mode tcp
    balance leastconn
    server web01 192.168.131.33:443 check
    server web02 192.168.131.34:443 check
```

- `mode tcp`: HAProxy работает на TCP-уровне, не вмешиваясь в содержимое трафика.
- Трафик пробрасывается на порт 443 бэкендов.

### Примеры конфигурации

HAProxy может работать как на транспортном (TCP, L4), так и на прикладном (HTTP, L7) уровне, что обеспечивает большую гибкость в балансировке различных типов трафика.

#### Пример 1: Балансировка HTTP-трафика (L7)

Этот пример демонстрирует балансировку HTTP-трафика, где HAProxy работает на прикладном уровне, позволяя использовать более сложные правила маршрутизации и инспекции HTTP-заголовков.

```haproxy
frontend http_frontend
    bind *:80
    mode http
    default_backend http_backend

backend http_backend
    mode http
    balance leastconn # Алгоритм балансировки: наименьшее количество соединений
    server web01 192.168.131.33:8080 check
    server web02 192.168.131.34:8080 check
```

- `mode http`: Указывает, что HAProxy работает на HTTP-уровне.
- `balance leastconn`: Используется алгоритм `leastconn`, который направляет запросы на сервер с наименьшим количеством активных HTTP-сессий.

#### Пример 2: Балансировка TCP-трафика (L4)

Этот пример показывает, как HAProxy может балансировать любой TCP-трафик (например, базы данных, SSH, или даже HTTPS в режиме passthrough), работая на транспортном уровне.

```haproxy
frontend tcp_frontend
    bind *:8080 # Пример порта для TCP-трафика
    mode tcp
    default_backend tcp_backend

backend tcp_backend
    mode tcp
    balance roundrobin # Алгоритм балансировки: поочередно
    server db01 192.168.131.33:5432 check # Пример: балансировка PostgreSQL
    server db02 192.168.131.34:5432 check
```

- `mode tcp`: Указывает, что HAProxy работает на TCP-уровне, не вмешиваясь в содержимое трафика. Это позволяет балансировать любые протоколы, работающие поверх TCP.
- `balance roundrobin`: Используется алгоритм `roundrobin` для поочередного распределения TCP-соединений.

## Примеры использования

### Балансировка нагрузки для API-сервера Kubernetes

В bare-metal кластерах Kubernetes HAProxy является стандартным решением для обеспечения высокой доступности и балансировки нагрузки для `kube-apiserver`.

- **Задача:** Распределить входящие запросы к API между несколькими master-узлами.
- **Решение:** HAProxy работает в режиме L4 (`mode tcp`), принимая трафик на виртуальном IP-адресе (управляемом [Keepalived](../../Networking/ServicesAndTools/keepalived_overview.md)) и пробрасывая его на порт `6443` активных master-узлов. HAProxy также выполняет health-check'и, чтобы направлять трафик только на работающие экземпляры API-сервера.

> Подробное руководство по настройке этой связки приведено в документе [Настройка High Availability API-сервера с помощью Keepalived и HAProxy](../../Kubernetes/Installation/kubeadm_ha_with_keepalived_haproxy.md).

## Дополнительная информация

### Ключевые особенности

- **Производительность:** Однопоточная событийная модель, минимальное потребление памяти, миллионы запросов в секунду.
- **Надёжность:** Доказанная стабильность, используется в критически важных средах.
- **Гибкость:** Балансировка HTTP/HTTPS и TCP-протоколов (базы данных, FTP, SSH, VPN); универсальное решение.
- **Безопасность:** Защита от DDoS (ограничение соединений, таймауты), поддержка ACL для фильтрации трафика.
- **Конфигурация без перезагрузки:** Плавная перезагрузка (graceful reload) без потери активных соединений.
- **Оптимизация соединений:** Поддержка Keep-Alive и HTTP/2 для уменьшения задержек.
- **Мониторинг:** Встроенная страница статистики в реальном времени (метрики запросов, состояние серверов, ошибки).
- **Маршрутизация:** Гибкие правила на основе заголовков, cookies, URL-путей (HTTP) или IP/портов (TCP).

HAProxy остаётся стандартом индустрии благодаря сочетанию высокой производительности, гибкости настройки и проверенной годами надёжности, являясь краеугольным камнем инфраструктуры в проектах любого масштаба.
