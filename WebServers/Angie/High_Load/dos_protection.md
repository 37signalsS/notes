# Защита от DoS-атак в Angie

## Определения

**Защита от DoS-атак (Denial of Service — «отказ в обслуживании») на уровне приложения (L7)** — комплекс методов и конфигураций, направленных на ограничение и фильтрацию входящих запросов. Основная цель — предотвратить исчерпание вычислительных ресурсов сервера (CPU, RAM, сетевые дескрипторы) и сохранить доступность сервиса для легитимных пользователей.

## Базовые концепции

Angie предоставляет расширенный набор инструментов для противодействия атакам прикладного уровня. В отличие от стандартного Nginx, Angie включает возможности мониторинга и синхронизации данных, которые позволяют строить более эффективные и прозрачные системы защиты.

### Типы угроз и методы защиты

| Тип угрозы | Метод защиты | Директива / Модуль |
|:-----------|:-------------|:-------------------|
| HTTP-флуд с одного IP | Ограничение частоты запросов | `limit_req`, `limit_req_zone` |
| Исчерпание соединений | Ограничение числа одновременных соединений | `limit_conn`, `limit_conn_zone` |
| Кластерный DoS | Синхронизация лимитов между узлами | Параметр `sync` в зонах |
| Медленные атаки (Slowloris) | Ограничение времени ожидания данных | `client_header_timeout`, `client_body_timeout` |
| Монополизация канала | Ограничение скорости отдачи | `limit_rate` |
| Автоматизированные боты | Блокировка по User-Agent | `map` + `if` |
| Атаки из конкретных регионов | GeoIP-блокировка | `ngx_http_geoip_module` |
| Примитивные боты без JS | Проверка браузера (Challenge) | `ngx_http_testcookie_module` |

### Принцип работы ограничения ресурсов

Эффективная защита строится на трех этапах:

1. **Идентификация (Зоны):** Создание областей в разделяемой памяти для хранения состояний клиентов по ключу (IP, Cookie, API Key).
2. **Синхронизация (SSoT):** В Angie состояние зон может синхронизироваться между всеми узлами кластера, создавая единый источник истины о поведении клиента.
3. **Действие:** Применение ограничений с возможностью мягкого тестирования (`dry_run`) или немедленной блокировки с заданным кодом ошибки.

### Границы применимости защиты на уровне сервера

Встроенные механизмы эффективны против атак средней интенсивности и ботов. Для отражения масштабных распределенных атак (DDoS) уровня терабит в секунду необходимо использование внешних сервисов очистки трафика, CDN и специализированных WAF.

Подробный обзор теории атак см. в [обзоре DoS/DDoS](../../../Security/ApplicationSecurity/ddos_overview.md).

## Практические сценарии

### Ограничение частоты запросов — limit_req

Модуль `ngx_http_limit_req_module` ограничивает скорость обработки запросов, используя алгоритм leaky bucket.

**Продвинутые параметры:**
- `sync` — синхронизирует счетчики запросов в кластере Angie.
- `dry_run` — включает режим тестирования: запросы не блокируются, но информация о превышении логируется.
- `status` — позволяет задать код ответа при блокировке (например, 429 вместо 503).

**Пример конфигурации:**

```nginx
http {
    # Зона с синхронизацией для кластера
    limit_req_zone $binary_remote_addr zone=api_limit:20m rate=10r/s sync;

    # Настройка логирования и кода ответа
    limit_req_log_level warn;
    limit_req_status 429;

    server {
        location /api/v1/ {
            # burst=20: разрешаем всплеск до 20 запросов в очереди
            # nodelay: обрабатываем всплеск немедленно без задержек
            limit_req zone=api_limit burst=20 nodelay;
        }
    }
}
```

### Ограничение одновременных соединений — limit_conn

Модуль `ngx_http_limit_conn_module` ограничивает количество *активных* соединений с одного ключа. Это критично для защиты от атак, пытающихся занять все доступные слоты соединений.

**Пример конфигурации:**

```nginx
http {
    # Ограничение по IP
    limit_conn_zone $binary_remote_addr zone=perip:10m sync;
    # Ограничение по виртуальному серверу (общий лимит на сайт)
    limit_conn_zone $server_name zone=perserver:1m;

    limit_conn_status 429;

    server {
        # Не более 20 соединений с одного IP
        limit_conn perip 20;
        # Не более 2000 соединений на весь сервер
        limit_conn perserver 2000;
    }
}
```

### Защита от медленных атак (Slowloris)

Атаки типа Slowloris удерживают соединения открытыми, отправляя данные крайне медленно. Для защиты необходимо агрессивно настраивать таймауты.

```nginx
http {
    # Время ожидания заголовков запроса
    client_header_timeout 10s;
    # Время ожидания тела запроса между двумя операциями чтения
    client_body_timeout   10s;
    # Время ожидания при передаче ответа клиенту
    send_timeout          10s;
    
    # Ограничение времени жизни keep-alive соединений
    keepalive_timeout     65s 20s; # Второе значение отправляется в заголовке Keep-Alive
}
```

### Ограничение ресурсов для HTTP/2 и HTTP/3

Современные протоколы позволяют мультиплексировать множество запросов в одном соединении, что создает новые векторы атак.

```nginx
http {
    server {
        listen 443 quic reuseport;
        listen 443 ssl;
        http2 on;
        http3 on;

        # Ограничение количества параллельных потоков в одном соединении
        http2_max_concurrent_streams 128;
        http3_max_concurrent_streams 128;

        # Ограничение на количество запросов в одном соединении
        keepalive_requests 1000;
    }
}
```

### Тюнинг буферов и заголовков

Ограничение размеров буферов предотвращает атаки, направленные на переполнение оперативной памяти.

```nginx
http {
    # Максимальный размер заголовков
    client_header_buffer_size 1k;
    large_client_header_buffers 4 8k;

    # Максимальный размер тела запроса (предотвращает заливку огромных файлов)
    client_max_body_size 10m;
    
    # Ограничение количества заголовков (защита от атак на парсер)
    # Доступно в Angie / Nginx 1.29.8+
    max_headers 50;
}
```

### Географическая и поведенческая блокировка

Использование GeoIP и User-Agent позволяет отсечь значительную часть автоматизированного "шума".

**Пример с GeoIP2:**

```nginx
http {
    geoip2 /etc/angie/geo/Country.mmdb {
        $geoip2_data_country_code default=RU country iso_code;
    }

    map $geoip2_data_country_code $is_blocked {
        default 0;
        CN      1;
        US      1;
    }

    server {
        if ($is_blocked) {
            return 403;
        }
    }
}
```

### Наблюдаемость и мониторинг ограничений

Angie позволяет отслеживать эффективность защиты через `status_zone` и встроенный API.

```nginx
http {
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;
    
    server {
        # Сбор метрик для зоны сервера
        status_zone server_stats;

        location /api/ {
            limit_req zone=api_limit burst=20;
        }
    }
}
```

**Метрики для анализа:**
- `limit_req_status` — переменная, принимающая значения `passed`, `delayed`, `rejected`, `delayed_dry_run`, `rejected_dry_run`.
- Логи в формате JSON позволяют строить алертинг на всплески `rejected` запросов.
