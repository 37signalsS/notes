# Защита от DoS-атак в Angie

## Определения

**Защита от L7 DoS-атак** — методы ограничения запросов на уровне приложения для предотвращения исчерпания ресурсов веб-сервера.

## Базовые концепции

Веб-серверы уязвимы к атакам типа «отказ в обслуживании» (DoS), цель которых — сделать сервис недоступным для легитимных пользователей. Angie (как и Nginx) предоставляет встроенные модули для защиты на уровне приложения (L7 OSI).

### Типы угроз и методы защиты

| Тип угрозы | Метод защиты | Директива/модуль |
|:-----------|:-------------|:-----------------|
| HTTP-флуд с одного IP | Ограничение частоты запросов | `limit_req`, `limit_req_zone` |
| Исчерпание соединений | Ограничение числа одновременных соединений | `limit_conn`, `limit_conn_zone` |
| Монополизация канала | Ограничение скорости отдачи | `limit_rate` |
| Автоматизированные боты | Блокировка по User-Agent | `map` + `if` |
| Атаки из конкретных регионов | GeoIP-блокировка | `ngx_http_geoip_module` |
| Примитивные боты без JS | Проверка браузера | `ngx_http_testcookie_module` |

### Принцип работы rate limiting

Все модули ограничения частоты работают по схожему принципу:

1. **Определение зоны (`*_zone`)** — создается область в разделяемой памяти для хранения состояний клиентов (по ключу, обычно IP-адрес)
2. **Применение ограничения** — в нужном контексте (`http`, `server`, `location`) активируется подсчет запросов/соединений
3. **Действие при превышении** — запросы отклоняются с кодом **503 Service Temporarily Unavailable** (по умолчанию) или задерживаются

### Ограничения защиты на уровне веб-сервера

> **Важно:** Встроенные модули Angie эффективны только против простых атак с одного или нескольких IP. Они не защищают от масштабных DDoS-атак, когда трафик идет с тысяч распределенных источников. Для серьезной защиты необходимы специализированные внешние сервисы (CDN/WAF, Cloudflare, Qrator).

Подробный обзор типов атак и методов противодействия см. в [обзоре DoS/DDoS](../../../Networking/Concepts/dos_ddos_overview.md).

## Практические сценарии

### Ограничение частоты запросов (`limit_req`)

Для защиты от атак с высокой частотой запросов (флуд) с одного IP-адреса используется модуль `ngx_http_limit_req_module`. Он позволяет ограничить количество запросов, обрабатываемых в единицу времени.

- **`limit_req_zone`**: Директива, определяемая в блоке `http`. Она создает зону в разделяемой памяти для хранения состояний ключей (например, IP-адресов клиентов).
  - `key`: В качестве ключа обычно используется `$binary_remote_addr` для отслеживания IP-адресов. Использование бинарной версии экономит память.
  - `zone`: Имя и размер зоны. `10m` хватает для хранения примерно 160,000 состояний.
  - `rate`: Заданная средняя скорость (например, `10r/s` — 10 запросов в секунду).
- **`limit_req`**: Директива, применяемая в блоке `location` или `server`. Она активирует ограничение для данного контекста.
  - `burst`: Определяет, на сколько запросов клиент может превысить среднюю скорость. Эти "лишние" запросы помещаются в очередь.
  - `nodelay`: Если указан этот параметр, запросы сверх лимита, но в пределах `burst`, обрабатываются немедленно. Запросы, превышающие `burst`, сразу отклоняются с ошибкой **503 Service Temporarily Unavailable**. Если `nodelay` не указан, "лишние" запросы обрабатываются с задержкой, чтобы соответствовать заданной средней скорости, что может быть нежелательно.

**Пример конфигурации:**

```nginx
http {
    # Зона для ограничения: 10 МБ, ключ - IP клиента, скорость - 10 запросов/сек.
    limit_req_zone $binary_remote_addr zone=one:10m rate=10r/s;
}

server {
    location /api/ {
        # Разрешаем всплеск до 20 запросов.
        # Запросы сверх 10r/s, но в пределах 20, обрабатываются сразу.
        # Все, что выше burst, отклоняется с ошибкой 503.
        limit_req zone=one burst=20 nodelay;
    }
}
```

**Ограничения:** Метод неэффективен против распределенных атак (DDoS), когда трафик идет с множества разных IP. Также общий лимит будет распространяться на всех пользователей за одним NAT.

#### Ограничение числа одновременных соединений (`limit_conn`)

Модуль `ngx_http_limit_conn_module` позволяет ограничить количество *активных обрабатываемых соединений* для определенного ключа (например, для одного IP-адреса).

Это не ограничение общего числа TCP-соединений, а именно тех, в рамках которых в данный момент сервер обрабатывает запрос (от чтения заголовков до отправки ответа).

- **`limit_conn_zone`**: Определяет зону для подсчета соединений (аналогично `limit_req_zone`).
- **`limit_conn`**: Применяет ограничение в `location`, `server` или `http`.

**Пример конфигурации:**

```nginx
http {
    # Зона для ограничения по IP-адресу
    limit_conn_zone $binary_remote_addr zone=perip:10m;
}

server {
    # Ограничиваем до 10 активных соединений на один IP
    limit_conn perip 10;

    location /downloads/ {
        # Более строгий лимит для тяжелого контента
        limit_conn perip 2;
    }
}
```

**Ключевые отличия от `limit_req`:**

- `limit_conn` считает активные соединения, а `limit_req` — частоту запросов.
- `limit_conn` доступен в контексте `stream` для TCP/UDP проксирования, что делает его полезным для защиты не-HTTP сервисов. `limit_req` работает только в `http`.

#### Ограничение скорости отдачи контента (`limit_rate`)

Для экономии пропускной способности канала или предотвращения его монополизации одним клиентом, можно ограничить скорость отдачи ответа.

- **`limit_rate`**: Статически задает максимальную скорость в байтах/сек.
- **Переменная `$limit_rate`**: Позволяет задавать скорость динамически.

**Пример статического ограничения:**

```nginx
location /video/ {
    # Ограничение скорости скачивания до 500 КБ/с
    limit_rate 500k;
}
```

**Пример динамического ограничения (в зависимости от User-Agent):**

```nginx
http {
    # По умолчанию ограничения нет (0)
    map $http_user_agent $limit_rate {
        default 0;
        # Для curl-подобных клиентов устанавливаем лимит 500k
        "~*curl" 500k;
    }
}

server {
    location /static/ {
        # Применяем переменную
        set $limit_rate $limit_rate;
    }
}
```

Также для MP4-файлов существует специализированный модуль `ngx_http_mp4_module`, который с помощью директивы `mp4_limit_rate` позволяет ограничить скорость отдачи на основе битрейта файла, что более эффективно для видеостриминга.

#### Блокировка по User Agent

Метод позволяет отсеивать нежелательных ботов (консольные утилиты, скрипты нагрузочного тестирования) по заголовку `User-Agent`. Используется директива `map` для определения переменной и блок `if` для блокировки.

**Пример конфигурации:**

```nginx
http {
    # Определяем переменную $limit_search_bots на основе User-Agent
    map $http_user_agent $limit_search_bots {
        default 0;
        # Блокируем подозрительные шаблоны (регулярные выражения, без учёта регистра)
        "~*tester" 1;
        "~*curl$" 1;
        # Внимание: избегайте слишком широких правил (например, просто "bot"),
        # чтобы не заблокировать легитимных ботов (Googlebot, YandexBot)
    }

    server {
        location / {
            # Блокировка с кодом 421 (Misconfigured)
            if ($limit_search_bots = 1) {
                return 421;
            }
        }
    }
}
```

**Ограничения:**

- Метод неэффективен против продвинутых ботов, подделывающих User-Agent
- Требует осторожности при составлении регулярных выражений
- Легитимные боты должны уважать `robots.txt`, что может быть альтернативным методом управления

> **Примечание:** Блок `if` в данном случае безопасен и предсказуем, так как используется только для возврата кода ответа.

#### GeoIP-блокировка по странам

Метод позволяет ограничивать доступ к сайту на основе географического расположения клиента, определяемого по IP-адресу с помощью базы GeoIP. Требует установки внешнего модуля `ngx_http_geoip_module`.

**Необходимые компоненты:**

- Модуль `ngx_http_geoip_module` (подключается в main-контексте)
- База GeoIP (например, [GeoLite2 Country](https://github.com/P3TERX/GeoLite.mmdb))

**Пример конфигурации:**

```nginx
# Подключение модулей в main-контексте
load_module modules/ngx_http_geoip_module.so;
load_module modules/ngx_stream_geoip_module.so;

http {
    # Подключение базы GeoIP (путь к файлу .mmdb)
    geoip_country /etc/nginx/GeoLite2-Country.mmdb;

    # Создаём переменную $allowed_country на основе кода страны
    map $geoip_country_code $allowed_country {
        default no;          # По умолчанию доступ запрещён
        RU yes;              # Разрешаем Россию
        BY yes;              # Разрешаем Беларусь
        # Добавьте другие разрешённые страны
    }

    server {
        location / {
            # Блокировка запрещённых стран
            if ($allowed_country = no) {
                return 403;  # Forbidden
            }
        }
    }
}
```

**Коды стран:** Используются стандартные двухбуквенные коды ISO 3166-1 (RU, US, DE, CN и т.д.).

**Ограничения и риски:**

- Базы GeoIP не всегда точны (особенно для мобильных сетей, корпоративных прокси)
- Пользователи могут использовать VPN для обхода блокировки
- Высокий риск блокировки легитимных пользователей (туристы, экспаты, командировки)
- Не рекомендуется для постоянного использования без веских причин

> **Рекомендация:** Используйте GeoIP-блокировку только как временную меру при активной атаке из конкретных регионов, когда другие методы исчерпаны. Для постоянной фильтрации трафика предпочтительнее специализированные CDN/WAF-сервисы.

#### Test Cookie модуль (проверка браузера)

Сторонний модуль `ngx_http_testcookie_module` позволяет проверять клиентов на способность обрабатывать JavaScript и cookies, что отсеивает примитивных ботов.

**Статус модуля:** Проект не обновляется с 2018 года, но продолжает работать. Модуль доступен в репозитории Angie/Nginx.

**Принцип работы:**

1. При первом запросе сервер выдаёт страницу с JavaScript-кодом
2. Скрипт генерирует и устанавливает cookie с зашифрованным токеном
3. После успешной установки cookie клиент перенаправляется на исходную страницу
4. Боты без поддержки JS не проходят проверку

**Пример конфигурации:**

```nginx
# Подключение модуля в main-контексте
load_module modules/ngx_http_testcookie_module.so;

http {
    server {
        location / {
            # Включение проверки
            testcookie on;

            # Имя для cookie
            testcookie_name BPC;

            # Секретный ключ для шифрования (обязательно уникальный!)
            testcookie_secret my_unique_secret_key_here;

            # Использование remote_addr в качестве ключа сессии
            testcookie_arg remote_addr;

            # Максимальное количество редиректов для установки cookie
            testcookie_max_attempts 3;

            # Шаблон страницы с JavaScript для установки cookie
            testcookie_refresh_template '<html><body>Checking your browser...<script src="/js/aes.min.js"></script></body></html>';

            # Путь к JS-файлу для расшифровки токена
            # Файл должен быть размещён в статике
            testcookie_refresh_js_url /js/aes.min.js;
        }
    }
}
```

**Ограничения:**

- Неэффективен против продвинутых ботнетов с полноценным браузерным стеком
- Требует поддержки JavaScript на стороне клиента
- Может создавать проблемы для пользователей с отключённым JS
- Модуль не получает активных обновлений

> **Рекомендация:** Используйте как дополнительный уровень защиты в сочетании с другими методами. Для серьёзной защиты рассмотрите специализированные решения (CAPTCHA, поведенческий анализ, облачные WAF).
