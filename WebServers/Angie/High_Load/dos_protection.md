# Защита от DoS-атак в Angie

## Определения

**Защита от DoS-атак (Denial of Service — «отказ в обслуживании») на уровне приложения (L7)** — методы ограничения и фильтрации входящих запросов для предотвращения исчерпания ресурсов веб-сервера (центральный процессор (CPU), оперативная память).

## Базовые концепции

Веб-серверы уязвимы к атакам типа «отказ в обслуживании» (DoS), цель которых — сделать сервис недоступным для легитимных пользователей. Angie (как и Nginx) предоставляет встроенные модули для защиты на прикладном уровне (L7) модели взаимодействия открытых систем (OSI, Open Systems Interconnection).

### Типы угроз и методы защиты

| Тип угрозы | Метод защиты | Директива/модуль |
|:-----------|:-------------|:-----------------|
| HTTP-флуд с одного IP | Ограничение частоты запросов | `limit_req`, `limit_req_zone` |
| Исчерпание соединений | Ограничение числа одновременных соединений | `limit_conn`, `limit_conn_zone` |
| Монополизация канала | Ограничение скорости отдачи | `limit_rate` |
| Автоматизированные боты | Блокировка по User-Agent | `map` + `if` |
| Атаки из конкретных регионов | GeoIP-блокировка | `ngx_http_geoip_module` |
| Примитивные боты без JS | Проверка браузера | `ngx_http_testcookie_module` |

### Принцип работы ограничения скорости (Rate Limiting)

Все модули ограничения частоты работают по схожему принципу:

1. **Определение зоны (`*_zone`)** — создается область в разделяемой памяти для хранения состояний клиентов (по ключу, обычно IP-адрес сетевого протокола).
2. **Применение ограничения** — в нужном контексте (`http`, `server`, `location`) активируется подсчет запросов или соединений.
3. **Действие при превышении** — запросы отклоняются с кодом **503 Service Temporarily Unavailable** (по умолчанию) или задерживаются.

### Ограничения защиты на уровне веб-сервера

> **Важно:** Встроенные модули Angie эффективны только против простых атак с одного или нескольких IP. Они не защищают от масштабных распределенных атак (DDoS — Distributed Denial of Service), когда трафик идет с тысяч источников. Для серьезной защиты необходимы специализированные внешние сервисы: сети доставки контента (CDN, Content Delivery Network) или межсетевые экраны для веб-приложений (WAF, Web Application Firewall).

Подробный обзор типов атак и методов противодействия см. в [обзоре DoS/DDoS](../../../Networking/Concepts/dos_ddos_overview.md).

## Практические сценарии

### Ограничение частоты запросов (`limit_req`)

Для защиты от атак с высокой частотой запросов (флуд) с одного IP-адреса используется модуль `ngx_http_limit_req_module`. Он позволяет ограничить количество запросов, обрабатываемых в единицу времени.

- **`limit_req_zone`**: Директива, определяемая в блоке `http`. Она создает зону в разделяемой памяти для хранения состояний ключей (например, IP-адресов клиентов).
  - `key`: В качестве ключа обычно используется `$binary_remote_addr` для отслеживания IP-адресов. Использование бинарной версии экономит память.
  - `zone`: Имя и размер зоны. `10m` хватает для хранения примерно 160 000 состояний.
  - `rate`: Заданная средняя скорость (например, `10r/s` — 10 запросов в секунду).
- **`limit_req`**: Директива, применяемая в блоке `location` или `server`. Она активирует ограничение для данного контекста.
  - `burst`: Определяет, на сколько запросов клиент может превысить среднюю скорость. Эти "лишние" запросы помещаются в очередь.
  - `nodelay`: Если указан этот параметр, запросы сверх лимита, но в пределах `burst`, обрабатываются немедленно. Запросы, превышающие `burst`, сразу отклоняются с ошибкой **503 Service Temporarily Unavailable**. Без `nodelay` запросы обрабатываются с задержкой для соблюдения лимита.

**Пример конфигурации:**

```nginx
http {
    # Зона для ограничения: 10 МБ, ключ - IP клиента, скорость - 10 запросов/сек.
    limit_req_zone $binary_remote_addr zone=one:10m rate=10r/s;
}

server {
    location /api/ {
        # Разрешаем всплеск до 20 запросов.
        # Запросы сверх 10r/s, но в пределах 20, обрабатываются сразу.
        # Все, что выше burst, отклоняется с ошибкой 503.
        limit_req zone=one burst=20 nodelay;
    }
}
```

**Ограничения:** Метод неэффективен против DDoS, когда трафик распределен. Также общий лимит будет распространяться на всех пользователей за одним механизмом преобразования адресов (NAT, Network Address Translation).

### Ограничение числа одновременных соединений (`limit_conn`)

Модуль `ngx_http_limit_conn_module` позволяет ограничить количество *активных обрабатываемых соединений* для определенного ключа (например, для одного IP-адреса).

Это не ограничение общего числа соединений протокола управления передачей (TCP, Transmission Control Protocol), а именно тех, в рамках которых в данный момент сервер обрабатывает запрос (от чтения заголовков до отправки ответа).

- **`limit_conn_zone`**: Определяет зону для подсчета соединений (аналогично `limit_req_zone`).
- **`limit_conn`**: Применяет ограничение в `location`, `server` или `http`.

**Пример конфигурации:**

```nginx
http {
    # Зона для ограничения по IP-адресу
    limit_conn_zone $binary_remote_addr zone=perip:10m;
}

server {
    # Ограничиваем до 10 активных соединений на один IP
    limit_conn perip 10;

    location /downloads/ {
        # Более строгий лимит для тяжелого контента
        limit_conn perip 2;
    }
}
```

**Ключевые отличия от `limit_req`:**

- `limit_conn` считает активные соединения, а `limit_req` — частоту запросов.
- `limit_conn` доступен в контексте `stream` для проксирования протоколов TCP и протокола пользовательских датаграмм (UDP, User Datagram Protocol), что делает его полезным для защиты не-HTTP сервисов. `limit_req` работает только в `http`.

### Ограничение скорости отдачи контента (`limit_rate`)

Для экономии пропускной способности канала или предотвращения его монополизации одним клиентом можно ограничить скорость отдачи ответа.

- **`limit_rate`**: Статически задает максимальную скорость в байтах/сек.
- **Переменная `$limit_rate`**: Позволяет задавать скорость динамически.

**Пример статического ограничения:**

```nginx
location /video/ {
    # Ограничение скорости скачивания до 500 КБ/с
    limit_rate 500k;
}
```

**Пример динамического ограничения (в зависимости от User-Agent):**

```nginx
http {
    # По умолчанию ограничения нет (0)
    map $http_user_agent $limit_rate {
        default 0;
        # Для curl-подобных клиентов устанавливаем лимит 500k
        "~*curl" 500k;
    }
}

server {
    location /static/ {
        # Применяем переменную
        set $limit_rate $limit_rate;
    }
}
```

Также для видеофайлов формата медиаконтейнера MP4 существует специализированный модуль `ngx_http_mp4_module`, который с помощью директивы `mp4_limit_rate` позволяет ограничить скорость отдачи на основе битрейта файла.

### Блокировка по User-Agent

Метод позволяет отсеивать нежелательных ботов (консольные утилиты, скрипты нагрузочного тестирования) по заголовку `User-Agent`. Используется директива `map` для определения переменной и блок `if` для блокировки.

**Пример конфигурации:**

```nginx
http {
    # Определяем переменную $limit_search_bots на основе User-Agent
    map $http_user_agent $limit_search_bots {
        default 0;
        # Блокируем подозрительные шаблоны (регулярные выражения, без учёта регистра)
        "~*tester" 1;
        "~*curl$" 1;
        # Избегайте слишком широких правил (например, просто "bot"),
        # чтобы не заблокировать легитимных ботов (Googlebot, YandexBot)
    }

    server {
        location / {
            # Блокировка с кодом 421 (Misconfigured)
            if ($limit_search_bots = 1) {
                return 421;
            }
        }
    }
}
```

**Ограничения:**

- Метод неэффективен против продвинутых ботов, подделывающих заголовок.
- Требует осторожности при составлении регулярных выражений.

> **Примечание:** Блок `if` в данном случае безопасен, так как используется только для возврата кода ответа.

### Географическая блокировка по IP-адресу (GeoIP)

Метод позволяет ограничивать доступ к сайту на основе географического расположения клиента. Требует установки модуля `ngx_http_geoip_module` и базы данных географических соответствий.

**Пример конфигурации:**

```nginx
# Подключение модуля в основном контексте
load_module modules/ngx_http_geoip_module.so;

http {
    # Путь к файлу базы данных формата MaxMind (MMDB)
    geoip_country /etc/nginx/GeoLite2-Country.mmdb;

    # Создаём переменную на основе кода страны
    map $geoip_country_code $allowed_country {
        default no;          # По умолчанию доступ запрещён
        RU yes;              # Разрешаем Россию
        BY yes;              # Разрешаем Беларусь
    }

    server {
        location / {
            if ($allowed_country = no) {
                return 403;  # Forbidden
            }
        }
    }
}
```

**Коды стран:** Используются стандартные двухбуквенные коды Международной организации по стандартизации (ISO, International Organization for Standardization).

**Ограничения:**

- Базы данных не всегда точны.
- Пользователи могут использовать виртуальные частные сети (VPN, Virtual Private Network) для обхода.
- Рекомендуется использовать только как временную меру при атаке из конкретных регионов.

### Проверка браузера (Test Cookie)

Сторонний модуль `ngx_http_testcookie_module` проверяет способность клиентов обрабатывать язык программирования JavaScript (JS) и файлы cookies, что отсеивает примитивных ботов.

**Принцип работы:**

1. При первом запросе сервер выдаёт страницу с кодом на языке JS.
2. Скрипт устанавливает cookie с токеном.
3. Клиент перенаправляется на исходную страницу.
4. Боты без поддержки JS не проходят проверку.

**Пример конфигурации:**

```nginx
# Подключение модуля
load_module modules/ngx_http_testcookie_module.so;

http {
    server {
        location / {
            testcookie on;
            testcookie_name BPC;
            testcookie_secret my_unique_secret;
            testcookie_refresh_template '<html><body>Checking...<script src="/js/aes.min.js"></script></body></html>';
        }
    }
}
```

**Ограничения:**

- Неэффективен против ботов с полноценным браузерным стеком.
- Может создавать проблемы для пользователей с отключённым JS.
