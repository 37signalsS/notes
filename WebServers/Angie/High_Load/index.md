# Настройка Angie для высоких нагрузок и защиты от атак

## Определения

**Оптимизация производительности (Performance Optimization)** — комплекс мер, направленных на повышение эффективности использования серверных ресурсов (CPU, RAM, Disk I/O, Network) и сокращение времени отклика.

**Высокая нагрузка (High Load)** — состояние системы, при котором объем входящего трафика или сложность обработки запросов приближаются к пределам пропускной способности инфраструктуры. В контексте 2026 года это также включает обработку всплесков трафика (traffic spikes) без деградации сервиса.

**Защита от DoS-атак (Denial of Service)** — набор техник для обеспечения доступности сервиса при попытках злоумышленников исчерпать ресурсы системы (CPU, дескрипторы файлов, полоса пропускания).

**Пропускная способность (Throughput)** — количество запросов или объем данных, обработанных сервером за единицу времени, обычно измеряемый в RPS (Requests Per Second) или Mbps.

**Задержка (Latency)** — время обработки одного запроса, обычно измеряемое как TTFB (Time To First Byte) или полное время ответа (TTLB).

```bash
# Проверка версии Angie

# → 65535  (должен быть >= worker_connections * 2)
```

## Базовые концепции

### Особенности Angie для High Load (версии 1.12+)

Angie (форк Nginx) включает ряд уникальных возможностей, критичных для современных высоконагруженных систем:

- **Сохранение индекса кэша (Cache Index Persistence):** Возможность сохранять зону разделяемой памяти кэша на диск. Это исключает этап "разогрева" (cache loading) после перезапуска сервера, позволяя сразу обрабатывать трафик на полной скорости.
- **Интеллектуальная балансировка и сессии:**
  - **`least_time`:** Балансировка по минимальному времени ответа (теперь в Open Source версии).
  - **Sticky Learn:** Нативная поддержка сессионной привязки через обучение на идентификаторах из ответов бэкенда (например, сессионные куки).
  - **Slow Start:** Плавное наращивание нагрузки на сервер после его восстановления.
- **Кластерная синхронизация (Sync Zones):** Возможность синхронизировать состояние зон (`limit_req`, `limit_conn`, `sticky`) между несколькими узлами Angie в реальном времени, обеспечивая консистентность лимитов во всем кластере (флагманская фича Angie PRO).
- **HTTP/3 и QUIC с eBPF:** Стабильная поддержка QUIC с использованием eBPF (`quic_bpf`) для маршрутизации UDP-пакетов между процессами, что предотвращает разрывы соединений при `reload`.
- **Сжатие Zstandard (zstd):** Нативная поддержка zstd, обеспечивающая превосходную степень сжатия при низкой нагрузке на CPU.
- **Грациозное обслуживание (Server Draining):** Состояние `drain` для апстримов позволяет плавно выводить узлы из эксплуатации, дообслуживая существующие сессии.

### Архитектура процессов и память

Angie использует событийно-ориентированную многопроцессную модель:

1.  **Master-процесс:** Читает конфигурацию, управляет воркерами, выполняет привилегированные операции (bind, setuid).
2.  **Worker-процессы:** Обрабатывают соединения в неблокирующем event loop. Количество обычно равно числу ядер CPU (`worker_processes auto;`).
3.  **Разделяемая память (Shared Memory):** Используется для зон (`zone`), кэша (`proxy_cache`), состояний балансировки и метрик. Размер ограничен параметром `worker_shm_zone_size` и доступной памятью.

### Подходы к оптимизации

- **Инфраструктурная:** Тюнинг ядра ОС (TCP buffers, `somaxconn`), эффективное распределение процессов (`worker_cpu_affinity`), использование kTLS для разгрузки CPU.
- **Архитектурная:** Применение динамических апстримов, использование API для управления конфигурацией без перезагрузки и интеграция с сервис-дискавери.
- **Клиентская:** HTTP/3, адаптивное сжатие, TLS 1.3 с сессионными тикетами.

### Принципы тестирования (Benchmarking)

- **Изоляция изменений:** Тестируйте по одной настройке за раз.
- **Имитация реальности:** Используйте профили нагрузки, соответствующие реальному поведению пользователей (RPS, Latency, Concurrent Connections).
- **Инструментарий:**
  - Для RPS-тестов: `wrk`, `wrk2`, `wrkx`, `h2load`.
  - Для комплексных сценариев: `k6`, `Яндекс.Танк`.
  - Подробнее: [Инструменты для бенчмарка веб-сервера](../../webserver_benchmarking.md).

## Практические сценарии

### Оптимизация производительности

Настройка параметров Angie для максимальной пропускной способности: тюнинг сетевого стека, Keep-Alive, буферизация и кэширование. Включает использование PCRE JIT и оптимизацию TLS.

**Быстрая проверка конфигурации:**

```bash
# Проверка синтаксиса
angie -t
# → nginx: the configuration file /etc/angie/angie.conf syntax is ok

# Применение и reload
angie -s reload
# → ожидаемый вывод: [notice] ... signal process started
```

**Валидация через curl:**

```bash
# Проверка HTTP/2 и сжатия
curl -I --http2 https://example.com/
# → HTTP/2 200
# → content-encoding: br

# Проверка HTTP/3
curl -I --http3-only https://example.com/
# → HTTP/3 200
```

Подробнее: [Оптимизация производительности](./performance_optimization.md).

### Защита от DoS-атак

Методы противодействия флуду на уровнях L4/L7: ограничение частоты запросов (`limit_req`), соединений (`limit_conn`) с поддержкой кластерной синхронизации, фильтрация по GeoIP и интеллектуальное ограничение ресурсов для HTTP/2/3.

**Валидация rate limiting:**

```bash
# Отправка burst-запросов, ожидаем 429
for i in $(seq 1 30); do curl -s -o /dev/null -w "%{http_code}\n" https://example.com/api/; done
# → большинство: 200
# → часть: 429 (при превышении rate)

# Проверка заголовка Retry-After (если настроен)
curl -I https://example.com/api/ | grep -i retry-after
# → Retry-After: 2
```

Подробнее: [Защита от DoS-атак](./dos_protection.md).

### Наблюдаемость и мониторинг (Observability)

Angie 2026 предоставляет расширенные инструменты для контроля под нагрузкой:

- **Нативный OpenTelemetry (OTel):** Модуль `otel` для трассировки запросов через OTLP/gRPC, что критично для отладки задержек в микросервисах.
- **Расширенный API и Метрики:** Нативный экспорт в формате Prometheus и JSON API для мониторинга апстримов, сертификатов и состояния зон в реальном времени.
- **Активные проверки (Active Health Checks):** Проактивный мониторинг бэкендов в HTTP и Stream контекстах.
- **Интерактивная консоль:** Веб-панель (Console Light) для визуализации состояния сервера.

## Диагностика и устранение неисправностей

### Типичные симптомы и причины

| Симптом | Возможная причина | Первый шаг диагностики |
| :--- | :--- | :--- |
| Высокий p99 latency при низком RPS | Деградация бэкенда, TCP retransmit | `ss -ti` на Angie и бэкенде |
| Резкие 502/503 | Переполнение очереди бэкенда, `worker_connections` исчерпан | `error_log`, `upstream_status` в access log |
| Angie не использует все ядра CPU | `worker_cpu_affinity` не настроен, `irqbalance` конфликтует | `top -H`, `/proc/interrupts` |
| Ошибки TLS handshake | Устаревшие cipher suites, несовместимость kTLS | `openssl s_client -connect host:443` |
| Всплески latency при reload | `worker_shutdown_timeout` слишком мал, долгие соединения | `error_log` при `reload` |

### Сценарий 1: Диагностика производительности

```bash
# 1. Проверка утилизации CPU/RAM
top -b -n 1 | grep angie
# → us% (user space) должен быть высоким при CPU-bound нагрузке
# → sy% (system) > 30% указывает на накладные ядра (прерывания, системные вызовы)

# 2. Проверка очередей сокетов
ss -ltni | grep -E "Send-Q|Recv-Q"
# → Send-Q/Recv-Q близки к 0 в steady state
# → Рост Send-Q на стороне Angie = клиенты не читают данные быстро
# → Рост Recv-Q = Angie не успевает обрабатывать входящие данные

# 3. Проверка прерываний NIC
cat /proc/interrupts | grep -E "eth|rx|tx"
# → Прерывания должны равномерно распределяться по ядрам

# 4. Проверка TCP retransmit
ss -ti | grep -i retrans
# → retrans > 0 = потеря пакетов в сети или перегрузка
```

### Сценарий 2: Диагностика DoS-атаки

```bash
# 1. Анализ логов до атаки
grep -c "GET /" /var/log/angie/access.log
# → Запомнить baseline RPS

# 2. Выявление аномальных IP
awk '{print $1}' /var/log/angie/access.log | sort | uniq -c | sort -nr | head -20
# → Топ-20 IP по количеству запросов

# 3. Проверка состояния лимитов
curl http://localhost/api/v1/http/limit_reqs/
# → Статистика по зонам ограничения

# 4. Экспресс-блокировка через iptables
iptables -A INPUT -s <attacker_ip> -j DROP
# → Временная мера до настройки limit_req
```

### Сценарий 3: Проблемы с HTTP/3 и QUIC

```bash
# Проверка доступности QUIC
curl -I --http3-only https://example.com/
# → HTTP/3 200  (работает)
# → curl: (35) ...  (не работает, проверить порты и firewall)

# Проверка UDP порта
ss -u -l | grep :443
# → UNCONN 0 0 *:quic *:*

# Проверка логов QUIC ошибок
grep -i "quic" /var/log/angie/error.log
# → [crit] ... quic_bpf not supported
```

## Рекомендации и передовые практики

### Чек-лист высокой нагрузки

- [ ] `worker_processes auto;` и `worker_cpu_affinity auto;` настроены
- [ ] `worker_rlimit_nofile` >= 100000
- [ ] Включен `sendfile on;` и `tcp_nopush on;`
- [ ] Настроен `open_file_cache` для статики
- [ ] Включено сжатие `zstd on;` или `gzip on;`
- [ ] `keepalive_timeout` и `keepalive_requests` настроены под профиль трафика
- [ ] Настроены таймауты: `client_header_timeout`, `client_body_timeout`, `send_timeout`
- [ ] Для HTTPS: `ssl_conf_command Options +KTLS;` и `ssl_ciphers` без legacy
- [ ] Настроен мониторинг `status_zone` или Prometheus экспорт
- [ ] Настроены лимиты `limit_req` и `limit_conn` с `sync` для кластера
- [ ] Проведено тестирование `wrk2`/`k6` с percentile-анализом (p95, p99, p99.9)

### Рекомендации по тюнингу

1.  **PCRE JIT:** Всегда включайте `pcre_jit on;` для ускорения регулярных выражений.
2.  **Open File Cache:** `open_file_cache max=10000 inactive=60s;` — кэширование дескрипторов открытых файлов значительно снижает количество системных вызовов при раздаче статики.
3.  **Сжатие Zstd:** Используйте `zstd on;` вместо Gzip для API-ответов, это дает выигрыш до 20-30% по трафику при меньшем потреблении CPU.
4.  **Бенчмаркинг:** В 2026 году для High Load тестов рекомендуется использовать `wrk2` или `k6`, так как они корректно учитывают Coordinated Omission.

## Границы применимости и ограничения

### Ограничения Angie OSS

- **Очереди (queue) в upstream:** Доступны только в Angie PRO. В OSS при превышении `max_conns` запросы получают 502.
- **Feedback balancing:** Алгоритм `feedback` доступен только в Angie PRO.
- **Кластерная синхронизация зон:** Полная функциональность `zone_sync` требует PRO лицензии для Production использования.

### Ограничения HTTP/3

- Требует открытия UDP-порта 443 на фаэрволе.
- Некоторые корпоративные прокси и балансировщики не поддерживают QUIC.
- eBPF `quic_bpf` требует Linux 5.7+ и наличия загружаемого модуля.

### Ограничения кэширования

- Размер кэша ограничен размером раздела `/var/cache/angie/` или указанной директории.
- Поля `Cache-Control: no-cache` заставляют Angie проверять бэкенд (Bypass).
- Кэширование потокового контента (HTTP/1.1 chunked) невозможно.

## Дополнительная информация

### Автоматизация TLS и ACME

Angie поддерживает встроенный модуль ACME для автоматического получения и продления TLS-сертификатов. Это исключает простои из-за просроченных сертификатов и упрощает управление крупными фермами серверов. Дополнительно доступен API для мониторинга сроков действия сертификатов.

### Тюнинг системного уровня

- **Ядро Linux:** Настройка `sysctl` для управления сетевыми очередями и буферами. Подробнее: [sysctl](../../../Linux/Core/kernel/sysctl.md).
- **eBPF и QUIC:** Использование eBPF для оптимизации сетевого стека и обеспечения стабильности QUIC-соединений. Подробнее: [Оптимизация HTTP/3 и eBPF](./performance_optimization.md#сценарий-4-тюнинг-http3-и-ebpf).
- **KTLS (Kernel TLS):** Использование системных вызовов для ускорения шифрования данных. Подробнее: [Настройка TLS в Angie](../angie_tls_setup.md).
