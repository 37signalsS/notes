# Модуль image_filter в Angie: безопасность и защита от DoS

## Определения

**DoS-атака на image_filter** — тип атаки на отказ в обслуживании, при которой злоумышленник генерирует большое количество запросов с произвольными или экстремальными параметрами трансформации изображений для исчерпания ресурсов CPU сервера.

## Базовые концепции

### Уязвимости модуля

Модуль `image_filter` выполняет ресурсоёмкие операции (resize, crop, конвертация в WebP/AVIF) в реальном времени. Без должной защиты он становится критической точкой отказа:

- **Бесконечные вариации:** Злоумышленник может менять размеры в URL (например, `100x100`, `100x101`, `100x102`), обходя кэш и заставляя сервер генерировать новые версии для каждого запроса.
- **Экстремальные размеры:** Запросы на генерацию очень больших изображений могут мгновенно забить буфер (`image_filter_buffer`) и перегрузить CPU.
- **Атаки на буфер:** Отправка очень больших исходных изображений для переполнения памяти при обработке. В Angie поддержка AVIF требует особой осторожности, так как декомпрессия AVIF потребляет значительно больше CPU, чем JPEG.
- **Исчерпание файловых дескрипторов:** При массовой генерации новых версий может произойти резкий рост дисковых операций и количества открытых файлов.

### Основные методы защиты

1. **Валидация параметров** — ограничение набора разрешённых размеров (белые списки).
2. **Подписывание URL** — использование модуля `secure_link` для предотвращения несанкционированного изменения параметров.
3. **Rate Limiting** — ограничение частоты запросов с одного IP-адреса. См. подробнее в [защите от DoS-атак](../dos_protection.md).
4. **Эффективное кэширование** — использование [кэширования](./caching.md) для минимизации повторной обработки.
5. **Изоляция ресурсов** — вынос процесса фильтрации на отдельные инстансы (см. [производительность](./performance.md)).

## Практические сценарии

### Сценарий: Белый список размеров через map

Использование директивы `map` позволяет гибко управлять разрешёнными комбинациями размеров и возвращать ошибку для всех остальных запросов.

```nginx
# Определение разрешенных размеров в контексте http
map $arg_size $is_valid_size {
    default 0;
    "100x100" 1;
    "200x200" 1;
    "400x400" 1;
    "800x600" 1;
}

server {
    location ~* ^/img/ {
        if ($is_valid_size = 0) {
            return 400;
        }

        # Проксирование на внутренний фильтр
        proxy_pass http://127.0.0.1:8081$uri?size=$arg_size;
    }
}
```

### Сценарий: Защита от подбора параметров через secure_link

Модуль `ngx_http_secure_link_module` позволяет проверять цифровую подпись запроса, сформированную на стороне приложения. Это исключает возможность запроса произвольных размеров.

```nginx
location ~* ^/img/(.*)$ {
    secure_link $arg_md5,$arg_expires;
    secure_link_md5 "$secure_link_expires$uri secret_key";

    if ($secure_link = "") { return 403; }
    if ($secure_link = "0") { return 410; }

    proxy_pass http://127.0.0.1:8081$uri;
}
```

**Преимущества:**

- Полная невозможность подбора параметров злоумышленником.
- Возможность установки срока жизни ссылки.

### Сценарий: Жесткая валидация через регулярные выражения

Более строгий подход, блокирующий невалидные запросы на этапе сопоставления с `location`.

```nginx
# Разрешаем только конкретные размеры в URL: /img/100x100/photo.jpg
location ~* ^/img/(100|200|400)x(100|200|400)/(.*)$ {
    set $width $1;
    set $height $2;
    set $file_path $3;

    proxy_pass http://127.0.0.1:8081/vp/img/$width/$height/$file_path;
}
```

**Преимущества:**

- Высокая производительность (нет проверок `if`).
- Читаемость конфигурации.
- Отсечение «мусорных» запросов до передачи в обработку.

## Дополнительная информация

### Рекомендации по безопасности

- **Ограничение буфера:** Всегда устанавливайте `image_filter_buffer` на разумном уровне (например, 10M–20M), чтобы предотвратить атаки на переполнение памяти. Помните, что директива называется `image_filter_buffer`, а не `image_filter_buffer_size`.
- **Внутренний сервер:** Держите инстанс с директивами `image_filter` на внутреннем порту (например, `127.0.0.1:8081`), закрытом от прямого доступа извне.
- **Мониторинг:** В Angie используйте `status_zone` для отслеживания нагрузки на локации фильтрации. Резкий рост ошибок `415` или `502/504` на бэкенде фильтрации сигнализирует об атаке или некорректно настроенных лимитах.
- **Защита от SSRF:** Если Angie скачивает оригиналы с внешних ресурсов (через `proxy_pass`), убедитесь, что доступ ограничен только доверенными доменами бэкендов.
