# Модуль image_filter в Angie: обзор возможностей

## Определения

**Модуль image_filter** — высокопроизводительный динамический модуль Angie, предназначенный для трансформации изображений в режиме реального времени. Он является глубоко переработанной версией стандартного модуля Nginx, расширенной инженерами Angie для поддержки современных форматов сжатия и гибкого управления качеством.

**Адаптивная доставка изображений (Adaptive Image Delivery)** — стратегия оптимизации веб-производительности, при которой сервер автоматически выбирает и отдает наиболее эффективный формат изображения (AVIF, WebP, JPEG) в зависимости от возможностей браузера клиента, определяемых через заголовок `Accept`.

**Согласование контента (Content Negotiation)** — процесс выбора формата ответа на основе анализа заголовка `Accept` запроса. В Angie реализуется через директиву `map`, которая сопоставляет возможности клиента с суффиксом файла или параметрами конвертации.

**Двойное проксирование (Double Proxying)** — архитектурный паттерн, разделяющий логику кэширования и трансформации контента между двумя уровнями (фронтенд и внутренний прокси). Фронтенд отвечает за кэширование и защиту, внутренний сервер — за ресурсоёмкую обработку. Это гарантирует, что CPU тратится на одну картинку только один раз.

**Ключ кэша (Cache Key)** — строковое значение, формируемое из переменных запроса, по которому Angie определяет уникальность объекта в кэше. При динамической трансформации в ключ ОБЯЗАТЕЛЬНО должны входить параметры ресайза, формат и качество сжатия.

## Базовые концепции

Модуль `ngx_http_image_filter_module` является фундаментом для построения систем адаптивной доставки контента. Его использование позволяет хранить на диске только оригиналы изображений высокого качества, генерируя необходимые вариации (размеры, форматы) по запросу.

### Ключевые преимущества Angie

1.  **Поддержка форматов нового поколения:** В отличие от базового Nginx, Angie нативно поддерживает чтение и запись **AVIF**, **WebP** и **HEIC**.
2.  **Директива Convert:** Позволяет менять формат (например, JPEG → AVIF) без изменения геометрии изображения, что критично для оптимизации трафика без потери композиции.
3.  **Тонкий тюнинг кодеков:** Специализированные директивы (например, `image_filter_avif_speed`) позволяют балансировать между нагрузкой на CPU и степенью сжатия.
4.  **Прогрессивная загрузка:** Поддержка `image_filter_interlace` для JPEG, что улучшает пользовательский опыт на медленных каналах связи.
5.  **Нативная наблюдаемость:** Интеграция с `status_zone` позволяет отслеживать метрики трансформаций через API в реальном времени.

### Архитектура системы обработки

Для обеспечения стабильности под высокой нагрузкой (High Load) обязательным является использование схемы **двухуровневого проксирования**.

#### Схема динамической обработки

```
Клиент (Accept: image/avif) → [Фронтенд: Проверка кэша] 
                                ↓
                                MISS → [Внутренний прокси: Трансформация]
                                          ↓
                                          [Запрос оригинала у хранилища]
                                          ↓
                                          [Применение image_filter: Resize/Convert]
                                          ↓
                                HIT ← [Кэширование результата + Vary: Accept]
```

**Ключевые аспекты архитектуры:**
- **Изоляция:** Тяжелые операции обработки (особенно AVIF) выносятся на внутренние воркеры или отдельные инстансы, чтобы не блокировать быструю отдачу статики.
- **Управление кэшем:** Обязательная передача заголовка `Vary: Accept`, чтобы разные браузеры получали подходящие им форматы (AVIF для Chrome, JPEG для старых Safari) по одному URL.
- **Эффективность:** В `proxy_cache` сохраняется готовый результат. Оригинал запрашивается только один раз при промахе кэша (cache miss).

#### Модели развертывания

| Модель | Описание | Применение |
|:-------|:---------|:-----------|
| **Single-node** | Фронтенд и фильтр на одном инстансе | Разработка, низкая нагрузка (<100 rps) |
| **Double Proxy** | Фронтенд (кэш) + внутренний сервер (фильтр) на одном хосте | Production, средняя нагрузка (100–5000 rps) |
| **Farm** | Фронтенд + пул внутренних фильтров за балансировщиком | High Load, >5000 rps, горизонтальное масштабирование |

### Поддерживаемые форматы и trade-offs

| Формат | Сжатие | CPU (отн. JPEG) | Поддержка в libgd | Применение |
|:-------|:-------|:----------------|:------------------|:-----------|
| **AVIF** | Максимальное (30–50% лучше WebP) | 10–50x | libavif | Современные браузеры, High Load 2026 |
| **WebP** | Хорошее (2–3x лучше JPEG) | 2–3x | libwebp | Fallback для браузеров без AVIF |
| **HEIC** | Отличное для фото Apple | 5–15x | libheif | Конвертация загрузок с iOS/macOS |
| **JPEG** | Базовое | 1x (база) | встроено | Progressive JPEG, широкая совместимость |
| **PNG** | Без потерь | 1–2x | встроено | Прозрачность, графика |

### Память и вычислительная модель

Каждая трансформация требует объема RAM, равного `image_filter_buffer`, для хранения полностью раскодированного изображения в пиксельной матрице. 

**Расчет буфера:**
```
Буфер ≥ (Ширина × Высота × 4 байта RGB) × 1.3 (запас на метаданные)
```

Примеры:
- 12 МП фото (4032×3024): ~46 MB несжато → буфер 20M–30M
- 8 К видео кадр (7680×4320): ~100 MB несжато → буфер 40M–60M

При 100 параллельных запросах и буфере 20M потребуется ~2 GB оперативной памяти только под нужды модуля.

## Практические сценарии

### Выбор стратегии трансформации

| Параметр | Динамическая (image_filter) | Статическая (Pre-generated) |
|:---------|:----------------------------|:----------------------------|
| **Дисковое место** | Минимальное (только оригинал) | Высокое (копии всех размеров) |
| **Нагрузка на CPU** | Высокая (при заполнении кэша) | Минимальная (только IO) |
| **Гибкость** | Любой размер по запросу | Только фиксированный набор |
| **Latency (первый запрос)** | Зависит от формата (AVIF — долго) | Минимальная |

### Базовые операции

- **`resize`**: Масштабирование изображения с сохранением пропорций.
- **`crop`**: Обрезка краев для достижения точного соответствия заданным размерам.
- **`convert`**: Принудительная смена формата.
- **`rotate`**: Поворот на 90, 180 или 270 градусов.

### Сценарий 1: Модель развертывания «Двойное проксирование»

Архитектурно правильный паттерн для любого production-нагрузки. Внешний фронтенд кэширует и защищает запросы, внутренний сервер только трансформирует.

```nginx
# Внешний фронтенд (порт 80/443)
server {
    listen 443 ssl http2;
    server_name img.example.com;
    
    location ~* ^/resize/(?<w>\d+)x(?<h>\d+)/(?<file>.+)$ {
        add_header Vary "Accept";
        proxy_cache img_cache;
        proxy_cache_key "$host$uri$is_args$args$http_accept";
        proxy_cache_valid 200 30d;
        proxy_cache_lock on;
        proxy_cache_use_stale error timeout updating;
        
        proxy_pass http://unix:/var/run/angie_img_filter.sock:/resize/$w/$h/$file;
    }
}

# Внутренний сервер (Unix-сокет)
server {
    listen unix:/var/run/angie_img_filter.sock;
    server_name localhost;
    
    root /var/www/images/originals;
    status_zone image_filter_backend;
    
    location ~* ^/resize/(?<w>\d+)x(?<h>\d+)/(?<file>.+)$ {
        internal;
        image_filter resize $w $h;
        image_filter_buffer 20M;
        image_filter_convert avif;
        image_filter_avif_quality 65;
        image_filter_avif_speed 9;
        image_filter_sharpen 1;
        
        error_page 415 = @empty;
    }
    
    location @empty {
        empty_gif;
    }
}
```

**Валидация:**
```bash
# Проверка работы Unix-сокета
ss -xl | grep angie_img_filter
# → LISTEN 0 128 /var/run/angie_img_filter.sock

# Проверка кэша
curl -I https://img.example.com/resize/400x300/photo.jpg
# → X-Cache-Status: MISS (первый запрос), затем HIT
```

### Сценарий 2: Наблюдаемость и алертинг через API Angie

Включение `status_zone` позволяет отслеживать эффективность работы в реальном времени. Для High Load критично настроить дашборд и алерты до попадания в production.

```nginx
# Внутренний сервер (трансформация)
server {
    listen unix:/var/run/angie_img_filter.sock;
    server_name localhost;
    status_zone image_filter_backend;
    
    # ... конфигурация фильтрации ...
}

# Фронтенд с API
server {
    listen 127.0.0.1:8080;
    server_name localhost;
    
    location /status {
        api /status/;
        allow 127.0.0.1;
        deny all;
    }
    
    location /p8s {
        prometheus;
    }
}
```

**Метрики для мониторинга:**
- **`responses.time`**: Среднее время ответа внутреннего фильтра. Используется для тюнинга `image_filter_avif_speed`.
- **`responses.codes.415`**: Частота ошибок из-за нехватки `image_filter_buffer`.
- **`requests.current`**: Количество параллельно обрабатываемых изображений.
- **`bandwidth`**: Объем отданного контента. Резкий рост может указывать на отравление кэша.

**Валидация:**
```bash
# Проверка статуса зоны
curl -s http://127.0.0.1:8080/api/6/http/status_zones/image_filter_backend | jq .

# Проверка Prometheus-метрик
curl -s http://127.0.0.1:8080/p8s | grep -E "angie_zone|image_filter"
```

### Сценарий 3: Планирование мощности (Capacity Planning)

Расчет параметров для горизонтального масштабирования.

**Формула:**
```
Пиковое количество параллельных трансформаций = (PPS × p_avif × t_avif) + (PPS × p_webp × t_webp)
```

Где:
- `PPS` — пиковое количество запросов в секунду
- `p_avif/p_webp` — доля запросов на соответствующий формат
- `t_avif/t_webp` — среднее время обработки одного запроса в секундах

**Пример расчета:**
- 1000 rps пик, 60% AVIF (180 мс), 30% WebP (40 мс), 10% кэш HIT
- Параллельные AVIF: 1000 × 0.6 × 0.18 = 108 воркеров
- Параллельные WebP: 1000 × 0.3 × 0.04 = 12 воркеров
- Итого: ~120 параллельных трансформаций

При `image_filter_buffer 20M` требуется ~2.4 GB RAM только для модуля. Добавьте 30% запас на ОС и другие процессы.

**Валидация:**
```bash
# Проверка утилизации CPU под нагрузкой
mpstat -P ALL 1 10 | grep -E "Average|CPU"

# Проверка утечек памяти
ps aux | grep angie | awk '{print $6}' | sort -n
```

### Сценарий 4: Аварийный режим (Graceful Degradation)

При перегрузке или отказе модуля image_filter система должна продолжать отдавать изображения, пусть и в менее оптимальном формате.

```nginx
# Фронтенд с fallback
server {
    listen 443 ssl http2;
    server_name img.example.com;
    
    location ~* ^/img/(?<w>\d+)x(?<h>\d+)/(?<file>.+)$ {
        proxy_cache img_cache;
        proxy_cache_key "$host$uri$is_args$args$http_accept";
        proxy_cache_valid 200 30d;
        
        proxy_intercept_errors on;
        error_page 502 503 504 = /fallback;
        
        proxy_pass http://internal_filter;
    }
    
    # Fallback: отдача оригинала без трансформации
    location /fallback {
        internal;
        root /var/www/images/originals;
        expires 7d;
    }
}
```

**Валидация:**
```bash
# Имитация отказа внутреннего сервера
systemctl stop angie@filter

# Проверка fallback
curl -I https://img.example.com/800x600/photo.jpg
# → HTTP/2 200 (оригинал, без AVIF)
```

## Устранение неисправностей (Troubleshooting)

| Симптом | Причина | Диагностика | Решение |
|:---|:---|:---|:---|
| `415 Unsupported Media Type` | Оригинал больше `image_filter_buffer` | `error_log`, код 415 в access log | Увеличить `image_filter_buffer` до 20M |
| 502 при проксировании к внутреннему фильтру | Внутренний сервер не слушает фильтруемый endpoint | `ss -xl \| grep sock` | Проверить `listen ... sock` и `proxy_pass` |
| Ошибки формата (WebP/AVIF не работают) | libgd без поддержки формата | Трансформация в JPEG, WebP не выдаётся | Обновить `libgd` или пересобрать модуль |

## Лучшие практики

1.  **Буфер 20M+** — вместе с ростом разрешения камер обязательное значение `image_filter_buffer` в 2026 году; иначе массовые `415`.
2.  **Валидация размеров** — не позволяйте произвольные комбинации размеров в URL; используйте regex-ограничения, иначе CPU DoS. Подробнее в [security.md](./security.md).
3.  **Схема «внешний кэш + внутренний фильтр»** — трансформации выполняются один раз, результат кэшируется на фронтенде. См. [caching.md](./caching.md).
4.  **Включайте `status_zone`** на фронтенд-сервере для слежения за `Cache Hit Ratio` и временем фильтрации.

## Дополнительная информация

### Установка и подключение

Модуль поставляется в виде динамической библиотеки и подключается в основном контексте `angie.conf`. Подробности в [Установка и настройка](./installation.md).

```nginx
load_module modules/ngx_http_image_filter_module.so;
```

### Технические ограничения и особенности

1.  **Буферизация (`image_filter_buffer`):** По умолчанию лимит составляет 1 MB. Для современных фотографий высокого разрешения этот параметр необходимо увеличивать до 10–20 MB, иначе сервер вернет ошибку `415 Unsupported Media Type`.
2.  **Зависимость от libgd:** Поддержка форматов (WebP, AVIF, HEIC) зависит от версии системной библиотеки `libgd`. Перед использованием проверьте поддержку через `angie -V`.
3.  **Безопасность:** Параметры трансформации в URL должны валидироваться. Прямой проброс размеров без ограничений позволяет злоумышленникам вызвать CPU DoS.
4.  **Ресурсоемкость AVIF:** Кодирование AVIF требует в 10–50 раз больше ресурсов CPU, чем JPEG. Используйте `image_filter_avif_speed` со значением `8–10` для баланса производительности.
5.  **Однопоточность воркера:** Один запрос обрабатывается одним воркером в один поток. Для параллельной обработки множества запросов требуется адекватное количество `worker_processes`, соответствующее числу ядер CPU.

### Типовой инцидент и реагирование (Runbook)

**Симптом:** Рост latency внутреннего фильтра выше 500 мс (P95) или ошибки 415.

**Диагностика:**
```bash
# 1. Проверка состояния воркеров
systemctl status angie
ps aux | grep angie | wc -l

# 2. Проверка кэша
curl -s http://127.0.0.1:8080/api/6/http/caches/img_cache | jq '.bytes | .total, .free'

# 3. Проверка ошибок 415
curl -s http://127.0.0.1:8080/api/6/http/status_zones/image_filter_backend | jq '.responses.codes."415"'
```

**Решение:**
1. Увеличить `image_filter_buffer` до 20M–30M.
2. Проверить размеры оригиналов в хранилище (`find /var/www/images -size +10M`).
3. При росте числа 415 — рассмотреть добавление CDN для offload.
4. При росте latency AVIF — уменьшить `image_filter_avif_quality` или увеличить `image_filter_avif_speed`.

### Очистка и откат изменений

Для отключения динамической трансформации без остановки сервиса:
1. Замените блоки с `image_filter` на статический `root` и `try_files`.
2. Очистите кэш результатов трансформации через `proxy_cache_purge` или удалите директорию кэша.
3. Убедитесь, что фронтенд корректно отдает статические файлы.
