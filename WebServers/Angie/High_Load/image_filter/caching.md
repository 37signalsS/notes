# Модуль image_filter в Angie: стратегии кэширования

## Определения

**Proxy Cache (Прокси-кэш)** — механизм временного хранения обработанного контента на диске. В Angie он дополнен функциями сохранения индекса, что критично для высоконагруженных систем с большим объемом данных.

**Cache Index Persistence (Сохранение индекса)** — уникальная функциональность Angie (директива `file=` в `proxy_cache_path`), позволяющая дампить метаданные зон разделяемой памяти на диск при выключении и мгновенно загружать их при старте. Это полностью устраняет фазу сканирования диска (cache loading) после перезапуска.

**Double Proxying (Двойное проксирование)** — архитектурный паттерн, разделяющий логику кэширования и трансформации контента между двумя уровнями (фронтенд и внутренний прокси) для обеспечения корректного сохранения результатов обработки.

**Cache Key (Ключ кэша)** — строковое значение, формируемое из переменных запроса, по которому Nginx/Angie определяет уникальность объекта в кэше. При динамической трансформации изображений в ключ ОБЯЗАТЕЛЬНО должны входить параметры ресайза, формат и, при необходимости, качество сжатия.

**Cache Stampede (Эффект «стада бизонов»)** — одновременный наплыв множества запросов на один и тот же MISS-объект, что создает пиковую нагрузку на бэкенд. Для предотвращения используется `proxy_cache_lock`.

**Cache Pollution (Отравление кэша)** — попадание в кэш неверного варианта контента из-за некорректного ключа. Например, отдача AVIF-версии браузеру, который поддерживает только JPEG, если ключ не учитывает `Accept`.

**Stale (Устаревший контент)** — объект, TTL которого истек, но который продолжает отдаваться клиентам при недоступности бэкенда или в процессе фонового обновления (`proxy_cache_use_stale`).

**Bypass (Обход кэша)** — принудительная передача запроса на бэкенд без обращения к кэшу, контролируется директивой `proxy_cache_bypass`.

## Предварительные требования

Перед настройкой кэширования убедитесь, что выполнен следующий минимальный набор условий:

1.  **Версия Angie:** >= 1.11.0 для нативной поддержки AVIF/WebP/HEIC; >= 1.12.0 для нативного `proxy_cache_purge`.
2.  **Библиотека libgd:** Поддержка нужных форматов проверяется командой:
    ```bash
    # Проверка поддерживаемых форматов через отладочный вывод
    angie -V 2>&1 | grep -o 'gd-\S*' | sort -u
    ```
3.  **Права на запись:** Пользователь, от которого работает Angie (обычно `angie` или `www-data`), должен иметь права на запись в директории кэша и индексного файла:
    ```bash
    mkdir -p /var/cache/angie/images /var/lib/angie
    chown -R angie:angie /var/cache/angie /var/lib/angie
    ```
4.  **Дисковое пространство:** Рассчитайте объем исходя из предполагаемого количества уникальных трансформаций (см. раздел «Расчет памяти» ниже).

## Базовые концепции

### Жизненный цикл объекта в кэше image_filter

```
1. Клиент → Frontend (MISS)
2. Frontend → Backend (image_filter: Resize/Convert)
3. Backend → Storage (запрос оригинала)
4. Storage → Backend (оригинал)
5. Backend → Frontend (трансформированный результат)
6. Frontend → Disk (запись в кэш)
7. Frontend → Client (отдача результата)

Последующие запросы с тем же ключом обслуживаются из кэша (HIT) без участия image_filter.
```

### Архитектурный подход: Двойное проксирование

Использование `image_filter` и `proxy_cache` в одном `location` является антипаттерном, так как Nginx/Angie кэшируют ответ *до* его модификации фильтром. Для кэширования именно **результата обработки** (например, уже сжатого AVIF) необходимо использовать двухслойную схему.

1.  **Внешний уровень (Frontend/Cache):**
    *   Принимает запрос от клиента.
    *   Формирует ключ кэша (включая параметры ресайза и формат).
    *   При `MISS` проксирует запрос на внутренний уровень.
    *   Кэширует полученный от внутреннего уровня **уже трансформированный** результат.
2.  **Внутренний уровень (Backend/Transform):**
    *   Запрашивает оригинал из хранилища (локальный диск, S3 через proxy_pass).
    *   Применяет `image_filter`.
    *   Отдает результат фронтенду.

**Варианты соединения между слоями:**
- **TCP (127.0.0.1:8081):** Просто в развертывании, но создает дополнительную нагрузку на loopback-интерфейс и требует управления портом.
- **Unix-сокет (`/run/angie/filter.sock`):** Более производительный вариант для High Load, исключает TCP-стек и позволяет использовать файловые права для контроля доступа.

### Золотые сигналы кэширования в 2026 году

*   **Hit Ratio:** Процент запросов, обслуженных из кэша. Для изображений целевое значение > 95%.
*   **Cold Start Latency:** Время, за которое сервер становится готов отдавать кэш после перезагрузки. Благодаря Persistence в Angie стремится к нулю.
*   **Bypass Rate:** Количество запросов, прошедших мимо кэша (например, из-за заголовков `No-Cache`).
*   **Purge Efficiency:** Скорость очистки устаревшего контента через API.

### Конструкция ключа кэша

При работе с `image_filter` ключ должен включать все параметры, влияющие на выходное изображение:

```nginx
# Минимально корректный ключ для адаптивной доставки
proxy_cache_key "$scheme$request_method$host$uri$is_args$args$http_accept";
```

**Обязательные компоненты ключа:**
- `$scheme$request_method$host` — базовая часть для различения хостов и методов.
- `$uri` — путь к изображению.
- `$http_accept` — формат (AVIF/WebP/JPEG), определяемый через `map`.

**Опасности неполного ключа:**
- Без `$http_accept` в ключе первый запрос от AVIF-совместимого браузера заполнит кэш, и все последующие клиенты (включая Safari без AVIF) получат неправильный формат. Это **Cache Pollution**.
- Без `$is_args$args` запросы с разными параметрами `w`/`h` будут кэшироваться под одним ключом.

### Структура директории кэша

Директива `levels` определяет схему вложенности папок для хранения файлов кэша. При наличии миллионов объектов неправильная конфигурация приводит к замедлению файловой системы:

```nginx
proxy_cache_path /var/cache/angie/images
                 levels=1:2
                 ...
```

- **`levels=1:2`**: Создает структуру `/X/YY/`, где `X` — однобуквенная папка, `YY` — двухбуквенная. Подходит для кэшей до ~10 млн объектов.
- **`levels=1:2:2`**: Для экстремально больших кэшей (>50 млн объектов), распределяет нагрузку по большему числу директорий.
- **`use_temp_path=off`:** Запрещает запись временных файлов в отдельный каталог, экономя I/O и место на диске.

### Синхронизация TTL и оригинала

При изменении исходного изображения старые кэшированные варианты становятся неактуальными. Существует два подхода:

1.  **Версионность URL:** При изменении оригинала меняется его URL (`photo.jpg?v=2`), что создает новый ключ кэша. Самый надежный метод.
2.  **Cache Purge:** Принудительная инвалидация через `proxy_cache_purge`. Подходит для случаев, когда URL изменить нельзя.

## Практические сценарии

### Сценарий 1: Настройка кэша с Persistence

Для кэшей объемом > 100 ГБ параметр `file=` является обязательным для предотвращения I/O-шторма при старте.

```nginx
http {
    # Определение зоны с сохранением индекса
    # keys_zone=img_cache:256m — 256 МБ RAM вмещают ~2 млн ключей
    # file=/var/lib/angie/img_cache.zone — путь к дампу индекса
    proxy_cache_path /var/cache/angie/images 
                     levels=1:2 
                     keys_zone=img_cache:256m:file=/var/lib/angie/img_cache.zone 
                     max_size=50g 
                     inactive=72h 
                     use_temp_path=off;
}
```

**Валидация:**
```bash
# После перезапуска Angie проверьте загрузку индекса
curl -s http://127.0.0.1:8080/api/6/http/caches/img_cache | jq .
# В выводе должны отсутствовать ошибки cache loader; hit_ratio уже не равен 0 при наличии warmed-кэша.
```

### Сценарий 2: Реализация паттерна «Двойное проксирование» через Unix-сокет

Сценарий с адаптивной отдачей форматов (Content Negotiation) и кэшированием результата. Использование Unix-сокета повышает производительность по сравнению с TCP loopback за счет исключения сетевого стека.

```nginx
# Внешний уровень (Фронтенд с кэшем)
server {
    listen 443 ssl http2;
    server_name images.example.com;

    location ~* ^/resize/(?<width>\d+)/(?<image>.+)$ {
        proxy_cache img_cache;
        # Ключ включает формат (Accept) и параметры ресайза
        proxy_cache_key "$scheme$request_method$host$width$image$http_accept";
        proxy_cache_valid 200 30d;
        
        # Защита от "стада бизонов"
        proxy_cache_lock on;
        proxy_cache_lock_age 10s;
        proxy_cache_lock_timeout 5s;
        
        # Фоновое обновление: отдать старый кэш, пока фильтр генерирует новый
        proxy_cache_use_stale error timeout updating;
        proxy_cache_background_update on;
        
        add_header X-Cache-Status $upstream_cache_status;
        add_header Vary "Accept"; # Критично для CDN и промежуточных прокси

        # Unix-сокет вместо TCP для максимальной производительности
        proxy_pass http://unix:/run/angie/filter.sock;
    }
}

# Внутренний уровень (Трансформация)
server {
    listen unix:/run/angie/filter.sock;

    location ~* ^/resize/(?<width>\d+)/(?<image>.+)$ {
        # Запрос оригинала из локального хранилища или S3
        proxy_pass http://storage_backend/$image;
        
        image_filter_buffer 20M;
        image_filter resize $width -;
        image_filter_avif_quality 65;
        image_filter_avif_speed 9;
        
        # Конвертация на основе заголовка от фронтенда (логика выбора формата)
        image_filter convert avif; 
    }
}
```

**Валидация:**
```bash
# Проверка кэширования первого запроса (MISS)
curl -sI "https://images.example.com/resize/400/photo.jpg" \
  -H "Accept: image/avif" | grep -i "x-cache-status"
# → X-Cache-Status: MISS

# Проверка повторного запроса (HIT)
curl -sI "https://images.example.com/resize/400/photo.jpg" \
  -H "Accept: image/avif" | grep -i "x-cache-status"
# → X-Cache-Status: HIT

# Проверка работы фильтра
identify /var/cache/angie/images/*/photo.jpg*
# Должен отдавать AVIF-файл с размером 400px
```

### Сценарий 3: Очистка кэша через API (Purge)

В Angie 1.12+ очистка кэша интегрирована в основную локацию.

```nginx
server {
    listen 127.0.0.1:8081;

    location / {
        proxy_cache img_cache;
        # Разрешаем метод PURGE только из доверенной сети
        proxy_cache_purge PURGE from 127.0.0.1 10.0.0.0/8;
        
        proxy_pass http://storage_backend;
    }
}
```

**Валидация:**
```bash
# Проверка наличия файла в кэше до очистки
ls -lh /var/cache/angie/images/*/photo.jpg*

# Очистка конкретного объекта
curl -X PURGE https://images.example.com/photo.jpg

# Проверка удаления
ls -lh /var/cache/angie/images/*/photo.jpg*
# → ls: No such file or directory
```

### Сценарий 4: Наблюдаемость через API и Prometheus

Мониторинг состояния кэша в реальном времени.

```nginx
server {
    listen 127.0.0.1:8080;

    location /status {
        api /status/;
        allow 127.0.0.1;
        deny all;
    }

    location /p8s {
        prometheus; # Нативный экспорт метрик кэша
    }
}
```

**Валидация:**
```bash
# Проверка статуса кэш-зоны
curl -s http://127.0.0.1:8080/api/6/http/caches/img_cache | jq .

# Проверка Prometheus-метрик
curl -s http://127.0.0.1:8080/p8s | grep -E "img_cache|cache"
```

### Сценарий 5: Ограничение размера кэша и политика удаления (LRU)

Конфигурация для сред с ограниченным дисковым пространством.

```nginx
http {
    proxy_cache_path /var/cache/angie/images 
                     levels=1:2 
                     keys_zone=img_cache:128m:file=/var/lib/angie/img_cache.zone 
                     max_size=20g 
                     inactive=168h 
                     use_temp_path=off
                     manager_files=1000
                     manager_threshold=10m
                     manager_sleep=50ms
                     loader_files=1000
                     loader_sleep=50ms
                     loader_threshold=10m;
}
```

**Пояснение параметров:**
- **`manager_files=1000`:** Количество файлов, проверяемых за одну итерацию процесса `cache manager`.
- **`manager_sleep=50ms`:** Задержка между итерациями. Уменьшение ускоряет реакцию на заполнение кэша, но увеличивает нагрузку на CPU.
- **`loader_files=1000` / `loader_sleep=50ms`:** Аналогичные параметры для процесса `cache loader` при старте.

**Валидация:**
```bash
# Мониторинг заполнения кэша
df -h /var/cache/angie/images

# Проверка, что cache manager активен
ps aux | grep "cache manager"

# Принудительная инвалидация неактуальных данных
find /var/cache/angie/images -type f -atime +7 -delete
```

## Устранение неисправностей (Troubleshooting)

| Симптом | Причина | Диагностика | Решение |
|:---|:---|:---|:---|
| Кэш не растет (всегда MISS) | `proxy_cache_methods` не включает запрашиваемый метод или TTL = 0 | `df -h` кэша + X-Cache-Status | Проверить `proxy_cache_methods`, `proxy_cache_valid` |
| Частые `MISS` при активном трафике | `keys_zone` мал / `inactive` слишком мал | `curl /status/http/caches/` | Увеличить `keys_zone` или `inactive` |
| Диск кэша переполнен | `max_size` не задан | `df -h` | Задать `max_size` в `proxy_cache_path` |
| Старые копии отдаются после изменения оригинала | `proxy_cache_use_stale` без `updating`? Отсутствие инвалидации | Логи и X-Cache-Status | Настроить purge/`proxy_cache_use_stale` или TTL |

## Лучшие практики

1.  **`proxy_cache_use_stale error timeout updating;`** — отдавайте старую копию, пока внутренний фильтр генерирует новую; это радикально снижает время ответа.
2.  **Включайте `$http_accept` в `proxy_cache_key`** для адаптивной раздачи форматов — иначе «отравите» кэш (AVIF-файл уйдёт клиенту без поддержки).
3.  **`manager_files` / `manager_sleep`** — настраивайте нагрузку cache manager под размер зоны (примеры в Доп. информации).
4.  **Не ставьте кэш и оригиналы на один диск** — рост кэша не должен влиять на хранение оригиналов.
5.  **Мониторьте Hit Ratio** через `/status/http/caches/` — падение HIT при стабильном трафике сигналит о проблеме с зоной.

## Дополнительная информация

### Расчет памяти под keys_zone

Формула приблизительного расчета:
```
Размер зоны (МБ) = (Количество уникальных ключей × 64 байта) / 1024 / 1024
```

**Примеры:**
- 500 000 ключей → ~30 MB
- 2 000 000 ключей → ~120 MB
- 10 000 000 ключей → ~600 MB

При выборе размера учитывайте, что зона хранится в разделяемой памяти и доступна всем воркерам. Переполнение RAM не происходит — старые записи вытесняются по LRU, но это ведет к увеличению количества MISS.

### Рекомендации по оптимизации

1.  **`proxy_cache_min_uses 2`**: Предотвращает кэширование изображений, запрашиваемых один раз (например, поисковыми ботами), экономя место на диске.
2.  **`proxy_cache_revalidate on`**: Использует GET запросы с `If-Modified-Since` при обновлении истекшего кэша, экономя трафик между слоями.
3.  **Размещение индекса:** Файл индекса (`.zone`) рекомендуется размещать на максимально быстрых носителях (NVMe/Tmpfs) для ускорения процесса Persistence.
4.  **Unix-сокеты для внутреннего проксирования:** Исключают TCP-overhead и позволяют упростить контроль доступа через файловые права (`chmod 660 /run/angie/filter.sock`).
5.  **Файловая система:** XFS или ext4 с отключенным `atime` (`noatime,nodiratime`) обеспечивают наилучшую производительность при миллионах мелких файлов. Btrfs подходит, но требует осторожности с квотами и снапшотами.
6.  **`proxy_cache_background_update on`:** Обновляет кэш в фоновом режиме после истечения TTL, не заставляя клиента ждать ответа от бэкенда. Особенно эффективно для AVIF-превью с большим `image_filter_avif_speed`.

### Мониторинг и пороговые значения

| Метрика | Целевое значение | Критическое значение | Действие |
|:--------|:-----------------|:---------------------|:---------|
| Hit Ratio | > 95% | < 85% | Проверить ключ кэша и параметры `inactive` |
| Bypass Rate | < 1% | > 5% | Проверить заголовки `No-Cache` и `proxy_cache_bypass` |
| Stale Ratio | < 5% | > 20% | Проверить доступность бэкенда и `proxy_cache_use_stale` |
| MISS Latency (P95) | < 500 мс | > 2000 мс | Проверить производительность image_filter и I/O хранилища |
| Cache Disk Usage | < 80% | > 90% | Расширить кэш или уменьшить `max_size` |
| Cache Loader Errors | 0 | > 0 | Проверить целостность индекса и права доступа |

### Ограничения

- **Размер индекса:** Зона 100 МБ в RAM позволяет хранить информацию о ~800 000 объектах. При превышении этого лимита Angie начнет удалять старые записи (LRU).
- **Disk I/O:** Даже при наличии кэша, чтение миллионов мелких файлов создает нагрузку. Рекомендуется использовать файловые системы с поддержкой эффективной работы с метаданными (XFS/Btrfs).
- **Фragmentation:** При интенсивной записи и удалении файлы кэша фрагментируются. Периодическая дефрагментация (для ext4) или использование XFS (менее чувствителен к фрагментации) снижает падение производительности.
- **Ограничение PURGE:** Встроенный `proxy_cache_purge` поддерживает только точное совпадение ключа. Для массовой инвалидации используйте каскадный PURGE или удаление по паттерну через `find` + `proxy_cache_path` пересоздание.

### Таблица типичных проблем и решений

| Проблема | Симптом | Причина | Решение |
|:---------|:--------|:--------|:--------|
| Отравление кэша | AVIF отдается Safari | Отсутствует `$http_accept` в ключе | Добавить `Accept` в `proxy_cache_key` |
| Низкий Hit Ratio | >50% MISS | Слишком короткий `inactive` или некорректный ключ | Проверить ключ, увеличить `inactive` |
| Долгий холодный старт | Angie долго запускается | Отсутствует `file=` в `proxy_cache_path` | Добавить Persistence |
| I/O-шторм при старте | Высокая нагрузка на диск | Сканирование диска cache loader | Использовать `file=` и `loader_files` |
| Ошибка 415 | `Unsupported Media Type` | Нехватка `image_filter_buffer` | Увеличить `image_filter_buffer` до 15–20 MB |
| Фрагментация кэша | Снижение скорости HIT | Множество удалений/записей | Переместить кэш на XFS, выполнить дефрагментацию |
| Утечка памяти | RSS Angie растет | Слишком большая `keys_zone` без Persistence | Настроить Persistence или уменьшить зону |

### Инструкция по очистке и откату

#### Очистка всего кэша
```bash
# Остановка Angie (опционально, для полной очистки)
systemctl stop angie

# Удаление файлов кэша
rm -rf /var/cache/angie/images/*

# Очистка индекса (если требуется полный сброс)
rm -f /var/lib/angie/img_cache.zone

# Запуск Angie
systemctl start angie
```

#### Выборочная очистка (Purge)
```bash
# Очистка конкретного изображения
curl -X PURGE https://images.example.com/resize/400/photo.jpg

# Массовая очистка по маске (без встроенного wildcard PURGE)
find /var/cache/angie/images -name "photo.jpg*" -delete
```

#### Откат конфигурации
```bash
# Перед изменением конфигурации создайте бэкап
cp /etc/angie/conf.d/image_filter.conf /etc/angie/conf.d/image_filter.conf.bak

# Если новая конфигурация вызывает проблемы, верните бэкап
cp /etc/angie/conf.d/image_filter.conf.bak /etc/angie/conf.d/image_filter.conf
angie -t && systemctl reload angie
```
