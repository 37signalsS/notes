# Модуль image_filter в Angie: стратегии кэширования

## Определения

**Proxy Cache (Прокси-кэш)** — механизм временного хранения обработанного контента на диске. В Angie он дополнен функциями сохранения индекса, что критично для высоконагруженных систем с большим объемом данных.

**Cache Index Persistence (Сохранение индекса)** — уникальная функциональность Angie (директива `file=` в `proxy_cache_path`), позволяющая дампить метаданные зон разделяемой памяти на диск при выключении и мгновенно загружать их при старте. Это полностью устраняет фазу сканирования диска (cache loading) после перезапуска.

**Double Proxying (Двойное проксирование)** — архитектурный паттерн, разделяющий логику кэширования и трансформации контента между двумя уровнями (фронтенд и внутренний прокси) для обеспечения корректного сохранения результатов обработки.

---

## Базовые концепции

Трансформация изображений (resize, convert, sharpen) — это ресурсоемкая операция, сильно нагружающая CPU. Без эффективного кэширования сервер быстро исчерпает ресурсы при росте трафика.

### Архитектурный подход: Двойное проксирование

Использование `image_filter` и `proxy_cache` в одном `location` является антипаттерном, так как Nginx/Angie кэшируют ответ *до* его модификации фильтром. Для кэширования именно **результата обработки** (например, уже сжатого AVIF) необходимо использовать двухслойную схему.

1.  **Внешний уровень (Frontend/Cache):**
    *   Принимает запрос от клиента.
    *   Формирует ключ кэша (включая параметры ресайза и формат).
    *   При `MISS` проксирует запрос на внутренний уровень.
    *   Кэширует полученный от внутреннего уровня **уже трансформированный** результат.
2.  **Внутренний уровень (Backend/Transform):**
    *   Запрашивает оригинал из хранилища (S3, локальный диск).
    *   Применяет `image_filter`.
    *   Отдает результат фронтенду.

### Золотые сигналы кэширования в 2026 году

*   **Hit Ratio:** Процент запросов, обслуженных из кэша. Для изображений целевое значение > 95%.
*   **Cold Start Latency:** Время, за которое сервер становится готов отдавать кэш после перезагрузки. Благодаря Persistence в Angie стремится к нулю.
*   **Bypass Rate:** Количество запросов, прошедших мимо кэша (например, из-за заголовков `No-Cache`).
*   **Purge Efficiency:** Скорость очистки устаревшего контента через API.

## Практические сценарии

### Сценарий 1: Настройка кэша с Persistence

Для кэшей объемом > 100 ГБ параметр `file=` является обязательным для предотвращения I/O-шторма при старте.

```nginx
http {
    # Определение зоны с сохранением индекса
    # keys_zone=img_cache:256m — 256 МБ RAM вмещают ~2 млн ключей
    # file=/var/lib/angie/img_cache.zone — путь к дампу индекса
    proxy_cache_path /var/cache/angie/images 
                     levels=1:2 
                     keys_zone=img_cache:256m:file=/var/lib/angie/img_cache.zone 
                     max_size=50g 
                     inactive=72h 
                     use_temp_path=off;
}
```

### Сценарий 2: Реализация паттерна «Двойное проксирование»

Сценарий с адаптивной отдачей форматов (Content Negotiation) и кэшированием результата.

```nginx
# Внешний уровень (Фронтенд с кэшем)
server {
    listen 443 ssl http2;
    server_name images.example.com;

    location ~* ^/resize/(?<width>\d+)/(?<image>.+)$ {
        proxy_cache img_cache;
        # Ключ включает формат (Accept) и параметры ресайза
        proxy_cache_key "$scheme$request_method$host$width$image$http_accept";
        proxy_cache_valid 200 30d;
        
        # Защита от "стада бизонов"
        proxy_cache_lock on; 
        proxy_cache_use_stale error timeout updating;
        
        add_header X-Cache-Status $upstream_cache_status;
        add_header Vary "Accept"; # Критично для CDN

        proxy_pass http://127.0.0.1:8081;
    }
}

# Внутренний уровень (Трансформация)
server {
    listen 127.0.0.1:8081;

    location ~* ^/resize/(?<width>\d+)/(?<image>.+)$ {
        # Запрос оригинала из S3 или локального хранилища
        proxy_pass http://s3_backend/$image;
        
        image_filter_buffer 20M;
        image_filter resize $width -;
        image_filter_avif_quality 65;
        image_filter_avif_speed 9;
        
        # Конвертация на основе заголовка от фронтенда (логика выбора формата)
        image_filter convert avif; 
    }
}
```

### Сценарий 3: Очистка кэша через API (Purge)

В Angie 1.12+ очистка кэша интегрирована в основную локацию.

```nginx
location / {
    proxy_cache img_cache;
    # Разрешаем метод PURGE только из доверенной сети
    proxy_cache_purge PURGE from 127.0.0.1 10.0.0.0/8;
    
    proxy_pass http://internal_transform_server;
}
```
*Запрос на очистку:* `curl -X PURGE https://images.example.com/resize/300/photo.jpg`

### Сценарий 4: Наблюдаемость через API и Prometheus

Мониторинг состояния кэша в реальном времени.

```nginx
server {
    listen 127.0.0.1:8080;

    location /status {
        api /status/;
        allow 127.0.0.1;
        deny all;
    }

    location /p8s {
        prometheus; # Нативный экспорт метрик кэша
    }
}
```
*Метрики кэша доступны через API:* `GET /status/http/caches/img_cache`

## Дополнительная информация

### Рекомендации по оптимизации

1.  **`proxy_cache_min_uses 2`**: Предотвращает кэширование изображений, запрашиваемых один раз (например, поисковыми ботами), экономя место на диске.
2.  **`proxy_cache_revalidate on`**: Использует GET запросы с `If-Modified-Since` при обновлении истекшего кэша, экономя трафик между слоями.
3.  **Размещение индекса:** Файл индекса (`.zone`) рекомендуется размещать на максимально быстрых носителях (NVMe/Tmpfs) для ускорения процесса Persistence.

### Ограничения

- **Размер индекса:** Зона 100 МБ в RAM позволяет хранить информацию о ~800 000 объектах. При превышении этого лимита Angie начнет удалять старые записи (LRU).
- **Disk I/O:** Даже при наличии кэша, чтение миллионов мелких файлов создает нагрузку. Рекомендуется использовать файловые системы с поддержкой эффективной работы с метаданными (XFS/Btrfs).
