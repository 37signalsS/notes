# Модуль image_filter в Angie: изменение размеров и трансформация

## Определения

**Resize (Изменение размера)** — операция пропорционального масштабирования изображения для его вписывания в заданные границы. В Angie позволяет динамически подстраивать изображения под различные разрешения устройств.

**Crop (Обрезка)** — операция масштабирования изображения до заполнения целевых размеров с последующим отсечением лишних краев. Используется для создания миниатюр с фиксированным соотношением сторон.

**Convert (Конвертация)** — уникальная функциональность Angie (директива `image_filter convert`), позволяющая «на лету» изменять формат изображения. Поддерживает преобразование в современные форматы (WebP, AVIF) и работу с проприетарными форматами Apple (HEIC).

**Sharpen (Резкость)** — фильтр постобработки, компенсирующий размытие, возникающее при программном уменьшении разрешения.

**Interlace (Прогрессивная загрузка)** — режим кодирования JPEG, при котором изображение отображается постепенно, снизу вверх, по мере загрузки. Реализуется через директиву `image_filter_interlace on`. В отличие от baseline JPEG, прогрессивный формат улучшает субъективное восприятие скорости загрузки на медленных каналах.

**Buffer (Буфер декомпрессии)** — объем оперативной памяти, выделяемый на один запрос для хранения полностью раскодированного изображения перед применением фильтров. Управляется директивой `image_filter_buffer` (по умолчанию 1M). При превышении размера оригинала возвращается ошибка `415 Unsupported Media Type`.

## Базовые концепции

Модуль `image_filter` в Angie (начиная с версии 1.11.0) значительно превосходит стандартный Nginx за счет нативной поддержки форматов нового поколения и возможности глубокой настройки кодеков.

### Архитектурный контекст

Директивы `resize`, `crop`, `convert` и `rotate` выполняются в контексте отдельного блока `server` или `location`, который в production-средах выносится на внутренний порт или Unix-сокет. Это предотвращает блокировку TLS-обработки и отдачи статики на внешнем фронтенде. Клиентский запрос проходит через фронтенд с `proxy_cache`, который при промахе кэша (MISS) проксирует запрос на внутренний сервер трансформации. Результат кэшируется фронтендом с обязательным ключом, учитывающим формат (`Vary: Accept`), чтобы избежать отравления кэша.

### Принципы работы операций

Все операции трансформации в Angie выполняются декомпрессией исходного изображения в RAM, применением математической операции к пиксельной матрице и последующим сжатием в целевой формат. Это делает их крайне ресурсоемкими: время обработки зависит от разрешения оригинала, сложности кодера и количества применяемых фильтров.

- **resize** — масштабирует изображение с сохранением пропорций (вписывание). Отрицательное значение в `<w>` или `<h>` (дефис) заставляет сервер вычислить недостающую сторону автоматически.
- **crop** — сначала масштабирует изображение так, чтобы оно полностью заполнило целевые размеры, затем обрезает лишнее по центру. Эквивалентно обрезке после `resize` с последующим `crop`, но выполняется за один проход.
- **convert** — изменяет контейнер и алгоритм сжатия без изменения геометрии. Критически важен для перехода с JPEG на AVIF/WebP для снижения трафика.
- **rotate** — поворачивает изображение на заданный угол (90, 180, 270). Меняет значения ширины и высоты соответственно.

### Зависимости и ограничения

Поддержка форматов WebP, AVIF и HEIC зависит от версии системной библиотеки `libgd`, с которой скомпилирован Angie. Перед использованием в production выполните проверку:

```bash
angie -V 2>&1 | grep -E "1.1[1-9]|image_filter"
ldd /usr/lib/angie/modules/ngx_http_image_filter_module.so | grep -E "webp|avif|heif"
```

Если вывод содержит `libwebp`, `libavif` или `libheif` — формат поддерживается. На Ubuntu 24.04+ и Debian 12+ актуальная поддержка AVIF/HEIC доступна из системных репозиториев.

### Основные операции трансформации

| Операция | Описание | Синтаксис |
|:---------|:---------|:----------|
| **resize** | Масштабирование с сохранением пропорций (вписывание). | `image_filter resize <w> <h>` |
| **crop** | Масштабирование и центрирование (заполнение). | `image_filter crop <w> <h>` |
| **convert** | Принудительное изменение выходного формата. | `image_filter convert <type>` |
| **rotate** | Поворот изображения (90, 180, 270 градусов). | `image_filter rotate <deg>` |
| **test** | Проверка, что файл является изображением. | `image_filter test` |

*Примечание: В параметрах `<w>` и `<h>` можно использовать `-` (дефис), чтобы сервер вычислил размер автоматически, сохранив пропорции.*

### Поддерживаемые форматы (2026)

Angie обеспечивает полноценную поддержку (чтение и запись) следующих форматов:

- **WebP:** Оптимальный баланс между сжатием и совместимостью. Требует на 2–3 раза больше CPU, чем JPEG.
- **AVIF:** Максимальное сжатие при высоком качестве (стандарт для High Load в 2026 году). Требует на 10–50 раз больше CPU, чем JPEG.
- **HEIC:** Чтение фотографий с мобильных устройств Apple для их последующей конвертации в веб-форматы.
- **JPEG/PNG/GIF:** Классические форматы с поддержкой прозрачности и анимации.

### Тонкий тюнинг качества

Для высоконагруженных систем критически важен баланс между нагрузкой на CPU и объемом трафика:

1. **AVIF Speed (`image_filter_avif_speed`):** Параметр от 0 до 10. Чем выше значение, тем быстрее кодирование, но ниже степень сжатия. Для High Load рекомендуется `8–10`.
2. **Quality:**
   - `image_filter_jpeg_quality`: Качество JPEG (рекомендуется `80–85`).
   - `image_filter_webp_quality`: Качество WebP (рекомендуется `75–80`).
   - `image_filter_avif_quality`: Качество AVIF (рекомендуется `60–70`).
   - `image_filter_heic_quality`: Качество HEIC (рекомендуется `60–75`).
3. **Sharpen:** Директива `image_filter_sharpen`. Значения `1–5` помогают сделать миниатюры более четкими без появления артефактов. Добавляет +15–30% к времени обработки.
4. **Interlace:** Директива `image_filter_interlace on` позволяет генерировать прогрессивные JPEG, улучшая субъективное время загрузки для конечного пользователя на медленных сетях.

### Взаимодействие с кэшированием и заголовками

Для корректной работы адаптивной доставки при динамическом ресайзе требуется заголовок `Vary: Accept`. Без него промежуточные прокси и CDN могут «отравить» кэш, отдав AVIF-версию браузеру, который поддерживает только JPEG. Ключ `proxy_cache_key` должен включать суффикс формата и параметры ресайза. Подробности в [Стратегии кэширования изображений](./caching.md).

## Практические сценарии

### Предварительные требования

1. **Angie >= 1.11.0** с загруженным модулем:
   ```bash
   angie -V 2>&1 | grep -E "1.1[1-9]|image_filter"
   # → Ожидаемый вывод: версия >= 1.11.0 и флаг --with-http_image_filter_module
   ```
2. **libgd** с поддержкой нужных форматов (WebP, AVIF, HEIC). Проверка:
   ```bash
   ldd /usr/lib/angie/modules/ngx_http_image_filter_module.so | grep -E "webp|avif|heif"
   ```
3. **Изоляция обработки:** Внешний фронтенд и внутренний сервер трансформации должны быть разными блоками `server`. Внутренний сервер слушает `127.0.0.1:8081` или Unix-сокет.
4. **Буфер:** Директива `image_filter_buffer` должна превышать размер самого большого оригинала в байтах (рекомендуется `15M–20M`).

### Сценарий 1: Адаптивная отдача AVIF с ресайзом

Самый актуальный сценарий для 2026 года: автоматический выбор AVIF для поддерживающих браузеров с динамическим изменением ширины.

**Ожидаемый результат:** При запросе `/img/resize/800/photo.jpg` с заголовком `Accept: image/avif,image/webp,*/*` клиент получает сжатую AVIF-версию шириной 800px.

```nginx
location ~* ^/img/resize/(?<width>\d+)/(?<image>.+)$ {
    proxy_pass http://internal_storage/$image;
    
    image_filter_buffer 20M;
    image_filter resize $width -;
    image_filter convert avif;
    image_filter_avif_quality 65;
    image_filter_avif_speed 9;
    image_filter_sharpen 2;
    image_filter_interlace on;

    add_header Vary "Accept";
    error_page 415 = /static/placeholder.png;
}
```

**Валидация:**
```bash
curl -I -H "Accept: image/avif" https://example.com/img/resize/800/photo.jpg
# → HTTP/2 200, Content-Type: image/avif, Vary: Accept
```

### Сценарий 2: Конвертация HEIC с iPhone в WebP

Полезно для сервисов с пользовательским контентом, где фотографии загружаются в формате HEIC.

**Ожидаемый результат:** При запросе `/upload/previews/photo.heic` клиент получает квадратную миниатюру 300x300 в формате WebP.

```nginx
location /upload/previews/ {
    image_filter convert webp;
    image_filter_webp_quality 80;
    image_filter crop 300 300;
    image_filter_buffer 20M;
    image_filter_sharpen 1;

    proxy_cache image_cache;
    proxy_cache_valid 200 1y;
    add_header Vary "Accept";
}
```

**Валидация:**
```bash
curl -I https://example.com/upload/previews/photo.heic
# → HTTP/2 200, Content-Type: image/webp
```

### Сценарий 3: Цепочка трансформаций (Rotate + Resize)

Angie позволяет выполнять последовательные действия в одной цепочке. В примере: поворот фото на 90 градусов и последующее уменьшение.

**Ожидаемый результат:** При запросе `/rotate-and-resize/photo.jpg` возвращается повернутое изображение размером 800x600 в формате progressive JPEG.

```nginx
location /rotate-and-resize/ {
    image_filter rotate 90;
    image_filter resize 800 600;
    image_filter_jpeg_quality 85;
    image_filter_interlace on;
    image_filter_sharpen 2;
    image_filter_buffer 20M;
}
```

**Валидация:**
```bash
curl -s -o /tmp/rotated.jpg https://example.com/rotate-and-resize/photo.jpg
file /tmp/rotated.jpg
# → JPEG image data, JFIF standard 1.01, aspect ratio, density 72x72, segment length 16
# → Exif: Orientation: rotate 90 CW (поворот применен)
identify /tmp/rotated.jpg
# → rotated.jpg JPEG 800x600 ...
```

### Сценарий 4: Безопасный ресайз через внутренний Unix-сокет

Архитектурно правильный паттерн для High Load. Внешний фронтенд кэширует и защищает запросы, внутренний сервер только трансформирует.

```nginx
# Внешний фронтенд (порт 80/443)
server {
    listen 443 ssl http2;
    server_name img.example.com;
    
    location ~* ^/resize/(?<w>\d+)x(?<h>\d+)/(?<file>.+)$ {
        add_header Vary "Accept";
        proxy_cache img_cache;
        proxy_cache_key "$host$uri$is_args$args$http_accept";
        proxy_cache_valid 200 30d;
        proxy_cache_lock on;
        proxy_cache_use_stale error timeout updating;
        
        proxy_pass http://unix:/var/run/angie_img_filter.sock:/resize/$w/$h/$file;
    }
}

# Внутренний сервер (Unix-сокет)
server {
    listen unix:/var/run/angie_img_filter.sock;
    server_name localhost;
    
    root /var/www/images/originals;
    status_zone image_filter_backend;
    
    location ~* ^/resize/(?<w>\d+)x(?<h>\d+)/(?<file>.+)$ {
        internal; # Запрет прямого доступа
        image_filter resize $w $h;
        image_filter_buffer 20M;
        image_filter_convert avif;
        image_filter_avif_quality 65;
        image_filter_avif_speed 9;
        image_filter_sharpen 1;
        
        error_page 415 = @empty;
    }
    
    location @empty {
        empty_gif;
    }
}
```

**Валидация:**
```bash
# Проверка работы Unix-сокета
ss -xl | grep angie_img_filter
# → LISTEN 0 128 /var/run/angie_img_filter.sock

# Проверка кэша
curl -I https://img.example.com/resize/400x300/photo.jpg
# → X-Cache-Status: MISS (первый запрос), затем HIT
```

## Операции и команды

```bash
# Проверка привязки Unix-сокета
ss -xl | grep angie_img_filter
# → LISTEN 0 128 /var/run/angie_img_filter.sock

# Разные размеры
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" \
  https://img.example.com/resize/100x100/photo.jpg      # → 200 image/jpeg

# Соотношение сторон (аргумент в URL filter)
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" \
  https://img.example.com/resize/400x300! (fit=crop)   # → 200

# Проверка, что нет кэш-промахов стабильно
curl -sI https://img.example.com/resize/400x300/photo.jpg | grep X-Cache-Status
# → X-Cache-Status: HIT
```

## Устранение неисправностей (Troubleshooting)

| Симптом | Причина | Решение |
|:---|:---|:---|
| `415` при большом размере | `image_filter_buffer` меньше оригинала | Увеличить до 20M (расчет: 12МП ≈ 46MB в RGB) |
| Картинка не меняет пропорции | Неверно заданный аргумент в `image_filter resize` | Проверить синтаксис: `image_filter resize 400 300;` |
| Максимальный размер не применяется | Параметры передаются бесконтрольно | Ограничить допустимые комбинации regex в `location` или через `map` |
| Очень медленная генерация больших файлов | Нет кэширования трансформаций | Схема «фронт-кэш + внутренний фильтр» (см. [caching.md](./caching.md)) |

## Лучшие практики

1.  **Один размер — одна трансформация**: кэшируйте результат на фронте; CPU тратится на картинку только один раз.
2.  **Ограничение набора размеров** обязательно (иначе произвольные `123x456` создадут миллионы уникальных кэшей — cache poisoning). См. [security.md](./security.md).
3.  **`image_filter_interlace on`** — прогрессивный JPEG улучшает perceived performance на медленных сетях.
4.  **Не забывайте про `Vary: Accept`** при адаптивной отдаче разных форматов по одному URL (см. [caching.md](./caching.md)).

## Дополнительная информация

### Критические рекомендации для High Load

1. **Буфер обработки (`image_filter_buffer`):** Самая частая причина ошибок `415`. Если исходное изображение (оригинал) больше этого буфера, трансформация не произойдет. В 2026 году, учитывая рост разрешения мобильных камер, устанавливайте не менее `20M`.
   - Расчет: разрешение 12 МП (4032x3024) в RGB занимает ~46 MB в несжатом виде. Выбирайте буфер с запасом 30–50%.
2. **Защита CPU (DoS):** Трансформация — ресурсоемкая операция. Обязательно ограничивайте возможные значения размеров через регулярные выражения в `location` или директиву `map`, чтобы злоумышленник не смог запросить миллионы уникальных ресайзов (например, 101x101, 102x102...).
   - Подробнее: **[Безопасность image_filter](./security.md)**.
3. **Схема «Двойного проксирования»:** Всегда используйте схему, где внешний сервер кэширует результат трансформации от внутреннего сервера с `image_filter`. Это гарантирует, что CPU тратится на одну картинку только один раз.
   - Подробнее: **[Стратегии кэширования изображений](./caching.md)**.
4. **Заголовок Vary:** Для адаптивной доставки по одному URL обязательно добавляйте `add_header Vary "Accept";`. Без этого кэш и CDN будут отдавать неправильные форматы.
5. **Прогрессивный JPEG:** Директива `image_filter_interlace on` позволяет изображениям JPEG загружаться постепенно, что улучшает субъективную производительность (Perceived Performance) на медленных сетях.

### Наблюдаемость и мониторинг

Включение `status_zone` на внутреннем сервере трансформации позволяет отслеживать эффективность работы в реальном времени:

- **`responses.time`**: Среднее время ответа внутреннего фильтра. Используется для тюнинга `image_filter_avif_speed`.
- **`responses.codes.415`**: Частота ошибок из-за нехватки `image_filter_buffer`.
- **`requests.current`**: Количество параллельно обрабатываемых изображений.

Пример запроса к API Angie:
```bash
curl http://127.0.0.1:8080/api/6/http/status_zones/image_filter_backend
```

### Ориентировочное время обработки (Latency)

На одном ядре 3 GHz при `image_filter_buffer 20M`:

| Операция | Время |
|:---------|:------|
| JPEG → WebP (800x600) | ~30–50 мс |
| JPEG → AVIF (speed 8, 800x600) | ~100–180 мс |
| Применение Sharpen (1–5) | +15–30% к базовому времени |
| JPEG → Progressive JPEG | +5–10% |

### Расчет памяти для High Load

Каждая трансформация требует объема RAM, равного `image_filter_buffer`. При 100 параллельных запросах и буфере 20M потребуется ~2 GB оперативной памяти только под нужды модуля. Учитывайте это при настройке `worker_rlimit_nofile` и лимитов `cgroups`/Kubernetes.

### Типичные ошибки и устранение неполадок

| Ошибка | Причина | Решение |
|:-------|:--------|:--------|
| `415 Unsupported Media Type` | Исходник превышает `image_filter_buffer` | Увеличить буфер до 20M или выше |
| `415` при валидном JPEG | `libgd` скомпилирован без поддержки WebP/AVIF | Пересобрать Angie с нужными флагами или установить пакет с поддержкой |
| Низкая скорость AVIF | Слишком низкое значение `image_filter_avif_speed` | Установить `8–10` для High Load |
| Отравление кэша | Отсутствует `Vary: Accept` или `$img_suffix` в `proxy_cache_key` | Добавить заголовок и расширить ключ |
| Высокий CPU при низкой нагрузке | Отсутствует кэширование результата | Реализовать двухслойную схему |
| Медленная загрузка на слабых сетях | Отсутствует `image_filter_interlace on` | Включить прогрессивный JPEG |

### Рекомендации по таймаутам

Устанавливайте адекватные `proxy_read_timeout` на фронтенде (например, 5s), так как генерация тяжелого AVIF может занимать сотни миллисекунд. Для предотвращения зависаний добавьте:
```nginx
proxy_connect_timeout 2s;
proxy_read_timeout 5s;
proxy_send_timeout 5s;
```

### Очистка и откат изменений

Для отключения динамической трансформации без остановки сервиса:
1. Замените блоки с `image_filter` на статический `root` и `try_files`.
2. Очистите кэш результатов трансформации через `proxy_cache_purge` или удалите директорию кэша.
3. Убедитесь, что фронтенд корректно отдает статические файлы.
