# Модуль image_filter в Angie: производительность и масштабирование

## Определения

**Производительность image_filter** — совокупная характеристика эффективности обработки изображений, измеряемая временем задержки (latency) на операцию и пропускной способностью (throughput) системы при различных типах трансформаций.

## Базовые концепции

### Факторы влияния на задержку

Время обработки одного изображения напрямую зависит от вычислительной сложности алгоритмов и характеристик исходного файла:

- **Формат и сжатие:** Декодирование PNG (особенно с LOSSLESS сжатием) требует значительно больше ресурсов CPU, чем JPEG.
- **Тип трансформации:** Операция `crop` обычно выполняется быстрее, чем `resize`, так как не требует пересчета всех пикселей изображения.
- **Целевой формат:** Кодирование в WebP или AVIF — наиболее ресурсоёмкий этап. WebP LOSSLESS является самым «дорогим» с точки зрения CPU.
- **Ориентировочные задержки:**
  - JPEG → WebP: ~40–60 мс.
  - PNG → WebP: ~80–120 мс.
  - Resize: добавляет ~10–20 мс к базовой обработке.

### Стратегии масштабирования

Поскольку `image_filter` является CPU-интенсивным процессом, при росте нагрузки требуется масштабирование:

1. **Вертикальное (Scale Up):** Увеличение количества ядер CPU и выделение большего числа `worker_processes`.
2. **Горизонтальное (Scale Out):** Вынос функционала фильтрации на отдельные инстансы (Dedicated Image Filter Nodes) за балансировщиком нагрузки.
3. **Изоляция в контейнерах:** Использование Docker/Kubernetes для ограничения ресурсов и независимого масштабирования узлов обработки.

## Практические сценарии

### Сценарий: Оптимизация буфера для тяжелых изображений

Директива `image_filter_buffer_size` определяет максимальный размер исходного изображения, которое Angie сможет загрузить в память для обработки.

```nginx
# Увеличение буфера до 20 МБ для работы с фото высокого разрешения
image_filter_buffer_size 20M;
```

**Рекомендация:** Не устанавливайте слишком большое значение глобально, чтобы избежать перерасхода оперативной памяти при массовых запросах.

### Сценарий: Проверка производительности через cURL

Для измерения времени обработки и проверки корректности работы кэша используйте cURL с форматированием вывода.

```bash
# Проверка времени ответа (time_total)
curl -o /dev/null -s -w 'Total time: %{time_total}s\n' https://images.example.com/img/photo.jpg

# Проверка статуса кэша и типа контента
curl -I https://images.example.com/img/photo.jpg | grep -E "Content-Type|X-Cache-Status"
```

### Мониторинг ключевых метрик

Для стабильной работы высоконагруженной системы необходимо отслеживать:

- **Upstream Response Time:** Время, затраченное внутренним сервером фильтрации на обработку.
- **Cache Hit Ratio:** Эффективность кэширования (цель — >90%). См. подробнее в [кэшировании](./caching.md).
- **CPU Load:** Загрузка ядер на инстансах `image_filter`.
- **Buffer Overflows:** Ошибки 415 или сообщения в логах о превышении `image_filter_buffer_size`.

## Дополнительная информация

### Тюнинг и ограничения

- **Последовательная обработка:** В рамках одного рабочего процесса изображения обрабатываются последовательно. Параллелизм достигается только за счет множества `worker_processes`.
- **Общие настройки производительности:** Глобальные параметры оптимизации (CPU affinity, лимиты файлов) описаны в [общем руководстве по производительности](../performance_optimization.md).
- **Альтернативы:** При экстремальных нагрузках (десятки тысяч запросов в секунду) рассмотрите специализированные микросервисы (Thumbor, Imaginary) или CDN с поддержкой Image Optimization.
