# Модуль image_filter в Angie: производительность и масштабирование

## Определения

**Производительность image_filter** — время обработки изображений, зависящее от формата исходного файла, целевого формата, размера и типа операции (конвертация, изменение размера, LOSSLESS/LOSSY сжатие).

## Базовые концепции

### Факторы влияния на производительность

**Время обработки (ориентировочно):**

- JPEG → WebP: ~40–60 мс
- PNG → WebP: ~80–120 мс (формат PNG использует LOSSLESS сжатие)
- С изменением размера (resize): +10–20 мс
- LOSSLESS (сжатие без потерь) операции требуют больше ресурсов, чем LOSSY (сжатие с потерями)

**Основные потребители ресурсов:**

1. Декодирование исходного изображения (особенно PNG с большим количеством цветов)
2. Операции изменения размера (resize) — CPU (Central Processing Unit)-зависимая операция
3. Кодирование в целевой формат (WebP LOSSLESS наиболее затратный)

### Масштабирование

**Стратегии:**

1. **Отдельный хост** — image_filter на выделенном сервере с доступом к общему хранилищу изображений
2. **Контейнеризация** — запуск в Docker для изоляции нагрузки и простого масштабирования
3. **Горизонтальное масштабирование** — несколько инстансов за балансировщиком нагрузки (Load Balancer — устройство/ПО для распределения запросов между серверами)

## Практические сценарии

### Рекомендации по оптимизации

1. Всегда используйте кэширование обработанных изображений (см. [кэширование](./caching.md))
2. Для высоких нагрузок — отдельный хост/контейнер для image_filter
3. Ограничьте допустимые размеры исходных изображений директивой `image_filter_buffer_size`
4. Используйте `proxy_cache_min_uses 2` для исключения одноразовых запросов из кэша

### Проверка производительности

```bash
# Проверка формата ответа (должен быть WebP)
curl -I https://images.example.com/img/photo.jpg | grep Content-Type
# → Content-Type: image/webp

# Проверка времени ответа (первый запрос медленный, последующие — из кэша)
curl -w "@curl-format.txt" -o /dev/null -s https://images.example.com/img/photo.jpg

# curl-format.txt:
# time_namelookup:  %{time_namelookup}\n
# time_connect:     %{time_connect}\n
# time_starttransfer: %{time_starttransfer}\n
# ----------\n
# time_total:       %{time_total}\n
```

### Мониторинг производительности

**Ключевые метрики:**

- Время ответа бэкенда (upstream response time)
- Hit/Miss ratio кэша (соотношение попаданий/промахов)
- Загрузка CPU на инстансах image_filter
- Размер буфера обработки (если приближается к `image_filter_buffer_size` — увеличить лимит)

## Дополнительная информация

**Тюнинг параметров:**

```nginx
# Увеличение буфера для больших изображений
image_filter_buffer_size 20M;

# Оптимизация Worker Processes
worker_processes auto;
worker_connections 1024;
```

**Ограничения:**

- Модуль image_filter обрабатывает изображения последовательно в рамках одного запроса
- Параллельная обработка достигается только на уровне Worker Processes
- Для очень высоких нагрузок рекомендуется выделенный сервис обработки изображений (например, Imaginary, Thumbor)
