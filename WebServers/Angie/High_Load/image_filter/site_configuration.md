# Модуль image_filter в Angie: конфигурация фронтенда

## Определения

**Image Front** — высокопроизводительный прокси-сервер (фронтенд), отвечающий за прием клиентских запросов, интеллектуальный выбор формата изображения, управление кэшем и защиту системы от перегрузок.

**Адаптивная доставка** — метод отдачи наиболее эффективного формата изображения (AVIF, WebP или HEIC) в зависимости от возможностей браузера, определяемых через заголовок `Accept`.

## Базовые концепции

### Логика выбора формата (Content Negotiation)

Для реализации адаптивности в Angie используется директива `map`, которая анализирует заголовок `Accept` и подготавливает переменные для маршрутизации.

*Примечание: Если ваши изображения уже сжаты заранее (на этапе сборки), используйте стратегию статической адаптивной доставки, описанную в руководстве по [Nginx Adaptive Content](../../../Nginx/Performance/nginx_adaptive_content.md).*

```nginx
# Определение оптимального формата на основе заголовка Accept
map $http_accept $img_suffix {
    "~*avif"  ".avif";
    "~*webp"  ".webp";
    "~*heic"  ".heic";
    default   "";
}

# Определение префикса для внутреннего проксирования к фильтру
map $http_accept $img_prefix {
    "~*avif"  "/convert/avif";
    "~*webp"  "/convert/webp";
    "~*heic"  "/convert/heic";
    default   "/resize";
}
```

### Важность заголовка Vary

При использовании одной и той же ссылки для разных форматов (например, `photo.jpg` отдает AVIF или WebP), необходимо обязательно добавлять заголовок `add_header Vary "Accept";`. Это сообщает промежуточным прокси-серверам и CDN, что контент зависит от возможностей клиента.

## Практические сценарии

### Сценарий: Полнофункциональный фронтенд с кэшированием

Этот пример демонстрирует архитектурно верный подход к доставке изображений с использованием внутреннего сервера фильтрации.

```nginx
server {
    listen 443 ssl http2;
    server_name images.example.com;
    
    # Зона мониторинга для фронтенда
    status_zone image_frontend;

    # Основная локация для запросов
    location ~* ^/img/(?<w>\d+)x(?<h>\d+)/(?<file>.+)$ {
        add_header Vary "Accept";
        add_header X-Cache-Status $upstream_cache_status;
        
        # Ключ кэша ОБЯЗАТЕЛЬНО должен включать формат ($img_suffix)
        proxy_cache image_cache;
        proxy_cache_key "$host$uri$is_args$args$img_suffix";
        
        # Защита от "стада бизонов"
        proxy_cache_lock on;
        proxy_cache_lock_timeout 5s;
        
        # Проксирование на внутренний сервер (фильтр)
        # Формируем путь вида: /convert/avif/100/100/photo.jpg
        proxy_pass http://127.0.0.1:8081$img_prefix/$w/$h/$file;
        
        proxy_cache_valid 200 30d;
        expires 30d;
    }
}
```

### Сценарий: Статическая раздача с фоллбэком

Если оптимизированные версии уже существуют на диске (например, созданы через `proxy_store` на бэкенде).

```nginx
location /static/img/ {
    add_header Vary "Accept";
    # Поиск: .avif -> .webp -> .heic -> оригинал
    try_files $uri$img_suffix $uri =404;
    
    expires 365d;
}
```

## Дополнительная информация

### Рекомендации по настройке кэша

- **proxy_cache_key:** Если забыть добавить `$img_suffix` в ключ кэша, первый запросивший (например, пользователь Chrome с AVIF) "отравит" кэш для всех остальных (пользователей Safari, которые AVIF не поддерживают).
- **proxy_cache_use_stale:** Рекомендуется включать `proxy_cache_use_stale error timeout updating;`, чтобы отдавать старые версии изображений, пока фильтр занят генерацией новых.
- **Мониторинг:** Используйте `status_zone` на фронтенде для отслеживания `Cache Hit Ratio` отдельно от производительности самого фильтра.

### Безопасность

Для предотвращения несанкционированного ресайза произвольных размеров используйте модуль `secure_link` на уровне фронтенда. Подробнее в [разделе безопасности](./security.md).
