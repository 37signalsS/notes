# Оптимизация производительности Angie

## Определения

**Оптимизация производительности** — настройка веб-сервера для эффективного использования ресурсов и повышения пропускной способности.

---

## Базовые концепции

### Подходы к оптимизации

- **Серверная производительность:** Эффективное использование ресурсов сервера (CPU, память, диск, сеть). Цели: минимизация потребления ресурсов, повышение пропускной способности (RPS — Requests Per Second).
- **Клиентская производительность:** Ускорение загрузки и отрисовки контента в браузере клиента. Цели: сокращение трафика, оптимизация кэширования, снижение задержек (TTFB — Time To First Byte).

### Связь с Nginx

Angie является форком Nginx с сохранением полной совместимости, поэтому большинство рекомендаций по оптимизации производительности Nginx применимы к Angie.

Основной источник знаний: [Оптимизация производительности Nginx](../../Nginx/Performance/nginx_performance_tuning.md).

## Практические сценарии

### Сценарий 1: Оптимизация производительности сервера

Многие из этих настроек пересекаются с общими рекомендациями в [руководстве по настройке производительности Nginx](../../Nginx/Performance/nginx_performance_tuning.md).

#### Основные настройки Angie/Nginx

- **`worker_processes auto;`**: Автоматически устанавливает количество рабочих процессов равным числу ядер CPU. Это оптимально, так как каждый воркер однопоточный.
- **`worker_cpu_affinity auto;`**: Привязывает каждый воркер к своему ядру CPU, что может улучшить производительность за счет лучшего использования кэша процессора, но снижает гибкость планировщика.
- **`worker_rlimit_nofile 100000;`**: Увеличивает лимит на количество открытых файловых дескрипторов для рабочих процессов.
- **`events { worker_connections 20000; }`**: Максимальное количество соединений на один воркер.

#### Сетевые настройки

- **`sendfile on;`**: Использовать эффективный системный вызов для отправки файлов, минуя копирование данных в пространство пользователя.

  > **Важно:** Для HTTPS требуется Kernel TLS. Использование с HTTP/2 приводит к деградации производительности.

  > **Полная информация:** [Kernel TLS в Nginx](../../Nginx/Performance/nginx_performance_tuning.md#kernel-tls-ktls)

- **`tcp_nopush on;` и `tcp_nodelay on;`**: Оптимизируют отправку пакетов, позволяя накапливать данные для формирования полных пакетов и одновременно отключая задержку для отправки небольших пакетов.
- **`listen 80 reuseport;`**: Позволяет каждому воркеру создать свой слушающий сокет на одном и том же порту. Ядро ОС само распределяет входящие соединения между воркерами, что повышает производительность на многоядерных системах.
- **`keepalive_timeout 120s;`**: Увеличивает таймаут для keep-alive соединений со стороны клиента.

---

### Сценарий 2: Серверное кэширование (`proxy_cache`)

- **`proxy_cache_path /path/to/cache ... keys_zone=my_cache:10m ...`**: Определяет зону кэширования на диске.
- **`proxy_cache my_cache;`**: Включает кэширование для `location`.
- **`proxy_cache_valid 200 10s;`**: Устанавливает время жизни кэша для ответов с кодом 200.
- **`proxy_cache_lock on;`**: Предотвращает "стадо бизонов" (cache stampede), отправляя только один запрос на бэкенд для обновления протухшего элемента.
- **`proxy_cache_background_update on;` и `proxy_cache_use_stale updating;`**: Позволяют отдавать клиенту устаревший ответ из кэша немедленно, пока в фоне идет его обновление. Это критически важно для производительности.
- **`proxy_cache_use_stale error timeout ...`**: Разрешает отдавать устаревший контент, если бэкенд недоступен.

Детали реализации описаны в руководстве по [кэшированию в Nginx](../../Nginx/Performance/Caching/proxy_caching.md).

---

### Сценарий 3: Оптимизация на стороне клиента

- **Версии HTTP:** Включайте **HTTP/2 и HTTP/3**, чтобы ускорить загрузку за счет мультиплексирования. См. [настройку версий в Nginx](../../Nginx/Performance/nginx_http_versions.md).
- **Сжатие:** Используйте **Zstd** (уровень 1-4) для динамического сжатия и **Brotli** (уровень 11) для статики. См. [заметку о сжатии в Nginx](../../Nginx/Performance/nginx_compression.md).

### Сценарий 4: Специфичные оптимизации Angie

- **Мониторинг:** Angie имеет встроенную поддержку вывода метрик в формате Prometheus и позволяет создавать кастомные метрики. Это даёт более глубокую наблюдаемость за производительностью (аналог Nginx Plus).
- **Оптимизация HTTP/3 (QUIC):**
  - Директива `quic_bpf on;` использует BPF в ядре для оптимального распределения UDP-пакетов QUIC между рабочими процессами (значительно повышает производительность HTTP/3 при высоких нагрузках).
  - **Осторожно с `Alt-Svc`:** При включении заголовка `add_header Alt-Svc 'h3=":443"; ma=86400';` клиенты кэшируют доступность HTTP/3 на сутки (`ma=86400`). Если отключить UDP/QUIC порт, клиенты будут получать ошибки в течение этого времени.
