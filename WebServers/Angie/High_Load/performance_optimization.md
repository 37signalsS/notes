# Оптимизация производительности Angie

## Определения

**Оптимизация производительности** веб-сервера — это комплекс мер по настройке операционной системы и программного обеспечения для наиболее эффективного использования ресурсов (центральный процессор (CPU), оперативная память, дисковая и сетевая подсистемы) и повышения пропускной способности.

## Базовые концепции

### Подходы к оптимизации

- **Серверная производительность:** Эффективное использование ресурсов сервера. Цели: минимизация потребления ресурсов, повышение пропускной способности (количество запросов в секунду — RPS, Requests Per Second).
- **Клиентская производительность:** Ускорение загрузки и отрисовки контента в браузере клиента. Цели: сокращение трафика, оптимизация кэширования, снижение задержек (время до первого байта — TTFB, Time To First Byte).

### Связь с Nginx

[Angie](../angie_overview.md) является форком Nginx с сохранением полной совместимости. Большинство методов оптимизации идентичны для обоих серверов.

Основной источник по тюнингу параметров: **[Оптимизация производительности Nginx](../../Nginx/Performance/nginx_performance_tuning.md)**.

## Практические сценарии

### Сценарий 1: Тюнинг сетевого стека Linux (sysctl)

Для достижения максимальной производительности Angie необходимо настроить параметры ядра, управляющие сетевым стеком. Рекомендуется создавать отдельный файл конфигурации (например, `/etc/sysctl.d/90-webserver.conf`).

#### Оптимизация TCP

- **`net.ipv4.tcp_slow_start_after_idle = 0`**: Запрещает сброс механизма TCP Slow Start после простоя соединения. Это критично для долгоживущих постоянных соединений (Keep-Alive), позволяя им сразу работать на полной скорости.
- **`net.ipv4.tcp_nodelay = 1`**: (Со стороны ядра) минимизирует задержки при отправке небольших пакетов.
- **`net.ipv4.ip_local_port_range = 1024 65535`**: Расширяет диапазон эфемерных портов для поддержки большого количества исходящих соединений к бэкендам.
- **`net.ipv4.tcp_tw_reuse = 1`**: Позволяет быстрее переиспользовать сокеты в состоянии `TIME_WAIT`.

#### Очереди и буферы

- **`net.core.somaxconn = 65535`**: Увеличивает очередь прослушиваемых сокетов (Accept Queue). Должно быть согласовано с параметром `backlog` в директиве `listen` в Angie.
- **`net.ipv4.tcp_max_syn_backlog = 16384`**: Размер очереди для полуоткрытых соединений (SYN packets).
- **`net.core.netdev_max_backlog = 10000`**: Максимальный размер очереди пакетов на входе сетевой карты.
- **`net.ipv4.tcp_rmem` / `net.ipv4.tcp_wmem`**: Настройка автотюнинга буферов чтения и записи TCP.

Применение настроек: `sudo sysctl --system`. Подробнее см. в разделе **[Тюнинг параметров ядра (sysctl)](../../../Linux/Core/kernel/sysctl.md)**.

### Сценарий 2: Глобальные настройки и HTTP-контекст

Базовая конфигурация в `angie.conf` определяет эффективность использования CPU и памяти.

#### Процессы и дескрипторы

- **`worker_processes auto;`**: По одному процессу на ядро.
- **`worker_cpu_affinity auto;`**: Минимизация переключений контекста. **Внимание:** если на сервере работают другие тяжелые нагрузки (например, СУБД), привязка может вызвать конкуренцию за конкретные ядра.
- **`worker_rlimit_nofile 100000;`**: Должно быть достаточно для всех открытых сокетов и файлов.

#### Оптимизация HTTP-соединений

- **`keepalive_requests 2000;`**: Увеличение лимита запросов в одном соединении Keep-Alive для экономии памяти на сокетах.
- **`open_file_cache max=10000 inactive=60s;`**: Кэширование дескрипторов открытых файлов, их размеров и времени модификации. Это снижает количество системных вызовов.
- **Таймауты:** Сокращайте таймауты для медленных клиентов, чтобы быстрее освобождать ресурсы:
  - `client_body_timeout 10s;`
  - `client_header_timeout 10s;`
  - `send_timeout 10s;`

### Сценарий 3: Оптимизация взаимодействия с бэкендами (Upstreams)

Эффективная работа с проксируемыми серверами критична для минимизации задержек.

- **Keep-Alive к бэкендам:** Позволяет переиспользовать соединения, значительно снижая нагрузку на CPU (особенно при использовании TLS к апстримам).
  ```nginx
  upstream backend_cluster {
      server 10.0.0.1:8080;
      keepalive 64; # Соединений на один рабочий процесс
  }
  
  location / {
      proxy_http_version 1.1;
      proxy_set_header Connection "";
      proxy_pass http://backend_cluster;
  }
  ```
- **Настройка буферов прокси:** Подбирайте размеры так, чтобы типичные ответы бэкенда помещались в RAM.
  - `proxy_buffer_size 4k;`
  - `proxy_buffers 16 16k;`
- **Таймауты подключения:** Используйте принцип **Fail Fast** для быстрой реакции на сбои бэкендов.
  - `proxy_connect_timeout 5s;`

### Сценарий 4: Серверное кэширование и защита от нагрузки

- **`proxy_cache_use_stale error timeout updating http_500 http_502;`**: Позволяет отдавать устаревший кэш при сбоях бэкенда или во время его обновления.
- **`proxy_cache_lock on;`**: Предотвращает лавинообразную нагрузку на бэкенд («стадо бизонов»).

Полное руководство: **[Серверное кэширование в Nginx](../../Nginx/Performance/Caching/proxy_caching.md)**.

### Сценарий 5: Оптимизация логирования

При экстремальных нагрузках запись логов на диск может стать узким местом.

- **Буферизация и сжатие:** Пишите логи блоками и сжимайте их «на лету».
  ```nginx
  access_log /var/log/angie/access.log combined buffer=32k flush=10s gzip=3;
  ```
- **Логирование через переменные:** Для динамически определяемых путей логов используйте `open_log_file_cache`.

### Сценарий 6: Оптимизация TLS и HTTP/3

- **`ssl_session_cache shared:SSL:10m;`**: Совместное использование кэша сессий между рабочими процессами.
- **`ssl_session_tickets on;`**: Механизм возобновления сессий без хранения состояния на сервере (для TLS 1.3).
- **`ssl_early_data on;`**: Включение Zero-RTT для ускорения повторных подключений (требует поддержки приложением).
- **`quic_bpf on;`**: Использование eBPF для маршрутизации UDP-пакетов HTTP/3 на уровне ядра.

## Дополнительная информация

### Рекомендации по настройке

1. **Не копируйте настройки слепо.** Всегда измеряйте влияние каждого изменения на вашей специфической нагрузке и железе.
2. **Соблюдайте баланс.** Оптимизация под низкую задержку (Low Latency) часто вступает в противоречие с оптимизацией под пропускную способность (Throughput).
3. **Используйте Kernel TLS (kTLS)** только для HTTP/1.1 при раздаче тяжелого статического контента. См. **[Оптимизация производительности Nginx](../../Nginx/Performance/nginx_performance_tuning.md)**.
