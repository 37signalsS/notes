# Контроль доступа в Angie

## Определения

**Контроль доступа** в [Angie](./angie_overview.md), как и в Nginx, представляет собой набор механизмов для управления доступом к сайтам и их отдельным частям (`locations`). Эти механизмы позволяют гибко настраивать правила, по которым пользователи и системы могут получать доступ к ресурсам, тем самым обеспечивая безопасность и гранулярное управление.

## Основные концепции

В Angie существует несколько встроенных и сторонних способов контроля доступа. Ключевые из них:

1. **Ограничение по IP-адресу (`ngx_http_access_module`)**: Простейший метод, разрешающий или запрещающий доступ на основе IP-адреса клиента.
2. **Базовая аутентификация (`ngx_http_auth_basic_module`)**: Стандартный механизм HTTP, запрашивающий у пользователя логин и пароль.
3. **Аутентификация через подзапрос (`ngx_http_auth_request_module`)**: Гибкий метод, делегирующий решение о доступе внешнему сервису или внутреннему `location` через отправку подзапроса.
4. **Аутентификация через PAM (`ngx_http_auth_pam_module`)**: Способ интеграции с системными пользователями Linux через Pluggable Authentication Modules (PAM).

## Практические сценарии

### 1. Ограничение по IP-адресу

Это самый простой способ ограничить доступ, разрешив его только для определённых IP-адресов или подсетей. Директивы `allow` и `deny` обрабатываются последовательно, и первое совпавшее правило определяет результат.

**Конфигурация:**

```nginx
location /protected/ {
    # 1. Разрешаем доступ из локальной сети
    allow 192.168.1.0/24;
    
    # 2. Разрешаем доступ с конкретного IP
    allow 203.0.113.5;

    # 3. Запрещаем доступ всем остальным
    deny all;

    # ... остальная конфигурация
}
```

- **`allow`**: Разрешает доступ для указанной сети или адреса.
- **`deny all`**: Запрещает доступ всем, кто не подпал под предыдущие правила `allow`.

### 2. Базовая аутентификация

Этот метод позволяет защитить ресурс с помощью стандартного окна ввода логина и пароля в браузере.

**Конфигурация:**

1. **Создание файла с паролями:**
    Для создания файла с пользователями и паролями используется утилита `htpasswd` (обычно из пакета `apache2-utils`).

    ```bash
    # Создать файл и добавить первого пользователя
    sudo htpasswd -c /etc/angie/htpasswd-users admin

    # Добавить еще одного пользователя (без флага -c)
    sudo htpasswd /etc/angie/htpasswd-users guest
    ```

2. **Настройка Angie:**
    В блоке `location` или `server` необходимо указать путь к файлу с паролями.

    ```nginx
    location /admin/ {
        auth_basic "Administrator Area";
        auth_basic_user_file /etc/angie/htpasswd-users;
    }
    ```

    - `auth_basic "Administrator Area"`: Текст, который увидит пользователь в диалоговом окне.
    - `auth_basic_user_file`: Путь к файлу с паролями.

**Ограничения:**

- Все пользователи, перечисленные в файле `auth_basic_user_file`, будут иметь доступ. Для разграничения прав для разных `location` необходимо создавать разные файлы с паролями.
- **Безопасность:** Данные передаются в кодировке Base64, поэтому базовую аутентификацию **необходимо** использовать только совместно с [шифрованием TLS (HTTPS)](./angie_tls_setup.md).

#### Комбинирование с ограничением по IP (`satisfy`)

Директива `satisfy` позволяет комбинировать несколько методов аутентификации. `satisfy any;` требует, чтобы **хотя бы одно** из условий было выполнено, в то время как `satisfy all;` (по умолчанию) требует выполнения **всех** условий.

**Пример:** Разрешить доступ либо из локальной сети, либо по паролю.

```nginx
location /admin/ {
    satisfy any; # Разрешить, если выполнено любое из правил

    # Правило 1: ограничение по IP
    allow 192.168.1.0/24;
    deny all;

    # Правило 2: базовая аутентификация
    auth_basic "Admin Area";
    auth_basic_user_file /etc/angie/htpasswd-users;
}
```

### 3. Аутентификация через подзапрос

Это наиболее гибкий метод, позволяющий делегировать принятие решения о доступе внешнему сервису. Angie отправляет на специальный "авторизующий" `location` подзапрос и на основе кода ответа ( `2xx` - разрешен, `4xx` - запрещен) принимает решение.

#### Сценарий 1: Проверка API-ключа средствами Angie

Логика проверки реализована прямо в конфигурации Angie.

```nginx
# Защищаемый ресурс
location /protected/ {
    # Делегируем аутентификацию на /_auth
    auth_request /_auth;
    
    # Если аутентификация успешна, запрос будет проксирован или обработан далее.
    return 200 "Доступ разрешен к защищенному ресурсу!";
    # proxy_pass http://my_backend_service; # Реальное использование
}

# Внутренняя локация для проверки API-ключа
location = /_auth {
    internal; # Доступна только для внутренних запросов Angie

    # Проверяем значение заголовка X-Api-Key
    if ($http_x_api_key != "secret-key") {
        # Если заголовок отсутствует или значение неверно, возвращаем 403 Forbidden
        return 403 "Неверный или отсутствующий X-Api-Key";
    }

    # Если заголовок X-Api-Key соответствует "secret-key", возвращаем 200 OK
    return 200;
}
```

#### Сценарий 2: Делегирование авторизации на `njs` (JavaScript)

Сложная логика авторизации выносится в отдельный JavaScript-файл с помощью модуля `njs`.

1. **Настройка Angie:**

    ```nginx
    # /etc/angie/angie.conf
    http {
        # ...
        # Импортируем js-модуль с логикой авторизации
        js_import /etc/angie/scripts/auth.js;
    }

    # /etc/angie/sites-available/default
    server {
        # ...

        # 1. Location, который будет проверять подзапросы
        location = /_auth_request {
            internal; # Доступен только для внутренних запросов
            js_content auth.authorize; # Вызываем функцию authorize из импортированного модуля
        }

        # 2. Защищаемый location
        location /secure/ {
            auth_request /_auth_request; # Включаем проверку
            
            # Переменные из модуля auth_request можно передать бэкенду
            # proxy_set_header X-User-ID $upstream_http_x_user_id;
            
            proxy_pass http://my_backend;
        }
    }
    ```

2. **Скрипт `auth.js` с логикой авторизации:**

    ```javascript
    // /etc/angie/scripts/auth.js
    function authorize(r) {
        // Пример: проверяем наличие и значение заголовка Authorization
        const authHeader = r.headersIn['Authorization'];

        if (authHeader && authHeader.startsWith('Bearer ') && authHeader.substring(7) === 'secret_token') {
            // Если токен верный, возвращаем 204 No Content (эквивалентно 2xx для auth_request)
            // и можем передать данные бэкенду через заголовки
            r.headersOut['X-User-ID'] = '123';
            r.return(204); // Доступ разрешен
            return;
        }

        // В противном случае запрещаем доступ
        r.return(401, "Authorization Required");
    }
    export default { authorize };
    ```

### 4. Аутентификация через PAM

Этот сторонний модуль (`ngx_http_auth_pam_module`) позволяет аутентифицировать пользователей через стандартный механизм PAM в Linux, используя системных пользователей. Подробное описание доступно в [PAM (Pluggable Authentication Modules)](../../Linux/Security/pam_overview.md).

1. **Установка и подключение модуля:**
    Для Angie Pro модуль устанавливается пакетом `angie-pro-module-pam`. В `angie.conf` необходимо добавить `load_module modules/ngx_http_auth_pam_module.so;`.

2. **Создание конфигурации сервиса PAM (`/etc/pam.d/angie`):**

    ```
    auth    required    pam_unix.so
    account required    pam_unix.so
    ```

3. **Настройка Angie:**

    ```nginx
    location /private/ {
        auth_pam "System Login Required";
        auth_pam_service_name "angie"; # Имя сервиса, созданного на шаге 2
    }
    ```

## Дополнительная информация

> **Примечание:** Механизмы контроля доступа, общие для Angie и Nginx, подробно описаны в общем руководстве по безопасности: **[Руководство по безопасности веб-сервера Nginx](../Nginx/Security/nginx_security_guide.md)**.

Существуют и другие модули для более специфических задач аутентификации, которые доступны для Angie, например:

- **`auth-jwt`**: Для валидации [JSON Web Tokens (JWT)](../../Security/Concepts/jwt.md).
- **[LDAP (Lightweight Directory Access Protocol)](../../Linux/SystemAdministration/users_management.md#LDAP-Lightweight-Directory-Access-Protocol)**: Для интеграции с корпоративными каталогами.
