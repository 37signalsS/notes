# Настройка отказоустойчивого кластера Angie с Keepalived (VRRP)

## 1. Концепции и определения

- **Цель:** Обеспечить непрерывную доступность сервиса (например, веб-сайта или API), распределенного за двумя или более серверами Angie. При отказе одного из серверов трафик должен автоматически перенаправляться на рабочий.
- **Компоненты:**
    - **Angie:** Высокопроизводительный веб-сервер и обратный прокси. В данном сценарии — основной сервис, доступность которого мы обеспечиваем. Подробнее в [общем обзоре Angie](./angie_overview.md).
    - **Keepalived:** Сервис, реализующий протокол VRRP для управления виртуальным IP-адресом. Детали можно найти в [обзоре Keepalived](../../../Networking/ServicesAndTools/keepalived_overview.md).
    - **VRRP (Virtual Router Redundancy Protocol):** Сетевой протокол, позволяющий нескольким узлам разделять один виртуальный IP-адрес (VIP) для обеспечения отказоустойчивости.
    - **Виртуальный IP-адрес (VIP):** Единый IP-адрес, который назначается активному серверу в кластере и "мигрирует" на резервный в случае сбоя. Клиенты всегда обращаются к этому VIP.

### Принцип работы

Схема состоит из двух или более серверов с Angie и Keepalived.

1.  **Роли:** Один сервер назначается `MASTER` (основной), остальные — `BACKUP` (резервные).
2.  **Обмен состоянием:** `MASTER` сервер периодически отправляет в сеть специальные мультикаст-сообщения — **VRRP advertisements**. Этими сообщениями он объявляет о своем "здоровье", высоком приоритете и о том, что он является владельцем виртуального IP-адреса.
3.  **Владение VIP:** Пока `MASTER` активен, VIP-адрес принадлежит ему. Весь клиентский трафик поступает на этот адрес и, соответственно, на `MASTER` узел.
4.  **Проверка сервиса (Health Check):** Keepalived на каждом узле постоянно проверяет работоспособность локального сервиса Angie с помощью специального скрипта. **Это критически важный механизм**: если сам сервер работает, но сервис Angie "завис" или не отвечает, кластер должен на это отреагировать. Если скрипт проверки завершается с ошибкой, Keepalived на этом узле добровольно **понижает свой приоритет**, давая возможность другому узлу стать `MASTER`.
5.  **Отказ (Failover):**
    - **Сценарий 1 (Отказ сервиса):** Скрипт проверки на `MASTER` узле не выполняется. Keepalived понижает свой приоритет. `BACKUP`-сервер, видя, что его собственный приоритет стал выше, перестает получать анонсы от `MASTER`, ждет короткий тайм-аут и сам становится `MASTER`, "захватывая" VIP-адрес.
    - **Сценарий 2 (Полный отказ узла):** Если `MASTER` прекращает отправлять VRRP-сообщения (из-за падения сервера, сети или остановки самого Keepalived), `BACKUP`-сервер с наивысшим приоритетом перестает их получать и после тайм-аута также захватывает роль `MASTER`.
6.  **Восстановление (Failback):** Когда оригинальный `MASTER` восстанавливается, он снова начинает отправлять VRRP-сообщения с более высоким приоритетом и (если не настроено иное) забирает VIP-адрес обратно, что приводит к обратному переключению.

## 3. Конфигурация

Предположим, у нас два сервера:

-   `node1` (Master): `192.168.1.101`
-   `node2` (Backup): `192.168.1.102`
-   Виртуальный IP: `192.168.1.100`

### 2.1. Конфигурация Keepalived (`/etc/keepalived/keepalived.conf`)

#### Скрипт проверки Angie (`/etc/keepalived/check_angie.sh`)

Скрипт должен проверять состояние Angie и завершаться с кодом `0` в случае успеха и ненулевым кодом в случае ошибки.

```bash
#!/bin/bash
# Более строгий вариант: проверяем, что Angie отдает именно код 200
STATUS_CODE=$(/usr/bin/curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1/health_check)
if [ "$STATUS_CODE" -eq 200 ]; then
  exit 0
else
  exit 1
fi
```
**Важно:**
- Используйте абсолютный путь к `curl`.
- Сделайте скрипт исполняемым: `chmod +x /etc/keepalived/check_angie.sh`.
- Убедитесь, что эндпоинт `/health_check` настроен в Angie.

#### Конфигурация для MASTER (`node1`)

```keepalived
global_defs {
   router_id angie_node_1
}

vrrp_script chk_angie {
    script "/etc/keepalived/check_angie.sh"
    interval 1   # Проверять каждую 1 секунду
    timeout 1    # Таймаут выполнения скрипта
    weight 20    # Если скрипт успешен, повысить приоритет на 20
    fall 2       # Считать сервис упавшим после 2 неудачных проверок
    rise 2       # Считать сервис поднявшимся после 2 удачных проверок
}

vrrp_instance VI_1 {
    state MASTER            # Изначальное состояние - MASTER
    interface enp1s0        # Сетевой интерфейс для VRRP
    virtual_router_id 51    # Уникальный ID для кластера, должен быть одинаковым на всех узлах
    priority 101            # Приоритет. У MASTER он должен быть выше.

    advert_int 1            # Интервал отправки VRRP-анонсов (в секундах)

    # Аутентификация для VRRP-пакетов. Пароль должен совпадать на всех узлах.
    authentication {
        auth_type PASS
        auth_pass your_secret_password
    }

    # Виртуальный IP-адрес, который будет "мигрировать"
    virtual_ipaddress {
        192.168.1.100/24
    }

    # Применение скрипта проверки
    track_script {
        chk_angie
    }
}
```

#### Конфигурация для BACKUP (`node2`)

Конфигурация почти идентична, но с `state BACKUP` и `priority 100`.

```keepalived
global_defs {
   router_id angie_node_2
}

vrrp_script chk_angie {
    # ... (та же конфигурация скрипта)
    script "/etc/keepalived/check_angie.sh"
    interval 1
    timeout 1
    weight 20
    fall 2
    rise 2
}

vrrp_instance VI_1 {
    state BACKUP            # Изначальное состояние - BACKUP
    interface enp1s0
    virtual_router_id 51    # Тот же ID
    priority 100            # Приоритет ниже, чем у MASTER

    advert_int 1

    authentication {
        auth_type PASS
        auth_pass your_secret_password # Тот же пароль
    }

    virtual_ipaddress {
        192.168.1.100/24
    }

    track_script {
        chk_angie
    }
}
```

### 2.2. Конфигурация Angie

На каждом сервере Angie должен быть легковесный эндпоинт для проверок.

```nginx
server {
    listen 80;
    server_name your_domain.com;

    # (Опционально) Заголовок для отладки
    # Позволяет видеть, какой сервер реально ответил.
    # На MASTER-узле: add_header X-Front-Node "master" always;
    # На BACKUP-узле: add_header X-Front-Node "backup" always;
    add_header X-Front-Node "master" always;

    location / {
        # Ваша основная конфигурация, например, отдача статики или проксирование
        root /usr/share/nginx/html;
        index index.html index.htm;
    }

    # Health check для Keepalived
    location /health_check {
        # Разрешаем доступ только с локального хоста (для скрипта Keepalived)
        allow 127.0.0.1;
        deny all;

        # Возвращаем простой и быстрый ответ.
        # Этот location не должен требовать много ресурсов.
        return 200 "OK";
        
        # Указываем, что логи для этих запросов не нужны, чтобы не засорять access.log
        access_log off;
    }
}
```

**Важно:**
- Конфигурация на `MASTER` и `BACKUP` узлах должна быть **идентичной**, за исключением значения в заголовке `X-Front-Node` (если вы его используете).
- В реальном проекте конфигурация Angie/Nginx, конечно, будет сложнее. Главное — обеспечить наличие легковесного `location` для проверок.
- Если для работы вашего приложения требуется не только работающий Angie, но и, например, доступность базы данных, логику `health_check` можно усложнить. Например, использовать `proxy_pass` на специальный эндпоинт вашего бэкенда, который и будет проверять все зависимости.

## 4. Диагностика и проверка

### 4.1. Базовая диагностика

1.  **Проверка VIP:**
    На активном узле (MASTER) команда `ip a` или `ip addr show <interface>` покажет виртуальный IP на указанном интерфейсе. На `BACKUP` узле его быть не должно.
    ```shell
    $ ip addr show enp1s0
    ...
        inet 192.168.1.101/24 brd 192.168.1.255 scope global enp1s0
        inet 192.168.1.100/24 scope global secondary enp1s0
    ...
    ```

2.  **Проверка логов Keepalived:**
    Изучите статус и логи сервиса, чтобы увидеть переходы состояний (`Entering MASTER STATE`, `Entering BACKUP STATE`).
    ```shell
    sudo systemctl status keepalived
    journalctl -u keepalived -f
    ```
    В логах также будет видно, почему изменился приоритет (например, из-за падения/поднятия `chk_angie` скрипта).

3.  **Проверка ответа от VIP:**
    С любой машины в той же L2-сети выполните `curl` к виртуальному IP. Если вы настроили заголовок `X-Front-Node`, вы увидите, какой узел ответил.
    ```shell
    curl -I http://192.168.1.100
    ```
    ```
    HTTP/1.1 200 OK
    Server: nginx/1.25.5
    ...
    X-Front-Node: master
    ```

### 4.2. Тестирование переключения

#### Сценарии отказа

-   **Остановка Angie на `MASTER` узле:** `sudo systemctl stop angie`
    -   Keepalived должен обнаружить это через `chk_angie` скрипт, понизить приоритет, и `BACKUP` узел захватит VIP. Через несколько секунд `curl` на VIP покажет `X-Front-Node: backup`.
-   **Остановка Keepalived на `MASTER` узле:** `sudo systemctl stop keepalived`
    -   `BACKUP` узел перестанет получать VRRP-анонсы и почти мгновенно захватит VIP.
-   **Полное выключение `MASTER` узла.**

При восстановлении сервиса `angie` на `MASTER` узле, он должен забрать VIP обратно (если не включен `nopreempt`).

#### Измерение времени простоя

1.  **Flood Ping:**
    Запускает `ping` с максимальной частотой. Каждая `.` — это потерянный пакет. Позволяет визуально оценить время недоступности VIP.
    ```shell
    # Требует sudo
    sudo ping -f 192.168.1.100
    ```
    Во время переключения вы увидите короткую серию потерянных пакетов.

2.  **Нагрузочное тестирование с Apache Bench (`ab`):**
    Эта утилита позволяет направить большое количество запросов и посчитать количество ошибок.
    ```shell
    # -c 10: 10 одновременных подключений
    # -n 100000: 100 000 запросов всего
    # -k: использовать Keep-Alive соединения
    ab -c 10 -n 100000 -k http://192.168.1.100/
    ```
    Запустите тест и во время его выполнения инициируйте один из сценариев отказа. В конце отчета `ab` посмотрите на `Failed requests`. В рабочем кластере их число должно быть очень небольшим (единицы), что говорит о быстром и корректном переключении.

## 5. Важные моменты и ограничения

-   **Требования к сети (L2-сегмент):** Все узлы кластера Keepalived должны находиться в одном L2-сегменте сети (в одной широковещательной домене), чтобы VRRP-анонсы (мультикаст-пакеты) могли быть успешно доставлены между ними.
-   **Split-Brain:** Это классическая проблема кластерных систем, когда узлы теряют связь друг с другом и оба решают, что они `MASTER`, захватывая VIP. Это приводит к конфликту IP-адресов. Использование не менее 3-х узлов и механизмов кворума (в более сложных системах, таких как Pacemaker) снижает этот риск.
-   **Preemption (вытеснение):**
    - По умолчанию, когда `MASTER` восстанавливается, он "отбирает" VIP обратно, так как его приоритет выше. Это вызывает дополнительное переключение.
    - Чтобы этого избежать, в `vrrp_instance` на `BACKUP` узлах можно добавить директиву `nopreempt`. В этом случае, если `BACKUP` стал мастером, он останется им, пока сам не выйдет из строя, даже если "главный" `MASTER` вернулся в строй. Это минимизирует количество переключений.
-   **Версии VRRP:**
    - Классическая конфигурация, описанная здесь, использует **VRRPv2**.
    - Если вам требуется поддержка **IPv6** или более точные тайм-ауты (в долях секунды), следует использовать **VRRPv3**, который также поддерживается Keepalived.

### 5.1. Синхронизация конфигураций и состояния

Keepalived отвечает только за "миграцию" IP-адреса. Он **не синхронизирует** данные между узлами.

-   **Конфигурация Angie:** Конфигурационные файлы Angie на всех узлах кластера должны быть идентичны. Для их синхронизации необходимо использовать внешние инструменты:
    -   Системы управления конфигурациями: **Ansible**, Puppet, Chef.
    -   Простая синхронизация через **`rsync`**.
    -   Специализированные инструменты, такие как **`angie-sync`** (или `nginx-sync` от F5/Nginx), которые отслеживают изменения в конфигурации на мастер-сервере и автоматически распространяют их на остальные узлы кластера.
-   **SSL-сертификаты:** Сертификаты также должны быть идентичны на всех узлах. Рекомендуется использовать автоматизированные средства их получения и распространения, например, Certbot с **DNS-аутентификацией**, что упрощает их развертывание сразу на всех серверах кластера.
-   **Состояние сессий:** В данном решении не синхронизируется состояние (например, установленные TCP-соединения). При переключении все активные соединения с бывшим `MASTER` будут разорваны, и клиентам потребуется переподключиться к VIP, попав уже на новый `MASTER`. Для L7-трафика (HTTP) это обычно не является проблемой, так как браузеры автоматически переподключаются.
