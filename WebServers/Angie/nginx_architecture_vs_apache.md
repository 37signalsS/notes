# Архитектура Nginx и проблема C10k (в сравнении с Apache)

Понимание ключевых архитектурных отличий Nginx от классических веб-серверов, таких как Apache, объясняет, почему Nginx (и его форк Angie) так эффективно справляются с высокой нагрузкой. Основа этого отличия лежит в решении так называемой **"проблемы C10k"** — задачи обслуживания 10 000 одновременных соединений.

## 1. Классическая модель Apache: Процесс на соединение (`pre-fork`)

В конце 1990-х и начале 2000-х годов, когда зарождался Nginx, серверное оборудование было значительно слабее: один процессор и десятки или сотни мегабайт оперативной памяти.

В этих условиях доминировал веб-сервер Apache со своей стандартной моделью обработки соединений `mpm_prefork`:

-   **Один процесс на одно соединение:** На каждое активное подключение от клиента Apache выделял отдельный рабочий процесс (worker process).
-   **Высокое потребление памяти:** Каждый такой процесс потреблял значительное количество оперативной памяти (несколько мегабайт, а с подключенным модулем PHP или Perl — десятки мегабайт).
-   **Проблема "медленных клиентов":** Клиент с медленным интернет-соединением (например, Dial-up) мог открыть несколько соединений для загрузки страницы и надолго "занять" соответствующее количество рабочих процессов, даже если большую часть времени он ничего не передавал, а просто поддерживал соединение (`keep-alive`).

**Результат:**
При росте количества одновременных пользователей (и, соответственно, соединений) сервер быстро исчерпывал оперативную память. Обслужить 10 000 соединений в такой модели было практически невозможно — это требовало бы гигантского, по меркам того времени, объема ОЗУ.

```
      Клиент 1 (6 соед.)     Клиент 2 (6 соед.)     ...     Клиент N
            | | | | | |           | | | | | |
      +-----+-----+-----+     +-----+-----+-----+
      | Apache Worker |     | Apache Worker |     ... (Тысячи процессов)
      +---------------+     +---------------+
 (занимает десятки МБ ОЗУ, даже если простаивает)
```

Хотя в современных версиях Apache появились другие, более эффективные модели (`event`, `worker`), исторически именно `pre-fork` был стандартом и являлся узким местом. К тому же, популярный модуль `mod_php` мог работать только в этой модели.

## 2. Модель Nginx: Асинхронность и управление событиями

Nginx был спроектирован с нуля для решения проблемы C10k. Его архитектура основана на **асинхронной, событийно-ориентированной модели (event-driven)**.

-   **Один рабочий процесс на множество соединений:** Один рабочий процесс Nginx может эффективно обслуживать тысячи одновременных соединений.
-   **Неблокирующие операции:** Nginx использует неблокирующий ввод-вывод. Когда рабочий процесс ожидает данных от клиента или ответа от бэкенда, он не "зависает", а немедленно переключается на обработку событий от других соединений.
-   **Минимальное потребление ресурсов:** Поскольку не нужно создавать отдельный процесс или поток на каждое соединение, потребление памяти и ресурсов процессора минимально. Рабочие процессы заняты только тогда, когда действительно нужно что-то делать (читать/писать данные).

**Результат:**
Nginx способен обслуживать десятки и сотни тысяч одновременных соединений на том же оборудовании, где Apache "умер" бы уже на нескольких тысячах.

```
      Клиент 1  Клиент 2  ...  Клиент 10000+
          \       |       /         |
           \      |      /          |
      +-----------------------------------------+
      |        Один Worker-процесс Nginx        |
      | (обрабатывает тысячи соед. асинхронно) |
      +-----------------------------------------+
 (потребляет фиксированное, предсказуемое кол-во ОЗУ)
```

### Динамический контент

Важно понимать, что Nginx по своей природе не исполняет динамический контент (как Apache с `mod_php`). Его задача — быть высокопроизводительным **прокси-сервером**.

-   **Статика:** Отдает статические файлы (HTML, CSS, JS, изображения) напрямую и очень быстро.
-   **Динамика:** Для динамических запросов Nginx проксирует запрос на специализированный бэкенд (например, PHP-FPM, Gunicorn, uWSGI), эффективно ожидая ответа и передавая его клиенту.

Таким образом, утверждение "Apache лучше для динамики, а Nginx для статики" не совсем корректно. Nginx превосходно справляется с **управлением соединениями** для *любого* типа контента, просто для динамики он выступает в роли умного и быстрого посредника.
