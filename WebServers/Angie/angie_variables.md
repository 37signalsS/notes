# Переменные в Angie

## Определения

**Переменные (variables)** — механизм хранения и передачи данных внутри конфигурации Angie, доступный на уровне `http`. Переменные представляют собой именованные строковые значения, которые используются различными модулями для динамической настройки поведения сервера: форматирования логов, маршрутизации, проксирования, блокировки и других задач.

Переменные Angie обладают следующими свойствами:
*   **Тип данных:** Всегда строки. Любое значение, включая числа и булевы операции, хранится как текст.
*   **Область видимости:** Глобальные в пределах одного запроса. Переменные, установленные в любом контексте (location, server), доступны во всех директивах, поддерживающих переменные.
*   **Источники:** Встроенные переменные (устанавливаются модулями автоматически) и пользовательские (определяются через `map`, `set`, `geo` и другие директивы).

> **Важно:** Не все директивы Angie поддерживают переменные. Если директива поддерживает переменные, это явно указано в её документации.

## Базовые концепции

### Встроенные переменные

Angie (и его прародитель [Nginx](../Nginx/Core/nginx_overview.md)) предоставляют обширный набор встроенных переменных, которые заполняются автоматически на основе параметров запроса и контекста выполнения.

**Наиболее используемые переменные:**

| Переменная | Описание |
| :--- | :--- |
| `$host` | Имя хоста из запроса (с учётом `Host` или `server_name`). |
| `$uri` | Текущий нормализованный URI (изменяется при `rewrite`). |
| `$request_uri` | Оригинальный URI запроса (не изменяется). |
| `$remote_addr` | IP-адрес клиента. |
| `$request_method` | HTTP-метод (GET, POST и т.д.). |
| `$args` | Строка запроса (query string). |
| `$scheme` | Протокол запроса (http или https). |
| `$request_id` | Уникальный идентификатор запроса (для трассировки). |
| `$request_time` | Время обработки запроса (в секундах с миллисекундами). |

### Шаблонные переменные HTTP-заголовков

Любой HTTP-заголовок клиента доступен как переменная с префиксом `$http_`. Имя переменной формируется путём замены дефисов на подчёркивания и перевода в нижний регистр.

```nginx
# Доступ к заголовку User-Agent:
$http_user_agent

# Доступ к заголовку X-Forwarded-For:
$http_x_forwarded_for

# Доступ к произвольному заголовку X-Custom-Header:
$http_x_custom_header
```

Этот механизм позволяет работать с любыми заголовками без необходимости их предварительного объявления.

### Директивы и переменные Angie (расширения Nginx)

Angie расширяет базовый набор переменных Nginx для поддержки специфичных для версии 1.x функций: mTLS, метрик, Kernel TLS и динамических путей к сертификатам.

| Переменная / Директива | Описание |
| :--- | :--- |
| `$ssl_client_verify` | Результат проверки клиентского сертификата (`SUCCESS`, `FAILED:reason`, `NONE`). |
| `$ssl_client_s_dn` | Distinguished Name субъекта клиентского сертификата. |
| `$ssl_client_i_dn` | Distinguished Name издателя (CA) клиентского сертификата. |
| `$ssl_client_s_dn_cn` | Common Name из DN субъекта. |
| `$ssl_client_serial` | Серийный номер клиентского сертификата. |
| `$ssl_client_v_remain` | Количество дней до истечения срока действия. |
| `$ssl_client_v_start` | Дата начала действия. |
| `$ssl_client_v_end` | Дата окончания действия. |
| `$ssl_client_sigalg` | Алгоритм подписи (`sha384WithRSAEncryption`). |
| `$ssl_client_raw_cert` | Полный текст сертификата в формате PEM. |
| `$binary_remote_addr` | IP-адрес клиента в бинарном формате (~4 байта для IPv4). Используется для зон `limit_req_zone` и `limit_conn_zone` для экономии памяти. |
| `$connection_serial` | Уникальный серийный номер соединения в рамках worker'а. Полезен для дедупликации за NAT. |
| `$connection` | ID соединения. |
| `$connection_id` | Уникальный идентификатор соединения. |

> **Примечание:** Полный список переменных зависит от загруженных модулей. Для просмотра доступных переменных используйте `angie -V` или конфигурацию с `log_format`.

Полные примеры конфигурации mTLS и переменных клиентских сертификатов см. в [Взаимная аутентификация клиентов (mTLS) в Angie](./angie_client_cert_auth.md).

## Практические сценарии

### 1. Переменные в формате логов

Логирование — одно из наиболее распространённых применений переменных. Формат лога определяется через набор переменных, которые подставляются в строку `log_format`.

Переменные для анализа [апстримов](./angie_reverse_proxy.md):
*   `$upstream_addr` — адрес бэкенд-сервера.
*   `$upstream_status` — HTTP-статус ответа от апстрима.
*   `$upstream_response_time` — время ответа апстрима.
*   `$upstream_cache_status` — результат работы кэша (`HIT`, `MISS`, `EXPIRED`).
*   `$request_time` — полное время обработки запроса (в секундах с миллисекундами).

Полные примеры настройки форматов логов, включая `extended` и JSON, см. в [Логирование в Angie](./angie_logging.md).

### 2. Ключи кэширования

Ключ кэширования определяет, по каким параметрам запроса происходит группировка кэшированных ответов. Использование переменных в `proxy_cache_key` позволяет корректно кэшировать контент для разных пользователей и протоколов.

```nginx
# Пример: кэширование с учётом протокола и заголовка (для балансировщиков)
proxy_cache_key "$scheme$request_method$host$request_uri$http_x_forwarded_proto";
```

Подробнее: [Настройка прокси-кэширования](../Nginx/Performance/Caching/proxy_caching.md).

### 3. Установка заголовков ответа

Директива `add_header` поддерживает переменные в значении, что позволяет формировать динамические заголовки. Переменные можно смешивать с обычным текстом.

```nginx
server {
    # Заголовок с переменными, смешанными с текстом
    add_header X-Request-URI "Requested: $request_uri" always;
    add_header X-Client-IP "Real IP: $remote_addr" always;

    location / {
        proxy_pass http://backend;
    }
}
```

Проверка установленных заголовков:
```bash
curl -I http://localhost/
# → X-Request-URI: Requested: /
# → X-Client-IP: Real IP: 127.0.0.1
```

### 4. Пользовательские переменные через `map`

Директива `map` — основной инструмент создания пользовательских переменных на основе значений других переменных. Определяется в контексте `http`.

**Синтаксис:**
```nginx
http {
    map $source_variable $target_variable {
        default       значение_по_умолчанию;
        значение_1    результат_1;
        значение_2    результат_2;
    }
}
```

**Ключевые особенности:**
*   Значения вычисляются **лениво** — только в момент первого обращения к `$target_variable`.
*   Значения **кэшируются** на весь запрос (по умолчанию).
*   Разделитель значений — точка с запятой.

**Регулярные выражения:**
```nginx
http {
    map $http_user_agent $limit_search_bots {
        default                         0;    # Значение по умолчанию
        "~*(Google|Bing|Yandex|MJ12bot)" 1;   # Регулярка с игнорированием регистра (~*)
        "~*bot"                         2;    # Подстрока "bot"
    }
}
```

*   `~*` — регулярное выражение без учёта регистра.
*   `~` — регулярное выражение с учётом регистра.
*   Отсутствие префикса — точное совпадение строки.

### 5. Условные блоки `if`

Переменные, созданные через `map`, используются в условиях для принятия решений. Блок `if` работает корректно с директивами модуля `rewrite` (например, `return`, `rewrite ... last/break`).

```nginx
http {
    map $http_user_agent $limit_search_bots {
        default                         0;
        "~*(Google|Bing|Yandex)"        1;
        "~*bot"                         2;
    }
}

server {
    # Блок mod_rewrite — безопасное использование if
    if ($limit_search_bots) {
        return 403;
    }

    location / {
        proxy_pass http://backend;
    }
}
```

Проверка:
```bash
curl -I -A "Googlebot/2.1" http://localhost/
# → HTTP/1.1 403 Forbidden (бот заблокирован)
```

Подробнее о безопасном использовании `if` см. [Перенаправления и перезапись URI в Angie](./angie_redirects_and_rewrites.md).

### 6. Хранение списков во внешних файлах (`include`)

Для объёмных списков (редиректов, блокировок, белых списков) директива `map` поддерживает подключение внешних файлов через `include`.

**Файл со списком (`/etc/angie/maps/redirects.map`):**
```text
# Синтаксис: источник значение
/old-page1      /new-page1
/old-page2      /new-page2
~^/blog/(.*)$   /articles/$1
```

**Конфигурация:**
```nginx
http {
    map $uri $redirect_target {
        default "";                    # Пустое значение = нет редиректа
        include /etc/angie/maps/redirects.map;
    }
}

server {
    if ($redirect_target) {
        return 301 $redirect_target;
    }
}
```

### 7. Параметр `volatile` — отключение кэширования переменных

По умолчанию переменные вычисляются один раз за запрос и кэшируются. Параметр `volatile` отключает это поведение, позволяя переменной пересчитываться при каждом обращении. Это необходимо, если переменная должна изменяться в результате редиректа или внутреннего перенаправления.

**Сценарий:** переменная зависит от URI, который изменяется в процессе обработки.

```nginx
http {
    map $uri $test {
        default     0;
        /test       1;
        /ddd        2;
    }
}
```

**Без `volatile` (значение кэшируется):**
```nginx
server {
    location /test {
        # URI меняется на /ddd, но переменная $test останется = 1
        return 302 /ddd;
    }

    location /ddd {
        add_header X-Test $test;
        return 200 "Value: $test";
    }
}
# → X-Test: 1 (кэшированное значение с первого вычисления)
```

**С `volatile` (пересчёт при каждом обращении):**
```nginx
http {
    map $uri $test volatile {
        default     0;
        /test       1;
        /ddd        2;
    }
}

server {
    location /test {
        return 302 /ddd;
    }

    location /ddd {
        add_header X-Test $test;
        return 200 "Value: $test";
    }
}
# → X-Test: 2 (переменная пересчитана для нового URI /ddd)
```

> **Внимание:** Использование `volatile` увеличивает нагрузку на сервер за счёт повторного вычисления. Применяйте только при необходимости.

### 8. Динамический выбор upstream

Переменные позволяют выбирать бэкенд-сервер динамически, на основе параметров запроса, что устраняет необходимость создания отдельных `location` для каждого сценария.

**Определение переменной:**
```nginx
http {
    map $uri $host_dest {
        default     backend_default;
        /api        backend_api;
        /admin      backend_admin;
    }
}
```

**Использование в upstream:**
```nginx
upstream backend_default {
    server 10.0.0.1:8080;
}

upstream backend_api {
    server 10.0.0.2:8080;
}

upstream backend_admin {
    server 10.0.0.3:8080;
}

server {
    location / {
        proxy_pass http://$host_dest;
    }
}
```

Одна конфигурация обслуживает несколько upstream-групп, выбирая нужную на основе URI или другой переменной.

### 9. Geo-модуль: переменные по IP-адресу

Модуль `ngx_http_geo_module` определяет переменные на основе IP-адреса клиента (или другой переменной, содержащей IP).

**Определение в контексте `http`:**
```nginx
http {
    geo $block_access {
        default     0;      # Разрешить по умолчанию
        192.168.1.0/24  1;  # Заблокировать подсеть
        10.0.0.0/8      1;  # Заблокировать диапазон
        203.0.113.5     1;  # Заблокировать конкретный IP
    }
}
```

**Использование в серверном блоке:**
```nginx
server {
    if ($block_access) {
        return 403;
    }

    location / {
        proxy_pass http://backend;
    }
}
```

**Работа с другой переменной (не `remote_addr`):**
Geo-модуль может принимать второй аргумент для чтения IP из другой переменной (например, из заголовка `X-Forwarded-For`):

```nginx
http {
    geo $real_client_ip {
        default     0;
        10.0.0.0/8  1;
    }
    # $real_client_ip определяется по $http_x_forwarded_for
}

# Использование в логе или условиях:
log_format geo '$remote_addr ($real_client_ip) - $request';
```

**Комбинирование geo и map для GeoIP-блокировки:**
```nginx
http {
    geoip2 /etc/angie/geo/Country.mmdb {
        $geoip2_country_code default=RU country iso_code;
    }

    map $geoip2_country_code $is_blocked {
        default     0;
        CN          1;    # Блокировка по коду страны
        IR          1;
    }
}

server {
    if ($is_blocked) {
        return 403;
    }
}
```

## Операции и команды

### Диагностика переменных через логи

Самый надёжный способ проверить подстановку переменной — вывод в access_log или error_log.

```bash
# Проверка подстановки заголовка User-Agent
curl -A "TestBot/1.0" -s http://localhost/ -I
# → X-Request-URI: Requested: /

# Проверка значения переменной в access_log
tail -F /var/log/angie/access.log | grep TestBot
# → 127.0.0.1 - - [21/Sep/2026:16:00:00 +0000] "GET / HTTP/1.1" 200 612 "-" "TestBot/1.0" ...
```

### Проверка разрешения переменных через `set`

Директива `set` может использоваться для отладки — присвойте переменной значение и верните его в заголовке ответа:

```nginx
http {
    map $http_user_agent $ua_category {
        default "unknown";
        "~*bot" "bot";
        "~*curl" "tool";
    }

    server {
        listen 8080;

        location / {
            set $debug_ua $ua_category;
            add_header X-Debug-UA $debug_ua always;
            return 200 "OK";
        }
    }
}
```

```bash
curl -A "curl/8.0" -s -I http://localhost:8080/
# → X-Debug-UA: tool
```

### Проверка метрик через API модуля `metric`

Модуль `metric` (Angie 1.11+) позволяет проверять значения переменных через эндпоинты API:

```bash
# Проверка появления ключей в зоне метрик
curl -s http://localhost:8888/status/http/metric_zones/browsers/metrics/ | jq keys
# → ["Chrome/120.0", "Firefox/121.0", ...]

# Проверка конкретного ключа
curl -s http://localhost:8888/status/http/metric_zones/browsers/metrics/Chrome/ | jq .
# → {"count": 5432}
```

### Проверка переменных SSL-сертификатов (mTLS)

Для проверки переменных клиентского сертификата используйте `add_header` в отладочном конфиге:

```nginx
server {
    listen 443 ssl;
    ssl_client_certificate /etc/angie/ssl/ca.crt;
    ssl_verify_client on;

    location / {
        add_header X-SSL-Client-Verify $ssl_client_verify always;
        add_header X-SSL-Client-S-DN $ssl_client_s_dn always;
        return 200 "OK";
    }
}
```

```bash
curl --cacert /etc/angie/ssl/ca.crt --cert client.pem https://localhost/
# → X-SSL-Client-Verify: SUCCESS
# → X-SSL-Client-S-DN: CN=client, O=internal, C=RU
```

### Проверка переменных в `limit_req_zone` и `limit_conn_zone`

```bash
# Проверка статуса зоны через API
curl -s http://localhost/api/v1/http/limit_reqs/api_cluster | jq .
# → {"zone":"api_cluster","passes":1024,"delayed":512,"rejected":128,...}
```

## Устранение неисправностей

### Переменная не разрешается (пустое значение)

**Симптом:** переменная в `log_format`, `add_header` или `map` подставляется как пустая строка.

**Возможные причины:**
- Переменная не поддерживается в используемой директиве.
- Переменная устанавливается после `rewrite` без `break`/`last`, и значение не сохраняется.
- В заголовке запроса нет ожидаемого значения (например, `$http_x_forwarded_for` пуст при прямом подключении).

**Диагностика:**
```bash
# Проверка заголовков запроса
curl -v http://localhost/ 2>&1 | grep -i "x-forwarded-for\|user-agent"

# Проверка access_log на пустые значения
awk '{print $0}' /var/log/angie/access.log | grep -E ' - - '
```

**Решение:**
- Убедитесь, что директива поддерживает переменные (см. документацию модуля).
- Добавьте `set $var ""` перед использованием для гарантии пустого значения по умолчанию.
- Используйте `default` в `map` для обработки отсутствующих значений.

### Значение переменной не обновляется после rewrite

**Симптом:** после внутреннего перенаправления переменная содержит устаревшее значение.

**Диагностика:**
```bash
# Проверка значения переменной после rewrite
curl -s http://localhost/test -I
# → X-Test: 1 (устаревшее значение)
```

**Решение:**
- Добавьте параметр `volatile` в `map` для переменной, которая должна пересчитываться.
- Убедитесь, что `rewrite` завершается флагом `break` или `last`.

### `ssl_certificate_cache` возвращает устаревший сертификат

**Симптом:** после обновления сертификата на диске Angie продолжает использовать старый.

**Возможные причины:**
- Кэш `ssl_certificate_cache` не сброшен.
- Переменная в пути к сертификату не изменилась (кэш привязан к ключу).

**Решение:**
```bash
# Сброс кэша SSL-сертификатов
sudo angie -s stop && sudo rm -rf /var/cache/angie/ssl/* && sudo angie

# Проверка
sudo angie -T | grep ssl_certificate_cache
# → показывает размер и TTL кэша
```

### Зона метрик модуля `metric` пустая (0 ключей)

**Симптом:** `metric_zone` зарегистрирована, но в ней нет ключей.

**Диагностика:**
```bash
# Проверка размера зоны
curl -s http://localhost:8888/status/http/metric_zones/browsers/ | jq .
# → {"zone":"browsers","size":2097152,"used":0,"keys":0,...}
```

**Возможные причины:**
- Переменная, передаваемая в `metric`, пустая.
- `on=request` / `on=end` указан неверно для контекста.
- Директива `metric` расположена в блоке, который не выполняется.

**Решение:**
- Проверьте, что переменная содержит значение: `curl -A "Test" http://localhost/` и проверьте лог.
- Убедитесь, что `metric` стоит внутри `location`, который обслуживает запросы.
- Используйте `metric on=request` для отладки заголовков, `on=end` для времени ответа.

### Переменная содержит специальные символы, которые ломают конфиг

**Симптом:** `angie -t` возвращает ошибку после добавления переменной.

**Возможные причины:**
- В значении переменной есть неэкранированные двойные кавычки.
- Значение содержит пробелы без кавычек.

**Решение:**
```nginx
# Правильно: значение в кавычках
add_header X-Custom "Value: $request_uri";

# Неправильно: пробелы без кавычек
add_header X-Custom Value: $request_uri;
```

### Переменная не поддерживается в директиве

**Симптом:** `angie -t` возвращает ошибку `"variable" is not allowed here` или переменная игнорируется.

**Решение:**
- Проверьте документацию директивы — не все директивы поддерживают переменные.
- Если директива не поддерживает переменные напрямую, используйте `set` для присвоения значения в поддерживаемом контексте.

### Высокое потребление памяти при использовании `map` с регулярными выражениями

**Симптом:** после добавления `map` с большим количеством регулярок память worker'а растёт.

**Решение:**
- Упростите регулярные выражения или замените их на точное совпадение.
- Используйте `map` с `default` в начале списка для быстрого попадания.
- Ограничьте количество уникальных значений переменной.

## Лучшие практики

### Безопасность

1. **Не логируйте чувствительные данные:** избегайте вывода `Authorization`, `Cookie`, `X-Forwarded-For` в access_log, если в них есть секретные токены. Используйте `map` для маскировки:

```nginx
http {
    map $http_authorization $auth_masked {
        default "";
        "~*." "***";
    }

    log_format main '$remote_addr - $http_x_forwarded_for [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" "$auth_masked"';
}
```

2. **Ограничьте доступ к эндпоинтам метрик:** модуль `metric` раскрывает топологию и нагрузки. Минимальная конфигурация:

```nginx
location = /status/http/metric_zones/ {
    allow 10.0.10.5;
    deny all;
}
```

3. **Используйте TLS** при доступе к метрикам через ненадёжные каналы.

### Производительность

1. **Избегайте `volatile` без необходимости:** параметр отключает кэширование переменной и увеличивает нагрузку на CPU.

2. **Используйте `$binary_remote_addr` для зон rate limiting:** бинарный формат (~4 байта) экономит память по сравнению с текстовым IP.

```nginx
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
```

3. **Ограничьте длину ключей в `map`:** длинные значения потребляют больше памяти в разделяемой зоне.

4. **Используйте `ssl_certificate_cache`** при работе с переменными в путях к сертификатам:

```nginx
http {
    ssl_certificate_cache max=1000 inactive=10m;

    server {
        listen 443 ssl;
        set $dynamic_cert "/etc/angie/ssl/$server_name/fullchain.pem";
        ssl_certificate $dynamic_cert;
    }
}
```

5. **Ограничьте кардинальность в метриках:** уникальные ключи >10 000 в зоне `metric_zone` потребляют много памяти. Используйте агрегацию или обрезку:

```nginx
map $http_user_agent $ua_short {
    default "other";
    "~*Chrome" "chrome";
    "~*Firefox" "firefox";
    "~*Safari" "safari";
}
```

### Эксплуатация

1. **Используйте `map` вместо множества `if`:** `map` вычисляется лениво и кэшируется на весь запрос.

2. **Проверяйте переменные после изменений:** используйте `curl` с отладкой заголовков для подтверждения подстановки.

3. **Именование переменных:** используйте осмысленные имена (`$ua_category`, `$block_access`) вместо необработанных значений (`$http_user_agent`).

4. **Верификация конфигурации:** всегда запускайте `angie -t` после добавления новых переменных.

5. **Ограничьте длину значений переменных:** некоторые директивы (например, `add_header`) имеют ограничения на длину значения.

## Дополнительная информация

### Экранирование знака доллара

В директивах, поддерживающих переменные, любой символ `$` интерпретируется как начало имени переменной. Чтобы вставить литеральный знак доллара, используйте `map` для определения переменной со значением `$`:

```nginx
http {
    map $uri $dollar {
        default $;
    }
}

server {
    # $dollar будет интерпретирован как литеральный символ "$"
    add_header X-Test "Price: 100$dollar";
}
```

Это стандартный приём, поскольку прямая подстановка `$` в директивах невозможна.

### Использование переменных в директивах модуля `rewrite`

Блок `if` модуля `rewrite` — единственное безопасное место для использования `if` внутри `location`. Внутри допустимы только директивы модуля `rewrite` (`return`, `rewrite ... last/break`).

Подробнее о стадиях обработки запроса и модулях см. [Перенаправления и перезапись URI в Angie](./angie_redirects_and_rewrites.md).

### Логирование с переменными для мониторинга

Для условного логирования (например, только медленные запросы) используйте `map` с параметром `if` директивы `access_log`. Подробные примеры и сценарии см. в [Логирование в Angie: Условное логирование](./angie_logging.md#условное-логирование).

### Мониторинг переменных через модуль metrics

Angie (1.11+) позволяет собирать агрегированную статистику по любым переменным через модуль `metric`. Подробнее: [Мониторинг: пользовательские метрики](./angie_monitoring/angie_monitoring_custom_metrics.md).
