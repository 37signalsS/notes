# Динамические группы проксируемых серверов в Angie

## Определения

- **Upstream (группа вышестоящих серверов)** — именованная группа бэкенд-серверов, между которыми балансировщик распределяет входящие запросы.
- **Динамический Upstream** — группа серверов, состав которой (IP-адреса, порты, веса) обновляется автоматически без перезагрузки конфигурации (`reload`).
- **Обнаружение сервисов (Service Discovery)** — процесс автоматического поиска адресов экземпляров сервисов в распределённой сети (DNS, Docker API, Consul).

## Базовые концепции

В современных [микросервисных архитектурах](../../Concepts/monolith_vs_microservices.md) экземпляры приложений постоянно создаются и уничтожаются. Использование статически прописанных IP-адресов в конфигурации балансировщика приводит к ошибкам при изменении инфраструктуры.

Angie поддерживает три основных способа реализации динамических апстримов:
1.  **Обнаружение через DNS:** разрешение имен по расписанию (A/AAAA) или через SRV-записи.
2.  **Интеграция с контейнерами:** автоматическое отслеживание изменений через Docker API (labels).
3.  **Динамическое API (Angie Pro):** добавление и удаление серверов через HTTP-запросы в реальном времени.

**Важное требование:** Любой динамический апстрим требует описания зоны разделяемой памяти (`zone`), где Angie хранит текущее состояние группы серверов для всех рабочих процессов.

## Практические сценарии

### Сценарий 1: Динамическое разрешение DNS (A/AAAA)

Метод эффективен для облачных сред и Kubernetes, где IP-адреса сервисов могут меняться, а имена остаются постоянными.

```nginx
http {
    # Резолвер обязателен для работы параметра resolve
    resolver 1.1.1.1 valid=10s;

    upstream backend {
        zone backend 64k;
        # Параметр resolve заставляет Angie периодически обновлять IP
        server backend.example.com resolve;
    }
}
```

### Сценарий 2: Использование DNS SRV-записей

Стандартный способ интеграции с [Consul](../../Consul/consul_overview.md). SRV-записи передают не только IP, но и порты, веса и приоритеты.

```nginx
http {
    resolver 10.0.0.1;

    upstream cluster {
        zone cluster 128k;
        # Использование SRV-записей через параметр service
        server backend.local resolve service=http;
    }
}
```

### Сценарий 3: Интеграция с Docker Labels

Angie умеет напрямую опрашивать Docker API и формировать апстрим на основе меток контейнеров. Это избавляет от необходимости настройки DNS-сервера внутри инфраструктуры.

**Конфигурация Docker (labels):**
```yaml
labels:
  - "angie.http.upstreams.webapp.server=app_container:8080"
  - "angie.http.upstreams.webapp.weight=5"
```

**Конфигурация Angie:**
```nginx
http {
    # Путь к сокету Docker
    docker endpoint unix:/var/run/docker.sock;

    upstream webapp {
        zone webapp 64k;
        # Серверы добавляются автоматически
    }
}
```

### Сценарий 4: Управление через API и персистентность (Angie Pro)

В коммерческой версии возможно полное управление составом группы через HTTP API. Для сохранения изменений после перезагрузки используется директива `state`.

```nginx
upstream dynamic_api {
    zone dynamic_api 1m;
    # Путь к файлу для сохранения состояния между рестартами
    state /var/lib/angie/state/dynamic_api.state;
}
```

## Дополнительная информация

### Мониторинг и отладка
Текущее состояние всех динамических апстримов (активные серверы, ошибки, задержки) доступно в реальном времени через [Console Lite](./angie_monitoring/angie_monitoring_console.md) или в формате JSON через эндпоинт `/status/upstreams`.

### Ограничения
*   Для DNS-разрешения необходимо гарантировать доступность и скорость работы резолвера.
*   Директива `state` требует отсутствия статических `server` в блоке `upstream`.
