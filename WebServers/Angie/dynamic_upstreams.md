# Динамические группы проксируемых серверов в Angie

В Angie, как и в Nginx, можно определять группы вышестоящих серверов (апстримов) не только статически, но и динамически. Это позволяет изменять состав бэкенд-серверов без перезагрузки конфигурации, что особенно полезно в облачных и контейнеризированных средах.

Существует несколько подходов для реализации этой функциональности.

## 1. Использование DNS A-записей

Самый простой способ — использовать DNS. За одной DNS A-записью можно закрепить несколько IP-адресов. Angie будет периодически опрашивать DNS-сервер и обновлять список серверов в апстриме.

### Конфигурация

Для этого в контексте `http` необходимо указать `resolver` (адрес DNS-сервера) и в блоке `upstream` использовать доменное имя с параметром `resolve`.

```nginx
# /etc/nginx/nginx.conf

http {
    # ...
    
    resolver 1.1.1.1 valid=5s; # Указываем адрес DNS-сервера, valid - время кеширования ответа

    upstream backend {
        zone backend 64k;
        server backend.example.com resolve; # Angie будет динамически разрешать это имя
        # status_zone backend_status; # Опционально: зона для мониторинга в Angie Console Light
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend;
        }
    }
    # ...
}
```

**Ключевые моменты:**
- `resolver`: Определяет DNS-сервер, который Angie будет использовать для разрешения имен.
- `resolve`: Флаг, который указывает Angie периодически переопределять DNS-имя в IP-адреса. Время кеширования ответа (TTL) берется из самой DNS-записи.

Этот метод прост, но имеет ограничения: нельзя управлять портами, весами или другими параметрами для каждого отдельного сервера.

Стоит отметить, что эта функциональность, ранее доступная только в коммерческой версии Nginx Plus, была реализована в open-source версии Angie с самого начала. Впоследствии она появилась и в open-source версии Nginx, что делает ее сейчас доступной в обеих системах.

## 2. Использование DNS SRV-записей

Более гибкий метод — использование SRV-записей в DNS. SRV-записи (Service records) позволяют для одной службы указать не только хост, но и порт, вес и приоритет для каждого сервера.

### Конфигурация Angie

Конфигурация Angie похожа на предыдущий метод, но в директиве `server` добавляется параметр `service`, указывающий на имя службы.

```nginx
# /etc/nginx/nginx.conf

http {
    # ...
    
    resolver 10.0.0.1; # Локальный или корпоративный DNS

    upstream backend_srv {
        zone backend_srv 64k;
        server backend.local.lan resolve service=http; # Ищем SRV-запись для службы http
    }
    # ...
}
```

### Конфигурация DNS (на примере BIND)

В файле зоны DNS необходимо создать SRV-записи. Формат записи: `_service._proto.name. TTL class SRV priority weight port target.`

```text
; Файл зоны для local.lan

; ... другие записи

; SRV-записи для нашего бэкенда
; _http._tcp.backend.local.lan.
_http._tcp.backend.local.lan. 60 IN SRV 10 2 9001 server1.local.lan.
_http._tcp.backend.local.lan. 60 IN SRV 10 1 9002 server2.local.lan.
_http._tcp.backend.local.lan. 60 IN SRV 20 1 9003 server3.local.lan. ; Резервный сервер

; A-записи для хостов
server1.local.lan. 60 IN A 127.0.0.1
server2.local.lan. 60 IN A 127.0.0.1
server3.local.lan. 60 IN A 127.0.0.1
```

**Параметры SRV-записи:**
- **Приоритет (Priority):** `10`, `20`. Чем меньше число, тем выше приоритет. Серверы с более низким приоритетом (большим числом) будут использоваться как резервные (`backup`).
- **Вес (Weight):** `2`, `1`. Распределяет нагрузку между серверами с одинаковым приоритетом.
- **Порт (Port):** `9001`, `9002`, `9003`. Порт, на котором работает сервис.
- **Цель (Target):** `server1.local.lan.`. Хост, на котором запущен сервис.

Этот метод дает значительно больше контроля над балансировкой и конфигурацией серверов.

Проверить корректность работы динамических апстримов, настроенных через SRV-записи, можно с помощью Angie Console Light, где отображаются активные серверы, их веса и статусы.

## 3. Использование Docker Labels

В контейнерных средах, особенно при использовании Docker, можно использовать Docker API для автоматического обнаружения бэкендов. Angie может подключаться к Docker-сокету, читать метки (labels) у запущенных контейнеров и на их основе формировать апстрим-группу.

### Конфигурация Docker Compose

В `docker-compose.yml` для сервисов, которые должны быть включены в апстрим, добавляются специальные метки.

```yaml
# docker-compose.yml
version: '3.8'

services:
  backend1:
    image: my-app:1.0
    networks:
      - app-net
    labels:
      - "angie.http.upstreams.my_app.server=backend1:8080" # Адрес и порт внутри Docker-сети
      - "angie.http.upstreams.my_app.weight=2"
      - "angie.http.upstreams.my_app.max_fails=3"

  backend2:
    image: my-app:1.0
    networks:
      - app-net
    labels:
      - "angie.http.upstreams.my_app.server=backend2:8080"
      - "angie.http.upstreams.my_app.weight=1"

networks:
  app-net:
    driver: bridge
```

**Формат меток:**
- `angie.http.upstreams.<upstream_name>.server=<internal_address>:<internal_port>`: Определяет сервер для апстрима с именем `<upstream_name>`. Адрес — это имя сервиса и *внутренний* порт внутри Docker-сети.
- `angie.http.upstreams.<upstream_name>.<parameter>=<value>`: Задает дополнительные параметры, такие как `weight`, `max_fails` и др.

### Конфигурация Angie

В конфигурации Angie необходимо указать путь к Docker-сокету и определить пустой апстрим-блок.

```nginx
# /etc/nginx/conf.d/docker_upstream.conf

http {
    # ...

    # Указываем путь к сокету Docker
    docker endpoint unix:/var/run/docker.sock;

    # Пустой апстрим, который будет заполнен на основе меток
    upstream my_app {
        zone my_app 64k;
        # Серверы будут добавлены автоматически
    }

    server {
        listen 80;
        location / {
            proxy_pass http://my_app;
        }
    }
}
```

### Права доступа

Пользователь, от имени которого работает Angie (например, `www-data`), должен иметь права на чтение и запись для Docker-сокета (`/var/run/docker.sock`). Самый простой способ — добавить этого пользователя в группу `docker`.

```bash
sudo usermod -aG docker www-data
```

Этот метод обеспечивает полную автоматизацию: при запуске новых контейнеров с нужными метками они автоматически добавляются в балансировку, а при остановке — удаляются.

Статус контейнеров Docker напрямую влияет на список апстримов:
- Приостановленный контейнер получит статус `failed`.
- Полностью остановленный контейнер будет удален из списка.
Проверить текущее состояние апстримов, управляемых через Docker Labels, можно также в Angie Console Light.
