# Динамические группы проксируемых серверов в Angie

## Определения

**Динамический Upstream в Angie** — это механизм автоматического управления составом групп бэкенд-серверов (IP-адреса, порты, веса, параметры доступности) без необходимости перезагрузки конфигурации (`reload`). 

**Обнаружение сервисов (Service Discovery)** — процесс автоматического поиска и регистрации адресов экземпляров приложений в распределенной среде. Angie реализует этот процесс через интеграцию с внешними источниками данных: DNS, Docker API и специализированное HTTP API.

## Базовые концепции

### Механизм разделяемой памяти (zone)
Для работы любого динамического апстрима обязательна директива `zone`. Она выделяет область памяти, доступную всем рабочим процессам (workers), где хранится текущее состояние группы серверов.
*   **Синтаксис:** `zone <name> <size>;`
*   **Размер:** 64 КБ памяти обычно достаточно для хранения данных о ~128 серверах.

### Преимущества перед Nginx OSS
В отличие от стандартного Nginx, где имена серверов разрешаются только один раз при старте, Angie:
1.  **Периодически обновляет DNS-записи** согласно TTL или заданному интервалу.
2.  **Нативно работает с Docker API**, отслеживая запуск и остановку контейнеров.
3.  **Предоставляет API управления**, аналогичное Nginx Plus, но с расширенными возможностями.

### Сохранение состояния (state)
При динамическом изменении состава апстрима через API или DNS, новые данные могут быть потеряны при перезагрузке процесса. Директива `state` позволяет сохранять текущую конфигурацию в файл.
*   **Важно:** В апстриме с `state` нельзя использовать статические директивы `server`.

## Практические сценарии

### Сценарий 1: Динамическое разрешение DNS (A/AAAA)

Используется в облачных средах (AWS, GCP, Kubernetes), где IP-адреса узлов эфемерны.

```nginx
http {
    # Резолвер обязателен. Параметр valid переопределяет TTL из DNS.
    resolver 127.0.0.1 valid=30s;
    resolver_timeout 5s;

    upstream app_servers {
        zone app_servers 64k;
        # Параметр resolve активирует динамическое обновление
        server backend.internal.cloud resolve;
    }
}
```

### Сценарий 2: Использование DNS SRV-записей

Идеально для интеграции с **Consul** или **HashiCorp Nomad**, так как SRV-записи передают не только IP, но и порты, веса и приоритеты.

```nginx
http {
    resolver 10.0.0.1;

    upstream consul_services {
        zone consul_services 128k;
        # service=http указывает Angie искать SRV-записи для _http._tcp.web.service.consul
        server web.service.consul resolve service=http;
    }
}
```

### Сценарий 3: Нативная интеграция с Docker

Angie опрашивает Docker API и автоматически наполняет апстрим контейнерами, имеющими соответствующие метки (labels).

**1. Настройка в Docker Compose:**
```yaml
services:
  webapp:
    image: my-app:latest
    labels:
      - "angie.http.upstreams.pool1.server=webapp:8080"
      - "angie.http.upstreams.pool1.weight=10"
      - "angie.http.upstreams.pool1.max_fails=3"
```

**2. Конфигурация в Angie:**
```nginx
http {
    # Подключение к сокету (требует прав на чтение/запись для пользователя angie)
    docker endpoint unix:/var/run/docker.sock;

    upstream pool1 {
        zone pool1 64k;
        # Серверы добавятся автоматически при появлении контейнеров с метками
    }
}
```

### Сценарий 4: Управление через HTTP API (Angie PRO)

Позволяет внешним скриптам или системам CI/CD напрямую управлять балансировкой.

```nginx
http {
    upstream dynamic_api {
        zone dynamic_api 128k;
        state /var/lib/angie/state/dynamic_api.conf;
    }

    server {
        listen 8080;
        
        location /api {
            # Включение API с правами на запись
            api write=on;
            allow 192.168.1.0/24;
            deny all;
        }
    }
}
```
**Пример запроса на добавление сервера:**
`curl -X POST -d '{"server": "10.0.0.5:80", "weight": 2}' http://localhost:8080/api/v1/http/upstreams/dynamic_api/servers`

## Дополнительная информация

### Сравнение методов Service Discovery

| Метод | Плюсы | Минусы |
| :--- | :--- | :--- |
| **DNS (A/AAAA)** | Простота, совместимость с любым стеком. | Зависимость от TTL и доступности DNS-сервера. |
| **DNS SRV** | Передача портов и весов, нативный Consul. | Требует настройки SRV-записей в инфраструктуре. |
| **Docker** | Не требует DNS, работает "из коробки" с метками. | Привязка к локальному или удаленному Docker API. |
| **HTTP API** | Максимальная гибкость, полный контроль. | Требует внешнего оркестратора (скриптов). |

### Мониторинг динамики
Для проверки текущего состава апстрима используйте модуль статистики. В реальном времени данные доступны через визуальный интерфейс [Console Lite](./angie_monitoring/angie_monitoring_console.md) или в JSON формате:
`curl http://localhost:8080/api/v1/http/upstreams/webapp`

### Рекомендации по эксплуатации
1.  **Права доступа Docker:** Если используется `unix socket`, убедитесь, что пользователь `angie` добавлен в группу `docker`.
2.  **Таймауты DNS:** Всегда настраивайте `resolver_timeout` и `valid`, чтобы избежать зависаний при проблемах с DNS.
3.  **Безопасность API:** Никогда не оставляйте `api write=on` открытым для публичного доступа; используйте `allow/deny` или `auth_basic`.
