# Логирование в Angie

## Определения

В Angie, как и в его прародителе [Nginx](../Nginx/Core/nginx_overview.md), существует два основных типа логов, критически важных для отладки, [мониторинга](./angie_monitoring/angie_monitoring_concepts.md) и анализа безопасности. В отличие от Nginx, Angie предоставляет расширенные возможности управления логами ошибок и поддержку современных форматов «из коробки»:

* **Лог доступа (`access_log`)**: Фиксирует информацию о каждом обработанном запросе клиента (HTTP) или сессии (Stream/L4). Запись в лог происходит на **последней фазе обработки запроса** (фаза `log`), после того как запрос прошел все остальные этапы.
* **Лог ошибок (`error_log`)**: Предназначен для записи информации о проблемах, возникших в процессе работы сервера, а также для диагностических сообщений.

## Базовые концепции

### Лог доступа (`access_log`)

`access_log` записывает информацию о каждом запросе клиента. Директиву можно размещать на уровнях `http`, `server` или `location`. 

**Особенности наследования:**
* Определение на вложенном уровне (например, в `location`) по умолчанию отменяет логирование, настроенное на более высоком уровне (`server`).
* Если требуется писать запрос одновременно в несколько файлов (например, в общий лог сервера и лог конкретного сайта), необходимо указать несколько директив `access_log` в одном контексте.

```nginx
# Стандартные форматы из пакета поставки:
# main — базовый (аналог combined в Nginx)
# extended — расширенный (рекомендуется для получения детальных метрик)

# Пример использования на уровне HTTP для всех серверов
http {
    access_log /var/log/angie/access.log extended;
}

# Отключение логирования для статических файлов
location /static/ {
    access_log off;
}
```

**Формат `extended` (преимущества):**
В отличие от стандартного `main`, расширенный формат включает переменные для анализа [апстримов](./angie_reverse_proxy.md) (`$upstream_response_time`, `$upstream_cache_status`) и заголовок `Host`, что критически важно при работе с множеством виртуальных хостов.


### Лог ошибок (`error_log`)

В Angie директива `error_log` значительно расширена по сравнению с классическим Nginx. Помимо уровня детализации, она поддерживает форматирование в JSON, фильтрацию сообщений и ограничение скорости записи.

#### Базовая настройка и уровни детализации

**Уровни детализации** (от самого критичного к самому подробному): `emerg`, `alert`, `crit`, `error`, `warn`, `notice`, `info`, `debug`. 

```nginx
# Глобальный лог ошибок с уровнем детализации 'warn'
error_log /var/log/angie/error.log warn;
```

* Для промышленной эксплуатации рекомендуется `warn` или `error`. 
* Уровень `notice` полезен для отладки модулей (например, **ACME (Automated Certificate Management Environment)**).
* Уровень `debug` требует сборки с флагом `--with-debug` и предназначен для глубокой диагностики.

#### Ограничение скорости (rate)

Параметр `rate` (Angie-specific) позволяет ограничить частоту записи сообщений в лог, что критично для предотвращения "зафлуживания" диска при массовых ошибках или атаках.

```nginx
# Ограничение скорости записи: не более 100 сообщений в секунду (по умолчанию 1000)
error_log /var/log/angie/error.log warn rate=100;
```

#### Фильтрация сообщений (filter)

Параметр `filter` (Angie-specific) позволяет записывать в лог только те сообщения, которые соответствуют заданному условию. Можно указывать несколько параметров `filter=file:` или `filter=event:` — они совпадают по префиксу, и любое совпадение пропускает сообщение. Несколько `filter=tag:` требуют наличия всех тегов одновременно.

* **Объекты фильтрации:**
    * `file`: Поиск по префиксу имени исходного файла (например, `filter=file:ngx_http_upstream`).
    * `event`: Поиск по префиксу ID события (например, `filter=event:http.upstream.peer`).
    * `tag`: Поиск по пользовательскому тегу (см. `error_log_user_tag`) или автоматическому тегу модуля (`http`, `stream`, `mail`, `upstream`, `peer`, `subrequest`).
    * `message`: Поиск по тексту сообщения об ошибке.
    * `logline`: Поиск по всей строке лога.
* **Типы сопоставления:**
    * Подстрока (например, `filter=message:timeout`).
    * Точное совпадение (`=`, например, `filter=tag:=api_error`).
    * Регулярное выражение (`~`, например, `filter=message:~H[23]`).

```nginx
# Логировать только ошибки, связанные с протоколами HTTP/2 или HTTP/3
error_log /var/log/angie/http2_3_errors.log warn filter=message:~H[23];
```

#### Формат JSON для лога ошибок

Angie поддерживает нативный вывод лога ошибок в формате JSON, что радикально упрощает интеграцию с системами сбора логов.

```nginx
# Использование JSON-формата (Angie-specific)
error_log /var/log/angie/error.json warn format=json;
```

**Поля в JSON-логе:**
* `timestamp`: Время события в формате ISO 8601.
* `level`: Уровень ошибки.
* `pid`/`tid`: ID процесса и потока.
* `message`: Текст сообщения.
* `tags`: Массив тегов, присвоенных сообщению.
* `client`/`server`/`request`: Контекстная информация о запросе (если доступна).

#### Формат строки текстового лога

Каждая запись в текстовом логе ошибок имеет формат:

```
timestamp [level] PID#TID: *request_id message
```

Где:
* `timestamp` — дата и время события.
* `level` — уровень логирования.
* `PID#TID` — идентификаторы процесса и потока.
* `*request_id` — уникальный ID запроса (если применимо).
* `message` — текст сообщения об ошибке.

#### Циклический буфер в памяти (`memory:`)

Для отладки Angie поддерживает запись логов ошибок в циклический буфер в памяти. Это полезно для временной диагностики без записи на диск:

```nginx
# Буфер на 64 КБ в памяти
error_log memory:64k warn;
```

Данные из буфера доступны через API (модуль `stub_status` или `metrics`) и не сохраняются при перезапуске процесса.

#### Логирование SSL-ключей (`ssl_keylog_file`)

Для анализа зашифрованного трафика Angie поддерживает запись SSL-ключей сессий в отдельный файл:

```nginx
# Запись ключей сессий TLS для анализа в Wireshark
ssl_keylog_file /var/log/angie/sslkeys.log;
```

> **Внимание!** Файл содержит секретные ключи и должен быть доступен только процессу Angie и/root. Используйте исключительно для отладки.

### Тегирование ошибок (`error_log_user_tag`)

Директива `error_log_user_tag` (Angie-specific) позволяет присвоить текущему запросу произвольный тег. Этот тег будет добавлен в поле `tags` (в JSON) или `tag:` (в тексте) лога ошибок, что позволяет связывать ошибки с конкретными логическими частями приложения или типами клиентов.

```nginx
location /api/v2/ {
    # Присваиваем тег всем запросам в этом location
    error_log_user_tag "api_v2_backend";
    
    # Можно использовать этот тег для фильтрации в отдельный файл
    error_log /var/log/angie/api_errors.log info filter=tag:api_v2_backend;
}
```

### Логирование в модуле Stream (L4)

Для проксирования трафика на уровне **L4 (Layer 4)** (**TCP (Transmission Control Protocol)** / **UDP (User Datagram Protocol)**) логирование настраивается в блоке `stream`. В отличие от HTTP, здесь фиксируются параметры сессии, а не отдельных запросов.

```nginx
stream {
    log_format basic '$remote_addr [$time_local] '
                     '$protocol $status $bytes_sent $bytes_received '
                     '$session_time "$upstream_addr"';

    access_log /var/log/angie/stream-access.log basic;
}
```

Переменные для [Stream/L4](./l4_balancing_and_proxying.md):
* `$protocol` — протокол (`TCP` или `UDP`).
* `$session_time` — длительность сессии в секундах.
* `$upstream_addr` — адрес бэкенд-сервера.

Подробнее см. в [L4 балансировка и проксирование](./l4_balancing_and_proxying.md).

### Логирование в Syslog и контейнерные среды

В современных инфраструктурах часто требуется отправка логов во внешние системы или сборщики контейнеров.

#### Логирование в стандартные потоки (Docker/Kubernetes)
Для контейнеризированных сред рекомендуется направлять логи в `stdout` и `stderr`, чтобы их мог перехватить рантайм контейнеров.
```nginx
# Перенаправление лога ошибок в stderr
error_log stderr warn;

# Перенаправление лога доступа в stdout (через символическую ссылку в официальных образах)
access_log /var/log/angie/access.log combined;
```

#### Логирование в Syslog
Angie поддерживает прямую отправку логов в **Syslog** без промежуточных файлов.
```nginx
# Пример отправки в Syslog на локальный сокет
access_log syslog:server=unix:/dev/log,facility=local7,tag=angie,severity=info combined;

# Пример отправки на удаленный сервер по UDP
error_log syslog:server=192.168.1.10:514,facility=local6,tag=angie_err warn;
```
Параметры `server`, `facility`, `tag` и `severity` позволяют гибко классифицировать сообщения на стороне приемника.

### Отладка и диагностика

#### Использование отладочного лога (`debug`)

Для получения максимально подробной информации о работе сервера используется уровень `debug`. 

1.  **Проверьте поддержку:** бинарный файл должен быть собран с флагом `--with-debug`. В пакетах для Linux обычно поставляется два бинарных файла: `angie` и `angie-debug`.
2.  **Переключите бинарный файл:** с помощью изменения символической ссылки (путь может отличаться в зависимости от дистрибутива):
    ```bash
    # Переключение на отладочную версию
    sudo ln -sf /usr/sbin/angie-debug /usr/sbin/angie
    sudo systemctl restart angie
    ```
3.  **Включите уровень debug:**
    ```nginx
    error_log /var/log/angie/error.log debug;
    ```

> **Внимание!** Отладочный бинарный файл работает медленнее, а лог растет очень быстро. Не используйте глобальный `debug` на высоконагруженных серверах без необходимости.

#### Директива `debug_connection`

Позволяет включить отладочный лог только для конкретных IP-адресов или подсетей, не перегружая основной лог.

```nginx
events {
    # Включить подробную отладку только для доверенного IP
    debug_connection 192.168.1.50;
}
```

## Практические сценарии

### Пользовательские форматы лога (`log_format`)

Для детального анализа стандартных форматов (`combined`) может быть недостаточно. Angie позволяет определять собственные форматы с помощью директивы `log_format`.

**Пример: Расширенный формат для анализа `upstream`**

```nginx
http {
    log_format extended '$remote_addr - $remote_user [$time_local] "$request" '
                      '$status $body_bytes_sent "$http_referer" '
                      '"$http_user_agent" "$http_x_forwarded_for" '
                      'rt=$request_time ua="$upstream_addr" '
                      'us="$upstream_status" ut="$upstream_response_time" '
                      'cs=$upstream_cache_status';

    access_log /var/log/angie/access.log extended;
}
```

Ключевые переменные для анализа [проксируемых серверов](./angie_reverse_proxy.md):

* `$request_time`: Полное время обработки запроса.
* `$upstream_addr`: Адрес `upstream` сервера.
* `$upstream_status`: HTTP-статус ответа от `upstream`.
* `$upstream_response_time`: Время ответа от `upstream`.
* `$upstream_cache_status`: Статус кэша (`HIT`, `MISS`, `EXPIRED`).

### Логирование в формате JSON

Для упрощения парсинга логов в автоматизированных системах (**ELK (Elasticsearch, Logstash, Kibana)**, [Loki](../../Loki/loki_overview.md), [Vector](../../Vector/vector_overview.md)) удобно использовать формат **JSON (JavaScript Object Notation)**. В Angie рекомендуется использовать параметр `escape=json` для корректной обработки спецсимволов и добавлять идентификаторы запросов для сквозной трассировки.

```nginx
http {
    log_format json_combined escape=json
      '{'
        '"timestamp":"$time_iso8601",'
        '"request_id":"$request_id",'         # Уникальный ID для трассировки
        '"remote_addr":"$remote_addr",'
        '"remote_user":"$remote_user",'
        '"request_method":"$request_method",'
        '"request_uri":"$request_uri",'
        '"status":$status,'
        '"body_bytes_sent":$body_bytes_sent,'
        '"request_time":$request_time,'       # Время обработки (в секундах с миллисекундами)
        '"http_referrer":"$http_referer",'
        '"http_user_agent":"$http_user_agent",'
        '"upstream_addr":"$upstream_addr",'
        '"upstream_status":"$upstream_status",'
        '"upstream_response_time":"$upstream_response_time",'
        '"upstream_cache_status":"$upstream_cache_status"'
      '}';

    access_log /var/log/angie/access.json json_combined;
}
```

### Настройка формата времени (`time_format`)

Директива `time_format` (Angie-specific) позволяет определять пользовательские переменные с нужным форматом времени, используя стандартные спецификаторы `strftime` и расширение `%L` для миллисекунд.

```nginx
http {
    # 1. Определяем переменную с форматом времени
    # Пример: ISO 8601 с миллисекундами
    time_format $iso_ms "%Y-%m-%dT%H:%M:%S.%L%z";
    
    # Пример: компактный формат для внутреннего аудита
    time_format $audit_time "%d/%m/%y %H:%M:%S";

    # 2. Используем переменные в log_format
    log_format timed '$remote_addr [$iso_ms] "$request" $status';
    access_log /var/log/angie/access.log timed;
}
```

### Условное логирование

Иногда требуется исключить из логов "шум" (например, запросы мониторинга или статику) или, наоборот, логировать только подозрительные запросы.

**Пример: Логировать только медленные запросы (более 1 секунды)**

```nginx
http {
    map $request_time $slow_request {
        ~^0\.  0; # Быстрее 1с
        default 1; # 1с и более
    }
}

server {
    # Лог только для "тяжелых" запросов
    access_log /var/log/angie/slow.log json_combined if=$slow_request;
}
```

### Интеграция с современными инструментами сбора логов

Хотя Angie может писать напрямую в Syslog, предпочтительным методом является запись в JSON-файлы с последующим сбором легковесными агентами.

*   **Vector**: Идеален для трансформации логов Angie перед отправкой в ClickHouse или Elasticsearch.
*   **Fluent Bit**: Минимальное потребление ресурсов, нативная поддержка парсинга JSON.
*   **Promtail**: Если используется стек Grafana Loki.

**Рекомендация:** При использовании JSON-логов в высоконагруженных системах всегда включайте буферизацию (см. раздел "Оптимизация производительности").

### Анализ логов инструментами Linux

Для быстрого анализа текстовых логов без использования тяжелых систем (ELK/Loki) удобно использовать стандартные конвейеры Linux.

**1. Топ IP-адресов по количеству запросов:**
```bash
awk '{print $1}' /var/log/angie/access.log | sort | uniq -c | sort -nr | head -n 10
```

**2. Поиск запросов с долгим ответом апстрима (более 1 секунды):**
Предполагается, что `$upstream_response_time` — предпоследнее поле в формате `extended`.
```bash
tail -n 1000 /var/log/angie/access.log | awk '$NF > 1.0 {print $0}'
```

**3. Анализ 404 ошибок по конкретному пути:**
```bash
grep " 404 " /var/log/angie/access.log | awk '{print $7}' | sort | uniq -c | sort -nr
```

**4. Просмотр лога в реальном времени с фильтрацией:**
```bash
tail -f /var/log/angie/access.log | grep --line-buffered "POST"
```

**5. Статистика по кодам ответа:**
```bash
awk '{print $9}' /var/log/angie/access.log | sort | uniq -c | sort -rn
# → 12456 200
# →  3421 304
# →   892 404
# →   234 500
```

**6. Анализ User-Agent (выявление ботов):**
```bash
awk -F'"' '{print $6}' /var/log/angie/access.log | sort | uniq -c | sort -rn | head -n 15
```

**7. Подсчёт уникальных IP за час (для анализа нагрузки):**
```bash
awk '$4 ~ /21\/Sep\/2026:1[0-9]/' /var/log/angie/access.log | awk '{print $1}' | sort -u | wc -l
```

**8. Поиск запросов с определённым заголовком:**
```bash
grep 'X-Forwarded-For' /var/log/angie/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head -n 10
```

### Автоматическая ротация логов (`logrotate`)

Angie не выполняет ротацию логов самостоятельно. Для автоматической ротации используется стандартная утилита `logrotate`. После переименования файла лога необходимо отправить сигнал Angie для переоткрытия файлов.

**Пример конфигурации `/etc/logrotate.d/angie`:**

```
/var/log/angie/*.log {
    daily
    missingok
    rotate 14
    compress
    delaycompress
    notifempty
    create 0640 www-data adm
    sharedscripts
    postrotate
        [ -f /var/run/angie.pid ] && kill -USR1 $(cat /var/run/angie.pid) || true
    endscript
}
```

**Параметры:**
* `daily` — ротация каждый день (можно `weekly`, `monthly`).
* `rotate 14` — хранить 14 последних файлов.
* `compress` — сжимать старые логи (gzip).
* `delaycompress` — откладывать сжатие на один цикл (чтобы текущий лог не сжимался).
* `sharedscripts` — выполнять `postrotate` один раз для всех файлов glob-паттерна.
* `postrotate` — команда, выполняемая после ротации; сигнал `USR1` заставляет Angie переоткрыть файлы логов.

**Проверка конфигурации:**
```bash
logrotate -d /etc/logrotate.d/angie  # Dry-run: показать, что будет сделано
logrotate -f /etc/logrotate.d/angie  # Принудительная ротация
```

### Логирование в контейнерные среды (Docker)

В контейнерах Angie рекомендуется направлять логи в `stdout`/`stderr`, чтобы перехватчик логов контейнера (Docker log driver, journald) мог их собирать.

**Пример конфигурации для Docker:**

```nginx
# Ошибки — в stderr (по умолчанию для контейнеров)
error_log stderr warn;

# Доступ — в stdout через символическую ссылку (в официальных образах Angie)
# или через отдельный механизм:
access_log /dev/stdout combined buffer=8k flush=5s;
```

> **Примечание:** Запись в `/dev/stdout` с буферизацией поддерживается в большинстве современных систем. Если возникают проблемы, используйте `access_log /var/log/angie/access.log combined;` и собирайте логи через volume mount.

## Решение проблем (Troubleshooting)

### Логи не записываются

**Причины и диагностика:**

1. **Проверьте права доступа:** процесс Angie (обычно `www-data` или `nginx`) должен иметь права на запись в директорию логов.
   ```bash
   ls -la /var/log/angie/
   # Директория должна принадлежать www-data:adm (или аналогичной группе)
   sudo chown -R www-data:adm /var/log/angie
   sudo chmod 750 /var/log/angie
   ```

2. **Проверьте конфигурацию:** убедитесь, что директива `access_log` или `error_log` указывает на корректный путь.
   ```bash
   angie -t  # Проверка конфигурации
   ```

3. **Проверьте, что директива не отключена:** ищите `access_log off;` в родительских контекстах (`server`, `location`).

### Высокое потребление диска логами

**Решения:**

1. **Включите буферизацию и сжатие:**
   ```nginx
   access_log /var/log/angie/access.log buffer=64k gzip=1 flush=10s;
   ```

2. **Настройте `rate` для error_log:**
   ```nginx
   error_log /var/log/angie/error.log warn rate=100;
   ```

3. **Настройте ротацию:** используйте `logrotate` (см. раздел "Автоматическая ротация логов").

4. **Используйте условное логирование:** исключите шумные запросы ( health check, статику).

### Логи после ротации не появляются в новом файле

Angie **не переоткрывает** файлы логов автоматически после ротации. Необходимо отправить сигнал:

```bash
kill -USR1 $(cat /var/run/angie.pid)
```

Проверьте, что PID-файл существует и доступен. Если Angie запущен через systemd:
```bash
systemctl reload angie  # Альтернатива: полная перезагрузка конфигурации
```

### Медленная запись логов при высокой нагрузке

**Причины:**
* Отсутствие буферизации.
* Запись на медленный диск (HDD вместо SSD).
* Слишком высокий уровень логирования (например, `info` вместо `warn`).

**Решения:**
1. Увеличьте размер буфера: `buffer=128k`.
2. Перенесите логи на быстрый диск (SSD или tmpfs для временных логов).
3. Понизьте уровень детализации: `error_log ... warn;`.
4. Используйте `if=` для исключения ненужных запросов.

### Логирование в Syslog: сообщения не приходят

**Диагностика:**
1. Проверьте доступность сервера Syslog:
   ```bash
   nc -zvu 192.168.1.10 514  # Проверка UDP-порта
   ```
2. Убедитесь, что Syslog-сервер настроен на прием сообщений от Angie (в `rsyslog.conf` или `syslog-ng`).
3. Проверьте параметры `facility` и `tag` — они должны совпадать с фильтрами на приемнике.
4. Angie ограничивает частоту сообщений Syslog (не более 1 раза в секунду для ошибок подключения).

## Лучшие практики

1.  **Обязательная буферизация** в продакшене: `access_log ... buffer=32k flush=5s;` снижает число syscall и не теряет кред для мониторинга при сбоях.
2.  **Не логируйте статику и health-проверки**: `if=...` в `access_log` и `location` с `access_log off` для `^~ /static/` уменьшают трафик логов и дисковую нагрузку.
3.  **Обязательная ротация с USR1**: настройте `logrotate` c `postrotate: kill -USR1 $(cat /var/run/angie.pid)` — без этого файл лога растёт бесконечно.
4.  **Выбирайте правильный уровень**: `error_log` на `warn` в production; `debug` только на время диагностики (заметно бьёт по производительности).
5.  **JSON-формат для централизованного сбора** (ELK/Loki): используйте кастомный `log_format` с `application/json` — проще парсить и агрегировать.
6.  **`open_log_file_cache`** для большого числа записей: `open_log_file_cache max=1000 inactive=20s min_uses=2 valid=1m;`.

## Дополнительная информация

### Оптимизация производительности логирования

При высоких нагрузках запись логов на диск может стать узким местом.

#### Буферизация (`buffer`)

Запись в лог происходит порциями, что снижает количество операций дискового ввода-вывода.

```nginx
access_log /var/log/angie/access.log extended buffer=32k flush=5s;
```

* `buffer=32k`: Размер буфера.
* `flush=5s`: Принудительный сброс буфера на диск по истечении времени.

#### Сжатие (`gzip`)

Angie может сжимать логи "на лету" перед записью, экономя дисковое пространство ценой небольшой нагрузки на **CPU (Central Processing Unit — центральный процессор)**.

```nginx
# Сжатие автоматически включает буферизацию
access_log /var/log/angie/access.log.gz extended gzip=1;
```

* `gzip=1`: Уровень сжатия (рекомендуется 1-3).

#### Кэширование дескрипторов файлов (`open_log_file_cache`)

Для систем с большим количеством файлов логов эта директива кэширует открытые файловые дескрипторы, сокращая системные вызовы.

```nginx
open_log_file_cache max=1000 inactive=20s min_uses=2 valid=1m;
```

### Ротация логов

Angie не закрывает и не переоткрывает файлы логов автоматически после их переименования или перемещения (например, внешней утилитой `logrotate`). Чтобы сервер начал писать в новый файл, ему необходимо отправить сигнал **USR1**:

```bash
# Переоткрытие файлов логов без перезагрузки конфигурации
kill -USR1 $(cat /var/run/angie.pid)
```
Это действие заставляет рабочий процесс переоткрыть все файлы логов, сохранив при этом производительность.
