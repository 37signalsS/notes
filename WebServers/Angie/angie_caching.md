# Кэширование в Angie (Nginx)

Кэширование в Angie (Nginx) играет ключевую роль в оптимизации производительности веб-приложений и снижении нагрузки на бэкенд-серверы. Оно позволяет эффективно управлять хранением и доставкой контента как на стороне клиента, так и на стороне сервера.

## 1. Клиентское кэширование

Клиентское кэширование — это механизм, позволяющий браузеру сохранять локальные копии ресурсов (CSS, JS, изображения), чтобы не запрашивать их повторно при последующих визитах. Это значительно ускоряет загрузку сайта, экономит трафик и снижает нагрузку на сервер.

Управление кэшированием осуществляется с помощью HTTP-заголовков, которые сервер отправляет вместе с ресурсом.

### 1.1. Заголовки для валидации (Условные запросы)

Эти заголовки не предотвращают запросы к серверу, но позволяют ему ответить кодом `304 Not Modified`, если ресурс не изменился. Браузер в этом случае использует свою локальную копию.

#### 1.1.1. `ETag`

`ETag` (Entity Tag) — это уникальный идентификатор версии ресурса, обычно хэш его содержимого.

-   **Сервер отправляет:** `ETag: "abcdef12345"`
-   **Клиент при повторном запросе отправляет:** `If-None-Match: "abcdef12345"`

Если `ETag` совпадает, сервер возвращает `304 Not Modified` без тела ответа.

**Пример использования `curl` для валидации `ETag`:**
```bash
# Первый запрос, получаем ETag
curl -I http://example.com/style.css
# HTTP/1.1 200 OK
# ETag: "abcdef12345"
# Last-Modified: Tue, 18 Nov 2025 15:00:00 GMT

# Повторный запрос с If-None-Match
curl -I -H "If-None-Match: \"abcdef12345\"" http://example.com/style.css
# HTTP/1.1 304 Not Modified
```

В Angie `ETag` для статических файлов включен по умолчанию. Его можно отключить:
```nginx
server {
    # ...
    etag off;
}
```

#### 1.1.2. `Last-Modified`

`Last-Modified` — это заголовок, указывающий дату и время последнего изменения файла.

-   **Сервер отправляет:** `Last-Modified: Tue, 18 Nov 2025 15:00:00 GMT`
-   **Клиент при повторном запросе отправляет:** `If-Modified-Since: Tue, 18 Nov 2025 15:00:00 GMT`

Если файл не изменялся с указанной даты, сервер возвращает `304 Not Modified`. Для статики Angie автоматически устанавливает этот заголовок на основе времени модификации файла в файловой системе.

**Пример использования `curl` для валидации `Last-Modified`:**
```bash
# Первый запрос, получаем Last-Modified
curl -I http://example.com/script.js
# HTTP/1.1 200 OK
# ETag: "fedcba54321"
# Last-Modified: Tue, 18 Nov 2025 15:00:00 GMT

# Повторный запрос с If-Modified-Since
curl -I -H "If-Modified-Since: Tue, 18 Nov 2025 15:00:00 GMT" http://example.com/script.js
# HTTP/1.1 304 Not Modified
```

#### 1.1.3. Эвристика браузера и `Pragma: no-cache`

Важно понимать, что браузеры могут использовать собственную эвристику для кэширования, даже если явные заголовки не предписывают "вечное" кэширование. Это означает, что ресурс может быть использован из локального кэша без запроса к серверу, если браузер считает его достаточно актуальным. В таких случаях вы не увидите `304 Not Modified` ответа.

Заголовок `Pragma: no-cache` является устаревшим (HTTP/1.0), но иногда все еще используется для предотвращения кэширования. В современных HTTP/1.1+ системах его функциональность заменяется директивой `Cache-Control: no-cache`. Принудительное отключение кэша в браузере (например, через DevTools) часто отправляет оба этих заголовка.

### 1.2. Заголовки для "вечного" кэширования

Эти заголовки позволяют браузеру использовать кэшированные ресурсы в течение заданного времени вообще без отправки запросов на сервер. Это наиболее эффективный способ кэширования.

#### 1.2.1. `Expires`

`Expires` — это устаревший заголовок, который указывает точную дату и время, до которых ресурс считается актуальным.

```nginx
location ~* \.(js|css|png|jpg|jpeg|gif|ico)$ {
    expires 1y; # Кэшировать на 1 год
    # Также можно использовать expires max; для кэширования до максимально возможного срока (2037 год)
}
```
Директива `expires` в Angie автоматически устанавливает и `Expires`, и `Cache-Control`.

#### 1.2.2. `Cache-Control`

`Cache-Control` — это современный и более гибкий заголовок, который имеет приоритет над `Expires`.

**Основные директивы `Cache-Control`:**
-   `max-age=<seconds>`: Указывает время в секундах, на которое ресурс можно кэшировать.
-   `public`: Ресурс может кэшироваться любыми кэшами (браузер, CDN, прокси).
-   `private`: Ресурс может кэшироваться только браузером конечного пользователя.
-   `no-cache`: Браузер должен каждый раз валидировать ресурс на сервере (отправлять условный запрос с `ETag` или `Last-Modified`).
-   `no-store`: Полностью запрещает кэширование.
-   `no-transform`: Запрещает любым промежуточным прокси-серверам (например, CDN) изменять или преобразовывать ресурс (например, сжимать изображения).
-   `immutable`: Говорит браузеру, что ресурс никогда не изменится. Это позволяет избежать повторной валидации даже после перезагрузки страницы.

**Пример конфигурации с `add_header`:**
```nginx
location ~* \.(js|css|png|jpg|jpeg|gif|ico)$ {
    # Кэшировать на 1 год, разрешить кэширование на всех уровнях,
    # запретить трансформировать ресурс и указать, что он неизменяем.
    add_header Cache-Control "public, max-age=31536000, no-transform, immutable";
}
```
Использование директивы `expires` часто является более простым способом, так как она генерирует правильный `Cache-Control: max-age=...` заголовок.

### 1.3. Стратегии сброса кэша

Когда используется "вечное" кэширование (`max-age` на длительный срок), возникает проблема обновления ресурсов у клиентов. Если вы просто измените файл на сервере, браузеры продолжат использовать старую версию из кэша.

Решение — изменять URL ресурса при каждом его обновлении. Это называется **cache busting** (сброс кэша).

**Способы:**
1.  **Версионирование в query string:** `style.css?v=1.2`
2.  **Хэш в имени файла:** `style.a1b2c3d4.css`

При изменении файла меняется его URL, и для браузера это совершенно новый ресурс, который он запрашивает с сервера. Этот подход обычно реализуется на уровне сборочных инструментов (Webpack, Gulp) или фреймворков.

### 1.4. Практические рекомендации по клиентскому кэшированию

-   **Для статики (JS, CSS, изображения):** Используйте "вечное" кэширование с `expires 1y` или `add_header Cache-Control "public, max-age=31536000, immutable"` и применяйте технику cache busting.
-   **Для динамического контента (HTML):** Используйте валидационное кэширование или короткое время жизни кэша. Часто для HTML-документов кэширование отключают (`Cache-Control: no-cache` или `private, max-age=0`), чтобы пользователь всегда получал актуальную версию страницы, которая, в свою очередь, будет содержать ссылки на кэшированные статические ресурсы.
-   **Отключение `ETag`:** При использовании cache busting (хэш в имени файла) заголовок `ETag` становится избыточным, и его можно отключить (`etag off;`) для небольшой экономии трафика.

### 1.5. Влияние на производительность

Клиентское кэширование значительно ускоряет загрузку веб-страниц при повторных посещениях, сокращая количество запросов к серверу и объем передаваемых данных. Это приводит к улучшению пользовательского опыта, снижению нагрузки на сервер и экономии трафика. Например, полная загрузка страницы без кэша может занимать более 17 секунд, тогда как с прогретым кэшем — всего 5.5 секунд. Более подробную информацию об общих методах оптимизации веб-приложений можно найти в [Комплексный анализ и оптимизация производительности веб-приложений](../../Concepts/web_performance_optimization_complete_guide.md).

## 2. Серверное кэширование

В этом разделе рассматриваются особенности серверного кэширования в Angie (NGINX), его корректная настройка и оптимизация для повышения производительности и отказоустойчивости.

### 2.1. Введение в серверное кэширование

Серверное кэширование позволяет Angie сохранять ответы от бэкенд-серверов и отдавать их клиентам напрямую, без повторного обращения к бэкенду. Это значительно снижает нагрузку на бэкенды, ускоряет отдачу контента и улучшает общую производительность системы.

Например, если бэкенды отвечают с задержкой в 5 мс, под нагрузкой они могут тормозить. Активация серверного кэширования позволяет отдавать ответы из кэша за 1 мс, даже при высокой нагрузке.

### 2.2. Базовая конфигурация серверного кэширования

Для работы кэша необходимо определить зону кэширования и настроить правила его использования.

#### 2.2.1. Определение зоны кэширования (`proxy_cache_path`)

Зона кэширования определяется в контексте `http` и указывает, где на диске будут храниться кэшированные файлы, а также параметры управления кэшем.

```nginx
http {
    # ...
    # Путь к кэшу, уровни вложенности директорий, название зоны, размер ключей в ОЗУ,
    # время неактивности элементов, максимальный размер кэша на диске.
    proxy_cache_path /var/cache/nginx/proxy_cache levels=1:2 keys_zone=my_cache:10m inactive=60m max_size=1g;
    proxy_temp_path /var/cache/nginx/proxy_temp; # Временная директория для записи
    # ...
}
```

*   `proxy_cache_path`: Определяет корневой каталог для кэшированных файлов.
    *   `levels=1:2`: Создает двухуровневую вложенную структуру директорий для хранения файлов кэша (например, `/var/cache/nginx/proxy_cache/c/29/`). Это предотвращает сваливание всех файлов в одну директорию, что может вызвать проблемы на файловой системе при большом количестве элементов.
    *   `keys_zone=my_cache:10m`: Определяет зону разделяемой памяти `my_cache` размером 10 МБ для хранения ключей кэша и метаданных. Это позволяет Angie быстро проверять наличие элемента в кэше.
    *   `inactive=60m`: Элементы кэша, которые не запрашивались в течение 60 минут, будут удалены.
    *   `max_size=1g`: Максимальный размер кэша на диске. При превышении этого размера старые элементы будут удаляться.
    *   **Управление кэшем:** За вычистку устаревших элементов отвечают отдельные процессы: `cache manager` (удаляет просроченные элементы) и `cache loader` (загружает метаданные кэша при старте).
    *   **`cache_state`:** Сохранение статуса кэша в специальном файле позволяет быстрее перезапускать процессы Angie, избегая полного вычитывания всего кэша с диска.
*   `proxy_temp_path`: Указывает временную директорию для файлов, которые Angie использует при записи ответов в кэш.

#### 2.2.2. Ключ кэширования (`proxy_cache_key`)

`proxy_cache_key` определяет, на основе каких параметров будет формироваться уникальный ключ для кэширования ответа. По умолчанию используется `$scheme$proxy_host$request_uri`.

```nginx
http {
    # ...
    # Пример ключа кэширования, включающего схему, хост и URI запроса.
    # Query string по умолчанию игнорируется, что полезно для предотвращения cache busting.
    proxy_cache_key "$scheme$host$request_uri";
    # ...
}
```

*   **Важно:** Если в ключ кэширования не включены GET-параметры (`$args`), то запросы с разными параметрами, но одинаковым URI, будут использовать один и тот же кэшированный ответ. Это может быть как преимуществом (защита от "cache busting"), так и недостатком (если параметры влияют на контент). Для включения GET-параметров можно использовать `$request_uri` (который включает `$args`) или явно добавить `$args` в ключ. Ключ должен точно определять кэшируемый элемент, чтобы избежать коллизий.
*   Ключ кэша можно дополнять параметрами аутентификации (например, куками), но это может привести к раздуванию кэша, если контент сильно персонализирован. Кэш наиболее эффективен для одинакового контента, выдаваемого всем пользователям, без какой-либо аутентификации или кастомизации выдачи.

#### 2.2.3. Время валидности кэша (`proxy_cache_valid`)

`proxy_cache_valid` определяет, как долго ответы с определенными HTTP-кодами будут считаться валидными в кэше.

```nginx
location / {
    proxy_cache my_cache; # Использование определенной зоны кэша
    proxy_cache_valid 200 302 100s; # Кэшировать ответы 200 и 302 на 100 секунд
    proxy_cache_valid 404 1m;     # Кэшировать ответы 404 на 1 минуту
    # ...
}
```

*   **Микрокэширование:** Для высоконагруженных систем можно использовать очень короткое время жизни кэша (например, 1 секунда), что позволяет значительно сократить нагрузку на бэкенд при большом количестве одновременных запросов. При 100 запросах в секунду это может стократно сократить нагрузку на бэкенд.

### 2.3. Повышение эффективности и отказоустойчивости кэширования

#### 2.3.1. `proxy_cache_lock` (Микрокэширование)

При большом количестве одновременных запросов к некэшированному ресурсу Angie может отправить все эти запросы на бэкенд. `proxy_cache_lock` гарантирует, что только один запрос будет отправлен на бэкенд для обновления кэша, пока остальные ждут. Это помогает предотвратить "эффект стада бизонов" при высокой нагрузке. Более подробно об этом можно узнать в [Настройка Angie для высоких нагрузок и защиты от DoS-атак: Конспект лекции](../Angie/high_load_tuning_and_dos_protection.md).

```nginx
location / {
    # ...
    proxy_cache_lock on; # Включить блокировку кэша
    # ...
}
```

#### 2.3.2. `proxy_cache_use_stale` (Отдача устаревшего ответа)

Эта директива позволяет Angie отдавать устаревший (просроченный) кэшированный ответ, если бэкенд недоступен или отвечает с ошибкой.

```nginx
location / {
    # ...
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
    # ...
}
```
*   `updating`: Отдавать устаревший ответ, пока новый ответ генерируется бэкендом (в сочетании с `proxy_cache_background_update`).
*   `error`, `timeout`, `http_50x`: Отдавать устаревший ответ при ошибках соединения, таймаутах или HTTP 5xx ошибках от бэкенда.
*   **Важно:** Хотя отдача устаревшего ответа повышает отказоустойчивость, требования приложения могут запрещать такое поведение. Всегда учитывайте, что лучше: устаревший контент или ошибка.

#### 2.3.3. `proxy_cache_background_update` (Фоновое обновление)

В сочетании с `proxy_cache_use_stale updating` позволяет Angie отдавать устаревший кэшированный ответ клиенту, пока в фоновом режиме происходит обновление кэша с бэкенда. Клиент не ждет обновления.

```nginx
location / {
    # ...
    proxy_cache_background_update on;
    proxy_cache_use_stale updating;
    # ...
}
```

### 2.4. Управление заголовками кэширования

#### 2.4.1. Игнорирование заголовков от бэкенда (`proxy_ignore_headers`)

Если бэкенд отправляет заголовки, запрещающие кэширование (например, `Cache-Control: no-cache`, `Expires` в прошлом), Angie по умолчанию будет их учитывать. `proxy_ignore_headers` позволяет игнорировать эти заголовки и принудительно кэшировать ответ, даже если бэкенд пытается это запретить.

```nginx
location / {
    # ...
    proxy_ignore_headers Cache-Control Expires Set-Cookie; # Игнорировать эти заголовки от бэкенда
    # ...
}
```

#### 2.4.2. Добавление заголовка `X-Cache-Status`

Для отладки и мониторинга полезно добавлять заголовок `X-Cache-Status` в ответы, чтобы видеть, был ли ответ взят из кэша (`HIT`), пропущен (`MISS`), или произошла другая ситуация. Этот статус также можно записывать напрямую в логи для последующей аналитики и отладки.

```nginx
location / {
    # ...
    add_header X-Cache-Status $upstream_cache_status;
    # ...
}
```
Возможные значения `$upstream_cache_status`: `MISS`, `HIT`, `EXPIRED`, `STALE`, `UPDATING`, `REVALIDATED`, `BYPASS`.

### 2.5. Обход и запрет кэширования

#### 2.5.1. `proxy_cache_bypass` (Обход кэша)

Позволяет определить условия, при которых запрос будет пропущен мимо кэша и всегда будет отправлен на бэкенд.

```nginx
location / {
    # ...
    # Обходить кэш, если в запросе есть параметр 'force_update'
    proxy_cache_bypass $arg_force_update;
    # ...
}
```
Если значение переменной, указанной в `proxy_cache_bypass`, не пустое и не равно "0", кэш будет обойден. При этом ответ от бэкенда все равно может быть сохранен в кэше, если нет других запрещающих директив.

#### 2.5.2. `proxy_no_cache` (Запрет сохранения в кэше)

Позволяет определить условия, при которых ответ не будет сохранен в кэше. В отличие от `proxy_cache_bypass`, эта директива именно запрещает запись ответа в кэш.

```nginx
location / {
    # ...
    # Не сохранять в кэше, если в запросе есть параметр 'no_cache'
    proxy_no_cache $arg_no_cache;
    # ...
}
```

### 2.6. Точечная очистка кэша (Cache Purge)

Стандартный модуль кэширования Angie не предоставляет встроенных средств для точечной очистки кэша. Для этого используется сторонний модуль `ngx_cache_purge`.

#### 2.6.1. Установка модуля `ngx_cache_purge`

Модуль `ngx_cache_purge` обычно доступен в пакетах для Angie (например, `angie-module-cache-purge` или `angie-pro-module-cache-purge`). После установки его необходимо подключить в `angie.conf`:

```nginx
# /etc/angie/angie.conf
load_module modules/ngx_http_cache_purge_module.so;
# ...
```

#### 2.6.2. Настройка `cache_purge` в `location`

После установки модуля можно настроить специальный `location` для обработки запросов на очистку кэша. **Крайне важно ограничить доступ к этому эндпоинту только для доверенных IP-адресов, так как очистка кэша может повлиять на производительность и доступность контента.**

```nginx
server {
    listen 80;
    server_name example.com;

    # ...
    
    location ~ /purge(/.*) {
        allow 127.0.0.1; # Разрешить очистку только с localhost
        deny all;        # Запретить всем остальным

        proxy_cache_purge my_cache $scheme$host$1; # Очистка кэша по ключу
        # $1 - это захваченная часть URI из регулярного выражения
        # Можно также указать тип ответа (HTML, JSON) о статусе очистки, например:
        # proxy_cache_purge_response_type json;
    }

    location / {
        proxy_pass http://my_backend;
        proxy_cache my_cache;
        proxy_cache_valid 200 302 100s;
        add_header X-Cache-Status $upstream_cache_status;
    }
}
```

*   Для очистки кэша используется HTTP-метод `PURGE`. Запрос `PURGE /purge/path/to/resource` на `example.com` очистит кэш для `http://example.com/path/to/resource`.
*   Пример использования `curl` для очистки:
    ```bash
    curl -X PURGE http://example.com/purge/path/to/resource
    ```
*   Модуль `ngx_cache_purge` поддерживает использование wildcard (`*`) для очистки диапазона ключей (например, `proxy_cache_purge my_cache $scheme$host$1*` для очистки всех ресурсов, начинающихся с `$1`).

### 2.7. Мониторинг кэша

Состояние кэша можно мониторить через Angie Console Lite (для Angie Pro) или с помощью Prometheus и Grafana. Метрики включают коэффициент попадания в кэш, использование дискового пространства, количество записей и промахов.

### 2.8. Практические рекомендации по серверному кэшированию

*   **Для статики:** Используйте длительное кэширование с `proxy_cache_valid` и `cache busting` на стороне клиента (изменение URL при обновлении файла).
*   **Для динамического контента:** Используйте микрокэширование (`proxy_cache_valid 1s`), `proxy_cache_lock`, `proxy_cache_background_update` и `proxy_cache_use_stale` для максимальной производительности и отказоустойчивости.
*   **Безопасность:** Всегда ограничивайте доступ к эндпоинтам очистки кэша (`cache_purge`) и мониторинга.
*   **Тестирование:** Тщательно тестируйте конфигурацию кэширования, чтобы убедиться, что она работает так, как ожидается, и не приводит к отдаче устаревшего или некорректного контента.
