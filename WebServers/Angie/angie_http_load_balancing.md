# Балансировка нагрузки HTTP в Angie

## Определения

**Балансировка нагрузки HTTP в Angie** — это процесс распределения входящего L7-трафика (HTTP/HTTPS) между несколькими бэкенд-серверами для повышения производительности и отказоустойчивости. Angie, являясь форком Nginx, наследует его мощные возможности балансировки, расширяя их функциями, ранее доступными только в платной версии Nginx Plus.

## Основные концепции

### Алгоритмы балансировки нагрузки

Angie поддерживает стандартные методы Nginx и добавляет собственные продвинутые алгоритмы.

| Метод | Описание | Особенности |
| :--- | :--- | :--- |
| **Round Robin** | Последовательный перебор серверов. | Дефолтный метод. Поддерживает веса (`weight`). |
| **Least Connections** | Запрос направляется на сервер с наименьшим числом активных соединений. | Хорошо работает при разном времени обработки запросов. |
| **IP Hash** | Клиент привязывается к серверу по IP-адресу (первые 3 октета IPv4). | Гарантирует попадание на тот же сервер, пока он жив. |
| **Hash** | Хеширование по произвольному ключу (URI, переменные). | Параметр `consistent` минимизирует перераспределение при изменении состава группы. |
| **Random** | Случайный выбор сервера. | Эффективен в кластерных конфигурациях, минимизирует блокировки. |
| **Feedback (Pro)** | Выбор на основе обратной связи от бэкендов. | Учитывает время ответа или кастомные метрики (например, Load Average). |

#### Продвинутый метод: Feedback (Angie Pro)

Метод с обратной связью позволяет динамически регулировать нагрузку на основе реальной производительности бэкендов.

```nginx
upstream backend {
    zone backend 64k;
    # Балансировка на основе времени ответа (усредненное значение)
    feedback method=upstream_response_time factor=2 inverse;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
```

- `method`: переменная для мониторинга (например, `$upstream_response_time`).
- `factor`: коэффициент влияния последних значений (сглаживание).
- `inverse`: чем меньше значение метрики, тем больше нагрузки получает сервер.

## Практические сценарии

### 1. Встроенный модуль `sticky` (Прилипание сессий)

Модуль `sticky` обеспечивает персистентность сессий, что необходимо для приложений, хранящих состояние (Stateful).

**Режимы работы:**

- `cookie`: Angie вставляет собственную куку для отслеживания сервера.
- `route`: Использование параметров запроса (например, GET-параметр или кука приложения) для выбора сервера.
- `learn`: Обучение на основе кук, создаваемых самим бэкендом (например, `JSESSIONID`).

```nginx
upstream backend {
    # Секретный ключ предотвращает преднамеренный выбор конкретного бэкенда (защита от DoS)
    sticky cookie session_id expires=1h path=/ secret=my_secret_key;
    server 10.0.0.1:8080 sid=white;
    server 10.0.0.2:8080 sid=blue;
}
```

*Параметр `strict` в режиме `sticky` заставляет выдавать ошибку (502), если целевой сервер недоступен, вместо перенаправления на другой.*

### 2. Проверки работоспособности (Health Checks)

Angie разделяет проверки на пассивные (доступны в OSS) и активные (Pro).

#### Пассивные проверки (OSS)

Выполняются непосредственно во время обработки клиентских запросов.

```nginx
upstream backend {
    # Если за 10с произошло 3 ошибки, сервер выводится из ротации на 10с
    server 10.0.0.1:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.2:8080 backup; # Используется только если остальные лежат
    server 10.0.0.3:8080 down;   # Полностью выведен из ротации
}
```

#### Активные проверки (Angie Pro)

Angie самостоятельно опрашивает бэкенды в фоновом режиме, не дожидаясь ошибок от клиентов.

```nginx
upstream backend {
    zone backend 64k;
    server 10.0.0.1:8080;
    check interval=5s fall=3 rise=2; # Активная проверка
    check_http_send "GET /health HTTP/1.0\r\nHost: example.com\r\n\r\n";
    check_http_expect_rescode 200;
}
```

### 3. Плавное управление серверами (`slow_start`, `drain`)

**Сценарий "прогрева" сервера:**
Параметр `slow_start=T` позволяет плавно вводить "холодный" бэкенд в ротацию, постепенно наращивая его вес от 0 до номинального значения в течение времени `T`. Это защищает только что запущенные сервисы от лавины запросов.

```nginx
upstream backend {
    zone backend 64k;
    server 10.0.0.1:8080 weight=5 slow_start=30s;
    server 10.0.0.2:8080 weight=5 slow_start=30s;
}
```

**Сценарий вывода на обслуживание:**
Параметр `drain` позволяет плавно выводить сервер из ротации. Angie перестает направлять на него новые запросы (кроме "прилипших"), давая возможность безболезненно обработать текущие перед выключением.

```nginx
# В runtime через API или конфигурацию
server 10.0.0.1:8080 drain;
```

### 3. Динамическое разрешение DNS (`resolve`)

Параметр `resolve` у директивы `server` позволяет Angie периодически перечитывать DNS-записи для upstream-серверов. Это критически важно для динамических окружений типа Docker или Kubernetes, где IP-адреса контейнеров могут меняться.

```nginx
http {
    resolver 10.0.0.2 valid=10s;

    upstream backend {
        zone backend 64k;
        server backend.example.com resolve;
    }
}
```

Подробнее о механизме динамического DNS см. [Динамические группы проксируемых серверов в Angie](./dynamic_upstreams.md).

### 4. Динамические группы серверов

Angie поддерживает динамическую конфигурацию upstream-серверов с помощью SRV-записей или через Docker Labels, что упрощает автоматизированное управление бэкендами без перезагрузки конфигурации.

**Пример с Docker Labels:**

```yaml
services:
  backend1:
    image: my-app:1.0
    labels:
      - "angie.http.upstreams.my_app.server=backend1:8080"
      - "angie.http.upstreams.my_app.weight=2"
```

Подробнее: [Динамические группы проксируемых серверов в Angie](./dynamic_upstreams.md).
