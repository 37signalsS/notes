# Балансировка нагрузки HTTP в Angie

## Определения

**Балансировка нагрузки HTTP в Angie** — это процесс распределения входящего трафика уровня L7 (прикладной уровень модели OSI) между группой бэкенд-серверов.

Ключевые преимущества Angie по сравнению с Nginx Open Source:
* **Активные проверки состояния (Active Health Checks)** доступны "из коробки".
* **Персистентность сессий (Sticky Sessions)** через модуль `sticky`.
* **Динамическое управление** апстримами через HTTP API без перезагрузки.
* **Продвинутый мониторинг** каждой группы серверов в реальном времени.

Общие принципы балансировки и базовые алгоритмы описаны в **[обзоре балансировки L7 в Nginx](../Nginx/Proxy/Load_Balancing/overview_concepts.md)**.

## Основные концепции

### Алгоритмы распределения нагрузки

Angie поддерживает все стандартные алгоритмы Nginx (Round Robin, Least Connections, IP Hash) и добавляет специфические механизмы.

| Метод | Описание | Особенности |
| :--- | :--- | :--- |
| **Least Time** | Выбор сервера с наименьшим временем ответа. | Доступно только в Angie. Учитывает задержки бэкенда. |
| **Sticky** | Привязка клиента к серверу через Cookie или Route. | Позволяет реализовать Stateful-балансировку. |
| **Hash** | Хеширование по произвольному ключу (URI, заголовки). | Поддерживает консистентное хеширование (`consistent`). |

### Зоны разделяемой памяти и мониторинг

Для работы большинства продвинутых функций (мониторинг, липкие сессии, активные проверки) необходимо объявить зону разделяемой памяти (`zone`) и зону статуса (`status_zone`).

```nginx
upstream app_servers {
    zone app_servers 64k;       # Хранение состояния группы
    status_zone app_status;      # Сбор метрик для API и консоли
    
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
```

## Практические сценарии

### 1. Настройка активных проверок (Active Health Checks)

В отличие от пассивных проверок (`max_fails`), активные проверки опрашивают бэкенды в фоновом режиме, позволяя Angie узнать о сбое до того, как на сервер попадет реальный запрос.

```nginx
upstream backend_pool {
    zone backend_pool 64k;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;

    # Активная проверка: раз в 5 секунд, 3 ошибки = down, 2 успеха = up
    check interval=5s fall=3 rise=2;
    check_http_send "GET /health HTTP/1.0\r\nHost: example.com\r\n\r\n";
    check_http_expect_rescode 200;
}
```

### 2. Липкие сессии (Sticky Sessions)

Механизм `sticky` позволяет привязать клиента к конкретному серверу. Это необходимо, если приложение хранит сессионные данные локально.

```nginx
upstream stateful_app {
    zone stateful_app 128k;
    # Метод 'cookie': Angie вставит свою куку 'route'
    sticky cookie route expires=1h domain=.example.com path=/;
    
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
```

### 3. Плавное управление (Slow Start и Drain)

Angie позволяет плавно вводить новые серверы в эксплуатацию, чтобы избежать всплеска нагрузки на "холодное" приложение.

* **Slow Start**: Постепенное увеличение веса сервера в течение заданного времени.
* **Drain**: Режим вывода из эксплуатации, при котором сервер дорабатывает текущие сессии, но не принимает новые.

```nginx
upstream production {
    zone production 64k;
    # Постепенный ввод сервера в течение 30 секунд
    server 10.0.0.1:8080 slow_start=30s;
}
```

### 4. Динамическое управление через HTTP API

Модуль `ngx_http_api_module` позволяет изменять параметры апстримов (менять веса, переводить в `down` или `drain`) через REST-запросы без редактирования конфигурации и `reload`.

**Включение API:**
```nginx
server {
    listen 8080;
    location /api/ {
        api;
        allow 192.168.1.0/24;
        deny all;
    }
}
```

**Пример запроса на перевод сервера в режим Drain:**
```bash
curl -X PATCH -d '{"drain":true}' \
  'http://localhost:8080/api/v1/http/upstreams/production/servers/0'
```

### 5. Динамическое обнаружение сервисов (DNS Resolution)

Angie позволяет использовать доменные имена в `upstream` и обновлять их IP-адреса согласно TTL из DNS без перезагрузки сервера. В Nginx Open Source такая возможность ограничена.

```nginx
http {
    # Указываем DNS-сервер (например, CoreDNS в Kubernetes)
    resolver 10.0.0.2 valid=10s;

    upstream cloud_apps {
        zone cloud_apps 64k;
        # Параметр 'resolve' заставляет Angie периодически обновлять IP
        server app.internal.service resolve;
    }
}
```
