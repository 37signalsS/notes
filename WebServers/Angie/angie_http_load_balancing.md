# Балансировка нагрузки HTTP(S) в Angie (Nginx)

В этом документе рассматриваются различные аспекты настройки балансировки нагрузки для HTTP(S) трафика с использованием Nginx (Angie). Для информации о балансировке нагрузки на уровне L4 (TCP/UDP) см. [Балансировка и проксирование L4-трафика (TCP/UDP) в Angie](./l4_balancing_and_proxying.md).

## 1. Основы балансировки нагрузки с `upstream`

Балансировка нагрузки в Nginx начинается с директивы `upstream`, которая позволяет определить группу бэкенд-серверов.

```nginx
upstream backend {
    zone backend_zone 64k; # Зона разделяемой памяти для хранения состояния
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
    server 127.0.0.1:9002;
    server 127.0.0.1:9003;
}

server {
    listen 80;
    location / {
        proxy_pass http://backend;
    }
}
```

По умолчанию используется алгоритм `round robin`, который равномерно распределяет запросы между серверами по очереди.

## 2. Алгоритмы балансировки нагрузки

Nginx поддерживает несколько алгоритмов балансировки нагрузки, которые можно указать в блоке `upstream`.

### 2.1. `round robin` (по умолчанию)

Распределяет запросы последовательно по всем серверам.

### 2.2. `hash`

Распределяет запросы на основе хеша указанной переменной (например, `$request_uri`, `$remote_addr`). Это обеспечивает "прилипание" клиента к одному и тому же бэкенду для одного и того же значения хеша. Использование параметра `consistent` минимизирует перераспределение клиентов между серверами в случае изменения состава группы (добавление или удаление серверов).

```nginx
upstream backend {
    hash $request_uri consistent; # consistent для минимизации перераспределения при изменении состава группы
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
    server 127.0.0.1:9002;
    server 127.0.0.1:9003;
}
```

### 2.3. `least_conn`

Направляет запрос на сервер с наименьшим количеством активных соединений.

### 2.4. `random`

Распределяет запросы случайным образом. Полезен, когда есть несколько балансировщиков перед одной группой бэкендов, и они не обмениваются информацией о нагрузке.

```nginx
upstream backend {
    random;
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
    server 127.0.0.1:9002;
    server 127.0.0.1:9003;
}
```

### 2.5. `random two least_conn`

Выбирает два случайных сервера и направляет запрос на тот из них, у которого меньше активных соединений.

В коммерческой версии [Angie Pro](./angie_pro_features.md) доступны также более продвинутые алгоритмы, такие как `least_time` и `feedback`.

## 3. Веса серверов (`weight`)

Для каждого сервера в блоке `upstream` можно указать вес, который определяет его долю в распределении трафика. По умолчанию `weight=1`.

```nginx
upstream backend {
    server 127.0.0.1:9000 weight=5; # Этот сервер получит в 5 раз больше трафика
    server 127.0.0.1:9001;
    server 127.0.0.1:9002;
    server 127.0.0.1:9003;
}
```

## 4. Sticky Sessions (Прилипание сессий)

Sticky sessions обеспечивают привязку клиента к конкретному бэкенду. В Open Source версии Angie доступны режимы `cookie` и `route`. Более продвинутые режимы, такие как `sticky learn`, доступны в [Angie Pro](./angie_pro_features.md).

### 4.1. Режим `cookie`

Nginx устанавливает специальную куку в браузере клиента, которая содержит информацию о выбранном бэкенде.

```nginx
upstream backend {
    sticky cookie srv_id expires=1h path=/; # srv_id - имя куки, expires - время жизни
    server 127.0.0.1:9000;
    server 127.0.0.1:9001;
    server 127.0.0.1:9002;
    server 127.0.0.1:9003;
}
```

-   `sticky cookie <name> [expires=time] [domain=domain] [path=path] [secure] [httponly]`: Включает прилипание на основе куки.
-   `sticky secret <string>`: Добавляет "соль" к значению куки для предотвращения легкого подбора хеша и защиты от атак, направленных на привязку к определенному бэкенду.
-   `sticky strict`: Если привязанный сервер недоступен, Angie немедленно вернет ошибку (например, 502 Bad Gateway). Если эта директива отключена, запрос будет перенаправлен на другой доступный сервер в группе `upstream` без возврата ошибки клиенту.

### 4.2. Режим `route`

Привязка происходит на основе значения переменной, которая передается в запросе (например, в URL-параметре). Этот метод может быть небезопасен, так как позволяет клиенту напрямую выбирать бэкенд, что может быть использовано для DoS-атаки на конкретный сервер.

```nginx
upstream backend {
    sticky route $arg_route; # Привязка на основе значения параметра 'route' из URL
    server 127.0.0.1:9000 route=green;
    server 127.0.0.1:9001 route=blue;
    server 127.0.0.1:9002 route=red;
    server 127.0.0.1:9003 route=yellow;
}
```

-   `sticky route <variable>`: Указывает переменную, по которой будет определяться маршрут. Например, `$arg_route` для параметра `route` в URL (`?route=green`).
-   `server ... route=<string>`: Определяет маршрут для конкретного сервера.

**Пример использования:**
Если клиент сделает запрос `http://example.com/?route=green`, то он будет направлен на сервер `127.0.0.1:9000`. Последующие запросы от этого клиента в рамках сессии (даже без параметра `route`) будут по-прежнему направляться на тот же сервер `127.0.0.1:9000`.

Если используется `sticky strict` (см. раздел 4.1) и клиент привязан к серверу, который помечен как `down`, Angie вернет ошибку (например, 502 Bad Gateway). Если `sticky strict` отключен, запрос будет перенаправлен на другой доступный сервер.

## 5. Управление состоянием серверов

Angie (Nginx) предоставляет несколько механизмов для управления состоянием бэкенд-серверов, включая проверки работоспособности и плавное изменение их участия в балансировке.

### 5.1. Пассивные проверки (`max_fails`, `fail_timeout`)

Основаны на анализе ответов от бэкенда. Если сервер возвращает ошибки или не отвечает, он временно исключается из балансировки.

```nginx
upstream backend {
    server 127.0.0.1:9000 max_fails=1 fail_timeout=10s; # Если 1 ошибка за 10 секунд, сервер считается нерабочим на 10 секунд
    server 127.0.0.1:9001;
}
```

*   `max_fails=<number>`: Количество неудачных попыток, после которых сервер считается нерабочим. По умолчанию 1.
*   `fail_timeout=<time>`: Время, в течение которого учитываются `max_fails`. Также это время, на которое сервер будет считаться нерабочим после достижения `max_fails`. По умолчанию 10 секунд.
*   Типы ошибок, которые учитываются для пассивных проверок, определяются директивой `proxy_next_upstream` (например, `error`, `timeout`, `http_500`, `http_503` и т.д.).

### 5.2. Статусы серверов (`down`, `backup`, `drain`)

*   `down`: Сервер всегда считается нерабочим и полностью исключен из балансировки. Это полезно, когда сервер выводится на длительное обслуживание.
*   `backup`: Сервер используется только тогда, когда все остальные (не `backup`) серверы в группе недоступны.
*   `drain`: (Доступно в Angie) Плавный вывод сервера из эксплуатации. Angie перестает направлять на него новые запросы (кроме "прилипших" сессий), позволяя ему доработать текущие и безопасно отключиться.

```nginx
upstream backend {
    server 127.0.0.1:9000;
    server 127.0.0.1:9001 down;   # Этот сервер не будет использоваться
    server 127.0.0.1:9002 backup; # Этот будет использоваться только при недоступности 9000
    server 127.0.0.1:9003 drain;  # На этот сервер перестанут идти новые запросы
}
```

### 5.3. Плавный старт (`slow_start`)

Директива `slow_start` (доступно в Angie) обеспечивает плавное наращивание нагрузки на сервер, который только что был добавлен в балансировку или восстановлен после сбоя. Его вес постепенно увеличивается от 0 до номинального значения в течение заданного времени, что позволяет серверу "прогреть" кэши и избежать перегрузки.

```nginx
upstream backend {
    server 127.0.0.1:9000 slow_start=30s;
    server 127.0.0.1:9001;
}
```

### 5.4. Активные проверки (Angie Pro / Nginx Plus)

В коммерческих версиях Angie Pro и Nginx Plus доступны активные проверки работоспособности, которые проактивно отправляют запросы на бэкенды для проверки их состояния, что позволяет еще быстрее реагировать на сбои.

## 6. Разрешение DNS для `upstream` серверов

По умолчанию Nginx разрешает доменные имена серверов в блоке `upstream` только один раз при загрузке конфигурации. Для динамического обновления DNS-записей используется директива `resolve`. Эта функция, ранее доступная только в Nginx Plus, была реализована в Open Source версии Angie, а позже появилась и в Open Source Nginx.

```nginx
http {
    resolver 127.0.0.1 valid=5s; # Указываем DNS-сервер и время кэширования
    
    upstream backend {
        server backend.example.com resolve; # Angie будет периодически обновлять IP-адрес
    }
}
```

*   `resolver <address> [valid=time]`: Определяет DNS-сервер, который будет использоваться для разрешения имен, и время кэширования записей.
*   `server <hostname> resolve`: Указывает Angie использовать встроенный резолвер для периодического обновления IP-адреса доменного имени. **Важно: директива `resolver` обязательна при использовании параметра `resolve`, иначе Nginx выдаст ошибку конфигурации.**

Также можно использовать SRV-записи DNS для управления списком и приоритетом бэкендов.

Для более подробной информации о динамической конфигурации upstream-серверов, включая использование SRV-записей и Docker Labels, см. [Динамические группы проксируемых серверов в Angie](./dynamic_upstreams.md).

## 7. Мониторинг состояния `upstream`

Состояние `upstream` серверов можно отслеживать через `ng console.light` (для Nginx Plus) или с помощью сторонних инструментов мониторинга, анализируя логи и метрики.
