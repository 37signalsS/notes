# Балансировка нагрузки HTTP в Angie

## Определения

**Балансировка нагрузки HTTP в Angie** — это процесс распределения входящего трафика уровня L7 (Layer 7 — прикладной уровень модели OSI (Open Systems Interconnection)) между несколькими бэкенд-серверами. Основными протоколами являются HTTP (HyperText Transfer Protocol) и HTTPS (HyperText Transfer Protocol Secure).

Цели балансировки:

* Повышение производительности за счет параллельной обработки запросов.
* Обеспечение отказоустойчивости (высокой доступности) при выходе из строя части серверов.
* Гибкое управление трафиком (плавный ввод/вывод серверов из эксплуатации).

Angie, являясь форком Nginx, наследует его возможности балансировки и расширяет их функциями, которые ранее были доступны только в коммерческой версии Nginx Plus.

## Основные концепции

### Алгоритмы балансировки нагрузки

Angie поддерживает стандартные методы распределения запросов и добавляет продвинутые алгоритмы на основе обратной связи.

| Метод | Описание | Особенности |
| :--- | :--- | :--- |
| **Round Robin** | Последовательный перебор серверов. | Используется по умолчанию. Поддерживает веса (`weight`). |
| **Least Connections** | Запрос направляется на сервер с наименьшим числом активных соединений. | Эффективен при разном времени обработки запросов бэкендами. |
| **IP Hash** | Привязка клиента к серверу на основе его IP (Internet Protocol) адреса. | Используются первые три октета IPv4 (Internet Protocol version 4). |
| **Hash** | Хеширование по произвольному ключу (URI (Uniform Resource Identifier), переменные). | Параметр `consistent` (консистентное хеширование) минимизирует перераспределение. |
| **Random** | Случайный выбор сервера из группы. | Минимизирует блокировки в высоконагруженных кластерных конфигурациях. |
| **Feedback (Angie Pro)** | Выбор на основе метрик производительности бэкендов. | Учитывает время ответа или системную нагрузку. См. [функции Angie Pro](./angie_monitoring/angie_monitoring_pro.md). |

### Зоны разделяемой памяти (Shared Memory Zones)

Для работы продвинутых функций балансировки (Least Connections, Sticky Sessions, Health Checks) необходимо использование директивы `zone`. Она выделяет участок памяти, доступный всем рабочим процессам Angie для хранения состояния группы серверов.

```nginx
upstream backend_pool {
    zone backend_pool 64k; # Обязательно для продвинутых методов
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
```

## Практические сценарии

### 1. Персистентность сессий (Sticky Sessions)

Встроенный модуль `sticky` позволяет закрепить клиента за конкретным сервером, что критично для приложений, хранящих состояние (Stateful).

```nginx
upstream app_cluster {
    zone app_cluster 128k;
    # Создание куки для отслеживания сессии
    sticky cookie session_id expires=1h path=/ secret=my_key;
    
    server 10.0.0.1:8080 sid=node_a;
    server 10.0.0.2:8080 sid=node_b;
}
```

*Параметр `secret` защищает от DoS (Denial of Service) атак, предотвращая преднамеренный выбор бэкенда клиентом.*

### 2. Проверки работоспособности (Health Checks)

Angie различает пассивные проверки (доступны в базовой версии) и активные (доступны в версии Pro).

**Пассивные проверки:**
Происходят во время обработки реальных пользовательских запросов. Если сервер возвращает ошибку, он временно выводится из ротации.

```nginx
upstream static_backend {
    server 10.0.0.1:80 max_fails=3 fail_timeout=30s;
}
```

**Активные проверки (Angie Pro):**
Angie самостоятельно опрашивает серверы в фоновом режиме по заданному расписанию. Подробнее: [Возможности Angie Pro](./angie_monitoring/angie_monitoring_pro.md).

```nginx
upstream api_backend {
    zone api_backend 64k;
    server 10.0.0.1:8080;
    
    check interval=5s fall=3 rise=2;
    check_http_send "GET /health HTTP/1.0\r\nHost: example.com\r\n\r\n";
    check_http_expect_rescode 200;
}
```

### 3. Плавное управление нагрузкой

**Метод "медленного старта" (`slow_start`):**
Позволяет постепенно наращивать нагрузку на сервер после его запуска или восстановления, предотвращая перегрузку "холодного" приложения.

```nginx
upstream production {
    zone production 64k;
    server 10.0.0.1:8080 slow_start=30s;
}
```

**Режим вывода из эксплуатации (`drain`):**
Позволяет завершить текущие сессии пользователей перед остановкой сервера. Новые пользователи на этот сервер не направляются.

```nginx
# Устанавливается через API или конфигурацию
server 10.0.0.1:8080 drain;
```

### 4. Динамическое обнаружение сервисов

Angie поддерживает динамическое разрешение имен через DNS (Domain Name System), что важно в облачных средах (Kubernetes, Docker).

```nginx
http {
    resolver 10.0.0.2 valid=10s;

    upstream cloud_services {
        zone cloud_services 64k;
        server service.internal.local resolve;
    }
}
```

Для более сложных сценариев с использованием записей SRV (Service Record) или меток Docker см. [Динамические группы проксируемых серверов в Angie](./dynamic_upstreams.md).
