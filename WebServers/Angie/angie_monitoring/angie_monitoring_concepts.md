# Мониторинг Angie — основные концепции

## Определения

**Мониторинг Angie** — комплексный процесс непрерывного сбора, агрегации и визуализации метрик состояния веб-сервера. В отличие от традиционного модуля `stub_status` в Nginx, Angie предоставляет полноценный REST API и нативный механизм экспорта данных, что позволяет интегрировать сервер в современные Observability-стеки без использования внешних агентов-экспортеров.

**Зона статуса (status_zone)** — именованный сегмент в разделяемой памяти (Shared Memory), предназначенный для хранения атомарных счетчиков и структур данных мониторинга. Директива `status_zone` активирует сбор метрик для конкретных виртуальных хостов, локаций или групп апстримов.

**Shared Memory (Разделяемая память)** — область оперативной памяти, доступная всем рабочим процессам (worker processes) сервера. Это критически важный компонент для согласованности метрик, так как каждый воркер инкрементирует счетчики в общей области, что позволяет получать единую картину состояния всего сервера.

**ngx_http_api_module** — встроенный модуль Angie, предоставляющий REST-подобный интерфейс для доступа к метрикам состояния, активной конфигурации и управлению апстримами в режиме реального времени. Данные передаются в формате JSON. Модуль включен в поставку по умолчанию и может быть отключен при сборке флагом `--without-http_api_module`.

**metric (модуль metric)** — модуль Angie, позволяющий создавать пользовательские (кастомные) зоны метрик в разделяемой памяти. Позволяет приложениям или внешним системам записывать произвольные числовые значения (счетчики, таймеры) через переменные или API, которые затем доступны для чтения через `/status/http/metric_zones/<zone>/`.

**Stub Status** — простейший модуль мониторинга (`ngx_http_stub_status_module`), унаследованный от Nginx. Предоставляет базовую текстовую страницу с минимальными счетчиками (активные соединения, принятые/обработанные, чтение/запись/ожидание). Менее информативен, чем API, но не требует настройки зон и работает без разделяемой памяти.

**Поколение конфигурации (Generation)** — целочисленный счетчик версий конфигурации. Инкрементируется при каждом успешном выполнении `reload`. Позволяет точно сопоставить работающие процессы с конкретной версией настроек и выявить "зомби-воркеры", которые не завершились после перезагрузки.

**Cache Zone (Зона кэша)** — именованная область в разделяемой памяти, создаваемая директивой `proxy_cache_path` с параметром `keys_zone`. Хранит метаданные кэшированных объектов (ключи, TTL, статусы попадания) и обеспечивает статистику эффективности кэширования (HIT/MISS/EXPIRED/STALE).

**Keepalive Connection Pool** — пул соединений с апстримами, сохраняемых в открытом состоянии между запросами для повторного использования. Управляется директивой `keepalive` внутри блока `upstream`. Метрики пула доступны через API и отслеживают количество активных и промежуточных (idle) соединений.

**Upstream Probe (Angie Pro)** — нативный механизм активных проверок состояния бэкенд-серверов в Angie Pro (директива `upstream_probe`). Отличается от модуля `check` в OSS гибкостью настройки: поддерживает именованные блоки `match`, HTTP-методы, проверку тела ответа, пороги `fails`/`passes`, режимы работы (`always`, `idle`, `onfail`) и начальную верификацию (`essential`).

## Базовые концепции

### Сравнение API-мониторинга и анализа логов

В архитектуре SRE-мониторинга Angie встроенный API решает задачи, недоступные классическому анализу Access-логов:

1. **In-flight запросы:** Возможность видеть количество запросов, которые обрабатываются прямо сейчас. Логи фиксируют событие только по факту завершения транзакции.
2. **Здоровье бэкендов:** Прямой мониторинг состояния серверов в `upstream` (up/down/unhealthy/draining), включая результаты активных проверок.
3. **Эффективность кэша:** Real-time статистика попаданий в кэш (`HIT/MISS/EXPIRED/STALE`), доступная до записи в лог.
4. **Низкий Overhead:** Сбор метрик в памяти требует значительно меньше CPU и I/O ресурсов по сравнению с записью и последующим парсингом текстовых файлов.

### Сравнение API и stub_status

| Критерий | API (`ngx_http_api_module`) | `stub_status` |
|:---|:---|:---|
| Формат вывода | JSON | Текст |
| Разделяемая память | Требуется (`status_zone`, `zone`) | Не требуется |
| Глубина метрик | Полная (upstreams, кэш, SSL, limit_conn, DNS) | Минимальная (соединения, запросы) |
| Встроенные переменные | Нет (данные через JSON) | `$connections_active`, `$connections_reading` и др. |
| Настройка | Требует конфигурации зон | Только директива `stub_status;` |
| Применение | Полноценный мониторинг, интеграция с системами | Health check, совместимость с Nginx |

### Архитектура сбора данных

Мониторинг в Angie организован по иерархическому принципу:
- **L4 (Stream):** Метрики транспортного уровня (соединения, байты, ошибки TCP/UDP).
- **L7 (HTTP):** Метрики прикладного уровня (HTTP-методы, коды ответов, задержки).
- **Внутреннее состояние:** Версия сервера, аптайм, нагрузка на зоны памяти и состояние поколений конфигурации.

### Жизненный цикл метрик

1. **Сбор (Collection):** Воркеры Angie инкрементируют атомарные счетчики в разделяемой памяти при обработке каждого запроса или соединения.
2. **Агрегация (Aggregation):** Данные из разделяемой памяти агрегируются по зонам (server_zones, location_zones, upstreams) по запросу API.
3. **Экспорт (Export):** API возвращает JSON с текущими значениями счетчиков. При запросе `/status/prometheus` данные преобразуются в формат OpenMetrics.

### Поколение конфигурации (Generation)

Поле `generation` в `/status/angie/` — целочисленный счетчик, который инкрементируется при каждом успешном `reload`. Используется для:
- Идентификации "зомби-воркеров" (процессы со старым поколением после reload).
- Сопоставления метрик с конкретной версией конфигурации при расследовании инцидентов.
- Верификации того, что новая конфигурация применена ко всем воркерам.

### Cache Zone концепция

Зона кэша создается директивой `proxy_cache_path` с параметром `keys_zone`:
```nginx
proxy_cache_path /data/cache keys_zone=my_cache:10m;
```
Зона `my_cache` объемом 10 МБ хранит ключи кэшированных объектов. Чем больше зона, тем больше объектов может быть кэшировано одновременно. Статистика эффективности кэша (HIT/MISS/EXPIRED/STALE) доступна через `/status/http/caches/<zone>/`.

### Модуль metric (пользовательские метрики)

Модуль `metric` позволяет создавать именованные зоны в разделяемой памяти для хранения произвольных числовых значений:
```nginx
http {
    metric_zone my_metrics 64k;
    
    server {
        location / {
            metric_inc my_metrics counter;
        }
    }
}
```
Значения читаются через `/status/http/metric_zones/my_metrics/`. Используется для кастомной бизнес-метрики (количество обработанных заказов, активных сессий и т.д.), которую не покрывают стандартные счетчики.

### Расчет ресурсов разделяемой памяти

Размер зоны (например, `zone status_zone 64k`) является важным параметром тюнинга.
- Минимальный размер зоны в Angie составляет 64 КБ.
- В зоне объемом 64 КБ может храниться статистика примерно для 20–30 уникальных объектов (например, серверов в апстриме).
- Для крупных инсталляций (сотни апстримов) рекомендуется выделять от 1 МБ до 10 МБ на зону.

## Практические сценарии

### Сценарий 1: Глобальный мониторинг HTTP сервера

Активация сбора базовых метрик (запросы, трафик, коды ответов) для всего виртуального хоста.

```nginx
server {
    listen 80;
    server_name production.example.com;

    status_zone production_vhost;

    location / {
        proxy_pass http://app_cluster;
    }
}
```

**Валидация:**
```bash
curl -s http://localhost:8888/status/http/server_zones/production_vhost/ | jq .requests.total
# → 4327
```

### Сценарий 2: Детализация метрик по критическим локациям

Позволяет отделить статистику API от статического контента в рамках одного сервера.

```nginx
server {
    status_zone main_site;

    location /api/v1/ {
        status_zone api_v1_critical;
        proxy_pass http://api_backend;
    }

    location /static/ {
        root /var/www/static;
    }
}
```

### Сценарий 3: Мониторинг групп апстримов (L7)

Обязательное условие для отображения бэкендов в [Console Light](./angie_monitoring_console.md).

```nginx
upstream app_cluster {
    zone app_cluster 128k;
    
    server 10.0.0.1:8080 weight=5;
    server 10.0.0.2:8080 weight=1;
    
    server 10.0.0.3:8080 backup;
}
```

### Сценарий 4: Контроль состояния TCP/UDP сервисов (L4)

```nginx
stream {
    server {
        listen 5432;
        status_zone postgres_proxy;
        proxy_pass pg_cluster;
    }
}
```

### Сценарий 5: Использование stub_status для минимального мониторинга

Для простых проверок доступности (load balancer health check) `stub_status` подходит лучше API — он легче и не требует настройки разделяемой памяти.

```nginx
server {
    listen 8080;

    location /health {
        stub_status;
        allow 10.0.0.0/8;
        deny all;
    }
}
```

**Проверка через curl:**
```bash
curl -s http://localhost:8080/health
# → Active connections: 1
# → server accepts handled requests
# →  123456 123456 234567
# → Reading: 0 Writing: 1 Waiting: 0
```

**Парсинг активных соединений для алертинга:**
```bash
ACTIVE=$(curl -s http://localhost:8080/health | awk '/Active connections/{print $3}')
if [ "$ACTIVE" -gt 1000 ]; then
    echo "ALERT: Active connections above threshold: $ACTIVE"
fi
```

### Сценарий 6: Мониторинг cache zone

Активация статистики кэширования и проверка её через API.

```nginx
http {
    proxy_cache_path /data/cache keys_zone=my_cache:10m;

    server {
        listen 80;
        server_name cache.example.com;

        location / {
            proxy_cache my_cache;
            proxy_pass http://backend_cluster;
        }
    }

    upstream backend_cluster {
        zone backend_cluster 64k;
        server 10.0.0.1:8080;
    }
}
```

**Проверка статистики кэша:**
```bash
curl -s http://localhost:8888/status/http/caches/my_cache/ | jq .
# → {
# →   "size": 10485760,
# →   "used": 5242880,
# →   "cold": 0,
# →   "hit": 1500,
# →   "stale": 5,
# →   "updating": 0
# → }
```

| Поле | Описание |
|:---|:---|
| `size` | Общий размер зоны кэша в байтах |
| `used` | Использовано памяти в байтах |
| `cold` | Объекты, к которым еще не было обращений |
| `hit` | Количество попаданий в кэш |
| `stale` | Устаревшие объекты, ожидающие обновления |
| `updating` | Объекты, в данный момент обновляемые фоновым процессом |

### Сценарий 7: Интеграция с внешним health check

Использование API как источника данных для Nagios/Icinga/Zabbix.

```bash
#!/bin/bash
# /usr/local/bin/check_angie_api.sh

API_URL="http://127.0.0.1:8888/status/angie/"
EXPECTED_VERSION="1.12"

RESPONSE=$(curl -sf --max-time 5 "$API_URL")
if [ $? -ne 0 ]; then
    echo "CRITICAL: Angie API недоступен"
    exit 2
fi

VERSION=$(echo "$RESPONSE" | jq -r '.version')
if [[ ! "$VERSION" =~ ^$EXPECTED_VERSION ]]; then
    echo "WARNING: Версия Angie $VERSION не соответствует ожидаемой $EXPECTED_VERSION"
    exit 1
fi

echo "OK: Angie $VERSION, API доступен"
exit 0
```

**Добавление в monitoring stack:**
```bash
chmod +x /usr/local/bin/check_angie_api.sh

# Проверка вручную
/usr/local/bin/check_angie_api.sh
# → OK: Angie 1.12.2, API доступен
```

### Сценарий 8: SLO / SLI и error budget на метриках Angie

SRE-подход к наблюдаемости: вместо «шумного» порога вручную определяются целевые уровни обслуживания. Общая методология SLI/SLO/error budget — [Методологии мониторинга (Concepts)](../../../Concepts/Observability_and_Monitoring/monitoring_methodologies.md).

**Типовой набор SLI из метрик Angie:**

| SLI | Какая метрика | Источник |
| :--- | :--- | :--- |
| Доступность HTTP-сервиса | `ok / total` по `status` (200/2xx/3xx/) | `status_zone` / Prometheus `angie_http_requests_total` |
| Latency (p95/p99) | Гистограмма `response_time` | `metric_zone` (histogram) |
| Доля медленных запросов | `requests > threshold` к общему числу | Гистограмма `metric_zone` |
| Нагрузка на upstream | `angie_upstream_response_time` | Prometheus |
| Доля 5xx | `sum(rate(angie_http_requests_total{status=~"5.."}[5m])) / sum(rate(...))` | Prometheus |

**Пример записи (recording rule) для SLO по 5xx:**

```yaml
groups:
  - name: angie_sli
    interval: 1m
    rules:
      - record: sli:angie:error_ratio_5m
        expr: |
          sum(rate(angie_http_requests_total{status=~"5.."}[5m]))
          / sum(rate(angie_http_requests_total[5m]))
```

```yaml
# Алерт: бюджет за 30 дней израсходован на 50% (burn rate 0.5 за 6 часов)
  - record: slo:angie:error_budget_burn
    expr: sli:angie:error_ratio_5m / 0.01   # SLO 99% — допустимо 1% ошибок
```

**Практические рекомендации:**

*   Для percentile-метрик используйте histogram из `metric_complex_zone` или агрегируйте `$request_time` из access-log в Prometheus (например, через loki/mimir запись с гистограммой).
*   Привязанный к SLO алертинг предпочтительнее однопроцентного: «error budget burn» даёт точные окна (multi-window, multi-burn-rate) — малый burn на коротком окне игнорируется, большой на длинном — паджит.
*   Каждая гипотеза «SLO нарушен» должна сопровождаться целью доступности: 99% → ~7.3 часа простоя/мес, 99.9% → ~43.8 минут/мес.
*   Метрики поколения (`generation` из `/status/angie/`) используйте как страту для SLI после каждого деплоя конфигурации.

## Операции и команды

### Основные команды curl для проверки работоспособности

```bash
# Проверка доступности API
curl -sf http://127.0.0.1:8888/status/angie/ && echo "API доступен" || echo "API недоступен"

# Получение версии Angie
curl -s http://127.0.0.1:8888/status/angie/ | jq -r '.version'
# → 1.12.2

# Проверка поколения конфигурации
curl -s http://127.0.0.1:8888/status/angie/ | jq -r '.generation'
# → 1

# Список всех server_zones
curl -s http://127.0.0.1:8888/status/http/server_zones/ | jq keys
# → ["main_frontend", "api_v1_critical"]

# Состояние апстрима
curl -s http://127.0.0.1:8888/status/http/upstreams/backend_cluster/ | \
  jq '.peers[] | {server, state, response_time: .health.response_time}'

# Активные соединения
curl -s http://127.0.0.1:8888/status/connections/ | jq .
# → {"accepted":2257,"dropped":0,"active":3,"idle":1}

# Проверка корректности проксирования Console Light
curl -s http://127.0.0.1:8888/console/api/status/angie/ | jq .version
# → "1.12.2"
```

### Проверка поколений воркеров при расследовании инцидентов

```bash
# Получение текущего поколения мастера

ps -eo pid,cmd | grep "angie: worker process"
```

## Устранение неполадок

**API возвращает пустой JSON для upstream:**
- Убедитесь, что в блоке `upstream` указана директива `zone <имя> <размер>;`. Без нее метрики upstream не собираются.

**`config_files` не отображается:**
- Проверьте, что `api_config_files on;` задано в контексте `http` (не в `location`).

**Метрики сбрасываются при `stop`/`start`:**
- Это ожидаемое поведение. Метрики хранятся в разделяемой памяти, которая освобождается при остановке процесса. При `reload` метрики сохраняются.

**Keepalive-соединения не кэшируются:**
- Проверьте `proxy_http_version 1.1;` и `proxy_set_header Connection "";` в location.
- Убедитесь, что бэкенд поддерживает HTTP/1.1 и keepalive.

**Высокое потребление памяти зонами:**
- Проверьте размеры зон через `/status/slabs/`. Для крупных установок увеличьте размер зон (например, `zone app_cluster 2m;`).

**API отвечает медленно:**
- Используйте `pretty=off` для компактного JSON.
- Запрашивайте только нужные подпути (например, `/status/http/upstreams/my_upstream/` вместо `/status/`).

**Пустые метрики после reload:**
- Зоны статуса должны быть созданы до перезагрузки. Убедитесь, что директива `status_zone` присутствует в конфигурации.

**Ошибка: `unknown directive "api"`:**
- Проверьте вывод `angie -V` на наличие `--with-http_api_module`. В официальных пакетах модуль включен по умолчанию.

## Лучшие практики

### Безопасность

1. **Никогда не открывайте API в публичный доступ** без ограничения по IP или аутентификации. Минимальная конфигурация:
   ```nginx
   location /status/ {
       api;
       allow 127.0.0.1;
       deny all;
   }
   ```
2. **Используйте TLS** при доступе к интерфейсу мониторинга через общедоступные сети или VPN.
3. **Отделяйте порт мониторинга** от порта, обслуживающего клиентский трафик. Рекомендуется использовать выделенный `server` блок с `listen 127.0.0.1:8888`.
4. **Включайте `api_config_files on`** только при необходимости просмотра конфигурации и только на внутреннем интерфейсе.

### Производительность

1. **Размер зон разделяемой памяти:** выделяйте память с запасом. Минимальный размер зоны — 64 КБ. Для крупных инсталляций (сотни апстримов) рекомендуется от 1 МБ до 10 МБ на зону.
2. **Избегайте избыточных зон:** каждая `status_zone` потребляет память. Создавайте зоны только для объектов, которые необходимо мониторить.
3. **Оптимизация запросов:** используйте `pretty=off` для снижения объема передаваемых данных и запрашивайте только нужные подпути API.

### Эксплуатация

1. **Именование зон:** используйте префиксы (`http_`, `stream_`, `up_`) для быстрого поиска зон в больших JSON-ответах API.
2. **Верификация после reload:** после каждой модификации конфигурации проверяйте доступность API и корректность отображения критических зон.
3. **Отслеживание поколения:** поле `generation` в `/status/angie/` позволяет сопоставить метрики с конкретной версией конфигурации. Используйте его при анализе инцидентов.
4. **Персистентность:** помните, что метрики в разделяемой памяти сбрасываются при полной остановке сервера (stop/start), но сохраняются при `reload`.

### Отладка

1. **Используйте `angie -T`** для проверки того, что *будет* загружено при следующем старте, и сравнивайте с тем, что *уже* работает через API.
2. **Проверяйте воркеры:** при подозрении на "зомби-воркеры" после reload сравнивайте поколение мастера (`/status/angie/generation`) с поколениями процессов в системе.
3. **Анализ зон:** используйте `/status/slabs/` для проверки использования памяти зонами и своевременного увеличения их размера.

## Дополнительная информация

### Инструменты визуализации и интеграции

- **[Console Light](./angie_monitoring_console.md):** Встроенный веб-интерфейс для оперативного контроля "здесь и сейчас".
- **[Prometheus](./angie_monitoring_prometheus.md):** Нативный экспорт метрик для долгосрочного хранения и алертинг.
- **[Angie Pro](./angie_monitoring_pro.md):** Расширенные возможности мониторинга в коммерческой версии.

### Сравнение инструментов мониторинга

| Инструмент | Применение | История | Масштаб | Алертинг |
|:---|:---|:---|:---|:---|
| **Console Light** | Оперативная отладка "здесь и сейчас" | Нет | Один узел | Нет |
| **API** | Скрипты, health check, интеграция | Нет | Один узел | Через внешние системы |
| **Prometheus + Grafana** | Долгосрочное хранение, тренды, Capacity Planning | Да (месяцы/годы) | Кластер | Нативный (Alertmanager) |

### Рекомендации по эксплуатации

1. **Именование зон:** Используйте префиксы (`http_`, `stream_`, `up_`) для быстрого поиска зон в больших JSON-ответах API.
2. **Безопасность:** Доступ к API (`location /status/`) всегда должен быть ограничен по IP или защищен аутентификацией.
3. **Персистентность:** Помните, что метрики в разделяемой памяти сбрасываются при полной остановке сервера (stop/start), но сохраняются при `reload`.

### Ограничения

1. **Отсутствие истории:** Метрики в разделяемой памяти не сохраняются между полными перезапусками (stop/start). Для долгосрочного хранения используйте Prometheus или внешние системы сбора.
2. **Один узел:** встроенный API и Console Light отображают состояние только того экземпляра Angie, к которому обращен запрос. Для кластерной инфраструктуры требуется централизованная система (Prometheus, Grafana).
3. **Браузерная зависимость:** Console Light требует современного браузера с поддержкой JavaScript и Fetch API.
