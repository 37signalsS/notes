# Мониторинг Angie — Основные концепции

## Определения

**Мониторинг Angie** — процесс сбора, анализа и визуализации метрик производительности и состояния веб-сервера. В отличие от устаревшего модуля `stub_status` в NGINX, Angie предоставляет встроенный **JSON API**, открывающий доступ к сотням метрик в реальном времени.

**Модуль `metric`** — встроенный механизм Angie для создания произвольных пользовательских метрик. Позволяет собирать бизнес-метрики и специализированные метрики производительности. Подробности — в [пользовательских метриках](./angie_monitoring_custom_metrics.md).

## Базовые концепции

### API-мониторинг реального времени vs. анализ логов

Традиционный подход к мониторингу веб-сервера через анализ логов имеет фундаментальные недостатки, которые решает нативный API в Angie:

1. **Ретроспективность логов**: Логи записываются *после* завершения обработки запроса. Это не позволяет отслеживать долгоживущие соединения, медленных клиентов или видеть начало DoS-атаки, когда запросы только начинают накапливаться. API, в свою очередь, показывает метрику `processing` (активные запросы) в реальном времени.
2. **Неполнота данных**: Логи не содержат информации о состоянии внутренних механизмов, таких как **зоны разделяемой памяти** (`slab`) или **зоны кэширования**. Их переполнение может привести к сбоям и недоступности сервиса. API предоставляет полный доступ к этим метрикам.
3. **Неточность и задержки**: Сторонние модули, такие как `vts`, также часто работают в лог-фазе, то есть считают метрики по окончании запроса, что делает их подверженными тем же недостаткам, что и анализ логов. Встроенный API в Angie предоставляет более точные значения непосредственно из рантайма.

### Подходы к мониторингу

1. **Интерактивный мониторинг**: Использование встроенного веб-интерфейса **Angie Console Light** и прямого доступа к **HTTP API** для быстрого обзора состояния сервера в реальном времени.
2. **Долгосрочная аналитика**: Сбор, хранение и визуализация метрик с помощью **Prometheus** и **Grafana** для анализа тенденций и настройки оповещений.

**Баланс между реальным временем и хранением:**

- **Console Light** обращается к API каждую секунду, предоставляя максимально актуальные данные, что идеально для оперативной диагностики.
- **Prometheus** собирает метрики с определённым интервалом (например, 15–30 секунд). Это может приводить к небольшой задержке в отображении данных на дашбордах Grafana, что является компромиссом в пользу эффективности долгосрочного хранения данных.

### Зоны мониторинга (`status_zone` и `metric_zone`)

Чтобы API начал отдавать подробные метрики, необходимо в конфигурации определить **зооны** — именованные области для сбора статистики.

- **`status_zone`**: Используется для сбора стандартной статистики по `server`, `location`, `upstream` и `cache`.
  - Для `server` блока: `status_zone server_example;`
  - Для `location` блока: `status_zone api_v2;`
- **`zone` в `upstream`**: `zone upstream_backend 64k;`
- **`keys_zone` в `proxy_cache_path`**: `proxy_cache_path ... keys_zone=my_cache:10m;`
- **`metric_zone` / `metric_complex_zone`**: Используются для агрегации произвольных метрик. Подробности — в [пользовательских метриках](./angie_monitoring_custom_metrics.md).

## Практические сценарии

### Сценарий 1: Мониторинг API-бэкенда

**Задача:** Отслеживать производительность и доступность бэкенда API.

```nginx
upstream api_backend {
    zone api_backend_zone 64k;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}

server {
    status_zone api_server;

    location /api/v2 {
        status_zone api_v2;
        proxy_pass http://api_backend;
    }
}
```

**Результат:** API отдаёт метрики по upstream (`api_backend_zone`), серверу (`api_server`) и location (`api_v2`) — количество запросов, ошибок, время отклика, активные соединения.

### Сценарий 2: Мониторинг кэширования

**Задача:** Контролировать эффективность кэширования и вовремя обнаруживать переполнение зоны кэша.

```nginx
proxy_cache_path /var/cache/angie levels=1:2 keys_zone=static_cache:10m max_size=1g;

server {
    location /static/ {
        status_zone static_content;
        proxy_cache static_cache;
        proxy_pass http://backend;
    }
}
```

**Результат:** Через API доступны метрики hit/miss ratio кэша, размер зоны, количество записей — что позволяет настраивать алерты на деградацию кэширования.

### Сценарий 3: Бизнес-метрики через `metric_zone`

**Задача:** Отслеживать количество заказов по конкретным эндпоинтам.

```nginx
metric_zone orders_total {
    metric counter $request_uri ~^/api/orders;
}

server {
    metric_zone api_metrics;

    location /api/orders {
        metric_complex_zone orders_by_status;
        proxy_pass http://order_service;
    }
}
```

**Результат:** Пользовательские метрики экспортируются в Prometheus и используются для бизнес-аналитики и алертинга.
