# Мониторинг Angie — Console Light и API

## Определения

**Angie Console Light** (также известный как **Console Lite**) — официальный встроенный веб-интерфейс для интерактивного мониторинга метрик Angie в режиме реального времени. Он представляет собой одностраничное приложение (SPA — Single Page Application), которое визуализирует данные из встроенного HTTP API, позволяя оперативно диагностировать состояние сервера без настройки внешних систем сбора данных.

**HTTP API мониторинга** — программный интерфейс (модуль `ngx_http_api_module`), предоставляющий статистику о работе сервера в формате JSON. Интерфейс позволяет получать данные о запросах, соединениях, состоянии апстримов, кэше, зонах разделяемой памяти и текущей конфигурации.

**Status Zone (Зона статуса)** — именованный сегмент в разделяемой памяти (Shared Memory), предназначенный для хранения атомарных счетчиков и структур данных мониторинга. Директива `status_zone` активирует сбор метрик для конкретных виртуальных хостов, локаций или групп апстримов.

**Shared Memory (Разделяемая память)** — область оперативной памяти, доступная всем рабочим процессам (worker processes) сервера. Критически важный компонент для согласованности метрик: каждый воркер инкрементирует счетчики в общей области, что позволяет получать единую картину состояния всего сервера.

**CORS (Cross-Origin Resource Sharing)** — механизм безопасности браузеров, ограничивающий cross-origin запросы. При развертывании Console Light и API на разных доменах или портах необходимо явно разрешать CORS, иначе браузер заблокирует запросы к API.

**Polling Interval (Интервал опроса)** — период времени, с которым Console Light выполняет повторные запросы к API для обновления данных на Dashboard. По умолчанию интервал составляет около 1 секунды, что обеспечивает near real-time отображение метрик.

## Базовые концепции

### Архитектура взаимодействия

Console Light работает как клиентское приложение. Браузер пользователя загружает статические файлы (HTML, JS, CSS) и выполняет периодические запросы к эндпоинту API.

```
┌─────────────┐      ┌───────────────┐      ┌─────────────┐
│   Browser   │─────>│ Console Light │─────>│  Angie API  │
│  (UI)       │      │  (Static)     │      │  (/status/) │
└─────────────┘      └───────────────┘      └─────────────┘
       ▲                                        │
       │                                        │
       └────────────────────────────────────────┘
              (Periodic polling, ~1 sec)
```

**Жизненный цикл запроса:**
1. Браузер загружает статический индекс (`index.html`) и ассеты (JS, CSS) из каталога Console Light.
2. JavaScript-код инициализирует Dashboard и начинает периодический опрос API (polling).
3. При каждом опросе браузер отправляет GET-запросы к эндпоинтам `/status/http/server_zones/<zone>/`, `/status/http/upstreams/<upstream>/` и другим разделам.
4. API возвращает JSON с текущими значениями счетчиков из разделяемой памяти.
5. Frontend обновляет графики и таблицы без перезагрузки страницы.

### Структура интерфейса (Dashboard)

Интерфейс разделен на логические блоки, соответствующие разделам API:
- **HTTP Zones:** статистика по виртуальным серверам и локациям (запросы, ответы по кодам, трафик).
- **HTTP Upstreams:** состояние групп бэкендов, веса серверов, количество ошибок и время отклика.
- **Caches:** эффективность использования кэша (Hit/Miss/Expired) и заполнение зон памяти.
- **Shared Zones:** использование памяти именованными зонами (`limit_req`, `limit_conn` и др.).
- **Stream:** статистика по TCP/UDP соединениям (L4).
- **Configs:** просмотрщик активных конфигурационных файлов (требует активации `api_config_files on`).

### Безопасность и ограничение доступа

Публикация интерфейса мониторинга в открытый доступ несет риски раскрытия топологии сети и метрик производительности. Рекомендуемые меры защиты:

1. **ACL (Списки доступа):** ограничение доступа по IP через директивы `allow` и `deny`.
2. **Аутентификация:** использование `auth_basic` или `auth_jwt`.
3. **Изоляция:** запуск консоли на выделенном внутреннем порту (например, `127.0.0.1:8888`).
4. **TLS:** обязательное использование HTTPS при доступе через публичные сети или ненадежные каналы.
5. **CORS:** при размещении Console Light на отдельном origin явно настройте заголовки `Access-Control-Allow-Origin` или используйте проксирование внутри того же `server` блока.

### Механизм обновления данных

Console Light использует стратегию **polling** (опроса):
- Каждые ~1 секунду браузер отправляет параллельные GET-запросы ко всем активным разделам API.
- При получении данных Dashboard выполняет пересчет агрегированных показателей (RPS, процент ошибок, среднее время отклика) на стороне клиента.
- При ошибке запроса (сеть, таймаут, 5xx) интерфейс отображает индикатор недоступности данных, но не прерывает работу.

## Практические сценарии

### Сценарий 1: Установка и развертывание

Пакет консоли устанавливается отдельно и содержит только статический контент.

```bash
# Ubuntu/Debian
sudo apt-get update
sudo apt-get install angie-console-light

# RHEL/AlmaLinux/Rocky Linux
sudo dnf install angie-console-light

# Проверка установки
ls -la /usr/share/angie-console-light/html/
# → index.html  static/  ...
```

**По умолчанию:**
- Путь к статическим файлам: `/usr/share/angie-console-light/html/`
- Пакет не создает серверный блок автоматически — требуется ручная конфигурация.

### Сценарий 2: Типовая конфигурация сервера мониторинга

Для корректной работы Console Light должна иметь доступ к API по относительному пути `/api/`. Наиболее надежный способ — проксирование внутри того же `server` блока для обхода политик CORS.

```nginx
server {
    listen 127.0.0.1:8888;
    server_name monitor.local;

    # Доступ только из внутренней сети
    allow 192.168.1.0/24;
    deny all;

    # Основной интерфейс
    location /console/ {
        alias /usr/share/angie-console-light/html/;
        index index.html;

        # Внутреннее проксирование к API
        location /console/api/ {
            api /status/;
        }
    }

    # Прямой доступ к API для внешних систем
    location /status/ {
        api;
        allow 127.0.0.1;
        deny all;
    }
}
```

**Валидация конфигурации:**
```bash
# Проверка синтаксиса
sudo angie -t

# Применение конфигурации
sudo angie -s reload

# Проверка доступности статики
curl -s http://127.0.0.1:8888/console/ | head -n 5
# → <!DOCTYPE html>
# → <html lang="en">
# → ...

# Проверка проксирования API (через консоль)
curl -s http://127.0.0.1:8888/console/api/status/angie/ | jq .version
# → "1.12.2"
```

### Сценарий 3: Активация детального мониторинга объектов

Console Light отображает данные только для тех объектов, для которых явно созданы зоны в памяти.

```nginx
http {
    # Для мониторинга кэша
    proxy_cache_path /data/cache keys_zone=my_cache:10m;

    # Для доступа к конфигурационным файлам через API
    api_config_files on;

    server {
        status_zone main_frontend; # Появится в разделе HTTP Zones

        location / {
            proxy_pass http://backend_cluster;
        }
    }

    upstream backend_cluster {
        zone backend_cluster 64k; # Обязательно для отображения в Upstreams
        server 10.0.0.1:8080;
    }
}
```

**Валидация:**
```bash
# Проверка наличия зон в API
curl -s http://127.0.0.1:8888/status/http/server_zones/ | jq keys
# → ["main_frontend"]

curl -s http://127.0.0.1:8888/status/http/upstreams/backend_cluster/ | jq .peers | keys
# → ["10.0.0.1:8080"]
```

### Сценарий 4: Диагностика производительности в реальном времени

Вкладка **Upstreams** позволяет отслеживать `Response Time` (время ответа бэкенда). Если среднее время ответа растет при стабильном количестве запросов, это указывает на деградацию производительности приложения.

**Практический чек-лист:**
```bash
# 1. Получение текущих значений response_time для всех пиров
curl -s http://127.0.0.1:8888/status/http/upstreams/backend_cluster/ | \
  jq '.peers[] | {server: .server, response_time: .health.response_time, state: .state}'

# 2. Сравнение с базовой линией (если есть исторические данные)
# Ожидаемый результат: response_time в пределах нормального для вашего SLO

# 3. Проверка количества активных соединений
curl -s http://127.0.0.1:8888/status/http/upstreams/backend_cluster/ | \
  jq '.peers[] | {server: .server, active: .selected.current}'
```

### Сценарий 5: Развертывание с TLS и внешним доступом

Для доступа к Console Light через публичные сети или VPN настройте HTTPS-терминацию.

```nginx
server {
    listen 443 ssl http2;
    server_name monitor.example.com;

    ssl_certificate     /etc/angie/ssl/monitor.example.com.crt;
    ssl_certificate_key /etc/angie/ssl/monitor.example.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;

    # Ограничение доступа по IP/VPN
    allow 10.0.0.0/8;
    allow 192.168.0.0/16;
    deny all;

    location /console/ {
        alias /usr/share/angie-console-light/html/;
        index index.html;

        location /console/api/ {
            api /status/;
        }
    }

    location /status/ {
        api;
        allow 127.0.0.1;
        deny all;
    }
}
```

**Валидация:**
```bash
# Проверка SSL-сертификата
curl -I https://monitor.example.com/console/
# → HTTP/2 200
# → server: Angie

# Проверка блокировки неразрешенных IP
curl -s https://monitor.example.com/console/api/status/angie/
# → 403 Forbidden (при запросе из вне диапазона allow)
```

### Сценарий 6: Мониторинг через systemd-сервис с автозапуском

Настройка Angie с активированным API и Console Light как системный сервис.

```bash
# Проверка статуса сервиса
systemctl status angie

# Включение автозапуска
sudo systemctl enable --now angie

# Проверка активного порта
ss -tlnp | grep angie
# → LISTEN 0 128 127.0.0.1:8888 ... angie
```

**Валидация после перезагрузки:**
```bash
# Перезагрузка сервиса
sudo systemctl restart angie

# Проверка доступности API после перезагрузки
curl -s http://127.0.0.1:8888/status/angie/ | jq .generation
# → 1 (или больше, если было несколько reload)

# Важно: метрики в разделяемой памяти сохраняются при reload,
# но сбрасываются при полной остановке (stop/start)
```

### Сценарий 7: Интеграция с внешними health check

Console Light можно использовать как источник данных для простых health check-скриптов.

```bash
#!/bin/bash
# /usr/local/bin/check_angie_api.sh

API_URL="http://127.0.0.1:8888/status/angie/"
EXPECTED_VERSION="1.12"

RESPONSE=$(curl -sf --max-time 5 "$API_URL")
if [ $? -ne 0 ]; then
    echo "CRITICAL: Angie API недоступен"
    exit 2
fi

VERSION=$(echo "$RESPONSE" | jq -r '.version')
if [[ ! "$VERSION" =~ ^$EXPECTED_VERSION ]]; then
    echo "WARNING: Версия Angie $VERSION не соответствует ожидаемой $EXPECTED_VERSION"
    exit 1
fi

echo "OK: Angie $VERSION, API доступен"
exit 0
```

**Добавление в monitoring stack:**
```bash
chmod +x /usr/local/bin/check_angie_api.sh

# Проверка вручную
/usr/local/bin/check_angie_api.sh
# → OK: Angie 1.12.2, API доступен

# Для Nagios/Icinga/Zabbix — вызов скрипта через External Check
```

## Операции и команды

### Основные эндпоинты API для Console Light

Console Light опрашивает следующие разделы API. Полную таблицу эндпоинтов см. в [Работа с конфигурацией через API](./angie_monitoring_api.md).

| Эндпоинт | Назначение в Console Light | Пример curl |
|:---|:---|:---|
| `/status/` | Корневой объект, проверка доступности API | `curl -s http://localhost:8888/status/` |
| `/status/angie/` | Версия, поколение, время загрузки | `curl -s http://localhost:8888/status/angie/` |
| `/status/connections/` | Активные/простаивающие соединения | `curl -s http://localhost:8888/status/connections/` |
| `/status/http/server_zones/<zone>/` | Метрики виртуального хоста | `curl -s http://localhost:8888/status/http/server_zones/main_frontend/` |
| `/status/http/location_zones/<zone>/` | Метрики локации | `curl -s http://localhost:8888/status/http/location_zones/api_v1/` |
| `/status/http/upstreams/<upstream>/` | Состояние бэкендов | `curl -s http://localhost:8888/status/http/upstreams/backend_cluster/` |
| `/status/http/caches/<zone>/` | Статистика кэша | `curl -s http://localhost:8888/status/http/caches/my_cache/` |
| `/status/stream/server_zones/<zone>/` | Метрики TCP/UDP серверов | `curl -s http://localhost:8888/status/stream/server_zones/postgres_proxy/` |

### Полезные команды для диагностики

```bash
# Проверка доступности API
curl -sf http://127.0.0.1:8888/status/angie/ && echo "API доступен" || echo "API недоступен"

# Получение версии Angie
curl -s http://127.0.0.1:8888/status/angie/ | jq -r '.version'
# → 1.12.2

# Проверка поколения конфигурации
curl -s http://127.0.0.1:8888/status/angie/ | jq -r '.generation'
# → 1

# Список всех server_zones
curl -s http://127.0.0.1:8888/status/http/server_zones/ | jq keys
# → ["main_frontend", "api_v1_critical"]

# Состояние апстрима
curl -s http://127.0.0.1:8888/status/http/upstreams/backend_cluster/ | \
  jq '.peers[] | {server, state, response_time: .health.response_time}'

# Активные соединения
curl -s http://127.0.0.1:8888/status/connections/ | jq .
# → {"accepted":2257,"dropped":0,"active":3,"idle":1}

# Проверка корректности проксирования Console Light
curl -s http://127.0.0.1:8888/console/api/status/angie/ | jq .version
# → "1.12.2"
```

## Устранение неполадок

| Проблема | Возможная причина | Решение |
|:---|:---|:---|
| **Интерфейс загружается, но данных нет** | Ошибка CORS или неверный путь к API. | Проверьте наличие `location /console/api/` с директивой `api`. Убедитесь, что проксирование настроено внутри того же `server` блока. |
| **Ошибка 403 Forbidden** | Сработали ограничения `allow/deny` или `auth_basic`. | Проверьте IP-адрес клиента и настройки доступа в блоке `server`. |
| **Список Upstreams пуст** | В блоке `upstream` отсутствует директива `zone`. | Добавьте `zone <name> <size>;` в конфигурацию апстрима. |
| **Не работает вкладка Configs** | Директива `api_config_files` установлена в `off`. | Установите `api_config_files on;` в контексте `http`. |
| **Данные не обновляются** | Низкая скорость сети или блокировка JS-скриптов. | Проверьте консоль разработчика в браузере (F12) на наличие ошибок сети. |
| **Ошибка: `unknown directive "api"`** | Модуль `ngx_http_api_module` не загружен. | Проверьте вывод `angie -V` на наличие `--with-http_api_module`. В официальных пакетах модуль включен по умолчанию. |
| **CORS-ошибка в консоли браузера** | Console Light и API размещены на разных origins. | Настройте проксирование внутри одного `server` блока или добавьте заголовки `add_header Access-Control-Allow-Origin`. |
| **Пустые метрики после reload** | Зоны статуса не были созданы до перезагрузки. | Убедитесь, что директива `status_zone` присутствует в конфигурации до reload. |
| **Метрики сбрасываются при restart** | Разделяемая память resides в RAM. | Это ожидаемое поведение. Для персистентности используйте внешние системы сбора (Prometheus, Grafana). |

## Лучшие практики

### Безопасность

1. **Никогда не открывайте API в публичный доступ** без ограничения по IP или аутентификации. Минимальная конфигурация:
   ```nginx
   location /status/ {
       api;
       allow 127.0.0.1;
       deny all;
   }
   ```
2. **Используйте TLS** при доступе к Console Light через общедоступные сети или VPN.
3. **Отделяйте порт мониторинга** от порта, обслуживающего клиентский трафик. Рекомендуется использовать выделенный `server` блок с `listen 127.0.0.1:8888`.
4. **Включайте `api_config_files on`** только при необходимости просмотра конфигурации и только на внутреннем интерфейсе.

### Производительность

1. **Размер зон разделяемой памяти:** выделяйте память с запасом. Минимальный размер зоны — 64 КБ. Для крупных инсталляций (сотни апстримов) рекомендуется от 1 МБ до 10 МБ на зону.
2. **Избегайте избыточных зон:** каждая `status_zone` потребляет память. Создавайте зоны только для объектов, которые необходимо мониторить.
3. **Polling overhead:** Console Light опрашивает API каждые ~1 секунду. При большом количестве одновременно открытых Dashboard это создает дополнительную нагрузку. Для фоновых систем сбора данных используйте нативный экспорт Prometheus (см. [Интеграция с Prometheus](./angie_monitoring_prometheus.md)).

### Эксплуатация

1. **Именование зон:** используйте префиксы (`http_`, `stream_`, `up_`) для быстрого поиска зон в больших JSON-ответах API.
2. **Верификация после reload:** после каждой модификации конфигурации проверяйте доступность API и корректность отображения критических зон.
3. **Отслеживание поколения:** поле `generation` в `/status/angie/` позволяет сопоставить метрики с конкретной версией конфигурации. Используйте его при анализе инцидентов.
4. **Резервное копирование:** Console Light — только статический контент. Для восстановления интерфейса достаточно переустановить пакет `angie-console-light`. Конфигурация сервера (server block) должна храниться в конфигурационных файлах Angie.

### Отладка

1. **Используйте `angie -T`** для проверки того, что *будет* загружено при следующем старте, и сравнивайте с тем, что *уже* работает через API.
2. **Проверяйте воркеры:** при подозрении на "зомби-воркеры" после reload сравнивайте поколение мастера (`/status/angie/generation`) с поколениями процессов в системе.
3. **Консоль разработчика:** при проблемах с отображением данных в Console Light открывайте DevTools (F12) и проверяйте сетевые запросы на предмет ошибок CORS, 403, 404.

## Дополнительная информация

### Сравнение с Prometheus

| Характеристика | Console Light / API | Prometheus + Grafana |
|:---|:---|:---|
| **Гранулярность** | Реал-тайм (~1 сек) | Интервал сбора (от 15 сек) |
| **История** | Отсутствует | Глубина хранения месяцы/годы |
| **Масштаб** | Один узел Angie | Весь кластер и инфраструктура |
| **Назначение** | Оперативная отладка и reload | Тренды, алертинг, Capacity Planning |
| **Overhead** | Минимальный (браузер опрашивает API) | Зависит от частоты скрапинга и числа targets |
| **Алертинг** | Отсутствует | Нативный (Alertmanager) |

### Возможности Angie Pro

В коммерческой версии Console Pro поддерживает **режим записи** (`write=on`). Это позволяет администратору через веб-интерфейс:
- Менять веса серверов "на лету".
- Выводить серверы из балансировки (`down`) или переводить в режим дообслуживания (`drain`).
- Сбрасывать счетчики статистики без перезапуска сервера.
- Управлять KV-зонами и просматривать latency percentiles.

### Рекомендации по выбору инструмента

- **Console Light** — для оперативной диагностики "здесь и сейчас" при разработке конфигурации или расследовании инцидента.
- **API** — для интеграции с внутренними скриптами, health check и мониторинговыми системами.
- **Prometheus + Grafana** — для долгосрочного хранения метрик, алертинга и Capacity Planning.
- **Angie Pro Console** — для динамического управления трафиком без редактирования конфигурационных файлов.

### Ограничения

1. **Отсутствие истории:** Console Light не хранит исторические данные. После перезагрузки сервера (stop/start) метрики в разделяемой памяти сбрасываются.
2. **Один узел:** интерфейс отображает состояние только того экземпляра Angie, к которому обращен запрос. Для кластерной инфраструктуры требуется открывать Console Light для каждого узла отдельно или использовать централизованные системы (Prometheus, Grafana).
3. **Браузерная зависимость:** корректная работа требует современного браузера с поддержкой JavaScript и Fetch API. Устаревшие браузеры могут не отображать Dashboard.
