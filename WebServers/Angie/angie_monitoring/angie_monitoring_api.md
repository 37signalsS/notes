# Мониторинг Angie — Работа с конфигурацией через API

## Определения

**API конфигурации Angie** — расширенный программный интерфейс, позволяющий не только читать метрики, но и получать текущую активную конфигурацию сервера, отслеживать версии (поколения) процессов и управлять состоянием узлов (в Angie PRO). 

**Ключевое отличие от `angie -T`**: Команда `angie -T` читает и парсит файлы с диска. API отдаёт конфигурацию, которую мастер-процесс Angie *уже загрузил и использует в рантайме*. Это критически важно для диагностики в случаях, когда файлы на диске были изменены, перемещены или удалены после запуска или последнего `reload`.

## Базовые концепции

### Директива `api_config_files`

По умолчанию Angie не отдает содержимое файлов конфигурации через API из соображений безопасности. Для активации этой возможности используется директива `api_config_files`.

- **Синтаксис:** `api_config_files on | off;`
- **Контекст:** `http`
- **Значение по умолчанию:** `off`

При включении этой опции сервер индексирует все загруженные файлы (включая основной `angie.conf` и все `include`) и делает их доступными по эндпоинту `/status/angie/config_files/`.

### Поколения конфигурации (Configuration Generation)

Каждый рабочий процесс (worker process) связан с определённым **поколением** конфигурации. 
1. При запуске сервера generation равен `1`.
2. При выполнении `reload` (`angie -s reload` или сигнал `HUP`) номер поколения в мастере инкрементируется.
3. Новые воркеры запускаются с актуальным номером поколения.
4. Старые воркеры продолжают дообслуживать соединения, после чего завершаются.

Это позволяет:
- Подтвердить успешное применение изменений (смена номера в API).
- Обнаружить «зависшие» процессы предыдущих поколений.
- Диагностировать проблемы с плавным перезапуском.

## Практические сценарии

### Сценарий 1: Получение текущей рантайм-конфигурации

Используется для сверки того, что сервер действительно работает на ожидаемых настройках, особенно если автоматизация (Ansible/Terraform) изменила файлы на диске, но `reload` еще не был выполнен.

```nginx
http {
    api_config_files on; # Разрешаем чтение файлов через API

    server {
        listen 8888;
        
        location /api/ {
            api /status/; # Точка входа API
            
            allow 127.0.0.1;
            deny all;
        }
    }
}
```

**Работа через CLI:**
```bash
# Получить список всех файлов, которые видит мастер-процесс
curl -s http://127.0.0.1:8888/api/status/angie/config_files/ | jq

# Получить содержимое angie.conf в виде JSON (с метаданными)
curl -s http://127.0.0.1:8888/api/status/angie/config_files/etc/angie/angie.conf
```

### Сценарий 2: Отслеживание смены поколений и жизненного цикла процессов

```bash
# 1. Проверяем текущее поколение мастера
curl -s http://127.0.0.1:8888/api/status/angie/ | jq .generation
# → 5

# 2. Сравнение с процессами в ОС
ps aux | grep angie
# → angie: worker process (gen=5) # Актуальный
# → angie: worker process (gen=4) # Старый, до сих пор не завершился
```

Если старый процесс остается в `ps` долгое время, это сигнал о наличии долгоживущих соединений (WebSocket, HTTP2 Streams) или блокировок в коде модулей.

### Сценарий 3: Диагностика проблем применения конфигурации

Если после `reload` номер поколения в эндпоинте `/status/angie/` не изменился, значит конфигурация не применилась. В этом случае необходимо проверить синтаксические ошибки:

```bash
angie -t # Проверка файлов на диске
```

## Безопасность

Экспорт конфигурации через API несет высокие риски, так как файлы могут содержать:
- Пути к SSL-сертификатам и ключам.
- IP-адреса и порты внутренней инфраструктуры.
- Секретные заголовки и логику авторизации.

**Рекомендации:**
1. **ACL:** Всегда используйте `allow/deny` для ограничения доступа к `/api/`.
2. **TLS:** Используйте HTTPS для доступа к эндпоинтам мониторинга.
3. **Минимизация:** Не включайте `api_config_files` без явной необходимости в промышленной эксплуатации.

## Дополнительная информация

- **Доступность:** Файлы конфигурации доступны только при включённой директиве `api`.
- **Ограничения:** Эндпоинт возвращает только те файлы, которые были успешно загружены при старте или последнем reload.
- **Персистентность:** Поколение хранится в разделяемой памяти зоны `status` и сбрасывается только при полной остановке процесса (cold start).
