# Graceful Reload и Binary Upgrade в Angie

**Актуально для:** Angie 1.12.x / Angie PRO 1.12.x

## Определения

**Graceful reload** — процедура горячего применения новой конфигурации без разрыва клиентских сетевых соединений: master-процесс выполняет парсинг и валидацию файлов конфигурации, открывает новые слушающие сокеты, запускает воркеры нового поколения и инициирует плавное завершение старых воркеров.

**Graceful shutdown** — процедура мягкой остановки процесса (worker или master): процесс прекращает прием новых входящих запросов, закрывает слушающие сокеты и дообслуживает ранее установленные сетевые сессии клиентов в пределах отведенного тайм-аута.

**Binary upgrade** — процедура замены исполняемого файла веб-сервера на лету (Zero-Downtime) без остановки сервиса и потери соединений: старый master-процесс порождает новый экземпляр сервера, передавая ему дескрипторы открытых слушающих сокетов.

**`.oldbin`** — служебный файл с идентификатором процесса (`/run/angie.pid.oldbin`), в который переименовывается PID-файл старого мастера в момент инициализации нового бинарного экземпляра.

**Поколение конфигурации (Generation)** — монотонно возрастающий целочисленный счетчик ревизий конфигурации master-процесса. Инкрементируется при каждом успешном reload, отображается в именах рабочих процессов в ОС (`ps`) и экспортируется через Status API (`/status/angie/`).

**`worker_shutdown_timeout`** — директива верхнего уровня конфигурации (`main`), ограничивающая максимальное время, предоставляемое рабочим процессам на дообслуживание соединений при graceful shutdown перед их принудительным закрытием.

**Master/Worker процессная модель** — архитектура разделения привилегий и задач: управляющий master-процесс работает с правами суперпользователя (`root`) для открытия привилегированных портов (<1024) и управления дочерними процессами, а непривилегированные worker-процессы (пользователь `angie`) изолированно обрабатывают сетевой трафик.

**IPC (Inter-Process Communication)** — внутренний механизм обмена сообщениями ядра между master-процессом и worker-процессами через пары локальных сокетов (`socketpair`), используемый для передачи команд жизненного цикла (`SIGQUIT`, `open logs`).

## Архитектура и принцип работы

### Модель процессов и распределение ролей

В архитектуре Angie функционируют несколько категорий процессов:

1. **Master-процесс (`root`):**
   * Считывает и валидирует конфигурационные файлы (`angie.conf` и директории `conf.d/`).
   * Создает и связывает слушающие сетевые сокеты (`bind()`, `listen()`).
   * Выделяет и инициализирует сегменты разделяемой памяти (Shared Memory Zones).
   * Управляет жизненным циклом рабочих процессов через системные сигналы и внутренние каналы IPC.
2. **Worker-процессы (`angie`):**
   * Работают в неблокирующем цикле обработки событий ввода-вывода ядра (`epoll` в Linux).
   * Принимают входящие TCP/UDP-соединения (`accept()`), выполняют TLS-терминацию, маршрутизацию HTTP-запросов и проксирование на бэкенды.
   * При получении команды на остановку выходят из цикла прослушивания сокетов и завершают активные транзакции.
3. **Вспомогательные процессы (`Cache Manager`, `Cache Loader`):**
   * `Cache Loader` — отрабатывает при старте для загрузки метаданных кэша с диска в разделяемую память `keys_zone`.
   * `Cache Manager` — периодически выполняет очистку устаревших элементов дискового кэша в соответствии с лимитами `max_size`.

```
                       [ Angie Master Process ] (PID 14205, root)
                             | (IPC socketpair / POSIX Signals)
          ┌──────────────────┼──────────────────┬──────────────────┐
          ▼                  ▼                  ▼                  ▼
    [ Worker #1 ]      [ Worker #2 ]      [ Cache Loader ]   [ Cache Manager ]
     (user: angie)      (user: angie)      (user: angie)      (user: angie)
          │                  │
          └─────────┬────────┘
                    ▼
     [ Shared Memory (shm) ] ── (status_zone, limit_req, proxy_cache, upstream)
```

### Механика Graceful Reload (SIGHUP)

Когда администратор или система автоматизации отправляет сигнал `SIGHUP` мастер-процессу (через `systemctl reload angie` или `angie -s reload`), выполняется следующий алгоритм:

```
[ SIGHUP получен ]
       │
       ▼
[ Парсинг и тест новой конфигурации ] ── Ошибка ──► [ Откат: логирование в error.log, ]
       │ Успех                                      [ старые воркеры продолжают работу ]
       ▼
[ Открытие новых сокетов и log-файлов ]
       │
       ▼
[ Инициализация / обновление Shared Memory ]
       │
       ▼
[ Инкремент Generation (например, #1 -> #2) ]
       │
       ▼
[ Запуск нового пула Worker-процессов ] ──► [ Новые воркеры принимают соединения ]
       │
       ▼
[ Команда Graceful Shutdown старым воркерам ]
       │
       ▼
[ Старые воркеры закрывают listen-сокеты ]
       │
       ├─► [ Обработка активных клиентских сессий ]
       │         │
       │         ▼
       │   [ Сессия завершена ] ──► [ Воркер завершает работу ]
       │
       └─► [ Достигнут worker_shutdown_timeout ]
                 │
                 ▼
           [ Принудительный сброс сокетов (RST) и выход ]
```

1. **Валидация:** Master проверяет синтаксис файлов, корректность директив и доступность путей. В случае ошибки мастер фиксирует событие в `error.log`, отменяет операцию и продолжает бесперебойно работать со старой стабильной конфигурацией.
2. **Сетевые ресурсы:** Мастер открывает новые сетевые сокеты (если в конфигурацию были добавлены новые директивы `listen`) и открывает новые дескрипторы журналов.
3. **Разделяемая память:** Master сопоставляет существующие `shm`-зоны с новыми. Зоны с неизменными параметрами переиспользуются без потери текущих счетчиков и состояний.
4. **Смена поколений:** Счетчик `generation` увеличивается на единицу. Запускаются новые worker-процессы с обновленными настройками.
5. **Дренирование (Draining):** Старым worker-процессам отправляется команда прекратить прием новых запросов. Они удаляют слушающие сокеты из своего цикла `epoll`, но продолжают обрабатывать уже принятые сетевые соединения.
6. **Keep-Alive сессии:** На открытых idle-соединениях старые воркеры инициируют закрытие, отправляя заголовок `Connection: close` в очередном ответе.
7. **Контроль времени:** Если соединение удерживается клиентом дольше `worker_shutdown_timeout`, процесс принудительно обрывает сокет и завершается, предотвращая утечку процессов.

### Механика Zero-Downtime Binary Upgrade (USR2 -> WINCH -> QUIT)

Процедура обновления бинарного файла веб-сервера без простоя основана на наследовании открытых файловых дескрипторов сокетов через системный вызов ядра `execve()`:

```
Фаза 1: Замена бинарного файла на диске (пакетный менеджер / сборка)
Фаза 2: kill -USR2 <Старый Master PID>
        ├─► Переименование /run/angie.pid в /run/angie.pid.oldbin
        ├─► Экспорт дескрипторов сокетов в окружение NGINX="<fd1>:<fd2>..."
        └─► execve(/usr/sbin/angie) ──► Старт Нового Master (PID 21450)
                                            └─► Запуск Новых Воркеров (Gen #1)
                                                 [Оба пула обслуживают трафик]

Фаза 3: kill -WINCH <Старый Master PID>
        └─► Старый Master останавливает своих воркеров.
            Старый Master спит в памяти (готов к откату).
            [100% трафика обслуживает Новый бинарник]

Фаза 4 (Успех): kill -QUIT <Старый Master PID>
        └─► Старый Master удаляет /run/angie.pid.oldbin и завершается.

Фаза 4 (Откат при сбое):
        ├─► kill -HUP <Старый Master PID>  (Старый мастер поднимает свои воркеры)
        └─► kill -TERM <Новый Master PID> (Новый мастер экстренно останавливается)
```

#### Сохранение Shared Memory и кэша на диске при обновлении бинарника

При переходе на новый бинарник Angie производит сброс метаданных разделяемой памяти на диск:
* Зоны кэширования `proxy_cache_path` сохраняют структуру ключей `keys_zone`, предотвращая «холодный старт» кэша.
* Новому мастер-процессу не требуется проводить полную повторную индексацию терабайтных дисковых массивов кэша процессом `cache loader`, что исключает пиковую нагрузку на подсистему дискового ввода-вывода (I/O).

#### Особенности взаимодействия с ядром: SO_REUSEPORT

При использовании директивы `listen ... reuseport;` ядро Linux балансирует входящие SYN-пакеты между слушающими сокетами разных воркеров через хэширование кортежа IP/порт. 
* Во время reload новые воркеры открывают свои сокеты `SO_REUSEPORT`.
* До закрытия сокетов старыми воркерами ядро продолжает распределять часть новых TCP SYN-пакетов в их очереди прослушивания.
* В современных версиях ядра Linux (>= 4.5) закрытие сокета старым воркером корректно перераспределяет незавершенные соединения из очереди `listen backlog` на оставшиеся активные сокеты, предотвращая отброс пакетов (SYN drops).

## Практические сценарии и конфигурация

### Сценарий 1: Настройка тайм-аутов graceful shutdown в `angie.conf`

Для надежной работы production-контуров необходимо гарантировать завершение старых воркеров и согласовать тайм-ауты веб-сервера с системным менеджером systemd.

Файл конфигурации `/etc/angie/angie.conf`:

```nginx
# Глобальный контекст конфигурации (main)
user angie;
worker_processes auto;
worker_rlimit_nofile 65535;
pid /run/angie.pid;

# Предельное время ожидания завершения активных соединений старыми воркерами
# Для REST API и микросервисов: 15s - 30s
# Для сервисов с WebSocket, gRPC или передачей больших файлов: 60s - 120s
worker_shutdown_timeout 30s;

events {
    worker_connections 8192;
    use epoll;
    multi_accept on;
}

http {
    include /etc/angie/mime.types;
    default_type application/octet-stream;

    # Тайм-аут ожидания запроса по keep-alive соединению
    # Должен быть меньше worker_shutdown_timeout
    keepalive_timeout 25s;

    # Тайм-аут передачи тела запроса клиентом
    client_body_timeout 15s;

    # Тайм-аут передачи ответа клиенту
    send_timeout 15s;

    include /etc/angie/conf.d/*.conf;
}
```

#### Согласование с systemd `TimeoutStopSec`

Если в unit-файле systemd значение `TimeoutStopSec` меньше, чем `worker_shutdown_timeout`, systemd отправит сигнал `SIGKILL` до того, как воркеры Angie успеют дообслужить клиентские сессии.

Создайте drop-in файл `/etc/systemd/system/angie.service.d/timeout.conf`:

```ini
[Service]
# Время ожидания остановки сервиса должно превышать worker_shutdown_timeout на 10-15 секунд
TimeoutStopSec=45s
```

Примените изменения в systemd:

```bash
sudo systemctl daemon-reload
# → перезагрузка конфигурации юнитов выполнена
```

### Сценарий 2: Штатный Graceful Reload в Production

Стандартный регламент применения изменений конфигурации.

#### 1. Предварительная проверка синтаксиса

Перед отправкой сигнала всегда выполняйте синтаксический тест:

```bash
sudo angie -t
# → angie: the configuration file /etc/angie/angie.conf syntax is ok
# → angie: configuration file /etc/angie/angie.conf test is successful
```

#### 2. Выполнение reload через systemd

```bash
sudo systemctl reload angie
# → reload выполнен штатно
```

Или через утилиту командной строки Angie:

```bash
sudo angie -s reload
# → сигнал SIGHUP отправлен мастер-процессу
```

#### 3. Валидация успешности смены поколения

Проверьте процессы в операционной системе:

```bash
ps -eo pid,ppid,cmd | grep "angie: worker process"
# → 15410 14205 angie: worker process #2
# → 15411 14205 angie: worker process #2
```

Запросите текущее поколение через встроенный Status API Angie:

```bash
curl -sf http://127.0.0.1:8888/status/angie/ | jq '{version, generation, uptime_sec: .uptime}'
```

Ожидаемый вывод:
```json
{
  "version": "1.12.3",
  "generation": 2,
  "uptime_sec": 3600
}
```

### Сценарий 3: Zero-Downtime Binary Upgrade на лету

Пошаговая процедура обновления версии исполняемого файла без разрыва установленных соединений.

```bash
# Шаг 1. Обновите пакет в операционной системе
# На Debian/Ubuntu:
sudo apt-get update && sudo apt-get --only-upgrade install angie -y
# На AlmaLinux/RHEL/РЕД ОС:
sudo dnf upgrade angie -y

# Шаг 2. Убедитесь, что новый бинарник валиден и понимает текущий конфиг
sudo angie -t
# → angie: the configuration file /etc/angie/angie.conf syntax is ok
# → angie: configuration file /etc/angie/angie.conf test is successful

# Шаг 3. Зафиксируйте PID текущего мастера
OLD_MASTER_PID=$(cat /run/angie.pid)
echo "PID старого мастера: ${OLD_MASTER_PID}"
# → PID старого мастера: 14205

# Шаг 4. Отправьте сигнал SIGUSR2 мастер-процессу
sudo kill -USR2 "${OLD_MASTER_PID}"
sleep 2

# Шаг 5. Убедитесь, что запустился второй мастер и создан файл .oldbin
ls -la /run/angie.pid*
# → -rw-r--r-- 1 root root 6 Oct 14 19:15 /run/angie.pid
# → -rw-r--r-- 1 root root 6 Oct 14 19:10 /run/angie.pid.oldbin

NEW_MASTER_PID=$(cat /run/angie.pid)
echo "Старый Master: $(cat /run/angie.pid.oldbin), Новый Master: ${NEW_MASTER_PID}"
# → Старый Master: 14205, Новый Master: 21450

# Шаг 6. Проверьте дерево процессов (должно работать 2 мастера и 2 набора воркеров)
ps -ef --forest | grep -E "[a]ngie"
# → root     14205     1  0 19:10 ?  angie: master process /usr/sbin/angie
# → angie    14206 14205  0 19:10 ?   \_ angie: worker process #1
# → root     21450 14205  0 19:15 ?   \_ angie: master process /usr/sbin/angie
# → angie    21451 21450  0 19:15 ?       \_ angie: worker process #1

# Шаг 7. Переведите воркеров старого мастера в graceful shutdown (SIGWINCH)
sudo kill -WINCH "${OLD_MASTER_PID}"
sleep 2

# Шаг 8. Проверьте, что старые воркеры завершились, а новый мастер держит трафик
ps -ef --forest | grep -E "[a]ngie"
# → root     14205     1  0 19:10 ?  angie: master process /usr/sbin/angie
# → root     21450 14205  0 19:15 ?   \_ angie: master process /usr/sbin/angie
# → angie    21451 21450  0 19:15 ?       \_ angie: worker process #1

# Шаг 9. Выполните проверку работоспособности сервиса (Smoke Test)
curl -sI http://127.0.0.1/ | grep -E "HTTP/|server:"
# → HTTP/1.1 200 OK
# → server: Angie/1.12.3

# Шаг 10. Успешный финал: завершите старый мастер-процесс (SIGQUIT)
sudo kill -QUIT "${OLD_MASTER_PID}"
sleep 1

# Проверка: остался только новый мастер с новым PID
test ! -f /run/angie.pid.oldbin && echo "Обновление завершено успешно!"
# → Обновление завершено успешно!
```

### Сценарий 4: Алгоритм Rollback при проблеме с новым бинарником

Если на шаге 8 или 9 выяснилось, что новая версия работает некорректно (падения, деградация ответов), выполните быстрый откат к старому мастеру:

```bash
OLD_MASTER_PID=$(cat /run/angie.pid.oldbin)
NEW_MASTER_PID=$(cat /run/angie.pid)

# 1. Отправьте SIGHUP старому мастеру (он мгновенно поднимет своих воркеров)
sudo kill -HUP "${OLD_MASTER_PID}"
sleep 1

# 2. Убедитесь, что воркеры старого мастера вернулись в строй
ps -ef --forest | grep -E "[a]ngie"
# → root     14205     1  0 19:10 ?  angie: master process /usr/sbin/angie
# → angie    22101 14205  0 19:20 ?   \_ angie: worker process #2
# → root     21450 14205  0 19:15 ?   \_ angie: master process /usr/sbin/angie
# → angie    21451 21450  0 19:15 ?       \_ angie: worker process #1

# 3. Принудительно завершите новый сбойный мастер и его воркеры
sudo kill -TERM "${NEW_MASTER_PID}"

# 4. Верните старый PID-файл на место
sudo mv /run/angie.pid.oldbin /run/angie.pid

# 5. Проверьте статус службы
echo "Сервис откачен на стабильный мастер PID: $(cat /run/angie.pid)"
# → Сервис откачен на стабильный мастер PID: 14205
```

### Сценарий 5: Скрипт автоматизированного безопасного reload для CI/CD

Bash-скрипт `/usr/local/bin/angie-safe-reload.sh` для использования в пайплайнах деплоя:

```bash
#!/usr/bin/env bash
set -euo pipefail

STATUS_URL="http://127.0.0.1:8888/status/angie/"
TIMEOUT=30

echo "[1/4] Валидация синтаксиса конфигурации..."
if ! angie -t -q; then
    echo "ОШИБКА: Синтаксический тест не пройден! Reload отменен." >&2
    exit 1
fi

echo "[2/4] Получение текущего поколения конфигурации..."
INITIAL_GEN=$(curl -sf "${STATUS_URL}" | jq -r '.generation // 0')
echo "Текущее поколение: ${INITIAL_GEN}"

echo "[3/4] Инициирование Graceful Reload..."
systemctl reload angie

echo "[4/4] Ожидание подтверждения смены поколения..."
ELAPSED=0
NEW_GEN="${INITIAL_GEN}"

while [[ "${NEW_GEN}" -le "${INITIAL_GEN}" ]]; do
    if [[ "${ELAPSED}" -ge "${TIMEOUT}" ]]; then
        echo "ПРЕДУПРЕЖДЕНИЕ: Время ожидания (${TIMEOUT}s) истекло. Номер поколения не обновился!" >&2
        exit 1
    fi
    sleep 1
    ELAPSED=$((ELAPSED + 1))
    NEW_GEN=$(curl -sf "${STATUS_URL}" | jq -r '.generation // 0')
done

echo "УСПЕХ: Конфигурация успешно применена. Новое поколение: ${NEW_GEN}"
```

Сделайте файл исполняемым:

```bash
sudo chmod +x /usr/local/bin/angie-safe-reload.sh
sudo /usr/local/bin/angie-safe-reload.sh
# → [1/4] Валидация синтаксиса конфигурации...
# → [2/4] Получение текущего поколения конфигурации...
# → Текущее поколение: 2
# → [3/4] Инициирование Graceful Reload...
# → [4/4] Ожидание подтверждения смены поколения...
# → УСПЕХ: Конфигурация успешно применена. Новое поколение: 3
```

### Сценарий 6: Управление жизненным циклом в локальных контейнерах (Docker/Podman)

По умолчанию утилиты `docker stop` и `podman stop` отправляют процессу контейнера сигнал `SIGTERM`. Для Angie это означает экстренную жесткую остановку с мгновенным обрывом клиентских сессий и генерацией ошибок `502 Bad Gateway` на upstream-балансировщиках.

#### 1. Указание правильного сигнала останова в Dockerfile

```dockerfile
FROM alpine:3.20

# Установка пакета Angie
RUN apk add --no-cache angie

# Обязательное указание STOPSIGNAL для корректного graceful shutdown
STOPSIGNAL SIGQUIT

EXPOSE 80 443

CMD ["angie", "-g", "daemon off;"]
```

#### 2. Настройка тайм-аута в Docker Compose

При остановке контейнера docker ожидает завершения процесса указанное количество секунд перед отправкой `SIGKILL`:

```yaml
services:
  web:
    image: angie:custom
    restart: always
    stop_signal: SIGQUIT
    # Тайм-аут должен быть больше worker_shutdown_timeout
    stop_grace_period: 40s
    ports:
      - "80:80"
      - "443:443"
```

#### 3. Выполнение безопасного reload внутри контейнера

```bash
docker exec -it angie_container angie -t
# → angie: the configuration file /etc/angie/angie.conf syntax is ok
# → angie: configuration file /etc/angie/angie.conf test is successful

docker exec -it angie_container angie -s reload
# → Graceful reload применен внутри изолированного окружения
```

## Операции и команды

### Сводная таблица POSIX-сигналов Angie

| Сигнал | Назначение | Действие Master-процесса | Действие Worker-процесса | Пример вызова |
|:---|:---|:---|:---|:---|
| `HUP` (`SIGHUP`) | Graceful Reload | Перечитывает конфигурацию, открывает сокеты, спавнит новое поколение воркеров, шлет команду завершения старым. | Завершает цикл приема новых соединений, дообслуживает текущие клиенты и выходит. | `kill -HUP $(cat /run/angie.pid)` |
| `QUIT` (`SIGQUIT`) | Graceful Shutdown | Дожидается корректного выхода всех воркеров, закрывает лог-файлы, удаляет PID-файл и завершается. | Прекращает `accept()`, дообслуживает активные запросы в пределах `worker_shutdown_timeout` и завершается. | `kill -QUIT $(cat /run/angie.pid)` |
| `TERM`, `INT` | Fast Shutdown | Немедленно отправляет `SIGKILL`/`SIGTERM` всем дочерним процессам и завершается. | Экстренно закрывает все клиентские сокеты без завершения транзакций и завершается. | `kill -TERM $(cat /run/angie.pid)` |
| `USR1` (`SIGUSR1`) | Reopen Log Files | Переоткрывает дескрипторы журналов (используется утилитой `logrotate`). | Переоткрывает файлы логов под непривилегированным пользователем. | `kill -USR1 $(cat /run/angie.pid)` |
| `USR2` (`SIGUSR2`) | Binary Upgrade | Переименовывает PID-файл в `.oldbin`, выполняет `execve()` с новым бинарником, передавая дескрипторы сокетов. | Игнорируется рабочими процессами. | `kill -USR2 $(cat /run/angie.pid)` |
| `WINCH` (`SIGWINCH`) | Graceful Stop Workers | Отправляет сигнал плавной остановки всем своим воркерам, но сам мастер остается активным без дочерних процессов. | Плавная остановка (graceful shutdown) воркера. | `kill -WINCH $(cat /run/angie.pid.oldbin)` |

## Диагностика и устранение неисправностей (Troubleshooting)

### Типовые проблемы и пути решения

| Симптом | Причина | Диагностика | Решение |
|:---|:---|:---|:---|
| **Воркеры старого поколения часами висят в `(is shutting down)`** | Клиенты удерживают долгие соединения (WebSocket, SSE, gRPC, HTTP/2 streams или медленная передача данных). | `ps -eo pid,cmd \| grep "shutting down"` | Настроить в глобальном блоке `angie.conf` директиву `worker_shutdown_timeout 30s;`. |
| **`systemctl reload angie` падает с ошибкой, сервис остается активным** | Ошибка синтаксиса конфигурации или недоступность подключаемого файла (SSL-сертификат, include). | `journalctl -u angie.service -e -n 50` и `angie -t` | Исправить ошибку в конфиге. Мастер предотвратил сбой, продолжая работу со старым конфигом. |
| **Сигнал `USR2` не создает новый процесс мастера** | Файл `/run/angie.pid.oldbin` уже существует от предыдущего неудачного апгрейда, либо нет прав на запись в каталог `/run/`. | `ls -la /run/angie.pid*` | Удалить зависший старый файл `.oldbin`, проверить права на директорию PID-файла. |
| **Systemd теряет контроль над сервисом после Binary Upgrade** | Старый мастер завершен по `SIGQUIT`, и systemd считает сервис остановленным, так как отслеживал изначальный PID. | `systemctl status angie` и `cat /run/angie.pid` | В unit-файле systemd должна присутствовать директива `PIDFile=/run/angie.pid`. Выполнить `systemctl daemon-reload`. |
| **Всплеск 502 Bad Gateway у клиентов при reload** | Значение `worker_shutdown_timeout` выставлено в `0` или отсутствует, воркер обрывает сокеты; либо перегружен `backlog`. | `grep -E "502" /var/log/angie/access.log` | Увеличить `worker_shutdown_timeout`, увеличить `net.core.somaxconn` и параметр `backlog` в директиве `listen`. |
| **Ошибка `could not allocate new zone` при reload** | Попытка увеличить размер зоны разделяемой памяти (`limit_req_zone`, `status_zone`) сверх доступного лимита RAM или fragment-памяти. | `tail -n 50 /var/log/angie/error.log` | Увеличить оперативную память сервера либо выполнить контролируемый рестарт в технологическое окно. |

### Глубокая диагностика зависших процессов воркеров

Если воркер удерживается в памяти и не завершается:

```bash
# 1. Найдите PID зависшего воркера
ZOMBIE_PID=$(ps -eo pid,cmd | grep "[a]ngie: worker process.*shutting down" | awk '{print $1}' | head -n1)
echo "Зависший воркер: ${ZOMBIE_PID}"

# 2. Посмотрите открытые сетевые сокеты и внешние IP-адреса клиентов
sudo lsof -i -a -p "${ZOMBIE_PID}"
# → COMMAND   PID  USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
# → angie   14206 angie    8u  IPv4 987654      0t0  TCP 192.168.1.10:https->203.0.113.45:54321 (ESTABLISHED)

# 3. Проверьте состояние соединений через ss
sudo ss -tp state established "sport = :443 or sport = :80" | grep "${ZOMBIE_PID}"
# → tcp   ESTAB   0   0   192.168.1.10:443   203.0.113.45:54321   users:(("angie",pid=14206,fd=8))

# 4. Проверьте системные вызовы процесса через strace
sudo strace -p "${ZOMBIE_PID}" -e trace=network,epoll_wait,read,write
# → epoll_wait(7, [{events=EPOLLIN, data=...}], 512, 1000) = 1
# → read(8, "...", 16384) = 450
```

## Лучшие практики (Best Practices)

1. **Pre-flight валидация обязательна:** Никогда не выполняйте `systemctl reload angie` в скриптах автоматизации или вручную без предварительного `angie -t`.
2. **Явный `worker_shutdown_timeout`:** Всегда объявляйте `worker_shutdown_timeout` на верхнем уровне `angie.conf`:
   * 15–30 секунд для стандартных HTTP/API сервисов.
   * 60–120 секунд для сервисов потокового видео, очередей SSE или активных WebSocket-каналов.
3. **Синхронизация с systemd:** Значение `TimeoutStopSec` в `/etc/systemd/system/angie.service.d/override.conf` должно гарантированно превышать `worker_shutdown_timeout` минимум на 15 секунд во избежание сброса соединений ядром по `SIGKILL`.
4. **Безопасная ротация логов:** Никогда не используйте `reload` или `restart` для ротации журналов доступа. Используйте утилиту `logrotate` с сигналом `kill -USR1 $(cat /run/angie.pid)`. Это мгновенно переоткрывает файлы без пересоздания процессов.
5. **Мониторинг поколений (Generation Drift):** Настройте мониторинг поля `.generation` в Status API (`/status/angie/`). Если счетчик поколений инкрементировался, а количество запущенных воркеров в системе превышает расчетное `worker_processes * 2` дольше 2 минут — инициируйте алерт об утечке процессов.
6. **Поочередный Upgrade в кластерах (Rolling Update):** В кластерах высокой доступности с [Keepalived](./angie_ha_with_keepalived.md) выполняйте binary upgrade последовательно:
   * Переведите узел в состояние `BACKUP` или выведите из балансировки.
   * Выполните обновление бинарника и дымовое тестирование.
   * Верните узел в кластер и перейдите к следующему серверу.

## Дополнительная информация

### Механизмы ядра Linux при наследовании дескрипторов

При инициализации `SIGUSR2` старый master-процесс передает список открытых слушающих сокетов дочернему процессу. По умолчанию файловые дескрипторы в Linux имеют флаг `FD_CLOEXEC`, закрывающий их при системном вызове `execve()`. Master-процесс Angie перед вызовом `execve()` временно сбрасывает этот флаг для массива слушающих сокетов и формирует специальную переменную окружения:

```bash
NGINX="14205:8,9,10,11"
```

Где:
* Первое число — PID старого мастера.
* Через двоеточие — список открытых номеров файловых дескрипторов слушающих портов (HTTP, HTTPS, Stream).

Новый бинарник при старте проверяет наличие переменной окружения `NGINX`, подхватывает готовые сокеты и начинает вызывать `epoll_ctl()` без повторного вызова `bind()`, что исключает ошибку ядра `EADDRINUSE` (`Address already in use`).
