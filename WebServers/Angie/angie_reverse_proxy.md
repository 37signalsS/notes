# Настройка Angie в роли обратного HTTP-прокси

Всем привет, сейчас поговорим о работе с NG в режиме обратного Proxy, то есть Reverse Proxy. Если интересно, то присоединяйтесь. Меня зовут Лавлинский Николай, я технический директор компании Metatlab и давайте перейдем к нашей теме.

Итак, мы сегодня будем по сути следовать возможности модуля Proxy. Преимущественно здесь будем находиться по документации и давайте начнем с простых вещей. Что такое Reverse Proxy вообще? Зачем он создан? Ну, на самом деле вы наверняка этим пользуетесь постоянно, то есть у вас есть frontend-сервер, за ним какое-то количество backends. И вам нужно пересылать запросы. Сегодня мы будем работать именно с протоколом HTTPS и HTTPS. Поэтому протоколу мы пересылаем запросы от клиентов в сторону backends и получаем ответы. Таким образом мы получаем схему обратного Proxy. Ну, здесь можно немного погрузиться в тему, что были классические Proxy-сервера, которые стали близко к пользователям, а обратные Proxy находятся близко к серверам, которые обслуживают их нагрузку. Но это не так уж важно. Главное, что у нас есть очень широкая функциональность Angie по настройке проксирования этих запросов и давайте мы посмотрим какие-то моменты из этих возможностей.

Итак, мы находимся в документации модели Proxy. Здесь есть базовые примеры и огромное количество директив. Надо понимать, что далеко не все вещи нужно пытаться крутить, если у вас нет на это какой-то серьезной причины. Ну, например, то, что касается кэширования, это специфичная тема, то есть это целый блок директив. Некоторые вещи по умолчанию также включены и работают, не требуют никаких настроек, а вот если вы решаете какую-то конкретную задачу, то вы находите под это директива и создаете свой конфиг.

## 1. Базовая конфигурация Reverse Proxy

Давайте начнем с базовой конфигурации и настроим свой тестовый стенд. У меня есть уже заранее запущенный бэкэнд на порту 9000. Это будет бэкэнд из докера, WS-кодер веб-дебаггер. Его особенность в том, что он показывает нам все окружение запроса, все параметры, считает по заголовке, все поля, которые он видит. И для этого как раз можно его использовать для отображения, как в зеркале, что к нему пришло, какой был запрос и так далее.

Если мы ходим на него напрямую, то мы видим, что, например, наше поле `RemoteAddr` это `192.168.122.1`. Это тот адрес, который моя виртуалка видит, как исходный. А если я зайду через Proxy, через 80-ый порт, здесь уже будет отвечать Angie, то я увижу, что здесь, например, `RemoteAddr` будет другой. Это будет как раз адрес из DockerCity. И все остальные заголовки, также поля и другие подробности мы здесь увидим.

### 1.1. Пример Docker-бэкенда

```bash
docker ps
# Пример вывода:
# CONTAINER ID   IMAGE          COMMAND                  CREATED         STATUS         PORTS                    NAMES
# 1234567890ab   ws-debugger    "python app.py"          2 hours ago     Up 2 hours     0.0.0.0:9000->8000/tcp   ws-debugger-backend
```
У меня запущено сразу несколько бэкендов. Они потребуются уже при других задачах. Сегодня нам достаточно вот этого порта 9000. Он слушает на всех интерфейсах и мы можем к нему обращаться. Он доступен по HTTP, работает там веб-сервер внутренний и в общем больше пока этого ничего не требуется.

### 1.2. Минимальная конфигурация Angie

С точки зрения Angie мы можем посмотреть на `reverse_proxy.conf`.
```nginx
server {
    listen 80;

    location / {
        proxy_pass http://localhost:9000;
    }
}
```
Здесь в `location /` минимальный префикс указан и в `proxy_pass` нет никаких адресов. Поэтому здесь все будет работать прозрачно. Адрес просто будет добавляться к запросу вот на этот back-end. То есть он будет точно таким же.

## 2. Установка заголовков

Удаленный IP адрес для back-end теперь становится адресом Angie. То есть запросы идут не от реального IP-адреса клиента, а от IP-адреса Angie. Соответственно нам нужно использовать либо `X-Forwarded-For`, как это часто бывает, когда back-end умеет с этим работать, либо заголовок `X-Real-IP`. При этом вы можете использовать здесь переменные. `$remote_addr` это простая переменная, содержащая IP-адрес клиента, а `$proxy_add_x_forwarded_for` она более сложная — она добавляет `$remote_addr` к уже существующему заголовку `X-Forwarded-For`, что полезно в цепочках прокси-серверов.

```nginx
server {
    listen 80;

    location / {
        proxy_pass http://localhost:9000;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header Host $host; # Или $http_host
    }
}
```

После применения такой конфигурации, на стороне бэкенда (в нашем случае, в выводе `ws-debugger`) можно увидеть, что `RemoteAddr` теперь является IP-адресом Angie, но при этом появились заголовки `X-Real-IP` и `X-Forwarded-For` с реальным IP-адресом клиента. Бэкенд может использовать эти заголовки, например, для записи в access-логи.

Также важно правильно передавать заголовок `Host`. По умолчанию, Angie передаст в `Host` имя апстрима из `proxy_pass` (в данном случае `localhost`). Чтобы бэкенд получал оригинальный `Host` из запроса клиента, используется директива `proxy_set_header Host $host;`. Переменная `$host` содержит имя хоста из запроса.

Помимо этих заголовков, на бэкенд также проксируются и другие заголовки изначального запроса, такие как `User-Agent`, `Accept`, `Accept-Language`, `Accept-Encoding`, которые могут быть важны для генерации корректного ответа.

## 3. Взаимодействие `location` и `proxy_pass` с URI

Поведение проксирования меняется в зависимости от того, указан ли URI в директиве `proxy_pass`.

Если в `proxy_pass` указан URI (как в примере ниже — `/real/`), то часть URI запроса, совпадающая с префиксом `location`, заменяется на URI из `proxy_pass`.

```nginx
server {
    listen 80;

    location /test/ {
        proxy_pass http://localhost:9000/real/;
        # ...
    }
}
```
В этом примере:
- Запрос к `/test/some/page` будет отправлен на бэкенд как `/real/some/page`.
- Запрос к `/test/` будет отправлен на бэкенд как `/real/`.

**Нюанс с завершающим слэшем:** Если `location` определен как префикс со слэшем на конце (`/test/`), то при запросе URI без слэша (`/test`) Angie по умолчанию вернет клиенту 301 редирект на URI со слэшем (`/test/`).

Иногда такой редирект нежелателен. Хотя в исходном материале упоминалась директива для отключения этого, стандартного простого способа отключить именно этот тип редиректа нет. Вместо этого используются другие подходы, например, определение двух `location` или использование `rewrite`.

Директива `proxy_redirect` служит для другой цели: она изменяет заголовки `Location` и `Refresh` в *ответах от бэкенда*, что полезно, когда бэкенд генерирует абсолютные редиректы, которые нужно "спрятать" за прокси.

Если же в `proxy_pass` URI не указан, как в самом первом примере (`proxy_pass http://localhost:9000;`), то URI запроса передается на бэкенд "как есть". Запрос `/some/page` будет отправлен на бэкенд как `/some/page`.

Правила взаимодействия `location` и `proxy_pass` могут быть сложными, особенно при использовании регулярных выражений. Рекомендуется обращаться к официальной документации для разбора конкретных случаев.

## 4. Keep-alive соединения с бэкендом

Включение `keep-alive` соединения в сторону бэкенда особенно актуально, если бэкенд находится на каком-то расстоянии. Это позволяет избежать затрат времени на повторные TCP и TLS хендшейки для каждого запроса.

Для этого нам потребуется блок `upstream`, который в основном используется для балансировки, но в данном случае мы будем его использовать для настройки соединений к одному серверу.

```nginx
http {
    upstream backend_keepalive {
        # zone необязательна для одного сервера, но полезна для общей статистики
        zone backend_keepalive 64k;
        server 127.0.0.1:9000;

        keepalive 32; # Количество keep-alive соединений в кэше для каждого worker-процесса
        keepalive_requests 1000; # Макс. количество запросов через одно keep-alive соединение
        keepalive_timeout 60s; # Таймаут неактивности для keep-alive соединения
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend_keepalive;
            proxy_http_version 1.1; # Для keep-alive необходим HTTP/1.1
            proxy_set_header Connection ""; # Очищаем заголовок Connection, чтобы он не передавался на бэкенд как "close"
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header Host $host;
        }
    }
}
```
Ключевые директивы для включения `keep-alive`:
1.  В блоке `upstream` указывается `keepalive` с количеством соединений, которые будут храниться в кэше для повторного использования.
2.  В `location` необходимо переключиться на протокол HTTP/1.1 (`proxy_http_version 1.1;`).
3.  В `location` необходимо "очистить" заголовок `Connection` (`proxy_set_header Connection "";`), чтобы Angie не передавал на бэкенд заголовок `Connection: close` от клиента.

После применения этой конфигурации, в отладочном выводе бэкенда можно увидеть, что используется протокол `HTTP/1.1` и отсутствует заголовок `Connection: close`, который был там ранее.

## 5. Дополнительные параметры проксирования

### 5.1. Буферизация

По умолчанию, буферизация включена, то есть при получении ответа от бэкенда, Angie старается получить его целиком и потом уже отдает клиенту. То есть, старается как можно быстрее разгрузить бэкенд, чтобы он не ждал, пока этот ответ получит клиент и продолжил свои обычные дела.

Размер и количество буферов определяется директивой `proxy_buffers`.
```nginx
http {
    proxy_buffers 8 16k; # 8 буферов по 16KB
    proxy_buffer_size 8k; # Размер буфера для первого блока ответа
    # ...
}
```
По умолчанию, размер каждого буфера равен размеру страницы памяти. Иногда мы хотим увеличить количество буферов, чтобы туда помещались большие ответы. Потому что, если нам не хватает этих буферов, тогда мы начинаем писать ответ на диск и буферизуем его таким образом с временным файлом. Это может быть не всегда оптимально.

Мы можем запретить запись в файл при переполнении буферов:
```nginx
http {
    proxy_max_temp_file_size 0; # Запретить запись во временный файл
    # ...
}
```
Кроме того, мы можем вообще отключить буферизацию. В целом, это не рекомендуется. Отключать буферизацию стоит только тогда, когда вы точно знаете, что вам это необходимо.
```nginx
http {
    proxy_buffering off; # Отключить буферизацию
    # ...
}
```
Отключение буферизации по сути отключает работу кэширования. Поэтому, если у вас есть кэширование, вы должны использовать буферизацию.

### 5.2. Таймауты

Мы можем использовать директивы для управления таймаутами:
*   `proxy_connect_timeout`: Таймаут на установление соединения с проксируемым сервером.
*   `proxy_read_timeout`: Таймаут на чтение ответа от проксируемого сервера.
*   `proxy_send_timeout`: Таймаут на передачу запроса проксируемому серверу.

По умолчанию эти задержки довольно-таки высокие (около 60 секунд). Иногда мы хотим их сократить, чтобы быстрее получать ошибки и, например, переключаться на какой-то другой бэкенд или не заставлять ждать пользователям.

```nginx
http {
    proxy_connect_timeout 5s;
    proxy_read_timeout 10s;
    proxy_send_timeout 10s;
    # ...
}
```
Значение конкретных таймаутов может быть разное. Это зависит от конкретных параметров вашего бэкенда, какие у вас запросы, какое время ответы вы от них ожидаете. Эти задержки можно контролировать не только на глобальном уровне `http`, но и вносить в конкретные `location`.

### 5.3. Перехват ошибок

Мы можем перехватывать ошибки от бэкенда и показывать вместо этого ошибочного ответа (например, стандартная страница ошибки Apache) ошибку на уровне Angie. Это позволяет скрыть, что у вас стоит какой-то конкретный бэкенд.
```nginx
http {
    proxy_intercept_errors on; # Включить перехват ошибок
    error_page 500 502 503 504 /50x.html;
    location = /50x.html {
        root /usr/share/nginx/html; # Путь к вашей странице ошибки
    }
    # ...
}
```

## 6. Проксирование на HTTPS

Если ваша инфраструктура использует какие-то публичные сети или не до конца безопасные, то может потребоваться передача между front-end и back-end только по протоколу TLS. В этом случае мы можем проксировать по протоколу HTTPS.

```nginx
http {
    upstream backend_https {
        zone backend_https 64k;
        server 127.0.0.1:9443; # Пример HTTPS бэкенда
        keepalive 32;
        keepalive_requests 1000;
        keepalive_timeout 60s;
    }

    server {
        listen 80;

        location / {
            proxy_pass https://backend_https; # Проксирование на HTTPS
            proxy_set_header Connection "";
            proxy_http_version 1.1;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header Host $host;

            # Настройки TLS для проксирования
            proxy_ssl_server_name on; # Передавать имя сервера при TLS-подключении
            proxy_ssl_name "backend.example.com"; # Указать конкретный домен
            proxy_ssl_verify off; # Отключить проверку сертификата бэкенда (использовать с осторожностью)
            proxy_ssl_session_reuse on; # Возобновление TLS-сессий
            proxy_ssl_protocols TLSv1.2 TLSv1.3; # Разрешенные протоколы
        }
    }
}
```

## 7. Использование Proxy Store (кэширование на диске)

`Proxy Store` позволяет не просто отдавать ответ от бэкенда, а еще сохранять его результат у себя локально. Это полезно, если, например, у вас статика находится на стороне бэкенда, но мы хотим проксирующим сервером отдавать ее еще из этого сервера напрямую.

```nginx
http {
    proxy_cache_path /var/cache/nginx/proxy_cache levels=1:2 keys_zone=my_cache:10m inactive=60m max_size=1g;
    proxy_temp_path /var/cache/nginx/proxy_temp;

    server {
        listen 80;

        location /static/ {
            root /var/www/html; # Корневая директория для статики
            error_page 404 = @fetch_static; # Если файл не найден, перенаправляем на @fetch_static
        }

        location @fetch_static {
            internal; # Доступно только для внутренних запросов
            proxy_pass http://localhost:9000/static/; # Проксируем на бэкенд
            proxy_store on; # Включаем сохранение ответа на диск
            proxy_store_access user:rw group:rw all:r; # Права доступа для сохраненных файлов
            proxy_temp_path /var/cache/nginx/proxy_temp; # Временная директория для записи
            proxy_cache my_cache; # Используем определенную зону кэша
            proxy_cache_valid 200 302 10m; # Кэшировать ответы 200, 302 на 10 минут
            proxy_cache_valid 404 1m; # Кэшировать ответы 404 на 1 минуту
            proxy_cache_revalidate on; # Ревалидация кэша
            proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504; # Использовать устаревший кэш при ошибках
        }
    }
}
```
В этом примере, если кто-то уже ходил на конкретный документ, мы его сохранили, будем отдавать его напрямую из нашего `location`. Это довольно-таки удобно, если у вас есть распределенная структура, и вы не хотите там вручную синхронизировать вот эти файлы между серверами. Это что-то типа кэширования, но условно бесконечное, то есть единожды положив этот файл, он у вас будет там всегда. Единственное, что нужно проверить, это собственно обновление этих файлов при их изменении.
