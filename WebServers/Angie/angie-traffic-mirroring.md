# Mirror (дублирование трафика) в Angie

## Определения

*   **Mirror** — механизм модуля `ngx_http_mirror_module`: для входящего запроса Angie формирует **копию** запроса и отправляет её на заданное зеркальное location/бэкенд, не меняя ответ для клиента. Исходный ответ формируется основным location.
*   **Shadow traffic** — «теневой» трафик: копия реального продакшен-трафика, направляемая на тестовые стенды, аналитические системы или новые версии сервиса.
*   **Зеркальный запрос (mirrored request)** — подзапрос, который исполняется Angie параллельно с основным. Его ответ клиенту не передаётся; впрочем, ошибки зеркала не влияют на основной ответ только на уровне протокола — ресурсы воркеров общие.

## Базовые концепции

### Принцип работы

Директивы модуля:

*   `mirror <uri>;` — URI внутреннего location, которому отправляется копия запроса. Может быть задано несколько раз.
*   `mirror_request_body on | off;` — копировать ли тело запроса (для POST). По умолчанию `on`.

Механика:

1. Angie получает запрос и начинает обработку в основном location.
2. Параллельно формируется зеркальный запрос (`PROXY`-подобный inner redirect) со всеми заголовками и телом.
3. Ответ зеркального location отбрасывается; основной ответные поток не блокирует завершение основного только в том случае, если зеркальный бэкенд отвечает без зависания.

Ключевое ограничение: **не существует «мягкого» разделения ресурсов** — зеркальный запрос исполняется в том же воркере. Медленный или недоступный зеркальный бэкенд может занять воркер и увеличить latency основного трафика. Поэтому зеркальный location следует отдельно защищать таймаутами и rate-limit'ами.

Подробная теория модуля в контексте внутренних запросов — [Сценарий 6: Дублирование трафика (`mirror`) (Nginx)](../Nginx/Core/Location/internal_routing.md).

### Когда применяется

*   **Проверка нового бэкенда под реальной нагрузкой** (shadow deployment) без влияния на пользователей.
*   **Сбор аналитики**: отправка копий запросов в системы метрик/логов без вмешательства в основной поток.
*   **Сверка ответов**: старый vs новый API на одном и том же трафике (важно: зеркальный ответ клиенту не возвращается, сравнение делает внешний инструмент).
*   **Репродукция бага**: повторение продакшен-запроса на тестовый сервис для отладки.
*   **Прогрев кэша/контроль гипотез** в нагрузочных сценариях.

Отличие от полноценного shadow-деплоя (когда трафик полностью обрабатывается кандидатом и результаты сравниваются) и от canary описал в [Shadow Deployment (CI-CD)](../../CI-CD/Deployment_Strategies/shadow_deployment.md).

## Практические сценарии

### Сценарий 1: Зеркалирование на отдельный стенд

```nginx
# Тестовый бэкенд, куда копируется весь трафик
location = /_mirror {
    internal;
    proxy_pass http://staging_backend;
    proxy_set_header X-Mirror-For $host;
    proxy_set_header X-Real-IP $remote_addr;

    # Зеркальный бэкенд не должен тормозить основной трафик
    proxy_connect_timeout 1s;
    proxy_read_timeout 2s;
    proxy_send_timeout 2s;
}

server {
    location /api/ {
        mirror /_mirror;
        proxy_pass http://production_backend;
        proxy_set_header X-Mirror-For "";
    }
}
```

Примечание: подзаголовки зеркального запроса можно переопределить через `proxy_set_header` внутри location `/_mirror`.

### Сценарий 2: Зеркалирование только выбранных запросов

Выключение зеркала по условию (например, для запросов с определённым заголовком или из определённой сети):

```nginx
map $http_x_debug $mirror_uri {
    default        "";
    "1"            /_mirror;
}

location /api/ {
    mirror $mirror_uri;          # пустая строка — зеркало отключено
    proxy_pass http://production_backend;
}
```

Директива `mirror` поддерживает переменные, поэтому так можно включать/выключать копирование по любому признаку без перезагрузки конфигурации (требуется только правильный `map`).

### Сценарий 3: Зеркалирование больших тел запросов

Для тяжёлых POST/PUT тело копируется по умолчанию. Если зеркальная система не нуждается в теле — отключайте, чтобы не расходовать память и I/O:

```nginx
location /upload/ {
    mirror /_mirror;
    mirror_request_body off;
    proxy_pass http://production_backend;
}

location = /_mirror {
    internal;
    proxy_pass http://analysis_backend;
    proxy_set_header Content-Length "";
}
```

### Сценарий 4: Метрики зеркального трафика

Используйте статусные зоны отдельно для зеркального location:

```nginx
location = /_mirror {
    internal;
    status_zone mirror;
    proxy_pass http://staging_backend;
}
```

В API (`/status/http/server_zones/mirror`) будет виден объём теневого трафика: активные соединения, `request_counter`, время обработки. Это позволяет оценить, какая доля запросов зеркалируется и не «съедает» ли зеркало ресурсы.

## Операции и команды

```bash
# Проверка конфигурации
angie -t
# → syntax is ok

# Проверка, что mirror-локация internal (недоступна снаружи)
curl -i http://example.com/_mirror
# → 404 Not Found (при попытке запросить снаружи — internal location недоступен)

# Анализ логов: пометить зеркальный бэкенд отдельным upsstream-полем
#   proxy_set_header X-Mirror-For ... ; затем в логе смотреть $upstream_addr

# Проверка метрик зеркальной зоны
curl http://127.0.0.1/status/http/server_zones/mirror
# → {"mirror": {"request_counter": 12345, "active": 0, ...}}
```

## Устранение неисправностей

### Зеркальный трафик замедляет основной

Причина — медленный или зависший зеркальный бэкенд в том же воркере.

**Диагностика и решение:**

```bash
# 1. Проверка, что зеркальный бэкенд отвечает быстро
curl -s -o /dev/null -w "%{time_total}\n" http://staging_backend/_health
# → 0.05  (если время растёт, чините сам стенд)

# 2. Ужесточить таймауты зеркального location
proxy_connect_timeout 1s;
proxy_read_timeout 2s;
```

Если стенд хронически «виснет» — выносите зеркалирование в отдельный экземпляр Angie (например, на пограничном NGINX делать только mirror и гнать поток в отдельный кластер).

### Ошибки в зеркале «портят» лог

Может создаваться впечатление ошибок прод-бэкенда. Пометьте зеркальный поток уникальными заголовками (`X-Mirror-For`) и фильтруйте в агрегаторе логов (Loki/ELK) по этому заголовку.

### Тело запроса не доходит до зеркала

Проверьте `mirror_request_body` (должен быть `on`) и отсутствие конфликтующих `proxy_set_header Content-Length "";` в цепочке.

## Лучшие практики

*   Зеркальный location обязательно `internal` — внешний доступ к нему должен быть невозможен.
*   На зеркальном location задавайте агрессивные таймауты и `limit_req`, чтобы защитить воркеры от «висящего» стенда.
*   Включайте зеркало управляемо (через `map`/переменную), а не навсегда — переключение без reload.
*   Не зеркалите трафик с чувствительными данными без явного разрешения и контроля доступа к зеркальной системе.
*   Следите за метриками зеркальной зоны — рост `active`/`request_counter` без роста основного трафика сигнализирует об аномалии.
