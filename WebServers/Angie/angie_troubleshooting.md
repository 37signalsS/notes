# Диагностика и устранение неисправностей Angie (SRE / Sysadmin Runbook)

**Актуально для:** Angie 1.12.x / Angie PRO 1.12.x, Linux Kernel 5.15+/6.x, systemd 245+

## Определения

* **MTTR (Mean Time To Repair)** — ключевая SRE-метрика, отражающая среднее время восстановления штатного функционирования сервиса с момента возникновения инцидента.
* **Listen Backlog Drops** — состояние переполнения системной очереди сокета в ядре Linux (`listen(..., backlog)`), при котором новые входящие TCP SYN-пакеты молча отбрасываются ядром из-за того, что рабочие процессы Angie не успевают вызывать `accept()`.
* **Worker CPU Lockup (100% CPU)** — зависание рабочего процесса Angie в бесконечном цикле или при обработке катастрофического возврата в регулярном выражении (ReDoS), блокирующее обработку других сетевых событий на данном процессорном ядре.
* **debug_connection** — директива блока `events` веб-сервера, позволяющая активировать максимально детальный уровень логирования (`debug`) исключительно для сетевых соединений с конкретных IP-адресов или CIDR-подсетей, не создавая разрушительной нагрузки на дисковый ввод-вывод сервера.
* **Core Dump (Аварийный дамп памяти)** — файл снимка виртуальной памяти процесса в момент критического сбоя (сигналы `SIGSEGV`, `SIGBUS`, `SIGABRT`), позволяющий в отладчике `gdb` локализовать точную инструкцию и стек вызовов упавшего модуля.
* **FlameGraph (Граф вызовов)** — визуальное представление профиля выполнения функций программы, построенное на базе выборки стеков вызовов утилитой `perf`, где ширина блоков пропорциональна времени, проведенному процессором в конкретной функции.

## Базовые концепции и архитектура

### Послойная модель локализации сбоев

Диагностика инцидентов в высоконагруженных инсталляциях Angie строится по восходящей модели — от сетевого стека ядра операционной системы до прикладного уровня:

```
[ Уровень 1: Сетевой стек ядра Linux ]
  ├── Очереди сокетов: Listen Backlog (somaxconn), SYN Backlog
  ├── Таблица отслеживания соединений: nf_conntrack
  └── Пул портов и сокеты в TIME_WAIT: ip_local_port_range
          │
          ▼
[ Уровень 2: Процессное пространство Angie ]
  ├── Master/Worker: мониторинг поколений (generation) и PID
  ├── Системные лимиты: LimitNOFILE, worker_rlimit_nofile
  ├── Разделяемая память (SHM): slab-аллокатор, переполнение зон
  └── Профилирование потоков: perf, eBPF, gdb
          │
          ▼
[ Уровень 3: Взаимодействие с Upstream и бэкендами ]
  ├── Буферизация: proxy_buffer_size (ошибки 'too big header')
  ├── Таймауты: proxy_connect_timeout, proxy_read_timeout
  └── Keepalive пулы: исчерпание сокетов, заголовки Hop-by-Hop
```

### Почему `strace -p` опасен на продакшене

Одной из самых распространенных ошибок системных администраторов при расследовании 100% нагрузки на Angie является запуск команды `strace -p <worker_pid>`.
* **Механика проблемы:** `strace` использует системный вызов ядра `ptrace`. На каждый системный вызов процесса (`epoll_wait`, `read`, `write`) ядро принудительно останавливает процесс контекстным переключением (context switch), передает управление утилите `strace` и возобновляет процесс.
* **Последствия в High Load:** при нагрузке свыше 5 000 RPS трассировка через `strace` замедляет рабочий процесс в 50–100 раз. Сокеты мгновенно переполняют очередь `backlog`, клиенты получают массовые таймауты (504 Gateway Timeout), а задержка p99 подскакивает до десятков секунд.
* **Безопасная альтернатива:** использование `perf trace` или легковесных eBPF-программ (`bpftrace`), анализирующих вызовы в кольцевом буфере ядра без остановки пользовательских потоков.

## Практические сценарии

### Сценарий 1: Точечный дебаг под нагрузкой через `debug_connection`

Включение глобального `error_log /var/log/angie/error.log debug;` на production-сервере с 20 000 RPS приведет к отказу дисковой подсистемы за несколько секунд. Для безопасной отладки конкретного инцидента директива задается в контексте `events`.

Файл `/etc/angie/angie.conf`:

```nginx
events {
    worker_connections 8192;
    use epoll;

    # Детальное логирование ВКЛЮЧАЕТСЯ ТОЛЬКО для инженера и тестовой подсети
    debug_connection 192.168.1.50;
    debug_connection 10.100.0.0/24;
}

http {
    # Для всех остальных клиентов лог сохраняет рабочий уровень warn/error
    error_log /var/log/angie/error.log warn;
    
    # ... остальная конфигурация ...
}
```

Применение и просмотр отладочного журнала:

```bash
sudo angie -t && sudo systemctl reload angie
# → angie: the configuration file /etc/angie/angie.conf syntax is ok
# → angie: configuration file /etc/angie/angie.conf test is successful

# Просмотр детального лога только для сессий с адреса 192.168.1.50
sudo tail -F /var/log/angie/error.log | grep "192.168.1.50"
# → [debug] 14205#14205: *120485 epoll add event: fd:23 op:1 ev:00002001
# → [debug] 14205#14205: *120485 SSL handshake: start
# → [debug] 14205#14205: *120485 http process request line: "GET /api/v1/checkout HTTP/2.0"
```

### Сценарий 2: Расследование 100% CPU воркера (perf + gdb)

Если один из воркер-процессов потребляет 100% процессорного времени одного ядра, необходимо выявить, в каком участке кода или модуле застрял процесс.

#### 1. Поиск зависшего процесса

```bash
top -b -n 1 -H -p $(pgrep -d',' -f "angie: worker")
# → PID   USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
# → 18450 angie     20   0  184520  65412  24120 R 100.0   0.4  15:20.11 angie: worker
```

#### 2. Профилирование через `perf top`

```bash
# Анализ активных функций ядра и библиотек в реальном времени
sudo perf top -p 18450 --sort comm,dso,symbol
# → Samples: 45K of event 'cycles', 4000 Hz, Event count (approx.): 23512411
# → Overhead  Shared Object      Symbol
# →   88.42%  libpcre2-8.so.0    [.] match
# →    5.12%  angie              [.] ngx_http_regex_exec
```
*Вывод:* 88% времени процессор тратит на сопоставление регулярных выражений внутри `libpcre2` — симптом ReDoS-уязвимости в одном из блоков `location` или NJS-скриптов.

#### 3. Снятие live backtrace через `gdb` без перезапуска

```bash
# Быстрое снятие стека вызовов всех потоков процесса
sudo gdb -p 18450 -batch -ex "thread apply all bt"
# → Thread 1 (Thread 0x7f9014b2a800 (LWP 18450)):
# → #0  0x00007f901451a240 in match () from /usr/lib/x86_64-linux-gnu/libpcre2-8.so.0
# → #1  0x00007f9014521400 in pcre2_match_8 () from /usr/lib/x86_64-linux-gnu/libpcre2-8.so.0
# → #2  0x000055c8210451a0 in ngx_http_regex_exec (r=0x55c82215a020, re=0x55c82189a110, s=0x55c82215a450)
```

### Сценарий 3: Настройка и анализ Core Dumps (Crash Recovery)

При падении воркера с сообщением `worker process exited on signal 11 (core dumped)` необходимо гарантировать сохранение дампа памяти.

#### 1. Настройка директив в `angie.conf`

```nginx
# Верхний уровень (main)
user angie;
worker_processes auto;

# Разрешить создание дампов памяти без ограничения по размеру
worker_rlimit_core 2048m;

# Каталог для записи аварийных дампов (пользователь angie обязан иметь права записи)
working_directory /var/log/angie/cores/;
```

#### 2. Подготовка каталога и прав ОС

```bash
sudo mkdir -p /var/log/angie/cores/
sudo chown -R angie:angie /var/log/angie/cores/
sudo chmod 700 /var/log/angie/cores/

# Разрешить сброс дампов для процессов сменивших UID/GID
sudo sysctl -w fs.suid_dumpable=2
# → fs.suid_dumpable = 2
```

#### 3. Анализ дампа с помощью `gdb`

```bash
# Запуск gdb с бинарником Angie и файлом дампа
sudo gdb /usr/sbin/angie /var/log/angie/cores/core.18450 -batch -ex "bt full"
# → Core was generated by `angie: worker process'.
# → Program terminated with signal SIGSEGV, Segmentation fault.
# → #0  0x00007f9015112044 in ngx_http_custom_module_handler (r=0x0) at src/http/modules/ngx_http_custom_module.c:142
# →         b = 0x0 (NULL pointer dereference)
```

### Сценарий 4: Диагностика очередей сокетов ядра (`ss`) и Listen Backlog Drops

Когда клиенты жалуются на периодические зависания при установке соединений (TCP SYN timeout), проблема заключается в переполнении очередей прослушивания.

```bash
# Просмотр слушающих сокетов Angie
ss -lnt '( sport = :80 or sport = :443 )'
# → State  Recv-Q  Send-Q  Local Address:Port  Peer Address:Port
# → LISTEN 8192    8192    0.0.0.0:443         0.0.0.0:*
# → LISTEN 512     8192    0.0.0.0:80          0.0.0.0:*
```

*Интерпретация:*
* Для слушающего сокета `Send-Q` — это максимальный размер очереди `backlog` (8192).
* `Recv-Q` — текущее количество полностью установленных TCP-соединений (после 3-way handshake), ожидающих, пока процесс Angie вызовет `accept()`.
* **Авария:** Если `Recv-Q >= Send-Q`, очередь переполнена! Все последующие SYN-пакеты отбрасываются ядром.

Проверка системного счетчика сбросов ядра:

```bash
netstat -s | grep -i "listen"
# → 142500 times the listen queue of a socket overflowed
# → 142500 SYNs to LISTEN sockets dropped
```

**Решение:**
1. Увеличить системный лимит ядра: `sysctl -w net.core.somaxconn=65535`.
2. Явно объявить параметр `backlog` в директиве `listen`: `listen 443 ssl backlog=32768;`.

### Сценарий 5: Разбор и локализация кодов ошибок (499 vs 502 vs 504)

На собеседованиях и в реальных дежурствах SRE это три самых частых источника инцидентов:

| Код | Название в спецификации | Кто генерирует | Реальная причина инцидента | Решение SRE |
| :--- | :--- | :--- | :--- | :--- |
| **499** | Client Closed Request | **Angie** (специфичный код) | Клиент (браузер, мобильное приложение) закрыл TCP-соединение до получения полного ответа от Angie (сработал таймаут фронтенда, пользователь нажал отмену). | Оптимизировать бэкенд; проверить, не выставлен ли таймаут в Axios/fetch меньше, чем время генерации ответа; включить `proxy_ignore_client_abort on;`, если запрос обязан дойти до бэкенда. |
| **502** | Bad Gateway | **Angie** | 1. Бэкенд аварийно упал или закрыл порт (TCP RST).<br>2. Заголовки бэкенда превысили `proxy_buffer_size`.<br>3. Бэкенд отправил некорректный ответ не по HTTP протоколу. | 1. Проверить `upstream sent too big header` в error.log -> увеличить `proxy_buffer_size 16k;`.<br>2. Проверить статус процесса приложения (OOM Killer).<br>3. Проверить сокет/порт upstream. |
| **504** | Gateway Timeout | **Angie** | Соединение с бэкендом установлено, но за время `proxy_read_timeout` бэкенд не прислал ни одного байта данных. | 1. Проверить медленные SQL-запросы или блокировки в БД.<br>2. Проверить не завис ли worker бэкенда.<br>3. Временно поднять `proxy_read_timeout 120s;`. |

## Рекомендации (Best Practices)

1. **Никогда не используйте `kill -9` для перезапуска:** Принудительное завершение мастер-процесса через `SIGKILL` оставляет разделяемую память (`shm`) и сокеты в неопределенном состоянии. Всегда используйте штатные сигналы `angie -s reload` (SIGHUP) или `systemctl reload angie`.
2. **Не используйте `$uri` в `proxy_pass`:** При проксировании на бэкенды передавайте `$request_uri` либо используйте чистый `proxy_pass http://upstream;` без URI-части. Использование `$uri` приводит к преждевременному декодированию URL-сущностей и создает уязвимости Path Traversal (`%2e%2e%2f`).
3. **Защита от EADDRNOTAVAIL (Port Exhaustion):** При высоком объеме обращений к апстримам всегда включайте HTTP/1.1 и очищайте заголовок Connection (`proxy_http_version 1.1; proxy_set_header Connection "";`), а также используйте директиву `proxy_bind` с пулом адресов.
4. **Регулярный аудит `error.log`:** Автоматизируйте алертинг в Zabbix/Prometheus при появлении в логе ошибок уровня `[emerg]`, `[alert]` и `[crit]`.
