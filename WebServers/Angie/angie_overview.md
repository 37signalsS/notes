# Обзор Angie

## Определения

**Angie** — это российский высокопроизводительный веб-сервер, являющийся форком [Nginx](../Nginx/Core/nginx_overview.md). Продукт разработан компанией ООО «Веб-сервер» командой ведущих разработчиков оригинального Nginx.

Angie является **drop-in** заменой Nginx: он сохраняет полную обратную совместимость по конфигурации и логике работы, одновременно предлагая расширенные функции мониторинга, балансировки и безопасности, которые в оригинальном проекте доступны только в коммерческой версии Nginx Plus или через сложные сторонние модули.

## Базовые концепции

### История и импортозамещение

*   **2022 год:** Создание форка на базе Nginx 1.23.1 для обеспечения технологической независимости и поддержки пользователей в РФ.
*   **Реестр российского ПО:** Программный комплекс Angie (версии Open Source, PRO и Ingress) включен в Единый реестр российских программ (запись № 17604).
*   **Сертификация:** Совместим с отечественными ОС (Astra Linux, РЕД ОС, Альт Линукс) и поддерживает работу в закрытых контурах.

### Ключевые преимущества перед Nginx (Open Source)

Angie активно развивает функционал, ориентированный на современные инфраструктуры:

*   **Расширенная наблюдаемость:** Встроенный REST API и модуль `metrics` для сбора детальной статистики (гистограммы, скользящие средние) в форматах JSON и Prometheus.
*   **Интеллектуальная балансировка:** Поддержка `least_time` (выбор сервера по времени ответа), `sticky learn` (привязка сессий по трафику) и режима `drain` для плавного вывода узлов из эксплуатации.
*   **Автоматизация ACME:** Встроенная поддержка протокола ACME для автоматического получения и продления TLS-сертификатов (включая поддержку в контексте `stream`).
*   **Автоматизация контейнеров:** Динамическое обнаружение и проксирование контейнеров Docker и Podman на основе меток (labels) без перезагрузки конфигурации.
*   **Современные протоколы:** Полноценная поддержка HTTP/3 (QUIC), Multipath TCP (MPTCP) и Encrypted Client Hello (ECH).
*   **IoT и специализированные решения:** Проксирование MQTT с балансировкой на основе идентификаторов устройств.

### Архитектура и версионирование

Angie наследует классическую событийно-ориентированную многопроцессную архитектуру (master и worker процессы), оптимизируя использование ресурсов под экстремальные нагрузки.

*   **Модель релизов:** Проект не использует разделение на `stable` и `mainline`. Каждый публичный релиз является стабильным и готовым к эксплуатации.
*   **Релизный цикл:** Обновления выходят ежеквартально.
*   **Актуальная версия (2026):** 1.12.2 (базируется на Nginx 1.27.x), включает исправления безопасности и расширенный функционал мониторинга.
    ```bash
    $ angie -v
    angie version: angie/1.12.2 (nginx/1.27.3)
    ```

## Практические сценарии

### Мониторинг и аналитика реального времени

Модуль `metrics` (Angie 1.11+) позволяет собирать агрегированную статистику по любым переменным:

*   **Гистограммы задержек:** Распределение времени ответа бэкендов.
*   **Скользящие средние:** Отслеживание трендов нагрузки в реальном времени.
*   **Visual Console:** Встроенная веб-панель для визуального контроля состояния апстримов.

Подробнее: [Мониторинг Angie — возможности Angie Pro](./angie_monitoring/angie_monitoring_pro.md).

### DoH и шифрованный DNS

Начиная с версии 1.12, Angie включает встроенный модуль `doh` для реализации **DNS-over-HTTPS (DoH, RFC 8484)**. Полная конфигурация, практические сценарии и отладка описаны в отдельном документе:

*   **[DNS over HTTPS (DoH) в Angie](./angie_doh_module.md)**

### Автоматизация в контейнерных средах

Angie (1.10+) поддерживает прямое взаимодействие с Docker/Podman API:

*   **Авто-апстримы:** Автоматическое добавление IP-адресов контейнеров в группы `upstream` на основе меток.
*   **Zero-reload:** Обновление списка бэкендов происходит в памяти без выполнения `reload`, что критично при частых перезапусках подов/контейнеров.

## Операции и команды

### Управление сервисом (systemd)

Angie поставляется как стандартный systemd-сервис. Основные операции:

```bash
# Проверка статуса
sudo systemctl status angie
# → Active: active (running) since ...

# Запуск и включение автозагрузки
sudo systemctl enable --now angie

# Перезагрузка конфигурации (graceful reload)
sudo systemctl reload angie

# Полная перезагрузка сервиса
sudo systemctl restart angie

# Просмотр логов в реальном времени
sudo journalctl -fu angie
```

### Проверка конфигурации

Перед применением конфигурации всегда выполняйте проверку синтаксиса:

```bash
# Проверка основного конфига
sudo angie -t
# → angie: the configuration file /etc/angie/angie.conf syntax is ok
# → angie: configuration file /etc/angie/angie.conf test is successful

# Проверка с указанием альтернативного конфига
sudo angie -t -c /etc/angie/angie.conf
```

### Диагностика портов и соединений

```bash
# Проверка слушаемых портов
ss -tlnp | grep angie
# → LISTEN 0 128 0.0.0.0:80

# Проверка активных соединений
ss -s
# → TCP: 1423 (estab 387, closed 231, orphaned 12, timewait 856)

# Проверка очередей сокетов (drop count)
ss -ltni | grep angie
# → skmem:(r0,rb8736,t0,tb0,f0,bl0) drops 0
```

### Работа с upstream и зонами

```bash
# Проверка конфигурации через API
curl -s http://127.0.0.1:8080/api/http/upstreams
# → [{"name":"app_servers","peers":[{"id":0,"server":"10.0.0.1:8080","name":"10.0.0.1:8080","address":"10.0.0.1:8080", ...}], ...}]

# Проверка состояния бэкендов
curl -s http://127.0.0.1:8080/api/http/upstreams/app_servers
# → {"peers":[{"state":"unreachable","responses":...}],"generation":42}

# Обновление upstream через API (Angie 1.10+)
curl -X POST http://127.0.0.1:8080/api/http/upstreams/app_servers/10.0.0.1:8080/peer \
  -d '{"address":"10.0.0.3:8080","weight":5,"max_conns":100}'
```

### Zero-downtime обновление бинарного файла (USR2/WINCH)

При обновлении пакета Angie в production обычный `systemctl restart` рвёт активные соединения. Пакетный менеджер (`apt install angie`) обновляет бинарник без перезапуска, но полное обновление версии рекомендовано выполнять сигнальным сценарием — как и в Nginx. Механика сигналов идентична: `USR2` запускает новый master поверх старого, `WINCH` плавно останавливает старые воркеры.

```bash
# 1. Установить новый пакет (бинарник заменен, старый мастер продолжает работать)
sudo dnf update angie   # или apt upgrade angie

# 2. Копнуть старую версию — на случай отката
sudo cp /usr/sbin/angie /usr/sbin/angie.old

# 3. Запустить новый master (PID старого сохраняется в angie.pid.oldbin)
sudo kill -USR2 $(cat /var/run/angie.pid)

# 4. Плавно остановить старые воркеры (новые воркеры уже обслуживают запросы)
sudo kill -WINCH $(cat /var/run/angie.pid.oldbin)

# 5. Проверить новую версию
angie -v && ss -tlnp | grep angie

# 6. Завершить старый master и его оставшиеся воркеры
sudo kill -QUIT $(cat /var/run/angie.pid.oldbin)
```

**Откат на предыдущую версию** (если новая версия проблемная):

```bash
sudo mv /usr/sbin/angie.old /usr/sbin/angie        # восстановить старый бинарник
sudo kill -USR2 $(cat /var/run/angie.pid)           # запустить его как новый master
sudo kill -QUIT $(cat /var/run/angie.pid.oldbin)    # погасить новую версию
```

Ключевые сигналы Angie:

| Сигнал | Действие |
| :--- | :--- |
| `USR1` | Переоткрыть файлы логов (после `logrotate`) |
| `USR2` | Запустить новый master с новым бинарником (плавный апгрейд) |
| `WINCH` | Остановить воркеры текущего master'а (после USR2) |
| `HUP` | Graceful reload конфигурации |
| `QUIT` | Graceful shutdown (дождаться завершения запросов) |
| `TERM` | Быстрое завершение |

При совместной установке Angie и Nginx следите за PID-файлами: `/var/run/angie.pid` у Angie, `/var/run/nginx.pid` у Nginx. Полный порядок апгрейда для семейства Nginx — [Настройка Nginx (сигналы)](../Nginx/Core/nginx_setup.md).

## Устранение неисправностей

### Конфигурация не применяется

**Симптомы:** После `reload` изменения не вступают в силу, Angie продолжает использовать старые пути или порты.

**Диагностика:**

```bash
# 1. Проверка синтаксиса
sudo angie -t
# → angie: configuration file /etc/angie/angie.conf test is successful

# 2. Проверка слушаемых портов
ss -tlnp | grep angie
# → LISTEN 0 128 0.0.0.0:80

# 3. Проверка PID и поколения
cat /var/run/angie.pid
# → 12345
ps -p 12345 -o pid,generation,cmd
# →   PID GENERATION CMD
# → 12345         42 angie: master process /usr/sbin/angie
```

**Решения:**

*   Убедитесь, что вы редактируете правильный конфиг (Angie использует `/etc/angie/`, а не `/etc/nginx/`).
*   Проверьте, нет ли опечаток в директивах (Angie игнорирует неизвестные директивы в `server` блоке).
*   Убедитесь, что после `reload` PID изменился (старые воркеры должны завершиться).

### 502/504 ошибки на бэкенде

**Симптомы:** Angie возвращает `502 Bad Gateway` или `504 Gateway Timeout`.

**Диагностика:**

```bash
# 1. Проверка доступности бэкенда напрямую
curl -v http://10.0.0.1:8080/health
# → HTTP/1.1 200 OK

# 2. Проверка состояния upstream через API
curl -s http://127.0.0.1:8080/api/http/upstreams/app_servers
# → "state":"unreachable"

# 3. Проверка таймаутов в конфигурации
grep -E 'proxy_connect_timeout|proxy_read_timeout|proxy_send_timeout' /etc/angie/conf.d/*.conf
```

**Решения:**

*   Увеличьте `proxy_read_timeout` для долгих операций (по умолчанию 60s).
*   Проверьте, что бэкенд слушает на правильном интерфейсе (не только `127.0.0.1`).
*   Убедитесь, что SELinux/AppArmor не блокируют соединения Angie к бэкенду.

### Логи после ротации не появляются в новом файле

**Симптомы:** После выполнения `logrotate` старые логи остаются, новые записи не попадают в новый файл.

**Решения:**

```bash
# Angie не переоткрывает файлы логов автоматически после ротации.
# Необходимо отправить сигнал:
kill -USR1 $(cat /var/run/angie.pid)

# Альтернатива через systemd:
sudo systemctl reload angie
```

## Лучшие практики

### Структура конфигурации

*   Разделяйте конфигурацию на логические файлы в `/etc/angie/conf.d/` и `/etc/angie/stream.d/`.
*   Используйте директиву `include` для подключения файлов, а не объединяйте все правила в одном `angie.conf`.
*   Храните конфигурацию в системе контроля версий (Git), исключая секреты.

### Безопасность

*   Никогда не запускайте Angie от имени `root` в production. Используйте отдельного пользователя (например, `angie`).
*   Ограничьте доступ к REST API и Console Light (`allow 127.0.0.1; deny all;`).
*   Используйте TLS 1.3 и современные шифры (подробнее в [Настройка TLS в Angie](./angie_tls_setup.md)).
*   Отключайте неиспользуемые методы HTTP (`TRACE`, `CONNECT`) и заголовки сервера (`server_tokens off;`).

### Производительность

*   Настройте `worker_rlimit_nofile` и `worker_connections` с запасом под пиковые нагрузки (подробнее в [Настройка Angie для высоких нагрузок](./High_Load/index.md)).
*   Используйте `keepalive` в блоке `upstream` для повторного использования соединений с бэкендом.
*   Включите кэширование статического контента (`proxy_cache_path`) с зоной `keys_zone`.
*   Для экстремальных RPS используйте `reuseport` и многоочередные NIC (RSS/IRQ балансировка).

### Резервное копирование и откат

*   Перед каждым `reload` создавайте резервную копию конфигурации:
    ```bash
    cp /etc/angie/angie.conf /etc/angie/angie.conf.bak.$(date +%Y%m%d%H%M%S)
    ```
*   Документируйте все изменения в конфигурации.
*   Настройте оповещения в Prometheus/Grafana на метрики `angie_upstream_response_time` и `angie_http_requests_total`.

### Логирование

*   Используйте формат `combined` или кастомный `log_format` с переменными `$upstream_response_time` и `$request_id`.
*   Для автоматизированных систем собирайте логи в JSON через модуль `json_combined`.
*   Настройте `logrotate` с сигналом `USR1` для переоткрытия файлов:
    ```bash
    /var/log/angie/*.log {
        daily
        rotate 30
        compress
        delaycompress
        missingok
        notifempty
        postrotate
            [ -f /var/run/angie.pid ] && kill -USR1 $(cat /var/run/angie.pid) || true
        endscript
    }
    ```
