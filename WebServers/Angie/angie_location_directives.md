# Директивы `location` в Angie (Nginx)

## 1. Обзор директивы `location`

Директива `location` используется для определения того, как Nginx должен обрабатывать запросы для различных URI. Она позволяет настроить специфические правила для определенных путей или шаблонов URL.

### 1.1. Синтаксис и модификаторы

Синтаксис директивы `location` выглядит следующим образом:

```nginx
location [ = | ~ | ~* | ^~ ] uri { ... }
location @name { ... }
```

Модификаторы определяют, как Nginx сопоставляет URI запроса с шаблоном `location`:

*   **`=` (точное совпадение):** Запрос должен точно соответствовать `uri`. Если найдено точное совпадение, поиск прекращается. Имеет наивысший приоритет.
*   **`^~` (префиксное, без регулярных выражений):** Если `uri` соответствует началу запрошенного URI, и это самое длинное совпадение среди префиксных `location`, то этот `location` выбирается, и дальнейший поиск регулярных выражений не производится.
*   **`~` (регулярное выражение, с учетом регистра):** `uri` интерпретируется как регулярное выражение, чувствительное к регистру.
*   **`~*` (регулярное выражение, без учета регистра):** `uri` интерпретируется как регулярное выражение, нечувствительное к регистру.
*   **Без модификатора (префиксное):** Если `uri` соответствует началу запрошенного URI, выбирается `location` с самым длинным совпадением. После этого, если не был использован `^~`, Nginx продолжит проверять `location` с регулярными выражениями.
*   **`@name` (именованное `location`):** Используется для внутренних перенаправлений (например, с помощью `try_files` или `error_page`) и не обрабатывает клиентские запросы напрямую.

### 1.2. Порядок обработки `location`

Nginx обрабатывает директивы `location` в следующем порядке: ([Глубокое погружение в директиву location в Nginx](../Nginx/nginx_location_directive.md))

1.  **Точные совпадения (`=`):** Сначала проверяются `location` с модификатором `=`. Если найдено точное совпадение, запрос обрабатывается этим `location`, и поиск прекращается.
2.  **Префиксные совпадения (`^~` и без модификатора):** Затем Nginx ищет префиксные `location`. Среди всех совпадений выбирается то, которое имеет самый длинный совпадающий префикс.
    *   Если выбранный префиксный `location` имеет модификатор `^~`, запрос обрабатывается им, и поиск прекращается.
    *   Если модификатора нет, Nginx запоминает этот `location` как потенциальный кандидат и переходит к шагу 3.
    *   **Приоритет префиксных `location`:** Среди префиксных `location` (без модификатора или с `^~`) выигрывает тот, у которого максимальная длина совпадения с URI запроса. Например, `location /foo/bar/` будет иметь приоритет над `location /foo/` для запроса `/foo/bar/baz.html`.

3.  **Регулярные выражения (`~` и `~*`):** Nginx проверяет все `location`, определенные с регулярными выражениями, в порядке их появления в конфигурационном файле. Первый `location` с регулярным выражением, который соответствует запросу, используется для его обработки.
    *   **Важно:** Если на шаге 2 был выбран префиксный `location` с модификатором `^~`, то поиск регулярных выражений не производится. Если же префиксный `location` был без модификатора, то после проверки регулярных выражений Nginx вернется к нему, если ни одно регулярное выражение не совпало.

4.  **Префиксное совпадение без модификатора (если не было регулярных выражений):** Если ни один `location` с регулярным выражением не совпал, используется префиксный `location`, найденный на шаге 2 (без модификатора `^~`).

**Приоритет:** `=` (точное совпадение) > `^~` (самое длинное префиксное совпадение, прекращает поиск) > `~` / `~*` (первое совпадение по порядку в файле) > без модификатора (самое длинное префиксное совпадение, если регулярные выражения не совпали).

## 2. Работа с файловой системой: `root` и `alias`

Директивы `root` и `alias` определяют, как Nginx сопоставляет URI запроса с файлами на диске.

### 2.1. Директива `root`

`root` определяет корневой каталог для запросов. Nginx добавляет полный URI запроса к значению `root` для формирования пути к файлу.

*   **Пример:**
    ```nginx
    server {
        root /var/www/html;
        location /images/ {
            # Запрос /images/pic.jpg будет искать файл по пути /var/www/html/images/pic.jpg
        }
        location = /test.html {
            root /var/www/special_tests;
            # Запрос /test.html будет искать файл по пути /var/www/special_tests/test.html
            # Это позволяет отдавать специфические файлы из других директорий.
        }
    }
    ```
*   `root` может быть определен на уровне `http`, `server` или `location`. Если `root` не указан в `location`, он наследуется от родительского блока.

### 2.2. Директива `alias`

`alias` используется для замены части URI запроса на указанный путь в файловой системе. `alias` может использоваться только внутри `location`.

*   **Пример:**
    ```nginx
    location /static/ {
        alias /opt/data/static_files/;
        # Запрос /static/css/style.css будет искать файл по пути /opt/data/static_files/css/style.css
        # Часть "/static/" из URI заменяется на "/opt/data/static_files/"
    }
    location /foot/ {
        alias /var/www/special_content/;
        # Запрос /foot/test.html будет искать файл по пути /var/www/special_content/test.html
        # Здесь "/foot/" из URI заменяется на "/var/www/special_content/".
        # Важно: если location заканчивается слэшем, alias также должен заканчиваться слэшем.
    }
    ```
*   **Важное отличие от `root`:** `alias` заменяет префикс URI, соответствующий `location`, тогда как `root` добавляет весь URI к корневому пути.
*   При использовании `alias` важно, чтобы путь `alias` заканчивался слэшем, если `location` также заканчивается слэшем, чтобы избежать некорректного формирования пути.

## 3. Обработка статических файлов и `try_files`

Директива `try_files` позволяет Nginx проверять существование файлов или директорий в указанном порядке и выполнять внутреннее перенаправление, если ни один из них не найден. Более подробно о `try_files`, а также о правилах rewrite и redirect можно узнать в [Nginx: Правила Rewrite, Redirect и Директива try_files](../Nginx/nginx_rewrite_rules_and_try_files.md).

*   **Синтаксис:** `try_files file ... uri;` или `try_files file ... =code;`
*   **Пример:**
    ```nginx
    location / {
        root /var/www/html;
        try_files $uri $uri/ /index.html =404;
        # 1. Пробует найти файл, соответствующий URI ($uri).
        # 2. Если не найден, пробует найти директорию ($uri/).
        # 3. Если и директория не найдена, делает внутреннее перенаправление на /index.html.
        # 4. Если /index.html также не найден, возвращает ошибку 404.
    }
    ```
*   `try_files` часто используется для обработки "красивых" URL (pretty URLs) в CMS, где все запросы, не соответствующие существующим файлам или директориям, перенаправляются на основной скрипт (например, `index.php`). Для эффективного использования `try_files` с статическими файлами рекомендуется ознакомиться с [Клиентское кэширование в Angie](../Angie/angie_caching.md).

## 4. Именованные `location` и `internal`

### 4.1. Именованные `location` (`@name`)

Именованные `location` не могут быть вызваны напрямую клиентом. Они используются для внутренних перенаправлений внутри Nginx, например, с помощью `try_files` или `error_page`. Дополнительную информацию о перенаправлениях и перезаписи URI можно найти в [Перенаправления и перезапись URI в Angie](../Angie/angie_redirects_and_rewrites.md).

*   **Пример:**
    ```nginx
    location / {
        try_files $uri @backend;
    }

    location @backend {
        proxy_pass http://my_backend_servers;
    }
    ```
    В этом примере, если Nginx не находит статический файл, он внутренне перенаправляет запрос на именованный `location @backend`, который затем проксирует запрос к бэкенд-серверам. Эта техника является основой для [настройки Angie в роли обратного HTTP-прокси](../Angie/angie_reverse_proxy.md) и [балансировки нагрузки HTTP(S)](../Angie/angie_http_load_balancing.md).

### 4.2. Директива `internal`

Директива `internal` внутри `location` делает этот `location` доступным только для внутренних запросов Nginx. Клиентские запросы к такому `location` будут отклонены (обычно с ошибкой 404 Not Found).

*   **Пример:**
    ```nginx
    location /private_data/ {
        internal;
        root /var/www/internal_files;
        # Этот location доступен только для внутренних перенаправлений Nginx.
        # Прямой запрос клиента к /private_data/ будет отклонен.
    }
    location /error_pages/ {
        internal;
        root /var/www/errors;
        # Если клиент попытается напрямую обратиться к /error_pages/404.html,
        # он получит ошибку 404 Not Found, несмотря на существование файла.
        # Этот location предназначен для использования с error_page директивой.
    }
    ```
*   Это полезно для защиты конфиденциальных ресурсов или для организации внутренних API, которые не должны быть доступны извне.

## 5. Обработка PHP-скриптов

Для обработки PHP-скриптов Nginx обычно использует FastCGI-протокол, взаимодействуя с PHP-FPM.

*   **Пример конфигурации для PHP:**
    ```nginx
    location ~ \.php$ {
        root           /var/www/html;
        fastcgi_pass   unix:/var/run/php/php7.4-fpm.sock; # Путь к сокету PHP-FPM
        fastcgi_index  index.php;
        include        fastcgi_params; # Включает стандартные параметры FastCGI
        fastcgi_param  SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }
    ```
*   Здесь используется регулярное выражение `~ \.php$` для сопоставления всех запросов, заканчивающихся на `.php`.
*   `fastcgi_pass` указывает адрес FastCGI-сервера (часто Unix-сокет).
*   `fastcgi_param SCRIPT_FILENAME` передает PHP-FPM полный путь к исполняемому скрипту.

## 6. Оптимизация и лучшие практики

*   **Используйте `^~` для статических файлов:** Для статических ресурсов, которые не требуют обработки регулярными выражениями, используйте `^~` для повышения производительности, так как это прекращает поиск `location` после первого совпадения.
*   **Централизованное управление заголовками:** Для общих заголовков (например, для кэширования статики) используйте `include` для вынесения их в отдельный файл, чтобы избежать дублирования и упростить управление.
*   **Избегайте сложных регулярных выражений:** Чрезмерное использование сложных регулярных выражений может снизить производительность. Старайтесь использовать префиксные `location` там, где это возможно.
*   **Мониторинг `location`:** Используйте встроенные средства мониторинга Nginx (например, `ng console.light` или кастомные метрики) для отслеживания того, какие `location` обрабатывают запросы, чтобы убедиться в корректности конфигурации и выявить неожиданное поведение. Для более детального мониторинга каждого `location` можно использовать "статус зоны" (status zones), которые позволяют собирать статистику по запросам, обрабатываемым конкретным `location`. Более подробно о мониторинге Angie можно узнать в [Мониторинг Angie](../Angie/angie_monitoring.md).
*   **Тестирование конфигурации:** Всегда проверяйте синтаксис конфигурации Nginx (`nginx -t`) и перезагружайте его (`nginx -s reload`) после внесения изменений.

### 6.1. Отладка `location` с помощью `return`

Для быстрой проверки того, какой `location` обрабатывает запрос, можно временно использовать директиву `return` внутри `location`. Это позволяет Nginx немедленно вернуть указанный HTTP-код и/или текст, прекратив дальнейшую обработку запроса.

*   **Пример:**
    ```nginx
    location ~ \.php$ {
        # Временно для отладки:
        return 200 "Location: Regexp PHP";
        # После отладки раскомментировать основную конфигурацию:
        # root           /var/www/html;
        # fastcgi_pass   unix:/var/run/php/php7.4-fpm.sock;
        # fastcgi_index  index.php;
        # include        fastcgi_params;
        # fastcgi_param  SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }
    ```
    Используя `curl` или браузер, можно увидеть ответ "Location: Regexp PHP", что подтверждает попадание запроса в этот `location`.

## 7. Примеры из WordPress

Типичная конфигурация `location` для WordPress часто включает:

*   Перенаправление HTTP на HTTPS. Подробная информация доступна в [Настройка TLS в Angie: безопасность и скорость](../Angie/angie_tls_setup.md).
*   `location /` с `try_files` для обработки статики и перенаправления на `index.php` для динамического контента.
*   `location ~ \.php$` для обработки PHP-скриптов через FastCGI.
*   `location` для защиты конфиденциальных файлов (например, `.htaccess`, `wp-config.php`).
*   Специальные `location` для статических ресурсов WordPress (например, `/wp-content/`).

```nginx
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name example.com;
    root /var/www/wordpress;
    index index.php index.html index.htm;

    # Защита конфиденциальных файлов
    location ~ /\.ht {
        deny all;
    }
    location ~ /(wp-config\.php|wp-trackback\.php|xmlrpc\.php) {
        deny all;
    }

    # Обработка статических файлов и перенаправление на index.php
    location / {
        try_files $uri $uri/ /index.php?$args;
    }

    # Обработка PHP-скриптов
    location ~ \.php$ {
        include snippets/fastcgi-php.conf; # Или полный набор fastcgi_params
        fastcgi_pass unix:/var/run/php/php7.4-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }

    # Специальный location для статики wp-content
    location ~* \.(js|css|png|jpg|jpeg|gif|ico)$ {
        expires max;
        log_not_found off;
    }
}
```
