# Настройка Angie для высоких нагрузок и защиты от DoS-атак: Конспект лекции

Этот документ представляет собой структурированный конспект лекции о настройке веб-серверов Nginx и Angie для работы в условиях высоких нагрузок, а также о базовых методах защиты от DoS-атак.

## 1. Введение: Nginx vs. Angie

-   **История:** Angie является форком Nginx, созданным ключевой командой разработчиков, покинувшей F5 (текущий владелец Nginx) после закрытия московского офиса разработки в 2022 году. Это привело к появлению трех "ветвей" развития: Nginx (F5), Angie и freenginx (проект Максима Дунина).
-   **Команда:** Основное ядро разработчиков оригинального Nginx теперь работает над Angie.
-   **Преимущества Angie:**
    -   **Активное развитие:** Angie развивается быстрее, инкорпорируя полезные изменения из Nginx и freenginx, а также добавляя собственную функциональность.
    -   **Больше функций в Open Source:** Многие возможности, доступные в Nginx только в платной версии (Nginx Plus), реализованы в бесплатной версии Angie. Например:
        -   Расширенный мониторинг через API и веб-интерфейс (`console-lite`).
        -   Плавный старт апстримов (`slow_start`).
        -   Динамическое разрешение DNS в `stream` модуле.
        -   Продвинутая балансировка нагрузки.
    -   **Готовые пакеты модулей:** Angie предоставляет официальные репозитории с уже скомпилированными популярными сторонними модулями (Brotli, Zstd, ModSecurity и др.), что избавляет от необходимости ручной сборки.
    -   **Поддержка:** Существует активное сообщество и прямой канал связи с разработчиками (например, через Telegram), где можно получить квалифицированную помощь.
    -   **Совместимость:** Angie сохраняет максимальную совместимость с конфигурацией Nginx, что делает миграцию очень простой.

## 2. Подход к оптимизации производительности

### 2.1. Клиентская и серверная производительность

Оптимизацию следует рассматривать с двух сторон:
-   **Клиентская производительность:** Скорость загрузки и отрисовки контента в браузере пользователя. Метрики: время до первого байта (TTFB), скорость рендеринга, интерактивность. Цели: сокращение трафика, оптимизация кэширования, снижение задержек.
-   **Серверная производительность:** Эффективность использования ресурсов сервера. Метрики: утилизация CPU, потребление памяти, пропускная способность (RPS). Цели: минимизация потребления ресурсов, повышение отказоустойчивости.

### 2.2. Принципы тестирования

-   **Тестируйте по одной настройке за раз**, чтобы четко понимать влияние каждого изменения.
-   **Результаты зависят от окружения:** Конкретные значения тюнинга зависят от оборудования, характера нагрузки и конфигурации приложения. Не копируйте настройки вслепую.
-   **Используйте адекватные инструменты:**
    -   **Клиентская сторона:** [WebPageTest](https://www.webpagetest.org/) для комплексного анализа загрузки в реальном браузере.
    -   **Серверная сторона:** `wrk2` или `wrrk` для генерации нагрузки с контролируемой частотой (RPS). Простой `wrk` или `ab` могут быть нерепрезентативны, так как они "стреляют" с максимальной скоростью. `Яндекс.Танк` также является мощным инструментом.

## 3. Стратегии защиты от DoS и DDoS-атак

### 3.1. DoS vs. DDoS

-   **DoS (Denial of Service):** Атака из одной точки. Легче обнаружить и заблокировать по IP.
-   **DDoS (Distributed Denial of Service):** Атака из множества распределенных точек (ботнет). Значительно сложнее для отражения.

### 3.2. Типы атак и методы защиты

-   **L3/L4 (объемные/сетевые) атаки:** Направлены на переполнение пропускной способности канала (например, UDP-флуд, SYN-флуд).
    -   **Защита на уровне сервера бесполезна:** Если входящий канал полностью забит, никакие правила `iptables` или настройки сервера не помогут, так как легитимный трафик просто не доходит до него.
    -   **Решение:** Защита на уровне вышестоящего провайдера, дата-центра или специализированного сервиса фильтрации трафика.

-   **L7 (атаки на приложение):** Направлены на исчерпание ресурсов самого приложения (CPU, память, диск) с помощью HTTP-запросов, которые выглядят легитимными.
    -   **Проблема:** Современные боты хорошо мимикрируют под реальных пользователей (используют реальные User-Agent, выполняют JS, делают паузы между запросами). При распределенной атаке (DDoS) частота запросов от одного бота может быть очень низкой, что делает невозможным его обнаружение по частотным характеристикам.
    -   **Аналогия с фильтрацией спама:** Эффективная защита требует сложных репутационных систем, поведенческого анализа на основе машинного обучения и глобальных данных об угрозах.
    -   **Вывод:** Защититься от серьезной L7 DDoS-атаки на уровне одного сервера практически невозможно. Для этого требуются профессиональные распределенные сервисы (например, Cloudflare, Qrator, Kaspersky DDoS Protection), которые терминируют трафик в своих облаках и пропускают к вашему серверу только очищенные запросы.

## 4. Практическая защита от простых DoS-атак: Ограничение частоты запросов

Для защиты от примитивных DoS-атак (с одного или нескольких IP-адресов с высокой частотой) можно использовать встроенный в Angie/Nginx модуль `limit_req`.

-   **`limit_req_zone`**: Определяется в блоке `http` и создает зону в разделяемой памяти для хранения состояний.
    -   `$binary_remote_addr`: Ключ для отслеживания (IP-адрес клиента). Можно добавлять и другие переменные.
    -   `zone=name:size`: Имя и размер зоны.
    -   `rate=...r/s`: Разрешенная частота запросов в секунду.
-   **`limit_req`**: Применяется в блоке `location` и активирует ограничение.
    -   `burst=...`: Позволяет обработать небольшое количество запросов, превышающих лимит, без задержки.
    -   `nodelay`: Запросы в рамках `burst` обрабатываются немедленно, а не с задержкой.

**Пример конфигурации:**
```nginx
http {
    # Зона для ограничения: 10 МБ, ключ - IP, скорость - 6 запросов/сек.
    limit_req_zone $binary_remote_addr zone=one:10m rate=6r/s;
}

server {
    location /search/ {
        # Ограничение для location /search/
        # Разрешен всплеск до 12 запросов без задержки
        limit_req zone=one burst=12 nodelay;
        # ...
    }
}
```
**Ограничения:** Этот метод неэффективен против DDoS и может заблокировать легитимных пользователей, работающих из-под одного NAT (например, большой офис).

## 5. Оптимизация на уровне сервера (Server-Side Tuning)

### 5.1. Тюнинг ядра Linux (sysctl)

Для высоконагруженных серверов рекомендуется использовать свежее ядро Linux, так как оно часто содержит хорошие настройки по умолчанию. Изменения следует вносить только при четком понимании их назначения.

-   **`net.ipv4.tcp_slow_start_after_idle=0`**: Не сбрасывать окно TCP-конгестии после простоя соединения. Полезно для долгоживущих keep-alive соединений.
-   **`net.core.netdev_max_backlog = 30000`**: Увеличить размер очереди пакетов, принимаемых от сетевой карты. Помогает не терять пакеты при кратковременных всплесках трафика.
-   **`net.ipv4.ip_local_port_range = 1024 65535`**: Расширить диапазон эфемерных портов для исходящих соединений.
-   **`net.ipv4.tcp_tw_reuse = 1`**: Разрешить повторное использование сокетов в состоянии `TIME-WAIT`.
-   **`net.ipv4.tcp_congestion_control = bbr`**: Алгоритм контроля перегрузки BBR от Google показывает хорошую производительность на каналах с потерями пакетов (например, мобильные сети).

### 5.2. Основные настройки Angie/Nginx

-   **`worker_processes auto;`**: Автоматически устанавливает количество рабочих процессов равным числу ядер CPU. Это оптимально, так как каждый воркер однопоточный.
-   **`worker_cpu_affinity auto;`**: Привязывает каждый воркер к своему ядру CPU, что может улучшить производительность за счет лучшего использования кэша процессора, но снижает гибкость планировщика.
-   **`worker_rlimit_nofile 100000;`**: Увеличивает лимит на количество открытых файловых дескрипторов для рабочих процессов.
-   **`events { worker_connections 20000; }`**: Максимальное количество соединений на один воркер.

### 5.3. Сетевые настройки

-   **`sendfile on;`**: Использовать эффективный системный вызов для отправки файлов, минуя копирование данных в пространство пользователя. **Важно:** `sendfile` не работает с TLS, если не включен Kernel TLS (`listen ... ssl_sendfile`). Для HTTP/2 использование `ssl_sendfile` может привести к деградации производительности.
-   **`tcp_nopush on;` и `tcp_nodelay on;`**: Оптимизируют отправку пакетов, позволяя накапливать данные для формирования полных пакетов и одновременно отключая задержку для отправки небольших пакетов.
-   **`listen 80 reuseport;`**: Позволяет каждому воркеру создать свой слушающий сокет на одном и том же порту. Ядро ОС само распределяет входящие соединения между воркерами, что повышает производительность на многоядерных системах.
-   **`keepalive_timeout 120s;`**: Увеличивает таймаут для keep-alive соединений со стороны клиента.

### 5.4. Серверное кэширование (`proxy_cache`)

Кэширование ответов от бэкендов — один из самых эффективных способов снижения нагрузки.

-   **`proxy_cache_path /path/to/cache ... keys_zone=my_cache:10m ...`**: Определяет зону кэширования на диске.
-   **`proxy_cache my_cache;`**: Включает кэширование для `location`.
-   **`proxy_cache_valid 200 10s;`**: Устанавливает время жизни кэша для ответов с кодом 200.
-   **`proxy_cache_lock on;`**: Предотвращает "стадо бизонов" (cache stampede), отправляя только один запрос на бэкенд для обновления протухшего элемента.
-   **`proxy_cache_background_update on;` и `proxy_cache_use_stale updating;`**: Позволяют отдавать клиенту устаревший ответ из кэша немедленно, пока в фоне идет его обновление. Это критически важно для производительности.
-   **`proxy_cache_use_stale error timeout ...`**: Разрешает отдавать устаревший контент, если бэкенд недоступен.

### 5.5. Оптимизация TLS

Шифрование TLS — одна из самых ресурсоемких операций.

-   **Протоколы:** `ssl_protocols TLSv1.2 TLSv1.3;`. Использование только современных и безопасных версий.
-   **Шифры:** `ssl_ciphers ...`. Настройка набора безопасных и производительных шифров.
-   **Кэширование сессий:**
    -   `ssl_session_cache shared:SSL:10m;`: Кэш для TLS 1.2, ускоряет повторные рукопожатия.
    -   `ssl_session_tickets on;`: Механизм для TLS 1.3.

## 6. Оптимизация на стороне клиента (Client-Side Tuning)

-   **Версии HTTP:**
    -   **HTTP/2:** Включает мультиплексирование (множество запросов в одном TCP-соединении), но уязвим к потере пакетов (Head-of-line blocking).
    -   **HTTP/3:** Работает поверх QUIC (UDP), решая проблему блокировки TCP. Развивается, но уже показывает хорошие результаты.
-   **Сжатие:**
    -   **Gzip:** Универсальный, но самый медленный и неэффективный из современных.
    -   **Brotli:** Отличное сжатие, идеально для статического контента (заранее сжатых файлов). Медленный на высоких степенях сжатия.
    -   **Zstd:** Очень быстрый, лучший выбор для динамического сжатия "на лету".
-   **Клиентское кэширование:** Использование заголовков `Cache-Control` и `Expires` для кэширования статики в браузере.
-   **Другие техники:** Оптимизация изображений (форматы WebP/AVIF), шрифтов, асинхронная загрузка JS.
