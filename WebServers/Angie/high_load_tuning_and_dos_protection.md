# Настройка Angie для высоких нагрузок и защиты от атак

## 1. Ключевые концепции

### 1.1. Angie vs. Nginx: Краткий обзор

-   **История:** [Angie](./angie_overview.md) является форком [Nginx](../../Nginx/Core/nginx_overview.md), созданным ключевой командой разработчиков, покинувшей F5 (текущий владелец Nginx) после закрытия московского офиса разработки в 2022 году.
-   **Преимущества Angie:**
    -   **Активное развитие:** Angie развивается быстрее, инкорпорируя полезные изменения из Nginx и freenginx, а также добавляя собственную функциональность.
    -   **Больше функций в Open Source:** Многие возможности, доступные в Nginx только в платной версии (Nginx Plus), реализованы в бесплатной версии Angie. Например:
        -   Расширенный мониторинг через API и веб-интерфейс (`console-lite`).
        -   Плавный старт апстримов (`slow_start`).
        -   Динамическое разрешение DNS в `stream` модуле.
        -   Продвинутая балансировка нагрузки.
    -   **Готовые пакеты модулей:** Angie предоставляет официальные репозитории с уже скомпилированными популярными сторонними модулями (Brotli, Zstd, ModSecurity и др.), что избавляет от необходимости ручной сборки.

    -   **Совместимость:** Angie сохраняет максимальную совместимость с конфигурацией Nginx, что делает [миграцию](./migration_from_nginx.md) очень простой.

### 1.2. Подходы к оптимизации производительности

-   **Клиентская производительность:** Скорость загрузки и отрисовки контента в браузере пользователя. Метрики: время до первого байта (TTFB), скорость рендеринга, интерактивность. Цели: сокращение трафика, оптимизация кэширования, снижение задержек.
-   **Серверная производительность:** Эффективность использования ресурсов сервера. Метрики: утилизация CPU, потребление памяти, пропускная способность (RPS). Цели: минимизация потребления ресурсов, повышение отказоустойчивости.

### 1.3. Принципы тестирования производительности

-   **Тестируйте по одной настройке за раз**, чтобы четко понимать влияние каждого изменения.
-   **Результаты зависят от окружения:** Не копируйте настройки вслепую; значения тюнинга зависят от оборудования и характера нагрузки.
-   **Используйте адекватные инструменты:**
    -   **Клиентская сторона:** [WebPageTest](https://www.webpagetest.org/) для комплексного анализа загрузки в реальном браузере.
    -   **Серверная сторона:** `wrk2` или `wrrk` для генерации нагрузки с контролируемой частотой (RPS). Простой `wrk` или `ab` могут быть нерепрезентативны, так как они "стреляют" с максимальной скоростью. `Яндекс.Танк` также является мощным инструментом.

### 1.4. Основы защиты от DoS/DDoS-атак

Защита от атак типа «отказ в обслуживании» (DoS/DDoS) — комплексная задача. Важно понимать их природу и почему защита на уровне одного веб-сервера имеет серьезные ограничения.

Подробный разбор типов атак (L3/L4, L7), их проблем и эффективных методов противодействия вынесен в основную заметку:
-   **[Обзор атак типа «Отказ в обслуживании» (DoS/DDoS)](../../../Networking/Concepts/dos_ddos_overview.md)**

Ключевой вывод заключается в том, что для защиты от масштабных атак необходимо использовать специализированные внешние сервисы.

## 2. Практические сценарии оптимизации и защиты

### 2.1. Защита от простых DoS-атак (`limit_req`)

Для защиты от примитивных DoS-атак с высокой частотой с одного IP можно использовать встроенный модуль `limit_req`. Логи этого модуля могут служить источником данных для таких инструментов, как [Fail2Ban](../../../Linux/Security/Tools/Fail2Ban.md).

-   **`limit_req_zone`**: Определяется в блоке `http` и создает зону в разделяемой памяти для хранения состояний (IP-адресов).
-   **`limit_req`**: Применяется в блоке `location` и активирует ограничение с заданными параметрами всплеска (`burst`) и обработки без задержек (`nodelay`).

**Пример конфигурации:**

```nginx
http {
    # Зона для ограничения: 10 МБ, ключ - IP, скорость - 6 запросов/сек.
    limit_req_zone $binary_remote_addr zone=one:10m rate=6r/s;
}

server {
    location /search/ {
        # Ограничение для location /search/
        # Разрешен всплеск до 12 запросов без задержки
        limit_req zone=one burst=12 nodelay;
        # ...
    }
}
```
**Ограничения:** Этот метод неэффективен против распределенных атак (DDoS) и может заблокировать легитимных пользователей, работающих из-под одного NAT. Подробнее см. в [общем обзоре DoS/DDoS атак](../../../Networking/Concepts/dos_ddos_overview.md).

### 2.2. Оптимизация на уровне сервера (Server-Side)

Многие из этих настроек пересекаются с общими рекомендациями в [руководстве по настройке производительности Nginx](../../Nginx/Performance/nginx_performance_tuning.md).

#### Основные настройки Angie/Nginx

-   **`worker_processes auto;`**: Автоматически устанавливает количество рабочих процессов равным числу ядер CPU. Это оптимально, так как каждый воркер однопоточный.
-   **`worker_cpu_affinity auto;`**: Привязывает каждый воркер к своему ядру CPU, что может улучшить производительность за счет лучшего использования кэша процессора, но снижает гибкость планировщика.
-   **`worker_rlimit_nofile 100000;`**: Увеличивает лимит на количество открытых файловых дескрипторов для рабочих процессов.
-   **`events { worker_connections 20000; }`**: Максимальное количество соединений на один воркер.

### Сетевые настройки

-   **`sendfile on;`**: Использовать эффективный системный вызов для отправки файлов, минуя копирование данных в пространство пользователя. **Важно:** `sendfile` не работает с TLS, если не включен Kernel TLS (`listen ... ssl_sendfile`). Для HTTP/2 использование `ssl_sendfile` может привести к деградации производительности.
-   **`tcp_nopush on;` и `tcp_nodelay on;`**: Оптимизируют отправку пакетов, позволяя накапливать данные для формирования полных пакетов и одновременно отключая задержку для отправки небольших пакетов.
-   **`listen 80 reuseport;`**: Позволяет каждому воркеру создать свой слушающий сокет на одном и том же порту. Ядро ОС само распределяет входящие соединения между воркерами, что повышает производительность на многоядерных системах.
-   **`keepalive_timeout 120s;`**: Увеличивает таймаут для keep-alive соединений со стороны клиента.

### 2.3. Серверное кэширование (`proxy_cache`)

-   **`proxy_cache_path /path/to/cache ... keys_zone=my_cache:10m ...`**: Определяет зону кэширования на диске.
-   **`proxy_cache my_cache;`**: Включает кэширование для `location`.
-   **`proxy_cache_valid 200 10s;`**: Устанавливает время жизни кэша для ответов с кодом 200.
-   **`proxy_cache_lock on;`**: Предотвращает "стадо бизонов" (cache stampede), отправляя только один запрос на бэкенд для обновления протухшего элемента.
-   **`proxy_cache_background_update on;` и `proxy_cache_use_stale updating;`**: Позволяют отдавать клиенту устаревший ответ из кэша немедленно, пока в фоне идет его обновление. Это критически важно для производительности.
-   **`proxy_cache_use_stale error timeout ...`**: Разрешает отдавать устаревший контент, если бэкенд недоступен.

Детали реализации описаны в руководствах по [кэшированию в Nginx](../../Nginx/Performance/nginx_proxy_caching.md) и [кэшированию в Angie](./angie_caching.md).

### 2.4. Оптимизация на стороне клиента (Client-Side)

#### Версии HTTP

-   **HTTP/2 и HTTP/3:** Ускоряют загрузку за счет мультиплексирования и, в случае HTTP/3, решения проблемы "Head-of-line blocking".
-   См. [обзор протокола HTTP](../../../Networking/Protocols/http.md) и [настройку версий в Nginx](../../Nginx/Performance/nginx_http_versions.md).

#### Сжатие

-   **Gzip:** Универсальный, но самый медленный.
-   **Brotli:** Отличное сжатие, идеально для статики.
-   **Zstd:** Очень быстрый, лучший выбор для динамического сжатия "на лету".
-   Подробнее см. в [заметке о сжатии в Nginx](../../Nginx/Performance/nginx_compression.md).

### 3.2. Оптимизация TLS

Шифрование [TLS](../../../Networking/Protocols/tls.md) — одна из самых ресурсоемких операций.

-   **Протоколы:** `ssl_protocols TLSv1.2 TLSv1.3;`. Использование только современных и безопасных версий.
-   **Шифры:** `ssl_ciphers ...`. Настройка набора безопасных и производительных шифров.
-   **Кэширование сессий:**
    -   `ssl_session_cache shared:SSL:10m;`: Кэш для TLS 1.2, ускоряет повторные рукопожатия.
    -   `ssl_session_tickets on;`: Механизм для TLS 1.3.

Подробности смотрите в руководствах по [настройке TLS в Angie](./angie_tls_setup.md) и [основной заметке по TLS в Nginx](../../Nginx/Security/nginx_tls_ssl_configuration.md).
