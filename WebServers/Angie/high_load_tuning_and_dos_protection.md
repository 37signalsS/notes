# Настройка Angie для высоких нагрузок и защиты от атак

## Определения

**Оптимизация производительности** веб-сервера — это комплекс мер, направленных на повышение эффективности использования серверных ресурсов (CPU, память, сеть) и ускорение доставки контента клиенту.

**Защита от DoS-атак (Denial of Service)** — это набор техник для противодействия атакам, цель которых — сделать веб-сервер недоступным для легитимных пользователей путем исчерпания его ресурсов.

## Основные концепции

### Подходы к оптимизации

- **Клиентская производительность:** Ускорение загрузки и отрисовки в браузере. Цели: сокращение трафика, оптимизация кэширования, снижение задержек (TTFB).
- **Серверная производительность:** Эффективное использование ресурсов сервера. Цели: минимизация потребления ресурсов, повышение пропускной способности (RPS).

### Принципы тестирования

- **Тестируйте по одной настройке за раз**, чтобы четко понимать ее влияние.
- **Используйте адекватные инструменты:**
  - **Клиентская сторона:** [WebPageTest](https://www.webpagetest.org/) для комплексного анализа загрузки в реальном браузере.
  - **Серверная сторона:** `wrk2` или `wrrk` для генерации нагрузки с контролируемой частотой (RPS). Простой `wrk` или `ab` могут быть нерепрезентативны, так как они "стреляют" с максимальной скоростью. `Яндекс.Танк` также является мощным инструментом.

### Основы защиты от DoS/DDoS-атак

Защита от атак — комплексная задача. Защита на уровне одного веб-сервера имеет ограничения и эффективна в основном против простых атак.
> Подробный разбор типов атак (L3/L4, L7) и методов противодействия вынесен в основную заметку: **[Обзор атак типа «Отказ в обслуживании» (DoS/DDoS)](../../Networking/Concepts/dos_ddos_overview.md)**

## Практические сценарии оптимизации и защиты

### Сценарий 1: Защита от простых L7 DoS-атак

#### Ограничение частоты запросов (`limit_req`)

Для защиты от атак с высокой частотой запросов (флуд) с одного IP-адреса используется модуль `ngx_http_limit_req_module`. Он позволяет ограничить количество запросов, обрабатываемых в единицу времени.

- **`limit_req_zone`**: Директива, определяемая в блоке `http`. Она создает зону в разделяемой памяти для хранения состояний ключей (например, IP-адресов клиентов).
  - `key`: В качестве ключа обычно используется `$binary_remote_addr` для отслеживания IP-адресов. Использование бинарной версии экономит память.
  - `zone`: Имя и размер зоны. `10m` хватает для хранения примерно 160,000 состояний.
  - `rate`: Заданная средняя скорость (например, `10r/s` — 10 запросов в секунду).
- **`limit_req`**: Директива, применяемая в блоке `location` или `server`. Она активирует ограничение для данного контекста.
  - `burst`: Определяет, на сколько запросов клиент может превысить среднюю скорость. Эти "лишние" запросы помещаются в очередь.
  - `nodelay`: Если указан этот параметр, запросы сверх лимита, но в пределах `burst`, обрабатываются немедленно. Запросы, превышающие `burst`, сразу отклоняются с ошибкой **503 Service Temporarily Unavailable**. Если `nodelay` не указан, "лишние" запросы обрабатываются с задержкой, чтобы соответствовать заданной средней скорости, что может быть нежелательно.

**Пример конфигурации:**

```nginx
http {
    # Зона для ограничения: 10 МБ, ключ - IP клиента, скорость - 10 запросов/сек.
    limit_req_zone $binary_remote_addr zone=one:10m rate=10r/s;
}

server {
    location /api/ {
        # Разрешаем всплеск до 20 запросов.
        # Запросы сверх 10r/s, но в пределах 20, обрабатываются сразу.
        # Все, что выше burst, отклоняется с ошибкой 503.
        limit_req zone=one burst=20 nodelay;
    }
}
```

**Ограничения:** Метод неэффективен против распределенных атак (DDoS), когда трафик идет с множества разных IP. Также общий лимит будет распространяться на всех пользователей за одним NAT.

#### Ограничение числа одновременных соединений (`limit_conn`)

Модуль `ngx_http_limit_conn_module` позволяет ограничить количество *активных обрабатываемых соединений* для определенного ключа (например, для одного IP-адреса).

Это не ограничение общего числа TCP-соединений, а именно тех, в рамках которых в данный момент сервер обрабатывает запрос (от чтения заголовков до отправки ответа).

- **`limit_conn_zone`**: Определяет зону для подсчета соединений (аналогично `limit_req_zone`).
- **`limit_conn`**: Применяет ограничение в `location`, `server` или `http`.

**Пример конфигурации:**

```nginx
http {
    # Зона для ограничения по IP-адресу
    limit_conn_zone $binary_remote_addr zone=perip:10m;
}

server {
    # Ограничиваем до 10 активных соединений на один IP
    limit_conn perip 10;

    location /downloads/ {
        # Более строгий лимит для тяжелого контента
        limit_conn perip 2;
    }
}
```
**Ключевые отличия от `limit_req`:**
- `limit_conn` считает активные соединения, а `limit_req` — частоту запросов.
- `limit_conn` доступен в контексте `stream` для TCP/UDP проксирования, что делает его полезным для защиты не-HTTP сервисов. `limit_req` работает только в `http`.

#### Ограничение скорости отдачи контента (`limit_rate`)

Для экономии пропускной способности канала или предотвращения его монополизации одним клиентом, можно ограничить скорость отдачи ответа.

- **`limit_rate`**: Статически задает максимальную скорость в байтах/сек.
- **Переменная `$limit_rate`**: Позволяет задавать скорость динамически.

**Пример статического ограничения:**
```nginx
location /video/ {
    # Ограничение скорости скачивания до 500 КБ/с
    limit_rate 500k;
}
```

**Пример динамического ограничения (в зависимости от User-Agent):**
```nginx
http {
    # По умолчанию ограничения нет (0)
    map $http_user_agent $limit_rate {
        default 0;
        # Для curl-подобных клиентов устанавливаем лимит 500k
        "~*curl" 500k;
    }
}

server {
    location /static/ {
        # Применяем переменную
        set $limit_rate $limit_rate;
    }
}
```
Также для MP4-файлов существует специализированный модуль `ngx_http_mp4_module`, который с помощью директивы `mp4_limit_rate` позволяет ограничить скорость отдачи на основе битрейта файла, что более эффективно для видеостриминга.

### Сценарий 2: Оптимизация производительности сервера

Многие из этих настроек пересекаются с общими рекомендациями в [руководстве по настройке производительности Nginx](../Nginx/Performance/nginx_performance_tuning.md).

#### Основные настройки Angie/Nginx

- **`worker_processes auto;`**: Автоматически устанавливает количество рабочих процессов равным числу ядер CPU. Это оптимально, так как каждый воркер однопоточный.
- **`worker_cpu_affinity auto;`**: Привязывает каждый воркер к своему ядру CPU, что может улучшить производительность за счет лучшего использования кэша процессора, но снижает гибкость планировщика.
- **`worker_rlimit_nofile 100000;`**: Увеличивает лимит на количество открытых файловых дескрипторов для рабочих процессов.
- **`events { worker_connections 20000; }`**: Максимальное количество соединений на один воркер.

### Сетевые настройки

- **`sendfile on;`**: Использовать эффективный системный вызов для отправки файлов, минуя копирование данных в пространство пользователя. **Важно:** `sendfile` не работает с TLS, если не включен Kernel TLS (`listen ... ssl_sendfile`). Для HTTP/2 использование `ssl_sendfile` может привести к деградации производительности.
- **`tcp_nopush on;` и `tcp_nodelay on;`**: Оптимизируют отправку пакетов, позволяя накапливать данные для формирования полных пакетов и одновременно отключая задержку для отправки небольших пакетов.
- **`listen 80 reuseport;`**: Позволяет каждому воркеру создать свой слушающий сокет на одном и том же порту. Ядро ОС само распределяет входящие соединения между воркерами, что повышает производительность на многоядерных системах.
- **`keepalive_timeout 120s;`**: Увеличивает таймаут для keep-alive соединений со стороны клиента.

### Сценарий 3: Серверное кэширование (`proxy_cache`)

- **`proxy_cache_path /path/to/cache ... keys_zone=my_cache:10m ...`**: Определяет зону кэширования на диске.
- **`proxy_cache my_cache;`**: Включает кэширование для `location`.
- **`proxy_cache_valid 200 10s;`**: Устанавливает время жизни кэша для ответов с кодом 200.
- **`proxy_cache_lock on;`**: Предотвращает "стадо бизонов" (cache stampede), отправляя только один запрос на бэкенд для обновления протухшего элемента.
- **`proxy_cache_background_update on;` и `proxy_cache_use_stale updating;`**: Позволяют отдавать клиенту устаревший ответ из кэша немедленно, пока в фоне идет его обновление. Это критически важно для производительности.
- **`proxy_cache_use_stale error timeout ...`**: Разрешает отдавать устаревший контент, если бэкенд недоступен.

Детали реализации описаны в руководствах по [кэшированию в Nginx](../Nginx/Performance/Caching/proxy_caching.md) и [кэшированию в Angie](../Nginx/Performance/Caching/proxy_caching.md).

### Сценарий 4: Оптимизация на стороне клиента

- **Версии HTTP:** Включайте **HTTP/2 и HTTP/3**, чтобы ускорить загрузку за счет мультиплексирования. См. [настройку версий в Nginx](../Nginx/Performance/nginx_http_versions.md).
- **Сжатие:** Используйте **Zstd** для динамического сжатия и **Brotli** для статики. См. [заметку о сжатии в Nginx](../Nginx/Performance/nginx_compression.md).

## Дополнительная информация

### Angie vs. Nginx: Краткий обзор

- **История:** [Angie](./angie_overview.md) — форк [Nginx](../Nginx/Core/nginx_overview.md), созданный ключевой командой разработчиков оригинального проекта.
- **Преимущества Angie:** Более быстрое развитие, больше функций в Open Source (мониторинг, `slow_start`, `drain`), готовые пакеты с модулями. Сохраняется полная совместимость с Nginx.

### Тюнинг ядра и TLS

- **Тюнинг ядра Linux:** Дополнительные параметры производительности можно настроить на уровне ядра. См. [заметку о sysctl](../../Linux/Core/kernel/sysctl.md).
- **Оптимизация TLS:** Шифрование — ресурсоемкая операция. Важно использовать современные протоколы (`TLSv1.2`, `TLSv1.3`) и кэширование сессий.

> Подробности смотрите в руководствах по [настройке TLS в Angie](./angie_tls_setup.md) и [основной заметке по TLS в Nginx](../Nginx/Security/TLS_SSL/nginx_tls_ssl_overview.md).
