# Инструменты для бенчмаркинга веб-серверов

## Определение

**Бенчмаркинг веб-сервера** — процесс измерения производительности серверного ПО при контролируемой нагрузке. Основные метрики: RPS (Requests Per Second — запросов в секунду), время ответа (latency — задержка) и пропускная способность сети (throughput).

**Закрытый цикл (Closed Loop)** — режим работы нагрузочного инструмента, когда новый запрос отправляется только после получения ответа на предыдущий. При замедлении сервера частота запросов падает. Примеры: `ab`, базовый `wrk`.

**Открытый цикл (Open Loop)** — режим, при котором запросы отправляются с заданной частотой независимо от скорости ответа сервера. Позволяет точнее симулировать реальную нагрузку. Примеры: `wrkx` с параметром `-R`, Яндекс.Танк.

**Coordinated Omission (Скоординированный пропуск)** — статистическая ошибка в инструментах с закрытым циклом, когда длительные ответы сервера блокируют отправку новых запросов, искусственно занижая среднюю задержку в отчетах.

## Основные концепции

### Принципы корректного тестирования

1. **Разделение окружений:** Агент тестирования (нагрузчик) и объект тестирования (веб-сервер) должны находиться на разных физических или виртуальных ресурсах. Запуск на одном хосте (через `localhost`) приводит к конкуренции за CPU и искажению сетевых показателей.
2. **Сетевой фактор:** Необходимо следить за параметром пропускной способности. Если значение приближается к лимиту сетевого интерфейса (например, 100 Мбит/с), тестируется пропускная способность сети, а не производительность сервера.
3. **Валидация настроек:** Следует проверять через логи или заголовки ответа, что сервер действительно применяет ожидаемые настройки (например, сжатие gzip/brotli).
4. **Анализ перцентилей:** Среднее время ответа малоинформативно. Критически важно анализировать 95-й, 99-й и 100-й (максимальный) перцентили для выявления проблем в "длинном хвосте".
5. **Длительность теста:** Тест должен длиться достаточно долго (минуты, иногда часы) для стабилизации показателей и выявления долговременных эффектов (например, утечек памяти или заполнения кэша).

### Обзор инструментов

| Инструмент | Потоки | Протоколы | Особенности |
| :--- | :--- | :--- | :--- |
| **ab (Apache Benchmark)** | Однопоточный | HTTP/1.0, 1.1 | Простой, встроен в `apache2-utils`. Лимитирован одним ядром CPU. |
| **wrk** | Многопоточный | HTTP/1.1 | Высокая производительность, поддержка Lua-скриптов. |
| **wrkx** | Многопоточный | HTTP/1.1 | Форк `wrk2` с патчами. Позволяет задавать фиксированный RPS (`-R`). |
| **h2load** | Многопоточный | HTTP/1.1, HTTP/2, HTTP/3 | Часть пакета `nghttp2`. Эффективен для тестирования H2 и HPACK. |

## Практические сценарии

### Использование Apache Benchmark (ab)

Подходит для быстрой оценки производительности на одном ядре CPU. Из-за однопоточности может стать бутылочным горлышком при тестировании очень быстрых систем (например, отдачи статики в Nginx).

```bash
# Установка (Ubuntu)
sudo apt install apache2-utils

# Запуск теста (5000 запросов, 10 соединений, Keep-Alive)
ab -n 5000 -c 10 -k -L -H "Accept-Encoding: gzip" https://example.com/
```

- `-n`: общее количество запросов.
- `-c`: уровень конкурентности (одновременных соединений).
- `-k`: Keep-Alive (использование одного соединения для нескольких запросов).
- `-H`: добавление кастомных заголовков.

### Тестирование с wrk и wrkx

`wrk` — стандарт для высокопроизводительных тестов. `wrkx` (форк `wrk2`) рекомендуется для точных измерений задержки при фиксированном RPS.

```bash
# Сборка wrkx (требует build-essential, libssl-dev, zlib1g-dev)
git clone https://github.com/deathhands/wrkx.git && cd wrkx && make

# Запуск теста (2 потока, 50 соединений, 20 секунд, целевой RPS 1000)
./wrk -t2 -c50 -d20s -R1000 --latency https://example.com/
```

- `-t2`: использование 2 потоков (2 ядер CPU).
- `-R1000`: (только в wrkx) целевая частота запросов.
- `--latency`: вывод детальной статистики по перцентилям.

### Тестирование HTTP/2 и HTTP/3 (h2load)

Утилита из пакета `nghttp2-client` для сравнения эффективности разных версий протоколов.

```bash
# Тестирование HTTP/2 (по умолчанию)
h2load -n 5000 -c 100 -t 2 https://example.com/

# Тестирование HTTP/1.1
h2load -n 5000 -c 100 -t 2 -H1 https://example.com/
```

### Тестирование производительности TLS

При сравнении TLS-библиотек или настроек шифрования необходимо учитывать специфику тестирования.

**Изоляция влияния TLS:**

- Нагрузчик (агент тестирования) и сервер должны находиться на разных физических или виртуальных машинах — `localhost` искажает показатели конкуренцией за CPU
- Перед прогоном убедиться, что пропускная способность сети (гигабитный линк) не является узким местом — она должна заведомо превышать ожидаемый результат
- Отключить сжатие контента (gzip/brotli) для изоляции влияния TLS-шифрования: `gzip off;`
- Для тестирования handshake создать endpoint, возвращающий минимальный ответ (200 OK без тела), чтобы исключить влияние дискового ввода-вывода

**Верификация шифров:**

Использовать `ssl_log_params` и кастомный `log_format` для логирования согласованного шифра и протокола:

```nginx
log_format tls_test '$remote_addr "$request" '
                     'ssl_cipher:$ssl_cipher ssl_protocol:$ssl_protocol';
server {
    access_log /var/log/nginx/tls_test.log tls_test;
    ssl_log_params on;
}
```

Перед замером производительности выполнить тестовый прогон с этим логом, затем отключить access_log для чистоты измерений.

**Смена TLS-библиотеки:**

При тестировании разных TLS-библиотек (OpenSSL, BoringSSL/AWS-LC) необходима пересборка nginx. Символическая ссылка `nginx` переключается между бинарниками, собранными с разными библиотеками:

```bash
nginx -V  # проверка версии OpenSSL
```

**Пример теста handshake (wrkx, 1 worker, TLS 1.3):**

```bash
./wrk -t1 -c50 -d30s -R20000 --latency https://server/zero
```

- `-t1` — 1 поток (нагрузка на одно ядро, соответствует `worker_processes 1`)
- `-R20000` — целевой RPS с запасом
- `/zero` — endpoint с минимальным ответом
