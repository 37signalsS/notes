# Инструменты для бенчмарка веб-сервера

## Definitions

**Бенчмаркинг веб-сервера** — процесс измерения производительности веб-сервера при контролируемой нагрузке. Основные метрики: RPS (Requests Per Second), время ответа (latency) и пропускная способность сети (throughput).

**Нулевой шаг (Browser Testing)** — использование инструментов разработчика в браузере для просмотра времени ответа бэкенда на одиночный запрос. Подходит для отладки, но не является полноценным бенчмарком сервера под нагрузкой.

**Закрытый цикл (Closed Loop)** — режим работы нагрузочного инструмента, когда новый запрос отправляется только после получения ответа на предыдущий. При замедлении сервера частота запросов падает. (Примеры: `ab`, базовый `wrk`).

**Открытый цикл (Open Loop)** — режим, при котором запросы отправляются с заданной частотой независимо от скорости ответа сервера. Позволяет лучше симулировать реальную нагрузку. (Пример: `wrkx` с параметром `-R`, `Яндекс.Танк`).

**Coordinated Omission (Скоординированный пропуск)** — статистическая ошибка в инструментах с закрытым циклом, когда длительные ответы сервера блокируют отправку новых запросов, искусственно занижая среднюю задержку в отчетах.

## Basic Concepts

### Принципы корректного тестирования

1.  **Разделение окружений:** Агент тестирования (нагрузчик) и объект тестирования (веб-сервер) должны находиться на разных мощностях. Запуск на одном хосте (через `localhost`) приводит к:
    *   **Конкуренции за ресурсы:** Утилита нагрузки и сервер делят одни и те же ядра CPU.
    *   **Искажению сети:** Исключение сетевых интерфейсов из уравнения не позволяет оценить их влияние.
    По-хорошему следует использовать удаленные агенты тестирования.
2.  **Сетевой фактор:** Необходимо следить за параметром `Transfer rate` (пропускная способность). Если значение приближается к потолку сетевого интерфейса (например, 100 Мбит/с), значит, вы тестируете возможности сети, а не производительность сервера.
3.  **Валидация настроек:** Всегда проверяйте через логи или браузер, что сервер действительно применяет ожидаемые настройки (например, сжатие). Можно скопировать нужные заголовки (`Accept-Encoding`, `Accept`) прямо из DevTools браузера и передать их утилите.
4.  **Анализ перцентилей:** Среднее время ответа малоинформативно. Важно смотреть на 95-й, 99-й и 100-й (максимальный) перцентили. Высокие значения в "длинном хвосте" указывают на проблемы, заметные для части пользователей.
5.  **Длительность теста:** Для повышения точности тест должен длиться не несколько секунд, а минуты. Если тестируется работа с базами данных, могут потребоваться часы для выявления долговременных эффектов.

### Основные инструменты

| Инструмент | Потоки | Протоколы | Особенности |
| :--- | :--- | :--- | :--- |
| **ab (Apache Benchmark)** | Однопоточный | HTTP/1.0, 1.1 | Простой, встроен в `apache2-utils`. Лимитирован одним ядром CPU. |
| **wrk** | Многопоточный | HTTP/1.1 | Высокая производительность, поддержка Lua-скриптов. |
| **wrkx** | Многопоточный | HTTP/1.1 | Форк `wrk2` с патчами (А. Рыбак, Death Hands). Позволяет задавать фиксированный RPS (`-R`). |
| **h2load** | Многопоточный | HTTP/1.1, HTTP/2, HTTP/3 | Часть пакета `nghttp2`. Эффективен для тестирования H2 и HPACK. HTTP/3 экспериментально. |

## Practical Scenarios

### Apache Benchmark (ab)

Утилита из пакета `apache2-utils`. Так как она однопоточная, при тестировании очень быстрых ресурсов (например, отдачи статики Nginx) вы можете упереться в производительность самой утилиты (одного ядра CPU), а не сервера.

```bash
# Установка (Ubuntu)
sudo apt install apache2-utils

# Запуск теста
ab -n 5000 -c 10 -k -L -H "Accept-Encoding: gzip" https://example.com/
```

- `-n`: общее количество запросов.
- `-c`: уровень конкурентности (одновременных соединений). Важно: реально это все равно один поток исполнения.
- `-k`: Keep-Alive (использование одного соединения для нескольких запросов). Позволяет тестировать пропускную способность, а не скорость установки соединений.
- `-L`: игнорировать разницу в длине ответов (по умолчанию `ab` считает ответы разной длины ошибочными).
- `-H`: добавление кастомных заголовков (например, для проверки сжатия).

### wrk и wrkx

`wrk` — стандарт де-факто для высокопроизводительных тестов. `wrkx` — форк `wrk2`, поддерживаемый Алексеем Рыбаком (Death Hands), с дополнительными патчами для повышения точности.

```bash
# Зависимости для сборки (Ubuntu 24.04)
sudo apt install build-essential git libssl-dev zlib1g-dev

# Сборка wrkx
git clone https://github.com/deathhands/wrkx.git
cd wrkx && make

# Запуск теста в wrkx
./wrk -t2 -c50 -d20s -R1000 --latency https://example.com/
```

- `-t2`: 2 потока исполнения (используют 2 ядра CPU).
- `-c50`: 50 параллельных соединений.
- `-d20s`: длительность теста 20 секунд.
- `-R1000`: (только в wrkx/wrk2) целевая частота 1000 запросов в секунду. Если сервер не справляется, реальная частота будет ниже.
- `--latency`: вывод подробной статистики по перцентилям и HDR-диаграммам.

### h2load (HTTP/2 и HTTP/3)

Инструмент из состава `nghttp2-client`. Позволяет сравнивать производительность разных версий протоколов в рамках одной утилиты.

```bash
# Установка (Ubuntu)
sudo apt install nghttp2-client

# Тестирование HTTP/2 (по умолчанию)
h2load -n 5000 -c 100 -t 2 https://example.com/

# Тестирование HTTP/1.1
h2load -n 5000 -c 100 -t 2 -H1 https://example.com/
```

- В результатах обратите внимание на **traffic savings** (HPACK) — экономию на передаче заголовков.
- Поддержка **HTTP/3** на данный момент является экспериментальной.

## Additional Information

### Бенчмарк как процесс познания

Главный эффект от бенчмаркинга — не "голые" цифры, а понимание того, как система реагирует на нагрузку.
- Если результаты странные или резко отличаются от ожидаемых — это повод анализировать систему глубже.
- Сравнивайте утилиты между собой: результаты `h2load -H1` и `wrk` на одном и том же сервере будут отличаться, так как утилиты работают по-разному.
- Проверяйте параметры TLS: разные утилиты (или одна утилита с разными серверами) могут договариваться о разных шифрах, что сильно влияет на CPU и RPS.

### Когда и что использовать?

- Если нужно быстро проверить RPS статики на одном ядре — **ab**.
- Если нужно выжать максимум RPS из сервера — **wrk**.
- Если нужно построить точный график задержки (Latency) при фиксированной нагрузке — **wrkx**.
- Если цель — сравнить производительность HTTP/1.1 vs HTTP/2 — **h2load**.
