# Инструменты для бенчмаркинга веб-серверов

## Определения

**Бенчмаркинг веб-сервера** — процесс измерения предельных возможностей серверного ПО и аппаратной части при контролируемой нагрузке. Основные метрики включают:
- **RPS (Requests Per Second):** количество успешно обработанных запросов в секунду.
- **Latency (Задержка):** время от момента отправки запроса до получения последнего байта ответа (TTLB).
- **Throughput (Пропускная способность):** объем переданных данных (бит/с), на который влияет как размер ресурсов, так и эффективность протоколов.

**Модели нагрузки:**

1.  **Закрытый цикл (Closed Loop / Concurrency-based):** режим, при котором новый запрос отправляется только после получения ответа на предыдущий. Если сервер начинает «тормозить», нагрузчик автоматически замедляется. Это скрывает реальные проблемы под нагрузкой. Примеры: `ab`, базовый `wrk`.
2.  **Открытый цикл (Open Loop / Rate-based):** режим, при котором запросы отправляются со строго заданной частотой (например, 1000 RPS) независимо от того, успел ли сервер ответить на предыдущие. Это лучше имитирует реальное поведение пользователей интернета. Примеры: `wrk2` (и его форки `wrkx`), `Vegeta`, `k6` (arrival rate).

**Скоординированный пропуск (Coordinated Omission):**
Статистическая аномалия, характерная для инструментов закрытого цикла. Если один запрос зависает на 10 секунд, нагрузчик в этом потоке тоже висит, не отправляя новые запросы. В итоговом отчете виден один плохой запрос, но не видны те тысячи запросов, которые должны были отправиться за это время и также получить огромную задержку. Это приводит к катастрофическому занижению перцентилей задержки в отчетах.

## Основные концепции

### Принципы корректного тестирования

Для получения достоверных данных необходимо соблюдать следующие правила изоляции:

1.  **Физическое разделение окружений:** Агент тестирования (нагрузчик) и объект тестирования (веб-сервер) обязаны находиться на разных физических ресурсах (или как минимум разных KVM-виртуалках с закрепленными ядрами CPU). Тестирование через `localhost` или внутри одного Docker-контейнера бессмысленно, так как нагрузчик потребляет ресурсы CPU, необходимые серверу, и обходит реальный сетевой стек ядра Linux.
2.  **Сетевой лимит:** Перед тестом рассчитайте ожидаемую пропускную способность. Если вы тестируете отдачу статики на 1 Гбит/с линке и получаете 120 МБ/с, вы уперлись в пропускную способность сетевого интерфейса, а не в производительность ПО.
3.  **Валидация настроек (Check-then-Benchmark):** Всегда выполняйте `curl -I --http3` перед тестом. Убедитесь, что:
    - Используется нужный протокол (HTTP/2, HTTP/3).
    - Включено сжатие (Brotli/Gzip), если оно тестируется.
    - Отсутствуют лишние редиректы (301/302).
4.  **Анализ перцентилей (The Tail Latency):** Среднее арифметическое время ответа бесполезно. Фокусируйтесь на:
    - **p95:** время ответа для 95% пользователей.
    - **p99:** критический показатель для "хвостовых" задержек.
    - **p99.9:** выявление редких, но критических блокировок (Stop-the-world в GC или дисковый I/O).

### Системная подготовка (Tuning)

Перед проведением тестов на экстремальные нагрузки (десятки и сотни тысяч RPS) необходимо настроить ядро Linux как на стороне сервера, так и на стороне нагрузчика.

**1. Лимиты файловых дескрипторов:**
Каждое соединение — это файл.
```bash
# Проверка и установка лимитов (ulimit)
ulimit -n 1000000
```

**2. Настройка TCP-стека (sysctl):**
```bash
# Увеличение диапазона локальных портов для нагрузчика
sysctl -w net.ipv4.ip_local_port_range="1024 65535"

# Быстрое переиспользование TIME_WAIT сокетов
sysctl -w net.ipv4.tcp_tw_reuse=1

# Увеличение размера очереди входящих соединений
sysctl -w net.core.somaxconn=65535
sysctl -w net.ipv4.tcp_max_syn_backlog=65535
```

### Обзор инструментов

| Инструмент | Язык | Протоколы | Особенности и статус 2026 |
| :--- | :--- | :--- | :--- |
| **ab** | C | HTTP/1.1 | Legacy. Один поток. Только для базовой проверки. |
| **wrk** | C | HTTP/1.1 | Максимальный RPS. Lua-скрипты. Страдает Coordinated Omission. |
| **wrk2 / wrkx** | C | HTTP/1.1 | Решает Coordinated Omission. Гистограммы HDR. Форк `wrkx` актуален для новых ОС. |
| **h2load** | C++ | HTTP/1.1, 2, 3 | Лучший для HTTP/2 и HTTP/3 (QUIC). Часть `nghttp2`. |
| **k6** | Go/TS | HTTP/1.1, 2, 3, gRPC | v2.2.0. Нативный TypeScript. Полный gRPC-стриминг. Стандарт CI/CD. |
| **ghz** | Go | gRPC | Специализированный для gRPC. Контроль соединений vs потоков. |
| **fortio** | Go | HTTP/1.1, 2, gRPC | Легковесный инструмент, стандарт для Istio. |
| **Vegeta** | Go | HTTP/1.1, 2 | Идеален для Open Loop (постоянный RPS). |
| **Bombardier** | Go | HTTP/1.1, 2 | Очень быстрый. Поддержка HTTP/2 из коробки. |
| **Hey** | Go | HTTP/1.1, 2 | Простая альтернатива `ab` с поддержкой HTTP/2. |

## Практические сценарии

### Использование Apache Benchmark (ab)

Подходит для быстрой проверки RPS конфигурации на одном ядре. Не поддерживает современные протоколы (HTTP/2+) и сложные заголовки.

```bash
# Установка (Ubuntu)
sudo apt install apache2-utils

# Тест: 10 000 запросов, 50 одновременных соединений, Keep-Alive включен
ab -n 10000 -c 50 -k -L -H "Accept-Encoding: gzip" https://example.com/
# -k: использование постоянных соединений (минимизация handshake)
# -L: следовать редиректам (иногда полезно для проверки балансировщиков)
```

### Тестирование с wrk2 / wrkx (Open Loop)

Позволяет задавать фиксированный RPS, что критично для построения графиков Latency vs Load.

```bash
# Запуск: 2 потока нагрузчика, 100 соединений, 30 секунд, целевой RPS 5000
wrk -t2 -c100 -d30s -R5000 --latency https://example.com/
# -R: Constant Request Rate (Open Loop)
# --latency: выводит таблицу перцентилей (HDR Histogram)
```

### Тестирование HTTP/2 и HTTP/3 (h2load)

Утилита из пакета `nghttp2-client`. Позволяет тестировать мультиплексирование (много стримов в одном соединении).

```bash
# Тестирование HTTP/3 (QUIC)
h2load -n 10000 -c 100 -m 50 --npn-list h3 https://example.com/
# -m: streams per connection (50 параллельных запросов в одном TCP/UDP соединении)
```
**Нюансы 2026:** При анализе HTTP/3 (QUIC) критически важно проверять эффективность **0-RTT** (Early Data). Если задержка первого запроса в соединении значительно выше последующих, значит 0-RTT не настроен или не работает. Также учитывайте, что обработка UDP для QUIC потребляет до 2–3 раз больше CPU, чем эквивалентный трафик по TCP.

### Использование Hey и Bombardier (Go-нагрузчики)

Эти инструменты значительно эффективнее `ab` и проще в установке, чем `wrk`.

```bash
# Hey: 200 запросов, 20 соединений, HTTP/2 по умолчанию
hey -n 200 -c 20 https://example.com/

# Bombardier: тест на 10 секунд с ограничением в 1000 RPS
bombardier -d 10s -r 1000 https://example.com/
```

### Сценарий: Глубокое тестирование производительности TLS

При сравнении библиотек (OpenSSL vs AWS-LC) или типов ключей (RSA vs ECDSA) следуйте этому протоколу:

1.  **Изоляция Handshake:** Создайте специальный эндпоинт:
    ```nginx
    location /zero {
        return 200 "";
        access_log off; # Отключение логов критично при высоких RPS
    }
    ```
    Это исключит влияние дискового I/O и времени генерации ответа бэкендом.
2.  **Отключение сжатия:** Установите `gzip off;` и `brotli off;`, чтобы CPU тратился только на криптографию.
3.  **Верификация шифров:** Включите логирование параметров TLS на этапе подготовки:
    ```nginx
    log_format tls_perf '$remote_addr "$request" $ssl_protocol $ssl_cipher';
    server {
        access_log /var/log/nginx/tls_verify.log tls_perf;
        ssl_log_params on; # Только в Angie или современных сборках Nginx
    }
    ```
    После того как убедитесь, что тест идет на нужном шифре (например, `TLS_AES_256_GCM_SHA384`), **ОБЯЗАТЕЛЬНО** выключите логирование для финального замера.
4.  **Смена библиотек:** При тестировании разных сборок Nginx используйте символические ссылки для переключения бинарника `nginx` и проверяйте версию через `nginx -V`.

### Современное нагрузочное тестирование с k6 (v2.2.0)

Обзор ключевых концепций k6: [Нагрузочное тестирование с помощью k6](../Testing/k6_load_testing.md). k6 версии 2.2.0 поддерживает нативный TypeScript и расширенные возможности gRPC-стриминга.

```typescript
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Options } from 'k6/options';

export const options: Options = {
  scenarios: {
    constant_request_rate: {
      executor: 'constant-arrival-rate',
      rate: 1000, // 1000 RPS
      timeUnit: '1s',
      duration: '1m',
      preAllocatedVUs: 50,
      maxVUs: 100,
    },
  },
  thresholds: {
    http_req_duration: ['p(99)<200'], // SLA: p99 должен быть меньше 200мс
  },
};

export default function () {
  let res = http.get('https://api.example.com/v1/health');
  check(res, { 'status is 200': (r) => r.status === 200 });
}
```

### Тестирование gRPC и WebSocket

1.  **gRPC:** Используйте специализированный инструмент **ghz** для глубокого анализа или **k6** (модуль `k6/net/grpc`) для сценариев.
    ```bash
    # Пример ghz: 10 соединений, 100 конкурентных запросов
    ghz --insecure --proto ./service.proto --call service.Method -c 10 -q 100 localhost:50051
    ```
    **Важно для Kubernetes:** Из-за "залипания" gRPC-соединений на L4-балансировщиках (Service ClusterIP), бенчмаркинг может нагружать только один под. Используйте Headless Services или Service Mesh для честной балансировки L7.
2.  **WebSocket:** k6 предоставляет нативную поддержку (модуль `k6/ws`). Для простого бенчмаркинга десятков тысяч соединений используйте `tsung`.

## Дополнительная информация

### Выбор инструмента по задаче

- **Нужен сырой RPS (Benchmark сервера):** `wrk`, `Bombardier` или `h2load`.
- **Нужна задержка под нагрузкой (SLA/Performance):** `wrk2`, `Vegeta` или `k6`.
- **Нужен HTTP/3 / QUIC:** `h2load` или `k6` (с xk6-http3).
- **Нужен gRPC:** `ghz`, `fortio` или `k6`.
- **Нужны сложные бизнес-сценарии (Auth, API flows):** `k6`.
