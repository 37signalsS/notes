## Определения

**Бенчмаркинг веб-сервера** — процесс измерения предельных возможностей серверного ПО и аппаратной части при контролируемой нагрузке. Основные метрики включают:
- **RPS (Requests Per Second):** количество успешно обработанных запросов в секунду.
- **Latency (Задержка):** время от момента отправки запроса до получения последнего байта ответа (TTLB).
- **Throughput (Пропускная способность):** объем переданных данных (бит/с), на который влияет как размер ресурсов, так и эффективность протоколов.

**Модели нагрузки:**

1.  **Закрытый цикл (Closed Loop / Concurrency-based):** режим, при котором новый запрос отправляется только после получения ответа на предыдущий. Если сервер начинает «тормозить», нагрузчик автоматически замедляется. Это скрывает реальные проблемы под нагрузкой. Примеры: `ab`, базовый `wrk`.
2.  **Открытый цикл (Open Loop / Rate-based):** режим, при котором запросы отправляются со строго заданной частотой (например, 1000 RPS) независимо от того, успел ли сервер ответить на предыдущие. Это лучше имитирует реальное поведение пользователей интернета. Примеры: `wrkx -R`, `Vegeta`, `k6` (arrival rate).

**Coordinated Omission (Скоординированный пропуск):**
Статистическая аномалия, характерная для инструментов закрытого цикла. Если один запрос «завис» на 10 секунд, нагрузчик в этом потоке тоже висит, не отправляя новые запросы. В итоговом отчете мы увидим один «плохой» запрос, но не увидим тех тысяч запросов, которые *должны были* отправиться за эти 10 секунд и тоже получить огромную задержку. Это приводит к катастрофическому занижению перцентилей задержки в отчетах.

## Основные концепции

### Принципы корректного тестирования

Для получения достоверных данных, которые можно использовать в Production, необходимо соблюдать следующие правила изоляции:

1.  **Физическое разделение окружений:** Агент тестирования (нагрузчик) и объект тестирования (веб-сервер) **ОБЯЗАНЫ** находиться на разных физических ресурсах (или как минимум разных KVM-виртуалках с закрепленными ядрами CPU). Тестирование через `localhost` или внутри одного Docker-контейнера бессмысленно, так как нагрузчик потребляет ресурсы CPU, необходимые серверу, и обходит реальный сетевой стек ядра Linux.
2.  **Сетевой лимит:** Перед тестом рассчитайте ожидаемую пропускную способность. Если вы тестируете отдачу статики на 1 Гбит/с линке и получаете 120 МБ/с, вы уперлись в сетевую карту, а не в производительность Nginx/Angie.
3.  **Валидация настроек (Check-then-Benchmark):** Всегда выполняйте `curl -I` перед тестом. Убедитесь, что:
    - Используется нужный протокол (HTTP/2, HTTP/3).
    - Включено сжатие (Brotli/Gzip), если оно тестируется.
    - Отсутствуют лишние редиректы (301/302).
4.  **Анализ перцентилей (The Tail Latency):** Среднее арифметическое время ответа бесполезно. Фокусируйтесь на:
    - **p95:** время ответа для 95% пользователей.
    - **p99:** критический показатель для "хвостовых" задержек.
    - **p99.9:** выявление редких, но критических блокировок (Stop-the-world в GC или дисковый I/O).

### Обзор инструментов (Статус 2026)

| Инструмент | Потоки | Протоколы | Статус 2026 |
| :--- | :--- | :--- | :--- |
| **ab** | 1 | HTTP/1.1 | Legacy. Только для простых тестов одного ядра. |
| **wrk** | Много | HTTP/1.1 | Стандарт для выжимания макс. RPS. Поддерживает Lua-скрипты. |
| **wrkx** | Много | HTTP/1.1 | **Рекомендуется** для замера задержки (решает Coordinated Omission). |
| **h2load** | Много | HTTP/1.1, 2, 3 | Эталон для тестирования современных бинарных протоколов. |
| **k6** | Много | HTTP/1.1, 2, 3, gRPC | Современный стандарт CI/CD. Сценарии на JS/TypeScript. |
| **Vegeta** | Много | HTTP/1.1, 2 | Идеален для Open Loop (Constant Request Rate). |

## Практические сценарии

### Использование Apache Benchmark (ab)

Подходит для быстрой проверки RPS конфигурации на одном ядре. Не поддерживает современные протоколы (HTTP/2+) и сложные заголовки.

```bash
# Установка (Ubuntu)
sudo apt install apache2-utils

# Тест: 10 000 запросов, 50 одновременных соединений, Keep-Alive включен
ab -n 10000 -c 50 -k -L -H "Accept-Encoding: gzip" https://example.com/
# -k: использование постоянных соединений (минимизация handshake)
# -L: следовать редиректам (иногда полезно для проверки балансировщиков)
```

### Тестирование с wrkx (Open Loop)

`wrkx` — это форк `wrk2` с исправлениями для современных ОС. Он позволяет задавать фиксированный RPS, что критично для построения графиков Latency vs Load.

```bash
# Сборка из исходников (требует OpenSSL 3.x)
git clone https://github.com/deathhands/wrkx.git && cd wrkx && make

# Запуск: 2 потока нагрузчика, 100 соединений, 30 секунд, целевой RPS 5000
./wrk -t2 -c100 -d30s -R5000 --latency https://example.com/
# -R: Constant Request Rate (Open Loop)
# --latency: выводит таблицу перцентилей с высокой точностью (High Dynamic Range Histogram)
```

### Тестирование HTTP/2 и HTTP/3 (h2load)

Утилита из пакета `nghttp2-client`. Лучший выбор для проверки мультиплексирования.

```bash
# Тестирование HTTP/3 (требует поддержки QUIC в клиенте)
h2load -n 10000 -c 100 -m 50 --npn-list h3 https://example.com/
# -m: количество параллельных потоков (streams) внутри одного соединения
# --npn-list: список протоколов для согласования (h3, h2, http/1.1)
```

### Сценарий: Глубокое тестирование производительности TLS

При сравнении библиотек (OpenSSL vs AWS-LC) или типов ключей (RSA vs ECDSA) следуйте этому протоколу:

1.  **Изоляция Handshake:** Создайте специальный endpoint в Nginx/Angie:
    ```nginx
    location /zero {
        return 200 "";
        access_log off; # Отключение логов критично при высоких RPS
    }
    ```
    Это исключит влияние дискового I/O и времени генерации ответа бэкендом.
2.  **Отключение сжатия:** Установите `gzip off;` и `brotli off;`, чтобы CPU тратился только на криптографию.
3.  **Верификация шифров:** Включите логирование параметров TLS на этапе подготовки:
    ```nginx
    log_format tls_perf '$remote_addr "$request" $ssl_protocol $ssl_cipher';
    server {
        access_log /var/log/nginx/tls_verify.log tls_perf;
        ssl_log_params on; # Только в Angie или современных сборках Nginx
    }
    ```
    После того как убедитесь, что тест идет на нужном шифре (например, `TLS_AES_256_GCM_SHA384`), **ОБЯЗАТЕЛЬНО** выключите логирование для финального замера.
4.  **Смена библиотек:** При тестировании разных сборок Nginx (например, системный OpenSSL 3.5 против AWS-LC 5.0) используйте символические ссылки для переключения бинарника `nginx` и проверяйте версию через `nginx -V`.

### Современное нагрузочное тестирование с k6

k6 позволяет писать гибкие сценарии на JS и интегрировать их в GitHub Actions / GitLab CI.

```javascript
import http from 'k6/http';
import { sleep, check } from 'k6';

export const options = {
  stages: [
    { duration: '1m', target: 100 }, // Прогрев до 100 пользователей
    { duration: '3m', target: 1000 }, // Пиковая нагрузка 1000 пользователей
    { duration: '1m', target: 0 },    // Остывание
  ],
  thresholds: {
    http_req_duration: ['p(99)<200'], // Тест провален, если p99 > 200мс
  },
};

export default function () {
  let res = http.get('https://example.com/api/v1/status');
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);
}
```

## Дополнительная информация

### Выбор инструмента по задаче

- **Нужен сырой RPS (Benchmark сервера):** `wrk`.
- **Нужна задержка под нагрузкой (SLA/Performance):** `wrkx` или `Vegeta`.
- **Нужен HTTP/3 / QUIC:** `h2load`.
- **Нужны бизнес-сценарии (Auth, API flows):** `k6`.
