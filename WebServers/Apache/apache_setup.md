# Установка и настройка Apache

    ```bash
    apt update && apt -y install apache2
    ```

    ```bash
    systemctl status apache2
    ```
На Ubuntu и Debian службы после установки запускаются и добавляются в автозапуск автоматически, на Centos это нужно сделать вручную.

## Настройка Firewall (CentOS)

На CentOS после установки нужно отредактировать настройки встроенного фаервола:

```bash
firewall-cmd --permanent --zone=public --add-service=http --add-service=https
firewall-cmd --reload
```

Проверить, что настройки успешно применились, можно с помощью команды:

```bash
firewall-cmd --list-all
```

В блоке `Services` в списке должны отображаться `http` и `https.

## Проверка работы

*   **CentOS/RHEL-подобные:** Теперь можно открыть IP-адрес вашего сервера в браузере — откроется стартовая страница веб-сервера (на современных RHEL-подобных дистрибутивах Apache по умолчанию не имеет приветственной страницы. CentOS 7 и 8 достигли EOL, рекомендуется использовать AlmaLinux/Rocky Linux).
*   **Debian и Ubuntu:** Можно сразу ввести IP-адрес вашего сервера в адресную строку браузера — откроется приветственная страница веб-сервера, размещенная в директории `/var/www/html`.

## Конфигурационные файлы

Расширенные настройки веб-сервера доступны в конфигурационном файле:

*   **Ubuntu и Debian:** `/etc/apache2/apache2.conf`
*   **CentOS:** `/etc/httpd/conf/httpd.conf`

## Архитектура Apache и проблема C10K

Исторически Apache был одним из самых популярных веб-серверов. Однако его традиционная архитектура столкнулась с проблемой C10K (обслуживание 10 000 одновременных соединений), особенно в режиме `Prefork` MPM (Multi-Processing Module).

### Проблема C10K в режиме Prefork

В режиме `Prefork` Apache запускает отдельный процесс для каждого входящего соединения. Это означает, что для 10 000 одновременных соединений потребуется 10 000 процессов Apache. Каждый такой процесс потребляет значительный объем оперативной памяти (даже если он простаивает), что приводит к высокому потреблению ресурсов и неэффективности при обработке большого количества неактивных, но открытых соединений. Это и есть **проблема C10k**.

### Multi-Processing Modules (MPM)

Apache использует MPM для управления тем, как он обрабатывает запросы клиентов. Основные MPM:
*   **Prefork:** Создает дочерние процессы, каждый из которых обрабатывает одно соединение. Процессы изолированы друг от друга, что обеспечивает стабильность, но приводит к высокому потреблению памяти при большом количестве соединений. Подходит для модулей, требующих изоляции (например, `mod_php`).
*   **Worker:** Использует несколько дочерних процессов, каждый из которых запускает несколько потоков. Каждый поток обрабатывает одно соединение. Это более эффективно с точки зрения памяти, чем `Prefork`, но требует, чтобы модули были потокобезопасными.
*   **Event:** Является развитием `Worker` MPM и предназначен для более эффективной обработки keep-alive соединений. Он использует асинхронный подход, позволяя одному потоку обрабатывать несколько соединений, которые неактивны. Это значительно улучшает масштабируемость по сравнению с `Prefork` и `Worker` для высоконагруженных сценариев.

### Сравнение с Nginx

В отличие от Apache (особенно в режиме `Prefork`), Nginx изначально был разработан с асинхронной, событийно-ориентированной архитектурой, что позволило ему эффективно решать проблему C10K с минимальным потреблением ресурсов. Nginx использует однопоточные воркер-процессы, каждый из которых может обрабатывать тысячи одновременных соединений.

Хотя современные версии Apache с MPM `Event` также могут работать эффективно, Nginx часто предпочтительнее для роли фронтенд-сервера, обратного прокси и балансировщика нагрузки благодаря своей легковесности и высокой производительности при обслуживании статического контента и проксировании запросов. Apache, в свою очередь, может быть использован как бэкенд-сервер для обработки динамического контента (например, PHP-приложений) за Nginx.
