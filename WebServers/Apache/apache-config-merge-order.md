# Apache: Порядок объединения конфигурационных секций (Merge Order)

**Актуально для:** Apache HTTP Server 2.4.x

---

## Определения

**Merge order (порядок объединения)** — детерминированный порядок, в котором ядро Apache HTTP Server объединяет директивы из различных конфигурационных контейнеров (`<Directory>`, `<Location>`, `<Files>`, `<VirtualHost>`, `<Proxy>`, `.htaccess`, `<If>`) при обработке входящего HTTP-запроса. Итоговая конфигурация определяется не последовательностью строк в файле, а типом контейнера, специфичностью пути и фазой обработки.

**Прецедентность (precedence)** — базовый принцип слияния конфигурации: директива из секции более высокого приоритета (вычисляемой позже в цепочке слияния) перекрывает аналогичную директиву из секции более низкого приоритета.

**Сливаемые директивы (mergeable directives)** — директивы, значения которых из родительского контекста наследуются и комбинируются с директивами дочернего контекста (например, `Options` с префиксами `+`/`-`, `Header merge/append`), в отличие от перекрывающих директив, которые замещаются целиком.

**Перекрывающие директивы (overriding directives)** — директивы, дочернее объявление которых полностью аннулирует родительское значение для данного запроса (например, `ErrorDocument`, `DirectoryIndex`, `SetHandler`).

**Контекст конфигурации (Configuration Context / Scope)** — область видимости директивы. Различают глобальный контекст (`server config`), контекст виртуального хоста (`<VirtualHost>`), контексты файловой системы (`<Directory>`, `<Files>`, `.htaccess`) и контексты пространства веб-адресов (`<Location>`, `<Proxy>`).

**AllowOverride** — директива в блоке `<Directory>`, определяющая группы директив, которые разрешено переопределять через локальные файлы `.htaccess` (например, `AuthConfig`, `FileInfo`, `Indexes`, `Limit`, `Options`, либо `All`/`None`).

**AuthMerging** — директива модуля `mod_authz_core`, явно управляющая логикой объединения требований авторизации (`Require`) при переходе между родительскими и дочерними секциями (`Off`, `And`, `Or`).

## Основные концепции

### Фазы обработки запроса и конфигурационные контейнеры

Apache HTTP Server обрабатывает каждый входящий запрос через последовательность фаз жизненного цикла (hook phases). Конфигурационные секции привязаны к соответствующим этапам:

| Фаза обработки | Контейнеры и директивы | Ответственность и назначение |
|---|---|---|
| 1. Анализ сокета и хоста | `Listen`, `<VirtualHost>` | Привязка к порту/IP, выбор виртуального хоста по IP, порту и SNI/заголовку `Host:`. |
| 2. Трансляция URL (Name translation) | `Alias`, `DocumentRoot`, `RewriteRule` | Преобразование запрашиваемого пути URL в локальный путь файловой системы или прокси-цель. |
| 3. Сопоставление с ФС (Directory/Files walk) | `<Directory>`, `<Files>`, `.htaccess` | Проверка прав доступа к физическим путям, чтение настроек каталогов. |
| 4. Пространство URL (Location walk) | `<Location>`, `<LocationMatch>` | Применение правил к финальному URL (включая виртуальные адреса и прокси). |
| 5. Проверка доступа и авторизация | `Require`, `AuthMerging`, `<Proxy>` | Проверка политик AuthN/AuthZ на базе накопленного дерева конфигурации. |
| 6. Генерация контента (Handler phase) | `SetHandler`, `AddHandler`, `ProxyPass` | Передача запроса обработчику (статический файл, FastCGI, модуль, балансировщик). |
| 7. Логирование и пост-обработка | `CustomLog`, `Header always` | Запись в журналы, отдача финальных заголовков клиенту. |

### Официальный алгоритм слияния (Apache 2.4 Merge Order)

Ядро Apache применяет конфигурационные контейнеры в строгом порядке из пяти основных групп. Каждая последующая группа перекрывает или дополняет параметры предыдущих:

1. **Группа 1: `<Directory>` (без регулярных выражений) и `.htaccess`:**
   - Секции `<Directory>` обрабатываются строго от **самого короткого компонента пути к самому длинному** (от корня ФС к вложенным каталогам), независимо от порядка их следования в конфигурационных файлах.
   - Если для одного и того же каталога задано несколько блоков `<Directory>`, они сливаются в порядке их появления в конфигурационном файле.
   - Файлы `.htaccess` читаются и сливаются **одновременно** с соответствующим уровнем каталога (при разрешении через `AllowOverride`). Директивы из `.htaccess` переопределяют настройки родительского `<Directory>` для данного каталога.
   - **Замещение прокси:** если запрос обрабатывается через `mod_proxy`, контейнер `<Proxy>` занимает место контейнера `<Directory>` в общем порядке объединения.

2. **Группа 2: `<DirectoryMatch>` и `<Directory ~>`:**
   - Обрабатываются после всех стандартных `<Directory>` и `.htaccess`.
   - Несколько блоков `<DirectoryMatch>` вычисляются строго в порядке их появления в конфигурационных файлах.

3. **Группа 3: `<Files>` и `<FilesMatch>`:**
   - Обрабатываются одновременно после секций каталогов.
   - Сливаются в порядке появления в конфигурации.

4. **Группа 4: `<Location>` и `<LocationMatch>`:**
   - Обрабатываются одновременно после секций файловой системы.
   - Сливаются в порядке появления в конфигурационных файлах.

5. **Группа 5: Условные секции `<If>`, `<ElseIf>`, `<Else>`:**
   - Обрабатываются **последними**, даже если синтаксически вложены внутрь предшествующих контейнеров (`<Directory>`, `<Files>`, `<Location>`).
   - Исключение: выражения `<If>`, которые вычисляются на ранних этапах работы ядра до сопоставления с ФС.

```
+------------------------------------------------------------------------+
| 1. <Directory "/var/web"> -> <Directory "/var/web/app"> + .htaccess    |
|    (от короткого пути к длинному; для proxy-запросов вместо нее <Proxy>)|
+------------------------------------------------------------------------+
                                    |
                                    v
+------------------------------------------------------------------------+
| 2. <DirectoryMatch "^/var/web/.*">                                    |
|    (в порядке появления в конфиге)                                     |
+------------------------------------------------------------------------+
                                    |
                                    v
+------------------------------------------------------------------------+
| 3. <Files "config.json"> и <FilesMatch "\.php$">                      |
|    (одновременно, в порядке появления)                                 |
+------------------------------------------------------------------------+
                                    |
                                    v
+------------------------------------------------------------------------+
| 4. <Location "/api"> и <LocationMatch "^/api/v[0-9]+">                 |
|    (одновременно, в порядке появления; перекрывает Directory и Files)  |
+------------------------------------------------------------------------+
                                    |
                                    v
+------------------------------------------------------------------------+
| 5. <If ...> / <ElseIf ...> / <Else>                                    |
|    (обрабатываются последними; перекрывают директивы групп 1-4)        |
+------------------------------------------------------------------------+
```

### Архитектурные правила и краевые условия

#### 1. Изоляция и приоритет VirtualHost
- Секции внутри блока `<VirtualHost>` применяются **после** аналогичных секций внешнего глобального контекста сервера (`server config`). Это позволяет виртуальным хостам переопределять общие настройки хоста.
- **Правило одного VirtualHost:** для каждого входящего TCP-соединения/HTTP-запроса Apache выбирает **ровно один** блок `<VirtualHost>` (по IP:Port и заголовку `Host:`/SNI). Директивы из разных секций `<VirtualHost>` **никогда не объединяются между собой**.

#### 2. Встраивание файлов через `Include` / `IncludeOptional`
- Директивы `Include` не создают изолированных областей видимости. Включаемый файл интерпретируется ровно так, как если бы его содержимое было буквально скопировано в место вызова `Include`.
- Порядок применения директив из каталогов (например, `conf.d/*.conf`) определяется **алфавитной сортировкой имен файлов**.

#### 3. Предварительная трансляция `<Location>`
- Ядро Apache выполняет предварительный проход `<Location>` / `<LocationMatch>` непосредственно перед фазой трансляции имени (`name translation phase`, где работают `Alias` и `DocumentRoot`). Результаты этого предварительного прохода полностью сбрасываются после завершения трансляции, а окончательное слияние `<Location>` выполняется на шаге 4.

#### 4. Особенность `<If>` внутри `.htaccess`
- Если директива `<If>` используется внутри файла `.htaccess` родительского каталога, вложенные в неё директивы будут объединены **после** обычных (не заключенных в `<If>`) директив из `.htaccess` подкаталога.

#### 5. Механизм слияния на уровне C-модулей (Per-module Merge Callbacks)
Слияние конфигураций в Apache — это вызов функций обратного вызова C-структур конкретных модулей (`merge_dir_config` и `merge_server_config`). Каждый модуль самостоятельно определяет семантику слияния своих параметров:

| Модуль / Директива | Тип слияния | Правило разрешения конфликта |
|---|---|---|
| `Options` (`core`) | Накопительное / Замещающее | Префиксы `+` и `-` добавляют или убирают флаги относительно родителя. Указание опций **без знаков** полностью сбрасывает все унаследованные параметры. |
| `Require` (`mod_authz_core`) | Управляемое (`AuthMerging`) | По умолчанию (`AuthMerging Off`) дочерний блок `Require` полностью перекрывает родительский. При `And`/`Or` правила объединяются в логический контейнер. |
| `Header` (`mod_headers`) | Накопительное | Действия `set`, `setifempty`, `append`, `merge`, `unset` применяются по очереди прохождения секций. Заголовки с флагом `always` и таблица `onsuccess` сливаются отдельно. |
| `RewriteEngine` (`mod_rewrite`) | Изолированное по умолчанию | Дочерний контекст или виртуальный хост **не наследует** правила родителя, если явно не указано `RewriteOptions Inherit` или `RewriteOptions InheritBefore`. |
| `ErrorDocument` (`core`) | Замещающее по коду | Дочерняя директива переопределяет страницу ошибки для конкретного HTTP-кода (например, 404). |
| `SetHandler` (`core`) | Замещающее | Последний обработчик по цепочке слияния перекрывает все предыдущие назначения. |

## Практические сценарии

### 1. Прецедентность `<Location>` над `<Directory>`

Контейнер `<Location>` обрабатывается позже `<Directory>`. Ограничения доступа файловой системы могут быть случайно или намеренно сняты через URL:

```apacheconf
# Защита на уровне файловой системы
<Directory "/var/www/vhosts/app">
    Options -Indexes +FollowSymLinks
    AllowOverride None
    Require all denied
</Directory>

# Открытие служебного URL
<Location "/healthz">
    SetHandler server-status
    # <Location> обрабатывается на шаге 4 (после Directory на шаге 1)
    # Доступ к /healthz будет разрешен, несмотря на запрет в /var/www/vhosts/app
    Require all granted
</Location>
```

---

### 2. Защита по умолчанию: специфичный `<Directory>` перекрывает корень

Каталоги объединяются от кратчайшего пути к длиннейшему. Стандартная конфигурация безопасности для исключения утечки системных файлов:

```apacheconf
# 1. Запретить доступ ко всей файловой системе ОС (кратчайший путь)
<Directory />
    AllowOverride None
    Require all denied
</Directory>

# 2. Разрешить доступ только к выделенному каталогу веб-приложения (более длинный путь)
<Directory "/var/www/html">
    Options -Indexes +FollowSymLinks
    AllowOverride None
    Require all granted
</Directory>
```

---

### 3. Точечное ограничение файлов через `<FilesMatch>`

Секция `<FilesMatch>` (шаг 3) вычисляется после `<Directory>` (шаг 1) и позволяет блокировать служебные файлы внутри общедоступных папок:

```apacheconf
<Directory "/var/www/html">
    Options -Indexes +FollowSymLinks
    AllowOverride None
    Require all granted
</Directory>

# Блокировка доступа к конфигурационным и скрытым файлам
<FilesMatch "(^\..*|\.(env|git|sql|yml|yaml|log))$">
    Require all denied
</FilesMatch>
```

---

### 4. Наследование авторизации через директиву `AuthMerging`

По умолчанию (`AuthMerging Off`) объявление `Require` во вложенной директории или `.htaccess` полностью отменяет авторизацию родителя. Для объединения политик безопасности используется режим `And`:

```apacheconf
# Корневой каталог защищен базовой аутентификацией
<Directory "/var/www/internal">
    AuthType Basic
    AuthName "Internal Area"
    AuthBasicProvider file
    AuthUserFile "/etc/httpd/conf/.htpasswd"
    Require valid-user
</Directory>

# В подкаталоге требуется одновременное нахождение в офисной подсети (And)
<Directory "/var/www/internal/admin">
    # AuthMerging And объединяет родительский 'Require valid-user'
    # с локальным 'Require ip' в неявный контейнер <RequireAll>
    AuthMerging And
    Require ip 10.100.0.0/16 192.168.1.0/24
</Directory>
```

---

### 5. Порядок слияния при обратном проксировании (`<Proxy>`)

При проксировании запросов контейнер `<Proxy>` заменяет собой `<Directory>` в цепочке слияния:

```apacheconf
<VirtualHost *:80>
    ServerName api.example.local

    # Контейнер <Proxy> вычисляется на шаге 1 вместо <Directory>
    <Proxy "balancer://backend_cluster">
        Require ip 10.0.0.0/8
    </Proxy>

    # Контейнер <Location> вычисляется на шаге 4 и перекрывает правила <Proxy>
    <Location "/public-api">
        ProxyPass "balancer://backend_cluster/public"
        Require all granted
    </Location>
</VirtualHost>
```

---

### 6. Условное переопределение через `<If>` и `<Else>`

Секции `<If>` (шаг 5) применяются в самом конце, позволяя корректировать поведение в зависимости от заголовков или окружения:

```apacheconf
<Directory "/var/www/html/download">
    Require all granted

    # Шаг 5: Переопределение ограничений для подозрительных клиентов
    <If "%{HTTP_USER_AGENT} =~ /(curl|wget|python-requests)/i">
        Require ip 192.168.1.0/24
    </If>
    <Else>
        Require all granted
    </Else>
</Directory>
```

---

### 7. Ловушка безопасности: `<Limit>` внутри `<Location>`

Использование `<Limit>` внутри `<Location>` для ограничения методов HTTP может непреднамеренно открыть доступ к файловой системе для остальных методов:

```apacheconf
# ОШИБКА: для всех методов, кроме POST (например, GET, HEAD),
# блок <Location> не содержит ограничений авторизации и ПЕРЕКРЫВАЕТ <Directory>
<Location "/admin">
    <Limit POST>
        Require valid-user
    </Limit>
</Location>

# БЕЗОПАСНОЕ РЕШЕНИЕ: использование <LimitExcept> или общей авторизации
<Location "/admin">
    <LimitExcept OPTIONS>
        Require valid-user
    </LimitExcept>
</Location>
```

## Операции и команды

Инструменты проверки синтаксиса, структуры виртуальных хостов и трассировки процесса слияния секций.

### 1. Синтаксический анализ и проверка подключений

```bash
# Проверка базового синтаксиса конфигурации
apachectl configtest
# → Syntax OK

# Проверка порядка загрузки включенных файлов (Include/IncludeOptional)
apachectl -t -D DUMP_INCLUDES

# →   (*) /etc/httpd/conf/httpd.conf
# →     (56) /etc/httpd/conf.modules.d/00-base.conf
# →     (120) /etc/httpd/conf.d/00-default.conf
# →     (121) /etc/httpd/conf.d/vhost-api.conf

# Вывод активной карты виртуальных хостов и порядка их выбора

# → *:80                   is a NameVirtualHost
# →          default server example.com (/etc/httpd/conf.d/00-default.conf:1)
```

### 2. Проверка загруженных модулей

```bash

# → Loaded Modules:
# →  core_module (static)
# →  so_module (static)
# →  authz_core_module (shared)
# →  headers_module (shared)
# →  rewrite_module (shared)
# → Syntax OK
```

### 3. Трассировка слияния директив через LogLevel

Для детальной отладки порядка слияния и работы авторизации в `httpd.conf` или внутри виртуального хоста задается постраничный уровень трассировки модулей:

```apacheconf
# Включение глубокой трассировки для ядра и модулей контроля доступа
LogLevel core:trace5 authz_core:trace5 rewrite:trace8
```

Просмотр журнала трассировки в реальном времени:

```bash
tail -f /var/log/httpd/error_log | grep -E "(authz_core|core)"
# → [authz_core:debug] [pid 14201] mod_authz_core.c(828): [client 192.168.1.50:43210] AH01626: authorization result of Require all granted: granted
# → [core:trace3] [pid 14201] request.c(320): [client 192.168.1.50:43210] URI to filename: /var/www/html/api/test.php
```

### 4. Проверка фактического HTTP-ответа

```bash
# Проверка заголовков ответа и HTTP-кода

# → HTTP/1.1 200 OK
# → Date: Mon, 14 Oct 2026 12:00:00 GMT

```

## Типичные ошибки и диагностика

| Симптом | Причина проблемы | Метод диагностики | Способ устранения |
|---|---|---|---|
| Ошибка `403 Forbidden` на разрешенном каталоге | Конфликт с корневым `<Directory />` или вложенным `.htaccess`, в котором задан `Require all denied` без `AuthMerging`. | Проверить журнал `error_log` с `LogLevel authz_core:trace5`. | Убедиться, что путь в дочернем `<Directory>` длиннее родительского. При необходимости включить `AuthMerging Off` (по умолчанию) для явной замены либо настроить `AllowOverride None`. |
| Ресурс открыт всему миру, несмотря на запрет в `<Directory>` | Контейнер `<Location>` или `<LocationMatch>` содержит `Require all granted` и перекрывает `<Directory>`, так как вычисляется позже (шаг 4). | Поиск пересечений URL и путей ФС: `grep -rn "Location" /etc/httpd/`. | Перенести ограничения доступа из `<Location>` в `<Directory>` или синхронизировать требования авторизации. |
| Сброс флагов `Options` (отключение `FollowSymLinks`) | Указание `Options` во вложенной директории без префиксов `+` или `-` полностью очищает все родительские опции. | Сравнить блоки `<Directory>` в родительских и дочерних файлах. | Всегда использовать модификаторы `Options +FollowSymLinks -Indexes` во вложенных контекстах вместо абсолютного перечисления `Options ...`. |
| Директивы в `.htaccess` не действуют | В родительском контейнере `<Directory>` задан `AllowOverride None`. | Команда `grep -rn "AllowOverride" /etc/httpd/`. | Указать требуемые группы директив: `AllowOverride AuthConfig FileInfo` или `AllowOverrideList DirectoryIndex`. |
| Разное поведение конфигурации на тестовом и продуктовом стендах | Различный порядок включения файлов `*.conf` через `IncludeOptional` из-за различия в именах файлов или локали сортировки. | Выполнить `apachectl -t -D DUMP_INCLUDES` на обоих серверах и сопоставить вывод. | Использовать числовые префиксы в именах конфигурационных файлов (`00-base.conf`, `10-vhost.conf`, `99-overrides.conf`). |
| Правила `RewriteRule` не работают во вложенном каталоге | `mod_rewrite` по умолчанию не наследует правила из вышестоящего контекста. | Добавить в конфигурацию `LogLevel rewrite:trace8`. | Добавить директиву `RewriteOptions Inherit` или `RewriteOptions InheritBefore` в дочерний блок `<Directory>` или `.htaccess`. |
| Несанкционированный доступ через метод `PUT`/`DELETE` к закрытому каталогу | В блоке `<Location>` задан `<Limit GET POST>`. Для неуказанных методов ограничения снимаются, и `<Location>` перекрывает `<Directory>`. | Аудит конфигурации на наличие блоков `<Limit>` внутри `<Location>`. | Заменить `<Limit>` на `<LimitExcept>` либо вынести авторизацию на уровень контейнера без фильтрации по методам. |

## Рекомендации и лучшие практики

1. **Принцип наименьших привилегий (Secure by Default):**
   - Всегда блокировать корневой каталог файловой системы в глобальном контексте:
     ```apacheconf
     <Directory />
         AllowOverride None
         Require all denied
     </Directory>
     ```
   - Разрешать доступ только к явно требуемым каталогам приложений.

2. **Разделение зон ответственности контейнеров:**
   - **`<Directory>` и `<Files>`** — использовать исключительно для контроля доступа к ресурсам файловой системы (права, `.htaccess`, обработка скриптов).
   - **`<Location>`** — использовать только для ресурсов, не привязанных к файловой системе: обработчики статуса (`server-status`, `server-info`), прокси-эндпоинты (`ProxyPass`), балансировщики. Не использовать `<Location>` для ограничения доступа к файлам на диске.

3. **Отказ от `.htaccess` в Production:**
   - Для всех рабочих каталогов устанавливать `AllowOverride None`.
   - Это исключает накладные расходы на постоянный опрос файловой системы на наличие `.htaccess` при каждом запросе (stat-вызовы) и предотвращает непреднамеренное переопределение правил безопасности веб-мастерами.

4. **Предсказуемость слияния `Options`:**
   - Никогда не смешивать в рамках одного проекта синтаксис `Options` со знаками (`+`/`-`) и без них. Во всех вложенных каталогах использовать только форму со знаками: `Options +FollowSymLinks -Indexes`.

5. **Явное управление наследованием авторизации:**
   - В сложных иерархических проектах явно задавать директиву `AuthMerging` (`Off`, `And`, `Or`), чтобы предотвратить случайное снятие парольной защиты дочерними директориями.

6. **Детерминированный порядок файлов конфигурации:**
   - Все подключаемые конфигурации в `conf.d/` или `sites-enabled/` именовать со строгими числовыми префиксами (`00-security.conf`, `10-ssl.conf`, `20-app.conf`), контролируя порядок слияния директив одного уровня.
