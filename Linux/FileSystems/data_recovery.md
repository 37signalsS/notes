# Логическое восстановление данных

## Определения

- **Логическое восстановление данных:** Процесс извлечения и восстановления файлов или ФС (Файловых Систем), потерянных из-за программных ошибок, случайного удаления, форматирования или логического повреждения структур данных, при условии физической исправности носителя.
- **Carving (Карвинг):** Метод восстановления данных, основанный на поиске известных сигнатур (заголовков и футеров) файлов в «сыром» потоке байтов, полностью игнорируя метаданные файловой системы.
- **TRIM (Discard):** Команда интерфейса ATA, позволяющая ОС информировать SSD о том, какие блоки данных больше не содержат полезной информации (например, после удаления файла). После выполнения TRIM данные физически обнуляются контроллером SSD, что делает восстановление невозможным.
- **Дескриптор файла (File Descriptor):** Абстрактный указатель (целое число), используемый процессом для доступа к открытому файлу. Если файл удалён с диска, но дескриптор открыт, данные остаются доступными через `/proc`.
- **Inode (Индексный дескриптор):** Структура метаданных ФС, содержащая права, размер, временные метки и указатели на блоки данных. При удалении файла inode помечается как свободный, но сами данные остаются на диске до перезаписи.
- **Lost+Found:** Специальный каталог в корне ext4/XFS, куда `fsck` перемещает файлы, чьи родительские директории повреждены или недоступны.
- **Undelete:** Восстановление удалённого файла через поиск его inode в журнале или таблице свободных inode и перестроение связей имени и данных.
- **dc3dd:** Forensic-версия `dd` с встроенным хешированием (MD5, SHA-1, SHA-256), хранением хешей в заголовке образа и поддержкой форензик-логирования. Используется для цепочки custody (chain of custody) при расследованиях.
- **bmap:** Утилита для ext4, отображающая логические блоки файла на физические блоки устройства. Полезна для определения, какие блоки нужно восстанавливать при частичном повреждении.

## Основные концепции

### Золотые правила восстановления

1.  **Стоп-запись:** Немедленно прекратите любую запись на носитель. Любая операция записи (включая автоматические логи системы) может перезаписать блоки, помеченные как свободные.
2.  **Режим Read-Only:** Всегда монтируйте повреждённый раздел в режиме «только чтение» или работайте с размонтированным устройством:
    ```bash
    mount -o remount,ro /dev/sdb1
    ```
3.  **Принцип образа:** Никогда не проводите эксперименты на оригинальном носителе. Создайте посекторную копию (образ) и работайте с ней.
4.  **Восстановление «вовне»:** Всегда сохраняйте восстановленные данные на **другой** физический накопитель.

### Влияние типа носителя и ФС

- **SSD против HDD:** На современных SSD с включенным TRIM восстановление удалённых файлов практически невозможно, так как контроллер очищает ячейки памяти в фоновом режиме сразу после команды `unlink`.
- **RAID-массивы:** Восстановление данных с RAID требует предварительной сборки массива (через `mdadm` или программные эмуляторы) и только после этого — применения инструментов логического восстановления.
- **Тип ФС:**
  - **Ext3/Ext4:** Хорошо поддаются восстановлению через анализ журнала.
  - **XFS:** Сложна в восстановлении из-за разреженной структуры и динамического выделения Inode.
  - **Btrfs:** Имеет встроенные инструменты для «отката» и восстановления из неповрежденных деревьев.

### Механика удаления файлов и возможности восстановления

При удалении файла через `rm` или `unlink()` ядро выполняет следующие шаги:
1. Удаляет запись из каталога (dentry).
2. Уменьшает счётчик ссылок (link count) в inode.
3. Если link count становится 0, помечает inode и блоки данных как свободные в битовых картах.

**Важно:** Сами данные на диске остаются нетронутыми до тех пор, пока блоки не будут выделены под новые файлы. Это означает:
- **Восстановление возможно** только если блоки данных не были перезаписаны.
- **Журнал ФС** (ext4, XFS) может содержать следы удалённых файлов и позволяет восстановить их через `extundelete` или анализ транзакций.
- **Page cache ядра** может содержать данные удалённого файла, если он не был вытеснен.

### Журналирование как инструмент восстановления

Журналируемые ФС (ext4, XFS, Btrfs) хранят историю операций в специальной области — журнале:
- **ext4 (JBD2):** При удалении файла операция записывается в журнал как транзакция. `extundelete` сканирует журнал, находит транзакции удаления и восстанавливает inode и блоки данных.
- **XFS:** Не имеет стандартного undelete, но `xfs_db` в экспертном режиме может исследовать логи (CIL/AIL) для поиска недавних изменений.
- **Btrfs:** Поддерживает `btrfs restore` для извлечения файлов из повреждённых snapshot'ов.

Подробнее о механизмах журналирования — в [Журналирование файловых систем](./journaling.md).

### Ограничения современных носителей

- **TRIM/Discard:** На SSD с включённым TRIM восстановление невозможно — контроллер физически обнуляет ячейки после `unlink`.
- **NVMe с namespace purge:** Аналогично TRIM, но на уровне namespace.
- **Шифрование:** Если раздел зашифрован (LUKS), восстановление возможно только после расшифровки всего раздела, так как структура ФС скрыта за слоем шифрования.
- **Сжатие на уровне ФС:** Btrfs/ZFS с включённым сжатием могут изменять расположение блоков, усложняя carving.

## Диагностика перед восстановлением

Перед началом любых восстановительных операций выполните базовую диагностику, чтобы выбрать правильный инструмент и избежать усугубления повреждений:

### Шаг 1. Определение состояния диска

```bash
# SMART-статус: ищем Reallocated_Sector_Ct, Current_Pending_Sector
sudo smartctl -a /dev/sdb | grep -E 'Reallocated|Pending|Offline_Uncorrectable'

# Журналы ошибок ядра
sudo dmesg | grep -iE 'error|fail|reset|blk_update|ata.*error'

# Проверка точек монтирования
findmnt -rn /dev/sdb1
# → если вывод пустой — устройство не смонтировано
```

### Шаг 2. Определение типа повреждения

| Симптом | Вероятная причина | Первый инструмент |
| :--- | :--- | :--- |
| ФС не монтируется, `dmesg` показывает "wrong fs type" или "superblock corrupted" | Повреждение суперблока или метаданных | `fsck` с резервным суперблоком |
| ФС монтируется, но файлы исчезли | Случайное удаление, rm, форматирование | `extundelete`, `debugfs`, `photorec` |
| `Read-only file system` при попытке записи | Автоматический переход ext4/XFS в RO | [Устранение неполадок: ФС в режиме read-only](./read_only_filesystem_troubleshooting.md) |
| `Input/output error` при чтении | Битые сектора, failing-диск | `ddrescue` для создания образа |
| Разделы не видны, диск отображается как неразмеченный | Повреждение таблицы разделов MBR/GPT | `testdisk`, `gdisk` |
| LVM: "device not found" или "VG not found" | Повреждение метаданных PV/VG | `pvck`, `vgcfgrestore` |
| RAID: `mdadm --detail` показывает degraded | Отказ одного или нескольких дисков | `mdadm --assemble --force` |

### Шаг 3. Выбор стратегии

1. **Файлы удалены, ФС монтируется:** Попробуйте `extundelete` (ext4) или `btrfs restore` (Btrfs).
2. **ФС не монтируется:** Используйте `fsck` на копии или `btrfs restore`/`xfs_db`.
3. **Метаданные уничтожены (форматирование):** Carving через `photorec`, `foremost` или `scalpel`.
4. **Диск физически поврежден:** `ddrescue` для создания образа, затем работа с образом.
5. **RAID/LVM сломан:** Сначала восстановите структуру массива/тома, затем применяйте ФС-инструменты.

## Практические сценарии

### 1. Восстановление файла, открытого процессом

Если файл был удалён из ФС (например, случайным `rm`), но процесс (база данных, логгер, веб-сервер) всё ещё удерживает его дескриптор.

**Шаги восстановления:**
1.  **Поиск PID и FD:**
    ```bash
    # Поиск процесса по имени файла или через lsof
    lsof +L1 | grep "deleted"
    # → nginx  1234  root  4r  REG  8,1  1024  45678 /var/log/nginx/access.log (deleted)
    ```
    Здесь `1234` — PID, `4` — номер дескриптора (FD).
2.  **Извлечение данных из /proc:**
    ```bash
    cp /proc/1234/fd/4 /mnt/recovery/access.log.restored
    ```

### 2. Восстановление разделов через TestDisk

**TestDisk** — стандарт для восстановления таблиц разделов (MBR/GPT) и исправления загрузочных секторов.

1.  Запуск: `sudo testdisk /dev/sdb`.
2.  Выбор `Analyse` → `Quick Search`.
3.  Если разделы найдены, используйте `P` для просмотра файлов и `C` для их копирования на другой диск перед записью новой таблицы разделов.

### 3. Файлоспецифичные инструменты

#### Ext4 (extundelete и debugfs)
`extundelete` автоматически анализирует журнал и пытается восстановить дерево каталогов.
```bash
# Восстановление всей директории
extundelete /dev/sdb1 --restore-directory /home/user/docs
```
`debugfs` позволяет вручную исследовать Inode:
```bash
debugfs -R "lsdel" /dev/sdb1  # Список недавно удаленных Inode
```

#### Btrfs (btrfs restore)
Позволяет копировать файлы с поврежденной ФС, которая не монтируется.
```bash
btrfs restore /dev/sdb1 /mnt/external_recovery
```

#### XFS (xfs_db)
В XFS нет надежного способа «отменить удаление» (undelete), но можно попытаться найти фрагменты данных через `xfs_db` в экспертном режиме.

### 4. Data Carving (PhotoRec, Foremost, Scalpel)

Если метаданные ФС полностью уничтожены (после форматирования), используются карверы.

- **PhotoRec:** Интерактивный и мощный, поддерживает сотни типов файлов.
  ```bash
  photorec /dev/sdb1
  ```
- **Foremost:** Консольная утилита от спецслужб США (OSI). Работает по конфигу сигнатур.
  ```bash
  foremost -i /dev/sdb1 -o /mnt/recovery/foremost
  ```
- **Scalpel:** Более производительный форк Foremost, оптимизированный для больших дисков.

### 5. Создание образов и восстановление с поврежденных носителей

Для работы с «умирающими» дисками (битые сектора) обычный `dd` не подходит, так как он зависает на ошибках. Подробное руководство по использованию `ddrescue` — в [Утилита dd — Использование ddrescue для восстановления данных](./dd.md#9-восстановление-данных-с-помощью-ddrescue).

- **GNU ddrescue:** Лучший инструмент для спасения данных. Он копирует сначала целые блоки, а затем пытается многократно вычитать поврежденные.
  ```bash
  # mapfile нужен для возобновления работы при прерывании
  ddrescue -d -r3 /dev/sdb /mnt/recovery/disk.img /mnt/recovery/rescue.log
  ```

### 6. Восстановление LV после случайного удаления (lvremove)

Если вы выполнили `lvremove`, данные на диске остаются целыми, пока экстенты не будут выделены под новый LV и затерты. **Чем меньше времени прошло — тем выше шанс на успех.**

**Шаг 1: Немедленно отмонтировать VG и не создавать новые LV**
```bash
sudo vgchange -an vg_data
```

**Шаг 2: Найти архив метаданных**
```bash
ls -lt /etc/lvm/archive/vg_data_*.vg | head -5
# → Найдите архив, созданный до lvremove
```

**Шаг 3: Восстановить LV из архива**
```bash
sudo lvcreate --name lv_data_restored --size 50G vg_data
sudo dd if=/dev/vg_data/lv_data_restored of=/mnt/recovery/lv_data.img bs=4M
```

**Шаг 4: Если архив недоступен**, используйте `pvscan` и `vgcfgrestore` для восстановления структуры VG, затем попробуйте собрать LV вручную через `lvcreate --restorefile`.

Подробнее — в [LVM: Практические сценарии восстановления](../FileSystems/LVM/advanced_topics/practical_scenarios.md).

### 7. Анализ и восстановление RAID-массива (mdadm)

При отказе диска в RAID 1/5/6 массив переходит в деградированное состояние. Данные остаются доступны через оставшиеся диски.

**Шаг 1: Диагностика состояния**
```bash
cat /proc/mdstat
# → md0 : active raid1 sda1[0] sdb1[1]
# →      976762944 blocks [2/2] [UU]

# Детальная информация
sudo mdadm --detail /dev/md0
```

**Шаг 2: Замена вышедшего диска**
```bash
# Копирование суперблока на новый диск
sudo mdadm --add /dev/md0 /dev/sdc1

# Наблюдение за ресинхронизацией
watch cat /proc/mdstat
# → [=======>.....]  recovery = 45.2%
```

**Шаг 3: Если массив не собирается автоматически**
```bash
# Принудительная сборка
sudo mdadm --assemble --force /dev/md0 /dev/sda1 /dev/sdb1

# Если метаданные повреждены, восстановить из суперблока
sudo mdadm --examine --scan > /etc/mdadm.conf
sudo update-initramfs -u
```

**Важно:** RAID защищает от отказа диска, но не от случайного удаления файлов внутри смонтированного массива. В этом случае работайте как с обычной ФС.

### 8. Восстановление после автоматического перехода ext4 в RO

Когда `ext4` сам переводится в `read-only`, данные не повреждены, но запись блокирована.

**Шаг 1: Определить RO-точку**
```bash
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
# → /dev/mapper/ubuntu--vg-root ext4 ro,relatime
```

**Шаг 2: Диагностика причины**
```bash
# Проверить SMART-статус диска
sudo smartctl -a /dev/sda | grep -E 'Reallocated|Pending|Error'

# Проверить dmesg на I/O ошибки
sudo dmesg | grep -iE 'ext4.*error|blk_update|ata.*error|buffer i/o'
```

**Шаг 3: Попытка перемонтировать в RW**
```bash
sudo mount -o remount,rw /dev/mapper/ubuntu--vg-root /
# → если успешно — проблема временная (например, сбой записи)
```

**Шаг 4: Если RW не работает**
```bash
# Загрузитесь с Live CD/USB
# Смонтируйте корень в RO
sudo mount -o ro /dev/sda2 /mnt/recovery

# Скопируйте критические данные
sudo rsync -av /mnt/recovery/home/ /mnt/external/home_backup/
```

Подробнее о механизме перехода в RO — в [Устранение неполадок: ФС в режиме read-only](./read_only_filesystem_troubleshooting.md).

### 9. Forensic-анализ с dc3dd и верификация хешей

Для юридически значимого восстановления (forensic) требуется сохранить целостность доказательств (chain of custody).

**Шаг 1: СозданиеForensic-образа с dc3dd**
```bash
# Установка (Debian/Ubuntu)
sudo apt install dc3dd

# Создание образа с хешированием
sudo dc3dd if=/dev/sdb of=/mnt/evidence/sdb.img hash=md5,sha256 log=/mnt/evidence/dc3dd.log

# Проверка хеша образа
md5sum /mnt/evidence/sdb.img
# → сравнивается с записью в dc3dd.log
```

**Шаг 2: Работа с образом**
```bash
# Монтирование образа в RO
sudo mount -o ro,loop /mnt/evidence/sdb.img /mnt/forensics

# Анализ файлов
find /mnt/forensics -type f -name "*.docx" -o -name "*.xlsx" | head -20
```

**Шаг 3: Carving с верификацией**
```bash
# PhotoRec с логом для отчётности
sudo photorec /dev/sdb -d /mnt/evidence/photorec_output -log

# Или foremost с конфигом
foremost -t all -i /mnt/evidence/sdb.img -o /mnt/evidence/foremost_output
```

### 10. Автоматизация первичной диагностики (сценарий для SRE)

При инциденте с потерей данных SRE должен быстро оценить ситуацию. Ниже приведён скрипт первичной диагностики:

```bash
#!/bin/bash
# recover-diagnose.sh — базовая диагностика перед восстановлением
# Использование: sudo ./recover-diagnose.sh /dev/sdb1

DEVICE="${1:?Укажите устройство}"
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
REPORT="/tmp/recover_diagnose_${TIMESTAMP}.txt"

echo "=== Диагностика устройства $DEVICE ===" > "$REPORT"
echo "Дата: $(date)" >> "$REPORT"

echo -e "\n--- SMART ---" >> "$REPORT"
sudo smartctl -a "$DEVICE" | grep -E 'Reallocated|Pending|Error' >> "$REPORT" 2>&1

echo -e "\n--- Точки монтирования ---" >> "$REPORT"
findmnt -rn "$DEVICE" >> "$REPORT" 2>&1

echo -e "\n--- Журнал ядра (последние 20 строк) ---" >> "$REPORT"
sudo dmesg | tail -20 | grep -iE "$(basename $DEVICE)|error|fail" >> "$REPORT" 2>&1

echo -e "\n--- Тип ФС ---" >> "$REPORT"
blkid -o value -s TYPE "$DEVICE" >> "$REPORT" 2>&1

echo -e "\n--- Суперблок (ext4) ---" >> "$REPORT"
sudo dumpe2fs -h "$DEVICE" 2>/dev/null | grep -E 'Filesystem state|Block count|Inode count' >> "$REPORT"

echo -e "\nОтчёт сохранён в $REPORT"
cat "$REPORT"
```

### 11. Восстановление XFS после сбоя

XFS не поддерживает undelete, но данные можно извлечь двумя способами:

**Способ А: xfs_db (экспертный режим)**
```bash
# Запуск в экспертном режиме
sudo xfs_db -r -c "sb 0" -c "p" -c "quit" /dev/sdb1
# → проверьте флаг 'state' и 'uuid'

# Поиск недавних inode (экспериментально)
sudo xfs_db -r -c "inode <addr>" -c "p" -c "quit" /dev/sdb1
```

**Способ Б: xfs_metadump**
```bash
# Дамп метаданных для offline-анализа
sudo xfs_metadump /dev/sdb1 /mnt/recovery/xfs_meta.dump

# Анализ дампа
sudo xfs_mdrestore /mnt/recovery/xfs_meta.dump /mnt/recovery/xfs_restore.img
```

### 12. Работа с образами: извлечение разделов и файлов

После создания образа (`ddrescue`, `dc3dd`) работайте только с образом:

**Монтирование конкретного раздела через loop с offset:**
```bash
# Определение offset раздела через fdisk/gdisk
sudo fdisk -l /mnt/recovery/disk.img
# → Device         Boot Start       End   Sectors  Size Id Type
# → /mnt/recovery/disk.img1       2048 1026047  1024000  500M 83 Linux

# Offset = Start * SectorSize (обычно 512)
OFFSET=$((2048 * 512))

# Монтирование
sudo mount -o ro,loop,offset=$OFFSET /mnt/recovery/disk.img /mnt/restore
```

**Извлечение файлов из RAW-образа:**
```bash
# Если ФС неизвестна или повреждена — carving
sudo photorec /mnt/recovery/disk.img

# Если ФС читается — прямое монтирование
sudo mount -o ro,loop /mnt/recovery/disk.img /mnt/restore
```

## Типичные ошибки и диагностика

| Проблема | Причина и решение |
| :--- | :--- |
| **"No space left on device" при монтировании** | Разреженный файл исчерпал место на хостовой ФС. Проверьте `df -h .` в директории с образом. Увеличьте файл через `truncate` или переместите его на диск с большим свободным местом. |
| **Высокое потребление RAM при работе с образами** | Двойное кэширование (page cache хоста + внутренний кэш ФС). Используйте `--direct-io=on` и/или `mount -o sync,dirsync`. |
| **"Device is busy" при losetup -d** | Устройство смонтировано или используется процессом. Найдите процесс: `sudo fuser -v /dev/loop0` или `lsof /dev/loop0`. Сначала размонтируйте (`umount`), затем удалите устройство. |
| **Ошибка "loop: I/O error" в dmesg** | Файл-образ удален или поврежден. Проверьте `ls -l /proc/$(pgrep -f loop)/fd` для поиска дескриптора. Если файл удален — восстановите из бэкапа или удалите устройство. |
| **Низкая производительность на NVMe хосте** | Отсутствует `--direct-io` или `--sector-size=4096`. Включите оба параметра. Также проверьте, что планировщик I/O на loop-устройстве не `mq-deadline` — для NVMe используйте `none`. |
| **Loop-устройства не создаются (нет /dev/loop-control)** | Модуль `loop` не загружен: `sudo modprobe loop`. В очень старых системах может потребоваться `modprobe max_loop=64`. |
| **Sparse файл внезапно занял много места** | ФС внутри образа записала данные в ранее "дырявые" блоки. Разреженные файлы скрывают реальное потребление места. Используйте `du --apparent-size` для логического размера и `du` для реального. |
| **extundelete возвращает "No undeleted inodes found"** | Журнал перезаписан или ФС монтировалась с опцией `data=writeback`. Восстановление через journal невозможно. Попробуйте carving (`photorec`) или создайте образ для offline-анализа. |
| **ddrescue зависает на одном секторе** | Устройство имеет "粘性" bad sector. Увеличьте `--max-read-rate` или используйте `--skip-pass` с ограничением скорости. |
| **Файлы recovered повреждены (0 байт или обрезка)** | Блоки данных были перезаписаны или файл фрагментирован и частично потерян. Проверьте `lost+found` на наличие фрагментов. |
| **btrfs restore пропускает файлы** | Используйте `--path-separators` и `--root` для указания правильного корня snapshot'а. Проверьте контрольные суммы: `btrfs check --readonly`. |
| **xfs_repair требует больше места, чем размер ФС** | XFS repair использует временные файлы в 2–3 раза больше размера ФС. Убедитесь, что на внешнем диске достаточно места, или работайте с образом. |
| **"Input/output error" при чтении образа** | Источник поврежден. Используйте `ddrescue` с тремя проходами: сначала быстрый пропуск битых блоков (`-n`), затем многопроходное чтение (`-r3`). |

## Лучшие практики

### 1. Производительность

- **Всегда используйте `--direct-io=on`** для production-образов объемом >1 ГБ. Это устраняет двойное кэширование.
- **Устанавливайте `--sector-size=4096`** на всех современных дисках (4K Native) и виртуальных машинах. На хостах с 512e дисками можно оставить значение по умолчанию.
- **Для I/O-интенсивных задач** (базы данных, компиляция) используйте `mount -o sync,dirsync` или `O_DIRECT` через `fio`, чтобы обойти page cache хоста полностью.
- **Не монтируйте** образы, к которым нужен только случайный доступ, через `mount -o loop`. Используйте `fuseiso` или монтируйте через `losetup` с отдельным управлением.

### 2. Надежность

- **Используйте `losetup -r`** для всех эталонных/распространяемых образов, чтобы предотвратить случайное изменение.
- **Проверяйте образ перед использованием:** `fsck -n` или `virt-cat`/`guestfish` для виртуальных машин.
- **Делайте бэкапы суперблока** перед изменениями: `sudo dd if=/dev/sda1 of=superblock_backup.bin bs=1M count=1`.
- **Не удаляйте файл-образа**, пока устройство привязано. `AUTOCLEAR` защищает только при `mount -o loop`, но не при ручном `losetup`.

### 3. Мониторинг

- **Отслеживайте привязки:** Добавьте `losetup -a` в мониторинг (Prometheus node exporter, Zabbix) для обнаружения утечек устройств.
- **Логируйте dmesg** на предмет ошибок `loop:`. В production это может указывать на повреждение образа или нехватку места.
- **Следите за `/proc/meminfo`** — если `Dirty` растет без записи на диск при работе с loop-образами, проверьте, не отключен ли writeback.

### 4. Безопасность

- **Ограничивайте права доступа** к файлам-образам: `chmod 600 disk.img`. Это предотвращает чтение данных другими пользователями.
- **Используйте `ro`** для неизменяемых артефактов (ISO, эталонные образы).
- **При работе с конфиденциальными данными** используйте LUKS поверх loop: `cryptsetup luksFormat /dev/loop0`, затем монтируйте расшифрованный mapper-устройство.
- **В контейнерах** запросите только необходимые capabilities (`SYS_ADMIN`, `BLOCK_DEVICE`). Не используйте `--privileged` без необходимости.
