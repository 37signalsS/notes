# Типы файлов в Linux

## Определения

- **Тип файла:** Свойство объекта в файловой системе, определяющее его внутреннюю структуру, назначение и набор допустимых системных вызовов для работы с ним.
- **Всё есть файл (Everything is a file):** Фундаментальная концепция архитектуры Unix/Linux, при которой доступ к аппаратным ресурсам (диски, клавиатуры), потокам данных (pipe) и системным интерфейсам (сокеты) осуществляется через унифицированный интерфейс файловых дескрипторов и стандартные системные вызовы (`open`, `read`, `write`, `close`).
- **st_mode:** Поле в структуре `stat` (и в Inode), которое содержит информацию о типе файла и правах доступа в виде битовой маски.

## Основные концепции

В Linux существует 7 стандартных типов файлов, определенных стандартом POSIX. Тип файла является статическим свойством и записывается в Inode в момент создания объекта.

### Классификация типов файлов

| Символ | Тип файла | Системная константа | Описание |
| :---: | :--- | :--- | :--- |
| **`-`** | **Обычный файл** | `S_IFREG` | Последовательность байтов. Данные хранятся в блоках данных ФС. Сюда относятся тексты, бинарные файлы (ELF), архивы. |
| **`d`** | **Каталог** | `S_IFDIR` | Список имен файлов и соответствующих им номеров Inode. В современных ФС (ext4, XFS) реализован как B-дерево или хеш-таблица. |
| **`l`** | **Символическая ссылка** | `S_IFLNK` | Содержит путь к другому объекту. Может указывать на файл, каталог или даже на несуществующий объект. |
| **`b`** | **Блочное устройство** | `S_IFBLK` | Интерфейс к оборудованию с произвольным доступом (диски). Данные передаются блоками фиксированного размера через Buffer Cache. |
| **`c`** | **Символьное устройство** | `S_IFCHR` | Интерфейс к оборудованию с последовательным доступом (терминалы, `/dev/null`). Данные передаются байт за байтом. |
| **`p`** | **Именованный канал (FIFO)** | `S_IFIFO` | Очередь для межпроцессного взаимодействия (IPC). Данные передаются через буфер в памяти ядра, не записываясь на диск. |
| **`s`** | **Сокет** | `S_IFSOCK` | Конечная точка для двунаправленной передачи данных между процессами (локально или по сети). |

### Низкоуровневая реализация (st_mode)

Тип файла кодируется в старших 4 битах (12-15) 16-битного поля `st_mode`. Для извлечения типа используется битовая маска `S_IFMT` (0170000 в восьмеричной системе).

| Константа (C) | Восьмеричное значение | Описание |
| :--- | :--- | :--- |
| `S_IFREG` | `0100000` | Обычный файл |
| `S_IFDIR` | `0040000` | Каталог |
| `S_IFLNK` | `0120000` | Символическая ссылка |
| `S_IFBLK` | `0060000` | Блочное устройство |
| `S_IFCHR` | `0020000` | Символьное устройство |
| `S_IFIFO` | `0010000` | FIFO (Named Pipe) |
| `S_IFSOCK` | `0140000` | Сокет |

Для проверки типа в программировании на C используются макросы, например `S_ISREG(m)`, которые выполняют операцию `(m & S_IFMT) == S_IFREG`.

### Взаимодействие с Inode и структурой данных

1.  **Обычные файлы:** Inode содержит указатели на блоки данных на диске. В современных ФС (ext4) используются экстенты (extents) для оптимизации хранения больших файлов.
2.  **Каталоги:** Это файлы со специальным флагом. Ядро интерпретирует их содержимое как список структур `dirent` (имя файла + номер Inode).
3.  **Символические ссылки:**
    *   **Fast Symlinks:** Если путь короткий (обычно < 60 байт), он хранится прямо в Inode (в поле, где обычно хранятся указатели на блоки), что экономит дисковые операции.
    *   **Slow Symlinks:** Если путь длинный, он записывается в отдельный блок данных.
4.  **Устройства (b, c):** Inode не содержит указателей на блоки данных. Вместо этого в полях `i_rdev` хранятся **Major** (идентификатор драйвера) и **Minor** (номер конкретного устройства) номера.
5.  **FIFO и Сокеты:** Inode служит лишь точкой входа (anchor) в файловой системе. Реальные данные передаются через структуры в оперативной памяти ядра.

### Специальные файловые системы и типы файлов

Псевдофайловые системы (procfs, sysfs, devtmpfs, tmpfs) генерируют файлы стандартных типов (`S_IFREG`, `S_IFDIR`, `S_IFLNK`, `S_IFCHR`), но их содержимое создается ядром динамически. Например:
- **`/proc`** — каталоги процессов (`S_IFDIR`), файлы статуса (`S_IFREG`), символические ссылки на текущий процесс (`/proc/self` → `S_IFLNK`).
- **`/sys`** — иерархия устройств и драйверов, где атрибуты (`uevent`, `modalias`) представлены обычными файлами (`S_IFREG`).
- **`/dev`** (devtmpfs) — узлы устройств (`S_IFBLK`/`S_IFCHR`), создаваемые автоматически при регистрации драйвера.
- **`sockfs`** — внутренняя ФС для сокетов (`S_IFSOCK`), невидимая в обычном дереве каталогов.
- **`pipefs`** — внутренняя ФС для именованных каналов (`S_IFIFO`).

Это означает, что команды `ls -l` и `find` корректно определяют типы файлов в `/proc`, `/sys` и `/dev`, но операции чтения/записи идут напрямую в память ядра, а не на диск.

### Расширенные атрибуты (xattr) и типы файлов

Расширенные атрибуты (xattr) — это пара «имя → значение», прикрепленная к Inode поверх стандартных прав и метаданных. xattr доступны для большинства типов файлов, но с ограничениями:
- **Обычные файлы и каталоги:** Поддержка повсеместная (ext4, XFS, Btrfs).
- **Символические ссылки:** В Linux xattr для symlink поддерживаются начиная с ядра 4.5, но утилиты часто игнорируют их.
- **Устройства, FIFO, Сокеты:** Поддержка зависит от реализации ФС; часто не используются.

xattr критичны для ACL (расширенных списков контроля доступа) и меток безопасности (SELinux, Smack). Проверка: `getfattr -d /path/to/file`.

### Специальные права и типы файлов (Sticky Bit, setuid/setgid)

Некоторые комбинации типа файла и специальных битов имеют критическое значение для безопасности и эксплуатации:
- **Sticky Bit на каталоге (`S_ISVTX`):** Позволяет удалять файлы из каталога только их владельцу, даже если права каталога `777`. Классический пример — `/tmp`. Проверка: `ls -ld /tmp` (`t` в позиции `others`).
- **setuid/setgid на обычных файлах:** При исполнении файл получает права владельца/группы. На устройствых файлах (`/dev/kmsg`, `/dev/mem`) setuid имеет смысл только для программ, явно требующих прямой доступ к оборудованию.
- **Named Pipe в cron/systemd:** FIFO-файлы используются для обмена данными между сервисами без диска. Важно проверять права доступа (`chmod 660`) для ограничения доступа.

## Практические сценарии

### Идентификация и диагностика

1.  **Команда `ls -l`**: Первый символ строки разрешений (например, `drwxr-xr-x` → каталог). Подробнее о формате вывода: [Команда ls](../Shell/ls.md).
2.  **Команда `stat`**: Показывает тип в текстовом виде и восьмеричный код `st_mode`.
    ```bash
    stat /dev/sda
    # → Device type: 8,0 (Major 8, Minor 0)
    # → Inode: 429 (Block special file)
    ```
3.  **Команда `file`**: Анализирует содержимое файла (Magic Numbers), что позволяет отличить JPEG от ELF внутри типа «Обычный файл».

### Поиск файлов по типу

Утилита `find` использует флаг `-type`:

```bash
# Найти все символические ссылки в /etc
sudo find /etc -type l

# Найти все сокеты в системе
sudo find / -type s 2>/dev/null

# Найти все блочные устройства (диски)
find /dev -type b
```

### Создание объектов различных типов

| Тип | Команда | Пример |
| :--- | :--- | :--- |
| **Обычный файл** | `touch`, `truncate` | `touch file.txt` |
| **Каталог** | `mkdir` | `mkdir my_dir` |
| **Символическая ссылка** | `ln -s` | `ln -s /etc/passwd link_to_pass` |
| **Жесткая ссылка** | `ln` | `ln existing_file hard_link` (Тип остается тем же) |
| **FIFO** | `mkfifo` | `mkfifo /tmp/my_pipe` |
| **Устройство** | `mknod` | `sudo mknod /dev/my_device c 10 200` (Требует root) |

### Аудит и безопасность

#### Поиск всех файлов устройств

Блочные и символьные устройства в неожиданных местах могут указывать на несанкционированное оборудование или контейнеры с повышенными привилегиями:

```bash
# Найти все блочные устройства вне /dev
sudo find / -path /proc -prune -o -path /sys -prune -o -type b -print

# Найти все символьные устройства вне /dev
sudo find / -path /proc -prune -o -path /sys -prune -o -type c -print
```

#### Поиск открытых сокетов и FIFO

Для диагностики зависших сервисов или утечек ресурсов:

```bash
# Все Unix-сокеты в /run (systemd, Docker, PostgreSQL)
sudo find /run -type s -ls

# FIFO, созданные более 7 дней назад
sudo find /tmp -type p -mtime +7 -ls
```

#### Проверка бинарных файлов на setuid/setgid

Файлы с setuid-битом на обычных исполняемых файлах требуют отдельного аудита:

```bash
# Найти все setuid-файлы
sudo find / -type f -perm -4000 -print 2>/dev/null

# Аудит SUID+SGID разом (любой из битов 6000)
sudo find / -perm /6000 -type f -ls 2>/dev/null

# Проверить, является ли файл ELF (не устройство)
file /usr/bin/sudo
# → /usr/bin/sudo: ELF 64-bit LSB executable
```

### Резервное копирование с учетом типов файлов

Разные типы файлов требуют разных стратегий резервного копирования:

```bash
# tar: по умолчанию сохраняет все типы, но для устройств создаёт sparse-файлы
tar -cvpf backup.tar /dev/sdb
# → /dev/sdb: character special (11, 0) — sparse-запись, не данные диска

# Для корректного копирования устройств используйте dd
sudo dd if=/dev/sda of=/backup/sda.img bs=4M status=progress

# rsync с сохранением всех типов (жесткие ссылки, права, xattr, ACL)
sudo rsync -aAXHv /data/ /backup/data/
```

### Поиск и очистка устаревших объектов

#### Устаревшие сокеты systemd и Docker

После аварийного завершения сервиса сокеты могут оставаться в `/run`:

```bash
# Найти сокеты, к которым нет открытых дескрипторов
sudo lsof +L1 | grep sock | awk '{print $9}' | sort -u

# Удалить только после остановки соответствующего сервиса
sudo systemctl stop myapp
sudo rm -f /run/myapp/socket
```

#### Устаревшие FIFO в /tmp

FIFO-файлы, оставшиеся после падения процесса, блокируют запись:

```bash
# Найти FIFO, не модифицированные более 30 дней
sudo find /tmp -type p -mtime +30 -delete

# Проверить, что процессы не зависли на записи
sudo lsof | grep FIFO
```

### Работа в контейнерах

Контейнеры имеют ограниченный набор файловых типов:
- **Устройства (`b`, `c`):** Отсутствуют по умолчанию. Для доступа требуется `--privileged`, `--device`, или явное создание через `mknod` в privileged-контейнере.
- **Сокеты:** Доступны, но `/proc/net` может быть ограничен namespace.
- **FIFO:** Полностью поддерживаются, но не пересекают границы контейнера.
- **Символические ссылки:** Поддерживаются, но при монтировании томов symlink-разрешение выполняется в контексте контейнера.

Проверка доступных типов внутри контейнера:

```bash
# Внутри контейнера (не privileged)
ls -l /dev
# → /dev/null, /dev/zero, /dev/random ... (виртуальные устройства)
# → Нет /dev/sda, /dev/tty

# Проверка, что /proc — это pсевдо-ФС
stat -f -c %T /proc
# → proc (не tmpfs, ext4 и т.д.)
```

### Специальные случаи имен файлов и удаления

#### Файлы с именами, начинающимися с дефиса (`-`)

Имена вроде `-f`, `--help` корректны в Linux, но интерпретируются утилитами как флаги:

```bash
# Ошибка: rm пытается разобрать -f как флаг
rm -f
# → rm: invalid option -- 'f'

# Правильно: явное указание конца опций или полный путь
rm -- -f
rm ./-f
```

#### Файлы с управляющими символами в именах

Имена могут содержать непечатные символы (Ctrl+A..Ctrl+Z, DEL и др.), которые невозможно набрать с клавиатуры:

```bash
# Пример: файл с именем "foo^Dbar" (Ctrl+D внутри)
ls
# → foo?bar      (ls заменяет управляющий символ на ?)

# ls -B показывает восьмеричные коды управляющих символов
ls -B
# → foo\004bar   (Ctrl+D = 004 в восьмеричной)

# Безопасное удаление: интерактивный режим или визуальные менеджеры
rm -i *
# → remove foo?bar? y/n

# Альтернатива: визуальные файловые менеджеры (Nautilus, Emacs dired, Midnight Commander)
# не боятся таких имён и позволяют удалить их через GUI/TUI.
```

#### Рекомендации
- Используйте `rm --` или `rm ./-name` для файлов, начинающихся с `-`.
- Для имён с управляющими символами: `rm -i *` (пофайловый запрос) или визуальные менеджеры.
- `ls -B` помогает диагностировать невидимые символы в именах.

## Устранение неполадок

-   **«Битые» ссылки (Dangling Links):** Символическая ссылка указывает на путь, которого не существует. Команда `ls` часто подсвечивает их красным. Проверка: `test -e link_name || echo "Broken"`.
-   **Ошибки типов в Docker:** Контейнеры по умолчанию не имеют доступа к блочным устройствам хоста. Для работы с ними (например, для мониторинга SMART) требуется флаг `--privileged` или явный проброс через `--device`.
-   **Лимит Inode:** Если в системе много мелких файлов (особенно типов `s` или `p`), могут закончиться Inode, даже если на диске есть свободное место. Проверка: `df -i`.
-   **Конфликт типов при монтировании:** Файл уже существует и является обычным файлом (`S_IFREG`), а монтирование требует каталог (`S_IFDIR`). Ошибка: `mount: wrong fs type, bad option, bad superblock`. Решение: удалить или переименовать файл.
-   **SELinux и типы файлов:** SELinux assigns security contexts to files based on type. После копирования файлов (`cp`) контекст может сбрасываться в `default_t`, что приводит к отказам в доступе. Проверка: `ls -Z`. Исправление: `restorecon -Rv /path`.
-   **Потеря привилегий при chroot:** В chroot-окружении файлы устройств (`/dev/null`, `/dev/zero`) должны существовать как реальные узлы (или через `bind`-монтирование devtmpfs), иначе приложения получают `ENOENT`.
-   **Зависшие процессы на FIFO:** Если читатель FIFO завершается, а писатель продолжает работать, писатель получает `SIGPIPE` и завершается. Если читатель активен, а писатель завис, `read()` блокируется. Диагностика: `lsof | grep FIFO`.
