# Файловые дескрипторы

## Определения

- **Файловый дескриптор (File Descriptor, FD):** Неотрицательное целое число, которое ядро Linux использует в качестве абстрактного указателя для идентификации открытого файла или ресурса ввода-вывода (I/O). С точки зрения программиста — это индекс в массиве открытых ресурсов процесса.
- **Описание открытого файла (Open File Description):** Системная структура данных (внутри ядра), на которую ссылается дескриптор. Она содержит состояние: текущее смещение (offset), флаги состояния (status flags) и счетчик ссылок.
- **Стандартные потоки (Standard Streams):** Три предопределенных дескриптора (`0`, `1`, `2`), которые автоматически открываются ядром для каждого нового процесса.
- **Таблица дескрипторов процесса (Process FD Table):** Локальная для каждого процесса структура, содержащая указатели на записи в общесистемной таблице открытых файлов. При `fork()` копируется полностью.
- **Общесистемная таблица открытых файлов (Open File Table):** Содержит Open File Descriptions. При `dup()`/`fork()` новые дескрипторы указывают на ту же запись, что и исходный.
- **Таблица Inode (Inode Table):** Хранит метаданные самого файла на диске (права, размер, физические блоки). Разные Open File Descriptions могут указывать на один и тот же inode.

## Основные концепции

### Стандартные потоки ввода-вывода

При запуске процесса ядро резервирует первые три записи в его таблице дескрипторов:

| FD | Название | Системный макрос | Описание |
| :--- | :--- | :--- | :--- |
| **0** | **stdin** | `STDIN_FILENO` | Стандартный ввод (по умолчанию — клавиатура). |
| **1** | **stdout** | `STDOUT_FILENO` | Стандартный вывод (по умолчанию — экран терминала). |
| **2** | **stderr** | `STDERR_FILENO` | Стандартный вывод ошибок (по умолчанию — экран терминала). |

Подробнее о работе с потоками в командной оболочке см. в разделе **[Перенаправление ввода-вывода в Bash](../Shell/io_redirection.md)** (включает экзаменационные сценарии LPIC-1 103.2).

### Трехуровневая архитектура ядра

В Linux реализована многослойная абстракция для управления ресурсами, что позволяет разным дескрипторам разделять состояние файла:

1.  **Таблица дескрипторов процесса (Process Descriptor Table):**
    - Локальна для каждого процесса.
    - Содержит записи, указывающие на записи в общесистемной таблице открытых файлов.
    - Флаг `FD_CLOEXEC` хранится именно здесь (на уровне дескриптора).
2.  **Общесистемная таблица открытых файлов (Open File Table):**
    - Содержит «Описания открытых файлов» (Open File Descriptions).
    - Хранит **текущую позицию (offset)**, флаги доступа (чтение/запись, `O_APPEND`, `O_NONBLOCK`) и счетчик ссылок.
    - При вызове `fork()` или `dup()` создаются новые дескрипторы, указывающие на **ту же самую** запись в этой таблице. Это причина, по которой родитель и потомок разделяют общее смещение в файле.
3.  **Таблица Inode (Inode Table):**
    - Хранит метаданные самого файла на диске (права, размер, физические блоки).
    - Разные записи в Open File Table (созданные через независимые вызовы `open()`) могут указывать на один и тот же Inode, но иметь разные смещения.

Подробнее о структуре метаданных см. в материале **[Ссылки, Inode и Dentry](./links_inodes_dentries.md)**.

### Системные вызовы создания дескрипторов

Ядро предоставляет несколько семейств системных вызовов для создания FD:

| Системный вызов | Ресурс | Пример использования |
| :--- | :--- | :--- |
| `open()` / `openat()` | Обычные файлы, директории | Открытие конфига, лога, FIFO |
| `socket()` | Сетевые сокеты (TCP/UDP/Unix) | Создание слушающего или клиентского сокета |
| `pipe()` / `pipe2()` | Анонимные каналы (IPC) | Канал между родителем и потомком |
| `socketpair()` | Пары связанных Unix-сокетов | Двусторонний канал для IPC |
| `accept()` / `accept4()` | Принятие входящего TCP-соединения | Возвращает новый FD для клиента |
| `epoll_create()` / `epoll_create1()` | Инстанс epoll | Мультиплексирование тысяч FD |
| `timerfd_create()` | Таймеры как FD | Интеграция таймеров в событийные циклы |
| `eventfd()` | Счетчик событий | Межпроцессное взаимодействие |
| `signalfd()` | Сигналы как данные | Чтение сигналов через `read()` |
| `memfd_create()` | Анонимный файл в RAM | Файл, не привязанный к ФС |
| `pidfd_open()` | Стабильный идентификатор процесса | Исключает риск переиспользования PID |

**Важность флага `O_CLOEXEC`:** Все современные системные вызовы поддерживают флаг `O_CLOEXEC` (Close-on-exec). Он указывает ядру автоматически закрыть дескриптор при выполнении `exec()`. Это критично для безопасности: без него дочерний процесс может получить доступ к открытому файлу паролей или сокету родителя.

### Дублирование дескрипторов: dup, dup2, dup3

Системные вызовы `dup()`/`dup2()`/`dup3()` создают новый дескриптор, указывающий на ту же Open File Description:

```bash
# В C: дублирование stdout в файл
int fd = open("log.txt", O_WRONLY | O_CREAT | O_APPEND, 0644);
dup2(fd, STDOUT_FILENO);  # stdout теперь пишет в log.txt
```

**Практическое значение для SRE:**
- Перенаправление стандартных потоков в демонах
- Обмен FD между родителем и потомком через неименованные каналы
- Восстановление стандартных потоков после временного перенаправления

### fcntl: управление флагами и блокировками

`fcntl()` (file control) — универсальный инструмент для управления FD:

| Команда | Назначение | Пример |
| :--- | :--- | :--- |
| `F_DUPFD` | Дублировать дескриптор | `fcntl(fd, F_DUPFD, 0)` |
| `F_SETFD` | Установить флаги дескриптора | `FD_CLOEXEC` |
| `F_SETFL` | Установить флаги состояния файла | `O_NONBLOCK`, `O_APPEND` |
| `F_GETLK` / `F_SETLK` | POSIX-блокировки (fcntl) | Блокировка диапазона байтов |
| `F_SETOWN` | Установить владельца для сигналов | Для `SIGIO` на сокетах |

** advisory vs mandatory блокировки:**
- `flock()` — advisory-блокировка на уровне всего файла. Процессы добровольно проверяют блокировку.
- `fcntl()` — advisory-блокировка на уровне диапазонов байтов. Более гранулярная.
- Mandatory locking устарел и редко используется.

### Наследование и флаги дескрипторов

Поведение дескрипторов при системных вызовах критично для безопасности и производительности:

-   **fork():** Потомок получает полную копию таблицы дескрипторов родителя. Дескрипторы указывают на те же Open File Descriptions.
-   **exec():** По умолчанию дескрипторы остаются открытыми в новой программе. Это может привести к утечке данных (например, если дочерний процесс получит доступ к открытому файлу паролей).
-   **O_CLOEXEC (Close-on-exec):** Флаг, указывающий ядру автоматически закрыть дескриптор при выполнении `exec()`. Рекомендуется использовать по умолчанию для всех открываемых файлов в многопоточных приложениях.
-   **O_NONBLOCK:** Переводит работу с дескриптором в неблокирующий режим. Если данных нет, `read()` вернет ошибку `EAGAIN` вместо ожидания.

### Концепция «Всё есть файл»

Благодаря абстракции FD, ядро предоставляет унифицированный интерфейс (`read`, `write`, `close`, `select/poll/epoll`) для работы с разнородными ресурсами:

-   **Обычные файлы и каталоги.**
-   **Сетевые сокеты:** TCP, UDP, Unix Domain Sockets.
-   **Каналы (Pipes):** Анонимные и именованные (`fifo`).
-   **Специальные дескрипторы уведомлений:**
    -   `eventfd`: Легковесный счетчик для межпроцессного взаимодействия.
    -   `signalfd`: Чтение сигналов как данных из файла.
    -   `timerfd`: Таймеры, интегрируемые в событийные циклы.
-   **Дескрипторы управления:** `epoll` инстансы, **[io_uring](../Core/kernel/io_uring.md)**.
-   **Анонимная память:** `memfd_create` (файл в RAM, не привязанный к ФС).
-   **Управление процессами:** `pidfd` (стабильный идентификатор процесса, исключающий риск переиспользования PID).

### Передача дескрипторов между процессами

Linux позволяет передавать FD между процессами через Unix Domain Sockets с использованием `SCM_RIGHTS`:

```c
struct msghdr msg = {0};
struct cmsghdr *cmsg;
char buf[CMSG_SPACE(sizeof(int))] = {0};

msg.msg_control = buf;
msg.msg_controllen = sizeof(buf);
cmsg = CMSG_FIRSTHDR(&msg);
cmsg->cmsg_level = SOL_SOCKET;
cmsg->cmsg_type = SCM_RIGHTS;
cmsg->cmsg_len = CMSG_LEN(sizeof(int));
*((int *) CMSG_DATA(cmsg)) = fd_to_send;
```

Этот механизм используется в:
- Systemd для управления сервисами (socket activation)
- Контейнерах (runtime передает сокеты приложениям)
- Мультиплексорах (nginx master → worker)

### Лимиты дескрипторов

Для защиты системы от «прожорливых» или некорректных приложений установлены ограничения:

1.  **Soft Limit (Мягкий лимит):** Текущее ограничение процесса. Процесс может сам увеличить его до Hard Limit через `setrlimit()`.
2.  **Hard Limit (Жесткий лимит):** Потолок, который может повысить только `root` (или процесс с `CAP_SYS_RESOURCE`).
3.  **System-wide Limit (`fs.file-max`):** Общий лимит открытых файлов для всего ядра.
4.  **fs.nr_open:** Максимальное значение, которое может принять `ulimit -n`.
5.  **cgroup pids.max:** В systemd-сервисах дополнительный лимит через `TasksMax=`.

Превышение лимита приводит к ошибке `Too many open files` (`EMFILE` — лимит процесса, `ENFILE` — лимит системы).

**Иерархия применения лимитов (от наиболее строгого к наименее строгому):**

```
Глобальные лимиты ядра (sysctl)        ← Приоритет 1
  ↓
Контрольные группы (cgroups)            ← Приоритет 2
  ↓
Системные сервисы (systemd)             ← Приоритет 3
  ↓
PAM / limits.conf (пользователи)        ← Приоритет 4
  ↓
ulimit / prlimit (текущая сессия/pid)   ← Приоритет 5
```

Подробнее о лимитах ресурсов см. в **[Концепции лимитов ресурсов](../Core/processes/resource_limits_concepts.md)**.

## Практические сценарии

### 1. Диагностика использования дескрипторов

Проверка лимитов текущей сессии:

```bash
# Мягкий / Жесткий лимиты
ulimit -Sn
ulimit -Hn
```

Просмотр лимитов **уже запущенного** процесса:

```bash
cat /proc/<PID>/limits | grep "Max open files"
# → Max open files            1024                 4096                 files
```

Изменение лимитов на лету (требует прав или того же пользователя):

```bash
# Установить новые лимиты для работающего процесса
sudo prlimit --pid <PID> --nofile=4096:8192
```

### 2. Настройка лимитов для systemd-сервисов

Для production-сервисов PAM-лимиты (`/etc/security/limits.conf`) **не применяются**. Используйте `LimitNOFILE=` в unit-файле:

```ini
# /etc/systemd/system/myapp.service
[Service]
ExecStart=/usr/bin/myapp
LimitNOFILE=65536
# Или unlimited:
# LimitNOFILE=infinity
```

Применение:

```bash
sudo systemctl daemon-reload
sudo systemctl restart myapp
# Проверка:
systemctl show myapp -p LimitNOFILE
# → LimitNOFILE=65536
```

Для временного увеличения без редактирования unit:

```bash
sudo systemctl runuser --property=LimitNOFILE=65536 myapp
```

### 3. Глубокий анализ через procfs (fd и fdinfo)

Директория `/proc/<PID>/fd/` содержит символические ссылки на все открытые ресурсы:

```bash
# Список открытых файлов
ls -l /proc/<PID>/fd/

# Подсчет количества открытых дескрипторов
ls /proc/<PID>/fd/ | wc -l

# Быстрый поиск конкретного файла
ls -l /proc/<PID>/fd/ | grep "/var/log/nginx"
```

Файлы в `/proc/<PID>/fdinfo/<FD>` предоставляют метаданные открытого дескриптора:

```bash
cat /proc/self/fdinfo/0
# → pos:    0          (текущее смещение)
# → flags:  02100002   (флаги доступа в восьмеричном виде)
# → mnt_id: 21         (ID монтирования)
```

Для сокетов `fdinfo` содержит расширенную информацию:

```bash
cat /proc/<PID>/fdinfo/3 | head -20
# → Для TCP: отправлено/получено байт, окна, состояние
# → Для eventpoll: список зарегистрированных FD
# → Для timerfd: следующее срабатывание
```

### 4. Поиск владельцев ресурсов (lsof и ss)

Утилита `lsof` (List Open Files) — основной инструмент инспекции:

```bash
# Кто открыл конкретный файл
sudo lsof /var/log/nginx/access.log

# Все сетевые дескрипторы процесса
sudo lsof -i -p <PID>

# Удалённые файлы, удерживаемые процессами
sudo lsof +L1 | grep deleted

# Альтернатива для сокетов (быстрее на нагруженных системах)
sudo ss -tp -p
```

Подробнее см. в справочнике **[lsof — Список открытых файлов](../Diagnostics/Processes/lsof.md)**.

### 5. Мониторинг потребления FD в production

Скрипт для мониторинга порога использования:

```bash
#!/bin/bash
# monitor_fd_threshold.sh
TARGET_PID=${1}
WARN_PERCENT=${2:-80}

if [ -z "$TARGET_PID" ]; then
    echo "Usage: $0 <PID> [warn_percent]"
    exit 1
fi

limit=$(grep "open files" /proc/$TARGET_PID/limits 2>/dev/null | awk '{print $4}')
current=$(ls /proc/$TARGET_PID/fd 2>/dev/null | wc -l)

if [ -z "$limit" ]; then
    echo "ERROR: Cannot read limits for PID $TARGET_PID"
    exit 1
fi

usage_pct=$((current * 100 / limit))
echo "PID: $TARGET_PID, FD: $current/$limit ($usage_pct%)"

if [ "$usage_pct" -gt "$WARN_PERCENT" ]; then
    echo "ALERT: FD usage above ${WARN_PERCENT}%"
    exit 1
fi
```

Мониторинг скорости роста FD для обнаружения утечек:

```bash
# Серия замеров с интервалом
for i in 1 2 3 4 5; do
    count=$(ls /proc/<PID>/fd 2>/dev/null | wc -l)
    echo "$(date '+%H:%M:%S') FD count: $count"
    sleep 600
done
# → Через 1 час: 1200
# → Через 2 часа: 2400
# → Скорость роста: ~200 FD/час — это утечка
```

### 6. Контейнеры: ограничения Docker/Podman

В контейнерах лимиты FD наследуются от рантайма:

```bash
# Проверка лимитов внутри контейнера
docker exec <container> sh -c 'ulimit -Sn; ulimit -Hn'

# Запуск с явным лимитом
docker run -d --ulimit nofile=65536:65536 nginx

# Проверка cgroup limits (cgroup v2)
cat /sys/fs/cgroup/nofile.max
cat /sys/fs/cgroup/nofile.current
```

**Важно:** В Docker лимит `nofile` по умолчанию может быть 1048576, но если хостовая ОС имеет `fs.nr_open` ниже, контейнер не сможет его использовать.

### 7. Диагностика: быстрое определение типа доминирующих FD

Перед увеличением лимитов исключите утечку:

```bash
# Общее распределение по типам
sudo lsof -p <PID> | awk '{print $5}' | sort | uniq -c | sort -rn
# →   950 TCP
# →    24 file
# →    12 UDP

# Углубленный анализ TCP-сокетов
sudo ss -tnp | grep <PID> | awk '{print $1}' | sort | uniq -c | sort -rn
# → CLOSE_WAIT 380  ← приложение не закрывает сокеты
# → ESTABLISHED 450
# → TIME_WAIT 120
```

### 8. Безопасность: FD как вектор утечки информации

Открытые FD могут сохранять доступ к конфиденциальным данным после `exec()`:

```bash
# Пример: процесс открыл файл с паролями, затем вызвал exec()
# Без O_CLOEXEC дочерний процесс наследует дескриптор

# Проверка FD, унаследованных сервисом
systemctl show <service> -p ExecMainPID
ls -l /proc/$(systemctl show <service> -p ExecMainPID --value)/fd/ | head -20
```

**Правила безопасности:**
- Всегда используйте `O_CLOEXEC` при открытии файлов в демонах.
- Проверяйте `FD_CLOEXEC` флаг через `fcntl(fd, F_GETFD)`.
- Никогда не передавайте чувствительные FD через `dup()` в дочерние процессы без необходимости.

### 9. Производительность: FD и событийные циклы

Каждое сетевое соединение consumes один FD. При проектировании высоконагруженных сервисов:

| Сервис | FD на соединение | Пример расчета (100K conn) |
| :--- | :--- | :--- |
| **Nginx** | 2 (клиент + бэкенд) | 200K FD |
| **PostgreSQL** | 1 + overhead | max_connections + 20 |
| **Java (Netty)** | 1-2 | Потоки * соединения |
| **Redis** | 1 | maxclients + 100 |

Для `epoll`-серверов лимит `fs.epoll.max_user_watches` должен превышать количество ожидаемых соединений:

```bash
# Проверка текущего значения
cat /proc/sys/fs/epoll/max_user_watches
# → 1048576 (по умолчанию ~4% от lowmem)

# Увеличение для высоконагруженных серверов
echo 5242880 | sudo tee /proc/sys/fs/epoll/max_user_watches
```

### 10. Решение проблем с удерживаемыми файлами (Deleted files)

Если файл удален (`rm`), но его FD открыт, ядро не освобождает место на диске:

1.  **Найти такие файлы:**
    ```bash
    sudo lsof +L1
    # ИЛИ
    sudo lsof | grep deleted
    ```
2.  **Освободить место:**
    -   Перезапустить сервис (лучший вариант).
    -   Обнулить файл через дескриптор, если нельзя остановить процесс:
        ```bash
        : > /proc/<PID>/fd/<FD_NUMBER>
        ```

Подробнее см. в **[Устранение нехватки места на диске](./disk_space_troubleshooting.md)**.

### 11. Диагностика утечек inotify-дескрипторов

```bash
# Подсчет inotify-дескрипторов конкретного процесса
ls /proc/<PID>/fd 2>/dev/null | grep inotify | wc -l

# Проверка глобальных лимитов inotify
cat /proc/sys/fs/inotify/max_user_watches
cat /proc/sys/fs/inotify/max_user_instances

# Поиск процессов с большим количеством inotify-дескрипторов
sudo lsof | grep inotify | awk '{print $1}' | sort | uniq -c | sort -rn | head

# Распространенные причины: IDE, файловые менеджеры, мониторинговые агенты
# которые создают watcher'ы, но не закрывают их после завершения работы
```

## Лучшие практики

1.  **Всегда используйте `O_CLOEXEC`** при открытии файлов в production-коде. Это предотвращает утечку FD в дочерние процессы.
2.  **Настраивайте `LimitNOFILE=` в systemd-юнитах**, а не `/etc/security/limits.conf`, для всех сервисов.
3.  **Мониторьте соотношение открытых FD к лимиту** (оптимальный порог — 70-80%).
4.  **Проверяйте `fs.nr_open` перед увеличением `ulimit -n`.** Если лимит не применяется, причина обычно в системном потолке.
5.  **Используйте `prlimit` для оперативного вмешательства** при инцидентах, а не перезапуск всего сервиса.
6.  **Для контейнеров настраивайте лимиты через runtime** (Docker `--ulimit`, containerd `Rlimits`), а не через `ulimit` в entrypoint.
7.  **Документируйте требуемые лимиты** для каждого сервиса в runbook.
