# Устранение нехватки места на диске

## Определения

- **Зарезервированное пространство (Reserved Blocks):** Часть дискового пространства в файловых системах семейства Ext (Ext2/3/4), доступная только пользователю `root`. По умолчанию составляет 5%.
- **Обнуление файла (Truncate):** Операция очистки содержимого файла до нулевого размера без его удаления. Позволяет освободить место, если файл удерживается открытым каким-либо процессом.

## Основные концепции

### Виды нехватки места

1. **Нехватка блоков (Blocks):** Исчерпание фактического объема для хранения данных. Проверяется через `df -h`.
2. **Исчерпание индексных дескрипторов (Inodes):** На диске есть свободные гигабайты, но нельзя создать новый файл, так как закончились записи в таблице метаданных. Проверяется через `df -i`.

### Удаленные, но открытые файлы

Частая причина ситуации, когда файлы удалены (через `rm`), но место на накопителе не освободилось. Это происходит потому, что работающий процесс продолжает удерживать файловый дескриптор открытым. Ядро освободит блоки данных только после завершения процесса или закрытия им дескриптора.

**Как найти такие файлы:**
Используйте команду `lsof` (list open files) и ищите файлы с пометкой `(deleted)`:
```bash
sudo lsof +L1
# Или через grep
sudo lsof | grep deleted
```
В выводе вы увидите `COMMAND`, `PID` и `SIZE`. Чтобы освободить место, нужно либо перезапустить процесс (`systemctl restart <service>`), либо обнулить файл через дескриптор в `/proc` (см. ниже).

**Важно:** Также не забывайте про разницу в системах исчисления (GB vs GiB), из-за которой «пропажа» ~7% объема диска является нормальным поведением. Подробнее см. в [Единицы измерения в Linux](./disk_storage_fundamentals.md#единицы-измерения).

Подробная механика описана в [Диагностика файловых систем и дискового пространства](../Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md#механизм-удалённых-открытых-файлов-deleted-but-open).

## Практические сценарии

### 1. Экстренное спасение (для Ext2/3/4)

Если диск заполнен на 100% и система "зависла" или не позволяет войти под обычным пользователем, можно временно обнулить резерв для `root`, чтобы получить 5% свободного места для проведения очистки.

```bash
# Уменьшить резерв до 0%
sudo tune2fs -m 0 /dev/sdXN
```

**После очистки диска обязательно верните резерв (рекомендуется 1-5%):**

```bash
sudo tune2fs -m 5 /dev/sdXN
```

### 2. Поиск виновников

**Быстрый поиск крупных директорий:**

```bash
sudo du -sh /* 2>/dev/null | sort -rh | head -20
```

**Интерактивный анализ:**
Рекомендуется использовать утилиту `ncdu`. Она позволяет наглядно перемещаться по дереву каталогов и сразу удалять ненужное.

```bash
sudo ncdu /
```

### 3. Чек-лист очистки системы

Если причина не в одном огромном файле, выполните стандартные шаги по очистке кэшей:

- **Системный журнал (journald):**

  ```bash
  # Оставить только последние 100 МБ логов
  sudo journalctl --vacuum-size=100M
  ```

- **Пакетный менеджер:**

  ```bash
  sudo apt-get clean      # Для Debian/Ubuntu
  sudo yum clean all      # Для RHEL/CentOS
  ```

- **Docker (удаление неиспользуемых ресурсов):**

  ```bash
  docker system prune -a --volumes
  ```

- **Логи приложений в `/var/log`:**
  Удалите старые архивные файлы (заканчивающиеся на `.gz` или `.1`).

### 4. Очистка файла без удаления (Truncate)

Если вы нашли огромный лог-файл, который нельзя удалить (потому что сервис перестанет писать логи или место не освободится из-за открытого дескриптора), используйте перенаправление для обнуления:

```bash
# Файл останется на месте, но его размер станет 0
sudo truncate -s 0 /var/log/very_large_app.log
# Или через перенаправление
sudo true > /var/log/very_large_app.log
```
