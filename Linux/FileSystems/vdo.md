# Virtual Data Optimizer (VDO)

## Определения

- **VDO (Virtual Data Optimizer):** Технология оптимизации дискового пространства в Linux, обеспечивающая дедупликацию, сжатие и тонкое выделение ресурсов (**Thin Provisioning**) на уровне блочного устройства. Изначально разработана компанией Permabit, затем приобретена и открыта Red Hat.
- **Дедупликация (Deduplication):** Метод исключения дубликатов данных путем хранения только одной уникальной копии блока и замены остальных ссылками на него. В VDO выполняется с помощью сервиса **UDS (Universal Deduplication Service)**.
- **Сжатие (Compression):** Уменьшение размера блоков данных с использованием алгоритма **LZ4**. Выполняется после дедупликации для блоков, которые остались уникальными.
- **UDS (Universal Deduplication Service):** Высокопроизводительный индекс, используемый VDO для быстрого определения того, записывался ли данный блок данных ранее.

## Основные концепции

### Архитектура и место в стеке

VDO функционирует как модуль ядра и располагается между физическим блочным устройством и файловой системой.

```text
+---------------------------------------------------+
|      Файловая система (XFS, Ext4, Btrfs)          |
+---------------------------------------------------+
|      Блочное устройство VDO (/dev/mapper/...)     |
+---------------------------------------------------+
|   VDO Layer (Дедупликация -> Сжатие -> Thin Prov) |
+---------------------------------------------------+
|   Физическое устройство (HDD, SSD, RAID, LUKS)    |
+---------------------------------------------------+
```

### Принципы работы

1.  **Поиск дубликатов (UDS):** При записи данных VDO вычисляет хеш блока и проверяет его наличие в индексе UDS. Если блок уже существует, создается ссылка.
2.  **Сжатие:** Если блок уникален, он передается модулю сжатия. Несколько сжатых блоков могут быть упакованы в один физический блок размером 4 КБ.
3.  **Тонкое выделение (Thin Provisioning):** VDO позволяет презентовать операционной системе логический объем, значительно превышающий физический (например, 10:1 для виртуальных машин).

### Режимы записи (Write Policy)

- **`sync` (Synchronous):** Запись подтверждается только после того, как данные физически записаны на диск. Обеспечивает максимальную сохранность, но снижает производительность. Рекомендуется для устройств без защиты от потери питания.
- **`async` (Asynchronous):** Запись подтверждается сразу после попадания в кэш VDO. Значительно быстрее, но требует наличия ИБП или дисков с защитой кэша (BBU/Supercaps).
- **`auto`:** VDO пытается автоматически определить тип устройства и выбрать оптимальный режим (по умолчанию).

## Практические сценарии

### Установка (RHEL/CentOS/Fedora)

В современных дистрибутивах (RHEL 9+) VDO интегрирован в LVM.

```bash
# Установка необходимых пакетов
sudo dnf install lvm2-vdo kmod-kvdo
```

### Создание VDO-тома через LVM (рекомендуемый способ)

В актуальных версиях управление осуществляется средствами `lvm2`.

```bash
# Создание VDO-тома в существующей Volume Group (vg01)
# --name: имя логического тома
# --size: физический объем, выделяемый под VDO
# --virtualsize: логический (видимый ФС) объем
sudo lvcreate --type vdo --name lvm_vdo_vol --size 10G --virtualsize 100G vg01

# Просмотр статистики через lvs
sudo lvs -a -o+vdo_compression,vdo_deduplication,vdo_usage_percent
```

### Создание VDO-тома через классическую утилиту (Legacy)

Используется в RHEL 8 и старых версиях.

```bash
# Создание тома
sudo vdo create --name=vdo_data --device=/dev/sdb --vdoLogicalSize=100G

# Проверка статуса
sudo vdo status --name=vdo_data
```

### Создание файловой системы и монтирование

Для VDO настоятельно рекомендуется использовать **XFS**.

```bash
# Создание XFS с отключением discard при форматировании (для контроля VDO)
sudo mkfs.xfs -K /dev/mapper/vg01-lvm_vdo_vol

# Монтирование через fstab с указанием зависимости от сервиса
# /etc/fstab:
# /dev/mapper/vg01-lvm_vdo_vol  /mnt/vdo  xfs  defaults,x-systemd.requires=vdo.service 0 0
```

### Мониторинг использования

```bash
# Просмотр физической экономии места
sudo vdostats --human-readable

# Пример вывода:
# Device                    Size      Used Available Percent Space saving%
# /dev/mapper/vdo_data     10.0G      4.2G      5.8G     42%           75%
```

## Производительность и требования

### Потребление ресурсов

- **CPU:** Значительная нагрузка при сжатии и вычислении хешей. Нагрузка пропорциональна скорости записи.
- **RAM:** Критически важный ресурс для индекса UDS.
  - Минимум: ~740 МБ для сервиса + индекс.
  - Эмпирическое правило: ~1 ГБ ОЗУ на 1 ТБ физического пространства.

### Ограничения и особенности

- **Размер Slab:** Минимальная единица распределения пространства в VDO. По умолчанию 2 ГБ. Если физический диск > 16 ТБ, необходимо увеличивать размер Slab.
- **Шифрование:** LUKS должен располагаться **под** VDO. Если зашифровать VDO-устройство сверху, дедупликация и сжатие будут неэффективны из-за высокой энтропии зашифрованных данных.

## Сценарии использования

| Сценарий | Эффективность | Комментарий |
| :--- | :--- | :--- |
| **Репозитории бэкапов** | Высокая | Многократные повторы блоков в инкрементальных копиях. |
| **Виртуализация (KVM)** | Высокая | Однотипные образы ОС и библиотек идеально дедуплицируются. |
| **Базы данных** | Низкая | Сжатие неэффективно для предварительно аллоцированных файлов. Высокие задержки I/O. |
| **Мультимедиа (Видео)** | Нулевая | Видео уже сжато на уровне кодека. |
