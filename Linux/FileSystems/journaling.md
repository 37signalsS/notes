# Журналирование файловых систем

## Определения

- **Журналируемая файловая система (Journaling Filesystem):** Файловая система, использующая специальную область — **журнал (journal, log)** — для предварительной записи метаданных (и иногда данных) перед их применением к основным структурам ФС. Это гарантирует атомарность операций и быстрое восстановление целостности.
- **WAL (Write-Ahead Logging):** Принцип «журнала предзаписи», при котором запись в лог на диске должна быть завершена и подтверждена контроллером до того, как изменения будут внесены в основные блоки ФС.
- **Транзакция:** Группа связанных изменений (например, выделение inode + обновление bitmap + запись данных), которая должна быть выполнена целиком (commit) или отменена (discard) при сбое.
- **Checkpoint (Контрольная точка):** Процесс переноса зафиксированных транзакций из журнала в основные структуры ФС с последующим освобождением места в журнале.
- **Физическое журналирование:** Запись в журнал полных блоков данных (как в JBD2). Надежно, но создает двойную нагрузку на I/O.
- **Логическое журналирование:** Запись в журнал только описания операции или конкретных изменившихся полей структур (как в XFS CIL). Значительно быстрее, но сложнее в реализации восстановления.

## Основные концепции

### Проблема несогласованности

Без журнала запись файла — это серия разрозненных операций (Inode -> Bitmap -> Data -> Directory). Сбой питания между этими шагами приводит к «грязному» состоянию ФС, требующему полного сканирования утилитой `fsck`, что на больших томах занимает часы. Журналирование сокращает время восстановления до долей секунды за счет «доигрывания» (Replay) лога.

### Реализация в ext4: JBD2 (Journaling Block Device)

Ext4 делегирует задачу журналирования уровню **JBD2**. Он работает с физическими блоками и управляет жизненным циклом транзакций:

1.  **Running (Выполнение):** Текущая активная транзакция, к которой прикрепляются все системные вызовы.
2.  **Locked (Блокировка):** Транзакция закрывается для новых операций.
3.  **Flush (Сброс):** Данные транзакции записываются в журнал.
4.  **Commit (Фиксация):** Записывается блок фиксации с контрольной суммой. С этого момента транзакция считается «завершенной» с точки зрения надежности.
5.  **Checkpoint (Контрольная точка):** Фоновый перенос блоков из журнала в основные области диска.
6.  **Finished (Завершение):** Место в журнале освобождается.

### Реализация в XFS: CIL (Committed Item List)

XFS спроектирована для высокой параллельности и использует механизм **Delayed Logging** через CIL, чтобы избежать узких мест глобальных блокировок JBD2.

- **CIL (Committed Item List):** In-memory буфер, агрегирующий изменения метаданных. Если один и тот же Inode меняется 100 раз за секунду, CIL сохранит только финальное состояние, радикально снижая нагрузку на диск.
- **CIL Push:** Периодически или по заполнению буфера, CIL «проталкивает» агрегированные изменения в физический лог (xlog) одной большой транзакцией.
- **AIL (Active Item List):** Список элементов, которые уже зафиксированы в логе, но еще не перенесены в основные блоки ФС. Даемон `xfsaild` постепенно переносит эти данные на диск.

### Режимы журналирования (на примере ext4)

| Режим | Что журналируется | Надежность | Производительность | Применение |
| :--- | :--- | :--- | :--- | :--- |
| **`data=journal`** | Данные и метаданные | Максимальная | Минимальная | Критичные БД, транзакционные логи. |
| **`data=ordered`** | Только метаданные | Высокая | Сбалансированная | Стандарт по умолчанию (Default). |
| **`data=writeback`** | Только метаданные | Средняя | Максимальная | Кэши, временные файлы. |

*Примечание:* В режиме `ordered` ядро гарантирует сброс блоков данных на диск **до** фиксации метаданных в журнале.

### Барьеры записи (Write Barriers)

Критическая опция (`mount -o barrier=1`). Заставляет диск сбрасывать свой кэш (volatile cache) на физический носитель перед завершением транзакции.
- **Риск:** Без барьеров сбой питания может «стереть» транзакцию, которую ядро уже считало завершенной.
- **Исключение:** Барьеры можно отключать (`barrier=0`) только при наличии аппаратного RAID-контроллера с батарейкой (BBU) или Supercaps.

## Практические сценарии

### 1. Тюнинг ext4: Интервал фиксации и режим

Для систем с ИБП (UPS) или некритичных данных можно увеличить интервал записи журнала, чтобы снизить I/O.

```bash
# Увеличение интервала фиксации до 60 секунд (по умолчанию 5)
sudo mount -o remount,commit=60,data=writeback /mnt/data
```

### 2. Вынос журнала XFS на внешний диск (External Log)

XFS позволяет хранить лог на отдельном сверхбыстром устройстве (NVMe), что критично для высоконагруженных метаданными задач (создание миллионов файлов).

```bash
# Создание ФС с внешним логом (например, на /dev/nvme0n1)
sudo mkfs.xfs -l logdev=/dev/nvme0n1 /dev/sda1

# Монтирование
sudo mount -o logdev=/dev/nvme0n1 /dev/sda1 /mnt/xfs_data
```

### 3. Тюнинг буферов лога XFS

Для серверов с большим объемом памяти можно увеличить размер буферов лога в памяти для повышения пропускной способности.

```bash
# Увеличение размера буферов лога (макс. 256k или 8 буферов по 32k)
sudo mount -o remount,logbsize=256k /mnt/xfs_data
```

### 4. Управление размером журнала ext4

Если журнал часто переполняется (большой поток мелких записей), его можно увеличить.

```bash
# Просмотр параметров
sudo dumpe2fs /dev/sda1 | grep -i 'Journal size'

# Увеличение (требует umount)
sudo umount /dev/sda1
sudo tune2fs -J size=1024 /dev/sda1
sudo e2fsck -f /dev/sda1
```

### 5. Диагностика повреждений журнала

Если ФС не монтируется из-за поврежденного журнала:

```bash
# Для ext4: очистка журнала и полная проверка
sudo e2fsck -fy /dev/sda1

# Для XFS: восстановление из лога (обычно происходит автоматически при mount)
# Если лог безнадежно поврежден (внимание: возможна потеря данных!)
sudo xfs_repair -L /dev/sda1
```
