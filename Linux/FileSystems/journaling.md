# Журналирование файловых систем

## Определения

- **Журналируемая файловая система (Journaling Filesystem):** Файловая система, использующая специальную область — **журнал (journal, log)** — для предварительной записи метаданных (и иногда данных) перед их применением к основным структурам ФС. Это гарантирует атомарность операций и быстрое восстановление целостности.
- **WAL (Write-Ahead Logging):** Принцип «журнала предзаписи», при котором запись в лог на диске должна быть завершена и подтверждена контроллером до того, как изменения будут внесены в основные блоки ФС.
- **Транзакция:** Группа связанных изменений (например, выделение inode + обновление bitmap + запись данных), которая должна быть выполнена целиком (commit) или отменена (discard) при сбое.
- **Checkpoint (Контрольная точка):** Процесс переноса зафиксированных транзакций из журнала в основные структуры ФС с последующим освобождением места в журнале.
- **Физическое журналирование:** Запись в журнал полных блоков данных (как в JBD2). Надежно, но создает двойную нагрузку на I/O.
- **Логическое журналирование:** Запись в журнал только описания операции или конкретных изменившихся полей структур (как в XFS CIL). Значительно быстрее, но сложнее в реализации восстановления.
- **Поток журналирования (`jbd2`):** Ядерный поток (kthread), который управляет жизненным циклом транзакций в ext4. Запускается автоматически при монтировании ФС с журналом.

## Основные концепции

### Проблема несогласованности

Без журнала запись файла — это серия разрозненных операций (Inode -> Bitmap -> Data -> Directory). Сбой питания между этими шагами приводит к «грязному» состоянию ФС, требующему полного сканирования утилитой `fsck`, что на больших томах занимает часы. Журналирование сокращает время восстановления до долей секунды за счет «доигрывания» (Replay) лога.

### Структура и расположение журнала

#### Журнал как специальный файл

В ext4 журнал хранится в скрытом файле `.journal` в корне ФС или в специальном inode (inode 8 для ext3/ext4). При создании ФС `mkfs.ext4` резервирует место для журнала. Размер по умолчанию составляет 128 МБ, но может быть увеличен через `tune2fs -J size=`.

```bash
# Просмотр информации о журнале
sudo dumpe2fs -h /dev/sda1 | grep -i 'Journal size\|Journal inode\|Journal backup'
```

#### Inode журнала

Журнал имеет собственный inode с типом `S_IFREG` (обычный файл), но Kernel обращается к нему напрямую, минуя стандартный путь VFS, чтобы минимизировать накладные расходы и избежать рекурсивного монтирования.

### Жизненный цикл транзакции в ext4: JBD2 (Journaling Block Device)

Ext4 делегирует задачу журналирования уровню **JBD2**. Он работает с физическими блоками и управляет жизненным циклом транзакций через ядерный поток `jbd2/<device>`:

1.  **Running (Выполнение):** Текущая активная транзакция, к которой прикрепляются все системные вызовы.
2.  **Locked (Блокировка):** Транзакция закрывается для новых операций.
3.  **Flush (Сброс):** Данные транзакции записываются в журнал.
4.  **Commit (Фиксация):** Записывается блок фиксации с контрольной суммой. С этого момента транзакция считается «завершенной» с точки зрения надежности.
5.  **Checkpoint (Контрольная точка):** Фоновый перенос блоков из журнала в основные области диска.
6.  **Finished (Завершение):** Место в журнале освобождается.

### Реализация в XFS: CIL (Committed Item List)

XFS спроектирована для высокой параллельности и использует механизм **Delayed Logging** через CIL, чтобы избежать узких мест глобальных блокировок JBD2.

- **CIL (Committed Item List):** In-memory буфер, агрегирующий изменения метаданных. Если один и тот же Inode меняется 100 раз за секунду, CIL сохранит только финальное состояние, радикально снижая нагрузку на диск.
- **CIL Push:** Периодически или по заполнению буфера, CIL «проталкивает» агрегированные изменения в физический лог (xlog) одной большой транзакцией.
- **AIL (Active Item List):** Список элементов, которые уже зафиксированы в логе, но еще не перенесены в основные блоки ФС. Даемон `xfsaild` постепенно переносит эти данные на диск.

### Восстановление после сбоя (Replay)

При монтировании ФС ядро выполняет **journal replay**:

1. Чтение журнала с конца.
2. Поиск последней контрольной точки (commit record).
3. Дочитывание всех транзакций, начиная с этой точки.
4. Применение изменений к основным структурам ФС.
5. Очистка журнала.

Для ext4/XFS этот процесс занимает доли секунды, что критически важно для времени загрузки серверов. Если журнал поврежден, replay не выполняется и требуется полная проверка `fsck`.

### Режимы журналирования (на примере ext4)

| Режим | Что журналируется | Надежность | Производительность | Применение |
| :--- | :--- | :--- | :--- | :--- |
| **`data=journal`** | Данные и метаданные | Максимальная | Минимальная | Критичные БД, транзакционные логи. |
| **`data=ordered`** | Только метаданные | Высокая | Сбалансированная | Стандарт по умолчанию (Default). |
| **`data=writeback`** | Только метаданные | Средняя | Максимальная | Кэши, временные файлы. |

*Примечание:* В режиме `ordered` ядро гарантирует сброс блоков данных на диск **до** фиксации метаданных в журнале.

### Барьеры записи (Write Barriers)

Критическая опция (`mount -o barrier=1`). Заставляет диск сбрасывать свой кэш (volatile cache) на физический носитель перед завершением транзакции.

- **Риск:** Без барьеров сбой питания может «стереть» транзакцию, которую ядро уже считало завершенной.
- **Исключение:** Барьеры можно отключать (`barrier=0`) только при наличии аппаратного RAID-контроллера с батарейкой (BBU) или Supercaps.

### Сравнение с Copy-on-Write (CoW)

В отличие от журналирования, CoW-файловые системы (Btrfs, ZFS) никогда не перезаписывают данные на месте. Изменения пишутся в новый блок, а указатели обновляются атомарно. Это обеспечивает инкапсуляцию целостности без отдельного журнала, но создает фрагментацию и требует больше места. Журналирование (ext4/XFS) пишет данные на место после replay, что экономит место, но требует барьеров для безопасности.

### Журналирование в других ФС

- **ReiserFS:** Одна из первых журналируемых ФС в Linux (до ext3). Использула физическое журналирование. Сейчас устарела.
- **JFS (IBM):** Использует логическое журналирование, похожее на XFS CIL. Эффективна для средних нагрузок.
- **Btrfs:** Хотя Btrfs использует CoW, она имеет внутренний журнал для метаданных при некоторых операциях (например, при создании снапшотов).

## Практические сценарии

### 1. Тюнинг ext4: Интервал фиксации и режим

Для систем с ИБП (UPS) или некритичных данных можно увеличить интервал записи журнала, чтобы снизить I/O.

```bash
# Увеличение интервала фиксации до 60 секунд (по умолчанию 5)
sudo mount -o remount,commit=60,data=writeback /mnt/data
```

### 2. Вынос журнала XFS на внешний диск (External Log)

XFS позволяет хранить лог на отдельном сверхбыстром устройстве (NVMe), что критично для высоконагруженных метаданными задач (создание миллионов файлов).

```bash
# Создание ФС с внешним логом (например, на /dev/nvme0n1)
sudo mkfs.xfs -l logdev=/dev/nvme0n1 /dev/sda1

# Монтирование
sudo mount -o logdev=/dev/nvme0n1 /dev/sda1 /mnt/xfs_data
```

### 3. Тюнинг буферов лога XFS

Для серверов с большим объемом памяти можно увеличить размер буферов лога в памяти для повышения пропускной способности.

```bash
# Увеличение размера буферов лога (макс. 256k или 8 буферов по 32k)
sudo mount -o remount,logbsize=256k /mnt/xfs_data
```

### 4. Управление размером журнала ext4

Если журнал часто переполняется (большой поток мелких записей), его можно увеличить.

```bash
# Просмотр параметров
sudo dumpe2fs /dev/sda1 | grep -i 'Journal size'

# Увеличение (требует umount)
sudo umount /dev/sda1
sudo tune2fs -J size=1024 /dev/sda1
sudo e2fsck -f /dev/sda1
```

### 5. Диагностика повреждений журнала

Если ФС не монтируется из-за поврежденного журнала:

```bash
# Для ext4: очистка журнала и полная проверка
sudo e2fsck -fy /dev/sda1

# Для XFS: восстановление из лога (обычно происходит автоматически при mount)
# Если лог безнадежно поврежден (внимание: возможна потеря данных!)
sudo xfs_repair -L /dev/sda1
```

### 6. Мониторинг активности журнала

Для диагностики производительности и поиска узких мест:

```bash
# Поиск потоков jbd2 (ext4)
ps aux | grep jbd2
# → root      123  0.0  0.0   ... /sbin/jbd2/sda1-8

# Мониторинг активности в реальном времени
sudo iostat -x 1 /dev/sda1

# Проверка очередей wait (если jbd2 создает нагрузку)
sudo atop 1 10
```

### 7. Проверка состояния журнала через tune2fs

```bash
# Полная информация о журнале ext4
sudo tune2fs -l /dev/sda1 | grep -i 'journal'

# → Journal inode: 8
# → Journal size: 128M
# → Journal backup: inode blocks
```

### 8. Восстановление после аварийного отключения питания

Стандартный протокол для серверов, восстановленных после сбоя питания:

```bash
# 1. Проверка SMART-статуса дисков (приоритет: проверка железа перед ФС)
sudo smartctl -a /dev/sdX | grep -E 'SMART overall|Reallocated|Current_Pending|Offline_Uncorrectable'

# 2. Проверка журналов ядра на предмет I/O ошибок
dmesg -T | grep -Ei 'EXT4-fs error|XFS|I/O error|Buffer I/O|read-only|abort' | tail -20

# 3. Принудительная проверка всех локальных ФС
sudo fsck -y -f /dev/sdX1
sudo fsck -y -f /dev/sdX2

# 4. Для XFS
sudo xfs_repair /dev/sdX3
```

### 9. Тестирование производительности journaling

```bash
# Создание тестового файла и измерение latency
sudo hdparm -t /dev/sda1

# С флагом barrier=1 (по умолчанию)
sudo mount -o remount,barrier=1 /mnt/data
time dd if=/dev/zero of=/mnt/data/testfile bs=1G count=1 oflag=dsync

# Без барьеров (только для тестов на не критичных данных!)
sudo mount -o remount,barrier=0 /mnt/data
time dd if=/dev/zero of=/mnt/data/testfile bs=1G count=1 oflag=dsync
```

### 10. Работа с journaling в контейнерах

Контейнеры не имеют прямого доступа к блочным устройствам, поэтому journaling настраивается на хосте:

```bash
# Проверка параметров journaling на смонтированных разделах контейнера
findmnt -o TARGET,FSTYPE,OPTIONS /mnt/data

# Изменение параметров journaling (на хосте)
sudo mount -o remount,data=ordered,barrier=1 /mnt/data
```

## Устранение неполадок

- **ФС переходит в RO после сбоя питания:** JBD2 не может записать транзакцию в журнал. ext4 переводит ФС в RO для защиты данных. Решение: проверка диска (`smartctl`), затем `fsck` или `xfs_repair`.
- **Высокая задержка записи (latency):** Частая перегрузка потока `jbd2`. Решение: увеличение `commit` интервала, вынос журнала на отдельное устройство, проверка `iostat -x` на `%util`.
- **Журнал переполняется:** При большом потоке мелких записей размер журнала по умолчанию (128 МБ) может оказаться недостаточным. Решение: `tune2fs -J size=1024M /dev/sdXN`.
- **Ошибка «Aborting journal»:** Критическая ошибка записи в журнал. Решение: немедленное отмонтирование, проверка диска, восстановление суперблока.
- **Конфликт barrier=0 с BBU:** При отключении барьеров без батарейки на RAID-контроллере данные могут быть потеряны при сбое питания. Решение: либо включить barrier=1, либо убедиться в наличии BBU.
- **XFS: внешний лог недоступен:** Если устройство внешнего лога вышло из строя, XFS переходит в RO. Решение: `xfs_repair` с переносом лога обратно на основной раздел.

## Лучшие практики

1.  **Всегда используйте journaling ФС** (ext4, XFS) для данных, где важна целостность. Отключайте journaling (`nolog` для XFS) только на временных кэшах.
2.  **Не отключайте барьеры (`barrier=0`) без BBU** на RAID-контроллере. Это основная защита от потери данных при сбое питания.
3.  **Для баз данных:** используйте `data=ordered` (по умолчанию) или XFS. Избегайте `data=writeback` на критичных данных.
4.  **Настройте автоматическую проверку:** `tune2fs -i 1m -c 30 /dev/sdXN` для ext4.
5.  **Мониторьте `jbd2` потоки:** высокая загрузка `%util` на потоке журнала указывает на необходимость тюнинга.
6.  **Для высоконагруженных серверов:** используйте внешний журнал XFS на NVMe или увеличьте `logbsize` до 256k.
7.  **Тестируйте сценарии восстановления:** регулярно проверяйте, как ведет себя ФС при отключении питания (на стенде).
8.  **Документируйте параметры journaling:** ведите реестр настроек ФС (`/etc/fstab`, `tune2fs -l`) для каждой системы.
