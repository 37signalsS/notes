# Журналирование файловых систем

## Определения

- **Журналируемая файловая система (Journaling Filesystem):** Файловая система, использующая специальную область — **журнал (journal, log)** — для предварительной записи изменений перед их применением к основным структурам данных. Это обеспечивает атомарность операций и быстрое восстановление целостности после сбоев.
- **WAL (Write-Ahead Logging):** Фундаментальный принцип «журнала предзаписи», гарантирующий, что запись в журнал всегда завершается до того, как измененные данные попадут в основную область хранения.
- **Транзакция:** Группа связанных изменений (например, выделение inode + обновление bitmap + запись данных), которая должна быть выполнена либо полностью, либо не выполнена совсем.
- **Checkpoint (Контрольная точка):** Процесс переноса зафиксированных транзакций из журнала в основные структуры ФС с последующим освобождением места в журнале.

## Основные концепции

### Проблема несогласованности

В файловых системах без журнала (например, ext2) запись файла — это серия разрозненных операций:
1.  Выделение Inode.
2.  Обновление Bitmap блоков.
3.  Запись данных.
4.  Обновление каталога (связка имени с Inode).

Если питание отключается в середине процесса, ФС остается в «грязном» (inconsistent) состоянии. После перезагрузки требуется полный скан всей поверхности диска утилитой `fsck`, что занимает часы на терабайтных массивах.

### Цикл работы журнала

```text
[1] Transaction Start -> [2] Write to Journal -> [3] Commit (Journal Sync) -> [4] Checkpoint (Main FS Update)
```
При сбое во время шага [4] система при загрузке просто «доигрывает» (Replay) транзакцию из журнала. Это занимает доли секунды.

### Режимы журналирования (на примере ext4)

| Режим | Что журналируется | Надежность | Производительность | Применение |
| :--- | :--- | :--- | :--- | :--- |
| **`data=journal`** | Данные и метаданные | Максимальная | Минимальная | Критичные БД, финансовые данные. |
| **`data=ordered`** | Только метаданные | Высокая | Сбалансированная | Стандарт по умолчанию для Linux. |
| **`data=writeback`** | Только метаданные | Средняя | Максимальная | Кэши, временные файлы, CI-воркеры. |

*Примечание:* В режиме `ordered` ядро гарантирует, что блоки данных записываются на диск **до** фиксации соответствующих метаданных в журнале.

### Барьеры записи (Write Barriers)

Критически важная настройка (`mount -o barrier=1`). Барьеры заставляют накопитель сбрасывать свой внутренний кэш на физическую пластину/чип перед фиксации транзакции в журнале.
- **Без барьеров:** Сбой питания может привести к тому, что транзакция отмечена в журнале как завершенная, но данные реально не покинули волатильный кэш диска -> ФС повреждена.
- **Рекомендация:** Отключайте барьеры (`barrier=0`) только если у контроллера дисков есть батарейка (BBU/Supercaps).

### Альтернативы: CoW и ZIL

- **Btrfs (Copy-on-Write):** Не имеет классического журнала. Вместо перезаписи старого блока всегда пишет в новый. Указатель на корень ФС переключается атомарно после успешной записи.
- **ZFS ZIL (ZFS Intent Log):** Используется для ускорения синхронных записей. Это не журнал ФС в классическом смысле, а лог транзакций, который может быть вынесен на отдельный сверхбыстрый диск (**SLOG**).

## Практические сценарии

### 1. Тюнинг журнала для HDD (Вынос на SSD)

На медленных HDD головка постоянно перемещается между данными и журналом. Вынос журнала на отдельный SSD радикально повышает IOPS метаданных.

```bash
# 1. Подготовка раздела журнала на SSD
sudo mke2fs -t ext4 -O journal_dev /dev/nvme0n1p1

# 2. Создание ФС с использованием внешнего журнала
sudo mkfs.ext4 -J device=/dev/nvme0n1p1 /dev/sda1

# Для существующей ФС:
sudo umount /dev/sda1
sudo tune2fs -J device=/dev/nvme0n1p1 /dev/sda1
```

### 2. Управление размером журнала

По умолчанию размер журнала составляет 128-512 МБ. На высоконагруженных системах (запись множества мелких файлов) журнал может переполняться.

```bash
# Просмотр параметров журнала
sudo dumpe2fs /dev/sda1 | grep -i 'journal'

# Увеличение журнала до 1 ГБ (требует размонтирования)
sudo umount /dev/sda1
sudo tune2fs -J size=1024 /dev/sda1
sudo e2fsck -f /dev/sda1
```

### 3. Диагностика повреждений

Если журнал поврежден (например, из-за физического сбоя SSD), ФС не смонтируется.

```bash
# Принудительная очистка журнала и полная проверка
sudo e2fsck -fy /dev/sda1
```

### 4. Оптимизация под базы данных

Для PostgreSQL/MySQL на ext4 часто рекомендуется `data=ordered`, но если надежность дисковой подсистемы гарантирована (RAID с BBU), можно использовать `data=writeback` для снижения задержек на фиксации метаданных.
