# Журналирование файловых систем

## Определения

* **Журналируемая файловая система (Journaling Filesystem)** — файловая система, которая перед применением любых изменений к основным структурам данных записывает их в специальную область — **журнал (journal, log)**. Это гарантирует возможность восстановления консистентного состояния после сбоя питания или краха системы.
* **Транзакция** — атомарная группа операций записи, которая либо применяется целиком, либо не применяется вовсе.
* **Write-Ahead Logging (WAL)** — фундаментальный принцип: данные сначала записываются в журнал, и только после подтверждения записи — в основное хранилище.

## Основные концепции

### Проблема, которую решает журналирование

**Без журналирования:** При записи файла система выполняет несколько разрозненных операций:

```
1. Выделить inode
2. Выделить блоки данных
3. Записать данные
4. Обновить bitmap свободных блоков
5. Обновить директорию (имя → inode)
```

Если питание отключится между шагами 3 и 4 — файловая система окажется в **несогласованном состоянии**: данные записаны, но inode их не «видит», или bitmap показывает блоки как свободные, хотя они заняты. После перезагрузки требуется полная проверка `fsck` (сканирование всей ФС), которая на больших дисках занимает **часы**.

**С журналированием:** Все 5 шагов сначала описываются как одна транзакция и записываются в журнал. Только после фиксации транзакции в журнале изменения применяются к основным структурам. Сбой на любом этапе → при загрузке ядро «доигрывает» или откатывает последнюю транзакцию из журнала. Восстановление занимает **секунды**.

### Как работает журналирование: Пошаговый цикл

```
┌──────────────────────────────────────────────┐
│  1. BEGIN_TRANSACTION                        │
│     Фиксируем, какие блоки будут изменены     │
├──────────────────────────────────────────────┤
│  2. WRITE_TO_JOURNAL                         │
│     Записываем метаданные (+ данные) в журнал │
├──────────────────────────────────────────────┤
│  3. COMMIT (checkpoint)                      │
│     Фиксируем транзакцию в журнале            │
├──────────────────────────────────────────────┤
│  4. APPLY_TO_MAIN_FS                         │
│     Применяем изменения к основным структурам │
├──────────────────────────────────────────────┤
│  5. FREE_JOURNAL_ENTRY                       │
│     Освобождаем место в журнале               │
└──────────────────────────────────────────────┘
```

### Режимы журналирования (ext4)

| Режим | Что журналируется | Надёжность | Производительность | Когда использовать |
| :--- | :--- | :--- | :--- | :--- |
| **`data=journal`** | Данные + метаданные | Максимальная | Минимальная (двойная запись) | Базы данных, критичные данные |
| **`data=ordered`** (по умолчанию) | Только метаданные; данные гарантированно записываются **до** фиксации метаданных | Высокая | Хорошая | General-purpose, веб-серверы |
| **`data=writeback`** | Только метаданные; данные могут быть записаны **в любом порядке** | Низкая (риск «мусора» в файлах после сбоя) | Максимальная | Временные файлы, кэш, CI-сборки |

**Проверка текущего режима:**

```bash
tune2fs -l /dev/sda1 | grep 'Filesystem features'
# или при монтировании:
mount | grep 'data='
```

**Изменение режима:**

```bash
# Временное изменение (при следующем монтировании)
mount -o remount,data=writeback /dev/sda1

# Постоянное изменение через /etc/fstab
# UUID=xxx /mnt/data ext4 defaults,data=journal 0 2
```

### Журналирование в XFS

XFS использует **только один режим** — журналирование метаданных с гарантированным порядком записи данных (аналог `data=ordered`). Это упрощает администрирование: нет выбора режима, но XFS оптимизирован для высокой производительности записи.

```bash
# Информация о журнале XFS
xfs_db -c 'sb 0' -c 'p' /dev/sda1 | grep -i log
```

### Btrfs и Copy-on-Write (CoW)

Btrfs не использует классический журнал. Вместо этого применяется **Copy-on-Write**: при изменении блока создаётся его копия, модифицируется, и только после успешной записи указатель переключается на новый блок. Это обеспечивает **атомарность** без двойной записи в журнал.

```bash
# Проверка режима CoW
btrfs filesystem show /mnt/data
```

### Сравнение журналируемых ФС

| ФС | Режимы журналирования | Восстановление после сбоя | Примечание |
| :--- | :--- | :--- | :--- |
| **ext4** | journal / ordered / writeback | Replay журнала (секунды) | Гибкий выбор режима |
| **XFS** | Только метаданные (ordered-подобный) | Replay log (секунды) | Высокая производительность, один режим |
| **Btrfs** | CoW (без журнала) | Атомарные транзакции | Самовосстановление, снапшоты |
| **ZFS** | Intent Log (ZIL) + CoW | Replay ZIL (секунды) | Максимальная надёжность |

## Практические сценарии

### Восстановление после сбоя с помощью журнала

При загрузке Linux автоматически проверяет «грязные» ФС:

```
[    2.145] EXT4-fs (sda1): recovery complete
[    2.146] EXT4-fs (sda1): mounted filesystem with ordered data mode
```

Строка `recovery complete` означает, что ядро replay-нуло журнал. Если журнал чист — сообщения нет.

**Ручная проверка журнала ext4:**

```bash
# Показать статус журнала
dumpe2fs /dev/sda1 | grep -i journal

# Вывод:
# Journal inode:            8
# Journal backup:           inode blocks
# Journal size:             128M
# Journal length:           32768
# Journal sequence:         0x0001a2b3
# Journal start:            0         ← 0 = журнал чист
```

Если `Journal start` ≠ 0 — в журнале есть незавершённые транзакции.

### Размер журнала и его влияние

Журнал ext4 по умолчанию занимает **128–512 МБ** (зависит от размера ФС).

```bash
# Проверить размер журнала
dumpe2fs /dev/sda1 | grep 'Journal size'

# Изменить размер журнала (ФС должна быть размонтирована)
tune2fs -J size=256 /dev/sda1
```

**Слишком маленький журнал:** частые checkpoint-ы, деградация производительности при интенсивной записи.

**Слишком большой журнал:** данные дольше остаются в журнале, выше риск потери при сбое до применения к основной ФС.

### Вынос журнала на отдельный носитель

**Сценарий:** Сервер БД на HDD. Журнал на том же диске → головки постоянно перемещаются между данными и журналом → просадки IOPS.

**Решение:** Журнал на SSD, данные на HDD.

```bash
# 1. Создать журнал на SSD (/dev/sdc1)
sudo mke2fs -t ext4 -O journal_dev /dev/sdc1

# 2. Создать ФС на HDD с внешним журналом (/dev/sdb1)
sudo mke2fs -t ext4 -J device=/dev/sdc1 /dev/sdb1

# Для существующей ФС:
sudo umount /dev/sdb1
sudo tune2fs -J device=/dev/sdc1 /dev/sdb1
sudo mount /dev/sdb1 /mnt/data
```

**Выигрыш:** Операции с метаданными (создание/удаление файлов) ускоряются в **2–5×** на HDD.

### Журналирование и fsck

| Ситуация | Без журналирования | С журналированием |
| :--- | :--- | :--- |
| Сбой питания | Полный `fsck` — сканирование всей ФС (минуты → часы) | Replay журнала — секунды |
| Чистая перезагрузка | `fsck` по расписанию (каждые 30 монтирований) | Журнал чист, replay не нужен |
| Повреждение журнала | `fsck` в обычном режиме | `e2fsck -f` — принудительная полная проверка |

**Отключение проверки по расписанию (только для ФС с журналированием):**

```bash
tune2fs -c 0 -i 0 /dev/sda1
# -c 0: отключить проверку по количеству монтирований
# -i 0: отключить проверку по времени
```

> **Важно:** Это безопасно только для журналируемых ФС. Для non-journaling ФС (ext2) регулярный `fsck` обязателен.

### Отключение журналирования

Возможно для ext4, но **не рекомендуется**:

```bash
sudo umount /dev/sda1
sudo tune2fs -O ^has_journal /dev/sda1
sudo e2fsck -f /dev/sda1  # обязательно после отключения
sudo mount /dev/sda1 /mnt/data
```

**Последствия:** ФС ведёт себя как ext2 — нет защиты от сбоев, после каждого некорректного отключения требуется полный `fsck`.

### Включение журналирования обратно

```bash
sudo umount /dev/sda1
sudo tune2fs -O has_journal /dev/sda1
sudo e2fsck -f /dev/sda1
sudo mount /dev/sda1 /mnt/data
```
