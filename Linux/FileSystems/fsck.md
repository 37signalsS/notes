# Проверка и восстановление целостности файловой системы (fsck)

## Определения

- **`fsck` (File System Check):** Стандартная утилита в Unix-подобных системах для проверки целостности файловой системы (ФС) и исправления обнаруженных ошибок. Является фронтендом (оберткой), который вызывает специализированные утилиты для конкретных типов ФС (например, `e2fsck` для ext4, `fsck.xfs` для XFS).
- **Коды возврата (Exit Codes):** Битовая маска результата выполнения:
  - `0`: Ошибок нет.
  - `1`: Ошибки найдены и исправлены.
  - `2`: Требуется перезагрузка системы.
  - `4`: Ошибки оставлены неисправленными.
  - `8`: Операционная ошибка (например, ФС смонтирована).
  - `128`: Ошибка разделяемой библиотеки.

## Основные концепции

### Безопасность выполнения

**Критическое правило:** `fsck` должна запускаться только на **размонтированной** файловой системе (или смонтированной в режиме `read-only`). Попытка исправления ошибок на работающей ФС с правами на запись приведет к необратимому повреждению данных.

### Автоматическая проверка при загрузке

Система инициирует проверку при загрузке в следующих случаях:

- ФС помечена как "грязная" (некорректное размонтирование/сбой питания).
- Достигнут лимит монтирований или интервал времени (для ext2/3/4).
- Порядок проверки определяется полем `<pass>` в файле [fstab](./mounting/fstab.md):
  - `0`: Не проверять.
  - `1`: Проверять первой (обычно только корень `/`).
  - `2`: Проверять после корня.

### Режимы работы

- **Автоматическое исправление (`-y` или `-a`):** Исправляет все ошибки без запроса подтверждения. Рекомендуется для неинтерактивных скриптов.
- **Безопасное исправление (`-p` — preen):** Автоматически исправляет только те ошибки, которые не требуют вмешательства администратора и не несут риска потери данных.
- **Только чтение (`-n`):** Выполняет диагностику без записи изменений. Безопасно для использования на смонтированных ФС.

## Практические сценарии

### Принудительный запуск проверки при следующей загрузке

Если невозможно размонтировать ФС (например, корень), следует запланировать проверку при старте системы.

**1. Через параметры загрузки ядра (GRUB):**
Добавьте параметры для форсирования проверки всеми системными инструментами:

```bash
fsck.mode=force fsck.repair=yes
```

**2. Через `tune2fs` (только для ext2/3/4):**
Обманите систему, установив счетчик монтирований выше лимита:

```bash
# Установить текущее число монтирований в 50 при лимите 30
sudo tune2fs -C 50 /dev/sdXN
```

### Проверка и восстановление XFS (`xfs_repair`)

В XFS утилита `fsck.xfs` не выполняет действий (так как XFS — журналируемая ФС с быстрым восстановлением при монтировании). Для глубокой проверки используется:

```bash
# Проверка и восстановление (требует размонтирования)
sudo xfs_repair /dev/sdXN

# Если журнал поврежден (последнее средство, возможна потеря данных)
sudo xfs_repair -L /dev/sdXN
```

### Проверка и восстановление Btrfs (`btrfs check`)

Для Btrfs используется встроенный инструментарий. Режим восстановления считается экспериментальным.

```bash
# Диагностика (безопасно)
sudo btrfs check /dev/sdXN

# Попытка исправления (рискованно, требует подтверждения)
sudo btrfs check --repair /dev/sdXN
```

> **Важно:** Перед использованием `--repair` на Btrfs необходимо создать посекторную копию раздела через [утилиту dd](./dd.md).

### Ручная интерактивная проверка

Если требуется контроль над каждым исправлением:

```bash
sudo fsck -r /dev/sdXN
```
