# Проверка и восстановление целостности файловой системы (fsck)

## Определения

- **`fsck` (File System Check):** Системная утилита в Unix-подобных ОС для проверки целостности файловых систем (ФС) и исправления структурных ошибок. Является высокоуровневым фронтендом (оберткой), который вызывает специализированные утилиты для конкретных типов ФС: `e2fsck` (ext2/3/4), `fsck.xfs` (XFS), `fsck.vfat` (FAT).
- **Суперблок (Superblock):** Критическая структура данных ФС, содержащая метаданные о самой ФС (размер, количество свободных блоков, точки монтирования). Повреждение суперблока делает ФС нечитаемой.
- **Коды возврата (Exit Codes):** Битовая маска результата выполнения:
  - `0`: Ошибок не обнаружено.
  - `1`: Ошибки найдены и успешно исправлены.
  - `2`: Система требует перезагрузки (изменения затронули корень или критические структуры).
  - `4`: Ошибки ФС оставлены неисправленными (требуется ручное вмешательство).
  - `8`: Операционная ошибка (например, ФС смонтирована в RW-режиме).
  - `16`: Ошибка использования или синтаксиса.
  - `32`: Проверка отменена пользователем.
  - `128`: Ошибка разделяемой библиотеки.

## Основные концепции

### Критические правила безопасности

1.  **Запрет на проверку смонтированных ФС:** `fsck` никогда не должна запускаться на файловой системе, смонтированной с правами на запись. Это гарантированно приведет к разрушению структур данных.
2.  **Режим Read-Only:** Допускается диагностика (`-n`) на смонтированной ФС, но результаты могут быть ложноположительными из-за активных дисковых операций.
3.  **Бэкап метаданных:** Перед выполнением операций восстановления на критически важных данных рекомендуется создать посекторный образ раздела через `dd` или `ddrescue`.

### Внутреннее устройство и работа fsck

#### Суперблок и резервные копии

Суперблок (superblock) — главная структура ФС, расположенная в фиксированном смещении от начала раздела:
- **ext4:** основной суперблок на смещении 1024 байт; резервные копии создаются каждые 32768 блоков (для блока 4K — примерно каждые 128 MB). Их количество зависит от размера ФС.
- **XFS:** суперблок хранится в двух местах (offset 0 и 65536) для отказоустойчивости; `xfs_repair` автоматически использует резервную копию, если основной поврежден.
- **Btrfs:** суперблоки реплицируются (обычно 3–4 копии); `btrfs check --super` позволяет проверить/восстановить конкретную копию.

#### Журналирование и его влияние на восстановление

Журналируемые ФС (ext4, XFS, Btrfs) минимизируют необходимость в полной проверке `fsck`:
- **ext4 (JBD2):** при монтировании выполняется **Replay журнала** — доигрывание незавершенных транзакций. Полный `e2fsck` требуется только при повреждении журнала или логических несоответствиях метаданных.
- **XFS:** аналогичный механизм — **Log Replay** при монтировании. `xfs_repair` требуется только если ФС не монтируется или replay не помогает.
- **Btrfs:** scrub проверяет контрольные суммы CoW; `btrfs check --repair` применяется только при невозможности монтирования.

#### Этапы проверки e2fsck (расширенный разбор)

1.  **Phase 1:** Проверка inode, блоков и размеров. Поиск конфликтов между inode, проверка счетчиков ссылок.
2.  **Phase 2:** Проверка структуры каталогов. Верификация связей между inode и именами файлов, проверка корректности dentry.
3.  **Phase 3:** Проверка связности каталогов. Поиск «осиротевших» каталогов, восстановление `.` и `..`.
4.  **Phase 4:** Проверка счетчиков ссылок (Link counts). Исправление расхождений между реальным количеством ссылок и данными inode; перемещение файлов в `/lost+found` при невозможности восстановления связи.
5.  **Phase 5:** Проверка информации о группах цилиндров (групповых дескрипторов) и битовых карт блоков/inode. Коррекция счетчиков свободных блоков и inodes.

### Механизмы автоматической проверки

В современных дистрибутивах с **systemd** проверка управляется сервисом `systemd-fsck@.service`.

- **Триггеры проверки:**
  - ФС помечена как «Dirty» (некорректное размонтирование, сбой питания).
  - Достигнут интервал времени или лимит монтирований.
- **Управление через `tune2fs` (для ext4):**
  - `sudo tune2fs -c 30 /dev/sdXN` — проверять каждые 30 монтирований.
  - `sudo tune2fs -i 1m /dev/sdXN` — проверять раз в месяц.
- **Конфигурация (fstab):** Поле `<pass>` (6-я колонка) в `/etc/fstab` определяет очередь:
  - `1`: Первоочередная проверка (только для корня `/`).
  - `2`: Последовательная проверка после корня.
  - `0`: Проверка отключена (рекомендуется для сетевых ФС и образов).

## Практические сценарии

### 1. Планирование проверки при следующей загрузке

Для проверки корневого раздела используются параметры загрузки ядра.

**Через GRUB (редактирование строки `linux`):**
```bash
fsck.mode=force fsck.repair=yes
```
- `fsck.mode=force` — принудительная проверка, даже если ФС чистая.
- `fsck.repair=yes` — автоматическое исправление всех найденных ошибок.

### 2. Восстановление ext4 при повреждении суперблока

Используются резервные копии суперблока, которые создаются автоматически при форматировании.

```bash
# 1. Поиск расположения запасных суперблоков
sudo mke2fs -n /dev/sdXN

# 2. Попытка восстановления с использованием конкретного суперблока
sudo e2fsck -b 32768 /dev/sdXN
```

### 3. Проверка без простоя через LVM Snapshot

Безопасный способ проверить ФС на работающем сервере:
1.  Создать снапшот тома: `lvcreate -s -L 1G -n check_snap /dev/vg/live_lv`.
2.  Запустить `fsck` на снапшоте: `e2fsck -f /dev/vg/check_snap`.
3.  Если ошибки найдены на снапшоте — планировать остановку сервиса для исправления оригинала.

### 4. Особенности восстановления XFS (`xfs_repair`)

XFS не использует `fsck` для исправления. При монтировании она выполняет автоматический Replay журнала. Если это не помогает:

```bash
# Проверка (размонтированной ФС)
sudo xfs_repair /dev/sdXN

# Если журнал поврежден (КРАЙНЯЯ МЕРА, приводит к потере последних транзакций)
sudo xfs_repair -L /dev/sdXN
```

**Поведение `fsck` на XFS:** если запустить `fsck` на разделе XFS, утилита не пытается исправить ФС, а выводит подсказку с рекомендацией использовать `xfs_repair`.

**Структура проверок `xfs_repair`:** утилита последовательно выполняет 8 проверок (inode и blockmap, inode allocation map, размеры, каталоги, pathname, счётчики ссылок, freemap, суперблок). При наличии orphaned файлов они помещаются в `lost+found`.

### 5. Особенности Btrfs (`btrfs check`)

В Btrfs для исправления используется `btrfs check`. 
- **Scrub:** Рекомендуется для профилактики (фоновая проверка контрольных сумм на смонтированной ФС): `btrfs scrub start /mnt/btrfs`.
- **Repair:** Использовать `--repair` только в крайнем случае, когда ФС не монтируется и `btrfs restore` не помогает.

```bash
# Проверка без изменений
sudo btrfs check /dev/sdXN

# Попытка восстановления структур (опасно!)
sudo btrfs check --repair /dev/sdXN
```

### 6. Автоматическая проверка через systemd-таймер

Настройка регулярной проверки не корневых ФС без вмешательства в `/etc/fstab`:

```bash
# Создание сервиса
cat << 'EOF' | sudo tee /etc/systemd/system/fsck-data.service
[Unit]
Description=Fsck data partition
DefaultDependencies=no
After=local-fs.target

[Service]
Type=oneshot
ExecStart=/usr/bin/fsck -y -C0 /dev/vg_data/lv_data
EOF

# Создание таймера (ежемесячно)
cat << 'EOF' | sudo tee /etc/systemd/system/fsck-data.timer
[Unit]
Description=Monthly fsck for data partition

[Timer]
OnCalendar=monthly
Persistent=true

[Install]
WantedBy=timers.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now fsck-data.timer
```

### 7. Диагностика смонтированной ФС (без изменений)

Безопасная проверка на работающей системе для оценки необходимости полной проверки:

```bash
# Только чтение, автоматический нет на все вопросы
sudo fsck -n /dev/sdXN

# Для XFS (только диагностика)
sudo xfs_repair -n /dev/sdXN
```

### 8. Проверка ФС в контейнере (Docker/LXC)

Для контейнеров с bind-mounted разделами проверка выполняется на хосте:

```bash
# 1. Определение устройств, используемых контейнером
docker inspect --format '{{.Mounts}}' mycontainer

# 2. Остановка контейнера и проверка на хосте
docker stop mycontainer
sudo fsck -y /dev/sdb1

# 3. Запуск контейнера
docker start mycontainer
```

### 9. Проверка после аварийного отключения питания

Стандартный протокол для серверов, восстановленных после сбоя питания:

```bash
# 1. Проверка SMART-статуса дисков (приоритет: проверка железа перед ФС)
sudo smartctl -a /dev/sdX | grep -E 'SMART overall|Reallocated|Current_Pending|Offline_Uncorrectable'

# 2. Проверка журналов ядра на предмет I/O ошибок
dmesg -T | grep -Ei 'EXT4-fs error|XFS|I/O error|Buffer I/O|read-only|abort' | tail -20

# 3. Принудительная проверка всех локальных ФС
sudo fsck -y -f /dev/sdX1
sudo fsck -y -f /dev/sdX2

# 4. Для XFS
sudo xfs_repair /dev/sdX3
```

### 10. Работа с RAID и fsck

**Software RAID (mdadm):**
```bash
# Проверка ФС на массиве (устройство /dev/md0)
sudo fsck -f /dev/md0

# Проверка после замены диска и rebuild
watch -n 5 'cat /proc/mdstat'
sudo fsck -f /dev/md0
```

**Hardware RAID:** проверка выполняется на уровне LUN (логического диска), представляемого контроллером.

### 11. Проверка зашифрованных ФС (LUKS)

LUKS-контейнер должен быть расшифрован перед проверкой:

```bash
# 1. Открытие контейнера
sudo cryptsetup open /dev/sda3 cryptdata

# 2. Проверка ФС внутри контейнера
sudo e2fsck -f /dev/mapper/cryptdata
# Или для LVM внутри LUKS:
sudo e2fsck -f /dev/vg_data/lv_crypto

# 3. Закрытие контейнера
sudo cryptsetup close cryptdata
```

### 12. Мониторинг и анализ результатов проверки

```bash
# Просмотр логов systemd-fsck
journalctl -u systemd-fsck -b

# Поиск ошибок fsck в syslog
grep -E 'fsck|e2fsck|xfs_repair' /var/log/syslog | tail -20

# Анализ кодов возврата (пример для скрипта)
result=$(sudo fsck -n /dev/sdXN 2>&1)
exit_code=$?
if [ $exit_code -eq 0 ]; then
    echo "ФС чистая"
elif [ $exit_code -eq 1 ]; then
    echo "Найдены ошибки, требуется исправление"
elif [ $exit_code -eq 4 ]; then
    echo "Ошибки оставлены без исправления — требуется ручное вмешательство"
fi
```

## Троублшутинг

### Типичные ошибки и решения

| Ошибка / Симптом | Причина | Решение |
|------------------|---------|---------|
| `fsck` падает с «Read-only file system» | ФС смонтирована в RW или защищена от записи | Перемонтировать в RO: `mount -o remount,ro /mountpoint` или использовать rescue-окружение |
| `fsck` сообщает «Wrong filesystem type» | Указано неверное устройство или суперблок поврежден | Проверить устройство через `blkid`, для ext4 попробовать резервный суперблок (`e2fsck -b <backup>`) |
| `xfs_repair` зависает или падает | Повреждение метаданных на критическом уровне | Создать образ через `ddrescue`, работать с образом; проверить состояние диска SMART |
| `btrfs check --repair` удаляет файлы | Более безопасная альтернатива: `btrfs restore` для извлечения данных без изменения ФС | Использовать `btrfs restore` на копии образа |
| `fsck` находит ошибки, но они возвращаются | Неисправность диска (bad sectors) или контроллера | Проверить `dmesg` на I/O errors, заменить диск, выполнить `fsck` после замены |
| `superblock corrupted` для ext4 | Основной суперблок нечитаем | Восстановить с резервного: `e2fsck -b 32768 /dev/sdXN` |
| `orphaned inodes` в большом количестве | Аварийное отключение питания во время активной записи | `fsck -y` исправит; для профилактики использовать journaling ФС |
| `free blocks/inodes count wrong` | Расхождение битовых карт и реального состояния | `fsck -y` исправит счетчики |
| `inode bitmap differences` | Повреждение bitmap-области | `fsck -y` перестроит bitmap из inode |

### Когда fsck не помогает

- **Физическое повреждение диска:** если `smartctl` показывает `Reallocated_Sector_Ct` или `Current_Pending_Sector` > 0 — сначала замените диск.
- **Повреждение на уровне LVM/RAID:** проверьте `pvscan`, `vgscan`, `cat /proc/mdstat` перед `fsck`.
- **Полное разрушение метаданных:** используйте `photorec`, `testdisk` или `extundelete` (для ext4) для восстановления файлов напрямую из данных.

## Валидация и верификация после восстановления

```bash
# 1. Проверка монтирования
sudo mount -o ro /dev/sdXN /mnt/check
df -h /mnt/check

# 2. Проверка целостности каталогов
sudo find /mnt/check -xdev -type f | wc -l
sudo find /mnt/check -xdev -type f -exec file {} \; | grep -v 'data' | head -20

# 3. Проверка lost+found
ls -la /mnt/check/lost+found
file /mnt/check/lost+found/* | head -20

# 4. Проверка XFS (если применимо)
sudo xfs_check /dev/sdXN

# 5. S.M.A.R.T. проверка после восстановления
sudo smartctl -H /dev/sdX
```

## Особые случаи и ограничения

### Файловые системы, не требующие fsck

- **ZFS / Btrfs (CoW):** обеспечивают целостность на уровне блоков; `fsck` не требуется при нормальном отмонтировании. `btrfs check` применяется только при невозможности монтирования.
- **Сетевые ФС (NFS, CIFS/SMB):** целостность проверяется на сервере; `fsck` на клиенте не применяется.

### Ограничения по размеру

- **ext4:** время проверки растет линейно с размером ФС. Для разделов >1 TB рекомендуется использовать `e2fsck -f` в maintenance-окно.
- **XFS:** `xfs_repair` требует в 2–3 раза больше свободного места, чем размер ФС (для временных файлов).
- **Btrfs:** `btrfs check --repair` на разделах >10 TB может занимать часы; предпочтительнее `btrfs restore` для извлечения данных.

### Шифрованные контейнеры (LUKS)

Всегда проверяйте ФС **после** расшифровки контейнера:
```bash
# НЕПРАВИЛЬНО: fsck на /dev/sda3 (LUKS-раздел)
sudo fsck /dev/sda3

# ПРАВИЛЬНО: fsck на открытом маппере
sudo cryptsetup open /dev/sda3 cryptdata
sudo fsck -f /dev/mapper/cryptdata
```

### Файловые системы в образах

```bash
# Проверка образа диска через loopback
sudo losetup -fP disk.img
sudo fsck -f /dev/loop0p1
sudo losetup -d /dev/loop0
```

## Лучшие практики

### Планирование и предотвращение

1.  **Используйте журналируемые ФС** (ext4, XFS) для всех данных, где важна целостность.
2.  **Настройте автоматическую проверку** через `tune2fs -i` и `-c` для ext4; для XFS/Btrfs полагайтесь на journal replay.
3.  **Мониторьте результат fsck** через `journalctl -u systemd-fsck` и алерты на коды возврата ≠ 0.

### Подготовка к восстановлению

1.  **Создавайте образы** критически важных разделов через `ddrescue` перед операциями `fsck`.
2.  **Проверяйте состояние диска** (`smartctl`, `dmesg`) перед `fsck` — если диск умирает, `fsck` может усугубить ситуацию.
3.  **Тестируйте восстановление** на стенде: регулярно проверяйте резервные копии и процедуры.

### Документация

- Ведите журнал всех операций `fsck` (дата, устройство, код возврата, действия).
- Для серверов критически важных данных создайте playbook/runbook с шагами восстановления.
