# Виртуальная файловая система /proc (procfs)

## Определения

- **procfs (Process Filesystem):** Псевдофайловая система в Linux (обычно монтируется в `/proc`), предоставляющая интерфейс к внутренним структурам данных ядра. Служит основным механизмом экспорта системной статистики и информации о процессах в пространство пользователя без использования системных вызовов специального назначения.
- **PID (Process Identifier):** Уникальный числовой идентификатор, присваиваемый ядром каждой активной задаче (процессу или потоку).
- **Control Plane ядра:** Роль `/proc` как интерфейса для изменения параметров ядра «на лету» через подкаталог `/proc/sys/` (программный бэкенд для утилиты `sysctl`).

## Основные концепции

### Механика работы
Файлы в `/proc` не существуют на диске. Это «окна» в оперативную память ядра. При чтении файла (например, `cat /proc/meminfo`) ядро динамически собирает данные и форматирует их в текст.
- **Интерфейс `seq_file`:** Большинство файлов в `/proc` используют этот интерфейс ядра для последовательного вывода больших объемов данных, что позволяет эффективно читать их по частям.
- **Неатомарность:** Чтение больших файлов (например, `smaps`) не является атомарным. Если состояние процесса изменится во время чтения, данные могут быть слегка рассогласованы.

### Иерархия и структура
1.  **Каталоги процессов (`/proc/[PID]/`):** Содержат информацию о конкретном процессе. Создаются и удаляются ядром автоматически.
2.  **Системная статистика:** Файлы в корне `/proc`, описывающие глобальное состояние ОС (CPU, память, диски, прерывания).
3.  **Параметры ядра (`/proc/sys/`):** Единственная часть `/proc`, доступная для записи (при наличии прав root), позволяющая менять настройки стека TCP/IP, виртуальной памяти и планировщика.
4.  **Специальные ссылки:**
    - **`/proc/self/`:** Ссылка на каталог процесса, который в данный момент обращается к `/proc`.
    - **`/proc/thread-self/`:** Ссылка на данные текущего потока.
    - **`/proc/mounts`:** Ссылка на `/proc/self/mounts`, показывающая список всех смонтированных ФС.

## Системная статистика (Корень /proc)

| Файл | Назначение для SRE / Системного инженера |
| :--- | :--- |
| `meminfo` | Детальная статистика RAM (Available, Dirty, Slab, HugePages). [Подробнее: proc_meminfo.md](../Diagnostics/Memory/proc_meminfo.md). |
| `cpuinfo` | Характеристики процессоров (модель, флаги AES/VMX, топология, баги CPU). |
| `stat` | Суммарная статистика: время в user/system/idle, время загрузки (btime), количество прерываний и контекстных переключений. |
| `loadavg` | Load Average (1/5/15 мин), количество активных задач и PID последнего созданного процесса. |
| `uptime` | Общее время работы системы и время простоя (idle time) в секундах. |
| `interrupts` | Количество прерываний по типам и по ядрам CPU (помогает выявить "прерывистые штормы"). |
| `softirqs` | Статистика программных прерываний (важно для диагностики сетевых задержек). |
| `diskstats` | Метрики ввода-вывода для всех блочных устройств. [Подробнее: proc_diskstats.md](../Diagnostics/Performance/DiskIO/proc_diskstats.md). |
| `partitions` | Список всех обнаруженных разделов и их размер в блоках. |
| `version` | Версия ядра, версия GCC, использованная для сборки, и дата сборки. |

## Информация о процессах (/proc/[PID]/)

| Файл | Описание контента и применение |
| :--- | :--- |
| `cmdline` | Полная строка запуска процесса (аргументы разделены `\0`). |
| `environ` | Переменные окружения процесса. |
| `exe` | Символическая ссылка на реальный исполняемый бинарник процесса. Ключевая точка проверки при расследовании подозрительных процессов (см. сценарий 5). |
| `cwd` | Символическая ссылка на текущий рабочий каталог процесса. |
| `root` | Символическая ссылка на корень ФС, как его видит процесс (отличается от `/` в chroot и контейнерах). |
| `fd/` | Подкаталог со ссылками на открытые дескрипторы (файлы, сокеты, epoll). |
| `status` | Человекочитаемый свод: UID/GID, лимиты, маски сигналов, волонтарные переключения контекста. |
| `maps` / `smaps` | Карта памяти. `smaps` дает детальный расчет PSS/RSS для каждого сегмента. |
| `smaps_rollup` | (Linux 4.14+) Агрегированная статистика памяти процесса. Читается быстрее, чем полный `smaps`. |
| `io` | I/O статистика: сколько байт реально прочитано/записано на диск vs из кэша. |
| `stack` | Текущий стек вызовов процесса в режиме ядра (поиск причин зависания в состоянии **D**). |
| `wchan` | Название функции ядра, в которой процесс ожидает ресурса. |
| `oom_score` | Текущий «рейтинг смерти» процесса (от 0 до 1000). Чем выше, тем вероятнее его убьет OOM Killer. |
| `oom_score_adj` | Коэффициент для ручной корректировки `oom_score` (от -1000 до 1000). |
| `ns/` | Ссылки на Namespaces (изоляцию) процесса. См. [Пространства имен](../Core/namespaces.md). |
| `task/` | Каталог со статистикой по каждому потоку (LWP) данного процесса. |

## Сеть и оборудование

- **`/proc/net/`:** Каталог со статистикой сетевого стека.
    - `dev`: Метрики сетевых интерфейсов (bytes, packets, errors, drops) для RX и TX.
    - `snmp`: Статистика протоколов IP, ICMP, TCP, UDP.
    - `tcp` / `udp`: Список открытых сокетов (в шестнадцатеричном формате).
- **`/proc/swaps`:** Информация об активных областях подкачки.
- **`/proc/mounts`:** Текущее состояние всех точек монтирования. Для более детального анализа в контейнерах рекомендуется использовать `/proc/self/mountinfo`.

## Безопасность и ограничения

### Параметр hidepid
Для предотвращения утечки информации в многопользовательских средах или контейнерах монтирование `/proc` поддерживает опцию `hidepid`:
- `hidepid=off` (0): По умолчанию. Все видят всё.
- `hidepid=1`: Пользователи не видят каталоги PID других пользователей (но процессы видны в `ps`).
- `hidepid=2` / `invisible`: Полная невидимость процессов других пользователей. С версии **Linux 5.9** добавлена опция `invisible`, которая делает PID-каталоги скрытыми даже для системных вызовов типа `getdents`.

### Ограничения производительности
Хотя чтение из `/proc` быстрое, частый опрос тысяч файлов (например, `smaps` для каждого процесса в системе) может создать заметную нагрузку на CPU. Современные инструменты (например, `Prometheus Node Exporter`) оптимизируют этот процесс.

## Практические сценарии

### 1. Поиск причины ожидания процесса (Wait Channel)
Если процесс «завис» в состоянии Uninterruptible Sleep (**D**), можно узнать, что именно он ждет:
```bash
cat /proc/[PID]/wchan
# → nfs_wait_bit_killable (ожидание ответа от сетевой ФС NFS)
```

### 2. Проверка доступной памяти для приложений
`MemFree` в `/proc/meminfo` часто вводит в заблуждение. SRE должны ориентироваться на `MemAvailable`:
```bash
grep MemAvailable /proc/meminfo
```

### 3. Анализ сетевых ошибок на интерфейсе
Прямое чтение счетчиков без использования утилит типа `ip` или `ifconfig`:
```bash
cat /proc/net/dev | grep eth0
```

### 4. Восстановление удаленного файла
Если файл удален (`rm`), но процесс его держит, его можно скопировать из `/proc/[PID]/fd/`. Подробности см. в [Логическое восстановление данных](./data_recovery.md#1-восстановление-файла-открытого-процессом).

### 5. Идентификация реального исполняемого файла процесса
Строка процесса в `ps` и `top` берется из `argv[0]` (файл `cmdline`) и может быть легко подменена самим приложением или не отражать реальный путь к бинарнику. Ссылка `exe`, наоборот, поддерживается ядром и всегда указывает на фактический исполняемый файл, который был загружен через `execve()`:

```bash
readlink -f /proc/<PID>/exe
# → /usr/sbin/nginx
```

Флаг `-f` разрешает все компоненты пути в канонический абсолютный путь.

Типовой сценарий: процесс выглядит как обычный `nginx` в выводе `ps`, но ссылка `exe` указывает на бинарник в неожиданном месте (`/tmp/`, `/dev/shm/`, домашний каталог пользователя) — признак маскировки под легитимный сервис или запуска не той версии, которая предполагается. Дополнительные проверки:

```bash
# Бинарник удален с диска, но процесс еще работает — ядро помечает ссылку суффиксом (deleted)
readlink /proc/<PID>/exe
# → /usr/local/bin/agent (deleted)

# Сверка контрольной суммы с эталонным пакетом (для выявления модифицированного бинарника)
sha256sum "$(readlink -f /proc/<PID>/exe)"
dpkg -V nginx   # Debian/Ubuntu: проверка файлов пакета по базе
rpm -V nginx    # RHEL/Alma/Rocky: аналогичная проверка

# Рабочий каталог и корень ФС процесса дополняют картину расследования
ls -l /proc/<PID>/cwd /proc/<PID>/root
```

Если бинарник удален с диска, сам файл еще можно восстановить через `/proc/[PID]/exe` (см. сценарий 4 и [Устранение неисправностей процессов](../Core/processes/Troubleshooting/index.md)). Для проверки привилегий такого процесса (file capabilities его бинарника) используйте `getcap $(readlink -f /proc/<PID>/exe)` — см. [Linux Capabilities](../Security/Mechanisms/Capabilities.md).
