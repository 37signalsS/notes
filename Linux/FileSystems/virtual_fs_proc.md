# Виртуальная файловая система /proc (procfs)

## Определения

- **procfs (Process Filesystem):** Псевдофайловая система в Linux (обычно монтируется в `/proc`), предоставляющая интерфейс к внутренним структурам данных ядра. Служит основным механизмом экспорта системной статистики и информации о процессах в пространство пользователя без использования системных вызовов специального назначения.
- **PID (Process Identifier):** Уникальный числовой идентификатор, присваиваемый ядром каждой активной задаче (процессу или потоку).
- **Control Plane ядра:** Роль `/proc` как интерфейса для изменения параметров ядра «на лету» через подкаталог `/proc/sys/` (программный бэкенд для утилиты `sysctl`). Детали архитектуры см. в [Настройка параметров ядра (sysctl)](../Core/kernel/sysctl.md).
- **seq_file:** Внутренний интерфейс ядра Linux для форматирования и последовательного чтения больших объемов данных из ядерных структур. Используется большинством файлов `/proc` для предотвращения переполнения буферов пользовательского пространства и опциональной поддержки `poll()`/`select()`.
- **hidepid:** Опция монтирования procfs, ограничивающая видимость каталогов `/proc/[PID]/` для непривилегированных пользователей. Критична для безопасности в многопользовательских средах и контейнерах.
- **subset:** Опция монтирования procfs, ограничивающая набор видимых подкаталогов (например, `subset=pid,net` скрывает `fs`, `sys`, `kernel`). Используется для минимизации поверхности атаки в контейнерах.
- **cgroup namespace:** Изоляция представления cgroup-иерархии. В контейнере `/proc/self/cgroup` показывает только видимые корни cgroup, а не полную иерархию хоста. См. [Пространства имен](../Core/namespaces.md).

## Монтирование и опции procfs

procfs монтируется автоматически systemd или ядром. Вручную:

```bash
mount -t proc proc /proc
```

### Опции монтирования

| Опция | Значение | Применение |
| :--- | :--- | :--- |
| `hidepid=off` (0) | По умолчанию. Все видят всё. | Отладка, single-user. |
| `hidepid=1` | Скрывает `/proc/[PID]/` чужих пользователей. Процессы видны в `ps`. | Базовая изоляция в shared-hosting. |
| `hidepid=2` / `invisible` | Полная невидимость чужих PID, даже через `getdents()`. С Linux 5.9 поддерживается `invisible`. | Compliance, hardened-хосты. |
| `gid=<gid>` | Указанная группа видит все PID даже при `hidepid=1/2`. | Monitoring, audit-группы. |
| `subset=<list>` | Ограничивает видимые подкаталоги. Например: `subset=pid,net`. | Контейнеры, минимальные rootfs. |
| `nosuid` | Игнорирует SUID-биты на файлах в `/proc`. | Безопасность. |
| `noexec` | Запрещает выполнение бинарников из `/proc`. | Безопасность. |
| `nodev` | Игнорирует символьные/блочные устройства в `/proc`. | Безопасность. |

**Пример для контейнера (hardened):**

```bash
mount -t proc proc /proc -o nosuid,noexec,nodev,hidepid=2,subset=pid,net
```

## Основные концепции

### Механика работы

Файлы в `/proc` не существуют на диске. Это «окна» в оперативную память ядра. При чтении файла (например, `cat /proc/meminfo`) ядро динамически собирает данные и форматирует их в текст. Детали реализации смотрите в справочнике [proc_meminfo.md](../Diagnostics/Memory/proc_meminfo.md).

- **Интерфейс `seq_file`:** Большинство файлов в `/proc` используют этот интерфейс ядра для последовательного вывода больших объемов данных, что позволяет эффективно читать их по частям.
- **Неатомарность:** Чтение больших файлов (например, `smaps`) не является атомарным. Если состояние процесса изменится во время чтения, данные могут быть слегка рассогласованы.
- **VFS-интеграция:** `/proc` регистрируется в VFS как обычная файловая система, но ее операции `read`/`write` перенаправляются в обработчики ядра (`proc_ops`), а не на диск.

### Иерархия и структура

1.  **Каталоги процессов (`/proc/[PID]/`):** Содержат информацию о конкретном процессе. Создаются и удаляются ядром автоматически.
2.  **Системная статистика:** Файлы в корне `/proc`, описывающие глобальное состояние ОС (CPU, память, диски, прерывания).
3.  **Параметры ядра (`/proc/sys/`):** Единственная часть `/proc`, доступная для записи (при наличии прав root), позволяющая менять настройки стека TCP/IP, виртуальной памяти и планировщика.
4.  **Специальные ссылки:**
    - **`/proc/self/`:** Ссылка на каталог процесса, который в данный момент обращается к `/proc`.
    - **`/proc/thread-self/`:** Ссылка на данные текущего потока.
    - **`/proc/mounts`:** Ссылка на `/proc/self/mounts`, показывающая список всех смонтированных ФС.

| `limits` | Текущие лимиты ресурсов (ulimit-style) для процесса. |
| `coredump_filter` | Битовые флаги, определяющие, какие сегменты памяти попадут в core dump. |

## Сеть и оборудование

- **`/proc/net/`:** Каталог со статистикой сетевого стека.
    - `dev`: Метрики сетевых интерфейсов (bytes, packets, errors, drops) для RX и TX.
    - `sockstat`: Сводка по сокетам: allocated, in-use, TCP, UDP, RAW, FRAG, TCP memory.
    - `arp`: Таблица ARP (IP → MAC). Устаревает в пользу `ip neigh`.
    - `route`: Таблица маршрутизации. Устаревает в пользу `ip route`.
    - `tcp` / `udp`: Список открытых сокетов (в шестнадцатеричном формате).
    - `netstat`: Расширенная статистика TCP/UDP (retransmits, listens overflows, syncookies).
    - `ip_tables_names`, `nf_conntrack`: Активные модули netfilter и счетчик conntrack.
- **`/proc/swaps`:** Информация об активных областях подкачки.
- **`/proc/mounts`:** Текущее состояние всех точек монтирования. Для более детального анализа в контейнерах рекомендуется использовать `/proc/self/mountinfo`.

## cgroup и контроль ресурсов

Ядро экспортирует информацию о принадлежности процессов к cgroup через `/proc`:

- **`/proc/self/cgroup`:** Текущий путь cgroup для вызывающего процесса. Формат зависит от версии cgroup (v1 vs v2). См. [Пространства имен](../Core/namespaces.md).
- **`/proc/[PID]/cgroup`:** cgroup-принадлежность конкретного процесса.

**Для диагностики контейнеров:** Внутри контейнера `/proc/self/cgroup` показывает только видимые через cgroup namespace корни. На хосте — полный путь.

```bash
# На хосте
cat /proc/self/cgroup
# → 0::/system.slice/docker-<id>.scope

# Внутри контейнера (cgroup namespace + правильный монтирование)
cat /proc/self/cgroup
# → 0::/
```

## Безопасность и ограничения

### Параметр hidepid

Для предотвращения утечки информации в многопользовательских средах или контейнерах монтирование `/proc` поддерживает опцию `hidepid`:
- `hidepid=off` (0): По умолчанию. Все видят всё.
- `hidepid=1`: Пользователи не видят каталоги PID других пользователей (но процессы видны в `ps`).
- `hidepid=2` / `invisible`: Полная невидимость процессов других пользователей. С версии **Linux 5.9** добавлена опция `invisible`, которая делает PID-каталоги скрытыми даже для системных вызовов типа `getdents`.

### Опция subset

С ядра 5.8 procfs поддерживает `subset=` для ограничения видимых подкаталогов:

```bash
# Только PID и сеть (минимум для большинства диагностических утилит)
mount -t proc proc /proc -o subset=pid,net

# Полный набор (по умолчанию)
mount -t proc proc /proc -o subset=pid,net,fs,sys,kernel,tracing
```

### Защита ядра через sysctl

Некоторые параметры безопасности напрямую влияют на содержимое `/proc`:

| Параметр | Влияние на /proc | Рекомендуемое значение |
| :--- | :--- | :--- |
| `kernel.kptr_restrict` | Скрывает адреса ядра в `/proc/kallsyms`. | `2` |
| `kernel.dmesg_restrict` | Запрет чтения `dmesg` и `/proc/kmsg` обычными пользователями. | `1` |
| `kernel.yama.ptrace_scope` | Ограничивает `ptrace` (в т.ч. чтение `/proc/PID/*` чужими процессами). | `2` или `3` |

### Ограничения производительности

Хотя чтение из `/proc` быстрое, частый опрос тысяч файлов (например, `smaps` для каждого процесса в системе) может создать заметную нагрузку на CPU. Современные инструменты (например, `Prometheus Node Exporter`) оптимизируют этот процесс. Детали производительности см. в [proc_meminfo.md — Best Practices](../Diagnostics/Memory/proc_meminfo.md#best-practices).

## Практические сценарии

### 1. Поиск причины ожидания процесса (Wait Channel)

Если процесс «завис» в состоянии Uninterruptible Sleep (**D**), можно узнать, что именно он ждет:

```bash
cat /proc/[PID]/wchan
# → nfs_wait_bit_killable (ожидание ответа от сетевой ФС NFS)
```

### 2. Проверка доступной памяти для приложений

`MemFree` в `/proc/meminfo` часто вводит в заблуждение. SRE должны ориентироваться на `MemAvailable`. Детали: [proc_meminfo.md](../Diagnostics/Memory/proc_meminfo.md).

```bash
grep MemAvailable /proc/meminfo
```

### 3. Анализ сетевых ошибок на интерфейсе

Прямое чтение счетчиков без использования утилит типа `ip` или `ifconfig`:

```bash
cat /proc/net/dev | grep eth0
```

### 4. Восстановление удаленного файла

Если файл удален (`rm`), но процесс его держит, его можно скопировать из `/proc/[PID]/fd/`. Подробности см. в [Логическое восстановление данных](./data_recovery.md#1-восстановление-файла-открытого-процессом).

### 5. Идентификация реального исполняемого файла процесса

Строка процесса в `ps` и `top` берется из `argv[0]` (файл `cmdline`) и может быть легко подменена. Ссылка `exe`, наоборот, поддерживается ядром и всегда указывает на фактический исполняемый файл:

```bash
readlink -f /proc/<PID>/exe
# → /usr/sbin/nginx
```

Дополнительные проверки:

```bash
# Бинарник удален с диска
readlink /proc/<PID>/exe
# → /usr/local/bin/agent (deleted)

# Сверка контрольной суммы
sha256sum "$(readlink -f /proc/<PID>/exe)"
dpkg -V nginx   # Debian/Ubuntu
rpm -V nginx    # RHEL/Alma/Rocky

# Рабочий каталог и корень ФС
ls -l /proc/<PID>/cwd /proc/<PID>/root
```

### 6. Аудит безопасности: loginuid и цепочка привилегий

`/proc/PID/loginuid` показывает, какой пользователь инициировал сессию. Это значение не меняется при `sudo` или `su`, что делает его критичным для non-repudiation:

```bash
# Проверка: процесс запущен через sudo или напрямую
cat /proc/<PID>/loginuid
# → 1000 (обычный пользователь)

cat /proc/<PID>/status | grep -E "^Uid|^Gid"
# → Uid: 0 0 0 0 (root, но loginuid=1000)
```

Если `loginuid != 0` у процесса, работающего от root — это признак использования `sudo` или setuid. Для аудите изменений смотрите audit log.

### 7. Диагностика зависаний без strace: /proc/PID/syscall

Если процесс в состоянии **D** (Uninterruptible Sleep) или **S** (Interruptible Sleep), `strace` может не работать. Файл `syscall` показывает текущий системный вызов:

```bash
# Процесс завис при чтении NFS
cat /proc/<PID>/syscall
# → 0 0x7fffd1234567 0x1 0x0 0x0 0x7fffd1234000 0x55 0x0 0x0 0x0 0x0 0x0

# Толкование: syscall NR=0 (read), arg1=fd, arg2=buf, arg3=count
# См. arch/x86/entry/syscalls/syscall_64.tbl для номеров
```

**Альтернатива:** `perf trace -p <PID>` или `bpftrace` для мониторинга syscall без attach.

### 8. Обнаружение escape из контейнера через mountinfo

Если внутри контейнера `/proc/self/mountinfo` показывает точки монтирования хоста (например, `/sys`, `/proc` хоста, корневой раздел с `shared` propagation) — контейнер потенциально скомпрометирован:

```bash
# ВНУТРИ контейнера (норма)
cat /proc/self/mountinfo | grep -E " / | /proc | /sys "
# → 19 26 0:19 / / rw,relatime - overlay ...

# ПОДОЗРИТЕЛЬНО: виден корневой раздел хоста
cat /proc/self/mountinfo | grep " / "
# → 252 0 8:1 / / rw,relatime - ext4 ...
```

### 9. Тюнинг TCP: диагностика retransmits через /proc/net/netstat

Прямой доступ к TCP-метрикам без `ss` или `netstat`:

```bash
# Retransmits и listens overflows
grep -E "RetransSegs|ListenOverflows|ListenDrops" /proc/net/netstat
# → TcpExt: RetransSegs 1423 ListenOverflows 89 ...

# Детализация по сокетам (в формате ss)
cat /proc/net/tcp | awk 'NR>1 {print $4}' | cut -d: -f2 | \
  xargs -I{} printf "%d\n" {} | sort | uniq -c | sort -nr | head
```

### 10. Анализ сокетной памяти через /proc/net/sockstat

`sockstat` показывает распределение памяти по типам сокетов:

```bash
cat /proc/net/sockstat
# skmem alloc: 45 32 45 32  # allocated, memory, TCP memory, TCP rmem
# TCP: inuse 150 orphan 0 tw 12 alloc 45 mem 3
# UDP: inuse 25 mem 1
# RAW: inuse 0
# UDPLITE: inuse 0
# PACKET: inuse 10
# ...
```

Если `TCP mem` растет без остановки — возможна утечка в kernel TCP-стеке или flood-атака.

### 11. Мониторинг slab-памяти ядра

Утечка в модуле ядра часто проявляется через рост `SUnreclaim` в `/proc/meminfo`. Для детализации:

```bash
# Топ-10 кэшей slab по размеру
cat /proc/slabinfo | column -t | sort -k3 -nr | head -n 11

# Детали по конкретному кэшу (например, skbuff_head_cache для сетевых буферов)
grep skbuff_head_cache /proc/slabinfo
# → skbuff_head_cache    512  512    ...
```

Если `dentry` или `inode_cache` растет без причины — проблема в кэшировании ФС или утечке dentry. См. [Slab Allocator](../Core/memory/slab_allocator.md).

### 12. Проверка блокировок ядра: /proc/locks

Файл `/proc/locks` показывает все активные POSIX- и flock-блокировки. Полезна при диагностике взаимоблокировок между процессами:

```bash
# Показать все блокировки
cat /proc/locks

# Пример вывода:
# 1: POSIX  ADVISORY  WRITE 12345 0 EOF  /data/db/file.db
# 2: FLOCK  ADVISORY  WRITE 12345 0 EOF  /data/db/file.db

# Найти, кто держит блокировку на файле
lsof /data/db/file.db
```

### 13. Анализ загрузки CPU через /proc/stat

`/proc/stat` дает детальную разбивку времени CPU по состояниям:

```bash
# Первая строка: aggregate CPU
grep "^cpu " /proc/stat
# → cpu  225721 0 45680 12345678 1234 0 1234 0 0 0

# Поля: user nice system idle iowait irq softirq steal guest guest_nice
# idle = $5 + $6 (если ядро < 4.11)

# Расчет загрузки
awk '/^cpu / {print 100 - ($5+$6)*100/($2+$3+$4+$5+$6+$7+$8)}' /proc/stat
```

Для per-CPU статистики используйте `mpstat` или парсите строки `cpu<N>`.

### 14. Диагностика I/O процесса через /proc/PID/io

Счетчики реального дискового I/O, не искаженные кэшированием:

```bash
# Чтение и запись в байтах
cat /proc/<PID>/io
# rchar: 1342177280  # прочитано через read() (включая кэш)
# wchar: 536870912   # записано через write()
# syscr: 131072      # количество read() syscalls
# syscw: 65536       # количество write() syscalls
# read_bytes: 67108864   # реальное чтение с диска (non-cache)
# write_bytes: 268435456 # реальная запись на диск
# cancelled_write_bytes: 0
```

`read_bytes` vs `rchar`: разница показывает эффективность кэширования. Если `read_bytes` близок к `rchar` — кэш не работает.

### 15. Постоянный идентификатор процесса: /proc/PID/status и /proc/PID/stat

Для скриптов, которые должны пережить recycle PID, используйте комбинацию `start_time` из `/proc/PID/stat`:

```bash
# Уникальный идентификатор: (PID, starttime)
awk '/^starttime/ {print $2}' /proc/<PID>/stat
# → 12345678  # в юнитах clock ticks (divide by sysconf(_SC_CLK_TCK))

# Для получения monotonic boot time в секундах:
ps -o pid,lstart,etime -p <PID>
```

## Трайблшутинг

### hidepid блокирует диагностику

**Симптом:** `ps`, `top`, `htop`, `pidstat` показывают только ваши процессы. `lsof` возвращает `Permission denied` для чужих PID.

**Причина:** `/proc` смонтирован с `hidepid=2` или `invisible`.

**Действия:**
1. Проверка: `grep hidepid /proc/mounts`.
2. Для диагностики: `sudo grep -E 'VmRSS|State' /proc/<PID>/status` или `sudo ls -l /proc/<PID>/fd/`.
3. Если нужно постоянное исключение для мониторинга: добавьте `gid=<gid>` к опциям монтирования и включите группу мониторинга.

### В контейнере /proc/PID/* недоступен

**Симптом:** `Permission denied` при чтении `/proc/<PID>/fd/` или `/proc/<PID>/status` внутри контейнера.

**Причина:** Контейнер запущен без `--pid=host` и с отдельным `/proc` namespace. Также возможен `hidepid` на уровне хоста.

**Действия:**
1. Проверьте mountinfo: `cat /proc/self/mountinfo | grep ' /proc '`.
2. Если `/proc` смонтирован с `subset=` — увеличьте видимые подкаталоги.
3. Для полноценной диагностики перезапустите контейнер с `--pid=host --privileged` (или хотя бы с доступом к нужным PID).

### Подозрение на container escape: /proc/self/mountinfo

**Симптом:** Внутри контейнера `/proc/self/mountinfo` показывает корневой раздел хоста, `/sys` хоста или shared propagation.

**Причина:** Контейнер скомпрометирован; escape через CAP_SYS_ADMIN, уязвимость ядра или неправильный запуск.

**Действия:**
1. Проверьте `cat /proc/self/mountinfo | grep -E " / | /proc | /sys "`.
2. Ищите major:minor корневого раздела хоста (например, `8:1` для `/dev/sda1`).
3. Немедленно изолируйте контейнер и проведите forensic-анализ.

### Процесс завис: /proc/PID/syscall + wchan

**Симптом:** Процесс в состоянии **D** (Uninterruptible Sleep). `strace -p` не работает.

**Действия:**
```bash
# Текущий syscall (если не -1, то процесс в ядре)
cat /proc/<PID>/syscall

# Wait channel (функция ядра, где процесс заблокирован)
cat /proc/<PID>/wchan

# Стек ядра (если debugfs доступен)
cat /proc/<PID>/stack
```

Частые причины: NFS hang, поврежденный inode, недоступный loop-образ, зависший multipath.

### OOM Killer: кто убит и почему

**Симптом:** Процесс mysteriously завершился с `Killed` в логах.

**Действия:**
```bash
# Проверьте last oom victim в journalctl
journalctl -k | grep -i "oom\|killed"

# Рейтинг процесса до убийства (если лог доступен)
cat /proc/<PID>/oom_score
# Чем выше, тем вероятнее убийство

# Корректировка для критичных сервисов
echo -500 > /proc/<PID>/oom_score_adj
# Или через systemd: OOMScoreAdjust=-500 в unit-файле
```

Детали управления: [OOM Killer Management](../Core/processes/oom_killer_management.md).
