# Ссылки, Inode и Dentry

## Определения

- **Индексный дескриптор (Inode / Index Node):** Фундаментальная структура данных файловой системы, хранящая метаданные об объекте (права, владелец, размер, временные метки), за исключением его имени. Имя файла в Unix — это лишь запись в каталоге, ссылающаяся на номер Inode.
- **Жёсткая ссылка (Hard Link):** Вторая (или последующая) запись в каталоге, указывающая на тот же самый номер Inode, что и оригинальный файл. С точки зрения ядра все жесткие ссылки на один файл абсолютно равноправны.
- **Символическая ссылка (Symlink / Soft Link):** Специальный файл-указатель, содержимым которого является путь к другому объекту. Имеет собственный уникальный Inode.
- **Запись каталога (Dentry / Directory Entry):** Объект в оперативной памяти (VFS), связывающий имя файла с его Inode. Используется для кэширования путей и ускорения доступа к файлам.

## Индексный дескриптор (Inode)

Каждый объект файловой системы (файл, каталог, ссылка, устройство) идентифицируется уникальным номером Inode в пределах своей точки монтирования.

### Структура и содержимое (на примере ext4)
В ФС ext4 стандартный размер Inode составляет **256 байт**. В нем хранятся следующие данные:
- **Mode:** тип файла и права доступа (битовая маска `rwx` + SUID/SGID/Sticky).
- **UID/GID:** идентификаторы владельца и группы.
- **Size:** размер файла в байтах.
- **Links count (`i_nlink`):** количество жестких ссылок на этот Inode.
- **Timestamps:**
    - `atime` (access): время последнего чтения данных.
    - `mtime` (modify): время последнего изменения **контента**.
    - `ctime` (change): время последнего изменения **метаданных** (прав, владельца) или статуса Inode.
    - `btime` (birth): время создания файла (поддерживается в ядрах 4.11+ и ФС ext4, XFS, Btrfs).
- **Указатели на блоки:** В ext4 используются **экстенты (extents)** — структуры, описывающие непрерывные диапазоны блоков, что значительно эффективнее старых схем с прямыми и косвенными указателями.

### Особенности распределения Inode
- **Статическое (ext4):** Количество Inode фиксируется в момент создания ФС (`mkfs.ext4 -i`). Если в системе создано миллионы мелких файлов, Inode могут закончиться при наличии свободного места на диске. Диагностика: `df -i`.
- **Динамическое (XFS, Btrfs):** Inode выделяются по мере необходимости, пока доступно дисковое пространство.
- **XFS (Allocation Groups):** Inode распределяются по группам выделения (AG). Каждая AG имеет собственную структуру управления inode, что позволяет параллельно выделять метаданные на многоядерных системах без глобальной блокировки.

### Поведение при открытом файловом дескрипторе
Если файл удален через `unlink()`, но процесс держит его открытым дескриптором, ядро не освобождает место на диске до закрытия дескриптора. Это поведение критично для понимания инцидентов, когда `df -h` показывает заполненный диск, но `du` не находит виновника. Подробнее о механизме открытых файлов и их связи с Inode: **[Файловые дескрипторы](./file_descriptors.md)**.

## Жесткие ссылки (Hard Links)

Жёсткая ссылка — это запись в каталоге вида **"имя -> номер Inode"**.

- **Синтаксис:** `ln [TARGET] [LINK_NAME]`
- **Механика счётчика:** Поле `i_nlink` в Inode инкрементируется при каждом создании жесткой ссылки.
- **Равноправие:** Нет разницы между «оригиналом» и жесткой ссылкой. Данные существуют, пока `i_nlink > 0`.
- **Ограничения:**
    - Нельзя создавать жесткие ссылки на директории (запрещено ядром для предотвращения циклов в иерархии). Исключение: записи `.` (ссылка на себя) и `..` (ссылка на родителя).
    - Нельзя создавать ссылки между разными файловыми системами (разделами), так как номера Inode уникальны только в рамках одной ФС.

### Логика `nlink` для директорий
Для каталогов значение `i_nlink` всегда $\ge 2$:
1. Ссылка из родительского каталога (имя папки).
2. Ссылка `.` внутри самой директории.
3. Каждая поддиректория добавляет **+1** к счетчику родителя за счет своей записи `..`.
Это позволяет ядру мгновенно определять, является ли каталог пустым.

### Использование для дедупликации и бэкапов
Жёсткие ссылки применяются для экономии места при резервном копировании и создании снапшотов:
```bash
# Резервная копия с жёсткими ссылками (сохраняет место, если файлы не изменились)
cp -al /data /data_backup
```
**Предупреждение:** Цепочки жестких ссылок могут создавать циклы в графе зависимостей при анализе файлов. Утилиты вроде `du` могут зациклиться; используйте `find -samefile` вместо рекурсивного обхода по ссылкам.

## Символические ссылки (Symlinks)

Символическая ссылка — это файл, содержащий путь (абсолютный или относительный).

- **Синтаксис:** `ln -s [TARGET] [LINK_NAME]`
- **Механика:** При обращении к симлинку ядро считывает путь и выполняет повторный поиск (path resolution).
- **Fast Symlinks:** Если путь короткий (обычно < 60 байт), он хранится прямо в структуре Inode (в поле для указателей на блоки), что позволяет избежать обращения к диску за данными ссылки.
- **Ограничения:**
    - Лимит вложенности: ядро прекращает поиск после **40** последовательных переходов (`MAXSYMLINKS`), чтобы избежать зацикливания.
    - Права доступа симлинка (отображаются в `ls -l`) обычно игнорируются; проверяются права только целевого объекта.

### Расширенные атрибуты (xattr)
Начиная с ядра 4.5, симлинки поддерживают расширенные атрибуты (xattr), хотя многие утилиты их игнорируют. Это позволяет прикреплять метаданные безопасности или сведения о версировании непосредственно к ссылке.

### Поведение в пространствах имен
При монтировании с опцией `--make-private` симлинки с абсолютными путями разрешаются в контексте namespace, в котором происходит доступ. Это важно для контейнеров: симлинк `/opt/app -> /usr/share/app` внутри контейнера указывает на путь хост-системы только при shared-монтировании.

## Запись каталога (Dentry) и кэширование

В то время как Inode — это дисковая структура, **Dentry** — это резидентная в памяти структура ядра.

- **Dcache (Dentry Cache):** Кэш, хранящий сопоставление путей и Inode. Без dcache ядру пришлось бы при каждом обращении к `/usr/bin/ls` последовательно считывать блоки данных каталогов `/`, `/usr` и `/usr/bin` с диска.
- **Slab Allocator:** Объекты dentry и inode управляются через специализированные кэши в RAM. При нехватке памяти ядро вызывает `slab shrinkers`, которые в первую очередь очищают неиспользуемые dentry (т.н. `VFS cache`). Подробнее: **[Slab Allocator](../Core/memory/slab_allocator.md)**.

### Отрицательные dentry (Negative Dcache)
Ядро кэширует также и отрицательные результаты поиска (несуществующие пути) для ускорения повторных обращений к отсутствующим файлам. При массовом доступе к несуществующим ресурсам (например, при DDoS или ошибках конфигурации) negative dentry могут занимать значительную часть dcache. Быстрая проверка количества отрицательных dentry: `/proc/sys/fs/dentry-state` (пятое поле).

## Механика удаления и перемещения

### Удаление (unlink)
Команда `rm` выполняет системный вызов `unlink()`:
1. Удаляется запись "имя -> Inode" из каталога.
2. Счётчик `i_nlink` в Inode уменьшается на 1.
3. Если `i_nlink == 0` **И** ни один процесс не держит файл открытым, блоки данных и Inode помечаются как свободные.
4. Если `i_nlink == 0`, но дескриптор открыт, Inode и блоки остаются в памяти до закрытия последнего дескриптора.
**Важно:** Для удаления файла требуются права на запись (`w`) и выполнение (`x`) в **родительском каталоге**, а не права на сам файл.

### Перемещение (rename)
- **В пределах одной ФС:** Операция `mv` атомарно меняет запись в каталоге. Inode и блоки данных не меняются. Это мгновенная операция вне зависимости от размера файла.
- **Между разными ФС:** Выполняется физическое копирование данных (`cp`) с последующим удалением оригинала (`rm`). Inode меняется.

### Файл удален, но открыт процессом
Если процесс держит файл открытым, `unlink()` удаляет только запись из каталога (dentry). Inode и блоки данных остаются в памяти до закрытия дескриптора. Это означает:
- Файл не виден в `ls`, но продолжает потреблять место на диске.
- Процесс может продолжать читать/писать через открытый fd.
- После закрытия последнего fd Inode освобождается автоматически.

Диагностика:
```bash
# Найти удаленные, но открытые файлы
sudo lsof +L1 | grep deleted
# → nginx   1234 root  REG  252,1 5242880 123456 /var/log/nginx/access.log (deleted)

# Размер занятого места через fd
ls -l /proc/1234/fd/1
```

Решение:
```bash
# Вариант 1: Перезапуск процесса (освобождает все fd)
systemctl reload nginx

# Вариант 2: Обрезать файл через fd (без перезапуска)
: > /proc/1234/fd/1
```

## Практические сценарии

### 1. Инспекция метаданных через `stat`
Утилита `stat` — основной инструмент для просмотра данных из Inode.
```bash
stat /etc/hosts
# → Inode: 12345  Links: 1
# → Access: (0644/-rw-r--r--)  Uid: ( 0/ root)  Gid: ( 0/ root)
# → Access: 2026-08-10 10:00:00  (atime)
# → Modify: 2026-08-10 09:30:00  (mtime)
# → Change: 2026-08-10 09:30:00  (ctime)
```

Для быстрого просмотра номера Inode используйте `ls -li`:
```bash
ls -li /etc/hosts
# → 12345 -rw-r--r-- 1 root root 123 Aug 10 10:00 /etc/hosts
```

### 2. Поиск всех имен файла (Hard Links)
Если нужно найти все жесткие ссылки на конкретный объект:
```bash
# Найти все файлы на разделе с тем же номером Inode
find / -inum $(stat -c %i /path/to/file) 2>/dev/null
```

### 3. Мониторинг VFS-кэшей (dcache, icache, page cache)
Для SRE важно понимать, как ядро использует RAM для кэширования метаданных. Подробные инструменты и интерпретация описаны в **[Внутреннее устройство ФС](./fs_internals.md#4-инспекция-vfs-кэшей-dcache-icache-page-cache)**.

Быстрая проверка:
```bash
# Баланс кэшей VFS в slab
cat /proc/sys/fs/dentry-state
# → 12345 6789 45 0 0 0  # count age max_pct [negative_dentries ...]

cat /proc/sys/fs/inode-state
# → 123456 7890 45 0 0 0 ...
```

### 4. Файл удален, но процесс держит дескриптор открытым

Классическая SRE-ситуация: `df -h` показывает 100% использования, но `du -sh /*` не находит виновника. Причина — файл удален через `rm`, но процесс продолжает писать в открытый дескриптор.

**Механизм:**

`rm` не удаляет данные файла мгновенно. Он удаляет его имя из каталога, а сами данные остаются доступными процессу, пока тот держит файл открытым.

Например, приложение пишет большой лог `/var/log/app.log`. Администратор удаляет его:

```bash
rm /var/log/app.log
```

`ls` больше его не покажет, но процесс продолжит писать в тот же файл. Место на диске при этом не освободится.

Диагностика:
```bash
# Найти все удаленные, но открытые файлы
sudo lsof +L1 | grep deleted
# → nginx   1234 root  REG  252,1 5242880 123456 /var/log/nginx/access.log (deleted)

# Проверка конкретного дескриптора
ls -l /proc/1234/fd/1
```

Решение:
```bash
# Вариант 1: Перезапуск процесса (освобождает все fd)
systemctl reload nginx

# Вариант 2: Обрезать файл через fd (без перезапуска)
: > /proc/1234/fd/1
```

### 5. Исчерпание Inode в контейнерах (Docker overlay2)
Драйвер `overlay2` создает множество мелких файлов для слоев и метаданных контейнеров. При массовом запуске/остановке контейнеров inodes могут закончиться раньше места на диске.

Диагностика:
```bash
# Проверка использования inodes на хосте
df -i /var/lib/docker
# → Filesystem     Inodes  IUsed  IFree IUse%
# → /dev/sda1      30967808 30967808 0     100%

# Поиск крупнейших каталогов overlay2
sudo du -sh /var/lib/docker/overlay2/* | sort -rh | head -n 10
```

Решение:
```bash
# Очистка неиспользуемых ресурсов Docker
docker system prune -af --volumes

# Настройка log rotation для контейнеров
# /etc/docker/daemon.json:
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

### 6. Blue-green deployment через симлинки
Для нулевого простоя при обновлении приложения используется атомарное переключение симлинка. Подробный сценарий описан в **[Управление файлами](../Shell/file_operations.md#blue-green-deployment-через-символические-ссылки)**.

Суть: новая версия развертывается в отдельный каталог, после чего симлинк `current` переключается на новый путь через `ln -sfn`. Поскольку `symlink(2)` + `rename(2)` атомарны в пределах одной ФС, запросы никогда не попадают на частично обновленный каталог.

### 7. Управление правами доступа (chmod)

**Синтаксис chmod:**
```bash
chmod <mode> <file>    # Символьный или восьмеричный режим
```

**Восьмеричное представление прав:**
| Бит | Значение | Символ |
|:---|:---|:---|
| 4 | Чтение | `r` |
| 2 | Запись | `w` |
| 1 | Выполнение | `x` |

**Примеры:**
| Команда | Расшифровка | Применение |
|:---|:---|:---|
| `chmod 755 file` | `rwxr-xr-x` — владелец всё, остальные чтение+выполнение | Исполняемые скрипты, бинарники |
| `chmod 644 file` | `rw-r--r--` — владелец запись, остальные чтение | Конфигурационные файлы, документы |
| `chmod 600 file` | `rw-------` — только владелец | Приватные ключи, файлы с секретами |
| `chmod 700 dir` | `rwx------` — только владелец | Домашние директории |

**Разница между файлами и директориями:**

Для файлов всё интуитивно понятно: `r` — читать содержимое, `w` — изменять, `x` — запускать как программу.

Для директорий значение битов отличается:

| Бит | Значение для файла | Значение для директории |
|:---|:---|:---|
| `r` (4) | Чтение содержимого | Вывод списка файлов (`ls`), но не чтение их содержимого |
| `w` (2) | Запись/изменение содержимого | Создание/удаление/переименование файлов внутри, даже если на них нет прав |
| `x` (1) | Выполнение как программы | **Вход в директорию** (`cd`), доступ к метаданным файлов (через `stat`, чтение содержимого известных файлов) |

**Ключевые нюанс с директориями:**
- Без `x` на директории нельзя `cd` в неё и нельзя получить доступ к файлам внутри, даже если известно их имя и на самом файле стоят права `rwx`.
- Без `w` на директории нельзя создавать или удалять файлы в ней, даже если на самом файле стоит `w`.
- Для полного доступа к файлу нужен `x` на **каждой** директории в пути до него.

**Рекурсивное изменение прав:**
```bash
# Для директорий — 755, для файлов — 644
find /path -type d -exec chmod 755 {} \;
find /path -type f -exec chmod 644 {} \;

# Или через символы
chmod -R u+rwX,g+rX,o+rX /path   # X — выполнение только для директорий и уже исполняемых файлов
```

**Специальные биты:**
| Бит | Значение | Восьмеричный префикс |
|:---|:---|:---|
| SUID | Выполнение от владельца файла | 4 (например, `4755`) |
| SGID | Выполнение от группы файла | 2 (например, `2755`) |
| Sticky | Удаление только владельцем (для `/tmp`) | 1 (например, `1777`) |

## Безопасность и защита ссылок

Ядро предоставляет механизмы защиты от атак через ссылки в общих каталогах (например, `/tmp`):
- `fs.protected_symlinks=1`: Запрещает следование по симлинкам в "липких" (sticky) директориях, если владелец ссылки не совпадает с владельцем целевого файла или текущим пользователем.
- `fs.protected_hardlinks=1`: Запрещает создание жестких ссылок на файлы, которыми пользователь не владеет или не имеет прав на чтение/запись.

Подробнее: **[Защита ссылок](../Security/Fstec/kernel_runtime_protection.md#защита-от-небезопасных-ссылок-symlinks-и-hardlinks)**.

## Устранение неполадок

### Inode exhaustion (`df -i` показывает 100%)
- **Причина:** Миллионы мелких файлов (кэши сессий, очереди почты, артефакты CI/CD).
- **Диагностика:** `df -i`, `sudo find / -xdev -type f | cut -d/ -f2 | sort | uniq -c | sort -rn | head`
- **Решение:** Удаление устаревших файлов, переход на ФС с динамическим выделением inode (XFS, Btrfs), увеличение количества inode при создании ФС (`mkfs.ext4 -N` для пересчета, `-i bytes-per-inode` для изменения соотношения).

### Dentry cache pressure
- **Причина:** Приложение обращается к сотням тысяч уникальных путей (веб-серверы, CI/CD агенты).
- **Симптомы:** Высокое `SReclaimable` в `/proc/meminfo`, `slabtop` показывает огромный `dentry` кэш.
- **Решение:** `sysctl -w vm.vfs_cache_pressure=50` (уменьшает агрессивность очистки dcache) или увеличение RAM.

### Симлинк-петли (loops)
- **Причина:** Циклические симлинки в иерархии.
- **Диагностика:** `find /path -type l -exec readlink {} \; | sort | uniq -d` (поиск дублирующихся целей) или `namei -l /path` для визуализации.
- **Решение:** Удаление петель, проверка через `find -L` (следовать по симлинкам).

### Hardlink bombs
- **Причина:** Злоумышленник или ошибка создают цепочки жестких ссылок, вызывающие зависание `find` или `du`.
- **Диагностика:** `find /path -type f -links +1 | wc -l` (количество файлов с несколькими ссылками).
- **Решение:** Использование `find -samefile` вместо рекурсивного обхода, настройка квот на количество ссылок.

## Лучшие практики

1. **Мониторинг inode:** Добавьте в `node_exporter` алерты на `node_filesystem_files_free` / `node_filesystem_files` для критических разделов. Порог: 80% использования.
2. **Разделение по ФС:** Хранилище с миллионами мелких файлов (логи, кэши) размещайте на отдельном разделе с ФС, имеющей динамические inode (XFS, Btrfs), чтобы избежать исчерпания.
3. **Атомарные обновления:** Используйте `mv` внутри одной ФС для атомарной замены файлов. Для деплоя приложений предпочитайте переключение симлинка `ln -sfn`.
4. **Избегайте жестких ссылок на директории:** Это создает циклы в файловой системе и может сломать инструменты резервного копирования. Используйте symlinks или bind-монтирования.
5. **Используйте `cp -al` для snapshot-ов:** Жёсткие ссылки позволяют создавать моментальные копии данных без дублирования блоков. Для инкрементальных бэкапов комбинируйте с `rsync --link-dest`.
6. **Восстанавливайте данные из открытых fd:** При падении сервиса с активными логами не удаляйте PID-файл немедленно — проверьте `/proc/<PID>/fd/` на наличие удаленных, но открытых файлов.
7. **Настройка VFS cache pressure:** Значение `vm.vfs_cache_pressure=50` подходит для систем с интенсивной работой с метаданными (веб-серверы, файловые хранилища). Значение по умолчанию `100` подходит для гетерогенных нагрузок.
