# Ссылки, Inode и Dentry

## Определения

### Жёсткая ссылка (Hard Link)

Жёсткая ссылка — **второе имя для тех же данных на диске**. Указывает на тот же **inode**, что и оригинальный файл. Имя файла — запись в директории, сопоставляющая имя с номером inode. Создание жёсткой ссылки — добавление ещё одной записи, указывающей на тот же inode.

* **Синтаксис:**

    ```bash
    ln [TARGET_FILE] [LINK_NAME]
    ```

  * `TARGET_FILE` — существующий файл.
  * `LINK_NAME` — новое имя (ссылка) для этого файла.

### Символическая ссылка (Symbolic Link / Symlink)

Символическая ссылка — **специальный файл-указатель**, содержащий **текстовый путь** к другому файлу или директории. Имеет собственный уникальный inode. При обращении к симлинку ОС читает путь и перенаправляет к целевому файлу.

* **Синтаксис:**

    ```bash
    ln -s [TARGET] [LINK_NAME]
    ```

  * `-s` — обязательный флаг, указывающий, что нужно создать символическую ссылку.
  * `TARGET` — путь, на который будет указывать ссылка (файл или директория).
  * `LINK_NAME` — имя самой ссылки.
  * `-f` - (--force): "Принудительно". Если по пути уже существует какой-то файл или другая ссылка, эта опция удалит его перед созданием новой ссылки.

### Inode (Индексный дескриптор)

**Inode** — структура данных в Unix-подобных ФС, хранящая всю метаинформацию о файле/директории, кроме имени и данных. Каждый файл/каталог имеет уникальный `inode`. Директория — специальный файл с таблицей «имя файла → номер inode».

**Размер и структура в ext4:** в файловой системе ext4 один inode занимает **256 байт**. В этих байтах хранится вся метаинформация: владелец, группа, права доступа, размер, временные метки с точностью до наносекунд (`atime`, `mtime`, `ctime`), счётчик жёстких ссылок и поле `i_block` (~60 байт) — указатели на реальные данные файла на диске. Имя файла в inode **не хранится** — оно живёт в каталоге.

### Dentry (Directory Entry)

**Dentry** — это структура в памяти ядра, которая связывает имя файла с его inode. Dentry кэшируются для ускорения доступа к файлам. Подробнее об управлении памятью для таких структур можно найти в статье о [Slab Allocator](../Core/memory/slab_allocator.md).

### Как устроена директория

Каталог в Linux — это специальный файл, внутри которого хранится таблица (список) записей вида **"имя файла -> номер inode"**. Имя файла **не хранится в inode** — оно живёт исключительно в этой таблице каталога.

Когда вы выполняете `cat file.txt`:

1. Ядро открывает каталог, находит строку `file.txt`
2. Берёт оттуда номер inode
3. Идёт в таблицу inode, читает метаданные и указатели на блоки
4. Только после этого начинает читать данные с диска

## Основные концепции

### Особенности жёстких ссылок

* **Равноправие:** Все жёсткие ссылки на один inode абсолютно равноправны. Не существует "оригинала" и "ссылки".
* **Создание:** При создании жёсткой ссылки (`ln file hardlink1`) ядро делает две вещи:
  1. Добавляет новую запись в каталог (ещё одно имя)
  2. Увеличивает счётчик жёстких ссылок (`i_nlink`) в inode на единицу
* **Удаление:** Системный вызов `unlink()` (используемый командой `rm`) удаляет запись из каталога и уменьшает счётчик ссылок. Данные с диска стираются только при выполнении **двух условий**:
  1. Счётчик ссылок дошёл до нуля
  2. **Ни один процесс не держит файл открытым** (через файловый дескриптор)

  Если процесс ещё пишет файл через открытый дескриптор, ядро не тронет данные, пока дескриптор не закроется. Это частая причина расхождения между `df` и `du` — см. [устранение нехватки места на диске](./disk_space_troubleshooting.md).
* **Ограничения:**
  * **Нельзя создать для директорий:** Это сделано для предотвращения зацикливания файловой системы (например, `dir1/link_to_dir1`), что могло бы сломать многие утилиты (`find`, `ls -R`). Единственное исключение — записи `.` и `..`, которыми управляет само ядро.
  * **Только в пределах одной файловой системы:** Inode уникален только в рамках своего раздела (файловой системы). Номера inode локальны для каждой ФС — нельзя создать жёсткую ссылку на файл, находящийся на другом диске или разделе, потому что hardlink хранит только номер без указания, на какой файловой системе его искать.
* **Практическое применение:** Инкрементальные бэкапы. Утилиты `rsync --link-dest` и `snapper` создают жёсткие ссылки на неизменённые файлы в каждом новом снапшоте, экономя дисковое пространство — данные на диске хранятся в одном экземпляре, но имеют несколько имён.
* **Проверка:** Команда `ls -li` покажет одинаковый номер inode для всех жёстких ссылок.

### Особенности символических ссылок

* **Указатель:** Symlink — это **отдельный файл** со своей собственной inode и своим номером. Содержимое этого файла — строка с путём к целевому файлу.
* **Fast symlink:** Если путь короткий (до ~60 байт), он хранится прямо в поле `i_block` самой inode — без выделения дополнительных блоков на диске. Для длинных путей выделяется отдельный блок данных.
* **Разрешение пути:** При обращении к симлинку ядро читает строку-путь и начинает разрешение пути заново. Если симлинк ссылается на другой симлинк, тот — на третий и т.д., ядро проходит по цепочке, но не бесконечно. Лимит — **40 переходов**. Если за 40 шагов до реального файла не добрались, ядро вернёт ошибку.
* **Права симлинка:** У симлинка всегда выставлены максимальные права, но на Linux они игнорируются — доступ определяется правами целевого файла.
* **"Битые" ссылки:** Если удалить целевой файл, симлинк "повиснет" и станет битым (dangling). Однако если затем создать новый файл **по тому же пути**, симлинк автоматически снова заработает — он хранит строку-путь, а не ссылку на конкретную inode.
* **Гибкость:**
  * Можно создавать ссылки на **директории**.
  * Можно создавать ссылки на файлы **в других файловых системах** (на других дисках, разделах, смонтированных сетевых папках).
  * Путь к цели может быть **относительным** или **абсолютным**.
* **Проверка:** `ls -l` показывает, куда указывает ссылка. Для вывода номеров inode используется команда `ls -i`.
* **Практическое применение:** Основа управления конфигурациями в Linux: `sites-enabled` / `sites-available` в Nginx, включение юнитов systemd (`systemctl enable`), цепочки версий библиотек, `/usr/bin/sh` — всё это симлинки.

### Метаданные, хранящиеся в Inode

* **Тип файла и права доступа (Mode)**: Например, обычный файл, директория, символическая ссылка, а также права `rwx`.
* **Владелец (UID) и Группа (GID)**: ID пользователя и группы, которым принадлежит файл.
* **Размер файла**: В байтах.
* **Временные метки**:
  * `atime`: Время последнего доступа (access time).
  * `mtime`: Время последней модификации содержимого (modification time).
  * `ctime`: Время последнего изменения метаданных inode (change time).
* **Счётчик жёстких ссылок**: Сколько имён (записей в директориях) ссылается на этот inode.
* **Расположение на диске**: Указатели на блоки данных, где физически хранится содержимое файла.

### Важные моменты об Inode

* **Уникальность и расположение**: Номера inode уникальны только в пределах одного раздела (файловой системы). У каждого раздела своя таблица inode. В файловых системах типа `ext2/3` таблица inode часто хранится перед блоками данных в каждой группе блоков. В некоторых файловых системах, например `FAT32`, концепция inode отсутствует, и метаданные хранятся непосредственно в элементах каталога.
* **Имя файла**: Имена файлов и директорий **не хранятся в inode**. Они находятся в файле-таблице родительской директории. Каталоги Unix представляют собой списки ассоциативных структур, каждая из которых содержит имя файла/директории и соответствующий номер inode. Драйвер файловой системы отвечает за поиск по имени в каталоге и преобразование его в правильный номер inode для доступа к метаданным.
* **Удаление файла**: Системный вызов `unlink()` (используемый командой `rm`) удаляет запись "имя -> inode" из директории и уменьшает счётчик ссылок в inode. Данные на диске помечаются как свободные и физически удаляются только когда счётчик достигает нуля.
* **Выделение inode'ов**:
  * **Статическое (Ext2/3/4)**: В этих файловых системах общее количество inode'ов **фиксируется** в момент создания (форматирования) командой `mkfs`. Это число зависит от общего размера раздела и заданного соотношения **байт на inode** (например, 1 inode на каждые 16 КБ).

      **Причины исчерпания inode:**

    * **Большое количество мелких файлов** — наиболее частая причина. Каждый файл использует минимум один inode, поэтому системы с огромным количеством маленьких файлов (кэши, почтовые серверы, код, сессии PHP, логи) исчерпают inode раньше, чем дисковое пространство.
    * **Недостаточное количество выделенных inode** — при создании ФС было задано слишком большое соотношение байт на inode (например, 16 КБ на inode вместо 4 КБ). Это критично для серверов, где ожидается большое количество файлов.
    * **Особенности файловой системы** — Ext3/Ext4 имеют фиксированное соотношение inode к объёму, задаваемое при создании. Неправильный расчёт приводит к раннему исчерпанию.

      Inode'ы могут закончиться на системах, где хранится **огромное количество очень маленьких файлов**. В таком сценарии место, выделенное под таблицы inode'ов, исчерпывается раньше, чем место для данных.
  * **Последствия статического выделения**: Основным последствием является невозможность создавать новые файлы, директории или ссылки.
    * **Создание новых файлов**: Невозможно, так как для нового файла требуется новый inode. Системные утилиты и приложения начнут выдавать ошибку **"No space left on device"**. Это может ввести в заблуждение, так как `df -h` будет показывать наличие свободного места, в то время как `df -i` покажет, что inode'ы использованы на 100%. Подробнее о диагностике и устранении этой проблемы см. в [Диагностика файловой системы и дискового пространства](../Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md).
    * **Запись в существующие файлы**: Возможна, так как это не требует выделения нового inode. Операция изменяет размер файла и дисковые блоки, но номер inode остаётся прежним.

  * **Динамическое (XFS, Btrfs, ZFS)**: Этот подход означает, что количество inode'ов не резервируется заранее при создании файловой системы. Вместо этого они **создаются по мере необходимости**. Это полностью решает проблему исчерпания inode'ов, так как их количество не ограничено заранее заданным лимитом.

### Права на удаление файла и родительская директория

Важно понимать, что права на удаление файла определяются не правами самого файла, а **правами родительской директории**. Поскольку операция удаления файла является модификацией родительской директории, для её выполнения требуются права на запись (`w`) в эту родительскую директорию. Если у пользователя нет прав на запись в директорию, он не сможет удалить файлы, находящиеся в ней, даже если у него есть полные права на сам файл.

### Почему удаление файла — это операция над директорией

В Linux/Unix удаление файла — это операция над директорией, а не над самим файлом. Это следует из архитектуры файловой системы:

**Архитектура хранения:**

1. **Данные файла** хранятся в блоках диска, на которые указывает inode
2. **Директория** — это специальный файл, содержащий таблицу соответствия «имя файла → inode»
3. **Имя файла** не хранится в inode, оно находится только в записи директории

**Что происходит при `rm file.txt`:**

```
1. Поиск записи "file.txt" в директории → получение номера inode
2. Уменьшение счётчика ссылок (i_nlink) в inode
3. Удаление записи "file.txt → inode" из директории
4. Если i_nlink == 0 → освобождение inode и блоков данных
```

**Системный вызов:** команда `rm` вызывает системный вызов `unlink()`, который удаляет запись из каталога и уменьшает счётчик ссылок. Данные освобождаются только когда счётчик ссылок достигает нуля **и** ни один процесс не держит файл открытым.

**Ключевой момент:** Вы модифицируете **содержимое директории** (удаляете из неё запись), а не сам файл напрямую. Файл как структура данных не «знает» о своём удалении — он просто теряет последнюю ссылку на себя.

**Следствия этой архитектуры:**

| Следствие | Объяснение |
| :--- | :--- |
| **Жёсткие ссылки** | Несколько имён → один inode. Удаление одного имени не удаляет данные |
| **Файл открыт, но удалён** | Данные не освободятся, пока процесс держит fd (i_nlink=0, но refcount>0) |
| **`rm` требует прав на директорию** | Нужна запись (`w`) в директорию, а не на сам файл |
| **Переименование быстрое** | `mv` в пределах одной ФС — это изменение записи в директории, данные не перемещаются |

**Почему так спроектировано:**

* **Единая модель:** директория — тоже файл (таблица имён)
* **Гибкость:** жёсткие ссылки, hardlink-бэкапы
* **Безопасность:** права на удаление контролируются через директорию
* **Эффективность:** данные не перемещаются при переименовании/удалении

## Практические сценарии

### Применение жёстких ссылок

* **Резервное копирование:** Некоторые утилиты (например, `rsync --link-dest`) используют жёсткие ссылки для создания инкрементальных бэкапов, экономя дисковое пространство. Неизменившиеся файлы представляются жёсткими ссылками на файлы из предыдущего бэкапа.
* **Безопасное обновление файлов:** Можно создать новый файл, а затем атомарно заменить старый, переименовав новый файл поверх старого.

### Применение символических ссылок

* **Управление версиями ПО:** Часто используется для переключения между разными версиями программ. Например, `/usr/bin/python` может быть симлинком на `/usr/bin/python3.11`.
* **Удобство доступа:** Создание "ярлыков" в домашних директориях для доступа к файлам, лежащим глубоко в файловой системе.
* **Конфигурационные файлы:** Размещение реальных конфигов в одном месте (например, в системе контроля версий) и создание симлинков на них в тех местах, где их ожидают программы (`/etc/nginx/sites-enabled/`, `~/.config/`).

### `mv` (перемещение и переименование) vs. `cp`: Практическое применение Inode

* **`cp` (копирование):**
  * Создаёт новый, отдельный inode.
  * Копирует все блоки данных из источника в новые блоки.
  * Фактически создаёт полную дубликат файла.
  * Это ресурсоёмкая операция, особенно для больших файлов.

* **`mv` (перемещение и переименование):**
  * **Переименование (`mv old_name new_name`)**: Если `new_name` находится в той же директории, `mv` просто меняет имя в записи директории. Inode и данные остаются нетронутыми. Это чрезвычайно быстрая операция.
  * **Перемещение в пределах одной файловой системы (`mv file /path/to/new_dir/`)**:
    * **Не трогает inode и блоки данных.**
    * Просто удаляет запись "имя → inode" из старой директории и добавляет её в новую.
    * Никакие данные физически не перемещаются, операция также очень быстрая.
  * **Примечание:** При выполнении `mv` между разными файловыми системами (например, с одного диска на другой), команда ведёт себя как `cp`, а затем `rm`: данные полностью копируются на новое место (с новым inode), после чего оригинал удаляется.

## Дополнительная информация

### Защита от небезопасных ссылок

Ядро Linux предоставляет механизмы защиты от атак через символические и жёсткие ссылки в каталогах с `world-writable` + `sticky` битом (например, `/tmp`). Параметры `fs.protected_symlinks` и `fs.protected_hardlinks` контролируют поведение ядра. Подробное описание — [Защита от небезопасных ссылок](../Security/Fstec/kernel_runtime_protection.md#защита-от-небезопасных-ссылок-symlinks-и-hardlinks).
