# Ссылки, Inode и Dentry

## Определения

### Жёсткая ссылка (Hard Link)

Жёсткая ссылка — это не отдельный файл, а **второе имя для тех же данных на диске**. Она напрямую указывает на тот же **inode** (индексный дескриптор), что и оригинальный файл. Каждый файл в системе представлен inode, который хранит метаданные (права, владелец, размер) и указатели на блоки данных. Имя файла — это лишь запись в директории, которая сопоставляет имя с номером inode. Когда вы создаете жёсткую ссылку, вы просто добавляете еще одну запись в директорию, которая указывает на тот же самый inode.

* **Синтаксис:**

    ```bash
    ln [TARGET_FILE] [LINK_NAME]
    ```

  * `TARGET_FILE` — существующий файл.
  * `LINK_NAME` — новое имя (ссылка) для этого файла.

### Символическая ссылка (Symbolic Link / Symlink)

Символическая ссылка (или симлинк) — это **специальный файл-указатель**, который содержит **текстовый путь** к другому файлу или директории. Аналог "ярлыка" в Windows. Симлинк имеет свой собственный, уникальный inode. Когда вы обращаетесь к нему, операционная система читает путь, записанный внутри, и перенаправляет вас к целевому файлу или директории.

* **Синтаксис:**

    ```bash
    ln -s [TARGET] [LINK_NAME]
    ```

  * `-s` — обязательный флаг, указывающий, что нужно создать символическую ссылку.
  * `TARGET` — путь, на который будет указывать ссылка (файл или директория).
  * `LINK_NAME` — имя самой ссылки.
  * `-f` - (--force): "Принудительно". Если по пути уже существует какой-то файл или другая ссылка, эта опция удалит его перед созданием новой ссылки.

### Inode (Индексный дескриптор)

**Inode (индексный дескриптор)** — это фундаментальная структура данных в Unix-подобных файловых системах. Она хранит всю метаинформацию о файле или директории, за исключением имени и самих данных. Каждый файл и каталог имеет свой уникальный `inode`. Сама директория по своей сути является специальным файлом, который содержит таблицу, сопоставляющую **имена файлов** с их **номерами inode (inumber)**. Когда вы обращаетесь к файлу по имени, система находит его в директории, получает номер inode и уже из inode извлекает всю остальную информацию.

### Dentry (Directory Entry)

**Dentry** — это структура в памяти ядра, которая связывает имя файла с его inode. Dentry кэшируются для ускорения доступа к файлам. Подробнее об управлении памятью для таких структур можно найти в статье о [Slab Allocator](../../Core/memory/slab_allocator.md).

## Основные концепции

### Особенности жёстких ссылок

* **Равноправие:** Все жёсткие ссылки на один inode абсолютно равноправны. Не существует "оригинала" и "ссылки".
* **Удаление:** Файл физически удаляется с диска только тогда, когда удаляется **последняя** жёсткая ссылка на него. Это происходит потому, что в inode есть счётчик ссылок, и данные освобождаются только когда он достигает нуля.
* **Ограничения:**
  * **Нельзя создать для директорий:** Это сделано для предотвращения зацикливания файловой системы (например, `dir1/link_to_dir1`), что могло бы сломать многие утилиты (`find`, `ls -R`).
  * **Только в пределах одной файловой системы:** Inode уникален только в рамках своего раздела (файловой системы). Нельзя создать жёсткую ссылку на файл, находящийся на другом диске или разделе.
* **Проверка:** Команда `ls -li` покажет одинаковый номер inode для всех жёстких ссылок.

### Особенности символических ссылок

* **Указатель:** Это не копия данных, а лишь путь.
* **"Битые" ссылки:** Если оригинальный файл или директорию удалить или переместить, символическая ссылка останется, но станет "битой" (dangling) — она будет указывать в никуда.
* **Гибкость:**
  * Можно создавать ссылки на **директории**.
  * Можно создавать ссылки на файлы **в других файловых системах** (на других дисках, разделах, смонтированных сетевых папках).
  * Путь к цели может быть **относительным** или **абсолютным**.
* **Проверка:** `ls -l` показывает, куда указывает ссылка. Для вывода номеров inode используется команда `ls -i`.

### Метаданные, хранящиеся в Inode

* **Тип файла и права доступа (Mode)**: Например, обычный файл, директория, символическая ссылка, а также права `rwx`.
* **Владелец (UID) и Группа (GID)**: ID пользователя и группы, которым принадлежит файл.
* **Размер файла**: В байтах.
* **Временные метки**:
  * `atime`: Время последнего доступа (access time).
  * `mtime`: Время последней модификации содержимого (modification time).
  * `ctime`: Время последнего изменения метаданных inode (change time).
* **Счётчик жёстких ссылок**: Сколько имён (записей в директориях) ссылается на этот inode.
* **Расположение на диске**: Указатели на блоки данных, где физически хранится содержимое файла.

### Важные моменты об Inode

* **Уникальность и расположение**: Номера inode уникальны только в пределах одного раздела (файловой системы). У каждого раздела своя таблица inode. В файловых системах типа `ext2/3` таблица inode часто хранится перед блоками данных в каждой группе блоков. В некоторых файловых системах, например `FAT32`, концепция inode отсутствует, и метаданные хранятся непосредственно в элементах каталога.
* **Имя файла**: Имена файлов и директорий **не хранятся в inode**. Они находятся в файле-таблице родительской директории. Каталоги Unix представляют собой списки ассоциативных структур, каждая из которых содержит имя файла/директории и соответствующий номер inode. Драйвер файловой системы отвечает за поиск по имени в каталоге и преобразование его в правильный номер inode для доступа к метаданным.
* **Удаление файла**: Системный вызов `unlink()` (используемый командой `rm`) удаляет запись "имя -> inode" из директории и уменьшает счётчик ссылок в inode. Данные на диске помечаются как свободные и физически удаляются только когда счётчик достигает нуля.
* **Выделение inode'ов**:
  * **Статическое (Ext2/3/4)**: В этих файловых системах общее количество inode'ов **фиксируется** в момент создания (форматирования) командой `mkfs`. Это число зависит от общего размера раздела и заданного соотношения **байт на inode** (например, 1 inode на каждые 16 КБ). Inode'ы могут закончиться на системах, где хранится **огромное количество очень маленьких файлов** (кэши, почтовые серверы, код). В таком сценарии, место, выделенное под таблицы inode'ов, исчерпывается раньше, чем место для данных.
  * **Последствия статического выделения**: Основным последствием является невозможность создавать новые файлы, директории или ссылки. Системные утилиты и приложения начнут выдавать ошибку **"No space left on device"**, что может ввести в заблуждение, так как `df -h` будет показывать наличие свободного места, в то время как `df -i` покажет, что inode'ы использованы на 100%. Подробнее о диагностике и устранении этой проблемы см. в [Диагностика файловой системы и дискового пространства](../../Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md).
  * **Динамическое (XFS, Btrfs, ZFS)**: Этот подход означает, что количество inode'ов не резервируется заранее при создании файловой системы. Вместо этого они **создаются по мере необходимости**. Это полностью решает проблему исчерпания inode'ов, так как их количество не ограничено заранее заданным лимитом.

### Права на удаление файла и родительская директория

Важно понимать, что права на удаление файла определяются не правами самого файла, а **правами родительской директории**. Поскольку операция удаления файла является модификацией родительской директории, для её выполнения требуются права на запись (`w`) в эту родительскую директорию. Если у пользователя нет прав на запись в директорию, он не сможет удалить файлы, находящиеся в ней, даже если у него есть полные права на сам файл.

## Практические сценарии

### Применение жёстких ссылок

* **Резервное копирование:** Некоторые утилиты (например, `rsync --link-dest`) используют жёсткие ссылки для создания инкрементальных бэкапов, экономя дисковое пространство. Неизменившиеся файлы представляются жёсткими ссылками на файлы из предыдущего бэкапа.
* **Безопасное обновление файлов:** Можно создать новый файл, а затем атомарно заменить старый, переименовав новый файл поверх старого.

### Применение символических ссылок

* **Управление версиями ПО:** Часто используется для переключения между разными версиями программ. Например, `/usr/bin/python` может быть симлинком на `/usr/bin/python3.11`.
* **Удобство доступа:** Создание "ярлыков" в домашних директориях для доступа к файлам, лежащим глубоко в файловой системе.
* **Конфигурационные файлы:** Размещение реальных конфигов в одном месте (например, в системе контроля версий) и создание симлинков на них в тех местах, где их ожидают программы (`/etc/nginx/sites-enabled/`, `~/.config/`).

### `mv` vs. `cp`: Практическое применение Inode

* **`cp` (копирование):**
  * Создаёт новый, отдельный inode.
  * Копирует все блоки данных из источника в новые блоки.
  * Фактически создаёт полную дубликат файла.
  * Это ресурсоёмкая операция, особенно для больших файлов.

* **`mv` (перемещение в пределах одной файловой системы):**
  * **Не трогает inode и блоки данных.**
  * Просто удаляет запись "имя → inode" из старой директории и добавляет её в новую.
  * Никакие данные физически не перемещаются.
  * **Примечание:** При выполнении `mv` между разными файловыми системами (например, с одного диска на другой), команда ведёт себя как `cp`, а затем `rm`: данные полностью копируются, после чего оригинал удаляется.

### Увеличение количества Inodes (Ext2/3/4)

**Проблема:** В файловых системах семейства `Ext` (Ext2, Ext3, Ext4) количество inodes (индексных дескрипторов) **фиксируется в момент форматирования раздела**. Изменить это значение на уже существующей файловой системе без её пересоздания **невозможно**. Если у вас закончились inodes, вы не сможете создавать новые файлы, даже если на диске много свободного места.

**Решение:** Единственный способ — это создать резервную копию данных, переформатировать раздел с новыми параметрами и восстановить данные.

1. **Резервное копирование (Критически важно!)**
    Перед любыми действиями создайте полную резервную копию всех данных с нужного раздела.

    ```sh
    sudo rsync -avh /path/to/your/mountpoint/ /path/to/backup/
    ```

2. **Отмонтирование раздела**

    ```sh
    sudo umount /path/to/your/mountpoint
    ```

3. **Переформатирование с нужным количеством inodes**
    Используйте команду `mkfs.ext4` с одним из флагов:
    * `-i bytes-per-inode`: Задаёт соотношение байт на один inode. Чем меньше значение, тем больше будет создано inodes.
        * Значение по умолчанию обычно `16384` (1 inode на 16 КБ).
        * Для систем с огромным количеством мелких файлов (почта, кэш) можно поставить `4096` (1 inode на 4 КБ).
    * `-N number-of-inodes`: Прямо указывает, сколько inodes нужно создать.

    **Пример (рекомендуемый способ):**

    ```sh
    sudo mkfs.ext4 -i 4096 /dev/sdXN # Замените /dev/sdXN на ваш раздел
    ```

4. **Монтирование и восстановление данных**

    ```sh
    sudo mount /dev/sdXN /path/to/your/mountpoint
    sudo rsync -avh /path/to/backup/ /path/to/your/mountpoint/
    ```

## Дополнительная информация

### Альтернативы файловым системам со статическим выделением Inode

Файловые системы, такие как **XFS** или **Btrfs**, выделяют inodes динамически, поэтому у них нет проблемы с исчерпанием их запаса. Миграция на одну из этих ФС может быть долгосрочным решением для систем с непредсказуемым или большим количеством файлов.

### Защита от небезопасных ссылок

Для получения информации о механизмах защиты от атак с использованием символических и жестких ссылок см. [Защита от небезопасных ссылок (symlinks и hardlinks)](../../Security/fstec_linux.md#Защита-от-небезопасных-ссылок-symlinks-и-hardlinks).
