# Ссылки, Inode и Dentry

## Определения

- **Индексный дескриптор (Inode / Index Node):** Фундаментальная структура данных файловой системы, хранящая метаданные об объекте (права, владелец, размер, временные метки), за исключением его имени. Имя файла в Unix — это лишь запись в каталоге, ссылающаяся на номер Inode.
- **Жёсткая ссылка (Hard Link):** Вторая (или последующая) запись в каталоге, указывающая на тот же самый номер Inode, что и оригинальный файл. С точки зрения ядра все жесткие ссылки на один файл абсолютно равноправны.
- **Символическая ссылка (Symlink / Soft Link):** Специальный файл-указатель, содержимым которого является путь к другому объекту. Имеет собственный уникальный Inode.
- **Запись каталога (Dentry / Directory Entry):** Объект в оперативной памяти (VFS), связывающий имя файла с его Inode. Используется для кэширования путей и ускорения доступа к файлам.

## Индексный дескриптор (Inode)

Каждый объект файловой системы (файл, каталог, ссылка, устройство) идентифицируется уникальным номером Inode в пределах своей точки монтирования.

### Структура и содержимое (на примере ext4)
В ФС ext4 стандартный размер Inode составляет **256 байт**. В нем хранятся следующие данные:
- **Mode:** тип файла и права доступа (битовая маска `rwx` + SUID/SGID/Sticky).
- **UID/GID:** идентификаторы владельца и группы.
- **Size:** размер файла в байтах.
- **Links count (`i_nlink`):** количество жестких ссылок на этот Inode.
- **Timestamps:**
    - `atime` (access): время последнего чтения данных.
    - `mtime` (modify): время последнего изменения **контента**.
    - `ctime` (change): время последнего изменения **метаданных** (прав, владельца) или статуса Inode.
    - `btime` (birth): время создания файла (поддерживается в ядрах 4.11+ и ФС ext4, XFS, Btrfs).
- **Указатели на блоки:** В ext4 используются **экстенты (extents)** — структуры, описывающие непрерывные диапазоны блоков, что значительно эффективнее старых схем с прямыми и косвенными указателями.

### Особенности распределения Inode
- **Статическое (ext4):** Количество Inode фиксируется в момент создания ФС (`mkfs.ext4 -i`). Если в системе создано миллионы мелких файлов, Inode могут закончиться при наличии свободного места на диске. Диагностика: `df -i`.
- **Динамическое (XFS, Btrfs):** Inode выделяются по мере необходимости, пока доступно дисковое пространство.

## Жесткие ссылки (Hard Links)

Жёсткая ссылка — это запись в каталоге вида **"имя -> номер Inode"**.

- **Синтаксис:** `ln [TARGET] [LINK_NAME]`
- **Механика счётчика:** Поле `i_nlink` в Inode инкрементируется при каждом создании жесткой ссылки.
- **Равноправие:** Нет разницы между «оригиналом» и жесткой ссылкой. Данные существуют, пока `i_nlink > 0`.
- **Ограничения:**
    - Нельзя создавать жесткие ссылки на директории (запрещено ядром для предотвращения циклов в иерархии). Исключение: записи `.` (ссылка на себя) и `..` (ссылка на родителя).
    - Нельзя создавать ссылки между разными файловыми системами (разделами), так как номера Inode уникальны только в рамках одной ФС.

### Логика `nlink` для директорий
Для каталогов значение `i_nlink` всегда $\ge 2$:
1. Ссылка из родительского каталога (имя папки).
2. Ссылка `.` внутри самой директории.
3. Каждая поддиректория добавляет **+1** к счетчику родителя за счет своей записи `..`.
Это позволяет ядру мгновенно определять, является ли каталог пустым.

## Символические ссылки (Symlinks)

Символическая ссылка — это файл, содержащий путь (абсолютный или относительный).

- **Синтаксис:** `ln -s [TARGET] [LINK_NAME]`
- **Механика:** При обращении к симлинку ядро считывает путь и выполняет повторный поиск (path resolution).
- **Fast Symlinks:** Если путь короткий (обычно < 60 байт), он хранится прямо в структуре Inode (в поле для указателей на блоки), что позволяет избежать обращения к диску за данными ссылки.
- **Ограничения:**
    - Лимит вложенности: ядро прекращает поиск после **40** последовательных переходов (`MAXSYMLINKS`), чтобы избежать зацикливания.
    - Права доступа симлинка (отображаются в `ls -l`) обычно игнорируются; проверяются права только целевого объекта.

## Запись каталога (Dentry) и кэширование

В то время как Inode — это дисковая структура, **Dentry** — это резидентная в памяти структура ядра.

- **Dcache (Dentry Cache):** Кэш, хранящий сопоставление путей и Inode. Без dcache ядру пришлось бы при каждом обращении к `/usr/bin/ls` последовательно считывать блоки данных каталогов `/`, `/usr` и `/usr/bin` с диска.
- **Slab Allocator:** Объекты dentry и inode управляются через специализированные кэши в RAM. При нехватке памяти ядро вызывает `slab shrinkers`, которые в первую очередь очищают неиспользуемые dentry (т.н. `VFS cache`). Подробнее: **[Slab Allocator](../Core/memory/slab_allocator.md)**.

## Механика удаления и перемещения

### Удаление (unlink)
Команда `rm` выполняет системный вызов `unlink()`:
1. Удаляется запись "имя -> Inode" из каталога.
2. Счётчик `i_nlink` в Inode уменьшается на 1.
3. Если `i_nlink == 0` **И** ни один процесс не держит файл открытым, блоки данных и Inode помечаются как свободные.
**Важно:** Для удаления файла требуются права на запись (`w`) и выполнение (`x`) в **родительском каталоге**, а не права на сам файл.

### Перемещение (rename)
- **В пределах одной ФС:** Операция `mv` атомарно меняет запись в каталоге. Inode и блоки данных не меняются. Это мгновенная операция вне зависимости от размера файла.
- **Между разными ФС:** Выполняется физическое копирование данных (`cp`) с последующим удалением оригинала (`rm`). Inode меняется.

## Практические сценарии

### 1. Инспекция метаданных через `stat`
Утилита `stat` — основной инструмент для просмотра данных из Inode.
```bash
stat /etc/hosts
# → Inode: 12345  Links: 1
# → Access: (0644/-rw-r--r--)  Uid: ( 0/ root)  Gid: ( 0/ root)
# → Access: 2026-08-10 10:00:00  (atime)
# → Modify: 2026-08-10 09:30:00  (mtime)
# → Change: 2026-08-10 09:30:00  (ctime)
```

### 2. Поиск всех имен файла (Hard Links)
Если нужно найти все жесткие ссылки на конкретный объект:
```bash
# Найти все файлы на разделе с тем же номером Inode
find / -inum $(stat -c %i /path/to/file) 2>/dev/null
```

### 3. Инкрементальные бэкапы
Инструменты типа `rsync --link-dest` создают жесткие ссылки на неизмененные файлы из предыдущего бэкапа. Это позволяет иметь несколько "полных" слепов системы, которые физически занимают место только один раз.

## Безопасность и защита ссылок

Ядро предоставляет механизмы защиты от атак через ссылки в общих каталогах (например, `/tmp`):
- `fs.protected_symlinks=1`: Запрещает следование по симлинкам в "липких" (sticky) директориях, если владелец ссылки не совпадает с владельцем целевого файла или текущим пользователем.
- `fs.protected_hardlinks=1`: Запрещает создание жестких ссылок на файлы, которыми пользователь не владеет или не имеет прав на чтение/запись.

Подробнее: **[Защита ссылок](../Security/Fstec/kernel_runtime_protection.md#защита-от-небезопасных-ссылок-symlinks-и-hardlinks)**.
