# LVM — Обзор и основные концепции

## Определения

**LVM (Logical Volume Manager — менеджер логических томов)** — система управления дисковым пространством в Linux, предоставляющая слой абстракции между физическими накопителями и файловыми системами.

**Device Mapper** — фреймворк ядра Linux, обеспечивающий отображение (mapping) одного блочного устройства на другое. Является основой для LVM, программных RAID (dm-raid) и шифрования (dm-crypt).

**Physical Volume (PV — физический том)** — диск, раздел или блочное устройство (например, LUKS-контейнер), инициализированное для LVM. Содержит метку и метаданные LVM.

**Volume Group (VG — группа томов)** — виртуальный пул, объединяющий ресурсы одного или нескольких PV. VG представляет собой единое адресное пространство для нарезки томов.

**Logical Volume (LV — логический том)** — виртуальный раздел, создаваемый из пространства VG. Для ОС выглядит как стандартное блочное устройство.

**Physical Extent (PE — физический экстент)** — минимальный квант данных (блок) в LVM. Все операции выделения места происходят кратно размеру PE.

## Базовые концепции

### Зачем нужен LVM: Проблемы классической схемы

Классическая схема разделов (MBR/GPT) имеет критическое ограничение: **свободное пространство можно добавить только к последнему разделу**. Это создаёт проблемы в динамических средах, где потребности сервисов меняются.

#### Почему нельзя расширить средний раздел?

При изменении размера не-last раздела изменяется его **начальный сектор**, что нарушает позицию суперблока файловой системы:

```bash
# Структура: sdb1 (1G) → sdb2 (1G) → sdb3 (1G) → свободно 7G
# Задача: добавить место к sdb3

# При расширении sdb2 удаляется и создаётся заново с новым концом
# Это СДВИГАЕТ начало sdb3 — суперблок ФС на sdb3 больше не на своём месте
# Результат: файловая система на sdb3 разрушена
```

Суперблок файловой системы (например, XFS хранит его со смещением 1024 байта от начала) имеет **фиксированную позицию**. Изменение начала раздела делает ФС неработоспособной — утилиты восстановления (fsck) не могут это исправить.

#### Решение: LVM

LVM вводит слой абстракции, где логические тома **не привязаны к физической позиции**:

| Операция | Классическая схема | LVM |
|:---------|:-------------------|:----|
| Расширить последний раздел | Возможно (с оговорками) | Возможно |
| Расширить средний раздел | **Невозможно** | Возможно онлайн |
| Перенести данные на другой диск | Требует остановки | `pvmove` онлайн |

### Иерархическая структура

Архитектура LVM строится по принципу снизу вверх:
1.  **PV Layer:** Подготовка носителей. В начале каждого PV резервируется **Metadata Area** (по умолчанию 1 МиБ) в виде кольцевого буфера в формате ASCII.
2.  **VG Layer:** Агрегация PV. Здесь определяется размер PE (по умолчанию **4 МиБ**).
3.  **LV Layer:** Выделение LE (Logical Extents), которые сопоставляются с PE.

### Типы логических томов (Mapping)

LVM поддерживает различные стратегии размещения данных на физических дисках:

| Тип тома | Отказоустойчивость | Производительность | Описание |
| :--- | :--- | :--- | :--- |
| **Linear** | Нет | Одиночный диск | Данные пишутся последовательно. Базовый тип. |
| **Striped** | Нет | **Высокая** | Аналог RAID 0. Чередование между PV. |
| **RAID 1/5/6/10** | **Высокая** | Зависит от уровня | Встроенная избыточность. См. [LVM RAID](./advanced_topics/advanced_topics.md#lvm-raid-и-отказоустойчивость). |

### LVM и RAID: Две архитектуры

Существует два подхода к комбинированию LVM и RAID:

#### Подход 1: LVM поверх RAID (Рекомендуемый)

RAID-массив выступает как обычное блочное устройство, которое инициализируется как PV:

```bash
# Создание RAID1 из двух дисков
sudo mdadm --create /dev/md127 --level=1 --raid-devices=2 /dev/sdb /dev/sdc

# Инициализация RAID как PV
sudo pvcreate /dev/md127

# Добавление в VG
sudo vgextend vg_data /dev/md127
```

**Преимущества:**
- LVM работает с RAID как с единым блочным устройством
- Можно использовать `pvmove` для миграции между массивами
- Гибкость LVM + отказоустойчивость RAID

#### Подход 2: Встроенный RAID в LVM

LVM имеет собственный механизм RAID (`lvcreate --type raid1`), использующий dm-raid:

```bash
# Создание RAID1 напрямую в LVM
sudo lvcreate --type raid1 -L 10G -n lv_raid vg_data /dev/sdb /dev/sdc
```

**Особенности:**
- Управление через LVM-команды (`lvconvert --replace` для замены диска)
- Синхронизация метаданных между слоями

#### Бесшовная конвертация: Обычный диск → RAID

Одно из главных преимуществ LVM — возможность **онлайн-конвертации** обычного диска в RAID без остановки сервиса:

```bash
# 1. Создать degraded RAID1 (один диск)
sudo mdadm --create /dev/md127 --level=1 --raid-devices=2 /dev/sdb missing

# 2. Добавить RAID в VG
sudo vgextend vg_data /dev/md127

# 3. Перенести данные с исходного диска на RAID
sudo pvmove /dev/sdc /dev/md127

# 4. Удалить исходный диск из VG
sudo vgreduce vg_data /dev/sdc

# 5. Добавить исходный диск в RAID
sudo mdadm /dev/md127 --add /dev/sdc
```

Все операции выполняются **без размонтирования** — файловые системы остаются доступными для чтения и записи.

### Размер PE и его влияние

- **Значение:** По умолчанию 4 МиБ. Можно изменить при создании VG (`vgcreate -s`).
- **Гранулярность:** PE определяет минимальный шаг изменения размера LV.
- **Производительность:** В LVM2 размер PE не влияет на скорость I/O, но влияет на скорость работы утилит управления (`lvs`, `vgs`) на огромных массивах (100+ ТБ). Для таких систем рекомендуется увеличивать PE до 32–128 МиБ.
- **Перерасход (Overhead):** При создании PV теряется ~4 МиБ на Metadata Area. LV, созданный размером 5 МиБ, фактически займёт 1 PE (8 МиБ с округлением вверх). Все операции выделения кратны размеру PE.

### Онлайн-расширение: Ключевое преимущество LVM

Главное преимущество LVM — возможность расширять **любой** логический том без остановки сервиса:

```bash
# Расширение LV и файловой системы одной командой
sudo lvextend -L +2G -r /dev/vg_data/lv_app
# → Logical volume vg_data/lv_app successfully resized.
# → resize2fs вызван автоматически
```

- Флаг `-r` (`--resizefs`) автоматически определяет тип ФС и вызывает нужную команду (`resize2fs`, `xfs_growfs`, `btrfs resize`).
- Флаг `-l +100%FREE` задействует всё свободное место VG.

**Поддержка файловыми системами:**

| ФС | Расширение | Уменьшение |
|:---|:-----------|:-----------|
| ext2/ext3/ext4 | Онлайн | Офлайн |
| XFS | Онлайн | **Не поддерживается** |
| Btrfs | Онлайн | Онлайн |

### Именование устройств и пути

LVM предоставляет два эквивалентных пути к одному и тому же устройству:

1.  **/dev/mapper/vgname-lvname** — канонический путь Device Mapper. Если в именах VG/LV есть дефис, он дублируется (например, `vg--data-lv--app`).
2.  **/dev/vgname/lvname** — удобная символическая ссылка, создаваемая LVM.

*Рекомендация:* Для `/etc/fstab` и загрузчика лучше использовать `/dev/mapper/` или UUID, для командной строки — `/dev/vgname/lvname`.

## Практические сценарии

### Создание базовой структуры хранения

Типовой процесс подготовки диска:

**Шаг 1: Инициализация PV**
```bash
sudo pvcreate /dev/sdb
# → Physical volume "/dev/sdb" successfully created.
```

**Шаг 2: Создание VG с увеличенным размером PE**
Полезно для будущих массивов большого объема.
```bash
sudo vgcreate -s 32M vg_data /dev/sdb
# → Volume group "vg_data" successfully created
```

**Шаг 3: Создание тома RAID 1**
```bash
sudo lvcreate --type raid1 -L 10G -n lv_critical vg_data
# → Logical volume "lv_critical" created.
```

**Шаг 4: Подготовка файловой системы**
```bash
sudo mkfs.ext4 /dev/vg_data/lv_critical
sudo mount /dev/vg_data/lv_critical /mnt/data
```

## Дополнительная информация

### Особенности эксплуатации и загрузки

Для глубокой настройки системы LVM (особенно при размещении корневого раздела на LVM) крайне важны следующие аспекты:
- **Фильтрация устройств:** Настройка `lvm.conf` для исключения конфликтов (Multipath, SAN).
- **Взаимодействие с загрузкой:** Настройка `initramfs`, `dracut` и служб `systemd` для активации VG.
- **Размещение /boot:** Рекомендации по выносу загрузочного раздела за пределы LVM.
