# LVM — Обзор и основные концепции

## Определения

**LVM (Logical Volume Manager — менеджер логических томов)** — система управления дисковым пространством в Linux, предоставляющая слой абстракции между физическими накопителями и файловыми системами. Позволяет создавать, изменять размеры, перемещать и удалять логические тома без остановки сервисов и привязки к физической позиции диска.

**Device Mapper** — фреймворк ядра Linux, обеспечивающий отображение (mapping) одного блочного устройства на другое. Является основой для LVM, программных RAID (dm-raid) и шифрования (dm-crypt). LVM выступает как пользовательский интерфейс для Device Mapper, управляя таблицами сопоставления (DM tables) через утилиты `dmsetup`, `lvm` и демон `dmeventd`.

**Physical Volume (PV — физический том)** — диск, раздел или блочное устройство (например, LUKS-контейнер), инициализированное для LVM. Содержит метку и метаданные LVM. Каждый PV имеет уникальный UUID, который сохраняется в метаданных и в области MDA (Metadata Area).

**Volume Group (VG — группа томов)** — виртуальный пул, объединяющий ресурсы одного или нескольких PV. VG представляет собой единое адресное пространство для нарезки томов. Имя VG уникально в пределах системы (при конфликтах имен при клонировании дисков используется `vgimportclone`).

**Logical Volume (LV — логический том)** — виртуальный分区, создаваемый из пространства VG. Для ОС выглядит как стандартное блочное устройство. LV может быть активным (available) или неактивным (unavailable), что определяется таблицей Device Mapper.

**Physical Extent (PE — физический экстент)** — минимальный квант данных (блок) в LVM. Все операции выделения места происходят кратно размеру PE. По умолчанию 4 МиБ, может быть увеличен при создании VG (`vgcreate -s 32M`).

**Metadata Area (MDA — область метаданных)** — участок в начале каждого PV (по умолчанию 1 МиБ), содержащий конфигурацию VG в формате ASCII. Организована как кольцевой буфер (ring buffer) — при обновлении метаданных новые данные записываются поверх старых с циклическим перезаписыванием. Наличие MDA позволяет восстановить VG из backup-файла.

**Device Mapper Table (таблица DM)** — структура данных в ядре, определяющая как блочное устройство отображается на физические ресурсы. Каждый LV соответствует одной или нескольким записям в таблице DM. Формат: `<logical_start_sector> <num_sectors> <target_type> <target_args>`.

## Базовые концепции

### Архитектура Device Mapper и роль LVM

Device Mapper работает на уровне ядра и предоставляет три ключевых абстракции:

```
┌─────────────────────────────────────────────────────┐
│                   Файловая система                    │
├─────────────────────────────────────────────────────┤
│              LVM (управление томами)                  │
├─────────────────────────────────────────────────────┤
│           Device Mapper (ядро Linux)                 │
│  ┌───────────┬───────────┬───────────┬────────────┐ │
│  │  linear   │  striped  │  mirror   │    thin    │ │
│  │  (линейный) │ (чередование) │ (зеркало) │ (тонкий)  │ │
│  └───────────┴───────────┴───────────┴────────────┘ │
├─────────────────────────────────────────────────────┤
│           Физические устройства ( block devices )     │
└─────────────────────────────────────────────────────┘
```

**Типы таргетов (targets)** — алгоритмы распределения данных, доступные в Device Mapper:

| Таргет | Тип | Описание |
|:---|:---|:---|
| `linear` | Базовый | Последовательное объединение участков. Основа для Linear LV. |
| `striped` | Производительность | Чередование блоков между устройствами (аналог RAID 0). |
| `mirror` | Отказоустойчивость | Зеркалирование данных (аналог RAID 1). |
| `snapshot` | Бэкап/откат | Копирование при записи (COW). Основа для снимков. |
| `thin-pool` | Масштабируемость | Пул с динамическим выделением места. Основа для Thin LV. |
| `cache` | Ускорение | Прозрачное кэширование SSD→HDD. |
| `crypt` | Безопасность | Шифрование данных (LUKS/dm-crypt). |

LVM управляет таблицами DM через утилиту `dmsetup` (на уровне ядра) и предоставляет пользователю удобный интерфейс (`pvcreate`, `lvcreate`, `vgextend` и т.д.).

### Зачем нужен LVM: Проблемы классической схемы

Классическая схема разделов (MBR/GPT) имеет критическое ограничение: **свободное пространство можно добавить только к последнему разделу**. Это создаёт проблемы в динамических средах, где потребности сервисов меняются.

#### Почему нельзя расширить средний раздел?

При изменении размера не-last раздела изменяется его **начальный сектор**, что нарушает позицию суперблока файловой системы:

```bash
# Структура: sdb1 (1G) → sdb2 (1G) → sdb3 (1G) → свободно 7G
# Задача: добавить место к sdb3

# При расширении sdb2 удаляется и создаётся заново с новым концом
# Это СДВИГАЕТ начало sdb3 — суперблок ФС на sdb3 больше не на своём месте
# Результат: файловая система на sdb3 разрушена
```

Суперблок файловой системы (например, XFS хранит его со смещением 1024 байта от начала) имеет **фиксированную позицию**. Изменение начала раздела делает ФС неработоспособной — утилиты восстановления (fsck) не могут это исправить.

#### Решение: LVM

LVM вводит слой абстракции, где логические тома **не привязаны к физической позиции**:

| Операция | Классическая схема | LVM |
|:---------|:-------------------|:----|
| Расширить последний раздел | Возможно (с оговорками) | Возможно |
| Расширить средний раздел | **Невозможно** | Возможно онлайн |
| Перенести данные на другой диск | Требует остановки | `pvmove` онлайн |
| Создать резервную копию | Требует dd/backup | Снимок (snapshot) за секунды |
| Шифрование | Раздел-за-разделом | LV с dm-crypt |

### Иерархическая структура

Архитектура LVM строится по принципу снизу вверх:
1.  **PV Layer:** Подготовка носителей. В начале каждого PV резервируется **Metadata Area** (по умолчанию 1 МиБ) в виде кольцевого буфера в формате ASCII.
2.  **VG Layer:** Агрегация PV. Здесь определяется размер PE (по умолчанию **4 МиБ**).
3.  **LV Layer:** Выделение LE (Logical Extents), которые сопоставляются с PE.

Каждый уровень имеет свою область ответственности:
- **PV** — управление физическими дисками и их инициализация
- **VG** — объединение дисковых ресурсов и управление пространством
- **LV** — предоставление томов для файловых систем и приложений

### Толстое и тонкое провизионирование: Концептуальное сравнение

LVM поддерживает два принципиально различных подхода к выделению пространства:

**Thick Provisioning (толстое провизионирование)** — физическое пространство выделяется **полностью и сразу** при создании LV. Данные записываются напрямую в выделенные экстенты:

```bash
# Thick LV: 100G физически заняты сразу
sudo lvcreate -L 100G -n lv_thick vg_data
```

**Thin Provisioning (тонкое провизионирование)** — физическое пространство выделяется **по мере записи данных** из общего пула. Пул может быть переподписан (overcommit) — суммарный размер LV может превышать размер пула:

```bash
# Thin LV: физически занято только то, что реально записано
sudo lvcreate -V 100G -T vg_data/thin_pool -n lv_thin
```

| Параметр | Thick | Thin |
|:---|:---|:---|
| Начальное выделение | Полный размер | 0 (только метаданные) |
| Overcommit | Невозможен | Возможен (риск заполнения пула) |
| Производительность | Предсказуемая | Зависит от заполнения пула |
| Восстановление | Стандартное | Требует `thin_repair` при повреждении метаданных |
| Мониторинг | `Data%` не нужен | Критичен: `data_percent`, `meta_percent` |

*Подробнее о тонком провизионировании: [LVM — Тонкое провизионирование](./thin-provisioning.md).*

### Типы логических томов (Mapping)

LVM поддерживает различные стратегии размещения данных на физических дисках:

| Тип тома | Отказоустойчивость | Производительность | Описание |
| :--- | :--- | :--- | :--- |
| **Linear** | Нет | Одиночный диск | Данные пишутся последовательно. Базовый тип. |
| **Striped** | Нет | **Высокая** | Аналог RAID 0. Чередование между PV. |
| **RAID 1/5/6/10** | **Высокая** | Зависит от уровня | Встроенная избыточность. См. [LVM RAID](./advanced_topics/advanced_topics.md#lvm-raid-и-отказоустойчивость). |
| **Thin** | Зависит от конфигурации | Динамическая | Динамическое выделение из thin pool. См. [Thin Provisioning](./thin-provisioning.md). |
| **Cache** | Нет | **Высокая** (read/write) | Ускорение SSD-кэшем. См. [LVM Cache](./advanced_topics/advanced_topics.md#lvm-cache-dm-cache). |

### LVM и RAID: Две архитектуры

Существует два подхода к комбинированию LVM и RAID:

#### Подход 1: LVM поверх RAID (Рекомендуемый)

RAID-массив выступает как обычное блочное устройство, которое инициализируется как PV:

```bash
# Создание RAID1 из двух дисков
sudo mdadm --create /dev/md127 --level=1 --raid-devices=2 /dev/sdb /dev/sdc

# Инициализация RAID как PV
sudo pvcreate /dev/md127

# Добавление в VG
sudo vgextend vg_data /dev/md127
```

**Преимущества:**
- LVM работает с RAID как с единым блочным устройством
- Можно использовать `pvmove` для миграции между массивами
- Гибкость LVM + отказоустойчивость RAID

#### Подход 2: Встроенный RAID в LVM

LVM имеет собственный механизм RAID (`lvcreate --type raid1`), использующий dm-raid:

```bash
# Создание RAID1 напрямую в LVM
sudo lvcreate --type raid1 -L 10G -n lv_raid vg_data /dev/sdb /dev/sdc
```

**Особенности:**
- Управление через LVM-команды (`lvconvert --replace` для замены диска)
- Синхронизация метаданных между слоями

#### Бесшовная конвертация: Обычный диск → RAID

Одно из главных преимуществ LVM — возможность **онлайн-конвертации** обычного диска в RAID без остановки сервиса:

```bash
# 1. Создать degraded RAID1 (один диск)
sudo mdadm --create /dev/md127 --level=1 --raid-devices=2 /dev/sdb missing

# 2. Добавить RAID в VG
sudo vgextend vg_data /dev/md127

# 3. Перенести данные с исходного диска на RAID
sudo pvmove /dev/sdc /dev/md127

# 4. Удалить исходный диск из VG
sudo vgreduce vg_data /dev/sdc

# 5. Добавить исходный диск в RAID
sudo mdadm /dev/md127 --add /dev/sdc
```

Все операции выполняются **без размонтирования** — файловые системы остаются доступными для чтения и записи.

### Размер PE и его влияние

- **Значение:** По умолчанию 4 МиБ. Можно изменить при создании VG (`vgcreate -s`).
- **Гранулярность:** PE определяет минимальный шаг изменения размера LV.
- **Производительность:** В LVM2 размер PE не влияет на скорость I/O, но влияет на скорость работы утилит управления (`lvs`, `vgs`) на огромных массивах (100+ ТБ). Для таких систем рекомендуется увеличивать PE до 32–128 МиБ.
- **Перерасход (Overhead):** При создании PV теряется ~4 МиБ на Metadata Area. LV, созданный размером 5 МиБ, фактически займёт 1 PE (8 МиБ с округлением вверх). Все операции выделения кратны размеру PE.

### Онлайн-расширение: Ключевое преимущество LVM

Главное преимущество LVM — возможность расширять **любой** логический том без остановки сервиса:

```bash
# Расширение LV и файловой системы одной командой
sudo lvextend -L +2G -r /dev/vg_data/lv_app
# → Logical volume vg_data/lv_app successfully resized.
# → resize2fs вызван автоматически
```

- Флаг `-r` (`--resizefs`) автоматически определяет тип ФС и вызывает нужную команду (`resize2fs`, `xfs_growfs`, `btrfs resize`).
- Флаг `-l +100%FREE` задействует всё свободное место VG.

**Поддержка файловыми системами:**

| ФС | Расширение | Уменьшение |
|:---|:-----------|:-----------|
| ext2/ext3/ext4 | Онлайн | Офлайн |
| XFS | Онлайн | **Не поддерживается** |
| Btrfs | Онлайн | Онлайн |

### Состояния активации (Activation States)

Каждый LV может находиться в одном из состояний, определяемых ядром через Device Mapper:

| Состояние | Атрибут `lvs` | Описание |
|:---|:---|:---|
| **Active** | `a` | Том доступен, таблица DM загружена, ФС может быть смонтирована. |
| **Inactive** | `-` | Том не активирован, данные доступны только на уровне блочных устройств. |
| **Partial** | `p` | Активирован частично (недоступны некоторые PV, например, при degraded RAID). |

Активация/деактивация:
```bash
# Активировать все LV в VG
sudo vgchange -ay vg_data

# Деактивировать конкретный LV
sudo lvchange -an vg_data/lv_app

# Принудительная частичная активация (при потере PV)
sudo vgchange -ay --partial vg_data
```

**Мониторинг активации:** Демон `dmeventd` (управляется через `lvm2-monitor.service`) отслеживает изменения состояния LV и автоматически реагирует (например, расширяет снимки при заполнении). Рекомендуется держать его включённым на всех серверах.

### Именование устройств и пути

LVM предоставляет несколько способов обращения к одному и тому же устройству:

1.  **/dev/mapper/vgname-lvname** — канонический путь Device Mapper. Если в именах VG/LV есть дефис, он дублируется (например, `vg--data-lv--app`). Рекомендуется для `/etc/fstab` и загрузчика.
2.  **/dev/vgname/lvname** — удобная символическая ссылка, создаваемая LVM. Удобна для командной строки.
3.  **UUID блочного устройства** — наиболее стабильный вариант для `/etc/fstab`, так как не зависит от порядка обнаружения дисков:
   ```bash
   # Получение UUID
   sudo blkid /dev/vg_data/lv_app
   # → /dev/vg_data/lv_app: UUID="a1b2c3d4-..." TYPE="ext4"

   # Использование в fstab
   UUID=a1b2c3d4-...  /mnt/data  ext4  defaults  0  2
   ```
4.  **/dev/disk/by-id/** — символьные ссылки с понятными именами (с учётом модели диска). Полезны для идентификации физических устройств.

**Рекомендация по приоритету:** UUID (fstab/boot) > /dev/mapper/ (ручные команды) > /dev/vgname/ (удобство).

## Практические сценарии

### Создание базовой структуры хранения

Типовой процесс подготовки диска:

**Шаг 1: Инициализация PV**
```bash
sudo pvcreate /dev/sdb
# → Physical volume "/dev/sdb" successfully created.
```

**Шаг 2: Создание VG с увеличенным размером PE**
Полезно для будущих массивов большого объема.
```bash
sudo vgcreate -s 32M vg_data /dev/sdb
# → Volume group "vg_data" successfully created
```

**Шаг 3: Создание тома RAID 1**
```bash
sudo lvcreate --type raid1 -L 10G -n lv_critical vg_data
# → Logical volume "lv_critical" created.
```

**Шаг 4: Подготовка файловой системы**
```bash
sudo mkfs.ext4 /dev/vg_data/lv_critical
sudo mount /dev/vg_data/lv_critical /mnt/data
```

### Расширение VG и LV (онлайн)

Добавление нового диска и расширение существующего тома:

**Шаг 1: Подготовка нового диска**
```bash
# Проверка доступности диска
lsblk /dev/sdc
# → NAME   MAJ:MIN RM SIZE RO TYPE MOUNTPOINT
# → sdc      8:32   0  100G  0 disk

# Очистка метаданных (если диск был использован)
sudo wipefs -a /dev/sdc

# Инициализация PV
sudo pvcreate /dev/sdc
# → Physical volume "/dev/sdc" successfully created.
```

**Шаг 2: Добавление PV в VG**
```bash
sudo vgextend vg_data /dev/sdc
# → Volume group "vg_data" successfully extended
# → Physical volume "/dev/sdc" changed
```

**Шаг 3: Расширение LV с авто-расширением ФС**
```bash
sudo lvextend -l +100%FREE -r /dev/vg_data/lv_app
# → Size of logical volume vg_data/lv_app changed from 50.00 GiB to 100.00 GiB.
# → resize2fs called automatically
```

**Шаг 4: Проверка**
```bash
sudo vgs vg_data
# → VG      #PV #LV #SN Attr   VSize   VFree
# → vg_data   2   3   0 wz--n- 150.00g    0

sudo lvs vg_data/lv_app
# → LV      VG      Attr       LSize   Pool Origin Data%  Meta%
# → lv_app  vg_data -wi-ao---- 100.00g
```

### Мониторинг и базовые проверки

Регулярные команды для проверки состояния LVM:

```bash
# Сводка по VG (свободное место, количество LV)
sudo vgs
# → VG      #PV #LV #SN Attr   VSize   VFree
# → vg_data   2   3   0 wz--n- 150.00g 50.00g

# Сводка по LV (размер, пул, использование)
sudo lvs
# → LV      VG      Attr       LSize   Pool       Origin Data%  Meta%
# → lv_app  vg_data Vwi-a-t--  50.00g thin_pool          45.23
# → lv_data vg_data -wi-ao---- 100.00g

# Проверка PV (свободное место на каждом диске)
sudo pvs
# → PV         VG      Fmt  Attr PSize   PFree
# → /dev/sdb   vg_data lvm2 a--  <50.00g 4.00g
# → /dev/sdc   vg_data lvm2 a-- <100.00g  0

# Проверка статуса dmeventd (мониторинг)
sudo systemctl status lvm2-monitor.service
# → ● lvm2-monitor.service - Monitoring of LVM2 mirrors and snapshots
# →    Active: active (running)
```

### fsfreeze: Гарантия целостности при создании снимков

Для получения **-consistent** (цельного) снимка файловой системы необходимо использовать `fsfreeze` перед созданием снимка:

```bash
# 1. Заморозка ФС (garantie that all pending writes are flushed)
sudo fsfreeze --freeze /mnt/data

# 2. Создание снимка
sudo lvcreate -s -L 10G -n snap_backup /dev/vg_data/lv_data

# 3. Разморозка ФС (ОБЯЗАТЕЛЬНО!)
sudo fsfreeze --unfreeze /mnt/data
```

**Почему это важно:**
- Без `fsfreeze` снимок может содержать незавершённые операции записи (partial writes)
- Для XFS и Btrfs — `fsfreeze` **обязателен** (нет online-уменьшения)
- Для ext4 — допустимо без `fsfreeze`, но для бэкапов рекомендуется `fsfreeze`

**Примечание:** `fsfreeze` блокирует ВСЕ операции записи на ФС до `--unfreeze`. Не используйте на производственных серверах без понимания последствий (кратковременная блокировка I/O).

### Write Barriers и безопасное завершение

**Write Barrier (барьер записи)** — механизм ядра Linux, гарантирующий, что данные, записанные после барьера, физически находятся на диске. Критичен для целостности данных при сбоях питания.

#### Когда барьеры важны для LVM

- **Thin provisioning:** При сбое без барьеров thin pool может оказаться в неконсистентном состоянии (данные записаны, но метаданные — нет).
- **Снимки (COW):** Без барьеров снимок может содержать неполные копии блоков.
- **LVM RAID:** Барьеры предотвращают "write hole" при сбое во время ребилда.

#### Настройка барьеров

```bash
# Проверка текущих барьеров на LV
sudo tune2fs -l /dev/vg_data/lv_data | grep "Filesystem features"
# → Filesystem features: has_journal extents ...
# → (barriers включены по умолчанию если есть BBU или SSD)

# Монтирование с барьерами (ext4)
sudo mount -o barrier=1 /dev/vg_data/lv_data /mnt/data
# → barrier=1: барьеры включены (по умолчанию)
# → barrier=0: барьеры ОТКЛЮЧЕНЫ ( Gefahr! только с BBU)

# XFS — барьеры включены по умолчанию
sudo mount -o nobarrier /dev/vg_data/lv_data /mnt/data  # ОПАСНО без BBU
```

#### Безопасное завершение работы (Safe Shutdown)

При аварийном завершении (отключение питания) LVM может оказаться в неконсистентном состоянии:

1. **Thin pool:** Метаданные могут не совпадать с данными.
2. **Снимки:** COW-буфер может содержать неполные блоки.
3. **VG метаданные:** MDA может быть повреждена.

**Порядок безопасного завершения:**

```bash
# 1. Остановить критичные сервисы
sudo systemctl stop postgresql redis mysql

# 2. Заморозить ФС (если нужен consistent снимок)
sudo fsfreeze --freeze /mnt/data

# 3. Создать снимок (если нужно)
sudo lvcreate -s -L 10G -n snap_before_shutdown /dev/vg_data/lv_data

# 4. Разморозить ФС
sudo fsfreeze --unfreeze /mnt/data

# 5. Деактивировать LV (для thin pool — дождаться завершения I/O)
sudo vgchange -an vg_data

# 6. Выполнить sync для сброса кэша
sync

# 7. Выключение
sudo shutdown -h now
```

#### fstab: опции для LVM

```bash
# /etc/fstab — оптимальные опции для LVM
/dev/vg_data/lv_data  /data  xfs  defaults,noatime,lazytime  0 2
/dev/vg_data/lv_swap  none   swap sw,pri=1                   0 0

# noatime — отключение обновления времени доступа (ускорение)
# lazytime — отложенный сброс временных меток (ядро 4.0+)
# barrier=1 — включены (по умолчанию для XFS)
```

### Автоматическое расширение Thin Pool и снимков

Настройка `dmeventd` для автоматического расширения при заполнении:

```bash
# Включение сервиса
sudo systemctl enable --now dmeventd

# Настройка порогов в /etc/lvm/lvm.conf
sudo vi /etc/lvm/lvm.conf
```

```ini
# Thin Pool
thin_pool_autoextend_threshold = 80   # Расширять при 80% заполнения
thin_pool_autoextend_percent = 20     # Расширять на 20% от текущего размера

# Снимки
snapshot_autoextend_threshold = 80
snapshot_autoextend_percent = 20
```

## Дополнительная информация

### Особенности эксплуатации и загрузки

Для глубокой настройки системы LVM (особенно при размещении корневого раздела на LVM) крайне важны следующие аспекты:
- **Фильтрация устройств:** Настройка `lvm.conf` для исключения конфликтов (Multipath, SAN).
- **Взаимодействие с загрузкой:** Настройка `initramfs`, `dracut` и служб `systemd` для активации VG.
- **Размещение /boot:** Рекомендации по выносу загрузочного раздела за пределы LVM.

Подробные инструкции и сценарии описаны в файле: **[LVM — Расширенные темы (Загрузка, Фильтры, RAID, Cache)](./advanced_topics/advanced_topics.md)**.

### Типичные ошибки и рекомендации для SRE

| Проблема | Причина | Решение |
|:---|:---|:---|
| Thin pool заполнен на 100% | Нет autoextend или порог слишком высокий | Настроить `thin_pool_autoextend_threshold = 80`, проверить `dmeventd` |
| Снимок заполнен | COW-буфер исчерпан | Расширить снимок (`lvextend`) или пересоздать, настроить `snapshot_autoextend_threshold` |
| VG не активируется | Повреждены метаданные | Использовать `vgcfgrestore` из backup (см. [practical_scenarios.md](./advanced_topics/practical_scenarios.md)) |
| LV в режиме read-only | Thin pool заполнен или I/O ошибки | Проверить `journalctl -k`, расширить pool, запустить `fsck` |
| Дубли UUID при клонировании | dd/rsync скопировал UUID PV | Использовать `vgimportclone` для переименования VG |
| pvmove завершается ошибкой | Нет свободного места в VG | Освободить место: `vgreduce`, `lvremove`, или добавить PV |

### Best Practices для DevOps/SRE

1. **Всегда используйте UUID** в `/etc/fstab` и конфигурации загрузчика — это устойчиво к перестановке дисков.
2. **Настройте `dmeventd`** и автоматическое расширение thin pool/snapshots на всех серверах.
3. **Регулярно делайте `vgcfgbackup`** — хотя backup-файлы создаются автоматически, храните копии на отдельном носителе.
4. **Тестируйте восстановление** на non-production окружении перед реальным инцидентом.
5. **Документируйте схему PV/VG/LV** для каждого сервера (в Wiki или Git).
6. **Не используйте снимки как permanent storage** — снимки замедляют запись и потребляют место в COW-буфере.
7. **Для критичных данных** комбинируйте LVM-снимки с `fsfreeze` и внешним бэкапом.
