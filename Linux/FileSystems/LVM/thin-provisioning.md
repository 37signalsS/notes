# LVM — Тонкое провизионирование (Thin Provisioning)

## Определения

**Тонкое провизионирование (Thin Provisioning)** — технология управления дисковым пространством, позволяющая выделять логическим томам виртуальный объем, значительно превышающий реально доступную физическую емкость.

**Тонкий пул (Thin Pool)** — специализированное логическое устройство (LV-контейнер), которое объединяет физическое пространство для хранения данных и область для метаданных. Он является «родительским» объектом для тонких томов.

**Тонкий том (Thin Volume)** — логический том, созданный внутри тонкого пула. Физическое место в пуле выделяется такому тому динамически только в момент записи данных (аллокация по требованию).

**Overcommit (Переподписка)** — ситуация, при которой суммарный виртуальный размер всех тонких томов превышает физический размер тонкого пула.

## Базовые концепции

### Механизм аллокации блоков

В отличие от традиционных (thick) томов, где экстенты резервируются при создании, в тонких томах используется отложенная аллокация:
1.  **Запрос на запись:** Операционная система пытается записать данные в блок тонкого тома.
2.  **Поиск свободного места:** LVM ищет свободный блок в тонком пуле.
3.  **Отображение (Mapping):** LVM создает связь между виртуальным адресом в тонком томе и физическим адресом в пуле.
4.  **Запись:** Данные физически сохраняются в пул.

### Важность TRIM / DISCARD

Для эффективной работы тонкого провизионирования крайне важно возвращать неиспользуемые блоки обратно в пул (например, после удаления файлов).
-   Файловая система должна быть примонтирована с опцией `discard` или периодически обрабатываться командой `fstrim`.
-   Без этого LVM будет считать блоки занятыми, даже если ФС пометила их как свободные, что приведет к преждевременному исчерпанию пула.

### Метаданные пула

Тонкий пул имеет отдельную область метаданных, где хранится карта отображения блоков.
-   **Критичность:** Переполнение области метаданных так же опасно, как и переполнение данными. Если метаданные закончатся, пул перейдет в режим `read-only` или `fail`.
-   **Рекомендация:** Начинайте с размера метаданных не менее 1 ГБ для больших пулов.

### Режимы при переполнении

Настраиваются в `lvm.conf` или через атрибуты тома:
-   **Reject:** Все попытки записи отклоняются с ошибкой I/O.
-   **Queue:** Операции записи ставятся в очередь в ожидании расширения пула (может вызвать «зависание» приложений).

## Практические сценарии

### Сценарий 1: Создание инфраструктуры тонкого пула

**Шаг 1: Создание пула**
Нужно указать размер данных (`-L`) и, желательно, размер метаданных (`--poolmetadatasize`).
```bash
sudo lvcreate -L 100G --poolmetadatasize 1G --thinpool tp_data vg0
# → Logical volume "tp_data" created.
```

**Шаг 2: Создание тонкого тома**
Указывается виртуальный размер (`-V`) и имя пула.
```bash
sudo lvcreate -V 1T --thin -n lv_app vg0/tp_data
# → Logical volume "lv_app" created.
```

### Сценарий 2: Мониторинг и реагирование

Для тонких пулов стандартного `df -h` недостаточно, так как он показывает виртуальный размер ФС.

**Проверка физического заполнения:**
```bash
sudo lvs -o lv_name,data_percent,metadata_percent vg0/tp_data
# → LV       Data%  Meta%
# → tp_data  75.20  12.40
```

**Ручное расширение пула:**
```bash
# Добавить 50 ГБ к физическому пространству пула
sudo lvextend -L +50G vg0/tp_data
```

### Сценарий 3: Настройка автоматического расширения

Чтобы избежать остановки сервисов при переполнении, используйте демон `dmeventd`.

**Правка `/etc/lvm/lvm.conf`:**
```ini
activation {
    # Расширять, если заполнено более 80%
    thin_pool_autoextend_threshold = 80
    # Добавлять 20% от текущего размера
    thin_pool_autoextend_percent = 20
}
```
*Примечание: Для работы этого механизма в VG всегда должно оставаться свободное место (VFree).*

### Сценарий 4: Тонкие снимки (Thin Snapshots)

Тонкие снимки создаются мгновенно и не занимают места, пока данные не начали меняться.

```bash
# Создание снимка
sudo lvcreate -s -n lv_app_snap_backup vg0/lv_app

# Просмотр зависимости
sudo lvs -o lv_name,thin_pool,origin
# → LV                  Pool     Origin
# → lv_app              tp_data
# → lv_app_snap_backup  tp_data  lv_app
```

## Дополнительная информация

### Рекомендации по эксплуатации
- **Overcommit:** Не превышайте коэффициент 3–5× для критических систем без строгой автоматизации расширения.
- **Тип носителя:** Тонкие пулы чувствительны к задержкам. Настоятельно рекомендуется использовать SSD/NVMe.
- **Фрагментация:** Динамическая аллокация ведет к фрагментации на уровне блоков LVM. Для задач с интенсивным последовательным чтением/записью лучше использовать традиционные тома.

### Надежность и актуальность
