# LVM — Тонкое провизионирование (Thin Provisioning)

## Определения

**Тонкое провизионирование (Thin Provisioning)** — технология управления дисковым пространством, позволяющая выделять логическим томам виртуальный объем, значительно превышающий реально доступную физическую емкость. Физическое пространство выделяется динамически только в момент записи данных (аллокация по требованию).

**Тонкий пул (Thin Pool)** — специализированное логическое устройство (LV-контейнер), объединяющее физическое пространство для хранения данных и область для метаданных. Является «родительским» объектом для тонких томов. Физически состоит из двух LV: данных (`tpool`) и метаданных (`tpool_tmeta`).

**Тонкий том (Thin Volume)** — логический том, созданный внутри тонкого пула. Физическое место выделяется динамически только в момент записи данных (аллокация по требованию). Виртуальный размер thin volume может превышать физический размер thin pool.

**Overcommit (Переподписка)** — ситуация, при которой суммарный виртуальный размер всех тонких томов превышает физический размер тонкого пула. Допустимый коэффициент переподписки зависит от критичности данных и рабочей нагрузки.

**Thin Snapshot** — снимок, созданный на основе тонкого тома. В отличие от традиционных (thick) снимков, поддерживает рекурсию (снимок со снимка) и использует общий пул метаданных. Физически выделяет место только для измененных блоков (CoW).

**External Origin (Внешний источник)** — обычный (thick) логический том, используемый как основа для множества тонких снимков. Позволяет создавать «золотые образы» ОС или приложений с минимальными затратами на клонирование.

**error_when_full** — параметр тонкого пула, определяющий поведение при исчерпании физического пространства. При значении `1` пул возвращает ошибки записи (I/O errors) вместо перехода в режим read-only, что позволяет приложению корректно обработать нехватку места.

## Базовые концепции

### Архитектура Thin Pool

Тонкий пул физически состоит из двух логических томов:

| Компонент | Описание | Типичный размер |
| :--- | :--- | :--- |
| **Data LV** (`tpool`) | Хранит фактические данные тонких томов | Основная часть выделенного пространства |
| **Metadata LV** (`tpool_tmeta`) | Хранит карту отображения виртуальных блоков на физические | 1–5% от размера Data LV |

```
Thin Pool (vg0/tp_data)
├── vg0/tp_data      — Data LV (100 ГБ)     → физические блоки данных
└── vg0/tp_data_tmeta — Metadata LV (1 ГБ)  → карта отображения
```

Критичность метаданных: если метаданные закончатся (Meta% = 100), пул перейдет в режим `Fail` и все тонкие тома станут недоступны для записи. Потеря metadataLV равносильна потере всех данных в пуле.

### Толстое vs тонкое провизионирование

| Характеристика | Thick Provisioning | Thin Provisioning |
| :--- | :--- | :--- |
| **Выделение места** | Полностью сразу при создании LV | Динамически при записи данных |
| **Overcommit** | Невозможен | Возможен (виртуальный > физического) |
| **Снимки** | Фиксированный COW-буфер из VG | Динамические из Thin Pool, рекурсия |
| **Производительность** | Предсказуемая (данные на выделенных блоках) | Зависит от фрагментации и chunk size |
| **Мониторинг** | `lvs` — Data% не применим | `lvs` — Data% и Meta% критичны |
| **Использование** | Базовые данные, БД, swap | VM, контейнеры, dev/test, клонирование |

### Механизм аллокации и Chunk Size

В тонких томах используется отложенная аллокация блоками, называемыми **Chunk** (чанк). Размер чанка (`chunksize`) настраивается при создании пула (от 64 КиБ до 1 ГиБ).

-   **Малый чанк (64–128 КиБ):** Эффективно для снимков (меньше данных копируется при CoW), но выше фрагментация и нагрузка на метаданные.
-   **Большой чанк (1 МиБ+):** Выше производительность последовательной записи и меньше фрагментация, но неэффективно для снимков.

### Механизм обнуления (Zeroing)

По умолчанию LVM зануляет каждый новый выделенный чанк перед записью (`-Zy`).
-   **Zeroing ON (рекомендуется):** Безопасно. Предотвращает чтение "остаточных" данных старых удаленных томов.
-   **Zeroing OFF (`-Zn`):** Повышает скорость первой записи в блок, но несет риски утечки данных (Data Leakage) между томами.

### Важность TRIM / DISCARD

Для возврата неиспользуемых блоков обратно в пул (после удаления файлов в ОС) необходимо использовать механизм TRIM.
-   Файловая система должна поддерживать `discard` (опция монтирования или `fstrim`).
-   Без этого пул будет считаться заполненным, даже если данные внутри тома удалены.

### Метаданные пула

Метаданные хранят карту отображения виртуальных блоков на физические.
-   **Размер:** Минимум 2 МиБ, максимум ~16 ГиБ. Рекомендуется начинать с **1 ГиБ** (`--poolmetadatasize 1G`).
-   **Критичность:** Если метаданные закончатся (Meta% = 100), пул заблокируется (Read-Only или Fail).
-   **Резервное копирование:** Рекомендуется периодически создавать резервную копию metadata LV для возможности восстановления.

### Поведение при переполнении Thin Pool

При исчерпании физического пространства в thin pool поведение зависит от параметра `error_when_full`:

| `error_when_full` | Поведение при переполнении | Рекомендация |
| :--- | :--- | :--- |
| `0` (по умолчанию) | Thin pool становится read-only, все LV в пуле замораживаются | Для dev/test сред |
| `1` | Запись возвращает I/O ошибку, но пул остается активным | Для продакшена (позволяет приложению обработать ошибку) |

Настройка в `/etc/lvm/lvm.conf`:
```ini
activation {
    error_when_full = 1
}
```

## Практические сценарии

### Сценарий 1: Создание тонкого пула и томов

**Шаг 1: Создание пула с оптимальными параметрами**
```bash
sudo lvcreate -L 100G --poolmetadatasize 1G --chunksize 256K --thinpool tp_data vg0
# → Logical volume "tp_data" created.
```

**Шаг 2: Создание тонкого тома**
```bash
sudo lvcreate -V 1T --thin -n lv_app vg0/tp_data
# → Logical volume "lv_app" created.
```

**Шаг 3: Проверка структуры**
```bash
sudo lvs -o lv_name,lv_size,segtype,thin_count vg0
# → LV       LSize   Thin#  Pool
# → tp_data  100.00g      1  tp_data
# → lv_app    1.00t            tp_data
```

### Сценарий 2: Мониторинг и автоматическое расширение

**Проверка состояния:**
```bash
sudo lvs -o lv_name,data_percent,metadata_percent vg0/tp_data
# → LV       Data%  Meta%
# → tp_data  75.20  12.40
```

**Настройка авторасширения в `/etc/lvm/lvm.conf`:**
```ini
activation {
    thin_pool_autoextend_threshold = 80
    thin_pool_autoextend_percent = 20
}
```
*Для работы необходим запущенный `dmeventd` (сервис `lvm2-monitor`).*

**Проверка и запуск dmeventd:**
```bash
# Проверка статуса
sudo systemctl status lvm2-monitor

# Запуск и включение автозапуска
sudo systemctl enable --now lvm2-monitor
```

### Сценарий 3: Восстановление при переполнении метаданных

Если пул перешел в режим `Fail` из-за Meta% = 100:

1.  **Попытка стандартного восстановления:**
    ```bash
    sudo lvconvert --repair vg0/tp_data
    ```
2.  **Ручное восстановление (если не помогло):**
    Создайте новый LV для метаданных большего размера и подмените его:
    ```bash
    sudo lvcreate -n new_meta -L 2G vg0
    sudo thin_repair -i /dev/mapper/vg0-tp_data_tmeta -o /dev/mapper/vg0-new_meta
    sudo lvconvert --thinpool vg0/tp_data --poolmetadata vg0/new_meta
    ```

**Предотвращение:**
-   Всегда используйте RAID1 для metadata LV тонкого пула.
-   Включите `dmeventd` и настройте `thin_pool_autoextend_threshold = 80`.
-   Регулярно проверяйте `data_percent` и `metadata_percent`.

### Сценарий 4: Использование внешнего источника (External Origin)

Позволяет использовать обычный (thick) том как основу для множества тонких снимков (например, "золотой образ" ОС).

```bash
# 1. Сделать исходный том доступным только для чтения
sudo lvchange -pr /dev/vg0/base_image
sudo lvchange -an /dev/vg0/base_image

# 2. Создать тонкий снимок на базе внешнего источника
sudo lvcreate -s --thinpool tp_data --name vm_clone_1 vg0/base_image
```

### Сценарий 5: Конвертация Thick LV в Thin LV (онлайн)

Позволяет преобразовать обычный (толстый) логический том в тонкий без остановки сервиса и потери данных.

**Предварительная проверка:**
```bash
# Проверка исходного LV
sudo lvs vg0/lv_data
# → LV      VG   Attr       LSize   Pool Origin Data%  Meta%
# → lv_data vg0  -wi-a---- 100.00g

# Проверка наличия thin pool (или создание нового)
sudo lvs vg0 | grep thin
# Если thin pool нет — создайте (см. Сценарий 1)
```

**Шаг 1: Конвертация**
```bash
sudo lvconvert --type thin --thinpool vg0/thin_pool vg0/lv_data
# → Logical volume vg0/lv_data successfully converted.
```

**Шаг 2: Проверка**
```bash
sudo lvs vg0/lv_data
# → LV      VG   Attr       LSize   Pool       Origin Data%  Meta%
# → lv_data vg0  Vwi-a-t-- 100.00g thin_pool          12.34
```

**Важно:** Данные на LV остаются на месте. LV теперь потребляет физическое пространство из thin pool динамически. Оригинальные данные占据 место в thin pool.

### Сценарий 6: Изменение размера Thin Pool и Thin Volume

Расширение пула и расширение тома — независимые операции. Пул определяет физическое пространство, а том — виртуальный размер.

**Расширение виртуального размера тонкого тома:**
```bash
sudo lvextend -V 2T /dev/vg0/thin_lv
```

**Расширение физического пространства тонкого пула:**
```bash
sudo lvextend -L +100G -r /dev/vg0/thin_pool
# → Size of logical volume vg0/thin_pool changed from 100.00 GiB to 200.00 GiB.
```

**Мониторинг после расширения:**
```bash
sudo lvs -o lv_name,lv_size,data_percent,metadata_percent,thin_count
# → LV          LSize   Data%  Meta%  Thin#
# → thin_pool  200.00g  45.23  12.45      2
# → thin_lv      2.00t
```

**Уменьшение Thin Pool (опасно!):**
```bash
# Уменьшение невозможно, пока thin pool содержит данные.
# Сначала необходимо переместить или удалить тонкие тома.
# Уменьшение metadata LV также ограничено — безопасно только при Meta% < 50%.
```

### Сценарий 7: Резервное копирование и восстановление метаданных Thin Pool

**Создание резервной копии метаданных:**
```bash
# Проверка текущего состояния
sudo lvs -o lv_name,lv_size,data_percent,metadata_percent vg0/thin_pool
# → LV         LSize   Data%  Meta%
# → thin_pool  100.00g  45.23   8.50

# Копирование metadata LV на безопасный носитель
sudo dd if=/dev/mapper/vg0-thin_pool_tmeta of=/backup/thin_pool_meta_$(date +%Y%m%d).img bs=4M
# → 262144+0 records in, 262144+0 records out
```

**Восстановление метаданных из резервной копии:**
```bash
# 1. Деактивация пула
sudo lvchange -an vg0/thin_pool

# 2. Восстановление metadata LV
sudo dd if=/backup/thin_pool_meta_20260913.img of=/dev/mapper/vg0-thin_pool_tmeta bs=4M

# 3. Проверка и активация
sudo thin_check /dev/mapper/vg0-thin_pool_tmeta
sudo lvchange -ay vg0/thin_pool
```

### Сценарий 8: Типичные ошибки и их решение

#### Thin Pool переполнен — все LV become read-only

**Причина:** Thin pool исчерпал физическое пространство.

**Решение:**
```bash
# 1. Проверить статус пула
sudo lvs -o lv_name,attr,data_percent,metadata_percent vg0/thin_pool

# 2. Расширить thin pool data
sudo lvextend -L +10G /dev/vg0/thin_pool

# 3. Расширить thin pool metadata (если нужно)
sudo lvextend -L +1G /dev/vg0/thin_pool_tmeta

# 4. Принудительно сделать LV доступным для записи
sudo lvchange -ay /dev/vg0/thin_pool
```

#### Metadata LV заполнены (Meta% = 100)

**Причина:** Метаданные тонкого пула исчерпаны, пул перешел в Fail.

**Решение:**
```bash
# 1. Попытка автоматического восстановления
sudo lvconvert --repair vg0/thin_pool

# 2. Если не помогло — ручное восстановление
sudo lvcreate -n new_tmeta -L 2G vg0
sudo thin_repair -i /dev/mapper/vg0-thin_pool_tmeta -o /dev/mapper/vg0-new_tmeta
sudo lvconvert --thinpool vg0/thin_pool --poolmetadata vg0/new_tmeta
sudo lvchange -ay vg0/thin_pool
```

#### Ошибка `Thin Pool metadata contains inconsistent data`

**Причина:** Повреждение метаданных (аварийное отключение, сбой I/O).

**Решение:**
```bash
# 1. Деактивация пула
sudo lvchange -an vg0/thin_pool

# 2. Проверка целостности
sudo thin_check /dev/mapper/vg0-thin_pool_tmeta

# 3. Если thin_check сообщает об ошибках — восстановление через thin_repair
sudo thin_repair -i /dev/mapper/vg0-thin_pool_tmeta -o /dev/mapper/vg0-new_tmeta
sudo lvconvert --thinpool vg0/thin_pool --poolmetadata vg0/new_tmeta

# 4. Активация
sudo lvchange -ay vg0/thin_pool
```

#### Thin Pool не активируется при загрузке

**Причина:** Отсутствие модулей LVM в initramfs или неправильная конфигурация.

**Решение:**
```bash
# 1. Проверка initramfs
lsinitramfs /boot/initrd.img-$(uname -r) | grep lvm
# Если lvm отсутствует:
sudo update-initramfs -u

# 2. Для centos/rhel:
sudo dracut --force --add lvm

# 3. Проверка конфигурации
sudo vgchange -ay vg0
```

## Дополнительная информация

### Рекомендации по эксплуатации
- **Overcommit:** Не превышайте коэффициент 3–5× для критических систем. Для данных, критичных к целостности, не превышайте 200% overcommit ratio.
- **Тип носителя:** Тонкие пулы критичны к задержкам; настоятельно рекомендуется использовать SSD/NVMe.
- **Фрагментация:** Динамическая аллокация ведет к фрагментации. Для БД с высокой нагрузкой на запись лучше использовать традиционные тома.
- **error_when_full:** Для продакшен-сред рекомендуется установить `error_when_full = 1`, чтобы приложение корректно обрабатывало нехватку места.
- **RAID для metadata:** Используйте RAID1 для metadata LV тонкого пула — потеря metadata равносильна потере всех данных.
- **Мониторинг:** Настройте алерты на `Data% > 80%` и `Meta% > 50%`. Используйте `dmeventd` для автоматического расширения.
- **Размер metadata:** Выделяйте 1–5% от размера thin pool для metadata (зависит от chunk size и размера пула).

### Утилиты для работы с Thin Pool

| Утилита | Назначение |
| :--- | :--- |
| `thin_check` | Проверка целостности метаданных тонкого пула |
| `thin_repair` | Восстановление поврежденных метаданных |
| `thin_dump` | Вывод содержимого метаданных (для отладки) |
| `thin_rmv` | Удаление тонкого тома из метаданных |
| `dmeventd` | Демон мониторинга и автоматического расширения |
