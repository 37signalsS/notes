# LVM: Практические сценарии восстановления и оптимизации

## Определения

**Восстановление метаданных (Metadata Recovery)** — процесс реанимации структуры групп томов и логических томов из резервных копий конфигурации или дампов метаданных физических томов.

**Миграция Swap (Swap Migration)** — перенос области подкачки с логического тома LVM в файл или на другой носитель для упрощения управления дисковым пространством и гибкости изменения размеров LV.

**vgsplit / vgmerge** — стандартные утилиты LVM для перемещения существующих логических томов (вместе с их физическими экстентами) между разными группами томов.

**Архив метаданных (Metadata Archive)** — автоматические копии состояния VG, сохраняемые в `/etc/lvm/archive/` перед каждым изменением структуры.

## Базовые концепции

### Механизмы защиты данных

LVM обеспечивает высокую живучесть системы благодаря двум уровням резервирования:
1.  **Backup (`/etc/lvm/backup/`):** содержит последнее актуальное состояние каждой VG.
2.  **Archive (`/etc/lvm/archive/`):** хранит историю изменений. Это позволяет откатиться к состоянию «до удаления LV».

### Межгрупповые операции

Хотя группы томов изолированы, LVM позволяет «отщеплять» часть ресурсов одной VG и «приклеивать» их к другой. Это безопаснее, чем использование одного логического тома в качестве физического для другой группы (LVM-on-LVM).

## Практические сценарии

### Сценарий 1: Восстановление PV после повреждения заголовка

Используется, если диск физически исправен, но LVM перестал распознавать его как PV (ошибка `unknown device`).

**Шаг 1: Поиск UUID поврежденного тома**
UUID можно найти в последнем бэкапе метаданных.
```bash
sudo grep -A 10 "physical_volumes" /etc/lvm/backup/vg_data
# → pv0 {
# →     id = "XYZ-123-abc-..."
```

**Шаг 2: Восстановление метки PV**
```bash
sudo pvcreate --uuid "XYZ-123-abc-..." --restorefile /etc/lvm/backup/vg_data /dev/sdb1
# → Physical volume "/dev/sdb1" successfully created.
```

**Шаг 3: Восстановление структуры группы томов**
```bash
sudo vgcfgrestore vg_data
sudo vgchange -ay vg_data
# → 1 logical volume(s) in volume group "vg_data" now active
```

### Сценарий 2: Восстановление случайно удаленного LV

Если вы выполнили `lvremove`, данные на диске всё еще целы, пока они не затерты. Их можно вернуть, откатив состояние VG.

**Шаг 1: Поиск нужного архива**
```bash
sudo vgcfgrestore --list vg_data
# → File: /etc/lvm/archive/vg_data_00005-98765.vg
# → Description: Created *before* executing 'lvremove -f vg_data/lv_critical'
```

**Шаг 2: Тестовое и финальное восстановление**
```bash
# Проверка
sudo vgcfgrestore --test -f /etc/lvm/archive/vg_data_00005-98765.vg vg_data

# Восстановление
sudo vgcfgrestore -f /etc/lvm/archive/vg_data_00005-98765.vg vg_data
sudo vgchange -ay vg_data
```

### Сценарий 3: Передача пространства между VG (vgsplit + vgmerge)

Задача: передать 20 ГБ из `vg_old` в `vg_new`.

**Шаг 1: Создание временного LV в источнике**
```bash
sudo lvcreate -L 20G -n lv_temp vg_old
```

**Шаг 2: Отделение LV в новую временную группу**
```bash
sudo vgsplit vg_old vg_transfer /dev/sdc1
# Здесь /dev/sdc1 — физический носитель, на котором размещен lv_temp.
# Если LV размазан по дискам, сначала используйте pvmove.
```

**Шаг 3: Слияние групп**
```bash
sudo vgmerge vg_new vg_transfer
# → Volume group "vg_transfer" successfully merged into "vg_new"
```

**Шаг 4: Удаление временного LV**
Теперь 20 ГБ стали свободным местом (VFree) в `vg_new`.
```bash
sudo lvremove vg_new/lv_temp
```

### Сценарий 4: Удаление «мертвого» диска из группы (Missing PV)

Если диск физически вышел из строя, и VG находится в состоянии `partial`.

**Шаг 1: Проверка состояния**
```bash
sudo vgs
# → VG      #PV #LV #SN Attr   VSize   VFree
# → vg_data   2   1   0 wz-pn- <40.00g <20.00g
# Атрибут 'p' (partial) указывает на отсутствие PV.
```

**Шаг 2: Удаление отсутствующих томов**
```bash
# Удалить все ссылки на отсутствующие PV (все данные на них будут потеряны!)
sudo vgreduce --removemissing --force vg_data
```
