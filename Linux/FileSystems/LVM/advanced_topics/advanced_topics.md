# LVM: Расширенные темы

## Определения

**Расширенные темы LVM** — комплексные вопросы эксплуатации системы логических томов, включающие взаимодействие с процессом загрузки ОС, глубокую диагностику метаданных, фильтрацию устройств, использование встроенных механизмов RAID и кэширования.

**initramfs (Initial RAM Filesystem)** — временная файловая система, используемая ядром при загрузке для активации драйверов и утилит (включая LVM), необходимых для поиска и монтирования корневого раздела.

**LVM RAID** — метод создания отказоустойчивых логических томов, использующий драйверы MD (Multiple Devices) ядра Linux, но управляемый через интерфейс LVM. Поддерживает уровни RAID 0, 1, 4, 5, 6, 10.

**LVM Cache (dm-cache)** — технология, позволяющая использовать быстрый накопитель (например, NVMe/SSD) в качестве кэширующего слоя для медленного LV (HDD), ускоряя операции чтения и записи.

**MDA (Metadata Area)** — зарезервированная область в начале физического тома (PV), где хранится описание структуры группы томов (VG) в текстовом формате.

**LVM Filter** — правило в конфигурационном файле `lvm.conf`, определяющее, какие блочные устройства LVM должен сканировать, а какие — игнорировать.

## Базовые концепции

### Взаимодействие с процессом загрузки

Для успешной загрузки системы с корнем на LVM необходимо наличие утилит LVM в `initramfs` и корректная конфигурация загрузчика.

#### Ограничение размещения /boot
Рекомендуется выносить каталог `/boot` на отдельный стандартный раздел (не LVM).
- **Причина:** Хотя современные GRUB умеют читать LVM, это усложняет восстановление при повреждении метаданных LVM.
- **Стандартная схема:**
  - `/dev/sda1` (512 МБ – 1 ГБ, ext4/XFS) — точка монтирования `/boot`.
  - `/dev/sda2` (LVM PV) — все остальные разделы (`/`, `/home`, `swap`).

#### Событийная активация (systemd)
LVM интегрируется с `systemd` через следующие службы:
- `lvm2-pvscan@.service`: Выполняет автоматическое сканирование PV при обнаружении устройства ядром (через `udev`).
- `lvm2-monitor.service`: Следит за состоянием томов и снимков через демон `dmeventd`. Необходим для автоматического расширения Thin Pool и замены сбойных сегментов в RAID.

### Фильтрация устройств (lvm.conf)

По умолчанию LVM сканирует все блочные устройства в `/dev/`. В сложных средах (Multipath, iSCSI, Docker, NVMe-oF) это может привести к ошибкам дублирования или существенному замедлению работы.

**Типы фильтров:**
- `filter`: Список регулярных выражений для путей устройств (например, `["a|/dev/sd.*|", "r|.*|"]`).
- `global_filter`: Применяется ко всем утилитам, включая `pvscan` и `vgscan`. Рекомендуется использовать именно его для исключения устройств на системном уровне.

### LVM RAID и отказоустойчивость

В отличие от классического MDADM, LVM RAID позволяет создавать избыточные тома внутри VG, используя свободное пространство PV.

**Основные уровни:**
- **raid1:** Зеркалирование. Требует минимум 2 PV.
- **raid5:** Чередование с контрольной суммой. Требует минимум 3 PV. Выдерживает отказ одного диска.
- **raid6:** Двойная контрольная сумма. Требует минимум 4 PV. Выдерживает отказ двух дисков.
- **raid10:** Сочетание зеркалирования и чередования. Требует минимум 4 PV.

### Ускорение через LVM Cache

LVM позволяет объединить быстрый LV (кэш) и медленный LV (данные).
- **Cache Pool:** Состоит из `data` (сами данные кэша) и `metadata` (индекс).
- **Режимы работы:**
  - `writethrough`: Данные пишутся одновременно в кэш и на медленный диск. Безопасно, ускоряет только чтение.
  - `writeback`: Данные пишутся сначала в кэш, затем сбрасываются на диск. Высокая скорость записи, но риск потери данных при отказе кэш-устройства (если оно не RAID1).

### Тюнинг и производительность

- **Alignment (Выравнивание):** LVM автоматически выравнивает данные по границам экстентов (PE). Важно следить, чтобы начало PV соответствовало физическому сектору диска (актуально для аппаратных RAID и SSD/NVMe).
- **Read-ahead:** Для систем с последовательным чтением больших файлов можно увеличить параметр `readahead` для конкретного LV (`lvchange -r <size>`).

## Практические сценарии

### Сценарий 1: Настройка фильтров устройств

Предотвращение сканирования локальных дисков при использовании Multipath.

**Редактирование `/etc/lvm/lvm.conf`:**
```ini
devices {
    # Игнорировать сырые пути дисков, использовать только пути Multipath (mpath)
    global_filter = [ "a|/dev/mapper/mpath.*|", "r|.*|" ]
}
```
*После изменения фильтра необходимо обновить кэш: `sudo vgscan`.*

### Сценарий 2: Восстановление загрузки (Rebuild initramfs)

Если система не находит VG при загрузке (ошибка `Volume group not found`).

#### Для Debian / Ubuntu
```bash
# Добавление модуля (если он не включен автоматически)
echo "lvm2" | sudo tee -a /etc/initramfs-tools/modules

# Обновление образа для текущего ядра
sudo update-initramfs -u
```

#### Для RHEL / Rocky / Fedora (dracut)
```bash
# Принудительное включение модуля
sudo dracut --force --add lvm --regenerate-all
```

### Сценарий 3: Создание отказоустойчивого тома (LVM RAID)

Создание томов с защитой от отказа дисков.

**Пример 1: RAID 10 (Зеркалирование + Чередование)**
```bash
# Требует минимум 4 PV. -i 2 (2 полосы чередования), каждое зеркалируется.
sudo lvcreate --type raid10 -L 100G -i 2 -n lv_mirrored my_vg
```

**Пример 2: RAID 5 (Чередование с контрольной суммой)**
```bash
# Требует минимум 3 PV. Выдерживает отказ одного диска.
sudo lvcreate --type raid5 -L 200G -n lv_protected my_vg
```

**Проверка состояния синхронизации:**
```bash
sudo lvs -o name,copy_percent,devices my_vg
# → lv_protected  15.42  lv_protected_rimage_0(0),...
```

### Сценарий 4: Настройка SSD-кэша для медленного HDD

Задача: ускорить работу тома `lv_data` с помощью SSD-диска `/dev/sdb`.

```bash
# 1. Создание PV на SSD и добавление в VG
sudo pvcreate /dev/sdb
sudo vgextend my_vg /dev/sdb

# 2. Создание Cache Pool (данные + метаданные) на SSD
sudo lvcreate -n cache_pool -L 50G my_vg /dev/sdb

# 3. Привязка кэша к основному LV
sudo lvconvert --type cache --cachepool my_vg/cache_pool my_vg/lv_data

# 4. Проверка
sudo lvs -a -o name,cache_read_hits,cache_write_hits my_vg
```

### Сценарий 5: Диагностика целостности метаданных

```bash
# Проверка физического тома на ошибки метаданных (MDA)
sudo pvck /dev/sdb1

# Проверка консистентности всей группы томов
sudo vgck my_vg

# Просмотр истории изменений метаданных
sudo vgcfgrestore --list my_vg
```
