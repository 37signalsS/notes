# Типы файловых систем: сравнительный обзор

## Определения

### Классификация файловых систем

Файловые системы классифицируются по назначению и архитектуре:

- **Дисковые (локальные)** — управляют данными на физических носителях (HDD, SSD, NVMe). Примеры: ext4, XFS, Btrfs, ZFS, F2FS.
- **Сетевые** — предоставляют доступ к файлам по сети. Примеры: NFS, CIFS/SMB, GlusterFS, CephFS.
- **Виртуальные (псевдо-ФС)** — не используют физическое хранилище, генерируются ядром в памяти. Примеры: procfs, sysfs, tmpfs, cgroupfs.
- **Специализированные** — оптимизированы под конкретные сценарии (ISO 9660 для оптических дисков, FAT32/exFAT для съёмных носителей).

### Ключевые характеристики ФС

При выборе файловой системы оцениваются:

- **Журналирование** — механизм защиты от сбоев питания.
- **Целостность данных** — обнаружение и предотвращение silent data corruption.
- **Снапшоты** — поддержка мгновенных снимков состояния ФС.
- **Компрессия** — встроенное сжатие данных на лету.
- **Дедупликация** — устранение дубликатов данных.
- **Масштабируемость** — максимальный размер ФС, файла, количество inode.
- **Производительность** — IOPS, пропускная способность, латентность при различных паттернах нагрузки.

## Основные концепции

### Ext4 (Fourth Extended Filesystem)

**Ext4** — самая распространённая журналируемая ФС в Linux, обратная совместимая с ext3/ext2.

**Архитектура:**

- **Inode:** Фиксированное количество задаётся при создании (`mkfs.ext4 -i` или `-N`). Исчерпание inode блокирует создание новых файлов даже при наличии свободного места.
- **Extent-based allocation:** Вместо блочных маппингов использует экстенты (непрерывные диапазоны блоков), что снижает фрагментацию и ускоряет работу с крупными файлами.
- **Delayed allocation:** Откладывает выделение блоков до момента фактической записи, улучшая использование пространства.

**Режимы журналирования:**

- `data=journal` — данные + метаданные (максимальная надёжность, двойная запись).
- `data=ordered` (по умолчанию) — метаданные журналируются, данные записываются до фиксации метаданных.
- `data=writeback` — только метаданные (максимальная производительность, риск потери данных при сбое).

**Ограничения:**

- Максимальный размер ФС: 1 EiB (теоретически), на практике ~50 TiB.
- Максимальный размер файла: 16 TiB.
- Нет встроенных снапшотов.
- Нет встроенной компрессии или дедупликации.
- Фиксированное количество inode.

**Сценарии использования:** General-purpose серверы, базы данных (PostgreSQL), корневые разделы, системы где важна стабильность и предсказуемость.

**Утилиты:** `mkfs.ext4`, `tune2fs`, `dumpe2fs`, `resize2fs`, `e2fsck`, `debugfs`.

### XFS

**XFS** — высокопроизводительная 64-битная журналируемая ФС, разработанная SGI, ставшая стандартом для RHEL/CentOS 7+ и крупных хранилищ.

**Архитектура:**

- **Динамические inode:** Создаются по мере необходимости, проблема исчерпания inode отсутствует.
- **Allocation groups:** Диск делится на независимые группы распределения, позволяя параллельные операции записи (высокий IOPS на многопроцессорных системах).
- **Delayed allocation:** Как и ext4, откладывает выделение блоков.
- **Extent-based:** Использует экстенты для эффективного управления пространством.

**Журналирование:** Только один режим — журналирование метаданных с гарантированным порядком записи данных (аналог `data=ordered`). Нет выбора режима, что упрощает администрирование.

**Ключевая особенность:** Не поддерживает уменьшение (`xfs_growfs` — только расширение). Для изменения размера необходимо备份 данные, пересоздать ФС, восстановить данные.

**Ограничения:**

- Максимальный размер ФС: 8 EiB.
- Максимальный размер файла: 8 EiB.
- Нет встроенных снапшотов (требуется LVM или DM).
- Нет встроенной компрессии или дедупликации.
- Восстановление удалённых файлов крайне затруднено.

**Сценарии использования:** Крупные хранилища данных, файловые серверы, системы с высокой параллельной записью, базы данных, контейнеры (Docker storage backend).

**Утилиты:** `mkfs.xfs`, `xfs_growfs`, `xfs_info`, `xfs_db`, `xfs_repair`, `xfs_quota`.

### Btrfs (B-Tree Filesystem / Butter FS)

**Btrfs** — современная ФС с Copy-on-Write, разработанная Oracle, позиционируется как замена ext4 с возможностями ZFS.

**Архитектура:**

- **Copy-on-Write (CoW):** При изменении блока создаётся его модифицированная копия, и только после успешной записи указатель переключается на новый блок. Обеспечивает атомарность без двойной записи в журнал.
- **B-Tree:** Все метаданные (и опционально данные) хранятся в B-Tree структурах, обеспечивая быструю навигацию.
- **Subvolumes:** Подтома — независимые иерархии файлов в рамках одной ФС, каждая со своими точками монтирования.
- **Динамические inode:** Создаются по мере необходимости.

**Ключевые фишки:**

- **Снапшоты:** Мгновенные снимки состояния ФС или подтомов на основе CoW. Занимают минимум места до внесения изменений.
- **Компрессия:** Встроенная прозрачная компрессия (zlib, lzo, zstd). Значительно экономит место на SSD, снижает износ.
- **Дедупликация:** Онлайн (автоматическая) и офлайн (`btrfs filesystem dedup`).
- **RAID 0/1/5/6/10:** Встроенная поддержка RAID без LVM/mdadm.
- **Self-healing:** При использовании зеркал (RAID 1/10) автоматически восстанавливает данные из контрольных сумм.
- **Проверка контрольных сумм:** CRC32C для данных и метаданных, обнаружение silent corruption.

**Ограничения:**

- RAID 5/6 экспериментальный, есть риск потери данных при сбоях.
- Производительность при большом количестве мелких файлов может уступать ext4/XFS.
- Сложность восстановления при серьёзных повреждениях.
- Не рекомендуется для баз данных с высокой записью (CoW вызывает фрагментацию и write amplification).

**Сценарии использования:** Домашние серверы, бэкап-хранилища, системы с необходимостью снапшотов, десктопы, тестовые среды.

**Утилиты:** `mkfs.btrfs`, `btrfs filesystem`, `btrfs subvolume`, `btrfs device`, `btrfs balance`, `btrfs check`, `btrfs restore`.

### ZFS (Zettabyte Filesystem)

**ZFS** — корпоративная ФС и менеджер томов в одном, разработанная Sun Microsystems. Известна максимальной надёжностью и защитой данных.

**Архитектура:**

- **Объединённая архитектура:** ZFS одновременно является и ФС, и менеджером томов (заменяет LVM + ФС).
- **Copy-on-Write:** Все записи атомарны, невозможно повредить данные при сбое питания.
- **Контрольные суммы:** Каждый блок данных и метаданных имеет чексумму ( Fletcher4, SHA-256). Обнаружение и исправление silent corruption.
- **ARC (Adaptive Replacement Cache):** Интеллектуальный кэш в RAM для данных и метаданных.
- **ZIL (ZFS Intent Log):** Журнал синхронных записей. Может быть вынесен на быстрый SSD (SLOG — Separate Log Device).
- **L2ARC:** Второй уровень кэша на SSD для часто читаемых данных.

**Ключевые фишки:**

- **Снапшоты:** Мгновенные, эффективные по месту, неограниченное количество.
- **Clones:** Записываемые копии снапшотов (для тестирования, разработки).
- **Компрессия:** lz4 (по умолчанию, быстрый), zstd, gzip. Прозрачная, с минимальными накладными расходами.
- **Дедупликация:** Глобальная на уровне пула. Требует значительного количества RAM (~5 ГБ на 1 ТБ данных).
- **RAID-Z (1/2/3):** Аналог RAID 5/6/7, но без проблемы write hole (благодаря CoW). RAID-Z3 выдерживает отказ 3 дисков.
- **Scrubbing:** Фоновая проверка целостности всех блоков с исправлением ошибок из зеркал/RAID-Z.
- **Сжатие + дедупликация:** Работают совместно, экономя до 80% места на типичных данных.

**Ограничения:**

- **Высокое потребление RAM:** Минимум 4-8 ГБ, для дедупликации — значительно больше.
- **Не поддерживается в ядре Linux напрямую:** Требуется ZFS on Linux (OpenZFS) как внешний модуль DKMS или пакет.
- **Сложность:** Требует понимания концепций (pool, dataset, vdev).
- **Производительность случайной записи:** Может уступать ext4/XFS на HDD без кэширующего SSD.
- Нельзя уменьшать пул или удалять отдельные vdev (в старых версиях, частично решено в OpenZFS 2.2+).

**Сценарии использования:** NAS (TrueNAS, Proxmox), хранилища бэкапов, архивы, виртуализация (iSCSI targets), системы с критичными требованиями к целостности данных.

**Утилиты:** `zpool create/status/list/scrub`, `zfs create/snapshot/clone/set/get/send/receive`.

### F2FS (Flash-Friendly File System)

**F2FS** — ФС, разработанная Samsung специально для NAND flash памяти (SSD, eMMC, UFS).

**Архитектура:**

- **Log-structured:** Все записи последовательные, минимизируя random write и износа flash.
- **Flash-aware:** Учитывает физику NAND flash (erase blocks, wear leveling, garbage collection).
- **Сегментированная структура:** Данные и метаданные хранятся в отдельных сегментах, оптимизируя GC.

**Ключевые фишки:**

- **Оптимизация для SSD:** Минимизация write amplification, поддержка TRIM.
- **Checkpoint:** Быстрое восстановление после сбоев (как журналирование, но быстрее).
- **Компрессия:** Встроенная прозрачная компрессия (lz4, lzohc, zstd).
- **Гибкое расположение:** Поддержка multi-device (хотя и не полноценный RAID).

**Ограничения:**

- Не предназначена для HDD (плохая производительность).
- Меньшая зрелость и стабильность по сравнению с ext4/XFS.
- Ограниченные возможности восстановления данных.
- Не подходит для баз данных и систем с частыми синхронными записями.

**Сценарии использования:** Мобильные устройства (Android), встроенные системы, SSD-накопители в десктопах, IoT.

**Утилиты:** `mkfs.f2fs`, `fsck.f2fs`, `f2fs_tools`.

## Практические сценарии

### Выбор ФС для базы данных

**PostgreSQL/MySQL:**

- **Рекомендация:** Ext4 или XFS.
- **Ext4:** `data=ordered` (по умолчанию), `noatime`, `barrier=1`. Стабильная производительность, хорошая поддержка.
- **XFS:** Высокий IOPS при параллельной записи, `noatime`. Лучше для крупных инстансов.
- **Избегать:** Btrfs (CoW вызывает фрагментацию), ZFS (требует тонкой настройки sync=disabled для производительности).

**Оптимизация:**

```bash
# Ext4 для PostgreSQL
UUID=xxx /var/lib/postgresql ext4 defaults,noatime,barrier=1,data=ordered 0 2

# XFS для высоконагруженной БД
UUID=xxx /var/lib/mysql xfs defaults,noatime,logbufs=8 0 2
```

### Выбор ФС для файлового сервера

**NAS/SMB/NFS сервер:**

- **Рекомендация:** ZFS или Btrfs.
- **ZFS:** RAID-Z, снапшоты, дедупликация, компрессия, self-healing. Идеален для NAS (TrueNAS).
- **Btrfs:** Проще в настройке, встроенный RAID, снапшоты. Хорош для домашних серверов.

**Конфигурация ZFS:**

```bash
# Создание пула RAID-Z2 (допуск 2 дисков)
zpool create storage raidz2 /dev/sda /dev/sdb /dev/sdc /dev/sdd /dev/sde

# Включение компрессии
zfs set compression=lz4 storage

# Создание dataset с снапшотами
zfs create storage/backups
zfs snapshot storage/backups@daily
```

### Выбор ФС для контейнеров (Docker/Kubernetes)

**Docker storage driver:**

- **Overlay2 (ext4/XFS):** Стандартный выбор. XFS с `d_type=true` предпочтителен для Docker.
- **Btrfs:** Поддержка снапшотов для слоёв образов, эффективное использование места.
- **ZFS:** Аналогично Btrfs, но с большей надёжностью.

**Kubernetes volumes:**

- **XFS:** Высокая производительность для PVC.
- **Ext4:** Универсальный выбор, хорошая поддержка.

### Выбор ФС для бэкапов

**Бэкап-хранилище:**

- **ZFS:** Снапшоты + дедупликация + компрессия = экономия 50-80% места.
- **Btrfs:** Снапшоты подтомов, отправка инкрементальных снапшотов (`btrfs send | btrfs receive`).

**Инкрементальные бэкапы Btrfs:**

```bash
# Полный снапшот
btrfs subvolume snapshot -r /data /data/@backup_0

# Инкрементальный
btrfs subvolume snapshot -r /data /data/@backup_1
btrfs send -p /data/@backup_0 /data/@backup_1 | btrfs receive /backup/
```

### Выбор ФС для SSD/NVMe

**Оптимизация для flash:**

- **F2FS:** Специально для NAND flash, минимизация износа.
- **Ext4/XFS:** С `noatime`, `discard` (TRIM), подходят для general-purpose.

**Ext4 для SSD:**

```bash
UUID=xxx / ext4 defaults,noatime,discard 0 1
```
