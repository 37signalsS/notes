# Типы файловых систем: сравнительный обзор

## Определения

### Классификация файловых систем

Файловые системы классифицируются по назначению и архитектуре:

- **Дисковые (локальные)** — управляют данными на физических носителях (HDD, SSD, NVMe). Примеры: ext4, XFS, Btrfs, ZFS, F2FS.
- **Сетевые** — предоставляют доступ к файлам по сети. Примеры: NFS, CIFS/SMB, GlusterFS, CephFS.
- **Виртуальные (псевдо-ФС)** — не используют физическое хранилище, генерируются ядром в памяти. Примеры: procfs, sysfs, tmpfs, cgroupfs.
- **Специализированные** — оптимизированы под конкретные сценарии (ISO 9660 для оптических дисков, FAT32/exFAT для съёмных носителей).
- **Многослойные (Overlay/Union)** — объединяют несколько директорий в одну виртуальную иерархию. Примеры: OverlayFS (основа Docker), AUFS.
- **Компактные/Read-only** — оптимизированы для максимального сжатия и скорости чтения на встраиваемых системах. Примеры: EROFS, SquashFS.

### Ключевые характеристики ФС

При выборе файловой системы оцениваются:

- **Журналирование** — механизм защиты от сбоев питания путём записи намерений в журнал.
- **Copy-on-Write (CoW)** — метод, при котором данные никогда не перезаписываются на месте; изменения пишутся в новый блок, обеспечивая атомарность.
- **Целостность данных** — использование контрольных сумм для обнаружения и предотвращения "тихого" повреждения данных (silent data corruption).
- **Снапшоты** — поддержка мгновенных снимков состояния ФС (на основе CoW или LVM).
- **Reflinks (Reference Links)** — поддержка копирования файлов "ссылками" на те же блоки (Copy-on-Write на уровне отдельных файлов). Позволяет мгновенно копировать огромные файлы без затрат места.
- **Компрессия** — встроенное прозрачное сжатие данных "на лету" (LZO, Zstd, LZ4).
- **Дедупликация** — устранение дубликатов данных на уровне блоков (инлайн или офлайн).
- **Масштабируемость** — максимальный размер ФС, файла, количество inode (статическое или динамическое).
- **Производительность** — IOPS, пропускная способность, латентность при различных паттернах нагрузки (случайная запись, последовательное чтение).

## Основные концепции

### Ext4 (Fourth Extended Filesystem)

**Ext4** — самая распространённая журналируемая ФС в Linux, обратная совместимая с ext3/ext2.

**Архитектура:**

- **Inode:** Фиксированное количество задаётся при создании (`mkfs.ext4 -i` или `-N`). Исчерпание inode блокирует создание новых файлов даже при наличии свободного места.
- **Extent-based allocation:** Вместо блочных маппингов использует экстенты (непрерывные диапазоны блоков), что снижает фрагментацию и ускоряет работу с крупными файлами.
- **Delayed allocation:** Откладывает выделение блоков до момента фактической записи, улучшая использование пространства.

**Режимы журналирования:**

- `data=journal` — данные + метаданные (максимальная надёжность, двойная запись).
- `data=ordered` (по умолчанию) — метаданные журналируются, данные записываются до фиксации метаданных.
- `data=writeback` — только метаданные (максимальная производительность, риск потери данных при сбое).

**Ограничения:**

- Максимальный размер ФС: 1 EiB (теоретически), на практике стабильно до 100 TiB.
- Максимальный размер файла: 16 TiB.
- Нет встроенных снапшотов и reflinks.
- Нет встроенной компрессии или дедупликации.
- Фиксированное количество inode (нельзя изменить без пересоздания ФС).

**Сценарии использования:** Универсальные серверы, корневые разделы, системы, где важна стабильность и предсказуемость.

**Утилиты:**
```bash
# Просмотр параметров ФС
sudo tune2fs -l /dev/sda1 | grep "Filesystem features"
# → Filesystem features: has_journal extents huge_file dir_nlink 64bit ...
```

### XFS

**XFS** — высокопроизводительная 64-битная журналируемая ФС, ставшая стандартом для RHEL/CentOS 7+ и высоконагруженных систем.

**Архитектура:**

- **Динамические inode:** Создаются по мере необходимости, проблема исчерпания inode отсутствует.
- **Allocation groups:** Диск делится на независимые группы распределения, позволяя параллельные операции записи (высокий IOPS на многопроцессорных системах).
- **Reflinks (с ядра 4.9+):** Поддержка Copy-on-Write на уровне файлов. Позволяет мгновенно клонировать файлы (`cp --reflink`).
- **Delayed allocation:** Эффективное распределение блоков.

**Журналирование:** Только журналирование метаданных. XFS гарантирует, что данные будут сброшены на диск перед метаданными в журнале (аналог `data=ordered`).

**Ключевая особенность:** Не поддерживает уменьшение (shrink). Только расширение.

**Ограничения:**

- Максимальный размер ФС/файла: 8 EiB.
- Нет встроенной компрессии или дедупликации (но reflinks позволяют реализовать дедупликацию сторонними средствами).
- Восстановление удалённых файлов крайне затруднено.

**Сценарии использования:** Крупные хранилища данных, базы данных (ClickHouse, PostgreSQL), Docker (с драйвером `overlay2` и `ftype=1`), системы с высокой параллельной записью.

**Утилиты:**
```bash
# Проверка поддержки reflinks и ftype
xfs_info /mnt/data | grep -E "reflink|ftype"
# → naming   =version 2              bsize=4096   ascii-ci=0 ftype=1
# → realtime =none                   extsz=4096   blocks=0, rtextents=0
# → reflink  =1
```

### Btrfs (B-Tree Filesystem / Butter FS)

**Btrfs** — современная ФС с Copy-on-Write (CoW), разработанная Oracle, сочетающая функции ФС и менеджера томов.

**Архитектура:**

- **Copy-on-Write (CoW):** Данные не перезаписываются; изменения пишутся в новые блоки, а указатели обновляются атомарно. Обеспечивает устойчивость к сбоям без двойной записи в журнал.
- **B-Tree:** Все метаданные и данные хранятся в B-деревьях, что ускоряет поиск и навигацию.
- **Subvolumes:** Логические разделы внутри одного пула, которые можно монтировать независимо.

**Ключевые фишки:**

- **Снапшоты:** Мгновенные снимки подтомов на основе CoW.
- **Компрессия:** Прозрачное сжатие (zlib, lzo, zstd). Zstd рекомендуется для большинства сценариев.
- **Дедупликация:** Офлайн (с помощью `duperemove`) или онлайн (через экспериментальные патчи).
- **Встроенный RAID:** Поддержка RAID 0, 1, 10. **RAID 5/6 до сих пор считается нестабильным** для метаданных (проблема write hole).
- **Self-healing:** Проверка контрольных сумм при каждом чтении и автоматическое восстановление из зеркальных копий.

**Ограничения:**

- Высокая фрагментация при частых случайных записях (базы данных, VM) из-за CoW. Рекомендуется использовать опцию `nodatacow` для конкретных файлов.
- Сложность мониторинга свободного места (`df -h` может показывать неверные данные).

**Сценарии использования:** Домашние ПК (дистрибутивы Fedora, openSUSE), бэкап-серверы, системы со снапшотами.

**Утилиты:**
```bash
# Проверка использования пространства
sudo btrfs filesystem usage /mnt/btrfs
# → Overall:
# →     Device size:                  20.00GiB
# →     Device allocated:              2.02GiB
# →     Device unallocated:           17.98GiB
```

### ZFS (Zettabyte Filesystem / OpenZFS)

**ZFS** — мощная корпоративная ФС и менеджер томов "в одном флаконе". В Linux используется реализация **OpenZFS**.

**Архитектура:**

- **Пул (zpool):** Объединение физических дисков (vdev) в единое хранилище.
- **Датасеты (datasets):** Логические ФС внутри пула с независимыми настройками (сжатие, квоты).
- **ARC (Adaptive Replacement Cache):** Продвинутый алгоритм кэширования в RAM, заменяющий стандартный Page Cache.

**Ключевые фишки (OpenZFS 2.x+):**

- **Block Cloning (reflinks):** Появилось в версии 2.2, позволяет мгновенно клонировать файлы внутри датасета.
- **Zstd компрессия:** Отличная альтернатива lz4 для архивных данных.
- **RAID-Z (1/2/3):** Программный RAID с защитой от "тихого" повреждения данных и write hole.
- **Native Encryption:** Шифрование данных без накладных расходов LUKS.
- **Scrubbing:** Регулярная фоновая проверка целостности всех блоков данных.

**Ограничения:**

- **Потребление RAM:** Рекомендуется от 1 ГБ RAM на 1 ТБ данных для ARC (минимум 4-8 ГБ на систему).
- **Сложность расширения:** До недавнего времени нельзя было просто добавить один диск в RAID-Z vdev (требуется добавление нового vdev или расширение всех дисков).
- **Вне ядра:** Устанавливается как внешний модуль через **DKMS** (Dynamic Kernel Module Support), что может потребовать пересборки при обновлении ядра.

**Сценарии использования:** Профессиональные NAS, гипервизоры (Proxmox), бэкап-хранилища, базы данных с высокими требованиями к целостности.

**Утилиты:**
```bash
# Просмотр статуса пула
sudo zpool status
# → pool: tank
# → state: ONLINE
# → scan: scrub repaired 0B in 00:05:12 with 0 errors
```

### EROFS (Enhanced Read-Only File System)

**EROFS** — современная легковесная ФС только для чтения, разработанная Huawei для мобильных устройств и контейнеров.

**Архитектура:**

- **Fixed-sized output compression:** Оптимизирована для высокой скорости случайного доступа при использовании сжатия (LZ4, Zstd).
- **Zero-copy:** Прямое отображение данных из блочного устройства в кэш страниц.

**Ключевые фишки:**

- **Экстремальная производительность:** На чтение быстрее SquashFS и даже ext4 (за счёт меньших накладных расходов VFS).
- **Минимальный размер:** Компактные метаданные и эффективное сжатие.

**Сценарии использования:** Образы Android, слои контейнеров (через `composefs`), прошивки встраиваемых систем, LiveCD.

**Утилиты:**
```bash
# Создание образа EROFS из директории
mkfs.erofs image.erofs ./source_dir
```

### F2FS (Flash-Friendly File System)

**F2FS** — ФС, разработанная Samsung специально для NAND flash памяти (SSD, eMMC, UFS).

**Архитектура:**

- **Log-structured:** Минимизирует износ ячеек flash путём последовательной записи данных.
- **Flash-aware:** Учитывает физические особенности NAND (erase blocks, wear leveling).

**Ключевые фишки:**

- **Оптимизация для SSD:** Высокая скорость случайной записи на флеш-носителях.
- **Checkpoint:** Быстрое восстановление после сбоев.
- **Компрессия:** Встроенная прозрачная компрессия (LZ4, Zstd).

**Ограничения:**

- Не предназначена для HDD (крайне низкая производительность).
- Меньшая зрелость по сравнению с ext4/XFS.

**Сценарии использования:** Смартфоны (Android), NVMe диски, SD-карты, Raspberry Pi.

**Утилиты:**
```bash
# Проверка ФС
sudo fsck.f2fs /dev/nvme0n1p1
```

## Практические сценарии

### Выбор ФС для базы данных

**PostgreSQL/MySQL:**

- **Рекомендация:** **XFS** (лучшая параллельность) или **Ext4** (стабильность).
- **Оптимизация:** Всегда использовать `noatime`. Для XFS с ядрами 4.9+ полезно включение `reflink=1` при форматировании для быстрых бэкапов.
- **ZFS:** Подходит для высоконадёжных БД при условии тюнинга `recordsize` под размер страницы БД (например, 8k для Postgres) и `logbias=throughput`.

### Выбор ФС для контейнеров (Docker/Kubernetes)

**Docker storage driver:**

- **Overlay2:** Рекомендуемый драйвер. Работает поверх **XFS** (предпочтительно с `ftype=1` и `reflink=1`) или **Ext4**. Использование reflinks в XFS значительно ускоряет сборку образов.
- **Btrfs/ZFS:** Используются как нативные драйверы, если хост уже работает на этих ФС. Позволяют эффективно использовать снапшоты для слоёв.

**Многослойность (OverlayFS):**
OverlayFS не является дисковой ФС, это слой объединения. Она монтирует `lowerdir` (read-only слои образа) и `upperdir` (write слой контейнера) в `merged` директорию. Детальный разбор работы в Docker — в **[Драйвере хранения OverlayFS](../../Docker/Docker_fs/docker_overlayfs.md)**.

### Выбор ФС для файлового сервера и NAS

**Рекомендация:** **ZFS** (OpenZFS).
- Обеспечивает максимальную защиту от "тихого" повреждения данных.
- Простая отправка снапшотов по сети (`zfs send | zfs receive`).
- Встроенное сжатие экономит место на медиа-контенте и документах.

### Выбор ФС для бэкапов

- **ZFS/Btrfs:** Использование инкрементальных снапшотов.
- **XFS:** Использование `cp --reflink` для создания мгновенных копий больших файлов без дублирования данных на диске.

### Выбор ФС для встраиваемых систем и образов

- **EROFS:** Если данные не будут меняться (прошивка, слои контейнеров). Обеспечивает минимальный размер и максимальную скорость загрузки.
- **SquashFS:** Альтернатива EROFS, чуть медленнее, но с более высокой степенью сжатия для специфических данных.
