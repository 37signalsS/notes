# Типы файловых систем: сравнительный обзор

## Определения

### Классификация файловых систем

Файловые системы классифицируются по назначению и архитектуре:

- **Дисковые (локальные)** — управляют данными на физических носителях (HDD, SSD, NVMe). Примеры: ext4, XFS, Btrfs, ZFS, F2FS.
- **Сетевые** — предоставляют доступ к файлам по сети. Примеры: NFS, CIFS/SMB, GlusterFS, CephFS.
- **Виртуальные (псевдо-ФС)** — не используют физическое хранилище, генерируются ядром в памяти. Примеры: procfs, sysfs, tmpfs, cgroupfs.
- **Специализированные** — оптимизированы под конкретные сценарии (ISO 9660 для оптических дисков, FAT32/exFAT для съёмных носителей).
- **Многослойные (Overlay/Union)** — объединяют несколько директорий в одну виртуальную иерархию. Примеры: OverlayFS (основа Docker), AUFS.
- **Компактные/Read-only** — оптимизированы для максимального сжатия и скорости чтения на встраиваемых системах. Примеры: EROFS, SquashFS.

### Ключевые характеристики ФС

При выборе файловой системы оцениваются:

- **Журналирование** — механизм защиты от сбоев питания путём записи намерений в журнал.
- **Copy-on-Write (CoW)** — метод, при котором данные никогда не перезаписываются на месте; изменения пишутся в новый блок, обеспечивая атомарность.
- **Целостность данных** — использование контрольных сумм для обнаружения и предотвращения "тихого" повреждения данных (silent data corruption).
- **Снапшоты** — поддержка мгновенных снимков состояния ФС (на основе CoW или LVM).
- **Reflinks (Reference Links)** — поддержка копирования файлов "ссылками" на те же блоки (Copy-on-Write на уровне отдельных файлов). Позволяет мгновенно копировать огромные файлы без затрат места.
- **Компрессия** — встроенное прозрачное сжатие данных "на лету" (LZO, Zstd, LZ4).
- **Дедупликация** — устранение дубликатов данных на уровне блоков (инлайн или офлайн).
- **Масштабируемость** — максимальный размер ФС, файла, количество inode (статическое или динамическое).
- **Производительность** — IOPS, пропускная способность, латентность при различных паттернах нагрузки (случайная запись, последовательное чтение).

### Архитектурные подходы к организации данных

Разные файловые системы используют различные стратегии для баланса между производительностью, целостностью и надёжностью:

- **Журналирование (ext4, XFS)** — перед изменением структур ФС намерение записывается в журнал. При сбое ядро доигрывает (replay) незавершённые транзакции. Обеспечивает быстрое восстановление, но создаёт двойную нагрузку на запись. Журналирование может покрывать только метаданные (XFS, ext4 по умолчанию) или также данные (ext4 `data=journal`).
- **Copy-on-Write (Btrfs, ZFS)** — данные никогда не перезаписываются на месте; изменения пишутся в новые блоки, а указатели обновляются атомарно. Исключает необходимость отдельного журнала и проблему "write hole", но создаёт фрагментацию при случайных записях и требует больше свободного места.
- **Log-structured (F2FS)** — все записи выполняются последовательно, что минимизирует износ NAND-ячеек. Особенно эффективно на флеш-носителях с ограниченным ресурсом перезаписи.
- **Read-only + сжатие (EROFS)** — метаданные оптимизированы для быстрого случайного доступа; данные читаются напрямую из сжатых блоков без распаковки в память.

**Write hole** — проблема классических RAID-контроллеров, при которой после сбоя питания запись, попавшая в кэш контроллера, не подтверждается на диск, но данные на диске оказываются в неконсистентном состоянии. CoW-ФС (Btrfs, ZFS) исключают write hole за счёт атомарного обновления указателей. В Btrfs RAID 5/6 write hole до сих пор является нерешённой проблемой для метаданных.

**Фрагментация** — разрыв непрерывности блоков файла на диске. Журналируемые ФС (ext4, XFS) фрагментируются меньше благодаря extent-based выделению и отложенному выделению (delayed allocation). CoW-ФС склонны к фрагментации при частых случайных записях; для Btrfs это mitigation через опцию `nodatacow` на конкретные файлы.

## Основные концепции

### Ext4 (Fourth Extended Filesystem)

**Ext4** — самая распространённая журналируемая ФС в Linux, обратная совместимая с ext3/ext2. Подробный разбор: [ext4.md](./ext4.md).

**Архитектура:**

- **Inode:** Фиксированное количество задаётся при создании (`mkfs.ext4 -i` или `-N`). Исчерпание inode блокирует создание новых файлов даже при наличии свободного места.
- **Extent-based allocation:** Вместо блочных маппингов использует экстенты (непрерывные диапазоны блоков), что снижает фрагментацию и ускоряет работу с крупными файлами.
- **Delayed allocation:** Откладывает выделение блоков до момента фактической записи, улучшая использование пространства.

**Режимы журналирования:**

- `data=journal` — данные + метаданные (максимальная надёжность, двойная запись).
- `data=ordered` (по умолчанию) — метаданные журналируются, данные записываются до фиксации метаданных.
- `data=writeback` — только метаданные (максимальная производительность, риск потери данных при сбое).

**Ограничения:**

- Максимальный размер ФС: 1 EiB (теоретически), на практике стабильно до 100 TiB.
- Максимальный размер файла: 16 TiB.
- Нет встроенных снапшотов и reflinks.
- Нет встроенной компрессии или дедупликации.
- Фиксированное количество inode (нельзя изменить без пересоздания ФС).

**Сценарии использования:** Универсальные серверы, корневые разделы, системы, где важна стабильность и предсказуемость.

**Утилиты:**
```bash
# Просмотр параметров ФС
sudo tune2fs -l /dev/sda1 | grep "Filesystem features"
# → Filesystem features: has_journal extents huge_file dir_nlink 64bit ...
```

**Особенности работы с SSD/NVMe:**

Ext4 корректно работает с SSD при включённом TRIM (`discard` в fstab или периодический `fstrim`). Для баз данных с intense write-нагрузкой на NVMe можно использовать `data=writeback` с барьерами записи для снижения латентности, но это требует гарантированного питания (ИБП или BBU). На SATA SSD ext4 часто показывает меньшую латентность записи, чем XFS, за счёт меньших накладных расходов на журналирование.

**Шифрование:**

Поддерживает **fscrypt** (ядро 5.x+) для прозрачного per-file шифрования на уровне ФС. Также может работать поверх LUKS для шифрования всего тома.

### XFS

**XFS** — высокопроизводительная 64-битная журналируемая ФС, ставшая стандартом для RHEL/CentOS 7+ и высоконагруженных систем. Подробный разбор: [xfs.md](./xfs.md).

**Архитектура:**

- **Динамические inode:** Создаются по мере необходимости, проблема исчерпания inode отсутствует.
- **Allocation groups:** Диск делится на независимые группы распределения, позволяя параллельные операции записи (высокий IOPS на многопроцессорных системах).
- **Reflinks (с ядра 4.9+):** Поддержка Copy-on-Write на уровне файлов. Позволяет мгновенно клонировать файлы (`cp --reflink`).
- **Delayed allocation:** Эффективное распределение блоков.

**Журналирование:** Только журналирование метаданных. XFS гарантирует, что данные будут сброшены на диск перед метаданными в журнале (аналог `data=ordered`).

**Ключевая особенность:** Не поддерживает уменьшение (shrink). Только расширение.

**Ограничения:**

- Максимальный размер ФС/файла: 8 EiB.
- Нет встроенной компрессии или дедупликации (но reflinks позволяют реализовать дедупликацию сторонними средствами).
- Восстановление удалённых файлов крайне затруднено.

**Сценарии использования:** Крупные хранилища данных, базы данных (ClickHouse, PostgreSQL), Docker (с драйвером `overlay2` и `ftype=1`), системы с высокой параллельной записью.

**Утилиты:**
```bash
# Проверка поддержки reflinks и ftype
xfs_info /mnt/data | grep -E "reflink|ftype"
# → naming   =version 2              bsize=4096   ascii-ci=0 ftype=1
# → realtime =none                   extsz=4096   blocks=0, rtextents=0
# → reflink  =1
```

**Особенности работы с SSD/NVMe:**

XFS хорошо масштабируется на NVMe благодаря allocation groups, позволяя параллельным потокам одновременно выделять место. Параметр `allocsize=1M` ускоряет запись больших файлов, выравнивая I/O под размер страницы NVMe. Для SATA SSD XFS может иметь slightly большую латентность по сравнению с ext4 из-за более сложного механизма выделения.

**Шифрование:**

XFS не имеет встроенного шифрования на уровне ФС. Шифрование реализуется через LUKS/Device Mapper. Для per-file шифрования можно использовать fscrypt (поддерживается в современных ядрах).

### Btrfs (B-Tree Filesystem / Butter FS)

**Btrfs** — современная ФС с Copy-on-Write (CoW), разработанная Oracle, сочетающая функции ФС и менеджера томов. Подробный разбор: [btrfs.md](./btrfs.md).

**Архитектура:**

- **Copy-on-Write (CoW):** Данные не перезаписываются; изменения пишутся в новые блоки, а указатели обновляются атомарно. Обеспечивает устойчивость к сбоям без двойной записи в журнал.
- **B-Tree:** Все метаданные и данные хранятся в B-деревьях, что ускоряет поиск и навигацию.
- **Subvolumes:** Логические разделы внутри одного пула, которые можно монтировать independently.

**Ключевые фишки:**

- **Снапшоты:** Мгновенные снимки подтомов на основе CoW.
- **Компрессия:** Прозрачное сжатие (zlib, lzo, zstd). Zstd рекомендуется для большинства сценариев.
- **Дедупликация:** Офлайн (с помощью `duperemove`) или онлайн (через экспериментальные патчи).
- **Встроенный RAID:** Поддержка RAID 0, 1, 10. **RAID 5/6 до сих пор считается нестабильным** для метаданных (проблема write hole).
- **Self-healing:** Проверка контрольных сумм при каждом чтении и автоматическое восстановление из зеркальных копий.

**Ограничения:**

- Высокая фрагментация при частых случайных записях (базы данных, VM) из-за CoW. Рекомендуется использовать опцию `nodatacow` для конкретных файлов.
- Сложность мониторинга свободного места (`df -h` может показывать неверные данные).

**Сценарии использования:** Домашние ПК (дистрибутивы Fedora, openSUSE), бэкап-серверы, системы со снапшотами.

**Утилиты:**
```bash
# Проверка использования пространства
sudo btrfs filesystem usage /mnt/btrfs
# → Overall:
# →     Device size:                  20.00GiB
# →     Device allocated:              2.02GiB
# →     Device unallocated:           17.98GiB
```

**Особенности работы с SSD/NVMe:**

Btrfs поддерживает опции монтирования `ssd` и `ssd_spread`, оптимизирующие алгоритмы выделения места под физику SSD. `discard=async` (ядро 5.6+) асинхронно отправляет TRIM, предотвращая фризы при массовом удалении файлов. Для NVMe `space_cache=v2` ускоряет монтирование за счёт кэширования карты свободного места.

**Шифрование:**

Btrfs поддерживает встроенное шифрование на уровне подтомов (ядро 6.1+). Также может работать поверх LUKS.

### ZFS (Zettabyte Filesystem / OpenZFS)

**ZFS** — мощная корпоративная ФС и менеджер томов "в одном флаконе". В Linux используется реализация **OpenZFS**.

**Архитектура:**

- **Пул (zpool):** Объединение физических дисков (vdev) в единое хранилище.
- **Датасеты (datasets):** Логические ФС внутри пула с независимыми настройками (сжатие, квоты).
- **ARC (Adaptive Replacement Cache):** Продвинутый алгоритм кэширования в RAM, заменяющий стандартный Page Cache.

**Ключевые фишки (OpenZFS 2.x+):**

- **Block Cloning (reflinks):** Появилось в версии 2.2, позволяет мгновенно клонировать файлы внутри датасета.
- **Zstd компрессия:** Отличная альтернатива lz4 для архивных данных.
- **RAID-Z (1/2/3):** Программный RAID с защитой от "тихого" повреждения данных и write hole.
- **Native Encryption:** Шифрование данных без накладных расходов LUKS.
- **Scrubbing:** Регулярная фоновая проверка целостности всех блоков данных.

**Ограничения:**

- **Потребление RAM:** Рекомендуется от 1 ГБ RAM на 1 ТБ данных для ARC (минимум 4-8 ГБ на систему).
- **Сложность расширения:** До недавнего времени нельзя было просто добавить один диск в RAID-Z vdev (требуется добавление нового vdev или расширение всех дисков).
- **Вне ядра:** Устанавливается как внешний модуль через **DKMS** (Dynamic Kernel Module Support), что может потребовать пересборки при обновлении ядра.

**Сценарии использования:** Профессиональные NAS, гипервизоры (Proxmox), бэкап-хранилища, базы данных с высокими требованиями к целостности.

**Утилиты:**
```bash
# Просмотр статуса пула
sudo zpool status
# → pool: tank
# → state: ONLINE
# → scan: scrub repaired 0B in 00:05:12 with 0 errors
```

**Особенности работы с SSD/NVMe:**

ZFS требует careful tuning для NVMe. `logbias=throughput` оптимизирует ZIL для последовательных записей, `primarycache=metadata` оставляет данные на устройстве, а metadata кэширует в ARC. Для enterprise NVMe с PLP (Power Loss Protection) можно использовать `sync=always` без критической потери производительности. На consumer SSD без PLP `sync=standard` предпочтительнее.

**Шифрование:**

ZFS имеет встроенное native encryption на уровне датасета. Ключи хранятся в ключевом хранилище или вводится при импорте пула. Шифрование не создаёт заметных накладных расходов по сравнению с LUKS.

### EROFS (Enhanced Read-Only File System)

**EROFS** — современная легковесная ФС только для чтения, разработанная Huawei для мобильных устройств и контейнеров.

**Архитектура:**

- **Fixed-sized output compression:** Оптимизирована для высокой скорости случайного доступа при использовании сжатия (LZ4, Zstd).
- **Zero-copy:** Прямое отображение данных из блочного устройства в кэш страниц.

**Ключевые фишки:**

- **Экстремальная производительность:** На чтение быстрее SquashFS и даже ext4 (за счёт меньших накладных расходов VFS).
- **Минимальный размер:** Компактные метаданные и эффективное сжатие.

**Сценарии использования:** Образы Android, слои контейнеров (через `composefs`), прошивки встраиваемых систем, LiveCD.

**Утилиты:**
```bash
# Создание образа EROFS из директории
mkfs.erofs image.erofs ./source_dir
```

**Шифрование:**

EROFS не поддерживает шифрование на уровне ФС (read-only). Шифрование применяется на уровне блочного устройства (LUKS) или на уровне контейнерных образов.

### F2FS (Flash-Friendly File System)

**F2FS** — ФС, разработанная Samsung специально для NAND flash памяти (SSD, eMMC, UFS).

**Архитектура:**

- **Log-structured:** Минимизирует износ ячеек flash путём последовательной записи данных.
- **Flash-aware:** Учитывает физические особенности NAND (erase blocks, wear leveling).

**Ключевые фишки:**

- **Оптимизация для SSD:** Высокая скорость случайной записи на флеш-носителях.
- **Checkpoint:** Быстрое восстановление после сбоев.
- **Компрессия:** Встроенная прозрачная компрессия (LZ4, Zstd).

**Ограничения:**

- Не предназначена для HDD (крайне низкая производительность).
- Меньшая зрелость по сравнению с ext4/XFS.

**Сценарии использования:** Смартфоны (Android), NVMe диски, SD-карты, Raspberry Pi.

**Утилиты:**
```bash
# Проверка ФС
sudo fsck.f2fs /dev/nvme0n1p1
```

**Особенности работы с SSD/NVMe:**

F2FS является нативной ФС для flash-памяти, оптимизированной под wear leveling и erase blocks. На TLC/QLC NVMe F2FS часто показывает лучшую производительность случайной записи, чем ext4/XFS, за счёт log-structured подхода, минимизирующего перезапись ячеек. Поддерживает режим `adaptive` для автоматической адаптации под характеристики устройства.

**Шифрование:**

Поддерживает **fscrypt** (ядро 5.10+) для per-file шифрования.

## Практические сценарии

### Выбор ФС для базы данных

**PostgreSQL/MySQL:**

- **Рекомендация:** **XFS** (лучшая параллельность) или **Ext4** (стабильность).
- **Оптимизация:** Всегда использовать `noatime`. Для XFS с ядрами 4.9+ полезно включение `reflink=1` при форматировании для быстрых бэкапов.
- **ZFS:** Подходит для высоконадёжных БД при условии тюнинга `recordsize` под размер страницы БД (например, 8k для Postgres) и `logbias=throughput`.

Для NVMe с enterprise SSD (с PLP) можно рассмотреть `data=writeback` на ext4 или `barrier=1` с оптимизированными `commit` интервалами. На consumer SSD без PLP используйте `data=ordered` (по умолчанию) и избегайте отключения барьеров.

### Выбор ФС для контейнеров (Docker/Kubernetes)

**Docker storage driver:**

- **Overlay2:** Рекомендуемый драйвер. Работает поверх **XFS** (предпочтительно с `ftype=1` и `reflink=1`) или **Ext4**. Использование reflinks в XFS значительно ускоряет сборку образов.
- **Btrfs/ZFS:** Используются как нативные драйверы, если хост уже работает на этих ФС. Позволяют эффективно использовать снапшоты для слоёв.

**Многослойность (OverlayFS):**
OverlayFS не является дисковой ФС, это слой объединения. Она монтирует `lowerdir` (read-only слои образа) и `upperdir` (write слой контейнера) в `merged` директорию. Детальный разбор работы в Docker — в **[Драйвер хранения OverlayFS](../../Docker/Docker_fs/docker_overlayfs.md)**.

### Выбор ФС для файлового сервера и NAS

**Рекомендация:** **ZFS** (OpenZFS).
- Обеспечивает максимальную защиту от "тихого" повреждения данных.
- Простая отправка снапшотов по сети (`zfs send | zfs receive`).
- Встроенное сжатие экономит место на медиа-контенте и документах.

Для домашнего NAS с ограниченным RAM (4–8 ГБ) рассмотрите Btrfs с RAID 1 или XFS с внешними бэкапами, так как ZFS потребляет значительный объём памяти под ARC.

### Выбор ФС для бэкапов

- **ZFS/Btrfs:** Использование инкрементальных снапшотов.
- **XFS:** Использование `cp --reflink` для создания мгновенных копий больших файлов без дублирования данных на диске.
- **Ext4:** Подходит для бэкапов на HDD, особенно при использовании LVM-снапшотов для создания consistent copies.

### Выбор ФС для встраиваемых систем и образов

- **EROFS:** Если данные не будут меняться (прошивка, слои контейнеров). Обеспечивает минимальный размер и максимальную скорость загрузки.
- **SquashFS:** Альтернатива EROFS, чуть медленнее, но с более высокой степенью сжатия для специфических данных.

### Миграция между файловыми системами

Смена ФС на Production-сервере требует планирования окон обслуживания. Наиболее надёжный метод — копирование данных через `rsync` или `tar`:

```bash
# Пример: миграция с ext4 на XFS
# 1. Создание нового тома (LVM или новый диск)
sudo lvcreate -L 100G -n data_xfs vg0

# 2. Форматирование в XFS
sudo mkfs.xfs -f /dev/vg0/data_xfs

# 3. Монтирование рядом со старым
sudo mkdir /mnt/data_new
sudo mount /dev/vg0/data_xfs /mnt/data_new

# 4. Первое копирование (с сохранением прав, владельцев, xattr)
sudo rsync -aAXHv --progress /mnt/data/ /mnt/data_new/

# 5. Переключение: остановка сервисов, финальная синхронизация, смена монтирования
sudo systemctl stop app
sudo rsync -aAXHv --progress /mnt/data/ /mnt/data_new/
sudo umount /mnt/data
sudo umount /mnt/data_new
sudo mount /dev/vg0/data_xfs /mnt/data
sudo systemctl start app
```

Для Btrfs возможен `btrfs send`/`receive` между разными подтомами, что эффективнее для инкрементальных миграций. ZFS поддерживает `zfs send`/`receive` между пулами.

### Мониторинг целостности и scrub

CoW-ФС (Btrfs, ZFS) требуют регулярной проверки контрольных сумм для обнаружения "тихих" повреждений:

```bash
# Btrfs: запуск scrub (проверка контрольных сумм и автоматическое восстановление)
sudo btrfs scrub start /mnt/btrfs
# Мониторинг статуса
sudo btrfs scrub status /mnt/btrfs
# → scrub started at Tue Sep 13 10:00:00 2026, running for 12 seconds
# → total bytes scrubbed: 1.15GiB with 0 errors

# ZFS: планирование scrub
sudo zpool scrub tank
# Проверка статуса
sudo zpool status tank
# → scan: scrub in progress since Wed Sep 13 10:05:00 2026
# →        1.45T scanned out of 5.20T at 450M/s, 28% done
```

Для ext4/XFS мониторинг строится вокруг `fsck` и SMART, так как они не проверяют данные на лету. Настройте регулярный `smartctl -a` и алерты на рост `Reallocated_Sector_Ct`.

### Выбор ФС для специфических рабочих нагрузок

**Система логирования (journald, syslog, ELK):**
- **XFS** или **Ext4** с `noatime` и `nodiratime`. Огромное количество мелких файлов (ротация логов) лучше всего работает на XFS с динамическими inode.
- На Btrfs используйте подтом `/var/log` с `nodatacow`, чтобы избежать фрагментации.

**Почтовый сервер (Postfix/Dovecot):**
- **XFS** — оптимальный выбор для тысяч небольших файлов (почтовые ящики в Maildir).
- При необходимости снэпшотов для бэкапа можно добавить LVM поверх XFS.

**CI/CD раннеры (GitLab CI, Jenkins):**
- **Btrfs** с подтомами для каждого джоба. Snapshot + discard после завершения сборки позволяет быстро освобождать место.
- Альтернатива: XFS с `cp --reflink` для workspace, что ускоряет инициализацию задач.

**Веб-сервер / Кэширование (Varnish, Nginx):**
- **tmpfs** (RAM) для высокоскоростного кэширования. Размер ограничен RAM.
- **Ext4** на SSD с `noatime` для persistent cache, если данные не влезают в RAM.

**Высокопроизводительные вычисления (HPC):**
- **XFS** с `allocsize=1M` и отключённым `barrier` на RAID с BBU. Лучшая масштабируемость на сотнях ядер.
- На NVMe можно рассмотреть **F2FS** для workloads с интенсивной случайной записью.

### Интеграция с systemd и автоматизация обслуживания

**systemd tmpfiles.d для очистки временных ФС:**

```bash
# /etc/tmpfiles.d/cleanup.conf
# Очистка /tmp каждые 3 дня
d /tmp 1777 root root 3d

# Очистка кэша пользователей раз в неделю
d /home/*/.cache 0750 user user 7d
```

**Таймеры для scrub и trim:**

```bash
# /etc/systemd/system/btrfs-scrub.service
[Unit]
Description=Btrfs scrub

[Service]
Type=oneshot
ExecStart=/usr/bin/btrfs scrub start /mnt/btrfs
```

```bash
# /etc/systemd/system/btrfs-scrub.timer
[Unit]
Description=Weekly Btrfs scrub

[Timer]
OnCalendar=weekly
Persistent=true

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl enable --now btrfs-scrub.timer
```

Для ZFS scrub также можно использовать systemd timer или встроенный `zpool scrub` через cron. Для fstrim на системах с systemd активируйте встроенный таймер:

```bash
sudo systemctl enable --now fstrim.timer
```

## Лучшие практики

1.  **Всегда используйте `noatime`** (или `lazytime` для баланса) в `/etc/fstab`. Это снижает лишние записи и увеличивает срок службы SSD.
2.  **Для баз данных используйте XFS** или Ext4 с `data=ordered`. Избегайте CoW-ФС (Btrfs/ZFS) без тщательного тюнинга `recordsize` и отключения CoW для файлов БД.
3.  **Планируйте capacity с запасом 15–20%.** При заполнении SSD выше 80% производительность резко падает (GC, SLC-кэш исчерпан). Для ZFS/Btrfs оставьте место для CoW-оверхеда.
4.  **Настройте автоматический scrub** (Btrfs/ZFS) и регулярный `fsck` (ext4/XFS через `tune2fs -i`/`-c`). Документируйте результаты.
5.  **Для overlay2 в Docker** используйте XFS с `ftype=1` и `reflink=1`. Это единственная конфигурация, позволяющая fully utilise copy-on-write для слоёв образов.
6.  **Никогда не используйте Btrfs RAID 5/6** в production. Write hole на уровне метаданных может привести к невосстановимой потере массива.
7.  **Изолируйте разделы с разными рабочими нагрузками.** `/var/log` с частой записью мелких файлов, `/home` с большими файлами и `/tmp` с ephemeral данными лучше монтировать отдельно с оптимальными для каждой нагрузки параметрами ФС.
