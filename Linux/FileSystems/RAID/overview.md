# Обзор RAID и mdadm

## Определения

### RAID

**RAID (Redundant Array of Independent Disks / Избыточный массив независимых дисков)** — технология объединения нескольких физических дисков в одну логическую сущность (массив) для решения двух ключевых задач:

1. **Производительность** — увеличение скорости чтения и записи данных за счёт параллелизации операций I/O.
2. **Отказоустойчивость** — защита от потери данных при выходе из строя одного или нескольких накопителей (в зависимости от уровня).

### Типы реализации RAID

| Тип | Описание | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **Программный** | Создаётся ОС средствами утилит (`mdadm` в Linux) | Гибкость, переносимость между системами, отсутствие vendor lock-in | Использование ресурсов CPU, зависимость от стабильности ядра |
| **Аппаратный** | Специализированный контроллер (HBA) с собственным CPU и RAM | Разгрузка CPU хоста, наличие кэша с защитой (BBU/Flash) | Высокая стоимость, риск потери данных при поломке контроллера |
| **Интегрированный (FakeRAID)** | Программная логика в чипсете материнской платы | Низкая стоимость | Худшая надежность, зависимость от специфичных драйверов |

> **Рекомендация:** В современных Linux-системах программный RAID на базе `mdadm` является стандартом де-факто для серверов без выделенного аппаратного контроллера. Он превосходит FakeRAID по стабильности и функциональности.

### Утилита mdadm

**`mdadm` (Multiple Devices Admin)** — основная утилита в Linux для управления программными RAID-массивами. Она взаимодействует с модулем ядра **MD (Multiple Devices)**.

*   **MD драйвер:** Работает на уровне блочных устройств, объединяя их в виртуальное устройство `/dev/mdX`.
*   **Слой в стеке:** Находится выше физических дисков, но ниже файловых систем или LVM.

## Основные концепции

### Архитектура и метаданные

Программный RAID хранит информацию о своей структуре в **суперблоке** на каждом диске-участнике. Это позволяет ОС автоматически собирать массив при загрузке.

**Версии метаданных:**

| Версия | Расположение | Особенности |
| :--- | :--- | :--- |
| **0.90** | Конец устройства | Устарела. Ограничение: 28 дисков, 2 ТБ на устройство. |
| **1.0** | Конец устройства | Позволяет читать данные как с обычного раздела без `mdadm` (удобно для `/boot`). |
| **1.1** | Начало устройства | Редко используется. |
| **1.2** | 4 КБ от начала | **Стандарт по умолчанию.** Оптимальна для современных систем. |

### Уровни RAID

Краткое сравнение (детальный разбор в [raid-levels.md](./raid-levels.md)):

| Уровень | Мин. дисков | Отказоустойчивость | Штраф на запись | Полезная ёмкость |
| :--- | :--- | :--- | :--- | :--- |
| **RAID 0** | 2 | 0 дисков | Нет | 100% |
| **RAID 1** | 2 | 1 диск | Нет | 50% |
| **RAID 5** | 3 | 1 диск | 4 (высокий) | (N-1)/N |
| **RAID 6** | 4 | 2 диска | 6 (очень высокий) | (N-2)/N |
| **RAID 10** | 4 | 1 диск в паре | Нет | 50% |

> **Важно:** Для дисков объёмом >2 ТБ настоятельно рекомендуется использовать RAID 6 или RAID 10. В RAID 5 время восстановления (rebuild) критически возрастает, повышая риск отказа второго диска или возникновения неисправимой ошибки чтения (URE).

## Планирование и надежность

### Разделы против целых дисков

При создании массива рекомендуется использовать разделы (тип `Linux raid autodetect`, код `FD` или `0xFD00` в GPT), а не целые диски (`/dev/sdb`).
*   **Преимущество:** Возможность оставить небольшое свободное место в конце диска. Это критично при замене диска на модель другого производителя, которая может оказаться на несколько мегабайт меньше.
*   **Гибкость:** Позволяет размещать на диске другие сущности (например, раздел для загрузчика).

### Bitmap (Write-intent bitmap)

Механизм, отслеживающий «грязные» блоки, которые еще не были синхронизированы между дисками.
*   **Зачем:** Значительно ускоряет восстановление массива после некорректного выключения системы (power failure). Вместо полной синхронизации всех данных (re-sync), `mdadm` обновит только измененные блоки.
*   **Минус:** Незначительное снижение производительности на запись.

### Scrubbing (Проверка целостности)

Процесс фонового чтения всех блоков массива для выявления ошибок чтения и несовпадений контрольных сумм.
*   **Команда:** `echo check > /sys/block/mdX/md/sync_action`
*   **Рекомендация:** Проводить проверку (consistency check) не реже одного раза в месяц.

### Hot Spare (Горячий резерв)

Диск, который подключен к системе, но не используется в активной работе массива до момента отказа одного из основных дисков.
*   **Автоматизация:** При сбое активного диска `mdadm` автоматически переносит данные на Hot Spare и начинает процесс восстановления.

## Практические сценарии

### Настройка автоматической сборки

После создания массива необходимо обновить конфигурацию, иначе после перезагрузки устройство может получить другое имя или не собраться.

1. **Обновление mdadm.conf:**
   ```bash
   # Сканирование текущих массивов и добавление в конфиг
   mdadm --detail --scan | sudo tee -a /etc/mdadm/mdadm.conf
   ```

2. **Обновление initramfs:**
   Критично для систем, где корневая ФС находится на RAID.
   ```bash
   sudo update-initramfs -u
   ```

### Мониторинг состояния

Текущий статус всех массивов доступен в реальном времени:
```bash
cat /proc/mdstat
```
*   `[UU]` — массив исправен.
*   `[_U]` или `[U_]` — массив деградирован (один диск отсутствует или неисправен).
