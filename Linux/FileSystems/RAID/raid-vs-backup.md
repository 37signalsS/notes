# Отличие RAID от резервного копирования

## Определения

**RAID (Redundant Array of Independent Disks)** — технология объединения физических накопителей в логическую единицу для обеспечения **высокой доступности (High Availability)** и производительности. RAID защищает систему от простоя при аппаратном отказе одного или нескольких дисков.

**Резервное копирование (Backup)** — создание копий данных на независимых носителях для обеспечения **сохранности данных (Data Preservation)** и возможности восстановления после логического повреждения, удаления или катастрофической потери.

> **Фундаментальное правило:** RAID — это не бэкап. RAID обеспечивает непрерывность бизнес-процессов (Uptime), а бэкап обеспечивает выживание данных (Data Survival).

---

## Основные концепции

### RPO/RTO и их связь с выбором стратегии

**RPO (Recovery Point Objective)** — максимально допустимый объем потери данных, выраженный во времени. Например, RPO = 15 минут означает, что система может потерять не более 15 минут данных. Определяет частоту бэкапов.

**RTO (Recovery Time Objective)** — максимально допустимое время восстановления системы до рабочего состояния. Определяет выбор инструментов и архитектуры восстановления.

| Параметр | RAID | Резервное копирование |
| :--- | :--- | :--- |
| **RPO** | ≈ 0 (данные доступны мгновенно) | Зависит от частоты бэкапов (часы, минуты) |
| **RTO** | ≈ 0 (непрерывная работа) | Зависит от размера данных и метода восстановления |

> **Важно:** RAID не влияет на RPO/RTO при логических ошибках. Если пользователь удалил файл или база данных повреждена, RAID реплицирует поврежденные данные мгновенно. Только бэкап позволяет «откатиться» к состоянию до ошибки.

### Ключевые отличия: матрица решений

| Критерий | RAID (Отказоустойчивость) | Резервное копирование (Сохранность) |
| :--- | :--- | :--- |
| **Защита от** | Аппаратный отказ диска/контроллера | Логические ошибки, удаление, шифровальщики |
| **Не защищает от** | Логических ошибок, удаления файлов, пожара | Аппаратного простоя (не обеспечивает Uptime) |
| **Стоимость** | Диски + контроллер (OPEX/CAPEX) | Хранилище + ПО (OPEX) |
| **Сложность** | Средняя (настройка, мониторинг) | Средняя-Высокая (политики, тестирование) |
| **Время восстановления** | Мгновенно (rebuild массива) | Часы-сутки (зависит от объема) |
| **Консистентность** | Мгновенная репликация (все изменения) | Точка восстановления (snap dump) |

## Сравнение концепций

### Цели и сценарии защиты

| Параметр | RAID (Отказоустойчивость) | Резервное копирование |
| :--- | :--- | :--- |
| **Основная цель** | Непрерывность работы системы (High Availability). | Восстановление данных (Disaster Recovery). |
| **Объект защиты** | Физический носитель (диск/контроллер). | Информация (файлы, БД, конфигурации). |
| **Логическая ошибка** | Реплицируется мгновенно (включая удаление файлов). | Позволяет «откатиться» к состоянию до ошибки. |
| **Место хранения** | Внутри того же сервера/СХД. | На независимом оборудовании или в облаке. |
| **Время восстановления** | Мгновенно (при отказе диска). | Зависит от объема данных и скорости сети (RTO). |

### Матрица угроз и эффективности (Контекст 2026)

| Тип угрозы | Защита через RAID | Защита через Backup | Комментарий |
| :--- | :--- | :--- | :--- |
| **Отказ 1 диска** | Да (кроме RAID 0) | Да | RAID позволяет продолжить работу без паузы. |
| **Множественный отказ** | Нет (зависит от RAID) | Да | Выход 3-х дисков в RAID 6 фатален для массива. |
| **Ошибка пользователя** | Нет | Да | `rm -rf` или `DROP TABLE` требуют бэкапа. |
| **Вирус-шифровальщик** | Нет | Да (Immutable) | RAID зашифрует все зеркала одновременно. |
| **Bit rot (тихая порча)** | Частично | Да | RAID без проверки контрольных сумм не видит порчу. |
| **Катастрофа (пожар)** | Нет | Да (Off-site) | Уничтожение площадки убивает массив. |
| **Сбой контроллера RAID** | Нет | Да | Контроллер — единственная точка отказа. |
| **Повреждение метаданных ФС** | Нет | Да | `fsck` может удалить поврежденные файлы. |
| **Одновременный отказ дисков** | Да (RAID 6/Z3) | Да | RAID 6 выдерживает 2 отказа, RAID-Z3 — 3. |

## Типичные заблуждения о RAID

### Заблуждение 1: «RAID защищает от потери данных»

**Реальность:** RAID защищает от **аппаратного простоя**, но не от **логической потери данных**. Если пользователь случайно удалил файлы или база данных повреждена, RAID мгновенно реплицирует поврежденные данные на все зеркала. После этого восстановление без бэкапа невозможно.

### Заблуждение 2: «RAID 1 = 100% надежность»

**Реальность:** RAID 1 (зеркало) не гарантирует выживание данных при:
- Одновременном выходе обоих дисков (крайне редко, но возможно)
- Повреждении метаданных ФС (ошибка реплицируется)
- Сбое контроллера RAID (оба диска недоступны)
- Логической ошибке (удаление файла — оно же на обоих дисках)

### Заблуждение 3: «RAID 5足够 для критичных данных»

**Реальность:** При современных дисках 16-20+ ТБ RAID 5 становится опасным:
- Rebuild занимает сутки и создает 100% нагрузку на оставшиеся диски
- Вероятность URE (Unrecoverable Read Error) на больших объемах крайне высока
- Один URE во время rebuild = потеря массива
- **Рекомендация:** Для дисков >8 ТБ использовать RAID 6 или RAID-Z2

### Заблуждение 4: «Снапшоты = бэкап»

**Реальность:** Снимки (LVM, ZFS, Btrfs) хранятся на том же физическом массиве:
- Не защищают от физического выхода массива из строя
- Не защищают от шифровальщиков (вирус зашифрует и снимки)
- Не защищают от пожара/затопления площадки
- **Рекомендация:** Снимки = быстрый откат, бэкап = выживание данных

### Заблуждение 5: «Есть RAID — бэкап не нужен»

**Реальность:** RAID и бэкап решают **разные задачи**:
- RAID = непрерывность работы (Uptime) при аппаратных сбоях
- Бэкап = выживание данных при логических ошибках и катастрофах
- **Оба обязательны** для критичных систем

## Технические нюансы

### Проблема «Bit rot» и целостность данных
Bit rot — постепенная деградация носителя, приводящая к изменению отдельных бит без явного отказа диска.
*   **Обычный RAID:** Контроллеры или `mdadm` (без использования ФС с CoW) могут не заметить повреждение блока. При чтении система получит битые данные, а при ресинхронизации «битое» значение может быть записано в зеркало.
*   **Решение:** Использование ФС с контрольными суммами (**ZFS**, **Btrfs**). Они интегрируют функции RAID и проверки целостности, позволяя исправлять Bit rot на лету (Self-healing).

### Уровни консистентности данных

При выборе стратегии защиты необходимо понимать разницу между уровнями консистентности:

| Уровень | Описание | Пример | Восстановление |
| :--- | :--- | :--- | :--- |
| **Crash-consistent** | Состояние как после внезапного выключения питания | Снапшот LVM, ВМ | БД может потребовать recovery |
| **Application-consistent** | Приложение сбросило все буферы на диск | `pg_dump`, `mysqldump` | БД готова к работе immediately |
| **File-system consistent** | ФС синхронизирована, но приложение не знает о снимке | Снапшот ZFS/Btrfs | Зависит от приложения |

**Почему это важно:** RAID работает на уровне блочных устройств и не контролирует консистентность данных приложений. При отказе диска RAID обеспечивает непрерывность работы, но не гарантирует целостность данных БД. Бэкап с application-consistent уровнем (через `pg_dump`, `xtrabackup`) гарантирует восстановление БД в согласованном состоянии.

### Проблема восстановления (Rebuild Penalty)
При использовании современных дисков большой емкости (HDD 30ТБ+) процесс восстановления RAID 5/6 становится критически опасным.
1.  **Нагрузка:** Rebuild создает 100% нагрузку на чтение всех оставшихся дисков в течение многих часов (или дней).
2.  **URE (Unrecoverable Read Error):** Вероятность встретить нечитаемый сектор на диске 30ТБ при полном чтении крайне высока. Для RAID 5 это означает потерю массива.
3.  **Вывод:** Наличие актуального бэкапа перед началом замены диска и ребилда — обязательное условие безопасности.

**Расчет времени ребилда:**
```
Время ребилда ≈ Объем массива / Скорость чтения оставшихся дисков
Пример: 12 ТБ массив на RAID 5 с 3 дисками, скорость чтения 200 МБ/с
12 ТБ / 200 МБ/с ≈ 60 000 секунд ≈ 16.7 часов
```

### Снимки (Snapshots) против Резервных копий
Снимки — это мгновенные состояния ФС или тома LVM.
*   **Снимки:** Хранятся на том же физическом массиве. Позволяют быстро восстановить случайно удаленный файл или откатить миграцию БД, но **не защищают** от физического выхода массива из строя.
*   **Резервные копии:** Полностью независимые наборы данных. Требуют ресурсов на передачу, но гарантируют восстановление даже при полной потере сервера.

**Рекомендация по использованию снимков:**
| Сценарий | Снапшоты | Бэкап | Обоснование |
| :--- | :--- | :--- | :--- |
| Откат миграции БД | Да | Нет | Быстрый откат за секунды |
| Восстановление после `rm -rf` | Частично | Да | Снапшот может быть зашифрован |
| Замена диска в RAID | Нет | Да | Физическая замена требует бэкап |
| Восстановление после пожара | Нет | Да (Off-site) | Снапшоты на той же площадке |

## Практические сценарии сбоев

### Сценарий 1: RAID 5 + отказ диска + URE при ребилде

**Ситуация:** Сервер с RAID 5 из 4 дисков по 10 ТБ. Один диск вышел из строя. Начат rebuild на новый диск.

**Проблема:** Во время rebuild на одном из оставшихся дисков обнаружен URE (Unrecoverable Read Error). Для RAID 5 это катастрофа — массив не может быть восстановлен.

**Последствия:**
- Полная потеря данных на массиве
- Время простоя: часы-сутки (восстановление из бэкапа)
- Потеря данных: от момента последнего бэкапа до момента сбоя

**Решение:** Наличие актуального бэкапа позволяет восстановить данные за RTO, определенное политикой.

**Пример команд для диагностики:**
```bash
# Проверка состояния массива
cat /proc/mdstat
# → md0 : active raid5 sdd1[3] sdc1[2] sdb1[1]
#       29297555456 blocks super 1.2 level 5, 512k chunk, algorithm 2 [4/3] [_UUU]

# Проверка логов на URE
dmesg | grep -i "error\|corrupt\|bad sector"
# → [12345.678] md0: data CRC error on sdb1
```

### Сценарий 2: RAID 1 (зеркало) + повреждение ФС

**Ситуация:** RAID 1 из двух дисков. Файловая система повреждена из-за сбоя питания.

**Проблема:** Оба диска содержат идентичные поврежденные данные. RAID 1 не помогает — он реплицирует ошибки.

**Последствия:**
- `fsck` может удалить поврежденные файлы
- Данные на обоих дисках идентичны (включая повреждения)
- Восстановление возможно только из бэкапа

**Пример восстановления:**
```bash
# Проверка файловой системы
sudo fsck -n /dev/md0
# → fsck.ext4:鲻 не удалось восстановить superblock

# Восстановление из бэкапа
sudo restore -r -f /backup/dump.0 /mnt/restore
```

### Сценарий 3: RAID 6 + шифровальщик

**Ситуация:** RAID 6 из 6 дисков. Вирус-шифровальщик зашифровал данные на сервере.

**Проблема:** RAID 6 выдержал бы отказ 2 дисков, но не защищает от шифрования. Все 6 дисков содержат зашифрованные данные.

**Последствия:**
- RAID массив функционирует (все диски «здоровы»)
- Данные зашифрованы на всех дисках одновременно
- Восстановление только из immutable бэкапа

**Пример использования immutable бэкапа:**
```bash
# Borg с append-only (защита от удаления)
borg init --encryption=repokey /backup/borg-repo
borg create --stats /backup/borg-repo::$(date +%Y%m%d) /data

# Проверка что старые архивы не удалены
borg list /backup/borg-repo
# → Архивы до заражения сохранены
```

### Сценарий 4: RAID 10 + ошибка администратора

**Ситуация:** RAID 10 из 8 дисков. Администратор случайно удалил важную директорию `/var/lib/mysql`.

**Проблема:** RAID 10 обеспечивает отказоустойчивость, но не защищает от ошибок людей. Удаление мгновенно реплицируется на все зеркала.

**Последствия:**
- Данные удалены на всех дисках
- Восстановление из снимка (если есть) или бэкапа

**Пример восстановления из снимка LVM:**
```bash
# Проверка доступных снимков
sudo lvs -o lv_name,lv_size,lv_origin

# Восстановление из снимка
sudo lvconvert --merge /dev/vg0/mysql_snap
```

## Практические стратегии

### Матрица выбора стратегии защиты

| Тип данных | RAID уровень | Бэкап стратегия | Частота бэкапа | RPO/RTO |
| :--- | :--- | :--- | :--- | :--- |
| **Web-сервер (статика)** | RAID 1 или RAID 10 | rsync + offsite | Ежедневно | RPO: 24ч, RTO: 1ч |
| **База данных (OLTP)** | RAID 10 | pg_dump/xtrabackup + WAL | Каждые 15 мин | RPO: 15 мин, RTO: 30 мин |
| **Файловый сервер** | RAID 5/6 | Borg/Restic + offsite | Ежедневно | RPO: 24ч, RTO: 2ч |
| **Mail-сервер** | RAID 1 | Borg + offsite | Каждые 6 часов | RPO: 6ч, RTO: 1ч |
| **Логи (ELK)** | RAID 0 + репликация | Снимки + архив | Ежедневно | RPO: 24ч, RTO: 4ч |
| **Критичная БД (金融)** | RAID 10 + Hot Spare | pg_dump + WAL + offsite | Непрерывно | RPO: 0, RTO: 5 мин |

### Современный стандарт: Правило «3-2-1-1-0»
1.  **3 копии данных:** Основная (рабочая) + 2 резервные.
2.  **2 типа носителей:** Например, RAID-массив сервера и LTO-лента или удаленный NAS.
3.  **1 копия Off-site:** В другом географическом регионе (облако S3, второй дата-центр).
4.  **1 копия Offline/Immutable:** Неизменяемое хранилище (Object Lock), защищенное от шифровальщиков.
5.  **0 ошибок:** Регулярное автоматизированное тестирование восстановления (Backup Validation).

**Практическая реализация:**
```bash
# 1. Локальный бэкап (Borg) — 2 копии на разных носителях
borg create --stats /backup/borg-local::$(date +%Y%m%d) /data
borg create --stats /mnt/usb/borg-usb::$(date +%Y%m%d) /data

# 2. Off-site копия (rsync)
rsync -avz --delete /backup/ user@remote-server:/backup/

# 3. Immutable копия (borg append-only через SSH)
borg create --stats /remote/borg-offsite::$(date +%Y%m%d) /data

# 4. Тест восстановления (0 ошибок)
borg extract --dry-run /backup/borg-local::$(date +%Y%m%d)
```

### Комплексный подход (Tiered Data Protection)
Для минимизации RPO и RTO рекомендуется использовать слои:
*   **L0 (Availability):** RAID 10 / RAID-Z3 для защиты от отказа "железа" и высокого IOPS.
*   **L1 (Versioning):** Снапшоты ФС (ZFS/Btrfs) каждые 15-60 минут для мгновенного отката.
*   **L2 (Local Backup):** Ежедневный бэкап на локальный сервер (BorgBackup, Restic) с дедупликацией.
*   **L3 (Archive):** Еженедельный зашифрованный архив в холодное хранилище (LTO-лента, offsite NAS).

**Пример реализации уровней:**
```bash
# L0: RAID 10 (аппаратный уровень)
sudo mdadm --create /dev/md0 --level=10 --raid-devices=4 /dev/sd[b-e]

# L1: Снапшоты каждые 30 минут (cron)
# /etc/cron.d/zfs-snapshot
*/30 * * * * root zfs snapshot -r pool/data@snap-$(date +\%Y\%m\%d-\%H\%M)

# L2: Ежедневный бэкап (borgmatic)
# /etc/cron.d/borg-backup
0 2 * * * root borgmatic --config /etc/borgmatic/config.yaml

# L3: Еженедельный off-site архив
0 3 * * 0 root rsync -avz /backup/ user@remote:/backup/
```
