# Внутреннее устройство файловых систем

## Определения

- **Файловая система (FileSystem, ФС):** Набор алгоритмов и структур данных, определяющих способ организации, иерархического хранения и именования данных на блочных устройствах.
- **VFS (Virtual File System):** Высокоуровневый слой абстракции в ядре Linux, предоставляющий приложениям унифицированный интерфейс (POSIX API) для взаимодействия с разнородными ФС (ext4, XFS, NFS, procfs).
- **Объект VFS:** Абстрактная структура данных в памяти ядра, представляющая элемент ФС. Основные объекты: Superblock, Inode, Dentry, File.
- **Экстент (Extent):** Непрерывный диапазон физических блоков на диске, описываемый парой «начальный блок + длина». Современная альтернатива поблочному маппингу, снижающая фрагментацию и размер метаданных.
- **Суперблок (Superblock):** Глобальная структура ФС, хранящая метаданные о томе: размер блока, количество inode, состояние монтирования, UUID, флаги. В ext4 резервируются backup-копии в каждой группе блоков для аварийного восстановления.
- **Dentry Cache (Dcache):** Кэш в памяти ядра, хранящий сопоставление компонентов пути и Inode для ускорения разрешения имён без повторного сканирования диска.
- **Page Cache:** Единый кэш страниц ядра, объединяющий кэширование данных файлов и метаданных. В современных ядрах (2.4+) Buffer Cache интегрирован в Page Cache.
- **Writeback:** Фоновый механизм отложенной записи «грязных» (dirty) страниц из RAM на диск, управляемый потоками `kworker` и подсистемой `balance_dirty_pages()`.
- **Блочный слой (Block Layer):** Подсистема ядра, преобразующая запросы VFS в структуры `bio`, управляющая очередями и передающая запросы драйверам устройств через планировщик.
- **Барьер записи (Write Barrier):** Гарантия ядра, что данные и метаданные фиксированы на диске в правильном порядке. Критичен для журналируемых ФС при отсутствии BBU.

## Архитектура VFS

VFS преобразует абстрактные системные вызовы (например, `read()`) в вызовы конкретных функций драйвера ФС через таблицы указателей на функции.

### Фундаментальные объекты VFS

| Объект | Структура в ядре | Описание | Основные операции (`_ops`) |
| :--- | :--- | :--- | :--- |
| **Superblock** | `struct super_block` | Описывает состояние смонтированной ФС. | `write_super`, `put_super`, `statfs`. |
| **Inode** | `struct inode` | Метаданные конкретного файла (права, размер, время). | `create`, `lookup`, `mkdir`, `setattr`. |
| **Dentry** | `struct dentry` | Связующее звено между именем файла и его Inode. | `d_compare`, `d_delete`, `d_release`. |
| **File** | `struct file` | Состояние открытого файла процессом (курсор, флаги). | `read`, `write`, `mmap`, `fsync`. |

Пример таблицы операций (`struct file_operations`) позволяет ядру вызывать `ext4_file_read` или `xfs_file_read` прозрачно для приложения.

### Жизненный цикл объектов VFS

**Inode:**
1. **Allocation:** При создании файла ФС выделяет inode на диске и загружает его в память (`struct inode`).
2. **Caching:** Inode кэшируется в `icache` (inode cache) для быстрого повторного доступа.
3. **Eviction:** При нехватке памяти ядро может выгрузить inode из кэша; при следующем обращении он будет загружен с диска заново.

**Dentry:**
1. **Allocation:** При разрешении пути создаётся цепочка dentry для каждого компонента (`/usr/bin/ls` → `/`, `/usr`, `/bin`, `ls`).
2. **Caching:** Dentry хранится в `dcache`. При повторном обращении к тому же пути ядро обходит сканирование диска.
3. **Pruning:** Неиспользуемые dentry помечаются как `unused` и удаляются шринкерами при нехватке памяти.

**Superblock:**
- Существует ровно один `super_block` на смонтированную ФС.
- Инициализируется при `mount()` и освобождается при `umount()`.
- Содержит указатель на `struct super_operations` — таблицу методов ФС.

### Механизм монтирования

При вызове `mount()` ядро:
1. Определяет тип ФС и вызывает соответствующий `fill_super()`.
2. Читает суперблок с диска и инициализирует `struct super_block`.
3. Создаёт dentry для корневого каталога (`/`).
4. Добавляет запись в mount-дерево текущего namespace.
5. Привязывает ФС к точке монтирования в VFS.

**Mount Propagation:**
- `shared`: События монтирования/размонтирования распространяются между участниками группы.
- `slave`: Получает события от `shared`, но не распространяет свои.
- `private`: Изоляция — события не распространяются.
- `unbindable`: То же, что `private`, но запрещает bind-монтирование.

### Путь запроса ввода-вывода (I/O Path)

1.  **Userspace:** Приложение вызывает `read(fd, buf, len)`.
2.  **VFS:** Находит `struct file` по дескриптору `fd`, проверяет права и обращается к связанному `inode`.
3.  **Page Cache:** Ядро ищет данные в оперативной памяти (Pages). Если данные найдены (Cache Hit), они копируются в буфер приложения.
4.  **FS Driver:** При промахе (Cache Miss) драйвер ФС преобразует логическое смещение в файле в адреса физических блоков (LBA) с помощью **экстентов** или карт блоков.
5.  **Block Layer:** Формирует структуру `bio` (Block I/O), которая передается планировщику (I/O Scheduler) и затем драйверу блочного устройства.

## Основные компоненты

### Физическая организация: Группы и области

Файловые системы делят диск на крупные логические области для локализации данных и метаданных, что снижает перемещение головок HDD.

- **Block Groups (ext4):** Диск делится на группы фиксированного размера. Каждая группа содержит копию суперблока (опционально), битовые карты блоков/инод и таблицу инод. Это позволяет хранить метаданные рядом с данными файла.
- **Allocation Groups (XFS):** Аналог групп блоков, но с поддержкой параллельного доступа. Каждая AG имеет собственные структуры управления свободным пространством (B+ деревья), что позволяет XFS эффективно масштабироваться на многоядерных системах.

### Кэширование и целостность

В современных ядрах (2.4+) Page Cache и Buffer Cache интегрированы.
- **Page Cache:** Кэширует данные файлов страницами (обычно 4 КБ).
- **Buffer Cache:** Используется для кэширования метаданных (структур управления ФС), которые не кратны размеру страницы или относятся к сырому блочному устройству.
- **Writeback:** Механизм отложенной записи «грязных» страниц из RAM на диск. Параметры тюнинга описаны в [настройке Page Cache](../Diagnostics/Performance/DiskIO/writeback_tuning.md).

### Блочный слой и запросы I/O

Block Layer преобразует запросы VFS в структуры `bio` и передаёт их драйверам устройств:
- **`struct bio`:** Описывает диапазон блоков на устройстве и направление (чтение/запись).
- **Request Queue:** Очередь запросов для каждого блочного устройства. Параметры очереди (глубина, размер сегмента) доступны в `/sys/block/<dev>/queue/`.
- **blk-mq:** Современная архитектура Multi-Queue, распределяющая запросы по аппаратным очередям накопителя (критично для NVMe).

### Журналирование и целостность

Механизм журналирования обеспечивает атомарность операций и быстрое восстановление после сбоев. Подробное описание режимов, JBD2, CIL и write barriers см. в **[Журналирование файловых систем](./journaling.md)**.

Ключевые понятия:
- **WAL (Write-Ahead Logging):** Запись в журнал должна быть подтверждена до внесения изменений в основные структуры.
- **Барьеры записи (`barrier=1`):** Гарантируют сброс кэша диска перед завершением транзакции. Обязательны при отсутствии BBU на RAID.

## Практические сценарии

### 1. Анализ топологии ФС через `findmnt`

Утилита позволяет увидеть иерархию монтирования и специфические VFS-флаги.

```bash
# Показать дерево монтирования с источниками и опциями
findmnt -D

# Проверить статус "readonly" и параметры журналирования
findmnt -no TARGET,OPTIONS /
```

### 2. Глубокое исследование метаданных (debugfs)

Для ext4 можно просмотреть структуру конкретного инода и его экстентов.

```bash
# Просмотр карты экстентов файла
sudo debugfs -R "extents /etc/passwd" /dev/sda1
# → Level 0: 1 1 542456 -- показывает диапазон блоков
```

### 3. Диагностика суперблоков (XFS)

XFS хранит суперблок в начале каждой Allocation Group.

```bash
# Инспекция геометрии ФС
sudo xfs_info /mnt/data

# Проверка состояния свободных блоков в AG
sudo xfs_db -c "freesp" /dev/sda1
```

### 4. Инспекция VFS-кэшей (dcache, icache, page cache)

VFS поддерживает кэширование путей (dcache), метаданных (icache) и данных (page cache). Их состояние можно наблюдать через `/proc`:

```bash
# Статистика page cache
grep -E "^(Buffers|Cached|Dirty|Writeback|Shmem)" /proc/meminfo
# → Cached:        12345678 kB
# → Dirty:          123456 kB
# → Writeback:       12345 kB

# Доля dentry и inode в slab
cat /proc/sys/fs/dentry-state
# → 12345 6789 45 0 0 0  # [count] [age] [max_pct] ...

cat /proc/sys/fs/inode-state
# → 123456 7890 45 0 0 0 ...

# Давление на VFS-кэш
sysctl vm.vfs_cache_pressure
# → 100 (default)
```

### 5. Диагностика writeback и dirty pages

Для SRE важно понимать, почему диск busy и где задержки:

```bash
# Грязные страницы и их возраст
cat /proc/meminfo | grep -E "Dirty|Writeback"
# → Dirty: 524288 kB
# → Writeback: 0 kB

# Активные flusher-потоки
ps aux | grep kworker | grep flush
# → root      123  0.0  0.0      0     0 ?        S    10:00   0:00 [kworker/3:1H-kblockd]

# Статистика BDI (Backing Device Info)
cat /sys/class/bdi/8:0/read_ahead_kb
# → 128
```

### 6. Проверка параметров суперблока и состояния ФС

```bash
# Полная информация о суперблоке ext4
sudo dumpe2fs -h /dev/sda1 | grep -E "Filesystem state|Block count|Inode count|Free blocks|Free inodes"
# → Filesystem state: clean
# → Block count:         244190936
# → Inode count:         30967808

# Проверка, какие dentry/inode находятся в памяти
sudo slabtop -s c | head -20
# → OBJS  SIZE  OBJ SIZE  SLABS  OBJ/SLAB  CACHE SIZE NAME
# → 12345   96    96.00    153     81       612K  dentry
# → 23456   96    96.00    366     64      1464K  ext4_inode_cache
```

### 7. Трассировка VFS-операций (ftrace/bcc)

Для глубокой диагностики производительности:

```bash
# Трассировка операций open() через ftrace
echo 1 | sudo tee /sys/kernel/debug/tracing/events/fs/open/open_enable
sudo cat /sys/kernel/debug/tracing/trace_pipe | head

# Или через bpftrace (если установлен)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_open { printf("%s %s\n", comm, str(args->filename)); }'
```

### 8. Контейнеры и изоляция ФС (Mount Namespaces)

VFS интегрируется с namespaces для изоляции файловых систем в контейнерах:

```bash
# Просмотр mount-пространства текущего процесса
cat /proc/1/mountinfo | head -20
# → 23 22 0:22 / /sys rw,nosuid,nodev,noexec,relatime - sysfs sysfs rw

# Сравнение mount-пространств контейнера и хоста
nsenter -t $(docker inspect --format '{{.State.Pid}}' container1) -m cat /proc/mounts | head

# Bind mount для изоляции
mount --bind /mnt/data /mnt/data
mount --make-private /mnt/data  # изоляция propagation
```

### 9. Отладка проблем с dentry и inode

```bash
# Принудительное освобождение неиспользуемого dcache
sudo sysctl -w vm.drop_caches=2
# → pagecache, dentries and inodes freed

# Проверка количества отрицательных dentry (не найденные пути)
cat /proc/sys/fs/dentry-state
# → 12345 6789 45 0 0 0  # пятое число = negative dentries

# Если negative dentry много — возможно, приложение активно проверяет несуществующие пути
```

## Типичные ошибки и диагностика

| Проблема | Причина и решение |
| :--- | :--- |
| **"No space left on device" при наличии свободного места** | Исчерпание inode (`df -i`). Решение: удалить мелкие файлы или пересоздать ФС с большим количеством inode (`mkfs.ext4 -N`). |
| **Высокий `Dirty` в `/proc/meminfo` без записи на диск** | Writeback stalled. Проверьте `iostat` на предмет busy-диска. Уменьшите `vm.dirty_ratio`. |
| **Большой `Dentry` cache при нехватке RAM** | Ядро удерживает много неиспользуемых dentry. Проверьте `vm.vfs_cache_pressure`. Для СУБД установите `50`, чтобы ускорить освобождение. |
| **Корневая ФС переходит в read-only** | Журнал обнаружил несогласованность. Проверьте `dmesg | grep -i ext4`. Возможно, требуется `fsck` или замена диска. |
| **Ошибка "Too many open files"** | Исчерпан лимит дескрипторов (`ulimit -n`). Проверьте `cat /proc/sys/fs/file-nr`. |
| **Файл удалён, но место не освобождается** | Файл открыт процессом (`lsof | grep deleted`). Убейте процесс или перезагрузите. |
| **Временные файлы в `/tmp` заполняют RAM** | tmpfs смонтирован без ограничения `size`. Проверьте `df -h /tmp` и добавьте `size=512M` в fstab. |

## Лучшие практики

### 1. Производительность и тюнинг

- **Настраивайте writeback под нагрузку:** Для СУБД используйте `vm.dirty_background_ratio=3` и `vm.dirty_ratio=10`. Для бэкапов — увеличенные значения.
- **Используйте `lazytime` вместо `noatime`** для баланса между скоростью и корректностью временных меток.
- **Для NVMe отключайте планировщик I/O:** `none` в `/sys/block/nvme*/queue/scheduler`.
- **Для HDD используйте `bfq`** для справедливого распределения пропускной способности.

### 2. Мониторинг и observability

- **Следите за `df -h` и `df -i`** в мониторинге. Исчерпание inode часто игнорируется.
- **Логируйте `dmesg`** на предмет ошибок ФС (`EXT4-fs error`).
- **Используйте `iostat -xz 1`** для обнаружения high await и %util на дисках.

### 3. Восстановление и откат

- **Перед `fsck` всегда делайте бэкап суперблока:** `sudo dd if=/dev/sda1 of=superblock_backup.bin bs=1M count=1`.
- **Используйте `tune2fs -l`** для проверки состояния суперблока перед действиями.
- **Для failing-дисков монтируйте в read-only:** `mount -o remount,ro /mountpoint` для минимизации повреждений.

### 4. Безопасность

- **Никогда не отключайте journaling (`-O ^has_journal`) на production-дисках** без понимания рисков.
- **Используйте `barrier=1`** (по умолчанию) для защиты от потери данных при сбое питания.
- **Ограничивайте размер tmpfs** (`size=`) в `/etc/fstab` для предотвращения заполнения RAM.
