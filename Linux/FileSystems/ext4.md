# ext4 (Fourth Extended Filesystem)

## Определения

**ext4** — журналируемая файловая система, являющаяся четвёртой версией в семействе ext (ext2 → ext3 → ext4). Стандартная ФС для дистрибутивов на базе Debian/Ubuntu, а также广泛 используется в嵌入式 системах и на корневых разделах.

**Ключевые понятия:**

- **Extent** — непрерывный диапазон физических блоков, выделяемых файлу. В отличие от блочного маппинга ext3, extents значительно снижают фрагментацию и ускоряют работу с большими файлами.
- **Delayed allocation (delayed alloc)** — механизм отложенного выделения блоков. ФС не выделяет физическое место при каждом `write()`, а накапливает данные в Page Cache и выделяет блоки перед фактическим сбросом на диск (writeback). Уменьшает фрагментацию, но увеличивает риск потери данных при аварийном отключении питания.
- **JBD2 (Journaling Block Device 2)** — подсистема ядра, реализующая журналирование для ext4. Обеспечивает атомарность транзакций через запись намерений в журнал перед применением изменений к основным структурам ФС.
- **Meta_bg (Metablock Group)** — распределённая структура метаданных, позволяющая ФС расти без централизованного DEScriptor Table.
- **Bigalloc** — опция, увеличивающая размер кластера (аллокационной единицы) с 4 КБ до мегабайт. Уменьшает overhead метаданных, но не рекомендуется для ФС с массой мелких файлов.
- **Inline data** — хранение данных размером менее ~60 байт непосредственно в inode, без выделения блоков на диске.
- **Project quotas (prjquota)** — квоты на уровне иерархии каталогов (поддеревьев), независимо от владельцев. Поддерживаются с ядра 4.4.
- **NLink上限** — расширение лимита количества hardlink для каталогов с 32000 до 65000 (опция `dir_nlink`).

## Основные концепции

### Архитектура

ext4 построена поверх абстракции VFS и использует следующие структуры:

```
┌─────────────────────────────────────────────┐
│  Приложение (open/read/write/close)          │
├─────────────────────────────────────────────┤
│  VFS (Virtual File System)                   │
├─────────────────────────────────────────────┤
│  ext4 драйвер (ext4_file_write_inode...)    │
├─────────────────────────────────────────────┤
│  JBD2 (журнал метаданных + данных)           │
├─────────────────────────────────────────────┤
│  Блочный слой (I/O scheduler, buffer cache) │
├─────────────────────────────────────────────┤
│  Физическое хранилище                        │
└─────────────────────────────────────────────┘
```

**Inode:** В ext4 количество inode фиксируется при создании ФС (`mkfs.ext4 -i <bytes-per-inode>` или `-N <count>`). Исчерпание inode блокирует создание новых файлов даже при наличии свободного места. Проверка: `df -i`.

**Extent tree:** Каждый inode содержит указатель на корневой extent. Для крупных файлов с фрагментированным распределением extents формируется B-дерево extents, хранящееся во вспомогательных блоках (extent tree depth > 0).

**Block groups:** Диск делится на block groups (обычно по 128 MiB с block size 4 КБ). Каждая group содержит копию суперблока, block bitmap, inode bitmap и inode table. Это обеспечивает локализацию данных и снижает seeks.

### Режимы журналирования

ext4 поддерживает три режима записи данных:

| Режим | Описание | Надёжность | Производительность |
| :--- | :--- | :--- | :--- |
| `data=journal` | Данные и метаданные пишутся в журнал | Максимальная | Низкая (двойная запись) |
| `data=ordered` (по умолчанию) | Только метаданные в журнале; данные записываются до фиксации метаданных | Высокая | Средняя |
| `data=writeback` | Только метаданные в журнале; порядок данных не гарантирован | Средняя | Высокая |

**Практические рекомендации:**
- `data=ordered` — для большинства production-сценариев (БД, файловые серверы).
- `data=writeback` — только с гарантированным питанием (ИБП, BBU контроллера). Допустимо для high-performance workloads (NVMe + ИБП).
- `data=journal` — максимальная безопасность, но двойная запись снижает throughput. Используется редко.

### Опции монтирования

| Опция | Описание | Рекомендация |
| :--- | :--- | :--- |
| `noatime` | Отключение обновления времени доступа | Обязательно для production |
| `lazytime` | Отложенный сброс временных меток в память | Альтернатива `noatime` |
| `nodiratime` | Отключение обновления времени доступа для каталогов | Дополнение к `noatime` |
| `barrier=1` | Включение барьеров записи (по умолчанию) | **Не отключать** без BBU |
| `commit=60` | Интервал фиксации транзакций (секунды, по умолчанию 5) | Увеличить для scratch-дисков |
| `errors=remount-ro` | При ошибке ФС → read-only (по умолчанию) | Стандарт для production |
| `discard` | Онлайн TRIM | Для SSD с низкой нагрузкой |
| `nobarrier` | Отключение барьеров | **Только** с BBU/ИБП |

```bash
# Пример fstab для production ext4 на SSD
UUID=a1b2c3d4-... /data ext4 defaults,noatime,nodiratime,errors=remount-ro 0 2

# Ext4 с writeback для БД на NVMe + ИБП
UUID=... /var/lib/postgresql ext4 defaults,noatime,data=writeback,commit=60 0 2
```

### Мониторинг состояния

```bash
# Просмотр параметров ФС
sudo tune2fs -l /dev/sda1 | grep -E 'Filesystem features|Block size|Inode count'

# Проверка количества свободных inode
df -i /data
# → Filesystem     Inodes  IUsed   IFree IUse% Mounted on
# → /dev/sda1      65536   1234   64302    2% /data

# Проверка времени последующего fsck
sudo tune2fs -l /dev/sda1 | grep -E 'Mount count|Check interval'
# → Mount count:          23
# → Maximum mount count:  30
# → Check interval:       15552000 (6 months)
```

## Практические сценарии

### Создание и настройка

```bash
# Форматирование раздела
sudo mkfs.ext4 -L DATA_DRIVE -i 4096 /dev/sdb1
# -i 4096: один inode на 4096 байт (хорошо для смешанных нагрузок)

# Для сервера с массой мелких файлов ( больше inode )
sudo mkfs.ext4 -L LOGS -i 2048 /dev/sdb1

# Для сервера с крупными файлами (меньше inode, больше эффективности)
sudo mkfs.ext4 -L MEDIA -i 65536 /dev/sdb1

# Монтирование
sudo mount -o noatime,nodiratime /dev/sdb1 /data
```

### Включение внутренних квот

```bash
# Включение опций usrquota и grpquota в суперблоке
sudo tune2fs -O quota /dev/sdb1

# Добавление в fstab
UUID=... /data ext4 defaults,usrquota,grpquota 0 2

# Установка лимита для пользователя
sudo setquota -u user1 1048576 1153434 0 0 /data

# Проверка
sudo repquota -aus /data
```

### Online resize

```bash
# Ext4 поддерживает онлайн-расширение (но не уменьшение)
sudo resize2fs /dev/vg_data/lv_data

# С указанием нового размера
sudo resize2fs /dev/vg_data/lv_data 200G
```

### Работа с superblock

```bash
# Бэкап суперблока (перед любыми изменениями!)
sudo dd if=/dev/sda1 of=superblock_backup.bin bs=1M count=1

# Восстановление с резервного суперблока
sudo e2fsck -b 32768 /dev/sda1
# 32768 — стандартное расположение первого резервного суперблока

# Просмотр всех резервных суперблоков
sudo mke2fs -n /dev/sda1 | grep "Backup superblock"
```

### De-frag (офлайн дефрагментация)

```bash
# ext4 не имеет online-дефрагментации для пользовательских файлов
# Используйте e4defrag для офлайн-дефрагментации

# Проверка фрагментации
sudo e4defrag -c /data
# → "fragmentation score" 0 = нет фрагментации, 100 = максимальная

# Дефрагментация (требует отмонтированной ФС или root)
sudo e4defrag /data
```

### Диагностика ошибок

```bash
# Проверка ФС (требует отмонтирования)
sudo umount /dev/sdb1
sudo e2fsck -f /dev/sdb1

# Автоматическое исправление
sudo e2fsck -y /dev/sdb1

# Проверка только (read-only)
sudo e2fsck -n /dev/sdb1

# Мониторинг ошибок ext4 в dmesg
sudo dmesg -T | grep -i "ext4"
# → EXT4-fs error (device sdb1): ext4_journal_check_start_recovery:2234: ...
# → EXT4-fs (sdb1): remounting filesystem read-only
```

### Исправление read-only перехода

```bash
# 1. Проверить причину read-only
sudo blockdev --getro /dev/sdb1
# → 1 (read-only)

# 2. Проверить dmesg на ошибки
sudo dmesg -T | grep -iE "ext4.*error|I/O error|abort"

# 3. Если ошибок нет — попробовать remount
sudo mount -o remount,rw /data

# 4. Если ФС в read-only из-за ошибок journals
sudo umount /dev/sdb1
sudo e2fsck -f /dev/sdb1
sudo mount /dev/sdb1 /data
```

### Автоматизация обслуживания

```bash
# Проверка intervalount count для автоматического fsck
sudo tune2fs -l /dev/sda1 | grep -E 'Mount count|Maximum mount count'
# → Mount count:          23
# → Maximum mount count:  30
# → Через 7 перезагрузок будет запущен автоматический fsck

# Принудительный fsck при следующей загрузке
sudo touch /forcefsck

# Или через tune2fs: установить счётчик в 0
sudo tune2fs -C 0 /dev/sda1
```

## Сравнение с другими ФС

| Критерий | ext4 | XFS | Btrfs |
| :--- | :--- | :--- | :--- |
| **Уменьшение (shrink)** | Да (офлайн) | Нет | Да |
| **Online fsck** | Нет | Да | Да |
| **Reflinks** | Нет | Да (ядро 4.9+) | Да (CoW) |
| **Снапшоты** | Нет (только LVM) | Нет (только LVM) | Да (subvolumes) |
| **Компрессия** | Нет | Нет | Да (Zstd, LZO) |
| **Inode** | Фиксированные | Динамические | Динамические |
| **Макс. размер ФС** | 1 EiB | 8 EiB | 16 EiB |
| **Макс. размер файла** | 16 TiB | 8 EiB | 16 EiB |
| **Online resize** | Да | Да (только расширение) | Да |

## Ограничения и подводные камни

1. **Исчерпание inode:** Критична проблема при массе мелких файлов (кэши, логи, PHP-сессии). Проверяйте `df -i` регулярно.
2. **Нет online-дефрагментации для пользовательских файлов:** `e4defrag` требует root-доступа и может быть небезопасен на работающей ФС.
3. **Нет reflinks:** Копирование файлов всегда физическое. Для быстрых клонов используйте XFS или Btrfs.
4. **Нет встроенного RAID/снапшотов:** Зависимость от LVM или mdadm.
5. **data=writeback без BBU:** Риск потери данных при сбое питания. Используйте только с ИБП.
