# Управление и диагностика сетей в Linux

В Linux интерфейс — это программная абстракция, которая управляется ядром и может соответствовать как физическому, так и виртуальному устройству.

*   **Физические интерфейсы (`eth0`, `enp3s0`, `wlan0`)
    *   Это интерфейсы, которые напрямую связаны с аппаратным обеспечением — вашей сетевой картой (NIC) или Wi-Fi адаптером.
    *   Именно они отправляют и принимают данные по медному кабелю или через радиоволны.
    *   У каждого такого интерфейса есть уникальный физический адрес (MAC-адрес).

*   **Виртуальные интерфейсы**
    *   Они не привязаны к реальному "железу" и создаются программно для специальных задач.
    *   **`veth` (Virtual Ethernet):** Это "виртуальный патч-корд". Интерфейсы `veth` всегда создаются парами. Что отправляется в один конец пары, выходит из другого. Это ключевая технология для контейнеризации (например, в Docker), позволяющая соединить сетевое пространство контейнера с хост-системой.
    *   **`bridge` (мост, `br0`):** Это "виртуальный свитч". Он позволяет объединять несколько других интерфейсов (как физических, так и виртуальных) в единую сеть, чтобы они могли общаться друг с другом. Широко используется в виртуализации и Docker.
    *   **`tun`/`tap`:** Используются для создания туннелей, чаще всего для VPN. Они позволяют программам пользовательского пространства (user-space) отправлять и получать сетевые пакеты.

## Управление сетевыми интерфейсами (`ip`)

-   **Посмотреть сетевые интерфейсы:**
    ```bash
    ip link
    ```

-   **Посмотреть все IP-адреса и состояние интерфейсов:**
    ```bash
    ip a
    # или в кратком виде (brief)
    ip -br a
    # или
    ip addr show
    ```

-   **Посмотреть имя хоста и его IP-адреса:**
    ```bash
    # Показывает только имя хоста
    hostname

    # Показывает IP-адрес, ассоциированный с именем хоста (может быть loopback 127.0.0.1)
    hostname -i

    # Показывает все реальные IP-адреса машины, назначенные на интерфейсы
    hostname -I
    ```

-   **Включить или выключить интерфейс:**
    ```bash
    # Выключить
    sudo ip link set dev eth0 down
    # Включить
    sudo ip link set dev eth0 up
    ```

-   **Добавить или удалить IP-адрес:**
    ```bash
    # Добавить
    sudo ip addr add 192.168.1.100/24 dev eth0
    # Удалить
    sudo ip addr del 192.168.1.100/24 dev eth0
    ```

-   **Посмотреть таблицу маршрутизации:**
    ```bash
    ip r
    # или
    ip route show
    ```

-   **Узнать, как ядро построит маршрут до конкретного IP:**
    Эта команда — мощный инструмент отладки. Она спрашивает ядро, какой маршрут будет использован для достижения указанного IP-адреса.
    ```bash
    ip route get 192.168.98.111
    ```
    *Вывод `192.168.98.111 dev enp4s0 src 192.168.98.102 ...` показывает, что для достижения цели будет использован интерфейс `enp4s0` с исходящим IP `192.168.98.102`.*

-   **Посмотреть статистику и ошибки интерфейсов:**
    ```bash
    # Ключ -s (statistics) добавляет подробную информацию о пакетах
    ip -s link
    ```
    *Обратите внимание на счетчики `errors` и `dropped`. Их рост указывает на проблемы с сетью или нехватку ресурсов ОС.*

## Постоянная настройка IP-адресов

Настройки, сделанные с помощью команды `ip`, являются временными и будут сброшены после перезагрузки. Для постоянной конфигурации необходимо редактировать системные файлы.

### Настройка в Debian/Ubuntu

Конфигурация сети определяется в файле `/etc/network/interfaces`. Этот файл хранит описания сетевых интерфейсов, маршрутов и шлюзов.

**Пример статической конфигурации:**

Откройте файл `/etc/network/interfaces` и найдите или добавьте следующие строки для вашего основного интерфейса (например, `eth0`):

```
# Основной сетевой интерфейс
auto eth0
iface eth0 inet static
    address 10.10.10.10       # Основной IPv4-адрес
    netmask 255.255.255.0     # Маска подсети
    gateway 10.10.10.1        # Шлюз по умолчанию
```

*   **`pointopoint`**: Этот параметр используется в сетях с технологией VPU, где нет общего broadcast-домена (адреса настраиваются с маской `/32`). Он явно задает маршрут до шлюза. Пример: `pointopoint 10.10.0.1`.

**Добавление дополнительных IP-адресов (алиасов):**

Можно назначить несколько IP-адресов на один физический интерфейс, используя псевдонимы (`eth0:0`, `eth0:1` и т.д.).

```
# Дополнительный IP-адрес
auto eth0:1
iface eth0:1 inet static
    address 10.10.10.11
    netmask 255.255.255.255
```

**Применение изменений:**

Для применения настроек перезапустите сетевую службу:
```bash
sudo systemctl restart networking
```
В некоторых случаях, например, при смене основного IP-адреса, может потребоваться полная перезагрузка сервера.

### Настройка в CentOS/RHEL

Конфигурационные файлы для каждого интерфейса находятся в `/etc/sysconfig/network-scripts/`. Например, для `eth0` это будет `ifcfg-eth0`.

**Пример статической конфигурации:**

```
DEVICE="eth0"          # Имя интерфейса
ONBOOT="yes"           # Запускать при старте системы
TYPE="Ethernet"        # Тип подключения
IPADDR="10.10.10.10"     # Основной IPv4-адрес
NETMASK="255.255.255.0"  # Маска подсети (или PREFIX=24)
GATEWAY="10.10.10.1"     # Шлюз по умолчанию
```

*   **Для сетей VPU**: Если используется VPU, добавляется параметр `SCOPE="peer 10.0.0.1"`. Также может потребоваться создание файла `/etc/sysconfig/network-scripts/route-eth0` с прямым маршрутом до шлюза.

**Применение изменений:**

```bash
sudo systemctl restart network.service
```

### Настройка в современных Ubuntu с помощью Netplan

В современных версиях Ubuntu (17.10+), для управления сетью используется `netplan`. Это утилита, которая использует декларативные YAML-файлы для описания сетевой конфигурации, а затем генерирует на их основе настройки для `systemd-networkd` (по умолчанию для серверов) или `NetworkManager` (по умолчанию для десктопов).

Конфигурационные файлы находятся в `/etc/netplan/`.

**Пример: Агрегация каналов (Bonding)**

`netplan` позволяет легко настраивать сложные конфигурации, такие как агрегация нескольких сетевых интерфейсов в один логический (`bond`).

```yaml
# /etc/netplan/server.yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    enp1s0f0: {}
    enp1s0f1: {}
  bonds:
    bond1:
      interfaces: [enp1s0f0, enp1s0f1]
      parameters:
        mode: 802.3ad
        mii-monitor-interval: 1
```

*   **`renderer: networkd`**: Указывает, что `netplan` должен генерировать конфигурацию для `systemd-networkd`.
*   **`ethernets`**: Перечисляет физические интерфейсы, которые будут использоваться.
*   **`bonds`**: Описывает логический интерфейс `bond1`, который объединяет `enp1s0f0` и `enp1s0f1`.
*   **`parameters`**: Задает параметры режима агрегации, в данном случае `802.3ad` (LACP).

**Применение конфигурации:**

1.  **`sudo netplan generate`**: Генерирует конфигурацию для рендерера, но не применяет ее. Полезно для проверки синтаксиса.
2.  **`sudo netplan apply`**: Применяет новую конфигурацию.

**Проверка состояния бонда:**

После применения конфигурации, можно проверить состояние агрегированного интерфейса, прочитав специальный файл в `/proc`.

```bash
cat /proc/net/bonding/bond1
```
В выводе будет подробная информация о режиме агрегации, активных портах и состоянии LACP, включая MAC-адрес партнера.

**Проверка состояния бонда:**

После применения конфигурации, можно проверить состояние агрегированного интерфейса, прочитав специальный файл в `/proc`.

```bash
cat /proc/net/bonding/bond1
```
В выводе будет подробная информация о режиме агрегации, активных портах и состоянии LACP, включая MAC-адрес партнера.

### Проверка доступности хоста (`ping`)

`ping` отправляет ICMP-запросы для проверки доступности хоста и измерения задержки.

-   **Анализ ответов `ping`:**
    -   **`Destination Host Unreachable`**: Ваш локальный маршрутизатор не знает, как добраться до цели. Проблема в вашей сети (нет маршрута, кабель отключен).
    -   **`Request Timed Out`**: Ответ не пришел вовремя. Причины: файрвол, перегрузка сети, хост выключен.
    -   **`TTL expired in transit`**: Пакет превысил лимит "прыжков". Чаще всего указывает на **петлю маршрутизации**.

-   **Тестирование MTU:**
    Отправка пакета, который не должен фрагментироваться. Помогает выявить проблемы с MTU на пути.
    ```bash
    # 1472 байта данных + 28 байт заголовков = 1500 байт
    ping -c 4 -s 1472 -M do 8.8.8.8
    ```

-   **Диагностика DNS и маршрутизации:**
    Простой тест для быстрой локализации проблемы.
    ```bash
    # 1. Проверяем доступность внешнего ресурса по имени
    ping -c 2 ya.ru

    # 2. Проверяем доступность внутреннего ресурса по IP
    ping -c 2 <ip-вашего-внутреннего-сервера>
    ```
    *Если первый `ping` не работает, а второй работает, проблема, скорее всего, в DNS или в маршрутизации во внешнюю сеть.*

### Диагностика системного резолвера (`resolvectl`)

В современных Linux-системах, использующих `systemd`, за разрешение DNS-имен часто отвечает служба `systemd-resolved`. Эта служба выступает в роли локального кэширующего DNS-резолвера.

При этом файл `/etc/resolv.conf` часто является "заглушкой" (stub), указывающей на локальный адрес `127.0.0.53`. Реальные DNS-серверы управляются `systemd-resolved`.

Утилита `resolvectl` — это основной инструмент для взаимодействия с этой службой.

*   **Проверить общий статус и текущие серверы:**
    Команда `resolvectl status` (или просто `resolvectl`) показывает подробную информацию о глобальных настройках и настройках для каждого сетевого интерфейса.

    ```bash
    $ resolvectl
    Global
         Protocols: -LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
      resolv.conf mode: stub
    Link 2 (ens3)
        Current Scopes: DNS
             Protocols: +DefaultRoute +LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
    Current DNS Server: 1.1.1.1
           DNS Servers: 1.1.1.1 8.8.8.8
            DNS Domain: linkmeup.ru
    ```
    Из вывода видно, какие DNS-серверы (`1.1.1.1`, `8.8.8.8`) используются для интерфейса `ens3`.

*   **Узнать, как система разрешит имя:**
    Команда `query` показывает, какой IP-адрес вернет именно системный резолвер, с учетом всех правил.

    ```bash

    resolvectl query example.com
    ```

-   **Порядок разрешения имен (`/etc/nsswitch.conf`):**
    Этот файл определяет, в каком порядке система будет пытаться разрешить имя хоста (например, сначала посмотреть в `/etc/hosts`, а потом идти в DNS). Строка `hosts:` отвечает за этот порядок.
    ```
    # Пример: сначала локальные файлы, потом DNS
    hosts:          files dns
    ```

## Анализ соединений и портов

-   **Показать все слушающие TCP и UDP порты и процессы, которые их используют:**
    ```bash
    sudo ss -tulpan
    ```
    -   `-t`: TCP, `-u`: UDP, `-l`: слушающие сокеты, `-p`: процессы, `-n`: числовой вывод, `-a`: все сокеты.

-   **Узнать, какой процесс занял определённый порт:**
    ```bash
    sudo ss -lntp 'sport = :443'
    ```

### Сканирование портов (`nmap`)

-   **Быстрое сканирование популярных портов на хосте:**
    ```bash
    nmap scanme.nmap.org
    ```

-   **Проверить, открыт ли конкретный порт:**
    ```bash
    nmap -p 80,443 192.168.1.1
    ```

-   **Определить версии служб, работающих на портах:**
    ```bash
    sudo nmap -sV 192.168.1.1
    ```

## Маршрутизация и анализ пути

`traceroute` и `mtr` — это ключевые утилиты для анализа маршрута, по которому сетевые пакеты следуют до хоста назначения.

**Ключевые особенности:**
*   **Показывают маршрут до цели (но только в одну сторону):** Важно помнить, что обратный маршрут может быть другим (асимметричная маршрутизация).
*   **Локализация проблем:** Помогают примерно понять, на каком узле (хопе) начинаются потери пакетов или растет задержка.
*   **Тестирование файрволов:** С помощью ключей можно менять протокол (ICMP, TCP, UDP) и порт, чтобы проверить, не блокирует ли файрвол определенные виды трафика.

### `traceroute`

Показывает путь, последовательно отправляя пакеты с увеличивающимся TTL (Time To Live).

```bash
# Стандартная трассировка с использованием ICMP (или UDP в некоторых системах)
traceroute example.com
```
*   Если на узле отображаются `* * *`, он может блокировать ICMP. Попробуйте трассировку через TCP, указав порт (например, 80 для веб-сервера).
    ```bash
    # Трассировка с использованием TCP SYN пакетов на порт 80
    sudo traceroute -T -p 80 example.com
    ```

### `mtr` (My Traceroute)

`mtr` — это более продвинутый инструмент, который объединяет функциональность `ping` и `traceroute`. Он постоянно отправляет пакеты и в реальном времени показывает статистику по каждому узлу на пути: потери (`Loss%`), количество отправленных пакетов (`Snt`), последнюю задержку (`Last`), среднюю (`Avg`), лучшую (`Best`) и худшую (`Wrst`).

Это делает `mtr` гораздо более наглядным для выявления нестабильных узлов.

```bash
# Запустить mtr в текстовом режиме
mtr example.com

# Запустить mtr с TCP-трассировкой
sudo mtr --tcp --port 80 example.com
```

## Анализ сетевого трафика (`tcpdump`)

-   **Прослушивать трафик на всех интерфейсах на порту 443:**
    ```bash
    sudo tcpdump -i any port 443 -nn
    ```
    -   `-i any`: Прослушивать на всех интерфейсах.
    -   `-nn`: Не преобразовывать IP-адреса и номера портов в имена (например, показывать `8.8.8.8` вместо `dns.google`).

-   **Записать весь трафик в файл для последующего анализа:**
    Эта команда захватывает полные пакеты и сохраняет их в файл `.pcap`, который затем можно открыть в программах вроде Wireshark.
    ```bash
    sudo tcpdump -n -A -s0 -w file.pcap
    ```
    -   `-n`: Не преобразовывать IP-адреса в имена.
    -   `-A`: Отображать содержимое каждого пакета в ASCII. Полезно для быстрого просмотра текстовых протоколов (HTTP, SMTP), но может создавать много "шума".
    -   `-s0` (`snaplen` 0): Захватывать пакеты целиком. По умолчанию `tcpdump` обрезает пакеты для экономии места, что может быть нежелательно при глубоком анализе.
    -   `-w file.pcap`: Записать сырые данные пакетов в файл `file.pcap`.
    -   **Примечание:** Если захваченные данные сжаты (например, gzip), Wireshark часто может их распознать и декодировать "на лету".

### `iperf3` (Пропускная способность)

`iperf3` — утилита для измерения пропускной способности сети между двумя хостами.

-   **На хосте-сервере:**
    ```bash
    iperf3 -s
    ```

-   **На хосте-клиенте:**
    ```bash
    # Простое измерение (клиент -> сервер)
    iperf3 -c <IP_адрес_сервера>

    # Измерение в обратную сторону (сервер -> клиент)
    iperf3 -c <IP_адрес_сервера> -R
    
    # Тест с несколькими потоками для насыщения канала
    # -t 60: время теста 60 секунд
    # -P 16: 16 параллельных потоков
    iperf3 -c <IP_адрес_сервера> -t 60 -P 16
    ```

### `ping` (Задержка и потери)

-   **Проверка средней задержки и потерь:**
    ```bash
    ping -c 20 example.com
    ```
    *Смотрите на `avg` в статистике и процент `packet loss`.*

### `curl` (Скорость загрузки)

-   **Измерение времени до начала передачи данных:**
    ```bash
    curl -o /dev/null -s -w "Время до первого байта: %{time_starttransfer}\n" https://example.com/file.zip
    ```
    *Чем меньше `time_starttransfer`, тем быстрее сервер отвечает, что косвенно говорит о низкой перегрузке.*

### `nload` / `bmon` (Визуализация трафика)

```bash
sudo apt install nload bmon
nload
# или
bmon
```
*Полезно запускать во время тестов `iperf3` для визуального контроля.*

Утилита для мониторинга сетевой активности в реальном времени. Показывает использование сетевого интерфейса процессами.

## Файрвол: nftables и iptables

Для настройки файрвола в Linux исторически использовалась утилита `iptables`. Однако в современных дистрибутивах ей на смену пришла `nftables`, которая предлагает более гибкий синтаксис и лучшую производительность.

-   **`nftables`**: Является современным стандартом. Подробное руководство находится в файле [nftables.md](./nftables.md).
-   **`iptables`**: Классический инструмент, который все еще широко используется. Для обратной совместимости часто работает поверх `nftables`. Подробное руководство по `iptables` находится в файле [../Security/iptables.md](../Security/iptables.md).

### Взаимодействие с Docker

Ключевой момент: Docker активно управляет правилами файрвола для обеспечения сетевой изоляции и проброса портов.

-   **Трафик к контейнерам идёт через цепочку `FORWARD`**, а не `INPUT`.
-   Если вы используете политику `DROP` для `FORWARD`, вам необходимо явно разрешать трафик для Docker в специальной цепочке `DOCKER-USER`.

Подробности о взаимодействии Docker и файрвола описаны в заметке [Docker и сеть](../Docker/docker_network.md).

### Проблема `TIME_WAIT`

Когда TCP-соединение закрывается, оно на некоторое время (обычно 60 секунд) переходит в состояние `TIME_WAIT` для гарантии доставки всех пакетов. На высоконагруженных серверах (например, прокси) большое количество таких сокетов может исчерпать лимит доступных портов.

-   **Диагностика:**
    ```bash
    ss -tan 'state time-wait' | wc -l
    ```

-   **Решение (настройка ядра):**
    Для постоянного применения добавьте эти строки в `/etc/sysctl.conf` и выполните `sudo sysctl -p`.
    ```ini
    # Разрешить повторное использование сокетов в состоянии TIME_WAIT для новых соединений (безопасно)
    net.ipv4.tcp_tw_reuse=1

    # Уменьшить время ожидания в TIME_WAIT (по умолчанию 60)
    net.ipv4.tcp_fin_timeout=30
    ```

### Оптимизация TCP с помощью BBR

**BBR (Bottleneck Bandwidth and Round-trip time)** — это современный алгоритм управления перегрузкой от Google.BBR моделирует реальную пропускную способность сети и задержку. Это позволяет достичь значительно более высокой производительности и низкой задержки, особенно в сетях с потерями или высокой задержкой (Long-Fat Networks).

1. Разведка: BBR периодически ненадолго увеличивает скорость отправки данных, чтобы проверить, не выросла ли пропускная способность канала (вдруг «трубу» расширили?).
2. Дренаж: После разведки он наоборот, немного снижает скорость, чтобы «осушить» возможные очереди из пакетов, которые могли скопиться в буферах маршрутизаторов, уменьшая задержку.
3. Стабильная работа: Основное время BBR работает на рассчитанной оптимальной скорости, которая обеспечивает максимальную пропускную способность при минимальной задержке

**Проверка версии ядра**

BBR требует ядро Linux версии `4.9` или выше.
```bash
uname -r
```

**Проверка доступных алгоритмов**

Убедитесь, что `bbr` есть в списке доступных.
```bash
sysctl net.ipv4.tcp_available_congestion_control
```

**Загрузка модуля (если необходимо)**

Обычно модуль уже загружен. Если нет, загрузите его и добавьте в автозагрузку.
```bash
# Загрузить модуль
sudo modprobe tcp_bbr

# Добавить в автозагрузку при старте системы
echo 'tcp_bbr' | sudo tee /etc/modules-load.d/bbr.conf
```

**Настройка `sysctl`**

Добавьте следующие строки в `/etc/sysctl.conf` для активации BBR.
```ini
# /etc/sysctl.conf

# Включить Fair Queuing (обязательно для BBR)
net.core.default_qdisc = fq

# Установить BBR как алгоритм контроля перегрузки
net.ipv4.tcp_congestion_control = bbr
```

**Применение и проверка**

Примените настройки и убедитесь, что BBR активен.
```bash
# Применить настройки
sudo sysctl -p

# Проверить, что BBR используется
sysctl net.ipv4.tcp_congestion_control
# Ожидаемый вывод: net.ipv4.tcp_congestion_control = bbr

# Убедиться, что модуль загружен
lsmod | grep bbr
```

-   **BBRv2:** Более новая, экспериментальная версия, нацеленная на улучшение справедливости при работе с потоками CUBIC. Требует кастомного ядра.
-   **Совместимость:** BBR может быть агрессивен по отношению к хостам с CUBIC. Также, старые прокси или VPN-шлюзы могут некорректно интерпретировать его поведение, хотя сегодня это встречается редко.

### Что такое сокет?

**Сокет** — это программный интерфейс (представленный как файл в ОС) для обмена данными между процессами. Эти процессы могут выполняться как на одной машине, так и в сети.

1.  **Сетевые сокеты (AF_INET, AF_INET6):**
    *   Используются для коммуникации по сети (например, через интернет).
    *   Они привязаны к IP-адресу и порту.
    *   Пример: веб-сервер, который "слушает" порт 80 для входящих HTTP-запросов.

2.  **Unix-сокеты (AF_UNIX):**
    *   Используются для обмена данными между процессами **на одной и той же машине**.
    *   Они не используют сетевой стек (IP-адреса и порты), а вместо этого создают специальный файл в файловой системе.
    *   **Преимущество:** Работают значительно быстрее сетевых сокетов, так как данные не проходят через сетевой интерфейс. Это делает их идеальными для локального IPC (Inter-Process Communication).

**Пример: Docker Socket (`/var/run/docker.sock`)**
Это Unix-сокет, который демон Docker (`dockerd`) использует как API. Клиент `docker` подключается к этому файлу для отправки команд. Доступ к этому файлу равносилен root-доступу к хост-системе.

## Постоянные имена сетевых интерфейсов

Иногда сетевой интерфейс «пропадает» или переименовывается после перезагрузки (например, `ens3` в `enp0s3`), особенно на серверах, использующих `systemd-networkd`. Это может нарушить работу файрвола, скриптов и других сетевых конфигураций.

Решение — зафиксировать имя интерфейса с помощью правила `systemd.link`.

1.  **Узнайте MAC-адрес нужного интерфейса:**
    ```bash
    ip link show
    ```
    Вы увидите что-то вроде `link/ether 52:54:00:ab:cd:ef`. Это и есть MAC-адрес.

2.  **Создайте файл правила `.link`:**
    Создайте файл `/etc/systemd/network/10-persistent.link` (имя может быть любым, но должно начинаться с числа и заканчиваться на `.link`).
    ```ini
    # /etc/systemd/network/10-persistent.link
    [Match]
    MACAddress=52:54:00:ab:cd:ef

    [Link]
    Name=lan0
    ```
    - `[Match]`: Условие, по которому `systemd-udevd` найдет устройство. `MACAddress` — самый надежный способ.
    - `[Link]`: Действие, которое нужно применить. `Name=lan0` задает новое, постоянное имя `lan0`.

3.  **Перезапустите службы:**
    Чтобы применить изменения, перезапустите службы, отвечающие за управление устройствами и сетью.
    ```bash
    sudo systemctl restart systemd-udevd
    sudo systemctl restart systemd-networkd
    ```

Теперь ваш сетевой интерфейс всегда будет называться `lan0`, независимо от порядка загрузки драйверов или изменений в оборудовании.

**Совет:** Вместо `MACAddress` можно использовать `Driver=` или `Path=`, если у вас несколько одинаковых сетевых карт и нужно привязаться к физическому порту.
