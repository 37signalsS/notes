# Общие вопросы настройки межсетевых экранов в Linux

## Определения

В данном файле собраны практические аспекты настройки сетевой безопасности, применимые к различным инструментам управления (iptables, nftables, firewalld, ufw). Основной упор сделан на системные механизмы обеспечения персистентности, архитектурные различия бэкендов и взаимодействие с инфраструктурными компонентами (Docker).

**Технологический стек (2026):**
- **[nftables](./nftables/architecture_and_concepts.md):** современный стандарт ядра Linux, заменяющий семейство iptables. Использует регистровую виртуальную машину и атомарные транзакции через Netlink.
- **eBPF / XDP:** программируемый уровень обработки пакетов. Позволяет выполнять фильтрацию на уровне драйвера сетевой карты (XDP) до передачи пакета в стек ядра, что критично для защиты от DDoS и высоконагруженных сервисов.
- **iptables-nft:** уровень совместимости, позволяющий использовать старый синтаксис iptables, транслируя его в байт-код nftables.

### Бэкенды iptables

| Бэкенд | Путь | Характеристики |
| :--- | :--- | :--- |
| `iptables-legacy` | `/sbin/iptables-legacy` | Работает напрямую с Netfilter; несовместим с nftables. |
| `iptables-nft` | `/sbin/iptables-nft` | Транслирует в байт-код nftables; правила видны в `nft list ruleset`. |
| `nft` (native) | `/sbin/nft` | Нативный инструмент; атомарные транзакции через Netlink. |

**Определение активного бэкенда:**
```bash
update-alternatives --display iptables
# → iptables - auto mode
# →   link best version is /usr/sbin/iptables-nft
# →   link currently points to /usr/sbin/iptables-nft
```

### Выражения conntrack и notrack

В nftables работа с отслеживанием соединений выполняется через выражения семейства `ct`:
- **`ct state`** — доступ к состоянию соединения (`established`, `related`, `new`, `invalid`).
- **`ct original saddr`** — исходный адрес до NAT.
- **`notrack`** — отключает отслеживание соединения в conntrack для конкретного пакета. Используется для снижения нагрузки на таблицу при обработке высоконагруженного трафика, не требующего stateful-анализа (например, DNS к кэширующему серверу).

### Flowtables

Flowtables (Fastpath) позволяют передавать пакеты установленных соединений напрямую между сетевыми интерфейсами, минуя классический стек Netfilter. Поддерживаются начиная с ядра 5.3+. Не работают с NAT и рядом выражений (`log`, `quota` внутри flowtable).

### ALG Helpers

Некоторые приложения (FTP, SIP, TFTP) требуют ALG (Application Layer Gateway) helpers в conntrack. В nftables управление осуществляется через `ct helper` и `ct helper set`. Неиспользуемые helpers следует удалять для уменьшения поверхности атаки.

### Сохранение правил между перезагрузками

Правила, примененные через командную строку, хранятся в оперативной памяти и сбрасываются при перезагрузке. Метод обеспечения персистентности зависит от инструмента и дистрибутива.

| Дистрибутив | Сценарий | Инструмент сохранения | Метод / Команда |
| :--- | :--- | :--- | :--- |
| **Ubuntu 24.04/26.04** | **ufw** (Default) | `ufw.service` | Автоматически (`/etc/ufw/*.rules`) |
| **Debian 12+ / Ubuntu** | **nftables** (Native) | `nftables.service` | `nft list ruleset > /etc/nftables.conf` |
| **RHEL 9+ / Alma / Rocky** | **firewalld** (Default) | `firewalld.service` | Использование флага `--permanent` |
| **Любой (Legacy)** | **iptables** | `iptables-persistent` | `netfilter-persistent save` |

#### Настройка персистентности nftables (Рекомендуемый метод)

В современных системах рекомендуется использовать нативный сервис `nftables`, который загружает правила атомарно.

```bash
# Сохранение текущей конфигурации в файл автозагрузки
sudo nft list ruleset | sudo tee /etc/nftables.conf

# Включение и запуск сервиса
sudo systemctl enable --now nftables
```

### Отслеживание состояний (Connection Tracking)

Современные файрволы являются **Stateful** — они отслеживают контекст соединений с помощью модуля `conntrack`. Это позволяет разрешать ответный трафик (ESTABLISHED, RELATED) одной строкой.

**Состояния соединений:**
- **NEW:** первый пакет соединения (например, SYN).
- **ESTABLISHED:** соединение установлено, идет двусторонний обмен.
- **RELATED:** ожидаемое новое соединение, связанное с существующим (например, данные FTP или ошибки ICMP).
- **INVALID:** пакет не связан ни с одной сессией (рекомендуется сбрасывать).

```bash
# Просмотр таблицы активных соединений
sudo conntrack -L

# Статистика conntrack (важно для диагностики переполнения таблицы)
sudo conntrack -S
```

### Семейства таблиц и хуки nftables

nftables использует семейства таблиц для обработки разных уровней:

| Семейство | Уровень OSI | Описание |
| :--- | :--- | :--- |
| **`inet`** | L3 (IPv4/v6) | Универсальное семейство для обработки обоих протоколов. Рекомендуется как стандарт. |
| **`ip`** / **`ip6`** | L3 | Специфичные таблицы для IPv4 или IPv6. |
| **`arp`** | L2/L3 | Фильтрация ARP-трафика. |
| **`bridge`** | L2 | Обработка кадров, проходящих через Linux Bridge. |
| **`netdev`** | L1/L2 | Работает на уровне сетевого драйвера. Поддерживает хуки `ingress` и `egress`. |

Приоритет хука определяет очередность обработки цепочек. Меньшее число означает более раннюю обработку.

### Архитектурные преимущества nftables

- **Атомарность транзакций:** обновление правил не приводит к разрывам. Все изменения применяются как единая операция через Netlink.
- **Регистровая виртуальная машина:** инструкции оперируют регистрами, что делает систему независимой от конкретных протоколов на уровне ядра.
- **Производительность O(1):** именованные наборы (Sets) и карты (Maps) позволяют искать за константное время.
- **Унификация семейств:** семейство `inet` позволяет писать общие правила для IPv4 и IPv6.

## Практические сценарии

### Выбор действия: DROP против REJECT

| Параметр | **DROP** | **REJECT** |
| :--- | :--- | :--- |
| **Поведение** | Пакет молча отбрасывается. | Пакет отклоняется с отправкой сообщения об ошибке. |
| **Скрытность** | Максимальная (Stealth mode). | Минимальная (сканеры видят хост). |
| **Отладка** | Сложная (клиент ждет таймаута). | Простая (клиент сразу получает отказ). |
| **Применение** | **Внешние интерфейсы (WAN).** | **Внутренние сети (LAN).** |

### Взаимодействие Docker и межсетевого экрана

Docker динамически манипулирует правилами Netfilter, что часто приводит к конфликтам.

**Ключевые особенности (2026):**
1. **Приоритет Docker:** Правила в цепочках Docker обрабатываются ДО цепочек `INPUT` высокоуровневых утилит (UFW/Firewalld). Опубликованный порт (`-p 80:80`) будет доступен, даже если UFW его блокирует.
2. **Использование nftables бэкенда:** В современных версиях Docker (28+) можно включить нативный бэкенд nftables в `daemon.json`, что улучшает совместимость.
3. **Цепочка DOCKER-USER:** Рекомендуемое место для пользовательских правил, влияющих на трафик контейнеров.

```bash
# Пример: Блокировка доступа к контейнерам со всех адресов, кроме доверенного (iptables)
sudo iptables -I DOCKER-USER -i eth0 ! -s 192.168.1.100 -j DROP
```

### Атомарное применение правил nftables

В nftables все изменения применяются атомарно через `nft -f <файл>`. Либо весь набор правил загружается успешно, либо ни одно изменение не вступает в силу. Это исключает «разрывные» состояния при делое.

```bash
# Проверка синтаксиса без применения
sudo nft -c -f /etc/nftables.conf
# → (нет вывода — ошибок нет)

# Применение конфигурации
sudo nft -f /etc/nftables.conf
```

### Валидация и откат

```bash
# Экспорт текущих правил для бэкапа
sudo nft list ruleset | sudo tee /root/nftables-backup-$(date +%F).nft

# Откат через восстановление из бэкапа
sudo nft flush ruleset
sudo nft -f /root/nftables-backup-$(date +%F).nft
```

### Диагностика и логирование

Для выявления проблем со связностью используйте логирование блокируемых пакетов.

```bash
# Добавление правила логирования в nftables (ограничьте частоту!)
nft add rule inet filter input limit rate 10/minute log prefix "DROP_EVENT: " drop

# Мониторинг логов
sudo journalctl -kf | grep "DROP_EVENT"

# Просмотр счетчиков правил
sudo nft list ruleset -a
# → tcp dport 22 accept # handle 5 packets 1542 bytes 98720
```

## Диагностика и устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `nf_conntrack: table full` | Таблица conntrack переполнена | `sysctl -w net.netfilter.nf_conntrack_max=524288` |
| Пакеты не логируются | В ядре отключен netfilter logging | `dmesg \| grep -i nf`; проверьте `log` выражение |
| Правила не применяются | Ошибка синтаксиса в середине файла | `nft -c -f <файл>` для проверки |
| Docker bypass | Правила INPUT не затрагивают docker-интерфейс | Используйте семейство `inet` и проверьте `bridge-nf-call-iptables` |
| Время ожидания SSH при миграции | Правило `ct state invalid drop` отбрасывает первый пакет | Временно добавьте `accept` для SSH перед отладкой |
| `nft list ruleset` пустой | Неактивный бэкенд iptables (iptables-legacy) | Проверьте `update-alternatives --display iptables` |
| Утечка памяти в nft_monitor | Слишком частые изменения правил в production | Используйте атомарные загрузки через `nft -f`, а не инкрементальные `add rule` |

| **firewalld** | L3-L4 | Средняя | nftables | RHEL-семейство, управление зонами. |

### Пограничные случаи и ограничения

1. **Атомарность:** При загрузке конфигурации через `nft -f` ошибка в середине файла не применяет ни одно изменение. Это защита, но требует тщательного тестирования перед деплоем.
2. **IPv6 и ICMPv6:** Без разрешения ICMPv6 (Neighbor Discovery, Packet Too Big) работа IPv6 нарушается. Не блокируйте весь ICMPv6 без анализа.
3. **Логирование `full`:** Выводит полный payload пакета в лог. На производительности сказывается сильно — используйте только для отладки на отдельных правилах.
4. **Rate limit:** Применяется к самому выражению, а не к цепочке. Если нужно ограничить всю цепочку, используйте `limit` в каждом правиле или `meter`.
5. **Conntrack и NAT:** При изменении NAT-таблиц conntrack не всегда корректно обновляет старые соединения. После изменения NAT-правил может потребоваться сброс conntrack: `conntrack -F`.
6. **Notrack:** Использование `notrack` для всего трафика отключает stateful-инспекцию. Используйте только для защищенных сегментов или UDP-сервисов, не требующих отслеживания.
7. **Flowtables и NAT:** Flowtables не поддерживают NAT. Для маршрутизаторов с NAT используйте классические цепочки.
8. **NAT loopback:** Для доступа к сервису по внешнему IP из внутренней сети требуется дополнительная маршрутизация. В nftables реализуется через двойной NAT (`dnat` + `snat`) или через `redirect`.
9. **MTU и фрагментация:** При изменении MTU на интерфейсе убедитесь, что nftables не фрагментирует пакеты, нарушая MSS. Используйте `tcpmss` clamp в `mangle` таблице.
10. **Асимметричная маршрутизация:** При разном пути входа и выхода `conntrack` может терять пакеты. Используйте `notrack` или отключите conntrack для таких маршрутов.
11. **ALG helpers:** Некоторые приложения (FTP, SIP, H.323) требуют ALG helpers в conntrack. Удалите неиспользуемые helpers.
12. **Совместное использование бэкендов:** `iptables-nft` и `nft` (native) могут сосуществовать, но создавая таблицы в одном семействе, они могут конфликтовать. Используйте разные семейства или имена таблиц для изоляции.
13. **Статическая компиляция ядра:** Если nftables собран статически в ядре, модули `nf_tables` и `nf_conntrack` недоступны для выгрузки. Проверьте `grep NFTABLES /boot/config-$(uname -r)`.
14. **Производительность больших sets:** При количестве элементов >100k в `ip` семействе может наблюдаться фрагментация памяти. Используйте конкатенации или разделите на несколько сетов.

### Best Practices

1. **Принцип Default Deny:** Устанавливайте политику `drop` для всех базовых цепочек (`input`, `forward`, `output`). Разрешайте явно.
2. **Stateful Inspection на первом месте:** Размещайте `ct state established,related accept` в верхней части цепочки для минимизации нагрузки.
3. **Используйте `inet` вместо дублирования `ip`/`ip6`:** Единая таблица `inet` упрощает поддержку и исключает рассинхронизацию правил.
4. **Sets вместо больших списков:** Для >10 элементов используйте `set` или `map`. Это ускоряет обработку и упрощает обновление.
5. **Атомарные загрузки:** Все изменения применяйте через `nft -f <файл>`, а не через отдельные `add rule` в production.
6. **Именование:** Используйте осмысленные имена таблиц и цепочек: `inet filter`, `inet nat`, `bridge filter`.
7. **Логирование:** Логируйте только `drop` и аномалии (`invalid`). Избегайте логирования всего трафика.
8. **Персистентность:** Храните конфигурацию в `/etc/nftables.conf` и используйте systemd-службу `nftables`.
9. **Версионирование:** Храните `nftables.conf` в git. Любые изменения проходят через code review.
10. **Ограничение conntrack:** Настройте `nf_conntrack_max`, `nf_conntrack_tcp_timeout_established` в `/etc/sysctl.d/99-nftables.conf` под нагрузку.
11. **Bogon filtering:** Блокируйте спуфинг-адреса (`0.0.0.0/8`, `127.0.0.0/8`, `224.0.0.0/3`) на внешних интерфейсах.
12. **Отключение ненужных helpers:** Удалите неиспользуемые ALG helpers (`conntrack -L` и `conntrack -D`).
13. **Тестирование:** Используйте `nft -c` перед деплоем. Проверяйте правила сканерами (`nmap`, `ss`).
14. **Backup:** Экспортируйте текущие правила перед каждым изменением.

### Очистка окружения

**Полное удаление nftables и возврат к iptables-legacy:**
```bash
# Остановка службы
systemctl stop nftables
systemctl disable nftables

# Очистка правил
nft flush ruleset

# Удаление правил iptables-nft (если активен)
iptables-nft -F
iptables-nft -X
ip6tables-nft -F
ip6tables-nft -X

# Переключение на iptables-legacy
update-alternatives --set iptables /usr/sbin/iptables-legacy
update-alternatives --set ip6tables /usr/sbin/ip6tables-legacy

# Удаление пакета (Debian/Ubuntu)
apt remove nftables

# Удаление пакета (RHEL/Fedora)
dnf remove nftables
```
