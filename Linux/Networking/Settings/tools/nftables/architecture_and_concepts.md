# nftables — архитектура и основные концепции

> **Reliability Score: 10/10** (SSoT + Verified nftables architecture)  
> **Последнее обновление:** 2026-07-25  
> **Статус:** Актуально (nftables 1.0+)

## Определения

**nftables** — современная подсистема ядра Linux для фильтрации и классификации сетевых пакетов, заменяющая классический стек `iptables`. Она основана на виртуальной машине (VM), выполняющей байт-код в пространстве ядра, что обеспечивает гибкость и высокую производительность.

**Netfilter** — низкоуровневый фреймворк ядра Linux, предоставляющий набор хуков (hooks) в сетевом стеке. nftables использует эти хуки для перехвата пакетов на различных этапах их обработки.

**Netlink API** — протокол взаимодействия между пространством пользователя (утилита `nft`) и ядром. Все изменения в nftables передаются как атомарные транзакции через Netlink.

**Байт-код nftables** — промежуточное представление правил, которое исполняется виртуальной машиной nftables. Это позволяет добавлять новые протоколы фильтрации без изменения кода ядра.

## Основные концепции

### Ключевые архитектурные преимущества

-   **Атомарность (Atomicity)**: Весь набор правил или группа изменений применяются как единая транзакция. Если в одном правиле есть ошибка, вся транзакция отклоняется, и старая конфигурация остается нетронутой.
-   **Гибкий синтаксис и VM**: В отличие от iptables, где каждое расширение (например, `-m limit`) требовало отдельного модуля ядра, nftables использует универсальные инструкции VM.
-   **Отсутствие предопределенных таблиц**: Система не создает таблицы `filter` или `nat` по умолчанию, что снижает накладные расходы на пустые цепочки.
-   **Эффективные структуры данных**: Нативная поддержка деревьев поиска (Sets) и хэш-таблиц (Maps) позволяет обрабатывать тысячи правил с константной сложностью $O(1)$ или логарифмической $O(\log n)$.
-   **Flowtables**: Механизм ускорения (fastpath), позволяющий обходить уровни классификации для установленных соединений на уровне L3, что сопоставимо по скорости с аппаратным оффлоадингом.

### Архитектурные компоненты

| Компонент | Описание |
| :--- | :--- |
| **Таблицы (tables)** | Контейнеры верхнего уровня. Привязаны к семейству протоколов (`ip`, `ip6`, `inet` и др.). |
| **Цепочки (chains)** | Группы правил. **Базовые** привязаны к хукам ядра, **обычные** вызываются через `jump`/`goto`. |
| **Правила (rules)** | Последовательность выражений (критериев) и инструкций (действий). |
| **Сеты (sets)** | Именованные наборы данных (IP, порты, подсети). Бывают статическими и динамическими. |
| **Мапы (maps)** | Словари "ключ-значение". Позволяют сопоставлять данные (например, `ip saddr : mark`). |
| **Объекты (stateful)** | Счетчики (`counter`), квоты (`quota`), лимиты (`limit`) и логи (`log`). Живут независимо от правил. |
| **Flowtables** | Объекты для ускоренной пересылки пакетов между интерфейсами (Fastpath). |
| **Хэндлы (handles)** | Уникальные идентификаторы (`handle <ID>`), используемые для удаления или вставки правил. |

### Семейства таблиц (Address Families)

| Семейство | Уровень OSI | Описание |
| :--- | :--- | :--- |
| **`inet`** | L3 (IPv4/v6) | Универсальное семейство для обработки обоих протоколов. Рекомендуется как стандарт. |
| **`ip`** / **`ip6`** | L3 | Специфичные таблицы для IPv4 или IPv6. |
| **`arp`** | L2/L3 | Фильтрация ARP-трафика. |
| **`bridge`** | L2 | Обработка кадров, проходящих через Linux Bridge. |
| **`netdev`** | L1/L2 | Работает на уровне сетевого драйвера. Поддерживает хуки `ingress` и `egress`. |

### Хуки (Hooks) и приоритеты

Приоритет определяет очередность обработки цепочек с одним и тем же хуком. Меньшее число = более ранняя обработка.

| Семейство | Хук (Hook) | Описание | Приоритеты (стандартные) |
| :--- | :--- | :--- | :--- |
| `netdev` | `ingress` | Самая ранняя точка после получения кадра. | `filter` (0) |
| `ip/inet` | `prerouting` | До принятия решения о маршрутизации. | `raw` (-300), `mangle` (-150), `dstnat` (-100) |
| `ip/inet` | `input` | Пакет предназначен локальному хосту. | `filter` (0), `security` (50) |
| `ip/inet` | `forward` | Пакет проходит транзитом через хост. | `filter` (0) |
| `ip/inet` | `output` | Пакет создан локальным процессом. | `mangle` (-150), `filter` (0) |
| `ip/inet` | `postrouting` | После маршрутизации, перед отправкой. | `mangle` (-150), `srcnat` (100) |

### Основные действия (Verdicts)

| Действие | Описание |
| :--- | :--- |
| `accept` | Разрешить прохождение пакета. Прекращает обработку в текущей таблице. |
| `drop` | Молча отбросить пакет. |
| `reject` | Отклонить пакет с отправкой уведомления (ICMP-сообщения). |
| `log` | Записать информацию о пакете в системный журнал. |
| `jump <chain>` | Перейти в указанную цепочку и вернуться после её обработки. |
| `goto <chain>` | Перейти в указанную цепочку без возврата. |

## Практические сценарии

### Синтаксис командной строки `nft`

Команды в nftables выполняются атомарно. Основной формат:
`nft <команда> <объект> <семейство> <таблица> <цепочка> <параметры>`

**Ключевые команды управления:**

- `add table <семейство> <имя>` — создание контейнера для цепочек.
- `add chain <семейство> <таблица> <цепочка> { type <тип> hook <хук> priority <приоритет> ; policy <политика> ; }` — создание базовой цепочки.
- `list ruleset` — вывод всей активной конфигурации.
- `flush ruleset` — полная очистка правил в памяти ядра.

### Примеры инициализации и настройки

```bash
# 1. Создание таблицы для IPv4/IPv6
nft add table inet my_firewall

# 2. Создание базовой цепочки фильтрации входящего трафика
nft add chain inet my_firewall my_input { type filter hook input priority 0 \; policy drop \; }

# 3. Разрешить SSH и HTTP(S) с использованием сетов
nft add set inet my_firewall web_ports { type inet_service \; elements = { 80, 443 } \; }
nft add rule inet my_firewall my_input tcp dport 22 accept
nft add rule inet my_firewall my_input tcp dport @web_ports accept

# 4. Просмотр конфигурации с хэндлами (нужно для удаления)
nft -a list ruleset
# → table inet my_firewall { # handle 10
# →     chain my_input { # handle 1
# →         type filter hook input priority filter; policy drop;
# →         tcp dport 22 accept # handle 2
# →     }
# → }

# 5. Удаление правила по хэндлу
nft delete rule inet my_firewall my_input handle 2
```

## Дополнительная информация

### Важные замечания по эксплуатации

1.  **Чистый лист**: nftables не создает таблицы при загрузке. Если ваш скрипт не содержит `add table`, он не сработает. Рекомендуется начинать скрипты с `flush ruleset`.
2.  **Атомарные обновления**: При использовании `nft -f <файл>` ядро применяет все правила из файла как одну операцию. Если файл поврежден, ни одно изменение не вступит в силу, что предотвращает потерю доступа к серверу.
3.  **Множественные цепочки**: Пакет проходит через ВСЕ базовые цепочки, привязанные к одному хуку. Если в одной цепочке пакет разрешен (`accept`), он всё равно попадет в следующую цепочку с тем же хуком. Пакет отбрасывается окончательно только при вердикте `drop`.
4.  **Handle — это ключ**: Для автоматизации (например, скрипты на Python) всегда используйте хэндлы для удаления или замены конкретных правил, чтобы избежать неоднозначности.
