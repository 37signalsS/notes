# TCP Wrappers (libwrap) в Linux

> **Статус технологии (Legacy):** TCP Wrappers считается устаревшим (deprecated) механизмом безопасности. 
> * **RHEL 8/9:** Технология полностью удалена.
> * **Ubuntu 24.04 / Debian 12:** Поддержка сохраняется для ряда служб (например, OpenSSH), так как дистрибутивы продолжают накладывать соответствующие патчи.
> * **Arch Linux:** Пакет перенесен в AUR (2021), в базовой системе не поддерживается.
> Стратегически рекомендуется миграция на фильтрацию уровня ядра (Netfilter/nftables) или встроенные средства приложений.

## Определения

* **TCP Wrappers** — программный слой управления доступом к сетевым службам на уровне прикладных протоколов (L7), разработанный Витсе Венемой (Wietse Venema) в 1990 году.
* **libwrap** — разделяемая библиотека, предоставляющая API для проверки прав доступа. Служба должна быть динамически или статически скомпилирована с поддержкой этой библиотеки.
* **tcpd** — классическая утилита-демон («обертка») для служб, запускаемых через суперсерверы `inetd` или `xinetd`. В современных системах используется редко, так как большинство демонов вызывают `libwrap` напрямую.

## Основные концепции

### Порядок обработки правил

Библиотека `libwrap` проверяет конфигурацию при каждом новом подключении. Как только найдено первое совпадение, проверка прекращается (First Match Win).

1.  **`/etc/hosts.allow`**: Белый список. Если совпадение найдено — доступ разрешен.
2.  **`/etc/hosts.deny`**: Черный список. Если совпадение найдено — доступ запрещен.
3.  **Разрешение по умолчанию**: Если правил для службы/клиента нет ни в одном файле, доступ разрешается.

### Синтаксис и опции

Общий формат:
```text
daemon_list : client_list [: option : option ...]
```

*   **daemon_list**: Имя процесса (например, `sshd`, `vsftpd`) или `ALL`.
*   **client_list**: IP, подсети (`192.168.1.`), домены (`.example.com`), или ключевые слова (`LOCAL`, `UNKNOWN`, `PARANOID`).
*   **Опции (Options)**:
    *   `allow` / `deny`: Явное указание действия (позволяет писать всё в одном файле).
    *   `spawn`: Запуск внешней команды.
    *   `banners`: Путь к директории с текстовыми приветствиями/предупреждениями.
    *   `severity`: Указание уровня логов (например, `severity auth.info`).

### Механизм работы

TCP Wrappers работает как промежуточный слой между сетевым соединением и целевым сервисом:

1. При установке соединения библиотека `libwrap` проверяет IP-адрес клиента
2. Если доступ разрешён, соединение передается целевому сервису
3. Если доступ запрещён, соединение разрывается без уведомления клиента

Этот механизм работает на уровне прикладных протоколов (L7), что ограничивает его эффективность — он не может фильтровать трафик до установки TCP-соединения.

## Практические сценарии

### 1. Базовое ограничение доступа для SSH

Наиболее безопасная конфигурация — запрет всего по умолчанию.

**Файл `/etc/hosts.allow`:**
```ini
# Разрешить конкретный IP и доверенную подсеть
sshd : 203.0.113.42, 192.168.1.0/24
```

**Файл `/etc/hosts.deny`:**
```ini
# Запретить всё остальное для всех служб, использующих libwrap
ALL : ALL
```

### 2. Использование текстовых баннеров (Banners)

Метод вывода предупреждения пользователю до установки соединения (часто использовалось для FTP или Telnet).

1. Создайте директорию: `mkdir /etc/banners`.
2. Создайте файл с именем службы: `vi /etc/banners/sshd`.
   ```text
   ВНИМАНИЕ! Доступ только для авторизованного персонала.
   Ваш IP (%h) зафиксирован.
   ```
3. Добавьте правило в `/etc/hosts.allow`:
   ```ini
   sshd : ALL : banners /etc/banners : allow
   ```

### 3. Логика исключений (EXCEPT)

Позволяет разрешить доступ сети, исключив конкретные проблемные узлы.

```ini
# Разрешить всем из локальной сети, кроме одного хоста
ALL : 192.168.1. EXCEPT 192.168.1.66
```

### 4. Дискретное логирование и SPAWN

Выполнение действий при попытке несанкционированного доступа.

```ini
sshd : ALL : spawn (echo "Попытка входа с %h (%a)" | mail -s "SSH Alert" admin@domain.com) & : deny
```
*   `%h` — имя хоста.
*   `%a` — IP-адрес клиента.
*   `%u` — имя пользователя (требует работающего `identd` на стороне клиента, что сейчас встречается редко).

### 5. Миграция с TCP Wrappers на systemd (IPAddressAllow/ IPAddressDeny)

Для современных дистрибутивов с systemd (RHEL 7+, Ubuntu 16.04+) рекомендуется переход на встроенные средства фильтрации:

**Пример конфигурации для SSH через systemd:**
```bash
# Создайте файл /etc/systemd/system/sshd.service.d/allow.conf
[Service]
IPAddressAllow=192.168.1.0/24 203.0.113.42
IPAddressDeny=0.0.0.0/0
```

**Применение изменений:**
```bash
sudo systemctl daemon-reload
sudo systemctl restart sshd
```

### 6. Диагностика проблем с доступом

Когда подключение отклоняется, но правила в hosts.allow/hosts.deny кажутся корректными:

**Проверка правил для конкретного IP:**
```bash
# Проверка через tcpdmatch
tcpdmatch sshd 192.168.1.100

# Проверка правил в файлах
grep -E "^sshd:|^ALL:" /etc/hosts.allow /etc/hosts.deny
```

**Проверка поддержки libwrap в сервисе:**
```bash
# Для динамически скомпилированных сервисов
ldd $(which sshd) | grep libwrap

# Для статически скомпилированных
strings $(which sshd) | grep hosts.allow
```

### 7. Комбинированное использование с Fail2Ban

Для повышения безопасности можно комбинировать TCP Wrappers с Fail2Ban:

**Конфигурация Fail2Ban для SSH:**
```ini
[sshd]
enabled = true
filter = sshd
action = iptables[name=SSH, port=ssh, protocol=tcp]
         hostsdeny[path="/etc/hosts.deny", match="sshd"]
logpath = /var/log/auth.log
maxretry = 5
bantime = 3600
```

## Диагностика и проверка

### Проверка поддержки в бинарных файлах

Если служба скомпилирована динамически (большинство современных систем):
```bash
ldd $(which sshd) | grep libwrap
# → libwrap.so.0 => /lib/x86_64-linux-gnu/libwrap.so.0
```

Если служба скомпилирована статически или `ldd` не дает ответа:
```bash
strings $(which sshd) | grep hosts.allow
# → /etc/hosts.allow
```

### Инструменты отладки

*   **`tcpdmatch`**: Предсказание результата проверки без реального подключения.
    ```bash
    tcpdmatch sshd 192.168.1.10
    # → client:   address  192.168.1.10
    # → access:   granted
    ```
*   **`tcpdchk`**: Проверка файлов конфигурации на наличие ошибок синтаксиса или конфликтов.
    ```bash
    tcpdchk -v
    # Проверяет наличие указанных файлов и корректность записей.
    ```

### Логирование и мониторинг

TCP Wrappers отправляет данные через `syslog`. По умолчанию используется `facility` — `mail`, `auth` или `daemon` (зависит от компиляции). Ищите записи в `/var/log/auth.log` или `journalctl -t tcpd`.

**Примеры поиска в логах:**
```bash
# Поиск отказов доступа
grep "refused" /var/log/auth.log

# Мониторинг в реальном времени
journalctl -t tcpd -f

# Статистика по IP-адресам
grep "refused connect" /var/log/auth.log | awk '{print $NF}' | sort | uniq -c | sort -nr
```

## Устранение неполадок

### Типичные ошибки

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Сервис не читает hosts.allow/hosts.deny** | Сервис не скомпилирован с поддержкой libwrap | Проверить через `ldd` или `strings`; использовать альтернативные методы фильтрации |
| **Подключения отклоняются, хотя правила разрешают** | Неправильный синтаксис правил или порядок обработки | Использовать `tcpdchk` для проверки синтаксиса; проверить порядок правил |
| **Доменные имена не разрешаются** | Проблемы с обратным DNS или слишком строгие правила | Использовать IP-адреса вместо доменных имен; проверить DNS-резолв |
| **Высокая нагрузка при большом количестве правил** | Линейный поиск правил при каждом подключении | Ограничить количество правил; перейти на nftables или systemd |

### Диагностика проблем

**Проблема: Сервис игнорирует правила TCP Wrappers**
```bash
# Проверка поддержки libwrap
ldd $(which sshd) | grep libwrap

# Проверка статической компиляции
strings $(which sshd) | grep hosts.allow

# Проверка через ltrace (если доступно)
ltrace -e wrap /usr/sbin/sshd -d
```

**Проблема: Медленная обработка подключений**
```bash
# Проверка количества правил
wc -l /etc/hosts.allow /etc/hosts.deny

# Профилирование времени выполнения
strace -T sshd -d 2>&1 | grep -E "connect|accept"
```

**Проблема: Логи не записываются**
```bash
# Проверка конфигурации syslog
grep -r "auth\|daemon\|mail" /etc/rsyslog.conf /etc/rsyslog.d/

# Проверка уровня логирования в правилах
grep "severity" /etc/hosts.allow /etc/hosts.deny
```

## Миграция на современные альтернативы

### Стратегия миграции

Для.organization с legacy-системами, использующими TCP Wrappers, рекомендуется поэтапная миграция:

**Этап 1: Аудит текущего использования**
```bash
# Поиск сервисов, поддерживающих libwrap
find /usr/sbin /usr/bin -type f -exec sh -c 'ldd {} 2>/dev/null | grep -q libwrap && echo {}' \;

# Проверка конфигурации
ls -la /etc/hosts.{allow,deny}
```

**Этап 2: Определение替代技术**
Для каждого сервиса определите оптимальный替代:
- **systemd (IPAddressAllow/ IPAddressDeny)** — для сервисов, управляемых systemd
- **nftables/iptables** — для сетевой фильтрации на уровне ядра
- **Встроенные средства сервиса** — если сервис поддерживает собственные механизмы ACL

**Этап 3: Параллельная работа**
На этапе миграции рекомендуется параллельная работа старых и новых механизмов:
```bash
# Пример для SSH с systemd и TCP Wrappers
# Сохранить hosts.allow/hosts.deny как резервный механизм
# Настроить IPAddressAllow/ IPAddressDeny в systemd
```

### Современные альтернативы

| Механизм | Уровень OSI | Рекомендация |
| :--- | :--- | :--- |
| **systemd (IPAddressAllow)** | L3-L4 | Лучшая замена для систем с systemd (RHEL 9+, Ubuntu 22+). |
| **nftables / firewalld** | L3-L4 | Основной стандарт для сетевой фильтрации. |
| **Fail2Ban** | L7 (Логи) | Защита от брутфорса на основе анализа поведения. |

## Дополнительная информация

### Ограничения TCP Wrappers

1. **Уровень фильтрации**: Работает только на уровне прикладных протоколов (L7), не может фильтровать трафик до установки TCP-соединения
2. **Производительность**: Линейный поиск правил при каждом подключении может создавать нагрузку при большом количестве правил
3. **Отсутствие-stateful фильтрации**: Не отслеживает состояние соединений
4. **Ограниченная поддержка**: Не все современные сервисы поддерживают libwrap

### Безопасные практики

1. **Используйте минимально необходимые правила**: Избегайте слишком широких правил типа `ALL: ALL`
2. **Предпочитайте IP-адреса доменным именам**: DNS-резолв может быть скомпрометирован
3. **Комбинируйте с другими механизмами**: Используйте TCP Wrappers как дополнение к файрволу
4. **Регулярно проверяйте логи**: Анализируйте отказы для выявления подозрительной активности
5. **Планируйте миграцию**: Перейдите на современные альтернативы до полного удаления поддержки

### Примеры реальных сценариев

**Сценарий 1: Защита FTP-сервера в legacy-системе**
```ini
# /etc/hosts.allow
vsftpd : 192.168.1.0/24 .internal.example.com
vsftpd : 203.0.113.100

# /etc/hosts.deny
vsftpd : ALL
```

**Сценарий 2: Ограничение доступа к службе мониторинга**
```ini
# /etc/hosts.allow
nrpe : 10.0.0.0/8
nrpe : 172.16.0.0/12

# /etc/hosts.deny
nrpe : ALL
```

**Сценарий 3: Логирование подключений для аудита**
```ini
# /etc/hosts.allow
sshd : ALL : spawn /usr/local/bin/log_ssh_access %h %a %u &
```
