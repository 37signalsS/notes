# Сетевая фильтрация в Linux (iptables и nftables)

Когда сетевой пакет поступает в систему, он проходит через различные этапы обработки в ядре. На этих этапах существуют "точки воздействия" (chains), где можно применять правила фильтрации. Эти правила определяют, как поступать с пакетом: пропустить, отбросить, изменить или перенаправить.

Традиционно в Linux для этих целей использовался `iptables`. Однако в современных дистрибутивах его место занял `nftables`, который является более гибким и мощным инструментом. `iptables` часто работает в режиме совместимости, используя подсистему `nftables` для выполнения своих правил. Таким образом, фактически в системе всегда работает только одна система фильтрации — `nftables`.

## Базовая диагностика сетевого фильтра

Перед началом работы с правилами или при диагностике сетевых проблем важно убедиться, что сетевой фильтр не блокирует трафик.

1.  **Проверка версии `iptables` (и совместимости с `nftables`):**
    ```bash
    iptables -v
    ```
    Эта команда может показать, что `iptables` использует бэкенд `nftables`.

2.  **Просмотр текущих правил `iptables`:**
    ```bash
    sudo iptables -nL
    sudo iptables -S
    ```
    Если вывод пуст или содержит только политики `ACCEPT` без явных правил, это означает, что `iptables` не активно фильтрует трафик.

3.  **Просмотр текущих правил `nftables`:**
    ```bash
    sudo nft list ruleset
    ```
    Если вывод пуст, это подтверждает отсутствие активных правил фильтрации. Если же вывод содержит таблицы и цепочки (например, `table inet filter { ... }`), но внутри цепочек нет правил, это также указывает на отсутствие активной фильтрации.

4.  **Сброс всех правил `nftables` (и `iptables` через совместимость):**
    ```bash
    sudo nft flush ruleset
    ```
    **ВНИМАНИЕ:** Эта команда удаляет все активные правила фильтрации. Используйте её с осторожностью, особенно на производственных серверах, так как это может открыть все порты и сделать систему уязвимой. Перед сбросом рекомендуется сохранить текущие правила (`sudo nft list ruleset > /etc/nftables.conf.bak`).

Если после этих проверок выясняется, что активных правил фильтрации нет, то проблемы с сетью, скорее всего, кроются не в сетевом фильтре.

# nftables без fail2ban: динамический бан брутфорса SSH (IPv4/IPv6)

## Создание таблицы, набора и цепочки

```bash
sudo nft -f - <<'EOF'
table inet fw {
  set ssh_bad {
    type inet_addr
    flags timeout
    timeout 1h      # дефолт для элементов
  }

  chain input {
    type filter hook input priority 0; policy accept;

    iif lo accept
    ct state established,related accept

    # уже занесённых — вон:
    ip saddr @ssh_bad drop

    # детект частых новых соединений на 22/tcp и бан + дроп:
    tcp dport 22 ct state new limit rate over 10/minute \
      add @ssh_bad { ip saddr timeout 2h } counter drop
  }
}
EOF
```

## Ручное управление бан-листом

Админ-бан/разбан:
```bash
# Добавить IP в бан-лист с таймаутом 24 часа и комментарием
sudo nft add element inet fw ssh_bad { 203.0.113.5 timeout 24h comment "manual" }

# Удалить IP из бан-листа
sudo nft delete element inet fw ssh_bad { 203.0.113.5 }
```

## Наблюдение за изменениями

Для отладки и мониторинга можно использовать:
```bash
sudo nft monitor set
```

## Персистентность (Debian/Ubuntu/RHEL/Alma)

Сохранение правил после перезагрузки:
```bash
# Сохранить текущие правила в файл
sudo nft list ruleset > /etc/nftables.conf

# Проверить синтаксис и атомарно загрузить правила из файла
sudo nft -c -f /etc/nftables.conf && sudo nft -f /etc/nftables.conf

# Включить и запустить сервис
sudo systemctl enable --now nftables
```

**Совет:** вынеси блок в `/etc/nftables.d/ssh-ban.nft` и подключи его через `include` в основном файле `/etc/nftables.conf`.

### Зачем и когда это нужно

-   **Базовая защита:** Эффективная защита от простого брутфорса без установки и настройки сторонних сервисов вроде `fail2ban`.
-   **Легковесность:** Подходит для edge-устройств, виртуальных машин или хостов контейнеризации, где не нужен полный функционал `fail2ban`.
-   **Универсальность:** Работает в `family inet`, что означает единую логику и для IPv4, и для IPv6 адресов.
-   **Расширенная защита:** Для более комплексной защиты от различных типов атак (SSH, NGINX DoS, FTP и т.д.) и более гибкой настройки рекомендуется использовать [Fail2Ban](../../Security/Tools/fail2ban_overview.md).

### Трюки и лучшие практики

-   `limit rate over` срабатывает только при **превышении** порога, поэтому обычные пользователи, подключающиеся по SSH, не пострадают.
-   Не используйте `flush table inet fw` в бою: это обнулит текущие динамические баны. Для обновления правил используйте точечные команды (`nft delete rule ...`, `nft add rule ...`) или всегда проверяйте синтаксис конфига (`nft -c -f ...`) перед его полной перезагрузкой.
-   Для нестандартных SSH-портов измените `tcp dport 22` на ваш порт.
