# ip neighbour: Управление соседями (ARP/NDP)

## Определения

* **`ip neighbour`** (синонимы: `ip neigh`, `ip n`) — специализированный объект утилиты `ip` из пакета `iproute2` для управления базой данных соседей (ARP-кэш для IPv4 и таблица NDP для IPv6).
* **Сосед (Neighbour)** — сетевой узел, находящийся в том же сегменте канального уровня (L2), взаимодействие с которым происходит напрямую без участия маршрутизаторов.
* **NUD (Neighbor Unreachability Detection)** — механизм ядра Linux для отслеживания состояния и доступности узлов в локальной сети.

## Предпосылки

### Требования к пакетам

| Дистрибутив | Команда установки |
| :--- | :--- |
| **Debian / Ubuntu** | `sudo apt install iproute2` |
| **RHEL / Fedora / CentOS** | `sudo dnf install iproute` |
| **Arch Linux** | `sudo pacman -S iproute2` |
| **Alpine** | `apk add iproute2` |
| **openSUSE** | `sudo zypper install iproute2` |

### Требования к ядро

Базовые функции `ip neighbour` доступны во всех современных ядрах Linux. Для работы с NDP (IPv6) ядро должно быть собрано с `CONFIG_IPV6=y`.

### Права root

Все команды изменения (add, change, del, flush) требуют привилегий суперпользователя (`sudo`). Команда `ip neigh show` доступна без root.

### Проверка текущего состояния

```bash
# Краткий просмотр ARP-таблицы
ip -br neigh show
# → 192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE

# Просмотр всех интерфейсов с детализацией
ip neigh show
```

## Основные концепции

### Состояния записей (NUD States)

Ядро Linux динамически изменяет состояние каждой записи в таблице соседей:

| Состояние | Описание | Таймеры и поведение |
| :--- | :--- | :--- |
| **REACHABLE** | Связность подтверждена: MAC-адрес известен, узел ответил на запрос недавно. | Переходит в STALE после `gc_stale_time` (60 сек по умолчанию). |
| **STALE** | Запись существует, но считается устаревшей. Требует подтверждения при следующей отправке данных. | Переходит в FAILED при неудачной попытке или в DELAY при отправке пакета. |
| **DELAY** | Пакет отправлен через STALE-запись; ядро ожидает подтверждения от верхних уровней (TCP ACK). | Через 5 сек (`delay_first_probe_time`) переходит в PROBE. |
| **PROBE** | Активная проверка: ядро отправляет серию ARP/NDP-запросов (обычно 3 попытки с интервалом ~1 сек). | После 3 неудачных попыток → FAILED. После ответа → REACHABLE. |
| **INCOMPLETE** | Начальная стадия: отправлен первый запрос, MAC-адрес еще не получен. | После 3 попыток → FAILED. После ответа → REACHABLE. |
| **FAILED** | Узел не ответил на серию запросов (ошибка разрешения адреса). | Удаляется через `gc_stale_time` (по умолчанию 60 сек). |
| **PERMANENT** | Статическая запись: добавлена вручную, не имеет срока жизни и не удаляется автоматически. | Не удаляется GC. Удаляется только вручную (`ip neigh del`). |
| **NOARP** | Интерфейс работает без разрешения адресов (например, `lo` или `p2p`). | Запись не требует ARP/NDP. |
| **PROBE (IPv6)** | В IPv6 вместо NUD PROBE используется Neighbor Solicitation (NS). | Аналогично IPv4, но через ICMPv6. |

### Диаграмма переходов NUD (State Machine)

```
                    +-------------+
                    |  NOARP      | (интерфейсы без ARP: lo, p2p)
                    +-------------+

  Создание записи → +-------------+
                    |  INCOMPLETE | ← отправлен первый ARP-запрос
                    +------+------+
                           |
              ┌────────────┼────────────┐
              ↓            ↓            ↓
        +----------+  +----------+  +----------+
        | REACHABLE|  |  FAILED  |  | DELAY    |
        +----+-----+  +----+-----+  +----+-----+
             |              ↑            |
             ↓              |            ↓
        +----------+        |       +----------+
        |  STALE   |--------+-------|  PROBE   |
        +----------+        |       +----+-----+
             |              |            |
             ↓              |            ↓
        +----------+        |       +----------+
        |  DELAY   |--------+-------| REACHABLE|
        +----------+ (5 сек)        +----------+

  PERMANENT: статическая запись, не участвует в state machine
```

### Флаги и источники данных

*   **router** (IPv6): Указывает, что данный узел анонсирует себя как маршрутизатор. Используется для обнаружения маршрутизаторов в локальной сети.
*   **proxy**: Хост настроен отвечать на ARP-запросы вместо другого узла (Proxy ARP/NDP). Полезно для маршрутизации между подсетями без настройки шлюза на каждом хосте.
*   **extern_learn**: Запись добавлена внешней подсистемой (например, через EVPN/VXLAN или контроллер SDN). Это предотвращает автоматическое удаление записи ядром.
*   **use**: Запись активно используется для передачи пакетов. Увеличивает счетчик `uses` в выводе `ip -s neigh`.
*   **permanent**: Статическая запись, не удаляется GC.
*   **lnl**: Запись привязана к интерфейсу (link-layer).

### Тюнинг Garbage Collection (GC)

В средах с огромным количеством соседей (гипервизоры, K8s узлы) необходимо увеличивать лимиты таблиц через `sysctl`:

| Параметр | Значение по умолчанию | Описание |
| :--- | :--- | :--- |
| `gc_thresh1` | 128 | Минимум записей, до которого очистка не запускается. |
| `gc_thresh2` | 512 | "Мягкий" лимит. Очистка начнется через 5 секунд после превышения. |
| `gc_thresh3` | 1024 | "Жесткий" лимит. Новые записи блокируются, если таблица заполнена. |

**Пример увеличения лимитов для Kubernetes-ноды:**

```bash
# Увеличение лимитов для подсети с 500+ подами
sudo sysctl -w net.ipv4.neigh.default.gc_thresh1=256
sudo sysctl -w net.ipv4.neigh.default.gc_thresh2=1024
sudo sysctl -w net.ipv4.neigh.default.gc_thresh3=2048

# Сохранение в /etc/sysctl.d/90-neigh.conf
echo "net.ipv4.neigh.default.gc_thresh1 = 256" | sudo tee /etc/sysctl.d/90-neigh.conf
echo "net.ipv4.neigh.default.gc_thresh2 = 1024" | sudo tee -a /etc/sysctl.d/90-neigh.conf
echo "net.ipv4.neigh.default.gc_thresh3 = 2048" | sudo tee -a /etc/sysctl.d/90-neigh.conf
```

**Рекомендации по значениям:**

| Тип системы | gc_thresh1 | gc_thresh2 | gc_thresh3 |
| :--- | :--- | :--- | :--- |
| **Рабочая станция / ноутбук** | 128 | 512 | 1024 |
| **Сервер (200-500 хостов в сети)** | 256 | 1024 | 2048 |
| **Kubernetes-нода (500+ подов)** | 512 | 2048 | 4096 |
| **Гипервизор (1000+ VM)** | 1024 | 4096 | 8192 |

## Практические сценарии

### Просмотр и анализ таблицы

```bash
# Краткий список всех соседей (рекомендуется для быстрой проверки)
ip -br neigh show
# → 192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
# → 192.168.1.2 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE

# Просмотр только IPv6 соседей (NDP)
ip -6 neigh show

# Просмотр расширенной статистики (счетчики использования записей)
ip -s neigh show
# → 192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
#    used 128/128, probes 0, gc 0
# → ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#   used: использований записи / максимальное до сброса
#   probes: количество активных проверок (PROBE state)
#   gc: количество попыток сборщика мусора удалить запись

# Просмотр только записей в определенном состоянии
ip neigh show nud reachable
# → 192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE

ip neigh show nud stale
# → 192.168.1.2 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE

ip neigh show nud all
# → Все записи, включая статические (permanent)

# Просмотр соседей на конкретном интерфейсе
ip neigh show dev eth0

# Фильтрация по IP
ip neigh show 192.168.1.1

# Детальный просмотр (флаги, VRF, тип устройства)
ip -d neigh show
```

**Интерпретация вывода `ip -s neigh`:**

| Поле | Описание |
| :--- | :--- |
| `used` | Количество обращений к записи (первое) / лимит (второе). Если достигнут лимит — запись сбрасывается. |
| `probes` | Количество активных ARP/NDP-запросов в состоянии PROBE (0-3). |
| `gc` | Количество попыток удаления сборщиком мусора. |

### Управление записями

```bash
# Добавление статической (бессмертной) записи
sudo ip neigh add 192.168.1.50 lladdr 00:11:22:33:44:66 dev eth0 nud permanent

# Добавление записи с начальным состоянием STALE (без ARP-запроса)
sudo ip neigh add 192.168.1.60 lladdr aa:bb:cc:dd:ee:ff dev eth0 nud stale

# Добавление записи с начальным состоянием REACHABLE
sudo ip neigh add 192.168.1.70 lladdr 11:22:33:44:55:66 dev eth0 nud reachable

# Замена существующей записи (или добавление, если не существует)
sudo ip neigh replace 192.168.1.50 lladdr 00:11:22:33:44:99 dev eth0 nud permanent

# Принудительный перевод записи в состояние проверки (PROBE)
sudo ip neigh change 192.168.1.1 dev eth0 nud probe

# Удаление записи из кэша
sudo ip neigh del 192.168.1.100 dev eth0
```

**Параметры команды `ip neigh add`:**

| Параметр | Описание | Пример |
| :--- | :--- | :--- |
| `lladdr <MAC>` | MAC-адрес соседа. | `lladdr 00:11:22:33:44:55` |
| `dev <iface>` | Интерфейс. | `dev eth0` |
| `nud <state>` | Начальное NUD-состояние. | `nud permanent`, `nud reachable` |
| `proxy` | Включить Proxy ARP для этой записи. | `proxy` |
| `router` | Пометить как маршрутизатор (IPv6). | `router` |

### Тонкая настройка ARP (Proxy и фильтрация)

```bash
# Включение Proxy ARP (ответ своим MAC за другие хосты)
sudo ip neigh add proxy 192.168.2.10 dev eth0
sudo sysctl -w net.ipv4.conf.eth0.proxy_arp=1

# arping — проверка доступности на уровне L2 (в обход Firewall)
arping -I eth0 192.168.1.1

# Проверка дубликатов IP (arping -D)
# exit code 0 = конфликт (два устройства ответили)
# exit code 1 = конфликтов нет
arping -D -I eth0 192.168.1.50

# Массовый поиск конфликтов в подсети
for ip in $(seq 1 254); do
  arping -D -I eth0 -c 1 192.168.1.$ip 2>/dev/null
  [ $? -eq 0 ] && echo "CONFLICT: 192.168.1.$ip"
done
```

```bash

ip neigh get 192.168.1.1 dev eth0
# → 192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE

# Наблюдение за изменениями в таблице (REACHABLE -> STALE и др.)

# → 192.168.1.50 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
# → 192.168.1.50 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE

# Мониторинг только изменений на конкретном интерфейсе

```

### Диагностика смены MAC-адреса для одного IP

Если соединение с устройством работает то стабильно, то пропадает, причина может скрываться не в маршрутизации и даже не в сервисе, а на L2-уровне. Linux хранит соответствие IP-адресов и MAC-адресов в neighbour table.

```bash
# Просмотр текущего состояния таблицы соседей
ip neigh
# → 192.168.1.50 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
```

Если тот же IP внезапно начинает указывать на другой MAC, это признак конфликта IP, HA-переключения или смены устройства за этим адресом.

```bash
# Мониторинг изменений в реальном времени
ip monitor neigh
# → 192.168.1.50 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
# → 192.168.1.50 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE
```

Если MAC меняется туда и обратно, сервер начинает отправлять трафик разным устройствам в зависимости от текущего состояния neighbour cache.

```bash
# Проверка конкретного IP
ip neigh show 192.168.1.50
```

Кроме MAC, можно увидеть состояние записи:

- **REACHABLE** — адрес недавно подтверждался.
- **STALE** — запись есть, но давно не проверялась.
- **FAILED** — neighbour resolution не удалось завершить.

### Причины смены MAC

Самый простой случай — два устройства используют один IP. Но MAC может меняться и штатно, например при failover в VRRP или другой HA-схеме: новый узел начинает отвечать за тот же IP.

В таком случае важно отличать ожидаемое переключение от постоянного ARP flapping.

### Критерии оценки

- `ip neigh` показывает текущее состояние.
- `ip monitor neigh` позволяет поймать изменение именно в момент его возникновения.
- Если один IP несколько раз за короткое время меняет MAC, проблема обычно находится на уровне ARP или L2, а не в приложении.

### Сценарий: замена сервера с тем же IP

Типичная ситуация: сервер заменён, IP сохранён, шлюз пингуется, но часть устройств в сети продолжает отправлять трафик на старый MAC. Причина — устаревшие ARP-записи на соседних хостах, коммутаторах (CAM/MAC-таблица) и в собственной neighbour table самого сервера. Стандартных `ip addr` и `ip route` недостаточно: нужно проверить связку **IP → ARP/neighbour → MAC → реальный интерфейс**.

Исходные данные для примера: заменён сервер с IP `10.0.0.10`. Старый MAC — `AA:AA:AA:AA:AA:AA`, новый — `BB:BB:BB:BB:BB:BB`.

**1. Текущее состояние neighbour table**

```bash
ip neigh show
# → 10.0.0.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE
```

Важен не только MAC, но и состояние NUD (`REACHABLE`, `STALE`, `DELAY`, `PROBE`, `INCOMPLETE`, `FAILED`). `STALE` после замены говорит о том, что запись ещё в кэше, но ядро отправит новый ARP-запрос при следующей передаче данных — это нормальный путь обновления.

**2. Проверка ARP до шлюза в обход Firewall**

```bash
arping -I eth0 10.0.0.1
```

`arping` работает на L2 и не зависит от правил iptables/nftables для ICMP. Если ответ приходит с неожиданного MAC — проблема не в маршрутизации, а в L2-сегменте (виртуальный MAC от VRRP/HA, чужой MAC при конфликте IP или остаточный кэш коммутатора).

**3. Просмотр ARP-трафика на интерфейсе**

```bash
tcpdump -ni eth0 arp
# → Who-has 10.0.0.10 tell 10.0.0.1
# → 10.0.0.10 is-at 11:22:33:44:55:66
```

Если разные устройства в одном широковещательном домене получают разные MAC для одного IP — это либо конфликт IP, либо некорректный failover (например, два VRRP-узла считают себя Master). `tcpdump` здесь показывает и источник запроса, и ответ — можно сразу определить, кто анонсирует MAC.

**4. Мониторинг изменений neighbour table в реальном времени**

```bash
ip monitor neigh
# → 10.0.0.10 dev eth0 lladdr AA:AA:AA:AA:AA:AA REACHABLE
# → deleted 10.0.0.10 dev eth0 lladdr AA:AA:AA:AA:AA:AA
# → 10.0.0.10 dev eth0 lladdr BB:BB:BB:BB:BB:BB REACHABLE
```

Полезно, когда проблема проявляется непостоянно: видно, как запись удаляется, заменяется и переходит между состояниями. Если MAC меняется туда-сюда за минуты — это ARP flapping, и нужно искать активный источник ложных ARP-ответов (часто — старый сервер, ещё не выключенный, или VRRP-конфликт).

**5. Контрольная проверка связности**

```bash
ping -c 5 10.0.0.1
```

Успешный ICMP сам по себе не подтверждает корректность ARP — пинг может пройти через закешированную запись. Реальная проверка: после обновления ARP соседние устройства должны видеть `BB:BB:BB:BB:BB:BB`, а не `AA:AA:AA:AA:AA:AA`. Для массовой проверки на клиентах используется связка:

```bash
# Принудительно сбросить старые записи на проблемных хостах
sudo ip neigh flush dev eth0

# Или точечно для конкретного IP
sudo ip neigh del 10.0.0.10 dev eth0
```

Если после сброса трафик восстанавливается, а через несколько минут снова деградирует — старый MAC присутствует в сети (сервер не выключен физически, неправильный failover в VRRP или остаточный gratuitous ARP от старого узла). Дополнительно проверить MAC-таблицу на коммутаторе доступа (`show mac address-table address AA:AA:AA:AA:AA:AA`) и поиск дубликатов через `arping -D -I eth0 10.0.0.10` — `exit code 0` означает конфликт.

### Диагностический сброс таблицы邻居

`ip neigh flush dev eth0` удаляет динамические записи соседей для указанного интерфейса и заставляет ядро заново выполнить разрешение IP → MAC при следующей передаче трафика. Команда не перезапускает интерфейс, не меняет IP-адреса, маршруты, правила файрвола, таблицу MAC-адресов коммутатора и кэши соседей на других узлах.

Операция затрагивает все динамические записи интерфейса, поэтому может вызвать кратковременную потерю связности и всплеск ARP/NDP-запросов. Если проблемный IP известен, предпочтительнее точечное удаление записи через `ip neigh del <IP> dev <interface>`; массовый `flush` оправдан, когда нужно проверить состояние таблицы целиком. Не следует путать эту команду с `ip address flush dev <interface>`: последняя удаляет IP-адреса с интерфейса и имеет значительно более широкие последствия.

Команда требует прав администратора. По умолчанию она не удаляет записи `permanent` и `noarp`; это важно при проверке статических или специально настроенных соседей.

Используйте сброс как диагностический приём, когда есть основание подозревать устаревшую локальную запись neighbour table — например, после замены сервера с тем же IP, миграции виртуальной машины, переключения VRRP/HA или изменения сетевого оборудования:

```bash
# 1. Зафиксировать состояние до изменения
ip neigh show dev eth0
# → 10.10.10.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE

# 2. Удалить динамические записи соседей интерфейса
sudo ip neigh flush dev eth0

# 3. Показать таблицу сразу после сброса
ip neigh show dev eth0
# → (записей может не быть, пока ядро не начало новое разрешение)

# 4. Создать обращение к соседу и проверить результат разрешения
ping -c 1 10.10.10.1
ip neigh show dev eth0
# → 10.10.10.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE
```

После flush запись не обязана появиться немедленно: она создаётся при следующем lookup или отправке трафика. Если ядро уже начало разрешение, в таблице можно увидеть состояние `INCOMPLETE`:

```bash
ip neigh show dev eth0
# → 10.10.10.1 dev eth0 INCOMPLETE
```

`INCOMPLETE` означает, что MAC-адрес ещё не получен. Ядро отправляет ARP-запрос вида `who-has 10.10.10.1 tell <локальный-IP>`; после ARP-ответа запись переходит, например, в `REACHABLE`:

```bash
ip neigh show dev eth0
# → 10.10.10.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE
```

Интерпретация результата:

| Наблюдение после сброса | Значение | Следующее действие |
| :--- | :--- | :--- |
| Запись отсутствует | Трафик к соседу после flush ещё не обращался | Выполнить контролируемое обращение и повторить `ip neigh show dev eth0` |
| Правильный MAC, `REACHABLE` или `STALE` | Разрешение прошло успешно; устаревшая локальная запись могла быть причиной симптома | Проверить стабильность MAC и наличие повторных смен записи |
| `INCOMPLETE` | Ядро ждёт ARP-ответ | Зафиксировать ARP запросы и ответы через `tcpdump -ni eth0 arp` |
| `FAILED` | Несколько попыток разрешения не дали ответа | Проверить L2, VLAN, физический линк и доступность соседа |
| Снова появляется неправильный MAC | `flush` не является исправлением причины | Искать источник ложного ARP/GARP, конфликт IP, проблему HA или коммутацию L2 |

Сброс邻居 table не устраняет ARP-проблему. Если шлюз или целевой узел не отвечает на ARP, после очистки запись закономерно останется `INCOMPLETE` или перейдёт в `FAILED`, а связность не восстановится. В этом случае нужно исследовать причину отсутствия ARP-ответа:

```bash
sudo tcpdump -ni eth0 arp
# → ARP, Request who-has 10.10.10.1 tell 10.10.10.2
# → ARP, Reply 10.10.10.1 is-at aa:bb:cc:dd:ee:ff
```

Если видны повторные запросы без ответа, проверяются физический уровень, VLAN и trunk, принадлежность IP соседу, фильтрация ARP, конфликт адресов и состояние коммутатора. Если ответ приходит с неожиданным MAC, проверяются GARP/ARP-флапинг, VRRP/HA и возможный конфликт IP. Таким образом, восстановление связи после `flush` подтверждает только гипотезу о некорректном локальном кэше; отсутствие восстановления требует диагностики ниже уровня neighbor table.

### Массовые операции

```bash
# Очистка всей таблицы для конкретного интерфейса
sudo ip neigh flush dev eth0

# Очистка только неисправных записей
sudo ip neigh flush all nud failed

# Очистка всех записей в состоянии STALE
sudo ip neigh flush all nud stale

# Очистка только записей в состоянии REACHABLE
sudo ip neigh flush all nud reachable

# Очистка ВСЕХ записей (включая статические — опасно!)
sudo ip neigh flush all nud permanent
```

**Параметры команды `ip neigh flush`:**

| Параметр | Описание |
| :--- | :--- |
| `dev <iface>` | Только для указанного интерфейса. |
| `nud <state>` | Только для записей в указанном состоянии. Допустимые: `permanent`, `noarp`, `reachable`, `stale`, `delay`, `probe`, `failed`, `incomplete`, `all`. |
| `all` | Все интерфейсы (если не указан `dev`). |

### IPv6 NDP (Neighbor Discovery Protocol)

В IPv6 функцию ARP заменяет **NDP (Neighbor Discovery Protocol, RFC 4861)**. Основные отличия:

| Параметр | ARP (IPv4) | NDP (IPv6) |
| :--- | :--- | :--- |
| **Тип запроса** | Broadcast | Multicast (solicited-node) |
| **Протокол** | Отдельный протокол (EtherType 0x0806) | ICMPv6 (Protocol 58) |
| **Типы сообщений** | Request / Reply | NS (135), NA (136), RS (133), RA (134) |
| **Безопасность** | Нет встроенной | SEND (RFC 3971), RA Guard |

```bash
# Просмотр NDP-таблицы (IPv6)
ip -6 neigh show
# → fe80::1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
# → 2001:db8::1 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE

# Детальный просмотр NDP
ip -6 -d neigh show

# Просмотр NDP с фильтрацией по состоянию
ip -6 neigh show nud reachable

# Добавление статической NDP-записи
sudo ip -6 neigh add 2001:db8::100 lladdr 00:11:22:33:44:55 dev eth0 nud permanent

# Мониторинг NDP-событий
ip -6 monitor neigh

# Проверка NDP через tcpdump (Neighbor Solicitation / Advertisement)
sudo tcpdump -ni eth0 'icmp6 && (ip6[40] == 135 || ip6[40] == 136)'
# → IP6 fe80::1 > ff02::1:ff00:1: ICMP6, neighbor solicitation
# → IP6 2001:db8::1 > fe80::1: ICMP6, neighbor advertisement
```

**Ключевые функции NDP:**

| Функция | Сообщения | Назначение |
| :--- | :--- | :--- |
| **Резолвинг (аналог ARP)** | NS (135) / NA (136) | Разрешение IPv6 → MAC |
| **Обнаружение маршрутизаторов** | RS (133) / RA (134) | Автоматическая конфигурация (SLAAC) |
| **Детекция дубликатов** | NS (135) | Duplicate Address Detection (DAD) |
| **Перенаправление** | Redirect | Оптимизация маршрута |

**Диагностика NDP-проблем:**

```bash
# Проверка SLAAC (получение адреса через RA)
ip -6 addr show dev eth0
# → inet6 2001:db8::1234/64 scope global dynamic
#   ← Address obtained via SLAAC

# Проверка Neighbor Solicitation / Advertisement
sudo tcpdump -ni eth0 'ip6 proto 58 && (ip6[40] == 135 || ip6[40] == 136)'

# Проверка DAD (Duplicate Address Detection)
sudo tcpdump -ni eth0 'ip6 proto 58 && ip6[40] == 135 && ip6 src ::'
# → Neighbor solicitation с src :: = DAD probe
```

## Диагностика и устранение неисправностей

### Анализ таблицы

```bash
# Быстрая проверка состояния
ip -br neigh show

# Статистика по состояниям
ip neigh show | awk '{print $NF}' | sort | uniq -c | sort -rn
# → 42 REACHABLE
# → 15 STALE
# → 3 FAILED

# Поиск записей с высоким использованием
ip -s neigh show | grep -B1 "used [0-9]*/[0-9]*" | head -20
```

### Типичные проблемы

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Микро-фризы сессий** | Resolve Timeout (хост теряет соседа). | Проверить счетчики `ip -s neigh`. Искать циклы REACHABLE → STALE → FAILED. |
| **INCOMPLETE / FAILED** | Узел не отвечает. | Проверить физику, VLAN и разрешить ARP в Firewall соседа. |
| **MAC-адрес для одного IP меняется** | Конфликт IP, HA-переключение (VRRP), ARP flapping. | `ip monitor neigh` — отследить смену; `ip neigh show <IP>` — проверить состояние; `arping -D` — проверить дубликаты. |
| **Записи не добавляются** | Переполнение таблицы (GC). | Увеличить `gc_thresh3` в `sysctl`. |
| **Proxy ARP не работает** | `proxy_arp` не включен на интерфейсе. | `sysctl -w net.ipv4.conf.<iface>.proxy_arp=1`. |
| **IPv6 NDP не работает** | `CONFIG_IPV6` не включен или `accept_ra=0`. | Проверить `ip -6 neigh show` и `sysctl net.ipv6.conf.<iface>.accept_ra`. |
| **arp_ignore срабатывает лишний раз** | Интерфейс имеет несколько IP-адресов. | `sysctl -w net.ipv4.conf.<iface>.arp_ignore=1` — отвечать только на ARP для IP этого интерфейса. |

### Сценарий: настройка ARP для Kubernetes (bare-metal)

В bare-metal кластерах Kubernetes_master-ноды используют VIP (Virtual IP) для HA-контроллера (keepalived/kube-vip). Slave-интерфейс с VIP не должен отвечать на ARP-запросы для этого VIP — иначе возникает конфликт (два хоста анонсируют один IP).

**Проблема:** Два узла с VIP `192.168.1.100` на `eth0` одновременно отвечают на ARP → ARP flapping → сетевая нестабильность.

**Решение — `arp_ignore=1` + `arp_announce=2`:**

```bash
# На ВСЕХ узлах с VIP (Master и Backup):
sudo sysctl -w net.ipv4.conf.all.arp_ignore=1
sudo sysctl -w net.ipv4.conf.all.arp_announce=2

# Для конкретного интерфейса (более точно):
sudo sysctl -w net.ipv4.conf.eth0.arp_ignore=1
sudo sysctl -w net.ipv4.conf.eth0.arp_announce=2

# Персистентность:
cat <<EOF | sudo tee /etc/sysctl.d/90-kube-vip-arp.conf
net.ipv4.conf.all.arp_ignore = 1
net.ipv4.conf.all.arp_announce = 2
EOF
sudo sysctl --system
```

**Как это работает:**
- `arp_ignore=1` — узел отвечает на ARP для VIP **только** если VIP является primary IP на интерфейсе. Backup-ноды (где VIP — secondary) не отвечают.
- `arp_announce=2` — при отправке ARP-запроса (Gratuitous ARP) узел использует IP основного адреса интерфейса, а не VIP.

**Дополнительно для kube-vip (L2-режим):**
```bash
# Gratuitous ARP для быстрого переключения (отправляется при получении VIP):
# kube-vip делает это автоматически; для keepalived:
sudo sysctl -w net.ipv4.conf.all.arp_announce=2
```

> **Подробнее:** Настройка HA-кластера Kubernetes на bare-metal — [k8s_ha_bare_metal_day2_operations.md](../../../../Kubernetes/Installation/HA_Cluster_Bare_Metal/k8s_ha_bare_metal_day2_operations.md). Протокол ARP — [arp.md](../../../../Networking/Protocols/arp.md).

## Оптимизация и лучшие практики

### Рекомендации

1. **Используйте статические записи (nud permanent) для критичных хостов:** Шлюзы, DNS-серверы, database-hosts — это предотвратит их потерю при GC.
2. **Настройте `arp_ignore=1` и `arp_announce=2`** на серверах с несколькими IP-адресами на одном интерфейсе (например, VIP + реальный IP) для предотвращения ложных ARP-ответов.
3. **Увеличивайте `gc_thresh*` пропорционально количеству хостов** в сегменте. Для Kubernetes-нод с 500+ подами `gc_thresh3=4096` — минимум.
4. **Используйте `ip monitor neigh` для длительной диагностики:** В отличие от `ip neigh show` (мгновенный снимок), `ip monitor` показывает переходы состояний.
5. **Для Proxy ARP убедитесь, что шлюз настроен на пропуск ARP-трафика** между подсетями и что `proxy_arp` включен на обоих интерфейсах (входящем и исходящем).
6. **Не смешивайте `ip neigh flush dev eth0` и `ip address flush dev eth0`:** Первая — очищает ARP-кэш (безвредно), вторая — удаляет IP-адреса (破坏性).
7. **В IPv6 убедитесь, что `accept_ra > 0`** на серверах, которым нужна SLAAC-конфигурация. Для маршрутизаторов `accept_ra=2`.

### Взаимодействие с другими подсистемами

| Подсистема | Влияние на neighbor table |
| :--- | :--- |
| **iptables / nftables** | ARP/NDP не проходит через Netfilter ( EtherType 0x0806, IPv6 neighbor). Фильтрация ARP возможна только через `ebtables` / `nft bridge`. |
| **bridge** | Мосты с `bridge link set dev <iface> flood on` flooded ARP-трафик на все порты. |
| **bond / team** | Агрегация каналов: ARP-трафик идет по active slave; failover обновляет neighbor table. |
| **VLAN** | ARP-трафик изолирован по VLAN. Neighbor table разделяется по VLAN-интерфейсам. |

## Очистка среды

### Удаление временных записей

```bash
# Удаление статической записи
sudo ip neigh del 192.168.1.50 lladdr 00:11:22:33:44:66 dev eth0 nud permanent

# Удаление всех записей на интерфейсе (кроме permanent)
sudo ip neigh flush dev eth0

# Удаление только FAILED-записей
sudo ip neigh flush all nud failed
```

### Восстановление стандартного поведения

```bash
# Сброс GC-порогов до значений по умолчанию
sudo sysctl -w net.ipv4.neigh.default.gc_thresh1=128
sudo sysctl -w net.ipv4.neigh.default.gc_thresh2=512
sudo sysctl -w net.ipv4.neigh.default.gc_thresh3=1024

# Отключение Proxy ARP (если включался)
sudo sysctl -w net.ipv4.conf.eth0.proxy_arp=0
```

### Проверка после очистки

```bash
# Убедитесь, что таблица восстанавливается
ip -br neigh show
# → После flush и обращения к хосту запись должна появиться

# Проверка статистики
ip -s neigh show
# → failed 0 (должно быть 0 после восстановления)
```

## Дополнительная информация

### Конфигурация через sysctl (Поведение ARP)

Помимо `ip neigh`, поведение сетевого стека определяется параметрами в `/proc/sys/net/ipv4/conf/`:

*   **arp_ignore**: Контролирует, отвечать ли на ARP-запросы, если целевой IP не настроен на входящем интерфейсе.
    *   `0` — отвечать на все ARP-запросы (по умолчанию).
    *   `1` — отвечать только если IP настроен именно на этом интерфейсе (защита от лишнего трафика в сложных топологиях).
    *   `2` — отвечать только если IP настроен на этом интерфейсе и маска подсети совпадает.
*   **arp_announce**: Определяет уровень ограничений при анонсировании локальных адресов в ARP-запросах.
    *   `0` — использовать любой локальный адрес (по умолчанию).
    *   `1` — использовать наиболее подходящий адрес для данной подсети.
    *   `2` — всегда использовать наиболее подходящий адрес для данной подсети (рекомендуется для L3-балансировки).
