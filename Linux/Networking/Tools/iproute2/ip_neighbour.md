# ip neighbour: Управление соседями (ARP/NDP)

## Определения

* **`ip neighbour`** (синонимы: `ip neigh`, `ip n`) — специализированный объект утилиты `ip` из пакета `iproute2` для управления базой данных соседей (ARP-кэш для IPv4 и таблица NDP для IPv6).
* **Сосед (Neighbour)** — сетевой узел, находящийся в том же сегменте канального уровня (L2), взаимодействие с которым происходит напрямую без участия маршрутизаторов.
* **NUD (Neighbor Unreachability Detection)** — механизм ядра Linux для отслеживания состояния и доступности узлов в локальной сети.

## Основные концепции

### Состояния записей (NUD States)

Ядро Linux динамически изменяет состояние каждой записи в таблице соседей:

| Состояние | Техническое описание |
| :--- | :--- |
| **REACHABLE** | Связность подтверждена: MAC-адрес известен, узел ответил на запрос недавно. |
| **STALE** | Запись существует, но считается устаревшей. Требует подтверждения при следующей отправке данных. |
| **DELAY** | Пакет отправлен через STALE-запись; ядро ожидает подтверждения от верхних уровней (TCP ACK). |
| **PROBE** | Активная проверка: ядро отправляет серию ARP/NDP-запросов (обычно 3 попытки). |
| **INCOMPLETE** | Начальная стадия: отправлен первый запрос, MAC-адрес еще не получен. |
| **FAILED** | Узел не ответил на серию запросов (ошибка разрешения адреса). |
| **PERMANENT** | Статическая запись: добавлена вручную, не имеет срока жизни и не удаляется автоматически. |
| **NOARP** | Интерфейс работает без разрешения адресов (например, `lo` или `p2p`). |

### Флаги и источники данных

*   **router** (IPv6): Указывает, что данный узел анонсирует себя как маршрутизатор.
*   **proxy**: Хост настроен отвечать на ARP-запросы вместо другого узла (Proxy ARP/NDP).
*   **extern_learn**: Запись добавлена внешней подсистемой (например, через EVPN/VXLAN или контроллер SDN). Это предотвращает автоматическое удаление записи ядром.

### Тюнинг Garbage Collection (GC)

В средах с огромным количеством соседей (гипервизоры, K8s узлы) необходимо увеличивать лимиты таблиц через `sysctl`:

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| `gc_thresh1` | 128 | Минимум записей, до которого очистка не запускается. |
| `gc_thresh2` | 512 | "Мягкий" лимит. Очистка начнется через 5 секунд после превышения. |
| `gc_thresh3` | 1024 | "Жесткий" лимит. Новые записи блокируются, если таблица заполнена. |

## Практические сценарии

### Просмотр и анализ таблицы

```bash
# Краткий список всех соседей (рекомендуется для быстрой проверки)
ip -br neigh show
# → 192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE

# Просмотр только IPv6 соседей (NDP)
ip -6 neigh show

# Просмотр расширенной статистики (счетчики использования записей)
ip -s neigh show
```

### Управление записями

```bash
# Добавление статической (бессмертной) записи
sudo ip neigh add 192.168.1.50 lladdr 00:11:22:33:44:66 dev eth0 nud permanent

# Принудительный перевод записи в состояние проверки (PROBE)
sudo ip neigh change 192.168.1.1 dev eth0 nud probe

# Удаление записи из кэша
sudo ip neigh del 192.168.1.100 dev eth0
```

### Тонкая настройка ARP (Proxy и фильтрация)

```bash
# Включение Proxy ARP (ответ своим MAC за другие хосты)
sudo ip neigh add proxy 192.168.2.10 dev eth0
sudo sysctl -w net.ipv4.conf.eth0.proxy_arp=1

# arping — проверка доступности на уровне L2 (в обход Firewall)
arping -I eth0 192.168.1.1
```

### Мониторинг и диагностика

```bash
# Эмуляция выбора соседа для конкретного назначения
ip neigh get 192.168.1.1 dev eth0

# Наблюдение за изменениями в RPDB (события REACHABLE -> STALE и др.)
ip monitor neigh
```

### Диагностика смены MAC-адреса для одного IP

Если соединение с устройством работает то стабильно, то пропадает, причина может скрываться не в маршрутизации и даже не в сервисе, а на L2-уровне. Linux хранит соответствие IP-адресов и MAC-адресов в neighbour table.

```bash
# Просмотр текущего состояния таблицы соседей
ip neigh
# → 192.168.1.50 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
```

Если тот же IP внезапно начинает указывать на другой MAC, это признак конфликта IP, HA-переключения или смены устройства за этим адресом.

```bash
# Мониторинг изменений в реальном времени
ip monitor neigh
# → 192.168.1.50 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
# → 192.168.1.50 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE
```

Если MAC меняется туда и обратно, сервер начинает отправлять трафик разным устройствам в зависимости от текущего состояния neighbour cache.

```bash
# Проверка конкретного IP
ip neigh show 192.168.1.50
```

Кроме MAC, можно увидеть состояние записи:

- **REACHABLE** — адрес недавно подтверждался.
- **STALE** — запись есть, но давно не проверялась.
- **FAILED** — neighbour resolution не удалось завершить.

### Причины смены MAC

Самый простой случай — два устройства используют один IP. Но MAC может меняться и штатно, например при failover в VRRP или другой HA-схеме: новый узел начинает отвечать за тот же IP.

В таком случае важно отличать ожидаемое переключение от постоянного ARP flapping.

### Критерии оценки

- `ip neigh` показывает текущее состояние.
- `ip monitor neigh` позволяет поймать изменение именно в момент его возникновения.
- Если один IP несколько раз за короткое время меняет MAC, проблема обычно находится на уровне ARP или L2, а не в приложении.

### Сценарий: замена сервера с тем же IP

Типичная ситуация: сервер заменён, IP сохранён, шлюз пингуется, но часть устройств в сети продолжает отправлять трафик на старый MAC. Причина — устаревшие ARP-записи на соседних хостах, коммутаторах (CAM/MAC-таблица) и в собственной neighbour table самого сервера. Стандартных `ip addr` и `ip route` недостаточно: нужно проверить связку **IP → ARP/neighbour → MAC → реальный интерфейс**.

Исходные данные для примера: заменён сервер с IP `10.0.0.10`. Старый MAC — `AA:AA:AA:AA:AA:AA`, новый — `BB:BB:BB:BB:BB:BB`.

**1. Текущее состояние neighbour table**

```bash
ip neigh show
# → 10.0.0.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE
```

Важен не только MAC, но и состояние NUD (`REACHABLE`, `STALE`, `DELAY`, `PROBE`, `INCOMPLETE`, `FAILED`). `STALE` после замены говорит о том, что запись ещё в кэше, но ядро отправит новый ARP-запрос при следующей передаче данных — это нормальный путь обновления.

**2. Проверка ARP до шлюза в обход Firewall**

```bash
arping -I eth0 10.0.0.1
```

`arping` работает на L2 и не зависит от правил iptables/nftables для ICMP. Если ответ приходит с неожиданного MAC — проблема не в маршрутизации, а в L2-сегменте (виртуальный MAC от VRRP/HA, чужой MAC при конфликте IP или остаточный кэш коммутатора).

**3. Просмотр ARP-трафика на интерфейсе**

```bash
tcpdump -ni eth0 arp
# → Who-has 10.0.0.10 tell 10.0.0.1
# → 10.0.0.10 is-at 11:22:33:44:55:66
```

Если разные устройства в одном широковещательном домене получают разные MAC для одного IP — это либо конфликт IP, либо некорректный failover (например, два VRRP-узла считают себя Master). `tcpdump` здесь показывает и источник запроса, и ответ — можно сразу определить, кто анонсирует MAC.

**4. Мониторинг изменений neighbour table в реальном времени**

```bash
ip monitor neigh
# → 10.0.0.10 dev eth0 lladdr AA:AA:AA:AA:AA:AA REACHABLE
# → deleted 10.0.0.10 dev eth0 lladdr AA:AA:AA:AA:AA:AA
# → 10.0.0.10 dev eth0 lladdr BB:BB:BB:BB:BB:BB REACHABLE
```

Полезно, когда проблема проявляется непостоянно: видно, как запись удаляется, заменяется и переходит между состояниями. Если MAC меняется туда-сюда за минуты — это ARP flapping, и нужно искать активный источник ложных ARP-ответов (часто — старый сервер, ещё не выключенный, или VRRP-конфликт).

**5. Контрольная проверка связности**

```bash
ping -c 5 10.0.0.1
```

Успешный ICMP сам по себе не подтверждает корректность ARP — пинг может пройти через закешированную запись. Реальная проверка: после обновления ARP соседние устройства должны видеть `BB:BB:BB:BB:BB:BB`, а не `AA:AA:AA:AA:AA:AA`. Для массовой проверки на клиентах используется связка:

```bash
# Принудительно сбросить старые записи на проблемных хостах
sudo ip neigh flush dev eth0

# Или точечно для конкретного IP
sudo ip neigh del 10.0.0.10 dev eth0
```

Если после сброса трафик восстанавливается, а через несколько минут снова деградирует — старый MAC присутствует в сети (сервер не выключен физически, неправильный failover в VRRP или остаточный gratuitous ARP от старого узла). Дополнительно проверить MAC-таблицу на коммутаторе доступа (`show mac address-table address AA:AA:AA:AA:AA:AA`) и поиск дубликатов через `arping -D -I eth0 10.0.0.10` — `exit code 0` означает конфликт.

### Массовые операции

```bash
# Очистка всей таблицы для конкретного интерфейса
sudo ip neigh flush dev eth0

# Очистка только неисправных записей
sudo ip neigh flush all nud failed
```

## Дополнительная информация

### Конфигурация через sysctl (Поведение ARP)

Помимо `ip neigh`, поведение сетевого стека определяется параметрами в `/proc/sys/net/ipv4/conf/`:

*   **arp_ignore**: Контролирует, отвечать ли на ARP-запросы, если целевой IP не настроен на входящем интерфейсе.
    *   `1` — отвечать только если IP настроен именно на этом интерфейсе (защита от лишнего трафика в сложных топологиях).
*   **arp_announce**: Определяет уровень ограничений при анонсировании локальных адресов в ARP-запросах.
    *   `2` — всегда использовать наиболее подходящий адрес для данной подсети (рекомендуется для L3-балансировки).

### Типичные проблемы

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Микро-фризы сессий** | Resolve Timeout (хост теряет соседа). | Проверить счетчики `ip -s neigh`. Искать циклы REACHABLE → STALE → FAILED. |
| **INCOMPLETE / FAILED** | Узел не отвечает. | Проверить физику, VLAN и разрешить ARP в Firewall соседа. |
| **MAC-адрес для одного IP меняется** | Конфликт IP, HA-переключение (VRRP), ARP flapping. | `ip monitor neigh` — отследить смену; `ip neigh show <IP>` — проверить состояние; `arping -D` — проверить дубликаты. |
| **Записи не добавляются** | Переполнение таблицы (GC). | Увеличить `gc_thresh3` в `sysctl`. |
