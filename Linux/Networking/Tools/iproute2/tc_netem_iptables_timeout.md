# Эмуляция сетевых таймаутов через iptables

## Определения

* **Сетевой таймаут (Network Timeout)** — ситуация, при которой отправитель не получает ответ от получателя в течение заданного времени.
* **Connection Timeout** — таймаут на этапе установления соединения (Handshake), когда сервис не отвечает на пакеты `SYN`.
* **Request/Read Timeout** — таймаут в уже установленном соединении, когда данные отправлены, но подтверждение их получения или ответ не приходят.
* **DROP** — действие `iptables`, при котором пакеты молча отбрасываются ядром без уведомления отправителя.
* **REJECT** — действие `iptables`, при котором пакет отбрасывается, но отправителю посылается уведомление (`ICMP port unreachable` или `TCP RST`).

## Основные концепции

### Зачем использовать iptables вместо tc netem?

Хотя `tc netem` отлично справляется с эмуляцией задержек и потерь пакетов, он работает на уровне очередей интерфейса. Для имитации **полного обрыва связи** или блокировки конкретных типов трафика (например, только данных в установленном соединении) `iptables` предоставляет более гибкие инструменты:

1. **Селективность:** можно блокировать трафик по конкретным IP, портам или флагам TCP.
2. **Поведение отправителя:** `DROP` заставляет стек TCP отправителя выполнять ретрансмиссии (Retransmissions) до истечения системного таймаута, что идеально имитирует проблемы в сети или падение узла.

### DROP vs REJECT в тестах отказоустойчивости

| Действие | Реакция клиента | Сценарий тестирования |
| :--- | :--- | :--- |
| **DROP** | Зависание (Hang), ретрансмиссии. | Эмуляция падения сети, "черных дыр", проблем с маршрутизацией. |
| **REJECT** | Мгновенная ошибка (Connection refused/reset). | Эмуляция неработающего процесса или закрытого порта. |

## Практические сценарии

### Эмуляция Connection Timeout (этап Handshake)

В этом сценарии имитируется ситуация, когда сервер "исчез" из сети.

```bash
# Молчаливое отбрасывание входящих соединений на порт 8080
sudo iptables -A INPUT -p tcp --dport 8080 -j DROP
```

*Результат:* Клиент будет отправлять `SYN` пакеты и ждать ответа до срабатывания своего таймаута (обычно от 30 до 127 секунд в зависимости от настроек ОС).

### Эмуляция Request Timeout (в установленном соединении)

Сценарий, при котором соединение устанавливается, но передача полезной нагрузки блокируется.

```bash
# Блокировка только пакетов с данными (флаг PSH)
sudo iptables -A INPUT -p tcp --tcp-flags PSH PSH --dport 8080 -j DROP
```

*Результат:* TCP Handshake проходит успешно, но любые попытки отправить данные приводят к зависанию на стороне отправителя.

### Эмуляция частичной потери связности (Partition)

Для имитации сетевого разделения (Network Partition) между двумя узлами.

```bash
# Блокировка всего трафика от конкретного IP
sudo iptables -A INPUT -s 192.168.1.50 -j DROP
```

### Использование в Docker

Docker управляет своими цепочками `iptables`. Для тестирования контейнеров рекомендуется вставлять правила в начало цепочки `DOCKER-USER`.

```bash
# Блокировка трафика к контейнеру по его внутреннему IP
sudo iptables -I DOCKER-USER -p tcp -d 172.17.0.2 --dport 80 -j DROP
```

## Дополнительная информация

### Очистка правил после тестов

Крайне важно удалять правила после завершения экспериментов.

```bash
# Удаление конкретного правила (замените -A на -D)
sudo iptables -D INPUT -p tcp --dport 8080 -j DROP

# Поиск номера правила для удаления
sudo iptables -L INPUT --line-numbers
sudo iptables -D INPUT <номер_строки>
```

### Метрики и мониторинг

Для подтверждения работы правил используйте следующие инструменты:

* `tcpdump -i any port 8080` — вы увидите ретрансмиссии без ответов.
* `ss -tapn` — вы увидите соединения в состоянии `SYN-SENT` или `ESTABLISHED` с растущими счетчиками ретрансмиссий.
