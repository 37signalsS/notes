# Эмуляция сетевых таймаутов через сетевые экраны

## Определения

* **Сетевой таймаут (Network Timeout)** — ситуация, при которой отправитель не получает ответ от получателя в течение заданного времени.
* **Connection Timeout** — таймаут на этапе установления соединения (Handshake), когда сервис не отвечает на пакеты `SYN`.
* **Request/Read Timeout** — таймаут в уже установленном соединении, когда данные отправлены, но подтверждение их получения или ответ не приходят.
* **DROP** — действие (target), при котором пакеты молча отбрасываются ядром без уведомления отправителя.
* **REJECT** — действие, при котором пакет отбрасывается, но отправителю посылается уведомление (`ICMP port unreachable` или `TCP RST`).

## Основные концепции

### Почему файрволы вместо tc netem?

Хотя `tc netem` (описанный в **[tc netem: Эмуляция сети](./tc_netem.md)**) отлично справляется с эмуляцией задержек на уровне интерфейса, сетевые экраны (`iptables`, `nftables`) обеспечивают более точную и селективную имитацию таймаутов:

1. **L4-селективность:** возможность блокировать трафик только для конкретных приложений, портов или типов TCP-пакетов.
2. **Имитация "Черных дыр":** `DROP` заставляет стек TCP отправителя выполнять экспоненциальные ретрансмиссии (Retransmissions), что идеально моделирует проблемы с маршрутизацией или "падение" удаленного узла.
3. **Эмуляция асимметрии:** блокировка только входящего (`INPUT`) или только исходящего (`OUTPUT`) трафика.

### Сравнение DROP и REJECT

| Действие | Реакция клиента | Сценарий тестирования |
| :--- | :--- | :--- |
| **DROP** | Зависание (Hang), ретрансмиссии. | Эмуляция обрыва кабеля, падения маршрутизатора, проблем с MTU. |
| **REJECT** | Ошибка (Connection refused/reset). | Эмуляция падения процесса сервиса или закрытого порта. |

## Практические сценарии

### Эмуляция таймаута соединения (Connection Timeout)

Имитация ситуации, когда сервер недоступен или пакеты до него не доходят.

#### Через iptables
```bash
# Молчаливое отбрасывание входящих SYN-пакетов на порт 8080
sudo iptables -A INPUT -p tcp --syn --dport 8080 -j DROP
```

#### Через nftables
```bash
# Создание временного правила в существующей таблице (например, inet filter)
sudo nft add rule inet filter input tcp dport 8080 tcp flags syn drop
```

*Результат:* Клиент будет бесконечно пытаться установить соединение до истечения своего таймаута (например, `connect timeout` в `curl`).

### Эмуляция таймаута чтения (Request/Read Timeout)

Соединение устанавливается успешно, но передача полезной нагрузки блокируется.

#### Через iptables
```bash
# Блокировка пакетов с данными (флаг PSH указывает на наличие данных в буфере)
sudo iptables -A INPUT -p tcp --tcp-flags PSH PSH --dport 8080 -j DROP
```

#### Через nftables
```bash
sudo nft add rule inet filter input tcp dport 8080 tcp flags psh drop
```

*Результат:* TCP Handshake проходит, но запрос "повисает" на этапе ожидания ответа.

### Эмуляция случайных потерь (Random Drops)

Имитация нестабильного канала связи на уровнях L3-L4.

#### Через iptables (модуль statistic)
```bash
# Отбрасывать каждый 10-й пакет (10% потерь)
sudo iptables -A INPUT -p tcp --dport 8080 -m statistic --mode nth --every 10 -j DROP

# Случайная потеря 20% пакетов (вероятность 0.2)
sudo iptables -A INPUT -p tcp --dport 8080 -m statistic --mode random --probability 0.2 -j DROP
```

#### Через nftables (numgen)
```bash
# Аналог потери каждого 10-го пакета
sudo nft add rule inet filter input tcp dport 8080 numgen inc mod 10 0 drop
```

### Тестирование на стороне клиента (Outgoing issues)

Если нужно протестировать поведение приложения при попытке отправить данные в "битую" сеть.

```bash
# Блокировка исходящих запросов к API на порту 443
sudo iptables -A OUTPUT -p tcp -d api.example.com --dport 443 -j DROP
```

### Использование в Docker

Docker управляет своими цепочками. Для тестирования контейнеров вставляйте правила в начало цепочки `DOCKER-USER`.

```bash
# Блокировка трафика к конкретному контейнеру
sudo iptables -I DOCKER-USER -p tcp -d 172.17.0.2 --dport 80 -j DROP
```

## Дополнительная информация

### Очистка после экспериментов

Неубранные правила могут привести к ложным инцидентам.

* **iptables:** `sudo iptables -D <chain> <rule_number>` или `sudo iptables -F` (очистка всех правил в таблице).
* **nftables:** `sudo nft delete rule <family> <table_name> <chain_name> handle <id>`.

### Диагностика в реальном времени

Для мониторинга того, что пакеты действительно отбрасываются:

```bash
# Проверка счетчиков пакетов в nftables
sudo nft list ruleset -a

# Просмотр ретрансмиссий через ss
watch -n 1 'ss -ti | grep -E "retrans|cwnd"'

# Анализ трафика через tcpdump
# → SYN-пакеты будут повторяться (Retransmission), но ответов (SYN-ACK) не будет
sudo tcpdump -ni any tcp port 8080
```
