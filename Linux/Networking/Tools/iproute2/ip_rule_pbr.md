# ip rule: Управление правилами маршрутизации

## Определения

* **`ip rule`** (синонимы: `ip ru`) — специализированный объект утилиты `ip` из пакета `iproute2`, предназначенный для управления базой данных правил маршрутизации (**RPDB — Routing Policy Database**).
* **RPDB (Routing Policy Database)** — механизм в ядре Linux, который определяет, какую таблицу маршрутизации использовать для обработки конкретного пакета.
* **Policy-Based Routing (PBR)** — маршрутизация на основе политик. Метод, позволяющий принимать решение о выборе пути не только по адресу назначения (как в классической маршрутизации), но и по адресу источника, входящему интерфейсу, метке фаервола, UID пользователя и другим атрибутам пакета.

## Предпосылки

### Требования к ядру

Для полноценной работы PBR ядро Linux должно быть собрано с поддержкой следующих опций:

| Опция ядра | Назначение |
| :--- | :--- |
| `CONFIG_IP_ADVANCED_ROUTER` | Включает расширенные возможности маршрутизации (множественные таблицы). |
| `CONFIG_IP_MULTIPLE_TABLES` | Поддержка множественных таблиц маршрутизации для IPv4. |
| `CONFIG_IPV6_MULTIPLE_TABLES` | Поддержка множественных таблиц маршрутизации для IPv6. |

Путь в конфигурации ядра: `Networking support → Networking options → TCP/IP networking`.

```bash
# Проверка поддержки множественных таблиц
grep -E "CONFIG_IP_MULTIPLE_TABLES|CONFIG_IPV6_MULTIPLE_TABLES" /boot/config-$(uname -r)
# → CONFIG_IP_MULTIPLE_TABLES=y
```

В большинстве современных дистрибутивов (Ubuntu, Debian, RHEL, Rocky, Alma) эти опции включены по умолчанию.

### Требования к пакетам

* **Пакет `iproute2`**: Установлен в системе (включает утилиту `ip`).
    ```bash
    # Debian/Ubuntu
    sudo apt install iproute2

    # RHEL/CentOS/Rocky
    sudo dnf install iproute
    ```

### Права root

Все команды `ip rule` (кроме `ip rule show`) требуют привилегий суперпользователя (`sudo`).

### Проверка текущего состояния

```bash
# Просмотр текущих правил RPDB
ip rule show
# → 0:	from all lookup local
# → 32766:	from all lookup main
# → 32767:	from all lookup default

# Просмотр с подробностями (VRF, suppress_prefixlength)
ip -d rule show

# Просмотр всех правил со всеми таблицами
ip rule show table all
```

## Основные концепции

### Механика оценки правил (First-Match)

При поступлении пакета (или его локальной генерации) ядро Linux выполняет следующие действия:

1. Пакет попадает в **RPDB** (Routing Policy Database).
2. Ядро последовательно проверяет правила от наименьшего приоритета (0) к наибольшему (32767).
3. **Первое совпавшее правило** (first-match) определяет судьбу пакета:
   - Указывает таблицу маршрутизации для поиска маршрута (`lookup`).
   - Или выполняет другое действие (`blackhole`, `unreachable`, `prohibit`).
   - Или передает управление следующему правилу (`goto`).
4. Если ни одно правило не совпало, используется правило с приоритетом **32767** (таблица `default`, обычно пустая).

> **Важно:** Проверка правил происходит **до** поиска маршрута в таблице. Даже если в таблице `main` есть маршрут, но правило RPDB направляет пакет в другую таблицу — будет использована указанная таблица.

```
Пакет → [Priority 0: local] → [Priority 100: table 100] → [Priority 32766: main] → [Priority 32767: default]
              ↑ первый match — стоп                        ↑ если не совпало выше
```

### Стандартный набор правил

По умолчанию в Linux настроены три правила, обеспечивающие базовую работу системы:

| Приоритет | Селектор | Таблица | Назначение |
| :--- | :--- | :--- | :--- |
| **0** | `from all` | `local` | Обработка локальных, петлевых (loopback) и широковещательных адресов. **Нельзя удалять.** |
| **32766** | `from all` | `main` | Основная таблица для стандартных и динамических маршрутов. |
| **32767** | `from all` | `default` | Резервная пустая таблица для пакетов, не попавших под иные правила. |

**Правило `local` (приоритет 0)** — критически важно. Оно обрабатывает:
- Адреса назначения, принадлежащие интерфейсам хоста.
- Широковещательные адреса.
- Loopback-адреса (`127.0.0.0/8`).

> **Никогда не удаляйте** правило с приоритетом 0. Это приведет к потере сетевой связности.

### Диапазоны приоритетов (рекомендации)

Для поддержания порядка в RPDB рекомендуется придерживаться следующих диапазонов:

| Диапазон | Назначение | Примеры |
| :--- | :--- | :--- |
| **0** | Системное правило `local`. | Не использовать для пользовательских правил. |
| **1–99** | Критичные системные правила (VPN-шлюзы, маршруты по умолчанию для特定ные подсети). | `ip rule add from 10.0.0.0/8 table 100 priority 10` |
| **100–999** | Основные PBR-правила (разделение трафика по портам, протоколам, пользователям). | `ip rule add ipproto tcp dport 443 table 150 priority 500` |
| **1000–32765** | Правила общего назначения, временныe правила, правила для отладки. | `ip rule add from 192.168.1.0/24 table 200 priority 2000` |
| **32766** | Системное правило `main`. | Не использовать. |
| **32767** | Системное правило `default`. | Не использовать. |

### Файл /etc/iproute2/rt_tables

Файл `/etc/iproute2/rt_tables` содержит маппинг числовых ID таблиц на их имена. Это делает конфигурацию более читаемой и поддерживаемой.

```
# /etc/iproute2/rt_tables
#
# numeric  name
#
255    local
254    main
253    default
0      unspec
100    isp1_table
101    isp2_table
200    vpn_user_table
```

**Рекомендации:**
- Используйте осмысленные имена (например, `isp1_table`, `vpn_user_table`).
- Избегайте пробелов и спецсимволов в именах.
- Не переопределяйте зарезервированные ID (0, 253, 254, 255).
- Имена таблиц доступны в командах `ip rule` и `ip route` вместо числовых ID:

```bash
# Использование имени вместо числового ID
sudo ip rule add from 10.0.0.0/8 table isp1_table priority 100
sudo ip route add default via 192.168.1.1 dev eth0 table isp1_table
```

### Справочник селекторов (условий)

| Селектор | Описание | Технические нюансы |
| :--- | :--- | :--- |
| **from / to** | Адрес источника / назначения. | Поддерживает префиксы (`from 10.0.0.0/24`) и `not` (отрицание). |
| **iif / oif** | Входящий / исходящий интерфейс. | `iif lo` используется для трафика, генерируемого локально. |
| **fwmark** | Метка пакета из Netfilter. | Позволяет реализовать логику L7 (через `iptables`/`nftables`). |
| **uidrange** | Диапазон UID пользователя. | Критично для per-user routing (изоляция процессов). |
| **ipproto** | Номер или имя протокола IP. | Требует ядро 4.17+ (TCP, UDP, ICMP и др.). |
| **sport / dport** | Порты источника / назначения. | Требует ядро 4.17+; работает в связке с `ipproto`. |
| **l3mdev** | L3 Master Device (VRF). | Сопоставление пакетов, принадлежащих конкретному **[VRF](../../vrf.md)**. |
| **tos** | Поле Type of Service. | Классификация трафика по приоритетам QoS. |
| **realms** | Routing realms (метки маршрутизации). | Продвинутый атрибут для классификации потоков. Требует настройки в `ip route`. |

**Примеры использования селекторов:**

```bash
# Фильтрация по протоколу и порту (ядро 4.17+)
sudo ip rule add ipproto tcp dport 443 table 100 priority 500

# Фильтрация по UID-диапазону
sudo ip rule add uidrange 1000-2000 table 200 priority 1000

# Фильтрация с отрицанием (всё, кроме указанной подсети)
sudo ip rule add to not 192.168.0.0/16 table vpn_table priority 2000

# Фильтрация по входящему интерфейсу
sudo ip rule add iif eth1 table isp2_table priority 300

# Фильтрация по TOS (Type of Service)
sudo ip rule add tos 0x10 table 100 priority 400
```

### Типы действий и продвинутые параметры

*   **lookup / table <ID>** — Искать маршрут в указанной таблице (основное действие).
*   **suppress_prefixlength <N>** — Игнорировать таблицу, если найденный в ней маршрут имеет маску префикса меньше или равную N (например, `0` — игнорировать default gateway).
*   **suppress_ifgroup <ID>** — Игнорировать таблицу, если исходящий интерфейс принадлежит группе ID.
*   **blackhole** — Молчаливо отбросить пакет.
*   **unreachable** — Отбросить и отправить ICMP "Network Unreachable".
*   **prohibit** — Отбросить и отправить ICMP "Communication Administratively Prohibited".
*   **goto <N>** — Перейти к правилу с указанным приоритетом (без выполнения поиска маршрута).
*   **nop** — Без действия (полезно для отладки и временного отключения правила).

## Практические сценарии

### Просмотр и анализ правил

```bash
# Просмотр всех правил (краткий)
ip rule show
# → 0:	from all lookup local
# → 100:	from 10.0.0.0/8 lookup isp1_table
# → 32766:	from all lookup main
# → 32767:	from all lookup default

# Просмотр с подробностями (VRF, suppress_prefixlength, goto)
ip -d rule show
# → 0:	from all lookup local
# → 100:	from 10.0.0.0/8 lookup isp1_table suppress_prefixlength 0

# Просмотр всех правил со всеми таблицами (включая пустые)
ip rule show table all
# → 0:	from all lookup local
# → 100:	from 10.0.0.0/8 lookup isp1_table
# → ... (содержимое каждой таблицы)

# Фильтрация правил по источнику
ip rule show | grep "from 10.0.0"
# → 100:	from 10.0.0.0/8 lookup isp1_table

# Фильтрация по приоритету
ip rule show | grep "^1000:"
# → 1000:	from 192.168.1.0/24 lookup vpn_table
```

### Изоляция трафика пользователя (UID-routing)

Направить трафик пользователя с UID 1001 через таблицу 200 (например, в VPN-туннель).

```bash
sudo ip rule add uidrange 1001-1001 table 200 priority 1000
```

### Маршрутизация по портам (L4 PBR)

Направить весь исходящий трафик на порт 443 (HTTPS) через конкретный интерфейс (таблица 150). Требует ядро 4.17+.

```bash
sudo ip rule add ipproto tcp dport 443 table 150 priority 500
```

### Умный пропуск таблицы (suppress_prefixlength)

Использовать таблицу 100, только если в ней есть конкретный маршрут к подсети. Если там только маршрут по умолчанию (`0.0.0.0/0`), правило будет проигнорировано, и ядро перейдет к следующему.

```bash
sudo ip rule add from 10.10.10.0/24 table 100 suppress_prefixlength 0
```

### Использование меток фаервола (fwmark)

Реализация сложной логики (например, балансировка трафика конкретного приложения).

```bash
# 1. Маркировка HTTP-трафика в nftables
# nft add rule inet filter prerouting tcp dport 80 meta mark set 0x80

# 2. Создание правила для помеченных пакетов
sudo ip rule add fwmark 0x80 table 80 priority 300
```

### Комбинирование условий с исключением (not)

Направить весь трафик, **кроме** трафика в локальную сеть `192.168.0.0/16`, через таблицу `vpn_table`.

```bash
sudo ip rule add to not 192.168.0.0/16 table vpn_table priority 2000
```

### IPv6-правила

Для управления правилами IPv6 используется флаг `-6`:

```bash
# Просмотр IPv6-правил
ip -6 rule show

# Добавление IPv6-правила
sudo ip -6 rule add from 2001:db8::/32 table ipv6_vpn priority 500

# Удаление IPv6-правила
sudo ip -6 rule del from 2001:db8::/32 table ipv6_vpn priority 500

# Правило для TCP/443 (ядро 4.17+)
sudo ip -6 rule add ipproto tcp dport 443 table ipv6_isp1 priority 500
```

### Бэкап и восстановление правил

```bash
# Сохранение текущих правил в файл
ip rule save > /tmp/ip_rules_backup.rules

# Просмотр сохраненных правил
cat /tmp/ip_rules_backup.rules
# → 0:	from all lookup local
# → 100:	from 10.0.0.0/8 lookup isp1_table

# Восстановление правил из файла
sudo ip rule restore < /tmp/ip_rules_backup.rules

# Сохранение только для конкретного протокола
ip -4 rule save > /tmp/ip4_rules.rules
ip -6 rule save > /tmp/ip6_rules.rules
```

### Очистка правил (flush)

**Внимание:** `ip rule flush` удаляет **все** пользовательские правила (оставляя только системные: local, main, default). Это **необратимая** операция.

```bash
# Просмотр правил перед очисткой
ip rule show

# Очистка всех пользовательских правил
sudo ip rule flush

# Проверка после очистки
ip rule show
# → 0:	from all lookup local
# → 32766:	from all lookup main
# → 32767:	from all lookup default
```

> **Рекомендация:** Перед `flush` всегда сохраняйте текущие правила (`ip rule save`) и убедитесь, что вы понимаете последствия.

### Удаление правил

```bash
# Удаление по атрибутам (необходимо полное совпадение параметров)
sudo ip rule del from 192.168.1.50 table 100

# Удаление по приоритету (наиболее надежный способ)
sudo ip rule del priority 1000

# Удаление IPv6-правила
sudo ip -6 rule del priority 500

# Проверка после удаления
ip rule show | grep "1000:"
# → (пусто — правило удалено)
```

### Валидация после изменений

После добавления или изменения правил всегда проверяйте корректность:

```bash
# 1. Проверка наличия правила
ip rule show | grep "1000:"
# → 1000:	from 192.168.1.0/24 lookup vpn_table

# 2. Эмуляция выбора маршрута (без реальной отправки)
ip route get 8.8.8.8 from 192.168.1.50
# → 8.8.8.8 via 10.0.0.1 dev tun0 table vpn_table src 192.168.1.50

# 3. Проверка маршрута в целевой таблице
ip route show table vpn_table
# → default via 10.0.0.1 dev tun0

# 4. Проверка связи (если возможно)
ping -c 3 -I 192.168.1.50 8.8.8.8
```

## Диагностика и устранение неисправностей

### Анализ RPDB

```bash
# Просмотр всех правил
ip rule show

# Детальный просмотр (включая подавление префиксов и VRF)
ip -d rule show

# Эмуляция выбора маршрута (важнейший инструмент отладки)
ip route get 8.8.8.8 from 192.168.1.50 iif eth1
# → В выводе будет указана выбранная таблица и шлюз.
```

### Проблема: Правило добавлено, но не работает

**Диагностика:**
```bash
# 1. Проверка наличия правила
ip rule show | grep "priority_500"
# → Если пусто — правило не добавлено

# 2. Проверка таблицы
ip route show table 150
# → Если пусто — нет маршрутов в целевой таблице

# 3. Эмуляция выбора маршрута
ip route get 8.8.8.8 from 192.168.1.50
# → Если показывает таблицу main — правило не совпало

# 4. Проверка приоритета
ip rule show | grep -E "^ *[0-9]+:"
# → Правило с меньшим приоритетом может перехватить пакет
```

**Решение:** Убедитесь, что селектор правила соответствует атрибутам пакета. Используйте `ip route get` с теми же параметрами (from, iif, fwmark), что и в правиле.

### Проблема: Конфликт правил

**Симптом:** Трафик уходит не в ту таблицу, хотя правило добавлено.

**Диагностика:**
```bash
# Просмотр правил в порядке приоритета
ip rule show
# → 100:	from 10.0.0.0/8 lookup table_A
# → 200:	from 10.0.0.0/8 lookup table_B
# → ↑ Правило с приоритетом 100 сработает первым

# Эмуляция для конкретного пакета
ip route get 8.8.8.8 from 10.0.0.5
# → Покажет, какую таблицу выбрало ядро
```

**Решение:** Измените приоритет конфликтующего правила или уточните селектор.

### Проблема: Асимметрия и rp_filter

При использовании PBR ответный трафик может уходить через интерфейс, отличный от входящего. Если включен **Strict Reverse Path Forwarding (RPF)**, ядро отбросит такой пакет.

**Решение:** Установить `rp_filter` в режим `2` (Loose).

```bash
# Временное включение
sudo sysctl -w net.ipv4.conf.all.rp_filter=2

# Постоянное включение в /etc/sysctl.d/99-pbr.conf
# net.ipv4.conf.all.rp_filter = 2
# net.ipv4.conf.default.rp_filter = 2
```

### Проблема: Правило пропадает после перезагрузки

**Причина:** Команды `ip rule` являются эфемерными и не сохраняются автоматически.

**Решение:** Используйте один из методов персистентности:

```bash
# NetworkManager
sudo nmcli connection modify "eth0" +ipv4.routing-rules "from 10.0.0.10 table 100"

# Netplan (/etc/netplan/50-cloud-init.yaml)
# routing-policy:
#   - from: 10.0.0.10
#     table: 100

# systemd-networkd (/etc/systemd/network/eth0.network)
# [RoutingPolicyRule]
# From=10.0.0.10
# Table=100
```

### Проблема: "RTNETLINK answers: Invalid argument"

**Причины:**
1. Неверный синтаксис команды.
2. Указана несуществующая таблица (не добавлена в `/etc/iproute2/rt_tables` и не создана через `ip route`).
3. Неподдерживаемый селектор (например, `sport` на ядре < 4.17).

**Решение:**
```bash
# Проверка версии ядра
uname -r
# → 5.15.0-xx (должно быть 4.17+ для L4-селекторов)

# Проверка таблицы
ip route show table 150
# → Если пусто — создайте маршрут
sudo ip route add default via 192.168.1.1 dev eth0 table 150
```

### Проблема: "RTNETLINK answers: File exists"

**Причина:** Правило с таким же селектором и приоритетом уже существует.

**Решение:**
```bash
# Просмотр существующего правила
ip rule show | grep "from 10.0.0.0/8"
# → 100:	from 10.0.0.0/8 lookup isp1_table

# Удаление перед добавлением
sudo ip rule del from 10.0.0.0/8 table isp1_table priority 100
sudo ip rule add from 10.0.0.0/8 table isp2_table priority 100

# Или использование другого приоритета
sudo ip rule add from 10.0.0.0/8 table isp2_table priority 101
```

### Проблема: Не работает IPv6 PBR

**Диагностика:**
```bash
# Проверка IPv6-правил
ip -6 rule show
# → Если пусто — нет IPv6-правил

# Проверка поддержки ядра
grep CONFIG_IPV6_MULTIPLE_TABLES /boot/config-$(uname -r)
# → CONFIG_IPV6_MULTIPLE_TABLES=y

# Эмуляция IPv6-маршрута
ip -6 route get 2001:db8::1 from 2001:db8::100
```

### Проблема: Трафик локально генерируемых пакетов не маршрутизируется по PBR

**Причина:** Для локального трафика (генерируемого самим хостом) используется селектор `iif lo`.

**Решение:**
```bash
# Правило для локального трафика
sudo ip rule add iif lo ipproto tcp sport 8080 table proxy_table priority 200

# Проверка
ip route get 8.8.8.8 from 127.0.0.1 iif lo sport 8080
```

## Оптимизация и лучшие практики

### Рекомендации

1. **Всегда указывайте `priority`:** Без него правила добавляются с уменьшающимся приоритетом относительно последнего добавленного, что может нарушить логику PBR.
2. **Используйте осмысленные имена таблиц:** Записывайте их в `/etc/iproute2/rt_tables` и используйте в командах вместо числовых ID.
3. **Группируйте правила по функциональному назначению:** Используйте диапазоны приоритетов (см. таблицу выше).
4. **Избегайте `flush` в продакшене:** Всегда сохраняйте текущие правила перед очисткой.
5. **Проверяйте после изменений:** Используйте `ip route get` для эмуляции выбора маршрута.
6. **Документируйте изменения:** Записывайте, какие правила добавлены и зачем.

### Взаимодействие с Netfilter

`ip rule` срабатывает **после** цепочки `PREROUTING` и **после** цепочки `OUTPUT` в Netfilter. Это означает:

- Маркировка (`fwmark`) должна устанавливаться в `PREROUTING` (для входящего трафика) или `OUTPUT` (для исходящего).
- Маркировка в `POSTROUTING` **не работает** для PBR (пакет уже прошел этап маршрутизации).

```bash
# Правильно: маркировка в PREROUTING
nft add rule inet filter prerouting tcp dport 443 meta mark set 0x1

# Неправильно: маркировка в POSTROUTING (не работает для PBR)
# nft add rule inet filter postrouting tcp dport 443 meta mark set 0x1
```

## Очистка среды

### Удаление временных правил

```bash
# Удаление конкретного правила
sudo ip rule del from 10.0.0.0/8 table isp1_table priority 100

# Удаление всех правил с определенным приоритетом
# (если использовался диапазон, например 1000-1099)
for pri in $(seq 1000 1099); do
  sudo ip rule del priority $pri 2>/dev/null
done

# Проверка после удаления
ip rule show
```

### Восстановление стандартных правил

```bash
# Проверка текущих правил
ip rule show
# → Должны остаться только: local (0), main (32766), default (32767)

# Если есть лишние правила — очистка
sudo ip rule flush

# Восстановление из бэкапа
sudo ip rule restore < /tmp/ip_rules_backup.rules
```

### Проверка после очистки

```bash
# Убедитесь, что системные правила на месте
ip rule show
# → 0:	from all lookup local
# → 32766:	from all lookup main
# → 32767:	from all lookup default

# Проверка маршрутизации
ip route get 8.8.8.8
# → Должен показать маршрут через основной интерфейс

# Проверка связи
ping -c 3 8.8.8.8
```

## Дополнительная информация

### Сохранение конфигурации (Persistence)

Команды `ip rule` применяются немедленно, но не сохраняются после перезагрузки.

*   **systemd-networkd**: Секция `[RoutingPolicyRule]` в `.network` файлах.
*   **Netplan**: Секция `routing-policy:` в YAML-файлах.
*   **NetworkManager**: Команда `nmcli connection modify <name> +ipv4.routing-rules "from 1.2.3.4 table 100"`.

Подробнее см. в разделе **[Администрирование PBR](../../Policy_Based_Routing/administration.md#сохранение-настроек-persistence)**.
