# tc netem: Эмуляция сетевых проблем

## Определения

* **`tc netem` (Network Emulator)** — компонент подсистемы управления трафиком (`tc`) в ядре Linux, входящий в пакет `iproute2`. Предназначен для имитации характеристик реальных сетей (задержки, потери, повреждения, дублирование и изменение порядка пакетов) на локальных интерфейсах.
* **`qdisc` (Queuing Discipline)** — дисциплина очереди. Механизм ядра Linux, управляющий порядком обработки и передачи пакетов. `netem` является бесклассовой (classless) дисциплиной, которая модифицирует поток пакетов перед их отправкой драйверу сетевой карты.

## Предпосылки

### Требования

* **Пакет `iproute2`**: Установлен в системе (включает утилиту `tc`).
    ```bash
    # Debian/Ubuntu
    sudo apt install iproute2

    # RHEL/CentOS/Rocky
    sudo dnf install iproute
    ```
* **Права root**: Все команды `tc` требуют привилегий суперпользователя (`sudo`).
* **Интерфейс**: Знание имени целевого сетевого интерфейса (`ip link show` для просмотра доступных).
* **Ядро Linux**: `netem` доступен начиная с ядра 2.6.x. Некоторые параметры (например, `slot`) требуют ядра 4.19+.

### Проверка работоспособности

```bash
# Проверка наличия модуля ядра
lsmod | grep sch_netem

# Если модуль не загружен
sudo modprobe sch_netem
```

## Основные концепции

### Эмулируемые параметры

| Параметр | Техническое описание | Область применения |
| :--- | :--- | :--- |
| **delay** | Внесение задержки и джиттера. | Симуляция WAN, спутниковых каналов, 4G/5G сетей. |
| **loss** | Искусственная потеря пакетов. | Тестирование устойчивости протоколов к потерям. |
| **corrupt** | Модификация случайного бита в пакете (noise). | Проверка механизмов контроля целостности (Checksum). |
| **duplicate** | Дублирование пакетов. | Тестирование идемпотентности API и дедупликации в VPN. |
| **reorder** | Нарушение последовательности доставки. | Симуляция Multipath-маршрутизации или ECMP. |
| **rate** | Ограничение полосы пропускания (базовое). | Моделирование узких каналов (Dial-up, Edge). |
| **limit** | Размер внутреннего буфера (в пакетах). | Тестирование влияния переполнения очередей (Bufferbloat). |
| **slot** | Отправка пакетов во временных слотах. | Эмуляция TDM-сетей, WiFi или TDMA. |

### Вариативность: Джиттер и Корреляция

Для создания реалистичных условий `netem` позволяет настраивать статистическую вариативность:

*   **Jitter (Джиттер)**: Разброс задержки относительно базового значения.
    *   *Пример:* `delay 100ms 10ms` означает задержку 100 ± 10 мс.
*   **Correlation (Корреляция)**: Определяет степень зависимости текущего события от предыдущего.
    *   *Пример:* `loss 5% 25%` означает вероятность потери 5%, но если предыдущий пакет был потерян, вероятность потери следующего возрастает на 25%. Это имитирует "всплески" (bursts) ошибок, характерные для реальных линий связи.

### Распределения задержки (Distribution)

По умолчанию используется равномерное распределение (**uniform**). Для имитации реального трафика в интернете доступны:
*   **normal**: Гауссово (нормальное) распределение.
*   **pareto** / **paretonormal**: Распределения с "тяжелыми хвостами", моделирующие редкие, но значительные задержки.

```bash
# Пример: задержка 150мс ± 20мс с Гауссовым распределением
sudo tc qdisc add dev eth0 root netem delay 150ms 20ms distribution normal
```

### Математические модели потерь

`netem` поддерживает три уровня сложности моделирования потерь:

1.  **random**: Простая модель с независимой вероятностью для каждого пакета.
2.  **gemodel (Gilbert-Elliot)**: Классическая модель с двумя состояниями (Good/Bad), имитирующая состояние радиоэфира.
    *   `p`: Вероятность перехода Good → Bad.
    *   `r`: Вероятность перехода Bad → Good.
    *   `1-h`: Вероятность ошибки в состоянии Bad.
    *   `1-k`: Вероятность ошибки в состоянии Good.
3.  **4-state**: Сложная модель Маркова для эмуляции глубоких замираний сигнала (fading).

### Ограничения `netem`

*   **Только исходящий трафик**: `netem` работает на egress (исходящих) пакетах. Для эмуляции проблем входящего трафика используйте IFB (Intermediate Functional Block) — см. раздел "Эмуляция входящего трафика".
*   **Не является шейпером**: `netem` не обеспечивает точного ограничения скорости. Для шейпинга используйте связку с `HTB` или `TBF`.
*   **Влияние на TCP-стек**: Задержки > 1с могут вызвать массовые ретрансмиссии TCP еще до отправки пакета с хоста. Учитывайте RTO (Retransmission Timeout).
*   **Одновременное применение**: Нельзя применить несколько экземпляров `netem` к одному интерфейсу. Используйте иерархию классов для комбинирования эффектов.
*   **Производительность**: На высокоскоростных каналах (>10 Gbps) `netem` может стать узким местом из-за обработки каждого пакета в ядре.

## Практические сценарии

### Основные команды управления

| Действие | Команда |
| :--- | :--- |
| **Добавить** | `sudo tc qdisc add dev eth0 root netem <параметры>` |
| **Изменить** | `sudo tc qdisc change dev eth0 root netem <параметры>` |
| **Удалить** | `sudo tc qdisc del dev eth0 root` |
| **Просмотр** | `tc qdisc show dev eth0` |
| **Статистика** | `tc -s qdisc show dev eth0` |

### Сценарий 1: Симуляция физических каналов

#### Межконтинентальный WAN

```bash
# Добавление задержки 200мс и потерь 0.1%
sudo tc qdisc add dev eth0 root netem delay 200ms loss 0.1%

# Проверка применения
tc qdisc show dev eth0
# → qdisc netem 8001: root refcnt 2 limit 1000 delay 200.0ms loss 0.1%

# Тестирование через ping
ping -c 10 192.168.1.1
# → Задержки должны быть ~200ms ± 20ms (с учетом jitter по умолчанию)
```

#### Нестабильный мобильный интернет

```bash
# Имитация 4G: задержка 80ms ± 40ms (25% корреляция) и потери 2% (25% корреляция)
sudo tc qdisc add dev eth0 root netem delay 80ms 40ms 25% loss 2% 25%

# Валидация через iperf3 (на удаленном хосте запустить iperf3 -s)
iperf3 -c 192.168.1.1 -t 30
# → Скорость снизится из-за потерь, jitter будет виден в отчете
```

### Сценарий 2: Тестирование идемпотентности API

```bash
# Дублирование 5% пакетов
sudo tc qdisc add dev eth0 root netem duplicate 5%

# Проверка через curl (многократный запрос к API)
for i in {1..100}; do
  curl -s -o /dev/null -w "%{http_code}\n" http://api.example.com/resource
done | sort | uniq -c
# → Должны быть только ответы 200 или 409 (Conflict), но не 500

# Очистка после теста
sudo tc qdisc del dev eth0 root
```

### Сценарий 3: Безопасное тестирование через фильтрацию по IP

**Важно:** Применение `netem` к корню (`root`) интерфейса затронет и SSH-сессию администратора. Используйте иерархию классов для защиты управления:

```bash
# 1. Создаем корневую дисциплину 'prio'
sudo tc qdisc add dev eth0 root handle 1: prio

# 2. Добавляем netem только во второй класс (band 2)
sudo tc qdisc add dev eth0 parent 1:2 handle 10: netem delay 100ms

# 3. Направляем в netem только трафик к тестовому серверу
sudo tc filter add dev eth0 protocol ip parent 1:0 prio 1 u32 \
    match ip dst 192.168.1.50 flowid 1:2

# Проверка: SSH-сессия останется отзывчивой
ssh admin@192.168.1.100  # другой хост

# Тест: задержка применится только к 192.168.1.50
ping 192.168.1.50  # ~100ms
ping 192.168.1.1   # ~0ms (без задержки)

# Очистка
sudo tc qdisc del dev eth0 root
```

### Сценарий 4: Эмуляция изменения порядка (Reordering)

```bash
# 25% пакетов отправляются немедленно, остальные — с задержкой 10мс
sudo tc qdisc add dev eth0 root netem delay 10ms reorder 25% 50%

# Тестирование через tcpretrans (требует nping или аналогичный инструмент)
sudo tcpretrans -i eth0
# → Будут видны reordering-события
```

### Сценарий 5: Эмуляция слотов (v4.19+)

Полезно для моделирования поведения систем в сетях с временным разделением доступа (TDM).

```bash
# Пакеты уходят только во временных слотах по 5мс каждые 50мс
sudo tc qdisc add dev eth0 root netem slot 50ms 5ms

# Проверка: интервалы между пакетами должны быть кратны 50мс
ping -i 0.01 -c 50 192.168.1.1
# → Задержки будут ~50ms, 100ms, 150ms и т.д.
```

### Сценарий 6: Эмуляция входящего трафика (IFB)

Для эмуляции проблем с входящим трафиком используйте IFB:

```bash
# 1. Загрузка модуля IFB
sudo modprobe ifb

# 2. Активация интерфейса IFB
sudo ip link set ifb0 up

# 3. Перенаправление входящего трафика на IFB
sudo tc qdisc add dev eth0 handle ffff: ingress
sudo tc filter add dev eth0 parent ffff: protocol ip u32 match u32 0 0 \
    action mirred egress redirect dev ifb0

# 4. Применение netem к IFB
sudo tc qdisc add dev ifb0 root netem delay 100ms

# Проверка: задержкаapply к входящему трафику
ping -c 5 192.168.1.100  # с другого хоста
# → Задержки ~100ms

# Очистка (в обратном порядке)
sudo tc qdisc del dev ifb0 root
sudo tc qdisc del dev eth0 ingress
sudo ip link set ifb0 down
sudo modprobe -r ifb
```

### Сценарий 7: Комбинирование с HTB для шейпинга

Для точного ограничения скорости с добавлением задержки:

```bash
# 1. Создание корневой qdisc HTB
sudo tc qdisc add dev eth0 root handle 1: htb default 10

# 2. Создание класса с ограничением скорости
sudo tc class add dev eth0 parent 1: classid 1:10 htb rate 1mbit ceil 1mbit

# 3. Добавление netem к классу
sudo tc qdisc add dev eth0 parent 1:10 handle 10: netem delay 50ms loss 1%

# Проверка
tc -s qdisc show dev eth0
# → Должны отображаться и HTB, и netem

# Тест
iperf3 -c 192.168.1.1 -t 10
# → Скорость ~1Mbps с задержкой ~50ms
```

## Диагностика и мониторинг

### Проверка конфигурации

```bash
# Просмотр текущей конфигурации
tc qdisc show dev eth0

# Просмотр детальной статистики (счетчики задержанных и потерянных пакетов)
tc -s qdisc show dev eth0
# → Sent bytes, packets, dropped, overlimits
```

### Мониторинг влияния на TCP-стек

```bash
# Наблюдение за ретрансмиссиями в реальном времени
watch -n 1 'ss -ti | grep -E "retrans|cwnd"'

# Проверка глобальных счетчиков TCP
nstat -az | grep -E 'TcpRetrans|TcpLoss'
# → TcpRetransSegs: количество ретрансмиссий
# → TcpExtTCPLostRetransmit: потерянные ретрансмиссии
```

### Валидация через ping

```bash
# Базовая проверка задержки
ping -c 10 <IP>

# Проверка jitter (statistics)
ping -c 100 <IP> | tail -1
# → rtt min/avg/max/mdev = .../XX.X/.../YY.Y ms
# → mdev — это джиттер
```

### Валидация через iperf3

```bash
# На сервере
iperf3 -s

# На клиенте (с various параметрами)
iperf3 -c <SERVER_IP> -t 30 -i 1
# → В отчете будут видны: jitter, потери, реальная пропускная способность
```

## Траблшутинг

### Проблема: SSH-сессия стала медленной/нечувствительной

**Причина:** `netem` применен к корню интерфейса и затрагивает весь трафик, включая SSH.

**Решение:**
```bash
# Быстрое восстановление (если есть доступ к консоли)
sudo tc qdisc del dev eth0 root

# Профилактика: всегда используйте фильтрацию (см. Сценарий 3)
```

### Проблема: Ошибка "RTNETLINK answers: No such file or directory"

**Причина:** Модуль `sch_netem` не загружен в ядро.

**Решение:**
```bash
# Загрузка модуля
sudo modprobe sch_netem

# Проверка загрузки
lsmod | grep sch_netem

# Для автоматической загрузки при старте
echo "sch_netem" | sudo tee -a /etc/modules-load.d/netem.conf
```

### Проблема: Ошибка "RTNETLINK answers: File exists"

**Причина:** Попытка добавить `netem` когда он уже применен к интерфейсу.

**Решение:**
```bash
# Проверка текущей конфигурации
tc qdisc show dev eth0

# Удаление существующей конфигурации перед добавлением новой
sudo tc qdisc del dev eth0 root

# Или использование change вместо add
sudo tc qdisc change dev eth0 root netem delay 200ms
```

### Проблема: Задержка не применяется к входящему трафику

**Причина:** `netem` работает только на исходящем трафике.

**Решение:** Используйте IFB (см. Сценарий 6).

### Проблема: Высокое потребление CPU при больших задержках

**Причина:** `netem` буферизует пакеты в ядре, что увеличивает нагрузку.

**Решение:**
```bash
# Уменьшение размера буфера
sudo tc qdisc add dev eth0 root netem delay 100ms limit 1000

# Мониторинг CPU
top -p $(pgrep -d, tc)
```

### Проблема: Потери не отображаются в статистике

**Причина:** Счетчики `dropped` в `tc -s` показывают потери в очереди, а не эмулируемые потери.

**Решение:** Используйте `iperf3` или `ping` для валидации реальных потерь.

## Очистка среды

**Важно:** Всегда удаляйте правила `netem` после завершения тестов во избежание "фантомных" проблем.

```bash
# Удаление всех правил qdisc с интерфейса
sudo tc qdisc del dev eth0 root

# Проверка удаления
tc qdisc show dev eth0
# → Должна отображаться только default qdisc (pfifo_fast или fq_codel)

# Если использовался IFB
sudo tc qdisc del dev ifb0 root
sudo tc qdisc del dev eth0 ingress
sudo ip link set ifb0 down
```
