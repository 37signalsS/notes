# Диагностика потерь пакетов в сетевом стеке Linux (Network Stack Packet Loss)

## Определения

* **Сетевой стек Linux (Network Stack)** — набор уровней обработки сетевого трафика в ядре, от получения пакета сетевой картой до передачи данных приложению.
* **Потери в стеке (Stack Drops)** — отбрасывание пакетов ядром из-за нехватки ресурсов, переполнения очередей или правил фильтрации, даже если физический уровень (L1/L2) работает без ошибок.
* **Clean Interface** — состояние сетевого интерфейса, при котором счётчики ошибок (`RX-ERR`, `RX-DRP` в выводе `ip -s link`) равны нулю, но пакеты всё равно теряются.

## Основные концепции

Когда пакет поступает на сетевую карту, он проходит через несколько очередей и механизмов обработки. Потери могут возникнуть на любом из этих этапов:

1. **Входная очередь (Input Queue / Backlog):** Пакеты из сетевой карты передаются ядру. Если ядро не успевает их обрабатывать (перегрузка CPU или прерываний), очередь переполняется.
2. **Netfilter / Conntrack:** Механизм отслеживания соединений. Если таблица соединений полна, новые пакеты отбрасываются.
3. **Буферы сокетов (Socket Buffers):** Пакеты ожидают, пока приложение вычитает их из сокета. Если приложение работает медленно, буфер переполняется.
4. **Фильтрация трафика:** Правила `iptables`/`nftables` могут молча отбрасывать пакеты без записи в логи.

## Практические сценарии

### Сценарий 1: Общая картина и диагностика по всем слоям

Прежде чем углубляться, проверьте глобальные счётчики стека и статистику интерфейсов.

**Команды:**

```bash
# Глобальные счётчики ошибок стека
netstat -s | grep -iE "drop|fail|error|overflow"
# или современный аналог
nstat -az | grep -iE "drop|overflow"

# Статистика интерфейсов (проверка L1/L2)
ip -s link show
```

**Что искать:** Если `ip -s link` показывает `RX-DRP = 0`, а `netstat -s` показывает рост `overflow` или `drop`, проблема локализована внутри стека ядра.

---

### Сценарий 2: Переполнение очереди входящих пакетов (softnet)

Пакеты приходят быстрее, чем ядро успевает их обрабатывать и передавать выше по стеку.

**Диагностика:**

```bash
cat /proc/net/softnet_stat
```

**Интерпретация:** Каждая строка соответствует ядру CPU.

* **Первая колонка:** Общее количество обработанных пакетов.
* **Вторая колонка:** Количество пакетов, отброшенных из-за переполнения `netdev_max_backlog`.
* **Третья колонка:** Время, в течение которого обработка прерывалась (time_squeeze).

Если вторая колонка растёт — ядро не справляется.

**Решение (Тюнинг):**
Увеличьте размер очереди и лимиты буферов:

```bash
sudo sysctl -w net.core.netdev_max_backlog=5000
sudo sysctl -w net.core.rmem_max=16777216
```

Подробнее: **[Управление очередями соединений](./Concepts/tcp_tuning/tcp_connection_queues.md)**.

---

### Сценарий 3: Переполнение таблицы соединений (conntrack)

Таблица соединений Netfilter полная, и новые пакеты (или пакеты вне существующих сессий) дропаются.

**Диагностика:**

```bash
# Текущее количество и лимит
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max

# Поиск ошибок в системном логе
dmesg | grep "nf_conntrack: table full"
```

**Решение (Тюнинг):**
Если `count` близок к `max`, увеличьте лимит или очистите таблицу:

```bash
sudo sysctl -w net.netfilter.nf_conntrack_max=524288
# Очистка таблицы (требует пакет conntrack)
sudo conntrack -F
```

---

### Сценарий 4: Переполнение буферов сокетов (Socket Buffer Overflow)

Приложение не успевает вычитывать данные из сокета, что приводит к переполнению приемного буфера. Особенно критично для UDP.

**Диагностика:**

```bash
# Сводная статистика сокетов
ss -s

# Ошибки приема в UDP
netstat -su | grep "packet receive errors"

# Поиск конкретных сокетов с ненулевой очередью приема (Recv-Q)
ss -unp | awk '$2 > 0'
```

**Интерпретация:** Ненулевой `Recv-Q` (вторая колонка в `ss`) означает, что данные находятся в буфере ядра, но приложение их ещё не забрало. Если очередь достигает максимума — начинаются дропы.

---

### Сценарий 5: Скрытые правила фильтрации (iptables)

Правило в файрволе отбрасывает трафик "молча", без логирования.

**Диагностика:**

```bash
# Просмотр счётчиков правил (ищите ненулевые значения у DROP/REJECT)
sudo iptables -L -n -v | grep -v "0     0"

# Проверка таблицы NAT (частая причина проблем с пробросом)
sudo iptables -t nat -L -n -v
```

**Что искать:** Счётчики пакетов (`pkts`) и байтов (`bytes`) для правил с действием `DROP` или `REJECT`. Если они быстро растут при попытке подключения — вы нашли причину.
