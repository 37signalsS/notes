# Инструменты диагностики сети

## Определения

**Сетевая диагностика** — это процесс выявления и устранения проблем в компьютерных сетях. Он включает в себя измерение производительности, анализ трафика и проверку конфигураций для обеспечения стабильной и быстрой работы сети.

## Основные концепции

Диагностика сети оперирует тремя ключевыми метриками:

1. **Пропускная способность (Bandwidth):** Максимальное количество данных, которое может быть передано по каналу за единицу времени. Измеряется утилитами вроде `iperf3`, **[xfr](../Diagnostics/Networking/xfr.md)**.
2. **Задержка (Latency/RTT):** Время, необходимое для прохождения пакета от отправителя к получателю и обратно. Измеряется `ping` и `mtr`.
3. **Потери пакетов (Packet Loss):** Процент пакетов, которые не достигли пункта назначения. Выявляется с помощью `ping` и `mtr`.

### TTL (Time To Live)

**TTL** — это число, назначаемое пакету при отправке. Каждый маршрутизатор на пути следования пакета уменьшает это значение на 1. Если значение достигает 0, пакет отбрасывается. Это предотвращает зацикливание пакетов в сети. По умолчанию в Linux TTL обычно равно 64.

**Интерпретация TTL в ответах:**

| TTL (ответ) | ОС (начальное значение) |
| :--- | :--- |
| 64 | Linux/Unix (начальное 64) |
| 128 | Windows (начальное 128) |
| 255 | Сетевое оборудование (начальное 255) |

**Формула оценки количества хопов:**

```
Хопы = начальное_TTL - полученное_TTL
```

Инструменты делятся на несколько категорий:

* **Анализаторы сокетов:** Показывают текущие соединения и слушающие порты (`ss`). Подробно: **[Анализ сокетов с помощью ss](../Diagnostics/Networking/ss.md)**.
* **Измерители производительности:** Тестируют реальную пропускную способность (`iperf3`, **[xfr](../Diagnostics/Networking/xfr.md)**). Подробно: **[iperf3](../Diagnostics/Networking/iperf3.md)**, **[xfr](../Diagnostics/Networking/xfr.md)**.
* **Инструменты трассировки:** Отслеживают маршрут пакетов и задержки на каждом узле (`mtr`, `traceroute`). Подробно: **[traceroute и mtr](../Diagnostics/Networking/traceroute_mtr.md)**.
* **Анализаторы трафика:** Перехватывают и декодируют сетевые пакеты для глубокого анализа (`tcpdump`, `wireshark`). Подробно: **[tcpdump](../Diagnostics/Networking/tcpdump.md)**.
* **Базовая проверка доступности:** `ping`, `nc`. Подробно: **[ping](../Diagnostics/Networking/ping.md)**.
* **TUI-инструменты:** Интерактивный мониторинг в реальном времени (`iftop`, `nload`, `snitch`, `iptraf-ng`). Подробно: **[Сетевые инструменты CLI и TUI](../Diagnostics/Networking/network_cli_tools.md)**.
* **Диагностика DNS:** `dig`, `nslookup`, `resolvectl`. Подробно: **[Диагностика DNS](../Diagnostics/Networking/dns/overview.md)**.
* **Диагностика HTTP/HTTPS:** `curl`. Подробно: **[Диагностика сетевых задержек с cURL](../Diagnostics/Networking/curl_network_diagnostics.md)**.

## Практические сценарии

### Сценарий 1: Проверка доступности порта и сервиса

**Задача:** Убедиться, что порт на удаленном хосте открыт и сервис на нем отвечает.
**Инструмент:** `nc` (netcat).

```bash
# Проверить доступность TCP-порта 443 на хосте example.com
nc -zv example.com 443

# Проверить доступность UDP-порта 53 на DNS-сервере
nc -zvu 8.8.8.8 53

# Проверить порт с указанием таймаута (в секундах)
nc -zv -w 3 example.com 443
```

* `Connection succeeded`: Порт открыт.
* `Connection refused`: Порт закрыт, сервис не запущен.
* `Connection timed out`: Пакеты блокируются (например, firewall).
* `-z`: Режим сканирования портов (без отправки данных).
* `-v`: Подробный вывод.
* `-u`: Использовать UDP вместо TCP.
* `-w`: Таймаут в секундах.

**NC для диагностики проблем с файрволом:**

NC позволяет определить, блокирует ли файрвол трафик. Если при подключении к открытому порту вы видите долгое ожидание (таймаут), это может означать, что файрвол молча отбрасывает пакеты (DROP). Если вы получаете "Connection refused", это означает, что порт закрыт (REJECT).

> **Примечание:** Для более сложных сценариев обхода firewall см. **[hping3 и tcping](../../Networking/Troubleshooting/ping_alternatives.md)**.

### Сценарий 2: Измерение реальной пропускной способности канала

**Задача:** Измерить максимальную скорость между двумя серверами.
**Инструменты:** `iperf3`, **[xfr](../Diagnostics/Networking/xfr.md)**.

```bash
# На сервере (принимающей стороне)
iperf3 -s

# На клиенте (отправляющей стороне)
iperf3 -c <IP-адрес сервера>

# Для проверки обратного канала (сервер -> клиент)
iperf3 -c <IP-адрес сервера> -R

# Многопоточный тест (10 потоков) для насыщения канала
iperf3 -c <IP-адрес сервера> -P 10

# Тест длительностью 60 секунд для стабильных результатов
iperf3 -c <IP-адрес сервера> -t 60
```

**Современная альтернатива — xfr (Rust):**

```bash
# Сервер
xfr server

# Клиент с TUI (интерактивный режим)
xfr client <IP-адрес сервера> --tui

# Клиент с JSON-выводом для автоматизации
xfr client <IP-адрес сервера> --json
```

Асимметрия скорости в прямом и обратном канале — частая проблема. Для точных результатов используйте многопоточный тест (`-P 10`) и длительные измерения (60 секунд).

### Сценарий 3: Поиск узкого места в сети (потери и задержки)

**Задача:** Определить, на каком участке сети происходят потери пакетов или возникает высокая задержка.
**Инструмент:** `mtr`.

```bash
# Запустить трассировку до хоста с отправкой 100 пакетов
mtr -rwzc 100 example.com
```

**Интерпретация вывода mtr:**

| Колонка | Описание |
| :--- | :--- |
| **Loss%** | Процент потерянных пакетов на хопе |
| **Snt** | Количество отправленных пакетов |
| **Last** | Последняя задержка (мс) |
| **Avg** | Средняя задержка (мс) |
| **Best** | Лучшая задержка (мс) |
| **Wrst** | Худшая задержка (мс) |
| **StDev** | Стандартное отклонение (стабильность) |

**Типичные проблемы:**

* **Высокие потери на одном хопе:** Если один узел показывает 100% потерь, но последующие отвечают нормально — маршрутизатор настроен не отвечать на ICMP/UDP. Это не проблема.
* **Нарастающие потери:** Если потери начинаются с определённого хопа и продолжаются до конца — реальная проблема на этом участке.
* **Высокий StDev:** Нестабильность канала (jitter).
* **Резкое увеличение Avg/Wrst:** Изменение маршрута или «бутылочное горлышко».

> **Примечание:** Для разовой трассировки без интерактива используйте `traceroute -T -p 80 example.com` (TCP-режим для обхода firewall).

### Сценарий 4: Анализ текущих соединений и производительности TCP

**Задача:** Посмотреть, какие процессы держат порты, и проверить состояние TCP-сессий.
**Инструменты:** `ss`, **[snitch](../Diagnostics/Networking/network_cli_tools.md)**.

```bash
# Показать все слушающие TCP и UDP порты с PID процессов
sudo ss -tulpn

# Все установленные TCP-соединения
ss -t state established

# Расширенная TCP-информация (RTT, cwnd, retransmits)
ss -ti

# Сводная статистика по протоколам
ss -s

# Соединения с конкретным портом
ss -t '( dport = :443 or sport = :443 )'
```

**Ключевые состояния TCP:**

* **LISTEN:** Сервер ожидает входящих подключений
* **SYN-SENT:** Клиент отправил SYN (возможна проблема с сетью/firewall)
* **SYN-RECV:** Сервер получил SYN (возможен [SYN-flood](../../Security/Concepts/dos_protection.md))
* **ESTABLISHED:** Соединение установлено
* **TIME-WAIT:** Соединение закрывается (большое количество требует [TCP-tuning](./Concepts/tcp_tuning/tcp_time_wait_management.md))

Подробное руководство по использованию `ss`, включая анализ `retransmits` и `RTT`, находится в специальной заметке: **[Анализ сокетов с помощью ss](../Diagnostics/Networking/ss.md)**.

**TUI-инструменты для мониторинга в реальном времени:**

* **[snitch](../Diagnostics/Networking/network_cli_tools.md)** — «htop для сети» (процессы + сокеты)
* **iftop** — трафик по соединениям (как `top` для сети)
* **nload/bmon** — общая нагрузка на интерфейс (графики)
* **iptraf-ng** — комбайн с детальной статистикой

### Сценарий 5: Комплексный порядок диагностики

**Методология «от простого к сложному»:**

| Шаг | Задача | Инструмент | Что проверяем |
| :--- | :--- | :--- | :--- |
| **1** | Проверка DNS | `ping`, `dig`, `nslookup` | Разрешается ли имя в IP |
| **2** | Базовая связность | `ping`, `mtr` | Доступность хоста, потери, задержки |
| **3** | Проверка портов | `nc`, `telnet` | Открыт ли порт сервиса |
| **4** | Анализ соединений | `ss`, `snitch` | Активные сессии, процессы |
| **5** | Пропускная способность | `iperf3`, `xfr` | Реальная скорость канала |
| **6** | Глубокий анализ | `tcpdump`, `wireshark` | Содержимое пакетов |

**Пример диагностики «не работает сайт»:**

```bash
# 1. Проверка DNS
ping -c 1 example.com
# Видим IP → DNS работает
# Ошибка → проблема с DNS (см. [Диагностика DNS](../Diagnostics/Networking/dns/overview.md))

# 2. Проверка связности
ping -c 10 example.com
# Потери >0% или высокий RTT → проблема в сети (см. mtr ниже)

# 3. Проверка порта (HTTP/HTTPS)
nc -zv example.com 443
# Connection refused → сервис не запущен
# Timed out → блокируется firewall

# 4. Поиск узкого места
mtr -rwzc 100 example.com
# Потери на конкретном хопе → проблема у провайдера

# 5. Анализ соединений (если проблема на сервере)
sudo ss -tulpn | grep :443
# Нет слушающего порта → сервис не запущен

# 6. Глубокий анализ (если предыдущие шаги не выявили проблему)
sudo tcpdump -i eth0 -nn 'host example.com and port 443'
```
