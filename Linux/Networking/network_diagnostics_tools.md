# Инструменты диагностики сети

## Определения

**Сетевая диагностика** — это систематический процесс выявления, анализа и устранения проблем в компьютерных сетях. Она включает в себя мониторинг доступности, измерение производительности, глубокий анализ трафика и верификацию конфигураций сетевого стека ОС и оборудования.

## Основные концепции

Эффективная диагностика опирается на три фундаментальные метрики:

1. **Пропускная способность (Bandwidth):** Максимальный объем данных, передаваемый по каналу в единицу времени. Инструменты: `iperf3`, **[xfr](../Diagnostics/Networking/xfr.md)**.
2. **Задержка (Latency/RTT):** Время прохождения пакета до узла и обратно. Инструменты: `ping`, `mtr`, `tcprtt` (eBPF).
3. **Потери пакетов (Packet Loss):** Процент пакетов, не достигших цели. Инструменты: `ping`, `mtr`, `nstat`.

### Методология диагностики (Bottom-up)

Диагностика должна следовать иерархии уровней (от простого к сложному):

1. **Физический уровень и L2:** Проверка линка, ошибок на интерфейсе и ARP-соседей.
2. **Сетевой уровень (L3):** IP-адресация, маршрутизация и ICMP-связность.
3. **Транспортный уровень (L4):** Доступность портов, состояние TCP-сессий.
4. **Прикладной уровень (L7):** DNS-резолвинг, HTTP-ответы, логи приложения.

### Категории инструментов

| Категория | Инструменты | Назначение |
| :--- | :--- | :--- |
| **Базовая связность** | `ping`, `arping` | Проверка доступности по IP/MAC. |
| **Трассировка пути** | `mtr`, `traceroute` | Поиск узких мест и потерь на маршруте. |
| **Анализ сокетов** | `ss`, `lsof` | Активные соединения, слушающие порты, PID процессов. |
| **Производительность** | `iperf3`, `xfr`, `ethtool` | Тест скорости, аппаратная статистика (дропы). |
| **Сканирование** | `nmap` | Обнаружение хостов и открытых портов. |
| **Анализ трафика** | `tcpdump`, `termshark` | Перехват и разбор «сырых» пакетов. |
| **Прикладной уровень** | `curl`, `dig`, `resolvectl` | Диагностика HTTP/HTTPS и DNS. |
| **eBPF (Observability)** | `pwru`, `bpftrace` | Глубокая трассировка пакетов внутри ядра. |
| **Firewall** | `nft`, `conntrack` | Анализ правил фильтрации и таблицы состояний. |

## Практические сценарии

### Сценарий 1: Проверка доступности порта (L4)

**Задача:** Убедиться, что порт на удаленном хосте открыт и не блокируется.

```bash
# Проверить TCP-порт 443 (HTTPS)
nc -zv example.com 443
# → Connection to example.com 443 port [tcp/https] succeeded!

# Проверить UDP-порт 53 (DNS) с таймаутом 2с
nc -zvu -w 2 8.8.8.8 53
# → Connection to 8.8.8.8 53 port [udp/domain] succeeded!
```

**Интерпретация результатов:**
- `succeeded`: Порт открыт.
- `Connection refused`: Порт закрыт ОС сервера (сервис не запущен).
- `Timed out`: Пакеты отбрасываются (DROP) файрволом.

### Сценарий 2: Тестирование пропускной способности (L3-L4)

**Задача:** Измерить реальную скорость между двумя узлами.

```bash
# На сервере (приёмник)
iperf3 -s

# На клиенте (отправитель), 10 потоков, 20 секунд
iperf3 -c <server_ip> -P 10 -t 20
# → [SUM]   0.00-20.00  sec  22.4 GBytes  9.62 Gbits/sec  sender
```

Для современных систем рекомендуется **[xfr](../Diagnostics/Networking/xfr.md)** из-за поддержки QUIC и встроенного TUI.

### Сценарий 3: Аппаратная диагностика и глобальные счётчики

Если сеть «тормозит» или есть потери, которые не видит `ping`, проверьте счётчики ядра и сетевой карты.

```bash
# Ошибки и дропы на уровне драйвера/железа
sudo ethtool -S eth0 | grep -E "error|drop|miss"
# → rx_dropped: 124 (сигнал о переполнении буферов)

# Глобальная статистика TCP/IP (современная замена netstat -s)
nstat -az | grep -E "TcpExtListenDrops|TcpRetransSegs"
# → TcpExtListenDrops 45 (очередь accept переполнена)
```

### Сценарий 4: Глубокая трассировка с eBPF

Если пакет входит в сервер (виден в `tcpdump`), но приложение его не получает, используйте `pwru`, чтобы найти место дропа внутри ядра.

```bash
# Отслеживание пути пакета до порта 80
sudo pwru --filter-dst-port 80
# → [timestamp] netif_receive_skb -> ip_rcv -> nft_do_chain -> [DROP]
```

### Сценарий 5: Диагностика DNS

В системах с `systemd-resolved` классический `cat /etc/resolv.conf` может быть неинформативен.

```bash
# Проверка текущих DNS-серверов и их статуса
resolvectl status

# Прямой запрос через системный резолвер
resolvectl query google.com
# → google.com: 142.250.186.206 -- link: eth0
```

## Порядок комплексной диагностики

При возникновении проблемы следуйте алгоритму:

1.  **`ip -br link`** — Поднят ли интерфейс (UP/LOWER_UP)?
2.  **`ip -c addr`** — Назначен ли корректный IP?
3.  **`ping -c 3 <gateway_ip>`** — Виден ли шлюз?
4.  **`resolvectl query google.com`** — Работает ли DNS?
5.  **`nc -zv <target_ip> <port>`** — Доступен ли порт приложения?
6.  **`mtr -rwzc 100 <target_ip>`** — Где начинаются потери в пути?
7.  **`ss -tulpn`** — Слушает ли приложение порт на нужном интерфейсе?
