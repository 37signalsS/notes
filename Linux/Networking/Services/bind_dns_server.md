# Настройка DNS-сервера BIND

## Определения

*   **BIND (Berkeley Internet Name Domain)** — это наиболее распространенное и широко используемое программное обеспечение для реализации DNS-сервера в Интернете.
*   **DNS (Domain Name System)** — распределенная система для преобразования доменных имен в IP-адреса. Подробное описание протокола находится в основной заметке: **[Протокол DNS](../../../Networking/Protocols/dns.md)**.

## Базовые концепции

BIND реализует полную спецификацию протокола DNS и может выполнять несколько ролей, которые определяют его поведение. Основные типы серверов подробно описаны в основной заметке о **[протоколе DNS](../../../Networking/Protocols/dns.md#типы-dns-серверов)**.

В контексте BIND чаще всего выделяют следующие конфигурации:

*   **Авторитативный сервер (Authoritative)**: Сервер, который хранит официальную информацию о доменной зоне и является первоисточником ответов на запросы о ней. Если такой сервер не находит имя в своей зоне, он авторитетно заявляет, что оно не существует, и дальнейшая рекурсия прекращается.
*   **Кэширующий/рекурсивный сервер (Caching/Recursive)**: Сервер, который принимает запросы от клиентов (например, от компьютеров в локальной сети), находит ответы в глобальной системе DNS и кэширует их. Это ускоряет последующие запросы к тем же доменам, снижая задержки и общую нагрузку на сеть, так как большая часть сотрудников, вероятно, обращается к одним и тем же ресурсам.

*   **Перенаправляющий DNS-сервер (Forwarding DNS Server)**: С точки зрения клиента, перенаправляющий сервер работает аналогично кэширующему, но механизм его работы совершенно иной. Он не выполняет рекурсивные запросы сам, вместо этого он перенаправляет все запросы (не найденные в его кэше) на внешние разрешающие серверы (форвардеры), а затем кэширует полученные от них ответы для последующих запросов.
    *   **Преимущества**:
        *   Снижение нагрузки на сервер: не обрабатывает полную процедуру рекурсии и итерирования.
        *   Экономия внешней пропускной способности: обрабатывается одиночный запрос к внешнему форвардеру, а не множество итераций.
        *   Использование кэша: как и кэширующий сервер, обслуживает запросы из своего кэша.
        *   Удобство для ограниченной внешней пропускной способности или миграции кэширующих серверов.
*   **Первичный (Master) и Вторичный (Slave) сервер**: Эта пара используется для отказоустойчивости.
    *   **Первичный (Master)**: Основной сервер, на котором администратор редактирует файлы зоны.
    *   **Вторичный (Slave)**: Автоматически копирует все данные (этот процесс называется **трансфер зоны**) с первичного сервера. Он обслуживает запросы, распределяя нагрузку и обеспечивая доступность DNS, если первичный сервер выйдет из строя.

## Практические сценарии

### 1. Установка BIND

Установка пакета `bind9` и утилит для диагностики DNS. Пакет `dnsutils` содержит ключевые инструменты (`dig`, `nslookup`), необходимые для проверки и отладки DNS-сервера. Подробнее об их использовании см. в заметке **[Диагностика DNS](../../../Linux/Diagnostics/Networking/dns_diagnostics.md)**.
```bash
sudo apt-get update
sudo apt-get install -y bind9 dnsutils
sudo systemctl enable --now bind9
```

### 2. Базовая конфигурация (`/etc/bind/named.conf.options`)

Этот файл содержит общие настройки сервера.

```
// Определяем ACL (Access Control List) для внутренних клиентов
// Эта секция должна быть до блока options
acl "my_clients" {
    192.168.0.0/24; // Пример внутренней подсети
    127.0.0.1;      // Локальный хост
    localnets;      // Все сети, к которым подключен данный хост
    // Включение 'localnets' автоматически включает все IP-адреса,
    // назначенные сетевым интерфейсам хоста.
};

options {
    directory "/var/cache/bind";
    
    // Включаем перенаправление запросов на внешние DNS-серверы.
    // Если сервер не может разрешить запрос из своего кэша, он будет перенаправлен.
    // Для работы перенаправляющего сервера необходимо явно указать forward only;
    forwarders {
        8.8.8.8;
        1.1.1.1;
    };
    forward only; // Сервер будет только перенаправлять запросы, но не выполнять рекурсию самостоятельно.
    
    // Если нужен рекурсивный сервер (без форвардинга), установите 'yes' и настройте 'allow-recursion'.
    // В случае перенаправляющего сервера, эта опция управляет, разрешать ли внешним клиентам использовать его для рекурсии.
    recursion yes; 

    // Указываем, на каких IP-адресах сервер будет принимать запросы.
    // По умолчанию BIND слушает на всех доступных интерфейсах (listen-on { any; }).
    // Для повышения безопасности рекомендуется указывать конкретные IP-адреса.
    listen-on { 172.16.0.5; 127.0.0.1; };
    
    // Разрешаем запросы только от клиентов, определенных в ACL "my_clients".
    // Без этой опции сервер будет отвечать на запросы от любых IP-адресов.
    allow-query { my_clients; };

    // Указывает BIND, где искать корневые серверы DNS (dot-zone).
    // Точка "." представляет собой корневую зону DNS, невидимую в обычных браузерах.
    // Это значение по умолчанию, но его можно явно указать.
    zone "." {
        type hint;
        file "db.root";
    };
    
    dnssec-validation auto;
    listen-on-v6 { any; };
};
```
**Проверка синтаксиса:**
```bash
sudo named-checkconf
```

### 3. Настройка перенаправляющего DNS-сервера (Forwarding DNS Server)

Перенаправляющий DNS-сервер позволяет сократить нагрузку на BIND, делегируя рекурсивные запросы внешним DNS-серверам (форвардерам).

1.  **Измените конфигурационный файл `/etc/bind/named.conf.options`:**
    ```
    options {
        directory "/var/cache/bind";
        
        // Серверы, на которые будут перенаправляться все запросы, которые не могут быть разрешены из кэша.
        forwarders {
            8.8.8.8; // Пример: Google Public DNS
            1.1.1.1; // Пример: Cloudflare DNS
        };
        // Обязательно: BIND будет только перенаправлять запросы, но не выполнять рекурсию самостоятельно.
        forward only; 

        // Если вы хотите, чтобы сервер принимал рекурсивные запросы от клиентов,
        // но при этом перенаправлял их дальше (как настроено выше), установите recursion yes;
        // Если сервер должен обслуживать только внешних клиентов, установите recursion no;
        recursion yes; 

        // Указываем, на каких IP-адресах сервер будет принимать запросы.
        listen-on { 172.16.0.5; 127.0.0.1; };
        
        // Для повышения безопасности, особенно если сервер не знает ответа.
        // Можно включить, если возникнут ошибки, но обычно не требуется для базовой работы.
        // dnssec-validation yes;
        // dnssec-enable yes;

        dnssec-validation auto;
        listen-on-v6 { any; };
    };
    ```
    **Пояснения к параметрам:**
    *   `forwarders { ... };`: Определяет список IP-адресов DNS-серверов, которым будут перенаправляться запросы.
    *   `forward only;`: Указывает BIND, что он должен **только** перенаправлять запросы. Если форвардеры не отвечают, сервер не будет пытаться выполнить рекурсию самостоятельно, а просто вернет ошибку клиенту.
    *   `forward first;`: При этой опции BIND сначала попытается перенаправить запрос, а если форвардеры не ответят, то выполнит рекурсию самостоятельно.
    *   `recursion yes;`: Разрешает серверу принимать рекурсивные запросы от клиентов (даже если он сам их не обрабатывает, а перенаправляет). Для внутренней сети обычно `yes`. Если сервер не должен отвечать на рекурсивные запросы (например, для внешнего использования), следует использовать `recursion no;` и настроить `allow-recursion` для конкретных IP-адресов.

2.  **Проверка синтаксиса и перезапуск службы:**
    ```bash
    sudo named-checkconf
    sudo systemctl restart bind9
    ```

3.  **Проверка работы на клиенте (пример):**
    Убедитесь, что клиент использует ваш перенаправляющий DNS-сервер (например, путем изменения `nameserver` в `/etc/resolv.conf` на IP вашего BIND-сервера). Затем выполните `dig` запрос.
    ```bash
    dig rambler.ru
    ```
    В ответе `dig` обратите внимание на секцию `;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: ...`, где `status: NOERROR` указывает на успешное разрешение. Также `AUTHORITY: 0` означает, что ответ получен не от авторитативного сервера, а от рекурсивного/перенаправляющего.

### 4. Настройка первичного (Master) DNS-сервера для локальной сети

Этот сценарий показывает, как настроить BIND в качестве авторитативного DNS-сервера для вашей внутренней сети (например, `local.lan`), чтобы он мог разрешать имена локальных хостов (например, `server1.local.lan`).

#### 4.1. Описание зоны в `named.conf.local`

Сначала в файле `/etc/bind/named.conf.local` объявляется новая зона, за которую будет отвечать наш сервер.

```
// /etc/bind/named.conf.local

zone "local.lan" {
    type master;
    file "/etc/bind/zones/db.local.lan"; // Путь к файлу с записями зоны
    allow-transfer { 172.16.0.6; };      // IP-адрес вторичного (slave) сервера, если он есть
};
```

#### 4.2. Создание файла зоны

1.  **Создайте директорию для файлов зон:**
    ```bash
    sudo mkdir -p /etc/bind/zones
    sudo chown bind:bind /etc/bind/zones
    ```

2.  **Используйте шаблон для создания файла зоны:**
    Чтобы не писать файл с нуля, удобно скопировать существующий шаблон `db.local`.
    ```bash
    sudo cp /etc/bind/db.local /etc/bind/zones/db.local.lan
    ```

3.  **Отредактируйте файл зоны:**
    Откройте `/etc/bind/zones/db.local.lan` и приведите его к следующему виду.

    ```
    ;
    ; BIND data file for local.lan
    ;
    $TTL    604800
    @       IN      SOA     ns1.local.lan. root.local.lan. (
                                  2         ; Serial (увеличивать при каждом изменении!)
                             604800         ; Refresh
                              86400         ; Retry
                            2419200         ; Expire
                             604800 )       ; Negative Cache TTL
    ;
    ; NS и A записи для самого домена
    @       IN      NS      ns1.local.lan.
    ns1     IN      A       192.168.52.149

    ; A-записи для других хостов в сети
    dnsserver   IN      A       192.168.52.149
    server1     IN      A       192.168.52.150
    ```
    - **`@`**: Обозначает саму зону (`local.lan`).
    - **`SOA`**: Start of Authority, основная запись, описывающая зону. `ns1.local.lan.` — имя первичного DNS-сервера, `root.local.lan.` — email администратора (точка вместо `@`).
    - **`Serial`**: Серийный номер. **Критически важно увеличивать его после каждого изменения**, чтобы вторичные серверы знали, что нужно обновить данные.
    - **`NS`**: Указывает на DNS-сервер (`Name Server`) для этой зоны.
    - **`A`**: Сопоставляет имя хоста с IPv4-адресом.

#### 4.3. Проверка и применение

1.  **Проверьте синтаксис конфигурации BIND и файла зоны:**
    ```bash
    # Проверка основных конфигов
    sudo named-checkconf

    # Проверка синтаксиса файла зоны
    sudo named-checkzone local.lan /etc/bind/zones/db.local.lan
    ```
    Если обе команды завершились без ошибок, можно продолжать.

2.  **Перезапустите BIND:**
    ```bash
    sudo systemctl restart bind9
    ```

#### 4.4. Верификация

Теперь можно проверить, что сервер отвечает за новую зону. Выполните `dig` с клиента, который использует ваш BIND-сервер.

```bash
dig dnsserver.local.lan
```
В выводе вы должны увидеть `A`-запись и, что самое главное, флаг `status: NOERROR` и `AUTHORITY: 1` в секции `HEADER`. Это означает, что ответ был получен от авторитативного сервера для этой зоны.
```
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12345
;; flags: qr aa rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 1, ADDITIONAL: 1
```
- `aa` (Authoritative Answer): флаг, подтверждающий, что ответ является авторитативным.


### 5. Настройка вторичного (Slave) DNS-сервера

1.  Установите `bind9` и `dnsutils` так же, как на первичном сервере.
2.  В файле `/etc/bind/named.conf.local` укажите зону как `slave`:
    ```
    zone "test.example.com" {
        type slave;
        file "/var/lib/bind/test.example.com.zone"; // BIND будет хранить копию здесь
        masters { 172.16.0.5; }; // IP-адрес первичного сервера
    };
    ```
3.  Перезагрузите BIND. Он автоматически попытается получить копию зоны с `master`-сервера.

### 6. Настройка обратной зоны (Reverse Zone)

Обратная зона используется для определения имени хоста по его IP-адресу с помощью **[PTR-записей](../../../Networking/Protocols/dns.md#ptr--запись-указатель-обратные-зоны)**.

#### 5.1. Описание и создание файла зоны

В `/etc/bind/named.conf.local` на первичном сервере:
```
zone "16.172.in-addr.arpa" {
    type master;
    file "/etc/bind/zones/rev.16.172.in-addr.arpa";
    allow-transfer { 172.16.0.6; };
};
```
Файл `/etc/bind/zones/rev.16.172.in-addr.arpa`:
```
$TTL 3600
@ IN SOA ns1.test.example.com. admin.test.example.com. (
    1
    3h
    1h
    1w
    1h )
IN NS ns1.test.example.com.
IN NS ns2.test.example.com.

; PTR-записи (последние два октета IP-адреса в обратном порядке)
5.0     IN PTR ns1.test.example.com.
6.0     IN PTR ns2.test.example.com.
101.3   IN PTR host.test.example.com.
```
На вторичном сервере настройка аналогична, только `type slave`.

## Расширенные детали

### 1. Использование представлений (Views)

Представления (views) позволяют отдавать разные ответы на DNS-запросы в зависимости от того, из какой сети пришел запрос. Это полезно для разделения внутреннего и внешнего DNS.

В файле `/etc/bind/named.conf` настраиваем представления:
```
// Определяем ACL (Access Control List) для внутренней сети
acl "internal-net" { 172.16.0.0/16; 127.0.0.1; };

// Представление для внутренних клиентов
view "internal" {
    match-clients { internal-net; };
    recursion yes; // Разрешаем рекурсию для своих

    // Подключаем внутренние зоны
    include "/etc/bind/named.conf.local"; 
};

// Представление для всех остальных (внешних)
view "external" {
    match-clients { any; };
    recursion no; // Запрещаем рекурсию для чужих

    // Здесь можно подключить файл с публичными зонами
    // zone "public-example.com" { ... };
};
```

### 2. Логирование

Для отладки можно настроить детальное логирование. Создайте директорию для логов, доступную для BIND:
```bash
sudo mkdir /var/log/named
sudo chown bind:bind /var/log/named
# Настройте AppArmor, если он используется
# sudo nano /etc/apparmor.d/local/usr.sbin.named
# ... и добавьте: /var/log/named/** rw,
```

Подключите логирование в `/etc/bind/named.conf`:
```
logging {
    channel query.log {
        file "/var/log/named/query.log" versions 5 size 10m;
        severity info;
        print-time yes;
    };
    category queries { query.log; };
};
```
После настройки перезагрузите BIND.
