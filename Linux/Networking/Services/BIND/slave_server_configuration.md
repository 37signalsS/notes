# Настройка вторичного сервера DNS в BIND

## Определения

**Вторичный сервер (Secondary / Slave)** — авторитативный **DNS (Domain Name System — система доменных имён)** сервер, который автоматически получает копию данных зоны с первичного (**Primary / Master**) сервера через механизм зонной передачи.

**Зонная передача (Zone Transfer)** — процесс синхронизации данных зоны между серверами с использованием протоколов **AXFR (Authoritative Transfer — полная передача зоны)** или **IXFR (Incremental Zone Transfer — инкрементальная передача зоны)**.

**TSIG (Transaction Signature — подпись транзакции)** — механизм обеспечения безопасности (RFC 2845), использующий общие секретные ключи для аутентификации и проверки целостности сообщений между серверами DNS, особенно при зонных передачах.

## Базовые концепции

### Алгоритм синхронизации данных

Процесс обновления данных на вторичном сервере следует строгому регламенту:

| Этап | Описание |
| :--- | :--- |
| 1 | Вторичный сервер запрашивает запись **SOA (Start of Authority — начальная запись зоны)** у первичного сервера. |
| 2 | Сравнивает серийный номер (**Serial**) полученной записи с текущей локальной версией. |
| 3 | Если Serial на первичном сервере больше → инициируется запрос на передачу зоны (**AXFR** или **IXFR**). |
| 4 | Полученные данные сохраняются в локальный файл зоны. |

### Механизмы NOTIFY и трансфера

*   **NOTIFY (RFC 1996):** механизм, при котором первичный сервер немедленно уведомляет вторичные серверы об изменении зоны, не дожидаясь истечения таймера `Refresh`.
*   **Инкрементальный трансфер (IXFR):** передача только изменённых ресурсных записей вместо всей зоны, что критично для больших зон и экономии трафика.
*   **Формат файлов:** современные версии BIND (9.16+) по умолчанию сохраняют файлы вторичных зон в бинарном формате (`raw`) для ускорения загрузки. Для сохранения в текстовом виде используется параметр `masterfile-format text;`.

## Практические сценарии

### 1. Настройка вторичного сервера (Secondary)

**Файл `/etc/bind/named.conf.local` на стороне Secondary:**

```conf
zone "corp.local" {
    type slave; // В BIND ключевое слово остается 'slave' для совместимости
    file "/var/lib/bind/db.corp.local.slave"; // Директория с правами на запись
    masters { 192.168.10.10; };               // IP (Internet Protocol) адрес Master-сервера
    masterfile-format text;                   // Сохранять в читаемом текстовом формате
};
```

**Права доступа (Debian/Ubuntu):**
Демон `named` должен иметь права на запись в директорию для сохранения полученных зон.
```bash
sudo chown bind:bind /var/lib/bind
sudo chmod 775 /var/lib/bind
```

### 2. Настройка первичного сервера (Primary)

Чтобы трансфер прошёл успешно, Master должен разрешить передачу данных конкретному **IP** или использовать **TSIG**.

**Файл `/etc/bind/named.conf.local` на стороне Primary:**

```conf
zone "corp.local" {
    type master;
    file "/etc/bind/zones/db.corp.local";
    allow-transfer { 192.168.10.20; }; // Разрешить трансфер только вторичному серверу
    also-notify { 192.168.10.20; };    // Принудительное уведомление об обновлениях
};
```

### 3. Использование TSIG для защиты трансфера

**TSIG** рекомендуется для защиты от подмены данных и несанкционированного получения всей зоны.

1.  **Генерация ключа:**
    ```bash
    tsig-keygen -a HMAC-SHA256 transfer-key > /etc/bind/transfer.key
    ```
2.  **Подключение ключа на обоих серверах:**
    ```conf
    include "/etc/bind/transfer.key";
    ```
3.  **Применение в конфигурации зоны:**
    ```conf
    // На стороне Master
    allow-transfer { key "transfer-key"; };
    
    // На стороне Secondary
    server 192.168.10.10 {
        keys { "transfer-key"; };
    };
    ```

## Проверка и диагностика

### Верификация синхронизации

После перезапуска или выполнения `rndc reload` проверьте наличие зонного файла и соответствие серийного номера.

```bash
# Проверка SOA на вторичном сервере
dig @127.0.0.1 corp.local SOA +short
# → 2025072501 (должен совпадать с Master)

# Проверка системного журнала
sudo journalctl -u bind9 -n 50 | grep "transfer"
# → transfer of 'corp.local/IN' from 192.168.10.10#53: Transfer status: success
```

### Типовые неисправности

*   **Порт TCP/53:** трансферы (**AXFR/IXFR**) всегда используют **TCP (Transmission Control Protocol)**. Убедитесь, что он открыт в брандмауэре.
*   **Permission Denied:** проверьте профили **AppArmor** или **SELinux** на стороне вторичного сервера, если запись файла не удается.
*   **Serial Number:** трансфер не начнётся, если Serial на мастере не был увеличен.

**Ручной принудительный трансфер:**
```bash
dig @192.168.10.10 corp.local AXFR
```
