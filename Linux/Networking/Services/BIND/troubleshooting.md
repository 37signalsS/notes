# Диагностика и устранение неисправностей BIND

## Определения

**named-checkconf** — специализированная утилита для проверки синтаксиса конфигурационных файлов BIND.

**named-checkzone** — утилита для проверки корректности файлов зонных данных (соответствие синтаксису и наличие обязательных записей).

**rndc (Remote Name Daemon Control — удалённое управление демоном имён)** — утилита командной строки для безопасного управления запущенным сервером BIND.

## Базовые концепции

### Уровни диагностики

Эффективный поиск неисправностей в BIND требует последовательной проверки нескольких уровней:

| Уровень | Назначение | Инструменты |
| :--- | :--- | :--- |
| **Конфигурация** | Проверка синтаксиса файлов и зон | `named-checkconf`, `named-checkzone` |
| **Служба** | Проверка состояния процесса и системных логов | `systemctl status`, `journalctl` |
| **Сеть** | Проверка доступности портов и интерфейсов | `ss`, `netstat`, `tcpdump` |
| **Разрешение** | Тестирование корректности ответов DNS | `dig`, `nslookup`, `host` |
| **Управление** | Взаимодействие с запущенным демоном | `rndc` |

### Коды ответов DNS (RCODE)

Результат выполнения DNS-запроса возвращается в поле **RCODE (Response Code — код ответа)** заголовка сообщения. Понимание этих кодов критически важно для диагностики:

- `NOERROR` — успешное выполнение.
- `NXDOMAIN` — доменное имя не существует.
- `SERVFAIL` — ошибка на стороне сервера.
- `REFUSED` — запрос отклонён (обычно из-за настроек **ACL (Access Control List — список контроля доступа)**).

Подробное описание всех кодов представлено в разделе **[Коды ответов RCODE](../../../../Networking/Protocols/DNS/dns_message_format.md#коды-ответов-rcode)**.

## Практические сценарии

### 1. Проверка конфигурации перед применением

Всегда проверяйте конфигурацию перед перезагрузкой сервера, чтобы избежать простоя.

```bash
# Проверка основных файлов конфигурации
sudo named-checkconf

# Проверка конкретной зоны (например, example.com)
sudo named-checkzone example.com /etc/bind/zones/db.example.com
```

**Ожидаемый вывод при успехе:** `OK`.

### 2. Анализ состояния службы и системных журналов

Если BIND не запускается, первым делом изучите вывод `systemctl` и журнал `journald`.

```bash
# Проверка статуса службы
systemctl status bind9

# Просмотр последних 50 записей в системном журнале
journalctl -u bind9 -n 50
```

**Типовые проблемы:**

- `failed to start`: ошибка синтаксиса (используйте `named-checkconf`).
- `permission denied`: некорректные права доступа на файлы или директории (рекомендуется `chown bind:bind`).
- `no TTL specified`: отсутствие директивы **$TTL (Time To Live — время жизни записи)** в начале файла зоны.

### 3. Проверка сетевой доступности (Порт 53)

BIND должен слушать порт `53` по протоколам UDP и TCP на необходимых интерфейсах.

```bash
# Проверка открытых сокетов
ss -tlnp | grep :53
ss -ulnp | grep :53
```

Если порты не прослушиваются, проверьте параметр `listen-on` в файле `named.conf.options` и настройки брандмауэра (`ufw` или `firewalld`).

### 4. Тестирование разрешения имен через dig

Утилита `dig` является основным инструментом для проверки ответов сервера. Подробности см. в [Диагностика DNS: Обзор](../../../Diagnostics/Networking/dns/overview.md).

```bash
# Запрос к локальному серверу напрямую
dig @127.0.0.1 example.com

# Проверка записи SOA (Start of Authority — начало полномочий)
dig @127.0.0.1 example.com SOA
```

**Анализ флагов в ответе:**

- `aa` (Authoritative Answer) — ответ получен от ответственного за зону сервера.
- `ra` (Recursion Available) — сервер поддерживает рекурсивные запросы.

### 5. Диагностика трансфера зон (AXFR)

Проверка синхронизации между Master и Slave серверами.

```bash
# Попытка полного трансфера зоны (AXFR — Authoritative Zone Transfer)
dig @<IP_MASTER> example.com AXFR
```

Если трансфер не удается, проверьте параметр `allow-transfer` на Master-сервере и доступность порта `53/tcp` (трансфер всегда использует TCP).

### 6. Расширенное логирование и управление через rndc

Утилита `rndc` позволяет изменять поведение сервера без его остановки.

```bash
# Временное включение логирования всех запросов
sudo rndc querylog on

# Увеличение уровня детализации отладки (от 1 до 9)
sudo rndc trace 5

# Очистка кэша резолвера
sudo rndc flush
```

## Дополнительная информация

- **CVE-2025-13878:** Критическая уязвимость (CVSS 7.5), приводящая к завершению процесса `named` при обработке некорректных записей BRID/HHIT. Исправлена в версиях 9.18.44 и 9.20.18.
- **Логи:** По умолчанию BIND пишет в `/var/log/syslog` (Debian/Ubuntu) или через `journald`. Расширенное логирование настраивается в блоке `logging`.
