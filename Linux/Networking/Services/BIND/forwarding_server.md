# BIND: Перенаправляющий сервер

## Определения

**Forwarding DNS-сервер (Domain Name System — система доменных имён)** — рекурсивный сервер, который перенаправляет все входящие запросы внешним DNS-серверам (форвардерам), а не выполняет полную итеративную рекурсию самостоятельно.

**Форвардер (Forwarder)** — внешний DNS-сервер, которому делегируется выполнение рекурсивного поиска (например, публичные серверы Google, Cloudflare или корпоративные апстримы).

**QNAME Minimization (Query Name Minimization — минимизация имени запроса)** — механизм обеспечения приватности (RFC 7816 / RFC 9156), при котором сервер отправляет вышестоящим инстанциям только минимально необходимую часть доменного имени.

## Базовые концепции

### Режимы перенаправления

| Режим | Описание | Конфигурация |
|-------|----------|--------------|
| **Forward only** | Сервер только перенаправляет запросы. Если форвардеры недоступны, клиент получит ошибку (**SERVFAIL**). | `forward only;` |
| **Forward first** | Сначала выполняется попытка перенаправления. При неудаче (тайм-аут) сервер пытается выполнить рекурсию самостоятельно. | `forward first;` |

### Преимущества архитектуры

*   **Снижение сетевой нагрузки:** сервер не опрашивает корневые и TLD-серверы напрямую, отправляя один пакет форвардеру.
*   **Агрегированное кэширование:** повторные запросы разных клиентов обслуживаются мгновенно из локальной оперативной памяти.
*   **Безопасность:** возможность централизованной фильтрации трафика через специализированные сервисы (например, Quad9 с блокировкой вредоносных доменов).

## Практические сценарии

### 1. Конфигурация перенаправления и производительности

**Файл `/etc/bind/named.conf.options`:**

```conf
// ACL (Access Control List — список управления доступом)
acl "trusted_clients" {
    192.168.1.0/24;
    127.0.0.1;
};

options {
    directory "/var/cache/bind";

    // Список форвардеров (рекомендуется минимум два)
    forwarders {
        9.9.9.9;         // Quad9 (Security + Privacy)
        1.1.1.1;         // Cloudflare
    };
    forward only;

    // Оптимизация кэширования (BIND 9.18+)
    prefetch 2 3600;     // Обновление популярных записей до истечения TTL
    
    // Приватность и безопасность
    qname-minimization relaxed; 
    dnssec-validation auto;

    recursion yes;
    allow-query { trusted_clients; };
    listen-on { any; };
};
```

### 2. Управление параметрами кэша

| Параметр | Описание | Рекомендация |
|----------|----------|--------------|
| `max-cache-size` | Максимальный объём памяти под кэш. | 50%–70% доступной **RAM (Random Access Memory)**. |
| `max-cache-ttl` | Максимальное время жизни записи в кэше (в секундах). | `86400` (1 день) для стабильности. |
| `prefetch` | Упреждающее обновление записей. | Полезно для высоконагруженных резолверов. |

### 3. Проверка и применение изменений

После редактирования конфигурации необходимо выполнить валидацию:

```bash
# Проверка синтаксиса (утилита не выводит ничего при успехе)
sudo named-checkconf

# Применение изменений без остановки службы
sudo rndc reconfig
```

### 4. Верификация разрешения имён

Используйте утилиту `dig` для проверки статуса ответа:

```bash
dig @127.0.0.1 google.com
```

**Анализ ответа:**
*   `status: NOERROR` — запрос успешно выполнен.
*   `flags: ra` (**Recursion Available**) — сервер подтвердил готовность выполнять рекурсию.
*   `AUTHORITY: 0` — признак того, что ответ получен из кэша или от форвардера (не авторитетный).

### 5. Диагностика и отладка

Если запросы не проходят:

1.  **Проверка журналов:** `sudo journalctl -u bind9 -n 100`.
2.  **Проверка доступности форвардеров:** `dig @9.9.9.9 example.com`.
3.  **Трассировка rndc:** `sudo rndc querylog on` (включает запись каждого запроса в лог).

## Дополнительная информация

Инструкции актуальны для **BIND (Berkeley Internet Name Domain)** версий 9.18+ **LTS (Long Term Support)** и 9.20+ **ESV (Extended Support Version)**.
