# ISC DHCP: Резервирование IP и передача маршрутов

> **Важно:** Программный стек ISC DHCP официально достиг стадии **EOL (End of Life)**. Для новых инсталляций в 2026 году **настоятельно рекомендуется** использовать **[Kea DHCP](./isc_dhcp_server_overview.md#kea-dhcp-современная-альтернатива)**. Данный файл предназначен для эксплуатации существующих систем и подготовки к миграции.

---

## Определения

**DHCP Reservation (Статическое назначение)** — механизм привязки фиксированного IP-адреса к уникальному идентификатору клиента (MAC-адресу или Client-ID). Это гарантирует, что устройство всегда будет получать один и тот же адрес.

**Classless Static Routes (RFC 3442)** — расширение протокола DHCP (опция 121), позволяющее передавать клиентам список маршрутов с произвольной маской подсети (**CIDR**).

**fixed-address** — директива в конфигурации `dhcpd`, указывающая конкретный IP-адрес для конкретного хоста.

**host declaration** — блок конфигурации `dhcpd.conf`, связывающий идентификатор клиента с набором параметров (IP, опции, загрузочный файл).

**Client Identifier (UID)** — поле опции 61 в пакете DHCP, по которому клиент идентифицирует себя. Может отличаться от MAC-адреса.

**use-host-decl-names** — директива, указывающая `dhcpd` использовать поле `option host-name` из блока `host` как имя клиента в lease-файле и DNS-записях (при включённом DDNS).

## Основные концепции

### Идентификация клиентов

Резервирование может выполняться двумя способами:
1.  **По MAC-адресу (Hardware Ethernet):** Классический метод, привязанный к физическому порту сетевой карты.
2.  **По Client-ID (dhcp-client-identifier):** Современный метод (RFC 2132), использующий уникальную строку или UID. Часто используется в Windows и современных дистрибутивах Linux. Если клиент присылает Client-ID, сервер может проигнорировать Hardware MAC, если это не настроено иначе.

### Жизненный цикл host declaration

При получении запроса `DHCPREQUEST` сервер выполняет следующие шаги:

1.  **Извлечение идентификатора:** Из пакета берётся `chaddr` (MAC) и/или `option dhcp-client-identifier`.
2.  **Поиск в базе:** `dhcpd` ищет совпадение среди активных `host` declarations.
3.  **Проверка состояния:** Если адрес уже выдан и находится в состоянии `active`, сервер просто обновляет таймеры (T1/T2) и отправляет `DHCPACK`.
4.  **Фиксация:** Если адрес свободен или истекла предыдущая аренда, сервер резервирует его за хостом и записывает в `dhcpd.leases` с пометкой `binding state active`.
5.  **Commit-before-ACK:** Перед отправкой `DHCPACK` запись фиксируется на диске через `fsync`.

> **Важно:** Если резервирование настроено для управления устройством (сетевым оборудованием), потеря файла `dhcpd.leases` приведёт к тому, что устройство получит новый адрес, что может нарушить маршрутизацию или доступ к управлению.

### Безопасность и ограничение пула

С помощью директивы `deny unknown-clients;` можно превратить DHCP-сервер в систему «белого списка», где IP-адреса будут выдаваться только хостам, явно описанным в блоках `host`.

### Наследование и переопределение опций

Опции, заданные в блоке `host`, имеют приоритет над опциями того же типа из `subnet` или глобальной области. Это позволяет, например, назначить конкретному серверу другой DNS-сервер или NTP, не затрагивая остальных клиентов.

```conf
subnet 10.0.10.0 netmask 255.255.255.0 {
    option routers 10.0.10.1;
    option domain-name-servers 10.0.1.10;
}

host special-workstation {
    hardware ethernet 00:11:22:33:44:55;
    fixed-address 10.0.10.50;
    option domain-name-servers 10.0.1.20, 1.1.1.1; # Переопределяет глобальный DNS
}
```

### Использование `use-host-decl-names`

По умолчанию `dhcpd` в lease-записи сохраняет hostname, присланный клиентом. Директива `use-host-decl-names true;` заставляет сервер использовать имя из `option host-name` внутри блока `host`. Это критически важно для корректного работы DDNS при резервировании.

```conf
global {
    use-host-decl-names true;
}

host printer-floor2 {
    hardware ethernet 00:11:22:33:44:55;
    fixed-address 10.0.10.50;
    option host-name "printer-floor2";
}
```

### Загрузочные параметры для конкретных хостов (PXE)

В блоке `host` можно указать параметры загрузки, которые переопределяют глобальные настройки PXE. Это удобно для развёртывания разных ОС на конкретных машинах:

```conf
host baremetal-node01 {
    hardware ethernet 00:11:22:33:44:55;
    fixed-address 10.0.40.10;
    next-server 10.0.40.10;
    filename "pxelinux.0";
}

host uefi-laptop {
    hardware ethernet aa:bb:cc:dd:ee:ff;
    fixed-address 10.0.40.11;
    next-server 10.0.40.10;
    filename "grubx64.efi";
}
```

### Нюансы RFC 3442 (Option 121)

Передача маршрутов через опцию 121 имеет критическую особенность: согласно стандарту, если клиент получает этот список, он **обязан игнорировать** стандартную опцию `routers` (шлюз по умолчанию).

**Техническое решение:** Для сохранения доступа во внешние сети необходимо передавать маршрут по умолчанию (`0.0.0.0/0`) первым элементом в списке опции 121.

## Практические сценарии

### 1. Резервирование IP-адреса (Разные методы)

```conf
# Метод 1: По MAC-адресу (наиболее частый)
host server-nas {
    hardware ethernet 00:11:22:33:44:55;
    fixed-address 10.0.10.20;
    option host-name "nas-primary";
}

# Метод 2: По Client-ID (для Windows/Modern Linux)
host developer-workstation {
    option dhcp-client-identifier 1:00:11:22:33:44:56; # 1: означает тип Ethernet
    fixed-address 10.0.10.21;
}
```

### 2. Передача статических маршрутов (Option 121)

Сценарий: Клиенты должны видеть сеть офиса `172.16.0.0/16` через шлюз `10.0.30.254`, сохраняя выход в интернет через основной шлюз `10.0.30.1`.

Формат байтового кодирования: `<маска_бит>, <байты_сети>, <IP_шлюза>`

```conf
subnet 10.0.30.0 netmask 255.255.255.0 {
    range 10.0.30.100 10.0.30.200;
    
    # Стандартный шлюз (для старых клиентов)
    option routers 10.0.30.1;

    # RFC 3442 (Option 121):
    # 1. Сеть 172.16.0.0/16: 16, 172, 16, 10, 0, 30, 254
    # 2. Маршрут по умолчанию (0/0): 0, 10, 0, 30, 1
    option rfc3442-classless-static-routes 
        16, 172, 16, 10, 0, 30, 254, 
        0, 10, 0, 30, 1;
}
```

### 3. Режим «Белого списка»

```conf
subnet 10.0.50.0 netmask 255.255.255.0 {
    # Запретить выдачу адресов всем, кто не описан в блоках 'host'
    deny unknown-clients;
    range 10.0.50.10 10.0.50.250;
}
```

### 4. Переопределение опций для конкретного хоста

Пример: выделенный DNS и NTP для сервера мониторинга.

```conf
subnet 10.0.10.0 netmask 255.255.255.0 {
    option routers 10.0.10.1;
    option domain-name-servers 10.0.1.10;
    option ntp-servers 10.0.1.20;
}

host monitoring-server {
    hardware ethernet 00:11:22:33:44:55;
    fixed-address 10.0.10.50;
    option domain-name-servers 10.0.1.30, 8.8.8.8;
    option ntp-servers 10.0.1.30;
}
```

### 5. PXE-загрузка для конкретного хоста

Разные хосты могут требовать разные загрузочные файлы (например, для установки ОС или загрузки в recovery-режим):

```conf
host test-node-01 {
    hardware ethernet 00:11:22:33:44:55;
    fixed-address 10.0.40.10;
    next-server 10.0.40.10;
    filename "pxelinux.0";
    option host-name "test-node-01";
}

host test-node-02-uefi {
    hardware ethernet aa:bb:cc:dd:ee:ff;
    fixed-address 10.0.40.11;
    next-server 10.0.40.10;
    filename "grubx64.efi";
}
```

### 6. DDNS для зарезервированного хоста

При статических назначениях можно отправлять обновления DNS только для конкретных хостов, указав зону в блоке `host`:

```conf
key ddns-key {
    algorithm HMAC-SHA512;
    secret "XXXXX...";
}

ddns-update-style interim;

zone corp.internal. {
    primary 10.0.1.10;
    key ddns-key;
}

subnet 10.0.10.0 netmask 255.255.255.0 {
    range 10.0.10.100 10.0.10.250;
}

host fileserver {
    hardware ethernet 00:11:22:33:44:55;
    fixed-address 10.0.10.20;
    option host-name "fileserver";
    ddns-hostname "fileserver"; # Имя для DNS
}
```

### 7. Замена оборудования (изменение MAC-адреса)

Если физический сервер заменяется, а IP-адрес должен остаться тем же:

1.  **Подготовьте конфигурацию:** Добавьте новый `host` блок с новым MAC.
2.  **Переименуйте старый блок** (или закомментируйте) для отката.
3.  **Проверьте синтаксис:** `sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf`
4.  **Перезапустите:** `sudo systemctl restart isc-dhcp-server`
5.  **На новом оборудовании** после загрузки выполните `dhclient -r && dhclient` для получения адреса.

> **Важно:** Если старое оборудование ещё работает и получит старый адрес по кэшу ARP, возможен конфликт. Убедитесь, что старое устройство выведено из эксплуатации или переведено на другой адрес.

### 8. Управление резервированием через OMAPI

`omshell` позволяет изменять конфигурацию `host` на лету без перезагрузки демона. Это полезно для временного резервирования адреса или снятия резерва:

```bash
omshell
> server localhost
> port 7911
> key omapi-key "base64_secret"
> connect
> new host
> set name = "temp-reservation"
> set hardware-address = 00:11:22:33:44:55
> set hardware-type = 1
> open
> set ip-address = 10.0.10.200
> update
> exit
```

Для поиска существующего хоста по MAC через OMAPI:

```bash
omshell
> server localhost
> port 7911
> key omapi-key "base64_secret"
> connect
> new host
> set hardware-address = 00:11:22:33:44:55
> open
# → obj: host ... ip-address = 10.0.10.20
> exit
```

## Управление базой аренд и резервирования

### Проверка резервирований в файле аренд

Чтобы убедиться, что резервирование работает, поищите в `dhcpd.leases` записи с нужным MAC:

```bash
# Поиск аренды по MAC
sudo grep "00:11:22:33:44:55" /var/lib/dhcp/dhcpd.leases -A 8

# → lease 10.0.10.20 {
# →   starts 1 2026/09/12 10:00:00;
# →   ends 3 2026/09/15 10:00:00;
# →   binding state active;
# →   hardware ethernet 00:11:22:33:44:55;
# →   uid "\001\000\021\022\023\024\025";
# →   client-hostname "server-nas";
# → }
```

### Аудит всех резервирований в конфигурации

```bash
# Извлечение всех host blocks и fixed-address из dhcpd.conf
grep -E "^host|fixed-address|hardware ethernet" /etc/dhcp/dhcpd.conf

# → host server-nas {
# → hardware ethernet 00:11:22:33:44:55;
# → fixed-address 10.0.10.20;
```

### Резервирование и Failover

При работе в паре **Failover** резервирования синхронизируются между узлами через протокол Failover (TCP 647). Однако существуют ограничения:

-   **Совместное использование:** Один и тот же `host` declaration может существовать в конфигурации обоих узлов.
-   **IP-адрес:** Должен находиться в пуле, обслуживаемом обоими узлами.
-   **Тип адреса:** Резервированные адреса не могут находиться в диапазоне `dynamic` на одном узле и `reserved` на другом. Статус `active` синхронизируется.

> **Практический совет:** В конфигурации Failover используйте один и тот же файл `dhcpd.conf` или синхронизируйте его через `rsync`/Ansible. Различия в `host` declarations между узлами приведут к непредсказуемому поведению при переключении.

## Решение проблем

### Конфликты и соответствия

*   **Конфликты в пуле:** Если `fixed-address` попадает внутрь динамического `range`, сервер может выдать этот адрес другому клиенту. **Правило:** Резервы должны быть вне диапазонов `range`.
*   **Игнорирование резерва:** Проверьте, не присылает ли клиент Client-ID (UID), который не совпадает с MAC. Попробуйте добавить `ignore-client-uids true;` в глобальные настройки для принудительной привязки только к MAC.
*   **Несоответствие Client-ID и MAC:** Если в резерве указан MAC, а клиент использует Client-ID, сервер создаст новую запись в `dhcpd.leases` без привязки к `host`. Проверьте логи: `grep -i "no free leases" /var/log/syslog` или `journalctl -u isc-dhcp-server`.

### Диагностика на сервере

```bash
# Проверка наличия опции 121 в ответах сервера
sudo tcpdump -i any port 67 or port 68 -vv -n
# → DHCP-ACK ... Option 121 (Classless Static Route), length 12: (172.16.0.0/16 -> 10.0.30.254, 0.0.0.0/0 -> 10.0.30.1)

# Валидация синтаксиса
sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf
# → success

# Проверка активных резервирований
sudo grep -E "^lease|^host|binding state active" /var/lib/dhcp/dhcpd.leases | grep -B1 "active" | grep "lease"

# Проверка, что резервированный адрес выдан именно зарезервированному хосту
sudo grep "00:11:22:33:44:55" /var/lib/dhcp/dhcpd.leases -A 5
```

### Типичные проблемы резервирования

| Проблема | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Клиент получает другой адрес | `fixed-address` вне обслуживаемой подсети | `grep "10.0.10.20" /var/lib/dhcp/dhcpd.leases` | Убедиться, что subnet включает `10.0.10.0/24` |
| IP не резервируется | Клиент отправляет Client-ID, а в конфиге только MAC | `tcpdump -i eth0 port 67 or port 68 -n -vv` | Добавить `ignore-client-uids true;` или указать Client-ID |
| Резерв не отрабатывает после перезагрузки | Повреждён `dhcpd.leases` или неверные права | `tail -5 /var/lib/dhcp/dhcpd.leases` | Восстановить из бэкапа, `chown dhcpd:dhcpd` |
| Два хоста с одним MAC | Дублирование MAC на VLAN или виртуальная машина | `grep "00:11:22:33:44:55" /var/lib/dhcp/dhcpd.leases` | Найти конфликт через ARP-таблицы коммутатора |
| Резерв работает только один раз | `fixed-address` совпадает с `range`, другой клиент занял адрес | `grep "10.0.10.20" /var/log/syslog` | Вынести резерв за пределы `range` |

## Дополнительная информация

### DHCPv6 и резервирование

ISC DHCP также поддерживает DHCPv6. Синтаксис аналогичен, но используется `fixed-address6` и `dhcp6-client-id`:

```conf
host ipv6-server {
    dhcp6-client-id 00:01:00:01:11:22:33:44:55;
    fixed-address6 2001:db8::50;
}
```

### Рекомендации SRE/SysAdmin

1.  **Документируйте все резервы:** Ведите реестр `host` declarations в CMDB или Ansible Vault. Неизвестные `host` блоки — причина 90% конфликтов при инцидентах.
2.  **Бэкап `dhcpd.conf`:** Храните конфигурацию в Git. Любое изменение должно проходить код-ревью.
3.  **Мониторинг пула:** Настройте алерт на количество активных аренд, приближающееся к размеру `range`. Резервы сокращают доступный пул.
4.  **Проверка MAC:** При поступлении нового оборудования запрашивайте MAC-адрес до установки ОС, чтобы внести его в резерв заранее.
5.  **Согласование с сетевым командой:** Убедитесь, что зарезервированные адреса не конфликтуют с статическими адресами на маршрутизаторах или балансировщиках.
