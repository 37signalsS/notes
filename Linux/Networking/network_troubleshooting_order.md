# Порядок диагностики сетевых проблем в Linux

## Определения

**Диагностика сети** — это процесс выявления и устранения проблем подключения. Ключевой принцип: **сеть — это поток**, а не набор разрозненных компонентов. Проблема чаще всего кроется не в том, что вы думаете.

## Основные концепции

### Разрушение распространённых заблуждений

| Заблуждение | Реальность |
| :--- | :--- |
| «Есть IP — сеть работает» | IP может быть назначен не на тот интерфейс |
| «Пинг работает — всё работает» | Пинг может идти другим маршрутом или через ICMP |
| «Это firewall» | Firewall чаще всего ни при чём, проблема в маршрутизации |
| «Перезапуск сети поможет» | Может усугубить проблему, потеряв SSH |

### Шесть проверок (всегда в этом порядке)

1. **Интерфейсы** → `ip addr show`
2. **Маршруты** → `ip route`
3. **ARP-кэш** → `ip neigh` (особенно на нодах с ВМ/LXC)
4. **Связность** → `ping`
5. **DNS** → `cat /etc/resolv.conf`, `nslookup`
6. **Firewall** → `iptables -L -n` (в последнюю очередь!)

> **Важно:** Нарушение этого порядка — основная причина потери времени на диагностику.

## Практические сценарии

### Сценарий 1: Проверка интерфейсов

**Команда:**

```bash
ip addr show
```

**Вопросы для самопроверки:**

1. Интерфейс активен (UP)?
2. У него правильный IP-адрес?
3. Это тот интерфейс, который вы себе представляете?

**Типичная ошибка:** Отладка `eth0`, тогда как реальный трафик идёт через `ens192`.

**Проверка:**

```bash
# Краткий вывод всех интерфейсов
ip -br addr

# Только активные интерфейсы
ip -br addr show up
```

### Сценарий 2: Проверка маршрутизации

**Команда:**

```bash
ip route
```

**Что искать:**

| Проблема | Симптом |
| :--- | :--- |
| Нет default route | `default via` отсутствует |
| Неправильный gateway | Указан неверный шлюз |
| Конфликт маршрутов | Несколько маршрутов к одной сети |

**Важно:** Если Linux не знает, куда отправлять пакеты, неважно, насколько правильны остальные настройки.

**Примеры:**

```bash
# Показать только маршрут по умолчанию
ip route | grep default

# Показать маршрут к конкретному хосту
ip route get 8.8.8.8
```

### Сценарий 2.5: Проверка ARP-кэша (Neighbor Table)

**Зачем проверять:** Если интерфейсы и маршруты в порядке, но связь нестабильна («хаос» — одни IP пингуются, другие нет, внезапные задержки), проблема может быть в переполнении ARP-таблицы или **ARP Spoofing** (атаке на локальную сеть).

**Команды:**

```bash
# Просмотр записей
ip neigh show

# Проверка на наличие ошибок (FAILED, INCOMPLETE)
ip -s neigh

# Проверка на дублирование IP (ARP Spoofing)
arping -I eth0 -D <gateway_ip>
```

**Что искать:**
- Большое количество статусов `FAILED` или `INCOMPLETE`.
- Неожиданная смена MAC-адреса шлюза.
- Несколько IP-адресов, указывающих на один и тот же MAC.

**Подробно:** [ARP и ARP Spoofing](../../Networking/Protocols/arp.md#arp-spoofing-arp-cache-poisoning)

### Сценарий 3: Проверка связности (пинг)

**Команда:**

```bash
ping -c 3 8.8.8.8
```

**Интерпретация:**

| Результат | Вывод |
| :--- | :--- |
| Пинг проходит | IP-маршрутизация работает |
| Пинг не проходит | Проблема с маршрутизацией (не DNS, не firewall!) |

**Важно:** Не стоит слепо доверять пингу. Некоторые узлы блокируют ICMP.

### Сценарий 4: Проверка DNS

**Команды:**

```bash
cat /etc/resolv.conf
nslookup google.com
# или
dig google.com
```

**Типичная проблема:**

```bash
# nameserver указывает на локальный сервис, который не запущен
nameserver 127.0.0.1
```

**Диагностика:**

| Проверка | Вывод |
| :--- | :--- |
| `ping 8.8.8.8` работает, `ping google.com` нет | Проблема с DNS |
| `nslookup` не возвращает IP | DNS-сервер недоступен или не отвечает |

**Подробно:** [Диагностика DNS](./Services/BIND/overview.md)

### Сценарий 5: Проверка firewall (в последнюю очередь!)

**Команды:**

```bash
# Для iptables
iptables -L -n

# Для firewalld
firewall-cmd --list-all

# Для nftables
nft list ruleset
```

**Важно:** Firewall чаще всего оказывается **последним** в списке причин. Если маршрут настроен неправильно — firewall ни при чём.

## Дополнительная информация

### Комплексный порядок диагностики

| Шаг | Задача | Команда | Что проверяем |
| :--- | :--- | :--- | :--- |
| **1** | Интерфейсы | `ip addr show` | Активность, IP, правильный интерфейс |
| **2** | Маршруты | `ip route` | Default route, gateway, конфликты |
| **3** | Связность | `ping -c 3 8.8.8.8` | IP-маршрутизация работает |
| **4** | DNS | `nslookup google.com` | Разрешение имён |
| **5** | Firewall | `iptables -L -n` | Правила фильтрации |

### Пример диагностики «Сервер не подключается к базе данных»

```bash
# 1. Проверяем интерфейс
ip addr show
# Интерфейс UP? IP правильный?

# 2. Проверяем маршрут
ip route
# Есть default route? Правильный gateway?

# 3. Проверяем связность с БД
ping -c 3 <IP_базы_данных>
# Если не работает → проблема с маршрутизацией

# 4. Проверяем порт БД
nc -zv <IP_базы_данных> 5432
# Connection succeeded → порт открыт
# Connection refused → сервис не запущен
# Timed out → блокируется firewall

# 5. Только теперь firewall
iptables -L -n | grep 5432
```

### Сценарий 6: Комплексная диагностика доступности сервиса (Сервер vs Клиент)

Если сервис недоступен, диагностику следует разделить на две части.

#### Шаг 1: Проверка на стороне сервера

1. **Запущен ли сервис?**
   ```bash
   ss -tulpan | grep :80  # Проверка порта 80
   ```
   * **Проблема:** Сервис не слушает порт или слушает не тот.
2. **На каком адресе висит сервис?**
   * Если это `127.0.0.1` (localhost), то снаружи к нему не подключиться. Нужно, чтобы сервис слушал `0.0.0.0` или конкретный внешний IP.
3. **Не мешает ли локальный Firewall?**
   ```bash
   iptables -L -n
   # или
   ufw status
   ```
   * Убедитесь, что входящий трафик на нужный порт разрешен (`ACCEPT`).
4. **Security Groups (если в облаке):**
   * Проверьте настройки фаервола на уровне облачного провайдера (AWS SG, Yandex Cloud SG). Если порт закрыт там, трафик даже не дойдет до операционной системы.

#### Шаг 2: Проверка на стороне клиента

1. **Базовая связность:**
   ```bash
   ping <IP_сервера>
   ```
2. **Доступность порта:**
   ```bash
   telnet <IP_сервера> <порт>
   # или
   nc -zv <IP_сервера> <порт>
   ```
   * **Connected:** Порт открыт, проблема в приложении или протоколе.
   * **Connection refused:** Порт закрыт на сервере (сервис не запущен).
   * **Connection timed out / Traing:** Пакеты дропаются по пути (Firewall/Security Group).
3. **Проверка прикладного уровня (HTTP/HTTPS):**
   ```bash
   curl -v http://<IP_сервера>
   ```
   * Флаг `-v` покажет процесс DNS-резолвинга, установку TCP-соединения, TLS-рукопожатие и HTTP-заголовки.
4. **Поиск обрыва на маршруте:**
   ```bash
   traceroute <IP_сервера>
   # или
   mtr <IP_сервера>
   ```
   * Покажет, на каком именно узле (хопе) пакеты перестают проходить.
