# Порядок диагностики сетевых проблем в Linux

## Определения

**Диагностика сети** — систематический процесс выявления и устранения проблем сетевого взаимодействия на разных уровнях модели OSI.

**Связность (Connectivity)** — способность узлов обмениваться данными по сети.

**Маршрутизация (Routing)** — процесс определения пути следования данных от отправителя к получателю.

**MTU (Maximum Transmission Unit)** — максимальный размер полезного блока данных одного пакета, который может быть передан по интерфейсу без фрагментации.

**eBPF (Extended Berkeley Packet Filter)** — технология ядра, позволяющая запускать программы в песочнице внутри ядра для глубокого мониторинга и диагностики трафика без изменения кода ядра.

## Основные концепции

### Ключевые принципы

1.  **Сеть — это поток:** Данные проходят через цепочку компонентов. Проблема в одном звене разрывает весь поток.
2.  **Изоляция уровней (Bottom-up):** Начинайте с физического уровня и двигайтесь вверх. Нет смысла проверять DNS, если интерфейс в состоянии `DOWN`.
3.  **Симметрия:** В сетях пакеты должны ходить в обе стороны. Если вы видите исходящий трафик, это не значит, что возвращается входящий.
4.  **Доверяй, но проверяй:** Пинг может работать через ICMP, но TCP-порт может быть закрыт фильтрацией или отсутствием процесса.

### Слой за слоем (Методология)

| Порядок | Объект проверки | Основные инструменты | Что ищем |
| :--- | :--- | :--- | :--- |
| **1** | Физика и L2 | `ip -br link`, `ethtool`, `dmesg` | Состояние Link, ошибки (errors/dropped), MTU |
| **2** | IP-адресация | `ip -c addr` | Наличие IP, правильность подсети |
| **3** | L2-соседи | `ip neigh` | ARP/NDP записи, статус STALE/FAILED |
| **4** | Маршрутизация | `ip route`, `ip rule` | Наличие Default Gateway, специфичные маршруты |
| **5** | ICMP-связность | `ping`, `mtr` | Пакетный RTT, потери, промежуточные узлы |
| **6** | DNS-резолвинг | `resolvectl`, `dig`, `nslookup` | Работа системного резолвера, доступность DNS-серверов |
| **7** | Порты и Сокеты | `ss -tulpn`, `nc`, `telnet` | Статус LISTEN, правильный bind (0.0.0.0 vs 127.0.0.1) |
| **8** | Фильтрация | `nft`, `iptables`, `conntrack` | Правила DROP/REJECT, логирование, лимиты сессий |
| **9** | Глубокая трассировка | `pwru`, `bpftrace`, `tcpdump` | Место дропа пакета внутри ядра, ретрансмиты |

## Практические сценарии

### Сценарий 1: Проверка интерфейсов и аппаратного уровня

Первым делом проверяем, видит ли ядро сетевую карту и активна ли она.

```bash
# Краткий статус всех интерфейсов
ip -br link show
# eth0 UP f0:2f:74:e1:5a:30 <BROADCAST,MULTICAST,UP,LOWER_UP>

# Проверка IP с цветовым выделением (удобно для глаз)
ip -c addr
# → 2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> ... inet 192.168.1.10/24

# Детальная статистика ошибок
ip -s link show eth0
# Ищем: errors, dropped, overruns (переполнение буфера ядра)

# Аппаратная статистика (дропы на уровне контроллера)
sudo ethtool -S eth0 | grep -E "drop|error"
# → rx_dropped: 0, tx_errors: 0

# Проверка системных логов на предмет ошибок драйвера/линка
dmesg | grep -iE "eth|ens|eno|network|link"
# → [12.345] igb 0000:01:00.0: eth0: Link is Up 1000 Mbps Full Duplex
```

**На что обратить внимание:**
- `state DOWN` — интерфейс выключен (`ip link set up`).
- `NO-CARRIER` — физический обрыв кабеля или проблема на стороне свитча.
- Большое количество `dropped` в `ip -s link` — ядро не успевает обрабатывать пакеты или переполнены очереди (`softnet`).

### Сценарий 2: L2-соседи (ARP/NDP)

Если IP настроен, но шлюз не пингуется, проверьте, видит ли сервер соседа по MAC-адресу.

```bash
# Просмотр таблицы соседей (ARP/NDP)
ip neigh show
# → 192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
```

**Диагностика через LLDP (IEEE 802.1AB):**
Если `ip neigh` пуст, используйте LLDP для поиска физически подключенного коммутатора:
```bash
# Просмотр соседей (требует lldpd)
lldpcli show neighbors
# Захват кадров вручную
sudo tcpdump -i eth0 -nn -v ether proto 0x88cc
```

**Статусы записей в `ip neigh`:**
- `REACHABLE` — всё в порядке.
- `STALE` — запись устарела, требует обновления при трафике.
- `FAILED` — сервер не смог получить MAC-адрес соседа (проблема L2 или изоляции портов).

### Сценарий 3: Маршрутизация и MTU

Если связь есть только внутри подсети, проверяем таблицу маршрутов.

```bash
# Проверка маршрута по умолчанию
ip route show default
# → default via 192.168.1.1 dev eth0 proto dhcp metric 100

# Предсказание пути пакета до конкретной цели
ip route get 8.8.8.8
# → 8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.10 uid 0

# Проверка MTU (актуально для VPN и облаков)
ping -M do -s 1472 8.8.8.8
# Если пакет не проходит: "Frag needed and DF set" — нужно уменьшать MTU или настраивать MSS Clamping.
```

### Сценарий 4: Фильтрация и состояние соединений (nftables/conntrack)

Современный Linux использует `nftables`. Проблемы часто вызваны переполнением таблицы состояний или скрытыми дропами.

```bash
# Просмотр текущих правил nftables
sudo nft list ruleset

# Трассировка пакета в реальном времени (найти, где именно дроп)
# 1. Добавить правило трассировки для теста
sudo nft add rule inet filter input ip saddr 1.2.3.4 meta nftrace set 1
# 2. Запустить монитор
sudo nft monitor trace

# Проверка лимитов conntrack (если соединений слишком много)
sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max
# → net.netfilter.nf_conntrack_count = 250000
# → net.netfilter.nf_conntrack_max = 262144 (близко к лимиту!)

# Проверка Reverse Path Filtering (пакеты дропаются, если пришли с "неверного" интерфейса)
sysctl -a | grep "\.rp_filter"
# Ожидается: 0 (выкл) или 2 (loose), значение 1 (strict) часто мешает асимметричной маршрутизации.
```

### Сценарий 5: Диагностика DNS

В современных дистрибутивах используется `systemd-resolved`.

```bash
# Проверка текущего статуса и серверов DNS
resolvectl status

# Прямой запрос через системный резолвер
resolvectl query google.com
# → google.com: 142.250.186.206 -- link: eth0

# Проверка файла конфигурации
cat /etc/resolv.conf
# Если там 127.0.0.53 — это stub-резолвер systemd.
```

### Сценарий 6: Проверка сокетов и слушающих портов

```bash
# Показать все слушающие TCP-порты с именами процессов
sudo ss -tulpn

# Проверка: слушает ли сервис внешний интерфейс?
# Ожидается: 0.0.0.0:80 или [::]:80
# Проблема: 127.0.0.1:80 (доступен только локально)

# Поиск "зависших" соединений (TIME-WAIT, CLOSE-WAIT)
ss -ant | awk '{print $1}' | sort | uniq -c
```

### Сценарий 7: Поиск места обрыва (MTR)

`mtr` (My Traceroute) объединяет `ping` и `traceroute`, показывая потери на каждом узле.

```bash
mtr -rwzc 100 8.8.8.8
```

**Интерпретация:**
- Потери на первом хопе — проблема в локальной сети/роутере.
- Потери на последнем хопе — проблема на целевом сервере/файрволе.
- Потери в середине — проблема у провайдера (магистральные узлы).

### Сценарий 8: Глубокая видимость с eBPF (pwru)

Если пакет «исчезает» в ядре и `tcpdump` его видит на входе, но не на выходе, используйте `pwru` (Packet Where Are You).

```bash
# Отслеживание пакета через функции ядра
sudo pwru --filter-dst-ip 8.8.8.8
# Покажет цепочку функций: netif_receive_skb -> ip_rcv -> nft_do_chain -> ...
# Если пакет дропнут, вы увидите последнюю функцию и причину.
```

## Дополнительная информация

### Чек-лист быстрого реагирования

1.  **`ip a`** — Есть ли IP и поднят ли линк?
2.  **`ip r`** — Есть ли шлюз по умолчанию?
3.  **`ip n`** — Виден ли MAC-адрес соседа (шлюза)?
4.  **`ping -c 3 8.8.8.8`** — Есть ли интернет по IP?
5.  **`resolvectl query google.com`** — Работает ли DNS?
6.  **`ss -ntlp`** — Слушает ли приложение нужный порт на нужном IP?
7.  **`dmesg | tail`** — Нет ли ошибок драйвера или OOM в логах?
