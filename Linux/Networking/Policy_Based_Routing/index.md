# Маршрутизация на основе политик (PBR) в Linux

## Определения

**Policy-Based Routing (PBR)** — механизм в ядре Linux, позволяющий выбирать таблицу маршрутизации на основе набора правил (политик). В отличие от традиционной маршрутизации (destination-based), где решение принимается только по IP-адресу назначения, PBR учитывает широкий спектр атрибутов: IP источника, входящий интерфейс, порт, протокол, а также метки пакетов (`fwmark`) и UID пользователя.

**Source-Based Routing (SBR)** — частный случай PBR, при котором маршрутизация осуществляется исключительно на основе адреса источника (селектор `from` в правиле).

**RPDB (Routing Policy Database)** — база данных правил в ядре Linux, которая определяет, какую таблицу маршрутизации использовать для обработки конкретного пакета. Ядро последовательно проверяет правила в RPDB от наименьшего приоритета к наибольшему (first-match).

## Предпосылки

### Требования к ядру

Для функционирования PBR ядро Linux должно быть собрано с поддержкой следующих опций:

- `CONFIG_IP_ADVANCED_ROUTER` — расширенные возможности маршрутизации.
- `CONFIG_IP_MULTIPLE_TABLES` — поддержка множественных таблиц маршрутизации для IPv4.
- `CONFIG_IPV6_MULTIPLE_TABLES` — поддержка множественных таблиц маршрутизации для IPv6.

Путь в конфигурации ядра: `Networking support → Networking options → TCP/IP networking`.

### Требования к пакетам

Пакет `iproute2` должен быть установлен в системе:

```bash
# Debian/Ubuntu
sudo apt install iproute2

# RHEL/CentOS/Rocky/Alma
sudo dnf install iproute
```

### Права доступа

Все команды `ip rule` (кроме `ip rule show`) требуют привилегий суперпользователя (`sudo`).

### Проверка текущего состояния

```bash
# Просмотр текущих правил RPDB
ip rule show
# → 0:	from all lookup local
# → 32766:	from all lookup main
# → 32767:	from all lookup default

# Детальный просмотр (с suppress_prefixlength, VRF)
ip -d rule show

# Проверка таблиц маршрутизации
ip route show table all
```

### Проверка поддержки ядра

```bash
# Проверка опций ядра
grep -E "CONFIG_IP_MULTIPLE_TABLES|CONFIG_IPV6_MULTIPLE_TABLES" /boot/config-$(uname -r)
# → CONFIG_IP_MULTIPLE_TABLES=y
# → CONFIG_IPV6_MULTIPLE_TABLES=y

# Проверка версии ядра (для L4-селекторов)
uname -r
# → 5.15.0-xx (ядро 4.17+ требуется для ipproto, dport, sport)
```

## Основные концепции

### Требования к ядру

Для функционирования PBR ядро Linux должно быть собрано с поддержкой следующих опций:

- `CONFIG_IP_ADVANCED_ROUTER` — расширенные возможности маршрутизации.
- `CONFIG_IP_MULTIPLE_TABLES` — поддержка множественных таблиц маршрутизации для IPv4.
- `CONFIG_IPV6_MULTIPLE_TABLES` — поддержка множественных таблиц маршрутизации для IPv6.

Путь в конфигурации ядра: `Networking support → Networking options → TCP/IP networking`.

### Принцип работы и RPDB

Стандартная маршрутизация в Linux использует одну главную таблицу (`main`) для всех решений. PBR расширяет эту модель, вводя **базу данных правил маршрутизации (RPDB — Routing Policy Database)**.

При поступлении пакета (или его локальной генерации) ядро последовательно проверяет правила в RPDB от наименьшего приоритета к наибольшему. Первое совпавшее правило указывает, в какой таблице искать маршрут.

```
┌─────────────────┐
│   Входящий      │
│    пакет        │
└────────┬────────┘
          │
          ▼
┌─────────────────┐
│  Проверка       │
│  RPDB (ip rule) │
└────────┬────────┘
          │
     ┌────┴────┬─────────┬─────────┐
     │         │         │         │
     ▼         ▼         ▼         ▼
┌───────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
│ local │ │  table  │ │  main   │ │ default │
│ (0)   │ │  (100)  │ │ (254/2) │ │  (253)  │
└───────┘ └─────────┘ └─────────┘ └─────────┘
```

#### Стандартный набор правил

По умолчанию в Linux настроены три правила, обеспечивающие базовую работу системы:

| Приоритет | Селектор | Таблица | Назначение |
| :--- | :--- | :--- | :--- |
| **0** | `from all` | `local` | Обработка локальных, петлевых (loopback) и широковещательных адресов. **Нельзя удалять.** |
| **32766** | `from all` | `main` | Основная таблица для стандартных и динамических маршрутов. |
| **32767** | `from all` | `default` | Резервная пустая таблица для пакетов, не попавших под иные правила. |

**Правило `local` (приоритет 0)** — критически важно. Оно обрабатывает:
- Адреса назначения, принадлежащие интерфейсам хоста.
- Широковещательные адреса.
- Loopback-адреса (`127.0.0.0/8`).

> **Никогда не удаляйте** правило с приоритетом 0. Это приведет к потере сетевой связности.

#### Диапазоны приоритетов (рекомендации)

Для поддержания порядка в RPDB рекомендуется придерживаться следующих диапазонов:

| Диапазон | Назначение | Примеры |
| :--- | :--- | :--- |
| **0** | Системное правило `local`. | Не использовать для пользовательских правил. |
| **1–99** | Критичные системные правила (VPN-шлюзы, маршруты по умолчанию для специфические подсети). | `ip rule add from 10.0.0.0/8 table 100 priority 10` |
| **100–999** | Основные PBR-правила (разделение трафика по портам, протоколам, пользователям). | `ip rule add ipproto tcp dport 443 table 150 priority 500` |
| **1000–32765** | Правила общего назначения, временные правила, правила для отладки. | `ip rule add from 192.168.1.0/24 table 200 priority 2000` |
| **32766** | Системное правило `main`. | Не использовать. |
| **32767** | Системное правило `default`. | Не использовать. |

### Компоненты реализации PBR

Реализация PBR базируется на взаимодействии трех уровней:

1.  **Множественные таблицы маршрутизации**: До 255 независимых таблиц. Имена и ID таблиц описываются в `/etc/iproute2/rt_tables`.
2.  **Правила маршрутизации (Rules)**: Управляются через `ip rule`. Каждое правило имеет **приоритет** (0–32767) и **селектор** (критерий отбора).
3.  **Классификация трафика**: Определение пакетов по атрибутам L3/L4 или по меткам, установленным фаерволом.

### Инструментарий администратора

Для управления PBR в Linux используется стандартный стек утилит:

| Инструмент | Назначение |
| :--- | :--- |
| **`ip rule`** | Просмотр и изменение базы данных правил (RPDB). |
| **`ip route`** | Работа с таблицами маршрутизации (ID 1–255). |
| **`sysctl`** | Управление параметрами сетевого стека (`rp_filter`). |
| **`nft / iptables`** | Трассировка и диагностика маркировки трафика. |
| **`tcpdump`** | Захват трафика на конкретных интерфейсах для проверки симметрии. |

### Взаимодействие с Netfilter

Правила `ip rule` срабатывают **после** цепочки `PREROUTING` и **после** цепочки `OUTPUT` в Netfilter. Это означает:

- Маркировка (`fwmark`) должна устанавливаться в `PREROUTING` (для входящего трафика) или `OUTPUT` (для исходящего).
- Маркировка в `POSTROUTING` **не работает** для PBR (пакет уже прошел этап маршрутизации).

```bash
# Правильно: маркировка в PREROUTING
nft add rule inet filter prerouting tcp dport 443 meta mark set 0x1

# Неправильно: маркировка в POSTROUTING (не работает для PBR)
# nft add rule inet filter postrouting tcp dport 443 meta mark set 0x1
```

### Поддержка протоколов и селекторы

PBR в Linux поддерживает как IPv4, так и IPv6. Управление осуществляется соответствующими ключами: `ip rule` (IPv4) и `ip -6 rule` (IPv6).

**Доступные селекторы:**

| Селектор | Описание | Технические нюансы |
| :--- | :--- | :--- |
| **from / to** | Адреса источника / назначения. | Поддерживает префиксы (`from 10.0.0.0/24`) и `not` (отрицание). |
| **iif / oif** | Входящий / исходящий интерфейсы. | `iif lo` используется для трафика, генерируемого локально. |
| **fwmark** | Метка пакета из Netfilter. | Позволяет реализовать логику L7 (через `iptables`/`nftables`). |
| **uidrange** | Диапазон UID пользователя. | Критично для per-user routing (изоляция процессов). |
| **ipproto** | Номер или имя протокола IP. | Требует ядро 4.17+ (TCP, UDP, ICMP и др.). |
| **sport / dport** | Порты источника / назначения. | Требует ядро 4.17+; работает в связке с `ipproto`. |
| **l3mdev** | L3 Master Device (VRF). | Сопоставление пакетов, принадлежащих конкретному VRF. |
| **tos** | Поле Type of Service. | Классификация трафика по приоритетам QoS. |
| **realms** | Routing realms (метки маршрутизации). | Продвинутый атрибут для классификации потоков. Требует настройки в `ip route`. |

**Примеры использования селекторов:**

```bash
# Фильтрация по протоколу и порту (ядро 4.17+)
sudo ip rule add ipproto tcp dport 443 table 100 priority 500

# Фильтрация по UID-диапазону
sudo ip rule add uidrange 1000-2000 table 200 priority 1000

# Фильтрация с отрицанием (всё, кроме указанной подсети)
sudo ip rule add to not 192.168.0.0/16 table vpn_table priority 2000

# Фильтрация по входящему интерфейсу
sudo ip rule add iif eth1 table isp2_table priority 300

# Фильтрация по TOS (Type of Service)
sudo ip rule add tos 0x10 table 100 priority 400
```

### Типы действий и продвинутые параметры

*   **lookup / table <ID>** — Искать маршрут в указанной таблице (основное действие).
*   **suppress_prefixlength <N>** — Игнорировать таблицу, если найденный в ней маршрут имеет маску префикса меньше или равную N (например, `0` — игнорировать default gateway).
*   **suppress_ifgroup <ID>** — Игнорировать таблицу, если исходящий интерфейс принадлежит группе ID.
*   **blackhole** — Молчаливо отбросить пакет.
*   **unreachable** — Отбросить и отправить ICMP "Network Unreachable".
*   **prohibit** — Отбросить и отправить ICMP "Communication Administratively Prohibited".
*   **goto <N>** — Перейти к правилу с указанным приоритетом (без выполнения поиска маршрута).
*   **nop** — Без действия (полезно для отладки и временного отключения правила).

### Локально генерируемый трафик (iif lo)

Для трафика, созданного самим сервером (локальные службы, прокси, агенты мониторинга), в `ip rule` используется селектор `iif lo`:

```bash
# Направить трафик локального прокси-сервера (порт 8080) в специальную таблицу
sudo ip rule add iif lo ipproto tcp sport 8080 table proxy_table priority 200
```

### Взаимодействие с ICMP Redirect

При использовании PBR классический ICMP Redirect **не генерируется**. Маршрутизатор видит, что пакет должен уходить через default gateway, но хост игнорирует Redirect, потому что PBR имеет приоритет над таблицей `main`.

Это важное ограничение в продакшене: если кратчайший путь к узлу лежит через другой интерфейс, а PBR направляет трафик в туннель или через отдельный шлюз, хост продолжает слать трафик через PBR-правило, даже если существует более короткий путь.

**Решение:** либо явно настроить маршруты в PBR-таблицах, либо отключить `accept_redirects`, чтобы избежать конфликтов:

```bash
# Отключение приема ICMP Redirect
sudo sysctl -w net.ipv4.conf.all.accept_redirects=0
```

### Подавление маршрутов (suppress_prefixlength)

Механизм позволяет пропустить таблицу маршрутизации, если найденный в ней маршрут является слишком общим (например, маршрут по умолчанию `0.0.0.0/0`). Это полезно для сценариев, где в дополнительной таблице нужны только специфичные маршруты, а при их отсутствии трафик должен обрабатываться следующими правилами RPDB.

```bash
# Использовать таблицу 100 только если в ней есть маршрут конкретнее, чем /0
sudo ip rule add from 10.10.10.0/24 table 100 suppress_prefixlength 0
```

### Файл /etc/iproute2/rt_tables

Файл `/etc/iproute2/rt_tables` содержит маппинг числовых ID таблиц на их имена. Это делает конфигурацию более читаемой и поддерживаемой.

```
# /etc/iproute2/rt_tables
#
# numeric  name
#
255    local
254    main
253    default
0      unspec
100    isp1_table
101    isp2_table
200    vpn_user_table
```

**Рекомендации:**
- Используйте осмысленные имена (например, `isp1_table`, `vpn_user_table`).
- Избегайте пробелов и спецсимволов в именах.
- Не переопределяйте зарезервированные ID (0, 253, 254, 255).
- Имена таблиц доступны в командах `ip rule` и `ip route` вместо числовых ID:

```bash
# Использование имени вместо числового ID
sudo ip rule add from 10.0.0.0/8 table isp1_table priority 100
sudo ip route add default via 192.168.1.1 dev eth0 table isp1_table
```

## Практические сценарии

### Асимметричная маршрутизация и обратный путь

**Проблема:** В системах с несколькими интернет-каналами ответ на пакет, пришедший на интерфейс B, может уйти через интерфейс A (если там настроен шлюз по умолчанию в таблице `main`). Это приводит к блокировкам со стороны фаерволов и механизмов защиты ядра (**Reverse Path Filtering**).

**Решение:**
1. Использование PBR для ответа через тот же интерфейс на основе IP источника.
2. Настройка параметра `rp_filter`.

#### Настройка Reverse Path Filtering (rp_filter)

При использовании PBR критически важно перевести интерфейсы в режим **Loose (2)**:
- `0`: Без фильтрации.
- `1` (Strict): Проверка, является ли входящий интерфейс оптимальным путем для обратного маршрута. **Несовместимо с PBR.**
- `2` (Loose): Проверка наличия любого маршрута к адресу источника через любой интерфейс. **Рекомендуемый режим для PBR.**

```bash
# Рекомендуемая настройка в /etc/sysctl.d/99-pbr.conf
net.ipv4.conf.all.rp_filter = 2
net.ipv4.conf.default.rp_filter = 2

# Применение без перезагрузки
sudo sysctl -p /etc/sysctl.d/99-pbr.conf
```

### Изоляция управляющего трафика (SSH / management)

**Задача:** Направлять SSH-трафик из подсети управления через выделенный канал или VPN-туннель, отделяя его от пользовательского трафика.

**Реализация (Source-Based Routing):**

```bash
# 1. Создание таблицы для управляющего трафика
echo "200 mgmt_table" | sudo tee -a /etc/iproute2/rt_tables
sudo ip route add default via 10.0.1.1 dev mgmt0 table mgmt_table

# 2. Правило для подсети управления
sudo ip rule add from 192.168.100.0/24 table mgmt_table priority 100
```

### Изоляция трафика мониторинга и бэкапов

**Задача:** Отделить трафик мониторинга (syslog, metrics, SNMP) и резервного копирования (rsync, bacula) от основного пользовательского трафика, чтобы избежать конкуренции за пропускную способность.

**Реализация:**

```bash
# 1. Таблица для мониторинга
echo "210 monitoring_table" | sudo tee -a /etc/iproute2/rt_tables
sudo ip route add default via 192.168.2.1 dev eth1 table monitoring_table

# 2. Правило по UID для агента мониторинга (например, UID 998)
sudo ip rule add uidrange 998-998 table monitoring_table priority 200

# 3. Правило для локально генерируемого трафика (syslog-клиент, порт 514)
sudo ip rule add iif lo ipproto udp dport 514 table monitoring_table priority 210
```

### Kill Switch для VPN-пользователей

**Задача:** Гарантировать, что трафик пользователя VPN не утечет в обычный интернет при разрыве туннеля.

**Реализация:**

```bash
# 1. Таблица VPN
echo "220 vpn_user_table" | sudo tee -a /etc/iproute2/rt_tables
sudo ip route add default via 10.8.0.1 dev tun0 table vpn_user_table

# 2. Правило по UID
sudo ip rule add uidrange 1001-1001 table vpn_user_table priority 1000

# 3. Запрет выхода через основной канал
sudo ip route add prohibit default table vpn_user_table metric 100
```

### Маркировка трафика (fwmark)

Для реализации сложной логики (например, маршрутизация HTTPS-трафика через быстрый канал) используется связка с Netfilter.

```bash
# nftables: установка метки для TCP/443
nft add rule inet filter prerouting tcp dport 443 meta mark set 0x1

# iproute2: выбор таблицы на основе метки
sudo ip rule add fwmark 0x1 table 101
```

### Взаимосвязь с DNAT (проброс портов)

При публикации сервисов на сервере с несколькими провайдерами PBR гарантирует, что ответный трафик от проброшенного порта вернется тому же провайдеру, через которого пришел запрос.

Подробные примеры конфигурации см. в разделе **[Сценарии PBR](./scenarios.md)**.

### Разделение трафика NTP

**Задача:** Направить NTP-трафик через стабильный канал (например, спутниковый или выделенный uplink), чтобы синхронизация времени не страдала от перегрузок в основном канале.

**Реализация:**

```bash
# 1. Таблица для NTP
echo "230 ntp_table" | sudo tee -a /etc/iproute2/rt_tables
sudo ip route add default via 192.168.3.1 dev eth2 table ntp_table

# 2. Правило для UDP/123
sudo ip rule add ipproto udp dport 123 table ntp_table priority 50
```

Подробные примеры настройки Dual-ISP, VPN-split-tunneling и балансировки см. в разделе **[Сценарии PBR](./scenarios.md)**.

## Персистентность конфигурации

По умолчанию изменения, внесенные через команды `ip`, являются эфемерными и сохраняются только до перезагрузки системы. Настройка персистентности зависит от используемого в дистрибутиве сетевого менеджера.

Краткий обзор методов:

| Метод | Файл / Команда | Поддерживаемые дистрибутивы |
| :--- | :--- | :--- |
| **NetworkManager** | `nmcli connection modify <name> +ipv4.routing-rules "from ... table ..."` | RHEL, CentOS, Alma, Rocky, Fedora |
| **Netplan** | `routing-policy:` в YAML-файле | Ubuntu 18.04+, Debian |
| **systemd-networkd** | Секция `[RoutingPolicyRule]` в `.network` файле | RHEL, Ubuntu, Debian, Arch |
| **/etc/network/interfaces** | `post-up` хуки | Debian legacy, Ubuntu legacy |
| **Скрипт в rc.local** | `ip rule restore < /etc/ip_rules.conf` | Универсальный метод |

Подробные инструкции по настройке персистентности см. в разделе **[Администрирование PBR](./administration.md)**.

### Бэкап и восстановление правил

Для ручного сохранения и восстановления правил используйте встроенные команды `ip`:

```bash
# Сохранение текущих правил IPv4
ip rule save > /etc/ip_rules_v4.conf

# Восстановление правил
sudo ip rule restore < /etc/ip_rules_v4.conf

# Для IPv6
ip -6 rule save > /etc/ip_rules_v6.conf
sudo ip -6 rule restore < /etc/ip_rules_v6.conf
```

## Диагностика и устранение неисправностей

### Проверка выбора маршрута (ip route get)

Самый важный инструмент для проверки PBR. Он позволяет увидеть, какую таблицу и шлюз выберет ядро для конкретного пакета без его реальной отправки.

```bash
# Эмуляция входящего пакета (проверка асимметрии)
ip route get 1.1.1.1 from 2.2.2.2 iif eth1

# Эмуляция исходящего пакета с меткой
ip route get 8.8.8.8 mark 0x1

# Проверка с указанием таблицы (явный запрос)
ip route get 8.8.8.8 table 100
```

### Типичные проблемы и решения

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| **Пакет дропается при входе** | Strict RPF (`rp_filter=1`) | Установить `net.ipv4.conf.<iface>.rp_filter = 2` (Loose mode). |
| **Маршрут игнорируется** | Конфликт приоритетов | Проверить `ip rule show`, переместить правило выше (меньший номер приоритета). |
| **Не работает SBR для IPv6** | Отсутствие `CONFIG_IPV6_MULTIPLE_TABLES` | Проверить конфиг ядра или использовать `ip -6 rule`. |
| **Метка не видна в PBR** | Маркировка в `POSTROUTING` | Перенести маркировку в `PREROUTING` или `MANGLE/OUTPUT` (до этапа маршрутизации). |
| **Таблица пуста** | Маршрут не добавлен в таблицу | Проверить `ip route show table <ID>`. |
| **"RTNETLINK answers: Invalid argument"** | Неверный синтаксис или неподдерживаемый селектор | Проверить версию ядра и синтаксис команды. |
| **"RTNETLINK answers: File exists"** | Правило с таким же селектором и приоритетом уже существует | Удалить существующее правило или изменить приоритет. |
| **Правило пропадает после перезагрузки** | Команды `ip rule` эфемерны | Настроить персистентность через NetworkManager, Netplan или systemd-networkd. |
| **Правило добавлено, но не работает** | Селектор не соответствует атрибутам пакета | Использовать `ip route get` с теми же параметрами (from, iif, fwmark). |

### Валидация после изменений

После добавления или изменения правил всегда проверяйте корректность:

```bash
# 1. Проверка наличия правила
ip rule show | grep "1000:"
# → 1000:	from 192.168.1.0/24 lookup vpn_table

# 2. Эмуляция выбора маршрута (без реальной отправки)
ip route get 8.8.8.8 from 192.168.1.50
# → 8.8.8.8 via 10.0.0.1 dev tun0 table vpn_table src 192.168.1.50

# 3. Проверка маршрута в целевой таблице
ip route show table vpn_table
# → default via 10.0.0.1 dev tun0

# 4. Проверка связи (если возможно)
ping -c 3 -I 192.168.1.50 8.8.8.8
```

Подробные методы отладки, мониторинг и способы сохранения конфигурации см. в разделе **[Администрирование PBR](./administration.md)**.

## Оптимизация и лучшие практики

1. **Всегда указывайте `priority`:** Без него правила добавляются с уменьшающимся приоритетом относительно последнего добавленного, что может нарушить логику PBR.
2. **Используйте осмысленные имена таблиц:** Записывайте их в `/etc/iproute2/rt_tables` и используйте в командах вместо числовых ID.
3. **Настраивайте `rp_filter = 2`:** При использовании PBR на многоканальных системах всегда переводите интерфейсы в режим Loose (2).
4. **Группируйте правила по функциональному назначению:** Используйте диапазоны приоритетов (см. таблицу выше).
5. **Избегайте `flush` в продакшене:** Всегда сохраняйте текущие правила (`ip rule save`) перед очисткой.
6. **Проверяйте после изменений:** Используйте `ip route get` для эмуляции выбора маршрута.
7. **Документируйте изменения:** Записывайте, какие правила добавлены и зачем.
8. **Используйте `ip -d rule show`:** Детальный вывод помогает обнаружить suppress_prefixlength и VRF-привязки.
9. **Маркируйте трафик до маршрутизации:** Помните, что `ip rule` срабатывает после `PREROUTING` и `OUTPUT`; маркировка в `POSTROUTING` не работает.

### Мониторинг статистики

В Linux нет встроенного счетчика попаданий (hit count) для правил `ip rule`. Для мониторинга активности правил рекомендуется использовать `nftables` со счетчиками для тех же критериев, что и в PBR.

```bash
# Создание счетчика для мониторинга трафика, подпадающего под PBR (метка 0x1)
nft add rule inet filter output meta mark 0x1 counter
```

### Очистка среды

```bash
# Удаление конкретного правила
sudo ip rule del from 10.0.0.0/8 table isp1_table priority 100

# Удаление всех правил с определенным приоритетом
for pri in $(seq 1000 1099); do
  sudo ip rule del priority $pri 2>/dev/null
done

# Проверка после удаления
ip rule show
# → Должны остаться только: local (0), main (32766), default (32767)
```

## Современные альтернативы и сравнение

### VRF (Virtual Routing and Forwarding)

**VRF** — более современный подход (ядро 4.4+). В отличие от PBR, где правила применяются к отдельным пакетам, VRF позволяет привязывать целые интерфейсы к изолированным доменам маршрутизации.

| Характеристика | PBR | VRF |
| :--- | :--- | :--- |
| **Уровень изоляции** | Пакетный (через правила) | Интерфейсный (доменный) |
| **Сложность настройки** | Средняя | Низкая (bind interface → done) |
| **Масштабируемость** | Ограничена размером RPDB | Высокая |
| **Производительность** | Выше (меньше overhead) | Средняя (доп. объекты ядра) |
| **Применение** | Тонкое управление трафиком | Изоляция сетей, Management VRF |

Подробнее см. в разделе **[VRF в Linux](../vrf.md)**.

## Дополнительная информация

### Влияние на производительность

Поскольку проверка RPDB происходит последовательно, большое количество правил (сотни и тысячи) может увеличить задержку обработки пакетов. Для массовой изоляции трафика (например, в облачных средах) предпочтительнее использовать VRF.

### Типичные вопросы на собеседовании

#### Теоретические

| Вопрос | Краткий ответ |
| :--- | :--- |
| **Что такое RPDB и как она работает?** | Routing Policy Database — база данных правил, проверяемых ядром от приоритета 0 к 32767. Первое совпавшее правило указывает таблицу для поиска маршрута. |
| **Чем `rp_filter=1` отличается от `rp_filter=2`?** | Strict (1) проверяет, что входящий интерфейс — оптимальный путь для ответа. Loose (2) проверяет лишь наличие любого маршрута к источнику. Strict несовместим с PBR. |
| **Почему `ip rule` срабатывает после PREROUTING?** | Потому что PBR решает, в какой таблице искать маршрут. PREROUTING обрабатывает пакет до маршрутизации; `ip rule` — это часть процесса маршрутизации. |
| **Что будет, если удалить правило local (priority 0)?** | Потеря связности: хост не сможет обрабатывать локальные, loopback и broadcast-адреса. |
| **PBR vs VRF — когда что использовать?** | PBR — для тонкого управления по атрибутам пакета (from, fwmark, dport). VRF — для полной изоляции интерфейсов (домены маршрутизации). |
| **Как работает CONNMARK?** | Сохраняет fwmark в ct mark записи conntrack (в PREROUTING) и восстанавливает его для ответных пакетов (в OUTPUT), обеспечивая симметричную маршрутизацию. |

#### Практические

| Вопрос | Краткий ответ |
| :--- | :--- |
| **Как проверить, какую таблицу выберет ядро?** | `ip route get <dst> from <src>` — эмуляция выбора маршрута без реальной отправки. |
| **Как настроить симметричную маршрутизацию через 2 ISP?** | CONNMARK: `nft add rule prerouting iifname "eth1" ct mark set 0x1` + `ip rule add fwmark 0x1 table isp1_table`. |
| **Почему fwmark в POSTROUTING не работает для PBR?** | POSTROUTING выполняется после маршрутизации. `ip rule` уже выбрал таблицу до POSTROUTING. |
| **Как обеспечить персистентность PBR после reboot?** | Systemd-networkd (`[RoutingPolicyRule]`), Netplan (`routing-policy:`), NetworkManager (`nmcli`), или systemd-сервис с `ip rule restore`. |
| **Как автоматизировать PBR на 100 серверах?** | Ansible: roles с шаблонами rt_tables, идемпотентные tasks для `ip rule`, `ip route replace`, sysctl через `ansible.posix.sysctl`. |
| **Как защититься от DDoS через PBR?** | Blackhole routing: `ip route add blackhole default table blackhole_table` + `ip rule add from <attacker_subnet> table blackhole_table`. |
