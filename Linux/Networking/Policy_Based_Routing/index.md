# Policy-Based Routing (PBR) в Linux

## Определения

**Policy-Based Routing (PBR)** — это механизм в ядре Linux, который позволяет выбирать таблицу маршрутизации на основе набора правил (политик). В отличие от традиционной маршрутизации (destination-routing), где решение принимается только на основе IP-адреса назначения, PBR позволяет учитывать другие параметры: IP-адрес источника, порт, протокол или даже метки пакетов (`fwmark`).

**SBR (Source-Based Routing)** — частный случай PBR, когда маршрутизация осуществляется на основе адреса источника (условие `from` в правиле маршрутизации).

---

## Basic Concepts

### Требования к ядру

Для поддержки PBR ядро Linux должно быть собрано с опциями:

- `CONFIG_IP_ADVANCED_ROUTER` — расширенный роутер
- `CONFIG_IP_MULTIPLE_TABLES` — поддержка множественных таблиц маршрутизации

Раздел ядра: `Networking support → Networking options → TCP/IP networking`.

### Принцип работы

Стандартная маршрутизация в Linux использует одну главную таблицу (`main`) для всех решений. PBR расширяет эту модель, позволяя создавать несколько независимых таблиц маршрутизации и определять, какую из них использовать для конкретного пакета.

```
┌─────────────────┐
│   Входящий      │
│    пакет        │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Проверка       │
│  ip rule (prio) │
└────────┬────────┘
         │
    ┌────┴────┐
    │         │
    ▼         ▼
┌───────┐ ┌─────────┐
│ local │ │  main   │
│table  │ │  table  │
└───────┘ └─────────┘
```

Процесс состоит из трех ключевых компонентов:

1. **Несколько таблиц маршрутизации**: Вы создаете кастомные таблицы, каждая со своим набором маршрутов (например, со своим шлюзом по умолчанию).
2. **Селекторы (Правила)**: С помощью команды `ip rule` вы создаете правила, которые определяют, по какому критерию выбирать таблицу. Правила проверяются по порядку (приоритету).
3. **Маркировка пакетов**: Часто для выбора нужных пакетов используется их маркировка с помощью `iptables` (таблица `mangle`, действие `MARK`). Правило `ip rule` затем ссылается на эту метку (`fwmark`).

### Селекторы правил (ip rule)

| Селектор | Описание | Пример |
| :--- | :--- | :--- |
| `from <IP>` | По исходному адресу | `from 192.168.1.100` |
| `to <IP>` | По адресу назначения | `to 10.0.0.0/8` |
| `iif <dev>` | По входящему интерфейсу | `iif eth1` |
| `oif <dev>` | По исходящему интерфейсу | `oif eth0` |
| `tos <value>` | По полю TOS IP-пакета (см. [Type of Service](../../../Networking/OSI_TCP_IP_Model/Network_layer/Protocols/ip_packet_structure.md)) | `tos 0x10` |
| `fwmark <mark>` | По метке iptables/nftables | `fwmark 0x2/0x2` |
| `sport/dport` | По порту источника/назначения | `sport 22` |
| `protocol` | По протоколу | `protocol tcp` |

**Комбинирование условий:** Условия можно комбинировать (например, `from 192.168.1.0/24 to 10.0.0.0/8`). Также доступен префикс `not`, исключающий пакеты, соответствующие условию.

**fwmark:** Наиболее гибкий селектор. При помощи `iptables` (таблица `mangle`) можно отфильтровать пакеты по множеству признаков и установить значения `FWMARK`, которые затем используются при роутинге.

### Сферы применения

- **Разделение трафика по разным каналам:** Например, направлять HTTP/S-трафик через один канал (VPN), а весь остальной трафик — напрямую.
- **Балансировка нагрузки:** Распределять трафик между несколькими интернет-провайдерами.
- **Изоляция сервисов:** Запрещать контейнерам доступ в интернет, но разрешать обмен данными в локальной сети.
- **Решение асимметричной маршрутизации:** Для серверов с несколькими интерфейсами в разных подсетях.

## Basic Concepts

### Проблема асимметричной маршрутизации

**Асимметричная маршрутизация** — ситуация, при которой входящий пакет приходит на один сетевой интерфейс, а ответный пакет уходит через другой.

**Причина возникновения:**
В системе с несколькими сетевыми интерфейсами в разных подсетях ядро Linux по умолчанию использует единую таблицу маршрутизации (`main`) для всех исходящих пакетов. При получении пакета на интерфейс `enp4s0` (IP `192.168.120.100`) ядро ищет маршрут для ответа на IP отправителя в таблице `main`. Если маршрут по умолчанию указывает на другой интерфейс (например, `enp2s0`), ответный пакет уйдёт через него с IP `192.168.110.100`.

**Почему это проблема:**

1. **Reverse Path Filtering (RP-filter)** — механизм безопасности ядра, который отбрасывает пакеты, если маршрут для ответа не совпадает с интерфейсом, на который пришёл запрос. Это защита от спуфинга и DDoS-атак.
2. **Разрыв соединений** — клиент ожидает ответ с того же IP, на который отправлял запрос. Если ответ приходит с другого IP, соединение не устанавливается.
3. **Проблемы с фаерволами** — stateful-фаерволы отслеживают состояние соединений и могут блокировать асимметричный трафик.

**Решение:** Использовать PBR для создания правила, которое предписывает использовать отдельную таблицу маршрутизации для пакетов, исходящих с конкретного IP-адреса интерфейса.

---

### Маршруты с метриками (ECMP и резервирование)

**Метрика маршрута** — числовое значение приоритета, определяющее порядок использования маршрутов при наличии нескольких путей к одной цели.

**Принцип работы:**

| Метрика | Описание |
| :--- | :--- |
| `100` | Основной маршрут (используется по умолчанию) |
| `200` | Резервный маршрут (используется при недоступности основного) |
| `300+` | Дополнительные резервные маршруты |

**Поведение ядра:**

- При наличии нескольких маршрутов по умолчанию с разными метриками ядро использует маршрут с **наименьшей метрикой**.
- Если основной маршрут становится недоступным (интерфейс down, шлюз не отвечает), ядро автоматически переключается на маршрут с следующей наименьшей метрикой.
- При восстановлении основного маршрута ядро **не всегда** автоматически возвращается на него — зависит от версии ядра и настроек.

**ECMP (Equal-Cost Multi-Path):**
Если несколько маршрутов имеют **одинаковую метрику**, ядро может балансировать трафик между ними (на уровне соединений, не пакетов).

**Ограничение метрик:**
Метрики влияют только на выбор маршрута в таблице `main`. Для PBR с отдельными таблицами маршрутизации метрики внутри каждой таблицы работают независимо.

### Резервирование каналов (Failover)

**Failover** — автоматическое переключение на резервный канал связи при отказе основного.

**Архитектура решения:**

```
                    ┌─────────────┐
                    │  Интернет   │
                    └──────┬──────┘
                           │
              ┌────────────┴────────────┐
              │                         │
       ┌──────▼──────┐           ┌──────▼──────┐
       │ Провайдер 1 │           │ Провайдер 2 │
       │  (основной) │           │ (резервный) │
       │ 192.168.50.1│           │192.168.150.1│
       └──────┬──────┘           └──────┬──────┘
              │                         │
       ┌──────▼──────┐           ┌──────▼──────┐
       │   enp0s3    │           │   enp0s8    │
       │ 192.168.50.2│           │192.168.150.2│
       └──────┴──────┴───────────┴──────┬──────┘
                                        │
                                ┌───────▼────────┐
                                │   Сервер       │
                                │  (мультихом)   │
                                └────────────────┘
```

**Компоненты системы:**

1. **Маршруты с метриками в таблице `main`:**
   - Основной маршрут: `metric 100`
   - Резервный маршрут: `metric 200`
   - Ядро использует маршрут с наименьшей метрикой

2. **Отдельные таблицы для PBR:**
   - Таблица `primary` (ID 100) — для трафика от основного IP
   - Таблица `secondary` (ID 200) — для трафика от резервного IP
   - Гарантируют симметричную маршрутизацию ответов

3. **Правила `ip rule`:**
   - `from 192.168.50.2 lookup primary` (priority 31000)
   - `from 192.168.150.2 lookup secondary` (priority 32000)
   - Обеспечивают ответ через тот же интерфейс, на который пришёл запрос

**Механизм переключения:**

| Событие | Действие ядра |
| :--- | :--- |
| Основной канал активен | Трафик через `enp0s3` (metric 100) |
| Основной канал недоступен | Удаление маршрута из таблицы, переключение на `enp0s8` (metric 200) |
| Восстановление основного | Добавление маршрута с metric 100, возврат на основной канал |

**Мониторинг доступности:**
Для автоматического переключения требуется внешний механизм мониторинга (скрипт, демон), который:

- Периодически проверяет доступность шлюза или внешнего хоста через каждый интерфейс
- Изменяет метрики маршрутов при обнаружении сбоя
- Возвращает исходные метрики при восстановлении

**Сценарии использования:**

- Домашние сети с двумя провайдерами
- Критичные серверы с требованием высокой доступности
- SD-WAN решения

### Взаимосвязь PBR и DNAT (проброс портов)

**Проблема:**
При настройке проброса портов (DNAT) на роутере для сервера с несколькими интерфейсами необходимо обеспечить симметричную маршрутизацию ответного трафика.

**Решение:**
PBR гарантирует, что ответный пакет будет отправлен через тот же интерфейс, на который поступил запрос:

```
Входящее соединение → Роутер (DNAT) → Интерфейс A (IP A)
                                           ↓
                                    Сервер (обработка)
                                           ↓
Ответное соединение ← Роутер (SNAT) ← Интерфейс A (IP A)
```

**Без PBR:**
Ответ может уйти через интерфейс B с IP B, что приведёт к:

- Разрыву соединения (клиент ожидает ответ с IP A)
- Блокировке фаерволом (asymmetric routing)

**С PBR:**
Правило `from IP_A lookup table_A` гарантирует ответ через интерфейс A.

**Пример для двух провайдеров:**

- Проброс порта 22 на `192.168.50.2` → ответ через `enp0s3`
- Проброс порта 22 на `192.168.150.2` → ответ через `enp0s8`

## Additional Information

### Порядок обработки правил

Ядро обрабатывает правила `ip rule` в порядке их **приоритета** (самое низкое число — самый высокий приоритет). По умолчанию правила добавляются с приоритетами, начиная с `32766` и ниже. Можно явно указать приоритет с помощью `priority <число>`.

**Стандартный набор правил:**

| Приоритет | Правило | Описание |
| :--- | :--- | :--- |
| `0` | `from all lookup local` | Локальная таблица (loopback, broadcast) |
| `1000` | (пользовательские) | PBR-правила |
| `32766` | `from all lookup main` | Основная таблица маршрутизации |
| `32767` | `from all lookup default` | Таблица по умолчанию |

Ваши правила будут вставлены между `local` и `main`, обеспечивая их проверку до стандартной маршрутизации.
