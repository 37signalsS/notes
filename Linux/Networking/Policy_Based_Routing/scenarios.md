## Practical Scenarios

### Сценарий 1: Разделение трафика по приложениям (VPN для браузера)

Рассмотрим пример, где нужно направлять трафик от веб-браузера через VPN, а SSH-трафик — напрямую.

Предположим, система имеет два сетевых интерфейса:

* `eth0` – основной канал в интернет (шлюз `192.168.1.1`).
* `tun0` – VPN-интерфейс (шлюз `10.8.0.1`).

**Важно:** Настройки `ip rule` и `ip route` не сохраняются после перезагрузки. Для постоянного применения добавьте команды в `/etc/network/interfaces`, `/etc/rc.local` или используйте systemd-networkd/NetworkManager.

#### 1. Создание дополнительных таблиц маршрутов

По умолчанию в Linux используется основная таблица `main`. Для PBR необходимо создать дополнительные. Имена таблиц и их числовые идентификаторы добавляются в файл `/etc/iproute2/rt_tables`.

```bash
# Добавляем таблицы, если они еще не существуют
sudo grep -qxF '100 vpn_table' /etc/iproute2/rt_tables || echo "100 vpn_table" | sudo tee -a /etc/iproute2/rt_tables
sudo grep -qxF '200 direct_table' /etc/iproute2/rt_tables || echo "200 direct_table" | sudo tee -a /etc/iproute2/rt_tables
```

**Проверка доступных таблиц:**

```bash
cat /etc/iproute2/rt_tables
```

#### 2. Добавление маршрутов в новые таблицы

Добавим маршруты по умолчанию для каждой таблицы, указывая соответствующий шлюз.

```bash
# Маршрут для прямого подключения через eth0
sudo ip route add default via 192.168.1.1 dev eth0 table direct_table

# Маршрут для подключения через VPN
sudo ip route add default via 10.8.0.1 dev tun0 table vpn_table
```

#### 3. Маркировка пакетов с помощью `iptables`

```bash
# Маркируем пакеты от пользователя 'browseruser' (под которым запущен браузер) меткой '1'
sudo iptables -t mangle -A OUTPUT -m owner --uid-owner browseruser -j MARK --set-mark 1

# Маркируем исходящий SSH-трафик (порт 22) меткой '2'
sudo iptables -t mangle -A OUTPUT -p tcp --dport 22 -j MARK --set-mark 2
```

**Важно:** Правила iptables также не сохраняются после перезагрузки. Используйте `iptables-save` и `iptables-restore` или пакет `iptables-persistent`.

#### 4. Создание правил маршрутизации

```bash
# Пакеты с меткой 1 направлять в таблицу 'vpn_table'
sudo ip rule add fwmark 1 table vpn_table

# Пакеты с меткой 2 направлять в таблицу 'direct_table'
sudo ip rule add fwmark 2 table direct_table
```

Теперь весь трафик от пользователя `browseruser` пойдет через VPN, а SSH-трафик — напрямую. Остальной трафик будет использовать стандартную таблицу `main`.

**Проверка конфигурации:**

```bash
# Показать все правила с приоритетами
ip rule show

# Показать маршруты в таблицах
ip route show table vpn_table
ip route show table direct_table
```

### Сценарий 2: Решение проблемы асимметричной маршрутизации

Это классическая проблема для серверов с несколькими сетевыми интерфейсами в разных подсетях.

**Проблема:**
Представим сервер с двумя IP-адресами:

* `ens3`: `10.0.4.101/24` со шлюзом по умолчанию `10.0.4.1` (прописан в таблице `main`).
* `ens5`: `10.0.5.101/24` (интерфейс для управления), шлюз для этой сети `10.0.5.1`.

Когда пакет приходит на адрес `10.0.5.101` (например, пинг с хоста `10.0.2.101`), ядро Linux должно отправить ответ. При поиске маршрута для ответа на `10.0.2.101` оно обращается к основной таблице маршрутизации (`main`), где видит, что этот адрес доступен через шлюз `10.0.4.1`. В итоге ответный пакет уходит с интерфейса `ens3` (с IP `10.0.4.101`), а не с `ens5` (с IP `10.0.5.101`), на который пришел запрос.

Такое поведение (входящий пакет на один интерфейс, а исходящий — с другого) называется **асимметричной маршрутизацией**. По умолчанию ядро Linux блокирует такие ответы из соображений безопасности и предсказуемости сети (см. **reverse path filtering**).

**Решение:**
Создать отдельную таблицу маршрутизации для интерфейса `ens5` и правило, которое будет заставлять весь трафик, **исходящий с IP-адреса `10.0.5.101`**, использовать эту новую таблицу.

#### 1. Создание таблицы маршрутизации

Добавим новую таблицу с именем `mgmt_table` и ID `200` в `/etc/iproute2/rt_tables`.

```bash
echo "200 mgmt_table" | sudo tee -a /etc/iproute2/rt_tables
```

#### 2. Добавление маршрутов в новую таблицу

Добавим в таблицу `mgmt_table` маршрут по умолчанию, который будет использовать шлюз в сети управления.

```bash
sudo ip route add default via 10.0.5.1 dev ens5 table mgmt_table
```

Можно также добавить более конкретный маршрут, если не нужен полный доступ:

```bash
# Например, маршрут только до локальных сетей
sudo ip route add 10.0.0.0/8 via 10.0.5.1 dev ens5 table mgmt_table
```

#### 3. Создание правила маршрутизации

Это ключевой шаг. Мы создаем правило, которое использует селектор `from`.

```bash
sudo ip rule add from 10.0.5.101 table mgmt_table priority 1000
```

Это правило гласит: "Если исходящий пакет имеет source IP `10.0.5.101`, для поиска маршрута используй `mgmt_table`". Приоритет `1000` ставит это правило выше стандартного правила для таблицы `main` (`32766`).

Теперь, когда ядро будет отправлять ответный пакет с IP `10.0.5.101`, оно сначала проверит правила `ip rule`, найдет наше правило с приоритетом `1000`, обратится к таблице `mgmt_table` и отправит пакет через правильный шлюз `10.0.5.1` на интерфейсе `ens5`. Проблема асимметричной маршрутизации решена.

**Проверка:**

```bash
# Убедиться, что правило добавлено
ip rule show | grep mgmt_table

# Проверить маршрут для пакета с IP 10.0.5.101
ip route get 10.0.2.101 from 10.0.5.101
```

### Сценарий 3: Балансировка трафика между аплинками

Балансировка нагрузки между несколькими провайдерами реализуется через множественные шлюзы по умолчанию с указанием весов (`weight`).

```bash
# Балансировка между двумя провайдерами
sudo ip route replace default scope global \
    nexthop via 11.22.33.1 dev eth0 weight 1 \
    nexthop via 55.66.77.1 dev eth1 weight 1
```

**Принцип работы:**

* Маршрут выбирается в зависимости от веса шлюза
* При весах `7` и `3` через первый шлюз уйдёт ~70% соединений, через второй — ~30%
* Распределение происходит на уровне соединений (не пакетов)

**Важно — кэширование маршрутов:**

Ядро кэширует маршруты, поэтому маршрут для конкретного хоста через определённый шлюз может оставаться в таблице некоторое время после последнего обращения. Для часто используемых хостов маршрут может не успевать сбрасываться и постоянно обновляться в кэше.

```bash
# Очистка кэша маршрутов (при необходимости)
sudo ip route flush cache
```

> **Примечание:** Команда `ip route flush cache` работает только для кэшированных маршрутов. В современных ядрах (с 4.19+) кэш маршрутов удалён, команда не требуется.

### Сценарий 4: Маркировка соединений через CONNMARK

Модуль `iptables CONNMARK` позволяет отслеживать и маркировать все пакеты, относящиеся к определённому соединению. Это полезно для маркировки входящих пакетов в цепочке `INPUT` и автоматического восстановления меток для исходящих пакетов в цепочке `OUTPUT`.

```bash
# Маркировка входящих соединений по интерфейсам
iptables -t mangle -A INPUT -i eth0 -j CONNMARK --set-mark 0x2
iptables -t mangle -A INPUT -i eth1 -j CONNMARK --set-mark 0x4

# Восстановление меток для исходящих пакетов
iptables -t mangle -A OUTPUT -j CONNMARK --restore-mark
```

**Принцип работы:**

1. Пакеты, приходящие с `eth0`, маркируются значением `2`
2. Пакеты, приходящие с `eth1`, маркируются значением `4`
3. Для всех исходящих пакетов проверяется принадлежность к соединению и восстанавливается метка, заданная для входящих

**Пример использования с PBR:**

```bash
# Маркировка пакетов на 80 порт
iptables -t mangle -A OUTPUT -p tcp --dport 80 -j MARK --set-mark 0x2

# Создание таблицы маршрутизации
ip route add default via 11.22.33.1 dev eth0 table 102

# Направление пакетов с меткой в таблицу
ip rule add fwmark 0x2/0x2 lookup 102
```

Маска `0x2/0x2` означает точное совпадение с меткой `0x2`.
