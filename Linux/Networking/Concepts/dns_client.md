# Настройка и диагностика DNS-клиента в Linux

## Определения

**DNS-клиент** — программное обеспечение или компонент ОС, ответственный за разрешение доменных имён в IP-адреса и наоборот. В Linux управляется комбинацией конфигурационных файлов и служб.

## Базовые концепции

Разрешение доменных имён в Linux управляется несколькими файлами и службами, работающими в определённом порядке.

### Порядок разрешения имён

```
Приложение (браузер, curl)
    ↓
Системный резолвер (glibc)
    ↓
/etc/nsswitch.conf (порядок: files → dns)
    ↓
┌─────────────────┬─────────────────┐
│   /etc/hosts    │   DNS-серверы   │
│   (локально)    │   (резолвер)    │
└─────────────────┴─────────────────┘
```

## Практические сценарии

### 1. Порядок разрешения имен: `/etc/nsswitch.conf`

Файл `nsswitch.conf` (Name Service Switch) — это главный конфигурационный файл, который определяет, где и в каком порядке система будет искать информацию, включая имена хостов.

За это отвечает строка, начинающаяся с `hosts:`.

```
# /etc/nsswitch.conf
...
# Сначала проверить локальные файлы (/etc/hosts), затем обратиться к DNS.
hosts:          files dns
...
```

* **`files`**: Означает, что сначала нужно посмотреть в файле `/etc/hosts`.
* **`dns`**: Означает, что если имя не найдено в `files`, нужно отправить запрос к DNS-серверам.
* **`mymachines`**: Используется `systemd-machined` для разрешения имен локальных контейнеров и виртуальных машин.
* **`mdns_minimal [NOTFOUND=return]`**: Используется для разрешения `.local` доменов через Multicast DNS (Avahi/Bonjour).

Порядок имеет значение. Стандартный `files dns` является наиболее распространенным и предсказуемым.

### 2. Локальная база данных: `/etc/hosts`

Этот файл представляет собой простую статическую таблицу соответствия IP-адресов и доменных имен.

* **Приоритет:** Записи в этом файле имеют наивысший приоритет (если `files` идет первым в `nsswitch.conf`). Система проверяет его **до** обращения к внешним DNS-серверам. Это означает, что если запись для домена найдена в `/etc/hosts`, DNS-запрос к внешним серверам не будет отправлен.
* **Формат:** `IP-адрес полное_имя_хоста короткое_имя`

    ```
    127.0.0.1   localhost
    10.20.30.40 fileserver.mycompany.local fileserver
    ```

### Вектор атаки: /etc/hosts

> **Безопасность:** Вредоносное ПО может добавлять записи в `/etc/hosts` для перенаправления трафика с легитимных сайтов на фишинговые IP-адреса.

**Пример атаки:**

```
# Злоумышленник добавляет:
185.199.108.153 github.com
```

**Проверка целостности:**

```bash
# Сверить с известными записями
cat /etc/hosts

# Проверить изменения файла (если используется auditd)
ausearch -f /etc/hosts -i
```

#### Поведение запущенных процессов при изменении `/etc/hosts`

**Важно:** Большинство запущенных процессов и приложений кэшируют результаты разрешения доменных имен (в том числе из `/etc/hosts`) для повышения производительности. При изменении файла `/etc/hosts` запущенные процессы обычно **не перечитывают его немедленно**. Они будут продолжать использовать информацию, которая была загружена в их кэш на момент запуска или последнего обращения к резолверу. Чтобы процесс обновил информацию, его, как правило, необходимо перезапустить или принудительно очистить его внутренний кэш (если такая функция предусмотрена).

**Вопрос:** Удалили запись в `/etc/hosts`, на которую полагался запущенный процесс. Что произойдет?

**Ответ:** Процесс продолжит использовать кеш DNS, и изменения не будут применены до перезапуска процесса или его кэша.

### 3. Классический DNS-клиент: `/etc/resolv.conf`

Этот файл напрямую указывает системе, какие DNS-серверы использовать для запросов.
Подробнее об управлении этим файлом в контексте постоянной настройки сети см. в [Постоянная настройка сети в Linux](../Settings/Persistent_Network/systemd_networkd.md).

**Важно:** В системах с NetworkManager файл `/etc/resolv.conf` обычно **генерируется автоматически** при каждом перезапуске сети или системы. Ручные изменения в этом файле могут быть перезаписаны. Для постоянных настроек DNS используйте `nmcli`, `nmtui` или `netplan`.

* **`nameserver`**: IP-адрес DNS-сервера. Можно указать несколько (обычно до 3), опрашиваются по порядку.
* **`search`**: Список доменных суффиксов. Если вы пытаетесь обратиться к хосту по короткому имени (например, `ping server1`), система автоматически попробует добавить к нему домены из списка `search`.
* **`options`**: Дополнительные параметры, например `timeout:1` (таймаут ожидания ответа 1 секунда).

**Пример:**

```
# /etc/resolv.conf

# Искать хосты в домене mycompany.local
search mycompany.local

# DNS-серверы для запросов
nameserver 192.168.1.1
nameserver 8.8.8.8
```

С такой конфигурацией, при `ping server1`, система сначала попытается найти `server1.mycompany.local`.

### Влияние конфигурации на производительность

Некорректная настройка `/etc/resolv.conf` может приводить к задержкам на этапе DNS-резолвинга. Подробнее о диагностике и оптимизации — в [Диагностика DNS-блокировок](../../Diagnostics/Networking/dns/overview.md#сценарий-5-dns-resolution-как-узкое-место-производительности).

## Дополнительная информация

### systemd-resolved: детальная конфигурация

В современных дистрибутивах (Ubuntu 17.10+, CentOS/RHEL 7+, Debian 10+) за разрешение имён отвечает `systemd-resolved`.

#### Конфигурационный файл

**`/etc/systemd/resolved.conf`:**

```ini
[Resolve]
# DNS-серверы (через пробел)
DNS=8.8.8.8 1.1.1.1

# Локальные домены для поиска
Domains=mycompany.local

# Отключить LLMNR (Local Link Multicast Name Resolution)
LLMNR=no

# Отключить Multicast DNS
MulticastDNS=no

# Включить DNSSEC (требуется поддержка серверами)
DNSSEC=yes

# Кэширование (yes/no)
Cache=yes
```

**Применение изменений:**

```bash
sudo systemctl restart systemd-resolved
```

#### Диагностика systemd-resolved

```bash
# Статус и текущие DNS-серверы
resolvectl status

# Статистика кэша и запросов
resolvectl statistics

# Очистка кэша
resolvectl flush-caches

# Тестовый запрос (через systemd-resolved)
resolvectl query example.com

# Проверка, какие DNS-серверы используются для домена
resolvectl domain
```

#### Проблемы и решения

| Проблема | Диагностика | Решение |
|----------|-------------|---------|
| `/etc/resolv.conf` перезаписывается | Файл symlink на `/run/systemd/resolve/stub-resolv.conf` | Настроить DNS в `resolved.conf` или networkd |
| Медленное разрешение имён | `resolvectl statistics` показывает высокий cache miss | Включить кэширование, проверить DNSSEC |
| Конфликт с NetworkManager | Оба сервиса пытаются управлять DNS | Отключить один из сервисов или настроить координацию |

#### Интеграция с NetworkManager

NetworkManager может управлять `systemd-resolved`:

```bash
# Проверить текущий DNS-плагин NM
cat /etc/NetworkManager/conf.d/*.conf

# Отключить управление DNS со стороны NM
# /etc/NetworkManager/NetworkManager.conf
[main]
dns=none

# Или использовать systemd-resolved
[main]
dns=systemd-resolved
```
