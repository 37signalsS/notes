# DNS-клиент в Linux: конфигурация и принципы работы

**Reliability Score: 10 (SSoT + Web)**

## Определения

**DNS-клиент (Domain Name System — система доменных имен)** — системный компонент или прикладное ПО, ответственное за преобразование доменных имен в IP-адреса и обратно. В Linux этот процесс реализуется через библиотеки системного уровня (glibc) и специализированные службы (systemd-resolved).

**Системный резолвер (glibc resolver)** — набор функций в стандартной библиотеке C (GNU C Library), которые приложения вызывают для разрешения имен. Его поведение определяется конфигурационными файлами NSS и параметрами резолвера.

**NSS (Name Service Switch — переключатель служб имен)** — механизм, позволяющий выбирать источники данных для различных системных баз (хосты, пользователи, группы). Источники для имен хостов настраиваются в файле `/etc/nsswitch.conf`.

**Stub-резолвер (заглушка)** — локальный DNS-сервер (обычно `systemd-resolved` на `127.0.0.53`), который принимает запросы от системного резолвера и пересылает их внешним (upstream) серверам, обеспечивая кэширование и поддержку современных протоколов.

**FQDN (Fully Qualified Domain Name — полностью определенное доменное имя)** — имя хоста, включающее все уровни иерархии DNS, заканчивающееся точкой (например, `example.com.`). В Linux-конфигурациях точка в конце часто опускается, но она критически важна для однозначного определения имени.

## Основные концепции

### Цепочка разрешения имени

Разрешение имен в Linux — это многоуровневый процесс. Приложение не «идет в DNS» напрямую; оно обращается к библиотеке, которая следует заданному алгоритму.

1.  **Приложение** вызывает функцию `getaddrinfo()` или `gethostbyname()`.
2.  **Библиотека glibc** читает `/etc/nsswitch.conf` (строка `hosts:`).
3.  **Обращение к источникам (по порядку):**
    *   `files` → Проверка локального файла `/etc/hosts`.
    *   `resolve` (или `dns`) → Запрос к службе `systemd-resolved` или напрямую к серверам из `/etc/resolv.conf`.
    *   `mdns_minimal` → Поиск в локальной сети для доменов `.local`.
4.  **Кэширование:** Если ответ найден в локальном кэше (systemd-resolved или nscd), он возвращается немедленно.

**Важное исключение:** Некоторые среды выполнения (например, Go при компиляции без CGO, Java) или контейнеры могут игнорировать NSS и читать `/etc/resolv.conf` напрямую. В таких случаях записи в `/etc/hosts` могут игнорироваться.

### Конфигурационные файлы и их роль

| Файл | Описание |
| :--- | :--- |
| `/etc/nsswitch.conf` | Определяет приоритеты: искать сначала в файлах или в DNS. |
| `/etc/hosts` | Статическая таблица IP ↔ Имя. Имеет наивысший приоритет (обычно). |
| `/etc/resolv.conf` | Список DNS-серверов и параметры поиска. В современных системах это симлинк. |
| `/etc/systemd/resolved.conf` | Основной конфиг службы `systemd-resolved` (DoT, DoH, DNSSEC, кэш). |

### Режимы работы /etc/resolv.conf

В современных дистрибутивах (Ubuntu 18.04+, RHEL 8+, Debian 11+) файл `/etc/resolv.conf` управляется службой `systemd-resolved`. Существует три основных режима:

1.  **Stub-режим (рекомендуется):** Симлинк на `/run/systemd/resolve/stub-resolv.conf`. Содержит `nameserver 127.0.0.53`. Позволяет использовать кэширование и раздельный DNS для разных интерфейсов (**Split DNS**).
2.  **Статический режим:** Обычный файл, созданный администратором. Службы игнорируют его, но кэширование и Split DNS отключаются.
3.  **Uplink-режим:** Симлинк на `/run/systemd/resolve/resolv.conf`. Содержит реальные IP-адреса внешних DNS-серверов, полученные по DHCP/VPN. Системный резолвер обращается к ним напрямую, минуя локальную заглушку.

## Практические сценарии

### 1. Управление через resolvectl

Для диагностики и настройки `systemd-resolved` следует использовать `resolvectl` вместо ручной правки файлов.

```bash
# Просмотр текущих серверов и состояния для каждого интерфейса
resolvectl status

# Проверка разрешения конкретного имени через службу
# → Показывает, через какой интерфейс и какой сервер прошел запрос
resolvectl query google.com

# Сброс локального DNS-кэша
resolvectl flush-caches

# Статистика попаданий в кэш и безопасности (DNSSEC)
resolvectl statistics
```

### 2. Сравнение системного и прямого разрешения

Если приложение не может найти хост, который «пингуется» через `dig`, проблема в цепочке NSS.

*   **Системный тест (NSS):** `getent ahosts example.com` — показывает, что видит ОС (учитывает `/etc/hosts`).
*   **Прямой тест (DNS):** `dig example.com +short` — опрашивает только DNS-серверы.

Если `getent` возвращает старый IP, который отсутствует в выводе `dig`, проверьте `/etc/hosts` или кэш `systemd-resolved`.

### 3. Оптимизация производительности (ndots и timeout)

Параметры в `/etc/resolv.conf` могут критически влиять на скорость работы приложений, особенно в облачных средах и Kubernetes.

*   **`ndots:5`:** Если в имени меньше 5 точек, резолвер будет перебирать все суффиксы из списка `search`, прежде чем попробует разрешить имя как FQDN. Это замедляет внешние запросы.
*   **`timeout:1` / `attempts:2`:** Ускоряет переключение на резервный DNS-сервер при сбое основного.

```bash
# Пример настройки через systemd-resolved
# /etc/systemd/resolved.conf
[Resolve]
DNS=1.1.1.1 8.8.8.8
Domains=~.
```

### 4. Настройка DNS over TLS (DoT) и DNS over HTTPS (DoH)

Для защиты DNS-трафика от перехвата и подмены используются современные протоколы шифрования.

```ini
# /etc/systemd/resolved.conf
[Resolve]
# DNS over TLS (DoT)
DNS=1.1.1.1#cloudflare-dns.com 8.8.8.8#dns.google
DNSOverTLS=yes

# DNS over HTTPS (DoH) - доступно в новых версиях systemd (v248+)
# DNS=https://cloudflare-dns.com/dns-query
```

После изменения перезапустите службу: `sudo systemctl restart systemd-resolved`.

### 5. Решение проблем с Split DNS в VPN

При подключении к VPN часто требуется, чтобы запросы к корпоративным доменам (`*.corp.internal`) шли через VPN-сервер, а все остальные — через обычный DNS.

`systemd-resolved` автоматически поддерживает это через параметры `Domains=`:
*   `Domains=corp.internal` (без тильды) — направляет только этот домен на интерфейс.
*   `Domains=~.` (с тильдой) — делает интерфейс предпочтительным для всех запросов (Default Route).

## Дополнительная информация

### Конфликты менеджеров сети

Частая проблема — одновременная попытка **NetworkManager** и **systemd-resolved** управлять файлом `/etc/resolv.conf`.

*   **Решение для NetworkManager:** Убедитесь, что в `/etc/NetworkManager/NetworkManager.conf` в секции `[main]` указано `dns=systemd-resolved`. Это заставит NM передавать полученные настройки резолверу.
*   **Режим только для чтения:** Если нужно заблокировать файл от изменений любыми службами, используйте `chattr +i /etc/resolv.conf` (крайняя мера).

### Тонкости mDNS и LLMNR

Служба `systemd-resolved` поддерживает протоколы LLMNR и mDNS для поиска устройств в локальной сети без DNS-сервера.

*   **mDNS (Multicast DNS):** Использует домен `.local`. Полезен в сетях с Apple-устройствами и Linux (Avahi).
*   **LLMNR (Link-Local Multicast Name Resolution):** Используется Windows-системами.

Если возникают задержки при запросах к несуществующим доменам, эти протоколы можно отключить в `resolved.conf` (`LLMNR=no`, `MulticastDNS=no`).
