# DNS-клиент в Linux: конфигурация и принципы работы

## Определения

**DNS-клиент** — программное обеспечение или компонент ОС, ответственный за разрешение доменных имён в IP-адреса и наоборот. В Linux управляется комбинацией конфигурационных файлов и служб.

**Системный резолвер (glibc)** — механизм, использующий `/etc/nsswitch.conf` для определения порядка и источников разрешения имён.

**NSS (Name Service Switch)** — механизм Linux, определяющий источники данных для разрешения имён: локальные файлы (`files`), DNS (`dns`), mDNS (`mdns_minimal`) и другие.

## Базовые концепции

### Порядок разрешения имён

Разрешение доменных имён в Linux — многоэтапный процесс, управляемый конфигурационными файлами в строго определённом порядке.

```
Приложение (браузер, curl)
    ↓
Системный резолвер (glibc)
    ↓
/etc/nsswitch.conf (порядок: files → dns)
    ↓
┌─────────────────┬─────────────────┐
│   /etc/hosts    │   DNS-серверы   │
│   (локально)    │   (резолвер)    │
└─────────────────┴─────────────────┘
    ↓
DNS-кэш ОС (если включён, например systemd-resolved)
    ↓
┌─────────────────────────────────┐
│  Корневые DNS-серверы (.)       │
│  → TLD-серверы (.com, .ru)      │
│  → Авторитетные серверы         │
└─────────────────────────────────┘
```

> **Диагностика порядка разрешения:** [Порядок разрешения имён](../../Diagnostics/Networking/dns/name_resolution.md)

### Файлы конфигурации

| Файл | Назначение |
| :--- | :--- |
| `/etc/nsswitch.conf` | Порядок разрешения (строка `hosts:`) |
| `/etc/hosts` | Локальная статическая таблица IP ↔ имя (наивысший приоритет) |
| `/etc/resolv.conf` | DNS-серверы, search-домены, опции резолвера |
| `/etc/systemd/resolved.conf` | Параметры `systemd-resolved` (кэширующий резолвер) |

> **Диагностика конфигурации:** [Конфигурация DNS-клиента](../../Diagnostics/Networking/dns/configuration.md)

## Практические сценарии

### 1. `/etc/nsswitch.conf` — порядок разрешения

Строка `hosts:` определяет последовательность источников и условия перехода между ними:

```
hosts:          files mdns_minimal [NOTFOUND=return] dns
```

| Источник | Описание |
| :--- | :--- |
| `files` | Проверка `/etc/hosts` (локальные переопределения) |
| `dns` | Запрос к DNS-серверам из `/etc/resolv.conf` |
| `mymachines` | Разрешение имён локальных контейнеров/ВМ (`systemd-machined`) |
| `mdns_minimal` | Multicast DNS для `.local` доменов (Avahi/Bonjour) |

#### Логика условий (Status Action)

В квадратных скобках указываются условия, которые могут остановить цепочку. Например, `[NOTFOUND=return]` означает: «если имя не найдено в этом источнике, прекратить поиск и не переходить к следующему».

### 2. Проверка системного резолвинга (getent)

Для проверки того, как система **на самом деле** видит имя, следует использовать `getent`, а не `dig` или `nslookup`.

* **`getent hosts <domain>`** — использует системные библиотеки (glibc) и проходит по всей цепочке из `nsswitch.conf`.
* **`dig <domain>`** — обращается напрямую к DNS-серверу, игнорируя `/etc/hosts` и настройки NSS.

Если `getent` и `dig` возвращают разные IP — проблема в локальной конфигурации (`/etc/hosts` или порядок в `nsswitch.conf`).

### 3. `/etc/hosts` — локальная база данных

Статическая таблица соответствия IP-адресов и доменных имён.

* **Приоритет:** наивысший (если `files` первый в `nsswitch.conf`). Если запись найдена в `/etc/hosts`, DNS-запрос не отправляется.
* **Формат:** `IP-адрес полное_имя_хоста короткое_имя`

    ```
    127.0.0.1   localhost
    10.20.30.40 fileserver.mycompany.local fileserver
    ```

#### Вектор атаки

Вредоносное ПО может добавлять записи для перенаправления трафика на фишинговые IP-адреса. Запущенные процессы кэшируют результаты разрешения и **не перечитывают** файл немедленно — требуется перезапуск процесса или очистка кэша резолвера.

```
# Пример атаки:
185.199.108.153 github.com
```

#### Кэширование запущенными процессами

Большинство процессов кэшируют результаты разрешения на момент запуска или последнего обращения к резолверу. При изменении `/etc/hosts` запущенные процессы **не обновляют кэш автоматически** — требуется перезапуск процесса или очистка кэша резолвера (`resolvectl flush-caches`).

### 3. `/etc/resolv.conf` — DNS-серверы

Файл указывает системе, какие DNS-серверы использовать для запросов.

> **Постоянная настройка:** в системах с NetworkManager файл генерируется автоматически. Ручные изменения перезаписываются. Для постоянной настройки используйте `nmcli`, `nmtui` или `netplan`. Подробнее: [Постоянная настройка сети в Linux](../../Settings/Persistent_Network/systemd_networkd.md).

| Директива | Описание |
| :--- | :--- |
| `nameserver` | IP DNS-сервера (до 3, опрашиваются по порядку) |
| `search` | Список доменных суффиксов для коротких имён |
| `options` | Дополнительные параметры (например `timeout:1`) |

**Пример:**

```
search mycompany.local

nameserver 192.168.1.1
nameserver 8.8.8.8
```

При `ping server1` система сначала попытается найти `server1.mycompany.local`.

> **Влияние на производительность:** некорректная настройка `/etc/resolv.conf` вызывает задержки DNS-резолвинга. Диагностика и оптимизация: [DNS resolution как узкое место производительности](../../Diagnostics/Networking/dns/dns_resolution_performance.md).

## Дополнительная информация

### systemd-resolved

В современных дистрибутивах (Ubuntu 17.10+, RHEL 7+, Debian 10+) за разрешение имён отвечает `systemd-resolved` — локальный кэширующий резолвер, выступающий посредником между приложениями и реальными DNS-серверами.

**Зачем он нужен:**

* **Раздельный DNS под каждый интерфейс (per-link):** VPN, Wi-Fi и Ethernet не затирают настройки друг друга.
* **Кэширование:** повторные запросы не уходят в сеть, ускоряя резолвинг.
* **Современные протоколы:** поддержка DNSSEC, DNS-over-TLS (DoT), LLMNR и mDNS для локальных сетей.

**Принцип работы:**

1. Поднимает локальный DNS-сервер на адресе `127.0.0.53:53` (stub-резолвер).
2. `/etc/resolv.conf` превращается в симлинк на `/run/systemd/resolve/stub-resolv.conf`.
3. Все приложения отправляют запросы на `127.0.0.53`. Служба сама решает, на какой upstream-сервер переслать запрос в зависимости от интерфейса и домена.

#### Конфигурация: `/etc/systemd/resolved.conf`

```ini
[Resolve]
# DNS-серверы (через пробел)
DNS=8.8.8.8 1.1.1.1

# Локальные домены для поиска
Domains=mycompany.local

# Отключить LLMNR (Local Link Multicast Name Resolution)
LLMNR=no

# Отключить Multicast DNS
MulticastDNS=no

# Включить DNSSEC (требуется поддержка серверами)
DNSSEC=yes

# Кэширование (yes/no)
Cache=yes
```

**Применение изменений:**

```bash
sudo systemctl restart systemd-resolved
```

> **Диагностика systemd-resolved:** [Конфигурация DNS-клиента](../../Diagnostics/Networking/dns/configuration.md) — сценарии проверки и устранения проблем.

### Интеграция с NetworkManager

NetworkManager может координировать работу с `systemd-resolved`:

```ini
# /etc/NetworkManager/NetworkManager.conf
[main]
# Отключить управление DNS со стороны NM
dns=none

# Или делегировать systemd-resolved
dns=systemd-resolved
```

Конфликт возникает, когда обе службы пытаются управлять `/etc/resolv.conf` — DNS работает нестабильно, файл перезаписывается.
