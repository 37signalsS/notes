# Оптимизация сетевых каналов и снижение латентности

## Определения

**Сетевая латентность (Network Latency — сетевая задержка)** — временной интервал между отправкой запроса и получением ответа. Измеряется как задержка в одну сторону (One-Way Delay) или в обе (**RTT — Round-Trip Time**).

**Bufferbloat (Раздувание буфера)** — деградация качества связи из-за избыточной буферизации пакетов в промежуточных узлах или на сетевой карте, что приводит к росту задержек и джиттера при высокой нагрузке.

**Хвостовая латентность (Tail Latency)** — показатели задержки для наихудших сценариев (перцентили **p95**, **p99**, **p99.9**). Именно они определяют «ощущаемую» производительность распределенных систем.

**Джиттер (Jitter)** — колебание (вариация) сетевой задержки во времени. Критичен для приложений реального времени (VoIP, видеостриминг, биржевая торговля).

**Zero-copy** — технология передачи данных, исключающая их копирование между пространствами пользователя и ядра, что радикально снижает нагрузку на CPU и латентность.

**Pacing (Сглаживание)** — механизм равномерного распределения пакетов во времени. Позволяет избежать всплесков трафика (Bursts), которые могут привести к потерям на коммутаторах с малым объемом памяти.

**EDT (Earliest Departure Time)** — современная модель планирования в Linux (начиная с ядра 4.19), где каждому пакету назначается временная метка выхода. Это обеспечивает сверхточный pacing, не требующий создания множества мелких очередей.

## Базовые концепции

### Компоненты общей задержки

Латентность является производной от четырех физических и логических факторов:

1.  **Задержка распространения (Propagation Delay):** Ограничена скоростью света в среде передачи (волокно ~200 000 км/с, медь ~200 000 км/с). Для 1000 км оптоволокна — минимум 5 мс в одну сторону. Это физический предел, который нельзя устранить программно.
2.  **Задержка сериализации (Serialization Delay):** Время на преобразование данных в битовый поток. Зависит от пропускной способности канала и размера пакета. Формула: `PacketSize / Bandwidth`. На 10 Gbps пакет 64 байта = 51.2 нс; на 1 Gbps = 512 нс. На низкоскоростных линках (100 Mbps) сериализация становится доминирующим фактором.
3.  **Задержка обработки (Processing Delay):** Время на деинкапсуляцию, проверку контрольных сумм, фильтрацию iptables/nftables, принятие решения о маршрутизации. В ядре Linux включает прохождение через SoftIRQ, NAPI, netfilter hooks. На современном CPU составляет 1–10 мкс на пакет.
4.  **Задержка в очередях (Queuing Delay):** Время ожидания в буферах NIC, qdisc, коммутаторов при перегрузке интерфейсов. Это единственный компонент, который можно эффективно оптимизировать программно. При Bufferbloat может достигать сотен миллисекунд.

### Влияние аппаратного обеспечения

На сверхнизких задержках (микросекунды) критичными становятся факторы хоста:

*   **NUMA-эффекты:** Доступ к сетевой карте из ядра CPU, находящегося на другом процессорном сокете, увеличивает задержку из-за использования шин QPI/UPI. Привязка IRQ и приложения к родной NUMA-ноде NIC снижает задержку на 50–200%.
*   **CPU Power Management:** Переход процессора в глубокие состояния сна (**C-states**, особенно C6/C7) и изменение частоты (**P-states**) вносят непредсказуемые задержки при «пробуждении» для обработки пакета. Для latency-sensitive workloads отключают через `intel_pstate=no_hwp` или `cpufreq` governor `performance`.
*   **PCIe Latency:** Задержки на шине PCIe при передаче данных от NIC в RAM. На PCIe 3.0 x16 — около 1–2 мкс; на PCIe 4.0 — вдвое меньше. Важно использовать максимальный линкс宽度, поддерживаемый NIC.
*   **Кэш-промахи (Cache Misses):** Если обработчик прерывания NIC и приложение выполняются на разных ядрах, данные не попадают в L1/L2 кэш, что добавляет 50–200 нс на доступ к RAM. RFS решает эту проблему, направляя пакеты на ядро с запущенным приложением.

### Физические пределы и планирование

Перед тюнингом необходимо оценить достижимый предел задержки:

```bash
# Пример: оценка propagation delay для 1000 км оптоволокна
# Скорость света в волокне: ~200 000 км/с
# Минимальный RTT = 2 * 1000 / 200000 = 10 мс (физический предел)
echo "scale=3; 2 * 1000 / 200000" | bc
# → 0.010
```

Если текущий RTT в 2–3 раза превышает propagation delay — проблема в очереди или обработке, а не в физике.

## Практические сценарии: Уровни оптимизации

### 1. Уровень ядра и сетевого стека

Тюнинг параметров `sysctl` для минимизации очередей и ускорения обработки.

| Параметр | Значение (Low Latency) | Описание |
| :--- | :--- | :--- |
| `net.ipv4.tcp_congestion_control` | `bbr` или `reno` | BBR минимизирует RTT; Reno может быть быстрее в локальных сетях без потерь. |
| `net.core.default_qdisc` | `fq` или `fq_codel` | Использование FQ необходимо для BBR и борьбы с Bufferbloat. |
| `net.ipv4.tcp_low_latency` | `1` | (Для старых ядер) Предпочитать низкую задержку пропускной способности. |
| `net.ipv4.tcp_fastopen` | `3` | Включение TFO для экономии 1 RTT при установке соединения. |
| `net.core.busy_poll` | `50` | Время (в мкс) ожидания пакетов в режиме активного опроса. |
| `net.core.busy_read` | `50` | Время (в мкс) активного опроса для блокирующих сокетов. |
| `net.core.netdev_budget` | `300` | Максимум пакетов за цикл NAPI. Увеличение до 600 помогает на 10GbE+ при многоядерных системах. |
| `net.core.netdev_budget_per_cpu` | `300` | Лимит пакетов на ядро за цикл NAPI. |
| `net.core.netdev_max_backlog` | `5000` | Размер очереди пакетов перед SoftIRQ. Увеличить при высоких нагрузках для предотвращения дропов. |
| `net.core.somaxconn` | `65535` | Размер очереди полных соединений для listen(). Критично для высоконагруженных серверов. |
| `net.ipv4.tcp_syncookies` | `0` | Отключить в production при правильном настройке backlog; syncookies ухудшают латентность. |
| `net.ipv4.tcp_tw_reuse` | `1` | Переиспользование TIME_WAIT сокетов для исходящих соединений. |
| `net.ipv4.tcp_fin_timeout` | `10` | Уменьшить таймаут FIN-WAIT-2. |
| `net.ipv4.tcp_keepalive_time` | `300` | Интервал keepalive. |
| `net.ipv4.tcp_keepalive_intvl` | `30` | Интервал между keepalive-пробами. |
| `net.ipv4.tcp_keepalive_probes` | `3` | Количество проб. |

**Важно:** Параметры `busy_poll` и `busy_read` требуют поддержки драйвером NIC (флаг `SO_BUSY_POLL`). Проверить:

```bash
ethtool -k eth0 | grep busy_poll
# → busy_poll: on
```

### 2. Уровень сетевой карты (NIC) и прерываний

Переход от прерываний к прямому управлению или балансировке.

*   **Affinity & Isolation:** Привязка прерываний сетевой карты к конкретным ядрам (**IRQ Affinity**) и изоляция этих ядер от планировщика ОС (`isolcpus`).
    *   *Подробнее:* **[RSS, RPS, RFS в Linux](./rss_rps_rfs.md)**.
*   **Interrupt Coalescing:** Отключение объединения прерываний (`ethtool -C eth0 rx-usecs 0`) для немедленной обработки каждого пакета ценой роста нагрузки на CPU.
*   **NUMA Alignment:** Убедитесь, что приложение и прерывания NIC работают на одной NUMA-ноде.
    ```bash
    cat /sys/class/net/eth0/device/numa_node
    # → 0
    ```
*   **RSS/RPS Configuration:** Настройка распределения RX-очередей по ядрам CPU.
    ```bash
    # Просмотр количества RX-очередей
    ethtool -l eth0 | grep RX
    
    # Настройка RSS с 4 очередями
    sudo ethtool -X eth0 equal 4
    
    # Привязка очередей к ядрам 0-3
    sudo ethtool -x eth0
    ```
*   **RPS/RFS:** Программное распределение для NIC с одной очередью или для дополнения аппаратного RSS.
    ```bash
    # Включение RPS на ядра 0-3 для eth0
    echo 0f > /sys/class/net/eth0/queues/rx-0/rps_cpus
    echo f0 > /sys/class/net/eth0/queues/rx-1/rps_cpus
    
    # Включение RFS
    echo 65536 > /sys/net/core/rps_sock_flow_entries
    ```

### 3. Технологии Kernel Bypass (Обход ядра)

Для систем с требованиями задержек < 10 мкс стандартный стек ядра становится препятствием.

*   **XDP (eXpress Data Path):** Обработка пакетов на уровне драйвера с помощью eBPF до создания структуры `sk_buff`. XDP_DROP / XDP_REDIRECT работают без участия NAPI.
*   **AF_XDP:** Высокопроизводительный адресный семейство сокетов для передачи пакетов в Userspace без копирования.
*   **DPDK (Data Plane Development Kit):** Полный перенос сетевого стека в пространство пользователя.
    *   *SSoT:* **[Обзор DPDK](../../../Networking/Concepts/dpdk/dpdk_overview.md)**.

**Сравнение технологий kernel bypass:**

| Технология | Задержка | Сложность | Использование |
| :--- | :--- | :--- | :--- |
| XDP | 1–5 мкс | Средняя | Фильтрация, DDoS-защита, балансировка |
| AF_XDP | 5–20 мкс | Высокая | Высокоскоростные приложения, Trading |
| DPDK | < 1 мкс | Очень высокая | VPP, телеком, специализированные NIC |

### 4. Оптимизация на уровне сокетов приложения

*   **TCP_NODELAY:** Отключение алгоритма Нагла. Пакеты отправляются немедленно, не дожидаясь заполнения буфера.
*   **SO_BUSY_POLL:** Позволяет сокету выполнять активный опрос драйвера вместо ожидания прерывания. Радикально снижает хвостовую латентность (p99).
*   **TCP_QUICKACK:** Принудительная отправка подтверждений без ожидания (отключает Delayed ACK).
*   **SO_PRIORITY:** Установка приоритета пакетов (0-7) для классификации в qdisc.
*   **TCP_CONGESTION:** Установка алгоритма на уровне сокета.

```bash
# Пример: настройка busy polling на уровне сокета
# В коде приложения:
# int val = 50; // микросекунды
# setsockopt(fd, SOL_SOCKET, SO_BUSY_POLL, &val, sizeof(val));

# Проверка текущих значений
sysctl net.core.busy_poll
sysctl net.core.busy_read
```

### 5. Оптимизация на уровне физической среды

*   **Выбор среды:** Волокно (Single-mode/Multi-mode) vs медь. Волокно дает минимальную задержку и наивысшую полосу.
*   **Jumbo Frames (MTU 9000):** Уменьшают количество пакетов и нагрузку на CPU за счет увеличения размера полезной нагрузки. Эффективно для large-file transfers, но увеличивает serialization delay для малых пакетов.
    ```bash
    # Проверка текущего MTU
    ip link show eth0 | grep mtu
    
    # Установка MTU 9000
    sudo ip link set mtu 9000 dev eth0
    
    # Проверка на противоположном конце (MTU должен совпадать!)
    ping -M do -s 8972 <remote-ip>
    ```
*   **Скорость линка и дуплекс:** Автосогласование (`autoneg on`) предпочтительнее фиксированной скорости, так как NIC может выбрать оптимальный режим.
    ```bash
    ethtool eth0 | grep -E "Speed|Duplex|Auto-negotiation"
    ```

### 6. Оптимизация DNS и NTP

*   **DNS:** Использование локального кэширующего резолвера (systemd-resolved, dnsmasq, CoreDNS) снижает TTFB на 10–100 мс.
*   **NTP:** Стабильность времени критична для TLS и распределенных систем. `chrony` точнее `ntpd` для нестабильных каналов.

## Дополнительная информация

### Диагностический чек-лист

Для поиска причин задержек используйте следующие инструменты:

1.  **Профилирование стека:** `bpftrace` для измерения времени прохождения пакета через функции ядра.
2.  **Анализ очередей:** `ss -i` (просмотр RTT и параметров конкретного TCP-соединения).
3.  **Аппаратный анализ:** `ethtool -S <iface>` (поиск дропов на уровне колец NIC).
4.  **Мониторинг джиттера:** `mtr` в режиме статистики или `iperf3` с UDP-тестом.
5.  **Анализ Bufferbloat:** `tc -s qdisc show dev eth0` и сравнение RTT под нагрузкой.
6.  **NUMA и IRQ:** `numastat`, `cat /proc/interrupts`, `mpstat -P ALL 1`.
7.  **Сетевые дропы:** `netstat -s | grep -i drop`, `nstat -s`, `cat /proc/net/softnet_stat`.
8.  **TCP Retransmits:** `ss -ti` (поле `retrans`), `nstat -s | grep Retrans`.
9.  **CPU Frequency:** `cpufreq-info`, `turbostat`.
10. **PCIe:** `lspci -vvv -s <bus:device> | grep -i "latency\|ltssr"`.

```bash
# Пример: просмотр RTT и отклонений для активных соединений
ss -tin

# Пример: статистика по дропам
cat /proc/net/softnet_stat

# Пример: мониторинг в реальном времени
watch -n1 'cat /proc/net/softnet_stat'
```

### Тюнинг для Real-Time систем

В критических сценариях (например, в промышленности) используется ядро с патчем **PREEMPT_RT**, которое делает обработку прерываний полностью вытесняемой, гарантируя предсказуемое время отклика.

Проверка поддержки PREEMPT_RT:

```bash
uname -v
# → # SMP PREEMPT_DYNAMIC Thu Aug 15 12:34:56 UTC 2026
# Если содержит PREEMPT_RT — патч применен

# Проверка задержек с cyclictest
sudo cyclictest -t1 -n -i 100 -l 10000
# → Histogram
#    000000 000000 000000 000000 000000 000000
#    000001 000000 000000 000000 000000 000000
#    000002 000000 000000 000000 000000 000000
#    ...
#    Минимальная задержка: 1 мкс
#    Средняя задержка: 5 мкс
#    Максимальная задержка: 25 мкс
```

### Troubleshooting: типичные проблемы латентности

| Симптом | Возможная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Высокий RTT при низкой нагрузке** | Неправильный duplex/speed, кабель, SFP | `ethtool eth0`, `dmesg` | Замена кабеля, проверка SFP, `ethtool -s autoneg on` |
| **RTT растет под нагрузкой** | Bufferbloat, неверный qdisc | `tc -s qdisc show`, `ping` под `iperf3` | Переключить на `fq_codel` или `fq`, отключить offload |
| **Высокий jitter (UDP)** | Перегрузка очередей, ECN-marking | `tc -s qdisc`, `mtr` | Настройка `fq_codel`, проверка `tc qdisc` |
| **Высокий %si в top** | SoftIRQ storm, нет RSS/RPS | `mpstat -P ALL 1`, `cat /proc/interrupts` | Настройка RSS/RPS, увеличение `netdev_budget` |
| **Рост столбца 2 в softnet_stat** | Переполнение backlog | `cat /proc/net/softnet_stat` | Увеличить `netdev_max_backlog`, включить RPS |
| **Высокий %st (Steal) в top** | Конкуренция за CPU с другими VMs | `mpstat -P ALL 1` | Выделенные ядра, KVM pinning, SR-IOV |
| **TCP Retransmits > 0** | Потери на L2/L3, переполнение буферов | `ss -ti`, `ethtool -S` | Проверка кабеля, настройка `tcp_retries2` |
| **Высокий CPU utilization на NIC** | Неподдерживаемый offload, маленькие кольца | `ethtool -S eth0` | Увеличить ring buffer, отключить неиспользуемые offload |
| **Кратные задержки 100 мс** | CFS throttling, C-state residency | `turbostat`, `mpstat` | Установка `intel_pstate=no_hwp`, governor `performance` |
| **Проблемы с TFO** | Неподдерживаемое ядро или middlebox | `sysctl net.ipv4.tcp_fastopen`, `tcpdump` | Включить в ядре 4.11+, проверить поддержку peer |

### Edge cases и ограничения

*   **Малые пакеты:** При MTU 1500 и трафике 64-байтных пакетов накладные расходы (interrupt, context switch, protocol processing) доминируют. Используйте busy polling или kernel bypass.
*   **Виртуализация:** Hypervisor добавляет 5–50 мкс задержки. Для KVM: проверьте `kvm_clock` и `kvm-pv` драйверы. SR-IOV снижает задержку до уровня bare-metal.
*   **Контейнеры:** Docker bridge (`docker0`) добавляет 10–30 мкс. Для низкой задержки используйте `macvlan` или `ipvlan` без моста.
*   **Смешанный MTU:** Если путь содержит сегменты с разным MTU, срабатывает Path MTU Discovery, что добавляет задержку при фрагментации. Используйте единый MTU в L2-домене.
*   **Избыточный budget:** Увеличение `netdev_budget` выше 1000 может привести к starvation пользовательских процессов. Находите баланс между сетью и приложением.
*   **br_netfilter:** Если включен `bridge-nf-call-iptables`, все Bridged трафик проходит через netfilter, добавляя 5–20 мкс. Отключите, если не нужен фильтра bridging-трафика.
*   **cgroup CPU limits:** В контейнерах cgroup `cpu.cfs_quota_us` может вызывать CFS throttling, что manifests как периодические задержки. Мониторьте через `docker stats` или `kubectl top`.

### Оптимизационный чек-лист

1.  **Базовый тюнинг:** Применить `sysctl` из раздела «Уровень ядра», перезагрузить `sysctl -p`.
2.  **Qdisc:** Установить `fq` для BBR или `fq_codel` для CUBIC/Reno.
3.  **NIC:** Отключить interrupt coalescing (`ethtool -C rx-usecs 0`), увеличить ring buffer (`ethtool -G`), отключить неиспользуемые offload.
4.  **NUMA:** Привязать IRQ и приложение к родной NUMA-ноде NIC.
5.  **RSS/RPS:** Включить аппаратный RSS (2+ очереди) и/или программный RPS/RFS.
6.  **Приложение:** Включить `TCP_NODELAY`, `SO_BUSY_POLL` (если поддерживается), `TCP_QUICKACK`.
7.  **Бенчмарк:** Измерить baseline с `iperf3`, `ping`, `ss`. Сравнить до/после.

```bash
# Полный сценарий: базовый тюнинг для low-latency сервера

# 1. sysctl
cat <<EOF | sudo tee /etc/sysctl.d/99-low-latency.conf
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
net.ipv4.tcp_fastopen = 3
net.ipv4.tcp_low_latency = 1
net.core.busy_poll = 50
net.core.busy_read = 50
net.core.netdev_max_backlog = 5000
net.core.somaxconn = 65535
net.ipv4.tcp_syncookies = 0
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 10
EOF
sudo sysctl -p /etc/sysctl.d/99-low-latency.conf

# 2. qdisc
sudo tc qdisc replace dev eth0 root fq

# 3. ethtool: отключить coalescing, увеличить кольца
sudo ethtool -C eth0 rx-usecs 0 rx-frames 1
sudo ethtool -G eth0 rx 4096 tx 4096

# 4. RSS: 4 очереди
sudo ethtool -X eth0 equal 4

# 5. Проверка
ethtool -c eth0
ethtool -g eth0
tc qdisc show dev eth0
sysctl net.ipv4.tcp_congestion_control
```
