# Оптимизация TCP в Linux

## Определения

* **Оптимизация TCP** — это процесс настройки параметров сетевого стека ядра Linux для улучшения производительности TCP-соединений, снижения задержек и повышения пропускной способности.
* **`TIME_WAIT`** — состояние TCP-соединения, в которое переходит одна из сторон после его закрытия для обеспечения надежной доставки последних пакетов и предотвращения проблем с новыми соединениями, использующими те же порты.
* **BBR (Bottleneck Bandwidth and Round-trip time)** — современный алгоритм контроля перегрузки сети, разработанный Google, который оптимизирует пропускную способность и минимизирует задержки путем моделирования характеристик канала.
* **TCP Backlog (очередь `listen()` / accept backlog)** — это очередь, в которой ядро Linux временно хранит входящие TCP-подключения. Фактически существует две очереди:
    *   **SYN backlog** — очередь для полуоткрытых соединений в состоянии `SYN_RECV` (клиент отправил SYN, сервер ответил SYN-ACK). Размер этой очереди контролируется параметром `net.ipv4.tcp_max_syn_backlog`.
    *   **Accept backlog** — очередь для полностью установленных соединений (`ESTABLISHED`), которые уже прошли TCP-рукопожатие, но еще не были приняты приложением через системный вызов `accept()`. Ее размер определяется параметром `net.core.somaxconn`.

    **Влияние переполнения backlog:**
    *   Если `SYN backlog` переполняется, новые SYN-пакеты могут быть отброшены (SYN drop), что приводит к задержкам или невозможности установить соединение для клиентов.
    *   Если `Accept backlog` переполняется, ядро может сбрасывать входящие соединения, отправляя клиентам `RST`-пакеты, что приводит к отказам в обслуживании под высокой нагрузкой.
    *   Возрастает эффект от SYN flood даже без атаки при переполнении `SYN backlog`.

## Базовые концепции

Производительность сетевых соединений в Linux сильно зависит от настроек TCP/IP стека ядра. На высоконагруженных серверах, обрабатывающих тысячи одновременных подключений, стандартные параметры могут стать узким местом.

Все параметры настраиваются через [[sysctl|../../Core/sysctl.md]]. Для временного применения используется `sudo sysctl -w <параметр>=<значение>`, а для постоянного — их следует добавлять в файл `/etc/sysctl.conf` (или `/etc/sysctl.d/99-network.conf`) и выполнять `sudo sysctl -p`.

## Практические сценарии

### 1. Управление очередями соединений

* **`net.core.somaxconn`**: Увеличивает максимальное количество ожидающих соединений в очереди `listen()`. Если приложение (например, Nginx) пытается установить `backlog` больше, чем `somaxconn`, будет использовано значение `somaxconn`.

    ```bash
    # Рекомендуемое значение для высоких нагрузок
    sudo sysctl -w net.core.somaxconn=65535
    ```

* **`net.ipv4.tcp_max_syn_backlog`**: Увеличивает размер очереди для соединений, находящихся в состоянии `SYN-RECV` (незавершенных). Это помогает предотвратить отбрасывание SYN-пакетов (SYN drop).

    ```bash
    sudo sysctl -w net.ipv4.tcp_max_syn_backlog=4096
    ```

* **`net.core.netdev_max_backlog`**: Увеличивает размер очереди пакетов, принимаемых от сетевой карты. Помогает не терять пакеты при кратковременных всплесках трафика, когда ядро не успевает их обработать.

     ```bash
    sudo sysctl -w net.core.netdev_max_backlog=30000
    ```

### 2. Управление состоянием `TIME_WAIT`

На серверах с большим количеством короткоживущих соединений (веб-серверы, API-шлюзы) скапливается много сокетов в состоянии `TIME_WAIT`, занимая порты и память.

* **`net.ipv4.tcp_tw_reuse`**: Разрешает ядру повторно использовать сокеты в состоянии `TIME_WAIT` для *новых исходящих* соединений. Это самый безопасный способ борьбы с нехваткой портов. Используйте с осторожностью, так как может привести к проблемам при определенных условиях.

    ```bash
    sudo sysctl -w net.ipv4.tcp_tw_reuse=1
    ```

    **Важно:** Этот параметр не затрагивает входящие соединения.

* **`net.ipv4.tcp_fin_timeout`**: Уменьшает время нахождения сокета в состоянии `FIN-WAIT-2`. Помогает быстрее освобождать ресурсы.

    ```bash
    sudo sysctl -w net.ipv4.tcp_fin_timeout=15
    ```

* **`net.ipv4.ip_local_port_range`**: Расширяет диапазон эфемерных портов для исходящих соединений. Это важно для прокси-серверов, которые устанавливают множество соединений с бэкендами.

    ```bash
    sudo sysctl -w net.ipv4.ip_local_port_range="1024 65535"
    ```

* **`net.ipv4.tcp_tw_recycle`**: **Устарел и опасен!** Этот параметр был удален из ядра Linux (начиная с 4.12) из-за проблем с клиентами за NAT. **Никогда не используйте его.**

**Диагностика:** Подробнее об утилите см. [**`ss`**](../../Linux/Diagnostics/Networking/ss.md).

```bash
# Подсчитать количество сокетов в состоянии TIME_WAIT
ss -tan 'state time-wait' | wc -l

# Общая статистика по сокетам
ss -s
```

### 3. Оптимизация буферов TCP

Размеры буферов влияют на пропускную способность, особенно в сетях с высокой задержкой (Long-Fat Networks).

* **`net.core.rmem_max` / `net.core.wmem_max`**: Максимальный размер буфера приема и передачи для всех типов соединений.
* **`net.ipv4.tcp_rmem` / `net.ipv4.tcp_wmem`**: Определяют минимальный, начальный и максимальный размер буферов для TCP.

```bash
# Пример для сетей 1 Гбит/с и выше
sudo sysctl -w net.core.rmem_max=16777216
sudo sysctl -w net.core.wmem_max=16777216
sudo sysctl -w net.ipv4.tcp_rmem='4096 87380 16777216'
sudo sysctl -w net.ipv4.tcp_wmem='4096 65536 16777216'
```

### 4. Выбор алгоритма контроля перегрузки: BBR

**BBR (Bottleneck Bandwidth and Round-trip time)** — это современный алгоритм, который значительно повышает пропускную способность и снижает задержку. Он показывает хорошую производительность на каналах с потерями пакетов (например, мобильные сети) и идеально подходит для веб-серверов и серверов раздачи контента.

* **`net.ipv4.tcp_slow_start_after_idle=0`**: Отключает сброс окна TCP-конгестии после простоя соединения. Полезно для долгоживущих keep-alive соединений, так как позволяет им не начинать передачу данных с минимальной скоростью после паузы.

    ```bash
    sudo sysctl -w net.ipv4.tcp_slow_start_after_idle=0
    ```

#### Как включить BBR

1. **Проверка версии ядра:** BBR требует ядро Linux версии `4.9` или выше (`uname -r`).
2. **Настройка `sysctl`:**

    ```ini
    # /etc/sysctl.conf
    # Включить Fair Queuing (обязательно для BBR)
    net.core.default_qdisc = fq
    # Установить BBR как алгоритм контроля перегрузки
    net.ipv4.tcp_congestion_control = bbr
    ```

3. **Применение и проверка:**

    ```bash
    sudo sysctl -p
    # Проверить, что BBR используется
    ss -ti | grep bbr
    ```

### 5. Настройка начального окна перегрузки (initcwnd)

Как обсуждалось в основной заметке о TCP, начальное окно перегрузки (`initcwnd`) определяет, сколько данных сервер может отправить в первой "волне" после установки соединения. Увеличение этого значения — один из самых эффективных способов уменьшить задержку при загрузке веб-ресурсов.

По умолчанию в Linux `initcwnd` равен **10** (десяти MSS), что соответствует примерно **14 КБ**. Это означает, что если ресурс больше, клиенту потребуется ждать дополнительный RTT для получения остатка. Многие CDN (Cloudflare, Google) и крупные провайдеры увеличивают это значение, чтобы ускорить первоначальную загрузку.

В Linux этот параметр настраивается не через `sysctl`, а непосредственно для маршрутов в таблице маршрутизации.

#### Просмотр текущего значения `initcwnd`

Используйте команду `ip route` для просмотра текущих `initcwnd` для маршрутов.

```bash
# Показать все маршруты и их параметры
ip route

# Вывод может выглядеть так:
# default via 192.168.1.1 dev eth0
# 192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.100

# Чтобы увидеть cwnd, ищем параметр 'initcwnd'. Если он не указан, используется значение по умолчанию.
ip route show | grep 'initcwnd'
```

#### Изменение значения `initcwnd`

Значение `initcwnd` можно изменить для конкретного маршрута или для маршрута по умолчанию.

```bash
# Установить initcwnd=30 для всех новых соединений, идущих через шлюз по умолчанию
# Сначала найдем шлюз по умолчанию
GATEWAY=$(ip route | grep default | awk '{print $3}')
DEVICE=$(ip route | grep default | awk '{print $5}')

# Пример изменения для существующего маршрута
sudo ip route change default via $GATEWAY dev $DEVICE initcwnd 30

# Проверяем, что изменения применились
ip route | grep default
# default via 192.168.1.1 dev eth0 initcwnd 30
```

**Рекомендации:**

* Увеличение `initcwnd` до **20-40** считается безопасным и эффективным для большинства веб-серверов.
* Это изменение не будет постоянным и сбросится после перезагрузки. Для постоянной настройки его нужно применять через скрипты управления сетью (например, `if-up.d` в Debian/Ubuntu или аналоги в других дистрибутивах).

## Дополнительная информация

### Принцип работы BBR

В отличие от классических алгоритмов, основанных на потерях (таких как CUBIC), BBR не ждет потери пакетов, чтобы снизить скорость. Вместо этого он постоянно моделирует сеть, измеряя два ключевых параметра:

1. **Пропускную способность узкого места (Bottleneck Bandwidth)**: Максимальная скорость передачи данных на пути.
2. **Время кругового пути (Round-trip time)**: Минимальная задержка.

На основе этих данных BBR старается поддерживать объем передаваемых данных на уровне, который точно соответствует произведению `Bandwidth * RTT` (Bandwidth-Delay Product), не создавая при этом лишних очередей на маршрутизаторах (bufferbloat).

### Защита от SYN-флуда

* **`net.ipv4.tcp_syncookies`**: Механизм защиты от атак типа "[[SYN-флуд|../../../Networking/Concepts/dos_ddos_overview.md#syn-флуд]]". Когда очередь `SYN-RECV` переполняется, сервер начинает отвечать специальными SYN-ACK пакетами ("SYN cookies"), не выделяя ресурсы. Если клиент отвечает правильно, соединение устанавливается.

    ```bash
    # Включение SYN cookies
    sudo sysctl -w net.ipv4.tcp_syncookies=1
    ```

    В современных ядрах этот механизм включен по умолчанию и активируется автоматически при риске переполнения.
