# Диагностика сокетов TCP в Linux

Данное руководство фокусируется на практическом применении инструментов анализа для проверки эффективности тюнинга и поиска узких мест в сетевом стеке. Полный справочник по флагам утилиты `ss` доступен в разделе **[Диагностика ss](../../../Diagnostics/Networking/ss.md)**.

## Определения

* **Диагностика TCP-сокетов** — процесс сбора и интерпретации низкоуровневых метрик соединений (RTT, cwnd, потери) для оценки производительности и выявления сетевых аномалий.
* **Socket Metrics (Метрики сокета)** — параметры внутреннего состояния TCP-стека для конкретной сессии, доступные через интерфейс `tcp_info` ядра.
* **eBPF (Extended Berkeley Packet Filter)** — технология ядра, позволяющая запускать программы мониторинга сетевых событий с минимальными накладными расходами без захвата полных пакетов.

## Основные концепции

### Инструментарий 2026 года

| Уровень | Инструмент | Преимущество |
| :--- | :--- | :--- |
| **Сессионный** | `ss -ti` | Максимально детальная информация по каждому соединению. |
| **Системный** | `nstat -az` | Глобальные счётчики ошибок и событий (backlog, syncookies). |
| **Событийный** | `bcc-tools`, `bpftrace` | Отслеживание задержек и переходов состояний в реальном времени. |
| **Пакетный** | `tcpdump` | Анализ содержимого пакетов и флагов при сложных аномалиях. |

### Ключевые метрики ss -ti

При анализе вывода `ss -ti` следует обращать внимание на:
*   **`rtt`**: Среднее время кругового обхода (мс). Высокие значения или большой разброс (`mdev`) указывают на проблемы в сети.
*   **`cwnd`**: Текущее окно перегрузки. Если оно маленькое при высоком BDP — TCP ограничен потерями.
*   **`retrans`**: Количество текущих ретрансмиссий и общая статистика потерь.
*   **`rcv_space`**: Текущий объем данных, который сокет готов принять (зависит от автотюнинга буферов).
*   **`unacked` / `sacked`**: Количество пакетов «в полете», не подтвержденных или подтвержденных через SACK.

## Практические сценарии

### 1. Анализ производительности «живых» соединений

Для проверки того, насколько эффективно работает тюнинг буферов и алгоритм BBR:

```bash
# Просмотр метрик для соединений на порту 443
ss -tin dst :443

# Интерпретация вывода (пример):
# bbr wscale:7,7 rto:204 rtt:0.52/0.03 ato:40 mss:1448 pmtu:1500 rcvmss:1448
#      cwnd:320 bytes_acked:15002048 segs_out:10500 segs_in:8900
#      pacing_rate 1.2Gbps delivery_rate 980Mbps busy:450ms unacked:15
```

*   **`pacing_rate`**: Если значительно выше `delivery_rate`, значит стек готов отправлять быстрее, но сеть или получатель не справляются.
*   **`busy`**: Время, в течение которого сокет был занят передачей. Помогает найти «ленивые» приложения.

### 2. Поиск скрытых потерь и таймаутов

Использование глобальных счётчиков для выявления проблем, которые не видны в `top` или `iostat`:

```bash
# Проверка сбросов пакетов из-за переполнения очередей
nstat -az | grep -E 'ListenOverflows|ListenDrops|ReqQFullDrop'

# Поиск признаков проблем с Middleboxes (файрволами)
nstat -az | grep -i 'TcpExtTCPFastOpenBlackhole'
```

Если растёт `ListenOverflows`, необходимо увеличивать `somaxconn` и `backlog` приложения. Если растёт `Blackhole`, использование TFO в этой сети вредно.

### 3. Диагностика через eBPF (Real-time)

В современных системах для отслеживания задержек установки соединений используются инструменты `bcc-tools`:

```bash
# Измерение задержки (Latency) установления TCP-соединений
sudo tcpconnlat

# Отслеживание процессов, которые делают много коротких соединений (нагрузка на TIME_WAIT)
sudo tcpconnect
```

### 4. Проверка Window Scaling и алгоритма Нагла

Если пропускная способность низкая при хорошем канале:

```bash
# Проверка, согласовано ли масштабирование окна (wscale)
ss -tno | grep -v 'wscale:0,0'

# Проверка, не включен ли алгоритм Нагла (флаг nagle)
# Если приложение использует TCP_NODELAY, в выводе будет 'nodelay'
ss -tin | grep -E 'nagle|nodelay'
```

## Дополнительная информация

### Таблица интерпретации симптомов

| Симптом | Метрика/Инструмент | Интерпретация |
| :--- | :--- | :--- |
| **Низкая скорость** | `ss -ti` -> `cwnd` | Если `cwnd` мал при низком RTT — в сети потери или мал `initcwnd`. |
| **Высокий TTFB** | `tcpconnlat` (eBPF) | Задержка на этапе Handshake (3-way или TLS). |
| **Connection Refused** | `nstat` -> `ListenOverflows` | Очередь `somaxconn` переполнена, приложение не успевает делать `accept()`. |
| **Зависание сессий** | `ss -tmo` -> `window:0` | Получатель выставил нулевое окно (Zero Window), он перегружен. |
