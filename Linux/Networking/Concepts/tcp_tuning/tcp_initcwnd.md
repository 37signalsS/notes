# Настройка initcwnd в Linux: управление начальным окном

## Определения

*   **initcwnd (Initial Congestion Window — начальное окно перегрузки)** — параметр протокола TCP, определяющий объём данных (в сегментах MSS), который сервер может отправить сразу после установления соединения, не дожидаясь подтверждений (ACK).
*   **initrwnd (Initial Receive Window — начальное окно приема)** — объём данных, который получатель готов принять в первой «волне» до получения первого ACK. В современных конфигурациях также фигурирует как **Initial Advertised Receive Window**.
*   **MSS (Maximum Segment Size — максимальный размер сегмента)** — максимальный объём полезных данных в одном пакете. Для сетей Ethernet с MTU 1500 MSS обычно составляет 1460 байт.
*   **Slow Start (Медленный старт)** — фаза алгоритма управления перегрузкой, начинающаяся с `initcwnd` и экспоненциально увеличивающая окно при получении ACK.
*   **BDP (Bandwidth-Delay Product — произведение полосы пропускания на задержку)** — максимальный объём данных, который может находиться «в полете» без остановки. Вычисляется как `Bandwidth × RTT`. Определяет, насколько besar должен быть `cwnd` для полной утилизации канала.

## Базовые концепции

В ядре Linux значение `initcwnd` по умолчанию составляет **10 MSS** (согласно RFC 6928), что эквивалентно примерно 14.6 КБ. Это значение является критическим порогом для веб-производительности («Правило 14 КБ»).

**Ключевая особенность реализации:** В Linux `initcwnd` настраивается не через глобальные параметры `sysctl`, а индивидуально для каждого маршрута (route). Это позволяет задавать разные окна для разных интерфейсов или направлений (например, локальная сеть vs интернет).

### Эволюция initcwnd: от RFC 3390 к RFC 6928

Параметр `initcwnd` не всегда был равен 10 MSS. Эволюция стандарта отражает рост пропускной способности сетей и изменение характера веб-трафика:

| Стандарт | Год | initcwnd | Контекст |
| :--- | :--- | :--- | :--- |
| **RFC 2001** | 1997 | 1 MSS | Начальное значение, консервативный подход для медленных сетей |
| **RFC 2414** | 1998 | 2-4 MSS | Первые эксперименты с увеличением для ускорения старта |
| **RFC 3390** | 2002 | min(4, max(2, bytes_acked/MSS)) | Динамическое начальное окно, адаптирующееся к размеру сегмента |
| **RFC 6928** | 2013 | 10 MSS | Фиксированное значение IW10, стандарт для современных сетей |

**Почему именно 10 MSS?** Расчет RFC 6928 основан на компромиссе:
- **Слишком мало (1-4 MSS):** Сервер вынужден ждать ACK перед отправкой новых данных, что увеличивает TTFB (Time To First Byte) для современных веб-страниц.
- **Слишком много (32+ MSS):** На сетях с высоким RTT (>100 мс) или малыми буферами промежуточного оборудования возникают массовые потери пакетов.
- **10 MSS** — оптимальный баланс для большинства сценариев: позволяет доставить основную часть HTML/CSS за один RTT при сохранении приемлемого уровня потерь.

### Правило 14 КБ

Связка `initcwnd = 10 MSS` и размера сегмента MSS = 1460 байт (Ethernet MTU 1500) дает **14 600 байт** (~14.25 КБ). Это значение критично для веб-производности:

- **HTML/CSS ≤ 14 КБ:** Страница отрисовывается за 1 RTT после handshake.
- **HTML/CSS > 14 КБ:** Требуется минимум 2 RTT (первый вылет + ожидание ACK + досылка).

Это явление известно как «Правило 14 КБ» и является основой оптимизации критического пути отрисовки страниц.

### Факторы, ограничивающие реальную производительность

При настройке `initcwnd` необходимо учитывать следующие ограничения:

1. **Окно получателя (rwnd):** Фактическая скорость определяется `min(cwnd, rwnd)`. Если клиент заявляет `rwnd < initcwnd`, серверный тюнинг будет игнорироваться.
2. **Bufferbloat:** Высокие значения `initcwnd` (32+ MSS) на сетях с буферами малого размера вызывают потерю пакетов в буферах промежуточных маршрутизаторов.
3. **Экстремальные значения (100+ MSS):** Могут привести к переполнению буферов даже на соврем оборудовании, особенно при RTT > 100 мс.

### Взаимодействие с Pacing (2026)

При установке `initcwnd` выше 20–32 MSS сервер генерирует мощный всплеск трафика (burst). Если промежуточное оборудование имеет малые буферы, это приведет к мгновенным потерям.
*   **Решение:** Использование дисциплины очередей `fq` (Fair Queueing), которая реализует **Pacing** (равномерное распределение пакетов во времени). В современных ядрах 6.x+ это является стандартом при использовании BBR.

```bash
# Проверка текущей дисциплины очередей
tc qdisc show dev eth0

# Включение fq (если не активно)
sudo tc qdisc replace dev eth0 root fq
```

**Почему Pacing критичен при высоких initcwnd:**
- Без Pacing: все 32 сегмента отправляются сразу → всплеск → потеря в буфере.
- С Pacing: сегменты равномерно распределяются во времени → стабильная передача.

### Параметр tcp_slow_start_after_idle

По умолчанию Linux сбрасывает окно перегрузки обратно к `initcwnd`, если соединение простаивало (один RTO). Для HTTP/1.1 с Keep-Alive или долгоживущих API-соединений это снижает производительность.
*   **Настройка:** `net.ipv4.tcp_slow_start_after_idle = 0` (через `sysctl`) предотвращает этот сброс.

```bash
# Проверка текущего значения
sysctl net.ipv4.tcp_slow_start_after_idle
# → net.ipv4.tcp_slow_start_after_idle = 1

# Временное отключение (до перезагрузки)
sudo sysctl -w net.ipv4.tcp_slow_start_after_idle=0

# Постоянное отключение
echo "net.ipv4.tcp_slow_start_after_idle=0" | sudo tee -a /etc/sysctl.d/99-tcp-tuning.conf
sudo sysctl --system
```

**Влияние на типичные сценарии:**
| Сценарий | tcp_slow_start_after_idle=1 (по умолчанию) | tcp_slow_start_after_idle=0 |
| :--- | :--- | :--- |
| HTTP/1.1 Keep-Alive | Сброс после 10-60 сек простоя → повторный Slow Start | Сохранение окна → быстрый ответ |
| HTTP/2 multiplexing | Аналогичный сброс | Сохранение окна |
| WebSocket/long-polling | Критичный сброс при каждом запросе | Без сброса |
| API с частыми запросами | Снижение throughput при интервале > 1 сек | Стабильная скорость |

## Практические сценарии

### 1. Проверка текущего значения

Если параметр не указан явно, ядро использует дефолт (10 MSS).

```bash
# Просмотр параметров маршрутов
ip route show

# Детальный просмотр для конкретного интерфейса
ip route show dev eth0
# → default via 192.168.1.1 dev eth0 proto dhcp metric 100 initcwnd 32 initrwnd 32

# Проверка для IPv6
ip -6 route show
```

### 2. Временная настройка (iproute2)

Изменения вступают в силу немедленно для новых соединений.

```bash
# Автоматическое определение шлюза и интерфейса
GATEWAY=$(ip route | grep default | awk '{print $3}')
DEVICE=$(ip route | grep default | awk '{print $5}')

# Установка initcwnd=32 и initrwnd=32 (стандарт для широкополосных сетей 2026 года)
sudo ip route change default via "$GATEWAY" dev "$DEVICE" initcwnd 32 initrwnd 32

# Настройка для IPv6
sudo ip -6 route change default via fe80::1 dev eth0 initcwnd 32 initrwnd 32
```

**Важно:** Изменения через `ip route` действуют только на новые соединения. Установленные соединения продолжают работать со старыми параметрами.

### 3. Постоянное сохранение настроек

#### Через Netplan (Ubuntu 24.04+)
```yaml
# /etc/netplan/01-netcfg.yaml
network:
  version: 2
  ethernets:
    enp1s0:
      dhcp4: true
      routes:
        - to: default
          via: 192.168.1.1
          congestion-window: 32
          advertised-receive-window: 32
```

#### Через systemd-networkd
```ini
# /etc/systemd/network/10-eth0.network
[Match]
Name=eth0

[Network]
DHCP=ipv4

[Route]
Gateway=_dhcp4
InitialCongestionWindow=32
InitialAdvertisedReceiveWindow=32
```

#### Через NetworkManager (nmcli)
```bash
# Изменение существующего соединения
sudo nmcli connection modify "Wired connection 1" \
    +ipv4.routes "0.0.0.0/0 192.168.1.1 initcwnd=32 initrwnd=32"

# Применение
sudo nmcli connection up "Wired connection 1"
```

### 4. Мониторинг активных сессий

```bash
# Просмотр cwnd и rtt для установленных соединений
ss -tin state established

# Фильтрация конкретных значений
ss -tin state established | grep -oE 'cwnd:[0-9]+|rtt:[0-9.]+'

# Просмотр для конкретного хоста
ss -tin state established dst 10.0.0.5

# Статистика по всем соединениям (средние значения)
ss -tin state established | awk '/cwnd/ {cwnd+=$1; n++} END {print "Avg cwnd:", cwnd/n}'
```

### 5. Диагностика: проверка применения настроек

После изменения маршрута необходимо убедиться, что параметр действительно применился:

```bash
# 1. Проверка маршрута
ip route show | grep default
# → default via 192.168.1.1 dev eth0 proto dhcp metric 100 initcwnd 32 initrwnd 32

# 2. Создание тестового соединения и проверка
curl -v http://example.com 2>&1 | grep -i "connected"

# 3. Проверка через ss для нового соединения
ss -tin state established dst 93.184.216.34
# → cwnd:32 rwnd:1460 mss:1460

# 4. Если cwnd не изменился — проверьте не перезаписывает ли его другой процесс
sudo ip route show table all | grep default
```

### 6. Откат настроек

Если настройка привела к проблемам (потери пакетов, снижение скорости):

```bash
# Возврат к значению по умолчанию (10 MSS)
GATEWAY=$(ip route | grep default | awk '{print $3}')
DEVICE=$(ip route | grep default | awk '{print $5}')

# Удаление initcwnd (возврат к дефолту ядра)
sudo ip route change default via "$GATEWAY" dev "$DEVICE"

# Или явная установка 10 MSS
sudo ip route change default via "$GATEWAY" dev "$DEVICE" initcwnd 10 initrwnd 10

# Проверка
ip route show | grep default
```

## Дополнительная информация

### Типичные проблемы и их решения

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **initcwnd не применяется** | Маршрут перезаписывается DHCP-клиентом | Настроить `dhcp-request-options` в dhclient.conf или использовать статический IP |
| **cwnd не растет выше initcwnd** | `tcp_slow_start_after_idle=1` сбрасывает окно | `sysctl -w net.ipv4.tcp_slow_start_after_idle=0` |
| **Высокие потери при initcwnd > 20** | Отсутствие Pacing / малые буферы роутера | Включить `tc qdisc replace dev eth0 root fq` или снизить initcwnd |
| **Клиент получает данные частями** | Клиентские `rwnd` < серверного `initcwnd` | Проверить через `ss -tin`; для старых клиентов снизить initcwnd до 10 |
| **Настройка сбрасывается после ребута** | Нет постоянной конфигурации | Использовать Netplan, systemd-networkd или NetworkManager |
| **Разные значения для IPv4 и IPv6** | Настраиваются отдельно через `ip route` и `ip -6 route` | Убедиться, что оба протокола настроены корректно |

### Диагностика через nstat

```bash
# Просмотр статистики перегрузок
nstat -az | grep -i cwnd
# → TcpExtTCPSlowStartRetransSegs    123    0.0    # Количество сегментов, отправленных в Slow Start

# Просмотр всех TCP-метрик, связанных с cwnd
nstat -az | grep -E "Cwnd|SlowStart|Congestion"
```

### Влияние на метрики производительности

Настройка `initcwnd` влияет на следующие ключевые метрики:

| Метрика | Описание | Влияние увеличения initcwnd |
| :--- | :--- | :--- |
| **TTFB (Time To First Byte)** | Время до получения первого байта ответа | Снижение (особенно для ресурсов ≤ 14 КБ) |
| **TTFP (Time To First Paint)** | Время до отрисовки первого пикселя | Снижение (если CSS критичен ≤ 14 КБ) |
| **Throughput** | Пропускная способность соединения | Незначительное снижение при потерях |
| **Packet Loss Rate** | Процент потерянных пакетов | Рост при высоких initcwnd без Pacing |

### Рекомендации по значениям

| Значение | Эквивалент | Сценарий применения |
| :--- | :--- | :--- |
| **10 MSS** | ~14.6 КБ | Стандарт RFC. Идеально для мобильных сетей и спутниковых каналов. |
| **32 MSS** | ~46.7 КБ | Стандарт 2026 года. Покрывает большинство Web/API запросов за 1 RTT. |
| **64 MSS** | ~93.4 КБ | Высокоскоростные линки (1Гбит+) с RTT > 20мс. Требует Pacing. |
| **100+ MSS** | > 146 КБ | Экстремальные значения. Могут вызвать переполнение буферов на старых роутерах. |

### Взаимодействие с другими параметрами TCP

При настройке `initcwnd` необходимо учитывать взаимодействие с другими параметрами:

| Параметр |/sysctl | Описание | Рекомендация |
| :--- | :--- | :--- | :--- |
| `tcp_wmem` | net.ipv4.tcp_wmem | Минимальный, начальный и максимальный размер буфера отправки | Убедиться, что max ≥ initcwnd × MSS |
| `tcp_rmem` | net.ipv4.tcp_rmem | Минимальный, начальный и максимальный размер буфера приема | Убедиться, что max ≥ initcwnd × MSS |
| `tcp_moderate_rcvbuf` | net.ipv4.tcp_moderate_rcvbuf | Автоматическая настройка окна приема | Рекомендуется: 1 (включено) |
| `tcp_congestion_control` | net.ipv4.tcp_congestion_control | Алгоритм контроля перегрузки | Использовать bbr для оптимального Pacing |

### Взаимодействие с BBR (v3)

Алгоритм **BBR (Bottleneck Bandwidth and RTT)** использует собственную оценку полосы, но `initcwnd` всё равно определяет объем данных в **первом** вылете пакетов. Сочетание `BBRv3` + `initcwnd 32` + `fq` (Pacing) дает наилучшие результаты для минимизации Time To First Byte (TTFB).

```bash
# Проверка текущего алгоритма контроля перегрузки
sysctl net.ipv4.tcp_congestion_control
# → net.ipv4.tcp_congestion_control = cubic

# Переключение на BBR (требует root)
sudo sysctl -w net.ipv4.tcp_congestion_control=bbr

# Постоянное изменение
echo "net.ipv4.tcp_congestion_control=bbr" | sudo tee -a /etc/sysctl.d/99-tcp-tuning.conf
sudo sysctl --system
```

**Важно:** BBR требует включенной дисциплины очередей `fq` для корректной работы Pacing.

### Стандарты (RFC)

| RFC | Название | Описание |
| :--- | :--- | :--- |
| **RFC 6928** | Increasing TCP's Initial Window | Основной стандарт IW10 (10 MSS). Рекомендует фиксированное начальное окно для ускорения загрузки веб-страниц. |
| **RFC 3390** | Increasing TCP's Initial Window | Устаревший стандарт (IW3-4). Динамическое вычисление начального окна. |
| **RFC 5681** | TCP Congestion Control | Фундаментальный стандарт управления перегрузкой. Определяет Slow Start, Congestion Avoidance, Fast Retransmit и Fast Recovery. |
| **RFC 9000** | QUIC: A UDP-Based Multiplexed and Secure Transport | Начальные окна в QUIC. Рекомендует `initial_window` в пределах 10-20 MSS. |
