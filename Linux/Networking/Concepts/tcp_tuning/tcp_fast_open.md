# TCP Fast Open (TFO): Ускорение установки соединений

## Определения

**TCP Fast Open (TFO — быстрое открытие TCP)** — расширение протокола TCP (RFC 7413), позволяющее передавать данные прикладного уровня (например, HTTP-запрос) непосредственно в пакете SYN. Это исключает один цикл приема-передачи (RTT) при установке соединения, что критично для производительности веб-сервисов и микросервисов.

**TFO Cookie** — криптографический токен, генерируемый сервером для проверки IP-адреса клиента. Он защищает от атак с подменой адреса (IP Spoofing) и SYN-флуда, гарантируя, что клиент ранее уже успешно устанавливал соединение. Cookie формируется по алгоритму HMAC-SHA256 от IP-адреса клиента и секретного ключа.

**RTT (Round-Trip Time)** — время, необходимое для прохождения сигнала от отправителя к получателю и обратно.

**SYN-ACK** — пакет, содержащий флаги SYN и ACK, используемый в процессе установки TCP-соединения для подтверждения получения SYN и инициации обратного подключения.

**Handshake** — процесс установки TCP-соединения, traditionally consisting of three steps: SYN → SYN-ACK → ACK.

## Основные концепции

### Эволюция TFO: от проблемы к решению

До появления TFO каждый новый TCP-связь требовал минимум **2 RTT** перед передачей данных:
1. **1 RTT** — завершение handshake (SYN → SYN-ACK → ACK)
2. **1 RTT** — передача данных и получение ответа

Для веб-страниц это означало, что даже при высокой пропускной способности канала, минимальное время до получения первого байта ответа (TTFB) составляло **2 RTT**. При RTT = 50 мс (typical для мобильных сетей) это давало задержку **100 мс** только на установление соединения и первый запрос.

**TFO решает эту проблему**, позволяя передавать данные уже в первом пакете SYN, что сокращает время до **1 RTT** для повторных соединений.

### Алгоритм работы

1.  **Первое соединение (Handshake):**
    - Клиент отправляет SYN с опцией запроса TFO Cookie (пустой cookie).
    - Сервер отвечает SYN-ACK, содержащим Cookie (HMAC от IP клиента + секретный ключ).
    - Соединение устанавливается обычным образом.
    - Клиент кеширует Cookie для использования в будущих соединениях.

2.  **Последующие соединения:**
    - Клиент отправляет SYN, содержащий сохраненный Cookie и данные (Payload).
    - Сервер проверяет Cookie. Если он валиден, сервер немедленно передает данные приложению, не дожидаясь ACK от клиента.
    - Сервер отправляет SYN-ACK, подтверждая прием данных.
    - Клиент отправляет ACK, завершая handshake.

**Экономия:** Время до получения первого байта ответа сокращается с **1.5-2 RTT** до **0.5-1 RTT**.

### Ограничения и особенности

1. **Размер данных:** Максимальный размер данных, передаваемых в SYN с TFO, ограничен размером TCP Options (примерно 1460 байт для MSS = 1460).
2. **Кеширование Cookie:** Cookie хранится на клиенте и валиден в течение определенного времени (обычно несколько минут).
3. **Роуминг:** При смене IP-адреса (например, переход с Wi-Fi на мобильную сеть) Cookie становится невалидным.

### Настройка через параметры ядра (sysctl)

Параметр `net.ipv4.tcp_fastopen` управляет поведением TFO через битовую маску:

| Бит | Значение | Режим | Описание |
| :--- | :--- | :--- | :--- |
| `0x1` | 1 | Клиент | Разрешить отправку данных в SYN (Client-side TFO). |
| `0x2` | 2 | Сервер | Разрешить прием данных в SYN (Server-side TFO). |
| `0x4` | 4 | Клиент (unsafe) | Отправлять данные в SYN без Cookie (риск спуфинга). |
| `0x200` | 512 | Сервер (unsafe) | Принимать данные в SYN без Cookie. |
| `0x400` | 1024 | Сервер (auto) | **(Kernel 4.11+)** Включать TFO для всех слушающих сокетов без модификации кода приложения. |

**Рекомендуемое значение для 2026 года:** `1027` (Клиент + Сервер + Авто-включение для всех сокетов).

**Пояснение значений:**
- `1` — включает TFO только для исходящих соединений (клиент).
- `2` — включает TFO только для входящих соединений (сервер).
- `3` — включает TFO для обоих направлений (клиент + сервер).
- `1027` — включает TFO для обоих направлений + автоматическое включение для всех слушающих сокетов (рекомендуется для серверов).

### Защита от Blackhole (Middleboxes)

Сетевое оборудование (брандмауэры, NAT) часто дропает пакеты SYN с данными, считая их аномальными. Для борьбы с этим в Linux реализован механизм **TFO Blackhole**:
*   Если SYN с данными не получает ответа, ядро переходит к обычному рукопожатию.
*   `net.ipv4.tcp_fastopen_blackhole_timeout_sec` — определяет время (в секундах), на которое ядро отключает TFO для конкретного направления после обнаружения «черной дыры».

### Безопасность и атаки повтора

Главный риск TFO — **атаки повторного воспроизведения (Replay Attacks)**. Злоумышленник может перехватить SYN с данными (например, "купить товар") и отправить его повторно.
*   **Решение:** TFO должен использоваться **только для идемпотентных запросов** (HTTP GET, HEAD), которые не изменяют состояние сервера. Для критических операций (POST/PUT) требуется защита на уровне приложения.

**Механизм защиты от Replay:**
1. **Криптографический Cookie:** Используется HMAC-SHA256 для генерации Cookie, что делает его невозможным для подделки.
2. **Временная валидность:** Cookie имеет ограниченный срок действия (обычно несколько минут).
3. **Привязка к IP:** Cookie привязан к IP-адресу клиента, что предотвращает использование украденного Cookie с другого устройства.

**Ограничения защиты:**
- Если злоумышленник имеет полный контроль над сетью (например, в публичном Wi-Fi), он может перехватить и повторно отправить SYN с данными.
- Для защиты от таких атак необходимо использовать TLS поверх TFO.

## Практические сценарии

### 1. Системная конфигурация

```bash
# Включение TFO (Client + Server + Auto)
sudo sysctl -w net.ipv4.tcp_fastopen=1027

# Установка статического ключа (необязательно, рекомендуется ротация)
# Если не задано, ключ генерируется при загрузке
echo "deadbeefdeadbeefdeadbeefdeadbeef" | sudo tee /proc/sys/net/ipv4/tcp_fastopen_key

# Проверка текущего значения
sysctl net.ipv4.tcp_fastopen
# → net.ipv4.tcp_fastopen = 1027
```

**Постоянное сохранение настроек:**
```bash
# Добавление в sysctl.conf
echo "net.ipv4.tcp_fastopen=1027" | sudo tee -a /etc/sysctl.d/99-tcp-tuning.conf
sudo sysctl --system
```

### 2. Поддержка в прикладном ПО и языках

*   **Nginx (1.5.8+):**
    ```nginx
    listen 443 ssl fastopen=256; # 256 — размер очереди TFO
    ```

*   **Apache:**
    ```apache
    # В модуле mod_proxy или mod_ssl
    Listen 443
    SSLEngine on
    ```

*   **Python (3.7+):**
    ```python
    import socket
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.setsockopt(socket.IPPROTO_TCP, socket.TCP_FASTOPEN, 5)
    ```

*   **Go:**
    ```go
    import "syscall"
    
    // Требуется использование Control функции
    dialer := &net.Dialer{
        Control: func(network, address string, c syscall.RawConn) error {
            return c.Control(func(fd uintptr) {
                syscall.SetsockoptInt(int(fd), syscall.IPPROTO_TCP, syscall.TCP_FASTOPEN_CONNECT, 1)
            })
        },
    }
    ```

*   **Java (Java 9+):**
    ```java
    Socket socket = new Socket();
    socket.setOption(StandardSocketOptions.TCP_FASTOPEN_CONNECT, true);
    socket.connect(new InetSocketAddress("example.com", 80));
    ```

### 3. Валидация работоспособности

```bash
# 1. Проверка через curl (с поддержкой TFO)
curl -v --tcp-fastopen http://example.com

# 2. Проверка через ss
ss -tin state established | grep tfo
# → tfo:1 означает, что соединение использовало TFO

# 3. Проверка через nstat
nstat -az | grep -i FastOpen
# → TcpExtTCPFastOpenActive       — Успешные исходящие TFO (клиент)
# → TcpExtTCPFastOpenPassive      — Успешные входящие TFO (сервер)
```

### 4. Диагностика и мониторинг

Для анализа эффективности TFO используются счетчики `nstat`:

```bash
# Просмотр статистики TFO
nstat -az | grep -i FastOpen

# Ключевые метрики:
# TcpExtTCPFastOpenActive       — Успешные исходящие TFO (клиент)
# TcpExtTCPFastOpenPassive      — Успешные входящие TFO (сервер)
# TcpExtTCPFastOpenCookieReq    — Количество запросов Cookie
# TcpExtTCPFastOpenCookieRecv   — Количество полученных Cookie
# TcpExtTCPFastOpenCookieCheck  — Количество проверок Cookie
# TcpExtTCPFastOpenBlackhole    — Количество обнаруженных Blackholes
# TcpExtTCPFastOpenOverflow     — Количество переполнений очереди TFO
```

Проверка конкретного соединения через `ss`:
```bash
ss -ti state established | grep tfo
# Результат "tfo:1" означает, что соединение использовало TFO.
```

**Диагностика проблем:**

1. **TFO не работает на клиенте:**
   ```bash
   # Проверка значения sysctl
   sysctl net.ipv4.tcp_fastopen
   # Должно быть: 1, 3, 5, 7, 1027 или другое значение с битом 0x1
   ```

2. **TFO не работает на сервере:**
   ```bash
   # Проверка значения sysctl
   sysctl net.ipv4.tcp_fastopen
   # Должно быть: 2, 3, 6, 7, 1027 или другое значение с битом 0x2
   
   # Проверка поддержки в приложении
   ss -tlnp | grep :80
   # Должно показать, что процесс слушает на порту
   ```

3. **Проблемы с Blackhole:**
   ```bash
   # Проверка наличия blackhole
   nstat -az | grep TcpExtTCPFastOpenBlackhole
   
   # Если значение растет, возможно, сетевое оборудование блокирует TFO
   # Решение: уменьшить tcp_fastopen_blackhole_timeout_sec или проверить конфигурацию файрвола
   ```

## Дополнительная информация

### Сравнение с TLS 1.3 и QUIC

| Характеристика | TCP Fast Open | TLS 1.3 0-RTT | QUIC (HTTP/3) |
| :--- | :--- | :--- | :--- |
| **Уровень** | L4 (TCP) | L6/L7 (TLS) | L4 (UDP) |
| **Защита данных** | Открытый текст в SYN | Зашифровано | Зашифровано |
| **Проблема Replay** | Да | Да | Да |
| **Совместимость** | Средняя (Middleboxes) | Высокая | Высокая |
| **Экономия RTT** | 1 RTT | 1 RTT | 0 RTT (с опциями) |
| **Защита от спуфинга** | Cookie (HMAC) | PSK или ECDHE | Token-based |

### Граничные случаи и ограничения

1. **Размер данных в SYN:**
   - Ограничен размером TCP Options (обычно 1460 байт для MSS = 1460).
   - Для передачи больших данных используйте обычный handshake.

2. **Роуминг и смена IP:**
   - При смене IP-адреса (например, переход с Wi-Fi на мобильную сеть) Cookie становится невалидным.
   - Клиент должен запросить новый Cookie при следующем соединении.

3. **Балансировщики нагрузки:**
   - Если за балансировщиком находятся несколько серверов, Cookie должен быть общим (используйте общий секретный ключ).

4. **Контейнеры и виртуальные машины:**
   - TFO работает в контейнерах, но может потребоваться настройка сетевого стека хоста.
   - Для Docker: `--sysctl net.ipv4.tcp_fastopen=1027`.

5. **Файрволы и NAT:**
   - Некоторые файрволы блокируют SYN с данными (считают их аномальными).
   - Решение: настройка правил для разрешения TFO или использование tcp_fastopen_blackhole_timeout_sec.

### Влияние на производительность

| Метрика | Без TFO | С TFO | Улучшение |
| :--- | :--- | :--- | :--- |
| **TTFB (Time To First Byte)** | 2 RTT | 1 RTT | 50% |
| **Latency для повторных соединений** | Высокая | Низкая | Значительное |
| **CPU overhead** | Минимальный | Минимальный | Незначительное |
| **Память** | Стандартная | +Cookie cache | Незначительное |

### Рекомендации по внедрению

1. **Этап 1: Мониторинг**
   - Включить TFO на тестовом сервере.
   - Мониторить счетчики `nstat` в течение 1-2 недель.

2. **Этап 2: Постепенное внедрение**
   - Начать с внутренних сервисов.
   - Распространить на внешние сервисы после проверки.

3. **Этап 3: Оптимизация**
   - Настроить `tcp_fastopen_blackhole_timeout_sec` в зависимости от инфраструктуры.
   - Регулярно ротировать секретный ключ.
