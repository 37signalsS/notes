# Оптимизация буферов TCP в Linux

## Определения

**TCP (Transmission Control Protocol — протокол управления передачей) буферы** — области оперативной памяти ядра, выделяемые для временного хранения входящих (`rmem`) и исходящих (`wmem`) данных сетевых соединений. Буферы приема (`SO_RCVBUF`) хранят данные до тех пор, пока приложение не прочитает их через `read()`/`recv()`. Буферы отправки (`SO_SNDBUF`) хранят данные до подтверждения их получения удаленной стороной (ACK).

**Автотюнинг TCP (TCP Autotuning)** — механизм ядра Linux, который динамически изменяет размер буфера для каждого соединения в пределах заданных границ на основе текущей нагрузки и сетевых характеристик (RTT, доступная полоса). Управление осуществляется через `net.ipv4.tcp_moderate_rcvbuf` (включено/выключено) и параметры `tcp_rmem`/`tcp_wmem`. Автотюнинг接收а включен по умолчанию (`tcp_moderate_rcvbuf = 1`), но отправки — нет (требует `SO_SNDBUF` или `TCP_NOTSENT_LOWAT`).

**BDP (Bandwidth-Delay Product — произведение пропускной способности на задержку)** — физический объем данных, который может находиться в сетевом канале «в полете». Рассчитывается как: `Bandwidth (bps) * RTT (s)`. BDP определяет минимальный размер окна приема для полной утилизации канала.

**sk_buff (Socket Buffer)** — основная структура данных ядра Linux для хранения сетевых пакетов. Каждый пакет represented в виде цепочки `sk_buff` (skb), каждая из которых содержит указатели на сырые данные и метаданные (протокольные заголовки, интерфейс получения и т.д.).

**tcp_mem** — глобальный параметр, определяющий лимиты потребления памяти всей подсистемой TCP в системе (суммарно для всех соединений). Измеряется в страницах памяти (обычно 4 КБ) и имеет формат `low pressure high`.

**Memory Pressure (Давление памяти)** — состояние системы, при котором общее потребление памяти TCP превышает порог `pressure` в `tcp_mem`. В этом режиме ядро ограничивает автотюнинг и пытается сжать буферы до значений `min`.

**Zero Window (нулевое окно)** — состояние, при котором получатель не может принять больше данных, потому что его буфер приема заполнен (`SO_RCVBUF`). Отправитель получает Window Update с размером окна 0 и прекращает передачу до получения Window Update с ненулевым размером.

**Window Full (окно заполнено)** — состояние, когда отправитель заполнил все доступное окно приема получателя и ждет ACK для освобождения места. В отличие от Zero Window, это временное состояние при нормальной работе.

## Основные концепции

### Иерархия параметров настройки

В Linux настройка буферов разделена на два уровня:

1.  **Глобальный уровень (`net.core.*`):** Устанавливает жесткие лимиты для всех типов сокетов (TCP, UDP, Unix sockets, RAW).
    *   `net.core.rmem_max` — абсолютный максимум для буфера приема.
    *   `net.core.wmem_max` — абсолютный максимум для буфера отправки.
    *   `net.core.rmem_default` — размер буфера приема по умолчанию для новых сокетов.
    *   `net.core.wmem_default` — размер буфера отправки по умолчанию.
2.  **Уровень протокола (`net.ipv4.tcp_*`):** Специфичные настройки для TCP, работающие в рамках глобальных лимитов `net.core`.
    *   `net.ipv4.tcp_rmem` — параметры буфера приема.
    *   `net.ipv4.tcp_wmem` — параметры буфера отправки.

**Важно:** Если `tcp_rmem` max > `rmem_max`, ядро использует `rmem_max` как верхний лимит. Аналогично для `wmem`.

### Формат параметров tcp_rmem и tcp_wmem

Каждая директива принимает три целочисленных значения (в байтах): `min default max`.

| Значение | Описание | Роль в системе |
| :--- | :--- | :--- |
| **min** | Минимальный размер | Гарантированный объем памяти даже в условиях сильной нехватки ОЗУ (**Memory Pressure**). Обычно 4 КБ (1 страница). |
| **default** | Начальный размер | Размер буфера при создании нового сокета. Должен быть согласован с BDP типичных соединений. Для 1 Гбит/с и 10 мс RTT: ~1.2 МБ. |
| **max** | Максимальный размер | Верхняя граница для автотюнинга. **Важно:** не может превышать `net.core.[r\|w]mem_max`. Для 100 Гбит/с и 10 мс RTT: ~125 МБ. |

### Алгоритм автотюнинга приема

Автотюнинг接收а (`tcp_moderate_rcvbuf = 1`) работает следующим образом:

1. **Мониторинг скорости чтения:** Ядро отслеживает, как быстро приложение читает данные из сокета (`read()`/`recv()`).
2. **Расчет необходимого размера:** Если приложение читает данные быстрее, чем они поступают, ядро увеличивает `rcv_space` (рассчитанный размер буфера).
3. **Применение ограничений:** Новый размер не может превышать `tcp_rmem` max и не может быть меньше `tcp_rmem` min.
4. **Уведомление отправителя:** После изменения размера буфера отправляется Window Update, сообщая новое окно приема.

**Особенности:**
- Автотюнинг接收а включен по умолчанию и работает эффективно для большинства сценариев.
- Автотюнинг отправки **не включен по умолчанию** — требует явного вызова `setsockopt(SO_SNDBUF)` или `TCP_NOTSENT_LOWAT`.
- При Memory Pressure автотюнинг отключается и буферы сжимаются до `min`.

### Управление накладными расходами (Overhead)

Не весь объем буфера используется для полезных данных. Часть памяти уходит на структуры данных ядра (`sk_buff`).
*   **`net.ipv4.tcp_adv_win_scale`:** коэффициент масштабирования. По умолчанию `1`, что означает, что половина буфера (`1/2^1`) отводится под прикладные данные, а половина — под служебные структуры. При значении `2` — 3/4 под данные, 1/4 под структуры.
*   **`net.ipv4.tcp_window_scaling`:** (RFC 7323) Обязательно должен быть включен (`1`) для использования окон более 64 КБ.
*   **`net.ipv4.tcp_moderate_rcvbuf`:** Включает/выключает автотюнинг接收а (1 = включен, 0 = выключен).

### Глобальный лимит tcp_mem и механизм Memory Pressure

В отличие от `tcp_rmem`, параметр `net.ipv4.tcp_mem` измеряется в **страницах памяти** (обычно 4 КБ) и имеет формат `low pressure high`:
*   **low:** Порог, ниже которого ядро не ограничивает выделение памяти.
*   **pressure:** При достижении этого порога ядро переходит в режим «давления памяти», отключая автотюнинг и пытаясь сжать буферы до значений `min`.
*   **high:** Абсолютный предел. При его достижении новые данные отбрасываются (Drop), а соединения могут принудительно закрываться.

**Расчет рекомендуемых значений tcp_mem:**
Для системы с 64 ГБ ОЗУ и выделением 25% на TCP:
- low: 25% от 64 ГБ = 16 ГБ = 4 194 304 страницы
- pressure: 50% от 16 ГБ = 8 ГБ = 2 097 152 страницы
- high: 75% от 16 ГБ = 12 ГБ = 3 145 728 страницы

### Взаимодействие с другими параметрами TCP

Буферы тесно взаимодействуют с другими параметрами стека TCP:
*   **`tcp_congestion_control`:** Алгоритм контроля перегрузки (CUBIC, BBR) влияет на скорость заполнения буферов.
*   **`tcp_window_scaling`:** Включает масштабирование окон, необходимое для больших буферов.
*   **`tcp_timestamps`:** Включает временные метки, необходимые для accurate RTT estimation.
*   **`tcp_sack`:** Включает selective acknowledgment, что позволяет более точно определять потерянные пакеты.

## Практические сценарии

### 1. Расчет оптимального размера буфера (BDP)

Для полной утилизации канала размер буфера должен быть не меньше **BDP**.

**Сценарий 2026 года (100 Гбит/с — High Bandwidth):**
*   Канал: 100 Гбит/с (~12.5 ГБ/с).
*   RTT: 10 мс (0.01 с).
*   **BDP** = 12 500 МБ/с × 0.01 с = **125 МБ**.

Для такого соединения значение `max` должно быть не менее 128 МБ (134 217 728 байт).

**Формулы для расчета:**
```
BDP (байты) = Bandwidth (Мбит/с) × RTT (мс) × 1000 / 8
BDP (МБ) = Bandwidth (Гбит/с) × RTT (мс) × 1000 / 8 / 1024
```

**Примеры расчета:**
| Канал | RTT | BDP | Рекомендуемый max |
| :--- | :--- | :--- | :--- |
| 1 Гбит/с | 10 мс | 1.25 МБ | 4 МБ |
| 10 Гбит/с | 10 мс | 12.5 МБ | 32 МБ |
| 100 Гбит/с | 10 мс | 125 МБ | 256 МБ |
| 10 Гбит/с | 50 мс | 62.5 МБ | 128 МБ |

### 2. Применение настроек для высокопроизводительных узлов

**Постоянное сохранение (`/etc/sysctl.d/99-network-performance.conf`):**

```ini
# Глобальные максимумы (128 МБ)
net.core.rmem_max = 134217728
net.core.wmem_max = 134217728

# TCP буферы: min (4K), default (стандарт), max (128M)
net.ipv4.tcp_rmem = 4096 131072 134217728
net.ipv4.tcp_wmem = 4096 131072 134217728

# Очереди интерфейса (важно для 10G+)
# netdev_max_backlog — очередь пакетов до попадания в IP-стек
net.core.netdev_max_backlog = 16384

# Включение автотюнинга приема
net.ipv4.tcp_moderate_rcvbuf = 1

# Глобальный лимит TCP памяти (пример для системы с 64ГБ ОЗУ)
# Значения в страницах (4КБ). Пример: 4ГБ 8ГБ 12ГБ
net.ipv4.tcp_mem = 1048576 2097152 3145728
```

Применить: `sudo sysctl -p /etc/sysctl.d/99-network-performance.conf`

### 3. Настройка для Docker и контейнеров

**Системные настройки (на хосте):**
```bash
# Увеличение лимитов для контейнеров
sudo sysctl -w net.core.rmem_max=134217728
sudo sysctl -w net.core.wmem_max=134217728
sudo sysctl -w net.ipv4.tcp_rmem="4096 131072 134217728"
sudo sysctl -w net.ipv4.tcp_wmem="4096 131072 134217728"
```

**Настройки для Docker:**
```bash
# При запуске контейнера
docker run --sysctl net.ipv4.tcp_rmem="4096 131072 134217728" \
           --sysctl net.ipv4.tcp_wmem="4096 131072 134217728" \
           your_image

# Или через /etc/docker/daemon.json
{
  "sysctls": {
    "net.ipv4.tcp_rmem": "4096 131072 134217728",
    "net.ipv4.tcp_wmem": "4096 131072 134217728"
  }
}
```

**Для Kubernetes:**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: high-perf-pod
spec:
  containers:
  - name: app
    image: your_image
    securityContext:
      sysctls:
      - name: net.ipv4.tcp_rmem
        value: "4096 131072 134217728"
      - name: net.ipv4.tcp_wmem
        value: "4096 131072 134217728"
```

### 5. Диагностика состояния буферов

**Использование `ss` для анализа конкретного соединения:**

```bash
# Просмотр параметров памяти сокета
ss -tin state established

# Ключевые поля в выводе:
# rcv_space: текущее окно приема (зависит от буфера)
# rcv_buf: текущий выделенный буфер приема
# wmem_queued: данные в очереди на отправку
# skmem:(r<rmem>,rb<rcv_buf>,t<wmem_queued>,tb<send_buf>)
```

**Пример вывода:**
```bash
ss -tin state established dst 192.168.1.100
# →ESTAB 0 0 192.168.1.1:22 192.168.1.100:54321
# → cubic wscale:7,7 rto:204 rtt:1.5/0.75 ato:40 mss:1448 pmtu:1500
# → rcvmss:1448 advmss:1448 cwnd:10 ssthresh:7 bytes_sent:1234
# → bytes_acked:1234 segs_out:100 segs_in:50 data_segs_out:80
# → send 77.2Mbps pacing_rate 154.4Mbps delivery_rate 77.2Mbps
# → rcv_space:14600 rcv_ssthresh:64088 minrtt:0.5
```

**Мониторинг через nstat:**
```bash
# Просмотр счетчиков памяти
nstat -az | grep -i TCPMemory

# Ключевые счетчики:
# TcpExtTCPMemoryPressures    — Количество срабатываний Memory Pressure
# TcpExtTCPMemoryPressuresScheduled — Запланированные освобождения памяти
```

## Дополнительная информация

### Bufferbloat и BBR

Использование огромных буферов с классическими алгоритмами (CUBIC, Reno) на нестабильных каналах может привести к **Bufferbloat** — пакеты «застревают» в очередях, что резко увеличивает задержку.
В 2026 году стандартом является использование **BBR (v3)**, который более эффективно управляет заполнением буферов, ориентируясь на реальную пропускную способность, а не на потери.

**Взаимодействие BBR с буферами:**
- BBR v3 целится в BDP, но не позволяет буферам расти бесконечно.
- При использовании BBR рекомендуется устанавливать `tcp_rmem` max ≈ 2× BDP.
- Мониторьте `delivery_rate` через `ss -tin` для оценки эффективности.

### Рекомендации по выбору значений (max)

| Тип системы | Лимит (max) | Примечание |
| :--- | :--- | :--- |
| **Обычные веб-серверы** | 16–32 МБ | Сбалансированный вариант для 1–10 Гбит/с. |
| **Стриминг / CDN** | 64–128 МБ | Для компенсации задержек при доставке тяжелого контента. |
| **Data Science / Grid** | 256 МБ+ | Для обработки огромных датасетов в 400 Гбит/с+ сетях. |
| **Базы данных** | 4–16 МБ | Баланс между производительностью репликации и потреблением памяти. |

### Типичные проблемы и их решение

| Проблема | Симптомы | Причина | Решение |
| :--- | :--- | :--- | :--- |
| **Memory Pressure** | Рост `TCPMemoryPressures` в nstat | `tcp_mem` max слишком низкий | Увеличить `tcp_mem` high |
| **Zero Window** | Приложение не успевает читать данные | `SO_RCVBUF` или `tcp_rmem` max слишком мал | Увеличить `tcp_rmem` max, оптимизировать приложение |
| **Window Full** | Отправитель ждет ACK | Маленький буфер отправки | Увеличить `tcp_wmem` max |
| **Bufferbloat** | Высокая задержка при стабильной скорости | Слишком большие буферы | Использовать BBR, уменьшить буферы |
| **Low Throughput** | Неполная утилизация канала | Буферы меньше BDP | Рассчитать BDP, увеличить `tcp_rmem`/`tcp_wmem` max |

### Диагностика проблем

**Проверка Memory Pressure:**
```bash
# Проверка текущего потребления памяти TCP
cat /proc/net/sockstat | grep TCP
# → TCP: inuse 150 orphan 0 tw 0 alloc 200 mem 150

# Если mem > pressure в tcp_mem, ядро в режиме Memory Pressure
sysctl net.ipv4.tcp_mem
# → net.ipv4.tcp_mem = 1048576 2097152 3145728
```

**Проверка состояния буферов:**
```bash
# Мониторинг в реальном времени
watch -n 1 'ss -tin state established | grep -E "rcv_space|rcv_buf"'

# Или через /proc/net/tcp
cat /proc/net/tcp | awk '{print $3, $4}' | head -10
```

**Проверка автотюнинга:**
```bash
# Проверка включения автотюнинга
sysctl net.ipv4.tcp_moderate_rcvbuf
# → net.ipv4.tcp_moderate_rcvbuf = 1

# Просмотр текущих значений буферов для соединения
ss -tin state established dst 10.0.0.1 | grep -E "rcv_space|rcv_buf|wmem_queued"
```

### Влияние на производительность

| Метрика | Без оптимизации | С оптимизацией | Улучшение |
| :--- | :--- | :--- | :--- |
| **Throughput** | 10–50% канала | 90–100% канала | 2–10× |
| **TTFB** | 2–3 RTT | 1–1.5 RTT | 30–50% |
| **Latency** | Высокая | Стабильная | Значительное |
| **CPU overhead** | Минимальный | Незначительный | Минимальный |

1. **Регулярная проверка nstat:**
   ```bash

   nstat -az | grep -E "TCPMemory|WindowFull|ZeroWindow"
   ```

2. **Настройка алертов:**
   ```bash

   fi
   ```
