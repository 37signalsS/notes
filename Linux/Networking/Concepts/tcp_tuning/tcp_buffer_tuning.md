# Оптимизация буферов TCP в Linux

## Определения

**TCP (Transmission Control Protocol — протокол управления передачей) буферы** — области оперативной памяти ядра, выделяемые для временного хранения входящих (`rmem`) и исходящих (`wmem`) данных сетевых соединений.

**Автотюнинг TCP (TCP Autotuning)** — механизм ядра Linux, который динамически изменяет размер буфера для каждого соединения в пределах заданных границ на основе текущей нагрузки и сетевых характеристик (RTT, доступная полоса).

**BDP (Bandwidth-Delay Product — произведение пропускной способности на задержку)** — физический объем данных, который может находиться в сетевом канале «в полете». Рассчитывается как: `Bandwidth (bps) * RTT (s)`.

**tcp_mem** — глобальный параметр, определяющий лимиты потребления памяти всей подсистемой TCP в системе (суммарно для всех соединений).

## Основные концепции

### Иерархия параметров настройки

В Linux настройка буферов разделена на два уровня:

1.  **Глобальный уровень (`net.core.*`):** Устанавливает жесткие лимиты для всех типов сокетов (TCP, UDP, Unix sockets, RAW).
    *   `net.core.rmem_max` — абсолютный максимум для буфера приема.
    *   `net.core.wmem_max` — абсолютный максимум для буфера отправки.
2.  **Уровень протокола (`net.ipv4.tcp_*`):** Специфичные настройки для TCP, работающие в рамках глобальных лимитов `net.core`.
    *   `net.ipv4.tcp_rmem` — параметры буфера приема.
    *   `net.ipv4.tcp_wmem` — параметры буфера отправки.

### Формат параметров tcp_rmem и tcp_wmem

Каждая директива принимает три целочисленных значения (в байтах): `min default max`.

| Значение | Описание | Роль в системе |
| :--- | :--- | :--- |
| **min** | Минимальный размер | Гарантированный объем памяти даже в условиях сильной нехватки ОЗУ (**Memory Pressure**). |
| **default** | Начальный размер | Размер буфера при создании нового сокета. Должен быть согласован с BDP типичных соединений. |
| **max** | Максимальный размер | Верхняя граница для автотюнинга. **Важно:** не может превышать `net.core.[r\|w]mem_max`. |

### Управление накладными расходами (Overhead)

Не весь объем буфера используется для полезных данных. Часть памяти уходит на структуры данных ядра (`sk_buff`).
*   **`net.ipv4.tcp_adv_win_scale`:** коэффициент масштабирования. По умолчанию `1`, что означает, что половина буфера (`1/2^1`) отводится под прикладные данные, а половина — под служебные структуры.
*   **`net.ipv4.tcp_window_scaling`:** (RFC 7323) Обязательно должен быть включен (`1`) для использования окон более 64 КБ.

### Глобальный лимит tcp_mem и механизм Memory Pressure

В отличие от `tcp_rmem`, параметр `net.ipv4.tcp_mem` измеряется в **страницах памяти** (обычно 4 КБ) и имеет формат `low pressure high`:
*   **low:** Порог, ниже которого ядро не ограничивает выделение памяти.
*   **pressure:** При достижении этого порога ядро переходит в режим «давления памяти», отключая автотюнинг и пытаясь сжать буферы до значений `min`.
*   **high:** Абсолютный предел. При его достижении новые данные отбрасываются (Drop), а соединения могут принудительно закрываться.

## Практические сценарии

### 1. Расчет оптимального размера буфера (BDP)

Для полной утилизации канала размер буфера должен быть не меньше **BDP**.

**Сценарий 2026 года (100 Гбит/с — High Bandwidth):**
*   Канал: 100 Гбит/с (~12.5 ГБ/с).
*   RTT: 10 мс (0.01 с).
*   **BDP** = 12 500 МБ/с × 0.01 с = **125 МБ**.

Для такого соединения значение `max` должно быть не менее 128 МБ (134 217 728 байт).

### 2. Применение настроек для высокопроизводительных узлов

**Постоянное сохранение (`/etc/sysctl.d/99-network-performance.conf`):**

```ini
# Глобальные максимумы (128 МБ)
net.core.rmem_max = 134217728
net.core.wmem_max = 134217728

# TCP буферы: min (4K), default (стандарт), max (128M)
net.ipv4.tcp_rmem = 4096 131072 134217728
net.ipv4.tcp_wmem = 4096 131072 134217728

# Очереди интерфейса (важно для 10G+)
# netdev_max_backlog — очередь пакетов до попадания в IP-стек
net.core.netdev_max_backlog = 16384

# Включение автотюнинга приема
net.ipv4.tcp_moderate_rcvbuf = 1

# Глобальный лимит TCP памяти (пример для системы с 64ГБ ОЗУ)
# Значения в страницах (4КБ). Пример: 4ГБ 8ГБ 12ГБ
net.ipv4.tcp_mem = 1048576 2097152 3145728
```

Применить: `sudo sysctl -p /etc/sysctl.d/99-network-performance.conf`

### 3. Диагностика состояния буферов

Использование `ss` для анализа конкретного соединения:

```bash
# Просмотр параметров памяти сокета
ss -tin state established

# rcv_space: текущее окно приема (зависит от буфера)
# rcv_buf: текущий выделенный буфер приема
# wmem_queued: данные в очереди на отправку
```

Если в выводе `nstat` растут счетчики `TCPMemoryPressures`, необходимо увеличить лимиты `tcp_mem`.

## Дополнительная информация

### Bufferbloat и BBR

Использование огромных буферов с классическими алгоритмами (CUBIC, Reno) на нестабильных каналах может привести к **Bufferbloat** — пакеты «застревают» в очередях, что резко увеличивает задержку.
В 2026 году стандартом является использование **BBR (v3)**, который более эффективно управляет заполнением буферов, ориентируясь на реальную пропускную способность, а не на потери.

### Рекомендации по выбору значений (max)

| Тип системы | Лимит (max) | Примечание |
| :--- | :--- | :--- |
| **Обычные веб-серверы** | 16–32 МБ | Сбалансированный вариант для 1–10 Гбит/с. |
| **Стриминг / CDN** | 64–128 МБ | Для компенсации задержек при доставке тяжелого контента. |
| **Data Science / Grid** | 256 МБ+ | Для обработки огромных датасетов в 400 Гбит/с+ сетях. |
