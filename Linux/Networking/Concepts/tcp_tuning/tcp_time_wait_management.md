# Управление состоянием TIME_WAIT

## Определения

**TIME_WAIT** — состояние TCP-соединения на стороне, инициировавшей закрытие, после получения FIN от удалённой стороны. Длительность — 2×MSL (Maximum Segment Lifetime, по умолчанию 60 секунд в Linux).

**Ephemeral ports** — диапазон эфемерных (временных) портов, используемых ядром для исходящих TCP-соединений.

## Basic Concepts

### Зачем нужен TIME_WAIT

TIME_WAIT решает две задачи:

1. **Надёжная доставка:** гарантирует, что последние пакеты (ACK) дойдут до удалённой стороны. Если ACK потерян, удалённая сторона повторно отправит FIN — сокет в TIME_WAIT ответит ACK.
2. **Защита от дубликатов:** предотвращает попадание «заблудившихся» пакетов старого соединения в новое, использующее те же IP:port.

### Проблематика

На серверах с большим количеством короткоживущих **исходящих** соединений (API-клиенты, прокси, микросервисы) скапливается много сокетов в TIME_WAIT, занимая эфемерные порты. Когда диапазон портов исчерпан, ядро не может выделить порт для `connect()` → ошибка `Cannot assign requested address`.

**Расчёт ёмкости:**

```
Доступные порты = ip_local_port_range (верх - низ + 1)
Макс. соединений/сек = Доступные порты / TIME_WAIT_длительность
```

При дефолтном диапазоне `32768–60999` (28232 порта) и TIME_WAIT 60 сек: ~470 новых соединений/сек.

### TIME_WAIT на сервере vs клиенте

| Роль | Кто в TIME_WAIT | Почему |
| :--- | :--- | :--- |
| **Клиент** (исходящие) | Клиент | Клиент инициирует закрытие (активная сторона) |
| **Сервер** (входящие) | Клиент | Сервер пассивно закрывает, клиент уходит в TIME_WAIT |
| **Прокси** (обе стороны) | Прокси (к upstream) | Прокси — клиент для upstream-серверов |

> **Вывод:** TIME_WAIT проблема **исходящих** соединений. Для входящих соединений TIME_WAIT уходит на клиента, не нагружая сервер.

### tcp_tw_recycle — удалён в ядре 4.12+

Параметр `tcp_tw_recycle` удалён из ядра Linux 4.12+ из-за несовместимости с NAT. Он использовал временные метки (timestamps) для ускоренного удаления TIME_WAIT-сокетов, что ломало соединения за NAT (разные хосты за одним NAT имели разные timestamp).

## Practical Scenarios

### Диагностика

```bash
# Проверка текущего диапазона ephemeral портов
cat /proc/sys/net/ipv4/ip_local_port_range
# Пример: 32768  60999

# Количество соединений в TIME_WAIT
ss -tan state time-wait | wc -l

# Детали TIME-WAIT сессий (время ожидания)
ss -tai state time-wait

# Сводная статистика
ss -s
```

**Интерпретация:** если количество TIME_WAIT близко к размеру диапазона портов → новые исходящие соединения будут падать.

### Настройка параметров

**Временно:**

```bash
# Разрешить повторное использование сокетов TIME_WAIT (исходящие)
sudo sysctl -w net.ipv4.tcp_tw_reuse=1

# Уменьшить время FIN-WAIT-2 (ускоряет закрытие)
sudo sysctl -w net.ipv4.tcp_fin_timeout=30

# Расширить диапазон ephemeral портов
sudo sysctl -w net.ipv4.ip_local_port_range="1024 65535"
```

**Постоянно** (`/etc/sysctl.d/99-network.conf`):

```ini
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 30
net.ipv4.ip_local_port_range = 1024 65535
```

Применение: `sudo sysctl -p /etc/sysctl.d/99-network.conf`

### Разбор параметров

| Параметр | По умолчанию | Рекомендуемое | Описание |
| :--- | :--- | :--- | :--- |
| `tcp_tw_reuse` | 0 | 1 | Повторное использование TIME_WAIT-сокетов **только для исходящих** соединений. Безопасен. |
| `tcp_fin_timeout` | 60 | 15–30 | Время удержания сокета в FIN-WAIT-2 перед закрытием. |
| `ip_local_port_range` | 32768–60999 | 1024–65535 | Диапазон ephemeral портов. ~64K портов вместо ~28K. |

> **Важно:** `tcp_tw_reuse` работает только для **исходящих** соединений. Для входящих (серверных) соединений он не применяется — TIME_WAIT всё равно уходит на клиента.

### Рекомендации по сценарию

| Сценарий | tcp_tw_reuse | ip_local_port_range | tcp_fin_timeout | Обоснование |
| :--- | :--- | :--- | :--- | :--- |
| **API-клиент** (исходящие HTTP) | 1 | 1024–65535 | 15 | Тысячи коротких соединений к API |
| **Прокси/балансировщик** | 1 | 1024–65535 | 15 | Исходящие к upstream-серверам |
| **Веб-сервер** (входящие HTTP) | 0 (не нужен) | 32768–60999 | 30 | TIME_WAIT уходит на клиентов |
| **Базы данных** (пул соединений) | 1 | 1024–65535 | 15 | Долгие соединения, но возможны всплески |

### Альтернативные решения

- **Connection pooling:** пул постоянных соединений вместо короткоживущих.
- **HTTP/2:** мультиплексирование запросов в одном TCP-соединении.
- **Keepalive:** повторное использование TCP-соединений (HTTP keep-alive).
- **Масштабирование портов:** при необходимости — несколько IP-адресов для увеличения ёмкости (каждый IP = 64K портов).
