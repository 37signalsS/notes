# Управление состоянием TIME_WAIT в Linux

## Определения

* **TIME_WAIT** — состояние TCP-соединения на стороне инициатора закрытия («активное закрытие»), наступающее после завершения обмена пакетами FIN/ACK. Сокет остается в этом состоянии в течение 2 × MSL (Maximum Segment Lifetime).
* **2 × MSL** — в Linux этот интервал жестко зашит в ядре и составляет **60 секунд**. Он не меняется параметром `tcp_fin_timeout`.
* **tcp_tw_reuse** — механизм ядра, позволяющий безопасно переиспользовать сокет в состоянии `TIME_WAIT` для нового исходящего соединения, если временные метки (**TCP Timestamps**) нового пакета SYN больше, чем у последнего пакета в закрытой сессии.

## Базовые концепции

### Зачем нужно ожидание 60 секунд?

1.  **Надежность закрытия:** Если последний ACK от инициатора потеряется, удаленная сторона отправит FIN повторно. Состояние `TIME_WAIT` позволяет узлу ответить на этот повторный FIN, завершив процедуру корректно.
2.  **Защита от «блуждающих» пакетов:** Гарантирует, что пакеты из старой сессии, задержавшиеся в сети, не будут ошибочно приняты в новое соединение с теми же IP и портами (5-tuple).

### Проблема исчерпания эфемерных портов

На высоконагруженных узлах (прокси-серверы, API-шлюзы) тысячи коротких соединений могут быстро заполнить диапазон портов.

**Формула лимита:**
`Connection Rate (conn/s) < Доступные порты / 60`

Если диапазон составляет 28 000 портов, то при скорости выше 460 соед./сек система начнет выдавать ошибку `EADDRNOTAVAIL`.

### Глобальный лимит tw_buckets

Параметр `net.ipv4.tcp_max_tw_buckets` ограничивает общее количество сокетов в `TIME_WAIT` в системе. Если предел достигнут, новые сокеты в это состояние не переходят, а закрываются немедленно с выводом предупреждения в `dmesg`. Это может привести к нарушению надежности TCP, но спасает от переполнения памяти.

## Практические сценарии

### 1. Диагностика и мониторинг

```bash
# Текущее количество сокетов в TIME_WAIT
ss -tan state time-wait | wc -l

# Глобальная статистика TCP (включая orphaned и tw)
ss -s

# Просмотр ошибок при нехватке buckets
dmesg | grep "TCP: time wait bucket table overflow"
```

### 2. Настройка для высоконагруженных систем (2026)

В 2026 году (ядра 6.x+) рекомендуется комбинировать системный тюнинг с оптимизацией приложений.

```ini
# /etc/sysctl.d/99-time-wait.conf

# 1. Безопасное переиспользование сокетов для исходящих соединений
# ТРЕБУЕТ net.ipv4.tcp_timestamps = 1
net.ipv4.tcp_tw_reuse = 1

# 2. Расширение диапазона портов (максимально возможное)
net.ipv4.ip_local_port_range = 1024 65535

# 3. Увеличение лимита buckets (для систем с большим объемом RAM)
# Позволяет держать в памяти больше закрытых сессий без сбросов
net.ipv4.tcp_max_tw_buckets = 262144

# 4. Тайм-аут ожидания FIN (не путать с 2xMSL!)
# Сокращает время пребывания в FIN-WAIT-2
net.ipv4.tcp_fin_timeout = 15
```

Применить: `sudo sysctl -p /etc/sysctl.d/99-time-wait.conf`

### 3. Сравнение методов решения

| Метод | Плюсы | Минусы |
| :--- | :--- | :--- |
| **Keep-Alive (App level)** | Самый эффективный; исключает RTT на Handshake. | Требует поддержки клиентом и сервером. |
| **tcp_tw_reuse** | Безопасно решает проблему портов. | Работает только для исходящих (клиентских) соединений. |
| **tcp_tw_recycle** | (УДАЛЕНО) | Не использовать! Ломает работу через NAT. |
| **Увеличение IP-диапазона** | Простота реализации. | Имеет физический предел (65535 портов). |

## Дополнительная информация

### Внимание: tcp_tw_reuse и входящие соединения

Распространенное заблуждение: тюнинг `TIME_WAIT` на веб-сервере поможет при наплыве клиентов.
**Это не так.** На сервере `TIME_WAIT` возникает только если сервер сам инициирует закрытие (что является антипаттерном). Если клиент закрывает соединение первым, `TIME_WAIT` остается на стороне клиента.

### Рекомендации по архитектуре

1.  **Connection Pooling:** В микросервисах всегда используйте пулы соединений (например, в Go `http.Transport` или пулы к БД).
2.  **Эфемерные IP:** Для балансировщиков (Nginx/HAProxy) можно назначать несколько IP-адресов на один интерфейс для связи с бэкендами, увеличивая доступное количество 5-tuple в разы.
