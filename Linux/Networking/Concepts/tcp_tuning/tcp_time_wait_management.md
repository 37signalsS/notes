# Управление состоянием TIME_WAIT в Linux

## Определения

**TIME_WAIT** — состояние TCP-соединения на стороне узла, который первым инициировал закрытие («активное закрытие»). Оно наступает после завершения обмена пакетами FIN/ACK. Сокет остается в этом состоянии в течение интервала $2 \times MSL$ (Maximum Segment Lifetime).

**2 × MSL** — в Linux этот интервал жестко зашит в исходном коде ядра и составляет **60 секунд**. Этот параметр **нельзя** изменить через `sysctl` (в отличие от некоторых других ОС).

**tcp_tw_reuse** — механизм ядра, позволяющий безопасно переиспользовать сокет в состоянии `TIME_WAIT` для нового исходящего соединения. Для работы этого механизма **обязательно** включение временных меток (**TCP Timestamps**).

**Эфемерные порты (Ephemeral Ports)** — диапазон динамических портов, используемых клиентом для инициации соединений. При накоплении тысяч сокетов в `TIME_WAIT` этот диапазон может быть исчерпан.

## Основные концепции

### Зачем нужно ожидание 60 секунд?

1.  **Надежность закрытия:** Если финальный ACK от инициатора потеряется в сети, удаленная сторона отправит FIN повторно. Состояние `TIME_WAIT` позволяет узлу «помнить» соединение и ответить на повторный FIN, завершив процедуру корректно.
2.  **Защита от «пакетов-призраков»:** Гарантирует, что задержавшиеся в сети сегменты из старой сессии не будут ошибочно приняты в новое соединение, использующее те же IP и порты (5-tuple: src_ip, src_port, dst_ip, dst_port, proto).

### Проблема исчерпания портов

На высоконагруженных прокси-серверах (Nginx, Envoy) или API-шлюзах высокая частота коротких соединений приводит к заполнению таблицы состояний.

**Математический лимит:**
`Максимальный RPS < (Количество свободных портов) / 60`

Если в системе доступно 30 000 портов, то при скорости выше 500 соединений в секунду система начнет выдавать ошибку `EADDRNOTAVAIL`.

### Роль TCP Timestamps

Механизм `tcp_tw_reuse` опирается на RFC 1323. Ядро разрешает переиспользование порта, если временная метка нового пакета SYN строго больше, чем метка последнего пакета, полученного в рамках закрытого соединения. Это гарантирует защиту от старых пакетов без ожидания полных 60 секунд.

## Практические сценарии

### 1. Диагностика и мониторинг

```bash
# Подсчет общего количества сокетов в TIME_WAIT
ss -tan state time-wait | wc -l

# Просмотр статистики из SNMP-счетчиков
nstat -az | grep -E 'TcpExtTW|TcpExtTCPTimeWaitOverflow'

# TcpExtTW — количество переиспользованных сокетов через tw_reuse
# TcpExtTCPTimeWaitOverflow — количество сброшенных сокетов из-за нехватки tw_buckets
```

### 2. Настройка системы для Highload

Рекомендуемая конфигурация для узлов с интенсивным исходящим трафиком:

```ini
# /etc/sysctl.d/99-time-wait-tuning.conf

# Включение временных меток (критично для tw_reuse)
net.ipv4.tcp_timestamps = 1

# Разрешение переиспользования TIME_WAIT для исходящих соединений
net.ipv4.tcp_tw_reuse = 1

# Расширение диапазона локальных портов
net.ipv4.ip_local_port_range = 1024 65535

# Лимит «корзин» для TIME_WAIT сокетов в памяти
# Если сокетов больше, они закрываются немедленно (с риском для надежности)
net.ipv4.tcp_max_tw_buckets = 262144

# Тайм-аут ожидания FIN (сокращает FIN-WAIT-2, не влияет на TIME_WAIT)
net.ipv4.tcp_fin_timeout = 15
```

Применить: `sudo sysctl -p /etc/sysctl.d/99-time-wait-tuning.conf`

### 3. Архитектурные решения (Best Practices)

Если тюнинг `sysctl` не помогает, проблему нужно решать на уровне архитектуры:

1.  **Connection Pooling:** Повторное использование TCP-сессий (Keep-Alive) между сервисами. Это радикально снижает частоту открытий/закрытий портов.
2.  **Дополнительные IP-адреса (Source IPs):** Для балансировщика можно назначить несколько IP на один интерфейс. Так как уникальность соединения определяется 5-tuple, каждый новый IP дает еще ~60 000 доступных портов.
3.  **SO_REUSEADDR:** Использование опции сокета в приложении, позволяющей серверу забиндиться на порт, даже если там есть сокеты в `TIME_WAIT` (решает проблему перезапуска сервиса).

## Дополнительная информация

### Миф о tcp_tw_recycle

В старых руководствах часто советовали `net.ipv4.tcp_tw_recycle = 1`. 
**Запомните:** Этот параметр полностью **удален из ядра Linux (4.12+)**. Он ломал работу через NAT, так как отвергал пакеты от разных клиентов за одним NAT-адресом из-за расхождения их временных меток. **Никогда не пытайтесь включить его.**

### TIME_WAIT на стороне сервера

Если вы видите тысячи `TIME_WAIT` на слушающем порту сервера (например, 80 или 443), это означает, что **сервер сам инициирует закрытие соединений**. 
*   **Причина:** Отсутствие HTTP Keep-Alive или некорректные настройки приложения.
*   **Решение:** Настройте Keep-Alive так, чтобы соединение закрывал клиент. Это перенесет состояние `TIME_WAIT` на клиентские машины, разгрузив сервер.
