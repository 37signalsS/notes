# Управление состоянием TIME_WAIT в Linux

## Определения

* **TIME_WAIT** — состояние TCP-соединения на стороне, инициировавшей закрытие, после получения финального сегмента **FIN (Finish)** от удалённой стороны. Длительность по умолчанию в Linux составляет 60 секунд (2 × MSL — **Maximum Segment Lifetime**).
* **Ephemeral ports (Эфемерные порты)** — диапазон временных портов, используемых ядром для инициации исходящих TCP-соединений.
* **tcp_tw_reuse** — параметр ядра, позволяющий повторно использовать сокеты в состоянии `TIME_WAIT` для новых исходящих соединений, если это безопасно с точки зрения временных меток.

## Основные концепции

### Назначение состояния TIME_WAIT

Состояние `TIME_WAIT` критически важно для корректной работы протокола TCP и выполняет две основные функции:

1. **Надёжность завершения (Graceful Shutdown):** гарантирует, что последний пакет подтверждения (**ACK**) будет доставлен. Если он потеряется, удалённая сторона повторно отправит свой **FIN**, а узел в `TIME_WAIT` сможет снова ответить **ACK**.
2. **Защита от перекрытия (Duplicate Protection):** предотвращает ситуацию, когда пакеты от старого («заблудившегося» в сети) соединения будут ошибочно приняты в новое соединение, использующее ту же комбинацию **IP:port** (5-tuple).

### Проблема исчерпания портов

На высоконагруженных узлах с большим количеством коротких исходящих соединений (прокси-серверы, API-клиенты) сокеты в `TIME_WAIT` могут занять весь доступный диапазон эфемерных портов. Это приводит к ошибке:
`Cannot assign requested address (EADDRNOTAVAIL)`.

**Формула ёмкости:**
`Максимальное количество соединений в секунду = Доступные порты / TIME_WAIT (60 сек)`

При стандартном диапазоне в ~28 000 портов лимит составляет около 470 соединений в секунду.

### Различия между сервером и клиентом

| Роль в соединении | Появление TIME_WAIT | Последствия |
| :--- | :--- | :--- |
| **Клиент** (исходящие) | На стороне клиента | Риск исчерпания эфемерных портов для новых `connect()`. |
| **Сервер** (входящие) | На стороне клиента (обычно) | Минимальное влияние на сервер, ресурсы потребляет клиент. |
| **Прокси/Балансировщик** | На прокси (к бэкенду) | Критическая точка; прокси выступает клиентом для upstream. |

### Устаревший параметр tcp_tw_recycle

Параметр **tcp_tw_recycle** полностью удалён из ядра Linux (начиная с версии 4.12+). Его использование приводило к разрыву соединений при работе через **NAT (Network Address Translation)**, так как он некорректно обрабатывал временные метки от разных узлов за одним публичным IP.

## Практические сценарии

### Диагностика состояния

```bash
# Проверка текущего диапазона эфемерных портов
sysctl net.ipv4.ip_local_port_range

# Подсчёт количества сокетов в TIME_WAIT
ss -tan state time-wait | wc -l

# Сводная статистика по всем типам сокетов
ss -s
```

### Тюнинг параметров через sysctl

**Рекомендуемые настройки для Highload:**

```bash
# Разрешить безопасное повторное использование портов
sudo sysctl -w net.ipv4.tcp_tw_reuse=1

# Расширить диапазон доступных портов
sudo sysctl -w net.ipv4.ip_local_port_range="1024 65535"

# Уменьшить время ожидания в FIN-WAIT-2
sudo sysctl -w net.ipv4.tcp_fin_timeout=15
```

**Сохранение настроек в `/etc/sysctl.d/99-network.conf`:**

```ini
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 15
net.ipv4.ip_local_port_range = 1024 65535
```

Применить изменения: `sudo sysctl --system`

### Выбор стратегии настройки

| Сценарий | Настройка | Обоснование |
| :--- | :--- | :--- |
| **Микросервисы / API** | `tcp_tw_reuse = 1` | Позволяет инициировать новые запросы без ожидания 60 сек. |
| **Балансировщик (Nginx)** | `ip_local_port_range` | Увеличение количества портов для соединений с бэкендами. |
| **Веб-сервер (входящие)** | По умолчанию | Не требует тюнинга `TIME_WAIT`, так как он ложится на клиентов. |
