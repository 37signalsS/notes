# Алгоритмы управления перегрузкой TCP в Linux

Данное руководство фокусируется на практической настройке и выборе алгоритмов в ядре Linux. Теоретические основы, формулы и детальное сравнение логики работы алгоритмов доступны в справочнике: **[Алгоритмы управления перегрузкой TCP (Теория)](../../../../Networking/Protocols/TCP/congestion/tcp_congestion_algorithms.md)**.

## Определения

* **Алгоритм управления перегрузкой (Congestion Control Algorithm)** — программный модуль ядра Linux, регулирующий размер окна перегрузки (`cwnd`) и скорость отправки пакетов на основе сигналов обратной связи от сети.
* **Loss-based алгоритмы (CUBIC, Reno)** — реагируют на потерю пакетов (Duplicate ACK или таймауты) как на единственный признак перегрузки.
* **Model-based алгоритмы (BBR)** — строят математическую модель канала на основе измерения минимального RTT и максимальной пропускной способности, минимизируя очереди.
* **BBRv3** — третья итерация алгоритма Google (стандарт 2026 года), значительно улучшившая сосуществование («справедливость») с классическими алгоритмами и стабильность на 400G+ линках.

## Основные концепции

### Зависимость от дисциплины очередей (qdisc)

Эффективность алгоритма напрямую зависит от того, как пакеты выходят в сеть.
*   **BBR требует `fq`**: Алгоритм BBR полагается на механизм **EDT (Earliest Departure Time)**, который реализован в дисциплине `fq`. Использование BBR с `fq_codel` или `pfifo_fast` крайне неэффективно и может привести к потерям.
*   **CUBIC универсален**: Хорошо работает с `fq_codel` и `cake`, эффективно борясь с bufferbloat.

Подробнее: [Дисциплины очередей TCP](./tcp_queueing_disciplines.md).

### Управление доступными алгоритмами

В ядре может быть загружено несколько модулей, но не все они могут быть разрешены для использования непривилегированными процессами.
*   `net.ipv4.tcp_available_congestion_control` — все загруженные модули.
*   `net.ipv4.tcp_allowed_congestion_control` — модули, которые разрешено выбирать приложениям.
*   `net.ipv4.tcp_congestion_control` — алгоритм по умолчанию для новых соединений.

## Практические сценарии

### 1. Проверка текущих возможностей ядра

```bash
# Список доступных в данный момент алгоритмов
sysctl net.ipv4.tcp_available_congestion_control

# Проверка, какие алгоритмы разрешены для выбора
sysctl net.ipv4.tcp_allowed_congestion_control

# Просмотр алгоритма для конкретных сокетов
ss -tin | grep 'cong:'
```

### 2. Включение BBRv3 (Рекомендуется для 2026)

Для современных ядер (6.x+) BBRv3 является оптимальным выбором для большинства серверных нагрузок.

**Постоянная настройка:**
```ini
# /etc/sysctl.d/99-network-bbr.conf

# 1. Обязательная дисциплина очереди для BBR
net.core.default_qdisc = fq

# 2. Установка BBR по умолчанию
net.ipv4.tcp_congestion_control = bbr

# 3. Рекомендуется включить ECN для BBRv2/v3
net.ipv4.tcp_ecn = 1
```

Применить: `sudo sysctl -p /etc/sysctl.d/99-network-bbr.conf`

### 3. Смена алгоритма для конкретного маршрута

Можно использовать разные алгоритмы для разных направлений (например, BBR для интернета и CUBIC для локальной сети):

```bash
# Установка алгоритма CUBIC только для конкретной подсети
sudo ip route add 10.0.0.0/24 via 192.168.1.1 congctl cubic
```

### 4. Динамическая загрузка модулей

Если нужного алгоритма нет в списке `available`, его можно загрузить как модуль ядра:

```bash
# Загрузка модуля (например, dctcp или westwood)
sudo modprobe tcp_dctcp

# После этого он появится в tcp_available_congestion_control
```

## Дополнительная информация

### Рекомендации по выбору (2026)

| Сценарий | Алгоритм | Примечание |
| :--- | :--- | :--- |
| **Публичные веб-серверы / API** | **BBR (v3)** | Максимальная скорость при наличии сетевых потерь. |
| **Внутренние сети ЦОД (Low Latency)** | **DCTCP** | Требует поддержки ECN на коммутаторах. |
| **Универсальный сервер (стабильность)** | **CUBIC** | Проверен временем, предсказуем в любых условиях. |
| **Спутниковые линки / Большой RTT** | **BBR** | Единственный способ «прокачать» толстые каналы с высоким пингом. |

> **Актуальность:** 2026 год (Ядра 6.x+, BBRv3).
