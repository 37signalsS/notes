# RSS, RPS, RFS: Многопоточная обработка сетевого трафика

## Определения

*   **RSS (Receive Side Scaling)** — аппаратная технология, реализованная в сетевых картах (NIC), которая распределяет входящие сетевые пакеты по нескольким очередям приема (RX queues), привязанным к разным ядрам CPU.
*   **RPS (Receive Packet Steering)** — программная технология в ядре Linux, которая выполняет ту же функцию, что и RSS, но на уровне ПО. Она позволяет распределять пакеты между CPU уже после того, как они были получены сетевой картой.
*   **RFS (Receive Flow Steering)** — программное расширение RPS, которое направляет пакеты одного и того же сетевого потока (flow) на то ядро CPU, где работает приложение, обрабатывающее этот поток. Это повышает локальность кэша.

## Основные концепции

### Проблема одного ядра

На высокоскоростных сетевых интерфейсах (10 Гбит/с и выше) обработка прерываний (IRQ) от сетевой карты на одном ядре CPU становится "узким местом". Это приводит к неравномерному распределению нагрузки, увеличению задержек и потерям пакетов, поскольку одно ядро не справляется с потоком данных.

### Принципы работы

Цель всех трех технологий — распределить обработку входящих пакетов по нескольким ядрам CPU для параллельной обработки.

*   **RSS (аппаратный уровень):**
    1.  Сетевая карта вычисляет хеш от полей пакета (обычно 4-tuple: IP источника/назначения, порт источника/назначения).
    2.  На основе хеша пакет помещается в одну из нескольких RX-очередей.
    3.  Каждая RX-очередь привязана к своему ядру CPU, которое и обрабатывает прерывание.

*   **RPS (программный уровень):**
    1.  Пакет принимается сетевой картой (в одну очередь).
    2.  Ядро Linux вычисляет хеш (аналогично RSS) и решает, какому CPU передать пакет для дальнейшей обработки.
    3.  RPS не требует специальной поддержки от сетевой карты и работает на любом оборудовании.

*   **RFS (улучшение RPS):**
    1.  Когда приложение выполняет системный вызов (например, `recv()`) на сокете, ядро запоминает, на каком CPU это произошло.
    2.  При поступлении новых пакетов для этого сокета RFS направит их на то же самое ядро.
    3.  Это значительно увеличивает вероятность попадания в кэш CPU (`cache hit rate`), так как данные приложения и сетевые данные находятся на одном ядре.

### NUMA-оптимизация

В системах с архитектурой NUMA (Non-Uniform Memory Access) важно, чтобы сетевая карта, ядро CPU, обрабатывающее ее прерывания, и само приложение находились на одной NUMA-ноде. Это минимизирует задержки доступа к памяти.
*   Прерывания (IRQ) от NIC должны обрабатываться CPU на той же NUMA-ноде, где установлена карта.
*   Приложение, работающее с сетью, должно быть привязано к ядрам той же NUMA-ноды с помощью утилит вроде `numactl`.

## Практические сценарии

### Диагностика и мониторинг

```bash
# Проверка текущего количества и лимитов RX/TX очередей
ethtool -l eth0

# Проверка загрузки CPU по ядрам (найти перегруженное ядро)
mpstat -P ALL 1

# Мониторинг программных прерываний (softirq)
watch -n 1 'cat /proc/softirqs'

# Просмотр статистики по прерываниям для поиска IRQ сетевой карты
cat /proc/interrupts | grep eth0
```

### Настройка RSS

Если сетевая карта поддерживает RSS, это предпочтительный вариант.

```bash
# Установить количество комбинированных очередей (включает RSS)
# Значение не должно превышать максимум, который показывает `ethtool -l`
sudo ethtool -L eth0 combined 8
```

### Настройка RPS

Используется, если нет аппаратной поддержки RSS или для дополнительной балансировки.

```bash
# Пример: для очереди rx-0 разрешить обработку на CPU 0-3 (маска 0-3 = 1+2+4+8 = 15 = 'f' в hex)
echo f > /sys/class/net/eth0/queues/rx-0/rps_cpus

# Пример: для очереди rx-1 разрешить обработку на CPU 4-7 (маска 4-7 = 16+32+64+128 = 240 = 'f0' в hex)
echo f0 > /sys/class/net/eth0/queues/rx-1/rps_cpus

# Рекомендация: не назначайте RPS на те же CPU, что обрабатывают аппаратные прерывания.
```

### Настройка RFS

Для максимальной производительности RFS следует включать вместе с RPS.

```bash
# Установить глобальный размер таблицы для отслеживания потоков
echo 32768 > /proc/sys/net/core/rps_sock_flow_entries

# Установить размер таблицы для конкретной RX-очереди
# Значение должно быть `rps_sock_flow_entries / <число_rx_очередей>`
echo 4096 > /sys/class/net/eth0/queues/rx-0/rps_flow_cnt
```

### Привязка прерываний (IRQ Affinity)

Для NUMA-оптимизации или ручного распределения прерываний.

```bash
# Узнать номер прерывания для очереди (например, eth0-rx-0)
IRQ_NUM=$(cat /proc/interrupts | grep 'eth0-rx-0' | awk '{print $1}' | tr -d ':')

# Привязать прерывание к CPU 0 (маска '1')
echo 1 > /proc/irq/$IRQ_NUM/smp_affinity

# Привязать к CPU 0-3 (маска 'f')
echo f > /proc/irq/$IRQ_NUM/smp_affinity
```

## Дополнительная информация

### Типичные проблемы и решения

*   **Перегрузка одного CPU при высоком трафике:** Проверьте, включен ли RSS через [`ethtool -l`](../../Tools/ethtool.md#управление-многопоточной-обработкой-rss). Если нет, настройте очереди через [`ethtool -L`](../../Tools/ethtool.md#управление-многопоточной-обработкой-rss). Если RSS не поддерживается, включите RPS.
*   **Высокий `cache miss rate` у сетевых приложений:** Включите RFS, чтобы данные приложения и сетевые пакеты обрабатывались на одном ядре.
*   **Задержки при доступе между NUMA-нодами:** Убедитесь, что прерывания от сетевой карты и приложение, работающее с сетью, привязаны к одной NUMA-ноде.
