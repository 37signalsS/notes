# RSS, RPS, RFS: Многопоточная обработка сетевого трафика

## Определения

* **RSS (Receive Side Scaling)** — аппаратная технология распределения входящих пакетов по нескольким очередям и CPU
* **RPS (Receive Packet Steering)** — программная балансировка обработки входящих пакетов между ядрами процессора
* **RFS (Receive Flow Steering)** — расширение RPS, направляющее пакеты конкретного потока на тот же CPU, где работает приложение

## Базовые концепции

### Проблема

На высокоскоростных сетевых интерфейсах (10 Гбит/с и выше) один CPU может стать узким местом при обработке прерываний. Это вызывает:
* Потерю пакетов
* Увеличение задержек
* Неравномерное распределение нагрузки

### Решение

Распределение обработки пакетов по нескольким ядрам CPU для параллельной обработки.

## RSS (Receive Side Scaling)

### Принцип работы

* Аппаратная функция сетевой карты
* Использует хеш от 4-tuple (src IP, dst IP, src port, dst port)
* Распределяет пакеты по нескольким RX-очередям
* Каждая очередь обрабатывается отдельным CPU

### Требования

* Поддержка со стороны сетевой карты
* Поддержка драйвером
* Достаточное количество RX-очередей

### Настройка

```bash
# Проверка количества RX/TX очередей
ethtool -l eth0

# Установка количества комбинированных очередей
ethtool -L eth0 combined 8
```

## RPS (Receive Packet Steering)

### Принцип работы

* Программная реализация (не требует поддержки NIC)
* После приёма пакета ядро распределяет его по CPU
* Использует ту же хеш-функцию, что и RSS

### Настройка

```bash
# Маска CPU для RPS (шестнадцатеричная)
# f = 1111 (CPU 0-3)
# ff = 11111111 (CPU 0-7)

# Для очереди rx-0 разрешаем обработку на CPU 0-3
echo f > /sys/class/net/eth0/queues/rx-0/rps_cpus

# Для очереди rx-1 разрешаем обработку на CPU 4-7
echo f0 > /sys/class/net/eth0/queues/rx-1/rps_cpus
```

### Выбор CPU

* Не назначайте RPS на CPU, обрабатывающие прерывания (IRQ)
* Используйте соседние NUMA-ноды для снижения задержек

## RFS (Receive Flow Steering)

### Премущества

* Направляет весь поток на тот же CPU, где работает приложение
* Увеличивает cache hit rate
* Снижает межпроцессорные прерывания (IPI)

### Настройка

```bash
# Глобальный размер flow table
echo 32768 > /proc/sys/net/core/rps_sock_flow_entries

# Размер flow table для конкретной очереди
echo 4096 > /sys/class/net/eth0/queues/rx-0/rps_flow_cnt
```

### Как работает

1. Приложение вызывает `recv()` на сокете
2. Ядро запоминает, какой CPU обрабатывает сокет
3. Последующие пакеты этого потока направляются на тот же CPU

## NUMA-оптимизация

### Принципы

* Обработка IRQ должна быть на NUMA-ноде, близкой к NIC
* Приложение должно работать на том же NUMA-узле
* Используйте `numactl` для привязки процессов

### Настройка affinity

```bash
# Привязка прерываний NIC к конкретным CPU
cat /proc/interrupts | grep eth0

# Изменение affinity (пример: CPU 0-3)
echo 0f > /proc/irq/<IRQ_NUMBER>/smp_affinity
```

## Практические рекомендации

### Сценарий 1: Высокая нагрузка на один CPU

```bash
# Проверка загрузки CPU
mpstat -P ALL 1

# Если softirq загружен на одном CPU, включите RPS
echo f > /sys/class/net/eth0/queues/rx-0/rps_cpus
```

### Сценарий 2: Много коротких соединений

```bash
# Включите RFS для лучшей локальности
echo 32768 > /proc/sys/net/core/rps_sock_flow_entries
echo 4096 > /sys/class/net/eth0/queues/rx-*/rps_flow_cnt
```

### Сценарий 3: NIC с поддержкой RSS

```bash
# Используйте аппаратный RSS вместо программного RPS
ethtool -L eth0 combined 8

# Отключите RPS, так как RSS уже распределяет нагрузку
echo 0 > /sys/class/net/eth0/queues/rx-*/rps_cpus
```

## Мониторинг

```bash
# Статистика RPS/RFS
cat /proc/net/rps_sock_flow_table

# Загрузка CPU по прерываниям
mpstat -I SUM -P ALL 1

# Статистика softirq
watch -n 1 'cat /proc/softirqs'
```

## Типичные проблемы

* **Перегрузка одного CPU** — увеличьте количество очередей или включите RPS
* **Высокий cache miss rate** — включите RFS
* **Задержки при меж-NUMA доступе** — привяжите приложение и IRQ к одной NUMA-ноде
