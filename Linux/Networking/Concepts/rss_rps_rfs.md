# Многопоточная обработка сетевого трафика в Linux: RSS, RPS, RFS, XPS

## Определения

**RSS (Receive Side Scaling — масштабирование на стороне приема)** — аппаратная технология сетевых карт (NIC), распределяющая входящие пакеты по нескольким RX-очередям. Каждая очередь генерирует свое прерывание (MSI-X), позволяя параллельно обрабатывать трафик на разных ядрах CPU.

**RPS (Receive Packet Steering — программное управление приемом)** — программная реализация RSS в ядре Linux. Используется, когда NIC имеет одну очередь или когда требуется распределить нагрузку на большее количество ядер, чем позволяет аппаратная часть.

**RFS (Receive Flow Steering — программное управление потоками)** — расширение RPS, которое направляет обработку пакета на то ядро CPU, где выполняется приложение-получатель. Это максимизирует попадание в кэш процессора (CPU Cache Locality).

**aRFS (Accelerated RFS)** — аппаратное ускорение RFS, при котором ядро передает информацию о потоках в NIC (через Flow Director), позволяя карте направлять пакеты в нужную RX-очередь аппаратно.

**XPS (Transmit Packet Steering — программное управление передачей)** — механизм выбора TX-очереди для исходящего трафика на основе ID текущего CPU. Предотвращает конкуренцию за блокировки (locks) между ядрами и снижает накладные расходы на переключение контекста.

**NAPI (New API)** — механизм ядра для обработки пакетов методом опроса (polling) вместо прерываний при высокой нагрузке. RSS и RPS работают внутри контекста NAPI. Подробнее о лимитах обработки см. [**Оптимизация NAPI и netdev_budget**](./napi_optimization.md).

## Основные концепции

### Масштабирование и Bottlenecks

В современных сетях (10/40/100 GbE) одно ядро CPU не способно обработать весь входящий трафик (лимит ~1.5–3 Mpps на ядро). Без многопоточности система сталкивается с:
*   **High SoftIRQ:** Ядро, обрабатывающее прерывания, загружено на 100%, что приводит к потере пакетов (drop) в очередях драйвера.
*   **Context Switching:** Постоянные прерывания мешают работе прикладного ПО.
*   **Packet Reordering:** Неправильная настройка RPS/RSS может привести к нарушению порядка пакетов в TCP-потоке, что вызывает срабатывание механизмов Fast Retransmit и падение скорости.

### Архитектурные уровни распределения

1.  **L1 (Hardware - RSS):** Распределение на уровне NIC на основе хеша 4-tuple (SrcIP, DstIP, SrcPort, DstPort).
2.  **L2 (Driver/Kernel - RPS):** Если RSS недостаточно, ядро распределяет пакеты после их получения из драйвера, используя IPI (Inter-Processor Interrupts).
3.  **L3 (NUMA/Cache - RFS):** Оптимизация на основе того, какое ядро владеет сокетом приложения.

### Взаимодействие с NUMA-архитектурой

Для систем с несколькими процессорами (NUMA) критически важно:
*   Привязывать прерывания NIC к ядрам той же NUMA-ноды, к которой подключена шина PCIe этой карты.
*   Обращение к памяти через QPI/UPI шину между сокетами увеличивает задержки на 50–200%.

## Практические сценарии

### 1. Глубокая диагностика SoftIRQ

Мониторинг того, как распределяется нагрузка между ядрами:

```bash
# Просмотр статистики мягких прерываний (ищите перекосы в NET_RX)
watch -n 1 "cat /proc/softirqs | grep NET_RX"

# Анализ переполнения очередей backlog и исчерпания бюджета
cat /proc/net/softnet_stat
# → 000a1234 00000005 00000010 ... 
# (5 пакетов отброшено, 16 раз не хватило netdev_budget)
```

### 2. Ручная привязка IRQ Affinity

Автоматический `irqbalance` часто работает некорректно на High Load. Ручная привязка обеспечивает стабильность:

```bash
# 1. Найти IRQ очереди сетевой карты
cat /proc/interrupts | grep -E "eth0-rx|eth0-combined"
# →  45: ... eth0-rx-0

# 2. Привязать к конкретному ядру (например, ядро 2, маска 4)
# Маска: 1=0, 2=1, 4=2, 8=3 ...
echo 4 | sudo tee /proc/irq/45/smp_affinity
```

### 3. Скрипт настройки RPS/XPS для всех ядер

Пример включения RPS на всех ядрах для интерфейса `eth0`:

```bash
#!/bin/bash
# Маска для 8 ядер (ff)
mask="ff"
for file in /sys/class/net/eth0/queues/rx-*/rps_cpus; do
    echo $mask > $file
done

for file in /sys/class/net/eth0/queues/tx-*/xps_cpus; do
    echo $mask > $file
done
```

### 4. Тюнинг RFS для минимизации задержек

RFS требует включения глобальной таблицы потоков и настройки для каждой очереди:

```bash
# Глобальный размер таблицы (рекомендуется 32768+)
sudo sysctl -w net.core.rps_sock_flow_entries=32768

# Настройка для конкретной RX-очереди
echo 4096 | sudo tee /sys/class/net/eth0/queues/rx-0/rps_flow_cnt
```

## Дополнительная информация

### Сравнение механизмов

| Механизм | Плюсы | Минусы |
| :--- | :--- | :--- |
| **RSS** | Нулевая нагрузка на CPU, минимальная задержка | Ограничено количеством очередей в железе |
| **RPS** | Работает на любом железе, гибкость | Накладные расходы на IPI и CPU хеширование |
| **RFS** | Лучшая локальность кэша, минимум Latency | Сложность настройки, CPU overhead |
| **XPS** | Исключает локи в TX-пути, повышает Throughput | Требует ручной привязки к топологии CPU |
