# Network Offloading: GRO/LRO/TSO

## Определения

**Offloading** — технология переноса части задач по обработке сетевых пакетов с центрального процессора (CPU) на специализированное аппаратное обеспечение сетевой карты (NIC) или на уровень ядра для оптимизации производительности.

**GRO (Generic Receive Offload)** — механизм в ядре Linux, который агрегирует несколько входящих пакетов, принадлежащих одному потоку, в один крупный "суперпакет" (SKB, `sk_buff`) перед передачей в сетевой стек. Программная реализация на уровне драйвера.

**LRO (Large Receive Offload)** — более старая технология, выполняющая аналогичную функцию аппаратно на сетевой карте. Может нарушать TCP-семантику, объединяя пакеты с разными заголовками.

**TSO (TCP Segmentation Offload)** — механизм разделения крупных TCP-пакетов на более мелкие сегменты аппаратно на NIC перед отправкой в сеть.

**UFO (UDP Fragmentation Offload)** — аналог TSO для UDP-трафика.

**GSO (Generic Segmentation Offload)** — программный аналог TSO на уровне ядра. Выполняет сегментацию пакетов непосредственно перед передачей драйверу NIC. Если драйвер поддерживает TSO, GSO делегирует ему задачу; если нет — сегментирует программно.

**Checksum Offloading** — вычисление контрольных сумм пакетов переносится с CPU на NIC.

## Базовые концепции

### Принцип работы

1. Сетевая карта получает пакеты из сети
2. Драйвер NIC (для GRO) или сама карта (для LRO) анализирует пакеты
3. Если пакеты принадлежат одному соединению (source/destination IP/port), они объединяются
4. Объединённый пакет передаётся сетевому стеку Linux как единое целое

### Типы offloading

| Тип | Направление | Уровень | Описание |
|-----|-------------|---------|----------|
| **GRO** | RX (входящий) | Ядро/драйвер | Агрегация пакетов перед стеком |
| **LRO** | RX (входящий) | Аппаратный | Агрегация на NIC |
| **TSO** | TX (исходящий) | Аппаратный | Сегментация больших TCP-пакетов |
| **GSO** | TX (исходящий) | Ядро | Программная сегментация (fallback для TSO) |
| **UFO** | TX (исходящий) | Аппаратный | Фрагментация UDP |
| **Checksum** | RX/TX | Аппаратный | Вычисление контрольных сумм |
| **VLAN** | RX/TX | Аппаратный | Обработка VLAN-тегов |

## Практические сценарии

### Проверка статуса offloading

```bash
# Проверка всех параметров offloading для интерфейса
sudo ethtool -k eth0

# Краткий вывод только активных параметров
sudo ethtool -k eth0 | grep "on"
```

**Пример вывода:**

```
Features for eth0:
rx-checksumming: on
tx-checksumming: on
scatter-gather: on
tcp-segmentation-offload: on
generic-receive-offloading: on
large-receive-offloading: off [fixed]
```

### Включение/отключение offloading

```bash
# Отключить GRO для снижения задержек (критичные по latency приложения)
sudo ethtool -K eth0 gro off

# Отключить LRO (если поддерживается)
sudo ethtool -K eth0 lro off

# Отключить TSO (для отладки или специфичных сценариев)
sudo ethtool -K eth0 tso off

# Включить обратно
sudo ethtool -K eth0 gro on
sudo ethtool -K eth0 tso on
```

> **Важно:** Настройки сбрасываются после перезагрузки. Для постоянного применения используйте конфигурацию сети дистрибутива или udev-правила.

### Сценарий: Оптимизация для низкой латентности

Для приложений реального времени (High-Frequency Trading, онлайн-игры, VoIP):

```bash
# Отключить GRO/LRO для минимизации задержек
sudo ethtool -K eth0 gro off lro off

# Отключить TSO для предсказуемой отправки пакетов
sudo ethtool -K eth0 tso off

# Проверить изменения
ethtool -k eth0 | grep -E "gro|lro|tso"
```

**Результат:** Уменьшение задержек на 10-50 мкс за счёт потери пропускной способности.

### Сценарий: Оптимизация для высокой пропускной способности

Для файловых серверов, CDN, backup-систем:

```bash
# Включить все доступные offloading
sudo ethtool -K eth0 gro on lro on tso on gso on

# Увеличить кольцевые буферы для обработки крупных пакетов
sudo ethtool -G eth0 rx 4096 tx 4096
```

**Результат:** Увеличение пропускной способности на 20-40% при высокой нагрузке.

### Диагностика проблем

**Симптом:** Высокая задержка или потери пакетов при нормальной загрузке CPU.

```bash
# 1. Проверить статистику ошибок на NIC
sudo ethtool -S eth0 | grep -E 'drop|error|overrun'

# 2. Проверить загрузку CPU по ядрам
mpstat -P ALL 1

# 3. Проверить, не отключены ли offloading нечаянно
ethtool -k eth0 | grep "off \[fixed\]"
```

**Возможные причины:**

- Offloading отключен на одном конце соединения
- Драйвер NIC не поддерживает нужные функции
- Аппаратные ограничения сетевой карты

### Постоянное применение настроек

**Debian/Ubuntu** (`/etc/network/interfaces`):

```
auto eth0
iface eth0 inet dhcp
    post-up /sbin/ethtool -K $IFACE gro off lro off
```

**RHEL/CentOS** (`/etc/sysconfig/network-scripts/ifcfg-eth0`):

```
ETHTOOL_OPTS="-K eth0 gro off lro off"
```

**systemd-networkd** (`/etc/systemd/network/10-eth.network`):

```ini
[Match]
Name=eth0

[Link]
TCPOffloading=yes
GenericReceiveOffload=no
```

## Дополнительная информация

### Преимущества и недостатки

| Преимущества | Недостатки |
|-------------|------------|
| **Снижение нагрузки на CPU** за счёт меньшего числа прерываний | **Скрытая нагрузка на одно ядро CPU**: агрегированные пакеты обрабатываются ядром, обслуживающим очередь RX — при отсутствии RSS/RPS вся нагрузка концентрируется на одном ядре, вызывая latency spikes |
| **Увеличение пропускной способности (throughput)** на 20-40% | **Увеличение задержек (latency)**: время на агрегацию пакетов добавляет 10-50 мкс |
| **Снижение per-packet overhead** | **Проблемы с маршрутизацией**: LRO может нарушать TCP-семантику |
| **Экономия энергии** на мобильных устройствах | **Сложность отладки**: пакеты в объединённом виде труднее анализировать |

### Взаимосвязь с другими технологиями

Offloading дополняет [балансировку по CPU — RSS, RPS, RFS](./rss_rps_rfs.md): без распределения прерываний вся работа от offloading концентрируется на одном ядре. В комплексе с [оптимизацией TCP](./tcp_tuning/tcp_tuning_overview.md) и [управлением трафиком через tc](../Tools/iproute2/tc.md) обеспечивает комплексную настройку сетевого стека. Управление параметрами — через [ethtool](../Tools/ethtool.md).

### Скрытая нагрузка от GRO/LRO

GRO и LRO агрегируют входящие пакеты в один крупный буфер, который обрабатывается ядром, обслуживающим очередь RX NIC. Без RSS/RPS вся нагрузка концентрируется на одном ядре, что даёт **latency spikes** при burst-трафике, хотя средняя загрузка системы остаётся низкой.

**Диагностика:**

```bash
# Проверить, включены ли GRO/LRO
ethtool -k eth0 | grep 'generic-receive-offload\|large-receive-offload'

# Проверить распределение softirq по ядрам
cat /proc/softirqs | grep NET_RX
```

Если счётчики `NET_RX` растут преимущественно на одном CPU — нагрузка не распределяется. Решение — включить RSS (аппаратно) или RPS (программно). Подробнее: [RSS, RPS, RFS](./rss_rps_rfs.md).

### Когда отключать offloading

| Сценарий | Рекомендуемые действия |
|----------|----------------------|
| **Отладка сетевых проблем** | Отключить GRO/LRO/TSO для "чистого" анализа трафика |
| **Приложения реального времени** | Отключить GRO/LRO для минимизации latency |
| **Виртуальные машины** | Проверить совместимость с гипервизором (может требовать отключения) |
| **Анализ трафика (IDS/IPS)** | Отключить для корректной инспекции пакетов |
| **Контейнеры с veth** | Может требовать отключения на хосте для корректной работы |
