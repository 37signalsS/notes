# Диагностика и информация о CPU

## Определения

**`/proc/cpuinfo`** — виртуальный файл в системе `/proc`, предоставляющий детальную информацию от ядра о каждом логическом процессорном ядре (частота, кэш, флаги инструкций, известные уязвимости).

**`lscpu`** — утилита, агрегирующая данные из `/proc/cpuinfo` и `/sys` для представления архитектуры CPU и топологии системы (сокеты, ядра, потоки) в удобном человекочитаемом формате. Поддерживает структурированный вывод в JSON (`-J`).

**`dmidecode`** — инструмент для чтения таблиц DMI (SMBIOS), позволяющий получить низкоуровневые аппаратные спецификации напрямую из BIOS/UEFI (модель, серийные номера, физические характеристики разъемов).

**`cpuid`** — специализированная утилита для дампинга подробной информации о функциях процессора, полученной напрямую через инструкцию CPUID (преимущественно для x86 архитектур).

**`hwinfo --cpu`** — комплексная утилита для инвентаризации, предоставляющая детальный технический отчет о процессоре, включая ревизии и специфические идентификаторы.

**`turbostat`** — утилита (из пакета `linux-cpupower`), отображающая реальную частоту ядер (включая Turbo Boost), энергопотребление (RAPL) и C-states в реальном времени.

**`cpupower`** — набор инструментов для управления параметрами энергопотребления процессора, частотными лимитами и профилями производительности (governors).

**`nproc`** — простая утилита для вывода количества доступных вычислительных юнитов (ядер/потоков), используемая преимущественно в скриптах.

**`mpstat`** — утилита из пакета `sysstat`, выводящая статистику по каждому логическому процессору отдельно (`%usr`, `%sys`, `%iowait`, `%irq`, `%soft`, `%steal`, `%idle`).

**`pidstat`** — утилита из пакета `sysstat` для мониторинга утилизации CPU на уровне отдельных процессов и потоков (PID/TID), включая время в user/kernel space.

**`lstopo`** / **`hwloc`** — инструменты для визуализации топологии CPU и NUMA в текстовом или графическом виде (из пакета `hwloc`), выявляющие расположение ядер, кэшей и узлов памяти.

## Базовые концепции

### Источники данных и их различия

| Источник | Уровень данных | Основное назначение |
| :--- | :--- | :--- |
| **Ядро (`lscpu`, `/proc/cpuinfo`)** | Операционный | Информация о том, как ОС видит и использует процессор. |
| **BIOS (`dmidecode`)** | Аппаратный | Информация о физическом железе, сокетах и спецификациях производителя. |
| **Sysfs (`/sys/devices/...`)** | Реальное время | Текущее состояние (частота, лимиты, температура, уязвимости). |

### Топология и современные архитектуры

Понимание иерархии ресурсов критично для оптимизации производительности (CPU pinning) и настройки виртуализации:

- **Socket (Сокет):** Физический разъем на материнской плате.
- **Core (Ядро):** Независимый вычислительный блок.
- **Hybrid Architecture (Гибридные архитектуры):**
    - **Intel (Performance/Efficient):** **P-cores** (производительные) и **E-cores** (энергоэффективные).
    - **ARM (big.LITTLE):** Кластеры мощных («big») и простых («LITTLE») ядер для экономии энергии.
- **Thread (Поток/Логическое ядро):** Логический юнит (Hyper-Threading/SMT), делящий ресурсы физического ядра.
- **NUMA (Non-Uniform Memory Access):** Архитектура, где память привязана к конкретным сокетам/чиплетам. Доступ к «своей» памяти быстрее.
- **Cache Hierarchy (Иерархия кэша):** Многоуровневая структура кэшей процессора. **L1d** (данные, ~32–64 КБ на ядро) и **L1i** (инструкции, ~32–64 КБ) — самые быстрые, но маленькие. **L2** (256 КБ – 2 МБ на ядро) — промежуточный уровень. **L3/LLC** (Last Level Cache, разделяемый, 16–128 МБ+) — последний уровень перед обращением к DRAM. При промахе кэша (cache miss) задержка может возрасти на 50–200 нс (DRAM) или 10–100 мкс (SSD).
- **CCD (Core Complex Die):** В чиплетных процессорах (AMD EPYC, Intel Xeon) группа ядер с разделяемым L3. Два CCD на одном сокете образуют внутренний NUMA-узел.

### Состояния и флаги процессора

**C-states (Idle States):** Состояния энергосбережения при простое. Чем глубже состояние, тем больше энергия экономится, но тем выше задержка выхода.
- **C0:** Активное выполнение (ядро работает).
- **C1 (Halt):** Ядро останавливается, но может возобновить работу за несколько тактов.
- **C6 (Deep Sleep):** Питание отключено, кэш сохраняется в выделенном SRAM. Восстановление занимает 50–200 мкс. Современные процессоры проводят 90–99% времени в C-states при низкой нагрузке.

**P-states (Performance States):** Уровни напряжения/частоты при активной работе. Управляются драйвером `intel_pstate` или `cpufreq`. Переходы между P-states добавляют недетерминизм (латентность 10–100 мкс), что критично для latency-sensitive нагрузок.

**Флаги инструкций (Instruction Set Flags):** Наборы расширений архитектуры x86/ARM64. Ключевые группы:
- **SIMD:** `sse`, `sse2`, `sse4_2`, `avx`, `avx2`, `avx-512` (векторизация данных).
- **Криптография:** `aes`, `vaes`, `pclmulqdq` (ускорение шифрования).
- **Виртуализация:** `vmx` (Intel VT-x), `svm` (AMD-V).
- **Управление памятью:** `smep`, `smap` (защита от переполнения буфера).

**CPU Steal Time (%st):** Показатель времени, в течение которого виртуальный CPU был готов к выполнению, но гипервизор не выделил ему физического времени. **Высокий steal (>10%) указывает на «шумного соседа» (Noisy Neighbor) или oversubscription на хосте.** В контейнеризированных средах (LXC/Docker) steal time учитывается через cgroup-accounting.

### Виртуализация и CPU

В виртуальных средах информация о CPU отражает настройки гипервизора:

- Без включенной **Nested Virtualization** гостевая ОС не увидит флаги аппаратного ускорения (`vmx` для Intel, `svm` для AMD). На ARM64 наличие поддержки проверяется флагом `virt`.
- Модель процессора может отображаться как эмулированная (например, "Common KVM processor").

Подробнее см. [Обзор виртуализации](../../Virtualization/virtualization_overview.md).

## Практические сценарии

### Идентификация архитектуры и топологии (`lscpu`)

```bash
# Общая сводка по архитектуре и ресурсам
lscpu

# Вывод в формате JSON для автоматизации
lscpu -J

# Проверка типов ядер (P-cores / E-cores) и кэша
lscpu -e

# Просмотр топологии кэша
lscpu -C

# Просмотр NUMA-узлов
lscpu -G
```

### Детальный анализ характеристик ядер (`/proc/cpuinfo`)

```bash
# Модель процессора и поддерживаемые инструкции (флаги)
grep -E "model name|flags" /proc/cpuinfo | head -n 2

# Сравнение ключевых флагов x86 vs ARM64
# x86: vmx, svm, aes, avx, sse4_2
# ARM: virt, fp, asimd, aes, crc32

# Проверка поддержки аппаратной виртуализации (x86)
grep -E "vmx|svm" /proc/cpuinfo

# Проверка поддержки виртуализации и SIMD на ARM64
lscpu | grep -iE "virt|asimd"

# Количество логических ядер (потоков)
grep -c "^processor" /proc/cpuinfo
```

### Низкоуровневая аппаратная информация

Требует прав `root`. Показывает физические данные, прошитые в BIOS.

```bash
# Детальная информация о физических процессорах
sudo dmidecode -t processor

# Технический отчет от hwinfo
hwinfo --cpu

# Просмотр версии микрокода (Microcode)
grep "microcode" /proc/cpuinfo | head -n 1
```

### Управление частотой и профилями (Scaling Governor)

Современные системы используют `intel_pstate`, `amd-pstate` или универсальные драйверы `cpufreq`.

```bash
# Текущий профиль (governor) для всех ядер
cat /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
# → performance (макс. частота) или powersave (энергосбережение)

# Получение подробной информации о частотах через cpupower
sudo cpupower frequency-info

# Реальный мониторинг частот, вольтажа и Turbo Boost (turbostat)
sudo turbostat --Interval 1
```

Подробнее о настройке профилей производительности см. [tuned](../../Core/tuned.md).

### Проверка уязвимостей CPU

Современный и надежный способ проверки состояния защиты от Spectre, Meltdown и др.

```bash
# Список всех уязвимостей и статус их исправления (mitigation)
grep . /sys/devices/system/cpu/vulnerabilities/*

# → /sys/devices/system/cpu/vulnerabilities/itlb_multihit:KVM: Mitigation: VMX unsupported
# → /sys/devices/system/cpu/vulnerabilities/l1tf:Mitigation: PTE Inversion
# → /sys/devices/system/cpu/vulnerabilities/meltdown:Mitigation: PTI
# → /sys/devices/system/cpu/vulnerabilities/spectre_v1:Mitigation: usercopy/swapgs barriers and __user pointer sanitization
```

### Диагностика перегрева и троттлинга

Троттлинг (снижение частоты) происходит при достижении критических температур.

```bash
# Мониторинг температуры ядер в реальном времени (пакет lm-sensors)
watch -n1 sensors

# Поиск сообщений о температурных событиях в журнале ядра
dmesg | grep -iE "thermal|throttl"
# → CPU0: Package temperature above threshold, cpu clock throttled

# Проверка лимитов температуры в sysfs
cat /sys/class/thermal/thermal_zone*/temp
```

### Мониторинг распределения нагрузки по ядрам (`mpstat`)

`mpstat` позволяет выявить дисбаланс нагрузки между ядрами (один overloaded, остальные idle).

```bash
# Статистика по всем ядрам, обновление каждую секунду, 10 итераций
mpstat -P ALL 1 10

# Вывод в процентах с заголовком
mpstat -P ALL -u 1 1

# Пример анализа:
# CPU    %usr   %nice   %sys   %iowait   %irq   %soft   %steal   %idle
# 0      45.20   0.00    2.10    0.00    0.00    0.00     0.00    52.70
# 1       2.30   0.00    1.50    0.00    0.00    0.00     0.00    96.20
# → Ядро 0 перегружено, ядро 1 простаивает — требуется настройка affinity или tuning.

# Фильтрация только пользовательского и системного времени
mpstat -P ALL 1 1 | awk 'NR>3 && $4+$6 > 80 {print $0}'
# → Автоматическое выявление перегруженных ядер для алертов.
```

### Учет CPU на уровне процессов (`pidstat`)

`pidstat` показывает, как процесс потребляет CPU с течением времени, включая время в user/kernel space.

```bash
# Мониторинг всех процессов с детализацией по потокам (-t)
pidstat -u -t 1 5

# Топ-5 процессов по среднему удельному CPU за интервал
pidstat -u 1 1 | sort -k4 -nr | head -n 6

# Отслеживание конкретного PID
pidstat -p <PID> -u 1 10

# Пример вывода:
#   UID       PID    %usr %system  %guest   %wait    %CPU   CPU  Command
#   0      12345   85.20    10.50    0.00    0.00    95.70     5  nginx: worker
# → Процесс 12345 потребляет 95.7% на ядре 5.
```

### Визуализация топологии (`lstopo` / `hwloc`)

Графическое или текстовое представление иерархии CPU, кэшей и NUMA-узлов.

```bash
# Текстовое представление топологии
lstopo no.txt

# Вывод в формате JSON (для автоматизации)
lstopo -of xml topology.xml

# Графическое представление (требует графическую среду или Cayley)
lstopo -of pdf cpu_topology.pdf

# Альтернатива: hwloc
hwloc-ls
hwloc-calc --cpulist package:0
# → Визуализация помогает понять, какие ядра разделяют L3 и на каких NUMA-узлах находятся.
```

### Расширенный анализ частот и энергопотребления (`turbostat`)

`turbostat` собирает данные о частотах, C-states и энергопотреблении (RAPL) с интервалом.

```bash
# Мониторинг всех ядер с интервалом 1 секунда
sudo turbostat --interval 1

# Ключевые столбцы:
# PkgWatt — потребление всего сокета (включая DRAM через RAPL)
# Core — частота ядра
# CPU%c1, CPU%c3, CPU%c6 — время в состояниях C0, C1, C3, C6
# Avg_MHz — реальная средняя частота (не nominal)

# Ограничение на конкретный сокет (для 2P систем)
sudo turbostat --socket 0 --interval 1

# Вывод в CSV для внешней обработки
sudo turbostat --interval 1 --csv > cpu_power.csv

# Пример анализа:
# PkgWatt = 85W, Avg_MHz = 2800, Turbo = Off
# → Процессор в базовой частоте. Если PkgWatt = 220W при той же нагрузке — включен Turbo Boost.
```

### Проверка и обновление микрокода (Microcode)

Микрокод (Microcode) — встроенный набор инструкций процессора, загружаемый ядром при загрузке. Обновления исправляют микропрограммные баги и уязвимости.

```bash
# Текущая версия микрокода из /proc/cpuinfo
grep -m1 "microcode" /proc/cpuinfo
# → microcode : 0x96000b13

# Проверка загруженной версии в рантайме
sudo dmesg | grep -i microcode
# → [    0.000000] microcode: microcode updated early to revision 0x96000b13, date = 2024-01-15

# Доступные версии в пакетах (Debian/Ubuntu)
grep microcode /var/log/dpkg.log | tail -n 5

# RHEL/CentOS
rpm -q microcode_ctl
```

### Анализ промахов кэша через `perf`

Связка `perf stat` позволяет количественно оценить эффективность кэш-памяти.

```bash
# Анализ промахов L1, L2, LLC (Last Level Cache) для команды
perf stat -e cache-references,cache-misses,L1-dcache-loads,L1-dcache-load-misses,LLC-loads,LLC-load-misses <команда>

# Вывод:
#      1,234,567 cache-reference
#        567,890 cache-misses          #    46.03% of all cache refs
#     12,345,678 L1-dcache-load
#      1,234,567 L1-dcache-load-misses #    10.00% of all L1-dcache hits
# → Высокий % cache-misses указывает на неоптимальный доступ к памяти (stride, NUMA).

# Мониторинг всей системы 10 секунд
sudo perf stat -e cache-references,cache-misses -a sleep 10
```
