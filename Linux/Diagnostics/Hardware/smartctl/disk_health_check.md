# Проверка здоровья дисков с помощью smartctl

## Определения

**Проверка здоровья дисков (Disk Health Check)** — комплексная процедура сбора, анализа и интерпретации данных S.M.A.R.T., журналов ошибок и результатов самотестирования для оценки текущего состояния накопителя. Основная цель — выявление признаков деградации (износ ячеек, ошибки поверхности, проблемы с интерфейсом) до наступления окончательного сбоя.

**Жизненный цикл проверки здоровья:**
1. **Базовый снимок (Baseline):** Фиксация исходных значений ключевых атрибутов при вводе диска в эксплуатацию.
2. **Регулярный мониторинг:** Опрос атрибутов по расписанию через `smartd` или скрипты.
3. **Глубокая диагностика:** Запуск самотестирования и анализ журналов при получении предупреждений.
4. **Корреляция:** Сопоставление данных SMART с логами ядра (`dmesg`) для исключения проблем с шиной.
5. **Принятие решения:** Плановая или срочная замена на основе динамики изменений.

## Базовые концепции

### Установка и подготовка

Инструментарий входит в состав пакета `smartmontools`. Для современных накопителей критически важно регулярно обновлять базу данных моделей.

```bash
# Установка (Ubuntu/Debian)
sudo apt update && sudo apt install smartmontools

# Установка (RHEL/Rocky/Alma)
sudo dnf install smartmontools

# Обновление базы данных накопителей (обязательно для новых NVMe)
sudo update-smart-drivedb
```

### Интерпретация общего статуса (Health Status)

| Статус | Значение | Действие |
| :--- | :--- | :--- |
| **`PASSED`** | Диск исправен, критические пороги не достигнуты. | Плановый мониторинг. |
| **`FAILED`** | Обнаружена неисправность, пороги превышены. | Замена диска в ближайшее время. |
| **`FAILURE IS IMMINENT`** | Прогнозируется немедленный выход из строя. | Срочное копирование данных и замена. |

> **Важно для автоматизации:** В скриптах всегда проверяйте exit code (`$?` в bash), а не только текстовый вывод. Например, `smartctl -H /dev/sda` может вернуть `PASSED` в тексте, но exit code `1` при наличии критических атрибутов.

### Диагностика SSD и NVMe (2026+)

В отличие от HDD, твердотельные накопители требуют фокуса на ресурсе записи и целостности данных:

- **SSD (SATA):** Основной показатель — `Wear_Leveling_Count` (процент оставшейся жизни).
- **NVMe 2.x:** Использует стандартизированный Health Log. Важнейшие метрики: `Percentage Used` (износ) и `Data Units Written`.
- **ZNS (Zoned Namespaces):** Требует контроля за количеством активных и открытых зон для предотвращения ошибок записи.

## Практические сценарии

### Предварительная подготовка и верификация

Перед началом диагностики убедитесь, что устройство доступно и поддерживает SMART:

```bash
# Список всех блочных устройств
lsblk

# Автоматический поиск дисков с поддержкой SMART
sudo smartctl --scan

# Проверка поддержки SMART конкретным устройством
sudo smartctl -i /dev/sda
# → result: SMART support is: Enabled/Disabled/Unavailable
```

Для работы с RAID-контроллерами, USB-дисками и дисками в standby см. детальное руководство в [Решение проблем (Troubleshooting)](./troubleshooting.md).

### Создание базового снимка (Baseline)

При вводе диска в эксплуатацию или после замены создайте эталонный снимок:

```bash
# Создание директории для хранения базовых снимков
mkdir -p /var/log/disk-health/baseline

# Полный снимок диска (модель, атрибуты, тесты)
sudo smartctl -a /dev/sda > /var/log/disk-health/baseline/sda_$(date +%Y%m%d).txt

# Экспорт в JSON для автоматизации
sudo smartctl -a /dev/sda --json > /var/log/disk-health/baseline/sda_$(date +%Y%m%d).json
```

**Что фиксировать в базовом снимке:**
- Модель и серийный номер (`smartctl -i`)
- Версия прошивки
- Значения ключевых атрибутов (Reallocated_Sector_Ct, Current_Pending_Sector, Power_On_Hours)
- Результаты первоначального `long` теста
- Температура в штатном режиме

### Быстрая оценка состояния

```bash
# Краткий вердикт (Health Check)
sudo smartctl -H /dev/sda
# → result: PASSED (ОК) или FAILED (требуется замена)

# Полный отчет (атрибуты, логи, результаты тестов)
sudo smartctl -a /dev/sda

# Для NVMe
sudo smartctl -a /dev/nvme0n1
```

### Глубокая диагностика через самотестирование

```bash
# Запуск короткого теста (2-5 мин)
sudo smartctl -t short /dev/sda

# Запуск расширенного теста (1-20 ч)
sudo smartctl -t long /dev/sda

# Проверка статуса выполнения и результатов
sudo smartctl -l selftest /dev/sda

# Остановка запущенного теста
sudo smartctl -X /dev/sda
```

**Варианты тестов и их применение:**

| Тест | Когда использовать |
| :--- | :--- |
| **`short`** | Ежедневная проверка. Быстрая проверка электроники и начальных блоков. |
| **`long`** | Плановое ежемесячное сканирование. Полная проверка поверхности/ячеек. |
| **`conveyance`** | При получении диска от производителя/из ремонта. Проверка на повреждения при транспортировке. |
| **`offline`** | Принудительный офлайн-сбор данных. Обновляет атрибуты типа `Offline`. |

### Анализ журнала ошибок (Error Log)

```bash
# Журнал ошибок SATA-диска
sudo smartctl -l error /dev/sda

# Журнал ошибок NVMe
sudo smartctl -l error /dev/nvme0n1
```

**Что искать в Error Log:**
- **LBA (Logical Block Address):** Физический адрес сектора с ошибкой. Если один и тот же LBA повторяется — сектор нестабилен.
- **Тип ошибки:** `READ` или `WRITE`. Ошибки записи чаще указывают на проблемы с поверхностью.
- **Временная метка:** Коррелируйте с `dmesg` для исключения проблем с шиной.

### Анализ критических параметров (Checklist)

> **Ключевое правило:** Анализируйте не только абсолютное значение, но и его **динамику**. Если количество ошибок или переназначенных секторов растёт — диск подлежит плановой замене, не дожидаясь окончательного отказа.

#### Для HDD (Механические диски)

```bash
# Вывод таблицы атрибутов с фильтрацией по критическим ID
sudo smartctl -A /dev/sda | grep -E "Reallocated|Pending|Uncorrectable|CRC|Hours|Temperature"
```

| Атрибут | ID | Описание | Критичность |
| :--- | :--- | :--- | :--- |
| `Reallocated_Sector_Ct` | 5 | Количество секторов, перенесенных в резервную область. Рост — прямой признак деградации. | **Высокая** |
| `Current_Pending_Sector` | 197 | Секторы, ожидающие проверки (потенциальные кандидаты в «битые»). | **Высокая** |
| `Offline_Uncorrectable` | 198 | Неисправимые ошибки при обращении к секторам. | **Высокая** |
| `UDMA_CRC_Error_Count` | 199 | Ошибки передачи данных по шине. Часто причина в плохом кабеле. | **Средняя** |
| `Power_On_Hours` | 9 | Общая наработка диска в часах. Помогает оценить возраст устройства. | Информационный |
| `Temperature_Celsius` | 194 | Текущая температура. Постоянный перегрев (>45-50°C) ускоряет выход из строя. | **Средняя** |
| `Spin_Retry_Count` | 10 | Ошибки раскрутки шпинделя. Признак износа мотора или подшипника. | **Высокая** |

#### Для SSD (SATA)

```bash
sudo smartctl -A /dev/sda | grep -E "Wear|Indicator|Written"
```

| Атрибут | Описание | Критичность |
| :--- | :--- | :--- |
| `Wear_Leveling_Count` | Указывает на оставшийся ресурс ячеек в процентах (начинается со 100 и стремится к 0). | **Высокая** |
| `Media_Wearout_Indicator` | Аналогичный показатель износа NAND-памяти. | **Высокая** |
| `Total_LBAs_Written` | Общий объем записанных данных. Позволяет рассчитать соответствие заявленному TBW. | Информационный |

#### Для NVMe (SSD)

```bash
sudo smartctl -a /dev/nvme0n1 | grep -E "Percentage|Critical|Spare|Errors"
```

| Параметр | Описание | Критичность |
| :--- | :--- | :--- |
| `percentage_used` | Процент израсходованного ресурса (0% — новый, >100% — ресурс официально исчерпан). | **Высокая** |
| `critical_warning` | Битовая маска критических предупреждений. Должен быть `0x00`. | **Критическая** |
| `available_spare` | Резерв запасных блоков для замены вышедших из строя (обычно 100%). Падение — критический сигнал. | **Высокая** |
| `media_errors` | Количество обнаруженных контроллером ошибок целостности данных. | **Высокая** |

### Анализ трендов (Trend Analysis)

S.M.A.R.T. полезен только при отслеживании динамики. Ниже приведен пример скрипта для ежедневного сбора метрик:

```bash
#!/bin/bash
# /usr/local/bin/disk-health-monitor.sh
# Ежедневный сбор критических атрибутов

LOG_DIR="/var/log/disk-health/daily"
DEVICE="/dev/sda"
DATE=$(date +%Y%m%d)

mkdir -p "$LOG_DIR"

# Сбор данных
sudo smartctl -A "$DEVICE" > "$LOG_DIR/${DEVICE##*/}_$DATE.txt"

# Извлечение ключевых атрибутов
echo "$DATE,$(sudo smartctl -A "$DEVICE" | awk '/Reallocated_Sector_Ct/ {print $10}'),$(sudo smartctl -A "$DEVICE" | awk '/Current_Pending_Sector/ {print $10}'),$(sudo smartctl -A "$DEVICE" | awk '/Temperature_Celsius/ {print $10}')" >> "$LOG_DIR/${DEVICE##*/}_trends.csv"
```

**Алгоритм анализа трендов:**

1. **Базовый снимок:** При вводе диска в эксплуатацию запишите текущие значения ключевых атрибутов.
2. **Мониторинг трендов:** Ежедневный рост `Reallocated_Sector_Ct` даже на 1–2 сектора — сигнал плановой замены. Резкий скачок (например, с 0 до 50 за час) указывает на катастрофическую деградацию поверхности.
3. **Корреляция типов:** Если растут одновременно `Reallocated_Sector_Ct` и `UDMA_CRC_Error_Count`, проблема, скорее всего, в кабеле/порте, а не в самих ячейках. Если растут только `Reallocated_Sector_Ct` — деградирует сам носитель.
4. **Критический масс:** Для SSD/NVMe одновременное падение `Available Spare` и рост `Critical Warning` требуют немедленной замены, даже если `Percentage Used` еще не достиг 100%.

### NVMe-specific глубокий анализ

Если `smartctl` показывает `PASSED`, но диск нестабилен, используйте `nvme-cli`:

```bash
# Полный лог здоровья
sudo nvme smart-log /dev/nvme0n1

# Журнал ошибок контроллера (SC, SCT)
sudo nvme error-log /dev/nvme0n1

# Persistent Event Log (NVMe 1.4+)
sudo nvme persistent-event-log /dev/nvme0n1 --output-format=json

# Проверка состояния PCIe-линка
sudo lspci -vv -s $(lspci | grep -i nvme | awk '{print $1}')

# Проверка версии прошивки
sudo nvme id-ctrl /dev/nvme0n1 | grep -i fr
```

**Типичные симптомы, когда SMART не помогает:**
- Диск периодически исчезает из системы (`nvme nvme0: Device not ready`)
- `I/O error` при стабильном `smartctl -H` → проблема в PCIe-линке, а не в NAND
- Резкое падение производительности без роста `Percentage Used` → проверьте throttling (`dmesg | grep -i throttl`)

Детальный анализ PCIe-ошибок: [Диагностика NVMe: AER и Reset](../nvme-errors-diagnostics.md).

### Автоматизация и мониторинг (JSON)

Для интеграции в скрипты используйте флаг `--json`:

```bash
# Проверка здоровья через jq
sudo smartctl -H /dev/nvme0n1 --json | jq '.smart_status.passed'

# Извлечение температуры SATA-диска
sudo smartctl -a /dev/sda --json | jq '.temperature.current'

# Фильтрация критических атрибутов NVMe
sudo smartctl -a /dev/nvme0n1 --json | jq '{percentage_used: .nvme_smart_health_information_log.percentage_used, critical_warning: .nvme_smart_health_information_log.critical_warning}'
```

## Процедура замены и критерии решений

### Критерии замены vs продолжения мониторинга

| Состояние | Действие |
| :--- | :--- |
| **`FAILURE IS IMMINENT`** | Немедленная замена. Диск может выйти из строя в любой момент. |
| **Рост `Reallocated_Sector_Ct`** за 24 ч | Запланировать замену в ближайшее время (24–48 ч). |
| **`Current_Pending_Sector` > 0** | Замена в течение недели. Сектор не может быть прочитан. |
| **`UDMA_CRC_Error_Count` растет** | Проверить кабель/бэкплейн. Если после замены кабеля рост продолжается — проблема в контроллере или диске. |
| **`Temperature_Celsius` > 60°C** | Проверить охлаждение. При стабильном перегреве прогнозируемый срок службы сокращается. |
| **Только `SMART overall-health` = `PASSED`, но есть атрибуты `Pre-fail`** | Продолжить мониторинг с увеличенной частотой (ежедневно). |
| **`Percentage Used` > 80%** | Плановая замена в течение 30 дней. |
| **`Available Spare` < 20%** | Плановая замена в течение 7 дней. |
| **`Critical Warning` != 0** | Немедленное резервное копирование и замена. |

### Процедура замены отказавшего диска

При получении алерта `FAILURE IS IMMINENT` или `Completed: read failure`:

1. **Изоляция:** Смонтируйте файловую систему в режиме `read-only`:
    ```bash
    mount -o remount,ro /mount/point
    ```
2. **Резервное копирование:** Скопируйте данные на резервный носитель. Не полагайтесь на RAID как на замену бэкапов.
3. **Идентификация модели:** Запишите модель и серийный номер:
    ```bash
    sudo smartctl -i /dev/sdX
    ```
4. **Замена физическая:** Замените диск, сохранив порядок подключения (особенно важно для SAS с dual-port).
5. **Восстановление массива:** Для RAID-md (`/proc/mdstat`) или LVM добавьте новый диск и запустите rebuild.
6. **Проверка нового диска:** Выполните `smartctl -t long` на новом диске и убедитесь в отсутствии производственных дефектов.

## Дополнительная информация

### Ограничения S.M.A.R.T.

- **Слепая зона:** S.M.A.R.T. не предсказывает внезапные сбои электроники или повреждения прошивки контроллера (до 30-40% всех случаев).
- **Троттлинг:** Современные NVMe при перегреве снижают производительность. Проверяйте температуру при диагностике тормозов.
- **Виртуализация:** При использовании некоторых RAID-контроллеров физические атрибуты могут быть скрыты.

### Best practices для SRE

1. **Установите baseline** при вводе диска в эксплуатацию.
2. **Ежедневный опрос:** Используйте `smartd` для ежедневного контроля.
3. **Для HDD в критичных системах:** опрос каждые 6 часов из-за скорости деградации механики.
4. **Планирование замены:** Заменяйте диски на Warning-уровне в течение 30 дней. На Critical-уровне — немедленно.
5. **База данных моделей:** Поддерживайте `smartd-drivedb` в актуальном состоянии:
    ```bash
    0 3 * * 0 root /usr/sbin/update-smart-drivedb
    ```
