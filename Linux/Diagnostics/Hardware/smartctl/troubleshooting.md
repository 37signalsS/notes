# Решение проблем при диагностике дисков (smartctl)

## Определения

**Поиск и устранение неисправностей (troubleshooting) smartctl** — это процесс выявления причин ошибок при чтении S.M.A.R.T.-данных, интерпретации результатов самодиагностики и настройки взаимодействия с накопителями в сложных конфигурациях (RAID-массивы, специфические контроллеры, USB-адаптеры, виртуализация). Область включает не только работу с утилитой `smartctl`, но и корреляцию данных SMART с системными журналами ядра (`dmesg`), а также принятие решений о замене оборудования.

---

## Базовые концепции

### Типовые препятствия для диагностики

1.  **Права доступа:** Прямое обращение к блочным устройствам требует привилегий суперпользователя (`root`). Любая попытка запуска `smartctl` от имени обычного пользователя завершится ошибкой `Permission denied` или `smartctl: Permission denied during open device`.
2.  **Аппаратная блокировка:** Некоторые RAID-контроллеры и USB-мосты скрывают команды S.M.A.R.T. или требуют инкапсуляции через специфические драйверы. Без правильного флага `-d` утилита либо не увидит устройство, либо вернет мусорные данные.
3.  **Виртуализация:**
    *   **ВМ (KVM/VMware):** Для доступа к SMART требуется проброс устройства (PCI Passthrough). Виртуальные диски (`virtio-blk`) обычно не отдают физические параметры.
    *   **Облачные диски (EBS, Azure Disk):** Не поддерживают SMART, так как являются сетевыми блоковыми устройствами. Диагностика проводится через API провайдера.
4.  **Устаревшие базы данных:** Новые модели дисков могут распознаваться некорректно без обновления `smartd-drivedb`.
5.  **Диски в режиме ожидания (standby/spindown):** Некоторые диски отключают электронику для энергосбережения. `smartctl` не может «разбудить» их автоматически и возвращает `Device open failed` или `READ SMART DATA failed`.
6.  **Устройство занято (Device Busy):** Если раздел смонтирован, используется LVM или multipath, ядро может блокировать доступ к устройству. В этом случае `smartctl` возвращает `Device busy` или `cannot open device`.

### Интерпретация статусов самодиагностики

При выполнении тестов (`-t short`, `-t long`) диск возвращает код завершения, который можно увидеть в `smartctl -l selftest`:

| Статус | Описание | Критичность |
| :--- | :--- | :--- |
| **`Completed without error`** | Тест пройден успешно, физических дефектов не обнаружено. | — |
| **`Completed: read failure`** | Найден нечитаемый сектор. Прямой признак деградации поверхности/ячеек. | **Высокая** |
| **`Completed: servo failure`** | Проблемы с механикой (актуатор, шпиндель). | **Критическая** |
| **`Completed: electrical failure`** | Неисправность электрических цепей или контроллера. | **Критическая** |
| **`Interrupted (host reset)`** | Тест прерван из-за сброса шины или перезагрузки системы. | **Средняя** |
| **`Aborted by host`** | Тест остановлен пользователем (`smartctl -X`) или прерван из-за перегрева/энергосбережения. | **Средняя** |
| **`Completed: unknown failure`** | Диск сообщил о сбое, но не классифицировал его. Требуется дополнительный анализ логов. | **Средняя** |

### Коды завершения smartctl (Exit Codes)

Для автоматизации и скриптов критично понимать возвращаемые коды:

| Код | Описание |
| :--- | :--- |
| **`0`** | Успешно. SMART-статус `PASSED`, команда выполнена. |
| **`1`** | Предупреждение. Устройство поддерживает SMART, но статус `FAILED` или есть критические атрибуты. |
| **`2`** | Критическая ошибка. Устройство не поддерживает SMART, неправильный флаг `-d`, или аппаратная ошибка доступа. |
| **`3`** | Синтаксическая ошибка команды. |
| **`4`** | Внутренняя ошибка smartctl (редко, обычно связана с поврежденной базой drivedb). |

> **Важно для автоматизации:** В скриптах всегда проверяйте exit code (`$?` в bash), а не только текстовый вывод. Например, `smartctl -H /dev/sda` может вернуть `PASSED` в тексте, но exit code `1` при наличии критических атрибутов.

### Протоколы и их особенности

ATA/SATA, NVMe и SAS используют разные механизмы сбора данных. Понимание архитектуры протокола помогает правильно интерпретировать ошибки:

| Протокол | Механизм ошибок | Типичные причины сбоев |
| :--- | :--- | :--- |
| **ATA/SATA** | Таблица атрибутов (Attribute Table), Error Log, Self-test Log. | Механический износ HDD, деградация NAND-ячеек SSD, ошибки передачи по шине (UDMA_CRC). |
| **NVMe** | Health Log Page (Critical Warning, Percentage Used, Data Units Written), Error Log, Persistent Event Log. | PCIe-линк, перегрев контроллера, исчерпание ресурса записи (TBW). |
| **SAS/SCSI** | Sense Data (ключи 0x00h–0x0Fh), Extended Sense, Log Pages. | Ошибка механизма (servo), сбой контрольной суммы CRC, неисправность контроллера расширения. |

**Ключевое правило:** Если `smartctl` показывает `PASSED`, но диск нестабилен — проблема часто не в ячейках памяти, а в шине (PCIe для NVMe, SATA-кабель для HDD, SAS-канал). В этом случае необходима корреляция с `dmesg` и анализ на уровне контроллера.

## Практические сценарии

### Типовые ошибки и их решение

| Ошибка | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `Permission denied` | Запуск от обычного пользователя. | Используйте `sudo smartctl ...`. |
| `Device open failed` | Устройство занято, защищено или путь неверный. | Проверьте путь через `lsblk` или `fdisk -l`. Если диск в standby — разбудите (`hdparm -B 255 /dev/sdX`). |
| `Device does not support SMART` | Неверный тип устройства или SMART выключен. | Используйте флаг `-d` или `-s on`. |
| `Read SMART Data failed` | Сбой контроллера или несовместимый USB-мост. | Попробуйте другой тип драйвера (`-d sat`, `-d jmicron`). |
| `Aborted by host` | Перегрев диска или прерван тест пользователем. | Проверьте температуру через `smartctl -A`, дайте остыть. |
| `Unknown USB bridge` | Мост не поддерживает прозрачную трансляцию SAT. | Используйте флаг `-d` с конкретным чипсетом или установите `usbutils` для идентификации. |
| `No SMART data available` | Диск не поддерживает SMART или находится за неподдерживаемым контроллером. | Проверьте модель через `smartctl -i`, используйте vendor-specific утилиты. |

### Диск за аппаратным RAID-контроллером

Для доступа к дискам в массиве необходимо «пробросить» команды через драйвер контроллера.

```bash
# LSI / Broadcom MegaRAID (диск в слоте 0)
sudo smartctl -d megaraid,0 -a /dev/sda

# HP Smart Array (HPE)
sudo smartctl -d cciss,0 -a /dev/sda

# Dell PERC (обычно использует драйвер megaraid)
sudo smartctl -d megaraid,1 -a /dev/sdb

# Adaptec RAID
sudo smartctl -d aacraid,0 -a /dev/sda

# Автоматический поиск дисков за всеми контроллерами
sudo smartctl --scan-open
```

> **Важно:** RAID-контроллер часто кэширует данные. При сбое питания данные в кэше могут быть потеряны. SMART показывает состояние физического диска, а не состояние RAID-массива. Для контроля массива используйте `MegaCLI`, `hpacucli` или `storcli`.

### Внешние USB-диски и док-станции

Многие USB-контроллеры требуют явного указания протокола трансляции (**SAT — SCSI to ATA Translation**).

```bash
# Попытка универсальной трансляции (рекомендуется)
sudo smartctl -d sat -a /dev/sdb

# Для старых контроллеров JMicron
sudo smartctl -d jmicron -a /dev/sdb

# Если устройство является NVMe-диском в USB-боксе
sudo smartctl -d sntjmicron -a /dev/sdb

# Для контроллеров ASM1153E (часто в современных боксах)
sudo smartctl -d sat -a /dev/sdb

# Для контроллеров ASM235CM (NVMe USB 3.2 Gen2)
sudo smartctl -d sntasmedia -a /dev/sdb
```

#### Матрица совместимости USB-чипсетов

| Чипсет | Протокол | Примечания |
| :--- | :--- | :--- |
| **ASM105x / ASM1153** | SAT | Часто встречаются в SATA-боксах, стабильно работают с `-d sat`. |
| **JMicron JMS539/567** | `jmicron` / `sntjmicron` | Требуют явного указания. Для NVMe — `sntjmicron`. |
| **ASMedia ASM235CM** | `sntasmedia` | NVMe USB 3.2, требуется специфический флаг. |
| **Realtek RTL9210/9211** | `sat` (иногда `sntrealtek`) | NVMe боксы, иногда нестабильны. |
| **Phoiho / Generic** | Нет поддержки | Прозрачная трансляция отсутствует, SMART недоступен. |

### Принудительное включение SMART

Если диагностика поддерживается, но деактивирована:

```bash
# Активация мониторинга и автоматического сохранения логов
sudo smartctl -s on -o on -S on /dev/sda
```

### NVMe: специфические проблемы

`smartctl` для NVMe предоставляет ограниченный набор данных по сравнению с `nvme-cli`. Если `smartctl` показывает `PASSED`, но диск нестабилен:

```bash
# Проверка статуса здоровья через nvme-cli (полный лог)
sudo nvme smart-log /dev/nvme0n1

# Проверка Persistent Event Log (NVMe 1.4+)
sudo nvme persistent-event-log /dev/nvme0n1 --output-format=json

# Журнал ошибок контроллера
sudo nvme error-log /dev/nvme0n1

# Проверка состояния PCIe-линка
sudo lspci -vv -s $(lspci | grep -i nvme | awk '{print $1}')
```

**Типичные симптомы, когда SMART не помогает:**
- Диск периодически исчезает из системы (`nvme nvme0: Device not ready`)
- `I/O error` при стабильном `smartctl -H` → проблема в PCIe-линке, а не в NAND
- Резкое падение производительности без роста `Percentage Used` → проверьте throttling (`dmesg | grep -i throttl`)

Детальный анализ PCIe-ошибок: [Диагностика ошибок NVMe: AER и Reset](../nvme-errors-diagnostics.md).

### SAS: Sense Data и расширенная диагностика

Для SAS-дисков `smartctl` возвращает ограниченные данные. Основной источник информации — **Sense Data**:

```bash
# Полный отчет SAS/SATA за контроллером
sudo smartctl -a -d scsi /dev/sg2

# Извлечение Sense Data через sg3_utils
sudo sg_logs -p 0x03 /dev/sg2  # Supported log pages
sudo sg_logs -p 0x02 /dev/sg2  # Write error counter
sudo sg_logs -p 0x0A /dev/sg2  # Self-test results
sudo sg_logs -p 0x1D /dev/sg2  # Non-medium error log
```

**Расшифровка Sense Key (основные значения):**
| Sense Key | Описание | Действие |
| :--- | :--- | :--- |
| **0x00** | No Sense | Нет ошибок. |
| **0x01** | Recovered Error | Ошибка исправлена контроллером, но рост значений — сигнал деградации. |
| **0x02** | Not Ready | Диск не готов (инициализация, форматирование). |
| **0x03** | Medium Error | Физический сбой поверхности/ячеек. Критично. |
| **0x04** | Hardware Error | Аппаратная неисправность (электроника, шпиндель). |
| **0x05** | Illegal Request | Некорректная команда. Часто после обновления прошивки. |
| **0x0B** | Aborted Command | Команда прервана. Может быть вызвана сбросом шины. |

### Диски в standby и энергосбережении

Диски в режиме ожидания не отвечают на команды SMART:

```bash
# Проверка текущего режима энергосбережения
sudo hdparm -C /dev/sda
# → device state is: standby

# Принудительное отключение энергосбережения (режим never)
sudo hdparm -B 255 /dev/sda

# Проверка таймаута выключения (в секундах)
sudo hdparm -S /dev/sda

# Разбудить диск (чтение 1 сектора)
sudo smartctl -i /dev/sda
```

> **Важно:** Некоторые диски (особенно внешние USB) не поддерживают стандартные команды `hdparm`. В этом случае используйте `sdparm` (SCSI) или временно отключите USB-автосуспенд (`echo on > /sys/bus/usb/devices/.../power/control`).

### Корреляция с dmesg: практический алгоритм

Ошибки `smartctl` часто сопровождаются сообщениями ядра о сбоях на шине. Для NVMe-накопителей это критично, так как проблема может быть в PCIe-линке.

```bash
# Поиск I/O ошибок и сбросов линка
dmesg -T | grep -iE "sd[a-z]|ata|nvme|error|timeout|reset|link"
# → result: blk_update_request: I/O error, dev sda, sector ...
# → result: nvme nvme0: I/O 42 QID 7 timeout, aborting
# → result: AER: Corrected: Receiver Error (RxErr)
```

**Пошаговый алгоритм диагностики:**

1. **Выполните `smartctl -a`** — если статус `PASSED`, но ошибки присутствуют — проблема вне NAND.
2. **Проверьте `dmesg`** на предмет ошибок шины (`ata`, `nvme`, `pcie`, `scsi`).
3. **Сопоставьте временные метки** — ошибки SMART и dmesg должны совпадать по времени.
4. **Проверьте кабели/слоты** — для SATA проверьте кабель, для NVMe — переставьте диск в другой слот PCIe.
5. **Проверьте питание** — для NVMe Gen5 требуется до 3A на линию 3.3V.

См. также: [Диагностика через dmesg](../../Kernel/dmesg/troubleshooting.md), [Диагностика NVMe: AER и Reset](../nvme-errors-diagnostics.md).

### Доступ к SMART через LVM

Диски, являющиеся Physical Volumes (PV) в LVM, доступны для smartctl напрямую через физическое устройство. Проблема возникает, когда неизвестно, какое `/dev/sdX` соответствует какому LV.

#### Определение физического устройства для LV

```bash
# Найти PV для конкретного VG
sudo pvs
# → /dev/sda2   centos   lvm2  a--  <99.50g    0

# Или через lvdisplay
sudo lvdisplay /dev/centos/root
# → ... /dev/sda2  1  1      [<99.50 GiB]

# Проверить все PV и их устройства
sudo pvdisplay --grep "Physical volume"
```

#### smartctl на PV (физическое устройство)

```bash
# После определения физического устройства
sudo smartctl -a /dev/sda
sudo smartctl -H /dev/sda

# Если PV — это.partition (например /dev/sda2), smartctl работает с диском целиком
sudo smartctl -i /dev/sda
```

#### Особенности LVM thin pool и snapshot

- **Thin pool:** SMART мониторит физический диск, а не виртуальный volume. Thin pool не влияет на физические атрибуты.
- **Snapshot:** Временные снапшоты не маскируют SMART-данные. Если физический диск деградирует, snapshot бесполезен — данные в thin pool уже повреждены.

### Доступ к SMART через multipath

Multipath объединяет несколько путей к одному логическому устройству (например, через SAN-коммутатор). smartctl должен работать с физическим путём, а не с маппингом multipath.

#### Определение физических путей

```bash
# Просмотр multipath-кластеров
sudo multipath -ll
# → mpath0 (35000c500a1b2c3d4) dm-0 HP,LOGICAL VOLUME
# →  size=100G features='1 queue_if_no_path' hwhandler='0' wp=rw
# │
# ├─ round-robin 0优先生策 1
# │ ├─ 8:0:0:0 sda 40:0  0  100G  0  active ready running
# │ └─ 8:0:1:0 sdb 40:1  0  100G  0  active ready running
# │
# └─ round-robin 0 приоритет 0
#   ├─ 8:0:2:0 sdc 40:2  0  100G  0  active ready running
#   └─ 8:0:3:0 sdd 40:3  0  100G  0  active ready running
```

#### smartctl на физические пути

```bash
# SMART-данные первого пути
sudo smartctl -a /dev/sda

# SMART-данные второго пути
sudo smartctl -a /dev/sdb

# Сравнение состояния дисков на разных путях
for path in sda sdb sdc sdd; do
  echo "=== /dev/$path ==="
  sudo smartctl -H "/dev/$path" 2>/dev/null | grep -i "result"
done
```

#### Учёт multipath в smartd

Конфигурация smartd для multipath-окружения:

```text
# Мониторить только один путь (избегать дублирования алертов)
/dev/sda -a -d scsi -m admin@example.com
# Исключить остальные пути
/dev/sdb -d scsi -n never
/dev/sdc -d scsi -n never
/dev/sdd -d scsi -n never
```

### Доступ к SMART через dm-crypt (LUKS)

LUKS-шифрованные разделы не блокируют доступ к физическому устройству для SMART-команд. Ключевой момент: smartctl обращается к физическому диску, а не к decrypted mapper-устройству.

#### Определение физического устройства

```bash
# Просмотр LUKS-устройств
sudo cryptsetup luksDump /dev/sda2 | grep "UUID"
# → UUID:           12345678-abcd-efgh-ijkl-123456789abc

# Найти, какой physical device стоит за LUKS
sudo lsblk -o NAME,TYPE,FSTYPE,MOUNTPOINT
# → sda
# → ├─sda1  ext4          /boot
# → └─sda2  crypto_LUKS
#     └─sda2_crypt lvm   centos-root  /

# Прямой доступ к физическому диску
sudo smartctl -a /dev/sda
```

#### Особенности работы с LUKS

```bash
# smartctl работает с физическим диском, НЕ с mapper-устройством
sudo smartctl -a /dev/sda           # Физический диск — РАБОТАЕТ
sudo smartctl -a /dev/sda2          # Раздел с LUKS — тоже работает (smartctl определит тип)
sudo smartctl -a /dev/mapper/sda2_crypt  # Decrypted device — НЕ работает (это block device, не disk)
```

### Корреляция: проблема шины vs проблема диска

Когда `smartctl -H` показывает `PASSED`, но система испытывает I/O-ошибки, проблема часто не в диске, а в шине или контроллере.

#### Алгоритм дифференциальной диагностики

| Симптом | Вероятная причина | Диагностический шаг |
| :--- | :--- | :--- |
| `I/O error` в dmesg + `PASSED` SMART | Проблема с кабелем/шиной | Заменить SATA-кабель, проверить `UDMA_CRC_Error_Count` |
| `I/O error` + `FAILED` SMART | Физический сбой диска | Замена диска |
| Периодические исчезновения NVMe | PCIe-линк нестабилен | `lspci -vv`, проверка AER в dmesg |
| Высокий `await` + низкий `%util` | Внешний throttle (SAN, гипервизор) | Проверить iSCSI/FC-latency |
| `Reset to device` + `I/O error` | Контроллер сбрасывает диск | Проверить firmware контроллера,更换电源 |
| Локальные ошибки на одном LBA | Нестабильный сектор | Мониторинг через `smartctl -l error` |

#### Матрица решений

```
smartctl -H = PASSED?
  ├─ ДА → smartctl -A: есть растущие атрибуты?
  │       ├─ ДА → Плановая замена (деградация медленная)
  │       └─ НЕТ → Проблема НЕ в диске
  │               ├─ Проверить кабель/шину (UDMA_CRC_Error_Count)
  │               ├─ Проверить dmesg на ошибки ATA/NVMe/SCSI
  │               └─ Проверить controller firmware
  └─ НЕТ → Физический сбой диска → Немедленная замена
```

### Процедура замены отказавшего диска

При получении алерта `FAILURE IS IMMINENT` или `Completed: read failure`:

1. **Изоляция:** Смонтируйте файловую систему в режиме `read-only`:
   ```bash
   mount -o remount,ro /mount/point
   ```
2. **Резервное копирование:** Скопируйте данные на резервный носитель. Не полагайтесь на RAID как на замену бэкапов.
3. **Идентификация модели:** Запишите модель и серийный номер:
   ```bash
   sudo smartctl -i /dev/sdX
   ```
4. **Замена физическая:** Замените диск, сохранив порядок подключения (особенно важно для SAS с dual-port).
5. **Восстановление массива:** Для RAID-md (`/proc/mdstat`) или LVM добавьте новый диск и запустите rebuild.
6. **Проверка нового диска:** Выполните `smartctl -t long` на новом диске и убедитесь в отсутствии производственных дефектов.

## Дополнительная информация

### Чек-лист быстрого исправления

1.  **Проверка кабелей:** Ошибки `UDMA_CRC_Error_Count` в 90% случаев исправляются заменой SATA-кабеля или переподключением разъема.
2.  **Обновление баз данных:** Если диск определяется как `Unknown model`, обновите базу данных драйверов:
    ```bash
    sudo update-smart-drivedb
    ```
3.  **Температурный режим:** Если тест прерывается с ошибкой `Aborted by host`, проверьте температуру. Некоторые диски прекращают тесты при перегреве.
4.  **Sense Data (SAS):** При анализе SAS-дисков обращайте внимание на коды Sense (например, `Sense Key: Medium Error`). Они точно указывают на физический сбой.
5.  **Выход из standby:** Если `smartctl` не видит диск, проверьте его состояние через `hdparm -C` или `cat /proc/diskstats`.
6.  **Multipath/LVM:** Если устройство занято, используйте `dmsetup status` или `multipath -ll` для определения маппинга.
7.  **Firmware:** Перед заменой диска проверьте наличие обновления прошивки. Иногда проблемы, которые выглядят как аппаратный отказ, решаются обновлением.

### Критерии замены vs продолжения мониторинга

| Состояние | Действие |
| :--- | :--- |
| **`FAILURE IS IMMINENT`** | Немедленная замена. Диск может выйти из строя в любой момент. |
| **Рост `Reallocated_Sector_Ct`** за 24 ч | Запланировать замену в ближайшее время (24–48 ч). |
| **`Current_Pending_Sector` > 0** | Замена в течение недели. Сектор не может быть прочитан, это прямой путь к отказу. |
| **`UDMA_CRC_Error_Count` растет** | Проверить кабель/бэкплейн. Если после замены кабеля рост продолжается — проблема в контроллере или диске. |
| **`Temperature_Celsius` > 60°C** | Проверить охлаждение. При стабильном перегреве прогнозируемый срок службы сокращается в разы. |
| **Только `SMART overall-health` = `PASSED`, но есть атрибуты `Pre-fail`** | Продолжить мониторинг с увеличенной частотой (ежедневно). |

### Прошивка (Firmware) и диагностика

Некоторые ошибки SMART являются ложными и устраняются обновлением прошивки:

```bash
# Проверка версии прошивки
sudo smartctl -i /dev/sda | grep -i firmware

# Обновление для NVMe (требует загрузки в чистую ОС или использования厂商утилит)
sudo nvme fw-download /dev/nvme0 --fw=new_firmware.bin
sudo nvme fw-activate /dev/nvme0

# Для SATA/SAS используйте vendor-specific утилиты (например, samsung_magician для Samsung)
```

> **Предупреждение:** Обновление прошивки — рискованная операция. Убедитесь в стабильности питания (ИБП), не прерывайте процесс и используйте только официальные образы.
