# `iotop` — мониторинг дисковой активности процессов

## Определения

- **`iotop`:** Интерактивная утилита (аналог `top`), предназначенная для мониторинга активности ввода-вывода (I/O) в реальном времени с детализацией до конкретных процессов и потоков.
- **`IO>` (I/O Wait):** Процент времени, в течение которого процесс ожидал завершения операций ввода-вывода (состояние `D` — uninterruptible sleep). Рассчитывается на основе статистики `taskstats` ядра.
- **`DISK READ/WRITE`:** Мгновенная скорость чтения и записи данных процессом (обычно в байтах, КБ или МБ в секунду).
- **`SWAPIN`:** Процент времени, затраченного на подкачку страниц из Swap в оперативную память. Высокий показатель — признак критической нехватки RAM и деградации производительности.
- **`iotop-c`:** Современная реализация утилиты на языке C. Она значительно производительнее оригинальной версии на Python, потребляет меньше ресурсов и часто является версией по умолчанию в новых дистрибутивах (например, в Fedora, Arch, Debian 12+).

## Основные концепции

`iotop` — это инструмент "второй линии" диагностики. Его используют, когда общие инструменты (`top`, `iostat`) подтвердили наличие проблемы (высокий `%wa` или `await`), и нужно найти конкретного виновника.

### Механизм работы

Утилита считывает данные из `/proc/self/taskstats` (через Netlink-сокеты). Ядро Linux ведет учет I/O для каждого процесса, если включены соответствующие опции компиляции.

**Ключевые отличия версий:**
- **Python-версия:** Оригинальная, гибкая, но может сама создавать заметную нагрузку на CPU при большом количестве процессов.
- **C-версия (`iotop-c`):** Энергоэффективная, поддерживает дополнительные фильтры и более плавное обновление интерфейса.

## Практические сценарии

### Интерактивный поиск виновника

Самый эффективный способ использования — запуск с фильтрацией только активных процессов.

```bash
# Рекомендуемый запуск: только процессы, реально выполняющие I/O в данный момент
sudo iotop -o

# Отображение накопленного объема данных (клавиша 'a' в процессе работы)
# Помогает найти процессы, которые пишут редко, но большими порциями
sudo iotop -a

# Группировка всех потоков приложения в одну строку (удобно для Java/PostgreSQL)
sudo iotop -P -o
```

### Диагностика системных служб и пользователей

```bash
# Мониторинг активности конкретного пользователя (например, веб-сервера)
sudo iotop -u www-data

# Мониторинг по списку PID
sudo iotop -p 1234,5678
```

### Использование в скриптах (Batch mode)

Для фиксации аномалий в логах без интерактивного интерфейса.

```bash
# Вывод 10 итераций с интервалом в 1 секунду
sudo iotop -b -n 10 -d 1 > iotop_capture.txt
```

### Интерактивные команды

В процессе работы интерактивной версии доступны горячие клавиши:

| Клавиша | Действие |
| :--- | :--- |
| **`o`** | Переключение фильтра "только активные" (Only active) |
| **`a`** | Переключение между скоростью (КБ/с) и объемом (КБ) |
| **`p`** | Переключение между процессами и потоками |
| **`i`** | Изменение приоритета I/O (ionice) для выбранного процесса |
| **`r`** | Инверсия сортировки |
| **`q`** | Выход |

## Дополнительная информация

### Системные требования

Для корректной работы `iotop` ядро должно быть собрано с параметрами:
- `CONFIG_TASKSTATS=y`
- `CONFIG_TASK_DELAY_ACCT=y`
- `CONFIG_TASK_IO_ACCOUNTING=y`

Проверить можно через `zcat /proc/config.gz | grep TASKSTATS` (если доступно).

### Ограничения и особенности

1.  **Проблема сэмплирования:** `iotop` делает моментальные снимки. Кратковременные всплески активности (длительностью < 1с) могут не попасть в отчет. В таких случаях лучше использовать `pidstat -d 1`.
2.  **Ядерные потоки (`kworker`):** Часто в топе можно увидеть процессы `kworker/u*:flush`. Это не виновники, а механизмы ядра, сбрасывающие "грязные" страницы из памяти на диск. Настоящего виновника нужно искать среди приложений, заполняющих Page Cache.
3.  **Высокоскоростные SSD/NVMe:** На сверхбыстрых дисках задержки настолько малы, что колонка `IO>` может всегда показывать 0%, даже при огромной пропускной способности. В этом случае ориентируйтесь на колонки `DISK READ/WRITE`.
4.  **Контейнеры:** Внутри Docker/LXC `iotop` может не видеть нагрузки, если не имеет доступа к `/proc` хоста или не обладает привилегиями `CAP_NET_ADMIN` (для Netlink).

### Альтернативные инструменты

- **`pidstat -d 1`:** Более точный сбор статистики без интерактивного интерфейса.
- **`atop`:** Позволяет просматривать исторические данные по I/O процессов.
- **`fatrace`:** Показывает, к каким конкретно файлам обращаются процессы прямо сейчас.
- **[iostat](./iostat.md):** Диагностика на уровне физических дисков.
