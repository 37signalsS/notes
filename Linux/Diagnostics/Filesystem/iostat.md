# iostat

## Определения

- **`iostat` (input/output statistics — статистика ввода-вывода):** Утилита из пакета `sysstat` для мониторинга статистики ввода-вывода блочных устройств и использования CPU. Собирает данные напрямую из интерфейса ядра `/proc/diskstats`. По умолчанию выводит статистику CPU с момента загрузки системы и средние значения дисков с момента загрузки — поэтому всегда используйте флаг `-y` или интервальный режим.
- **IOPS (количество операций ввода-вывода в секунду):** Метрики `r/s` (чтение) и `w/s` (запись). Ключевой показатель для транзакционных нагрузок, таких как базы данных (БД). На современных NVMe может достигать 500K–3M для случайных 4K-операций.
- **Пропускная способность (`rMB/s`, `wMB/s` или `rkB/s`, `wkB/s`):** Скорость передачи данных в МБ/с или КБ/с. Важна для последовательных операций (бэкапы, потоковое видео).
- **`await` (Average Wait):** Среднее время (в мс) от момента создания запроса до завершения его обслуживания. Включает время в очереди планировщика и время фактической обработки устройством. Формула: `await = (Δ Field_7 + Δ Field_11) / (Δ Field_4 + Δ Field_8)`, где Field_* — поля из `/proc/diskstats`.
- **`aqu-sz` / `avgqu-sz` (Average Queue Size):** Средняя длина очереди запросов к устройству. В новых версиях `sysstat` используется `aqu-sz` (Weighted I/O time / Δt), в старых — `avgqu-sz`. Оба значения рассчитываются из поля 14 `/proc/diskstats` (Weighted I/O time).
- **`f_await` (Flush Await):** Среднее время выполнения операций сброса кэша (flush). Критично для анализа производительности записи в БД, так как `fsync` и `fdatasync` вызывают flush. В ядрах 5.5+ данные берутся из полей 19–20 `/proc/diskstats`.
- **`%util` (Utilization):** Процент времени, в течение которого устройство было занято обработкой запросов. Рассчитывается как `Δ Field_13 / Δt × 100%`. Для SSD/NVMe 100% не означает насыщение из-за параллельной обработки.
- **`svctm` (Service Time):** Среднее время обслуживания запроса. **Устаревший показатель**, не рекомендуется к использованию в ядрах версии 2.6.38 и выше, так как он не учитывает параллелизм современных устройств.

## Основные концепции

`iostat` позволяет получить объективную картину производительности дисковой подсистемы и ответить на вопрос: «Справляется ли оборудование с текущей нагрузкой?». В отличие от `iotop`, который идентифицирует виновников нагрузки, `iostat` анализирует состояние самих устройств.

### Источник данных: `/proc/diskstats`

Все метрики `iostat` рассчитываются из кумулятивных счетчиков в `/proc/diskstats`. Для получения мгновенных значений нужно взять два снимка с интервалом Δt:

| Поле | Описание | Использование в iostat |
| :--- | :--- | :--- |
| 4 | Reads completed | Числитель для `await` |
| 7 | Time spent reading (ms) | Числитель для `await` |
| 8 | Writes completed | Знаменатель для `await` |
| 11 | Time spent writing (ms) | Числитель для `await` |
| 13 | Time spent doing I/O (ms) | Числитель для `%util` |
| 14 | Weighted I/O time (ms) | Числитель для `avgqu-sz` / `aqu-sz` |
| 19 | Flush requests completed | Числитель для `f_await` (ядро 5.5+) |
| 20 | Time spent flushing (ms) | Числитель для `f_await` (ядро 5.5+) |

### Ключевые метрики для диагностики

| Метрика | Норма для HDD | Норма для SSD/NVMe | Признак проблемы |
| :--- | :--- | :--- | :--- |
| `await` | < 20 мс | < 1 мс | Значительные задержки или переполнение очереди |
| `aqu-sz` | < 2 | < 1 (на один поток) | Постоянно растущая очередь запросов |
| `%util` | < 80% | < 90% | Устройство близко к пределу возможностей |
| `r_await`/`w_await` | — | — | Разделение задержек на чтение и запись |

**Важное примечание:** Высокое значение `%util` не всегда означает проблему. Для современных SSD и RAID-массивов полная утилизация может достигаться при сохранении низкой латентности за счет параллельной обработки запросов. Критическим признаком перегрузки является высокий `await` при высокой утилизации.

### Интерпретация полей расширенной статистики (`-x`)

**Статистика центрального процессора (CPU):**

- `%user`: Время выполнения в пользовательском режиме (приложения).
- `%system`: Время выполнения в режиме ядра (системные вызовы, драйверы).
- `%iowait`: Время, в течение которого CPU простаивал в ожидании завершения операций ввода-вывода. Высокий показатель при низкой загрузке CPU — признак дискового узкого места.
- `%idle`: Время простоя без выполнения каких-либо задач.
- `%steal`: Время, "украденное" у гостевой ВМ гипервизором. Показывает только на виртуализированных системах (KVM, VMware, Xen). На bare-metal `%steal` должен быть близок к 0. Постоянный `%steal` > 5% — признак overselling CPU на хосте или noisy neighbor.

**Статистика дисковых устройств (Device):**

- `rrqm/s`, `wrqm/s`: Количество запросов на чтение/запись, объединенных планировщиком ввода-вывода (merge).
- `r/s`, `w/s`: Количество завершенных операций чтения и записи в секунду (IOPS).
- `rkB/s`, `wkB/s` (`rMB/s`, `wMB/s`): Пропускная способность в КБ/с или МБ/с.
- `rareq-sz`, `wareq-sz`: Средний размер запроса на чтение и запись (в КБ). Помогает понять характер нагрузки (Small Random vs Large Sequential).
- `avgrq-sz`: Средний размер запроса в секторах.
- `avgqu-sz` / `aqu-sz`: Средняя длина очереди запросов.
- `await`: Среднее время ожидания (мс), включая время в очереди.
- `r_await`, `w_await`: Латентность отдельно для чтения и записи.
- `f_await`: Латентность операций сброса кэша (flush).
- `%util`: Процент времени утилизации устройства (bandwidth utilization).

### Взаимодействие с cgroups v2

В системах с cgroups v2 контроллер `io` предоставляет дополнительные метрики, которые дополняют `iostat`:

- **`io.stat`:** Показывает кумулятивную статистику (rbytes, wbytes, rios, wios, dbytes, dios) для каждого cgroup. Позволяет увидеть, какой именно slice или контейнер генерирует нагрузку, если `iostat` показывает высокую утилизацию устройства.
- **`io.max`:** Жесткие лимиты (BPS/IOPS) могут ограничивать устройства ниже их физического потенциала. Если `await` высокий, но `%util` низкий — проверьте `io.max` в соответствующем cgroup.
- **Делегирование:** Для корректной работы `io.stat` внутри контейнера родительский slice/systemd должен иметь `Delegate=yes`.

### Нюансы для SSD и NVMe

Для современных NVMe-накопителей с поддержкой Multi-queue классические пороги `iostat` требуют адаптации:

- **Порог `await`:** Для NVMe значение `> 0.5 мс` часто указывает на начало деградации (Steady State) или переключение в SLC-кэш.
- **`%util`:** На NVMe 100% утилизация не означает насыщение — диск может обрабатывать тысячи запросов параллельно. Ориентируйтесь на `aqu-sz` и P99 latency.
- **Планировщик:** Для NVMe стандартом является `none`. Планировщики типа `mq-deadline` или `bfq` добавляют задержку, превышающую время отклика самого накопителя.
- **Flush-штормы:** Высокое `f_await` при низком общем `await` указывает на проблемы с кэшированием или отсутствие PLP (Power Loss Protection) у consumer SSD.

## Практические сценарии

### Мониторинг в реальном времени

```bash
# Исключение "первого отчета" и обновление каждые 2 секунды
iostat -dx -y 2

# Статистика в МБ/с с указанием временных меток
iostat -dxmt 2

# Мониторинг только активных устройств (скрыть простаивающие)
iostat -dxz 1

# Отображение имен LVM вместо dm-X
iostat -dxN 1

# Мониторинг конкретного устройства (например, nvme1n1)
iostat -dx 1 5 /dev/nvme1n1

# Быстрая оценка: человекочитаемый формат, 3 замера с интервалом 1 с
iostat -xh 1 3
```

### Диагностика swap-активности

Swap-операции видны в `iostat` как высокий `await` на устройстве, где активен swap:

```bash
# Проверка активного swap
swapon --show

# Мониторинг диска swap
iostat -xz 1 5 /dev/sda
# → await > 10 мс на диске swap = дисковая узкое место

# Поиск kswapd через iotop
sudo iotop -oP
# → kswapd0 с активной записью = свопинг под давлением памяти
```

**Решение:** Временное снижение `vm.dirty_ratio` и `vm.dirty_background_ratio` или добавление RAM. Подробнее: [Диагностика Swap и Page Faults](../../Core/memory/swap_diagnostics.md).

### Мониторинг NVMe и SSD

Для NVMe-устройств используйте более строгие пороги:

```bash
# Мониторинг NVMe с порогом await < 0.5 мс
iostat -x 1 /dev/nvme0n1

# Проверка SMART-атрибутов
sudo nvme smart-log /dev/nvme0 | grep -E 'Temperature|Percentage Used|Available Spare'

# Проверка throttling в логах
dmesg -T | grep -i "nvme.*throttl"
```

### Диагностика узких мест ввода-вывода (I/O Bottleneck)

1. **Оценка задержек:** Если `await` стабильно выше 20 мс для HDD или 1 мс для SSD — дисковая подсистема перегружена.
2. **Проверка очереди:** Значение `aqu-sz` (или `avgqu-sz`) больше 1–2 указывает на то, что запросы скапливаются в очереди.
3. **Облачный Throttling:** В облачных средах (AWS EBS, GCP PD) `iowait` может быть низким, но `await` высоким из-за ограничений провайдера. Подробности в разделе **[Низкий iowait при высокой задержке диска](../Performance/DiskIO/iowait_and_latency.md)**.
4. **Поиск виновника:** Если `iostat` подтверждает проблему на уровне устройства, используйте `iotop -o` или `pidstat -d 1` для поиска конкретных процессов.

### Сбор данных для анализа

```bash
# Сохранение данных в формате JSON для автоматизированной обработки (ELK, Python)
iostat -dx -o JSON 2 300 > iostat_log.json

# Запись расширенной статистики в текстовый файл
iostat -dx 2 60 > iostat_log.txt

# Парсинг JSON через jq: извлечение await для устройства sda
cat iostat_log.json | jq -r '.sysstat.hosts[].statistics[].disk[].device // empty' | grep sda
```

### Автоматизация и мониторинг

```python
# Пример парсинга вывода iostat в Python (требуется sysstat с поддержкой JSON)
import json
import subprocess

result = subprocess.run(['iostat', '-dxo', 'JSON', '1', '3'], capture_output=True, text=True)
data = json.loads(result.stdout)

for stat in data['sysstat']['hosts'][0]['statistics']:
    for disk in stat['disk']:
        if disk['await'] > 20:
            print(f"ALERT: {disk['device']} await={disk['await']}ms")
```

```bash
# Мониторинг через PSI (Pressure Stall Information)
cat /proc/pressure/io
# → some avg10=15.20 avg60=10.05 avg300=5.00 total=1234567
# some avg10 > 10 = приложения испытывают задержки из-за диска
```

## Установка

`iostat` входит в состав пакета `sysstat`. Установка:

```bash
# Debian / Ubuntu
sudo apt install sysstat

# RHEL / CentOS / Fedora
sudo dnf install sysstat

# Arch Linux
sudo pacman -S sysstat
```

**Включение сбора данных (systemd-based системы):**

```bash
sudo systemctl enable --now sysstat
# Данные будут сохраняться в /var/log/sysstat/ для исторического анализа
```

## Типичные ошибки и диагностика

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `await` высокий, но `%util` низкий | Внешний троттлинг (облако) или проблема в очереди планировщика | Проверьте `iostat -xz 1`, сравните `aqu-sz` с порогами |
| `%util` = 100%, но `await` низкий | SSD/NVMe с параллельной обработкой запросов | Нормально для быстрых дисков; проверяйте `aqu-sz` |
| `f_await` высокий при низком `await` | Проблема с flush (нет PLP, медленный журнал ФС) | Проверьте `dmesg`, перейдите на enterprise SSD с PLP |
| Первый отчет бесполезен | По умолчанию `iostat` выводит средние с момента загрузки | Всегда используйте `-y` или интервальный режим |
| Нет поля `f_await` | Ядро < 5.5 или старая версия sysstat | Обновите sysstat; на старых ядрах flush не показывается |
| `iostat` не показывает cgroup-разделение | Нужен `io.stat` из cgroups v2 | Используйте `cat /sys/fs/cgroup/.../io.stat` |
| Высокий `iowait`, но `await` низкий | Проблема в сетевых ФС (NFS/CIFS), а не в локальном диске | Проверьте `nfsiostat` или `mountstats` |
| `iowait` низкий, но `await` высокий | Облачный throttling или перегрузка очереди планировщика | Проверьте `aqu-sz`, `iostat -xz 1` |

## Дополнительная информация

### Взаимосвязь с iowait и Load Average

Процессы, находящиеся в состоянии `uninterruptible sleep` (ожидание ввода-вывода, статус `D` в `ps` или `top`), напрямую влияют на показатель `Load Average`. Высокие значения `await` и `%util` в `iostat` обычно коррелируют с ростом `iowait` и `Load Average`.

**Команды для проверки:**

```bash
# Просмотр процессов в состоянии D
ps -eo pid,stat,wchan:20,comm | awk '$2 ~ /D/ {print}'

# Определение kernel-функции, блокирующей процесс
cat /proc/<PID>/wchan
# → Примеры: wait_on_page_bit (ожидание чтения с диска), jbd2_log_wait_commit (ожидание коммита в журнал ext4)

# Мониторинг системных вызовов и очередей через vmstat
vmstat 1 5
```

### Ограничения

1.  **Первичный отчет:** По умолчанию первый вывод `iostat` содержит средние значения с момента загрузки системы. Всегда используйте флаг `-y` или интервальный режим.
2.  **Средние значения:** `await` — средняя метрика, которая скрывает "хвостовые задержки" (Tail Latency). Для поиска P95/P99 используйте `biolatency-bpfcc`.
3.  **Сетевые ФС:** `iostat` на клиенте не показывает реальную задержку сетевого хранилища. Используйте `nfsiostat` или `mountstats` для NFS/CIFS.
4.  **io_uring:** Современные приложения, использующие `io_uring`, могут не генерировать видимой активности в `iostat` через классические системные вызовы. Используйте `perf record -e 'block:block_rq_issue'`.
5.  **Планировщики `none` / `kyber`:** На этих планировщиках приоритизация на уровне `task->ioprio` игнорируется. Для управления используйте cgroups v2 (`io.weight`).
6.  **Облачные среды:** В облаке низкий `iowait` при высокой задержке — норма при throttling. `iostat` показывает Symptoms, но не причину (лимиты провайдера).

### Рекомендации по чистоте эксперимента

1.  **Запуск с интервалом:** Всегда используйте интервальный режим (`iostat 2 10`) и игнорируйте первую итерацию.
2.  **Идентификация планировщика:** Проверяйте активный планировщик через `/sys/block/<dev>/queue/scheduler`. Если активен `none` или `kyber` — классические пороги `await` могут не работать.
3.  **Корреляция с `iotop`:** Если `iostat` показывает проблему, а `iotop` не находит виновника — проверяйте writeback, kworker, io_uring.
4.  **Серийный номер диска:** Для точной идентификации устройства используйте `lsblk -o NAME,SERIAL,SIZE,ROTA` и сверяйте с `iostat`.
5.  **JSON для автоматизации:** Для сбора метрик в мониторинг используйте `-o JSON`, избегайте парсинга текстового вывода.
