# `iostat`

## Определения

- **`iostat` (input/output statistics):** Утилита из пакета `sysstat` для мониторинга статистики ввода-вывода блочных устройств. Фокусируется на производительности дисков, а не на процессах.
- **IOPS (`r/s`, `w/s`):** Операции чтения/записи в секунду. Ключевой показатель для транзакционных нагрузок (БД).
- **Пропускная способность (`rMB/s`, `wMB/s`):** Скорость передачи данных в МБ/с. Важна для последовательных операций (файловые серверы, бэкапы).
- **`await`:** Среднее время ожидания запроса I/O (в очереди + обработка), мс.
- **`%util`:** Процент времени, когда устройство было занято обработкой запросов.
- **`svctm`:** Устаревшая метка среднего времени обслуживания. **Не рекомендуется** к использованию с ядра 2.6.38+.

## Основные концепции

`iostat` отвечает на вопрос: **"Как диск справляется с нагрузкой?"** (в отличие от [iotop](./iotop.md), который показывает "*кто* создает нагрузку").

### Ключевые метрики для диагностики

| Метрика | Норма HDD | Норма SSD | Проблема |
| :--- | :--- | :--- | :--- |
| `await` | <20 мс | <1 мс | Задержки, очередь |
| `%util` | <80% | <90% | Устройство перегружено |
| `r_await`/`w_await` | — | — | Раздельные задержки чтения/записи |
| `rrqm/s`/`wrqm/s` | — | — | Слияние запросов (низкое для SSD) |

**Важно:** Высокий `%util` сам по себе не проблема — это лишь показывает, что диск работает. Высокий `await` при `%util` ~100% — признак I/O bottleneck.

### Интерпретация полей расширенной статистики (`-x`)

**CPU статистика:**

- `%user`: Время в пользовательском режиме
- `%nice`: Время в пользовательском режиме с приоритетом nice
- `%system`: Время в режиме ядра
- `%iowait`: Время ожидания I/O (простой CPU)
- `%idle`: Простой без задач

**Device статистика:**

- `rrqm/s`, `wrqm/s`: Запросы на слияние (read/write merge)
- `r/s`, `w/s`: Операций чтения/записи в секунду (IOPS)
- `rkB/s`, `wkB/s`: Пропускная способность (КБ/с)
- `avgrq-sz`: Средний размер запроса (сектора)
- `avgqu-sz`: Средняя длина очереди запросов
- `await`: Среднее время ожидания (мс)
- `svctm`: Среднее время обслуживания (устарело)
- `%util`: Утилизация устройства

## Практические сценарии

### Мониторинг в реальном времени

```bash
# Расширенная статистика по всем дискам каждые 2 секунды
iostat -dx 2

# Статистика в МБ с временными метками
iostat -dxmt 2

# Конкретный диск (например, nvme1n1)
iostat -dx 1 5 /dev/nvme1n1
```

### Диагностика I/O bottleneck

```bash
# 1. Проверка утилизации и задержек
iostat -x 1 3

# 2. Если await > 20 мс (HDD) или > 1 мс (SSD) — диск перегружен
# 3. Проверка avgqu-sz: очередь > 1-2 указывает на bottleneck

# 4. Сравнение с топ-процессами через iotop
sudo iotop -o
```

### Низкий iowait при высокой задержке

**Проблема:** `iowait` низкий, CPU свободен, но диск тормозит.

**Причина:** `iowait` показывает только время простоя CPU в ожидании I/O. Если процессы находятся в очереди на диск, но CPU переключается на другие задачи, `iowait` остаётся низким.

**Диагностика:**

```bash
# Ключевые метрики в iostat -x:
# - await > 20 мс (HDD) / > 1 мс (SSD) — высокая задержка
# - avgqu-sz > 1-2 — растущая очередь
# - %util может быть < 100% (не полная загрузка)
iostat -x 1
```

**Типичные сценарии:**

- **Burst-запись:** Writeback, логи, бэкапы
- **Смешанная read/write нагрузка:** Устройство не успевает обслуживать очередь равномерно
- **Медленный диск:** Высокая латентность устройства

> **Важно:** Смотрите на `await` и `avgqu-sz`, а не только на `iowait`. Подробно: [disk_io_troubleshooting.md](../Performance/disk_io_troubleshooting.md#низкий-iowait-при-высокой-задержке-диска).

### Сбор данных для анализа

```bash
# Запись в CSV для последующего анализа
iostat -dx -o JSON 2 300 > iostat_log.json

# Или классический формат
iostat -dx 2 60 > iostat_log.txt
```

### Интерпретация результатов

**Сценарий 1: Веб-сервер с медленными ответами**

- `%wa` в `top` > 20% → проверяем `iostat -x`
- `await` высокий, `%util` ~100% → диск не справляется
- Решение: SSD, RAID, оптимизация запросов

**Сценарий 2: База данных**

- Ожидаем IOPS > 1000, `await` < 1 мс
- `avgqu-sz` > 4 → очередь растёт
- Решение: NVMe, увеличение `iodepth`, кэширование

**Сценарий 3: Файловый сервер**

- Высокая пропускная способность (`wkB/s`)
- `avgrq-sz` большой → последовательная запись
- Норма: `%util` < 80%, `await` < 10 мс

## Дополнительная информация

### Связь с `iowait` и Load Average

Процессы в состоянии `uninterruptible sleep` (ожидание I/O) вносят вклад в `%wa` (`iowait`) и Load Average. Высокие `await` и `%util` в `iostat` коррелируют с ростом этих метрик.

**Диагностика:**

```bash
# Проверка iowait
top -bn1 | grep "Cpu(s)"

# Или через vmstat
vmstat 1 5

# Процессы в состоянии D (uninterruptible sleep)
ps aux | awk '$8 ~ /D/ {print}'
```

### Установка sysstat

| Дистрибутив | Команда |
| :--- | :--- |
| Ubuntu/Debian | `apt install sysstat` |
| CentOS/RHEL | `yum install sysstat` |
| Fedora | `dnf install sysstat` |
| Arch | `pacman -S sysstat` |

> **Примечание:** После установки может потребоваться включение сбора статистики в `/etc/default/sysstat`.
