# Диагностика файловых систем и дискового пространства

## Определения

- **Файловая система (Filesystem — ФС):** Способ организации, хранения и доступа к данным на носителе. Определяет структуру каталогов, метаданные и методы выделения блоков.
- **Блочное устройство (Block device):** Устройство хранения, которое читает и записывает данные блоками фиксированного размера (обычно 512 байт или 4 КБ). Примеры: жесткий диск (HDD), SSD, NVMe, RAID-массив.
- **Раздел (Partition):** Логическая часть блочного устройства, выделенная для отдельной ФС или swap. Представлен в таблице разделов (MBR или GPT).
- **Таблица разделов (Partition table):** Структура на диске, описывающая расположение разделов.
  - **MBR (Master Boot Record):** Устаревший формат, максимум 4 первичных раздела, размер раздела до 2 ТБ.
  - **GPT (GUID Partition Table):** Современный формат, поддерживает до 128 разделов, размер до 9,4 зеттабайт.
- **Индексный дескриптор (Inode):** Фундаментальная структура данных, хранящая метаинформацию о файле (права, владелец, размер, временные метки, указатели на блоки), кроме его имени.
- **`df` (disk free):** Утилита для отображения общего объема, используемого и доступного пространства в смонтированных ФС. Работает на уровне суперблока.
- **`du` (disk usage):** Утилита для оценки объема дискового пространства, занимаемого файлами или каталогами. Работает путем рекурсивного обхода.
- **`stat`:** Утилита для вывода подробной информации об Inode файла или параметрах файловой системы.
- **`lsblk` (list block devices):** Утилита для вывода иерархического списка блочных устройств (диски, разделы, LVM).
- **Разреженный файл (Sparse file):** Файл, который логически имеет большой размер, но физически занимает меньше места, так как «пустые» блоки (нулевые) не записываются на диск.
- **Резерв root (Reserved blocks):** Процент дискового пространства, зарезервированный для пользователя `root` (по умолчанию 5% в Ext4). Защищает ФС от полного заполнения обычными пользователями.
- **LVM (Logical Volume Manager):** Слой абстракции между блочными устройствами и ФС.
  - **PV (Physical Volume):** Физический диск или раздел, добавленный в LVM.
  - **VG (Volume Group):** Группа PV, образующая пул пространства.
  - **LV (Logical Volume):** Логический том в VG, на котором создается ФС.
  - **Thin Provisioning:** Технология выделения пространства по мере необходимости, без предварительного резервирования всего размера LV.
- **Снапшот (Snapshot):** Точка во времени состояния LV. Создается на основе COW (Copy-on-Write) и позволяет откатиться к предыдущему состоянию без удаления текущих данных.
- **Swap:** Раздел или файл, используемый как расширение оперативной памяти. Диагностика swap — часть анализа дискового пространства, так как swap-нагрузка влияет на общее состояние диска.

## Основные концепции

### Блочные устройства, разделы и таблицы разделов

Диагностика начинается с понимаения физической структуры хранения. Блочное устройство делится на разделы, каждый из которых может содержать отдельную ФС.

```bash
# Иерархия дисков и разделов
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,FSTYPE
# → NAME   SIZE TYPE  MOUNTPOINT FSTYPE
# → sda    931G disk
# → ├─sda1  512M part  /boot/efi  vfat
# → ├─sda2   20G part  /          ext4
# → └─sda1  100G part  /home      xfs
# → sdb    1.8T disk
# → └─sdb1  1.8T part              LVM2_member
```

**GPT vs MBR:** GPT является современным стандартом и поддерживает разделы >2 ТБ. Для диагностики целостности таблицы разделов используйте `gdisk` или `sgdisk`:

```bash
# Проверка GPT
sudo gdisk -l /dev/sda
# → GPT: present, found; using GPT
```

### Различия в механизмах подсчета: `df` против `du`

Данные этих утилит часто не совпадают из-за разного подхода к сбору информации:

1. **`df` (Disk Free):** Считывает метаданные из суперблока файловой системы. Это обеспечивает мгновенный результат, так как ядро постоянно обновляет счетчики свободных/занятых блоков. Отражает состояние всей ФС.
2. **`du` (Disk Usage):** Рекурсивно обходит каталоги и выполняет системный вызов `stat()` для каждого объекта, суммируя фактическое количество блоков. Это медленнее, но показывает распределение места по конкретным директориям.

### Причины расхождений (Discrepancy)

- **Удаленные, но открытые файлы (Deleted-but-open):** `du` не видит файл (его нет в каталоге), а `df` считает блоки занятыми (дескриптор открыт).
- **Разреженные файлы (Sparse files):** `du` показывает фактический размер на диске, в то время как другие инструменты могут показывать логический размер.
- **Точки монтирования:** `df` показывает статистику по каждой ФС отдельно. `du` по умолчанию переходит границы ФС (если не указан флаг `-x`).
- **Размер блока и фрагментация:** ФС выделяет место блоками (обычно 4 КБ). Даже файл в 1 байт займет 1 блок (4 КБ). При миллионах мелких файлов разница между "размером данных" и "занятым местом" становится критической.
- **Резерв root:** `df` включает зарезервированное пространство в используемое место. Обычные пользователи видят меньше свободного места, чем root.

### Механизм удалённых открытых файлов (Deleted-but-open)

Команда `rm` выполняет системный вызов `unlink()`, который удаляет только запись в каталоге (связь имени с Inode). Данные и Inode уничтожаются ядром только при выполнении двух условий:
1. **link count = 0** — на Inode больше нет жестких ссылок.
2. **Reference count = 0** — ни один процесс не держит файл открытым.

**Схема процесса:**
```text
каталог          inode          блоки на диске
/var/log/  --> app.log  -->  [блок1][блок2][блок3]
                ^
                | открытый дескриптор (FD)
                nginx (PID 1234, FD 7)

после rm (unlink):
каталог          inode          блоки на диске
/var/log/  --> (удалено) -->  [блок1][блок2][блок3]
                ^                    ^
                | FD (PID 1234)      | всё ещё занято!
```

**Почему `rm + touch` не работает для ротации:**
- `rm` удаляет ссылку на старый Inode.
- `touch` создает новый файл с **новым** Inode.
- Работающий процесс продолжает писать в старый Inode через открытый дескриптор.
- Место не освобождается, а новые логи пишутся в "никуда".

**Правильный способ — обнуление (Truncate):**
```bash
truncate -s 0 /path/to/log
# ИЛИ
> /path/to/log
```
Это обнуляет содержимое Inode на месте, не меняя его номер и не разрывая связь с открытыми дескрипторами.

### Диагностика нехватки Inodes

Лимит на количество файлов может закончиться раньше, чем место в гигабайтах.

- **Ext4 (Статическое выделение):** Количество Inode фиксируется при `mkfs`. По умолчанию: 1 Inode на 16 КБ.
- **XFS / Btrfs (Динамическое выделение):** Inode создаются по мере необходимости.

**Команды диагностики:**
```bash
# Проверка использования дескрипторов
df -ih
# → Filesystem     Inodes IUsed IFree IUse% Mounted on
# → /dev/sda1        3.2M  3.2M     0  100% /

# Поиск каталога с наибольшим числом файлов
find /var -xdev -printf '%h\n' | sort | uniq -c | sort -rn | head -20
# →  54321 /var/spool/postfix/maildrop
```

### Резерв root (Reserved Blocks)

В ФС семейства Ext (Ext2/3/4) по умолчанию резервируется 5% пространства для пользователя `root`. Это защищает систему от полного заполнения при переполнении диска обычными пользователями. Для диагностики:

```bash
# Проверка процента резерва
tune2fs -l /dev/sda2 | grep "Reserved block count"
# → Reserved block count:     262144
# → Reserved GDT blocks:      494
# → Reserved blocks per group:32768
```

Для временного получения дополнительного места при экстренном спасении можно обнулить резерв:

```bash
sudo tune2fs -m 0 /dev/sda2
# После очистки верните значение (1-5%)
sudo tune2fs -m 5 /dev/sda2
```

### LVM: логика работы и диагностика

LVM добавляет уровень абстракции между физическими дисками и ФС. Диагностика начинается с анализа пула физических томов (PV), группы томов (VG) и логических томов (LV).

```bash
# Физические тома
sudo pvs
# →   PV         VG     Fmt  Attr PSize   PFree
# →   /dev/sdb1  vg0    lvm2 a--  931.51g 500.00g

# Группа томов
sudo vgs
# →   VG   #PV #LV #SN Attr   VSize   VFree
# →   vg0    1   3   0 wz--n- 931.51g 500.00g

# Логические тома
sudo lvs
# →   LV   VG   Attr       LSize   Pool Origin Data%  Meta%
# →   root vg0  -wi-ao----  200.00g
# →   data vg0  -wi-ao----  300.00g
# →   snap vg0  Vwi-a-tz--  100.00g root   5.00
```

**Thin Provisioning:** LV может быть создан как "тонкий" том, который выделяет пространство по мере необходимости. Риск — переполнение пула при превышении фактического размера.

### Снапшоты

Снапшот LV создается на основе COW (Copy-on-Write). При изменении данных в оригинальном LV старые блоки копируются в область снапшота.

```bash
# Создание снапшота
sudo lvcreate --size 10G --snapshot --name snap_root /dev/vg0/root

# Откат к снапшоту (требует отмонтирования)
sudo lvconvert --merge /dev/vg0/snap_root
```

### Точки монтирования и опции

Опции монтирования влияют на диагностику. Например, `noatime` отключает запись времени доступа, снижая нагрузку на диск.

```bash
# Проверка опций монтирования
findmnt -o TARGET,OPTIONS,FSTYPE
# → TARGET  OPTIONS        FSTYPE
# → /       ro,relatime    ext4
# → /home   rw,noatime     xfs
```

## Инструментарий и практические сценарии

### План быстрой диагностики

```bash
# 1. Общее состояние и типы ФС
df -hT

# 2. Проверка Inodes
df -i

# 3. Анализ блочных устройств и разделов
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,FSTYPE,ROTA

# 4. Поиск крупнейших директорий (глубина 2 уровня, на одной ФС)
sudo du -xh --max-depth=2 / | sort -rh | head -20

# 5. Поиск файлов размером более 1 ГБ
find / -type f -size +1G -exec ls -lh {} \; 2>/dev/null

# 6. Поиск удаленных, но открытых файлов
sudo lsof +L1 2>/dev/null
```

### Анализ открытых файлов процесса

Если диск переполнен из-за работающего процесса:

```bash
# Найти PID процесса
PID=$(pgrep -f "nginx")

# Список открытых файлов и их размеров
sudo lsof -p $PID -s | awk '$5 == "REG" {print $7, $9}' | sort -n

# Список всех дескрипторов в /proc
ls -la /proc/$PID/fd/
```

### Диагностика через dmesg

Ошибки диска и ФС часто фиксируются в кольцевом буфере ядра. Анализ dmesg позволяет обнаружить аппаратные сбои и ошибки ввода-вывода до перехода ФС в read-only.

```bash
# Поиск ошибок EXT4, XFS, I/O
sudo dmesg -T | grep -Ei 'EXT4|XFS|BTRFS|I/O error|Buffer I/O|read-only|abort'
# → [Sat Sep 12 14:23:01 2026] EXT4-fs error (device sdc1): ext4_journal_check_start:83: Detected aborted journal
# → [Sat Sep 12 14:23:01 2026] Buffer I/O error on dev sdc1, logical block 123456, async page read
```

### Безопасная очистка (Rescue)

Подробные инструкции по восстановлению случайно удаленных данных см. в разделе **[Логическое восстановление данных](../../FileSystems/data_recovery.md)**. Краткие методы очистки:

1. **Обнуление блоков (если файл удален, но FD открыт):**
   ```bash
   # Позволяет освободить место без перезапуска процесса
   > /proc/$PID/fd/$FD
   ```
2. **Временное уменьшение резерва root (для Ext4):**
   ```bash
   # Получаем 5% свободного места для маневра
   tune2fs -m 0 /dev/sdX
   ```

### Работа с разреженными файлами

Разреженные файлы могут вводить в заблуждение при анализе места.

```bash
# Создание разреженного файла 10 ГБ
truncate -s 10G big_file

# Проверка stat
stat big_file
# → Size: 10737418240  Blocks: 0  IO Block: 4096 regular empty file
```
Утилита `du` корректно покажет `0` блоков, а `ls` покажет `10G`.

### Использование современных утилит (ncdu, gdu)

Для интерактивного анализа рекомендуется `ncdu`. Она быстрее и нагляднее стандартного `du`.

```bash
# Анализ с игнорированием других точек монтирования
ncdu -x /
```
`gdu` — аналогичный инструмент, написанный на Go, работает значительно быстрее на SSD и при больших объемах данных.

## Практические сценарии

### Ситуация: На диске есть место, но создать файл нельзя

1. **Исчерпание Inodes:** Проверьте `df -i`. Решение — удаление миллионов мелких файлов (кэши сессий, очереди почты).
2. **Резерв root:** При заполнении >95% (для Ext4) обычные пользователи блокируются.
3. **Дисковые квоты:** Проверьте `quota -u $USER`.
4. **Фрагментация (крайне редко):** В очень старых или специфических ФС может не быть непрерывного блока нужного размера.

### Ситуация: Диск переполнился мгновенно

1. **Утечка в логи:** Проверьте `/var/log` через `du -sh /var/log/* | sort -rh`.
2. **Core Dumps:** Проверьте наличие файлов `core.*` в рабочих директориях приложений.
3. **Бесконечный цикл записи:** Проверьте `iotop`, чтобы найти процесс, который пишет больше всех.

### Ситуация: Файловая система перешла в read-only

После аппаратной ошибки или сбоя журнала ФС может автоматически переключиться в режим `read-only`. Симптом — невозможность создания или изменения файлов с ошибкой `Read-only file system`.

```bash
# 1. Проверка опций монтирования
findmnt -no TARGET,OPTIONS /
# → / ro,relatime

# 2. Проверка флага на уровне блочного устройства
sudo blockdev --getro /dev/sda2
# → 1 (заблокирован) или 0 (разблокирован)

# 3. Анализ логов ядра
sudo dmesg -T | grep -Ei 'EXT4|XFS|I/O error|read-only|abort'
```

Если причина устранена (заменен кабель, восстановлен RAID), перемонтируйте ФС в RW:

```bash
sudo mount -o remount,rw /
```

### Ситуация: Диагностика LVM и расширение тома

```bash
# Проверка свободного места в VG
sudo vgs
# → vg0   VFree 500.00g

# Расширение LV на 20 ГБ
sudo lvextend -L +20G /dev/vg0/data
sudo resize2fs /dev/vg0/data  # для ext4
# ИЛИ
sudo xfs_growfs /mnt/data    # для XFS (онлайн)
```

### Ситуация: Анализ swap и давления на память

```bash
# Статус swap
swapon --show
# → NAME      TYPE  SIZE   USED PRIO
# → /dev/sda5 partition 8G 2.1G -2

# Проверка активности swap
sar -W 1 5
# → kbswpfree  kbswpused  %swpused  kbswpcad  %swpcad

# Временное отключение swap (для диагностики)
sudo swapoff -a
```

## Устранение неполадок

| Ошибка / Симптом | Причина | Диагностика | Решение |
|:---|:---|:---|:---|
| `df` показывает 100%, `du` показывает 50% | Удаленные, но открытые файлы | `sudo lsof +L1` | Перезапуск процесса или truncate через `/proc/PID/fd/FD` |
| `No space left on device`, но `df -h` показывает место | Исчерпание Inodes | `df -i` | Удаление миллионов мелких файлов |
| `Read-only file system` | Аппаратная ошибка I/O или aborted journal | `dmesg`, `blockdev --getro` | Замена кабеля/диска, `mount -o remount,rw` |
| `df` и `du` расходятся на несколько ГБ | Резерв root или sparse-файлы | `tune2fs -l`, `du --apparent-size` | Норма для Ext4; проверка sparse |
| `Too many open files` в логах приложения | Утечка дескрипторов | `lsof -p $PID \| wc -l`, `cat /proc/$PID/limits` | Увеличение `nofile` в systemd/ulimit |
| Файл 0 байт, но `du` показывает гигабайты | Разреженный файл (sparse) | `du --apparent-size` vs `du` | Нормальное поведение sparse-файлов |
| `Input/output error` при чтении | Аппаратный сбой диска | `dmesg`, `smartctl` | Замена диска, восстановление данных с бэкапа |
| `Reserved blocks` исчерпаны для пользователя | >95% заполнения Ext4 | `df -h` | Временное `tune2fs -m 0`, затем очистка |

## Рекомендации (Best Practices)

1. **Мониторинг:** Настройте алерты на `df -h` (>80%) и `df -i` (>80%). Используйте `node_exporter` для сбора метрик `node_filesystem_*`.
2. **Логирование:** Настройте ротацию логов через `logrotate` или `journald` с ограничением размера. Мониторьте `/var/log` независимо.
3. **Резервное копирование:** Перед операциями с LVM (удаление VG, уменьшение LV) создавайте снапшоты. Тестируйте восстановление.
4. **Thin Provisioning:** Используйте с осторожностью. Настройте `lvm.conf` с `error_when_full = 1`, чтобы избежать потери данных при переполнении пула.
5. **SMART-мониторинг:** Включайте `smartd` для ежедневной проверки дисков. Алерты на `FAILED_NOW` или `Pre-fail` атрибуты.
6. **ФС и Journaling:** Для критичных данных используйте журналируемые ФС (ext4, XFS). При сбоях journaling минимизирует время восстановления.
