# ionice — управление приоритетами ввода-вывода

## Определения

- **ionice:** Утилита командной строки для назначения и изменения приоритета операций ввода-вывода (I/O) для конкретных процессов в Linux. Она позволяет операционной системе более эффективно распределять дисковые ресурсы между критически важными приложениями и фоновыми задачами. Входит в состав пакета `util-linux`, поэтому доступна в большинстве дистрибутивов по умолчанию.
- **ioprio (I/O Priority):** Внутренний приоритет дисковых операций процесса в ядре Linux. Хранится в `task_struct` потока и передается через вызов `ioprio_set(2)`. Состоит из класса (3 бита) и уровня (5 бит), что дает 8 уровней внутри классов Best-effort и Realtime.
- **Классы планирования I/O:**
    - **Idle (Класс 3):** Самый низкий приоритет. Процесс получает доступ к диску только в те периоды, когда нет активных запросов от любых других процессов. Идеально подходит для фоновых задач, таких как создание бэкапов, индексация поиска или обновление баз данных антивирусов.
    - **Best-effort (Класс 2):** Стандартный класс для большинства процессов. Содержит 8 уровней приоритета (0–7, где 0 — наивысший). Если уровень не указан явно, ядро вычисляет его на основе значения `nice` процесса: `prio = (nice + 20) / 5`.
    - **Realtime (Класс 1):** Наивысший приоритет. Процесс получает доступ к диску немедленно, как только у него появляются данные для записи или чтения, потенциально вытесняя все остальные процессы. Требует прав суперпользователя (`root`) или привилегии `CAP_SYS_NICE`.

## Основные концепции

`ionice` взаимодействует с блочным слоем ядра и напрямую зависит от выбранного планировщика ввода-вывода. Основная цель использования — минимизация влияния тяжелых операций ввода-вывода на интерактивность системы или производительность высоконагруженных сервисов (например, СУБД).

### Внутренний механизм

1. **Системный вызов `ioprio_set(2)`:** Утилита `ionice` вызывает этот syscall для установки класса и приоритета в `task->ioprio`. Значение кодируется так: биты 0–2 — класс, биты 3–7 — уровень (для Best-effort и Realtime).
2. **Наследование при `fork()`:** Дочерний процесс наследует приоритет I/O родителя. Это позволяет обернуть скрипт в `ionice -c 3` и быть уверенным, что все дочерние процессы (tar, rsync, gzip) унаследуют класс Idle.
3. **Влияние на kernel threads:** Потоки ядра (`kworker`, `kthreadd`) имеют собственные приоритеты I/O и не наследуют `ionice` пользовательских процессов. Writeback-потоки (`flush-*`) управляются ядром отдельно.
4. **Планировщики и классы:**
   - **BFQ / BFQ-mq:** Читает `task->ioprio` для каждого запроса и строит отдельную очередь на процесс. Полная поддержка всех 3 классов и 8 уровней.
   - **mq-deadline:** Поддерживает классы, но уровни 0–7 часто обрабатываются упрощенно или игнорируются. Это планировщик по умолчанию во многих современных серверных дистрибутивах (Ubuntu 22.04+, RHEL 9+).
   - **Kyber / none:** Практически полностью игнорируют `task->ioprio`. Эти планировщики ориентированы на сверхбыстрые NVMe-устройства, где задержки настолько малы, что сложная логика очередей только увеличивает накладные расходы на CPU.

**Проверка планировщика для диска `sda`:**
```bash
cat /sys/block/sda/queue/scheduler
# → [mq-deadline] bfq none
# Скобки указывают на текущий активный планировщик.
```

### Взаимодействие с cgroups v2

В системах с cgroups v2 контроллер `io` может **переопределять** настройки `ionice`:

- **`io.max`:** Жесткие лимиты (BPS/IOPS) имеют приоритет над `ionice`. Если процесс с `ionice -c 1` попадает в cgroup с `wiops=10`, он будет ограничен лимитом.
- **`io.weight`:** Относительный вес (1–10000, дефолт 100) влияет на распределение полосы пропускания внутри cgroup. Процессы с `ionice -c 3` внутри cgroup с высоким `io.weight` все равно будут ждать свободного диска.
- **Делегирование:** Для работы `ionice` внутри контейнера родительский slice/systemd должен иметь `Delegate=yes`, иначе запись в cgroup будет отклонена.

### Нюансы для SSD и NVMe

Для современных NVMe-накопителей с поддержкой Multi-queue классический механизм `ionice` становится менее эффективным, так как задержки операций составляют едицы–десятки микросекунд и разница между классами визуализируется слабо. В таких системах рекомендуется использовать **cgroups v2** и контроллер `io` для управления весами (`io.weight`) или лимитами.

## Практические сценарии

### Выполнение тяжелых фоновых задач

Сценарии, когда нужно выполнить ресурсоемкую операцию, не снижая отзывчивость системы.

```bash
# Запуск синхронизации файлов с минимальным приоритетом (Idle)
ionice -c 3 rsync -a /var/log /mnt/backup

# Запуск архивации логов с низким приоритетом в классе Best-effort
ionice -c 2 -n 7 tar -czf logs.tar.gz /var/log/nginx/*.log

# Фоновый парсинг логов через cron: низкий CPU + низкий I/O
nice -n 19 ionice -c 3 /opt/scripts/parse-logs.sh > /var/log/parse.log 2>&1
```

### Оптимизация производительности СУБД

Обеспечение «быстрого пути» для процессов базы данных.

```bash
# Назначение высшего приоритета Best-effort для процессов PostgreSQL
sudo ionice -c 2 -n 0 -p $(pgrep -f postgres)

# Перевод критически важного процесса в Realtime (использовать с осторожностью!)
sudo ionice -c 1 -n 4 -p 1234
# ВНИМАНИЕ: Ошибка в приложении с RT-приоритетом может привести к «голоданию» 
# системных процессов и зависанию всей ОС.
```

### Systemd-юниты (production pattern)

Для production-сервисов предпочтительнее задавать приоритеты в unit-файле, а не через командную строку. Это гарантирует, что приоритет будет применен при старте и сохранен при перезапуске:

```ini
[Service]
ExecStart=/usr/bin/etcd --config-file /etc/etcd/etcd.conf.yml
Nice=-10
IOSchedulingClass=realtime
IOSchedulingPriority=0
```

Применить: `sudo systemctl daemon-reload && sudo systemctl restart etcd`.

**Важно:** Директивы `IOSchedulingClass=` и `IOSchedulingPriority=` работают только если systemd запущен с поддержкой cgroup v2 и делегировал контроллер `io`.

### Контейнеризация (Docker / LXC)

По умолчанию контейнеры не имеют доступа к `ioprio_set`:

```bash
# Запуск контейнера с возможностью изменения I/O-приоритета
docker run --cap-add=SYS_NICE --name myapp -d myimage

# Полный доступ (как hostPID для процессов)
docker run --privileged --name myapp -d myimage

# Проверка внутри контейнера
docker exec myapp ionice -c 2 -n 0 -p 1
```

Без `--cap-add=SYS_NICE` попытка смены класса завершится ошибкой `Operation not permitted`.

### LVM: миграция дисков

При замене физического диска в LVM операция `pvmove` создает интенсивную запись. Чтобы не мешать приложениям, используйте фоновый режим с `ionice`:

```bash
# Фоновый миграция с минимальным приоритетом I/O
sudo ionice -c 3 pvmove -b /dev/sdb
```

Подробнее см. [Замена физического диска в LVM](../../FileSystems/LVM/operations/lvm_disk_replacement.md).

### Просмотр и проверка настроек

```bash
# Проверить приоритет I/O конкретного процесса по PID
ionice -p 5678
# → best-effort: prio 4

# Комбинированный запуск (CPU Nice + I/O Nice) для максимальной изоляции
nice -n 19 ionice -c 3 ./my_heavy_script.sh

# В systemd-сервисе проверить delegation
systemctl show myservice -p IOSchedulingClass,IOSchedulingPriority
```

## Установка

`ionice` входит в состав пакета `util-linux` и доступен практически во всех дистрибутивах по умолчанию. Если утилита отсутствует:

```bash
# Debian / Ubuntu
sudo apt install util-linux

# RHEL / CentOS / Fedora
sudo dnf install util-linux

# Arch Linux
sudo pacman -S util-linux
```

## Типичные ошибки и диагностика

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `Operation not permitted` | Нет `CAP_SYS_NICE` или `root` | Запустите с `sudo` или добавьте capability |
| `ionice` не влияет на скорость | Активный планировщик `none` или `kyber` | Переключите на `bfq` или `mq-deadline` |
| Приоритет не сохраняется у детей | Процесс явно вызывает `ioprio_set` с дефолтом | Проверьте код приложения или обертки |
| В контейнере не работает | Нет `--cap-add=SYS_NICE` | Добавьте capability или используйте `--privileged` |
| Сетевые ФС (NFS/CIFS) | Управление очередями на стороне сервера | `ionice` не помогает; настройте сервер хранилища |
| `mdadm` RAID игнорирует приоритет | Блоки собираются на уровне массива | Используйте `--bitmap` или снижайте приоритет на уровне массива |
| Приоритет выше, но диск занят | `io.max` в cgroup переопределяет `ionice` | Проверьте `cat /sys/fs/cgroup/.../io.max` |
| Высокое `iowait` у RT-процесса | Реальный дефицит диска, а не приоритет | Проверьте `iostat -xz 1`, `await`, `%util` |

## Мониторинг во время использования ionice

```bash
# В отдельном терминале
iostat -x 1 5          # Дисковая подсистема (%util, await, aqu-sz)
iotop -oP              # Только активные процессы (hotkey 'i' меняет ionice на лету)
pidstat -d 1           # Дисковая активность по процессам
vmstat 1 5             # Сводная статистика (r, b, si, so)

# Проверка приоритетов cgroup
cat /sys/fs/cgroup/system.slice/postgres.service/io.weight
cat /sys/fs/cgroup/system.slice/postgres.service/io.max

# Для NVMe
sudo nvme smart-log /dev/nvme0 | grep -E 'Temperature|Percentage Used'

# Для PSI
cat /proc/pressure/io
```

## Дополнительная информация

### Ограничения и особенности

1.  **Сетевые ФС:** `ionice` не влияет на приоритеты при работе с NFS, CIFS или iSCSI, так как управление очередями происходит на стороне сервера хранения.
2.  **Программный RAID:** При использовании `mdadm` настройки `ionice` для процессов могут игнорироваться на уровне сборки блоков.
3.  **Контейнеры:** Для использования `ionice` внутри контейнера Docker необходимо добавить привилегию `--cap-add=SYS_NICE`. Без неё попытка смены класса завершится ошибкой `Operation not permitted`.
4.  **cgroups v2 vs ionice:** Если в cgroup задан `io.max`, то `ionice` не сможет превысить этот лимит. `ionice` работает только в рамках разрешенной квоты.
5.  **Планировщики `none` / `kyber`:** На этих планировщиках `ionice` игнорируется. Используйте cgroups v2 (`io.weight`) для приоритизации.

### Рекомендации по чистоте эксперимента

1.  **Запуск от root:** Для получения полной статистики по всем процессам используйте `sudo`. Без привилегий `ionice` может не изменить приоритет чужих процессов.
2.  **Идентификация планировщика:** Всегда проверяйте активный планировщик через `/sys/block/<dev>/queue/scheduler`. Если активен `none` или `kyber` — `ionice` не сработает.
3.  **Корреляция с `iostat`:** Всегда сверяйте вывод `ionice` с `iostat -xz 1`. Если приоритет повышен, но `await` не снижается — проблема в планировщике или в самом устройстве.
4.  **Серийный номер диска:** Для точной идентификации устройства используйте `lsblk -o NAME,SERIAL,SIZE,ROTA` и сверяйте с `iostat`.
5.  **Systemd delegation:** В systemd-сервисах проверяйте, что родительский slice делегирует контроллер `io`: `systemctl show -.slice -p Delegate`.
