# `ionice` — управление приоритетами ввода-вывода

## Определения

- **`ionice`:** Утилита командной строки для назначения и изменения приоритета операций ввода-вывода (I/O) для конкретных процессов в Linux.
- **Классы планирования I/O:**
  - **Idle (Класс 3):** Самый низкий приоритет. Процесс получает доступ к диску только в периоды отсутствия запросов от других классов. Идеально для фоновых задач (бэкапы, индексация).
  - **Best-effort (Класс 2):** Стандартный класс для большинства процессов. Содержит 8 уровней приоритета (0–7, где 0 — высший). Если уровень не указан, ядро вычисляет его на основе значения `nice` процесса.
  - **Realtime (Класс 1):** Наивысший приоритет. Процесс получает диск немедленно при наличии данных для записи/чтения. Требует прав суперпользователя или привилегии `CAP_SYS_NICE`.

## Основные концепции

`ionice` работает на уровне планировщика ввода-вывода ядра. Его основная цель — предотвратить "захват" дискового ресурса тяжелыми фоновыми операциями, что критично для интерактивных систем и баз данных.

### Взаимосвязь с планировщиками (Критично)

Эффективность `ionice` напрямую зависит от активного планировщика I/O в ядре:
- **`BFQ` (Budget Fair Queuing):** Обеспечивает полную поддержку всех классов `ionice`. Рекомендуется для HDD и интерактивных десктопных систем.
- **`CFQ` (Completely Fair Queuing):** Классический планировщик с полной поддержкой `ionice` (удален в новых ядрах в пользу Multi-queue).
- **`mq-deadline`:** Поддерживает классы, но приоритеты внутри классов могут игнорироваться. По умолчанию во многих современных дистрибутивах.
- **`none` / `kyber`:** Практически игнорируют настройки `ionice`. Для SSD/NVMe приоритезация часто переносится на уровень cgroups.

**Проверка планировщика для диска `sda`:**
```bash
cat /sys/block/sda/queue/scheduler
# → [mq-deadline] kyber bfq none
# Настройки ionice наиболее эффективны, если выбран bfq
```

### Нюансы для SSD и NVMe

На современных быстрых накопителях задержки настолько малы, что классическое разделение по времени (timeslices), используемое `ionice`, становится неэффективным. Для NVMe-устройств с поддержкой Multi-queue рекомендуется использовать **cgroups v2** и контроллер `io` (`io.weight`).

## Практические сценарии

### Запуск фоновых задач

Сценарии, когда нужно выполнить тяжелую работу, не "подвешивая" систему.

```bash
# Запуск синхронизации файлов с минимальным приоритетом (Idle)
ionice -c 3 rsync -a /var/log /mnt/backup

# Запуск архивации с низким приоритетом в классе Best-effort
ionice -c 2 -n 7 tar -czf backup.tar.gz /home/user/data
```

### Приоритизация работающей базы данных

```bash
# Назначение высшего приоритета Best-effort для PostgreSQL
sudo ionice -c 2 -n 0 -p $(pgrep -f postgres)

# Перевод критичного процесса в Realtime (использовать с осторожностью!)
sudo ionice -c 1 -n 4 -p 1234
```

### Просмотр текущих настроек

```bash
# Проверить приоритет конкретного процесса
ionice -p 5678
# → best-effort: prio 4
```

### Комбинированный подход (CPU + I/O)

Для максимальной изоляции фонового процесса используйте `nice` и `ionice` вместе.

```bash
# Полная изоляция процесса архивации
nice -n 19 ionice -c 3 backup_script.sh
```

## Дополнительная информация

### Выбор класса и уровня

| Сценарий | Класс | Уровень | Комментарий |
| :--- | :--- | :--- | :--- |
| **Бэкап / Логи** | 3 (Idle) | — | Не мешает ничему, кроме другого Idle |
| **Обычный софт** | 2 (Best-effort) | 4 | Стандартное значение для всех процессов |
| **СУБД (Prod)** | 2 (Best-effort) | 0–2 | Гарантирует "быстрый путь" к контроллеру |
| **RT системы** | 1 (Realtime) | 0–7 | Может вызвать зависание ОС при ошибке в коде приложения |

### Современная альтернатива: cgroups v2

В современных инфраструктурах (Docker, Kubernetes) `ionice` заменяется настройками ресурсов в cgroups. Это позволяет ограничивать не только приоритет, но и абсолютные лимиты (IOPS, BPS).

```bash
# Пример установки веса I/O через cgroup v2 (уровень 1-10000)
echo "8:0 weight=100" > /sys/fs/cgroup/user.slice/io.weight
```

### Ограничения

1.  **Протоколы:** `ionice` часто не работает для сетевых ФС (NFS, CIFS) и некоторых видов программных RAID.
2.  **Зависания:** Использование `Realtime` может привести к тому, что системные процессы (например, журналирование ФС) не получат доступ к диску, что вызовет Kernel Panic или зависание.
3.  **Контейнеры:** Требуется `--cap-add=SYS_NICE` для изменения приоритетов внутри контейнера.
