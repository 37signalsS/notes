# `dmesg` — Просмотр сообщений ядра

## Определения

**`dmesg`** (сокращение от _display message_ или _driver message_) — утилита командной строки для просмотра и управления сообщениями из **кольцевого буфера ядра**. Незаменима для диагностики проблем с оборудованием, драйверами и ядром, особенно во время и сразу после загрузки системы.

**Кольцевой буфер ядра (kernel ring buffer)** — структура данных фиксированного размера в памяти ядра для хранения логов. При заполнении новые сообщения перезаписывают самые старые, обеспечивая сбор логов на ранних этапах загрузки.

## Основные концепции

### Кольцевой буфер ядра

Кольцевой буфер — это структура данных фиксированного размера в памяти ядра, где хранятся логи. Когда буфер заполняется, новые сообщения начинают перезаписывать самые старые. Это обеспечивает сбор логов даже на самых ранних этапах загрузки системы.

**Размер буфера по умолчанию:** зависит от дистрибутива и конфигурации ядра (обычно 256 КБ – 2 МБ). Размер можно изменить через параметр ядра `log_buf_len`.

### Уровни и источники сообщений

- **Уровень (level):** Определяет важность сообщения. Стандартные уровни включают `emerg`, `alert`, `crit`, `err`, `warn`, `notice`, `info`, `debug`.
- **Источник (facility):** Указывает на подсистему ядра, сгенерировавшую сообщение, например `kern`, `user`, `daemon`, `auth`.

Полный список уровней (от критического к отладочному):

| Уровень | Число | Описание |
|---------|-------|----------|
| `emerg` | 0 | Система неработоспособна |
| `alert` | 1 | Требуется немедленное действие |
| `crit` | 2 | Критические условия |
| `err` | 3 | Условия ошибки |
| `warn` | 4 | Предупреждения |
| `notice` | 5 | Нормальные, но значимые события |
| `info` | 6 | Информационные сообщения |
| `debug` | 7 | Отладочные сообщения |

Основные источники: `kern`, `user`, `mail`, `daemon`, `auth`, `syslog`, `lpr`, `news`.

### Временные метки

`dmesg` поддерживает несколько форматов отображения времени:

- **Без флага:** Время в секундах с момента загрузки ядра (например, `[ 123.456789]`)
- **`-T` (ctime):** Читаемый формат с датой и временем (например, `Mon Jan 15 10:30:45 2024`)
- **`-t` (delta):** Время относительно предыдущего сообщения
- **`-d` (delta):** Дельта времени с точностью до микросекунд
- **`-x` (decode):** Отображение источника и уровня в виде префиксов

> **Важно:** Флаг `-T` требует, чтобы `systemd-journald` или `rsyslog` синхронизировали часы ядра с системным временем. В системах без `systemd` может отображаться некорректное время.

### Интеграция с `systemd-journald`

В современных системах с `systemd` логи ядра также собираются в [`systemd-journald`](../../SystemAdministration/Logging/journald.md) и доступны через команду [`journalctl -k`](../Logging/journalctl.md#логи-ядра-аналог-dmesg) или `journalctl --dmesg`. [`journalctl`](../Logging/journalctl.md) предоставляет более мощные средства для фильтрации, но `dmesg` остается быстрым инструментом для оперативной диагностики, особенно в окружениях, где `journald` недоступен (например, в `initramfs`).

### Интерфейс `/proc/kmsg`

Кольцевой буфер ядра также доступен через виртуальный файл `/proc/kmsg`. Этот файл предоставляет прямой доступ к сообщениям ядра в реальном времени:

```bash
# Чтение сообщений из /proc/kmsg (требует root)
sudo cat /proc/kmsg
```

**Ограничения:**

- Одновременно читать `/proc/kmsg` может только один процесс
- Чтение файла может мешать работе системных демонов логирования
- Для большинства задач используйте `dmesg` вместо прямого чтения `/proc/kmsg`

## Практические сценарии

### Базовый просмотр логов

```bash
# Вывод с постраничной навигацией
dmesg | less

# Вывод с читаемым форматом времени и раскрашиванием
dmesg -T -H
```

### Мониторинг в реальном времени

Эта команда работает аналогично `tail -f`, позволяя отслеживать новые сообщения ядра в реальном времени.

```bash
dmesg --follow # или dmesg -w
```

### Фильтрация вывода

- **По содержимому (аналог `grep`):**

    ```bash
    # Поиск сообщений, связанных с USB
    dmesg | grep -i usb
    ```

- **По уровню важности:**

    ```bash
    # Показать только ошибки и критические сообщения
    dmesg --level=err,crit
    ```

    _Доступные уровни: `emerg`, `alert`, `crit`, `err`, `warn`, `notice`, `info`, `debug`._

- **По источнику (подсистеме):**

    ```bash
    # Показать сообщения, относящиеся только к процессам аутентификации
    dmesg --facility=auth
    ```

    _Основные источники: `kern`, `user`, `mail`, `daemon`, `auth`, `syslog`, `lpr`, `news`._

- **Комбинация флагов для удобного анализа:**

    ```bash
    # Человекочитаемый вывод (-H), отображение времени (-T) и источника/уровня (-x)
    dmesg -HTx | less
    ```

### Управление буфером

```bash
# Очистить кольцевой буфер (требует прав root)
# Полезно перед отладкой для изоляции новых сообщений.
sudo dmesg -C

# Посмотреть текущий размер буфера
dmesg --buffer-size
```

### Диагностика OOM Killer

**OOM Killer (Out Of Memory Killer)** — механизм ядра, который принудительно завершает процессы при нехватке оперативной памяти. Сообщения об этом записываются в кольцевой буфер.

```bash
# Поиск сообщений об OOM Killer
dmesg -T | grep -i "oom\|killed process"

# Поиск процессов, убитых из-за нехватки памяти
dmesg -T | grep -i "out of memory"

# Детальная информация об OOM-событии
dmesg -T | grep -A 20 "Out of memory"
```

**Типичный вывод OOM Killer:**

```text
[12345.678901] Out of memory: Killed process 1234 (java) total-vm:8048576kB, anon-rss:7340032kB, file-rss:0kB
[12345.678902] oom_reaper: reaped process 1234 (java), now anon-rss:0kB, file-rss:0kB
```

**Поля в сообщении:**

- `total-vm`: Общий объём виртуальной памяти процесса
- `anon-rss`: Объём анонимной памяти (heap, стек)
- `file-rss`: Объём памяти, отображённой из файлов (mapped files)

**Что делать при OOM:**

1. **Идентифицировать процесс:** По имени и PID в сообщении
2. **Проверить лимиты памяти:** [`ulimit -a`](../../Core/processes/limits.md), cgroups, Docker/Kubernetes limits
3. **Анализ потребления:** Использовать [`htop`](../Processes/htop.md), [`ps`](../Processes/ps.md), [`smem`](../Memory/smem.md)
4. **Настроить swap:** Временно увеличить swap-пространство или добавить [`zswap`](../../Core/memory/swap_management.md)
5. **Оптимизировать приложение:** Уменьшить потребление памяти (heap size, кэши)

> **См. также:** [OOM Killer в Kubernetes](../../../Kubernetes/Troubleshooting/Common_Errors/oomkilled_pods.md), [Управление памятью процессов](../../Core/processes/limits.md)

## Дополнительная информация

### Расшифровка типичных ошибок ядра

#### Ошибка `__ratelimit: ... msgs suppressed`

Эта запись означает, что ядро проигнорировало некоторое количество однотипных сообщений, чтобы предотвратить переполнение логов (флуд). Сама по себе она не является ошибкой, но указывает на наличие основной проблемы, которая генерирует слишком много событий за короткое время.

**Что делать:**

1. Найдите источник флуда, проанализировав сообщения, предшествующие `__ratelimit`.
2. Изучите конфигурацию приложения или драйвера, вызывающего чрезмерное логирование, и при необходимости уменьшите уровень детализации логов.

#### Ошибка `unreachable code reached`

Это критическая ошибка, которая указывает на то, что ядро попыталось выполнить код, который логически не должен быть достижим. Частые причины:

- Ошибка в коде ядра или модуля.
- Несовместимость драйверов или конфликт между ними.
- Повреждение памяти.

**Что делать:**

1. Проверьте список загруженных модулей (`lsmod`) на предмет недавних изменений или наличия сторонних драйверов.
2. Убедитесь, что версия ядра и драйверов совместимы, особенно после обновлений.
3. Если проблема воспроизводится, попробуйте откатить последние изменения (обновление ядра, установка ПО) и сообщите об ошибке разработчикам дистрибутива или соответствующего модуля.

### Типичные сообщения об ошибках оборудования

#### Ошибки диска / SATA / NVMe

```text
[12345.678901] ata1.00: exception Emask 0x0 SAct 0x0 SErr 0x0 action 0x6 frozen
[12345.678902] ata1.00: failed command: WRITE FPDMA
[12345.678903] blk_update_request: I/O error, dev sda, sector 12345678
```

**Диагноз:** Проблемы с диском или SATA-кабелем.

**Что делать:**

1. Проверить SMART диска: [`smartctl -a /dev/sda`](../Hardware/smartctl.md)
2. Заменить SATA-кабель или проверить подключение
3. Проверить логи на предмет bad sectors: `dmesg | grep -i "reallocated\|pending\|uncorrectable"`

#### Ошибки оперативной памяти (ECC)

```text
[12345.678901] EDAC MC0: 1 CE memory read error
[12345.678902] EDAC MC0: 1 UE memory read error
```

**Диагноз:**

- `CE` (Correctable Error) — исправимая ошибка, ECC исправил автоматически
- `UE` (Uncorrectable Error) — неисправимая ошибка, возможна паника ядра

**Что делать:**

1. Запустить тест памяти: `memtest86+`
2. Проверить логи EDAC: `grep -i "edac" /var/log/mcelog`
3. Заменить неисправный модуль RAM

#### Ошибки PCIe / драйверов

```text
[12345.678901] AER: PCIe Bus Error: severity=Corrected, type=Physical Layer
[12345.678902] pcieport 0000:00:1c.0:   device [8086:xxxx] error status = 0x00000010
```

**Диагноз:** Проблемы с PCIe-устройством или драйвером.

**Что делать:**

1. Обновить прошивку BIOS/UEFI
2. Обновить драйверы устройства
3. Проверить физическое подключение устройства

#### Thermal throttling (троттлинг процессора)

```text
[12345.678901] Thermal zone ID exceeded temperature limit
[12345.678902] CPU0: Package temperature above threshold, cpu clock throttled
```

**Диагноз:** Перегрев процессора, включено принудительное снижение частоты.

**Что делать:**

1. Проверить температуру: [`sensors`](../Hardware/hardware_listing.md#мониторинг-температуры)
2. Очистить систему охлаждения, заменить термопасту
3. Проверить работу вентиляторов

### Настройка размера буфера ядра

Размер кольцевого буфера задаётся параметром ядра `log_buf_len` и может быть изменён:

**Временное изменение (до перезагрузки):**

```bash
# Не поддерживается всеми ядрами, требует перезагрузки
sudo dmesg -s 16777216  # 16 МБ (работает не во всех версиях)
```

**Постоянное изменение (через параметры загрузки):**

Добавить в загрузчик (GRUB):

```text
log_buf_len=16M
```

1. Отредактировать `/etc/default/grub`:
   ```bash
   GRUB_CMDLINE_LINUX="log_buf_len=16M"
   ```
2. Обновить конфигурацию GRUB:
   ```bash
   sudo update-grub  # Debian/Ubuntu
   sudo grub2-mkconfig -o /boot/grub2/grub.cfg  # RHEL/CentOS
   ```
3. Перезагрузиться

**Проверка текущего размера:**

```bash
dmesg --buffer-size
# или
grep log_buf_len /proc/cmdline
```

### Параметры ядра, связанные с логированием

| Параметр | Описание |
|----------|----------|
| `log_buf_len=N` | Размер буфера ядра (N = 128K, 256K, 1M, 2M, 4M, 8M, 16M) |
| `loglevel=N` | Уровень логирования для консоли (0-8, по умолчанию 4) |
| `quiet` | Скрыть большинство сообщений при загрузке |
| `debug` | Включить отладочные сообщения ядра |
| `earlyprintk` | Включить ранний вывод через консоль (для отладки загрузки) |

> **См. также:** [Настройка параметров ядра (sysctl)](../../Core/kernel/sysctl.md), [Процесс загрузки ядра](../../Core/kernel/boot_process.md)
