# dmesg — Просмотр сообщений ядра

## Определения

**`dmesg`** (display message) — системная утилита командной строки, предназначенная для вывода и управления сообщениями из **кольцевого буфера ядра** (kernel ring buffer). Она является основным инструментом для низкоуровневой диагностики операционной системы, позволяя анализировать события, происходящие до старта пользовательских процессов и демонов логирования.

**Кольцевой буфер ядра** — специализированная область памяти фиксированного размера, куда ядро Linux записывает сообщения о своем состоянии, обнаруженном оборудовании, загрузке драйверов и критических ошибках.

## Базовые концепции

### Механизм кольцевого буфера

Кольцевой буфер (Ring Buffer) работает по принципу FIFO с перезаписью: когда выделенный объем памяти заполняется, новые сообщения начинают записываться поверх самых старых. Это гарантирует, что в памяти всегда хранятся последние диагностические данные, не вызывая утечек памяти при длительной работе системы.

*   **Размер буфера:** По умолчанию составляет от 256 КБ до 16 МБ в зависимости от архитектуры и конфигурации.
*   **Настройка размера:** Изменяется через параметр загрузки ядра `log_buf_len` (например, `log_buf_len=1M` в конфигурации GRUB) или через `CONFIG_LOG_BUF_SHIFT` при компиляции ядра.

### Интерфейсы доступа

Существует несколько способов взаимодействия с сообщениями ядра:
1.  **`/dev/kmsg`:** Современный структурированный интерфейс. Предоставляет доступ к метаданным (уровни, метки времени, caller ID). Рекомендуется для использования современными утилитами.
2.  **`/proc/kmsg`:** Устаревший интерфейс, работающий по принципу «одного читателя». Если процесс (например, `rsyslog`) читает из этого файла, данные изымаются, и другие читатели их не увидят.
3.  **Системный вызов `syslog(2)`:** Традиционный программный интерфейс для чтения буфера.

### Уровни важности и источники

Каждое сообщение классифицируется по двум признакам: **Level** (уровень критичности) и **Facility** (подсистема).

| Уровень (Level) | Значение | Описание |
| :--- | :--- | :--- |
| `emerg` | 0 | Система неработоспособна (Emergency) |
| `alert` | 1 | Требуется немедленное действие (Alert) |
| `crit` | 2 | Критическая ошибка (Critical) |
| `err` | 3 | Ошибка выполнения (Error) |
| `warn` | 4 | Предупреждение (Warning) |
| `notice` | 5 | Значимое штатное событие (Notice) |
| `info` | 6 | Информационное сообщение (Info) |
| `debug` | 7 | Отладочные данные (Debug) |

**Основные источники (Facilities):** `kern` (ядро), `user` (пользовательские процессы), `daemon` (системные службы), `auth` (безопасность).

### Ограничение интенсивности (Ratelimiting)

Для защиты от «шторма логов», который может переполнить буфер и замедлить систему, ядро использует механизм **printk ratelimit**. Если определенный тип сообщения генерируется слишком часто, вывод приостанавливается, и появляется запись: `__ratelimit: N msgs suppressed`.

### Безопасность и права доступа

Доступ к сообщениям ядра может содержать чувствительную информацию об адресах в памяти (ASLR) и структуре системы.
*   **`kernel.dmesg_restrict`:** Параметр `sysctl`, ограничивающий доступ.
    *   `0`: Любой пользователь может читать `dmesg`.
    *   `1`: Требуются привилегии `CAP_SYSLOG` (обычно через `sudo`).
*   **Проверка:** `sysctl kernel.dmesg_restrict`.

## Практические сценарии

### Выбор инструмента: dmesg vs journalctl

| Характеристика | `dmesg` | `journalctl -k` |
| :--- | :--- | :--- |
| **Источник данных** | Прямо из ОЗУ (кольцевой буфер) | Дисковое хранилище `journald` |
| **Сохранность** | Только текущая сессия | Сохраняется между перезагрузками |
| **Доступность** | Доступно сразу после старта ядра | Требует запущенного демона `systemd-journald` |
| **Фильтрация** | Быстрая, базовая | Мощная (по времени, по юнитам, по приоритетам) |

### Использование в контейнерах и Namespaces

В средах виртуализации и контейнеризации (Docker, LXC, Kubernetes) поведение `dmesg` зависит от настроек изоляции:
*   **Изоляция логов:** По умолчанию сообщения ядра видны во всех контейнерах, если не включена изоляция именных пространств пользователя (User Namespaces).
*   **Ограничения:** В большинстве PaaS-решений доступ к `dmesg` внутри контейнера заблокирован по соображениям безопасности.
*   **Рекомендация:** Для диагностики проблем внутри контейнера лучше использовать `kubectl logs` или логи рантайма, а `dmesg` — только на уровне хоста.

### Управление состоянием буфера

В процессе отладки часто требуется «обнулить» историю, чтобы видеть только новые события:
*   `sudo dmesg -C`: Полная очистка буфера.
*   `sudo dmesg -c`: Вывод текущего содержимого с последующей очисткой.
