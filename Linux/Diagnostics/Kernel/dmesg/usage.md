# Использование dmesg: просмотр и фильтрация

## Определения

**Практическое использование dmesg** — это применение набора инструментов и параметров утилиты для извлечения, фильтрации и интерпретации сообщений из кольцевого буфера ядра. Это включает в себя настройку меток времени, идентификацию подсистем-отправителей, мониторинг событий в реальном времени и управление состоянием памяти буфера.

---

## Базовые концепции

### Параметры отображения времени

`dmesg` поддерживает множество форматов меток времени, что критично для сопоставления логов ядра с журналами приложений (например, Nginx или системными событиями в `journalctl`).

*   **`-T` (`--ctime`):** Преобразование секунд uptime в человекочитаемую дату и время. *Внимание: может быть неточным после циклов сна (suspend/resume).*
*   **`-d` (`--delta`):** Вывод разницы во времени между последовательными сообщениями. Помогает выявлять задержки при загрузке драйверов.
*   **`-H` (`--human`):** Включает «человекочитаемый» режим: раскрашивание вывода, автоматическое использование пейджера (less) и удобный формат времени.
*   **`--time-format <формат>`:** Позволяет выбрать конкретный стандарт вывода:
    *   `iso`: Формат ISO-8601 (рекомендуется для автоматизации).
    *   `reltime`: Относительное время.
    *   `ctime`: Аналог `-T`.
    *   `notime`: Полное отключение меток времени (удобно для `diff`).

### Идентификация и декодирование

Для упрощения анализа сырых данных ядра используются флаги расшифровки метаданных.

*   **`-x` (`--decode`):** Декодирует числовые префиксы уровней и источников в текстовые метки (например, вместо `<3>` выводит `err :`).
*   **`-e` (`--reltime`):** Отображает время в локальном формате с указанием смещения.
*   **`--caller`:** Добавляет идентификатор вызывающего объекта (Caller ID, например, `[T123]`). Позволяет понять, какой поток (Thread ID) или процессор инициировал запись сообщения. Требует поддержки `CONFIG_PRINTK_CALLER` в ядре.

## Практические сценарии

### Мониторинг в реальном времени

Используется для отладки событий, происходящих «здесь и сейчас» (подключение оборудования, ошибки сети).

```bash
# Непрерывное отслеживание (аналог tail -f)
dmesg --follow  # или сокращенно dmesg -w

# Мониторинг с декодированием и человекочитаемым временем
dmesg -wHx
```

### Фильтрация по категориям и приоритетам

Встроенные фильтры работают быстрее и потребляют меньше ресурсов, чем конвейеры с `grep`.

```bash
# Фильтрация по уровням (через запятую или диапазоном)
dmesg --level=err,crit    # Только ошибки и критические сбои
dmesg --level=warn+       # От предупреждений и выше (warn, err, crit, alert, emerg)

# Фильтрация по подсистемам (Facility)
dmesg --facility=kern,daemon  # Сообщения только от ядра и системных служб
```

### Экспорт и работа со структурированными данными

Для передачи логов в системы анализа (ELK, Loki) или обработки через `jq`.

```bash
# Вывод в формате JSON
dmesg --json  # или dmesg -J

# Поиск по шаблону с сохранением контекста
dmesg | grep -iE "usb|sda|nvme" -C 3

# Отключение пейджера для вывода в файл или конвейер
dmesg --nopager > kernel_log.txt
```

### Управление кольцевым буфером

Операции требуют прав суперпользователя (`sudo`).

*   **`sudo dmesg -C`:** Полная очистка буфера. Полезно перед воспроизведением бага, чтобы «зачистить» лишний шум.
*   **`sudo dmesg -c`:** Прочитать содержимое и СРАЗУ очистить его (Read and Clear).
*   **`-s <размер>` (`--buffer-size`):** Задает размер буфера, который `dmesg` должен запросить у ядра (по умолчанию используется значение из `/proc/sys/kernel/log_buf_len`).

### Анализ критических событий (OOM)

Диагностика принудительного завершения процессов из-за нехватки памяти (Out Of Memory).

```bash
# Поиск событий OOM Killer с метками времени
dmesg -T | grep -iE "oom|killed process"
```
> Подробная методология: [**Диагностика OOM Killer**](../../../Core/processes/oom_killer_diagnostics.md)
