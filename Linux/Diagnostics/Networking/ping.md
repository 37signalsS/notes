# ping (Packet Internet Groper)

## Определения

**`ping`** — фундаментальная утилита для проверки сетевой связности между узлами. Работает на **сетевом уровне (L3)** модели OSI, используя протокол **ICMP** (Internet Control Message Protocol) для отправки запросов `Echo Request` и получения ответов `Echo Reply`.

## Основные концепции

### Принцип работы и уровни OSI

1.  Отправитель формирует пакет ICMP Type 8 (Echo Request) и инкапсулирует его в IP-пакет.
2.  Получатель отвечает пакетом ICMP Type 0 (Echo Reply).
3.  Измеряется **RTT (Round-Trip Time)** — время прохождения пакета туда и обратно.

**Важно:** У `ping` нет и не может быть порта. Порты — это атрибут транспортного уровня (L4, TCP/UDP). ICMP работает "параллельно" TCP/UDP на сетевом уровне. Любой ответ с указанием порта для ping технически безграмотен.

### Что подтверждает успешный ответ

-   Целевой хост активен (стек протоколов ОС отвечает).
-   Существует двусторонний маршрут между хостами.
-   ICMP-трафик не блокируется промежуточными или локальными брандмауэрами.
-   Уровень L2 (ARP/NDP) функционирует корректно (разрешение IP в MAC успешно).

### Ограничения

-   **Ложное чувство безопасности:** `ping` прошел ≠ сервис работает. Хост может пинговаться, но веб-сервер (L7) или база данных могут быть мертвы.
-   **Блокировка ICMP:** Многие публичные хосты (например, `microsoft.com`) и корпоративные файрволы блокируют ICMP Echo, оставаясь при этом доступными по TCP.
-   **Асимметрия:** `ping` не показывает, на каком именно плече (туда или обратно) происходят задержки или потери.

### Основные метрики и интерпретация

| Метрика | Описание | Критерии нормы |
| :--- | :--- | :--- |
| **RTT** | Round-Trip Time (мс) | Стабильность важнее абсолютного значения. |
| **Packet Loss** | Процент потерянных пакетов | 0% в локальной сети. >1% — признак перегрузки или проблем L1/L2. |
| **mdev (jitter)** | Среднеквадратичное отклонение | Высокий `mdev` (более 10-15% от avg) — признак "джиттера", критично для real-time трафика. |
| **TTL** | Time to Live (время жизни) | Количество хопов до цели. Уменьшается на 1 каждым маршрутизатором. |

### Интерпретация TTL для определения ОС

| Полученный TTL | Предполагаемая ОС (Начальный TTL) | Примечание |
| :--- | :--- | :--- |
| **~64** | Linux / Unix / macOS (64) | Современные десктопные и серверные Unix-системы. |
| **~128** | Windows (128) | Стандарт для всех версий Windows. |
| **~255** | Сетевое оборудование (255) | Маршрутизаторы Cisco, Juniper, коммутаторы. |

**Формула расчета пути:** `Кол-во маршрутизаторов = Начальный_TTL - Полученный_TTL`.
*Пример:* Получен TTL=53. Ближайшее стандартное — 64. 64-53 = 11 хопов.

### Таблица типов ICMP для ping

| Тип (Type) | Код (Code) | Описание | Роль в работе ping |
| :--- | :--- | :--- | :--- |
| **8** | 0 | Echo Request | Запрос, отправляемый утилитой. |
| **0** | 0 | Echo Reply | Ответ, ожидаемый утилитой. |
| **3** | 0–15 | Destination Unreachable | Цель недоступна (ошибки маршрутизации, фильтрации). |
| **11** | 0 | Time Exceeded | TTL истек (пакет попал в петлю или слишком длинный путь). |

## Практические сценарии

### Базовая диагностика

```bash
# Ограниченное количество пакетов (стандарт для диагностики)
ping -c 5 8.8.8.8

# С интервалом 0.5 сек (быстрая проверка стабильности)
ping -i 0.5 ya.ru

# Слышимый пинг (подает сигнал при ответе)
ping -a 192.168.1.1
```

### Анализ статистики потерь

| Результат теста | Вероятная причина |
| :--- | :--- |
| **loss 0%, RTT стабилен** | Сеть исправна на уровне L3. |
| **loss >5%** | Перегрузка канала (Congestion), ошибки на портах коммутаторов, плохой Wi-Fi. |
| **RTT скачет (высокий mdev)** | Буферблоат (Bufferbloat) на маршрутизаторе или нестабильный канал связи. |
| **100% loss** | Хост выключен, блокировка ICMP или отсутствие маршрута. |

### Тестирование MTU и Path MTU Discovery

Используется, если мелкие пакеты проходят, а большие (SSH-сессии, передача файлов) зависают.

```bash
# Проверка прохождения стандартного MTU 1500
# -s 1472 (данные) + 8 (ICMP) + 20 (IP) = 1500 байт
# -M do — запретить фрагментацию (Don't Fragment)
ping -s 1472 -M do 8.8.8.8
```

**Формула расчета:** `Полезная нагрузка (-s) = Желаемый_MTU - 28`.
Если возвращается ошибка `Frag needed and DF set`, значит на пути есть узел с меньшим MTU.

### Работа в IPv6 средах

В современных дистрибутивах `ping` един для обоих протоколов.

```bash
# Явное указание IPv6
ping -6 google.com

# Пинг всех узлов сегмента (Link-local multicast)
# ОБЯЗАТЕЛЬНО указывать интерфейс через % или -I
ping -6 ff02::1%eth0
```

### Привязка к источнику

Необходимо при наличии нескольких ISP или в сложных VRF/VLAN.

```bash
# Отправка через конкретный интерфейс
ping -I eth1 1.1.1.1

# Отправка с конкретного IP-адреса
ping -I 10.0.5.50 8.8.8.8
```

### Адаптивный и Flood пинг

```bash
# Адаптивный (отправляет следующий пакет сразу после ответа)
sudo ping -A 192.168.1.1

# Flood (экстремальная нагрузка для поиска потерь)
# ВНИМАНИЕ: может положить слабые устройства
sudo ping -f 192.168.1.1
```

### Коды возврата (Exit Codes)

Понимание кодов завершения важно для автоматизации и скриптов:
- `0` — Успех (получен хотя бы один ответ).
- `1` — Ошибка (запросы отправлены, но ответов нет — 100% loss).
- `2` — Системная ошибка (неверные параметры, проблемы с DNS, отсутствие прав).

## Дополнительная информация

### Работа без прав Root и в контейнерах

Исторически `ping` требовал `setuid` бита, так как использовал `SOCK_RAW` для формирования ICMP-пакетов. В современных системах это решается двумя способами:
1. **Capabilities:** Назначение `cap_net_raw+p` бинарному файлу.
2. **ping_group_range:** Настройка ядра `net.ipv4.ping_group_range`, позволяющая обычным пользователям открывать специальные `SOCK_DGRAM` сокеты для ICMP.

В Docker-контейнерах `ping` может не работать, если:
- Не проброшена capability `NET_RAW` (по умолчанию обычно разрешена).
- В базовом образе (например, Alpine) отсутствует утилита или не настроены права.

### Если ping не проходит: Алгоритм

1.  **Проверка ARP-кэша:** `ip neigh show`.
    -   Если есть MAC-адрес (`REACHABLE`) — физика и L2 работают. Проблема в L3 (Firewall/Маршрутизация).
    -   Если запись `FAILED` или `INCOMPLETE` — проблема в кабеле, VLAN или хост физически выключен.
2.  **Проверка DNS:** `ping google.com`.
    -   Если ошибка `Name or service not known` — проблема в `/etc/resolv.conf`. См. **[Диагностика DNS](./dns/overview.md)**.
    -   Если IP определился (в скобках), но ответов нет — DNS исправен, проблема в связности.
3.  **Проверка порта (L4):** Если ICMP заблокирован, проверьте конкретный сервис:
    ```bash
    nc -zv 1.1.1.1 443
    ```
