# DNS resolution как узкое место производительности

## Проблема

Сервис отвечает, CPU и I/O в порядке, но часть запросов периодически «подвисает». Задержка возникает не внутри приложения, а на этапе DNS-резолвинга — до установления соединения.

## Причины блокировок

- **`getaddrinfo()` блокируется:** Каждый вызов может ожидать ответа от DNS-сервера
- **Множественные попытки:** Запросы к нескольким nameserver'ам из `/etc/resolv.conf`
- **IPv6 → IPv4 fallback:** При недоступности IPv6 происходит задержка до fallback
- **Search-домены:** Поиск по списку доменов из `search` увеличивает количество запросов
- **Медленные резолверы:** При сетевых сбоях или высокой загрузке DNS время ответа растёт до сотен миллисекунд

**Особенность асинхронных сервисов:** В многопоточных приложениях блокировка происходит на уровне libc, что влияет на все потоки, даже если они не выполняют DNS-запросы.

## Диагностика

### Шаг 1: Определить потери времени через strace

```bash
# Трассировка сетевых вызовов процесса
strace -tt -e trace=network,connect,recvfrom,sendto -p <pid>
```

**Индикатор проблемы:** Видны паузы на `recvfrom`/`sendto` к DNS-серверам (порт 53):

```
14:23:45.123456 sendto(3, "\x01\x02...", 42, 0, {sa_family=AF_INET, sin_addr={s_addr=inet_addr("8.8.8.8")}, sin_port=htons(53)}, 16) = 42
14:23:45.234567 recvfrom(3, "\x01\x02...", 128, 0, {sa_family=AF_INET, sin_addr={s_addr=inet_addr("8.8.8.8")}, sin_port=htons(53)}, [16]) = 128
# ^ Пауза 111 мс между вызовами — задержка на стороне DNS
```

Если задержка между `sendto` и `recvfrom` превышает 50–100 мс — проблема во внешней DNS-инфраструктуре или сетевом пути.

### Шаг 2: Проверить конфигурацию резолверов

```bash
cat /etc/resolv.conf
```

**На что обратить внимание:**

- **Порядок `nameserver`:** Запросы идут по порядку, первый недоступный — задержка до таймаута
- **Наличие `search`:** Каждый search-домен — дополнительный DNS-запрос
- **Опции `options`:** `timeout:`, `attempts:`, `ndots:` влияют на время ожидания

**Пример проблемной конфигурации:**

```
search corp.local department.corp.local internal.corp.local
nameserver 10.0.0.1
nameserver 10.0.0.2
options ndots:5
```

При `ndots:5` запрос `ping db` породит 6 DNS-запросов (3 search-домена × 2 nameserver).

### Шаг 3: Измерить реальное время резолва

```bash
# Многократный запрос для выявления скачков
for i in {1..10}; do dig +stats example.com | grep "Query time"; done
```

**Индикаторы проблемы:**

- Время скачет от 5 мс до 200+ мс
- Есть `SERVER: 10.0.0.1#53` с высоким временем ответа
- В статистике видны `retries` или `timeout`

### Шаг 4: Проверить активность UDP-запросов к DNS

```bash
# Показать UDP-сокеты на порт 53
ss -u -a | grep :53
```

Большое количество сокетов в состоянии `UNCONN` может указывать на множество ожидающих DNS-запросов.

## Решение

### Оптимизация `/etc/resolv.conf`

```
# Убрать лишние search-домены
search corp.local

# Надёжные DNS-серверы с быстрым ответом
nameserver 10.0.0.1
nameserver 8.8.8.8

# Оптимизировать таймауты и попытки
options timeout:1 attempts:2 ndots:1
```

### Кэширование на уровне приложения

- Включить кэширование DNS в приложении (если поддерживается)
- Использовать `nscd` (Name Service Cache Daemon) на уровне ОС
- Для Go: `GODEBUG=netdns=go` для использования чистого Go-резолвера

### Для высоконагруженных сервисов

- Развернуть локальный кэширующий резолвер (dnsmasq, unbound)
- Использовать `NodeLocalDNS` в Kubernetes
- Настроить `--dns` в Docker для обхода прокси
