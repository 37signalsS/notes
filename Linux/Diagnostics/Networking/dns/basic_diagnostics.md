# Базовая диагностика DNS

## Определения

**DNS-резолвинг** — процесс преобразования доменного имени в IP-адрес. В Linux это многоуровневая операция, вовлекающая системные библиотеки (NSS), локальные службы (`systemd-resolved`) и внешние DNS-серверы.

**Триаж (Triage) DNS** — первичная классификация проблемы для определения уровня сбоя: локальная конфигурация, сетевая связность или инфраструктура DNS-сервера.

## Базовые концепции

### Алгоритм комплексной диагностики (Checklist)

При возникновении проблем следуйте пошаговому алгоритму «от локального к глобальному»:

| **Шаг** | **Действие** | **Команда** | **Цель** |
| :--- | :--- | :--- | :--- |
| **1** | Проверка L3-связности | `ping -c 3 8.8.8.8` | Исключить общие проблемы с сетью. |
| **2** | Системный резолвинг | `getent hosts example.com` | Проверить результат глазами ОС (NSS). |
| **3** | Прямой опрос (Резолвер) | `dig example.com` | Увидеть ответ от текущего резолвера и **оставшийся TTL**. |
| **4** | Трассировка иерархии | `dig example.com +trace` | Увидеть путь от корня и точку обрыва. |
| **5** | Опрос Authoritative NS | `dig @ns1.example.com example.com` | Исключить влияние кэша резолвера. |
| **6** | Сравнение резолверов | `dig @1.1.1.1 example.com` | Сравнить ответы разных провайдеров (поиск кэш-коллизий). |

### Анализ вывода команды dig

При диагностике обращайте внимание на следующие поля:

1.  **TTL (Time To Live):** в выводе `dig` второе поле в секции `ANSWER` показывает, сколько секунд осталось лежать этой записи в кэше вашего резолвера. Если адрес неверный, вы будете точно знать, сколько времени ждать до обновления.
2.  **Флаги (Flags):** наличие флага `aa` (Authoritative Answer) означает, что ответ получен напрямую от владельца зоны, а не из кэша.
3.  **Секция ANSWER:** если она пуста, но `RCODE` — `NOERROR`, значит домен существует, но записи запрашиваемого типа для него нет.

### Интерпретация кодов ответа (RCODE)

Понимание кода ответа в выводе `dig` или `nslookup` экономит время при локализации:

-   **NOERROR**: Запрос успешен. Если при этом секция `ANSWER` пуста — записи данного типа не существует (но домен есть).
-   **NXDOMAIN**: Доменное имя не существует в глобальной или локальной зоне.
-   **SERVFAIL**: Ошибка на стороне DNS-сервера (проблемы с рекурсией, конфигурацией или проверкой DNSSEC).
-   **REFUSED**: Сервер отклонил запрос (ошибка в ACL или лимиты на количество запросов).

### Влияние Firewall и MTU

В современных сетях (особенно с DNSSEC) пакеты DNS могут превышать стандартные 512 байт.
-   **Симптом**: `dig +short` работает для маленьких записей, но «зависает» или выдает ошибку для больших (например, `TXT` с ключами).
-   **Причина**: Блокировка фрагментированных UDP-пакетов или порта 53/TCP (необходим, если пакет не влез в UDP).
-   **Проверка**: Принудительно использовать TCP: `dig +tcp example.com`.

## Практические сценарии

### Сценарий 1: "DNS работает через раз" (Intermittent failures)

**Проблема**: Часть запросов проходит мгновенно, часть — с задержкой в 5 секунд.

**Диагностика**:
1.  Проверьте количество DNS-серверов в `/etc/resolv.conf`. Если первый сервер в списке недоступен, системный резолвер (glibc) ждет 5 секунд (таймаут по умолчанию) перед переходом ко второму.
2.  **Решение**: Удалите нерабочий сервер или настройте опции таймаута:
    `options timeout:1 attempts:2 rotate`

### Сценарий 2: "Пинг работает, браузер — нет" (Конфликт NSS)

**Проблема**: `ping google.com` разрешает имя, но `curl` или приложение выдает ошибку.

**Диагностика**:
Проверьте файл `/etc/nsswitch.conf`. Возможно, для `hosts` указан специфический модуль (например, `wins` или `mdns`), который работает некорректно для конкретных доменов.
**Команда для проверки**: `getent ahosts example.com`. Если она возвращает пустой результат или ошибку, проблема в цепочке NSS.

### Сценарий 3: Диагностика "заглушки" (Stub Resolver)

В системах с `systemd-resolved` файл `/etc/resolv.conf` указывает на `127.0.0.53`.

**Проблема**: Прямой опрос `dig @8.8.8.8` работает, а обычный `dig` — нет.
**Действие**:
```bash
# Проверить, получает ли systemd-resolved DNS-серверы от DHCP/NetworkManager
resolvectl status

# Проверить логи службы на наличие ошибок апстримов
journalctl -u systemd-resolved -f
```

### Сценарий 4: Обратный резолвинг (Reverse Lookup)

Используется для проверки соответствия IP-адреса имени хоста (PTR-записи).

```bash
# Быстрая проверка через host
host 93.184.216.34

# Детальная проверка через dig
dig -x 93.184.216.34
```
