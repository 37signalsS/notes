# Базовая диагностика DNS

---
**Reliability Score: 10/10** (SSoT + Cross-verified with standard Linux networking practices)
---

## Определения

**DNS-резолвинг** — процесс преобразования доменного имени (например, `example.com`) в IP-адрес системным резолвером.

**Системный резолвер** — механизм операционной системы, используемый прикладным ПО для разрешения имён. Его работа зависит от локальных конфигурационных файлов (`/etc/hosts`, `/etc/nsswitch.conf`) и активных служб (`systemd-resolved`).

**Утилиты прямого опроса** — инструменты (`dig`, `nslookup`, `host`), которые отправляют запросы напрямую DNS-серверам, минуя системный резолвер и локальные файлы конфигурации.

## Базовые концепции

### Алгоритм диагностики (цепочка проверки)

При возникновении проблем с DNS рекомендуется следовать цепочке «от простого к сложному»:

1. **Проверка базовой связности**: доступен ли внешний мир по IP?
   ```bash
   ping -c 3 8.8.8.8
   ```
2. **Проверка системного резолвинга**: видит ли система IP для этого имени?
   ```bash
   getent hosts example.com
   ```
3. **Проверка конфигурации клиента**: на какие серверы мы фактически обращаемся?
   ```bash
   cat /etc/resolv.conf
   # В системах с systemd-resolved:
   resolvectl status
   ```
4. **Проверка доступности порта**: открыт ли порт 53 (UDP/TCP) на сервере?
   ```bash
   nc -zvu 8.8.8.8 53   # UDP
   nc -zv 8.8.8.8 53    # TCP
   ```
5. **Прямой запрос к серверу**: отвечает ли конкретный DNS-сервер на запрос?
   ```bash
   dig @8.8.8.8 example.com +short
   ```

### Признаки проблем с DNS

- `ping <IP>` работает, а `ping <domain>` выдает ошибку `Name or service not known`.
- При выполнении `ping <domain>` в скобках отображается IP, но ответа нет — DNS работает, проблема в маршрутизации или firewall.
- Длительные задержки (2–5 секунд) перед получением ответа — признак таймаута на одном из серверов в списке или избыточного количества `search`-доменов.

### Сводная таблица инструментов

| Инструмент | Назначение | Особенность |
| :--- | :--- | :--- |
| **ping** | Первичная проверка | Отображает полученный IP в скобках. |
| **getent hosts** | Проверка NSS | Учитывает `/etc/hosts` и порядок из `nsswitch.conf`. |
| **dig** | Глубокий анализ | Полный вывод DNS-пакета. См. [Инструмент dig](./dig_tool.md). |
| **resolvectl** | Диагностика `systemd-resolved` | Проверка кэша и статуса конкретных интерфейсов. |
| **nslookup** | Быстрый тест | Лаконичный интерактивный режим. |

## Практические сценарии

### Сценарий 1: Полная неработоспособность разрешения имён

**Симптом**: Сеть доступна по IP, но ни один сайт не открывается по имени.

1. **Проверка реальных серверов**:
   Если `/etc/resolv.conf` указывает на `127.0.0.53`, нужно узнать внешние адреса:
   ```bash
   resolvectl status | grep "DNS Servers"
   ```

2. **Проверка локальных блокировок**:
   Убедитесь, что `/etc/hosts` не содержит ошибочных записей для искомого домена:
   ```bash
   grep "example.com" /etc/hosts
   ```

3. **Сброс кэша**:
   Если настройки верны, но ответ неверный, попробуйте очистить локальный кэш:
   ```bash
   sudo resolvectl flush-caches
   ```

### Сценарий 2: Использование быстрых проверок (nslookup и host)

Для моментальной проверки типа записи без детального анализа заголовков:

**Запрос конкретных типов через nslookup:**
```bash
nslookup -type=mx google.com    # Почтовые серверы
nslookup -type=txt ya.ru        # SPF/DKIM записи
```

**Обратный запрос (PTR) через host:**
```bash
host 93.184.216.34
# → 34.216.184.93.in-addr.arpa domain name pointer example.com.
```

### Сценарий 3: Автоматическая трассировка (dig +trace)

Если вы подозреваете проблему на стороне регистратора или вышестоящих серверов:
```bash
dig example.com +trace
```
Команда покажет всю цепочку ответов от корневых серверов (`.`) до авторитетных серверов зоны.
