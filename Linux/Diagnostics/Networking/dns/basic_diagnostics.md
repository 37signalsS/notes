# Базовая диагностика DNS

## Определения

**DNS-резолвинг** — процесс преобразования доменного имени (например, `example.com`) в IP-адрес системным резолвером.

**Системный резолвер** — механизм операционной системы, используемый прикладным ПО для разрешения имён. Его работа зависит от локальных конфигурационных файлов (`/etc/hosts`, `/etc/nsswitch.conf`) и активных служб (`systemd-resolved`).

**Утилиты прямого опроса** — инструменты (`dig`, `nslookup`, `host`), которые отправляют запросы напрямую DNS-серверам, минуя системный резолвер и локальные файлы конфигурации.

## Базовые концепции

### Алгоритм диагностики (цепочка проверки)

При возникновении проблем с DNS рекомендуется следовать цепочке «от простого к сложному»:

1. **Проверка базовой связности**: работает ли сеть вообще? (`ping 8.8.8.8`)
2. **Проверка системного резолвинга**: видит ли система IP для этого имени? (`ping example.com`)
3. **Проверка конфигурации клиента**: на какие серверы мы обращаемся? (`cat /etc/resolv.conf`)
4. **Проверка доступности порта**: открыт ли порт 53 на сервере? (`nc -zv 8.8.8.8 53`)
5. **Прямой запрос к серверу**: отвечает ли DNS-сервер на конкретный запрос? (`dig @8.8.8.8 example.com`)

### Признаки проблем с DNS

- `ping <IP>` работает, а `ping <domain>` выдает ошибку `Name or service not known`.
- При выполнении `ping <domain>` в скобках отображается IP — это признак того, что DNS работает, а проблема может быть в сетевой доступности или самом приложении.
- Длительные задержки (несколько секунд) перед началом выполнения команды часто указывают на таймауты при опросе одного из DNS-серверов или неверный порядок в `search`-доменах.

### Сводная таблица инструментов

| Инструмент | Назначение | Особенность |
| :--- | :--- | :--- |
| **ping** | Быстрая проверка разрешения | Отображает полученный IP в скобках. |
| **getent** | Проверка NSS | Показывает реальное поведение системы с учетом `hosts`. |
| **nslookup** | Интерактивная проверка | Простота и наглядность для быстрых тестов. |
| **dig** | Глубокий анализ | Полная техническая информация о пакете. См. [Инструмент dig](./dig_tool.md). |
| **resolvectl** | Диагностика `systemd-resolved` | Проверка кэша и per-link настроек. |

## Практические сценарии

### Сценарий 1: Диагностика «DNS не работает»

**Симптом**: Сеть доступна по IP, но имена не разрешаются.

1. **Проверка текущих серверов**:

    ```bash
    cat /etc/resolv.conf
    # Если используется stub-резолвер, проверьте реальные серверы:
    resolvectl status
    ```

2. **Проверка через системный резолвер (NSS)**:
    Выясняем, видит ли система запись в `/etc/hosts` или получает её извне.

    ```bash
    getent ahosts ya.ru
    ```

3. **Проверка доступности DNS-порта**:
    Проверяем доступность порта 53 по UDP (основной) и TCP (для больших ответов).

    ```bash
    nc -zvu 8.8.8.8 53
    nc -zv 8.8.8.8 53
    ```

4. **Изоляция проблемы прямой проверкой**:
    Если прямой запрос к `8.8.8.8` успешен, а системный резолвинг — нет, проблема в локальной конфигурации (`resolv.conf`, `nsswitch.conf` или firewall).

    ```bash
    dig @8.8.8.8 ya.ru +short
    ```

### Сценарий 2: Использование быстрых утилит (nslookup и host)

Хотя `dig` является эталоном, `nslookup` и `host` удобны для мгновенных проверок.

**Запрос конкретных типов записей через nslookup:**

```bash
nslookup -type=mx google.com    # Почтовые серверы
nslookup -type=soa google.com   # Информация о зоне
```

**Лаконичные проверки через host:**

```bash
host google.com                 # Только результат (A, AAAA, MX)
host -t ns google.com           # Только NS-серверы
host 8.8.8.8                    # Обратный запрос (PTR)
```

### Сценарий 3: Ручная трассировка разрешения

Позволяет понять, на каком этапе иерархии (Root → TLD → Authoritative) происходит сбой.

1. Спросить корневой сервер о зоне `.ru`: `dig @a.root-servers.net ru NS`
2. Спросить сервер зоны `.ru` о домене: `dig @a.dns.ripn.net example.ru NS`
3. Спросить авторитетный сервер об IP: `dig @ns.example.ru example.ru A`

Автоматизированный вариант этой процедуры: `dig example.com +trace`.
