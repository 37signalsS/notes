# Базовая диагностика DNS

## Определения

**DNS-резолвинг** — процесс преобразования доменного имени в IP-адрес. В Linux это многоуровневая операция, вовлекающая системные библиотеки (NSS), локальные службы (`systemd-resolved`) и внешние DNS-серверы.

**Триаж (Triage) DNS** — первичная классификация проблемы для определения уровня сбоя: локальная конфигурация, сетевая связность или инфраструктура DNS-сервера.

**Stub-резолвер** — локальная служба, принимающая DNS-запросы от приложений и пересылающая их upstream-серверам. В современных дистрибутивах Linux — `systemd-resolved`, слушающий на `127.0.0.53:53`. Заменяет классический прямой доступ к `/etc/resolv.conf` из приложений.

**Рекурсивный резолвер** — сервер, который самостоятельно проходит всю иерархию DNS от корневых серверов до авторитетного NS для указанной зоны. Обычно предоставляется провайдером или корпоративным DHCP.

**Авторитетный сервер (Authoritative Nameserver)** — конечный источник данных для зоны. Отвечает с флагом `aa` в заголовке и содержит исходные записи зоны.

**Отрицательное кэширование (Negative Caching, RFC 2308)** — механизм, при котором ответ `NXDOMAIN` или `NODATA` кэшируется на время, указанное в поле `MINIMUM` SOA-записи зоны. Предотвращает шторм запросов на несуществующие домены, но мешает быстрому повторному тестированию после создания записи.

## Базовые концепции

### Уровни резолвинга в Linux

Диагностика DNS в Linux требует понимания трёх уровней:

1.  **Приложение → NSS → Ядро ОС**: Приложение вызывает `getaddrinfo()` или `gethostbyname()`. glibc/musl читают `/etc/nsswitch.conf` и опрашивают источники в указанном порядке (`files`, `resolve`, `dns`, `mdns_minimal`).
2.  **Локальный кэш / stub-резолвер**: Если источник `resolve`, запрос уходит через D-Bus в `systemd-resolved`. Если `dns` — напрямую в `/etc/resolv.conf`. `systemd-resolved` кэширует ответы и может пересылать запросы upstream.
3.  **Внешняя инфраструктура**: Рекурсивные резолверы (8.8.8.8, 1.1.1.1) или авторитетные серверы.

**Почему это важно:** Одна и та же команда (`ping example.com`, `curl example.com`, `dig example.com`) проходит разные пути. `dig` минует NSS и локальный кэш, отправляя запрос напрямую указанному серверу. `getent hosts` проходит через весь стек NSS. Разница в результатах — главный симптом диагностики.

### Алгоритм комплексной диагностики (Checklist)

При возникновении проблем следуйте пошаговому алгоритму «от локального к глобальному»:

| **Шаг** | **Действие** | **Команда** | **Ожидаемый результат** | **Цель** |
| :--- | :--- | :--- | :--- | :--- |
| **1** | Проверка L3-связности | `ping -c 3 8.8.8.8` | Ответы от сервера, потери <1% | Исключить общие проблемы с сетью. |
| **2** | Системный резолвинг (NSS) | `getent hosts example.com` | IP-адрес или ошибка | Проверить результат глазами ОС. |
| **3** | Прямой опрос резолвера | `dig +short example.com` | IP-адрес или пусто | Увидеть ответ от текущего DNS-сервера. |
| **4** | Трассировка иерархии | `dig example.com +trace` | Полная цепочка от корня | Увидеть путь и точку обрыва. |
| **5** | Опрос Authoritative NS | `dig @ns1.example.com example.com` | Ответ с флагом `aa` | Исключить влияние кэша. |
| **6** | Сравнение резолверов | `dig @1.1.1.1 example.com` | Ответ от публичного резолвера | Найти рассинхронизацию кэшей. |

**Примечание:** Если `getent hosts` возвращает другой результат, чем `dig`, проблема в `/etc/hosts`, NSS или локальном кэше (`systemd-resolved`, `nscd`). Если оба возвращают ошибку — проблема в сетевой связности или upstream-инфраструктуре.

### Анализ вывода команды dig

При диагностике обращайте внимание на следующие поля:

1.  **TTL (Time To Live):** в выводе `dig` второе поле в секции `ANSWER` показывает, сколько секунд осталось лежать этой записи в кэше вашего резолвера. Если адрес неверный, вы будете точно знать, сколько времени ждать до обновления.
    ```bash
    dig example.com +noall +answer
    # → example.com.    3499    IN    A    93.184.216.34
    #    (второе поле = остаточный TTL в секундах)
    ```
2.  **Флаги (Flags):** наличие флага `aa` (Authoritative Answer) означает, что ответ получен напрямую от владельца зоны, а не из кэша.
3.  **Секция ANSWER:** если она пуста, но `RCODE` — `NOERROR`, значит домен существует, но записи запрашиваемого типа для него нет.
4.  **Флаг TC (Truncated):** если установлен, ответ не влез в UDP и требует TCP. Используйте `dig +tcp` для получения полного ответа.

### Интерпретация кодов ответа (RCODE)

Понимание кода ответа в выводе `dig` или `nslookup` экономит время при локализации:

-   **NOERROR**: Запрос успешен. Если при этом секция `ANSWER` пуста — записи данного типа не существует (но домен есть).
-   **NXDOMAIN**: Доменное имя не существует в глобальной или локальной зоне. Помните об отрицательном кэшировании: этот ответ может быть сохранён в кэше резолвера.
-   **SERVFAIL**: Ошибка на стороне DNS-сервера (проблемы с рекурсией, конфигурацией или проверкой DNSSEC).
-   **REFUSED**: Сервер отклонил запрос (ошибка в ACL или лимиты на количество запросов).
-   **FORMERR**: Сервер не понял формат запроса (часто при несовпадении версий EDNS).
-   **NOTAUTH**: Клиент запросил зону-transfer у сервера, не являющегося авторитетным для неё.

### Влияние Firewall и MTU

В современных сетях (особенно с DNSSEC) пакеты DNS могут превышать стандартные 512 байт.

-   **Симптом**: `dig +short` работает для маленьких записей, но «зависает» или выдает ошибку для больших (например, `TXT` с ключами).
-   **Причина**: Блокировка фрагментированных UDP-пакетов или порта 53/TCP (необходим, если пакет не влез в UDP).
-   **Проверка**: Принудительно использовать TCP: `dig +tcp example.com`.
-   **Диагностика фаервола**:
    ```bash
    # Проверка доступности UDP/53
    nc -zv 8.8.8.8 53 -u
    # → Connection to 8.8.8.8 53 port [udp/*] succeeded!

    # Проверка доступности TCP/53
    nc -zv 8.8.8.8 53
    # → Connection to 8.8.8.8 53 port [tcp/*] succeeded!
    ```

### Отрицательное кэширование

Ответы `NXDOMAIN` кэшируются на время `MINIMUM` из SOA-записи зоны (RFC 2308). После добавления нового домена старый ответ может возвращаться из кэша резолвера до истечения этого срока.

```bash
# Проверка SOA для определения MINIMUM TTL
dig example.com SOA +short
# → ns1.example.com. admin.example.com. 2023091501 3600 600 86400 3600
#    (последнее поле = 3600 секунд = 1 час отрицательного кэширования)

# Обход кэша (если резолвер поддерживает +cd)
dig example.com +cd
```

### Сравнение инструментов диагностики

| Инструмент | Что проверяет | Когда использовать |
| :--- | :--- | :--- |
| `getent hosts` | NSS + /etc/hosts + stub-резолвер | Первый шаг: «что видит система» |
| `dig` | Чистый DNS-ответ | Изоляция проблемы: сервер или ОС? |
| `resolvectl query` | systemd-resolved (с интерфейсом и кэшем) | Когда используется resolved |
| `host` / `nslookup` | Простой резолвинг | Быстрая проверка, совместимость |
| `tcpdump` / `tshark` | Сетевые пакеты | Когда утилиты дают противоречивые результаты |
| `nc` / `nmap` | Доступность порта | Проверка фаервола и связности |

## Практические сценарии

### Сценарий 1: "DNS работает через раз" (Intermittent failures)

**Проблема**: Часть запросов проходит мгновенно, часть — с задержкой в 5 секунд.

**Диагностика**:
1.  Проверьте количество DNS-серверов в `/etc/resolv.conf`. Если первый сервер в списке недоступен, системный резолвер (glibc) ждет 5 секунд (таймаут по умолчанию) перед переходом ко второму.
2.  Проверьте, нет ли потерь пакетов до первого сервера:
    ```bash
    # Таймаут 1 секунда, 3 попытки
    dig @<first_dns> example.com +time=1 +tries=3 +stats
    ```
3.  Проверьте, не включен ли `rotate` в `resolv.conf`:
    ```bash
    grep rotate /etc/resolv.conf
    ```

**Решение**: Удалите нерабочий сервер или настройте опции таймаута:
`options timeout:1 attempts:2 rotate`

**Валидация**: После исправления `getent hosts example.com` должен возвращаться за <100 мс стабильно. Проверьте 10 последовательных вызовов:
```bash
for i in $(seq 1 10); do time getent hosts example.com; done
```

### Сценарий 2: "Пинг работает, браузер — нет" (Конфликт NSS)

**Проблема**: `ping google.com` разрешает имя, но `curl` или приложение выдает ошибку.

**Диагностика**:
Проверьте файл `/etc/nsswitch.conf`. Возможно, для `hosts` указан специфический модуль (например, `wins` или `mdns`), который работает некорректно для конкретных доменов.
**Команда для проверки**: `getent ahosts example.com`. Если она возвращает пустой результат или ошибку, проблема в цепочке NSS.

**Решение**: Проверьте наличие модулей, которые могут блокировать запрос:
```bash
grep '^hosts:' /etc/nsswitch.conf
# Уберите mdns_minimal [NOTFOUND=return], если Avahi не запущен
```

**Валидация**: `getent hosts example.com` и `curl -s -o /dev/null -w "%{time_namelookup}\n" http://example.com` должны возвращать результаты.

### Сценарий 3: Диагностика "заглушки" (Stub Resolver)

В системах с `systemd-resolved` файл `/etc/resolv.conf` указывает на `127.0.0.53`.

**Проблема**: Прямой опрос `dig @8.8.8.8` работает, а обычный `dig` — нет.

**Диагностика**:
```bash
# Проверить, получает ли systemd-resolved DNS-серверы от DHCP/NetworkManager
resolvectl status

# Проверить логи службы на наличие ошибок апстримов
journalctl -u systemd-resolved -f

# Проверить, слушает ли stub-резолвер на 127.0.0.53
ss -ulnp | grep ':53'
# → LISTEN 0 4096 127.0.0.53:53 ... (должен присутствовать)
```

**Решение**: Если служба не запущена, включите её. Если `DNSStubListener=no` в `resolved.conf`, измените `resolv.conf` на реальные серверы.

**Валидация**: Обычный `dig example.com` должен возвращать ответ.

### Сценарий 4: Обратный резолвинг (Reverse Lookup)

Используется для проверки соответствия IP-адреса имени хоста (PTR-записи). В SSH, SMTP и логах обратное разрешение позволяет идентифицировать источник соединения.

```bash
# Быстрая проверка через host
host 93.184.216.34

# Детальная проверка через dig
dig -x 93.184.216.34
dig 34.216.184.93.in-addr.arpa PTR +short

# Проверка через NSS (как видит система)
getent hosts 93.184.216.34
```

**Типичная проблема**: PTR-запись указывает на `host.example.com`, но обратное разрешение возвращает `host`. Разница в суффиксе поиска (`search`) может вызывать ошибки валидации в почтовых системах.

### Сценарий 5: nscd устаревший кэш

**Проблема**: После обновления DNS-записей приложения продолжают видеть старый IP, хотя `dig` показывает новый.

**Диагностика**:
```bash
# Проверьте статус nscd
systemctl status nscd

# Просмотр статистики
sudo nscd -g
# Обратите внимание на «Cache Hits» для базы hosts

# Принудительная перезагрузка кэша
sudo nscd -i hosts
```

**Примечание**: В системах с `systemd-resolved` и без `nscd` используйте `resolvectl flush-caches`.

**Валидация**: `getent hosts example.com` должен вернуть новый IP.

### Сценарий 6: DNS заблокирован файрволом (порт 53)

**Проблема**: `dig` зависает или выдает `connection timed out`, хотя `ping` до 8.8.8.8 проходит.

**Диагностика**:
```bash
# Проверка UDP/53
nc -zv 8.8.8.8 53 -u
# → Connection timed out (блокировка UDP)

# Проверка TCP/53
nc -zv 8.8.8.8 53
# → Connection refused или таймаут (блокировка TCP)

# Проверка через iptables/nftables на хосте
sudo iptables -L -n | grep 53
sudo nft list ruleset | grep 53
```

**Решение**: Откройте порт 53/UDP и 53/TCP на локальном фаерфоле. Если блокировка на стороне провайдера или корпоративной сети, используйте альтернативные порты (853 для DoT, 443 для DoH) или обходные каналы.

**Валидация**: `dig @8.8.8.8 example.com +short` возвращает IP за <1 секунду.

### Сценарий 7: Диагностика после смены сети (VPN / новый интерфейс)

**Проблема**: После подключения VPN или изменения сетевого интерфейса DNS перестает работать.

**Диагностика**:
```bash
# 1. Проверьте, какой интерфейс активен
ip route get 8.8.8.8

# 2. Проверьте DNS-серверы на интерфейсе
resolvectl status

# 3. Проверьте search домены
grep search /etc/resolv.conf

# 4. Проверьте, не перезаписал ли NetworkManager настройки
nmcli device show eth0 | grep DNS
```

**Решение**: Если `systemd-resolved` не получил новые DNS от DHCP, перезапустите службу или настройте статические домены для интерфейса:
```bash
resolvectl domain eth0 '~corp.local'
resolvectl dns eth0 10.0.0.2
```

**Валидация**: `resolvectl query internal.corp.local` должен возвращаться через правильный интерфейс.

### Сценарий 8: DNSSEC-провал (SERVFAIL без очевидных причин)

**Проблема**: Все запросы возвращают `SERVFAIL`, хотя authoritative сервер работает.

**Диагностика**:
```bash
# Отключите проверку DNSSEC на клиенте (если используется)
dig example.com +dnssec +cd +noall +answer

# Проверьте цепочку доверия
dig example.com DNSKEY +dnssec

# Проверьте, есть ли DS-запись у регистратора
dig example.com DS +noall +answer
```

**Причины**:
1. Истек срок действия RRSIG на authoritative сервере.
2. Несоответствие алгоритмов подписи (RSASHA1 vs RSASHA256).
3. Отсутствие или устаревшая DS-запись у регистратора.
4. Прокси/резолвер не поддерживает EDNS0 и обрезает ответ.

**Решение**: Исправьте конфигурацию authoritative сервера или временно отключите DNSSEC-проверку на резолвере (не рекомендуется для продакшена).

**Валидация**: `dig +dnssec example.com` возвращает флаг `ad` (Authenticated Data).

### Сценарий 9: Проверка после изменения DNS-записей (Smoke Test)

После изменения DNS-записей (переезд на новый IP, смена NS-серверов) выполните минимальный набор проверок:

```bash
# 1. Проверьте серию зоны на новом authoritative сервере
dig @ns1.example.com example.com SOA
# → Убедитесь, что серийный номер увеличился

# 2. Проверьте новую запись напрямую у authoritative сервера
dig @ns1.example.com example.com A

# 3. Проверьте распространение через несколько независимых резолверов
for resolver in 8.8.8.8 1.1.1.1 9.9.9.9; do
    echo "=== $resolver ==="
    dig @"$resolver" example.com A +short
done

# 4. Проверьте обратное разрешение (PTR) для нового IP
dig -x <new_ip_address>

# 5. Проверьте TTL старых записей
dig @old_resolver example.com A +ttlunits
# → Убедитесь, что старый IP исчезнет после истечения TTL
```

### Сценарий 10: Кэш-отравление (Cache Poisoning)

**Проблема**: `dig @8.8.8.8` возвращает неверный IP, хотя авторитетный сервер отдает правильный.

**Диагностика**:
```bash
# Ответ от резолвера (может быть кэширован)
dig @8.8.8.8 example.com +short

# Ответ напрямую от авторитетного сервера
dig @ns1.example.com example.com +short

# Если ответы различаются — возможное кэш-отравление
# Очистка кэша резолвера (если доступно)
dig @127.0.0.1 example.com +cd
```

**Решение**: Используйте DNSSEC (`+dnssec`), переключитесь на другой резолвер или очистите локальный кэш.

## Best Practices

1.  **Всегда проверяйте NSS перед DNS**: `getent hosts` — первый шаг. `ping` и `curl` используют NSS, `dig` — нет.
2.  **Используйте FQDN с точкой** (`example.com.`) при диагностике, чтобы исключить влияние `search` доменов.
3.  **Настройте таймауты**: `options timeout:1 attempts:2 rotate` в `resolv.conf` снижает p99-задержку при сбое одного сервера.
4.  **Ограничьте search домены**: более 2–3 суффиксов приводят к каскаду лишних запросов.
5.  **Не редактируйте `/etc/resolv.conf` напрямую** в системах с `systemd-resolved` или `NetworkManager`. Используйте `resolvectl` или `nmcli`.
6.  **Включайте логирование** `systemd-resolved` при проблемах: `resolvectl log-level debug`.
7.  **Используйте `getent ahosts` вместо `getent hosts`**, если нужно увидеть все адреса (IPv4 и IPv6) и порядок их приоритета.
