# Базовая диагностика DNS

## Определения

**DNS-резолвинг** — процесс преобразования доменного имени (например, `google.com`) в IP-адрес (например, `142.250.185.206`) системным резолвером.

**Системный резолвер** — механизм ОС, используемый приложениями (`ping`, `curl`, браузер) для разрешения имён. Поведение определяется `/etc/nsswitch.conf`, `/etc/hosts`, `/etc/resolv.conf`.

**Утилиты прямого опроса** — `dig`, `nslookup`, `host`. Отправляют запросы напрямую DNS-серверам, минуя локальные настройки резолвера. Используются для изоляции проблемы.

## Базовые концепции

### Диагностическая цепочка

При проблемах с DNS диагностика идёт от простого к сложному:

1. **Проверка связности** — `ping 8.8.8.8` (сеть работает?)
2. **Проверка резолвинга** — `ping google.com` (имя разрешается?)
3. **Проверка конфигурации** — `cat /etc/resolv.conf` (какие серверы используются?)
4. **Проверка доступности DNS** — `nc -zv 8.8.8.8 53` (порт 53 доступен?)
5. **Прямой запрос к серверу** — `dig @8.8.8.8 google.com` (сервер отвечает?)

### Признаки проблем с DNS

- `ping 8.8.8.8` работает, но `ping google.com` → `Name or service not known`
- При пинге домена виден IP в скобках — DNS работает
- Ошибка `Name or service not known` без IP — DNS не работает

### Инструменты быстрой проверки

| Инструмент | Назначение | Особенность |
| :--- | :--- | :--- |
| `ping` | Проверка резолвинга и связности | Показывает IP в скобках при успехе |
| `nslookup` | Быстрая проверка DNS-записей | Лаконичный вывод, показывает сервер-ответчик |
| `dig` | Детальный анализ DNS | Полная информация: заголовки, секции, статистика |
| `getent` | Проверка через системный NSS | Показывает реальное поведение системы (с учётом hosts и кэша) |
| `resolvectl` | Опрос через systemd-resolved | Показывает кэш, TTL и сервер-источник ответа |
| `nc` | Проверка доступности порта 53 | TCP (`-zv`) и UDP (`-zvu`) |

## Практические сценарии

### Сценарий 1: Базовая диагностика «не работает DNS»

**Симптом:** `ping 8.8.8.8` работает, но `ping google.com` выдаёт `Name or service not known`.

#### Шаг 1: Проверить конфигурацию DNS-клиента

```bash
cat /etc/resolv.conf
# В системах с systemd-resolved файл может указывать на stub 127.0.0.53
# Для получения реальных серверов: resolvectl status
```

#### Шаг 2: Проверить реальное разрешение имён (NSS и resolved)

Для проверки того, как домен разрешается системой (включая локальные кэши и `/etc/hosts`), используются:

```bash
# Проверка через Name Service Switch (как видят приложения)
getent ahosts google.com

# Проверка через системный резолвер (источник ответа, кэш, TTL)
resolvectl query google.com
```

#### Шаг 3: Проверить доступность DNS-сервера

```bash
# Проверить IP-связность
ping 8.8.8.8

# Проверить доступность DNS-порта (53/TCP и 53/UDP)
nc -zv 8.8.8.8 53
nc -zvu 8.8.8.8 53
```

#### Шаг 3: Выполнить прямой запрос к серверу

```bash
dig @8.8.8.8 google.com
```

Если запрос успешен, а системный резолвинг нет — проблема в локальной конфигурации (например, firewall блокирует `systemd-resolved`).

### Сценарий 2: Использование nslookup для разных типов запросов

#### Простой запрос A-записи

```bash
nslookup google.com
```

Команда покажет IP-адреса (A и AAAA) и адрес DNS-сервера, предоставившего ответ.

#### Запрос конкретного типа записи

```bash
nslookup -type=mx google.com    # MX-записи (почтовые серверы)
nslookup -type=soa google.com   # SOA-запись (авторитетная информация о зоне)
```

SOA-запрос покажет первичный сервер имён для зоны и контактный email администратора.

#### Трассировка цепочки делегирования

Ручной путь разрешения имени от корневых серверов:

1. Найти корневой сервер (например, `a.root-servers.net`)
2. Спросить NS-серверы для зоны `.com`: `nslookup -type=ns com a.root-servers.net`
3. У полученного сервера (`a.gtld-servers.net`) спросить NS для `google.com`: `nslookup -type=ns google.com a.gtld-servers.net`
4. У полученного сервера (`ns1.google.com`) спросить A-запись: `nslookup google.com ns1.google.com`
