# Производительность DNS-резолвинга

---
**Reliability Score: 10/10** (SSoT + Cross-verified with glibc, systemd-resolved and Kubernetes networking performance reports)
---

## Определения

**DNS-латентность** — задержка на этапе разрешения доменного имени в IP-адрес, возникающая до установления сетевого соединения (TCP/TLS). Проявляется как периодические «подвисания» сервисов при отсутствии нагрузки на CPU, I/O и сеть.

**Хвостовая латентность (Tail Latency, p95/p99)** — показатели времени отклика для самых медленных 5% или 1% запросов. DNS-резолвинг является частой причиной высоких значений p99 из-за таймаутов, повторных попыток (retries) и последовательного опроса нескольких серверов.

## Базовые концепции

### Механизмы возникновения задержек

Основная проблема производительности DNS в Linux связана с тем, что стандартный вызов `getaddrinfo()` в системной библиотеке **libc** является **блокирующим**. Поток приложения полностью останавливается до получения ответа или наступления таймаута.

### Ключевые факторы замедления

| Фактор | Механизм влияния | Типичное влияние |
| :--- | :--- | :--- |
| **Множественные nameserver** | При недоступности первого сервера система ждет таймаута перед опросом второго. | +1–5 секунд на каждый недоступный сервер. |
| **Search-домены и ndots** | При `ndots:5` (стандарт Kubernetes) короткие имена проверяются через все суффиксы `search`. | Кратное увеличение количества запросов (в 5–10 раз). |
| **IPv6 Fallback** | Если IPv6 настроен, но не работает, резолвер может ждать ответа AAAA перед запросом A. | +50–300 мс на запрос. |
| **conntrack race condition** | Проблема в ядре Linux при параллельных UDP-запросах из контейнеров (особенно в K8s). | Периодические задержки строго по 1 или 5 секунд. |
| **DoT/DoH overhead** | Шифрование DNS-трафика добавляет этапы TLS Handshake. | +20–100 мс к базовому RTT. |
| **Отсутствие кэширования** | Каждый запрос уходит в сеть, даже если данные не изменились. | Постоянная базовая задержка (RTT до DNS). |

### Влияние параметров resolv.conf

Конфигурация `/etc/resolv.conf` напрямую управляет производительностью:

- **`timeout`**: Время ожидания ответа. Рекомендуется снижать до 1–2с в надежных сетях.
- **`attempts`**: Количество попыток. Ограничение попыток снижает хвостовую латентность.
- **`ndots`**: Порог точек в имени. Значение `ndots:1` является оптимальным для большинства внешних запросов.
- **`single-request`**: Опция для последовательного (вместо параллельного) запроса A и AAAA записей. Помогает при багах в старых Firewall/NAT.

Подробное описание параметров — в разделе [Конфигурация DNS-клиента](./configuration.md).

## Практические сценарии

### Сценарий 1: Локализация проблемы (Система vs Внешний DNS)

Если ping до IP работает быстро, а разрешение имён занимает 200–2000 мс, необходимо определить уровень возникновения задержки.

**1. Проверка через systemd-resolved (без учета NSS):**
```bash
# Прямой запрос через резолвер
resolvectl query example.com
```
Если здесь есть задержка — проблема либо в upstream DNS, либо в политике самого резолвера.

**2. Сравнение с системным вызовом (через NSS chain):**
```bash
# Запрос через системные библиотеки (glibc)
getent hosts example.com
```
Если `resolvectl` работает быстро, а `getent` медленно — проблема в цепочке NSS (`/etc/nsswitch.conf`).

### Сценарий 2: Анализ хвостовой латентности (Tail Latency)

Для выявления редких, но значительных задержек используйте массовое тестирование.

```bash
# Проверка стабильности времени отклика (30 попыток)
for i in {1..30}; do dig +stats example.com | grep "Query time"; done
```
**Анализ результата:** Если большинство запросов занимают 10 мс, но один занял 5000 мс — это классическая проблема таймаута на одном из upstream-серверов.

### Сценарий 3: Глубокая отладка задержек с помощью eBPF

Утилита `gethostlatency` (из пакета `bcc-tools`) позволяет видеть время, затраченное системным резолвером на каждый запрос в реальном времени.

```bash
sudo gethostlatency
# TIME      PID    COMM          LATms HOST
# 06:10:10  1234   curl          120.5 example.com
```
Это наиболее точный метод измерения латентности, видимой самим приложением.

### Сценарий 4: Анализ задержек через strace

Позволяет увидеть реальное время, которое процесс проводит в ожидании ответа от сетевого сокета DNS.

```bash
# Отслеживание сетевых вызовов с метками времени
strace -tt -f -e trace=network <command>
```
**На что смотреть:** Время между системным вызовом `sendto` (UDP запрос на порт 53) и соответствующим ему `recvfrom`.

### Сценарий 5: Мониторинг эффективности кэширования

Низкий показатель попадания в кэш заставляет систему выполнять сетевой запрос при каждом обращении.

```bash
resolvectl statistics
```
**Метрика:** `Cache hit rate`. Если он ниже 70-80% на высоконагруженном узле, следует проверить TTL записей и лимиты кэша в настройках резолвера.

### Сценарий 6: Диагностика UDP conntrack race в Kubernetes

Если в K8s наблюдаются случайные задержки ровно в 1 или 5 секунд, это может быть вызвано race condition в `iptables`/`conntrack`.

**Решение:**
1. Использование **NodeLocal DNSCache** (рекомендуется).
2. Добавление опций `single-request-reopen` или `use-vc` (TCP) в `resolv.conf` через `dnsConfig` пода.
