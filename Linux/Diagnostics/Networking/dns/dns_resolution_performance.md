# DNS resolution как узкое место производительности

## Определения

**DNS-латентность** — задержка на этапе разрешения доменного имени в IP-адрес, возникающая до установления TCP-соединения. Проявляется как периодические «подвисания» сервисов при штатных CPU, I/O и сети.

**Хвостовая латентность (p95/p99)** — метрики, отражающие наихудшие 5% или 1% запросов. DNS-резолвинг — частая причина высоких p95/p99 из-за таймаутов и повторных попыток.

## Базовые концепции

### Механизм блокировки

Вызов `getaddrinfo()` в libc — **блокирующий**. Каждый вызов ожидает ответа от DNS-сервера, и в многопоточных приложениях это влияет на все потоки, даже не выполняющие DNS-запросы.

### Источники задержек

| Причина | Механизм | Типичная задержка |
| :--- | :--- | :--- |
| **Блокирующий `getaddrinfo()`** | Поток ждёт ответа от DNS-сервера | 50–500 мс |
| **Множественные nameserver'ы** | Запросы к каждому серверу по порядку из `/etc/resolv.conf` | +100–500 мс на каждый недоступный |
| **IPv6 → IPv4 fallback** | При недоступности IPv6 — ожидание таймаута | +50–200 мс |
| **Search-домены** | Поиск по списку доменов из `search` | Каждый домен — дополнительный запрос |
| **Медленные резолверы** | Высокая загрузка DNS или сетевые потери | Скачки от 5 мс до 500+ мс |
| **Высокий `ndots`** | Короткие имена проверяются по всем search-доменам | При `ndots:5` запрос `ping db` = 6 DNS-запросов |

### Влияние конфигурации resolv.conf

Параметры `/etc/resolv.conf` напрямую определяют время резолвинга:

- **`nameserver`** — порядок серверов; первый недоступный → задержка до таймаута
- **`search`** — каждый домен суффикса × каждый nameserver = отдельный запрос
- **`options timeout:N`** — время ожидания ответа (по умолчанию 5 сек)
- **`options attempts:N`** — количество повторных попыток
- **`options ndots:N`** — порог точек, ниже которого имя считается «коротким» и проверяется через search-домены

Подробнее о файлах конфигурации — в [Конфигурация DNS-клиента](./configuration.md).

## Практические сценарии

### Сценарий 1: Определение потерь времени через strace

**Симптом:** Сервис периодически «подвисает», причина неясна.

```bash
strace -tt -e trace=network,connect,recvfrom,sendto -p <pid>
```

**Индикатор проблемы:** Паузы между `sendto` и `recvfrom` к DNS-серверам (порт 53):

```
14:23:45.123456 sendto(3, "\x01\x02...", 42, 0, {sa_family=AF_INET, sin_port=htons(53)}, 16) = 42
14:23:45.234567 recvfrom(3, "\x01\x02...", 128, 0, {sa_family=AF_INET, sin_port=htons(53)}, [16]) = 128
# ^ Пауза 111 мс — задержка на стороне DNS
```

Задержка >50–100 мс между `sendto` и `recvfrom` указывает на проблему во внешней DNS-инфраструктуре или сетевом пути.

### Сценарий 2: Диагностика проблемной конфигурации resolv.conf

**Симптом:** Медленное разрешение имён, особенно коротких имён хостов.

```bash
cat /etc/resolv.conf
```

**Проблемная конфигурация:**

```
search corp.local department.corp.local internal.corp.local
nameserver 10.0.0.1
nameserver 10.0.0.2
options ndots:5
```

При `ndots:5` запрос `ping db` породит 6 DNS-запросов (3 search-домена × 2 nameserver).

### Сценарий 3: Измерение реального времени резолва

```bash
for i in {1..10}; do dig +stats example.com | grep "Query time"; done
```

**Индикаторы проблемы:**

- Время скачет от 5 мс до 200+ мс
- В выводе виден `SERVER: 10.0.0.1#53` с высоким временем ответа
- В статистике `dig` видны `retries` или `timeout`

Инструмент `dig` подробно описан в [Инструмент dig](./dig_tool.md).

### Сценарий 4: Проверка активности UDP-запросов к DNS

```bash
ss -u -a | grep :53
```

Большое количество сокетов в состоянии `UNCONN` указывает на множество ожидающих DNS-запросов.

### Сценарий 5: Оптимизация resolv.conf

```
search corp.local
nameserver 10.0.0.1
nameserver 8.8.8.8
options timeout:1 attempts:2 ndots:1
```

### Сценарий 6: Кэширование для высоконагруженных сервисов

**На уровне ОС:**

- `nscd` (Name Service Cache Daemon) — кэширование `getaddrinfo()`
- `systemd-resolved` — кэш включён по умолчанию

**На уровне приложения:**

- Встроенный DNS-кэш фреймворка (если поддерживается)
- Go: `GODEBUG=netdns=go` — чистый Go-резолвер, блокирует только своё рантайм-ядро

**Инфраструктурные решения:**

- Локальный кэширующий резолвер: `dnsmasq`, `unbound`
- Kubernetes: `NodeLocalDNS` — DaemonSet с кэшем на каждой ноде
- Docker: `--dns` — обход прокси, прямой запрос к указанным серверам

Полный контекст оптимизации латентности — в [Оптимизация сетевых каналов](../../../Networking/Concepts/network_latency_optimization.md).
