# Производительность DNS-резолвинга

## Определения

**DNS-латентность** — задержка на этапе разрешения доменного имени в IP-адрес, возникающая до установления сетевого соединения (TCP/TLS). Проявляется как периодические «подвисания» сервисов при отсутствии нагрузки на CPU, I/O и сеть.

**Хвостовая латентность (Tail Latency, p95/p99)** — показатели времени отклика для самых медленных 5% или 1% запросов. DNS-резолвинг является частой причиной высоких значений p99 из-за таймаутов, повторных попыток (retries) и последовательного опроса нескольких серверов.

## Базовые концепции

### Механизмы возникновения задержек

Основная проблема производительности DNS в Linux связана с тем, что стандартный вызов `getaddrinfo()` в системной библиотеке libc является **блокирующим**. Поток приложения полностью останавливается до получения ответа или наступления таймаута.

### Ключевые факторы замедления

| Фактор | Механизм влияния | Типичное влияние |
| :--- | :--- | :--- |
| **Множественные nameserver** | При недоступности первого сервера система ждет таймаута перед опросом второго. | +1–5 секунд на каждый недоступный сервер. |
| **Search-домены и ndots** | При `ndots:5` (стандарт Kubernetes) короткие имена проверяются через все суффиксы `search`. | Кратное увеличение количества запросов (в 5–10 раз). |
| **IPv6 Fallback** | Если IPv6 настроен, но не работает, резолвер ждет ответа AAAA перед запросом A. | +50–300 мс на запрос. |
| **Таймауты резолвера** | Стандартный таймаут в `/etc/resolv.conf` часто слишком велик (5с). | Резкие скачки p99 при сетевых потерях. |
| **Отсутствие кэширования** | Каждый запрос уходит в сеть, даже если данные не изменились. | Постоянная базовая задержка (RTT до DNS). |

### Влияние параметров resolv.conf

Конфигурация `/etc/resolv.conf` напрямую управляет производительностью:

- **`timeout`**: Время ожидания ответа. Рекомендуется снижать до 1–2с в надежных сетях.
- **`attempts`**: Количество попыток. Ограничение попыток снижает хвостовую латентность.
- **`ndots`**: Порог точек в имени. Значение `ndots:1` является оптимальным для большинства внешних запросов.

Подробное описание параметров — в разделе [Конфигурация DNS-клиента](./configuration.md).

## Практические сценарии

### Сценарий 1: Локализация проблемы (Система vs Внешний DNS)

Если ping до IP работает быстро, а разрешение имён занимает 200–2000 мс, необходимо определить, где возникает задержка: в системном резолвере или на стороне вышестоящего DNS.

**1. Проверка через systemd-resolved (без учета NSS):**
```bash
# Прямой запрос через резолвер
resolvectl query example.com
```
Если здесь есть задержка — проблема либо в upstream DNS, либо в политике самого резолвера.

**2. Сравнение с системным вызовом (через NSS chain):**
```bash
# Запрос через системные библиотеки (glibc)
getent hosts example.com
```
Если `resolvectl` работает быстро, а `getent` медленно — проблема в цепочке NSS (`/etc/nsswitch.conf`).

### Сценарий 2: Анализ цепочки резолвинга (NSS)

Типичный кейс деградации производительности связан с лишними или медленными модулями в NSS.

**Диагностика:**
```bash
cat /etc/nsswitch.conf | grep hosts
```
**Признак проблемы:** Наличие `mdns` (или `mdns4_minimal`) перед `dns`. В корпоративных сетях или при использовании VPN mDNS может добавлять секунды задержки на каждый lookup, пытаясь найти имя в локальном сегменте.

### Сценарий 3: Проверка эффективности кэширования

Низкий показатель попадания в кэш заставляет систему выполнять сетевой запрос при каждом обращении.

**Диагностика:**
```bash
resolvectl statistics
```
**На что смотреть:** Если `Cache hit rate` низкий, система постоянно ходит в сеть. Это может быть вызвано низким TTL записей или слишком частой очисткой кэша.

### Сценарий 4: Сравнение локальной и внешней латентности

Позволяет окончательно подтвердить, является ли проблема локальной.

```bash
# Замер задержки локального резолвера
dig example.com @127.0.0.53 | grep "Query time"

# Замер задержки внешнего DNS (например, Cloudflare)
dig example.com @1.1.1.1 | grep "Query time"
```
Разница в показателях наглядно показывает, где теряется время.

### Сценарий 5: Анализ задержек через strace

Позволяет увидеть реальное время, которое процесс проводит в ожидании ответа от сетевого сокета DNS.

```bash
# Отслеживание сетевых вызовов с метками времени
strace -tt -e trace=network -p <PID>
```

**Признак проблемы:** Значительная разница во времени между системными вызовами `sendto` (отправка запроса на порт 53) и `recvfrom` (получение ответа).

### Сценарий 6: Выявление влияния ndots в Kubernetes

В Kubernetes-средах высокий `ndots` часто приводит к тому, что запросы к внешним именам (например, `google.com`) сначала пытаются разрешиться как внутренние сервисы.

**Диагностика:**

```bash
# Измерение времени и просмотр количества запросов
dig +stats google.com
```

Если в статистике `dig` или в дампе трафика (`tcpdump`) видны запросы вида `google.com.default.svc.cluster.local`, значит `ndots` замедляет работу.

### Сценарий 3: Массовое тестирование производительности

```bash
# Проверка стабильности времени отклика (10 попыток)
for i in {1..10}; do dig +stats example.com | grep "Query time"; done
```

Если время отклика нестабильно (например, 2 мс, 2 мс, 500 мс), это указывает на проблемы в сети или на перегрузку вышестоящего DNS-резолвера.

### Сценарий 4: Оптимизация через локальное кэширование

Для снижения латентности на высоконагруженных узлах применяются локальные резолверы:

- **systemd-resolved**: Встроенное кэширование в современных дистрибутивах.
- **nscd**: Кэширование на уровне системных вызовов libc.
- **NodeLocalDNS**: Специализированное решение для Kubernetes для минимизации трафика к CoreDNS.

### Сценарий 5: Проверка перегрузки UDP-сокетов

```bash
# Просмотр очереди UDP-пакетов
ss -unlp | grep :53
```

Наличие больших очередей на прием (`Recv-Q`) у DNS-служб указывает на то, что резолвер не справляется с потоком запросов.
