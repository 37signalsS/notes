# Конфигурация DNS-клиента: диагностика и проверка

## Определения

**Конфигурация DNS-клиента** — совокупность настроек ОС, определяющих выбор DNS-серверов, порядок опроса источников имен и параметры работы системного резолвера.

**Системный резолвер** — компонент glibc, выполняющий разрешение имен через системные вызовы (например, `getaddrinfo`). Поведение резолвера критически зависит от файлов конфигурации и активных служб управления сетью. Полная теория и принципы работы — в разделе [DNS-клиент в Linux: концепции](../../../Networking/Concepts/dns_client.md).

## Базовые концепции

### Конфигурационная иерархия

Диагностика конфигурации DNS всегда начинается с проверки трех ключевых точек:

1. **Порядок поиска (`/etc/nsswitch.conf`):** Определяет, пойдет ли система сначала в локальный файл `hosts` или сразу к DNS-серверам.
2. **Локальные исключения (`/etc/hosts`):** Статическая таблица имен, имеющая (обычно) приоритет над внешними запросами.
3. **Список серверов (`/etc/resolv.conf`):** Главный файл с адресами DNS-серверов. В современных системах управляется динамически.

### Службы управления конфигурацией

В Linux за автоматическую настройку DNS отвечают конкурирующие или взаимодействующие службы:

- **systemd-resolved:** Современный стандарт. Создает локальный stub-резолвер на `127.0.0.53`.
- **NetworkManager:** Настраивает DNS на основе полученных по DHCP или VPN данных.
- **netplan:** Высокоуровневая обертка для конфигурации сети (Ubuntu).

Критически важно определить, какая служба управляет файлом `/etc/resolv.conf` в данный момент, чтобы избежать перезаписи ручных настроек.

## Практические сценарии

### Сценарий 1: Проверка целостности конфигурационных файлов

Первичная диагностика при некорректном разрешении имен:

```bash
# 1. Проверка порядка разрешения (ищем строку hosts)
grep '^hosts:' /etc/nsswitch.conf
# Ожидается: hosts: files dns (files должен быть первым)

# 2. Поиск подозрительных записей в hosts
cat /etc/hosts

# 3. Анализ resolv.conf: файл или ссылка?
ls -l /etc/resolv.conf
# Если ссылка на /run/systemd/resolve/stub-resolv.conf — управляет systemd-resolved
# Если ссылка на /run/NetworkManager/resolv.conf — управляет NetworkManager
```

### Сценарий 2: Диагностика и управление systemd-resolved

Если `/etc/resolv.conf` указывает на `127.0.0.53`, диагностика выполняется через `resolvectl`:

```bash
# Проверка текущих upstream DNS-серверов для каждого интерфейса
resolvectl status

# Проверка глобальных настроек
resolvectl statistics

# Тестовый запрос через службу (показывает, какой сервер ответил)
resolvectl query ya.ru

# Очистка DNS-кэша при подозрении на устаревшие данные
resolvectl flush-caches
```

### Сценарий 3: Устранение конфликтов управления DNS

**Симптом:** Настройки DNS «слетают» после перезагрузки или переподключения сети.

**Причина:** Несколько служб пытаются одновременно управлять `/etc/resolv.conf`.

**Диагностика и решение:**

1. Проверьте содержимое `/etc/NetworkManager/NetworkManager.conf`.
2. Если вы хотите, чтобы NetworkManager передавал данные в `systemd-resolved`, убедитесь, что в секции `[main]` установлен параметр `dns=systemd-resolved`.
3. Если вы настраиваете DNS вручную и хотите запретить службам трогать `/etc/resolv.conf`, удалите симлинк и создайте обычный файл, либо установите `dns=none` в конфигурации NetworkManager.

### Сценарий 4: Проверка параметров производительности (ndots)

**Симптом:** Медленное разрешение имен во внешних сетях (особенно в Kubernetes).

**Проверка:**

```bash
grep 'options' /etc/resolv.conf
```

Если `ndots` установлен в значение > 1 (например, `ndots:5`), любое имя с количеством точек меньше 5 будет сначала проверяться через все суффиксы `search`. Это создает избыточную нагрузку и задержки.
