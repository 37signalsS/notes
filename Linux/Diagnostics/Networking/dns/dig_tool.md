# Детальный анализ DNS с помощью dig

## Определения

**`dig` (Domain Information Groper)** — утилита для выполнения DNS-запросов и получения детальной информации о доменах. Входит в состав пакета `dnsutils` (Debian) или `bind-utils` (RHEL). В отличие от `nslookup` или `host`, предоставляет полный вывод протокола: заголовки, секции ответа, статистику и флаги. Начиная с версии BIND 9.18, поддерживает современные протоколы шифрования (DoH, DoT) и структурированный вывод (JSON, YAML).

**Прямой опрос DNS** — метод диагностики, при котором утилита отправляет запросы напрямую авторитетным серверам или рекурсивным резолверам, минуя кэш и конфигурацию локального stub-резолвера (`systemd-resolved`). Позволяет изолировать проблемы инфраструктуры от проблем ОС.

## Базовые концепции

### Установка

```bash
# Debian/Ubuntu
sudo apt-get install -y dnsutils

# RHEL/CentOS/Rocky Linux
sudo dnf install -y bind-utils

# Alpine
apk add bind-utils

# macOS (Homebrew)
brew install bind

# Проверка версии
dig -v
# → DiG 9.18.18-0ubuntu0.22.04.2-Ubuntu
```

### Структура вывода

```bash
dig example.com
```

Основные секции ответа:

1. **HEADER**: Общая информация (статус запроса, ID транзакции, количество записей в секциях).
2. **OPT PSEUDOSECTION**: Информация о расширениях EDNS (например, размер UDP-пакета, COOKIE, NSID).
3. **QUESTION SECTION**: Подтверждение запрашиваемого домена и типа записи.
4. **ANSWER SECTION**: Ресурсные записи, соответствующие запросу (искомый результат).
5. **AUTHORITY SECTION**: Список авторитетных серверов имен для домена (NS-записи).
6. **ADDITIONAL SECTION**: Дополнительная информация (например, IP-адреса NS-серверов).
7. **Статистика**: Время выполнения, используемый сервер, дата, размер сообщения и транспортный протокол (в новых версиях).

### DNS-сообщение в контексте вывода dig

Каждый DNS-запрос представляет собой бинарное сообщение фиксированной структуры (12-байтовый заголовок + переменные секции). Утилита `dig` декодирует это сообщение в текстовый вид:

- **Transaction ID** (16 бит): случайное число, генерируемое клиентом для сопоставления ответа с запросом. В выводе dig отображается как `id: 41234`.
- **Флаги** (16 бит): управляющие биты. В выводе dig отображаются как `qr rd ra ad`.
- **QDCOUNT/ANCOUNT/NSCOUNT/ARCOUNT**: количество записей в каждой секции. Dig показывает их как `QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1`.

EDNS0 реализуется через псевдо-запись **OPT** в секции Additional:
- Позволяет увеличить размер UDP-пакета свыше 512 байт (до 4096 байт, рекомендуется 1232).
- Добавляет флаг `do` (DNSSEC OK) и размер буфера `udp: 4096`.

### Транспортные протоколы: UDP vs TCP

| Характеристика | UDP | TCP |
| :--- | :--- | :--- |
| **Лимит размера** | 512 байт (без EDNS), до 4096 байт (с EDNS) | 65535 байт |
| **Флаг TC** | Устанавливается при превышении лимита → клиент переключается на TCP | Не применяется |
| **Соединение** | Stateless | Stateful (3-way handshake) |
| **Таймаут (типичный)** | 2–5 секунд | 5–30 секунд |
| **Использование** | 90%+ DNS-трафика | AXFR/IXFR, большие ответы DNSSEC |

**Когда dig переключается на TCP:**
- Ответ превышает лимит UDP (флаг `TC` в заголовке).
- Явное указание флага `+tcp`.
- Зонная передача (AXFR/IXFR) — всегда по TCP.
- Сервер возвращает `FORMERR` при использовании EDNS.

### Коды ответов и флаги

#### Коды статуса (RCODE)

| Статус | Описание |
| :--- | :--- |
| **NOERROR** | Запрос выполнен успешно. |
| **NXDOMAIN** | Доменное имя не существует. |
| **SERVFAIL** | Ошибка на стороне DNS-сервера (проблемы с рекурсией или зоной). |
| **REFUSED** | Запрос отклонён сервером (например, по ACL или лимитам). |
| **FORMERR** | Ошибка формата запроса (сервер не смог понять запрос). |
| **NOTIMP** | Функциональность не реализована на сервере. |
| **NOTAUTH** | Сервер не является авторитетным для указанной зоны. |

#### Флаги ответа

| Флаг | Описание |
| :--- | :--- |
| **qr** | Query/Response — это ответ (отсутствие флага означает запрос). |
| **aa** | Authoritative Answer — ответ получен от владельца зоны (не из кэша). |
| **rd** | Recursion Desired — клиент запросил рекурсию (установлено в запросе). |
| **ra** | Recursion Available — сервер поддерживает рекурсию. |
| **tc** | TrunCated — пакет был обрезан (требуется переход на TCP). |
| **ad** | Authenticated Data — данные успешно проверены через DNSSEC. |
| **cd** | Checking Disabled — серверу предписано не проверять DNSSEC. |

### Конфигурация и автоматизация

#### Файл .digrc

Параметры, указанные в `~/.digrc`, применяются автоматически к каждому запуску `dig`. Это удобно для постоянного использования лаконичного вывода.

```bash
# Пример содержимого .digrc
+nocookie
+multiline
+noall
+answer
+stats
```

**Безопасность:** не храните в `.digrc` конфиденциальные данные (например, TSIG-ключи в явном виде). Файл доступен для чтения всем пользователям системы.

#### Пакетная обработка (Batch mode)

Для проверки большого списка доменов используйте флаг `-f`.

```bash
# domains.txt содержит список имен, по одному на строку
dig -f domains.txt +short
```

#### Параллельная обработка списка доменов

```bash
# Обработка списка в 20 параллельных потоков
cat domains.txt | xargs -P 20 -I {} dig +short {}
```

#### Использование в systemd-таймерах

```ini
# /etc/systemd/system/dig-check.service
[Unit]
Description=DNS health check

[Service]
Type=oneshot
ExecStart=/usr/bin/dig @8.8.8.8 example.com +short
```

### Основные опции

| Опция | Описание |
| :--- | :--- |
| `+short` | Краткий вывод (только значения данных). |
| `+multiline` | Многострочный, легкочитаемый формат записей (например, для SOA). |
| `+noall +answer` | Скрыть всё, кроме секции ответа. |
| `+trace` | Трассировка пути от корневых серверов до авторитетных. |
| `+tcp` | Принудительное использование TCP вместо UDP. |
| `-x` | Обратный DNS-запрос (Reverse Lookup) — IP в домен. |
| `-p <port>` | Использовать нестандартный порт (по умолчанию 53). |
| `-4` / `-6` | Принудительное использование IPv4 или IPv6. |
| `+dnssec` | Запросить записи DNSSEC (RRSIG, DNSKEY). |
| `+client=<subnet>` | Использовать EDNS Client Subnet (ECS) для проверки GeoDNS. |
| `+nsid` | Запросить идентификатор сервера (Name Server ID). |
| `+json` / `+yaml` | Структурированный вывод (BIND 9.18+). |
| `+bufsize=<size>` | Установить размер UDP-буфера (по умолчанию 512, рекомендуется 4096 для DNSSEC). |
| `+time=<seconds>` | Таймаут на запрос (по умолчанию 5 секунд). |
| `+tries=<count>` | Количество попыток (по умолчанию 3). |
| `+retry=<count>` | Количество повторных попыток при TCP-соединении. |
| `+dscp=<value>` | Установить значение DSCP (0–63) для маркировки трафика QoS. |
| `+ignore` | Игнорировать ошибки соединения (полезно для массовых проверок). |
| `+besteffort` | Пытаться интерпретировать повреждённые ответы. |
| `+edns=<version>` | Указать версию EDNS (по умолчанию 0). |
| `+cookie` | Включить DNS Cookies (RFC 7873) для защиты от амплификаций. |
| `+subnet=<subnet>` | Эквивалент `+client`, передаёт подсеть для GeoDNS. |
| `+ttlunits` | Отображать TTL в человекочитаемом формате (сек/мин/час/дни). |
| `+qr` | Показывать исходный запрос в выводе. |
| `+comments` | Включить комментарии в вывод (по умолчанию включено). |

### Коды возврата (Exit Codes)

| Код | Описание |
| :--- | :--- |
| **0** | Запрос выполнен успешно (NOERROR). |
| **1** | Ошибка использования (неверные параметры). |
| **2** | Ошибка разрешения (DNS-сервер недоступен). |
| **3** | Ошибка формата ответа. |
| **5** | Таймаут запроса. |
| **8** | Ошибка выделения памяти. |
| **9** | Не удалось отправить запрос. |
| **10** | Ожидаемый ответ не получен (например, при использовании `-x`). |
| **11** | Нет записей в ответе (NXDOMAIN, NODATA). |
| **12** | Ошибка чтения файла (флаг `-f`). |

### Типичные сообщения об ошибках

| Сообщение | Причина | Решение |
| :--- | :--- | :--- |
| `connection timed out` | Сервер недоступен или пакеты теряются | Проверьте доступность порта 53: `nc -zv <host> 53` |
| `no servers could be reached` | Все указанные DNS-серверы недоступны | Проверьте `/etc/resolv.conf`, сетевую связность, firewall |
| `communications error to <ip>#53: operation timed out` | Таймаут при отправке запроса | Увеличьте `+time`, проверьте MTU и фаервол |
| `malformed response` | Сервер вернул невалидный ответ | Попробуйте `+tcp`, проверьте целостность пакета |
| `could not get address for <host>: not found` | NXDOMAIN или NODATA | Проверьте правильность имени, кэш резолвера |
| `tsig verify failure` | Неверная подпись TSIG | Проверьте ключ, синхронизацию времени, алгоритм |

## Практические сценарии

### Сценарий 1: Базовый запрос и выбор типа записи

```bash
dig ya.ru            # Запрос A-записи (по умолчанию)
dig ya.ru MX         # Запрос почтовых серверов
dig ya.ru TXT        # Запрос текстовых записей (SPF/DKIM)
dig example.com ANY  # Запрос всех известных записей (может быть ограничен сервером)
```

### Сценарий 2: Диагностика GeoDNS через Client Subnet

Позволяет проверить, какой IP вернет сервер для пользователя из другого региона.

```bash
# Имитация запроса из сети Нью-Йорка (США)
dig @8.8.8.8 google.com +client=72.224.0.0/16
```

### Сценарий 3: Проверка идентификатора сервера (NSID)

Используется для определения того, в какой конкретно Anycast-узел попал запрос.

```bash
dig @8.8.8.8 google.com +nsid +short
# → nsid: 67 31 34 32 (g.vrsn.net)
```

### Сценарий 4: Трассировка и диагностика зон

```bash
# Просмотр всей цепочки делегирования
dig example.com +trace

# Проверка SOA-записи с подробным форматированием
dig example.com SOA +multiline

# Проверка возможности трансфера зоны (AXFR)
dig @ns1.example.com example.com AXFR
```

### Сценарий 5: Современные и специфические записи

```bash
# Проверка HTTPS-записи (используется для Service Binding и ALPN)
dig google.com HTTPS

# Проверка записей безопасности (CAA, TLSA, SSHFP)
dig google.com CAA
dig _443._tcp.example.com TLSA
dig example.com SSHFP
```

### Сценарий 6: Шифрованные протоколы (DoH/DoT)

Требует BIND 9.18+.

```bash
# DNS over TLS (DoT)
dig +tls @1.1.1.1 example.com

# DNS over HTTPS (DoH)
dig +https @8.8.8.8 example.com
```

### Сценарий 6a: Проверка DoH через kdig (Knot DNS)

`kdig` — утилита из пакета `knot-dns-utils`, альтернатива `dig` с расширенным выводом TLS-параметров и нативной поддержкой DoH/DoT.

```bash
# Debian/Ubuntu
sudo apt install -y knot-dnsutils

# RHEL/Fedora
sudo dnf install -y knot-dns-utils

# Проверка версии
kdig -v
# → kdig 3.2.5
```

**DoH-запрос с детализацией TLS-сессии:**

```bash
# Запрос через DoH (аналогично dig +https)
kdig @dns.yandex.com +https networks-course.ru

# В выводе присутствуют детали:
# - TLS-рукопожатие (TLS 1.3, набор шифров)
# - HTTP/2-сессия (метод POST, путь /dns-query)
# - HTTP-статус 200 OK
# - Бинарный DNS-ответ
```

**Сравнение транспортов (одинаковое содержимое, разные обёртки):**

```bash
# Прямой DNS (UDP 53)
kdig @8.8.8.8 example.com

# DNS over TLS (TCP 853)
kdig @1.1.1.1 +tls example.com

# DNS over HTTPS (TCP 443)
kdig @dns.yandex.com +https example.com
```

### Сценарий 7: Диагностика за балансировщиками (PROXYv2)

Используется для тестирования серверов, ожидающих протокол PROXY (BIND 9.20+).

```bash
dig +proxy @10.0.0.5 example.com
```

### Сценарий 8: Машиночитаемый вывод для скриптов

```bash
# Извлечение только IP-адреса через JSON и jq
dig example.com +json | jq -r '.answer[] | select(.type == "A") | .data'
```

### Сценарий 9: Сравнение ответов нескольких резолверов

Выявляет рассинхронизацию кэшей, Split-horizon DNS и проблемы делегирования.

```bash
# Сравнение ответов от трёх публичных резолверов
for server in 8.8.8.8 1.1.1.1 9.9.9.9; do
  echo "=== $server ==="
  dig @$server example.com +short
done
```

### Сценарий 10: Диагностика переключения TCP/UDP

Проверяет, какие ответы обрезаются (флаг TC) и требуют TCP.

```bash
# Проверка флага TC в ответе
dig example.com +dnssec +noall +header
# → ;; flags: qr rd ra tc; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
#    (флаг tc=1 — ответ обрезан)

# Принудительный TCP для получения полного ответа
dig example.com +dnssec +tcp +noall +answer
```

### Сценарий 11: Проверка DNSSEC-цепочки доверия

```bash
# Запрос с DNSSEC-записями
dig example.com +dnssec +multiline

# Проверка с отключением валидации (для диагностики)
dig example.com +dnssec +cd +noall +answer

# Проверка DNSKEY авторитетного сервера
dig example.com DNSKEY +dnssec
```

### Сценарий 12: Тестирование зонной передачи (AXFR)

```bash
# Попытка неавторизованной передачи зоны
dig @ns1.example.com example.com AXFR +noall +answer

# Передача с TSIG-аутентификацией
dig @ns1.example.com example.com AXFR -k /etc/bind/mykey.key +noall +answer
```

### Сценарий 13: Проверка конфигурации форвардера

Проверяет, что локальный DNS-сервер корректно пересылает запросы upstream.

```bash
# Запрос через локальный форвардер
dig @127.0.0.1 example.com +short

# Трассировка через форвардер
dig @127.0.0.1 example.com +trace

# Проверка, что форвардер не возвращает кэшированные данные
dig @127.0.0.1 example.com +cd
```

### Сценарий 14: Обнаружение кэш-отравления (Cache Poisoning)

Сравнение ответов от резолвера и авторитетного сервера.

```bash
# Ответ от резолвера (может быть кэширован)
dig @8.8.8.8 example.com +short

# Ответ напрямую от авторитетного сервера
dig @ns1.example.com example.com +short

# Если ответы различаются — возможное кэш-отравление
# Очистка кэша резолвера (если доступно)
dig @127.0.0.1 example.com +cd
```

### Сценарий 15: Мониторинг TTL и кэширования

Отслеживание изменения TTL для планирования миграций.

```bash
# Получение TTL для записи
dig example.com +ttlunits +noall +answer

# Проверка остаточного TTL в кэше резолвера
dig example.com +noall +answer
# → example.com.    3499    IN    A    93.184.216.34
#    (второе поле — TTL, уменьшается с каждым запросом)
```

### Сценарий 16: Проверка после изменения DNS-записей

Смoke-тест после обновления зоны.

```bash
# 1. Проверить серию зоны
dig example.com SOA +short
# → ns1.example.com. admin.example.com. 2023091501 3600 600 86400 3600

# 2. Проверить новую запись
dig new-sub.example.com +short

# 3. Проверить старую запись (если изменялся IP)
dig example.com +short

# 4. Проверить распространение (разные серверы)
dig @ns1.example.com example.com +short
dig @ns2.example.com example.com +short
```

### Сценарий 17: Диагностика проблем с обратным резолвингом (PTR)

```bash
# Прямой запрос PTR-записи
dig -x 93.184.216.34

# Проверка через IN-ADDR.ARPA
dig 34.216.184.93.in-addr.arpa PTR +short

# Проверка обратного резолвинга через getent (NSS)
getent hosts 93.184.216.34
```

### Сценарий 18: Тестирование параметров /etc/resolv.conf

Проверка параметров `ndots`, `search`, `timeout` через прямой запрос.

```bash
# Имитация ndots=5 (добавляет search domain)
dig api.example.com +search +ndots=5

# Проверка с явным указанием search domain
dig api.example.com.svc.cluster.local +short

# Проверка таймаута
dig @8.8.8.8 example.com +time=1 +tries=1 +stats
```

### Сценарий 19: Проверка ECS (EDNS Client Subnet) для CDN

```bash
# Без ECS (резолвер передаёт только IP клиента)
dig @8.8.8.8 example.com +short

# С ECS из подсети 72.224.0.0/16 (Нью-Йорк)
dig @8.8.8.8 example.com +client=72.224.0.0/16 +short

# С ECS из подсети 213.180.193.0/24 (Москва)
dig @8.8.8.8 example.com +client=213.180.193.0/24 +short
```

### Сценарий 20: Скрипт-проверка работоспособности DNS

```bash
#!/bin/bash
# dig_healthcheck.sh — простой чекер доступности DNS-серверов

SERVERS=("8.8.8.8" "1.1.1.1" "9.9.9.9")
DOMAIN="example.com"
TIMEOUT=2

for server in "${SERVERS[@]}"; do
  if dig @"$server" "$DOMAIN" +time="$TIMEOUT" +tries=1 +short | grep -qE '^[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+$'; then
    echo "OK: $server"
  else
    echo "FAIL: $server"
  fi
done
```

### Сценарий 21: Диагностика через dig + tcpdump
