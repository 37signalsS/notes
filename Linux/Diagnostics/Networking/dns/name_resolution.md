# Порядок разрешения имён в Linux

## Определения

**Разрешение имён (name resolution)** — процесс преобразования доменного имени в IP-адрес системным резолвером glibc согласно порядку, заданному в `/etc/nsswitch.conf`.

**NSS (Name Service Switch)** — механизм Linux, определяющий источники данных для разрешения имён: локальные файлы (`files`), DNS (`dns`), mDNS (`mdns_minimal`) и другие.

## Базовые концепции

### Порядок разрешения

Стандартная строка в `/etc/nsswitch.conf`:

```
hosts: files dns
```

**Последовательность:**

1. **`files`** — проверка `/etc/hosts` (локальные переопределения)
2. **`dns`** — запрос к DNS-серверам из `/etc/resolv.conf`

> **Важно:** Запись в `/etc/hosts` имеет приоритет над DNS, что часто маскирует реальные проблемы с разрешением имён.

### Полная цепочка разрешения

```
Приложение (браузер, curl)
    ↓
Системный резолвер (glibc)
    ↓
/etc/nsswitch.conf (порядок: files → dns)
    ↓
┌─────────────────┬─────────────────┐
│   /etc/hosts    │   DNS-серверы   │
│   (локально)    │   (резолвер)    │
└─────────────────┴─────────────────┘
    ↓
DNS-кэш ОС (если включён, например systemd-resolved)
    ↓
┌─────────────────────────────────┐
│  Корневые DNS-серверы (.)       │
│  → TLD-серверы (.com, .ru)      │
│  → Авторитетные серверы         │
└─────────────────────────────────┘
```

### Вектор атаки: `/etc/hosts`

Вредоносное ПО может добавлять записи в `/etc/hosts` для перенаправления трафика на фишинговые IP-адреса. Запущенные процессы кэшируют результаты разрешения и **не перечитывают** файл немедленно — требуется перезапуск процесса.

> **См. также:** [Настройка DNS-клиента](../../../Networking/Concepts/dns_client.md) — детальное описание механизма разрешения.

## Практические сценарии

### Сценарий 1: Проверка порядка разрешения имён

```bash
# Проверить текущий порядок
grep '^hosts:' /etc/nsswitch.conf
# Ожидается: hosts: files dns

# Проверить содержимое /etc/hosts
cat /etc/hosts
```

### Сценарий 2: Диагностика маскировки проблем через /etc/hosts

**Симптом:** Домен разрешается, но в неожиданный IP-адрес.

```bash
# Проверить, есть ли запись в hosts
grep 'example.com' /etc/hosts

# Сравнить с реальным DNS
dig example.com +short
```

Если IP из `/etc/hosts` отличается от DNS — запись маскирует проблему или является несанкционированной.

### Сценарий 3: Проверка целостности /etc/hosts

```bash
# Сверить с известными записями
cat /etc/hosts

# Проверить изменения через auditd (если настроен)
ausearch -f /etc/hosts -i
```

### Сценарий 4: Проблема с кэшированием после изменения /etc/hosts

**Симптом:** Изменили `/etc/hosts`, но приложение продолжает использовать старый IP.

**Причина:** Запущенные процессы кэшируют результаты разрешения.

**Решение:**

```bash
# Очистить кэш systemd-resolved (если используется)
resolvectl flush-caches

# Перезапустить приложение/сервис
sudo systemctl restart <service>
```
