# Порядок разрешения имён в Linux: диагностика

## Определения

**NSS (Name Service Switch)** — механизм в Unix-подобных системах, определяющий источники данных для разрешения различных системных сущностей, включая имена хостов. Настраивается через `/etc/nsswitch.conf`.

**Системный резолвер** — часть библиотеки glibc, которая обрабатывает запросы приложений на разрешение имён, следуя правилам NSS.

**mDNS (Multicast DNS)** — протокол разрешения имён в локальной сети без использования централизованного DNS-сервера (использует домен `.local`). В Linux реализуется через службу Avahi.

## Базовые концепции

### Диагностические инструменты

Для корректной диагностики необходимо понимать разницу между инструментами, использующими системный резолвер, и инструментами прямого опроса:

| Инструмент | Уровень работы | Что проверяет |
| :--- | :--- | :--- |
| **getent hosts** | Системный (NSS) | Итоговый результат для приложений (учитывает `/etc/hosts` и NSS). |
| **dig / host** | Протокольный (DNS) | Работоспособность конкретных DNS-серверов в обход NSS. |
| **resolvectl query** | Служба (systemd) | Состояние кэша и ответ от `systemd-resolved`. |
| **avahi-resolve** | Локальная сеть | Разрешение имён в сегменте L2 (mDNS). |

### Ключевые файлы

- **`/etc/nsswitch.conf`** — «карта» поиска. Строка `hosts:` определяет последовательность (например, сначала файлы, потом DNS).
- **`/etc/hosts`** — локальные статические записи.
- **`/etc/resolv.conf`** — настройки DNS-серверов для источника `dns`.

Полная теория и описание файлов представлены в разделе [DNS-клиент в Linux: концепции](../../../Networking/Concepts/dns_client.md).

## Практические сценарии

### Сценарий 1: Проверка цепочки разрешения (NSS vs DNS)

Если домен резолвится в неожиданный IP или не резолвится вовсе, необходимо проверить расхождение между системным и прямым ответом.

```bash
# 1. Проверить системный результат (как видят приложения)
getent hosts example.com

# 2. Проверить ответ конкретно от DNS
dig example.com +short
```

**Интерпретация:**

- Если `getent` выдает результат, а `dig` — нет: запись жестко прописана в `/etc/hosts`.
- Если IP различаются: локальный файл `hosts` переопределяет данные из DNS (либо в NSS первым стоит другой источник, например `mdns`).

### Сценарий 2: Диагностика задержек из-за mDNS

Если разрешение имён (особенно несуществующих) занимает несколько секунд, причиной часто является некорректная настройка Multicast DNS.

**Признаки:**

- Задержка около 5 секунд при каждом новом запросе.
- В `/etc/nsswitch.conf` указан источник `mdns` или `mdns_minimal` без условий.

**Диагностика:**

```bash
# Проверить разрешение через Avahi
avahi-resolve -n hostname.local
```

**Решение:** Убедиться, что в `nsswitch.conf` используется условие `[NOTFOUND=return]` после `mdns_minimal`, чтобы предотвратить поиск обычных доменов через multicast.

### Сценарий 3: Расхождение IP между разными процессами

Бывают ситуации, когда одно приложение видит новый IP, а другое — старый.

**Возможные причины:**

1. **Игнорирование NSS:** Некоторые рантаймы (Go без CGO, Java) или контейнеры могут читать `/etc/resolv.conf` напрямую, полностью игнорируя `/etc/hosts`.
2. **Кэширование на уровне приложения:** Долгоживущие процессы (базы данных, Java-приложения) кэшируют IP в памяти и не перечитывают данные до перезапуска, даже если TTL записи истек.
3. **Кэш ОС:** Если используется `nscd` или `systemd-resolved`, проверьте состояние их кэша.

```bash
# Очистка кэша systemd-resolved
resolvectl flush-caches
```

### Сценарий 4: Выявление «фантомных» записей в hosts

Старые записи в `/etc/hosts` часто маскируют реальные IP серверов после миграций.

**Диагностика:**

```bash
# Поиск совпадений в системном файле
grep -w "example.com" /etc/hosts
```

Всегда проверяйте этот файл первым при любых аномалиях с разрешением имён на конкретном хосте.
