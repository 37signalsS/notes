# Порядок разрешения имён в Linux: диагностика

## Базовые концепции

Процесс разрешения имён управляется системным резолвером и настраивается через `/etc/nsswitch.conf`. Детальное описание механизмов и файлов конфигурации см. в заметке [DNS-клиент в Linux: конфигурация и принципы работы](../../../Networking/Concepts/dns_client.md).

### Ключевые инструменты диагностики

1. **`getent hosts <domain>`** — **эталонный метод**. Показывает результат разрешения так, как его видит система и большинство приложений (использует glibc).
2. **`dig <domain>`** — прямой запрос к DNS. Игнорирует `/etc/hosts` и `nsswitch.conf`. Полезен для проверки работоспособности конкретных DNS-серверов.
3. **`avahi-resolve -n <hostname>.local`** — диагностика mDNS (Multicast DNS). Помогает выявить проблемы с резолвингом в локальной сети без выделенного DNS.

## Практические сценарии

### Сценарий 1: Проверка цепочки разрешения

Если домен резолвится в неожиданный IP или не резолвится вовсе:

```bash
# 1. Проверить порядок источников
cat /etc/nsswitch.conf | grep hosts

# 2. Проверить системный результат
getent hosts example.com

# 3. Проверить прямой DNS-ответ
dig example.com +short
```

**Анализ результатов:**
* Если `getent` выдает IP, а `dig` — нет: запись жестко прописана в `/etc/hosts`.
* Если `getent` и `dig` выдают разные IP: `/etc/hosts` перебивает DNS или в цепочке NSS стоит источник (например, `mdns`), который отдает старые данные.

### Сценарий 2: Диагностика mDNS задержек

mDNS может добавлять значительные задержки (до 5 секунд), если система пытается разрешить имя через multicast, а сеть не отвечает или заблокирована.

```bash
# Проверить разрешение через Avahi
avahi-resolve -n hostname.local
```

Если резолвинг `.local` имен тормозит, проверьте наличие `mdns_minimal [NOTFOUND=return]` в `nsswitch.conf`. Флаг `[NOTFOUND=return]` предотвращает переход к обычному DNS для `.local` доменов, что экономит время.

### Сценарий 3: Расхождение IP между процессами

Разные процессы могут получать разные IP для одного домена, если:
* Один процесс использует системный резолвер (`getent`), а другой — встроенную DNS-библиотеку (как Go-приложения без CGO или некоторые Java-стеки), которая игнорирует настройки NSS.
* Применяется балансировка DNS с низким TTL, и процессы запрашивают данные в разное время.

## Что ломается на практике

1. **Локальные переопределения (`/etc/hosts`):** старые записи в `hosts` годами маскируют реальные IP серверов, вызывая ошибки при миграциях.
2. **Блокирующий mDNS:** если в цепочке стоит `mdns` без условий, система может долго ждать таймаута multicast-запроса перед тем, как пойти в DNS.
3. **Игнорирование NSS:** некоторые современные приложения (особенно в контейнерах) читают напрямую `/etc/resolv.conf`, полностью игнорируя `/etc/hosts` и порядок из `nsswitch.conf`.
4. **Кэширование:** изменения в `nsswitch.conf` или `hosts` применяются мгновенно для новых запросов, но запущенные сервисы (базы данных, веб-серверы) могут хранить старый IP в памяти до перезапуска.
