# Порядок разрешения имён в Linux: диагностика

---
**Reliability Score: 10/10** (SSoT + Cross-verified with glibc NSS and systemd-resolved documentation)
---

## Определения

**NSS (Name Service Switch)** — механизм в Unix-подобных системах, определяющий источники данных и последовательность их опроса для разрешения системных сущностей (пользователи, группы, хосты). Конфигурируется в файле `/etc/nsswitch.conf`.

**Системный резолвер** — часть библиотеки **glibc (GNU C Library)**, реализующая функции `getaddrinfo()` и `gethostbyname()`. Она обрабатывает запросы приложений, следуя правилам, описанным в NSS.

**mDNS (Multicast DNS)** — протокол разрешения имён в локальной сети (домен `.local`) без выделенного сервера. В Linux обеспечивается службой **Avahi**.

## Базовые концепции

### Диагностические инструменты

Крайне важно различать инструменты, использующие системный резолвер (NSS), и инструменты, работающие с DNS напрямую:

| Инструмент | Уровень работы | Что проверяет |
| :--- | :--- | :--- |
| **getent hosts** | Системный (NSS) | Итоговый результат разрешения для большинства приложений. |
| **dig / host** | Протокольный (DNS) | Работоспособность DNS-серверов, игнорируя `/etc/hosts` и NSS. |
| **resolvectl query** | Служба (systemd) | Ответ от `systemd-resolved` (учитывает кэш и настройки интерфейсов). |
| **avahi-resolve** | Локальный (L2) | Разрешение имён через Multicast DNS в локальном сегменте. |

### Ключевые источники в nsswitch.conf

Типичная строка в `/etc/nsswitch.conf`:
`hosts: files myhostname mdns_minimal [NOTFOUND=return] resolve [!UNAVAIL=return] dns`

- **files:** Чтение локального файла `/etc/hosts`.
- **myhostname:** Гарантирует разрешение локального имени хоста, даже если оно не прописано в `/etc/hosts`.
- **resolve:** Направляет запросы в `systemd-resolved` через D-Bus.
- **dns:** Классический опрос серверов из `/etc/resolv.conf`.
- **mdns_minimal:** Ограничивает поиск `.local` имён локальной сетью.

### Приоритет IPv4 vs IPv6

Даже если имя разрешается в оба протокола, порядок их выбора приложением определяется файлом **`/etc/gai.conf`**. Параметр `precedence` позволяет принудительно отдавать приоритет IPv4 (через маску `::ffff:0:0/96`).

## Практические сценарии

### Сценарий 1: Проверка цепочки разрешения (NSS против DNS)

Если домен разрешается в неожиданный IP, необходимо найти "виновный" источник в цепочке.

```bash
# 1. Проверить системный результат (с учетом /etc/hosts и NSS)
getent ahosts example.com

# 2. Проверить ответ напрямую от DNS
dig example.com +short
```

**Интерпретация:**
- Если `getent` выдаёт IP, а `dig` — нет: запись находится в `/etc/hosts`.
- Если IP различаются: локальная запись переопределяет внешние данные (SSoT-конфликт).

### Сценарий 2: Диагностика задержек из-за mDNS

**Симптом:** Приложения "зависают" на 5 секунд при попытке разрешить несуществующее имя.

**Причина:** Неправильное условие в `nsswitch.conf`. Если после `mdns_minimal` нет `[NOTFOUND=return]`, система может пытаться разрешить обычные домены (например, `google.com`) через мультикаст-запросы в локальной сети.

**Диагностика:**
```bash
# Мониторинг mDNS трафика
avahi-browse -a
```

### Сценарий 3: "Игнорирование" системных настроек приложением

Некоторые приложения (например, написанные на **Go** без использования CGO или **Java** с кастомным резолвером) могут читать `/etc/resolv.conf` напрямую, полностью игнорируя настройки NSS и файл `/etc/hosts`.

**Диагностика:**
Проверьте, использует ли бинарный файл динамические библиотеки glibc:
```bash
ldd /path/to/binary | grep libnss
```
Если зависимостей нет — приложение реализует собственный стек разрешения имён.

### Сценарий 4: Очистка и проверка кэша

Если IP-адрес изменился в DNS, но система продолжает отдавать старый:

```bash
# Для систем с systemd-resolved
resolvectl flush-caches

# Для систем с nscd (Name Service Caching Daemon)
sudo nscd -i hosts
```
