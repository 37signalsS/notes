# Диагностика DNS в контейнерах

## Определения

**DNS в контейнерах** — механизм разрешения доменных имён внутри изолированных сетевых пространств. В отличие от хостовых систем, контейнеры часто используют специализированные прокси-серверы (Docker `127.0.0.11`) или внутрикластерные службы (CoreDNS в Kubernetes).

**Встроенный DNS Docker** — локальный резолвер на адресе `127.0.0.11`, который перенаправляет запросы к DNS-серверам хоста. Его конфигурация статична и не всегда обновляется при изменении сетевых настроек хост-системы (например, при подключении VPN).

**CoreDNS** — стандартный DNS-сервер для Kubernetes, обеспечивающий обнаружение сервисов внутри кластера и пересылку внешних запросов.

## Базовые концепции

### Особенности разрешения имён

В контейнеризированных средах процесс разрешения имён имеет ряд архитектурных отличий от классического Linux-хоста:

| Среда | DNS-сервер | Основная задача |
| :--- | :--- | :--- |
| **Docker** | `127.0.0.11` | Проксирование на хост + разрешение имен контейнеров в пользовательских сетях. |
| **Kubernetes** | CoreDNS (`ClusterIP`) | Разрешение имен сервисов (`svc.cluster.local`) и подов. |
| **K8s + NodeLocalDNS** | `169.254.25.10` | Локальное кэширование на узле для снижения нагрузки на CoreDNS. |

### Типичные точки отказа

1. **Рассинхронизация Docker и хоста:** Контейнеры продолжают использовать старые DNS-серверы после смены Wi-Fi сети или активации VPN на хосте.
2. **Проблемы с search-доменами:** В Kubernetes избыточное количество поисковых суффиксов в сочетании с высоким `ndots` (обычно 5) вызывает значительные задержки при разрешении внешних имен.
3. **Недоступность CoreDNS:** Перегрузка, ошибки конфигурации или проблемы с сетевой связностью (NetworkPolicies) внутри кластера.

## Практические сценарии

### Сценарий 1: Первичная проверка в Docker

Если контейнер не разрешает имена, но хост работает корректно, следует проверить цепочку проксирования.

```bash
# 1. Проверить resolv.conf внутри контейнера
docker exec <container_id> cat /etc/resolv.conf
# Ожидается: nameserver 127.0.0.11

# 2. Тестовый запрос напрямую к встроенному резолверу
docker exec <container_id> dig ya.ru
# Если ответ SERVFAIL — встроенный DNS потерял связь с вышестоящими серверами.
```

**Решение:** Перезапуск контейнера или настройка статических DNS в `/etc/docker/daemon.json`. Подробные методы исправления — в разделе **[Решение проблем с DNS в Docker](../../../../Docker/Docker_network/troubleshooting/dns_resolution_issues.md)**.

### Сценарий 2: Диагностика в Kubernetes

При проблемах с обнаружением сервисов или внешних ресурсов в кластере:

```bash
# 1. Проверить статус подов и логов CoreDNS
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system -l k8s-app=kube-dns

# 2. Проверить resolv.conf в проблемном поде
kubectl exec <pod_name> -- cat /etc/resolv.conf
# Проверьте значение ndots и список search-доменов.

# 3. Тестовый запрос FQDN сервиса
kubectl exec <pod_name> -- nslookup <service_name>.<namespace>.svc.cluster.local
```

При выявлении задержек или ошибок конфигурации обратитесь к детальному руководству: **[DNS в Kubernetes](../../../../Kubernetes/Networking/dns_deep_dive.md)**.

### Сценарий 3: Анализ DNS-трафика в реальном времени

Если стандартные утилиты не дают ответа, необходимо увидеть "живой" обмен пакетами.

```bash
# Требуется установленный tcpdump (на хосте или в контейнере)
tcpdump -n -p -i eth0 port 53
```

Этот метод позволяет увидеть избыточные запросы к доменам поиска (например, `google.com.default.svc.cluster.local`), вызванные высоким значением `ndots`.
