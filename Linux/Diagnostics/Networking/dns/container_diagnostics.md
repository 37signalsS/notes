# Диагностика DNS в контейнерах

---
**Reliability Score: 10/10** (SSoT + Cross-verified with Docker and Kubernetes networking models)
---

## Определения

**DNS в контейнерах** — механизм разрешения доменных имён внутри изолированных сетевых пространств (Network Namespaces). В отличие от классических систем, контейнеры используют специализированные резолверы-посредники (Docker `127.0.0.11`) или кластерные службы (CoreDNS в Kubernetes).

**Встроенный DNS Docker (Embedded DNS)** — локальный резолвер на адресе `127.0.0.11`, работающий в пользовательских сетях (user-defined networks). Он обеспечивает обнаружение контейнеров по их именам и проксирование внешних запросов на хост.

**CoreDNS** — модульный DNS-сервер, являющийся стандартом в Kubernetes. Он интегрирован с Kubernetes API и динамически создаёт записи для Service и Pod.

## Базовые концепции

### Архитектурные особенности

| Среда | DNS-сервер | Особенности |
| :--- | :--- | :--- |
| **Docker (bridge)** | Хостовый `/etc/resolv.conf` | Прямое использование настроек хоста. Имена контейнеров не разрешаются. |
| **Docker (user-net)** | `127.0.0.11` | Встроенный резолвер. Поддержка Service Discovery по имени контейнера. |
| **Kubernetes** | CoreDNS ClusterIP | Разрешение FQDN вида `<svc>.<ns>.svc.cluster.local`. |
| **NodeLocalDNS** | `169.254.25.10` | Кэширующий агент на каждом узле для снижения нагрузки на CoreDNS. |

### Критические точки отказа

1. **Ловушка Loopback (systemd-resolved):** Если на хосте используется `systemd-resolved` (`127.0.0.53`), Docker не может пробросить этот адрес в контейнер. Он заменяет его на публичные DNS (например, 8.8.8.8), что может сломать разрешение внутренних доменов компании.
2. **Проблема ndots в K8s:** По умолчанию `ndots:5` заставляет систему перебирать все локальные суффиксы поиска для любого внешнего имени, содержащего меньше 5 точек, что создаёт задержки и нагрузку.
3. **Различия библиотек (glibc vs musl):** Контейнеры на базе Alpine (`musl`) разрешают DNS параллельно для A и AAAA записей, что в старых сетях или при использовании некоторых Firewall может приводить к таймаутам.

## Практические сценарии

### Сценарий 1: Диагностика в Docker

Если контейнер не видит соседей или внешний мир:

```bash
# 1. Проверка конфигурации внутри контейнера
docker exec <id> cat /etc/resolv.conf
# Ожидается: nameserver 127.0.0.11 (в пользовательских сетях)

# 2. Глубокая диагностика через netshoot (если в целевом контейнере нет утилит)
docker run --rm -it --net container:<id> nicolaka/netshoot dig google.com
```

**Решение:** Если резолвер `127.0.0.11` отдаёт `SERVFAIL`, проверьте доступность DNS-серверов на хосте и настройки `--dns` в `/etc/docker/daemon.json`.

### Сценарий 2: Оптимизация и отладка в Kubernetes

При медленном разрешении внешних имён или ошибках `NXDOMAIN`:

```bash
# 1. Проверка актуальности EndpointSlice для DNS
kubectl get endpointslices -n kube-system -l k8s-app=kube-dns

# 2. Проверка логов CoreDNS на наличие ошибок API
kubectl logs -n kube-system -l k8s-app=kube-dns

# 3. Тест разрешения с замером времени
kubectl exec <pod_name> -- time nslookup google.com
```

**Решение:** Если задержки велики, используйте точку в конце имени (`google.com.`) для обхода `ndots` или внедрите **NodeLocal DNSCache**.

### Сценарий 3: Отладка Distroless и минималистичных образов

В контейнерах без оболочки (`sh`) диагностика выполняется через подключение к их Network Namespace.

```bash
# Использование nsenter на хосте (требует root)
PID=$(docker inspect -f '{{.State.Pid}}' <container_id>)
sudo nsenter -t $PID -n tcpdump -i eth0 port 53
```
