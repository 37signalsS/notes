## Определения

**DNS (Domain Name System)** — распределённая система преобразования доменных имён в IP-адреса и обратно. Теория и описание протокола представлены в разделе [Протокол DNS](../../../../Networking/Protocols/DNS/dns.md).

**Диагностика DNS** — комплекс мероприятий по выявлению и устранению проблем с разрешением имён, включающий проверку конфигурации клиента, анализ сетевых пакетов и оценку производительности резолвинга.

## Базовые концепции

### Архитектура диагностики в Linux

Диагностика DNS опирается на два различных уровня взаимодействия с системой:

1. **Системный резолвер (libc):** Механизм, который используют прикладные программы (`ping`, `curl`, браузеры). Его поведение определяется файлами `/etc/nsswitch.conf` (порядок поиска), `/etc/hosts` (локальные записи) и `/etc/resolv.conf` (внешние серверы).
2. **Утилиты прямого опроса (`dig`, `nslookup`, `host`):** Инструменты, отправляющие запросы напрямую к DNS-серверам. Они игнорируют локальные файлы конфигурации (hosts, nsswitch) и используются для изоляции проблем на стороне DNS-инфраструктуры.

### Ключевые инструменты

| Инструмент | Назначение | Особенности |
| :--- | :--- | :--- |
| **dig** | Детальный анализ записей | Основной инструмент. Показывает заголовки, флаги и статистику. См. [Инструмент dig](./dig_tool.md). |
| **nslookup** | Быстрая проверка | Лаконичный вывод, удобен для интерактивной работы. |
| **host** | Простой запрос | Минимальный вывод, идеален для использования в скриптах. |
| **resolvectl** | Управление резолвером | Утилита для систем с `systemd-resolved`. Управляет кэшем и статусом. |
| **delv** | Валидация DNSSEC | Инструмент для проверки цепочки доверия DNSSEC. |
| **ping** | Первичная проверка | Показывает IP в скобках при успешном разрешении имени. |
| **getent** | Проверка NSS | Показывает, как имя разрешается с учётом `/etc/hosts`. |

### Использование systemd-resolved

В современных дистрибутивах (Ubuntu 18.04+, RHEL 8+, Debian 11+) за разрешение имён отвечает служба `systemd-resolved`. Она предоставляет локальный заглушечный резолвер (stub resolver) на адресе `127.0.0.53`.

**Основные команды диагностики:**

```bash
# Текущий статус, используемые DNS-серверы и поддержка DoT/DNSSEC
resolvectl status

# Резолвинг имени через системную службу (аналог getent, но с деталями)
resolvectl query example.com

# Сброс локального DNS-кэша
resolvectl flush-caches

# Просмотр статистики кэширования (hit/miss) и запросов
resolvectl statistics
```

## Практические сценарии

### Сценарий 1: Первичная диагностика при полной потере связи

Если сетевые адреса (IP) доступны, но доменные имена не разрешаются, необходимо следовать диагностической цепочке: от проверки файлов конфигурации до прямых запросов к публичным резолверам.
Подробный алгоритм действий описан в разделе **[Базовая диагностика DNS](./basic_diagnostics.md)**.

### Сценарий 2: Анализ производительности и задержек

Высокое время `time_namelookup` в выводе `curl` или периодические «зависания» приложений часто связаны с некорректными таймаутами или длинными списками `search` в конфигурации.
Методы поиска узких мест и оптимизации собраны в разделе **[DNS resolution performance](./dns_resolution_performance.md)**.

### Сценарий 3: Диагностика в изолированных средах (контейнерах)

DNS в Docker и Kubernetes имеет специфическую архитектуру (встроенные прокси-серверы, CoreDNS). Проблемы здесь часто связаны с рассинхронизацией сети хоста и контейнера или параметром `ndots`.
Специфика диагностики описана в разделе **[Диагностика DNS в контейнерах](./container_diagnostics.md)**.

### Сценарий 4: Сложные конфигурации (Split-horizon DNS)

Ситуации, когда один и тот же домен разрешается в разные IP-адреса внутри и снаружи корпоративной сети, требуют глубокого анализа заголовков ответов и использования `resolvectl` для проверки привязки DNS к конкретным интерфейсам (link-specific DNS).
Теоретическая база представлена в разделе **[Split-horizon DNS](../../../../Networking/Protocols/DNS/dns_advanced.md#split-horizon-dns)**.
