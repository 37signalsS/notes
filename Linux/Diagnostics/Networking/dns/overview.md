# Диагностика DNS: Обзор

## Определения

**DNS (Domain Name System)** — распределённая система преобразования доменных имён в IP-адреса и обратно. Детальное описание протокола — в [Протокол DNS](../../../../Networking/Protocols/DNS/dns.md).

**Диагностика DNS** — процесс выявления и устранения проблем с разрешением имён, включающий проверку конфигурации клиента, анализ DNS-запросов и оценку производительности.

## Базовые концепции

### Архитектура диагностики

Диагностика DNS в Linux опирается на два уровня взаимодействия с DNS:

- **Системный резолвер (glibc):** Механиз, который приложения (`ping`, `curl`, браузеры) используют для разрешения имён. Поведение определяется конфигурацией: `/etc/nsswitch.conf` (порядок поиска), `/etc/hosts` (локальные записи), `/etc/resolv.conf` (DNS-серверы).

- **Утилиты прямого опроса (`dig`, `host`, `nslookup`):** Отправляют запросы напрямую к указанным DNS-серверам, игнорируя `/etc/nsswitch.conf` и `/etc/hosts`. Используются для «чистой» проверки работы DNS без влияния локальной конфигурации.

### Ключевые инструменты

| Инструмент | Назначение | Особенности |
| :--- | :--- | :--- |
| `dig` | Детальный анализ DNS-записей | Полный вывод: заголовки, секции ответа, статистика. Основной инструмент диагностики. Подробнее — в [Инструмент dig](./dig_tool.md). |
| `nslookup` | Быстрая проверка DNS-записей | Лаконичный вывод, удобен для интерактивной работы. |
| `host` | Простой DNS-запрос | Минимальный вывод, удобен для скриптов. |
| `resolvectl` | Управление `systemd-resolved` | Статус, кэш, статистика запросов, управление службой. |
| `ping` | Проверка резолвинга и связности | Показывает IP в скобках при успешном разрешении. |

### systemd-resolved

В современных дистрибутивах (Ubuntu 17.10+, RHEL 7+, Debian 10+) за разрешение имён отвечает `systemd-resolved` — локальный кэширующий резолвер. `/etc/resolv.conf` обычно является symlink на `/run/systemd/resolve/stub-resolv.conf` с `nameserver 127.0.0.53`. Базовые команды диагностики:

```bash
resolvectl status           # Текущие DNS-серверы и домены
resolvectl statistics       # Статистика кэша и запросов
resolvectl flush-caches     # Очистка кэша
resolvectl query example.com # Тестовый запрос через службу
```

Полная конфигурация — в [Конфигурация DNS-клиента](./configuration.md), теория разрешения имён — в [Порядок разрешения имён](./name_resolution.md).

## Практические сценарии

### Сценарий 1: Первичная диагностика «DNS не работает»

**Симптом:** `ping 8.8.8.8` работает, но `ping google.com` выдаёт `Name or service not known`.

**Порядок действий:**

1. Проверить конфигурацию: `cat /etc/resolv.conf`
2. Проверить доступность DNS-сервера: `nc -zv 8.8.8.8 53`
3. Выполнить прямой запрос: `dig @8.8.8.8 google.com`
4. Если прямой запрос успешен — проблема в локальной конфигурации (firewall, `systemd-resolved`, `/etc/nsswitch.conf`)

Базовый алгоритм диагностики — в [Базовая диагностика](./basic_diagnostics.md).

### Сценарий 2: Диагностика производительности DNS

**Симптом:** Сервис отвечает, но запросы периодически «подвисают». Высокое `time_namelookup` в curl.

**Диагностика:**

```bash
# Измерить время ответа многократно
for i in {1..10}; do dig +stats example.com | grep "Query time"; done

# Проверить конфигурацию resolv.conf
cat /etc/resolv.conf
# Внимание: порядок nameserver, search-домены, options ndots/timeout/attempts
```

Частые причины задержек: множественные nameserver'ы, длинные search-списки, высокий `ndots`, недоступность IPv6. Подробный разбор — в [DNS resolution performance](./dns_resolution_performance.md).

### Сценарий 3: Диагностика DNS в контейнерах

**Особенности:** Docker использует встроенный DNS-прокси (`127.0.0.11`), который может не обновлять адреса при смене сети хоста (Wi-Fi, VPN, перезапуск `systemd-resolved`). Диагностика отличается от хостовой — в [Диагностика DNS в контейнерах](./container_diagnostics.md).

### Сценарий 4: Диагностика Split-horizon DNS

**Симптом:** Сервис доступен снаружи, но не работает внутри сети (или наоборот). Подозрение на разные ответы DNS для разных зон.

**Диагностика:**

```bash
# Что видит система (с учётом NSS и кэша)
getent ahosts example.com

# Запрос через локальный резолвер (systemd-resolved)
resolvectl query example.com

# Прямой запрос к конкретному DNS-серверу (в обход локальных настроек)
dig @<dns_server_ip> example.com
```

Подробный разбор концепции и рисков — в [Split-horizon DNS](../../../../Networking/Protocols/DNS/dns_advanced.md#split-horizon-dns-split-dns).
