# Диагностика HTTP-задержек: сеть или приложение

## Определения

**Диагностика HTTP-задержек** — процесс идентификации этапа, на котором происходит замедление обработки запроса: на уровне сетевой инфраструктуры (DNS, TCP), протоколов безопасности (TLS) или внутри самого приложения (бэкенда).

Основным инструментом для решения этой задачи является **curl**. Благодаря опции `-w` (`--write-out`), утилита позволяет извлекать точные временные метрики для каждого этапа жизненного цикла HTTP-запроса.

## Основные концепции

### Логика разделения слоев

Любой HTTP-запрос проходит через последовательные стадии, каждую из которых можно измерить:

1. **Сетевой слой (Network Layer):** включает разрешение имен (DNS) и установку TCP-соединения.
2. **Слой безопасности (Security Layer):** время на выполнение TLS-рукопожатия и обмен ключами.
3. **Слой приложения (Application Layer):** время ожидания первого байта ответа (TTFB) после завершения всех сетевых и криптографических процедур.
4. **Итог (Total Time):** общее время от начала выполнения команды до завершения передачи данных.

**Базовое правило локализации:**

- Рост метрик `dns` или `connect` указывает на проблемы в **сети** или инфраструктуре.
- Рост метрики `ttfb` (starttransfer) указывает на задержки **внутри** приложения (медленные запросы к БД, тяжелая логика).

### Ключевые метрики curl

| Метрика | Описание | Слой |
| :--- | :--- | :--- |
| `time_namelookup` | Время разрешения DNS-имени | Сеть |
| `time_connect` | Время установки TCP-соединения | Сеть |
| `time_appconnect` | Время завершения TLS-рукопожатия | TLS |
| `time_starttransfer` | TTFB (Time to First Byte) | Приложение |
| `time_total` | Общее время операции | Итог |

## Практические сценарии

### 1. Детальный анализ таймингов одного запроса

Использование форматированного вывода для получения точных цифр:

```bash
curl -w "DNS: %{time_namelookup}s | Connect: %{time_connect}s | TLS: %{time_appconnect}s | TTFB: %{time_starttransfer}s | Total: %{time_total}s\n" \
-o /dev/null -s https://example.com
# → DNS: 0.001234s | Connect: 0.015432s | TLS: 0.045678s | TTFB: 0.089012s | Total: 0.091234s
```

### 2. Изоляция DNS-проблем

Сравнение обычного запроса с запросом по конкретному IP помогает исключить задержки на этапе DNS.

```bash
# Принудительное разрешение домена на конкретный IP
curl --resolve example.com:443:93.184.216.34 https://example.com
```

*Опция `--resolve` является безопасной альтернативой правке `/etc/hosts`, так как действует только в рамках текущего вызова.*

### 3. Отслеживание пауз в реальном времени

Режим `verbose` позволяет визуально оценить, на какой строке вывода возникает задержка:

```bash
curl -v https://example.com
# → *   Trying 93.184.216.34:443...
# → * Connected to example.com (93.184.216.34) port 443 (#0)
# → * ALPN, offering h2
# → (пауза на TLS-рукопожатии)
# → * SSL connection using TLSv1.3
```

### 4. Проверка стабильности (циклический тест)

Выявление плавающих задержек, характерных для нестабильной сети или балансировщиков нагрузки:

```bash
for i in {1..10}; do \
curl -o /dev/null -s -w "Attempt $i: %{time_total}s\n" https://example.com; \
done
# → Attempt 1: 0.085s
# → Attempt 2: 0.120s
# → ...
```

### 5. Сравнение локального и внешнего пути

Помогает определить, вносится ли задержка внешним интернетом или внутренним сетевым контуром.

```bash
# Локальный запрос к сервису (внутри инфраструктуры)
curl -o /dev/null -s -w "Local: %{time_total}s\n" http://127.0.0.1:8080

# Запрос через публичный адрес
curl -o /dev/null -s -w "External: %{time_total}s\n" https://example.com
```

### 6. Нагрузочное тестирование (Stress Test)

Если задержки возникают только при параллельных запросах, это свидетельствует о дефиците ресурсов (CPU, БД, пулы соединений).

```bash
# Использование ApacheBench (ab)
ab -n 200 -c 20 https://example.com/
# → Time per request: 150.234 [ms] (mean)

# Использование wrk
wrk -t2 -c50 -d10s https://example.com/
# → Requests/sec: 456.78
```

## Дополнительная информация

### Интерпретация результатов

| Метрика | Вероятная причина задержки | Рекомендуемые действия |
| :--- | :--- | :--- |
| Высокий `namelookup` | Медленный или перегруженный DNS | Проверить `/etc/resolv.conf`, использовать локальный кэш |
| Высокий `connect` | Сетевые потери, перегрузка канала, Firewall (DROP) | Проверить **[mtr](./traceroute_mtr.md)** и **[ss](./ss.md)** |
| Высокий `appconnect` | Высокая нагрузка на CPU сервера, медленная криптография | Проверить нагрузку на сервере, обновить версию TLS |
| Высокий `starttransfer` | Медленный бэкенд, блокировки в БД, неоптимальный код | Анализ логов приложения, профилирование кода |
