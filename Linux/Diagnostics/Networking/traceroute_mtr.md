# traceroute и mtr

## Определения

**`traceroute`** — консольная утилита для отслеживания маршрута следования IP-пакетов от локального хоста до удалённого узла. Она отображает список всех промежуточных маршрутизаторов (хопов), через которые проходит пакет.

**`mtr`** (My Traceroute) — современный инструмент диагностики сети, объединяющий функциональность `traceroute` и `ping`. Он постоянно отправляет пакеты, собирая динамическую статистику по каждому узлу маршрута в реальном времени.

## Основные концепции

### Принцип работы traceroute (механизм TTL)

Утилита использует поле **TTL** (Time To Live) в заголовке IP-пакета. TTL — это счётчик «прыжков», который уменьшается на 1 каждым маршрутизатором. Если TTL достигает 0, маршрутизатор отбрасывает пакет и возвращает отправителю сообщение **[ICMP Time Exceeded](../../../Networking/Protocols/ICMP/icmp_time_exceeded.md)**.

**Алгоритм работы:**

1. `traceroute` отправляет первый пакет с **TTL=1**. Первый маршрутизатор отбрасывает его и возвращает ответ — так определяется первый хоп.
2. Затем отправляется пакет с **TTL=2**, который проходит первый узел и «умирает» на втором.
3. Процесс повторяется с постепенным увеличением TTL (`TTL=3`, `TTL=4`...) до тех пор, пока пакет не достигнет целевого узла или не будет превышен лимит хопов (по умолчанию 30).

Интерпретация TTL в ответах позволяет косвенно определить ОС узла:

- **64:** Linux/Unix
- **128:** Windows
- **255:** Сетевое оборудование

### Принцип работы mtr

`mtr` работает аналогично `traceroute`, но вместо разового прохода выполняет постоянное зондирование всех узлов маршрута. Это позволяет выявить плавающие проблемы (jitter, периодические потери пакетов), которые незаметны при разовой проверке.

### Интерпретация результатов

| Симптом | Значение |
| :--- | :--- |
| Высокий `Loss%` на одном хопе, далее OK | Маршрутизатор настроен игнорировать ICMP/UDP (не является проблемой) |
| Нарастающие потери от конкретного хопа до конца | Реальная проблема на этом участке сети (перегрузка, сбой) |
| Резкий рост `Avg`/`Wrst`, сохраняющийся далее | Очереди или перегрузка на данном маршрутизаторе |
| Высокий `StDev` | Нестабильность задержки (jitter), проблемы с буферизацией |

## Практические сценарии

### Базовая трассировка маршрута

```bash
# Стандартная трассировка (обычно UDP или ICMP)
traceroute ya.ru
# → 1  192.168.1.1 (192.168.1.1)  0.345 ms  0.211 ms  0.189 ms

# Ускоренная трассировка без разрешения имён (DNS)
traceroute -n ya.ru
# → 1  192.168.1.1  0.312 ms  0.201 ms  0.178 ms

# Трассировка через TCP (порт 80) для обхода брандмауэров
sudo traceroute -n -T -p 80 ya.ru
```

### Диагностика в реальном времени с помощью mtr

```bash
# Интерактивный режим (по умолчанию)
mtr google.com
```

В интерактивном режиме `mtr` обновляет таблицу метрик каждую секунду. Рекомендуется наблюдать за выводом в течение 2–5 минут для сбора достоверной статистики.

### Генерация отчётов для анализа

```bash
# Вывод отчёта после 10 циклов (без интерактивного интерфейса)
mtr -r -c 10 ya.ru

# Подробный отчёт: 100 циклов, широкое отображение имён и AS-номеров
mtr -rwzc 100 ya.ru
# → HOST: my-workstation          Loss%   Snt   Last   Avg  Best  Wrst StDev
# →   1.|-- AS???  192.168.1.1     0.0%   100    0.3   0.4   0.2   1.5   0.2
# →   2.|-- AS1234 10.0.0.1        0.0%   100    1.5   1.8   1.2   5.4   0.5
```

Параметры команды:

- `-r`: режим отчёта (report)
- `-w`: широкий формат вывода (wide)
- `-z`: отображение номеров автономных систем (AS)
- `-c`: количество отправляемых пакетов (cycles)

## Дополнительная информация

### Сравнение протоколов трассировки

- **UDP (по умолчанию в Linux):** большинство маршрутизаторов пропускают его, но конечные хосты могут блокировать.
- **ICMP (по умолчанию в Windows `tracert`):** часто блокируется на границах сетей.
- **TCP:** наиболее эффективен для обхода брандмауэров, так как имитирует обычное веб-соединение.
