# xfr — измерение пропускной способности сети

## Определения

**`xfr`** — современный высокопроизводительный инструмент для тестирования пропускной способности сети, написанный на языке **Rust**. Является функциональной заменой `iperf3`, предлагая встроенный графический интерфейс (TUI), поддержку современных транспортных протоколов (QUIC, MPTCP) и многопоточную архитектуру на базе **Tokio** для эффективного использования ресурсов на каналах 10GbE и выше.

**Goodput** — полезная пропускная способность, измеряемая в битах/сек полезных данных прикладного уровня (за вычетом заголовков транспортного и сетевого уровней, а также повторных передач). В отличие от raw throughput, goodput отражает реальную скорость доставки данных приложению.

**BDP (Bandwidth-Delay Product)** — произведение пропускной способности канала на Round-Trip Time (RTT). Определяет минимальный объем буферов, необходимых для полной утилизации канала: `BDP = Bandwidth (bps) × RTT (s)`.

**Zero-copy I/O** — механизм передачи данных между пространством ядра и пользовательским пространством без лишнего копирования в буферы CPU, что снижает задержки и нагрузку на процессор при высоких скоростях передачи.

## Основные концепции

Инструмент реализует клиент-серверную архитектуру, оптимизированную для высоконагруженных локальных сетей и современных транспортных протоколов.

- **Многопоточность и Multi-client:** Сервер `xfr` способен обрабатывать несколько независимых сессий тестирования от разных клиентов одновременно, эффективно распределяя нагрузку по ядрам CPU за счет асинхронного рантайма **Tokio**.
- **LAN Discovery (mDNS):** Возможность автоматического обнаружения серверов в локальной сети через multicast DNS без предварительного знания их IP-адресов.
- **MPTCP (Multi-Path TCP):** Позволяет прозрачно объединять пропускную способность нескольких сетевых интерфейсов (например, Ethernet + Wi-Fi) в один поток данных. *Требует поддержки MPTCP в ядре Linux (v5.6+).*
- **QUIC:** Реализация тестирования поверх UDP с шифрованием TLS 1.3, что позволяет оценивать производительность протоколов следующего поколения (HTTP/3) и их устойчивость к потерям пакетов.
- **Интерактивный TUI:** Встроенная панель мониторинга с живыми графиками, статистикой по каждому потоку и метриками задержки.
- **Архитектура на базе Tokio:** Использование асинхронного рантайма Tokio позволяет обрабатывать тысячи соединений в рамках одного процесса, минимизируя контекстные переключения и обеспечивая масляную модель планирования задач.

### Принцип работы

1. **Инициализация:** Клиент отправляет контрольный запрос на порт 5201 (по умолчанию). Сервер отвечает и создает сессию тестирования.
2. **Negotiation:** Стороны согласовывают параметры: протокол (TCP/UDP/QUIC/MPTCP), количество потоков, длительность, целевую полосу (для UDP).
3. **Data Transfer:** Данные передаются через нумерованные потоки Tokio. Для TCP используется режим `TCP_NODELAY` для минимизации задержек на маленьких пакетах; для QUIC — реализация на базе `quinn` или аналогичной библиотеки с поддержкой 0-RTT.
4. **Metrics Collection:** С обоих сторон собирается статистика: байты отправлено/получено, ретрансмиссии (TCP), джиттер (UDP/QUIC), RTT.
5. **Reporting:** Результаты агрегируются и выводятся в TUI или JSON.

### Почему Rust / Tokio?

В отличие от `iperf3` (C, однопоточная модель), архитектура на Rust + Tokio дает:
- **Memory Safety:** Отсутствие гонок данных и утечек памяти при обработке тысяч соединений.
- **Zero-cost Abstractions:** Асинхронный код компилируется в эффективные state machines без накладных расходов, характерных для потоковой модели в high-connection scenarios.
- **Work-stealing:** Планировщик Tokio автоматически балансирует задачи между ядрами, что критично для 100GbE+ интерфейсов, где один поток не способен насыпить канал.

## Установка и проверка

### Установка

```bash
# Через Cargo (требуется Rust toolchain)
cargo install xfr

# macOS (Homebrew)
brew install lance0/tap/xfr
```

### Верификация установки

```bash
xfr --version
# → xfr 0.x.x

# Проверка доступных транспортов
xfr --list-transports
# → tcp, udp, quic, mptcp
```

### Настройка брандмауэра

По умолчанию используется порт **5201** (совместимость с `iperf3`) для управления и передачи данных.

```bash
# Разрешение трафика в ufw
sudo ufw allow 5201/tcp
sudo ufw allow 5201/udp

# Для firewalld
sudo firewall-cmd --add-port=5201/tcp --permanent
sudo firewall-cmd --add-port=5201/udp --permanent
sudo firewall-cmd --reload
```

## Параметры ядра, влияющие на тестирование

Для получения релевантных результатов необходимо настроить сетевой стек до начала тестирования. Неправильные параметры могут искусственно ограничивать пропускную способность.

### Буферы сокетов

```bash
# Максимальный размер буферов приема/отправки
sudo sysctl -w net.core.rmem_max=67108864
sudo sysctl -w net.core.wmem_max=67108864

# Диапазоны буферов TCP (min default max)
sudo sysctl -w net.ipv4.tcp_rmem="4096 87380 67108864"
sudo sysctl -w net.ipv4.tcp_wmem="4096 65536 67108864"

# Память, выделяемая под TCP-сокеты (в страницах по 4KB)
sudo sysctl -w net.ipv4.tcp_mem="8388608 12582912 16777216"
```

### Очереди соединений

```bash
# Максимальный размер очереди полностью установленных соединений
sudo sysctl -w net.core.somaxconn=65535

# Очередь полуоткрытых соединений (SYN-RECV)
sudo sysctl -w net.ipv4.tcp_max_syn_backlog=16384

# Очередь пакетов на уровне интерфейса
sudo sysctl -w net.core.netdev_max_backlog=5000
```

### Дополнительные параметры

```bash
# Включение TCP Fast Open для снижения задержки handshake
sudo sysctl -w net.ipv4.tcp_fastopen=3

# Исключение защитного алгоритма от перегрузок для чистого измерения
# (ТОЛЬКО для изолированных тестовых стендов!)
sudo sysctl -w net.ipv4.tcp_congestion_control=cubic
```

> **Важно:** Изменения через `sysctl -w` временные (до перезагрузки). Для постоянного применения добавьте параметры в `/etc/sysctl.d/99-network-benchmark.conf`.

### Аппаратная оптимизация (NIC)

```bash
# Увеличение размеров кольцевых буферов (Ring Buffers)
sudo ethtool -G eth0 rx 4096 tx 4096

# Отключение прерываний (Coalescing) для снижения задержек
sudo ethtool -C eth0 rx-usecs 0 tx-usecs 0

# Включение multi-queue (если NIC поддерживает)
sudo ethtool -L eth0 combined 8

# Проверка offloading (для тестов с маленькими пакетами может давать ложные результаты)
ethtool -k eth0 | grep -E "scatter|tx-checksum|gro|gso|tso"
```

## Практические сценарии

### Обнаружение серверов в сети

Поиск запущенных экземпляров `xfr serve` в локальном сегменте:

```bash
xfr discover
# → [Found] 192.168.1.50:5201 (hostname: srv-bench-01)
```

### Режимы работы сервера

```bash
# Обычный запуск (вывод логов в stdout)
xfr serve

# Запуск с графической панелью (мониторинг всех активных тестов)
xfr serve --tui

# Запуск как systemd-сервис (см. ниже)
```

### Базовое тестирование (TCP и UDP)

```bash
# Стандартный тест TCP (10 секунд)
xfr 192.168.1.50

# Тестирование UDP с ограничением полосы (например, 1 Гбит/с)
xfr 192.168.1.50 -u -b 1G
```

### Тестирование QUIC и MPTCP

```bash
# Тест через QUIC (UDP 443/5201)
xfr 192.168.1.50 --quic

# Тест через MPTCP (проверка агрегации каналов)
xfr 192.168.1.50 --mptcp
```

### Расширенные параметры потоков и направлений

```bash
# 10 параллельных потоков на 60 секунд
xfr 192.168.1.50 -P 10 -t 60s

# Реверсивный режим (Download: сервер -> клиент)
xfr 192.168.1.50 --reverse

# Двунаправленный режим (Full-Duplex)
xfr 192.168.1.50 --bidir
```

### Анализ регрессий производительности (`xfr diff`)

```bash
# Сохранение эталона в JSON
xfr 192.168.1.50 --json > base.json

# Сравнение текущего теста с файлом
xfr diff base.json <(xfr 192.168.1.50 --json)
# → [Diff] Result: -1.2% Bandwidth, +5ms Jitter
```

### Тестирование в контейнере (Docker/Podman)

```bash
# Сервер (host network для доступа к физическим интерфейсам)
docker run -d --name xfr-srv --network host --cap-add NET_ADMIN xfr serve

# Клиент
docker run --rm --network host xfr 192.168.1.50 -t 30 -P 4
```

> **Примечание:** Без `--network host` Docker применяет собственный стек, что измеряет производительность моста/оверлея, а не физического канала.

### NUMA-aware тестирование

На системах с несколькими сокетами (NUMA) важно привязывать процессы и прерывания к одному узлу для избежания доступа к удаленной памяти.

```bash
# Проверка топологии NUMA
numactl --hardware

# Запуск сервера на NUMA-node 0
numactl --cpunodebind=0 --membind=0 xfr serve

# Запуск клиента на NUMA-node 0
numactl --cpunodebind=0 --membind=0 xfr 192.168.1.50 -P 8
```

### Привязка к CPU и IRQ балансировка

```bash
# Привязка процесса xfr к конкретному ядру (например, core 2)
taskset -c 2 xfr 192.168.1.50 -t 60

# Отключение irqbalance для стабильной привязки прерываний NIC
sudo systemctl disable --now irqbalance

# Проверка распределения прерываний
watch -n1 'cat /proc/interrupts | grep eth0'
```

### Тестирование с Jumbo Frames

```bash
# Настройка MTU 9000 на обоих концах
sudo ip link set dev eth0 mtu 9000

# Запуск теста с увеличенным размером буфера
xfr 192.168.1.50 -l 8192 -t 30
```

### systemd-сервис для постоянного сервера

```ini
# /etc/systemd/system/xfr-server.service
[Unit]
Description=xfr Bandwidth Server
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/xfr serve --tui
Restart=on-failure
RestartSec=5

# Ограничения ресурсов (опционально)
CPUAffinity=0 1
MemoryMax=512M

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now xfr-server
```

### Многоместное тестирование (mesh)

```bash
#!/usr/bin/env bash
# bench-mesh.sh — тестирование пропускной способности между всеми узлами кластера
HOSTS=(192.168.1.10 192.168.1.11 192.168.1.12)

for src in "${HOSTS[@]}"; do
  for dst in "${HOSTS[@]}"; do
    if [ "$src" != "$dst" ]; then
      echo "=== $src -> $dst ==="
      ssh "$src" "xfr $dst -t 20 -P 4 --json" | tee "bench-${src}-${dst}.json"
    fi
  done
done
```

## Интерпретация результатов

### Throughput vs Goodput

- **Throughput (бит/сек):** Общий объем переданных бит, включая заголовки Ethernet, IP, TCP/UDP и повторные передачи.
- **Goodput (бит/сек полезной нагрузки):** Реальная скорость полезных данных приложения. Для TCP goodput обычно на 5-15% ниже throughput из-за overhead и ретрансмиссий.

### Типичные артефакты

| Артефакт | Причина | Действие |
| :--- | :--- | :--- |
| **Retransmits > 0** | Потери пакетов на L2/L3, переполнение буферов коммутаторов | Проверьте `ethtool -S`, `tc qdisc`, замените кабель |
| **CPU utilization > 90%** | Ограничение производительностью процессора (часто на 10GbE+) | Используйте `numactl`, `taskset`, проверьте `mpstat` |
| **Асимметрия Upload/Download** | Неправильная настройка дуплекса на портах, политики провайдера | Проверьте `ethtool eth0` (duplex), тестируйте в обе стороны |
| **Jitter > 1ms (UDP)** | Перегрузка очередей (Bufferbloat), ECN-marking | Настройте `fq_codel` qdisc, проверьте `tc -s qdisc` |
| **Дискретность результатов (±10%)** | Вариабельность фоновой нагрузки, turbo boost | Зафиксируйте частоту CPU (`cpufreq-set`), отключите hyper-threading |

### Оценка CPU Bound

```bash
# Во время теста в другом терминале
mpstat -P ALL 1
# → Если %usr + %sys接近 100% на всех ядрах — тест ограничен CPU, не сетью

# Для QUIC это особенно характерно (user-space стек)
```

## Типичные проблемы и решения

| Симптом | Диагностика через xfr | Вероятная причина | Исправление |
| :--- | :--- | :--- | :--- |
| **Низкий throughput (<1Gbps на 10G NIC)** | `xfr --json` — низкий goodput, retransmits > 0 | Недостаточные буферы или потери на L2 | Увеличить `rmem_max`/`wmem_max`, проверить `ethtool -S` |
| **Высокий jitter (UDP/QUIC)** | Jitter > 1ms, стабильная полоса | Bufferbloat, некорректный qdisc | Переключиться на `fq_codel`, проверить `tc qdisc show` |
| **CPU saturation** | `mpstat` показывает 100% на ядрах xfr | Недостаточная производительность CPU | `numactl`, `taskset`, отключение HT |
| **Асимметрия Upload/Download** | Upload >> Download или наоборот | Дуплекс, политики QoS, или firmware bug | Проверить `ethtool eth0`, тесты в reverse mode |
| **MPTCP не агрегирует** | `xfr --mptcp` — скорость равна одному интерфейсу | MPTCP не поддерживается или не настроен в ядре | Проверить `sysctl net.mptcp.enabled`, `ip mptcp limit` |
| **QUIC тест падает** | Ошибка соединения через 5-10 секунд | Firewall блокирует UDP 5201, или MTU mismatch | Разрешить UDP 5201, настроить MTU 1500/9000 |
| **Потери пакетов при 0% retransmits (UDP)** | `xfr -u` — lost packets растет | Приемный буфер переполняется | Увеличить `net.core.rmem_max`, проверить `netstat -su` |
| **Низкая скорость на VLAN/VXLAN** | Throughput ниже ожидаемого на 20-30% | Overhead инкапсуляции, размер MTU | Увеличить MTU до 9000 (jumbo frames) или 16110 для VXLAN |

## Дополнительная информация

### Безопасность и авторизация

Использование **Pre-Shared Key (PSK)** для защиты сервера от несанкционированных тестов:

# На сервере

### Интеграция с мониторингом (Prometheus)

Сервер `xfr` может выступать в роли экспортера метрик:

```bash
xfr serve --prometheus 9100
```

**Ключевые метрики:**
- `xfr_bandwidth_bps`: Текущая пропускная способность.
- `xfr_retransmits_total`: Общее количество ретрансмиссий (TCP).
- `xfr_jitter_seconds`: Джиттер для UDP/QUIC.
- `xfr_active_clients`: Количество одновременно подключенных клиентов.

#### Prometheus Alert Rules

```yaml
groups:
  - name: xfr_alerts
    rules:
      - alert: XfrBandwidthDegradation
        expr: xfr_bandwidth_bps < 1000000000
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "Bandwidth below 1Gbps on {{ $labels.instance }}"
          description: "Current bandwidth is {{ $value }} bps."

      - alert: XfrHighRetransmits
        expr: rate(xfr_retransmits_total[5m]) > 100
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "High TCP retransmits on {{ $labels.instance }}"
          description: "Retransmit rate is {{ $value }} pps."
```

### Сравнение xfr и iperf3

| Характеристика | iperf3 | xfr |
| :--- | :--- | :--- |
| **Язык** | C | Rust |
| **Архитектура** | Однопоточная | Многопоточная (Tokio) |
| **Параллельные тесты** | Нет (очередь) | Да (одновременно) |
| **QUIC / MPTCP** | Нет | Да |
| **Графики (TUI)** | Нет | Встроены |
| **Автообнаружение** | Нет | mDNS |
| **Анализ различий** | Внешние скрипты | Команда `diff` |

### Сравнение с другими инструментами

| Инструмент | Язык | Особенности | Когда использовать |
| :--- | :--- | :--- | :--- |
| **iperf3** | C | Эталон, широко распространен, SCTP | Базовые тесты, совместимость |
| **nuttcp** | C | Детальная статистика, поддержка multicast | Тесты с фиксированным размером пакета |
| **netperf** | C | Тесты request/response (TCP_RR, UDP_RR) | Оценка latency под высокой нагрузкой |
| **xfr** | Rust | QUIC, MPTCP, TUI, multi-client | Современные протоколы, визуализация |

### Edge Cases и ограничения

**1. Права доступа:**
- Привязка к низким портам (<1024) требует `CAP_NET_BIND_SERVICE`.
- В контейнерах без `NET_ADMIN` xfr работает, но не может настроить сокетные буферы (`SO_RCVBUFFORCE`).

**2. Контейнеры и namespace:**
- Каждый контейнер имеет свой network namespace. `xfr` по умолчанию показывает сокеты текущего namespace.
- Для тестирования между namespace используйте `ip netns exec` или `--network host`.

**3. Высокоскоростные сети (100GbE/400GbE):**
- При тысячах соединений однопоточный клиент может быть bottleneck. Используйте `-P` с числом потоков, равным количеству очередей NIC (`ethtool -l eth0`).
- Включите `ethtool -K eth0 rx off tx off` для отключения offloading при детальном анализе пакетов.

**4. Многопоточные приложения:**
- `SO_REUSEPORT` создает отдельные listen-сокеты на каждый поток — будете видеть несколько строк для одного порта.
- Для тестирования приложений с `SO_REUSEPORT` запускайте отдельный `xfr serve` на каждом порту или используйте балансировку.

**5. QUIC и блокировки firewall:**
- QUIC использует UDP. Классические firewall, настроенные только на TCP, могут блокировать трафик.
- Проверяйте `conntrack -U` (update) для отслеживания UDP-сессий.
