# Диагностика DNS

## Определения

*   **DNS (Domain Name System):** Распределенная система для преобразования доменных имен в IP-адреса и обратно. Подробное описание протокола находится в заметке: [Протокол DNS](../../Networking/Protocols/dns.md).
*   **Системный резолвер:** Процесс, который приложения (`ping`, `curl`, браузер) используют для разрешения имён. Его поведение определяется системной конфигурацией (включая `/etc/hosts`), что может маскировать проблемы с внешними DNS-серверами.
*   **Утилиты прямого опроса (`dig`, `host`, `nslookup`):** Инструменты, которые напрямую отправляют запросы на DNS-сервер, игнорируя локальные настройки вроде `/etc/hosts`. Незаменимы для "чистой" проверки DNS-записей.
*   **`dig` (Domain Information Groper):** Предпочтительный инструмент для диагностики DNS из-за полноты выводимой информации и гибкости.

## Основные концепции

### `systemd-resolved`

На многих современных дистрибутивах `systemd-resolved` выступает в роли локального кэширующего DNS-резолвера. Все DNS-запросы от приложений сначала поступают к нему.

Утилита `resolvectl` — это основной инструмент для взаимодействия с `systemd-resolved`.

*   **Проверить общий статус и текущие серверы:**
    Команда `resolvectl status` (или просто `resolvectl`) показывает подробную информацию о глобальных настройках и настройках для каждого сетевого интерфейса.
    ```bash
    $ resolvectl
    Global
         Protocols: -LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
      resolv.conf mode: stub
    Link 2 (ens3)
        Current Scopes: DNS
             Protocols: +DefaultRoute +LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
    Current DNS Server: 1.1.1.1
           DNS Servers: 1.1.1.1 8.8.8.8
            DNS Domain: mycompany.local
    ```
    Из вывода видно, что для интерфейса `ens3` используются DNS-серверы `1.1.1.1` и `8.8.8.8`, а также домен поиска `mycompany.local`.

*   **Выполнить запрос через системный резолвер (узнать, как система разрешит имя):**
    Команда `query` показывает, какой IP-адрес вернет именно системный резолвер.
    ```bash
    resolvectl query example.com
    ```

*   **Очистить кэш:**
    ```bash
    sudo resolvectl flush-caches
    ```
    Иногда требуется обновить DNS-кеш только для одного сетевого интерфейса. Например, для `eth0`:
    ```bash
    resolvectl flush-caches eth0
    ```

*   **Проверить статистику кэша:**
    ```bash
    resolvectl statistics
    ```
    Растущий счётчик `Transactions in progress` или большое количество `Cache Misses` может указывать на проблемы с вышестоящими DNS-серверами или сетевой связностью.

*   **Проверить резолв домена через локальный кеширующий резолвер (systemd-resolved):**
    ```bash
    dig @127.0.0.53 example.com
    ```
    Это позволяет убедиться, что изменения в DNS-кеше применились, и что локальный резолвер корректно обрабатывает запросы, при этом все остальные сервисы остаются онлайн.

## Практические сценарии

### Базовая диагностика DNS

#### Быстрая проверка DNS-резолвинга

Если `ping 8.8.8.8` работает, но `ping google.com` выдаёт «Name or service not known» — это проблема с DNS.

**Проверка конфигурации DNS (`/etc/resolv.conf`):**
```bash
cat /etc/resolv.conf
```

Файл должен содержать рабочие DNS-серверы:
```
nameserver 8.8.8.8
nameserver 8.8.4.4
```

Если файл пустой или содержит неправильные адреса — резолвинг не работает.

**Проверка доступности DNS-сервера:**
```bash
# Проверка IP-связности
ping 8.8.8.8

# Проверка доступности DNS-порта (53)
nc -zv 8.8.8.8 53
```

Порт 53 — это стандартный порт DNS. Если порт закрыт или недоступен — сервер не может отвечать на DNS-запросы.

#### `dig` — детальная DNS-диагностика

```bash
dig google.com
```

Вывод показывает:
* Какой DNS-сервер ответил
* Сколько времени занял запрос
* Полученные A-записи (IP-адреса)

**Типичные ошибки в `dig`:**

| Статус | Значение | Причина |
|--------|----------|---------|
| `NXDOMAIN` | Домен не существует | Опечатка или домен удалён |
| `SERVFAIL` | Ошибка сервера | Проблема на стороне DNS-сервера |
| `REFUSED` | Запрос отклонён | ACL блокирует ваш IP |
| `connection timed out` | Таймаут соединения | DNS-сервер недоступен, проверьте firewall |

```bash
# Запросить MX-запись (почтовые серверы)
dig ya.ru MX

# Отследить весь путь DNS-запроса от корневых серверов
dig ya.ru +trace

# Запрос к конкретному DNS-серверу
dig @1.1.1.1 example.com
```

#### `nslookup` — альтернатива dig

Проще, чем dig, но менее информативен. Полезен для быстрой проверки.
```bash
nslookup google.com
nslookup ya.ru
```

#### `host`
Простой инструмент для быстрых проверок.
```bash
# Запросить A, AAAA и MX записи
host ya.ru

# Запросить конкретный тип записи (например, NS)
host -t NS habr.com
```

### Проблема в DNS или в сети?

Чтобы локализовать проблему, сравните ответ от системного резолвера и внешнего публичного DNS-сервера.

1.  **Выполните тест через внешний резолвер:** `dig @1.1.1.1 example.com` (используя DNS от Cloudflare).
2.  **Сравните результат:** Если ответ от внешнего сервера приходит мгновенно, а от системного резолвера (`dig example.com`) — медленно или с ошибкой, проблема локальная (например, в конфигурации `/etc/resolv.conf` или в работе `systemd-resolved`).

### Диагностика DNS в контейнерах и Kubernetes

DNS в контейнеризированных средах имеет особенности:

* **Kubernetes:** DNS обычно предоставляется [CoreDNS или NodeLocalDNS](../../Kubernetes/Networking/dns_deep_dive.md). Подробная диагностика описана в разделе «Диагностика DNS в Kubernetes».
* **Docker:** Использует встроенный DNS на `127.0.0.11`. Проблемы с DNS в Docker и их решение описаны в заметке [Устранение проблем с сетью Docker](../../Docker/Docker_troubleshooting/network_connectivity_issues.md#сценарий-4-проблемы-с-dns-в-контейнерах).
