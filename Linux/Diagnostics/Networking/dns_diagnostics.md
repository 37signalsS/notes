# Диагностика DNS

## Определения

**DNS (Domain Name System)** — распределённая система преобразования доменных имён в IP-адреса и обратно. Детальное описание протокола — в [Протокол DNS](../../../Networking/Protocols/dns.md).

**Ключевые компоненты:**

- **Системный резолвер:** Процесс, который приложения (`ping`, `curl`, браузер) используют для разрешения имён. Поведение определяется конфигурацией (`/etc/nsswitch.conf`, `/etc/hosts`, `/etc/resolv.conf`).
- **Утилиты прямого опроса (`dig`, `host`, `nslookup`):** Отправляют запросы напрямую DNS-серверам, игнорируя локальные настройки. Используются для "чистой" проверки DNS.
- **`dig` (Domain Information Groper):** Основной инструмент диагностики благодаря детальному выводу и гибкости.
- **`nslookup`:** Простой инструмент для быстрой проверки DNS-записей.
- **`resolvectl`:** Утилита для работы с `systemd-resolved` (статус, кэш, статистика).

## Основные концепции

### Порядок разрешения имён в Linux

Разрешение имён управляется файлом `/etc/nsswitch.conf`. Стандартная строка:

```
hosts: files dns
```

**Порядок:**

1. **`files`** — проверка `/etc/hosts` (локальные переопределения)
2. **`dns`** — запрос к DNS-серверам из `/etc/resolv.conf`

> **Важно:** Запись в `/etc/hosts` может переопределять DNS, что часто маскирует проблемы.

### Конфигурация DNS-клиента

| Файл | Назначение |
| :--- | :--- |
| `/etc/nsswitch.conf` | Порядок разрешения (files/dns) |
| `/etc/hosts` | Локальная база имён |
| `/etc/resolv.conf` | DNS-серверы (может генерироваться автоматически) |
| `/etc/systemd/resolved.conf` | Настройки `systemd-resolved` |

Подробно — в [Настройка DNS-клиента](../../Networking/Concepts/dns_client.md).

### systemd-resolved

В современных дистрибутивах (Ubuntu 17.10+, RHEL 7+) за разрешение имён отвечает `systemd-resolved` — локальный кэширующий резолвер.

**Особенности:**

- `/etc/resolv.conf` → symlink на `/run/systemd/resolve/stub-resolv.conf`
- `nameserver 127.0.0.53` — локальный stub-резолвер
- Получает DNS-серверы от DHCP, NetworkManager или статической конфигурации

## Практические сценарии

### Сценарий 1: Базовая диагностика "не работает DNS"

Если `ping 8.8.8.8` работает, но `ping google.com` выдаёт «Name or service not known» — это проблема с DNS.

1. **Проверить конфигурацию DNS-клиента:**

    ```bash
    # Узнать, какие DNS-серверы использует система
    cat /etc/resolv.conf
    # В системах с systemd-resolved этот файл может указывать на локальный stub 127.0.0.53
    # Для получения реальных серверов используйте `resolvectl status`
    ```

2. **Проверить доступность DNS-сервера:**

    ```bash
    # Проверить IP-связность с сервером
    ping 8.8.8.8
    # Проверить доступность DNS-порта (53/TCP и 53/UDP)
    nc -zv 8.8.8.8 53
    nc -zvu 8.8.8.8 53
    ```

3. **Выполнить прямой запрос к серверу:**

    ```bash
    # Запросить A-запись у конкретного DNS-сервера
    dig @8.8.8.8 google.com
    ```

    Если этот запрос успешен, а системный резолвинг нет, проблема в локальной конфигурации (например, firewall блокирует `systemd-resolved`).

4. **Быстрая проверка DNS через ping:**

    Если при пинге домена вы видите IP-адрес в скобках — DNS работает. Если видите ошибку "Name or service not known" — проблема с DNS.

    ```bash
    # DNS работает (видим IP в ответе)
    ping -c 1 google.com
    # PING google.com (142.250.185.206): 56 data bytes

    # DNS не работает (ошибка разрешения имени)
    ping -c 1 example.ru
    # ping: example.ru: Name or service not known
    ```

### Сценарий 2: Использование nslookup для разных типов запросов

`nslookup` — простой инструмент для проверки DNS. В отличие от `dig`, имеет более лаконичный вывод и по умолчанию показывает, какой DNS-сервер ответил на запрос.

- **Простой запрос A-записи:**

    ```bash
    nslookup google.com
    ```

    Команда покажет IP-адреса (A и AAAA) для `google.com`, а также адрес DNS-сервера, который предоставил ответ.

- **Запрос конкретного типа записи:**

    ```bash
    # Запросить MX-записи (почтовые серверы)
    nslookup -type=mx google.com

    # Запросить SOA-запись (авторитетная информация о зоне)
    nslookup -type=soa google.com
    ```

    Ответ на SOA-запрос покажет первичный сервер имен для зоны (ns1.google.com) и контактный email администратора.

- **Трассировка цепочки делегирования:**
    Можно вручную проследить путь разрешения имени, начиная с корневых серверов.
    1. Находим один из корневых серверов (например, `a.root-servers.net`).
    2. Спрашиваем у него про NS-серверы для зоны `.com`: `nslookup -type=ns com a.root-servers.net`.
    3. У полученного сервера (например, `a.gtld-servers.net`) спрашиваем про NS-серверы для `google.com`: `nslookup -type=ns google.com a.gtld-servers.net`.
    4. У полученного сервера (например, `ns1.google.com`) спрашиваем А-запись для `google.com`: `nslookup google.com ns1.google.com`.

### Сценарий 3: Детальный анализ DNS-записи с помощью `dig`

**`dig` (Domain Information Groper)** — мощная утилита для выполнения DNS-запросов и получения детальной информации о доменах. Входит в состав пакета `dnsutils` (Debian) или `bind-utils` (RHEL). В отличие от `nslookup` или `host`, `dig` показывает полную информацию: заголовки запроса, секции ответа, время отклика и статистику.

**Установка:**

```bash
# Debian/Ubuntu
sudo apt-get install -y dnsutils

# RHEL/CentOS
sudo dnf install -y bind-utils

# Alpine
apk add bind-utils
```

#### Основные примеры использования

**Простой запрос A-записи:**

```bash
dig cortel.cloud
```

**Пример вывода:**

```
; <<>> DiG 9.20.20 <<>> cortel.cloud
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 48488
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 4096
;; QUESTION SECTION:
;cortel.cloud.      IN  A

;; ANSWER SECTION:
cortel.cloud.    4746  IN  A  95.181.181.7

;; Query time: 174 msec
;; SERVER: 77.88.8.8#53(77.88.8.8) (UDP)
;; WHEN: Tue Mar 05 11:15:58 +03 2026
;; MSG SIZE  rcvd: 57
```

**Запрос к определённому DNS-серверу:**

```bash
dig @8.8.8.8 cortel.cloud    # использовать DNS Google
dig @1.1.1.1 example.com     # использовать DNS Cloudflare
```

**Краткий вывод (только IP):**

```bash
dig cortel.cloud +short
# 95.181.181.7
```

**Полезные опции:**

| Опция | Описание |
| :--- | :--- |
| `+noall +answer` | Показать только секцию ответа |
| `+short` | Краткий вывод (только данные) |
| `+stats` | Добавить статистику (время, размер) |
| `+tcp` | Использовать TCP вместо UDP |
| `+dnssec` | Запросить DNSSEC-данные |
| `+trace` | Полный путь от корневых серверов |
| `+ttlid` | Показать TTL записей |
| `+multi` | Многострочный вывод (для DNSKEY) |

**Примеры использования опций:**

```bash
# Только ответ с TTL
dig +noall +answer +ttlid example.com

# Полный путь делегирования
dig google.com +trace

# Запрос DNSSEC-подписей
dig +dnssec example.com

# Запрос конкретных записей
dig ya.ru MX           # почтовые серверы
dig ya.ru NS           # авторитативные серверы
dig _http._tcp.example.com SRV  # SRV-запись
```

**Анализ ответа:**

| Поле | Описание |
| :--- | :--- |
| **STATUS** | `NOERROR` (успех), `NXDOMAIN` (домен не найден), `SERVFAIL` (ошибка сервера) |
| **Query time** | Время выполнения запроса (мс) |
| **SERVER** | DNS-сервер, который ответил |
| **flags** | `qr` (ответ), `rd` (рекурсия запрошена), `ra` (рекурсия доступна), `AA` (авторитетный ответ) |

> **Примечание:** Для детального анализа времени DNS-запроса в составе HTTP-запросов см. [Диагностика сетевых задержек с curl](./curl_network_diagnostics.md).

### Сценарий 4: Диагностика DNS в контейнерах

DNS в контейнеризированных средах имеет особенности:

- **Kubernetes:** DNS обычно предоставляется [CoreDNS или NodeLocalDNS](../../../Kubernetes/Networking/dns_deep_dive.md).
- **Docker:** Использует встроенный DNS на `127.0.0.11`. Проблемы решаются через проверку конфигурации демона и сети контейнера. Подробнее см. [Устранение проблем с DNS в Docker](../../../Docker/Docker_troubleshooting/network_connectivity_issues.md#сценарий-4-проблемы-с-dns-в-контейнерах).
