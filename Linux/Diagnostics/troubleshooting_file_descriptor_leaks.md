# Диагностика утечек файловых дескрипторов и файловых блокировок

## Определения

*   **Утечка файловых дескрипторов**: Ситуация, когда процесс не освобождает [файловый дескриптор](../../FileSystems/file_descriptors.md) после завершения работы с ресурсом. Это приводит к исчерпанию лимитов и ошибкам, таким как `Too many open files`. Подробнее см. в [руководстве по диагностике этой ошибки](./Troubleshooting/troubleshooting_too_many_open_files.md).
*   **Файловая блокировка (Lock)**: Механизм для синхронизации доступа к файлу. Некорректное управление блокировками вызывает "подвисание" процессов, которые пытаются получить доступ к заблокированному ресурсу.

## Основные концепции

Утечки и блокировки не всегда очевидны. Процесс может удерживать дескриптор или блокировку на файле, который кажется свободным. Стандартная утилита [`lsof`](../../Processes/lsof.md) может не показать проблему, если она полагается на неактуальную информацию в `/proc`.

**Типичные симптомы:**

*   Зависание утилит резервного копирования.
*   «Подвисание» баз данных (например, SQLite) без ошибок в логах.
*   Невозможность удалить или изменить файл, который не используется видимыми процессами.

## Практические сценарии

### 1. Поиск процесса, удерживающего файл

Если стандартные утилиты не помогают, можно найти процесс напрямую через `/proc` или с помощью специализированных инструментов.

*   **Прямой поиск в `/proc`**:
    ```bash
    # Замените <имя_файла> на имя искомого файла
    ls -l /proc/*/fd | grep <имя_файла>
    ```
    Этот метод надежно определяет `PID` процесса, удерживающего файл, путем поиска символических ссылок в директориях файловых дескрипторов всех процессов. Детали см. в описании [`/proc`](../../FileSystems/virtual_fs_proc.md).

*   **Использование `fuser`**:
    Утилита `fuser` определяет, какие процессы используют указанный файл.
    ```bash
    fuser -v <путь_к_файлу>
    ```

### 2. Анализ файловых блокировок

Для диагностики активных блокировок используется `lslocks`.

```bash
# Вывести текущие блокировки
lslocks

# Наблюдать за блокировками в реальном времени
watch -n 1 lslocks
```

**Ключевые поля в выводе:**
*   `COMMAND`, `PID`: Процесс, удерживающий блокировку.
*   `TYPE`: Тип блокировки (`FLOCK`, `POSIX`).
*   `MODE`: Режим (`READ`, `WRITE`). `WRITE`-блокировка — наиболее частая причина "зависаний".

### 3. Анализ процесса и системных лимитов

После определения `PID` можно получить детальную информацию о процессе и проверить системные лимиты.

*   **Информация о процессе:**
    ```bash
    ps -fp <PID>
    ```
*   **Анализ системных лимитов:**
    Исчерпание общего лимита файловых дескрипторов в системе — одна из причин проблем. Методы проверки описаны в руководстве [о файловых дескрипторах](../../FileSystems/file_descriptors.md#мониторинг-и-управление-лимитами).

## Дополнительная информация

*   Для глубокого анализа файлов, открытых конкретным процессом, используйте [`lsof -p <PID>`](../Processes/lsof.md).
*   Блокировки на уровне баз данных требуют специфичных инструментов, например, для [PostgreSQL](../../Databases/PostgreSQL/Concepts/concurrency_and_locking.md).
*   Для отслеживания системных вызовов `open` и `close` в реальном времени можно использовать [`strace`](./Troubleshooting/tracing_and_debugging.md).
