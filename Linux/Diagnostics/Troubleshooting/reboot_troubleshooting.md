# Диагностика причин перезагрузки Linux

## Определения

**Диагностика перезагрузки** — это процесс анализа системной информации и журналов для установления точной причины, по которой операционная система была перезапущена. Цель состоит в том, чтобы отличить штатное, инициированное действие от аварийного сбоя.



## Основные концепции

Существует два фундаментально разных типа перезагрузок:

-   **Штатная перезагрузка (Initiated Reboot):** Вызвана преднамеренным действием пользователя или системного процесса. Такие события всегда оставляют четкие следы в системных журналах.
    -   **Примеры:** Выполнение команд `reboot`, `shutdown -r`, `init 6`; автоматическая перезагрузка после установки обновлений ядра.
-   **Аварийная перезагрузка (System Crash):** Вызвана непредвиденным событием, которое система не смогла обработать. Логи о таких событиях могут отсутствовать или быть неполными, так как ОС отключается мгновенно.
    -   **Примеры:** Сбой электропитания, аппаратная ошибка (память, CPU), критическая ошибка ядра (Kernel Panic).

## Практические сценарии

#### Шаг 1: Определение времени перезагрузки

-   **Показать время текущей загрузки:**
    ```bash
    who -b
    # system boot  2023-10-27 10:00
    ```

-   **Показать историю всех зарегистрированных перезагрузок:**
    ```bash
    last reboot
    ```
    Эта команда считывает файл `/var/log/wtmp` и показывает, когда система была загружена.

#### Шаг 2: Анализ системных журналов


-   **Для современных систем с `systemd`:**
    ```bash
    # 1. Показать список всех зарегистрированных загрузок (boots)
    # Каждая загрузка имеет свой ID (например, -1, -2) и хэш.
    [`journalctl --list-boots`](../../Diagnostics/Logging/journalctl.md#список-всех-зарегистрированных-загрузок-для-выбора-конкретной)

    # 2. Изучить логи предыдущей загрузки (-1), чтобы найти причину сбоя.
    # Флаг -r выводит логи в обратном порядке (от новых к старым),
    # что позволяет сразу увидеть последние события перед сбоем.
    [`journalctl -b -1 -r`](../../Diagnostics/Logging/journalctl.md#логи-с-последней-загрузки)
    ```
    **Что искать:** Сообщения `reboot`, `shutdown`, `power off`, `Reached target Shutdown`, а также критические ошибки, непосредственно предшествующие потере связи.

-   **Для старых систем (`syslog`):**
    ```bash
    # Пути к логам могут отличаться: /var/log/syslog, /var/log/messages, /var/log/boot.log
    sudo grep -iE 'shutdown|reboot|power' /var/log/messages
    ```

#### Шаг 3: Проверка `auditd` (если используется)

Если в системе настроен демон аудита `auditd`, он может точно показать, какой процесс или пользователь инициировал штатную перезагрузку.

```bash
# Найти события загрузки и выключения в логах аудита
sudo ausearch -i -m system_boot,system_shutdown
```



## Дополнительная информация

#### Включение постоянного хранения логов `journald`

Для надежной диагностики сбоев критически важно, чтобы логи `journald` сохранялись между перезагрузками. По умолчанию они могут храниться в `/run/log/journal` (т.е. в памяти) и теряться при сбое.

**Чтобы включить постоянное хранение:**

1.  Создайте каталог для хранения логов:
    ```bash
    sudo mkdir -p /var/log/journal
    ```
2.  Перезапустите сервис `systemd-journald`, чтобы он подхватил новый каталог:
    ```bash
    sudo systemctl restart systemd-journald
    ```
3.  Проверьте, что хранилище стало постоянным (`Storage: persistent`):
    ```bash
    [`journalctl -b`](../../Diagnostics/Logging/journalctl.md#логи-с-последней-загрузки) | head -n 1
    ```

#### Анализ паники ядра (Kernel Panic)

Если перезагрузка вызвана **Kernel Panic**, стандартные логи будут неполными, так как ядро "падает" до того, как успевает записать информацию.

-   **Механизм `kdump`:** Это стандартный способ отладки паники ядра в Linux. `kdump` использует второе, "резервное" ядро, которое загружается в момент сбоя основного и сохраняет полный образ оперативной памяти (`vmcore`) на диск.
-   **Проверка:** Если `kdump` настроен, поищите файлы `vmcore` в директории `/var/crash/`. Наличие таких файлов — прямое доказательство того, что причиной перезагрузки была паника ядра.
-   **Анализ:** Для анализа `vmcore`-файлов используется специализированная утилита `crash`.
