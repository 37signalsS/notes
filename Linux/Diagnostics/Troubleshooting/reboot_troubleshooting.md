# Диагностика причин перезагрузки Linux

## Определения

**Диагностика перезагрузки** — это процесс анализа системной информации и журналов для установления точной причины, по которой операционная система была перезапущена. Цель состоит в том, чтобы отличить штатное, инициированное действие от аварийного сбоя.

## Основные концепции

Существует два фундаментально разных типа перезагрузок:

- **Штатная перезагрузка (Initiated Reboot):** Вызвана преднамеренным действием пользователя или системного процесса. Такие события всегда оставляют четкие следы в системных журналах.
  - **Примеры:** Выполнение команд `reboot`, `shutdown -r`, `init 6`; автоматическая перезагрузка после установки обновлений ядра.
- **Аварийная перезагрузка (System Crash):** Вызвана непредвиденным событием, которое система не смогла обработать. Логи о таких событиях могут отсутствовать или быть неполными, так как ОС отключается мгновенно.
  - **Примеры:** Сбой электропитания, аппаратная ошибка (память, CPU), критическая ошибка ядра (Kernel Panic).

## Практические сценарии

#### Шаг 1: Определение времени перезагрузки

- **Показать время текущей загрузки:**

    ```bash
    who -b
    # system boot  2023-10-27 10:00
    ```

- **Показать историю всех зарегистрированных перезагрузок:**

    ```bash
    last reboot
    ```

    Эта команда считывает файл `/var/log/wtmp` и показывает, когда система была загружена.

#### Шаг 2: Анализ системных журналов

- **Для современных систем с `systemd`:**

    ```bash
    # 1. Показать список всех зарегистрированных загрузок (boots)
    # Каждая загрузка имеет свой ID (например, -1, -2) и хэш.
    [`journalctl --list-boots`](../../../Diagnostics/journalctl.md#список-всех-зарегистрированных-загрузок-для-выбора-конкретной)

    # 2. Изучить логи предыдущей загрузки (-1), чтобы найти причину сбоя.
    # Флаг -r выводит логи в обратном порядке (от новых к старым),
    # что позволяет сразу увидеть последние события перед сбоем.
    [`journalctl -b -1 -r`](../../../Diagnostics/journalctl.md#логи-с-последней-загрузки)
    ```

    **Что искать:** Сообщения `reboot`, `shutdown`, `power off`, `Reached target Shutdown`, а также критические ошибки, непосредственно предшествующие потере связи.

- **Для старых систем (`syslog`):**

    ```bash
    # Пути к логам могут отличаться: /var/log/syslog, /var/log/messages, /var/log/boot.log
    sudo grep -iE 'shutdown|reboot|power' /var/log/messages
    ```

#### Шаг 3: Проверка `auditd` (если используется)

Если в системе настроен демон аудита `auditd`, он может точно показать, какой процесс или пользователь инициировал штатную перезагрузку.

```bash
# Найти события загрузки и выключения в логах аудита
sudo ausearch -i -m system_boot,system_shutdown
```

## Дополнительная информация

#### Включение постоянного хранения логов `journald`

Для надежной диагностики сбоев критически важно, чтобы логи `journald` сохранялись между перезагрузками. По умолчанию они могут храниться в `/run/log/journal` (т.е. в памяти) и теряться при сбое.

**Чтобы включить постоянное хранение:**

1. Создайте каталог для хранения логов:

    ```bash
    sudo mkdir -p /var/log/journal
    ```

2. Перезапустите сервис `systemd-journald`, чтобы он подхватил новый каталог:

    ```bash
    sudo systemctl restart systemd-journald
    ```

3. Проверьте, что хранилище стало постоянным (`Storage: persistent`):

    ```bash
    [`journalctl -b`](../../../Diagnostics/journalctl.md#логи-с-последней-загрузки) | head -n 1
    ```

#### Анализ паники ядра (Kernel Panic)

Если перезагрузка вызвана **Kernel Panic**, стандартные логи будут неполными, так как ядро "падает" до того, как успевает записать информацию.

- **Механизм `kdump`:** Это стандартный способ отладки паники ядра в Linux. `kdump` использует второе, "резервное" ядро, которое загружается в момент сбоя основного и сохраняет полный образ оперативной памяти (`vmcore`) на диск.
- **Проверка:** Если `kdump` настроен, поищите файлы `vmcore` в директории `/var/crash/`. Наличие таких файлов — прямое доказательство того, что причиной перезагрузки была паника ядра.
- **Анализ:** Для анализа `vmcore`-файлов используется специализированная утилита `crash`.

## Перезагрузка системы при отказе дисковой подсистемы

### Проблема: Почему команда `reboot` не работает?

Представим ситуацию: на физическом сервере произошел сбой аппаратного RAID-контроллера. Дисковая подсистема стала полностью недоступной (I/O errors), но операционная система, включая ваш shell, продолжает работать в оперативной памяти. Попытка выполнить `reboot` или `shutdown -r now` в этой консоли не приводит к перезагрузке.

**Причина** кроется в том, что процесс перезагрузки в современных Linux-системах — это не единичная атомарная операция, а сложный процесс, зависящий от диска:

1. **Зависимость от бинарных файлов:** Команда `reboot` (которая часто является символической ссылкой на `systemctl`) и сам `systemctl` являются исполняемыми файлами, находящимися на диске (например, в `/usr/bin/` или `/sbin/`). При попытке их выполнить система не может прочитать их с отказавшего диска.
2. **Зависимость от скриптов и сервисов:** `systemd` (или `init` в старых системах) при выключении последовательно останавливает системные сервисы. Этот процесс управляется скриптами и `unit`-файлами, которые также хранятся на диске. Система не может их прочитать, чтобы корректно завершить работу.
3. **Синхронизация файловых систем:** Одним из последних шагов перед перезагрузкой является вызов `sync`, который пытается сбросить все кэшированные данные на диск. Эта операция "зависает" в бесконечном ожидании (состояние `D` - uninterruptible sleep), так как диск не отвечает.

В результате вы остаетесь с работающей в памяти ОС, которая не может завершить свою работу и передать управление на перезагрузку.

### Решение: Magic SysRq Key

Единственным надежным способом перезагрузить систему в таком состоянии без физического доступа является использование **"магической" клавиши SysRq**. Это механизм ядра Linux, который позволяет выполнять низкоуровневые команды напрямую, в обход большинства высокоуровневых абстракций ОС.

Даже если вы не можете нажать `Alt+SysRq+<клавиша>` на физической клавиатуре, вы можете активировать те же команды через `/proc`, если у вас есть доступ к shell:

1. **Включить все функции SysRq** (если не включено):

    ```bash
    echo 1 | sudo tee /proc/sys/kernel/sysrq
    ```

2. **Выполнить безопасную перезагрузку (REISUB):** Последовательно отправляем команды ядру.

    ```bash
    # Un'R'aw - перехватить управление клавиатурой у X-сервера.
    echo r > /proc/sysrq-trigger
    # T'e'rminate - послать SIGTERM всем процессам, кроме init.
    echo e > /proc/sysrq-trigger
    # K'i'll - послать SIGKILL всем процессам, кроме init.
    echo i > /proc/sysrq-trigger
    # 'S'ync - синхронизировать все смонтированные файловые системы (эта команда, скорее всего, "зависнет" или не выполнится, но ее стоит попробовать).
    echo s > /proc/sysrq-trigger
    # 'U'nmount - перемонтировать все файловые системы в режим "только чтение".
    echo u > /proc/sysrq-trigger
    # Re'b'oot - немедленно перезагрузить систему.
    echo b > /proc/sysrq-trigger
    ```

Команда `echo b > /proc/sysrq-trigger` является "последним средством". Она вызывает немедленную, "грязную" перезагрузку, аналогичную нажатию кнопки Reset. Данные в кэше могут быть потеряны, но в ситуации с отказавшим диском они все равно не могли быть сохранены. Этот метод обходит зависшие процессы и напрямую инициирует аппаратную перезагрузку.
