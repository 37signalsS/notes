# Диагностика причин перезагрузки Linux

## 1. Определение

Неожиданная перезагрузка Linux-системы может привести к простоям и потерям данных. Диагностика причин является ключевым шагом для предотвращения таких инцидентов в будущем.

## 2. Основные концепции

- **Штатная перезагрузка (Initiated):** Вызвана действием пользователя или системы (команды `reboot`, `shutdown`, установка обновлений). Такие события обычно оставляют четкие следы в системных журналах.
- **Аварийная перезагрузка (Crash):** Вызвана сбоем питания, аппаратной ошибкой или паникой ядра (Kernel Panic). Такие события часто не логируются должным образом, так как система отключается мгновенно.

## 3. Практические сценарии

### Шаг 1: Определение времени перезагрузки

Первым делом нужно узнать, когда произошла последняя загрузка системы.

-   **Показать время текущей загрузки:**
    ```bash
    who -b
    ```

-   **Показать историю всех перезагрузок:**
    ```bash
    last reboot
    ```

### Шаг 2: Анализ системных журналов

Просмотр системных логов — основной способ найти причину штатной перезагрузки.

- **Для systemd-систем (`journalctl`):**
  Это наиболее предпочтительный метод.
  ```bash
  # Показать список всех зарегистрированных загрузок
  journalctl --list-boots

  # Изучить логи предыдущей загрузки (самый важный шаг для анализа сбоя)
  # Флаг -r показывает логи в обратном порядке (от новых к старым)
  journalctl -b -1 -r
  ```
  Ищите сообщения о `shutdown`, `reboot`, `power off` или ошибки, предшествующие потере связи.

- **Для старых систем (syslog):**
  ```bash
  # Пути могут отличаться: /var/log/syslog, /var/log/messages
  sudo grep -i 'shutdown\|reboot' /var/log/messages
  ```

### Шаг 3: Использование `auditd`

Если настроен аудит, `ausearch` может показать, кто или что инициировало перезагрузку.
```bash
sudo ausearch -i -m system_boot,system_shutdown | tail -4
```

## 4. Продвинутые детали

### Включение постоянного хранения логов `journald`

По умолчанию `journald` может не сохранять логи между перезагрузками. Чтобы логи были доступны после сбоя, включите постоянное хранение:
```bash
sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo systemctl restart systemd-journald
```
*Примечание: вместо `kill` лучше использовать `restart` для перезапуска сервиса.*

### Анализ Kernel Panic

Если перезагрузка была вызвана паникой ядра, стандартные логи могут быть неполными. Для анализа таких сбоев используется механизм `kdump`. Он сохраняет образ памяти в момент сбоя (`vmcore`) в директорию (часто `/var/crash/`) для последующего анализа с помощью утилиты `crash`. Проверка наличия файлов в этой директории может указать на Kernel Panic как причину перезагрузки.
