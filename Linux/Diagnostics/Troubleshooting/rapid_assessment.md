# Быстрая диагностика сервера (Rapid Assessment)

## Definitions

**Rapid Assessment (Первичная диагностика)** — методология экспресс-анализа состояния Linux-сервера, занимающая от 30 до 60 секунд. Цель — не детальное решение проблемы, а быстрая локализация «бутылочного горлышка» (CPU, Memory, I/O, Network) и фильтрация ложных гипотез.

**Метод USE (Utilization, Saturation, Errors)** — концептуальная основа диагностики, предложенная Брендоном Греггом, фокусирующаяся на утилизации ресурсов, их насыщении (очередях) и наличии ошибок.

## Basic Concepts

Протокол состоит из последовательного выполнения команд, каждая из которых отвечает на специфический вопрос о состоянии системы.

| Порядок | Команда | Объект анализа | Что искать (Red Flags) |
| :--- | :--- | :--- | :--- |
| 1 | `uptime` | Load Average | LA >> кол-во ядер; резкий рост за 1 мин. |
| 2 | `dmesg -T \| tail` | Kernel / HW | OOM-killer, TCP Drop, I/O errors, Segfaults. |
| 3 | `vmstat 1 5` | Контекст / Своп | Высокий `si`/`so` (свопинг), высокий `cs` (переключения). |
| 4 | `mpstat -P ALL 1` | Перекос CPU | Одно ядро на 100% при низком общем CPU (прерывания). |
| 5 | `pidstat 1 5` | Процессы | Конкретный PID, потребляющий ресурсы прямо сейчас. |
| 6 | `iostat -xz 1 5` | Диск | `%util` > 80%, высокий `await` (> 10-20ms). |
| 7 | `free -h` | Память | `available` близок к нулю. |
| 8 | `sar -n DEV 1` | Сеть | Насыщение пропускной способности (rxkB/s, txkB/s). |
| 9 | `sar -n TCP,ETCP 1` | TCP ошибки | Рост `retrans/s` (ретрансмиты). |
| 10 | `top` / `htop` | Общий вид | Зомби-процессы, аномальные состояния (D, Z). |

## Practical Scenarios

### 1. Анализ общей нагрузки (uptime)
```bash
uptime
# → 18:30:05 up 10 days, 2:15, 3 users, load average: 15.05, 10.10, 5.02
```
**Интерпретация:** Если LA значительно превышает количество CPU-ядер, система перегружена. Сравнение трех чисел показывает тренд: растет нагрузка или падает.
*Подробнее:* [Планирование процессов и LA](../../Core/processes/scheduling.md).

### 2. Ошибки ядра и системы (dmesg)
```bash
dmesg -T | tail -n 50
# → [Sun Aug  9 18:30:00 2026] Out of memory: Kill process 1234 (mysqld)
```
**Интерпретация:** Ищите OOM-killer (нехватка памяти), ошибки файловой системы или аппаратные сбои. Флаг `-T` добавляет читаемое время.

### 3. Насыщение и контекст (vmstat)
```bash
vmstat 1
# → r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
# → 5  0      0   100M    50M  2500M    0    0     0   500  100  500 80 15  5  0  0
```
**Интерпретация:**
- `r` (runnable): Очередь на выполнение. Если больше кол-ва ядер — CPU перегружен.
- `si`/`so` (swap in/out): Если значения отличны от нуля — система активно использует своп (критично для производительности).

### 4. Поиск «виновника» (pidstat)
```bash
pidstat 1 5
# → PID    %usr %system  %guest  %wait    %CPU   CPU  Command
# → 1234  80.00   15.00    0.00   5.00   95.00     2  python3
```
**Интерпретация:** Позволяет увидеть нагрузку в динамике, включая `%wait` (время ожидания CPU).

### 5. Дисковая подсистема (iostat)
```bash
iostat -xz 1
# → Device:  rrqm/s  wrqm/s  r/s  w/s  rkB/s  wkB/s  await  %util
# → sda        0.00    5.00  100  500   4000  20000  35.00  95.00
```
**Интерпретация:** `%util` показывает время занятости диска. `await` — среднее время обработки запроса (включая очередь). Значения `await > 20ms` обычно указывают на деградацию.

### 6. Сетевая активность (sar)
```bash
sar -n DEV 1
# → IFACE   rxpck/s   txpck/s    rxkB/s    txkB/s
# → eth0    10000.0   12000.0   15000.0   20000.0
```
**Интерпретация:** Сравните текущие значения с пропускной способностью канала. Постоянная нагрузка на уровне 90%+ может вызывать пакетные потери.

## Additional Information

### Порядок действий при аварии
1. **Локализация:** CPU (LA, vmstat), Память (free), Диск (iostat), Сеть (sar).
2. **Идентификация:** Найти конкретный процесс через `pidstat` или `top`.
3. **Проверка логов:** `dmesg` и системные журналы.
