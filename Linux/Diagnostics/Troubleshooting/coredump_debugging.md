# Отладка через Coredump в Linux

## Определения

**Coredump (дамп памяти)** — файл, содержащий снимок оперативной памяти процесса в определенный момент времени. Включает в себя состояние регистров, стек вызовов и значения переменных.

**gcore** — утилита (часть пакета GDB), позволяющая снять дамп памяти работающего процесса без его принудительного завершения.

**core_pattern** — параметр ядра Linux (`/proc/sys/kernel/core_pattern`), определяющий, куда и с каким именем будут сохраняться дампы при падении процессов.

---

## Базовые концепции

### Снятие дампа без остановки процесса

Классическая отладка через `gdb attach` останавливает выполнение процесса на все время работы отладчика. Для production-систем это часто недопустимо. Решение — снять coredump «живого» процесса и анализировать его отдельно, пока само приложение продолжает работу.

| Метод | Описание | Плюсы/Минусы |
| :--- | :--- | :--- |
| **`gcore`** | Специализированная утилита | Стандартный метод, минимальная пауза (доли секунды) |
| **`gdb -batch`** | Команда GDB с немедленным отсоединением | Не требует `gcore`, но чуть медленнее |
| **`/proc/<PID>/mem`** | Прямое копирование памяти через ядро | Самый быстрый метод, но требует ручной склейки или спец. инструментов |

## Практические сценарии

### Сценарий: Снятие дампа работающего процесса

#### Способ 1: Использование gcore (Рекомендуемый)

Утилита `gcore` создает дамп и сразу возобновляет работу процесса.

```bash
# Установка (если отсутствует)
# apt install gdb / dnf install gdb

# Снятие дампа
sudo gcore -o /tmp/myapp.core <PID>
```

#### Способ 2: Через GDB в пакетном режиме

Если `gcore` недоступен, можно использовать сам `gdb`. Флаг `-batch` и команда `detach` гарантируют, что процесс будет «заморожен» только на время записи файла.

```bash
sudo gdb -p <PID> -batch -ex "gcore /tmp/myapp.core" -ex detach
```

#### Способ 3: Копирование через /proc (Экстремальный)

Для процессов с огромным объемом памяти (десятки ГБ), где даже `gcore` вызывает заметную паузу, можно попытаться прочитать память напрямую:

```bash
sudo cp /proc/<PID>/mem /tmp/mem.dump 2>/dev/null
```
> **Внимание:** Это даст «сырой» снимок памяти, который сложнее анализировать в GDB без заголовков ELF.

### Анализ полученного дампа

Для анализа дампа необходимо иметь сам исполняемый файл (бинарник) той же версии, что и запущенный процесс.

```bash
# Запуск анализа
gdb /usr/bin/myapp /tmp/myapp.core
```

**Основные команды анализа:**

```gdb
# Посмотреть стек всех потоков
(gdb) thread apply all bt

# Выбрать конкретный поток
(gdb) thread <N>

# Переместиться по фреймам стека
(gdb) frame <N>

# Посмотреть локальные переменные в текущем фрейме
(gdb) info locals

# Вывести значение конкретной переменной
(gdb) print variable_name
```

### Настройка автоматического сбора дампов

Чтобы дампы сохранялись автоматически при аварийном завершении приложения (Segmentation fault и т.д.):

1. **Снять лимиты в сессии:**
   ```bash
   ulimit -c unlimited
   ```

2. **Настроить шаблон имени и путь:**
   ```bash
   # %e — имя файла, %p — PID
   echo "/tmp/core.%e.%p" | sudo tee /proc/sys/kernel/core_pattern
   ```

#### Использование systemd-coredump

В современных дистрибутивах дампы управляются через `systemd`. Они сохраняются в бинарном журнале.

```bash
# Список последних дампов
coredumpctl list

# Посмотреть информацию о конкретном дампе (по PID)
coredumpctl info <PID>

# Открыть последний дамп в GDB (автоматически подберет бинарник)
coredumpctl gdb <PID>
```

## Дополнительная информация

### Работа с отладочными символами (Debug Symbols)

Без символов (`debug symbols`) вместо имен функций в стеке будут адреса памяти (`??`), что делает отладку невозможной.

**Как установить символы:**

```bash
# Ubuntu/Debian
sudo apt install myapp-dbgsym

# RHEL/CentOS
sudo dnf debuginfo-install myapp
```

**Если символы в отдельном файле:**
Внутри GDB укажите путь к ним:
```gdb
(gdb) set debug-file-directory /usr/lib/debug
```

### Безопасность

Coredump содержит **полный снимок памяти**, включая:
- Секреты, пароли, API-ключи, находящиеся в переменных.
- Персональные данные пользователей, обрабатываемые в этот момент.

**Правила работы:**
1. Не передавайте дампы по открытым каналам связи.
2. Храните дампы в защищенных директориях (права `600`).
3. Удаляйте дампы сразу после завершения анализа.
