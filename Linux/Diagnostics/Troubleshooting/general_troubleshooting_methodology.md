# Общая методология диагностики сервисов

## Definitions

**Диагностика сервисов (Troubleshooting)** — систематический процесс выявления причин сбоев, некорректного функционирования или низкой производительности программных систем.

**Принцип «снизу вверх» (Bottom-up)** — подход к диагностике, начинающийся с низшего уровня стека (физический сервер, ОС) и последовательно движущийся к верхнему (процесс, приложение, зависимости). Позволяет исключать возможные причины сбоя на каждом этапе.

## Basic Concepts

### Ключевые правила

1. **Не паниковать и действовать методично** — траблшутинг это цикл: `Гипотеза → Проверка`. Если гипотеза не подтвердилась, выдвигаем следующую.

2. **Не перезагружать!** — перезагрузка скрывает, а не решает проблему. Необходимо собрать максимум диагностической информации до принятия радикальных мер.

3. **Оценить масштаб и границы инцидента:**
   - **Масштаб:** Один хост или весь сервис/кластер?
   - **Временная привязка:** Что изменилось непосредственно перед сбоем? (CI/CD, конфиги, сертификаты, DNS).
   - **Влияние:** Сколько пользователей страдает? Какова критичность?

4. **Метод сравнения (Bad vs Good):** Если есть работающий эталонный узел, сравните его конфигурацию, версии пакетов и состояние ресурсов с проблемным узлом (`diff`, `History`).

5. **Следовать принципу «снизу вверх»:** диагностика начинается с ОС и постепенно поднимается по стеку технологий, последовательно исключая причины.

### Уровни стека диагностики

| Уровень | Область | Ключевые инструменты |
| :--- | :--- | :--- |
| **0** | **Загрузка (Boot)** | Консоль (IPMI, VNC), BIOS, GRUB, Initramfs |
| **1** | Сервер и ОС | `ping`, `ssh`, `htop`, `df`, `dmesg` |
| **2** | Процесс и порты | `systemctl`, `ps`, `ss`, `lsof` |
| **3** | Приложение и логи | `journalctl`, `tail -f`, `curl` |
| **4** | Зависимости | `telnet`, `nc`, логи БД/кэшей |
| **5** | Конфигурация и код | `git log`, `diff`, системы управления конфигурациями |

## Practical Scenarios

### Уровень 0: Проблемы загрузки

Если сервер недоступен по SSH, необходимо получить доступ к консоли (IPMI/KVM).
**Карта загрузки:**

- **BIOS/UEFI** (ищет загрузчик) → **GRUB** (выбирает ядро) → **Kernel** (инициализирует железо) → **Initramfs** (монтирует root) → **Systemd** (запускает процессы).

**Где мы застряли?**

- Ошибка GRUB → проблема до ядра (загрузчик).
- Kernel Panic → проблема в ядре или `rootfs`.
- Initramfs Shell → проблема с хранилищем (UUID, RAID, LVM).

Подробнее: [Процесс загрузки и восстановление](../Core/kernel/boot_process.md#troubleshooting-boot-issues)

### Уровень 1: Сервер и ОС

**Красные флаги (Red Flags):**

- **High Load Average при низком CPU:** Почти всегда проблема с вводом-выводом (IO Wait).
- **Растет Swap, падает Available Memory:** Нехватка памяти (Memory Pressure).
- **Диск заполнен на 100%:** Процессы не могут писать логи/сокеты.
- **Ошибки в dmesg:** `Read-only file system`, `I/O error`, `Out of memory (OOM)`.

```bash
# Проверка OOM Killer
dmesg -T | grep -i "oom"
```

Подробнее о диагностике ресурсов: [Диагностика производительности](./linux_performance_diagnostics_case.md)

### Уровень 2: Процесс и порты

**Статус процесса:**

```bash
systemctl status <service_name>    # подробнее: [systemd Service Management](../../Core/systemd/service_management.md)
ps aux | grep <process_name>       # подробнее: [ps](../Processes/ps.md)
```

**Сетевые порты:**

```bash
ss -tlpn | grep :<port>     # современная утилита: [ss](../Networking/ss.md)
```

### Уровень 3: Приложение и логи

**Логи приложения:**

```bash
# systemd-сервисы
journalctl -u <service_name> -f    # подробнее: [journalctl](../journalctl/journalctl_overview.md)

# Классические лог-файлы
tail -f /var/log/<service_name>/error.log
```

**Диагностика без логов:**
Если сервис падает или не запускается, не оставляя записей в логах:
1. **`strace`**: Запустите процесс под `strace`, чтобы увидеть системные вызовы и понять, на каком этапе происходит сбой (например, отсутствие доступа к файлу или неудачный сетевой вызов).
   ```bash
   strace -f -e trace=network,file <service_command>
   ```
2. **`journalctl -xe`**: Проверьте системный журнал на предмет ошибок сегментации (segfault) или вмешательства OOM Killer.

**Health Checks и локальный доступ:**
Если сервис «жив» на localhost, но недоступен снаружи — проверяйте Health Check на балансировщике (путь, порт, код ответа). Используйте `curl` для проверки непосредственно на сервере:

```bash
curl -v localhost:<port>/health
```

**Диагностика железа и дисков:**
Если наблюдается общая деградация производительности или ошибки ввода-вывода:
- **`smartctl`**: Проверьте состояние дисков на предмет аппаратных ошибок.
  ```bash
  sudo smartctl -a /dev/sdX
  ```
- **`iostat` / `iotop`**: Анализ нагрузки на диск в реальном времени.

### Уровень 4: Зависимости и Сеть

**SSL/TLS (Красные флаги):**

- Истекший сертификат.
- Неполная цепочка (Missing Intermediate).
- Неверное системное время на сервере.

```bash
# Проверка сертификата
openssl s_client -connect <host>:443 -servername <host>
```

**Проверка доступности БД и кэшей:**

```bash
nc -zv <db_host> <db_port>
```

Подробнее: [Порядок диагностики сети](../../Networking/network_troubleshooting_order.md)

## Post-mortem (Анализ после инцидента)

**Главное правило:** Беспристрастность (Blameless). Ищем «почему система позволила», а не «кто виноват».

### Структура отчета

1. **Факты и таймлайн:** Когда началось, когда обнаружено, когда исправлено.
2. **Симптомы и Влияние:** Что видели пользователи, на сколько узлов повлияло.
3. **Корневая причина (Root Cause):**
   - **Триггер:** Что произошло (например, запуск CI/CD пайплайна).
   - **Уязвимость:** Почему это привело к сбою (например, отсутствие health check при деплое или единая точка отказа).
4. **Action Items:** Конкретные шаги, чтобы инцидент не повторился.
