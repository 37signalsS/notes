# Общая методология диагностики сервисов

## Definitions

**Траблшутинг (Troubleshooting)** — систематический процесс выявления, изоляции и устранения причин некорректного поведения системы. Эффективная диагностика опирается на факты (Observation), а не на догадки (Assumption).

**Принцип «снизу вверх» (Bottom-up)** — стратегия, начинающаяся с физического уровня и ОС и поднимающаяся к прикладному коду. Позволяет последовательно исключать возможные причины сбоя на каждом этапе.

**Наблюдение (Observation)** — объективные данные из логов и метрик (например, «HTTP 502 в логах Nginx»).

**Интерпретация (Interpretation)** — гипотеза о причине (например, «502 ошибка, значит бэкенд упал»). Ошибка на этапе интерпретации ведет к ложному пути диагностики.

## Basic Concepts

### Золотые правила диагностики

1.  **Разделяй факты и догадки** — записывайте только то, что видите. «Сервис тормозит» — это интерпретация. «P99 Latency выросла с 100мс до 5000мс» — это факт.
2.  **Не перезагружать без данных!** — перезагрузка скрывает проблему, очищая контекст (состояние RAM, сетевые соединения). Сначала соберите логи и дампы.
3.  **Метод сравнения (Bad vs Good)** — всегда ищите работающий эталон. Чем отличается конфигурация, версии пакетов или нагрузка на работающем узле от проблемного? (`diff`, `git log`).
4.  **Сначала — макро-анализ** — не ныряйте в код приложения, пока не убедились, что на сервере есть свободное место и не «лежит» сеть.

### Стратегии диагностики

| Стратегия | Принцип | Когда использовать |
| :--- | :--- | :--- |
| **Bottom-up** | От железа к коду | Полная недоступность, «черный экран», проблемы ОС. |
| **Top-down** | От UI/API к syscalls | Функциональные баги, ошибки бизнес-логики. |
| **Divide & Conquer** | Проверка середины стека | Сложные сетевые взаимодействия (например, проверка L4). |
| **Change-based** | Анализ последних изменений | Внезапные сбои после деплоя или патча. |

### Методологии мониторинга

-   **USE (Infrastructure):** Utilization, Saturation, Errors (для ресурсов: CPU, RAM, Disk).
-   **RED (Services):** Rate, Errors, Duration (для API и микросервисов).
-   **Golden Signals:** Latency, Traffic, Errors, Saturation.
*Подробнее:* [**Методологии мониторинга**](../../../Concepts/Observability_and_Monitoring/monitoring_methodologies.md).

## Practical Scenarios

### Уровень 0: Проблемы загрузки (Boot)

Если сервер недоступен по SSH, получите доступ к консоли (IPMI/KVM/VNC).
**Карта загрузки:**
**BIOS/UEFI** (поиск загрузчика) → **GRUB** (выбор ядра) → **Kernel** (инициализация железа) → **Initramfs** (монтирование root) → **Systemd** (старт процессов).

**Где мы застряли?**
- **Ошибка GRUB:** Проблема до ядра (загрузчик, таблица разделов).
- **Kernel Panic:** Проблема в ядре, драйверах или повреждении `rootfs`.
- **Initramfs Shell:** Проблема с монтированием дисков (UUID, RAID, LVM).

*Подробнее:* [**Восстановление при сбоях загрузки**](./boot_failure_recovery.md).

### Уровень 1: Сервер и ОС (Rapid Assessment)

**Красные флаги (Red Flags):**
- **High Load Average при низком CPU:** Почти всегда IO Wait (диск).
- **Растет Swap при наличии Free RAM:** Memory Pressure (нехватка памяти).
- **Диск заполнен на 100%:** Процессы не могут писать логи или открывать сокеты.
- **Ошибки в dmesg:** `Read-only file system`, `I/O error`, `MCE`.

**Быстрая проверка (60 секунд):**
```bash
uptime              # → Load Average (насыщенность)
dmesg -T | tail     # → Ошибки ядра и OOM Killer
df -h               # → Свободное место
free -h             # → Реально доступная память (available)
iostat -xz 1 3      # → Утилизация и задержки дисков
```
*Подробнее:* [**Быстрая диагностика сервера**](./rapid_assessment.md).

### Уровень 2: Процесс и порты (Runtime)

**Статус процесса:**
```bash
systemctl status <service>    # → Active: active (running) или failed
ps aux | grep <process>       # → Поиск зомби (Z) или D-state
```

**Сетевые порты:**
```bash
# Проверка, кто слушает порт
ss -tlpn | grep :80
# → LISTEN 0 128 0.0.0.0:80 ... users:(("nginx",pid=123,fd=6))
```

### Уровень 3: Приложение и логи

**Анализ логов:**
```bash
# Логи systemd-юнита
journalctl -u <service> -f -n 100

# Если сервис падает без логов, проверьте хвост системного журнала
journalctl -xe
```

**Диагностика «молчаливого» падения:**
Если логов нет, используйте трассировку системных вызовов:
```bash
sudo strace -f -e trace=network,file <service_command>
# → openat(..., "/etc/app.conf", ...) = -1 ENOENT (Файл не найден)
```
*Подробнее:* [**Трассировка и отладка**](./tracing_and_debugging.md).

**Health Checks и локальный доступ:**
Проверьте, отвечает ли сервис самому себе, чтобы исключить влияние сети:
```bash
curl -v localhost:<port>/health
# → HTTP/1.1 200 OK
```

**Диагностика железа и дисков:**
```bash
sudo smartctl -a /dev/sdX     # Аппаратные ошибки диска
iotop -o                      # Какие процессы грузят диск прямо сейчас
```

### Уровень 5: Диагностика медленной работы сервера

**Медленная работа** всегда означает одно: где-то выстроилась очередь. Это может быть очередь к процессору, диску, памяти, сетевому интерфейсу, базе данных или внешнему сервису. Вся диагностика сводится к поиску того, **где именно** эта очередь.

#### Два типа проблемных ситуаций

Перед диагностикой важно различить два типа жалоб, которые на первый взгляд звучат одинаково:

1.  **Пользователь долго ждёт ответа.** Приложение не отвечает, но ресурсы сервера свободны. Причина — очередь **вне** сервера: за базой данных, внешним API или внутренней службой.
2.  **Сам сервер «задыхается».** Ресурсы на пределе, все процессы стоят в очереди. Причина — очередь **внутри** сервера.

Эти ситуации далеко не всегда связаны: сервер может быть загружен под завязку и отвечать мгновенно, а может работать на 5% мощности, но задерживать ответы на 10–20 секунд.

Кроме того, проблема может быть не на том сервере, который подозревается изначально. Любое приложение почти никогда не живёт одно: оно запраивает данные из базы на соседнем сервере, обращается к внешним сервисам и внутренним службам. Если любой из этих компонентов начнёт отвечать медленно, ваш сервер будет выглядеть абсолютно здоровым, но пользователи почувствуют задержку. Сам сервер при этом не будет тормозить — он будет ждать.

#### Алгоритм диагностики

Диагностика начинается с общей картины, что стоит и прибесплатно, и сразу направляет на нужную ветвь. Проверки идут от самых дешёх и быстрых к самым дорогим.

**Шаг 1. Общая оценка (Load Average).** Смотрите [Load Average](../../Core/processes/scheduling.md). Метрика состоит из трёх чисел — за 1, 5 и 15 минут. Если первое число сильно больше последнего, проблема только что началась и растёт. Если наоборот — пик уже прошёл.

Чтобы правильно интерпретировать Load Average, знайте количество логических ядер. Значение, сопоставимое с числом ядер, означает полную загрузку. Однако в Linux в Load Average включаются не только процессы, ждущие CPU, но и процессы в состоянии D (Uninterruptible Sleep), ожидающие диск. Поэтому высокий Load Average при низком %CPU — признак проблем с диском, сетью (NFS) или блокировками в ядре.

```bash
uptime
# → load average: 0.15, 0.25, 0.10
nproc
# → 8 (количество логических ядер)
cat /proc/loadavg
# → 0.15 0.25 0.10 1/800 12345
```

**Шаг 2. Состояние процессов (`top`).** Смотрите [Утилита top](../../Diagnostics/Processes/top.md). Здесь важны не «красивые» проценты, а два вопроса:
- Есть ли процесс, который забрал себе весь процессор?
- В каком состоянии сидят остальные процессы?

Статусы процессов обозначаются буквами: **R** — работает или готов работать; **D** — застрял в ожидании диска, его нельзя даже прервать.

Здесь ставится главный развилка:
- **Ветвь A (ресурсы исчерпаны):** кто-то забрал ресурс, остальные ждут.
- **Ветвь B (ресурсы свободны, сервер ждёт):** процессы стоят не из-за нехватки CPU/памяти/диска, а из-за ожидания чужого ответа.

#### Ветвь A: Исчерпание ресурсов

Если найден процесс, который забрал все ресурсы, или процессы стоят в очереди — проверьте четыре ресурса по порядку.

**1. Процессор.** Смотрите [vmstat](../../Diagnostics/Memory/vmstat.md) с интервалом в секунду. Колонка очереди (`r`) показывает, сколько задач ждёт своей доли. Если очередь стабильно больше числа ядер — процессора действительно не хватает.

Также проверьте загрузку по ядрам через [sar](../Performance/sar.md), так как бывают случаи, когда общая загрузка выглядит нормально, а одно конкретное ядро долбится в 100%. Это однопоточная задача, и расследование по этой ветке завершено.

```bash
vmstat 1 5
# → r b swpd free buff cache si so bi bo in cs us sy id wa st
# → 5 2 0 100M 50M 2500M 0 0 0 500 100 500 80 15 5 0 0
```

**2. Память.** Не обращайте внимания на колонку `free` в `free` — она почти всегда показывает мало свободной памяти, потому что Linux отдаёт незанятую память под кэш и возвращает её по первому требованию. Смотрите на `available`.

```bash
free -h
# → Можно использовать: 50G, Бесподпись (available): 10G
```

А вот на что смотреть — это Swap. Если в `vmstat` колонки `si` и `so` отличны от нуля, система прямо сейчас гоняет страницы памяти на диск и обратно. Это одна из самых мучительных разновидностей торможения: формально всё работает, но фактически всё стоит.

```bash
vmstat 1 5
# → si и so > 0 → активный свопинг
```

Если система активно свопит — проверьте [OOM Killer](../../Core/processes/oom_killer_mechanism.md). Если приложение молча перезапускается (например, раз в сутницу) — причина, скорее всего, в OOM-киллере, который выбирает самый «тяжёлый» процесс и избавляется от него, чтобы спасти остальных.

В современных системах с группами ресурсов (cgroups) существует режим, при котором избавляются не от одного процесса, а от всей группы разом. Это сделано для пулов обработчиков, где выживший наполовину пул ведёт себя хуже, чем полностью отсутствующий.

**3. Диск.** Смотрите [iostat](../../Diagnostics/Filesystem/iostat.md) с расширенным выводом (`-x`). Нас интересуют две цифры: насколько устройство занято и сколько в среднем ждёт один запрос. Если время ожидания (`await`) уехало за десятки миллисекунд — диск не справляется, и все, кто к нему обращаются, стоят в очереди.

Не забудьте проверить место — как обычное, так и количество записей файловой системы (inodes), которое кончается независимо от свободного места.

```bash
iostat -xz 1
# → Device:  rrqm/s  wrqm/s  r/s  w/s  ...  await  %util
# → sda        0.00    5.00  100  500  ...  35.00  95.00

df -h    # → Свободное место на диске
df -i    # → Свободные inodes (критично при множестве мелких файлов)
```

**4. Сеть.** При проверке сети важно убедиться, что вы не упёрлись в лимит пропускной способности и что у вас нет ошибок и потерь на интерфейсе.

```bash
ip -s link show eth0
# → rx_errors, tx_errors — признаки проблем на уровне драйвера или кабеля
```

Если на этом этапе найдено хотя бы одно узкое место — вы уже не гадаете, а идёте чинить конкретную проблему. А если все четыре ресурса чистые, значит, нужно переходить ко второй ветке.

#### Ветвь B: Ожидание зависимостей

Все четыре ресурса чисты, но пользователи ждут свои ответы по несколько десятков секунд. Это значит, что процессы стоят — они ждут кого-то.

**Шаг 1. Что именно ждут процессы?**

Статусы процессов показывают состояние. Если их много и они находятся в статусе **D** (Uninterruptible Sleep) — они ждут диск, даже когда сам диск по цифрам не загружен. Так бывает с сетевыми файловыми системами. Если процессы просто спят (статус **S**), а нагрузки нет — скорее всего, они ждут сеть.

```bash
ps -eo pid,stat,wchan:20,comm | grep " D "
# → D-state процессы, заблокированные на I/O
```

Подробнее о диагностике D-state: [Отладка процессов](../../Core/processes/Troubleshooting/debugging.md), [Чек-лист диагностики I/O](../Performance/DiskIO/diagnostic_checklist.md).

**Шаг 2. Кого именно ждут?**

Откройте соединения командой [ss](../../Diagnostics/Networking/ss.md) и увидите, куда ваша машина стучится и сколько таких соединений висит. Если большое количество подключений замерло в ожидании ответа от одного и того же адреса — виновник найден. Но это, скорее всего, не ваша машина.

```bash
ss -tnp | grep ESTAB
# → список установленных соединений с PID
```

**Шаг 3. Локальная диагностика.**

Перед тем как копать дальше, выполните замер, который сразу отсекает половину подозреваемых. Постучитесь в приложение прямо на своей машине, минуя балансировщик и интернет. Если локально оно отвечает мгновенно, а снаружи медленно — приложение ни при чём, и разбирать нужно путь до него.

```bash
curl -s -o /dev/null -w "%{time_total}s\n" http://localhost:8080/health
# → 0.005s — приложение здорово, проблема в сети или балансировщике
```

Если и локально оно работает медленно — копайте внутрь.

**Шаг 4. Замер времени до зависимостей.**

С помощью `curl` с выводом времени (см. [Жизненный цикл веб-запроса](../../../Networking/Concepts/web_request_lifecycle.md)) измерьте время до каждой зависимости по очереди: сколько отвечает база, сколько внешний сервис, сколько внутренняя служба. Обычно какая-нибудь одна из зависимостей почти всегда выделяется на фоне остальных.

```bash
curl -w "\
DNS Resolution:    %{time_namelookup}s\n\
TCP Connect:       %{time_connect}s\n\
TLS Handshake:     %{time_appconnect}s\n\
Time to First Byte:%{time_starttransfer}s\n\
Total Time:        %{time_total}s\n\
" -o /dev/null -s https://api.example.com
# → DNS Resolution:    0.005s
# → TCP Connect:       0.025s
# → Time to First Byte: 2.500s
# → Total Time:        2.600s
```

Смотрите не только на средние показатели, но и на разброс. Ровная задержка, одинаковая для всех запросов, обычно означает, что вы упираетесь в одного и того же источник и всегда ждёте его фиксированное время. А если большинство запросов быстрые, но каждый десятый висит несколько секунд — ищите очередь: ресурс кончается периодически под всплеск нагрузки.

**Шаг 5. Разрешение имён (DNS).**

Разрешение имён — редкий, но очень неприятный случай. Если у сервера сломан или замедлен путь к службе имён, каждый исходящий запрос получает ровную добавку в несколько секунд. Это выглядит так, будто бы всё одинаково тормозит: медленно, ровно, без всплесков и по всем направлениям сразу.

```bash
dig example.com
# → Query time: 5000ms — проблема с DNS-резолвером
```

Подробнее о диагностике DNS: [DNS-мисконфигурация](../../../Networking/Troubleshooting/real_case_troubleshooting_dns_misconfig.md), [Производительность DNS-резолвинга](../Networking/dns/dns_resolution_performance.md).

#### База данных

База данных стоит на пути почти каждого запроса, поэтому оказывается виновником чаще всех. Ломаться в базе может четыре вещи.

**1. Исчерпание пула подключений.**

Приложение держит к базе не отдельное соединение на каждый запрос, а заранее открытый набор — пул. Пул конечен, и если все подключения заняты, следующий запрос не идёт в базу вообще, а встаёт в очередь за свободным. При этом снаружи всё выглядит как просто медленная база, хотя сама база при этом может работать вполне штатно.

Увидев исчерпанный пул, первым делом хочется его увеличить. Иногда это действительно может помочь, но часто это сделает ситуацию ещё хуже: каждое подключение к базе стоит ей памяти и процессорного времени, а число одновременных запросов, которые она реально способна тянуть, ограничено её ядрами и дисками. Расширив пул, вы не увеличиваете пропускную способность базы — вы просто переносите очередь: до этого запросы ждали снаружи, а теперь ждут внутри базы и мешают друг другу.

Подробнее о пулах соединений: [Connection Pooling](../../../Networking/Concepts/connection_pooling.md), [Управление соединениями в БД](../../../Databases/Concepts/database_performance_concepts.md#управление-соединениями-connection-management).

**2. Медленные запросы.**

В любой базе можно посмотреть, что выполняется прямо сейас и сколько времени уже занимает. Как правило, там можно обнаружить один запрос, который идёт минутами, десятками минут или часами, потому что данных стало больше, чем в тот момент, когда его придумали, а нужный индекс так и не сделали.

Подробнее: [Диагностика дисковых узких мест в базах данных](../../../Databases/db_disk_bottleneck_troubleshooting.md).

**3. Блокировки.**

Блокировка — это когда один запрос держит строку или таблицу, и остальные ждут, пока он отпустит. Почти всегда можно найти одну застрявшую транзакцию, которую кто-то открыл, но не закрыл.

- PostgreSQL: [Конкуренция и блокировки](../../../Databases/PostgreSQL/Concepts/concurrency_and_locking.md#диагностика-очереди-блокировок)
- MySQL: [Блокировки и взаимоблокировки](../../../Databases/MySQL/locking_and_deadlocks.md)

**4. Переполнение памяти.**

Пока рабочие данные помещаются в память базы, она отвечает из памяти и делает это очень быстро. Но как только данные перестают помещаться, каждый запрос начинает ходить на диск — и вы видите ту же самую картину с дисковой очередью и большим временем ожидания.

```bash
psql -c "SELECT datname, blks_read, blks_hit FROM pg_stat_database;"
# → Высокие blks_read при низком hit ratio → данные не помещаются в shared_buffers
```

#### Приложение

Если все предыдущие шаги не дали ответа — последний подозреваемый.

**1. Исчерпание обработчиков (Handler/Thread Pool).**

У любого приложения, которое отвечает на запросы, есть набор рабочих процессов или потоков, и их конечное число. Если каждый из них занят медленным запросом, новые запросы встают в очередь. Ситуация может быть обманчивой: процессор почти не загружен, память свободна, при этом сайт не отвечает. Это та же очередь, только теперь она возникает из-за обработчиков.

Смотрите на статус пула — сколько обработчиков занято из конкретного числа. Если занято всё — причина найдена. Диагностика через метрики рантайма — [Метрики рунтайма приложений](../../../Concepts/Observability_and_Monitoring/application_runtime_metrics.md).

**2. Утечка памяти.**

Здесь важен не мгновенный замер, а тренд. Нужно смотреть на память процесса за несколько дней. Если она ровно ползёт вверх и никогда не спадает — приложение не отдаёт то, что взяло. Подробнее: [Отладка процессов: утечки памяти](../../Core/processes/Troubleshooting/debugging.md).

**3. Приложение на собственных блокировках.**

Процесс жив, процессор не ест, а работа не идёт, потому что все потоки заблокированы в ожидании. Симптом такой же, как и с утечкой: перезапуск временно помогает, а через сутницу проблема возвращается.

**4. Перезапуск как временная мера.**

Перезапуск действительно может помочь и почти всегда, ведь он обнуляет утечку, освобождает зависшие обработчики и сбрасывает залипшие соединения. Но это всего лишь отсрочка той же самой проблемы. Если после рестарта стало хорошо, а через сутницу снова плохо — причина накапливается со временем, и это почти наверняка утечка или незакрываемые ресурсы. Замеры до перезапуска надо успеть снять, иначе следующий круг вы будет начинать с нуля.

**5. Профилирование.**

Если все остальное не помогло, снимите профиль работающего процесса и увидьте, какая функция реально съедает процессорное время. Раньше для этого приложение надо было останавливать и перезапускать особенным образом, а сейчас профиль снимают с живой системы, почти без накладных расходов.

Подробнее: [Профилирование: глубокое погружение](../../../Concepts/Observability_and_Monitoring/profiling_deep_dive.md), [Непрерывное профилирование](../../../Concepts/continuous_profiling.md).

## Post-mortem (Анализ инцидента)

Цель — системные улучшения, а не поиск виновных (Blameless Culture).

### Структура отчета
1.  **Timeline:** Хронология (проблема возникла → алерт сработал → инженер зашел → фикс применен).
2.  **Impact:** Масштаб (сколько пользователей затронуто, какие регионы).
3.  **Root Cause:** Истинная причина (например, «отсутствие таймаутов в коде привело к блокировке всех worker-потов»).
4.  **Action Items:** Конкретные шаги «Что сделать, чтобы не повторилось».
