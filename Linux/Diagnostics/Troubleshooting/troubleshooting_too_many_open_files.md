# Диагностика ошибки "too many open files"

## Определения

**Файловый дескриптор (File Descriptor, FD)** — неотрицательное целое число, идентифицирующее открытый файл, сокет или другой ресурс I/O. Подробнее: [Файловые дескрипторы](../../FileSystems/file_descriptors.md).

**Ошибка «too many open files» (EMFILE/ENFILE)** — возникает при исчерпании лимита открытых файловых дескрипторов процессом (EMFILE) или системой в целом (ENFILE).

**Soft limit** — текущий действующий лимит. Процесс может увеличить soft limit до значения hard limit.

**Hard limit** — максимальное значение для soft limit. Изменить может только root.

## Основные концепции

### Иерархия лимитов

Лимиты устанавливаются на нескольких уровнях:

| Уровень | Механизм | Где настраивается |
| :--- | :--- | :--- |
| Система | `fs.file-max` | `/proc/sys/fs/file-max`, `sysctl` |
| Пользователь | `nofile` soft/hard | `/etc/security/limits.conf` |
| Сервис (systemd) | `LimitNOFILE` | Unit-файл сервиса |
| Сессия | `ulimit -n` | `~/.bashrc`, `/etc/profile` |
| Процесс | `/proc/<PID>/limits` | Наследуется от родителя |

Подробно: [Иерархия лимитов процессов](../../Core/processes/resource_limits_concepts.md).

### Утечка файловых дескрипторов

Ситуация, когда процесс открывает файлы/сокеты, но не закрывает их. Приводит к постепенному исчерпанию лимита и ошибке EMFILE.

### Неочевидные причины ошибки

1. **Недостаток прав доступа:** Иногда ошибка "too many open files" может возникать косвенно, если у процесса нет прав на открытие файла или запись в директорию, что приводит к некорректной обработке ошибок в коде приложения и исчерпанию дескрипторов при попытках повторного открытия.
2. **Лимиты интерпретаторов (PHP/Java):** В веб-приложениях лимиты могут быть заданы на уровне конфигурации среды выполнения (например, в настройках пула PHP-FPM), которые могут быть ниже системных.
3. **Ошибки запуска systemd:** Если сервис не стартует после рестарта (хотя бинарник на месте), это может быть связано с отсутствием прав доступа к рабочей директории или лог-файлам, что блокирует открытие дескрипторов при инициализации.

## Практические сценарии

### Шаг 1: Подсчёт открытых дескрипторов

```bash
# Количество открытых FD процесса
sudo lsof -p <PID> | wc -l

# Альтернатива через /proc
ls /proc/<PID>/fd | wc -l
```

Подробнее: [`lsof`](../Processes/lsof.md).

### Шаг 2: Проверка лимитов процесса

```bash
grep "Max open files" /proc/<PID>/limits
```

Пример вывода:

```
Max open files            8192                 65535                files
```

Здесь `8192` — soft limit, `65535` — hard limit.

### Шаг 3: Проверка лимитов на разных уровнях

```bash
# Текущая сессия
ulimit -n

# Глобальная статистика использования FD
# Вывод: <allocated> <free> <max>
cat /proc/sys/fs/file-nr
# → 2944    0    1048576

# Глобальный лимит системы (можно увеличить через sysctl)
cat /proc/sys/fs/file-max

# Лимиты пользователя (PAM)
cat /etc/security/limits.conf

# Лимит systemd-сервиса
systemctl show <service_name> -p LimitNOFILE
```

### Шаг 4: Увеличение лимита

**Временно для текущей сессии (ulimit):**

```bash
ulimit -n 65536
```

Действует до закрытия терминала. Не может превысить hard limit. Удобно для быстрой проверки или запуска проблемного скрипта.

**systemd-сервис (редактирование юнита):**

```ini
[Service]
LimitNOFILE=65535
```

```bash
sudo systemctl daemon-reexec
sudo systemctl restart <service_name>
```

**systemd-сервис (runtime, без редактирования файлов):**

```bash
sudo systemctl set-property service.service LimitNOFILE=65536
```

Изменение применяется немедленно (через cgroups), для вступления в силу требуется перезапуск сервиса. Эффект сохраняется после перезагрузки (запись в `/etc/systemd/system.control/`).

**Системный уровень (`fs.file-max`):**

```bash
# Временно
sudo sysctl -w fs.file-max=2097152

# Постоянно (/etc/sysctl.d/90-file-max.conf)
fs.file-max = 2097152
```

**Пользовательский уровень (`/etc/security/limits.conf`):**

Для конкретного пользователя:

```
appuser    soft    nofile    65536
appuser    hard    nofile    65536
```

Для всех пользователей сразу:

```
*    soft    nofile    65535
*    hard    nofile    65535
```

### Шаг 5: Диагностика в Kubernetes

Если процесс работает в pod, ulimit наследуется от контейнерного рантайма (containerd / CRI-O), а не от хоста напрямую.

```bash
# Проверка изнутри пода
kubectl exec -it $POD -- sh -c 'ulimit -n; ulimit -Hn'

# Единственный достоверный источник — /proc/PID/limits
PID=$(kubectl exec -it $POD -- pgrep -f myapp | head -1 | tr -d '\r')
kubectl exec -it $POD -- cat /proc/$PID/limits | grep "Max open files"
```

### Шаг 6: Настройка лимита в Kubernetes

Декларативного поля `resources.limits.openFiles` не существует. Используют три подхода:

**Подход 1 — containerd (правильное решение):**

```toml
# /etc/containerd/config.toml
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
  Rlimits = [
    { type = "RLIMIT_NOFILE", hard = 1048576, soft = 1048576 }
  ]
```

**Подход 1 — CRI-O:**

```ini
# /etc/crio/crio.conf
[crio.runtime]
default_ulimits = [
  "nofile=1048576:1048576",
]
```

После перезапуска рантайма все новые контейнеры наследуют эти лимиты.

**Подход 2 — securityContext.sysctls (ограниченно):**

```yaml
spec:
  securityContext:
    sysctls:
      - name: fs.file-max
        value: "1048576"
```

Задаёт общесистемный лимит в namespace контейнера, но не soft limit процесса. Типичную проблему EMFILE не решает.

**Подход 3 — ulimit в entrypoint (костыль):**

```dockerfile
ENTRYPOINT ["/bin/sh", "-c", "ulimit -n 1048576 && exec /usr/local/bin/myapp"]
```

Важный нюанс: процесс может поднять soft limit только до hard limit. Если hard limit = 1024, команда `ulimit -n 1048576` завершится ошибкой. Для повышения hard limit контейнеру нужна capability `CAP_SYS_RESOURCE`, которой обычно нет у защищённых подов.

## Дополнительная информация

### ulimit vs inode limit (вопрос на собеседовании)

`ulimit -n` и `df -i` — два разных уровня ограничений:

| | ulimit (nofile) | Inode limit (df -i) |
|:---|:---|:---|
| Что ограничивает | Количество открытых FD на процесс/пользователя | Общее количество файлов (inode) на файловой системе |
| Уровень | Процесс / сессия / пользователь | Файловая система |
| Типичное сообщение | `Too many open files` | `No space left on device` (даже если `df -h` свободен) |
| Диагностика | `cat /proc/sys/fs/file-nr` | `df -ih` |
| Утечка | Программная (FD не закрыты) | Переполнение fs (миллионы мелких файлов) |

Если `df -h` и `df -ih` в норме, а сервис падает с `Too many open files` — проблема именно в лимитах FD, а не в дисковом пространстве.

### Динамическая трассировка с strace

Для выявления утечки FD отслеживают вызовы `openat` и `close`:

```bash
sudo strace -e trace=openat,close -p <PID>
```

Подробнее: [Трассировка и отладка](./tracing_and_debugging.md).

### Когда повышение лимита — правильное решение

Не каждая ошибка EMFILE — утечка. Иногда лимит действительно слишком низок для рабочей нагрузки:

- Реверс-прокси (NGINX, Envoy, HAProxy) с десятками тысяч соединений
- WebSocket-сервер с постоянными соединениями
- Сервер БД с большим количеством клиентских подключений
- Пограничный CDN-узел

Для таких сценариев выставляют default ulimit в рантайме на уровне 1 048 576 и выше, предварительно убедившись, что внутренние ограничения самого приложения (`worker_connections`, уровень параллелизма и т. д.) настроены соответствующим образом.

### Мониторинг

```promql
# Доля использованных FD процесса (process_exporter или встроенные метрики языка)
process_open_fds / process_max_fds > 0.8

# Для pod через cAdvisor / kubelet
container_file_descriptors / container_ulimits_soft{ulimit="open_files"} > 0.8

# Детектор CLOSE_WAIT (требуется exporter состояний TCP)
node_netstat_Tcp_CloseWait > 1000
```

Алерт на уровне 80% использования FD позволяет обнаружить утечку за несколько дней до падения продакшена.

### Правильная ментальная модель

`ulimit -n` — мягкое ограничение на уровне процесса, которое задаёт компонент, запускающий процесс: unit systemd, containerd, сессия shell и т. д. В Kubernetes цепочка: kubelet → runtime → контейнер → процесс.

EMFILE в продакшене сводится к одной из двух причин:
1. **Утечка на уровне приложения** — лимит нормальный, но код не закрывает FD.
2. **Нагрузка превышает лимит рантайма** — нужно исправлять конфигурацию рантайма, а не городить костыли в pod.

Последовательность диагностики всегда одинакова: проверить лимит → посчитать FD → определить типы → найти источник утечки. Повышение лимита без исправления кода только маскирует проблему.
