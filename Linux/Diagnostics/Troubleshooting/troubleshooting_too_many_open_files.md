# Диагностика ошибки «too many open files»

## Определения

**Файловый дескриптор (File Descriptor, FD)** — неотрицательное целое число, используемое процессом для обращения к открытым файлам, сокетам, каналам (pipes) и другим ресурсам ввода-вывода. Подробнее: [**Файловые дескрипторы**](../../FileSystems/file_descriptors.md).

**Описание открытого файла (Open File Description)** — структура данных в ядре Linux, на которую ссылается дескриптор. Содержит текущее смещение (offset), флаги доступа и счетчик ссылок. Несколько дескрипторов процесса могут указывать на одно и то же описание (например, после `dup()`).

**Ошибка EMFILE (Too many open files)** — исчерпан лимит дескрипторов на уровне конкретного процесса. Приложение не может открывать новые ресурсы. Возвращается системным вызовом `open()`, `socket()`, `epoll_create()`.

**Ошибка ENFILE (File table overflow)** — исчерпан общесистемный лимит дескрипторов в ядре Linux (`fs.file-max`). Возвращается любому процессу при попытке открыть новый файл. В отличие от EMFILE, ENFILE требует вмешательства администратора и увеличения глобального лимита.

**Soft limit (Мягкий лимит)** — текущее действующее ограничение. Процесс может самостоятельно увеличить его до значения жесткого лимита.

**Hard limit (Жесткий лимит)** — «потолок» для мягкого лимита. Увеличить его может только пользователь с правами root или процесс с capability `CAP_SYS_RESOURCE`.

**fs.nr_open** — системный параметр ядра, определяющий абсолютный максимум для любого `ulimit -n`. Даже root не может установить лимит выше этого значения.

**fs.file-max** — глобальный лимит количества открытых файловых дескрипторов для всех процессов в системе. При превышении возвращается ENFILE.

---

## Основные концепции

### Иерархия лимитов

Ограничения проверяются ядром последовательно. Процесс должен пройти через все «фильтры»:

| Уровень | Механизм / Параметр | Где настраивается |
| :--- | :--- | :--- |
| **Ядро (Hard)** | `fs.nr_open` | `/proc/sys/fs/nr_open` |
| **Система (Total)** | `fs.file-max` | `/proc/sys/fs/file-max`, `sysctl` |
| **Пользователь** | `nofile` soft/hard | `/etc/security/limits.conf` (через PAM) |
| **Сервис (systemd)** | `LimitNOFILE` | Unit-файл сервиса |
| **Сессия** | `ulimit -n` | `~/.bashrc`, `/etc/profile` |
| **Процесс** | `/proc/<PID>/limits` | Наследуется от родителя |

### Жизненный цикл файлового дескриптора

1.  **Создание:** При вызове `open()`, `socket()`, `pipe()` ядро выделяет запись в таблице дескрипторов процесса и возвращает минимальный свободный номер.
2.  **Использование:** Дескриптор передается в `read()`, `write()`, `ioctl()`, `epoll_ctl()`.
3.  **Закрытие:** При `close()` ядро уменьшает счетчик ссылок на Open File Description. При достижении нуля запись удаляется из ядерных таблиц.
4.  **Утечка:** Если `close()` не вызван (из-за ошибки в коде или отсутствия `finally`), дескриптор остается в таблице процесса до его завершения.

### Внутреннее устройство ядра

Ядро Linux поддерживает три уровня таблиц:
- **Таблица дескрипторов процесса (PDT):** Локальна для каждого процесса. Содержит указатели на Open File Descriptions.
- **Общесистемная таблица открытых файлов (Open File Table):** Содержит Open File Descriptions. При `dup()`/`fork()` новые дескрипторы указывают на ту же запись.
- **Таблица Inode:** Хранит метаданные файла на диске.

При исчерпании `fs.file-max` ядро возвращает `ENFILE` всем процессам, независимо от их индивидуальных лимитов.

### Классификация ресурсов по типам дескрипторов

Для диагностики важно понимать, какой тип ресурса занимает дескрипторы:

| Тип | Пример | Характерные признаки |
| :--- | :--- | :--- |
| **Обычные файлы** | `/var/log/app.log` | Путь в `/proc/PID/fd` |
| **Сетевые сокеты** | TCP/UDP соединения | `socket:[12345]`, анализируются через `ss` |
| **Pipes** | Каналы между процессами | `pipe:[12345]` |
| **Unix Domain Sockets** | Локальное IPC | `socket:[12345]`, анализируются через `ss -xp` |
| **epoll/kqueue** | Мультиплексирование I/O | `anon_inode:[eventpoll]` |
| **eventfd/timerfd** | События и таймеры | `anon_inode:[eventfd]`, `anon_inode:[timerfd]` |
| **io_uring** | Асинхронный I/O | `/sys/fs/cgroup/...` или `io_uring` в fdinfo |

### Причины возникновения ошибки

1.  **Утечка дескрипторов:** Программа открывает файлы/сокеты, но не закрывает их (например, из-за ошибок в логике или отсутствия блоков `finally`).
2.  **Недостаток прав доступа (Косвенно):** Если у процесса нет прав на запись в директорию, он может бесконечно пытаться переоткрыть файл в цикле, поглощая дескрипторы при некорректной обработке ошибок.
3.  **Лимиты сред выполнения:** Интерпретаторы (PHP-FPM, Java) могут иметь собственные настройки пулов, которые ниже системных.
4.  **CLOSE_WAIT Storm:** Накопление сокетов, которые не были закрыты приложением после получения FIN от клиента.
5.  **Fork-бомба:** Резкий рост количества процессов, каждый из которых наследует дескрипторы родителя.
6.  **Недостаточный `fs.file-max`:** При большом количестве concurrent-соединений (L7-балансировщики, шардированные БД) системный лимит может быть исчерпан суммой по всем процессам.

## Практические сценарии

### Шаг 1: Подсчёт и анализ открытых дескрипторов

```bash
# Общее количество открытых FD процесса
ls /proc/<PID>/fd | wc -l
# → 1024

# Глубокий анализ типов ресурсов (позволяет найти источник утечки)
ls -l /proc/<PID>/fd
# → lrwx------ 1 ... 0 -> /etc/hosts (Файл)
# → lrwx------ 1 ... 3 -> socket:[123456] (Сеть)
# → lrwx------ 1 ... 4 -> anon_inode:[eventfd] (События ядра, характерно для Java/Netty)
# → lrwx------ 1 ... 5 -> pipe:[234567] (Межпроцессное взаимодействие)
```

**Детализация по типам через `lsof`:**

```bash
# Подсчет открытых файлов по типам
lsof -p <PID> | awk '{print $5}' | sort | uniq -c | sort -rn
# →   950 TCP
# →    24 file
# →    12 UDP
# →     6 IPv4

# Анализ состояния сокетов
lsof -i -p <PID> | awk '{print $9}' | cut -d'>' -f2 | sort | uniq -c | sort -rn
# →   450 ESTABLISHED
# →   380 CLOSE_WAIT
# →   120 TIME_WAIT
```

### Шаг 2: Проверка лимитов процесса и системы

```bash
# Какие лимиты видит ядро для конкретного процесса прямо сейчас
grep "Max open files" /proc/<PID>/limits
# → Max open files            1024                 4096                 files

# Глобальная статистика использования дескрипторов (выделено / свободно / максимум)
cat /proc/sys/fs/file-nr
# → 2944    0    1048576

# Проверка текущего значения fs.nr_open (абсолютный потолок)
sysctl fs.nr_open
# → fs.nr_open = 2097152

# Лимит systemd-сервиса (без чтения файлов юнитов)
systemctl show <service_name> -p LimitNOFILE
# → LimitNOFILE=65536
```

### Шаг 3: Увеличение лимитов

**Системный уровень:**
```bash
# Временно
sudo sysctl -w fs.file-max=2097152
# Постоянно (/etc/sysctl.d/90-file-max.conf)
fs.file-max = 2097152
fs.nr_open = 2097152
```

**Сервис systemd (правильный метод):**
```bash
sudo systemctl edit <service_name>
# [Service]
# LimitNOFILE=1048576

sudo systemctl daemon-reload
sudo systemctl restart <service_name>
```

**Пользовательский уровень (PAM):**
В `/etc/security/limits.conf`:
```text
*    soft    nofile    65535
*    hard    nofile    65535
```

**Оперативное изменение для running-процесса:**
```bash
# Изменение лимита без перезапуска (требует прав)
sudo prlimit --pid <PID> --nofile=65536:131072
```

### Шаг 4: Диагностика и настройка в Kubernetes

В Kubernetes лимиты наследуются от рантайма узла (Node), а не от параметров `resources` в манифесте пода.

**Диагностика внутри пода:**
```bash
# Проверка мягкого и жесткого лимитов
kubectl exec $POD -- sh -c 'ulimit -Sn; ulimit -Hn'
# → 1024
# → 1048576
```

**Настройка через Container Runtime (Рекомендуется):**
Для **containerd** (`/etc/containerd/config.toml`):
```toml
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
  Rlimits = [
    { type = "RLIMIT_NOFILE", hard = 1048576, soft = 1048576 }
  ]
```
После изменения рантайм требует перезапуска, а поды — пересоздания.

**Костыль (ulimit в entrypoint):**
```dockerfile
ENTRYPOINT ["/bin/sh", "-c", "ulimit -n 65536 && exec /app/binary"]
```
*Внимание:* Работает только если контейнеру разрешена capability `CAP_SYS_RESOURCE`.

### Шаг 5: Диагностика ENFILE (общесистемное исчерпание)

```bash
# Если cat /proc/sys/fs/file-nr показывает, что выделено близко к максимуму:
cat /proc/sys/fs/file-nr
# → 1048000    0    1048576

# Топ-процессы по потреблению FD
for pid in $(ls /proc | grep '^[0-9]\+$'); do
    count=$(ls /proc/$pid/fd 2>/dev/null | wc -l)
    comm=$(cat /proc/$pid/comm 2>/dev/null)
    echo "$count $pid $comm"
done | sort -rn | head -20
# → 4500 1234 java
# → 3200 5678 nginx
# → 1800 9012 postgres

# Проверка, что проблема именно в ENFILE, а не EMFILE:
# Если file-nr близок к максимуму — это ENFILE.
# Если конкретный процесс достиг своего лимита — это EMFILE.
```

**Сравнение ulimit (EMFILE) и inodes (ENFILE / "No space left on device"):**

| Характеристика | ulimit (`nofile`) | Inode limit (`df -i`) |
| :--- | :--- | :--- |
| **Что ограничивает** | Количество открытых FD в RAM | Количество файлов на диске |
| **Типичная ошибка** | `Too many open files` | `No space left on device` |
| **Утечка** | Программная (не закрытые дескрипторы) | Дисковая (много маленьких файлов) |
| **Диагностика** | `ulimit -n`, `/proc/<PID>/limits` | `df -i`, `stat -f .` |
| **Решение** | Увеличение `nofile` soft/hard | Увеличение inodes при `mkfs` или удаление старых файлов |

> **Важно:** Ошибка `No space left on device` не всегда означает нехватку места на диске. Если `df -h` показывает свободное место, но `df -i` исчерпал inodes — проблема в большом количестве мелких файлов.

### Шаг 6: Восстановление без перезапуска (только для опытных администраторов)

**Важно:** Самостоятельное закрытие дескрипторов из userspace может привести к падению приложения. Используйте только при невозможности перезапуска.

```bash
# Способ 1: Обнуление файла через дескриптор (безопасно для логов)
: > /proc/<PID>/fd/<FD_NUMBER>

# Способ 2: Поиск и закрытие утечек через gdb (опасно)
gdb -p <PID> -batch -ex "call close(<FD_NUMBER>)"

# Способ 3: Перезапуск только воркеров (если архитектура позволяет)
nginx -s reload        # Graceful restart
systemctl kill -s SIGUSR1 <service>  # Для приложений, поддерживающих graceful
```

### Шаг 7: Мониторинг и алертинг

**Bash-скрипт для проверки порога:**

```bash
#!/bin/bash
# check_fd_limits.sh
PID=${1:-1}
THRESHOLD=80

limit=$(cat /proc/$pid/limits 2>/dev/null | grep "open files" | awk '{print $4}')
current=$(ls /proc/$pid/fd 2>/dev/null | wc -l)

if [ -z "$limit" ]; then
    echo "ERROR: Cannot read limits for PID $pid"
    exit 1
fi

percent=$((current * 100 / limit))
echo "PID: $pid, FD: $current/$limit ($percent%)"

if [ "$percent" -gt "$THRESHOLD" ]; then
    echo "ALERT: FD usage above ${THRESHOLD}%"
    exit 1
fi
```

**Анализ логов приложения:**

```bash
# Поиск EMFILE в логах journalctl
journalctl -u <service> --since "10 minutes ago" | grep -i "too many open files\|EMFILE\|ENFILE"

# Поиск в логах приложения
grep -r "Too many open files" /var/log/app/

# Проверка системных логов
dmesg | grep -i "file-max\|nr_open"
```

### Шаг 8: Типовые сценарии для распространенных сервисов

**Nginx/Angie:**
```bash
# Проверка текущих лимитов worker-процесса
cat /proc/$(pgrep -n 'nginx: worker')/limits | grep "Max open files"

# В конфиге Nginx: worker_rlimit_nofile должен быть >= worker_connections * 2
# (клиент + бэкенд на каждое проксируемое соединение)
# Если worker_connections=1024, то worker_rlimit_nofile >= 2048
```

**PostgreSQL:**
```bash
# PostgreSQL открывает FD для каждого соединения + WAL + файлы данных
# max_connections не должен превышать доступный лимит FD
# Рекомендация: LimitNOFILE >= max_connections + max_worker_processes + 20
cat /proc/$(pgrep -n postgres)/limits | grep "Max open files"
```

**Java-приложения (JVM):**
```bash
# JVM создает потоки, каждый из которых может открывать сокеты
# Минимальный лимит: кол-во потоков * 10 + запас
# Для приложения с 200 потоками: LimitNOFILE >= 65536
ulimit -u 65536
java -Xmx4g -jar app.jar
```

**Redis:**
```bash
# Redis открывает FD для каждого клиента + RDB/AOF файлы
# maxclients не должен превышать (LimitNOFILE - запас)
redis-cli CONFIG GET maxclients
# → 10000 (по умолчанию)
# Рекомендация: LimitNOFILE >= maxclients + 100
```

## Дополнительная информация

### Сравнение ulimit и лимита inodes (Вопрос на собеседовании)

| Характеристика | ulimit (nofile) | Inode limit (df -i) |
| :--- | :--- | :--- |
| **Что ограничивает** | Кол-во открытых FD в RAM | Кол-во файлов на диске |
| **Типичная ошибка** | `Too many open files` | `No space left on device` |
| **Утечка** | Программная (не вызван `close`) | Системная (миллионы мелких файлов) |

### Динамическая трассировка (strace)

Если лимиты высоки, но FD растут — ищите код, который не закрывает файлы.
```bash
sudo strace -p <PID> -e trace=openat,socket,close
# → openat(AT_FDCWD, "/tmp/tmp.txt", ...) = 10
# → socket(AF_INET, SOCK_STREAM, ...) = 11
# (Если за ними не следует close(10) или close(11) — это утечка)
```

### Мониторинг (PromQL)

```promql
# Процент использования лимита процессом
process_open_fds / process_max_fds > 0.8

# Обнаружение CLOSE_WAIT шторма
node_netstat_Tcp_CloseWait > 1000
```

### Анти-паттерны и частые ошибки

| Ошибка | Причина | Риск | Решение |
| :--- | :--- | :--- | :--- |
| Увеличение `ulimit -n` без изменения `fs.file-max` | Игнорирование системного потолка | ENFILE при высокой нагрузке | Увеличить оба параметра |
| Настройка `limits.conf` для systemd-сервиса | PAM не применяется к сервисам | Лимит остается старым | Использовать `LimitNOFILE=` в юните |
| Установка `LimitNOFILE=1048576` без проверки `fs.nr_open` | Системный потолок ниже | `ulimit -n` не применяется | `sysctl fs.nr_open` должен быть >= лимита |
| Игнорирование `CLOSE_WAIT` в мониторинге | Фокус только на EMFILE | Утечка сокетов | Мониторить `ss`/`netstat` по состояниям |
| Использование `ulimit` в entrypoint контейнера | Требует `CAP_SYS_RESOURCE` | Падение контейнера | Настраивать через runtime или systemd |

### Крайние случаи

- **Read-only корневой раздел:** Нельзя изменить `/etc/security/limits.conf` или `/etc/sysctl.d/`. Используйте `sysctl -w` и `prlimit` для runtime-изменений.
- **Immutable файлы (`chattr +i`):** Нельзя изменить конфигурационные файлы. Используйте `systemctl edit` для drop-in'ов.
- **32-битные системы:** `fs.nr_open` по умолчанию может быть ниже (около 1 млн), но адресное пространство ограничено.
- **NUMA-системы:** На SMP-системах с большим количеством ядер потребление FD может быть выше из-за увеличения количества concurrent-соединений.
- **Виртуализация (steal time):** В гостевых ОС при высокой нагрузке на хост-систему могут возникать задержки, которые приводят к накоплению сокетов в `CLOSE_WAIT`.

### Лучшие практики

1.  **Всегда проверяйте `fs.nr_open` перед увеличением `ulimit -n`.** Если `ulimit` не применяется, причина обычно в системном потолке.
2.  **Используйте `LimitNOFILE=` в systemd-юнитах, а не PAM,** для сервисов.
3.  **Мониторьте соотношение открытых FD к лимиту** (оптимальный порог — 70-80%).
4.  **Настройте алерты на рост CLOSE_WAIT** — это признак утечки сокетов на стороне приложения.
5.  **Документируйте требуемые лимиты** для каждого сервиса в runbook.
6.  **При развертывании новых сервисов** сразу проверяйте применяемые лимиты через `/proc/PID/limits`.
7.  **Для Java-приложений** учитывайте, что каждый поток может открывать сокеты; лимит `nofile` должен быть >= `nproc * 10`.
8.  **Используйте `prlimit` для оперативного вмешательства** при инцидентах, а не перезапуск всего сервиса.

### Чек-лист первичной диагностики

```bash
# 1. Какой лимит у процесса?
cat /proc/<PID>/limits | grep "Max open files"

# 2. Сколько FD открыто сейчас?
ls /proc/<PID>/fd | wc -l

# 3. Какой процент использования?
percent=$(( $(ls /proc/$PID/fd | wc -l) * 100 / $(cat /proc/$PID/limits | grep "open files" | awk '{print $4}') ))

# 4. Какие типы FD занимают ресурсы?
lsof -p <PID> | awk '{print $5}' | sort | uniq -c | sort -rn | head

# 5. Какое состояние сокетов?
ss -tnp | grep <PID> | awk '{print $1}' | sort | uniq -c | sort -rn

# 6. Достигнут ли системный лимит?
cat /proc/sys/fs/file-nr

# 7. Какой fs.nr_open?
sysctl fs.nr_open

# 8. Есть ли CLOSE_WAIT?
ss -tnp | grep CLOSE_WAIT | wc -l
```

### Очистка и восстановление после инцидента

1.  **Восстановление стандартных лимитов** (если временно увеличивали):
    ```bash
    sudo sysctl -w fs.file-max=8388608
    sudo sysctl -w fs.nr_open=1048576
    ```
2.  **Удаление временных drop-in'ов systemd** (если создавали для экстренного вмешательства):
    ```bash
    sudo systemctl revert <service_name>
    ```
3.  **Очистка конфигурационных файлов** от временных правок:
    ```bash
    sudo rm /etc/sysctl.d/99-emergency.conf
    ```
4.  **Проверка отсутствия утечек** после восстановления:
    ```bash
    watch -n5 'ls /proc/<PID>/fd | wc -l'
    ```
