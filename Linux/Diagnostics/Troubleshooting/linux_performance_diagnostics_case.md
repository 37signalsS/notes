# Диагностика производительности в Linux: практические кейсы

## Definitions

**TTFB (Time To First Byte)** — время от отправки запроса клиентом до получения первого байта ответа. Ключевая метрика производительности backend.

**Load Average (LA)** — среднее число процессов в очереди на исполнение и в состоянии uninterruptible sleep (I/O). Подробнее: [Планировщик и LA](../../Core/processes/scheduling.md#load-average-интерпретация).

**I/O Wait (`wa`)** — процент времени простоя CPU в ожидании завершения I/O-операций. Высокое значение указывает на bottleneck дисковой/сетевой подсистемы.

**Энтропия** — уровень случайности, используемый ядром для криптографических операций. Нехватка вызывает блокировки приложений. Подробнее: [Диагностика проблем с низкой энтропией](./linux_entropy_troubleshooting.md).

## Basic Concepts

### Общий подход к диагностике

1. **Локализация:** определить, где возникает задержка — frontend или backend.
2. **Измерение:** использовать конкретные метрики (время ответа сервера, CPU, I/O).
3. **Воспроизведение:** создать стабильные условия для измерения эффекта изменений.

### Паттерны проблем

| Симптом | Вероятная причина | Инструменты диагностики |
| :--- | :--- | :--- |
| Высокий TTFB | Нагрузка на CPU (PHP, Python, etc.) | `ab` + `htop` |
| Задержка без нагрузки CPU/I/O | Ожидание внешнего ресурса | `strace`, анализ кода |
| Высокий LA при нормальной работе | I/O-bound процессы (`rsync`, backup) | `top` → `wa`, `iotop` |
| Случайные зависания при крипто-операциях | Нехватка энтропии | `/proc/sys/kernel/random/entropy_avail` |

## Practical Scenarios

### Кейс 1: Высокий TTFB — PHP/WordPress

**Симптом:** TTFB ~600 мс.

**Диагностика:**

1. DevTools Network → подтверждение: высокий TTFB, проблема на сервере.
2. Нагрузка `ab` + мониторинг `top` → `php-fpm` потребляет 100% CPU.
3. Проверка конфигурации PHP:
   - Отладочные модули (`xdebug`, `xhprof`) → отключение → TTFB ~400 мс.
   - Включение `OPcache` → кэширование опкода → TTFB ~200 мс.

**Выводы:**

- Отладочные модули (`Xdebug`, `Xhprof`) запрещены на production.
- `OPcache` обязателен для любого PHP-production.
- Подход «нагрузи и смотри» (`ab` + `top`) эффективен для быстрой локализации.

### Кейс 2: Задержка отображения — клиентский JS

**Симптом:** страница загружается несколько секунд, но все ресурсы <100 мс.

**Диагностика:**

1. DevTools Network → все запросы быстрые. Проблема не в backend.
2. DevTools Performance → длинная пауза (idle time) до first paint.
3. Анализ кода → обнаружен `setTimeout(..., 4000)` для «плавной» анимации.

**Выводы:**

- Медленная загрузка ≠ проблема backend.
- DevTools Performance необходим для диагностики клиентских проблем.
- Искусственные задержки (`setTimeout`) — частая причина «необъяснимых» тормозов.

### Кейс 3: Плавающий TTFB (20 мс → 3 с)

**Симптом:** TTFB нестабилен, CPU и I/O в норме даже при замедлениях.

**Диагностика:**

1. DevTools → подтверждение плавающего TTFB.
2. Нагрузочное тестирование `ab` → CPU и I/O отсутствуют.
3. Гипотеза: синхронный блокирующий вызов к внешнему API (`curl`, `file_get_contents`).
4. Проверка: анализ кода или [`strace -p <PID>`](./tracing_and_debugging.md#strace-трассировка-системных-вызовов).

**Выводы:**

- Отсутствие нагрузки при высоком времени ответа = ожидание внешнего ресурса.
- Синхронные вызовы к сторонним сервисам — причина нестабильности.
- **Решения:** кэширование ответов, асинхронные вызовы, адекватные таймауты.

### Кейс 4: Высокий LA (900) при нормальной работе

**Симптом:** LA экстремальный, но ключевые сервисы работают без сбоев.

**Диагностика:**

1. `top` → высокое значение `wa` (I/O wait) → нагрузка I/O-bound.
2. Контекст: сервер резервного копирования, постоянно пишущий на медленный накопитель.
3. Процессы `rsync` в состоянии `D` (uninterruptible sleep) раздувают LA, но не блокируют остальные сервисы.

**Выводы:**

- Высокий LA ≠ проблема с CPU. Ключевая метрика — `iowait` (`wa`).
- Интерпретировать LA нужно в контексте роли сервера.

### Кейс 5: Случайные зависания без нагрузки

**Симптом:** система периодически «зависает» при SSH, TLS, старте Java-приложений. CPU, I/O, сеть в норме.

**Диагностика:**

Нехватка энтропии в ядре. Процессы блокируются на `/dev/random` в ожидании случайных данных.

**Решение:** установка `haveged` или `rng-tools`.

**Подробнее:** [Диагностика проблем с низкой энтропией](./linux_entropy_troubleshooting.md).

## Additional Information

### Рекомендации по диагностике производительности

- **Всегда начинайте с локализации** — client vs server. Не тратьте время на серверную диагностику при клиентских проблемах.
- **Используйте комбинацию инструментов** — нагрузка (`ab`, `wrk`) + мониторинг (`htop`, `atop`, `iostat`).
- **Контекст важен** — один и тот же показатель LA=900 критичен для веб-сервера и нормален для backup-сервера.
- **Профилируйте перед оптимизацией** — без точного измерения причин улучшение невозможно.
