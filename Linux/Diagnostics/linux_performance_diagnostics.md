# Диагностика производительности в Linux: Обзор

Эта заметка представляет собой структурированный конспект по основам диагностики производительности в операционных системах Linux. Цель — систематизировать подходы к анализу проблем и дать обзор ключевых утилит.

## 1. Ключевые ресурсы системы

Производительность системы напрямую зависит от четырех основных аппаратных ресурсов. Кроме них, существуют и программные ограничения.

| Ресурс | Ключевые параметры | Узкие места |
| :--- | :--- | :--- |
| **CPU (Процессор)** | Количество ядер/потоков (логических процессоров, SMT), тактовая частота (базовая, Turbo Boost, динамическая), размер кэша, архитектура (например, NUMA). | Утилизация (user/system), время ожидания I/O (`iowait`), переключения контекста, неравномерная нагрузка на ядра, сложность определения 100% загрузки из-за динамической частоты. |
| **RAM (Память)** | Объем (GB), пропускная способность (GB/s, зависит от количества каналов, типа, частоты, поколения), задержки. | Нехватка доступной памяти, активный swapping (индикатор нехватки памяти, регулируется `swap-ness`), неоптимальное распределение памяти (например, слишком большой кэш). |
| **Disk (Диск)** | IOPS (операций ввода/вывода в секунду, зависит от типа I/O и размера блока), пропускная способность (MB/s, линейное чтение/запись), задержки (ms, особенно seek time для HDD), глубина очереди (Q-length). | Высокие задержки (seek time) на HDD (особенно для случайного I/O), исчерпание IOPS, переполнение очереди к диску, разница в производительности между HDD и NVMe. |
| **Network (Сеть)** | Пропускная способность (Gbps, до 400 Gbps в серверных средах), задержки (RTT, критичны между ЦОД и клиент-сервер), тип интерфейса (медь/оптика). | Утилизация канала, потери пакетов, высокие задержки до внешних сервисов, перегрузка (congestion), неэффективная обработка пакетов (без Smart NICs). |

**Программные ресурсы:** Существуют также лимиты на уровне ОС, которые могут стать узким местом:
*   Количество файловых дескрипторов (`ulimit`).
*   Количество доступных портов.
*   Размер пулов соединений.
*   Inodes в файловой системе.
*   Блокировки (mutexes, semaphores).

## 2. Методологии диагностики

Хаотичное использование знакомых утилит — неэффективный подход. Системная диагностика требует методологии.

### Анти-методы (чего следует избегать)

*   **Использование знакомого, а не нужного:** Запускать `top` по привычке, даже если проблема в диске.
*   **Случайный поиск в интернете:** Проблемы производительности слишком специфичны для общего запроса "у меня все тормозит".
*   **Тюнинг "всего подряд":** Изменение множества параметров одновременно без понимания их влияния.
*   **Обвинение "соседа":** Псилогическое желание свалить проблему на другой компонент системы (сеть, БД), не проведя диагностику на своей стороне.

### Методика формулирования проблемы

Прежде чем приступать к поиску решения, необходимо четко сформулировать проблему, ответив на следующие вопросы:

*   **Почему вы считаете, что есть проблема?** (Иногда проблемы нет или она находится вне вашей зоны ответственности).
*   **Когда система работала хорошо?** (Помогает определить временные рамки возникновения проблемы).
*   **Что изменилось недавно?** (Софт, железо, нагрузка, настройки, окружение, сезонные факторы).
*   **Можно ли выразить деградацию системы в терминах задержек (latency) или времени выполнения (runtime)?** (Необходимо иметь метрики для измерения улучшения).
*   **Затрагивает ли проблема других людей или приложения?** (Определить масштаб и критичность проблемы, а также затронутые компоненты архитектуры).
*   **Окружение:** В рамках чего существует проблема? (Версии приложений, ОС, конфигурации, аппаратные ресурсы — важно для воспроизведения в тестовой среде).

### Метод характеристики нагрузки

Помогает декомпозировать систему и понять характер нагрузки:

*   **Что порождает нагрузку?** (Конкретный PID, процесс, группа процессов, пользователь, IP-адрес).
*   **Откуда появилась нагрузка?** (Кто кого вызывает, "stack trace" вызовов внутри приложения и между компонентами).
*   **Что представляет собой нагрузка?** (IOPS, загрузка CPU, read/write операции, размер блоков).
*   **Как нагрузка изменяется во времени?** (Постоянная, волнообразная, пиковая, уже прошла).

### Методика USE (Utilization, Saturation, Errors)

Предложена Брэнданом Греггом. Для **каждого** ресурса системы проверяются три ключевых аспекта:

1.  **Utilization (Утилизация):** Процент времени, в течение которого ресурс был занят работой. Например, `%util` для диска или `100% - %idle` для CPU. Высокая утилизация — не всегда проблема, но это первый признак для дальнейшего анализа.
2.  **Saturation (Насыщение):** Наличие очереди к ресурсу. Указывает на то, что ресурс не справляется с потоком запросов, и они вынуждены ждать. Примеры: длина очереди к диску, Load Average для CPU. Насыщение — это всегда проблема производительности.
3.  **Errors (Ошибки):** Явные ошибки, связанные с работой ресурса. Например, ошибки ввода-вывода, отброшенные сетевые пакеты.

## 3. Базовые утилиты для быстрой диагностики

| Утилита | Назначение | Ключевые метрики |
| :--- | :--- | :--- |
| `uptime` | Общее состояние системы, время работы. | **Load Average (1, 5, 15 мин):** Среднее число процессов в очереди на исполнение (Run Queue) + в ожидании I/O. Показывает "насыщение" CPU и диска. Высокий Load Average может быть вызван медленными дисками. Позволяет оценить динамику нагрузки. |
| `free -h` | Состояние оперативной памяти. | `available` — реальный объем памяти, доступный приложениям. Большой объем кэша (`cache`) может быть сокращен при нехватке памяти. Использование `swap` само по себе не проблема, но активная запись/чтение в `swap` (см. `vmstat`) указывает на нехватку RAM. |
| `top` / `htop` | Динамический мониторинг процессов в реальном времени. | `%CPU` (пользовательская, системная, `iowait`), `%MEM`, состояние процессов (R - running, S - sleeping, D - uninterruptible sleep/disk I/O, Z - zombie). Позволяет увидеть потребление CPU однопоточными (макс. 100%) и многопоточными (более 100%) процессами. |
| `vmstat 1` | Статистика виртуальной памяти, I/O, CPU. | `si`/`so` (swap-in/swap-out) — показывает активную подкачку (признак нехватки RAM). `cs` (context switches) — переключения контекста, высокие значения могут указывать на накладные расходы CPU. `r` (runnable processes), `b` (blocked processes). |
| `iostat -xz 1` | Детальная статистика по дисковым устройствам. | `%util` (утилизация), `avgqu-sz` (средний размер очереди, показатель насыщения), `await` (среднее время ожидания I/O), `tps` (транзакций в секунду, т.е. IOPS). Позволяет оценить нагрузку на диск, но не по процессам. |
| `iotop` | Мониторинг дискового I/O **по процессам**. | Показывает, какой именно процесс активно читает/пишет на диск (в отличие от `top` и `iostat`). Позволяет сортировать по активности записи/чтения. |
| `mpstat -P ALL 1` | Статистика по каждому ядру/потоку CPU. | Позволяет выявить неравномерность нагрузки и определить, упирается ли однопоточный процесс в одно ядро, даже при низкой общей утилизации CPU. |
| `pidstat` | Статистика по отдельным процессам. | Показывает потребление CPU, памяти и I/O для конкретного процесса, включая номер ядра, на котором он работает. |
| `dstat` | Универсальный инструмент для мониторинга ресурсов. | Объединяет информацию из `vmstat`, `iostat`, `ifstat` и `netstat`, предоставляя обзор CPU, дисков, сети, памяти и процессов. |
| `sar` | Универсальный сборщик системной активности (CPU, память, диски, сеть и др.). | `sar -n DEV 1` для мониторинга сети (пакеты/байты в секунду, утилизация интерфейса). Может собирать исторические данные. |
| `atop` | Продвинутый монитор, который пишет историю. | Позволяет "отмотать" состояние системы назад во времени (записывает логи). Предоставляет обширные метрики по CPU (по ядрам), памяти, swap, дискам, сетевым интерфейсам и процессам в едином окне. |

### Linux PSI (Pressure Stall Information)

**Что такое PSI?**

PSI — это механизм ядра Linux, позволяющий отслеживать **давление (pressure)** на ключевые ресурсы: CPU, память и I/O. Он показывает, сколько времени процессы провели в ожидании этих ресурсов, что помогает выявить узкие места до того, как ситуация станет критичной (например, до вмешательства `oom-killer`).

PSI не измеряет загрузку напрямую — он измеряет **«stall time»** — сколько процессов одновременно не могли продолжить работу из-за нехватки ресурса. Это дает более реалистичную картину деградации системы, особенно в условиях высокой конкуренции за ресурсы.

**Как использовать для мониторинга?**

Проверка PSI осуществляется через псевдофайлы в `/proc/pressure/`:

```bash
# Давление на CPU
cat /proc/pressure/cpu

# Давление на память
cat /proc/pressure/memory

# Давление на I/O
cat /proc/pressure/io
```

**Пример вывода `/proc/pressure/cpu`:**

```
some avg10=0.00 avg60=0.00 avg300=0.00 total=0
full avg10=0.00 avg60=0.00 avg300=0.00 total=0
```

**Пояснения к выводу:**

*   `some`: Показывает время, в течение которого **хотя бы один** процесс испытывал задержку из-за нехватки ресурса.
*   `full`: Показывает время, в течение которого **все** активные процессы испытывали задержку из-за нехватки ресурса (т.е. система полностью "зависла" по этому ресурсу).
*   `avg10`, `avg60`, `avg300`: Среднее время задержки за последние 10, 60 и 300 секунд соответственно.
*   `total`: Общее накопленное время задержки с момента загрузки системы.

**Значение PSI:**

PSI позволяет увидеть, когда система начинает испытывать нехватку ресурсов, еще до того, как традиционные метрики (например, утилизация CPU) покажут 100%. Это критически важно для проактивного мониторинга и предотвращения сбоев. Например, высокий `full` PSI по памяти может указывать на скорое срабатывание `oom-killer`.

## 4. Углубленный анализ

Если базовые утилиты указали на компонент, можно использовать более мощные инструменты.

### Профилирование CPU с `perf`

`perf` — мощнейший инструмент для анализа производительности на уровне ядра и приложений, использующий счетчики в ядре. Для его работы могут потребоваться пакеты `linux-tools-generic` и `linux-tools-<версия_ядра>`.

*   `perf top`: Показывает, какие функции/символы (в ядре или приложениях) потребляют больше всего CPU в данный момент, с разбивкой по компонентам и библиотекам.
*   `perf record -p <PID> -g -- sleep 10`: Записывает профиль работы конкретного процесса со стеком вызовов (`-g` для трассировки стека), что позволяет строить Flame Graph.
*   `perf report`: Анализирует записанный профиль, представляя данные в виде дерева вызовов. При отсутствии символов может потребоваться установка отладочных символов (`debug symbols`).

Подробнее см. в **[Инструменты отладки и трассировки в Linux](./debugging_and_tracing_tools.md)**.

### Трассировка системных вызовов `strace`

Позволяет отследить, какие системные вызовы делает процесс. Полезно для понимания, чего процесс ждет (например, ответа от сети или чтения файла).

```bash
strace -p <PID>
```

### Анализ короткоживущих процессов

Иногда нагрузку создают процессы, которые запускаются и завершаются так быстро, что не видны в `top`.

*   `forkstat`: Утилита, которая эффективно отслеживает системные вызовы `fork`, `exec` и `exit`, показывая иерархию порождения процессов в реальном времени. Позволяет выявлять короткоживущие процессы, которые трудно заметить в `top`.
*   `execsnoop` (из bcc-tools): Использует eBPF для отслеживания только вызовов `exec`.
