# Утилита `witr`

## Определения

**`witr`** (Why Is That Running) — современная диагностическая утилита с открытым исходным кодом, написанная на Rust, предназначенная для быстрого выяснения причин запуска процессов в Linux. Она агрегирует данные из различных подсистем ядра и пространства пользователя, предоставляя единый отчет о «генеалогии» процесса, его сетевой активности и потенциальных рисках.

Утилита особенно эффективна в ситуациях, когда в системе обнаружен незнакомый процесс, и требуется мгновенно восстановить цепочку его запуска (запущен ли он интерактивно через SSH, является ли частью системного сервиса `systemd` или запущен планировщиком `cron`).

## Основные концепции

### Источники информации и механизмы

`witr` работает как интеллектуальный агрегатор, собирая данные из:
- **`procfs`** (`/proc`): считывает атрибуты процесса (стартовое время, рабочий каталог, переменные окружения, UID/GID) и его иерархию (PPID).
- **`cgroups` и `systemd`**: сопоставляет PID с контрольными группами через `/proc/[PID]/cgroup`. Это позволяет точно определить принадлежность процесса к `systemd`-юниту (service, scope, slice) или сессии пользователя.
- **Сетевой стек**: анализирует `/proc/net/` (аналог [`ss`](../Networking/ss.md)) для поиска прослушиваемых портов и активных соединений, привязанных к процессу.

### Определение systemd-юнита через cgroups

В современных дистрибутивах (Debian 9+, RHEL 7+, Ubuntu 16.04+) `systemd` использует cgroups v2 (unified hierarchy) для организации процессов. `witr` читает файлы `/proc/<PID>/cgroup`, чтобы сопоставить процесс с unit-файлом.

Для cgroups v2 путь обычно выглядит как:
```text
0::/system.slice/nginx.service
```
или для пользовательской сессии:
```text
0::/user.slice/user-1000.slice/user@1000.service/session-3.scope
```

На основе этого пути `witr` определяет:
- **Тип юнита**: `.service` (демон), `.scope` (сессия), `.slice` (группа), `.socket` (сокет-активируемый юнит).
- **Принадлежность к системе или пользователю**: префиксы `system.` и `user.`.
- **Владельца**: UID/GID из `/proc/<PID>/status`.

### Анализ цепочки запуска (Lineage)

В отличие от стандартного `pstree`, `witr` фокусируется на **логической ответственности**. Она прослеживает цепочку до PID 1 (обычно `systemd`) или лидера сессии, помогая отличить:
- **Интерактивные процессы**: цепочка ведет к `sshd` или эмулятору терминала.
- **Системные службы**: процесс находится внутри `.service` юнита.
- **Периферийные задачи**: дочерние процессы других приложений (например, воркеры Nginx или PHP-FPM).

Для построения lineage `witr` использует `/proc/<PID>/status` (поле `PPid`) и `/proc/<PID>/cmdline`, интерпретируя промежуточные процессы (например, `systemd` → `sshd` → `bash` → `python`).

### Автоматический аудит контекста

Утилита помечает потенциально аномальные характеристики процесса:
- **Public Listening**: процесс открыл сокет на `0.0.0.0` или `::`, что делает его доступным извне.
- **Root execution**: выполнение от суперпользователя (риск эскалации при компрометации).
- **Suspicious Path**: запуск из путей, часто используемых вредоносным ПО для обхода проверок (`/tmp`, `/dev/shm`, `/var/tmp`).

## Практические сценарии

### Установка

Утилита устанавливается через пакетный менеджер Rust.

```bash
# Установка через cargo
cargo install witr

# Принудительное обновление
cargo install --force witr
```

Репозиторий проекта: [github.com/pranshuparmar/witr](https://github.com/pranshuparmar/witr)

### Базовая диагностика процесса

```bash
# Анализ процесса по имени
witr nginx

# Анализ конкретного PID
witr --pid 1234
```

**Пример интерпретации отчета:**
```text
Target: /usr/bin/python3 (PID: 2100)
Why: Запущен пользователем 'admin' внутри SSH-сессии (sshd.service).
Listening: *:8080 (TCP)
Warnings:
  - Процесс слушает внешние интерфейсы (0.0.0.0).
  - Процесс запущен с правами Root.
```

### Поиск виновника занятого порта

Если необходимо быстро понять, какое приложение заняло порт и зачем оно запущено:

```bash
# Поиск по порту с полным контекстом запуска
witr --port 8080
```

### Расследование инцидентов (Incident Response)

Если в `top` обнаружен подозрительный процесс с высокой нагрузкой:
1. Выполните `witr --pid <PID>`.
2. Проверьте поле **Why It Exists**.
3. Если цепочка обрывается на `sshd` неизвестного пользователя — это признак взлома сессии.
4. Если процесс запущен из `/tmp`, изучите его окружение (клавиша `e` в `htop` или просмотр `/proc/[PID]/environ`).

### Анализ linger-процессов и systemd --user

В системах с `systemd` пользовательские службы, запущенные через `systemd --user`, могут продолжать работать после выхода из сессии, если включен linger (`loginctl enable-linger <user>`). `witr` позволяет определить, принадлежит ли процесс такой "фоновой" сессии:

```bash
# Найти процесс пользователя, не привязанный к активной сессии
witr --pid $(pgrep -u alice -P 1 | head -1)
```

Если в отчете unit будет вида `user@1000.service` без `session-N.scope` — это linger-процесс. Для управления используйте:
```bash
loginctl enable-linger alice   # разрешить
loginctl disable-linger alice  # запретить
```

### Интеграция с journalctl

После определения systemd-юнита через `witr` перейдите к анализу логов:

```bash
# Получить имя юнита из отчета witr, например nginx.service
journalctl -u nginx.service -n 100 --no-pager
```

Для отслеживания логов в реальном времени:
```bash
journalctl -u nginx.service -f
```

### Автоматизация и скриптовое использование

`witr` подходит для интеграции в скрипты аудита:

```bash
#!/bin/bash
# audit-listening.sh — найти все процессы, слушающие внешние порты
for pid in $(ss -tlnp | awk -F'pid=' '{print $2}' | tr -d ')' | sort -u); do
    witr --pid "$pid" 2>/dev/null | grep -E 'Target:|Listening:|Why:'
done
```

### Диагностика в контейнерах

Внутри контейнера `witr` видит только процессы текущего namespace. Для анализа хостового процесса из контейнера:

```bash
# На хосте: получить PID процесса контейнера
HOST_PID=$(docker inspect --format '{{.State.Pid}}' myapp)

# Анализ на хосте (вместо запуска внутри контейнера)
witr --pid "$HOST_PID"
```

Если контейнер использует `cgroups v2` с `--cgroupns=host`, `witr` корректно определит системный unit. При изолированном `cgroupns` unit будет отображаться как часть контейнера.

## Производительность и масштабирование

- **Нагрузка на `/proc`**: `witr` читает несколько файлов на один процесс (`status`, `cmdline`, `cgroup`, `fd`, `net/*`). На системах с >10k процессами это занимает заметное время. Используйте фильтры (`--pid`, `--port`, `--name`) для ограничения выборки.
- **DNS-резолвинг**: по умолчанию `witr` может пытаться резолвить IP-адреса. На больших системах или при отсутствии DNS это вызывает задержки. Добавьте флаг отключения DNS, если поддерживается, или настройте `/etc/nsswitch.conf`.
- **Конкурентный доступ**: параллельное чтение `/proc` из нескольких инстансов `witr` создает пиковую нагрузку на disk I/O при работе с медленным storage (например, NFS с `/proc` over network — редкий случай).

## Типичные ошибки и их решения

| Ошибка / симптом | Причина | Решение |
| :--- | :--- | :--- |
| Нет вывода для ожидаемого процесса | Процесс завершился; PID переиспользован | Использовать `pidfd` (Linux 5.3+) или `/proc/PID/starttime` для проверки. |
| `Permission denied` при чтении `/proc/<PID>/fd/` | Процесс принадлежит другому пользователю и включен `hidepid=2` | Запускать через `sudo`. |
| Отображается неправильный unit | Процесс в контейнере с изолированным cgroupns | Использовать `witr` на хосте, а не внутри контейнера. |
| Зависание на больших системах | DNS-резолвинг или зависшая ФС | Добавить флаг отключения DNS, ограничить фильтрами. |
| `witr: command not found` | Утилита не установлена или `$PATH` не включает `~/.cargo/bin` | Установить через `cargo install witr` или добавить путь в `.profile`. |

## Ограничения

- **Зависимость от метаданных ядра**: Если процесс использует техники маскировки (например, подмена `argv` или запуск через `memfd_create`), `witr` может отображать неполные данные.
- **Требования к привилегиям**: Для доступа к сетевой информации других пользователей и данным `/proc` требуется `sudo`.
- **В контейнерах**: видимость ограничена текущими namespaces и cgroupns.

## Сравнение с аналогами

| Инструмент | Преимущества | Когда выбирать |
| :--- | :--- | :--- |
| **`witr`** | Агрегированный отчет (Сеть + cgroups + Lineage) за один вызов. | Быстрый аудит незнакомых процессов и инцидентов. |
| [`ps`](./ps.md) | Стандарт, визуальное дерево. | Детальный статический анализ всех процессов. |
| [`lsof -i`](./lsof.md) | Глубокий аудит дескрипторов. | Анализ конкретных файлов и сокетов. |
| `pstree` | Легкость, визуализация иерархии. | Визуализация родительских связей. |
