# Поиск потока, потребляющего CPU внутри процесса

## Определения

*   **TID (Thread ID)** — уникальный идентификатор потока на уровне ядра Linux (также называется **LWP — Light Weight Process**). В рамках одного процесса (PID) каждый поток имеет свой TID.
*   **PID (Process ID)** — идентификатор основного процесса (лидера группы потоков).
*   **Call Graph (Граф вызовов)** — иерархическая структура вызовов функций, позволяющая отследить путь выполнения кода от точки входа до текущего состояния.
*   **Hot Spot** — участок кода (функция), в котором программа проводит большую часть времени при высокой нагрузке.

## Основные концепции

### Почему поток потребляет 100% CPU

Высокая нагрузка на конкретный поток обычно вызвана одной из следующих причин:
-   **Busy Loop (Бесконечный цикл):** ошибка логики, при которой поток выполняет пустые или повторяющиеся операции без пауз (`sleep` или ожидания событий).
-   **Spin-lock (Спин-блокировка):** поток постоянно опрашивает флаг блокировки вместо того, чтобы уйти в режим ожидания (Sleeping). Это эффективно для очень коротких задержек, но губительно при долгой конкуренции за ресурс.
-   **Активная обработка данных:** выполнение тяжелых математических вычислений, шифрования или компрессии.
-   **Lock Contention (Конкуренция за блокировки):** ситуация, когда множество потоков одновременно пытаются захватить одну блокировку (например, `mutex`), что приводит к деградации производительности (хотя в этом случае нагрузка может быть и в `system` CPU из-за работы планировщика).

## Практические сценарии

### Сценарий 1: Идентификация проблемного TID

Для поиска конкретного потока, перегружающего ядро CPU, можно использовать несколько инструментов.

#### Использование `top` (Режим Threads)
```bash
# Показать потоки конкретного процесса
top -H -p <PID>
```
Нажмите **`H`** в интерактивном режиме для переключения вида (столбец PID превратится в TID).

#### Использование `ps` (Статический снимок)
```bash
# Вывод всех потоков процесса с указанием потребления CPU и номера ядра (PSR)
ps -L -p <PID> -o pid,tid,psr,pcpu,comm
```

#### Использование `pidstat` (Интервальная статистика)
```bash
# Мониторинг нагрузки по потокам каждую секунду
pidstat -t -p <PID> 1
```

### Сценарий 2: Анализ активности в реальном времени (`strace`)

Если нужно быстро понять, не застрял ли поток на системных вызовах (например, бесконечные попытки чтения из сокета):

```bash
# Отслеживание системных вызовов конкретного TID
sudo strace -p <TID>
```
Если `strace` ничего не выводит, значит, поток выполняет код в пространстве пользователя (Userspace) и не обращается к ядру.

### Сценарий 3: Профилирование (`perf`)

Утилита `perf` позволяет точно определить «горячую» функцию в коде.

```bash
# 1. Запись профиля конкретного TID на 10 секунд с графом вызовов
sudo perf record -g -t <TID> sleep 10

# 2. Анализ отчета
sudo perf report --tid <TID>
```
В отчете ищите функции с максимальным значением **Overhead**. Используйте `Enter` для раскрытия стека вызовов.

### Сценарий 4: Анализ стека вызовов (`gdb`)

Если нужно «заморозить» поток и посмотреть, какую именно строку кода он выполняет.

#### Соответствие TID и потоков GDB
У `gdb` внутренняя нумерация потоков. Чтобы найти нужный:
```bash
sudo gdb -p <PID>
(gdb) info threads
```
Ищите строку `LWP <TID>`. Запомните внутренний ID (первый столбец).

#### Просмотр стека
```bash
# Переключение на поток
(gdb) thread <ID>

# Вывод стека вызовов
(gdb) bt

# Снятие стека всех потоков сразу (неинтерактивно)
sudo gdb -p <PID> -batch -ex "thread apply all bt" > stacks.txt
```

### Сценарий 5: Специфика Java-приложений

В Java TID из ОС соответствует полю `nid` (native id) в дампе потоков, но `nid` представлен в **шестнадцатеричном** формате.

1.  Найдите TID (десятичный) через `top -H`.
2.  Переведите TID в HEX: `printf '%x\n' <TID>`.
3.  Снимите дамп потоков: `jstack <PID> > jstack.txt`.
4.  Найдите в файле строку `nid=0x<HEX_TID>`.

## Дополнительная информация

### Ограничения
-   **Символы отладки:** Для эффективного использования `perf` и `gdb` исполняемые файлы должны содержать отладочную информацию (не быть «стрипнутыми») или иметь установленные `debug-info` пакеты.
-   **Безопасность:** Использование `ptrace` (необходимо для `gdb` и `strace`) может быть ограничено параметром `kernel.yama.ptrace_scope`.

### Сравнение методов

| Метод | Плюсы | Минусы |
| :--- | :--- | :--- |
| `top -H` | Мгновенно, без установки ПО. | Только цифры, без контекста кода. |
| `perf` | Минимальные накладные расходы. | Требует символы отладки. |
| `gdb` | Максимальная детализация (переменные). | Останавливает процесс (Stop-the-world). |
| `strace` | Показывает взаимодействие с ОС. | Высокие накладные расходы. |
