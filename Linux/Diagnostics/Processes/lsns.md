# Утилита `lsns`

## Определения

**`lsns`** (list namespaces) — системная утилита из пакета `util-linux`, предназначенная для считывания информации обо всех доступных пространствах имен (namespaces) в системе. Она предоставляет удобный древовидный или табличный вид, позволяя быстро определить границы изоляции процессов, сетевых интерфейсов и точек монтирования.

В отличие от ручного просмотра `/proc/[pid]/ns/`, `lsns` агрегирует данные, показывает количество процессов в каждом пространстве имен и позволяет фильтровать их по типам.

### Файловая система nsfs

Каждое пространство имён представлено в `/proc/<PID>/ns/` как символическая ссылка на объект `nsfs`. Inode-номера этих ссылок служат **уникальными идентификаторами** пространств имён. Утилита `lsns` считывает эти inode и строит по ним агрегированную таблицу.

```
# Пример:
# lrwxrwxrwx 1 root root 0 Sep  6 12:00 net -> 'net:[4026531840]'
```

Сравнение inode-номеров позволяет определить, разделяют ли процессы одно пространство имён:
```bash
readlink /proc/$PID1/ns/net
readlink /proc/$PID2/ns/net
```

## Основные концепции

### Механика работы

Утилита использует несколько механизмов для сбора данных:
1. **Сканирование `/proc`**: перебор всех запущенных процессов и чтение ссылок в их директориях `ns/`.
2. **`ioctl(2)`**: вызовы `NS_GET_USERNS`, `NS_GET_PARENT` и `NS_GET_NSTYPE` для определения иерархии и типов.
3. **`listns(2)` (Kernel 6.19+)**: современный системный вызов для атомарного получения списка всех пространств имен, что значительно быстрее сканирования `/proc` на высоконагруженных системах.

### Интерпретация вывода (Колонки)

При запуске без аргументов `lsns` выводит следующие ключевые поля:

| Столбец | Описание |
| :--- | :--- |
| **NS** | Идентификатор пространства имен (inode номер в `nsfs`). |
| **TYPE** | Тип пространства (mnt, net, pid, user, uts, ipc, cgroup, time). |
| **NPROCS** | Количество процессов, находящихся в данном пространстве. |
| **PID** | Идентификатор процесса с наименьшим PID в этом пространстве (обычно лидер/init). |
| **USER** | Владелец процесса, указанного в колонке PID. |
| **COMMAND** | Команда процесса, указанного в колонке PID. |

### Жизненный цикл и отсчёт ссылок

Пространство имён существует до тех пор, пока на него существует хотя бы одна ссылка:
- **Процессы**, находящиеся в пространстве имён.
- **Bind-mounts** файлов дескрипторов из `/proc/PID/ns/` (используется для персистентности, например в `ip netns`).
- **Дочерние пространства имён**, если родительское не уничтожено.

Когда счётчик ссылок достигает нуля, ядро освобождает пространство имён. `lsns` показывает только namespace, на которые есть хотя бы одна ссылка.

### Иерархия и родительские отношения

Для PID и User namespace существует иерархия. `lsns` с опцией `--tree` позволяет увидеть цепочку родительских пространств. Это критично при расследовании контейнерных инцидентов, когда нужно понять, к какому User Namespace относится подозрительный процесс.

### Режимы вывода

- **Табличный (по умолчанию)**: компактный вид с сортировкой по типу.
- **Древовидный (`--tree`)**: показывает вложенность namespace, особенно полезен для PID и User.
- **Список (`--list`)**: подробный вывод, похожий на `ls -l`.

### Полезные флаги

- **`-n`** (`--noheadings`): убрать заголовки (для скриптов).
- **`-J`** (`--json`): вывод в формате JSON для автоматизации и передачи в системы мониторинга.
- **`-l`** (`--list`): вывод в виде списка (по умолчанию).
- **`-o`** (`--output`): выбор конкретных колонок (см. `lsns --help` для полного списка).
- **`-t`** (`--type`): фильтрация по типу namespace (mnt, net, pid, user, uts, ipc, cgroup, time).
- **`-p`** (`--pid`): фильтрация по PID процесса.
- **`--tree`**: древовидный вывод с отображением иерархии.

## Практические сценарии

### Общий обзор и поиск аномалий

Позволяет увидеть все активные пространства имен и понять, какие из них созданы контейнерами или специализированными службами.

```bash
# Вывести все пространства имен в системе
sudo lsns

# Древовидный вид для PID namespace (видна иерархия)
sudo lsns -t pid --tree

# JSON-вывод для автоматизации
sudo lsns -J > /tmp/ns_snapshot.json
```

### Проверка конкретного процесса

Если подозрительный процесс ведет себя странно (не видит файлы или сеть), проверьте, в каких пространствах он находится.

```bash
# Показать все пространства имен, к которым принадлежит PID
lsns -p <PID>

# С parent-иерархией
lsns -p <PID> --tree
```

### Глубокая диагностика по типам

#### 1. PID Namespace: Изоляция дерева процессов
Полезно для поиска процессов, которые «спрятались» за новым корнем дерева.

```bash
# Вывод только PID namespaces с кастомными колонками
lsns -t pid -o NS,TYPE,NPROCS,PID,COMMAND
```
*Если `NPROCS` > 0, но вы не видите этих процессов в обычном `ps`, значит, они находятся в изолированном дереве.*

#### 2. Network Namespace: Сетевая изоляция
Позволяет обнаружить интерфейсы и маршруты, которые не видны в основном пространстве хоста (например, внутри Docker-контейнеров или `ip netns`).

```bash
# Список всех сетевых пространств имен
lsns -t net -o NS,NPROCS,PID,COMMAND
```

#### 3. Mount Namespace: Изоляция файловой системы
Критично для расследования проблем с монтированием (`target is busy`), «застрявших» контейнеров и процессов, удерживающих ФС.

```bash
# Анализ пространств монтирования
lsns -t mnt -o NS,NPROCS,PID,COMMAND
```

### Обнаружение «призрачных» пространств имен

Если пространство имен существует (закреплено через bind mount), но в нем нет активных процессов, `NPROCS` будет равен **0**. Это верный признак утечки или намеренного закрепления ресурсов (как это делает `ip netns`).

### Security Audit: проверка изоляции namespace

В рамках аудита безопасности проверяйте, что контейнеры и сервисы не имеют неожиданного доступа к пространствам имен хоста.

```bash
# 1. Получить список всех namespace с NPROCS=0 (возможно, забытые bind-mounts)
sudo lsns -o NS,TYPE,NPROCS,PID,COMMAND | awk '$3 == 0 && $2 != "time"'

# 2. Проверить, нет ли процессов пользователя, размещённых в User Namespace хоста
sudo lsns -t user -o NS,NPROCS,PID,COMMAND

# 3. Найти процессы, которые видят host PID namespace (ожидается только для root/systemd)
sudo lsns -t pid | grep -v '^[ ]*1[ ]*pid'
```

### Container Escape Prevention Audit

Проверка, что контейнерные процессы не имеют доступа к пространствам имен хоста:

```bash
# Для каждого контейнера (через cgroup или docker inspect)
# сравнить его namespace с namespace PID 1 хоста
HOST_PID_NS=$(readlink /proc/1/ns/pid)
for pid in $(pgrep -f 'docker|containerd'); do
  CONT_PID_NS=$(readlink /proc/$pid/ns/pid)
  if [ "$HOST_PID_NS" = "$CONT_PID_NS" ]; then
    echo "WARNING: PID $pid shares host PID namespace"
  fi
done
```

### Валидация изоляции systemd-сервисов

Systemd может создавать изолированные namespace для сервисов. Проверка:

```bash
# Найти MainPID сервиса
PID=$(systemctl show --property=MainPID --value my-app)

# Проверить, что сервис получил отдельные namespace
sudo lsns -p $PID -o NS,TYPE,NPROCS,PID,COMMAND

# Ожидается: утилита должна показать отдельные записи для mnt, net, ipc и т.д.
# с NPROCS=1 и COMMAND=my-app
```

### Pre/Post Deploy namespace snapshot

Сравнение namespace до и после деплоя помогает обнаружить утечки:

```bash
# До деплоя
sudo lsns -J > /tmp/ns_before.json

# ... deploy ...

# После деплоя
sudo lsns -J > /tmp/ns_after.json

# Различия (требуется jq)
jq -r '.[] | [.ns, .type, .nprocs] | @tsv' /tmp/ns_before.json | sort > /tmp/ns_before.txt
jq -r '.[] | [.ns, .type, .nprocs] | @tsv' /tmp/ns_after.json | sort > /tmp/ns_after.txt
diff /tmp/ns_before.txt /tmp/ns_after.txt
```

### Automated monitoring via JSON batch mode

Для систем мониторинга используйте JSON-вывод:

```bash
# Собрать снапшот и извлечь namespace с аномально высокой нагрузкой
sudo lsns -J | jq -r '.[] | select(.nprocs > 100) | "\(.type) \(.ns) \(.nprocs) \(.command)"'
```

### Audit hidepid и доступность процессов

При настроенном `hidepid=2` на `/proc`, `lsns` всё ещё видит все namespace, так как читает их напрямую через ioctl, а не через сканирование `/proc` другими пользователями.

```bash
# Проверка: даже с hidepid=2 утилита показывает полную картину
sudo lsns -t pid -o NS,TYPE,NPROCS,PID,COMMAND
```

### Диагностика при "зависших" монтированиях

Если `umount` возвращает `target is busy`, используйте `lsns` для обнаружения процессов в монтируемом namespace:

```bash
# Найти Mount Namespace, держащий точку монтирования
MOUNT_POINT=/data
TARGET_DEV=$(findmnt -n -o SOURCE $MOUNT_POINT)

# Найти PID через mountinfo
for pid in /proc/[0-9]*; do
  if grep -q "$TARGET_DEV" $pid/mountinfo 2>/dev/null; then
    echo "PID $pid holds mount"
    lsns -p ${pid#/proc/} -t mnt
  fi
done
```

## Кейс: От «границы» к «внутренностям»

Часто процесс выглядит «обычным» в `ps` на хосте, но его ресурсы изолированы. Алгоритм диагностики:

1. **Обнаружение**: Используем `lsns`, чтобы увидеть границы (NS ID) и лидера пространства.
2. **Вход**: Используем `nsenter` для выполнения команд внутри этого окружения.

```bash
# 1. Находим NS ID сетевого пространства для подозрительного PID
NS_ID=$(lsns -p <PID> -t net -n -o NS)

# 2. Смотрим таблицу маршрутизации ИМЕННО этого пространства
sudo nsenter -t <PID> -n ip route show
```

## Валидация и верификация

### Cross-check с /proc и ps

Всегда проверяйте вывод `lsns` через независимые источники:

```bash
# Сравнение PID namespace
lsns -t pid -o NS,PID,COMMAND | head
ps -eo pid,comm | head

# Верификация network namespace
lsns -t net -o NS,PID,COMMAND | head
ls -l /proc/$(pgrep -n sshd)/ns/net
```

### Верификация иерархии через nsenter

```bash
# Проверка, что процесс действительно в указанном namespace
PID=1234
lsns -p $PID -t net -o NS
# → net:[4026531840]

# Подтверждение через /proc
readlink /proc/$PID/ns/net
# → net:[4026531840]
```

## Best Practices

1. **Используйте `lsns` как первый инструмент интроспекции:** Он даёт общую картину быстрее, чем ручной обход `/proc/*/ns/`.
2. **Сочетайте с `nsenter`:** `lsns` показывает границы, `nsenter` позволяет внутри них работать.
3. **Используйте JSON-вывод для автоматизации:** `lsns -J` удобно парсить в Python/Go/bash.
4. **Мониторьте NPROCS=0:** Появление «призрачных» namespace может указывать на утечки bind-mount.
5. **Проверяйте иерархию в security audit:** Особенно User Namespace — он определяет, какой UID маппинг используется.
6. **Не полагайтесь только на `lsns`:** Он показывает snapshot. Для динамики используйте `pidstat`, `ps` или `top`.
7. **Используйте `--tree` для сложных сред:** В LXC или системах с несколькими уровнями вложенности namespace помогает понять границы контейнера/сервиса.
8. **Ведите baseline:** Сохраняйте `lsns -J` снапшоты в changelog/deploy-пайплайнах для детектирования аномалий.

## Ограничения и граничные случаи

1. **Требует root для полного обзора:** Без привилегий `lsns` покажет только namespace текущего пользователя.
2. **Snapshot, не история:** Утилита не записывает события создания/удаления namespace. Для аудита используйте `auditd` с правилами на `clone`/`unshare`/`setns`.
3. **Kernel 6.19+ для listns(2):** На старых ядрах утилита полагается на сканирование `/proc`, что медленно на системах с >10k процессов.
4. **Не показывает содержимое namespace:** Только метаданные. Для деталей используйте `nsenter`.
5. **Time Namespace:** В старых версиях `util-linux` тип `time` может отсутствовать в выводе.
6. **PID reuse:** После завершения процесса его PID может быть переиспользован, и `lsns -p <PID>` покажет другой namespace.
7. **Cgroup v2:** В cgroup v2 иерархия cgroup namespace может отличаться от ожидаемой; `lsns` показывает только видимость, а не лимиты.

## Сравнение с аналогами

| Инструмент | Преимущества | Когда выбирать |
| :--- | :--- | :--- |
| **`lsns`** | Табличный вид, агрегация по NS ID, подсчет процессов, JSON-вывод. | Поиск неожиданных пространств, обзор системы, аудит. |
| `ls -l /proc/PID/ns` | Доступно без установки доп. утилит. | Быстрая проверка одного процесса. |
| `ip netns list` | Работает с именованными пространствами `iproute2`. | Управление сетевыми стеками. |
| [`ps -eo ns`](./ps.md) | Позволяет фильтровать процессы по NS ID напрямую. | Массовый поиск процессов в конкретном NS. |
| [`nsenter`](./nsenter.md) | Вход в namespace для выполнения команд. | Глубокая диагностика после обнаружения через `lsns`. |
