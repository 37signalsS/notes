# Утилита `htop`

## Определения

**`htop`** — интерактивный системный монитор процессов с текстовым интерфейсом (TUI), являющийся современной и расширенной альтернативой классической утилите [`top`](./top.md).

**Ключевые преимущества:**
- **Наглядность:** Графические шкалы и детальная цветовая кодировка ресурсов.
- **Интерактивность:** Полная поддержка прокрутки, поиска и управления мышью.
- **Функциональность:** Управление сигналами, приоритетами (nice/ionice), аудит процессов (файлы, переменные окружения, системные вызовы) без выхода из программы.

## Основные концепции

### Архитектура и источники данных

`htop` агрегирует данные напрямую из виртуальной файловой системы `/proc` и, при необходимости, из `/sys`. В отличие от `top`, который полагается на системные вызовы `getrusage()` и `wait4()`, `htop` опрашивает `/proc/<pid>/stat`, `/proc/<pid>/status`, `/proc/<pid>/smaps_rollup` и другие файлы, что даёт более детальную и своевременную картину, особенно для многопоточных приложений.

**Жизненный цикл обновления:**
1. Чтение snapshot'а `/proc` (все процессы за один момент).
2. Агрегация метрик (CPU, память, I/O, PSI).
3. Отрисовка интерфейса с учётом настроек meters и сортировки.
4. Ожидание интервала `-d` и повтор.

### Структура интерфейса

`htop` предоставляет три функциональные области: заголовок с индикаторами, таблицу процессов и панель действий.

#### Верхняя панель (Индикаторы)
Отображает текущую нагрузку. Цветовая легенда (по умолчанию):

- **ЦП (CPU)**:
  - **Синий**: процессы с низким приоритетом (`nice > 0`).
  - **Зеленый**: пользовательские процессы (нормальный приоритет).
  - **Красный**: системные процессы (ядро).
  - **Оранжевый**: время ожидания ввода-вывода (IO wait).
  - **Аквамариновый**: виртуализация (Steal time).

- **Память (Mem)**:
  - **Зеленый**: занято процессами (Resident Memory).
  - **Синий**: буферы (Buffers).
  - **Желтый/Оранжевый**: кэш страниц (Cache).

- **Swap**:
  - Отображает использование подкачки. Рост Swap при наличии свободной RAM указывает наMemory pressure или агрессивный `vm.swappiness`.

#### Режимы отображения CPU (Irix vs Solaris)

Нажатие **`I`** (Shift+i) переключает режим расчета `%CPU`:
- **Irix mode (по умолчанию в htop):** 100% = одно ядро. На 32-ядерном сервере суммарный `%CPU` может достигать 3200%.
- **Solaris mode:** 100% = все ядра. Суммарный `%CPU` никогда не превышает 100% × количество ядер, но сравнение процессов между собой становится менее интуитивным.

**Практическое значение:** Для быстрого определения «пожирателя» CPU используйте Irix mode. Для оценки общей утилизации системы — Solaris mode.

#### Индикаторы давления (PSI — Pressure Stall Information)
В современных версиях (3.0+) доступны метрики PSI, показывающие процент времени, в течение которого процессы ожидали ресурсов (CPU, Memory, I/O) за последние 10, 60 и 300 секунд.
- **`some`**: хотя бы одна задача заблокирована.
- **`full`**: все задачи в cgroup/системе заблокированы (только для RAM и I/O).

Настройка: `F2` -> `Meters` -> перетащить `Pressure Stall Information`.

Подробнее о PSI: [Pressure Stall Information (PSI)](../../Core/kernel/psi.md).

#### Meters (Индикаторы)
Каждый индикатор в верхней панели называется «meter». Доступные типы:
- **Text:** Простой текст (например, «CPU[####....] 50%»).
- **Bar:** Графическая шкала.
- **Graph:** Мини-график за последние интервалы (полезно для трендов).
- **LED:** Маленькие цветные квадраты (полезно для компактного отображения).

Настройка: `F2` -> `Meters` -> `F6` (Add) / `F7` (Up) / `F8` (Down) / `F9` (Remove).

#### Список процессов
Таблица поддерживает горизонтальную прокрутку, позволяя просматривать полные пути команд и аргументы. Столбец `S` (Status) соответствует состояниям процесса в Linux (`R`, `S`, `D`, `Z`, `T`).

Подробнее о состояниях процессов: [Практические сценарии мониторинга процессов](../../Core/processes/practical_scenarios.md).

## Практические сценарии

### Основные режимы запуска

```bash
# Базовый запуск
htop

# Запуск с фильтром по пользователю
htop -u username

# Мониторинг конкретных PID
htop -p 1234,5678

# Установка интервала обновления в десятых долях секунды
htop -d 10 # → обновление раз в 1 секунду

# Запуск в черно-белом режиме (для старых терминалов)
htop -C

# Запуск с отключенным mouse (для удалённых сессий без мыши)
htop --no-mouse
```

### Пакетный режим (Batch mode)

Для автоматизации и сбора снапшотов используется флаг `-b`. В этом режиме `htop` выводит текстовый поток, аналогичный `top -b`, но с дополнительными столбцами и без интерактивных управляющих последовательностей.

```bash
# Одиночный снапшот (аналог top -n 1)
htop -b -n 1

# Снапшот с сортировкой по памяти
htop -b -n 1 -o +%MEM | head -n 20

# Сбор 5 снапшотов с интервалом 2 секунды
htop -b -n 5 -d 20

# Фильтрация по пользователю и сохранение в лог
htop -b -n 1 -u www-data > /tmp/www_snapshot_$(date +%Y%m%d_%H%M%S).txt

# Отслеживание роста памяти конкретного процесса
htop -b -d 5 -p 1234 | grep -E '^[0-9]+' >> /tmp/pid_1234_mem.log
```

**Валидация:** Сравните вывод `htop -b` с `ps` или `pidstat` для подтверждения согласованности данных. Подробнее: [Валидация и верификация](#валидация-и-верификация).

### Интерактивные команды (Горячие клавиши)

#### Навигация и вид
| Клавиша | Действие |
| :--- | :--- |
| **`F5`** / **`t`** | Древовидный режим (Tree view) — иерархия родитель/потомок. |
| **`H`** | Скрыть/показать пользовательские потоки (Threads). |
| **`K`** | Скрыть/показать потоки ядра (Kernel Threads). |
| **`F2`** / **`S`** | Меню настроек (Setup): цвета, столбцы, индикаторы, экраны. |
| **`F10`** / **`q`** | Выход из программы. |
| **`I`** | Переключение режима CPU (Irix/Solaris). |
| **`T`** | Сортировка по времени (TIME). |
| **`P`** | Сортировка по CPU (`%CPU`). |
| **`M`** | Сортировка по памяти (`%MEM`). |
| **`>`** / **`<`** | Сдвиг столбцов сортировки вправо/влево. |

#### Поиск и фильтрация
| Клавиша | Действие |
| :--- | :--- |
| **`F3`** / **`/`** | Поиск процесса по имени (переход к следующему). |
| **`F4`** / **`\`** | **Интерактивный фильтр**: оставляет на экране только подходящие процессы. |
| **`u`** | Фильтр по владельцу процесса. |

#### Управление и аудит
| Клавиша | Действие |
| :--- | :--- |
| **`F9`** / **`k`** | Отправить сигнал (Kill menu). |
| **`F7`** / **`F8`** | Изменение приоритета (`nice`). |
| **`i`** | Настройка приоритета I/O (**ionice**). |
| **`e`** | Просмотр переменных окружения процесса. |
| **`l`** | Список открытых файлов процесса через [`lsof`](./lsof.md). |
| **`s`** | Трассировка системных вызовов через `strace`. |
| **`a`** | Установка **CPU Affinity** (привязка к ядрам). |
| **`L`** | Трассировка библиотечных вызовов через `ltrace`. |

Подробнее об управлении приоритетами: [Планирование процессов](../../Core/processes/scheduling.md), [ionice](./../Filesystem/ionice.md).

### Сценарии для SRE / DevOps / Sysadmin

#### Сценарий 1: Быстрая оценка системы (Rapid Assessment)

При поступлении алерта выполните последовательный осмотр:

```bash
# 1. Запустите htop с деревом процессов для визуальной оценки иерархии
htop

# 2. Оцените Load Average через верхнюю панель или нажмите F2 -> Meters -> Load Average

# 3. Сортируйте по CPU (P) и Memory (M) для выявления лидеров
# 4. Проверьте статус D/Z через столбец S
```

Для структурированной методологии Rapid Assessment см. [Быстрая диагностика сервера](../Troubleshooting/rapid_assessment.md).

#### Сценарий 2: Диагностика Load Average и инцидентов

Высокий LA при низком `%CPU` usu часто указывает на процессы в D-state или ожидание I/O:

```bash
# 1. Запустите htop и отсортируйте по CPU (P)
# 2. Нажмите F6 и выберите столбец S (Status) для группировки
# 3. Ищите процессы в состоянии D (Uninterruptible Sleep)
# 4. Для таких процессов нажмите 's' (strace) или 'l' (lsof) для аудита

# Параллельно проверяйте PSI:
# F2 -> Meters -> Pressure Stall Information -> I/O
# Если full avg10 > 5% — система «голодает» по дискам
```

Подробнее о D-state: [Невидимый I/O и D-state](../../Diagnostics/Performance/DiskIO/invisible_io.md).

#### Сценарий 3: Аудит безопасности процессов

Поиск подозрительных процессов, неавторизованных бинарников и аномальных родителей:

```bash
# 1. Запустите древовидный режим (F5) и отсортируйте по пользователю (u)
# 2. Ищите процессы с неожиданными родителями (python внутри httpd)
# 3. Проверьте пути команд: нажмите F2 -> Columns -> Command
# 4. Для подозрительного PID: 'e' (env), 'l' (lsof), 's' (strace)

# Обнаружение процессов, скрытых от обычного пользователя:
# Если /proc смонтирован с hidepid=2, htop покажет только собственные процессы
# Переключитесь на root для полной видимости
```

Подробнее о hidepid: [Виртуальная файловая система /proc](../../FileSystems/virtual_fs_proc.md).

#### Сценарий 4: Автоматизированные снапшоты (Pre/Post Deploy)

Фиксация состояния системы до и после деплоя для сравнения:

```bash
#!/bin/bash
# pre_deploy_snapshot.sh
SNAP_DIR="/var/log/deploy_snapshots"
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
mkdir -p "$SNAP_DIR"

# Снапшот CPU/Memory
htop -b -n 1 -o +%CPU | head -n 15 > "$SNAP_DIR/cpu_$TIMESTAMP.txt"
htop -b -n 1 -o +%MEM | head -n 15 > "$SNAP_DIR/mem_$TIMESTAMP.txt"

# Снапшот процессов
ps -eo pid,ppid,stat,%cpu,%mem,comm --sort=-%cpu > "$SNAP_DIR/ps_cpu_$TIMESTAMP.txt"
ps -eo pid,ppid,stat,%cpu,%mem,comm --sort=-rss > "$SNAP_DIR/ps_mem_$TIMESTAMP.txt"

echo "Snapshot saved to $SNAP_DIR"
```

После деплоя повторите и сравните:
```bash
diff -u "$SNAP_DIR/cpu_before.txt" "$SNAP_DIR/cpu_after.txt" | less
```

#### Сценарий 5: Обнаружение утечек памяти

Мониторинг роста RSS конкретного процесса в реальном времени:

```bash
# 1. Запустите htop и найдите процесс с растущим RES
# 2. Нажмите F6 -> RES -> Enter для сортировки по Resident Memory
# 3. Отмечайте значения вручную или используйте pidstat для автоматизации:

# Автоматическое логирование роста памяти
pidstat -r -p <PID> 60 > /tmp/mem_leak_$(date +%Y%m%d).csv

# Или через htop batch:
watch -n 60 'htop -b -n 1 -p <PID> | grep -E "^[0-9]+"'
```

Подробнее о метриках памяти: [Метрики потребления памяти процесса](../../Core/memory/process_memory_metrics.md).

#### Сценарий 6: Мониторинг в tmux/screen сессиях

Для долгоживущих мониторинговых сессий на production-серверах:

```bash
# Запуск htop в tmux с автономным режимом
tmux new-session -d -s monitor 'htop --no-mouse'

# Присоединение для просмотра
tmux attach -t monitor

# Отсоединение без остановки (Ctrl+B, D)
# Отправка команды в фон: tmux send-keys -t monitor '' C-c
```

Для `screen`:
```bash
screen -dmS monitor htop --no-mouse
screen -r monitor
```

**Рекомендация:** Используйте `htop -d 5` для снижения нагрузки на CPU при долгих сессиях.

#### Сценарий 7: Валидация после деплоя

Проверка, что новый релиз не вызывает аномалий:

```bash
# 1. Зафиксируйте baseline до деплоя (см. Сценарий 4)
# 2. После деплоя запустите:
htop -b -n 1 -o +%CPU | head -n 10 > /tmp/post_deploy_cpu.txt
htop -b -n 1 -o +%MEM | head -n 10 > /tmp/post_deploy_mem.txt

# 3. Проверьте количество процессов и тредов:
ps -eo nlwp,comm --sort=-nlwp | head -n 10

# 4. Проверьте отсутствие зомби:
htop -b -n 1 | grep -c ' Z '

# 5. Сравните с baseline
```

### Диагностика производительности

#### Анализ многопоточных приложений
Для приложений на Java, Go или Python (с потоками) общее потребление CPU может превышать 100% (до `количество_ядер * 100%`). Нажмите **`H`**, чтобы увидеть каждый поток отдельно и выявить, какой именно из них вызывает нагрузку. Подробнее: [Поиск проблемного потока](./thread_cpu_troubleshooting.md).

#### Мониторинг контейнеров
В современных дистрибутивах `htop` умеет отображать столбец `CONTAINER` или `CTID`, что позволяет идентифицировать процессы внутри Docker/LXC.
Настройка: `F2` -> `Columns` -> добавить `CONTAINER`.

Для анализа cgroup-лимитов используйте: [systemd-cgtop](../../Core/systemd/cgtop.md).

## Дополнительная информация

### Конфигурация
Настройки `htop` сохраняются в текстовом файле:
- **`~/.config/htop/htoprc`** (или `/etc/htoprc` для системных настроек).
Это позволяет переносить настроенный интерфейс (цвета, столбцы) между серверами.

### Вкладки и Экраны (Screens)
В версии 3.0+ реализована поддержка нескольких экранов. Вы можете настроить один экран для мониторинга CPU, а другой — для детального анализа памяти, переключаясь между ними клавишами `Tab` или `Shift+Tab`.
Настройка: `F2` -> `Screens`.

### Валидация и верификация

Для подтверждения корректности данных `htop` сравнивайте вывод с независимыми источниками:

```bash
# 1. Сравнение лидеров по CPU
htop -b -n 1 -o +%CPU | head -n 10
ps -eo pid,%cpu,comm --sort=-%cpu | head -n 10

# 2. Сравнение лидеров по памяти
htop -b -n 1 -o +%MEM | head -n 10
ps -eo pid,%mem,rss,comm --sort=-rss | head -n 10

# 3. Проверка точности %CPU (Irix vs Solaris mode)
# В Solaris mode сумма всех %CPU <= 100 * N_CPU
# В Irix mode сумма может превышать 100 * N_CPU на процессы в очереди

# 4. Верификация PSI
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
# Сравните с индикаторами в верхней панели htop
```

### Безопасность и ограничения
- **Hidepid**: Если `/proc` смонтирован с опцией `hidepid=2`, `htop` от обычного пользователя не увидит чужие процессы. Подробнее: [Виртуальная файловая система /proc](../../FileSystems/virtual_fs_proc.md).
- **Оверхед**: На системах с 1000+ ядер и огромным количеством процессов сам процесс `htop` может потреблять значительные ресурсы. В таких случаях рекомендуется увеличить интервал обновления (`-d`) или использовать `pidstat`/`ps` для снапшотов.
- **GPU**: Мониторинг NVIDIA/AMD GPU доступен только в сборках с поддержкой соответствующих библиотек (проверьте наличие индикаторов в `F2` -> `Meters`).
- **strace/ltrace overhead:** Трассировка процессов через `s` или `L` в `htop` вызывает значительные накладные расходы. Используйте только для кратковременной диагностики, но не для долгого мониторинга.
- **Permissions:** Просмотр переменных окружения (`e`), открытых файлов (`l`) и трассировка (`s`, `L`) требуют прав владельца процесса или `root`.

### Рекомендации и очистка (Best Practices)

1. **Используйте `htop` для интерактивной работы, `top` для скриптов:** `htop` удобнее, но часто отсутствует в минимальных образах. Для автоматизации применяйте `htop -b` или fallback на `ps`/`pidstat`.
2. **Настройте интервал под задачу:** 0.5–1 секунда для reactive-мониторинга, 5–10 секунд для trend-анализа, чтобы снизить overhead.
3. **Комбинируйте с `pidstat` для исторических данных:** `htop` — snapshot/realtime, `pidstat` — история с интервалами.
4. **Используйте древовидный режим для fork-серверов:** Apache, PHP-FPM, Nginx worker — нажмите `F5` для визуализации иерархии.
5. **Не оставляйте `htop` в production tmux на месяцы:** Он потребляет ресурсы. Для долгосрочного мониторинга используйте `atop` с логами или внешние системы мониторинга.
6. **Структурируйте настройки:** Экспортируйте `~/.config/htop/htoprc` в репозиторий конфигураций для воспроизводимости окружения.

### Ограничения и крайние случаи

- **Очень большое количество процессов (>5000):** Навигация и обновление интерфейса замедляются. Используйте фильтр `F4` или переключитесь на `ps` с сортировкой.
- **GUI-сессии и мышь:** Поддержка мыши работает только в совместимых терминалах (xterm, gnome-terminal, iTerm2). В консолях Linux (tty) или через ssh без X11 forwarding мышь не доступна. Используйте `--no-mouse`.
- **Контейнеры и cgroups:** `htop` внутри контейнера показывает только процессы этого контейнера (cgroup v2). С хоста используйте `ps` с фильтром по cgroup или `systemd-cgtop` для кросс-контейнерного анализа.
- **PID reuse:** После завершения процесса PID может быть переиспользован. При долгих мониторинговых сессиях сверяйте также command line (`ps -o cmd`) или время старта (`ps -o lstart`).
- **strace/ptrace ограничения:** Если `kernel.yama.ptrace_scope=2` (по умолчанию в современных Ubuntu), прикрепление `strace` к процессу другого пользователя запрещено. Используйте `sudo` или настройте `ptrace_scope`.
- **Терминальный эмулятор:** При использовании `tmux`/`screen` через медленный сетевой канал (высокий ping, потери пакетов) интерфейс `htop` может «замирать». Увеличьте интервал (`-d 20`) или используйте `mosh` вместо `ssh`.

| [`top`](./top.md) | Стандарт POSIX, всегда в наличии. | Минимальные системы, скрипты. |
| [`atop`](../Performance/atop.md) | Запись истории на диск. | Анализ инцидентов в прошлом. |
| **`btop`** | Исключительная визуализация и графики. | Мощные рабочие станции, современный UI. |
| [`pidstat`](./pidstat.md) | Таймсериес, итерации, per-CPU. | `sar`-подобный сбор, мониторинг через cron. |
| [`syswatch`](../Performance/syswatch.md) | Автоматические подсказки. | Быстрый поиск аномалий. |
| [`ps`](./ps.md) | Статический снапшот, фильтры. | Скрипты, однократные выборки. |
