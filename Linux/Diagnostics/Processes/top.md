# Утилита `top`

## Определения

**`top`** — классическая консольная утилита для динамического мониторинга процессов и системных ресурсов в реальном времени. Входит в пакет `procps-ng` и является стандартом де-факто для первичной диагностики производительности Linux-систем.

**Ключевые особенности:**
- **Низкие накладные расходы:** Потребляет минимум ресурсов CPU и RAM.
- **Интерактивность:** Позволяет менять формат отображения, фильтровать и завершать процессы без перезапуска.
- **Пакетный режим:** Поддержка вывода данных для последующего парсинга или логирования.

## Основные концепции

Интерфейс `top` состоит из двух логических блоков: **сводная информация** (верхняя панель) и **таблица процессов**. Данные обновляются автоматически каждые 3 секунды (интервал по умолчанию).

### Сводная информация (Заголовок)

#### Системное время и средняя нагрузка (Uptime & Load Average)
```text
top - 10:20:05 up 12 days,  4:15,  2 users,  load average: 0.15, 0.25, 0.10
```
- **`load average`**: среднее количество процессов в очереди на выполнение (состояния R и D) за последние 1, 5 и 15 минут.
    - **Интерпретация на многоядерных системах**: Значение 1.0 на 4-ядерной системе означает 25% загрузки.
    - **Нормализованный LA (Normalized Load Average)**: значение LA, делённое на число ядер CPU. Удобно для сравнения машин разного размера: нормализованный LA ≈ 1.0 означает полную загрузку узла независимо от количества ядер. Нормализованный LA в 3–5 при продолжающейся работе сервиса — почти всегда признак застревания задач в D-state, а не реальной очереди к процессору (см. «Аномалии» ниже).
    - **Влияние I/O и Сети**: В Linux (в отличие от BSD) в LA включаются процессы в состоянии **D** (Uninterruptible Sleep). Это означает, что высокий LA может быть вызван не только CPU, но и дисковыми задержками или проблемами с сетевыми файловыми системами (например, зависшая **NFS-шара**).
    - **Аномалии**: Возможно высокое значение LA (например, 20 на 4 ядрах) при нормальной работе сервиса, если процессы «залипли» в ожидании ввода-вывода.
    - Подробнее: [Интерпретация Load Average](../../Core/processes/scheduling.md#интерпретация-load-average).

#### Состояния задач (Tasks)
Отображает распределение процессов по жизненному циклу.
- **`total`**: общее количество задач.
- **`running`**: процессы в состоянии **R** (выполняются или готовы).
- **`sleeping`**: процессы в состояниях **S** (прерываемый сон) или **D** (непрерываемый сон).
- **`stopped`**: остановленные задачи (**T**).
- **`zombie`**: «зомби» (**Z**), процессы, которые фактически не потребляют ресурсов (кроме записи в таблице идентификаторов PID), так как завершились, но их родитель еще не считал код выхода. Если таблица PID забьется зомби-процессами, создание новых процессов станет невозможным.

#### Состояния CPU (Cpu(s))
Метрики показывают, на что тратится процессорное время (в %):
- **`us`** (user): время выполнения кода в пространстве пользователя (библиотеки, прикладное ПО).
- **`sy`** (system): время выполнения кода ядра (системные вызовы, драйверы).
    - **Водораздел**: Граница проходит по системным вызовам (syscalls). Код ядра (`sy`) запускается только в ответ на запрос приложения или аппаратное прерывание.
- **`ni`** (nice): время процессов с изменённым приоритетом.
- **`id`** (idle): время простоя.
- **`wa`** (iowait): время ожидания завершения дискового или сетевого I/O. Процессор в это время простаивает, но не может переключиться на другие задачи из-за ожидания данных.
- **`hi`** (hardware irq): время обработки аппаратных прерываний (запросы напрямую от железа).
- **`si`** (software irq): время обработки программных прерываний (например, обработка сетевых пакетов после их приема сетевой картой).
- **`st`** (steal): время, «украденное» гипервизором у виртуальной машины. Значения >5% критичны для производительности.

#### Оперативная память и Swap (Mem & Swap)
Интерактивные клавиши **`E`** (в сводке) и **`e`** (в таблице) позволяют менять масштаб отображения (KiB, MiB, GiB, TiB, PiB, EiB).
- **`total`**: физическая память.
- **`free`**: абсолютно неиспользуемая память.
- **`used`**: память, занятая приложениями.
- **`buff/cache`**: временные данные для ускорения I/O.
- **`avail Mem`**: реальный объем памяти, который можно выделить новому приложению.
    - **Важно**: `avail Mem` всегда меньше, чем `free + buff/cache`, так как часть кэша (например, кэш ядра, Slab) является невыгружаемой (non-evictable) и необходима для работы системы.

### Таблица процессов

| Столбец | Описание |
| :--- | :--- |
| **PID** | Идентификатор процесса. В системе может быть несколько процессов с одинаковым PID, если они находятся в разных **PID Namespaces** (основа контейнеризации). |
| **USER** | Эффективный владелец процесса. |
| **PR** / **NI** | **PR** — реальный приоритет в ядре. Значение `rt` указывает на Real-Time политику. **NI** — пользовательская поправка (nice). Две колонки нужны, так как ядро может динамически менять `PR` в зависимости от поведения процесса, в то время как `NI` остается статичным. |
| **VIRT** | Объем виртуальной памяти, который процесс *запросил* (может значительно превышать RAM). |
| **RES** | Резидентная память — сколько физической RAM процесс занимает *на самом деле*. |
| **SHR** | Разделяемая память — часть RES, которая может использоваться другими процессами (например, общие библиотеки `.so`). |
| **S** | Текущий статус процесса (**R**, **S**, **D**, **Z**, **T**). |
| **%CPU** | Использование CPU. В режиме `Irix` (клавиша `I`) 100% — это полная загрузка одного ядра. |
| **%MEM** | Доля RES в общем объеме физической памяти. |
| **TIME+** | Суммарное время CPU, затраченное процессом (с точностью до 0.01 сек). |
| **COMMAND** | Команда запуска или имя исполняемого файла (клавиша `c` переключает вид). |

## Практические сценарии

### Интерактивное управление

Запустите `top` и используйте следующие клавиши для управления:

#### Навигация и вид
- **`q`**: Выход из утилиты (использовать именно эту клавишу, а не `Ctrl+C`).
- **`1`**: Развернуть/свернуть статистику по каждому ядру CPU отдельно.
- **`V`**: Переключить в древовидный режим (Forest view) — наглядно показывает связи родитель/потомок.
- **`z` / `b`**: Включить цветовое выделение / переключить режим жирного шрифта.
- **`Z`**: Меню настройки цветовой схемы и подсветки.
- **`x`**: Подсветить текущую колонку сортировки.
- **`y`**: Подсветить работающие (Running) процессы.
- **`c`**: Переключить отображение `COMMAND` (имя файла vs полная командная строка).
- **`H`**: Скрыть/показать потоки (Threads).

#### Сортировка и фильтрация
- **`M`**: Сортировка по памяти (`%MEM`). Регистр важен — нужно нажимать именно заглавную букву (Shift+M).
- **`P`**: Сортировка по нагрузке CPU (`%CPU`). Регистр важен — нужно нажимать именно заглавную букву (Shift+P).
- **`T`**: Сортировка по общему времени работы (`TIME+`).
- **`f`**: Меню управления полями (Field Management) — позволяет добавлять столбцы (например, `CGROUPS`, `PSR`, `WCHAN`) и выбирать поле сортировки.
- **`o` / `O`**: Фильтрация (например, `COMMAND=nginx`). Регистронезависимая (`o`) и зависимая (`O`). Сброс фильтра — `=`.
- **`u`**: Фильтр по имени пользователя.

#### Управление процессами
- **`k`**: Завершить процесс (kill). Потребуется ввести PID и номер сигнала (по умолчанию 15 — `SIGTERM`).
- **`r`**: Изменить приоритет (renice).
- **`d`** или **`s`**: Изменить интервал обновления (в секунды).

### Мониторинг в реальном времени

Для критических ситуаций, когда необходимо отслеживать малейшие всплески нагрузки, стандартный интервал 3 секунды слишком велик. Используйте флаг `-d` для изменения частоты обновления:

```bash
# Обновление данных каждую секунду
top -d 1
```

Это позволяет выявить кратковременные пики нагрузки, которые незаметны при стандартном интервале.

### Использование в скриптах (Пакетный режим)

Для автоматизации или создания периодических снимков системы используется флаг `-b`:

```bash
# Сделать 5 снимков состояния с интервалом 2 секунды и сохранить в файл
top -b -n 5 -d 2 > top_report.txt

# Вывести только топ-5 процессов по памяти в данный момент
top -b -n 1 -o +%MEM | head -n 12 | tail -n 6

# Отображение объема памяти в человекочитаемом формате (M/G/T)
top -E g
```

### Диагностика проблем производительности

1.  **Выявление «прожорливых» потоков**:
    Нажмите **`H`** в интерактивном режиме или запустите `top -H -p <PID>`. Это позволит увидеть нагрузку от каждого потока (Thread) внутри процесса. Подробнее: [Поиск проблемного потока](./thread_cpu_troubleshooting.md).
2.  **Анализ дисковых задержек**:
    Если `%wa` высокий, обратите внимание на процессы в состоянии **D**. Добавьте колонку `WCHAN` (через `f`), чтобы увидеть функцию ядра, на которой заблокирован процесс. Для детального анализа I/O используйте [`iotop`](../Filesystem/iotop.md).
3.  **Анализ нехватки памяти**:
    Ориентируйтесь на показатель `avail Mem`. Если он стремится к нулю, а `Swap used` растет, система находится на грани OOM (Out Of Memory).
4.  **Контейнерная среда и Namespaces**:
    Внутри контейнера `top` может отображать данные всего хоста, если не используются `lxcfs` или специфические настройки cgroup. Для анализа по сервисам используйте [`systemd-cgtop`](../../Core/systemd/cgtop.md).
5.  **Безопасность (Hidepid)**:
    Если `/proc` смонтирован с `hidepid=2`, пользователь в `top` увидит только свои процессы, что ограничивает диагностику общесистемных проблем без прав root.

## Сценарии для SRE / DevOps / Sysadmin

### Сценарий 1: Быстрая оценка состояния узла (Rapid Assessment)

При получении алерта о высокой нагрузке используйте `top` как первый инструмент для «тройного клика» по системе:

```bash
# Шаг 1: Общий обзор (10 секунд)
top -b -n 1 -E g

# Шаг 2: Идентификация «тяжелых» процессов
top -b -n 1 -o +%CPU | head -n 15
top -b -n 1 -o +%MEM | head -n 15

# Шаг 3: Проверка дисковых задержек (%wa)
top -b -n 1 | grep -E 'Cpu\(s\)|%wa'
```

Интеграция с Rapid Assessment workflow см. в [Практические сценарии мониторинга процессов](../../Core/processes/practical_scenarios.md#сценарий-6-rapid-assessment-методология-быстрой-оценки).

### Сценарий 2: Диагностика инцидентов по алерту Load Average

```bash
# 1. Сравнение LA с числом ядер
NPROC=$(nproc)
LA=$(awk '{print $1}' /proc/loadavg)
echo "LA: $LA, Cores: $NPROC"
if [ $(echo "$LA > $NPROC" | bc) -eq 1 ]; then
    echo "LA превышает число ядер — есть очередь задач"
fi

# 2. Проверка состояния D-state процессов
ps -eo pid,stat,%cpu,comm | awk '$2 ~ /D/'

# 3. Поиск процесса с максимальным TIME+ (долго работает)
top -b -n 1 -o +TIME+ | head -n 12
```

### Сценарий 3: Аудит безопасности в реальном времени

```bash
# Поиск процессов, запущенных из нестандартных путей
top -b -n 1 -o +%CPU | awk 'NR>7 && $0 ~ /\/tmp\|\/dev\/shm\|\/var\/tmp/'

# Проверка процессов с изменённым nice (возможен crypto-miner)
ps -eo pid,user,ni,pri,comm,args | awk '$4 != 0 && $3 != 0'

# Мониторинг новых процессов (аналог auditd в реальном времени)
watch -n 1 'top -b -n 1 | tail -n +8 | head -n 10'
```

### Сценарий 4: Автоматизированный сбор снапшотов для отчётов

```bash
# Сбор метрик каждые 30 секунд в течение 10 минут (20 снимков)
for i in $(seq 1 20); do
    echo "=== Snapshot $i at $(date) ===" >> /var/log/top_snapshots.log
    top -b -n 1 -E g | head -n 20 >> /var/log/top_snapshots.log
    echo "" >> /var/log/top_snapshots.log
    sleep 30
done

# Парсинг для поиска топ-5 процессов по памяти за весь период
grep -E '^[ ]*[0-9]+' /var/log/top_snapshots.log | \
    awk '{print $6, $7, $12}' | sort -rn | head -5
```

### Сценарий 5: Поиск утечек памяти

```bash
# Запуск top в фоне с интервалом 5 секунд
top -b -d 5 -E g | grep -E '^(top|Mem:|Swap:)' >> memory_leak.log &

# Через 30 минут: проверка роста RES
grep 'Mem:' memory_leak.log | tail -20

# Идентификация процессов с растущим RES
watch -n 5 'ps -eo pid,user,%mem,rss,comm --sort=-rss | head -11'
```

### Сценарий 6: Мониторинг в tmux/screen сессиях

```bash
# Запуск top в фоне с перезапуском при падении
tmux new-session -d -s monitor 'top -d 2'

# Присоединение к сессии для просмотра
tmux attach -t monitor

# Отсоединение без остановки (Ctrl+B, D)
```

### Сценарий 7: Валидация работы сервисов после деплоя

```bash
# Сравнение состояния до и после деплоя
# До деплоя:
top -b -n 1 -E g > before_deploy.txt

# После деплоя (через 2 минуты):
top -b -n 1 -E g > after_deploy.txt

# Сравнение ключевых метрик
diff <(grep -E 'load average|Mem:|Cpu' before_deploy.txt) \
     <(grep -E 'load average|Mem:|Cpu' after_deploy.txt)
```

## Диагностика инцидентов (Incident Response)

При получении алерта о высокой нагрузке или подозрительной активности `top` используется как первый инструмент для оценки состояния узла:

### Workflow 1: Высокий Load Average

```bash
# Шаг 1: Определение типа нагрузки
top -b -n 1 | grep -E 'Cpu\(s\)|Tasks'

# Если %wa > 30% — проблема с I/O (диски, NFS)
# Если %us + %sy > 90% — проблема с CPU

# Шаг 2: Детализация по процессам
top -b -n 1 -o +%CPU | head -n 12
ps -eo pid,ppid,stat,%cpu,%mem,comm --sort=-%cpu | head -10

# Шаг 3: Проверка D-state (если высокий LA при низком CPU)
ps -eo pid,stat,comm | awk '$2 ~ /D/'
cat /proc/<PID>/wchan
```

### Workflow 2: Подозрение на crypto-miner или ботнета

```bash
# Поиск скрытых процессов с высокой нагрузкой
top -b -n 1 -u root -o +%CPU | head -n 10

# Проверка путей (нестандартные директории)
top -b -n 1 | awk 'NR>7 && $0 ~ /\/tmp\|\/var\/run\|\/dev\/shm/'

# Проверка network connections подозрительного процесса
PID=$(pgrep -f suspicious_pattern)
ss -tlnp | grep $PID
lsof -p $PID | grep ESTABLISHED
```

## Валидация и верификация

### Проверка целостности данных

```bash
# Сравнение snapshot с live-режимом (должны совпадать ± погрешность)
SNAPSHOT=$(top -b -n 1 -o +%MEM | head -n 12 | tail -n 5)
LIVE=$(top -d 1 | head -n 15 | tail -n 5)

# Валидация конфигурации
top -b -n 1 | grep -E 'Cpu\(s\)|Mem:' | wc -l  # должно быть 2
```

### Согласованность с другими инструментами

```bash
# Сравнение top с ps (погрешность <5%)
TOP_CPU=$(top -b -n 1 -o +%CPU | head -n 10 | tail -n 1 | awk '{print $9}')
PS_CPU=$(ps -p <PID> -o %cpu=)
echo "Top: $TOP_CPU, ps: $PS_CPU"
```

## Рекомендации и очистка

### Best Practices

1. **Используйте пакетный режим для автоматизации:** Интерактивный `top` не подходит для скриптов — всегда используйте `-b`.
2. **Настройте интервал под задачу:** 1–2 секунды для reactive-мониторинга, 5–10 секунд для trend-анализа.
3. **Комбинируйте с `pidstat` для исторических данных:** `top` — snapshot, `pidstat` — история.
4. **Используйте `htop` для интерактивной работы, `top` для скриптов:** `htop` удобнее, но часто отсутствует в минимальных образах.
5. **Мониторьте `%st` на виртуальных машинах:** Значения >5% указывают на проблемы с гипервизором (noisy neighbor).

### Очистка ресурсов

```bash
# Остановка фоновых top-процессов
pkill -f "top -b"

# Очистка временных файлов
rm -f /tmp/top_report.txt /tmp/top_snapshots.log
```

## Ограничения и крайние случаи

- **Snapshot-эффект:** `top` показывает состояние на момент вызова. Для динамики используйте интерактивный режим или `pidstat`.
- **Точность CPU:** На многоядерных системах суммарный `%CPU` может превышать 100%. Нажмите `I` (Irix mode), чтобы переключить расчет: 100% на все ядра или 100% на одно ядро.
- **Влияние на систему:** Частые обновления (`-d 0.1`) при большом количестве процессов могут сами создавать заметную нагрузку на CPU.
- **Скрытые процессы:** При монтировании `/proc` с опцией `hidepid=2` обычный пользователь видит только свои процессы. Подробнее см. в [**Виртуальной файловой системе /proc**](../../FileSystems/virtual_fs_proc.md#параметр-hidepid).
- **GUI-сессии:** В графических окружениях (GNOME, KDE) `top` может показывать процессы X-сервера и композитного менеджера, что создает шум при диагностике.
- **Контейнеры:** Внутри контейнера `top` может отображать данные всего хоста, если не используются `lxcfs` или специфические настройки cgroup. Для анализа по сервисам используйте [`systemd-cgtop`](../../Core/systemd/cgtop.md).
- **Масштабирование:** При >1000 процессов навигация в `top` затруднительна. Используйте `ps` с фильтрацией или `htop` с поиском.
- **tmux/screen:** В мультиплексорах `top` может отображаться некорректно из-за управления терминалом. Используйте `TERM=linux` или `screen -T linux`.
- **NFS/D-state:** Зависшие NFS-операции могут вызвать массовый D-state, который невозможно очистить без переподключения. `top` покажет высокий LA, но не причину — используйте [`invisible_io.md`](../../Diagnostics/Performance/DiskIO/invisible_io.md) для диагностики.
- **PID переиспользование:** `top` показывает PID в момент снимка. Короткоживущие процессы могут переиспользовать PID до обновления — проверяйте `TIME+` и `START` колонки.
- **Точность памяти:** `top` показывает RSS, что может вводить в заблуждение при работе с разделяемыми библиотеками. Для точного анализа используйте [`smem`](../Memory/smem.md).
- **Влияние strace/ptrace:** Если к процессу прикреплен `strace`, `top` может показывать состояние `T` (stopped), что не отражает реальную нагрузку.

## Современные альтернативы

В 2026 году классический `top` часто уступает место более функциональным TUI-мониторам, особенно на десктопах и рабочих станциях. Ниже — практические замены с учётом сценария использования.

### btop

**`btop`** — современный монитор на C++, наследник bashtop → bpytop → btop. Показывает CPU, память, диск, сеть, температуру и (в зависимости от сборки) GPU. Интерфейс рассчитан на «эстетичный» просмотр метрик в реальном времени.

```bash
# Debian/Ubuntu
sudo apt install btop

# Из исходников
git clone https://github.com/aristocratos/btop.git
cd btop && make && sudo make install
```

**Когда выбирать:** рабочие станции, десктопы, серверы с GPU. На древнем железе 2010 года btop может сам потреблять заметный CPU.

### glances

**`glances`** — кросс-платформенный монитор на Python. В терминале работает как TUI, а через флаг `-w` отдаёт ту же сводку в браузер (WebUI).

```bash
pip install glances[web]
glances -w
```

**Когда выбирать:** серверы, куда не хочется лишний раз ходить по SSH, но нужен браузерный доступ к сводке.

### bottom

**`bottom`** ( `btm` ) — минималистичный монитор на Rust. Легче btop и приятнее htop, но на боевом сервере таскать всё сразу не стоит. Выбирайте htop плюс что-то потяжелее.

```bash
# cargo
cargo install bottom

# Или пакет
sudo apt install bottom
```

### Внешние системы мониторинга

Для постоянного наблюдения за несколькими серверами удобнее self-hosted-решения:

- **[Beszel](https://github.com/henrygd/beszel)** — лёгкий self-hosted мониторинг с hub + agent. В браузере показывает CPU, RAM, load average, диски, I/O, сеть, температуры и метрики Docker/Podman-контейнеров.
- **[Monitorix](https://github.com/mikaku/Monitorix)** — старый, но живой и лёгкий мониторинг Linux/Unix. Collector работает демоном, а встроенный HTTP-сервер отдаёт графики в браузер.
- **[Cockpit](https://github.com/cockpit-project/cockpit)** — веб-консоль для управления сервером: состояние, нагрузка, логи, сеть, хранилища и управление системными службами.

### Сравнение с аналогами

| Инструмент | Преимущества | Недостатки |
| :--- | :--- | :--- |
| [`htop`](./htop.md) | Графические шкалы, поддержка мыши, удобная прокрутка. | Часто отсутствует в «минимальных» образах. |
| [`atop`](../Performance/atop.md) | Ведение исторических логов, детальная статистика по I/O. | Сложный интерфейс, требует обучения. |
| **`btop`** | Исключительная визуализация, GPU/температура/сеть в одном окне. | Тяжелее htop, на слабом железе потребляет лишний CPU. |
| **`glances`** | TUI + WebUI, кросс-платформенный. | Зависимость от Python, overhead веб-сервера. |
| **`bottom`** | Лёгкий Rust-аналог, приятный UI. | Меньше метрик, чем у btop/glances. |
| [`ps`](./ps.md) | Идеально для разовых статических снимков в скриптах. | Не интерактивен. |
| [**`systemd-cgtop`**](../../Core/systemd/cgtop.md) | Агрегация данных по cgroups (сервисам). | Не показывает детализацию по отдельным PID. |
