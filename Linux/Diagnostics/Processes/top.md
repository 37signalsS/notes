# `top`

## Определения

**`top`** — стандартная консольная утилита Unix-подобных систем для динамического мониторинга процессов и системных ресурсов в реальном времени. Входит в пакет `procps-ng` (Linux) или `procps` (BSD/macOS).

**Ключевые особенности:**

- Встроена в базовую поставку большинства дистрибутивов
- Минимальное потребление ресурсов
- Поддержка пакетного режима для скриптов
- Интерактивное управление отображением

## Основные концепции

Интерфейс `top` разделён на две части: **сводная информация** (header) и **список процессов**.

### Сводная информация (Header)

#### Время и uptime

**Пример:** `top - 14:50:30 up 2 days, 4:21, 1 user, load average: 0.05, 0.08, 0.07`

| Поле | Описание |
| :--- | :--- |
| `14:50:30` | Текущее системное время |
| `up 2 days, 4:21` | Uptime — время работы без перезагрузки |
| `1 user` | Количество активных пользовательских сессий (см. [`w`](./w.md)) |
| `load average: 0.05, 0.08, 0.07` | Средняя нагрузка за 1, 5, 15 минут (см. [scheduling.md](../../Core/processes/scheduling.md#load-average-la)) |

#### Статистика задач (Tasks)

**Пример:** `Tasks: 114 total, 1 running, 113 sleeping, 0 stopped, 0 zombie`

| Состояние | Описание |
| :--- | :--- |
| `total` | Общее количество процессов |
| `running` | Выполняются или готовы к выполнению (R) |
| `sleeping` | В прерываемом сне (S), ожидают события |
| `stopped` | Остановлены сигналом (T) |
| `zombie` | Завершены, не освобождены родителем (Z) — см. [basic_concepts.md](../../Core/processes/basic_concepts.md) |

#### Статистика CPU (Cpu(s))

| Метрика | Описание | Когда проблема |
| :--- | :--- | :--- |
| `us` (user) | Пользовательские процессы | >80% — нагрузка от приложений |
| `sy` (system) | Ядро, системные вызовы | >30% — проблемы драйверов/I/O |
| `ni` (nice) | Процессы с изменённым приоритетом | — |
| `id` (idle) | Простой CPU | <20% — высокая нагрузка |
| `wa` (iowait) | Ожидание I/O (диск, сеть) | >15-20% — bottleneck I/O, см. [`iotop`](../Filesystem/iotop.md) |
| `hi` (hardware irq) | Аппаратные прерывания | >10% — проблемы оборудования |
| `si` (software irq) | Программные прерывания | Высокое — сетевая нагрузка |
| `st` (steal) | Украдено гипервизором (VM) | >5% — перегрузка хоста |

> **Важно:** Низкий `iowait` не всегда означает отсутствие проблем с диском. Если `await` в [`iostat -x`](../Filesystem/iostat.md#низкий-iowait-при-высокой-задержке) высокий, а `avgqu-sz` растёт — диск перегружен, даже если `wa` низкий. Это происходит при burst-записи или смешанной нагрузке read/write.

> **Примечание:** Время на `sy` (system) — это затраты на **системные вызовы** (syscalls): чтение файлов, сеть, создание процессов.

#### Steal Time (st) — детальное описание

**Steal time** — это процент времени, в течение которого виртуальная машина (VM) готова к выполнению, но не получает доступ к физическому CPU из-за конкуренции с другими VM на том же гипервизоре.

**Причины возникновения:**

1. **Перегрузка хоста:** Слишком много VM делят ограниченные физические ядра
2. **Шумные соседи:** Другие VM на хосте потребляют все доступные ресурсы
3. **Нехватка тайм-слотов:** Планировщик гипервизора не выделяет достаточно CPU времени

**Единицы измерения:** Проценты (0-100%). Значение >5% указывает на проблемы, >10% — критично.

**Практический пример из production:**

> **Сценарий:** Кластер PostgreSQL с Patroni и Consul для координации master/slave.
>
> **Проблема:** Программисты создали множество вложенных SELECT в PostgreSQL, что привело к 100% загрузке CPU пользовательским временем (us). Консул-клиент на той же машине не получал достаточно тайм-слотов для связи с Consul-сервером.
>
> **Последствие:** Patroni-кластер развалился, потому что Consul не мог отписаться в сеть о статусе мастера. Начались повторные выборы мастера, что привело к простою.
>
> **Решение:**
>
> 1. Срочно: Повысить приоритет процесса Consul через `renice` (меньшее значение nice = высший приоритет)
> 2. Долгосрочно: Оптимизировать запросы PostgreSQL, разнести процессы по разным VM
>
> **Команда для диагностики:**
>
> ```bash
> # Проверить steal time
> top -bn1 | grep "Cpu(s)"
>
> # Посмотреть приоритеты процессов
> ps -eo pid,ppid,nice,pri,comm --sort=-pcpu | head -20
>
> # Временно повысить приоритет (требует root)
> renice -n -10 -p <PID_consul>
> ```

> **Рекомендация:** Для критичных процессов в VM используйте `nice`/`renice` для установки приоритета, либо рассмотрите CPU pinning (привязку к ядрам). См. [CPU Pinning](../../Core/cpu_pinning.md).

#### Память (KiB Mem / KiB Swap)

**Пример:**

```
KiB Mem :  2048000 total,  130000 free, 1200000 used,  718000 buff/cache
KiB Swap:  1024000 total,  800000 free,  224000 used. 1800000 avail Mem
```

| Поле | Описание |
| :--- | :--- |
| `total` | Общий объём RAM / swap |
| `free` | Полностью свободная память (может быть мало — это нормально) |
| `used` | Используется процессами |
| `buff/cache` | Кэш ядра (buffers + page cache) — освобождается при необходимости |
| `avail Mem` | Доступно для приложений (реалистичная оценка) |

> **Важно:** Не беспокойтесь, если `free` мало. Реально доступная память = `free` + `buff/cache`. Беспокоиться стоит, если активно используется `swap` или `avail Mem` мало.

Подробное описание метрик памяти: [process_memory_metrics.md](../../Core/memory/process_memory_metrics.md).

### Список процессов

| Столбец | Описание |
| :--- | :--- |
| `PID` | Идентификатор процесса |
| `USER` | Владелец процесса |
| `PR` | Приоритет планировщика (может быть `rt` — real-time) |
| `NI` | Nice-значение (-20 до +19) |
| `VIRT` | Виртуальная память (VSS) — см. [process_memory_metrics.md](../../Core/memory/process_memory_metrics.md) |
| `RES` | Резидентная память (RSS) в RAM |
| `SHR` | Разделяемая память |
| `S` | Состояние (R/S/D/Z/T) — см. [basic_concepts.md](../../Core/processes/basic_concepts.md) |
| `%CPU` | Процент использования CPU (100% = одно ядро) |
| `%MEM` | Процент использования физической памяти |
| `TIME+` | Суммарное время CPU (мин:сек.сотые) |
| `COMMAND` | Команда запуска |

> **Примечание:** `%CPU` > 100% означает использование нескольких ядер (200% = 2 ядра).

## Практические сценарии

### Интерактивный режим

```bash
# Базовый запуск
top

# Запуск с интервалом обновления 2 секунды
top -d 2

# Мониторинг конкретного PID
top -p 1234

# Мониторинг нескольких PID
top -p 1234,5678,9012

# Сортировка по памяти при запуске
top -o %MEM
```

#### Горячие клавиши

| Клавиша | Действие |
| :--- | :--- |
| `1` | Развернуть статистику по ядрам CPU |
| `A` | Сортировка по возрасту процесса |
| `F` / `O` | Выбор столбцов для отображения |
| `H` | Показать потоки (threads) |
| `I` | Переключить режим Irix/Solaris (влияет на расчёт %CPU) |
| `k` | "Убить" процесс (ввести PID и сигнал) |
| `M` | Сортировка по памяти (`RES`) |
| `N` | Сортировка по PID |
| `P` | Сортировка по CPU (по умолчанию) |
| `R` | Инвертировать порядок сортировки |
| `s` | Изменить интервал обновления |
| `T` | Сортировка по времени CPU |
| `u` | Фильтр по пользователю |
| `z` | Включить цвета |
| `q` | Выход |

### Пакетный режим (скрипты, логирование)

```bash
# Сделать 3 снимка с интервалом 5 секунд в файл
top -b -n 3 -d 5 > top_log.txt

# Логирование для анализа (каждые 10 секунд)
top -b -d 10 >> /var/log/top.log &

# Получить текущую загрузку CPU (одна строка)
top -bn1 | grep "Cpu(s)"

# Сохранить топ-20 процессов по памяти
top -b -n 1 -o %MEM | head -n 25 > memory_usage.txt
```

### Диагностика проблем

#### Высокая нагрузка CPU

1. Запустить `top`
2. Отсортировать по `%CPU` (клавиша `P`)
3. Определить процессы-лидеры
4. Нажать `H` для просмотра потоков (если многопоточное приложение)
5. При необходимости отправить сигнал (`k`)

#### Высокий iowait

1. Проверить строку `Cpu(s)`: значение `wa` > 15-20%
2. Запустить [`iotop`](../Filesystem/iotop.md) для определения процесса:

   ```bash
   sudo iotop -o
   ```

3. Альтернативно: [`pidstat -d 1`](./pidstat.md)

#### Проверка zombie-процессов

```bash
# В top: посмотреть строку Tasks (zombie count)
# Или через ps:
ps aux | awk '$8 ~ /Z/ {print}'
```

#### Анализ утечек памяти

1. Запустить `top`, отсортировать по `%MEM` (`M`)
2. Наблюдать за ростом `RES` у процессов
3. Проверить `VIRT` — большой рост может указывать на утечку
4. Для точного анализа использовать [`smem`](../Memory/smem.md)

## Дополнительная информация

### Конфигурация

`top` сохраняет настройки в `~/.config/procps/toprc` или `~/.toprc`.

**Настройка в интерактивном режиме:**

- `W` — сохранить текущие настройки
- `Y` — показать путь к файлу конфигурации

### Сравнение с аналогами

| Инструмент | Преимущества | Недостатки |
| :--- | :--- | :--- |
| [`htop`](./htop.md) | Цветной интерфейс, деревья, мышь | Требует установки |
| [`atop`](../Performance/atop.md) | Исторические логи, все метрики | Требует демона |
| [`ps`](./ps.md) | Скрипты, снимки | Не интерактивный |
| [`systemd-cgtop`](../../Core/systemd/cgtop.md) | Агрегация по cgroups | Только systemd |

### Ограничения

- **Одномоментный снимок:** Для истории требуется [`atop`](../Performance/atop.md) или [`sar`](../Performance/sar.md)
- **Ограниченная детализация:** Для глубокого анализа I/O — [`pidstat`](./pidstat.md), памяти — [`smem`](../Memory/smem.md)
- **Нет агрегации по сервисам:** Для systemd — [`systemd-cgtop`](../../Core/systemd/cgtop.md).
