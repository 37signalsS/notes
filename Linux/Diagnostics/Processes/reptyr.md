# Утилита `reptyr`

## Определения

**`reptyr`** — специализированная утилита интерфейса командной строки (CLI — Command Line Interface), написанная на C, предназначенная для перехвата запущенного процесса из одной терминальной сессии и его переноса в другую без остановки выполнения, потери контекста или необходимости перезапуска.

## Основные концепции

### Назначение инструмента

Типичный сценарий использования возникает, когда длительный процесс (сборка программного обеспечения, миграция базы данных, передача файлов, обучение модели) был запущен в обычной сессии Secure Shell (SSH) без использования терминальных мультиплексоров (`tmux` или `screen`). При разрыве сетевого соединения такой процесс получит сигнал `SIGHUP` и принудительно завершится. `reptyr` позволяет «спасти» выполнение, переместив процесс в стабильную сессию мультиплексора или другой терминал.

Кроме того, утилита полезна при администрировании: например, для подключения к интерактивному процессу, запущенному другим пользователем (с правами `root`), без необходимости завершать и перезапускать его.

### Принцип работы

Утилита использует системный вызов `ptrace` (process trace) для временной приостановки целевого процесса. В этот момент `reptyr` выполняет перехват файловых дескрипторов, связанных со стандартными потоками ввода-вывода (stdin, stdout, stderr), и перенаправляет их на управляющий терминал новой сессии.

Для ядра Linux этот процесс выглядит как смена управляющего терминала (controlling terminal) процесса. `reptyr` не копирует состояние процесса в памяти — она изменяет дескрипторы файлового описателя (file descriptor table) целевого процесса, что делает перехват быстрым и не требующим дополнительного пространства.

### Ключевые понятия

- **Управляющий терминал (controlling TTY)** — терминальное устройство, ассоциированное с сессией. Процесс может иметь только один controlling TTY.
- **Лидер сессии (session leader)** — процесс, создавший сессию (обычно оболочка или `sshd`). Только лидер сессии может владеть controlling TTY.
- **Группа процессов (process group)** — набор процессов, связанных с одним заданием (job). Управляются как единое целое для сигналов.
- **Псевдотерминал (PTY)** — пара виртуальных устройств (`master`/`slave`), эмулирующих работу последовательного порта. Современные терминалы (`gnome-terminal`, `xterm`, `tmux`) используют PTY.
- **`SIGHUP`** — сигнал (`signal 1`), отправляемый процессу при потере управляющего терминала (разрыв SSH, закрытие окна терминала). По умолчанию приводит к завершению процесса.

### Механизм `SIGHUP` и управление заданиями

При закрытии терминала или обрыве SSH-соединения ядро отправляет сигнал `SIGHUP` всем процессам группы переднего плана (foreground process group), связанной с этим терминалом. Поведение по умолчанию — завершение.

**Защита от `SIGHUP` без `reptyr`:**
- **`nohup`** — запускает процесс, игнорирующий `SIGHUP`, и перенаправляет вывод в `nohup.out`.
- **`disown`** — встроенная команда `bash`/`zsh`, которая удаляет задание из таблицы активных jobs оболочки. После `disown` процесс не получит `SIGHUP` от родительской оболочки.
- **`trap '' HUP`** — программная установка игнорирования `SIGHUP` внутри скрипта.

`reptyr` используется, когда процесс уже запущен и защита от `SIGHUP` не была настроена заранее.

### Требования и безопасность

Для корректной работы требуются права суперпользователя (`root`) или специфические настройки ядра. В современных дистрибутивах Linux возможность использования `ptrace` для процессов, не являющихся дочерними, ограничена механизмом **Yama LSM** (Linux Security Module), параметр `ptrace_scope`.

**Уровни `ptrace_scope`:**
| Значение | Поведение | Риск |
| :--- | :--- | :--- |
| `0` | Классическое поведение — любой процесс может `ptrace`-ить любой другой | Высокий |
| `1` (по умолчанию) | Только родительские процессы могут `ptrace` потомков | Средний |
| `2` | Только потомки `init` (PID 1) могут использовать `ptrace` | Низкий |
| `3` | Полный запрет на `ptrace` | Максимальный |

**Временное разрешение перехвата:**
```bash
echo 0 | sudo tee /proc/sys/kernel/yama/ptrace_scope
```

**Перманентная настройка:**
Отредактируйте файл `/etc/sysctl.d/10-ptrace.conf` (или создайте новый):
```text
kernel.yama.ptrace_scope = 0
```
И примените изменения: `sudo sysctl -p /etc/sysctl.d/10-ptrace.conf`.

Подробнее об ограничениях: [Защита среды выполнения ядра](../Security/Fstec/kernel_runtime_protection.md#уровни-ограничений-ptrace_scope).

**Установка:**
```bash
# Debian/Ubuntu
sudo apt install reptyr

# RHEL/CentOS/Fedora
sudo dnf install reptyr

# Arch Linux
sudo pacman -S reptyr
```

## Практические сценарии

### Перенос работающего процесса в `tmux`

Рассмотрим пример переноса утилиты `top` из обычного терминала в сессию `tmux`.

1. **Приостановка процесса**: Нажмите `Ctrl+Z` в текущем терминале.
2. **Перевод в фоновый режим**:
   ```bash
   bg
   ```
3. **Определение идентификатора процесса (PID — Process Identifier)**:
   ```bash
   jobs -l
   # [1]+  7972 Stopped (signal)     top
   ```
4. **Отвязка от текущей оболочки (Shell)**:
   ```bash
   disown top
   ```
5. **Запуск и подключение**: Войдите в новую сессию (например, `tmux`) и выполните перехват по PID:
   ```bash
   reptyr 7972
   ```

### Перехват процесса другого пользователя

Если процесс запущен другим пользователем, `reptyr` должен запускаться через `sudo`:
```bash
sudo reptyr <PID>
```

**Важно:** Процесс унаследует переменные окружения и права исходного владельца, но его управляющим терминалом станет ваш текущий терминал. После перехвата `sudo` можно завершить сессию — процесс продолжит работу в новом терминале.

### Сценарий: восстановление после обрыва SSH

**Ситуация:** Вы запустили длинную команду (например, `apt upgrade` или `git clone`) на удаленном сервере без `tmux`. SSH-соединение разорвалось, и вы не можете подключиться обратно к тому же PTY, так как сессия завершилась.

**Решение:**
1. Подключитесь к серверу заново.
2. Найдите процесс по имени:
   ```bash
   pgrep -l apt
   # → 12345 apt
   ```
3. Запустите `tmux` (или `screen`) в новой сессии:
   ```bash
   tmux new -s rescue
   ```
4. Выполните перехват:
   ```bash
   sudo reptyr 12345
   ```
5. Процесс продолжит работу в новом терминале. Если был запущен интерактивный `apt`, вывод будет отображаться в `tmux`.

### Сценарий: спасение длительной компиляции

**Ситуация:** Запущена сборка ядра или大型 проекта (`make -j$(nproc)`), которая займет несколько часов. Если терминал закроется, компиляция прервется, и придется заново ждать.

**Решение:**
```bash
# На старом терминале: найти PID компилятора
pgrep -l make
# → 28901 make

# На новом терминале (в tmux):
tmux new -s build
sudo reptyr 28901
```

После перехвата `make` продолжит работу в фоне сессии `tmux`. Вы можете отсоединиться (`Ctrl+B D`) и вернуться позже (`tmux attach -t build`).

### Сценарий: rescue миграции базы данных

**Ситуация:** Запущена длительная миграция PostgreSQL или MySQL через `psql`/`mysql` клиент. При разрыве SSH сессия интерактивного клиента завершится, и сервер БД может зависнуть в ожидании завершения транзакции.

**Решение:**
```bash
# На новом терминале:
tmux new -s db-migrate
sudo reptyr <PID_psql_or_mysql>
```

Если клиент уже завершился, а миграция выполняется на стороне сервера БД, используйте `reptyr` для подключения к демону БД или к дочернему процессу миграции.

### Сценарий: rescue передачи файлов

**Ситуация:** Запущено копирование большого файла через `scp` или `rsync` в интерактивном режиме. При обрыве сети `scp` завершится, и передаче придется начинать заново (если не настроено продолжение).

**Решение:**
```bash
# Если scp еще работает (например, завис в ожидании):
sudo reptyr <PID_scp>
```

Для `rsync` с поддержкой докачки (`--partial`) можно перезапустить передачу, но `reptyr` позволит избежать этого, сохранив текущее состояние.

### Сценарий: отладка зависшего процесса из новой сессии

**Ситуация:** Процесс завис в состоянии D (Uninterruptible Sleep) или потребляет 100% CPU. Вы хотите подключить `strace` или `gdb`, но делать это из текущего терминала неудобно.

**Решение:**
```bash
# Запустите reptyr для перехвата в tmux
tmux new -s debug
sudo reptyr <PID>
strace -p <PID>
```

Теперь отладчик работает в изолированной сессии `tmux`, и вы можете отсоединиться, не прерывая диагностику.

### Сценарий: автоматизация и скриптовое использование

`reptyr` может использоваться в скриптах для автоматического rescue процессов:

```bash
#!/bin/bash
# auto-rescue.sh — автоматический перенос критических процессов в tmux
PROCESS_NAME="my_worker"
TMUX_SESSION="rescue-$(date +%s)"

# Найти процесс
PID=$(pgrep -x "$PROCESS_NAME" | head -1)

if [ -z "$PID" ]; then
    echo "Процесс $PROCESS_NAME не найден"
    exit 1
fi

# Создать сессию tmux и перехватить процесс
tmux new-session -d -s "$TMUX_SESSION" "sudo reptyr $PID && bash"

echo "Процесс $PROCESS_NAME (PID: $PID) перехвачен в tmux сессию $TMUX_SESSION"
echo "Подключение: tmux attach -t $TMUX_SESSION"
```

## Производительность и масштабирование

- **Накладные расходы `ptrace`:** При перехвате ядро приостанавливает целевой процесс, что может вызвать задержку в работающих приложениях (особенно в реальном времени). Для интерактивных TUI-приложений (`top`, `htop`) это может привести к кратковременному «зависанию» экрана.
- **Время перехвата:** Зависит от скорости чтения `/proc/<PID>/mem` и переподключения дескрипторов. Обычно занимает 0.1–1 секунду для типичного процесса.
- **Влияние на production:** `reptyr` безопасен для production, если процесс можно кратковременно приостановить. Для критических сервисов (базы данных, очереди) используйте во время окон обслуживания.
- **Многопоточные процессы:** Перехват многопоточного процесса требует дополнительных шагов (см. ограничения).

## Типичные ошибки и их решения

| Ошибка / симптом | Причина | Решение |
| :--- | :--- | :--- |
| `Operation not permitted` | `ptrace_scope` > 0 или процесс чужого пользователя | Включить `ptrace_scope = 0` или использовать `sudo` |
| `No such process` | PID был переиспользован или процесс завершился | Проверить через `ps -p <PID>`; использовать `pidfd` (Linux 5.3+) |
| `[target process] exists` | Старая оболочка пытается управлять процессом | Выполнить `disown` перед `reptyr` |
| `reptyr: failed to reopen terminal` | PTY недоступен или права на `/dev/pts/*` | Проверить права доступа к PTY, использовать `sudo` |
| TUI отображается некорректно | Специфичная версия `ncurses` или размер окна | Выполнить `reset` или `Ctrl+L` в целевом терминале |
| Процесс завершается после перехвата | Процесс имеет обработчик `SIGHUP` | Настроить игнорирование сигнала до перехвата |
| `Operation not permitted` для setuid-процесса | Ядро блокирует `ptrace` для setuid-binaries | Запустить `reptyr` от имени владельца процесса или отключить проверку |

## Ограничения

- **Сложные интерфейсы (TUI):** Программы, использующие сложные библиотеки отрисовки (например, специфичные версии `ncurses`), могут некорректно восстанавливать интерфейс. В таких случаях часто помогает принудительная перерисовка экрана (`reset`, `Ctrl+L`).
- **Специфические дескрипторы:** `reptyr` перехватывает основные дескрипторы (0, 1, 2). Если процесс использует дополнительные файловые дескрипторы для общения с исходным терминалом (например, `tmux` send-keys через FIFO), они могут быть потеряны.
- **Setuid-программы:** Перехват процессов с установленным битом `setuid` (например, запущенных через `sudo` программ) может быть запрещен ядром даже при `ptrace_scope = 0` (зависит от версии ядра и Yama LSM).
- **Зомби и фоновые процессы:** `reptyr` не может перехватить процесс, который уже стал зомби (zombie, состояние `Z`) или находится в процессе завершения (exit state).
- **Многопоточные процессы:** Начиная с Linux 3.7, `ptrace` поддерживает перехват многопоточных процессов, но требуется использовать `reptyr -T` для явного указания потока. Некоторые версии `reptyr` могут нестабильно работать с потоками.
- **PID Namespaces:** В изолированном PID namespace `reptyr` видит процессы внутри namespace. Для перехвата процесса из другого namespace требуется использовать `nsenter`.
- **Переиспользование PID:** Если целевой процесс завершился, а его PID был переиспользован другим процессом, `reptyr` перехватит неверный процесс. Всегда проверяйте PID перед перехватом (`ps -p <PID> -o pid,cmd`).

## Сравнение с аналогами

| Метод | Когда использовать | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **`reptyr`** | Процесс уже запущен без мультиплексора, требуется сохранить интерактивность. | Позволяет «спасти» процесс без перезапуска; сохраняет TTY-интерфейс. | Требует настройки `ptrace`, не всегда стабилен с TUI, требует временной приостановки процесса. |
| [`ps`](./ps.md) | Статический анализ — не для перехвата. | Стандартный, всегда доступен. | Нет функции перехвата. |
| **`nohup`** | Процесс еще не запущен. | Простота, гарантированное игнорирование `SIGHUP`. | Весь вывод идет в файл, нет интерактивности. |
| **`disown`** | Процесс запущен, требуется только защита от `SIGHUP`. | Отвязывает процесс от Shell, не требует `root`. | Не дает возможности перехватить ввод-вывод в новый терминал. |
| **`tmux`/`screen`** | Профилактический метод (до запуска процесса). | Полная изоляция от SSH-разрывов. | Требует предварительного запуска мультиплексора. |
| [CRIU](../../Core/processes/Troubleshooting/checkpoint_restore.md) | Сохранение и восстановление состояния процесса на диск. | Полный live-migrate, survives reboot. | Сложность настройки, не все приложения поддерживаются. |
