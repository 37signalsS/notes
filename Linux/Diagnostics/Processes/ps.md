# Утилита `ps`

## Определения

**`ps`** (process status) — стандартная системная утилита в Linux (основная реализация — пакет `procps-ng`), предназначенная для создания статического снимка (snapshot) текущих процессов системы. В отличие от динамических мониторов ([`top`](./top.md), [`htop`](./htop.md)), `ps` выводит информацию один раз и завершается, что делает её идеальной для скриптов и детального аудита.

### Реализации

- **procps-ng**: наиболее полная версия, стандарт для большинства дистрибутивов (Debian, RHEL, Arch). Поддерживает все три стиля опций.
- **BusyBox ps**: сильно упрощенная версия, часто встречающаяся в минималистичных контейнерах (Alpine Linux) и встроенных системах. Поддерживает ограниченный набор флагов (обычно только `-w`, `-o`, `-T`).

Утилита считывает данные из виртуальной файловой системы `/proc` и представляет их в человекочитаемом или машинном формате.

## Основные концепции

### Поведение `ps` без аргументов (вид по умолчанию)

Запуск `ps` без каких-либо флагов выдаёт на первый взгляд «скромный» список — обычно всего две-три строки (оболочка `bash`/`zsh`, из которой вы работаете, и сама вызванная утилита `ps`). Это не ошибка, а результат **стратегии выборки по умолчанию (default selection)**, принятой в реализации procps-ng.

Без аргументов `ps` отбирает процессы по двум критериям **одновременно**:

1.  **Тот же эффективный UID**, что у вызывающего пользователя (только «ваши» процессы).
2.  **Тот же управляющий терминал (controlling TTY)**, что у текущего сеанса (только задачи, привязанные к этому окну терминала).

Иными словами, «голая» `ps` показывает лишь задачи, запущенные от вашего имени **и** прикреплённые к вашему текущему терминалу. Фоновые демоны (без управляющего терминала — `?` в колонке TTY), процессы других пользователей и задачи в других терминалах/сессиях в вывод не попадают. Именно поэтому в интерактивной оболочке видны только она сама и вызванная `ps`.

**Почему так исторически:** в эпоху многопользовательских серверов (до появления `ps aux`) администратору чаще всего требовался быстрый взгляд на собственные задачи в текущем сеансе, а не полный список всех процессов машины. Полный обзор системы требует явного расширения выборки флагами (`ps aux`, `ps -ef`, `ps -e`).

```bash
# Минимальный вывод «по умолчанию» — только текущий TTY и текущий пользователь
ps
#   PID TTY          TIME CMD
#  1234 pts/0    00:00:00 bash
#  5678 pts/0    00:00:00 ps
```

Основные колонки вывода «по умолчанию»:

- **PID (Process ID):** Уникальный числовой идентификатор процесса. Назначается ядром в момент создания задачи; нумерация начинается с 1. Полную теорию идентификаторов см. в [Основных концепциях процессов](../../Core/processes/basic_concepts.md#уровни-идентификации).
- **TTY:** Управляющий терминал (controlling terminal), к которому привязан процесс. Для демонов обычно `?`.
- **TIME:** Суммарное процессорное время, потраченное процессом (пользовательское + системное), а не время с момента старта.
- **CMD:** Имя команды/процесса (в этом виде — без аргументов).

**Почему вывод «беднее», чем у `ps aux`:** `ps aux` снимает оба ограничения выборки по умолчанию — флаг `a` добавляет процессы всех пользователей с терминалами, `u` включает ориентированный на пользователя формат с потреблением ресурсов, `x` добавляет процессы без терминала (демоны). Подробнее о стилях опций — ниже.

### Стили написания опций

`ps` уникальна тем, что поддерживает три различных синтаксиса, наследуемых от разных веток Unix:

| Стиль | Синтаксис | Пример | Описание |
| :--- | :--- | :--- | :--- |
| **BSD** | Без дефиса | `ps aux` | Популярный интерактивный формат. **Важно:** BSD-стиль не использует дефисы перед флагами (`ps aux`, а не `ps -aux`); написание с дефисом интерпретируется как System V и может вызвать ошибку или неверный вывод. |
| **System V** | С одним дефисом | `ps -ef` | Стандарт POSIX. Используется в классических скриптах администрирования. |
| **GNU** | С двумя дефисами | `ps --pid 1` | Современный стиль с длинными именами аргументов. |

**Важно:** Смешивание стилей (например, `ps -aux`) может приводить к предупреждениям или интерпретации `a` как аргумента к `-u` в некоторых старых реализациях.

### Переменные окружения

Поведение `ps` можно настроить глобально:
- **`PS_FORMAT`**: задает формат вывода по умолчанию (аналог `-o`).
- **`PS_PERSONALITY`**: меняет стиль работы утилиты (например, `linux`, `bsd`, `posix`).
- **`PS_COLUMNS`**: принудительно устанавливает ширину вывода (полезно при перенаправлении в файл).

### Состояния процессов (STAT)

Код состояния в выводе `ps` дает понимание о текущем жизненном цикле задачи.

| Код | Название | Описание |
| :--- | :--- | :--- |
| **R** | Running | Выполняется или стоит в очереди на выполнение. |
| **S** | Sleeping | Прерываемый сон (ожидание события, например, сетевого пакета). |
| **D** | Disk sleep | Непрерываемый сон (обычно ожидание ввода-вывода I/O). Не убивается `SIGKILL`. |
| **I** | Idle | Бездействующий поток ядра (v4.14+). Не учитывается в Load Average. |
| **Z** | Zombie | Завершен, но запись в таблице процессов не удалена родителем. |
| **T** | Stopped | Остановлен сигналом (например, `Ctrl+Z` или `SIGSTOP`). |
| **t** | Traced | Остановлен отладчиком во время трассировки. |
| **X** | Dead | Процесс «мертв» (практически не встречается в выводе). |

**Модификаторы (дополнительные символы):**
- **`<`** — высокий приоритет (отрицательный `nice`).
- **`N`** — низкий приоритет (положительный `nice`).
- **`L`** — страницы памяти заблокированы в RAM (например, для реального времени).
- **`s`** — лидер сессии (Session Leader).
- **`l`** — многопоточный процесс (использует NPTL).
- **`+`** — находится в группе процессов переднего плана (foreground).

Подробнее о теории состояний см. в [Основных концепциях процессов](../../Core/processes/basic_concepts.md#состояния-процесса).

## Практические сценарии

### Классический обзор системы

```bash
# Стандартный BSD-формат (все пользователи, с терминалами и без)
ps aux

# Полный список процессов с PPID (иерархия) и временем старта
ps -ef

# Вывод всех процессов текущего пользователя
ps -x
```

### Фильтрация через grep (распространённый паттерн)

При работе с `ps aux` самым частым сценарием является поиск конкретного процесса или службы. Поскольку `ps` не имеет встроенного полнотекстового поиска по командной строке, используется стандартный паттерн с `grep`:

```bash
# Найти все процессы, содержащие "systemd"
ps aux | grep systemd

# Исключить сам grep из результатов (частый источник шума)
ps aux | grep systemd | grep -v grep

# Поиск с игнорированием регистра
ps aux | grep -i nginx
```

**Важно:** При фильтрации по точному имени службы используйте `grep -w` или экранируйте спецсимволы, чтобы избежать ложных совпадений (например, `bash` совпадёт с `my-bash-script`).

### Детальный анализ ресурсов

```bash
# Топ-10 процессов по потреблению памяти (RSS)
ps aux --sort=-%mem | head -n 11

# Топ-10 процессов по потреблению CPU
ps aux --sort=-%cpu | head -n 11

# Проверка, на каких ядрах CPU (PSR) работают процессы
ps -eo pid,psr,comm --sort=psr
```

### Древовидное отображение (Иерархия)

Помогает визуализировать связи "родитель-потомок", что критично для анализа Master/Worker структур (Nginx, PostgreSQL).

```bash
# Визуальное дерево (BSD)
ps auxf

# Дерево с использованием ASCII-графики и PPID (GNU/SystemV)
ps -ef --forest
```

### Работа с потоками (Threads)

В Linux потоки (LWP) являются отдельными задачами в ядре. Стандартный `ps` скрывает их, объединяя в один процесс.

```bash
# Показать все потоки конкретного процесса (LWP — Light Weight Process)
ps -L -p <PID>

# Вывести все процессы и все их потоки в системе
ps -eLf
```

### Кастомный формат вывода (для автоматизации)

Использование `-o` позволяет создавать отчеты, пригодные для парсинга.

```bash
# Вывод без заголовков (удобно для циклов в bash)
ps -h -o pid,comm

# Форматирование ширины столбцов и задание своих имен
ps -eo pid,user,comm:20,etime="UPTIME"

# Получение реального (ruid) и эффективного (euid) владельца
ps -eo pid,ruid,euid,comm

# Проверка Linux Capabilities процесса
ps -eo pid,comm,caps
```

### Мощный поиск и фильтрация

```bash
# Найти процессы по эффективному пользователю (UID/Name)
ps -u username

# Найти процессы по реальному пользователю (RUID)
ps -U username

# Найти процессы по группе
ps -G groupname

# Найти все процессы, КРОМЕ указанного пользователя (инверсия)
ps -U root -u root -N

# Найти процессы по PID или списку PID
ps -p 1234,5678,9012
```

### Сценарии для SRE / DevOps / Sysadmin

#### Сценарий 1: Быстрый Health-check сервиса

```bash
# Проверка, что сервис запущен и работает
SERVICE="nginx"
PIDS=$(ps -C $SERVICE -o pid= | wc -l)
if [ "$PIDS" -gt 0 ]; then
    echo "$SERVICE running: $PIDS processes"
else
    echo "$SERVICE NOT running"
fi
```

#### Сценарий 2: Поиск процессов с нетипичным потреблением CPU

```bash
# Найти процессы, потребляющие более 80% CPU в момент вызова
ps -eo pid,user,%cpu,comm --sort=-%cpu | awk 'NR==1 || $3 > 80'
```

#### Сценарий 3: Поиск процессов, запущенных от имени root

```bash
# Найти все root-процессы с их命令行
ps -U root -u root -o pid,etime,cmd
```

#### Сценарий 4: Проверка наличия зомби-процессов

```bash
# Количество зомби в системе
ps -eo stat | grep -c '^Z'
# → 0 (в норме)
```

Подробнее о механике работы с зомби см. в [**Руководстве по отладке процессов**](../../Core/processes/Troubleshooting/index.md#устранение-зомби-и-сирот).

#### Сценарий 5: Проверка реального бинарника процесса

Строка процесса в `ps` берется из `argv[0]` и может быть подменена. Для проверки реального пути используйте `/proc/PID/exe`:

```bash
# Реальный путь к бинарнику
readlink -f /proc/<PID>/exe
# → /usr/sbin/nginx

# Проверка на подмену: если бинарник в /tmp/ или /dev/shm/ — это подозрение
readlink -f /proc/<PID>/exe | grep -E '^/tmp/|/dev/shm/'
```

Подробнее см. в [**Виртуальной файловой системе /proc**](../../FileSystems/virtual_fs_proc.md#идентификация-реального-исполняемого-файла-процесса).

## Диагностика инцидентов (Incident Response)

### Workflow для SRE при алерте Load Average

При срабатывании алерта по Load Average используйте `ps` для идентификации виновника:

```bash
# Этап 1: Быстрая оценка
uptime
# → load average: 12.50 10.30 8.20 — сравните с nproc

# Этап 2: Топ-потребителей CPU
ps -eo pid,user,%cpu,%mem,stat,comm --sort=-%cpu | head -n 10

# Этап 3: Топ-потребителей памяти
ps -eo pid,user,rss,vsz,stat,comm --sort=-rss | head -n 10

# Этап 4: Проверка D-state процессов (если LA растёт, но CPU свободен)
ps -eo pid,stat,wchan:20,comm | awk '$2~/D/'
```

Для глубокого анализа состояний D см. [**Невидимый ввод-вывод**](../../Diagnostics/Performance/DiskIO/invisible_io.md#интерпретация-каналов-ожидания-wchan).

### Аудит безопасности

#### Выявление подозрительных процессов

```bash
# Поиск процессов, запущенных из нестандартных путей
ps -eo pid,user,comm,args | grep -E '/tmp/|/dev/shm/|/var/tmp/'

# Поиск процессов, маскирующихся под системные
ps -eo pid,user,comm | awk '$2 != "root" && $2 != "systemd" && $3 ~ /^[a-z]+$/'

# Проверка capabilities у всех процессов
ps -eo pid,user,comm,caps | grep -v '=ep'
```

#### Анализ удалённых сессий

```bash
# Все процессы с удалёнными сессиями
ps -eo pid,user,tty,stat,start,cmd | grep -E 'pts/|ssh|mosh'
```

## Мониторинг и автоматизация

### Скрипт для SRE: Мониторинг бездействия

```bash
#!/bin/bash
# idle_process_monitor.sh — мониторинг процессов, неактивных более N секунд

THRESHOLD=3600  # 1 час в секундах
ps -eo pid,user,etime,stat,comm --no-headers | while read PID USER ETIME STAT COMM; do
    # ETIME формат: [[DD-]HH:]MM:SS
    SECONDS=$(echo $ETIME | awk -F: '{if (NF==3) print $1*3600+$2*60+$3; else if (NF==2) print $1*60+$2; else print $1}')
    if [ "$SECONDS" -gt "$THRESHOLD" ] && [[ "$STAT" =~ ^S ]]; then
        echo "IDLE: PID=$PID USER=$USER ETIME=$ETIME COMM=$STAT $COMM"
    fi
done
```

### Интеграция с journald

```bash
# Сопоставление PID с последними логами journald
ps -eo pid,comm | tail -n +2 | while read PID COMM; do
    echo "=== $PID ($COMM) ==="
    journalctl _PID=$PID -n 5 --no-pager 2>/dev/null || echo "No logs"
done
```

### Автоматический отчёт по ресурсам

```bash
#!/bin/bash
# process_snapshot.sh — snapshot для архивации

OUTFILE="/var/log/process_snapshots/ps_$(date +%Y%m%d_%H%M%S).txt"
mkdir -p "$(dirname "$OUTFILE")"

{
    echo "=== Snapshot: $(date) ==="
    echo "--- System ---"
    uptime
    echo "--- Top CPU ---"
    ps -eo pid,user,%cpu,%mem,stat,comm --sort=-%cpu | head -n 11
    echo "--- Top MEM ---"
    ps -eo pid,user,rss,vsz,stat,comm --sort=-rss | head -n 11
    echo "--- Zombies ---"
    ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/'
    echo "--- D-state ---"
    ps -eo pid,stat,wchan:20,comm | awk '$2 ~ /D/'
} > "$OUTFILE"
```

## Валидация и верификация

### Проверка корректности utmp

```bash
# Проверить целостность базы utmp
sudo utmpdump /var/run/utmp
# → Должен показать корректные временные метки и типы записей

# Сравнить utmp с wtmp (исторические сессии)
sudo utmpdump /var/log/wtmp | tail
```

### Сравнение `w` и `ps`

```bash
# Активные сессии (кроме собственных)
ps -eo pid,user,tty,stat,cmd | grep -v '^.*$$' | grep -E 'pts/|tty[0-9]'

# Все пользователи с терминалами
ps -eo user,tty | sort | uniq
```

Для детального мониторинга пользовательских сессий см. [**Мониторинг пользователей и сессий**](../../SystemAdministration/Users/user_monitoring.md#мониторинг-активных-сессий).

## Рекомендации и очистка

### Best Practices

1. **Комбинируйте `ps` с `top` для динамики.** `ps` дает snapshot, `top` — тренды.
2. **Коррелируйте Load Average с типами процессов.** Высокий LA + много `D-state` = I/O проблема. Высокий LA + много `R` = CPU проблема.
3. **Используйте `ps -eo` вместо `ps aux` в скриптах.** Гибкий формат `-o` позволяет точно контролировать вывод и избегать проблем с парсингом.
4. **Проверяйте реальный бинарник через `/proc/PID/exe`.** Строка `CMD` в `ps` может быть подменена.
5. **Не доверяйте `WHAT` blind.** В некоторых реализациях `ps` показывает только первые 80 символов командной строки.

### Очистка

```bash
# Завершение зависшей сессии (если пользователь отключился некорректно)
sudo loginctl terminate-session <SESSION_ID>

# Очистка битых записей в utmp (осторожно!)
sudo utmpdump /var/run/utmp > /tmp/utmp_clean.txt
sudo cp /tmp/utmp_clean.txt /var/run/utmp
```

## Траблшутинг и диагностика

### Типичные ошибки и их причины

| Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| `ps` показывает только текущего пользователя | Включен `hidepid=2` в `/proc` | `grep hidepid /proc/mounts` | Используйте `sudo` или отключите `hidepid` для диагностики |
| В поле `FROM` отображается `-` для SSH | DNS-резолвинг отключен (`UseDNS no` в sshd_config) | `ssh -vv localhost` | Настройте `UseDNS no` или используйте IP-адреса |
| `ps aux` медленно работает на большом количестве процессов | Слишком много процессов (>10k) | `ps -eo pid | wc -l` | Используйте `ps -C <name>` для фильтрации по имени |
| `%CPU` показывает 0 для активного процесса | Слишком короткое время жизни процесса | `ps -p PID -o pid,%cpu,etime` | Используйте `top` для динамического наблюдения |
| `ps` не показывает процессы в контейнере | Namespace изоляция | `ls /proc/<PID>/ns` | Используйте `nsenter` или `docker exec` |

### Отдельные кейсы

#### Кейс 1: Процесс не виден в `ps aux`, но порт занят

Признак: процесс существует, но `ps aux | grep <name>` ничего не показывает.

```bash
# Причина 1: hidepid=2
grep hidepid /proc/mounts

# Причина 2: процесс в другом namespace (контейнер)
ls -la /proc/<PID>/ns

# Причина 3: argv[0] изменён, а поиск по имени не срабатывает
ps -eo pid,args | grep -v grep | head
```

#### Кейс 2: Разница между `ps` и `top` по %CPU

`ps` считает `%CPU` как `(время_cpu / время_жизни) * 100`. Для процесса, запущенного 1 секунду назад и использовавшего 0.5с CPU, `ps` покажет 50%, хотя в данный момент он простаивает.

```bash
# Для реального моментального %CPU используйте:
top -b -n 1 | grep <PID>

# Или mpstat для общего CPU
mpstat -P ALL 1 1
```

#### Кейс 3: Древовидный вывод показывает разрыв иерархии

Если `ps auxf` или `ps -ef --forest` показывают разрывы (процесс без родителя), это может быть вызвано:
1. Родитель завершился, и PID был переиспользован.
2. Процесс создан через `clone()` с флагом `CLONE_PARENT`.
3. PID namespace изоляция в контейнере.

```bash
# Проверка PPID и starttime для подтверждения переиспользования PID
ps -eo pid,ppid,lstart,comm | grep <PID>
```

### Ограничения

- **Snapshot-эффект:** `ps aux` показывает состояние на момент вызова. Для динамики используйте `top` или `pidstat`.
- **Расчет %CPU:** В отличие от `top`, `ps` рассчитывает `%cpu` как `(время_cpu / время_жизни_процесса) * 100`. Для только что запущенного тяжелого процесса значение будет расти постепенно.
- **Точность памяти:** `ps` оперирует RSS, что может вводить в заблуждение при работе с разделяемыми библиотеками. Для точного анализа используйте `smem`.
- **Длина аргументов:** В некоторых реализациях `ps` обрезает командную строку (обычно до 80 или 4096 символов). Полную командную строку читайте из `/proc/PID/cmdline`.
- **Скрытые процессы:** При монтировании `/proc` с опцией `hidepid=2` обычный пользователь видит только свои процессы. Подробнее см. в [**Виртуальной файловой системе /proc**](../../FileSystems/virtual_fs_proc.md#параметр-hidepid).

### Ограничения и крайние случаи

- **GUI-сессии:** В графических окружениях (GNOME, KDE) `ps aux` показывает сотни процессов, связанных с compositor, polkit, dconf и т.д. Фильтруйте по ключевым словам для целевых служб.
- **Контейнеры:** Внутри контейнера `ps` показывает только процессы этого namespace. Для просмотра всех процессов хоста используйте `ps` на хосте или `nsenter`.
- **Масштаб:** На системах с >10k процессами `ps aux` может занимать noticeable время. Используйте `ps -C <name>` или фильтрацию по UID.
- **PTY/TTY:** В systemd-сервисах без `StandardInput=tty` поле TTY будет `?`. Это нормально для демонов.
- **tmux/screen:** Процессы внутри tmux/screen имеют свои PTY. `ps` показывает их корректно, но `w`/`who` может не отображать логин, если сессия detached.
- **NFS/D-state:** Процессы в состоянии D, ожидающие NFS, могут «заморозить» систему. `ps` показывает их, но убить нельзя — требуется восстановление сети или reboot. Подробнее см. в [**Невидимом вводе-выводе**](../../Diagnostics/Performance/DiskIO/invisible_io.md).
- **io_uring:** Современные приложения, использующие `io_uring`, могут не генерировать классических D-state. `ps` покажет их в состоянии `S` или `R`, несмотря на активный I/O.
- **PID переиспользование:** После завершения процесса его PID может быть назначен новому. Для идентификации используйте `/proc/PID/starttime` или `pidfd` (Linux 5.3+).

## Современные альтернативы

Классический `ps` остаётся незаменимым для скриптов и статических снапшотов, но для интерактивного поиска процессов в 2026 году есть более удобные аналоги.

### procs

**`procs`** — современный заменитель `ps` на Rust. Показывает процессы с цветами и деревом, TCP/UDP-порты, I/O и имя Docker-контейнера.

```bash
cargo install procs

# Дерево процессов
procs --tree

# Сортировка по CPU (по убыванию)
procs --sortd cpu

# Живой режим, как top
procs --watch-interval 1
```

**Когда выбирать:** десктопы и серверы с Rust-окружением, когда нужен красивый интерактивный просмотр с деревом и портами.

### bcc / bpftrace

Набор утилит из [bcc](https://github.com/iovisor/bcc) цепляется к ядру через eBPF и показывает события в реальном времени:

```bash
# Новые exec() и короткоживущие команды (ps их не видит)
sudo execsnoop

# Кто какие файлы открывает
sudo opensnoop

# Топ по TCP-трафику, как iotop для сети
sudo tcptop
```

`execsnoop` особенно полезен для дебага кронов и воркеров: `ps` не видит процесс, который родился и умер между двумя опросами, а `execsnoop` — видит. Из минусов — нужны свежие ядра и root.

### pidstat

**`pidstat`** из пакета `sysstat` показывает CPU, I/O и память по отдельным процессам с интервалами. Подходит для регулярного сбора через cron.

```bash
# CPU, память и I/O каждые 2 секунды
pidstat 2

# Только процессы с не-idle состоянием
pidstat -w -p ALL 1
```

Подробнее: [Утилита pidstat](./pidstat.md).

### Внешние системы и панели

- **[Webmin](https://webmin.com/docs/modules/running-processes/)** — модуль Running Processes позволяет через браузер смотреть дерево процессов, искать по владельцу или командной строке, сортировать по CPU и завершать процессы.
- **[Monit](https://github.com/skynet/monit)** — следит за процессами, файлами, файловыми системами и хостами, умеет реагировать на условия и автоматически перезапускать сервис.
- **[Netdata](https://github.com/netdata/netdata)** — собирает CPU, RAM, диски, сеть, приложения, контейнеры и другие метрики с секундной детализацией и хранит историю.
