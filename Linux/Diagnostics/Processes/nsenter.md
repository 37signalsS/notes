# Утилита `nsenter`

## Определения

**`nsenter`** (namespace enter) — системная утилита из пакета `util-linux`, предназначенная для выполнения команд в контексте уже существующих пространств имен (namespaces). Она является основным инструментом «входа» в изолированное окружение процесса без использования специализированных средств оркестрации (таких как `docker exec` или `kubectl exec`).

В контексте контейнеризации `nsenter` позволяет заглянуть внутрь namespace работающего контейнера напрямую с хоста, когда `docker exec` недоступен: в образе отсутствует shell, userspace сломан, или контейнерный runtime не может запустить новый процесс.

Утилита работает на базе системного вызова `setns(2)`, который позволяет текущему потоку переключиться в указанное пространство имен.

## Основные концепции

### Принцип работы

Ядро Linux представляет каждое пространство имён как объект в виртуальной файловой системе `nsfs`. Доступ к нему осуществляется через символические ссылки в `/proc/<PID>/ns/`. Inode-номера этих ссылок служат **уникальными идентификаторами** пространств имён в системе.

```bash
# Просмотр пространств имён процесса
ls -l /proc/<PID>/ns/
# → lrwxrwxrwx 1 root root 0 Sep  6 12:00 net -> 'net:[4026531840]'
# → lrwxrwxrwx 1 root root 0 Sep  6 12:00 mnt -> 'mnt:[4026531841]'
```

Сравнение inode-номеров позволяет определить, разделяют ли процессы одно пространство имён:

```bash
readlink /proc/$PID1/ns/net
readlink /proc/$PID2/ns/net
```

### Жизненный цикл пространства имён

Пространство имён существует до тех пор, пока на него существует хотя бы одна ссылка:
- **Процессы**, находящиеся в пространстве имён.
- **Bind-mounts** файлов дескрипторов из `/proc/PID/ns/` (используется для персистентности, например в `ip netns`).
- **Дочерние пространства имён**, если родительское не уничтожено.

Когда счётчик ссылок достигает нуля, ядро освобождает пространство имён. Поэтому при отладке важно убедиться, что целевой процесс всё ещё существует, иначе его PID может быть переиспользован, а namespace — уничтожен.

### Системный вызов `setns(2)`

В отличие от `clone(2)`, создающего новый namespace, `setns(2)` позволяет **присоединиться** к уже существующему пространству имён через его файловый дескриптор:

```bash
# Открытие fd сетевого пространства контейнера
sudo nsenter --net=/proc/$PID/ns/net -- ip addr show
```

Этот вызов лежит в основе работы `nsenter`, `docker exec` и `kubectl exec`.

### Требования к привилегиям

Для переключения в пространство имен `nsenter` требует доступа к файловым дескрипторам в `/proc/[pid]/ns/`. Поэтому для работы с процессами других пользователей требуются права **root**.

На уровне ядраLinux переключение namespace для чужого процесса требует capability `CAP_SYS_ADMIN` в текущем namespace. В современных дистрибутивах возможность использования `ptrace` и `setns` для процессов, не являющихся дочерними, может быть ограничена механизмом **Yama LSM** (Linux Security Module), параметр `ptrace_scope`. Хотя `nsenter` напрямую не использует `ptrace`, ограничения `ptrace_scope` могут косвенно влиять на возможность отладки чужих процессов.

### Влияние User Namespace

Если целевой процесс находится в изолированном User Namespace, маппинг UID/GID может повлиять на восприятие прав. Процесс, который является rootом внутри своего User Namespace, на хосте может иметь непривилегированный UID. `nsenter` в этом случае будет работать, но с правами, соответствующими маппингу.

### Флаги выбора пространств имен

| Флаг | Тип (Namespace) | Описание |
| :--- | :--- | :--- |
| **`-m`**, **`--mount`** | Mount | Изолированное дерево каталогов и точек монтирования. |
| **`-u`**, **`--uts`** | UTS | Hostname и доменное имя. |
| **`-i`**, **`--ipc`** | IPC | Очереди сообщений, разделяемая память (POSIX/SysV). |
| **`-n`**, **`--net`** | Network | Сетевой стек (интерфейсы, маршруты, сокеты). |
| **`-p`**, **`--pid`** | PID | Дерево процессов (требует `--fork` для работы внутри). |
| **`-U`**, **`--user`** | User | Идентификаторы пользователей и групп (UID/GID). |
| **`-C`**, **`--cgroup`** | Cgroup | Видимость иерархии cgroups. |
| **`-T`**, **`--time`** | Time | Системные часы (Boottime/Monotonic). |

### Взаимодействие с cgroups

Хотя `nsenter` напрямую переключает только пространства имён, в современных системах cgroups тесно связаны с namespace. При входе в Mount Namespace (`-m`) и PID Namespace (`-p`) вы будете видеть cgroup-иерархию так, как она видна целевому процессу. Для полной диагностики cgroup-лимитов комбинируйте `nsenter` с чтением файлов в `/sys/fs/cgroup/`.

### Валидация после входа

После переключения namespace всегда проверяйте корректность окружения:

```bash
# Проверка namespace (сравнение inode)
readlink /proc/self/ns/net
readlink /proc/<оригинальный_PID>/ns/net

# Ожидается: одинаковые inode
```

Это предотвращает ошибки, когда `nsenter` не удался и команда выполнилась в исходном namespace.

## Практические сценарии

### 1. Отладка сети контейнера

Самый частый сценарий: в контейнере нет утилит `ip`, `tcpdump` или `ss`, но нужно проверить его сетевое состояние.

```bash
# Получить PID лидера контейнера
PID=$(docker inspect -f '{{.State.Pid}}' <container_id>)

# Посмотреть таблицу маршрутизации внутри контейнера
sudo nsenter -t $PID -n ip route show

# Захватить трафик интерфейса контейнера с хоста
sudo nsenter -t $PID -n tcpdump -i eth0 -w dump.pcap
```

### 2. Исследование файловой системы (Mount)

Позволяет увидеть иерархию монтирования именно так, как её видит процесс, включая приватные монтирования и `chroot`.

```bash
# Проверка mountinfo процесса
sudo nsenter -t $PID -m cat /proc/self/mountinfo
```

### 3. Полный вход в окружение (Shell)

Запуск командной оболочки, полностью переключенной во все пространства имен процесса.

```bash
# Вход во все основные неймспейсы (включая cgroup)
# --fork необходим для корректной работы PID namespace
sudo nsenter -t $PID -m -u -i -n -p -C --fork /bin/bash
```

### 4. Работа с именованными пространствами (ip netns)

`nsenter` может подключаться не только по PID, но и напрямую к файлам дескрипторов (bind mounts).

```bash
# Вход в сетевой namespace, созданный через iproute2
sudo nsenter --net=/var/run/netns/my_ns ip link show
```

### 5. Отладка Distroless и минимальных образов

В образах типа `distroless` или `scratch` отсутствует оболочка (`sh`/`bash`). `nsenter` позволяет запустить утилиты с хоста, «пробросив» их в контекст контейнера.

```bash
# Запуск ss с хоста, но в сетевом стеке контейнера
sudo nsenter -t $PID -n ss -lntp
```

### 6. Доступ к namespace работающего контейнера с хоста

Контейнер не обязан иметь shell внутри себя. Если приложение работает, но `docker exec` недоступен или сам контейнерный userspace сломан, namespace можно открыть непосредственно с хоста.

```bash
# 1. Находим PID основного процесса контейнера
PID=$(docker inspect -f '{{.State.Pid}}' <container>)
# → 4217

# 2. Проверяем его namespaces
ls -l /proc/4217/ns/
# → net  -> net:[4026532456]
# → mnt  -> mnt:[4026532457]
# → pid  -> pid:[4026532458]

# 3. Заходим сразу во все основные namespace
sudo nsenter -t 4217 -m -u -i -n -p -C --fork

# 4. Проверяем окружение
hostname
ip addr
mount
ps aux
```

При этом команды выполняются с host kernel, но видят изолированное окружение контейнера.

**Можно войти только в нужный namespace**, если проблема локализована:

```bash
# Сетевая конфигурация контейнера с хоста
sudo nsenter -t 4217 -n ip addr

# Его mount namespace
sudo nsenter -t 4217 -m mount
```

### 7. Вход в namespace systemd-сервиса

Systemd может запускать сервисы в изолированных namespace (через `PrivateNetwork=true`, `PrivateMounts=true` и другие флаги). Для диагностики сервиса без `systemctl exec` или `machinectl shell` используйте `nsenter`:

```bash
# Получить MainPID сервиса
PID=$(systemctl show --property=MainPID --value my-app.service)
# → 12847

# Войти в mount namespace сервиса
sudo nsenter -t $PID -m -- ls /app

# Войти в network namespace
sudo nsenter -t $PID -n -- ss -tlpn

# Полный вход (как systemd exec)
sudo nsenter -t $PID -m -u -i -n -p -- /bin/bash
```

### 8. Диагностика без контейнеризации (простые процессы)

`nsenter` полезен не только для контейнеров. Любой процесс, запущенный в отдельном namespace (например, через `unshare`), может быть исследован:

```bash
# Процесс запущен в изолированном netns через unshare
unshare -n -- ping 8.8.8.8 &
# → PID 5234

# Войти в его сетевой namespace с хоста
sudo nsenter -t 5234 -n -- ip addr show
# → видит только lo, без eth0
```

### 9. Автоматизация: вход в namespace по имени (ip netns)

Для скриптов, где PID неизвестен, используйте bind-mount namespace:

```bash
#!/bin/bash
# auto_nsenter.sh — универсальный вход в netns по имени
NS_NAME="${1:-default}"
CMD="${2:-ip addr show}"

if [ ! -d "/var/run/netns/$NS_NAME" ]; then
    echo "Namespace $NS_NAME не найден"
    exit 1
fi

sudo nsenter --net="/var/run/netns/$NS_NAME" -- $CMD
```

### 10. Проверка cgroup-лимитов контейнера

`nsenter` позволяет увидеть cgroup-иерархию глазами контейнера:

```bash
PID=$(docker inspect -f '{{.State.Pid}}' <container>)

# Войти в cgroup namespace
sudo nsenter -t $PID -C -- cat /proc/self/cgroup

# Проверить лимиты памяти (cgroups v2)
sudo nsenter -t $PID -m -- cat /sys/fs/cgroup/memory.max

# Проверить давление памяти (PSI)
sudo nsenter -t $PID -m -- cat /sys/fs/cgroup/memory.pressure
```

### 11. Отладка DNS внутри контейнера

Если контейнер не может резолвить имена, проверьте его DNS-конфигурацию через mount namespace:

```bash
PID=$(docker inspect -f '{{.State.Pid}}' <container>)

# Посмотреть resolv.conf глазами контейнера
sudo nsenter -t $PID -m -- cat /etc/resolv.conf

# Проверить /etc/hosts
sudo nsenter -t $PID -m -- cat /etc/hosts

# Запустить nslookup в контексте контейнера
sudo nsenter -t $PID -n -- nslookup kubernetes.default.svc.cluster.local
```

## Почему `nsenter` особенно полезен при авариях

`docker exec` фактически зависит от container runtime и возможности запустить новый процесс внутри контейнера. `nsenter` работает иначе: он использует namespace уже существующего процесса через `/proc/<PID>/ns`.

Поэтому если внутри контейнера сломан shell, отсутствуют утилиты или runtime не может выполнить exec, диагностику всё ещё можно проводить с хоста.

## Производительность и масштабирование

- **Накладные расходы:** Практически нулевые. Переключение namespace происходит на уровне дескрипторов задач (`task_struct`) и не требует TLB flush.
- **Время входа:** Зависит от скорости создания дочернего процесса (если используется `--fork`). Обычно занимает 1–10 мс.
- **Влияние на production:** `nsenter` безопасен для production. Он не останавливает целевой процесс (в отличие от `ptrace`/`strace`). Для критических сервисов использование разрешено без окон обслуживания.
- **Многопоточные процессы:** При входе в PID namespace с `--fork` создаётся дочерний процесс. Для анализа многопоточного приложения это не создаёт проблем, так как дочерний процесс наследует namespace.
- **Масштабирование:** На системах с >10k процессов поиск PID через `docker inspect` или `pgrep` может занять заметное время. Используйте `crictl` или `containerd` напрямую для более быстрого получения PID в Kubernetes-средах.

## Типичные ошибки и их решения

| Ошибка / симптом | Причина | Решение |
| :--- | :--- | :--- |
| `Permission denied` | Недостаточно прав (`CAP_SYS_ADMIN`) или SELinux/AppArmor блокирует `setns`. | Запустите от `root` или проверьте контекст безопасности. |
| `No such file or directory` | Процесс завершился, bind-mount удалён, или namespace не существует. | Проверьте `ps -p <PID>`; убедитесь, что bind-mount существует. |
| `reassociate to namespace failed` | Ядро не поддерживает данный тип NS или архитектурные ограничения. | Проверьте версию ядра и наличие соответствующих файлов в `/proc/[pid]/ns/`. |
| PID не меняется при входе в PID ns | Не используется флаг `--fork`. | При переключении PID namespace новый идентификатор получает только дочерний процесс. Добавьте `--fork`. |
| `Operation not permitted` для setuid-процесса | Ядро блокирует `setns` для setuid-binaries в некоторых конфигурациях. | Запустить `nsenter` от имени владельца процесса. |
| TUI отображается некорректно | Специфичная версия `ncurses` или размер окна. | Выполнить `reset` или `Ctrl+L` в целевом терминале. |
| Выход из shell не возвращает в исходный namespace | `nsenter` не изменяет namespace родительского процесса; дочерний процесс завершается. | Это ожидаемое поведение. Для постоянного переключения используйте `unshare`. |

## Ограничения

- **Требует root для чужих процессов:** Без привилегий `nsenter` работает только в namespace текущего пользователя.
- **PID Namespace + --fork:** При входе в PID namespace без `--fork` команда выполняется в исходном namespace, что приводит к неожиданному поведению.
- **User Namespace mapping:** Если целевой процесс находится в User Namespace с remapped UIDs, файлы и устройства могут отображаться с неожиданными правами.
- **SELinux/AppArmor:** Эти MAC-системы работают на уровне хоста. Даже внутри namespace процесс наследует политику хоста. При контейнеризации требуется явная маркировка.
- **Сетевые интерфейсы:** В новом net namespace интерфейс `lo` по умолчанию выключен (`state DOWN`). Необходимо явно `ip link set lo up`.
- **Setuid-программы:** Перехват процессов с установленным битом `setuid` может быть запрещён ядром.
- **Зомби и фоновые процессы:** `nsenter` не может перехватить процесс, который уже стал зомби (zombie, состояние `Z`) или находится в процессе завершения (exit state).
- **PID reuse:** Если целевой процесс завершился, а его PID был переиспользован другим процессом, `nsenter` войдёт в namespace неверного процесса. Всегда проверяйте PID перед входом (`ps -p <PID> -o pid,cmd`).
- **Time Namespace:** Доступен только на ядрах 5.6+. На старых системах флаг `-T`/`--time` будет проигнорирован или вызовет ошибку.
- **Невозможность входа в родительский namespace:** Если процесс уже находится в изолированном namespace, `nsenter` не позволит «вернуться» в родительский без знания его дескриптора.
- **Cgroup v2 иерархия:** В cgroup v2 иерархия cgroup namespace может отличаться от ожидаемой; `nsenter` показывает только видимость, а не лимиты.

## Сравнение с аналогами

| Метод | Когда использовать | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **`nsenter`** | Вход в существующее окружение процесса; отладка контейнеров/сервисов. | Минимальные зависимости, работа через ядро, доступ при сломанном userspace. | Требует root на хосте и известный PID; не изменяет namespace родительского shell. |
| [`lsns`](./lsns.md) | Обнаружение namespace и поиск PID. | Табличный вид, агрегация по NS ID, JSON-вывод. | Только инспекция, не выполняет команды. |
| **`unshare`** | Создание нового namespace. | Полная изоляция, не требует целевого процесса. | Не подходит для входа в существующее окружение. |
| **`docker exec`** | Удобство, интеграция с Docker API. | Удобство, интеграция с Docker API. | Зависит от runtime и наличия shell/утилит в образе; недоступен при авариях. |
| **`kubectl debug`** | Создание эфемерных контейнеров. | Нативно для K8s, инжекция sidecar. | Требует прав в RBAC; не работает без доступа к кластеру. |
| [CRIU](../../Core/processes/Troubleshooting/checkpoint_restore.md) | Сохранение и восстановление состояния процесса на диск. | Полный live-migrate, survives reboot. | Сложность настройки, не все приложения поддерживаются. |
| **`strace`/`gdb`** | Отладка syscalls или интерактивная отладка. | Глубокий анализ поведения процесса. | Требуют `ptrace`, что может быть заблокировано Yama LSM; останавливают процесс. |
