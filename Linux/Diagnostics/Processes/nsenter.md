# Утилита `nsenter`

## Определения

**`nsenter`** (namespace enter) — системная утилита из пакета `util-linux`, предназначенная для выполнения команд в контексте уже существующих пространств имен (namespaces). Она является основным инструментом «входа» в изолированное окружение процесса без использования специализированных средств оркестрации (таких как `docker exec` или `kubectl exec`).

В контексте контейнеризации `nsenter` позволяет заглянуть внутрь namespace работающего контейнера напрямую с хоста, когда `docker exec` недоступен: в образе отсутствует shell, userspace сломан, или контейнерный runtime не может запустить новый процесс.

Утилита работает на базе системного вызова `setns(2)`, который позволяет текущему потоку переключиться в указанное пространство имен.

## Основные концепции

### Механика работы

Для переключения в пространство имен `nsenter` требует доступа к файловым дескрипторам в `/proc/[pid]/ns/`. Поэтому для работы с процессами других пользователей требуются права **root**.

### Флаги выбора пространств имен

| Флаг | Тип (Namespace) | Описание |
| :--- | :--- | :--- |
| **`-m`**, **`--mount`** | Mount | Изолированное дерево каталогов и точек монтирования. |
| **`-u`**, **`--uts`** | UTS | Hostname и доменное имя. |
| **`-i`**, **`--ipc`** | IPC | Очереди сообщений, разделяемая память (POSIX/SysV). |
| **`-n`**, **`--net`** | Network | Сетевой стек (интерфейсы, маршруты, сокеты). |
| **`-p`**, **`--pid`** | PID | Дерево процессов (требует `--fork` для работы внутри). |
| **`-U`**, **`--user`** | User | Идентификаторы пользователей и групп (UID/GID). |
| **`-C`**, **`--cgroup`** | Cgroup | Видимость иерархии cgroups. |
| **`-T`**, **`--time`** | Time | Системные часы (Boottime/Monotonic). |

## Практические сценарии

### 1. Отладка сети контейнера

Самый частый сценарий: в контейнере нет утилит `ip`, `tcpdump` или `ss`, но нужно проверить его сетевое состояние.

```bash
# Получить PID лидера контейнера
PID=$(docker inspect -f '{{.State.Pid}}' <container_id>)

# Посмотреть таблицу маршрутизации внутри контейнера
sudo nsenter -t $PID -n ip route show

# Захватить трафик интерфейса контейнера с хоста
sudo nsenter -t $PID -n tcpdump -i eth0 -w dump.pcap
```

### 2. Исследование файловой системы (Mount)

Позволяет увидеть иерархию монтирования именно так, как её видит процесс, включая приватные монтирования и `chroot`.

```bash
# Проверка mountinfo процесса
sudo nsenter -t $PID -m cat /proc/self/mountinfo
```

### 3. Полный вход в окружение (Shell)

Запуск командной оболочки, полностью переключенной во все пространства имен процесса.

```bash
# Вход во все основные неймспейсы (включая cgroup)
# --fork необходим для корректной работы PID namespace
sudo nsenter -t $PID -m -u -i -n -p -C --fork /bin/bash
```

### 4. Работа с именованными пространствами (ip netns)

`nsenter` может подключаться не только по PID, но и напрямую к файлам дескрипторов (bind mounts).

```bash
# Вход в сетевой namespace, созданный через iproute2
sudo nsenter --net=/var/run/netns/my_ns ip link show
```

### 5. Отладка Distroless и минимальных образов

В образах типа `distroless` или `scratch` отсутствует оболочка (`sh`/`bash`). `nsenter` позволяет запустить утилиты с хоста, «пробросив» их в контекст контейнера.

```bash
# Запуск ss с хоста, но в сетевом стеке контейнера
sudo nsenter -t $PID -n ss -lntp
```

### 6. Доступ к namespace работающего контейнера с хоста

Контейнер не обязан иметь shell внутри себя. Если приложение работает, но `docker exec` недоступен или сам контейнерный userspace сломан, namespace можно открыть непосредственно с хоста.

```bash
# 1. Находим PID основного процесса контейнера
PID=$(docker inspect -f '{{.State.Pid}}' <container>)
# → 4217

# 2. Проверяем его namespaces
ls -l /proc/4217/ns/
# → net  -> net:[4026532456]
# → mnt  -> mnt:[4026532457]
# → pid  -> pid:[4026532458]

# 3. Заходим сразу во все основные namespace
sudo nsenter -t 4217 -m -u -i -n -p -C --fork

# 4. Проверяем окружение
hostname
ip addr
mount
ps aux
```

При этом команды выполняются с host kernel, но видят изолированное окружение контейнера.

**Можно войти только в нужный namespace**, если проблема локализована:

```bash
# Сетевая конфигурация контейнера с хоста
sudo nsenter -t 4217 -n ip addr

# Его mount namespace
sudo nsenter -t 4217 -m mount
```

## Почему `nsenter` особенно полезен при авариях

`docker exec` фактически зависит от container runtime и возможности запустить новый процесс внутри контейнера. `nsenter` работает иначе: он использует namespace уже существующего процесса через `/proc/<PID>/ns`.

Поэтому если внутри контейнера сломан shell, отсутствуют утилиты или runtime не может выполнить exec, диагностику всё ещё можно проводить с хоста.

## Траблшутинг и ограничения

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **`Permission denied`** | Недостаточно прав или SELinux/AppArmor блокирует `setns`. | Запустите от `root` или проверьте контекст безопасности. |
| **PID не меняется** | Не используется флаг `--fork` при входе в PID ns. | При переключении PID namespace новый идентификатор получает только дочерний процесс. Добавьте `--fork`. |
| **`nsenter: reassociate to namespace failed`** | Ядро не поддерживает данный тип NS или архитектурные ограничения. | Проверьте версию ядра и наличие соответствующих файлов в `/proc/[pid]/ns/`. |

## Дополнительная информация

### Сравнение с аналогами

| Инструмент | Преимущества | Недостатки / Когда выбирать |
| :--- | :--- | :--- |
| **`nsenter`** | Минимальные зависимости, работа через ядро, доступ при сломанном userspace контейнера. | Требует `root` на хосте и известный PID. |
| `docker exec` | Удобство, интеграция с Docker API. | Зависит от runtime и наличия shell/утилит в образе; недоступен при авариях. |
| `kubectl debug` | Создание эфемерных контейнеров. | Требует прав в RBAC; не работает без доступа к кластеру. |
| [`lsns`](./lsns.md) | Позволяет найти цель (PID/NS ID). | Только инспекция, не выполняет команды. |

### Важный нюанс

Namespace изолирует пространство имён, но не создаёт отдельное ядро. Процессы контейнера и хоста используют одно Linux kernel, просто смотрят на разные namespace. Это означает, что утилиты хоста (например, `ip` или `ss`) работают в контексте контейнера, но используют ядро хоста.
