# journalctl — Обзор и основные концепции

## Определения

**`journalctl`** — утилита командной строки, предназначенная для запроса, фильтрации и анализа системных журналов, собираемых службой `systemd-journald`. Является основным интерфейсом доступа к бинарному хранилищу логов в экосистеме `systemd`.

**`systemd-journald`** — системный демон, обеспечивающий централизованный сбор структурированных логов со всей операционной системы (ядро, системные службы, пользовательские приложения, stdout/stderr).

## Основные концепции

### Структурированное и централизованное логирование

В отличие от традиционных текстовых логов (например, в `/var/log/syslog`), `journalctl` работает с бинарным форматом, где каждое сообщение представляет собой набор пар `ключ=значение`.

**Преимущества подхода:**
- **Метаданные (Metadata):** К каждому сообщению автоматически привязывается контекст выполнения: PID, UID/GID, имя сервиса, исполняемый файл, идентификатор сессии и др.
- **Индексация:** Бинарный формат позволяет индексировать поля, что обеспечивает мгновенный поиск по времени или конкретным метаданным без полного сканирования файлов.
- **Целостность:** Бинарные файлы сложнее модифицировать незаметно, чем текстовые. Поддерживается криптографическая защита (FSS).

### Архитектура и хранение

`journalctl` считывает данные из файлов журнала, которые могут располагаться в двух местах:

| Тип хранения | Путь | Особенности |
| :--- | :--- | :--- |
| **Энергозависимое (Volatile)** | `/run/log/journal` | Хранится в RAM (tmpfs). Данные теряются после перезагрузки. Используется, если `/var/log/journal` недоступен. |
| **Постоянное (Persistent)** | `/var/log/journal` | Хранится на диске. Сохраняет историю между загрузками системы. |

Утилита использует механизм `mmap()` для отображения файлов журнала в память, что обеспечивает высокую производительность при чтении и фильтрации огромных объемов данных.

### Поля метаданных (Metadata Fields)

`journalctl` позволяет фильтровать логи по любым полям, хранящимся в журнале. Основные технические поля:

| Поле | Описание |
| :--- | :--- |
| `_PID` | Идентификатор процесса (Process ID). |
| `_UID` | Идентификатор пользователя (User ID). |
| `_COMM` | Имя исполняемого файла (короткое). |
| `_EXE` | Полный путь к исполняемому файлу. |
| `_SYSTEMD_UNIT` | Имя юнита systemd (сервиса), породившего лог. |
| `_BOOT_ID` | Уникальный ID текущей сессии загрузки. |
| `_TRANSPORT` | Метод передачи лога в демон (`driver`, `syslog`, `journal`, `stdout`, `kernel`). |
| `_MACHINE_ID` | Идентификатор локальной машины. |
| `PRIORITY` | Уровень важности сообщения (0–7). |

Полный список полей, доступных в текущем журнале, можно получить командой `journalctl --fields`.

### Уровни приоритета

Фильтрация по приоритету (`-p`) использует стандартные уровни syslog:

| Код | Уровень | Описание |
| :--- | :--- | :--- |
| 0 | **emerg** | Система непригодна для использования (паника). |
| 1 | **alert** | Требуется немедленное вмешательство. |
| 2 | **crit** | Критическое состояние. |
| 3 | **err** | Ошибки. |
| 4 | **warning** | Предупреждения. |
| 5 | **notice** | Нормальные, но важные события. |
| 6 | **info** | Информационные сообщения. |
| 7 | **debug** | Сообщения отладки. |

### Сессии загрузки (Boots)

Каждая перезагрузка системы помечается уникальным `_BOOT_ID`. Это позволяет `journalctl` обращаться к архивам логов прошлых сессий:
- `--list-boots`: Вывод списка всех доступных сессий с их ID и временем.
- `-b -1`: Просмотр логов предыдущей загрузки.
- `-b 0`: Логи текущей сессии.

### Безопасность и проверка целостности

1. **Права доступа:** Чтение журналов разрешено пользователю `root` и членам групп `systemd-journal`, `adm`, `wheel`.
2. **Forward Secure Sealing (FSS):** Технология цифровой подписи журнала. Если FSS включена (параметр `Seal=yes` в `journald.conf`), `journalctl` может верифицировать подлинность записей:
   - `journalctl --verify` — проверяет целостность текущих файлов.
   - `journalctl --verify --verify-key=<key>` — глубокая криптографическая проверка.

## Дополнительная информация

### Удаленное логирование (Remote Logging)

Хотя `journalctl` по умолчанию работает с локальными файлами, экосистема `systemd` включает компоненты для работы по сети:
- **`systemd-journal-upload`**: Передает локальные логи на удаленный сервер.
- **`systemd-journal-remote`**: Принимает логи от удаленных хостов и сохраняет их в бинарном формате journald.
- **`systemd-journal-gatewayd`**: Предоставляет HTTP/JSON интерфейс к логам для браузеров или внешних систем мониторинга.

### Производительность и оптимизация

- **Индексация:** `journalctl` всегда работает быстрее, если фильтрация выполняется по полям (`-u`, `-p`, `_PID=`) или по времени (`--since`), так как это задействует бинарные индексы. Текстовый поиск через `-g` (`--grep`) значительно медленнее, так как требует декомпрессии и парсинга каждого сообщения.
- **Сжатие:** По умолчанию файлы журнала сжимаются (LZ4 или XZ). Это экономит место на диске, но может немного замедлять доступ при чтении очень старых архивов.
