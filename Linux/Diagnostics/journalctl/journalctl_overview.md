# journalctl — Обзор и основные концепции

## Определения

**`journalctl`** — утилита командной строки, предназначенная для запроса, фильтрации и анализа системных журналов, собираемых службой `systemd-journald`. Является основным интерфейсом доступа к бинарному хранилищу логов в экосистеме `systemd`.

**`systemd-journald`** — системный демон, обеспечивающий централизованный сбор структурированных логов со всей операционной системы (ядро, системные службы, пользовательские приложения, stdout/stderr).

**Journal File** — бинарный файл журнала. Бывает двух типов: **активный** (файл, в который в данный момент ведется запись) и **архивный** (закрытый файл только для чтения). Механизм очистки (`vacuum`) никогда не удаляет активные файлы.

**Boot ID** — уникальный 128-битный идентификатор, присваиваемый системе при каждой загрузке. Хранится в `/proc/sys/kernel/random/boot_id` и используется journald для маркировки записей, принадлежащих конкретной сессии загрузки.

**Курсор (Cursor)** — уникальный строковый указатель на конкретную запись в журнале. Используется в автоматизации для продолжения чтения логов с момента последней обработки, исключая дубликаты или пропуски.

**Пространство имён (Namespace)** — механизм изоляции логов (введен в systemd 245), позволяющий разделять системный журнал и журналы конкретных приложений или контейнеров.

**Ограничение частоты (Rate Limiting)** — механизм journald, который подавляет дублирующиеся сообщения при превышении порога `RateLimitBurst` за интервал `RateLimitIntervalSec`. Важен для предотвращения переполнения хранилища при циклических ошибках.

## Основные концепции

### Жизненный цикл журнала

Понимание жизненного цикла журнала необходимо для диагностики и планирования емкости:

1. **Сбор (Collection):** journald перехватывает логи через `/dev/kmsg` (ядро), Unix-сокеты systemd, `stdout`/`stderr` сервисов и сокет `/dev/log` (совместимость с syslog).
2. **Индексация:** К каждому сообщению добавляются метаданные: PID, UID, GID, имя сервиса, исполняемый файл, Boot ID и др. Поля заполняются ядром или systemd, что исключает подмену отправителя.
3. **Запись:** Сообщение записывается в текущий активный файл журнала.
4. **Ротация:** При достижении лимитов размера или времени активный файл закрывается и становится архивным. Создается новый активный файл.
5. **Очистка (Vacuum):** Архивные файлы удаляются по критериям размера, времени или количества согласно настройкам `journald.conf` или ручным командам `vacuum`.

### Структурированное и централизованное логирование

В отличие от традиционных текстовых логов (например, в `/var/log/syslog`), `journalctl` работает с бинарным форматом, где каждое сообщение представляет собой набор пар `ключ=значение`.

**Преимущества подхода:**
- **Метаданные (Metadata):** К каждому сообщению автоматически привязывается контекст выполнения: PID, UID/GID, имя сервиса, исполняемый файл, идентификатор сессии и др.
- **Индексация:** Бинарный формат позволяет индексировать поля, что обеспечивает мгновенный поиск по времени или конкретным метаданным без полного сканирования файлов.
- **Целостность:** Бинарные файлы сложнее модифицировать незаметно, чем текстовые. Поддерживается криптографическая защита (FSS).

### Архитектура и хранение

`journalctl` считывает данные из файлов журнала, которые могут располагаться в двух местах:

| Тип хранения | Путь | Особенности |
| :--- | :--- | :--- |
| **Энергозависимое (Volatile)** | `/run/log/journal` | Хранится в RAM (tmpfs). Данные теряются после перезагрузки. Используется, если `/var/log/journal` недоступен. |
| **Постоянное (Persistent)** | `/var/log/journal` | Хранится на диске. Сохраняет историю между загрузками системы. |

Утилита использует механизм `mmap()` для отображения файлов журнала в память, что обеспечивает высокую производительность при чтении и фильтрации огромных объемов данных.

**Организация файлов на диске:**
- Файлы размещаются в подкаталогах по `Machine ID`: `/var/log/journal/<machine-id>/`.
- Имена файлов: `system.journal` (системные логи), `user-<UID>.journal` (пользовательские), `system@<hash>.journal` (архивные сессии).
- journald автоматически определяет режим хранения при загрузке: если существует `/var/log/journal`, используется постоянное хранилище.

### Поля метаданных (Metadata Fields)

`journalctl` позволяет фильтровать логи по любым полям, хранящимся в журнале. Поля делятся на две категории:

- **Системные поля** (заполняются ядром или systemd): `_PID`, `_UID`, `_COMM`, `_EXE`, `_SYSTEMD_UNIT`, `_BOOT_ID`, `_MACHINE_ID`, `_TRANSPORT`, `SYSLOG_IDENTIFIER`, `SYSLOG_FACILITY`, `SYSLOG_PID`.
- **Поля сообщений** (заполняются приложением): `MESSAGE`, `MESSAGE_ID`, `PRIORITY`, `CODE_FILE`, `CODE_LINE`.

Основные технические поля:

| Поле | Описание | Источник |
| :--- | :--- | :--- |
| `_PID` | Идентификатор процесса (Process ID). | Ядро / systemd |
| `_UID` | Идентификатор пользователя (User ID). | Ядро / systemd |
| `_COMM` | Имя исполняемого файла (короткое). | Ядро / systemd |
| `_EXE` | Полный путь к исполняемому файлу. | systemd |
| `_SYSTEMD_UNIT` | Имя юнита systemd (сервиса), породившего лог. | systemd |
| `_BOOT_ID` | Уникальный ID текущей сессии загрузки. | Ядро |
| `_TRANSPORT` | Метод передачи лога в демон (`driver`, `syslog`, `journal`, `stdout`, `kernel`). | journald |
| `_MACHINE_ID` | Идентификатор локальной машины. | systemd |
| `PRIORITY` | Уровень важности сообщения (0–7). | Приложение / syslog |
| `MESSAGE_ID` | Уникальный идентификатор типа сообщения (128-битный UUID). | Приложение |

Полный список полей, доступных в текущем журнале, можно получить командой `journalctl --fields`.

### Уровни приоритета

Фильтрация по приоритету (`-p`) использует стандартные уровни syslog (RFC 5424):

| Код | Уровень | Описание |
| :--- | :--- | :--- |
| 0 | **emerg** | Система непригодна для использования (паника). |
| 1 | **alert** | Требуется немедленное вмешательство. |
| 2 | **crit** | Критическое состояние. |
| 3 | **err** | Ошибки. |
| 4 | **warning** | Предупреждения. |
| 5 | **notice** | Нормальные, но важные события. |
| 6 | **info** | Информационные сообщения. |
| 7 | **debug** | Сообщения отладки. |

Фильтр `-p` принимает как числовые значения, так и именованные уровни. При указании порогового уровня выводятся все сообщения с указанным и более высоким приоритетом.

### Сессии загрузки (Boots)

Каждая перезагрузка системы помечается уникальным `_BOOT_ID`. Это позволяет `journalctl` обращаться к архивам логов прошлых сессий:

- `--list-boots`: Вывод списка всех доступных сессий с их ID, индексом и временем начала.
- `-b -1`: Просмотр логов предыдущей загрузки.
- `-b 0`: Логи текущей сессии (по умолчанию).

Boot ID генерируется ядром при каждой загрузке и хранится в `/proc/sys/kernel/random/boot_id`. Это делает каждую сессию уникальной и позволяет коррелировать события, произошедшие во время одного цикла работы системы.

### Пространства имён (Namespaces)

В systemd 245+ появилась возможность изолировать логи с помощью пространств имен:

- В юнит-файле указывается `LogNamespace=<name>`.
- Запускается отдельный экземпляр `systemd-journald@<name>.service`.
- Логи хранятся в `/var/log/journal/<machine-id>.<name>/`.
- Настройки читаются из `/etc/systemd/journald@<name>.conf`.

**Применение:** изоляция логов контейнеров, многопользовательских окружений, критичных приложений от системного журнала.

### Безопасность и проверка целостности

1. **Права доступа:** Чтение журналов разрешено пользователю `root` и членам групп `systemd-journal`, `adm` (Debian/Ubuntu) или `wheel` (RHEL/Fedora).
2. **Forward Secure Sealing (FSS):** Технология цифровой подписи журнала. Если FSS включена (параметр `Seal=yes` в `journald.conf`), `journalctl` может верифицировать подлинность записей:
   - `journalctl --verify` — проверяет целостность текущих файлов.
   - `journalctl --verify --verify-key=<key>` — глубокая криптографическая проверка.
3. **Синхронизация:** `journalctl --sync` принудительно записывает данные из кэша на диск. Используется перед вакуумом или отключением питания.
4. **Доступ к пользовательским журналам:** Флаг `--user` позволяет просматривать логи сервисов, запущенных в контексте текущего пользователя. Для сервисов, работающих без активной сессии, включите lingering: `loginctl enable-linger <username>`.

## Практические сценарии

### Быстрый поиск ошибок сервиса

```bash
# Ошибки конкретного сервиса за последний час
journalctl -u nginx -p err --since "1 hour ago"

# Только критические ошибки за сегодня
journalctl -p crit --since today

# Поиск по шаблону в сообщениях
journalctl -u sshd --grep "Failed password"
```

### Анализ загрузки системы

```bash
# Все ошибки текущей загрузки
journalctl -b --priority=err

# Логи предыдущей загрузки (если доступны)
journalctl -b -1 --priority=warning

# Список всех доступных загрузок
journalctl --list-boots
```

### Мониторинг в реальном времени

```bash
# Логи сервиса в реальном времени
journalctl -u docker -f

# Отключение пейджера для скриптов
journalctl -u kubelet -f --no-pager

# Ограничение начального объема
journalctl -u app -f --lines=100
```

### Аудит и безопасность

```bash
# Все использования sudo конкретным пользователем
journalctl _COMM=sudo | grep username

# Попытки входа по SSH
journalctl -u sshd | grep "Failed password"

# События systemd-logind (создание/удаление сессий)
journalctl -u systemd-logind.service
```

### Корреляция событий по Boot ID

```bash
# Найти Boot ID проблемной загрузки
journalctl --list-boots

# Просмотреть события конкретного Boot ID
journalctl -b -1 _SYSTEMD_UNIT=network.target

# Сравнить поведение сервиса между загрузками
journalctl -b -1 -u app.service
journalctl -b -2 -u app.service
```

### Интеграция с контейнерами

```bash
# Логи конкретного контейнера (Docker с journald драйвером)
journalctl CONTAINER_NAME=myapp -n 50

# Ошибки контейнера
journalctl CONTAINER_NAME=myapp -p err

# Мониторинг kubelet
journalctl -u kubelet -f | grep -iE "probe|unhealthy"
```

### Автоматизация и SIEM

```bash
# Получение курсора для парсинга
journalctl --show-cursor -u app --since "1 hour ago"

# Продолжение чтения с последнего курсора
journalctl --after-cursor="s=1234567890abcdef;i=1;b=abcdef1234567890"

# Экспорт в JSON для парсинга
journalctl -u app --since "1h ago" -o json | jq '.MESSAGE'
```

## Дополнительная информация

### Удаленное логирование (Remote Logging)

Хотя `journalctl` по умолчанию работает с локальными файлами, экосистема `systemd` включает компоненты для работы по сети:

- **`systemd-journal-upload`**: Передает локальные логи на удаленный сервер через TLS или обычное TCP-соединение.
- **`systemd-journal-remote`**: Принимает логи от удаленных хостов и сохраняет их в бинарном формате journald. Может работать в режиме записи в архивные файлы или в оперативном режиме.
- **`systemd-journal-gatewayd`**: Предоставляет HTTP/JSON интерфейс к логам для браузеров или внешних систем мониторинга.

**Архитектура удаленного логирования:**
```
[Хост 1] --(journal-upload)--> [Центральный сервер: journal-remote]
[Хост 2] --(journal-upload)--> [Центральный сервер: journal-remote]
[Браузер/SIEM] --(HTTP/JSON)--> [Центральный сервер: journal-gatewayd]
```

### Производительность и оптимизация

- **Индексация:** `journalctl` всегда работает быстрее, если фильтрация выполняется по полям (`-u`, `-p`, `_PID=`, `--since`) или по времени, так как это задействует бинарные индексы. Текстовый поиск через `-g` (`--grep`) значительно медленнее, так как требует декомпрессии и парсинга каждого сообщения.
- **Сжатие:** По умолчанию файлы журнала сжимаются (LZ4 или XZ). Это экономит место на диске, но может немного замедлять доступ при чтении очень старых архивов.
- **Форматы вывода:** Для скриптов используйте `--output=cat` (минимальные накладные расходы) или `--output=json` (надежный парсинг). Избегайте `--output=short-precise` в автоматизации — он содержит нестандартные символы.
- **Курсоры:** При написании парсеров используйте `--show-cursor` и `--after-cursor`, чтобы гарантировать отсутствие пропусков при перезапуске сборщика.

### Взаимодействие с традиционными syslog-демонами

journald не заменяет rsyslog или syslog-ng, а может с ними сосуществовать:

- **ForwardToSyslog=yes** (в `journald.conf`): journald дублирует все сообщения в `/dev/log`, откуда их может подхватить rsyslog.
- **ForwardToSyslog=no** (по умолчанию в большинстве дистрибутивов): journald — единственный сборщик логов.
- **Использование rsyslog:** требуется, когда необходимо отправлять логи на внешний syslog-сервер, применять сложные фильтры или использовать троттлинг на стороне демона.

При интеграции Docker с journald убедитесь, что `ForwardToSyslog` настроен корректно, чтобы избежать дублирования логов контейнеров в `/var/log/syslog`.

### Известные ограничения

- **Энергозависимое хранение по умолчанию:** На свежеустановленных системах без `/var/log/journal` логи хранятся в RAM и теряются после перезаботки. Это частая причина «исчезновения» логов на новых серверах.
- **Отсутствие `_SYSTEMD_UNIT`:** Процессы, не запущенные через systemd (например, напрямую из cron или shell), могут не иметь поля `_SYSTEMD_UNIT`. Вместо него используйте `_COMM` или `_EXE`.
- **Регистр в `--grep`:** По умолчанию `--grep` (`-g`) чувствителен к регистру. Используйте `--grep-case-sensitive=false` для нечувствительного поиска.
- **Бинарные данные в полях:** Некоторые поля (например, `_CMDLINE`) могут содержать непечатаемые символы. При парсинге JSON учитывайте, что значения могут быть base64-encoded.
- **Ограничение частоты записи (Rate Limiting):** journald по умолчанию подавляет дублирующиеся сообщения. Если важные логи отсутствуют, проверьте настройки `RateLimitIntervalSec` и `RateLimitBurst` в `journald.conf`.
- **Версия systemd:** Некоторые функции (например, `--namespace`, `--output-fields`) доступны только в systemd 245+. Проверяйте версию: `journalctl --version`.
