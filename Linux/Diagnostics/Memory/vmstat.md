# vmstat — статистика виртуальной памяти

## Определения

**`vmstat`** (Virtual Memory Statistics) — классическая системная утилита командной строки (входит в пакет `procps-ng`), предназначенная для оперативного мониторинга состояния ресурсов системы. Она предоставляет моментальный снимок активности процессов, использования RAM, работы подкачки (swap), интенсивности ввода-вывода (I/O) и нагрузки на CPU.

## Основные концепции

### Механизм получения данных

Утилита является интерпретатором виртуальных файлов ядра:
- `/proc/meminfo` — данные о памяти.
- `/proc/stat` — общая статистика CPU и прерываний.
- `/proc/vmstat` — детальные счетчики виртуальной памяти.
- `/proc/slabinfo` — статистика Slab-аллокатора (для `-m`).

### Особенности вывода

- **Первая строка:** Всегда содержит **средние значения** с момента загрузки системы (`uptime`), а не текущие показатели. Для актуальной картины используйте интервальный режим.
- **Интервальный режим:** При запуске `vmstat 1` последующие строки показывают дельту (изменения) за последнюю секунду.
- **Широкий формат (-w):** Рекомендуется для современных систем с большим количеством ядер, чтобы избежать "съезда" колонок.

### CPU-утилизация: модель us / sy / id / wa / st

Столбцы CPU отражают распределение времени процессора за интервал:

- **us (user):** Пользовательское время — приложения в userspace. Высокий `us` (>80%) на многоядерной системе может означать либо один интенсивный процесс, либо слишком много worker-ов.
- **sy (system):** Системное время — обработка прерываний, системных вызовов, контекстных переключений. Постоянный `sy` > 25–30% указывает на накладные расходы ядра (например, высокая плотность контекстных переключений, active reclaim, cgroup throttling).
- **id (idle):** Простой CPU. Важно отличать истинный простой от `iowait`: при `id` > 0 и `wa` > 0 дисковая подсистема тормозит, а не CPU.
- **wa (iowait):** Время, потраченное на ожидание завершения операций ввода-вывода. `wa` — это не нагрузка на CPU, а сигнал от планировщика, что задачи готовы выполняться, но заблокированы на диске. Для локализации используйте `iostat` или `pidstat -d`.
- **st (steal):** Время, "украденное" у гостевой ВМ гипервизором. Показывает только на виртуализированных системах (KVM, VMware, Xen). На bare-metal `st` должен быть близок к 0. Постоянный `st` > 5% — признак overselling CPU на хосте или noisy neighbor.

### Процессы и очереди: r и b

- **r (runnable):** Количество процессов в состоянии `TASK_RUNNING` или `TASK_INTERRUPTIBLE`, готовых к выполнению, но ожидающих своей очереди на CPU. Если `r` стабильно превышает количество доступных ядер — система CPU-bound.
- **b (blocked / uninterruptible sleep):** Процессы в состоянии `TASK_UNINTERRUPTIBLE` (D-state). Обычно ожидают завершения дискового I/O, сетевых операций NFS или завершения работы драйвера. `b > 0` не всегда проблематично, но постоянный `b` > 2–3 на обслуживаемом приложении указывает на деградацию диска или сетевого хранилища.

### Память: free, cache и водяные знаки

Столбцы `free`, `buff` и `cache` в `vmstat` дают упрощенную картину:
- **free:** Полностью неиспользуемая RAM. На здоровой системе `free` близок к 0, потому что ядро использует свободную память для Page Cache.
- **buff** (buffers): Метаданные файловых систем (inode, dentry). В ядрах 2.6+ объединены с `cache` в единый счетчик.
- **cache:** Page Cache (файловый кэш). Высокое значение — нормально и желательно для I/O-нагруженных систем.

Для оценки реально доступной памяти используйте **MemAvailable** из `/proc/meminfo`. См. [`/proc/meminfo`](./proc_meminfo.md).

### Расшифровка ключевых полей

| Группа | Поле | Описание | Индикатор проблем |
| :--- | :--- | :--- | :--- |
| **procs** | `r` | Очередь выполнения (runnable). | `r > ядер CPU` — процессор перегружен. |
| | `b` | Процессы в Uninterruptible sleep. | `b > 0` — ожидание диска или сетевого I/O. |
| **memory** | `swpd` | Использованный Swap. | Рост при малом `available` — нехватка RAM. |
| | `free` | Полностью свободная память. | Близкое к 0 — норма при высоком `cache`. |
| | `buff` | Метаданные файловых систем. | — |
| | `cache` | Page Cache (файловый кэш). | Высокое значение — эффективно для I/O. |
| **swap** | `si` / `so` | Swap-in / Swap-out (страниц/с). | Постоянные значения > 0 — Memory Thrashing. |
| **io** | `bi` / `bo` | Blocks in/out (считано/записано). | Высокие значения при высоком `wa`. |
| **system** | `in` | Прерывания в секунду. | Аномальный рост — проблемы с драйверами. |
| | `cs` | Context Switches (переключения). | Высокий `cs` при низком CPU — лишние потоки. |
| **cpu** | `us` / `sy` | Время User / System. | Высокий `sy` (>30%) — накладные расходы ядра. |
| | `wa` | I/O Wait (ожидание диска). | `wa > 15%` — дисковая подсистема тормозит. |
| | `st` | Steal time (украденное время). | `st > 0` — гипервизор перегружен (Overselling). |

## Практические сценарии

### 1. Детальная статистика дисков (-d)

Показывает сводную статистику по всем блочным устройствам: количество чтений, записей и объединенных (merged) запросов.

```bash
vmstat -d
# Колонки: reads (total, merged, sectors, ms), writes (total, merged, sectors, ms), IO (cur, s)
```
- **ms (milliseconds):** Суммарное время, затраченное на чтение/запись. Позволяет косвенно оценить латентность.

### 2. Анализ конкретных разделов (-p)

Полезно для изоляции нагрузки на конкретный раздел (например, корень `/` vs `/data`).

```bash
# Базовые счетчики для раздела sda1
vmstat -p /dev/sda1
```

### 3. Диагностика Slab-аллокатора (-m)

Позволяет увидеть, какие структуры ядра (inode, dentry, сетевые буферы) потребляют память. Требует прав **root**.

```bash
sudo vmstat -m | sort -k 2 -nr | head -n 10
```
- **Cache:** Название кэша (например, `ext4_inode_cache`).
- **Num:** Количество активных объектов.
- **Total:** Общее количество выделенных объектов.
- **Pages:** Количество физических страниц под данный кэш.

### 4. Счетчик создания процессов (-f)

Показывает общее количество форков (`fork`, `vfork`, `clone`) с момента загрузки.

```bash
vmstat -f
# Полезно для поиска "fork-bomb" или скриптов, порождающих слишком много короткоживущих процессов.
```

### 5. Добавление временных меток (-t)

Критично при длительном мониторинге в лог-файл.

```bash
vmstat -t 5 > vmstat_monitor.log
```

### 6. Диагностика CPU-насыщения (r, cs, us, sy)

Сценарий для SRE: вы получили алерт по росту Load Average или latency. `vmstat 1` позволяет быстро понять, CPU-bound система или нет.

```bash
vmstat -w 1 10
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
#  8  0      0  20480  16384 8388608    0    0     0    50 1000 8000 45 10 45  0  0
```

**Интерпретация:**
- `r=8` при 4 ядрах — очередь в 2 раза длиннее доступного ресурса.
- `us=45%, sy=10%` — приложение активно работает, но ядерные накладные расходы не критичны.
- `cs=8000` — высокий контекст-свитч storm. Для локализации используйте `pidstat -w 1` или `perf top`.
- Если `r` высокий, но `us+sy` низкий (<30%), проверьте `wa` (I/O bound) или `b` (D-state).

**Корреляция с pidstat:**
```bash
# Найти процессы, генерирующие контекстные переключения
pidstat -w -u 1 5 | grep -E "PID|cs"
```

### 7. Анализ D-state и дисковых блокировок (b, wa)

Постоянные ненулевые значения в столбце `b` означают процессы в `TASK_UNINTERRUPTIBLE`. Это классический признак проблем с хранилищем (NFS,SAN, медленный диск).

```bash
# 1. Сначала видим подтверждение в vmstat
vmstat 1 5
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
#  2  4      0  10240  8192  4194304    0    0     0  8192  500 2000 10  5 85  0  0
# → b=4: 4 процесса заблокированы на диске

# 2. Находим конкретные PID в D-state
ps -eo pid,stat,wchan,comm | grep '^.* D '
# или
sudo iotop -oP
# → PID 2345  [kswapd0]  ожидает swap-операции
# → PID 3456  [java]     ожидает чтения с NFS
```

**Дифференциальная диагностика:**
- `wa` высокий, `b` низкий: диск перегружен, но процессы не блокируются надолго.
- `wa` высокий, `b` высокий: дисковые операции долгие (медленный диск, сетевой сбой).
- `wa` низкий, `b` высокий: процессы зависают в драйверах (например, NFS stale handle).

### 8. Долгосрочный мониторинг (логирование и CSV)

Для трендового анализа и построения графиков перенаправьте вывод `vmstat` в файл с таймстемпами.

```bash
# Мониторинг с таймстемпами (флаг -t) в CSV-подходящем формате
vmstat -t -n 5 > /var/log/vmstat.log

# Конвертация в CSV для анализа в pandas/Excel
vmstat -t 1 | awk 'NR==1 || NR%2==0' > vmstat_sample.log
```

**Интеграция с sar для исторических данных:**
```bash
# Включение сбора vmstat-подобных данных через sar (sysstat)
sar -u 1 100 > cpu.log          # CPU
sar -b 1 100 > paging.log       # Paging (page fault rate)
sar -r 1 100 > memory.log       # Memory
# Исторические данные за предыдущие дни
sar -u -f /var/log/sysstat/sa15
```

### 9. Корреляция с pidstat и ps (vmstat → процесс)

`vmstat` дает системную картину, но не показывает, *какой процесс* потребляет ресурсы. Стандартный SRE-пайплайн:

```bash
# Шаг 1: Обнаружение аномалии
vmstat 1 3
# → r=12, us=85%, wa=5%: CPU перегружен

# Шаг 2: Топ потребителей CPU
ps -eo pid,user,%cpu,%mem,comm --sort=-%cpu | head -n 10
# или
top -b -n 1 | head -n 20

# Шаг 3: Детальный анализ по процессу
pidstat -u -p ALL 1 5
# PID    %usr %system  %guest   %wait    %CPU   CPU  Command
# 4821   80.00    10.00    0.00    5.00   90.00     3  java

# Шаг 4: Контекстные переключения
pidstat -w -p 4821 1 5
# cswch/s: количество voluntary context switches
# nvcswch/s: количество non-voluntary context switches (вытеснение)
```

### 10. Визуализация через wide-режим и Active/Inactive память

На системах с >16 ядрами стандартный вывод `vmstat` "плывет". Используйте комбинацию флагов:

```bash
# Широкий формат + мегабайты + активная память
vmstat -w -S M -a 1
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
#  r  b   swpd   free   buff  cache  inact   act    si   so    bi    bo   in   cs us sy id wa st
#  4  0    512    128    256   2048  1024  4096     0    0     2   500  800 6000 20  5 75  0  0
```

- **inact (inactive):** Память, к которой давно не обращались. Первый кандидат на выгрузку в swap или удаление из кэша.
- **act (active):** Память, активно используемая процессами или кэшем.

### 11. Сценарий: виртуализация и steal time (st)

`vmstat` — один из немногих инструментов, который без дополнительных модулей показывает `st` (steal time).

```bash
# На хосте KVM/QEMU проверяйте steal time гостевой ОС
vmstat -w 1
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
#  2  0      0  40960  16384 524288    0    0     0    10  200  500 30 10 60  0  12.5
# → st=12.5%: гипервизор забирает 12.5% CPU-времени у этой ВМ
```

**Действия SRE:**
1. Проверьте нагрузку на хост-машину (`virsh nodecpuinfo`, `htop` на хосте).
2. Оцените overselling ratio: `vCPUs_total_guests /物理_cores`.
3. При `st > 5–10%` постоянный — запросите миграцию ВМ или увеличение guaranteed CPU.

## Трайблшутинг

### Первая строка всегда показывает средние с boot

Ошибка новичка: запустить `vmstat` без интервала и принять первую строку за текущее состояние.

```bash
# НЕПРАВИЛЬНО: интерпретация первой строки как "сейчас"
vmstat
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
#  0  0    512 1048576 491520 2048000    0    0     0     1  100  200  5  2 93  0  0
# → Всё выглядит идеально, но сервер уже 10 минут в огне. Это среднее с boot!
```

Всегда используйте интервальный режим для диагностики: `vmstat 1`.

### free близко к 0 — это не всегда проблема

На современном Linux `free` стремится к 0, потому что ядро использует свободную RAM для Page Cache. Индикатор проблем — **MemAvailable** в `/proc/meminfo`, а не столбец `free`.

```bash
# Сравнение vmstat и /proc/meminfo
vmstat -a 1
free -h
cat /proc/meminfo | grep -E "MemTotal|MemFree|MemAvailable|Buffers|Cached"
# free показывает 128M, но MemAvailable = 12G — это нормально.
```

### wa высокий, но iostat показывает низкий await

`wa` в `vmstat` — агрегированная метрика по всем дискам. Возможности:
1. Один диск перегружен, а остальные свободны (проверьте `iostat -xz 1`).
2. Ожидание не дисковое, а сетевое (NFS, CIFS). `vmstat` не отличает диск от сети.
3. Ожидание в блокирующих системных вызовах (futex, mutex). Проверьте `pidstat -w`.

### st > 0 на bare-metal сервере

Если `vmstat` показывает `st > 0` на физическом сервере без гипервизора — это баг или аппаратная проблема. Проверьте:
- Включен ли BIOS-параметр `Intel VT-x` / `AMD-V` без реальной виртуализации (некоторые чипсеты предодают ложные readings).
- Обновление microcode и ядра.

### r > cores, но us + sy < 30%

Система "зависла", но CPU простаивает. Причины:
1. **I/O bound:** `wa` высокий. Диск или сеть — узкое место.
2. **Memory bound:** `si`/`so` активный. Thrashing.
3. **Lock contention:** Процессы ожидают освобождения spinlock/mutex (kernel или userspace). Диагностика: `perf lock` или `bpftrace`.

## Best Practices

1. **Всегда используйте интервалы.** Одиночный запуск `vmstat` без аргументов почти бесполезен для диагностики — первая строка содержит средние с момента загрузки.
2. **Используйте `-w` на системах >8 ядер.** Без широкого формата колонки сливаются, особенно `cs`, `us`, `sy`.
3. **Комбинируйте с `pidstat` или `ps`.** `vmstat` отвечает на вопрос *что* происходит, `pidstat` — *кто* виноват.
4. **Для RAM используйте `MemAvailable`, а не `free`.** `free` в `vmstat` — устаревшая метрика. `/proc/meminfo` дает актуальную картину доступной памяти.
5. **Собирайте baseline** в "холодное" время (после разогрева, но до пика нагрузки). Сравнивайте текущие показатели с baseline, а не с абсолютными порогами.
6. **Мониторьте тренды, а не мгновенные значения.** Один `wa=30%` за 1 секунду не означает проблему. Постоянный `wa > 15%` в течение минут — это.
7. **В контейнерных средах учитывайте cgroup-лимиты.** `vmstat` показывает нагрузку на *хост*, а не внутри контейнера. Для контейнеров используйте `systemd-cgtop` или чтение `/sys/fs/cgroup/`.
8. **Для исторического анализа используйте `sar` вместо `vmstat`.** `vmstat` — для реального времени. Для трендов за часы/дни нужен `sar` (пакет `sysstat`).

## Типичные инциденты и их диагностика

### Инцидент 1: "Система тормозит, но CPU простаивает"

**Симптом:** `vmstat` показывает `r=12`, но `us+sy < 30%`. Сервис не отвечает.

**Диагностика:**
```bash
# Шаг 1: Определение типа bottleneck
vmstat -w 1 5
# → r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
# → 12 4      0  10240  8192  4194304    0    0     0  8192  500 2000 10  5 85  0  0
# → r=12, b=4, wa=0, si/so=0

# Шаг 2: Проверка PSI
cat /proc/pressure/memory
# → some avg10=0.00 avg60=0.00 avg300=0.00 total=0
# → full avg10=0.00 avg60=0.00 avg300=0.00 total=0

cat /proc/pressure/io
# → some avg10=45.23 avg60=38.12 avg300=25.00 total=123456789
```

**Причина:** `r=12` (очередь на CPU) при `us+sy < 30%` означает, что процессы готовы, но не могут выполняться. `b=4` указывает на блокировку в D-state. PSI I/O подтверждает проблему с диском.

**Ключевое:** `vmstat` показывает симптом (очередь), PSI — причину (I/O bottleneck). Всегда проверяйте PSI при неоднозначных значениях.

---

### Инцидент 2: "Swap активен, но free показывает много памяти"

**Симптом:** `vmstat` показывает `si/so > 0`, но `free -h` показывает `free: 8G`.

**Диагностика:**
```bash
# Шаг 1: Проверка swap activity
vmstat 1 5
# → si   so
# → 128  256   ← Активный swap

# Шаг 2: Проверка MemAvailable
grep -E "MemAvailable|MemFree|Cached" /proc/meminfo
# → MemAvailable:    8388608 kB  (8 ГБ)
# → MemFree:         1048576 kB  (1 ГБ)
# → Cached:         20971520 kB  (20 ГБ)

# Шаг 3: Проверка swappiness
cat /proc/sys/vm/swappiness
# → 60  ← Стандартное значение
```

**Причина:** Ядро активно выгружает неактивные страницы (Page Cache) в swap, даже при наличии `MemAvailable`. Это нормальное поведение при `swappiness=60`.

**Ключевое:** `si/so > 0` не означает проблему, если `MemAvailable` достаточный и латентность не растет. Проверяйте PSI memory для оценки реального давления.

---

### Инцидент 3: "Steal time > 0 на bare-metal сервере"

**Симптом:** `vmstat` показывает `st > 0`, но сервер не виртуализован.

**Диагностика:**
```bash
# Шаг 1: Проверка steal time
vmstat -w 1 5
# → st
# → 12.5  ← Критично!

# Шаг 2: Проверка виртуализации
cat /proc/cpuinfo | grep -i "hypervisor"
# → hypervisor: 0  ← bare-metal

# Шаг 3: Проверка BIOS
dmesg | grep -i "vmx\|svm"
# → VMX: disabled → BIOS не включил виртуализацию
```

**Причина:** `st > 0` на bare-metal указывает на ошибку конфигурации BIOS или драйверов. Возможна аппаратная проблема.

**Ключевое:** `st` должен быть 0 на bare-metal. Любое ненулевое значение — признак проблемы.

---

### Инцидент 4: "Context switches растут, но CPU не загружен"

**Симптом:** `vmstat` показывает `cs > 50000`, но `us+sy < 20%`.

**Диагностика:**
```bash
# Шаг 1: Проверка context switches
vmstat -w 1 5
# → cs
# → 85000  ← Высокий context switch storm

# Шаг 2: Поиск процессов-виновников
pidstat -w -u 1 5 | grep -E "PID|cs"
# → PID    %usr %system  %guest   %wait    %CPU   CPU  Command
# → 1234   2.00    3.00    0.00    0.00    5.00     0  nginx

# Шаг 3: Детальный анализ
pidstat -w -p 1234 1 10
# → cswch/s: voluntary context switches (ожидание I/O)
# → nvcswch/s: non-voluntary (вытеснение планировщиком)
```

**Причина:** Много мелких потоков или IPC-операций. `cswch` (voluntary) — ожидание I/O/ locks. `nvcswch` (non-voluntary) — вытеснение из-за истекшего кванта.

**Ключевое:** Высокий `cs` при низком CPU указывает на проблему с архитектурой приложения (лишние потоки, contention).

### Инцидент 5: "iowait высокий, но диск не нагружен"

**Симптом:** `vmstat` показывает `wa > 15%`, но `iostat` показывает низкую утилизацию.

**Диагностика:**
```bash
# Шаг 1: Проверка iowait
vmstat -w 1 5
# → wa
# → 25  ← Высокий iowait

# Шаг 2: Проверка дисков
iostat -xz 1 5
# → Device  r/s   w/s  await  %util
# → sda     5.00  10.00  3.50   15.00  ← Нормально!

# Шаг 3: Проверка NFS/сеть
mount | grep nfs
# → 192.168.1.10:/data on /data type nfs4

# Шаг 4: Проверка PSI I/O
cat /proc/pressure/io
# → some avg10=45.23 avg60=38.12 avg300=25.00 total=123456789
```

**Причина:** `wa` в `vmstat` — агрегированная метрика по всем дискам и сетевым I/O. Если локальный диск не нагружен, проблема в NFS/CIFS или другом сетевом хранилище.

**Ключевое:** `vmstat` не различает локальный диск и сеть. Используйте `iostat` для локальных дисков и `nfsstat`/`ps` для NFS.

## Дополнительная информация

### Взаимодействие с PSI (Pressure Stall Information)

Хотя `vmstat` показывает симптомы (очереди в `r`, ожидание в `wa`), он не дает понимания, **насколько сильно** страдают процессы. 
- Если `vmstat` показывает высокий `wa`, проверьте `/proc/pressure/io`.
- Если `vmstat` показывает активный `si/so`, проверьте `/proc/pressure/memory`.

### Полезные флаги форматирования

- `-S M`: Вывод в мегабайтах (удобнее для анализа RAM на современных серверах).
- `-n`: Вывести заголовок только один раз (удобно для конвейеров).
- `-a`: Показать активную/неактивную память (Active/Inactive) вместо Buffers/Cache.
- `-w`: Широкий формат (полезно на >8 ядер).
