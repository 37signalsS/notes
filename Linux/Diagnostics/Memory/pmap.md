# pmap — карта памяти процесса

## Определения

`pmap` (Process Memory Map) — системная утилита командной строки, входящая в пакет `procps-ng`, предназначенная для отображения подробной карты виртуальной памяти одного или нескольких процессов. Она визуализирует структуру адресного пространства, позволяя анализировать распределение сегментов кода, данных, библиотек и динамически выделяемой памяти.

**Назначение в контексте DevOps/SRE:**
- Быстрая идентификация аномально больших сегментов памяти (утечки, фрагментация).
- Анализ структуры адресного пространства для корреляции с ошибками `SIGSEGV`, `SIGBUS`.
- Диагностика конфликтов библиотек (Duplicate Symbol Resolution, PreLoading).
- Подготовка данных для принятия решений о перезапуске сервиса при утечке памяти.

## Основные концепции

### Внутреннее устройство pmap

Утилита является интерфейсом к виртуальной файловой системе `/proc`. Она агрегирует и форматирует данные из двух основных источников:
- `/proc/<PID>/maps`: Базовая информация об адресах, правах доступа и путях к файлам.
- `/proc/<PID>/smaps`: Детальная статистика по каждому сегменту (RSS, PSS, Swap и др.).

**Алгоритм работы:**
1. Утилита открывает `/proc/<PID>/maps` и читает список VMA (Virtual Memory Areas).
2. Для каждого VMA определяется источник: файловое отображение, анонимная память, системный сегмент.
3. При использовании флагов `-x`, `-X`, `-XX` открывается `/proc/<PID>/smaps` и извлекаются расширенные метрики.
4. Данные агрегируются и выводятся в табличном формате.

**Производительность:** Чтение `/proc/<PID>/smaps` имеет накладные расходы на порядок выше, чем чтение `/proc/<PID>/maps`, так как требует парсинга тысяч строк для процессов с большим количеством mmap-областей (например, JVM с классами, Go-приложения с большим числом goroutine stacks).

### Модель разрешений и доступ к /proc

Доступ к `/proc/<PID>/maps` ограничен владельцем процесса (или root). Доступ к `/proc/<PID>/smaps` требует дополнительных прав:

- **Владелец процесса:** может читать `maps` и `smaps` полностью.
- **Другой непривилегированный пользователь:** может читать только `maps`; `smaps` вернет нулевые значения для RSS/PSS.
- **Root:** полный доступ ко всем процессам.

**Практический эффект:**
```bash
# Без sudo: поля RSS/PSS будут нулевыми для чужих процессов
pmap -X 1234 | grep libc
# → 00007f3e8b0a1000   1812K    0K    0K   ...  (RSS=0 для чужого процесса)

# С sudo: полные данные
sudo pmap -X 1234 | grep libc
# → 00007f3e8b0a1000   1812K  1812K  512K   ...  (реальный RSS)
```

### Метки сегментов (Mapping Labels)

В выводе `pmap` часто встречаются специальные метки в колонке `Mapping`:
- `[stack]`: Основной стек процесса.
- `[stack:<TID>]`: Стек конкретного потока (Thread).
- `[heap]`: Динамическая память (куча), выделяемая через `brk()`.
- `[anon]`: Анонимная память. Сюда попадают данные, выделенные через `mmap()` (например, большие блоки `malloc`), а также области BSS.
- `[vvar]`: Данные ядра, доступные в userspace только для чтения (например, текущее время).
- `[vdso]`: Virtual Dynamic Shared Object — механизм ускорения системных вызовов.
- `[vsyscall]`: Устаревший механизм, аналогичный `vdso`.
- `[sysv]`: Сегмент разделяемой памяти System V IPC (`shmget`/`shmat`).
- `[aio]`: Анонимная память, выделенная для Linux AIO (Asynchronous I/O).

### Права доступа и флаги (Mode)

Поле `Mode` описывает атрибуты сегмента:
- `r` (read): Чтение разрешено.
- `w` (write): Запись разрешена.
- `x` (execute): Исполнение разрешено.
- `p` (private): Private (Copy-on-Write). Изменения в этой области не видны другим процессам.
- `s` (shared): Shared. Сегмент разделяется между процессами (например, разделяемая память IPC или системные библиотеки).

**Взаимосвязь с NX/DEP:** Если сегмент не имеет флага `x`, это означает, что NX (No-Execute) работает для этого региона. Попытка выполнить код в таком сегменте приведет к `SIGSEGV`.

### Влияние ASLR

`pmap` позволяет наглядно увидеть работу **ASLR** (Address Space Layout Randomization). При каждом перезапуске процесса начальные адреса сегментов (`[stack]`, `[heap]`, библиотеки) будут меняться, что затрудняет эксплуатацию уязвимостей типа переполнения буфера.

### Влияние THP (Transparent Huge Pages)

THP может влиять на вывод `pmap`:
- При использовании THP размер сегмента в колонке `Kbytes` может не совпадать с размером файла на диске (быть кратен 2 МБ).
- В режиме `-X` появляется колонка `THPeligible`, указывающая, может ли сегмент быть объединен в Huge Page.

### Форматы вывода и флаги утилиты

| Флаг | Формат | Назначение |
| :--- | :--- | :--- |
| (без флагов) | Address, Kbytes, Mapping | Минимальный вывод |
| `-p` | Address, Offset, Device, Inode, Mapping | С путями и метаданными inode |
| `-x` | Address, Kbytes, RSS, Dirty, Mode, Mapping | Стандартное расширенное представление |
| `-X` | Address, Kbytes, RSS, PSS, Shared_Clean, Shared_Dirty, Private_Clean, Private_Dirty, Swap, Mode, Mapping | Полная детализация из smaps |
| `-XX` | Все поля smaps без обработки | Для отладки и глубокого анализа |
| `-d` | Address, Offset, Device, Inode, Mapping (аналог -p) | Альтернативный формат детализации |

## Практические сценарии

### Предварительные требования

**Аппаратные и программные требования:**
- ОС: Linux с ядром 2.6.16+ (базовый `maps`) или 3.14+ (полный `smaps`).
- Пакет: `procps-ng` (обычно установлен по умолчанию в большинстве дистрибутивов).
- Права: `sudo` для доступа к `/proc/<PID>/smaps` чужих процессов.
- Ядро 4.14+ для агрегированного `/proc/<PID>/smaps_rollup` (альтернатива `pmap -XX`).

**Проверка версии procps-ng:**
```bash
pmap -V | head -1
# → pmap (procps-ng) 3.3.15
```

### 1. Базовый обзор и идентификация файлов

Используется для понимания того, какие библиотеки загружены и где они находятся в памяти.

```bash
# Показать базовую карту с полными путями к файлам (-p)
pmap -p <PID>

# Пример вывода:
# 000055799988a000    148K r-x-- /usr/bin/bash
# 00007f3e8b0a1000   1812K r-x-- /usr/lib/x86_64-linux-gnu/libc-2.31.so
```

**Интерпретация:**
- Адрес `000055799988a000` — начало сегмента кода bash в виртуальном адресном пространстве.
- Размер `148K` — виртуальный размер (VSS) сегмента.
- Флаги `r-x--` — чтение и исполнение разрешены, запись запрещена (сегмент кода).

### 2. Расширенный анализ потребления (-x)

Режим `-x` (extended) — основной инструмент для быстрой оценки "веса" сегментов.

```bash
# Расширенный формат: Address, Kbytes, RSS, Dirty, Mode, Mapping
pmap -x <PID>
```

| Столбец | Описание |
| :--- | :--- |
| **Address** | Начальный виртуальный адрес сегмента. |
| **Kbytes** | Виртуальный размер (VSS). Память, которую процесс "запросил". |
| **RSS** | Resident Set Size. Память, реально занимающая место в RAM. |
| **Dirty** | "Грязные" страницы. Данные, измененные в памяти и не синхронизированные с диском. |
| **Mode** | Права доступа и тип (private/shared). |
| **Mapping** | Источник сегмента (файл или системная метка). |

**Ключевое наблюдение:** Если `RSS` значительно меньше `Kbytes` — сегмент был зарезервирован, но не использован (например, `mmap` большого файла без доступа). Это нормально для JVM и Go, где `malloc` резервирует большое адресное пространство.

### 3. Глубокая диагностика с PSS и Swap (-X)

Режим `-X` извлекает практически все важные метрики из `smaps`. Это наиболее точный способ анализа в современных системах.

```bash
# Максимально информативный вывод
sudo pmap -X <PID>
```

**Ключевые дополнительные метрики в `-X`:**
- **PSS (Proportional Set Size):** Показывает реальный вклад процесса в использование физической памяти, разделяя общие библиотеки пропорционально количеству использующих их процессов.
- **USS (Unique Set Size):** Не отображается отдельной колонкой, но рассчитывается как сумма `Private_Clean + Private_Dirty`. Это память, которая освободится при завершении *только этого* процесса.
- **Swap / SwapPss:** Объем данных сегмента, вытесненный в область подкачки.
- **THPeligible:** Возможность использования Transparent Huge Pages для данного сегмента.
- **Private_Clean / Private_Dirty:** Чистые и грязные приватные страницы (входят в USS).
- **Shared_Clean / Shared_Dirty:** Чистые и грязные общие страницы (входят в Shared RSS).

### 4. Поиск утечек и аномалий

#### 4.1 Поиск крупнейших сегментов по RSS

```bash
# Найти топ-10 сегментов по RSS
pmap -x <PID> | sort -k 3 -n -r | head -n 10
```

#### 4.2 Поиск сегментов, использующих Swap

```bash
# Найти сегменты с ненулевым Swap (требует -X)
pmap -X <PID> | awk '$10 > 0 {print $0}'
# Замените $10 на актуальный номер колонки Swap в вашей версии
```

#### 4.3 Дифференциация типов утечек

```bash
# 1. Утечка кучи (heap leak) — растет Private_Anon
sudo pmap -X <PID> | grep -E 'Private_Dirty|Private_Clean' | awk '{sum+=$NF} END {print sum}'

# 2. Утечка mmap/mapped file — растет Private_File
sudo pmap -X <PID> | awk '$8 ~ /anon/ || $8 ~ /\.so/ || $8 ~ /\.dat/ {sum+=$5} END {print sum}'

# 3. Рост разделяемой памяти (Shared) — проверка tmpfs, /dev/shm, IPC
sudo pmap -X <PID> | awk '$7 ~ /shared/ {sum+=$4} END {print sum}'
```

### 5. Анализ всех параметров процесса (-XX)

Выводит все поля из `/proc/PID/smaps` без предварительной обработки.

```bash
# Полный дамп статистики ядра
sudo pmap -XX <PID>
```

**Когда использовать:** Требуется для отладки нестандартных метрик (например, `Locked`, `VmFlags`, `Referenced`). В повседневной практике достаточно `-X`.

### 6. Сравнение снимков (snapshot diff) для выявления роста

Для обнаружения утечек необходимо сравнивать вывод `pmap` в разные моменты времени:

```bash
# Снимок 1
sudo pmap -x <PID> > /tmp/pmap_before.txt

# ... ждем 5-10 минут ...

# Снимок 2
sudo pmap -x <PID> > /tmp/pmap_after.txt

# Поиск новых или выросших сегментов
diff --old-line-format='REMOVED: %L' --new-line-format='ADDED: %L' --unchanged-line-format='SAME: %L' /tmp/pmap_before.txt /tmp/pmap_after.txt | grep -E 'ADDED:|SAME:' | sort -k2 -nr | head -20
```

**Более простой подход (сортировка по RSS):**
```bash
# Сравнение топ-10 сегментов до и после
echo "=== BEFORE ===" && sudo pmap -x <PID> | sort -k3 -nr | head -10
sleep 300
echo "=== AFTER ===" && sudo pmap -x <PID> | sort -k3 -nr | head -10
```

### 7. Анализ конкретных типов приложений

#### 7.1 Java (JVM)

JVM выделяет память через `mmap` для Metaspace, Code Cache и Direct Buffers. `pmap` помогает определить, что именно растет:

```bash
# Поиск сегментов, связанных с JVM
sudo pmap -X <PID> | grep -E 'java|jvm|CodeCache|Metaspace|CompressedClassSpace'
# НаGrowth: обратите внимание на анонимные сегменты размером >100M
```

**Типичные паттерны JVM:**
- Рост `[anon]` с флагом `rw-p` — Direct ByteBuffers или Metaspace.
- Рост сегментов с путем к `.jar` или классам — Classloader leak.

#### 7.2 Python

Python выделяет память через `malloc` (обертка над `brk`/`mmap`). Большие `[anon]` сегменты часто указывают на утечки в C-расширениях (numpy, pandas, lxml):

```bash
# Python: поиск анонимных сегментов >10M
sudo pmap -x <PID> | awk '$6 ~ /\[anon\]/ && $2 > 10240 {print}'
```

#### 7.3 Go

Go-рантайм выделяет отдельный стек для каждой goroutine (по умолчанию 2-8 КБ). При 100,000+ goroutine это видно как множество `[stack]` сегментов:

```bash
# Go: проверка количества стеков goroutine
pmap -p <PID> | grep -c '\[stack'
# → 125000  (возможна утечка goroutine)

# Go: проверка анонимной памяти (heap Go)
pmap -x <PID> | grep '\[anon\]' | sort -k2 -nr | head -10
```

### 8. Интеграция с gdb для анализа core dump

`pmap` работает только с running-процессами. Для анализа упавших процессов используйте `gdb`:

```bash
# Включение core dumps
ulimit -c unlimited
echo "/tmp/core.%e.%p.%t" | sudo tee /proc/sys/kernel/core_pattern

# После падения:
gdb /usr/bin/myapp /tmp/core.myapp.12345.1694438400
(gdb) info proc mappings
# Показывает аналогичную pmap информацию

(gdb) maintenance info sections
# Показывает загруженные библиотеки и их адреса
```

**Связь с pmap:** `gdb info proc mappings` показывает те же VMA, что и `/proc/PID/maps`, но для уже завершенного процесса.

### 9. Использование pmap в контейнерах

Внутри контейнера `pmap` работает корректно, но показывает адресное пространство именно этого контейнера:

```bash
# Внутри контейнера
pmap -x 1

# На хосте: анализ процесса контейнера
CONTAINER_PID=$(sudo docker inspect --format '{{.State.Pid}}' <container_name>)
sudo pmap -x $CONTAINER_PID
```

**Важно:** В контейнере с ограничением `--memory=4g` процесс может иметь `VmSize` до 128 ТБ (лимит архитектуры), но реальный RSS ограничен cgroup. `pmap` покажет виртуальное адресное пространство, а не cgroup-лимит.

### 10. Скриптовое использование и автоматизация

Для сбора метрик в мониторинге (Prometheus, Datadog) или runbook'ах:

```bash
#!/bin/bash
# pmap_collect.sh — сбор ключевых метрик pmap
PID=${1:?Usage: $0 <PID>}

# 1. Общий RSS
RSS=$(sudo pmap -x $PID | tail -1 | awk '{print $3}')
echo "process_rss_kbytes=$RSS"

# 2. Память в swap
SWAP=$(sudo pmap -X $PID | awk 'NR>1 {sum+=$10} END {print sum}')
echo "process_swap_kbytes=$SWAP"

# 3. Количество сегментов
SEGMENTS=$(sudo pmap -p $PID | wc -l)
echo "process_mmap_segments=$SEGMENTS"

# 4. Количество анонимных сегментов
ANON=$(sudo pmap -p $PID | grep -c '\[anon\]')
echo "process_anon_segments=$ANON"
```

### 11. Детектирование HugePages и THP

```bash
# Проверка использования THP в режиме -X
sudo pmap -X <PID> | awk '$12 == "yes" {print $0}'
# → Сегменты, которые могут быть объединены в THP

# Проверка, какие сегменты фактически используют HugePages
sudo pmap -X <PID> | awk '$2 > 2048 && $8 ~ /\[anon\]/ {print}'
# → Сегменты >2M в анонимной памяти (вероятно THP)

# Проверка через /proc (более точно)
grep -i "huge" /proc/<PID>/smaps | head
# → AnonHugePages:     2048 kB
```

### 12. Анализ VMA leak (утечки виртуального адресного пространства)

VMA leak — ситуация, когда процесс выделяет новые области через `mmap()`, но не освобождает их. При этом `VmRSS` может оставаться стабильным, но `VmSize` растет:

```bash
# Мониторинг роста VmSize vs VmRSS
watch -n5 "grep -E 'VmSize|VmRSS|VmPTE' /proc/<PID>/status"

# Детализация через pmap
watch -n5 "pmap -x <PID> | tail -1"
# Обратите внимание на рост Kbytes при стабильном RSS
```

**Классические причины:**
1. **JIT-компиляторы**: Выделяют память под скомпилированный код без `munmap`.
2. **Библиотеки кэширования**: Множество мелких `mmap` для файлов конфигурации.
3. **Ошибки в обработке ошибок**: При неудаче `mmap()` не вызывается `munmap()`.

## Типичные ошибки и их решение

### 1. Permission denied / нулевые значения RSS

**Симптом:** В выводе `pmap -x` колонки RSS/PSS равны 0 для процессов другого пользователя.

**Решение:**
```bash
# Используйте sudo
sudo pmap -X <PID>

# Или настройте /proc/sys/kernel/yama/ptrace_scope
echo 0 | sudo tee /proc/sys/kernel/yama/ptrace_scope
```

### 2. pmap "зависает" или работает очень медленно

**Симптом:** `pmap -X` на процессе с 10,000+ VMA работает несколько секунд или минут.

**Причина:** Чтение и парсинг `/proc/PID/smaps` линейно зависит от количества VMA.

**Решение:**
```bash
# Используйте smaps_rollup вместо полного smaps
cat /proc/<PID>/smaps_rollup | grep -E 'Rss|Pss|Swap'

# Или ограничьте pmap определенным сегментом
sudo pmap -X <PID> | head -100
```

### 3. Truncated output (обрезанный вывод)

**Симптом:** Вывод `pmap -XX` обрывается.

**Причина:** Ограничение размера pipe buffer.

**Решение:**
```bash
# Перенаправьте вывод в файл
sudo pmap -XX <PID> > /tmp/pmap_full.txt

# Или используйте xargs
sudo pmap -p <PID> | xargs -I {} echo {}
```

### 4. VSS vs RSS: путаница с метриками

**Симптом:** Большое значение `Kbytes` кажется проблемой, но система не испытывает нехватки памяти.

**Объяснение:** Это может быть зарезервированное адресное пространство (например, в Go или Java), которое не потребляет физическую RAM.

```bash
# Проверка соотношения VSS к RSS
pmap -x <PID> | awk 'NR>1 {ratio=$2/$3; if(ratio>100) print "HIGH VSS/RSS:", $0}'
```

### 5. Лимиты ядра: vm.max_map_count

**Симптом:** Процесс падает с `ENOMEM` при попытке `mmap`, хотя `free` показывает свободную RAM.

**Причина:** Количество VMA процесса приближается к `vm.max_map_count`.

**Диагностика:**
```bash
# Текущий лимит
sysctl vm.max_map_count
# → 65530

# Количество VMA процесса
pmap -p <PID> | wc -l
# → 65000 (приближается к лимиту)
```

**Решение:**
```bash
# Временное увеличение (до перезагрузки)
sudo sysctl -w vm.max_map_count=262144

# Постоянное увеличение
echo "vm.max_map_count=262144" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

### 6. Права доступа: чужой процесс

**Симптом:** `pmap -X` показывает нулевые RSS/PSS для процессов другого пользователя.

**Решение:** Всегда используйте `sudo` для диагностики production-процессов, если они не принадлежат текущему пользователю.

### 7. Забытый [anon]: утечка в куче или mmap

**Симптом:** Огромные сегменты `[anon]` без привязки к библиотекам.

**Диагностика:**
```bash
# Топ анонимных сегментов
sudo pmap -X <PID> | grep '\[anon\]' | sort -k3 -nr | head -10

# Если растет Private_Dirty в [anon] — утечка heap/mmap
```

## Рекомендации и best practices

### 1. Выбор флага pmap

| Сценарий | Рекомендуемый флаг | Обоснование |
| :--- | :--- | :--- |
| Быстрый обзор библиотек | `-p` | Минимальный вывод, нет накладных расходов |
| Быстрая оценка "веса" | `-x` | RSS/VSS/Dirty, быстрее чем -X |
| Детальный анализ PSS/Swap | `-X` | Полная статистика из smaps |
| Отладка нестандартных полей | `-XX` | Все поля smaps без обработки |
| Анализ чужих процессов | `sudo pmap -x` | Требуются права для smaps |

### 2. Минимизация накладных расходов

- Для процессов с >5000 VMA избегайте `-X` и `-XX` на production без необходимости.
- Используйте `cat /proc/PID/smaps_rollup` как более быструю альтернативу.
- Запускайте `pmap` с низким приоритетом `nice` на высоконагруженных системах:
  ```bash
  sudo nice -n 19 pmap -X <PID>
  ```

### 3. Комбинация с другими инструментами

**Для полной картины всегда используйте несколько источников:**
```bash
# 1. Общий обзор (ps)
ps -o pid,vsz,rss,%mem,comm -p <PID>

# 2. Детализация сегментов (pmap)
sudo pmap -X <PID> | head -20

# 3. Агрегированная статистика (smaps_rollup)
cat /proc/<PID>/smaps_rollup

# 4. Таймсериес (pidstat)
pidstat -r -p <PID> 5

# 5. Мониторинг NUMA (numastat)
numastat -p <PID>
```

### 4. Документирование и сравнение

Для SRE-практик:
- Сохраняйте "здоровые" снапшоты `pmap` в runbook'ах для сравнения.
- Используйте `diff` между снапшотами как аргумент для эскалации при утечках.
- Ведите историю роста `VmPeak` и `VmHWM` для критичных сервисов.

### 5. Безопасность

- Не запускайте `pmap -XX` на процессах с конфиденциальными данными без необходимости — вывод может содержать пути к чувствительным файлам.
- Ограничьте доступ к `sudo pmap` через `sudoers`:
  ```
  # /etc/sudoers.d/pmap
  sre_user ALL=(ALL) NOPASSWD: /usr/bin/pmap -x *, /usr/bin/pmap -X *
  ```

## Дополнительная информация

### Сравнение методов анализа

| Метод | Сильные стороны | Ограничения |
| :--- | :--- | :--- |
| **`pmap`** | Удобство, форматирование, фокус на сегментах | Только статический снимок |
| **`smem`** | Точный расчет PSS/USS по всей системе | Требует установки, медленнее |
| **`ps` / `top`** | Быстрота, доступность | Показывают только агрегированные VSS/RSS |
| **`/proc/PID/smaps_rollup`** | Быстрый агрегированный взгляд | Меньше деталей по отдельным сегментам |
| **`gdb info proc mappings`** | Работает с core dumps | Требует остановки процесса / наличия дампа |

### Типичные паттерны утечек по данным pmap

| Паттерн в pmap | Вероятная причина | Действие SRE |
| :--- | :--- | :--- |
| **Рост `[heap]` (Private_Dirty)** | Утечка malloc/brk (C/C++, Java Native) | Проверьте Valgrind, JFR, `tcmalloc` stats |
| **Рост множества `[anon]` >10M** | mmap-утечка (JIT, кэши) | Проверьте количество VMA: `pmap -p | wc -l` |
| **Рост `[stack]` отдельных TID** | Бесконечная рекурсия или переполнение | Проверьте `/proc/<PID>/limits | grep stack` |
| **Рост Shared File (библиотеки)** | Коэффициент CoW после fork() | Проверьте PSS через `smem`. Если RSS растет, а PSS нет — это CoW |
| **Swap в [anon] растет** | Процесс не трогает страницы, swappiness высокий | Установите `vm.swappiness=1` для СУБД |
| **`[sysv]` или `[aio]` растут** | Утечка System V IPC или AIO | `ipcs -a`, проверьте дочерние процессы |

### Границы применимости pmap

1. **Статичность:** `pmap` показывает снимок на момент вызова. Для динамики используйте `pidstat` или `watch`.
2. **Overhead:** Режимы `-X` и `-XX` блокируют процесс на чтение `smaps`. На production используйте осторожно.
3. **Только Linux:** Утилита специфична для `/proc`. На других UNIX-системах аналогов нет.
4. **Нет истории:** `pmap` не сохраняет исторические данные. Для трендов используйте внешние агенты сбора метрик.
5. **Container namespace:** В namespace PID 1 контейнера `pmap` покажет корректные адреса, но на хосте PID будут другими.

### Лимиты и известные особенности

1. **`vm.max_map_count`:** Если количество строк в `pmap` приближается к значению `sysctl vm.max_map_count` (обычно 65530), процесс может начать падать с ошибками "Out of memory" при попытке выделить новый сегмент, даже если свободная RAM есть.
2. **32-битные системы:** На 32-битных архитектурах (i386, armhf) адресное пространство ограничено 4 ГБ, что приводит к более частым конфликтам mmap и необходимости использования `vm.mmap_min_addr`.
3. **Ядра < 3.14:** На старых ядрах `/proc/PID/smaps` может отсутствовать или быть неполным. Используйте `-x` как максимальный режим.
