# smem — утилита точного анализа памяти

## Определения

**`smem`** — специализированный инструмент командной строки (написанный на Python), предназначенный для детального аудита потребления оперативной памяти в Linux. Главное преимущество `smem` перед стандартными утилитами (`top`, `ps`) заключается в корректном расчете **PSS** (Proportional Set Size), что позволяет объективно оценить реальный вклад каждого процесса в загрузку RAM с учетом разделяемых библиотек и сегментов памяти.

## Установка

Утилита доступна в официальных репозиториях большинства дистрибутивов.

### Дистрибутивы и команды
- **Ubuntu / Debian:** `sudo apt install smem`
- **RHEL / CentOS / Rocky:** `sudo dnf install epel-release && sudo dnf install smem`
- **Arch Linux:** `sudo pacman -S smem`
- **Alpine Linux:** `apk add smem`

### Зависимости для визуализации
Для генерации графиков (флаги `--pie`, `--bar`) требуется Python-библиотека **matplotlib**:
- `sudo apt install python3-matplotlib` (или через `pip install matplotlib`)

## Основные концепции

### Математика метрик (USS, PSS, RSS)

`smem` агрегирует данные из `/proc/<PID>/smaps`. Понимание разницы между метриками критично для SRE:

- **USS (Unique Set Size):** Сумма полей `Private_Clean` и `Private_Dirty`. Это память, которая принадлежит *только* этому процессу. При завершении процесса именно этот объем RAM вернется системе немедленно.
- **PSS (Proportional Set Size):** Основная метрика `smem`. Рассчитывается как `USS + (Shared Memory / N)`, где `N` — количество процессов, использующих данный сегмент. Сумма PSS всех процессов дает наиболее точное приближение к общему объему занятой RAM.
- **RSS (Resident Set Size):** Стандартный показатель (аналог в `ps`). Суммирует все страницы в RAM, к которым есть доступ, включая разделяемые. Суммирование RSS по процессам всегда приводит к завышенным результатам (оверкаунтинг).

### Учет Swap (Swap PSS)

В современных ядрах (4.3+) и версиях `smem` поддерживается расчет **Swap PSS**. Если стандартный Swap показывает общий объем вытесненных данных сегмента, то Swap PSS делит его пропорционально между процессами-владельцами, предотвращая двойной учет при анализе подкачки.

### Внутреннее устройство smem

Утилита является пользовательским пространственным агрегатором данных из виртуальной файловой системы `/proc`. Понимание алгоритма работы необходимо для корректной интерпретации результатов и диагностики ошибок:

1. **Сбор списка процессов:** `smem` сканирует каталог `/proc`, отфильтровывая нечисловые имена (например, `self`, `thread-self`) и не-PID-сущности.
2. **Чтение `smaps`:** Для каждого PID открывается `/proc/<PID>/smaps`. Этот файл содержит детализацию каждой VMA (Virtual Memory Area): `Rss`, `Pss`, `Private_Clean`, `Private_Dirty`, `Shared_Clean`, `Shared_Dirty`, `Swap`, `Pss_Swap` и другие поля.
3. **Агрегация по ключам:** Данные суммируются по PID, команде (`Command`), пользователю (`User`) или маппингу (`Mapping`), в зависимости от флага вывода.
4. **Форматирование:** Результаты выводятся в табличном,条形图 или круговой диаграмме с использованием `matplotlib`.

**Производительность:** Чтение и парсинг `/proc/PID/smaps` имеет накладные расходы на порядок выше, чем чтение `/proc/PID/stat`. На системе с 10,000+ процессами или приложениями с тысячами mmap-областей (JVM, Go-сервисы) выполнение `smem` может занимать 5-30 секунд.

### Модель разрешений и доступ к /proc

Доступ к файлу `/proc/<PID>/smaps` регулируется стандартной моделью прав Linux:

- **Собственные процессы:** Любой пользователь может читать `smaps` своих процессов.
- **Чужие процессы:** Требуются права `root` (или `CAP_SYS_PTRACE`). Без `sudo` утилита не имеет доступа к `smaps` чужих процессов, что делает расчет PSS/USS невозможным (будут отображаться нули или только свои данные).
- **В контейнерах:** В namespace PID 1 контейнера `smem` покажет корректные данные только для процессов внутри namespace. Для анализа всех процессов хоста запускайте утилиту на хосте или используйте `nsenter`.

### NUMA-анализ

На системах с неоднородным доступом к памяти (NUMA) утилита поддерживает флаг `--numa`, который добавляет столбцы с распределением PSS по узлам NUMA. Это критично для:

- Балансировки потоков ядра (IRQ affinity, `taskset`, `numactl`).
- Диагностики "теневого" потребления памяти, когда процесс физически использует удаленный узел.
- Оптимизации баз данных (PostgreSQL, MySQL) и высоконагруженных сетевых приложений.

```bash
# Распределение памяти по NUMA-узлам для топ-10 процессов
sudo smem --numa -tk -s pss -r | head -n 11
```

### Производительность и ограничения

- **Механизм работы:** В отличие от `top` (читающего легкий `/proc/PID/stat`), `smem` парсит тяжеловесные текстовые файлы `/proc/PID/smaps` для каждого процесса.
- **Масштабируемость:** На системах с 10,000+ процессами или огромным количеством маппингов (базы данных) выполнение команды может занимать несколько секунд и создавать заметную нагрузку на CPU/IO.
- **Права доступа:** Без `sudo` утилита не имеет доступа к `smaps` чужих процессов, что делает расчет PSS/USS невозможным (будут отображаться нули или только свои данные).
- **Только Linux:** Утилита зависит от наличия `/proc/PID/smaps`. На других UNIX-подобных системах (FreeBSD, macOS) работает не поддерживается.
- **Python dependency:** Требуется Python 3. На минимальных системах (Alpine, container-образы) может потребоваться установка интерпретатора.

### smemcap — архитектура и применение

`smemcap` — вспомогательная утилита, написанная на C, предназначенная для быстрого создания архива с дампом `/proc` без накладных расходов Python-интерпретатора.

**Когда использовать:**
- Наproduction-серверах, где установка Python или запуск `smem` нежелателен.
- Для сбора данных в момент инцидента, когда любая дополнительная нагрузка на CPU критична.
- Для последующего офлайн-анализа на рабочей станции.

**Ограничения:**
- Снимок статический (как в момент создания архива).
- Не учитывает динамику процессов, завершившихся до момента сбора.
- Размер архива пропорционален количеству процессов (обычно 10-100 MB на сервер с 1000 процессами).

## Практические сценарии

### 1. Поиск виновников Memory Pressure

Сортировка по PSS с итоговой строкой — лучший способ найти реальных потребителей памяти.

```bash
# -t (totals), -k (human-readable), -s (sort field), -r (reverse)
sudo smem -tk -s pss -r | head -n 20
```

**Ожидаемый вывод:**
```
  PID User     Command                         Swap      USS      PSS      RSS
 1234 root     java                         1.2Gi   512Mi   768Mi   2.1Gi
 5678 mysql    mysqld                         256Mi   128Mi   192Mi   384Mi
```

**Интерпретация:** Если `PSS` близок к `RSS` у лидера — процесс почти не делит память. Если `RSS` значительно превышает `PSS` — значительная часть памяти разделяется (библиотеки, кэши).

### 2. Группировка по пользователям или маппингам

Позволяет быстро определить, какой сервис или пользователь "съел" память, не вдаваясь в детали PID.

```bash
# Агрегация по пользователям
smem -u -k

# Анализ потребления в разрезе библиотек и файлов (-m = mappings)
smem -m -k | sort -k 4 -nr | head
```

**Варианты группировки:**
- `-u` / `--user`: по владельцам процессов.
- `-m` / `--mappings`: по файлам и библиотекам в памяти.
- `-p` / `--process`: по именам процессов (агрегация по identical command names).

### 3. Фильтрация и поиск

Использование регулярных выражений для анализа конкретных приложений.

```bash
# Анализ всех процессов nginx
smem -rk -P nginx

# Процентное соотношение использования памяти
smem -p -s pss
```

**Кombинирование фильтров:**
```bash
# Все процессы пользователя www-data, сортировка по USS
sudo smem -t -k -s uss -r -U www-data
```

### 4. Диагностика на нагруженных системах (smemcap)

Если запуск тяжелого Python-скрипта на сервере нежелателен, используется `smemcap` (написан на C), который быстро делает слепок `/proc` в tar-архив.

```bash
# На сервере (мгновенный сбор данных)
sudo smemcap > memory_dump.tar

# На рабочей станции (анализ собранных данных)
smem -S memory_dump.tar -tk
```

**Валидация:** Убедитесь, что архив создан корректно:
```bash
tar tf memory_dump.tar | head
# → proc/1234/smaps
# → proc/5678/smaps
```

### 5. Построение графиков

Визуализация распределения памяти между процессами (требует X-сервер или сохранение в файл).

```bash
# Круговая диаграмма по PSS для топ-10 процессов
smem --pie name -c "pss" --limit 10
```

Для сохранения в файл без X-сервера используйте переменную окружения `MPLBACKEND`:
```bash
MPLBACKEND=Agg smem --pie name -c "pss" --limit 10 --output memory_pie.png
```

### 6. Анализ Swap через smem

`smem` корректно считает Swap PSS, предотвращая двойной учет при анализе подкачки. Это особенно полезно при диагностике Memory Pressure, вызванного вытеснением.

```bash
# Топ процессов по реально занимаемому Swap
sudo smem -t -k -s swap -r | head -n 20
```

**Интерпретация:**
- Высокий `Swap` у `java` или `postgres` часто указывает на избыточное выделение буферов.
- Если `Swap PSS` растет, а `RSS` стабилен — процесс активно использует вытеснение, но не утекает в RAM.

### 7. Анализ в контейнерах

При работе с Docker/LXC доступ к `/proc` хоста ограничен namespace контейнера. Для анализа памяти хостовых процессов изнутри контейнера:

```bash
# Смотреть PID контейнера с хоста
CONTAINER_PID=$(docker inspect --format '{{.State.Pid}}' <container_name>)

# Через nsenter получить доступ к /proc хоста
sudo nsenter -t $CONTAINER_PID -m -- smem -tk -s pss -r | head
```

**Альтернатива:** Запуск `smem` непосредственно на хосте с фильтрацией по cgroup:
```bash
# Найти PID процессов контейнера по cgroup
sudo smem -P $(cat /proc/$(docker inspect -f '{{.State.Pid}}' web)/cgroup | grep -oP '\d+:\/docker\/\K[^"]+') -k
```

### 8. NUMA-анализ

На серверах с несколькими сокетами и NUMA-узлами важна локализация памяти.

```bash
# Показать распределение PSS по NUMA-узлам
sudo smem --numa -tk -s pss -r | head -n 15
```

**Диагностика удаленного доступа:**
```bash
# Если PSS на ноде 0 значительно больше, чем на ноде, где запущен процесс,
# возможно, требуется настройка irqbalance или numactl
sudo smem --numa -w | grep -E "(nginx|java)" | awk '$3 != $4 {print "MIGRATED:", $0}'
```

### 9. Скриптовая автоматизация и мониторинг

`smem` может использоваться в cron, системных сервисах и скриптах для регулярного сбора метрик.

**Пример: Сбор метрик в CSV для построения трендов**
```bash
#!/bin/bash
# /usr/local/bin/memory_baseline.sh
OUT="/var/log/memory/smem_$(date +%Y%m%d_%H%M%S).csv"
sudo smem -t -k -s pss -r > "$OUT"
```

**Пример: Алертинг при росте PSS**
```bash
#!/bin/bash
# Порог: 1.5 GB для процесса java
THRESHOLD=$((1536 * 1024))  # в KB
ALERT_PROCESS="java"

LEADER=$(sudo smem -t -k -s pss -r -P "$ALERT_PROCESS" | head -n 2 | tail -n 1)
PSS_KB=$(echo "$LEADER" | awk '{print $5}' | numfmt --from=iec)

if [ "$PSS_KB" -gt "$THRESHOLD" ]; then
    echo "ALERT: $ALERT_PROCESS PSS=$PSS_KB KB exceeds threshold $THRESHOLD KB" | \
        tee -a /var/log/memory_alerts.log
    # Здесь можно добавить вызов pagerduty, telegram-bot и т.д.
fi
```

### 10. Базовое тестирование и drift detection

Для выявления утечек памяти необходимо фиксировать baseline и отслеживать drift.

**Создание baseline:**
```bash
# После "теплого" запуска приложения (стабильное состояние)
sudo smem -t -k -s pss -r > /opt/baselines/smem_baseline_$(date +%Y%m%d).txt
```

**Сравнение с baseline:**
```bash
BASELINE="/opt/baselines/smem_baseline_20260901.txt"
CURRENT=$(mktemp)
sudo smem -t -k -s pss -r > "$CURRENT"

# Простой diff по процессам
join -j 1 <(sort "$BASELINE") <(sort "$CURRENT") | awk '
  { diff = $5 - $8; if (diff > 10240) print "DRIFT:", $0 }
'
```

**Валидация:** Drift на 10 MB и более для критичных процессов требует внимания. Для JVM-приложений учитывайте GC-паузы: после полного GC память может не вернуться к baseline, но тренд должен быть стабилен.

### 11. Интеграция с pmap для глубокого анализа сегментов

`smem` дает агрегированную картину по всей системе, но не показывает детализацию сегментов внутри одного процесса. Для полной картины комбинируйте с [`pmap`](./pmap.md).

```bash
# 1. Найти процесс с аномальным PSS
SUSPECT=$(sudo smem -t -k -s pss -r | awk 'NR==2 {print $1}')

# 2. Детализация через pmap
sudo pmap -x $SUSPECT | head -n 30
```

**Сценарий:**
- `smem` показывает, что `java` потребляет 2 GB PSS.
- `pmap -x` показывает, что `[heap]` вырос на 500 MB за час.
- Вывод: утечка в куче (heap). Дальнейший анализ: `jmap`, `jhat`, или async-profiler.

## Траблшутинг

### Проблема: smem показывает нули в PSS/USS для чужих процессов

**Причина:** Запущено без `sudo`. `/proc/PID/smaps` чужих процессов недоступен обычному пользователю.

**Решение:**
```bash
sudo smem -tk -s pss -r | head
```

### Проблема: smem работает слишком медленно

**Причина:** Парсинг `smaps` на системе с 10,000+ процессами или приложениями с тысячами VMA.

**Решение:**
1. Используйте `smemcap` для офлайн-анализа.
2. Ограничьте вывод: `smem -P <pattern>` для фильтрации.
3. Используйте `/proc/PID/smaps_rollup` для отдельного процесса — это в 10-100 раз быстрее.

### Проблема: smem: command not found

**Причина:** Утилита не установлена или не в PATH.

**Решение:**
```bash
# Установка
sudo apt install smem  # Debian/Ubuntu

# Проверка PATH
which smem
```

### Проблема: ImportError: No module named matplotlib

**Причина:** Не установлена зависимость для графиков.

**Решение:**
```bash
sudo apt install python3-matplotlib
# или
pip install matplotlib
```

### Проблема: Рост PSS не останавливается после завершения пиковой нагрузки

**Причина:** Утечка памяти (не возврат страниц ядру) или фрагментация кучи.

**Диагностика:**
```bash
# 1. Проверьте, завершились ли дочерние процессы
ps aux | grep <app>

# 2. Проверьте VmHWM (пиковый RSS) через /proc/PID/status
grep -E "VmHWM|VmRSS" /proc/<PID>/status

# 3. Если VmHWM >> VmRSS и разница растет — фрагментация
# Если VmRSS растет — утечка
```

## Best Practices

1. **Всегда используйте `sudo`** для получения полной картины по системе. Без привилегий `smem` не видит чужие процессы.
2. **Используйте `-k` (human-readable)** во всех production-скриптах. Числа в KB трудно читать для человека.
3. **Комбинируйте с `smaps_rollup`** для быстрого анализа отдельного процесса. `smem` — для системной картины, `cat /proc/PID/smaps_rollup` — для мгновенного снимка одного процесса.
4. **Используйте `smemcap`** на production-серверах. Это минимизирует overhead при сборе данных.
5. **Собирайте baseline** в "холодное" время (после разогрева, но до пика нагрузки). Сравнивайте текущие показатели с baseline, а не с абсолютными порогами.
6. **Мониторьте тренд PSS**, а не мгновенные значения. Один замер в 2 GB не означает утечку — важно, растет ли он со временем.
7. **Учитывайте NUMA** на многосокетных серверах. Высокий PSS на удаленном узле может указывать на неправильную балансировку.
8. **Для CI/CD пайплайнов** используйте `ps_mem` вместо `smem`, если нужна только быстрая проверка на утечки. `smem` предпочтительнее для глубокой диагностики.

## Типичные инциденты и их диагностика

### Инцидент 1: "RSS по процессам превышает общую RAM"

**Симптом:** Суммарный `RSS` из `ps` больше, чем физическая RAM. Администратор думает, что система переполнена.

**Диагностика:**
```bash
# Неправильно: суммарный RSS
ps -eo pid,rss --sort=-rss | awk '{sum+=$2} END {printf "Total RSS: %.1f GB\n", sum/1024/1024}'
# → Total RSS: 48.5 GB  (при 32 ГБ RAM!)

# Правильно: суммарный PSS
sudo smem -tk -s pss -r | tail -1
# → 28.3 GB  (корректно)
```

**Причина:** RSS двойной учет shared-страниц (библиотеки, fork). PSS делит shared пропорционально, давая реальную картину.

**Ключевое:** Суммарный RSS всегда завышен. Для точного анализа используйте PSS через `smem`.

---

### Инцидент 2: "Процесс потребляет много памяти, но USS маленький"

**Симптом:** `ps` показывает большой RSS у процесса, но `smem` показывает маленький USS.

**Диагностика:**
```bash
# Сравнение RSS, PSS и USS
sudo smem -tk -p -P nginx
# →  PID User     Command                         Swap      USS      PSS      RSS
# → 1234 www-data nginx: worker                   0K     12Mi     48Mi    256Mi
```

**Причина:** Процесс разделяет много общих страниц (библиотеки, mmap-файлы). RSS включает все shared, USS — только unique.

**Ключевое:**
- `RSS` = Private + Shared (все страницы, к которым есть доступ)
- `PSS` = Private + (Shared / N процессов)
- `USS` = Private (только уникальные страницы)

При завершении процесса освободится только USS. Shared-страницы используются другими процессами.

---

### Инцидент 3: "PSS растет, но RSS стабилен"

**Симптом:** `smem` показывает рост PSS, но `ps` показывает стабильный RSS.

**Диагностика:**
```bash
# Сравнение PSS и RSS для процесса
sudo smem -tk -p -P java | head -5
# →  PID User     Command                         Swap      USS      PSS      RSS
# → 5678 root     java                          128Mi     512Mi     768Mi    1024Mi

# Проверка shared страниц
sudo pmap -x 5678 | grep -E "Shared_Clean|Shared_Dirty"
# → Shared_Clean:    256000 kB
# → Shared_Dirty:      0 kB
```

**Причина:** Другие процессы завершились, и shared-страницы стали "более приватными" для оставшегося процесса. PSS вырос, хотя физическое потребление не изменилось.

**Ключевое:** PSS может расти без реального роста потребления — это нормальное поведение при завершении других процессов.

---

### Инцидент 4: "Swap PSS растет, RSS стабилен"

**Симптом:** Процесс активно использует swap, но RSS не растет.

**Диагностика:**
```bash
# Проверка Swap PSS
sudo smem -tk -s swap -r | head -10
# →  PID User     Command                         Swap      USS      PSS      RSS
# → 1234 postgres postgres                        512Mi      0K       0K     256Mi

# Проверка через /proc
grep -E "VmRSS|VmSwap" /proc/1234/status
# → VmRSS:    262144 kB
# → VmSwap:   524288 kB
```

**Причина:** Процесс выделил память, но не обращался к ней. Ядро выгрузило неактивные страницы в swap.

**Ключевое:** Высокий Swap не означает проблему, если приложение не испытывает задержек. Для БД (PostgreSQL, MySQL) это нормальное поведение.

---

### Инцидент 5: "smem не показывает PSS для чужих процессов"

**Симптом:** `smem` показывает нули в колонке PSS для процессов другого пользователя.

**Диагностика:**
```bash
# Без sudo
smem -tk -s pss -r | head -5
# →  PID User     Command                         Swap      USS      PSS      RSS
# → 1234 postgres postgres                        512Mi       0K       0K     256Mi

# С sudo
sudo smem -tk -s pss -r | head -5
# →  PID User     Command                         Swap      USS      PSS      RSS
# → 1234 postgres postgres                        512Mi     128Mi     192Mi     256Mi
```

**Причина:** `/proc/<PID>/smaps` недоступен без `sudo`. `smem` не может рассчитать PSS без доступа к `smaps`.

**Ключевое:** Всегда используйте `sudo` для диагностики памяти на production-серверах.

## Дополнительная информация

### Сравнение с альтернативами

| Инструмент | Преимущества | Недостатки |
| :--- | :--- | :--- |
| **`smem`** | Самый точный расчет PSS/USS, группировка, `smemcap`. | Зависимость от Python, медленный парсинг. |
| **`ps_mem`** | Максимально легкий, один файл, очень быстрый. | Минимум опций (только USS/PSS/Total). |
| **[`pmap`](./pmap.md)** | Детальный разбор *внутри* процесса (сегменты). | Сложно агрегировать данные по всей системе. |
| **`smaps_rollup`** | Встроен в ядро, мгновенный доступ. | Только один процесс за раз, нет группировки. |
