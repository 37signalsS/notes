# `journalctl`: Просмотр и анализ логов Systemd

## Определения

*   **`journalctl`** — это утилита командной строки для просмотра, фильтрации и анализа логов, собранных службой `systemd-journald`.
*   **`systemd-journald`** — это системная служба, которая централизованно собирает и управляет логами от всех компонентов операционной системы, включая ядро, службы и приложения. Она хранит данные в структурированном бинарном формате.

## Основные концепции

### Централизованное и структурированное логирование

Служба `systemd-journald` собирает логи со всего окружения `systemd` (ядро, системные сервисы, приложения, stdout/stderr) в **структурированном бинарном формате**. В отличие от традиционных текстовых логов (например, `rsyslog`), это обеспечивает:

*   **Централизацию:** Все системные сообщения хранятся в одном месте.
*   **Обогащение метаданными:** Каждое сообщение автоматически получает метаданные (имя сервиса, PID процесса, UID пользователя, уровень приоритета и т.д.).
*   **Мощную и быструю фильтрацию:** Возможность фильтровать логи по любым метаданным без парсинга текстовых строк.

### Хранение логов

Логи `systemd-journald` могут храниться двумя способами:

1.  **Энергозависимое (Volatile):** По умолчанию логи хранятся в `/run/log/journal`. Эта директория монтируется как `tmpfs` и очищается при каждой перезагрузке системы.
2.  **Постоянное (Persistent):** Если существует директория `/var/log/journal`, `systemd-journald` автоматически начнет использовать её для постоянного хранения логов. В этом случае логи сохраняются между перезагрузками.

### Уровни приоритета логов

`journalctl` позволяет фильтровать сообщения по их уровню приоритета (от 0 до 7, от самого критического до отладочного):

*   `0: emerg` (System is unusable)
*   `1: alert` (Action must be taken immediately)
*   `2: crit` (Critical conditions)
*   `3: err` (Error conditions)
*   `4: warning` (Warning conditions)
*   `5: notice` (Normal but significant condition)
*   `6: info` (Informational messages)
*   `7: debug` (Debug-level messages)

## Практические сценарии (`journalctl`)

### 1. Просмотр логов

*   **Все логи (в обратном хронологическом порядке):**
    ```bash
    journalctl
    ```
*   **Логи в реальном времени (поток событий):**
    ```bash
    journalctl -f
    ```
*   **Логи ядра (аналог `dmesg`):**
    ```bash
    journalctl -k
    # Или для просмотра в реальном времени:
    journalctl -kf
    ```
*   **Логи с последней загрузки:**
    ```bash
    journalctl -b
    # Для предыдущей загрузки (например, -1, -2 и т.д.):
    journalctl -b -1
    ```
*   **Список всех зарегистрированных загрузок (для выбора конкретной):**
    ```bash
    journalctl --list-boots
    ```
*   **Логи от новых к старым (обратный порядок):**
    ```bash
    journalctl -r
    ```

### 2. Фильтрация логов

*   **По службе (unit):**
    ```bash
    # Логи сервиса Nginx
    journalctl -u nginx.service
    # И с отслеживанием в реальном времени:
    journalctl -u nginx.service -f
    ```
*   **По нескольким службам:**
    ```bash
    journalctl -u sshd.service -u httpd.service
    ```
*   **По идентификатору процесса (PID):**
    ```bash
    journalctl _PID=1234
    ```
*   **По идентификатору пользователя (UID):**
    ```bash
    journalctl _UID=1000
    ```
*   **По времени:**
    ```bash
    # За последний час
    journalctl --since "1 hour ago"
    # С определенной даты и времени
    journalctl --since "2023-10-26 18:00:00"
    # Между двумя датами
    journalctl --since "2023-10-26 18:00:00" --until "2023-10-26 18:10:00"
    ```
*   **По уровню приоритета:**
    ```bash
    # Только ошибки и более критичные сообщения
    journalctl -p err
    # Только предупреждения и ошибки
    journalctl -p warning..err
    ```
*   **По пути к исполняемому файлу:**
    ```bash
    journalctl /usr/lib/systemd/systemd
    ```

### 3. Настройка и управление хранением логов

*   **Включение постоянного хранения логов:**
    ```bash
    sudo mkdir -p /var/log/journal
    sudo systemctl restart systemd-journald
    ```
    После этого логи будут сохраняться между перезагрузками в `/var/log/journal`.

*   **Ограничение размера журнала (в `/etc/systemd/journald.conf`):**
    Для предотвращения чрезмерного роста логов настройте параметры в секции `[Journal]`:
    ```ini
    # Максимальный общий размер журнала (например, 4 ГБ). Если этот лимит будет превышен,
    # старые логи будут удаляться.
    SystemMaxUse=4G

    # Минимальный объем свободного места, который должен оставаться на диске.
    # Удаление старых логов будет производиться до тех пор, пока это условие не будет выполнено.
    SystemKeepFree=15%

    # Максимальный размер одного файла журнала (например, 200 МБ).
    SystemMaxFileSize=200M

    # Хранение логов только в оперативной памяти (отключить постоянное хранение).
    # Storage=volatile
    # Хранение логов постоянно (в /var/log/journal).
    # Storage=persistent
    # Автоматическое определение (по умолчанию): persistent, если /var/log/journal существует, иначе volatile.
    # Storage=auto
    ```
    После изменения файла необходимо перезапустить службу:
    ```bash
    sudo systemctl restart systemd-journald
    ```
    Проверить текущий размер журнала:
    ```bash
    journalctl --disk-usage
    ```

## Дополнительная информация

### Анализ проблем с запуском сервисов

`journalctl` незаменим при диагностике проблем с запуском сервисов, особенно при загрузке системы.

*   **Просмотр логов сервиса с начала текущей загрузки:**
    ```bash
    journalctl -u myservice.service -b
    ```
    Флаг `-b` (boot) критически важен, так как он отфильтровывает логи, относящиеся только к текущей сессии загрузки, игнорируя предыдущие ручные запуски.

### Альтернативные способы просмотра вывода процесса

Если сервис настроен так, что `journalctl` не показывает его вывод (например, если он пишет напрямую в файл), можно прибегнуть к прямому анализу файловых дескрипторов процесса через `/proc`:

1.  **Найти PID процесса:** Используйте `systemctl status <имя_сервиса>` или [`ps aux | grep <имя_процесса>`](../Processes/ps.md).
2.  **Проверить, куда направлен вывод:** Файловые дескрипторы `1` (stdout) и `2` (stderr) в директории `/proc/<PID>/fd/` покажут, куда процесс пишет свои логи.
    ```bash
    ls -l /proc/<PID>/fd/
    ```
3.  **Прочитать вывод напрямую:** Если вывод направлен в пайп или файл, его можно прочитать.
    ```bash
    tail -f /proc/<PID>/fd/1
    ```

### Интеграция с `rsyslog`

Хотя `journald` отлично подходит для локального хранения и анализа, для пересылки логов на удаленные серверы часто используется [rsyslog](../../SystemAdministration/Logging/rsyslog.md). `rsyslog` может забирать сообщения напрямую из `journald` для их дальнейшей фильтрации и отправки в централизованное хранилище.
