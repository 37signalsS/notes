# Инструменты мониторинга, трассировки и отладки в Linux

**Определения:**
*   **Мониторинг:** Непрерывный сбор и анализ данных о состоянии и производительности системы или приложения. Цель — выявление трендов, аномалий и своевременное оповещение о проблемах.
*   **Трассировка:** Запись и анализ последовательности событий или вызовов функций в программе или системе. Используется для понимания потока выполнения и выявления причин задержек или сбоев.
*   **Отладка:** Процесс выявления и устранения ошибок (багов) в программном обеспечении. Включает остановку выполнения программы, пошаговый просмотр кода и анализ состояния переменных.


## Трассировка и профилирование

Эти инструменты позволяют заглянуть "внутрь" работающего процесса или ядра.

### strace: Трассировка системных вызовов

`strace` — перехватывает и записывает **системные вызовы (system calls)** процесса и получаемые им сигналы. Незаменим для диагностики проблем с доступом к файлам, сетевыми соединениями и правами.
- **Присоединиться к процессу:** `sudo strace -p <PID>`
- **Отследить дочерние процессы и время вызовов:** `sudo strace -f -ttT <команда>`
- **Фильтровать по типу вызовов:** `strace -e trace=network,open ...`

---

### ltrace: Трассировка библиотечных функций

`ltrace` — отслеживает вызовы функций из динамических библиотек (`.so`). Полезно, когда системных вызовов недостаточно для понимания логики приложения.

---

## Глубокая отладка и системные механизмы

### PSI (Pressure Stall Information)
Механизм ядра Linux, позволяющий отслеживать "давление" на ключевые системные ресурсы: **CPU**, **память** и **ввод-вывод (I/O)**. Показывает, сколько времени процессы **потеряли из-за нехватки** этого ресурса.
- `cat /proc/pressure/cpu`: Давление на CPU.
- `cat /proc/pressure/memory`: Давление на память.
- `cat /proc/pressure/io`: Давление на I/O.
- **Подробнее:** См. [Pressure Stall Information (PSI): Мониторинг "давления" на ресурсы](../Core/kernel/psi.md).

---

### lsof: Мониторинг открытых файлов

В Linux всё — это файл. Сюда попадают не только документы на диске, но и сокеты, устройства, пайпы. Иногда это приводит к странным ситуациям: файл вроде удалили, а место на диске не освободилось. Или порт висит занятым, хотя процесс уже остановлен. В таких случаях незаменим инструмент `lsof` (list open files).

`lsof` — это утилита, которая показывает список открытых файлов (файловых дескрипторов) для каждого процесса в системе. Она может получать информацию из `/proc` файловой системы, агрегируя и представляя её в удобном виде.

**Несколько базовых приёмов:**
*   `lsof /path/to/file` — покажет, какой процесс держит файл открытым. Полезно, если удалённый лог «не освобождает» место.
*   `lsof -i :8080` — кто слушает порт 8080 или держит соединение. Отлично работает при отладке сетевых сервисов.
*   `lsof -u www-data` — все открытые файлы конкретного пользователя, например, у веб-сервера.
*   `lsof -p <PID>` — все открытые файлы для процесса с указанным PID.

**Диагностика и продвинутое использование:**
*   **Поиск удаленных, но открытых файлов:** Если вы удалили файл, но место на диске не освободилось, это может быть связано с тем, что файл всё ещё открыт каким-то процессом. Команда `lsof | grep deleted` поможет найти такие процессы.
    *   Для поиска файлов, у которых количество ссылок (link count) меньше 1, то есть удалённых файлов, можно использовать: `sudo lsof +L1`.
    *   Если это не критичный сервис, можно просто завершить процесс, используя его PID из вывода `lsof`.
*   **Утечки файловых дескрипторов:** Иногда сервисы постепенно «съедают» лимит открытых файлов. `lsof -p <PID>` покажет, чем именно завален процесс.
    *   Чтобы посчитать количество открытых файлов для процесса: `lsof -p <PID> | wc -l`.
*   **Идентификация файлов, используемых процессом для записи/чтения:**
    *   `lsof -p <PID> | grep -E 'w|u'` — найти все файлы, открытые процессом для записи (w) или с неизвестным доступом (u).
*   **Отладка контейнеров:** В контейнерах Docker или Kubernetes вы можете использовать `lsof` или `/proc` для анализа, какие файлы контейнер использует из хостовой системы (например, mounted volumes или configmaps).
*   **Подозрительные соединения:** В связке с `df` и `du` утилита позволяет быстро вычислить «невидимых пожирателей места», а при отладке сетей — вычленить подозрительные соединения.

## Как посмотреть вывод (stdout) запущенного сервиса?

Когда приложение запущено как сервис, его стандартный вывод (stdout) может быть перенаправлен. Вот несколько способов его просмотреть.

### 1. `journalctl` (для systemd-сервисов)
Если сервис управляется через `systemd`, его логи, включая stdout и stderr, обычно централизованно собираются в `journald`.

```bash
# Показать логи для указанного юнита
sudo journalctl -u [имя_юнита]

# Показать последние 100 строк и следить за новыми логами
sudo journalctl -u [имя_юнита] -n 100 -f
```

### 2. Перехват stdout/stderr в рантайме без перезапуска
Иногда `journalctl` не показывает логи в реальном времени, или вы не хотите/не можете использовать `strace`. В таком случае можно напрямую "подключиться" к файловым дескрипторам процесса, чтобы понять, что он пишет в stdout или stderr.

#### Шаг 1: Поиск дескрипторов вывода
Сначала узнаём PID основного процесса сервиса:
```bash
systemctl show -p MainPID your-service.service
```

Затем идём в директорию `/proc/<PID>/fd/` и смотрим, куда указывают его стандартные потоки вывода (stdout — дескриптор `1`, stderr — `2`):
```bash
ls -l /proc/<PID>/fd/
```
Результат может быть разным:
- `-> /dev/null` (вывод отбрасывается)
- `-> socket:[12345]` (вывод идет в сокет, например, в `journald`)
- `-> /run/log/journal/...` (вывод идет в файл журнала)

#### Шаг 2: Чтение вывода
В зависимости от того, куда направлен вывод, можно использовать разные инструменты:
- **Если это сокет:** Можно попытаться "подключиться" к нему с помощью `socat`.
- **Если это пайп или лог-файл:** Можно читать его напрямую в реальном времени.
  ```bash
  tail -f /proc/<PID>/fd/1
  ```

#### Шаг 3: Перенаправление вывода на лету
Иногда вы хотите временно направить stdout/stderr в другой файл (например, в отладочный лог). Если приложение не закрывает дескрипторы, можно попробовать следующий трюк, чтобы дублировать вывод:
```bash
# Создаем временный файл для лога
exec 3>/tmp/debug.log

# Дублируем вывод из stdout процесса в наш файл
# Этот метод может не сработать для всех типов процессов
sudo tee /proc/<PID>/fd/1 >/dev/null <&3
```

### 3. `strace` (трассировка системных вызовов)
`strace` позволяет перехватить данные, которые процесс пишет в файловые дескрипторы, включая stdout (дескриптор 1). Этот способ может замедлить работу приложения, а вывод требует интерпретации.

```bash
# Отслеживать только системные вызовы write, показывая до 9999 символов на строку
sudo strace -e write -s 9999 -p <PID>
```

Например, строка `Привет, это тестовое сообщение!` в `strace` будет выглядеть как закодированная последовательность:
```
write(1, "\320\237\321\200\320\270\320\262\320\265\321\202, \321\215\321\202\320\276 \321\202\320\265\321\201\321\202\320\276\320\262\320\276\320\265 \321\201\320\276\320\276\320\261\321\211\320\265\320\275\320\270\320\265!\n", 58) = 58
```
Здесь `write(1, ...)` означает запись в файловый дескриптор `1` (stdout).
