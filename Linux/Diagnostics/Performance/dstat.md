# `dstat` (Versatile Resource Statistics)

## Определение

**`dstat`** — это универсальный инструмент для мониторинга производительности системы в реальном времени. Утилита объединяет возможности классических инструментов, таких как [`vmstat`](../Memory/vmstat.md), [`iostat`](../Filesystem/iostat.md), `netstat` и `ifstat`, предоставляя единый поток данных с цветовой индикацией. Она позволяет наблюдать за всеми ресурсами системы одновременно, выявлять корреляции между нагрузками и экспортировать данные для последующего анализа.

## Основные концепции

### Эволюция: dstat, dool и pcp-dstat

Оригинальный проект `dstat` (Python 2) официально признан устаревшим (deprecated). В современных системах используются два основных наследника:

1.  **`pcp-dstat` (Performance Co-Pilot):**
    *   **Статус:** Промышленный стандарт (входит в состав PCP 7.x).
    *   **Особенности:** Поддерживает удаленный мониторинг и ретроспективный анализ (воспроизведение логов).
    *   **Рекомендация:** Использовать в Production-окружениях и для мониторинга удаленных систем.
2.  **`dool`:**
    *   **Статус:** Прямой форк оригинального `dstat`, портированный на Python 3.
    *   **Особенности:** Полная совместимость со старыми Python-плагинами. Не требует установки серверных компонентов (демонов).
    *   **Рекомендация:** Использовать для быстрой локальной отладки и на системах без PCP.

### Архитектура и система плагинов

`dstat` построен на модульной архитектуре плагинов. Каждый флаг (`-c`, `-d`, `-m`) активирует соответствующий плагин, который читает данные из `/proc`, `/sys` или собственных источников ядра и форматирует вывод. В отличие от монолитных утилит, это позволяет комбинировать любые группы метрик в единой временной шкале.

Плагины делятся на три категории:
- **Встроенные (core):** CPU, память, диск, сеть, swap, загрузка, прерывания, переключения контекста.
- **Расширенные (ext):** `--vm-adv`, `--nfs3`, `--nfsd4`, `--innodb-buffer`, `--gpfs`.
- **Сторонние:** Плагины для конкретных приложений (Redis, MySQL, PostgreSQL, Apache). Устанавливаются в `/usr/share/dstat/` или `~/.dstat/`.

### Преимущества мониторинга в режиме «свитка»

В отличие от интерактивных утилит ([`top`](../Processes/top.md), [`htop`](../Processes/htop.md)), которые обновляют экран, `dstat` выводит данные построчно (rolling log). Это критически важно для:
- **Обнаружения всплесков (spikes):** Кратковременные пики нагрузки не исчезают с экрана.
- **Корреляционного анализа:** Можно визуально сопоставить момент роста сетевого трафика с ростом нагрузки на диск или CPU.
- **Цветовой индикации:** Значения (B, KB, MB, GB) подсвечиваются разными цветами, что позволяет мгновенно оценить масштаб нагрузки.

### Цветовая индикация

Цвета в выводе `dstat` сигнализируют о пороговых значениях:
- **Зеленый:** Нормальные значения.
- **Красный:** Превышение безопасного порога (например, `%util` > 90% или высокий `await`).
- **Желтый:** Предупреждение (например, рост очереди диска).

Цветовая схема может отличаться в зависимости от темы терминала. Для перенастройки используйте переменную окружения `COLUMNS` или флаг `--noheaders` для машинного парсинга.

### Установка

```bash
# Debian / Ubuntu (pcp-dstat часто идет как 'dstat' по умолчанию)
sudo apt install pcp-system-tools  # pcp-dstat
sudo apt install dool              # dool

# RHEL / Fedora / CentOS
sudo dnf install pcp-system-tools

# Arch Linux
sudo pacman -S dool
```

## Предварительные требования

### Аппаратные требования
- Доступ к целевому блочному устройству для анализа дисковых метрик.
- Для eBPF-плагинов требуется ядро 4.9+ с включенным `CONFIG_BPF` и `CONFIG_BPF_SYSCALL`.
- Для PSI (Pressure Stall Information) требуется ядро 4.20+ с включенным `CONFIG_PSI`. Проверка: `grep CONFIG_PSI /boot/config-$(uname -r)`.

### Программные требования
- **`dool`:** Python 3.7+ (проверка: `python3 --version`).
- **`pcp-dstat`:** PCP 5.0+ (проверка: `pminfo --version`).
- Терминал с поддержкой ANSI-цветов для корректного отображения индикации.

### Настройка прав доступа
Для сбора расширенных метрик (включая статистику по процессам) требуются права root или соответствующие capabilities:
```bash
# Временное изменение (до перезагрузки)
sudo sysctl -w kernel.perf_event_paranoid=-1

# Постоянное изменение
echo "kernel.perf_event_paranoid = -1" | sudo tee -a /etc/sysctl.d/99-perf.conf
sudo sysctl --system
```

### Проверка установки
```bash
# Версия dool
dool --version

# Версия pcp-dstat
pcp-dstat --version

# Доступные плагины
dool --list
# или
pcp-dstat --list
```

## Практические сценарии

### Комплексный мониторинг ресурсов

Запуск без параметров выводит базовый набор: CPU, диски, сеть, пейджинг и системные прерывания.

```bash
dstat 1 10
# 1 — интервал в секунды, 10 — количество отсчетов
```

### Per-CPU анализ и steal time

Для выявления неравномерной загрузки ядер на SMP-системах или при проблемах с планировщиком:

```bash
# Разбивка по каждому CPU (до 32 ядер)
dstat -c --cpu-* 1

# На виртуальных машинах: отслеживание украденного времени (%steal)
# Высокий steal (>10%) указывает на contention на гипервизоре или overcommit
dstat -c -- steal 1
```

### Анализ памяти и page faults

```bash
# Подробная статистика памяти с page faults
dstat -m --vm -gd 1

# Критичные метрики:
# - majf: major faults (обращения к диску/swap)
# - minf: minor faults (кэш-промахи)
# - used: используемая RAM
# - buf: память, занятая buffer cache
```

### Мониторинг прерываний и переключений контекста

```bash
# Системные прерывания (int) и добровольные переключения контекста (csw)
dstat -y 1

# Высокий csw (>100k/сек на ядро) указывает на контенденцию или переключение между процессами
# Высокий int указывает на проблемы с оборудованием или сетевым стеком
```

### Сетевая диагностика (TCP/UDP/Unix sockets)

```bash
# Статистика TCP-сокетов (listening, active, time_wait)
dstat --tcp --socket

# Детализация по UDP и ошибкам
dstat --udp --tcp --err 1

# Для корреляции сетевых ошибок с загрузкой:
dstat -n --tcp --err --top-cpu 1
```

### Анализ эффективности диска

```bash
# Утилизация и подробная дисковая статистика
dstat -d --disk-util --fs 1

# Для NVMe и современных SSD: orient на aqu-sz (глубину очереди) и await
# dstat не показывает await напрямую; используйте iostat -xz 1 для детализации
dstat -d --disk-util 1
```

### Выявление процессов-виновников нагрузки

```bash
# Процессы, потребляющие максимум CPU, RAM и I/O прямо сейчас
dstat -c --top-cpu --top-mem --top-io
```

### Корреляционный анализ при инцидентах

SRE-сценарий: при срабатывании алерта на high latency или dropped connections, `dstat` позволяет за 30 секунд собрать «снимок» всех ресурсов и экспортировать в CSV для post-mortem:

```bash
# Снимок системы на момент инцидента
dstat --output incident_snapshot_$(date +%Y%m%d_%H%M%S).csv -cdnmsy 1 30

# Параметры:
# -c CPU, -d диск, -n сеть, -m память, -s swap, -y прерывания/контекст
```

### Экспорт данных в CSV

```bash
dstat --output performance_report.csv -cdn 5 100
```

Для автоматизации можно использовать заголовок CSV:
```bash
dstat --output report.csv --nocolor -cdnm 1 60
```

### Регрессионное тестирование производительности в CI/CD

```bash
# В Makefile или CI-скрипте
DSTAT_BASELINE=baseline.csv
DSTAT_CURRENT=current.csv

# Сбор baseline
dstat --nocolor --output $DSTAT_BASELINE -cdnm 1 30 > /dev/null

# После деплоя: сбор current
dstat --nocolor --output $DSTAT_CURRENT -cdnm 1 30 > /dev/null

# Сравнение: отклонение > 5% по CPU или памяти = fail
python3 ci/compare_dstat.py $DSTAT_BASELINE $DSTAT_CURRENT --threshold 5
```

## Устранение неисправностей

| Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| `ImportError: No module named dstat` или `dool` не найден | Плагин не установлен или путь к плагинам некорректен | `dool --list` или `ls /usr/share/dstat/` | Установите `dstat-plugin-<name>` или проверьте `PYTHONPATH` |
| Нет данных по процессам (`--top-cpu` пуст) | Недостаточно прав или `perf_event_paranoid` слишком строгий | `sudo dstat -c --top-cpu` | Запустите с `sudo` или настройте `perf_event_paranoid` |
| Пустой CSV-файл | Нет прав на запись или путь некорректен | `ls -la output.csv` | Укажите абсолютный путь и проверьте права |
| Цвета отображаются как Escape-коды | Терминал не поддерживает ANSI или `TERM` не установлен | `echo $TERM` | Установите `TERM=xterm-256color` или используйте `--nocolor` |
| Вывод обрезается или сдвинут | Ширина терминала меньше, чем количество активных плагинов | `stty size` | Увеличьте ширину терминала или используйте `--quiet` |
| Высокий overhead самого dstat | Слишком частый опрос (<0.5 сек) или плагины с тяжелыми источниками | `pidstat -p $(pgrep dool) 1` | Увеличьте интервал до 1-2 сек, отключите редкие плагины |
| `--tcp` показывает нули | Ядро старше 2.6.32 или stat-файлы не экспортируют TCP метрики | `cat /proc/net/tcp` | Обновите ядро или используйте `ss -s` в связке |

## Рекомендации

### Best Practices

1. **Используйте `dool` для локальной отладки, `pcp-dstat` для Production.** `dool` не требует серверных компонентов и быстрее запускается. `pcp-dstat` обеспечивает удаленный доступ и хранение исторических метрик.
2. **Ограничивайте интервал сбора 1-2 секундами.** Интервалы <0.5 сек создают ненужную нагрузку на CPU и диск без смыслового прироста для большинства диагностических задач.
3. **Всегда экспортируйте в CSV при расследовании инцидентов.** Текстовый вывод исчезает из истории терминала; CSV позволяет перестроить графики и сравнить с baseline.
4. **Комбинируйте с `pidstat` для per-process анализа.** `dstat` показывает агрегированную картину, но не идентифицирует PID. Для связки «метрика → процесс» используйте [`pidstat`](../Processes/pidstat.md).
5. **Используйте `--nocolor` в скриптах и CI.** Цветные Escape-коды сломают парсинг `awk`/`sed`.
6. **Не смешивайте `dstat` с `sar` для одного и того же метрического интервала.** `dstat` для real-time, `sar` для долгосрочных трендов. См. [`sar`](./sar.md).

### Методология диагностики (SRE)

1. **Шаг 1 — Первичная разведка (30 сек):**
   ```bash
   dstat -cdnmsy 1 5
   ```
   Оцените CPU, диск, сеть, память, swap, прерывания и контекстные переключения одновременно.

2. **Шаг 2 — Локализация ресурса:**
   Если рост `%wa` — перейдите к [`iostat`](../Filesystem/iostat.md) и [`iotop`](../Filesystem/iotop.md).
   Если рост `%usr` + высокий `csw` — перейдите к [`pidstat`](../Processes/pidstat.md) и [`perf`](./perf.md).
   Если сетевые ошибки — используйте [`nstat`](../Networking/network_cli_tools.md) и `ss`.

3. **Шаг 3 — Сбор доказательств:**
   Запустите `dstat --output incident.csv -cdnmsy 1 30` для фиксации полной картины в момент пика.

4. **Шаг 4 — Постмортем:**
   Импортируйте CSV в Grafana, Excel или Python (pandas) для построения графиков и корреляционного анализа.

## Ограничения и особенности

### Аппаратные ограничения
- **Агрегация по дискам:** На системах с сотнями дисков (SAN, large-scale NVMe) вывод `dstat -d` становится нечитаемым. Используйте фильтрацию через `grep` или переходите к `iostat -p`.
- **Счетчики PMU:** В отличие от [`perf`](./perf.md), `dstat` не имеет доступа к аппаратным счетчикам (PMC) процессора и не может выявлять микроархитектурные проблемы (cache misses, branch mispredictions).

### Программные ограничения
- **Отсутствие исторических логов:** `dstat` не пишет логи на диск самостоятельно. Для хранения истории требуется перенаправление вывода (`--output` или `tee`).
- **Оверхед:** При частоте опроса <0.5 сек и большом количестве плагинов overhead может достигать 1-2% CPU. Для production мониторинга используйте `pcp-dstat` с накоплением в PMDA.
- **Парсинг вывода:** Цветной вывод не предназначен для машинного парсинга. Всегда используйте `--nocolor` в скриптах.

### Особенности в контейнерах
- Внутри контейнера `dstat` видит только ресурсы контейнера (cgroup). Для общесистемного мониторинга запускайте `dstat` на хосте.
- Плагины, читающие `/proc` напрямую, могут показывать неполную картину из-за namespaces.

### Особенности на виртуализации
- **Steal time:** Метрика `%steal` доступна только если гипервизор экспортирует её через паравиртуализацию (KVM, Xen). В некоторых облачных окружениях steal time невидим внутри гостя.
- **Дисковые метрики:** На виртуальных дисках `%util` может показывать ~100% даже при низкой фактической загрузке из-за особенностей эмуляции. Для точной диагностики используйте PSI (`/proc/pressure/io`) и [`iotop`](../Filesystem/iotop.md).

## Дополнительная информация

### Возможности PCP 7.x (pcp-dstat)

В современных системах `pcp-dstat` получил значительные обновления:
- **Наносекундная точность:** Высокое разрешение временных меток.
- **Новые домены метрик:** Поддержка Btrfs, GPU (Apple Silicon) и энергетических сенсоров.
- **Удаленный просмотр:** Мониторинг другого хоста через `dstat --host <hostname>`.
- **Ретроспективный анализ:** Возможность воспроизведения исторических метрик через `pmrep` или Grafana.

### Полезные плагины и флаги

- `-y`, `--sys`: Статистика прерываний (int) и переключений контекста (csw).
- `--vm-adv`: Расширенная статистика виртуальной памяти (dirty, writeback).
- `--nfs3`, `--nfsd4`: Мониторинг сетевых файловых систем.
- `--innodb-buffer`: Статистика буфера InnoDB для баз данных.
- `--lock`: Статистика блокировок файловой системы (Linux 5.5+).
- `--battery`: Заряд батареи ноутбука (только `dool`).
- `--freespace`: Свободное место на смонтированных ФС.
- `--apc`: Статистика ИБП через `apcupsd`.
- `--md`: Состояние RAID-массивов (mdadm).

### Сравнение с аналогами

| Инструмент | Сильные стороны | Ограничения | Типичное применение |
| :--- | :--- | :--- | :--- |
| **`dstat`** | Гибкий вывод, модули, цветной, rolling log | Нет исторических логов, нет PSI | Ad-hoc диагностика, Real-time |
| **[`sar`](./sar.md)** | Долгосрочная история, стандартный в большинстве distro | Дискретность 10 минут, нет PSI | Capacity planning, месячные тренды |
| **[`atop`](./atop.md)** | Исторические логи, PSI, завершённые процессы, GPU | Бинарный формат, overhead демона | Post-mortem, nightly сборы, deep-dive |
| **[`pidstat`](../Processes/pidstat.md)** | Per-process/thread, cron-дружественный | Только числа, нет PSI | Регулярный сбор по процессам |
