# Диагностика дискового ввода-вывода (I/O) в Linux

**Диагностика дисковой подсистемы** — это процесс выявления узких мест (bottlenecks) в цепочке от системного вызова приложения до физического накопителя. В современных системах (ядро 6.x+, NVMe, blk-mq) фокус сместился с анализа пропускной способности (throughput) на анализ **распределения задержек (latency)** и **давления на ресурсы (pressure)**.

## Определение

- **Pressure Stall Information (PSI)**: Механизм ядра Linux для измерения реального «голодания» системы. Показывает процент времени, когда процессы были заблокированы в ожидании завершения I/O. Самый надежный индикатор влияния диска на отзывчивость приложений.
- **I/O Wait (`%wa`)**: Процент времени CPU, проведенный в ожидании дисковых операций при отсутствии других задач. Может вводить в заблуждение на многоядерных системах и NVMe.
- **Задержка (Await/Latency)**: Среднее время выполнения одного запроса блочным устройством, включая время в очереди.
- **blk-mq (Multi-Queue)**: Современная многоочередная архитектура стека I/O ядра Linux, устраняющая узкие места при работе с быстрыми накопителями (NVMe).
- **Uninterruptible Sleep (D-state)**: Состояние процесса, ожидающего ввода-вывода. Процессы в `D` увеличивают `Load Average` и не реагируют на сигналы завершения.
- **avgqu-sz (Average Queue Size)**: Средняя длина очереди запросов к устройству. Рассчитывается из Weighted I/O time (поле 14 `/proc/diskstats`). Для HDD порог перегрузки — >2, для SSD/NVMe — >4–8.
- **f_await (Flush Await)**: Среднее время выполнения операций сброса кэша (flush). В ядрах 5.5+ данные берутся из полей 19–20 `/proc/diskstats`. Критично для баз данных.

## Основные концепции

### Современный стек ввода-вывода

Процесс I/O в ядре 6.x+ организован следующим образом:
1. **Application**: Использует `read/write`, `mmap` или современный асинхронный интерфейс **`io_uring`**.
2. **Page Cache**: Ядро кэширует данные в RAM. Процесс **Writeback** (потоки `kworker/u*:flush-*`) асинхронно сбрасывает «грязные» страницы на диск.
3. **blk-mq**: Распределяет запросы по нескольким очередям (по одной на каждое ядро CPU), что критично для NVMe.
4. **Device**: Аппаратная обработка. Для SSD/NVMe характерно параллельное выполнение тысяч команд.

### Почему iostat может лгать

Традиционные метрики часто неактуальны для SSD и NVMe:
- **`%util`**: Значение 100% на NVMe **не означает** насыщения. Диск может обрабатывать еще тысячи запросов параллельно. Ориентируйтесь на `aqu-sz` (глубину очереди).
- **`svctm`**: **Полностью устарела (DEPRECATED)**. В архитектуре blk-mq этот показатель математически невозможно рассчитать корректно. Его следует игнорировать.
- **Средний `await`**: Прячет «хвосты» задержек. 99% быстрых запросов могут скрыть 1% критически медленных. Используйте гистограммы.

### PSI: some и full

`/proc/pressure/io` содержит два ключевых поля:
- **`some`**: процент времени, когда **хотя бы один** процесс ждал I/O. Показывает влияние на отзывчивость приложений (latency-ориентированная метрика).
- **`full`**: процент времени, когда **все** активные процессы ждали I/O. Показывает критическое насыщение (saturation).
- `avg10`, `avg60`, `avg300`: скользящие средние за 10, 60 и 300 секунд. `total` — кумулятивное время с момента загрузки.

### cgroups v2 I/O controller

В системах с systemd и контейнерами контроллер `io` (cgroups v2) предоставляет метрики, дополняющие `iostat`:
- **`io.stat`**: Кумулятивная статистика (`rbytes`, `wbytes`, `rios`, `wios`, `dbytes`, `dios`) для каждого cgroup. Позволяет увидеть, какой slice/контейнер генерирует нагрузку.
- **`io.max`**: Жесткие лимиты (BPS/IOPS) могут ограничивать устройства ниже физического потенциала. Если `await` высокий, а `%util` низкий — проверьте `io.max` в соответствующем cgroup.
- **Делегирование**: Для корректной работы `io.stat` внутри контейнера родительский slice/systemd должен иметь `Delegate=yes`.

## Предварительные требования

### Аппаратные требования
- Доступ к целевому блочному устройству (`/dev/sdX`, `/dev/nvmeXnY`).
- Для eBPF-инструментов (`bpftrace`, `bcc-tools`) требуется ядро 4.9+ с `CONFIG_BPF=y` и `CONFIG_BPF_SYSCALL=y`.
- Для PSI требуется ядро 4.20+ с `CONFIG_PSI=y`.
- Для TASK_DELAY_ACCT требуется `CONFIG_TASK_DELAY_ACCT=y` (нужна для `iotop`, `pidstat`).

### Программные требования

```bash
# Debian/Ubuntu
sudo apt update && sudo apt install -y sysstat iotop bpfcc-tools bpftrace perf-tools-unstable smartmontools nvme-cli fatrace pidstat procps

# RHEL/CentOS/Fedora
sudo dnf install -y sysstat iotop bcc-tools bpftrace perf smartmontools nvme-cli fatrace pidstat procps-ng

# Arch Linux
sudo pacman -S sysstat iotop bpftrace bcc-tools fatrace smartmontools nvme-cli procps

# openSUSE/SLES
sudo zypper install -y sysstat iotop bpftrace bcc-tools fatrace smartmontools nvme-cli procps
```

### Проверка конфигурации ядра

```bash
# Статистика задержек задач (нужна для iotop, pidstat)
grep TASK_DELAY_ACCT /boot/config-$(uname -r)
# → CONFIG_TASK_DELAY_ACCT=y

# PSI (нужна для cat /proc/pressure/io)
grep PSI /boot/config-$(uname -r)
# → CONFIG_PSI=y

# eBPF (нужна для biolatency, biosnoop, bpftrace)
grep -E "CONFIG_BPF=|CONFIG_BPF_SYSCALL=" /boot/config-$(uname -r)
# → CONFIG_BPF=y
# → CONFIG_BPF_SYSCALL=y
```

### Включение сбора данных

```bash
# Включение TASK_DELAY_ACCT на лету (если не включена в ядре)
echo 1 | sudo tee /proc/sys/kernel/task_delayacct

# Проверка PSI
[ -e /proc/pressure/io ] && echo "PSI Enabled" || echo "PSI Disabled — добавьте psi=1 в GRUB"

# Включение исторического сбора sysstat (для sar, iostat с историей)
sudo systemctl enable --now sysstat
```

## Практические сценарии

### Алгоритм современной диагностики

#### Шаг 1: Оцените влияние на систему через PSI

```bash
cat /proc/pressure/io
# → some avg10=15.20 avg60=10.05 avg300=5.00 total=1234567
# some avg10 > 5-10% — система «тормозит» из-за диска.
# full avg10 > 5% — все процессы заблокированы (критическая ситуация).
```

**Ожидаемый результат:** Подтверждено влияние I/O на задержки. Валидация: если `some avg10 < 5%`, переходите к анализу CPU/RAM.

#### Шаг 2: Локализуйте устройство через `iostat`

```bash
iostat -xz 1
# Смотрите на await (задержка) и aqu-sz (очередь).
```

**Ожидаемый результат:** Выявлено устройство (`sda`, `nvme0n1`, `dm-1`) с аномальными метриками. Валидация: `await` стабильно выше порога на протяжении 3+ измерений.

#### Шаг 3: Найдите процесс-виновника

```bash
iotop -Pa -o
# Или через pidstat:
pidstat -d 1
```

**Ожидаемый результат:** Идентифицирован PID процесса с наибольшим `DISK WRITE`/`DISK READ`. Валидация: `pidstat -d` показывает тот же PID, что и `iotop`.

#### Шаг 4: Проанализируйте каналы ожидания (wchan)

```bash
ps -eo pid,state,wchan:30,comm | grep " D "
```

**Ожидаемый результат:** Указана конкретная функция ядра (`io_schedule`, `ext4_inode_lock` и т.д.), указывающая на тип проблемы.

#### Шаг 5: Анализируйте распределение задержек через eBPF

```bash
# Построение гистограммы задержек (Essential)
sudo biolatency-bpfcc -D 1 10

# Отслеживание каждого запроса в реальном времени
sudo biosnoop-bpfcc
```

**Ожидаемый результат:** Выявлены P95/P99 выбросы задержек (`biolatency`) или конкретные запросы > 100 мс (`biosnoop`).

#### Шаг 6: Проверьте аппаратный уровень

```bash
# Логи ядра на наличие таймаутов и ошибок
dmesg -T | grep -iE "timeout|blocked|error|reset|nvme|scsi|ata"

# SMART-статистика
sudo smartctl -a /dev/sda | grep -E 'SMART|Reallocated|Pending|Current_Pending_Sector|Temperature'

# NVMe — подробный лог
sudo nvme smart-log /dev/nvme0 2>/dev/null | grep -E 'critical_warning|temperature|percentage_used|available_spare'
```

**Ожидаемый результат:** Выявлены физические ошибки (bad sectors, failing controller, overheating) или проблемы с RAID.

## Устранение неполадностей

| Симптом | Возможная причина | Метод диагностики | Решение |
| :--- | :--- | :--- | :--- |
| `await` высокий, `iowait` низкий | Многоядерность, полезная нагрузка маскирует ожидание | `cat /proc/pressure/io` (some avg10) | Анализ через PSI, а не `top`/`htop` |
| `await` высокий, `%util` низкий | Внешний троттлинг (СХД, hypervisor) или проблема в очереди планировщика | `iostat -xz 1` (смотрим `avgqu-sz`, `r/s`, `w/s`) | Замена диска, изменение scheduler на `deadline`/`bfq`, увеличение stripe size (RAID) |
| Процессы в `D-state`, но диск простаивает | Lock Contention (VFS/inode) или зависший NFS | `ps -eo pid,state,wchan:30,comm \| grep " D "`, `nfsstat -m` | Перезапуск NFS-демона, вынос журнала на отдельный диск |
| `biolatency` показывает пики >100 мс | Аппаратная ошибка или throttling (в VM/СХД) | `dmesg`, `smartctl`, `cat /proc/pressure/io` | Замена диска, проверка контроллера или гипервизора (IOPS limit) |
| Высокий `iowait` при `await` < 5 мс | Устройство действительно быстрое, но CPU не успевает обрабатывать прерывания | `mpstat -P ALL 1`, `/proc/interrupts` | Настройка `irqbalance`, ручная привязка прерываний |
| `iotop` показывает только `kworker` | Фоновый writeback или журналирование | `biosnoop-bpfcc`, `cat /proc/meminfo \| grep Writeback` | Корректировка `vm.dirty_*` параметров. Подробнее: [Роль kworker и процессов writeback](./DiskIO/kworker_flush.md) |
| `f_await` >> `await` | Отсутствие PLP (Power Loss Protection) или переполнение SLC-кэша | `iostat -xz 1` (смотрим `f_await`) | Проверка `nvme smart-log`, увеличение `vm.dirty_ratio` для редких fsync |

## Валидация

Каждая диагностическая сессия должна завершаться проверкой:

1. **Базовый сценарий (Baseline):** Зафиксируйте метрики в нормальном состоянии (`iostat -xz 1 10`, `cat /proc/pressure/io`).
2. **Стресс-тест:** Воспроизведите проблему (`fio`, `stress-ng`, `dd if=/dev/zero of=/tmp/test bs=4K count=1000000 oflag=direct`).
3. **Диагностика:** Примените методики из сценария.
4. **Валидация:** После remediation метрики должны вернуться к baseline.
5. **Мониторинг:** Настройте алерты для предотвращения рецидивов.

### Кросс-инструментальная согласованность

| Инструмент | Что проверять | Ожидаемое здоровое значение |
| :--- | :--- | :--- |
| `cat /proc/pressure/io` | Давление I/O | `some avg10 < 5%` |
| `iostat -xz 1` | Задержка устройства | `await < 1ms` (SSD/NVMe), `< 20ms` (HDD) |
| `iostat -xz 1` | Очередь | `aqu-sz < 2` (HDD), `< 4–8` (NVMe) |
| `iotop -o` | Процесс-виновник | Виден PID с `DISK WRITE`/`DISK READ` |
| `biolatency-bpfcc` | Tail Latency | P99 < 10ms |
| `smartctl -a` | Здоровье диска | `Reallocated_Sector_Ct = 0`, `Temperature < 60°C` |
| `dmesg` | Аппаратные ошибки | Нет строк `timeout`, `error`, `reset` |

## Рекомендации (Best Practices)

1. **Проверяйте PSI первым:** Перед тем как углубляться в трассировку процессов, убедитесь, что проблема действительно в I/O. `cat /proc/pressure/io` даёт ответ за секунду.
2. **Не доверяйте `%util` на NVMe:** На многоочередных устройствах 100% утилизации не означает насыщение. Используйте `aqu-sz` и P99 latency.
3. **Используйте `iostat -xz` без исключения:** Флаг `-x` обязателен для просмотра расширенной статистики. Всегда добавляйте `-z` для исключения неактивных устройств.
4. **Коррелируйте метрики:** Никогда не полагайтесь на одну утилиту. Сочетайте `iostat` (устройства), `pidstat` (процессы), `vmstat` (система) и PSI (давление).
5. **Проверяйте оборудование:** При высокой задержке без явного виновника первым делом запустите `smartctl` и `dmesg`. Физические ошибки часто маскируются под «невидимый» I/O.
6. **Изучайте Wait Channels:** `cat /proc/<PID>/wchan` часто даёт больше информации, чем десять минут просмотра `iotop`.
7. **Не игнорируйте файловую систему:** Метаданные (inode, journal) могут становиться узким местом даже на быстрых NVMe.
8. **Настраивайте алерты:** Используйте `node_exporter` с PSI-метриками для proactive-мониторинга. Пороги: `some avg10 > 5%` (warning), `full avg10 > 5%` (critical).

## Ограничения и особенности

### Многоядерные системы

`%iowait` — системная метрика, распределенная по всем ядрам. На 32-ядерном сервере `%wa = 3%` может означать, что одно ядро простаивает 100% времени. Используйте PSI или `mpstat -P ALL 1` для точного анализа.

### Виртуализация (KVM, VMware, Xen)

- **`%steal`** в `iostat`/`mpstat` показывает время, «украденное» гипервизором. Постоянный `%steal > 5%` — признак overselling или noisy neighbor.
- Паравиртуализированные драйверы (`virtio-blk`, `vmw_pvscsi`) могут кэшировать запросы, скрывая реальную задержку от гостевой ОС.
- Внешний троттлинг (SAN, hypervisor) может вызывать высокий `await` при низком `%util`.

### cgroups v1 vs v2

- **cgroups v1**: `io.stat` существует только для blkio контроллера. Нет PSI (`io.pressure` отсутствует). Используйте `cat /sys/fs/cgroup/blkio/*/io.stat`.
- **cgroups v2**: `io.pressure` доступен, что позволяет измерять давление на I/O внутри контейнера. Лимиты `io.max` создают искусственный троттлинг.
- Внутри контейнера `iotop` видит только процессы этого контейнера.

### Сетевые ФС (NFS, FUSE, CIFS)

- NFS добавляет сетевую задержку, которая в `iotop` выглядит как обычный I/O wait. Используйте `nfsstat -m` и `nfsiostat`.
- FUSE-файловые системы (`sshfs`) блокируют процесс в пользовательском пространстве. Видно по `wchan` (`fuse_dev_read`).
- При зависании NFS-сервера поток writeback уходит в `D-state` на неопределённое время. Единственное решение — `umount -f` или перезагрузка.

### 32-битные системы

На архитектурах, отличных от x86_64, формат `/proc/<pid>/io` остается совместимым, но некоторые eBPF-утилиты могут требовать перекомпиляции.

### SSD и NVMe

- **Write Amplification**: Внутренний GC SSD может увеличивать физическую запись в 3–10 раз относительно логической. `await` может быть низким, но износ носителя ускоряется.
- **SLC-кэш**: Высокий `await` после заполнения SLC-кэша — нормальное поведение consumer SSD. Ориентируйтесь на P99 latency, а не на средние значения.
- **Flush-штормы**: Высокое `f_await` при низком общем `await` указывает на отсутствие PLP (Power Loss Protection).

### RAID и шифрование

- **Hardware RAID**: Контроллер скрывает отдельные диски. `iostat` показывает только виртуальное устройство. Для диагностики используйте утилиты вендора (`megacli`, `hpacucli`).
- **dm-crypt (LUKS)**: Шифрование добавляет overhead на CPU. При высокой нагрузке процесс `dm-crypt` может потреблять CPU, маскируя проблему как CPU-bound.

### io_uring

Интерфейс `io_uring` (ядро 5.1+) обходит классические `read`/`write`, на которых базируется `taskstats`. `iotop` и `pidstat` не видят такую нагрузку. Для диагностики используйте `perf record -e 'block:block_rq_issue'` или `bpftrace` на `io_uring_submit_sqe`.

### Writeback и kworker

Физический сброс выполняют `kworker`, а не исходный процесс. `iotop` показывает `kworker`, а не приложение-писатель. Для атрибуции используйте `bpftrace` на `writeback_dirty_page`.

### Формат секторов в `/proc/diskstats`

В `/proc/diskstats` сектор всегда равен 512 байтам, независимо от физического размера сектора диска (4K, 8K). Для перевода в байты: `(sectors * 512)`.

## Сравнение инструментов

| Уровень | Инструменты | Что позволяют увидеть |
| :--- | :--- | :--- |
| **Система (PSI)** | `cat /proc/pressure/io`, `vmstat` | Общее влияние нехватки I/O на задержки приложений. |
| **Устройство** | `iostat`, `/proc/diskstats`, `sar -d` | Утилизация физических дисков, задержки (`await`, `aqu-sz`), очереди. |
| **Контейнер** | `systemd-cgtop`, `io.stat` (cgroup v2), `io.max` | Изоляция нагрузки и эффекты лимитирования (Throttling). |
| **Процесс** | `iotop`, `pidstat -d`, `/proc/<pid>/io` | Распределение нагрузки (чтение/запись) между PID. |
| **Файловая система** | `fatrace`, `lsof`, `strace`, `opensnoop` | Конкретные файлы и системные вызовы (`read`/`write`, `openat`). |
| **Блочный уровень** | `blktrace`, `biolatency`, `biosnoop` | Жизненный цикл запроса: от очереди до подтверждения контроллером. |
| **Ядро (Events)** | `perf`, `bpftrace` | Активность `io_uring`, внутренние блокировки ФС, прерывания. |

Детальное сравнение возможностей `iostat`, `iotop`, `biolatency` и `syswatch` приведено в **[таблице сравнения](./DiskIO/diagnostic_tools_comparison.md)**.
