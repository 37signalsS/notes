# Диагностика дискового ввода-вывода (I/O) в Linux

**Диагностика дисковой подсистемы** — это процесс выявления узких мест (bottlenecks) в цепочке от системного вызова приложения до физического накопителя. В современных системах (2025–2026) фокус сместился с анализа пропускной способности (throughput) на анализ **распределения задержек (latency)** и **давления на ресурсы (pressure)**.

## Определение

- **Pressure Stall Information (PSI)**: Механизм ядра Linux для измерения реального «голодания» системы. Показывает процент времени, когда процессы были заблокированы в ожидании завершения I/O. Самый надежный индикатор влияния диска на отзывчивость приложений.
- **I/O Wait (`%wa`)**: Процент времени CPU, проведенный в ожидании дисковых операций при отсутствии других задач. Может вводить в заблуждение на многоядерных системах и NVMe.
- **Задержка (Await/Latency)**: Среднее время выполнения одного запроса блочным устройством, включая время в очереди.
- **blk-mq (Multi-Queue)**: Современная многоочередная архитектура стека I/O ядра Linux, устраняющая узкие места при работе с быстрыми накопителями (NVMe).
- **Uninterruptible Sleep (D-state)**: Состояние процесса, ожидающего ввода-вывода. Процессы в `D` увеличивают `Load Average` и не реагируют на сигналы завершения.

## Основные концепции

### Современный стек ввода-вывода

Процесс I/O в ядре 6.x+ организован следующим образом:
1. **Application**: Использует `read/write`, `mmap` или современный асинхронный интерфейс **`io_uring`**.
2. **Page Cache**: Ядро кэширует данные в RAM. Процесс **Writeback** (потоки `kworker/u*:flush-*`) асинхронно сбрасывает «грязные» страницы на диск.
3. **blk-mq**: Распределяет запросы по нескольким очередям (по одной на каждое ядро CPU), что критично для NVMe.
4. **Device**: Аппаратная обработка. Для SSD/NVMe характерно параллельное выполнение тысяч команд.

### Почему iostat может лгать

Традиционные метрики часто неактуальны для SSD и NVMe:
- **`%util`**: Значение 100% на NVMe **не означает** насыщения. Диск может обрабатывать еще тысячи запросов параллельно. Ориентируйтесь на `aqu-sz` (глубину очереди).
- **`svctm`**: **Полностью устарела (DEPRECATED)**. В архитектуре blk-mq этот показатель математически невозможно рассчитать корректно. Его следует игнорировать.
- **Средний `await`**: Прячет «хвосты» задержек. 99% быстрых запросов могут скрыть 1% критически медленных. Используйте гистограммы.

## Практические сценарии

### Алгоритм современной диагностики

1. **Оцените влияние на систему через PSI:**
   ```bash
   cat /proc/pressure/io
   # avg10 > 5-10% — система «тормозит» из-за диска.
   ```
2. **Локализуйте устройство через `iostat`:**
   ```bash
   iostat -xz 1
   # Смотрите на await (задержка) и aqu-sz (очередь).
   ```
3. **Найдите процесс-виновник:**
   ```bash
   iotop -Pa -o
   # Или через pidstat:
   pidstat -d 1
   ```
4. **Анализируйте распределение задержек через eBPF (BCC/bpftrace):**
   ```bash
   # Построение гистограммы задержек (Essential)
   sudo biolatency-bpfcc 10
   
   # Отслеживание каждого запроса в реальном времени
   sudo biosnoop-bpfcc
   ```
