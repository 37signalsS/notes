# `atop` (Advanced System & Process Monitor)

## Определение

**`atop`** — продвинутый интерактивный полноэкранный монитор производительности для Linux, предназначенный для глубокого анализа ресурсов системы. В отличие от стандартных инструментов ([`top`](../Processes/top.md), [`htop`](../Processes/htop.md)), `atop` специализируется на ведении исторических логов и предоставляет наиболее полную картину использования CPU, памяти, дисков и сети, включая данные о завершённых процессах и поддержку современных механизмов ядра, таких как PSI (Pressure Stall Information).

## Основные концепции

### Исторический анализ (Снимки состояния)

Ключевая особенность `atop` — наличие фонового демона (`atop.service`), который через заданные промежутки времени делает «снимки» (snapshots) состояния всей системы и записывает их в бинарные файлы. Это позволяет проводить ретроспективный анализ (post-mortem) инцидентов, которые уже завершились.

- **Пути к логам:** `/var/log/atop/`.
- **Имена файлов:** `atop_YYYYMMDD` (например, `atop_20260809`).
- **Формат:** бинарный, несжатый по умолчанию (начиная с atop 2.8+ поддерживается сжатие gzip).
- **Размер лога:** зависит от `LOGINTERVAL` и `LOGGENERATIONS`. При интервале 60 секунд и хранении 28 дней файл занимает ~300–500 МБ.

### PSI и визуализация давления на ресурсы

Начиная с версий 2.11+, `atop` глубоко интегрирован с механизмом **PSI (Pressure Stall Information)**. Это позволяет увидеть не только загрузку ресурса, но и степень «голодания» процессов из-за его нехватки.

- **Некоторые (Some):** процент времени, когда хотя бы один процесс ожидал ресурса.
- **Полные (Full):** процент времени, когда все не-idle процессы были заблокированы в ожидании ресурса (критический показатель).
- **Бар-графики:** режим визуализации (клавиша `B`), отображающий PSI в виде наглядных шкал для CPU, памяти и дисков.
- **Теоретические основы:** см. [Pressure Stall Information (PSI)](../../Core/kernel/psi.md).

### Комплексный мониторинг ресурсов

`atop` агрегирует данные из `/proc`, сетевого стека, контрольных групп (cgroups) и специфических счётчиков:

- **CPU:** нагрузка на ядра, частота, время в прерываниях, `steal time`. Поддержка до 4096 ядер.
- **Память:** детализация по типам (free, cache, slab), поддержка PSI, мониторинг `oom_score` и `oom_score_adj`.
- **Диск I/O:** нагрузка на блочные устройства, очереди, латентность.
- **Сеть:** трафик по интерфейсам. С использованием **`netatop-bpf`** доступна статистика SNET/RNET на уровне каждого процесса.
- **GPU:** при использовании демона `atopgpud` отображает статистику NVIDIA GPU (отдельно вычислительную и графическую нагрузку).
- **Контейнеры:** автоматическое определение Container ID и имён подов (Pod names).
- **Завершённые процессы:** `atop` сохраняет агрегированную информацию о процессах, завершившихся между снимками, что критично для post-mortem анализа.

### Цветовая индикация

Утилита подсвечивает критические значения нагрузки цветом:

- **Голубой (Cyan):** нормальная работа.
- **Красный (Red):** ресурс исчерпан или находится под критической нагрузкой.
- **Жёлтый (Yellow):** пограничное состояние.

## Предварительные требования

### Аппаратные и программные требования

- **ОС:** Linux с ядром 4.20+ (рекомендуется 5.4+ для полной поддержки PSI и cgroups v2).
- **Архитектура:** x86_64, ARM64.
- **Память:** минимум 512 МБ свободной RAM для демона atop.
- **Диск:** минимум 1 ГБ свободного места под логи (при интервале 60 секунд и retention 28 дней).

### Проверка поддержки PSI

```bash
# Проверка наличия /proc/pressure/
[ -d /proc/pressure ] && echo "PSI включён" || echo "PSI отключён — добавьте psi=1 в параметры ядра GRUB"
```

### Инициализация переменных окружения

```bash
# Убедитесь, что systemd-resolved не мешает сбору DNS-статистики (если используете systemd)
grep -q '^DNS=' /etc/systemd/resolved.conf && echo "DNS настроен" || echo "Проверьте /etc/systemd/resolved.conf"
```

## Установка и настройка

### Установка пакета

```bash
# Debian / Ubuntu
sudo apt update && sudo apt install atop

# RHEL / CentOS / Fedora
sudo dnf install atop

# Arch Linux
sudo pacman -S atop

# Проверка версии
atop -h | head -n 1
# → atop 2.8.1 (2025/03/15) ...
```

### Настройка фонового сбора данных

Для работы режима отчётов необходимо включить службу:

```bash
sudo systemctl enable --now atop
```

**Конфигурация (Retention & Interval):**
Параметры настраиваются в `/etc/default/atop` (Debian/Ubuntu) или `/etc/sysconfig/atop` (RHEL):

- **`LOGINTERVAL`**: интервал между снимками (по умолчанию 600с). Для диагностических целей рекомендуется 60с.
- **`LOGGENERATIONS`**: срок хранения логов в днях (по умолчанию 28).
- **`LOGCOMPRESSION`**: сжатие старых логов (`gzip`).

**Пример конфигурации для production-хоста с высокими нагрузками:**

```bash
# /etc/default/atop
LOGINTERVAL=60
LOGGENERATIONS=14
LOGCOMPRESSION=gzip
```

### Верификация корректной работы демона

```bash
# Проверка статуса службы
systemctl status atop
# ● atop.service - Atop advanced performance monitor
#      Loaded: loaded (/lib/systemd/system/atop.service; enabled; vendor preset: enabled)
#      Active: active (running) ...

# Проверка создания файла лога
ls -lh /var/log/atop/atop_$(date +%Y%m%d)
# -rw-r--r-- 1 root root 4.5M Sep 12 03:00 /var/log/atop/atop_20260912
```

## Практические сценарии

### Сценарий 1: Retrospektive analyse инцидента (Post-Mortem)

**Ситуация:** Приложение упало между 02:00 и 04:00. Нужно определить причину.

```bash
# 1. Открыть лог за текущие сутки
atop -r

# 2. Перейти ко времени начала проблем (02:00)
# В интерактивном режиме: b → 02:00 → Enter

# 3. Проверить, какие процессы завершились в этом интервале
# В atop завершённые процессы подсвечиваются красным вверху экрана
# Нажмите 'q' для выхода изdetailed view, затем 'p' для просмотра завершённых процессов

# 4. Сохранить отчёт в файл
# В atop: c (команда) → atop -w /tmp/atop_incident_$(date +%Y%m%d) 60 12
```

**Валидация:**
- Убедитесь, что в отчёте присутствуют записи с 02:00 до 04:00.
- Проверьте столбцы `RSIZE`, `VGROW`, `MAJFLT` для подозрительных процессов.

### Сценарий 2: Обнаружение утечки памяти в production

**Ситуация:** RAM используется на 95%, нужно найти виновника.

```bash
# Запуск atop в интерактивном режиме с сортировкой по памяти
atop -m

# Нажмите M для сортировки по убыванию RAM
# Обратите внимание на столбцы:
# - RSIZE: резидентная память
# - VGROW: рост виртуальной памяти за последний интервал
# - RGROW: рост резидентной памяти за последний интервал

# Если VGROW > 0 стабильно в течение нескольких интервалов — процесс течёт
# MAJFLT > 0 указывает на чтение страниц с диска (нехватка физической памяти)
```

**Диагностика завершённых OOM-процессов:**

```bash
# Проверка логов systemd journal на предмет OOM Kill
journalctl -u atop --since "1 hour ago" | grep -i "oom\|kill"

# Проверка ядерного лога
dmesg | grep -i "out of memory\|oom-kill"
```

### Сценарий 3: Диагностика дисковой подсистемы (I/O瓶颈)

**Ситуация:** Приложения жаловались на медленный отклик. Нужно понять, связано ли это с диском.

```bash
# 1. Запустите atop и перейдите в детализацию по дискам (клавиша d)
atop -d 1

# 2. Обратите внимание на:
# - KBytes/s: объём данных
# - Avq: средняя длина очереди
# - MSIO: среднее время I/O в миллисекундах
# - %Busy: процент utilisation диска

# 3. Для PSI-анализа нажмите B (бар-графики) и переключитесь на DSK
# some avg10 > 10% = дисковый pressure

# 4. Для экспорта отчёта в файл
atopsar -d -I 1 -f /var/log/atop/atop_$(date +%Y%m%d)
```

### Сценарий 4: Анализ steal time на виртуализированных хостах

**Ситуация:** Хосты KVM/Xen показывают высокую нагрузку CPU, но процессы внутри гостя не потребляют много ресурсов.

```bash
# Запустите atop
atop

# Нажмите g (общий вид) или B (бар-графики)
# Обратите внимание на столбец %steal в секции CPU
# %steal > 10% = гипервизор «отбирает» время у гостя

# Дополнительная проверка через vmstat
vmstat 1 10
# столбец 'st' — steal time

# Действия:
# 1. Проверьте neighbouring гости на хосте (требует доступа к гипервизору)
# 2. Рассмотрите миграцию ВМ на другой физический хост
# 3. Убедитесь, что у ВМ выделено достаточно vCPU и она не overcommitted
```

### Сценарий 5: Ночная автоматизация с atopsar

**Ситуация:** Нужно получать ежедневные отчёты для capacity planning.

```bash
# Создайте скрипт /usr/local/bin/atop-daily-report.sh
cat << 'EOF' | sudo tee /usr/local/bin/atop-daily-report.sh
#!/bin/bash
REPORT_DATE=$(date -d "yesterday" +%Y%m%d)
LOG_FILE="/var/log/atop/atop_${REPORT_DATE}"
REPORT_DIR="/var/log/atop/reports"
mkdir -p "${REPORT_DIR}"

if [ ! -f "${LOG_FILE}" ]; then
    echo "Файл лога ${LOG_FILE} не найден" >&2
    exit 1
fi

# Генерация сводного отчёта
atopsar -c -r ${LOG_FILE} > "${REPORT_DIR}/cpu_${REPORT_DATE}.txt"
atopsar -m -r ${LOG_FILE} > "${REPORT_DIR}/mem_${REPORT_DATE}.txt"
atopsar -d -r ${LOG_FILE} > "${REPORT_DIR}/disk_${REPORT_DATE}.txt"
atopsar -n -r ${LOG_FILE} > "${REPORT_DIR}/net_${REPORT_DATE}.txt" 2>/dev/null || true

# Поиск пикового момента
atopsar -P CPU,PRM,DSK -r ${LOG_FILE} | grep -E "^[0-9]{2}:" | sort -t' ' -k2 -nr | head -n 5 >> "${REPORT_DIR}/peak_${REPORT_DATE}.txt"

echo "Отчёт за ${REPORT_DATE} сохранён в ${REPORT_DIR}"
EOF

sudo chmod +x /usr/local/bin/atop-daily-report.sh

# Добавление в cron
echo "0 6 * * * root /usr/local/bin/atop-daily-report.sh" | sudo tee -a /etc/crontab
```

### Сценарий 6: Мониторинг завершённых процессов для RCA

**Ситуация:** После рестарта сервиса появились zombie-процессы. Нужно понять, какие процессы завершились некорректно.

```bash
# Запустите atop и переключитесь в режим завершённых процессов
atop
# Нажмите 'p' для просмотра завершённых процессов ( exited )

# Для детального просмотра конкретного PID в историческом логе
atop -r /var/log/atop/atop_20260809
# Нажмите 'p', затем введите PID процесса
```

## Устранение неисправностей

### Типичные ошибки

**1. Логи не создаются (`/var/log/atop/` пустой):**

- *Причина:* `atop.service` не запущен или отключён.
- *Решение:*
  ```bash
  sudo systemctl enable --now atop
  sudo systemctl status atop
  ```
- *Верификация:* `ls -l /var/log/atop/atop_$(date +%Y%m%d)` должен существовать.

**2. Ошибка «Cannot open /var/log/atop/atop_YYYYMMDD»:**

- *Причина:* Нет прав на чтение бинарного файла.
- *Решение:* `sudo atop -r /var/log/atop/atop_YYYYMMDD` или добавьте пользователя в группу `adm`.

**3. PSI-столбцы отображаются нулями:**

- *Причина:* Ядро собрано без `CONFIG_PSI` или `psi=0` в GRUB.
- *Проверка:*
  ```bash
  grep CONFIG_PSI /boot/config-$(uname -r)
  # → CONFIG_PSI=y
  ```
- *Решение:* Добавьте `psi=1` в параметры ядра, обновите GRUB и перезагрузитесь.

**4. Сетевая статистика (SNET/RNET) отсутствует:**

- *Причина:* `netatop-bpf` не установлен или демон не запущен.
- *Решение:*
  ```bash
  sudo apt install netatop-bpf  # или сборка из исходников
  sudo systemctl enable --now netatop-bpf
  ```
- *Верификация:* В atop нажмите `n` — столбцы SNET/RNET должны наполняться.

**5. Высокое потребление atop:**

- *Причина:* Слишком частый `LOGINTERVAL` (например, 1 секунда) на высоконагруженном хосте.
- *Решение:* Увеличьте интервал до 30–60 секунд для production. Для краткосрочного диагностирования используйте `atop -r` с меньшим интервалом только на время сбора.

### Диагностические команды

```bash
# Проверка конфигурации atop
ps aux | grep atop
# root      1234  0.0  0.1  123456  3456 ?        Ss   Sep12   0:00 /usr/sbin/atop -R -w /var/log/atop/atop_20260912 60

# Проверка логов на ошибки
sudo journalctl -u atop --since "1 hour ago" | grep -i "error\|fail\|warn"

# Проверка наличия логов за последние N дней
ls -lht /var/log/atop/atop_* | head -n 7

# Проверка места, занимаемого логами
du -sh /var/log/atop/

# Проверка устаревших логов (старше LOGGENERATIONS)
find /var/log/atop/ -name "atop_*" -mtime +30 -ls
```

## Рекомендации (Best Practices)

1. **Включайте atop на всех production-хостах с первого дня.** Ретроспективный анализ невозможен без исторических данных.
2. **Настраивайте LOGINTERVAL исходя из характерного времени инцидентов.** Для большинства production-систем 60 секунд — оптимальный баланс между детализацией и размером лога.
3. **Храните логи не менее 14 дней.** Для capacity planning и RCA требуется минимум две недели истории.
4. **Включайте сжатие логов (`LOGCOMPRESSION=gzip`).** Экономит до 70% дискового пространства. `atopsar` работает со сжатыми файлами без предварительной декомпрессии.
5. **Не используйте atop как основной инструмент real-time мониторинга на 1000+ хостах.** Для централизованного сбора используйте Prometheus + node_exporter. `atop` — инструмент для глубокой диагностики на одном хосте.
6. **Мониторьте сам сбор:** добавьте проверку, что файлы `atop_YYYYMMDD` создаются (например, через cron: `test -f /var/log/atop/atop$(date +%Y%m%d)`).
7. **Используйте atopsar для автоматизации.** `atop` интерактивен, `atopsar` — скриптуемый.
8. **Для хостов с виртуализацией отслеживайте `%steal`.** Это первый индикатор noisy neighbour.

## Ограничения и особенности (Edge Cases)

- **Бинарный формат:** лог-файлы `atop` не向后兼容. Файл, созданный atop 2.8, может не открываться в atop 2.6. Храните alongside atop бинарники или используйте `atopsar` для экспорта в текст/CSV.
- **Overhead:** при интервале <10 секунд на высоконагруженном хосте atop может добавлять 1–3% к CPU. Рекомендуемый минимум — 30 секунд.
- **Завершённые процессы:** atop сохраняет только агрегированную статистику по завершённым процессам, а не полный trace. Для детального анализа завершённых процессов используйте `auditd` или `execsnoop` (bpftrace).
- **Сеть без netatop:** без `netatop-bpf` atop показывает только общесистемный сетевой трафик по интерфейсам, но не per-process.
- **GPU:** мониторинг GPU работает только с NVIDIA и требует установленного `atopgpud`. AMD GPU не поддерживается.
- **cgroups v1 vs v2:** atop 2.8+ предпочитает cgroups v2. На системах с cgroups v1 некоторые метрики (особенно PSI) могут отсутствовать.

## Дополнительная информация

### Сетевой мониторинг (netatop-bpf)

В современных системах рекомендуется использовать **`netatop-bpf`**, который использует eBPF для сбора статистики без необходимости компиляции модуля ядра.

1. Установите пакет `netatop-bpf` (если доступен в дистрибутиве) или соберите из исходников.
2. Загрузите eBPF-программы и запустите сопутствующий демон.
3. `atop` автоматически обнаружит активный сборщик и наполнит колонки SNET/RNET.

### Мониторинг GPU (atopgpud)

Демон `atopgpud` взаимодействует с библиотекой NVML (NVIDIA) через UNIX-сокеты.

- Для активации мониторинга GPU запустите `atop` с флагом `-k`.
- В интерактивном режиме появится строка `GPU` с указанием процента использования памяти и ядер.

### Специфические метрики памяти

- **`RSIZE`**: реальный объём физической памяти (Resident set size).
- **`VGROW` / `RGROW`**: рост виртуальной/резидентной памяти за интервал. Ключевой индикатор утечек.
- **`MAJFLT`**: serious page faults. Если значение стабильно выше 0, система активно читает страницы с диска (Swap/Binary), что свидетельствует о нехватке RAM.
- **`MINFLT`**: minor page faults. Указывает на загрузку страниц из файлового кэша; обычно не критично.

### Генерация отчётов с помощью atopsar

Утилита `atopsar` позволяет получать агрегированную текстовую статистику.

```bash
# Сводный отчёт по CPU из лога
atopsar -c -r /var/log/atop/atop_20260801

# Просмотр нагрузки на диски
atopsar -d -f /var/log/atop/atop_20260801

# Статистика PSI (Memory Pressure)
atopsar -M -f /var/log/atop/atop_20260801

# Сводный отчёт по сети (требует netatop)
atopsar -n -r /var/log/atop/atop_20260801

# Экспорт в CSV для внешней обработки
atopsar -c -r /var/log/atop/atop_20260801 -h | gzip > cpu_report.csv.gz
```

### Сравнение с аналогичными инструментами

| Инструмент | Сильные стороны | Ограничения | Типичное применение |
| :--- | :--- | :--- | :--- |
| **`atop`** | Исторические логи, PSI, завершённые процессы, GPU | Бинарный формат, overhead демона | Post-mortem, nightly сборы, deep-dive |
| **`sar`** | Долгосрочная история, стандартный в большинстве distro | Дискретность 10 минут, нет PSI | Capacity planning, месячные тренды |
| **`dstat`** | Гибкий вывод, модули, цветной | Нет исторических логов | Ad-hoc диагностика,Real-time |
| **`pidstat`** | Per-process/thread, cron-дружественный | Только числа, нет PSI | Регулярный сбор по процессам |
