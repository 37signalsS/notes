# `perf`

## Определение

**`perf`** — официальный инструмент профилирования производительности в ОС Linux, поставляемый вместе с исходным кодом ядра. Он использует аппаратные счётчики производительности процессора (Performance Monitoring Units, PMU) и программные точки трассировки для глубокого анализа работы системы и приложений. `perf` позволяет выявлять «горячие» функции, промахи кэша, задержки планировщика и неэффективные участки кода на уровне инструкций.

## Основные концепции

### Типы событий (`perf list`)

`perf` может отслеживать тысячи различных событий, которые делятся на группы:
- **Hardware Events:** Аппаратные события PMU (циклы CPU, выполненные инструкции, промахи кэша L1/LLC, предсказания ветвлений).
- **Software Events:** Программные счетчики ядра (переключения контекста, ошибки страниц, миграции процессов).
- **Tracepoints:** Статические точки в коде ядра (система `ftrace`), например, `sched:sched_switch` или `syscalls:sys_enter_read`.
- **Dynamic Probes:** Динамические точки трассировки в ядре (`kprobes`) или пользовательском пространстве (`uprobes`).

### Механизмы сбора

- **Сэмплирование (Sampling):** Периодическое снятие «снимков» (например, 99 раз в секунду). Позволяет статистически определить нагрузку с минимальным оверхедом (обычно < 1%).
- **Счётчики (Counting):** Подсчёт общего количества событий за интервал времени. Даёт 100% точность количества, но не привязывает события к конкретному коду.

### Требования и доступ

Для полноценной работы необходимы установленные пакеты `linux-tools-$(uname -r)`.
Настройка доступа для не-root пользователей через `sysctl`:
- **`kernel.perf_event_paranoid`**:
    - `2` — запрещен доступ к CPU (только пользовательские события).
    - `1` — разрешен доступ к CPU (ядро и приложения).
    - `0` — разрешен доступ к данным `ftrace`.
    - `-1` — полный доступ (без ограничений).

## Практические сценарии

### Проверка доступных событий

```bash
# Список всех поддерживаемых событий на данном железе/ядре
perf list
```

### Анализ эффективности CPU (`perf stat`)

Позволяет оценить общую эффективность выполнения кода.

```bash
# Подсчёт IPC (Instructions Per Cycle) и промахов кэша
perf stat -e cycles,instructions,cache-misses,cache-references <команда>
```
> **Метрика IPC:** Если IPC < 1.0, процессор простаивает (Stalled) в ожидании памяти или I/O. Оптимальное значение — выше 1.5–2.0.

### Профилирование функций (`perf record` и `report`)

```bash
# Запись профиля с графом вызовов (-g) для всей системы (-a) на 10 секунд
sudo perf record -F 99 -g -a -- sleep 10

# Просмотр отчёта в интерактивном TUI
sudo perf report
```

### Анализ на уровне инструкций (`perf annotate`)

Позволяет увидеть, какие конкретно строки ассемблерного кода вызывают нагрузку внутри функции.

```bash
# Требуется предварительный perf record
# Внутри perf report выберите функцию и нажмите 'a' (annotate)
# Или запустите напрямую:
perf annotate --stdio
```

### Диагностика планировщика (`perf sched`)

Анализ времени ожидания процессов в очереди (Run Queue).

```bash
# Сбор событий
sudo perf sched record -a sleep 5

# Статистика задержек
sudo perf sched latency
```
Ключевая метрика: `avg delay` — среднее время «голодания» (Runnable, но не на CPU).

### Визуализация через Flame Graphs

Flame Graphs превращают тысячи строк `perf script` в наглядную карту «горячих путей».

```bash
# 1. Сбор данных
sudo perf record -F 99 -ag -- sleep 30

# 2. Обработка скриптами (требуется репозиторий FlameGraph)
perf script | ./stackcollapse-perf.pl | ./flamegraph.pl > profile.svg
```

## Дополнительная информация

### Разрешение символов (Symbols)

Если в отчёте вместо имен функций отображается `[unknown]` или шестнадцатеричные адреса:
1. **Ядро:** Установите `debuginfo` пакеты или проверьте наличие `/proc/kallsyms`.
2. **Приложения:** Убедитесь, что бинарные файлы не «очищены» (stripped) и имеют таблицы символов.
3. **JIT (Java/Node.js):** Используйте вспомогательные агенты (например, `perf-map-agent` для Java) для генерации карт символов в `/tmp/perf-<PID>.map`.

### Влияние на систему (Overhead)

`perf` работает значительно быстрее и безопаснее, чем `strace` или `gdb`, так как большая часть обработки происходит в контексте ядра. Однако высокая частота сэмплирования (`-F 9999`) на многоядерных системах может вызвать кратковременное замедление.
