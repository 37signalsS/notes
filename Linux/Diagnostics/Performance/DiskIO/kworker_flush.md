# Роль kworker/u*:flush-* в дисковом вводе-выводе (I/O)

## Определение

- **Грязные страницы (Dirty Pages)**: Страницы в системном кэше (Page Cache), содержимое которых было изменено приложением, но ещё не синхронизировано с постоянным хранилищем.
- **Обратная запись (Writeback)**: Фоновый процесс ядра Linux по переносу «грязных» страниц из оперативной памяти на диск.
- **`kworker/u*:flush-*`**: Специализированные рабочие потоки ядра (kernel worker threads), ответственные за сброс данных на конкретные блочные устройства. Например, `flush-8:0` обслуживает устройство с мажорным номером 8 и минорным 0 (обычно `/dev/sda`).

## Основные концепции

### Механизм работы

1. **Асинхронная запись**: Приложение выполняет системный вызов `write()`, данные копируются в Page Cache, и вызов немедленно завершается.
2. **Накопление**: Ядро помечает страницы как `Dirty` и продолжает накапливать их в памяти.
3. **Триггер сброса**: При достижении порога `vm.dirty_background_ratio` или истечении времени `vm.dirty_expire_centisecs` ядро инициирует фоновый сброс.
4. **Работа flush-потоков**: Потоки `kworker/u*:flush-*` считывают данные из RAM и отправляют их в очередь блочного устройства.

### Причины аномальной нагрузки (100% I/O)

- **Медленное хранилище**: Скорость записи данных в RAM значительно превышает пропускную способность диска.
- **Массивные залпы записи**: Накопление слишком большого объёма данных перед сбросом (высокий `dirty_ratio`).
- **Множество мелких файлов**: Каждая операция сброса требует обновления метаданных файловой системы, что создаёт накладные расходы.
- **Блокировка процессов**: Если объём грязных страниц достигает `vm.dirty_ratio`, ядро блокирует новые операции записи от приложений до тех пор, пока flush-потоки не освободят место.

## Практические сценарии

### Диагностика активности kworker

Если система «зависает» на операциях ввода-вывода, а `top` показывает активность ядерных потоков, выполните следующие шаги:

```bash
# 1. Проверка текущего объёма данных, ожидающих записи
cat /proc/meminfo | grep -E "Dirty|Writeback"

# 2. Идентификация конкретных kworker потоков
ps aux | grep kworker | grep flush

# 3. Трассировка запросов ввода-вывода в реальном времени (требует bcc-tools)
sudo biosnoop | grep kworker

# 4. Поиск приложений, которые "грязнят" память
sudo fatrace | grep -E "WRITE|OPEN"
```

### Устранение проблем с производительностью

Основным методом борьбы с задержками, вызванными `writeback`, является тюнинг параметров ядра `vm.dirty_*`. Это позволяет сделать сброс данных более частым и менее интенсивным («размазанным» во времени).

**Инструкции по настройке см. в разделе: [Настройка writeback: параметры ядра](./writeback_tuning.md).**
