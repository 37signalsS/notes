# Роль kworker и процессов writeback в дисковом вводе-выводе (I/O)

## Определение

- **Грязные страницы (Dirty Pages)**: Страницы оперативной памяти в системном кэше (Page Cache), содержимое которых было изменено приложением, но ещё не синхронизировано с постоянным хранилищем.
- **Обратная запись (Writeback)**: Фоновый механизм ядра Linux по переносу «грязных» страниц из оперативной памяти на диск.
- **`kworker` (Kernel Worker)**: Универсальные рабочие потоки ядра, выполняющие задачи из системных очередей (`workqueues`). Задачи по сбросу данных (flush) делегируются именно этим потокам.
- **`writeback` (подсистема)**: Компонент ядра, управляющий очередностью и интенсивностью сброса данных. В списке процессов может отображаться как поток `[writeback]`.

## Основные концепции

### Механизм работы

1. **Асинхронная запись**: Приложение выполняет системный вызов `write()`, данные копируются в Page Cache, и вызов немедленно завершается.
2. **Накопление**: Ядро помечает страницы как `Dirty` и продолжает накапливать их в RAM.
3. **Триггер сброса**: При достижении порога `vm.dirty_background_ratio` (асинхронно) или `vm.dirty_ratio` (синхронно/блокирующе) ядро инициирует сброс.
4. **Делегирование**: Подсистема `writeback` ставит задачу в очередь, которую подхватывает свободный поток `kworker`.

### Причины аномальной нагрузки (высокий %util при активности kworker)

- **Медленное хранилище**: Скорость генерации «грязных» страниц в RAM значительно превышает пропускную способность диска (IOPS/Throughput).
- **Массивные залпы записи**: Накопление слишком большого объёма данных перед сбросом из-за высоких значений `dirty_ratio`.
- **Фрагментация и метаданные**: Множество мелких файлов заставляют ядро часто обновлять дерево inode и журнал файловой системы (Journaling), что замедляет flush.
- **I/O Stalls (Замирания)**: Если объём грязных страниц достигает `vm.dirty_ratio`, ядро блокирует (throttle) новые операции `write()` от приложений до тех пор, пока данные не будут сброшены.

## Практические сценарии

### Диагностика активности механизмов сброса

Если система демонстрирует высокую задержку (latency), а `top` показывает активность ядерных потоков, выполните следующие шаги:

```bash
# 1. Проверка текущего объёма данных, ожидающих записи
cat /proc/meminfo | grep -E "Dirty|Writeback"
# → result: Dirty: 1048576 kB (1 ГБ данных ожидает сброса)

# 2. Определение функции ядра, на которой заблокирован kworker или приложение
# (Ожидание на 'balance_dirty_pages' подтверждает проблему Writeback)
cat /proc/<PID>/wchan
# → result: balance_dirty_pages_ratelimited

# 3. Трассировка запросов ввода-вывода в реальном времени (eBPF)
sudo biolatency-bpfcc 1 10
# → result: гистограмма задержек, позволяющая увидеть "хвосты" медленных операций

# 4. Поиск приложений, которые наиболее активно "грязнят" память (требует fatrace)
sudo fatrace | grep -E "WRITE" | head -n 20
# → result: python3(1234): W /var/lib/data.db
```

### Устранение проблем с производительностью

Основным методом борьбы с задержками является тюнинг параметров ядра `vm.dirty_*`. Это позволяет сделать сброс данных более частым и менее интенсивным («размазанным» во времени), предотвращая резкое заполнение очередей диска.

**Подробные инструкции по тюнингу: [Настройка writeback: параметры ядра](./writeback_tuning.md).**
