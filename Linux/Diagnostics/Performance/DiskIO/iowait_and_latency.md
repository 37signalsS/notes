# Низкий iowait при высокой задержке диска

## Определение

- **Ожидание ввода-вывода (I/O Wait, `%wa`)**: Процент времени, в течение которого процессор (CPU) простаивал, не выполняя вычислений, так как в системе был хотя бы один поток, ожидающий завершения операций ввода-вывода.
- **Задержка (Latency/Await)**: Фактическое время выполнения запроса блочным устройством. Включает время нахождения в очереди планировщика (queue latency) и время обслуживания самим устройством (service time).
- **Pressure Stall Information (PSI)**: Механизм ядра Linux для измерения реального «голодания» системы по ресурсам (I/O, CPU, RAM). Показывает время, потерянное процессами в ожидании, независимо от загрузки CPU.
- **Uninterruptible Sleep (D-state)**: Состояние процесса, заблокированного в системном вызове ожидания завершения операции ввода-вывода или другого ресурса на уровне ядра. Процесс в этом состоянии не может быть прерван сигналами, включая `SIGKILL`, и напрямую увеличивает показатель `Load Average`.
- **Троттлинг хранилища (Storage Throttling)**: Принудительное замедление операций ввода-вывода контроллером, гипервизором или программным уровнем при достижении лимитов IOPS, пропускной способности или очереди запросов. Может возникать как в облачных объемах, так и в on-premises СХД (SAN/NAS) при насыщении портов или бэкэнда.

## Основные концепции

### Почему iowait вводит в заблуждение

В современных многоядерных и многопоточных системах показатель `iowait` перестал быть надёжным индикатором проблем с диском. Это связано с алгоритмом его расчета в ядре:

1.  **Тиковая модель**: Ядро инкрементирует счетчик `iowait` только если CPU простаивает (`idle`) **и** в очереди этого CPU есть хотя бы одна задача в состоянии `D-state` (uninterruptible sleep). Если на ядре есть хотя бы одна runnable-задача, планировщик не считает CPU простаивающим, и время ожидания I/O не попадает в `iowait`.
2.  **Эффект многоядерности**: Если на одном ядре процесс ждет диск (`D-state`), а на другом ядре выполняется полезная работа, общесистемный `iowait` будет размыт. На 32-ядерном сервере один полностью заблокированный диск вызовет рост `iowait` всего на ~3.1%, что легко пропустить.
3.  **Маскировка полезной нагрузкой**: Если в системе всегда есть задачи, готовые к выполнению (Runnable), планировщик просто переключает CPU на них. В этом случае время ожидания ввода-вывода для заблокированного процесса «маскируется» полезной работой других потоков, и `iowait` может быть равен нулю при катастрофических задержках диска.
4.  **Учет `%steal` на виртуализации**: В гостевой ВМ `iowait` может быть близок к нулю, тогда как гипервизор считывает время, «украденное» у гостя (`%steal` в `iostat`), и задерживает завершение запросов. В этом случае PSI внутри гостя показывает давление, а `iowait` — нет.

### Механизм деградации без роста iowait

1.  **Блокировка процесса**: Приложение отправляет запрос на чтение/запись и переходит в `D-state`.
2.  **Переключение контекста**: Планировщик передаёт освободившийся CPU другому процессу (например, вычислительной задаче).
3.  **Рост очереди (Queueing)**: Запросы к диску накапливаются в очереди (параметр `avgqu-sz` в `iostat`), увеличивая фактическое время ожидания (`await`).
4.  **Результат**: Приложение «тормозит», задержка (`await`) растет до сотен мс, но `iowait` остается низким, так как CPU занят другой работой.

### Демонстрация эффекта маскировки iowait (sysbench)

Ниже приведены практические примеры из блога Percona ([Understanding Linux IOWait](https://www.percona.com/blog/understanding-linux-iowait/)), показывающие, как нагрузка на CPU маскирует `iowait` даже при полностью загруженной дисковой подсистеме.

#### Пример 1: Дисковая нагрузка + CPU-нагрузка = исчезновение iowait

**Шаг 1.** Создаём жёсткую нагрузку на дисковую подсистему (прямой I/O, случайное чтение, 8 потоков):
```bash
sysbench --threads=8 --time=0 --max-requests=0 fileio \
  --file-num=1 --file-total-size=10G --file-io-mode=sync \
  --file-extra-flags=direct --file-test-mode=rndrd run
```
Проверяем через `vmstat 1` — колонка `wa` (iowait) будет высокой.

**Шаг 2.** Не останавливая первый тест, добавляем нагрузку на CPU:
```bash
sysbench --threads=8 --time=0 cpu run
```
Снова смотрим `vmstat` — `wa` резко упадёт до нуля или низких значений, хотя первый тесс продолжает нагружать диски.

**Пояснение:** Когда процессор простаивает в ожидании I/O, это учитывается в `iowait`. Как только появляются готовые к выполнению задачи (runnable), планировщик переключает CPU на них — время ожидания I/O перестаёт засчитываться в `iowait`, хотя дисковая подсистема остаётся перегруженной.

#### Пример 2: Зависимость iowait от числа ядер

Запускаем тот же дисковый тест, но в 1 поток на ВМ с 4 ядрами:
```bash
sysbench --threads=1 --time=0 --max-requests=0 fileio \
  --file-num=1 --file-total-size=10G --file-io-mode=sync \
  --file-extra-flags=direct --file-test-mode=rndrd run
```
`iowait` будет в районе 20–25%. На ВМ с 32–64 ядрами значение станет незначительным (менее 1–3%), хотя дисковая подсистема полностью загружена.

**Вывод:** Высокий `iowait` указывает на ожидание CPU, но низкий `iowait` **не гарантирует** отсутствие проблем с дисками. Для диагностики используйте `vmstat 1` (столбец `b` — процессы в `D-state`) и PSI (`/proc/pressure/io`).

### Конкуренция за блокировки (Lock Contention)

Если потоки ждут освобождения inode или directory lock, они переходят в `D-state`, но диск при этом не совершает физических операций. Это «невидимая» задержка, маскирующаяся под I/O. На практике это проявляется при:
- Массовых операциях с одним файлом или каталогом (логи, БД с высокой конкуренцией).
- Файловых системах с агрессивной журнализацией (`ext4` с `data=journal`, `xfs`).
- NFS-серверах, где конкуренция за `inode` на стороне сервера приводит к задержкам на стороне клиента.

### Троттлинг хранилища

Принудительное замедление I/O может происходить на нескольких уровнях:
- **Контроллер/СХД**: Ограничение IOPS или throughput на уровне массива (SAN) или NAS-шлюза.
- **Hypervisor**: Дросселирование IOPS виртуального диска при превышении лимита пула.
- **cgroups**: Ограничение `io.max` или `io.weight` в cgroups v2 приводит к принудительному замедлению процессов внутри контрольной группы.
- **Файловая система**: `jbd2` может приостанавливать потоки при переполнении журнала.

## Предварительные требования

### Аппаратные требования
- Доступ к целевому блочному устройству (`/dev/sdX`, `/dev/nvmeXnY`) для диагностики.
- Для eBPF-инструментов (`bpftrace`, `bcc-tools`) требуется ядро 4.9+ с включенным `CONFIG_BPF` и `CONFIG_BPF_SYSCALL`.
- Для PSI требуется ядро 4.20+ с включенным `CONFIG_PSI`. Проверка: `grep CONFIG_PSI /boot/config-$(uname -r)`.

### Программные требования

```bash
# Debian/Ubuntu
sudo apt install sysstat iotop bpfcc-tools bpftrace perf-tools-unstable smartmontools nvme-cli fatrace pidstat

# RHEL/CentOS/Fedora
sudo dnf install sysstat iotop bcc-tools bpftrace perf smartmontools nvme-cli fatrace pidstat

# Arch Linux
sudo pacman -S sysstat iotop bpftrace perf smartmontools nvme-cli fatrace procps-ng

# openSUSE/SLES
sudo zypper install sysstat iotop bpftrace perf smartmontools nvme-cli fatrace procps
```

### Настройка окружения

```bash
# Включение сбора статистики задержек задач (если отключено)
echo 1 > /proc/sys/kernel/task_delayacct

# Проверка PSI
[ -e /proc/pressure/io ] && echo "PSI Enabled" || echo "PSI Disabled — добавьте psi=1 в GRUB"
```

## Практические сценарии

### Диагностический поток

Следуйте иерархии от общего давления к конкретному процессу:

1.  **Общее давление (PSI)**: Подтвердите, что проблема в I/O.
    ```bash
    cat /proc/pressure/io
    # some avg10 > 10% — приложения уже испытывают задержки из-за диска.
    ```

2.  **Устройство (iostat)**: Найдите проблемный диск.
    ```bash
    iostat -xz 1
    # await > 20 мс (HDD) или > 1 мс (SSD) — диск перегружен.
    # avgqu-sz > 2 — очередь растет быстрее, чем диск обрабатывает запросы.
    ```

3.  **Процесс (iotop / pidstat)**: Найдите виновника.
    ```bash
    sudo iotop -Pa -o
    pidstat -d 1
    ```

4.  **Точка блокировки (wchan)**: Уточните, где именно в ядре заблокирован процесс.
    ```bash
    ps -eo pid,state,wchan:30,comm | grep " D "
    ```

5.  **Глубокая трассировка (eBPF / blktrace)**: Если стандартные утилиты молчат.
    ```bash
    sudo biolatency-bpfcc -D 1 10
    sudo biosnoop-bpfcc | awk '$NF > 100'
    ```

### Глубокая диагностика скрытых задержек

#### 1. Анализ PSI (Pressure Stall Information)

Это самый надежный метод в ядрах 4.20+. PSI показывает реальное влияние нехватки I/O на производительность.

```bash
cat /proc/pressure/io
# → result: some avg10=15.20 avg60=10.05 avg300=5.00 total=1234567
# some: Время, в течение которого ХОТЯ БЫ ОДИН процесс ждал I/O. Индикатор деградации latency.
# full: Время, в течение которого ВСЕ активные процессы ждали I/O. Индикатор критического насыщения (saturation).
```
**Интерпретация:** Если `some avg10 > 10`, приложения уже испытывают заметные задержки из-за диска.

#### 2. Расширенная статистика iostat

Используйте `iostat -xz 1`, чтобы увидеть состояние очередей и задержек на уровне устройства.

```bash
# Ищем несоответствие между %util и await
iostat -xz 1
# → Device:  r/s    w/s   await  avgqu-sz  %util
#   sda      10.0   50.0  75.00  4.50      98.00
```
- **`await`**: Если > 20 мс для HDD или > 1 мс для SSD — диск является узким местом.
- **`avgqu-sz`**: Постоянные значения > 1 указывают на то, что запросы скапливаются в очереди быстрее, чем диск их обрабатывает.

#### 3. Использование eBPF (offcputime)

Инструмент `offcputime-bpfcc` позволяет увидеть, на каких функциях и как долго процессы находятся вне CPU. Это помогает подтвердить блокировку на I/O.

```bash
# Трассировка процессов, находящихся вне CPU более 5 мс
sudo offcputime-bpfcc -K -m 5
```

#### 4. Анализ каналов ожидания (wchan)

Если процесс «завис», проверьте, на чем именно:
```bash
cat /proc/<PID>/wchan
# → result: io_schedule, get_request, wait_on_page_bit или jbd2_log_wait_commit
```
Эти значения подтверждают, что процесс заблокирован именно на уровне дисковой подсистемы.

### Валидация диагноза

После определения причины задержки подтвердите её remediability:

1.  **Корреляция PSI и iostat**: Если `await` растет, а `some avg10` в `/proc/pressure/io` остается низким — проблема может быть в планировщике или в самой утилите `iostat` (старая версия `sysstat`). Обновите `sysstat` до версии 12+.
2.  **Сравнение `await` и `svctm`**: Если `await` значительно превышает время обслуживания устройства (узнайте через `smartctl` или `fio`), проблема в очереди планировщика, а не в самом диске.
3.  **Изоляция контейнера**: Запустите стресс-тест внутри контейнера и сравните PSI хоста с PSI контейнера (cgroups v2: `/sys/fs/cgroup/.../io.pressure`). Если давление на хосте выше — проблема в noisy neighbor.
4.  **Проверка оборудования**: Исключите аппаратные ошибки перед тюнингом ПО:
    ```bash
    sudo smartctl -a /dev/sda | grep -E 'Reallocated|Pending|Current_Pending_Sector'
    sudo dmesg | grep -iE 'error|timeout|reset|ata|nvme|scsi'
    ```

## Типичные ошибки и устранение неполадок

| Симптом | Возможная причина | Метод диагностики | Решение |
| :--- | :--- | :--- | :--- |
| `await` высокий, `iowait` низкий | Многоядерность, полезная нагрузка маскирует ожидание | `cat /proc/pressure/io` (some avg10) | Анализ через PSI, а не `top`/`htop` |
| `await` высокий, `%util` низкий | Внешний троттлинг (СХД, hypervisor) или проблема в очереди планировщика | `iostat -xz 1` (смотрим `avgqu-sz`, `r/s`, `w/s`) | Замена диска, изменение scheduler на `deadline`/`bfq`, увеличение stripe size (RAID) |
| Процессы в `D-state`, но диск простаивает | Lock Contention (VFS/inode) или зависший NFS | `ps -eo pid,state,wchan:30,comm \| grep " D "`, `nfsstat -m` | Перезапуск NFS-демона, пересборка ядра с увеличенным `NR_CPUS` для better scalability |
| `biolatency` показывает пики >100 мс | Аппаратная ошибка или throttling (в VM/СХД) | `dmesg`, `smartctl`, `cat /proc/pressure/io` | Замена диска, проверка контроллера или гипервизора (IOPS limit), сброс кэша контроллера |
| Высокий `iowait` при `await` < 5 мс | Устройство действительно быстрое, но CPU не успевает обрабатывать прерывания | `mpstat -P ALL 1`, `/proc/interrupts` | Настройка `irqbalance`, ручная привязка прерываний |
| `iotop` показывает только `kworker` | Фоновый writeback или журналирование | `biosnoop-bpfcc`, `cat /proc/meminfo \| grep Writeback` | Корректировка `vm.dirty_*` параметров. Подробнее: [Роль kworker и процессов writeback](./kworker_flush.md) |

## Ограничения и особые случаи

### Многоядерные системы
На серверах с >16 ядрами общесистемный `iowait` может быть <1% даже при полной деградации одного диска. Всегда используйте PSI (`some avg10`) или `vmstat 1` (столбец `b` — процессы в `D-state`) для первичной оценки.

### Виртуализация (KVM, VMware, Proxmox)
- **`%steal`**: В `iostat` столбец `%steal` показывает время, «украденное» у гостя гипервизором. Постоянный `%steal` > 5% — признак overselling CPU или noisy neighbor. В этом случае `iowait` внутри ВМ минимален, а приложения тормозят.
- **Виртуальные диски**: `await` в гостевой ОС включает сетевую задержку до гипервизора. Для оценки реального диска используйте `fio` внутри гостя и сравните с `fio` на хосте.

### Контейнеры (cgroups v1 vs v2)
- **cgroups v1**: `io.pressure` отсутствует. Используйте `cat /sys/fs/cgroup/blkio/docker/*/io.stat` для просмотра IOPS/байт.
- **cgroups v2**: `io.pressure` доступен, что позволяет измерять давление на I/O внутри контейнера. Путь: `/sys/fs/cgroup/<container-id>/io.pressure`.
- Внутри контейнера `iotop` видит только процессы этого контейнера, но не может отличить I/O контейнера от I/O хоста.

### NFS и сетевые ФС
- Сетевые файловые системы добавляют сетевую задержку, которая в `iotop` выглядит как обычный I/O wait.
- `nfsstat -c` и `nfsstat -m` помогают区分 сетевые проблемы от локальных.
- FUSE-файловые системы (например, `sshfs`) могут заблокировать процесс в пользовательском пространстве, что видно по `wchan` (`fuse_dev_read`).

### 32-битные системы
На архитектурах, отличных от x86_64, адресация `/proc/<pid>/io` может отличаться. Формат файла остаётся совместимым, но некоторые eBPF-утилиты могут требовать перекомпиляции.

### SSD write amplification
- Внутренний Garbage Collection SSD может вызывать кратковременные всплески задержки (up to 100+ мс) при фоновой перезаписи блоков. Это видно в `biolatency` как длинный «хвост» гистограммы.
- Накопители с DRAM-кэшем (Samsung, Intel) маскируют этот эффект лучше, чем бюджетные модели.

## Мониторинг и алертинг

### Prometheus (node_exporter)

Начиная с **node_exporter 1.8.0** поддерживается сбор PSI-метрик:

```yaml
groups:
  - name: io_pressure_alerts
    rules:
      - alert: HighIOPressureSome
        expr: |
          rate(node_pressure_io_waiting_seconds_total{state="some"}[5m]) > 0.1
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Высокое давление на I/O ({{ $labels.instance }})"
          description: "Процессы ждут I/O {{ $value | humanizePercentage }} времени за 5 минут. Проверьте await и avgqu-sz в iostat."

      - alert: CriticalIOPressureFull
        expr: |
          rate(node_pressure_io_waiting_seconds_total{state="full"}[5m]) > 0.05
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Критическое насыщение I/O ({{ $labels.instance }})"
          description: "Все активные процессы заблокированы на I/O {{ $value | humanizePercentage }} времени. Требуется немедленная реакция."
```

### Grafana

Рекомендуемые панели:
- **Time series** для `node_pressure_io_waiting_seconds_total` с зонами Warning/Critical.
- **Heatmap** распределения времени простоя по часам суток (выявление циклов batch-задач).
- **Correlation panel** — совместный график PSI I/O + `await` + `avgqu-sz` из `node_exporter`.
