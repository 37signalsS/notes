# Низкий iowait при высокой задержке диска

## Определение

- **Ожидание ввода-вывода (I/O Wait, `%wa`)**: Процент времени, в течение которого процессор (CPU) простаивал, не выполняя вычислений, так как все активные потоки ожидали завершения операций ввода-вывода.
- **Задержка (Latency/Await)**: Фактическое время выполнения запроса блочным устройством, включая время нахождения в очереди планировщика.
- **Pressure Stall Information (PSI)**: Механизм ядра Linux, позволяющий увидеть реальное «голодание» системы по I/O, даже если CPU занят другой работой.

## Основные концепции

### Проблема несоответствия метрик

В современных многоядерных системах показатель `iowait` часто перестаёт быть надёжным индикатором проблем с диском. Ситуация, когда `iowait` близок к нулю, но дисковые операции выполняются крайне медленно, может привести к ошибочному выводу о том, что дисковая подсистема исправна.

### Причины занижения iowait

Метрика `iowait` фиксирует только те периоды, когда ядро не может переключить CPU на другие задачи. Если в системе есть процессы, готовые к выполнению (Runnable), планировщик переключает CPU на них. В этом случае время ожидания ввода-вывода для заблокированного процесса «маскируется» полезной работой других потоков.

**Механизм возникновения:**
1. **Блокировка процесса**: Процесс отправляет запрос на ввод-вывод и переходит в состояние `D-state` (uninterruptible sleep).
2. **Переключение контекста**: Планировщик передаёт CPU другому процессу, которому не нужен ввод-вывод.
3. **Рост очереди**: Запросы на диске накапливаются в очереди устройства (параметр `avgqu-sz`), увеличивая фактическую задержку (`await`).
4. **Результат**: `iowait` остаётся низким, так как CPU занят, но производительность приложений в `D-state` деградирует.

## Практические сценарии

### Глубокая диагностика через iostat и PSI

Для выявления скрытых проблем с диском следует использовать расширенную статистику и индикаторы давления (Pressure).

```bash
# 1. Проверка системного давления по I/O (самый надежный современный метод)
cat /proc/pressure/io
# → result: some avg10=15.20 avg60=10.05 avg300=5.00 total=1234567
# Значение avg10 > 10 указывает на серьезное влияние задержек I/O на производительность.

# 2. Просмотр расширенной статистики дисков
iostat -xz 1
# → result:
# Device:  rrqm/s  wrqm/s    r/s    w/s   rMB/s   wMB/s  avgrq-sz  avgqu-sz  await  %util
# sda        0.00    5.00  10.00  50.00    0.40    2.50     96.00      4.50  75.00  98.00
```

**Ключевые показатели для анализа:**
- **`await`**: Среднее время обработки запроса (включая очередь). Порог для HDD: > 20 мс, для SSD: > 1 мс.
- **`avgqu-sz`**: Средняя длина очереди. Постоянные значения > 1–2 указывают на перегрузку.
- **`%util`**: Процент времени, в течение которого устройство было занято. Постоянные 100% — явный признак лимита пропускной способности.

### Использование eBPF для анализа задержек

Если `iowait` низок, но `await` высок, eBPF-инструменты помогут увидеть распределение (гистограмму) задержек, что позволяет отличить редкие выбросы от системной деградации.

```bash
# Распределение задержек ввода-вывода
sudo biolatency-bpfcc 1 10
# → result: гистограмма, где значения в колонке usecs/msecs показывают время выполнения.
```

### Контекст облачных сред и виртуализации

В виртуализированных средах (AWS, GCP, Azure) задержка может быть вызвана **Throttling** (ограничением IOPS/Throughput со стороны гипервизора).
- Процесс может зависнуть в `D-state`, ожидая «разрешения» на запись от облачного хранилища.
- При этом `iowait` внутри ВМ будет минимальным, так как гипервизор просто не отдаёт управление процессору, пока запрос I/O не «пройдёт» квоту.
