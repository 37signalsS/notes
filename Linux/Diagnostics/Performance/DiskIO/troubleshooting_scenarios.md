# Практические сценарии диагностики дискового ввода-вывода (I/O)

В данном разделе собраны прикладные кейсы по выявлению и устранению проблем производительности дисковой подсистемы в Linux — от аномалий кэширования до специфики облачных инфраструктур.

## Определения

- **I/O Wait (`%wa`)**: Метрика CPU, указывающая на простой процессора в ожидании завершения дисковых операций.
- **Pressure Stall Information (PSI)**: Механизм ядра для количественной оценки влияния нехватки ресурсов (I/O, CPU, RAM) на реальные задержки приложений.
- **Uninterruptible Sleep (D-state)**: Состояние процесса, заблокированного в системном вызове (обычно I/O). Увеличивает `Load Average`.
- **Writeback**: Процесс фонового сброса измененных данных (грязных страниц) из Page Cache на физический носитель.

## Основные концепции

Диагностика I/O часто осложняется уровнями абстракции (RAID, LVM, файловые системы) и асинхронностью операций. Сценарии ниже демонстрируют методику локализации "виновника" в условиях, когда стандартные инструменты мониторинга дают неполную картину.

## Практические сценарии

### Сценарий 1: Высокий I/O wait при "пустом" iotop

**Симптомы:** Утилита `top` показывает `%wa > 30%`, но `iotop -o` не выявляет процессов с активной записью или чтением.

**Причина:** Интенсивный **Writeback** или нагрузка на метаданные (журналирование). `iotop` часто не может сопоставить фоновый сброс данных потоками `kworker` с исходным процессом-писателем.

**Диагностика:**
```bash
# 1. Проверка объема грязных страниц (Dirty Pages)
cat /proc/meminfo | grep -E "Dirty|Writeback"
# → Dirty: 800 MB (высокое значение провоцирует агрессивный сброс)

# 2. Идентификация реального давления через PSI
cat /proc/pressure/io
# → some avg10=25.00 (подтверждает, что процессы теряют время на I/O)

# 3. Поиск "виновников" через bpftrace (трассировка dirtying страниц)
sudo bpftrace -e 'tracepoint:writeback:writeback_dirty_page { @[comm] = count(); }'
# → result: [python3] 4500 (показывает, кто "грязнит" память быстрее всех)
```
**Решение:** Оптимизация параметров `vm.dirty_*`. Подробнее: [Тюнинг writeback](./writeback_tuning.md).

### Сценарий 2: Микро-задержки и "длинный хвост" (Tail Latency)

**Симптомы:** Средняя задержка (`await`) в норме (1-2 мс), но приложение периодически "замирает" на 500+ мс.

**Причина:** Конкуренция за блокировки на уровне ФС, очереди планировщика или "сборка мусора" (GC) внутри SSD.

**Диагностика:**
```bash
# 1. Анализ распределения задержек (гистограмма)
sudo biolatency-bpfcc -D 1 10
# → Ищите значения в корзинах > 128ms. Флаг -D покажет разбивку по дискам.

# 2. Трассировка конкретных долгих запросов
sudo biosnoop-bpfcc | awk '$NF > 100'
# → Показывает запросы, выполнявшиеся более 100 мс (PID, Диск, Latency).
```

### Сценарий 3: Задержки в облаке (AWS EBS / GCP PD Throttling)

**Симптомы:** Приложение работает медленно, `iowait` внутри ВМ близок к нулю, но `await` в `iostat` достигает 200-500 мс.

**Причина:** Исчерпание лимитов IOPS или Throughput (Burst Credits). Гипервизор принудительно задерживает запросы, при этом CPU ВМ просто простаивает ("кража времени" на уровне I/O).

**Диагностика:**
```bash
# 1. Сверка await и %util
iostat -xz 1
# → await: 150.0, %util: 20.0 (классический признак внешнего троттлинга)

# 2. Проверка аппаратных таймаутов в dmesg
dmesg | grep -iE "timeout|blocked|reset"
# → nvme nvme0: I/O 123 QID 4 timeout, completion polled
```
**Решение:** Увеличить размер тома или сменить тип диска (например, с `gp2` на `gp3` в AWS) для повышения базовых лимитов.

### Сценарий 4: Маскировка нагрузки через io_uring

**Симптомы:** База данных (например, ScyllaDB или современный Postgres) создает высокую нагрузку, но `iotop` и `pidstat` показывают нулевой I/O.

**Причина:** Использование интерфейса `io_uring`, который работает в обход классических системных вызовов, на которых базируется большинство утилит `procps`.

**Диагностика:**
```bash
# Трассировка активности io_uring через perf
sudo perf record -e 'io_uring:*' -a sleep 5
sudo perf report
```
**Решение:** Использовать современные eBPF-инструменты (например, `biotop`), которые работают на уровне блочных устройств, а не системных вызовов.

### Сценарий 5: Деградация RAID-массива

**Симптомы:** Резкое падение производительности чтения/записи, рост Load Average.

**Диагностика:**
```bash
# 1. Проверка статуса программного RAID
cat /proc/mdstat
# → [UUU_U] (символ "_" указывает на выпавший диск)

# 2. Анализ скорости ребилда (если он идет)
cat /proc/sys/dev/raid/speed_limit_max
```
**Решение:** Замена неисправного диска. Для минимизации влияния ребилда на приложения можно временно снизить `speed_limit_max`.

### Сценарий 6: Проблемы выравнивания разделов (Misalignment)

**Симптомы:** Низкая производительность записи на SSD/NVMe или аппаратных RAID, особенно при мелких блоках.

**Диагностика:**
```bash
# Проверка выравнивания разделов
sudo parted /dev/sda align-check opt 1
# → 1 aligned (если "not aligned" — каждая запись требует Read-Modify-Write цикла)
```
