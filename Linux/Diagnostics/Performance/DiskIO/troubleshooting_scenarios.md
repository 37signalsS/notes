# Практические сценарии диагностики дискового ввода-вывода (I/O)

В данном разделе собраны прикладные кейсы по выявлению и устранению проблем производительности дисковой подсистемы в Linux.

## Определение

- **I/O Wait (`wa`)**: Показатель процессорного времени, затраченного на ожидание завершения операций ввода-вывода.
- **Uninterruptible Sleep (D-state)**: Состояние процесса, ожидающего завершения I/O. Процесс в этом статусе увеличивает `Load Average`.
- **Грязные страницы (Dirty Pages)**: Страницы в оперативной памяти (Page Cache), содержимое которых было изменено, но ещё не синхронизировано с диском.
- **Direct I/O**: Режим записи или чтения данных напрямую на диск, минуя системный кэш страниц.

## Основные концепции

Диагностика I/O часто требует выхода за рамки стандартных инструментов типа `top` или `iotop`. В сценариях ниже рассматриваются случаи «скрытой» нагрузки, аномального поведения планировщиков и аппаратных сбоев. Каждый сценарий включает описание симптомов, шаги диагностики и возможные решения.

## Практические сценарии

### Сценарий 1: Высокий I/O wait при «пустом» iotop

**Симптомы:** Утилита `top` показывает `%wa` более 50%, однако `iotop -o` не выявляет активных процессов-«писателей».

**Диагностика:**
Скорее всего, нагрузка вызвана фоновым сбросом грязных страниц (Writeback) ядерными потоками.

```bash
# Проверка объёма грязных страниц
cat /proc/meminfo | grep -E "Dirty|Writeback"

# Поиск процессов, которые открывали файлы на запись за последнее время
sudo fatrace | grep -E "WRITE|OPEN"

# Проверка активности потоков kworker
ps aux | grep kworker | grep flush
```

**Решение:** Отрегулировать параметры сброса кэша, чтобы сделать запись более плавной.

```bash
# Временное уменьшение порогов для более частого сброса
sudo sysctl -w vm.dirty_ratio=10
sudo sysctl -w vm.dirty_background_ratio=5
```

*Подробнее: [Настройка writeback](./writeback_tuning.md)*.

### Сценарий 2: Поиск процесса по кумулятивной нагрузке

**Проблема:** Мгновенные снимки `iotop` не показывают виновника, так как процесс совершает короткие, но интенсивные всплески записи.

**Решение:** Изучение кумулятивной статистики в `/proc/<pid>/io`.

```bash
# Поиск топ-20 процессов по объёму записанных данных с момента старта
for pid in /proc/[0-9]*; do
    if [ -r "$pid/io" ]; then
        echo -n "$pid "
        grep "write_bytes" "$pid/io" | awk '{print $2}'
    fi
done 2>/dev/null | sort -k2 -rn | head -20
```

### Сценарий 3: Детальный анализ задержек через biosnoop

**Инструмент:** `biosnoop` (входит в пакет `bcc-tools` / `bpfcc-tools`). Позволяет видеть каждый конкретный запрос к блочному устройству.

```bash
# Запуск трассировки (требует прав root)
sudo biosnoop
```

**Интерпретация вывода:**

- Поле **LAT(ms)** показывает фактическую задержку выполнения операции диском.
- Если задержка высока только у `kworker`, проблема в интенсивности Writeback.
- Если задержка высока у пользовательского процесса (например, `postgres`), диск не справляется с синхронными запросами.

### Сценарий 4: Низкоуровневая трассировка через blktrace

**Когда использовать:** Если `biosnoop` недоступен или требуется анализ работы планировщика I/O.

```bash
# Запись трассировки устройства sda в реальном времени
sudo blktrace -d /dev/sda -o - | blkparse -i -
```

**Ключевые события:**

- `Q` (Queued): Запрос попал в очередь.
- `C` (Completed): Запрос выполнен устройством.
Большая разница во времени между `Q` и `C` подтверждает проблему на уровне оборудования или контроллера.

### Сценарий 5: Мониторинг обращений к файлам через fatrace

**Когда использовать:** Нужно быстро понять, к каким именно файлам на диске идут обращения.

```bash
# Мониторинг всех операций записи в реальном времени
sudo fatrace -f W

# Фильтрация по конкретной точке монтирования или директории
sudo fatrace | grep "/var/log"
```

### Сценарий 6: Выявление аппаратных проблем

**Алгоритм действий:**

1. Проверить системные логи ядра на наличие ошибок контроллера:

   ```bash
   dmesg | grep -iE "error|timeout|reset|blocked"
   ```

2. Изучить ошибки в журнале за последний час:

   ```bash
   journalctl -k --since "1 hour ago" | grep -iE "i/o|block"
   ```

3. Проверить состояние диска через SMART:

   ```bash
   sudo smartctl -H /dev/sda
   ```

*Подробнее: [Здоровье диска (SMART)](../Hardware/smartctl/disk_health_check.md)*.

### Сценарий 7: Диагностика лимитов cgroup (Docker/K8s)

**Проблема:** Процесс внутри контейнера работает медленно, хотя диск в системе свободен.

**Проверка:**

```bash
# Просмотр статистики I/O для конкретного юнита systemd или контейнера
cat /sys/fs/cgroup/system.slice/<unit_name>.service/io.stat

# Проверка установленных лимитов (bps/iops)
cat /sys/fs/cgroup/system.slice/<unit_name>.service/io.max
```
