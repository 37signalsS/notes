# Практические сценарии диагностики дискового ввода-вывода (I/O)

В данном разделе собраны прикладные кейсы по выявлению и устранению проблем производительности дисковой подсистемы в Linux.

## Определение

- **I/O Wait (`wa`)**: Процент времени CPU, затраченного на ожидание дисковых операций.
- **Pressure Stall Information (PSI)**: Механизм ядра для оценки реального влияния нехватки ресурсов (I/O, CPU, RAM) на задержки приложений.
- **Uninterruptible Sleep (D-state)**: Состояние процесса, ожидающего завершения ввода-вывода. Увеличивает `Load Average`.
- **Writeback**: Процесс сброса грязных страниц из Page Cache на диск потоками `kworker`.

## Основные концепции

Диагностика I/O часто требует выхода за рамки стандартных инструментов типа `top`. В сценариях ниже рассматриваются случаи «скрытой» нагрузки, задержек в облачных средах и аномального поведения кэша. Каждый сценарий включает симптомы, шаги диагностики и решения.

## Практические сценарии

### Сценарий 1: Высокий I/O wait при «пустом» iotop

**Симптомы:** Утилита `top` показывает `%wa > 50%`, но `iotop -o` не выявляет активных процессов.

**Диагностика:**
Скорее всего, нагрузка вызвана интенсивным **Writeback** (фоновым сбросом данных).

```bash
# 1. Проверка объёма грязных страниц
cat /proc/meminfo | grep -E "Dirty|Writeback"
# → result: Dirty: 524288 kB

# 2. Идентификация блокировок через PSI
cat /proc/pressure/io
# → result: some avg10=25.00 avg60=15.20 avg300=10.05

# 3. Поиск процессов, которые открывали файлы на запись (fatrace)
sudo fatrace | grep -E "WRITE" | head -n 10
# → result: python3(123): W /tmp/temp_data.log
```

**Решение:** Отрегулировать параметры тюнинга грязных страниц. Подробнее: [Тюнинг writeback](./writeback_tuning.md).

### Сценарий 2: Поиск процесса по кумулятивной нагрузке

**Проблема:** `iotop` не фиксирует виновника из-за кратковременных, но частых всплесков записи.

**Решение:** Использование кумулятивной статистики `/proc/<pid>/io`.

```bash
# Поиск топ-20 процессов по объёму записанных данных с момента старта
for pid in /proc/[0-9]*; do
    [ -r "$pid/io" ] && echo "$pid $(grep write_bytes $pid/io | awk '{print $2}')"
done | sort -k2 -rn | head -n 20
# → result: (список PID и байтов)
```

### Сценарий 3: Задержки в облачных средах (AWS EBS / GCP PD)

**Симптомы:** Приложение периодически «замирает», `iowait` внутри ВМ низок, но `await` в `iostat` зашкаливает.

**Диагностика:**
Причина — **Cloud Throttling** (исчерпание лимитов IOPS или Burst Credits).

```bash
# Проверка латентности на уровне блочного устройства
iostat -xz 1
# → result: await > 100ms при %util < 30%

# Проверка гистограммы задержек (eBPF)
sudo biolatency-bpfcc 1 10
# → result: (гистограмма с "хвостами" > 100ms)
```

**Решение:** Увеличить тип диска или размер тома для получения большего лимита IOPS.

### Сценарий 4: Трассировка задержек конкретного приложения

**Инструмент:** `biosnoop-bpfcc`. Позволяет увидеть латентность каждого запроса в реальном времени.

```bash
# Трассировка запросов (требует bcc-tools)
sudo biosnoop-bpfcc | head -n 10
# → result: TIME(s) COMM PID DISK T SECTOR BYTES LAT(ms)
# → result: 0.0001 mysqld 1234 sda W 123456 4096 45.20
```

### Сценарий 5: Диагностика лимитов cgroup v2 (Docker/K8s)

**Проблема:** Контейнер работает медленно при свободном диске на хосте.

```bash
# Просмотр статистики троттлинга для контейнера
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/io.stat
# → result: 8:0 riops=123 wiops=45

# Проверка установленных жестких лимитов
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/io.max
# → result: 8:0 rbps=1048576 wbps=1048576
```

### Сценарий 6: Выявление аппаратных проблем

```bash
# Поиск сообщений о блокировках и ошибках в логах ядра
dmesg | grep -iE "i/o|error|blocked|timeout"
# → result: blk_update_request: I/O error, dev sda...

# Проверка здоровья через SMART
sudo smartctl -H /dev/sda
# → result: PASSED или FAILED
```
