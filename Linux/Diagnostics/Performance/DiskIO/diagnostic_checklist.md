# Чек-лист диагностики дискового ввода-вывода (I/O)

Данный документ представляет собой пошаговый алгоритм выявления причин деградации производительности дисковой подсистемы.

## Определение

- **I/O Wait (`wa`)**: Показатель процессорного времени, затраченного на ожидание завершения операций ввода-вывода. Высокие значения (обычно >15–20%) указывают на наличие узкого места в дисковой или сетевой подсистеме.
- **Uninterruptible Sleep (D-state)**: Состояние процесса, ожидающего завершения ввода-вывода. Процессы в этом статусе увеличивают `Load Average` и не могут быть завершены сигналом `SIGKILL`.
- **Грязные страницы (Dirty Pages)**: Данные в системном кэше (Page Cache), которые были изменены приложениями, но ещё не записаны на физический диск.
- **Блочный ввод-вывод (Block I/O)**: Операции чтения и записи на уровне блочных устройств (дисков, разделов).

## Основные концепции

### Иерархия диагностики

Эффективный поиск проблем I/O строится по принципу «от общего к частному»:

1. **Обзор системы**: Определение наличия проблемы (iowait, Load Average).
2. **Анализ устройств**: Идентификация конкретного диска или раздела с задержками.
3. **Поиск процесса**: Определение приложения, генерирующего основную нагрузку.
4. **Детализация**: Анализ конкретных файловых операций и системных вызовов.
5. **Аппаратная проверка**: Поиск признаков физической деградации носителя.

## Практические сценарии

### Шаг 1: Общий обзор системы

Используйте `vmstat` для оценки общей картины без детализации по устройствам.

```bash
vmstat 1 5
```

**На что смотреть:**

- `wa`: Если стабильно выше 20% — диск является узким местом.
- `bi`/`bo`: Интенсивность чтения/записи в блоках.
- `si`/`so`: Если активен свопинг, это создаёт колоссальную нагрузку на I/O.

### Шаг 2: Статистика по блочным устройствам

Определите, какой именно диск перегружен, с помощью расширенной статистики `iostat`.

```bash
iostat -xz 1
```

**На что смотреть:**

- `%util`: Если близко к 100%, устройство работает на пределе возможностей.
- `await`: Средняя задержка (мс). Норма: < 20 мс (HDD), < 1 мс (SSD).
- `avgqu-sz`: Длина очереди. Постоянные значения > 1–2 — явный признак перегрузки.
- *Подробнее: [Статистика iostat](../../Filesystem/iostat.md)*.

### Шаг 3: Идентификация процессов-виновников

Найдите приложение, которое создает основную нагрузку, используя `pidstat` или `iotop`.

```bash
# Просмотр статистики по процессам (наиболее точный метод)
pidstat -d 1

# Интерактивный режим (только активные процессы)
sudo iotop -o
```

*Подробнее: [Использование pidstat](../../Processes/pidstat.md) и [Мониторинг iotop](../../Filesystem/iotop.md)*.

### Шаг 4: Анализ файловых операций

Если виновник не очевиден, используйте `fatrace` для отслеживания обращений к файлам в реальном времени.

```bash
sudo fatrace | head -50
```

Позволяет увидеть тип операции (WRITE, OPEN), PID процесса и полный путь к файлу. Полезно для поиска проблем в распределённых ФС.

### Шаг 5: Проверка скрытых факторов

- **Удалённые файлы**: Файлы, которые удалены, но удерживаются процессами, могут вызывать I/O нагрузку при записи в них.

  ```bash
  lsof +L1
  ```

- **Грязные страницы**: Проверьте объём данных, ожидающих записи.

  ```bash
  grep -E "Dirty|Writeback" /proc/meminfo
  ```

  *Подробнее: [Настройка writeback](./writeback_tuning.md)*.

### Шаг 6: Аппаратные ошибки и логи ядра

Проверьте системные логи на наличие сообщений об ошибках контроллера или диска.

```bash
dmesg | grep -iE "i/o|error|blocked"
journalctl -k --since "1 hour ago" | grep -iE "i/o|block"
```

Если найдены ошибки, проверьте состояние диска через [SMART](../Hardware/smartctl/disk_health_check.md).
