# Невидимый ввод-вывод: почему iotop может не показывать виновника нагрузки

## Определение

- **Uninterruptible Sleep (D-state)**: Состояние процесса, ожидающего завершения операции ввода-вывода (I/O). Процесс в этом состоянии не может быть прерван сигналами, включая `SIGKILL`, и напрямую влияет на показатель `Load Average`.
- **Pressure Stall Information (PSI)**: Механизм ядра Linux (начиная с v4.20), позволяющий количественно оценить время ожидания (stall) ресурсов CPU, памяти и I/O. Даёт объективную картину «давления» на систему, даже если `iowait` низок.
- **Direct I/O**: Режим выполнения операций чтения или записи, при котором данные передаются между приложением и устройством в обход системного кэша страниц (Page Cache).
- **Block I/O**: Операции ввода-вывода на уровне блочного устройства, которые обрабатываются планировщиком ввода-вывода ядра.

## Основные концепции

Утилита [`iotop`](../../Filesystem/iotop.md) работает по принципу сэмплирования, снимая моментальные снимки состояния процессов. Процесс попадает в отчёт только в том случае, если он находился в состоянии ожидания I/O именно в момент снятия сэмпла. Это делает его неэффективным против кратковременных, но частых всплесков.

### Причины «невидимого» ввода-вывода

| Причина | Механизм | Метод обнаружения |
| :--- | :--- | :--- |
| **Короткие всплески** | Процесс завершает операцию между сэмплами `iotop` | `pidstat -d 1`, `fatrace` |
| **Ядерные потоки (kworker)** | Сброс данных на диск фоновыми потоками ядра (Writeback) | `biosnoop`, `/proc/meminfo` |
| **Журналирование (jbd2)** | Файловая система (ext4/xfs) сбрасывает транзакции журнала на диск | `biolatency`, `dmesg` |
| **Синхронизация RAID** | Фоновая проверка или ребилд массива (`mdadm`, LVM RAID) | `cat /proc/mdstat` |
| **Direct I/O** | Данные минуют Page Cache, что может иначе отображаться в статистике | `/proc/<pid>/io` |
| **Удалённые, но открытые файлы** | Процесс пишет в файл, который уже удалён из файловой системы | `lsof +L1` |
| **Ограничения cgroup** | Ввод-вывод ограничивается на уровне контрольных групп (Throttling) | `/sys/fs/cgroup/*/io.stat` |
| **Сетевые ФС (NFS/CIFS)** | Задержки вызваны сетевым ожиданием, а не локальным диском | `nfsstat -m`, `mount` |
| **Swap I/O** | Активная выгрузка страниц памяти в раздел подкачки | `vmstat 1` (колонки si/so) |

## Практические сценарии

### Глубокая диагностика скрытой нагрузки

Если стандартный запуск `iotop -o` не выявляет источник нагрузки, используйте следующие инструменты:

```bash
# Проверка системного давления по I/O (PSI)
cat /proc/pressure/io
# → result: some avg10=15.20 avg60=10.05 avg300=5.00 total=1234567

# Анализ задержек на уровне устройства (проверка наличия очереди)
iostat -x 1
# → result: %util > 80%, await > 10ms, avgqu-sz > 1.0

# Поиск процессов с кратковременной активностью I/O (интервал 1с)
pidstat -d 1
# → result: PID, kB_rd/s, kB_wr/s, iodelay

# Мониторинг обращений к файлам в реальном времени
sudo fatrace | head -20
# → result: app(123): W /path/to/file

# Определение функции ядра, на которой заблокирован процесс в D-state
cat /proc/<PID>/wchan
# → result: call_rwsem_down_read_failed или wait_on_page_bit

# Проверка наличия открытых дескрипторов удалённых файлов
lsof +L1
# → result: (найти файлы с (deleted) в имени, но большим размером)

# Анализ интенсивности сброса данных из Page Cache
watch -n1 "cat /proc/meminfo | grep -E 'Dirty|Writeback'"
# → result: Dirty: 500 MB (высокое значение провоцирует фоновый сброс)
```

### Использование eBPF инструментов

Современные eBPF-скрипты позволяют видеть I/O там, где классические утилиты бессильны.

```bash
# Распределение задержек ввода-вывода (гистограмма)
sudo biolatency-bpfcc
# → result: показывает, есть ли "хвосты" задержек выше 100мс

# Трассировка каждого запроса I/O с указанием процесса и диска
sudo biosnoop-bpfcc | head -20
# → result: TIME(s), COMM, PID, DISK, T, SECTOR, BYTES, LAT(ms)
```
