# Невидимый ввод-вывод: почему iotop может не показывать виновника нагрузки

## Определение

- **Uninterruptible Sleep (D-state)**: Состояние процесса, ожидающего завершения операции ввода-вывода (I/O) или другого ресурса на уровне ядра. Процесс в этом состоянии не может быть прерван сигналами, включая `SIGKILL`, и напрямую увеличивает показатель `Load Average`.
- **Pressure Stall Information (PSI)**: Механизм ядра Linux (начиная с v4.20), позволяющий количественно оценить время ожидания (stall) ресурсов CPU, памяти и I/O. Даёт объективную картину «давления» на систему, даже если `iowait` низок.
- **Wait Channels (wchan)**: Функция ядра или точка в коде, на которой процесс заблокирован в ожидании события (например, завершения дисковой операции).
- **io_uring**: Современный интерфейс асинхронного ввода-вывода Linux, который может маскировать нагрузку для традиционных утилит мониторинга, использующих классические системные вызовы.
- **TASK_DELAY_ACCT**: Опция ядра (`CONFIG_TASK_DELAY_ACCT`), необходимая для сбора статистики задержек задач, на которую опирается `iotop`.

## Основные концепции

### Архитектура стека ввода-вывода

Для понимания «невидимого» I/O необходимо учитывать многоуровневую архитектуру подсистемы ввода-вывода Linux:

1.  **Приложение** вызывает `write()` или `read()`.
2.  **Page Cache** (страничный кэш ядра) принимает данные. При записи процесс немедленно получает подтверждение, а физический сброс откладывается.
3.  **Flusher threads** (`kworker`) асинхронно сбрасывают грязные страницы на диск.
4.  **Блочный слой** (block layer) формирует запросы и отправляет их драйверу устройства.
5.  **Драйвер** взаимодействует с контроллером (NVMe, SATA, SCSI).

На каждом уровне традиционные утилиты могут «потерять» связь между конечным устройством и исходным процессом.

### Почему iotop «пропускает» нагрузку

Утилита [`iotop`](../../Filesystem/iotop.md) и аналогичные ей инструменты полагаются на статистику задержек задач (`taskstats`), предоставляемую ядром. Существует несколько фундаментальных причин, по которым реальный виновник нагрузки может не отображаться:

1.  **Проблема сэмплирования**: `iotop` снимает моментальные снимки состояния. Если процесс выполняет I/O короткими всплесками (bursts) между сэмплами, он не попадёт в отчёт.
2.  **Атрибуция фоновым потокам**: В Linux запись часто происходит асинхронно через Page Cache. Процесс-«писатель» лишь помечает страницы как грязные (dirty), а физический сброс на диск выполняют ядерные потоки `kworker` или `jbd2` (для журналов ФС). `iotop` при этом покажет нагрузку на `kworker`, а не на исходное приложение.
3.  **Уровни абстракции**: Использование LVM, MD RAID или шифрования (`dm-crypt`) создаёт дополнительные слои. Нагрузка может быть видна на виртуальном устройстве, но при анализе процессов она «растворяется» в потоках обслуживания этих слоёв.
4.  **Отсутствие CONFIG_TASK_DELAY_ACCT**: Если ядро собрано без этой опции или она выключена (`nodelayacct` в параметрах загрузки), `iotop` не сможет получить данные о задержках и будет показывать нули.

### Причины «невидимого» ввода-вывода

| Причина | Механизм | Метод обнаружения |
| :--- | :--- | :--- |
| **Короткие всплески** | Высокая частота малых операций между сэмплами | `pidstat -d 1`, `fatrace`, `perf record -e block:block_rq_issue` |
| **Writeback (Dirty Pages)** | Фоновый сброс данных потоками `kworker` | `biosnoop`, `watch -n1 grep -E 'Dirty\|Writeback' /proc/meminfo` |
| **Журналирование (jbd2)** | Фиксация транзакций ext4/xfs на диске | `biolatency`, `dmesg`, `blktrace` |
| **Синхронизация RAID/LVM** | Ребилд или проверка целостности массива | `cat /proc/mdstat`, `lvs -a` |
| **Direct I/O и io_uring** | Обход стандартных механизмов учета Page Cache | `/proc/<pid>/io`, `bpftrace -e 'tracepoint:syscalls:sys_enter_io_uring_enter { ... }'` |
| **Lock Contention (VFS/Inode)** | Конкуренция за блокировки inode или директорий | `pidstat -w`, `perf lock`, `ps -eo wchan | grep lock` |
| **Удалённые открытые файлы** | Запись в дескриптор файла, удалённого через `rm` | `lsof +L1`, `find /proc/*/fd -ls | grep '(deleted)'` |
| **FUSE и сетевые ФС** | Задержки на уровне пользователя (FUSE) или сети (NFS) | `ps -eo state,wchan,comm | grep D`, `nfsstat -m` |
| **Память и Swap** | Сброс страниц в Swap или компакция (Transparent Huge Pages) | `vmstat 1` (si/so), `cat /proc/pressure/memory` |
| **Throttling (cgroups)** | Принудительное замедление I/O для лимитирования | `cat /sys/fs/cgroup/*/io.stat`, `cat /proc/<pid>/cgroup` |
| **Массовые openat()** | Тысячи проверок несуществующих файлов/конфигов, невидимых `iotop` | `opensnoop`, `bpftrace` на `tracepoint:syscalls:sys_enter_openat` |

- `CONFIG_BPF`: требуется для `bpftrace` и BCC-утилит (ядро 4.9+ с `CONFIG_BPF_SYSCALL`).

## Практические сценарии

### 1. Анализ PSI (Pressure Stall Information)

PSI — самый быстрый способ подтвердить, что «тормоза» вызваны именно вводом-выводом, даже если `iowait` мал.

```bash
cat /proc/pressure/io
# → result: some avg10=15.20 avg60=10.05 avg300=5.00 total=1234567
# some: процессы ждали I/O, но CPU был занят чем-то полезным.
# full: все процессы были заблокированы на I/O (критическая ситуация).
```

**Интерпретация:** Если `some avg10 > 10`, приложения уже испытывают заметные задержки. Значение `full` растёт только при полном насыщении.

### 2. Диагностика блокировок файловой системы (Lock Contention)

Иногда диск почти не загружен (`%util` низкий), но задержки операций растут из-за того, что десятки потоков конкурируют за одни и те же inode или directory lock.

**Признаки и диагностика:**

1.  **Переключение контекста:** Если количество добровольных (`cswch/s`) и недобровольных (`nvcswch/s`) переключений резко растёт, процесс может ждать освобождения блокировки.
    ```bash
    pidstat -w 1
    ```

2.  **Анализ блокировок через perf:** Позволяет увидеть, какие блокировки удерживаются дольше всего и какие функции ядра вызывают наибольшую конкуренцию.
    ```bash
    # Сбор данных (во время нагрузки)
    sudo perf lock record sleep 30
    # Генерация отчета
    sudo perf lock report
    ```

3.  **Анализ функций ожидания (VFS):** Если несколько процессов в `D-state` ожидают функции VFS (`inode_lock`, `ext4_*`, `xfs_*`), проблема, скорее всего, в конкуренции за метаданные, а не в диске.
    ```bash
    ps -eo pid,state,wchan:30,comm | awk '$2=="D"'
    ```

4.  **Специфика ext4 (mb_groups):** Неравномерное распределение аллокации может приводить к повышенной конкуренции между потоками.
    ```bash
    cat /proc/fs/ext4/*/mb_groups
    ```

### 3. Интерпретация каналов ожидания (wchan)

Если процесс висит в `D-state`, проверьте, на какой именно функции ядра он заблокирован:

```bash
ps -eo pid,state,wchan:30,comm | grep " D "
# → 1234 D io_schedule my_app
# → 5678 D get_request kworker/1:1
```

**Основные значения wchan:**
- `io_schedule`: Общее ожидание ввода-вывода.
- `get_request`: Процесс ждёт свободный слот в очереди планировщика (диск перегружен).
- `wait_on_page_bit`: Ожидание доступа к странице в кэше (часто при чтении или подкачке).
- `call_rwsem_down_read_failed`: Ожидание семафора (конкуренция за доступ к структурам данных, например, при частых `mmap`).
- `jbd2_log_wait_commit`: Ожидание фиксации данных в журнале ФС.
- `inode_lock` / `ext4_inode_lock` / `xfs_ilock`: Конкуренция за блокировки inode (Lock Contention).
- `balance_dirty_pages`: Ядро принудительно замедляет процесс из-за переполнения кэша записи.

### 4. Использование perf для трассировки блочного уровня

Если `iotop` молчит, можно посмотреть, какие процессы отправляют запросы на уровень блочных устройств:

```bash
sudo perf record -e block:block_rq_issue -a sleep 10
sudo perf report --sort comm,pid
# → Показывает реальных инициаторов запросов к драйверу диска.
```

### 5. Проверка io_uring

Для современных приложений (базы данных, веб-серверы) классический `iotop` может не видеть активность. Используйте `bpftrace`:

```bash
# Трассировка входов в io_uring
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_io_uring_enter { @[comm] = count(); }'
# Нажмите Ctrl+C для остановки и просмотра агрегированной статистики
# → @[postgres]: 45231
# → @[mysqld]: 28914
```

### 6. Отслеживание открытия файлов (openat / opensnoop)

Приложение может тормозить не из-за дисковой нагрузки, а из-за тысяч вызовов `openat()` в секунду на несуществующие файлы, конфигурации или каталоги. `iotop` это не показывает, потому что данные с диска фактически не читаются: система выполняет путь поиска по каталогам, получает `ENOENT` и отбрасывает результат. Нагрузка попадает на CPU и VFS, а не на блок-уровень.

**Инструменты:**

- **`opensnoop`** (из пакета `bcc-tools`) — трассирует syscalls `open`, `openat`, `openat2` напрямую в ядре и выводит PID, процесс, дескриптор, код ошибки и путь.
- **`bpftrace`** — агрегирует события в ядре и показывает статистику по процессам и путям, что удобно при тысячах событий в секунду.

**Базовый вывод opensnoop:**

```bash
sudo opensnoop
# → PID     COMM        FD  ERR  PATH
# → 4217    app         12   0   /etc/app/config.json
# → 4217    app         -1   2   /etc/app/cache.db
# → 4217    app         -1   2   /tmp/app.lock
```

- `FD=-1` означает, что открыть файл не удалось.
- `ERR=2` соответствует `ENOENT` — файл не существует.
- Успешные открытия (`ERR=0`) тоже видны, но для поиска «тормозов» особенно интересны именно неудачные попытки: они показывают, что приложение повторяет бесполезный поиск.

**Фильтрация:**

```bash
# Только неудачные открытия
sudo opensnoop -x

# Только конкретный процесс
sudo opensnoop -p 4217
```

**Агрегация через bpftrace:**

Если вывод слишком большой, собирайте статистику непосредственно в ядре:

```bash
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_openat
{
    @[comm, str(args.filename)] = count();
}'
```

После остановки (`Ctrl+C`) получаете агрегированные счетчики, например:

```
@[app, "/etc/app/config.json"]: 18432
@[app, "/tmp/app.lock"]: 9217
@[app, "/proc/self/status"]: 4081
```

**Что искать:**

- Огромное количество обращений к одному и тому же несуществующему файлу.
- Постоянное чтение конфигурации вместо её кэширования.
- Бесконечный поиск библиотек или конфигов по нескольким каталогам.
- Приложения, которые постоянно открывают `/proc` и `/sys`.

**Важно:** `opensnoop` показывает именно попытки открытия, а не только успешные операции. Поэтому через него видны ошибки, которые обычный мониторинг диска вообще не заметит. Это типичный случай, когда «приложение просто тормозит», а причина — в тысячах повторяющихся syscall `openat()` и бесполезных поисках файлов.

### 7. Per-process I/O через /proc/\<pid\>/io

Для быстрого анализа ввода-вывода конкретного процесса без установки дополнительных инструментов используйте pseudo-файл `/proc/<pid>/io`:

```bash
cat /proc/1234/io
# → rchar: 123456789
# → wchar: 987654321
# → syscr: 12345
# → syscw: 98765
# → read_bytes: 123456789
# → write_bytes: 987654321
# → cancelled_write_bytes: 0
```

**Интерпретация:**
- `rchar`/`wchar`: общий объём данных, переданный через системные вызовы (включая Page Cache).
- `read_bytes`/`write_bytes`: реальный объём, прочитанный/записанный на диск (минус кэш).
- Если `wchar` >> `write_bytes` — процесс пишет много, но диск почти не нагружен (активный Page Cache).
- Если `write_bytes` близок к `wchar` — используется Direct I/O или кэш переполнен.

### 8. Диагностика файловой активности (fatrace)

Утилита `fatrace` (File Access Trace) показывает, какие процессы обращаются к каким файлам в реальном времени:

```bash
# Все события файлового доступа
sudo fatrace -t
# → 18:00:01 app(1234): W /var/lib/mysql/data.db
# → 18:00:01 app(1234): R /etc/app/nginx.conf

# Только конкретный процесс
sudo fatrace -t -p 1234

# Только события записи
sudo fatrace -w
```

### 9. Аппаратная диагностика

Если процессы в `D-state` не объясняются нагрузкой, проверьте физическое состояние дисков:

```bash
# SMART-статистика (замените sda на нужное устройство)
sudo smartctl -a /dev/sda | grep -E 'SMART|Reallocated|Pending|Current_Pending_Sector'

# Логи ядра на ошибки диска
sudo dmesg | grep -iE 'error|timeout|reset|ata|nvme|scsi'

# NVMe — подробный лог
sudo nvme smart-log /dev/nvme0 | grep -E 'critical_warning|temperature|percentage_used'
```

## Использование eBPF инструментов

eBPF позволяет «прошить» стек I/O и увидеть задержки там, где стандартные счетчики их не фиксируют.

```bash
# Распределение задержек (гистограмма)
# Помогает понять, вызвана ли проблема редкими долгими запросами или общей медлительностью
sudo biolatency-bpfcc -D 1 10
# -D: показать гистограммы для каждого устройства отдельно.

# Кто именно пишет на диск прямо сейчас (на уровне block io)
sudo biosnoop-bpfcc | head -n 20
# → Трассирует каждый запрос: COMM, PID, LAT(ms)

# Время, проведённое процессом вне CPU (offcputime)
sudo offcputime-bpfcc -K -m 5
# Показывает, в каких функциях ядра процесс проводит время, ожидая I/O.
```

## Типичные ошибки и устранение неполадок

| Симптом | Возможная причина | Метод диагностики | Решение |
| :--- | :--- | :--- | :--- |
| `iotop` показывает только `kworker` | Фоновый writeback или журналирование | `biosnoop-bpfcc`, `cat /proc/meminfo \| grep Writeback` | Нормальное поведение ядра. Если `kworker` загружает диск >80% — тюнинг `vm.dirty_*` параметров |
| `iotop` показывает нули для процесса | `CONFIG_TASK_DELAY_ACCT` отключена, io_uring, Direct I/O | `grep TASK_DELAY_ACCT /boot/config-$(uname -r)`, `bpftrace` | Включите `CONFIG_TASK_DELAY_ACCT` или используйте `pidstat -d`, `bpftrace` |
| Высокий `await` при низком `%util` | Случайное чтение (Random I/O) или умирающий диск | `iostat -xz 1` (смотрим `avgqu-sz`, `r/s`, `w/s`) | Замена диска, изменение scheduler на `deadline`/`bfq`, увеличение stripe size (RAID) |
| Процессы в `D-state`, но диск простаивает | Lock Contention (VFS/inode) или зависший NFS | `ps -eo pid,state,wchan:30,comm \| grep " D "`, `nfsstat -m` | Перезапуск NFS-демона, пересборка ядра с увеличенным `NR_CPUS` для better scalability |
| `sar -d` показывает нагрузку, но нет процесса-виновника | Всё тот же writeback или kworker | `sar -n DEV`, `cat /proc/meminfo \| grep Dirty` | Корректировка `vm.dirty_ratio` и `vm.dirty_background_ratio` |
| `biolatency` показывает пики >100 мс | Аппаратная ошибка или throttling (в VM) | `dmesg`, `smartctl`, `cat /proc/pressure/io` | Замена диска, проверка гипервизора (IOPS limit), сброс кэша контроллера |

## Best Practices

1.  **Проверяйте PSI первым:** Перед тем как углубляться в трассировку процессов, убедитесь, что проблема действительно в I/O. `cat /proc/pressure/io` даёт ответ за секунду.
2.  **Коррелируйте метрики:** Никогда не полагайтесь на одну утилиту. Сочетайте `iostat` (устройства), `pidstat` (процессы), `vmstat` (система) и PSI (давление).
3.  **Используйте `pidstat -d` для коротких всплесков:** В отличие от `iotop`, `pidstat` показывает изменения за заданный интервал и не пропускает кратковременную активность.
4.  **Проверяйте оборудование:** При высокой задержке без явного виновника первым делом запустите `smartctl` и `dmesg`. Физические ошибки (bad sectors, failing controller) часто маскируются под «невидимый» I/O.
5.  **Мониторьте историю:** Для анализа инцидентов после факта используйте `sar` (sysstat) или `atop` с включённым журналированием. Это позволяет увидеть всплески, которые не были замечены в реальном времени.
6.  **Изучайте Wait Channels:** `cat /proc/<pid>/wchan` часто даёт больше информации, чем десять минут просмотра `iotop`. Канал ожидания указывает на конкретную функцию ядра.
7.  **Не игнорируйте файловую систему:** Метаданные (inode, journal) могут становиться узким местом даже на быстрых NVMe. Проверяйте `jbd2` и `ext4`/`xfs` метрики через `pidstat` и `perf`.

## Ограничения и особые случаи

### 32-битные системы
На архитектурах, отличных от x86_64, адресация `/proc/<pid>/io` может отличаться. Формат файла остаётся совместимым, но некоторые eBPF-утилиты могут требовать перекомпиляции.

### Контейнеры (cgroups v1 vs v2)
- **cgroups v1:** `io.stat` существует только для blkio контроллера. Нет PSI (`io.pressure` отсутствует). Используйте `cat /sys/fs/cgroup/blkio/docker/*/io.stat`.
- **cgroups v2:** `io.pressure` доступен, что позволяет измерять давление на I/O внутри контейнера. Путь: `/sys/fs/cgroup/<container-id>/io.pressure`.
- Внутри контейнера `iotop` видит только процессы этого контейнера, но не может отличить I/O контейнера от I/O хоста.

### Виртуализация (KVM, VMware)
- Паравиртуализированные драйверы (`virtio-blk`, `vmw_pvscsi`) могут кэшировать запросы, скрывая реальную задержку от гостевой ОС.
- В гипервизорных средах throttling часто применяется на уровне хоста, и гость видит только результат, а не причину. Используйте `dmesg` и метрики хоста для подтверждения.

### RAID/шифрование
- **Hardware RAID:** Контроллер скрывает отдельные диски. `iostat` показывает только виртуальное устройство. Для диагностики используйте утилиты вендора (`megacli`, `hpacucli`).
- **dm-crypt (LUKS):** Шифрование добавляет overhead на CPU. При высокой нагрузке процесс `dm-crypt` может потреблять CPU, маскируя проблему как CPU-bound, хотя корень — в I/O.

### NFS/FUSE
- Сетевые файловые системы добавляют сетевую задержку, которая в `iotop` выглядит как обычный I/O wait.
- `nfsstat -c` и `nfsstat -m` помогают区分 сетевые проблемы от локальных.
- FUSE-файловые системы (например, `sshfs`) могут заблокировать процесс в пользовательском пространстве, что видно по `wchan` (`fuse_dev_read`).
