# Диагностика Tail Latency

## Определение

**Tail Latency** (или "длинный хвост" задержек) — это явление, при котором большинство запросов к сервису обрабатываются быстро, но небольшая часть из них занимает аномально много времени. Например, 99% запросов выполняются за 50 мс, а оставшийся 1% — за 1-2 секунды.

Такие редкие, но болезненные тормоза сложно отследить с помощью стандартных метрик (среднее CPU, утилизация памяти), так как в среднем система выглядит незагруженной.

## Основные концепции

Чаще всего источник tail latency находится не в коде приложения, а на уровне операционной системы: в планировщике задач, механизмах блокировок или сетевом стеке. Проблема рождается на границе между пользовательским приложением и ядром Linux.

Основные "подозреваемые":
1.  **Задержки планировщика (Scheduler Latency):** Поток приложения готов к работе, но ядро не предоставляет ему процессорное время из-за высокой конкуренции или других причин.
2.  **Конкуренция за блокировки (Lock Contention):** Потоки простаивают, ожидая освобождения мьютексов или фьютексов (`futex`), которые используются для синхронизации.
3.  **Проблемы в сетевом стеке:** Потери пакетов, маленький размер окна перегрузки TCP (`cwnd`) или высокая задержка (`RTT`) могут приводить к "зависанию" отдельных запросов.

## Практические сценарии: Поиск источника задержек

### 1. Проверка задержек планировщика

Если CPU свободен, память есть, а GC не срабатывает, первое, что стоит проверить, — это задержки планировщика. Для этого используется `perf`. Подробное описание инструмента доступно в заметке **[Анализ производительности с помощью `perf`](./perf.md)**.

```bash
# 1. Собрать события планировщика в течение 30 секунд
sudo perf sched record -a sleep 30

# 2. Проанализировать собранные данные
sudo perf sched latency
```

Этот отчёт показывает, какие процессы и потоки долго ждут CPU. Ищите процессы с большим `wakeup latency` (время от пробуждения до получения CPU) или странные паузы между запусками потоков.

### 2. Анализ конкуренции за блокировки (futex)

Когда потоки активно ждут `futex`-блокировки, сервис может выглядеть «ненагруженным», но при этом отдельные запросы застревают в очередях синхронизации. `perf trace` поможет это отследить.

```bash
# Отслеживать системные вызовы futex в реальном времени
sudo perf trace -e futex
```
Большое количество долгих ожиданий `futex` указывает на "бутылочное горлышко" в коде, связанное с синхронизацией.

### 3. Диагностика сетевого стека

Если с CPU всё чисто, стоит заглянуть в сеть с помощью `ss`. Подробное описание инструмента доступно в заметке **[Анализ сокетов с помощью `ss`](../Networking/ss.md)**.

```bash
# Проверить состояние TCP-соединений к порту сервиса
ss -ti dst :<порт_сервиса>
```

На что обращать внимание в выводе `ss -ti`:
-   **Маленький `cwnd` (Congestion Window):** TCP "душит" соединение из-за потерь пакетов.
-   **Большое количество `retrans` (Retransmissions):** Явный признак потерь пакетов в сети.
-   **Резко выросший `RTT` (Round-Trip Time):** Указывает на задержки на маршруте, особенно за VPN, балансировщиками или при проблемах с MTU.
