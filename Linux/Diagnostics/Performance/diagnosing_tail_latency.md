# Диагностика Tail Latency (Хвостовой задержки)

## Определение

**Tail Latency** (или «длинный хвост» задержек) — это явление, при котором подавляющее большинство запросов к системе обрабатываются быстро (согласно SLA), но небольшая часть (перцентили p95, p99, p99.9) занимает аномально много времени. Например, при среднем времени ответа в 50 мс, 1% запросов может выполняться 2 секунды и более.

Особенность Tail Latency заключается в том, что её практически невозможно обнаружить по усреднённым метрикам (Mean Latency, Average CPU), так как они скрывают аномальные выбросы. Основная цель диагностики — найти причину **ожидания** (waiting), а не выполнения.

## Основные концепции

### Принцип «хвоста» и почему средние значения вводят в заблуждение

В распределённых системах и ядрах Linux задержки редко服从 нормальному распределению. Чаще всего мы видим логнормальное или степенное распределение, где «хвост» содержит редкие, но критичные события.

- **Медиана (p50):** отражает типичный опыт пользователя.
- **p95/p99:** показывают наихудший опыт 5% или 1% пользователей. Именно эти запросы формируют восприятие надёжности системы.
- **p99.9:** экстремальные случаи, характерные для high-frequency trading и real-time систем.

**Формула Кингмана:** время ожидания в очереди $W$ экспоненциально растёт при приближении утилизации ресурсов $U$ к 100%:
$$W = \frac{U}{1-U} \cdot S$$
где $S$ — среднее время обслуживания. При $U = 0.8$ ожидание уже в 4 раза больше среднего времени; при $U = 0.9$ — в 10 раз.

### Ключевые причины возникновения

В современных Linux-системах (ядра 6.x+) диагностика сместилась от анализа «загрузки» ресурсов к анализу «давления» (pressure) и трассировке событий вне CPU.

1.  **Задержки планировщика (Scheduler Latency):** Поток готов к выполнению (Runnable), но ядро не предоставляет ему CPU из-за конкуренции.
2.  **Троттлинг контейнеров (Cgroup Throttling):** Искусственное замедление процесса ядром из-за превышения лимитов `cpu.max` или `memory.high` в cgroup v2.
3.  **Ожидание вне CPU (Off-CPU):** Блокировки на мьютексах/фьютексах, ожидание дискового I/O или сетевых ответов.
4.  **Микро-джиттер (Jitter):** Задержки, вызванные обработкой аппаратных прерываний (HardIRQ), мягких прерываний (SoftIRQ) или системными задачами ядра (например, Transparent Huge Pages).
5.  **Сетевой стек:** Потери пакетов, приводящие к таймаутам ретрансмиссии (RTO), или малый размер окна TCP (`cwnd`).

### PSI: Some vs Full

При работе с `/proc/pressure/*` важно различать:

- **`some`**: процент времени, когда **хотя бы одна** задача была заблокирована. Указывает на конкуренцию.
- **`full`**: процент времени, когда **все** не-idle задачи были заблокированы одновременно. Указывает на критическое насыщение (thrashing).

Для CPU и IRQ доступна только метрика `some`, так как система всегда выполняет хотя бы один процесс (планировщик).

## Предварительные требования

### Аппаратные требования

- **ОС:** Linux с ядром 5.4+ (рекомендуется 6.1+ для полной поддержки PSI и cgroups v2).
- **Архитектура:** x86_64, ARM64.
- **Доступ:** root-права для установки eBPF-инструментов (bcc-tools, bpftrace).

### Программные требования

```bash
# Проверка версии ядра
uname -r
# → 6.1.0-18-amd64 (требуется минимум 5.4)

# Установка инструментов eBPF (Debian/Ubuntu)
apt-get install bpfcc-tools linux-headers-$(uname -r) bpftrace

# Проверка наличия PSI
cat /proc/pressure/cpu
# → some avg10=0.00 avg60=0.00 avg300=0.00 total=0

# Проверка включенного task_delayacct
cat /proc/sys/kernel/task_delayacct
# → 1 (обязательно для offcputime-bpfcc)
```

### Требования к окружению

- **cgroups v2:** убедитесь, что система использует cgroups v2 (не hybrid mode):
  ```bash
  mount | grep cgroup2
  # → cgroup2 on /sys/fs/cgroup type cgroup2 (rw,nosuid,nodev,noexec,relatime)
  ```
- **Отключенный irqbalance** (рекомендуется для high-load систем): `systemctl disable --now irqbalance`
- **Наличие `rtla`** (Kernel 5.17+):
  ```bash
  rtla timerlat top --help
  ```

## Практические сценарии

### Шаг 1: Оценка системного давления (PSI)

Метрики PSI позволяют мгновенно понять, является ли причиной задержек нехватка CPU, памяти или I/O.

```bash
# Проверка давления на CPU (некоторые задачи ждут ресурсов)
cat /proc/pressure/cpu
# some avg10=12.50 avg60=5.30 avg300=2.10 total=1450234
# avg10 > 10% — явный признак конкуренции за процессор.

# Проверка давления на память (признак активного reclaim или swap)
cat /proc/pressure/memory
# full avg10=0.00 avg60=0.00 avg300=0.00 total=0

# Проверка давления на I/O (дисковые задержки)
cat /proc/pressure/io
# some avg10=8.40 avg60=3.20 avg300=1.50 total=892341
```

**Ожидаемый результат:** `avg10` < 5% для каждого ресурса в здоровой системе. Значения > 10% указывают на активные задержки.

### Шаг 2: Диагностика троттлинга в контейнерах

В Kubernetes/Docker задержки p99 часто вызваны механизмом CFS Throttling.

```bash
# Проверка статистики троттлинга в cgroup v2
cat /sys/fs/cgroup/system.slice/my-app.service/cpu.stat
# nr_periods 12345
# nr_throttled 892
# throttled_usec 12500000
# → throttled_usec / nr_periods > 10% — проблема

# Или для Docker-контейнера
cat /sys/fs/cgroup/docker/<CONTAINER_ID>/cpu.stat
```

**Валидация:** `nr_throttled` не должен расти со скоростью >10% от `nr_periods`. При превышении — увеличить лимиты или оптимизировать код.

### Шаг 3: Off-CPU анализ через eBPF

Самый мощный метод поиска причин Tail Latency. Позволяет увидеть, где поток «спал», пока пользователь ждал ответ.

```bash
# Сбор стеков вызовов при блокировках (требуется bcc-tools)
sudo offcputime-bpfcc -p <PID> 10
# → Вывод: суммарное время вне CPU с раскладкой по стеку вызовов.
# Ищите: mutex_lock, sem_wait, fsync, poll_schedule_timeout, io_submit.

# Построение гистограммы задержек в очереди планировщика
sudo runqlat-bpfcc 10 1
# → Гистограмма: ось X = задержка в мкс/мс, ось Y = количество событий.
# «Хвост» за 10 мс — симптом нехватки CPU.
```

**Ожидаемый результат:** доминирующие пики на 0–100 мкс (здоровый runqlat). Широкий «хвост» за 1–10 мс требует внимания.

### Шаг 4: Анализ сетевого стека через `ss` и `tcpconnlat`

Проверка состояния TCP-соединений для исключения сетевых причин.

```bash
# Детальная информация о TCP-параметрах (rto, cwnd, retrans)
ss -ti dst :<порт_сервиса>
# Ищите: rto: 300 (большое значение = медленные ретрансмиссии), retrans: >0

# Измерение задержек handshake (eBPF)
sudo tcpconnlat
# → Время от SYN до ESTABLISHED для каждого соединения.

# Отслеживание ретрансмиссий в реальном времени
sudo tcpretrans
```

### Шаг 5: Выявление джиттера через `rtla`

Новый стандарт (Kernel 5.17+) для диагностики микро-задержек, вызванных ядром или оборудованием.

```bash
# Измерение задержки пробуждения задачи (Timer Latency)
sudo rtla timerlat top -d 10
# → Трассировка задержек на уровне таймеров ядра.
# Ищите: выбросы > 100 мкс (воздействие HardIRQ/SoftIRQ).

# Анализ задержек планировщика (sched)
sudo rtla sched lat top -d 10
```

### Шаг 6: Диагностика дискового вклада (Tail Latency на диске)

Дисковые задержки часто становятся причиной «хвоста», особенно на NVMe с высокой вариативностью.

```bash
# Гистограмма задержек выполнения I/O (eBPF)
sudo biolatency-bpfcc -D 1 10
# → Распределение задержек по гистограмме.
# Обращайте внимание на корзины > 50–100 мс (хвост).

# Трассировка конкретного блочного устройства
sudo biosnoop-bpfcc -d sda 1
# → Каждая операция I/O: PID, команда, задержка, размер.
# Сопоставьте PID с «проблемным» процессом из Step 3.

# Проверка D-state процессов (Uninterruptible Sleep)
ps -eo pid,stat,pri,ni,wchan,comm | grep '^.* D '
# → Процессы в D состоянии ожидают завершения I/O.
```

### Шаг 7: Анализ Transparent Huge Pages (THP) и дефрагментации

THP могут вызывать микропаузы (compaction stalls), которые искажают Tail Latency.

```bash
# Проверка настройки THP
cat /sys/kernel/mm/transparent_hugepage/enabled
# → [madvise] (рекомендуется) или always

# Мониторинг stall'ов компакции
cat /proc/vmstat | grep -E "compact_success|compact_fail|compact_daemon_migrate"
# → Рост compact_fail при высокой нагрузке = деградация.
```

## Устранение неисправностей

| Проблема | Вероятная причина | Диагностические команды | Решение |
| :--- | :--- | :--- | :--- |
| **p99 вырос, p50 в норме** | Off-CPU блокировки, мьютексы | `sudo offcputime-bpfcc -p <PID> 5` | Оптимизировать синхронизацию, уменьшить критическую секцию |
| **Высокий `throttled_usec`** | CFS Throttling, превышение cpu.max | `cat /sys/fs/cgroup/.../cpu.stat` | Увеличить `cpu.max` или оптимизировать bursts |
| **p99 растёт под нагрузкой** | Формула Кингмана: U → 100% | `cat /proc/pressure/cpu` + `uptime` | Добавить capacity, внедрить queue shedding |
| **Резкие скачки p99** | SoftIRQ Storm, Network IRQ | `sudo rtla timerlat top -d 5` | Настроить `irqbalance`, RSS/RPS, уменьшить netdev_budget |
| **Tail Latency на диске** | D-state, I/O pressure | `sudo biolatency-bpfcc -D 1 10` | Переход на NVMe, включение blk-mq, проверка schedulers |
| **Рост RTO, retrans** | Потери пакетов, перегрузка | `ss -ti`, `sudo tcpretrans` | Настроить TCP BBR, проверить MTU, offload'ы |
| **p99.9 экстремальный** | THP compaction, GC pauses | `cat /proc/vmstat \| grep compact` | Переключить THP на `madvise`, настроить THP defrag |

## Валидация

### Ожидаемые результаты здоровой системы

- **PSI:** `avg10` < 2% для CPU/Memory/I/O.
- **runqlat:** 99% событий < 1 мс.
- **offcputime:** доминирующие стеки — ожидание `poll`/`epoll_wait` (сетевые серверы), а не `mutex_lock` (признак contention).
- **biolatency:** 99% операций < 10 мс на SSD/NVMe.
- **tcpconnlat:** handshake < 1 мс в локальной сети.

### Согласованность с другими инструментами

| Инструмент | Что проверять | Согласованность |
| :--- | :--- | :--- |
| [`atop`](./atop.md) | PSI и CPU статистика за интервал | Должно совпадать с `cat /proc/pressure/*` |
| [`sar`](./sar.md) | `DEV` и `QUEUE` — задержки диска | Коррелирует с `biolatency-bpfcc` |
| [`perf`](./perf.md) | `perf sched` — время runnable | Должно объяснять пики в `runqlat` |
| [`ss`](https://man7.org/linux/man-pages/man8/ss.8.html) | `-ti` — RTO, retrans | Должно объяснять сетевой `avg10` в PSI |

## Рекомендации (Best Practices)

1.  **Мониторинг перцентилей, а не средних:** Настройте алерты на p99/p99.9, а не на Average. Среднее значение скрывает проблемы.
2.  **SLO на p99, а не p50:** Для SLA веб-сервисов используйте p99. Это гарантирует опыт 99% пользователей.
3.  **PSI-first диагностика:** При каждом инциденте первым делом проверяйте `/proc/pressure/*`. Это позволяет за секунды понять класс проблемы (CPU/Memory/I/O).
4.  **eBPF по необходимости:** Инструменты bcc-tools дают максимальную детализацию, но требуют root. В продакшене используйте их для targeted-диагностики, а не для постоянного мониторинга.
5.  **Сопоставление PID и cgroup:** При диагностике в Kubernetes сопоставляйте PID cgroup-пути через `cat /proc/<PID>/cgroup`. Это позволяет найти ответственный под.
6.  **Корреляция Timeline:** Используйте `atop` или `syswatch` для восстановления Timeline инцидента. Сопоставляйте пики p99 с метриками системы в тот же момент.
7.  **Избегайте «средней» температуры по больнице:** p99 на уровне сервиса может скрывать, что проблема только на одной реплике. Разделяйте метрики по pod/node.
8.  **Документируйте baseline:** Измерьте p99 в спокойном состоянии (baseline). Любое отклонение >2x baseline — повод для глубокой диагностики.

## Ограничения и особенности

1.  **Только чтение / Linux-only:** `offcputime-bpfcc`, `runqlat-bpfcc`, `rtla` — инструменты Linux. На macOS и Windows доступна только PSI через аналоги (no native PSI).
2.  **Overhead eBPF:** На высоконагруженных системах (100k+ процессов) `offcputime-bpfcc` может создавать overhead до 3–5% CPU из-за частых событий.
3.  **Kernel version sensitivity:**
    - `rtla` требует ядро 5.17+.
    - `biolatency-bpfcc` требует ядро 4.18+ с бэкporтом.
    - Некоторые `tracepoints` отсутствуют в старых ядрах RHEL/CentOS 7.
4.  **Container namespace isolation:** В Docker/Kubernetes `offcputime-bpfcc` видит стеки всех контейнеров на хосте. Нужно фильтровать по PID (см. `cat /proc/<PID>/cgroup`).
5.  **Tracing vs Sampling:** Трассировка (`-e trace=all`) создаёт огромные объёмы данных и не подходит для длительных сессий. Используйте сэмплирование или eBPF с агрегацией на стороне ядра.
6.  **NMI watchdog interference:**在某些 системах NMI watchdog может конфликтовать с `rtla` и `perf`, вызывая дополнительные задержки. Отключайте его на время диагностики: `echo 0 > /proc/sys/kernel/nmi_watchdog`.
7.  **Virtualization noise:** В виртуализированных окружениях (KVM, VMware) `steal time` (`%steal` в `top`) может имитировать Tail Latency, вызванный «шумным соседом» (noisy neighbor). Проверяйте `cat /proc/pressure/cpu` + `virt-what`.
8.  **Transparent Huge Pages:** Включённый THP (`always`) может вызывать недетерминированные паузы compaction (до сотен мс), которые трудно отловить без `tracepoints`.
9.  **Сетевые драйверы:** Некоторые NIC-драйверы не поддерживают hardware timestamping, что делает измерение network tail latency неточным.
10. **Средние значения iostat:** `await` и `%util` скрывают Tail Latency. На NVMe 100% `%util` не означает насыщение. Используйте `biolatency-bpfcc` для гистограмм.
