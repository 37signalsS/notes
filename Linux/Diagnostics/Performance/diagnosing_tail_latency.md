# Диагностика Tail Latency (Хвостовой задержки)

## Определение

**Tail Latency** (или «длинный хвост» задержек) — это явление, при котором подавляющее большинство запросов к системе обрабатываются быстро (согласно SLA), но небольшая часть (перцентили p95, p99, p99.9) занимает аномально много времени. Например, при среднем времени ответа в 50 мс, 1% запросов может выполняться 2 секунды и более.

Особенность Tail Latency заключается в том, что её практически невозможно обнаружить по усреднённым метрикам (Mean Latency, Average CPU), так как они скрывают аномальные выбросы. Основная цель диагностики — найти причину **ожидания** (waiting), а не выполнения.

## Основные концепции

В современных Linux-системах (ядра 6.x+) диагностика сместилась от анализа «загрузки» ресурсов к анализу «давления» (pressure) и трассировке событий вне CPU.

### Ключевые причины возникновения

1.  **Задержки планировщика (Scheduler Latency):** Поток готов к выполнению (Runnable), но ядро не предоставляет ему CPU из-за конкуренции.
2.  **Троттлинг контейнеров (Cgroup Throttling):** Искусственное замедление процесса ядром из-за превышения лимитов `cpu.max` или `memory.high` в cgroup v2.
3.  **Ожидание вне CPU (Off-CPU):** Блокировки на мьютексах/фьютексах, ожидание дискового I/O или сетевых ответов.
4.  **Микро-джиттер (Jitter):** Задержки, вызванные обработкой аппаратных прерываний (HardIRQ), мягких прерываний (SoftIRQ) или системными задачами ядра (например, Transparent Huge Pages).
5.  **Сетевой стек:** Потери пакетов, приводящие к таймаутам ретрансмиссии (RTO), или малый размер окна TCP (`cwnd`).

## Практические сценарии

### Шаг 1: Оценка системного давления (PSI)

Метрики PSI позволяют мгновенно понять, является ли причиной задержек нехватка CPU, памяти или I/O.

```bash
# Проверка давления на CPU (некоторые задачи ждут ресурсов)
cat /proc/pressure/cpu
# avg10 > 10% — явный признак конкуренции за процессор.

# Проверка давления на память (признак активного reclaim или swap)
cat /proc/pressure/memory
```

### Шаг 2: Диагностика троттлинга в контейнерах

В Kubernetes/Docker задержки p99 часто вызваны механизмом CFS Throttling.

```bash
# Проверка статистики троттлинга в cgroup v2
cat /sys/fs/cgroup/system.slice/my-app.service/cpu.stat
# Ищите рост поля 'throttled_usec'.
```

### Шаг 3: Off-CPU анализ через eBPF

Самый мощный метод поиска причин Tail Latency. Позволяет увидеть, где поток «спал», пока пользователь ждал ответ.

```bash
# Сбор стеков вызовов при блокировках (требуется bcc-tools)
sudo offcputime-bpfcc -p <PID> 10

# Построение гистограммы задержек в очереди планировщика
sudo runqlat-bpfcc 10 1
```

### Шаг 4: Анализ сетевого стека через `ss` и `netstacklat`

Проверка состояния TCP-соединений для исключения сетевых причин.

```bash
# Детальная информация о TCP-параметрах (rto, cwnd, retrans)
ss -ti dst :<порт_сервиса>

# Измерение задержек внутри функций сетевого стека ядра (eBPF)
sudo netstacklat
```

### Шаг 5: Выявление джиттера через `rtla`

Новый стандарт (Kernel 5.17+) для диагностики микро-задержек, вызванных ядром или оборудованием.

```bash
# Измерение задержки пробуждения задачи (Timer Latency)
sudo rtla timerlat top
```

## Дополнительная информация

### Инструменты для разных уровней анализа

| Уровень | Инструмент | Что искать |
| :--- | :--- | :--- |
| **Система** | `PSI` | `avg10` > 5% для любого ресурса. |
| **Планировщик** | `runqlat` | «Хвосты» гистограммы > 10 мс. |
| **Приложение** | `offcputime` | Стеки с `mutex_lock`, `sem_wait`, `fsync`. |
| **Сеть** | `ss`, `tcpretrans` | Рост `rto` или наличие `retrans`. |
| **Микро** | `rtla`, `Intel PT` | Задержки на уровне инструкций и прерываний. |

### Ретроспективный анализ

Для анализа инцидентов в прошлом используйте:
- [`atop`](./atop.md): хранит историю PSI и активности процессов.
- [`sar`](./sar.md): отчеты о сетевых ошибках и очередях CPU.
- **Continuous Profiling** (Pyroscope/Parca): eBPF-профилирование Off-CPU в режиме 24/7.
