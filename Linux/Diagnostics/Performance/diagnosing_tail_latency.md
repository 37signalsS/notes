# Диагностика Tail Latency

## Определения

**Tail Latency** (или «длинный хвост» задержек) — это явление, при котором большинство запросов к сервису обрабатываются быстро, но небольшая часть занимает аномально много времени. Например, 99% запросов выполняются за 50 мс, а оставшийся 1% — за 1–2 секунды.

Такие редкие задержки сложно отследить с помощью стандартных метрик (среднее значение CPU, утилизация памяти), так как в среднем система выглядит незагруженной.

Инструменты, описанные в этом разделе, дополняют друг друга: [perf](./perf.md) анализирует задержки на уровне ядра, [sar](./sar.md) отслеживает исторические данные о производительности системы.

## Основные концепции

Источник tail latency находится не в коде приложения, а на уровне операционной системы: в планировщике задач, механизмах блокировок или сетевом стеке.

Основные причины:

1. **Задержки планировщика (Scheduler Latency):** Поток приложения готов к выполнению, но ядро не предоставляет процессорное время из-за высокой конкуренции.
2. **Конкуренция за блокировки (Lock Contention):** Потоки простаивают в ожидании освобождения мьютексов или фьютексов (`futex`), используемых для синхронизации.
3. **Проблемы сетевого стека:** Потери пакетов, малый размер окна перегрузки TCP (`cwnd`) или высокая задержка (`RTT`) приводят к задержкам отдельных запросов.

## Практические сценарии

### 1. Проверка задержек планировщика

Для анализа задержек планировщика используется `perf`. Подробное описание — в заметке [Анализ производительности с помощью `perf`](./perf.md).

```bash
# Собрать события планировщика в течение 30 секунд
sudo perf sched record -a sleep 30

# Проанализировать собранные данные
sudo perf sched latency
```

Отчёт показывает процессы и потоки с наибольшим временем ожидания CPU. Ключевые метрики: `wakeup latency` (время от пробуждения до получения CPU) и паузы между запусками потоков.

### 2. Анализ конкуренции за блокировки (futex)

При ожидании потоками `futex`-блокировок сервис может выглядеть ненагруженным, но отдельные запросы задерживаются в очередях синхронизации.

```bash
# Отслеживать системные вызовы futex в реальном времени
sudo perf trace -e futex
```

Большое количество длительных ожиданий `futex` указывает на проблему синхронизации в коде.

### 3. Диагностика сетевого стека

Для проверки состояния TCP-соединений используется `ss`. Подробное описание — в заметке [Анализ сокетов с помощью `ss`](../Networking/ss.md).

```bash
# Проверить состояние TCP-соединений к порту сервиса
ss -ti dst :<порт_сервиса>
```

Ключевые метрики в выводе `ss -ti`:

- **`cwnd` (Congestion Window):** Малое значение указывает на ограничение пропускной способности TCP из-за потерь пакетов.
- **`retrans` (Retransmissions):** Высокое значение подтверждает потерю пакетов в сети.
- **`RTT` (Round-Trip Time):** Резкое увеличение указывает на задержки на маршруте (VPN, балансировщики, проблемы с MTU).

### 4. Проверка распределения сетевой нагрузки (SoftIRQ и RPS/XPS)

Неравномерное распределение `softirq` — частая причина tail latency в высоконагруженных сетевых приложениях.

**Симптоматика:** интерфейс пропускает трафик, пропускная способность в норме, но одно ядро загружено обработкой `softirq` (`si` в `top`/`htop`), остальные — не задействованы. Под пиковой нагрузкой это вызывает скачки latency.

**Причина:** технологии GRO/LRO ([Network Offloading](../../Networking/Concepts/offloading.md)) агрегируют пакеты, но обработка концентрируется на одном ядре при отсутствии настройки RPS/XPS.

**Диагностика:**

```bash
# Распределение прерываний
cat /proc/interrupts

# Активность softirq по ядрам
cat /proc/softirqs | grep NET_RX

# Настройки RPS/XPS
cat /sys/class/net/eth0/queues/rx-*/rps_cpus
cat /sys/class/net/eth0/queues/tx-*/xps_cpus
```

Если счётчики растут на одном CPU, а маски пустые — нагрузка не распределяется.

**Решение:** настройка RPS/XPS для равномерного распределения по ядрам. Подробно — в [RSS, RPS, RFS](../../Networking/Concepts/rss_rps_rfs.md#симптоматика-неравномерного-распределения).
