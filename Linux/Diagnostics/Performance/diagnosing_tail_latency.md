# Диагностика Tail Latency

## Определение

**Tail Latency** (или «длинный хвост» задержек) — это явление, при котором подавляющее большинство запросов к системе обрабатываются быстро (согласно SLA), но небольшая часть (перцентили p95, p99, p99.9) занимает аномально много времени. Например, при среднем времени ответа в 50 мс, 1% запросов может выполняться 2 секунды и более.

Особенность Tail Latency заключается в том, что её крайне сложно обнаружить по усреднённым метрикам (Average CPU, Mean Latency), так как система в целом может выглядеть недозагруженной и исправной.

## Основные концепции

В распределённых системах Tail Latency часто возникает не из-за ошибок в коде приложения, а из-за микро-задержек на уровне операционной системы, оборудования или сетевого взаимодействия.

### Ключевые причины возникновения

1. **Задержки планировщика (Scheduler Latency):** Поток приложения готов к выполнению (состояние Runnable), но ядро не предоставляет ему процессорное время из-за конкуренции с другими процессами или прерываниями.
2. **Конкуренция за блокировки (Lock Contention):** Потоки простаивают в ожидании освобождения примитивов синхронизации (мьютексов, фьютексов), что может не отражаться на загрузке CPU.
3. **Сетевой стек и очереди:** Потери пакетов, переполнение очередей сетевых карт, повторные передачи (retransmissions) или малый размер окна TCP (`cwnd`).
4. **Фоновые процессы ОС:** Активность `kswapd` (свопинг), `jbd2` (журналирование ФС) или прозрачные огромные страницы (Transparent Huge Pages).

## Практические сценарии

### Анализ задержек планировщика через `perf`

Для выявления ситуаций, когда процесс ждёт CPU, используется подкоманда `perf sched`. Подробности настройки инструмента — в разделе [Анализ производительности с помощью perf](./perf.md).

```bash
# Сбор событий планировщика (на всех ядрах) в течение 30 секунд
sudo perf sched record -a sleep 30

# Вывод таблицы задержек
sudo perf sched latency
```

**Метрики:**

- `avg delay`: среднее время ожидания CPU после пробуждения.
- `max delay`: максимальный «затык», вызвавший Tail Latency.

### Диагностика блокировок через `perf trace`

Если приложение потребляет мало CPU, но отвечает медленно, возможно, оно блокируется на системных вызовах.

```bash
# Отслеживание системных вызовов futex (синхронизация потоков)
sudo perf trace -e futex
```

Длительные вызовы `futex` с последующим пробуждением указывают на высокую конкуренцию за общие ресурсы внутри приложения.

### Проверка сетевых параметров через `ss`

Анализ состояния конкретных TCP-соединений помогает исключить проблемы на транспортном уровне. Подробности — в [Анализ сокетов с помощью ss](../Networking/ss.md).

```bash
# Детальная информация о TCP-соединениях к конкретному порту
ss -ti dst :<порт_сервиса>
```

**На что смотреть:**

- `rto`: (Retransmission Timeout) — высокие значения указывают на потери пакетов.
- `cwnd`: (Congestion Window) — малый размер окна ограничивает скорость передачи.
- `retrans`: наличие повторных передач подтверждает проблемы в сети.

### Проверка распределения SoftIRQ

Неравномерная нагрузка на ядра при обработке сетевых прерываний (`SoftIRQ`) — классическая причина скачков задержек.

```bash
# Просмотр статистики мягких прерываний по ядрам
watch -n1 "cat /proc/softirqs | grep NET_RX"
```

Если одно ядро загружено на 100% (поле `si` в `top`), а остальные простаивают, необходимо настроить механизмы RPS/XPS. Подробно — в [RSS, RPS, RFS](../../Networking/Concepts/rss_rps_rfs.md).

## Дополнительная информация

### Инструменты исторического анализа

Для ретроспективного анализа Tail Latency, когда инцидент уже завершён, используются данные системных сборщиков:

- [`sar`](./sar.md): позволяет посмотреть историческую нагрузку на CPU, сеть и диски с интервалом в несколько минут.
- [`atop`](./atop.md): сохраняет более детальные «снимки» системы, включая активность отдельных процессов.
