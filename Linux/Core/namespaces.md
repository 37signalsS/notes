# Пространства имён (namespaces)

## Определения

**Namespaces (Пространства имён)** — фундаментальный механизм ядра Linux, обеспечивающий изоляцию и виртуализацию системных ресурсов для группы процессов. Он позволяет процессам иметь собственные независимые экземпляры системных ресурсов, создавая полную иллюзию работы в отдельной операционной системе.

**Ключевое различие между Namespaces и Cgroups:**

- **Namespaces** отвечают за **изоляцию видимости** (что процесс *может видеть*). Например, список процессов, сетевые интерфейсы или точки монтирования.
- **[Контрольные группы (cgroups)](./cgroups.md)** отвечают за **ограничение потребления** (что процесс *может использовать*). Например, лимиты CPU, RAM или лимиты на количество процессов (PIDs).

Вместе эти технологии образуют основу современной контейнеризации (Docker, Podman, Kubernetes, systemd-nspawn).

## Основные концепции

### Типы namespaces

| Namespace | Флаг `clone(2)` | Изолирует | Ключевые объекты |
| :--- | :--- | :--- | :--- |
| **Mount (mnt)** | `CLONE_NEWNS` | Таблица монтирования | Точки монтирования, корень ФС, Propagation. |
| **Process ID (pid)** | `CLONE_NEWPID` | Дерево процессов | PID 1, родительские связи, сигнализация. |
| **Network (net)** | `CLONE_NEWNET` | Сетевой стек | Интерфейсы, маршруты, iptables, сокеты. |
| **User** | `CLONE_NEWUSER` | UID/GID, Capabilities | Маппинг пользователей, Rootless-режимы. |
| **IPC** | `CLONE_NEWIPC` | Межпроцессное взаимодействие | System V IPC, POSIX Message Queues. |
| **UTS** | `CLONE_NEWUTS` | Идентификаторы хоста | Hostname, Domainname (NIS). |
| **Cgroup** | `CLONE_NEWCGROUP` | Иерархия ресурсов | Видимость пути к cgroup в `/proc/self/cgroup`. |
| **Time** | `CLONE_NEWTIME` | Системные часы | `CLOCK_BOOTTIME`, `CLOCK_TAI`. |

### Детальное описание механизмов

#### Mount (mnt)
Изолирует набор точек монтирования, видимых процессом. 
- Позволяет создавать изолированные корневые файловые системы (**rootfs**).
- Поддерживает механизм **Propagation** (Shared, Private, Slave, Unbindable), определяющий, как монтирования на хосте отражаются внутри namespace и наоборот.
- **Подробно:** [Пространства имён монтирования (mount namespaces)](../Virtualization/mount_namespaces.md).

#### PID (Process ID)
Позволяет процессам в разных namespaces иметь одинаковые PID.
- Первый процесс в новом PID namespace получает **PID 1** и берет на себя роль `init`.
- Если PID 1 завершается, ядро рассылает `SIGKILL` всем процессам в этом пространстве имен.
- Процесс «видит» только своих потомков в текущем namespace, но сам виден из родительского namespace с другим (глобальным) PID.

#### Network (net)
Обеспечивает полную виртуализацию сетевого стека.
- Каждый namespace имеет собственные интерфейсы (включая `lo`), таблицы маршрутизации, правила `iptables/nftables` и абстрактные сокеты.
- Для связи между namespaces используются **veth-пары** (виртуальные кабели) или мосты (bridge).
- **Подробно:** [Утилита ip netns](../Networking/Tools/iproute2/ip_netns.md).

#### User
Изолирует идентификаторы пользователей и групп.
- Позволяет процессу иметь `UID 0` (root) внутри namespace, оставаясь непривилегированным пользователем на хосте.
- **Capabilities** проверяются относительно текущего User Namespace. Это позволяет безопасно выполнять операции монтирования или настройки сети внутри контейнера.

#### Time (5.6+)
Позволяет изменять системное время внутри namespace без влияния на хост. Основная цель — поддержка миграции контейнеров (CRIU), когда нужно сохранить значение `uptime` или `boottime` процесса после переноса на другой физический сервер.

### Современные изменения и архитектура (2024–2026)

#### Pidfs и Pidfds (Kernel 6.8+)
Технология `pidfs` превращает дескрипторы процессов (pidfds) в полноценные объекты файловой системы. Это исключает риск «переиспользования PID» (когда сигнал отправляется не тому процессу, который занял освободившийся ID) и позволяет извлекать метаданные (UID, namespaces) атомарно через `ioctl`.

#### Масштабируемость Network Namespaces (Kernel 6.13+)
Исторически сетевой стек Linux был ограничен глобальной блокировкой `RTNL` (Routing Netlink). В новых ядрах блокировка стала локальной для каждого сетевого пространства имен, что позволяет создавать и удалять тысячи интерфейсов в секунду в плотных контейнерных средах без взаимного влияния.

#### Системный вызов listns(2) (Kernel 6.19+)
Заменяет медленное сканирование `/proc`. Позволяет получить список всех активных пространств имен, включая те, что не привязаны к процессам, а удерживаются открытыми файловыми дескрипторами (например, через `bind mount`).

### Системные вызовы API

| Вызов | Назначение | Технические детали |
| :--- | :--- | :--- |
| **`clone()`** | Создание процесса. | Флаги `CLONE_NEW*` определяют, какие ресурсы будут изолированы в новом процессе. |
| **`unshare()`** | Изоляция текущего процесса. | Позволяет процессу «отключиться» от общих ресурсов без создания нового процесса (fork). |
| **`setns()`** | Вход в namespace. | Присоединяет вызывающий поток к существующему пространству имен по дескриптору файла в `/proc/[pid]/ns/`. |

## Практические сценарии

### 1. Создание изолированной оболочки (unshare)

Команда `unshare` — основной инструмент для экспериментов с изоляцией.

```bash
# Запуск изолированной среды:
# -m (mnt), -u (uts), -i (ipc), -n (net), -p (pid), -f (fork), -U (user)
# --map-root-user: текущий пользователь становится root внутри
sudo unshare -muinpU --fork --map-root-user bash

# Внутри оболочки:
hostname container-x # Хост-система не изменится
ip link              # Виден только интерфейс lo (нужно поднять: ip link set lo up)
ps -ef               # Список процессов пуст (нужно перемонировать /proc)
```

### 2. Вход в пространство имен (nsenter)

Используется для отладки контейнеров, когда стандартные средства (например, `docker exec`) недоступны или ограничены.

```bash
# 1. Найти PID процесса в контейнере
PID=$(docker inspect <id> --format '{{.State.Pid}}')

# 2. Войти в сетевой стек и mount-пространство контейнера
sudo nsenter -t $PID -n -m bash

# 3. Проверить сетевые маршруты глазами контейнера
ip route show
```

### 3. Инспекция namespaces процесса

Каждый процесс хранит ссылки на свои namespaces в директории `/proc`.

```bash
# Список ссылок для текущего процесса
ls -l /proc/self/ns/

# Вывод: net:[4026531905], pid:[4026531836] и т.д.
# Одинаковый ID в квадратных скобках означает, что процессы разделяют один и тот же namespace.
```

### 4. Утилита lsns

Позволяет быстро увидеть дерево изоляции в системе.

```bash
# Список всех активных namespaces и количество процессов в них
lsns

# Фильтрация по типу
lsns -t net
```

### Поиск и устранение неисправностей

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **Operation not permitted** | Недостаточно прав для создания namespace. | Используйте `sudo` или User Namespaces (`unshare -U`), если они разрешены в системе. |
| **Процессы не видны через ps** | Не пересмонтирован `/proc`. | В новом PID namespace нужно заново смонтировать `/proc`: `mount -t proc proc /proc`. |
| **Не удается войти в namespace** | Процесс завершился. | Проверьте существование PID через `kill -0 <PID>`. |
| **Сетвые коллизии в netns** | Переменные ядра (sysctl) не изолированы. | Некоторые `sysctl` в Linux глобальны (например, параметры TCP-стека), другие изолированы на уровне netns. |
| **Namespace висит после удаления** | На него есть ссылка (bind mount). | Проверьте `mount | grep ns/`. Файлы в `/run/netns/` удерживают сетевые пространства имен активными. |
