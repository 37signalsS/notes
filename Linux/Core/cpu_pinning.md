# Привязка к процессору (CPU Pinning)

## Определения

**CPU Pinning** (привязка к процессорным ядрам, CPU affinity) — механизм жесткого назначения процесса или потока для выполнения на определённом физическом ядре (или наборе ядер) CPU. Это предотвращает автоматическую миграцию задачи планировщиком ОС между ядрами.

**Ключевые цели:**
- **Локальность кэша:** Исключение промахов кэша (L1/L2/L3) и минимизация инвалидации строк кэша при «переезде» процесса между ядрами.
- **Минимизация джиттера (Jitter):** Устранение накладных расходов на переключение контекста и балансировку нагрузки планировщиком.
- **Изоляция ресурсов:** Защита критических задач от влияния «шумных соседей» (Noisy Neighbors).
- **NUMA-оптимизация:** Привязка процесса к ядрам, имеющим прямой (наибыстрый) доступ к конкретным регионам оперативной памяти.

## Основные концепции

### Механизмы привязки в Linux

| Механизм | Уровень | Описание | Основные инструменты |
| :--- | :--- | :--- | :--- |
| **CPU Affinity** | User-space | Маска разрешенных ядер для конкретного PID. | `taskset`, `sched_setaffinity()` |
| **cpuset (Cgroups v2)** | Kernel | Иерархическое ограничение ядер и NUMA-узлов. | `cgroups`, `systemd`, `docker` |
| **Exclusive Partitions** | Kernel | Резервирование ядер (ядра удаляются из общего планировщика). | `cpuset.cpus.exclusive` |
| **isolcpus** | Boot-time | Параметр ядра для удаления ядер из общего планировщика. | `/etc/default/grub` |
| **IRQ Affinity** | Kernel | Привязка обработки прерываний к конкретным ядрам. | `/proc/irq/*/smp_affinity` |

### Сравнение cpuset и taskset

| Характеристика | `cpuset` (Cgroups) | `taskset` (CPU Affinity) |
| :--- | :--- | :--- |
| **Уровень реализации** | Ядро (контроллер cgroups) | Системный вызов (`sched_setaffinity`) |
| **Изоляция памяти NUMA** | **Да** (через `cpuset.mems`) | Нет |
| **Управление группами** | Да (через иерархию групп) | Нет (только индивидуальные PID) |
| **Наследование** | Автоматическое для всех потомков | Требует явного применения к каждому потоку |
| **Интеграция** | Нативно в Docker, K8s, Systemd | Внешние скрипты / ручной запуск |

### Топология и SMT (Hyper-Threading)

При пиннинге критично учитывать топологию процессора. Ошибочная привязка двух высоконагруженных потоков к разным логическим ядрам одного физического ядра (**siblings**) приведет к конкуренции за общие исполнительные блоки (ALU, FPU) и кэш L1/L2.

**Проверка соответствия ядер:**
```bash
# Показать пары логических ядер (siblings), разделяющих одно физическое ядро
cat /sys/devices/system/cpu/cpu*/topology/thread_siblings_list
```
**Пример:** Если `cpu0` и `cpu8` являются сиблингами, для достижения максимальной производительности одного потока ядро `cpu8` должно оставаться свободным.

## Программные интерфейсы и инструменты

### 1. taskset — базовое управление
Утилита для быстрой установки или получения маски соответствия CPU.

```bash
# Запустить процесс на ядре 2
taskset -c 2 ./my_app

# Изменить привязку работающего процесса (PID 1234) на ядра 0 и 3
taskset -pc 0,3 1234

# Использование шестнадцатеричной маски (0x3 = бинарное 0011 = ядра 0 и 1)
taskset 0x3 ./my_app

# Показать текущую привязку процесса
taskset -p 1234
```

### 2. numactl — привязка с учетом топологии
Критически важен для систем с несколькими сокетами или чиплетной архитектурой (например, AMD EPYC, Intel Xeon).

```bash
# Запустить на ядрах 0-3 с использованием локальной памяти только NUMA-узла 0
numactl --cpunodebind=0 --membind=0 ./my_app

# Привязка к конкретным физическим ядрам
numactl --physcpubind=0,1,2,3 --membind=0 ./my_app

# Просмотр топологии системы и «расстояния» между узлами
numactl --hardware
```

### 3. cpuset (Cgroups v2) — изоляция ресурсов
Современный метод (ядра 4.5+). Позволяет создавать изолированные «партиции» ядер.

```bash
# Создание группы
sudo mkdir /sys/fs/cgroup/isolated_tasks

# Разрешить ядра 4-7
echo "4-7" | sudo tee /sys/fs/cgroup/isolated_tasks/cpuset.cpus

# Сделать ядра эксклюзивными (Kernel 6.x+)
# Эти ядра перестанут использоваться общим планировщиком для других задач
echo "isolated" | sudo tee /sys/fs/cgroup/isolated_tasks/cpuset.cpus.partition

# Перемещение процесса в группу
echo 1234 | sudo tee /sys/fs/cgroup/isolated_tasks/cgroup.procs
```

### 4. Программный интерфейс (C API)
Прямое управление из кода приложения через системные вызовы.

```c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>

void pin_to_core(int core_id) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core_id, &cpuset);

    // Установка привязки для текущего потока (pid=0)
    if (sched_setaffinity(0, sizeof(cpu_set_t), &cpuset) == -1) {
        perror("sched_setaffinity");
    }
}
```

## Современные механизмы (2024–2026)

### Планировщик EEVDF (Kernel 6.6+)
Заменил классический CFS. Благодаря механизму «виртуальных дедлайнов», EEVDF значительно точнее соблюдает задержки (latency) для интерактивных задач. Пиннинг в современных ядрах всё чаще используется не для «борьбы» с планировщиком, а для **гарантии кэш-локальности** и предсказуемости доступа к памяти.

### Sched_ext (Kernel 6.11+)
Фреймворк для загрузки планировщиков через eBPF. 
- Позволяет использовать специализированные планировщики (например, `scx_layered`), которые могут динамически менять стратегии пиннинга в зависимости от типа нагрузки.
- Оптимизирован для игровых и высоконагруженных интерактивных задач.

### Гибридные процессоры (Intel P/E-cores)
В современных ядрах (Linux 6.x+) планировщик учитывает разницу между производительными (P) и энергоэффективными (E) ядрами. 
**Критический нюанс:** Ошибочный пиннинг вычислительно-сложного потока на E-ядро может привести к деградации производительности в 2-4 раза. Всегда проверяйте типы ядер через `lscpu -e`.

## Практические сценарии

### 1. Высокопроизводительные базы данных (PostgreSQL)
Для СУБД важно изолировать фоновые процессы обслуживания от обработки транзакций.

```bash
# Привязка фоновых процессов PostgreSQL к выделенным ядрам (0-3)
taskset -pc 0-3 $(pgrep -f "postgres: writer|postgres: checkpointer")
```

### 2. Сетевые приложения и DPDK
В задачах пакетной обработки (Data Plane Development Kit) ядра должны быть полностью изолированы от прерываний ОС и тиков таймера.

**Настройка через GRUB:**
```bash
# Изолировать ядра 2-7, отключить тики планировщика (nohz_full) и RCU-коллбэки
GRUB_CMDLINE_LINUX_DEFAULT="... isolcpus=2-7 nohz_full=2-7 rcu_nocbs=2-7"
```

**Перенос прерываний сетевой карты:**
```bash
# Найти номер прерывания (IRQ) сетевой карты
grep eth0 /proc/interrupts
# Привязать IRQ к ядру 0 (маска 0001)
echo 1 > /proc/irq/[IRQ_NUMBER]/smp_affinity
```

### 3. Контейнеризация (Kubernetes)
Использование CPU Manager с политикой `static` для гарантированных ресурсов.

```yaml
# Pod манифест для гарантированного пиннинга (класс Guaranteed)
spec:
  containers:
  - name: heavy-app
    image: my-app:latest
    resources:
      limits:
        cpu: "4"    # Должно быть целым числом
        memory: "4Gi"
      requests:
        cpu: "4"    # Requests должны быть равны Limits
```
*Kubelet автоматически применит `cpuset` к контейнеру, физически изолируя его на конкретных ядрах.*

## Мониторинг и диагностика

| Команда | Назначение |
| :--- | :--- |
| `ps -eLo pid,psr,comm` | Столбец `PSR` показывает номер ядра, на котором выполняется поток. |
| `mpstat -P ALL 1` | Позволяет увидеть дисбаланс нагрузки по всем ядрам в реальном времени. |
| `lscpu -e` | Детальная топология: сокеты, узлы NUMA, кэши L1-L3 и типы ядер (P/E). |
| `perf sched latency` | Измерение задержек планировщика для конкретных ядер. |
| `htop` | Настройка `Columns` -> `PROCESSOR` позволяет визуально отслеживать миграцию. |

## Дополнительная информация

### Поиск и устранение неисправностей

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Пиннинг не применяется** | Иерархия cgroups (systemd/docker) имеет приоритет. | Проверьте `cpuset.cpus` в вышестоящих группах. |
| **Высокий Jitter на ядре** | Прерывания (IRQ) попадают на изолированное ядро. | Проверьте `/proc/interrupts`, настройте `irqbalance --banlist`. |
| **Снижение скорости I/O** | Пиннинг на другой NUMA-узел относительно HBA/NIC. | Используйте `numactl -H` и привязывайте к ядрам, «близким» к шине PCI. |
| **Конфликт SMT** | Потоки конкурируют за ресурсы одного физ. ядра. | Привязывайте к сиблингам (например, 0 и 8) либо отключайте SMT в BIOS. |
