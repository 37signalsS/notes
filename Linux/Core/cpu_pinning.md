# Привязка к процессору (CPU Pinning)

## Определения

**CPU Pinning** (привязка к процессорным ядрам, CPU affinity) — механизм жесткого назначения процесса или потока для выполнения на определённом физическом ядре (или наборе ядер) CPU. Это предотвращает автоматическую миграцию задачи планировщиком ОС между ядрами.

**Ключевые цели:**
- **Локальность кэша:** Исключение промахов кэша (L1/L2/L3) и «загрязнения» кэша другими процессами.
- **Минимизация джиттера (Jitter):** Устранение накладных расходов на переключение контекста и балансировку нагрузки планировщиком.
- **Изоляция ресурсов:** Защита критических задач от влияния «шумных соседей» (Noisy Neighbors) в многопользовательских средах.
- **NUMA-оптимизация:** Привязка процесса к ядрам, имеющим прямой (наибыстрый) доступ к конкретным регионам оперативной памяти.

## Основные концепции

### Механизмы привязки в Linux

| Механизм | Уровень | Описание | Основные инструменты |
| :--- | :--- | :--- | :--- |
| **CPU Affinity** | User-space | Маска разрешенных ядер для конкретного PID. | `taskset`, `sched_setaffinity()` |
| **cpuset (Cgroups v2)** | Kernel | Иерархическое ограничение ядер и NUMA-узлов. | `cgroups`, `systemd`, `docker` |
| **Exclusive Partitions** | Kernel | Резервирование ядер (ядра удаляются из общего планировщика). | `cpuset.cpus.exclusive` |
| **isolcpus** | Boot-time | Параметр ядра для удаления ядер из общего планировщика. | `/etc/default/grub` |
| **IRQ Affinity** | Kernel | Привязка обработки прерываний к конкретным ядрам. | `/proc/irq/*/smp_affinity` |

### Сравнение cpuset и taskset

| Характеристика | `cpuset` (Cgroups) | `taskset` (CPU Affinity) |
| :--- | :--- | :--- |
| **Уровень реализации** | Ядро (контроллер cgroups) | Системный вызов (`sched_setaffinity`) |
| **Изоляция памяти NUMA** | **Да** (через `cpuset.mems`) | Нет |
| **Управление группами** | Да (через иерархию групп) | Нет (только индивидуальные PID) |
| **Наследование** | Автоматическое для всех потомков | Требует явного применения к каждому потоку |
| **Интеграция** | Нативно в Docker, K8s, Systemd | Внешние скрипты / ручной запуск |

### Инструменты и программные интерфейсы

#### 1. taskset — базовое управление
Утилита для установки или получения маски соответствия CPU.

```bash
# Запустить процесс на ядре 2
taskset -c 2 ./my_app

# Изменить привязку работающего процесса (PID 1234) на ядра 0 и 3
taskset -pc 0,3 1234

# Использование шестнадцатеричной маски (0x3 = 0011 в двоичной системе = ядра 0 и 1)
taskset 0x3 ./my_app

# Показать текущую привязку процесса
taskset -p 1234
```

#### 2. numactl — привязка с учетом топологии
Критически важен для многопроцессорных систем и процессоров с несколькими NUMA-доменами (например, AMD EPYC, Intel Xeon).

```bash
# Запустить на ядрах 0-3 с использованием памяти только NUMA-узла 0
numactl --cpunodebind=0 --membind=0 ./my_app

# Привязка к конкретным физическим ядрам
numactl --physcpubind=0,1,2,3 --membind=0 ./my_app

# Просмотр топологии системы
numactl --hardware
```

#### 3. cpuset (Cgroups v2) — изоляция ресурсов
Современный метод (ядра 4.5+). Позволяет создавать изолированные «партиции» ядер.

```bash
# Создание группы
sudo mkdir /sys/fs/cgroup/isolated_tasks

# Разрешить ядра 4-7
echo "4-7" | sudo tee /sys/fs/cgroup/isolated_tasks/cpuset.cpus

# Сделать ядра эксклюзивными (Kernel 6.x+)
# Эти ядра перестанут использоваться общим планировщиком для других задач
echo "isolated" | sudo tee /sys/fs/cgroup/isolated_tasks/cpuset.cpus.partition

# Перемещение процесса в группу
echo 1234 | sudo tee /sys/fs/cgroup/isolated_tasks/cgroup.procs
```

#### 4. Программный интерфейс (C API)
Прямое управление из кода приложения для минимизации задержек.

```c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>

void pin_to_core(int core_id) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core_id, &cpuset);

    if (sched_setaffinity(0, sizeof(cpu_set_t), &cpuset) == -1) {
        perror("sched_setaffinity");
    }
}
```

### Современные механизмы (2024–2026)

#### Планировщик EEVDF (Kernel 6.6+)
Заменил CFS. Благодаря механизму «виртуальных дедлайнов», EEVDF значительно лучше обрабатывает latency-sensitive задачи. Пиннинг теперь чаще используется не для борьбы с планировщиком, а для **гарантии кэш-локальности**.

#### Sched_ext (Kernel 6.11+)
Фреймворк для загрузки планировщиков через eBPF. 
- Позволяет использовать специализированные планировщики (например, `scx_layered`), которые могут динамически менять стратегии пиннинга в зависимости от нагрузки.
- Оптимизирован для игровых и высоконагруженных интерактивных задач.

#### Гибридные процессоры (Intel P/E-cores)
В современных ядрах (7.0+) планировщик понимает разницу между производительными (P) и энергоэффективными (E) ядрами. 
**Важно:** Ошибочный пиннинг критического потока на E-ядро может привести к деградации производительности в 2-3 раза. Всегда проверяйте типы ядер через `lscpu -e`.

## Практические сценарии

### 1. Высокопроизводительные базы данных (PostgreSQL / MySQL)
Для СУБД важно изолировать процессы записи (Writer) и фоновой очистки (Vacuum) от клиентских запросов.

```bash
# Привязка PostgreSQL к первым 4 ядрам (0-3)
taskset -pc 0-3 $(pgrep -f "postgres: writer")
```

### 2. Сетевые приложения и DPDK
В задачах пакетной обработки (Data Plane Development Kit) ядра должны быть полностью изолированы от прерываний ядра и других задач.

**Настройка через GRUB:**
```bash
# Изолировать ядра 2-7, отключить тики планировщика (nohz_full)
# и перенести обратные вызовы RCU
GRUB_CMDLINE_LINUX_DEFAULT="... isolcpus=2-7 nohz_full=2-7 rcu_nocbs=2-7"
```

**Перенос прерываний сетевой карты:**
```bash
# Найти IRQ сетевой карты
grep eth0 /proc/interrupts
# Привязать IRQ к ядру 0 (маска 0001)
echo 1 > /proc/irq/[IRQ_NUMBER]/smp_affinity
```

### 3. Контейнеризация (Kubernetes)
Использование CPU Manager с политикой `static`.

```yaml
# Pod манифест для гарантированного пиннинга
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        cpu: "2"    # Целое число ядер
        memory: "200Mi"
      requests:
        cpu: "2"    # Должно быть равно limits
```
*Примечание: Kubelet автоматически применит `cpuset` к контейнеру.*

### 4. Оптимизация через Tuned
Профиль `cpu-partitioning` является стандартом для RHEL/CentOS/Ubuntu в High-Performance сценариях.

```bash
sudo tuned-adm profile cpu-partitioning
# Конфигурация изолируемых ядер: /etc/tuned/cpu-partitioning-variables.conf
```

### Инструменты мониторинга и диагностики
- **`ps -eLo pid,psr,comm`**: PSR показывает номер ядра, на котором в данный момент выполняется поток.
- **`mpstat -P ALL 1`**: Позволяет увидеть дисбаланс нагрузки по ядрам.
- **`perf sched latency`**: Измерение задержек планировщика для конкретных ядер.
- **`htop`**: Нажмите `f2` -> `Columns` -> добавьте `PROCESSOR` для визуального контроля.

### Поиск и устранение неисправностей

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Пиннинг не работает** | Иерархия cgroups переопределяет taskset. | Проверьте `cpuset.cpus` в родительских cgroups. |
| **Высокий Jitter на ядре** | Прерывания (IRQ) попадают на изолированное ядро. | Проверьте `/proc/interrupts`, настройте `irqbalance --banlist`. |
| **Снижение производительности** | Пиннинг на разные NUMA-узлы. | Проверьте `numactl -H`, используйте ядра одного узла. |
| **Hyper-Threading конфликт** | Процессы привязаны к разным логическим ядрам одного физического ядра. | Привязывайте процессы к парам (например, 0 и 8), либо отключайте SMT. |

### Предостережения
- **Никогда не изолируйте все ядра:** Системе необходимо минимум 1-2 «housekeeping» ядра для работы ОС, Kubelet, SSH и прерываний.
- **Двухсторонний эффект:** Неправильный пиннинг может замедлить систему больше, чем его отсутствие, из-за конфликтов за кэш и шину памяти.
