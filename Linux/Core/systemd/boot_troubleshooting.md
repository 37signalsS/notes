# Диагностика загрузки и проблем запуска сервисов

## Определения

* **Контекст загрузки (Boot Context)** — специфическая среда выполнения, в которой `systemd` активирует юниты во время старта системы. Отличается от интерактивной сессии ограниченным окружением (`PATH`), отсутствием пользовательских переменных и поэтапной готовностью ресурсов (сеть, файловые системы).
* **Rescue Mode (Режим спасения)** — состояние системы (`rescue.target`), предназначенное для ремонта, когда базовая конфигурация исправна, но требуется ручное вмешательство. Монтирует все локальные файловые системы, но запускает минимум сервисов.
* **Emergency Mode (Аварийный режим)** — минимальное состояние (`emergency.target`), используемое при критических сбоях (например, невозможность смонтировать корень или ошибки в `fstab`). Монтирует только корневой раздел в режиме read-only.

## Основные концепции

### Отличия режимов восстановления

| Характеристика | Rescue Mode | Emergency Mode |
| :--- | :--- | :--- |
| **Цель в systemd** | `rescue.target` | `emergency.target` |
| **Файловые системы** | Монтирует всё из `/etc/fstab` | Только корень (`/`) |
| **Уровень изоляции** | Выше (запущены udev, сокеты) | Минимальный (только PID 1 и shell) |
| **Когда использовать** | Сброс пароля, ремонт сервисов | Ошибки монтирования, повреждение ФС |

### Причины сбоев при автозапуске

Если сервис успешно запускается вручную через `systemctl start`, но падает при загрузке, причина обычно в одном из факторов:
1. **Гонка зависимостей:** Сервис требует ресурс (БД, сеть, диск), который еще не готов.
2. **Пути и окружение:** Использование относительных путей или переменных, доступных только в shell администратора.
3. **Права доступа:** Различия в контекстах безопасности (SELinux/AppArmor) или запуск от имени другого пользователя.

## Практические сценарии

### 1. Отладка через параметры ядра (GRUB)

Если система не загружается, можно изменить параметры запуска в меню загрузчика:

* **`systemd.debug_shell`** — запускает root-оболочку на **TTY9** (`Ctrl+Alt+F9`). Позволяет выполнять команды `systemctl` прямо в процессе «зависшей» загрузки.
* **`systemd.confirm_spawn=yes`** — интерактивный режим. Система будет запрашивать подтверждение (y/n) перед запуском каждого сервиса.
* **`systemd.log_level=debug`** — максимально подробный вывод действий `systemd` на консоль.
* **`systemd.unit=emergency.target`** — принудительная загрузка в аварийный режим.

### 2. Анализ журналов загрузки

```bash
# Показать логи только текущей (последней) загрузки
journalctl -b

# Вывести только ошибки и критические сообщения текущей сессии
journalctl -p err -b

# Поиск сообщений о циклических зависимостях
journalctl -b | grep "ordering cycle"
# → Found ordering cycle on ...
```

### 3. Поиск узких мест (Тайминги)

```bash
# Список юнитов, замедляющих загрузку
systemd-analyze blame
# → 7.345s network-manager.service
# → 2.120s dev-sda2.device

# Анализ критической цепи для конкретного сервиса
systemd-analyze critical-chain nginx.service
```

### 4. Исправление ошибок монтирования (Emergency Mode)

Если система застряла в Emergency Mode из-за ошибок в `/etc/fstab`:
1. Перемонтировать корень в режим записи: `mount -o remount,rw /`.
2. Найти ошибку в логах: `journalctl -xb`.
3. Отредактировать `/etc/fstab`.
4. Перезагрузиться: `systemctl reboot`.

### 5. Превентивная проверка юнитов

Перед тем как отправить сервис в продакшн, проверьте его на логические ошибки:

```bash
# Проверка синтаксиса и зависимостей без запуска
systemd-analyze verify /etc/systemd/system/myapp.service
```
