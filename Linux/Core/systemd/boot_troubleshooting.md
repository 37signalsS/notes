# Диагностика загрузки и проблем запуска сервисов

## Определения

* **Контекст загрузки (Boot Context)** — специфическая среда выполнения, в которой `systemd` активирует юниты (units) во время старта ОС (Операционная Система). В этом режиме отсутствуют интерактивные оболочки, переменная окружения `${PATH}` ограничена, а многие сетевые и файловые ресурсы могут быть ещё не готовы.
* **Режим восстановления (Emergency Mode)** — состояние системы, при котором загрузка прерывается из-за критической ошибки (например, невозможности смонтировать диск), и администратору предоставляется консоль для ручного исправления ситуации.

## Основные концепции

### Разница между ручным и автоматическим запуском

Часто возникает ситуация: команда `systemctl start app` успешно запускает сервис в работающей системе, но после перезагрузки этот же сервис оказывается в статусе `failed`.

Основные причины различий:

1. **Зависимости**: при ручном старте сеть и диски уже готовы. При загрузке сервис может пытаться стартовать раньше них.
2. **Окружение**: в сессии пользователя доступны переменные окружения и пути, которых нет у системного демона.
3. **Права доступа**: при ручном запуске через `sudo` могут использоваться иные контексты безопасности.

## Практические сценарии

### 1. Анализ журналов текущей загрузки

Использование флага `-b` позволяет отсечь лишнюю информацию из прошлых сессий.

```bash
# Показать логи сервиса только с момента последнего включения системы
journalctl -u nginx.service -b
# → Jun 07 10:00:01 host systemd[1]: Starting A high performance web server...

# Показать только критические ошибки загрузки всей системы
journalctl -p err -b
# → -- Logs begin at Sun 2026-06-07 09:55:00 MSK. --
# → Jun 07 09:55:10 host systemd[1]: Failed to mount /data.
```

### 2. Поиск узких мест в цепочке запуска

Если система загружается слишком долго, необходимо найти сервис-виновник.

```bash
# Список юнитов, отсортированный по времени активации
systemd-analyze blame
# → 7.345s network-manager.service
# → 1.200s ssh.service

# Визуализация критической цепочки для конкретного сервиса
systemd-analyze critical-chain nginx.service
# → nginx.service @10.500s +1.685s
```

### 3. Решение проблем с путями (ExecStart)

В юнит-файлах всегда должны использоваться абсолютные пути к исполняемым файлам.

```ini
# ОШИБКА: systemd не найдет файл в ограниченном PATH
ExecStart=my_script.sh

# ПРАВИЛЬНО: полный путь гарантирует запуск
ExecStart=/usr/local/bin/my_script.sh
```

### 4. Чек-лист быстрой диагностики

| Проблема | Инструмент проверки | Метод решения |
| :--- | :--- | :--- |
| **Юнит не включен** | `systemctl is-enabled` | Выполнить `systemctl enable`. |
| **Циклическая зависимость** | `journalctl -b` | Найти сообщение "Found ordering cycle" и удалить лишний `After/Before`. |
| **Диск не готов** | `mount -a` | Использовать `RequiresMountsFor=` в юнит-файле. |
| **Таймаут старта** | `systemctl status` | Увеличить значение `TimeoutStartSec=` в секции `[Service]`. |

## Дополнительная информация

### Выход из режима восстановления (Emergency Mode)

Если система загрузилась в консоль восстановления:

1. Выполнить `journalctl -xb`, чтобы найти причину сбоя (обычно это ошибки в `/etc/fstab`).
2. Исправить конфигурацию.
3. Выполнить `systemctl reboot` или `systemctl default`.
