# Диагностика проблем с запуском сервисов при загрузке

## Определения

*   **Контекст запуска (Boot Context):** Среда, в которой `systemd` запускает службы во время загрузки системы. Характеризуется отсутствием интерактивной сессии, ограниченным `$PATH` и неполной готовностью системных ресурсов (сеть, диски).
*   **Ручной запуск (Manual Start):** Запуск службы командой `systemctl start` в уже загруженной и полностью функционирующей системе, в контексте сессии пользователя.

## Основные концепции

Классическая проблема: `systemctl start myservice` работает, но после перезагрузки сервис не запущен. Почти всегда причина кроется не в самом исполняемом файле, а в порядке запуска, окружении или зависимостях, которые на момент старта сервиса еще не готовы.

При ручном запуске сервис стартует в "тёплой" системе, где все необходимые ресурсы (сеть, файловые системы, другие службы) уже доступны. При загрузке `systemd` запускает сервис в ином, "холодном" контексте, что и приводит к различиям в поведении.

## Практические сценарии диагностики

### 1. Проверка статуса и логов

Первый шаг — убедиться, что сервис включен для автозапуска, и проверить его статус и логи.

*   **Проверить, включен ли сервис:**
    ```bash
    systemctl is-enabled myservice.service
    ```
*   **Включить автозапуск, если выключен:**
    ```bash
    sudo systemctl enable myservice.service
    ```
*   **Проверить статус сервиса:**
    ```bash
    systemctl status myservice.service
    ```
*   **Просмотреть логи сервиса с начала текущей загрузки:**
    ```bash
    journalctl -u myservice.service -b
    ```
    Ключ `-b` (boot) критически важен, так как он отфильтровывает логи, относящиеся только к текущей сессии загрузки, игнорируя предыдущие ручные запуски. Более подробно о работе с логами `systemd` см. в [Journald: Централизованный сбор логов](../Logging/journald.md).

### 2. Анализ зависимостей

Частая причина — неверно указанные зависимости. Сервис пытается стартовать до того, как поднимется сеть, примонтируются диски или запустятся другие необходимые службы. Подробное описание зависимостей `systemd` можно найти в [Юниты, таргеты и зависимости systemd](./units_and_dependencies.md).

*   **Просмотр зависимостей:**
    ```bash
    systemctl show myservice.service | grep -E 'After=|Wants=|Requires='
    ```
    Для просмотра дерева зависимостей можно использовать `systemctl list-dependencies myservice.service`. Подробнее об этом и других командах `systemctl` см. в [Управление службами Systemd (systemctl)](./service_management.md).

*   **Зависимость от сети:**
    Если сервису нужна сеть, простой директивы `After=network.target` часто недостаточно, так как она лишь указывает на запуск *после* юнита `network.target`, но не гарантирует, что сеть действительно доступна. Правильнее использовать `network-online.target`:
    ```ini
    [Unit]
    Description=My Awesome Service
    After=network-online.target
    Wants=network-online.target
    ```
*   **Зависимость от монтирования:**
    Если сервис зависит от определенной точки монтирования, используйте `RequiresMountsFor=`:
    ```ini
    [Unit]
    Description=My Service That Needs a Specific Mount
    RequiresMountsFor=/mnt/data
    ```
    Это гарантирует, что `systemd` запустит сервис только после того, как указанный путь станет активной точкой монтирования.

### 3. Проверка путей и окружения

Контекст запуска при загрузке имеет минимальное окружение, в частности, урезанную переменную `PATH`. Это может привести к тому, что команды, указанные с относительными путями, не будут найдены.

*   **Проверить переменные окружения:**
    ```bash
    systemctl show myservice.service | grep Environment
    ```
*   **Решение:** Всегда используйте абсолютные пути к исполняемым файлам и скриптам в директиве `ExecStart`.

    **Неправильно:**
    ```ini
    ExecStart=my_app --config /etc/my_app.conf
    ```
    **Правильно:**
    ```ini
    ExecStart=/usr/local/bin/my_app --config /etc/my_app.conf
    ```

### 4. Настройка автоматического перезапуска

Иногда сервис падает при старте из-за кратковременных сбоев. `systemd` может быть настроен так, чтобы автоматически перезапускать его.

*   **Проверить настройки перезапуска:**
    ```bash
    systemctl show myservice.service | grep Restart
    ```
*   **Добавить политику перезапуска:**
    В секцию `[Service]` юнит-файла можно добавить директивы для автоматического перезапуска:
    ```ini
    [Service]
    Restart=on-failure
    RestartSec=5
    ```
    - `Restart=on-failure`: Перезапускать сервис, если он завершился с ненулевым кодом выхода.
    - `RestartSec=5`: Установить 5-секундную задержку перед попыткой перезапуска.

После внесения изменений в юнит-файл необходимо перезагрузить конфигурацию `systemd`:
```bash
sudo systemctl daemon-reload
```
