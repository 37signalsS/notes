# Systemd: Управление системой и службами

## Определения

* **`systemd`**: Современный менеджер системы и служб для Linux, стандарт для большинства дистрибутивов. Отвечает за инициализацию системы после загрузки ядра и управление службами, сокетами, точками монтирования и другими системными ресурсами.
* **`SystemV (SysVinit)`**: Классическая система инициализации в Unix-подобных системах, предшественник `systemd`.
* **`Upstart`**: Система инициализации, разработанная Canonical (для Ubuntu), предшественник `systemd` в некоторых дистрибутивах. Использовала event-driven подход.
* **`cloud-init`**: Стандартный инструмент для кроссплатформенной инициализации облачных экземпляров (виртуальных машин) при первом запуске. Позволяет автоматически выполнять скрипты, настраивать сеть, создавать пользователей, устанавливать пакеты и применять конфигурации, используя данные, предоставляемые облачной платформой.
* **Уровни выполнения (Runlevels)**: Концепция `SysVinit`, определяющая состояние системы и набор запущенных служб.
  * **0 (`runlevel0.target`)**: Выключение системы.
  * **1 (`runlevel1.target`, `rescue.target`)**: Однопользовательский режим для восстановления. Запускается минимальный набор служб, доступен только `root`.
  * **2 (`runlevel2.target`)**: Многопользовательский режим без поддержки сети (в некоторых дистрибутивах, например, Debian, это стандартный многопользовательский режим с сетью).
  * **3 (`runlevel3.target`, `multi-user.target`)**: Стандартный многопользовательский режим с поддержкой сети (текстовая консоль).
  * **4 (`runlevel4.target`)**: Не используется, зарезервирован для пользовательских нужд.
  * **5 (`runlevel5.target`, `graphical.target`)**: Многопользовательский режим с графическим интерфейсом (GUI).
  * **6 (`runlevel6.target`, `reboot.target`)**: Перезагрузка системы.

* **Таргеты (Targets)**: Концепция `systemd`, представляющая точку синхронизации, объединяющую группу юнитов (служб, сокетов и т.д.). Являются заменой уровней выполнения `SysVinit`.
* **Архитектура `systemd`**:
  * **`systemd` (PID 1)**: Главный демон, запускается ядром и управляет всеми процессами.
  * **`systemctl`**: Основной инструмент командной строки для взаимодействия с `systemd` через **D-Bus**.
  * **`journald`**: Демон для сбора и хранения логов в бинарном формате. См. [Journald: Централизованный сбор логов](../../SystemAdministration/Logging/journald.md).
  * **`udev`**: Управляет файлами устройств в `/dev` и событиями оборудования. Подробнее см. в [Udev: подсистема динамического управления устройствами](../udev.md).
  * **`networkd`, `timedated`, `logind`**: Специализированные демоны для управления сетью, временем и пользовательскими сессиями.

## Основные концепции

### SystemD vs SystemV (SysVinit)

`systemd` заменил `SysVinit`, используя **таргеты** вместо уровней выполнения. `systemd` обеспечивает обратную совместимость, сопоставляя старые уровни выполнения с новыми таргетами.

### Ключевые преимущества Systemd

* **Параллельный запуск служб**: Ускоряет загрузку системы за счет анализа зависимостей и параллельного запуска.
* **Декларативные unit-файлы**: Использование `.ini`-подобных файлов для описания служб вместо shell-скриптов.
* **Интегрированное управление логами**: `journald` централизованно собирает логи, упрощая отладку.
* **Автоматический перезапуск служб**: Встроенная возможность перезапуска "упавших" сервисов.
* **Простота конфигурации**: Единый синтаксис для управления системными ресурсами.
* **Богатый функционал**: Комплексный набор инструментов для управления системой (сессии, сеть, время).

### Управление ресурсами и изоляция: Control Groups (cgroups)

`systemd` активно использует [cgroups](../cgroups.md#использование-cgroups-в-systemd) для надежного управления процессами, их завершения и установки лимитов на ресурсы (CPU, память, I/O).

## Практические сценарии

### Как определить, что systemd используется в системе?

1. **Проверка процесса с PID 1**:

    ```bash
    stat /proc/1/exe
    ```

    Вывод `File: /proc/1/exe -> /lib/systemd/systemd` указывает на управление `systemd`.

2. **Проверка файла `/sbin/init`**:

    ```bash
    ls -l /sbin/init
    ```

    `/sbin/init` должен быть символической ссылкой на `systemd` (например, `'/sbin/init' -> '../lib/systemd/systemd'`).

3. **Наличие каталога `/run/systemd/system`**:

    ```bash
    ls /run/systemd/system
    ```

    Наличие данного каталога является надежным признаком активности `systemd`.

### Визуализация иерархии процессов (systemd-cgls)

`systemd-cgls` (control groups list) — это утилита, которая рекурсивно отображает иерархию контрольных групп (`cgroups`), предоставляя точное представление о том, как `systemd` управляет процессами.

На сервере с несколькими службами и контейнерами (например, Docker) команда покажет:
* **Службы**: Какие процессы принадлежат каждой службе (`sshd.service`, `nginx.service`).
* **Контейнеры**: Как процессы, запущенные внутри контейнеров, сгруппированы и изолированы на хост-системе.

Это мощный инструмент для диагностики и анализа структуры запущенных сервисов, который показывает иерархию управления ресурсами, в отличие от [`ps`](../../Diagnostics/Processes/ps.md), который показывает только иерархию родитель-потомок.

### Мониторинг ресурсов Control Groups (systemd-cgtop)

`systemd-cgtop` — это интерактивный инструмент для мониторинга использования CPU, памяти и I/O группами контроля (cgroups). В отличие от [`top`](../../Diagnostics/Processes/top.md), который фокусируется на отдельных процессах, `systemd-cgtop` агрегирует данные по cgroups, что позволяет быстро определить, какой сервис или группа сервисов потребляет больше всего ресурсов.

Подробности использования: [systemd-cgtop: Мониторинг ресурсов Control Groups](./cgtop.md)

**Пример вывода:**

```
-.slice
├─system.slice
│ ├─nginx.service
│ │ ├─1184 nginx: master process /usr/sbin/nginx ...
│ │ └─1185 nginx: worker process
│ ├─docker.service
│ │ └─...
│ └─sshd.service
│   └─1024 /usr/sbin/sshd -D
└─user.slice
  └─user-1000.slice
```
### Практические сценарии: Использование cloud-init

`cloud-init` — это стандартный инструмент для первоначальной настройки облачных серверов (виртуальных машин) при их запуске. Он позволяет автоматизировать множество задач по настройке системы, используя метаданные и пользовательские данные, предоставляемые облачной платформой.

**Основные возможности `cloud-init`:**

*   **Настройка сети**: Конфигурация сетевых интерфейсов, DNS-серверов.
*   **Установка пакетов**: Автоматическая установка необходимого программного обеспечения.
*   **Создание пользователей и управление SSH-ключами**: Добавление новых пользователей, настройка их прав и импорт публичных SSH-ключей для безопасного доступа.
*   **Выполнение скриптов**: Запуск shell-скриптов или скриптов на Python для выполнения произвольных задач настройки.
*   **Конфигурация hostname**: Установка имени хоста сервера.
*   **Форматирование и монтирование дисков**: Автоматическая подготовка дополнительных дисков.

**Как работает `cloud-init`:**

1.  **Запуск**: `cloud-init` запускается на ранней стадии загрузки системы, до того как большинство системных служб будут активны.
2.  **Получение данных**: Он обращается к API облачной платформы (например, OpenStack metadata service, AWS EC2 metadata service) для получения метаданных экземпляра и пользовательских данных (user-data).
3.  **Обработка**: `cloud-init` обрабатывает эти данные, выполняя серии модулей (network, users-groups, package-update, runcmd и т.д.), которые реализуют запрошенную конфигурацию.

**Пример `user-data` для `cloud-init` (YAML-формат):**

```yaml
#cloud-config
users:
  - name: newuser
    sudo: ALL=(ALL) NOPASSWD:ALL
    ssh_authorized_keys:
      - ssh-rsa AAAAB3NzaC...your_public_key...
packages:
  - nginx
runcmd:
  - systemctl enable nginx
  - systemctl start nginx
write_files:
  - path: /etc/motd
    permissions: '0644'
    content: |
      Welcome to my cloud server!
      Configured by cloud-init.
```
