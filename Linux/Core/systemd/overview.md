# systemd: Обзор системы и менеджера служб

## Определения

* **`systemd`** — современный менеджер системы и служб для Linux, ставший промышленным стандартом. Он отвечает за инициализацию системы после загрузки ядра и управление жизненным циклом ресурсов через **юниты** (службы, сокеты, точки монтирования).
* **Менеджер процессов (PID 1)** — первый процесс, запускаемый ядром. Выступает в роли «родителя всех процессов», обеспечивая параллелизацию, контроль зависимостей и восстановление служб после сбоев.
* **Транзакционный движок (Transaction Engine)** — внутренний механизм `systemd`, который строит граф зависимостей при получении запроса (например, старт сервиса) и гарантирует атомарность изменений состояния. Если зависимость не может быть удовлетворена, вся транзакция отклоняется.
* **Таргеты (Targets)** — юниты-группировщики, представляющие целевое состояние системы (например, `multi-user.target`). Заменяют устаревшие уровни выполнения (runlevels).
* **Шины сообщений (D-Bus и Varlink)** — механизмы межпроцессного взаимодействия, через которые внешние утилиты (`systemctl`, `hostnamectl`) общаются с основным демоном.
* **Делегирование cgroup (Cgroup Delegation)** — передача управления подгруппами контрольных групп пользовательским сессиям и сервисам. Без делегирования `systemd` не может эффективно изолировать ресурсы для отдельных юнитов.
* **Slice (Слайс)** — иерархическая группа юнитов для совместного управления ресурсами (CPU, память, I/O) через контрольные группы.

### Архитектурные компоненты

`systemd` — это не только PID 1, но и обширная экосистема вспомогательных демонов:
* **`journald`** — сбор и хранение логов в индексированном бинарном формате с поддержкой метаданных.
* **`logind`** — управление сессиями пользователей, рабочими местами (seats) и питанием.
* **`resolved`** — сетевое разрешение имен с поддержкой DNS-over-TLS, DNSSEC и LLMNR.
* **`networkd`** — сетевая конфигурация на основе декларативных файлов.
* **`udev`** — менеджер устройств, отвечающий за динамическое создание узлов в `/dev`.
* **`systemd-boot`** — простой и эффективный загрузчик UEFI (бывший Gummiboot).

### Новые компоненты (v250+)

* **`run0`** — современная замена `sudo`, работающая через API менеджера служб без использования SUID-битов (минимизация векторов атак).
* **`systemd-oomd`** — демон мониторинга нехватки памяти (OOM), оперирующий данными PSI (Pressure Stall Information) для предотвращения «зависания» системы.
* **`systemd-repart`** — декларативное перераспределение разделов диска при первой загрузке или обновлении образа.

## Основные концепции

### Эволюция инициализации

`systemd` заменяет последовательный запуск громоздких shell-скриптов на параллельную активацию юнитов. Это достигается за счет **Socket-based activation**: менеджер создает сокет сразу, а соответствующую службу запускает только при поступлении первого запроса. Такой подход устраняет «холодный старт» и снижает время отклика для редких сервисов.

### Архитектура PID 1

Первый процесс `systemd` выполняет три критически важные функции:
1. **Управление процессами** — перехватывает сигналы, очищает «зомби-процессы», перезапускает упавшие службы в соответствии с политикой `Restart=`.
2. **Управление cgroups** — создает иерархию контрольных групп, делегирует их подсистемам и обеспечивает привязку процессов к юнитам.
3. **Управление состоянием** — поддерживает граф зависимостей, преобразует запросы в очередь заданий (jobs) и координирует параллельный запуск.

### Механизм транзакций и очереди заданий

При любой операции (`start`, `stop`, `reload`) `systemd` не выполняет действие немедленно. Вместо этого:
1. Строит граф зависимостей для целевого юнита.
2. Вычисляет минимальный набор юнитов, которые нужно запустить/остановить.
3. Помещает задания в очередь, где они могут выполняться параллельно, если нет блокирующих связей (`After=`/`Before=`).
4. Гарантирует атомарность: если любая зависимость не может быть удовлетворена, вся транзакция откатывается.

### Ключевые механизмы

* **Декларативность** — конфигурация описывается в `.ini`-подобных файлах, что исключает ошибки логики в скриптах.
* **Очередь заданий (Jobs)** — `systemd` преобразует граф зависимостей в очередь заданий. Задания могут быть выполнены параллельно, если между ними нет прямых блокирующих связей.
* **Интеграция с cgroup v2** — иерархическое управление ресурсами (CPU, Memory, I/O) и жесткая привязка процессов к юнитам (предотвращение «осиротевших» процессов).
* **Soft-Reboot** — перезапуск всего пользовательского пространства без перезагрузки ядра Linux.
* **Image-Based Computing** — поддержка неизменяемых образов ОС через расширения системы (`sysext`) и конфигурации (`confext`).
* **Credentials** — безопасная передача секретов в юниты без их жесткого прописывания в конфигурационных файлах (v250+).
* **Dynamic Users** — `systemd` может создавать временных пользователей для сервисов, которые автоматически удаляются после остановки юнита.

## Практические сценарии

### Идентификация системы

```bash
# Проверка процесса PID 1
stat /proc/1/exe
# → File: /proc/1/exe -> /lib/systemd/systemd

# Проверка активного рантайма
ls -d /run/systemd/system
# → /run/systemd/system
```

### Диагностика процесса загрузки

```bash
# Общее время загрузки
systemd-analyze
# → Startup finished in 2.5s (kernel) + 10.2s (userspace) = 12.7s

# Анализ критической цепи для конкретного таргета
systemd-analyze critical-chain multi-user.target

# Проверка синтаксиса и безопасности всех юнитов
systemd-analyze verify
systemd-analyze security
```

### Диагностика упавших служб

```bash
# Список всех failed-юнитов
systemctl --failed

# Детальный статус конкретного сервиса
systemctl status --full nginx.service

# Поиск последних ошибок в journald
journalctl -u nginx.service -p err --since "1 hour ago"
```

### Поиск и анализ юнитов

```bash
# Список всех загруженных, но неактивных юнитов
systemctl list-units --all --state=inactive

# Поиск юнитов, тормозящих загрузку
systemd-analyze blame

# Дерево зависимостей таргета
systemctl list-dependencies multi-user.target

# Сравнение конфигурации с системной (поиск локальных изменений)
systemd-delta
```

### Управление состоянием служб

```bash
# Быстрый restart без daemon-reload (если unit-файл не менялся)
sudo systemctl restart nginx.service

# Перезагрузка конфигурации без остановки (для nginx, haproxy и т.д.)
sudo systemctl reload nginx.service

# Принудительная перезагрузка конфигурации systemd
sudo systemctl daemon-reload

# Включение автозапуска и немедленный старт
sudo systemctl enable --now sshd.service
```

### Мониторинг ресурсов

```bash
# Просмотр дерева контрольных групп
systemd-cgls

# Интерактивный мониторинг потребления ресурсов юнитами
systemd-cgtop
```

### Работа с журналами

```bash
# Просмотр логов сервиса в реальном времени
journalctl -u nginx.service -f

# Логи с текущей загрузки
journalctl -b

# Фильтр по приоритету (err, warning, info)
journalctl -u sshd.service -p err --since today
```

## Диагностика и устранение неисправностей

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Служба в состоянии `failed` | Ошибка в конфигурации или отсутствие зависимости. | `journalctl -u <service> -n 50` для просмотра последних логов; `systemd-analyze verify <unit>` для проверки синтаксиса. |
| Служба не стартует автоматически | Отключен автозапуск (`disabled`). | `systemctl enable --now <service>`. |
| Цепная зависимость (`ordering cycle`) | Противоречивые директивы `After=`/`Before=`. | `systemd-analyze critical-chain` для визуализации; пересмотрите порядок запуска. |
| Высокий `Exposure Level` (≥ 7.0) | Отсутствуют директивы sandboxing. | Добавьте `ProtectSystem=strict`, `PrivateDevices=yes`, `NoNewPrivileges=yes`. |
| Ресурсы не ограничиваются | Отключен accounting (`CPUAccounting=no`). | Включите `CPUAccounting=yes`, `MemoryAccounting=yes` в unit-файле и выполните `daemon-reload`. |
| Медленная загрузка | Длинная критическая цепь или sequential-запуск. | `systemd-analyze blame` + `systemd-analyze critical-chain`; используйте `Wants=` вместо `Requires=` где возможно. |
| Логи теряются | `ForwardToSyslog=no` или неправильная конфигурация `journald`. | Проверьте `/etc/systemd/journald.conf`; убедитесь, что демон запущен. |

## Рекомендации по эксплуатации

1. **Безопасность (Sandboxing)**: Используйте встроенные директивы изоляции в юнитах (`ProtectSystem=strict`, `PrivateDevices=yes`, `NoNewPrivileges=yes`). Это значительно снижает ущерб при компрометации службы.
2. **Модификация**: Никогда не редактируйте файлы в `/lib/systemd/system/` напрямую. Используйте `systemctl edit <unit>`, который создаст переопределяющий drop-in файл в `/etc`.
3. **Автоматизация**: Для временных задач используйте `systemd-run`, что позволит управлять ими как полноценными юнитам с логированием и лимитами.
4. **Наблюдаемость**: Всегда проверяйте статус через `systemctl status`, так как он содержит последние строки логов и CGroup-иерархию процессов.
5. **Аккаунтинг ресурсов**: Включайте `CPUAccounting=yes`, `MemoryAccounting=yes`, `IOAccounting=yes` в production-юнитах для детализированной наблюдаемости через `systemd-cgtop`.
6. **Валидация**: Проверяйте синтаксис юнитов через `systemd-analyze verify` перед деплоем.
7. **Дроп-ин вместо правки**: Используйте `systemctl edit` для внесения изменений; это сохраняет возможность обновления пакетов без конфликтов.
8. **Credentials для секретов**: Храните пароли и ключи в `systemd-creds` (v250+), а не в открытом виде в unit-файлах.
9. **Изоляция пользователей**: Запускайте сервисы от выделенных пользователей (`User=`, `Group=`) с минимальными привилегиями.
10. **Ограничение TasksMax**: Устанавливайте `TasksMax=` для защиты от fork-бомб, особенно для публично доступных сервисов.

## Процесс загрузки системы

### Фазы загрузки

Процесс загрузки Linux с systemd состоит из шести последовательных фаз:

```
┌─────────────────────────────────────────────────────────────────────┐
│ 1. Firmware (UEFI/BIOS)                                            │
│    • Инициализация оборудования                                     │
│    • POST (Power-On Self-Test)                                      │
│    • Выбор загрузочного устройства                                  │
└─────────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 2. Загрузчик (GRUB/systemd-boot)                                   │
│    • Чтение конфигурации загрузчика                                 │
│    • Выбор ядра и initramfs                                         │
│    • Передаче управление ядру с параметрами командной строки       │
└─────────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 3. Ядро (Kernel)                                                    │
│    • Распаковка и инициализация                                     │
│    • Загрузка драйверов (диски, LVM, RAID, LUKS)                   │
│    • Запуск PID 1 (systemd)                                         │
└─────────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 4. initramfs                                                        │
│    • Временная ФС в RAM                                             │
│    • Монтирование корня (root)                                      │
│    • Настройка LVM/RAID, расшифровка LUKS                          │
│    • Передача управления systemd                                    │
└─────────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 5. systemd (PID 1)                                                  │
│    • Запуск генераторов (fstab → .mount юниты)                     │
│    • Переразметка дисков (systemd-repart)                           │
│    • Активация базовых сервисов (udev, journald)                   │
│    • Определение default.target                                     │
└─────────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 6. Userspace                                                        │
│    • Параллельный запуск сервисов                                   │
│    • Монтирование разделов из fstab                                 │
│    • Запуск сетевых сервисов                                        │
│    • Достижение default.target (multi-user.target)                 │
└─────────────────────────────────────────────────────────────────────┘
```

### Компоненты systemd на этапе загрузки

На разных фазах загрузки работают различные компоненты systemd:

| Фаза | Компонент | Назначение |
| :--- | :--- | :--- |
| **initramfs** | `systemd-cryptsetup` | Расшифровка LUKS2-разделов |
| **initramfs** | `systemd-repart` | Переразметка дисков при первом запуске |
| **Ранний boot** | `systemd-udevd` | Обнаружение устройств, создание узлов в `/dev` |
| **Ранний boot** | `systemd-journald` | Сбор логов (с ранних этапов) |
| **Ранний boot** | `systemd-fstab-generator` | Преобразование `/etc/fstab` в `.mount` юниты |
| **Поздний boot** | `systemd-resolved` | DNS-резолвер (для сетевых сервисов) |
| **Поздний boot** | `systemd-timesyncd` | Синхронизация времени (NTP) |
| **Поздний boot** | `systemd-networkd` | Сетевая конфигурация |

### Диагностика загрузки

```bash
# Общее время загрузки по фазам
systemd-analyze
# → Startup finished in 2.5s (kernel) + 1.2s (initrd) + 10.1s (userspace) = 13.8s

# Критическая цепь (узкие места)
systemd-analyze critical-chain multi-user.target
# → multi-user.target @12.185s
# → └─nginx.service @10.500s +1.685s

# Самые медленные юниты
systemd-analyze blame
# → 7.345s NetworkManager-wait-online.service
# → 2.120s dev-sda2.device

# Диаграмма Ганта загрузки
systemd-analyze plot > boot.svg

# Логи загрузки
journalctl -b

# Ошибки загрузки
journalctl -b -p err
```

### Типичные проблемы загрузки

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Долгая загрузка** | `NetworkManager-wait-online` или `systemd-networkd-wait-online` | Отключите wait-online или переключитесь на `After=network.target` |
| **Сервис не стартует** | Зависимость не готова (БД, сеть) | Проверьте `After=` и `Requires=` в unit-файле |
| **Mount failed** | Ошибка в `/etc/fstab` | Проверьте UUID, опции монтирования |
| **Emergency mode** | Повреждение ФС или некорректный fstab | Используйте `fsck`, проверьте `/etc/fstab` |
| **Циклические зависимости** | Противоречивые `After=`/`Before=` | Используйте `systemd-analyze critical-chain` |

### Оптимизация загрузки

```bash
# 1. Отключите wait-online (для серверов)
sudo systemctl disable NetworkManager-wait-online.service
sudo systemctl mask systemd-networkd-wait-online.service

# 2. Используйте socket-activation для редких сервисов
sudo systemctl enable --now sshd.socket  # вместо sshd.service

# 3. Уменьшите таймауты
sudo systemctl set-property global DefaultTimeoutStartSec=10s

# 4. Отключите неиспользуемые сервисы
sudo systemctl disable --now bluetooth.service

# 5. Используйте Type=exec вместо simple
[Service]
Type=exec  # вместо Type=simple
```

## Ограничения и особенности

* `systemd` не является универсальным решением для всех сценариев инициализации. Для специализированных сред (embedded, container-изоляция без полного init) могут требоваться альтернативы.
* В дистрибутивах, использующих устаревшие ядра (< 4.15), поддержка cgroup v2 и некоторых директив sandboxing ограничена.
* Пользовательские таймеры (`--user`) требуют включенного `lingering` для работы при отсутствии активных сессий.
* Некоторые дистрибутивы (например, RHEL/CentOS) используют устаревшие версии systemd с ограниченной поддержкой новых директив.
* Монотонные таймеры (`OnBootSec=`, `OnUnitActiveSec=`) сбрасываются при каждой перезагрузке — они не substitutes для календарных планировщиков.
