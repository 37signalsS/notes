# Управление службами с помощью systemctl

`systemctl` — это основной инструмент командной строки для взаимодействия с `systemd` и управления службами.

## Основные команды

-   **Проверить статус службы:**

    ```bash
    systemctl status httpd.service # Пример: просмотр статуса Apache
    # Если служба неактивна, вывод будет 'Inactive (dead)'
    ```
-   **Запустить службу:**

    ```bash
    sudo systemctl start httpd.service # Запуск Apache
    # После запуска статус изменится на 'Active (running)'
    ```

- **Запустить, остановить или перезапустить службу:**
    ```bash
    sudo systemctl start nginx.service
    sudo systemctl stop nginx.service
    sudo systemctl restart nginx.service
    ```

- **Перечитать конфигурацию службы без полного перезапуска (если служба это поддерживает):**
    ```bash
    sudo systemctl reload nginx.service
    ```

- **Показать детальный статус службы, последние логи и иерархию cgroup:**
    ```bash
    systemctl status nginx.service
    ```

### Обновление конфигурации systemd

После внесения изменений в юнит-файлы на диске, необходимо сообщить `systemd` о необходимости перечитать конфигурацию.

```bash
sudo systemctl daemon-reload
```

## Разница между `reload` и `restart`

- **`reload`**: "Вежливо" просит службу перечитать свой конфигурационный файл без прерывания работы. Существующие соединения не разрываются. Этот метод работает, только если служба его поддерживает.
- **`restart`**: "Жестко" останавливает все процессы службы и запускает их заново. Это всегда работает, но приводит к кратковременному простою.


## Редактирование и переопределение юнитов

Иногда нужно изменить поведение systemd-сервиса, но:
– не хочется трогать оригинальный файл юнита в `/usr/lib/systemd/system`,
– правка временная или нужна только до следующей перезагрузки,
– важно иметь возможность быстро откатить изменения.

Для этих задач используется `systemctl edit` и связанные с ней команды.

### Постоянные правки (`systemctl edit`)

Чтобы создать постоянное изменение, не затрагивая оригинальный файл юнита (что безопасно при обновлениях пакетов), используется команда `systemctl edit`.

```bash
sudo systemctl edit nginx.service
```

Эта команда открывает текстовый редактор и создает (или редактирует) файл-дополнение (override) в `/etc/systemd/system/nginx.service.d/override.conf`. Директивы, указанные в этом файле, будут иметь приоритет над оригинальным юнитом.

**Пример: изменение команды запуска**
```ini
[Service]
# Сначала необходимо сбросить существующую директиву
ExecStart=
# А затем указать новую
ExecStart=/usr/sbin/nginx -g 'daemon off; master_process on;'
```
> **Важно:** При переопределении директив, которые могут встречаться несколько раз (например, `ExecStart`), сначала нужно сбросить их пустым значением, а затем указать новое.

### Временные правки (до перезагрузки)

Для тестирования или временных изменений, которые не должны сохраняться после перезагрузки, используется флаг `--runtime`.

```bash
systemctl edit --runtime my-service.service
```

Эта команда создает override-файл в директории `/run/systemd/system/my-service.service.d/`, которая является временной файловой системой (`tmpfs`). Все изменения из этого файла исчезнут после перезагрузки.

### Проверка и откат изменений

Перед применением изменений или для отладки полезно посмотреть итоговую конфигурацию юнита со всеми примененными override-файлами.

```bash
# Показать итоговый конфиг
systemctl cat my-service.service
```

Если внесенные изменения привели к проблемам, их можно легко отменить.

```bash
# Удалить override-файлы и вернуть юнит к состоянию по умолчанию
systemctl revert my-service.service
```

### Атомарный перезапуск после изменений

После редактирования юнита необходимо перечитать конфигурацию `systemd` и перезапустить сам сервис.

```bash
# 1. Перечитать все конфигурационные файлы
sudo systemctl daemon-reload

# 2. Перезапустить сервис (если он уже запущен)
sudo systemctl try-restart my-service.service
```

Команда `daemon-reexec` является более "глубокой" операцией, которая перезапускает сам `systemd` (PID 1), но на практике для применения изменений в юнитах достаточно `daemon-reload`.

## Управление автозапуском

- **Включить автозапуск службы при загрузке системы:**
  (создает символическую ссылку в `.wants/` каталоге нужного таргета)
    ```bash
    sudo systemctl enable nginx.service
    ```

- **Отключить автозапуск (удаляет симлинк):**
    ```bash
    sudo systemctl disable nginx.service
    ```

- **Проверить, включен ли автозапуск:**
    ```bash
    systemctl is-enabled nginx.service
    # Возможные статусы: enabled, disabled, static, masked
    ```
*Статус `static` означает, что юнит не имеет секции `[Install]` и обычно запускается как зависимость другого юнита.*

## Маскировка служб

Маскировка — это "абсолютный запрет". Она создает символическую ссылку из юнита на `/dev/null`, что делает невозможным его запуск вручную или как зависимость. Это полезно для предотвращения конфликтов (например, между `NetworkManager` и `systemd-networkd`).

```bash
# Полностью запретить запуск службы
sudo systemctl mask NetworkManager.service

# Отменить маскировку
sudo systemctl unmask NetworkManager.service
```

## Анализ состояния и зависимостей

```bash
# Показать все активные юниты
systemctl list-units

# Показать все установленные юнит-файлы и их статус автозагрузки
systemctl list-unit-files --type=service

# Показать юниты, от которых зависит служба (прямые зависимости)
systemctl list-dependencies nginx.service

# Показать юниты, которые зависят от этой службы (обратные зависимости)
systemctl list-dependencies --reverse nginx.service

# Показать все юниты, которые не смогли запуститься
systemctl --failed
```

## Типы сервисов (`Type=`)

Параметр `Type=` в секции `[Service]` юнит-файла определяет, как `systemd` отслеживает состояние службы.

-   `simple` (по умолчанию): `ExecStart` — это главный процесс. `systemd` считает сервис запущенным сразу после его старта.
-   `forking`: `ExecStart` запускает процесс, который создает своего потомка (fork) и завершается. `systemd` считает главным дочерний процесс. Требует указания `PIDFile=`. Используется для "старых" демонов (nginx, httpd).
-   `oneshot`: Для скриптов, которые должны выполниться один раз и завершиться. `systemd` ждет их завершения. Часто используется с `RemainAfterExit=yes`, чтобы сервис считался активным даже после завершения процесса.
-   `notify`: Сервис сам уведомляет `systemd` о готовности через `sd_notify()`. Самый надежный способ управления зависимостями.
-   `dbus`: Сервис считается готовым, когда его имя появляется на шине D-Bus.

## Логирование

### Просмотр логов (`journalctl`)

`systemd` включает в себя мощную подсистему логирования `journald`. Для просмотра и анализа логов используется утилита `journalctl`.

Подробное описание `journalctl` и его возможностей находится в основной заметке: **[systemd-journald: Современная система логирования](../../SystemAdministration/Logging/journald.md)**.

### `logrotate` и службы `systemd`

Хотя `journald` управляет бинарными логами, многие приложения по-прежнему пишут текстовые логи, которые ротируются с помощью `logrotate`. `systemd` играет важную роль в этом процессе, так как `logrotate` часто использует `postrotate` скрипты для отправки сигналов службам (`kill -USR1` или `systemctl reload`), чтобы они корректно переоткрыли свои лог-файлы после ротации. Это предотвращает потерю логов и гарантирует, что приложения продолжат писать в новые файлы.

Пример из `logrotate` для Nginx, где `systemd` используется для перезагрузки конфигурации:

```
/var/log/nginx/*.log {
    ...
    postrotate
        [ -f /var/run/nginx.pid ] && kill -USR1 `cat /var/run/nginx.pid`
        # Или, если служба управляется systemd и поддерживает reload:
        # systemctl reload nginx.service
    endscript
}
```

Более детально о `logrotate` и его конфигурации можно узнать в основной заметке о логировании.

## Проверка синтаксиса юнит-файлов (`systemd-analyze verify`)

Прежде чем активировать новый или измененный юнит, полезно проверить его на наличие синтаксических ошибок. Для этого используется команда `systemd-analyze verify`.

```bash
# Проверить синтаксис файла юнита
systemd-analyze verify /etc/systemd/system/my-custom.service
```

Если в файле есть ошибки, команда выведет подробную информацию о том, что именно и в какой строке неверно. Если ошибок нет, команда завершится без вывода. Это простой способ убедиться в корректности файла перед выполнением `daemon-reload` и запуском службы.

## Оптимизация производительности и приоритеты при холодном старте

### IOSchedulingClass и IOSchedulingPriority

Позволяют задать класс и приоритет доступа к диску.

Пример:

```ini
[Service]
IOSchedulingClass=best-effort
IOSchedulingPriority=2
```

Если сервис работает с базами или логами — можно установить класс `realtime` или поднять приоритет ближе к `0` (чем ниже — тем выше приоритет).

### CPUSchedulingPolicy и CPUSchedulingPriority

Контроль приоритетов на уровне CPU-шедулера. Для критичных задач — `SCHED_FIFO` или `SCHED_RR`.

```ini
[Service]
CPUSchedulingPolicy=fifo
CPUSchedulingPriority=50
```

### StartLimitBurst и StartLimitIntervalSec

Позволяют контролировать поведение при частых перезапусках. Иногда systemd из-за быстрых рестартов просто «глушит» сервис.

```ini
[Unit]
StartLimitBurst=10
StartLimitIntervalSec=30
```

Можно дать больше попыток на старте — особенно если сервис зависит от сети или сторонних демонов.

### TimeoutStartSec

Если холодный старт занимает время, а systemd слишком рано считает запуск проваленным — увеличьте таймаут:

```ini
[Service]
TimeoutStartSec=60s
```

### ExecStartPre и ReadyNotify

Иногда лучше запускать предварительную инициализацию отдельно, чтобы основная служба стартовала уже с готовым окружением.

```ini
[Service]
ExecStartPre=/usr/local/bin/warmup.sh
Type=notify
```

### Nice и OOMScoreAdjust

Если нужно приоритетное планирование и защита от OOM killer’а:

```ini
[Service]
Nice=-5
OOMScoreAdjust=-500
```
