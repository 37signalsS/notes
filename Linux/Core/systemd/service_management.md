# Управление службами через systemctl

## Определения

* **Служба (Service)** — в экосистеме `systemd` это процесс или группа процессов, жизненным циклом которых управляет система инициализации. Каждая служба описывается в текстовом конфигурационном файле — юнит-файле (например, `nginx.service`).
* **`systemctl`** — центральная утилита командной строки для взаимодействия с менеджером `systemd`. Она позволяет изменять состояние системы, управлять службами, анализировать их статус и настраивать параметры автозагрузки.

## Основные концепции

### Управление состоянием юнита

Базовые команды для изменения текущего состояния службы в режиме реального времени.

```bash
# Запуск службы
sudo systemctl start nginx.service
# → запуск основного процесса и зависимостей

# Остановка службы
sudo systemctl stop nginx.service
# → отправка SIGTERM процессам юнита

# Перезапуск службы
sudo systemctl restart nginx.service
# → полная остановка и новый запуск (приводит к кратковременному простою)

# Перечитывание конфигурации приложения
sudo systemctl reload nginx.service
# → запрос к приложению перечитать конфигурацию без остановки процесса
```

### Анализ статуса и метаданных

Команда `status` предоставляет детальную информацию о работе юнита.

```bash
systemctl status nginx.service
# → ● nginx.service - A high performance web server and a reverse proxy server
# →    Loaded: loaded (/lib/systemd/system/nginx.service; enabled; vendor preset: enabled)
# →    Active: active (running) since Sat 2024-06-08 10:00:00 MSK; 1h ago
# →      Main PID: 1234 (nginx)
# →     Tasks: 2 (limit: 4915)
# →    Memory: 45.2M
# →    CPU: 1.2s
# →    CGroup: /system.slice/nginx.service
```

**Ключевые поля статуса:**
* **`Loaded`** — путь к файлу на диске и статус автозагрузки.
* **`Active`** — текущее состояние (например, `active (running)`, `failed`, `inactive (dead)`).
* **`Main PID`** — идентификатор основного процесса.
* **`CGroup`** — контрольная группа, через которую `systemd` изолирует процессы и ограничивает ресурсы (CPU, RAM, I/O).

Для использования в скриптах удобно применять "чистые" команды проверки:
```bash
# Проверка, активна ли служба
systemctl is-active nginx.service
# → active

# Проверка, завершилась ли служба с ошибкой
systemctl is-failed nginx.service
# → failed (если есть ошибки) или active/inactive (если нет)
```

### Управление автозагрузкой и блокировка

Настройка поведения службы при старте системы.

| Команда | Описание |
| :--- | :--- |
| `systemctl enable <unit>` | Включить автозапуск (создание симлинков в `.wants/`). |
| `systemctl disable <unit>` | Отключить автозапуск (удаление симлинков). |
| `systemctl enable --now <unit>` | Включить и запустить немедленно. |
| `systemctl mask <unit>` | Полная блокировка (привязка юнита к `/dev/null`). |
| `systemctl unmask <unit>` | Снятие блокировки. |

**Важные нюансы:**
- **Start vs Enable:** Это самая частая ловушка. `start` запускает службу "здесь и сейчас", но после перезагрузки она не поднимется. `enable` настраивает автозапуск, но не запускает службу немедленно. Для полноценной работы обычно нужны обе команды (или `enable --now`).
- **Masking:** Это "рубильник под стеклом". Маскировка — это более жесткий запрет, чем `disable`. Если служба замаскирована, `systemd` откажется её трогать, даже если она потребуется как зависимость для другого юнита. Это полезно для гарантированного отключения нежелательных компонентов.

## Практические сценарии

### Анализ состава системы

```bash
# Показать все активные юниты
systemctl list-units
# → список запущенных служб, сокетов и таргетов

# Показать только упавшие юниты
systemctl --failed
# → UNIT            LOAD   ACTIVE SUB    DESCRIPTION
# → app.service     loaded failed failed My Custom Application

# Показать все установленные файлы юнитов и их статус автозагрузки
systemctl list-unit-files --type=service

# Показать зависимости службы
systemctl list-dependencies nginx.service
# → nginx.service
# → ├─system.slice
# → └─network.target
```

### Редактирование и переопределение (Overrides)

Для изменения параметров службы без редактирования файлов в `/usr/lib/` (которые затираются при обновлении пакетов) используется механизм **drop-in** файлов через `systemctl edit`.

```bash
# Создание или редактирование переопределений
sudo systemctl edit nginx.service
```
Это создаст файл в `/etc/systemd/system/nginx.service.d/override.conf`.

**Пример изменения лимитов памяти:**
```ini
[Service]
MemoryMax=500M
```

**Важное правило для списков:** если вы переопределяете директиву, которая может встречаться несколько раз (например, `ExecStart`), её нужно сначала очистить:
```ini
[Service]
ExecStart=
ExecStart=/usr/sbin/nginx -g 'daemon off;'
```

### Применение изменений и daemon-reload

#### Что делает `daemon-reload`
Команда `systemctl daemon-reload` заставляет `systemd` полностью пересобрать внутреннее представление о юнитах: перечитываются все файлы в `/etc/systemd/system/` и `/usr/lib/systemd/system/`, пересчитываются зависимости и обновляется граф сервисов. Запущенные процессы при этом **не перезапускаются**.

#### Последовательность действий при изменении конфига
Если изменить `ExecStart`, переменные окружения или лимиты, работающий процесс продолжит использовать старые настройки. Для применения новых параметров необходимо:
```bash
# 1. Сказать systemd перечитать файлы с диска
sudo systemctl daemon-reload
# 2. Перезапустить саму службу
sudo systemctl restart nginx.service
```

### Управление свойствами «на лету»

Некоторые параметры ресурсов можно менять без редактирования файлов и перезагрузки.

```bash
# Ограничить CPU для работающей службы до 50%
sudo systemctl set-property nginx.service CPUQuota=50%
# → изменения записываются в /etc/systemd/system.control/ и применяются немедленно
```

## Дополнительная информация

### Диагностика и журналы

Все службы `systemd` автоматически направляют вывод в системный журнал `journald`.

* **Просмотр логов в реальном времени**: `journalctl -u nginx.service -f`
* **Проверка синтаксиса перед запуском**: `systemd-analyze verify /etc/systemd/system/my-service.service`
* **Сводка расхождений конфигурации**: `systemd-delta`
