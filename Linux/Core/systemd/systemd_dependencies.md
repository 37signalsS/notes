# Управление зависимостями в systemd

## Определения

**Зависимости между юнитами** — это встроенные механизмы системы инициализации `systemd`, которые определяют логические взаимосвязи и строгий порядок активации различных компонентов Операционной Системы (ОС). Они гарантируют, что службы будут запущены только при наличии необходимых ресурсов и в правильной последовательности, предотвращая состояния гонки (race conditions).

В `systemd` выделяют два фундаментально разных типа связей:

* **Логическая зависимость** (директивы `Wants`, `Requires`, `BindsTo`): Определяет, должен ли один юнит активироваться при запуске другого.
* **Порядок запуска** (директивы `After`, `Before`): Определяет временную последовательность активации юнитов, не создавая между ними логической связи.

## Основные концепции

### Типы директив и их поведение

Для надежной работы сервисов рекомендуется всегда комбинировать логическую зависимость с указанием порядка запуска.

| Директива | Тип связи | Описание поведения |
| :--- | :--- | :--- |
| **`After=`** | Порядок | Текущий юнит начнет запуск только **после** того, как указанный юнит завершит свою активацию. |
| **`Before=`** | Порядок | Текущий юнит должен полностью запуститься **до** того, как начнется старт указанного юнита. |
| **`Wants=`** | Логика (слабая) | `systemd` попытается запустить указанный юнит. Если он не сможет стартовать, это не повлияет на работу текущего юнита. |
| **`Requires=`** | Логика (сильная) | Указанный юнит становится обязательным. Если он не запустится, текущий юнит также перейдет в состояние ошибки. |
| **`BindsTo=`** | Логика (жёсткая) | Связывает жизненные циклы: если зависимый юнит останавливается или пропадает (например, отключается устройство), текущий юнит немедленно останавливается. |
| **`PartOf=`** | Логика (групповая) | Позволяет транслировать команды остановки и перезапуска от родительского юнита (например, таргета) к текущему. |
| **`Conflicts=`** | Конфликт | Взаимное исключение: запуск текущего юнита приведет к автоматической остановке всех юнитов, перечисленных в этой директиве. |

### Матрица совместной работы при сбоях

| Конфигурация | Если зависимость упала при старте | Если зависимость упала в процессе работы |
| :--- | :--- | :--- |
| `Wants=` | Текущий юнит всё равно запустится. | Ничего не происходит. |
| `Requires=` | Текущий юнит не будет запущен. | Ничего не происходит (по умолчанию). |
| `BindsTo=` | Текущий юнит не будет запущен. | Текущий юнит будет немедленно остановлен. |

## Практические сценарии

### Ожидание готовности сети (IP-адреса)

Обычная зависимость `After=network.target` гарантирует только запуск сетевого стека, но не получение адреса по DHCP или готовность интерфейсов. Для сервисов, которым нужен доступ в интернет, используйте `network-online.target`.

```ini
[Unit]
Description=Cloud Backup Service
# Пытаемся активировать сетевые подключения
Wants=network-online.target
# Ждем, пока сеть действительно станет доступна
After=network-online.target
```

### Зависимость от базы данных

Если приложение не может работать без связи с Базой Данных (БД), используйте комбинацию `Requires` и `After`.

```ini
[Unit]
Description=Web Application Backend
Requires=postgresql.service
After=postgresql.service
```

### Диагностика дерева зависимостей

Для проверки того, как `systemd` выстроил связи для конкретного юнита, используются встроенные команды.

```bash
# Просмотр дерева юнитов, от которых зависит сервис
systemctl list-dependencies nginx.service
# → nginx.service
# → ├─system.slice
# → └─network.target

# Реверсивные зависимости: кто зависит от данного юнита
systemctl list-dependencies --reverse nginx.service
# → nginx.service
# → └─multi-user.target
```

### Визуализация и поиск "узких мест"

Инструменты анализа позволяют увидеть критические пути загрузки, вызванные длинными цепочками зависимостей.

```bash
# Показать критическую цепочку, определяющую время загрузки
systemd-analyze critical-chain
# → graphical.target @12.185s
# → └─multi-user.target @12.185s
# →   └─nginx.service @10.500s +1.685s

# Генерация графической схемы зависимостей в формате SVG (Scalable Vector Graphics)
systemd-analyze plot > dependencies_map.svg
# → создание файла для детального анализа в браузере
```

## Дополнительная информация

### Типичные ошибки

* **Циклические зависимости**: Ситуация, когда Юнит А зависит от Юнита Б, а Юнит Б — от Юнита А. В этом случае `systemd` выдаст ошибку "Found ordering cycle" и откажется запускать часть юнитов.
* **Зависимость без порядка**: Использование `Requires=` без `After=` может привести к тому, что оба юнита начнут запускаться одновременно, и основной юнит упадет, не дождавшись готовности зависимости.
