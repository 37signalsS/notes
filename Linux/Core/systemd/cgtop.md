# systemd-cgtop: Мониторинг ресурсов контрольных групп

## Определения

* **`systemd-cgtop`** — интерактивная системная утилита для мониторинга потребления ресурсов (CPU, память, I/O) в режиме реального времени, сгруппированных по иерархии контрольных групп (**cgroups**). Относится к пакету `systemd` и по умолчанию присутствует во всех современных дистрибутивах, использующих systemd в качестве init-системы.
* **Control Group (cgroup)** — механизм ядра Linux для объединения процессов в иерархические группы с целью изоляции, ограничения и учета ресурсов.
* **Cgroup v2 (unified hierarchy)** — актуальная версия механизма cgroups, использующая единое дерево `/sys/fs/cgroup` и поддерживающая все контроллеры одновременно.
* **Cgroup v1** — устаревшая версия с разрозненными иерархиями для каждого контроллера (cpu, memory, blkio и т.д.). `systemd-cgtop` работает в этой среде, но некоторые метрики (в частности, рекурсивный подсчет) могут вести себя иначе.
* **Accounting** — механизм сбора статистики использования ресурсов внутри cgroup. Включается через параметры `CPUAccounting=`, `MemoryAccounting=`, `IOAccounting=`, `TasksAccounting=` в юнит-файлах или глобально в `system.conf`.

## Основные концепции

### Требования и ограничения

* **Версия systemd:** для корректной работы cgroup v2 необходим systemd ≥ 230 (рекомендуется ≥ 247, как в RHEL 9 / Ubuntu 22.04).
* **Ядро Linux:** поддержка cgroup v2 доступна начиная с ядра 4.15, но для PSI и стабильного делегирования контроллеров рекомендуется ядро ≥ 5.4.
* **Права доступа:** для чтения метрик системных cgroups требуется обычные права пользователя; для записи в `cgroup.subtree_control` или изменения лимитов — `root`.
* **Агрегация данных:** `systemd-cgtop` суммирует нагрузку от всех процессов внутри cgroup, включая дочерние группы (если включен рекурсивный режим). Это отличает его от `top`/`htop`, которые показывают отдельные PID.

### Преимущества агрегации данных

В отличие от классических инструментов типа `top`, которые фокусируются на отдельных процессах (PID), `systemd-cgtop` агрегирует метрики на уровне логических юнитов: сервисов (`.service`), пользовательских сессий (`.scope`) и организационных контейнеров (`.slice`). Это позволяет мгновенно оценить общую нагрузку от приложения (например, веб-сервера), даже если оно состоит из множества дочерних процессов.

### Интерпретация метрик (колонки вывода)

| Колонка | Описание | Примечание |
| :--- | :--- | :--- |
| **Control Group** | Путь к группе в иерархии cgroups. | Начинается с `/` (root). |
| **Tasks** | Количество активных потоков и процессов в группе. | Требует `TasksAccounting=yes`. |
| **%CPU** | Процент использования процессорного времени. | 100% обычно соответствует 1 полному ядру. |
| **Memory** | Текущее потребление оперативной памяти группой. | В cgroup v2 соответствует `memory.current`. |
| **Input/s** | Скорость чтения данных с блочных устройств. | Требует `IOAccounting=yes`. |
| **Output/s** | Скорость записи данных на блочные устройства. | Требует `IOAccounting=yes`. |

> **Примечание:** В режиме `--raw` значения Memory, Input/s и Output/s отображаются в байтах/сек, а не в человекочитаемом формате.

### Сравнение с альтернативами

| Инструмент | Уровень агрегации | Режим | Когда использовать |
| :--- | :--- | :--- | :--- |
| **`systemd-cgtop`** | cgroup (сервис, slice, scope) | Интерактивный / batch | Быстрая оценка потребления ресурсов по юнитам systemd. |
| **`top` / `htop`** | PID | Интерактивный | Детализация по отдельным процессам, ручная сортировка. |
| **`ps`** | PID | Пакетный | Скриптовая выборка снапшотов процессов. |
| **`systemd-cgls`** | cgroup | Дерево | Визуализация иерархии cgroups без метрик. |
| **`cat /sys/fs/cgroup/.../*`** | cgroup | Пакетный | Детальная пер-файловая статистика (например, `cpu.stat`, `memory.current`). |
| **`pidstat -G`** | cgroup | Пакетный | История метрик cgroups через `sysstat` (если поддерживается ядром). |

### Требования к сбору метрик (Accounting)

Для отображения данных необходимо активировать соответствующие контроллеры в настройках `systemd`. Это можно сделать глобально в `/etc/systemd/system.conf` или в unit-файле конкретной службы:

```ini
[Service]
CPUAccounting=yes
MemoryAccounting=yes
IOAccounting=yes
TasksAccounting=yes
```

> **Важно:** В большинстве современных дистрибутивов (Ubuntu 22.04+, RHEL 9+, Debian 12+) базовый аккаунтинг включен по умолчанию для системных юнитов. Для пользовательских сессий (user@.service) и временных scopes учет может потребовать явного включения.

### Валидация настройки accounting

Перед использованием `systemd-cgtop` убедитесь, что контроллеры активны:

```bash
# Проверка глобальных параметров
systemctl show --property=CPUAccounting --property=MemoryAccounting --property=IOAccounting --property=TasksAccounting

# Проверка конкретного сервиса
systemctl show nginx.service --property=CPUAccounting --property=MemoryAccounting

# Проверка доступных контроллеров cgroup v2 (должны быть delegation)
cat /sys/fs/cgroup/cgroup.controllers
# → cpu io memory pids
```

Если контроллеры не делегированы в подгруппу, метрики могут отображаться как 0 или отсутствовать.

### Поддержка cgroup v2

`systemd-cgtop` полноценно поддерживает **cgroup v2** (unified hierarchy). В этом режиме утилита по умолчанию отображает рекурсивные значения: ресурсы, потребляемые дочерними группами, суммируются в родительском слайсе, что дает прозрачную картину потребления ресурсов всей веткой дерева.

В **cgroup v1** рекурсивный подсчет отсутствует по архитектурным причинам (раздельные иерархии), поэтому `systemd-cgtop` показывает только прямых членов группы.

## Практические сценарии

### Поиск «тяжелых» потребителей ресурсов

Использование флагов сортировки при запуске позволяет быстро выявить проблемные юниты.

```bash
# Сортировка по потреблению памяти
systemd-cgtop --order=memory

# Сортировка по нагрузке на диск (I/O)
systemd-cgtop --order=io

# Сортировка по количеству задач (поиск «форк-бомб» или утечек потоков)
systemd-cgtop --order=tasks
```

**Ожидаемый результат:** курсор автоматически устанавливается на строку с максимальным значением выбранной метрики.

### Детекция утечек памяти и CPU-спайков

Для SRE-диагностики полезно фиксировать снапшот в batch-режиме с интервалом:

```bash
# Сбор метрик каждые 2 секунды, 10 итераций, только память и CPU
systemd-cgtop --batch --iterations=10 --delay=2 --order=memory --raw > /tmp/mem_snapshot.txt

# Парсинг топ-3 потребителей памяти
awk 'NR>1 {print $1, $4}' /tmp/mem_snapshot.txt | sort -k2 -nr | head -n 3
```

### Мониторинг в контейнеризированных средах

При работе с контейнерами (nspawn, LXC) или глубокой вложенностью в Kubernetes вывод может быть перегружен.

```bash
# Ограничение глубины дерева (показать только верхние 3 уровня)
systemd-cgtop --depth=3

# Мониторинг ресурсов конкретной машины или контейнера
systemd-cgtop --machine=my_container
```

> **Важно:** Флаг `--machine` требует работающего `systemd-nspawn` контейнера. Для Docker/Podman контейнеров используйте `--depth` или фильтрацию по пути cgroup (`/system.slice/docker-*.scope`).

### Пакетный режим для диагностики и интеграции с мониторингом

Snapshot-режим удобен для логирования состояния системы или использования в скриптах.

```bash
# Однократный вывод данных в «сыром» виде (в байтах)
systemd-cgtop --batch --iterations=1 --raw
# → Control Group                            Tasks   %CPU   Memory  Input/s Output/s
# → /                                          452    12.5  2456789123        0        0
```

**Парсинг для Prometheus-экспортера или кастомного мониторинга:**

```bash
# Извлечение только сервисов systemd (игнорируя корень /)
systemd-cgtop --batch --iterations=1 --raw | awk 'NR>1 && $1 ~ /\.service$/ {print $1, $4}'
# → getty.service 123456
# → sshd.service 987654
```

### Настройка частоты обновления

По умолчанию данные обновляются каждую секунду. Для снижения нагрузки на мониторинг интервал можно увеличить.

```bash
# Обновление раз в 5 секунд
systemd-cgtop --delay=5
```

### Мониторинг конкретного пользователя или сессии

Для анализа ресурсов, потребляемых пользовательскими сессиями:

```bash
# Фильтр по user slice (пример для UID 1000)
systemd-cgtop --depth=2 | grep "user-1000"
# Или через прямой путь
systemd-cgtop --batch --raw | grep "/user.slice/user-1000.slice"
```

### Диагностика проблем с I/O

При подозрении на чрезмерную нагрузку на диск:

```bash
# Сортировка по Output/s для поиска записывающих процессов
systemd-cgtop --order=io

# Однократная проверка без интерактивного режима
systemd-cgtop --batch --iterations=1 --raw | sort -k6 -nr | head -n 10
```

## Интерактивное управление

Во время работы утилиты доступны следующие горячие клавиши:

| Клавиша | Действие |
| :--- | :--- |
| **`c`** | Сортировать по CPU. |
| **`m`** | Сортировать по памяти. |
| **`i`** | Сортировать по I/O. |
| **`t`** | Сортировать по количеству задач (Tasks). |
| **`p`** | Сортировать по пути (Path). |
| **`+` / `-`** | Увеличить / уменьшить глубину отображения дерева. |
| **`r`** | Переключить режим рекурсивного подсчета. |
| **`d`** | Изменить интервал обновления (запрос ввода в секундах). |
| **`%`** | Переключить CPU между процентами и временем. |
| **`SPACE`** | Принудительно обновить данные на экране. |
| **`q`** | Выход из программы. |

## Диагностика и устранение неисправностей

### Типичные ошибки

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Все метрики равны 0 | Отключен accounting в `system.conf` или unit-файле. | Включите нужные `*Accounting=yes` и перезапустите службу: `systemctl daemon-reload && systemctl restart <unit>`. |
| Отсутствует столбец I/O | `IOAccounting=no` по умолчанию или не включен `blkio` контроллер. | Включите `IOAccounting=yes`; для cgroup v2 проверьте `cgroup.subtree_control`. |
| `%CPU` > 100% на многоядерной системе | Ожидаемое поведение: 100% = 1 ядро. | Используйте режим `%` для переключения в абсолютное время CPU. |
| Нет данных по `--machine` | Указанный контейнер не запущен через `systemd-nspawn` или имеет другое имя. | Проверьте: `machinectl list`. |
| Путаница между cgroup v1 и v2 | В v1 рекурсивный подсчет не работает, пути отличаются. | Проверьте: `stat -fc %T /sys/fs/cgroup/` (v2 = `cgroup2fs`). |
| Ошибка доступа к cgroup | Отсутствуют права на чтение подгруппы (обычно в user slice). | Используйте `sudo` или проверьте делегирование контроллеров. |
| Форк-бомб не детектируются | `TasksAccounting=no` или лимит не выставлен. | Включите учет и установите `TasksMax=` в unit-файле. |

### Проверка корректности работы

```bash
# 1. Убедитесь, что утилита видит cgroup иерархию
systemd-cgtop --batch --iterations=1 --depth=1

# 2. Проверьте, что данные не нулевые для известной активной службы
systemd-cgtop --batch --raw | grep sshd.service

# 3. Сравните с прямой записью из cgroup (должны совпадать)
cat /sys/fs/cgroup/system.slice/sshd.service/cpu.max
systemd-cgtop --batch --raw | grep sshd.service | awk '{print $3}'
```

## Рекомендации по эксплуатации (Best Practices)

1. **Включение accounting по умолчанию:** Для production-сервисов всегда включайте `CPUAccounting=yes`, `MemoryAccounting=yes` и `IOAccounting=yes` в unit-файлы. Это минимальная стоимость за детализированную наблюдаемость.
2. **Использование batch-режима для исторических данных:** Интерактивный режим unsuitable для долгосрочного логирования. Используйте `--batch --iterations=N --delay=S` в combination с `cron` или `systemd-timer` для построения временных рядов.
3. **Фильтрация по depth:** В системах с глубокой иерархией (Kubernetes, Docker с многоуровневыми slice) всегда используйте `--depth=2` или `--depth=3`, чтобы вывод оставался читаемым.
4. **Корреляция с journald:** При обнаружении аномалии в `systemd-cgtop` сразу проверяйте логи службы через `journalctl -u <service> --since "10 min ago"` для контекста.
5. **Ограничение TasksMax:** Для защиты от форк-бомб устанавливайте `TasksMax=` в unit-файлах и отслеживайте столбец `Tasks` в `systemd-cgtop`.
6. **Не используйте для per-PID анализа:** `systemd-cgtop` агрегирует данные. Для детализации по процессам используйте `top`, `htop` или `pidstat`.
7. **Кросс-проверка с cgroup fs:** При сомнениях в данных `systemd-cgtop` сверяйтесь с прямым чтением файлов в `/sys/fs/cgroup/`, особенно для тонкой настройки лимитов.

## Ограничения утилиты

* Не показывает детализацию по отдельным PID внутри cgroup.
* В cgroup v1 отсутствует рекурсивный подсчет ресурсов.
* Для I/O-метрик требует включенного `IOAccounting=`, что может незначительно влиять на производительность в высоконагруженных системах (современные ядра минимизируют overhead).
* Интерфейс ncurses не поддерживает мышь и сложную навигацию.
* Batch-режим выводит «сырые» числа, требуя постобработки для интеграции с внешними системами.
