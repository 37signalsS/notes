# Интеграция Docker с systemd

## Определения

**Интеграция Docker с systemd** — это подход, при котором жизненный цикл Docker-контейнеров управляется с помощью `systemd` на хост-системе. Каждый контейнер или группа связанных контейнеров определяется как сервис `systemd` (юнит-файл), что позволяет запускать, останавливать, перезапускать и управлять ими как стандартными системными службами.

## Основные концепции

Использование `systemd` для управления Docker-контейнерами дает следующие преимущества:

* **Управление зависимостями:** Вы можете запустить контейнер только после старта определённой системной службы (например, базы данных или сетевого сервиса) с помощью директив `After` и `Requires`. Подробнее о зависимостях `systemd` см. в [Юниты, таргеты и зависимости systemd](./systemd_units_overview.md).
* **Интеграция в экосистему `systemd`:** Позволяет использовать единый интерфейс для управления всеми службами (`systemctl`), централизованно собирать логи через `journald`, запускать контейнеры по расписанию с помощью таймеров `systemd` и автоматически перезапускать их при сбоях. Общие сведения о `systemd` доступны в [Обзор Systemd: Управление системой и службами](./overview.md).
* **Автоматизация при развертывании:** Управление контейнерами легко встраивается в существующие сценарии автоматизации (например, с помощью Ansible), которые работают с юнитами `systemd`.

## Практические сценарии

### 1. Юнит-файл для запуска контейнера Nginx

Рассмотрим пример файла `nginx-container.service`, который запускает, останавливает и перезапускает контейнер Nginx.

```ini
[Unit]
Description=Nginx Container
# Жесткая зависимость: сервис не запустится, если docker.service неактивен
Requires=docker.service
# Порядок запуска: сервис будет запущен только после docker.service
After=docker.service

[Service]
Restart=always

# Команды для очистки перед стартом
# Знак "-" игнорирует ошибки (например, если контейнер не существует)
ExecStartPre=-/usr/bin/docker stop nginx-container
ExecStartPre=-/usr/bin/docker rm nginx-container

# Основная команда запуска контейнера
# Флаг --rm автоматически удаляет контейнер после его остановки
ExecStart=/usr/bin/docker run --rm --name nginx-container -p 8080:80 nginx

# Команда для корректной остановки контейнера
ExecStop=/usr/bin/docker stop nginx-container

[Install]
# Добавление сервиса в автозагрузку для многопользовательского режима
WantedBy=multi-user.target
```

**Ключевые директивы:**

* **`[Unit]`**: Зависимости — `Requires=docker.service` (жёсткая), `After=docker.service` (порядок). Подробнее: [Dependencies SSoT](./systemd_dependencies.md).
* **`[Service]`**: `Restart=always` — перезапуск при любом завершении. `ExecStartPre=-...` — очистка перед стартом (знак `-` игнорирует ошибки). `ExecStop` — корректная остановка.
* **`[Install]`**: `WantedBy=multi-user.target` — стандартный многопользовательский режим.

### 2. Управление сервисом

После создания файла `/etc/systemd/system/nginx-container.service` управление осуществляется стандартными командами `systemctl`. Подробнее: [Управление службами (systemctl)](./service_management.md).

```bash
# Перечитать конфигурацию systemd после создания или изменения юнита
sudo systemctl daemon-reload

# Запустить сервис
sudo systemctl start nginx-container.service

# Включить автозапуск при загрузке системы
sudo systemctl enable nginx-container.service

# Проверить статус
systemctl status nginx-container.service
```

## Дополнительная информация

**Важно:** Данный подход описывает управление Docker-контейнерами *на хост-системе*. Не следует путать это с попытками запустить `systemd` в качестве PID 1 *внутри* контейнера, что считается анти-паттерном из-за нарушения принципа "один процесс на контейнер" и проблем с привилегиями.

Подробнее об этой проблеме читайте в документе [Systemd в Docker: почему это анти-паттерн](../../../Docker/docker_systemd.md).
