# Интеграция Docker с systemd

## Определения

**Интеграция Docker с systemd** — это архитектурный подход, при котором жизненный цикл Docker-контейнеров управляется системой инициализации `systemd` на хост-системе. В этом сценарии каждый контейнер или группа связанных контейнеров описывается как стандартный юнит-файл (unit file) сервиса `systemd`. Это позволяет использовать единый инструмент управления для нативных системных служб и контейнеризированных приложений.

## Основные концепции

Использование `systemd` в качестве менеджера для Docker-контейнеров предоставляет следующие возможности:

* **Управление зависимостями**: Контейнер запускается строго после готовности необходимых системных ресурсов (сеть, файловые системы) или других служб (например, база данных на хосте).
* **Единый интерфейс управления**: Администратор использует стандартные команды `systemctl` и `journalctl` для управления всеми компонентами системы.
* **Автоматическое восстановление**: Механизмы `systemd` позволяют гибко настраивать политики перезапуска контейнеров при их аварийном завершении.
* **Планирование**: Возможность запуска контейнеров по расписанию с помощью таймеров `systemd` (замена cron (Command Run On)).
* **Централизованное логирование**: Вывод контейнеров автоматически направляется в `journald` (бинарный системный журнал), что упрощает агрегацию и анализ логов.

## Практические сценарии

### 1. Создание юнит-файла для контейнера

Пример конфигурации сервиса для запуска контейнера Nginx (Engine X). Файл следует разместить по пути `/etc/systemd/system/nginx-container.service`.

```ini
[Unit]
Description=Nginx Container Service
# Указываем, что сервис зависит от работающего демона Docker
Requires=docker.service
After=docker.service

[Service]
# Автоматический перезапуск при сбое
Restart=always

# Подготовка окружения перед стартом
# Символ "-" перед командой означает игнорирование ошибок (например, если контейнера нет)
ExecStartPre=-/usr/bin/docker stop nginx-container
ExecStartPre=-/usr/bin/docker rm nginx-container

# Запуск контейнера
# Параметр --rm обеспечивает удаление контейнера после его остановки демоном
ExecStart=/usr/bin/docker run --rm --name nginx-container -p 8080:80 nginx

# Команда для корректного завершения работы контейнера
ExecStop=/usr/bin/docker stop nginx-container

[Install]
# Целевое состояние для автозагрузки (аналог runlevel 3)
WantedBy=multi-user.target
```

### 2. Управление контейнером через systemctl

После создания или изменения юнит-файла необходимо выполнить следующие действия:

```bash
# Обновление конфигурации менеджера юнитов
sudo systemctl daemon-reload
# → обновление кэша конфигурации systemd

# Активация автозагрузки сервиса
sudo systemctl enable nginx-container.service
# → Created symlink /etc/systemd/system/multi-user.target.wants/nginx-container.service

# Запуск сервиса
sudo systemctl start nginx-container.service
# → запуск процесса docker run в контексте юнита

# Проверка текущего состояния
systemctl status nginx-container.service
# → ● nginx-container.service - Nginx Container Service
# →    Active: active (running) since ...
```

## Дополнительная информация

### Управление на хосте против systemd внутри контейнера

Важно различать два подхода:

1. **Управление контейнерами на хосте через systemd** (описано выше) — является рекомендуемой практикой для обеспечения надежности и интеграции в инфраструктуру.
2. **Запуск systemd внутри контейнера (как PID (Process ID) 1)** — считается анти-паттерном. Это нарушает принцип "один процесс на контейнер", требует запуска в привилегированном режиме (`--privileged`) и усложняет архитектуру.

Для более подробного анализа проблем запуска `systemd` внутри контейнера см. документ [Systemd в Docker: почему это анти-паттерн](../../../Docker/docker_systemd.md).
