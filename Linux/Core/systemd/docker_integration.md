# Запуск Docker-контейнеров как сервисов systemd

Хотя для управления контейнерами существуют специализированные инструменты, такие как Docker Compose или Kubernetes, иногда бывает полезно запускать Docker-контейнеры как обычные системные службы `systemd`.

**Преимущества такого подхода:**

*   **Управление зависимостями:** Вы можете запустить контейнер только после старта определённой системной службы (например, базы данных или сетевого сервиса).
*   **Интеграция в экосистему `systemd`:** Единый интерфейс для управления всеми службами, логирование через `journald`, использование таймеров и т.д.
*   **Автоматизация при развертывании:** Управление контейнерами можно встроить в существующие сценарии автоматизации (например, Ansible), которые работают с юнитами `systemd`.

## Пример: Юнит для запуска контейнера Nginx

Рассмотрим пример файла `nginx-container.service`, который запускает, останавливает и перезапускает контейнер Nginx.

```ini
[Unit]
Description=Nginx Container
Requires=docker.service
After=docker.service

[Service]
Restart=always
ExecStartPre=-/usr/bin/docker stop nginx-container
ExecStartPre=-/usr/bin/docker rm nginx-container
ExecStart=/usr/bin/docker run --rm --name nginx-container -p 8080:80 nginx
ExecStop=/usr/bin/docker stop nginx-container

[Install]
WantedBy=multi-user.target
```

### Разбор файла юнита

*   **`[Unit]` секция:**
    *   `Requires=docker.service`: Жесткая зависимость. Этот юнит не запустится, если `docker.service` не активен.
    *   `After=docker.service`: Порядок запуска. Этот юнит будет запущен только *после* `docker.service`.

*   **`[Service]` секция:**
    *   `Restart=always`: `systemd` будет всегда пытаться перезапустить контейнер, если он остановился (например, после перезагрузки или в случае ошибки).
    *   `ExecStartPre=-/usr/bin/docker stop ...` и `ExecStartPre=-/usr/bin/docker rm ...`: Эти команды выполняются перед запуском основного процесса. Они останавливают и удаляют контейнер с таким же именем, если он уже существует. Это предотвращает ошибки при перезапуске сервиса.
        *   **Важно:** Знак `-` перед командой означает, что `systemd` проигнорирует ошибку, если команда завершится с ненулевым кодом выхода (например, если контейнера для остановки не существует). Это аналог конструкции `|| true` в shell-скриптах.
    *   `ExecStart=/usr/bin/docker run ...`: Основная команда, которая запускает контейнер.
        *   `--rm`: Флаг, который автоматически удаляет контейнер после его остановки. Это полезно для "одноразовых" контейнеров, но может быть неудобно, если нужно отлаживать остановленный контейнер. В примере выше `ExecStartPre` уже выполняет очистку, поэтому `--rm` можно использовать для дополнительной гарантии.
        *   `--name nginx-container`: Задает имя контейнера, что позволяет легко управлять им в командах `ExecStartPre` и `ExecStop`.
    *   `ExecStop=/usr/bin/docker stop nginx-container`: Команда, которая будет выполнена для остановки сервиса. Она корректно останавливает контейнер.

*   **`[Install]` секция:**
    *   `WantedBy=multi-user.target`: Указывает, что при выполнении `systemctl enable` для этого юнита, он будет добавлен в автозагрузку для стандартного многопользовательского режима.

### Управление сервисом

После создания файла `/etc/systemd/system/nginx-container.service`, управление им осуществляется стандартными командами `systemctl`:

```bash
# Перечитать конфигурацию systemd
sudo systemctl daemon-reload

# Запустить сервис
sudo systemctl start nginx-container.service

# Включить автозапуск при загрузке системы
sudo systemctl enable nginx-container.service

# Проверить статус
systemctl status nginx-container.service
```

**Важно:** Данный подход описывает управление Docker-контейнерами *на хост-системе*. Не следует путать это с попытками запустить `systemd` в качестве PID 1 *внутри* контейнера, что считается анти-паттерном. Подробнее об этой проблеме читайте в документе [Systemd в Docker: почему это анти-паттерн](../../Docker/docker_systemd.md).
