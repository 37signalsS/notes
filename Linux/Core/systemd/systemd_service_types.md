# Типы сервисов в systemd

## Определения

**`Type=`** — это ключевая директива в секции `[Service]` юнит-файла (unit file), которая определяет алгоритм запуска процесса и способ, которым менеджер системных служб `systemd` отслеживает его готовность.

Выбор правильного типа критически важен для корректной работы механизмов зависимостей: `systemd` должен точно знать, когда сервис полностью инициализирован и готов принимать запросы от других служб.

## Основные концепции

### Классификация типов запуска

Директива `Type=` управляет тем, как `systemd` интерпретирует завершение процесса запуска.

| Тип | Описание механизма готовности | Сфера применения |
| :--- | :--- | :--- |
| **`simple`** | (Значение по умолчанию). Считается готовым сразу после выполнения системного вызова `fork()`. | Большинство современных приложений, которые не уходят самостоятельно в фоновый режим. |
| **`exec`** | Аналогичен `simple`, но считается готовым только после успешного выполнения `execve()`. | Позволяет выявлять ошибки (например, отсутствие бинарного файла) до того, как служба будет считаться запущенной. |
| **`forking`** | Готов, когда основной (родительский) процесс завершается, оставляя в памяти дочерний процесс («демона»). | Классические серверные службы (например, `nginx`, `sshd`). |
| **`oneshot`** | Считается активным только после того, как основной процесс полностью завершит свою работу. | Короткоживущие задачи: скрипты настройки системы, миграции БД (База Данных). |
| **`notify`** | Ждет явного сообщения о готовности через сокет (протокол `sd_notify`). | Сложные приложения с длительной инициализацией (например, `postgresql`, `etcd`). |
| **`dbus`** | Считается готовым после регистрации указанного имени на системной шине D-Bus (Desktop Bus). | Системные компоненты, глубоко интегрированные с графической средой или оборудованием. |

### Обязательные требования к типам

* **Для `Type=forking`**: Необходимо использовать директиву `PIDFile=`, чтобы `systemd` мог идентифицировать PID (Process ID) главного процесса после того, как родительский процесс выйдет из памяти.
* **Для `Type=notify`**: Приложение должно поддерживать вызов `sd_notify("READY=1")`.
* **Для `Type=oneshot`**: Рекомендуется использовать `RemainAfterExit=yes`, если вы хотите, чтобы сервис сохранял статус `active` после завершения скрипта (например, чтобы зависимые от него службы могли запуститься).

## Практические сценарии

### Настройка современного приложения (Type=simple)

Подходит для приложений, которые пишут логи в стандартный поток вывода (`stdout`) и управляются напрямую.

```ini
[Service]
Type=simple
ExecStart=/usr/bin/node /opt/app/index.js
Restart=on-failure
```

### Настройка классического демона (Type=forking)

Используется для программ, которые самостоятельно выполняют форк и переводят себя в фоновый режим.

```ini
[Service]
Type=forking
ExecStart=/usr/sbin/my_daemon --daemonize
PIDFile=/run/my_daemon.pid
```

### Сервис с длительной инициализацией (Type=notify)

Гарантирует, что зависимые юниты (units) не начнут старт, пока это приложение не будет полностью функционально.

```ini
[Service]
Type=notify
ExecStart=/usr/local/bin/heavy_app
# Увеличенный таймаут для холодного старта
TimeoutStartSec=300
```

### Выполнение разовой задачи при загрузке (Type=oneshot)

Пример скрипта для предварительного разогрева кэша или проверки структуры каталогов.

```ini
[Service]
Type=oneshot
ExecStart=/usr/local/bin/system_warmup.sh
# Сохранять статус active для удовлетворения зависимостей
RemainAfterExit=yes
```

## Дополнительная информация

### Диагностика типа и состояния процесса

Для проверки того, как ОС (Операционная Система) и `systemd` видят конкретный сервис, используйте утилиту `systemctl`.

```bash
# Проверить текущий тип сервиса
systemctl show nginx.service --property=Type
# → Type=forking

# Узнать идентификатор основного процесса
systemctl show nginx.service --property=MainPID
# → MainPID=1234
```
