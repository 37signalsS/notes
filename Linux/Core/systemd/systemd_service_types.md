# Типы сервисов в systemd

## Определения

* **`Type=`** — ключевая директива секции `[Service]`, определяющая алгоритм запуска процесса и способ, которым `systemd` отслеживает его готовность.
* **Готовность (Readiness)** — состояние юнита, при котором `systemd` считает его успешно запущенным и переходит к активации зависимых служб.
* **sd_notify** — протокол уведомлений, позволяющий приложению сообщать менеджеру системных служб о смене своего состояния (инициализация, перезагрузка, завершение).

## Основные концепции

### Сравнение типов запуска

| Тип | Определение готовности | Обнаружение ошибок старта | Применение |
| :--- | :--- | :--- | :--- |
| **`simple`** | Сразу после `fork()`. | Низкое (считает успех, даже если бинарник не найден). | Простые скрипты, логи в stdout. |
| **`exec`** | (v240+) После `execve()`. | Среднее (упадет, если бинарник отсутствует или нет прав). | Современная замена `simple`. |
| **`forking`** | Когда родительский процесс завершается. | Среднее. | Классические демоны (`nginx`, `sshd`). |
| **`oneshot`** | После завершения главного процесса. | Высокое. | Скрипты настройки, миграции БД. |
| **`notify`** | После получения сигнала `READY=1`. | Максимальное. | Сложные службы (`postgresql`, `docker`). |
| **`notify-reload`** | (v253+) Аналог `notify`. | Максимальное. | Службы с поддержкой нативной перезагрузки. |
| **`dbus`** | После появления имени на шине D-Bus. | Высокое. | Системные компоненты (GNOME, BlueZ). |
| **`idle`** | После выполнения всех активных заданий. | Низкое. | Неприоритетные задачи. |

### Детальный разбор ключевых типов

#### Simple vs Exec
Рекомендуется всегда использовать **`Type=exec`** вместо `simple`. В режиме `exec` менеджер дожидается фактического запуска исполняемого файла. Если файл поврежден или отсутствует, `systemctl start` мгновенно вернет ошибку, тогда как `simple` может ложно отрапортовать об успехе.

#### Notify и Notify-Reload
Это «золотой стандарт» для надежных сервисов. Приложение само сообщает, когда оно закончило прогрев кэшей и открыло порты.
* **`NotifyAccess=`** — управляет правами на отправку уведомлений. Значение `all` необходимо, если вы используете shell-обертку, вызывающую `systemd-notify`.
* **`Type=notify-reload`** (v253+) — избавляет от необходимости прописывать `ExecReload`. Systemd посылает сигнал (SIGHUP) и ждет от приложения `RELOADING=1` → `READY=1`.

#### Oneshot и сохранение состояния
Обычно `oneshot` сервисы переходят в `inactive` сразу после завершения процесса.
* **`RemainAfterExit=yes`** — позволяет юниту оставаться в статусе `active` (exited). Это необходимо, чтобы другие юниты, зависящие от этого (`Requires`, `After`), видели, что задача успешно выполнена.

## Практические сценарии

### Использование уведомлений в shell-скриптах

Если сервис запускается через обертку, используйте `NotifyAccess=all`.

```ini
[Service]
Type=notify
NotifyAccess=all
ExecStart=/usr/local/bin/wrapper.sh
```

**Скрипт `wrapper.sh`**:
```bash
#!/bin/bash
# Предварительная настройка
sleep 2 
# Уведомляем systemd о готовности
systemd-notify --ready --status="Initialized and ready"
# Запускаем основное приложение
exec /usr/bin/myapp
```

### Настройка классического демона (Forking)

Для типов `forking` обязательно наличие PID-файла для корректного мониторинга.

```ini
[Service]
Type=forking
ExecStart=/usr/sbin/my_daemon --daemonize
PIDFile=/run/my_daemon.pid
Restart=on-failure
```

### Разовая задача миграции (Oneshot)

```ini
[Service]
Type=oneshot
ExecStart=/usr/bin/db_migrate
RemainAfterExit=yes
```

## Дополнительная информация

### Диагностика типа и параметров

```bash
# Проверить текущий тип и PID главного процесса
systemctl show my-app.service -p Type -p MainPID
# → Type=notify
# → MainPID=5678

# Проверить итоговый статус и причину остановки
systemctl status my-app.service
# → ● my-app.service - ...
# →    Active: failed (Result: protocol) # Ошибка notify-протокола
```
