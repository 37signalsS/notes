Ядро является центральным компонентом операционной системы, отвечающим за управление процессами, памятью и оборудованием. Подробно о том, как ядро управляет процессами, можно прочитать в документе [processes.md](./processes.md).

## Модули ядра (Kernel Modules)

Модули ядра — это фрагменты кода, которые можно динамически загружать в ядро Linux или выгружать из него по мере необходимости. Они расширяют функциональность работающего ядра, не требуя перезагрузки системы. С помощью модулей реализуются:
-   Драйверы устройств (для видеокарт, сетевых адаптеров, USB-устройств).
-   Драйверы файловых систем (ext4, xfs, btrfs).
-   Сетевые протоколы и многое другое.

### Lazy Loading (Загрузка по требованию)

Ключевой особенностью модульной архитектуры является **Lazy Loading** (ленивая или отложенная загрузка). Это механизм, при котором модули ядра загружаются не при старте системы, а только тогда, когда они действительно необходимы. Это позволяет:
-   **Ускорить загрузку системы:** Ядро остается компактным, загружая только самые необходимые компоненты.
-   **Экономить память:** Модули не занимают RAM, пока не будут вызваны.

Например, модуль для файловой системы `vfat` не будет загружен, пока вы не попытаетесь смонтировать USB-накопитель, отформатированный в FAT32. В этот момент ядро обнаружит необходимость в модуле и автоматически загрузит его.

### Управление модулями

Основной утилитой для управления модулями является `modprobe`.

-   **Просмотреть загруженные модули:**
    ```bash
    lsmod
    ```

-   **Загрузить модуль (и его зависимости):**
    ```bash
    sudo modprobe <имя_модуля>
    # Пример: sudo modprobe vboxdrv
    ```

-   **Выгрузить модуль:**
    ```bash
    sudo modprobe -r <имя_модуля>
    ```

-   **Запретить автоматическую загрузку модуля (blacklist):**
    Чтобы предотвратить загрузку проблемного или ненужного модуля, его можно добавить в "черный список".
    1.  Создайте файл в `/etc/modprobe.d/`, например `blacklist-my.conf`.
    2.  Добавьте в него строку:
        ```
        blacklist <имя_модуля>
        ```
    3.  Обновите initramfs, чтобы изменения применились при следующей загрузке:
        ```bash
        # Для Debian/Ubuntu
        sudo update-initramfs -u
        # Для RHEL/CentOS
        sudo dracut -f -v
        ```

## "Загрязнение" ядра (Kernel Taint)

**Taint-флаг** — это механизм ядра Linux, который указывает на то, что система находится в нестандартном или потенциально нестабильном состоянии.

Состояние флага можно проверить, прочитав специальный файл в `/proc`:

```bash
cat /proc/sys/kernel/tainted
```

-   Если команда возвращает `0`, ядро чистое.
-   Любое другое число указывает на одну или несколько причин "загрязнения".

Также информация о "загрязнении" появляется в логах ядра при сбоях (`dmesg`).

### Основные причины "загрязнения"

-   **`P` (Proprietary Module):** Загружен проприетарный (не-GPL) модуль, например, драйвер NVIDIA.
-   **`F` (Forcefully Loaded):** Модуль был загружен принудительно (`insmod -f`).
-   **`G` (Staging Driver):** Загружен драйвер из ветки `staging` — экспериментальный код.
-   **`W` (Warning):** Ядро выдало предупреждение (например, `WARN_ONCE`).
-   **`O` (Out-of-tree Module):** Загружен модуль, который не является частью официального дерева исходного кода ядра.
-   **`M` (Machine Check Error):** Произошёл аппаратный сбой, зафиксированный процессором.

## Обновление ядра без перезагрузки

В средах, требующих максимального времени безотказной работы (uptime), перезагрузка для обновления ядра может быть неприемлема. Существуют технологии, позволяющие применять обновления безопасности "на лету".

1.  **`kpatch` и `ksplice` (Live Patching):**
    -   **Как работает:** Эти инструменты применяют патчи к работающему ядру прямо в памяти. Они перенаправляют вызовы старых, уязвимых функций на новые, исправленные версии, не останавливая работу системы.
    -   **Назначение:** В основном используется для критических обновлений безопасности.
    -   **Применение:** `kpatch` (разработан Red Hat) и `ksplice` (разработан Oracle) являются коммерческими или поддерживаемыми производителями решениями.

2.  **`kexec`:**
    -   **Как работает:** `kexec` — это системный вызов, который позволяет загрузить новое ядро непосредственно из текущего, минуя BIOS/UEFI и аппаратную инициализацию. Это не "живой патч", а скорее "быстрая перезагрузка" в новое ядро.
    -   **Преимущества:** Значительно сокращает время простоя по сравнению с полной перезагрузкой, так как пропускается долгий этап POST.
    -   **Использование:**
        ```bash
        # Загрузить новое ядро и initramfs в память
        sudo kexec -l /boot/vmlinuz-новое-ядро --initrd=/boot/initrd.img-новое-ядро --reuse-cmdline

        # Выполнить "перезагрузку"
        sudo kexec -e
        ```

## Интерфейсы ядра для пространства пользователя

### seq_file API

**seq_file** (sequential file) — это интерфейс ядра Linux, предназначенный для упрощения вывода больших объемов последовательных данных из ядра в пространство пользователя, чаще всего через виртуальные файловые системы, такие как `/proc` или `/sys`.

**Проблема, которую решает `seq_file`:**
До появления `seq_file` разработчикам драйверов и модулей ядра приходилось вручную управлять буфером для вывода данных. Это было сложно и приводило к ошибкам:
-   Нужно было выделять большой буфер в памяти ядра, рискуя его переполнить.
-   Требовалось вручную отслеживать смещение (offset) при чтении, чтобы пользовательские приложения могли читать данные по частям.
-   Возникали состояния гонки (race conditions) при одновременном доступе к изменяющимся данным.

**Как `seq_file` решает эти проблемы:**
`seq_file` предоставляет простой и безопасный итераторный механизм:
1.  **Последовательная генерация:** Данные генерируются "на лету" небольшими порциями (чанками) по мере их запроса из пространства пользователя.
2.  **Автоматическое управление буфером и смещением:** API само управляет выделением временного буфера и отслеживает, какая часть данных уже была прочитана, избавляя разработчика от ручной работы.
3.  **Экономия памяти:** Вместо выделения огромного буфера под все данные сразу, `seq_file` использует небольшой буфер для генерации очередной порции, что эффективно с точки зрения использования памяти.
4.  **Потокобезопасность:** Предоставляет механизмы для безопасного доступа к структурам данных ядра во время итерации.

**Пример использования:**
Когда вы выполняете `cat /proc/meminfo`, ядро использует `seq_file` для итерации по своим внутренним структурам данных о памяти и форматирует их в виде текста, который вы видите в терминале.

## Управление параметрами ядра с помощью `sysctl`

`sysctl` — это утилита, которая позволяет просматривать и изменять параметры ядра Linux "на лету", без необходимости перезагрузки. Эти параметры управляют поведением различных подсистем, таких как сеть, виртуальная память и файловая система.

**Основные команды:**

-   **Просмотреть все доступные параметры:**
    ```bash
    sudo sysctl -a
    ```

-   **Прочитать значение конкретного параметра:**
    ```bash
    sudo sysctl vm.swappiness
    ```

-   **Изменить значение параметра временно (до перезагрузки):**
    ```bash
    sudo sysctl -w vm.swappiness=10
    ```

**Сохранение параметров:**

Чтобы изменения сохранялись после перезагрузки, их необходимо записать в файл `/etc/sysctl.conf` или в отдельный файл в директории `/etc/sysctl.d/`.

1.  **Отредактируйте файл:**
    ```
    # /etc/sysctl.conf
    vm.swappiness = 10
    net.ipv4.ip_forward = 1
    ```

2.  **Примените изменения:**
    ```bash
    sudo sysctl -p
    ```

## Изоляция CPU (isolcpus)

`isolcpus` — это параметр загрузки ядра Linux, который позволяет "изолировать" один или несколько процессоров (ядер) от планировщика задач общего назначения.

### Зачем это нужно?

Когда ядро изолирует CPU, оно перестает автоматически размещать на нем обычные пользовательские процессы и большинство потоков ядра. Это ядро остается "чистым" и свободным для выполнения только тех задач, которые были явно к нему привязаны.

Основная цель — устранить "шум" и непредсказуемые задержки (jitter), вызванные переключениями контекста, прерываниями и другими фоновыми задачами.

**Основные сценарии использования:**
-   **Приложения реального времени (Real-time):** Где требуется гарантированное время отклика без задержек.
-   **Высокопроизводительные вычисления (HPC):** Для научных или финансовых расчетов, где каждый цикл CPU на счету.
-   **Сетевые приложения с низкой задержкой:** Например, для обработки большого количества пакетов в секунду.
-   **Виртуализация:** Выделение эксклюзивных ядер для виртуальных машин.

### Как это работает

Параметр `isolcpus` передается ядру во время загрузки через конфигурацию загрузчика (например, GRUB).

**Пример конфигурации в `/etc/default/grub`:**
```
# Изолировать ядра 2 и 3
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash isolcpus=2,3"
```
После изменения конфигурации необходимо обновить GRUB (`sudo update-grub`) и перезагрузить систему.

После загрузки с этим параметром, планировщик не будет использовать ядра 2 и 3 для обычных задач. Чтобы запустить на них критически важное приложение, необходимо явно привязать его к этим ядрам с помощью утилит, таких как `taskset` или `numactl`.

```bash
# Запустить my_app на изолированном ядре 2
taskset -c 2 ./my_app
```

## Прерывания: Hard IRQ, SoftIRQ и Tasklets

Прерывания — это сигналы от аппаратного или программного обеспечения, которые требуют немедленного внимания процессора. В Linux они делятся на два основных уровня для эффективной обработки.

### 1. Аппаратные прерывания (Hard IRQ)

-   **Что это:** Прямые сигналы от оборудования (сетевой карты, дискового контроллера, клавиатуры).
-   **Задача обработчика (ISR - Interrupt Service Routine):** Выполнить абсолютно минимальную, критически важную работу (например, скопировать данные из буфера сетевой карты в RAM), отключив на это время другие прерывания. Эта работа должна быть максимально быстрой, чтобы не блокировать систему.
-   **Проблема:** Длительная работа в контексте Hard IRQ парализует систему.

### 2. Программные прерывания (SoftIRQ)

`SoftIRQ` (Software Interrupt Request) — это механизм ядра для выполнения "отложенной" работы, которая была инициирована аппаратным прерыванием, но не является настолько срочной.

**Как это работает:**
1.  Обработчик Hard IRQ выполняет свою быструю задачу.
2.  Перед завершением он помечает, что необходимо выполнить соответствующий `SoftIRQ`.
3.  Ядро запускает обработчики `SoftIRQ` в более подходящий момент, когда прерывания уже включены и система не заблокирована.

**Зачем это нужно:**
-   **Разгрузка Hard IRQ:** Позволяет минимизировать время, в течение которого система не реагирует на другие аппаратные прерывания.
-   **Эффективность:** Обработка `SoftIRQ` происходит в контексте ядра, но без жестких ограничений Hard IRQ, что является компромиссом между скоростью и отзывчивостью системы.

**Основные пользователи `SoftIRQ`:**
-   **Сетевая подсистема:** Обработка входящих сетевых пакетов.
-   **Планировщик задач:** Управление процессами.
-   **Таймеры ядра.**

Высокое значение `si` в выводе `top` или `htop` указывает на интенсивную работу `SoftIRQ`, что часто связано с высокой сетевой нагрузкой.

### Tasklets

Tasklet — это еще один, более простой механизм отложенной обработки, построенный поверх `SoftIRQ`. Основное отличие в том, что однотипные тасклеты всегда выполняются последовательно (не могут выполняться параллельно на разных CPU), что упрощает их написание, так как не требуется сложная синхронизация.

## Вытесняющая многозадачность (Preemption) в ядре

**Kernel Preemption** (вытеснение в ядре) — это механизм, который позволяет ядру Linux прервать выполнение текущей задачи (даже если она находится в режиме ядра), чтобы отдать процессор более высокоприоритетной задаче.

### Зачем это нужно?

В ранних версиях ядра, если процесс делал системный вызов и переходил в режим ядра, он не мог быть вытеснен, пока не завершит свою работу в ядре или не уйдет в спящий режим добровольно. Это могло приводить к большим задержкам (latency) для высокоприоритетных процессов, которые были вынуждены ждать.

Вытесняемое ядро решает эту проблему, позволяя планировщику "вклиниться" и запустить более важную задачу.

-   **Преимущество:** Значительно улучшает **отзывчивость (responsiveness)** системы и предсказуемость времени отклика. Критически важно для десктопных систем и систем реального времени.
-   **Недостаток:** Увеличивает накладные расходы из-за более частых переключений контекста, что может незначительно снизить общую **пропускную способность (throughput)** системы.

### Модели вытеснения

При компиляции ядра Linux можно выбрать одну из нескольких моделей вытеснения:

1.  **No Forced Preemption (Server):** Невытесняемое ядро. Задача в режиме ядра выполняется до своего завершения или добровольной блокировки. Оптимизировано для максимальной пропускной способности, подходит для серверных нагрузок, где задержки не так критичны.
2.  **Voluntary Kernel Preemption (Desktop):** Ядро проверяет необходимость вытеснения в определенных, "безопасных" точках своего кода. Это компромисс между пропускной способностью и отзывчивостью.
3.  **Preemptible Kernel (Low-Latency Desktop):** Полностью вытесняемое ядро. Прерывание может произойти практически в любой момент. Обеспечивает наилучшую отзывчивость и минимальные задержки.

## Pressure Stall Information (PSI): Мониторинг "давления" на ресурсы

**Pressure Stall Information (PSI)** — это механизм ядра Linux, который позволяет отслеживать "давление" на ключевые системные ресурсы: CPU, память и ввод-вывод (I/O). В отличие от традиционных метрик загрузки (например, CPU utilization), PSI показывает, сколько времени процессы **потеряли** из-за нехватки ресурсов.

Это позволяет выявить узкие места в производительности до того, как ситуация станет критической (например, до срабатывания OOM Killer или полного "зависания" системы).

### Как это работает

PSI не измеряет загрузку напрямую. Вместо этого он измеряет **"stall time"** — время, в течение которого один или несколько процессов не могли выполняться, потому что ждали доступа к ресурсу.

-   **Давление на память:** Процессы ждут, пока ядро освободит память.
-   **Давление на CPU:** Процессов, готовых к выполнению, больше, чем доступных ядер.
-   **Давление на I/O:** Процессы ждут завершения операций ввода-вывода.

### Как использовать PSI

Информация доступна через файлы в `/proc/pressure/`:

```bash
# Показать "давление" на CPU
cat /proc/pressure/cpu

# Показать "давление" на память
cat /proc/pressure/memory

# Показать "давление" на ввод-вывод
cat /proc/pressure/io
```

Каждый файл содержит строки `some` и `full`, которые показывают процент времени за последние 10, 60 и 300 секунд, в течение которого **хотя бы один** (`some`) или **все** не-idle процессы (`full`) были заблокированы из-за нехватки данного ресурса.

Высокие значения в `some` указывают на потерю пропускной способности, а в `full` — на серьезное насыщение ресурса.

## Планировщик ввода-вывода (I/O Scheduler)


**Планировщик ввода-вывода (I/O Scheduler)** — это компонент ядра Linux, который управляет порядком выполнения запросов на чтение и запись для блочных устройств (HDD, SSD). Его основная задача — оптимизировать дисковые операции для достижения различных целей: минимизации задержек, обеспечения справедливости между процессами или максимизации пропускной способности.

Выбор правильного планировщика критически важен для производительности системы, особенно для баз данных и файловых серверов.

### Основные типы планировщиков

Современные ядра Linux предлагают несколько планировщиков, каждый со своими особенностями:

1.  **`none` (ранее `noop`)**:
    -   **Принцип работы:** Самый простой планировщик. Он просто помещает все входящие запросы в очередь FIFO (First-In, First-Out) и не выполняет никакой сортировки или переупорядочивания.
    -   **Когда использовать:** Идеально подходит для быстрых устройств, которые не выигрывают от сложной логики планирования, таких как NVMe SSD и другие устройства с очень низкими задержками. Также хорош для виртуализированных сред, где планирование выполняется на уровне гипервизора.

2.  **`mq-deadline`**:
    -   **Принцип работы:** Гарантирует, что ни один запрос не будет "голодать" слишком долго. Каждому запросу назначается максимальное время ожидания (дедлайн). Планировщик отдает приоритет запросам, чей дедлайн истекает.
    -   **Когда использовать:** Хороший выбор для систем с базами данных (например, PostgreSQL, MySQL), где важны предсказуемые и низкие задержки для операций чтения.

3.  **`bfq` (Budget Fair Queueing)**:
    -   **Принцип работы:** Сложный планировщик, ориентированный на обеспечение справедливости и низкой задержки для интерактивных приложений. Он выделяет каждому процессу "бюджет" на количество дисковых операций.
    -   **Когда использовать:** Отлично подходит для десктопных систем и для смешанных нагрузок, где важна отзывчивость интерфейса. Для серверных нагрузок может создавать дополнительные накладные расходы.

4.  **`kyber`**:
    -   **Принцип работы:** Относительно новый планировщик, разработанный для очень быстрых устройств (NVMe). Он пытается достичь целевых задержек для запросов, динамически подстраивая свою агрессивность.
    -   **Когда использовать:** На современных серверах с NVMe-накопителями.

### Управление планировщиком

-   **Проверить текущий планировщик для устройства `sda`:**
    Активный планировщик указан в квадратных скобках.
    ```bash
    cat /sys/block/sda/queue/scheduler
    # Вывод: [mq-deadline] kyber bfq none
    ```

-   **Изменить планировщик временно (до перезагрузки):**
    ```bash
    # Установить планировщик 'none' для sda
    echo none | sudo tee /sys/block/sda/queue/scheduler
    ```

-   **Изменить планировщик постоянно (с помощью `udev`):**
    Чтобы изменение сохранялось после перезагрузки, можно создать правило `udev`.
    1.  Создайте файл `/etc/udev/rules.d/60-io-schedulers.rules`.
    2.  Добавьте в него строку:
        ```
        ACTION=="add|change", KERNEL=="sd[a-z]", ATTR{queue/scheduler}="mq-deadline"
        ```
    Это правило будет применять планировщик `mq-deadline` ко всем дискам `sd*`.

## io_uring: Высокопроизводительный асинхронный I/O

**io_uring** — это современный интерфейс для асинхронного ввода-вывода (I/O) в ядре Linux (появился в ядре 5.1). Он был разработан как высокопроизводительная альтернатива старым моделям (таким как `epoll` и `AIO`) с целью минимизировать накладные расходы на системные вызовы.

### Как это работает: Кольцевые буферы

В отличие от традиционного подхода, где для каждой операции I/O требуется системный вызов, `io_uring` использует общую память между приложением и ядром для пакетной обработки запросов.

1.  **Создаются две кольцевые очереди (ring buffers):**
    -   **Submission Queue (SQ):** Очередь для отправки запросов. Приложение помещает в нее одну или несколько операций (например, "прочитать файл", "отправить пакет по сети").
    -   **Completion Queue (CQ):** Очередь для получения результатов. Ядро асинхронно выполняет операции из SQ и помещает результаты (статус завершения, количество прочитанных байт) в CQ.

2.  **Минимум системных вызовов:** Приложение может добавить в очередь множество операций и затем сделать всего **один** системный вызов, чтобы уведомить ядро о необходимости их обработки. После этого оно может забрать результаты из очереди завершения, также минимизируя переключения контекста.

### Преимущества

-   **Высокая производительность и низкая задержка:** Значительно сокращается количество дорогостоящих переключений между пространством пользователя и ядром.
-   **Настоящая асинхронность:** Позволяет эффективно выполнять большое количество одновременных операций I/O.
-   **Универсальность:** В отличие от `epoll`, который работает только с сетевыми сокетами, `io_uring` поддерживает не только сетевой и дисковый I/O, но и множество других системных вызовов (например, `openat`, `statx`, `accept`).

## Синхронизация и параллелизм в ядре

### Lock-free / Lockless Programming

**Lockless programming** — это подход к написанию кода для многопоточных систем, который избегает использования традиционных блокировок (таких как мьютексы или спинлоки) для синхронизации доступа к общим ресурсам. Вместо блокировки потока, ожидающего доступа, используются другие механизмы, которые не останавливают выполнение.

**Зачем это нужно в ядре?**
В ядре Linux производительность и отзывчивость критически важны. Традиционные блокировки могут приводить к проблемам:
-   **Инверсия приоритетов:** Высокоприоритетная задача может простаивать, ожидая, пока низкоприоритетная задача освободит блокировку.
-   **Deadlocks (взаимоблокировки):** Два или более потока могут бесконечно ожидать друг друга, чтобы освободить ресурсы.
-   **Снижение производительности:** На многоядерных системах постоянные блокировки и разблокировки создают большие накладные расходы.

**Основные механизмы Lock-free:**

1.  **Атомарные операции:** Это операции (например, инкремент, сравнение с обменом), которые выполняются как единое, неделимое действие. Процессор гарантирует, что никакая другая операция не сможет вмешаться в их выполнение. Они являются строительными блоками для более сложных lock-free алгоритмов.

2.  **Барьеры памяти (Memory Barriers):** Инструкции, которые говорят компилятору и процессору не переупорядочивать операции с памятью. Это гарантирует, что другие ядра увидят изменения в памяти в правильном, предсказуемом порядке.

3.  **RCU (Read-Copy-Update):** Один из самых мощных lock-free механизмов в ядре Linux, оптимизированный для сценариев, где чтений гораздо больше, чем записей (например, в сетевых подсистемах или при кэшировании записей файловой системы - dentry cache).

    *   **Чтение (Read):** Читатели получают доступ к данным абсолютно без каких-либо блокировок, что делает операции чтения очень быстрыми.
    *   **Запись (Update):** Когда потоку-писателю нужно изменить данные, он создает их копию, вносит изменения в эту копию и затем атомарно меняет указатель на общие данные, чтобы он указывал на новую, измененную версию.
    *   **Освобождение (Copy):** Самый сложный этап. Старая версия данных не может быть освобождена немедленно, так как другие читатели все еще могут ее использовать. Писатель ждет так называемый "период благодати" (grace period) — это интервал времени, за который все читатели, начавшие работу до обновления указателя, гарантированно завершат свои операции. Только после этого старая копия данных безопасно удаляется.

Этот подход позволяет множеству читателей работать параллельно и без задержек, в то время как писатель выполняет обновление.

## Kernel Panic: анализ и отладка

**Kernel Panic** — это критическая, невосстановимая ошибка ядра операционной системы, при которой оно не может безопасно продолжать работу. Система останавливается для предотвращения дальнейшего повреждения данных.

**Анализ сбоев (`crash dumps`):**
Для анализа причин Kernel Panic используется механизм `kdump`. Он работает, загружая второе, минимальное ядро (`crashkernel`) в зарезервированную область памяти. Когда основное ядро падает, управление передаётся `crashkernel`, которое сохраняет образ памяти (дамп) основного ядра на диск.

**Процесс анализа:**

1.  **Настройка `kdump`:** Убедитесь, что `kdump` установлен и сервис активен (`systemctl is-active kdump`).
2.  **Анализ дампа:** После перезагрузки сохранённый дамп (обычно в `/var/crash/`) можно проанализировать с помощью утилиты `crash`.
3.  **Просмотр логов:** Первичную информацию о панике часто можно найти в системных логах до перезагрузки:
    ```bash
    # Логи ядра с последней загрузки
    journalctl -k -b -1
    # или
    dmesg -T
    ```

## Инструмент: `dmesg`

`dmesg` (display message) — это утилита для просмотра сообщений из кольцевого буфера ядра. Она незаменима для диагностики проблем с оборудованием и драйверами, особенно во время загрузки системы.

-   **Человекочитаемый вывод с постраничной навигацией:**
    ```bash
    dmesg -H
    ```

-   **Читаемый формат времени:**
    ```bash
    dmesg -T
    ```

-   **Показать уровень (приоритет) сообщений:**
    ```bash
    dmesg -x
    ```

-   **Вывод в реальном времени (следить за новыми сообщениями):**
    ```bash
    dmesg -w
    ```

-   **Комбинация полезных флагов (читаемое время, постраничный просмотр, уровни):**
    ```bash
    dmesg -HTx
    ```

-   **Очистить буфер `dmesg` (требует прав `root`):**
    ```bash
    sudo dmesg -C
    ```

В современных системах с `systemd` логи ядра также собираются в `journald` и доступны через команду `journalctl -k` или `journalctl --dmesg`.
