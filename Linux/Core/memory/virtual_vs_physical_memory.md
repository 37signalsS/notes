# Виртуальная и физическая память

## Определения

* **Физическая память (RAM)**: Аппаратные чипы на материнской плате, используемые процессором для выполнения кода и хранения данных.
* **Виртуальная память**: Абстракция операционной системы, предоставляющая каждому процессу изолированное адресное пространство. Процессы используют виртуальные адреса, которые аппаратура (MMU) и ядро преобразуют в физические.
* **Страница (Page)**: Минимальная единица управления памятью. По умолчанию в Linux — 4 КБ. Изменяется через `getconf PAGESIZE`.
* **Page Fault (ошибка страницы)**: Исключение от MMU при обращении к виртуальной странице, которой ещё нет в физической памяти. Бывает двух типов:
  * **Minor (мягкий)**: страница уже в RAM, но не отображена в таблицу страниц процесса. Обрабатывается быстро, без I/O.
  * **Major (жёсткий)**: страница отсутствует в RAM и загружается с диска (из swap или файлового кэша). Вызывает задержки.
* **Анонимные страницы**: Страницы, не связанные с файлом на диске (стек, куча, `malloc`). При нехватке RAM выгружаются в [swap](./swap_management.md).
* **File-backed страницы**: Страницы, отображённые на файл (код библиотек, mmap). При нехватке RAM просто удаляются из памяти — их можно перечитать с диска.

## Основные концепции

### Адресное пространство процесса

Каждый процесс в Linux при запуске получает **виртуальное адресное пространство**, разделённое на сегменты:

```
  ┌─────────────────────┐  ← 0xFFFFFFFF... (kernel space)
  │   Ядро (kernel)     │  — общее для всех процессов
  ├─────────────────────┤
  │       Стек          │  — растёт вниз
  │       ↓             │
  │                     │
  │       ↑             │
  │       Куча (heap)   │  — растёт вверх (malloc/brk/mmap)
  ├─────────────────────┤
  │  Сегмент данных     │  — инициализированные и BSS переменные
  ├─────────────────────┤
  │  Сегмент кода (.text)│ — машинные инструкции программы
  └─────────────────────┘  ← 0x0
```

**Ключевые моменты:**

* **Разделение kernel/userspace**: Верхняя часть адресного пространства зарезервирована за ядром. Процесс не имеет к ней прямого доступа.
* **Куча растёт вверх, стек — вниз**: Между ними остаётся свободное пространство, которое может быть использовано динамически.
* **mmap-области**: Произвольные отображения файлов или анонимной памяти, размещаемые между кучей и стеком.

### Механизм работы

1. **Таблицы страниц (Page Tables)**: Для каждого процесса ядро хранит карту соответствия виртуальных страниц их физическому расположению:
    * В физической памяти (ОЗУ).
    * В пространстве подкачки ([swap](./swap_management.md)) на диске.
    * Не выделена (память зарезервирована через `malloc`, но ещё не использована — физической памяти пока не потребляет).
2. **MMU (Memory Management Unit)**: Аппаратный блок процессора, преобразующий виртуальные адреса в физические с использованием таблиц страниц. Для ускорения MMU использует кэш **TLB (Translation Lookaside Buffer)**.
3. **Кэш TLB**: Хранит последние трансляции «виртуальный → физический». При попадании (TLB hit) адресация мгновенна. При промахе (TLB miss) — дорогой обход таблиц страниц. Использование [HugePages](./performance_tuning.md) снижает давление на TLB.

### Ключевые преимущества

* **Изоляция процессов**: Каждый процесс изолирован в своём виртуальном адресном пространстве, что предотвращает конфликты памяти между процессами.
* **Эффективное использование ОЗУ**: Общие библиотеки загружаются в физическую память однократно, а их страницы отображаются (через Copy-on-Write) в виртуальные пространства всех использующих их процессов.
* **Использование памяти сверх объёма ОЗУ**: Неактивные страницы могут быть выгружены в swap, освобождая ОЗУ для активных задач.

### Что происходит, когда в таблице страниц «нет места»

Термин «нет места в таблице страниц» может означать два принципиально разных сценария: **исчерпание TLB** (аппаратный кэш трансляций) и **нехватка RAM под сами page table entries**.

### Сценарий 1: TLB Miss — кэш трансляций переполнен

**TLB (Translation Lookaside Buffer)** — это крошечный (обычно 64–1024 записи), но крайне быстрый кэш внутри процессора. Он хранит последние трансляции «виртуальный → физический». Когда TLB заполнен и нужной записи нет — происходит **TLB miss**.

**Цепочка событий при TLB miss:**

1. MMU не находит запись в TLB.
2. Процессор выполняет **page table walk** — последовательный обход 4-уровневой иерархии таблиц страниц в RAM:
   ```
   CR3 → PGD → PUD → PMD → PTE → физический адрес
   ```
3. Каждый уровень — обращение к RAM. Без кэширования это **4×100+ наносекунд** задержки вместо 1–2 нс при TLB hit.
4. Найденная запись загружается в TLB, вытесняя самую «старую» запись (LRU).

**Последствия при массовом TLB miss:**

| Симптом | Причина |
| :--- | :--- |
| CPU не упирается в 100%, но производительность падает | Процессор тратит циклы на page table walk вместо полезной работы |
| Рост `dTLB-load-misses` в `perf stat` | Прямое подтверждение TLB pressure |
| Падение IPC (instructions per cycle) | Меньше инструкций выполняется за такт из-за простоев |
| Латентность растёт при увеличении числа потоков | Каждый поток «вымывает» записи TLB другого потока |

**Диагностика:**

```bash
# Проверка TLB miss rate
perf stat -e dTLB-load-misses,dTLB-loads,iTLB-load-misses,iTLB-loads -a sleep 10

# Если miss rate > 1-5% — есть проблема
# dTLB-load-misses / dTLB-loads → процент промахов
```

**Решение — HugePages:**

Обычная страница = 4 КБ → 1 запись TLB покрывает 4 КБ.
HugePage = 2 МБ → 1 запись TLB покрывает **2 МБ** (в 512 раз больше).

Использование HugePages радикально снижает количество записей в TLB:

```bash
# Проверка текущего использования HugePages
cat /proc/meminfo | grep -i huge

# Выделение 1024 HugePages по 2 МБ
sudo sysctl -w vm.nr_hugepages=1024
```

Подробнее о настройке HugePages — в [Оптимизации и тонкой настройке памяти](./performance_tuning.md).

### Сценарий 2: Нехватка RAM под сами page table entries

Каждая запись в таблице страниц (PTE — Page Table Entry) занимает **8 байт** (64-бит). Иерархия для одного процесса:

| Уровень | Размер | Сколько записей | Память |
| :--- | :--- | :--- | :--- |
| **PGD** (Page Global Directory) | 1 страница (4 КБ) | 512 | 4 КБ |
| **PUD** (Page Upper Directory) | 512 × 4 КБ | 512² = 262 144 | ~2 МБ |
| **PMD** (Page Middle Directory) | 512² × 4 КБ | 512³ | ~1 ГБ |
| **PTE** (Page Table Entry) | 512³ × 4 КБ | 512⁴ | до 512 ГБ |

На практике ядро аллоцирует таблицы **лениво** — только при первом обращении к странице. Но при огромном VSS процесса (сотни ГБ) или тысячах процессов с большим адресным пространством, **сами таблицы страниц потребляют гигабайты RAM**.

**Последствия:**

| Симптом | Причина |
| :--- | :--- |
| `free` показывает мало RAM, но RSS процессов суммарно невелик | RAM потребляют page tables (невидимы в RSS) |
| `SUnreclaim` в `/proc/meminfo` растёт | Page tables = неосвобождаемая память ядра |
| OOM Killer срабатывает «без причины» | Пользовательские процессы «не виноваты», но RAM съели их page tables |
| `kswapd` активно работает, но не освобождает page tables | Page tables = `SUnreclaim`, не подлежат освобощению |

**Диагностика:**

```bash
# Сколько RAM потребляют page tables
cat /proc/meminfo | grep -i pagetables
# Pagetables:      125824 kB

# Детальная разбивка Slab (page tables часть SUnreclaim)
cat /proc/meminfo | grep -E 'Slab|SReclaimable|SUnreclaim'

# Page tables конкретного процесса
grep Pgtables /proc/<PID>/status
# Pgtables:  2048 kB

# Суммарно по всем процессам
awk '/^Pgtables:/ {sum += $2} END {print sum, "kB"}' /proc/*/status 2>/dev/null
```

**Почему page tables нельзя просто «освободить»:**

Page tables — это **SUnreclaimable** память ядра. Они не выгружаются в swap, не удаляются shrinker-ами. Единственный способ освободить RAM, занятую page tables:

1. **Завершить процесс** — его page tables освобождаются целиком.
2. **munmap** — процесс сам освобождает отображённые области, ядро удаляет соответствующие PTE.
3. **HugePages** — одна запись PMD (2 МБ) заменяет 512 записей PTE (4 КБ каждая), экономя ~4 КБ RAM на каждый 2 МБ блок.

**Решения:**

| Проблема | Решение |
| :--- | :--- |
| Один процесс с огромным VSS | Использовать HugePages для рабочих данных |
| Тысячи контейнеров с mmap | Ограничить `memory.max` в cgroups |
| Фрагментированные аллокации | Кастомный аллокатор (`jemalloc`/`tcmalloc`) |
| Ненужные mmap-области | Аудит приложения — убрать лишние `mmap` |

### Как ядро выделяет память процессам

#### Резервирование (Virtual Allocation)

Когда процесс вызывает `malloc(n)`, ядро **резервирует** виртуальное адресное пространство, но **не выделяет физическую память**. Это называется **demand paging** — «выделение по требованию».

```c
char *p = malloc(1024 * 1024 * 100);  // Запросили 100 МБ
// Физическая память: 0 байт использовано
```

Методы резервирования:

* **`brk`/`sbrk`**: Сдвигают границу кучи (heap). Для небольших аллокаций.
* **`mmap`**: Отображает анонимную область или файл. Для крупных аллокаций (>128 КБ в glibc).

#### Фактическое выделение (Page Fault + Physical Allocation)

Физическая память выделяется только при **первом обращении** к зарезервированной странице:

1. Процесс читает или записывает `p[0]`.
2. MMU обнаруживает, что страница не отображена в физическую память → **minor page fault**.
3. Ядро находит свободную страницу в RAM, обнуляет её, обновляет таблицу страниц процесса.
4. Процесс продолжает работу — теперь адрес валиден.

Именно поэтому VSS процесса может быть 10 ГБ, а RSS — 50 МБ: большая часть памяти зарезервирована, но не затребована физически.

#### Copy-on-Write (CoW) для форков

При вызове `fork()` ядро **не копирует** память родителя. Вместо этого страницы родителя и ребёнка помечаются как **copy-on-write** — общие, доступные только для чтения.

* Пока процессы только читают — они используют одни и те же физические страницы.
* Когда один из процессов делает запись → возникает page fault → ядро создаёт приватную копию этой страницы для записывающего процесса.

Это обеспечивает быстрое создание процессов и экономию RAM.

#### Обратное давление (Memory Reclaim)

Когда свободная RAM заканчивается, ядро запускает демона **`kswapd`**, который освобождает память в порядке приоритета:

1. **Сброс чистого файлового кэша** (page cache) — мгновенно, страницы просто удаляются.
2. **Запись «грязных» страниц** (dirty pages) на диск, затем освобождение.
3. **Выгрузка анонимных страниц в swap** — самый медленный вариант.
4. **OOM Killer** — если RAM и swap исчерпаны, ядро убивает процесс с наихудшим «score».

Подробнее о работе reclaim и кэширования — в [кэшировании и освобождении памяти](caching_and_reclaiming.md).

### Сравнение физической и виртуальной памяти

| Характеристика          | Физическая память (RAM)     | Виртуальная память                  |
| :---------------------- | :-------------------------- | :---------------------------------- |
| **Что это?**            | Реальные аппаратные чипы.   | Абстракция, создаваемая ОС.         |
| **Скорость**            | Очень высокая.              | Мгновенна при TLB hit, медленнее при page fault. |
| **Размер**              | Ограничен объёмом ОЗУ.      | Ограничен архитектурой (64-бит = огромное пространство). |
| **Доступ**              | Прямой доступ имеет только ядро. | Процессы работают с виртуальными адресами. |
| **Потребление**         | Потребляется при первом обращении. | Резервируется при `malloc`/`mmap`. |

### Проверка размера страницы

Размер страницы по умолчанию (обычно 4 КБ) можно узнать командой:

```bash

# 4096
```

Знание размера страницы полезно для анализа производительности и работы с [HugePages](./performance_tuning.md).

## Дополнительная информация

### Чрезмерное выделение памяти (Memory Overcommit)

Процесс может запросить больше виртуальной памяти, чем есть в системе — это штатный режим Linux, называемый **memory overcommit**.

Ключевой принцип: **`malloc()` ≠ потребление RAM**. При `malloc(100GB)` на системе с 16 ГБ RAM ядро лишь резервирует адресное пространство (VSS растёт). Физическая память не выделяется — только при первом обращении к странице (demand paging). Если процесс реально затронет все 100 ГБ → ядро начнёт искать свободную RAM → swap → **OOM Killer**.

Подробнее о режимах `vm.overcommit_memory` и рекомендациях — в [Оптимизации и тонкой настройке памяти](./performance_tuning.md).
