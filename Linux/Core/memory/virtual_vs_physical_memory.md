# Виртуальная и физическая память в Linux

## Определения

* **Физическая память (RAM)**: Аппаратный ресурс (модули оперативной памяти), организованный в виде набора пронумерованных байтов. Минимальная единица управления — **Frame** (физический кадр).
* **Виртуальная память**: Уровень абстракции, предоставляющий каждому процессу иллюзию владения непрерывным, изолированным адресным пространством (Virtual Address Space), размер которого ограничен только разрядностью архитектуры.
* **MMU (Memory Management Unit)**: Аппаратный блок процессора, выполняющий преобразование виртуальных адресов в физические «на лету» при каждом обращении к памяти.
* **Страница (Page)**: Минимальный блок виртуальной памяти (стандарт — 4 КБ). Соответствующий блок в физической памяти называется **Frame** (кадр).
* **Таблицы страниц (Page Tables)**: Иерархические структуры данных в RAM, описывающие отображение виртуальных страниц на физические кадры. Каждый элемент таблицы называется **PTE** (Page Table Entry).
* **TLB (Translation Lookaside Buffer)**: Специализированный аппаратный кэш внутри CPU, хранящий результаты последних трансляций адресов для минимизации обращений к RAM.
* **ASLR (Address Space Layout Randomization)**: Технология безопасности, рандомизирующая базовые адреса сегментов процесса (стек, куча, библиотеки) для затруднения эксплуатации уязвимостей.
* **VMA (Virtual Memory Area)**: Диапазон виртуального адресного пространства с едиными правами доступа и происхождением (например, сегмент кода библиотеки, анонимная куча, стек).
* **mmap()**: Системный вызов для отображения файлов или устройств в адресное пространство процесса, а также для выделения анонимной памяти.
* **brk()/sbrk()**: Системные вызовы для управления границей кучи (heap) процесса. `brk()` устанавливает конечный адрес сегмента данных.
* **Zero Page**: Страница, заполненная нулями, используемая ядром для ленивого выделения памяти при первом обращении к анонимным страницам (экономит физическую память).
* **vmalloc**: Механизм ядра для выделения больших непоследовательных областей виртуальной памяти (используется драйверами для ядерных структур).
* **kmap**: Механизм для временного отображения высоких адресов физической памяти (HighMem) в адресное пространство ядра (на 32-битных системах).

## Основные концепции

### Иерархия таблиц страниц

Для экономии памяти ядро использует многоуровневые таблицы. В архитектуре x86_64 стандартно применяются:

1.  **4-уровневые таблицы (4-level paging)**:
    *   Используются 48 бит виртуального адреса (47 бит данных + 1 знаковый).
    *   Позволяют адресовать до 128 ТБ виртуальной и до 64 ТБ физической памяти.
    *   Уровни: `PGD` → `PUD` → `PMD` → `PTE`.
2.  **5-уровневые таблицы (5-level paging / LA57)**:
    *   Введены в ядре 4.14 для поддержки серверов с экстремальным объемом RAM.
    *   Используются 57 бит виртуального адреса.
    *   Лимит адресного пространства: 128 ПБ (виртуальное) и 4 ПБ (физическое).
    *   Добавлен пятый уровень: `P4D`.

Каждая VMA в адресном пространстве процесса описывается диапазоном виртуальных адресов, который отображается через иерархию таблиц страниц на физические кадры или swap-область.

### Механизм трансляции и оптимизации

Каждое обращение к памяти требует "прохода" по всем уровням таблиц (Page Table Walk).
* **PCID (Process-Context Identifiers)**: Позволяет помечать записи в TLB идентификатором процесса. Это исключает необходимость полной очистки (flush) TLB при переключении контекста (Context Switch), что критично для производительности систем под нагрузкой.
* **HugePages**: Использование страниц размером 2 МБ или 1 ГБ позволяет исключить один или два уровня таблиц страниц. Это сокращает глубину Page Table Walk и значительно снижает нагрузку на TLB. Подробнее: **[Оптимизация HugePages](./performance_tuning.md)**.
* **TLB Shootdown**: При изменении таблиц страниц на одном ядре процессора необходимо инвалидировать соответствующие записи в TLB других ядер. Это требует отправки межпроцессорных прерываний (IPI), что вызывает задержки. PCID снижает частоту shootdown.
* **TLB Flush**: Полная очистка TLB происходит при переключении контекста или изменении глобальных таблиц (KPTI). Измеряется через `perf stat -e cycles:k -e instructions:k` или через `vmstat` при высоком `context switch`.

### Структура адресного пространства процесса

При загрузке ELF-исполняемого файла ядро создает адресное пространство процесса с типовым layout:

```
0x0000000000000000 ────> Младшие адреса
│  [vsyscall] / [vvar]   │ (ядро: время, сигналы)
│  [vdso]                │ (динамическая библиотека ядра)
├────────────────────────┤
│  mmap-области          │ (библиотеки .so, mmap файлов)
│  (Stack растет вниз)   │
├────────────────────────┤
│  [heap]                │ (куча, растет вверх)
├────────────────────────┤
│  BSS (неинициализ. данные)
│  Data (инициализ. данные)
│  Text (код программы)
0x7fffffffffffffff ────> Старшие адреса (user-space limit)
```

*   **Text (Code)**: Машинный код программы. Только чтение (`read-only`), исполняемый. Размер фиксируется ELF-заголовком.
*   **Data**: Инициализированные глобальные и статические переменные. Чтение и запись. Загружается из файла в RAM.
*   **BSS (Block Started by Symbol)**: Неинициализированные глобальные переменные. Заполняется нулями при старте. В ELF не занимает места в файле, но резервирует адреса.
*   **Heap (Куча)**: Динамическая память (`malloc`, `new`). Растет «вверх» к старшим адресам. Управляется через `brk()`/`sbrk()` для небольших выделений и `mmap()` для больших.
*   **Stack (Стек)**: Локальные переменные, аргументы функций, адреса возврата. Растет «вниз» к младшим адресам. Размер управляется через `RLIMIT_STACK`.
*   **Memory Mapping**: Общие библиотеки (`.so`), отображение файлов (`mmap`). Находится между стеком и кучей. Может содержать множество VMA.
*   **[vdso] (Virtual Dynamic Shared Object)**: Динамическая библиотека, отображаемая ядром в адресное пространство каждого процесса для ускорения системных вызовов (например, `gettimeofday`). Не требует загрузки файла с диска.
*   **[vvar] (VDSO Variables)**: Область для обмена данными между ядром и userspace через VDSO (например, время суток, TSC).
*   **[vsyscall]**: Устаревший механизм, аналогичный `vdso`, с фиксированным адресом (для обратной совместимости). Подробнее о сегментах процесса: **[Анатомия процесса](../processes/basic_concepts.md)**.

**ASLR и рандомизация:**
Ядро рандомизирует базовые адреса стек, кучи и mmap-регион через параметр `/proc/sys/kernel/randomize_va_space`:
* `0`: Полностью отключено. Используется для отладки или устаревшего ПО.
* `1` (по умолчанию): Рандомизация всех регионов, кроме `[vdso]`.
* `2`: Рандомизация также `[vdso]` и `[heap]`, максимальная энтропия.

На 64-битных системах стандартный размер рандомизации — 28 бит для mmap, что дает ~256 МБ разброс.

### Виртуальные Memory Areas (VMA) и /proc/pid/maps

**VMA** — минимальная единица управления виртуальной памятью в ядре. Каждый VMA описывается структурой `vm_area_struct` и содержит:
*   Начальный и конечный виртуальные адреса.
*   Права доступа (`VM_READ`, `VM_WRITE`, `VM_EXEC`, `VM_SHARED`).
*   Флаги (`VM_MAYREAD`, `VM_MAYWRITE`, `VM_MAYEXEC`, `VM_MAYSHARE`).
*   Ссылку на файл (если `file-backed`) или `NULL` (если анонимный).
*   Операции (`vm_ops`): функции для обработки Page Faults (`fault`, `major_fault`, `page_mkwrite`).

**`/proc/<PID>/maps`** — текстовый файл, экспортирующий список VMA процесса:

```bash
cat /proc/self/maps
# → 555555554000-555555555000 r--p 00000000 08:01 262161 /usr/bin/cat
# → 555555555000-555555556000 r-xp 00001000 08:01 262161 /usr/bin/cat
# → 7ffff7dd0000-7ffff7df0000 rw-p 00000000 00:00 0   [heap]
# → 7ffff7f94000-7ffff7fc5000 r--p 00000000 08:01 262159 /usr/lib/ld-linux-x86-64.so.2
# → 7ffff7fc5000-7ffff7fc6000 rw-p 00000000 00:00 0   [stack]
```

**Расшифровка полей:**
1.  **Диапазон адресов**: `start-end`.
2.  **Права доступа**: `r` (read), `w` (write), `x` (execute), `p` (private/CoW).
3.  **Смещение в файле**: hex-смещение от начала файла.
4.  **Устройство**: `major:minor` файловой системы.
5.  **Inode**: номер inode (0 для анонимных VMA).
6.  **Путь к файлу**: имя файла или системная метка (`[heap]`, `[stack]`, `[vdso]`).

**Private vs Shared VMA:**
*   **Private (`p`)**: Изменения видны только в рамках процесса (CoW для файлов, изоляция для анонимных). Это стандартный режим для кода и данных процесса.
*   **Shared (`s`)**: Изменения видны всем процессам, отобразившим этот файл. Используется для `MAP_SHARED` (разделяемая память, mmap файлов с записью).

**File-backed vs Anonymous:**
*   **File-backed**: Адреса отображены на файл или устройство. Могут быть выгружены в swap или сброшены на диск. Включают код программ, библиотеки, отображенные файлы.
*   **Anonymous**: Не связаны с файлом. Заполняются Zero Page при первом доступе. При выгрузке данные попадают в swap. Включают heap, stack, `mmap(MAP_ANONYMOUS)`.

**Диагностика утечек VMA:**
```bash
# Мониторинг роста числа VMA
watch -n1 "cat /proc/<PID>/status | grep Vm"
# VmSize:      123456 kB   (виртуальное адресное пространство)
# VmRSS:        34567 kB   (физическая память)
# VmPTE:           128 kB   (таблицы страниц)

# Если VmSize растет, а VmRSS стабилен — возможно, утечка VMA (mmap без munmap)
```

### Защита памяти (R/W/X) и NX/DEP

Каждая страница (и VMA) имеет биты защиты, контролируемые MMU и ядром:

*   **`r` (read)**: Разрешено чтение.
*   **`w` (write)**: Разрешена запись.
*   **`x` (execute)**: Разрешено исполнение машинного кода.
*   **`p` (private)**: Private mapping (Copy-on-Write).
*   **`s` (shared)**: Shared mapping.

**NX (No-Execute) / DEP (Data Execution Prevention):**
*   **NX**: Бит в PTE, запрещающий исполнение кода на странице, даже если она помечена как readable. Защищает от эксплойтов, пытающихся выполнить шелл-код в стеке или куче.
*   **DEP**: Аналогичный механизм в архитектуре x86 (XD — eXecute Disable). Включен по умолчанию на современных процессорах и ядрах.
*   **Проверка статуса:**
    ```bash
    # Проверка поддержки NX на CPU
    grep nx /proc/cpuinfo | head -1
    # → flags : ... nx ...
    
    # Проверка через pmap (сегменты кода имеют 'x', данные — нет)
    pmap -x <PID> | grep -E "heap|stack|anon"
    # → 00007f3e8b1a7000     8     8     0 rw-p [heap]  (нет 'x' — NX работает)
    ```

**`mprotect()`:**
Системный вызов для динамического изменения прав доступа к диапазону страниц. Критически важен для:
*   **JIT-компиляторов**: Выделяют память с `rw-`, компилируют код, затем меняют на `r-x`.
*   **Стековых защитников (Stack Smashing Protector)**: Меняют стек на `rw-` при необходимости, затем возвращают `rwx` (редко) или оставляют `rw-` с guard pages.

**`mseal()` (ядро >= 6.10):**
"Запечатывание" mapping — предотвращает последующие `mprotect()`/`mremap()`/`munmap()`. Защищает от атак типа GOT overwrite, когда эксплойт пытается изменить права на сегмент кода.

### Типы маппинга (mmap)

**Основные флаги `mmap()`:**

| Флаг | Описание |
| :--- | :--- |
| `MAP_ANONYMOUS` | Анонимная память (не связана с файлом). Заполняется Zero Page. |
| `MAP_FILE` | Обычное отображение файла (дефолт). |
| `MAP_SHARED` | Изменения видны всем процессам и записываются обратно в файл (если file-backed). |
| `MAP_PRIVATE` | Изменения копируются при записи (CoW), не видны другим процессам. |
| `MAP_FIXED` | Принудительно разместить по заданному адресу (опасно, может перезаписать существующие VMA). |
| `MAP_HUGETLB` | Использовать HugePages (2 МБ или 1 ГБ). |
| `MAP_LOCKED` | Запретить выгрузку страниц в swap (аналог `mlock()`). |
| `MAP_POPULATE` | Предварительно загрузить страницы в RAM (prefault). |
| `MAP_NORESERVE` | Не резервировать swap-пространство (увеличивает риск OOM). |

**`brk()`/`sbrk()` vs `mmap()`:**
*   **`brk()`**: Устанавливает конечный адрес сегмента данных (heap). Используется `malloc` для небольших выделений (обычно < 128 КБ, зависит от `M_MMAP_THRESHOLD`). Простой, но фрагментирует кучу.
*   **`mmap()`**: Выделяет отдельные VMA. Используется для больших блоков, разделяемой памяти и отображения файлов. Каждое выделение — отдельный VMA с собственной таблицей страниц.

**`madvise()`:**
Подсказка ядру о паттерне доступа к области памяти:
*   `MADV_NORMAL` (дефолт), `MADV_RANDOM` (случайный доступ, отключить readahead), `MADV_SEQUENTIAL` (последовательный доступ).
*   `MADV_DONTNEED`: Страницы можно освободить, PTE сбрасываются. При повторном доступе — Zero Page.
*   `MADV_FREE` (Linux 4.5+): Страницы помечаются как "свободные", но остаются в адресном пространстве. Если процесс обратится к ним до освобождения — данные сохранятся.
*   `MADV_HUGEPAGE` / `MADV_NOHUGEPAGE`: Подсказка для THP.

### Безопасность и KPTI

**KPTI (Kernel Page Table Isolation)** — механизм защиты от аппаратной уязвимости **Meltdown** (CVE-2017-5754). Он разделяет таблицы страниц пользователя и ядра, чтобы предотвратить утечку данных через спекулятивное выполнение.
Подробный разбор механизма, влияния на производительность и статуса на современных CPU см. в основном файле: **[KPTI (Kernel Page Table Isolation)](../../Security/Mechanisms/KPTI.md)**.

### Жизненный цикл выделения памяти (Demand Paging)

Linux использует "ленивую" стратегию: память не выделяется физически до тех пор, пока процесс к ней не обратится.

1.  **Запрос (malloc/mmap)**: Ядро создает структуру `VMA` (Virtual Memory Area), помечая диапазон адресов как доступный, но PTE остаются пустыми.
2.  **Исключение (Page Fault)**: При обращении к адресу MMU не находит запись в таблицах и генерирует исключение.
    *   **Minor (Soft) Fault**: Данные уже в RAM (например, в Page Cache или разделяемой библиотеке), ядро просто обновляет PTE.
    *   **Major (Hard) Fault**: Данные нужно прочитать с диска (Swap или исполняемый файл). Процесс блокируется до завершения I/O.
    *   **Invalid Fault**: Обращение к недопустимому адресу (например, `NULL`). Результат — `SIGSEGV` (Segmentation Fault).
3.  **Copy-on-Write (CoW)**: При создании процесса через `fork()` ядро не копирует данные. И родитель, и потомок используют одни и те же физические кадры. Копирование кадра происходит только в момент, когда один из процессов пытается произвести запись.
4.  **Zero Page**: Для анонимных страниц ядро использует общую страницу, заполненную нулями. Это позволяет экономить физическую память — при записи страница копируется в private frame.
5.  **Swap Readahead**: При Major Fault из swap ядро может предзагрузить несколько соседних страниц (аналогично дисковому readahead), чтобы снизить количество будущих faults. Размер управляется через `/proc/sys/vm/page-cluster`.
6.  **mlock()/munlock()**: Фиксация страниц в RAM (запрет выгрузки в swap). Используется для критичных данных (криптографические ключи, реальное время).
7.  **madvise()**: Подсказка ядру о паттерне доступа (см. раздел выше).

### NUMA и виртуальная память

В мультисокетных системах время доступа к памяти зависит от расположения процессора относительно модуля RAM (NUMA — Non-Uniform Memory Access). В Linux это отражено в структуре зон и политиках выделения:

*   **NUMA Node**: Отдельный процессор + набор модулей RAM. Доступ к локальной памяти (~60-100 нс) быстрее, чем к удаленной (~100-200 нс через QPI/UPI).
*   **`/proc/<PID>/numa_maps`**: Анализ распределения памяти процесса по NUMA-узлам.
    ```bash
    cat /proc/<PID>/numa_maps
    # → 00400000 default=1
    # → 00600000 default=1
    # → 7f0000000000 default=0 interleave=0
    # → 7f0000001000 default=0
    # → Адрес    PreferredNode  Pages  Status
    ```
    *   `default=N`: Нода, к которой "привязан" VMA по умолчанию.
    *   `N0=N, N1=N`: Количество страниц на каждой ноде.
*   **NUMA Balancing**: Ядро может автоматически перемещать страницы ближе к использующим их ядрам. Включается через `kernel.numa_balancing=1` (по умолчанию).
*   **numactl**: Позволяет принудительно привязать процесс к ноде или интерливить память.
    ```bash
    # Просмотр топологии
    numactl --hardware
    # available: 2 nodes (0-1)
    # node 0 cpus: 0 1 2 3 4 5 6 7
    # node 0 size: 65536 MB
    # node distances:
    # node   0   1
    #   0:  10  21
    #   1:  21  10
    
    # Привязка процесса к ноде 0
    numactl --cpunodebind=0 --membind=0 my_application
    
    # Interleave по всем нодам
    numactl --interleave=all my_application
    ```
    Подробнее о тюнинге NUMA: **[Оптимизация NUMA](./performance_tuning.md)**.

### vmalloc и ядерное адресное пространство

**`vmalloc`**: Механизм ядра для выделения виртуально непрерывных, но физически фрагментированных областей памяти. Используется драйверами для:
*   Загрузки больших модулей ядра.
*   Создания буферов для DMA.
*   Выделения памяти под сетевые структуры.

Статистика доступна в `/proc/meminfo` (`VmallocUsed`) и `/proc/vmallocinfo` (детализация по выделениям).

**`kmap` / `kmap_atomic`**: На 32-битных системах с HighMem (память выше 896 МБ) ядро не может напрямую адресовать всю RAM через прямой маппинг. `kmap` временно отображает нужную страницу HighMem в фиксированное окно адресного пространства ядра.

## Практические сценарии

### Анализ карт памяти процесса

Инструмент `pmap` визуализирует адресное пространство процесса.
```bash
# Показать карту памяти с правами доступа и именами сегментов
pmap -x <PID>
# → Address           Kbytes     RSS   Dirty Mode  Mapping
# → 000055799a46a000      20      20       0 r-x-- nginx
```
*   `Dirty`: Объем данных, измененных процессом (не может быть просто выброшен из памяти).
*   `RSS`: Сколько физических кадров реально выделено под этот диапазон.
*   `Mode`: Права доступа (`r`/`w`/`x`) и тип (`p` private, `s` shared).

Для детального анализа см. **[pmap — карта памяти процесса](../../Diagnostics/Memory/pmap.md)**.

### Анализ /proc/pid/maps и поиск утечек маппинга

Утечка виртуальной памяти (VMA leak) — это ситуация, когда процесс выделяет новые области через `mmap()` или `brk()`, но не освобождает их через `munmap()`/`brk()`. При этом `VmRSS` может оставаться стабильным, но `VmSize` неуклонно растет, пока процесс не упрется в `RLIMIT_AS` или `vm.max_map_count`.

```bash
# Мониторинг роста VmSize vs VmRSS
watch -n5 "grep -E 'VmSize|VmRSS|VmPTE|VmExe|VmData|VmStk' /proc/<PID>/status"
# VmSize:     7891234 kB   (растет — подозрение на VMA leak)
# VmRSS:       123456 kB   (стабильно — физическая память не растет)

# Детализация: какие сегменты растут
pmap -x <PID> | sort -k 2 -n -r | head -n 20

# Поиск анонимных регионов (частые виновники mmap-утечек)
cat /proc/<PID>/maps | grep anon | wc -l
# → 1523  (много анонимных регионов — вероятна утечка mmap)
```

**Классические причины VMA leak:**
1.  **JIT-компиляторы**: Выделяют память под скомпилированный код и не освобождают старые регионы.
2.  **Библиотеки кэширования**: Выделяют множество мелких `mmap` для файлов конфигурации.
3.  **Ошибки в обработке ошибок**: При неудаче `mmap()` не вызывается `munmap()` ранее выделенных регионов.
4.  **Наследование через `fork()`**: Потомки наследуют VMA родителя, что может давать ложный рост общего VmSize на системе.

### Диагностика давления на таблицы страниц

Сами таблицы страниц занимают место в RAM и не могут быть вытеснены в Swap.
```bash
# Проверка объема RAM, занятого таблицами страниц
grep PageTables /proc/meminfo
# → PageTables:      45678 kB
```
Если значение исчисляется гигабайтами — это признак огромного количества процессов или фрагментации адресного пространства. Рекомендуется переходить на HugePages.

Для процесса конкретно:
```bash
# VmPTE — таблицы страниц для конкретного процесса
grep VmPTE /proc/<PID>/status
# → VmPTE:          128 kB
```

### Мониторинг TLB и производительности трансляции

**`perf` для TLB misses:**
```bash
# Количество TLB misses (instruction/data)
sudo perf stat -e instructions,cycles,cache-references,cache-misses,\
dtlb-load-misses,dtlb-store-misses,itlb-misses <command>

# Пример вывода:
#      1,234,567,890 instructions              # 1.50  insns per cycle
#             45,678 dtlb-load-misses            # 0.01% of all dTLB cache hits
```

**`perf` для TLB shootdown:**
```bash
# IPI (Inter-Processor Interrupt) — индикатор TLB shootdown
sudo perf stat -e 'smp_apic_interrupt' -a -- sleep 5
# → 12,345 smp_apic_interrupt  (высокое значение = активный shootdown)
```

**Анализ через `vmstat`:**
```bash
# Рост context switches (cs) при переключении процессов с большими адресными пространствами
vmstat 1
# cs  — количество context switches в секунду
```

### Диагностика ASLR и NX/DEP

**Проверка глобального статуса ASLR:**
```bash
cat /proc/sys/kernel/randomize_va_space
# 0 = отключен
# 1 = частично (дефолт)
# 2 = максимальная энтропия

# Временное изменение (требует root)
echo 2 | sudo tee /proc/sys/kernel/randomize_va_space
```

**Визуальная проверка ASLR для конкретного процесса:**
```bash
# Запустить процесс дважды и сравнить базовые адреса
for i in 1 2 3; do pmap -p <PID> | head -n 5; echo "---"; done
# Адреса [stack], [heap] и библиотек должны отличаться

# Проверка через /proc/pid/maps
cat /proc/<PID>/maps | head -n 10
# Если базовые адреса не меняются между запусками — ASLR отключен
```

**Проверка NX/DEP:**
```bash
# Поддержка на CPU
grep nx /proc/cpuinfo | head -1
# flags : ... nx ... 

# Проверка, что стек не исполняемый (NX работает)
pmap -x <PID> | grep stack
# → 00007fff8c000000     132     132     0 rw-p [stack]  (нет 'x')
```

### NUMA: анализ топологии и привязка памяти

**Диагностика распределения памяти по нодам:**
```bash
# Общая топология
numactl --hardware
# available: 2 nodes (0-1)
# node 0 cpus: 0 1 2 3 4 5 6 7
# node 0 size: 65536 MB
# node distances:
# node   0   1
#   0:  10  21
#   1:  21  10

# Статистика по нодам
numastat -p <PID>
# Node 0    Node 1    Total
# huge  0.00      0.00      0.00
# file  12.34     34.56     46.90
# anon  123.45     67.89    191.34
# ...

# Детализация для процесса
cat /proc/<PID>/numa_maps
# → 00400000 default=1
# → 00600000 default=1
# → 7f0000000000 default=0 interleave=0 N1=128 N0=256
```

**Привязка для отладки:**
```bash
# Запуск на конкретной ноде
numactl --cpunodebind=0 --membind=0 stress --vm 1 --vm-bytes 1G

# Interleave для тестирования
numactl --interleave=all dd if=/dev/zero of=/tmp/test bs=1M count=1024
```

### Ограничения виртуальной памяти (ulimit, systemd, cgroup)

Лимиты применяются в иерархии: cgroup > systemd > PAM/limits.conf > ulimit.

```bash
# Проверка rlimit для процесса
cat /proc/<PID>/limits | grep "virtual memory"
# Max virtual memory          unlimited            unlimited            bytes

# Установка временного лимита (bash)
ulimit -v 1048576  # 1 ГБ в КБ
./my_application

# Проверка через prlimit (для чужого процесса)
sudo prlimit -p <PID> -v
# RESOURCE DESCRIPTION                             SOFT       HARD UNITS
# AS       address space limit                  unlimited            unlimited bytes

# Проверка системных лимитов
sysctl vm.max_map_count
# → 65530  (максимальное количество VMA на процесс)
```

**Взаимодействие с cgroup v2:**
```bash
# Если cgroup ограничивает memory.max, а RLIMIT_AS — unlimited,
# процесс упадет по OOM при достижении memory.max
cat /sys/fs/cgroup/system.slice/my.service/memory.max
# → 4G

# Для systemd-сервисов
systemctl show my.service -p MemoryMax
# MemoryMax=4G
```

### Контейнеры: виртуальная память и лимиты cgroup

В контейнере процесс видит собственное адресное пространство, но физическая память ограничена cgroup:

```bash
# Внутри контейнера
cat /proc/meminfo
# MemTotal:       4096 MB  (ограничение Docker --memory=4g)

# На хосте — реальное потребление контейнера
cat /sys/fs/cgroup/system.slice/docker-<id>.scope/memory.current
cat /sys/fs/cgroup/system.slice/docker-<id>.scope/memory.max

# Сравнение VmSize внутри и снаружи
# Внутри контейнера: VmSize может доходить до 128 ТБ (ограничение arch)
# На хосте: реальное потребление ограничено memory.max
```

**Важно:** `ulimit -v` внутри контейнера работает параллельно с `memory.max`. Если контейнеру выделено 4 ГБ, а `ulimit -v` установлен в 2 ГБ, процесс упадет по `ENOMEM` при 2 ГБ, даже если `memory.max` позволяет 4 ГБ.

### Диагностика Page Faults (Minor vs Major)

**Minor Page Fault**: Страница уже в RAM (Page Cache, общая библиотека), но не в таблице страниц текущего процесса. Обрабатывается быстро (~мкс).
**Major Page Fault**: Страница нужно читать с диска (swap, исполняемый файл). Блокирует процесс на время I/O (~мс).

```bash
# Общая статистика faults
grep -E "pgfault|pgmajfault" /proc/vmstat
# pgfault                 1523421
# pgmajfault               89123

# По процессам (pidstat)
pidstat -r 1
# UID       PID    VSZ   RSS   %MEM   majflt/s
# 1000      1234  56789  12345   0.12    0.00

# В atop (клавиша 'm')
# MINFLT — minor faults, MAJFLT — major faults
```

Для глубокого анализа см. **[Диагностика Swap и Page Faults](./swap_diagnostics.md)**.

### Диагностика через core dumps и отладчики

**Core dump** — полный снимок памяти процесса на момент падения. Позволяет анализировать адресное пространство после сбоя.

```bash
# Включение core dumps (временно)
ulimit -c unlimited
echo "/tmp/core.%e.%p" | sudo tee /proc/sys/kernel/core_pattern

# Анализ через gdb
gdb /usr/bin/myapp /tmp/core.myapp.12345
(gdb) info files
# Symbols from "/usr/bin/myapp".
# Local core dump file:
# ...
(gdb) info proc mappings
# process 12345
# Mapped address spaces:
#      0x555555554000->0x555555755000 at 0x00000000: /usr/bin/myapp [stack]
# ...
```

**Valgrind (Memcheck):**
```bash
# Поиск утечек и ошибок доступа
valgrind --leak-check=full --show-leak-kinds=all ./myapp
# ==12345== LEAK SUMMARY:
# ==12345==    definitely lost: 512 bytes in 1 blocks
# ==12345==    indirectly lost: 0 bytes in 0 blocks
```

**Address Sanitizer (ASan):**
```bash
# Компиляция с ASan
gcc -fsanitize=address -g myapp.c -o myapp
./myapp
# ==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address ...
```

### eBPF-трассировка событий mmap и page faults

**bpftrace для отслеживания mmap:**
```bash
# Топ процессов по частоте mmap
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_mmap /args->addr == 0/ {
    @mmap[comm] = count();
}
' | sort -rn | head

# Размеры выделений через mmap
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_mmap {
    @sizes[comm] = hist(args->len);
}
'
```

**bpftrace для отслеживания page faults:**
```bash
# Гистограмма задержки Page Faults (в микросекундах)
sudo bpftrace -e 'software:page-faults:1 { @start[tid] = nsecs; }
    software:page-faults:0 /@start[tid]/ { @us = hist((nsecs - @start[tid]) / 1000); delete(@start[tid]); }'
```

Для глубокого анализа swap и major faults см. **[swap_diagnostics.md]**.

### Тюнинг THP

THP позволяет ядру автоматически объединять мелкие страницы в 2-мегабайтные.
```bash
# Проверка статуса THP
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never — включено для всех.
```
На базах данных (PostgreSQL, Redis) THP часто вызывает задержки из-за работы `khugepaged`. В таких случаях рекомендуется режим `madvise` или `never`.

Подробнее: **[Оптимизация HugePages](./performance_tuning.md)**.
