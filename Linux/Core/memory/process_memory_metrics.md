# Метрики потребления памяти процесса

## Определения

* **VSS (Virtual Set Size / VSZ)**: Общий объём виртуального адресного пространства, который процесс зарезервировал в ядре. Включает в себя код, данные, стек, кучу, разделяемые библиотеки и память, выделенную через `malloc`, но ещё не использованную физически.
* **RSS (Resident Set Size)**: Объём физической памяти (RAM), которую процесс фактически занимает в данный момент. Делится на анонимную (Anonymous), файловую (File-backed) и разделяемую (Shared) части.
* **PSS (Proportional Set Size)**: Показатель, учитывающий разделяемую память (Shared Memory) пропорционально количеству процессов, которые её используют. Считается наиболее точным индикатором вклада процесса в общую нагрузку на RAM.
* **USS (Unique Set Size)**: Объём физической памяти, который принадлежит исключительно данному процессу (Private). Это объём, который будет освобожден немедленно при завершении процесса.
* **WSS (Working Set Size)**: Рабочий набор — объём памяти, который был необходим процессу за последние интервалы времени для выполнения задач без задержек. Это динамическая метрика, определяющая порог "тормозов" системы (Thrashing).
* **SHR (Shared Memory)**: Объём резидентной памяти, которая может быть потенциально разделена с другими процессами (библиотеки, `tmpfs`, сегменты System V IPC).
* **Swap (Подкачка)**: Объём данных процесса, которые были выгружены из RAM на диск.

## Основные концепции

### VSS (Virtual Set Size) — Виртуальная память

* **Механизм**: VSS отражает только **резервирование** адресного пространства. Благодаря механизму [Memory Overcommit](./performance_tuning.md), сумма VSS всех процессов может многократно превышать объём физической RAM.
* **Детализация в `/proc/<pid>/status`**:
    * `VmPeak`: Пиковое значение VSS за всё время жизни процесса.
    * `VmSize`: Текущее значение VSS.
    * `VmData`: Размер сегмента данных.
    * `VmStk`: Размер сегмента стека.
    * `VmExe`: Размер сегмента исполняемого кода.
    * `VmLib`: Размер библиотечного кода.
* **Диагностика**: Огромный VSS (сотни ГБ) типичен для сред исполнения с Garbage Collector (Go, Java) или приложений, использующих `mmap` для больших файлов, и обычно не является признаком проблемы.

### RSS (Resident Set Size) — Резидентная память

Это физическая память, реально занятая процессом. RSS состоит из трех ключевых компонентов:
1. **Anonymous RSS**: Память, не связанная с файлами (куча, стек, динамические данные). Рост этого показателя — основной индикатор утечки памяти.
2. **File-backed RSS**: Кэш страниц файлов, отображенных в память (библиотеки, исполняемые файлы, `mmap`). Ядро может освободить эту память (Reclaim), если она не помечена как "грязная" (dirty).
3. **Shared RSS**: Память, общая для нескольких процессов.

**Проблема точности**: RSS суммирует всю разделяемую память целиком для каждого процесса. Если 10 инстансов одного приложения используют общую библиотеку в 10 МБ, системный монитор покажет 100 МБ потребления, хотя реально в RAM занято только 10 МБ.

### PSS и USS — Пропорциональный и Уникальный счет

Эти метрики решают проблему "двойного счета" разделяемой памяти.
* **Формула PSS**: `PSS = USS + (Shared_Clean / N) + (Shared_Dirty / N)`, где N — количество процессов, использующих сегмент.
* **Значимость USS**: `USS = Private_Clean + Private_Dirty`. Это "чистая стоимость" процесса. Если убить процесс, система получит именно этот объем свободной RAM.
* **Инструментарий**: Стандартные `top`/`ps` **не умеют** считать PSS/USS. Для этого используются `smem` или чтение `/proc/<pid>/smaps`.

### WSS (Working Set Size) — Рабочий набор

WSS — это подмножество RSS, к которому процесс обращался за последние N секунд (обычно период сканирования ядра).
* **Критичность**: Если физической RAM меньше, чем сумма WSS всех активных процессов, ядро начинает постоянно вытеснять и тут же возвращать страницы с диска (**Thrashing**).
* **Kubernetes (cgroup v1/v2)**: Метрика `working_set_bytes` рассчитывается как `usage - total_inactive_file`. Именно по этой метрике принимается решение об OOM-завершении (OOMKill) пода.
* **DAMON (Data Access MONitor)**: Современный механизм ядра (5.15+), позволяющий точно измерять WSS с минимальными накладными расходами на CPU.

## Практические сценарии

### Анализ с помощью стандартных утилит

```bash
# Просмотр VSS (VSZ) и RSS для конкретного процесса
ps -o pid,vsz,rss,comm -p <PID>
# →   PID    VSZ   RSS COMMAND
# →  1234 150240  4096 nginx
```

### Точный анализ PSS и USS через smem и ps_mem

Утилиты `smem` и `ps_mem` рассчитывают PSS и USS, суммируя данные из `/proc/<pid>/smaps`.

```bash
# Сортировка процессов по потреблению PSS (в КБ)
smem -tk -s pss -r | head
# →   PID User     Command                         Swap      USS      PSS      RSS
# →  1234 root     nginx                              0     2.1M     3.5M     8.2M

# Удобный отчет по суммарному потреблению группами процессов
sudo ps_mem
# →  Private  +   Shared  =  RAM used	Program
# →  3.1 MiB  +   1.2 MiB =  4.3 MiB	nginx (4)
```

### Детальная разбивка через интерфейс /proc

1.  **`/proc/<pid>/smaps_rollup`**: Рекомендуемый способ в 2024-2025 гг. Агрегирует данные по всей карте памяти процесса без накладных расходов на парсинг тысяч строк `smaps`.
    ```bash
    cat /proc/<PID>/smaps_rollup
    # → Rss:                8520 kB
    # → Pss:                5120 kB
    # → Pss_Anon:           2048 kB
    # → Pss_File:           3072 kB
    # → Private_Dirty:      2000 kB (почти всегда равно USS)
    ```

2.  **`/proc/<pid>/status`**: Быстрый обзор лимитов и текущего состояния.
    ```bash
    grep -E "VmRSS|VmHWM|VmSwap|VmPeak" /proc/<PID>/status
    # → VmPeak:          150240 kB (пиковый VSS)
    # → VmHWM:             8192 kB (High Water Mark — пиковый RSS)
    # → VmRSS:             4096 kB (текущий RSS)
    # → VmSwap:             512 kB (объем в свопе)
    ```

3.  **`/proc/<pid>/statm`**: Формат для быстрой машинной обработки (значения в страницах памяти).
    * Поля: `size` (VSS), `resident` (RSS), `shared` (Shared), `text` (Code), `lib`, `data`, `dt`.

### Метрики в cgroup v2 (Docker / Kubernetes)

Для анализа процесса внутри контейнера следует использовать интерфейс cgroups:
`cat /sys/fs/cgroup/memory.stat`

* **`anon`**: Анонимная память (соответствует анонимному RSS).
* **`file`**: Страничный кэш (соответствует File RSS).
* **`kernel_stack` / `slab`**: Память, потребляемая структурами ядра от имени процесса (часто "белое пятно" в мониторинге).
* **`workingset_refault`**: Количество раз, когда страница рабочего набора была вытеснена и тут же потребовалась снова (прямой индикатор нехватки лимитов).

## Дополнительная информация

### Сравнение метрик для различных задач

| Сценарий | Рекомендуемая метрика | Почему? |
| :--- | :--- | :--- |
| **Поиск утечки памяти** | **USS / Private_Dirty** | Отражает рост памяти, принадлежащей только этому процессу. |
| **Capacity Planning** | **PSS** | Позволяет рассчитать, сколько процессов влезет в сервер. |
| **Troubleshooting OOM** | **RSS / WSS** | Отражает фактическое владение физическими страницами. |
| **Лимиты ulimit** | **VSS** | Лимиты часто устанавливаются на общий объём виртуальной памяти. |
