# Метрики потребления памяти процесса

## Определения

* **VSS (Virtual Set Size) / VSZ**: Общий объём **виртуальной памяти**, доступный процессу.
* **RSS (Resident Set Size) / RES**: Объём памяти, который процесс **реально занимает в физической RAM** в данный момент.
* **PSS (Proportional Set Size)**: «Справедливая» доля физической памяти, занимаемая процессом, с пропорциональным учётом разделяемых библиотек.
* **USS (Unique Set Size)**: Объём памяти, который является **уникальным** для данного процесса и будет освобождён после его завершения.

## Основные концепции

### VSS (Virtual Set Size)

* **Что включает:** Всё, что отображено в адресное пространство процесса: код, данные, стек, куча, разделяемые библиотеки, а также память, запрошенная (`malloc`), но ещё не использованная.
* **Ключевая особенность:** Сумма VSS всех процессов может **многократно превышать** объём физической RAM. Это нормально и является следствием работы [виртуальной памяти](./virtual_vs_physical_memory.md) и механизма [overcommit](./performance_tuning.md). Большая цифра VSS не всегда указывает на проблему.

### RSS (Resident Set Size)

* **Что включает:** Ресурсы процесса, находящиеся сейчас в RAM.
* **Проблема:** RSS суммирует **всю** разделяемую память. Если 10 процессов используют одну библиотеку размером 100 МБ, эти 100 МБ будут добавлены к RSS *каждого* из 10 процессов. Сумма RSS по системе неинформативна.

### PSS (Proportional Set Size)

* **Как решает проблему RSS:** Учитывает разделяемую память пропорционально.
* **Формула:** `PSS = (Уникальная память) + (Разделяемая память / Количество процессов, которые её используют)`.
* **Пример:** Если 2 процесса используют библиотеку на 100 МБ, в PSS каждого будет засчитано по 50 МБ. Сумма PSS всех процессов даёт реалистичную оценку потребления RAM.

### USS (Unique Set Size)

* **Что включает:** Только память, принадлежащая исключительно данному процессу.
* **Главная ценность:** Самый точный показатель того, **сколько физической памяти освободится, если завершить данный процесс**.

## Практические сценарии

### Анализ с помощью `top` и `ps`

Стандартные утилиты показывают VSS (под заголовком `VIRT`) и RSS (`RES`). Этого достаточно для быстрой оценки, но не для точного анализа. Подробнее: [ps](../../Diagnostics/Processes/ps.md), [top](../../Diagnostics/Processes/top.md).

```bash
ps aux | head
# USER         PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
# root           1  0.0  0.1 169420 11988 ?        Ss   Dec12   0:02 /sbin/init
```

### Точный анализ с помощью `smem`

Утилита `smem` — лучший инструмент для анализа, так как показывает USS, PSS и RSS. Подробное использование: [smem](../../Diagnostics/Memory/smem.md).

```bash
# Установить smem (Debian/Ubuntu)
# sudo apt-get install smem

# Показать отчёт по процессам, отсортированный по PSS
smem -t -p
```

### Детальный анализ через `/proc`

Файл `/proc/<PID>/smaps` содержит детальную разбивку по всем отображенным участкам памяти процесса. Также полезную информацию можно получить из `/proc/<PID>/status` (поля `VmSize`, `VmRSS`, `VmData` и др.) и `/proc/<PID>/statm`.

## Дополнительная информация

### Какую метрику когда использовать?

| Задача | Метрика | Обоснование |
| :--- | :--- | :--- |
| Выявление утечки памяти | **USS** (в динамике) | Постоянный рост уникальной памяти — надёжный признак утечки |
| Оценка освобождаемой памяти после завершения процесса | **USS** | Именно этот объём система вернёт в свободное пользование |
| Диагностика нехватки RAM в системе | **Сумма PSS** | Если близка к общему объёму RAM — память действительно заканчивается |
| Проверка чрезмерного запроса виртуальной памяти | **VSS** | Огромное значение (десятки/сотни ГБ) может указывать на ошибку в программе |
