# Кэширование и освобождение памяти в Linux

## Определения

* **Page Reclaim**: Процесс освобождения [страниц памяти](./virtual_vs_physical_memory.md) ядром Linux путем вытеснения неиспользуемых данных при низком уровне свободной памяти.
* **Dirty Page ("грязная" страница)**: Страница в оперативной памяти (RAM), измененная, но не синхронизированная с постоянным хранилищем. Подробнее о записи грязных страниц и настройке dirty_* параметров см. в **[Оптимизации памяти](./performance_tuning.md)**.
* **Writeback**: Фоновый процесс записи "грязных" страниц из кэша памяти на диск.

## Основные концепции

### Принцип Linux: свободная память — потерянная память

Linux придерживается принципа: незанятую память нужно использовать с пользой. Ядро агрессивно кэширует данные, поэтому на рабочем сервере `free` может показывать мало свободной памяти, но это не проблема — кэш освобождается мгновенно, когда приложениям нужна RAM.

### Page Cache vs Buffer Cache

Команда `free` объединяет оба кэша в одну колонку `buff/cache`, но это разные вещи:

**Page Cache** — кэш содержимого файлов. Когда приложение читает файл с диска, ядро оставляет его копию в памяти. При повторном обращении данные отдаются из RAM без обращения к диску. Страницы в page cache бывают двух видов:

* **"Чистые" (clean)** — совпадают с тем, что уже лежит на диске. Могут быть выкинуты мгновенно — данные не потеряются.
* **"Грязные" (dirty)** — приложение уже записало новые данные, но до диска они ещё не доехали. Нельзя выкинуть без записи на диск, иначе данные будут потеряны.

Page Cache — основной потребитель памяти на любом рабочем сервере.

**Buffer Cache** — кэш служебных структур файловой системы: суперблок, таблица inode, group descriptors и другая навигационная кухня ФС. Он обычно маленький (200–400 МБ), но без него ядру пришлось бы при каждом обращении к файлу лезть на диск за метаданными.

### Available — оценка ядра

Колонка `available` в выводе `free` — это оценка самого ядра: сколько памяти оно сможет отдать новым приложениям без обращения в swap. Ядро считает available примерно так:

```
available ≈ free + ~50% file cache + ~50% reclaimable slab - резерв
```

Почему не весь кэш? Если выкинуть всё, система формально выживет, но производительность сильно просядет — каждое чтение файла пойдёт на диск.

**Пример:** `free` = 1,2 ГБ, `buff/cache` = 13 ГБ, `available` = 14 ГБ — система полностью здорова. 13 ГБ в buff/cache — это не проблема, а содержимое файлов, которые сервер недавно читал или писал.

### Механизм Page Reclaim

При снижении свободной памяти ниже `watermark` активируется `kswapd` для освобождения памяти.

* **Списки Active и Inactive**:
  * **Active list**: Недавно использованные страницы.
  * **Inactive list**: Давно неиспользуемые страницы, кандидаты на вытеснение.

* **Алгоритм работы `kswapd`**:
  * Сканирует `Inactive` список.
  * **"Чистые" страницы**: Удаляются из памяти (если совпадают с диском). В отличие от slab-кэшей (dentry, inode), которые освобождаются через [slab shrinker](./slab_allocator.md), page cache просто сбрасывается.
  * **"Грязные" страницы**: Записываются на диск (или в [swap](./swap_management.md)) перед освобождением.
  * Ядро перемещает старые страницы из `Active` в `Inactive` список.

### "Грязные" страницы и Writeback

Ядро откладывает запись изменений на диск, помечая страницы как "грязные", для оптимизации ввода-вывода. Подробности о параметрах dirty_* и настройке writeback см. в **[Оптимизации памяти](./performance_tuning.md)**.

## Практические сценарии

### Диагностика кэша и reclaim

Просмотр текущей статистики памяти:

```bash
free -h
# →               total    used    free   shared  buff/cache  available
# → Mem:           15Gi   1.2Gi   1.5Gi   200Mi     13Gi       14Gi
```

Просмотр деталей по зонам памяти и watermark:

```bash
cat /proc/zoneinfo | grep -E 'min|low|high|nr_free_pages'
```

Параметры dirty_* и рекомендации по настройке для различных workload описаны в **[Оптимизации памяти](./performance_tuning.md)**.

## Дополнительная информация

### Режимы освобождения памяти

* **Фоновое освобождение (Background Reclaim)**:
  * Выполняется `kswapd` при падении свободной памяти ниже `pages_high`.
  * Работает в фоновом режиме, не блокируя пользовательские процессы.

* **Прямое освобождение (Direct Reclaim)**:
  * Происходит при запросе памяти, когда ее количество ниже `pages_min`.
  * Запрашивающий процесс блокируется и синхронно освобождает страницы, что может вызвать задержки.

Пороги (`watermarks`) находятся в `/proc/zoneinfo`. Активное прямое освобождение указывает на нехватку RAM. Детали метрик см. в [статистике памяти](../../Diagnostics/Memory/proc_meminfo.md).

### Водяные знаки памяти (Memory Watermarks)

Ядро Linux использует три уровня водяных знаков для управления памятью:

| Watermark | Описание |
| :--- | :--- |
| **WMARK_MIN** | Минимальный уровень. При достижении запускается прямое освобождение (direct reclaim) |
| **WMARK_LOW** | Порог для запуска фонового освобождения (kswapd) |
| **WMARK_HIGH** | Целевой уровень, до которого kswapd пытается освободить память |

Просмотр текущих значений:

```bash
cat /proc/zoneinfo | grep -E 'min|low|high'
```

**`vm.min_free_kbytes`** — параметр, контролирующий минимальный запас свободной памяти. Рекомендуется устанавливать в 2–3% от общего объёма RAM для серверов.
