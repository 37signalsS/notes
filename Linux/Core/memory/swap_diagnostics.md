# Диагностика Swap и Page Faults в Linux

## Определения

* **Page Fault (ошибка страницы)** — прерывание процессора, возникающее, когда программа обращается к виртуальной странице памяти, которая не сопоставлена с физической RAM.
* **Minor Page Fault** — страница находится в памяти (например, в Page Cache или разделяемой памяти), но не в таблице страниц процесса. Обрабатывается быстро.
* **Major Page Fault** — страница отсутствует в RAM и требует чтения с диска (из файла или swap). Главная причина задержек ("фризов") при нехватке памяти.
* **Swap-in (si)** — чтение данных из пространства подкачки обратно в RAM.
* **Swap-out (so)** — выгрузка данных из RAM в пространство подкачки.
* **Thrashing** — критическое состояние, при котором система тратит большую часть ресурсов на перемещение данных между RAM и swap, не выполняя полезной работы.
* **Pressure Stall Information (PSI)** — механизм ядра для количественной оценки времени, потерянного задачами из-за нехватки ресурсов (Memory, I/O, CPU).

## Основные концепции

### Почему растет Swap при свободной памяти

Использование swap не всегда означает проблему. Ядро Linux перемещает в swap неактивные анонимные страницы, чтобы освободить место для **Page Cache** (дискового кэша). Это ускоряет работу с файловой системой. 
Проблема возникает только при **активном обмене** (высокие показатели `si`/`so`), что указывает на нехватку памяти для "горячего" набора данных.

### Взаимосвязь Swap и давления на память

Высокая активность подкачки — симптом дефицита. Ключевые индикаторы в `/proc/vmstat`:
* `pswpin` / `pswpout`: Счетчики операций подкачки. Постоянный рост говорит о дефиците.
* `pgmajfault`: Счетчик Major Page Faults.

### Современные механизмы: MGLRU и PSI

1. **MGLRU (Multi-Gen LRU)**: С ядра 6.1 заменяет старый алгоритм активных/неактивных списков. Позволяет ядру точнее понимать, какие страницы действительно "старые", снижая количество ошибочных выгрузок в swap.
   * Проверка статуса: `cat /sys/kernel/mm/lru_gen/enabled`.
2. **PSI**: Позволяет отличить "здоровый" свопинг от деградации. Если `full avg10 > 5-10%` в `/proc/pressure/memory`, система реально "тормозит" из-за ожидания памяти.

## Практические сценарии

### Алгоритм комплексной диагностики

#### 1. Общая оценка (vmstat)
```bash
vmstat 1
# Наблюдайте за колонками swap (si, so) и cpu (wa).
# Высокий 'wa' (I/O wait) при si/so > 0 подтверждает дисковые задержки.
```

#### 2. Проверка давления на ресурсы (PSI)
Это наиболее точный метод для современных ядер (4.20+).
```bash
cat /proc/pressure/memory
# some — хотя бы один процесс ждал память.
# full — ВСЕ не-idle процессы стояли в ожидании (критично!).
```
Подробнее: **[Pressure Stall Information (PSI)](../kernel/psi.md)**.

#### 3. Анализ конкретных потребителей (smem и pidstat)
Обычный `top` может вводить в заблуждение (из-за Shared memory). `smem` показывает PSS (Proportional Set Size).
```bash
# Топ процессов по использованию swap
smem -t -k -s swap -r | head
```
Детализация Major Faults по процессам:
```bash
pidstat -r 1
# Ищите высокие значения в колонке majflt/s.
```

#### 4. Диагностика сжатого Swap (Zram/Zswap)
Если используется Zram, обычные утилиты покажут использование "диска", но реально это RAM.
```bash
# Статистика Zram
zramctl
# → NAME       ALGORITHM DISKSIZE  DATA  COMPR  TOTAL STREAMS MOUNTPOINT
# → /dev/zram0 zstd            2G  1.2G   300M   350M      16 [SWAP]
```
Для Zswap (кэш перед диском):
```bash
grep -r . /sys/kernel/debug/zswap/
```

#### 5. Изучение зон памяти и вотермарков
```bash
cat /proc/zoneinfo | grep -E "Node|free|low|high"
# Если free < low, ядро начинает агрессивно вытеснять страницы (direct reclaim).
```

### Диагностика Page Faults

Major Page Faults возникают не только из-за swap, но и при чтении бинарных файлов или mmap-файлов.

**Инструментарий:**
* **perf**: Точный анализ причин прерываний.
  ```bash
  perf stat -e major-faults,minor-faults -p <PID> sleep 5
  ```
* **pmap**: Карта памяти процесса. Помогает понять, какой именно файл или сегмент вызывает ошибки.
  ```bash
  pmap -x <PID> | sort -k 3 -n -r | head -n 20
  ```

## Дополнительная информация

### Взаимосвязь с другими механизмами

* **OOM Killer**: Если диагностика показывает критическое давление (`PSI full > 20%`), следующим шагом может стать срабатывание **[OOM Killer](../processes/oom_killer_mechanism.md)**.
* **Тюнинг**: Если swap используется слишком агрессивно, проверьте параметры `vm.swappiness` и `vm.vfs_cache_pressure` в **[Оптимизации памяти](./performance_tuning.md)**.
* **VFS**: Массовые Major Faults могут быть связаны с очисткой кэша метаданных. См. **[Slab Allocator](./slab_allocator.md)**.
