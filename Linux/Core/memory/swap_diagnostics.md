# Диагностика Swap и Page Faults

## Определения

* **Page Fault (ошибка страницы)** — исключение от [MMU](./virtual_vs_physical_memory.md) при обращении к виртуальной странице, которой нет в физической памяти. Подробнее: [Виртуальная и физическая память](./virtual_vs_physical_memory.md).
* **Minor fault (мягкий отказ)** — страница уже в RAM, но отсутствует в таблице страниц процесса. Обрабатывается быстро, без I/O.
* **Major fault (жёсткий отказ)** — страница отсутствует в RAM и должна быть загружена с диска (из swap или файлового кэша). Вызывает задержки из-за дискового I/O.
* **Swap-in (si)** — чтение страниц из swap в RAM.
* **Swap-out (so)** — запись страниц из RAM в swap.

## Основные концепции

### Почему swap активен при кажущейся свободной RAM?

Ядро Linux проактивно выгружает редко используемые страницы в swap, чтобы освободить RAM для дискового кэша (page cache). Это нормальное поведение — кэш файлов ускоряет чтение, а неактивные данные процессов хранятся на диске.

**Проблема возникает, когда:** процессы начинают активно обращаться к выгруженным страницам → возникают **major page faults** → система тратит время на чтение с диска из swap → наблюдаются «тормозы».

### Swap и давление на память

Высокая swap-активность — симптом нехватки RAM. Ключевые индикаторы:

| Метрика | Нормальное значение | Проблема |
| :--- | :--- | :--- |
| `si` / `so` (vmstat) | 0 | Ненулевые значения = активный свопинг |
| `pswpin` / `pswpout` (/proc/vmstat) | Низкие или стабильные | Постоянный рост = непрерывный I/O swap |
| `wa` (iowait) | < 5% | Рост вместе с `si`/`so` = дисковая задержка из-за swap |
| `kswapd` CPU usage | Близок к 0% | Высокое потребление = ядро тратит ресурсы на управление памятью |

### Dirty Pages и их влияние

`Dirty` страницы — изменённые данные в RAM, ещё не записанные на диск. Рост `Dirty` без сброса вызывает задержки и I/O spikes. Подробнее о настройке dirty-параметров: [Оптимизация памяти](./performance_tuning.md).

## Практические сценарии

### Диагностика: последовательность действий

**Симптом:** сервер медленно отвечает, но `free` показывает достаточно RAM.

#### Шаг 1: Проверить активные swap-устройства

```bash
swapon -s
# или
swapon --show
```

Покажет список swap-разделов/файлов, их размер и текущее использование.

#### Шаг 2: Мониторинг swap-активности в реальном времени

```bash
vmstat 1
```

**Ключевые колонки:**
- `si` (swap-in) — чтение из swap в RAM. Рост = процессы обращаются к выгруженным данным.
- `so` (swap-out) — запись из RAM в swap. Рост = ядро выгружает неактивные страницы.

**Интерпретация:**
- `si`/`so` = 0 → swap не используется активно, система в норме.
- `si`/`so` растут → ядро активно работает с swap → это причина задержек.
- Высокий `wa` (iowait) вместе с `si`/`so` → подтверждение дисковой задержки из-за swap.

Подробнее: [vmstat](../../Diagnostics/Memory/vmstat.md).

#### Шаг 3: Проверить общее использование swap

```bash
cat /proc/meminfo | grep Swap
```

Покажет `SwapTotal`, `SwapFree`, `SwapCached` — общую картину swap-памяти. Подробнее: [proc_meminfo](../../Diagnostics/Memory/proc_meminfo.md).

#### Шаг 4: Проверить счётчики страниц swap

```bash
cat /proc/vmstat | grep -E 'pswpin|pswpout'
```

- `pswpout` — количество страниц, записанных в swap.
- `pswpin` — количество страниц, считанных обратно из swap.

Высокие значения обоих счётчиков указывают на постоянный I/O swap и нехватку RAM.

#### Шаг 5: Проверить давление памяти на уровне ядра

```bash
cat /proc/zoneinfo | less
```

Столбцы `nr_free_pages` и `low` показывают, какие зоны памяти (DMA, Normal, HighMem) близки к исчерпанию и когда ядро начинает активно использовать swap или `kswapd`. Подробнее о `kswapd` и reclaim-процессах: [кэширование и освобождение памяти](caching_and_reclaiming.md).

#### Шаг 6: Проверить активность `kswapd`

```bash
pidstat -t -p $(pgrep -d, kswapd0) 1
```

Показывает, сколько CPU тратит демон управления памятью (`kswapd`) на очистку и свопинг. Высокое потребление CPU сигнализирует о том, что ядро тратит много ресурсов на управление памятью, пытаясь предотвратить OOM.

#### Шаг 7: Проверить использование swap по cgroups (для контейнеров/VM)

```bash
cat /sys/fs/cgroup/memory/<cgroup>/memory.stat
```

Смотрим `total_rss`, `total_swap`, `unevictable`. Для production-контейнеров это часто более точный показатель нагрузки, чем `top` внутри контейнера. `<cgroup>` — путь к конкретной контрольной группе. Подробнее: [cgroups](../cgroups.md).

### Диагностика Page Faults

Page faults замедляют приложение, даже если CPU свободен. Время уходит не в вычисления, а в обработку отказов страниц — особенно **major faults** с чтением с диска.

#### 1. `vmstat` — общая картина по системе

Параметры `si`/`so` и `wa` уже описаны в [Шаге 2](#шаг-2-мониторинг-swap-активности-в-реальном-времени). Для page faults используйте:

```bash
vmstat 1
```

#### 2. `pidstat -r` — page faults по процессам

```bash
pidstat -r 1
```

**Ключевые метрики:**
- `minflt/s` — minor faults в секунду. Высокие значения = интенсивная работа с памятью.
- `majflt/s` — major faults в секунду. Рост = нехватка RAM и чтение с диска.

Сравнивайте процессы: кто генерирует больше `majflt/s`, тот создаёт нагрузку на подсистему памяти. Подробнее: [pidstat](../../Diagnostics/Processes/pidstat.md).

#### 3. `perf stat` — точный подсчёт faults

```bash
perf stat -e page-faults,minor-faults,major-faults <cmd>
```

Даёт точное количество всех типов faults для конкретного процесса или команды.

#### 4. `/proc/<pid>/stat` — сырые счётчики процесса

```bash
cat /proc/<pid>/stat | awk '{print $10,$12}'
```

Выводит накопленные значения minor faults (поле 10) и major faults (поле 12) для конкретного PID.

#### 5. `perf top` — анализ «горячих» точек кода

```bash
sudo perf top
```

Если faults частые, `perf top` показывает, какие функции ядра или приложения вызывают наибольшую активность. Подробнее: [perf](../../Diagnostics/Performance/perf.md).

#### Интерпретация результатов

| Паттерн | Диагностика | Действие |
| :--- | :--- | :--- |
| Высокие `minflt/s`, низкие `majflt/s` | Нормальная работа с памятью, страницы переиспользуются из RAM | Не требует вмешательства |
| Высокие `majflt/s` + рост `si`/`so` | Критическая нехватка RAM, активный свопинг | Увеличить RAM или оптимизировать приложение |
| Высокие `majflt/s` без `si`/`so` | Приложение активно работает с файловым кэшем или mmap-файлами | Проверить паттерн доступа к файлам |

### Анализ распределения Dirty Pages

```bash
cat /proc/meminfo | grep -E 'Dirty|Writeback'
```

Если `Dirty` растёт, процессы создают много кэшируемых страниц, а ядро ещё не сбросило их на диск. Это может вызвать задержки и фоновые I/O spikes. Подробнее: [proc_meminfo](../../Diagnostics/Memory/proc_meminfo.md).

### Анализ распределения памяти процесса

```bash
pmap -x <pid>
```

Показывает детальное распределение памяти процесса, включая swap. Подробнее: [pmap](../../Diagnostics/Memory/pmap.md).

## Дополнительная информация

### Выбор инструмента диагностики

Для быстрой общей оценки используйте [`vmstat`](../../Diagnostics/Memory/vmstat.md), для подтверждения постоянного I/O swap — счётчики `/proc/vmstat` (`pswpin`/`pswpout`). Состояние зон памяти анализируется через `/proc/zoneinfo`, поиск процесса-виновника — [`pidstat -r`](../../Diagnostics/Processes/pidstat.md). Детальный анализ конкретного процесса выполняет [`perf stat`](../../Diagnostics/Performance/perf.md), распределение памяти — [`pmap`](../../Diagnostics/Memory/pmap.md), общую статистику — [`/proc/meminfo`](../../Diagnostics/Memory/proc_meminfo.md). Для диагностики контейнерных сред смотрите `memory.stat` в cgroups.
