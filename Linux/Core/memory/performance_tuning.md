# Оптимизация и тонкая настройка памяти

## Определения

* **Memory Overcommit**: Механизм ядра, позволяющий процессам запрашивать больше виртуальной памяти, чем физически доступно в системе (RAM + swap).
* **OOM Killer (Out of Memory Killer)**: Механизм ядра, принудительно завершающий процессы для освобождения памяти при её острой нехватке. Подробное описание механизма выбора жертвы и управления поведением см. в [Лимиты ресурсов и OOM Killer](../processes/limits.md).
* **KSM (Kernel Samepage Merging)**: Фоновый процесс, объединяющий идентичные страницы памяти в одну физическую страницу с пометкой "copy-on-write" для экономии RAM.
* **UMA (Uniform Memory Access)**: Архитектура, в которой все процессоры имеют одинаковое время доступа (latency) ко всей оперативной памяти.
* **NUMA (Non-Uniform Memory Access)**: Архитектура памяти в многопроцессорных системах, где память разделена на "узлы". Процессор имеет быстрый доступ к локальному узлу и медленный — к удаленным.
* **HugePages (HugeTLB)**: Страницы памяти большого размера (2 МБ или 1 ГБ), используемые для снижения накладных расходов на управление памятью.
* **Transparent Huge Pages (THP)**: Автоматический механизм ядра, пытающийся "прозрачно" объединять обычные страницы в HugePages.

## Основные концепции

### Memory Overcommit

* **Преимущество**: Позволяет запустить больше приложений, резервирующих память "про запас".
* **Риск**: При одновременном использовании всей зарезервированной памяти приводит к вызову **OOM Killer**.

### KSM: Дедупликация памяти

* **Принцип**: KSM объединяет одинаковые страницы. При записи создается персональная копия (Copy-on-Write).
* **Плюсы**: Экономит RAM в средах с дублирующимися данными (виртуализация, контейнеры).
* **Минусы**: Потребляет CPU, может вызывать задержки при CoW.

### Архитектуры доступа к памяти: UMA vs NUMA

#### Определения

* **UMA (Uniform Memory Access / Равномерный доступ к памяти):** Классическая архитектура, характерная для большинства настольных компьютеров и старых серверов. Все процессоры (ядра) подключены к памяти через общую шину, и время доступа к любой ячейке памяти одинаково для всех ядер.
* **NUMA (Non-Uniform Memory Access / Неравномерный доступ к памяти):** Архитектура современных многопроцессорных серверов. Система состоит из нескольких "узлов" (NUMA nodes), каждый из которых включает в себя группу процессорных ядер и собственный банк локальной памяти. Доступ процессора к "своей" локальной памяти происходит очень быстро, а к памяти другого узла ("удаленной" памяти) — значительно медленнее из-за необходимости использовать межсоединение (например, QPI/UPI).

#### Почему NUMA — проблема для баз данных?

Производительность баз данных и других высоконагруженных приложений крайне чувствительна к задержкам доступа к памяти (memory latency). Проблема возникает, когда планировщик ОС перемещает процесс, работающий на одном NUMA-узле, на другой, или когда процессу на одном узле требуются данные из памяти, расположенной на другом узле. Эти "перекрестные" обращения к удаленной памяти вызывают значительные задержки, которые становятся серьезным узким местом и деградируют общую производительность.

#### Как с этим бороться?

Основная стратегия — обеспечить **локальность NUMA (NUMA locality)**, то есть привязать процесс и его память к одному и тому же NUMA-узлу.

1. **`numactl`:** Стандартная утилита для управления NUMA-политиками. Она позволяет принудительно запустить процесс на ядрах конкретного узла и заставить его выделять память только из локальной памяти этого узла.
2. **Привязка CPU (CPU Pinning):** Явное указание, на каких ядрах CPU может выполняться процесс. Подробное описание см. в [Привязка процессов к CPU (CPU Pinning)](../cpu_pinning.md).
3. **Memory Interleaving (чередование памяти):** Настройка на уровне BIOS/UEFI, которая "перемешивает" страницы памяти между всеми NUMA-узлами. Система начинает видеть всю память как единый UMA-домен. Это устраняет проблему "удаленного" доступа, но ценой того, что **весь доступ к памяти становится немного медленнее** (так как преимущества от локального доступа теряются). Этот вариант может быть компромиссом для приложений, которые не могут быть оптимизированы под NUMA.

### Управление Swap (подкачкой)

Swap — дисковое пространство для выгрузки неактивных страниц RAM. Параметр `vm.swappiness` контролирует агрессивность использования swap.

**Важно:** В ядрах Linux 6.8+ диапазон `vm.swappiness` расширен с **0–100** до **0–200** для более точной настройки.

**Рекомендации:**
- **General-purpose workloads / Kubernetes:** `60` (значение по умолчанию)
- **Серверы приложений:** `10–30`
- **Базы данных (PostgreSQL, MySQL, Oracle):** `1–10`
- **Системы с большим файловым кэшем:** `90+` (агрессивный swap для сохранения кэша)

Подробное описание см. в [Управление Swap (файлом подкачки)](swap_management.md).

### Кэш Dirty Pages (Грязных страниц)

#### Определения

* **Dirty Pages (Грязные страницы):** Это страницы в оперативной памяти (внутри [page cache](caching_and_reclaiming.md)), которые были изменены приложением, но еще не записаны на постоянное хранилище (диск).
* **`vm.dirty_background_ratio`:** Процент **доступной памяти**, по достижении которого фоновые потоки ядра (`kworker`/`pdflush`) начинают **асинхронно** сбрасывать "грязные" страницы на диск. Этот процесс не блокирует приложения.
* **`vm.dirty_ratio`:** Процент **доступной памяти**, по достижении которого процесс, выполняющий запись, **блокируется** и принудительно выполняет **синхронную** запись своих грязных страниц на диск. Это может вызывать видимые "зависания" (stalls) приложений.
* `vm.dirty_expire_centisecs`: Время в сотых долях секунды, по истечении которого грязная страница считается "старой" и может быть сброшена на диск при следующей активности фоновых потоков.
* `vm.dirty_writeback_centisecs`: Интервал между запусками фоновых потоков, проверяющих наличие грязных страниц для записи.

#### Где применяется и как настраивать?

Эти параметры контролируют баланс между производительностью дисковой записи и использованием оперативной памяти.

* **Нагрузки с интенсивной записью на медленные диски (HDD):**
  * **Задача:** Накопить как можно больше данных в RAM, чтобы объединить множество мелких случайных записей в одну большую последовательную, что гораздо эффективнее для HDD.
  * **Рекомендация:** Увеличить `vm.dirty_background_ratio` и `vm.dirty_ratio`.
  * **Пример:** `vm.dirty_background_ratio = 10`, `vm.dirty_ratio = 40`.

* **Системы с быстрыми дисками (SSD/NVMe) и/или большим объемом RAM:**
  * **Проблема:** Большие значения `dirty_ratio` на системах с большим количеством RAM (например, 128 ГБ) могут привести к накоплению десятков гигабайт грязных страниц. Когда лимит достигается, система пытается синхронно сбросить огромный объем данных, вызывая длительную паузу ("I/O storm"), во время которой система не отвечает.
  * **Рекомендация:** Значительно уменьшить значения, чтобы обеспечить более плавную и постоянную запись на диск, избегая больших всплесков.
  * **Пример:** `vm.dirty_background_ratio = 5`, `vm.dirty_ratio = 10`.

* **Базы данных и критичные системы:**
  * **Задача:** Минимизировать риск потери данных при внезапном сбое питания. Данные, находящиеся в dirty-кэше, при сбое будут утеряны.
  * **Рекомендация:** Уменьшить `dirty_ratio` и `dirty_expire_centisecs`, чтобы данные как можно быстрее попадали на диск. Это соответствует принципам работы Write-Ahead Log (WAL), который СУБД используют для обеспечения долговечности (Durability).

### HugePages и Transparent Huge Pages (THP)

#### TLB (Translation Lookaside Buffer)

**TLB** — аппаратный кэш процессора, хранящий соответствия виртуальных адресов физическим. Ускоряет трансляцию адресов, выполняемую MMU.

**Проблема:** Когда рабочий набор данных не помещается в TLB, растёт количество **TLB miss**. Каждый miss требует обхода таблиц страниц (page tables), что добавляет десятки–сотни циклов процессора.

**Симптомы TLB-узкого места:**
- CPU не упирается в 100%, память «есть», iowait низкий — но производительность падает
- Рост CPU time без явного роста полезной работы
- Особенно заметно при большом количестве мелких аллокаций, фрагментированной памяти или росте числа потоков

**Диагностика:**

```bash
# Проверка TLB miss
perf stat -e dTLB-load-misses,iTLB-load-misses -a sleep 10

# Оценка IPC (instructions per cycle)
perf stat -e cycles,instructions,cache-misses -a sleep 10

# Проверка page faults
perf stat -e minor-faults,major-faults -a sleep 10
```

> **Интерпретация:** Рост доли `dTLB-load-misses` и падение IPC указывают на то, что процессор тратит время на адресную трансляцию. `minor-faults` в большом количестве усиливают давление на TLB и page tables.

**Решение:** Использование **Huge Pages** уменьшает количество записей в TLB (одна страница 2 МБ заменяет 512 страниц по 4 КБ), но добавляет компромиссы по аллокации и фрагментации.

#### Standard HugePages (HugeTLB)

Страницы памяти большого размера (2 МБ или 1 ГБ), которые резервируются администратором заранее.

* **Преимущества**:
  * **Снижение нагрузки на TLB**: Ускоряет преобразование виртуальных адресов в физические за счет меньшего количества записей в TLB.
  * **Уменьшение размера таблиц страниц**: Снижает потребление памяти ядром.
  * **Предсказуемость**: Память выделена заранее и не подвержена фрагментации.

#### Transparent Huge Pages (THP)

Механизм ядра, который пытается "прозрачно" для приложений объединять обычные страницы (4 КБ) в "огромные" (2 МБ).

#### Проблемы и решения для THP

Несмотря на благие намерения, автоматическое поведение THP создает серьезные проблемы для высокопроизводительных и чувствительных к задержкам приложений (базы данных, системы реального времени).

* **Проблема 1: Непредсказуемые задержки (Latency Spikes):**
  * **Причина:** Фоновый процесс ядра `khugepaged` постоянно сканирует память в поисках смежных 4-килобайтных страниц, чтобы объединить их в одну 2-мегабайтную. На время этого процесса (который включает блокировку, перемещение страниц и обновление таблиц страниц) могут возникать короткие, но критичные "зависания" (stalls), неприемлемые для СУБД.
* **Проблема 2: Высокая утилизация CPU и фрагментация:**
  * **Причина:** Другой процесс, `kcompactd`, пытается дефрагментировать память, перемещая страницы, чтобы создать непрерывные блоки для `khugepaged`. Эта активность может приводить к высокой утилизации CPU (до 100%) и блокировкам памяти, что также вызывает просадки производительности.
* **Проблема 3: Излишнее потребление памяти:** Если приложение выделяет память небольшими порциями, THP все равно может выделить целую 2-мегабайтную страницу, что приводит к неэффективному использованию RAM.

**Решение и лучшая практика:**
**Для баз данных (Oracle, PostgreSQL, MongoDB и др.), систем виртуализации и любых приложений, требующих стабильно низкой задержки, настоятельно рекомендуется отключать THP** и вместо этого использовать предварительно выделенные **Standard HugePages**. Это обеспечивает предсказуемую производительность без случайных пауз.

#### Диагностика Compaction Stalls

Когда ядру требуется выделить крупный непрерывный блок памяти (для THP или order>0 аллокаций), при фрагментированной памяти запускается **memory compaction** — перемещение страниц для формирования contiguous-области. В этот момент потоки могут блокироваться, что проявляется как кратковременные latency spikes без очевидного CPU или I/O bottleneck.

**Проверка активности compaction:**

```bash
# Счётчики compaction в vmstat
cat /proc/vmstat | grep compact

# Ключевые метрики:
# compact_stall — количество раз, когда процессы ждали завершения compaction
# compact_fail — неудачные попытки compaction
# compact_success — успешные compaction
```

Рост `compact_stall` означает, что процессы реально ждали завершения compaction.

**Проверка уровня фрагментации:**

```bash
# Просмотр свободных блоков разного порядка (order)
cat /proc/buddyinfo
```

Если мало свободных блоков высокого order — крупные аллокации требуют сборки памяти.

**Проверка активности THP:**

```bash
# Статус THP
cat /sys/kernel/mm/transparent_hugepage/enabled

# Использование анонимных huge pages
cat /proc/meminfo | grep AnonHugePages
```

Подробнее о метриках памяти, включая `AnonHugePages`, см. в [`/proc/meminfo`](../../Diagnostics/Memory/proc_meminfo.md).

При активном THP и фрагментированной памяти попытки выделить huge pages создают периодические паузы. В high-load среде это проявляется как кратковременные latency spikes без явных CPU или I/O bottleneck.

#### Сравнение и ключевые различия

| Характеристика | Transparent Huge Pages (THP) | Standard HugePages (HugeTLB) |
| :--- | :--- | :--- |
| **Управление** | **Автоматическое.** Ядро само решает, когда объединять страницы. | **Ручное.** Администратор должен заранее зарезервировать пул страниц. |
| **Прозрачность** | **Да.** Приложения не знают, что работают с большими страницами. | **Нет.** Приложения должны быть модифицированы для использования `hugetlbfs`. |
| **Гибкость** | Высокая. Страницы могут быть динамически разделены обратно на 4 КБ. | Низкая. Память резервируется и не может быть использована для других нужд. |
| **Производительность** | Может вызывать **непредсказуемые задержки** из-за фоновой работы по слиянию и дефрагментации памяти. | Обеспечивает **предсказуемую высокую производительность**, так как страницы выделяются сразу. |

## Практические сценарии

### Управление Memory Overcommit

Регулируется параметром `vm.overcommit_memory`:

* `0` (по умолчанию): Эвристика. Отклоняет очевидно "жадные" запросы.
* `1`: Разрешать всегда. Повышает риск OOM.
* `2`: Не разрешать. Строгое ограничение (`SwapTotal + RAM * overcommit_ratio`). Полезно для СУБД.

```bash
# Установить строгий режим (не разрешать overcommit)
sudo sysctl -w vm.overcommit_memory=2
```

### Управление NUMA с `numactl`

```bash
# Запустить my_app на узле CPU 0 и выделять память только с этого узла
numactl --cpunodebind=0 --membind=0 my_app
```

### Настройка HugePages

```bash
# Выделить 1024 страницы по 2 МБ (всего 2 ГБ)
sudo sysctl -w vm.nr_hugepages=1024
```

### Управление THP

Проверка статуса:

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never
```

* `always`: THP включен для всех процессов.
* `madvise`: THP включен только для процессов, которые явно запросили это через системный вызов `madvise()`.
* `never`: THP полностью отключен.

Отключение до перезагрузки:

```bash
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/defrag
```

### Использование кастомных аллокаторов памяти

* **Проблема:** Стандартный аллокатор памяти `glibc` (`malloc`) может быть неэффективным для высоконагруженных приложений с интенсивными операциями выделения/освобождения памяти. Это приводит к фрагментации памяти, снижению производительности и увеличению задержек, особенно в многопоточных средах.

* **Решение:** Использовать специализированные, высокопроизводительные аллокаторы памяти, такие как `jemalloc` или `tcmalloc` (из Google Performance Tools). Эти аллокаторы лучше оптимизированы для многопоточных сред и больших объемов памяти, существенно повышая производительность приложений (например, баз данных, таких как MySQL, или веб-серверов).

* **Методы интеграции:**
    1. **`LD_PRELOAD`:** Самый простой способ. Достаточно установить аллокатор и указать путь к его библиотеке через переменную окружения `LD_PRELOAD` перед запуском приложения. Это "заставляет" приложение использовать альтернативный аллокатор без перекомпиляции.

        ```bash
        # Установка jemalloc (для Debian/Ubuntu)
        sudo apt-get install libjemalloc-dev
        
        # Запуск приложения с jemalloc
        LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 my_application
        ```

    2. **Интеграция на этапе сборки:** Некоторые приложения позволяют указать кастомный аллокатор при компиляции.

* **Применение:** Особенно полезно для СУБД, таких как MySQL (Percona Server по умолчанию использует `jemalloc`), Redis, Cassandra, а также для высокопроизводительных веб-серверов и любых приложений с интенсивным использованием памяти.

## Дополнительная информация

### Параметр ядра `vfs_cache_pressure`

Контролирует агрессивность освобождения ядром памяти для кэширования **dentry** и **inode**, хранящихся с помощью [Slab Allocator](slab_allocator.md).

* **Значение по умолчанию: `100`**. Ядро быстро освобождает кэш inode/dentry.
* **Низкое значение (например, `50`):** Ядро дольше хранит кэш, может ускорить доступ к файлам, но увеличивает риск нехватки памяти для процессов.
* **Высокое значение (более `100`):** Ядро очень агрессивно очищает кэш метаданных.

```bash
sudo sysctl -w vm.vfs_cache_pressure=50
```
