# Оптимизация и тонкая настройка памяти

## Определения

* **Memory Overcommit**: Механизм ядра, позволяющий процессам запрашивать больше виртуальной памяти, чем физически доступно в системе (RAM + swap).
* **OOM Killer (Out of Memory Killer)**: Механизм ядра, принудительно завершающий процессы для освобождения памяти при её острой нехватке. Подробное описание см. в [Механизм OOM Killer](../processes/oom_killer_mechanism.md).
* **KSM (Kernel Samepage Merging)**: Фоновый процесс, объединяющий идентичные страницы памяти в одну физическую страницу с пометкой "copy-on-write" для экономии RAM.
* **UMA (Uniform Memory Access)**: Архитектура, в которой все процессоры имеют одинаковое время доступа (latency) ко всей оперативной памяти.
* **NUMA (Non-Uniform Memory Access)**: Архитектура памяти в многопроцессорных системах, где память разделена на "узлы" (nodes). Процессор имеет быстрый доступ к локальному узлу и медленный — к удаленным.
* **HugePages (HugeTLB)**: Страницы памяти большого размера (2 МБ или 1 ГБ), используемые для снижения накладных расходов на управление памятью.
* **Transparent Huge Pages (THP)**: Автоматический механизм ядра, пытающийся "прозрачно" объединять обычные страницы в HugePages.
* **Dirty Pages (Грязные страницы)**: Страницы в оперативной памяти (внутри [page cache](caching_and_reclaiming.md)), изменённые приложением, но ещё не записанные на диск.
* **TLB (Translation Lookaside Buffer)**: Аппаратный кэш процессора, хранящий соответствия виртуальных адресов физическим для ускорения трансляции адресов.
* **Page Table Entry (PTE)**: Запись в таблице страниц, хранящая информацию о соответствии одной виртуальной страницы физической.
* **Memory Compaction**: Процесс дефрагментации памяти ядром для создания непрерывных блоков (необходим для выделения HugePages).

## Основные концепции

### Memory Overcommit

* **Преимущество**: Позволяет запустить больше приложений, резервирующих память "про запас".
* **Риск**: При одновременном использовании всей зарезервированной памяти приводит к вызову **OOM Killer**.
* **Механизм**: Регулируется через `vm.overcommit_memory`. При значении `2` ядро ограничивает выделение виртуальной памяти формулой: `SwapTotal + RAM * overcommit_ratio`.

### KSM: Дедупликация памяти

* **Принцип**: KSM сканирует анонимную память и объединяет одинаковые страницы. При попытке записи создается персональная копия (Copy-on-Write).
* **Плюсы**: Экономит RAM в средах с множеством идентичных данных (виртуализация, контейнеры).
* **Минусы**: Потребляет CPU на сканирование, может вызывать задержки при записи (CoW).

### Архитектуры доступа к памяти: UMA vs NUMA

#### Проблема NUMA для производительности

Производительность баз данных и высоконагруженных приложений чувствительна к задержкам (latency). В NUMA-системах доступ к памяти "чужого" узла (через шину QPI/UPI) занимает значительно больше времени (~150–200 нс против ~100 нс локально). Если планировщик перемещает процесс между узлами или память выделяется на удаленном узле, возникает деградация производительности.

#### Стратегии оптимизации NUMA

1. **NUMA Locality**: Привязка процесса и его памяти к одному узлу через `numactl`.
2. **CPU Pinning**: Явная привязка потоков к ядрам конкретного узла. Подробнее см. в [CPU Pinning](../cpu_pinning.md).
3. **Memory Interleaving**: Чередование страниц между всеми узлами. Превращает систему в "медленный UMA". Полезно, если приложение невозможно оптимизировать под NUMA, но нужно избежать перекосов нагрузки.

### Управление Swap (подкачкой)

Swap используется для выгрузки неактивных анонимных страниц. Параметр `vm.swappiness` (диапазон 0–200) определяет баланс между очисткой файлового кэша и свопингом.

**Рекомендации по Swappiness:**

* **General-purpose / Kubernetes**: `60` (баланс)
* **Серверы приложений (Java)**: `10–30` (приоритет RAM)
* **Базы данных**: `1–10` (минимизация пауз)
* **Системы с огромным кэшем**: `90+` (агрессивный swap для удержания файлов в памяти)

Подробное описание см. в [Управление Swap](swap_management.md).

### Кэш Dirty Pages (Грязных страниц)

Ядро откладывает запись на диск для оптимизации I/O, накапливая "грязные" страницы.

* **`vm.dirty_background_ratio`**: Процент памяти, при котором `kworker` начинает **асинронную** запись. Не блокирует приложение.
* **`vm.dirty_ratio`**: Процент памяти, при котором процесс **блокируется** для **синхронной** записи. Приводит к "зависаниям" (stalls).

**Настройка под нагрузки:**

* **Медленные диски (HDD)**: Увеличить лимиты (например, 10/40), чтобы объединить мелкие записи в большие последовательные блоки.
* **Быстрые диски (SSD/NVMe) + много RAM**: Уменьшить лимиты (например, 5/10), чтобы избежать "I/O storms" (внезапных сбросов десятков гигабайт данных).
* **Критичные к потере данных данные**: Минимизировать лимиты и `dirty_expire_centisecs` для быстрой фиксации на диске.

### HugePages и Transparent Huge Pages (THP)

#### Проблема TLB и таблиц страниц

1. **TLB Miss**: При использовании стандартных страниц (4 КБ) в современных системах с сотнями ГБ RAM кэш TLB быстро переполняется. Каждый промах требует **page table walk** (4 обращения к RAM), что резко снижает IPC (instructions per cycle).
2. **Накладные расходы Page Tables**: PTE для огромных адресных пространств могут занимать гигабайты RAM (т.к. они невыгружаемые — `SUnreclaim`).

**HugePages решают обе проблемы**: одна запись в TLB/PTE покрывает 2 МБ или 1 ГБ, снижая давление на кэш и объем метаданных.

#### Standard HugePages vs THP

| Характеристика | THP (Transparent) | Standard HugePages |
| :--- | :--- | :--- |
| **Управление** | Автоматическое (ядро) | Ручное (администратор) |
| **Прозрачность** | Да (не требует правок кода) | Нет (требует hugetlbfs/mmap) |
| **Предсказуемость** | Низкая (возможны Latency Spikes) | Высокая (фиксированный пул) |

**Latensy Spikes при THP**: Возникают из-за работы `khugepaged` (слияние страниц) и `kcompactd` (дефрагментация). В моменты дефрагментации процессы могут блокироваться (`compact_stall`).

**Рекомендация для СУБД**: Отключить THP и использовать **Standard HugePages**. Это критично для Oracle, PostgreSQL, MongoDB, SAP HANA.

## Практические сценарии

### Диагностика узких мест памяти

#### Проверка TLB и производительности

```bash
# Проверка TLB miss rate (если > 1-5% — нужны HugePages)
perf stat -e dTLB-load-misses,dTLB-loads -a sleep 10

# Проверка Page Faults
perf stat -e minor-faults,major-faults -p <PID>
```

#### Анализ фрагментации и дефрагментации

```bash
# Проверка задержек из-за дефрагментации (compaction stalls)
cat /proc/vmstat | grep compact_stall

# Анализ свободных блоков (если мало блоков высокого order — память фрагментирована)
cat /proc/buddyinfo
```

#### Проверка использования HugePages процессом

```bash
# Сколько анонимных huge pages использует процесс
grep AnonHugePages /proc/<PID>/smaps | awk '{sum+=$2} END {print sum}'

# Проверка распределения по NUMA-узлам
numastat -p <PID>
```

### Настройка параметров ядра

```bash
# Отключение THP (рекомендуется для баз данных)
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/defrag

# Резервирование 1024 HugePages (2 ГБ)
sudo sysctl -w vm.nr_hugepages=1024

# Настройка строгого режима Overcommit
sudo sysctl -w vm.overcommit_memory=2
sudo sysctl -w vm.overcommit_ratio=80
```

### Оптимизация NUMA

```bash
# Запуск процесса с привязкой к узлу 0 (ядра и память)
numactl --cpunodebind=0 --membind=0 ./my_app

# Просмотр топологии системы
numactl --hardware
```

### Использование кастомных аллокаторов

Стандартный `malloc` из `glibc` может вызывать фрагментацию в многопоточных средах.
**Решение**: Использование `jemalloc` или `tcmalloc`.

```bash
# Запуск приложения с jemalloc без перекомпиляции
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 ./my_app
```

## Дополнительная информация

### Влияние `vfs_cache_pressure`

Параметр `vm.vfs_cache_pressure` контролирует агрессивность очистки кэша dentry/inode (метаданные ФС).

* **`100` (default)**: Баланс.
* **`< 100`**: Ядро дольше хранит метаданные в RAM. Ускоряет `ls`, `find`, но снижает объем памяти для данных.
* **`> 100`**: Агрессивная очистка. Полезно, если метаданные вытесняют рабочие данные приложения.

### Проверка потребления RAM таблицами страниц

Если `free` показывает большой расход RAM, но RSS процессов мал, проверьте `Pagetables`:

```bash
cat /proc/meminfo | grep Pagetables
# Если значение измеряется гигабайтами — переходите на HugePages
```

Подробнее о метриках ядра см. в [Диагностика /proc/meminfo](../../Diagnostics/Memory/proc_meminfo.md).
