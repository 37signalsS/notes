# Оптимизация и тонкая настройка памяти

## Определения

* **Memory Overcommit**: Механизм ядра, позволяющий процессам запрашивать больше виртуальной памяти, чем физически доступно в системе (RAM + swap).
* **OOM Killer (Out of Memory Killer)**: Механизм ядра, принудительно завершающий процессы для освобождения памяти при её острой нехватке. Подробнее см. в [Лимиты ресурсов и OOM Killer](../processes/limits.md).
* **KSM (Kernel Samepage Merging)**: Фоновый процесс, объединяющий идентичные страницы памяти в одну физическую страницу с пометкой "copy-on-write" для экономии RAM.
* **NUMA (Non-Uniform Memory Access)**: Архитектура памяти в многопроцессорных системах, где память разделена на "узлы". Процессор имеет быстрый доступ к локальному узлу и медленный — к удаленным.
* **HugePages (HugeTLB)**: Страницы памяти большого размера (2 МБ или 1 ГБ), используемые для снижения накладных расходов на управление памятью.
* **Transparent Huge Pages (THP)**: Автоматический механизм ядра, пытающийся "прозрачно" объединять обычные страницы в HugePages.

## Основные концепции

### Memory Overcommit

* **Преимущество**: Позволяет запустить больше приложений, резервирующих память "про запас".
* **Риск**: При одновременном использовании всей зарезервированной памяти приводит к вызову **OOM Killer**.

### KSM: Дедупликация памяти

* **Принцип**: KSM объединяет одинаковые страницы. При записи создается персональная копия (Copy-on-Write).
* **Плюсы**: Экономит RAM в средах с дублирующимися данными (виртуализация, контейнеры).
* **Минусы**: Потребляет CPU, может вызывать задержки при CoW.

### NUMA: Локальность памяти

* **Проблема**: Процесс на одном CPU, работающий с памятью на удаленном узле, снижает производительность из-за задержек.
* **Цель**: Обеспечить **локальность NUMA** — размещение процесса и памяти на одном узле. Для управления используются `numactl` и [привязка к CPU](../kernel/cpu_pinning.md).

#### Почему это проблема для БД?
Производительность баз данных крайне чувствительна к задержкам доступа к памяти (memory latency). Если процесс СУБД, исполняемый на одном NUMA-узле, вынужден постоянно обращаться к данным, расположенным в памяти другого (удаленного) узла, эти многочисленные медленные доступы становятся серьезным узким местом, деградируя общую производительность.

#### Как с этим бороться?
Основной метод борьбы — принудительная локализация процесса и его памяти в рамках одного NUMA-узла. Утилита `numactl` является стандартным инструментом для этого.

### Управление Swap (подкачкой)

Swap — дисковое пространство для выгрузки неактивных страниц RAM. Параметр `vm.swappiness` контролирует агрессивность использования swap.
Подробное описание см. в [Управление Swap (файлом подкачки)](swap_management.md).

### Кэш Dirty Pages
#### Определения
*   **Dirty Pages (Грязные страницы):** Это страницы в оперативной памяти (page cache), которые были изменены, но еще не записаны на диск.
*   **`vm.dirty_background_ratio`:** Процент системной памяти, по достижении которого фоновые потоки ядра (`pdflush`/`flusher`) начинают асинхронно записывать "грязные" страницы на диск. **Процессы при этом не блокируются.**
*   **`vm.dirty_ratio`:** Процент системной памяти, по достижении которого все процессы, генерирующие дисковый ввод-вывод, принудительно переключаются в режим **синхронной записи**. Это блокирует процесс до тех пор, пока данные не будут записаны, что может вызывать видимые "зависания" приложений.

#### Для чего это нужно и где применяется?
Эта пара параметров контролирует баланс между производительностью дисковой записи и риском потери данных.
*   **Высокая производительность:** Позволяя ядру кэшировать большое количество записей в RAM, система может объединять множество мелких операций в одну большую последовательную запись, что значительно эффективнее для HDD.
*   **Контроль использования памяти:** Ограничивает объем RAM, занимаемый под кэш записи, чтобы не допустить вытеснения полезных данных (кэш чтения, память приложений).

#### Где делать меньше, где больше?
*   **Уменьшать значения** (например, `dirty_background_ratio=5`, `dirty_ratio=10`):
    *   **Системы с быстрыми дисками (SSD/NVMe):** Быстрые диски не получают большого выигрыша от кэширования записи. Меньшие значения обеспечивают более равномерную нагрузку на диск и предотвращают большие всплески I/O.
    *   **Базы данных и критичные системы:** Необходимо минимизировать риск потери данных при сбое питания. Частая запись на диск уменьшает окно, в котором данные существуют только в RAM.
    *   **Предотвращение "зависаний":** На системах с большим объемом RAM высокий `dirty_ratio` может означать гигабайты данных, которые должны быть синхронно сброшены на диск, вызывая длинные паузы.
*   **Увеличивать значения:**
    *   **Системы с медленными дисками (HDD):** Позволяет ядру накопить больше данных для их последующей эффективной последовательной записи.
    *   **Нагрузки с большим количеством мелких записей:** Например, интенсивное логирование. Кэширование позволяет "сгладить" нагрузку на диск.

### HugePages и Transparent Huge Pages (THP)

#### Standard HugePages (HugeTLB)

Страницы памяти большого размера (2 МБ или 1 ГБ).

* **Преимущества**:
  * **Снижение нагрузки на TLB**: Меньше промахов TLB, ускоряет доступ к памяти.
  * **Уменьшение размера таблиц страниц**: Меньше записей для того же объема памяти.

#### Transparent Huge Pages (THP)

Механизм ядра, автоматически объединяющий обычные страницы (4 КБ) в "огромные" (2 МБ). Работает "прозрачно" для приложений.

#### Сравнение и ключевые различия

| Характеристика | Transparent Huge Pages (THP) | Standard HugePages (HugeTLB) |
| :--- | :--- | :--- |
| **Управление** | **Автоматическое.** Ядро само решает, когда объединять страницы. | **Ручное.** Администратор должен заранее зарезервировать пул страниц. |
| **Прозрачность** | **Да.** Приложения не знают, что работают с большими страницами. | **Нет.** Приложения должны быть модифицированы для использования `hugetlbfs`. |
| **Гибкость** | Высокая. Страницы могут быть динамически разделены обратно на 4 КБ. | Низкая. Память резервируется и не может быть использована для других нужд. |
| **Производительность** | Может вызывать **непредсказуемые задержки** из-за фоновой работы по слиянию и дефрагментации памяти. | Обеспечивает **предсказуемую высокую производительность**, так как страницы выделяются сразу. |

#### Проблемы и рекомендации для THP

Автоматическое поведение THP может создавать серьезные проблемы для высокопроизводительных приложений (например, баз данных). Основная причина — **непредсказуемые задержки (latency spikes)**, вызванные фоновой работой системного процесса `khugepaged`. Этот процесс постоянно сканирует память, пытаясь найти смежные 4-килобайтные страницы для их объединения в одну 2-мегабайтную. На время этого процесса (включая перемещение страниц и обновление таблиц страниц) могут возникать короткие, но критичные "зависания" (stalls), которые неприемлемы для СУБД, требующих стабильного и низкого времени отклика.

**Для баз данных, таких как Oracle, PostgreSQL, MongoDB, и других систем, чувствительных к задержкам, общепринятой лучшей практикой является отключение THP** и использование предварительно выделенных **Standard HugePages**. Это обеспечивает предсказуемую производительность без случайных пауз.

## Практические сценарии

### Управление Memory Overcommit

Регулируется параметром `vm.overcommit_memory`:

* `0` (по умолчанию): Эвристика. Отклоняет очевидно "жадные" запросы.
* `1`: Разрешать всегда. Повышает риск OOM.
* `2`: Не разрешать. Строгое ограничение (`SwapTotal + RAM * overcommit_ratio`). Полезно для СУБД.

```bash
# Установить строгий режим (не разрешать overcommit)
sudo sysctl -w vm.overcommit_memory=2
```

### Управление NUMA с `numactl`

```bash
# Запустить my_app на узле CPU 0 и выделять память только с этого узла
numactl --cpunodebind=0 --membind=0 my_app
```

### Настройка HugePages

```bash
# Выделить 1024 страницы по 2 МБ (всего 2 ГБ)
sudo sysctl -w vm.nr_hugepages=1024
```

### Управление THP

Проверка статуса:

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never
```

* `always`: THP включен для всех процессов.
* `madvise`: THP включен только для процессов, которые явно запросили это через системный вызов `madvise()`.
* `never`: THP полностью отключен.

Отключение до перезагрузки:

```bash
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/defrag
```

## Дополнительная информация

### Параметр ядра `vfs_cache_pressure`

Контролирует агрессивность освобождения ядром памяти для кэширования **dentry** и **inode**, хранящихся с помощью [Slab Allocator](slab_allocator.md).

* **Значение по умолчанию: `100`**. Ядро быстро освобождает кэш inode/dentry.
* **Низкое значение (например, `50`):** Ядро дольше хранит кэш, может ускорить доступ к файлам, но увеличивает риск нехватки памяти для процессов.
* **Высокое значение (более `100`):** Ядро очень агрессивно очищает кэш метаданных.

```bash
sudo sysctl -w vm.vfs_cache_pressure=50
```
