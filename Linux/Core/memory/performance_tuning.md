# Оптимизация и тонкая настройка памяти

## Определения

* **Memory Overcommit**: Режим работы ядра, при котором процессам разрешается запрашивать (но не обязательно использовать) больше виртуальной памяти, чем доступно физически (RAM + Swap).
* **OOM Killer (Out of Memory Killer)**: Механизм ядра, который выбирает и завершает процесс (на основе `oom_score`) для спасения системы при критической нехватке памяти. Подробнее: **[Механизм OOM Killer](../processes/oom_killer_mechanism.md)**.
* **MGLRU (Multi-Gen LRU)**: Современный алгоритм управления страницами (с ядра 6.1), заменяющий классический двухуровневый LRU. Группирует страницы по "поколениям" доступа, что снижает накладные расходы на CPU и повышает точность выбора кандидатов на выгрузку.
* **NUMA (Non-Uniform Memory Access)**: Архитектура многопроцессорных систем, где время доступа к памяти зависит от расположения процессора относительно модуля RAM.
* **HugePages**: Механизм использования страниц памяти большого размера (2 МБ или 1 ГБ вместо 4 КБ) для минимизации объема таблиц страниц и снижения промахов TLB.
* **TLB (Translation Lookaside Buffer)**: Аппаратный кэш процессора для быстрого преобразования виртуальных адресов в физические.
* **Dirty Pages (Грязные страницы)**: Модифицированные данные в оперативной памяти, ожидающие записи на диск (Writeback).
* **Watermarks (Вотермарки)**: Пороги свободной памяти (`min`, `low`, `high`), при достижении которых ядро начинает фоновое (`kswapd`) или прямое (`direct reclaim`) освобождение памяти.

## Основные концепции

### Режимы Overcommit (vm.overcommit_memory)

Ядро поддерживает три стратегии выделения памяти:
1. **`0` (Heuristic)**: Ядро использует эвристику, чтобы отклонять явно избыточные запросы (по умолчанию).
2. **`1` (Always)**: Все запросы на выделение памяти одобряются. Рискованно, но полезно для приложений с разреженными массивами данных (Sparse arrays).
3. **`2` (Strict)**: Общий объем выделяемой памяти не может превышать лимит: `SwapTotal + (RAM * overcommit_ratio / 100)`. Рекомендуется для обеспечения предсказуемости и предотвращения хаотичного OOM.

### Тюнинг Dirty Pages и Writeback

Параметры `vm.dirty_*` критичны для производительности дискового ввода-вывода.
* **`vm.dirty_background_ratio`**: Порог асинхронного сброса.
* **`vm.dirty_ratio`**: Порог блокирующего (синхронного) сброса.

Подробные профили настройки (БД, Файловые серверы, HDD/SSD) см. в: **[Настройка writeback](../../Diagnostics/Performance/DiskIO/writeback_tuning.md)**.

### Управление вотермарками и агрессивностью очистки

Если система "фризит" при выделении памяти, хотя `MemAvailable` еще велик, может потребоваться настройка вотермарков:
* **`vm.watermark_scale_factor`**: Увеличивает зазор между `min`, `low` и `high`. Позволяет `kswapd` проснуться раньше и подготовить свободные страницы до того, как процессы заблокируются в `direct reclaim`. (Типовое значение: `100–500`).
* **`vm.vfs_cache_pressure`**: Баланс между очисткой Page Cache и кэшем метаданных (inode/dentry). Подробнее: **[Slab Allocator](./slab_allocator.md)**.

### Алгоритм MGLRU (Multi-Gen LRU)

В новых ядрах (>= 6.1) рекомендуется убедиться, что MGLRU включен. Он значительно эффективнее работает в условиях Memory Pressure.
```bash
# Проверка (должен быть не 0)
cat /sys/kernel/mm/lru_gen/enabled
```

### HugePages и THP (Transparent Huge Pages)

#### Проблема TLB
На серверах с сотнями ГБ RAM стандартные страницы по 4 КБ создают огромные таблицы страниц (Pagetables), которые могут занимать гигабайты и не вытесняются в swap. Огромные страницы снижают эти накладные расходы.

| Тип | Плюсы | Минусы |
| :--- | :--- | :--- |
| **Standard HugePages** | Гарантированная память, отсутствие задержек на выделение. | Требует настройки приложения и резервирования при загрузке. |
| **THP** | Прозрачность для приложений. | Возможны задержки (Latency Spikes) из-за работы `khugepaged` и фрагментации. |

**Рекомендация**: Для высоконагруженных СУБД (PostgreSQL, Oracle, ClickHouse) отключайте THP и используйте явные HugePages.

## Практические сценарии

### Диагностика узких мест

#### Проверка TLB и Page Tables
Если `Pagetables` в `/proc/meminfo` растут выше 1-2 ГБ, это прямой сигнал к переходу на HugePages.
```bash
grep Pagetables /proc/meminfo
```

#### Проверка задержек из-за фрагментации
```bash
cat /proc/vmstat | grep compact_stall
# Рост счетчика означает, что процессы ждут дефрагментации памяти для выделения HugePages.
```

### Настройка под нагрузку базы данных

Типовой профиль для PostgreSQL/MySQL на выделенном сервере:
```bash
# Минимизация свопинга
vm.swappiness = 1
# Строгий контроль выделения (защита от OOM)
vm.overcommit_memory = 2
vm.overcommit_ratio = 80
# Тюнинг Dirty Pages для избежания "I/O storms"
vm.dirty_ratio = 10
vm.dirty_background_ratio = 5
# Отключение агрессивной дефрагментации HugePages
echo never > /sys/kernel/mm/transparent_hugepage/enabled
```

### Оптимизация NUMA

В мультисокетных системах важно избегать ситуации, когда процесс на сокете 0 обращается к памяти на сокете 1.
* **`kernel.numa_balancing = 1`**: Разрешает ядру автоматически перемещать страницы ближе к использующим их ядрам.
* **`numactl`**: Используется для принудительной привязки процесса к узлу.
```bash
# Запуск процесса строго на узле 0
numactl --cpunodebind=0 --membind=0 my_application
```
