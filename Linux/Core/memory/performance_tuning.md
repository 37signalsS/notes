## Оптимизация и тонкая настройка памяти

### Управление выделением памяти (Memory Overcommit)

**Memory Overcommit** — это механизм ядра, который позволяет процессам запрашивать (выделять) больше виртуальной памяти, чем физически доступно в системе (RAM + swap). Это возможно, потому что программы часто резервируют память "про запас", но не используют её всю сразу.

#### Риски и преимущества

-   **Преимущество:** Повышает эффективность использования памяти на системах, где запущено много процессов, каждый из которых резервирует больше памяти, чем реально использует. Это позволяет запустить больше приложений на той же системе.
-   **Риск:** Если процессы внезапно начнут использовать ранее зарезервированную память, физическая память может закончиться. Это приведет к вызову **OOM Killer**, который принудительно завершит один или несколько процессов для освобождения ресурсов.

#### Режимы работы

Поведение этого механизма регулируется параметром `vm.overcommit_memory`:

-   `0` (Heuristic overcommit handling, по умолчанию): Ядро использует эвристику для оценки, достаточно ли памяти. Очевидно "жадные" запросы, которые могут привести к переполнению, отклоняются.
-   `1` (Always overcommit): Ядро всегда разрешает выделение памяти, каким бы большим ни был запрос. Этот режим может быть полезен для некоторых научных вычислений, но повышает риск вызова OOM Killer.
-   `2` (Don't overcommit): Ядро строго запрещает выделять больше виртуальной памяти, чем доступно (`SwapTotal + (RAM * vm.overcommit_ratio / 100)`). `vm.overcommit_ratio` — это процент RAM, который можно выделить сверх swap (по умолчанию 50%). Этот режим полезен для служб, где стабильность важнее эффективности использования памяти (например, для баз данных).

Настройка производится через `sysctl`:

```bash
sudo sysctl -w vm.overcommit_memory=1
```

### Оптимизация памяти: Kernel Samepage Merging (KSM)

**KSM (Kernel Samepage Merging)** — это фоновый процесс в ядре, который сканирует память и ищет идентичные страницы. Если он находит две или более одинаковые страницы, он объединяет их в одну, помечая её как "copy-on-write" (CoW).

**Как это работает:**

1.  KSM объединяет одинаковые страницы в одну физическую страницу.
2.  Если какой-либо процесс пытается изменить эту страницу, ядро автоматически создает для него копию, и только после этого процесс вносит изменения.

**Где используется:**

-   **Системы виртуализации (KVM, QEMU):** Для дедупликации памяти между множеством однотипных гостевых ОС.
-   **Контейнерные среды:** Для экономии памяти при запуске большого количества одинаковых контейнеров.

**Плюсы и минусы:**

-   **Плюс:** Значительно сокращает потребление RAM в средах с высокой степенью дублирования данных.
-   **Минус:** Потребляет ресурсы CPU на постоянное сканирование памяти и может вызывать небольшие задержки при первой записи в "объединенную" страницу из-за необходимости выполнить операцию Copy-on-Write.

KSM управляется через файлы в `/sys/kernel/mm/ksm/`.

### Оптимизация для архитектуры NUMA

**NUMA (Non-Uniform Memory Access)** — это архитектура построения памяти, используемая в многопроцессорных системах. В ней память физически разделена на "узлы" (nodes), и каждый процессор (или группа ядер) имеет быстрый локальный доступ к своему узлу памяти, но более медленный доступ к памяти других узлов.

**Проблема:** Если процесс, выполняющийся на одном процессоре, постоянно обращается к памяти, расположенной на другом узле, возникают задержки, снижающие производительность.

**Оптимизация:**

Основная стратегия — обеспечить **локальность NUMA**, то есть сделать так, чтобы процесс и память, с которой он работает, находились на одном и том же узле.

-   **`numactl`**: Это основная утилита для управления политиками NUMA. Она позволяет принудительно запускать процесс на определённом узле и выделять ему память только из этого узла.
    ```bash
    # Запустить процесс my_app на узле 0 и выделять ему память только оттуда
    numactl --cpunodebind=0 --membind=0 my_app
    ```

### Использование HugePages

**HugePages** — это страницы памяти большого размера (обычно 2 МБ или 1 ГБ вместо стандартных 4 КБ). Их использование позволяет сократить накладные расходы на управление памятью.

**Преимущества:**

-   **Снижение нагрузки на TLB (Translation Lookaside Buffer):** TLB — это кэш процессора для трансляции виртуальных адресов в физические. Использование меньшего количества больших страниц вместо огромного количества маленьких снижает вероятность промахов в TLB, ускоряя доступ к памяти.
-   **Уменьшение размера таблиц страниц:** Требуется меньше записей для отображения того же объёма памяти.

**Применение:**

HugePages особенно полезны для приложений, работающих с большими объёмами непрерывной памяти, таких как базы данных (Oracle, PostgreSQL) и системы виртуализации (KVM).

**Активация:**

Количество HugePages настраивается через параметр ядра:

```bash
# Выделить 1024 страницы по 2 МБ (всего 2 ГБ)
sudo sysctl -w vm.nr_hugepages=1024
```

### Transparent Huge Pages (THP)

**Transparent Huge Pages (THP)** — это механизм ядра Linux, который работает в фоновом режиме и пытается автоматически объединять обычные страницы памяти (4 КБ) в "огромные" страницы (2 МБ). Цель та же, что и у `HugePages` — снизить накладные расходы на управление памятью и ускорить доступ за счет более эффективного использования TLB.

Ключевое слово здесь — **"прозрачный" (Transparent)**. В отличие от стандартных `HugePages`, которые требуют ручной настройки и резервирования, THP работает автоматически без необходимости внесения изменений в код приложений.

#### Как это работает

Ядро постоянно сканирует память и, если находит смежные 4-килобайтные страницы, которые можно объединить в одну 2-мегабайтную, выполняет их слияние (defrag/compaction).

#### THP vs HugePages (HugeTLB)

| Характеристика | Transparent Huge Pages (THP) | Standard HugePages (HugeTLB) |
| :--- | :--- | :--- |
| **Управление** | **Автоматическое.** Ядро само решает, когда объединять страницы. | **Ручное.** Администратор должен заранее зарезервировать пул страниц. |
| **Прозрачность** | **Да.** Приложения не знают, что работают с большими страницами. | **Нет.** Приложения должны быть модифицированы для использования `hugetlbfs`. |
| **Гибкость** | Высокая. Страницы могут быть динамически разделены обратно на 4 КБ. | Низкая. Память резервируется и не может быть использована для других нужд. |
| **Производительность** | Может вызывать **непредсказуемые задержки** из-за фоновой работы по слиянию и дефрагментации памяти. | Обеспечивает **предсказуемую высокую производительность**, так как страницы выделяются сразу. |

#### Проблемы и рекомендации

Несмотря на кажущееся удобство, автоматическое поведение THP часто создает проблемы для высокопроизводительных приложений, особенно для баз данных (MongoDB, Redis, Oracle и др.). Процесс дефрагментации (`kcompactd`) может блокировать доступ к памяти, вызывая короткие, но критичные "зависания" (latency spikes).

**Поэтому для многих серверных нагрузок рекомендуется отключать THP.**

#### Управление THP

-   **Проверить текущий режим:**

    ```bash
    cat /sys/kernel/mm/transparent_hugepage/enabled
    # [always] madvise never
    ```
    -   `always`: THP включен для всех процессов.
    -   `madvise`: THP включен только для процессов, которые явно запросили это через системный вызов `madvise()`.
    -   `never`: THP полностью отключен.

-   **Отключить THP (временно, до перезагрузки):**

    ```bash
    echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
    echo never | sudo tee /sys/kernel/mm/transparent_hugepage/defrag
    ```

Для постоянного отключения необходимо добавить эти команды в стартовый скрипт (например, `/etc/rc.local`) или использовать параметры загрузки ядра (`transparent_hugepage=never`).

### Параметр ядра `vfs_cache_pressure`

Этот параметр контролирует, насколько агрессивно ядро будет освобождать память, используемую для кэширования **dentry** (записи каталогов) и **inode** (метаданные файлов).

-   **Значение по умолчанию: `100`**. Ядро быстро освобождает кэш inode/dentry.
-   **Низкое значение (например, `50`):** Ядро будет дольше хранить этот кэш в памяти. Это может ускорить доступ к файлам на системах с большим количеством файлов, но увеличит риск нехватки памяти для процессов.
-   **Высокое значение (более `100`):** Ядро будет очень агрессивно очищать кэш метаданных.

Настройка производится аналогично `swappiness` через `sysctl`:

```bash
sudo sysctl -w vm.vfs_cache_pressure=50
```
