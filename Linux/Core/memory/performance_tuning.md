## Оптимизация и тонкая настройка памяти

### 1. Определения

**Memory Overcommit** - Механизм ядра, который позволяет процессам запрашивать больше виртуальной памяти, чем физически доступно в системе (RAM + swap).

**OOM Killer (Out of Memory Killer)** - Механизм ядра, который принудительно завершает процессы для освобождения памяти при ее острой нехватке. Выбор "жертвы" зависит от множества факторов, подробнее см. в **[[../processes/limits.md|Лимиты ресурсов и OOM Killer]]**.

**KSM (Kernel Samepage Merging)** - Фоновый процесс в ядре, который сканирует память, находит идентичные страницы, объединяет их в одну физическую страницу и помечает её как "copy-on-write" (CoW) для экономии RAM.

**NUMA (Non-Uniform Memory Access)** - Архитектура памяти в многопроцессорных системах, где память разделена на "узлы" (nodes). Процессор имеет быстрый доступ к своему локальному узлу памяти и более медленный — к удаленным узлам.

**HugePages (HugeTLB)** - Страницы памяти большого размера (обычно 2 МБ или 1 ГБ вместо стандартных 4 КБ), которые требуют ручной настройки и используются для снижения накладных расходов на управление памятью для высокопроизводительных приложений.

**Transparent Huge Pages (THP)** - Автоматический механизм ядра, который пытается "прозрачно" для приложений объединять обычные страницы в HugePages.

### 2. Основные концепции

#### Memory Overcommit

-   **Преимущество:** Позволяет запустить больше приложений, так как они часто резервируют память "про запас", но не используют её всю.
-   **Риск:** Если процессы начнут одновременно использовать всю зарезервированную память, это приведет к вызову **OOM Killer**.

#### KSM: Дедупликация памяти

-   **Как работает:** KSM объединяет одинаковые страницы. При попытке записи в такую страницу ядро создает для процесса её персональную копию (Copy-on-Write).
-   **Плюсы:** Значительно экономит RAM в средах с дублирующимися данными (виртуализация, контейнеры).
-   **Минусы:** Потребляет CPU на сканирование и может вызывать небольшие задержки при CoW.

#### NUMA: Локальность памяти

-   **Проблема:** Если процесс на CPU 0 постоянно работает с памятью на узле 1, производительность падает из-за задержек доступа к удаленной памяти.
-   **Цель оптимизации:** Обеспечить **локальность NUMA** — разместить процесс и используемую им память на одном и том же узле. Для управления локальностью NUMA используются утилиты `numactl`, а также механизмы **[[../kernel/cpu_pinning.md|привязки к CPU]]**.

#### Управление Swap (подкачкой)

Swap — это дисковое пространство, используемое при нехватке RAM. Правильная настройка swap критически важна для стабильности системы. Ключевой параметр `vm.swappiness` контролирует, насколько агрессивно ядро будет использовать swap.

> Подробное описание механизмов работы, настройки и тюнинга swap-пространства см. в отдельной заметке: **[[swap_management.md|Управление Swap (файлом подкачки)]]**.

#### HugePages и Transparent Huge Pages (THP)

##### Standard HugePages (HugeTLB)

HugePages — это страницы памяти большого размера (обычно 2 МБ или 1 ГБ), использование которых позволяет сократить накладные расходы на управление памятью. Они особенно полезны для приложений, работающих с большими объёмами непрерывной памяти, таких как базы данных (Oracle, PostgreSQL) и системы виртуализации (KVM).

**Преимущества:**

-   **Снижение нагрузки на TLB (Translation Lookaside Buffer):** TLB — это кэш процессора для трансляции виртуальных адресов в физические. Использование меньшего количества больших страниц вместо огромного количества маленьких снижает вероятность промахов в TLB, ускоряя доступ к памяти.
-   **Уменьшение размера таблиц страниц:** Требуется меньше записей для отображения того же объёма памяти.

##### Transparent Huge Pages (THP)

THP — это механизм ядра, который работает в фоновом режиме и пытается автоматически объединять обычные страницы памяти (4 КБ) в "огромные" страницы (2 МБ). Ключевое слово здесь — **"прозрачный" (Transparent)**, так как THP работает автоматически без необходимости внесения изменений в код приложений. Ядро постоянно сканирует память и, если находит смежные 4-килобайтные страницы, которые можно объединить, выполняет их слияние.

##### Сравнение и ключевые различия

| Характеристика | Transparent Huge Pages (THP) | Standard HugePages (HugeTLB) |
| :--- | :--- | :--- |
| **Управление** | **Автоматическое.** Ядро само решает, когда объединять страницы. | **Ручное.** Администратор должен заранее зарезервировать пул страниц. |
| **Прозрачность** | **Да.** Приложения не знают, что работают с большими страницами. | **Нет.** Приложения должны быть модифицированы для использования `hugetlbfs`. |
| **Гибкость** | Высокая. Страницы могут быть динамически разделены обратно на 4 КБ. | Низкая. Память резервируется и не может быть использована для других нужд. |
| **Производительность** | Может вызывать **непредсказуемые задержки** из-за фоновой работы по слиянию и дефрагментации памяти. | Обеспечивает **предсказуемую высокую производительность**, так как страницы выделяются сразу. |

##### Проблемы и рекомендации для THP

Несмотря на кажущееся удобство, автоматическое поведение THP часто создает проблемы для высокопроизводительных приложений, особенно для баз данных (MongoDB, Redis, Oracle и др.). Фоновый процесс дефрагментации (`kcompactd`) может блокировать доступ к памяти, вызывая короткие, но критичные "зависания" (latency spikes).

**Поэтому для многих серверных нагрузок рекомендуется отключать THP.**

### 3. Практические сценарии

#### Управление Memory Overcommit

Регулируется параметром `vm.overcommit_memory`:

- `0` (по умолчанию): Эвристика. Отклоняет очевидно "жадные" запросы.
- `1`: Разрешать всегда. Повышает риск OOM.
- `2`: Не разрешать. Строгое ограничение (`SwapTotal + RAM * overcommit_ratio`). Полезно для СУБД.

```bash
# Установить строгий режим (не разрешать overcommit)
sudo sysctl -w vm.overcommit_memory=2
```

#### Управление NUMA с `numactl`

```bash
# Запустить my_app на узле CPU 0 и выделять память только с этого узла
numactl --cpunodebind=0 --membind=0 my_app
```

#### Настройка HugePages

```bash
# Выделить 1024 страницы по 2 МБ (всего 2 ГБ)
sudo sysctl -w vm.nr_hugepages=1024
```

#### Управление THP

Проверка статуса:

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never
```
-   `always`: THP включен для всех процессов.
-   `madvise`: THP включен только для процессов, которые явно запросили это через системный вызов `madvise()`.
-   `never`: THP полностью отключен.

Отключение до перезагрузки:
```bash
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/defrag
```

### 4. Продвинутые детали

#### Параметр ядра `vfs_cache_pressure`

Этот параметр контролирует, насколько агрессивно ядро будет освобождать память, используемую для кэширования **dentry** (записи каталогов) и **inode** (метаданные файлов), которые хранятся с помощью механизма **[Slab Allocator](slab_allocator.md)**.

-   **Значение по умолчанию: `100`**. Ядро быстро освобождает кэш inode/dentry.
-   **Низкое значение (например, `50`):** Ядро будет дольше хранить этот кэш в памяти. Это может ускорить доступ к файлам на системах с большим количеством файлов, но увеличит риск нехватки памяти для процессов.
-   **Высокое значение (более `100`):** Ядро будет очень агрессивно очищать кэш метаданных.

```bash
sudo sysctl -w vm.vfs_cache_pressure=50
```
