# Оптимизация и тонкая настройка памяти

## Определения

* **Memory Overcommit**: Механизм ядра, позволяющий процессам запрашивать больше виртуальной памяти, чем физически доступно в системе (RAM + swap).
* **OOM Killer (Out of Memory Killer)**: Механизм ядра, принудительно завершающий процессы для освобождения памяти при её острой нехватке. Подробнее см. в [[../processes/limits.md|Лимиты ресурсов и OOM Killer]].
* **KSM (Kernel Samepage Merging)**: Фоновый процесс, объединяющий идентичные страницы памяти в одну физическую страницу с пометкой "copy-on-write" для экономии RAM.
* **NUMA (Non-Uniform Memory Access)**: Архитектура памяти в многопроцессорных системах, где память разделена на "узлы". Процессор имеет быстрый доступ к локальному узлу и медленный — к удаленным.
* **HugePages (HugeTLB)**: Страницы памяти большого размера (2 МБ или 1 ГБ), используемые для снижения накладных расходов на управление памятью.
* **Transparent Huge Pages (THP)**: Автоматический механизм ядра, пытающийся "прозрачно" объединять обычные страницы в HugePages.

## Основные концепции

### Memory Overcommit

* **Преимущество**: Позволяет запустить больше приложений, резервирующих память "про запас".
* **Риск**: При одновременном использовании всей зарезервированной памяти приводит к вызову **OOM Killer**.

### KSM: Дедупликация памяти

* **Принцип**: KSM объединяет одинаковые страницы. При записи создается персональная копия (Copy-on-Write).
* **Плюсы**: Экономит RAM в средах с дублирующимися данными (виртуализация, контейнеры).
* **Минусы**: Потребляет CPU, может вызывать задержки при CoW.

### NUMA: Локальность памяти

* **Проблема**: Процесс на одном CPU, работающий с памятью на удаленном узле, снижает производительность из-за задержек.
* **Цель**: Обеспечить **локальность NUMA** — размещение процесса и памяти на одном узле. Для управления используются `numactl` и [[../kernel/cpu_pinning.md|привязка к CPU]].

### Управление Swap (подкачкой)

Swap — дисковое пространство для выгрузки неактивных страниц RAM. Параметр `vm.swappiness` контролирует агрессивность использования swap.
Подробное описание см. в [[swap_management.md|Управление Swap (файлом подкачки)]].

### HugePages и Transparent Huge Pages (THP)

#### Standard HugePages (HugeTLB)

Страницы памяти большого размера (2 МБ или 1 ГБ).

* **Преимущества**:
  * **Снижение нагрузки на TLB**: Меньше промахов TLB, ускоряет доступ к памяти.
  * **Уменьшение размера таблиц страниц**: Меньше записей для того же объема памяти.

#### Transparent Huge Pages (THP)

Механизм ядра, автоматически объединяющий обычные страницы (4 КБ) в "огромные" (2 МБ). Работает "прозрачно" для приложений.

#### Сравнение и ключевые различия

| Характеристика | Transparent Huge Pages (THP) | Standard HugePages (HugeTLB) |
| :--- | :--- | :--- |
| **Управление** | **Автоматическое.** Ядро само решает, когда объединять страницы. | **Ручное.** Администратор должен заранее зарезервировать пул страниц. |
| **Прозрачность** | **Да.** Приложения не знают, что работают с большими страницами. | **Нет.** Приложения должны быть модифицированы для использования `hugetlbfs`. |
| **Гибкость** | Высокая. Страницы могут быть динамически разделены обратно на 4 КБ. | Низкая. Память резервируется и не может быть использована для других нужд. |
| **Производительность** | Может вызывать **непредсказуемые задержки** из-за фоновой работы по слиянию и дефрагментации памяти. | Обеспечивает **предсказуемую высокую производительность**, так как страницы выделяются сразу. |

#### Проблемы и рекомендации для THP

Автоматическое поведение THP может создавать проблемы для высокопроизводительных приложений (например, баз данных) из-за "зависаний" (latency spikes), вызванных фоновой дефрагментацией.

**Рекомендуется отключать THP для многих серверных нагрузок.**

## Практические сценарии

### Управление Memory Overcommit

Регулируется параметром `vm.overcommit_memory`:

* `0` (по умолчанию): Эвристика. Отклоняет очевидно "жадные" запросы.
* `1`: Разрешать всегда. Повышает риск OOM.
* `2`: Не разрешать. Строгое ограничение (`SwapTotal + RAM * overcommit_ratio`). Полезно для СУБД.

```bash
# Установить строгий режим (не разрешать overcommit)
sudo sysctl -w vm.overcommit_memory=2
```

### Управление NUMA с `numactl`

```bash
# Запустить my_app на узле CPU 0 и выделять память только с этого узла
numactl --cpunodebind=0 --membind=0 my_app
```

### Настройка HugePages

```bash
# Выделить 1024 страницы по 2 МБ (всего 2 ГБ)
sudo sysctl -w vm.nr_hugepages=1024
```

### Управление THP

Проверка статуса:

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never
```

* `always`: THP включен для всех процессов.
* `madvise`: THP включен только для процессов, которые явно запросили это через системный вызов `madvise()`.
* `never`: THP полностью отключен.

Отключение до перезагрузки:

```bash
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/defrag
```

## Дополнительная информация

### Параметр ядра `vfs_cache_pressure`

Контролирует агрессивность освобождения ядром памяти для кэширования **dentry** и **inode**, хранящихся с помощью [[slab_allocator.md|Slab Allocator]].

* **Значение по умолчанию: `100`**. Ядро быстро освобождает кэш inode/dentry.
* **Низкое значение (например, `50`):** Ядро дольше хранит кэш, может ускорить доступ к файлам, но увеличивает риск нехватки памяти для процессов.
* **Высокое значение (более `100`):** Ядро очень агрессивно очищает кэш метаданных.

```bash
sudo sysctl -w vm.vfs_cache_pressure=50
```
