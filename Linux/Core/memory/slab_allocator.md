# Slab Allocator в Linux

## Определения

* **Buddy System** (Система двойников): Базовый аллокатор страниц ядра Linux. Выделяет память блоками по $2^n$ страниц (минимально 1 страница — обычно 4 КБ). Slab Allocator запрашивает у него целые страницы и "нарезает" их на мелкие объекты.
* **Slab Allocator**: Высокоуровневый механизм управления памятью, предназначенный для эффективного выделения памяти под часто используемые объекты фиксированного размера (структуры данных ядра).
* **Slab Cache** (Кэш слэбов): Логическая группировка объектов одного типа (например, `inode_cache`, `dentry`, `task_struct`). Каждый кэш управляет набором слэбов.
* **Slab** (Слэб): Один или несколько смежных листов (pages) физической памяти, выделенных из Buddy System. Слэб разделен на равные участки для хранения объектов и может находиться в одном из трех состояний: *full* (заполнен), *partial* (частично заполнен), *empty* (пуст).
* **Slab Object**: Индивидуальный экземпляр структуры данных (например, одна структура `task_struct`), хранящийся внутри слэба.
* **kmalloc**: Кэши общего назначения для выделения памяти произвольного размера (например, `kmalloc-128`, `kmalloc-512`). Используются, когда для объекта не создан специализированный кэш.
* **SReclaimable**: Часть Slab-памяти (см. `/proc/meminfo`), которую ядро может освободить под давлением памяти (например, кэши VFS).
* **SUnreclaim**: Часть Slab-памяти, которую нельзя освободить (критические структуры ядра).
* **Slab Shrinker**: Механизм обратного вызова (callback), который ядро использует для уменьшения размера `SReclaimable`-кэшей при нехватке памяти.
* **KReclaimable**: Суммарная очищаемая память ядра (`SReclaimable` + другие кэши с shrinkers). Поле в `/proc/meminfo`.
* **Zombie Slabs**: Слэбы, оставшиеся после удаления cgroup, но все еще содержащие объекты, используемые ядром (например, открытые файлы). В ядрах v5.9+ переносятся в родительскую cgroup механизмом **Slab Memory Reparenting**.
* **SLUB**: Современный стандартный аллокатор в Linux (с ядра 2.6.22). Заменил SLAB и SLOB. Основан на идее "unqueued" freelist с per-CPU кэшем для снижения contention.

## Основные концепции

### Проблема фрагментации

Стандартный аллокатор страниц (Buddy System) работает с минимальным размером в 4 КБ. Выделение памяти под структуры размером в десятки или сотни байт через Buddy System приводит к двум проблемам:
1. **Внутренняя фрагментация**: Если структуре нужно 128 байт, а выделяется 4096 байт, ~97% памяти пропадает зря.
2. **Затраты на инициализацию**: Ядро тратит ресурсы на многократную инициализацию (конструкторы) и очистку (деструкторы) сложных структур при каждом создании/удалении.

Slab Allocator решает это, создавая "пул" уже инициализированных объектов.

### Иерархия выделения памяти

```text
[ Приложение / Ядро ]
        ↓
[ Slab Allocator (SLUB) ]  <-- Управляет объектами (напр. 128 байт)
        ↓
[ Buddy System ]           <-- Управляет страницами (4 КБ)
        ↓
[ Физическая память ]
```

### Архитектура SLUB

Современный SLUB-аллокатор использует трехуровневую организацию памяти для минимизации contention на SMP-системах:

1. **Per-CPU Slab (cpu_slab)**: Каждый процессор имеет выделенный "горячий" слэб для частых аллокаций/освобождений. Это исключает блокировки при операциях с объектами.
2. **Partial List**: Список частично заполненных слэбов кэша. При нехватке места в `cpu_slab` аллокатор берет объект отсюда.
3. **Full/Empty Lists**: Полностью заполненные и пустые слэбы. Empty слэбы возвращаются в Buddy System через `kmem_cache_shrink()`.

**Colored Slabs**: SLUB размещает объекты в слэбе с определенным смещением (color), чтобы разные кэши не конфликтовали по кэш-линиям процессора. Это снижает false sharing.

**Freelist (список свободных объектов)**:
- В SLUB freelist — это простой стек указателей внутри слэба. При освобождении объект помещается в freelist; при выделении — извлекается.
- При включенном `CONFIG_SLUB_CPU_PARTIAL` также используется partial list для снижения contention.

### Принцип работы Slab Allocator

1. **Объектное кэширование**: Вместо уничтожения объекта после использования, аллокатор помечает его как "свободный" и оставляет в памяти. При следующем запросе того же типа объект выдается мгновенно.
2. **Минимизация фрагментации**: Объекты плотно упаковываются внутри слэбов.
3. **NUMA-оптимизация**: Современный аллокатор (SLUB) старается выделять объекты из памяти того же NUMA-узла, на котором исполняется поток.
4. **Cache-friendly размещение**: SLUB использует цветовое смещение (color offset), чтобы объекты из разных кэшей не попадали на одну кэш-линию, снижая false sharing.

### Кэши общего назначения (kmalloc)

Для небольших аллокаций, не привязанных к конкретному типу данных, ядро поддерживает набор кэшей `kmalloc-N`, где N — размер в байтах (обычно степени двойки: 8, 16, 32... 8192). В ядре 6.x размеры доходят до `kmalloc-2^25` (32 МБ) для PAGE_SIZE=4K.
```bash
grep kmalloc /proc/slabinfo | head -n 5
# → kmalloc-8k          125    128   8192    4    8 : tunables    0    0    0 : slabdata     32     32      0
# → kmalloc-4k          452    512   4096    8    8 : tunables    0    0    0 : slabdata     64     64      0
```

### Механизм slab merge

По умолчанию SLUB объединяет (merge) кэши с одинаковым размером объекта в один общий кэш. Это экономит память, но снижает безопасность: overflow в одном типе объектов может повредить другой. Параметр загрузки `slab_nomerge` отключает это поведение.

### NUMA-поведение

При выделении памяти SLUB учитывает NUMA-топологию:
- Если текущий процессор принадлежит NUMA-узлу N, аллокатор предпочитает страницы из зоны N.
- При нехватке памяти в локальном узле происходит fallback на удаленные узлы, что увеличивает латентность доступа.
- На гетерогенных архитектурах (big.LITTLE) это означает разницу в скорости доступа между P-cores и E-cores.

### Базовый API ядра (C)

Для разработчиков модулей ядра доступны следующие функции:
* `kmem_cache_create()`: Создает новый именованный кэш для объектов фиксированного размера.
* `kmem_cache_alloc()`: Выделяет объект из существующего кэша.
* `kmem_cache_free()`: Возвращает объект в кэш.
* `kmalloc()` / `kfree()`: Аналоги `malloc`/`free` для общего пользования (выделяют память из кэшей `kmalloc-N`).

### Взаимодействие с OOM Killer

Slab-память учитывается при расчете давления на память. Когда `SReclaimable` слишком велик, shrinkers активно освобождают кэши. Однако если `SUnreclaim` растет из-за утечки в драйвере, это потребляет RAM, сокращая доступную память для процессов и повышая риск срабатывания OOM Killer. Подробнее: **[Механизм OOM Killer](../processes/oom_killer_mechanism.md)**.

### Связь с VFS и файловыми системами

Большая часть `SReclaimable` состоит из кэшей dentry и inode. При интенсивной работе с файлами (веб-серверы, СУБД) эти кэши могут занимать гигабайты. Ядро использует `shrinkers` для их принудительной очистки при дефиците памяти. Подробнее: **[Inodes и Dentries](../../FileSystems/links_inodes_dentries.md)**.

## Безопасность и отладка

### Защита от эксплойтов (Hardening)

Современное ядро Linux включает механизмы защиты Slab от атак типа Heap Overflow и Use-After-Free:
1. **Hardened Usercopy** (`CONFIG_HARDENED_USERCOPY`): Проверяет границы объекта при копировании данных между ядром и пользователем (`copy_to_user`/`copy_from_user`).
2. **Freelist Hardening** (`CONFIG_SLAB_FREELIST_HARDENED`): Запутывает (XOR) указатели в списке свободных объектов, чтобы злоумышленник не мог легко перехватить управление списком.
3. **Randomization** (`CONFIG_SLAB_FREELIST_RANDOM`): Рандомизирует порядок объектов внутри нового слэба, затрудняя предсказание адресов.
4. **Kmalloc Isolation** (`RANDOM_KMALLOC_CACHES`, с ядра 6.6): Создает несколько независимых копий кэшей `kmalloc` для изоляции подсистем друг от друга.

### Обнаружение ошибок (KASAN)

**KASAN** (Kernel Address Sanitizer) — мощный инструмент динамического анализа. Он использует "теневую память" (shadow memory) для проверки каждого обращения к Slab. Если поток обращается к уже освобожденному объекту или выходит за границы выделенной области, ядро генерирует подробный отчет (Panic или Warning).

### Обнаружение повреждений (SLUB Debug)

При включенном `slub_debug` (параметр загрузки ядра) SLUB добавляет проверки целостности:
- **Redzoning**: Выделяет красную зону (padding) перед/после объекта; попытка записи за границы вызывает панику.
- **Poisoning**: Заполняет свободные объекты паттерном `0x6b` (POISON_FREE) и выделенные — `0x00` или `0xAA`; несанкционированный доступ виден по измененному паттерну.
- **Object tracking**: Фиксирует стек аллокации каждого объекта для диагностики утечек.

```bash
# Включить отладку для конкретного кэша (временно)
echo 0xdeadbeef > /sys/kernel/slab/<cache_name>/ Poison
echo 1 > /sys/kernel/slab/<cache_name>/ red_zone
```

## Практические сценарии

### Пороги и базовая оценка

Для production-систем установите базовые ориентиры (значения в `/proc/meminfo`):
- **SReclaimable**: 15–40% от общего `Slab` нормально для систем с интенсивным I/O. Если > 50% — проверьте VFS-нагрузку.
- **SUnreclaim**: < 5% от RAM на стабильной системе. Постоянный рост — признак утечки.
- **Slab / RAM**: на серверах с большим количеством файлов (веб, файловые хранилища) Slab может занимать 5–10% RAM без аномалии.

### Диагностика разрастания Slab

Если `SUnreclaim` постоянно растет, это может указывать на утечку памяти в модуле ядра или драйвере. Рост `SReclaimable` обычно нормален для систем с интенсивным I/O.

**Просмотр общей статистики:**
```bash
grep -E 'Slab|SReclaimable|SUnreclaim' /proc/meminfo
# → Slab:             254320 kB
# → SReclaimable:     182140 kB
# → SUnreclaim:        72180 kB
```

**Анализ через slabtop:**
Утилита `slabtop` (требует прав root) позволяет сортировать кэши по объему памяти или количеству объектов.
```bash
# Сортировка по размеру кэша (клавиша 'c')
slabtop -o -s c
```
Популярные кэши:
* `dentry`: Кэш имен файлов. Растет при обращении к множеству разных файлов.
* `inode_cache`: Кэш метаданных файлов.
* `kernfs_node_cache`: Кэш структур `/sys` и `/proc`.

**Детальный анализ через /proc/slabinfo:**
Файл содержит подробную статистику (требует `CONFIG_SLABINFO`).
```bash
cat /proc/slabinfo | column -t | head -n 5
# → name            <active_objs>  <num_objs>  <objsize>  <objperslab>  <pagesperslab>
# → nf_conntrack    452            500         320        12            1
```
* `active_objs`: Количество используемых объектов.
* `num_objs`: Общее количество выделенных объектов (включая свободные).
* `objsize`: Размер одного объекта в байтах.

### Проверка в современных системах (SLUB)

В системах со SLUB-аллокатором детальную информацию можно найти в `/sys/kernel/slab/`.
```bash
# Список всех кэшей
ls -l /sys/kernel/slab/

# Проверка "зомби-слэбов" (от удаленных cgroups)
ls -l /sys/kernel/slab/*/cgroup/
```

### Slab и Control Groups (kmemcg)

Ядро изолирует использование Slab-памяти между контейнерами.
* **Zombie Slabs**: Если контейнер (cgroup) удален, но объекты в его слэбах еще используются ядром (например, открытые файлы), эти слэбы помечаются как "dying". В современных ядрах (v5.9+) введен механизм **Slab Memory Reparenting**, который переносит такие объекты в родительскую cgroup, предотвращая утечки памяти "зомби-слэбов".
* **Проверка**: Использование памяти слэбов включено в общий лимит `memory.current` для cgroup v2.

### Механизм Slab Shrinker

Когда системе требуется память (свободная память опускается ниже вотермарка `low`), вызываются шринкеры. Они проходят по `SReclaimable`-кэшам и удаляют старые объекты. Самые известные потребители — **dentry** и **inode** (кэши путей и метаданных файлов). Подробнее о структурах VFS см. в **[Inodes и Dentries](../../FileSystems/links_inodes_dentries.md)**.

### Тюнинг vm.vfs_cache_pressure

Параметр определяет приоритет очистки слэбов VFS по сравнению с Page Cache.
* `100` (default): Равный приоритет.
* `50`: Ядро будет в 2 раза менее охотно очищать inode/dentry.
* `200`: Агрессивная очистка метаданных (снижает производительность FS, но освобождает RAM).

Подробное описание параметров `sysctl` см. в **[Оптимизация памяти](./performance_tuning.md)**.

### Диагностика утечек памяти ядра

Если `MemAvailable` падает, а память процессов (`Active(anon)`) стабильна, проверьте `SUnreclaim`. Постоянный рост этого значения указывает на утечку в драйвере или модуле ядра.

```bash
# Мониторинг роста SUnreclaim
watch -n1 "grep SUnreclaim /proc/meminfo"

# Детализация через slabtop
sudo slabtop -s c | head -n 20
```

Корреляция событий:
1. **Загрузка модуля ядра**: после `insmod`/`modprobe` может расти `SUnreclaim` из-за кэшей модуля.
2. **Mount/unmount ФС**: при монтировании новых ФС создаются кэши super_block, mount_cache; при некорректном размонтировании они могут оставаться в памяти.
3. **Сетевые соединения**: рост `nf_conntrack` или `sock_inode_cache` указывает на высокую сетевую активность или утечку conntrack.
4. **Удаление cgroup**: после массового удаления контейнеров zombie slabs временно увеличивают `SUnreclaim`.

### Взаимодействие с PSI (Pressure Stall Information)

На современных ядрах (4.20+) PSI отслеживает давление на память, вызванное как процессами, так и ядром. Slab shrinkers влияют на `memory.pressure`:
```bash
# Проверка текущего давления
cat /proc/pressure/memory
# → some avg10=0.50 avg60=0.20 avg300=0.05 total=1234567
# → full avg10=0.00 avg60=0.00 avg300=0.00 total=1234
```
Если `some` растет при отсутствии swapon/si-so — вероятно, ядро активно чистит slab кэши, блокируя процессы.

### Мониторинг через Prometheus (node_exporter)

Метрики `node_slab_*` позволяют строить дашборды и алерты:
```bash
# Список доступных метрик
curl -s http://localhost:9100/metrics | grep node_slab | head -n 20
# → node_slab_reclaimable_bytes{type="dentry"} 1.23456e+07
# → node_slab_unreclaimable_bytes{type="kmalloc-4k"} 5.6789e+06
```
Рекомендуемые алерты:
- **SUnreclaim > 10% RAM** на протяжении > 5 минут — возможна утечка.
- **Рост SUnreclaim > 100 МБ/час** — требуется диагностика модулей.
- **SReclaimable / Slab > 70%** — система тратит много ресурсов на очистку VFS-кэшей; проверьте `vm.vfs_cache_pressure`.

### Анализ kernel log при slab corruption

При повреждении slab SLUB генерирует подробный отчет в `dmesg`:
```bash
dmesg | grep -iE "slab|corruption|bug:|BUG:"
# → BUG kmalloc-2k: Object at 0xffff888000123450 not last freed
# → INFO: Slab 0xffff888000100000 objects=256 used=254 fp=0xffff888000123450 flags=0xffffffff00000000
# → Bytes b4 0xffff887ffffffff0: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```
Для глубокого анализа используйте `crash` или `kdump`:
```bash
# Анализ дампа памяти
crash /usr/lib/debug/lib/modules/$(uname -r)/vmlinux /var/crash/...
crash> kmem -s <cache_name>
crash> kmem -z
```

### Экстренные меры при критическом разрастании

Если `SUnreclaim` заполняет RAM и приближается к OOM:
1. **Идентифицировать "топ-пожирателей"**:
   ```bash
   sudo slabtop -o -s c | head -n 15
   ```
2. **Принудительная очистка** (осторожно! может вызвать падение производительности):
   ```bash
   # Попросить ядро освободить пустые слэбы
   echo 2 > /proc/sys/vm/drop_caches
   ```
   Это удаляет **page cache** и **SReclaimable** (dentries/inodes), но не трогает `SUnreclaim`.
3. **Перезагрузка** — единственный способ освободить `SUnreclaim` из модулей ядра с утечкой.
4. **Для cgroup-изоляции**: ограничьте `kmem.limit_in_bytes` (cgroup v1) или `memory.max` (cgroup v2), чтобы контейнер не мог заполнить slab.

### Дифференциальная диагностика: slab leak vs process leak

| Симптом | Slab Leak | Process Leak |
|---------|-----------|--------------|
| `SUnreclaim` растет | Да | Нет |
| `Active(anon)` растет | Нет | Да |
| `MemAvailable` падает | Да | Да |
| ООМ Killer убивает процессы | Редко (при очень большом SUnreclaim) | Часто |
| `slabtop` показывает рост одного кэша | Да | Нет |
| `top`/`ps` показывает рост RSS у процесса | Нет | Да |

### Практический чек-лист SRE

При эскалации по памяти:
1. `free -h` — общая картина.
2. `grep -E 'Slab|SReclaimable|SUnreclaim' /proc/meminfo` — доля slab.
3. `sudo slabtop -o -s c` — какие кэши растут.
4. `cat /proc/pressure/memory` — давление на память (PSI).
5. `dmesg -T | grep -iE 'slab|corruption|out of memory'` — ошибки ядра.
6. `sudo vmstat -m` — альтернативный вид slab-статистики (если `/proc/slabinfo` недоступен).
7. Для cgroup: `cat /sys/fs/cgroup/memory/system.slice/memory.kmem.usage_in_bytes` (cgroup v1) или `cat /sys/fs/cgroup/system.slice/memory.current` (cgroup v2).

### Тюнинг для высоконагруженных систем

1. **`vm.vfs_cache_pressure`**: для систем с миллионами файлов (например, хранение артефактов) установите `50`, чтобы ускорить очистку метаданных.
2. **`vm.min_free_kbytes`**: на серверах с 64 ГБ+ RAM установите `1048576` (1 ГБ) для снижения риска `direct reclaim`.
3. **`slab_nomerge`**: в параметрах загрузки ядра для систем с высокими требованиями к безопасности; предотвращает Cross-Cache Overflow.
4. **`slub_debug=ZF`**: для отладки на тестовых стендах (zero freelist, red zone, poisoning). Не используйте в production — снижает производительность на 20–40%.

### Сценарий: восстановление после утечки в сетевом драйвере

Случай: после обновления модуля `ixgbe` `SUnreclaim` растет на 50 МБ/час.

```bash
# 1. Определить кэш-лидер
sudo slabtop -o -s s | head -n 5
# → ixgbe_tx_buffer_cache   увеличение...

# 2. Проверить, используется ли модуль
lsmod | grep ixgbe

# 3. Попробовать выгрузить модуль (осторожно!)
sudo rmmod ixgbe
# → Если ссылок нет, модуль выгрузится и память освободится.

# 4. Если выгрузка невозможна (устройство в использовании):
#    - Перевести интерфейсы в down
#    - Выгрузить модуль
#    - Перезагрузить модуль или установить стабильную версию

# 5. Мониторинг после вмешательства
watch -n5 "grep SUnreclaim /proc/meminfo"
```

## Дополнительная информация

### Разновидности Slab Allocator

| Аллокатор | Описание | Статус |
| :--- | :--- | :--- |
| **SLAB** | Классическая реализация (Solaris-style). | Удален в Linux 6.8 (2024). |
| **SLOB** | Минималистичный аллокатор для встраиваемых систем. | Удален в Linux 6.4 (2023). |
| **SLUB** | Современный стандарт. Лучшая масштабируемость и отладка. | **Единственный доступный с Linux 6.8.** |
| **SLUB_TINY** | Специальный режим SLUB для систем с малым объемом RAM. | Замена SLOB в новых ядрах. |

### Полезные параметры загрузки ядра

* `slab_nomerge`: Запрещает объединение схожих по размеру кэшей. Полезно для безопасности (изоляция объектов разных типов) или отладки.
* `slub_debug`: Включает проверки целостности слэбов (может значительно снизить производительность).
* `slub_debug=ZF`: Zero freelist validation + Redzone + Poisoning.
* `init_on_alloc=1` / `init_on_free=1`: Зануление памяти при выделении/освобождении для защиты от утечек данных.
