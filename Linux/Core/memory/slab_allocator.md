# Slab Allocator в Linux

## Определения

**Slab Allocator** - Это механизм управления памятью, который ядро Linux использует для эффективного выделения памяти под собственные, часто используемые структуры данных (объекты). Примерами таких объектов являются `inodes`, `dentries` (кэш путей файловой системы), дескрипторы файлов и сетевые буферы.

**Slab** - Память, используемая ядром для кэширования собственных структур данных. В выводе `/proc/meminfo` она делится на:

- **`SReclaimable`**: Часть `Slab`, которую ядро может освободить при нехватке памяти (например, кэши `inodes` и `dentries`).
- **`SUnreclaim`**: Часть `Slab`, которую освободить нельзя, так как она содержит критически важные для работы ядра данные.

**Slab Shrinker** - Это механизм ядра, который отвечает за освобождение памяти, занятой "освобождаемыми" (`SReclaimable`) кэшами, когда в системе возникает нехватка памяти.

## Основные концепции

#### Проблема, которую решает Slab

Ядро постоянно создает и уничтожает огромное количество однотипных объектов. Стандартное выделение и освобождение памяти для каждого из них привело бы к двум проблемам:

1. **Внешняя фрагментация:** Появление множества мелких, несмежных блоков свободной памяти ("дыр"), которые сложно использовать повторно.
2. **Накладные расходы:** Затраты процессорного времени на инициализацию каждого нового объекта и его очистку при уничтожении.

#### Как работает Slab Allocator

1. **Создание кэшей:** Для каждого типа объектов (`inode`, `dentry` и т.д.) создается отдельный "кэш".
2. **Выделение слэбов:** Каждый кэш состоит из одного или нескольких "слэбов" (slabs) — это смежные страницы физической памяти.
3. **Переиспользование объектов:** Когда ядру нужен новый объект, он берется из соответствующего кэша. Когда объект больше не нужен, он не освобождается полностью, а возвращается в свой слэб и помечается как свободный. Это устраняет необходимость в повторной инициализации и снижает фрагментацию.

#### Механизм Slab Shrinker

Когда системе не хватает памяти, ядро через `slab shrinker` вызывает специальные функции, зарегистрированные для "освобождаемых" кэшей. Эти функции "знают", как безопасно удалить из кэша старые или неиспользуемые объекты (`inodes`, `dentries`), возвращая занимаемую ими память в общий пул.

## Практические сценарии

#### Диагностика разрастания Slab

**Симптомы проблемы:**

- Свободной памяти становится всё меньше, но сумма RSS всех процессов не сходится с реальным потреблением
- OOM всё ближе, а в user-space «лишней» памяти нет
- Slab в `/proc/meminfo` стабильно растёт

**Просмотр распределения Slab:**

```bash
# Общая информация о Slab
cat /proc/meminfo | grep -E 'Slab|SReclaimable|SUnreclaim'

# Топ кэшей по потреблению памяти
cat /proc/slabinfo | sort -k3 -nr | head

# Интерактивный мониторинг
slabtop -o
```

**Анализ лидеров потребления:**

| Кэш | Причина роста |
| :--- | :--- |
| `dentry` | Большое количество файловых операций, работа с множеством файлов |
| `inode` | Интенсивная работа с метаданными ФС, много мелких файлов |
| `skbuff` | Сетевая нагрузка, большой поток пакетов |
| `task_struct` | Много процессов/потоков |

#### Различение Reclaimable и Unreclaimable

```bash
# Освобождаемая память (теоретически может быть освобождена)
cat /proc/meminfo | grep SReclaimable

# Неосвобождаемая память (критически важные структуры ядра)
cat /proc/meminfo | grep SUnreclaim
```

> **Важно:** `SReclaimable` может освобождаться медленно или неэффективно при высоком давлении памяти, создавая ощущение «пропавшей» RAM.

#### Просмотр статистики Slab

Утилита `slabtop` позволяет в реальном времени отслеживать, какие кэши объектов занимают больше всего памяти. Это помогает понять, на что ядро расходует `Slab`-память.

```bash
# Запустить slabtop и отсортировать по количеству объектов
slabtop -o
```

#### Тюнинг `vm.vfs_cache_pressure`

Этот параметр напрямую контролирует, насколько агрессивно ядро будет освобождать память из slab-кэшей, используемых для метаданных файловой системы — **dentry** (записи каталогов) и **inode** (метаданные файлов).

Подробное описание и примеры использования см. в основной заметке: **[Оптимизация и тонкая настройка памяти](performance_tuning.md)**.

## Дополнительная информация

#### Разновидности Slab Allocator

1. **SLAB:** Оригинальная реализация. Страдала от внутренней фрагментации и была сложна в отладке. **Удалён в Linux 6.8** (январь 2024) как устаревший.
2. **SLUB:** Реализация по умолчанию в современных ядрах. Значительно проще, эффективнее и лучше подходит для отладки. Фокусируется на минимальных накладных расходах и хорошей производительности на многопроцессорных системах. **Единственный поддерживаемый аллокатор начиная с Linux 6.8.**
3. **SLOB (Simple List of Blocks):** Очень простая реализация, предназначенная для встраиваемых систем с крайне ограниченным объемом памяти. **Удалён в Linux 6.4** (май 2023) из-за отсутствия активных пользователей.

**Историческая справка:** До Linux 6.8 выбор аллокатора происходил на этапе компиляции ядра. Начиная с Linux 6.8, SLUB является единственным доступным аллокатором, что упростило код ядра и обеспечило прирост производительности до +34% в некоторых сценариях.
