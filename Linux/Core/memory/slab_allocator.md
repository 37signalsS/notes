# Slab Allocator в Linux

## Определения

* **Buddy System** (Система двойников): Базовый аллокатор страниц ядра Linux. Выделяет память блоками по $2^n$ страниц (минимально 1 страница — обычно 4 КБ). Slab Allocator запрашивает у него целые страницы и "нарезает" их на мелкие объекты.
* **Slab Allocator**: Высокоуровневый механизм управления памятью, предназначенный для эффективного выделения памяти под часто используемые объекты фиксированного размера (структуры данных ядра).
* **Slab Cache** (Кэш слэбов): Логическая группировка объектов одного типа (например, `inode_cache`, `dentry`, `task_struct`). Каждый кэш управляет набором слэбов.
* **Slab** (Слэб): Один или несколько смежных листов (pages) физической памяти, выделенных из Buddy System. Слэб разделен на равные участки для хранения объектов и может находиться в одном из трех состояний: *full* (заполнен), *partial* (частично заполнен), *empty* (пуст).
* **Slab Object**: Индивидуальный экземпляр структуры данных (например, одна структура `task_struct`), хранящийся внутри слэба.
* **kmalloc**: Кэши общего назначения для выделения памяти произвольного размера (например, `kmalloc-128`, `kmalloc-512`). Используются, когда для объекта не создан специализированный кэш.
* **SReclaimable**: Часть Slab-памяти (см. `/proc/meminfo`), которую ядро может освободить под давлением памяти (например, кэши VFS).
* **SUnreclaim**: Часть Slab-памяти, которую нельзя освободить (критические структуры ядра).
* **Slab Shrinker**: Механизм обратного вызова (callback), который ядро использует для уменьшения размера `SReclaimable`-кэшей при нехватке памяти.

## Основные концепции

### Проблема фрагментации

Стандартный аллокатор страниц (Buddy System) работает с минимальным размером в 4 КБ. Выделение памяти под структуры размером в десятки или сотни байт через Buddy System приводит к двум проблемам:
1. **Внутренняя фрагментация**: Если структуре нужно 128 байт, а выделяется 4096 байт, ~97% памяти пропадает зря.
2. **Затраты на инициализацию**: Ядро тратит ресурсы на многократную инициализацию (конструкторы) и очистку (деструкторы) сложных структур при каждом создании/удалении.

Slab Allocator решает это, создавая "пул" уже инициализированных объектов.

### Иерархия выделения памяти

```text
[ Приложение / Ядро ]
       ↓
[ Slab Allocator (SLUB) ]  <-- Управляет объектами (напр. 128 байт)
       ↓
[ Buddy System ]           <-- Управляет страницами (4 КБ)
       ↓
[ Физическая память ]
```

### Принцип работы Slab Allocator

1. **Объектное кэширование**: Вместо уничтожения объекта после использования, аллокатор помечает его как "свободный" и оставляет в памяти. При следующем запросе того же типа объект выдается мгновенно.
2. **Минимизация фрагментации**: Объекты плотно упаковываются внутри слэбов.
3. **NUMA-оптимизация**: Современный аллокатор (SLUB) старается выделять объекты из памяти того же NUMA-узла, на котором исполняется поток.

### Кэши общего назначения (kmalloc)

Для небольших аллокаций, не привязанных к конкретному типу данных, ядро поддерживает набор кэшей `kmalloc-N`, где N — размер в байтах (обычно степени двойки: 8, 16, 32... 8192).
```bash
grep kmalloc /proc/slabinfo | head -n 5
# → kmalloc-8k          125    128   8192    4    8 : tunables    0    0    0 : slabdata     32     32      0
# → kmalloc-4k          452    512   4096    8    8 : tunables    0    0    0 : slabdata     64     64      0
```

### Базовый API ядра (C)

Для разработчиков модулей ядра доступны следующие функции:
* `kmem_cache_create()`: Создает новый именованный кэш для объектов фиксированного размера.
* `kmem_cache_alloc()`: Выделяет объект из существующего кэша.
* `kmem_cache_free()`: Возвращает объект в кэш.
* `kmalloc()` / `kfree()`: Аналоги `malloc`/`free` для общего пользования (выделяют память из кэшей `kmalloc-N`).

## Безопасность и отладка

### Защита от эксплойтов (Hardening)

Современное ядро Linux включает механизмы защиты Slab от атак типа Heap Overflow и Use-After-Free:
1. **Hardened Usercopy** (`CONFIG_HARDENED_USERCOPY`): Проверяет границы объекта при копировании данных между ядром и пользователем (`copy_to_user`/`copy_from_user`).
2. **Freelist Hardening** (`CONFIG_SLAB_FREELIST_HARDENED`): Запутывает (XOR) указатели в списке свободных объектов, чтобы злоумышленник не мог легко перехватить управление списком.
3. **Randomization** (`CONFIG_SLAB_FREELIST_RANDOM`): Рандомизирует порядок объектов внутри нового слэба, затрудняя предсказание адресов.
4. **Kmalloc Isolation** (`RANDOM_KMALLOC_CACHES`, с ядра 6.6): Создает несколько независимых копий кэшей `kmalloc` для изоляции подсистем друг от друга.

### Обнаружение ошибок (KASAN)

**KASAN** (Kernel Address Sanitizer) — мощный инструмент динамического анализа. Он использует "теневую память" (shadow memory) для проверки каждого обращения к Slab. Если поток обращается к уже освобожденному объекту или выходит за границы выделенной области, ядро генерирует подробный отчет (Panic или Warning).

## Практические сценарии

### Диагностика разрастания Slab

Если `SUnreclaim` постоянно растет, это может указывать на утечку памяти в модуле ядра или драйвере. Рост `SReclaimable` обычно нормален для систем с интенсивным I/O.

**Просмотр общей статистики:**
```bash
grep -E 'Slab|SReclaimable|SUnreclaim' /proc/meminfo
# → Slab:             254320 kB
# → SReclaimable:     182140 kB
# → SUnreclaim:        72180 kB
```

**Анализ через slabtop:**
Утилита `slabtop` (требует прав root) позволяет сортировать кэши по объему памяти или количеству объектов.
```bash
# Сортировка по размеру кэша (клавиша 'c')
slabtop -o -s c
```
Популярные кэши:
* `dentry`: Кэш имен файлов. Растет при обращении к множеству разных файлов.
* `inode_cache`: Кэш метаданных файлов.
* `kernfs_node_cache`: Кэш структур `/sys` и `/proc`.

**Детальный анализ через /proc/slabinfo:**
Файл содержит подробную статистику (требует `CONFIG_SLABINFO`).
```bash
cat /proc/slabinfo | column -t | head -n 5
# → name            <active_objs>  <num_objs>  <objsize>  <objperslab>  <pagesperslab>
# → nf_conntrack    452            500         320        12            1
```
* `active_objs`: Количество используемых объектов.
* `num_objs`: Общее количество выделенных объектов (включая свободные).
* `objsize`: Размер одного объекта в байтах.

### Проверка в современных системах (SLUB)

В системах со SLUB-аллокатором детальную информацию можно найти в `/sys/kernel/slab/`.
```bash
# Список всех кэшей
ls -l /sys/kernel/slab/

# Проверка "зомби-слэбов" (от удаленных cgroups)
ls -l /sys/kernel/slab/*/cgroup/
```

### Slab и Control Groups (kmemcg)

Ядро изолирует использование Slab-памяти между контейнерами.
* **Zombie Slabs**: Если контейнер (cgroup) удален, но объекты в его слэбах еще используются ядром (например, открытые файлы), эти слэбы помечаются как "dying". В современных ядрах (v5.9+) введен механизм **Slab Memory Reparenting**, который переносит такие объекты в родительскую cgroup, предотвращая утечки памяти "зомби-слэбов".
* **Проверка**: Использование памяти слэбов включено в общий лимит `memory.current` для cgroup v2.

### Механизм Slab Shrinker

Когда системе требуется память (свободная память опускается ниже вотермарка `low`), вызываются шринкеры. Они проходят по `SReclaimable`-кэжам и удаляют старые объекты. Самые известные потребители — **dentry** и **inode** (кэши путей и метаданных файлов). Подробнее о структурах VFS см. в **[Inodes и Dentries](../../FileSystems/links_inodes_dentries.md)**.

### Тюнинг vm.vfs_cache_pressure

Параметр определяет приоритет очистки слэбов VFS по сравнению с Page Cache.
* `100` (default): Равный приоритет.
* `50`: Ядро будет в 2 раза менее охотно очищать inode/dentry.
* `200`: Агрессивная очистка метаданных (снижает производительность FS, но освобождает RAM).

Подробное описание параметров `sysctl` см. в **[Оптимизация памяти](./performance_tuning.md)**.

## Дополнительная информация

### Разновидности Slab Allocator

| Аллокатор | Описание | Статус |
| :--- | :--- | :--- |
| **SLAB** | Классическая реализация (Solaris-style). | Удален в Linux 6.8 (2024). |
| **SLOB** | Минималистичный аллокатор для встраиваемых систем. | Удален в Linux 6.4 (2023). |
| **SLUB** | Современный стандарт. Лучшая масштабируемость и отладка. | **Единственный доступный с Linux 6.8.** |
| **SLUB_TINY** | Специальный режим SLUB для систем с малым объемом RAM. | Замена SLOB в новых ядрах. |

### Полезные параметры загрузки ядра

* `slab_nomerge`: Запрещает объединение схожих по размеру кэшей. Полезно для безопасности (изоляция объектов разных типов) или отладки.
* `slub_debug`: Включает проверки целостности слэбов (может значительно снизить производительность).
* `init_on_alloc=1` / `init_on_free=1`: Зануление памяти при выделении/освобождении для защиты от утечек данных.
