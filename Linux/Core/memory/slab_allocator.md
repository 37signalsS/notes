# Slab Allocator в Linux

## Определения

* **Slab Allocator**: Механизм управления памятью ядра Linux для эффективного выделения памяти под часто используемые структуры данных (объекты): `inodes`, `dentries`, дескрипторы файлов, сетевые буферы.
* **Slab Cache**: Разговорный термин для памяти Slab, используемой ядром для кэширования внутренних объектов. В `/proc/meminfo` отображается как `Slab`.
* **Slab**: Память, используемая ядром для кэширования собственных структур данных. Делится на:
  * **`SReclaimable`**: Часть `Slab`, которую ядро может освободить при нехватке памяти (кэши `inodes`, `dentries`).
  * **`SUnreclaim`**: Часть `Slab`, которую освободить нельзя — содержит критически важные данные ядра.
* **Slab Shrinker**: Механизм ядра, освобождающий память из `SReclaimable`-кэшей при нехватке памяти.

## Основные концепции

### Проблема, которую решает Slab

Ядро постоянно создаёт и уничтожает огромное количество однотипных объектов. Стандартное выделение и освобождение памяти для каждого приводит к:

1. **Внешняя фрагментация** — множество мелких несмежных блоков свободной памяти, которые сложно использовать повторно.
2. **Накладные расходы** — затраты процессорного времени на инициализацию каждого нового объекта и его очистку при уничтожении.

### Как работает Slab Allocator

1. **Создание кэшей:** Для каждого типа объектов (`inode`, `dentry` и т. д.) создаётся отдельный кэш.
2. **Выделение слэбов:** Каждый кэш состоит из одного или нескольких слэбов — смежных страниц физической памяти.
3. **Переиспользование объектов:** Когда ядру нужен объект, он берётся из кэша. При «освобождении» объект возвращается в слэб как свободный — без повторной инициализации. Это снижает фрагментацию и ускоряет аллокации.

### Механизм Slab Shrinker

При нехватке памяти ядро через `slab shrinker` вызывает функции, зарегистрированные для `SReclaimable`-кэшей. Эти функции безопасно удаляют старые или неиспользуемые объекты (`inodes`, `dentries`), возвращая память в общий пул.

## Практические сценарии

### Диагностика разрастания Slab

**Симптомы:**

* Свободной памяти становится меньше, но сумма RSS (Resident Set Size) всех процессов не сходится с реальным потреблением.
* OOM (Out Of Memory) ближе, а в user-space «лишней» памяти нет.
* `Slab` в `/proc/meminfo` стабильно растёт.

**Просмотр распределения Slab:**

```bash
# Общая информация о Slab
cat /proc/meminfo | grep -E 'Slab|SReclaimable|SUnreclaim'

# Топ кэшей по потреблению памяти
cat /proc/slabinfo | sort -k3 -nr | head

# Интерактивный мониторинг
slabtop -o
```

**Анализ лидеров потребления:**

| Кэш | Причина роста |
| :--- | :--- |
| `dentry` | Большое количество файловых операций, работа с множеством файлов. |
| `inode` | Интенсивная работа с метаданными файловой системы, много мелких файлов. |
| `skbuff` | Сетевая нагрузка, большой поток пакетов (`sk_buff`). |
| `task_struct` | Много процессов или потоков. |

### Различение Reclaimable и Unreclaimable

```bash
# Освобождаемая память (теоретически может быть освобождена)
cat /proc/meminfo | grep SReclaimable

# Неосвобождаемая память (критически важные структуры ядра)
cat /proc/meminfo | grep SUnreclaim
```

> **Важно:** `SReclaimable` может освобождаться медленно или неэффективно при высоком давлении памяти, создавая ощущение «пропавшей» RAM (Random Access Memory).

### Просмотр статистики Slab

Утилита `slabtop` позволяет в реальном времени отслеживать, какие кэши занимают больше всего памяти.

```bash
# Запустить slabtop и отсортировать по количеству объектов
slabtop -o
```

### Тюнинг `vm.vfs_cache_pressure`

Параметр контролирует агрессивность освобождения slab-кэшей метаданных VFS (Virtual File System) — **dentry** и **inode**.

Подробное описание и примеры: **[Оптимизация и тонкая настройка памяти](./performance_tuning.md)**.

## Дополнительная информация

### Разновидности Slab Allocator

| Аллокатор | Описание | Статус |
| :--- | :--- | :--- |
| **SLAB** | Оригинальная реализация. Страдала от внутренней фрагментации, сложна в отладке. | Удалён в Linux 6.8 (январь 2024). |
| **SLUB** | По умолчанию в современных ядрах. Проще, эффективнее, лучше для отладки. Минимальные накладные расходы, хорошая производительность на SMP (Symmetric Multi-Processing). | Единственный поддерживаемый с Linux 6.8. |
| **SLOB** (Simple List of Blocks) | Упрощённая реализация для встраиваемых систем с крайне ограниченной памятью. | Удалён в Linux 6.4 (май 2023). |

Начиная с Linux 6.8 SLUB — единственный доступный аллокатор, что упростило код ядра и обеспечило прирост производительности до +34% в некоторых сценариях.
