# Control Groups (cgroups)

## Определения

**Control Groups (cgroups)** — механизм ядра Linux для ограничения, учёта и изоляции потребления ресурсов (CPU, память, I/O, сеть) группами процессов.

На концептуальном уровне `cgroups` дополняют [пространства имён (namespaces)](./namespaces.md):

- **`namespaces`** отвечают за **изоляцию видимости** (что процесс может *видеть*)
- **`cgroups`** отвечают за **ограничение потребления** (что процесс может *использовать*)

**Ключевая файловая система:** [cgroupfs](../FileSystems/virtual_filesystems.md#cgroupfs), монтируется в `/sys/fs/cgroup`.

**Основные возможности:**

- **Ограничение ресурсов:** Установка лимитов на CPU, память, I/O
- **Приоритезация:** Выделение большего/меньшего количества ресурсов через веса (shares/weights)
- **Учёт:** Сбор статистики по потреблению ресурсов
- **Контроль:** Заморозка, возобновление, завершение процессов

## Основные концепции

### Контроллеры cgroups

Контроллеры (иногда называемые «субсистемами») — это компоненты ядра, отвечающие за конкретный тип ресурсов:

| Контроллер | Назначение | Ключевые параметры (v2) |
| :--- | :--- | :--- |
| `cpu` | Управление процессорным временем | `cpu.weight`, `cpu.max` |
| `memory` | Ограничение RAM и swap | `memory.low`, `memory.high`, `memory.max` |
| `io` | Ограничение I/O операций для блочных устройств | `io.weight`, `io.max` |
| `pids` | Ограничение количества процессов | `pids.max` |
| `devices` | Разрешение/запрет доступа к устройствам (`/dev`) | `devices.allow`, `devices.deny` |
| `freezer` | Приостановка/возобновление процессов | `cgroup.freeze` |
| `cpuset` | Привязка к ядрам CPU и узлам NUMA | `cpuset.cpus`, `cpuset.mems` |
| `net_prio` | Приоритет сетевого трафика | `net_prio.priority` |
| `hugetlb` | Управление огромными страницами памяти | `hugetlb.<size>.max` |

> **Примечание:** В cgroups v2 некоторые контроллеры могут быть недоступны или иметь отличия в именах параметров.

### Cgroups v1 vs Cgroups v2

**Cgroups v2** — современный стандарт, используемый по умолчанию в современных дистрибутивах (Fedora 31+, Ubuntu 20.04+, Debian 11+, RHEL 9+).

| Характеристика | Cgroups v1 | Cgroups v2 |
| :--- | :--- | :--- |
| **Архитектура** | Несколько независимых иерархий (одна на контроллер) | Единая унифицированная иерархия |
| **Управление** | Сложнее, разные пути для контроллеров | Проще, все контроллеры вместе |
| **Путь** | `/sys/fs/cgroup/cpu/`, `/sys/fs/cgroup/memory/` | `/sys/fs/cgroup/` |
| **Поддержка** | Устаревает, совместимость | **Современный стандарт** |
| **Лимиты памяти** | Жёсткие (`memory.limit_in_bytes`) | Мягкие + жёсткие (`memory.high`, `memory.max`) |
| **I/O приоритеты** | `blkio.weight` | `io.weight` |
| **Деревья** | Разные деревья для разных контроллеров | Единое дерево для всех |

**Ключевые улучшения v2:**

- **Единая иерархия:** Процесс находится в одной группе для всех контроллеров
- **Гибкое управление памятью:** Введены «мягкие» лимиты (`memory.low`, `memory.high`)
- **Строгая изоляция:** Улучшенная безопасность и предсказуемость
- **Упрощённая делегация:** Непривилегированные пользователи могут управлять своими cgroups

### Оверхед и производительность

Активация контроллеров cgroups, особенно `memory`, создаёт дополнительную нагрузку на ядро из-за отслеживания использования каждой страницы памяти. Это осознанный компромисс между производительностью и предсказуемостью системы.

**Типичный оверхед:**

- **CPU:** 1–3% при активной работе с памятью
- **Память:** ~1–2 МБ на cgroup для структур данных ядра
- **I/O:** Минимальный, зависит от контроллера

> **Вывод:** Для большинства рабочих нагрузок оверхед пренебрежимо мал по сравнению с выгодой от изоляции ресурсов.

### Осведомлённость приложений о cgroups

Установка лимитов через cgroups — это лишь половина дела. Приложение, работающее внутри cgroup (например, в контейнере), должно быть "осведомлено" об этих лимитах.

Многие программы, особенно старые версии, при запуске пытаются определить доступные ресурсы (память, CPU) и, не умея считывать лимиты из cgroups, видят ресурсы всей хост-машины.

**Пример:**
Старая версия Java (до 8u131) не была осведомлена о cgroups. Запущенная в контейнере с лимитом памяти в 1 ГБ на хосте с 64 ГБ, она могла попытаться выделить себе кучу (heap) значительно больше 1 ГБ. Как только потребление памяти превышало лимит, OOM-киллер ядра принудительно "убивал" процесс Java.

## Практические сценарии

### Управление через Systemd

`systemd` активно использует `cgroups` для управления службами, что является одним из его ключевых преимуществ перед старыми системами инициализации. Каждая служба, запущенная `systemd`, помещается в собственную контрольную группу.

Это позволяет:

1. **Надежно отслеживать процессы**: Все дочерние процессы сервиса остаются внутри его cgroup, что позволяет `systemd` видеть их всех и надежно управлять ими.
2. **Гарантированно завершать процессы**: При остановке сервиса `systemd` убивает все процессы в его cgroup, не оставляя "осиротевших" или "зомби" процессов.
3. **Ограничивать ресурсы**: `systemd` предоставляет простой интерфейс для установки лимитов на ресурсы для каждой службы через её юнит-файл.

#### Практические инструменты

`systemd` предоставляет утилиты для работы с создаваемой им иерархией cgroup:

- `systemd-cgls`: Показывает иерархию cgroups в виде дерева.
- `systemd-cgtop`: Мониторит потребление ресурсов (CPU, память, I/O) в реальном времени, сгруппированное по cgroups.

#### Пример: Ограничение ресурсов в юнит-файле

Вы можете устанавливать лимиты на ресурсы для каждого сервиса через директивы в секции `[Service]` его юнит-файла (используя синтаксис `cgroups v2`).

```ini
# /etc/systemd/system/my-app.service
[Unit]
Description=My Application

[Service]
ExecStart=/usr/bin/my-app

# --- Настройки ресурсов ---
# Включаем учет для всех нужных ресурсов
CPUAccounting=true
MemoryAccounting=true
IOAccounting=true

# Ограничение памяти
MemoryMax=500M 
# Можно также использовать MemoryHigh (мягкий лимит) и MemoryLow (защищенный минимум)

# Ограничение CPU
CPUQuota=50% 
# Ограничивает использование CPU до 50% от одного ядра. 
# Для многоядерных систем можно указать > 100%, например, CPUQuota=200% для 2 ядер.

# Ограничение I/O
BlockIOWeight=500 
# Устанавливает вес для I/O операций (от 10 до 1000, по умолчанию 100).

[Install]
WantedBy=multi-user.target
```

После изменений необходимо перезагрузить конфигурацию `systemd` и перезапустить службу:

```bash
sudo systemctl daemon-reload
sudo systemctl restart my-app.service
```

### Ручное управление cgroups v2

Хотя `systemd` является предпочтительным способом, `cgroups` можно настраивать и вручную через файловую систему `/sys/fs/cgroup`. Это полезно для скриптов или для глубокого понимания их работы.

#### 1. Проверка активации cgroups v2

Убедитесь, что ваша система использует cgroups v2: `mount | grep cgroup`. Если вывод содержит `cgroup2`, все готово. В противном случае, для переключения на v2 может потребоваться добавить параметр `systemd.unified_cgroup_hierarchy=1` в конфигурацию загрузчика GRUB.

#### 2. Создание группы и установка ограничений

```bash
# Создаем новую группу
sudo mkdir /sys/fs/cgroup/test_group

# Задайте максимальную долю CPU для группы. Значение `10000 100000` означает, что группа может использовать не более 10000 микросекунд из каждых 100000, т.е. 10% одного ядра
echo "10000 100000" | sudo tee /sys/fs/cgroup/test_group/cpu.max

# Устанавливаем жесткий лимит памяти в 256 МБ
echo 256M | sudo tee /sys/fs/cgroup/test_group/memory.max
```

Чтобы OOM Killer убивал процессы всей группы при превышении лимита, а не отдельные процессы:

```bash
echo 1 > /sys/fs/cgroup/test_group/memory.oom.group
 ```

#### 3. Перемещение процесса в группу

```bash
# Запускаем процесс для теста
stress --cpu 1 --timeout 120 &

# Получаем его PID и перемещаем в cgroup
echo $(pgrep stress) | sudo tee /sys/fs/cgroup/test_group/cgroup.procs
```

Теперь процесс `stress` и все его дочерние процессы будут работать в рамках установленных лимитов.

#### 4. Мониторинг

Вы можете отслеживать потребление ресурсов, читая псевдофайлы внутри директории `cgroup`:

- **CPU:** `cat /sys/fs/cgroup/test_group/cpu.stat`
- **Память:** `cat /sys/fs/cgroup/test_group/memory.current`

### Контроллер cpuset: изоляция CPU и памяти NUMA

**CPUSET** — контроллер cgroups, позволяющий назначать определённые ядра CPU и узлы NUMA для группы процессов. В отличие от контроллера `cpu` (который ограничивает долю процессорного времени), `cpuset` обеспечивает **жёсткую привязку** процессов к конкретным ядрам.

#### Назначение

- **Изоляция высоконагруженных сервисов:** Гарантия, что критичные процессы не будут конкурировать за CPU с фоновыми задачами
- **Снижение кэш-промахов:** Процессы не мигрируют между ядрами, сохраняя данные в кэше L1/L2/L3
- **Предсказуемость задержек:** Исключение «шумных соседей» и переключений контекста
- **Оптимизация для NUMA-архитектур:** Привязка процессов к памяти локального NUMA-узла

#### Ключевые файлы контроллера

| Файл | Назначение | Пример значения |
| :--- | :--- | :--- |
| `cpuset.cpus` | Список разрешённых ядер CPU | `0-3`, `1,3,5-7` |
| `cpuset.mems` | Список разрешённых NUMA-узлов | `0`, `0-1` |
| `cpuset.cpus.effective` | Фактически доступные ядра (учитывает родительскую группу) | Автоматически |
| `cpuset.mems.effective` | Фактически доступные NUMA-узлы | Автоматически |

#### Пример: создание изолированной группы

```bash
# Создание группы
mkdir /sys/fs/cgroup/cpuset/isolated

# Разрешить ядра 2-3 и NUMA-узел 0
echo "2-3" > /sys/fs/cgroup/cpuset/isolated/cpuset.cpus
echo "0" > /sys/fs/cgroup/cpuset/isolated/cpuset.mems

# Включить контроллер для дочерних групп
echo "+cpuset" > /sys/fs/cgroup/cgroup.subtree_control

# Переместить процесс в группу
echo <PID> > /sys/fs/cgroup/cpuset/isolated/cgroup.procs
```

После этого процессы в группе `isolated` будут выполняться **только** на ядрах 2 и 3, используя память NUMA-узла 0. Планировщик Linux не сможет перемещать эти процессы на другие ядра.

#### CPUSET vs CPU affinity (`taskset`)

| Характеристика | `cpuset` (cgroups) | `taskset` (CPU affinity) |
| :--- | :--- | :--- |
| **Уровень** | Kernel (cgroups) | User-space (`sched_setaffinity`) |
| **Изоляция памяти NUMA** | ✅ Да | ❌ Нет |
| **Управление группой процессов** | ✅ Через cgroup.procs | ❌ Только по одному PID |
| **Наследование** | ✅ Дочерние процессы наследуют ограничения | ❌ Требуется явная установка для каждого процесса |
| **Интеграция с контейнерами** | ✅ Docker (`--cpuset-cpus`), Kubernetes | ❌ Не используется напрямую |

#### Применение в контейнеризации

**Docker:**

```bash
docker run --cpuset-cpus="0-3" --cpuset-mems="0" my-app
```

**Kubernetes** (требует CPU Manager с политикой `static`):

```yaml
resources:
  requests:
    cpu: "2"    # Гарантированные ядра (при integer значении)
  limits:
    cpu: "2"
```

### Troubleshooting

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| OOM Killer убивает процесс | Превышен лимит `memory.max` | Увеличить лимит или оптимизировать приложение |
| Процесс не перемещается в cgroup | Активный процесс с дочерними | Переместить все процессы или использовать `cgroup.procs` |
| Контроллер недоступен | Не включён в `cgroup.subtree_control` | `echo "+controller" > /sys/fs/cgroup/cgroup.subtree_control` |
| Cgroups v1 вместо v2 | Старый дистрибутив или параметр ядра | Добавить `systemd.unified_cgroup_hierarchy=1` в GRUB |
