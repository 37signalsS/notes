# Udev — динамическое управление устройствами

## Определения

**Udev (userside /dev)** — подсистема ядра Linux и демон (`systemd-udevd`), отвечающий за динамическое управление файлами устройств в каталоге `/dev`. Он обрабатывает события ядра (**uevents**), возникающие при подключении, отключении или изменении состояния оборудования.

В современных системах (systemd v250+) `udev` является частью `systemd` и тесно интегрирован с механизмами безопасности (TPM2, Credentials), управлением сессиями (`logind`) и доступом пользователей (`uaccess`).

### Архитектура и поток uevents

Современный механизм управления устройствами в Linux является гибридным и состоит из двух уровней:

1.  **Уровень ядра (devtmpfs):** Как только ядро обнаруживает новое устройство, драйвер регистрирует его. Ядро мгновенно создает базовый узел в `/dev` (например, `/dev/sdb`). Это гарантирует, что критические устройства доступны до запуска системных служб.
2.  **Уровень пользователя (Udev):** Демон `systemd-udevd` получает уведомление от ядра через netlink-сокет (`NETLINK_KOBJECT_UEVENT`). Он анализирует атрибуты устройства в `/sys`, применяет правила (udev rules), создает дополнительные символические ссылки (например, в `/dev/disk/by-uuid/`), устанавливает права доступа (ACL) и владельцев.

**Поток события (uevent flow):**

1.  Ядро генерирует uevent при изменении состояния kobject (подключение устройства, изменение режима питания).
2.  uevent передается через netlink-сокет всем подписчикам, включая `systemd-uevd`.
3.  `udevd` импортирует атрибуты из `sysfs` и `hwdb`, строит базу свойств события (`ID_*` переменные).
4.  Обрабатываются правила из `/etc/udev/rules.d/`, `/run/udev/rules.d/` и `/usr/lib/udev/rules.d/`.
5.  Выполняются действия: создание симлинков, изменение прав, запуск внешних команд или триггер systemd-юнитов.

**Важно:** `udev` работает в userspace, но зависит от `sysfs` и `devtmpfs`. Если `sysfs` недоступен или поврежден, `udev` не может определить атрибуты устройства и корректно применить правила.

### База данных свойств (Properties Database)

При обработке события `udev` строит словарь свойств (`key=value`), доступный в правилах через `ENV{key}`. Свойства делятся на несколько источников:

| Источник | Примеры | Описание |
| :--- | :--- | :--- |
| **sysfs** | `ID_MODEL`, `ID_SERIAL_SHORT` | Читаются напрямую из атрибутов устройства и его родителей. |
| **hwdb** | `ID_INPUT_KEY`, `ID_DPI` | Дополнительные свойства, которых нет в `sysfs` (названия моделей, специфичные настройки). |
| **Внутренние** | `ACTION`, `DEVPATH`, `SUBSYSTEM` | Генерируются самим `udev` на основе контекста события. |

Имена свойств следуют стандарту `ID_<CATEGORY>_<ATTRIBUTE>`. Полный список доступных свойств можно получить командой:
```bash
udevadm info -a -n /dev/sda | grep '{id}'
```

### Безопасность и модель разрешений

`udev` предоставляет три механизма управления доступом к устройствам, которые следует использовать согласно принципу наименьших привилегий:

| Механизм | Уровень | Применение | Ограничения |
| :--- | :--- | :--- | :--- |
| **`MODE`** | POSIX права | Быстрые задания прав для всех пользователей | Неинтерактивный, не учитывает активную сессию. `MODE="0666"` небезопасен в многопользовательских системах. |
| **POSIX ACL** | Расширенные ACL | Точечное назначение прав пользователям/группам | Требует ручного управления, не масштабируется при смене пользователя. |
| **`TAG+="uaccess"`** | Сессионный ACL | Предоставляет доступ только активному пользователю локальной сессии | Рекомендуемый способ для периферийных устройств (USB, Thunderbolt). Требует running `systemd-logind`. |

**Взаимодействие с polkit:** В системах с `systemd-logind` политики доступа к устройствам могут управляться через `polkit`. Например, подключение внешнего диска может требовать аутентификации, если текущий пользователь не находится в локальной сессии.

**Контекст безопасности:** В системах с включенным Secure Boot режим **Lockdown** (`integrity` или `confidentiality`) ограничивает возможности `udev` по загрузке неподписанных модулей и прямому доступу к оборудованию.

### Интеграция с systemd

Правила `udev` тесно интегрированы с `systemd` через несколько механизмов:

#### 1. Файлы `.link` (Physical Layer Configuration)

Файлы `.link` применяются `udev` при обнаружении устройства для изменения его физических параметров (имя интерфейса, MAC-адрес, MTU). Они обрабатываются до применения сетевых правил.

```ini
# /etc/systemd/network/10-storage.link
[Match]
MACAddress=00:a1:b2:c3:d4:e5

[Link]
Name=eth-storage
MTUBytes=9000
```

**Приоритет:** Файлы `.link` обрабатываются раньше, чем правила `udev` из `rules.d/`, и имеют более высокий приоритет для переименования интерфейсов.

#### 2. Юниты `.device`

Для каждого обнаруженного устройства `systemd` создает виртуальный юнит `.device`. Например, `/dev/sda` соответствует юниту `dev-sda.device`. Эти юниты используются для выражения зависимостей:

```ini
# /etc/systemd/system/mnt-data.mount
[Unit]
After=dev-sdb1.device
Requires=dev-sdb1.device
```

#### 3. Триггерing юнитов через `SYSTEMD_WANTS`

Правила `udev` могут запрашивать запуск systemd-юнитов, передавая их имена через `ENV{SYSTEMD_WANTS}`:

```text
# /etc/udev/rules.d/99-backup.rules
ACTION=="add", SUBSYSTEM=="block", ENV{ID_SERIAL_SHORT}=="XYZ123", TAG+="systemd", ENV{SYSTEMD_WANTS}+="backup-task@%k.service"
```

`%k` заменяется на имя ядра устройства (например, `sdb`). Использование `TAG+="systemd"` обязательно для активации механизма.

**Преимущество:** `systemd` управляет жизненным циклом сервиса, включая таймауты, зависимости и логирование. Это корректно替代яет прямое использование `RUN` для долгих задач.

#### 4. `systemd-run` для долгих операций

Если требуется запустить произвольный скрипт, который может выполняться дольше таймаута `udev` (по умолчанию 180 секунд), используйте `systemd-run`:

```text
RUN+="/usr/bin/systemd-run --unit=my-handler@%k /usr/local/bin/handler.sh %k"
```

`systemd-run` создает transient-юнит, который существует независимо от жизненного цикла процесса `udev`.

**Основные функции:**

| Функция | Описание |
| :--- | :--- |
| **Динамическое управление** | Создание и удаление нод устройств (device nodes) в `/dev` в реальном времени. |
| **Именование (Persistent Naming)** | Присвоение стабильных имен и создание симлинков на основе атрибутов (UUID, серийный номер, путь на шине). |
| **Управление доступом** | Назначение владельцев, групп и прав (POSIX ACL) через механизм `uaccess`. |
| **Загрузка драйверов** | Автоматическая загрузка модулей ядра при обнаружении нового оборудования. |
| **Информационная база** | Поддержка базы данных состояний устройств для других программ (например, `lsblk`, `Xorg`, `libinput`). |
| **Интеграция с systemd** | Триггерing юнитов, применение `.link` файлов, создание `.device` юнитов. |

## Основные концепции

### Правила udev (udev rules)

Правила определяют логику обработки событий. Они считываются при запуске демона и могут быть обновлены на лету.

**Расположение правил (в порядке приоритета):**
1.  **Пользовательские:** `/etc/udev/rules.d/` — основной каталог для администратора.
2.  **Временные:** `/run/udev/rules.d/` — генерируются динамически во время работы.
3.  **Системные:** `/usr/lib/udev/rules.d/` — поставляются дистрибутивом. **Не редактируйте их напрямую.**

**Синтаксис:** Файлы должны иметь расширение `.rules`. Имена начинаются с двузначного числа (приоритет), например `60-persistent-storage.rules`. Чем меньше число, тем выше приоритет. Правила обрабатываются последовательно, поэтому порядок внутри файла и между файлами важен.

#### Ключи сопоставления (Match Keys)

Используются для идентификации устройства. Оператор `==` (равно) или `!=` (не равно).

| Ключ | Описание | Пример |
| :--- | :--- | :--- |
| `SUBSYSTEM` | Категория устройства. | `SUBSYSTEM=="net"` |
| `KERNEL` | Имя устройства в ядре. | `KERNEL=="sd[a-z]*"` |
| `ATTRS{file}` | Атрибут в `sysfs` (включая родителей). | `ATTRS{model}=="SATA SSD"` |
| `ENV{var}` | Переменная окружения udev. | `ENV{ID_FS_TYPE}=="ext4"` |
| `DRIVERS` | Имя драйвера ядра. | `DRIVERS=="usb-storage"` |
| `ACTION` | Тип события. | `ACTION=="add|change|remove"` |

#### Ключи действий (Assignment Keys)

Используются для изменения параметров. Оператор `=` (установить) или `+=` (добавить в список).

| Ключ | Описание | Пример |
| :--- | :--- | :--- |
| `NAME` | Имя интерфейса (только для сетевых карт). | `NAME="eth-internal"` |
| `SYMLINK` | Создать символическую ссылку в `/dev`. | `SYMLINK+="usb_flash"` |
| `OWNER, GROUP` | Назначить владельца и группу. | `GROUP="dialout"` |
| `MODE` | Установить права доступа. | `MODE="0660"` |
| `TAG` | Добавить тег (например, `uaccess`). | `TAG+="uaccess"` |
| `RUN` | Выполнить внешнюю команду. | `RUN+="/usr/bin/logger"` |
| `ENV{}` | Установить переменную окружения события. | `ENV{SYSTEMD_WANTS}+="service"` |

#### Переменные подстановки

В правилах `udev` доступны переменные, которые заменяются во время обработки события:

| Переменная | Описание | Пример |
| :--- | :--- | :--- |
| `%k` | Имя ядра устройства. | `sdb`, `eth0` |
| `%n` | Номер устройства (для блочных устройств — номер раздела). | `1` для `sdb1` |
| `%p` | Имя родительского устройства. | `pci-0000:00:1f.2` |
| `%c` | Значение свойства, заданного ключом `ENV{...}`. | Значение `ID_SERIAL` |
| `%%` | Символ `%`. | Используется для экранирования |

### Аппаратная база данных (hwdb)

**udev hwdb** — это бинарная база данных, содержащая дополнительные свойства устройств (например, названия моделей, специфические настройки клавиатур, корректировки акселерометров), которые невозможно получить напрямую из `sysfs`.

- **Исходные файлы:** `/usr/lib/udev/hwdb.d/` и `/etc/udev/hwdb.d/`.
- **Обновление базы:** `sudo udevadm hwdb --update`.
- **Применение:** udev импортирует данные из hwdb в переменные окружения события.

**Структура файла hwdb:**
```text
# /etc/udev/hwdb.d/90-custom-keyboard.hwdb
evdev:input:*
  KEYBOARD_KEY_700e2=launch1
  KEYBOARD_KEY_700e3=battery
```

После изменения файлов hwdb всегда выполните:
```bash
sudo udevadm hwdb --update && sudo udevadm trigger --attr-match=subsystem=input
```

### Предсказуемые имена сетевых интерфейсов

Механизм **Predictable Network Interface Names** (введен в systemd) заменяет нестабильные имена типа `eth0` на имена, привязанные к физическому расположению (слот PCI, USB-порт).

**Схемы именования:**
1.  `enp0s3`: Ethernet на шине PCI 0, слот 3.
2.  `wlp2s0`: Wi-Fi на шине PCI 2, слот 0.
3.  `enx<MAC>`: Имя на основе MAC-адреса (часто для USB-адаптеров).

За это отвечает правило `80-net-setup-link.rules` и встроенная команда `net_id`.

**Отключение предсказуемых имен:** В редких случаях (например, совместимость с устаревшим ПО) можно вернуться к традиционным именам, добавив параметр загрузчика `net.ifnames=0` или создав собственный `.link` файл. Однако это не рекомендуется для production-систем.

### Udev в ранней загрузке (initramfs)

`udev` запускается еще до монтирования корневой файловой системы. Его задачи в `initramfs`:
1.  Обнаружение контроллеров дисков и загрузка модулей.
2.  Создание нод для RAID, LVM и зашифрованных разделов.
3.  Ожидание появления устройства, указанного в параметре `root=` загрузчика.

**Особенности:** В `initramfs` используются облегченные правила и ограниченный набор модулей. Если критическое устройство не определяется, проверьте модули в `MODULES` (dracut) или `initramfs` (mkinitcpio).

### Обнаружение и обработка устройств

**Поиск устройств в sysfs:**

Для написания правил udev необходимо знать точные атрибуты устройства. Используйте команду `udevadm info` для обхода дерева устройств:

```bash
# Полный обход атрибутов устройства (включая родителей)
udevadm info -a -n /dev/sdb

# Только свойства (key=value)
udevadm info -q property -n /dev/sdb1

# Фильтр по подстроке
udevadm info -q property -n /dev/sdb1 | grep -E 'ID_FS_UUID|ID_FS_TYPE|ID_SERIAL'
```

**Путь в sysfs vs путь в ядре:**
- Путь в sysfs: `/sys/block/sdb/sdb1` — отражает иерархию устройств.
- Путь в ядре: `/dev/sdb1` — имя узла устройства.

При написании правил используйте `KERNEL=="sd[a-z]*"` для совпадения с именами ядра и `ENV{ID_SERIAL}=="..."` для совпадения с свойствами udev.

## Управление и диагностика (udevadm)

`udevadm` — основной инструмент администратора.

```bash
# Мониторинг событий в реальном времени (add/remove/change)
udevadm monitor --udev --property

# Получение всех атрибутов устройства (для написания правил)
# Используйте путь из /dev или /sys
udevadm info -a -n /dev/sdb

# Проверка применения правил без физического переподключения (test)
udevadm test /sys/class/block/sdb

# Перезагрузка правил и базы hwdb
sudo udevadm control --reload-rules
sudo udevadm hwdb --update

# Принудительный вызов событий для существующих устройств
sudo udevadm trigger

# Сброс кэша устройств (например, после изменения правил переименования)
sudo udevadm settle --timeout=30
```

### Мониторинг событий: что между ядром и /dev

Появление файла устройства в `/dev` — это двухфазный процесс. Ядро само по себе только публикует событие (uevent); реальный файл в `/dev` создаётся либо на уровне `devtmpfs` (базовая нода), либо демоном `systemd-udevd` (симлинки и свойства). Команда `udevadm monitor` показывает обе фазы в реальном времени и позволяет увидеть, где именно происходит обработка.

```bash
# Полный мониторинг: события ядра + события userspace udev
udevadm monitor
# → KERNEL[12345.678901] add      /devices/.../usb1/1-2 (usb)
# → UDEV   [12345.681234] add      /devices/.../usb1/1-2 (usb)
```

**Структура строки вывода:**

- `KERNEL[...]` — событие сгенерировано ядром (kobject uevent). Устройство обнаружено драйвером, но udev ещё не обработал его.
- `UDEV  [...]` — событие обработано демоном `systemd-udevd`: прочитаны атрибуты `sysfs`, применены правила, созданы симлинки, выставлены права. После этой строки файл устройства и сопутствующие симлинки гарантированно присутствуют в `/dev`.

**Разница между двумя этапами:** строка `KERNEL` показывает, что ядро зарегистрировало устройство; строка `UDEV` показывает, что userspace-часть закончила обработку. Между ними udev запускает внешние программы (например, `ata_id`, `scsi_id`), читает `hwdb`, применяет правила и при необходимости вызывает `RUN` или запускает systemd-юниты. Если в логе есть только `KERNEL add`, но нет `UDEV add` — обработка зависла (часто из-за длительного `RUN`-скрипта или ошибки в правиле).

**Фильтрация событий:**

```bash
# Только события ядра
udevadm monitor --kernel

# Только события userspace udev
udevadm monitor --udev

# Конкретная подсистема (block — диски, net — сетевые, usb — USB)
udevadm monitor --kernel --udev --subsystem-match=block

# Свойства события (ID_SERIAL, ID_FS_TYPE и т.д.)
udevadm monitor --udev --subsystem-match=block --property
```

**Типичная картина при подключении диска:**

```bash
udevadm monitor --kernel --udev --subsystem-match=block
# → KERNEL[...] add /devices/.../nvme0n1   (block)
# → KERNEL[...] add /devices/.../nvme0n1p1 (block)
# → KERNEL[...] add /devices/.../nvme0n1p2 (block)
# → UDEV   [...] add /devices/.../nvme0n1   (block)
# → UDEV   [...] add /devices/.../nvme0n1p1 (block)
# → UDEV   [...] add /devices/.../nvme0n1p2 (block)
```

Сначала идут все `KERNEL`-события (ядро обнаружило диск и его разделы почти одновременно), затем — соответствующие `UDEV`-события после применения правил. Разделы (`p1`, `p2`) обрабатываются отдельными событиями, что позволяет задавать для них индивидуальные правила и симлинки.

### Идентификация устройства и стабильные имена

Имя `/dev/sdX` нестабильно: после перезагрузки один и тот же диск может стать `sdb` или `sdc`. Чтобы понять, почему устройство получило конкретное имя и какие стабильные ссылки ему соответствуют, используется `udevadm info`.

```bash
# Полный набор данных: атрибуты sysfs + свойства udev + путь в sysfs
udevadm info --query=all --name=/dev/sda

# Только свойства (key=value) — то, что доступно в правилах через ENV{...}
udevadm info --query=property --name=/dev/sdb

# Только путь в sysfs (для udevadm test)
udevadm info --query=path --name=/dev/sdb
# → /devices/pci0000:00/0000:00:1f.2/ata1/host0/target0:0:0/0:0:0:0/block/sdb
```

**Ключевые свойства, формирующие стабильные симлинки:**

| Свойство | Источник | Симлинк в `/dev/disk/` |
| :--- | :--- | :--- |
| `ID_SERIAL`, `ID_SERIAL_SHORT` | серийный номер (SCSI, NVMe, USB) | `by-id/` |
| `ID_WWN` | World Wide Name (ATA/SCSI) | `by-id/` |
| `ID_FS_UUID`, `ID_FS_LABEL` | UUID/label файловой системы | `by-uuid/`, `by-label/` |
| `ID_PATH`, `ID_PATH_TAG` | физический путь по шине (PCI/USB) | `by-path/` |
| `ID_MODEL`, `ID_VENDOR` | модель/производитель | используется в правилах |
| `ID_FS_TYPE` | тип ФС (ext4, xfs, swap) | используется в правилах |

**Кейс: диск меняет имя `sda`/`sdb` после перезагрузки.** Имя `sdX` назначается ядром в порядке обнаружения и не привязано к конкретному устройству. Решение — использовать стабильный идентификатор:

```bash
# Узнать стабильный идентификатор текущего диска
udevadm info --query=property --name=/dev/sdb | grep -E 'ID_SERIAL|ID_PATH|ID_FS_UUID'
# → ID_SERIAL=ATA_Samsung_SSD_860_S3Z2NX0M123456
# → ID_PATH=pci-0000:00:1f.2-ata-1
# → ID_FS_UUID=a1b2c3d4-...

# Использовать в /etc/fstab и сервисах
UUID=a1b2c3d4-...  /mnt/data  ext4  defaults,nofail  0  2
# или
/dev/disk/by-id/ata-Samsung_SSD_860_S3Z2NX0M123456  /mnt/data  ext4  defaults,nofail  0  2
```

`nofail` в опциях `fstab` важен для дисков, которые могут быть не подключены при загрузке: система загрузится даже при их отсутствии.

### Валидация правил

Перед применением правил проверьте их синтаксис:

```bash
# Проверить синтаксис всех файлов в каталоге
sudo udevadm test $(udevadm info -q path -n /dev/sdb)

# Проверить конкретное правило
sudo udevadm test --action=add /sys/class/block/sdb
```

В выводе `udevadm test` обратите внимание на раздел `UEVENT` и `PROGRAM`, где показано, какие правила сработали и какие команды будут выполнены.

## Практические сценарии

### 1. Стабильное именование дисков для баз данных

Используйте симлинки в `/dev/disk/by-id/` или создайте собственные через `SYMLINK`, чтобы избежать путаницы при добавлении/удалении дисков.

```text
# /etc/udev/rules.d/60-persistent-storage.rules
# Создание симлинка для SSD баз данных PostgreSQL
SUBSYSTEM=="block", ENV{ID_SERIAL_SHORT}=="Samsung_SSD_960_PRO_xxx", SYMLINK+="disk/postgres_ssd"

# Симлинк для HDD с данными backup
SUBSYSTEM=="block", ENV{ID_SERIAL_SHORT}=="WD40EFRX_xxx", SYMLINK+="disk/backup_hdd"
```

**Применение и проверка:**
```bash
sudo udevadm control --reload-rules
sudo udevadm trigger --type=devices --action=add

# Проверка
ls -l /dev/disk/postgres_ssd
# → /dev/disk/postgres_ssd -> ../../sda
```

**Важно:** Используйте симлинки в `/etc/fstab` и конфигурациях сервисов, а не прямые пути `/dev/sda`. Это предотвратит сбои при изменении порядка обнаружения дисков.

### 2. Доступ к USB-устройству без root (uaccess)

Механизм `uaccess` предоставляет ACL-права только активному пользователю в локальной сессии. Это безопаснее, чем `MODE="0666"`.

```text
# /etc/udev/rules.d/50-my-device.rules
# Разрешить доступ к программатору (VendorID:ProductID)
SUBSYSTEM=="usb", ATTR{idVendor}=="1234", ATTR{idProduct}=="abcd", TAG+="uaccess"
```

**Проверка:**
```bash
# Подключите устройство и проверьте ACL
getfacl /dev/bus/usb/001/005

# В выводе должен быть владелец с правами rw
# owner:ivan:rw-
```

**Примечание:** `uaccess` работает только при наличии активной локальной сессии (`logind`). Для headless-серверов или Docker-контейнеров используйте `MODE` или `GROUP`:

```text
SUBSYSTEM=="usb", ATTR{idVendor}=="1234", ATTR{idProduct}=="abcd", GROUP="plugdev", MODE="0660"
```

### 3. Управление сетевыми интерфейсами

#### 3.1 Персистентное именование через .link файлы

На современных системах предпочтительнее использовать `.link` файлы `systemd-networkd` вместо правил `udev` для переименования интерфейсов:

```ini
# /etc/systemd/network/10-storage-nic.link
[Match]
MACAddress=00:a1:b2:c3:d4:e5
Driver=ixgbe

[Link]
Name=eth-storage
MTUBytes=9000
```

#### 3.2 MAC-адрес и VFIO (SR-IOV)

Для проброса виртуальных функций (VF) в гостевую ВМ используйте правила `udev` для фиксации MAC-адреса и перевода в unbind:

```text
# /etc/udev/rules.d/99-vfio-pci.rules
# Привязать VF к драйверу vfio-pci
SUBSYSTEM=="drm", KERNEL=="card*", RUN+="/usr/bin/bash -c 'echo %k > /sys/bus/pci/drivers/vfio-pci/bind'"
```

Подробнее см. [Настройка SR-IOV и VFIO](../../Networking/Concepts/dpdk/sriov_setup.md).

### 4. Запуск задачи при подключении диска

**Важно:** Использование `RUN` напрямую для долгих задач (например, бэкапа) запрещено, так как udev убьет процесс по таймауту. Правильный способ — запуск systemd-юнита.

```text
# /etc/udev/rules.d/99-backup.rules
# Запуск сервиса при появлении диска с конкретным серийным номером
ACTION=="add", SUBSYSTEM=="block", ENV{ID_SERIAL_SHORT}=="XYZ123", TAG+="systemd", ENV{SYSTEMD_WANTS}+="backup-task@%k.service"
```

**Создание соответствующего сервиса:**

```ini
# /etc/systemd/system/backup-task@.service
[Unit]
Description=Backup task for %i
After=dev-%i.device
Requires=dev-%i.device

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh /dev/%i
User=backup
Group=backup
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

### 5. Настройка планировщика I/O

Настройка планировщика для разных типов дисков (HDD vs SSD). Подробную теорию и альтернативные подходы см. в [Планировщики ввода-вывода](./kernel/io_schedulers.md).

```text
# /etc/udev/rules.d/60-iosched.rules
# Установить bfq для вращающихся дисков (HDD)
ACTION=="add|change", KERNEL=="sd[a-z]", ATTR{queue/rotational}=="1", ATTR{queue/scheduler}="bfq"

# mq-deadline для SATA SSD
ACTION=="add|change", KERNEL=="sd[a-z]", ATTR{queue/rotational}=="0", ATTR{queue/scheduler}="mq-deadline"

# Отключить планировщик для NVMe
ACTION=="add|change", KERNEL=="nvme*", ATTR{queue/scheduler}="none"
```

### 6. Автоматическое монтирование USB

Для автоматического монтирования внешних носителей используйте отдельные правила `udev` в связке с `systemd-mount` или готовые `.mount` юниты. Подробные сценарии см. в [Automount через udev](../FileSystems/mounting/scenarios/udev_mount.md).

**Краткий пример (только для справки):**
```text
# /etc/udev/rules.d/99-usb-mount.rules
ACTION=="add", SUBSYSTEM=="block", ENV{ID_FS_UUID}=="a1b2c3d4", \
    RUN+="/usr/bin/systemd-mount --no-block --collect --options=noatime,nodev,nosuid /dev/%k /mnt/backup"
```

### 7. Мониторинг и observability

#### 7.1 Мониторинг событий udev в production

```bash
# Просмотр событий в реальном времени с фильтрацией по подсистеме
udevadm monitor --udev --subsystem-match=block --property

# Мониторинг только событий добавления
udevadm monitor --udev --property | grep '^ACTION=.*add'
```

#### 7.2 Логирование

Все события и ошибки `udev` пишутся в journald:

```bash
# Просмотр логов udev в реальном времени
journalctl -u systemd-udevd -f

# Просмотр ошибок за последний час
journalctl -u systemd-udevd --since "1 hour ago" -p err

# Поиск ошибок применения правил для конкретного устройства
journalctl -u systemd-udevd | grep -i 'sdb'
```

#### 7.3 Статистика и медленные правила

```bash
# Проверка времени обработки событий
systemd-analyze blame | grep udev

# Поиск медленных RUN-скриптов
journalctl -u systemd-udevd | grep -E 'run|timeout|killed'
```

### 8. Edge Cases и нестандартные сценарии

#### 8.1 Горячее подключение/отключение (Hotplug)

При интенсивном подключении/отключении устройств (например, USB-хабы с множеством флешек) могут возникать гонки:

```text
# /etc/udev/rules.d/99-race-fix.rules
# Задержка перед выполнением действия для стабилизации устройства
ACTION=="add", SUBSYSTEM=="block", ENV{ID_FS_TYPE}!="", RUN+="/usr/bin/systemd-run --delay=2 /usr/local/bin/stable-handler.sh %k"
```

#### 8.2 Устройства с одинаковыми серийными номерами

Некоторые USB-устройства (особенно некачественные) имеют одинаковые серийные номера. В таких случаях используйте путь на шине (`by-path`) или комбинацию атрибутов:

```text
SUBSYSTEM=="block", ENV{ID_PATH}=="pci-0000:00:14.0-usb-0:2:1.0", SYMLINK+="disk/usb_port2"
```

#### 8.3 Инициализация LVM и Multipath

`udev` автоматически активирует LVM-группы при появлении физических томов. Для тонкой настройки:

```text
# /etc/udev/rules.d/12-dm-permissions.rules
# Запретить автоматическую активацию определенных PV
ENV{DM_NAME}=="vg_data", ENV{SYSTEMD_WANTS}+="disable-lvm-activation@%k.service"
```

## Устранение неполадок

### Типичные ошибки и диагностика

| Проблема | Причина и решение |
| :--- | :--- |
| **Правило не работает** | Проверьте синтаксис (частая ошибка: `=` вместо `==`). Убедитесь, что файл заканчивается на `.rules`. Используйте `udevadm test` для отладки. |
| **Скрипт в RUN не видит команд** | У `udev` ограниченный `$PATH`. Используйте только абсолютные пути: `/usr/bin/ls` вместо `ls`. |
| **Переменные ENV пустые** | Убедитесь, что вы не пытаетесь использовать переменные до того, как они были импортированы (порядок правил важен). Используйте `udevadm info` для проверки доступных свойств. |
| **Устройство "занято" при переименовании** | Сетевые интерфейсы нельзя переименовывать, если они уже подняты (UP). Используйте `.link` файлы systemd или отключите интерфейс перед переименованием. |
| **Правило срабатывает дважды** | Проверьте наличие дублирования в разных каталогах (`/etc/` и `/usr/lib/`). Используйте `ENV{ID_FS_TYPE}=="ext4"` для сужения совпадения. |
| **Монтирование не происходит** | Проверьте `systemctl status` для соответствующего mount-юнита. Убедитесь, что используется `systemd-mount` или `ENV{SYSTEMD_WANTS}`, а не прямой `RUN+="/bin/mount"`. |
| **Устройство исчезает после перезагрузки** | Для RAID/ multipath проверьте, что `mdadm.conf` или `multipath.conf` содержит конфигурацию. Иначе `udev`/`initramfs` не соберут массив автоматически. |
| **Права доступа не применяются** | Проверьте наличие тега `uaccess` или правильный `GROUP`/`MODE`. В headless-средах `uaccess` не работает без `logind`. |

### Методика отладки сложных правил

1.  **Получите полный путь устройства:**
    ```bash
    udevadm info -q path -n /dev/sdb
    # → /devices/pci0000:00/0000:00:1f.2/ata1/host0/target0:0:0/0:0:0:0/block/sdb
    ```

2.  **Протестируйте правило на этом пути:**
    ```bash
    sudo udevadm test --action=add /sys/block/sdb
    ```

3.  **Проверьте последовательность применения:**
    В выводе `udevadm test` найдите строки `udev_rules_apply` и проверьте, что ваше правило появилось в списке. Если нет — проверьте приоритет (двузначное число в начале имени файла).

4.  **Принудительный вызов события:**
    ```bash
    sudo udevadm trigger --subsystem-match=block --action=add /dev/sdb
    ```

5.  **Ожидание завершения обработки:**
    ```bash
    sudo udevadm settle --timeout=30
    ```

6.  **Проверка логов:**
    ```bash
    journalctl -u systemd-udevd -f
    ```

### Восстановление после сбоя именования

Если неправильное правило переименовало критический интерфейс, и система потеряла доступность:

1.  Перезагрузитесь в rescue-режим или используйте `init=/bin/bash`.
2.  Переименуйте или удалите проблемный файл в `/etc/udev/rules.d/`.
3.  Пересоберите `initramfs` (если правило влияет на раннюю загрузку):
    ```bash
    dracut --force /boot/initramfs-%version%.img %version%
    ```
4.  Перезагрузитесь.

## Best Practices для SRE и Sysadmin

### 1. Стабильность имен устройств

- **Всегда используйте** пути `/dev/disk/by-uuid/`, `/dev/disk/by-label/` или `/dev/disk/by-id/` в `/etc/fstab`, конфигурациях сервисов и скриптах мониторинга.
- **Не полагайтесь** на имена вида `/dev/sda`, `/dev/nvme0n1` — они могут измениться при добавлении/удалении оборудования.
- Для критических систем создайте собственные симлинки через `SYMLINK` в правилах `udev` с понятными именами (например, `disk/postgres_data`).

### 2. Правила таймаутов и долгие операции

- **Никогда не используйте** `RUN+="/bin/mount"` или `RUN+="/usr/bin/rsync"` напрямую в правилах `udev`.
- Для долгих задач всегда используйте `ENV{SYSTEMD_WANTS}` или `systemd-run`.
- Установите разумные таймауты для сервисов, запускаемых через `udev`, чтобы они не блокировали очередь событий.

### 3. Безопасность

- **Избегайте** `MODE="0666"` и открытых прав для всех устройств. Используйте `GROUP` + `MODE="0660"` для shared-устройств или `TAG+="uaccess"` для интерактивных.
- Для headless-серверов добавьте пользователей в группу `dialout`, `plugdev` или создайте специализированные группы.
- Регулярно аудируйте правила в `/etc/udev/rules.d/` на предмет избыточных прав.

### 4. Мониторинг и алертинг

- **Мониторьте** логи `systemd-udevd` на предмет ошибок:
  ```bash
  journalctl -u systemd-udevd -p err --since "24 hours ago"
  ```
- **Алерт** на массовые события `remove` для блочных устройств — это может указывать на проблемы с шиной или cables.
- **Валидируйте** правила после изменений в CI/CD пайплайне:
  ```bash
  udevadm test $(udevadm info -q path -n /dev/sda) | grep -E 'error|fail|invalid'
  ```

### 5. Версионирование и откат

- Храните правила `udev` в Git-репозитории.
- Тестируйте правила на staging-сервере перед применением в production.
- Для отката изменений:
  ```bash
  sudo udevadm control --reload-rules
  sudo udevadm trigger --type=devices --action=remove
  ```

### 6. Производительность

- Минимизируйте количество правил в `/etc/udev/rules.d/`. Удаляйте устаревшие правила.
- Избегайте сложных скриптов в `RUN`. Если логика превышает 10 строк, вынесите ее в systemd-сервис.
- Используйте `IMPORT{program}` вместо `RUN` для сбора данных, если возможно — это неблокирующая операция.
