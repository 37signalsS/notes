# SSD: Burst I/O и деградация производительности

## Определения

**Burst I/O (Взрывной ввод-вывод)** — явление, при котором SSD обеспечивает кратковременную пиковую производительность, значительно превышающую его возможности в установившемся режиме (Steady State). После заполнения внутренних буферов или кэша скорость записи резко падает, а задержки (latency) растут.

**Write Amplification (WA — усиление записи)** — коэффициент, отражающий отношение объема данных, фактически записанных во флеш-память, к объему данных, полученных от операционной системы. Идеальное значение WA = 1.0; реальные значения для случайной записи могут достигать 3–10.

**Garbage Collection (GC — сборка мусора)** — фоновый процесс контроллера по очистке блоков памяти от невалидных данных (удаленных файлов) для подготовки ячеек к новой записи.

**Zoned Namespaces (ZNS) / Flexible Data Placement (FDP)** — современные технологии NVMe (2024–2026 гг.), позволяющие хост-системе или приложению напрямую управлять размещением данных на накопителе, минимизируя WA и влияние GC.

## Основные концепции

### Причины деградации производительности

Деградация SSD обусловлена физическими ограничениями NAND-памяти и архитектурой контроллеров.

1.  **Исчерпание SLC-кэша:** Потребительские диски (TLC/QLC) используют часть ячеек в быстром SLC-режиме. При длительной непрерывной записи кэш переполняется, и контроллер вынужден писать напрямую в медленные ячейки, одновременно уплотняя данные, что снижает скорость в 5–10 раз.
2.  **Агрессивная сборка мусора (GC):** Когда на диске мало свободного места, контроллер начинает перемещать данные «на лету» во время записи пользователя. Это создает микропаузы и увеличивает «хвостовые» задержки (tail latency).
3.  **Влияние PLP (Power Loss Protection) на синхронную запись:**
    -   **Enterprise SSD (с PLP):** Имеют конденсаторы, позволяющие подтверждать запись сразу после попадания в RAM-кэш диска. Это делает операции `fsync` и `FUA (Force Unit Access)` чрезвычайно быстрыми.
    -   **Consumer SSD (без PLP):** Вынуждены сбрасывать данные из кэша на медленную NAND-память при каждом подтверждении записи, что катастрофически снижает производительность баз данных.
4.  **Насыщение очереди (Queue Depth):** При пиковых нагрузках (Burst) аппаратные очереди контроллера могут переполняться. Новые запросы ожидают в блочном слое ядра, что приводит к экспоненциальному росту задержек.

### Архитектура стека ввода-вывода (2025–2026)

*   **blk-mq (Multi-Queue):** Стандартный многоочередной слой ядра Linux, эффективно распределяющий нагрузку по ядрам CPU.
*   **NVMe Passthrough (`io_uring_cmd`):** Современный метод (ядро 6.x), позволяющий приложениям (RocksDB, SPDK) отправлять команды напрямую контроллеру, минуя планировщики и абстракции блочного слоя. Это снижает нагрузку на CPU и уменьшает задержки на 30–40%.

## Практические сценарии

### Мониторинг и диагностика

Для анализа состояния NVMe-накопителей используйте специализированные инструменты.

```bash
# Просмотр статистики ошибок и температуры (nvme-cli)
sudo nvme smart-log /dev/nvme0

# Идентификация поддержки FDP (Flexible Data Placement)
sudo nvme id-ctrl /dev/nvme0 -H | grep "FDP"
```

**Анализ задержек через iostat:**
```bash
iostat -x 1 /dev/nvme0n1
# Обращайте внимание на 'await' (среднее время) и '%util'.
# Для NVMe значение await > 0.5 мс под нагрузкой может указывать на начало деградации.
```

### Оптимизация на уровне ядра

1.  **Выбор планировщика:** Для NVMe всегда рекомендуется использовать `none` (отсутствие планировщика), так как задержки алгоритмов ядра выше, чем задержки самого накопителя.
    ```bash
    echo none | sudo tee /sys/block/nvme0n1/queue/scheduler
    ```
2.  **Тюнинг глубины очереди:**
    ```bash
    # Увеличение nr_requests позволяет сглаживать пиковые Burst-нагрузки
    echo 256 | sudo tee /sys/block/nvme0n1/queue/nr_requests
    ```
3.  **Использование io_uring:** Перевод приложений на асинхронный движок `io_uring` с поддержкой `O_DIRECT` является наиболее эффективным способом минимизации эффекта Burst I/O.

### Управление свободным пространством

**Over-Provisioning (OP):** Резервирование части объема диска (например, 10–20%), недоступной файловой системе. Это дает контроллеру больше места для GC, радикально снижает Write Amplification и стабилизирует производительность в Steady State.

## Дополнительная информация

### Сравнение поведения дисков

| Параметр | Consumer (TLC/QLC) | Enterprise (Mixed Use) |
| :--- | :--- | :--- |
| **Steady State Speed** | Нестабильна, низкая | Постоянная, высокая |
| **Write Amplification** | Высокий (из-за SLC-кэша) | Низкий (оптимизированный FTL) |
| **PLP** | Нет (риск при fsync) | Да (быстрые транзакции) |
| **Ресурс (TBW)** | Низкий | Очень высокий |
