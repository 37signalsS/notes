# SSD: Burst I/O и деградация производительности

## Определения

**Burst I/O на SSD (Solid State Drive — твердотельный накопитель)** — явление, при котором кратковременные пиковые нагрузки приводят к резкому росту задержек (latency) и падению пропускной способности (throughput), несмотря на высокие заявленные характеристики устройства.

**Write Amplification (WA — усиление записи)** — коэффициент, показывающий, во сколько раз фактический объём записи на NAND флеш-память превышает объём данных, полученных от хоста. `WA = (запись на NAND) / (запись от хоста)`.

**Garbage Collection (GC — сборка мусора)** — фоновый процесс контроллера SSD по перемещению валидных данных из частично заполненных блоков для их последующего стирания и освобождения под новые записи.

## Основные концепции

### Архитектурные причины деградации

Проблема коренится в физике NAND флеш-памяти и алгоритмах работы контроллера SSD.

**1. Garbage Collection (Сборка мусора)**
Ячейки флеш-памяти нельзя перезаписать напрямую — блок данных необходимо сначала стереть. При интенсивной записи контроллер активирует фоновую сборку мусора: перемещает валидные страницы из «грязных» блоков в новые. Этот процесс создаёт **микропаузы**, во время которых запросы от операционной системы ожидают завершения внутренних переупаковок.

**2. Write Amplification (Усиление записи)**
Мелкий случайный ввод-вывод (random I/O) заставляет контроллер перезаписывать целые блоки памяти, даже если изменились лишь отдельные страницы.

```
WA = 1   — идеально (последовательная запись)
WA = 3–10 — типично для мелкого random I/O
```

Последствия: ускоренный износ ячеек (сокращение ресурса TBW — Total Bytes Written) и рост задержек.

**3. Насыщение очереди команд (Queue Depth saturation)**
Контроллер SSD имеет ограниченную глубину очереди. Когда пиковая нагрузка исчерпывает этот лимит, новые запросы ожидают на стороне хоста, что приводит к скачкам latency.

**4. Исчерпание SLC-кэша**
Многие потребительские и часть корпоративных SSD используют SLC-кэш (псевдо-SLC на базе TLC/QLC ячеек). При непрерывной записи кэш переполняется, и контроллер переключается на прямую запись в медленные ячейки, что снижает скорость в 3–10 раз.

### Взаимосвязь факторов

```
Мелкий random I/O / Burst-запись
    ↓
Write Amplification ↑
    ↓
Garbage Collection активнее
    ↓
Контроллер занят внутренней переупаковкой
    ↓
Очередь (Queue Depth) заполняется → latency растёт, throughput падает
```

## Практические сценарии

### Минимизация эффекта burst I/O

**1. Асинхронный ввод-вывод**
Используйте современные интерфейсы вместо блокирующих синхронных операций:

- **`io_uring`** — современный интерфейс ядра (5.1+), минимизирует накладные расходы на системные вызовы. Подробнее: [**io_uring — асинхронный ввод-вывод**](./io_uring.md).

**2. Настройка глубины очереди в ядре**

```bash
# Проверить текущее значение лимита запросов
cat /sys/block/sda/queue/nr_requests
# → 128

# Увеличить лимит для сглаживания пиков
echo 256 | sudo tee /sys/block/sda/queue/nr_requests
# → 256
```

**3. Выбор планировщика ввода-вывода (I/O Scheduler)**

```bash
# Проверить текущий планировщик
cat /sys/block/sda/queue/scheduler
# → [mq-deadline] none bfq kyber
```

Для быстрых NVMe (Non-Volatile Memory Express) рекомендуется `none`, для SATA SSD — `mq-deadline`. Подробнее: [**I/O Schedulers**](./io_schedulers.md).

**4. Прямой ввод-вывод (Direct I/O)**
Обход системного кэша страниц (page cache) устраняет лишние копирования данных в памяти:

```bash
# Тест производительности с direct I/O через dd
dd if=/dev/zero of=testfile bs=4k count=100000 oflag=direct
# → 100000+0 records in ... 409.6 MB, 120 MB/s
```

**5. Мониторинг производительности и трассировка**

```bash
# Расширенная статистика каждую секунду
iostat -x 1 /dev/sda
# → Device: r/s w/s rMB/s wMB/s await %util
# → sda     0.0 500.0 0.0  25.0  5.2   85.0

# Трассировка задержек каждого запроса (требует bcc-tools)
sudo biosnoop
# → TIME(s)     COMM           PID    DISK    T  SECTOR    BYTES   LAT(ms)
# → 0.000000    kworker/u16:1  1234   sda     W  1024      4096    0.15

# Низкоуровневый анализ очередей
sudo blktrace -d /dev/sda -o - | blkparse -i -
```

Критический показатель в `iostat`: `await` (среднее время ожидания). Для SSD нормой считается < 1 мс. Значения > 5 мс указывают на деградацию из-за внутренних процессов накопителя.

### Диагностика теплового троттлинга

NVMe-накопители при достижении критической температуры (> 70°C) принудительно снижают скорость для защиты от перегрева.

```bash
# Проверка текущей температуры через smartctl
sudo smartctl -a /dev/nvme0 | grep Temperature
# → Temperature: 45 Celsius

# Просмотр лога предупреждений о перегреве
sudo nvme smart-log /dev/nvme0
```

## Дополнительная информация

### Резервирование области (Over-Provisioning)

Корпоративные (Enterprise) SSD имеют зарезервированную область (7–28% от ёмкости), недоступную пользователю. Увеличение этой области снижает коэффициент усиления записи и даёт больше пространства для эффективной работы Garbage Collection.

### Сравнение типов SSD

| Параметр | Потребительский (Consumer) | Корпоративный (Enterprise) |
| :--- | :--- | :--- |
| **SLC-кэш** | Динамический, большой | Минимальный или отсутствует |
| **Стабильность записи** | Падает при исчерпании кэша | Постоянная высокая скорость |
| **Защита от потери питания** | Обычно отсутствует | Конденсаторы (PLP — Power-loss protection) |
