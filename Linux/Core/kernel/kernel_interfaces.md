# Интерфейсы ядра Linux

## Определения

**Интерфейсы ядра** — это совокупность механизмов, через которые прикладное программное обеспечение (Userspace) взаимодействует с ядром (Kernelspace). Они обеспечивают безопасное выполнение привилегированных операций, управление ресурсами и получение данных о состоянии системы.

В архитектуре Linux интерфейсы являются единственным легитимным способом преодоления границы между уровнями защиты (Ring 3 и Ring 0). Они гарантируют изоляцию процессов за счет строгой валидации всех входящих запросов.

## Основные концепции

### Системные вызовы (System Calls)

Основной программный API ядра. Число системных вызовов в Linux превышает **500**; каждая архитектура (x86_64, ARM64, RISC-V) имеет собственную таблицу вызовов с уникальными номерами. Приложения не вызывают их напрямую — **glibc** (и аналоги: musl, bionic) предоставляет обертки (libc-функции), которые через соглашение о вызовах помещают аргументы в регистры и исполняют инструкцию перехода.

**Механизмы перехода:**
- **`syscall` (x86_64):** Современная быстрая инструкция перехода в режим ядра.
- **`int 0x80` (x86/legacy):** Старый механизм через программное прерывание (медленнее).
- **`sysenter` / `sysexit`:** Оптимизированные инструкции для x86.
- **`svc #0` (ARM64):** Инструкция Supervisor Call для AArch64.

**vDSO (virtual Dynamic Shared Object):** Ядро отображает небольшую библиотеку в память процесса, позволяя выполнять «легкие» вызовы (например, `gettimeofday`, `getrandom` 6.11+) без реального переключения контекста процессора (устраняет накладные расходы на trap).

**Современные вызовы (2024–2026):**
- **`mseal()` (6.10+):** «Запечатывание» областей памяти (защита от изменения прав на mapping после `mprotect`/`mremap`).
- **`futex2` (6.16+):** Улучшенная синхронизация с поддержкой NUMA и сброшенными часами.
- **`pidfd`:** Управление процессами через стабильные файловые дескрипторы вместо переиспользуемых PID.
- **`clone3()` (5.3+):** Современный интерфейс создания процессов/потоков через `struct clone_args`; возвращает `pidfd` при создании процесса.
- **`openat2()` (5.6+):** Расширенный `openat` с `struct open_how` — защита от path traversal (критично для контейнеров и `chroot`).
- **`statx()` (4.11+):** Современная версия `stat`/`fstat` с расширенной метаданной (цифровые подписи, большие временные метки).
- **`getrandom()` (3.17+):** Криптографически безопасный генератор случайных чисел (перехватывает энтропию из HW RNG и драйверов).

**Фильтрация системных вызовов (seccomp):**
- Ядро поддерживает **seccomp-bpf** (режим `filter`, Mode 2): процесс может установить BPF-фильтр, который будет проверяться при каждом системном вызове. Это основа для снижения поверхности атаки. Подробности: [**Seccomp**](../../Security/Mechanisms/Seccomp.md).
- Проверка статуса: `grep Seccomp /proc/<PID>/status` → `0` (off), `1` (strict), `2` (filter).

**Таблица системных вызовов:**
- На x86_64: `/usr/include/x86_64-linux-gnu/asm/unistd_64.h` или `ausyscall --dump`
- Просмотр вызовов конкретного процесса: `strace -c` (сводка по количеству), `perf trace`

### Виртуальные файловые системы (VFS)

Ядро экспортирует свои структуры данных через файлы («все есть файл»).

- **procfs (`/proc`):** Информация о процессах, памяти и системных метриках. См. [**procfs**](../../FileSystems/virtual_fs_proc.md).
- **sysfs (`/sys`):** Структурированная объектная модель устройств, драйверов и модулей. См. [**sysfs**](../../FileSystems/virtual_fs_sys.md).
- **debugfs / tracefs:** Специализированные интерфейсы для глубокой отладки и трассировки (ftrace).
- **configfs:** Позволяет пользователю динамически создавать и настраивать объекты ядра из Userspace.

### Специализированные интерфейсы

- **Netlink:** Сокетный протокол (`AF_NETLINK`) для двустороннего обмена (ядро ↔ пользователи).
  - `NETLINK_ROUTE`: Настройка сети (маршруты, адреса).
  - `NETLINK_AUDIT`: Получение событий безопасности.
  - `NETLINK_GENERIC`: Пользовательские семейства сообщений.
  - `NETLINK_CONNECTOR`: Уведомления о событиях ядра (热插拔, задачи).
  - `NETLINK_KOBJECT_UEVENT`: Уведомления `udev` о подключении/отключении устройств.
- **ioctl (Input/Output Control):** Универсальный интерфейс для команд драйверам, которые не вписываются в модель read/write (например, извлечение лотка CD-ROM или настройка RAID).
- **io_uring:** Высокопроизводительный асинхронный интерфейс обмена через разделяемые кольцевые буферы. См. [**io_uring**](./io_uring.md).
- **eBPF:** Программируемость ядра через загрузку байт-кода в точки трассировки и сетевые хуки. См. [**eBPF**](./ebpf.md).

### Механизм ptrace

**ptrace (Process Trace)** — системный вызов для отладки и наблюдения за процессами. Позволяет:
- Останавливать и возобновлять выполнение целевого процесса.
- Читать/писать его память и регистры.
- Перехватывать системные вызовы (на входе и выходе) и сигналы.
- Устанавливать точки останова (через замену инструкций на `int3`).

ptrace — фундамент для `strace`, `gdb`, `ltrace` и большинства системных утилит диагностики. Механизм требует `CAP_SYS_PTRACE` или соответствия правилу Yama (`ptrace_scope`). Подробности: [**Трассировка и отладка**](../../Diagnostics/Troubleshooting/tracing_and_debugging.md).

### Интерфейс prctl (Process Control)

**prctl (Process Control)** — системный вызов для изменения свойств процessa в реальном времени:
- `PR_SET_NAME` / `PR_GET_NAME`: изменение имени процесса (отображается в `ps`).
- `PR_SET_DUMPABLE`: управление доступом к coredump.
- `PR_SET_SECCOMP`: включение seccomp-режима.
- `PR_SET_NO_NEW_PRIVS`: предотвращение получения новых привилегий через `execve()`.
- `PR_SET_PTRACER`: разрешение ptrace для конкретного PID.
- `PR_SET_CHILD_SUBREAPER`: назначение процесса как "суб-рипера" для перехвата потомков.
- `PR_SET_TIMERSLACK`: настройка задержки пробуждения для энергоэффективности.

```c
#include <sys/prctl.h>
prctl(PR_SET_NAME, "my-worker", 0, 0, 0);
```

### Механизм синхронизации: futex и futex2

**futex (Fast Userspace Mutex)** — механизм синхронизации в ядре, который позволяет реализовывать примитивы блокировок (mutex, semaphore, rwlock) в userspace с минимальными syscall, только когда блокировка действительно нуждается в блокировании.

- **futex (Linux 2.6+):** Классический механизм.
- **futex2 (6.16+):** Современная версия с поддержкой NUMA-узлов, сброшенных часов и улучшенной семантикой.

futex — основа для `pthread_mutex`, `pthread_cond`, `sem_*`, а также для `io_uring` и большинства внутренних механизмов ядра. Подробности: [**Механизмы синхронизации**](./kernel_synchronization.md).

### Интерфейсы управления сигналами

Сигналы — механизм асинхронных уведомлений процессов:
- **`kill(pid, sig)` / `tkill(tid, sig)` / `tgkill(tgid, tid, sig)`:** Отправка сигнала процессу/потоку.
- **`pidfd_send_signal(pidfd, sig, ...)` (5.3+):** Безопасная отправка сигнала через `pidfd` (устраняет race condition при переиспользовании PID).
- **`sigaction()`:** Установка обработчиков сигналов с тонкой настройкой (маски, флаги `SA_RESTART`).
- **`signalfd()`:** Превращение сигналов в файловые дескрипторы (удобно для `epoll`/`io_uring`).

Подробности: [**Сигналы процессов**](../processes/signals.md).

### Интерфейсы управления памятью

Syscalls для работы с виртуальной памятью:
- **`mmap()` / `munmap()`:** Выделение и освобождение виртуальных страниц.
- **`mprotect()`:** Изменение прав доступа к страницам (R/W/X).
- **`mremap()`:** Расширение/сжатие и перенос существующего mapping.
- **`madvise()`:** Подача рекомендаций ядру о характере использования памяти (`MADV_HUGEPAGE`, `MADV_DONTNEED`, `MADV_POPULATE_WRITE`).
- **`msync()`:** Синхронная запись изменений в файл (для `mmap`-нутых файлов).

**Современные вызовы:**
- **`mseal()` (6.10+):** «Запечатывание» mapping — предотвращает последующие `mprotect`/`mremap`/`munmap`, что защищает от некоторых exploit-ов типа GOT overwrite.
- **`map_shadow()` (5.14+):** Выделение страниц, немедленно заполненных нулями (для JIT-компиляторов).

### Интерфейсы таймеров и времени

- **`timerfd_create()` / `timerfd_settime()`:** Создание таймеров как файловых дескрипторов (совместимо с `epoll`/`io_uring`/`poll`).
- **`clock_nanosleep()`:** Современный `nanosleep` с поддержкой часов (`CLOCK_MONOTONIC`, `CLOCK_REALTIME`, `CLOCK_TAI`).
- **`timer_create()` / `timer_settime()`:** POSIX-таймеры с доставкой сигнала или потока уведомления.
- **`clock_gettime()`:** Точное чтение времени (часто через vDSO без реального перехода в Ring 0).

### Интерфейсы межпроцессного взаимодействия (IPC)

- **Shared Memory:** `shmget`/`shmat` (SysV) или `mmap(MAP_SHARED, MAP_ANONYMOUS)`.
- **Message Queues:** `msgget`/`msgsnd`/`msgrcv` (SysV) или `mq_open`/`mq_send`/`mq_receive` (POSIX).
- **Semaphores:** `semget`/`semop` (SysV) или `sem_open`/`sem_wait` (POSIX).
- **Pipes/FIFOs:** `pipe2()`, `mkfifo()`.
- **Unix Domain Sockets:** `socket(AF_UNIX, ...)` — высокоскоростной IPC на основе ФС.

Подробности: [**IPC**](../processes/ipc.md).

### Фильтры и ограничения доступа

Современные интерфейсы для снижения поверхности атаки:
- **Seccomp (BPF):** Фильтрация системных вызовов. Подробности: [**Seccomp**](../../Security/Mechanisms/Seccomp.md).
- **Landlock:** Песочница на уровне ФС и сети. Подробности: [**Landlock**](../../Security/Mechanisms/Landlock.md).
- **Capabilities:** Гранулярные привилегии вместо root. Подробности: [**Capabilities**](../../Security/Mechanisms/Capabilities.md).

## Практические сценарии

### 1. Анализ взаимодействия через strace

```bash
# Трассировка с измерением времени выполнения syscall
strace -T -e openat,read ls /tmp
# → openat(..., "/tmp", ...) = 3 <0.000042>

# Проверка использования vDSO (syscalls не будут видны в strace)
# Пример: gettimeofday обычно выполняется через vDSO
```

**Механизм работы:** `strace` использует `ptrace` для остановки процесса при входе/выходе из каждого syscall. Это вносит значительные задержки, поэтому для production-сред лучше использовать eBPF. Подробности: [**Трассировка и отладка**](../../Diagnostics/Troubleshooting/tracing_and_debugging.md).

### 2. Мониторинг Netlink через ss

```bash
# Просмотр открытых сокетов Netlink
ss -an --netlink
# → Netlink  0  0  16 (NETLINK_AUDIT)  0  ...
```

### 3. Безопасность и фильтрация

Для снижения поверхности атаки на ядро используются фильтры:
- **Seccomp (bpf):** Белый/черный список разрешенных syscall для процесса. См. [**Seccomp**](../../Security/Mechanisms/Seccomp.md).
- **Landlock:** Песочница на уровне ядра для ограничения доступа к ФС и сети. См. [**Landlock**](../../Security/Mechanisms/Landlock.md).
- **BPF Tokens (6.9+):** Делегирование прав на использование eBPF в контейнерах.

### 4. Проверка статуса seccomp и capabilities процесса

```bash
# Проверка режима seccomp для процесса
grep -E "Seccomp|NoNewPrivs" /proc/123/status
# → Seccomp: 2 (Filter)
# → NoNewPrivs: 1

# Проверка effective capabilities (маска CapEff в hex)
grep Cap /proc/123/status
# → CapInh:	0000000000000000
# → CapPrm:	00000000a80425fb
# → CapEff:	00000000a80425fb
# → CapBnd:	00000000a80425fb

# Декодирование маски через capsh
capsh --decode=00000000a80425fb
```

**Диагностика:** Если `Seccomp: 0`, процесс не защищен seccomp. Если `CapEff` содержит `CAP_SYS_ADMIN`, процесс имеет широкие привилегии. Сравнение масок через XOR:
```bash
printf '%x\n' $((0xa80425fb ^ 0xa80425f9)) | xargs capsh --decode
# → 0x0000000000000002=cap_dac_override
```

### 5. Мониторинг файловых дескрипторов

```bash
# Подсчёт открытых дескрипторов процесса
ls /proc/<PID>/fd | wc -l

# Проверка лимита дескрипторов
cat /proc/<PID>/limits | grep "Max open files"

# Просмотр типов дескрипторов (обычные файлы, сокеты, pipe, io_uring)
ls -la /proc/<PID>/fd
```

### 6. Проверка поддержки интерфейсов ядра

```bash
# Проверка поддержки ключевых интерфейсов в текущем ядре
grep -E "CONFIG_EPOLL|CONFIG_IO_URING|CONFIG_BPF|CONFIG_SECURITY_YAMA|CONFIG_FUTEX|CONFIG_PID_NS|CONFIG_NETLINK|CONFIG_PROC_FS|CONFIG_SYS_FS" /boot/config-$(uname -r)

# Проверка наличия io_uring
grep CONFIG_IO_URING /boot/config-$(uname -r)
# → CONFIG_IO_URING=y

# Проверка наличия eBPF и JIT
lsmod | grep -E 'bpf|jit'
```

### 7. Мониторинг активности системных вызовов

```bash
# Сводка по количеству системных вызовов (perf)
sudo perf trace -a -c
# → Общее количество вызовов по типам

# Подсчёт syscall по процессам через eBPF (без остановки процесса)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'

# Мониторинг в реальном времени через perf
sudo perf stat -e syscalls:sys_enter,syscalls:sys_exit -a sleep 5
```

### 8. Проверка использования vDSO

```bash

# Просмотр используемых виртуальных библиотек (включая vdso/vsyscall)
ldd /bin/ls | grep -E "vdso|vsyscall"
# → linux-vdso.so.1 (0x...)

# Проверка доступных функций vDSO
cat /proc/self/maps | grep vdso
# → 7ffc...:7ffc... vdso ...
```

**Интерпретация:** Если `gettimeofday` не появляется в `strace`, значит он выполняется через vDSO (без перехода в Ring 0). Это нормальное поведение для современных glibc.

### 9. Управление процессами через pidfd

```bash

# Просмотр pidfd-дескрипторов процесса
ls -la /proc/<PID>/fd | grep pidfd

# Отправка сигнала через pidfd (теоретически, через специализированный код)
# Безопаснее классического kill, т.к. pidfd привязан к конкретному процессу
```

Для практического использования pidfd в коде: [**pidfd в процессах**](../processes/additional_info.md).

### 10. Мониторинг eBPF программ и карт

```bash
# Список загруженных eBPF-программ
sudo bpftool prog list

# Просмотр содержимого eBPF-карты
sudo bpftool map dump id <map_id>

# Просмотр BTF-данных ядра (необходимо для eBPF CO-RE)
ls -la /sys/kernel/btf/vmlinux

# Проверка ограничений eBPF
sysctl kernel.unprivileged_bpf_disabled
# → 1 (рекомендуется для production)
```

### 11. Аудит загрузки модулей и изменений параметров

```bash

# Просмотр истории загрузки модулей через auditd
ausearch -k modules -i | tail -20
# → type=PROCTITLE ... init_module ...

# Просмотр изменений capability через auditd
grep -i "capability" /var/log/audit/audit.log

# Проверка параметров ядра в реальном времени
watch -n1 'cat /proc/sys/kernel/pid_max /proc/sys/kernel/threads-max'
```

Подробности об аудите: [**auditd**](../../SystemAdministration/Logging/auditd.md).
