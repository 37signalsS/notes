# Зависания ядра: Soft Lockup и Hard Lockup

## Определения

**Lockup (зависание)** — это состояние ядра Linux, при котором один или несколько процессоров (CPU) перестают отвечать на запросы системы или планировщика задач в течение длительного времени.

* **Soft Lockup**: Ситуация, когда ядро "зацикливается" в контексте ядра на одном CPU на длительное время (обычно >20 секунд по умолчанию) и не возвращает управление планировщику задач. При этом прерывания (interrupts) всё еще могут обрабатываться.
* **Hard Lockup**: Более тяжелое состояние, когда CPU полностью перестает реагировать на любые события, включая обычные прерывания. Обычно это вызвано бесконечным циклом в коде ядра с отключенными локальными прерываниями.

## Основные концепции

### Механизм Watchdog

Для обнаружения зависаний ядро Linux использует механизмы "сторожевых таймеров" (watchdog):

1. **Soft Lockup Watchdog**:
    * Для каждого CPU создается поток ядра (`watchdog/N`).
    * Этот поток периодически обновляет метку времени (timestamp).
    * Если метка не обновлялась дольше установленного порога (параметр `kernel.watchdog_thresh`), ядро делает вывод о "мягком" зависании.
2. **Hard Lockup (NMI) Watchdog**:
    * Использует неблокируемые прерывания (NMI — Non-Maskable Interrupts).
    * NMI могут прерывать выполнение кода ядра даже при отключенных обычных прерываниях.
    * Если счетчик прерываний для CPU не инкрементируется, NMI-обработчик фиксирует "жесткое" зависание.

### Причины возникновения

* **Ошибки в драйверах**: Бесконечные циклы или слишком длинные критические секции.
* **Взаимоблокировки (Deadlocks)**: Ситуации, когда два или более процесса бесконечно ждут освобождения ресурсов друг другом.
* **Аппаратные сбои**: Неисправность CPU, памяти или перегрев.
* **Чрезмерная нагрузка**: В редких случаях экстремальная нагрузка на прерывания (interrupt storm) может имитировать зависание.

## Практические сценарии

### Диагностика через логи

При обнаружении зависания ядро выводит диагностическую информацию в `dmesg`.

```text
# Пример сообщения о Soft Lockup
watchdog: BUG: soft lockup - CPU#1 stuck for 22s! [myservice:1234]
```

В логе обычно приводится **stack trace** (стек вызовов), указывающий на функцию ядра, в которой произошло зависание. Это ключевая информация для отладки.

```bash
# Поиск сообщений о зависаниях в текущей сессии
dmesg | grep -i lockup

# Поиск в логах предыдущих загрузок
journalctl -k -b -1 | grep -i lockup
```

### Настройка параметров через sysctl

Параметры поведения при зависаниях настраиваются через [sysctl](./sysctl.md):

* **`kernel.watchdog_thresh`**: Порог обнаружения зависания в секундах (по умолчанию 10, что соответствует 20 секундам для soft lockup).
* **`kernel.softlockup_panic`**: Если установлено в `1`, система вызовет [Kernel Panic](./kernel_panic.md) при обнаружении soft lockup. Это полезно для автоматической перезагрузки и сбора дампа (`kdump`).
* **`kernel.nmi_watchdog`**: Включение (`1`) или выключение (`0`) NMI watchdog для поиска hard lockups.

**Пример настройки:**

```bash
# Установить порог обнаружения в 5 секунд
sudo sysctl -w kernel.watchdog_thresh=5

# Включить панику при soft lockup для автоматической перезагрузки
sudo sysctl -w kernel.softlockup_panic=1
```

### Инструменты глубокой диагностики

* **perf**: Позволяет профилировать работу CPU и выявлять функции, потребляющие слишком много времени.
* **ftrace**: Позволяет отслеживать цепочки вызовов функций ядра в реальном времени.
* **crash**: Используется для анализа дампов памяти после [Kernel Panic](./kernel_panic.md), вызванной зависанием.
