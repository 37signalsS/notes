# Зависания ядра: Soft Lockup, Hard Lockup и Hung Task

## Определения

**Lockup (зависание)** — критическое состояние ядра Linux, при котором один или несколько центральных процессоров (CPU) перестают отвечать на запросы планировщика, прерывания или системные события в течение длительного времени.

- **Soft Lockup**: Состояние, при котором CPU зацикливается в контексте ядра (например, в бесконечном цикле) и не возвращает управление планировщику. При этом аппаратные прерывания (interrupts) продолжают обрабатываться.
- **Hard Lockup**: Состояние, при котором CPU полностью перестает реагировать на любые события, включая обычные прерывания. Обычно вызвано бесконечным циклом в критической секции с отключенными локальными прерываниями.
- **Hung Task**: Состояние отдельного процесса (task), который находится в состоянии «беспрерывного сна» (Uninterruptible Sleep, состояние `D`) дольше установленного порога (обычно 120 секунд). Часто указывает на проблемы с вводом-выводом (I/O) или блокировками файловой системы.

## Основные концепции

### Сторожевые таймеры (Watchdog)

Для автоматического обнаружения зависаний ядро использует механизмы Watchdog:

| Тип детектора | Механизм | Условие срабатывания |
| :--- | :--- | :--- |
| **Soft Lockup** | Высокоприоритетный поток `watchdog/N` | Метка времени потока не обновлялась более `2 × watchdog_thresh`. |
| **Hard Lockup (NMI)** | Немаскируемые прерывания (NMI) | Счётчик прерываний CPU не инкрементировался в течение `watchdog_thresh`. |
| **Buddy Detector** | Процессоры следят друг за другом (ядро 6.5+) | CPU «напарник» обнаруживает отсутствие прогресса у соседа (актуально для VM). |
| **Hung Task** | Периодический мониторинг очереди задач | Процесс находится в состоянии `D` дольше `hung_task_timeout_secs`. |

### RCU CPU Stall Detector

Механизм **RCU Stall** отслеживает ситуации, когда подсистема Read-Copy Update (RCU) не может завершить «льготный период» (grace period). Это часто является предвестником или формой зависания, вызванной длительным удержанием ресурсов в секциях RCU.

### Причины возникновения

1.  **Ошибки в драйверах**: Бесконечные циклы или слишком длительное выполнение в контексте прерывания.
2.  **Взаимоблокировки (Deadlocks)**: Ошибки синхронизации, когда потоки бесконечно ждут освобождения ресурсов друг друга.
3.  **Высокая нагрузка на I/O**: Приводит к массовому появлению Hung Tasks.
4.  **Виртуализация**: Задержки со стороны гипервизора (Steal Time) могут имитировать зависания для гостевой ОС.

## Практические сценарии

### Анализ системных журналов

При обнаружении зависания ядро выводит подробный отчет (Stack Trace) в `dmesg`.

**Пример Soft Lockup:**
`watchdog: BUG: soft lockup - CPU#1 stuck for 22s! [myservice:1234]`

**Пример Hung Task:**
`INFO: task myservice:1234 blocked for more than 120 seconds.`

```bash
# Поиск зависаний в текущем логе
dmesg -T | grep -iE "lockup|hung|stall"

# Анализ логов предыдущей загрузки (если включен persistent journal)
journalctl -k -b -1 | grep -iE "lockup|hung|stall"
```

### Настройка параметров через sysctl

Управление детекторами осуществляется через [**sysctl**](./sysctl.md).

| Параметр | Рекомендуемое значение | Описание |
| :--- | :--- | :--- |
| `kernel.watchdog_thresh` | `10` | Базовый порог обнаружения (в секундах). |
| `kernel.softlockup_panic` | `1` | Вызывать Kernel Panic при обнаружении Soft Lockup. |
| `kernel.hardlockup_panic` | `1` | Вызывать Kernel Panic при обнаружении Hard Lockup. |
| `kernel.hung_task_timeout_secs` | `120` | Таймаут для обнаружения Hung Tasks (0 — отключить). |
| `kernel.hung_task_panic` | `0` | Вызывать панику при Hung Task (обычно не рекомендуется). |
| `kernel.hung_task_all_cpu_backtrace` | `1` | Выводить стек всех CPU при обнаружении Hung Task. |

```bash
# Включение паники при зависании для автоматической перезагрузки (HA-кластеры)
sudo sysctl -w kernel.softlockup_panic=1
sudo sysctl -w kernel.hardlockup_panic=1
```

### Специфика облачных сред и виртуализации

В виртуальных машинах аппаратные NMI часто недоступны. В современных ядрах (6.5+) рекомендуется использовать **Buddy Hardlockup Detector**:
- Убедитесь, что в конфигурации ядра включено `CONFIG_HARDLOCKUP_DETECTOR_BUDDY`.
- При высоких значениях Steal Time порог `watchdog_thresh` следует увеличить (например, до `20`), чтобы избежать ложных срабатываний из-за оверселлинга ресурсов гипервизором.

### Глубокая отладка

Если зависание воспроизводится, используйте следующие инструменты:
1.  **`perf`**: Для идентификации функций ядра, потребляющих больше всего времени.
2.  **`ftrace`**: Для трассировки конкретных функций и путей выполнения.
3.  **`crash`**: Для анализа дампа памяти `vmcore` после срабатывания Kernel Panic.
