# Вытесняющая многозадачность ядра (Kernel Preemption)

## Определения

**Вытесняющая многозадачность ядра (Kernel Preemption)** — механизм планировщика Linux, позволяющий принудительно прерывать выполнение процесса, даже если он находится в режиме ядра (Kernel Mode), для передачи ресурсов более приоритетной задаче.

В отличие от кооперативной многозадачности, где процесс должен сам отдать управление (`yield`), вытеснение гарантирует предсказуемое время отклика (latency), что критично для интерактивных систем и реального времени (RT).

**Ключевые термины:**
- **Preemption Point:** Точка в коде ядра, где планировщик может безопасно переключить контекст.
- **Preempt Count:** Счетчик внутри структуры процесса (`thread_info`), указывающий, находится ли процесс в критической секции, где вытеснение запрещено.
- **Context Switch:** Процесс сохранения состояния текущей задачи (`switch_mm`, `switch_to`) и восстановления состояния новой.
- **Preempt Disable:** Региональный запрет вытеснения (например, `preempt_disable()`), используемый вокруг коротких критических секций.
- **CONFIG_PREEMPT:** Параметр сборки ядра, определяющий, включена ли вообще поддержка вытеснения в режиме ядра.

## Архитектура и модели (Состояние на 2026 год)

### Preempt Count: что именно запрещает вытеснение

В современных ядрах счетчик вытеснения (`preempt_count`) представляет собой битовую маску, где каждый бит соответствует определенному типу блокировки:

- **Бит 0 (`PREEMPT_NEED_RESCHED`):** Устанавливается планировщиком при появлении более приоритетной задачи.
- **Бит 1 (`PREEMPT_DISABLED`):** Устанавливается макросом `preempt_disable()` / `preempt_enable()`.
- **Бит 2 (`HARDIRQ_OFFSET`):** Устанавливается при входе в аппаратный обработчик прерывания (`local_irq_disable`).
- **Бит 3 (`SOFTIRQ_OFFSET`):** Устанавливается при обработке SoftIRQ (`local_bh_disable`).
- **Биты 4+:** Используются для блокировок (`spinlock` добавляет `PREEMPT_LOCKED_OFFSET`, в PREEMPT_RT — `PREEMPT_RT_LOCKED_OFFSET`).

Вытеснение возможно только тогда, когда `preempt_count == 0` и флаг `TIF_NEED_RESCHED` установлен.

### PREEMPT_DYNAMIC: переключение моделей на лету

Механизм **PREEMPT_DYNAMIC** (ядро 5.x+) позволяет менять модель вытеснения без перекомпиляции ядра, используя **Static Keys (Jump Labels)**. Каждая потенциальная точка вытеснения в коде ядра компилируется с проверкой динамического флага; при переключении модели ядро корректирует адреса переходов, не перезагружаясь.

### Модели вытеснения

| Модель | Параметр | Описание | Применение |
| :--- | :--- | :--- | :--- |
| **No Preemption** | `none` | Вытеснение только при выходе из ядра или добровольно. Максимальная пропускная способность. | Серверы с упором на Raw Throughput. |
| **Voluntary** | `voluntary` | Использование явных точек `cond_resched()`. Баланс. | Универсальные серверные нагрузки. |
| **Full** | `full` | Вытеснение в любой точке, кроме критических секций (удержание spinlock, irq disabled). | Десктопы, низкая задержка. |
| **Lazy** | `lazy` | **Стандарт 2026 (6.13+).** Откладывает вытеснение обычных задач до безопасных точек, но сохраняет мгновенное для RT. | Оптимальный баланс (Default). |
| **Real-Time** | `rt` | Полное вытеснение (Mainline с 6.12). Превращает spinlocks в спящие mutex. | Системы жесткого реального времени. |

### PREEMPT_RT: ядро реального времени

Слияние патчей PREEMPT_RT в mainline (ядро 6.12+) изменило архитектуру:
- **Sleeping Spinlocks:** Обычные `spinlock_t` теперь могут усыплять процесс (превращаясь в адаптивные мьютексы). Для кода, который **категорически** не может спать, используются `raw_spinlock_t`.
- **Наследование приоритетов (PI):** Решает проблему инверсии приоритетов, когда низкоприоритетный поток удерживает замок, нужный высокоприоритетному.
- **Threaded IRQs:** Все обработчики прерываний по умолчанию выполняются в контексте процесса, что позволяет планировщику балансировать их как обычные задачи.
- **High-Resolution Timers (HRTIMER):** Гарантируют точность пробуждения задач на уровне микросекунд.

### Планировщик EEVDF (Earliest Eligible Virtual Deadline First)

Пришедший на смену CFS (ядро 6.12+), EEVDF изменил логику вытеснения:
- **Eligible Time (Время готовности):** Момент, когда задача теоретически должна получить доступ к CPU с учетом её `nice` и веса.
- **Virtual Deadline (Виртуальный дедлайн):** Срок, к которому задача должна завершить очередной квант. В отличие от CFS, где вытеснение происходит по накопленному `vruntime`, EEVDF вытесняет текущую задачу, когда у претендента дедлайн наступает раньше, а текущая задача уже «вычерпала» свою порцию времени.
- **Time Slice Request:** Приложения могут запрашивать кванты времени через `sched_setattr()`, влияя на частоту вытеснения без изменения `nice`.

### Механизм Proxy Execution

Для решения проблемы **инверсии приоритетов** активно внедряется Proxy Execution (ядро 6.14+):
- Если высокоприоритетная задача блокируется на ресурсе, удерживаемом низкоприоритетной задачей, она «одалживает» свой контекст выполнения держателю ресурса.
- Это позволяет низкоприоритетной задаче быстрее завершить критическую секцию под приоритетом (дедлайном) заблокированной задачи, минимизируя задержки вытеснения.

## Взаимодействие с подсистемами

### Вытеснение и прерывания (IRQ)

- В моделях `full` и `rt` обработка прерываний (Top Half) может быть вытеснена, если используется **Threaded IRQ** (`threadirqs`). Без этого параметра аппаратные обработчики остаются атомарными и невытесняемыми.
- См. подробности: [Обработка прерываний в ядре Linux](./interrupts.md).

### Вытеснение и синхронизация

- **Spinlock:** В моделях `none`/`voluntary` удержание spinlock запрещает вытеснение на текущем CPU (чтобы держатель не был прерван). В модели `rt` spinlock становится адаптивным mutex, который может уснуть.
- **RCU:** `rcu_read_lock()` запрещает вытеснение и отложенные вызовы (preempt + softirq), гарантируя, что читатель не будет прерван на период Grace Period.
- См. подробности: [Механизмы синхронизации в ядре](./kernel_synchronization.md).

### Вытеснение и изоляция CPU

- Параметр загрузки `isolcpus` исключает ядра из общего планировщика. На изолированных ядрах вытеснение происходит только для RT-задач, привязанных к этим ядрам явно.
- Параметр `nohz_full` отключает системный тик (tickless) на указанных ядрах, снижая фоновый шум и делая преемпцию более предсказуемой.
- См. подробности: [Изоляция CPU](./cpu_isolation.md).

## Практические сценарии

### Определение активной модели и параметров загрузки

```bash
# 1. Проверка модели через dmesg
dmesg | grep -i preempt
# → [    0.000000] Dynamic Preempt: lazy

# 2. Просмотр доступных моделей (требуется debugfs)
cat /sys/kernel/debug/sched/preempt
# → none voluntary full lazy (rt)

# 3. Проверка, поддерживает ли ядро PREEMPT_DYNAMIC
grep CONFIG_PREEMPT_DYNAMIC /boot/config-$(uname -r)
# → CONFIG_PREEMPT_DYNAMIC=y

# 4. Параметры загрузки (GRUB)
cat /proc/cmdline | grep -oE 'preempt=[^ ]+'
# → preempt=lazy
```

### Динамическая настройка (Runtime)

Если модель не заблокирована на этапе сборки, её можно изменить на лету:

```bash
# Переключение в режим полной вытесняемости для минимизации задержек
echo full | sudo tee /sys/kernel/debug/sched/preempt
# → full

# Возврат к стандартной модели
echo lazy | sudo tee /sys/kernel/debug/sched/preempt
# → lazy

# Применение параметра GRUB на постоянной основе
sudo sed -i 's/GRUB_CMDLINE_LINUX_DEFAULT="/GRUB_CMDLINE_LINUX_DEFAULT="preempt=full /' /etc/default/grub
sudo update-grub
```

### Диагностика задержек (Jitter) и сравнение моделей

Пакет `rt-tests` позволяет измерить влияние модели преемпции на latency:

```bash
 # cyclictest: тест на задержку отклика
# -p 95: приоритет RT, -m: закрепить в памяти, -n: clock_nanosleep
# -l 100000: количество итераций, -c 0: использовать только ядро 0
sudo cyclictest -p 95 -m -n -l 100000 -c 0

# → T: 0 ( 1234) P:95 I:1000 C:100000 Min:      2 Act:    4 Avg:    5 Max:   12

# Ожидаемые ориентиры для ядер 7.x:
# - none:      Max > 100 мкс (серверная модель)
# - voluntary: Max 20–50 мкс
# - lazy:      Max 10–30 мкс
# - full:       Max 5–15 мкс
# - rt:        Max < 5 мкс (обычно 1–3 мкс)
```

### Взаимодействие с изоляцией CPU

Для максимально стабильной задержки используйте преемпцию в связке с изоляцией. Детальная настройка параметров загрузки, динамическая изоляция через cgroup v2 и сценарии привязки RT-задач описаны в **[Изоляция CPU](./cpu_isolation.md)**.

### Управление приоритетами через chrt

```bash
 # Планировщик SCHED_FIFO (RT, не сбрасывается при явном yield)
sudo chrt -f 50 ./rt_task

# SCHED_RR (RT, кольцевой)
sudo chrt -r 50 ./rt_task

# Проверка политики и приоритета
chrt -p <PID>
# → pid 1234's current scheduling policy: SCHED_FIFO
# → pid 1234's current scheduling priority: 50
```

### Мониторинг вытеснения через eBPF

```bash
 # Подсчет принудительных переключений контекста (involuntary cswch)
sudo bpftrace -e '
kprobe:finish_task_switch
/arg0 != prev_task/
{
  @involuntary[comm] = count();
}
'
```

```bash
 # Отслеживание функций, временно запрещающих вытеснение
sudo bpftrace -e '
kprobe:preempt_count_add
/arg0 > 0/
{
  @preempted[stack] = count();
}
'
```

```bash
 # Анализ задержек планировщика через perf
sudo perf sched record -a -- sleep 5
sudo perf sched latency
# → показывает平均/максимальную задержку между пробуждением задачи и её выполнением
```

### Мониторинг через стандартные утилиты

```bash
 # Контекстные переключения: добровольные vs принудительные
ps -eo pid,comm,cswch,nvcswch | sort -k3 -nr | head

# pidstat -w: переключения контекста в реальном времени
sudo pidstat -w 1

# vmstat 1: system column показывает cswch/s и in (interrupts)
vmstat 1 5
# → procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
# →  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
```

### Диагностика RCU stall из-за вытеснения

При слишком агрессивной модели вытеснения или в PREEMPT_RT могут возникать задержки RCU:

```bash
 # Проверка таймаута RCU stall (по умолчанию 10 секунд для PREEMPT)
dmesg | grep -i "rcu: INFO: rcu_preempt detected stalls"
# → rcu: INFO: rcu_preempt detected stalls on CPUs/tasks: 2-3

# Увеличение таймаута для отладки (временно)
echo 30 > /sys/module/rcutree/parameters/rcu_cpu_stall_timeout

# Постоянно через GRUB
GRUB_CMDLINE_LINUX_DEFAULT="... rcu_cpu_stall_timeout=30"
```

### Troubleshooting: распространенные проблемы

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Высокий `cswch/s` (involuntary) | Слишком агрессивная модель `full`/`rt` на高 нагрузке | Переключиться на `lazy` или `voluntary` |
| RCU stall в PREEMPT_RT | Длинные критические секции в драйвере | Поиск через `lockdep` + `ftrace`; откат драйвера |
| Пропускные способность падает при `full` | Частые вытеснения в сетевом стекe (ksoftirqd) | Проверить `irqbalance`, увеличить `net.core.some`; рассмотреть `voluntary` |
| Аудио/джаitter в PREEMPT_RT | Низкий приоритет аудио-потока | Увеличить `chrt` приоритет; проверить `irq` affinity |
| Система зависает при `rt` | Несовместимый драйвер с PREEMPT_RT | Откат до `lazy`; проверить `taint` флаг |

### Recovery: сценарии возврата к стабильной работе

```bash
 # Сценарий 1: Нестабильная работа драйвера после включения PREEMPT_RT
# 1. Откат модели через debugfs
echo lazy | sudo tee /sys/kernel/debug/sched/preempt

# 2. Проверка, что модель переключилась
cat /sys/kernel/debug/sched/preempt
# → lazy

# 3. Если debugfs недоступен (например, ядро без PREEMPT_DYNAMIC):
# Перезагрузка с параметром GRUB
sudo grub-reboot "Linux with preempt=lazy"
sudo reboot
```

```bash
 # Сценарий 2: Высокий cswch/s без видимой нагруженности приложения
# 1. Проверить, какие ядра выполняют переключения
sudo perf sched record -a -- sleep 3
sudo perf sched latency | grep -E "Task|latency"

# 2. Если проблема в ksoftirqd — проверить affinity IRQ
cat /proc/interrupts | grep -i eth0
cat /proc/irq/*/smp_affinity | head
```
