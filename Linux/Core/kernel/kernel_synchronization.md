# Механизмы синхронизации в ядре Linux

## Определения

**Синхронизация в ядре** — это совокупность программных примитивов и архитектурных правил, предназначенных для координации доступа нескольких потоков выполнения (процессов, прерываний, обработчиков eBPF) к разделяемым структурам данных.

**Атомарная операция (Atomic Operation)** — неделимая операция над памятью, которая выполняется целиком без возможности прерывания. Базовый уровень синхронизации без блокировок.

**Барьер памяти (Memory Barrier)** — инструкция процессора или директива компилятора, гарантирующая строгий порядок операций чтения/записи до и после барьера. Необходима из-за внеочередного выполнения инструкций (Out-of-order execution) в современных CPU.

**Состояние гонки (Race Condition)** — аномалия, при которой результат работы зависит от случайного порядка выполнения потоков. В ядре приводит к **Kernel Panic** или повреждению данных.

**Deadlock (Взаимная блокировка)** — состояние, при котором два или более потоков бесконечно ждут освобождения ресурсов, захваченных друг другом. В ядре приводит к зависанию системы (см. [Зависания ядра](./lockups.md)).

## Основные концепции

### Проблема параллелизма

Linux является многопоточным и вытесняемым (Preemptive) ядром. Конфликты возникают при:
1.  **SMP (Symmetric Multiprocessing):** Одновременный доступ с разных ядер CPU.
2.  **Прерывания (IRQ):** Аппаратный обработчик прерывает основной код и обращается к тем же данным.
3.  **Softirqs/Tasklets:** Отложенная обработка прерываний, работающая в атомарном контексте.
4.  **Вытеснение:** Переключение контекста планировщиком внутри критической секции.

### Иерархия примитивов блокировки

| Механизм | Контекст | Поведение | Особенности |
| :--- | :--- | :--- | :--- |
| **Atomic (`atomic_t`)** | Любой | Без блокировки | Только простые типы и операции. |
| **Спинлок (Spinlock)** | Любой | Активное ожидание | Запрещает вытеснение на текущем CPU. |
| **Мьютекс (Mutex)** | Процесс | Сон (Sleep) | Можно удерживать долго. |
| **Семафор (Semaphore)** | Процесс | Сон (Sleep) | Счетчик доступа (N потоков). |
| **RW-Locks** | Любой | Multiple R / Single W | Риск голодания писателя. |
| **Seqlock** | Любой | Fast R / Precise W | Читатель проверяет счетчик версии. |

### Барьеры памяти и атомарность

В SMP-системах запись в память одним ядром может быть видна другому ядру не сразу или в другом порядке.
- `smp_mb()` — полный барьер (чтение + запись).
- `smp_rmb()` — барьер чтения.
- `smp_wmb()` — барьер записи.
- `READ_ONCE()` / `WRITE_ONCE()` — предотвращают оптимизации компилятора, которые могут удалить «лишние» обращения к памяти.
- `barrier()` — чистый барьер компилятора (без аппаратного эффекта); предотвращает перестановку компилятором операций вокруг него.

#### Атомарные переменные (atomic_t)

Атомарные операции реализуются через специальные CPU-инструкции (x86: `LOCK`-префикс, ARM: `LDREX`/`STREX`, RISC-V: `LR`/`SC`). В ядре используются типы `atomic_t` (int), `atomic64_t` (long long) и `atomic_long_t`:

| Оператор | Описание | Использование |
| :--- | :--- | :--- |
| `atomic_set(&v, val)` | Установить значение | Инициализация счетчика |
| `atomic_read(&v)` | Прочитать значение | Проверка состояния |
| `atomic_inc(&v)` / `atomic_dec(&v)` | Инкремент / декремент | Счетчики ссылок (refcount) |
| `atomic_inc_return(&v)` | Инкремент + возврат нового значения | Атомарная проверка на ноль |
| `atomic_dec_and_test(&v)` | Декремент, проверка на ноль | Освобождение ресурса при refcount=0 |
| `atomic_cmpxchg(&v, old, new)` | CAS: если == old, заменить на new | Алгоритмы без блокировок |
| `atomic_xchg(&v, new)` | Атомарная замена и возврат старого значения | Реализация спин-локов |
| `atomic_fetch_add(&v, n)` | Прибавить, вернуть старое значение | Счетчики в RCU |
| `atomic_or`/`atomic_and` | Побитовые операции | Флаги состояния |

Эти операции лежат в основе всех остальных примитивов синхронизации. Подробнее о userspace-атомарных операциях и futex: [Атомарные операции](../../../Concepts/atomic_operations.md) и [Конкурентность в Linux](../processes/concurrency.md).

### Спинлоки (Spinlocks)

Спинлок — это блокировка, при которой поток активно ожидает (крутится в цикле), не переводясь в сон. Используется в критических секциях, где сон недопустим (например, в обработчиках прерываний).

**Варианты спинлоков:**
- `spinlock_t` — стандартный спинлок. В PREEMPT_RT может усыпать (становится адаптивным mutex).
- `raw_spinlock_t` — спинлок, который **никогда** не усыпает. Используется в самых критических участках (например, для защиты структур RCU, NMI-обработчиков).
- `spin_lock_irqsave()` — захват спинлока с отключением прерываний на текущем CPU. Сохраняет флаг IRQ в переменную (восстанавливается через `spin_unlock_irqrestore()`).
- `spin_lock_bh()` — захват с отключением SoftIRQ (нижних половин), но без отключения Hard IRQ.
- Вложенные спинлоки (nested locking): `spin_lock_nested(&lock, subclass)`.

**Ticket spinlock:** в архитектурах x86 и ARM64 используется алгоритм "билетной" блокировки, где каждый поток получает номер билета, гарантируя честный доступ (FIFO-порядок) без голодания.

### Мьютексы (Mutex)

Мьютекс — блокировка, при которой поток переводится в сон при конкуренции. Используется для защиты критических секций, которые могут длиться достаточно долго (I/O, аллокация памяти).

| Функция | Описание |
| :--- | :--- |
| `mutex_lock(&m)` | Захватить мьютекс (сон при конкуренции) |
| `mutex_trylock(&m)` | Попытка захвата без сна (возвращает 0/1) |
| `mutex_unlock(&m)` | Освободить мьютекс |
| `mutex_lock_interruptible(&m)` | Захват, прерываемый сигналами (возвращает -EINTR) |

**Priority Inheritance (PI) Mutex:** решает проблему инверсии приоритетов. Если высокоприоритетный поток ждёт мьютекс, удерживаемый низкоприоритетным, ядро временно повышает приоритет держателя до уровня ждущего. Это реализуется на уровне планировщика через механизм дерева зависимостей (`pi_tree`).

**WW-Mutex (Wait/Wound):** используется в драйверах DRM/GPU для предотвращения дедлоков при захвате нескольких буферов. Алгоритм: первый поток (wounded) «поранен», второй (waiting) ждет; если wounded-поток пытается захватить занятый лок, он получает `-EDEADLK` и должен откатиться.

### RW-Locks (Read-Write Locks) и Semaphores

**RW-spinlock (`rwlock_t`):** позволяет нескольким читателям одновременно, но только одному писателю. Читатели не блокируют друг друга; писатель блокирует всех. Риск голодания писателя при постоянном потоке читателей решается через «non-greedy» режим.

**RWSem (`struct rw_semaphore`):** более тяжелая версия RW-lock, которая **может усыпать** (контекст процесса). Используется в VFS для защиты inode/dentry. Имеет оптимизацию «handoff», при котором владелец передаёт блокировку следующему в очереди, избегая потери производительности на арбитраж.

### Seqlock (Sequence Locks)

Seqlock — это блокировка для данных с частым чтением и редким изменением. Читатель не блокируется и не спит, а вместо этого проверяет «счётчик версии» до и после чтения. Если счётчик изменился (запись вставилась посередине), читатель повторяет операцию.

- `seqlock_t` / `seqcount_t` — основной тип.
- `write_seqlock(&s)` / `write_sequnlock(&s)` — захват/освобождение для писателя (эксклюзивно).
- `read_seqbegin(&s)` — начало чтения (получить номер версии).
- `read_seqretry(&s, seq)` — конец чтения: если версия изменилась, повторить.

Часто используется в ядре для защиты статистики (например, выделенная память, статистика сетевых интерфейсов).

### Семафоры (Kernel Semaphores)

`struct semaphore` — счётчик доступа с блокировкой. `down(&sem)` уменьшает счётчик (спит, если он стал отрицательным), `up(&sem)` увеличивает. Используется для ограничения количества потоков, одновременно использующих ресурс.

### Completion

**Completion** — примитив для ожидания завершения однократного события:
- `init_completion(&c)` — инициализация.
- `wait_for_completion(&c)` — ожидание.
- `complete(&c)` / `complete_all(&c)` — сигнал завершения.

Широко используется в драйверах для ожидания асинхронных операций (DMA, USB-транзакции).

### Local Locks

**Local locks (`local_lock_t`):** защита данных, локальных для конкретного CPU. `local_lock(&ll)` не блокирует другие CPU, а только гарантирует, что текущее CPU не будет вытеснено и не переключит контекст на другую задачу. Используется для защиты per-CPU структур данных. Стоимость почти нулевая (в основном — это `preempt_disable()`).

### Futex (Fast Userspace Mutex)

**Futex** — механизм синхронизации в ядре, который позволяет реализовывать примитивы блокировок (mutex, semaphore, rwlock) в userspace с минимальными переходами в ядро. Основной принцип:

1.  **Fast path (Userspace):** Поток пытается изменить значение futex-слова. Если это удалось (значение изменилось с ожидаемого), захват завершён в userspace. Перехода в ядро нет.
2.  **Slow path (Kernel):** Если значение занято (конкуренция), поток вызывает `SYS_futex` с `FUTEX_WAIT`, который проверяет значение и, если оно всё ещё занято, переводит поток в сон на очередь ожидания futex.

| Команда | Описание |
| :--- | :--- |
| `FUTEX_WAIT` | Если `*uaddr == val`, спать до `FUTEX_WAKE` |
| `FUTEX_WAKE` | Разбудить до `nr_wake` спящих потоков |
| `FUTEX_REQUEUE` | Переместить ждущие из одной очереди в другую |
| `FUTEX_CMP_REQUEUE` | Requeue с проверкой значения (для robust futex) |
| `FUTEX_WAIT_REQUEUE_PI` | PI-aware очередь (Priority Inheritance) |
| `FUTEX_LOCK_PI` / `FUTEX_UNLOCK_PI` | Захват/освобождение PI futex |

**Priority Inheritance Futex (PI futex):** используется pthread_mutex_t в пользовательском пространстве для решения инверсии приоритетов. Ядро хранит очередь PI-ожидания и может передавать приоритет держателю.

**Robust Futex:** если поток, удерживающий futex, завершается аварийно, futex автоматически становится доступным (через список `robust_list` в struct task_struct).

Подробнее о userspace-футексах: [Конкурентность и синхронизация процессов](../processes/concurrency.md).

### RCU (Read-Copy-Update)

Механизм для структур с частым чтением и редким изменением (например, таблицы маршрутизации).
- **Читатели:** Используют `rcu_read_lock()` (очень дешево, просто запрещает вытеснение).
- **Писатели:** Создают копию, меняют её и подменяют указатель (`rcu_assign_pointer`).
- **Grace Period (Льготный период):** Время, необходимое для завершения всех активных чтений. Только после этого старая копия удаляется через `synchronize_rcu()` или `call_rcu()`.

## Современная эра (2024–2026)

### Слияние PREEMPT_RT (ядро 6.12+)

Патчи реального времени стали частью основного ядра:
- **Sleeping Spinlocks:** Обычные `spinlock_t` тепеперь могут усыплять процесс (превращаясь в адаптивные мьютексы). Для кода, который **категорически** не может спать, используются `raw_spinlock_t`.
- **Наследование приоритетов (PI):** Решает проблему инверсии приоритетов, когда низкоприоритетный поток удерживает замок, нужный высокоприоритетному.
- **Threaded IRQs:** Все обработчики прерываний по умолчанию выполняются в контексте процесса, что позволяет планировщику балансировать их как обычные задачи.

### Синхронизация в eBPF

Программы eBPF стали полноценными участниками синхронизации:
- **`bpf_spin_lock`**: Защита данных в BPF Maps.
- **BPF Per-CPU Maps:** Использование локальных данных CPU для полной отмены блокировок.
- **Verified Deadlock Prevention:** Верификатор eBPF анализирует граф блокировок и запрещает загрузку кода, который может вызвать дедлок.

### Futex2 (Linux 5.15+)

Новый интерфейс системных вызовов для futex с поддержкой:
- **Векторные операции:** `FUTEX_WAITV` и `FUTEX_WAKE` позволяют атомарно ждать нескольких futex-слов одновременно.
- **Большие варьанты:** поддержка 64-битных, 32-битных и 8-битных futex-слов.
- **PI futex:** поддержка Priority Inheritance в новом API.

Это особенно важно для высокопроизводительных приложений (СУБД, in-memory хранилища), где традиционный futex ограничен одним словом.

## Внутренние механизмы диагностики

### Lockdep (Dependency Validator)

**Lockdep** — подсистема ядра (`CONFIG_PROVE_LOCKING`), которая отслеживает порядок захвата и освобождения всех блокировок во время выполнения. Она строит граф зависимостей и проверяет его на предмет циклов (потенциальных дедлоков).

**Как это работает:**
1.  Каждая блокировка классифицируется по **lock class** (строковый ключ, например, имя структуры + тип).
2.  При захвате Lock A → Lock B система запоминает эту пару.
3.  Если где-то Lock B → Lock A, обнаруживается цикл → **warning в dmesg** даже если дедлок ещё не произошёл.
4.  Lockdep также проверяет: захват того же лока дважды, освобождение не захваченного лока, использование заблокированного лока после `free()`.

**Важно:** Lockdep активируется только в debug-сборках ядра (`CONFIG_LOCKDEP=y`) и добавляет накладные расходы (~5-10% на конкуренцию). В production обычно отключен.

### KCSAN (Kernel Concurrency Sanitizer)

**KCSAN** — динамический анализатор состояний гонки (race condition), аналогичный ThreadSanitizer, но для ядра. Он использует **hardware watchpoints** или **software watchpoints** для отслеживания одновременного доступа нескольких потоков к одной ячейке памяти без синхронизации.

**Как работает:**
1.  Потоки, установившие watchpoint на адрес, «контролируются».
2.  Если другой поток пытается получить доступ к этому адресу без синхронизации — KCSAN регистрирует гонку.
3.  Использует выборочную выборку (sampling) для снижения накладных расходов.

Активируется через параметр загрузки `kcsan` или `CONFIG_KCSAN=y`.

## Практические сценарии

### Алгоритм выбора примитива

1.  Нужно защитить простую переменную (счетчик)? → **Atomic**.
2.  Критическая секция очень короткая и не может спать (в IRQ)? → **Spinlock**.
3.  Секция может длиться долго (I/O, аллокация памяти)? → **Mutex**.
4.  Читателей на порядок больше чем писателей? → **RCU**.
5.  Нужно защитить данные только для текущего CPU? → **local_lock** или **Per-CPU переменные**.

### Мониторинг конкуренции за блокировки

#### /proc/lock_stat

Файл `/proc/lock_stat` предоставляет агрегированную статистику по блокировкам ядра (требует `CONFIG_LOCK_STAT=y`).

```bash
# Просмотр статистики блокировок
sudo cat /proc/lock_stat | head -n 30
# → lock: ffff888123456789  ops: 123456  min: 123  max: 45678  avg: 456  wait_total: 789012  wait_avg: 6
#   contentions: 10
```

**Интерпретация полей:**
- `ops` — общее количество операций с блокировкой.
- `contentions` — количество конкуренций (когда поток пришлось ждать).
- `wait_total` / `wait_avg` — суммарное и среднее время ожидания в наносекундах.
- `min` / `max` / `avg` — время захвата (hold time) в наносекундах.

```bash
# Поиск "горячих" блокировок с наибольшей конкуренцией
sudo awk '/^lock:/ {print $0}' /proc/lock_stat | sort -t= -k6 -n -r | head -n 10
```

#### perf lock

`perf lock` — мощный инструмент для профилирования блокировок на уровне ядра и приложений:

```bash
# Сбор данных о блокировках в течение 30 секунд
sudo perf lock record -a sleep 30

# Отчёт: топ блокировок по времени удержания
sudo perf lock report
# → показывает функции и типы блокировок с самым долгим hold time

# Анализ конкуренции (кто ждал)
sudo perf lock contention
# → выводит гистограмму времени ожидания и топ потоков

# Валидация: проверка на наличие аномалий в lock ordering
sudo perf lock validate
```

#### Мониторинг через eBPF

```bash
# bpftrace: время удержания mutex в ядре
sudo bpftrace -e '
tracepoint:lock:mutex_lock { @start[tid] = nsecs; }
tracepoint:lock:mutex_unlock /@start[tid]/ {
  $us = (nsecs - @start[tid]) / 1000;
  @latency = hist($us);
  delete(@start[tid]);
}'
```

```bash
# bpftrace: время ожидания futex в userspace
sudo bpftrace -e '
uprobe:/lib/x86_64-linux-gnu/libc.so.6:pthread_mutex_lock { @start[tid] = nsecs; }
uretprobe:/lib/x86_64-linux-gnu/libc.so.6:pthread_mutex_lock /@start[tid]/ {
  $wait = (nsecs - @start[tid]) / 1000;
  @futex_wait = hist($wait);
  delete(@start[tid]);
}'
```

#### Отладка Futex

```bash
# strace: отслеживание вызовов futex
strace -e trace=futex -p <PID>
# → futex(0x7f..., FUTEX_WAIT_BITSET_PRIVATE, 0, NULL, ...) = ?

# Проверка заблокированных futex через /proc/PID/wchan
ps -eo pid,comm,wchan:30 | grep -i futex

# Мониторинг очереди ожидания futex через BPF
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_futex { @futex_calls[comm] = count(); }'
```

### Диагностика через Lockdep

Lockdep анализирует иерархию захвата блокировок. Если поток захватывает `Lock A -> Lock B`, а другой `Lock B -> Lock A`, Lockdep выдаст предупреждение **до** того, как случится реальный дедлок.

```bash
# Просмотр графа зависимостей блокировок
sudo cat /proc/lockdep_chains | head

# Статистика конкуренции (конфликтов) за замки
# Помогает найти "горячие" блокировки, тормозящие систему
sudo cat /proc/lock_stat | head -n 15
```

### Отладка состояния гонки

Если система ведет себя нестабильно, используйте **KCSAN** (Kernel Concurrency Sanitizer).

```bash
# Проверка отчетов KCSAN в dmesg
dmesg | grep KCSAN
# → HW breakpoint: read to 0x... by task ...
```

### Настройка и проверка конфигурации ядра

Для активации диагностических подсистем синхронизации необходимо включить соответствующие опции сборки:

```bash
# Проверка текущей конфигурации
grep -E "CONFIG_LOCKDEP|CONFIG_LOCK_STAT|CONFIG_KCSAN|CONFIG_PROVE_LOCKING|CONFIG_DEBUG_LOCK_ALLOC|CONFIG_PROVE_RCU" /boot/config-$(uname -r)
# → CONFIG_LOCK_STAT=y
# → CONFIG_PROVE_LOCKING=y
# → CONFIG_DEBUG_LOCK_ALLOC=y
```

| Параметр | Описание | Накладные расходы |
| :--- | :--- | :--- |
| `CONFIG_LOCKDEP` | Активирует Lockdep и CONFIG_PROVE_LOCKING | 5-10% на конкуренцию |
| `CONFIG_LOCK_STAT` | Сбор статистики через /proc/lock_stat | 3-5% |
| `CONFIG_KCSAN` | Kernel Concurrency Sanitizer (race detection) | 10-30% |
| `CONFIG_DEBUG_LOCK_ALLOC` | Проверка правильного использования lock-примитивов | 2-5% |
| `CONFIG_PROVE_RCU` | Валидация использования RCU | 1-3% |
| `CONFIG_DEBUG_SPINLOCK` | Проверка двойного захвата/освобождения spinlock | 1-2% |

### Устранение проблем с конкуренцией за блокировки

| Симптом | Возможная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Высокий `%sys` в `top` | Интенсивное использование spinlock | `perf lock contention` | Пересмотр алгоритма; использовать RCU или per-CPU данные |
| `perf lock` показывает долгие hold time | Долгая критическая секция в спинлоке | `perf lock report` | Вынести тяжелую работу за пределы спинлока; переключить на mutex |
| Потоки в `D-state` с `wchan=mutex_lock` | Конкуренция за мьютекс | `cat /proc/lock_stat` | Разбить защищенные данные на несколько мьютексов; использовать RCU |
| Futex contention в приложении | Горячий mutex в userspace | `strace -e futex`, `perf lock` | Использовать sharded lock (разделить на N мьютексов по хешу ключа) |
| RCU CPU stall | Длинная критическая секция в RCU reader | `dmesg | grep rcu` | Сократить критическую секцию; использовать `cond_resched_rcu()` |
