# Механизмы синхронизации в ядре Linux

## Определения

**Синхронизация в ядре** — это совокупность программных примитивов и архитектурных правил, предназначенных для координации доступа нескольких потоков выполнения (процессов, прерываний, обработчиков eBPF) к разделяемым структурам данных. Она критически важна для предотвращения повреждения памяти и обеспечения целостности состояния системы.

**Состояние гонки (Race Condition)** — аномалия, при которой результат операции зависит от непредсказуемой последовательности или времени выполнения событий. В ядре это часто приводит к критическим сбоям (**Kernel Panic**) или «тихому» повреждению данных.

## Основные концепции

### Проблема параллелизма

Ядро Linux является многопоточным и вытесняемым (Preemptive). Конфликты доступа возникают в следующих случаях:
1.  **SMP (Symmetric Multiprocessing):** Два процесса на разных ядрах CPU одновременно модифицируют одни и те же данные.
2.  **Прерывания:** Основной код ядра прерывается аппаратным обработчиком (ISR), который обращается к тем же структурам.
3.  **Вытеснение (Preemption):** Планировщик переключает контекст на более приоритетную задачу в середине критической секции.

### Базовые примитивы блокировки

| Механизм | Поведение при занятости | Область применения |
| :--- | :--- | :--- |
| **Мьютекс (Mutex)** | Поток засыпает (sleep) | Длительные операции в контексте процесса. |
| **Спинлок (Spinlock)** | Активное ожидание (busy-wait) | Короткие секции, контекст прерываний. |
| **raw_spinlock_t** | Жесткая блокировка | Критические узлы (планировщик, низкоуровневые IRQ). |
| **local_lock** | Защита per-CPU данных | Замена глобальному отключению прерываний. |

### RCU (Read-Copy-Update)

RCU — это высокопроизводительный механизм, оптимизированный для сценариев «много читателей, мало писателей». Он позволяет читателям обращаться к данным без использования каких-либо блокировок.

*   **Принцип:** Писатель создает копию данных, вносит изменения и атомарно подменяет указатель. Старая версия удаляется только после завершения «льготного периода» (Grace Period), когда все активные читатели гарантированно закончили работу.
*   **Lazy RCU (ядро 6.12+):** Позволяет ядру группировать коллбэки для экономии энергии, что критично для мобильных и встраиваемых систем.
*   **SRCU (Sleepable RCU):** Вариант, в критических секциях которого потокам разрешено засыпать.

## Современная эра (2024–2026)

### Слияние PREEMPT_RT (ядро 6.12+)

Полная интеграция патчей реального времени в основную ветку ядра радикально изменила логику синхронизации:
*   **Sleeping Spinlocks:** В ядрах с включенным RT обычные `spinlock_t` превращаются в «спящие» блокировки (`rt_mutex`). Это позволяет системе оставаться отзывчивой даже при глубокой вложенности блокировок.
*   **Priority Inheritance (PI):** Наследование приоритетов стало стандартным механизмом для предотвращения инверсии приоритетов. Если высокоприоритетный поток ждет блокировку, удерживаемую низкоприоритетным, последний временно получает приоритет ждущего.

### Синхронизация в eBPF

Современные eBPF-программы (2025+) получили доступ к полноценным примитивам:
*   **`bpf_spin_lock`**: Позволяет синхронизировать доступ к элементам BPF Maps.
*   **`rqspinlock` (ядро 6.15+):** Позволяет BPF-программам захватывать несколько блокировок одновременно с автоматической защитой от дедлоков со стороны верификатора.

## Практические сценарии

### Выбор инструмента

При разработке или анализе кода следуйте правилу минимально необходимой блокировки:
1.  **Можно засыпать?** Используйте `mutex`.
2.  **Контекст прерывания?** Только `spinlock` (или `raw_spinlock`, если это код планировщика).
3.  **Данные только для текущего CPU?** Используйте `local_lock`.
4.  **Чтение > 90% времени?** Всегда выбирайте `RCU`.

### Диагностика проблем (Lockdep)

**Lockdep** — это встроенный в ядро валидатор блокировок. Он отслеживает иерархию захвата замков и предупреждает о потенциальных дедлоках до того, как они произойдут.

```bash
# Проверка статистики блокировок (требует CONFIG_LOCK_STAT)
sudo cat /proc/lock_stat | head -n 20

# Поиск сообщений о нарушении иерархии блокировок
dmesg | grep -i "possible recursive locking"
```

### Анализ через системные вызовы (Futex)

Пользовательские блокировки (Mutex в glibc) транслируются в системные вызовы `futex` (Fast Userspace Mutex).
```bash
# Трассировка ожидания блокировок процессом
strace -e futex -p <PID>
# → futex(0x..., FUTEX_WAIT_PRIVATE, 2, NULL) ...
```
