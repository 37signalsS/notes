# Планировщики ввода-вывода (I/O Schedulers)

## Определения

**Планировщик ввода-вывода (I/O Scheduler)** — это компонент подсистемы блочного ввода-вывода ядра Linux, который определяет порядок передачи запросов на чтение и запись физическому накопителю. Основная цель планировщика — минимизация времени поиска (для HDD), предотвращение «голодания» (starvation) запросов и оптимизация пропускной способности (throughput) или задержек (latency).

В современных ядрах (начиная с 5.0+) классические одноочередные планировщики (CFQ, Deadline, NOOP) полностью заменены на многоочередную архитектуру **blk-mq**.

## Основные концепции

### Архитектура Multi-Queue (blk-mq)

Традиционный блочный слой использовал одну общую очередь на всё устройство, что становилось узким местом на многоядерных системах. Архитектура **blk-mq** решает эту проблему, разделяя ввод-вывод на два уровня:
1.  **Программные очереди (Software Queues):** Создаются для каждого ядра CPU. Это минимизирует конкуренцию за блокировки (lock contention).
2.  **Аппаратные очереди (Hardware Queues):** Напрямую сопоставляются с очередями контроллера устройства (например, NVMe поддерживает до 64 000 таких очередей).

### Типы современных планировщиков (2024–2025)

| Планировщик | Сложность | Ключевая особенность | Оптимален для |
| :--- | :--- | :--- | :--- |
| **`none`** | Нулевая | Прямая передача запросов устройству без задержек в ядре. | NVMe, облачные ВМ, SSD (High-end). |
| **`mq-deadline`** | Низкая | Гарантирует максимальное время ожидания для каждого запроса. | SATA SSD, универсальные серверы. |
| **`kyber`** | Средняя | Использует «токены» для ограничения задержек чтения и записи. | NVMe под смешанной нагрузкой. |
| **`bfq`** | Высокая | Предоставляет каждому процессу «бюджет» времени диска. | HDD, десктопы (отзывчивость). |

### Тренды и специфика (2025)

*   **Бутылочное горлышко — CPU:** На сверхбыстрых накопителях (PCIe Gen5) время, затрачиваемое ядром на «умное» планирование, часто превышает время самой физической записи. Поэтому **`none`** стал стандартом де-факто для высокопроизводительных систем.
*   **Виртуализация:** В облачных средах (AWS, GCP, Azure) планирование выполняется гипервизором. Использование любого планировщика внутри гостевой ОС (кроме `none`) приводит к «двойному планированию» и росту задержек.
*   **Проблема Noisy Neighbor:** Планировщик **`kyber`** признан лучшим инструментом для серверов, где фоновые задачи (бэкапы, сборка мусора БД) могут резко увеличивать P99 задержки критических приложений.

## Практические сценарии

### Идентификация и изменение планировщика

```bash
# Просмотр доступных и активного планировщика для устройства nvme0n1
cat /sys/block/nvme0n1/queue/scheduler
# → [none] mq-deadline kyber bfq

# Изменение планировщика «на лету» (без перезагрузки)
echo kyber | sudo tee /sys/block/nvme0n1/queue/scheduler
```

### Автоматизация через правила udev

Для сохранения настроек после перезагрузки рекомендуется использовать правила `udev`. Создайте файл `/etc/udev/rules.d/60-io-schedulers.rules`:

```text
# Для NVMe всегда используем none (максимальная скорость)
ACTION=="add|change", KERNEL=="nvme[0-9]*", ATTR{queue/scheduler}="none"

# Для SATA SSD используем mq-deadline (баланс)
ACTION=="add|change", KERNEL=="sd[a-z]", ATTR{queue/rotational}=="0", ATTR{queue/scheduler}="mq-deadline"

# Для классических HDD используем bfq (устранение фризов)
ACTION=="add|change", KERNEL=="sd[a-z]", ATTR{queue/rotational}=="1", ATTR{queue/scheduler}="bfq"
```

После создания файла примените правила:
```bash
sudo udevadm control --reload-rules && sudo udevadm trigger
```

### Рекомендации по выбору

1.  **Базы данных на NVMe:** Используйте `none`. Оверхед планировщика снижает IOPS.
2.  **Облачные инстансы:** Всегда `none`.
3.  **Файловые серверы (HDD):** Только `bfq`. Он эффективно группирует запросы, минимизируя перемещение головок диска.
4.  **SATA SSD (Legacy):** `mq-deadline`.
