# Паника ядра (Kernel Panic)

## Определения

**Kernel Panic** — критическое состояние, при котором ядро обнаруживает неустранимую ошибку и прекращает работу. Это защитный механизм, предотвращающий повреждение данных на дисках при потере целостности самого ядра.

**Kernel Oops** — серьезная, но потенциально нефатальная ошибка. Ядро пытается продолжить работу, "убив" вызвавший ошибку процесс. Однако после Oops состояние ядра считается нестабильным (Tainted).

**BUG() / WARN()** — макросы в коде ядра для обработки аномалий. `BUG()` обычно приводит к панике или Oops, `WARN()` только выводит стек вызовов в `dmesg`.

**kdump (Kernel Crash Dump)** — механизм сохранения дампа оперативной памяти (`vmcore`) в момент сбоя. Использует `kexec` для загрузки резервного ядра поверх упавшего.

**pstore (Persistent Store)** — механизм сохранения логов ядра в энергонезависимую память (NVRAM, EFI или зарезервированная RAM — `ramoops`), которая доступна после перезагрузки.

## Основные концепции

### Жизненный цикл паники (Panic Flow)

Когда возникает фатальная ошибка, ядро проходит через следующие этапы:
1.  **Вызов `panic()`**: Функция в `kernel/panic.c` останавливает планировщик и прерывания на текущем CPU.
2.  **Оповещение (Notifiers)**: Выполняются функции из `panic_notifier_list` (например, для гашения светодиодов на сервере или отправки сообщения в IPMI).
3.  **Запись в pstore**: Если настроен `ramoops`, ядро копирует содержимое `dmesg` в зарезервированную область памяти.
4.  **Kdump (опционально)**: Если kdump активен, выполняется `kexec` — немедленный переход в аварийное ядро без сброса оборудования.
5.  **Действие по умолчанию**: Если kdump не сработал, ядро либо зависает (halt), либо перезагружается через время, указанное в `kernel.panic`.

### Механизмы сохранения данных (2024–2026)

#### kdump: Резервирование памяти
Для надежной работы `kdump` требуется зарезервировать память заранее через параметры загрузки ядра:
- `crashkernel=auto` — автоматическое выделение (может не работать в облаках).
- `crashkernel=256M` — рекомендуемый минимум для современных систем.

#### ramoops: Конфигурация pstore
Чтобы pstore работал через оперативную память (актуально для встраиваемых систем и облаков), необходимо выделить сегмент, который **не будет** очищен при мягкой перезагрузке:
`memmap=1M$0x60000000 ramoops.mem_address=0x60000000 ramoops.mem_size=0x100000 ramoops.record_size=0x4000`

## Практические сценарии

### Настройка поведения через sysctl

Управление поведением системы при различных типах сбоев:

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| `kernel.panic` | `30` | Время (сек) до автоматической перезагрузки после паники. |
| `kernel.panic_on_oops` | `1` | Считать любой Oops фатальным (рекомендуется для HA-кластеров). |
| `kernel.softlockup_panic` | `1` | Вызывать панику, если процесс завис в ядре более чем на 20 сек. |
| `kernel.unknown_nmi_panic` | `1` | Паника при получении неизвестного немаскируемого прерывания (NMI). |

### Глубокий анализ дампа (crash)

Если `kdump` создал файл `vmcore`, анализ выполняется утилитой `crash`:

```bash
# Запуск анализатора (требуются debuginfo-пакеты ядра)
sudo crash /usr/lib/debug/boot/vmlinux-$(uname -r) /var/crash/127.0.0.1-.../vmcore

# Ключевые команды внутри crash:
# bt        - вывод стека вызовов (Stack Trace) упавшего процесса.
# log       - вывод dmesg из дампа (последние сообщения перед паникой).
# ps        - список всех процессов в момент сбоя.
# mod       - список загруженных модулей ядра.
# struct    - просмотр содержимого структур ядра в памяти.
```

### Диагностика через pstore

После перезагрузки проверьте наличие отчетов:
```bash
# Смонтировать pstore, если не сделано автоматически
mount -t pstore pstore /sys/fs/pstore

# Просмотр лога паники
cat /sys/fs/pstore/dmesg-ramoops-0
```
