# Паника ядра (Kernel Panic)

## Определения

**Kernel Panic** — критическая невосстановимая ошибка ядра, при которой оно не может безопасно продолжать работу. Система останавливается для предотвращения повреждения данных, выводит диагностическую информацию, затем «зависает» или перезагружается.

## Основные концепции

### Причины Kernel Panic

- **Аппаратные сбои:** Неисправность оперативной памяти, процессора, диска.
- **Ошибки в ядре или драйверах:** Самая частая причина. Разыменование нулевого указателя, доступ к неверной области памяти, взаимоблокировки (deadlocks). См. также **[Зависания ядра (lockups.md)](./lockups.md)**.
- **Повреждение файловой системы:** Критические ошибки в корневой файловой системе, которые ядро не может исправить.
- **Некорректная конфигурация:** Ошибки в параметрах загрузки ядра.

### Механизм сбора аварийных дампов (`kdump`)

Для "посмертного" анализа причин Kernel Panic используется механизм `kdump`.

**Как это работает:**

1. **Резервирование памяти:** При загрузке системы для `kdump` резервируется небольшой участок оперативной памяти (с помощью параметра ядра `crashkernel=...`).
2. **Загрузка "ядра-сборщика":** В эту зарезервированную память загружается второе, минималистичное ядро Linux (`crashkernel` или "capture kernel").
3. **Срабатывание при панике:** Когда в основном ядре происходит паника, управление передаётся ядру-сборщику.
4. **Сохранение дампа:** Ядро-сборщик сохраняет образ (дамп) всей оперативной памяти основного ядра в файл на диске (обычно в `/var/crash/`).

Этот механизм надежен, так как ядро-сборщик работает в чистом, нетронутом паникой окружении.

## Практические сценарии

### Настройка поведения при панике: автоматическая перезагрузка

По умолчанию после Kernel Panic система может "зависнуть". Для серверов часто предпочтительнее автоматическая перезагрузка. Это поведение контролируется параметром ядра `kernel.panic`, который можно изменить через [sysctl](./sysctl.md).

- `kernel.panic = 0` (по умолчанию): Ядро будет ожидать вечно.
- `kernel.panic > 0`: Ядро перезагрузится через указанное количество секунд.

**Как настроить (перезагрузка через 10 секунд):**

1. **Временно (до следующей перезагрузки):**

    ```bash
    sudo sysctl -w kernel.panic=10
    ```

2. **Постоянно:**
    Добавьте `kernel.panic = 10` в файл в `/etc/sysctl.d/` (например, `99-kernel-panic.conf`) и примените настройки: `sudo sysctl -p`.

### Анализ `crash dump`

После перезагрузки системы сохранённый дамп можно проанализировать.

1. **Настройка `kdump`:** Убедитесь, что `kdump` установлен и сервис активен.

    ```bash
    # Для RHEL/CentOS
    sudo yum install kexec-tools
    sudo systemctl enable --now kdump.service

    # Для Debian/Ubuntu
    sudo apt install linux-crashdump
    ```

2. **Анализ дампа с помощью `crash`:**
    Утилита `crash` позволяет в интерактивном режиме исследовать состояние системы в момент сбоя.

    ```bash
    # Для анализа требуется сам дамп и отладочные символы для упавшего ядра
    sudo crash /var/crash/127.0.0.1-2025-11-29-15:30:00/vmcore /usr/lib/debug/lib/modules/`uname -r`/vmlinux
    ```

    **Основные команды в `crash`:**
    - `bt`: Показать backtrace (стек вызовов) для процесса, вызвавшего панику.
    - `log` или `dmesg`: Показать лог ядра из дампа.
    - [`ps`](../../Diagnostics/Processes/ps.md): Показать список процессов в момент сбоя.
    - `vm`: Показать информацию о состоянии виртуальной памяти.
    - `files`: Показать открытые файлы для процесса.

3. **Просмотр системных логов:**

   Первичную информацию о панике можно найти в логах предыдущей загрузки:

   ```bash
   # Логи ядра с предыдущей загрузки
   journalctl -k -b -1
   ```
