# Паника ядра (Kernel Panic)

## Определения

**Паника ядра (Kernel Panic)** — фатальное состояние ядра Linux, при котором оно обнаруживает критическую внутреннюю ошибку и не может продолжать безопасную работу. Для предотвращения повреждения данных и файловых систем ядро немедленно останавливает выполнение всех процессов, выводит диагностическую информацию (Panic Message) и инициирует перезагрузку или переход в режим отладки.

**kdump (Kernel Crash Dump)** — механизм ядра для создания полных дампов оперативной памяти (vmcore) в момент сбоя. Использует технологию `kexec` для запуска вторичного ядра («capture kernel») после падения основного.

**pstore (Persistent Store)** — энергонезависимое хранилище в ядре (на базе EFI Variables или зарезервированной RAM — `ramoops`), позволяющее сохранить лог `dmesg` и стек вызовов непосредственно в момент паники, когда запись на диск или по сети невозможна.

## Основные концепции

### Причины возникновения

1.  **Программные ошибки:** Разыменование нулевого указателя (NULL pointer dereference), ошибки в драйверах, бесконечные циклы в контексте прерываний.
2.  **Сбои синхронизации:** Взаимоблокировки (Deadlocks) критических ресурсов. Подробнее: [**Механизмы синхронизации**](./kernel_synchronization.md).
3.  **Аппаратные сбои:** Ошибки в работе оперативной памяти (ECC errors), процессора или системной шины.
4.  **Повреждение системных структур:** Нарушение целостности VFS или невозможность монтирования корневого раздела (Root FS). См. [**Процесс загрузки**](./boot_process.md).

### Механизмы сохранения данных (2024–2025)

#### kdump и проблема резервирования памяти
Традиционный метод `crashkernel=auto` в современных ядрах (6.x+) и облачных средах часто оказывается ненадежным. Рекомендуется использовать явное резервирование памяти в параметрах загрузки:
- `crashkernel=256M` — для стандартных систем.
- `crashkernel=512M` — для высоконагруженных систем со сложным сетевым стеком.

#### pstore как "Single Source of Truth" (SSoT)
В облачных инстансах (AWS, Azure), где запись `vmcore` по сети часто прерывается в момент паники, **pstore** становится единственным надежным источником данных. Служба `systemd-pstore` при загрузке автоматически собирает отчеты из `/sys/fs/pstore/` и сохраняет их в `/var/lib/systemd/pstore/`.

## Практические сценарии

### Настройка поведения при панике

Для серверов критически важно обеспечить автоматическое восстановление.

```bash
# Перезагрузка через 30 секунд после паники (sysctl)
sudo sysctl -w kernel.panic=30

# Вызывать панику при возникновении Kernel Oops (по умолчанию отключено)
sudo sysctl -w kernel.panic_on_oops=1
```

Для постоянного сохранения настроек создайте файл `/etc/sysctl.d/99-panic.conf`.

### Настройка kdump в облачных средах

В 2024–2025 годах для стабильной работы `kdump` на облачных узлах рекомендуется включать пост-нотификаторы:

```bash
# Добавить в параметры загрузки ядра (GRUB_CMDLINE_LINUX)
crash_kexec_post_notifiers=1
```
Это гарантирует, что ядро успеет отправить сообщения в консоль и записать данные в `pstore` перед попыткой запуска вторичного ядра.

### Анализ инцидента (SSoT-подход)

Если система перезагрузилась после сбоя, следуйте алгоритму:

1.  **Проверка pstore (наиболее надежно):**
    ```bash
    ls -l /var/lib/systemd/pstore/
    # Изучите файлы dmesg.txt на наличие стека вызовов (Call Trace)
    ```
2.  **Проверка системного журнала:**
    ```bash
    journalctl -k -b -1 | grep -i "panic"
    ```
3.  **Анализ vmcore (если настроен kdump):**
    ```bash
    sudo crash /usr/lib/debug/boot/vmlinux-$(uname -r) /var/crash/<timestamp>/vmcore
    # Команды внутри crash: 'bt' (stack trace), 'log' (dmesg), 'ps' (процессы)
    ```
