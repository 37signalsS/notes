# Паника ядра (Kernel Panic)

## Определения

**Паника ядра (Kernel Panic)** — критическая невосстановимая ошибка ядра Linux, при которой оно не может безопасно продолжать работу. Система останавливается для предотвращения повреждения данных, выводит диагностическую информацию в консоль, после чего либо зависает, либо автоматически перезагружается.

**kdump (Kernel Crash Dump)** — механизм ядра для создания дампов памяти в момент сбоя. Использует технологию `kexec` для запуска второго («спасательного») ядра после паники основного.

**vmcore** — файл образа оперативной памяти (дамп), сохраняемый механизмом `kdump` для последующего анализа.

## Основные концепции

### Причины возникновения

- **Ошибки в коде ядра или драйверах:** разыменование нулевого указателя, доступ к неверной области памяти, взаимоблокировки (Deadlocks). См. подробнее в [**Зависания ядра**](./lockups.md).
- **Аппаратные сбои:** неисправность оперативной памяти (RAM — Random Access Memory), процессора (CPU — Central Processing Unit) или дискового контроллера.
- **Повреждение файловой системы:** критические ошибки в структурах данных корневого раздела, препятствующие работе VFS (Virtual File System).
- **Ошибки конфигурации:** некорректные параметры командной строки ядра в загрузчике GRUB.

### Механизм kdump

Процесс сбора дампа организован так, чтобы минимизировать влияние повреждённого состояния основного ядра:

1. **Резервирование памяти:** при загрузке системы для `kdump` выделяется защищённая область памяти (параметр `crashkernel=...`).
2. **Загрузка Capture-ядра:** в зарезервированную область загружается минималистичное ядро Linux.
3. **Срабатывание:** при наступлении паники основное ядро передаёт управление Capture-ядру без полного цикла перезагрузки оборудования.
4. **Сохранение:** Capture-ядро монтирует диски и сохраняет содержимое памяти основного ядра в файл `/var/crash/.../vmcore`.

## Практические сценарии

### Настройка автоматической перезагрузки

По умолчанию система может оставаться в состоянии паники до вмешательства администратора. Для серверов рекомендуется настроить автоматический перезапуск через [**sysctl**](./sysctl.md).

```bash
# Временно (до перезагрузки): перезапуск через 10 секунд
sudo sysctl -w kernel.panic=10
# → kernel.panic = 10

# Постоянно:
# Добавить строку 'kernel.panic = 10' в /etc/sysctl.d/99-panic.conf
sudo sysctl -p /etc/sysctl.d/99-panic.conf
```

### Подготовка среды анализа (kdump)

```bash
# Установка инструментов (Debian/Ubuntu)
sudo apt install linux-crashdump -y

# Установка инструментов (RHEL/CentOS)
sudo yum install kexec-tools -y
sudo systemctl enable --now kdump.service
```

### Анализ дампа утилитой `crash`

Для анализа требуются: сам файл `vmcore` и файл `vmlinux` с отладочными символами, соответствующий версии ядра в дампе.

```bash
# Запуск интерактивного анализа
sudo crash /var/crash/<timestamp>/vmcore /usr/lib/debug/lib/modules/$(uname -r)/vmlinux

# Основные команды внутри crash:
# bt        — показать backtrace (стек вызовов) в момент падения
# log       — вывести кольцевой буфер сообщений ядра (dmesg)
# ps        — список процессов в момент сбоя
# vm        — информация о виртуальной памяти
# files     — открытые дескрипторы для процесса
```

### Поиск следов паники в системных журналах

Если `kdump` не настроен, причину сбоя можно попытаться найти в логах предыдущей загрузки (при условии, что `journald` настроен на постоянное хранение).

```bash
# Логи ядра за предыдущую сессию
journalctl -k -b -1
# → ... BUG: unable to handle kernel NULL pointer dereference ...
# → ... Kernel panic - not syncing: Fatal exception ...
```
