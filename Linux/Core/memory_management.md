## Про память в Linux

Когда вы смотрите на показатели памяти (например, в top, free или через `cat /proc/meminfo`), важно понимать, что именно подразумевается под «used», «free», «buff/cache» и т. д. На первый взгляд может казаться, что система «съедает» всю память, но зачастую это лишь особенности кэширования и работы ядра.

1. Total — Общий объём оперативной памяти (RAM), который распознаёт ядро Linux. Это не физический объем всей памяти, а объем, доступный системе после того, как ядро зарезервировало часть для своих нужд. То есть, это физический объем минус память, зарезервированная ядром. Эта метрика показывает, сколько памяти доступно для использования в пользовательском пространстве.
    
2. Used — Количество памяти, занимаемой процессами, включая их программный код.
    
3. Free — Память, которая прямо сейчас не задействована ни под процессы, ни под кэш. Важно понимать, что это не означает, что она полностью доступна для новых приложений; скорее, это память, которая системе "не нужна" в данный момент. Низкое значение `Free` не всегда является проблемой, так как Linux активно использует доступную память для кэширования. Ориентироваться только на этот столбец для оценки доступности памяти для новых приложений не рекомендуется.

4. Shared — Объем памяти, которая может быть разделена между несколькими процессами. Это используется для межпроцессного взаимодействия (IPC) и для загрузки общих библиотек. Вместо того чтобы загружать одну и ту же библиотеку в память для каждого процесса, она загружается один раз в разделяемую память, и все процессы получают к ней доступ. Это позволяет эффективно использовать память.
    
5. Buff/Cache
    - Buffers — память, зарезервированная под буферизацию операций ввода-вывода (I/O). Сегодня это место, где данные компонуются в нужные фрагменты (например, для записи на диск блоками по 4 КБ, когда данные поступают меньшими частями). Это помогает оптимизировать операции записи.

    - Cache — память, используемая для кэширования файловых данных (page cache). Когда процессу требуется доступ к файлу с диска, система загружает его в кэш. При повторном чтении данные берутся из кэша, минуя медленный диск. Память организована в виде страниц (обычно по 4 КБ), и эта область, куда загружаются страницы файла, называется файловым кэшем. Также существует понятие "грязных страниц" (dirty pages) — это страницы в кэше, которые были изменены, но еще не записаны на диск. Ядро не выгружает кэшированные данные сразу после завершения процесса, так как их повторная загрузка с диска занимает больше времени, чем хранение в памяти "на всякий случай". Ядро предпочитает хранить данные в кэше, рассчитывая, что они могут понадобиться снова. Если приложению понадобится память, ядро автоматически «отдаст» часть кэша, так что buff/cache не означает «пропавшую» память. Если система хорошо нагружена и имеет большой объем кэша, это означает, что она эффективно использует доступную память.

6. Available — **Наиболее важный показатель.** Показывает объём памяти, который ядро может отдать под новые процессы без использования swap. Эта метрика учитывает `Free` и часть `Buff/Cache`, которую можно безболезненно освободить. Если программе потребуется больше памяти, система очистит часть кэша, чтобы предоставить ее. Высокое значение `Available` (например, более 50% от `Total`) при низком `Free` указывает на то, что система эффективно использует память для кэширования и при этом имеет достаточный резерв для новых приложений. Не стоит бояться низких значений в столбце `Free`, если `Available` показывает достаточный объем.
    
7. Swap — Когда системе не хватает физической памяти (или при определённой настройке swappiness), неиспользуемые страницы памяти могут выгружаться в swap-раздел (или файл). Если swap активно используется, это может указывать на нехватку RAM, но иногда ядро использует swap и при наличии свободной памяти, если считает, что выгрузка «простаивающих» страниц — более эффективный вариант.

## Оперативная память (ОЗУ)

По умолчанию команда `free` выводит информацию в килобайтах. Для более удобного чтения используются следующие опции:

```sh
free -h # Человекочитаемый формат (G, M, K)
free -m # В мегабайтах
```
Важно помнить, что столбец `Total` в выводе `free` показывает не общий физический объем установленной RAM, а объем памяти, доступный системе после того, как ядро зарезервировало часть для своих нужд. Это может быть меньше, чем физически установленная память.

| Поле       | Значение | Что означает                                                                 |
|------------|----------|-----------------------------------------------------------------------------|
| **total**  | 7.7G     | Вся оперативная память в системе.                                           |
| **used**   | 3.2G     | Память, занятая процессами (но не вся реально используется, total - free - buff/cache).      |
| **free**   | 843M     | Полностью свободная память (не используется ни для чего).                   |
| **shared** | 123M     | Память, разделяемая между процессами (например, shared libraries, IPC).     |
| **buff/cache** | 3.7G | Память, занятая кэшем и буферами (может быть освобождена при необходимости).|
| **available** | 2.9G | Реальная физическая память, которую система может выделить новым процессам без запуска механизма подкачки (swapping). Это наиболее точный показатель свободной памяти для приложений.(≈ free + часть buff/cache).  |

Файл `/proc/meminfo` предоставляет исчерпывающую статистику об использовании оперативной и swap-памяти. Рассмотрим ключевые параметры:

**Общая память:**
-   `MemTotal`: Общий объем физической RAM.
-   `MemFree`: Количество полностью свободной, неиспользуемой памяти. Это "сырой" показатель, который часто бывает низким, так как Linux стремится использовать свободную память для кэширования.
-   `MemAvailable`: **Наиболее важный показатель для оценки свободной памяти.** Это оценка того, сколько памяти доступно для запуска новых приложений без необходимости выгрузки данных в swap. Включает `MemFree` и часть кэша, которую можно безболезненно освободить.

**Кэш и буферы:**
-   `Buffers`: Память, используемая для временного хранения "сырых" дисковых блоков. Это кэш метаданных файловой системы.
-   `Cached`: Память, используемая для кэширования данных, прочитанных с диска (page cache). При повторном чтении файла данные будут взяты отсюда, а не с медленного диска.
-   `SwapCached`: Память, которая была выгружена в swap, а затем снова загружена в RAM, но все еще остается в swap-файле. Если понадобится, ее можно будет быстро выгрузить обратно, не записывая на диск заново.

**Активная и неактивная память:**
-   `Active`: Память, которая активно используется в данный момент.
-   `Inactive`: Память, которая использовалась, но сейчас неактивна. Является основным кандидатом на вытеснение (reclaiming) при нехватке памяти.
-   `Active(anon)` / `Inactive(anon)`: Анонимная память (не связанная с файлами), которая активно/неактивно используется. Это, как правило, память процессов (стек, куча).
-   `Active(file)` / `Inactive(file)`: Память, используемая для кэширования файлов, которая активно/неактивно используется.
-   `Unevictable`: Страницы памяти, которые нельзя выгрузить в swap (например, заблокированные с помощью `mlock()`).
-   `Mlocked`: Память, заблокированная процессом с помощью системного вызова `mlock()`. Гарантированно не будет выгружена в swap.

#### Механизм Page Reclaim

**Page Reclaim** — это процесс, при котором ядро Linux освобождает память, когда её становится недостаточно. Ядро пытается вытеснить из RAM страницы, которые давно не использовались.

**Как это работает:**
1.  **Списки Active и Inactive:** Ядро поддерживает два основных списка страниц памяти:
    *   **Active list:** Содержит страницы, к которым недавно были обращения.
    *   **Inactive list:** Содержит страницы, которые давно не использовались. Они являются кандидатами на вытеснение.

2.  **Процесс `kswapd`:** Когда количество свободной памяти опускается ниже определённого порога (`pages_low`), просыпается специальный процесс ядра `kswapd`. Его задача — сканировать страницы и освобождать память, пока её уровень не достигнет порога `pages_high`.

3.  **Алгоритм:**
    *   `kswapd` в первую очередь сканирует страницы из `Inactive` списка.
    *   Если страница "чистая" (clean), то есть её содержимое не было изменено и совпадает с данными на диске (например, это кэш файла), она просто удаляется из памяти.
    *   Если страница "грязная" (dirty), то есть была изменена (например, данные приложения), она сначала должна быть записана на диск (в swap или в исходный файл), и только потом её можно освободить.
    *   `kswapd` также периодически перемещает страницы из `Active` списка в `Inactive`, если к ним давно не было обращений, чтобы "состарить" их и сделать кандидатами на вытеснение.

**Swap-пространство:**
-   `SwapTotal`: Общий размер раздела или файла подкачки.
-   `SwapFree`: Количество свободного места в swap.

**Страницы памяти:**
-   `Dirty`: Память, которая была изменена, но еще не записана на диск. Если система внезапно выключится, эти данные будут потеряны.
-   `Writeback`: Память, которая в данный момент записывается на диск.
-   `AnonPages`: Анонимные (нефайловые) страницы памяти, используемые процессами.
-   `Mapped`: Память, которая отображена в адресное пространство процессов (например, файлы или библиотеки).
-   `Shmem`: Объем разделяемой памяти (включая `tmpfs`).

**Память ядра:**
-   `Slab`: Память, используемая ядром для кэширования собственных структур данных (inodes, dentries и т.д.).
-   `SReclaimable`: Часть `Slab`, которую можно освободить при нехватке памяти.
-   `SUnreclaim`: Часть `Slab`, которую освободить нельзя.
-   `KernelStack`: Память, выделенная для стеков потоков ядра.
-   `PageTables`: Память, занимаемая таблицами страниц, которые используются для трансляции виртуальных адресов в физические.

### Slab Allocator: Кэширование объектов ядра

**Slab Allocator** — это механизм управления памятью, который ядро Linux использует для эффективного выделения памяти под собственные, часто используемые структуры данных (объекты). Примерами таких объектов являются `inodes`, `dentries` (кэш путей файловой системы), дескрипторы файлов и сетевые буферы.

**Проблема, которую он решает:**
Ядро постоянно создает и уничтожает огромное количество однотипных объектов. Если бы для каждого из них память выделялась и освобождалась стандартным образом, это привело бы к двум проблемам:
1.  **Внешняя фрагментация:** Постоянное выделение и освобождение мелких блоков памяти привело бы к "дырам" в памяти, которые сложно использовать повторно.
2.  **Накладные расходы:** Каждый раз при создании объекта его нужно инициализировать, а при уничтожении — выполнять очистку. Это затратно по времени.

**Как работает Slab Allocator:**
1.  Он создает "кэши" для каждого типа объектов.
2.  Каждый кэш состоит из одного или нескольких "слэбов" (slabs) — это одна или несколько смежных страниц физической памяти.
3.  Каждый слэб "нарезан" на объекты нужного размера.
4.  Когда ядру нужен новый объект (например, `inode`), он просто берется из соответствующего кэша. Когда объект больше не нужен, он не освобождается полностью, а возвращается в свой слэб и помечается как свободный, готовый к повторному использованию.

Это значительно снижает фрагментацию и ускоряет работу ядра, так как объекты переиспользуются уже в инициализированном состоянии.

**Управление памятью:**
-   `CommitLimit`: Общий объем виртуальной памяти, который система может выделить. Рассчитывается как `SwapTotal + (MemTotal * vm.overcommit_ratio / 100)`.
-   `Committed_AS`: Объем виртуальной памяти, который уже был выделен (запрошен) процессами. Если это значение приближается к `CommitLimit`, система близка к нехватке памяти.


### Slab Shrinker: Механизм освобождения кэшей ядра

**Slab shrinker** — это механизм ядра Linux, который отвечает за освобождение памяти, занятой кэширующими структурами (slab caches), когда в системе возникает нехватка памяти. Он является ключевым элементом, который делает часть `Slab` "освобождаемой" (`SReclaimable`).

**Как он участвует в освобождении памяти:**

1.  **Регистрация шринкера:** Каждая подсистема ядра, использующая slab-кэширование для объектов, которые можно безопасно удалить (например, `dentry cache`, `inode cache`), регистрирует специальную `shrinker-функцию`. Эта функция "знает", как освободить неиспользуемые объекты из своего кэша.

2.  **Вызов при нехватке памяти:** Когда системе не хватает памяти, ядро запускает процесс освобождения страниц (`page reclaim`). В рамках этого процесса оно вызывает зарегистрированные `shrinker-функции`. Это может быть инициировано как фоновым демоном `kswapd`, так и напрямую, если процесс пытается выделить память и сталкивается с её нехваткой.

3.  **Процесс "усыхания" (shrinking):**
    *   Shrinker-функция сообщает ядру, сколько объектов она потенциально может освободить.
    *   Ядро просит её освободить определённое количество объектов.
    *   Shrinker пытается удалить из кэша "старые" или неиспользуемые элементы, возвращая занимаемую ими память в общий пул.

Таким образом, `slab shrinker` позволяет ядру гибко управлять своей собственной памятью, освобождая кэши, которые в данный момент не критичны, чтобы отдать память пользовательским процессам.

### "Грязные" страницы (Dirty Pages) и Writeback

**Dirty Page** ("грязная" страница) — это страница в оперативной памяти (RAM), содержимое которой было изменено, но эти изменения еще не были записаны на постоянное хранилище (диск).

**Как это работает:**
Когда приложение записывает данные в файл, ядро Linux для повышения производительности не сразу сбрасывает их на диск. Вместо этого оно помечает соответствующую страницу памяти как "грязную" и откладывает запись. Это позволяет накапливать несколько операций записи и выполнять их более эффективно за один раз.

Процесс записи "грязных" страниц на диск называется **Writeback**.

**Управление через `sysctl`:**
Поведение этого механизма контролируется несколькими параметрами ядра в `/proc/sys/vm/`:

-   `vm.dirty_background_ratio`: Процент системной памяти, который может быть заполнен "грязными" страницами, прежде чем фоновые процессы ядра (`pdflush`/`kworker`) начнут их запись на диск.
-   `vm.dirty_ratio`: Максимальный процент системной памяти, который могут занимать "грязные" страницы. Когда этот порог достигнут, все новые операции ввода-вывода блокируются до тех пор, пока "грязные" страницы не будут записаны на диск. Это может вызывать "зависание" приложений, выполняющих запись.
-   `vm.dirty_expire_centisecs`: Максимальное время (в сотых долях секунды), в течение которого страница может оставаться "грязной" перед тем, как будет принудительно записана на диск.
-   `vm.dirty_writeback_centisecs`: Интервал, с которым просыпаются процессы ядра для проверки наличия "грязных" страниц, которые нужно записать.

Правильная настройка этих параметров важна для систем с интенсивной записью, чтобы сбалансировать производительность и избежать длительных пауз.

**Огромные страницы (Huge Pages):**
-   `HugePages_Total` / `HugePages_Free` / `Hugepagesize`: Информация о количестве и размере "огромных страниц". Они используются для уменьшения накладных расходов на управление памятью для приложений, работающих с большими объемами данных (например, базы данных).


## Физическая и виртуальная память

В Linux, как и в большинстве современных ОС, процессы не могут обращаться к физической оперативной памяти (RAM) напрямую. Вместо этого система предоставляет каждому процессу **виртуальную память** — абстракцию, которая решает несколько ключевых задач:

1.  **Изоляция:** Виртуальная память, выделенная одному процессу, полностью изолирована и недоступна для других. Это фундаментальный механизм безопасности, который не позволяет одному приложению "покуситься" на память другого.
2.  **Сопоставление с реальной памятью:** Когда процесс хочет записать или прочитать данные, происходит сопоставление (mapping) виртуальных адресов с физическими. Этим управляет ядро ОС в **пространстве ядра (kernelspace)**.

| Характеристика | Физическая память (RAM) | Виртуальная память |
| :--- | :--- | :--- |
| **Что это?** | Реальные аппаратные чипы на материнской плате. | Абстракция, создаваемая операционной системой. |
| **Скорость** | Очень высокая. | Значительно медленнее, особенно при доступе к данным на диске. |
| **Размер** | Ограничен объемом установленных модулей ОЗУ. | Ограничен размером жесткого диска и архитектурой процессора. |
| **Доступ** | Процессор может выполнять код только из физической памяти. | Процессы работают с виртуальными адресами, которые ОС и аппаратура "переводят" в физические. |

**Как это работает: Механизм страниц**

И физическая, и виртуальная память делятся на небольшие блоки фиксированного размера, называемые **страницами** (обычно 4 КБ).

1.  **Таблицы страниц:** Для каждого процесса ядро Linux ведет специальную карту — **таблицу страниц**. В этой таблице для каждой виртуальной страницы процесса записано, где она находится на самом деле:
    *   В какой-то физической странице в ОЗУ.
    *   На жестком диске в специальном разделе или файле (swap).
    *   Нигде (если память была запрошена, но еще не использовалась).

2.  **MMU (Memory Management Unit):** Это специальный аппаратный блок в процессоре. Когда программа обращается к адресу в своей виртуальной памяти, MMU на лету заглядывает в таблицу страниц и мгновенно преобразует виртуальный адрес в физический.

**Преимущества и принципы работы виртуальной памяти:**
*   **Изоляция процессов:** Каждый процесс работает в своем собственном "пузыре" виртуальной памяти и не может испортить память другого процесса. Виртуальная память, выделенная одному процессу, полностью изолирована и недоступна для других.
*   **Использование памяти, превышающей ОЗУ (Overcommit):** Программы могут запрашивать больше памяти, чем физически установлено. Неактивные страницы памяти выгружаются в **пространство подкачки (swap)** на диске. Linux часто использует механизм **"чрезмерного выделения" (overcommit)**, когда система *обещает* процессу больше виртуальной памяти, чем есть в RAM. Например, процессу дадут запрошенные 6 ГБ виртуальной памяти при наличии всего 4 ГБ физической. Процесс будет работать, пока его реальное потребление не превысит доступный объем в 4 ГБ. Как только это произойдет, и если swap будет исчерпан, возникнет ошибка выделения, которая может спровоцировать **OOM Killer**. Этот механизм позволяет минимизировать процесс выделения физической памяти, выделяя ее только тогда, когда программа начинает записывать реальные данные в запрошенную память.
*   **Эффективное использование ОЗУ:** Общие библиотеки загружаются в физическую память только один раз, а не для каждого процесса.
*   **Индивидуальное адресное пространство:** Виртуальная память представляет собой индивидуальное, нефизическое адресное пространство для каждого процесса, что упрощает управление памятью и позволяет процессам работать, не зная о физическом расположении данных.

### Vmstat: мониторинг активности swap

Утилита `vmstat` предоставляет информацию о процессах, памяти, подкачке, вводе-выводе, системных прерываниях и активности процессора. В контексте swap особенно важны два поля в её выводе:

-   **si (swap-in):** Объем памяти, загруженный из swap-раздела в RAM (в килобайтах в секунду). Постоянно высокое значение `si` свидетельствует о том, что системе не хватает оперативной памяти, и она вынуждена постоянно считывать данные с медленного диска.
-   **so (swap-out):** Объем памяти, выгруженный из RAM в swap-раздел (в килобайтах в секунду). Высокое значение `so` говорит о том, что система активно освобождает RAM, перемещая неактивные страницы в swap.

### Метрики потребления памяти процесса

При анализе потребления памяти отдельным процессом (например, в `top`, `ps` или `smem`) используются несколько ключевых метрик, которые важно различать.

*   **VSS (Virtual Set Size) или VSZ (Virtual Memory Size):**
    *   **Что это:** Общий объем **виртуальной памяти**, который процесс "видит" или к которому теоретически может получить доступ.
    *   **Что включает:** Все, что отображено в адресное пространство процесса: его код, данные, стек, куча, разделяемые библиотеки, а также память, которая была запрошена у ядра (`malloc`), но еще физически не выделена и не используется.
    *   **Вывод:** Сумма VSS всех процессов в системе может **многократно превышать** объем физической RAM. Это нормально и является следствием работы механизма виртуальной памяти и overcommit. Сама по себе большая цифра VSS не всегда указывает на проблему.

*   **RSS (Resident Set Size) или RES (Resident Memory):**
    *   **Что это:** Объем памяти, который процесс **реально занимает в физической оперативной памяти (RAM)** в данный момент.
    *   **Что включает:** Код, данные и другие ресурсы процесса, которые сейчас находятся в RAM.
    *   **Что НЕ включает:** Память, выгруженную в swap, или память, которая была запрошена, но еще не использовалась.
    *   **Проблема:** RSS включает в себя **всю** разделяемую память (например, общие библиотеки). Если 10 процессов используют одну и ту же библиотеку размером 100 МБ, эти 100 МБ будут учтены в RSS *каждого* из 10 процессов. Сумма RSS всех процессов также может быть больше, чем RAM.

*   **PSS (Proportional Set Size):**
    *   **Что это:** Более "справедливая" метрика, чем RSS. Она учитывает разделяемую память пропорционально.
    *   **Как считается:** `PSS = (Уникальная память процесса) + (Разделяемая память / Количество процессов, которые ее используют)`.
    *   **Пример:** Если 2 процесса используют библиотеку размером 100 МБ, то в PSS каждого из них будет засчитано по 50 МБ.
    *   **Вывод:** Сумма PSS всех процессов дает гораздо более реалистичную оценку общего потребления RAM в системе.

*   **USS (Unique Set Size):**
    *   **Что это:** Объем памяти, который является **уникальным** для данного процесса и не разделяется ни с кем другим.
    *   **Вывод:** Это самый точный показатель того, **сколько физической памяти освободится, если завершить данный процесс**. Утилита `smem` отлично подходит для просмотра этой метрики.

| Метрика | Что показывает | Когда полезна |
| :--- | :--- | :--- |
| **VSS/VSZ** | Сколько виртуальной памяти "видит" процесс. | Для понимания, сколько памяти процесс *запрашивает* у системы. |
| **RSS/RES** | Сколько физической памяти занимает процесс, включая разделяемую. | Быстрая, но неточная оценка потребления RAM. |
| **PSS** | "Справедливая" доля процесса в физической памяти. | Наиболее точная оценка реального вклада процесса в общую загрузку RAM. |
| **USS** | Уникальная память процесса. | Чтобы узнать, сколько памяти освободится после "убийства" процесса. |

### Управление Swap (файлом подкачки)

**Swap** (или файл подкачки) — это пространство на диске, которое операционная система использует, когда ей не хватает оперативной памяти (RAM). Если память заполнена, ядро Linux перемещает неактивные страницы памяти (данные) из RAM в swap-пространство, освобождая RAM для более важных задач. Это предотвращает сбои системы из-за нехватки памяти.

Существует два основных способа организации swap:
1.  **Swap-раздел (swap partition)**: Отдельный раздел на диске, предназначенный исключительно для подкачки.
2.  **Swap-файл (swap file)**: Специальный файл, расположенный внутри существующей файловой системы (например, `/swapfile`). Является более гибким и удобным решением.

#### Swap-раздел vs Swap-файл

Хотя исторически считалось, что отдельный раздел работает быстрее, на практике эта разница незначительна, особенно на современных дисках. Swap в виде файла позволяет на лету менять свой размер или вовсе его отключать, если экстренно понадобится доступное место. Это весомое преимущество, которое стоит использовать.

| Характеристика      | Swap-раздел                                       | Swap-файл                                           |
| ------------------- | ------------------------------------------------- | --------------------------------------------------- |
| **Производительность** | Традиционно считался быстрее, но на современных SSD разница незначительна. | Практически не уступает разделу по скорости.        |
| **Гибкость**        | **Низкая**. Размер сложно изменить без утилит для работы с разделами. | **Высокая**. Легко создать, удалить или изменить размер на лету. |
| **Использование**     | Классический подход, обязателен для старых систем. | Современный и рекомендуемый подход в большинстве случаев. |
| **Гибернация**      | Необходим для режима гибернации (сохранения состояния RAM на диск). | С современными ядрами Linux гибернация в swap-файл также возможна, но требует более сложной настройки. |

### Философия использования Swap: Избегать или использовать?

Существует два основных подхода к использованию swap в серверных окружениях:

1.  **Подход "Swap как зло":** Сторонники этого подхода утверждают, что на высоконагруженных производственных серверах swap следует отключать.
    *   **Аргументация:** Если приложению начинает не хватать оперативной памяти, его производительность при активном свопинге катастрофически падает. Пользователи сталкиваются с медленной работой сервиса, что может быть хуже, чем его полная недоступность. Отсутствие swap приводит к тому, что при нехватке памяти OOM Killer немедленно завершит "прожорливый" процесс. Это делает проблему видимой сразу, позволяя администраторам быстрее отреагировать (например, добавив RAM или оптимизировав приложение), вместо того чтобы сервис "тихо умирал" неделями.
    *   **Вывод:** Лучше спланировать систему с достаточным количеством RAM, чтобы swap не требовался. Пусть сервис упадет быстро, чем будет медленно деградировать.

2.  **Подход "Swap как подушка безопасности":** Этот подход рассматривает swap как необходимый защитный механизм.
    *   **Аргументация:** Небольшой swap-раздел (1–4 ГБ) может спасти систему от сбоя при кратковременных, неожиданных всплесках потребления памяти. Он также полезен для выгрузки неактивных страниц системных демонов, освобождая больше RAM для критически важных приложений. Некоторые приложения (например, определенные СУБД) в принципе требуют наличия swap для корректной работы.
    *   **Вывод:** Swap необходим, но его активное использование — это сигнал о нехватке RAM. `swappiness` при этом следует устанавливать в низкое значение (1-10).

**Итог:** Выбор стратегии зависит от конкретной задачи. Для домашних компьютеров и некритичных серверов наличие swap является нормой. Для высокопроизводительных систем, где деградация производительности недопустима, часто выбирают стратегию "без swap", но это требует более тщательного планирования и мониторинга ресурсов.

### Рекомендации по использованию для разных сценариев

| Сценарий | Использовать Swap? | Рекомендуемый размер | Swappiness (`vm.swappiness`) | Тип (Файл/Раздел) | Примечания |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Рабочая станция / Ноутбук** | Да, настоятельно | >= RAM (для гибернации), иначе 4-8 ГБ для систем > 8ГБ RAM. | 60 (стандарт) | Файл (гибкость) | Полезно для запуска множества приложений и необходимо для режима гибернации (suspend-to-disk). |
| **Сервер баз данных (MySQL, PostgreSQL)** | С большой осторожностью | 1–4 ГБ (как "подушка безопасности") | 1–10 | Раздел (производительность) | Активный свопинг критически снижает производительность БД. Swap здесь нужен только для предотвращения OOM killer. |
| **Сервер приложений (Web, Microservices)** | Да | 0.5x RAM или 4–8 ГБ | 10–30 | Файл (гибкость) | Предотвращает падение приложений при утечках памяти или неожиданных пиках нагрузки. |

#### Создание и активация Swap-файла

Рекомендуемый способ создания swap-файла — использование утилиты `dd`, которая гарантированно запишет нули в файл, что является более надежной практикой.

```bash
# 1. Создать файл размером 1 ГБ с помощью dd
# of=/swap - путь к файлу
# bs=1024 - размер блока 1 КБ
# count=1000000 - количество блоков (1024 * 1000000 = ~1 ГБ)
sudo dd if=/dev/zero of=/swap bs=1024 count=1000000

# 2. Установить правильные права доступа (только root должен иметь доступ)
sudo chmod 0600 /swap

# 3. Отформатировать файл как swap-пространство
sudo mkswap /swap

# 4. Активировать swap-файл
sudo swapon /swap

# 5. Добавить запись в /etc/fstab для автоматического подключения при загрузке
echo '/swap swap swap defaults 0 0' | sudo tee -a /etc/fstab
```

> **Важное замечание:** Не рекомендуется создавать swap-файл с помощью `truncate` или `fallocate` (`truncate -s 1G /swap`, `fallocate -l 1G /swap`). Эти команды создают "разреженный" (sparse) файл мгновенно, не записывая в него данные физически. Для swap-файла предпочтительнее явное выделение и обнуление пространства с помощью `dd`.

#### Проверка состояния

```sh
# Показать активные swap-области
swapon --show

# Показать использование памяти и swap
free -h
```

#### Отключение и удаление Swap-файла

Если swap-файл больше не нужен, его можно отключить и удалить.

```bash
# 1. Отключить swap-файл (требуются права суперпользователя)
sudo swapoff /swap

# Чтобы отключить все активные swap-устройства:
# sudo swapoff -a

# 2. Удалить запись из /etc/fstab
# Закомментируйте или удалите строку '/swap swap swap defaults 0 0'

# 3. Удалить сам файл
sudo rm /swap
```

#### Рефакторинг: замена LVM-раздела на swap-файл

Если система использует LVM и swap выделен в виде отдельного логического тома (LV), его можно безопасно (но с осторожностью) преобразовать в swap-файл, а освободившееся место добавить к корневому разделу.

**Последовательность действий:**

1.  **Проверить список разделов:**
    ```bash
    sudo lvs
    # Пример вывода:
    # LV     VG          Attr       LSize   Pool Origin Data%  Meta%  Move Log Cpy%Sync Convert
    # root   web-01-vg   -wi-ao---- <27.51g
    # swap_1 web-01-vg   -wi-ao----  <1.54g
    ```

2.  **Отключить swap и удалить его из fstab:**
    ```bash
    # Отключить все swap-разделы
    sudo swapoff -a
    ```
    Сразу после этого **обязательно** закомментируйте или удалите соответствующую строку в `/etc/fstab`. Она может выглядеть так:
    `/dev/mapper/web--01--vg-swap_1 none swap sw 0 0`

3.  **Удалить логический том (LV) со swap:**
    ```bash
    # lvremove /dev/web-01-vg/swap_1
    # Do you really want to remove active logical volume web-01-vg/swap_1? [y/n]: y
    #   Logical volume "swap_1" successfully removed.
    ```

4.  **Расширить корневой раздел на все освободившееся место:**
    ```bash
    # lvextend -l +100%FREE /dev/web-01-vg/root
    #   Size of logical volume web-01-vg/root changed from <27.51 GiB (7042 extents) to 29.04 GiB (7435 extents).
    #   Logical volume web-01-vg/root successfully resized.
    ```

5.  **"Растянуть" файловую систему на весь раздел:**
    Увеличение раздела не означает автоматического увеличения файловой системы.
    ```bash
    # Для файловых систем ext2/ext3/ext4
    # resize2fs /dev/web-01-vg/root
    # resize2fs 1.47.2 (1-Jan-2025)
    # Filesystem at /dev/web-01-vg/root is mounted on /; on-line resizing required
    # old_desc_blocks = 4, new_desc_blocks = 4
    # The filesystem on /dev/web-01-vg/root is now 7613440 (4k) blocks long.
    ```

6.  **Проверить результат и создать swap-файл:**
    ```bash
    df -h | grep root
    # /dev/mapper/web--01--vg-root  29G  4.7G   23G  18% /
    ```
    После этого можно создавать swap-файл, как описано в инструкции выше.

> **Обязательно перезагрузите сервер** после завершения всех операций, чтобы убедиться в корректности изменений, особенно в `/etc/fstab`.

## Тюнинг параметров Swap

`vm.swappiness` — это параметр ядра Linux, который контролирует, насколько агрессивно система будет использовать swap. Значение варьируется от 0 до 100.

-   **`100`**: Максимально агрессивное использование swap. Ядро будет выгружать данные в swap очень активно.
-   **`60`**: Значение по умолчанию для большинства дистрибутивов.
-   **`10`**: Рекомендуемое значение для серверов и десктопов. Ядро будет неохотно использовать swap, предпочитая сначала очищать файловый кэш.
-   **`0 или 1`**: Ядро будет избегать swap любой ценой и прибегнет к нему только чтобы предотвратить OOM-ошибку.

**Как проверить текущее значение:**
```sh
cat /proc/sys/vm/swappiness
```

**Как временно изменить значение:**
```sh
sudo sysctl vm.swappiness=10
```

**Как изменить значение навсегда:**
Откройте файл `/etc/sysctl.conf` и добавьте или измените строку:
```
vm.swappiness=10
```
Затем примените изменения: `sudo sysctl -p`.

### Приоритет Swap (Swap Priority)

Если в системе используется несколько swap-устройств (файлов или разделов), можно задать для каждого из них **приоритет**. Устройство с более высоким приоритетом будет использоваться в первую очередь. Приоритеты могут быть в диапазоне от -1 до 32767.

Это полезно, например, если у вас есть быстрый SSD и медленный HDD. Вы можете создать swap-раздел на каждом из них и задать более высокий приоритет для swap на SSD.

**Как задать и изменить приоритет:**

1.  **Просмотр приоритетов:**
    ```sh
    swapon --show # или swapon -s
    ```

2.  **Изменение приоритета:** Нельзя изменить приоритет "на лету". Нужно сначала отключить swap, а затем включить его с новым приоритетом.
    ```bash
    # Пытаемся изменить приоритет активного swap - получаем ошибку
    sudo swapon -p 10 /swapfile
    # swapon: /swapfile: swapon failed: Устройство или ресурс занято

    # Правильный способ:
    # 1. Отключаем swap
    sudo swapoff /swapfile

    # 2. Включаем с новым приоритетом
    sudo swapon -p 10 /swapfile
    ```

3.  **Закрепление в `/etc/fstab`:** Чтобы приоритет сохранялся после перезагрузки, его нужно указать в опциях монтирования в файле `/etc/fstab`.
    ```
    # <file>        <mount point>   <type>  <options>         <dump>  <pass>
    /swapfile       none            swap    sw,pri=10         0       0
    /dev/sdb2       none            swap    sw,pri=5          0       0
    ```


## Управление выделением памяти (Memory Overcommit)

**Memory Overcommit** — это механизм ядра, который позволяет процессам запрашивать (выделять) больше виртуальной памяти, чем физически доступно в системе (RAM + swap). Это возможно, потому что программы часто резервируют память "про запас", но не используют её всю сразу.

### Риски и преимущества

-   **Преимущество:** Повышает эффективность использования памяти на системах, где запущено много процессов, каждый из которых резервирует больше памяти, чем реально использует. Это позволяет запустить больше приложений на той же системе.
-   **Риск:** Если процессы внезапно начнут использовать ранее зарезервированную память, физическая память может закончиться. Это приведет к вызову **OOM Killer**, который принудительно завершит один или несколько процессов для освобождения ресурсов.

### Режимы работы

Поведение этого механизма регулируется параметром `vm.overcommit_memory`:

-   `0` (Heuristic overcommit handling, по умолчанию): Ядро использует эвристику для оценки, достаточно ли памяти. Очевидно "жадные" запросы, которые могут привести к переполнению, отклоняются.
-   `1` (Always overcommit): Ядро всегда разрешает выделение памяти, каким бы большим ни был запрос. Этот режим может быть полезен для некоторых научных вычислений, но повышает риск вызова OOM Killer.
-   `2` (Don't overcommit): Ядро строго запрещает выделять больше виртуальной памяти, чем доступно (`SwapTotal + (RAM * vm.overcommit_ratio / 100)`). `vm.overcommit_ratio` — это процент RAM, который можно выделить сверх swap (по умолчанию 50%). Этот режим полезен для служб, где стабильность важнее эффективности использования памяти (например, для баз данных).

Настройка производится через `sysctl`:
```bash
sudo sysctl -w vm.overcommit_memory=1
```

## Оптимизация памяти: Kernel Samepage Merging (KSM)

**KSM (Kernel Samepage Merging)** — это фоновый процесс в ядре, который сканирует память и ищет идентичные страницы. Если он находит две или более одинаковые страницы, он объединяет их в одну, помечая её как "copy-on-write" (CoW).

**Как это работает:**
1.  KSM объединяет одинаковые страницы в одну физическую страницу.
2.  Если какой-либо процесс пытается изменить эту страницу, ядро автоматически создает для него копию, и только после этого процесс вносит изменения.

**Где используется:**
-   **Системы виртуализации (KVM, QEMU):** Для дедупликации памяти между множеством однотипных гостевых ОС.
-   **Контейнерные среды:** Для экономии памяти при запуске большого количества одинаковых контейнеров.

**Плюсы и минусы:**
-   **Плюс:** Значительно сокращает потребление RAM в средах с высокой степенью дублирования данных.
-   **Минус:** Потребляет ресурсы CPU на постоянное сканирование памяти и может вызывать небольшие задержки при первой записи в "объединенную" страницу из-за необходимости выполнить операцию Copy-on-Write.

KSM управляется через файлы в `/sys/kernel/mm/ksm/`.

## Оптимизация для архитектуры NUMA

**NUMA (Non-Uniform Memory Access)** — это архитектура построения памяти, используемая в многопроцессорных системах. В ней память физически разделена на "узлы" (nodes), и каждый процессор (или группа ядер) имеет быстрый локальный доступ к своему узлу памяти, но более медленный доступ к памяти других узлов.

**Проблема:** Если процесс, выполняющийся на одном процессоре, постоянно обращается к памяти, расположенной на другом узле, возникают задержки, снижающие производительность.

**Оптимизация:**
Основная стратегия — обеспечить **локальность NUMA**, то есть сделать так, чтобы процесс и память, с которой он работает, находились на одном и том же узле.

-   **`numactl`**: Это основная утилита для управления политиками NUMA. Она позволяет принудительно запускать процесс на определённом узле и выделять ему память только из этого узла.
    ```bash
    # Запустить процесс my_app на узле 0 и выделять ему память только оттуда
    numactl --cpunodebind=0 --membind=0 my_app
    ```

## Использование HugePages

**HugePages** — это страницы памяти большого размера (обычно 2 МБ или 1 ГБ вместо стандартных 4 КБ). Их использование позволяет сократить накладные расходы на управление памятью.

**Преимущества:**
-   **Снижение нагрузки на TLB (Translation Lookaside Buffer):** TLB — это кэш процессора для трансляции виртуальных адресов в физические. Использование меньшего количества больших страниц вместо огромного количества маленьких снижает вероятность промахов в TLB, ускоряя доступ к памяти.
-   **Уменьшение размера таблиц страниц:** Требуется меньше записей для отображения того же объёма памяти.

**Применение:**
HugePages особенно полезны для приложений, работающих с большими объёмами непрерывной памяти, таких как базы данных (Oracle, PostgreSQL) и системы виртуализации (KVM).

**Активация:**
Количество HugePages настраивается через параметр ядра:
```bash
# Выделить 1024 страницы по 2 МБ (всего 2 ГБ)
sudo sysctl -w vm.nr_hugepages=1024
```

## Transparent Huge Pages (THP)

**Transparent Huge Pages (THP)** — это механизм ядра Linux, который работает в фоновом режиме и пытается автоматически объединять обычные страницы памяти (4 КБ) в "огромные" страницы (2 МБ). Цель та же, что и у `HugePages` — снизить накладные расходы на управление памятью и ускорить доступ за счет более эффективного использования TLB.

Ключевое слово здесь — **"прозрачный" (Transparent)**. В отличие от стандартных `HugePages`, которые требуют ручной настройки и резервирования, THP работает автоматически без необходимости внесения изменений в код приложений.

### Как это работает

Ядро постоянно сканирует память и, если находит смежные 4-килобайтные страницы, которые можно объединить в одну 2-мегабайтную, выполняет их слияние (defrag/compaction).

### THP vs HugePages (HugeTLB)

| Характеристика | Transparent Huge Pages (THP) | Standard HugePages (HugeTLB) |
| :--- | :--- | :--- |
| **Управление** | **Автоматическое.** Ядро само решает, когда объединять страницы. | **Ручное.** Администратор должен заранее зарезервировать пул страниц. |
| **Прозрачность** | **Да.** Приложения не знают, что работают с большими страницами. | **Нет.** Приложения должны быть модифицированы для использования `hugetlbfs`. |
| **Гибкость** | Высокая. Страницы могут быть динамически разделены обратно на 4 КБ. | Низкая. Память резервируется и не может быть использована для других нужд. |
| **Производительность** | Может вызывать **непредсказуемые задержки** из-за фоновой работы по слиянию и дефрагментации памяти. | Обеспечивает **предсказуемую высокую производительность**, так как страницы выделяются сразу. |

### Проблемы и рекомендации

Несмотря на кажущееся удобство, автоматическое поведение THP часто создает проблемы для высокопроизводительных приложений, особенно для баз данных (MongoDB, Redis, Oracle и др.). Процесс дефрагментации (`kcompactd`) может блокировать доступ к памяти, вызывая короткие, но критичные "зависания" (latency spikes).

**Поэтому для многих серверных нагрузок рекомендуется отключать THP.**

### Управление THP

-   **Проверить текущий режим:**
    ```bash
    cat /sys/kernel/mm/transparent_hugepage/enabled
    # [always] madvise never
    ```
    -   `always`: THP включен для всех процессов.
    -   `madvise`: THP включен только для процессов, которые явно запросили это через системный вызов `madvise()`.
    -   `never`: THP полностью отключен.

-   **Отключить THP (временно, до перезагрузки):**
    ```bash
    echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
    echo never | sudo tee /sys/kernel/mm/transparent_hugepage/defrag
    ```

Для постоянного отключения необходимо добавить эти команды в стартовый скрипт (например, `/etc/rc.local`) или использовать параметры загрузки ядра (`transparent_hugepage=never`).

### Параметр ядра `vfs_cache_pressure`

Этот параметр контролирует, насколько агрессивно ядро будет освобождать память, используемую для кэширования **dentry** (записи каталогов) и **inode** (метаданные файлов).

-   **Значение по умолчанию: `100`**. Ядро быстро освобождает кэш inode/dentry.
-   **Низкое значение (например, `50`):** Ядро будет дольше хранить этот кэш в памяти. Это может ускорить доступ к файлам на системах с большим количеством файлов, но увеличит риск нехватки памяти для процессов.
-   **Высокое значение (более `100`):** Ядро будет очень агрессивно очищать кэш метаданных.

Настройка производится аналогично `swappiness` через `sysctl`:
```bash
sudo sysctl -w vm.vfs_cache_pressure=50
```
