# Resource Limits Concepts

## Определения

**Лимиты ресурсов (Resource Limits)** — ограничения на потребление системных ресурсов (CPU, память, файловые дескрипторы, процессы), устанавливаемые для пользователя или процесса. Предотвращают исчерпание ресурсов одним процессом или пользователем.

**Soft Limit (мягкий лимит)** — текущее действующее ограничение. Пользователь может увеличивать его до значения hard limit.

**Hard Limit (жесткий лимит)** — верхняя граница, до которой можно увеличить soft limit. Повышать hard limit может только `root`.

**OOM Killer** — механизм ядра Linux, принудительно завершающий процессы при нехватке RAM для предотвращения отказа системы.

**Fork Bomb** — атака типа "отказ в обслуживании", при которой процесс экспоненциально создает копии, исчерпывая лимиты процессов.

## Основные концепции

### Типы лимитов

| Лимит | Флаг `ulimit` | Описание | Единицы |
| :--- | :--- | :--- | :--- |
| **Открытые файлы** | `-n` | Максимальное количество открытых файловых дескрипторов | файлы |
| **Процессы** | `-u` | Максимальное количество процессов/потоков пользователя | процессы |
| **Виртуальная память** | `-v` | Максимальный объем виртуальной памяти | KB |
| **Размер памяти (RSS)** | `-m` | Максимальный размер резидентной памяти | KB |
| **Core-файл** | `-c` | Максимальный размер core-дампа (0 = отключено) | KB |
| **Время CPU** | `-t` | Максимальное процессорное время | секунды |
| **Размер файла** | `-f` | Максимальный размер создаваемого файла | блоки (512 байт) |
| **Размер сегмента данных** | `-d` | Максимальный размер heap | KB |
| **Размер стека** | `-s` | Размер стека потока | KB |
| **Блокировка памяти** | `-l` | Объём памяти, который можно заблокировать в RAM (не свопить) | KB |
| **Ожидающие сигналы** | `-i` | Максимальное количество ожидающих сигналов | сигналы |
| **Приоритет планирования** | `-e` | Приоритет планирования процессов | nice |
| **Real-time приоритет** | `-r` | Приоритет real-time процессов | приоритет |
| **Real-time время** | `-R` | Лимит времени real-time задач без блокировок | мкс |
| **POSIX очереди** | `-q` | Максимальный размер очереди сообщений | байты |
| **Размер pipe** | `-p` | Размер буфера канала | блоки (512 байт) |
| **Файловые блокировки** | `-x` | Количество файловых блокировок | блокировки |

### Иерархия применения лимитов

В современных системах существует несколько уровней управления ресурсами. Лимиты применяются от наиболее строгих к наименее строгим:

```
┌─────────────────────────────────────────┐
│         cgroups v2 (контейнеры)         │  ← Самые строгие лимиты
│         memory.max, pids.max            │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│         systemd (сервисы)               │  ← Приоритет для демонов
│         LimitNOFILE, LimitNPROC         │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│    PAM / limits.conf (пользователи)     │  ← Для пользовательских сессий
│    * soft nofile 65536                  │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│         ulimit (текущая сессия)         │  ← Временные лимиты
│         ulimit -n 4096                  │
└─────────────────────────────────────────┘
```

**Порядок применения (от высшего к низшему):**

1. **cgroups v2** — самые строгие лимиты для контейнеров (`memory.max`, `pids.max`, `cpu.max`)
2. **systemd директивы** — для сервисов (`LimitNOFILE`, `LimitNPROC`, `LimitCORE`)
3. **PAM / limits.conf** — для пользовательских сессий, аутентифицирующихся через PAM (SSH, GUI)
4. **ulimit** — временные лимиты текущей сессии shell

> **Важно:** В современных системах `systemd` — основной и наиболее надежный механизм управления ресурсами для сервисов. Настройки `limits.conf` не влияют на системные сервисы, управляемые `systemd`.

### Механизмы установки лимитов

#### systemd (предпочтительный для сервисов)

Лимиты устанавливаются в юнит-файле сервиса. systemd применяет их напрямую через `setrlimit()`, минуя PAM.

```ini
# /etc/systemd/system/my-app.service
[Service]
LimitNOFILE=65536      # Лимит на количество открытых файлов
LimitNPROC=2048        # Лимит на количество процессов
LimitCORE=infinity     # Лимит на размер core-файла
LimitAS=8G             # Лимит на адресное пространство
OOMScoreAdjust=-1000   # Защита от OOM Killer
```

После изменения:

```bash
sudo systemctl daemon-reload && sudo systemctl restart my-app
```

Глобальные настройки для всех сервисов задаются в `/etc/systemd/system.conf`. Подробнее: [**Persistent Limits Configuration**](./persistent_limits_configuration.md).

#### PAM / limits.conf (для пользовательских сессий)

```bash
# /etc/security/limits.conf
# <domain>  <type>  <item>    <value>
# ------------------------------------
*           soft    nofile    65536
*           hard    nofile    131072
student     hard    nproc     1024
@usergroup  hard    as        2048000  # Виртуальная память (KB)
```

> **Важно:** Для применения изменений пользователь должен перезайти в систему (logout/login). Файл обрабатывается модулем `pam_limits.so`.

#### ulimit (временные лимиты)

Команда `ulimit` управляет лимитами для **текущей сессии оболочки**. Подробный справочник по `ulimit` и практические примеры — в [**Ulimit Usage**](./ulimit_usage.md).

```bash
# Просмотр всех лимитов
ulimit -a

# Просмотр и установка лимита на открытые файлы
ulimit -n           # посмотреть
ulimit -n 4096      # установить

# Защита от Fork Bomb
ulimit -u 1024

# Ограничение виртуальной памяти для процесса (в KB)
ulimit -v 2048000
```

> **Важно:** Изменения `ulimit` действуют только для текущей сессии и дочерних процессов.

## Практические сценарии

### Диагностика лимитов процесса

```bash
# Просмотр лимитов работающего процесса
cat /proc/<PID>/limits

# Проверка лимита на открытые файлы
grep "Max open files" /proc/<PID>/limits

# Проверка текущих лимитов сессии
ulimit -a
```

### Ограничение использования памяти

Для ограничения потребления памяти процессом можно использовать несколько уровней контроля:

1. **`ulimit` (для текущей сессии):**
   - `-v` (Virtual Memory): ограничивает весь объем виртуальной памяти.
   - `-m` (RSS): ограничивает объем физической памяти (на современных ядрах Linux часто игнорируется в пользу cgroups).

   ```bash
   # Ограничить виртуальную память до 500 МБ для запускаемой команды
   ulimit -v 512000
   ./memory_hungry_app
   ```

2. **`systemd` (для сервисов):**
   - `MemoryMax` и `MemoryHigh` — современные директивы, использующие cgroups v2.

   ```ini
   [Service]
   MemoryMax=1G
   ```

3. **`cgroups` (наиболее надежный метод):**
   - Позволяет жестко ограничить ресурсы для группы процессов. В cgroups v2 это файл `memory.max`.

### Защита от Fork Bomb

```bash
# Временная защита (текущая сессия)
ulimit -u 1024

# Постоянная защита (/etc/security/limits.conf)
* hard nproc 4096
```

### Сервис с повышенными лимитами

```ini
# /etc/systemd/system/nginx.service.d/override.conf
[Service]
LimitNOFILE=131072
LimitNPROC=8192
```

```bash
sudo systemctl daemon-reload && sudo systemctl restart nginx
```

### Проверка применения лимитов

```bash
# Проверить лимиты процесса systemd-сервиса
systemctl show my-app.service | grep LimitNOFILE

# Проверить фактические лимиты процесса
cat /proc/$(pgrep -f my-app)/limits | grep "Max open files"
```

## Дополнительная информация

### Взаимодействие лимитов

- **cgroups v2** — самые строгие ограничения. Если `memory.max` в cgroup установлен ниже, чем любой другой лимит (systemd, limits.conf, ulimit), процесс будет ограничен cgroup.
- **systemd** создаёт cgroup для каждого сервиса. Директивы `Limit...` применяются через `setrlimit()`, а не через PAM.
- **OOM Killer** в контейнерах действует в пределах cgroup memory лимитов — при исчерпании памяти cgroup OOM Killer завершит процесс внутри контейнера, не затрагивая хост.
- **ulimit** может уменьшать soft limit без привилегий, но увеличивать — только до hard limit. Повышение hard limit требует `root`.

### QoS и приоритизация при нехватке ресурсов

Лимиты влияют на поведение OOM Killer и планировщика:

- Процессы с `OOMScoreAdjust=-1000` защищены от OOM Killer (наиболее важная настройка)
- Процессы с `OOMScoreAdjust=1000` убиваются первыми
- В контейнерах OOM Killer действует в пределах cgroup memory лимитов

### Историческая справка

- **System V IPC** лимиты (`msgget`, `semget`, `shmget`) управляются отдельно через `/proc/sys/kernel/` параметры
- **POSIX IPC** использует `/dev/shm` и `/dev/mqueue` с правами файловой системы
- **cgroups v1** устарел; **cgroups v2** (unified hierarchy) — современный стандарт (ядро 4.5+, 2016).

Подробнее об иерархии применения лимитов см. в [**Limits Hierarchy**](./limits_hierarchy.md). Механизм OOM Killer описан в [**OOM Killer Mechanism**](./oom_killer_mechanism.md).
