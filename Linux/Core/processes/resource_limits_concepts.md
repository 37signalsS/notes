# Концепции лимитов ресурсов в Linux

## Определения

**Лимиты ресурсов (Resource Limits / rlimits)** — механизм ядра Linux для гранулярного ограничения потребления системных ресурсов (процессорное время, память, дескрипторы) на уровне отдельных процессов. Это критически важный компонент системной безопасности и стабильности, защищающий от монополизации ресурсов и DoS-атак.

**Мягкий лимит (Soft Limit):** Действующее ограничение. При его достижении ядро отправляет процессу сигнал (например, `SIGXCPU` при превышении времени CPU) или возвращает ошибку системного вызова (например, `EMFILE` при `open()`). Процесс может самостоятельно увеличивать мягкий лимит до значения жесткого.

**Жесткий лимит (Hard Limit):** Абсолютный потолок для мягкого лимита. Только привилегированный пользователь (с capability `CAP_SYS_RESOURCE`) может повышать жесткий лимит. Обычный процесс может только понижать его (действие необратимо для данной инкарнации процесса).

**rlimit syscalls:** Группа системных вызовов (`getrlimit`, `setrlimit` и современный `prlimit`), через которые ядро управляет этими параметрами.

## Основные концепции

### Типы лимитов (rlimit_resource)

| Ресурс | Флаг ulimit | Техническое имя | Описание и технические нюансы | Единицы |
| :--- | :--- | :--- | :--- | :--- |
| **Открытые файлы** | `-n` | `RLIMIT_NOFILE` | Максимум файловых дескрипторов. Ограничен сверху параметром `fs.nr_open`. Включает сокеты и пайпы. | файлы |
| **Процессы** | `-u` | `RLIMIT_NPROC` | Лимит на количество задач (потоков) для **всего UID** пользователя. Новые `fork()` вернут `EAGAIN`. | задачи |
| **Виртуальная память**| `-v` | `RLIMIT_AS` | Лимит на общее адресное пространство (Address Space). Влияет на `mmap` и `brk`. | KB |
| **Резидентная память**| `-m` | `RLIMIT_RSS` | **Устарело.** В современных ядрах (2.6+) не имеет эффекта. Заменено на лимиты памяти в cgroups. | KB |
| **Время CPU** | `-t` | `RLIMIT_CPU` | Суммарное время CPU. При достижении шлется `SIGXCPU` (мягкий), затем `SIGKILL` (жесткий). | сек. |
| **Блокировка памяти** | `-l` | `RLIMIT_MEMLOCK` | Объём памяти, фиксируемый в RAM через `mlock()`. Предотвращает вытеснение в Swap. | KB |
| **RT Timeout** | Нет | `RLIMIT_RTTIME` | Лимит времени непрерывного выполнения в Real-Time режиме (`SCHED_FIFO`/`RR`) без блокирующего вызова. | мкс. |
| **Размер стека** | `-s` | `RLIMIT_STACK` | Максимальный размер стека потока. Превышение вызывает `SIGSEGV`. | KB |
| **Core-дампы** | `-c` | `RLIMIT_CORE` | Максимальный размер файла снимка памяти (0 — дампы отключены). | KB |
| **Размер файла** | `-f` | `RLIMIT_FSIZE` | Максимальный размер создаваемого/расширяемого файла. Превышение вызывает `SIGXFSZ`. | блоки |
| **Сигналы** | `-i` | `RLIMIT_SIGPENDING` | Максимальное количество сигналов, стоящих в очереди для данного UID. | сигналы |
| **Приоритет nice** | `-e` | `RLIMIT_NICE` | Максимальный приоритет (nice value), который процесс может установить (диапазон 20...-20). | nice |
| **RT Приоритет** | `-r` | `RLIMIT_RTPRIO` | Максимальный приоритет реального времени, который может быть установлен через `sched_setscheduler`. | приор. |
| **POSIX очереди** | `-q` | `RLIMIT_MSGQUEUE` | Лимит памяти для POSIX очередей сообщений (mqueue) для данного UID. | байты |

### Иерархия и приоритеты применения

Лимиты применяются в порядке от наиболее строгих к наименее строгим. Механизм с более высоким приоритетом в списке (более низким уровнем в ОС) всегда имеет преимущество.

```
┌───────────────────────────────────────────┐
│ Глобальные лимиты ядра (sysctl)           │ ← Приоритет 1 (fs.nr_open, fs.file-max)
└───────────────────────────────────────────┘
                    ↓
┌───────────────────────────────────────────┐
│ Контрольные группы (cgroups v2)           │ ← Приоритет 2 (memory.max, pids.max)
└───────────────────────────────────────────┘
                    ↓
┌───────────────────────────────────────────┐
│ Системные сервисы (systemd)               │ ← Приоритет 3 (LimitNOFILE=...)
└───────────────────────────────────────────┘
                    ↓
┌───────────────────────────────────────────┐
│ PAM / limits.conf (пользователи)          │ ← Приоритет 4 (SSH/Login сессии)
└───────────────────────────────────────────┘
                    ↓
┌───────────────────────────────────────────┐
│ ulimit (текущая сессия)                   │ ← Приоритет 5 (Временный)
└───────────────────────────────────────────┘
```

**Ключевые правила взаимодействия:**
- **rlimits vs Cgroups:** Лимиты `ulimit` (rlimits) работают параллельно с `cgroups`. Если cgroup ограничивает память (`memory.max`) до 100MB, а `RLIMIT_AS` установлен в 1GB, процесс упадет по OOM при достижении 100MB.
- **Изоляция systemd:** Настройки из `limits.conf` (PAM) **не влияют** на системные сервисы. Для них используются только директивы `Limit*=` в юнит-файлах.
- **UID-лимиты:** Некоторые rlimits (`NPROC`, `SIGPENDING`) суммируются по всем процессам пользователя (UID), а не по отдельному PID.

## Практические сценарии

### Диагностика: Три уровня для ошибки EMFILE

При возникновении ошибки `Too many open files` (код `EMFILE`) необходимо проверить три уровня ограничений:

1.  **Лимит процесса (rlimit):** Проверяется ядром при каждом `open()`. 
    *   Просмотр: `cat /proc/<PID>/limits | grep "Max open files"`.
2.  **Потолок ядра для процесса (`fs.nr_open`):** Абсолютная верхняя граница, выше которой нельзя поднять `RLIMIT_NOFILE` даже через root.
    *   Просмотр: `sysctl fs.nr_open`.
3.  **Общесистемный лимит (`fs.file-max`):** Общее количество дескрипторов всеми процессами на хосте. 
    *   Просмотр: `sysctl fs.file-max`.

**Решение:** Если вы установили `ulimit -n 2000000`, но он не применяется, скорее всего, он упирается в `fs.nr_open` (по умолчанию ~1.04 млн).

### Предотвращение Fork Bomb

Используются два дополняющих механизма:
- **`RLIMIT_NPROC`**: Традиционный метод. Ограничивает количество задач для всего UID. Опасно тем, что один "бешеный" сервис может лишить лимита все остальные сервисы того же пользователя (например, `www-data`).
- **`pids.max` (cgroups)**: Современный метод. Ограничивает количество задач именно в рамках конкретной cgroup (сервиса или контейнера), не затрагивая других. В systemd настраивается через `TasksMax=`.

### Особенности RLIMIT_MEMLOCK

Критичен для приложений, работающих с памятью напрямую (DPDK, базы данных с HugePages, криптография):
- Если лимит слишком мал, `mlock()` или `mmap(MAP_LOCKED)` вернут `ENOMEM`.
- Это часто является причиной сбоев при запуске **HashiCorp Vault** или **Oracle DB**, которые пытаются защитить ключи/память от попадания в Swap.

## Дополнительная информация

### Технические нюансы и подводные камни

1.  **Наследование:** Лимиты наследуются через `fork()`. При `execve()` лимиты сохраняются, что позволяет оболочке настраивать окружение перед запуском приложения.
2.  **Capabilities:** Для повышения жесткого лимита (Hard Limit) процессу необходима привилегия **`CAP_SYS_RESOURCE`**. Понижать жесткий лимит может любой процесс, но это действие необратимо.
3.  **prlimit(2):** Универсальный системный вызов (введен в Linux 2.6.36). Позволяет:
    - Считывать и устанавливать лимиты атомарно.
    - Управлять лимитами *другого* процесса по его PID (при наличии прав `CAP_SYS_RESOURCE` или совпадении UID).
