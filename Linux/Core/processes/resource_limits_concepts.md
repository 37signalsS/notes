# Концепции лимитов ресурсов

## Определения

**Лимиты ресурсов (Resource Limits)** — ограничения на потребление системных ресурсов (CPU, память, файловые дескрипторы, процессы), устанавливаемые для пользователя или процесса. Предотвращают исчерпание ресурсов одним процессом или пользователем (проблема Noisy Neighbor).

**Soft Limit (мягкий лимит)** — текущее действующее ограничение. Пользователь может увеличивать его до значения hard limit самостоятельно.

**Hard Limit (жесткий лимит)** — верхняя граница, до которой можно увеличить soft limit. Повышать hard limit может только привилегированный пользователь (`root`).

**OOM Killer (Out-Of-Memory Killer)** — механизм ядра Linux, принудительно завершающий процессы при критической нехватке RAM для предотвращения краха всей системы.

**Fork Bomb** — тип атаки или программной ошибки, при которой процесс бесконечно создает свои копии, исчерпывая лимиты на количество процессов и вызывая отказ в обслуживании.

## Основные концепции

### Типы лимитов

| Лимит | Флаг `ulimit` | Описание | Единицы |
| :--- | :--- | :--- | :--- |
| **Открытые файлы** | `-n` | Максимальное количество открытых файловых дескрипторов (nofile) | файлы |
| **Процессы** | `-u` | Максимальное количество процессов/потоков пользователя (nproc) | процессы |
| **Виртуальная память** | `-v` | Максимальный объем адресного пространства (as/address space) | KB |
| **Размер памяти (RSS)** | `-m` | Максимальный размер резидентной памяти (часто игнорируется в пользу cgroups) | KB |
| **Core-файл** | `-c` | Максимальный размер core-дампа (0 = отключено) | KB |
| **Время CPU** | `-t` | Суммарное процессорное время | секунды |
| **Размер файла** | `-f` | Максимальный размер создаваемого файла | блоки (512 байт) |
| **Размер сегмента данных** | `-d` | Максимальный размер heap процесса | KB |
| **Размер стека** | `-s` | Размер стека потока | KB |
| **Блокировка памяти** | `-l` | Объём памяти, который можно заблокировать в RAM (mlock) | KB |
| **Ожидающие сигналы** | `-i` | Максимальное количество сигналов в очереди | сигналы |
| **Приоритет планирования** | `-e` | Максимальный приоритет nice | nice |
| **Real-time приоритет** | `-r` | Приоритет реального времени | приоритет |

### Иерархия применения лимитов

Лимиты применяются в порядке от наиболее строгих к наименее строгим. Механизм с более высоким приоритетом (верхним в списке) всегда имеет преимущество.

```
┌─────────────────────────────────────────┐
│         cgroups v2 (контейнеры)         │  ← Приоритет 1 (Абсолютный)
│         memory.max, pids.max            │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│         systemd (сервисы)               │  ← Приоритет 2
│         LimitNOFILE, LimitNPROC         │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│    PAM / limits.conf (пользователи)     │  ← Приоритет 3
│    * soft nofile 65536                  │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│         ulimit (текущая сессия)         │  ← Приоритет 4 (Временный)
│         ulimit -n 4096                  │
└─────────────────────────────────────────┘
```

**Ключевые правила:**

- **Абсолютный приоритет cgroups:** Если cgroup ограничивает память до 1GB, никакой `ulimit` или настройки systemd не позволят процессу использовать больше.
- **Изоляция systemd:** Настройки из `limits.conf` (PAM) **не влияют** на системные сервисы. Для них используются только директивы в юнит-файлах.
- **Временный характер ulimit:** Действует только в рамках текущей сессии shell и её дочерних процессов.

### Механизмы установки лимитов

#### systemd (для системных служб)

Лимиты устанавливаются напрямую через системный вызов `setrlimit()` при запуске процесса.
Подробнее: [**Persistent Limits Configuration**](./persistent_limits_configuration.md).

```ini
# /etc/systemd/system/my-app.service
[Service]
LimitNOFILE=65536      # Максимум открытых файлов
LimitNPROC=2048        # Максимум процессов
OOMScoreAdjust=-1000   # Защита от OOM Killer
```

#### PAM / limits.conf (для сессий пользователей)

Используется модулем `pam_limits.so` при входе пользователя (SSH, GUI, login).

```bash
# /etc/security/limits.conf
*           soft    nofile    65536
*           hard    nofile    131072
student     hard    nproc     1024
```

#### ulimit (для текущей сессии)

Встроенная команда оболочки для оперативного управления лимитами.
Подробнее: [**Ulimit Usage**](./ulimit_usage.md).

## Практические сценарии

### Диагностика лимитов процесса

```bash
# Просмотр лимитов работающего процесса (ядро Linux)
cat /proc/<PID>/limits

# Проверка конкретного параметра (например, Max open files)
grep "Max open files" /proc/<PID>/limits
```

### Ограничение использования памяти

1. **systemd (MemoryMax):** Использует cgroups v2 для жесткого ограничения.

   ```ini
   [Service]
   MemoryMax=1G
   ```

2. **ulimit (-v):** Ограничивает виртуальную память (Address Space).

   ```bash
   ulimit -v 512000
   ./app
   ```

### Защита от Fork Bomb

Для предотвращения исчерпания ресурсов новыми процессами:

```bash
# В limits.conf
* hard nproc 4096

# В сессии
ulimit -u 1024
```

### Проверка применения в иерархии

```bash
# 1. Лимиты systemd
systemctl show my-app.service | grep LimitNOFILE

# 2. Лимиты cgroups (v2)
cat /sys/fs/cgroup/system.slice/my-app.service/memory.max

# 3. Глобальный лимит ядра
cat /proc/sys/fs/file-max
```

## Дополнительная информация

### Взаимодействие лимитов

- **cgroups v2** — современный стандарт управления ресурсами (ядро 4.5+). Позволяет ограничивать не только количество, но и интенсивность (например, IOPS или полосу пропускания CPU).
- **OOM Score** — значение от -1000 до 1000, определяющее приоритет процесса для OOM Killer. Процессы с -1000 (например, sshd, systemd) защищены от завершения.
- **cgroup pids.max** — ограничивает количество процессов/потоков в cgroup. Утечка потоков (горутины, не завершающиеся под нагрузкой) упрётся в этот лимит раньше, чем в nofile. Проверка: `cat /sys/fs/cgroup/pids.max`.
- **Три лимита для EMFILE:** При ошибке `Too many open files` (EMFILE) срабатывает самое строгое из трёх ограничений:
  - Soft limit процесса (`RLIMIT_NOFILE`) — проверяется при каждом `open()`. Процесс может повысить до hard limit.
  - `fs.nr_open` (kernel per-process ceiling) — абсолютный потолок, выше которого нельзя поднять soft limit ни одному процессу. Проверка: `sysctl fs.nr_open`.
  - `fs.file-max` (system-wide) — общий лимит на все процессы. Релевантен только на сильно загруженных хостах.
  
  **Ключевой момент:** `fs.nr_open` часто забывают. Даже при высоких `ulimit -n` и `fs.file-max` процесс не сможет открыть больше `fs.nr_open` дескрипторов. Для постоянного увеличения:
  ```bash
  sysctl -w fs.nr_open=2097152
  sysctl -w fs.file-max=2097152
  ```
