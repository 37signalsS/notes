# Концепции лимитов ресурсов в Linux

## Определения

**Лимиты ресурсов (Resource Limits / rlimits)** — механизм ядра Linux, предназначенный для ограничения потребления системных ресурсов (процессорное время, память, дескрипторы) на уровне отдельных процессов. Это фундаментальный уровень защиты от монополизации ресурсов и атак типа "отказ в обслуживании" (DoS).

**Мягкий лимит (Soft Limit):** Текущее действующее ограничение. При его достижении ядро отправляет процессу сигнал (например, `SIGXCPU`) или возвращает ошибку системного вызова (например, `EMFILE`). Процесс может самостоятельно увеличивать мягкий лимит до значения жесткого.

**Жесткий лимит (Hard Limit):** Абсолютный потолок для мягкого лимита. Только привилегированный пользователь (с capability `CAP_SYS_RESOURCE`) может повышать жесткий лимит.

**rlimit syscalls:** Группа системных вызовов (`getrlimit`, `setrlimit` и современный `prlimit`), через которые ядро управляет этими параметрами.

## Основные концепции

### Типы лимитов (rlimit_resource)

| Ресурс | Флаг ulimit | Техническое имя | Описание и технические нюансы | Единицы |
| :--- | :--- | :--- | :--- | :--- |
| **Открытые файлы** | `-n` | `RLIMIT_NOFILE` | Максимум файловых дескрипторов. Ограничен сверху параметром `fs.nr_open`. | файлы |
| **Процессы** | `-u` | `RLIMIT_NPROC` | Лимит на количество процессов/потоков для данного UID пользователя. | задачи |
| **Виртуальная память**| `-v` | `RLIMIT_AS` | Лимит на общее адресное пространство (Address Space) процесса. | KB |
| **Резидентная память**| `-m` | `RLIMIT_RSS` | **Устарело.** В современных ядрах практически не имеет эффекта, заменено на лимиты cgroups. | KB |
| **Время CPU** | `-t` | `RLIMIT_CPU` | Суммарное время использования CPU. При достижении шлется `SIGXCPU`, затем `SIGKILL`. | сек. |
| **Блокировка памяти** | `-l` | `RLIMIT_MEMLOCK` | Объём памяти, фиксируемый в RAM через `mlock()`. Критично для баз данных и криптографии. | KB |
| **RT Timeout** | Нет | `RLIMIT_RTTIME` | Лимит времени непрерывного выполнения в Real-Time режиме без блокирующего вызова. | мкс. |
| **Размер стека** | `-s` | `RLIMIT_STACK` | Максимальный размер стека потока выполнения. | KB |
| **Core-дампы** | `-c` | `RLIMIT_CORE` | Максимальный размер файла снимка памяти (0 — отключено). | KB |
| **Размер файла** | `-f` | `RLIMIT_FSIZE` | Максимальный размер создаваемого или расширяемого файла. | блоки |
| **Сигналы** | `-i` | `RLIMIT_SIGPENDING` | Максимальное количество сигналов, стоящих в очереди для данного UID. | сигналы |
| **Приоритет nice** | `-e` | `RLIMIT_NICE` | Максимальный приоритет (nice value), который процесс может установить. | nice |
| **RT Приоритет** | `-r` | `RLIMIT_RTPRIO` | Максимальный приоритет реального времени. | приор. |

### Иерархия и приоритеты применения

Лимиты применяются в порядке от наиболее строгих к наименее строгим. Механизм с более высоким приоритетом в списке (более низким уровнем в ОС) всегда имеет преимущество.

```
┌───────────────────────────────────────────┐
│ Глобальные лимиты ядра (sysctl)           │ ← Приоритет 1 (fs.nr_open, fs.file-max)
└───────────────────────────────────────────┘
                    ↓
┌───────────────────────────────────────────┐
│ Контрольные группы (cgroups v2)           │ ← Приоритет 2 (memory.max, pids.max)
└───────────────────────────────────────────┘
                    ↓
┌───────────────────────────────────────────┐
│ Системные сервисы (systemd)               │ ← Приоритет 3 (LimitNOFILE=...)
└───────────────────────────────────────────┘
                    ↓
┌───────────────────────────────────────────┐
│ PAM / limits.conf (пользователи)          │ ← Приоритет 4 (SSH/Login сессии)
└───────────────────────────────────────────┘
                    ↓
┌───────────────────────────────────────────┐
│ ulimit (текущая сессия)                   │ ← Приоритет 5 (Временный)
└───────────────────────────────────────────┘
```

**Ключевые правила взаимодействия:**
- **Иерархия cgroups:** Если cgroup ограничивает память до 1GB, никакие настройки `ulimit` или systemd не позволят процессу использовать больше.
- **Изоляция systemd:** Настройки из `limits.conf` (PAM) **не влияют** на системные сервисы. Для них используются только директивы в юнит-файлах.

## Практические сценарии

### Диагностика: Три потолка для ошибки EMFILE

При возникновении ошибки `Too many open files` необходимо проверить три уровня ограничений в следующем порядке:

1.  **Лимит процесса (rlimit):** Проверяется ядром при каждом `open()`. 
    *   Просмотр: `cat /proc/<PID>/limits | grep "Max open files"`.
2.  **Потолок ядра для одного процесса (`fs.nr_open`):** Абсолютная верхняя граница, выше которой нельзя поднять `RLIMIT_NOFILE` (даже через `ulimit -n`). 
    *   Просмотр: `sysctl fs.nr_open`.
3.  **Общесистемный лимит (`fs.file-max`):** Общее количество открытых дескрипторов всеми процессами на хосте. 
    *   Просмотр: `sysctl fs.file-max`.

**Решение:** Если вы установили `ulimit -n 2000000`, но он не применяется, скорее всего, он упирается в `fs.nr_open` (по умолчанию ~1.04 млн).
```bash
# Увеличение потолков ядра
sysctl -w fs.nr_open=2097152
sysctl -w fs.file-max=2097152
```

### Защита от Fork Bomb

Для предотвращения исчерпания ресурсов новыми процессами используются два механизма:
- **`RLIMIT_NPROC`**: Ограничивает количество задач для **всего UID**. Один пользователь может исчерпать лимит всех своих сервисов одновременно.
- **`pids.max` (cgroups)**: Современный и более точный метод, ограничивающий количество задач именно в рамках сервиса или контейнера.
    *   В systemd: `TasksMax=1024`.

### Диагностика лимитов живого процесса

SRE-специалисты используют `/proc` как единственный достоверный источник:
```bash
# Просмотр всех действующих rlimits
cat /proc/<PID>/limits

# Проверка реального использования дескрипторов
ls /proc/<PID>/fd | wc -l
```

## Дополнительная информация

### Технические нюансы и подводные камни

1.  **Наследование:** Лимиты наследуются через `fork()`. При `execve()` лимиты сохраняются.
2.  **Capabilities:** Для повышения жесткого лимита (Hard Limit) процессу необходима привилегия `CAP_SYS_RESOURCE`. Понижать жесткий лимит может любой процесс, но это действие необратимо для текущего процесса.
3.  **RLIMIT_MEMLOCK и безопасность:** Слишком высокий лимит позволяет злонамеренному процессу заблокировать всю физическую RAM (через `mlock`), вызвав отказ системы. Слишком низкий — не позволит запустить ПО, использующее `mlock` для защиты секретов (пароли, ключи) от попадания в Swap.
4.  **prlimit(2):** С версии ядра 2.6.36 доступен вызов `prlimit`, который позволяет как считывать, так и устанавливать лимиты для *другого* процесса по его PID.
