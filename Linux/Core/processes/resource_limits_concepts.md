# Концепции лимитов ресурсов в Linux

## Определения

**Лимиты ресурсов (Resource Limits / rlimits)** — механизм ядра Linux для гранулярного ограничения потребления системных ресурсов (процессорное время, память, дескрипторы, количество потоков) на уровне отдельных процессов или потоков. Это критически важный компонент системной безопасности и стабильности, защищающий от монополизации ресурсов и DoS-атак.

**Мягкий лимит (Soft Limit):** Действующее ограничение. При его достижении ядро отправляет процессу сигнал (например, `SIGXCPU` при превышении времени CPU) или возвращает ошибку системного вызова (например, `EMFILE` при `open()`). Процесс может самостоятельно увеличивать мягкий лимит до значения жесткого.

**Жесткий лимит (Hard Limit):** Абсолютный потолок для мягкого лимита. Только привилегированный пользователь (с capability `CAP_SYS_RESOURCE`) может повышать жесткий лимит. Обычный процесс может только понижать его (действие необратимо для данной инкарнации процесса).

**rlimit syscalls:** Группа системных вызовов (`getrlimit`, `setrlimit` и современный `prlimit`), через которые ядро управляет этими параметрами. Вызовы хранят пару значений `(soft, hard)` для каждого типа ресурса.

**pids.max (cgroups):** В контексте лимитов процессов важно различать rlimit `RLIMIT_NPROC` (ограничение на уровне UID) и cgroup `pids.max` (ограничение для конкретной группы процессов). В systemd оба механизма работают совместно через `TasksMax=`.

## Основные концепции

### Типы лимитов (rlimit_resource)

| Ресурс | Флаг ulimit | Техническое имя | Описание и технические нюансы | Единицы |
| :--- | :--- | :--- | :--- | :--- |
| **Открытые файлы** | `-n` | `RLIMIT_NOFILE` | Максимум файловых дескрипторов на процесс. Ограничен сверху параметром `fs.nr_open`. Включает сокеты, пайпы, fifo, epoll/kqueue инстансы. | файлы |
| **Процессы** | `-u` | `RLIMIT_NPROC` | Лимит на количество **задач (threads)** для **всего UID** пользователя. Новые `clone()`/`fork()`/`vfork()` вернут `EAGAIN`. В modern ядрах учитываются все потоки, включая главный. | задачи |
| **Виртуальная память**| `-v` | `RLIMIT_AS` | Лимит на общее адресное пространство (Address Space). Влияет на `mmap`, `brk`, `stack`. Взаимодействует с `vm.max_map_count`. При превышении `mmap` вернет `ENOMEM`. | KB |
| **Резидентная память**| `-m` | `RLIMIT_RSS` | **Устарело.** В современных ядрах (2.6+) не имеет эффекта на одиночные процессы. Заменено на лимиты памяти в cgroups (`memory.max`, `memory.high`). | KB |
| **Время CPU** | `-t` | `RLIMIT_CPU` | Суммарное время CPU в секундах реального времени. При достижении мягкого лимита — `SIGXCPU` (процесс может поймать). При достижении жесткого (soft+3 сек по умолчанию) — `SIGKILL`. | сек. |
| **Блокировка памяти** | `-l` | `RLIMIT_MEMLOCK` | Объём памяти, фиксируемый в RAM через `mlock()`, `mlock2()`, `mmap(MAP_LOCKED)`. Предотвращает вытеснение в Swap. Ограничен `CAP_IPC_LOCK` для непривилегированных процессов (по умолчанию 64 КБ без capability). | KB |
| **RT Timeout** | Нет | `RLIMIT_RTTIME` | Лимит времени непрерывного выполнения в Real-Time режиме (`SCHED_FIFO`/`RR`) без блокирующего вызова. Сбрасывается при возврате из kernel space в user space. | мкс. |
| **Размер стека** | `-s` | `RLIMIT_STACK` | Максимальный размер стека потока. Превышение вызывает `SIGSEGV` (guard page). Влияет на глубину рекурсии. Для главного потока также ограничивает `mmap`-регион стека. | KB |
| **Core-дампы** | `-c` | `RLIMIT_CORE` | Максимальный размер файла снимка памяти (0 — дампы отключены). Влияет на создание `core_pattern`. Ограничен `fs.suid_dumpable` для SUID-бинарников. | KB |
| **Размер файла** | `-f` | `RLIMIT_FSIZE` | Максимальный размер создаваемого/расширяемого файла. Превышение вызывает `SIGXFSZ`, который по умолчанию завершает процесс. | блоки |
| **Сигналы** | `-i` | `RLIMIT_SIGPENDING` | Максимальное количество сигналов, стоящих в очереди для данного UID. Включает realtime-сигналы (`SIGRTMIN`...`SIGRTMAX`). Ограничивает `sigqueue()` и `kill()`. | сигналы |
| **Приоритет nice** | `-e` | `RLIMIT_NICE` | Максимальный приоритет (nice value), который процесс может установить (диапазон 20...-20). Формула: минимум nice = `20 - rlim_cur`. По умолчанию (`0`) запрещает любой повышение приоритета. | nice |
| **RT Приоритет** | `-r` | `RLIMIT_RTPRIO` | Максимальный приоритет реального времени, который может быть установлен через `sched_setscheduler()`. Влияет на `SCHED_FIFO` и `SCHED_RR`. | приор. |
| **POSIX очереди** | `-q` | `RLIMIT_MSGQUEUE` | Лимит памяти для POSIX очередей сообщений (mqueue) для данного UID. Ограничивает общий размер всех очередей пользователя. | байты |

### Ограничения на уровне потоков (thread-level vs process-level)

Важное архитектурное отличие: большинство rlimits применяются на уровне **lightweight process (LWP)**, а не на уровне группы потоков. Это означает:

- **`RLIMIT_NOFILE`**: Суммируется по всем потокам процесса. Если процесс имеет 100 потоков, каждый открывает 50 файлов, общее потребление — 5000 FD.
- **`RLIMIT_NPROC`**: Суммируется по всем процессам и потокам UID. Это защита от fork-бомб на уровне пользователя.
- **`RLIMIT_AS`**: Применяется индивидуально к каждому потоку (каждому имеет свое адресное пространство в рамках процесса).
- **`RLIMIT_CPU`**: Суммируется по всем потокам процесса. Время CPU накапливается глобально для задачи.

**Практическое следствие:** При настройке `ulimit -n 65536` для Java-приложения с 200 потоками, фактический потолок на поток — около 328 дескрипторов.

### Взаимодействие с namespaces

**PID Namespace:**
- `RLIMIT_NPROC` относится к **UID в namespace**, но ядро считает глобально по всем namespace для одного UID. Это означает, что запуск 100 контейнеров от одного пользователя внутри разных PID namespace все равно суммируется в общий лимит `RLIMIT_NPROC`.
- В Kubernetes это критично: лимит `NPROC` для pod'ов с `runAsUser=1000` общий для всех контейнеров в pod и даже соседних pod'ов на том же узле.

**User Namespace:**
- При маппинге UID в user namespace, rlimits применяются к **внешнему UID**. Внутренний root (UID 0) внутри namespace имеет те же лимиты, что и отображаемый пользователь.
- Это защита от escape: даже если внутри namespace процесс стал root, он не может обойти `RLIMIT_NOFILE` внешнего пользователя.

**Mount Namespace:**
- `/proc/<PID>/limits` привязан к PID namespace. Внутри контейнера `cat /proc/self/limits` показывает лимиты конкретного процесса, а не хоста.

### Детализация сигналов и ошибок

**`SIGXCPU` (RLIMIT_CPU):**
- Мягкий лимит: `kill(pid, SIGXCPU)`. По умолчанию завершает процесс, но процесс может установить обработчик через `signal(SIGXCPU, handler)`.
- После мягкого лимита ядро дает 3 секунды реального времени (настраивается через `/proc/sys/kernel/sched_rt_period_us`) до отправки `SIGKILL`.
- Если процесс поймал `SIGXCPU` и продолжает выполняться, второй сигнал (`SIGKILL`) отправляется по истечении grace period.

**`SIGXFSZ` (RLIMIT_FSIZE):**
- Отправляется при превышении `RLIMIT_FSIZE` в момент записи в файл.
- По умолчанию `SIGXFSZ` завершает процесс (core dump по `RLIMIT_CORE`).
- Обработчик может корректно закрыть файл и завершить операцию.

**`EMFILE` / `ENFILE` (RLIMIT_NOFILE):**
- `EMFILE`: Процесс исчерпал свой `RLIMIT_NOFILE`. Возвращается при `open()`, `socket()`, `epoll_create()`.
- `ENFILE`: Система исчерпала `fs.file-max`. Возвращается при `open()`. Требует увеличения глобального лимита.

### Иерархия и приоритеты применения

Лимиты применяются в порядке от наиболее строгих к наименее строгим. Механизм с более высоким приоритетом в списке (более низким уровнем в ОС) всегда имеет преимущество.

```
┌───────────────────────────────────────────┐
│ Глобальные лимиты ядра (sysctl)           │ ← Приоритет 1 (fs.nr_open, fs.file-max, vm.max_map_count)
└───────────────────────────────────────────┘
                     ↓
┌───────────────────────────────────────────┐
│ Контрольные группы (cgroups v2)           │ ← Приоритет 2 (memory.max, pids.max, cpu.max)
└───────────────────────────────────────────┘
                     ↓
┌───────────────────────────────────────────┐
│ Системные сервисы (systemd)               │ ← Приоритет 3 (LimitNOFILE=..., LimitNPROC=...)
└───────────────────────────────────────────┘
                     ↓
┌───────────────────────────────────────────┐
│ PAM / limits.conf (пользователи)          │ ← Приоритет 4 (SSH/Login сессии, окружение)
└───────────────────────────────────────────┘
                     ↓
┌───────────────────────────────────────────┐
│ ulimit / prlimit (текущая сессия/pid)     │ ← Приоритет 5 (Временный / Runtime)
└───────────────────────────────────────────┘
```

**Ключевые правила взаимодействия:**
- **rlimits vs Cgroups:** Лимиты `ulimit` (rlimits) работают параллельно с `cgroups`. Если cgroup ограничивает память (`memory.max`) до 100MB, а `RLIMIT_AS` установлен в 1GB, процесс упадет по OOM при достижении 100MB.
- **Изоляция systemd:** Настройки из `limits.conf` (PAM) **не влияют** на системные сервисы. Для них используются только директивы `Limit*=` в юнит-файлах.
- **UID-лимиты:** Некоторые rlimits (`NPROC`, `SIGPENDING`) суммируются по всем процессам пользователя (UID), а не по отдельному PID.
- **Класс SCHED_IDLE:** Даже если процесс имеет `RLIMIT_RTPRIO`, но планировщик назначает `SCHED_IDLE`, приоритет не применяется.

## Практические сценарии

### Диагностика: Три уровня для ошибки EMFILE

При возникновении ошибки `Too many open files` (код `EMFILE`) необходимо проверить три уровня ограничений:

1.  **Лимит процесса (rlimit):** Проверяется ядром при каждом `open()`. 
    *   Просмотр: `cat /proc/<PID>/limits | grep "Max open files"`.
2.  **Потолок ядра для процесса (`fs.nr_open`):** Абсолютная верхняя граница, выше которой нельзя поднять `RLIMIT_NOFILE` даже через root.
    *   Просмотр: `sysctl fs.nr_open`.
3.  **Общесистемный лимит (`fs.file-max`):** Общее количество дескрипторов всеми процессами на хосте. 
    *   Просмотр: `sysctl fs.file-max`.

**Решение:** Если вы установили `ulimit -n 2000000`, но он не применяется, скорее всего, он упирается в `fs.nr_open` (по умолчанию ~1.04 млн).

### Диагностика: RLIMIT_NPROC и предупреждение fork bomb

Для диагностики приближения к лимиту `RLIMIT_NPROC`:

```bash
# Текущее количество процессов пользователя
ps -u <USER> --no-headers | wc -l

# Лимит из limits
grep "Max processes" /proc/$(pgrep -u <USER> -n)/limits

# Проверка через /proc/PID/status (для конкретного процесса)
grep -E "Threads|VmPeak|VmSize" /proc/<PID>/status
```

**Мониторинг через auditd (preventive):**
```bash
# Аудит создания процессов
sudo auditctl -a always,exit -F arch=b64 -S clone -S fork -S vfork -k process_spawn
sudo ausearch -k process_spawn --start recent | aureport -x --summary
```

### Диагностика: RLIMIT_MEMLOCK и базы данных

Для приложений, работающих с памятью напрямую (DPDK, базы данных с HugePages, криптография):

```bash
# Проверка текущего лимита
grep "Max locked memory" /proc/$(pgrep -n postgres)/limits

# Проверка, что память зафиксирована
grep -i "locked" /proc/$(pgrep -n postgres)/smaps | awk '{sum+=$2} END {print sum/1024 " MB"}'

# Диагностика ошибок ENOMEM при mlock
sudo dmesg | grep -i "memlock\|mlock\|locked"
```

Если лимит слишком мал, `mlock()` или `mmap(MAP_LOCKED)` вернут `ENOMEM`. Это часто является причиной сбоев при запуске **HashiCorp Vault** или **Oracle DB**, которые пытаются защитить ключи/память от попадания в Swap.

### Аудит лимитов по всему кластеру (SSH/Ansible)

```bash
# Ансибл-плейбуг для сбора лимитов
ansible all -m shell -a "cat /proc/$(pgrep -n systemd)/limits | grep -E 'Max open files|Max processes|Max locked memory'" --limit production

# Или через pdsh
pdsh -g all "grep -H . /proc/[0-9]*/limits 2>/dev/null | grep -E 'nofile|nproc|memlock'" | sort | uniq
```

### Анализ взаимодействия rlimits и cgroups

При конфликте между `RLIMIT_AS` и `memory.max`:

```bash
# 1. Проверка rlimit процесса
cat /proc/<PID>/limits | grep "address space"

# 2. Проверка cgroup memory.max
cat /sys/fs/cgroup/system.slice/<service>.service/memory.max

# 3. Проверка текущего потребления
cat /sys/fs/cgroup/system.slice/<service>.service/memory.current

# 4. Проверка статистики OOM
cat /sys/fs/cgroup/system.slice/<service>.service/memory.events
# oom 0
# oom_kill 2
# oom_group_kill 0
```

### Сегменты стека и RLIMIT_STACK

Диагностика переполнения стека:

```bash
# Проверка размера стека
cat /proc/<PID>/limits | grep "stack"

# Просмотр карты памяти для поиска guard pages
pmap -x <PID> | grep -E "stack|guard"

# Проверка размера стека в runtime
cat /proc/<PID>/status | grep VmStk
```

### Мониторинг SIGPENDING

Для приложений с высокой частотой сигналов (например, селекторов на сигналах):

```bash
# Статистика сигналов ядра
grep -E "sigpending|sigspray" /proc/stat

# Проверка через perf
sudo perf stat -e signal:sig_deliver -a -- sleep 5
```

## Дополнительная информация

### Технические нюансы и подводные камни

1.  **Наследование:** Лимиты наследуются через `fork()`. При `execve()` лимиты сохраняются, что позволяет оболочке настраивать окружение перед запуском приложения.
2.  **Capabilities:** Для повышения жесткого лимита (Hard Limit) процессу необходима привилегия **`CAP_SYS_RESOURCE`**. Понижать жесткий лимит может любой процесс, но это действие необратимо.
3.  **prlimit(2):** Универсальный системный вызов (введен в Linux 2.6.36). Позволяет:
    - Считывать и устанавливать лимиты атомарно.
    - Управлять лимитами *другого* процесса по его PID (при наличии прав `CAP_SYS_RESOURCE` или совпадении UID).
4.  **Threaded лимиты:** В многопоточных приложениях `pthread_create()` может вернуть `EAGAIN` как из-за `RLIMIT_NPROC`, так и из-за `pids.max` cgroup. Диагностика должна проверять оба источника.
5.  **Заметки по RLIMIT_MEMLOCK:** Без `CAP_IPC_LOCK` лимит по умолчанию — 64 КБ. При наличии capability — `unlimited` (на уровне rlimit) или `RLIMIT_MEMLOCK` (на уровне PAM). Некоторые дистрибутивы (RHEL) понижают лимит через `pam_limits` даже для root.
6.  **Взаимодействие с seccomp:** В контейнерах с `seccomp` профилем системные вызовы `prlimit()` и `setrlimit()` могут быть запрещены, что делает невозможным динамическое изменение лимитов изнутри контейнера.
7.  **Потокобезопасность ulimit:** `ulimit` является shell builtin и его вызовы не атомарны при параллельном выполнении в одном процессе. Для скриптов используйте `prlimit` или `systemd-run`.

### Типичные ошибки и их причины

| Ошибка | Ресурс | Причина | Решение |
| :--- | :--- | :--- | :--- |
| `Too many open files` | `RLIMIT_NOFILE` / `fs.file-max` | Исчерпан лимит дескрипторов | Увеличить `ulimit -n`, `LimitNOFILE=`, проверить `fs.nr_open` |
| `Cannot allocate memory` при `fork()` | `RLIMIT_NPROC` / `pids.max` | Исчерпан лимит задач | Увеличить `ulimit -u`, `TasksMax=`, проверить `pids.max` cgroup |
| `ENOMEM` при `mlock()` | `RLIMIT_MEMLOCK` | Мало зафиксированной памяти | Увеличить `ulimit -l`, добавить `CAP_IPC_LOCK` |
| `SIGXFSZ` при записи | `RLIMIT_FSIZE` | Превышен размер файла | Увеличить `ulimit -f` или отключить `ulimit -f unlimited` |
| `SIGXCPU` / `SIGKILL` | `RLIMIT_CPU` | Превышено время CPU | Увеличить `ulimit -t` или оптимизировать алгоритм |
| `Operation not permitted` | `CAP_SYS_RESOURCE` | Попытка повысить Hard Limit без capability | Использовать `sudo`, настроить capability в unit-файле |
| `EMFILE` при высокой нагрузке | `fs.nr_open` | Системный потолок ниже запрашиваемого | `sudo sysctl -w fs.nr_open=2097152` |
