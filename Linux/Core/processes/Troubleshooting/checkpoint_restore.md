# Механизмы сохранения и восстановления процессов

## Определения

**Checkpoint/Restore** — технология сохранения полного состояния запущенного процесса (или группы процессов) в файлы-образы на диске с возможностью последующего восстановления его работы с того же места.

**CRIU (Checkpoint/Restore In Userspace)** — основная утилита в Linux для реализации механизмов заморозки и восстановления процессов. Работает преимущественно в пространстве пользователя, используя современные возможности ядра.

**ptrace** — системный вызов, позволяющий одному процессу (трассировщику) наблюдать и контролировать выполнение другого процесса (трассируемого), а также изменять его память и регистры. Используется инструментами диагностики и переноса процессов.

## Основные концепции

### Принципы работы CRIU

Механизм создания снимка (checkpoint) включает в себя сбор следующих данных:

- **Страницы памяти** — полное содержимое оперативной памяти процесса.
- **Состояние регистров** — значения счетчика команд и регистров процессора.
- **Файловые дескрипторы** — информация об открытых файлах, сокетах и каналах (pipes).
- **Дерево процессов** — иерархия потоков и дочерних задач.
- **Сигналы** — список заблокированных и ожидающих обработки сигналов.
- **Ресурсы изоляции** — привязка к пространствам имён (namespaces) и контрольным группам (cgroups).

При восстановлении процесса ядро и CRIU воссоздают окружение, идентичное исходному.

### Ограничения и зависимости

- **Привилегии:** Для работы требуются права `root` или специфические возможности: `CAP_CHECKPOINT_RESTORE`, `CAP_SYS_PTRACE`, `CAP_SYS_ADMIN`.
- **Сетевые соединения:** Процессы с активными TCP-соединениями требуют использования опции `--tcp-established` для сохранения состояния сокетов.
- **Архитектура:** Восстановление возможно только на системе с совместимой архитектурой процессора и версией ядра.
- **Устройства:** Процессы, взаимодействующие напрямую с драйверами специфических устройств (например, GPU), могут иметь проблемы при восстановлении, если состояние драйвера не может быть сохранено.

### Виртуальная файловая система /proc

Интерфейс `/proc` предоставляет критически важные ссылки для восстановления:

- `/proc/<PID>/exe` — символическая ссылка на исполняемый файл процесса. Даже если файл удален с диска, ссылка остается валидной, пока процесс запущен.
- `/proc/<PID>/fd/` — список открытых файловых дескрипторов.

## Практические сценарии

### Использование CRIU для заморозки и восстановления

#### 1. Создание снимка (dump)

```bash
# -t: указать PID (Process Identifier)
# --images-dir: путь к директории для сохранения состояния
# --shell-job: разрешить сохранение задач, запущенных из shell
sudo criu dump -t <PID> --images-dir /tmp/checkpoint --shell-job
```

#### 2. Восстановление (restore)

```bash
# --daemon: запустить восстановленный процесс в фоновом режиме
sudo criu restore --images-dir /tmp/checkpoint --shell-job --daemon
```

### Восстановление удаленного исполняемого файла

Если файл был удален, но процесс продолжает работать, его можно скопировать из памяти ядра:

1. **Найти PID процесса:**

   ```bash
   pgrep -f <name>
   ```

2. **Восстановить бинарный файл:**

   ```bash
   cp /proc/<PID>/exe /path/to/restored_binary
   ```

### Перезапуск процесса без изменения PID

С помощью утилиты `nsenter` можно подменить работающий процесс новым, сохранив его идентификатор и часть окружения.

```bash
# Вход в namespaces процесса 1234 и запуск нового кода через exec
sudo nsenter -t 1234 -m -u -i -n -p -- bash -c 'exec /usr/local/bin/new_version'
```

Подробное описание параметров `nsenter` доступно в разделе [**Пространства имён (Namespaces)**](../../namespaces.md).

### Перенос процесса в новый терминал

Утилита `reptyr` позволяет переместить процесс, запущенный в обычной SSH-сессии, внутрь мультиплексора (например, `tmux`), чтобы избежать его завершения при разрыве связи.

```bash
# Внутри tmux сессии:
reptyr <PID>
```

Детальное руководство по использованию см. в разделе [**Использование reptyr**](../../../Diagnostics/Processes/reptyr.md).
