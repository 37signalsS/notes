# Механизмы сохранения и восстановления процессов

## Определения

**Checkpoint/Restore** — технология сохранения полного состояния запущенного процесса (или группы процессов) в файлы-образы на диске с возможностью последующего восстановления его работы с того же места.

**CRIU (Checkpoint/Restore In Userspace)** — основная утилита в Linux для реализации механизмов "заморозки" и восстановления процессов. Позволяет выполнять миграцию живых приложений, балансировку нагрузки и быстрый перезапуск без потери состояния.

**ptrace** — системный вызов, позволяющий одному процессу (трассировщику) наблюдать и контролировать выполнение другого процесса. Используется CRIU для "захвата" процесса и чтения его состояния.

## Основные концепции

### Принципы работы CRIU

Создание снимка (checkpoint) включает в себя сбор следующих данных:
- **Память:** Полное содержимое адресного пространства.
- **Состояние CPU:** Регистры, счетчик команд, состояние FPU.
- **Ресурсы ядра:** Открытые файлы (FD), сокеты (включая TCP-состояния), каналы (pipes).
- **Иерархия:** Дерево процессов, PID/TID, родственные связи.
- **Изоляция:** Привязка к Namespaces и Cgroups (критично для контейнеров).

При восстановлении процесса ядро и CRIU воссоздают окружение, идентичное исходному, включая те же PID (если они не заняты).

### Ограничения и зависимости

- **Привилегии:** Требуются права `root` или наличие `CAP_CHECKPOINT_RESTORE` (начиная с ядра Linux 5.9).
- **Ядро:** Версия ядра должна поддерживать необходимые опции (например, `CONFIG_CHECKPOINT_RESTORE`).
- **Сетевые соединения:** Для сохранения TCP-соединений требуется опция `--tcp-established`. После восстановления может потребоваться коррекция сетевых маршрутов.
- **Внешние зависимости:** Состояние внешних ресурсов (баз данных, API) не сохраняется автоматически. Приложение должно уметь обрабатывать временные разрывы соединений.

### CRIU в контейнеризации

CRIU является фундаментом для расширенных функций современных систем:
- **Docker:** Команда `docker checkpoint` позволяет сохранять состояние контейнера. Требует включения экспериментальных функций.
- **Kubernetes:** Используется для миграции подов без потери состояния и сокращения времени запуска (Container Pre-warming).
- **Podman:** Нативная поддержка `podman container checkpoint`.

## Практические сценарии

### Использование CRIU

#### 1. Создание снимка (dump)
Процесс будет приостановлен или завершен (по умолчанию), а его состояние сохранено в указанную директорию.
```bash
# -t: PID процесса
# --images-dir: куда сохранять файлы-образы
# --shell-job: разрешить сохранение задач, связанных с терминалом
sudo criu dump -t <PID> --images-dir /tmp/checkpoint --shell-job
```

#### 2. Восстановление (restore)
```bash
# --daemon: запустить восстановленный процесс в фоновом режиме
sudo criu restore --images-dir /tmp/checkpoint --shell-job --daemon
```

### Восстановление удаленного исполняемого файла
Если бинарный файл был удален с диска, но процесс продолжает работать, его можно восстановить из памяти ядра через интерфейс `/proc`.
```bash
# Восстановление исполняемого файла по его PID
cp /proc/<PID>/exe /path/to/restored_binary
```

### Перезапуск процесса с сохранением PID (nsenter)
Метод позволяет запустить новый код внутри существующей группы пространств имен.
```bash
# Запуск новой версии кода в контексте процесса 1234
sudo nsenter -t 1234 -m -u -i -n -p -- bash -c 'exec /usr/local/bin/new_app'
```

### Перенос процесса в tmux/screen (reptyr)
Позволяет "перехватить" дескрипторы терминала и перепривязать их к новому сеансу.
```bash
# Перехват процесса внутри новой сессии tmux
reptyr <PID>
```
Подробности: [**Использование reptyr**](../../../Diagnostics/Processes/reptyr.md).
