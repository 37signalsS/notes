# Устранение неисправностей процессов в Linux

## Определения

**Troubleshooting процессов** — системный процесс выявления, локализации и устранения сбоев в работе вычислительных задач. Охватывает анализ жизненного цикла (создание, работа, завершение) и потребления ресурсов.

**Exit Code (Код завершения)** — числовой статус (0–255), передаваемый родителю при выходе. Значение `0` — успех, остальные — специфичные ошибки. Подробнее: [**Коды возврата в Shell**](../../../Shell/exit_codes.md).

**Coredump (Дамп памяти)** — объектный файл, содержащий образ памяти процесса на момент фатального сбоя (`SIGSEGV`, `SIGILL`). Позволяет выполнить «посмертный» анализ состояния регистров и стека.

**OOM Killer (Out-of-Memory Killer)** — защитный механизм ядра, принудительно завершающий процессы при критической нехватке RAM. Подробно: [**Механизм OOM Killer**](../oom_killer_mechanism.md).

**Uninterruptible Sleep (Состояние D)** — состояние процесса, ожидающего завершения системного вызова (обычно I/O). Процесс в этом состоянии не реагирует на сигналы, включая `SIGKILL`.

**Context Switching (Переключение контекста)** — процедура сохранения состояния одной задачи и восстановления другой. Чрезмерное количество переключений (Voluntary/Involuntary) ведет к деградации производительности.

## Основные концепции

### Эшелонированная диагностика (Macro → Micro)

Диагностика процессов всегда начинается с общего обзора системы и сужается до конкретного системного вызова:

1.  **Macro-уровень (Хост):** Анализ Load Average, CPU Steal, Memory Pressure (PSI). Инструменты: `top`, `htop`, `btop`, `vmstat`.
2.  **Micro-уровень (Процесс):** Детализация потребления ресурсов конкретным PID. Инструменты: `pidstat`, `ps`, `pgrep`.
3.  **Deep-уровень (Внутреннее состояние):** Исследование дескрипторов, карт памяти и стеков вызовов. Инструменты: `/proc/PID/*`, `lsof`, `pstack`.
4.  **Событийный уровень (Трассировка):** Перехват системных вызовов и сигналов в реальном времени. Инструменты: `strace`, `bpftrace`, `perf`.

### Матрица ответственности за ресурсы

При поиске "виновника" нагрузки следует проверять следующие узкие места:
- **CPU:** Очереди на выполнение (`runqueue`), время в Kernelspace (системные вызовы), влияние прерываний.
- **Memory:** Разница между RSS и PSS, состояние Swap, утечки в куче (heap).
- **I/O:** Задержки дисковых операций, лимиты пропускной способности, блокировки файлов.
- **FD (Дескрипторы):** Утечки сокетов, пайпов и открытых файлов.

## Практические сценарии

### Сценарии диагностики и отладки

| Проблема | Описание и первый шаг | Ссылка на решение |
| :--- | :--- | :--- |
| **Утечки памяти** | Рост RSS/PSS при стабильной нагрузке. Проверка через `smem`. | [Отладка памяти](./debugging.md) |
| **Зомби-процессы** | Накопление `<defunct>` в `ps`. Проверка родительского процесса. | [Анализ зомби](./debugging.md) |
| **OOM Killer** | Процесс внезапно исчезает с кодом 137. Проверка `dmesg`. | [Диагностика OOM](../oom_killer_diagnostics.md) |
| **Состояние D** | Процесс «висит» и не убивается. Проверка `wchan` и `stack`. | [Анализ состояния D](../practical_scenarios.md) |
| **Too many open files** | Ошибки `EMFILE` / `ENFILE`. Проверка лимитов `ulimit -n`. | [Лимиты файлов](../../../Diagnostics/Troubleshooting/troubleshooting_too_many_open_files.md) |
| **Аварийный крах** | Segmentation fault. Настройка и анализ coredump. | [Coredump отладка](../../../Diagnostics/Troubleshooting/coredump_debugging.md) |
| **Высокий Context Switch** | Процесс потребляет CPU на переключениях. Проверка `pidstat -w`. | [CPU диагностика](../../../Diagnostics/Processes/thread_cpu_troubleshooting.md) |

### Техники восстановления

- **Восстановление удаленного бинарного файла:** Если исполняемый файл был удален с диска, но процесс запущен, его можно восстановить из `/proc/PID/exe`.
- **Заморозка процесса (CRIU):** Сохранение состояния процесса для миграции или отложенного анализа. Подробно: [**Работа с CRIU**](./checkpoint_restore.md).

## Дополнительная информация

### Безопасность при отладке

1.  **Влияние strace:** Использование `strace` в продакшене замедляет процесс в десятки раз. Рекомендуется использовать **eBPF** инструменты (`bpftrace`).
2.  **Ptrace YAMA:** Современные системы ограничивают возможность подключения к чужим процессам (параметр `kernel.yama.ptrace_scope`).
3.  **Чувствительные данные:** Coredumps и трассировки могут содержать пароли и ключи в открытом виде.
