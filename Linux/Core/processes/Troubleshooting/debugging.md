# Отладка процессов: утечки памяти, дампы памяти и зомби-процессы

## Определения

**Отладка (Debugging) процессов** — совокупность методов диагностики и устранения неисправностей, связанных с некорректным потреблением ресурсов, аварийными завершениями и нарушениями жизненного цикла процессов в Linux.

**Утечка памяти (Memory Leak)** — ситуация, при которой процесс выделяет оперативную память, но не освобождает её после использования. Это ведет к постепенному росту потребления **RAM (Random Access Memory)** и может спровоцировать срабатывание механизма **OOM (Out-of-Memory)** Killer.

**Дамп памяти (Coredump)** — снимок адресного пространства процесса в момент его аварийного завершения. Содержит состояние регистров, стека и памяти, что необходимо для "посмертной" отладки.

**Зомби-процесс (Zombie Process)** — завершенный процесс, запись о котором остается в таблице процессов ядра до тех пор, пока родительский процесс не прочитает статус его выхода.

## Основные концепции

### Типичные проблемы жизненного цикла

- **Аварийные сигналы:** Процесс может быть завершен ядром при получении сигналов **SIGSEGV (Signal Segmentation Violation)**, **SIGFPE (Signal Floating-Point Exception)** или **SIGQUIT (Signal Quit)**. Последний принудительно инициирует создание дампа памяти.
- **Накопление зомби-процессов:** Если родительский процесс игнорирует сигнал **SIGCHLD (Signal Child)** и не вызывает функцию `wait()`, дочерние процессы переходят в состояние `Z` (Zombie). Они не потребляют ресурсы **CPU (Central Processing Unit — центральный процессор)** или **RAM (Random Access Memory — оперативная память)**, но занимают записи в таблице процессов.
  - **Риски:** Исчерпание лимита PID (блокировка запуска новых программ), нагрузка на структуры данных ядра и возможный отказ в обслуживании (DoS).
- **Деградация производительности:** Утечки памяти на ранних стадиях могут не приводить к падению, но вызывать избыточный свопинг (swapping) и замедление системы. В отличие от ресурсов процессора, память не восполняется автоматически без перезапуска или очистки.

Подробная иерархия лимитов и их влияние на процессы описаны в разделе [**Концепции лимитов ресурсов**](../resource_limits_concepts.md).

## Практические сценарии

### Диагностика утечек памяти

#### 1. Использование Valgrind

Инструмент для динамического анализа кода на наличие ошибок работы с памятью:

```bash
valgrind --leak-check=full --show-leak-kinds=all ./your_program
```

#### 2. Трассировка системных вызовов (strace)

Отслеживание выделения и освобождения памяти через вызовы `mmap` и `munmap`:

```bash
strace -e trace=mmap,munmap -p <PID>
```

Подробнее: [**Трассировка и отладка**](../../../Diagnostics/Troubleshooting/tracing_and_debugging.md).

#### 3. Анализ через /proc

Проверка текущего потребления памяти процессом:

```bash
# Просмотр VmSize (виртуальная память) и VmRSS (физическая память)
cat /proc/<PID>/status | grep -E 'VmSize|VmRSS|VmSwap'
```

### Анализ аварийных завершений (Coredump)

#### 1. Настройка лимитов

По умолчанию размер дампа часто ограничен нулем. Чтобы разрешить запись дампов:

```bash
# Разрешить дампы неограниченного размера в текущей сессии
ulimit -c unlimited
```

#### 2. Управление через systemd-coredump

В современных дистрибутивах дампы управляются через `systemctl`.

- **Список дампов:** `coredumpctl list`
- **Информация о сбое:** `coredumpctl info <PID>`
- **Отладка в gdb (GNU Debugger):** `coredumpctl debug <PID>`

#### 3. Ручной анализ в gdb

Если дамп сохранен в файл:

```bash
gdb /path/to/binary /path/to/coredump

# Полезные команды внутри gdb:
(gdb) bt          # Вывод стека вызовов (backtrace)
(gdb) info locals # Просмотр локальных переменных
```

### Устранение зомби-процессов

#### Диагностика

```bash
# Поиск процессов в состоянии Z
ps aux | grep ' Z '

# Определение родителя (PPID — Parent Process Identifier)
ps -o ppid= -p <ZOMBIE_PID>
```

#### Устранение

1. **Сигнал родителю:** Отправьте родителю сигнал о завершении потомка, чтобы спровоцировать вызов `wait()`:

   ```bash
   kill -s SIGCHLD <PARENT_PID>
   ```

2. **Завершение родителя:** Если родитель "завис" и не очищает зомби, его необходимо завершить. После этого зомби будут "усыновлены" процессом `init` (PID 1) и автоматически удалены.
