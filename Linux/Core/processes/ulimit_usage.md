# Управление лимитами ресурсов: ulimit и prlimit

## Определения

**Лимиты ресурсов (Resource Limits)** — это системные ограничения на потребление вычислительных ресурсов (процессорное время, память, количество файлов), накладываемые ядром Linux на процессы.

**ulimit** — встроенная команда оболочки (shell builtin), предназначенная для управления лимитами текущего сеанса и всех его дочерних процессов.

**prlimit** — внешняя утилита (часть `util-linux`), позволяющая просматривать и изменять лимиты любого запущенного процесса по его PID, а также устанавливать лимиты для новых программ.

**getrlimit / setrlimit** — фундаментальные системные вызовы ядра Linux, на которых базируются все инструменты управления лимитами.

## Основные концепции

### Мягкие и жесткие лимиты

Каждый ресурс имеет два связанных с ним значения:
- **Soft Limit (Мягкий):** Действующее ограничение. При его достижении ядро может отправить сигнал (например, `SIGXCPU`) или вернуть ошибку (например, `EMFILE`). Пользователь может самостоятельно увеличивать его до значения жесткого лимита.
- **Hard Limit (Жесткий):** Абсолютный потолок для мягкого лимита. Только привилегированный пользователь (`root`) может повышать жесткий лимит. Обычный пользователь может только понижать его (необратимо для текущей сессии).

### Способы управления лимитами

| Инструмент | Метод | Область действия |
| :--- | :--- | :--- |
| **ulimit** | Builtin-команда | Текущий shell и его потомки |
| **prlimit** | Утилита / syscall | Любой процесс по PID (требует прав или того же UID) |
| **/proc/PID/limits** | Файл procfs | Только просмотр текущих лимитов процесса |
| **systemd** | Директивы юнита | Конкретный сервис и его cgroup |
| **PAM (limits.conf)** | Конфигурационный файл | Все сессии пользователя при логине |

## Практические сценарии

### Работа с текущей сессией (ulimit)

```bash
# Просмотр всех мягких лимитов текущей сессии
ulimit -a

# Просмотр жесткого лимита на открытые файлы
ulimit -Hn

# Увеличение мягкого лимита на количество процессов до 4096
ulimit -Su 4096

# Отключение лимита на размер core-дампа
ulimit -c unlimited
```

### Управление работающими процессами (prlimit)

`prlimit` незаменим для SRE, когда нужно изменить лимиты без перезапуска приложения (например, при угрозе падения из-за нехватки дескрипторов).

```bash
# Просмотр всех лимитов конкретного процесса
prlimit -p 1234

# Изменение лимита открытых файлов (soft=4096, hard=8192) для PID 1234
sudo prlimit --pid 1234 --nofile=4096:8192

# Запуск новой программы с определенным лимитом памяти
prlimit --as=1G ./my_script.sh
```

### Диагностика через procfs

Файл `/proc/PID/limits` — единственный достоверный источник информации о лимитах, которые *фактически* видит процесс в данный момент.

```bash
# Проверка лимитов процесса Nginx
cat /proc/$(pgrep nginx | head -1)/limits
# → Max open files            1024                 4096                 files
```

### Использование в скриптах для защиты ресурсов

```bash
#!/bin/bash
# Защита от утечек памяти и зависаний в скрипте автоматизации
ulimit -v 512000    # Лимит виртуальной памяти 512MB
ulimit -t 60        # Лимит времени CPU 1 минута

./run_untrusted_code.py
```

## Дополнительная информация

### Технические нюансы

1.  **Наследование:** Лимиты наследуются при `fork()` и сохраняются при `execve()`.
2.  **Capabilities:** Для изменения чужих лимитов или повышения жесткого лимита процессу необходима привилегия `CAP_SYS_RESOURCE`.
3.  **Лимит nofile:** Даже если вы установите `ulimit -n 999999`, процесс может упереться в системные ограничения ядра:
    - `fs.nr_open` — максимальное значение `nofile` для одного процесса.
    - `fs.file-max` — общесистемный лимит на все открытые файлы.
4.  **Связь с cgroups:** Лимиты `ulimit` (rlimits) работают параллельно с ограничениями cgroups. Если cgroup ограничивает память до 100MB, а `ulimit -v` установлен в 1GB, процесс упадет по OOM при достижении 100MB.
