# Основные концепции процессов в Linux

## Определения

**Процесс** — это динамический объект, представляющий собой выполняющийся экземпляр программы, обладающий собственными ресурсами и изолированный от других процессов. В ядре Linux любая единица выполнения (процесс или поток) представлена структурой `task_struct` и называется **задачей (task)**.

Фундаментальные понятия Userspace, Kernelspace и системных вызовов подробно описаны в разделе [**Процессы: Определения**](./definitions.md).

## Основные концепции

### Анатомия процесса (Образ памяти)

При запуске программы ядро создает «образ» процесса в виртуальной памяти. Он состоит из нескольких функциональных сегментов:

| Сегмент | Назначение | Особенности |
| :--- | :--- | :--- |
| **Text (Code)** | Машинный код программы. | Только чтение (`read-only`), исполняемый. |
| **Data** | Инициализированные глобальные и статические переменные. | Чтение и запись. |
| **BSS** | Неинициализированные глобальные переменные. | Заполняется нулями при старте. |
| **Heap (Куча)** | Динамическая память (`malloc`, `new`). | Растет «вверх» к старшим адресам. |
| **Stack (Стек)** | Локальные переменные, аргументы функций, адреса возврата. | Растет «вниз» к младшим адресам. |
| **Memory Mapping**| Общие библиотеки (`.so`), отображение файлов (`mmap`). | Находится между стеком и кучей. |

### Методы создания процессов

В Linux создание новых задач осуществляется через механизмы дублирования и замещения образа.

- **`fork()`** — классический вызов, создающий полную копию родительского процесса.
  - Возвращает `0` в дочернем процессе и `PID` ребенка в родительском.
  - Использует механизм **Copy-on-Write (CoW)**: физические страницы памяти копируются только при попытке записи, что делает `fork()` крайне эффективным.
- **`exec()`** — семейство вызовов (`execve` и др.), заменяющих текущий образ процесса новой программой.
  - **Техническая деталь:** Файловые дескрипторы по умолчанию сохраняются при `exec`. Для предотвращения утечек ресурсов рекомендуется использовать флаг **`O_CLOEXEC`** при открытии файлов.
- **`clone()`** — универсальный вызов, лежащий в основе создания как процессов, так и **потоков (threads)**. Позволяет гибко выбирать, какие ресурсы разделять между родителем и потомком (память, файловая таблица, сигналы).
  - Подробное сравнение процессов и потоков приведено в [**Дополнительной информации**](./additional_info.md).

### Идентификация и иерархия

#### Уровни идентификации
Каждый процесс вписан в сложную иерархию:
1.  **PID (Process ID):** Уникальный идентификатор процесса.
2.  **PPID (Parent PID):** Ссылка на родителя.
3.  **PGID (Process Group ID):** Группирует процессы для управления заданиями (Job Control) и рассылки сигналов (например, всему конвейеру `ls | grep`). Практическое использование Job Control в shell описано в [**Горячие клавиши и шорткаты Shell**](../../Shell/shell_shortcuts.md#управление-фоновыми-задачами).
4.  **SID (Session ID):** Группирует процессы в рамках одного входа пользователя (терминальной сессии).

#### Специальные процессы
- **PID 0 (idle):** Контекст ядра, когда CPU простаивает.
- **PID 1 (init / systemd):** «Отец всех процессов». Первый процесс Userspace.
  - **Reparenting:** «Усыновляет» процессы-сироты (**Orphan**), чей родитель завершился.
  - **Reaping:** Обязан собирать статусы завершения через `wait()` для предотвращения накопления **зомби-процессов**.

#### Пространства имен (Namespaces)
Механизм изоляции, позволяющий процессу иметь разные PID на разных уровнях:
- Внутри контейнера процесс может видеть себя под **PID 1**.
- На хосте тот же процесс будет иметь свой реальный глобальный **PID (например, 5678)**.

### Состояния процесса

Статус процесса отображается в `top`, `ps` (колонка `STAT`).

| Состояние | Код | Описание |
| :--- | :--- | :--- |
| **Running** | **R** | Выполняется или готов к выполнению (в очереди планировщика). |
| **Sleeping** | **S** | Прерываемый сон (Interruptible). Ожидает внешнего события (I/O). |
| **Uninterruptible**| **D** | Непрерываемый сон. Обычно ожидание дискового I/O. Не реагирует на сигналы. |
| **Stopped** | **T** | Остановлен сигналом управления (`SIGSTOP`, `Ctrl+Z`). |
| **Zombie** | **Z** | Завершен, но запись в таблице процессов осталась до вызова `wait()` родителем. |
| **Idle** | **I** | Бездействующий поток ядра (Kernel Thread). |

### Переключение контекста (Context Switch)

Ядро создает иллюзию параллелизма, быстро переключая процессор между задачами.
- **Стоимость:** Переключение между процессами «дорогое», так как требует смены таблиц страниц памяти и очистки кэшей процессора (TLB).
- **Потоки:** Переключение между потоками одного процесса дешевле, так как они разделяют адресное пространство.

### Уровни привилегий процесса (UID/GID)

Каждый процесс имеет несколько уровней идентификаторов пользователя и группы, которые ядро проверяет при выполнении привилегированных операций:

| Тип | Описание |
| :--- | :--- |
| **Real UID/GID (RUID/RGID)** | Идентификатор пользователя, который запустил процесс. |
| **Effective UID/GID (EUID/EGID)** | Идентификатор, используемый ядром для проверки прав доступа. Может отличаться от Real (например, у `setuid`-бинарников). |
| **Saved UID/GID** | Сохраненное значение, позволяющее процессу временно повышать и понижать привилегии (переключаться между Real и Effective). |
| **Filesystem UID/GID (FSUID/FSGID)** | Отдельный идентификатор для проверки прав при доступе к файлам. Позволяет процессу иметь одни права для файловой системы и другие — для остальных операций. |

**Практическое значение:**
- При запуске `sudo` процесс получает `EUID=0` (root), хотя `RUID` остается идентификатором обычного пользователя.
- `CAP_SETUID`/`CAP_SETGID` — capabilities, позволяющие менять UID/GID без полных прав root.
- Команда `ps -o pid,user,uid,euid,comm` показывает разницу между реальным и эффективным UID.

### Управляющий терминал и лидер сессии

**Управляющий терминал (Controlling Terminal)** — устройство ввода-вывода, связанное с сессией. Лидер сессии (процесс, вызвавший `setsid()`) получает к нему доступ и может читать/писать напрямую.

- **Форкирование терминала:** При нажатии `Ctrl+C` терминал отправляет `SIGINT` всем процессам в foreground-группе.
- **Отвязка:** Демоны и службы обычно отсоединяются от терминала через `setsid()` или перенаправляют stdin/stdout/stderr.
- **Практика:** В systemd-сервисах управляющий терминал отсутствует по умолчанию (`StandardInput=tty` только если явно указан).

### Демонизация (Daemonization)

**Демон (Daemon)** — процесс, работающий в фоновом режиме без управляющего терминала. Классический алгоритм включает **двойной fork (double-fork)**, который обеспечивает:
1. Отвязку от родительского shell.
2. Гарантию, что процесс не является лидером сессии и не может случайно захватить управляющий терминал.
3. Усыновление процессом PID 1 (systemd/init).

```bash
# Классический шаблон демонизации (POSIX)
(
    # 1. Первый fork: родитель завершается
    if [ $$ -ne 1 ]; then
        ( umask 0; cd /; setsid "$0" "$@" )
        exit 0
    fi
    
    # 2. Второй fork: гарантируем неперезахват терминала
    if [ $$ -ne 1 ]; then
        ( exec "$@" )
        exit 0
    fi
) &
```

**Современный контекст:** В systemd большинство аспектов демонизации (рабочая директория, права, перенаправление stdout/stderr в journald) берёт на себя сам менеджер служб. Демонизация вручную требуется только для совместимости с устаревшими инициализационными системами.

### pidfd (PID File Descriptor)

**pidfd** — файловый дескриптор, привязанный к конкретной инкарнации процесса. В отличие от числового PID, который может быть переиспользован ядром после завершения процесса, `pidfd` гарантирует, что вы взаимодействуете именно с тем процессом, который ожидали. Подробнее: [**Дополнительная информация**](./additional_info.md#pidfd-pid-file-descriptor).

## Практические сценарии

### Жизненный цикл команды в Shell

Выполнение `ls` в терминале:
1. **Wait:** Shell ждет ввода пользователя.
2. **Fork:** Shell создает дочерний процесс (свою копию).
3. **Exec:** Дочерний процесс заменяет себя кодом `/bin/ls`.
4. **Wait:** Shell блокируется до завершения ребенка.
5. **Exit & Cleanup:** `ls` завершается, Shell считывает код возврата и выводит приглашение к вводу.

### Поиск и идентификация процессов

DevOps/SRE ежедневно используют команды для быстрого поиска процессов по имени, пользователю или состоянию:

```bash
# Поиск PID по имени (быстро)
pidof nginx
pgrep -a nginx
pgrep -u www-data nginx           # Только пользователь www-data
pgrep -af "nginx: worker"         # Полная командная строка

# Интерактивные процессы текущего пользователя
ps -u $USER -o pid,ppid,%cpu,%mem,stat,start,time,comm,args --sort=-%cpu | head -20

# Процессы, блокирующие файл/порт
fuser 80/tcp
fuser /var/lib/mysql

# Дерево процессов для конкретного PID
pstree -ap <PID>
pstree -p $(pgrep -n systemd) | head -30

# Все процессы systemd-сервиса (только PID)
systemctl show --property=MainPID,ControlPID myapp.service
systemctl list-dependencies myapp.service
```

### Диагностика владельца и прав

Информация о UID/GID, capabilities и лимитах доступна в `/proc/<PID>/status`:

```bash
# Права и привилегии процесса
grep ^Uid /proc/<PID>/status
# → Uid:    1000    1000    1000    1000
#    (Real, Effective, Saved, Filesystem)

# Набор capability (в шестнадцатеричном виде)
grep ^CapEff /proc/<PID>/status

# Расшифровка mask (полные права root = all ones)
capsh --decode=000001ffffffffff
```

### Управление сигналами

DevOps-инженер использует сигналы для управления жизненным циклом без перезапуска:

```bash
# Graceful shutdown (SIGTERM → SIGINT → SIGKILL)
kill -15 <PID>
kill -s SIGTERM <PID>

# Перезагрузка конфигурации (SIGHUP)
kill -1 $(pgrep nginx)

# Немедленное завершение (SIGKILL) — последний resort
kill -9 <PID>

# Завершение по имени (опасно в production!)
killall -15 nginx
pkill -15 nginx          # Более безопасно, чем killall

# Безопасное завершение через systemd (предпочтительно)
systemctl stop myapp.service
systemctl kill --signal=SIGTERM myapp.service

# Отправка сигнала всей процессной группе (PGID)
kill -TERM -<PGID>
```

**Важно:** Сигналы доставляются только в контексте namespace. В контейнере `kill -1 $(pgrep nginx)` завершит только nginx внутри этого контейнера, но не на хосте. Для межnamespace-управления используйте `nsenter` или API оркестратора (kubectl, docker).

### Управление приоритетами

Ядро планирует процессорное время на основе **веса**, который задается через `nice`. Подробная теория — в разделе [**Планирование процессов**](./scheduling.md#приоритеты-процессов-nice-и-pr). Практические команды:

```bash
# Запуск фоновой задачи с низким приоритетом (nice=19)
nice -n 19 tar czf /backup/archive.tar.gz /data

# Изменение приоритета запущенного процесса
renice 10 -p <PID>       # NI=10 (приоритет ниже среднего)
sudo renice -5 -p <PID>  # NI=-5 (высокий приоритет, только root)
sudo renice 5 -u www-data # Все процессы пользователя

# Приоритет дискового I/O (ionice)
ionice -c 3 -p <PID>     # idle — только когда диск свободен
ionice -c 2 -n 7 dd if=/dev/zero of=/tmp/test bs=1M count=1000

# Проверка
ps -o pid,ni,pri,comm -p <PID>
```

### Запуск временных процессов (systemd-run)

`systemd-run` — современная альтернатива `&` и `nohup` для запуска фоновых задач с гарантированными лимитами и автоочисткой:

```bash
# Простой фоновый скрипт
systemd-run --user --scope ./backup.sh

# С лимитами памяти, CPU и процессов
systemd-run --user --scope \
  -p MemoryMax=512M \
  -p CPUQuota=50% \
  -p LimitNOFILE=65536 \
  -p TasksMax=128 \
  ./data_sync.sh

# Одноразовый таймер (отложенный старт)
systemd-run --user --on-calendar="2026-09-06 04:00:00" /usr/local/bin/rotate_logs.sh

# Просмотр созданного временного юнита
systemctl --user list-units --type=scope --all
systemctl --user status run-*.scope
```

### Фоновые супервизоры (cron, at, tmux, screen)

#### Cron и at

Демон `cron` запускает задачи по расписанию. Каждый запуск создает новый дочерний процесс:

```bash
# Просмотр запланированных задач
crontab -l
cat /etc/crontab
ls /etc/cron.d/

# Логи выполнения (Debian/Ubuntu)
grep CRON /var/log/syslog

# Логи (RHEL/CentOS)
cat /var/log/cron

# Запуск одноразовой задачи
echo "/usr/local/bin/cleanup.sh" | at 03:00
atq  # Очередь задач
atrm 3  # Удалить задачу №3
```

**Важно:** Cron запускает задачи в минимальном окружении. Всегда используйте абсолютные пути, экспортируйте переменные в заголовке crontab или указывайте их в unit-файле systemd.

#### tmux и screen

Эмуляторы терминала, работающие как супервизоры процессов. Позволяют отсоединяться и присоединяться к сессиям:

```bash
# tmux: создание именованной сессии
tmux new -s monitoring

# Отсоединение (без завершения процессов): Ctrl+B D

# Присоединение обратно
tmux attach -t monitoring

# Список сессий
tmux list-sessions

# screen: аналогично
screen -S long_running
screen -r long_running
```

Для production-сервисов предпочтительнее `systemd` (авторестарт, логи, изоляция), но `tmux` незаменим для интерактивных долгих задач (отладка, мониторинг в реальном времени).

### Анализ зомби и сирот

**Зомби (Z)** не потребляют ресурсы, но занимают место в таблице процессов. Важно помнить: **зомби нельзя «убить» напрямую** через `kill -9`, так как процесс уже мертв.

```bash
# Поиск зомби-процессов
ps aux | awk '$8=="Z" {print $2}'
ps -eo pid,ppid,stat,comm | awk '$3=="Z"'

# Найти родителя зомби
ps -o ppid= -p <ZOMBIE_PID>

# Если родитель — PID 1 (systemd), обычно зомби подбираются автоматически
# Если нет — проверяем systemd
systemctl status systemd

# Если зомби много, проблема в родителе (не вызывает wait()).
# Для очистки таблицы завершите родителя: kill <PARENT_PID>
# После этого зомби станут сиротами и будут усыновлены PID 1.
```
Если зомби много, проблема в родителе (не вызывает `wait()`). Для очистки таблицы необходимо либо устранить ошибку в родителе, либо завершить его, чтобы «сирот» усыновил PID 1. Подробные методы решения описаны в разделе [**Отладка и устранение зомби**](./Troubleshooting/debugging.md#устранение-зомби-и-сирот).

### Трассировка и дерево процессов

```bash
# Визуализация иерархии с аргументами
pstree -ap

# Кто запустил конкретный процесс?
ps -o ppid= -p <PID>

# Визуализация только процессов пользователя
pstree -u $USER
```

### Диагностика типичных проблем

| Проблема | Диагностика | Решение |
| :--- | :--- | :--- |
| **Высокий Load Average** | `uptime` (1/5/15), `top`, `vmstat 1` | Определить источник: CPU (`top`) или I/O (`iotop`, `pidstat -d`) |
| **Процесс в D-state** | `ps aux \| awk '$8~/D/'`, `cat /proc/<PID>/stack` | Восстановить storage/NFS; перезагрузка |
| **Fork-бомба** | `ps -eo pid,ppid,stat \| grep R \| wc -l` | `kill -9 $(ps -o ppid= -p <initiator>)`; ограничить `pids.max` |
| **PID exhaustion** | `cat /proc/sys/kernel/pid_max`; `dmesg \| grep PID` | Увеличить `kernel.pid_max`; найти источник via `auditd` |
| **OOM Kill** | `dmesg -T \| grep -i "oom\|killed process"` | Настроить `OOMScoreAdjust`; добавить swap; ограничить cgroup |
| **Зомби-массовка** | `ps -eo stat \| grep -c Z` | Завершить родителя; проверить `systemd` и `subreaper` |

**Команды быстрой диагностики:**

```bash
# 1. Топ-5 по CPU
ps -eo pid,ppid,user,%cpu,%mem,stat,comm --sort=-%cpu | head -6

# 2. Топ-5 по памяти
ps -eo pid,ppid,user,%mem,rss,vsz,stat,comm --sort=-%mem | head -6

# 3. Общая статистика
vmstat 1 5
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
#  1  0      0 409600  12340 876543    0    0     2     1   45   50  5  2 93  0  0

# 4. Load Average и запущенные процессы
uptime
# → 14:32:01 up 45 days,  3:12,  2 users,  load average: 0.52, 0.48, 0.55

# 5. Проверка OOM событий
dmesg -T | grep -i "out of memory"
journalctl -k -p err | grep -i oom
```

## Дополнительная информация

### Среда окружения

Процессы наследуют переменные окружения родителя. Это основной способ передачи конфигурации (например, `PATH`, `HOME`, `DB_URL`) в Linux. Список переменных процесса можно увидеть в `/proc/<PID>/environ` (разделены нулевым байтом).

### Безопасность и изоляция

- **Chroot:** Ограничение видимости файловой системы (старый метод).
- **Namespaces:** Изоляция ресурсов (PID, Network, Mount).
- **Capabilities:** Позволяют дать процессу право слушать порты < 1024 (`CAP_NET_BIND_SERVICE`) без выдачи полных прав `root`.
- **SELinux/AppArmor:** Мандатное управление доступом (MAC), дополняющее дискреционные права (DAC).

### Наблюдаемость (Observability)

Для SRE критически важно настроить наблюдаемость процессов до возникновения инцидентов:
- **Метрики:** `node_exporter` (Prometheus), `collectd`, `Datadog Agent`.
- **Логи:** `journald` (systemd), `rsyslog` для централизованного сбора.
- **Трейсы:** `strace`, `perf`, `bpftrace` для кратковременной глубокой отладки.
- **Алертинг:** Пороговые значения на количество зомби, высокий `load average`, `cs` (context switches), OOM kills.
