# Механизм OOM Killer в Linux

## Определения

**OOM Killer (Out-of-Memory Killer)** — это защитный механизм ядра Linux, который активируется при критической нехватке оперативной памяти и невозможности выделения новых страниц. Его задача — предотвратить крах всей системы (Kernel Panic) путем принудительного завершения процессов, потребляющих избыточное количество ресурсов.

**Memory Overcommit** — механизм ядра, позволяющий процессам выделять (allocate) больше виртуальной памяти, чем фактически доступно в физической RAM и Swap. OOM Killer является следствием использования агрессивных политик Overcommit.

**oom_score** — итоговый рейтинг «плохости» процесса (от 0 до 1000). Чем выше значение, тем выше вероятность завершения процесса ядром.

**OOM Reaper** — специальный поток ядра (появился в ядре 4.6), который ускоряет освобождение памяти после того, как процесс был убит OOM Killer, путем асинхронной очистки его адресного пространства.

## Основные концепции

### Жизненный цикл срабатывания OOM

Процесс активации OOM Killer состоит из нескольких этапов:

1.  **Allocation Failure:** Процесс запрашивает страницу памяти, но свободных страниц в RAM и Swap нет.
2.  **Direct Reclaim:** Ядро пытается освободить память путем очистки кэшей (Page Cache) и выгрузки неиспользуемых страниц.
3.  **Check Overcommit:** Если очистка не помогла, ядро проверяет политики `vm.overcommit_memory`. Если выделение невозможно — вызывается функция `out_of_memory()`.
4.  **Badness Calculation:** Ядро сканирует все процессы (кроме иммунных) и вычисляет их `oom_score`.
5.  **Signal Delivery:** Выбранному процессу отправляется сигнал **SIGKILL (9)**.
6.  **Reaping:** OOM Reaper асинхронно очищает память убитого процесса, даже если процесс «завис» в состоянии Zombie или Uninterruptible Sleep (D-state).

### Алгоритм вычисления oom_score (oom_badness)

Современный алгоритм (начиная с ядра 3.7) рассчитывает рейтинг линейно:
- **Базовое значение:** Процент используемой резидентной памяти (RSS) + используемый Swap относительно общего объема памяти.
- **Формула:** `oom_score = (%_memory_usage * 10) + oom_score_adj`.
- **Иммунитет:**
    - **PID 1 (systemd/init):** Никогда не убивается.
    - **Kernel Threads:** Имеют полный иммунитет.
    - **Процессы с `oom_score_adj = -1000`:** Исключаются из списка кандидатов.

### Параметры ядра (sysctl)

Настройки, радикально меняющие поведение системы при OOM:

| Параметр | Описание | Значения |
| :--- | :--- | :--- |
| **`vm.panic_on_oom`** | Вызывать Kernel Panic вместо убийства процесса. | `0` (Default), `1` (Panic), `2` (Panic кроме cgroups) |
| **`vm.oom_kill_allocating_task`** | Убить именно тот процесс, который запросил память, вместо поиска по рейтингу. | `0` (Search), `1` (Kill current) |
| **`vm.oom_dump_tasks`** | Выводить детальную информацию о процессах в dmesg при срабатывании OOM. | `1` (Enabled) |
| **`vm.overcommit_memory`** | Режим управления выделением памяти. | `0` (Heuristic), `1` (Always), `2` (Strict) |

### Декодирование лога в dmesg

При срабатывании OOM в логах появляется запись:
`Out of memory: Killed process 1234 (mysqld) total-vm:5242880kB, anon-rss:2097152kB, file-rss:0kB, shmem-rss:0kB`
- **total-vm:** Общий объем виртуальной памяти.
- **anon-rss:** Реально занимаемая оперативная память (анонимные страницы).
- **file-rss:** Память, связанная с файлами (кэш).

## Практические сценарии

### Мониторинг рейтингов процессов

Для оценки текущих кандидатов на вылет можно использовать скрипт:

```bash
# Топ-10 процессов по oom_score
printf "%-10s %-10s %s\n" "SCORE" "PID" "COMMAND"
for p in /proc/[0-9]*; do
    pid=${p##*/}
    [ -r $p/oom_score ] && printf "%-10s %-10s %s\n" \
        "$(cat $p/oom_score)" "$pid" "$(cat $p/comm)"
done 2>/dev/null | sort -nr | head -10
```

### Принудительный вызов OOM для тестирования

**ВНИМАНИЕ:** Опасно для работающей системы. Используется только в тестовых средах для проверки реакции приложений.

```bash
# Эмуляция нехватки памяти через SysRq (требует прав root)
echo f > /proc/sysrq-trigger
```

### Защита критичного сервиса

```bash
# Установка максимальной защиты для базы данных
echo -1000 | sudo tee /proc/$(pidof postgres)/oom_score_adj
```

## Дополнительная информация

### Код выхода и контейнеры

Процесс, завершенный OOM Killer, всегда возвращает код **137** (128 + SIGKILL). В Docker и Kubernetes это отображается как статус `OOMKilled`.

### Современные альтернативы

1.  **systemd-oomd:** Пользовательский демон, который убивает процессы превентивно, основываясь на данных **PSI (Pressure Stall Information)**, не дожидаясь критического зависания ядра.
2.  **Early OOM:** Альтернативный легковесный демон для десктопных систем.
