# Механизм OOM Killer в Linux

## Определения

**OOM Killer (Out-of-Memory Killer)** — это защитный механизм ядра Linux, который при критической нехватке оперативной памяти принудительно завершает один или несколько процессов. Его главная цель — сохранить работоспособность всей операционной системы, жертвуя наименее важными (по мнению алгоритма) задачами.

**oom_score** — числовой рейтинг "плохости" процесса, вычисляемый ядром автоматически. Чем выше значение (от 0 до 1000), тем выше вероятность того, что процесс будет выбран в качестве "жертвы" при возникновении ситуации нехватки памяти.

**oom_score_adj** — корректирующий коэффициент (от -1000 до 1000), позволяющий пользователю или системному администратору вручную изменять приоритет выживания процесса.

## Основные концепции

### Алгоритм работы и последовательность действий

Когда ядро Linux обнаруживает, что свободная физическая память (**RAM — Random Access Memory**) и пространство подкачки (**Swap**) исчерпаны, и оно больше не может выделить страницу памяти для системных нужд, запускается процедура OOM.

1. **Анализ состояния:** Ядро вызывает функцию `out_of_memory()`, которая проверяет, действительно ли ситуация критическая (учитываются политики **Overcommit**).
2. **Сканирование задач:** Система проходит по списку всех активных процессов. При этом **PID (Process Identifier) 1** (`init` или `systemd`) и потоки ядра (**Kernel Threads**) имеют иммунитет, так как их завершение приведет к немедленному краху всей системы (**Kernel Panic**).
3. **Вычисление рейтинга:** Для каждого кандидата вызывается функция `oom_badness()`. Базовый рейтинг рассчитывается пропорционально объему потребляемой оперативной памяти.
4. **Выбор жертвы:** Выбирается процесс с максимальным итоговым значением рейтинга.
5. **Принудительное завершение:** Ядро отправляет выбранному процессу сигнал **SIGKILL (9)**. Этот сигнал невозможно перехватить или проигнорировать, поэтому процесс завершается немедленно без возможности сохранить данные или выполнить очистку (cleanup).
6. **Логирование:** В системный журнал (`dmesg` или `journalctl -k`) записывается детальный отчет, начинающийся с фразы `Out of memory: Killed process...`.
7. **Восстановление:** После высвобождения ресурсов ядро возвращается к нормальному выполнению задач.

### Параметры управления в procfs

Вся информация для взаимодействия с механизмом находится в виртуальной файловой системе **procfs** по пути `/proc/<PID>/`:

| Файл | Диапазон | Назначение |
| :--- | :--- | :--- |
| **`oom_score`** | 0 – 1000 | Текущий рейтинг, рассчитанный ядром (только чтение). |
| **`oom_score_adj`** | -1000 – 1000 | Пользовательская надбавка к рейтингу (чтение/запись). |
| **`oom_adj`** | -17 – 15 | Устаревший интерфейс управления (не рекомендуется к использованию). |

### Факторы, влияющие на рейтинг (oom_score)

**Увеличивают риск завершения:**

- Высокое потребление резидентной памяти (RSS).
- Наличие большого количества дочерних процессов, также потребляющих память.
- Высокое значение `nice` (низкий приоритет планирования).
- Малое время работы процесса (новые процессы считаются менее ценными, чем долгоживущие).

**Снижают риск завершения:**

- Работа от имени пользователя `root` (незначительный бонус).
- Наличие прямого доступа к оборудованию.
- Отрицательное значение `oom_score_adj`.

## Практические сценарии

### Просмотр текущих рейтингов системы

Для быстрого поиска потенциальных жертв можно использовать однострочный сценарий:

```bash
# Вывод топ-10 процессов по oom_score
for p in /proc/[0-9]*; do
    pid=${p##*/}
    [ -r $p/oom_score ] && printf "%4s %8s %s\n" \
        "$(cat $p/oom_score 2>/dev/null)" \
        "$pid" \
        "$(cat $p/comm 2>/dev/null)"
done 2>/dev/null | sort -nr | head -10
```

### Защита критически важного процесса

Если необходимо гарантировать выживание демона (например, базы данных), следует установить минимальное значение корректировки:

```bash
# Установка максимальной защиты (доступно только root)
echo -1000 | sudo tee /proc/<PID>/oom_score_adj

# Проверка примененного значения
cat /proc/<PID>/oom_score_adj
```

Значение `-1000` полностью исключает процесс из алгоритма выбора жертвы (рейтинг станет равным 0).

## Дополнительная информация

### Взаимодействие с контрольными группами (cgroups)

В современных средах (Docker, Kubernetes) OOM Killer может срабатывать не только при нехватке общей памяти системы, но и при достижении лимита конкретной группы процессов. В cgroups v2 существует параметр `memory.oom.group`, который заставляет ядро убивать все процессы в группе одновременно при превышении лимита любым из них.

Подробнее см. раздел [**OOM Killer в контейнерах**](./oom_killer_containers.md).

### Код завершения процесса

Процесс, убитый OOM Killer, всегда завершается с **Exit Code 137**. Это сумма базового кода 128 и номера сигнала 9 (SIGKILL).

### Историческая справка

- Механизм был значительно переработан в ядре 2.6.
- В ядре 3.7 интерфейс `oom_score_adj` стал основным, обеспечивая линейную зависимость от объема памяти.
- В ядре 4.19 появилась поддержка **PSI (Pressure Stall Information)**, позволяющая более точно предсказывать наступление OOM.
