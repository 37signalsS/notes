# Планирование процессов в Linux

## Определения

**Планировщик ядра (Scheduler)**
Компонент ядра, который решает, какой из готовых к выполнению процессов ([`Runnable`](./process_states.md)) получит процессорное время. Его главная задача — эффективно и справедливо распределять ресурсы CPU.

**Переключение контекста (Context Switching)**
Процесс сохранения состояния одного процесса и восстановления состояния другого для переключения CPU на его выполнение. Это основа многозадачности.

**Load Average (LA)**
Показатель средней нагрузки, отражающий среднее число процессов в очереди на исполнение (состояния `Runnable` и `Uninterruptible Sleep`) за 1, 5 и 15 минут.

## Основные концепции

### Планировщик Linux

С точки зрения планировщика ядра Linux, фундаментальной единицей планирования является **"задача" (task)**. В Linux нет строгого разделения между процессами и потоками на уровне планировщика; каждый поток рассматривается как отдельная задача.

#### Основные принципы работы планировщика

*   **Completely Fair Scheduler (CFS):** Для обычных процессов (не реального времени) в Linux используется планировщик CFS. Его главная цель — обеспечить "справедливое" распределение процессорного времени между всеми задачами в `runqueue`. CFS не использует фиксированные кванты времени, а стремится дать каждой задаче долю процессорного времени.
*   **Виртуальное время (vruntime):** CFS отслеживает, сколько времени каждая задача уже поработала, используя переменную `vruntime`. Планировщик всегда выбирает для выполнения из `runqueue` ту задачу, у которой наименьшее значение `vruntime`, то есть ту, которая получила меньше всего процессорного времени.
*   **Планирование на основе потоков:** Поскольку планировщик оперирует задачами, а каждый поток является задачей, то планирование в Linux по своей сути является планированием на основе потоков. Это означает, что потоки одного и того же процесса могут выполняться параллельно на разных ядрах процессора.
*   **Классы планирования:** В Linux существуют различные классы планирования. Помимо `SCHED_NORMAL` (для CFS), есть классы для процессов реального времени, такие как `SCHED_FIFO` (первым пришел — первым вышел) и `SCHED_RR` (циклическое обслуживание), которые имеют более высокий приоритет. Процессы реального времени будут выполняться до тех пор, пока они готовы к выполнению, даже если другие процессы "голодают".

### Runqueue: Очередь готовых задач

**Runqueue** — это фундаментальная структура данных в ядре, в которой хранятся все задачи, находящиеся в состоянии `Ready` (готовы к выполнению) и ожидающие своей очереди на процессор.

-   **У каждого CPU своя очередь:** В многопроцессорных (SMP) системах у каждого процессорного ядра есть своя собственная `runqueue`. Это позволяет ядрам принимать решения о планировании независимо друг от друга, минимизируя блокировки.
-   **Балансировка нагрузки:** Ядро постоянно следит за тем, чтобы очереди `runqueue` были сбалансированы. Если `runqueue` одного процессора становится слишком длинной, а другого — короткой, планировщик может **мигрировать** задачи с перегруженного CPU на менее загруженный.

Длина `runqueue` (отображаемая в `Load Average`) является важным показателем производительности.

### Completely Fair Scheduler (CFS)
Основной планировщик для обычных процессов (`SCHED_NORMAL`). Его цель — обеспечить "справедливое" распределение процессорного времени.
- **Виртуальное время (`vruntime`):** CFS отслеживает, сколько "виртуального" времени каждая задача уже поработала. Планировщик всегда выбирает задачу с наименьшим `vruntime`.
- **Приоритеты (`nice`):** Значение `nice` (от -20 до +19) влияет на то, как быстро накапливается `vruntime`. У процессов с высоким приоритетом (низкий `nice`) `vruntime` растет медленнее, поэтому они получают больше процессорного времени.

### Классы и политики планирования
- **`SCHED_NORMAL` (CFS):** Стандартная политика для большинства задач.
- **`SCHED_FIFO` и `SCHED_RR`:** Политики для задач реального времени. Они имеют более высокий приоритет и вытесняют обычные процессы.
    - `FIFO` (First-In, First-Out): задача выполняется до тех пор, пока сама не отдаст CPU.
    - `RR` (Round-Robin): задача выполняется в течение кванта времени, а затем перемещается в конец очереди своего приоритета.
- Подробнее о механизмах вытеснения см. в заметке [о вытесняющей многозадачности](../kernel/preemption.md).

### Приоритет процесса: `nice` и `PR`

-   **`NI` (Nice value):** Значение, которое пользователь может настраивать. Диапазон: от **-20** (самый высокий приоритет) до **+19** (самый низкий приоритет). По умолчанию большинство процессов стартуют с `NI = 0`.
-   **`PR` (Priority):** Реальный приоритет, который видит ядро. Для обычных процессов вычисляется по формуле `PR = 20 + NI`.

### Интерпретация Load Average

Значение LA необходимо соотносить с **количеством ядер процессора**.

- **LA < количества ядер**: Система не перегружена.
- **LA ≈ количеству ядер**: Система полностью утилизирована.
- **LA > количества ядер**: Система перегружена, процессы стоят в очереди.

В Linux LA учитывает процессы в состояниях **R (Running/Runnable)** и **D (Uninterruptible Sleep)**. Это значит, что высокий LA может быть вызван не только нехваткой CPU, но и медленной дисковой подсистемой или проблемами с сетью.

## Практические сценарии

### Управление приоритетом
- **`nice`**: Запускает новую команду с указанным приоритетом.
    ```bash
    # Запустить команду с самым низким приоритетом
    nice -n 19 <команда>
    ```
- **`renice`**: Изменяет приоритет уже запущенного процесса.
    ```bash
    # Повысить приоритет (только root)
    sudo renice -5 -p <PID>
    ```

### Диагностика производительности по Load Average

Высокий LA — это симптом, который требует анализа.

1. **Высокий LA, высокий `us%`/`sy%` CPU**: Узкое место — процессор. Ищите процессы, потребляющие CPU.
2. **Высокий LA, низкий `us%`/`sy%` CPU, высокий `wa%` (iowait)**: Узкое место — система ввода-вывода. Процессы копятся в состоянии `D`, ожидая диск или сеть. Используйте `iotop`, `iostat`.
3. **Однопоточное приложение**: Если LA=1, а приложение "тормозит" на многоядерной системе, вероятно, оно однопоточное и полностью утилизировало одно ядро.

## Расширенные детали

### Процессорное время vs. I/O Wait

Важно понимать, что планировщик напрямую управляет только доступом к CPU. Когда процесс переходит в состояние `D` (Uninterruptible Sleep) для ожидания операции ввода-вывода, он **удаляется из `runqueue`** и не потребляет процессорное время.

Однако, поскольку Linux включает такие процессы в расчет `Load Average`, этот показатель становится метрикой не только загрузки CPU, но и общего "спроса на ресурсы" в системе, включая диски и сеть. Это одно из ключевых отличий LA в Linux от других UNIX-систем.
