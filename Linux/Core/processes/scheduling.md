# Process Scheduling in Linux

## Определения

**Планировщик ядра (Scheduler)** — компонент ядра, решающий, какой из готовых к выполнению процессов получит процессорное время. Главная задача — эффективное и справедливое распределение CPU.

**Переключение контекста (Context Switching)** — процесс сохранения состояния одного процесса и восстановления состояния другого для переключения CPU. Основа многозадачности.

**Load Average (LA)** — показатель средней нагрузки, отражающий среднее число задач в состояниях Running, Runnable или Uninterruptible Sleep (D-state). Рассчитывается как экспоненциально взвешенное скользящее среднее (EWMA) за 1, 5 и 15 минут. В Linux включает задачи в D-state, что отличает его от большинства Unix/BSD систем.

**Runqueue** — структура данных ядра, содержащая все задачи в состоянии `Ready`, ожидающие доступа к CPU. В SMP-системах у каждого ядра своя runqueue.

Подробнее о состояниях процессов: [**Basic Concepts**](./basic_concepts.md#состояния-процесса).

## Основные концепции

### Планировщик Linux

Фундаментальной единицей планирования в Linux является **"задача" (task)**. Планировщик не различает процессы и потоки — каждый поток рассматривается как отдельная задача.

#### Эволюция планировщика

| Версия ядра | Планировщик | Описание |
| :--- | :--- | :--- |
| **2.6.0 – 6.5** | **CFS** (Completely Fair Scheduler) | Использовал `vruntime` для справедливого распределения CPU |
| **6.6+ (октябрь 2023)** | **EEVDF** (Earliest Eligible Virtual Deadline First) | Планировщик по умолчанию, улучшенная обработка приоритетов |
| **6.12+ (ноябрь 2024)** | **EEVDF** | Код CFS полностью удалён из ядра |

> **Важно:** Ядро 6.6+ использует EEVDF. Современные дистрибутивы (RHEL 10, Ubuntu 24.04+, Fedora 39+) — на EEVDF.

#### Принципы работы EEVDF

**EEVDF** использует концепцию "eligible time" (время готовности) для каждой задачи:

- **Eligible Time** — момент, когда задача становится готова к выполнению с учётом приоритета (nice) и deadline
- **Deadline** — виртуальный срок, назначаемый задаче на основе eligible time
- **Выбор задачи** — планировщик выбирает задачу с earliest eligible virtual deadline

**Отличия от CFS:**

- Меньшая латентность для интерактивных задач
- Более точная обработка nice: влияет на deadline, а не на скорость накопления vruntime
- Улучшенная балансировка между группами задач (cgroups, threads)

#### Классы планирования

| Класс | Политика | Описание |
| :--- | :--- | :--- |
| `SCHED_NORMAL` | EEVDF | Стандартные процессы (по умолчанию) |
| `SCHED_FIFO` | FIFO | Real-time: выполняется до добровольной отдачи CPU |
| `SCHED_RR` | Round-Robin | Real-time: квант времени, затем в конец очереди |
| `SCHED_IDLE` | Idle | Самый низкий приоритет, выполняется когда нет других задач |
| `SCHED_BATCH` | Batch | Пакетные задачи, минимизация переключений контекста |

Real-time классы (`SCHED_FIFO`, `SCHED_RR`) всегда имеют приоритет над `SCHED_NORMAL`. Подробнее о вытеснении: [**Kernel Preemption**](../kernel/preemption.md).

### Runqueue и балансировка нагрузки

- **У каждого CPU своя очередь** — в SMP-системах каждое ядро имеет собственную runqueue
- **Балансировка нагрузки** — ядро автоматически перемещает задачи между runqueue для равномерного распределения
- **Длина runqueue** — косвенно отражается в Load Average

### Приоритет процесса: `nice` и `PR`

| Параметр | Диапазон | Описание |
| :--- | :--- | :--- |
| **`NI` (Nice)** | `-20` … `+19` | Настраиваемый пользователем приоритет. По умолчанию `0` |
| **`PR` (Priority)** | `0` … `39` | Реальный приоритет ядра. Для обычных процессов: `PR = 20 + NI` |

Чем ниже значение `NI`, тем выше приоритет. Процесс с `NI = -20` получает максимум CPU-времени.

### Load Average: интерпретация

Load Average показывает среднее число активных задач за 1, 5 и 15 минут (EWMA):

| Метрика | Характеристика |
| :--- | :--- |
| **LA₁ (1 мин)** | Быстрая реакция, "нагрузка здесь и сейчас" |
| **LA₅ (5 мин)** | Сглаживает всплески, для оперативной оценки |
| **LA₁₅ (15 мин)** | Долгосрочный тренд нагрузки |

**Тренды:**

- `LA₁ > LA₅ > LA₁₅` → нагрузка растёт
- `LA₁ < LA₅ < LA₁₅` → нагрузка падает
- Все три ≈ равны → стационарный режим

**Связь с числом CPU (N):**

- `LA ≈ N` → система загружена полностью
- `LA ≫ N` → очередь задач растёт (CPU или I/O bottleneck)
- `LA ≪ N` → запас по производительности есть

**Пример:** `load average: 2.50, 1.80, 1.20` на 2-ядерной системе → за последнюю минуту перегрузка (LA > N).

**Linux vs Unix:** В Linux LA включает задачи в D-state (ожидание I/O). Высокий LA при низком CPU usage обычно означает I/O bottleneck.

### Источник данных: `/proc/loadavg`

```bash
$ cat /proc/loadavg
0.88 1.03 1.09 1/1017 19782
```

| Поле | Значение |
| :--- | :--- |
| `0.88` | LA за 1 минуту |
| `1.03` | LA за 5 минут |
| `1.09` | LA за 15 минут |
| `1/1017` | `1` — Running/Runnable задач, `1017` — всего задач в системе |
| `19782` | PID последнего созданного процесса |

### Load Average (Средняя нагрузка)

**Load Average (LA)** в Linux — это среднее количество процессов, находящихся в состоянии **Running** (выполняются), **Runnable** (ожидают очереди на CPU) или **Uninterruptible Sleep** (состояние `D`, ожидание ввода-вывода).

#### Три значения Load Average
При просмотре LA всегда отображается три числа, например: `0.52, 0.40, 0.35`.
1.  **Первое (1 мин):** Текущая мгновенная нагрузка.
2.  **Второе (5 мин):** Средняя нагрузка за последние 5 минут (тренд).
3.  **Третье (15 мин):** Долгосрочная нагрузка.

**Интерпретация:**
- Если LA равен количеству ядер CPU, система загружена на 100%.
- Если LA значительно выше количества ядер, процессы стоят в очереди (возможны задержки).
- Если LA растет слева направо (`0.10, 0.50, 1.00`), нагрузка падает. Если наоборот — нагрузка растет.

#### Как посмотреть Load Average
- **`uptime`** — самый быстрый способ.
- **`top`** или **`htop`** — в верхней строке.
- **`cat /proc/loadavg`** — сырые данные из ядра.

## Практические сценарии

### Управление приоритетом

```bash
# Запустить команду с пониженным приоритетом
nice -n 19 <команда>

# Повысить приоритет запущенного процесса (только root)
sudo renice -5 -p <PID>

# Понизить приоритет запущенного процесса (любой пользователь)
renice +10 -p <PID>
```

> **Ограничение:** Обычный пользователь может только увеличивать nice (понижать приоритет). Уменьшать nice (повышать приоритет) может только `root`.

### Диагностика производительности по Load Average

| Симптом | Причина | Диагностика |
| :--- | :--- | :--- |
| **Высокий LA + высокий `us%`/`sy%`** | CPU bottleneck | `top`, `htop` — поиск CPU-ёмких процессов |
| **Высокий LA + высокий `wa%` (iowait)** | I/O bottleneck | `iotop`, `iostat` — поиск медленных дисков |
| **Высокий LA + низкий `%CPU`** | I/O wait, NFS, блокировки | `dstat`, `vmstat`, `iostat -x` |
| **LA = 1, однопоточное приложение** | Утилизировано одно ядро | `pidstat -u 1` — CPU на поток |
| **Низкий LA, высокие задержки** | Scheduler latency | `perf sched` — анализ задержек планировщика |

Подробнее: [**Анализ задержек планировщика**](../../Diagnostics/Performance/perf.md#анализ-задержек-планировщика-perf-sched).

### Проверка текущего планировщика

```bash
# Версия ядра
uname -r

# Для ядра <6.6: планировщик для блочного устройства
cat /sys/block/sda/queue/scheduler

# Для ядра 6.6+: EEVDF по умолчанию
# Проверить через debugfs (если доступен)
cat /sys/kernel/debug/sched/features
```

## Дополнительная информация

### Планировщик vs I/O Wait

Планировщик управляет только доступом к CPU. Задачи в состоянии `D` (Uninterruptible Sleep) **удаляются из runqueue** и не потребляют CPU. Однако Linux включает их в Load Average, делая эту метрикой не только загрузки CPU, но и общего "спроса на ресурсы" (диски, сеть, блокировки ФС).

### Pressure Stall Information (PSI)

Начиная с ядра 4.20, Linux предоставляет метрики PSI — более точную альтернативу Load Average для оценки давления ресурсов:

```bash
# Проверить поддержку PSI
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
```

PSI показывает процент времени, в течение которого задачи простаивали из-за нехватки CPU, памяти или I/O. В отличие от LA, PSI разделяет причины задержек. Подробнее: [**PSI**](../kernel/psi.md).

### CPU Pinning и планировщик

**CPU Pinning** — механизм привязки процессов к конкретным ядрам CPU. Гарантирует, что планировщик не будет перемещать задачу между ядрами. Полезно для NUMA-оптимизации и снижения cache misses. Подробнее: [**CPU Pinning**](../cpu_pinning.md).
