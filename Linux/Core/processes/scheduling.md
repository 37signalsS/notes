# Планирование процессов в Linux

## Определения

**Планировщик ядра (Scheduler)** — высокопроизводительный компонент ядра Linux, определяющий очередность и продолжительность выполнения задач на центральном процессоре (CPU). Его цель — обеспечить баланс между пропускной способностью системы (throughput) и минимальными задержками (latency) для интерактивных приложений.

**Переключение контекста (Context Switching)** — процедура сохранения состояния текущего процесса (регистры, стек, программный счетчик) и восстановления состояния другого процесса. Различают два типа:
- **Добровольное (Voluntary):** Процесс сам отдает CPU, ожидая завершения ввода-вывода или засыпая.
- **Принудительное (Involuntary):** Планировщик прерывает процесс по истечении его кванта времени (preemption) или при появлении более приоритетной задачи.

**Средняя нагрузка (LA — Load Average)** — показатель, отражающий среднее количество задач в состояниях выполнения (Running), готовности к выполнению (Runnable) или непрерываемого сна (Uninterruptible Sleep / D-state). Рассчитывается как экспоненциально взвешенное скользящее среднее (EWMA) за периоды в 1, 5 и 15 минут.

**Очередь выполнения (Runqueue)** — фундаментальная структура данных ядра, содержащая список всех задач в состоянии готовности. В SMP-системах (Symmetric Multi-Processing) каждое ядро CPU имеет собственную индивидуальную очередь выполнения.

Подробнее о состояниях процессов см. в разделе [**Основные концепции**](./basic_concepts.md#состояния-процесса).

## Основные концепции

### Эволюция планировщиков Linux

В Linux фундаментальной единицей планирования является **"задача" (task)**. Ядро не делает жестких различий между процессами и потоками — каждый поток рассматривается как отдельная задача со своей структурой `task_struct`.

| Версия ядра | Планировщик | Описание |
| :--- | :--- | :--- |
| **2.6.23 – 6.5** | **CFS (Completely Fair Scheduler)** | Использовал виртуальное время выполнения (`vruntime`) и красно-черные деревья для балансировки. |
| **6.6+ (2023 г.)** | **EEVDF (Earliest Eligible Virtual Deadline First)** | Текущий планировщик по умолчанию. Обеспечивает более точное соблюдение приоритетов и низкую латентность. |

#### Принцип работы EEVDF

Планировщик **EEVDF** заменяет концепцию накопления `vruntime` на расчет времени готовности и дедлайнов:
- **Eligible Time (Время готовности):** Момент времени, когда задача теоретически должна получить доступ к ресурсам CPU с учетом её приоритета (`nice`) и веса.
- **Virtual Deadline (Виртуальный дедлайн):** Срок, к которому задача должна завершить свой очередной квант времени.
- **Выбор задачи:** Из списка задач, ставших "готовыми" (eligible), выбирается та, у которой самый ранний виртуальный дедлайн.

**Преимущества:**
- Устранение проблемы "latency lag", когда интерактивные задачи долго ждали CPU после пробуждения в CFS.
- Более предсказуемое распределение времени CPU для задач с разными приоритетами.

### Классы и политики планирования

Планировщик использует иерархию классов. Если задача из более высокого класса готова к выполнению, она всегда вытесняет задачу из более низкого класса.

| Класс | Политика | Описание |
| :--- | :--- | :--- |
| **Stop** | N/A | Самый высокий приоритет. Используется для миграции задач и выключения CPU. |
| **Deadline** | `SCHED_DEADLINE` | Гарантированное время выполнения (Real-time). |
| **Real-time** | `SCHED_FIFO`, `SCHED_RR` | Задачи реального времени с фиксированными приоритетами (1–99). |
| **Fair** | `SCHED_NORMAL`, `SCHED_BATCH` | Обычные задачи (EEVDF). |
| **Idle** | `SCHED_IDLE` | Фоновые задачи с минимальным приоритетом. |

### Приоритеты процессов: nice и PR

**Этимология и концептуальная метафора:** Термин *nice* заимствован из английского, где он означает «вежливый», «любезный». Эта метафора — ключ к пониманию контринтуитивной природы шкалы: **«вежливый» процесс уступает дорогу другим**, отдавая их в очередь раньше себя. Поэтому высокое значение `nice` означает *«более вежливый»* → *«меньше процессорного времени»* → **низкий приоритет**. Низкое или отрицательное значение означает *«наглый»*, *«не уступающий»* → **высокий приоритет**. Именно эта «вывернутая наизнанку» логика и порождает большинство ошибок: администратор ставит значение «побольше», думая, что даёт «побольше» ресурсов.

**Фактор уступчивости (`NI`, Nice)** — единственная «ручка» во всём выводе мониторинговых утилит, доступная пользователю для прямого управления: число, по которому ядро определяет свою политику в отношении процессов, конкурирующих за CPU. Ключевое правило обратно интуиции: **чем выше фактор уступчивости, тем ниже приоритет процесса**. «Вежливый» процесс уступает дорогу; низкое или отрицательное значение означает высокий приоритет — процесс лезет вперёд всех. Большинство ошибок в этой теме растёт отсюда: администратор ставит значение «побольше», думая, что даёт «побольше».

1. **Диапазон значений:** зависит от системы. В Linux — от `-20` (высший приоритет) до `+19` (низший); во BSD — от `-20` до `+20`. Обычный процесс стартует с `0`.
2. **`PR` (Priority):** внутренний приоритет ядра. Для обычных процессов итоговый приоритет вычисляется как `PR = 20 + NI` (поэтому у процесса с `NI = 0` в колонке `PR` утилиты [top](../../Diagnostics/Processes/top.md) отображается `20`). Для RT-процессов отображается как `rt` (что соответствует внутренним значениям < 0).
3. **Вес, а не квота:** nice — это не скорость и не выделенная доля, а вес задачи. Планировщик раздаёт процессорное время пропорционально весам: каждый шаг по шкале умножает вес примерно на 1.25. Отсюда практические ориентиры: один шаг — около 10% разницы в доле CPU, пять шагов — почти вдвое, между крайними значениями — тысячи раз (в таблице весов ядра `nice -20` соответствует весу 88761, а `nice +19` — всего 15).
4. **Доля, а не запрет:** если машина простаивает и конкурентов нет, процесс с уступчивостью `19` спокойно потребляет все 100% CPU — делить не с кем. Уступчивость включается только в момент конкуренции за процессор. Поэтому утверждение «поставил бэкапу 19 — теперь он никому не мешает» верно лишь наполовину: на CPU он действительно не мешает, но см. ниже про I/O.
5. **Наследование:** если пользователь не предпринимает специальных мер, дочерний процесс наследует фактор уступчивости родителя. Запущенный скрипт, поднимающий ещё пять программ, передаёт вес всей цепочке до последнего потомка: придавив родителя, придавливаешь всё дерево.

#### Храповик приоритетов (необратимое действие)

Владелец процесса может **увеличить** свой фактор уступчивости (сделать себе хуже), но **не может уменьшить** его — даже чтобы вернуть стандартное значение. Поднял с `0` до `10` — обратной дороги нет: храповик щёлкает только в одну сторону, и никакой командой от имени пользователя его назад не провернуть. Это редкий пример действия в Linux, которое невозможно отменить штатными средствами. При попытке запустить процесс с отрицательным значением nice (повысить приоритет) обычный пользователь получает `Permission denied`.

Причины столь жёсткого запрета:
1. Если бы значение можно было опускать, любой пользователь поставил бы своей программе `-20` и забрал бы машину себе целиком.
2. Запрет распространяется даже на возврат к нулю, чтобы процессы с низким приоритетом не могли порождать высокоприоритетных потомков: иначе схема обхода тривиальна — придавленный процесс рожает ребёнка с нормальным приоритетом и работает через него. Храповик закрывает и эту лазейку, поскольку дети наследуют уже придавленное значение и поднять его тоже не могут.

Исключение одно: **суперпользователь** может устанавливать произвольные значения любому процессу любого пользователя — в любую сторону. Это же делает nice инструментом административного воздействия: одной строкой можно придавить не отдельный процесс, а все процессы пользователя.

Тонкости реализации:
- С ядра 2.6.12 частичный «обратный ход» возможен, если процессу назначен лимит `RLIMIT_NICE`: минимальное значение nice, которое процесс может установить, равно `20 - rlim_cur`. При лимите по умолчанию (`0`) снижение запрещено полностью.
- Процесс с capability `CAP_SYS_NICE` ограничения храповика не действует (см. [ограничения ресурсов](./resource_limits_concepts.md)).

### Вытеснение (Preemption)

Linux поддерживает различные модели вытеснения, настраиваемые при компиляции ядра (`CONFIG_PREEMPT_*`) или переключаемые динамически через **PREEMPT_DYNAMIC** (ядро 5.x+):

- **No Preemption (Server):** Вытеснение только в точках перепланирования. Максимальная пропускная способность.
- **Voluntary Preemption (Desktop):** Добавляет явные точки вытеснения в код ядра. Баланс между скоростью и отзывчивостью.
- **Full Preemption (Low-Latency Desktop):** Почти любой код ядра может быть вытеснен. Минимальные задержки, полезно для аудио и Real-time.
- **Lazy (Standard 2026, ядро 6.13+):** Откладывает вытеснение обычных задач до безопасных точек, но сохраняет мгновенное для RT. Является значением по умолчанию в современных дистрибутивах.

**PREEMPT_DYNAMIC** позволяет менять модель на лету без перезагрузки, используя Static Keys. Проверить активную модель:

```bash
dmesg | grep -i preempt
# → [    0.000000] Dynamic Preempt: lazy
cat /sys/kernel/debug/sched/preempt 2>/dev/null
# → none voluntary full lazy (rt)
```

Подробнее об архитектуре вытеснения, `PREEMPT_RT`, `Proxy Execution` и взаимодействии с синхронизацией см. в разделе [**Вытесняющая многозадачность ядра**](../kernel/preemption.md).

### Интерпретация Load Average

В расчет LA включаются процессы в состоянии непрерываемого сна (**D-state**), ожидающие I/O. Поэтому высокий LA при низком %CPU — признак проблем с диском, сетью (NFS) или блокировками в ядре.

**Связь с количеством ядер CPU (N):**
- `LA ≈ N`: Система загружена полностью, очередей нет.
- `LA > N`: Задачи стоят в очереди. Если LA значительно превышает N, производительность деградирует из-за перегрузки.
- `LA < N`: Имеется запас вычислительной мощности.

### Тонкая настройка планировщика (/proc/sys/kernel/sched_*)

Ядро Linux exposes несколько ключевых параметров в `/proc/sys/kernel/`, влияющих на поведение EEVDF/CFS:

| Параметр | Назначение | Типовое значение |
| :--- | :--- | :--- |
| `sched_min_granularity_ns` | Минимальный квант времени для обычных задач. Меньшее значение → выше отзывчивость, но больше переключений. | 10 000 000 (10 мс) |
| `sched_wakeup_granularity_ns` | Порог, при котором пробуждаемая задача может вытеснить текущую. Управляет «резвостью» интерактивных задач. | 15 000 000 (15 мс) |
| `sched_migration_cost_ns` | Стоимость миграции задачи между ядрами в наносекундах. Высокое значение удерживает задачи на текущем ядре, уменьшая cache-miss. | 10 000 000 (10 мс) |
| `sched_child_runs_first` | Если `1`, дочерний процесс получает приоритет при создании. Полезно для fork-heavy workloads. | 0 |

**Практическое применение:**

```bash
# Просмотр текущих значений
sysctl kernel.sched_min_granularity_ns
# → kernel.sched_min_granularity_ns = 10000000

# Временное изменение (до перезагрузки)
sudo sysctl -w kernel.sched_wakeup_granularity_ns=5000000

# Постоянное изменение — создайте файл в /etc/sysctl.d/
echo "kernel.sched_min_granularity_ns = 8000000" | \
  sudo tee /etc/sysctl.d/99-scheduler-tuning.conf
sudo sysctl --system
```

> **Важно:** Тюнинг этих параметров полезен для специализированных workloads (HFT, high-frequency trading, real-time audio). Для большинства серверных нагрузок значения по умолчанию являются оптимальными.

### Источники данных: /proc/loadavg

```bash
cat /proc/loadavg
# → 0.50 0.40 0.30 1/800 12345
#   ↑ LA1  ↑ LA5  ↑ LA15 ↑ активные/всего ↑ последний PID
```

## Практические сценарии

### Управление приоритетами (nice, renice)

Работу делят ровно две команды: `nice` устанавливает фактор уступчивости **при создании** процесса (принимает строку запуска), `renice` изменяет приоритет **уже выполняющегося** процесса (принимает PID, имя пользователя или группу процессов).

Ключевое практическое различие: `nice` работает с именем команды на старте, `renice` — с уже запущенным PID. Это позволяет «придавить» зависший или вышедший из-под контроля процесс без перезапуска и потери данных.

```bash
# Простой пример: запустить таймер с пониженным приоритетом в фоне
nice -n 10 sleep 500 &
# Проверка: в колонке NI отображается установленное значение
ps -o pid,ni,comm -p $!
# →   PID  NI COMMAND
# → 12345  10 sleep

# Запуск процесса с пониженным приоритетом (+5 к уступчивости).
# Классика: архивация, сборка проекта, перекодирование видео — работа несрочная
nice -n 5 /usr/bin/longtask

# Повышение приоритета работающего процесса до -5.
# Отрицательное значение = повышение приоритета, поэтому нужен sudo
renice -5 -p 8123

# Массовое понижение приоритета ВСЕХ процессов пользователя.
# Только суперпользователь может менять чужие процессы
sudo renice 5 -u backup_user

# То же для целой группы процессов
sudo renice 5 -g <PGID>
```

Проверка результата:

```bash
ps -o pid,ni,comm -p 8123
# →   PID  NI COMMAND
# →  8123  -5 longtask
```

При выполнении `renice` система выводит отчёт: старое и новое значение приоритета. Это позволяет немедленно убедиться, что изменение применено корректно.

#### Ловушка знаков и порядка аргументов: приращение против абсолютного значения

Две внешне похожие строки меняют приоритет противоположно:

```bash
nice -n 5 my_command   # приращение: процесс станет УСТУПЧИВЕЕ (приоритет ниже)
renice 5 -p <PID>      # абсолютное значение: процесс станет НАГЛЕЕ (приоритет выше)
```

Причина в том, что способ установки желаемого приоритета реализован по-разному даже в рамках одной системы:
- `nice` принимает ключ `-N` — **насколько сдвинуть** значение относительно текущего.
- `renice` (util-linux) трактует первый аргумент как **абсолютное** значение приоритета. Историческая особенность: ключ `-n` у `renice` тоже задаёт абсолютное значение и лишь с переменной окружения `POSIXLY_CORRECT` становится относительным; явные ключи `--priority` (абсолютное) и `--relative` (приращение) работают одинаково при любом окружении.
- Во FreeBSD наоборот: `renice` без ключей работает с абсолютными значениями, а с ключом `-n` — с приращением.

**Экзаменационная ловушка:** у `renice` нет флага `-n` в том смысле, в каком он есть у `nice`. В тестовых заданиях часто подсунут вариант с лишним `-n` или перепутанным порядком аргументов (`renice -p 12 9876` вместо `renice 12 -p 9876`). Правильный порядок: желаемый приоритет — сразу после команды БЕЗ флага, флаг `-p`/`-u`/`-g` — в самом конце перед идентификатором.

**Экзаменационная ловушка (значение 20):** Шкала `nice` в Linux строго ограничена диапазоном **от -20 до +19**. Значение `+20` **не существует** — любые попытки установить его приводят к ошибке или автоматической урезке до `+19`. На экзаменах типичный вопрос «какое значение nice соответствует максимальному приоритету?» порождает две классические ошибки: (1) выбор `+19` (самое большое число, но это **минимальный** приоритет); (2) выбор `20` (забывают о верхней границе шкалы). Правильный ответ — **`-20`** (самое маленькое число = максимальный приоритет). Проверить диапазон можно командой `nice -n 20 true` — система вернёт ошибку или предупреждение о недопустимом значении.

Знаки `+`/`-` обязательны только для интерпретатора команд; остальные реализации их игнорируют. Отсюда практическое следствие: чтобы дать новой программе высокий приоритет, придётся написать два минуса подряд — выглядит как опечатка, но это единственный корректный способ:

```bash
sudo nice -n -5 my_command
```

#### Встроенная версия nice в оболочке

Существует версия `nice`, встроенная прямо в оболочку: она есть в `csh` и ряде других оболочек, но отсутствует в `bash`. Если не указать полное имя команды, будет вызвана встроенная версия со своим синтаксисом (`+приращение` / `-приращение` без ключа `-n`). Одна и та же строка на двух машинах отработает по-разному просто потому, что у пользователей разные оболочки. Лечится занудно, но надёжно — вызовом по полному пути:

```bash
/usr/bin/nice -n 19 ./my_heavy_script.sh
```

#### Ограничение: nice не управляет памятью и вводом-выводом

Производительность подсистемы ввода-вывода растёт далеко не так стремительно, как быстродействие CPU, поэтому диски стали основным узким местом большинства систем — а фактор уступчивости на подсистемы управления памятью и I/O **не влияет вообще**. Следствие обидное: даже низкоприоритетный процесс способен монополизировать эти ресурсы или захватить непропорционально большую их часть. Бэкап с уступчивостью `19` не мешает никому на процессоре, но всё равно кладёт сервер, забив очередь к диску. Высокий `%iowait` (см. [диагностику iowait](../../Diagnostics/Performance/DiskIO/iowait_and_latency.md)) nice'ом не лечится в принципе — лечится другой командой.

Правильная фоновая задача комбинирует обе ручки: минимальный CPU-приоритет, следом класс Idle для I/O, и только потом сама команда:

```bash
nice -n 19 ionice -c 3 ./backup.sh
```

Классы `ionice` (Real-time / Best-effort / Idle), зависимость от активного планировщика I/O и ограничения описаны в разделе [ionice — управление приоритетами ввода-вывода](../../Diagnostics/Filesystem/ionice.md).

#### Современная практика

Администраторам теперь редко приходится определять приоритеты вручную: машины стали намного быстрее, и планировщик, как правило, обслуживает все процессы достаточно оперативно. Типовые точки применения ручки сегодня:
- постоянный приоритет для сервиса — директива `Nice=` (и `IOSchedulingClass=` для I/O) в unit-файле systemd;
- задачи с постоянной потребностью в высоком приоритете — классы планирования реального времени (`SCHED_FIFO`/`SCHED_RR` через `chrt`; в колонке `PR` они отображаются как `rt`);
- жёсткие гарантии и изоляция групп процессов — cgroups (`cpu.weight`, `cpu.max`) вместо nice.

#### Диагностика: наблюдение за значениями NI в top

Колонка **`NI`** в интерактивных мониторах ([`top`](../../Diagnostics/Processes/top.md), `htop`) отображает текущий фактор уступчивости процесса. Для диагностики конкуренции за CPU полезно:

1. **Отсортировать по NI:** В `top` нажмите `f`, выберите поле `n` (NI) для сортировки, затем `Enter` — процессы с самыми «наглыми» (отрицательными) приоритетами встанут в начале списка.
2. **Обратить внимание на системные процессы:** Многие фоновые демоны (например, `kswapd`, некоторые `kworker`) запускаются с ненулевыми значениями NI — это намёк на их роль в системе. Процессы с `NI = -5` и ниже (или `PR < 20`) требуют повышенного внимания: они имеют прямой или косвенный доступ к CPU в обход обычных задач.
3. **Проверить границы:** Команда `nice -n 20 true` завершится ошибкой — система не допускает значение `+20`, максимальное допустимое — `+19`. Аналогичная проверка для нижней границы: `nice -n -21 true` потребует root и вернёт ошибку.

### Привязка к ядрам (CPU Affinity)

Позволяет закрепить процесс за конкретными ядрами CPU для минимизации промахов кэша и исключения миграции между ядрами. В современных ядрах (6.6+) с планировщиком EEVDF affinity всё чаще используется не для «борьбы» с планировщиком, а для **гарантии кэш-локальности** и предсказуемости доступа к памяти.

**Базовые примеры:**

```bash
# Запуск процесса на 0 и 1 ядрах
taskset -c 0,1 ./my_app

# Изменение привязки для работающего процесса
taskset -cp 2,3 <PID>

# Проверка текущей маски affinity
taskset -p <PID>
# → pid 1234's current affinity mask: 0x3
```

**NUMA-топология:** На многосокетных системах (`2P`, `4P`) или чиплетных архитектурах (AMD EPYC, Intel Xeon) привязка должна учитывать локальность памяти. Используйте `numactl --hardware` для просмотра топологии и `numactl --cpunodebind=0 --membind=0` для привязки к конкретному NUMA-узлу.

**Systemd-сервисы:** Для постоянного управления affinity используйте директиву `CPUAffinity=` в unit-файле:

```ini
# /etc/systemd/system/myapp.service
[Service]
ExecStart=/usr/bin/my_app
CPUAffinity=0 1 2 3

# Или диапазоном
CPUAffinity=0-3
```

```bash
systemctl daemon-reload && systemctl restart myapp
taskset -pc $(systemctl show -p MainPID --value myapp)
```

**Внутреннее устройство:** Ядро хранит маску разрешенных ядер в поле `cpus_allowed` структуры `task_struct`. Системные вызовы `sched_setaffinity()` / `sched_getaffinity()` изменяют и возвращают эту маску. Текущее значение можно прочитать через `/proc/<PID>/status`:

```bash
grep Cpus_allowed_list /proc/<PID>/status
# → Cpus_allowed_list:  0,2,4
```

> **Важно:** Даже при наличии affinity ядро может мигрировать задачу между разрешенными ядрами для балансировки. Полная изоляция от миграции достигается через `cpuset.cpus.exclusive` (ядро 6.x+) или `isolcpus`. Детальный разбор механизмов, ограничений, безопасность и тонкости пиннинга см. в разделе [**Привязка к процессору (CPU Pinning)**](../cpu_pinning.md).

### Управление CPU через systemd

В production-средах ручное управление `nice`/`renice` через cron или скрипты уступает место декларативному подходу через unit-файлы. Systemd предоставляет набор директив для управления планированием CPU и I/O:

```ini
# /etc/systemd/system/database.service
[Service]
ExecStart=/usr/bin/postgres

# --- CPU приоритет ---
Nice=-10
CPUWeight=50          # Относительный вес (по умолчанию 100). Действует в cgroups v2.
CPUQuota=150%         # Жесткий лимит: 1.5 ядра. Превышение вызывает троттлинг.

# --- I/O приоритет ---
IOSchedulingClass=realtime
IOSchedulingPriority=2

# --- Отслеживание ---
CPUAccounting=true
```

| Директива | Назначение | Примечание |
| :--- | :--- | :--- |
| `Nice=` | Фактор уступчивости (`-20` … `19`). | Отрицательные значения требуют `CapabilityBoundingSet=CAP_SYS_NICE` или root. |
| `CPUWeight=` | Относительный вес для fair scheduling. | В cgroups v2 соответствует `cpu.weight`. По умолчанию `100`. |
| `CPUQuota=` | Жесткий лимит CPU в процентах. | `50%` = половина одного ядра; `150%` = 1.5 ядер. |
| `IOSchedulingClass=` | Класс планирования I/O. | `idle`, `best-effort` (по умолчанию), `realtime`. |
| `IOSchedulingPriority=` | Приоритет внутри класса I/O. | Диапазон зависит от класса (0–7 для best-effort). |

**Проверка применения:**

```bash
# Показать cgroup юнита и значения
systemctl show database.service -p CPUWeight -p CPUQuota -p Nice -p IOSchedulingClass
# → CPUWeight=50
# → CPUQuota=150%
# → Nice=-10
# → IOSchedulingClass=realtime

# Проверить троттлинг через cpu.stat
cat /sys/fs/cgroup/system.slice/database.service/cpu.stat
# → usage_usec 1234567890
# → throttled_usec 1234    ← если > 0, троттлинг активен
```

Для разовых задач используйте `systemd-run`:

```bash
# Запустить бэкап с низким приоритетом CPU и I/O
sudo systemd-run --scope \
  --nice=19 \
  --cpu-weight=10 \
  --io-weight=10 \
  /usr/local/bin/backup.sh
```

> **См. также:** [Контрольные группы (cgroups)](../cgroups.md) — полный обзор иерархии и параметров.

### Изоляция ядер (Isolcpus)

Параметр загрузки ядра `isolcpus` позволяет полностью исключить указанные ядра из общего планирования. Задачи на них можно запустить только принудительно через `taskset`, `chrt` или `cgroups`. Это используется для критически важных задач реального времени и высоконагруженных сетевых приложений (DPDK).

**Пример параметра загрузки (GRUB):**

```bash
# /etc/default/grub
GRUB_CMDLINE_LINUX_DEFAULT="... isolcpus=2-7 nohz_full=2-7 rcu_nocbs=2-7"
```

После перезагрузки ядра 2–7 исключаются из домена балансировки (`sched_domain`). На них больше не работают системные таймеры (`tickless` через `nohz_full`), что снижает джиттер.

**Современная альтернатива — cpuset exclusive partitions (ядро 6.x+):**

```bash
# Создание эксклюзивной партиции без перезагрузки
sudo mkdir -p /sys/fs/cgroup/isolated
echo "4-7" | sudo tee /sys/fs/cgroup/isolated/cpuset.cpus
echo "isolated" | sudo tee /sys/fs/cgroup/isolated/cpuset.cpus.partition
```

В отличие от `isolcpus`, `cpuset.cpus.exclusive` позволяет динамически добавлять и удалять ядра из изоляции.

> **Важно:** На изолированных ядрах обычные задачи не планируются автоматически. Если привязать к ним процесс без явного указания affinity, он останется в очереди на housekeeping-ядрах. Детальная настройка `nohz_full`, `rcu_nocbs`, IRQ affinity и NUMA-топология описана в разделе [**Изоляция CPU**](../kernel/cpu_isolation.md).

### Real-time политики (`chrt`, `schedtool`)

Планировщик Linux предоставляет политики реального времени (`SCHED_FIFO`, `SCHED_RR`) с фиксированными приоритетами 1–99. Задачи RT вытесняют все обычные (`SCHED_NORMAL`) задачи, включая те, что имеют отрицательный `nice`.

**chrt — просмотр и установка политик:**

```bash
# Запуск RT-задачи с политикой SCHED_FIFO, приоритет 50
sudo chrt -f 50 ./rt_worker

# Политика SCHED_RR (Round-Robin) с приоритетом 30
sudo chrt -r 30 ./rt_worker

# Просмотр политики работающего процесса
chrt -p $(pgrep rt_worker)
# → pid 1234's current scheduling policy: SCHED_FIFO
# → pid 1234's current scheduling priority: 50

# Сброс политики на обычную (SCHED_OTHER)
sudo chrt -o 0 <PID>
```

**schedtool — расширенное управление:**

`chrt` не позволяет изменять `sched_rr_quantum` (квант времени для RR) или политику `SCHED_DEADLINE`. Для этого используйте `schedtool` (пакет `schedtool`):

```bash
# Установка SCHED_RR с квантом 10 мс
sudo schedtool -R -t 10000 <PID>

# Просмотр всех параметров планирования
schedtool -p $(pgrep rt_worker)
```

**Комбинация с CPU Affinity:**

Для критически важных RT-задач комбинируйте политику и привязку:

```bash
# RT-задача, привязанная к ядру 0
sudo chrt -f 50 taskset -c 0 ./rt_worker
```

> **Предупреждение:** Ошибка в RT-задаче (бесконечный цикл без `sleep`/`yield`) может занять ядро на 100% и заблокировать всю систему. Всегда тестируйте RT-код в изолированной среде. Для production используйте `SCHED_DEADLINE` или cgroups с `cpu.max`, которые предоставляют гарантии времени без риска монополизации.

### Мониторинг и диагностика

| Инструмент | Назначение |
| :--- | :--- |
| **top / htop** | Интерактивный просмотр LA, %CPU, NI, PR. В `top` сортируйте по `NI` (`f` → `n`) для выявления задач с отрицательными приоритетами. |
| **vmstat 1** | Просмотр очереди выполнения (`procs r`), `b` (непрерываемый сон), `si`/`so` (swapping). Ключевая метрика — столбец `r`: если он стабильно > N (количество ядер), система перенасыщена. |
| **pidstat -w 1** | Переключения контекста: `cswch/s` (добровольные) и `nvcswch/s` (принудительные). Всплески `nvcswch/s` указывают на нехватку CPU. |
| **sar -q** | Исторические данные Load Average и длины очереди. Требует пакет `sysstat`. |
| **chrt** | Просмотр и изменение политик реального времени. |
| **perf sched** | Детальный анализ задержек планировщика, миграций и вытеснений. |

**Примеры диагностики:**

```bash
# 1. vmstat: количество задач в очереди (столбец r)
vmstat 1
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
#  2  0      0 2800000  50000 600000    0    0     1     2   12   45  5  2 93  0  0
# ↑ r=2: две задачи в очереди на 4 ядра — система не перегружена

# 2. pidstat: переключения контекста по процессам
pidstat -w -p ALL 1
#   UID       PID   cswch/s nvcswch/s  Command
#     0      1234     120.5       2.1  postgres
# ↑ высокий cswch/s — процесс часто блокируется на I/O

# 3. sar: Load Average и длина очереди за последний час
sar -q -f /var/log/sysstat/sa$(date +%d)
# 12:00:01 PM   runq-sz  plist-sz   ldavg-1   ldavg-5  ldavg-15
# 12:00:01 PM       2      380      1.25      1.10      0.95

# 4. perf sched: задержки планировщика (требует root)
sudo perf sched latency
#   Task              |   CPU count |   avg delay | total delay | ...delays
#   postgres: writer  |         256 |     12.3 us |   3145.12 ms | migrations=5

# 5. perf sched: map и timehist (требует root)
sudo perf sched record -- sleep 5
sudo perf sched latency
```

**Виртуализация и CPU Steal (`%st`):**

В облачных/виртуальных средах (KVM, VMware, Hyper-V) столбец `%st` в `top`/`mpstat` показывает время, когда гипервизор забирал CPU у гостевой системы. Высокий `%st` (значительное отличное от нуля) означает, что соседние виртуальные машины конкурируют за физические ядра, и планировщик гостя не может получить обещанное время.

```bash
mpstat -P ALL 1
# CPU  %usr   %nice    %sys %iowait    %irq   %soft  %steal  %idle
# 0    45.00    2.00    3.00    1.00    0.50    1.00   15.00  32.50
# ↑ %steal=15% — гипервизор активно перераспределяет время; guest лишен гарантий
```

**Diagnostic rule of thumb:**
- `vmstat r` постоянно > N: нехватка CPU или слишком низкие приоритеты у фоновых задач.
- `pidstat nvcswch/s` > 5000 на процесс: подозрение на «thrashing» или неправильно настроенный nice.
- `perf sched latency` показывает миграции > 1000 на задачу: проблема с affinity или балансировкой NUMA.

### Диагностика типичных проблем планирования

| Проблема | Симптомы | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Высокий LA при свободном CPU** | LA > N, `%id` > 50% | `vmstat 1` → столбец `b` > 0 | Процессы в D-state: диск, NFS, блокировки ядра. Проверьте `iostat`, `cat /proc/<PID>/wchan`. |
| **CFS Throttling** | Задержки ~100 мс, `%wa` растет | `cat /sys/fs/cgroup/.../cpu.stat` → `nr_throttled > 0` | Увеличить `cpu.max` / `cpu.cfs_quota_us`, уменьшить количество конкурентов. |
| **Контекст-свитч storm** | `%sy` > 30%, `cs` > 100K/s | `pidstat -w 1`, `vmstat 1` → `cs` | Понизить `nice` фоновых задач, уменьшить количество рабочих процессов (workers), проверить spinlock contention через `perf lock`. |
| **RT-задача не получает CPU** | RT-задача зависает, высокий LA | `chrt -p <PID>`, `dmesg \| grep -i "xentic"` | Проверить, что `CONFIG_PREEMPT_RT` активен, нет starvation со стороны других RT-задач, `isolcpus` сконфигурирован. |
| **Миграции между ядрами** | Высокий cache-miss, нестабильная latency | `perf stat -e sched:sched_migrate -p <PID> sleep 5` | Установить `taskset`/`CPUAffinity`, проверить `sched_domain` через `cpupat`. |
| **CPU Steal > 0** | `%st` > 10%, sluggishness | `mpstat -P ALL 1` | На гипервизоре: уменьшить oversubscription, изменить affinity доменов, запросить гарантированные cores. |
| **Nice храповик** | Процесс невозможно вернуть к `NI=0` | `ps -o pid,ni,comm -p <PID>` | Только root может установить произвольное `nice`. Для обычных пользователей — перезапуск процесса. |

## Дополнительная информация

### Информация о давлении на ресурсы (PSI)

**Pressure Stall Information (PSI)** — современный механизм, заменяющий Load Average в задачах точного мониторинга. PSI показывает процент времени, в течение которого задачи ожидали CPU, память или I/O.
- **Some:** Хотя бы одна задача заблокирована.
- **Full:** Все задачи в системе (или контрольной группе) заблокированы (актуально для памяти и I/O).

Подробнее см. раздел [**PSI — статистика давления на ресурсы**](../kernel/psi.md).

### Планирование и Cgroups

Механизм **Cgroups (Control Groups)** позволяет ограничивать время CPU для групп процессов. В cgroups v2 (современные дистрибутивы Ubuntu 22.04+, RHEL 9+) контроллер `cpu` предоставляет три ключевых механизма:

| Файл | Назначение | Пример |
| :--- | :--- | :--- |
| `cpu.weight` | Относительный вес (1–10000). Аналог `cpu.shares` из v1. | `echo 100 > cpu.weight` |
| `cpu.max` | Жесткий лимит (квота + период). Формат: `quota period`. | `echo "150000 100000" > cpu.max` |
| `cpu.stat` | Статистика: `usage_usec`, `user_usec`, `system_usec`, `nr_throttled`, `throttled_usec`. | `cat cpu.stat` |

**Практические примеры (cgroups v2):**

```bash
# 1. Создание группы и установка веса (20% от system.slice)
sudo mkdir -p /sys/fs/cgroup/batch
echo "200" | sudo tee /sys/fs/cgroup/batch/cpu.weight
echo 1234 | sudo tee /sys/fs/cgroup/batch/cgroup.procs

# 2. Жесткий лимит: 50% одного ядра (50000/100000)
echo "50000 100000" | sudo tee /sys/fs/cgroup/batch/cpu.max

# 3. Проверка троттлинга
cat /sys/fs/cgroup/batch/cpu.stat
# → nr_throttled: 42
# → throttled_usec: 123456
# ↑ процесс 42 раза был приостановлен из-за превышения квоты

# 4. Через systemd-run (без ручного создания cgroup)
sudo systemd-run --scope --cpu-weight=50 --cpu-quota=25% \
  /usr/local/bin/heavy_task.sh
```

**Взаимодействие с nice:**

- `nice`/`renice` меняет вес задачи внутри её cgroup.
- Если cgroup имеет `cpu.max`, задача с `nice -20` всё равно будет троттлиться при превышении квоты.
- Если `cpu.max` не установлен, приоритеты работают пропорционально `cpu.weight` родительской группы.

> **Важно:** CFS Throttling проявляется как задержки кратные `cpu.cfs_period_us` (по умолчанию 100 мс). При обнаружении паттерна `100 мс` в сетевых или прикладных задержках проверяйте `nr_throttled`. Детальная диагностика троттлинга в Kubernetes/Docker описана в разделе [**Троттлинг процессора (CPU Throttling)**](../../../Kubernetes/Troubleshooting/Common_Errors/cpu_throttling.md). Полный обзор иерархии cgroups, `cpu.max.burst`, `cpuset` и наследования см. в разделе [**Контрольные группы (cgroups)**](../cgroups.md).
