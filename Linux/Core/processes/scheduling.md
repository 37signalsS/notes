# Планирование процессов в Linux

## Определения

**Планировщик ядра (Scheduler)** — компонент ядра Linux, определяющий очередность и продолжительность выполнения процессов на центральном процессоре (CPU — Central Processing Unit). Его основная задача заключается в обеспечении эффективного и справедливого распределения ресурсов между конкурирующими задачами.

**Переключение контекста (Context Switching)** — процедура сохранения состояния (регистры, программный счетчик, стек) текущего процесса и восстановления состояния другого процесса для передачи ему управления CPU. Это является основой многозадачности в операционных системах.

**Средняя нагрузка (LA — Load Average)** — показатель, отражающий среднее количество задач в состояниях выполнения (Running), готовности к выполнению (Runnable) или непрерываемого сна (Uninterruptible Sleep / D-state). Рассчитывается как экспоненциально взвешенное скользящее среднее (EWMA — Exponentially Weighted Moving Average) за периоды в 1, 5 и 15 минут.

**Очередь выполнения (Runqueue)** — фундаментальная структура данных ядра, содержащая список всех задач в состоянии готовности, ожидающих выделения процессорного времени. В системах с симметричной многопроцессорностью (SMP — Symmetric Multi-Processing) каждое ядро процессора имеет собственную индивидуальную очередь выполнения.

Подробнее о состояниях процессов см. в разделе [**Основные концепции**](./basic_concepts.md#состояния-процесса).

## Основные концепции

### Эволюция планировщиков Linux

В Linux фундаментальной единицей планирования является **"задача" (task)**. Ядро не делает различий между процессами и потоками — каждый поток рассматривается как отдельная задача, подлежащая планированию.

| Версия ядра | Планировщик | Описание |
| :--- | :--- | :--- |
| **2.6.0 – 6.5** | **CFS (Completely Fair Scheduler)** | "Полностью справедливый планировщик". Использовал виртуальное время выполнения (`vruntime`) для балансировки нагрузки. |
| **6.6+ (октябрь 2023)** | **EEVDF (Earliest Eligible Virtual Deadline First)** | "Самый ранний допустимый виртуальный дедлайн". Текущий планировщик по умолчанию, обеспечивающий более точное соблюдение приоритетов. |
| **6.12+ (ноябрь 2024)** | **EEVDF** | Код устаревшего CFS полностью удален из исходного кода ядра. |

#### Принцип работы EEVDF

Планировщик **EEVDF** заменяет концепцию накопления `vruntime` на расчет времени готовности и дедлайнов для каждой задачи:

- **Eligible Time (Время готовности)** — момент времени, когда задача теоретически должна получить доступ к ресурсам CPU с учетом её приоритета (`nice`) и веса.
- **Virtual Deadline (Виртуальный дедлайн)** — срок, к которому задача должна завершить свой очередной квант времени.
- **Выбор задачи** — планировщик всегда выбирает задачу с самым ранним виртуальным дедлайном среди всех готовых к выполнению.

**Преимущества перед CFS:**

- Снижение задержек (latency) для интерактивных приложений.
- Более предсказуемое поведение при использовании параметра `nice`.
- Улучшенная изоляция ресурсов между группами задач (`cgroups`).

### Классы и политики планирования

| Класс | Политика | Описание |
| :--- | :--- | :--- |
| `SCHED_NORMAL` | EEVDF | Стандартные пользовательские процессы (по умолчанию). |
| `SCHED_FIFO` | FIFO (First-In, First-Out) | Реальное время: выполняется до тех пор, пока сама не отдаст CPU или не будет вытеснена более приоритетной задачей. |
| `SCHED_RR` | Round-Robin | Реальное время: циклическое планирование с фиксированным квантом времени. |
| `SCHED_BATCH` | Пакетный режим | Оптимизация для задач, требующих длительных вычислений без частого переключения контекста. |
| `SCHED_IDLE` | Фоновый режим | Минимальный приоритет, выполняется только при полном отсутствии других задач в системе. |

Задачи реального времени всегда имеют безусловный приоритет над обычными процессами.

### Приоритеты процессов: `nice` и `PR`

В выводе системных утилит (например, `top` или `htop`) отображаются два параметра приоритета:

1. **`NI` (Nice)** — значение от `-20` (высший приоритет) до `+19` (низший приоритет). По умолчанию равно `0`. Этот параметр настраивается пользователем.
2. **`PR` (Priority)** — реальный приоритет, используемый планировщиком ядра. Для обычных процессов рассчитывается по формуле: `PR = 20 + NI`.

### Интерпретация Load Average

Показатель Load Average позволяет оценить общую загруженность ресурсов системы:

- **LA₁ (1 минута):** Текущий всплеск или падение нагрузки.
- **LA₅ (5 минут):** Краткосрочный тренд.
- **LA₁₅ (15 минут):** Долгосрочный тренд.

**Связь с количеством ядер CPU (N):**

- `LA ≈ N`: Система загружена полностью, но очередей нет.
- `LA > N`: Задачи ожидают в очереди. Если LA значительно превышает N, возможна деградация производительности.
- `LA < N`: В системе имеется запас вычислительной мощности.

**Примеры интерпретации:**

- **Система с 16 ядрами:** `LA = 16` означает полную загрузку. Если `LA = 128`, система находится в состоянии критической перегрузки, задачи стоят в огромной очереди.
- **Система с 128 ядрами:** `LA = 16` — это нормальное состояние (загружено всего ~12% ресурсов), а `LA = 128` — полная утилизация всех ядер.

**Особенность Linux:** В расчет LA включаются процессы в состоянии непрерываемого сна (`D-state`), ожидающие завершения операций ввода-вывода (I/O — Input/Output). Поэтому высокий LA при низком использовании CPU часто указывает на проблемы с дисковой подсистемой или сетевыми файловыми системами (NFS — Network File System).

**Пример для 4-ядерной машины:**

- `LA = 1.0` ≈ 25% загрузки CPU
- `LA = 4.0` ≈ 100% (все ядра заняты)
- `LA = 6.0` — очередь переполнена, задачи ждут в очереди

### Источники данных: /proc/uptime и /proc/loadavg

Утилиты `uptime`, `top` и `htop` берут данные напрямую из виртуальной файловой системы `/proc`:

- **`/proc/uptime`** — два числа: общее количество секунд работы системы и суммарное время бездействия (по всем CPU). Утилита `uptime` форматирует эти секунды в человекочитаемый вид.
- **`/proc/loadavg`** — пять полей: LA за 1, 5, 15 минут; количество активных / общее число процессов; PID последнего созданного процесса.

```bash
# Прямое чтение времени работы системы
cat /proc/uptime
# → 9592411.58 9566042.33
#   ↑ секунд работы  ↑ секунд простоя (сумма по CPU)

# Количество логических CPU (nproc)
nproc
# → 4

# Просмотр /proc/loadavg напрямую
cat /proc/loadavg
# → 0.50 0.40 0.30 1/800 12345
#   ↑ LA₁ ↑ LA₅ ↑ LA₁₅ ↑ активные/всего процессов ↑ PID последнего процесса

# Утилита uptime — форматированный вывод
uptime
# → 10:00:00 up 30 days, 1 user, load average: 0.50, 0.40, 0.30
```

Проверить природу LA можно экспериментально: запуск фоновой задачи увеличивает счётчик процессов и влияет на среднюю нагрузку.

```bash
# Проверка /proc/loadavg до и после загрузки CPU
cat /proc/loadavg
# → 0.00 0.01 0.03 1/123 1566
cat /dev/urandom > /dev/null &
# → [1] 1639
cat /proc/loadavg
# → 1.00 0.69 0.35 2/124 1679
kill %1
```

### Математика Load Average: EWMA

Три значения LA — это экспоненциально взвешенное скользящее среднее (EWMA, Exponentially Weighted Moving Average) за всё время работы системы, где веса убывают с разной скоростью:

- **LA₁** = 63% активности за последнюю минуту + 37% всей предыстории до неё.
- **LA₅** и **LA₁₅** — то же соотношение для 5 и 15 минут соответственно.

То есть LA — это не строго «среднее за последние N минут», а значение, в котором активность последнего окна имеет наибольший вес, но полная предыстория тоже учитывается.

## Практические сценарии

### Управление приоритетами через nice и renice

```bash
# Запуск новой задачи с минимальным приоритетом
nice -n 19 tar -czf backup.tar.gz /data
# → (процесс запустится с приоритетом 19)

# Изменение приоритета уже запущенного процесса
# Только суперпользователь (root) может повышать приоритет (уменьшать nice)
sudo renice -n -5 -p 1234
# → 1234 (process ID) old priority 0, new priority -5

# Снижение приоритета (увеличение nice) доступно обычному пользователю
renice -n 10 -p 1234
# → 1234 (process ID) old priority 0, new priority 10
```

### Диагностика узких мест по Load Average

| Симптом | Вероятная причина | Инструменты диагностики |
| :--- | :--- | :--- |
| **Высокий LA + Высокий `%CPU`** | Нехватка вычислительной мощности (CPU bottleneck) | `top`, `htop`, `pidstat` |
| **Высокий LA + Высокий `%iowait`** | Ожидание дисковых операций (I/O bottleneck) | `iotop`, `iostat -x 1`, `vmstat` |
| **Высокий LA + Низкий `%CPU`** | Блокировки в ядре, ожидание сети или NFS | `dstat`, `strace`, анализ состояний процессов |

## Дополнительная информация

### Информация о задержках из-за давления на ресурсы (PSI)

**Pressure Stall Information (PSI)** — современный механизм ядра Linux, позволяющий точно определить, какой процент времени задачи простаивали из-за нехватки CPU, памяти или ввода-вывода. В отличие от Load Average, PSI позволяет четко разделить причины задержек.

Подробнее см. раздел [**PSI — статистика давления на ресурсы**](../kernel/psi.md).

### Привязка к ядрам процессора (CPU Pinning)

**CPU Pinning** (Affinity) — механизм, позволяющий жестко закрепить процесс или поток за определенным ядром CPU. Это предотвращает миграцию задачи между ядрами, что критично для высокопроизводительных приложений, чувствительных к задержкам кэша и архитектуре неравномерного доступа к памяти (NUMA — Non-Uniform Memory Access).

Подробнее см. раздел [**CPU Pinning**](../cpu_pinning.md).

### Влияние планировщика на ввод-вывод

Планировщик процессов управляет только доступом к CPU. Для управления приоритетами доступа к дисковой подсистеме используется отдельный механизм — планировщики ввода-вывода (I/O Schedulers). Управлять ими можно с помощью утилиты `ionice`.

Подробнее см. раздел [**Планировщики ввода-вывода**](../kernel/io_schedulers.md).
