# OOM Killer в контейнерных средах

## Определения

**OOM Killer в контейнерах** — это специализированный режим работы механизма принудительного завершения процессов в условиях изоляции ресурсов (Docker, Kubernetes). В контейнеризованных средах ядро Linux оперирует иерархией контрольных групп (**cgroups**), что позволяет изолировать последствия нехватки памяти внутри конкретной группы, не затрагивая стабильность хоста.

**OOMKilled** — индикатор состояния контейнера, указывающий на то, что один из его процессов был завершен ядром из-за превышения установленного лимита памяти контрольной группы.

## Основные концепции

### Иерархическая модель OOM

Механизм защиты срабатывает на двух уровнях, каждый из которых имеет свою логику:

| Уровень | Триггер | Логика выбора жертвы |
| :--- | :--- | :--- |
| **Системный (Host)** | Исчерпание всей RAM + Swap на узле. | Глобальное сканирование всех процессов хоста и контейнеров. Выбирается процесс с наибольшим `oom_score`. |
| **Групповой (Container)** | Превышение лимита контрольной группы (`memory.max`). | Сканируются процессы только внутри данной cgroup. Выбирается «худший» процесс внутри контейнера. |

### Механизмы cgroups v2 для управления памятью

В отличие от cgroups v1, современный стандарт (**cgroups v2**) предоставляет более гибкие инструменты контроля, которые Kubernetes использует для реализации **Memory QoS**:

- **`memory.min` (Hard Guarantee):** Минимальный объем памяти, который ядро гарантированно не заберет у группы (соответствует `requests.memory` в K8s).
- **`memory.high` (Throttle Threshold):** Мягкий лимит. При его достижении ядро начинает агрессивно замедлять (throttle) процессы группы и выполнять очистку кэша, пытаясь избежать вызова OOM Killer.
- **`memory.max` (Hard Limit):** Абсолютный потолок. При попытке выделить память сверх этого значения немедленно вызывается OOM Killer.

### Классы QoS в Kubernetes и oom_score_adj

Kubernetes транслирует бизнес-логику приоритетов в параметры ядра через `oom_score_adj` (диапазон от -1000 до 1000). Это определяет, кого ядро убьет первым при **системном OOM**:

| Класс QoS | Значение `oom_score_adj` | Стратегия выживания |
| :--- | :--- | :--- |
| **Guaranteed** | **-997** | Практически неприкосновенны для системного OOM Killer. |
| **Burstable** | **2 – 999** | Приоритет зависит от соотношения запросов к лимитам. Чем больше памяти запрошено, тем выше защита. |
| **BestEffort** | **1000** | Первые кандидаты на удаление при нехватке памяти на узле. |

> **Критический нюанс:** Если контейнер превышает свой собственный `limits.memory` (`memory.max`), класс QoS не имеет значения — процесс будет убит групповым OOM Killer.

## Практические сценарии

### Групповое завершение (memory.oom.group)

Для сложных приложений (например, PostgreSQL или Nginx с мастером и воркерами) частичная потеря процессов может привести к некорректному состоянию (data corruption).

В **cgroups v2** можно включить атомное завершение всей группы:
```bash
# Включить групповое завершение (требует root на хосте или настройки рантайма)
echo 1 > /sys/fs/cgroup/system.slice/container-id.scope/memory.oom.group
```
Если любой процесс в этом контейнере вызывает OOM, ядро мгновенно завершит **все** процессы в этой cgroup.

### Диагностика OOMKilled в реальном времени

Для анализа причин падения контейнера используйте комбинацию инструментов:

```bash
# 1. Проверка причины завершения в Kubernetes
kubectl get pod <pod_name> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'

# 2. Поиск логов конкретного инцидента на узле
# Ищите строку "oom-killer" и "Memory cgroup out of memory"
dmesg -T | grep -iE "oom|killed"

# 3. Проверка текущих лимитов cgroups v2 внутри контейнера
cat /sys/fs/cgroup/memory.max
```

### Настройка в Docker

```bash
# Запуск контейнера с защитой от системного OOM
docker run --oom-score-adj=-500 my-app

# Отключение OOM Killer (только при наличии жесткого лимита -m)
# ВНИМАНИЕ: Опасно, может привести к зависанию хоста
docker run -m 1g --oom-kill-disable my-app
```

## Дополнительная информация

### Код выхода 137

Универсальный признак работы OOM Killer. Рассчитывается как `128 (база) + 9 (SIGKILL)`. Если вы видите этот код в `docker ps -a` или `kubectl describe`, значит приложение не успело обработать завершение и было остановлено ядром.

### Почему PID 1 в контейнере — это проблема

Процесс с PID 1 имеет специфическое поведение в Linux: он игнорирует сигналы по умолчанию. Однако OOM Killer отправляет **SIGKILL**, который невозможно игнорировать даже PID 1. Это гарантирует, что "зависший" контейнер будет остановлен.
