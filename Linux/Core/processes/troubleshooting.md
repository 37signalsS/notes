# Устранение неисправностей процессов

## Определения

### CRIU (Checkpoint/Restore In Userspace)

**CRIU** — это утилита для Linux, которая позволяет "заморозить" работающий процесс или группу процессов и сохранить их состояние в виде набора файлов на диске. Позже это состояние можно использовать для восстановления процессов с того же самого места, даже на другой машине.

### Код завершения (Exit code)

**Код завершения (Exit code)** — это целочисленное значение, которое программа или команда возвращает после своего завершения. Подробное описание кодов завершения см. в заметке [**Коды завершения (Exit codes)**](../../Shell/exit_codes.md).

### Дамп памяти (Coredump)

**Дамп памяти (Coredump)** — это файл, содержащий снимок рабочего адресного пространства процесса в момент его аварийного завершения (часто в результате получения [сигнала](./signals.md), такого как `SIGSEGV` или `SIGQUIT`). Он используется для посмертной отладки (post-mortem debugging), чтобы понять причину сбоя.

## Основные концепции

### Коды завершения (Exit Codes)

Код завершения можно проверить с помощью переменной `$?`.

| Код | Описание | Пример |
| :--- | :--- | :--- |
| **0** | Успешное завершение | Команда выполнилась без ошибок |
| **1** | Общая ошибка | Общая ошибка приложения |
| **2** | Неправильное использование | Неверные аргументы командной строки |
| **126** | Нет прав на выполнение | Файл есть, но нет прав на запуск |
| **127** | Команда не найдена | Опечатка в имени или нет в PATH |
| **128 + N** | Завершение сигналом | `130` = `128 + 2` (SIGINT), `137` = `128 + 9` (SIGKILL) |
| **130** | Прерывание (Ctrl+C) | SIGINT (сигнал 2) |
| **137** | OOM Kill / SIGKILL | SIGKILL (сигнал 9) — часто от OOM Killer |
| **143** | SIGTERM | Graceful shutdown (сигнал 15) |

```bash
# Проверить код завершения последней команды
ls /nonexistent
echo $?  # Вывод: 2

# Проверить код завершения успешно
ls /etc
echo $?  # Вывод: 0
```

### Как работает CRIU

CRIU сохраняет практически все состояние процесса: память, PID, открытые файлы, сокеты (включая установленные TCP-соединения), каналы, таймеры и т.д.

**Зачем это нужно:**

- **Живая миграция (Live Migration):** Перенос контейнеров или приложений между серверами практически без простоя.
- **Ускорение запуска:** "Долгоиграющие" приложения можно быстро восстанавливать из сохраненного состояния.
- **Отказоустойчивость:** Периодическое сохранение состояния критически важных процессов.

### Как работает Coredump

При аварийном завершении процесса, если это разрешено настройками системы, ядро создает файл coredump, содержащий полную копию памяти процесса и его состояния.

## Практические сценарии

### Checkpoint/Restore с помощью CRIU

#### 1. "Заморозить" процесс (dump)

```bash
# -t <pid>: указать PID процесса
# --images-dir: директория для сохранения файлов состояния
sudo criu dump -t <PID> --images-dir /tmp/checkpoint
```

#### 2. Восстановить процесс (restore)

```bash
# --daemon: запустить процесс в фоновом режиме
# --restore-detached: отсоединиться от процесса после восстановления
sudo criu restore --images-dir /tmp/checkpoint --daemon --restore-detached
```

### Анализ открытых файлов процесса

Для просмотра списка файлов, используемых процессом, применяется утилита `lsof`. Подробное описание и примеры использования находятся в основной заметке: [**`lsof` — Список открытых файлов**](../../Diagnostics/Processes/lsof.md).

```bash
# Показать все открытые файлы процесса
lsof -p <PID>

# Показать открытые сетевые соединения
lsof -i -p <PID>

# Найти процесс, использующий файл
lsof /var/log/nginx/error.log
```

### Восстановление удаленного исполняемого файла

Если вы случайно удалили скрипт или бинарный файл, пока он еще выполнялся, его можно восстановить. Ядро Linux не удаляет файл с диска (его inode и данные), пока хотя бы один процесс держит его открытым.

#### Шаги восстановления

1. **Найти PID процесса.** Используйте `pgrep` или [`ps`](../../Diagnostics/Processes/ps.md), чтобы найти идентификатор запущенного процесса.

    ```bash
    # Например, для скрипта 'my_script.sh'
    pgrep -f my_script.sh
    ```

2. **Скопировать файл из `/proc`.** Исполняемый файл доступен по символической ссылке `/proc/<PID>/exe`. Даже после удаления исходного файла эта ссылка все еще указывает на данные в памяти.

    ```bash
    # Если PID равен 12345
    cp /proc/12345/exe /path/to/restored_script.sh
    ```

    Эта команда создаст точную копию удаленного файла.

### Диагностика утечек памяти

#### 1. Valgrind

Инструмент для обнаружения утечек памяти:

```bash
valgrind --leak-check=full --show-leak-kinds=all ./your-program
```

#### 2. strace для анализа памяти

Отслеживание системных вызовов `mmap` и `munmap`:

```bash
strace -e trace=mmap,munmap -p <PID>
```

Подробнее об утилите см. [**Трассировка и отладка**](../../Diagnostics/Troubleshooting/tracing_and_debugging.md).

#### 3. /proc/<PID>/status

```bash
# Проверить потребление памяти процессом
cat /proc/<PID>/status | grep -E 'VmSize|VmRSS|VmSwap'

# Мониторить в реальном времени
watch -n1 'cat /proc/<PID>/status | grep -E "VmSize|VmRSS"'
```

### Анализ сбоев: Coredump

#### 1. Разрешить создание coredump

```bash
# Разрешить создание coredump неограниченного размера
ulimit -c unlimited

# Проверить текущий лимит
ulimit -c
```

#### 2. Настроить шаблон имени файла

```bash
# Посмотреть текущий шаблон
cat /proc/sys/kernel/core_pattern

# Установить свой шаблон (требует root)
echo '/var/cores/core.%e.%p.%t' > /proc/sys/kernel/core_pattern
```

#### 3. systemd-coredump

В современных системах с `systemd` процесс создания и управления дампами централизован.

**Конфигурация:** `/etc/systemd/coredump.conf`

**Утилита `coredumpctl`:**

```bash
# Показать список всех сохранённых дампов
coredumpctl list

# Показать подробную информацию о последнем сбое
coredumpctl info

# Извлечь дамп в файл для анализа в gdb
coredumpctl dump <PID> -o my_coredump

# Запустить gdb с последним дампом
coredumpctl debug
```

#### 4. Анализ в gdb

```bash
gdb /path/to/binary my_coredump

# Внутри gdb:
(gdb) bt          # Получить backtrace
(gdb) info locals # Показать локальные переменные
(gdb) print var   # Показать значение переменной
```

### Перезапуск процесса без изменения PID

Можно подменить исполняемый файл работающего процесса, используя `nsenter` для входа в его [пространства имён (namespaces)](../namespaces.md) и `exec` для запуска нового бинарника. Это позволяет сохранить PID, открытые сокеты и файловые дескрипторы.

```bash
# Находим PID старого процесса
pidof nginx  # допустим, PID = 1234

# Входим в его окружение и заменяем процесс новым
sudo nsenter -t 1234 -m -u -i -n -p -- bash -c 'exec /usr/local/bin/nginx-new -c /etc/nginx/nginx.conf'
```

> Подробнее о `nsenter` читайте в заметке о [пространствах имён](../namespaces.md).

### Перенос запущенного процесса в новый терминал (screen/tmux)

**Ситуация:** Вы запустили долгий скрипт, он работает уже несколько часов, но вы забыли запустить его внутри `screen` или `tmux`. Вам нужно отключиться от сервера, но закрытие терминала убьет и скрипт.

**Решение:** Используйте утилиту `reptyr`, чтобы «перехватить» процесс и перенести его в новый терминал.

#### Шаги

1. **Найти PID процесса.**

    ```bash
    pgrep -af your_script
    ```

2. **Отправить процесс в фон.** Нажмите `Ctrl+Z`, чтобы остановить процесс, а затем выполните команду `bg`, чтобы он продолжил работу в фоновом режиме.

    ```bash
    # После нажатия Ctrl+Z
    bg
    ```

3. **Отвязать процесс от текущей оболочки.** Это необходимо, чтобы `reptyr` мог его забрать.

    ```bash
    disown <PID>
    ```

4. **Переключиться в новый `screen` или `tmux` и "забрать" процесс.**

    ```bash
    reptyr <PID>
    ```

    Теперь процесс выполняется в вашем новом терминале, и вы можете безопасно отключаться.

> **Важно:** Для работы `reptyr` может потребоваться изменить настройку ядра:
>
> ```bash
> echo 0 | sudo tee /proc/sys/kernel/yama/ptrace_scope
> ```

### Зомби-процессы

#### Диагностика

```bash
# Найти все зомби-процессы
ps aux | grep ' Z '

# Посчитать количество зомби
ps aux | awk '$8 ~ /Z/ {print}' | wc -l

# Узнать родителя зомби-процесса
ps -eo pid,ppid,stat,cmd | grep ' Z '
```

#### Устранение

1. **Отправить SIGCHLD родителю:**

    ```bash
    # Найти PPID зомби
    ps -o ppid= -p <ZOMBIE_PID>
    
    # Отправить сигнал родителю
    kill -CHLD <PPID>
    ```

2. **Если родитель не реагирует — завершить его:**

    ```bash
    kill -TERM <PPID>
    # Или, если не помогает
    kill -KILL <PPID>
    ```

3. **Если зомби породил systemd (PID 1):**

    Зомби будут очищены автоматически при следующем вызове `wait()` со стороны systemd.

## Дополнительная информация

### Связь с observability

Диагностика процессов является частью более широкой практики **Observability** (наблюдаемость системы). Подробнее см. в заметке [**Observability Overview**](../../Concepts/Observability_and_Monitoring/observability_overview.md).

**Три столпа observability применительно к процессам:**

1. **Метрики:** CPU, память, I/O (top, ps, pidstat)
2. **Логи:** Вывод приложения, syslog, journalctl
3. **Трассировки:** strace, perf, bpftrace
