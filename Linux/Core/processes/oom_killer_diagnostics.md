# Диагностика OOM Killer в Linux

## Определения

**Диагностика OOM Killer** — это процесс выявления, анализа и расследования инцидентов принудительного завершения процессов ядром из-за критической нехватки оперативной памяти (**OOM — Out of Memory**).

**gfp_mask (Get Free Pages mask)** — шестнадцатеричный код в логах ядра, указывающий, какой именно тип памяти запрашивало ядро в момент сбоя (например, память для пользователя, метаданные или DMA).

**Silent OOM** — ситуация, при которой процесс завершается без явной записи в системном логе (часто при достижении лимитов внутри контейнера или при мгновенном крахе аллокатора).

## Основные концепции

### Источники диагностических данных

| Источник | Команда | Назначение |
| :--- | :--- | :--- |
| **Кольцевой буфер ядра** | `dmesg -T` | Просмотр событий с человекочитаемыми временными метками. |
| **Журнал systemd** | `journalctl -k` | Поиск архивных записей OOM, сохранившихся после перезагрузки. |
| **Интерфейс procfs** | `/proc/PID/status` | Просмотр лимитов и текущего потребления живого процесса. |
| **Память cgroups** | `/sys/fs/cgroup/...` | Фактические лимиты и статистика потребления для контейнеров (cgroups v2). |
| **Утилита smem** | `smem -rk` | Точный подсчет PSS/USS (реальное владение памятью). |

### Глубокий разбор лога OOM Killer

При срабатывании OOM ядро выводит блок информации. Рассмотрим ключевые строки:

```text
[1234.56] psql invoked oom-killer: gfp_mask=0x100cca(GFP_HIGHUSER_MOVABLE), order=0, oom_score_adj=0
...
[1234.57] CPU: 1 PID: 1234 Comm: psql Not tainted 5.15.0-generic
...
[1234.58] oom-kill:constraint=CONSTRAINT_MEMCG,nodemask=(null),cpuset=/,mems_allowed=0,oom_memcg=/kubepods/pod123,task_memcg=/kubepods/pod123,task=psql,pid=1234,uid=1000
[1234.59] Out of memory: Killed process 1234 (psql) total-vm:5242880kB, anon-rss:2097152kB, file-rss:0kB, shmem-rss:0kB, UID:1000 pgtables:5120kB oom_score_adj:0
```

#### Декодирование параметров:
- **`gfp_mask`**: 
    - `0x100cca`: Обычный запрос памяти для приложения (Heap/Stack). Проблема в Userspace.
    - `0x14000c0`: Запрос метаданных (например, открытие файлов). Проблема может быть в утечке дескрипторов.
- **`order`**: Размер запроса в страницах. `order=0` (4KB) — норма. Высокий `order` (например, 9 — 2MB) может указывать на фрагментацию памяти или запрос HugePages.
- **`constraint`**: 
    - `CONSTRAINT_NONE`: Системный OOM (закончилась вся память на хосте).
    - `CONSTRAINT_MEMCG`: Лимитный OOM (процесс уперся в лимит контейнера/cgroup).
- **`anon-rss`**: Реальная память процесса (анонимные страницы). Если это значение близко к лимиту — в приложении утечка.

## Практические сценарии

### Сценарий 1: Быстрый поиск виновников (One-liners)

```bash
# Поиск всех событий OOM за последние 24 часа
journalctl -k --since "1 day ago" | grep -i "out of memory"

# Список процессов, которые будут убиты следующими (Топ-10 по oom_score)
printf "%-10s %-10s %s\n" "SCORE" "PID" "COMMAND"
for p in /proc/[0-9]*; do
    pid=${p##*/}
    [ -r $p/oom_score ] && printf "%-10s %-10s %s\n" \
        "$(cat $p/oom_score)" "$pid" "$(cat $p/comm)"
done 2>/dev/null | sort -nr | head -10
```

### Сценарий 2: Идентификация Silent OOM

Иногда процесс умирает с кодом `137`, но в `dmesg` пусто. Причины:
1.  **Mmap Failure:** Приложение проверяет результат `malloc`/`mmap` и само вызывает `abort()`, если ядро вернуло `NULL` (политика Overcommit=2).
2.  **External SIGKILL:** Процесс был убит другим менеджером (например, `systemd-oomd` или скриптом мониторинга).

**Как проверить:**
```bash
# Проверка статистики cgroup v2 на предмет OOM (даже если лога нет)
cat /sys/fs/cgroup/system.slice/my_service.service/memory.events
# oom 5          <-- Количество срабатываний
# oom_kill 3     <-- Количество реально убитых процессов
```

### Сценарий 3: Мониторинг OOM в реальном времени (bpftrace)

Для SRE-инженеров важно ловить момент OOM без постоянного парсинга логов.

```bpftrace
# Отслеживание вызова oom_kill_process в ядре
bpftrace -e 'kprobe:oom_kill_process { 
    printf("OOM Killer triggered! Killed PID %d (%s)\n", args->chosen->pid, str(args->chosen->comm)); 
}'
```

### Сценарий 4: Глубокий анализ утечки (smaps_rollup)

Если `RSS` в `top` растет, проверьте `PSS` (Proportional Set Size) — это наиболее точный показатель физической памяти, за который "отвечает" процесс.

```bash
# Сравнение RSS и PSS для процесса
grep -E "Rss|Pss" /proc/<PID>/smaps_rollup
# Если PSS значительно меньше RSS — процесс использует много разделяемых библиотек.
# Если PSS ≈ RSS — процесс потребляет уникальную память (вероятная утечка).
```

## Дополнительная информация

### Чек-лист расследования (RCA)

1.  **Уровень:** Это системный OOM или лимит контейнера (`constraint`)?
2.  **Виновник:** Это тот же процесс, что запросил память (`invoked oom-killer`), или случайная жертва с высоким рейтингом?
3.  **Тип памяти:** Что преобладает в логе — `anon-rss` (утечка в коде) или `file-rss` (слишком активная работа с файлами/кэшем)?
4.  **Время:** Есть ли корреляция с графиками PSI (`/proc/pressure/memory`)?
