# Процессы в Linux: Дополнительная информация

## Определения

**pidfd (PID File Descriptor)** — файловый дескриптор, привязанный к конкретной структуре управления процессом в ядре (`task_struct`), а не к числовому идентификатору **PID (Process Identifier)**. Обеспечивает безопасное управление процессами, исключая возможность ошибки при переиспользовании PID ядром.

**TGID (Thread Group ID)** — идентификатор группы потоков. В Linux все потоки одного процесса имеют одинаковый TGID, который совпадает с PID главного потока процесса (лидера группы).

**TID (Thread ID)** — уникальный идентификатор задачи в ядре. Для однопоточного процесса PID = TGID = TID. Для многопоточного процесса каждый поток имеет свой уникальный TID.

## Основные концепции

### Сравнение fork() и clone(): Системные и библиотечные вызовы

В Linux существует различие между системными вызовами (прямой интерфейс ядра) и библиотечными вызовами (обертки в **glibc — GNU C Library**).

- **Системный уровень:** Ядро Linux предоставляет универсальный вызов `clone()` и устаревший `fork()`.
- **Библиотечный уровень:** Программисты используют функции `fork()` и `clone()` из библиотеки `glibc`.
- **Реализация:** Современная `glibc` реализует библиотечную функцию `fork()` через системный вызов `clone()` с набором флагов, эмулирующих классическое дублирование процесса. Библиотечный `clone()` позволяет вручную настраивать общие ресурсы (память, дескрипторы, сигналы) для создания потоков.

### Процессы против Потоков: Концептуальное сравнение

| Аспект | Процесс | Поток (Thread) |
| :--- | :--- | :--- |
| **Управление** | Управляется планировщиком задач ядра. | Управляется приложением через потоковые библиотеки (pthreads). |
| **Ресурсы** | Изолированное адресное пространство, свои дескрипторы. | Общее адресное пространство процесса и общие ресурсы. |
| **Изоляция** | Полная. Ошибка в одном процессе не влияет на другие. | Отсутствует. Ошибка в одном потоке может завершить весь процесс. |
| **Стоимость** | Дорогое создание и переключение контекста. | Дешевое создание и быстрое переключение контекста. |
| **Синхронизация** | Требуются механизмы **IPC (Inter-Process Communication)**. | Используются примитивы в общей памяти (мьютексы, спинлоки). |

### Зомби-процессы и управление их жизненным циклом

Зомби-процесс (`Z-state`) — это завершившаяся задача, запись о которой удерживается в таблице процессов ядра до тех пор, пока родитель не выполнит чтение статуса выхода. Накопление зомби может привести к исчерпанию лимита PID и отказу в обслуживании.

Подробные инструкции по диагностике и устранению см. в разделе [**Отладка процессов: Зомби-процессы**](./Troubleshooting/debugging.md#устранение-зомби-процессов).

### Безопасное управление процессами через pidfd

Традиционное управление процессами через числовые PID подвержено "состоянию гонки" (race condition): процесс может завершиться, его PID может быть немедленно переиспользован ядром для новой задачи, и сигнал `kill` уйдет неверному адресату.

**Механизм pidfd (Linux 5.3+):**

- Создается через `pidfd_open()` или `clone3()` с флагом `CLONE_PIDFD`.
- Файловый дескриптор жестко привязан к конкретной инкарнации процесса.
- Даже если процесс завершился, дескриптор остается валидным до его закрытия, но попытки отправить сигнал "новому" владельцу того же PID через этот дескриптор будут пресечены ядром.

## Практические сценарии

### Использование pidfd для отправки сигналов (C)

```c
#include <sys/syscall.h>
#include <sys/wait.h>
#include <signal.h>
#include <unistd.h>
#include <poll.h>

// Получение pidfd для существующего процесса
int pfd = syscall(SYS_pidfd_open, target_pid, 0);

// Безопасная отправка сигнала (исключает попадание в переиспользованный PID)
syscall(SYS_pidfd_send_signal, pfd, SIGTERM, NULL, 0);

// Асинхронное ожидание завершения процесса через poll()
struct pollfd poll_data = { .fd = pfd, .events = POLLIN };
poll(&poll_data, 1, -1); // Ждем события завершения процесса
```

## Дополнительная информация

### Исторический контекст и альтернативы

- **Solaris:** В старых Unix-системах накопление зомби было критической проблемой, часто требовавшей перезагрузки. Linux решает это через автоматическое переназначение родителя (re-parenting) на `init/systemd`.
- **Modern API:** Системный вызов `clone3()` является современным расширением `clone()`, обеспечивающим более гибкую настройку пространства имен и автоматическое получение `pidfd` при создании процесса.
- **Связь с сигналами:** `pidfd` интегрирован с подсистемой сигналов. Подробнее см. раздел [**Сигналы процессов**](./signals.md).
