# Процессы в Linux: Дополнительная информация

## `fork()` vs `clone()`: Системные и библиотечные вызовы

Существует некоторая путаница, связанная с `clone()` и `fork()`, поскольку они существуют как на уровне системных вызовов (интерфейс ядра), так и на уровне библиотечных вызовов (например, в `glibc`).

### Системные вызовы

Это прямой интерфейс к ядру Linux. Исторически существовали оба системных вызова: `fork()` и `clone()`.

### Библиотечные вызовы

Это "обертки" в стандартных библиотеках (например, `glibc`), которые программисты используют в своих приложениях.

Для обеспечения обратной совместимости и унификации, современные реализации `glibc` используют следующий подход:

1. **`clone()` и `fork()` являются библиотечными вызовами**, которые вы используете в своем коде.
2. Оба этих библиотечных вызова внутри себя используют **единый системный вызов `clone()`** для взаимодействия с ядром, но с разными флагами.
    - Библиотечный `fork()` вызывает системный `clone()` с флагами, которые эмулируют классическое поведение `fork()` (полное дублирование процесса).
    - Библиотечный `clone()` позволяет программисту самому указать флаги для тонкой настройки того, какие ресурсы будут общими между родительским и дочерним процессами/потоками.

**Важно:** С точки зрения планировщика ядра Linux, фундаментальной единицей планирования является не процесс, а "задача" (task). Каждый поток, созданный с помощью `clone()`, рассматривается как отдельная задача, подлежащая планированию.

## Процессы vs Потоки: концептуальное отличие

### Фундаментальное различие на уровне управления

| Аспект | Процесс | Поток |
| :--- | :--- | :--- |
| **Управление** | Управляется **ядром ОС** через планировщик задач. | Управляется **приложением** (через потоковые библиотеки: pthreads, goroutines). |
| **Выделение ресурсов** | При создании ядро выделяет: изолированное адресное пространство, таблицу файловых дескрипторов, контекст безопасности, стек. | Потоки используют ресурсы процесса: общее адресное пространство, файловые дескрипторы. Каждый поток имеет только свой стек и регистры. |
| **Изоляция** | Полная изоляция. Процессы не могут напрямую влиять на память друг друга. | Отсутствие изоляции между потоками одного процесса. Ошибка в одном потоке (`SIGSEGV`) завершает весь процесс. |
| **Стоимость создания** | Дорогая: выделение новых структур в ядре, копирование таблиц страниц (с CoW). | Дешёвая: создаются только структуры для стека и регистров в адресном пространстве процесса. |
| **Переключение контекста** | Дорогое: смена таблиц страниц (TLB flush), загрузка нового адресного пространства. | Дешёвое: переключаются только регистры и стек, таблицы страниц остаются теми же. |
| **Параллелизм** | Процессы выполняются параллельно на разных ядрах независимо. | Потоки одного процесса могут выполняться параллельно на разных ядрах, но требуют синхронизации. |
| **Синхронизация** | Требуются механизмы [IPC](./ipc.md): shared memory, семафоры, сообщения. | Используются мьютексы, условные переменные, спинлоки в общей памяти. |
| **Риски** | Минимальные: падение процесса не влияет на другие. | **Deadlock** (взаимоблокировка), **race condition** (гонка данных) при неправильной синхронизации. |

> **Практическое следствие:** В языках с многопоточностью (Go, Java, C++ с pthreads) приложение само реализует логику распределения задач между потоками, блокировки и ожидания. В мультипроцессорных архитектурах (например, Go с goroutines) используется гибридный подход: множество легковесных потоков приложения мапится на меньшее количество потоков ОС.

## Чем опасны зомби-процессы?

1. **Блокировка записей в таблице процессов:** Зомби-процессы не занимают память или CPU, но они удерживают свою запись в таблице процессов ядра. Эта таблица имеет ограниченный размер (задается параметром `pid_max`), как для всей системы, так и для каждого пользователя.

2. **Исчерпание PID:** Если родительский процесс (особенно долгоживущий демон) постоянно создает дочерние процессы, но не обрабатывает их завершение, количество зомби-процессов будет расти. При достижении лимита PID, выделенного для пользователя, система больше не сможет создавать новые процессы для этого пользователя.

3. **Отказ в обслуживании:** Это приводит к серьезным проблемам:
    - Пользователь, от имени которого запущен родительский процесс, **не сможет зайти на сервер** (локально или удаленно), так как для создания сессии нужно запустить новый процесс (например, `bash`).
    - На уже открытой консоли **невозможно будет выполнить какие-либо команды**, так как командный интерпретатор не сможет создать дочерний процесс для их выполнения.

4. **Необходимость перезагрузки:** В особо тяжелых случаях, если родительский процесс, порождающий зомби, работает от имени суперпользователя (`root`), и его невозможно перезапустить стандартными средствами, единственным способом восстановить работоспособность системы может стать **перезагрузка**, иногда даже аппаратная.

Некоторые операционные системы (например, старые версии Solaris) имели механизмы аварийного завершения части процессов для восстановления работоспособности при возникновении такой ситуации. В Linux основной механизм защиты — это усыновление осиротевших процессов процессом `init`/`systemd`.

## pidfd: безопасное управление процессами

### Проблема PID reuse (race condition)

Традиционные методы управления процессами через PID (`kill(pid, sig)`, `waitpid(pid, ...)`) подвержены **гонке состояний**:

```
Поток A: kill(pid, SIGTERM)  → процесс завершился
Ядро:    PID переиспользован → новый процесс получил тот же PID
Поток A: kill(pid, SIGKILL)  → убит НЕ тот процесс!
```

Эта проблема критична в:

- **Оркестраторах** (Kubernetes, Docker) — управление жизненным циклом контейнеров
- **Демонах-супервизорах** (systemd, supervisord) — контроль дочерних процессов
- **Многопоточных приложениях** — несколько потоков работают с одним процессом

### Решение: pidfd (PID File Descriptor)

**pidfd** — файловый дескриптор, привязанный к конкретной структуре `task_struct` ядра, а не к числовому PID. Даже если PID переиспользован, pidfd продолжает ссылаться на исходный процесс.

**Ключевые системные вызовы (Linux 5.3+):**

| Вызов | Описание |
| :--- | :--- |
| `pidfd_open(pid, flags)` | Получить pidfd по существующему PID |
| `pidfd_send_signal(pidfd, sig, info, flags)` | Отправить сигнал через pidfd |
| `clone3(&args, size)` | Создать процесс с `CLONE_PIDFD` — сразу получить pidfd |
| `waitid(P_PIDFD, pidfd, &info, options)` | Ожидать завершения процесса по pidfd |

### Как это работает

1. **Ядро создаёт уникальный дескриптор** для процесса через `pidfd_open()` или `clone3()` с `CLONE_PIDFD`.
2. **pidfd остаётся валидным** пока существует `task_struct` процесса, даже при переиспользовании PID.
3. **Сигналы через pidfd** (`pidfd_send_signal()`) гарантированно доставляются целевому процессу.
4. **Ожидание через pidfd** (`waitid(P_PIDFD, ...)`) — ожидание завершения конкретного процесса.
5. **poll/epoll на pidfd** — асинхронное отслеживание завершения (POLLIN при exit).

### Сравнение: традиционные методы vs pidfd

| Аспект | `kill()`/`waitpid()` | `pidfd_*` |
| :--- | :--- | :--- |
| **PID reuse** | Уязвимы — сигнал может уйти не тому процессу | Иммунитет — привязка к `task_struct` |
| **Race conditions** | Возможны между `kill()` и завершением | Исключены на уровне ядра |
| **Асинхронное ожидание** | Требует цикла опроса или `signalfd` | Поддержка `poll()`/`epoll()` |
| **Многопоточность** | Нужны блокировки для безопасности | Безопасен по дизайну |
| **Совместимость** | POSIX, все UNIX | Linux 5.3+ |
| **Сложность** | Простой API | Требует работы с syscall |

### Практический пример

```c
#include <sys/syscall.h>
#include <sys/wait.h>
#include <signal.h>
#include <unistd.h>
#include <errno.h>

// Получить pidfd процесса
int pidfd = syscall(SYS_pidfd_open, pid, 0);

// Безопасно отправить SIGTERM — нет риска убить не тот процесс
syscall(SYS_pidfd_send_signal, pidfd, SIGTERM, NULL, 0);

// Ожидать завершения через pidfd
siginfo_t info;
waitid(P_PIDFD, pidfd, &info, WEXITED);

// poll() для асинхронного отслеживания
struct pollfd pfd = { .fd = pidfd, .events = POLLIN };
poll(&pfd, 1, -1);  // Блокируется до завершения процесса
```

### Когда использовать pidfd

**Рекомендуется:**

- Оркестраторы контейнеров (Docker, Kubernetes, containerd)
- Системные демоны и супервизоры (systemd, supervisord)
- Многопоточные приложения, управляющие дочерними процессами
- Долгосрочное наблюдение за процессами

**Не требуется:**

- Разовые скрипты с заведомо коротким жизненным циклом
- Интерактивные команды в терминале
- Простые утилиты мониторинга

> **Связь с сигналами:** pidfd — альтернативный канал доставки сигналов, дополняющий традиционные `kill()`/`pkill()`. Подробнее: [Отправка сигналов через pidfd](./signals.md#отправка-сигналов-через-pidfd).

> **Создание процессов:** `clone3()` с `CLONE_PIDFD` — современный метод рождения процессов с pidfd. Подробнее: [Методы создания процессов](./basic_concepts.md#методы-создания-процессов).
