# Процессы в Linux: Дополнительная информация

## Определения

**pidfd (PID File Descriptor)** — стабильный файловый дескриптор, привязанный к конкретной инкарнации процесса в ядре. В отличие от числового PID, который может быть переиспользован ядром после завершения процесса, `pidfd` гарантирует, что вы взаимодействуете именно с тем процессом, который ожидали.

**pidfd_getfd** — системный вызов, позволяющий одному процессу (при наличии соответствующих прав) «забрать» дубликат файлового дескриптора из другого процесса через его `pidfd`. Это критически важно для SRE-инструментов и системных сервисов (например, перехват сокетов).

**TGID (Thread Group ID)** — идентификатор группы потоков. В Userspace этот идентификатор отображается как привычный PID процесса.

**TID (Thread ID)** — уникальный идентификатор конкретной задачи (потока) в ядре. В однопоточном приложении PID = TGID = TID.

**PGID (Process Group ID)** — идентификатор группы процессов, используемый для управления заданиями (Job Control). Группа позволяет отправлять сигналы (например, `SIGINT`) сразу нескольким процессам, работающим в одном конвейере.

**SID (Session ID)** — идентификатор сессии, объединяющий несколько групп процессов под одним управляющим терминалом.

## Основные концепции

### Иерархия идентификаторов

Ядро Linux организует задачи в многоуровневую структуру для эффективного управления ресурсами и маршрутизации сигналов:

1.  **Задачи (TIDs):** Базовые единицы планирования ядра.
2.  **Группы потоков (TGIDs/PIDs):** Наборы задач, разделяющих адресное пространство и системные ресурсы.
3.  **Группы процессов (PGIDs):** Используются для группировки процессов, запущенных одной командой или конвейером.
4.  **Сессии (SIDs):** Группируют процессы одного интерактивного входа или фоновой службы.

#### Взаимодействие с PID namespace

Внутри PID namespace иерархия идентификаторов изолируется. Процесс внутри контейнера видит себя как PID 1, но на хосте имеет глобальный PID (например, 5678). `TGID` внутри namespace соответствует локальному PID, а не глобальному. При отправке сигнала по `PGID` или `SID` доставка ограничена пределами namespace.

```bash
# Проверка namespace процесса
ls -la /proc/<PID>/ns/pid

# Сравнение PID внутри и снаружи namespace
readlink /proc/<PID>/ns/pid
readlink /proc/self/ns/pid
```

### Эволюция системных вызовов создания

В Linux создание задач прошло путь от простого дублирования до высокоточного конфигурирования:

- **`fork()` / `vfork()` (Legacy):** Устаревшие интерфейсы. В современной `glibc` реализованы как обертки над `clone()`.
- **`clone()` (Стандарт):** Позволяет создавать потоки или процессы, явно указывая флаги разделения ресурсов (память, файловая система, дескрипторы).
- **`clone3()` (Modern, Linux 5.3+):** Использует структуру `struct clone_args`. Позволяет:
  - Автоматически получать `pidfd` при создании процесса.
  - Указывать размер и расположение стека.
  - Управлять PID-пространствами имен без лишних `setns`.
  - С версии ядра 6.x поддерживает расширенные флаги для интеграции с cgroups v2 напрямую при создании.

#### struct clone_args: флаги разделения ресурсов

При использовании `clone()` / `clone3()` флаги определяют, что родитель и потомок будут разделять:

| Флаг | Разделяемый ресурс | Типичное использование |
| :--- | :--- | :--- |
| **`CLONE_VM`** | Адресное пространство (таблицы страниц) | Потоки (threads). Записи в памяти видны обоим. |
| **`CLONE_FS`** | Корневая директория и umask | Практически всегда используется вместе с `CLONE_VM`. |
| **`CLONE_FILES`** | Таблица файловых дескрипторов | Потоки. Один `close()` виден всем. |
| **`CLONE_SIGHAND`** | Обработчики сигналов | Потоки. `signal()` в одном потоке меняет обработчик для всех. |
| **`CLONE_THREAD`** | Привязка к группе потоков | Создание потока в существующей группе (NPTL). |
| **`CLONE_SYSVSEM`** | Семафоры SysV | Совместимость с legacy IPC. |
| **`CLONE_NEWPID`** | Новое PID namespace | Контейнеры. Потомок становится PID 1 в новом namespace. |
| **`CLONE_PIDFD`** | Возврат pidfd | Безопасное управление процессом без Race Condition. |

### Продвинутые механизмы ожидания (waitid)

Системный вызов `waitid()` предоставляет гораздо больше контроля, чем старый `waitpid()`:

| Флаг | Описание |
| :--- | :--- |
| `WEXITED` | Ждать завершения процесса. |
| `WSTOPPED` | Ждать остановки процесса сигналом. |
| `WCONTINUED` | Ждать возобновления процесса после `SIGCONT`. |
| `WNOHANG` | Не блокировать выполнение, если статус не изменился. |
| `WNOWAIT` | Оставить процесс в состоянии зомби (не «поглощать» статус), чтобы его можно было подождать еще раз. |

#### Практическое отличие от waitpid

`waitpid()` возвращает только PID завершившегося потомка и его статус. `waitid()` позволяет:
- Получить расширенную информацию через `siginfo_t` (включая причину остановки, ID отправителя сигнала).
- Ждать конкретное состояние (`WEXITED`, `WSTOPPED`, `WCONTINUED`) без лишних проверок.
- Использовать `WNOWAIT` для инспекции статуса без «съедания» записи о зомби.

### Процессы против Потоков: Глубокое сравнение

| Характеристика | Процесс | Поток (Thread) |
| :--- | :--- | :--- |
| **Системная сущность** | Задача с флагом `CLONE_VM` (выкл) | Задача с флагом `CLONE_VM` (вкл) |
| **Адресное пространство** | Изолированное (свои таблицы страниц) | Общее (разделяемые таблицы страниц) |
| **Дескрипторы (FD)** | Своя таблица (по умолчанию) | Общая таблица |
| **Сигналы** | Свои обработчики и маски | Общие обработчики, свои маски |
| **Переключение контекста** | Требует смены MMU (дорого) | Без смены MMU (дешево) |

#### Матрица решений: процесс или поток?

| Критерий | Процесс (fork) | Поток (pthread) |
| :--- | :--- | :--- |
| **Изоляция** | Полная (сбой одного не ломает другое) | Нет (ошибка памяти в одном потоке валит весь процесс) |
| **Обмен данными** | Требует IPC (pipe, socket, shm) | Прямой доступ к общим переменным |
| **Стоимость создания** | Выше (копирование таблиц страниц, CoW) | Ниже (общие таблицы) |
| **Масштабирование** | Ограничено PID namespace (по умолчанию ~32768) | Выше (потоки легче, но дескрипторы и стек тратят память) |
| **Стек** | Собственный стек (8 MB по умолчанию) | Собственный стек (2–8 MB, настраивается) |
| **Отладка** | Проще (отдельный адресное пространство) | Сложнее (разделяемая память, race conditions) |
| **Сценарий** | Запуск внешних команд, изоляция сервисов, sandbox | Вычислительные задачи, серверы с пулом воркеров, низкая задержка |

### Механизм переусыновления (Reparenting)

В Linux дерево процессов является непрерывным. Если родительский процесс завершается раньше своих потомков, они не могут остаться без родителя.

1.  **Сироты (Orphans):** Процессы, чей родитель завершился, становятся «сиротами».
2.  **Усыновление:** Ядро автоматически переназначает родителя таких процессов на **PID 1** (обычно `systemd` или `init`). В современных ядрах также существует механизм `PR_SET_CHILD_SUBREAPER`, позволяющий процессу стать «суб-рипером» и усыновлять потомков внутри своего поддерева.
3.  **Очистка зомби:** Процесс PID 1 (или суб-рипер) спроектирован так, чтобы немедленно вызывать `wait()` для любых усыновленных завершившихся процессов. Именно поэтому завершение «кривого» родителя эффективно очищает систему от накопленных им зомби-процессов.

#### PR_SET_CHILD_SUBREAPER в практике

Директива `prctl(PR_SET_CHILD_SUBREAPER, 1)` позволяет демону или супервизору become adoptive parent для процессов, порожденных внутри его поддерева:

```bash
# Проверка, является ли процесс subreaper
grep ^Subreaper /proc/<PID>/status
# → Subreaper: 1
```

```python
# Пример на Python (требует ctypes)
import ctypes

libc = ctypes.CDLL(None)
PR_SET_CHILD_SUBREAPER = 36
libc.prctl(PR_SET_CHILD_SUBREAPER, 1, 0, 0, 0)
```

**Когда использовать:**
- В контейнерах без полноценного init: ваш мониторинг-агент может усыновлять зомби.
- В супервизорах (supervisord, s6): чтобы очищать зомби без участия PID 1.
- Для отладки: найти «кривого» родителя, который плодит зомби.

## Практические сценарии

### Безопасное управление через pidfd (C)

Использование `pidfd` исключает Race Condition при отправке сигналов (когда PID завершившегося процесса успевает переиспользоваться другим процессом).

```c
#include <sys/syscall.h>
#include <sys/wait.h>
#include <signal.h>
#include <unistd.h>
#include <poll.h>
#include <stdio.h>

int main() {
    pid_t target_pid = 1234; 

    // 1. Открываем pidfd для процесса
    int pfd = syscall(SYS_pidfd_open, target_pid, 0);
    if (pfd == -1) {
        perror("pidfd_open");
        return 1;
    }

    // 2. Безопасно отправляем сигнал. 
    // Сигнал уйдет только "тому самому" процессу.
    if (syscall(SYS_pidfd_send_signal, pfd, SIGTERM, NULL, 0) == -1) {
        perror("pidfd_send_signal");
    }

    // 3. Асинхронное ожидание через poll (вместо блокирующего waitpid)
    struct pollfd poll_data = { .fd = pfd, .events = POLLIN };
    poll(&poll_data, 1, -1);
    
    close(pfd);
    return 0;
}
```

### Мониторинг pidfd в userspace

```bash
# Просмотр pidfd-дескрипторов процесса
ls -la /proc/<PID>/fd | grep pidfd

# Проверка поддержки pidfd в ядре
grep CONFIG_PIDFD /boot/config-$(uname -r)
# → CONFIG_PIDFD=y
```

### Перехват файлового дескриптора (pidfd_getfd)

Сценарий для SRE: вы хотите посмотреть, что пишет процесс в сокет, не перезапуская его.

```bash
# Псевдокод логики (требует CAP_SYS_PTRACE)
# 1. Получаем pidfd процесса
# 2. Используем pidfd_getfd(pfd, target_fd, 0)
# 3. Теперь в нашем процессе есть копия дескриптора target_fd
```

### Отправка сигналов процессным группам (PGID)

```bash
# Отправка SIGTERM всей группе процессов (например, всему конвейеру)
kill -TERM -<PGID>

# Пример: завершение всех процессов пользователя www-data
pkill -u www-data

# Безопасное завершение только foreground-группы текущего терминала
kill -INT -$(ps -o pgid= -p $$ | tr -d ' ')
```

### Мониторинг идентификаторов в терминале

Для просмотра иерархии групп и сессий используйте флаги `ps`:

```bash
# Вывод PID, PGID, SID и командной строки
ps -eo pid,pgid,sid,comm

# Просмотр TID (потоков) внутри процесса
ps -L -p <PID> -o pid,tid,comm

# Дерево процессов с PGID/SID
pstree -p -g
```

### Управление потоками ядра (kworker)

**Потоки ядра (Kernel Threads)** — служебные задачи, работающие только в Kernelspace. Не имеют пользовательского адресного пространства и игнорируют сигналы userspace.

```bash
# Список всех потоков ядра
ps -efj | grep "\["

# Проверка CPU affinity kworker'ов
taskset -p $(pgrep -o kworker/0)

# Ограничение unbound kworker'ов конкретными CPU
echo "0-3" | sudo tee /sys/fs/cgroup/cpuset/cpuset.cpus
```

**kworker (workqueue):** Потоки, выполняющие отложенную работу (deferred work) из очереди ядра. Делятся на:
- **Per-CPU kworker:** Работают только на назначенном ядре.
- **Unbound kworker:** Могут мигрировать между ядрами.

```bash
# Поиск kworker'ов с высокой нагрузкой
pidstat -w -p $(pgrep kworker) 1

# Ограничение unbound kworker'ов на определенных CPU
echo "workqueue.unbound_cpus=0-3" | sudo tee /proc/cmdline
```

### Выбор между процессом и потоком

Для SRE важно понимать архитектурные последствия выбора:

```bash
# Проверка количества потоков в процессе

```

### Использование waitid в супервизоре

При написании супервизора на Python/C:

```python
# Псевдокод: неблокирующий сбор статусов детей
import os, signal

while True:
    try:
        # WNOHANG: не блокировать, если нет завершившихся детей
        result = os.waitid(os.P_ALL, 0, os.WEXITED | os.WNOHANG)
        if result:
            print(f"Child {result.pid} exited with {result.status}")
    except ChildProcessError:
        break
```

### Спонтанные процессы ядра

Ядро при старте порождает служебные потоки (Kernel Threads), которые обычно имеют низкие PID и отображаются в `ps` в квадратных скобках (например, `[kworker/0:1]`). Они работают только в Kernelspace и не имеют адресного пространства пользователя.

### Ограничения и edge cases

1. **pidfd_open:** Требует, чтобы целевой процесс находился в текущем PID namespace (или чтобы вызывающий имел `CAP_SYS_PTRACE` в родительском namespace). Нельзя открыть `pidfd` для чужого PID namespace без привилегий.
2. **clone3:** Требует ядро 5.3+. Не поддерживается в старых контейнерах (например, Docker с устаревшим Host kernel).
3. **PR_SET_CHILD_SUBREAPER:** Работает только для потомков, порожденных после установки флага. Уже существующие дети не усыновляются.
4. **Zombie в namespace:** PID 1 внутри namespace отвечает за рейпинг зомби ТОЛЬКО внутри этого namespace. Зомби на хосте не зависят от PID 1 контейнера.

### Наблюдаемость (Observability)

Для SRE критически важно настроить мониторинг процессов до возникновения инцидентов:

- **Метрики:** Скорость создания процессов (`fork_rate`), количество зомби, количество потоков на процесс, `cs` (context switches).
- **Логи:** `auditd` для отслеживания `execve()` и `clone()`.
- **Алертинг:** Пороговые значения на количество зомби > 0, рост PID consumption, высокий `cs`.

```bash
# Мониторинг создания процессов через auditd
auditctl -a always,exit -S clone,fork,execve -F arch=b64

# Чтение логов
ausearch -i -sc execve | tail -20
```
