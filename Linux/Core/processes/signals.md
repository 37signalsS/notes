# Сигналы процессов в Linux

## Определения

**Сигналы (Signals)** — это асинхронные программные прерывания, отправляемые процессам для уведомления о событиях. Они являются фундаментальным механизмом [**межпроцессного взаимодействия (IPC)**](./ipc.md) и основным средством управления жизненным циклом процессов в Unix-подобных системах.

**Количество сигналов:** В современных Linux-системах поддерживается 64 сигнала.
- **1–31:** Стандартные сигналы POSIX.
- **34–64:** Сигналы реального времени (Real-time signals), имеющие номера от `SIGRTMIN` до `SIGRTMAX`.

**Диспозиция сигнала (Signal Disposition):** Текущий способ реакции процесса на конкретный сигнал. Существует три варианта:
- **Действие по умолчанию (Default action):** Заданное ядром поведение.
  - `Term`: Завершение процесса.
  - `Core`: Завершение процесса с созданием дампа памяти (Core Dump).
  - `Stop`: Остановка (пауза) выполнения процесса.
  - `Cont`: Возобновление выполнения остановленного процесса.
  - `Ign`: Игнорирование сигнала.
- **Игнорирование (Ignore):** Явное указание ядру отбрасывать сигнал (неприменимо к `SIGKILL` и `SIGSTOP`).
- **Пользовательский обработчик (Signal Handler):** Перехват сигнала и вызов функции, определенной в коде приложения.

## Основные концепции

### Жизненный цикл сигнала

1. **Генерация (Generation):** Сигнал инициируется ядром (ошибки CPU, таймеры), пользователем (клавиатура) или другим процессом (системный вызов `kill`, `tgkill`, `pidfd_send_signal`).
2. **Ожидание (Pending):** Сигнал сгенерирован, но еще не доставлен (например, если он заблокирован процессом или процесс не находится в состоянии выполнения).
3. **Доставка (Delivery):** Ядро приостанавливает выполнение процесса, переключает контекст и выполняет диспозицию (стандартное действие или обработчик).

### Блокировка и маскирование сигналов

Процесс может временно блокировать доставку определенных сигналов, устанавливая **маску сигналов (Signal Mask)**.

- **Механизмы:** Системные вызовы `sigprocmask` (для однопоточных) или `pthread_sigmask` (для многопоточных приложений).
- **Особенности:**
  - Заблокированные сигналы остаются в состоянии ожидания (`pending`) и доставляются сразу после разблокировки.
  - **Сигналы реального времени** при блокировке ставятся в очередь.
  - **Стандартные сигналы** не ставятся в очередь: если за время блокировки пришло несколько идентичных сигналов, после разблокировки будет доставлен только один.

### Обработка сигналов: signal vs sigaction

Существует два основных способа установки обработчика:
1. **signal():** Устаревший интерфейс с неопределенным поведением в разных Unix-системах (может сбрасывать обработчик на `SIG_DFL` после первого вызова).
2. **sigaction():** Современный стандарт POSIX. Позволяет:
   - Блокировать другие сигналы во время работы обработчика.
   - Получать расширенную информацию о сигнале (структура `siginfo_t`: PID отправителя, причина ошибки).
   - Автоматически перезапускать прерванные системные вызовы (`SA_RESTART`).

### Безопасность функций (Async-signal-safety)

Обработчик сигнала прерывает основной поток выполнения в произвольный момент. Это накладывает жесткие ограничения:
- **Запрещено:** Вызывать функции, использующие глобальное состояние или внутренние блокировки (например, `malloc`, `free`, `printf`, `exit`).
- **Разрешено:** Вызывать только **асинхронно-безопасные функции** (async-signal-safe), такие как `write`, `read`, `_exit`, `waitpid`, `getpid`.
- **Рекомендация:** В обработчике следует только устанавливать флаг (типа `volatile sig_atomic_t`) и проверять его в основном цикле программы.

### Анализ масок сигналов через /proc

Для диагностики поведения процесса (например, почему он не реагирует на `SIGTERM`), можно изучить его статус в `/proc`.

```bash
cat /proc/<PID>/status | grep Sig
# SigPnd: 0000000000000000 (Ожидающие сигналы для процесса)
# SigBlk: 0000000000001000 (Заблокированные сигналы)
# SigIgn: 0000000000000000 (Игнорируемые сигналы)
# SigCgt: 0000000180014007 (Перехваченные сигналы с обработчиками)
```
Маски представлены в шестнадцатеричном виде. Для их расшифровки можно использовать утилиту `kill -l` или онлайн-калькуляторы масок.

Дополнительно через `/proc/<PID>/status` можно проверить состояние ожидающих сигналов:
- **SigPnd:** Ожидающие сигналы для всего процесса (общий сигнальный массив для всех потоков).
- **ShdPnd:** Ожидающие сигналы для ведущего потока (thread group leader).

Для получения pending-сигналов через код можно использовать `sigpending()`.

### Источники генерации сигналов

Сигналы могут генерироваться из трёх источников:

1. **Ядро (Kernel-generated):**
   - **Ошибки исключений CPU:** `SIGSEGV` (нарушение защиты памяти), `SIGBUS` (ошибка шины), `SIGILL` (недопустимая инструкция), `SIGFPE` (арифметическая ошибка).
   - **Системные вызовы:** `SIGPIPE` (запись в pipe без читателя), `SIGXCPU`/`SIGXFSZ` (превышение лимитов CPU/размера файла).
   - **Таймеры:** `SIGALRM` (реальной времени от `alarm()`), `SIGPROF` (профилирования), `SIGVTALRM` (виртуального времени).
   - **OOM Killer:** При критическом дефиците памяти ядро отправляет `SIGKILL` процессам для освобождения памяти.

2. **Пользователь (User-generated):**
   - Ввод с терминала: `SIGINT` (Ctrl+C), `SIGTSTP` (Ctrl+Z), `SIGQUIT` (Ctrl+\\).
   - Вызовы `kill()`, `raise()`, `abort()`.

3. **Другие процессы (Process-generated):**
   - Системные вызовы отправки: `kill()`, `tgkill()`, `tkill()`, `pidfd_send_signal()`, `rt_sigqueueinfo()`.
   - События дочернего процесса: `SIGCHLD`.

### Механизмы отправки сигналов

- **kill(pid, sig):** Классический системный вызов. Отправляет сигнал процессу по PID. Если `pid > 0` — конкретному процессу; если `pid == 0` — всем процессам в группе; если `pid == -1` — всем процессам, у которых есть право на отправку (за исключением init и kernel threads).
- **tgkill(tgid, tid, sig):** Отправляет сигнал конкретному потоку (TID) внутри группы. Это современная и надёжная альтернатива `tkill()`, которая не имеет проблемы с переиспользованием TID.
- **rt_sigqueueinfo() / sigqueue():** Отправляют сигнал реального времени с данными (целое число или указатель). Гарантируют доставку и порядок.
- **pidfd_send_signal(pidfd, sig, ...):** (Linux 5.3+) Отправляет сигнал через `pidfd` — дескриптор, полученный от `pidfd_open()`. Устраняет race condition, когда PID завершается и его номер занимает другой процесс.

### Pending-сигналы и sigpending()

Сигнал, который заблокирован или не может быть доставлен немедленно, становится ожидающим (`pending`). Использование `sigpending()` позволяет приложению проверить, какие сигналы ожидают доставки:

```c
sigset_t pending;
sigpending(&pending);
if (sigismember(&pending, SIGUSR1)) {
    // SIGUSR1 ожидает доставки
}
```

**Важно:** Стандартные сигналы не ставятся в очередь. Если процесс получил `SIGUSR1` три раза во время блокировки, после разблокировки обработчик будет вызван только один раз. Сигналы реального времени (`SIGRTMIN+N`) ставятся в очередь и доставляются все.

#### Расшифровка сигналов для SRE

| Сигнал | Частый сценарий SRE |
| :--- | :--- |
| **SIGTERM** | Корректное завершение сервисов, перезагрузка демонов (`kill -HUP`). |
| **SIGKILL** | Аварийное завершение зависшего процесса (exit code 137 — частый индикатор OOM Killer). |
| **SIGINT** | Прерывание foreground-процесса (Ctrl+C), graceful shutdown в контейнерах. |
| **SIGQUIT** | Дамп памяти + завершение (полезно для post-mortem анализа без отладчика). |
| **SIGCHLD** | Управление дочерними процессами (супервизоры, init-системы, zombie reaping). |
| **SIGUSR1/USR2** | Пользовательская сигнализация: переконфигурация логгера, ротация, кастомные heartbeat. |
| **SIGPIPE** | Обрыв pipe/сокета; приложение часто завершается, если не установлен `SIG_IGN`. |
| **SIGSTOP/SIGCONT** | Диагностика: приостановка процесса для анализа состояния (`kill -STOP` → `gdb` attach → `kill -CONT`). |
| **SIGXCPU/SIGXFSZ** | Превышение лимитов cgroup/ulimit; помогают выявить утечки ресурсов до OOM. |

### Ключевые механизмы и особенности

#### SIGTERM против SIGKILL

- **SIGTERM (15):** Стандартный способ завершения. Дает приложению время на **Graceful Shutdown**: закрытие соединений, сохранение состояния, удаление временных файлов.
- **SIGKILL (9):** Принудительная остановка ядром. Процесс не получает уведомления. Опасно повреждением данных в БД или оставшимися блокировками в разделяемой памяти.

#### OOM Killer и сигналы

При критическом дефиците памяти ядро активирует **OOM Killer** (Out-of-Memory Killer), который выбирает процесс для принудительного завершения с целью освобождения памяти. OOM Killer использует `SIGKILL`, поэтому:
- **Exit code 137** в Docker/Kubernetes — частый индикатор OOM Killer (128 + 9 = 137).
- **Detection:**
  ```bash
  dmesg | grep -i "oom\|killed process"
  journalctl -k | grep -i oom
  ```
- **Предотвращение:** Настройка лимитов памяти (`memory.limit_in_bytes` в cgroup, `--memory` в Docker, `resources.limits.memory` в K8s) и использование early-oom мониторинга.

#### Процессы в состоянии D (Uninterruptible Sleep)

Процессы в состоянии **D** (`TASK_UNINTERRUPTIBLE`) игнорируют **все** сигналы, включая `SIGKILL`. Это происходит при ожидании завершения операций ввода-вывода на уровне ядра (например, NFS-монтирование зависло, или проблема с storage). Такие процессы можно "убить" только двумя способами:
1. Завершить операцию I/O (например, восстановить NFS-соединение).
2. Перезагрузить систему (reboot).

```bash
ps aux | grep ' D '
# Если процесс в D-state — SIGKILL не поможет, нужно чинить storage/network
```

#### Дампы памяти (Core Dumps)

При сигналах с действием `Core` создается снимок памяти процесса для последующей отладки (GDB).
- **Настройка лимитов:** `ulimit -c unlimited` разрешает создание дампов.
- **Путь сохранения:** Регулируется через `/proc/sys/kernel/core_pattern`.
- **systemd:** В современных дистрибутивах дампы собираются через `systemd-coredump` и просматриваются командой `coredumpctl`.

#### Сигналы реального времени (RT)

В отличие от стандартных сигналов:
- Гарантированно доставляются в порядке очереди.
- Не объединяются: если отправлено 10 сигналов, будет 10 вызовов обработчика.
- Позволяют передавать данные (целое число или указатель) через `sigqueue()`.

#### signalfd: Обработка сигналов как файлов

Системный вызов `signalfd` позволяет читать сигналы через обычный файловый дескриптор. Это интегрирует обработку сигналов в современные событийные циклы (`epoll`, `io_uring`), избегая проблем с асинхронно-безопасными функциями в обработчиках.

## Практические сценарии

### Управление процессами через терминал

```bash
# Плавная остановка (SIGTERM)
kill <PID>

# Принудительное завершение (SIGKILL)
kill -9 <PID>

# Поиск процессов по шаблону перед завершением (безопасный подход)
pgrep -a python           # Просмотр совпадений (PID + имя)
pgrep -af "worker.py"     # Поиск по полной командной строке (аргументам)

# Перезагрузка конфигурации (многие демоны используют SIGHUP)
kill -HUP $(pgrep nginx)

# Остановка/возобновление процесса
kill -STOP <PID>
kill -CONT <PID>
```

### Завершение процессов по имени: killall

Команда `killall` позволяет завершать процессы по их имени без необходимости знать PID. Это экономит время при необходимости завершить множество процессов с одинаковым именем.

```bash
# Завершение всех процессов с именем "sleep" (по умолчанию — SIGTERM)
killall sleep

# Принудительное завершение по имени
killall -9 sleep
killall -KILL sleep
```

**Особенности и риски:**
- `killall` завершает **все** процессы с указанным именем в текущем пространстве имен PID
- В контейнеризированных средах учитывайте, что `killall nginx` может затронуть процессы в других контейнерах, если запущено вне нужного namespace
- Для безопасного завершения по имени предпочтительнее `pkill` с предварительной проверкой через `pgrep`

### Типичный рабочий процесс завершения зависшего процесса

Рекомендуемая последовательность действий при завершении зависшего процесса:

```bash
# 1. Найти PID процесса
pgrep -a <имя_процесса>
ps aux | grep <имя_процесса>

# 2. Отправить вежливый запрос на завершение (SIGTERM, сигнал 15)
kill <PID>

# 3. Проверить, завершился ли процесс
ps -p <PID>

# 4. Если процесс не отвечает — принудительное завершение (SIGKILL, сигнал 9)
kill -9 <PID>
```

**Экзаменационный нюанс:** Многие новички ошибочно полагают, что `kill` по умолчанию отправляет SIGKILL (9). Это неверно: по умолчанию Linux всегда пытается действовать корректно — `kill` без указания сигнала отправляет SIGTERM (15). SIGKILL (9) — это «тяжелая артиллерия», применяемая только когда процесс не реагирует на вежливую просьбу.

### Безопасное управление и риски pkill

Утилита `pkill` удобна, но опасна из-за поиска по имени процесса по умолчанию.

- **Риск ложных срабатываний:** `pkill python` может завершить не только целевой скрипт, но и все процессы `python` в текущем пространстве имен.
- **Опасность `pkill -f`:** Флаг `-f` ищет совпадение во всей командной строке. Например, `pkill -f worker` может зацепить процесс с аргументом `--user=worker-admin`.
- **Рекомендации по безопасности (SRE):**
  1. **Предварительная проверка:** Сначала выполните `pgrep -a` или `pgrep -af` с тем же шаблоном, чтобы увидеть список потенциальных жертв.
  2. **Точечное завершение:** Вместо имени используйте PID. Перед `kill <PID>` проверьте детали процесса:
     ```bash
     ps -p <PID> -o pid,ppid,user,comm,args
     ```
  3. **Проверка Namespace:** В контейнеризированных средах PID 123 на хосте и в контейнере — это разные процессы. Проверьте пространство имен процесса перед отправкой сигнала:
     ```bash
     # Сравнение Namespace процесса с текущим (self)
     readlink /proc/<PID>/ns/pid
     readlink /proc/self/ns/pid
     ```

### Безопасная отправка через pidfd

Системный вызов `pidfd_send_signal` (Linux 5.3+) решает проблему "переиспользования PID". Если процесс завершился, а его PID занял другой процесс, сигнал через `pidfd` (который является дескриптором конкретного процесса) не будет доставлен новому владельцу PID.

### Сигналы в контейнеризации (Docker/Kubernetes)

- **Проблема PID 1:** В Linux процесс с PID 1 не имеет обработчиков сигналов по умолчанию. Если приложение (например, на Python/Node.js) запущено как PID 1 и не регистрирует обработчики явно, оно будет игнорировать `SIGTERM`.
- **Решение:** Использование `init`-процессов типа `tini` или `dumb-init`, которые пробрасывают сигналы дочерним процессам.
- **Kubernetes:** Сначала отправляет `SIGTERM`, ждет `terminationGracePeriodSeconds` (по умолчанию 30с) и, если под еще жив, отправляет `SIGKILL`.

### Сигналы в systemd-сервисах

Systemd использует сигналы для управления жизненным циклом служб. Понимание этой механики критично для SRE:

- **SIGTERM:** Стандартный сигнал остановки. Отправляется по умолчанию при `systemctl stop`. Timeout регулируется через `TimeoutStopSec` (по умолчанию 90 секунд в systemd).
- **SIGKILL:** Отправляется автоматически после истечения `TimeoutStopSec`, если процесс не завершился.
- **SIGHUP:** Используется для перезагрузки конфигурации. Systemd отправляет его при `systemctl reload` (если сервис поддерживает reload).
- **SIGINT:** Может быть использован как альтернативный сигнал остановки (например, для Java-приложений).
- **SIGRTMIN+3:** Специальный сигнал для корректной остановки systemd внутри контейнера. `SIGTERM`, полученный менеджером как PID 1, не означает остановку — по `man systemd(1)` он сериализует состояние, перезапускает менеджер и десериализует состояние заново (эквивалент `systemctl daemon-reexec`). Подробнее — в [docker_systemd.md](../../../Docker/docker_systemd.md).

```ini
# /etc/systemd/system/myapp.service
[Service]
ExecStart=/usr/bin/myapp
ExecReload=/bin/kill -HUP $MAINPID
KillSignal=SIGTERM
TimeoutStopSec=30
WatchdogSec=60
Restart=on-failure
```

**Watchdog:** Если сервис поддерживает `sd_notify(0, "WATCHDOG=1")`, systemd будет ожидать heartbeat. При отсутствии heartbeat в течение `WatchdogSec` systemd автоматически отправляет `SIGTERM`, а затем `SIGKILL`.

### Управление сигналами в shell-скриптах

В shell-скриптах используется команда `trap` для перехвата сигналов:

```bash
#!/bin/bash

cleanup() {
    echo "Получен сигнал, выполняем очистку..."
    rm -f /tmp/myapp.lock
    exit 0
}

# Перехватить SIGINT (Ctrl+C) и SIGTERM
trap cleanup SIGINT SIGTERM

# Игнорировать SIGPIPE (предотвращает преждевременное завершение при обрыве pipe)
trap '' SIGPIPE

echo "PID: $$"
while true; do
    sleep 1
done
```

**Практические паттерны:**
- **Защита критических секций:** `trap '' INT TERM` перед `rm -rf` или `mv`, чтобы прерванный скрипт не оставил систему в неконсистентном состоянии.
- **Graceful shutdown в bash:** `trap` + флаг переменная + проверка в цикле.
- **Ограничение:** В shell нельзя безопасно вызывать `exit` из trap при `set -e` — используйте флаг и дождитесь конца цикла.

### Отладка сигналов с помощью strace

`strace` позволяет увидеть, какие сигналы получает процесс и как он на них реагирует:

```bash
# Отслеживание всех сигналов
strace -e trace=signal -p <PID>

# Отслеживание сигналов + syscall'ы при чтении/записи
strace -e trace=signal,read,write -p <PID>

# Проверка блокировки SIGTERM: если SIGTERM не доставляется, процесс заблокировал его
strace -e trace=all -p <PID> 2>&1 | grep -i "sigprocmask\|SIGTERM"
```

### Проверка существования процесса: kill -0

Сигнал `0` — это специальный "пустой" сигнал, который не отправляется, но проверяет возможность доставки:

```bash
# Проверка, существует ли процесс (без отправки сигнала)
kill -0 <PID> && echo "Process exists" || echo "Process dead"

# Использование в скриптах
if kill -0 "$PID" 2>/dev/null; then
    echo "Process $PID is still running"
fi
```

### Анализ core dumps

```bash
# Включение core dumps
ulimit -c unlimited

# Просмотр последнего core dump через systemd-coredump
coredumpctl list
coredumpctl info <PID>
coredumpctl dump <PID> -o /tmp/core.dump

# Анализ в GDB
gdb /usr/bin/myapp /tmp/core.dump
(gdb) bt full
(gdb) info registers
(gdb) x/16x $sp

# Извлечение executable path из coredump
coredumpctl info <PID> | grep "Executable"
```

## Безопасность сигналов

### Права на отправку сигналов

Ядро проверяет, имеет ли процесс право отправить сигнал:
- **Обычные пользователи:** Могут отправлять сигналы только процессам, принадлежащим тому же пользователю (реальный/effective UID).
- **root (UID 0):** Может отправлять сигналы любому процессу (за исключением некоторых kernel threads).
- **CAP_KILL:** Capability, расширяющая права на отправку сигналов между пользовательскими пространствами имен PID (Namespaces).

### Атаки через сигналы

- **Signal Flooding:** Злоумышленник, имея доступ к запущенному процессу, может отправить тысячи `SIGALRM` или `SIGUSR1`, вызвав деградацию производительности.
- **Race condition с SIGKILL:** Невозможно перехватить `SIGKILL`, но можно попытаться сбросить обработчик других сигналов.
- **Защита:** Использование `prctl(PR_SET_PDEATHSIG, SIGKILL)` для автоматического завершения дочернего процесса при смерти родителя.

### Двойные обработчики и fork/exec

При вызове `fork()` дочерний процесс наследует обработчики сигналов. При `exec()` обработчики сбрасываются на `SIG_DFL`. Это важно для безопасности: дочерний процесс после `exec()` не будет неожиданно обрабатывать сигналы, установленные родителем.

## Дополнительная информация

### Коды завершения (Exit Codes)

Если процесс завершился по сигналу, его код выхода в shell вычисляется как `128 + номер сигнала`:
- `130` (128 + 2) — Прервано пользователем (SIGINT).
- `137` (128 + 9) — Принудительно убито (SIGKILL), часто указывает на OOM Killer.
- `143` (128 + 15) — Корректно завершено по сигналу (SIGTERM).

Подробнее см. раздел [**Коды завершения (Exit Codes)**](../../Shell/exit_codes.md).

### Группы процессов и терминал

Сигналы от клавиатуры (`SIGINT`, `SIGTSTP`) отправляются всей **группе процессов переднего плана (Foreground Process Group)**. Это позволяет одной комбинацией клавиш остановить весь конвейер команд (например, `cat file | grep pattern | less`). Управление foreground/background задачами из shell описано в [**Горячие клавиши и шорткаты Shell**](../../Shell/shell_shortcuts.md#управление-фоновыми-задачами).

- **setsid():** Системный вызов, создающий новую сессию (session) и делающий процесс лидером группы и лидером сессии.
- **setpgid():** Перемещает процесс в другую группу процессов. Используется для управления фоновыми задачами.

### Изоляция и Namespaces

Сигналы могут передаваться между пространствами имен PID (Namespaces), но с ограничениями. Процесс в родительском пространстве имен может отправить сигнал процессу в дочернем, но не наоборот (если только у них нет общих привилегий).
- Процесс PID 1 внутри Namespace игнорирует любые сигналы от процессов внутри того же Namespace, для которых он не установил обработчик.
- Сигналы от родительского Namespace (например, от `docker stop`) доставляются в любом случае.

Подробнее см. [**Namespaces (Пространства имён)**](../namespaces.md).

### Выбор механизма завершения: система принятия решений

| Сценарий | Рекомендуемый сигнал / метод | Обоснование |
| :--- | :--- | :--- |
| **Стандартное завершение сервиса** | `SIGTERM` | Даёт приложению время на graceful shutdown. |
| **Принудительное завершение зависшего процесса** | `SIGKILL` | Не перехватывается; используется как крайняя мера. |
| **Java-приложение в Docker** | `SIGQUIT` или `SIGTERM` | PostgreSQL предпочитает `SIGINT`; Java/Sidekiq часто требуют `SIGQUIT`. |
| **Nginx** | `SIGQUIT` | Graceful shutdown с завершением текущих запросов. |
| **Релоад конфигурации** | `SIGHUP` | Многие демоны (nginx, haproxy, sshd) перечитывают конфиг без перезапуска. |
| **Диагностика D-state** | Невозможно | Нужно чинить storage/network или перезагружать систему. |
| **Уведомление без завершения** | `SIGUSR1` / `SIGUSR2` | Кастомные события: ротация логов, реконфигурация. |
| **Остановка процесса для отладки** | `SIGSTOP` / `SIGCONT` | Приостановить для `gdb` attach, затем продолжить. |
| **Таймаут завершения systemd** | `TimeoutStopSec` | После истечения — автоматический `SIGKILL`. |

## Типовые проблемы и устранение неполадок

### 1. Процесс игнорирует SIGTERM

**Симптомы:** `docker stop` или `systemctl stop` зависает на 10/30 секунд, затем отправляется SIGKILL (exit code 137).

**Причины:**
- Процесс запущен как PID 1 без обработчика сигналов (Python, Node.js без явной регистрации).
- Сигнал заблокирован через `sigprocmask()`.
- Обработчик сигнала установлен в `SIG_IGN` (игнорирование).

**Диагностика и решение:**
```bash
# Проверка маски сигналов
grep Sig /proc/<PID>/status
# SigIgn: 0000000000000000 — если здесь не 0, сигнал игнорируется

# Проверка обработчиков через strace
strace -e trace=signal -p <PID>
# Если нет rt_sigaction(SIGTERM) — обработчик не установлен

# Решения:
# 1. Использовать exec-form в Dockerfile
# 2. Добавить явный обработчик в код приложения
# 3. Использовать tini/dumb-init как PID 1
# 4. В systemd: добавить ExecStop со своим обработчиком
```

### 2. Накопление зомби-процессов

**Симптомы:** Процессы в состоянии `Z` в выводе `ps aux`, исчерпание PID namespace.

**Причины:**
- PID 1 не вызывает `wait()`/`waitpid()`.
- Приложение порождает дочерние процессы и не перехватывает `SIGCHLD`.

**Решение:**
```bash
# Поиск зомби
ps aux | grep ' Z '

# Если PID 1 — это ваше приложение: добавьте обработчик SIGCHLD или используйте tini
docker run --init myapp

# Проверка, является ли init корректным adoptive parent
cat /proc/1/status | grep PPid
```

### 3. Процесс в состоянии D (Uninterruptible Sleep)

**Симптомы:** `kill -9 <PID>` не работает, процесс завис навсегда, `ps` показывает `D`.

**Причины:**
- NFS-монтирование зависло (NFS hang).
- Проблемы с storage (iSCSI timeout, SAN issue).
- `futex` в состоянии ожидания (редко).

**Решение:**
```bash
# Проверка состояния
ps aux | awk '$8 ~ /D/'

# Анализ стека
cat /proc/<PID>/stack
# или
pstack <PID>

# Нет решения без reboot, кроме восстановления storage
# В Docker: docker kill --signal SIGKILL не поможет
```

### 4. OOM Killer убил процесс

**Симптомы:** Процесс внезапно завершается с exit code 137 (SIGKILL), нет явного `kill` в логах.

**Диагностика:**
```bash
# Проверка ядерных логов
dmesg | grep -i "oom\|killed process"
journalctl -k | grep -i oom

# Проверка usage памяти
free -h
cat /sys/fs/cgroup/memory/memory.usage_in_bytes
cat /sys/fs/cgroup/memory/memory.max_usage_in_bytes
```

**Решение:**
```bash
# Увеличить лимит памяти (Docker)
docker run --memory=2g myapp

# В Kubernetes
resources:
  limits:
    memory: "2Gi"

# В systemd
MemoryMax=2G
```

### 5. Контейнер не завершается корректно

**Симптомы:** `docker stop` ждет 10 секунд, затем SIGKILL.

**Решение:**
```bash
# Использовать exec-form CMD
# Добавить STOPSIGNAL в Dockerfile
STOPSIGNAL SIGTERM

# Использовать --init или tini
docker run --init myapp

# В compose.yml
services:
  app:
    init: true
    stop_signal: SIGTERM
    stop_grace_period: 30s
```

### 6. Сигналы не доставляются внутри namespace

**Симптомы:** `kill` внутри контейнера завершает не тот процесс, или сигнал не доходит.

**Диагностика:**
```bash
# Проверка namespace
readlink /proc/<PID>/ns/pid
readlink /proc/self/ns/pid

# Использование nsenter для отправки сигнала в правильном namespace
nsenter -t <PID> -n kill -TERM <PID_IN_NS>
```
