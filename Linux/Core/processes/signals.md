# Сигналы в Linux

## Определения

**Сигналы** — это программные прерывания, асинхронно отправляемые процессам для уведомления о событиях. Являются ключевым механизмом [межпроцессного взаимодействия (IPC)](./ipc.md) и используются для управления жизненным циклом процессов.

**Количество сигналов:** В современных ядрах Linux определено 64 сигнала (сигналы с номерами 1–64). Первые 32 сигнала стандартизированы POSIX, остальные (33–64) являются сигналами реального времени (RT signals) и могут использоваться для пользовательских целей.

## Основные концепции

### Жизненный цикл и обработка

1. **Генерация:** Сигнал создается ядром (например, при аппаратной ошибке), другим процессом (через системный вызов `kill()`) или пользователем (например, `Ctrl+C`).
2. **Доставка:** Сигнал доставляется процессу, но остается "ожидающим" (pending), если процесс временно заблокировал его доставку.
3. **Обработка:** Процесс выполняет одно из действий:
    * **Действие по умолчанию:** Для каждого сигнала есть стандартное поведение (завершение, игнорирование, создание coredump).
    * **Перехват:** Процесс выполняет кастомную функцию-обработчик.
    * **Игнорирование:** Процесс игнорирует сигнал. Сигналы `SIGKILL` и `SIGSTOP` игнорировать или перехватить нельзя.

### Категории сигналов

* **Сигналы завершения:** Запрашивают или требуют завершения работы (`SIGTERM`, `SIGKILL`, `SIGINT`).
* **Сигналы управления:** Приостанавливают и возобновляют выполнение (`SIGSTOP`, `SIGCONT`, `SIGTSTP`).
* **Сигналы-уведомления:** Информируют о событиях (`SIGCHLD`, `SIGHUP`).
* **Сигналы об ошибках:** Сообщают об аппаратных или программных ошибках (`SIGSEGV`, `SIGFPE`).

### Таблица основных сигналов

| Сигнал | Номер | Описание | Действие по умолчанию | Можно перехватить |
| :--- | :--- | :--- | :--- | :--- |
| **SIGHUP** | 1 | Hangup (разрыв связи) | Завершение | Да |
| **SIGINT** | 2 | Interrupt (прерывание) | Завершение | Да |
| **SIGQUIT** | 3 | Quit (выход) | Завершение + coredump | Да |
| **SIGKILL** | 9 | Kill (немедленное завершение) | Завершение | **Нет** |
| **SIGTERM** | 15 | Terminate (корректное завершение) | Завершение | Да |
| **SIGSTOP** | 19 | Stop (остановка) | Остановка | **Нет** |
| **SIGCONT** | 18 | Continue (возобновление) | Продолжить | Да |
| **SIGTSTP** | 20 | Terminal Stop (остановка с терминала) | Остановка | Да |
| **SIGCHLD** | 17 | Child status changed | Игнорирование | Да |
| **SIGSEGV** | 11 | Segmentation violation | Завершение + coredump | Да |
| **SIGFPE** | 8 | Floating-point exception | Завершение + coredump | Да |

> **Примечание:** Номера сигналов могут отличаться на разных архитектурах. Всегда используйте имена сигналов в скриптах.

### Ключевые сигналы

#### SIGHUP (1)

Изначально — разрыв связи с терминалом. Сейчас используется для запроса на **перечитывание конфигурации** без перезапуска службы (например, `nginx`, `systemd`).

```bash
# Перечитать конфигурацию nginx
pkill -HUP nginx
# Или через systemd
systemctl reload nginx
```

#### SIGINT (2)

Сигнал прерывания с клавиатуры (`Ctrl+C`). Похож на `SIGTERM`, процесс может его перехватить.

#### SIGQUIT (3)

Сигнал выхода (`Ctrl+\`), аналогичен `SIGINT`, но дополнительно создает **coredump** (снимок памяти процесса), если это разрешено.

#### SIGKILL (9)

Безусловное, **немедленное завершение** процесса. Сигнал невозможно перехватить или проигнорировать. Ядро операционной системы завершает процесс напрямую, **не давая ему шанса выполнить какие-либо "грамотные" действия** (например, сохранить данные, закрыть файлы или соединения), а также без возможности сообщить родителю о своем завершении. Это "грубое" завершение.

> **Риски использования SIGKILL:**
>
> * Потеря данных и повреждение файлов
> * Утечка ресурсов (незакрытые сетевые соединения, временные файлы)
> * Появление осиротевших процессов

#### SIGTERM (15)

Стандартный сигнал для **корректного завершения** процесса. Позволяет процессу выполнить очистку (сохранить данные, закрыть файлы, завершить транзакции). Если в программе не прописана специальная логика для `SIGTERM`, по умолчанию процесс будет завершен. Сигнал по умолчанию для утилиты `kill`.

> **Graceful Shutdown:** Приложения должны перехватывать `SIGTERM` для корректного завершения работы. Это особенно важно в контейнерах (Docker, Kubernetes), где `docker stop` отправляет именно `SIGTERM`.

> **Важно:** При получении `SIGTERM` процесс **сам решает**, как завершаться — может сохранить состояние, закрыть соединения, записать логи. Это занимает время, но гарантирует целостность данных. Если процесс не обрабатывает `SIGTERM`, он будет завершен ядром по умолчанию.

**Практическое правило:** Всегда сначала пробуйте `kill <PID>` (SIGTERM), и только если процесс не реагирует — используйте `kill -9 <PID>` (SIGKILL).

#### SIGSTOP (19) / SIGCONT (18)

* **SIGSTOP:** Безусловная **остановка (пауза)** выполнения процесса. Не может быть перехвачен или проигнорирован.
* **SIGCONT:** **Возобновляет** выполнение процесса, ранее остановленного сигналом `SIGSTOP` или `SIGTSTP`.

```bash
# Остановить процесс
kill -STOP <PID>

# Возобновить процесс
kill -CONT <PID>
```

#### SIGTSTP (20)

Сигнал остановки с клавиатуры (`Ctrl+Z`). В отличие от `SIGSTOP`, может быть перехвачен или проигнорирован.

#### SIGCHLD (17)

Отправляется родительскому процессу при завершении (или остановке) дочернего. Требует от родителя обработать статус потомка через системный вызов `wait()`, чтобы избежать появления зомби-процессов.

### Сигналы реального времени (RT signals)

Сигналы с номерами **34–64** (в некоторых ядрах 33–64) называются сигналами реального времени (Real-Time Signals, `SIGRTMIN` + N).

**Особенности:**

* Могут использоваться для пользовательских целей
* Поддерживают очередь (в отличие от стандартных сигналов)
* Имеют приоритеты (с меньшим номером — выше приоритет)
* Передают дополнительную информацию (сигналы с данными)

```bash
# Использование в bash
kill -SIGRTMIN+2 <PID>
```

## Практические сценарии

### Отправка сигналов

Для отправки сигналов используются утилиты `kill`, `pkill` и `killall`.

* **`kill <PID>`**: Отправляет сигнал конкретному процессу по его идентификатору.
* **`pkill <name>`**: Отправляет сигнал процессам по их имени.
* **`killall <name>`**: Похожа на `pkill`, но в некоторых системах имеет более строгое поведение (ищет точное совпадение имени процесса).

```bash
# Отправить запрос на корректное завершение (SIGTERM)
kill 1234

# Принудительно завершить все процессы с именем "chrome"
pkill -9 chrome
# или
killall -KILL chrome

# Дать команду nginx перечитать конфигурацию
pkill -HUP nginx
# Аналогично: systemctl reload nginx или nginx -s reload

# Приостановить все процессы пользователя 'user'
killall -STOP -u user

# Возобновить их
killall -CONT -u user

# Отправить сигнал реальному времени
kill -SIGRTMIN+1 <PID>
```

### Обработка SIGCHLD

Корректная обработка `SIGCHLD` родительским процессом с вызовом `wait()` или `waitpid()` обязательна для предотвращения накопления зомби-процессов. Если родитель не обрабатывает этот сигнал, ядро оставляет завершенные дочерние процессы в таблице процессов в виде "зомби".

### Сигналы в Docker и Kubernetes

**Docker:**

* `docker stop` отправляет `SIGTERM`, затем через 10 секунд `SIGKILL`
* `STOPSIGNAL` в Dockerfile позволяет изменить сигнал остановки

```dockerfile
STOPSIGNAL SIGQUIT
```

**Kubernetes:**

* Pod получает `SIGTERM` при удалении или масштабировании
* `terminationGracePeriodSeconds` (по умолчанию 30 сек) определяет время до `SIGKILL`

## Дополнительная информация

### Переносимость сигналов

Номера сигналов (например, 15 для `SIGTERM`) могут отличаться в разных UNIX-подобных системах и на разных архитектурах. Имена (`SIGTERM`, `SIGKILL`) стандартизированы в POSIX и являются полностью переносимыми.

**Рекомендация:** В скриптах и программах всегда используйте имена сигналов, а не их числовые значения.

### SIGKILL и зомби-процессы

"Убить" зомби-процесс сигналом `SIGKILL` **невозможно**, так как он уже не является исполняемым кодом, а представляет собой лишь запись в таблице процессов. Единственный способ его убрать — корректно завершить родительский процесс или дождаться, пока родитель обработает `SIGCHLD`.

### Отладка обработки сигналов

```bash
# Отследить получение сигналов процессом
strace -e trace=signal -p <PID>

# Посмотреть маску заблокированных сигналов
cat /proc/<PID>/status | grep Sig
```
