# Сигналы процессов в Linux

## Определения

**Сигналы (Signals)** — это асинхронные программные прерывания, отправляемые процессам для уведомления о событиях. Они являются фундаментальным механизмом [**IPC (Inter-Process Communication — межпроцессное взаимодействие)**](./ipc.md) и основным средством управления жизненным циклом процессов.

**Количество сигналов:** В современных Linux-системах поддерживается 64 сигнала.
- **1–31:** Стандартные сигналы POSIX.
- **32–64:** Сигналы реального времени (Real-time signals), имеющие номера от `SIGRTMIN` до `SIGRTMAX`.

**Диспозиция сигнала (Signal Disposition):** Текущий способ реакции процесса на конкретный сигнал. Существует три варианта:
- **Действие по умолчанию (Default action):** Заданное ядром поведение (Term, Core, Stop, Cont, Ign).
- **Игнорирование (Ignore):** Сигнал отбрасывается (кроме `SIGKILL` и `SIGSTOP`).
- **Пользовательский обработчик (Signal Handler):** Вызов функции, определенной в коде приложения.

## Основные концепции

### Жизненный цикл сигнала

1. **Генерация (Generation):** Сигнал инициируется ядром (ошибки CPU, таймеры), пользователем (клавиатура) или другим процессом (системный вызов `kill`).
2. **Ожидание (Pending):** Сигнал сгенерирован, но еще не доставлен (например, если он заблокирован процессом).
3. **Доставка (Delivery):** Ядро приостанавливает выполнение процесса и переключает контекст на выполнение обработчика или стандартного действия.

### Блокировка и маскирование сигналов

Процесс может временно блокировать доставку определенных сигналов, устанавливая **маску сигналов (Signal Mask)** через системные вызовы `sigprocmask` (для однопоточных) или `pthread_sigmask` (для многопоточных приложений).

- **Заблокированные сигналы** остаются в состоянии ожидания (pending) и доставляются сразу после разблокировки.
- **Сигналы реального времени** при блокировке ставятся в очередь, в то время как стандартные сигналы могут быть потеряны, если за время блокировки пришло несколько идентичных сигналов (доставится только один).

### Безопасность функций (Async-signal-safety)

Обработчик сигнала прерывает основной поток выполнения в произвольный момент. Это накладывает жесткие ограничения на функции, которые можно вызывать внутри обработчика:
- **Запрещено:** Вызывать функции, использующие глобальное состояние или блокировки (например, `malloc`, `free`, `printf`).
- **Разрешено:** Вызывать только **асинхронно-безопасные функции** (async-signal-safe functions), такие как `write`, `read`, `_exit`, `waitpid`.

### Анализ масок сигналов через /proc

Для диагностики поведения процесса (например, почему он не реагирует на `SIGTERM`), можно изучить его статусные файлы в `/proc`.

```bash
cat /proc/<PID>/status | grep Sig
# SigPnd: 0000000000000000 (Ожидающие сигналы для процесса)
# SigBlk: 0000000000000000 (Заблокированные сигналы)
# SigIgn: 0000000000001000 (Игнорируемые сигналы)
# SigCgt: 0000000180014007 (Перехваченные сигналы с обработчиками)
```
Значения представлены в виде 64-битных шестнадцатеричных масок, где каждый бит соответствует номеру сигнала.

### Таблица основных сигналов

| **SIGHUP** | 1 | Разрыв связи (Hangup) / Перезагрузка конфига | Term | Да |

| **SIGQUIT** | 3 | Выход (Ctrl+\\) | Core | Да |
| **SIGKILL** | 9 | Безусловное немедленное завершение | Term | **Нет** |
| **SIGTERM** | 15 | Стандартный сигнал завершения | Term | Да |
| **SIGSTOP** | 19 | Безусловная остановка процесса | Stop | **Нет** |
| **SIGCONT** | 18 | Возобновление остановленного процесса | Cont | Да |
| **SIGSEGV** | 11 | Ошибка сегментации (Invalid memory) | Core | Да |
| **SIGCHLD** | 17 | Изменение статуса дочернего процесса | Ign | Да |
| **SIGPIPE** | 13 | Запись в канал без читателя | Term | Да |
| **SIGUSR1/2** | 10/12 | Пользовательские сигналы | Term | Да |

### Ключевые механизмы и особенности

#### SIGTERM против SIGKILL

- **SIGTERM (15):** Позволяет выполнить **Graceful Shutdown**. Приложение закрывает дескрипторы, сохраняет состояние и завершает транзакции.
- **SIGKILL (9):** Принудительная остановка ядром. Процесс не получает уведомления. Опасно потерей данных или "зависанием" внешних ресурсов (например, блокировок в БД).

#### SIGHUP (1) и современные службы

В системных демонах (Nginx, PostgreSQL, systemd) `SIGHUP` традиционно используется для перечитывания файлов конфигурации без остановки процесса (Hot Reload).

#### Сигналы реального времени (RT)

В отличие от стандартных сигналов:
- Гарантированно доставляются в порядке очереди.
- Не объединяются: если отправлено 10 сигналов, будет 10 вызовов обработчика.
- Могут нести полезную нагрузку (целое число или указатель) через `sigqueue`.

#### signalfd: Обработка сигналов как файлов

Современный Linux предоставляет системный вызов `signalfd`, который позволяет получать сигналы через обычный файловый дескриптор. Это позволяет обрабатывать сигналы в рамках единого событийного цикла (`epoll`, `select`) вместе с сетевым трафиком, не создавая асинхронных обработчиков.

## Практические сценарии

### Управление через терминал и PID

```bash
# Плавная остановка (SIGTERM)
kill <PID>

# Принудительное завершение (SIGKILL)
kill -9 <PID>

# Перезагрузка конфигурации демона
kill -HUP $(cat /var/run/nginx.pid)

# Остановка всех процессов определенного пользователя
pkill -u <username>
```

### Безопасная отправка через pidfd

Системный вызов `pidfd_send_signal` (Linux 5.3+) решает проблему переиспользования PID (race condition). Даже если процесс завершился и его PID занял другой процесс, сигнал через `pidfd` уйдет только оригинальному адресату. Подробнее см. [**pidfd: безопасное управление процессами**](./additional_info.md#pidfd-безопасное-управление-процессами).

### Сигналы в Docker и Kubernetes

Оркестраторы используют сигналы для управления жизненным циклом контейнеров.

- **Завершение:** Сначала отправляется `SIGTERM`, по истечении `terminationGracePeriodSeconds` (в K8s по умолчанию 30с) — `SIGKILL`.
- **Проблемы с PID 1:** В контейнерах процесс с PID 1 не имеет обработчиков сигналов по умолчанию. Если приложение не обрабатывает `SIGTERM` явно, оно будет завершаться только принудительно по `SIGKILL` по истечении таймаута.
- **preStop хуки:** В Kubernetes выполняются **перед** отправкой `SIGTERM`.

### Инструменты отладки

```bash
# Отслеживание сигналов в реальном времени
strace -e signal -p <PID>

# Проверка диспозиции сигналов процесса (через дешифровку масок)
cat /proc/<PID>/status | grep Sig
```

## Дополнительная информация

### Коды завершения (Exit Codes)

Если процесс завершился по сигналу, его код выхода равен `128 + номер сигнала`.
- `130` (128+2) — Прервано пользователем (SIGINT).
- `137` (128+9) — Убито ядром или OOM Killer (SIGKILL).
- `143` (128+15) — Корректно завершено по таймауту (SIGTERM).

Подробнее см. раздел [**Коды завершения (Exit Codes)**](../../Shell/exit_codes.md).

### Группы процессов и терминал

Сигналы, генерируемые клавиатурой (`SIGINT`, `SIGTSTP`), отправляются всей **группе процессов переднего плана (Foreground Process Group)**. Это позволяет одной комбинацией клавиш остановить весь конвейер команд (`ls | grep | awk`).
