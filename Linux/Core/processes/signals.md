# Process Signals in Linux

## Определения

**Сигналы (Signals)** — асинхронные программные прерывания, отправляемые процессам для уведомления о событиях. Ключевой механизм [**IPC**](./ipc.md) для управления жизненным циклом процессов.

**Количество:** 64 сигнала (номера 1–64). Первые 32 — стандартные POSIX, остальные (33–64) — сигналы реального времени (RT signals).

**pidfd (PID File Descriptor)** — файловый дескриптор процесса, введённый в Linux 5.3. Уникальный ссылочный объект, который остаётся валидным для конкретного процесса даже при переиспользовании его PID. Решает проблему race conditions при управлении процессами через традиционные PID-базированные методы. Подробнее: [pidfd: безопасное управление процессами](./additional_info.md#pidfd-безопасное-управление-процессами).

## Основные концепции

### Жизненный цикл сигнала

1. **Генерация:** Создание сигнала ядром (аппаратная ошибка), другим процессом (`kill()`) или пользователем (`Ctrl+C`).
2. **Доставка:** Сигнал доставляется процессу. Может остаться pending, если процесс заблокировал его.
3. **Обработка:** Одно из действий:
   - **Действие по умолчанию** — завершение, игнорирование, coredump
   - **Перехват (catch)** — выполнение кастомного обработчика
   - **Игнорирование** — сигнал отбрасывается (`SIGKILL`, `SIGSTOP` игнорировать нельзя)

### Категории сигналов

| Категория | Сигналы | Назначение |
| :--- | :--- | :--- |
| **Завершение** | `SIGTERM`, `SIGKILL`, `SIGINT` | Корректное или принудительное завершение |
| **Управление** | `SIGSTOP`, `SIGCONT`, `SIGTSTP` | Приостановка и возобновление |
| **Уведомления** | `SIGCHLD`, `SIGHUP` | Информация о событиях |
| **Ошибки** | `SIGSEGV`, `SIGFPE`, `SIGBUS` | Аппаратные/программные ошибки |

### Таблица основных сигналов

| Сигнал | Номер | Описание | Действие по умолчанию | Перехват |
| :--- | :--- | :--- | :--- | :--- |
| **SIGHUP** | 1 | Разрыв связи | Завершение | Да |
| **SIGINT** | 2 | Прерывание (Ctrl+C) | Завершение | Да |
| **SIGQUIT** | 3 | Выход (Ctrl+\\) | Завершение + coredump | Да |
| **SIGKILL** | 9 | Немедленное завершение | Завершение | **Нет** |
| **SIGTERM** | 15 | Корректное завершение | Завершение | Да |
| **SIGSTOP** | 19 | Остановка | Остановка | **Нет** |
| **SIGCONT** | 18 | Возобновление | Продолжить | Да |
| **SIGTSTP** | 20 | Остановка с терминала (Ctrl+Z) | Остановка | Да |
| **SIGCHLD** | 17 | Изменение статуса дочернего | Игнорирование | Да |
| **SIGSEGV** | 11 | Segmentation violation | Завершение + coredump | Да |
| **SIGFPE** | 8 | Floating-point exception | Завершение + coredump | Да |

> **Примечание:** Номера сигналов зависят от архитектуры. Всегда используйте имена сигналов в скриптах.

### Ключевые сигналы

#### SIGTERM (15) vs SIGKILL (9)

| Характеристика | SIGTERM | SIGKILL |
| :--- | :--- | :--- |
| **Тип** | Корректное завершение | Принудительное завершение |
| **Перехват** | Да | Нет |
| **Очистка ресурсов** | Процесс управляет сам | Нет |
| **Риски** | Нет | Потеря данных, утечка ресурсов |
| **Использование** | `kill <PID>` (по умолчанию) | `kill -9 <PID>` (крайняя мера) |

**SIGTERM:** Стандартный сигнал для graceful shutdown. Процесс может сохранить данные, закрыть соединения, записать логи. Занимает время, но гарантирует целостность.

**SIGKILL:** Ядро завершает процесс напрямую, без возможности выполнить cleanup. Процесс не может сообщить родителю о завершении.

> **Правило:** Всегда сначала `kill <PID>` (SIGTERM), только при отсутствии реакции — `kill -9 <PID>` (SIGKILL).

#### SIGHUP (1)

Изначально — разрыв связи с терминалом. Сейчас используется для **перечитывания конфигурации** без перезапуска:

```bash
# Перечитать конфигурацию nginx
pkill -HUP nginx
# Или через systemd
systemctl reload nginx
```

#### SIGINT (2) / SIGQUIT (3)

- **SIGINT** — прерывание с клавиатуры (`Ctrl+C`). Похож на SIGTERM, перехватывается.
- **SIGQUIT** — выход (`Ctrl+\`). Аналогичен SIGINT, но создаёт **coredump**.

#### SIGSTOP (19) / SIGCONT (18)

- **SIGSTOP** — безусловная пауза процесса. Не перехватывается.
- **SIGCONT** — возобновление выполнения.

```bash
kill -STOP <PID>   # Пауза
kill -CONT <PID>   # Возобновление
```

#### SIGTSTP (20)

Остановка с клавиатуры (`Ctrl+Z`). В отличие от SIGSTOP, может быть перехвачен.

#### SIGCHLD (17)

Отправляется родителю при завершении/остановке дочернего процесса. Требует вызова `wait()`/`waitpid()` для предотвращения зомби-процессов. Подробнее: [**Troubleshooting: Зомби-процессы**](./Troubleshooting/debugging.md#зомби-процессы).

### Сигналы реального времени (RT signals)

Номера **34–64** (`SIGRTMIN + N`). Особенности:

- Пользовательские цели
- Поддерживают очередь (в отличие от стандартных сигналов)
- Приоритет: меньший номер → выше приоритет
- Передают дополнительную информацию (сигналы с данными)

```bash
kill -SIGRTMIN+2 <PID>
```

## Практические сценарии

### Отправка сигналов

| Утилита | Синтаксис | Когда использовать |
| :--- | :--- | :--- |
| `kill` | `kill -<SIGNAL> <PID>` | Точный PID процесса |
| `pkill` | `pkill -<SIGNAL> <name>` | Поиск по имени процесса |
| `killall` | `killall -<SIGNAL> <name>` | Точное совпадение имени |

```bash
# Корректное завершение (SIGTERM)
kill 1234

# Принудительное завершение всех процессов chrome
pkill -9 chrome
killall -KILL chrome

# Перечитать конфигурацию
pkill -HUP nginx

# Приостановить все процессы пользователя
killall -STOP -u user
killall -CONT -u user

# Real-time сигнал
kill -SIGRTMIN+1 <PID>
```

### Отправка сигналов через pidfd

Традиционные методы (`kill`, `kill()`) уязвимы к **PID reuse** — если процесс завершился и его PID назначен новому процессу, сигнал может уйти не адресату.

**pidfd** решает эту проблему на уровне ядра:

```c
// Получить pidfd процесса (syscall, Linux 5.3+)
int pidfd = pidfd_open(pid, 0);

// Отправить сигнал через pidfd — безопасно, без race conditions
pidfd_send_signal(pidfd, SIGTERM, NULL, 0);

// waitid с pidfd — ожидание завершения конкретного процесса
waitid(P_PIDFD, pidfd, &siginfo, WEXITED);
```

**Системные вызовы pidfd:**

| Вызов | Назначение | Linux |
| :--- | :--- | :--- |
| `pidfd_open(pid, flags)` | Получить файловый дескриптор процесса | 5.3+ |
| `pidfd_send_signal(fd, sig, info, flags)` | Отправить сигнал через pidfd | 5.3+ |
| `clone3(&args, size)` | Создать процесс с pidfd (флаг `CLONE_PIDFD`) | 5.3+ |
| `waitid(P_PIDFD, pidfd, ...)` | Ждать завершения процесса по pidfd | 5.3+ |
| `poll()/epoll()` на pidfd | Отслеживать завершение процесса (POLLIN при exit) | 5.3+ |

**Преимущества pidfd:**

- **Иммунитет к PID reuse** — pidfd привязан к конкретному `task_struct`, а не к числовому PID
- **Асинхронное ожидание** — pidfd поддерживает `poll()`/`epoll()`, не нужно циклически опрашивать
- **Единый интерфейс** — файловые дескрипторы работают с существующими механизмами (epoll, select)
- **Безопасность в многопоточных средах** — нет гонки между `kill()` и завершением процесса

> **Практическое правило:** Для долгосрочного управления процессами (демоны, оркестраторы, контейнеры) предпочтительнее pidfd. Для разовых операций в скриптах — традиционные `kill`/`pkill` остаются допустимыми.

### Graceful Shutdown в контейнерах

**Docker:**
- `docker stop` → `SIGTERM`, через 10s → `SIGKILL`
- `STOPSIGNAL` в Dockerfile меняет сигнал остановки

```dockerfile
STOPSIGNAL SIGQUIT
```

**Kubernetes:**
- Pod получает `SIGTERM` при удалении/масштабировании
- `terminationGracePeriodSeconds` (по умолчанию 30s) → время до `SIGKILL`

Коды выхода контейнеров: 137 = SIGKILL (128+9), 143 = SIGTERM (128+15). Подробнее: [**OOM Killer в контейнерах**](./oom_killer_containers.md).

### Отладка обработки сигналов

```bash
# Отследить сигналы процесса
strace -e trace=signal -p <PID>

# Маска заблокированных сигналов
cat /proc/<PID>/status | grep Sig
```

## Дополнительная информация

### Переносимость сигналов

Номера сигналов различаются на разных UNIX-системах и архитектурах. Имена (`SIGTERM`, `SIGKILL`) стандартизированы POSIX и переносимы.

**Рекомендация:** Всегда используйте имена сигналов, а не числа.

### SIGKILL и зомби-процессы

Зомби-процесс **невозможно** удалить сигналом `SIGKILL` — это уже не исполняемый код, а запись в таблице процессов. Удаление возможно через:
- Корректное завершение родительского процесса
- Обработку `SIGCHLD` родителем

### Связь с кодами выхода

Завершение по сигналу: код выхода = `128 + номер сигнала`.

| Сигнал | Код выхода | Контекст |
| :--- | :--- | :--- |
| SIGINT (2) | 130 | Прерывание пользователем |
| SIGKILL (9) | 137 | OOM Killer, `kill -9` |
| SIGTERM (15) | 143 | Graceful shutdown timeout |

Подробнее: [**Exit Codes**](../../Shell/exit_codes.md).
