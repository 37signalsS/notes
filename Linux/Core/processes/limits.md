# Лимиты ресурсов и OOM Killer

## Определения

* **Лимиты ресурсов (Resource Limits):** Ограничения на потребление системных ресурсов (CPU, память, количество файлов), устанавливаемые для пользователя или процесса. Утилита `ulimit` и конфигурационные файлы позволяют управлять этими лимитами.
* **OOM Killer (Out-of-Memory Killer):** Механизм ядра Linux, который принудительно завершает процессы при острой нехватке оперативной памяти (RAM) для предотвращения полного отказа системы.
* **Fork Bomb:** Атака типа "отказ в обслуживании", при которой процесс экспоненциально создает свои копии, быстро исчерпывая лимит процессов и другие ресурсы системы.

## Основные концепции

### "Мягкие" и "Жесткие" лимиты

* **Soft Limit ("Мягкий" лимит):** Текущее действующее ограничение для процесса. Любой пользователь может увеличивать свой мягкий лимит до значения жесткого лимита.
* **Hard Limit ("Жесткий" лимит):** Верхняя граница, до которой можно увеличить мягкий лимит. Изменять (повышать) жесткий лимит может только `root`.

### Типы лимитов

| Лимит | Флаг `ulimit` | Описание | Единицы |
| :--- | :--- | :--- | :--- |
| **Открытые файлы** | `-n` | Максимальное количество открытых файловых дескрипторов | файлы |
| **Процессы** | `-u` | Максимальное количество процессов пользователя | процессы |
| **Виртуальная память** | `-v` | Максимальный объем виртуальной памяти | KB |
| **Размер памяти (RSS)** | `-m` | Максимальный размер резидентной памяти | KB |
| **Core-файл** | `-c` | Максимальный размер core-дампа | KB |
| **Время CPU** | `-t` | Максимальное время CPU | секунды |
| **Размер файла** | `-f` | Максимальный размер создаваемого файла | блоки |

### Как OOM Killer выбирает "жертву"

Когда в Linux заканчивается оперативная память, система стоит перед критическим выбором: зависнуть полностью или пожертвовать одним из процессов, чтобы выжить. За это жёсткое, но необходимое решение отвечает механизм OOM Killer.

Он не убивает процессы случайно. Вместо этого для каждого вычисляется **"рейтинг плохости" (oom_score)**. Процесс с наивысшим рейтингом признаётся наименее важным и подлежит уничтожению. В расчёте участвуют почти все процессы, кроме `init` и потоков ядра (kernel threads).

Каждый процесс имеет три связанных файла в `/proc/<PID>/`:

| Файл | Диапазон | Описание | Кто изменяет |
| :--- | :--- | :--- | :--- |
| `oom_score` | 0–1000 | Текущее значение очков. Вычисляется ядром автоматически | Ядро (автоматически) |
| `oom_score_adj` | -1000–1000 | Корректирующий коэффициент для влияния на oom_score | Пользователь (вручную) |
| `oom_adj` | -17–15 | Устаревший аналог `oom_score_adj` | Устарел |

> **Важно:** Изменение `oom_score_adj` автоматически пересчитывает `oom_adj`.

**Формула расчёта итогового score:**

```
Итоговый score = oom_score (от ядра) + oom_score_adj (пользовательский)
```

**Факторы, повышающие `oom_score` (увеличивают шанс быть убитым):**

* Большое потребление оперативной памяти (RAM)
* Наличие большого количества дочерних процессов, которые также потребляют память
* Высокое значение `nice` (низкий приоритет процесса)
* Короткое время жизни процесса

**Факторы, понижающие `oom_score` (уменьшают шанс быть убитым):**

* Процесс запущен от имени `root`
* Процесс имеет прямой доступ к оборудованию
* Длительное время работы (недавно запущенные процессы имеют некоторую защиту)
* Низкое значение `oom_score_adj`
* Процесс является частью cgroup с собственными лимитами памяти

### Уровни применения лимитов

В современных системах существует несколько уровней управления ресурсами:

```
┌─────────────────────────────────────────┐
│         systemd (сервисы)               │  ← Приоритет для демонов
│         LimitNOFILE, LimitNPROC         │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│         cgroups v2 (контейнеры)         │  ← Жёсткие лимиты
│         memory.max, pids.max            │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│    PAM / limits.conf (пользователи)     │  ← Для пользовательских сессий
│    * soft nofile 65536                  │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│         ulimit (текущая сессия)         │  ← Временные лимиты
│         ulimit -n 4096                  │
└─────────────────────────────────────────┘
```

> **Важно:** Для системных сервисов всегда используйте директивы в `.service` файлах `systemd`. Это наиболее надежный и предсказуемый способ.

## Практические сценарии

### Управление лимитами (`ulimit`)

Команда `ulimit` позволяет просматривать и устанавливать "мягкие" лимиты для **текущей сессии оболочки**.

```bash
# Посмотреть все текущие лимиты
ulimit -a

# Посмотреть и установить лимит на количество открытых файлов (nofile)
ulimit -n
ulimit -n 4096

# Защита от «Fork Bomb» путем ограничения количества процессов
ulimit -u 1024

# Ограничить максимальный объем виртуальной памяти для процесса (в килобайтах)
ulimit -v 2048000
```

> **Важно:** Изменения `ulimit` действуют только для текущей сессии и дочерних процессов.

### Постоянная настройка лимитов

#### 1. Для сервисов `systemd` (предпочтительный способ)

Лимиты устанавливаются прямо в юнит-файле сервиса.

```ini
# /etc/systemd/system/my-app.service
[Service]
LimitNOFILE=65536      # Лимит на количество открытых файлов
LimitNPROC=2048        # Лимит на количество процессов
LimitCORE=infinity     # Лимит на размер core-файла
LimitAS=8G             # Лимит на адресное пространство
OOMScoreAdjust=-1000   # Защита от OOM Killer
```

После изменения файла:
```bash
sudo systemctl daemon-reload
sudo systemctl restart my-app
```

#### 2. Для пользовательских сессий (классический способ)

Используется файл `/etc/security/limits.conf`.

```bash
# /etc/security/limits.conf
# <domain>  <type>  <item>    <value>
# ------------------------------------
*           soft    nofile    65536
*           hard    nofile    131072
student     hard    nproc     1024
@usergroup  hard    as        2048000  # Лимит адресного пространства (virtual memory) в КБ
```

> **Важно:** Для применения изменений пользователь должен перезайти в систему (logout/login).

### Управление поведением OOM Killer

#### Для обычного процесса

Изменение `oom_score_adj` в реальном времени:

```bash
# Сделать процесс "неубиваемым" (максимальная защита)
sudo echo -1000 > /proc/<PID>/oom_score_adj

# Сделать процесс главным кандидатом на уничтожение
sudo echo 1000 > /proc/<PID>/oom_score_adj

# Просмотреть текущие значения
cat /proc/<PID>/oom_score
cat /proc/<PID>/oom_score_adj
```

> **Предупреждение:** Значение `-1000` не даёт 100% гарантии. При экстремальной нехватке памяти OOM Killer может всё равно выбрать этот процесс.

#### Для сервиса `systemd`

Используется директива в юнит-файле:

```ini
[Service]
OOMScoreAdjust=-1000
OOMPolicy=continue  # Продолжить работу сервиса после OOM
```

#### Для контейнеров Docker

```bash
# Запустить контейнер с изменённым oom_score_adj
docker run --oom-score-adj=500 nginx

# Запустить контейнер с отключённым OOM Killer
docker run --oom-kill-disable=true nginx
```

> **Важно:** `--oom-kill-disable` работает только вместе с `-m` (ограничение памяти).

### Диагностика и тестирование OOM Killer

#### Просмотр рейтинга OOM для процессов

```bash
# Все процессы, отсортированные по oom_score
for p in /proc/[0-9]*; do 
    pid=${p##*/}
    [ -r $p/oom_score ] && printf "%4s %5s %8s %s\n" \
        "$(cat $p/oom_score 2>/dev/null)" \
        "$(cat $p/oom_score_adj 2>/dev/null)" \
        "$pid" \
        "$(cat $p/comm 2>/dev/null)"
done | sort -nr | head -20
```

Пример вывода:
```
700  0      131351  fail2ban-server
693  0      1254    node
692  0      131649  fwupd
```

В данном примере, если произойдет OOM, процесс `fail2ban-server` (PID 131351) будет первым кандидатом на завершение, так как у него самый высокий `oom_score` (700).

#### Просмотр логов OOM Killer

```bash
# Через dmesg
dmesg -T | grep -i "oom\|killed process"

# Через journalctl
journalctl -k | grep -i "oom-kill"

# Детальный просмотр последних OOM событий
journalctl -k -g "Out of memory" -n 50
```

Пример записи в логе:
```
[114247.906865] oom-kill:constraint=CONSTRAINT_NONE,nodemask=(null),
cpuset=/,mems_allowed=0,global_oom,task_memcg=/system.slice/fail2ban.service,
task=fail2ban-server,pid=131351,uid=0
[114247.906966] Out of memory: Killed process 131351 (fail2ban-server) 
total-vm:886820kB, anon-rss:19928kB, file-rss:30592kB, shmem-rss:0kB, 
UID:0 pgtables:628kB oom_score_adj:0
```

#### Принудительный вызов OOM Killer

> **ПРЕДУПРЕЖДЕНИЕ:** Используйте эту команду с осторожностью! Она приведет к немедленному завершению одного или нескольких процессов!

```bash
# Включить sysrq-trigger (если отключен)
echo 1 > /proc/sys/kernel/sysrq

# Принудительно вызвать OOM Killer
echo f > /proc/sysrq-trigger

# Проверить логи
dmesg | tail -50
```

## Дополнительная информация

### Иерархия применения лимитов

В современных системах `systemd` предоставляет основной и наиболее надежный механизм управления ресурсами для сервисов. Настройки лимитов для пользовательских сессий (`limits.conf`) и настройки для сервисов (`systemd`) по большей части независимы.

* Лимиты, установленные в `/etc/systemd/system.conf`, применяются ко всем сервисам и пользовательским сессиям, запущенным через `systemd`.
* Директивы `Limit...` в юнит-файле сервиса имеют приоритет над глобальными настройками `systemd` для этого конкретного сервиса.
* `/etc/security/limits.conf` применяется к сессиям пользователей, которые аутентифицируются через PAM (например, при входе по SSH или в графическую оболочку), но, как правило, не влияет на системные сервисы, управляемые `systemd`.

**Порядок применения (от высшего к низшему):**

1. **cgroups v2** — самые строгие лимиты (для контейнеров)
2. **systemd директивы** — для сервисов
3. **PAM / limits.conf** — для пользовательских сессий
4. **ulimit** — временные лимиты сессии

### OOM Killer в контейнерах

В контейнерах (Docker, Kubernetes) OOM Killer работает на двух уровнях:

| Уровень | Механизм | Результат |
| :--- | :--- | :--- |
| **Хост** | Ядро Linux | Убивает процесс контейнера |
| **Контейнер** | cgroups memory.limit | OOM внутри контейнера |

**Kubernetes QoS классы:**

| QoS класс | oom_score_adj | Описание |
| :--- | :--- | :--- |
| **Guaranteed** | -998 |Highest защита (лимита = request) |
| **Burstable** | 2–999 | Средняя защита |
| **BestEffort** | 1000 | Первый кандидат на удаление |

### Культурные отсылки

Выражение "[PRESS F TO PAY RESPECT](https://en.wikipedia.org/wiki/Press_F_to_pay_respects)" стало популярным мемом после его появления в игре Call of Duty: Advanced Warfare. Существует предположение, что один из контрибьюторов в ядро Linux (mchehab) намеренно использовал "f" как триггер для `sysrq-trigger`, отсылая к этому мему. Это совпадение или намеренная шутка, но оно добавляет неожиданный культурный контекст к работе системных инженеров.
