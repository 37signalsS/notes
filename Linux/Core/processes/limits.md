# Лимиты ресурсов и OOM Killer

## Определения

*   **Лимиты ресурсов (Resource Limits)**: Ограничения на потребление системных ресурсов (CPU, память, количество файлов), устанавливаемые для пользователя или процесса. Утилита `ulimit` и конфигурационные файлы позволяют управлять этими лимитами.
*   **OOM Killer (Out-of-Memory Killer)**: Механизм ядра Linux, который принудительно завершает процессы при острой нехватке оперативной памяти (RAM) для предотвращения полного отказа системы.
*   **Fork Bomb**: Атака типа "отказ в обслуживании", при которой процесс экспоненциально создает свои копии, быстро исчерпывая лимит процессов и другие ресурсы системы.

## Основные концепции

### "Мягкие" и "Жесткие" лимиты

*   **Soft Limit ("Мягкий" лимит):** Текущее действующее ограничение для процесса. Любой пользователь может увеличивать свой мягкий лимит до значения жесткого лимита.
*   **Hard Limit ("Жесткий" лимит):** Верхняя граница, до которой можно увеличить мягкий лимит. Изменять (повышать) жесткий лимит может только `root`.

### Как OOM Killer выбирает "жертву"

Выбор процесса для завершения основан на "очках негодности" (**oom_score**). Чем больше очков у процесса, тем выше вероятность, что он будет "убит".

Каждый процесс имеет три связанных файла в `/proc/<PID>/`:

*   `oom_score`: Текущее значение очков (от 0 до 1000). Это значение нельзя изменять напрямую.
*   `oom_score_adj`: Корректирующий коэффициент, который позволяет влиять на `oom_score`. Диапазон: от -1000 до +1000.
*   `oom_adj`: Устаревший аналог `oom_score_adj`. Диапазон: от -17 до +15. Изменение `oom_score_adj` автоматически пересчитывает `oom_adj`.

**Факторы, повышающие `oom_score` (увеличивают шанс быть убитым):**

*   Большое потребление оперативной памяти (RAM).
*   Наличие большого количества дочерних процессов, которые также потребляют память.
*   Высокое значение `nice` (низкий приоритет процесса).

**Факторы, понижающие `oom_score` (уменьшают шанс быть убитым):**

*   Процесс запущен от имени `root`.
*   Процесс имеет прямой доступ к оборудованию.
*   Малое время работы (недавно запущенные процессы имеют некоторую защиту).
*   Низкое значение `oom_score_adj`.

## Практические сценарии

### Управление лимитами (`ulimit`)

Команда `ulimit` позволяет просматривать и устанавливать "мягкие" лимиты для **текущей сессии оболочки**.

```bash
# Посмотреть все текущие лимиты
ulimit -a

# Посмотреть и установить лимит на количество открытых файлов (nofile)
ulimit -n
ulimit -n 4096

# Защита от «Fork Bomb» путем ограничения количества процессов
ulimit -u 1024
```

### Постоянная настройка лимитов

1.  **Для сервисов `systemd` (предпочтительный способ):**
    Лимиты устанавливаются прямо в юнит-файле сервиса.
    ```ini
    # /etc/systemd/system/my-app.service
    [Service]
    LimitNOFILE=65536  # Лимит на количество открытых файлов
    LimitNPROC=2048   # Лимит на количество процессов
    LimitCORE=infinity # Лимит на размер core-файла
    ```

2.  **Для пользовательских сессий (классический способ):**

    Используется файл `/etc/security/limits.conf`.
    ```
    # <domain>  <type>  <item>    <value>
    # ------------------------------------
    *           soft    nofile    65536
    *           hard    nofile    131072
    student     hard    nproc     1024
    ```

### Управление поведением OOM Killer

*   **Для обычного процесса:**
    Изменение `oom_score_adj` в реальном времени.
    ```bash
    # Сделать процесс "неубиваемым"
    sudo echo -1000 > /proc/<PID>/oom_score_adj

    # Сделать процесс главным кандидатом на уничтожение
    sudo echo 1000 > /proc/<PID>/oom_score_adj
    ```
*   **Для сервиса `systemd`:**
    Используется директива в юнит-файле.
    ```ini
    [Service]
    OOMScoreAdjust=-1000
    ```

## Дополнительная информация

### Иерархия применения лимитов

В современных системах `systemd` предоставляет основной и наиболее надежный механизм управления ресурсами для сервисов. Настройки лимитов для пользовательских сессий (`limits.conf`) и настройки для сервисов (`systemd`) по большей части независимы.

*   Лимиты, установленные в `/etc/systemd/system.conf`, применяются ко всем сервисам и пользовательским сессиям, запущенным через `systemd`.
*   Директивы `Limit...` в юнит-файле сервиса имеют приоритет над глобальными настройками `systemd` для этого конкретного сервиса.
*   `/etc/security/limits.conf` применяется к сессиям пользователей, которые аутентифицируются через PAM (например, при входе по SSH или в графическую оболочку), но, как правило, не влияет на системные сервисы, управляемые `systemd`.

Поэтому для надежного управления ресурсами демонов всегда следует использовать директивы в их `.service` файлах.
