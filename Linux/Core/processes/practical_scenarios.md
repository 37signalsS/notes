# Практические сценарии мониторинга процессов

## Определения

**Мониторинг процессов (Process Monitoring)** — совокупность методов и инструментов для непрерывного наблюдения за состоянием, потреблением ресурсов и жизненным циклом задач в операционной системе для обеспечения надежности (SRE).

**Виртуальная файловая система /proc (procfs)** — интерфейс ядра Linux, экспортирующий данные о процессах. Это основной источник данных для большинства утилит мониторинга (ps, top, lsof).

**Наблюдаемость (Observability)** — способность системы предоставлять внешние данные (метрики, логи, трейсы), позволяющие диагностировать причины инцидентов без внесения изменений в код.

**Rapid Assessment (Быстрая оценка)** — методология диагностики инцидентов по принципу «Macro → Micro → Root Cause». Позволяет локализовать проблему за минуты, а не часы, за счет последовательного сужения области поиска.

## Основные концепции

### Эшелонированный мониторинг (Macro → Micro)

Эффективная диагностика требует последовательного сужения области поиска:

| Уровень | Инструментарий | Сфера применения |
| :--- | :--- | :--- |
| **Системный (Macro)** | `top`, `htop`, `btop`, `vmstat` | Общий обзор, выявление аномалий (CPU/RAM spikes). |
| **Процессный (Micro)** | `pidstat`, `ps`, `pgrep` | Детализация потребления конкретным PID или группой. |
| **Внутренний (Deep)** | `/proc/PID/*`, `strace`, `lsof` | Анализ системных вызовов, дескрипторов и памяти. |
| **Событийный (Events)** | `perf`, `bpftrace`, `auditd` | Отслеживание короткоживущих процессов и прерываний ядра.

### Жизненный цикл и состояния процесса

Ядро Linux переводит задачи (task_struct) через дискретные состояния. Понимание этих состояний позволяет SRE быстро определить класс проблемы:

| Состояние | Обозначение | Значение для SRE |
| :--- | :--- | :--- |
| **Running (R)** | `R` | Процесс выполняется на CPU или стоит в очереди (runqueue). |
| **Sleeping (S)** | `S` | Ожидает события (таймер, сигнал, данные с диска/сети). Нормальное состояние для большинства демонов. |
| **Uninterruptible Sleep (D)** | `D` | Заблокирован внутри ядра (обычно I/O). Не реагирует на сигналы, включая `SIGKILL`. Увеличивает Load Average. |
| **Zombie (Z)** | `Z` | Завершился, но статус не прочитан родителем через `wait()`. Не потребляет CPU/RAM, но занимает запись в таблице процессов. |
| **Stopped (T)** | `T` | Остановлен сигналом (`SIGSTOP`, `SIGTSTP`). Может быть возобновлен `SIGCONT`. |

#### Load Average и контекстные переключения

`Load Average` — среднее количество задач в состояниях Running или Runnable за последние 1/5/15 минут. Важно: в Linux процессы в состоянии **D** (Uninterruptible Sleep) также учитываются в LA.

```bash
# Текущий Load Average
cat /proc/loadavg
# → 2.34 1.89 1.56 3/512 12345
#                      ↑    ↑
#               Running/Ready  Last PID

# Детализация контекстных переключений
pidstat -w 1
# cswch/s — добровольные (ожидание ресурса)
# nvcswch/s — принудительные (квант времени истек)
```

**Интерпретация для SRE:**
- **LA > N (где N = количество CPU):** Есть очередь задач. Проверьте `vmstat 1`, столбец `r` (runnable).
- **Высокий LA при низком CPU %:** Часто указывает на процессы в D-state или ожидание I/O.
- **Высокий voluntary cswch/s:** Процессы часто блокируются на чтении/записи.
- **Высокий nonvoluntary cswch/s:** Недостаток CPU для текущей нагрузки (thrashing, overload).

### Ключевые точки интроспекции в /proc/PID/

Для глубокого анализа процесса SRE используют специфичные файлы в procfs:

| Файл | Назначение для SRE |
| :--- | :--- |
| `smaps_rollup` | Сводная статистика памяти: PSS (реальная доля RAM), RSS, USS. |
| `io` | Реальная статистика ввода-вывода (сколько байт передано на диск/в кэш). |
| `stack` | Текущий стек вызовов ядра (помогает найти причину зависания в состоянии D). |
| `wchan` | Название функции ядра, в которой процесс ожидает ресурса. |
| `status` | Метаданные: лимиты, маски сигналов, UID/GID, количество потоков. |
| `limits` | Фактические лимиты процесса (единственный источник истины). |
| `fd/` | Директория со ссылками на все открытые файлы и сокеты. |

## Практические сценарии

### Сценарий 1: Диагностика нехватки ресурсов (CPU/RAM/IO)

Последовательное уточнение при аномальном потреблении:

```bash
# 1. Поиск лидеров по CPU (snapshot)
ps -eo pid,ppid,%cpu,%mem,comm --sort=-%cpu | head -11

# 2. Мониторинг I/O активности в реальном времени
# pidstat -d показывает дисковую активность (чтение/запись байт в секунду)
pidstat -d 1 -p <PID>

# 3. Проверка реального владения памятью (PSS)
# В отличие от RSS, PSS корректно делит разделяемые библиотеки между процессами.
grep ^Pss /proc/<PID>/smaps_rollup
```
Подробнее о метриках памяти см. [**Метрики потребления памяти процесса**](../memory/process_memory_metrics.md).

### Сценарий 2: Глубокий анализ состояния D (Uninterruptible Sleep)

Процессы в состоянии **D** заблокированы внутри ядра (обычно на I/O) и не реагируют на `kill -9`.

```bash
# 1. Определение функции ожидания (Wait Channel)
cat /proc/<PID>/wchan
# → nfs_wait_bit_killable  (Проблема с сетевой ФС NFS)
# → __lock_page            (Ожидание страницы памяти с диска)

# 2. Просмотр полного стека ядра (требует sudo)
sudo cat /proc/<PID>/stack
```

### Сценарий 3: Интроспекция контейнеров (nsenter)

Для диагностики процессов внутри контейнеров (Docker/K8s) часто эффективнее «войти» в их неймспейсы с хоста.

```bash
# 1. Поиск хостового PID процесса контейнера
PID=$(pgrep -f "имя_вашего_приложения")

# 2. Выполнение команд в сетевом (net) и PID неймспейсе контейнера
# Позволяет использовать инструменты хоста (tcpdump, ss) внутри контейнера
sudo nsenter -t $PID -n -p ss -tlpn

# 3. Просмотр открытых файлов процесса контейнера напрямую
sudo lsof -p $PID
```

### Сценарий 4: Поиск утечек ресурсов (FD и Memory)

Утечки файловых дескрипторов или памяти — частая причина падения высоконагруженных систем.

```bash
# Поиск "топ-виновников" по количеству открытых дескрипторов
ls -d /proc/[0-9]* | xargs -I{} sh -c 'echo "$(ls {}/fd 2>/dev/null | wc -l) $(cat {}/comm 2>/dev/null)"' | sort -rn | head -10

# Проверка наличия удаленных, но открытых файлов (занимают место на диске)
lsof +L1
```

### Сценарий 5: Современный мониторинг через eBPF (bpftrace)

Использование `bpftrace` позволяет ловить события в реальном времени с минимальным оверхедом (в отличие от `strace`).

```bash
# Отслеживание запуска всех новых процессов в системе (execsnoop)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_execve { printf("%s -> %s\n", comm, str(args->filename)); }'

# Отслеживание процессов, открывающих конкретный файл
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat /str(args->filename) == "/etc/shadow"/ { printf("PID %d (%s) accessed shadow!\n", pid, comm); }'
```

### Сценарий 6: Rapid Assessment (Методология быстрой оценки)

Когда сработал пейджинг и время на диагностику ограничено, применяйте последовательный алгоритм:

```bash
# Шаг 1: Общий обзор системы (10 секунд)
vmstat 1 3
# → r: задачи в очереди CPU
# → si/so: swap in/out
# → wa: время CPU в ожидании I/O
# → si/so > 0 = проблема с памятью

# Шаг 2: Идентификация «тяжелых» процессов (10 секунд)
ps -eo pid,ppid,stat,%cpu,%mem,comm --sort=-%cpu | head -10
ps -eo pid,ppid,stat,%cpu,%mem,comm --sort=-%mem | head -10

# Шаг 3: Детализация по PID (30 секунд)
pidstat -p <PID> -d -r -w -u 1 5

# Шаг 4: Проверка состояния ядра
dmesg -T | tail -20
journalctl -k --since "10 minutes ago" | grep -i "error\|oom\|killed"
```

**Правило:** Если за 60 секунд не локализован процесс-виновник — переключайтесь на системный уровень (cgroup, cAdvisor, Prometheus).

### Сценарий 7: Диагностика и очистка зомби-процессов

Зомби-процессы (статус **Z**) уже завершены и не потребляют CPU/RAM, но занимают запись в таблице процессов. Накопление зомби ведет к исчерпанию `pid_max`.

```bash
# 1. Поиск всех зомби
ps aux | awk '$8 ~ /Z/'

# 2. Определение родителя
ZOMBIE_PID=1234
PPID=$(ps -o ppid= -p $ZOMBIE_PID | tr -d ' ')

# 3. Проверка, жив ли родитель
if ps -p $PPID > /dev/null; then
    # Родитель жив — отправляем SIGCHLD
    kill -s SIGCHLD $PPID
else
    # Родитель мертв — зомби должны быть усыновлены PID 1
    # Если нет — перезапустите супервизор
    echo "Parent $PPID is dead, zombies should be reaped by init"
fi

# 4. Если родитель-зомби-мейкер не реагирует, завершите его
# (только после консультации с владельцем сервиса)
kill -9 $PPID
```

### Сценарий 8: Fork bomb и исчерпание PID

Fork bomb — атака или баг, при которых процесс экспоненциально порождает копии себя, исчерпывая таблицу процессов.

```bash
# 1. Обнаружение резкого роста количества процессов
watch -n1 'ps -eo pid,stat,comm | wc -l'

# 2. Поиск процессов с одинаковым именем и множеством детей
pstree -p | head -20

# 3. Остановка fork bomb (требует root)
# Сначала найдите PID родителя
pgrep -f "bomb_pattern"
kill -9 <PARENT_PID>

# 4. Если kill не помогает (таблица переполнена), перезагрузка
# kernel.pid_max можно увеличить заранее
sudo sysctl -w kernel.pid_max=4194304
```

### Сценарий 9: Управление приоритетом и CPU affinity

```bash
# Просмотр текущего nice значения
ps -o pid,ni,pri,comm -p <PID>

# Снижение приоритета (более высокий nice = ниже приоритет)
sudo renice +10 -p <PID>

# Повышение приоритета (только root; максимальный приоритет -20)
sudo renice -5 -p <PID>

# Установка CPU affinity (привязка к конкретным ядрам)
# Процесс будет работать ТОЛЬКО на CPU 0 и 1
taskset -pc 0,1 <PID>

# Проверка текущего affinity
taskset -p <PID>
# → pid 1234's current affinity mask: 3

# Использование ionice для ограничения дискового приоритета (CFQ/BFQ)
# Классы: 1=realtime, 2=best-effort, 3=idle
sudo ionice -c 3 -p <PID>
```

### Сценарий 10: Безопасное завершение процессов

```bash
# Поиск PID по имени
pgrep -f "pattern"

# Отправка SIGTERM всей группе процессов по PGID
kill -TERM -<PGID>

# Завершение всех процессов пользователя
pkill -u www-data

# systemctl kill с указанием сигнала
sudo systemctl kill --signal=SIGTERM myapp.service

# Безопасное завершение только foreground-группы текущего терминала
kill -INT -$(ps -o pgid= -p $$ | tr -d ' ')
```

### Сценарий 11: Поиск процесса по порту или сокету

```bash
# Какой процесс слушает порт 8080?
ss -tlnp | grep :8080
# → LISTEN 0 128 *:8080 *:* users:(("nginx",pid=1234,fd=6))

# Альтернатива: fuser (часто быстрее)
sudo fuser -v 8080/tcp

# Поиск процесса, удерживающего файл/сокет
sudo lsof -i :8080
```

### Сценарий 12: Управление процессами через systemd

```bash
# Запуск временного процесса с лимитами
systemd-run --user --scope \
  -p LimitNOFILE=65536 \
  -p MemoryMax=512M \
  -p CPUQuota=200% \
  ./worker.sh

# Принудительное завершение всех процессов в юните
sudo systemctl kill myapp.service

# Просмотр всех дочерних процессов юнита
systemctl status myapp.service
# → CGroup: /system.slice/myapp.service
#           ├─1234 /usr/bin/myapp
#           ├─1235 /usr/bin/myapp --worker
#           └─1236 /usr/bin/myapp --worker
```

### Сценарий 13: Диагностика маскирования сигналов

Если процесс игнорирует `SIGTERM` или ведет себя аномально:

```bash
# Извлечение масок сигналов
grep Sig /proc/<PID>/status
# SigPnd: 0000000000000000
# SigBlk: 0000000000000000
# SigIgn: 0000000000000002  ← SIGINT проигнорирован
# SigCgt: 0000000180000000  ← SIGTERM пойман

# Декодирование шестнадцатеричной маски
# Каждый бит соответствует сигналу 1..64
# 0000000000000002 = сигнал 2 (SIGINT) игнорируется
```

### Сценарий 14: Учет процессов (auditd)

Для безопасности и compliance требуется логирование создания процессов и открытия критичных файлов.

```bash
# Включение аудита execve (запуск программ)
sudo auditctl -a always,exit -S execve -F arch=b64 -k process_exec

# Логирование открытия /etc/shadow
sudo auditctl -a always,exit -S openat -F path=/etc/shadow -F success=1 -k shadow_access

# Чтение логов
ausearch -i -k process_exec | tail -20

# Отключение правила
sudo auditctl -d always,exit -S execve
```

## Дополнительная информация

### Сравнение инструментов интроспекции

| Инструмент | Сильные стороны | Ограничения | Типичное применение |
| :--- | :--- | :--- | :--- |
| **`htop`** | Интерактивность, управление, наглядность | Не подходит для сценариев/алертинга | Ежедневный мониторинг, kill/nice |
| **`btop`** | Графики GPU/CPU/сеть, визуализация потоков | Больше потребляет ресурсы, чем htop | Демонстрация, deep-dive |
| **`pidstat`** | Таймсериес, итерации, per-CPU | Только числа, нет графиков | `sar`-подобный сбор, мониторинг через cron |
| **`atop`** | Исторические логи, данные по завершенным процессам | Исторические логи требуют места | Post-mortem анализ, nightly |
| **`bpftrace`** | Zero-copy, фильтрация в ядре, минимальный оверхед | Требует root, сложный синтаксис | Продакшен-трассировка |
| **`strace`** | Полные syscall + аргументы | Останавливает процесс, деградация 10-100x | Короткая отладка, не для прода |

### Безопасность и производительность

1.  **Риски strace:** `strace` останавливает процесс на каждом системном вызове. На нагруженном сервере это может привести к деградации производительности на 90%+. Используйте только для короткой отладки.
2.  **Права доступа:** Чтение многих файлов в `/proc/PID/` (например, `stack`, `io`, `fd/`) требует прав владельца процесса или `root`.
3.  **Атомарность:** Помните, что состояние процесса в `/proc` может измениться в процессе чтения.
4.  **Чистка после отладки:** Если вы запускали `strace -f`, убедитесь, что не оставили остановленных дочерних процессов. `strace` прикрепляет `ptrace` к каждому потоку; при завершении сессии процессы возобновляются, но проверяйте:
    ```bash
    # Проверка на остановленные процессы после отладки
    ps -eo pid,stat,comm | grep '^[[:space:]]*[0-9]*[[:space:]]*T'
    ```

### Типичные ошибки и их решение

1.  **Невозможно отправить SIGKILL процессу в состоянии D:**
    - *Причина:* Процесс заблокирован на уровне ядра (NFS, disk I/O). Никакие сигналы не доставляются, пока операция не завершится.
    - *Решение:* Устраните причину блокировки (переподключите NFS, замените диск). Если проблема системная — перезагрузка.

2.  **Зомби-процессы не исчезают после завершения родителя:**
    - *Причина:* PID 1 (init/systemd) некорректно обрабатывает `SIGCHLD`. Часто встречается в минимальных контейнерах без инициализации.
    - *Решение:* Используйте `tini` или `dumb-init` в качестве `ENTRYPOINT`.

3.  **`pgrep` не находит процесс по имени:**
    - *Причина:* `pgrep` ищет только по имени процесса (`comm`), а не по полной командной строке.
    - *Решение:* Используйте `pgrep -f` для поиска по полной командной строке (`cmdline`).
