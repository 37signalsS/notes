# Практические сценарии мониторинга процессов

## Определения

**Мониторинг процессов (Process Monitoring)** — совокупность методов и инструментов для непрерывного наблюдения за состоянием, потреблением ресурсов и жизненным циклом задач в операционной системе.

**Виртуальная файловая система /proc (procfs)** — основной программный интерфейс ядра Linux для экспорта данных о процессах. Содержимое `/proc` генерируется ядром "на лету" в оперативной памяти и не занимает места на диске.

**Наблюдаемость (Observability)** — способность системы предоставлять внешние данные (метрики, логи, трейсы), позволяющие сделать вывод о её внутреннем состоянии без внесения изменений в код приложения.

## Основные концепции

### Эшелонированный мониторинг (Macro → Micro)

Для эффективной диагностики SRE-специалисты используют иерархический подход:

| Уровень | Инструментарий | Сфера применения |
| :--- | :--- | :--- |
| **Системный (Macro)** | `top`, `htop`, `vmstat`, `uptime` | Общий обзор хоста, поиск аномалий нагрузки. |
| **Процессный (Micro)** | `pidstat`, `ps`, `pgrep` | Детализация потребления ресурсов конкретным PID. |
| **Внутренний (Deep)** | `/proc/PID/*`, `strace`, `lsof` | Анализ системных вызовов, карт памяти и дескрипторов. |
| **Событийный (Events)** | `perf`, `ebpf` (bpftrace), `auditd` | Отслеживание короткоживущих процессов и прерываний. |

### Ключевые точки интроспекции в /proc/PID/

Для глубокого анализа поведения процесса следует использовать специализированные файлы:

| Файл | Назначение для SRE |
| :--- | :--- |
| `smaps_rollup` | Сводная статистика памяти: PSS (реальная доля RAM), RSS, USS. |
| `io` | Статистика ввода-вывода: сколько реально прочитано/записано (включая кэш). |
| `stack` | Текущий стек вызовов ядра. Позволяет увидеть, в какой функции "завис" процесс. |
| `wchan` | Название функции ядра, в которой процесс ожидает ресурса (Wait Channel). |
| `status` | Информативная сводка: лимиты, маски сигналов, UID/GID, количество потоков. |
| `exe` | Символическая ссылка на реальный исполняемый файл процесса на диске. |

## Практические сценарии

### Сценарий 1: Диагностика нехватки ресурсов (CPU/RAM/IO)

Когда процесс потребляет аномально много ресурсов, требуется последовательное уточнение:

```bash
# 1. Поиск лидеров по CPU/MEM (snapshot)
ps -eo pid,ppid,%cpu,%mem,comm --sort=-%cpu | head -11

# 2. Мониторинг I/O активности конкретного PID (обновление каждую секунду)
# Требуется пакет sysstat (утилита pidstat)
pidstat -d 1 -p <PID>

# 3. Проверка реального владения памятью (PSS)
# В отличие от RSS, PSS корректно делит разделяемые библиотеки между процессами
grep ^Pss /proc/<PID>/smaps_rollup
```
Подробнее о метриках памяти см. [**Метрики потребления памяти процесса**](../memory/process_memory_metrics.md).

### Сценарий 2: Анализ процессов в состоянии D (Uninterruptible Sleep)

Процессы в состоянии **D** не реагируют на сигналы (включая `SIGKILL`), так как заблокированы внутри ядра.

```bash
# 1. Поиск функции ожидания
cat /proc/<PID>/wchan
# → nfs_wait_bit_killable  (Проблема с NFS-сервером)
# → __lock_page            (Ожидание дискового I/O или нехватка RAM)

# 2. Просмотр полного стека ядра для идентификации места блокировки
sudo cat /proc/<PID>/stack
```

### Сценарий 3: Мониторинг процессов внутри контейнеров

При работе с Docker/Kubernetes SRE часто нужно исследовать процесс контейнера с точки зрения хоста:

```bash
# 1. Поиск хостового PID процесса контейнера
pgrep -f "имя_вашего_приложения"

# 2. Выполнение команды в сетевом пространстве имен процесса (без входа в контейнер)
sudo nsenter -t <PID> -n ip addr

# 3. Просмотр сетевых соединений процесса контейнера
sudo lsof -i -nP -p <PID>
```

### Сценарий 4: Отслеживание жизненного цикла и событий

Для поиска "дребезга" (быстро перезапускающихся процессов) или отслеживания новых задач:

```bash
# Подсветка изменений в выводе pgrep (например, для пользователя www-data)
watch -d "pgrep -u www-data | xargs ps -o pid,comm -p"

# Отправка сигналов группе процессов (например, перезагрузка всех воркеров)
pkill -HUP -f "nginx: worker"
```

### Сценарий 5: Скриптовая диагностика утечек (One-liners)

```bash
# Топ-5 процессов по количеству открытых дескрипторов (FD)
# Эффективный способ выявления утечек сокетов или файлов
ls -d /proc/[0-9]* | xargs -I{} sh -c 'echo "$(ls {}/fd 2>/dev/null | wc -l) $(cat {}/comm 2>/dev/null)"' | sort -rn | head -5

# Чтение аргументов запуска с очисткой от нулевых байтов
cat /proc/<PID>/cmdline | tr '\0' ' ' && echo
```

## Дополнительная информация

### Выбор инструментария: pidof vs pgrep

- **`pidof`**: Используйте в скриптах автоматизации, когда точно известно имя бинарного файла. Работает быстрее, возвращает только список PID.
- **`pgrep`**: Используйте для гибкого поиска по регулярным выражениям, пользователям или всей командной строке (флаг `-f`).

### Безопасность и влияние на производительность

1.  **Риски strace:** Использование `strace` на критическом процессе может замедлить его выполнение в десятки раз. Для продакшена используйте **ebpf** (`bpftrace`) или `perf`.
2.  **Атомарность /proc:** Чтение данных из `/proc` не является атомарной операцией. Процесс может завершиться или изменить состояние между открытием файла и его чтением.
3.  **Права доступа:** Глубокая диагностика (`stack`, `fd/`, `smaps`) требует прав владельца процесса или `root`.
