# Межпроцессное взаимодействие (IPC) в Linux

## Определения

**Межпроцессное взаимодействие (IPC — Inter-Process Communication)** — это набор механизмов и протоколов, которые позволяют независимым процессам обмениваться данными, уведомлениями и синхронизировать свою совместную работу в рамках одной операционной системы. 

> **Примечание:** В контексте анализа производительности процессоров аббревиатура **IPC** также может означать **Instructions Per Cycle** (количество инструкций за такт). Подробнее об этой метрике см. в [**Диагностика производительности с perf**](../../Diagnostics/Performance/perf.md).

В Linux IPC делится на три основные категории:
1. **Обмен данными:** Передача байтовых потоков или дискретных сообщений.
2. **Разделение ресурсов:** Совместное использование областей памяти.
3. **Синхронизация:** Координация доступа к общим ресурсам для предотвращения состояний гонки.

## Основные концепции

### Механизмы взаимодействия

#### Каналы (Pipes)

Классический механизм потоковой передачи данных, основанный на модели «производитель — потребитель».

- **Неименованные каналы (Anonymous Pipes):**
  - Полудуплексный режим (передача данных в одном направлении).
  - Используются для связи между родительским и дочерним процессами через системный вызов `pipe()`.
  - В командной оболочке создаются с помощью оператора конвейера `|`.
  
  ```bash
  # Пример конвейера в shell
  ls -la | grep ".txt" | wc -l
  ```

- **Именованные каналы (FIFO — First In, First Out):**
  - Обеспечивают связь между любыми процессами, даже не связанными родством.
  - Представлены как специальные файлы в файловой системе (тип `p`).
  - Поддерживают двустороннюю связь при использовании пары каналов.
  
  ```bash
  # Создание FIFO
  mkfifo /tmp/my_fifo
  
  # Запись данных
  echo "Hello" > /tmp/my_fifo
  
  # Чтение данных (в другом терминале)
  cat < /tmp/my_fifo
  ```

#### Очереди сообщений (Message Queues)

Асинхронный обмен дискретными сообщениями (пакетами).

- Ядро управляет очередями, позволяя процессам отправлять сообщения с разными приоритетами.
- Сообщение удаляется из очереди сразу после прочтения.
- Поддерживает работу нескольких отправителей и получателей одновременно.
- **POSIX Message Queues** (`mq_open`) предоставляют более современный интерфейс через виртуальную ФС (`/dev/mqueue`).

```c
// Пример использования System V IPC на языке C
int msgid = msgget(key, IPC_CREAT | 0666);
msgsnd(msgid, &msg, size, 0);  // Отправить
msgrcv(msgid, &msg, size, type, 0);  // Получить
```

#### Разделяемая память (Shared Memory)

Наиболее производительный метод обмена данными, исключающий копирование между ядром и пользовательским пространством.

- Ядро выделяет область физической памяти, которая проецируется в адресное пространство нескольких процессов.
- **memfd_create:** Современный системный вызов для создания анонимных файлов в памяти (`tmpfs`). В сочетании с `F_ADD_SEALS` (sealing) позволяет создавать области памяти, защищенные от модификации или изменения размера после инициализации.
- **mmap:** Отображение файла или устройства в память. Для IPC между неродственными процессами используется `mmap` с флагами `MAP_SHARED | MAP_ANONYMOUS` или отображение обычного файла/`tmpfs`.
- **Синхронизация:** Обязательно требует использования внешних механизмов (семафоров, мьютексов или футексов) для предотвращения состояния гонки (race conditions).

```c
// Разделяемая память через mmap
int fd = shm_open("/my_shm", O_CREAT | O_RDWR, 0666);
ftruncate(fd, SIZE);
void *ptr = mmap(NULL, SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
```

#### Семафоры (Semaphores) и Футексы (Futexes)

Механизмы синхронизации доступа к общим ресурсам.

- **Семафор:** Целочисленный счетчик, контролируемый ядром. Блокирует процесс, если ресурс занят.
- **Футекс (Fast Userspace Mutex):** Низкоуровневый примитив, на котором базируются высокоуровневые мьютексы (`pthreads`). Основная часть операций выполняется в пространстве пользователя без переключения в режим ядра, что значительно быстрее традиционных семафоров. Подробнее о механизме см. [**Конкурентность процессов**](./concurrency.md).

#### Сокеты (Sockets)

Универсальный механизм для локальной и сетевой коммуникации.

- **Unix Domain Sockets (AF_UNIX):** Оптимизированы для локального взаимодействия.
  - **Путевые сокеты:** Используют путь в ФС (например, `/var/run/docker.sock`). Требуют очистки файла после закрытия.
  - **Абстрактные сокеты:** Не привязаны к файловой системе (имя начинается с нуль-байта `\0`), автоматически удаляются при закрытии всех дескрипторов.
  - **Передача дескрипторов (SCM_RIGHTS):** Уникальная возможность AF_UNIX — передача открытого файлового дескриптора от одного процесса другому.
  - Подробнее см. [**Интерфейс сокетов (Socket API)**](../../../Networking/Concepts/socket_api.md).
- **Network Sockets (AF_INET/AF_INET6):** Используются для связи по сети (TCP/UDP).

#### Сигнальные и событийные дескрипторы (eventfd, signalfd)

Современные Linux-специфичные механизмы, позволяющие интегрировать IPC в циклы обработки событий (`epoll`, `select`, `io_uring`).

- **eventfd:** Легковесный механизм уведомлений через файловый дескриптор (счетчик 64-бит). Часто используется в виртуализации (KVM/QEMU) и как простой механизм пробуждения потоков.
- **signalfd:** Позволяет читать сигналы через файловый дескриптор, избегая сложностей с асинхронными обработчиками сигналов.

#### Файловые блокировки (File Locking)

Механизм координации доступа к общим файлам между процессами.

- **flock:** Блокировка на уровне всего файла. Advisory-блокировка, автоматически снимается при закрытии дескриптора.
- **fcntl (POSIX lock):** Блокировка на уровне диапазонов байтов. Более гранулярная, поддерживает раздельные блокировки на чтение (`F_RDLCK`) и запись (`F_WRLCK`).
- **Mandatory Locking:** Принудительный режим (считается устаревшим), при котором ядро блокирует доступ независимо от логики процессов.
- Подробнее о различиях и практическом использовании см. [**Конкурентность процессов**](./concurrency.md) и [**Диагностика утечек файловых дескрипторов**](../../Diagnostics/Troubleshooting/troubleshooting_file_descriptor_leaks.md).

#### Файлы (Files) и отображение в память (mmap)

- **Обычные файлы:** Простой способ обмена данными через диск или `tmpfs`. Требует блокировок (`flock`, `fcntl`).
- **mmap:** Отображение файла или устройства в память, что позволяет работать с данными напрямую. Используется для разделяемой памяти на базе файлов.

```bash
# Инспекция разделяемой памяти через /dev/shm
ls -la /dev/shm
du -sh /dev/shm/*
```

#### Сигналы (Signals)

Программные прерывания для асинхронных уведомлений.

- Используются для передачи простых событий (остановка, перезагрузка конфигурации).
- Подробное описание см. в заметке [**Сигналы процессов**](./signals.md).

#### Binder (Android IPC)

Специализированный механизм IPC, разработанный для Android, но доступный в mainline ядре Linux.

- Основан на драйвере символьного устройства (`/dev/binder`).
- Обеспечивает высокопроизводительный RPC (Remote Procedure Call) с управлением временем жизни объектов и идентификацией отправителя на уровне ядра.
- В обычном серверном Linux практически не используется, заменяясь D-Bus или gRPC.

### Сравнение механизмов IPC

| Механизм | Скорость | Сложность | Дуплекс | Синхронизация | Область применения |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Каналы (Pipes)** | Средняя | Низкая | Полудуплекс | Автоматическая | Shell-конвейеры, родитель-потомок |
| **Очереди сообщений** | Средняя | Средняя | Полный | Автоматическая | Асинхронные задачи, приоритеты |
| **Разделяемая память** | **Максимальная** | Высокая | Полный | **Требуется ручная** | Большие объемы данных, видео |
| **Unix Sockets** | Высокая | Средняя | Полный | Автоматическая | Локальные API, передача дескрипторов |
| **eventfd** | Высокая | Низкая | Полудуплекс | Автоматическая | Уведомления в асинхронных циклах |
| **Сигналы** | Высокая | Низкая | Нет данных | Нет | Управление жизненным циклом |

## Практические сценарии

### Использование Unix Domain Sockets (Docker API)

Классический пример локального взаимодействия через сокет `/var/run/docker.sock`.

```bash
# Прямой вызов Docker API через Unix-сокет
curl --unix-socket /var/run/docker.sock http://localhost/containers/json

# Проверка типа файла сокета
ls -l /var/run/docker.sock
# → s-rw-rw---- 1 root docker 0 ... /var/run/docker.sock (префикс 's' означает socket)
```

### Работа с разделяемой памятью и /dev/shm

В контейнерных средах разделяемая память часто становится узким местом.

`/dev/shm` — это каталог, который внутри Linux реализован как `tmpfs` (временная файловая система в оперативной памяти). Он используется для POSIX shared memory (`shm_open`), отображения файлов в память (`mmap`) и других механизмов IPC между процессами.

В контейнере ситуация отличается от хоста: `/dev/shm` выглядит как обычный каталог, но внутри Linux это отдельный mount point типа `tmpfs`, который создаётся в собственном mount namespace контейнера. Контейнер получает не просто каталог `/dev/shm` хоста, а собственный экземпляр `tmpfs`.

```bash
# Проверка текущего размера /dev/shm (в контейнере по умолчанию 64MB)
df -h /dev/shm

# Проверка типа файловой системы
mount | grep shm
# → tmpfs on /dev/shm type tmpfs ... size=64m

# Временное увеличение размера tmpfs для /dev/shm
sudo mount -o remount,size=2G /dev/shm

# Постоянная настройка через /etc/fstab
tmpfs /dev/shm tmpfs defaults,size=2G 0 0

# Просмотр содержимого разделяемой памяти
ls -la /dev/shm/
```

Поэтому приложения, активно использующие shared memory (PostgreSQL, Chromium, Python multiprocessing, различные IPC-механизмы), могут падать с ошибками, не похожими на нехватку дискового пространства:

```bash
# Пример: запись в /dev/shm в контейнере с лимитом 64MB
dd if=/dev/zero of=/dev/shm/test bs=1M count=100
# → No space left on device

# При этом корневая файловая система может иметь десятки гигабайт свободного места
df -h /
```

Размер можно увеличить при запуске контейнера:

```bash
# Docker run
docker run --shm-size=1g ...

# Docker Compose
services:
  app:
    shm_size: '1gb'
```

При этом важно не путать размер `tmpfs` `/dev/shm` с обычным memory limit контейнера. `tmpfs` использует RAM (и может взаимодействовать с swap), поэтому большой `--shm-size` не означает, что контейнер автоматически получил столько физической памяти. Существует два независимых ограничения:

- `/dev/shm size` — сколько shared-memory filesystem может содержать
- cgroup memory limit — сколько памяти контейнер в целом может использовать

Поэтому контейнер может иметь `--shm-size=2g`, но при `memory.max=512m` всё равно упереться в общий memory limit раньше.

### Использование eventfd для уведомлений

```c
#include <sys/eventfd.h>
#include <unistd.h>
#include <stdint.h>

int efd = eventfd(0, EFD_SEMAPHORE | EFD_NONBLOCK);
uint64_t u;
read(efd, &u, sizeof(uint64_t));  // Блокируется до сигнала
write(efd, &u, sizeof(uint64_t)); // Пробуждает читателя
```

### Конвейеры и FIFO

```bash
# Неименованный канал
dmesg | grep -i error

# Именованный канал (FIFO)
mkfifo /tmp/log_pipe
cat < /tmp/log_pipe &
echo "Message" > /tmp/log_pipe
```

### Передача дескрипторов через Unix Domain Sockets (SCM_RIGHTS)

```c
// Отправка дескриптора файла через Unix-сокет
struct msghdr msg = {0};
struct iovec iov = {.iov_base = "X", .iov_len = 1};
msghdr.msg_iov = &iov;
msghdr.msg_iovlen = 1;
char cmsgbuf[CMSG_SPACE(sizeof(int))];
msghdr.msg_control = cmsgbuf;
msghdr.msg_controllen = sizeof(cmsgbuf);
struct cmsghdr *cmsg = CMSG_FIRSTHDR(&msghdr);
cmsg->cmsg_level = SOL_SOCKET;
cmsg->cmsg_type = SCM_RIGHTS;
cmsg->cmsg_len = CMSG_LEN(sizeof(int));
memcpy(CMSG_DATA(cmsg), &fd, sizeof(int));
sendmsg(sock, &msghdr, 0);
```

## Диагностика и отладка

Для анализа IPC взаимодействий используются следующие инструменты:

1. **strace:** Отслеживание системных вызовов IPC (`shmget`, `msgsnd`, `sendmsg`).
   ```bash
   strace -e trace=ipc,network ./my_app
   ```
2. **lsof:** Список открытых файлов, включая каналы и Unix-сокеты.
   ```bash
   lsof -U  # Список всех Unix сокетов
   lsof | grep FIFO
   ```
3. **ss (Socket Statistics):** Детальная информация о сокетах.
   ```bash
   ss -xl  # Список прослушиваемых Unix сокетов
   ```
4. **ipcs / lsipc:** Просмотр ресурсов System V IPC.
   ```bash
   ipcs -a        # Все ресурсы
   ipcs -m        # Только разделяемая память
   ipcs -q        # Только очереди
   ```
5. **lslocks:** Просмотр активных файловых блокировок (`flock`, `fcntl`).
   ```bash
   lslocks
   # → COMMAND  PID  TYPE  SIZE MODE  M  START  END PATH
   # → dockerd  950  FLOCK  32K WRITE 0      0    0 /var/lib/docker/...
   ```
6. **lsipc:** Альтернатива `ipcs` с расширенным форматированием (part of `util-linux`).
7. **busctl:** Инструмент для отладки D-Bus (systemd).
   ```bash
   busctl list
   busctl status org.freedesktop.NetworkManager
   ```
8. **/proc интерфейсы:**
   ```bash
   # Просмотр POSIX-разделяемой памяти
   ls -la /dev/shm/
   
   # Просмотр POSIX очередей сообщений
   ls -la /dev/mqueue/
   
   # Просмотр System V IPC через proc
   ls -la /proc/sysvipc/
   ```

### Безопасность IPC

#### Безопасность Unix Domain Sockets

- **Права доступа:** Путевые сокеты наследуют стандартные права ФС. Для критичных сокетов (например, `/var/run/docker.sock`) используйте групповые ACL или TCP-сокет с TLS.
- **Пользовательские группы:** Доступ к Docker-сокету через группу `docker` (`usermod -aG docker <user>`).
- **Абстрактные сокеты:** Не привязаны к ФС, исключают атаки через race condition на создание файла. Используются для внутренней коммуникации systemd.

#### Безопасность разделяемой памяти

- **Права доступа:** Сегменты System V IPC и файлы в `/dev/shm` должны иметь минимально необходимные права (`0600` для пользовательских сегментов).
- **Очистка:** При завершении процесса сегменты SysV IPC не удаляются автоматически. Используйте `ipcrm` или настройте `kernel.msgmnb`, `kernel.shmmax` для ограничения ресурсов.
- **Swap:** Для защиты чувствительных данных используйте `mlockall(MCL_CURRENT | MCL_FUTURE)` с capability `CAP_IPC_LOCK`. Подробнее см. [**Установка Vault**](../../../Vault/guides/vault_installation.md).

## Типовые проблемы и устранение неполадок

### 1. Недостаток /dev/shm в контейнере

**Симптомы:** Падение PostgreSQL, Chromium, или Java-приложений с ошибкой «Cannot allocate memory» или «No space left on device».

**Причина:** В контейнере `/dev/shm` смонтирован как отдельный `tmpfs` (по умолчанию 64 MB), а не как каталог на общей файловой системе. Это независимый лимит, не связанный с `df -h /` или cgroup memory limit. Приложения, ожидающие `/dev/shm` ≥ 1 GB, падают, хотя общий лимит памяти контейнера может быть configured correctly.

**Решение:**
```bash
# Docker Compose: увеличить shared memory
services:
  app:
    shm_size: '1gb'

# Docker run:
docker run --shm-size=1g myapp

# Kubernetes: использовать emptyDir с medium: Memory
volumes:
  - name: dshm
    emptyDir:
      medium: Memory
      sizeLimit: 1Gi
volumeMounts:
  - name: dshm
    mountPath: /dev/shm
```

**Важно:** `--shm-size` и cgroup memory limit — это два независимых ограничения. Контейнер может иметь `--shm-size=2g`, но при `memory.max=512m` упереться в общий memory limit раньше. Настройте оба параметра при работе с memory-intensive приложениями.

### 2. Зависшие объекты System V IPC после аварийного завершения

**Симптомы:** Накопление неиспользуемых сегментов памяти, ошибка «No space left on device» при создании новых сегментов.

**Диагностика и решение:**
```bash
# Просмотр всех ресурсов
ipcs -a

# Удаление конкретного сегмента
ipcrm -m <shmid>    # Shared Memory
ipcrm -q <msgid>    # Message Queue
ipcrm -s <semid>    # Semaphore

# Пакетная очистка (осторожно!)
for seg in $(ipcs -m | awk 'NR>3 {print $2}'); do ipcrm -m $seg; done
```

### 3. Блокировка файлов мешает работе сервисов

**Симптомы:** Скрипт не запускается, «уже запущено»; `lslocks` показывает зависшую блокировку.

**Решение:**
```bash
# Поиск блокировок
lslocks
sudo lsof /var/lib/dpkg/lock-frontend

# Принудительное снятие (только если процесс неработоспособен)
fuser -k /var/lib/dpkg/lock-frontend
```

### 4. D-Bus: сервис не отвечает

**Симптомы:** `systemctl status` показывает активный сервис, но клиент не получает ответ по D-Bus.

**Диагностика:**
```bash
# Проверка активности на шине
busctl list | grep <сервис>

# Просмотр ошибок в journalctl
journalctl -u dbus -u <сервис> --since "10 minutes ago"

# Тестовый вызов метода
busctl call <сервис> /путь/к/объекту интерфейс.Метод тип_аргументов аргументы
```

### 5. Утечка дескрипторов Unix Domain Sockets

**Симптомы:** Рост количества открытых сокетов, `lsof | wc -l` увеличивается.

**Диагностика:**
```bash
# Поиск процессов с большим количеством Unix-сокетов
lsof -U | awk '{print $2}' | sort | uniq -c | sort -rn | head

# Проверка состояния сокетов
ss -xp | grep <PID>
```

## Дополнительная информация

### Шина сообщений D-Bus

**D-Bus** — высокоуровневая система IPC, стандарт для Linux Desktop и системных сервисов (systemd).

- **sd-bus:** Современная C-библиотека (часть systemd) для работы с D-Bus, значительно более эффективная, чем старая `libdbus`.
- **Интроспекция:** `busctl` позволяет просматривать доступные сервисы и вызывать методы в реальном времени.
- **Активные соединения:** `busctl` показывает PID процесса, открывшего соединение, что упрощает отладку.

### POSIX IPC vs System V IPC

| Характеристика | System V (Legacy) | POSIX (Modern) |
| :--- | :--- | :--- |
| **Интерфейс** | `shmget`, `msgget`, `semget` | `shm_open`, `mq_open`, `sem_open` |
| **Идентификация** | Числовые ключи (`ftok`) | Имена путей (начинаются с `/`) |
| **Видимость** | Команда `ipcs` | Файлы в `/dev/shm`, `/dev/mqueue` |
| **Удаление** | Явное (`ipcrm`) или при перезагрузке | Ссылка в ФС удаляется через `*_unlink` |

**Рекомендация:** В новом коде предпочитайте POSIX IPC из-за простоты управления жизненным циклом и совместимости с файловыми правами.

### Изоляция IPC через Namespaces

Механизмы IPC (кроме Unix-сокетов на базе файлов и обычных файлов) изолируются через **IPC Namespaces**. Это гарантирует, что контейнеры не могут получить доступ к разделяемой памяти или очередям хоста или других контейнеров.

- **Важно:** В ядрах до 5.10 очереди сообщений POSIX (`mq_open`) не изолируются через IPC namespace.
- **Практика:** Docker и Kubernetes автоматически создают отдельный IPC namespace для каждого контейнера. Для общего доступа используйте флаг `--ipc=shareable` или `--ipc=container:<имя>`.

Подробнее см. [**Namespaces (Пространства имён)**](../namespaces.md).

### Лимиты ядра для IPC

Настройки IPC регулируются через `sysctl`:
- `kernel.shmmax` — максимальный размер сегмента разделяемой памяти.
- `kernel.shmall` — общее количество страниц разделяемой памяти в системе.
- `kernel.msgmax` — максимальный размер сообщения в очереди.
- `kernel.msgmnb` — максимальный размер очереди сообщений.

```bash
# Просмотр текущих лимитов
sysctl -a | grep kernel.shm
sysctl -a | grep kernel.msg

# Временная настройка (до перезагрузки)
sudo sysctl -w kernel.shmmax=268435456
sudo sysctl -w kernel.shmall=65536

# Постоянная настройка в /etc/sysctl.conf
kernel.shmmax = 268435456
kernel.shmall = 65536
```

### Выбор механизма взаимодействия

1. **Максимальная скорость:** Разделяемая память + футексы.
2. **Передача сложных структур/дескрипторов:** Unix Domain Sockets.
3. **Shell-скриптинг:** Каналы и FIFO.
4. **Асинхронные уведомления:** `eventfd` или Сигналы.
5. **Системная интеграция и RPC:** D-Bus (через `sd-bus`) или gRPC.
6. **Простая координация скриптов:** Файловые блокировки (`flock`). Подробнее: [**Конкурентность процессов**](./concurrency.md).
