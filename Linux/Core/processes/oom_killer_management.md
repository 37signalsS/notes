# Управление механизмом OOM Killer в Linux

## Определения

**Управление OOM Killer (Out-of-Memory Killer)** — это процесс настройки поведения ядра Linux при критической нехватке памяти через корректировку рейтинга процессов (`oom_score_adj`), политики системного менеджера **systemd** (`OOMScoreAdjust`, `OOMPolicy`) и параметры контейнеризации (**Docker**, **Kubernetes**).

Цель управления заключается в защите критически важных компонентов системы и обеспечении предсказуемого поведения приложений при исчерпании ресурсов оперативной памяти (**RAM — Random Access Memory**) и пространства подкачки (**Swap**).

## Основные концепции

### Механизмы управления

Для влияния на алгоритм выбора "жертвы" механизмом OOM Killer используются следующие инструменты:

| Механизм | Область применения | Диапазон / Значения |
| :--- | :--- | :--- |
| **`oom_score_adj`** | Отдельный процесс (через **procfs**) | `-1000` (макс. защита) … `1000` (макс. риск) |
| **systemd `OOMScoreAdjust`** | Сервис systemd (unit-файл) | Аналогично `oom_score_adj` |
| **systemd `OOMPolicy`** | Сервис systemd (unit-файл) | `continue`, `stop`, `restart` |
| **Docker `--oom-score-adj`** | Контейнер Docker | `-1000` … `1000` |
| **Docker `--oom-kill-disable`** | Контейнер Docker | Полное отключение OOM для контейнера |
| **cgroups `memory.oom.group`** | Группа процессов (**cgroups v2**) | `0` (индивидуально) или `1` (групповое завершение) |

### Значения параметра oom_score_adj

| Значение | Эффект | Рекомендуемые сценарии |
| :--- | :--- | :--- |
| **-1000** | Максимальная защита | Критичные службы: **SSH (Secure Shell)**, **systemd**, **dbus**. |
| **-500 … -1** | Повышенная защита | Базы данных (**PostgreSQL**, **MySQL**), системы мониторинга. |
| **0** | По умолчанию | Большинство стандартных пользовательских процессов. |
| **1 … 999** | Повышенный риск | Вспомогательные задачи, тестовые скрипты. |
| **1000** | Гарантированная жертва | Процессы, которые должны быть убиты первыми при нехватке памяти. |

> **Важно:** Даже значение `-1000` не дает абсолютной гарантии выживания. При экстремальном дефиците памяти ядро может быть вынуждено завершить даже защищенный процесс.

### Политика OOMPolicy в systemd

Начиная с версии 243, systemd поддерживает настройку `OOMPolicy`:

- **`continue`**: systemd игнорирует завершение процесса механизмом OOM Killer и оставляет юнит в работающем состоянии (если выжили другие процессы в группе).
- **`stop`**: При срабатывании OOM Killer для любого процесса в юните, systemd принудительно останавливает весь сервис.
- **`restart`**: systemd автоматически перезапускает сервис после его завершения по причине OOM (при условии настройки параметров `Restart=`).

## Практические сценарии

### Настройка для отдельного процесса

```bash
# Получить текущий PID (Process Identifier) процесса
PID=$(pgrep -f my_app)

# Установить максимальную защиту (требуются права root)
echo -1000 | sudo tee /proc/$PID/oom_score_adj

# Проверить итоговый рейтинг (oom_score) и корректировку
cat /proc/$PID/oom_score
cat /proc/$PID/oom_score_adj
```

### Настройка для сервиса systemd

```ini
# /etc/systemd/system/important-service.service
[Service]
# Повысить приоритет выживания
OOMScoreAdjust=-500
# Автоматически перезапускать после убийства ядром
OOMPolicy=restart
Restart=on-failure
RestartSec=5s
```

Применение изменений:

```bash
sudo systemctl daemon-reload && sudo systemctl restart important-service
```

### Настройка для контейнеров Docker

```bash
# Запуск контейнера с защитой от OOM
docker run --oom-score-adj=-500 --name my_db redis

# Полное отключение OOM Killer для контейнера
# ВНИМАНИЕ: Требует лимита памяти (-m), иначе контейнер может "повесить" хост
docker run -m 1g --oom-kill-disable=true nginx
```

### Групповое завершение в cgroups v2

Для приложений, состоящих из множества связанных процессов, целесообразно убивать всю группу целиком, чтобы избежать нарушения целостности данных:

```bash
# Включить групповое завершение для конкретной cgroup
echo 1 | sudo tee /sys/fs/cgroup/system.slice/my_app.service/memory.oom.group
```

## Дополнительная информация

### Безопасность и риски

1. **Использование `--oom-kill-disable`**: Крайне опасная настройка. Если процесс в таком контейнере начнет бесконтрольно потреблять память, ядро не сможет его остановить, что приведет к деградации производительности всей системы или полной остановке хоста.
2. **Ложные ожидания**: Защита процесса через `oom_score_adj` не заменяет правильную настройку лимитов и мониторинг.
3. **Мониторинг**: Всегда настраивайте уведомления о срабатывании OOM Killer. Подробности см. в [**Диагностике OOM Killer**](./oom_killer_diagnostics.md).

### Автоматизация управления OOM Score

Пример скрипта для массовой настройки приоритетов:

```bash
#!/bin/bash
# Скрипт для установки oom_score_adj по шаблону имени
SET_SCORE=-500
PATTERN="nginx"

for pid in $(pgrep -f "$PATTERN"); do
    echo "Применение oom_score_adj=$SET_SCORE для $PATTERN (PID: $pid)"
    echo $SET_SCORE | sudo tee /proc/$pid/oom_score_adj > /dev/null
done
```

### Рекомендации по выбору стратегии

| Тип нагрузки | Рекомендуемое значение | Причина |
| :--- | :--- | :--- |
| **СУБД (Базы данных)** | `-800 … -500` | Критичность целостности данных. |
| **Web-серверы** | `-400 … -200` | Высокие требования к доступности сервиса. |
| **Очереди сообщений** | `-500 … -300` | Предотвращение потери транзитных данных. |
| **Фоновые воркеры** | `0 … 300` | Можно безопасно перезапустить. |
| **CI/CD агенты** | `500 … 1000` | Временные задачи, которыми можно пожертвовать. |
