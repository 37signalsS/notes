# Управление механизмом OOM Killer в Linux

## Определения

**Управление OOM Killer (Out-of-Memory Killer)** — это совокупность методов и настроек, позволяющих регулировать поведение ядра Linux при критической нехватке памяти. Основная цель — защита системных служб и обеспечение предсказуемости системы путем приоритизации процессов для завершения.

**oom_score_adj** — интерфейс ядра для ручной корректировки вероятности завершения процесса. Значения варьируются от `-1000` (полная защита) до `+1000` (первая очередь на завершение).

**systemd-oomd** — современный пользовательский демон (введен в systemd 247), работающий на основе **PSI (Pressure Stall Information)**. Он убивает процессы превентивно, не дожидаясь критического зависания ядра.

## Основные концепции

### Иерархия механизмов управления

| Уровень | Инструментарий | Метод воздействия |
| :--- | :--- | :--- |
| **Процессный** | `oom_score_adj` | Прямая запись в `/proc/PID/oom_score_adj`. |
| **Системные службы** | systemd unit | Директивы `OOMScoreAdjust` и `OOMPolicy`. |
| **Пользовательский (User-space)** | `systemd-oomd` | Мониторинг PSI и управление через `oomctl`. |
| **Ядерный (Kernel)** | `sysctl` | Глобальные флаги (`panic_on_oom`, `oom_kill_allocating_task`). |
| **Контейнерный** | Docker / K8s | Флаги рантайма и классы QoS. |

### Параметры oom_score_adj

| Значение | Описание | Применение |
| :--- | :--- | :--- |
| **-1000** | Исключение из списка жертв | Только для `systemd`, `sshd`, `dbus`. |
| **-999 … -1** | Снижение риска | Базы данных, критичные бизнес-приложения. |
| **0** | По умолчанию | Большинство стандартных задач. |
| **1 … 1000** | Повышение риска | CI/CD агенты, вспомогательные скрипты, браузеры. |

### Управление через systemd-oomd

`systemd-oomd` оперирует на уровне контрольных групп (cgroups). Он анализирует файлы в `/proc/pressure/` и принимает решение о завершении всей группы, если давление на ресурсы превышает пороги.

**Преимущества:**
- Предотвращает состояние "Trashing" (бесконечный свопинг), когда система еще жива, но не отвечает.
- Позволяет настраивать лимиты на уровне пользователя или сервиса.

## Практические сценарии

### Настройка systemd-oomd для сервиса

Чтобы включить защиту или принудительное завершение через `systemd-oomd`, используйте следующие параметры в юнит-файле:

```ini
[Service]
# Индивидуальная настройка рейтинга
OOMScoreAdjust=-500

# Политика при срабатывании OOM:
# continue (только этот процесс), stop (весь юнит), restart (перезапуск)
OOMPolicy=restart

# Настройка порогов давления для oomd (ManagedOOM)
# kill — убивать при превышении, auto — наследовать системные правила
ManagedOOMSwap=kill
ManagedOOMMemoryPressure=kill
ManagedOOMMemoryPressureLimit=60%
```

### Глобальные настройки ядра (sysctl)

Для изменения глобального поведения OOM Killer:

```bash
# Убить процесс, запросивший память, вместо долгого поиска жертвы
sysctl -w vm.oom_kill_allocating_task=1

# Вызывать Kernel Panic вместо убийства (для кластеров с HA-переключением)
sysctl -w vm.panic_on_oom=1

# Детальный дамп всех задач в dmesg при OOM
sysctl -w vm.oom_dump_tasks=1
```

### Скрипт массовой защиты процессов

SRE-специалисты часто используют автоматизацию для защиты групп процессов:

```bash
#!/bin/bash
# Защита всех процессов PostgreSQL
for pid in $(pgrep -f "postgres"); do
    echo "Защита PostgreSQL PID: $pid"
    echo -800 > /proc/$pid/oom_score_adj
done
```

### Управление через oomctl

Утилита для мониторинга состояния демона `systemd-oomd`:

```bash
# Просмотр статуса мониторинга cgroups
oomctl dump

# Вывод:
# Dry Run: no
# Swap Used Limit: 90.00%
# Default Memory Pressure Limit: 60.00%
# Default Memory Pressure Duration: 20s
```

## Дополнительная информация

### Безопасность и риски

1.  **Риски `-1000`**: Установка этого значения для тяжелых приложений (например, Java Heap) может привести к тому, что ядро убьет все вспомогательные процессы ОС (включая SSH), но не тронет "виновника", сделав хост недоступным.
2.  **Swap и zRAM**: Настройка `zram` позволяет избежать OOM за счет сжатия памяти, что эффективнее, чем агрессивное управление OOM Killer.
3.  **Контейнеры**: Помните, что в Kubernetes `oom_score_adj` выставляется автоматически на основе QoS-классов. Ручное изменение этого параметра внутри пода обычно игнорируется или сбрасывается.
