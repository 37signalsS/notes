# Процессы в Linux: Определения

## Определения

### Пространство пользователя (Userspace) и пространство ядра (Kernelspace)

Операционная система Linux разделяет работу на два фундаментальных режима выполнения кода: **Userspace (пространство пользователя)** и **Kernelspace (пространство ядра)**. Это разделение базируется на аппаратных уровнях защиты процессора (Rings) и критически важно для обеспечения стабильности системы.

| Характеристика | Userspace (Пространство пользователя) | Kernelspace (Пространство ядра) |
| :--- | :--- | :--- |
| **Что выполняется?** | Прикладные программы, оболочки, библиотеки | Ядро ОС, драйверы, системные модули |
| **Уровень привилегий** | Низкий (Ring 3). Процессы изолированы | Максимальный (Ring 0). Полный доступ |
| **Доступ к железу** | Опосредованно через системные вызовы | Прямой и неограниченный |
| **Память** | Изолированное виртуальное пространство | Единое адресное пространство ядра |
| **Переключение** | Требует Trap/Exception для смены режима | Работает в привилегированном режиме |
| **Отказоустойчивость** | Сбой завершает только конкретный процесс | Ошибка ведет к Kernel Panic |

### Процесс и задача (Task)

**Процесс** — это экземпляр выполняемой программы, обладающий собственными ресурсами и контекстом безопасности. В ядре Linux нет жесткого разделения между процессами и потоками; обе сущности представлены структурой `task_struct` и называются **задачами (tasks)**.

Ключевые составляющие процесса:
- **Адресное пространство:** Личная виртуальная память процесса. Включает программный код (text), сегмент данных (data), кучу (heap) и стек вызовов (stack).
- **Контекст процесса:** Набор данных, необходимых ядру для управления процессом (состояние регистров, открытые файлы, переменные окружения).

### Поток (Thread) и легковесный процесс (LWP)

**Поток** — это отдельная линия выполнения в рамках процесса. В Linux потоки часто называют **легковесными процессами (LWP — Lightweight Processes)**.
- Все потоки одного процесса разделяют общее адресное пространство и системные ресурсы, но имеют собственные регистры процессора и стек.
- В Linux потоки реализуются через системный вызов `clone` с флагами, указывающими на разделение ресурсов (например, `CLONE_VM` для разделения памяти).
- Технически, с точки зрения ядра, поток — это задача (`task_struct`), у которой идентификатор группы потоков (**TGID**) совпадает с **PID** основного потока (лидера группы).

### Переключение контекста (Context Switch)

**Переключение контекста** — процедура сохранения состояния (контекста) текущей задачи и восстановления состояния другой задачи для её выполнения на процессоре.
- Это "невидимая" работа планировщика, позволяющая множеству процессов работать параллельно на одном ядре CPU (псевдопараллелизм).
- Переключение между потоками одного процесса ("внутрипроцессное") происходит быстрее, чем между разными процессами, так как не требует смены таблиц страниц памяти (MMU context).

### Атрибуты процесса (Паспорт процесса)

Каждый процесс обладает набором атрибутов, необходимых для управления и безопасности:
- **PID (Process Identifier):** Уникальный числовой идентификатор.
- **PPID (Parent PID):** Идентификатор родительского процесса.
- **TGID (Thread Group ID):** Идентификатор группы потоков (для пользователя это обычно и есть PID).
- **UID / GID:** Идентификаторы владельца и группы (Real, Effective, Saved).
- **Capabilities:** Набор привилегий, заменяющий классическое "всё или ничего" для пользователя root.
- **pidfd (PID File Descriptor):** Файловый дескриптор, привязанный к конкретной инкарнации процесса. Исключает риск отправки сигнала не тому процессу, если PID был переиспользован ядром.

### Системные вызовы (System Calls)

**Системный вызов** — программный интерфейс для перехода из Userspace в Kernelspace для выполнения привилегированных операций (ввод-вывод, управление процессами).

Механизмы ускорения:
- **vDSO (virtual Dynamic Shared Object):** Виртуальная библиотека, отображаемая ядром в память процесса. Позволяет выполнять "дешевые" системные вызовы (например, `gettimeofday`, `clock_gettime`) полностью в пространстве пользователя без дорогостоящего переключения режима CPU.
- **vsyscall:** Устаревший механизм (использовал фиксированные адреса), заменен на vDSO из соображений безопасности (ASLR).

## Основные концепции

### Механизм переключения режимов

Когда приложению нужно выполнить системный вызов:
1.  **Подготовка:** Аргументы помещаются в регистры.
2.  **Запрос:** Выполняется инструкция `syscall` (x86_64).
3.  **Переход:** Процессор переключается в Ring 0, ядро сохраняет контекст пользователя и выполняет запрос.
4.  **Возврат:** Ядро возвращает результат и переключает процессор обратно в Ring 3.

#### Цена переключения режимов: практический пример

Накладные расходы на переходы Userspace ↔ Kernelspace (сохранение/восстановление контекста, копирование данных между адресными пространствами) незаметны на единичных вызовах, но становятся определяющими при обработке тысяч событий в секунду. Показательный кейс из практики небольших провайдеров: PPPoE-концентратор на слабом железе.

*   **Демон в userspace** — каждый пакет обрабатывается через серию syscalls: одна машина вытягивала порядка **50 пользователей**.
*   **Реализация в виде модуля ядра** — пакеты обрабатываются без выхода в userspace: то же железо обслуживало порядка **500 пользователей**.

Разница на порядок объясняется тем, что код в kernelspace не платит за каждую порцию работы цену syscall-перехода. Отсюда следуют два архитектурных правила: критичные к производительности подсистемы (сетевая обработка, драйверы, ФС) живут в ядре, а для обратной задачи — избавить частые «дешёвые» вызовы от перехода в Ring 0 — существует vDSO.

### Иерархия процессов (PGID и SID)

Ядро Linux организует задачи в многоуровневую структуру для управления заданиями и рассылки сигналов:

- **PID (Process ID):** Уникальный идентификатор задачи.
- **PPID (Parent PID):** Ссылка на родительский процесс.
- **TGID (Thread Group ID):** Идентификатор группы потоков. В userspace отображается как привычный PID.
- **PGID (Process Group ID):** Группирует процессы для управления заданиями (Job Control). Сигналы, отправленные группе, доставляются всем её членам (например, `SIGINT` всему конвейеру `cat | grep | less`).
- **SID (Session ID):** Группирует процессы в рамках одного входа пользователя (терминальной сессии). Лидер сессии — процесс, который создал её через `setsid()`.

**Практический пример:**

```bash
# Просмотр иерархии PID/PGID/SID
ps -eo pid,ppid,pgid,sid,comm

# Кто является лидером сессии для текущего терминала?
ps -o pid,pgid,sid,comm -p $$
```

### Copy-on-Write (CoW)

**Copy-on-Write** — механизм оптимизации, используемый при создании процессов через `fork()`. Вместо немедленного копирования всей памяти родителя ядро делает страницы памяти общими для чтения. Физическое копирование происходит только при попытке записи одним из процессов.

- **Преимущество:** `fork()` становится дешевой операцией даже для процессов с гигабайтами памяти.
- **Современные разработки:** В ядрах 6.x появился механизм `fork_connector` и расширения для более тонкого управления CoW в контейнерах.
- **Отключение CoW:** Для баз данных (PostgreSQL, MySQL) часто рекомендуется отключить CoW на уровне файловой системы (Btrfs `nodatacow`, XFS `nocow`) или использовать `mlock()`/`madvise(..., MADV_DONTFORK)` для критичных структур.

### Пространства имён (Namespaces)

**Namespace** — механизм изоляции ресурсов, позволяющий группе процессов иметь собственный «взгляд» на часть системы. В контексте процессов наиболее важны:

- **PID namespace:** Изолирует дерево процессов. Процесс внутри контейнера видит себя как PID 1, но на хосте имеет глобальный PID (например, 5678).
- **Mount namespace:** Изолирует точки монтирования файловых систем.
- **Network namespace:** Изолирует сетевой стек (интерфейсы, таблицы маршрутов, порты).
- **User namespace:** Изолирует UID/GID, позволяет мапить root внутри namespace в непривилегированного пользователя на хосте.

```bash
# Проверка namespace процесса
ls -la /proc/<PID>/ns/

# Вход в namespace процесса (например, для отладки)
nsenter -t <PID> -n -- ip address show
```

### Контрольные группы (cgroups)

**cgroups** — механизм ядра для ограничения, учёта и приоритизации потребления ресурсов группами процессов. В отличие от namespaces (изоляция видимости), cgroups ограничивают потребление.

- **cgroups v2 (Unified Hierarchy):** Современный стандарт, объединяющий все контроллеры в единую иерархию. Используется по умолчанию в Ubuntu 20.04+, RHEL 9+, Debian 11+.
- **Ключевые контроллеры:**
  - `cpu` / `cpuset` — ограничение и привязка к ядрам CPU.
  - `memory` — лимиты RAM, swap, pressure stall information (PSI).
  - `io` — ограничение операций ввода-вывода.
  - `pids` — ограничение количества процессов/потоков.

```bash
# Проверка cgroup для процесса
cat /proc/<PID>/cgroup

# Просмотр лимитов (cgroups v2)
cat /sys/fs/cgroup/system.slice/myapp.service/memory.max
cat /sys/fs/cgroup/system.slice/myapp.service/cpu.max
```

### Демонизация (Daemonization)

**Демон (Daemon)** — процесс, работающий в фоновом режиме без управляющего терминала. Классический процесс демонизации включает:

1. **Fork и выход родителя:** Родитель завершается, чтобы демон стал сиротой и был усыновлён PID 1.
2. **Создание новой сессии:** `setsid()` — демон становится лидером новой сессии и detached от терминала.
3. **Второй fork (опционально):** Гарантирует, что демон не является лидером сессии и не может accidentally захватить терминал.
4. **Смена рабочей директории:** Обычно на `/` или на специализированную директорию.
5. **Установка umask:** Обычно `0` для полного контроля над правами создаваемых файлов.
6. **Закрытие/перенаправление дескрипторов:** stdin, stdout, stderr перенаправляются в `/dev/null` или в лог-файлы.

```bash
# Пример демона на Python (упрощённо)
import os, sys, daemon

with daemon.DaemonContext(
    working_directory='/tmp',
    umask=0o022,
    stdout=open('/var/log/mydaemon.log', 'a+'),
    stderr=open('/var/log/mydaemon.err', 'a+'),
):
    do_work()
```

В современном Linux большинство демонов управляются через **systemd**, который берёт на себя многие аспекты демонизации (рабочая директория, права, перенаправление stdout/stderr в journald).

### Структура task_struct

Ядро хранит данные о каждой задаче в структуре `task_struct` (`include/linux/sched.h`). Основные поля:
- **`state`**: Текущее состояние (Running, Sleeping и др.).
- **`stack`**: Указатель на стек режима ядра.
- **`mm`**: Ссылка на дескриптор памяти процесса (таблицы страниц).
- **`pid`** и **`tgid`**: Идентификаторы.
- **`parent`**, **`children`**, **`sibling`**: Указатели на родственников в дереве процессов. На родителе лежит обязанность по сбору статуса завершения потомков (**reaping**) для предотвращения появления зомби.
- **`files`**: Таблица открытых файловых дескрипторов.
- **`signal`** и **`sighand`**: Обработка сигналов.

## Практические сценарии

### Анализ времени выполнения

Утилита `time` разделяет время работы программы:
- **user**: Время выполнения кода приложения в пространстве пользователя.
- **sys**: Время, проведенное ядром при обслуживании системных вызовов процесса.

```bash
time dd if=/dev/zero of=/dev/null count=1000000
# user    0m0.120s
# sys     0m0.450s  <-- Значительная часть времени ушла на syscalls (write/read)
```

### Идентификация потоков ядра

**Потоки ядра (Kernel Threads)** — служебные задачи, работающие только в Kernelspace.

Особенности отображения в `ps`:
- Название в квадратных скобках (например, `[kworker/0:1]`).
- Отсутствие адресного пространства пользователя (нет сегментов `text` или `stack` в Userspace).
- Не реагируют на сигналы Userspace (например, `kill -9`), так как никогда не переходят в режим пользователя для проверки очереди сигналов.

```bash
# Список потоков ядра, порожденных kthreadd (PID 2)
ps -efj | grep "\["
```

### Диагностика процессов

Базовый набор утилит для сбора информации о процессах в production-среде:

```bash
# Быстрый поиск PID по имени
pidof nginx
pgrep -a nginx
pgrep -af "nginx: worker"  # Поиск по полной командной строке

# Детальная информация о процессе
ps -p <PID> -o pid,ppid,user,%cpu,%mem,vsz,rss,stat,start,time,comm,args

# Иерархия дерева процессов
pstree -ap
pstree -p <PID>  # Дерево для конкретного процесса

# Поиск родителя и детей
ps -o ppid= -p <PID>
ps --ppid <PPID> -o pid,comm,stat
```

### Инспекция через /proc

Виртуальная файловая система `/proc` предоставляет доступ к внутренним структурам ядра. Ключевые файлы для диагностики:

```bash
# Общая информация
cat /proc/<PID>/status      # Имя, состояние, UID/GID, память, сигналы
cat /proc/<PID>/cmdline     # Командная строка (разделена нулевыми байтами)
cat /proc/<PID>/environ     # Переменные окружения (разделены нулевыми байтами)
cat /proc/<PID>/limits      # Лимиты ресурсов (ulimit)
cat /proc/<PID>/cgroup      # Контрольные группы

# Открытые файлы и сокеты
ls -la /proc/<PID>/fd/      # Файловые дескрипторы
cat /proc/<PID>/net/tcp     # TCP-соединения процесса
cat /proc/<PID>/net/udp     # UDP-сокеты

# Стек ядра (для анализа зависаний)
cat /proc/<PID>/stack

# Адресное пространство
cat /proc/<PID>/maps        # Регионы памяти (VMA)
cat /proc/<PID>/smaps       # Детальная информация по регионам
```

### Процессы в состоянии D (Uninterruptible Sleep)

Процессы в состоянии **D** (`TASK_UNINTERRUPTIBLE`) находятся внутри системного вызова в ядре и не реагируют на сигналы, включая `SIGKILL`. Обычно это ожидание завершения дискового I/O или операций со storage.

```bash
# Поиск процессов в D-state
ps aux | awk '$8 ~ /D/'
ps -eo pid,stat,comm,args | awk '$2 ~ /D/'

# Анализ стека (что именно ждет процесс)
cat /proc/<PID>/stack
# или
pstack <PID>

# Частые причины:
# - NFS-монтирование зависло
# - Проблемы с iSCSI/SAN
# - Блокировка на уровне блочного устройства
```

**Важно:** Единственные способы «освободить» D-state процесс:
1. Завершить операцию I/O (восстановить NFS/SAN).
2. Перезагрузить систему.

### Анализ зомби-процессов

**Зомби (Z)** — завершенный процесс, запись о котором remains в таблице процессов, так как родитель не вызвал `wait()`. Зомби не потребляют CPU/RAM, но занимают PID.

```bash
# Поиск всех зомби
ps aux | awk '$8 == "Z" {print $2, $11, $13}'

# Найти родителя зомби
ps -o ppid= -p <ZOMBIE_PID>

# Количество зомби в системе
ps -eo stat | grep -c Z

# Если родитель — PID 1 (systemd), обычно зомби подбираются автоматически
# Если нет — проверяем systemd
systemctl status systemd
```

### Управление приоритетами (nice, renice, ionice)

Linux позволяет влиять на приоритет процессов при планировании CPU и дискового I/O.

```bash
# Запуск процесса с пониженным приоритетом CPU (nice = 19 — минимальный)
nice -n 19 tar czf /backup/archive.tar.gz /data

# Изменение приоритета запущенного процесса
renice 10 -p <PID>    # Повысить приоритет (требует root для значений < 0)
renice -5 -p <PID>    # Ещё выше (только root)

# Приоритет дискового I/O (ionice)
ionice -c 2 -n 3 dd if=/dev/zero of=/tmp/test bs=1M count=1000
# -c 2 = best-effort (по умолчанию), -n 3 = lowest priority
# -c 3 = idle (только когда диск свободен)

# Проверка текущего nice-значения
ps -o pid,ni,comm -p <PID>
```

### Трассировка и отладка

```bash
# strace — системные вызовы процесса
strace -p <PID>                    # Все syscalls в реальном времени
strace -e trace=open,read,write -p <PID>  # Только указанные syscalls
strace -c -p <PID>                 # Статистика по syscalls (сколько времени занял каждый)
strace -f -p <PID>                 # Следить за дочерними процессами (-f = follow forks)

# ltrace — вызовы библиотечных функций
ltrace -p <PID>

# gdb — отладчик
gdb -p <PID>
(gdb) bt full       # Полный stack trace
(gdb) info threads  # Список потоков
(gdb) thread apply all bt  # Stack trace всех потоков

# pstack — краткий стек всех потоков (альтернатива gdb)
pstack <PID>

# lsof — открытые файлы и сокеты
lsof -p <PID>
lsof -i :80        # Кто держит порт 80
lsof +L1            # Удаленные файлы, которые всё ещё открыты процессом
```

### Ограничения процессов (ulimit / prlimit)

```bash
# Просмотр текущих лимитов
ulimit -a
cat /proc/<PID>/limits

# Ключевые лимиты:
# - nofile (open files): максимальное количество FD
# - nproc (max user processes): максимальное количество процессов
# - core (core file size): размер дампа памяти
# - memlock: объем памяти, который можно заблокировать (mlock)

# Изменение лимита для текущей сессии
ulimit -n 65535      # Максимум открытых файлов
ulimit -u 4096       # Максимум процессов

# Изменение лимита запущенного процесса (требует root)
prlimit --pid <PID> --nofile=65535:65535

# Постоянная настройка через systemd
# /etc/systemd/system/myapp.service.d/limits.conf
[Service]
LimitNOFILE=65535
LimitNPROC=4096
```

### Systemd-интеграция

В современных дистрибутивах systemd является PID 1 и основным управляющим процессом:

```bash
# Статус сервиса
systemctl status nginx

# Просмотр логов сервиса
journalctl -u nginx --since "10 minutes ago"
journalctl -u nginx -f  # Follow в реальном времени

# Показать дерево cgroups
systemd-cgtop
systemd-cgls

# Перезагрузка конфигурации (отправляет SIGHUP)
systemctl reload nginx

# Плавная остановка (SIGTERM → SIGKILL по таймауту)
systemctl stop nginx
```

### Контейнерная диагностика процессов

```bash
# PID процесса контейнера на хосте
PID=$(docker inspect --format '{{.State.Pid}}' <container>)

# Вход в namespace контейнера
nsenter -t $PID -n -- ip address show
nsenter -t $PID -m -- ls /app

# Выполнение команды внутри контейнера (аналог docker exec)
nsenter -t $PID -m -u -i -n -p -- /bin/bash

# Для Kubernetes: PID пода через crictl
crictl ps | grep <pod-name>
crictl inspect <container-id> | grep -i pid

# Поиск зомби в контейнере
docker exec <container> ps aux | grep -w Z
```

## Типовые проблемы и устранение неполадок

| Проблема | Симптомы | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Zombie-процессы** | `ps` показывает `Z`, исчерпание PID | `ps aux \| awk '$8=="Z"'`; найти PPID | Устранить проблему в родителе; завершить родителя; в контейнере — перезапустить под |
| **D-state процесс** | `kill -9` не работает, процесс висит | `ps aux \| awk '$8~/D/'`; `cat /proc/<PID>/stack` | Восстановить storage/NFS; перезагрузить систему |
| **Высокий cs (context switches)** | `vmstat 1` показывает высокий `cs` | `vmstat 1`; `pidstat -w 1` | CPU pinning; `taskset`; проверка `cpus_allowed` в `task_struct` |
| **Fork-бомба** | `fork: Cannot allocate memory`; `PIDPressure` | `ps -eo pid,ppid,stat,comm \| awk '$3~/R/' \| wc -l` | `kill -9 $(ps -o ppid= -p <initiator>)`; ограничение через `pids.max` в cgroup |
| **Ограничение файлов** | `Too many open files` | `cat /proc/<PID>/limits \| grep "open files"`; `lsof -p <PID> \| wc -l` | Увеличить `ulimit -n` или `LimitNOFILE` в systemd |
| **PID 1 игнорирует сигналы** | `docker stop` висит 10 секунд | `docker exec <c> ps -p 1 -o pid,comm,args`; `grep Sig /proc/1/status` | Использовать `tini` (`--init`); exec-form в Dockerfile; явный обработчик SIGTERM |

## Best Practices

1. **Никогда не используйте `kill -9` как первую меру.** Сначала отправляйте `SIGTERM`, дайте приложению время на graceful shutdown, затем `SIGKILL`.
2. **Мониторьте зомби-процессы.** Добавьте алерт на `ps -eo stat | grep -c Z > 0`. Зомби не потребляют RAM, но исчерпывают PID namespace.
3. **Используйте `pidfd` вместо PID в скриптах** (Linux 5.3+). Это исключает race condition при переиспользовании PID.
4. **Настраивайте `LimitNOFILE` и `LimitNPROC`** в systemd-юнитах для production-сервисов. Значения по умолчанию (1024/4096) часто недостаточны.
5. **Не запускайте приложения как PID 1 без инициализации.** Используйте `tini`, `dumb-init` или `s6-overlay` для корректной обработки сигналов и zombie reaping.
6. **Привязывайте критические процессы к CPU** (`cpuset`, `taskset`, `sched_setaffinity`) для минимизации jitter и context switch overhead.
7. **Используйте cgroups v2** для ограничения ресурсов. Проверяйте `cpu.stat` (`nr_throttled`) и `memory.high` для early detection проблем.

## Дополнительная информация

### Почему разделение критически важно

1.  **Безопасность:** Изоляция приложений друг от друга и от ядра.
2.  **Стабильность:** Сбой в прикладной программе не приводит к краху всей системы (Kernel Panic).
3.  **Управление ресурсами:** Ядро выступает арбитром при доступе к железу (CPU, RAM, диск).
