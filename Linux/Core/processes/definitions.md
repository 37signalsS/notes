# Процессы в Linux: Определения

## Определения

### Userspace и Kernelspace

Операционная система Linux разделяет работу на два фундаментальных режима выполнения кода: **Userspace (пространство пользователя)** и **Kernelspace (пространство ядра)**. Это разделение базируется на аппаратных уровнях защиты процессора (Rings) и критически важно для обеспечения стабильности системы.

| Характеристика | Userspace (Пространство пользователя) | Kernelspace (Пространство ядра) |
| :--- | :--- | :--- |
| **Что выполняется?** | Прикладные программы, оболочки, библиотеки | Ядро ОС, драйверы, системные модули |
| **Уровень привилегий** | Низкий (Ring 3). Процессы изолированы | Максимальный (Ring 0). Полный доступ |
| **Доступ к железу** | Опосредованно через системные вызовы | Прямой и неограниченный |
| **Память** | Изолированное виртуальное пространство | Единое адресное пространство ядра |
| **Переключение** | Требует Trap/Exception для смены режима | Работает в привилегированном режиме |
| **Отказоустойчивость** | Сбой завершает только конкретный процесс | Ошибка ведет к Kernel Panic |

### Процесс и задача (Task)

**Процесс** — это экземпляр выполняемой программы, обладающий собственными ресурсами и контекстом безопасности. В ядре Linux нет жесткого разделения между процессами и потоками; обе сущности представлены структурой `task_struct` и называются **задачами (tasks)**.

Ключевые составляющие процесса:
- **Адресное пространство:** Личная "квартира" процесса в оперативной памяти. Включает программный код, используемые библиотеки, переменные и стек вызовов.
- **Записи внутри ядра (Досье):** Ядро ведет детальный учет каждого процесса, включая выделенную память, текущее состояние, приоритет, открытые файлы и сетевые порты, маски сигналов и владельца.

### Поток (Thread)

**Поток** — это отдельная линия выполнения в рамках процесса. У процесса есть как минимум один поток, но их может быть много.
- Потоки позволяют современным программам (например, веб-серверам) обрабатывать тысячи запросов одновременно, распределяя их по разным ядрам процессора.
- В Linux потоки реализуются как задачи, разделяющие адресное пространство родителя (флаг `CLONE_VM` при вызове `clone`).
- Все потоки процесса разделяют PID (технически — TGID, Thread Group ID), файловые дескрипторы и обработчики сигналов, но имеют собственные стеки и регистры.

### Атрибуты процесса (Паспорт процесса)

Каждый процесс обладает набором атрибутов, которые системный администратор должен уметь анализировать:
- **PID (Process Identifier):** Уникальный числовой идентификатор. В современных системах один и тот же процесс может иметь разные PID: например, PID 1 внутри контейнера и PID 3000 на хост-машине (эффект "относительности" благодаря пространствам имён/namespaces).
- **PPID (Parent PID):** Номер родительского процесса.
- **UID / GID:** Идентификаторы владельца и группы. Различают реальный (кто запустил) и эффективный (чьи права действуют сейчас) идентификаторы.
- **Приоритет (Priority / Nice):** Определяет "уступчивость" процесса к соседям по процессору.
- **Управляющий терминал (TTY):** Окно терминала, через которое нажатия клавиш (например, Ctrl+C) долетают до процесса.
- **Таблица дескрипторов:** Ссылки на открытые файлы, сокеты и каналы.
- **pidfd (PID File Descriptor):** Современный механизм (Linux 5.3+) для безопасного обращения к процессу через файловый дескриптор, исключающий ошибки при переиспользовании PID.

### Системные вызовы (System Calls)

**Системный вызов** — единственный санкционированный способ перехода из Userspace в Kernelspace для выполнения привилегированных операций. 

Механизмы оптимизации:
- **vDSO (virtual Dynamic Shared Object):** Небольшая библиотека, экспортируемая ядром в адресное пространство процесса. Позволяет выполнять некоторые вызовы (например, `gettimeofday`) полностью в Userspace без переключения режима процессора.
- **vsyscall:** Устаревший предшественник vDSO, использовавший фиксированные адреса в памяти.

## Основные концепции

### Механизм переключения режимов

Когда приложению нужно прочитать файл или отправить сетевой пакет, происходит следующая последовательность:
1.  **Подготовка:** Аргументы вызова помещаются в регистры CPU.
2.  **Переход:** Выполняется инструкция `syscall` (x86_64) или программное прерывание.
3.  **Обработка:** Процессор переключается в Ring 0, ядро проверяет права доступа и выполняет код.
4.  **Возврат:** После завершения ядро выполняет `sysret`, возвращая управление в Userspace (Ring 3).

### Структура task_struct

Ядро хранит информацию о каждой задаче в массивной структуре `task_struct` (определена в `include/linux/sched.h`). Она содержит:
- **Состояние задачи:** Running, Sleeping, Zombie и др.
- **Информация о планировщике:** Приоритет, кванты времени.
- **MMU Info:** Ссылки на таблицы страниц памяти.
- **Сигналы:** Маски заблокированных и ожидающих сигналов.
- **Кредиты безопасности:** UID, GID, capabilities.

### Виртуализация и Ring -1

В современных системах с поддержкой аппаратной виртуализации (Intel VT-x, AMD-V) появляется дополнительный уровень — **Ring -1** (или VMX Root Mode). В нем работает гипервизор (KVM), который управляет выполнением нескольких "гостевых" ядер ОС.

## Практические сценарии

### Анализ времени в разных режимах

С помощью утилиты `time` можно увидеть, сколько времени процесс провел в каждом пространстве:

```bash
time find /etc -name "*.conf"
# real    0m0.045s
# user    0m0.008s  <-- Время выполнения кода в Userspace
# sys     0m0.015s  <-- Время, затраченное ядром на обслуживание системных вызовов процесса
```

### Идентификация потоков ядра

**Потоки ядра (Kernel Threads)** выполняют фоновые задачи (например, сброс грязных страниц на диск или обслуживание прерываний). В отличие от обычных процессов, они работают целиком внутри адресного пространства ядра.

#### Особенности отображения в `ps`

В выводе `ps aux` или `ps -ef` потоки ядра легко узнать по следующим признакам:
- **Квадратные скобки:** Название процесса заключено в `[...]` (например, `[kworker/0:1]`). Это происходит потому, что у потоков ядра нет сегментов памяти пользователя (stack, heap) и, соответственно, нет командной строки (arguments) в Userspace. Утилита `ps`, обнаружив пустой буфер командной строки, выводит внутреннее имя ядра в скобках.
- **Низкие PID:** Большинство системных потоков ядра порождаются при старте системы и имеют идентификаторы в начале списка (PID 2 обычно принадлежит `[kthreadd]`).
- **Отсутствие TTY:** В колонке терминала всегда стоит знак вопроса `?`.

```bash
# Поиск всех потоков ядра
ps -ef | grep "\["
# root         2       0  0 10:00 ?        00:00:00 [kthreadd]
# root         9       2  0 10:00 ?        00:00:00 [kworker/0:1H-events_highpri]
```

#### Почему их нельзя «убить» (даже root'у)

Даже обладая правами суперпользователя, вы не сможете завершить поток ядра командой `kill -9 <PID>`. Это обусловлено архитектурой доставки сигналов:

1.  **Отсутствие перехода в Userspace:** Сигналы (например, `SIGKILL`) доставляются процессу только в момент его возврата из режима ядра в режим пользователя. Поскольку потоки ядра **никогда не переходят в режим пользователя**, они физически не достигают точки проверки очереди сигналов.
2.  **Игнорирование сигналов:** Потоки ядра по умолчанию не имеют обработчиков сигналов. Они управляются внутренними механизмами ядра (например, `kthread_stop()`) и реагируют только на специальные системные события.
3.  **Безопасность системы:** Принудительное завершение жизненно важных потоков (например, `kswapd` или `jbd2`) привело бы к немедленной блокировке системы или потере данных. Поэтому ядро защищает их от внешних воздействий Userspace.

**Что делать, если поток ядра грузит CPU?**
Это симптом проблемы, а не сама проблема. Высокая нагрузка `[kworker]` обычно указывает на интенсивный ввод-вывод (I/O) или шквал прерываний, а `[ksoftirqd]` — на высокую сетевую нагрузку. Бороться нужно с причиной (нагрузкой), а не с системным потоком.

## Дополнительная информация

### Почему разделение критически важно

1.  **Безопасность (Security):** Ошибка в браузере не позволяет ему напрямую прочитать содержимое файлов паролей или вмешаться в работу сетевого экрана.
2.  **Стабильность (Stability):** Некорректно написанное приложение может упасть с ошибкой `Segmentation Fault` в Userspace, но операционная система продолжит работу.
3.  **Абстракция:** Userspace работает с виртуальными адресами и логическими файлами, в то время как Kernelspace управляет физическими страницами RAM и секторами дисков.
