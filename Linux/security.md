## Capabilities

Традиционная модель прав в Unix делит все процессы на две категории: непривилегированные (обычные пользователи) и полностью привилегированные (`root`, UID 0). Такой подход "всё или ничего" небезопасен. Механизм **capabilities** решает эту проблему, разделяя всемогущество `root` на отдельные, гранулярные привилегии.

Процесс может иметь только тот набор "способностей", который ему действительно необходим для работы, не получая полных прав суперпользователя. Например, веб-серверу для работы на порту 80 нужна только привилегия `CAP_NET_BIND_SERVICE`, а не полный доступ к системе.

**Преимущества:**

-   **Повышение безопасности:** Если процесс с ограниченным набором capabilities будет скомпрометирован, злоумышленник не получит полные права `root`.
-   **Принцип наименьших привилегий:** Процессы работают с минимально необходимым набором прав.


-   **`getcap`**: Показывает capabilities, установленные для файла.
    ```bash
    getcap /usr/bin/ping
    ```

-   **`setcap`**: Устанавливает или удаляет capabilities для файла.
    ```bash
    # Дать бинарному файлу право слушать порты ниже 1024
    sudo setcap 'cap_net_bind_service=+ep' /path/to/binary
    ```
    - `+ep` означает "добавить в набор Effective и Permitted".

## Системный аудит с помощью `auditd`

**`auditd`** — это подсистема аудита в ядре Linux, которая позволяет отслеживать и записывать события, связанные с безопасностью, такие как доступ к файлам и системные вызовы.

Подробное описание `auditd`, его настройка и примеры использования находятся в документе [logs.md](./logs.md#3-аудит-доступа-auditd).

## Изоляция процессов: сокрытие процессов от других пользователей

По умолчанию в большинстве дистрибутивов Linux любой пользователь может видеть все процессы, запущенные в системе, с помощью команд `ps`, `top` или `htop`. Хотя детальная информация (например, переменные окружения) доступна только владельцу процесса или `root`, сам факт существования процессов, их PID и имена видны всем. Это может представлять угрозу безопасности, раскрывая информацию о запущенных сервисах и их активности.

Чтобы усилить безопасность, можно настроить ядро так, чтобы пользователи могли видеть **только свои собственные процессы**.

Это достигается путем монтирования виртуальной файловой системы `/proc` со специальной опцией `hidepid`.

**Возможные значения `hidepid`:**

-   `hidepid=0` (по умолчанию): Все пользователи могут видеть все процессы.
-   `hidepid=1`: Пользователи видят только свои процессы. Содержимое директорий `/proc/<PID>` скрыто от других пользователей, но сами директории (и, следовательно, номера PID) все еще видны.
-   `hidepid=2` (рекомендуется): Пользователи видят только свои процессы. Директории `/proc/<PID>`, принадлежащие другим пользователям, становятся для них невидимыми. Это наиболее строгий и безопасный вариант.

Дополнительно можно использовать опцию `gid`, чтобы создать группу-исключение (например, `auditors`), члены которой смогут видеть все процессы, как и `root`.

Чтобы изменения сохранялись после перезагрузки, необходимо отредактировать файл `/etc/fstab`.

1.  **Откройте `/etc/fstab` с правами `root`:**
    ```sh
    sudo nano /etc/fstab
    ```

2.  **Найдите строку, отвечающую за монтирование `/proc`** (или добавьте новую, если ее нет).

3.  **Добавьте опции `hidepid=2` и `gid=...`** в четвертое поле (опции монтирования).

    **Пример строки в `/etc/fstab`:**
    ```
    # <file system> <mount point>   <type>  <options>         <dump>  <pass>
    proc            /proc           proc    defaults,hidepid=2,gid=procview 0       0
    ```
    -   `hidepid=2`: Включает строгую изоляцию.
    -   `gid=procview`: Задает имя группы (или ее GID), которая будет исключена из этого правила. Не забудьте создать эту группу (`sudo groupadd procview`) и добавить в нее доверенных пользователей (`sudo usermod -aG procview <username>`).

4.  **Перемонтируйте `/proc`, чтобы применить изменения немедленно:**
    ```sh
    sudo mount -o remount /proc
    ```

После этого обычные пользователи, залогинившись в систему, при выполнении `ps aux` или `htop` увидят только свои собственные процессы и системные процессы, запущенные от их имени.
