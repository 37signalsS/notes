Ядро является центральным компонентом операционной системы, отвечающим за управление процессами, памятью и оборудованием. Подробно о том, как ядро управляет процессами, можно прочитать в документе [processes.md](./processes.md).

## "Загрязнение" ядра (Kernel Taint)

**Taint-флаг** — это механизм ядра Linux, который указывает на то, что система находится в нестандартном или потенциально нестабильном состоянии.

### Как посмотреть флаги

Состояние флага можно проверить, прочитав специальный файл в `/proc`:

```bash
cat /proc/sys/kernel/tainted
```

-   Если команда возвращает `0`, ядро чистое.
-   Любое другое число указывает на одну или несколько причин "загрязнения".

Также информация о "загрязнении" появляется в логах ядра при сбоях (`dmesg`).

### Основные причины "загрязнения"

-   **`P` (Proprietary Module):** Загружен проприетарный (не-GPL) модуль, например, драйвер NVIDIA.
-   **`F` (Forcefully Loaded):** Модуль был загружен принудительно (`insmod -f`).
-   **`G` (Staging Driver):** Загружен драйвер из ветки `staging` — экспериментальный код.
-   **`W` (Warning):** Ядро выдало предупреждение (например, `WARN_ONCE`).
-   **`O` (Out-of-tree Module):** Загружен модуль, который не является частью официального дерева исходного кода ядра.
-   **`M` (Machine Check Error):** Произошёл аппаратный сбой, зафиксированный процессором.

## Обновление ядра без перезагрузки

В средах, требующих максимального времени безотказной работы (uptime), перезагрузка для обновления ядра может быть неприемлема. Существуют технологии, позволяющие применять обновления безопасности "на лету".

1.  **`kpatch` и `ksplice` (Live Patching):**
    -   **Как работает:** Эти инструменты применяют патчи к работающему ядру прямо в памяти. Они перенаправляют вызовы старых, уязвимых функций на новые, исправленные версии, не останавливая работу системы.
    -   **Назначение:** В основном используется для критических обновлений безопасности.
    -   **Применение:** `kpatch` (разработан Red Hat) и `ksplice` (разработан Oracle) являются коммерческими или поддерживаемыми производителями решениями.

2.  **`kexec`:**
    -   **Как работает:** `kexec` — это системный вызов, который позволяет загрузить новое ядро непосредственно из текущего, минуя BIOS/UEFI и аппаратную инициализацию. Это не "живой патч", а скорее "быстрая перезагрузка" в новое ядро.
    -   **Преимущества:** Значительно сокращает время простоя по сравнению с полной перезагрузкой, так как пропускается долгий этап POST.
    -   **Использование:**
        ```bash
        # Загрузить новое ядро и initramfs в память
        sudo kexec -l /boot/vmlinuz-новое-ядро --initrd=/boot/initrd.img-новое-ядро --reuse-cmdline

        # Выполнить "перезагрузку"
        sudo kexec -e
        ```

## Управление параметрами ядра с помощью `sysctl`

`sysctl` — это утилита, которая позволяет просматривать и изменять параметры ядра Linux "на лету", без необходимости перезагрузки. Эти параметры управляют поведением различных подсистем, таких как сеть, виртуальная память и файловая система.

**Основные команды:**

-   **Просмотреть все доступные параметры:**
    ```bash
    sudo sysctl -a
    ```

-   **Прочитать значение конкретного параметра:**
    ```bash
    sudo sysctl vm.swappiness
    ```

-   **Изменить значение параметра временно (до перезагрузки):**
    ```bash
    sudo sysctl -w vm.swappiness=10
    ```

**Сохранение параметров:**

Чтобы изменения сохранялись после перезагрузки, их необходимо записать в файл `/etc/sysctl.conf` или в отдельный файл в директории `/etc/sysctl.d/`.

1.  **Отредактируйте файл:**
    ```
    # /etc/sysctl.conf
    vm.swappiness = 10
    net.ipv4.ip_forward = 1
    ```

2.  **Примените изменения:**
    ```bash
    sudo sysctl -p
    ```

## Управление выделением памяти (Memory Overcommit)

**Memory Overcommit** — это механизм ядра, который позволяет процессам запрашивать больше виртуальной памяти, чем физически доступно в системе. Это возможно, потому что программы часто резервируют память, но не используют её всю сразу.

Поведение этого механизма регулируется параметром `vm.overcommit_memory`:

-   `0` (Heuristic overcommit handling, по умолчанию): Ядро использует эвристику для оценки, достаточно ли памяти. Запросы, которые очевидно ведут к переполнению, отклоняются.
-   `1` (Always overcommit): Ядро всегда разрешает выделение памяти, каким бы большим ни был запрос. Этот режим может быть опасен, так как повышает риск вызова OOM Killer.
-   `2` (Don't overcommit): Ядро строго ограничивает выделение виртуальной памяти. Процесс не может запросить больше, чем `SwapTotal + (RAM * overcommit_ratio)`. `overcommit_ratio` — это процент RAM, который можно выделить сверх swap (по умолчанию 50%).

Настройка производится через `sysctl`:
```bash
sudo sysctl -w vm.overcommit_memory=1
```

## Оптимизация памяти: Kernel Samepage Merging (KSM)

**KSM (Kernel Samepage Merging)** — это фоновый процесс в ядре, который сканирует память и ищет идентичные страницы. Если он находит две или более одинаковые страницы, он объединяет их в одну, помечая её как "copy-on-write" (CoW).

**Как это работает:**
1.  KSM объединяет одинаковые страницы в одну физическую страницу.
2.  Если какой-либо процесс пытается изменить эту страницу, ядро автоматически создает для него копию, и только после этого процесс вносит изменения.

**Преимущества:**
-   **Экономия RAM:** KSM значительно сокращает потребление памяти, особенно в средах с высокой степенью дублирования данных, например, при запуске множества однотипных виртуальных машин на одном хосте.

KSM управляется через файлы в `/sys/kernel/mm/ksm/`.

## Оптимизация для архитектуры NUMA

**NUMA (Non-Uniform Memory Access)** — это архитектура построения памяти, используемая в многопроцессорных системах. В ней память физически разделена на "узлы" (nodes), и каждый процессор (или группа ядер) имеет быстрый локальный доступ к своему узлу памяти, но более медленный доступ к памяти других узлов.

**Проблема:** Если процесс, выполняющийся на одном процессоре, постоянно обращается к памяти, расположенной на другом узле, возникают задержки, снижающие производительность.

**Оптимизация:**
Основная стратегия — обеспечить **локальность NUMA**, то есть сделать так, чтобы процесс и память, с которой он работает, находились на одном и том же узле.

-   **`numactl`**: Это основная утилита для управления политиками NUMA. Она позволяет принудительно запускать процесс на определённом узле и выделять ему память только из этого узла.
    ```bash
    # Запустить процесс my_app на узле 0 и выделять ему память только оттуда
    numactl --cpunodebind=0 --membind=0 my_app
    ```

## Использование HugePages

**HugePages** — это страницы памяти большого размера (обычно 2 МБ или 1 ГБ вместо стандартных 4 КБ). Их использование позволяет сократить накладные расходы на управление памятью.

**Преимущества:**
-   **Снижение нагрузки на TLB (Translation Lookaside Buffer):** TLB — это кэш процессора для трансляции виртуальных адресов в физические. Использование меньшего количества больших страниц вместо огромного количества маленьких снижает вероятность промахов в TLB, ускоряя доступ к памяти.
-   **Уменьшение размера таблиц страниц:** Требуется меньше записей для отображения того же объёма памяти.

**Применение:**
HugePages особенно полезны для приложений, работающих с большими объёмами непрерывной памяти, таких как базы данных (Oracle, PostgreSQL) и системы виртуализации (KVM).

**Активация:**
Количество HugePages настраивается через параметр ядра:
```bash
# Выделить 1024 страницы по 2 МБ (всего 2 ГБ)
sudo sysctl -w vm.nr_hugepages=1024
```

## Kernel Panic: анализ и отладка

**Kernel Panic** — это критическая, невосстановимая ошибка ядра операционной системы, при которой оно не может безопасно продолжать работу. Система останавливается для предотвращения дальнейшего повреждения данных.

**Анализ сбоев (`crash dumps`):**
Для анализа причин Kernel Panic используется механизм `kdump`. Он работает, загружая второе, минимальное ядро (`crashkernel`) в зарезервированную область памяти. Когда основное ядро падает, управление передаётся `crashkernel`, которое сохраняет образ памяти (дамп) основного ядра на диск.

**Процесс анализа:**
1.  **Настройка `kdump`:** Убедитесь, что `kdump` установлен и сервис активен (`systemctl is-active kdump`).
2.  **Анализ дампа:** После перезагрузки сохранённый дамп (обычно в `/var/crash/`) можно проанализировать с помощью утилиты `crash`.
3.  **Просмотр логов:** Первичную информацию о панике часто можно найти в системных логах до перезагрузки:
    ```bash
    # Логи ядра с последней загрузки
    journalctl -k -b -1
    # или
    dmesg -T
    ```
