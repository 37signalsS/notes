# Управление и тюнинг Java (JVM)

## Определения

*   **JVM (Java Virtual Machine):** Виртуальная машина, исполняющая Java-байт-код. Управляет памятью, потоками и ресурсами.
*   **JDK (Java Development Kit):** Полный набор инструментов для разработки, включая компилятор (`javac`), JRE и инструменты диагностики (`jcmd`, `jstack`).
*   **JRE (Java Runtime Environment):** Минимальная среда выполнения (JVM + библиотеки). В современных версиях (Java 11+) поставляется в виде модульных сборок через `jlink`.
*   **Куча (Heap):** Область памяти для объектов приложения. Управляется Garbage Collector.
*   **Сжатые указатели (Compressed OOPs):** Оптимизация JVM, позволяющая использовать 4-байтовые указатели вместо 8-байтовых. Работает при размере кучи **до ~31.5 ГБ**. Превышение этого порога приводит к резкому росту потребления памяти.
*   **GraalVM Native Image:** Технология компиляции Java-кода в самодостаточный бинарный файл (AOT-компиляция). Обеспечивает мгновенный старт и минимальное потребление RAM, но ограничивает динамические возможности (Reflection).

## Основные концепции

### Версионирование и байт-код

Версия компиляции определяет минимальную версию JRE для запуска. Байт-код более новой версии не запустится на старой JRE (ошибка `UnsupportedClassVersionError`).

| Версия Java | Major version байт-кода | Статус (2025) |
| :--- | :--- | :--- |
| 8 | 52 | Legacy / Maintenance |
| 11 | 55 | Old LTS |
| 17 | 61 | Current LTS |
| 21 | 65 | Modern LTS |
| 23 | 67 | Latest Feature |

### Структура памяти JVM (Non-Heap)

Общее потребление памяти процессом Java (`RSS`) всегда больше, чем размер кучи (`Xmx`). Оно включает:
1.  **Metaspace:** Метаданные классов. Лимитируется через `-XX:MaxMetaspaceSize`.
2.  **Code Cache:** Память для JIT-скомпилированного кода.
3.  **Thread Stacks:** Память под каждый поток (по умолчанию 1 МБ на поток).
4.  **Direct Memory:** Используется для высокопроизводительного ввода-вывода (NIO). Лимитируется через `-XX:MaxDirectMemorySize`.

### Поддержка контейнеров и cgroups v2

Современная JVM корректно считывает лимиты ресурсов из контрольных групп Linux.

*   **cgroups v1:** Поддерживается с JDK 8u191 и JDK 10+.
*   **cgroups v2:** Полная поддержка введена в **JDK 15+** (бэкпорт в 8u372). Критично для современных дистрибутивов (Ubuntu 22.04+, RHEL 9).
*   **Проблемы старых версий:** Без поддержки cgroups JVM видит всю память хоста и может быть убита OOM Killer ядра при достижении лимита контейнера.

## Современные сборщики мусора (Garbage Collectors)

Выбор GC зависит от требований к задержке (latency) и пропускной способности (throughput).

| GC | Особенности | Когда использовать |
| :--- | :--- | :--- |
| **G1GC** | Баланс между паузами и CPU. Дефолт с Java 9. | Универсальный выбор для большинства задач. |
| **Generational ZGC** | Паузы < 1 мс. Введен в Java 21. | Приложения с жесткими требованиями к SLA по задержкам. |
| **Shenandoah** | Низкие паузы, эффективное сжатие памяти. | Альтернатива ZGC, лучше справляется с фрагментацией на некоторых нагрузках. |

## Практические сценарии

### Настройка для Production (Java 17/21+)

Рекомендуемый набор флагов для запуска в контейнере (Kubernetes/Docker):

```bash
java -XX:+UseContainerSupport \
     -XX:MaxRAMPercentage=75.0 \
     -XX:+ExitOnOutOfMemoryError \
     -XX:+UnlockDiagnosticVMOptions \
     -Xlog:gc*:file=/var/log/app/gc.log:time,uptime,level,tags \
     -jar app.jar
# → JVM выделит 75% от лимита памяти контейнера под Heap
# → При OOM процесс завершится с ошибкой, позволяя оркестратору его перезапустить
```

### Динамическое управление памятью

Если приложение имеет выраженные пики нагрузки, можно разрешить JVM возвращать неиспользуемую память ОС:

```bash
# -XX:SoftMaxHeapSize: целевой размер кучи, который JVM будет стараться соблюдать
# -Xmx: жесткий предел для пиковых нагрузок
java -XX:MaxRAMPercentage=80.0 -XX:SoftMaxHeapSize=1G -jar app.jar
```

### Диагностика работающего приложения

Использование встроенных инструментов JDK без остановки процесса:

```bash
# Проверка текущих лимитов и версии (Container Awareness)
jcmd <PID> VM.info | grep -A 5 "container"
# → Container memory limit: 1024.0M
# → CPU shares: 1024

# Снятие дампа потоков (Thread Dump)
jcmd <PID> Thread.print > threads.txt

# Запуск профилирования JFR (Java Flight Recorder) на 60 секунд
jcmd <PID> JFR.start duration=60s filename=recording.jfr
```

### Профилирование с помощью async-profiler

Лучший инструмент для поиска утечек в Native Memory и CPU-bottlenecks в Linux:

```bash
# Профилирование CPU (Wall-clock)
./asprof -d 30 -f cpu_profile.html <PID>
# → Создание FlameGraph для анализа горячих путей в коде
```
