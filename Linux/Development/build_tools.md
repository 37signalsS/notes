# Кэширование компиляции с `ccache`

`ccache` — это инструмент, который кэширует результаты компиляции исходного кода. При повторной сборке проекта, если файлы не изменились, `ccache` предоставляет уже скомпилированные объектные файлы из кэша, что значительно ускоряет процесс.

### Как это работает

`ccache` работает как "обертка" для компилятора (такого как `gcc` или `clang`). Он проверяет хэш исходного файла и параметров компиляции. Если результат для такого хэша уже есть в кэше, возвращается готовый объектный файл. Если нет — вызывается настоящий компилятор, а результат его работы сохраняется в кэш.

### Настройка и использование

1.  **Установка:**

    ```bash
    # Debian/Ubuntu
    sudo apt install ccache
    # RHEL/CentOS
    sudo dnf install ccache
    ```

2.  **Интеграция с системой сборки:**

    Самый простой способ — указать `ccache` в качестве компилятора через переменные окружения.

    ```bash
    export CC="ccache gcc"
    export CXX="ccache g++"
    ```
    После этого любая система сборки (`make`, `cmake`) будет автоматически использовать `ccache`.

3.  **Управление кэшем:**

    -   **Указание директории кэша:**

        По умолчанию кэш хранится в `~/.ccache`. Путь можно изменить:

        ```bash
        export CCACHE_DIR=/path/to/cache
        ```

    -   **Просмотр статистики:**

        ```bash
        ccache -s
        ```

        Эта команда покажет размер кэша, количество попаданий и промахов.

## Динамическая компоновка (Dynamic Linking)

Когда программа использует общие библиотеки (`.so` файлы), процесс связывания символов (функций, переменных) из этих библиотек с программой может происходить либо в момент запуска, либо откладываться до первого вызова.

### Отложенная привязка (Lazy Binding)

**Отложенная привязка (Lazy Binding)** — это техника, используемая динамическим компоновщиком (`ld.so`) для ускорения запуска программ.

-   **Проблема:** При запуске программы, если сразу разрешать адреса всех внешних функций из десятков библиотек, старт может занять значительное время.
-   **Решение:** Вместо этого, разрешение адреса функции откладывается до момента ее первого вызова.

**Как это работает:**

Механизм реализуется с помощью двух специальных таблиц:

1.  **PLT (Procedure Linkage Table / Таблица связывания процедур):** Это "батут" или трамплин. Когда программа впервые вызывает внешнюю функцию, она на самом деле вызывает заглушку в PLT.
2.  **GOT (Global Offset Table / Глобальная таблица смещений):** Хранит реальные адреса функций. Изначально она заполнена указателями обратно на PLT.

**Процесс первого вызова:**

1.  Программа вызывает функцию, попадая в ее запись в **PLT**.
2.  Запись в PLT передает управление динамическому компоновщику (`ld.so`).
3.  Компоновщик находит реальный адрес функции в нужной библиотеке.
4.  Этот адрес записывается в **GOT**.
5.  Управление передается на реальный адрес функции.

**Последующие вызовы:**

При всех последующих вызовах этой же функции, запись в PLT сразу же перенаправляет управление на реальный адрес, сохраненный в GOT, минуя медленный процесс поиска. Это значительно снижает накладные расходы.
