# Обзор механизмов безопасности в Linux

## Definitions

**Механизмы безопасности Linux** — совокупность встроенных в ОС функций, политик и инструментов для защиты от несанкционированного доступа, модификации, разрушения или раскрытия информации.

**Defense in Depth (Многослойная защита)** — стратегия безопасности, при которой защитные механизмы располагаются слоями (периметр, хост, приложение, ядро). Компрометация одного слоя не приводит к полному взлому системы.

**HCK (Harden Repeat)** — цикличный подход к безопасности: Исследование → Попытка взлома (Attack) → Укрепление (Harden) → Повтор. Позволяет эмпирически подтверждать эффективность защитных мер.

Этот документ — SSoT для высокоуровневого обзора механизмов безопасности Linux. Детальные описания каждого механизма находятся в соответствующих заметках.

## Basic Concepts

### Архитектура безопасности: уровни ядра и пользователя

| Уровень | Функции безопасности | Риски компрометации |
| :--- | :--- | :--- |
| **Ядро (Kernel)** | Сегментация прав, изоляция процессов, защита памяти | Компрометация ядра делает бессмысленными любые меры пользовательского уровня |
| **Пользовательский (User)** | Контроль доступа, аутентификация, авторизация, аудит | Большинство взаимодействий и атак происходит на этом уровне |

**Приоритет защиты:**

- Ядро: использовать официальные образы, регулярно обновляться, следовать рекомендациям по защите от известных уязвимостей
- Пользовательский уровень: сосредоточить усилия на правильной настройке прав доступа и политик безопасности

### Абстракция операций контроля доступа

Все операции пользовательского уровня представляются как процесс:

```
Субъект → Запрос → Объект
```

Пример (`open /etc/passwd`):

- **Субъект:** пользователь или процесс
- **Запрос:** операция чтения
- **Объект:** файл `/etc/passwd`

Ядро обеспечивает контроль доступа на основе разрешений, предотвращая несанкционированный доступ.

### Модели контроля доступа

**Discretionary Access Control (DAC):** традиционная модель, где владелец ресурса сам определяет права доступа. Реализация — стандартные права доступа к файлам Linux (`rwx` для владельца, группы и остальных). Подробности: [права доступа к файлам Linux](./Concepts/File_Permissions/overview_definitions.md).

**Mandatory Access Control (MAC):** централизованная политика безопасности (недоступная для изменения пользователями) определяет доступ на основе меток (контекстов) безопасности, присвоенных субъектам (процессам) и объектам (файлам). Процесс с меткой "веб-сервер" не сможет читать файлы с меткой "документы_пользователей", даже если запущен от имени `root`.

### Изоляция и ограничение процессов

Предотвращают распространение вредоносного влияния с одного скомпрометированного процесса на всю систему. Основные механизмы:

- **Capabilities:** разделение привилегий `root` на гранулярные права
- **Seccomp:** фильтр системных вызовов
- **Namespaces и Cgroups:** изоляция процессов и управление ресурсами (основа контейнеризации)
- **hidepid:** скрытие процессов в `/proc` от других пользователей

### Защита ядра и памяти

- **KASLR (Kernel Address Space Layout Randomization):** рандомизация размещения кода ядра в памяти при каждой загрузке
- **ASLR (Address Space Layout Randomization):** рандомизация расположения стека, кучи и библиотек в памяти пользовательских приложений

Оба механизма усложняют эксплуатацию уязвимостей, затрудняя предсказание расположения критически важных структур памяти.

### Аудит и мониторинг

Системы регистрации событий безопасности для отслеживания активности и обнаружения аномалий:

- **auditd:** подсистема аудита ядра для детального отслеживания событий (доступ к файлам, системные вызовы, изменения конфигурации, попытки повышения привилегий)
- **Проверка целостности файлов:** инструменты (`AIDE`, `debsums`, `rpm -Va`) для обнаружения несанкционированных изменений в системных файлах
- **Fail2Ban:** автоматическая защита от brute-force атак через анализ логов

### Управление доступом и идентификацией

Механизмы аутентификации пользователей и предоставления привилегий:

- **Пользователи и группы:** управление учётными записями, правами и привилегиями
- **GPG/OpenPGP:** шифрование, цифровая подпись и проверка целостности данных

## Practical Scenarios

### 1. Контроль доступа

| Механизм | Тип | Ссылка |
| :--- | :--- | :--- |
| DAC (стандартные права `rwx`) | Discretionary | [Права доступа к файлам](./Concepts/File_Permissions/overview_definitions.md) |
| SELinux | Mandatory (метки/контексты) | [SELinux](./Mechanisms/SELinux.md) |
| AppArmor | Mandatory (профили по путям) | [AppArmor](./Mechanisms/AppArmor.md) |

**Выбор механизма MAC:**

- SELinux — детальная изоляция на основе меток, предпочтителен для контейнеров и облачных сред
- AppArmor — профили, привязанные к путям файлов, проще в настройке

### 2. Изоляция процессов

| Механизм | Назначение | Ссылка |
| :--- | :--- | :--- |
| Capabilities | Гранулярные привилегии вместо `root` | [Capabilities](./Mechanisms/Capabilities.md) |
| Seccomp | Фильтрация системных вызовов | [Seccomp](./Mechanisms/Seccomp.md) |
| Namespaces + Cgroups | Изоляция процессов и ресурсов | [Namespaces и Cgroups](../../Docker/Concepts/linux_isolation.md) |
| hidepid (`/proc`) | Скрытие процессов от других пользователей | — |

**Сценарий изоляции контейнера:**

1. Capabilities — минимальный набор привилегий (`setcap`)
2. Seccomp — запрет опасных системных вызовов
3. AppArmor/SELinux — профиль/политика для процесса
4. Read-only rootfs — защита файловой системы

### 3. Защита ядра и памяти

| Механизм | Уровень | Ссылка |
| :--- | :--- | :--- |
| KASLR | Ядро | [KASLR](./Mechanisms/KASLR.md) |
| ASLR | Пользовательские приложения | — |

**Проверка статуса:**

- KASLR: `/proc/cmdline` (наличие `kaslr`), `/proc/kallsyms`
- ASLR: `sysctl kernel.randomize_va_space` (режимы 0/1/2)

### 4. Аудит и мониторинг

| Инструмент | Назначение | Ссылка |
| :--- | :--- | :--- |
| auditd | Аудит системных вызовов и событий | — |
| AIDE, debsums, rpm -Va | Проверка целостности файлов | [Проверка целостности](./Concepts/file-integrity-checking.md) |
| fail2ban | Защита от brute-force | [fail2ban](./Tools/fail2ban.md) |

**Сценарий расследования инцидента:**

1. auditd — поиск событий по времени/процессу/пользователю (`ausearch`, `aureport`)
2. Проверка целостности файлов — обнаружение изменённых бинарников
3. Fail2Ban — анализ заблокированных IP-адресов

### 5. Управление доступом и идентификацией

### Требования ФСТЭК

Механизмы безопасности Linux частично покрывают требования ФСТЭК:

- Контроль доступа: DAC/MAC, PAM
- Защита ядра: ASLR (`kernel.randomize_va_space`)
- Аудит: auditd
- Целостность: AIDE, проверка подписей пакетов

Подробности: [Обзор требований ФСТЭК](./Fstec/overview.md)
