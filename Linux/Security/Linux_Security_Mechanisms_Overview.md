# Обзор механизмов безопасности в Linux

## Определения

**Механизмы безопасности Linux** — совокупность встроенных в ОС функций, политик и инструментов для защиты от несанкционированного доступа, модификации, разрушения или раскрытия информации.

**Defense in Depth (Многослойная защита)** — стратегия безопасности, при которой защитные механизмы располагаются слоями (периметр, хост, приложение, ядро). Компрометация одного слоя не приводит к полному взлому системы.

**HCK (Harden Repeat)** — цикличный подход к безопасности: Исследование → Попытка взлома (Attack) → Укрепление (Harden) → Повтор. Позволяет эмпирически подтверждать эффективность защитных мер.

**LSM (Linux Security Modules)** — фреймворк в ядре Linux, позволяющий реализовывать различные модули мандатного контроля доступа (MAC). LSM перехватывает системные вызовы непосредственно перед обращением к внутренним объектам ядра (файлам, сокетам, структурам IPC).

Детальные описания каждого механизма находятся в соответствующих заметках.

## Базовые концепции

### Эшелонированная архитектура защиты

Современный стек безопасности Linux представляет собой многоуровневую систему исторических и современных надстроек (актуальность 2026 г.):
1.  **Дискреционная модель (DAC):** базовые права доступа (`rwx`), владельцы и группы.
2.  **Функциональные расширения:** механизмы, дополняющие DAC гранулярными правилами (ACL, Linux Capabilities, PAM).
3.  **Принудительные модули (LSM):** системы мандатного контроля (SELinux, AppArmor, Landlock), переопределяющие правила доступа на уровне ядра.
4.  **Безопасность времени выполнения (Runtime Security):** мониторинг и блокировка на основе eBPF (Tetragon) и контроль целостности кода (IPE).

### Системные недостатки традиционной модели (DAC)

Классическая модель прав Unix обладает рядом критических ограничений:
1.  **Монолитность привилегий:** учетная запись `root` является единственной точкой отказа; её компрометация ведет к полной потере контроля.
2.  **Риски делегирования (SetUID):** механизмы повышения прав через SUID-биты сложны в безопасной реализации и являются приоритетной целью атак.
3.  **Отсутствие сетевого контекста:** модель не верифицирует идентификаторы (UID/GID), поступающие из сети (риск подмены на уровне файловых систем).
4.  **Сложность управления группами:** создание групп является административной привилегией, что ограничивает пользователей в самостоятельной настройке гранулярного доступа.
5.  **Статичность правил:** многие логики доступа жестко вшиты в бинарные файлы и демоны, требуя пересборки для изменения политик.
6.  **Дефицит аудита:** традиционная модель фиксирует текущие права, но не обеспечивает детального протоколирования использования привилегий.

### Архитектура безопасности: уровни ядра и пользователя

| Уровень | Функции безопасности | Риски компрометации |
| :--- | :--- | :--- |
| **Ядро (Kernel)** | Сегментация прав, изоляция процессов, защита памяти, **Lockdown**, **IPE** | Компрометация ядра делает бессмысленными любые меры пользовательского уровня |
| **Пользовательский (User)** | Контроль доступа, аутентификация, авторизация, аудит, **Sandboxing (Landlock)** | Большинство взаимодействий и атак происходит на этом уровне |

**Приоритет защиты:**
- **Ядро:** Использовать доверенные образы, регулярно обновляться (Livepatching), активировать механизмы Hardening (KASLR, Lockdown).
- **Пользовательский уровень:** Сосредоточить усилия на принципе наименьших привилегий (Least Privilege) и песочницах для недоверенного кода.

### Абстракция операций контроля доступа

Все операции пользовательского уровня представляются как процесс:

```
Субъект (Процесс) → Запрос (Syscall) → Объект (Файл/Ресурс)
```

Пример (`open /etc/passwd`):
- **Субъект:** процесс с UID 1000 и контекстом `user_t`.
- **Запрос:** операция `read`.
- **Объект:** файл `/etc/passwd` с меткой `passwd_file_t`.

Ядро обеспечивает контроль доступа, последовательно опрашивая все уровни защиты (DAC → LSM → Seccomp).

### Модели контроля доступа

*   **Discretionary Access Control (DAC):** традиционная модель, где владелец ресурса сам определяет права доступа. Подробности: **[Права доступа к файлам Linux](./Concepts/File_Permissions/overview_definitions.md)**.
*   **Mandatory Access Control (MAC):** централизованная политика безопасности (недоступная для изменения пользователями) определяет доступ на основе меток (контекстов). Процесс с меткой «веб-сервер» не сможет читать файлы с меткой «документы_пользователей», даже если запущен от имени `root`.

### Изоляция и ограничение процессов

Предотвращают распространение вредоносного влияния (Blast Radius):
- **Capabilities:** разделение привилегий `root` на гранулярные права.
- **Seccomp:** фильтр системных вызовов (снижение поверхности атаки на ядро).
- **Landlock:** LSM для создания песочниц приложениями без прав суперпользователя (self-sandboxing).
- **Namespaces:** изоляция ресурсов (сеть, PID, mount) — основа контейнеризации.
- **cgroups v2:** управление ресурсами и лимитами.
- **hidepid:** скрытие процессов в `/proc` от других пользователей.

### Защита ядра и памяти

- **KASLR (Kernel Address Space Layout Randomization):** рандомизация адресов ядра.
- **Kernel Lockdown:** запрет доступа к функциям ядра, позволяющим изменять код ядра из userspace (даже для `root`).
- **IPE (Integrity Policy Enforcement):** LSM, разрешающий запуск только подписанного доверенного кода.
- **ASLR:** рандомизация памяти пользовательских приложений.

### Аудит и мониторинг

- **auditd:** подсистема аудита ядра (syscalls, доступ к файлам).
- **Tetragon (eBPF):** современный мониторинг безопасности в реальном времени с минимальными накладными расходами.
- **Проверка целостности:** инструменты (**AIDE**, **debsums**, **rpm -Va**) для поиска несанкционированных изменений.
- **Fail2Ban:** автоматическая защита от brute-force атак через анализ логов.

### 2. Изоляция процессов (Контейнерный Hardening)

Три механизма не взаимозаменяемы — каждый оценивает одно и то же действие по-своему:

```
Capabilities → что процессу в принципе разрешено (что он может)
Seccomp      → как процесс взаимодействует с ядром (как он просит)
LSM          → какое поведение допустимо в данном контексте (куда он лезет)
```

1. **Capabilities (РОВ С ВОДОЙ)** — сброс привилегий. Если злоумышленник получил RCE, он не может создать raw-сокет (без `CAP_NET_RAW`) или смонтировать ФС (без `CAP_SYS_ADMIN`).
2. **Seccomp (СТЕНА)** — ограничивает syscall. `RuntimeDefault` блокирует `unshare` и `mount` даже без явного запрета capability.
3. **AppArmor / SELinux (ОХРАНА)** — политика, оценивающая контекст. Может запретить чтение `/etc/shadow`, даже если DAC и capabilities это разрешают.

**Пример в Kubernetes (Security Context):**

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop: [ALL]
    add: [NET_BIND_SERVICE]
  seccompProfile:
    type: RuntimeDefault
  appArmorProfile:
    type: Localhost
    localhostProfile: my-flask-app
```

## Дополнительная информация

### Требования ФСТЭК (2026)

Механизмы безопасности Linux частично покрывают требования ФСТЭК:
- Контроль доступа: DAC/MAC (SELinux/AppArmor), PAM.
- Защита ядра: Lockdown, IPE, ASLR.
- Аудит: auditd, eBPF-мониторинг.
- Целостность: AIDE, проверка подписей пакетов и исполняемых файлов (IMA/EVM).

Подробности: **[Обзор требований ФСТЭК](./Fstec/overview.md)**.
