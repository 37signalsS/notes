# Специальные права доступа в Linux

## Определения

**Специальные права (Special Permissions)** — расширенные права (`SUID`, `SGID`, `Sticky Bit`), изменяющие стандартное поведение системы при доступе к файлам и директориям. Они дополняют стандартную модель DAC — см. [обзор прав доступа](./overview_definitions.md).

## Основные концепции

### SUID (Set User ID)

| Параметр | Значение |
| :--- | :--- |
| **Назначение** | Файл выполняется с правами **владельца**, а не запускающего пользователя |
| **Применимость** | Только **бинарные исполняемые файлы** |
| **Числовое значение** | `4` (устанавливается перед основными правами: `4755`) |
| **Обозначение** | `s` вместо `x` в правах владельца: `-rwsr-xr-x` |
| **Заглавная `S`** | `-rwSr-xr-x` — владелец не имеет `x`. Ошибка конфигурации |

**Практическое применение («Магия» подмены идентификатора):**
Делегирование специфических полномочий root обычным пользователям. Классический пример — утилита `passwd`.
1. Файл паролей `/etc/shadow` доступен только root. Обычный пользователь не имеет к нему доступа на запись.
2. Бинарный файл `/usr/bin/passwd` имеет установленный **SUID-бит** и принадлежит root.
3. Когда пользователь запускает `passwd`, процесс работает с **Effective UID root** (EUID 0).
4. Это позволяет программе дотянуться до `/etc/shadow` и обновить пароль.
5. При этом программа сама проверяет, кто её вызвал, и ограничивает действия: обычный пользователь может сменить только *свой* пароль, в то время как root — любой.

**Безопасность и риски:**
*   **Лакомая мишень:** Любая дыра в SUID-программе — это прямой путь к получению прав root на всей машине.
*   **Железное правило:** Чем меньше в системе SUID-программ, тем выше безопасность. Никогда не ставьте этот флаг на программы, которые для этого специально не писались.
*   **Игнорирование на скриптах:** SUID-бит **игнорируется на скриптах** (`.sh`, `.py` и т.д.). Ядро запускает не сам скрипт, а его интерпретатор, поэтому бит не применяется. Это предотвращает эскалацию привилегий через уязвимые скрипты.

### SGID (Set Group ID)

| Параметр | Значение |
| :--- | :--- |
| **Для файлов** | Выполняется с правами **группы-владельца** |
| **Для директорий** | Новые файлы и поддиректории наследуют **группу родительской директории** |
| **Числовое значение** | `2` (например: `2775`) |
| **Обозначение** | `s` вместо `x` в правах группы: `-rwxr-sr-x` |
| **Заглавная `S`** | `-rwxr-Sr-x` — группа не имеет `x`. Ошибка конфигурации |

SGID на директориях — основной инструмент для организации совместной работы: все файлы, созданные в общей директории, автоматически принадлежат одной группе. **Подкаталоги также наследуют SGID-бит**, так что это работает рекурсивно. Незаменимая вещь для совместных директорий, когда команда разработчиков должна иметь доступ к общим файлам через групповые права.

### Sticky Bit

| Параметр | Значение |
| :--- | :--- |
| **Назначение** | В современных системах — **только для директорий** |
| **Эффект** | Удалить/переименовать файл может только **владелец файла**, **владелец директории** или `root`. Без sticky bit в директории с правами `777` любой пользователь мог бы удалять чужие файлы, поскольку удаление — это запись в каталог |
| **Кто может установить** | Владелец директории или `root` |
| **Обозначение** | `t` в правах остальных: `drwxrwxrwt` |
| **Заглавная `T`** | `drwxrwxrwT` — у «остальных» нет `x` |
| **Пример** | `/tmp` — права `1777`. Все создают файлы, но удалять могут только свои |

Классический пример — `/tmp`: все пользователи создают файлы, но удалять могут только свои.

## Практические сценарии

### Установка и удаление специальных прав

```bash
# SUID (символьный и числовой режим)
chmod u+s /usr/bin/binary
chmod 4755 /usr/bin/binary

# SGID на файл
chmod g+s /usr/bin/binary
chmod 2755 /usr/bin/binary

# SGID на директорию (наследование группы)
chmod g+s /shared/project
chmod 2775 /shared/project

# Sticky Bit
chmod +t /tmp/public_dir
chmod 1777 /tmp/public_dir

# Удаление специальных прав
chmod u-s /usr/bin/binary   # снять SUID
chmod g-s /usr/bin/binary   # снять SGID
chmod -t /tmp/public_dir    # снять Sticky Bit
```

### Поиск файлов с SUID/SGID

Регулярный аудит — обязательная практика безопасности:

```bash
# Все файлы с SUID-битом
find / -type f -perm -4000 2>/dev/null

# Все файлы с SGID-битом
find / -type f -perm -2000 2>/dev/null

# Файлы с SUID или SGID (объединённый поиск)
find / -type f \( -perm -4000 -o -perm -2000 \) -exec ls -l {} \;

# Поиск с выводом владельца и прав
find / -type f -perm -4000 -exec stat -c '%A %U %n' {} \;
```

### Снятие SUID/SGID с нелегитимных файлов

```bash
# Удалить SUID-бит
sudo chmod u-s /path/to/suspicious_binary

# Удалить SGID-бит
sudo chmod g-s /path/to/suspicious_binary
```

### Безопасное монтирование файловых систем

Для предотвращения эскалации привилегий через съёмные носители и пользовательские разделы используйте `nosuid`:

```bash
# В /etc/fstab
UUID=...    /home    ext4    defaults,nosuid,nodev    0    2
UUID=...    /tmp     ext4    defaults,nosuid,noexec,nodev    0    2

# При монтировании tmpfs
mount -t tmpfs -o nosuid,noexec,nodev,size=1G tmpfs /tmp
```

Опции монтирования: [`nosuid`, `noexec`](../../../FileSystems/mounting/fstab.md).

## Дополнительная информация

* **Связь с DAC:** Специальные права расширяют, но не заменяют стандартную модель [Discretionary Access Control](./overview_definitions.md).
* **Управление:** Краткая справка по `chmod`/`chown`/`umask` — [управление правами: quick reference](./permissions_management_quickref.md).
* **Расширенные механизмы:** ACL, атрибуты и временные метки — [ACL, атрибуты и временные метки](./acl_immutable_timestamps.md).
* **Безопасность:** Core dump для SUID/SGID файлов отключается параметром `fs.suid_dumpable = 0` — [kernel_runtime_protection.md](../../Fstec/kernel_runtime_protection.md#запрет-создания-core-dump-для-suidsgid-файлов).
* **Аудит:** Регулярное сканирование SUID/SGID файлов — [file_permissions_control.md](../../Fstec/file_permissions_control.md#аудит-suid-и-guid-битов).
* **Контейнеры:** Флаг `--security-opt=no-new-privileges` запрещает повышение привилегий через SUID/SGID внутри контейнеров — [container_hardening.md](../../../../Docker/Docker_security/container_hardening.md).
