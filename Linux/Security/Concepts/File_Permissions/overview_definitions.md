# Права доступа, атрибуты и привилегии в Linux: Обзор

## Определения

* **Права доступа (Permissions):** Основной механизм безопасности в Linux, определяющий, какие действия (`чтение`, `запись`, `выполнение`) и кто (`владелец`, `группа`, `остальные`) может выполнять над файлом или директорией.
* **Специальные права (Special Permissions):** Расширенные права (`SUID`, `SGID`, `Sticky Bit`), которые изменяют стандартное поведение системы при доступе к файлам и директориям, часто для временного повышения привилегий.
* **ACL (Access Control Lists):** Расширенный механизм прав, который позволяет назначать разрешения для любого произвольного пользователя или группы, дополняя стандартную модель «владелец-группа-остальные».
* **Атрибуты файлов (File Attributes):** Флаги, устанавливаемые на уровне файловой системы (например, флаг `immutable`), которые могут запрещать определённые действия с файлом даже для суперпользователя `root`.
* **Umask (User File-Creation Mask):** Механизм, определяющий права доступа, которые **не будут** установлены для новых файлов и директорий по умолчанию.
* **Linux Capabilities:** Механизм ядра, разделяющий привилегии суперпользователя `root` на отдельные гранулярные права, позволяя процессам иметь только необходимый минимум полномочий (принцип наименьших привилегий).
* **LSM (Linux Security Modules):** Фреймворк в ядре Linux, позволяющий реализовывать различные модули безопасности (SELinux, AppArmor), которые работают «поверх» стандартной модели прав доступа.

## Базовые концепции

### 1. Стандартная модель прав доступа (Discretionary Access Control, DAC)

**Discretionary Access Control (DAC)** — это традиционная модель безопасности в Linux, при которой владелец ресурса (файла, каталога) сам определяет, кто и какие действия может выполнять над этим ресурсом. Это ключевая особенность отличает DAC от более строгих моделей, таких как Mandatory Access Control (MAC), где доступ регулируется централизованной политикой, которую пользователь не может изменить. В Linux механизмы MAC (SELinux, AppArmor) реализуются через фреймворк **LSM**.

#### Ограничения стандартной модели (DAC)

| Проблема | Описание | Компенсация |
| :--- | :--- | :--- |
| **Трудоёмкость настройки** | Управление для множества пользователей и сценариев громоздко | ACL, группы |
| **Проблема распространения** | Пользователь с `r` может скопировать и передать файл | MAC (SELinux, AppArmor) |
| **Централизация на пользователе** | Компрометация учётной записи = доступ ко всем ресурсам | MAC, изоляция процессов |
| **Бинарность привилегий** | Либо обычный пользователь, либо всемогущий `root` | Linux Capabilities |

**Концепция "запрещено по умолчанию"**: В идеальной системе безопасности по умолчанию доступ к ресурсам запрещен всем. Разрешения выдаются точечно, исходя из необходимости. Такой подход минимизирует риски, так как любая излишне предоставленная привилегия увеличивает поверхность атаки. Если пользователю не хватает прав, он обратится к администратору, что является нормальным процессом. Обратная ситуация, когда у пользователя слишком много прав, редко становится известной, так как пользователи, как правило, не сообщают о своих избыточных возможностях.

**Роли в модели DAC:**

* **Владелец файла**: Субъект, создавший файл. Обладает полным контролем над ним и может предоставлять или отзывать права доступа у других пользователей и групп.
* **Суперпользователь (root)**: Обладает абсолютными привилегиями в системе, может управлять доступом к любым объектам, независимо от их владельца. Это "суперсущность", которой доверено управление всей системой.

Система прав строится на трех китах: для кого и какие права. Суперпользователь `root` (UID 0) является исключением и имеет неограниченный доступ к системе.

### 2. Linux Capabilities (Гранулярные привилегии)

Традиционная модель DAC страдает от проблемы «всё или ничего» для суперпользователя. Если процессу нужно выполнить одну привилегированную операцию (например, открыть 80-й порт), ему приходится давать полный доступ `root`.

**Linux Capabilities** решают эту проблему, разбивая права `root` на десятки мелких частей:
* `CAP_NET_BIND_SERVICE`: право слушать порты ниже 1024.
* `CAP_SYS_TIME`: право изменять системное время.
* `CAP_CHOWN`: право менять владельца любых файлов.

Использование Capabilities позволяет запускать сервисы от имени обычного пользователя, выдавая им только строго необходимые привилегии ядра.

* **Подробнее:** [Linux Capabilities](../../Mechanisms/Capabilities.md).

### 3. Представление прав

Права можно представить в двух форматах, которые отображаются командой `ls -l`.

* **Символьное представление:** `-rwxrw-r--`
    Первый символ строки указывает на тип файла:
  * `-`: Обычный файл
  * `d`: Директория
  * `l`: Символическая ссылка
  * `c`: Символьное устройство
  * `b`: Блочное устройство
  * `p`: Именованный канал (pipe)
  * `s`: Сокет
  * `rwx` (Владелец): чтение, запись, выполнение.
  * `rw-` (Группа): чтение, запись.
  * `r--` (Остальные): только чтение.
* **Числовое (восьмеричное) представление:**

    | Число | Права | Описание |
    | :--- | :--- | :--- |
    | `7` | `rwx` | Полный доступ |
    | `6` | `rw-` | Чтение и запись |
    | `5` | `r-x` | Чтение и выполнение |
    | `4` | `r--` | Только чтение |
    | `2` | `-w-` | Только запись |
    | `1` | `--x` | Только выполнение |
    | `0` | `---` | Нет доступа |

    > **Пример:** Права `rwxr-xr--` в числовом виде будут `754`.

### 3. Маска прав по умолчанию (umask)

**Umask (User File-Creation Mask)** — это механизм, определяющий права доступа для новых файлов и директорий. При создании объекта ядро берет максимально возможные права (`666` для файлов, `777` для директорий) и вычитает из них (точнее, применяет побитовое И с инверсией маски) значение `umask`.

* **Зачем это нужно:** Обеспечение безопасности «из коробки» — чтобы новые файлы не были доступны всем пользователям системы без явного разрешения владельца.
* **Где настраивается:**
    * Глобально: `/etc/login.defs` (параметр `UMASK`), `/etc/profile`.
    * Персонально: `~/.bashrc` или `~/.profile`.
    * Через PAM: модуль `pam_umask.so`.

Практические примеры настройки и таблицу значений см. в **[Краткой справке по управлению правами](./permissions_management_quickref.md#настройка-umask)**.

## Практические сценарии

### Примеры использования chmod

**Команда chmod +x FILENAME**

Устанавливает бит **выполнения (execute)** для всех категорий пользователей (владелец, группа, остальные).

* **Для файла:** Делает файл исполняемым (скрипт, бинарный файл).
* **Для директории:** Позволяет входить в директорию и обращаться к её содержимому.

**Права 0750 (rwxr-x---)**

Восьмеричное представление прав доступа, где:

* `0`: Специальные биты (SUID/SGID/Sticky) не установлены.
* `7`: Владелец имеет полные права (`rwx`).
* `5`: Группа имеет права на чтение и выполнение (`r-x`).
* `0`: Остальные пользователи не имеют никаких прав (`---`).

**Контекст использования:**

* **Для файла:** Владелец может читать, изменять и запускать файл. Группа может читать и запускать (например, общий скрипт). Остальные не видят даже содержимого.
* **Для директории:** Владелец может всё (создавать/удалять файлы). Группа может входить (`x`) и просматривать список файлов (`r`), но не может создавать или удалять их. Остальные не могут даже войти в директорию.

### Диагностика: почему chmod 777 не всегда решает проблему

Установка прав `777` (полный доступ для всех) часто является первым шагом при возникновении ошибок доступа, но она не гарантирует решение проблемы. Если после `chmod 777` доступ всё ещё запрещён, причина часто кроется в механизмах, работающих поверх стандартной модели DAC (Discretionary Access Control).

#### 1. ACL перекрывает стандартные права

Списки контроля доступа (Access Control Lists, ACL) имеют приоритет над стандартными unix-правами. Если на файле установлен ACL, он может явно запрещать доступ конкретному пользователю, даже если `chmod` показывает `777`.

* **Признак:** Наличие символа `+` в выводе `ls -l` (например, `-rwxrwxrwx+`).
* **Диагностика:** `getfacl /path/to/file`
* **Решение:** Очистить все ACL командой `setfacl -b /path/to/file` или изменить конкретное правило.
* **Подробнее:** [ACL, атрибуты и временные метки](./acl_immutable_timestamps.md).

#### 2. SELinux или AppArmor блокируют доступ

Системы принудительного контроля доступа (Mandatory Access Control, MAC) могут запретить доступ на основе контекста безопасности (метки) или профиля приложения, игнорируя стандартные права.

* **Диагностика SELinux:**
  * Проверка логов аудита: `ausearch -m avc -ts recent` или `dmesg | grep denied`.
  * Проверка контекста файла: `ls -Z /path/to/file`.
  * Быстрая проверка: временно перевести SELinux в режим `permissive` командой `sudo setenforce 0`.
* **Диагностика AppArmor:**
  * Проверка статуса: `sudo aa-status`.
  * Проверка логов: `journalctl -fx | grep -i apparmor`.
* **Подробнее:** [SELinux](../../Mechanisms/SELinux.md), [AppArmor](../../Mechanisms/AppArmor.md).

#### 3. Проблема в иерархии директорий (Принцип проходимости)

Для доступа к файлу нужны права на выполнение (`x`) на **все** директории в пути. Если хотя бы одна родительская директория имеет права `700` и принадлежит другому пользователю, до вложенного файла невозможно "добраться", какие бы права ни стояли на нём самом.

* **Диагностика:** `namei -l /full/path/to/file` — показывает права на каждый элемент пути от корня до целевого объекта.
* **Подробнее:** [Принцип проходимости (бит x)](#типы-прав-какие-права).

#### 4. Процесс запущен от имени другого пользователя

Права на файл могут выглядеть верно, но процесс (например, веб-сервер) может работать не от того пользователя, которого вы ожидаете.

* **Диагностика:**
  * Узнать пользователя процесса: `ps aux | grep process_name`.
  * Проверить текущего пользователя: `id`.
* **Решение:** Убедиться, что пользователь процесса имеет доступ к файлу напрямую или через группу.

#### 5. Атрибут неизменяемости (Immutable)

Если на файл установлен атрибут `i` (immutable), его нельзя изменить или удалить даже пользователю `root` с правами `777`.

* **Диагностика:** `lsattr /path/to/file` (наличие буквы `i`).
* **Решение:** Снять атрибут командой `sudo chattr -i /path/to/file`.

#### 6. Файловая система примонтирована с опциями noexec, nosuid или nodev

Если раздел примонтирован с ограничивающими опциями, ядро блокирует определённые действия независимо от прав доступа (DAC).

* **noexec:** Запрещает прямой запуск исполняемых файлов. Часто применяется для `/tmp`, `/home`, `/var/tmp`.
  * **Диагностика:** `findmnt -T /path/to/file` — ищите `noexec` в колонке `OPTIONS`.
  * **Обход:** Запуск через интерпретатор (например, `python3 script.py`).
* **nosuid:** Игнорирует SUID/SGID биты на этом разделе. Полезно для защиты от эскалации привилегий через внешние носители.
  * **Диагностика:** Ошибка `Permission denied` или отсутствие повышения прав при запуске SUID-бинарника.
* **nodev:** Запрещает интерпретацию символьных и блочных устройств.
* **Подробнее:** [fstab и опции монтирования](../../../FileSystems/mounting/fstab.md), [специальные права (раздел безопасности)](./special_permissions.md#безопасное-монтирование-файловых-систем).

#### 7. NFS root_squash

При монтировании NFS-шары опция `root_squash` (включена по умолчанию) маппит запросы от `root` клиента в анонимного пользователя (`nobody:nogroup`). Если файл принадлежит `root` на сервере, а `nobody` не имеет прав на выполнение — возникает `Permission denied`.

* **Признак:** `exportfs -v` покажет активные опции экспорта, включая `root_squash`.
* **Диагностика:** Выполнить `sudo -u nobody <команда>` на сервере для проверки доступа.
* **Решение:** Изменить владельца или права файла для `nobody`, либо (небезопасно) добавить `no_root_squash` в `/etc/exports`.
* **Подробнее:** [NFS troubleshooting](../../../Networking/Services/nfs/nfs_troubleshooting.md), [NFS security](../../../Networking/Services/nfs/nfs_security.md).

#### 8. Неверный shebang (интерпретатор)

При запуске скрипта через `./script.sh` ядро читает первую строку (`#!`) и пытается вызвать указанный в ней интерпретатор. Если путь к интерпретатору указан неверно, он отсутствует в системе или файл сохранён в Windows-формате (`CRLF`) — возникает ошибка `No such file or directory` (или `bad interpreter`), которую иногда путают с проблемами прав доступа. Ошибка `Permission denied` при наличии бита `x` чаще указывает на `noexec` или блокировку со стороны MAC (SELinux/AppArmor).

* **Диагностика:**
  * `file script.sh` — покажет тип файла и путь к интерпретатору.
  * `head -1 script.sh | cat -A` — выявит лишние символы, например `^M` (CRLF) в конце строки.
  * `strace ./script.sh 2>&1 | head -n 20` — покажет системный вызов `execve` и причину отказа (например, `ENOENT`).
* **Решение:** Установить недостающий интерпретатор, исправить путь в shebang (использование `#!/usr/bin/env bash` повышает переносимость) или пересохранить файл в Unix-формате (`dos2unix script.sh`).
* **Подробнее:** [Выполнение скриптов в Bash](../../../Shell/bash_scripting_execution.md).

#### 9. Битая символическая ссылка (Broken Symlink)

Если файл является символической ссылкой, `ls -l` часто показывает права `lrwxrwxrwx`. Однако это права самой ссылки, а не целевого файла. Если целевой файл отсутствует, система выдаст ошибку `No such file or directory`. Если же целевой файл существует, но на него нет прав — `Permission denied`.

* **Диагностика:**
  * `readlink -f /path/to/file` — проверить, куда ведет ссылка и существует ли цель.
  * `ls -LH /path/to/file` — проверить права именно целевого файла (флаг `-L` разыменовывает ссылку).

#### 10. Файловая система только для чтения (Read-Only FS)

Если раздел примонтирован в режиме `ro` (read-only) или перешел в него автоматически из-за ошибок записи/сбоев оборудования, любые попытки записи в файл с правами `777` будут отклонены.

* **Диагностика:** `mount | grep " (ro,"` или `grep "[[:space:]]ro[[:space:],]" /proc/mounts`.
* **Решение:** Проверить логи ядра (`dmesg`) на предмет ошибок ФС, исправить их (`fsck`) и перемонтировать раздел в `rw`: `mount -o remount,rw /mount/point`.

#### 11. Скрытые символы или пробелы в имени файла

Ошибка доступа может быть вызвана тем, что вы пытаетесь открыть файл, имя которого отличается от визуально отображаемого (например, лишний пробел в конце `file.txt ` или непечатаемый символ).

* **Диагностика:**
  * `ls -b` — отображает непечатаемые символы в виде экранированных последовательностей.
  * `ls -Q` — заключает имена файлов в кавычки, что позволяет увидеть лишние пробелы.

#### 12. Пользовательские пространства имен (User Namespaces)

В контейнеризированных средах (Docker, Podman, LXC) UID внутри контейнера может не соответствовать UID на хосте. Если на хосте включен `userns-remap`, пользователь `root` внутри контейнера может быть смапплен в непривилегированного пользователя на хосте. В этом случае доступ к файлам хоста будет ограничен, несмотря на их "внешние" права.

* **Подробнее:** [User Namespaces в Docker](../../../Docker/Docker_security/host_daemon_hardening.md#2-настройка-user-namespaces-daemonjson).

#### Резюме: Чек-лист диагностики прав доступа

| Команда | Что проверяет |
| :--- | :--- |
| `namei -l /path/to/file` | Права на **все** директории по пути к файлу (принцип проходимости) |
| `getfacl <file>` | Наличие расширенных списков доступа (ACL) |
| `lsattr <file>` | Атрибуты файловой системы (например, `immutable`) |
| `lsattr -d <dir>` | Атрибуты родительской директории (препятствуют `w` операциям) |
| `ls -Z <file>` | Контекст безопасности SELinux |
| `ausearch -m avc -ts recent` | Последние отказы в доступе от SELinux |
| `aa-status` | Статус профилей AppArmor |
| `findmnt -T /path/to/file` | Опции монтирования (`noexec`, `nosuid`, `nodev`, `ro`) |
| `mount \| grep " (ro,"` | Проверка файловой системы на Read-Only режим |
| `readlink -f <file>` | Проверка целостности символической ссылки |
| `ls -bQ <file>` | Поиск скрытых символов или пробелов в имени |
| `exportfs -v` | Опция NFS `root_squash`, маппинг root в nobody |
| `head -1 script.sh \| cat -A` | Наличие CRLF (`^M`) или неверный путь в shebang |
| `strace ./script.sh 2>&1 \| tail -20` | Реальная ошибка при `execve` (ENOENT на интерпретатор) |
| `ps aux \| grep <name>` | От какого пользователя запущен процесс |
| `getcap <file>` | Наличие Linux Capabilities, перекрывающих стандартное поведение |

## Дополнительная информация

* **Inode:** Вся метаинформация о файле, включая права доступа, хранится в его [inode](../../../FileSystems/links_inodes_dentries.md#индексный-дескриптор-inode).
* **Связь с пользователями:** Система прав тесно связана с концепцией [управления пользователями и группами](../../../SystemAdministration/users_management.md).
* **Копирование файлов:** Утилита `cp` по умолчанию создаёт файлы с правами, определёнными `umask`. Для сохранения исходных прав и атрибутов используйте флаги `cp -p` или `cp -a`.
