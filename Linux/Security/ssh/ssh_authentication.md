# Аутентификация в SSH

Процесс аутентификации в SSH начинается после того, как клиент и сервер установили безопасный зашифрованный канал. Клиент должен доказать серверу, что у него есть право на доступ.

## Типы аутентификации

### Аутентификация по паролю

1.  Клиент запрашивает у пользователя пароль.
2.  Пароль отправляется на сервер **по уже зашифрованному каналу**.
3.  Сервер проверяет пароль и предоставляет доступ в случае успеха.
> **Примечание:** Этот метод менее безопасен и подвержен атакам перебора (brute-force). Рекомендуется отключать его на сервере.

### Опции клиента SSH для аутентификации

Иногда требуется явно указать клиенту SSH, какие методы аутентификации использовать или не использовать. Это делается с помощью флагов `-o` в команде `ssh`.

*   `-o PreferredAuthentications=password`: Указывает SSH отдавать предпочтение аутентификации по паролю.
*   `-o PubkeyAuthentication=no`: Явно отключает аутентификацию по открытому ключу.

### Аутентификация по SSH-ключу

Этот метод является более безопасным и предпочтительным. Он использует пару криптографических ключей: приватный и публичный.

1.  Клиент отправляет на сервер ID своего **публичного ключа**, которым он хочет аутентифицироваться.
2.  Сервер ищет этот ключ в файле `~/.ssh/authorized_keys` того пользователя, под которым происходит вход.
3.  Если ключ найден, сервер создает случайное сообщение (challenge), шифрует его этим **публичным ключом** и отправляет клиенту.
4.  Только владелец соответствующего **приватного ключа** может расшифровать это сообщение. Клиент расшифровывает его.
5.  Клиент вычисляет хеш из расшифрованного сообщения и ключа сессии, отправляя его обратно на сервер.
6.  Сервер выполняет те же вычисления и сравнивает результаты. Если они совпадают, это доказывает, что клиент владеет приватным ключом, и доступ предоставляется. **Приватный ключ при этом никогда не покидает клиентскую машину.**

С точки зрения криптографии, этот процесс основан на **асимметричном шифровании**, где для шифрования информации используется один ключ (публичный), а для расшифровки — другой (приватный). Главная особенность заключается в том, что из публичного ключа невозможно получить приватный, что делает систему очень безопасной.

**Аналогия с сундуком и ключами:**
Представьте, что у вас есть сундук с особым замком, который можно закрыть одним ключом (публичным), но открыть только другим (приватным).
*   **Публичный ключ** — это ключ, которым вы можете закрыть сундук. Вы можете раздать его всем желающим. Если кто-то хочет отправить вам секретное сообщение, он кладет его в сундук и закрывает вашим публичным ключом.
*   **Приватный ключ** — это ключ, которым вы можете открыть сундук. Этот ключ должен храниться в строжайшем секрете и никогда не передаваться никому. Только вы можете открыть сундук и прочитать сообщение.
В контексте SSH, сервер использует ваш публичный ключ для "закрытия" сообщения (шифрования), а ваш клиент использует ваш приватный ключ для "открытия" (расшифровки), доказывая, что он является законным владельцем.

## Работа с SSH-ключами

### Генерация SSH-ключей

Для аутентификации по ключу необходимо сгенерировать пару: публичный (`.pub`) и приватный.

```bash
# Рекомендуется использовать современный и безопасный алгоритм Ed25519
ssh-keygen -t ed25519 -C "your_email@example.com"
```
- `-t ed25519`: Указывает тип ключа.
- `-C "комментарий"`: Помогает идентифицировать ключ.
- **В процессе генерации:**
    - Вам будет предложено указать путь для сохранения ключей (по умолчанию `~/.ssh/id_ed25519`). Обычно можно оставить значение по умолчанию.
    - Затем будет предложено ввести **кодовую фразу (passphrase)**. Это дополнительный уровень безопасности для вашего приватного ключа. Если вы хотите использовать ключ в скриптах или для автоматизации без ввода пароля, оставьте кодовую фразу пустой (дважды нажмите Enter). В противном случае, каждый раз при использовании ключа потребуется вводить эту фразу.

### Управление ключами с помощью ssh-agent

`ssh-agent` — это фоновый процесс, который хранит приватные ключи в памяти и избавляет от необходимости вводить пароль от ключа при каждом подключении.

```bash
# Запуск агента в текущей сессии
eval "$(ssh-agent -s)"

# Добавление ключа в агент
ssh-add ~/.ssh/id_ed25519
```

### Копирование публичного ключа на сервер

Содержимое вашего **публичного** ключа (например, `~/.ssh/id_ed25519.pub`) необходимо добавить в файл `~/.ssh/authorized_keys` на сервере в домашней директории нужного пользователя.

**Автоматический способ (рекомендуется):**
```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server
```
> **Преимущества:** `ssh-copy-id` автоматически создает директорию `~/.ssh` на сервере (если ее нет), устанавливает правильные права доступа (700 для `~/.ssh` и 600 для `authorized_keys`) и добавляет публичный ключ в файл `authorized_keys`, избавляя от ручной настройки и потенциальных ошибок с правами.

**Ручной способ:**
```bash
# На сервере
mkdir -p ~/.ssh
# Вставьте сюда содержимое вашего .pub файла
nano ~/.ssh/authorized_keys
```

### Настройка прав доступа

Крайне важно установить правильные права доступа, иначе SSH-сервер может отказать в подключении из соображений безопасности.

**На клиенте:**
```bash
chmod 600 ~/.ssh/id_ed25519
```

**На сервере:**
```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```
