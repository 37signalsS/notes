# Аутентификация в SSH

## Определения

**Аутентификация в SSH** — это процесс, в ходе которого клиент доказывает серверу, что у него есть право на доступ. Этот этап наступает сразу после того, как между клиентом и сервером установлен безопасный зашифрованный канал.

Существует два основных типа аутентификации:

1. **Аутентификация по паролю:** Простой, но менее безопасный метод, основанный на отправке пароля пользователя по зашифрованному каналу.
2. **Аутентификация по публичному ключу:** Более безопасный и предпочтительный метод, использующий криптографическую пару ключей (приватный и публичный) для подтверждения личности клиента без передачи секретных данных по сети.

## Основные концепции

### Процесс аутентификации по паролю

1. Клиент запрашивает у пользователя пароль.
2. Пароль отправляется на сервер **по уже зашифрованному каналу**.
3. Сервер проверяет пароль и предоставляет доступ в случае успеха.

> **Примечание:** Этот метод уязвим для атак перебора (brute-force), поэтому его рекомендуется отключать на сервере в пользу аутентификации по ключу. См. директиву `PasswordAuthentication no` в [настройках безопасности сервера](./ssh_server_security.md).

### Процесс аутентификации по публичному ключу

Этот метод основан на принципах **асимметричного шифрования**, где для шифрования информации используется один ключ (публичный), а для расшифровки — другой (приватный). Главная особенность заключается в том, что из публичного ключа невозможно получить приватный, что делает систему очень безопасной.

1. Клиент отправляет на сервер идентификатор (ID) своего **публичного ключа**, который он намеревается использовать.
2. Сервер ищет этот публичный ключ в файле `~/.ssh/authorized_keys` в домашнем каталоге пользователя, под которым осуществляется вход.
3. Если ключ найден, сервер создает случайное сообщение (challenge), шифрует его **публичным ключом** клиента и отправляет обратно.
4. Клиент, получив зашифрованное сообщение, использует свой **приватный ключ** для его расшифровки. Это может сделать только владелец соответствующего приватного ключа.
5. Клиент вычисляет хеш из расшифрованного сообщения и отправляет его на сервер.
6. Сервер выполняет те же вычисления и сравнивает результаты. Их совпадение доказывает, что клиент владеет приватным ключом, и доступ предоставляется. **При этом сам приватный ключ никогда не покидает клиентскую машину.**

## Практические сценарии

### Генерация SSH-ключей

Для использования аутентификации по ключу сначала необходимо сгенерировать пару: приватный и публичный (`.pub`) ключи.

```bash
# Рекомендуется использовать современный и безопасный алгоритм Ed25519
ssh-keygen -t ed25519 -C "your_email@example.com"
```

- `-t ed25519`: Указывает тип создаваемого ключа.
- `-C "комментарий"`: Метка, которая помогает идентифицировать ключ (часто используют email).

### Копирование публичного ключа на сервер

Чтобы разрешить вход, содержимое **публичного** ключа (`~/.ssh/id_ed25519.pub`) нужно добавить в файл `~/.ssh/authorized_keys` на сервере.

**Автоматический способ (рекомендуется):**
Утилита `ssh-copy-id` автоматически выполняет все необходимые шаги, включая создание каталогов, установку правильных прав доступа и  добавляет публичный ключ в файл `authorized_keys`.

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server
```

**Ручной способ:**

1. Скопируйте содержимое вашего `.pub` файла.
2. Подключитесь к серверу и добавьте скопированный текст в конец файла `~/.ssh/authorized_keys`:

    ```bash
    # На сервере
    mkdir -p ~/.ssh
    echo "СОДЕРЖИМОЕ_ПУБЛИЧНОГО_КЛЮЧА" >> ~/.ssh/authorized_keys
    ```

> **Важно:** Корректные права доступа к файлам и каталогам критически важны. SSH-сервер не позволит аутентифицироваться по ключу, если права слишком разрешающие. Подробное руководство находится в заметке о [безопасности сервера SSH](./ssh_server_security.md#проверка-и-установка-прав-доступа).

## Дополнительная информация

### Защита приватного ключа кодовой фразой (Passphrase)

В процессе генерации ключа `ssh-keygen` предлагает установить **кодовую фразу (passphrase)**. Это дополнительный слой защиты: даже если ваш приватный ключ будет украден, злоумышленник не сможет им воспользоваться, не зная этой фразы. Приватный ключ хранится на диске в зашифрованном виде.

- **Для интерактивных сессий:** Всегда задавайте кодовую фразу.
- **Для автоматизации:** Если ключ используется в скриптах, кодовую фразу можно оставить пустой.

### Управление ключами с помощью `ssh-agent`

Чтобы не вводить кодовую фразу при каждом подключении, используется `ssh-agent` — фоновый процесс, который кеширует расшифрованные приватные ключи в памяти.

```bash
# Запуск агента в текущей сессии
eval "$(ssh-agent -s)"

# Добавление ключа в агент (потребуется ввести кодовую фразу один раз)
ssh-add ~/.ssh/id_ed25519
```

После этого все последующие `ssh` команды в этой сессии будут автоматически использовать ключ из агента без запроса кодовой фразы.
