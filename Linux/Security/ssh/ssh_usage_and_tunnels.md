# Практическое использование SSH

## Определения

**SSH-туннелирование (проброс портов, Port Forwarding)** — это механизм создания зашифрованного канала (туннеля) между локальной и удаленной машиной, через который можно безопасно перенаправлять сетевой трафик произвольных TCP-сервисов.

**X11 Forwarding (проброс X11)** — это технология, позволяющая запускать графические (GUI) приложения на удаленном сервере и отображать их окна на локальном рабочем столе.

**Agent Forwarding (проброс агента)** — это функция SSH, которая позволяет использовать локальный `ssh-agent` для аутентификации на последующих серверах в цепочке, избавляя от необходимости хранить приватные ключи на промежуточных узлах.

**Jump Host (узел-бастион)** — это специально защищенный сервер, который выступает в роли единой точки входа во внутреннюю, изолированную сеть. Доступ к внутренним ресурсам осуществляется "прыжком" через этот узел.

## Основные концепции

### Инкапсуляция трафика

Ключевая идея туннелирования заключается в "обертывании" (инкапсуляции) трафика другого протокола (например, HTTP, VNC или запросов к базе данных) в зашифрованное SSH-соединение. Это позволяет безопасно работать с сервисами, которые сами по себе не поддерживают шифрование, или получать доступ к ресурсам в закрытых сетях.

### Безопасность при многоступенчатых подключениях

При работе с несколькими серверами подряд (например, `локальная машина → сервер A → сервер B`) возникает задача аутентификации на каждом шаге.

- **Проброс агента (`-A`)** решает эту задачу, "одалживая" аутентификационные данные с вашей локальной машины промежуточному серверу. Это удобно, но **создает риск безопасности**: если промежуточный узел скомпрометирован, злоумышленник может использовать сокет вашего агента для доступа к другим системам.
- **Jump Host (`-J` или `ProxyJump`)** является более безопасной альтернативой. Он просто "пробрасывает" TCP-соединение, не получая доступа к данным сессии. Промежуточный узел выступает лишь в роли транспортного посредника.

## Практические сценарии

### Базовое подключение

**Стандартная команда подключения:**
```bash
ssh user@host
```

Здесь `user` — это имя пользователя на удаленном сервере, а `host` — это IP-адрес или доменное имя сервера. При первом подключении система попросит подтвердить отпечаток ключа сервера.

**Подключение с указанием порта:**
```bash
ssh -p 2222 user@host
```

**Подключение с явным указанием ключа:**
```bash
ssh -i ~/.ssh/id_ed25519_project user@host
```

**Важные замечания:**
- Если имя пользователя не указано, SSH использует имя текущего локального пользователя
- При первом подключении к хосту потребуется подтвердить отпечаток ключа — **всегда выполняйте первое подключение вручную** перед использованием в автоматизации (cron, скрипты)
- Если ключ хоста изменился (переустановка сервера), SSH заблокирует подключение с предупреждением о возможной MITM-атаке. Удалите старую запись командой `ssh-keygen -R <host>` и подключитесь заново

### Удалённое выполнение команд

```bash
# Простая команда
ssh user@server "ls -l /var/www"

# Для интерактивных команд (top, htop) требуется псевдо-терминал (-t)
ssh -t user@server "top"
```

### Передача файлов и работа с файловой системой

Для обзора утилит, предназначенных для передачи файлов и интерактивного управления сессиями (`scp`, `rsync`, `sshfs`, `lazyssh`), обратитесь к основному руководству: **[Инструменты командной строки SSH](./ssh_cli_tools.md)**.

### Проброс портов (Туннелирование)

- **Локальный проброс (`-L`):** Доступ к удаленному сервису через локальный порт.
  *Сценарий: Доступ к базе данных `db.internal:5432`, доступной только с машины `gateway`.*

  ```bash
  ssh -L 5433:db.internal:5432 user@gateway
  ```

  Теперь подключение к `localhost:5433` на вашей машине будет перенаправлено на `db.internal:5432`.

- **Удаленный проброс (`-R`):** Предоставление доступа к локальному сервису через порт на удаленном сервере.
  *Сценарий: Показать коллеге веб-приложение, работающее на `localhost:3000`.*

  ```bash
  ssh -R 8080:localhost:3000 user@public_server
  ```

  Теперь подключение к `public_server:8080` будет перенаправлено на ваш `localhost:3000`.

- **Динамический проброс (`-D`):** Создание SOCKS-прокси.
  *Сценарий: Безопасный веб-серфинг через `server`.*

  ```bash
  ssh -D 8080 user@server
  ```

  Настроив браузер на использование SOCKS5-прокси `localhost:8080`, весь его трафик пойдет через `server`.

### Проброс графического интерфейса (X11 Forwarding)

Запуск GUI-приложений с удаленного сервера с отображением на локальной машине.

```bash
# Подключиться с флагом -X (или -Y для "доверенного" проброса)
ssh -X user@server

# После подключения запустить GUI-приложение
gedit .bashrc
```

> **Важно:** Проброс X11 **не рекомендуется** для серверов. Графический интерфейс на сервере обычно не нужен, а проброс X11 может создавать дополнительные риски безопасности, особенно если удалённая система скомпрометирована. Используйте только при реальной необходимости.

### Безопасное подключение через промежуточные хосты

- **Agent Forwarding (`-A`):** Удобно, но менее безопасно.

  ```bash
  # Подключаемся к первому серверу с пробросом агента
  ssh -A user@server1

  # С него подключаемся ко второму, используя ключ с локальной машины
  ssh user@server2
  ```

- **Jump Host (`-J`):** Рекомендуемый, безопасный способ.

  ```bash
  # Прямая команда
  ssh -J user@jump_host user@internal_server

  # Более удобная настройка через ~/.ssh/config:
  ```

  ```ini
  Host internal_server
    HostName 10.0.0.5
    User app_user
    ProxyJump jump_user@jump.example.com
  ```

  Подробные инструкции находятся в [руководстве по конфигурации клиента SSH](./ssh_client_config.md#настройка-подключения-через-jump-host-proxyjump).

- **Альтернатива на сетевом уровне (iptables DNAT):** Если требуется производительность или постоянный доступ, можно использовать проброс портов через iptables на промежуточном сервере. См. [Проброс SSH через iptables](../../Networking/Concepts/nat.md#проброс-ssh-через-iptables-альтернатива-ssh-proxyjump).

## Дополнительная информация

### Рекомендации по безопасности

- **`ProxyJump` > `Agent Forwarding`:** Всегда предпочитайте использование `ProxyJump` (`-J`) вместо проброса агента (`-A`), если только вам не требуется использовать локальный ключ на нескольких машинах в цепочке вручную.
- **X11 Forwarding:** Включайте проброс X11 только при необходимости, так как он может создавать дополнительные риски безопасности, если удаленная система скомпрометирована.
