# Безопасность SSH-сервера (sshd)

## 1. Определения

**Безопасность SSH-сервера** — это комплекс мер, направленных на защиту службы `sshd` (SSH daemon) от несанкционированного доступа, атак и других угроз. `sshd` является основной службой для удаленного управления системами на базе Linux, что делает её критически важной целью для злоумышленников. Правильная настройка `sshd` является фундаментальным аспектом обеспечения безопасности всей системы.

## 2. Основные концепции

### 2.1. Файл конфигурации `/etc/ssh/sshd_config`

Это главный файл, определяющий поведение SSH-сервера. Ниже приведены ключевые директивы безопасности.

-   **Отключение аутентификации по паролю:**
        -   `PasswordAuthentication no`: **(Критически важно)** Отключает аутентификацию по паролю, разрешая только более безопасный [вход по ключам](./ssh_authentication.md). Перед включением убедитесь, что доступ по ключам настроен.
    -   **Запрет входа для `root`:**
        -   `PermitRootLogin no`: Полностью запрещает прямой вход от имени `root`. Это заставляет злоумышленника сначала получить доступ к учетной записи обычного пользователя, а затем повышать привилегии.
        -   `PermitRootLogin yes`: **(КРАЙНЕ НЕБЕЗОПАСНО!)** Разрешает прямой вход для `root` по паролю или ключу. **Настоятельно не рекомендуется для production-систем.** Использовать только в крайних случаях и только с аутентификацией по ключу, предварительно убедившись, что другой доступ к системе невозможен.
        -   `prohibit-password`: Альтернативный вариант, который разрешает вход `root` только по SSH-ключу. Менее безопасен, чем `no`.
    -   **Ограничение попыток входа:**
        -   `MaxAuthTries 3`: Уменьшает количество попыток аутентификации, что замедляет атаки перебора (brute-force).
    -   **Смена стандартного порта:**
        -   `Port 22`: По умолчанию SSH слушает порт `22`. **Настоятельно рекомендуется изменить стандартный порт** на нестандартный (например, `15134`, `2239`), чтобы уменьшить количество автоматизированных атак от ботов.
    -   **Другие важные директивы:**    -   `PermitEmptyPasswords no`: Запрещает вход с пустыми паролями.
    -   `PubkeyAuthentication yes`: Убеждается, что аутентификация по ключам включена.
    -   `ChallengeResponseAuthentication no`: Отключает интерактивные методы аутентификации "вызов-ответ".
    -   `GSSAPIAuthentication no`, `KerberosAuthentication no`: Отключает аутентификацию через Kerberos/GSSAPI, если она не используется, для уменьшения векторов атак.

### 2.2. Контроль прав доступа

Для безопасной работы SSH требует строгих прав на файлы и каталоги. Неправильные разрешения могут привести к отказу в аутентификации по ключу.

-   **Общее правило:** Конфиденциальные файлы (приватные ключи) должны быть доступны для чтения и записи только их владельцу (`600`), а содержащие их каталоги — только для просмотра и изменения владельцем (`700`).

| Путь                                  | Права | Владелец       | Описание                                                                                                                                                                                                           |
| ------------------------------------- | ----- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `~/.ssh` (на клиенте и сервере)       | `700` | Пользователь   | Каталог с конфигурацией и ключами.                                                                                                                                                                                 |
| `~/.ssh/authorized_keys` (на сервере) | `600` | Пользователь   | Файл с публичными ключами, которым разрешен доступ.                                                                                                                                                                |
| `~/.ssh/id_*` (на клиенте)            | `600` | Пользователь   | Приватные ключи пользователя. **Их утечка компрометирует доступ!**                                                                                                                                                   |
| `~/.ssh/id_*.pub` (на клиенте)        | `644` | Пользователь   | Публичные ключи, не содержат секретной информации.                                                                                                                                                                 |
| `~/.ssh/config` (на клиенте)          | `600` | Пользователь   | Файл конфигурации клиента SSH.                                                                                                                                                                                     |
| `/etc/ssh/ssh_host_*_key` (на сервере) | `600` | `root:root`    | Приватные ключи хоста.                                                                                                                                                                                             |
| `/etc/ssh/ssh_host_*_key.pub` (на сервере)|`644`| `root:root`    | Публичные ключи хоста.                                                                                                                                                                                             |

> **Важно:** Если права на `~/.ssh` или `~/.ssh/authorized_keys` слишком открыты (например, `775` или `664`), `sshd` отклонит аутентификацию по ключу, записав в лог ошибку, например: `Authentication refused: bad ownership or modes for directory /home/user/.ssh`.

### 2.3. Ограничение доступа пользователей

Рекомендуется использовать "белый список" (whitelist), явно разрешая доступ только определённым пользователям или группам.

-   `AllowUsers user1 user2@host`: Разрешает вход только указанным пользователям. Можно ограничить доступ по IP или хосту.
-   `AllowGroups sshusers`: Разрешает вход только пользователям, входящим в группу `sshusers`.

**Важно:** Директивы `Allow` имеют приоритет над `Deny`. Рекомендуется использовать только `AllowUsers` или `AllowGroups`, чтобы избежать путаницы.

### 2.4. Логирование и криминалистика

Анализ логов — ключевой элемент для выявления атак и расследования инцидентов.

-   `/var/log/auth.log` (Debian/Ubuntu) или `/var/log/secure` (CentOS/RHEL): Основной лог аутентификации.
-   `/var/log/wtmp`: Журнал успешных входов, выходов и перезагрузок.
-   `/var/log/btmp`: Журнал неудачных попыток входа (ключевой для выявления brute-force атак).
-   `/var/log/lastlog`: Информация о последнем входе каждого пользователя.

### 2.5. Ограничение доступа по IP-адресу (TCP Wrappers)

Использование `hosts.allow` и `hosts.deny` позволяет контролировать доступ к сетевым службам (включая `sshd`) на основе IP-адреса клиента. Этот механизм известен как TCP Wrappers.

#### Принцип работы
Когда клиент пытается подключиться к службе, настроенной с использованием TCP Wrappers, демон `sshd` (или другая служба) проверяет файлы `/etc/hosts.allow` и `/etc/hosts.deny`.
1.  **`/etc/hosts.allow`**: Проверяется первым. Если найдено соответствующее правило, доступ разрешается, и дальнейшая проверка не производится.
2.  **`/etc/hosts.deny`**: Если правило не найдено в `hosts.allow`, проверяется `hosts.deny`. Если найдено соответствующее правило, доступ запрещается.
3.  **Нет правил**: Если правила не найдены ни в одном из файлов, доступ по умолчанию разрешается.

#### Настройка для `sshd`
Для ограничения доступа к `sshd` используйте следующие правила:

**Разрешить доступ с определенных IP-адресов:**
Добавьте в `/etc/hosts.allow`:
```ini
sshd: 192.168.1.100 192.168.1.101
```
Это разрешит подключение только с IP-адресов `192.168.1.100` и `192.168.1.101`.

**Запретить доступ со всех остальных IP-адресов:**
Добавьте в `/etc/hosts.deny`:
```ini
sshd: ALL
```
В комбинации эти правила означают "разрешить SSH только с 192.168.1.100 и 192.168.1.101, а всем остальным запретить".

**Важно:**
*   После изменения файлов `hosts.allow` или `hosts.deny` **не требуется перезапускать `sshd`**. Изменения применяются немедленно.
*   Убедитесь, что правила не блокируют ваш собственный доступ к серверу.
*   Этот метод является базовым и не заменяет полноценный файрвол (`iptables`, `nftables`, `ufw`).
*   В случае конфликта (правило разрешает в `hosts.allow`, но запрещает в `hosts.deny`), правило из `hosts.allow` имеет приоритет.

## 3. Практические сценарии

### 3.1. Настройка резервного SSH-доступа

Чтобы не потерять доступ к серверу после сбоя `firewall` или `NetworkManager`, можно настроить резервный экземпляр `sshd` на другом порту.

1.  **Создайте копию конфигурации:**
    ```bash
    sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config_alt
    ```
2.  **Отредактируйте `/etc/ssh/sshd_config_alt`:**
    ```ini
    Port 2222
    ListenAddress 192.168.100.10  # IP-адрес на интерфейсе управления
    PidFile /run/sshd-alt.pid
    # Убедитесь, что остальные настройки (например, PasswordAuthentication) безопасны
    ```
3.  **Запустите второй экземпляр:**
    -   **Вручную:** `sudo /usr/sbin/sshd -f /etc/ssh/sshd_config_alt`
    -   **Через `systemd` (рекомендуется):** `sudo systemctl start sshd@alt.service` и `sudo systemctl enable sshd@alt.service` (может потребовать создания unit-файла).

### 3.2. Расширенное логирование SFTP

Для отслеживания файловых операций через SFTP измените директиву `Subsystem` в `/etc/ssh/sshd_config`:

```ini
Subsystem sftp /usr/lib/openssh/sftp-server -f AUTHPRIV -l INFO
```

### 3.3. Изменение порта SSH при включенном SELinux

Простое изменение порта в `sshd_config` на системе с SELinux приведет к ошибке запуска службы.

1.  **Измените порт** в `/etc/ssh/sshd_config` (например, на `5022`).
2.  **Сообщите SELinux** о новом разрешенном порте для `sshd`:
    ```bash
    sudo semanage port -a -t ssh_port_t -p tcp 5022
    ```
3.  **Перезапустите `sshd`:** `sudo systemctl restart sshd`.

### 3.4. Отладка проблем с `sshd`

-   **Запуск в отладочном режиме:** Для быстрой диагностики можно запустить `sshd` на временном порту в режиме отладки. Он не будет отсоединяться от консоли и выведет всю отладочную информацию.
    ```bash
    # На сервере
    sudo /usr/sbin/sshd -d -p 2222
    
    # С клиента
    ssh user@host -p 2222 -v
    ```
-   **Проверка конфигурации:** Перед перезапуском сервиса всегда проверяйте синтаксис файла конфигурации:
    ```bash
    sudo sshd -t
    ```

### 3.5. Ошибка "True/False" в `sshd_config` при использовании Ansible

При генерации `sshd_config` из шаблона Ansible (`.j2`) может возникнуть проблема: YAML-парсер Ansible преобразует строковые `"yes"` и `"no"` в булевы `True` и `False`, что делает конфигурацию невалидной для `sshd`.

-   **Проблема:**
    ```yaml
    # vars.yml
    sshd_permit_root_login: "yes"
    ```
    ```jinja2
    # sshd_config.j2
    PermitRootLogin {{ sshd_permit_root_login }}
    ```
    **Результат в файле:** `PermitRootLogin True` (неверно).

-   **Решение 1 (кавычки в шаблоне):**
    ```jinja2
    PermitRootLogin "{{ sshd_permit_root_login }}"
    ```
-   **Решение 2 (логика в шаблоне):**
    ```jinja2
    PermitRootLogin {% if sshd_permit_root_login %}yes{% else %}no{% endif %}
    ```

## 4. Дополнительная информация

### 4.1. Инструменты для защиты от атак

-   **[Fail2Ban](./../Tools/fail2ban_overview.md):** Утилита, которая анализирует логи и автоматически блокирует IP-адреса, с которых ведутся [атаки перебора (brute-force)](../../Concepts/brute_force_attacks.md).
-   **Endlessh:** SSH-ловушка ("tarpit"), которая "замораживает" ботов, бесконечно отправляя им SSH-баннер, но не завершая соединение. [GitHub-репозиторий](https://github.com/skeeto/endlessh).

### 4.2. Инструменты для аудита безопасности

-   **`ssh-audit`:** Инструмент командной строки для аудита конфигурации SSH-сервера и клиента. Проверяет используемые алгоритмы, выявляет уязвимости и дает рекомендации. [GitHub-репозиторий](https://github.com/jtesta/ssh-audit).

### 4.3. Сокрытие SSH-сервера с помощью Port Knocking

**Port Knocking** — это метод защиты SSH-сервера, при котором порт SSH (обычно 22 или измененный на нестандартный) изначально закрыт файрволом и становится доступным только после того, как клиент инициирует правильную последовательность соединений ("стуков") к заранее определенным "закрытым" портам. Это помогает скрыть SSH-сервис от автоматических сканирований портов и брутфорс-атак, делая его невидимым до выполнения "стука".

#### Определения

*   **`knockd`**: Демон, который мониторит сетевой трафик и, при обнаружении предопределенной последовательности "стуков", динамически модифицирует правила файрвола (например, `iptables`) для временного открытия SSH-порта для IP-адреса клиента.

#### Основные концепции

1.  **Невидимость SSH**: Порт SSH по умолчанию закрыт файрволом, что предотвращает его обнаружение при обычном сканировании портов.
2.  **Последовательность "стуков"**: Клиент отправляет TCP- или UDP-пакеты на заданную последовательность портов, которые также должны быть закрыты.
3.  **Динамическое открытие**: `knockd` распознает правильную последовательность и временно открывает SSH-порт только для IP-адреса клиента.
4.  **Автоматическое закрытие**: Через заданный промежуток времени или по обратной последовательности "стуков" порт SSH снова закрывается.

#### Практический сценарий: Настройка Port Knocking для SSH

Рассмотрим настройку `knockd` для открытия/закрытия SSH-порта (например, 2239) на сетевом интерфейсе `enp3s0`.

**Настройка сервера:**

1.  **Установите `knockd` и `iptables-persistent` (для сохранения правил файрвола после перезагрузки):**
    ```bash
    sudo apt install knockd iptables-persistent
    ```

2.  **Настройте `iptables` для закрытия SSH-порта по умолчанию:**
    Убедитесь, что ваш SSH-порт (например, 2239) изначально закрыт для всех входящих соединений.
    ```bash
    sudo iptables -A INPUT -p tcp --dport 2239 -j REJECT --reject-with tcp-reset
    # Сохраните правила iptables, чтобы они применялись после перезагрузки
    sudo netfilter-persistent save
    ```

3.  **Настройте `knockd` в файле `/etc/knockd.conf`:**
    ```ini
    [options]
        logfile = /var/log/knockd.log
        interface = enp3s0 # Замените на имя вашего сетевого интерфейса (например, eth0)

    [openSSH]
        sequence = 7000,8000,9000     # Последовательность портов для открытия SSH
        seq_timeout = 5               # Максимальный таймаут между "стуками"
        command = /usr/sbin/iptables -I INPUT -s %IP% -p tcp --dport 2239 -j ACCEPT
        tcpflags = syn                # Ожидать только SYN-пакеты

    [closeSSH]
        sequence = 9000,8000,7000     # Последовательность портов для закрытия SSH
        seq_timeout = 5
        command = /usr/sbin/iptables -D INPUT -s %IP% -p tcp --dport 2239 -j ACCEPT
        tcpflags = syn
    ```
    *   `%IP%`: Переменная, автоматически заменяемая на IP-адрес клиента, успешно выполнившего последовательность "стуков".
    *   `iptables -I INPUT`: Вставляет правило в начало цепочки `INPUT`, что обеспечивает его приоритет.
    *   `iptables -D INPUT`: Удаляет ранее добавленное правило.

4.  **Включите `knockd` в файле `/etc/default/knockd`:**
    Измените `START_KNOCKD=0` на `START_KNOCKD=1`.

5.  **Запустите `knockd`:**
    ```bash
    sudo systemctl enable --now knockd
    sudo systemctl status knockd
    ```

**Использование на клиенте:**

1.  **Установите `knock` утилиту:**
    ```bash
    sudo apt install knock
    ```

2.  **Выполните "стук" для открытия SSH-порта:**
    ```bash
    knock <IP_адрес_сервера> 7000 8000 9000
    ```
    После успешного "стука" вы сможете подключиться по SSH:
    ```bash
    ssh user@<IP_адрес_сервера> -p 2239
    ```
    Альтернативно, можно использовать `netcat` (nc) для "стуков" (по одному на каждый порт):
    ```bash
    nc -zvw1 <IP_адрес_сервера> 7000
    nc -zvw1 <IP_адрес_сервера> 8000
    nc -zvw1 <IP_адрес_сервера> 9000
    ```

3.  **Выполните "стук" для закрытия SSH-порта (после завершения работы):**
    ```bash
    knock <IP_адрес_сервера> 9000 8000 7000
    ```

#### Дополнительные рекомендации

*   **Таймаут автоматического закрытия**: В `knockd.conf` можно добавить `cmd_timeout = 10` (в секции `[openSSH]`), чтобы правило `ACCEPT` автоматически удалялось через 10 секунд. Это повышает безопасность, гарантируя, что порт не останется открытым бесконечно.
*   **Безопасность**: Port Knocking не заменяет надежную аутентификацию (например, по SSH-ключам) или полноценный файрвол. Это дополнительный механизм обфускации, который снижает вероятность обнаружения SSH-сервиса автоматическими ботами.
*   **Ограничения NAT**: Использование Port Knocking может быть затруднено, если клиент находится за NAT, так как его исходящий IP-адрес может быть непредсказуем или изменяться.
