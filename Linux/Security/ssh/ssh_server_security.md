# Безопасность сервера SSH

## Рекомендации по настройке `/etc/ssh/sshd_config`

Для повышения безопасности SSH-сервера рекомендуется внести следующие изменения в конфигурационный файл `/etc/ssh/sshd_config`:

- `Port 22`: **Измените стандартный порт на другой** (значение должно быть больше 1024, например, `Port 15134`). Это значительно снижает количество автоматических атак от ботов, которые по умолчанию сканируют 22-й порт. Перенос SSH на нестандартный порт не является полноценной защитой, но существенно уменьшает "шум" в логах и количество попыток подбора.
- `PermitRootLogin no`: **Запретите прямой вход от имени `root`**. Пользователь `root` существует на каждой Linux-системе, что делает его легкой мишенью для атак. Отключение прямого входа для `root` вынуждает злоумышленника сначала подобрать логин обычного пользователя, а затем повышать привилегии, что усложняет атаку.
  - `prohibit-password`: Эта опция запрещает вход по паролю под пользователем `root`, но разрешает ему вход по ssh-ключу, если он добавлен в `/root/.ssh/authorized_keys`.
  - `no`: Эта опция полностью запрещает вход под пользователем `root` как по паролю, так и по ssh-ключу. **Рекомендуется использовать `no` для максимальной безопасности.**
- `PermitEmptyPasswords no`: Запрещает вход пользователям с пустыми паролями. Значение по умолчанию (`no`) является безопасным и должно быть сохранено.
- `PasswordAuthentication no`: **(Критически важно)** Отключите аутентификацию по паролю, оставив только более надежный вход по ключам. **Перед отключением убедитесь, что вход по SSH-ключам настроен и работает корректно, иначе вы можете потерять доступ к серверу!**
- `PubkeyAuthentication yes`: Убедитесь, что аутентификация по ключам включена. Это основной и наиболее безопасный метод аутентификации.
- `MaxAuthTries 3`: Ограничивает количество попыток аутентификации по паролю (если `PasswordAuthentication` не `no`) до 3. Это помогает предотвратить брутфорс-атаки, хотя полное отключение парольной аутентификации является более эффективной мерой.
- `AllowUsers user1 user2@host`: Позволяет явно указать, каким пользователям разрешен вход. Можно указать пользователя и хост, с которого разрешен вход. Используйте для создания "белого списка" пользователей.
- `AllowGroups group1 group2`: Позволяет явно указать, пользователям из каких групп разрешен вход. Используйте для создания "белого списка" групп.

**Общая рекомендация по безопасности:**
Отключайте все методы аутентификации и функции SSH, которые вы не используете (например, `GSSAPIAuthentication`, `KerberosAuthentication`, `ChallengeResponseAuthentication` и т.д.). Чем меньше открытых векторов для атак, тем безопаснее система.

После внесения изменений перезапустите SSH-сервис:
```bash
sudo systemctl restart sshd
```

### Проверка и установка прав доступа

Для безопасной работы SSH-сервер требует строгого соблюдения прав доступа к файлам и каталогам, связанным с SSH. Неправильные разрешения могут привести к тому, что сервер отклонит подключение по ключу, чтобы предотвратить потенциальные уязвимости (например, если приватный ключ или список авторизованных ключей доступны для изменения другим пользователям).

**Общее правило:** Конфиденциальные файлы (приватные ключи) должны быть доступны для чтения и записи только их владельцу (`600`), а каталоги, в которых они хранятся, — только для просмотра и изменения владельцем (`700`).

**На сервере:**
-   Домашний каталог пользователя (`/home/user`): Не должен быть доступен для записи другим пользователям. `755` или `750` являются стандартными.
-   Каталог `.ssh` (`~/.ssh`): Должен принадлежать пользователю и иметь права `700` (только владелец имеет полный доступ).
    ```bash
    chmod 700 ~/.ssh
    ```
-   Файл авторизованных ключей (`~/.ssh/authorized_keys`): Должен иметь права `600` (только владелец может читать и писать).
    ```bash
    chmod 600 ~/.ssh/authorized_keys
    ```
-   Ключи хоста (`/etc/ssh/ssh_host_*_key`): Приватные ключи хоста должны быть доступны для чтения только группе `root` или `ssh_keys` и иметь права `640` или `600`.

**На клиенте:**
-   Каталог `.ssh` (`~/.ssh`): Права `700`.
    ```bash
    chmod 700 ~/.ssh
    ```
-   Файл конфигурации (`~/.ssh/config`): Рекомендуются права `600`.
    ```bash
    chmod 600 ~/.ssh/config
    ```
-   Приватные ключи (`~/.ssh/id_*`): Должны иметь строгие права `600`.
    ```bash
    chmod 600 ~/.ssh/id_*
    ```
-   Публичные ключи (`~/.ssh/id_*.pub`): Не содержат секретной информации и могут иметь более свободные права, например `644`.

> **Важно:** Если права на сервере на `~/.ssh` или `~/.ssh/authorized_keys` будут слишком открытыми (например, `775` или `664`), `sshd` отклонит аутентификацию по ключу с сообщением об ошибке в логах сервера, например: `Authentication refused: bad ownership or modes for directory /home/user/.ssh`.

### Настройка логирования SFTP

По умолчанию SFTP-сервер (который является подсистемой SSH) может не предоставлять достаточно детализированных логов. Для улучшения логирования SFTP-операций (скачивание/загрузка файлов) можно добавить или изменить директиву `Subsystem sftp` в `/etc/ssh/sshd_config` следующим образом:

```ini
Subsystem sftp /usr/lib/openssh/sftp-server -f AUTHPRIV -l INFO
```
- `-f AUTHPRIV`: Указывает syslog-facility для логов (по умолчанию используется `AUTH`).
- `-l INFO`: Устанавливает уровень логирования на `INFO`, что обычно достаточно для отслеживания основных операций.
После изменения не забудьте перезапустить службу `sshd`.

### Резервный SSH-доступ для аварийных ситуаций

Бывают ситуации, когда после обновления `firewall` или `NetworkManager` основной SSH-доступ перестает работать. Чтобы не остаться без доступа к серверу, можно заранее настроить резервный `sshd` на другом порту и, возможно, на другом IP-адресе (сетевом интерфейсе).

**1. Создание резервной конфигурации**

Скопируйте существующий конфигурационный файл `sshd` для создания альтернативной версии:
```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config_alt
```

**2. Редактирование резервной конфигурации**

Откройте `/etc/ssh/sshd_config_alt` и измените ключевые параметры, чтобы избежать конфликтов с основным экземпляром `sshd`:
```ini
# Укажите другой порт
Port 2222

# Прослушивайте только определенный IP-адрес (например, адрес на интерфейсе управления)
ListenAddress 192.168.100.10

# Укажите другой файл для PID процесса
PidFile /run/sshd-alt.pid

# Можно также указать отдельные ключи хоста, если это необходимо
# HostKey /etc/ssh/ssh_host_rsa_key_alt
```
*   **Важно:** Выбирайте `ListenAddress`, который не затрагивается вашими основными сетевыми правилами или изменениями.

**3. Запуск второго экземпляра sshd**

Вы можете запустить его вручную или настроить как службу `systemd`.

*   **Вручную:**
    ```bash
    sudo /usr/sbin/sshd -f /etc/ssh/sshd_config_alt
    ```
    Эта команда запустит новый процесс `sshd` с использованием альтернативного конфигурационного файла.

*   **Через `systemd` (рекомендуется):**
    В некоторых дистрибутивах можно использовать параметризованные службы. Например, для `sshd@alt.service` `systemd` автоматически будет искать файл `/etc/ssh/sshd_config_alt`.
    ```bash
    # Запустите службу
    sudo systemctl start sshd@alt.service

    # Включите автозапуск при загрузке
    sudo systemctl enable sshd@alt.service
    ```
    Если параметризованные службы не настроены, вам может потребороваться создать собственный `unit-файл` для `systemd`.

**4. Проверка доступа**

С другой машины в той же сети попробуйте подключиться к резервному порту:
```bash
ssh -p 2222 user@192.168.100.10
```

### Ограничение доступа пользователей

Для более тонкого контроля доступа к SSH-серверу можно использовать директивы `AllowUsers`, `AllowGroups`, `DenyUsers`, `DenyGroups`. Рекомендуется использовать подход "белых списков" (whitelist), явно разрешая доступ только определённым пользователям или группам.

-   `AllowUsers user1 user2@host`: Разрешает вход только указанным пользователям. Можно указать пользователя и хост, с которого разрешен вход.
-   `AllowGroups group1 group2`: Разрешает вход только пользователям, входящим в указанные группы.
-   `DenyUsers user3`: Запрещает вход указанным пользователям.
-   `DenyGroups group3`: Запрещает вход пользователям, входящим в указанные группы.

```ini
# Разрешить вход только пользователям 'admin' и 'devuser'
AllowUsers admin devuser
# Запретить всем остальным
# DenyUsers * # Лучше не использовать DenyUsers * с AllowUsers
```
Или, если нужно разрешить только членам группы `sshusers`:
```ini
AllowGroups sshusers
```
**Важно:** Директивы `Allow` имеют приоритет над `Deny`. Если пользователь указан в `AllowUsers` и `DenyUsers`, ему будет разрешен вход. Рекомендуется использовать только `AllowUsers` или `AllowGroups` для создания "белого списка" и не использовать `Deny` одновременно, чтобы избежать путаницы.

## Логирование SSH-сессий и криминалистика

**Основные файлы журналов SSH-сессий:**

-   `/var/log/wtmp`: Журнал всех входов и выходов пользователей, а также перезагрузок системы. Содержит историю успешных подключений.
-   `/var/log/btmp`: Журнал неудачных попыток входа в систему. Является ключевым источником информации для выявления атак методом перебора (brute-force).
-   `/var/log/lastlog`: Записывает информацию о последнем входе каждого пользователя.

## Защита от атак

### Атаки методом перебора (Brute-force)

Подробное описание различных типов атак методом перебора (брутфорс), таких как полный перебор, словарные атаки, параллельные и временные логические атаки, а также общие методы противодействия им, вы найдете в документе [Атаки методом перебора (Brute-force Attacks)](../../../Security/Concepts/brute_force_attacks.md).

### Fail2Ban

Для защиты SSH от брутфорс-атак рекомендуется использовать утилиту [Fail2Ban](../../../Security/Tools/fail2ban_overview.md). Она анализирует логи служб (включая SSH) и автоматически блокирует IP-адреса, с которых ведутся атаки перебором.

Подробную информацию об установке, настройке и управлении Fail2Ban, а также о его интеграции с NGINX для защиты от DoS-атак, можно найти в документе [Fail2Ban: Защита сервера от атак](../../../Security/Tools/fail2ban_overview.md).

### Endlessh: SSH-ловушка

**Endlessh** — это простая утилита, которая работает как "ловушка" (tarpit) для SSH-клиентов. Она захватывает SSH-соединения, бесконечно отправляя им баннер SSH, но никогда не завершая хендшейк. Это эффективно "замораживает" автоматизированных ботов и сканеры, которые пытаются подобрать пароли или найти уязвимости.

- **Ссылка:** [skeeto/endlessh on GitHub](https://github.com/skeeto/endlessh)

### Инструменты для аудита безопасности SSH

#### ssh-audit

`ssh-audit` — это мощный инструмент командной строки для аудита конфигурации SSH-сервера и клиента. Он позволяет анализировать настройки безопасности, выявлять уязвимости и получать рекомендации по улучшению.

**Возможности:**

-   Анализ конфигурации SSH как на сервере, так и на клиенте.
-   Захват баннера, распознавание устройства или программного обеспечения и операционной системы, обнаружение сжатия.
-   Сбор алгоритмов обмена ключами, ключей хоста, шифрования и аутентификации сообщений.
-   Информация о безопасности алгоритма (с какого времени, удален/отключен, небезопасен/слаб/устаревший и т. д.).
-   Рекомендации по алгоритму (добавлять или удалять в зависимости от распознанной версии программного обеспечения).
-   Анализ совместимости версий SSH на основе информации об алгоритме.
-   Историческая информация из OpenSSH, Dropbear SSH и libssh.
-   Проверка политик безопасности для обеспечения соответствия защищенной/стандартной конфигурации.
-   Работает на Linux и Windows; поддерживает Python 3.9 - 3.13; не имеет зависимостей.

**GitHub:** [https://github.com/jtesta/ssh-audit](https://github.com/jtesta/ssh-audit)
