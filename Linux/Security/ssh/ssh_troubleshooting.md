# Диагностика и устранение неисправностей SSH

## Определения

**SSH Troubleshooting** — систематический процесс выявления проблем подключения: анализ клиентской конфигурации, сетевого пути, серверных настроек и аутентификации.

**Verbose Mode** — режим детализации SSH-клиента (`-v`, `-vv`, `-vvv`). Показывает каждый этап подключения в реальном времени — основной диагностический инструмент.

**SSH Handshake** — начальный этап соединения: согласование версии протокола, алгоритмов шифрования, обмена ключами. Сбои чаще всего вызваны несовместимостью конфигураций.

## Базовые концепции

### Систематический подход

Диагностика идёт по цепочке: **Клиент → Сеть → Сервер → Аутентификация**.

| Этап | Что проверять | Инструменты |
| :--- | :--- | :--- |
| **Клиент** | Адрес, порт, DNS, локальный файрвол, `~/.ssh/config` | `ssh -v`, `nslookup` |
| **Сеть** | Маршрут, блокировки портов, MTU | `ping`, `nc -zv`, `traceroute` |
| **Сервер** | Статус `sshd`, порт прослушивания, файрвол | `systemctl status sshd`, `ss -tlpn` |
| **Аутентификация** | Учётные данные, права на ключи, ограничения доступа | `ssh -vvv`, логи сервера |

### Источники информации

**Детальный вывод клиента:**

| Флаг | Детализация | Когда использовать |
| :--- | :--- | :--- |
| `-v` | Основные этапы (согласование, аутентификация) | Большинство проблем |
| `-vv` | Выбранные алгоритмы, детали обмена | Сложные проблемы совместимости |
| `-vvv` | Каждый пакет, отладка протокола | Крайние случаи, баг-репорты |

**Логи сервера:**

| Дистрибутив | Команда / Путь |
| :--- | :--- |
| **systemd (все)** | `sudo journalctl -u ssh -f` (или `sshd`) |
| **Debian / Ubuntu** | `sudo tail -f /var/log/auth.log` |
| **RHEL / Alma / Rocky** | `sudo tail -f /var/log/secure` |

**Проверка эффективной конфигурации:**

Иногда реальные настройки отличаются от тех, что вы видите в файлах (из-за `Include`, `Match` блоков или значений по умолчанию).

```bash
# На стороне клиента: показать все примененные параметры для хоста
ssh -G myserver.com

# На стороне сервера: показать итоговую конфигурацию демона
sudo sshd -T
```

Ключевые маркеры в логах: `Accepted` (успех), `Failed` (неудача), `Invalid User` (нет пользователя), `bad ownership or modes` (неверные права).

## Практические сценарии

### Сценарий 1: Соединение не устанавливается

**Симптомы:** `Connection timed out`, `Connection refused`, `No route to host`, `Unknown host`.

```bash
# 1. Разрешается ли имя?
nslookup <hostname>
dig +short <hostname>
```

Если DNS не сработал:
- **Проверить статическую запись** — `/etc/hosts` проверяется раньше DNS (через `nsswitch.conf`): `grep <hostname> /etc/hosts`.
- **Проверить резолвер** — какой DNS-сервер используется: `cat /etc/resolv.conf` (строка `nameserver`).
- **Проверить доступность резолвера:** `ping -c 3 <NS_IP>`.
- Если `dig` сработал, а `ssh` нет — проблема в системном резолвере (libc, nsswitch), а не в DNS как таковом. Проверить: `getent hosts <hostname>`.

```bash
# 2. Проверить сетевой маршрут (если IP известен, но недоступен)
traceroute -n <server_ip>
# TTL-механизм: каждый роутер уменьшает TTL на 1,
# при TTL=0 шлёт ICMP «Time Exceeded».
# Потеря пакетов после конкретного хопа указывает на проблемный участок.

# 3. Проверить доступность порта
nc -zv <server_ip> 22
# succeeded! — порт открыт, проблема в sshd
# Connection refused — порт закрыт, sshd не запущен
# timed out — блокировка файрволом
```

```bash
# 4. Проверить статус службы
# Debian/Ubuntu
sudo systemctl status ssh
# RHEL/CentOS
sudo systemctl status sshd

# 5. Проверить порт прослушивания
sudo ss -tlpn | grep -E 'ssh|sshd'

# 6. Проверить файрвол
sudo iptables -L -n
sudo nft list ruleset
```

### Сценарий 2: Доступ запрещён

**Симптом:** `Permission denied (publickey,password)`.

#### Проблемы с authorized_keys (ключ добавлен, но запрашивает пароль)

Это одна из самых частых проблем. Основные причины и способы их устранения:

1. **Неверные права доступа (наиболее вероятно):**
   SSH-сервер очень строг к правам доступа. Если директория или файл доступны для записи кому-то, кроме владельца, `sshd` проигнорирует ключи.
   - **Решение:**

     ```bash
     chmod 700 ~/.ssh
     chmod 600 ~/.ssh/authorized_keys
     chmod 755 ~  # Домашняя директория НЕ должна быть 777
     ```

2. **Владелец файлов:**
   Убедитесь, что владельцем является текущий пользователь, а не `root`.
   - **Решение:** `chown -R $USER:$USER ~/.ssh`

3. **Ошибки в формате ключа:**
   Ключ в `authorized_keys` должен быть одной длинной строкой. Лишние переносы строк или пробелы в начале/конце ломают его.
   - **Решение:** Проверьте файл через `cat -A ~/.ssh/authorized_keys`.

4. **Логирование на сервере:**
   Точный ответ всегда есть в логах сервера (`/var/log/auth.log` или `/var/log/secure`).
   - **Что искать:** `Authentication refused: bad ownership or modes`.

5. **Конфигурация сервера (`sshd_config`):**
   Проверьте, разрешена ли вообще аутентификация по ключам:
   - `PubkeyAuthentication yes`
   - `AuthorizedKeysFile .ssh/authorized_keys`

6. **SELinux (для RHEL / Alma / Rocky):**
   Контекст безопасности может мешать чтению файлов.
   - **Проверка:** `ls -Z ~/.ssh`
   - **Исправление:** `restorecon -Rv ~/.ssh`

### Сценарий 2.1: Учетная запись заблокирована

**Симптом:** Доступ запрещен даже с верным паролем/ключом.

1. **Блокировка PAM (pam_faillock):**
   После нескольких неудачных попыток входа (brute-force) аккаунт может быть временно заморожен.
   - **Проверка (RHEL/CentOS/Rocky):** `sudo faillock --user <username>`
   - **Сброс:** `sudo faillock --user <username> --reset`

2. **Заблокированный пароль в `/etc/shadow`:**
   Если в поле пароля стоит `!` или `*`, пользователь не может войти по паролю (но может по ключу, если не настроено обратное).
   - **Проверка:** `sudo passwd -S <username>` (статус `L` — locked, `P` — usable).

3. **Срок действия пароля истек:**
   Пользователь может войти, но SSH-сессия сразу закрывается или требует смены пароля.
   - **Проверка:** `chage -l <username>`

### Сценарий 2.2: Системные и внешние ограничения

1. **Наличие файла `/etc/nologin`:**
   Если этот файл существует, вход разрешен только для `root`. Остальные увидят содержимое файла и разрыв связи.
   - **Решение:** Удалить файл (часто остается после техобслуживания).

2. **Отсутствие свободного места:**
   Если диск (особенно разделы `/var`, `/tmp` или `/home`) заполнен на 100%, SSH не сможет создать временные файлы или записать логи, что приведет к ошибке аутентификации.
   - **Проверка:** `df -h`

3. **Некорректная оболочка (Shell):**
   Если у пользователя в `/etc/passwd` указан несуществующий путь к оболочке или `/usr/sbin/nologin`.
   - **Проверка:** `getent passwd <username> | cut -d: -f7`

### Сценарий 2.3: Изменение ключа хоста

**Симптом:** `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!`

**Причины:** переустановка ОС, замена сервера с тем же IP, MITM-атака (наиболее опасный). Симптом одинаков для обоих случаев.

**Проверка ключа без подключения — `ssh-keyscan`:**

```bash
# Снять текущий ключ с сервера
ssh-keyscan -t rsa,ed25519 target-host 2>/dev/null

# Сравнить с записью в known_hosts
ssh-keygen -F target-host -f ~/.ssh/known_hosts
```

Если ключи не совпадают — снять отпечаток обеих версий для визуального сравнения:

```bash
ssh-keygen -lf <(ssh-keyscan -t ed25519 target-host 2>/dev/null)
```

**Правильная практика — предварительное сохранение fingerprint:**

Перед любой переустановкой сервера сохранять отпечаток через доверенный канал (телефон, закрытый чат, CMDB):

```bash
# До переустановки — на сервере
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub > /secure-storage/host-fingerprint-$(hostname).txt

# После переустановки — сверяем
diff <(ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub) /secure-storage/host-fingerprint-$(hostname).txt
```

**Массовый аудит host key всей инфраструктуры:**

```bash
while read host; do
  current=$(ssh-keyscan -t ed25519 "$host" 2>/dev/null | awk '{print $3}')
  expected=$(grep "$host" /secure-storage/known-hosts-baseline.txt | awk '{print $3}')
  if [[ "$current" != "$expected" ]]; then
    echo "MISMATCH: $host"
  fi
done < hosts.txt
```

**Автоматическое доверие через SSH CA:**

Для инфраструктуры с частым пересозданием хостов (автоскейлинг-группы, контейнеры) статичный `known_hosts` неприменим. Вместо этого используется SSH CA — центральный центр сертификации, подписывающий ключи хостов (см. подробнее [SSH CA (Certificates)](./server/ssh_certificate_authentication.md)):

```ini
# Настройка доверия к CA вместо конкретных ключей
@cert-authority *.internal.company.com $(cat ca.pub)
```

При такой схеме пересоздание хоста не требует ручной сверки — новый инстанс получает сертификат от того же CA, и клиент доверяет ему автоматически.

```bash
# Вручную — удалить старую запись (только после сверки!)
ssh-keygen -R <hostname_or_ip>
```

### Сценарий 2.4: Проблемы инициализации оболочки

**Симптом:** Соединение устанавливается, аутентификация проходит, но сессия сразу закрывается или «висит».

1. **Ошибки в `.bashrc`, `.bash_profile`, `.zshrc`:**
   Если в скриптах инициализации есть ошибки (например, бесконечный цикл или вызов `exit`), сессия закроется сразу после входа.
   - **Диагностика:** Попробовать войти без выполнения скриптов инициализации:
     ```bash
     ssh user@host "/bin/bash --noprofile --norc"
     ```

2. **Зависшие процессы оболочки:**
   Если оболочка пытается выполнить команду, которая требует ввода или ожидает ответа от недоступного ресурса (например, монтирование NFS).

### Сценарий 2.5: Ограничения ресурсов сервера

Если сервер достигает лимитов, он может отклонять новые соединения.

1. **MaxStartups:** Количество одновременных «недоаутентифицированных» соединений (те, что на этапе ввода логина/пароля).
   - **Симптом:** Случайные отказы в подключении под большой нагрузкой.
   - **Проверка:** `sshd -T | grep -i maxstartups`

2. **MaxSessions:** Максимальное количество открытых сессий в рамках одного TCP-соединения (актуально при мультиплексировании).
   - **Проверка:** `sshd -T | grep -i maxsessions`

### Сценарий 3: Медленное подключение

**Симптом:** Пауза 2-10 секунд перед запросом пароля или появлением приветствия.

1. **Таймаут GSSAPI-аутентификации:**
   Клиент по умолчанию пытается использовать GSSAPI (Kerberos), и если она не настроена, ждет таймаут.
   - **Решение:** Добавить в `~/.ssh/config`:
     ```ini
     Host *
       GSSAPIAuthentication no
     ```

2. **Проблемы с Reverse DNS (на стороне сервера):**
   SSH-сервер по умолчанию пытается разрешить IP-адрес клиента в доменное имя для записи в логи и проверки `Match` блоков. Если DNS-серверы на стороне сервера работают медленно или не имеют обратной зоны, возникает задержка.
   - **Решение:** Отключить проверку в `/etc/ssh/sshd_config`:
     ```ini
     UseDNS no
     ```
   - **Примечание:** Это может повлиять на правила доступа, основанные на именах хостов.

### Сценарий 4: Соединение «зависает»

**Симптом:** Аутентификация проходит, появляется приветствие, но любая команда (или даже просто вывод `ls -R`) «вешает» терминал.

**Причина:** Проблемы фрагментации пакетов (**MTU**). Пакеты стандартного размера (1500 байт) не проходят через некоторые участки сети (VPN-тоннели, Docker-сети, старые роутеры), если установлен флаг DF (Don't Fragment).

**Диагностика:** Попробовать выполнить `ping` с запретом фрагментации и уменьшающимся размером пакета, чтобы найти максимальный рабочий MTU.
Подробнее: [ping](../../Diagnostics/Networking/ping.md).

**Решение:**
- Уменьшить MTU на сетевом интерфейсе.
- Или использовать **MSS Clamping** на роутере.
- Временное решение: `ssh -o "ProxyCommand=nc %h %p"` (иногда помогает за счет другого способа передачи данных).

### Сценарий 5: Разрыв соединения при бездействии

**Симптом:** Автоматическое закрытие сессии после периода бездействия («Broken pipe» или «Connection reset by peer»).

**Причина:** Промежуточные устройства (файрволы, NAT, провайдеры) закрывают бездействующие TCP-соединения.

**Решение:** Настройка keep-alive.

#### Клиентская конфигурация (`~/.ssh/config`)

```ini
Host *
  ServerAliveInterval 60
  ServerAliveCountMax 3
```

`ServerAliveInterval 60` — клиент отправляет пустой пакет каждые 60 секунд. `ServerAliveCountMax 3` — разрыв после 3 неудачных попыток (~180 секунд без ответа).

Подробнее: [Конфигурация клиента SSH](./ssh_client_config.md#полезные-директивы-расширенный-список).

#### Серверная конфигурация (`/etc/ssh/sshd_config`)

```ini
TCPKeepAlive yes
ClientAliveInterval 180
ClientAliveCountMax 3
```

Таймаут = `ClientAliveInterval × ClientAliveCountMax` → `180 × 3 = 540 сек` (9 минут).

Перезапуск после изменений: `sudo systemctl restart sshd`.

#### Различия клиентских и серверных настроек

| Параметр | Сторона | Файл |
| :--- | :--- | :--- |
| `ServerAliveInterval` | Клиент | `~/.ssh/config` |
| `ClientAliveInterval` | Сервер | `/etc/ssh/sshd_config` |
| `TCPKeepAlive` | Сервер (TCP-уровень) | `/etc/ssh/sshd_config` |

**Рекомендация:** Персональные настройки — клиентская конфигурация. Корпоративные серверы — серверная.

#### Предостережения

- Значения `<30 секунд` создают избыточный трафик.
- Keep-alive предотвращает разрыв, но не восстанавливает соединение.
- Для сохранения сессий при разрывах: [tmux](./ssh_session_management.md#tmux) или [screen](./ssh_session_management.md#gnu-screen).

## Дополнительная информация

### Запуск `sshd` в отладочном режиме

Безопасный способ тестирования конфигурации сервера без влияния на основной сервис:

```bash
# На сервере — отладочный sshd (один процесс, не уходит в фон)
sudo /usr/sbin/sshd -d -p 2222

# С клиента — подключение в детальном режиме
ssh user@host -p 2222 -vvv
```

Ключ `-d` предотвращает уход в фон, отладочная информация выводится в консоль. Логи видны с обеих сторон.

Подробнее о мониторинге сервера: [SSH Monitoring](./server/ssh_monitoring_and_troubleshooting.md).

### Проблема «Too many authentication failures»

Если в вашем `ssh-agent` загружено много ключей, SSH-клиент пробует их все по очереди. Если сервер настроен на ограничение попыток (`MaxAuthTries`), он закроет соединение до того, как дело дойдет до нужного ключа.

**Решение:**
- Ограничить ключи для конкретного хоста: `ssh -o IdentitiesOnly=yes -i ~/.ssh/id_rsa user@host`.
- Или добавить `IdentitiesOnly yes` в `~/.ssh/config`.

### Анализ трафика с помощью Wireshark

Когда `ssh -vvv` не даёт ответа, анализ пакетов выявляет проблемы на низком уровне.

**Что искать:**

| Этап | Пакет | Интерпретация |
| :--- | :--- | :--- |
| **Обмен версиями** | `SSH-2.0-...` | Клиент и сервер согласны с версией |
| **Согласование алгоритмов** | `Key Exchange Init` | Проверить наличие общего алгоритма для шифрования, KEX, MAC |
| **New Keys** | `New Keys` | Канал установлен — проблема в аутентификации. Если нет — проблема в согласовании ключей |

### Быстрая диагностика: чек-лист

```bash
# 1. Разрешается ли имя и какая эффективная конфигурация?
ssh -G myserver.com | grep -E "hostname|port|user"
dig +short myserver.com

# 2. Доступен ли порт и отвечает ли сервис?
nc -zv myserver.com 22
ssh user@host -v 2>&1 | head -20

# 3. Какие алгоритмы согласованы (проблемы KEX/Cipher)?
ssh user@host -vv 2>&1 | grep -i "kex\|cipher\|mac"

# 4. Какие методы аутентификации предложены сервером?
ssh user@host -vv 2>&1 | grep "Authentications that can continue"

# 5. Проверка статуса на сервере (если есть доступ)
sudo sshd -t && sudo journalctl -u ssh -n 50
```
