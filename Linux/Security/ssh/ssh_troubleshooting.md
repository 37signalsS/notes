# Поиск и устранение неисправностей SSH

При возникновении проблем с SSH-подключением важно систематически проверять все возможные точки отказа, двигаясь от клиента к серверу.

### 1. Детальный вывод клиента (Verbose Mode)
Это самый важный инструмент для диагностики. Флаг `-v` заставляет SSH-клиент показывать в реальном времени, что именно он делает. Используйте его всегда в первую очередь.

-   `ssh -v user@host`: **Основные этапы.** Показывает процесс согласования, попытки аутентификации, чтение конфигураций. Помогает быстро понять, где сбой.
-   `ssh -vv user@host`: **Подробности обмена.** Добавляет информацию о выбранных алгоритмах, детальные сообщения аутентификации.
-   `ssh -vvv user@host`: **Максимальная детализация.** Показывает всё вплоть до каждого пакета. Идеально для отладки сложных проблем с ключами, `known_hosts` или специфических ошибок рукопожатия.

**Пример:** При ошибке `Permission denied (publickey,password)` подробный вывод покажет, какие именно публичные ключи были предложены серверу и почему они были отклонены.

### 2. Анализ логов на стороне сервера
Позволяет увидеть, как сервер реагирует на вашу попытку подключения.

-   Команда (для систем с `systemd`): `sudo journalctl -u sshd -f`
-   Команда (для старых систем с `syslog`): `sudo tail -f /var/log/auth.log`

**Что искать в логах:**
- `Accepted publickey for...`: Успешная аутентификация по ключу.
- `Failed password for...`: Неудачная попытка входа по паролю.
- `Invalid user...`: Пользователь не существует.
- `Connection closed by authenticating user...`: Соединение закрыто клиентом.
- `Connection refused by tcp_wrappers`: Доступ заблокирован на уровне `/etc/hosts.allow` или `/etc/hosts.deny`.

### 3. Пошаговая проверка

#### Проблемы на стороне клиента (ваша машина)
*   **Неправильное имя хоста или IP:** Убедитесь, что адрес верен.
*   **Ошибка разрешения имени (DNS):** Попробуйте подключиться по IP-адресу. Если по IP работает, а по имени нет — проблема в DNS. (`nslookup <hostname>`).
*   **Локальный файрвол:** Проверьте, не блокирует ли ваш файрвол исходящие соединения на нужный порт.
*   **Неправильный порт:** Если SSH на сервере работает на нестандартном порту, его нужно явно указать: `ssh user@host -p <port_number>`.

#### Проблемы на уровне сети
*   **Отсутствие сетевого подключения:** Проверьте доступность сервера (`ping <server_ip>`).
*   **Сетевой файрвол:** Корпоративный или провайдерский файрвол может блокировать порт.
    *   **Проверка доступности порта `nc` (netcat):**
        ```bash
        # -z сканирует порт, не отправляя данные, -v дает подробный вывод
        nc -zv <server_ip> 22 
        ```
        - **Успех:** `Connection to <server_ip> port 22 [tcp/ssh] succeeded!`
        - **Отказ:** `nc: connect to <server_ip> port 22 (tcp) failed: Connection refused` (порт закрыт на сервере).
        - **Тайм-аут:** Соединение блокируется где-то по пути (файрвол).
    *   **Проверка маршрута до хоста:** `traceroute -T -p 22 <server_ip>` (покажет, где обрывается соединение).

#### Проблемы на стороне сервера
*   **Сервер выключен или не загрузился.**
*   **Служба SSH не запущена (`sshd`):**
    ```bash
    # Проверить статус службы
    systemctl status sshd
    # Если не установлена (Debian/Ubuntu)
    sudo apt update && sudo apt install openssh-server
    ```
*   **Служба SSH слушает другой порт:** Проверьте `Port` в `/etc/ssh/sshd_config` и вывод команды:
    ```bash
    # ss -tlpn | grep sshd
    # Пример: LISTEN 0.0.0.0:2222 означает, что нужно подключаться на порт 2222
    ```
*   **Файрвол на сервере:** `iptables`, `nftables` или `firewalld` могут блокировать порт.
    *   Команды: `sudo iptables -L -n`, `sudo nft list ruleset`.
*   **Закончились ресурсы:** Нехватка памяти или места на диске.
    *   Команды: `free -h`, `df -h`.

#### Проблемы с аутентификацией и доступом
*   **Неправильный логин или пароль.**
*   **Неправильные права на файлы/директории:** SSH требует строгих прав. Некорректные разрешения являются частой причиной сбоев аутентификации по ключу. См. [полное руководство по правам доступа](./ssh_server_security.md#проверка-и-установка-прав-доступа).
*   **Неправильный публичный ключ:** Ключ на клиенте не соответствует ключу в `~/.ssh/authorized_keys` на сервере.
*   **Пользователю запрещен вход:** Проверьте директивы `AllowUsers`, `DenyUsers`, `AllowGroups`, `DenyGroups` в `/etc/ssh/sshd_config`.
*   **SELinux/AppArmor:** Эти системы мандатного доступа могут блокировать операции SSH.
    *   Команды: `sestatus`, `aa-status`. Ищите ошибки в `/var/log/audit/audit.log` или `/var/log/syslog`.

### Углубленная диагностика

1.  **Запуск `sshd` в отладочном режиме на другом порту:**
    *   Это безопасный способ протестировать конфигурацию, не затрагивая основной SSH-сервис.
    *   На сервере: `sudo /usr/sbin/sshd -d -p 2222`.
    *   Сервер запустится на порту 2222, не уйдет в фон (`-d`) и будет выводить всю отладочную информацию в консоль.
    *   С клиента: `ssh user@host -p 2222 -v`.

2.  **Проверка проблем с MTU (фрагментация пакетов):**
    *   **Симптом:** Соединение устанавливается, но "зависает" после аутентификации или при передаче данных. Часто бывает при использовании VPN.
    *   **Диагностика (для Linux):** Используйте `ping` для определения MTU. Подробнее см. [**`ping`**](../../Diagnostics/Networking/ping.md).

3.  **Анализ рукопожатия SSH в Wireshark:**
    *   Когда `ssh -vvv` не дает ответа, анализ трафика с помощью Wireshark может помочь увидеть "сырые" пакеты обмена. Это полезно для диагностики проблем на самом низком уровне: сбои согласования алгоритмов, несовместимость протоколов или проблемы с ключами хоста.
    *   **Что искать:**
        1.  **Обмен версиями протокола:** Убедитесь, что клиент и сервер согласны с версией (`SSH-2.0`).
        2.  **Согласование алгоритмов (`Key Exchange Init`):** Проверьте списки алгоритмов шифрования, обмена ключами и MAC. Если нет общих, соединение разорвется.
        3.  **Обмен ключами (Diffie-Hellman):** Посмотрите, происходит ли обмен эфемерными публичными ключами.
        4.  **`New Keys`:** Если эти пакеты отправлены, значит, шифрованный канал установлен. Проблема, скорее всего, на следующем этапе — аутентификации. Если нет, проблема в согласовании ключей.

### Устранение задержки при подключении (GSSAPIAuthentication)

Иногда при подключении по SSH возникает заметная пауза (2-5 секунд) перед запросом пароля или началом сессии. Чаще всего это связано с попытками SSH использовать GSSAPI (Generic Security Service Application Program Interface) для аутентификации, которая по умолчанию включена. Это особенно заметно, если Kerberos не используется или DNS-настройки (прямое и обратное разрешение имен) на клиенте или сервере некорректны. SSH-клиент тратит время на ожидание ответа от GSSAPI, которого не получает.

**Как решить:**

1.  **Отключение на клиенте (рекомендуемый способ):**
    Создайте или отредактируйте файл `~/.ssh/config` на вашем локальном компьютере и добавьте следующие строки:

    ```
    Host *
        GSSAPIAuthentication no
    ```
    Это отключит GSSAPI для всех SSH-подключений с данного клиента. Если нужно отключить только для конкретных хостов, замените `Host *` на `Host your_server_alias`.

2.  **Отключение на сервере (если у вас есть доступ):**
    Отредактируйте файл `/etc/ssh/sshd_config` на сервере. Найдите строку `GSSAPIAuthentication yes` и измените ее на:

    ```
    GSSAPIAuthentication no
    ```
    После изменения конфигурации перезапустите службу `sshd`:

    ```bash
    sudo systemctl restart sshd
    ```
    Отключение GSSAPI на сервере повлияет на всех клиентов, подключающихся к этому серверу.

**Почему это работает:** Отключение GSSAPIAuthentication предотвращает попытки SSH использовать Kerberos, устраняя задержку, вызванную таймаутами при отсутствии или некорректной настройке Kerberos/DNS.
