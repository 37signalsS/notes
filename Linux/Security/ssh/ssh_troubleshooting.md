# Диагностика и устранение неисправностей SSH

## Определения

**Диагностика SSH (SSH Troubleshooting)** — это систематический процесс выявления и решения проблем, препятствующих успешному подключению или корректной работе сессии SSH. Процесс включает в себя анализ ошибок на всех этапах: от конфигурации клиента до настроек сервера и состояния сети.

**Verbose Mode (детальный режим)** — это режим работы SSH-клиента, активируемый флагами `-v`, `-vv` или `-vvv`. Он выводит подробную информацию о каждом шаге процесса подключения, являясь основным инструментом для быстрой диагностики.

**Рукопожатие SSH (SSH Handshake)** — начальный этап установки соединения, в ходе которого клиент и сервер договариваются о параметрах сессии: версии протокола, алгоритмах шифрования и обмена ключами. Сбои на этом этапе часто связаны с несовместимостью конфигураций.

## Основные концепции

### Систематический подход

**Клиент → Сеть → Сервер → Аутентификация**

1. **Клиент:** Корректны ли настройки на вашей машине (адрес, порт, DNS, локальный файрвол)?
2. **Сеть:** Есть ли сетевой маршрут до сервера? Не блокируется ли порт внешними файрволами?
3. **Сервер:** Запущена ли служба `sshd`? Не блокирует ли её файрвол сервера?
4. **Аутентификация:** Верны ли учётные данные? Корректны ли права на файлы ключей? Разрешен ли доступ пользователю?

### Ключевые источники информации

1. **Детальный вывод клиента (`ssh -v`):** Это ваш главный инструмент. Он показывает, что клиент пытается делать в реальном времени и на каком этапе происходит сбой.
    - `-v`: Основные этапы (согласование, аутентификация).
    - `-vv`: Детали обмена (выбранные алгоритмы).
    - `-vvv`: Максимальная детализация (вплоть до каждого пакета), необходимая для сложных проблем.

2. **Логи сервера:** Показывают, как сервер реагирует на попытку подключения.
    - **Команда:** `sudo journalctl -u sshd -f` (для `systemd`) или `sudo tail -f /var/log/auth.log` (для `syslog`).
    - **Что искать:** `Accepted` (успех), `Failed` (неудача), `Invalid user` (нет такого пользователя), `bad ownership or modes` (неверные права доступа).

## Практические сценарии

### Сценарий 1: Соединение не устанавливается

**Симптомы:** `Connection timed out`, `Connection refused`, `No route to host`.

1. **Проверьте DNS и порт:** Убедитесь, что имя хоста разрешается в правильный IP (`nslookup <hostname>`) и что вы используете верный порт (`ssh user@host -p <port>`).
2. **Проверьте сетевую доступность:**
    - **Ping:** `ping <server_ip>` (проверяет, отвечает ли сервер).
    - **Доступность порта:** `nc -zv <server_ip> 22`.
        - `succeeded!`: Порт открыт. Проблема на стороне `sshd`.
        - `Connection refused`: Порт закрыт. `sshd` не запущен или слушает другой порт.
        - `timed out`: Порт блокируется файрволом (на клиенте, сервере или в сети).
3. **Проверьте статус службы на сервере:**

    ```bash
    sudo systemctl status sshd
    ```

4. **Проверьте, какой порт слушает `sshd`:**

    ```bash
    sudo ss -tlpn | grep sshd
    ```

5. **Проверьте правила файрвола на сервере:** (`sudo iptables -L -n`, `sudo nft list ruleset`).

### Сценарий 2: Доступ запрещен

**Симптом:** `Permission denied (publickey,password)`.

1. **Анализируйте вывод `ssh -v`:** Он покажет, какие методы аутентификации были предприняты и почему они провалились.
2. **Проверьте логин:** Убедитесь, что имя пользователя указано верно.
3. **Проверьте права доступа на сервере:** Это самая частая причина ошибок при аутентификации по ключу.
    - `~/.ssh` должен иметь права `700`.
    - `~/.ssh/authorized_keys` должен иметь права `600`.
    - Подробнее см. [руководство по безопасности сервера](./ssh_server_security.md#важность-корректных-прав-доступа).
4. **Проверьте ограничения доступа на сервере:** Изучите директивы `AllowUsers`, `DenyUsers`, `AllowGroups`, `DenyGroups` в `/etc/ssh/sshd_config`.
5. **Проверьте SELinux/AppArmor:** Временно отключите их для диагностики (`sudo setenforce 0`). Если подключение удалось, необходимо настроить для них корректные политики.

### Сценарий 3: Медленное подключение

**Симптом:** Заметная пауза (2-5 секунд) перед запросом пароля или входом в систему.

- **Причина:** Чаще всего это связано с таймаутом аутентификации GSSAPI, которая включена по умолчанию, но не настроена.
- **Решение (на клиенте):** Добавьте в `~/.ssh/config`:

    ```ini
    Host *
      GSSAPIAuthentication no
    ```

### Сценарий 4: Соединение "зависает"

**Симптом:** Соединение устанавливается, аутентификация проходит, но сессия неактивна или "зависает" при передаче данных.

- **Причина:** Часто связано с проблемами фрагментации пакетов (MTU), особенно при использовании VPN.
- **Диагностика:** Используйте `ping` с запретом фрагментации для определения корректного размера MTU. Детали см. в руководстве [ping](../../Diagnostics/Networking/ping.md).

## Дополнительная информация

### Запуск `sshd` в отладочном режиме

Это безопасный способ протестировать конфигурацию сервера, не затрагивая основной сервис.

1. **На сервере** остановите основной сервис `sshd` или запустите отладочный на другом порту:

    ```bash
    sudo /usr/sbin/sshd -d -p 2222
    ```

    Ключ `-d` предотвращает уход в фон и выводит всю отладочную информацию в консоль.
2. **С клиента** подключитесь к тестовому порту в детальном режиме:

    ```bash
    ssh user@host -p 2222 -vvv
    ```

    Теперь вы видите логи одновременно с обеих сторон, что позволяет точно выявить проблему.

### Анализ трафика с помощью Wireshark

Когда даже `ssh -vvv` не дает ответа, анализ "сырых" пакетов в Wireshark может выявить проблемы на самом низком уровне.

- **Что искать в обмене пакетами:**
    1. **Обмен версиями протокола:** Убедитесь, что клиент и сервер согласны с версией (`SSH-2.0`).
    2. **Согласование алгоритмов (`Key Exchange Init`):** Проверьте, есть ли у сторон хотя бы один общий алгоритм для каждого из типов: шифрования, обмена ключами и MAC.
    3. **`New Keys`:** Если эти пакеты отправлены, значит, шифрованный канал установлен, и проблема, скорее всего, на следующем этапе — аутентификации. Если нет — проблема в согласовании ключей.
