# Диагностика и устранение неисправностей SSH

## Определения

**SSH Troubleshooting** — систематический процесс выявления проблем подключения: анализ клиентской конфигурации, сетевого пути, серверных настроек и аутентификации.

**Verbose Mode** — режим детализации SSH-клиента (`-v`, `-vv`, `-vvv`). Показывает каждый этап подключения в реальном времени — основной диагностический инструмент.

**SSH Handshake** — начальный этап соединения: согласование версии протокола, алгоритмов шифрования, обмена ключами. Сбои чаще всего вызваны несовместимостью конфигураций.

## Базовые концепции

### Систематический подход

Диагностика идёт по цепочке: **Клиент → Сеть → Сервер → Аутентификация**.

| Этап | Что проверять | Инструменты |
| :--- | :--- | :--- |
| **Клиент** | Адрес, порт, DNS, локальный файрвол, `~/.ssh/config` | `ssh -v`, `nslookup` |
| **Сеть** | Маршрут, блокировки портов, MTU | `ping`, `nc -zv`, `traceroute` |
| **Сервер** | Статус `sshd`, порт прослушивания, файрвол | `systemctl status sshd`, `ss -tlpn` |
| **Аутентификация** | Учётные данные, права на ключи, ограничения доступа | `ssh -vvv`, логи сервера |

### Источники информации

**Детальный вывод клиента:**

| Флаг | Детализация | Когда использовать |
| :--- | :--- | :--- |
| `-v` | Основные этапы (согласование, аутентификация) | Большинство проблем |
| `-vv` | Выбранные алгоритмы, детали обмена | Сложные проблемы совместимости |
| `-vvv` | Каждый пакет, отладка протокола | Крайние случаи, баг-репорты |

**Логи сервера:**

| Дистрибутив | Команда / Путь |
| :--- | :--- |
| **systemd (все)** | `sudo journalctl -u ssh -f` (или `sshd`) |
| **Debian/Ubuntu** | `sudo tail -f /var/log/auth.log` |
| **RHEL/CentOS** | `sudo tail -f /var/log/secure` |

Ключевые маркеры в логах: `Accepted` (успех), `Failed` (неудача), `Invalid User` (нет пользователя), `bad ownership or modes` (неверные права).

## Практические сценарии

### Сценарий 1: Соединение не устанавливается

**Симптомы:** `Connection timed out`, `Connection refused`, `No route to host`, `Unknown host`.

```bash
# 1. Разрешается ли имя?
nslookup <hostname>
dig +short <hostname>
```

Если DNS не сработал:
- **Проверить статическую запись** — `/etc/hosts` проверяется раньше DNS (через `nsswitch.conf`): `grep <hostname> /etc/hosts`.
- **Проверить резолвер** — какой DNS-сервер используется: `cat /etc/resolv.conf` (строка `nameserver`).
- **Проверить доступность резолвера:** `ping -c 3 <NS_IP>`.
- Если `dig` сработал, а `ssh` нет — проблема в системном резолвере (libc, nsswitch), а не в DNS как таковом. Проверить: `getent hosts <hostname>`.

```bash
# 2. Проверить сетевой маршрут (если IP известен, но недоступен)
traceroute -n <server_ip>
# TTL-механизм: каждый роутер уменьшает TTL на 1,
# при TTL=0 шлёт ICMP «Time Exceeded».
# Потеря пакетов после конкретного хопа указывает на проблемный участок.

# 3. Проверить доступность порта
nc -zv <server_ip> 22
# succeeded! — порт открыт, проблема в sshd
# Connection refused — порт закрыт, sshd не запущен
# timed out — блокировка файрволом
```

```bash
# 4. Проверить статус службы
# Debian/Ubuntu
sudo systemctl status ssh
# RHEL/CentOS
sudo systemctl status sshd

# 5. Проверить порт прослушивания
sudo ss -tlpn | grep -E 'ssh|sshd'

# 6. Проверить файрвол
sudo iptables -L -n
sudo nft list ruleset
```

### Сценарий 2: Доступ запрещён

**Симптом:** `Permission denied (publickey,password)`.

#### Проблемы с authorized_keys (ключ добавлен, но запрашивает пароль)

Это одна из самых частых проблем. Основные причины и способы их устранения:

1. **Неверные права доступа (наиболее вероятно):**
   SSH-сервер очень строг к правам доступа. Если директория или файл доступны для записи кому-то, кроме владельца, `sshd` проигнорирует ключи.
   - **Решение:**

     ```bash
     chmod 700 ~/.ssh
     chmod 600 ~/.ssh/authorized_keys
     chmod 755 ~  # Домашняя директория НЕ должна быть 777
     ```

2. **Владелец файлов:**
   Убедитесь, что владельцем является текущий пользователь, а не `root`.
   - **Решение:** `chown -R $USER:$USER ~/.ssh`

3. **Ошибки в формате ключа:**
   Ключ в `authorized_keys` должен быть одной длинной строкой. Лишние переносы строк или пробелы в начале/конце ломают его.
   - **Решение:** Проверьте файл через `cat -A ~/.ssh/authorized_keys`.

4. **Логирование на сервере:**
   Точный ответ всегда есть в логах сервера (`/var/log/auth.log` или `/var/log/secure`).
   - **Что искать:** `Authentication refused: bad ownership or modes`.

5. **Конфигурация сервера (`sshd_config`):**
   Проверьте, разрешена ли вообще аутентификация по ключам:
   - `PubkeyAuthentication yes`
   - `AuthorizedKeysFile .ssh/authorized_keys`

6. **SELinux (для RHEL/CentOS/Fedora):**
   Контекст безопасности может мешать чтению файлов.
   - **Проверка:** `ls -Z ~/.ssh`
   - **Исправление:** `restorecon -Rv ~/.ssh`

### Сценарий 2.1: Изменение ключа хоста

**Симптом:** `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!`

**Причины:** переустановка ОС, замена сервера с тем же IP, MITM-атака (наиболее опасный).

```bash
# Удалить старую запись
ssh-keygen -R <hostname_or_ip>

# Подключиться заново и подтвердить новый отпечаток
ssh user@host
```

В production — сверять отпечатки с администратором сервера перед удалением записей из `known_hosts`.

### Сценарий 3: Медленное подключение

**Симптом:** Пауза 2-5 секунд перед запросом пароля.

**Причина:** Таймаут GSSAPI-аутентификации (включена по умолчанию, но не настроена).

**Решение** — добавить в `~/.ssh/config`:

```ini
Host *
  GSSAPIAuthentication no
```

### Сценарий 4: Соединение «зависает»

**Симптом:** Аутентификация проходит, сессия неактивна.

**Причина:** Проблемы фрагментации пакетов (MTU), особенно через VPN.

**Диагностика:** `ping` с запретом фрагментации для определения корректного MTU. Подробнее: [ping](../../Diagnostics/Networking/ping.md).

### Сценарий 5: Разрыв соединения при бездействии

**Симптом:** Автоматическое закрытие сессии после периода бездействия.

**Причина:** Промежуточные устройства (файрволы, NAT, провайдеры) закрывают бездействующие TCP-соединения.

**Решение:** Настройка keep-alive.

#### Клиентская конфигурация (`~/.ssh/config`)

```ini
Host *
  ServerAliveInterval 60
  ServerAliveCountMax 3
```

`ServerAliveInterval 60` — клиент отправляет пустой пакет каждые 60 секунд. `ServerAliveCountMax 3` — разрыв после 3 неудачных попыток (~180 секунд без ответа).

Подробнее: [Конфигурация клиента SSH](./ssh_client_config.md#полезные-директивы).

#### Серверная конфигурация (`/etc/ssh/sshd_config`)

```ini
TCPKeepAlive yes
ClientAliveInterval 180
ClientAliveCountMax 3
```

Таймаут = `ClientAliveInterval × ClientAliveCountMax` → `180 × 3 = 540 сек` (9 минут).

Перезапуск после изменений: `sudo systemctl restart sshd`.

#### Различия клиентских и серверных настроек

| Параметр | Сторона | Файл |
| :--- | :--- | :--- |
| `ServerAliveInterval` | Клиент | `~/.ssh/config` |
| `ClientAliveInterval` | Сервер | `/etc/ssh/sshd_config` |
| `TCPKeepAlive` | Сервер (TCP-уровень) | `/etc/ssh/sshd_config` |

**Рекомендация:** Персональные настройки — клиентская конфигурация. Корпоративные серверы — серверная.

#### Предостережения

- Значения `<30 секунд` создают избыточный трафик.
- Keep-alive предотвращает разрыв, но не восстанавливает соединение.
- Для сохранения сессий при разрывах: [tmux](./ssh_session_management.md) или [screen](./ssh_session_management.md).

## Дополнительная информация

### Запуск `sshd` в отладочном режиме

Безопасный способ тестирования конфигурации сервера без влияния на основной сервис:

```bash
# На сервере — отладочный sshhd на другом порту
sudo /usr/sbin/sshd -d -p 2222

# С клиента — подключение в детальном режиме
ssh user@host -p 2222 -vvv
```

Ключ `-d` предотвращает уход в фон, отладочная информация выводится в консоль. Логи видны с обеих сторон.

Подробнее о мониторинге сервера: [SSH Monitoring](./server/ssh_monitoring_and_troubleshooting.md).

### Анализ трафика с помощью Wireshark

Когда `ssh -vvv` не даёт ответа, анализ пакетов выявляет проблемы на низком уровне.

**Что искать:**

| Этап | Пакет | Интерпретация |
| :--- | :--- | :--- |
| **Обмен версиями** | `SSH-2.0-...` | Клиент и сервер согласны с версией |
| **Согласование алгоритмов** | `Key Exchange Init` | Проверить наличие общего алгоритма для шифрования, KEX, MAC |
| **New Keys** | `New Keys` | Канал установлен — проблема в аутентификации. Если нет — проблема в согласовании ключей |

### Быстрая диагностика: чек-лист

```bash
# 1. Разрешается ли имя?
nslookup myserver.com
dig +short myserver.com
cat /etc/resolv.conf
# /etc/hosts проверяется раньше DNS: grep myserver.com /etc/hosts

# 2. Доступен ли порт?
nc -zv myserver.com 22

# 3. Отвечает ли sshd?
ssh user@host -v 2>&1 | head -20

# 4. Какие алгоритмы согласованы?
ssh user@host -vv 2>&1 | grep -i "kex\|cipher\|mac"

# 5. Какие методы аутентификации предложены?
ssh user@host -vv 2>&1 | grep "Authentications that can continue"
```
