# SSH-аутентификация по сертификатам (SSH CA)

## Определения

**SSH CA (Certificate Authority, Центр сертификации SSH)** — это модель аутентификации в OpenSSH, основанная на иерархии доверия (PKI). Вместо того чтобы хранить тысячи публичных ключей пользователей на каждом сервере, серверы настраиваются на доверие подписи единого центра сертификации.

**SSH-сертификат** — специальный формат публичного ключа (пользователя или хоста), который содержит метаданные (идентификатор, список разрешенных логинов, срок действия, ограничения) и криптографическую подпись приватного ключа CA.

**Principals (Принципалы)** — список разрешенных системных имен пользователей (для пользовательских сертификатов) или имен хостов (для хостовых сертификатов), для которых данный сертификат является валидным.

## Основные концепции

### Принцип работы иерархии доверия

В отличие от традиционной модели `authorized_keys` (Trust on First Use, TOFU), SSH CA обеспечивает централизованное управление:

1.  **Доверие к корню**: Публичный ключ CA (`ca_user.pub`) размещается на всех серверах один раз.
2.  **Выпуск**: Пользователь генерирует локальную пару ключей и отправляет запрос на подпись. CA выпускает сертификат с заданным временем жизни (TTL).
3.  **Верификация**: При подключении сервер проверяет только подпись CA на предъявленном сертификате и соответствие метаданных (время, логин). Если подпись валидна — доступ разрешен.

### Типы сертификатов

-   **Пользовательские (User Certificates)**: Используются для входа на сервер. Заменяют записи в `~/.ssh/authorized_keys`.
-   **Хостовые (Host Certificates)**: Используются серверами для подтверждения своей подлинности клиентам. Это полностью решает проблему «Warning: Remote host identification has changed» и избавляет от необходимости подтверждать отпечатки ключей вручную.

### Преимущества перед статическими ключами

-   **Централизация**: Отзыв доступа или добавление нового пользователя не требует подключения к целевым серверам.
-   **Ограничение по времени**: Сертификаты могут выдаваться на часы или даже минуты (Short-lived certs), что делает их кражу бессмысленной.
-   **Аудит**: Каждый сертификат имеет уникальный ID (Key ID), который фиксируется в системных логах при входе.

## Практические сценарии

### Сценарий 1: Развертывание инфраструктуры SSH CA

**1. Генерация ключей центра сертификации:**
```bash
# Ключ для подписи пользователей
ssh-keygen -t ed25519 -f ~/.ssh/ca_user -C "SSH User CA"
# Ключ для подписи хостов
ssh-keygen -t ed25519 -f ~/.ssh/ca_host -C "SSH Host CA"
```

**2. Настройка серверов для доверия пользователям:**
Скопируйте `ca_user.pub` в `/etc/ssh/ca_user.pub`.
Добавьте в `/etc/ssh/sshd_config`:
```ssh
TrustedUserCAKeys /etc/ssh/ca_user.pub
```

**3. Настройка клиентов для доверия хостам:**
Добавьте публичный ключ `ca_host.pub` в файл `~/.ssh/known_hosts` (или глобально в `/etc/ssh/ssh_known_hosts`) с префиксом `@cert-authority`:
```text
@cert-authority *.example.com ssh-ed25519 AAAAC3Nza... (тело ключа ca_host.pub)
```

### Сценарий 2: Выпуск пользовательского сертификата

**Задача**: Выдать пользователю `developer` доступ под именами `dev` и `ubuntu` на 8 часов.

```bash
# Подписание публичного ключа пользователя
# -s: ключ CA
# -I: ID сертификата (для логов)
# -n: список разрешенных логинов (principals)
# -V: срок действия (от текущего момента +8 часов)
ssh-keygen -s ~/.ssh/ca_user -I "dev_access_123" -n dev,ubuntu -V +8h id_ed25519.pub

# → Результат: файл id_ed25519-cert.pub
```

### Сценарий 3: Выпуск хостового сертификата

**Задача**: Подписать ключ сервера `web01.example.com`.

```bash
# На стороне сервера используется его хостовый ключ /etc/ssh/ssh_host_ed25519_key.pub
ssh-keygen -s ~/.ssh/ca_host -I "host_web01" -h -n web01.example.com,10.0.1.5 -V +52w /path/to/ssh_host_ed25519_key.pub

# В sshd_config сервера нужно указать путь к сертификату:
# HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub
```

### Сценарий 4: Управление отзывом через KRL (Key Revocation List)

Если сертификат скомпрометирован до истечения срока его действия, его необходимо отозвать.

**1. Создание списка отзыва:**
```bash
ssh-keygen -k -f /etc/ssh/ca_revoked_keys
```

**2. Добавление серийного номера или ключа в список:**
```bash
ssh-keygen -k -u -f /etc/ssh/ca_revoked_keys compromised_user_key.pub
```

**3. Подключение списка в `sshd_config`:**
```ssh
RevokedKeys /etc/ssh/ca_revoked_keys
```

## Дополнительная информация

### Критические опции сертификатов (Critical Options)

При подписании можно добавить дополнительные ограничения:
- `force-command="cmd"`: Принудительный запуск конкретной команды.
- `source-address="192.168.1.0/24"`: Ограничение по IP источника.

По умолчанию сертификаты разрешают проброс портов и агента. Если это не требуется, используйте флаг `-O clear` при подписании, чтобы сбросить все разрешения, и добавляйте нужные через `-O permit-X`.

### Защита приватного ключа CA

Безопасность всей инфраструктуры SSH CA держится на приватных ключах `ca_user` и `ca_host`.
- **Offline CA**: Ключи не должны храниться на серверах, доступных извне.
- **HSM / Vault**: Рекомендуется использовать аппаратные модули безопасности или специализированное ПО.
- **Автоматизация**: Для крупных сред используйте [HashiCorp Vault: Secret Engines](../../../../Vault/concepts.md#движки-секретов-secret-engines), который автоматизирует выпуск кратковременных сертификатов через API.

### Диагностика сертификатов

Для просмотра содержимого и метаданных файла сертификата:
```bash
ssh-keygen -L -f id_ed25519-cert.pub
```
