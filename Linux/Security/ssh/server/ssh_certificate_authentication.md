# SSH-аутентификация по сертификатам (SSH CA)

## Определения

**SSH CA (Certificate Authority, Центр сертификации SSH)** — это модель аутентификации в OpenSSH, основанная на иерархии доверия (PKI). Вместо того чтобы хранить тысячи публичных ключей пользователей на каждом сервере, серверы настраиваются на доверие подписи единого центра сертификации.

**SSH-сертификат** — специальный формат публичного ключа (пользователя или хоста), который содержит метаданные (идентификатор, список разрешенных логинов, срок действия, ограничения) и криптографическую подпись приватного ключа CA.

**Principals (Принципалы)** — список разрешенных системных имен пользователей (для пользовательских сертификатов) или имен хостов (для хостовых сертификатов), для которых данный сертификат является валидным.

**Key ID** — уникальный идентификатор сертификата, задаваемый при подписании. Фиксируется в системных логах при входе и используется для аудита.

**KRL (Key Revocation List, Список отзыва ключей)** — файл, содержащий серийные номера отозванных сертификатов или их публичные ключи. OpenSSH проверяет этот файл перед выдачей доступа.

**Short-lived certificates (Кратковременные сертификаты)** — сертификаты с минимальным сроком действия (от нескольких минут до нескольких часов), что минимизирует риск при компрометации.

## Предварительные требования

### Аппаратные и программные требования

| Компонент | Минимум | Рекомендация |
| :--- | :--- | :--- |
| **OpenSSH** | 6.2+ (поддержка сертификатов) | 9.8p1+ (поддержка ML-KEM, ED25519-SK) |
| **ОС** | Linux с systemd | RHEL 8+, Debian 11+, Ubuntu 22.04+ |
| **Ядро** | 3.2+ | 5.4+ (полная поддержка seccomp, Landlock) |
| **Память** | 256 MB | 1 GB+ (при нагрузке >500 одновременных сессий) |
| **Хранилище** | 100 MB | SSD (для журналов и KRL при большом числе отзывов) |

### Инициализация окружения

```bash
# Обновление пакетов
sudo apt update && sudo apt upgrade -y openssh-server

# Проверка версии OpenSSH
sshd -V
# → sshd version OpenSSH_9.8p1, ...

# Создание рабочей директории для CA
sudo mkdir -p /etc/ssh/ca
sudo chmod 700 /etc/ssh/ca
```

### Требования к безопасности хранения ключей

Приватные ключи CA (`ca_user`, `ca_host`) должны храниться на отдельном хосте или в HSM/Vault с доступом только для администраторов. Ключи не должны присутствовать на production-серверах в plain text.

## Основные концепции

### Принцип работы иерархии доверия

В отличие от традиционной модели `authorized_keys` (Trust on First Use, TOFU), SSH CA обеспечивает централизованное управление:

1. **Доверие к корню**: Публичный ключ CA (`ca_user.pub`) размещается на всех серверах один раз.
2. **Выпуск**: Пользователь генерирует локальную пару ключей и отправляет запрос на подпись. CA выпускает сертификат с заданным временем жизни (TTL).
3. **Верификация**: При подключении сервер проверяет только подпись CA на предъявленном сертификате и соответствие метаданных (время, логин, principals). Если подпись валидна — доступ разрешен.

### Жизненный цикл сертификата

1. **Создание запроса**: Пользователь генерирует пару ключей (или использует существующую).
2. **Подпись CA**: Администратор или автоматизированный скрипт подписывает публичный ключ пользователя, задавая principals, TTL и critical options.
3. **Распространение**: Сертификат (`id_ed25519-cert.pub`) передается пользователю и добавляется в `~/.ssh/` или встраивается в скрипт автоматической поставки.
4. **Использование**: При подключении клиент автоматически предъявляет сертификат; сервер верифицирует подпись CA.
5. **Истечение**: По истечении TTL сертификат автоматически становится невалидным; клиенту требуется новая подпись.
6. **Отзыв**: Если сертификат скомпрометирован до истечения срока, его серийный номер добавляется в KRL.

### Архитектура инфраструктуры CA

```
Offline CA Host (HSM / Vault / HSM-backed host)
  |-- ca_user.key (offline, подпись пользовательских сертификатов)
  |-- ca_host.key (offline, подпись хостовых сертификатов)
       |
       +---> Production Server 1: TrustedUserCAKeys /etc/ssh/ca_user.pub
       |         HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub
       |
       +---> Production Server 2: TrustedUserCAKeys /etc/ssh/ca_user.pub
                 RevokedKeys /etc/ssh/ca_revoked_keys
```

**Offline CA Host**: Хранит приватные ключи CA (`ca_user.key`, `ca_host.key`) на изолированном хосте или в HSM/Vault. Никогда не доступен из production-сети.

**Production Server**: Содержит только публичные ключи CA (`ca_user.pub`, `ca_host.pub`) и пути к сертификатам в `sshd_config`. Приватные ключи CA на серверах отсутствуют.

### Сравнение моделей аутентификации

| Модель | Масштабируемость | Безопасность | Аудит | Сложность администрирования |
| :--- | :--- | :--- | :--- | :--- |
| **TOFU / authorized_keys** | Низкая (ручное управление) | Средняя (зависит от прав на файл) | Ограниченный | Высокая при >50 серверов |
| **AuthorizedKeysCommand** | Средняя (зависит от бэкенда) | Средняя (зависит от источника) | Умеренный | Средняя |
| **SSH CA** | Высокая (централизованное доверие) | Высокая (короткие TTL, KRL, principals) | Полный (Key ID, сроки) | Низкая после развертывания |

### Типы сертификатов

- **Пользовательские (User Certificates)**: Используются для входа на сервер. Заменяют записи в `~/.ssh/authorized_keys`.
- **Хостовые (Host Certificates)**: Используются серверами для подтверждения своей подлинности клиентам. Это полностью решает проблему «Warning: Remote host identification has changed» и избавляет от необходимости подтверждать отпечатки ключей вручную.

### Преимущества перед статическими ключами

- **Централизация**: Отзыв доступа или добавление нового пользователя не требует подключения к целевым серверам.
- **Ограничение по времени**: Сертификаты могут выдаваться на часы или даже минуты (Short-lived certs), что делает их кражу бессмысленной.
- **Аудит**: Каждый сертификат имеет уникальный ID (Key ID), который фиксируется в системных логах при входе.
- **Принципы наименьших привилегий**: Возможность жесткого ограничения principals, source-address и force-command на уровне сертификата.

## Практические сценарии

### Сценарий 1: Развертывание инфраструктуры SSH CA

**Задача**: Развернуть двухуровневую инфраструктуру: отдельный хост для CA и группу production-серверов, доверяющих этому CA.

**1. Генерация ключей центра сертификации (на isolated хосте):**
```bash
# Ключ для подписи пользователей (хранить offline)
ssh-keygen -t ed25519 -f ~/.ssh/ca_user -C "SSH User CA" -N ""

# Ключ для подписи хостов (хранить offline)
ssh-keygen -t ed25519 -f ~/.ssh/ca_host -C "SSH Host CA" -N ""
```
# → Результат: ca_user, ca_user.pub, ca_host, ca_host.pub

**2. Настройка серверов для доверия пользователям:**
Скопируйте `ca_user.pub` на каждый сервер в `/etc/ssh/ca_user.pub` (права 644, владелец root:root).
Добавьте в `/etc/ssh/sshd_config`:
```ssh
TrustedUserCAKeys /etc/ssh/ca_user.pub
```
Проверка конфигурации и применение:
```bash
sudo sshd -t
sudo systemctl reload sshd
# → Проверка логов: journalctl -u sshd | grep -i "trustedusercakeys"
```

**3. Настройка клиентов для доверия хостам:**
Добавьте публичный ключ `ca_host.pub` в файл `~/.ssh/known_hosts` (или глобально в `/etc/ssh/ssh_known_hosts`) с префиксом `@cert-authority`:
```text
@cert-authority *.example.com ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI...
```
Валидация:
```bash
ssh -o BatchMode=yes web01.example.com echo "ok"
# → При первом подключении не должно быть запроса на подтверждение fingerprint
```

### Сценарий 2: Выпуск пользовательского сертификата

**Задача**: Выдать пользователю `developer` доступ под именами `dev` и `ubuntu` на 8 часов.

```bash
# Подписание публичного ключа пользователя
# -s: ключ CA
# -I: ID сертификата (для логов)
# -n: список разрешенных логинов (principals)
# -V: срок действия (от текущего момента +8 часов)
ssh-keygen -s ~/.ssh/ca_user -I "dev_access_123" -n dev,ubuntu -V +8h id_ed25519.pub

# → Результат: файл id_ed25519-cert.pub
```

Валидация выпуска:
```bash
# Просмотр метаданных сертификата
ssh-keygen -L -f id_ed25519-cert.pub
# → Проверка principals, срока действия и Key ID

# Тестовый вход (должен пройти без запроса пароля)
ssh -i id_ed25519 dev@web01.example.com
# → В логах сервера:Accepted publickey for dev from ... cert authz key ID "dev_access_123"
```

### Сценарий 3: Выпуск хостового сертификата

**Задача**: Подписать ключ сервера `web01.example.com`.

```bash
# На стороне сервера используется его хостовый ключ /etc/ssh/ssh_host_ed25519_key.pub
ssh-keygen -s ~/.ssh/ca_host -I "host_web01" -h -n web01.example.com,10.0.1.5 -V +52w /path/to/ssh_host_ed25519_key.pub

# В sshd_config сервера нужно указать путь к сертификату:
# HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub
```

Валидация хостового сертификата:
```bash
sudo sshd -t
sudo systemctl reload sshd

# С клиента:
ssh -o BatchMode=yes web01.example.com echo "host ok"
# → Не должно быть предупреждения "Remote host identification changed"
```

### Сценарий 4: Управление отзывом через KRL (Key Revocation List)

Если сертификат скомпрометирован до истечения срока его действия, его необходимо отозвать.

**1. Создание списка отзыва:**
```bash
ssh-keygen -k -f /etc/ssh/ca_revoked_keys
```

**2. Добавление серийного номера или ключа в список:**
```bash
ssh-keygen -k -u -f /etc/ssh/ca_revoked_keys compromised_user_key.pub
```

**3. Подключение списка в `sshd_config`:**
```ssh
RevokedKeys /etc/ssh/ca_revoked_keys
```

**4. Валидация отзыва:**
```bash
sudo sshd -t
sudo systemctl reload sshd

# Попытка входа с отозванным сертификатом должна завершиться ошибкой:
# → Received disconnect from ...: 11: Bye Bye [preauth]
```

### Сценарий 5: Атомарная ротация CA с нулевым простоем

**Задача**: Заменить истекший корневой ключ CA без потери доступа для активных пользователей.

```bash
# 1. Генерация нового корневого ключа CA
ssh-keygen -t ed25519 -f ~/.ssh/ca_user_v2 -C "SSH User CA v2" -N ""

# 2. На всех серверах добавить доверие к новому CA
sudo tee -a /etc/ssh/sshd_config << 'EOF'
# Доверие к обоим CA во время перехода
TrustedUserCAKeys /etc/ssh/ca_user.pub /etc/ssh/ca_user_v2.pub
EOF

# 3. Выпуск сертификатов новым CA (параллельно)
for user in devops admin; do
  ssh-keygen -s ~/.ssh/ca_user_v2 -I "rotated_${user}" -n ${user} -V +8h ${user}_id_ed25519.pub
done

# 4. Проверка и применение
sudo sshd -t && sudo systemctl reload sshd

# 5. После полного перехода удаление старого CA
sudo sed -i '/ca_user\.pub/d' /etc/ssh/sshd_config
sudo sshd -t && sudo systemctl reload sshd
```

## Диагностика и устранение неполадок

### Типичные ошибки и их решения

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `Certificate invalid: not yet valid` | Часы на сервере и клиенте рассинхронизированы | Проверить NTP: `timedatectl status`; синхронизировать через `chronyd`/`systemd-timesyncd` |
| `Certificate invalid: expired` | TTL сертификата истек | Выпустить новый сертификат с актуальным `-V`; проверить текущий через `ssh-keygen -L` |
| `Certificate signed by non-CA key` | Файл `TrustedUserCAKeys` указывает на обычный ключ, а не CA | Убедиться, что используется публичный ключ CA (`ca_user.pub`), а не сертификат или приватный ключ |
| `Invalid certificate` / `key too short` | Алгоритм ключа не соответствует политике `PubkeyAcceptedAlgorithms` | Добавить `ssh-ed25519-cert-v01@openssh.com` в `PubkeyAcceptedAlgorithms` или использовать алгоритм, разрешенный на сервере |
| `User not in principal list` | Пользователь пытается войти под именем, отсутствующим в principals | Выпустить новый сертификат с правильным `-n` или добавить principal в существующий (требует переподписи) |
| `No matching certificate found` | Клиент не передает сертификат (отсутствует `-i` или агент не загружен) | Проверить `ssh -vvv`; убедиться, что сертификат добавлен в агент: `ssh-add -l` |
| `Revoked certificate` | Серийный номер сертификата присутствует в KRL | Проверить KRL: `ssh-keygen -Q -f /etc/ssh/ca_revoked_keys id_ed25519-cert.pub`; удалить из KRL при необходимости |
| `sshd: KRL parse error` | Поврежденный файл KRL или неверный формат | Пересоздать KRL; проверить права доступа: `chmod 644 /etc/ssh/ca_revoked_keys` |

### Диагностический чеклист

```bash
# 1. Проверка конфигурации sshd
sudo sshd -T | grep -E "TrustedUserCAKeys|RevokedKeys"
# → Должен отображаться путь к ca_user.pub и ca_revoked_keys

# 2. Валидация сертификата пользователя
ssh-keygen -L -f ~/.ssh/id_ed25519-cert.pub
# → Проверка: Valid, principals, key ID, serial

# 3. Проверка KRL
ssh-keygen -Q -f /etc/ssh/ca_revoked_keys id_ed25519-cert.pub
# → Если ключ не отозван — вывода нет; если отозван — выводится serial

# 4. Отладка подключения с сертификатом
ssh -vvv -i id_ed25519 dev@web01.example.com
# → Поиск строк: "cert-authz", "key ID", "principals", "signature accepted"

# 5. Проверка логов сервера
sudo journalctl -u sshd --since "10 minutes ago" | grep -E "cert authz|Invalid certificate|Revoked"
```

## Рекомендации по безопасности

1. **Offline-хранение CA**: Приватные ключи CA не должны находиться на production-серверах. Используйте выделенный хост, HSM или Vault.
2. **Кратковременные сертификаты**: Устанавливайте TTL не более 8–24 часов для пользователей и не более 52 недель для хостов. Это ограничивает окно компрометации.
3. **Принцип наименьших привилегий**: Используйте `-O force-command`, `-O source-address` и `-O no-pty` при подписании, чтобы сузить возможности злоумышленника при краже сертификата.
4. **Приватный ключ CA**: Храните `ca_user` и `ca_host` на зашифрованных носителях. Используйте аппаратные модули безопасности (HSM, YubiHSM) или HashiCorp Vault с поддержкой transit secrets engine.
5. **Аудит**: Включите `LogLevel VERBOSE` для фиксации Key ID и fingerprint в логах. Интегрируйте логи в SIEM.
6. **Ротация**: Планируйте ротацию ключей CA раз в 1–2 года. Используйте сценарий атомарной ротации (см. Сценарий 5).
7. **KRL**: Поддерживайте актуальный KRL. Автоматизируйте добавление записей при увольнении сотрудников или компрометации ключей.
8. **Приоритет сертификатов**: В `PubkeyAcceptedAlgorithms` явно укажите сертификатные алгоритмы перед обычными ключами, чтобы клиенты с валидными сертификатами не падали на password аутентификацию.

## Крайние случаи и ограничения

| Случай | Поведение / Риск | Рекомендация |
| :--- | :--- | :--- |
| **Пустой principals при подписании** | Сертификат валиден для ЛЮБОГО пользователя, которого сервер может создать (например, `root`). | Всегда указывайте `-n` с конкретными principals; избегайте пустого списка. |
| **Совмещение `TrustedUserCAKeys` и `authorized_keys`** | Если пользователь присутствует и в CA, и в `authorized_keys` — сервер может выбрать любой метод. | Для аудита используйте `TrustedUserCAKeys` как единственный источник; исключите дубли из `authorized_keys`. |
| **Nested `Match` с CA** | OpenSSH не поддерживает вложенные `Match`. `TrustedUserCAKeys` внутри `Match` работает, но вложенные блоки игнорируются. | Используйте один `Match` с несколькими критериями: `Match User alice Group sftp-users Address 10.0.0.0/8`. |
| **KRL с большим числом отзывов** | Файл KRL может расти до сотен МБ, замедляя загрузку sshd. | Разбивайте KRL по группам или используйте промежуточные CA с отдельными KRL. |
| **Сертификат с `cert-authority` в known_hosts и измененный ключ** | Если хост изменил ключ, но запись в `known_hosts` остается с `@cert-authority`, клиент продолжает доверять любому сертификату, подписанному этим CA. | При компрометации хостового CA немедленно замените `@cert-authority` запись на новый CA или конкретные ключи. |
| **ForceCommand с интерактивными скриптами** | Если `force-command` задает неинтерактивный скрипт, а клиент запрашивает shell — соединение завершается. | Убедитесь, что скрипт не требует TTY; при необходимости используйте `no-pty` в critical options. |
| **Сертификаты и Ansible / автоматизация** | Ansible playbook, выполненный под статическим ключом, не увидит переменные окружения из сертификата. | Используйте `ansible_ssh_private_key_file` с сертификатом или настройте `ProxyJump` через bastion с CA. |

## Дополнительная информация

### Критические опции сертификатов (Critical Options)

При подписании можно добавить дополнительные ограничения:
- `force-command="cmd"`: Принудительный запуск конкретной команды.
- `source-address="192.168.1.0/24"`: Ограничение по IP источника.
- `no-pty`: Запрет выделения псевдотерминала.
- `no-port-forwarding`: Запрет проброса портов.
- `no-agent-forwarding`: Запрет проброса SSH-агента.
- `no-X11-forwarding`: Запрет проброса X11.
- `no-user-rc`: Запрет выполнения `~/.ssh/rc`.

По умолчанию сертификаты разрешают проброс портов и агента. Если это не требуется, используйте флаг `-O clear` при подписании, чтобы сбросить все разрешения, и добавляйте нужные через `-O permit-X`.

### Пример: выпуск ограниченного сертификата для CI/CD

```bash
ssh-keygen -s ~/.ssh/ca_user \
  -I "ci_runner_$(date +%Y%m%d)" \
  -n deploy \
  -V +4h \
  -O force-command="/usr/local/bin/ci-runner.sh" \
  -O no-pty \
  -O no-agent-forwarding \
  -O no-port-forwarding \
  -O source-address="10.0.2.0/24" \
  ci_runner_id_ed25519.pub
```

### Защита приватного ключа CA

Безопасность всей инфраструктуры SSH CA держится на приватных ключах `ca_user` и `ca_host`.
- **Offline CA**: Ключи не должны храниться на серверах, доступных извне.
- **HSM / Vault**: Рекомендуется использовать аппаратные модули безопасности или специализированное ПО.
- **Автоматизация**: Для крупных сред используйте [HashiCorp Vault: Secret Engines](../../../../Vault/concepts.md#движки-секретов-secret-engines), который автоматизирует выпуск кратковременных сертификатов через API.

### Интеграция с системной аутентификацией

SSH CA может работать совместно с PAM для дополнительных проверок. Однако при использовании `TrustedUserCAKeys` аутентификация считается успешной после верификации сертификата; PAM выполняется, но не может отклонить доступ на основе пароля (если только не настроены дополнительные методы).

Для интеграции с LDAP/AD и автоматическим созданием домашних директорий используйте [PAM: обзор и настройка](../../pam_overview.md).

### Диагностика сертификатов

Для просмотра содержимого и метаданных файла сертификата:
```bash
ssh-keygen -L -f id_ed25519-cert.pub
```

Для проверки отзыва конкретного сертификата:
```bash
ssh-keygen -Q -f /etc/ssh/ca_revoked_keys id_ed25519-cert.pub
```
