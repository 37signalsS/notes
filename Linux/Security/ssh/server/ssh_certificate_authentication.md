# SSH-аутентификация по сертификатам (SSH CA)

## Определения

**SSH CA (Certificate Authority)** — это модель аутентификации в OpenSSH, основанная на инфраструктуре открытых ключей (PKI). Вместо доверия конкретным публичным ключам пользователей, серверы доверяют подписи единого центра сертификации.

**SSH-сертификат** — это публичный ключ пользователя или хоста, дополненный метаданными (идентификатор, список разрешенных логинов, срок действия) и подписанный приватным ключом CA.

## Основные концепции

### Принцип работы SSH CA

В отличие от традиционного подхода с `authorized_keys`, где ключи хранятся децентрализованно на каждом сервере, SSH CA позволяет централизовать управление доступом.

1.  **Доверие к CA**: Открытый ключ CA (`ca_user.pub`) размещается на всех серверах инфраструктуры.
2.  **Выпуск сертификата**: Пользователь генерирует обычную пару ключей и отправляет публичный ключ на сервер CA.
3.  **Подписание**: CA подписывает ключ, создавая файл сертификата (`id_ed25519-cert.pub`).
4.  **Аутентификация**: При подключении клиент предъявляет серверу свой сертификат. Сервер проверяет подпись CA и метаданные (не истек ли срок, разрешен ли логин).

### Типы сертификатов

-   **Пользовательские сертификаты**: Аутентифицируют пользователя на сервере. Содержат список допустимых системных логинов (`principals`).
-   **Хостовые сертификаты**: Позволяют серверу подтвердить свою подлинность клиенту, избавляя от ручного подтверждения отпечатков в `known_hosts`.

## Практические сценарии

### Сценарий 1: Развертывание SSH CA

**1. Генерация ключей CA**

```bash
# Генерация ключа для подписи пользователей
ssh-keygen -t ed25519 -f ~/.ssh/ca_user -C "SSH User CA"
```

**2. Настройка серверов для доверия CA**

Скопируйте `ca_user.pub` на все целевые серверы (например, в `/etc/ssh/ca_user.pub`) и добавьте директиву в `/etc/ssh/sshd_config`:

```ini
TrustedUserCAKeys /etc/ssh/ca_user.pub
```

Перезапустите SSH: `sudo systemctl restart ssh`.

**3. Подписание ключа пользователя**

```bash
# Подписание ключа id_ed25519.pub
# -s: путь к ключу CA
# -I: внутренний идентификатор (для логов)
# -n: список разрешенных логинов (principals)
# -V: срок действия (например, на 1 день)
ssh-keygen -s ~/.ssh/ca_user -I "user_id_123" -n root,admin -V +1d id_ed25519.pub
```

В результате будет создан файл `id_ed25519-cert.pub`.

### Сценарий 2: Использование сертификата клиентом

Пользователю достаточно иметь файлы `id_ed25519` и `id_ed25519-cert.pub` в одной директории. OpenSSH автоматически обнаружит сертификат при подключении.

Для проверки содержимого сертификата:
```bash
ssh-keygen -L -f id_ed25519-cert.pub
```

### Сценарий 3: Отзыв сертификатов (KRL)

Для досрочного отзыва сертификатов используется список отозванных ключей (KRL — Key Revocation List).

**1. Создание списка:**
```bash
ssh-keygen -k -f /etc/ssh/ca_revoked_keys
```

**2. Добавление ключа в список:**
```bash
ssh-keygen -k -u -f /etc/ssh/ca_revoked_keys compromised-cert.pub
```

**3. Подключение списка в sshd_config:**
```ini
RevokedKeys /etc/ssh/ca_revoked_keys
```

## Жизненный цикл SSH-сертификатов

Сертификаты имеют строго ограниченный период валидности. Это ключевое преимущество перед статическими ключами.

1.  **Создание**: Задается период через флаг `-V [начало]:[конец]`.
2.  **Использование**: Права действуют только в рамках указанного окна.
3.  **Истечение**: По истечении срока сертификат становится недействительным автоматически.
4.  **Пролонгация**: Требуется повторное подписание ключа (часто автоматизируется через API или PAM-системы).

## Сравнение подходов

| Характеристика | authorized_keys | SSH CA (Certificates) |
| :--- | :--- | :--- |
| **Масштабируемость** | Низкая (децентрализовано) | Высокая (централизовано) |
| **Срок действия** | Бессрочно (по умолчанию) | Ограничен метаданными |
| **Отзыв доступа** | Ручное удаление строк | Автоматическое истечение или KRL |
| **Управление** | Трудоемкое (на каждом узле) | Удобное (только на CA) |
| **Сложность внедрения** | Низкая | Средняя (требует инфраструктуры CA) |
| **Безопасность** | Средняя (риск забытых ключей) | Высокая (короткоживущие доступы) |

## Дополнительная информация

### Защита центра сертификации (CA)

Безопасность всей инфраструктуры зависит от защиты приватного ключа CA:
- Хранение на изолированной машине или в HSM/Vault.
- Ограничение доступа к операциям подписания через аутентификацию (например, через PAM/SSO).
- Обязательное журналирование всех фактов выпуска сертификатов.
- Регулярная ротация ключей CA.
