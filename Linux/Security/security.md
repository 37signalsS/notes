# Безопасность в Linux

## Linux Security Modules (LSM) Framework

**Linux Security Modules (LSM)** — это фреймворк в ядре Linux, который предоставляет стандартизированную инфраструктуру для реализации различных моделей принудительного контроля доступа (Mandatory Access Control, MAC). Его основная задача — позволить разработчикам создавать модули безопасности, которые могут усиливать стандартные права доступа в Linux, не требуя при этом внесения изменений в основной код ядра.

**Как это работает (Hook-based security):**

LSM встраивает "хуки" (hooks) в ключевые точки кода ядра, которые вызываются непосредственно перед выполнением критически важных операций, таких как:
-   Доступ к файлу (`open`, `read`, `write`).
-   Выполнение программы (`execve`).
-   Работа с сетью (создание сокета, прием пакета).
-   Управление процессами (`fork`, `kill`).

Когда происходит такая операция, ядро передает управление активному модулю LSM. Модуль анализирует контекст (какой процесс, какой ресурс, какие права) и выносит вердикт: **разрешить** или **запретить** операцию.

**Зачем это нужно:**
-   **Модульность:** Позволяет "подключать" различные модели безопасности (SELinux, AppArmor, Smack) без перекомпиляции ядра.
-   **Централизация:** Обеспечивает единый механизм для контроля доступа по всей системе.
-   **Безопасность:** Позволяет реализовать более строгие политики, чем стандартная модель прав `DAC` (Discretionary Access Control), где правами управляет владелец файла.

**SELinux** и **AppArmor** являются самыми известными реализациями, построенными на базе фреймворка LSM.

## SELinux (Security-Enhanced Linux)

**SELinux** — это модуль безопасности ядра Linux, который реализует систему принудительного контроля доступа (Mandatory Access Control, MAC). В отличие от стандартной модели прав доступа в Linux (Discretionary Access Control, DAC), где правами управляет владелец файла, SELinux применяет централизованные политики безопасности, от которых не могут отказаться ни пользователи, ни процессы.

Основная задача SELinux — ограничить ущерб от скомпрометированных процессов, не позволяя им выйти за рамки своего "контекста безопасности".

Подробное описание SELinux, его режимов работы, инструментов управления и практических примеров настройки находится в документе [SELinux (Security-Enhanced Linux): Управление и Практика](./selinux_management.md).

## AppArmor

**AppArmor** — это инструмент, который может помочь администраторам ограничить права пользователей, определив конкретные профили для пользователей и связанных с ними процессов. Он реализует систему принудительного контроля доступа (Mandatory Access Control, MAC) на основе путей к файлам.

Следуя шагам, описанным в статье, администраторы могут создавать профили AppArmor, анализировать их и вводить ограничения на разрешения пользователей. В конечном счете, внедрение этих методов приводит к созданию более безопасной и эффективной системы Linux.

*Дальнейшие подробности по созданию и управлению профилями AppArmor, включая информацию из Части 1 и Части 2 статьи, будут добавлены здесь.*

## Seccomp (Secure Computing Mode)


**Seccomp** — это механизм безопасности в ядре Linux, который работает как "фильтр" системных вызовов (syscalls), доступных процессу. Его основная задача — ограничить поверхность атаки на ядро, запрещая процессу выполнять любые системные вызовы, кроме строго определённого набора. Это эффективный способ изоляции приложений, особенно в контейнерах.

Seccomp работает в двух режимах:

1.  **`strict`**: Очень строгий режим, который разрешает процессу использовать только 4 системных вызова: `read()`, `write()`, `_exit()` и `sigreturn()`. Любая другая попытка системного вызова завершает процесс с сигналом `SIGKILL`.
2.  **`filter` (seccomp-bpf)**: Гибкий режим, который позволяет определять произвольные правила фильтрации с помощью BPF (Berkeley Packet Filter). Этот режим используется в Docker и Kubernetes для применения профилей безопасности, которые разрешают только необходимые для работы контейнера системные вызовы.

### Практическое применение

#### Проверка режима Seccomp у процесса

Информацию о режиме seccomp для конкретного процесса можно найти в файле `/proc/<PID>/status`:

```bash
# Проверить статус seccomp для текущей оболочки
cat /proc/$$/status | grep Seccomp
```
-   `Seccomp: 0` — seccomp отключен.
-   `Seccomp: 1` — режим `strict`.
-   `Seccomp: 2` — режим `filter`.

#### Применение в Docker

Docker по умолчанию использует seccomp-профиль, который блокирует около 44 из 300+ системных вызовов, считающихся опасными или редко используемыми.

Можно запустить контейнер с кастомным профилем безопасности:

```bash
# Запуск контейнера с пользовательским JSON-файлом профиля seccomp
docker run --security-opt seccomp=/path/to/custom_profile.json alpine
```

Или полностью отключить seccomp (не рекомендуется):

```bash
docker run --security-opt seccomp=unconfined ...
```

Seccomp, наряду с Namespaces и Capabilities, является одним из фундаментальных строительных блоков, обеспечивающих изоляцию контейнеров в Linux.


## Capabilities

Традиционная модель прав в Unix делит все процессы на две категории: непривилегированные (обычные пользователи) и полностью привилегированные (`root`, UID 0). Такой подход "всё или ничего" небезопасен. Механизм **capabilities** решает эту проблему, разделяя всемогущество `root` на отдельные, гранулярные привилегии.


Процесс может иметь только тот набор "способностей", который ему действительно необходим для работы, не получая полных прав суперпользователя. Например, веб-серверу для работы на порту 80 нужна только привилегия `CAP_NET_BIND_SERVICE`, а не полный доступ к системе.

### Преимущества

-   **Повышение безопасности:** Если процесс с ограниченным набором capabilities будет скомпрометирован, злоумышленник не получит полные права `root`.
-   **Принцип наименьших привилегий:** Процессы работают с минимально необходимым набором прав.

### Управление capabilities

#### Просмотр capabilities

-   **Для файла (с помощью `getcap`):**
    ```bash
    # Проверить capabilities, назначенные файлу
    getcap /bin/ping
    ```
    *В некоторых системах путь может быть `/usr/bin/ping`.*

-   **Для запущенного процесса:**
    Информацию о capabilities, которыми обладает процесс, можно найти в файле `/proc/<PID>/status`.
    ```bash
    # Проверить capabilities текущей оболочки
    cat /proc/$$/status | grep Cap
    ```

#### Назначение и удаление capabilities

-   **`setcap`**: Устанавливает или удаляет capabilities для файла.

    **Примеры:**
    ```bash
    # Дать бинарному файлу право работать с сырыми сокетами (нужно для ping)
    sudo setcap cap_net_raw=ep /bin/ping

    # Дать бинарному файлу право слушать порты ниже 1024
    sudo setcap cap_net_bind_service=+ep /path/to/binary

    # Удалить все capabilities с файла
    sudo setcap -r /path/to/binary
    ```
    -   `=ep` или `=+ep` означает "добавить capability в наборы **E**ffective и **P**ermitted".
    -   `-r` удаляет все capabilities.

## KASLR (Kernel Address Space Layout Randomization)

**KASLR** — это механизм безопасности ядра Linux, который случайным образом размещает код самого ядра, его модули и другие ключевые структуры в виртуальной памяти при каждой загрузке системы.

### Зачем это нужно?

Основная цель KASLR — усложнить эксплуатацию уязвимостей ядра. Многие атаки (например, с использованием техники возвратно-ориентированного программирования, ROP) требуют от злоумышленника знания точных адресов функций или гаджетов в памяти ядра. Если эти адреса постоянно меняются, атака, успешная на одной машине, с высокой вероятностью провалится на другой или даже после простой перезагрузки.

KASLR является аналогом **ASLR (Address Space Layout Randomization)**, который применяется для защиты приложений в пространстве пользователя, но перенесенным на уровень ядра.

### Как это работает

При каждой загрузке ядро выбирает случайное смещение и размещает свой код и данные по этому новому адресу. Это делает непредсказуемыми адреса системных вызовов, внутренних функций и структур данных ядра.

KASLR включен по умолчанию в большинстве современных дистрибутивов Linux.

## Системный аудит с помощью `auditd`

**`auditd`** — это подсистема аудита в ядре Linux, которая позволяет отслеживать и записывать события, связанные с безопасностью, такие как доступ к файлам и системные вызовы.

Подробное описание `auditd`, его настройка и примеры использования находятся в документе [Аудит доступа: auditd](../SystemAdministration/Logging/auditd.md).

## Изоляция процессов: сокрытие процессов от других пользователей

По умолчанию в большинстве дистрибутивов Linux любой пользователь может видеть все процессы, запущенные в системе, с помощью команд `ps`, `top` или `htop`. Хотя детальная информация (например, переменные окружения) доступна только владельцу процесса или `root`, сам факт существования процессов, их PID и имена видны всем. Это может представлять угрозу безопасности, раскрывая информацию о запущенных сервисах и их активности.

Чтобы усилить безопасность, можно настроить ядро так, чтобы пользователи могли видеть **только свои собственные процессы**.

Это достигается путем монтирования виртуальной файловой системы `/proc` со специальной опцией `hidepid`.

**Возможные значения `hidepid`:**

-   `hidepid=0` (по умолчанию): Все пользователи могут видеть все процессы.
-   `hidepid=1`: Пользователи видят только свои процессы. Содержимое директорий `/proc/<PID>` скрыто от других пользователей, но сами директории (и, следовательно, номера PID) все еще видны.
-   `hidepid=2` (рекомендуется): Пользователи видят только свои процессы. Директории `/proc/<PID>`, принадлежащие другим пользователям, становятся для них невидимыми. Это наиболее строгий и безопасный вариант.

Дополнительно можно использовать опцию `gid`, чтобы создать группу-исключение (например, `auditors`), члены которой смогут видеть все процессы, как и `root`.

Чтобы изменения сохранялись после перезагрузки, необходимо отредактировать файл `/etc/fstab`.

1.  **Откройте `/etc/fstab` с правами `root`:**
    ```sh
    sudo nano /etc/fstab
    ```

2.  **Найдите строку, отвечающую за монтирование `/proc`** (или добавьте новую, если ее нет).

3.  **Добавьте опции `hidepid=2` и `gid=...`** в четвертое поле (опции монтирования).

    **Пример строки в `/etc/fstab`:**
    ```
    # <file system> <mount point>   <type>  <options>         <dump>  <pass>
    proc            /proc           proc    defaults,hidepid=2,gid=procview 0       0
    ```
    -   `hidepid=2`: Включает строгую изоляцию.
    -   `gid=procview`: Задает имя группы (или ее GID), которая будет исключена из этого правила. Не забудьте создать эту группу (`sudo groupadd procview`) и добавить в нее доверенных пользователей (`sudo usermod -aG procview <username>`).

4.  **Перемонтируйте `/proc`, чтобы применить изменения немедленно:**
    ```sh
    sudo mount -o remount /proc
    ```

После этого обычные пользователи, залогинившись в систему, при выполнении `ps aux` или `htop` увидят только свои собственные процессы и системные процессы, запущенные от их имени.
