# Landlock

## Определения

**Landlock** — современный модуль безопасности Linux (LSM), реализующий механизм песочницы (sandboxing) на уровне приложений. Он позволяет непривилегированным процессам (не требующим прав `root`) самостоятельно ограничивать собственный доступ к ресурсам ядра, таким как файловая система, сеть и механизмы IPC.

**Принцип «Замка изнутри»:** В отличие от традиционных LSM (SELinux, AppArmor), управление которыми осуществляется администратором через внешние политики, Landlock позволяет разработчику интегрировать логику безопасности непосредственно в код приложения. Процесс сам «запирает дверь», прежде чем начать обработку потенциально опасных данных (например, парсинг файлов из внешних источников).

## История и эволюция

### Предпосылки и разработка (2015–2021)

Landlock возник из необходимости обеспечить sandboxing для десктопных приложений (браузеры, офисные пакеты) и контейнеризированных рабочих нагрузок без участия системного администратора. Традиционные LSM требуют централизованного управления политиками, что создает задержку между потребностью в изоляции и её реализацией.

Разработка началась в 2015 году как часть проекта **Mickaël Salaün** (AFuz). Ключевые вехи:
- **2015–2018:** Прототипы, обсуждения в LKML, отработка архитектуры на основе inodes.
- **2019:** Первый патч серия, принятая в mainline.
- **2021 (ядро 5.13):** Интеграция Landlock v1 в ядро Linux.

### Итерации ABI (2021–2026)

Landlock развивается итеративно через версии ABI. Приложение должно проверять поддерживаемую версию ядра перед применением правил.

| Версия ABI | Ядро | Год | Основные возможности |
| :--- | :--- | :--- | :--- |
| **v1** | 5.13 | 2021 | Базовый доступ к ФС (чтение, запись, выполнение, создание директорий). |
| **v2** | 5.44 | 2022 | Уточнение прав на создание файлов и директорий, обработка символических ссылок. |
| **v3** | 6.0 | 2023 | Улучшенная обработка монтирования, уточнение правил для `O_TMPFILE`. |
| **v4** | 6.7 | 2024 | Контроль сетевого стека: ограничения на операции `bind` и `connect` для TCP. |
| **v5** | 6.10 | 2024 | **Контроль IOCTL:** возможность ограничения вызовов `ioctl(2)` для символьных и блочных устройств. |
| **v6** | 6.12 | 2024 | **IPC Scoping:** ограничение сигналов (`SIGKILL`, `SIGSTOP`) и доступа к абстрактным сокетам UNIX вне домена. |
| **v7** | 6.15 | 2025 | **Управление аудитом:** флаги для контроля логирования отказов (например, `LOG_NEW_EXEC_ON`). |

## Основные концепции

### Ключевые особенности

*   **Unprivileged (Без прав root):** Любой процесс может создать и применить правила Landlock. Это критически важно для контейнеризированных приложений и пользовательского ПО (браузеры, офисные пакеты).
*   **Стекируемость (Stackable):** Landlock работает поверх других LSM. Он может только сужать права доступа, установленные SELinux или AppArmor, но никогда не может их расширить.
*   **Иерархичность и наследование:** Ограничения, наложенные на родительский процесс, автоматически наследуются всеми дочерними потоками и процессами. Отменить их невозможно.
*   **Безопасность путей (No TOCTOU):** В отличие от Seccomp, Landlock оперирует объектами ядра (inodes), а не строковыми путями, что исключает атаки типа Time-of-Check to Time-of-Use.

### Архитектура и интеграция в ядро

Landlock функционирует как стандартный LSM, перехватывающий операции доступа до их выполнения:

1.  **Создание ruleset:** Процесс вызывает `landlock_create_ruleset()`, определяя набор ресурсов, которые он намерен ограничивать (`handled_access_fs`, `handled_access_net`, `handled_access_ioctl`). Ядро возвращает файловый дескриптор ruleset.
2.  **Добавление правил:** Через `landlock_add_rule()` процесс привязывает конкретные пути (правило `PATH_BENEATH`) или порты к ruleset с указанными правами доступа (`allowed_access`).
3.  **Активация:** Перед применением ruleset процесс должен установить флаг `no_new_privs` через `prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)`. Это гарантирует, что последующий `execve()` не получит новых привилегий и не обойдет песочницу.
4.  **Ограничение:** `landlock_restrict_self()` применяет ruleset к текущему потоку. Ядро проверяет `no_new_privs` и, если флаг установлен, связывает правила с `task_struct`.
5.  **Наследование:** Все дочерние процессы, созданные через `fork()`/`clone()` после `landlock_restrict_self()`, наследуют restrictions. Правила не могут быть ослаблены или удалены.

**Важность `no_new_privs`:** Без этого флага `landlock_restrict_self()` завершится ошибкой `EPERM`. `no_new_privs` также блокирует SUID-бинарники, файловые capabilities и другие механизмы повышения привилегий через `execve()`, обеспечивая непроницаемость песочницы.

### Ключевые термины

| Термин | Описание |
| :--- | :--- |
| **Ruleset** | Набор правил Landlock, привязанный к файловому дескриптору. Определяет, какие типы ресурсов (`fs`, `net`, `ioctl`) будут ограничены. |
| **Path Beneath** | Правило доступа, разрешающее или запрещающее операции в пределах указанной директории (на основе inode). |
| **`no_new_privs`** | Флаг ядра, запрещающий процессу получать новые привилегии через `execve()`. Обязателен для активации Landlock. |
| **ABI Version** | Версия интерфейса Landlock, определяющая доступные права доступа. Приложение должно проверять совместимость с ядром. |
| **`LANDLOCK_DENY`** | Событие аудита, генерируемое при попытке доступа, нарушающей правила Landlock. |
| **Stackable LSM** | Архитектура, позволяющая нескольким LSM работать одновременно. Landlock может только сужать права, установленные другими LSM. |

### Сравнение с современными механизмами (2026)

| Характеристика | Seccomp | Landlock (ABI v7+) | AppArmor | SELinux |
| :--- | :--- | :--- | :--- | :--- |
| **Объект фильтрации** | Системные вызовы (номера syscalls) | Объекты ресурсов (пути ФС, порты, сигналы) | Пути и профили приложений | Метки (контексты) всех объектов |
| **Контекст данных** | Не видит содержимое указателей | **Видит и проверяет** объекты, на которые указывают аргументы | Видит пути и домены приложений | Видит полный контекст (user:role:type) |
| **Привилегии** | `no_new_privs` (не требует root) | **Не требуются** (плюс `no_new_privs`) | Требует root для загрузки профилей | Требует root для управления политиками |
| **Управление** | Процесс / контейнерный runtime | Приложение само (self-sandboxing) | Администратор ОС | Администратор ОС / Security Team |
| **Основная цель** | Снижение поверхности атаки на ядро | Изоляция бизнес-логики и данных | Изоляция приложений администратором | Мандатный контроль доступа (MAC) |

### Преимущества и ограничения

**Преимущества:**
1.  **Defence in Depth:** Даже при наличии RCE-уязвимости атакующий будет заперт в пустой директории без доступа к сети.
2.  **Нулевое администрирование:** Не требует настройки сложных профилей на стороне ОС.
3.  **Производительность:** Проверки выполняются в контексте LSM с минимальными задержками.
4.  **Гранулярность:** Правила привязываются к inode, что исключает атаки обхода через симлинки и TOCTOU.

**Ограничения:**
1.  **Модификация кода:** Требуется интеграция через системные вызовы или библиотеки.
2.  **Зависимость от ядра:** Старые ядра (до 5.13) не поддерживают механизм, а расширенные функции требуют свежих релизов (6.x/7.x).
3.  **Однонаправленность:** Правила могут только сужать права. После `landlock_restrict_self()` откат невозможен.
4.  **Ограниченная сеть:** Контроль сети доступен только начиная с ABI v4 (ядро 6.7+).

## Практические сценарии

### 1. Проверка поддержки ядра и версии ABI

Перед использованием Landlock необходимо убедиться, что ядро поддерживает требуемую версию ABI.

```bash
# Проверка версии ядра
uname -r
# → 6.12.0-1-amd64 (поддерживает ABI v1–v6)

# Проверка, что Landlock загружен в ядро
zgrep LANDLOCK /proc/config.gz 2>/dev/null || \
  grep CONFIG_LANDLOCK /boot/config-$(uname -r)
# → CONFIG_LANDLOCK=y

# Проверка поддерживаемой версии ABI (требует landlock-utils или liblandlock)
# Альтернативно: через /sys/kernel/security/lsm
cat /sys/kernel/security/lsm | grep landlock
# → landlock
```

### 2. Ограничение доступа к файловой системе (C)

Типичный сценарий: разрешить приложению читать только конфигурацию и писать только в лог.

```c
#include <linux/landlock.h>
#include <sys/prctl.h>
#include <fcntl.h>
#include <unistd.h>

int main() {
    // 1. Создание набора правил (ruleset)
    struct landlock_ruleset_attr attr = {
        .handled_access_fs = LANDLOCK_ACCESS_FS_READ_FILE |
                             LANDLOCK_ACCESS_FS_WRITE_FILE,
    };
    int ruleset_fd = landlock_create_ruleset(&attr, sizeof(attr), 0);
    if (ruleset_fd < 0) {
        perror("landlock_create_ruleset");
        return 1;
    }

    // 2. Добавление исключения: разрешить чтение /etc/myapp
    struct landlock_path_beneath_attr path = {
        .allowed_access = LANDLOCK_ACCESS_FS_READ_FILE,
        .parent_fd = open("/etc/myapp", O_PATH | O_DIRECTORY),
    };
    if (path.parent_fd < 0) {
        perror("open");
        return 1;
    }
    if (landlock_add_rule(ruleset_fd, LANDLOCK_RULE_PATH_BENEATH, &path, 0) < 0) {
        perror("landlock_add_rule");
        return 1;
    }

    // 3. Активация песочницы
    if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) < 0) {
        perror("prctl");
        return 1;
    }
    if (landlock_restrict_self(ruleset_fd, 0) < 0) {
        perror("landlock_restrict_self");
        return 1;
    }

    // С этого момента доступ к путям за пределами /etc/myapp вернет EACCES
    close(ruleset_fd);
    return 0;
}
```

Компиляция и проверка:

```bash
gcc -o sandbox sandbox.c
./sandbox
# При попытке открыть /etc/passwd → EACCES
```

### 3. Использование в Go

Высокоуровневая библиотека для интеграции Landlock в Go-приложения:

```go
import "github.com/landlock-lsm/go-landlock/landlock"

func main() {
    // Разрешить только чтение /usr/lib и /etc/ssl
    err := landlock.V1.RestrictPaths(
        landlock.RODirs("/usr/lib", "/etc/ssl"),
    )
    if err != nil {
        log.Fatalf("Could not restrict: %v", err)
    }
    // С этого момента доступ к другим путям будет возвращать EACCES
}
```

### 4. Ограничение сетевых соединений (ABI v4+)

Предотвращение выхода процесса в интернет или подключения к неавторизованным ресурсам:

*   **`LANDLOCK_ACCESS_NET_BIND_TCP`:** Разрешает прослушивание порта.
*   **`LANDLOCK_ACCESS_NET_CONNECT_TCP`:** Разрешает установку исходящего соединения.

```c
struct landlock_ruleset_attr attr = {
    .handled_access_net = LANDLOCK_ACCESS_NET_BIND_TCP |
                          LANDLOCK_ACCESS_NET_CONNECT_TCP,
};
```

### 5. Отладка и устранение проблем

#### Типичные ошибки и решения

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `landlock_create_ruleset: EINVAL` | Ядро не поддерживает указанный `handled_access_*` | Проверить версию ABI через `uname -r`; понизить требуемые права до поддерживаемых |
| `landlock_restrict_self: EPERM` | Флаг `no_new_privs` не установлен | Вызвать `prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)` перед `landlock_restrict_self()` |
| `EACCES` при открытии файла | Путь не входит в разрешенные `PATH_BENEATH` | Добавить недостающую директорию через `landlock_add_rule()` |
| `LANDLOCK_DENY` в аудите, но процесс работает | Флаги аудита ABI v7+ не настроены | Проверить, что `ruleset_attr` включает нужные флаги аудита (если поддерживается ядром) |
| Правила не наследуются дочерним процессом | `landlock_restrict_self()` вызван после `fork()` | Вызывать `landlock_restrict_self()` до создания дочерних процессов |

#### Аудит и отладка

Начиная с **ABI v7**, Landlock позволяет гибко настраивать аудит. Для диагностики используйте:

```bash
# Проверка событий Landlock в системном логе
journalctl -k | grep LANDLOCK_DENY
# → "audit: landlock: denied ..."

# Трассировка отказов через strace
strace -f -e trace=%file ./sandboxed-app 2>&1 | grep -E "EACCES|EAGAIN"
```

### 6. Интеграция с systemd

Для сервисов, запускаемых через systemd, sandboxing можно реализовать через вспомогательный бинарный wrapper:

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My App with Landlock sandbox

[Service]
ExecStartPre=/usr/bin/landlock-wrapper --fs-read /etc/myapp --fs-write /var/log/myapp
ExecStart=/usr/bin/myapp
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
```

Директива `NoNewPrivileges=yes` эквивалентна установке `no_new_privs` и предотвращает получение новых привилегий через `execve()`.

### 7. Ограничение планировщика (cron)

Для задач cron, выполняющих недоверенный код, можно использовать wrapper-скрипт:

```bash
#!/bin/bash
# /usr/local/bin/landlock-cron-wrapper

# Разрешить доступ только к рабочим директориям
LANDLOCK_FS_READ="/data/input,/etc/ssl/certs"
LANDLOCK_FS_WRITE="/data/output,/tmp"

# Вызов Landlock через Python-скрипт (см. следующий пример)
exec /usr/local/bin/landlock-py \
  --fs-read $LANDLOCK_FS_READ \
  --fs-write $LANDLOCK_FS_WRITE \
  "$@"
```

```cron
# Crontab entry
0 2 * * * landlock-cron-wrapper /opt/scripts/process-data.sh
```

### 8. Профилирование через strace

Для определения, какие пути и системные вызовы использует приложение:

```bash
# Запуск под strace с фильтрацией файловых операций
strace -f -e trace=file,network -o trace.log ./my-app

# Анализ уникальных путей доступа
grep -oP '"(/[^"]+)"' trace.log | sort -u

# Проверка попыток доступа за пределами разрешенных директорий
grep "EACCES" trace.log
```

### Уровни совместимости

| Обозначение | Описание |
| :--- | :--- |
| **[OK]** | Стандартный профиль работает без изменений. |
| **[!]** | Требуется добавление 1–3 исключений в PATH_BENEATH. |
| **[BLOCKED]** | Требуется capability или syscall, которые Landlock не может заменить (например, `CAP_SYS_ADMIN` для монтирования). |

## Ограничения и архитектурные нюансы

1.  **Требует изменений в коде:** В отличие от AppArmor/SELinux, Landlock не может быть применён к существующему бинарнику без перекомпиляции или использования wrapper-скриптов.
2.  **Ограниченная сетевая поддержка:** Полный контроль сети (TCP bind/connect) доступен только с ABI v4 (ядро 6.7+).
3.  **Нет контроля mount namespace:** Landlock не может предотвратить монтирование файловых систем внутри namespace. Для этого требуются отдельные механизмы (User Namespace + restrictions).
4.  **Наследование необратимо:** После вызова `landlock_restrict_self()` процесс и все его потомки навсегда получают ограничения. Отменить их можно только завершив процесс.
5.  **Взаимодействие с другими LSM:** Landlock работает поверх других LSM, но не заifies их логики. Если AppArmor или SELinux уже заблокировали доступ, Landlock не получит управление.
