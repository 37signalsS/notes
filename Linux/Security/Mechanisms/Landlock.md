# Landlock

## Определения

**Landlock** — это современный модуль безопасности Linux (LSM), реализующий механизм песочницы (sandboxing) на уровне приложений. Он позволяет непривилегированным процессам (не требующим прав `root`) самостоятельно ограничивать собственный доступ к ресурсам ядра, таким как файловая система, сеть и механизмы IPC.

**Принцип «Замка изнутри»:** В отличие от традиционных LSM (SELinux, AppArmor), управление которыми осуществляется администратором через внешние политики, Landlock позволяет разработчику интегрировать логику безопасности непосредственно в код приложения. Процесс сам «запирает дверь», прежде чем начать обработку потенциально опасных данных (например, парсинг файлов из сети).

## Основные концепции

### Ключевые особенности

*   **Unprivileged (Без прав root):** Любой процесс может создать и применить правила Landlock. Это критически важно для контейнеризированных приложений и пользовательского ПО (браузеры, офисные пакеты).
*   **Стекируемость (Stackable):** Landlock работает поверх других LSM. Он может только сужать права доступа, установленные SELinux или AppArmor, но никогда не может их расширить.
*   **Иерархичность и наследование:** Ограничения, наложенные на родительский процесс, автоматически наследуются всеми дочерними потоками и процессами. Отменить их невозможно.
*   **Безопасность путей (No TOCTOU):** В отличие от Seccomp, Landlock оперирует объектами ядра (inodes), а не строковыми путями, что исключает атаки типа Time-of-Check to Time-of-Use.

### Версии ABI и эволюция (2021–2026)

Landlock развивается итеративно через версии ABI. Приложение должно проверять поддерживаемую версию ядра перед применением правил.

| Версия ABI | Ядро | Год | Основные возможности |
| :--- | :--- | :--- | :--- |
| **v1** | 5.13 | 2021 | Базовый доступ к ФС (чтение, запись, выполнение, создание директорий). |
| **v4** | 6.7 | 2024 | Контроль сетевого стека: ограничения на операции `bind` и `connect` для TCP. |
| **v5** | 6.10 | 2024 | **Контроль IOCTL:** возможность ограничения вызовов `ioctl(2)` для символьных и блочных устройств. |
| **v6** | 6.12 | 2024 | **IPC Scoping:** ограничение сигналов (`SIGKILL`, `SIGSTOP`) и доступа к абстрактным сокетам UNIX вне домена. |
| **v7** | 6.15 | 2025 | **Управление аудитом:** флаги для контроля логирования отказов (например, `LOG_NEW_EXEC_ON`). |
| **v8** | 7.0 | 2026 | **Thread Sync (TSYNC):** принудительная синхронизация правил между всеми потоками процесса. |

### Сравнение с Seccomp

| Характеристика | Seccomp | Landlock |
| :--- | :--- | :--- |
| **Объект фильтрации** | Системные вызовы (номера syscalls) | Объекты ресурсов (пути ФС, порты, сигналы) |
| **Контекст данных** | Не видит содержимое указателей | **Видит и проверяет** объекты, на которые указывают аргументы |
| **Сложность** | Высокая (требует знания архитектуры syscall) | Низкая (оперирует привычными понятиями доступа) |
| **Основная цель** | Снижение поверхности атаки на ядро | Изоляция бизнес-логики и данных |

### Преимущества и ограничения

**Преимущества:**
1. **Defence in Depth:** Даже при наличии RCE-уязвимости атакующий будет заперт в пустой директории без доступа к сети.
2. **Нулевое администрирование:** Не требует настройки сложных профилей на стороне ОС.
3. **Производительность:** Проверки выполняются в контексте LSM с минимальными задержками.

**Ограничения:**
1. **Модификация кода:** Требуется интеграция через системные вызовы или библиотеки.
2. **Зависимость от ядра:** Старые ядра (до 5.13) не поддерживают механизм, а расширенные функции требуют свежих релизов (6.x/7.x).

## Практические сценарии

### 1. Ограничение доступа к файловой системе (C)

Типичный сценарий: разрешить приложению читать только конфигурацию и писать только в лог.

```c
#include <linux/landlock.h>
#include <sys/prctl.h>

// 1. Создание набора правил (ruleset)
struct landlock_ruleset_attr attr = {
    .handled_access_fs = LANDLOCK_ACCESS_FS_READ_FILE | LANDLOCK_ACCESS_FS_WRITE_FILE,
};
int ruleset_fd = landlock_create_ruleset(&attr, sizeof(attr), 0);

// 2. Добавление исключения: разрешить чтение /etc/myapp
struct landlock_path_beneath_attr path = {
    .allowed_access = LANDLOCK_ACCESS_FS_READ_FILE,
    .parent_fd = open("/etc/myapp", O_PATH | O_DIRECTORY),
};
landlock_add_rule(ruleset_fd, LANDLOCK_RULE_PATH_BENEATH, &path, 0);

// 3. Активация песочницы
prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
landlock_restrict_self(ruleset_fd, 0);
```

### 2. Использование в Go (библиотека landlock-go)

В облачной разработке часто используется высокоуровневая обертка для Go:

```go
import "github.com/landlock-lsm/go-landlock/landlock"

func main() {
    // Разрешить только чтение /usr/lib и /etc/ssl
    err := landlock.V1.RestrictPaths(
        landlock.RODirs("/usr/lib", "/etc/ssl"),
    )
    if err != nil {
        log.Fatalf("Could not restrict: %v", err)
    }
    // С этого момента доступ к другим путям будет возвращать EACCES
}
```

### 3. Ограничение сетевых соединений (ABI v4+)

Предотвращение выхода процесса в интернет или подключения к базе данных, если это не предусмотрено:

*   **LANDLOCK_ACCESS_NET_BIND_TCP:** Разрешает прослушивание порта.
*   **LANDLOCK_ACCESS_NET_CONNECT_TCP:** Разрешает установку исходящего соединения.

## Дополнительная информация

### Аудит и отладка

Начиная с **ABI v7**, Landlock позволяет гибко настраивать аудит. Это решает проблему «невидимых» отказов, когда приложение перестает работать без объяснения причин в системных логах. 
При разработке рекомендуется использовать `landlock-utils` и системный аудит (`auditd`) для отслеживания событий `LANDLOCK_DENY`.
