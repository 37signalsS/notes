# Seccomp

## Определения

**Seccomp (Secure Computing Mode)** — механизм безопасности в ядре Linux, работающий как фильтр системных вызовов (syscalls), доступных процессу. Основная задача — ограничение поверхности атаки на ядро путём запрета процессу выполнять любые системные вызовы, кроме строго определённого набора. Ключевой инструмент для изоляции приложений, особенно в контейнерах.

## Основные концепции

### Режимы работы

| Режим | Описание | Применение |
| :--- | :--- | :--- |
| **`strict`** | Разрешает только 4 syscall: `read()`, `write()`, `_exit()`, `sigreturn()`. Любая другая попытка вызова немедленно завершает процесс сигналом `SIGKILL` | Максимальная безопасность, очень простые программы |
| **`filter` (seccomp-bpf)** | Гибкая политика через BPF (Berkeley Packet Filter). Позволяет создавать белые или чёрные списки системных вызовов | Docker, Kubernetes, браузеры, кастомные профили |

### Как это работает внутри

Когда процесс делает системный вызов, ядро перед его выполнением прогоняет запрос через **BPF-фильтр**.

* Фильтр написан на ограниченном языке, компилируется один раз и выполняется в контексте ядра крайне быстро.
* Результат фильтрации: `ALLOW` (разрешить), `ERRNO` (вернуть ошибку), `TRAP` (сгенерировать сигнал), или `KILL` (немедленно завершить процесс).

### Роль в изоляции контейнеров

Seccomp — один из трёх фундаментальных строительных блоков изоляции контейнеров в Linux:

| Механизм | Что изолирует |
| :--- | :--- |
| **Namespaces** | Ресурсы: файловая система, сеть, процессы (PID), пользователи |
| **Capabilities** | Привилегии суперпользователя (`root`) |
| **Seccomp** | Взаимодействие процесса с ядром (системные вызовы) |

Поскольку контейнеры используют общее ядро хоста, ограничение syscalls критично. Без seccomp процесс внутри контейнера может вызвать опасные функции (например, `ptrace()`, `keyctl()` или `perf_event_open()`), что может привести к компрометации хоста или других контейнеров.

## Практические сценарии

### 1. Проверка режима Seccomp

Информацию о режиме seccomp для конкретного процесса можно найти в файле `/proc/<PID>/status`.

```bash
# Проверить статус seccomp для текущей оболочки
grep Seccomp /proc/$$/status # → Seccomp: 2
```

Возможные значения:

* `Seccomp: 0` — Отключён.
* `Seccomp: 1` — `strict`.
* `Seccomp: 2` — `seccomp-bpf` (filter).

### 2. Применение в Docker

Docker по умолчанию применяет seccomp-профиль, который блокирует около **44 системных вызовов** из ~300+ доступных. Это снижает поверхность атаки на ядро, не нарушая работу большинства приложений.

**Основные блокируемые syscalls:**

* `ptrace`, `keyctl`, `add_key`, `request_key` — предотвращают манипуляции с памятью процессов и ключами ядра.
* `mount`, `umount2` — запрещают монтирование файловых систем внутри контейнера.
* `kexec_load`, `reboot` — запрещают перезагрузку или смену ядра.
* `perf_event_open` — предотвращает мониторинг производительности, который может раскрыть данные других процессов.

**Посмотреть активный профиль контейнера:**

```bash
docker inspect <container_name_or_id> | grep -A5 seccomp # → "SecurityOpt": [ "seccomp=unconfined" ]
```

**Запуск с пользовательским профилем:**

```bash
# custom_profile.json — правила seccomp в формате JSON
docker run --security-opt seccomp=/path/to/custom_profile.json alpine # → ...
```

**Полное отключение (например, для отладки):**

```bash
docker run --rm -it --security-opt seccomp=unconfined alpine /bin/sh # → / #
```

### 3. Применение в Kubernetes

В Kubernetes профиль seccomp настраивается в контексте безопасности Пода или контейнера (`securityContext`).

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: seccomp-demo
spec:
  securityContext:
    seccompProfile:
      # Использует профиль по умолчанию, предоставляемый средой выполнения контейнеров (Docker, containerd)
      type: RuntimeDefault 
  containers:
  - name: test-container
    image: alpine
    command: ["sleep", "3600"]
    # Можно переопределить профиль на уровне контейнера
    securityContext:
      seccompProfile:
        # Отключает seccomp для этого конкретного контейнера
        type: Unconfined 
```

Доступные типы `seccompProfile`:

* `RuntimeDefault`: Профиль по умолчанию, предоставляемый средой выполнения.
* `Unconfined`: Seccomp не применяется.
* `Localhost`: Используется кастомный профиль, который должен находиться на узле в директории `<kubelet-root-dir>/seccomp/`.

## Дополнительная информация

### Ограничения (Где seccomp не спасает)

Seccomp не является универсальным средством защиты и не заменяет другие механизмы:

* **Не заменяет Namespaces и Capabilities:** Если процессу нужны расширенные сетевые права (`CAP_NET_ADMIN`), seccomp это не заблокирует (если сам syscall разрешен). Это лишь один из слоев эшелонированной защиты (*Defense in Depth*).
* **Сложность настройки:** Создание идеального профиля для сложного приложения — трудоемкий процесс. Слишком строгий профиль может привести к внезапному аварийному завершению программы при вызове редкой функции.
* **Аргументы системных вызовов:** Классический seccomp фильтрует только по номеру syscall и значениям аргументов (регистрам). Он не может глубоко анализировать данные в памяти, на которые указывают указатели (например, конкретные пути к файлам в `open()`).

* **Контекст:** Seccomp — один из механизмов изоляции Linux, описанных в [обзоре механизмов безопасности](../Linux_Security_Mechanisms_Overview.md).
* **Связанные технологии:** [Namespaces](../../Core/namespaces.md), [Capabilities](./Capabilities.md).
