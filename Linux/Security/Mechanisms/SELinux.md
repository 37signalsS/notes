# SELinux (Security-Enhanced Linux)

## Зачем нужен SELinux?

Стандартные права Linux (rwx) основаны на модели **DAC** — доступ определяется владельцем объекта. Однако это не защищает от:

- Вредоносного ПО, запущенного от имени пользователя (например, заражённый браузер может получить доступ к SSH-ключам пользователя).
- Процессов, работающих с повышенными привилегиями.

**SELinux** реализует **MAC** (Mandatory Access Control) — принудительный контроль доступа, где политики нельзя обойти.

## Определения

- **SELinux** — механизм принудительного контроля доступа (Mandatory Access Control, MAC) в ядре Linux. Применяет централизованные политики безопасности, которые нельзя обойти пользователям или процессам.
- **MAC (Mandatory Access Control)** — мандатное управление доступом, где политики определяются централизованно.
- **DAC (Discretionary Access Control)** — дискреционное управление доступом, где правами управляет владелец файла (стандартная модель Linux).
- **LSM (Linux Security Modules)** — фреймворк в ядре Linux для реализации моделей MAC. SELinux построен на базе LSM.
- **AppArmor** — альтернативный LSM-модуль, используемый в Ubuntu, Debian, openSUSE. В отличие от SELinux, основан на **путях**, а не на метках.
- **Контекст безопасности** — метка в формате `user:role:type:level`, хранящаяся в расширенных атрибутах файлов.

### Компоненты контекста безопасности

| Компонент | Описание | Пример |
|-----------|----------|--------|
| **User** | Пользователь SELinux | `system_u`, `unconfined_u` |
| **Role** | Роль, определяющая доступные домены | `system_r`, `object_r` |
| **Type/Domain** | Тип для объектов, домен для процессов | `httpd_t`, `httpd_sys_content_t` |
| **Level** | Уровень чувствительности (MLS/MCS) | `s0`, `s0:c0.c1023` |

### Типы политик

- **TE (Type Enforcement)** — основной механизм контроля доступа в SELinux. Связывает процессы и объекты с типами и определяет правила их взаимодействия (чтение, запись, выполнение).
- **RBAC (Role-Based Access Control)** — управление доступом на основе ролей.
- **MLS (Multi-Level Security)** — многоуровневая система (иерархические уровни: «совершенно секретно», «секретно», «открыто»).
- **MCS (Multi-Category Security)** — многокатегорийная система (неиерархические категории: «проект А», «проект Б»). Расширение MLS для более тонкой сегментации.

#### Type Enforcement (TE) — детализация

TE реализует контроль доступа через типизацию:

| Компонент | Описание | Пример |
|-----------|----------|--------|
| **Типизация объектов** | Файлы, сокеты, устройства получают тип | `httpd_sys_content_t`, `shadow_t` |
| **Типизация процессов** | Процессы работают в доменах (типах) | `httpd_t`, `sshd_t` |
| **Правила доступа** | Политика определяет разрешённые операции между типами | `httpd_t` может читать `httpd_sys_content_t`, но не `shadow_t` |
| **Блокировка ядром** | Нарушения блокируются на уровне ядра | Даже процесс от `root` будет заблокирован |

**Ключевое отличие от DAC:** В стандартной модели Linux владелец файла определяет права (`rwx`). В TE политики централизованы и не могут быть изменены пользователем, включая `root`.

## Основные концепции

### Схема работы

1. **Субъект** (процесс с контекстом) пытается получить доступ к **объекту** (файл, порт с контекстом).
2. SELinux проверяет политики (база данных правил в ядре).
3. На основе сопоставления контекстов — **разрешает** или **запрещает** доступ.
4. Все действия протоколируются.

### Режимы работы

| Режим | Описание | Применение |
|-------|----------|------------|
| **Enforcing** | Политики активно применяются, нарушения блокируются и логируются | Производственная среда |
| **Permissive** | Политики не применяются, но нарушения логируются | Отладка, создание политик |
| **Disabled** | SELinux полностью отключен | Не рекомендуется |

### Булевы значения (Booleans)

Параметризованные политики для включения/отключения функций без изменения всей политики.

**Примеры:**

- `httpd_can_network_connect` — разрешить HTTPD сетевые соединения.
- `samba_enable_home_dirs` — разрешить Samba доступ к домашним каталогам.
- `allow_ftpd_full_access` — полный доступ FTP.

### Особенности применения

- **Гибкое ограничение прав** — на уровне ядра.
- **Снижение рисков** — от ошибок разработчиков или компрометации.
- **Изоляция процессов** — ограничение скомпрометированных процессов.
- **Протоколирование** — все действия записываются в журнал.

> **Важно:** Пользователь `root` с контекстом `unconfined_t` не ограничен SELinux.

## Практические сценарии

### Управление режимами

```bash
# Проверка текущего статуса
sestatus
getenforce

# Временное переключение (до перезагрузки)
sudo setenforce 0  # Permissive
sudo setenforce 1  # Enforcing

# Постоянное отключение (требуется перезагрузка)
# /etc/selinux/config
SELINUX=disabled
```

> Полное отключение (`Disabled`) требует перезагрузки для перемаркировки ФС. `setenforce 0` переводит только в `Permissive`.

### Просмотр контекстов

```bash
# Файлы и каталоги
ls -Z /var/www/html
# drwxr-xr-x. root root system_u:object_r:httpd_sys_content_t:s0 /var/www/html

# Процессы
ps -Z aux | grep nginx
# system_u:system_r:httpd_t:s0 root 12345 ... nginx
```

> Подробнее о `ps`: [`ps`](../../Diagnostics/Processes/ps.md)

### Управление пользователями, ролями, типами

```bash
# Просмотр соответствия системных пользователей пользователям SELinux
semanage login -l

# Привязка пользователя к SELinux-пользователю
sudo semanage login -a -s staff_u user1

# Просмотр пользователей SELinux
semanage user -l

# Просмотр ролей
semanage role -l

# Просмотр типов
seinfo -t
```

### Переходы доменов (Domain Transitions)

Когда один процесс запускает другой, SELinux может разрешить или запретить переход в другой домен.

```bash
# Просмотр разрешённых переходов доменов
sesearch -T -s httpd_t
```

### Управление портами

```bash
# Разрешенные порты для типа http_port_t
semanage port -l | grep http_port_t

# Добавление нового порта
sudo semanage port -a -t http_port_t -p tcp 5080

# Удаление порта
sudo semanage port -d -t http_port_t -p tcp 5080
```

### Управление файловыми контекстами

```bash
# Просмотр правил
semanage fcontext -l | grep '/var/www'

# Добавление правила для нового каталога (постоянное изменение политики)
sudo semanage fcontext -a -t httpd_sys_content_t "/srv/my_app(/.*)?"

# Временное изменение контекста файла (до перезагрузки/перемаркировки)
sudo chcon -t httpd_sys_content_t /srv/my_app/index.html

# Восстановление контекста по умолчанию
sudo restorecon -Rv /srv/my_app
```

> **Примечание:** `chcon` — временное изменение, которое сбрасывается при `restorecon`. Рекомендуется использовать `semanage fcontext` для постоянных изменений.

### Управление булевыми значениями

```bash
# Просмотр всех значений
getsebool -a

# Временное включение/отключение
sudo setsebool httpd_can_network_connect on

# Постоянное включение
sudo setsebool -P httpd_can_network_connect on
```

### Диагностика и устранение проблем

```bash
# Логи аудита (отказы SELinux)
sudo tail -f /var/log/audit/audit.log | grep AVC

# Принудительная перемаркировка файлов при загрузке
sudo touch /.autorelabel
# После перезагрузки система перемаркирует все файлы
```

**Экспорт и импорт политик:**

```bash
# Экспорт всех настроек (порты, контексты, булевы значения)
sudo semanage export -f selinux_settings.mod

# Импорт настроек
sudo semanage import -f selinux_settings.mod
```

**Создание модуля политики:**

```bash
# Генерация модуля из логов
sudo grep "AVC" /var/log/audit/audit.log | audit2allow -M my_custom_policy

# Установка модуля
sudo semodule -i my_custom_policy.pp
```

### Примеры настройки

**Изменение порта SSH:**

```bash
# 1. Изменить порт в /etc/ssh/sshd_config (например, 5022)
# 2. Добавить порт в SELinux
sudo semanage port -a -t ssh_port_t -p tcp 5022
# 3. Перезапустить sshd
```

**Изменение каталога данных MySQL:**

```bash
# Для каталога /srv/mysql
sudo semanage fcontext -a -t mysqld_db_t "/srv/mysql(/.*)?"
sudo restorecon -Rv /srv/mysql
```

### SELinux и Docker

```bash
# Монтирование тома с автоматической сменой контекста
# z — приватный контекст
# Z — общий контекст
docker run -v /host/path:/container/path:z my_image
```

### MCS (Multi-Category Security) — изоляция контейнеров

**MCS** — расширение SELinux для изоляции процессов и контейнеров на одном хосте с более тонкой сегментацией, чем стандартный Type Enforcement.

**Как это работает:**

- Каждый процесс и объект получает набор категорий (categories), которые определяют, к каким «группам» данных он может обращаться.
- MCS проверяет совместимость категорий при доступе к файлам, сокетам и другим ресурсам.
- Даже если политики TE позволяют доступ, несовпадение категорий приведёт к отказу в доступе.

**Формат метки MCS:**

```
system_u:system_r:container_t:s0:c123,c456
```

- `c123,c456` — MCS-категории, назначаемые контейнеру при старте.
- Два контейнера с разными категориями не могут взаимодействовать, даже если имеют одинаковый тип `container_t`.

**Практическое применение в контейнерах:**

| Флаг | Описание | Применение |
|------|----------|------------|
| `:z` | Общая метка SELinux | Несколько контейнеров могут получать доступ к одному volume |
| `:Z` | Приватная метка SELinux | Только один контейнер имеет доступ к volume |

**Пример:**

```bash
# Приватный доступ — только этот контейнер может работать с томом
podman run --rm -it -v ~/data:/data:Z alpine sh

# Общий доступ — несколько контейнеров могут работать с томом
podman run --rm -it -v ~/shared:/data:z alpine sh
```

> **Важно:** MCS обеспечивает изоляцию на уровне ядра, что делает её более надёжной по сравнению с изоляцией на уровне пользователей или процессов.

**Отличие MCS от MLS:**

| Характеристика | MLS | MCS |
|----------------|-----|-----|
| **Структура** | Иерархическая (уровни) | Неиерархическая (категории) |
| **Пример** | «совершенно секретно» > «секретно» | «проект А», «проект Б» (равноправны) |
| **Комбинирование** | Доступ к нижним уровням | Любая комбинация категорий |
| **Основное применение** | Военные, госсектор | Изоляция контейнеров, мультитенант |
