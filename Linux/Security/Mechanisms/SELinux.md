# SELinux (Security-Enhanced Linux): Управление и Практика

## Введение в SELinux

**SELinux (Security-Enhanced Linux)** — это механизм принудительного контроля доступа (Mandatory Access Control, MAC), реализованный в ядре Linux. В отличие от стандартной модели дискреционного контроля доступа (Discretionary Access Control, DAC), где правами управляет владелец файла, SELinux применяет централизованные политики безопасности, которые не могут быть обойдены ни пользователями, ни процессами.

Основная задача SELinux — ограничить ущерб от скомпрометированных процессов, не позволяя им выйти за рамки своего "контекста безопасности".

### История создания

*   Разработано Агентством национальной безопасности США (NSA).
*   Впервые появилось в ядре Linux в 1998 году.
*   В 2003 году был реализован фреймворк LSM (Linux Security Modules), который позволил подключать различные модели безопасности. SELinux вошел в состав ядра Linux 2.6.

### Особенности применения

*   **Гибкое ограничение прав:** SELinux позволяет гибко ограничивать права пользователей и процессов на уровне ядра.
*   **Снижение рисков:** Снижает риски, возникающие вследствие ошибок разработчиков или компрометации приложений. Например, если скомпрометированный процесс попытается выполнить системный вызов, который не соответствует его политике, SELinux заблокирует это действие.
*   **Изоляция процессов:** Ограничивает потенциально опасные или скомпрометированные процессы в правах, не позволяя им выполнять действия, не предусмотренные политикой.
*   **Протоколирование действий:** SELinux записывает все свои действия в системный журнал, что критически важно для аудита и расследования инцидентов безопасности.

## Основные термины и понятия

### MLS (Multi-Level Security) и MCS (Multi-Category Security)

Это механизмы мандатного управления доступом, которые по умолчанию редко используются в повседневной практике. Они характеризуются вертикальным уровнем контроля, используя метки.

*   **Многоуровневая система безопасности (MLS):** Определяет иерархические уровни доступа (например, "совершенно секретно", "секретно", "конфиденциально").
*   **Многокатегорийная система безопасности (MCS):** Определяет неиерархические категории доступа (например, "проект А", "проект Б").

Эти механизмы требуют сложного проектирования политик безопасности и обычно применяются в сферах с высокими требованиями к защите данных (например, финансовые учреждения, государственные структуры). Их можно сравнить с уровнями доступа, такими как "особо важный" или "совершенно секретный", где объекты и пользователи наделяются соответствующими метками.

### RBAC (Role-Based Access Control)

Управление доступом на основе ролей. В SELinux это означает:
*   **SELinux User:** Сущность, которая сопоставляется с обычным пользователем Linux.
*   **Role:** Определяет, в какие домены может входить пользователь.
*   **User:** Пользователь, который входит в определенную роль.

Пользователь, входящий в определенную роль, получает доступ к соответствующим доменам (наборам действий). Это позволяет разделить пользователей на группы и предоставить им доступ к определенным ресурсам, а все остальное по умолчанию запретить.

### Type Enforcement (TE)

Это основной механизм принудительной типизации доступа в SELinux, с которым чаще всего приходится работать.

*   **Контекст безопасности (Security Context):** Является меткой, атрибутом, который хранится в расширенных атрибутах файловой системы. Выглядит как строка переменной длины и объединяет в себе:
    *   **SELinux User:** Пользователь SELinux.
    *   **Role:** Роль.
    *   **Type (Domain):** Тип (для объектов) или домен (для процессов).
    *   **Sensitivity/Category:** Уровень чувствительности/категории (используется в MLS/MCS).

    Пример контекста: `system_u:object_r:httpd_port_t:s0`

    SELinux работает путем сопоставления контекста субъекта (процесса) с контекстом объекта (файла, порта). Если политика разрешает взаимодействие между этими контекстами, действие выполняется; в противном случае — блокируется.

*   **Домен (Domain):** Для процессов домен определяет список разрешенных действий. Это набор правил, описывающих, что процесс может делать с различными объектами.
*   **Тип (Type):** Для объектов (файлов, каталогов, портов) тип определяет, кто может получить к ним доступ.
*   **Роль (Role):** Определяет, в какие домены может входить пользователь, то есть какие наборы действий пользователь имеет право запускать.

### Схема работы SELinux

1.  **Субъект (процесс) с контекстом безопасности** пытается получить доступ к **объекту (файлу, порту) с контекстом безопасности**.
2.  **SELinux** обращается к своим политикам (базе данных правил, загруженной в ядро).
3.  На основе сопоставления контекстов субъекта и объекта, SELinux **разрешает** или **запрещает** доступ.
4.  Все действия протоколируются.

### Фреймворк LSM (Linux Security Modules)

LSM — это фреймворк в ядре Linux, который предоставляет стандартизированную инфраструктуру для реализации различных моделей MAC. Он встраивает "хуки" в ключевые точки кода ядра, которые вызываются перед выполнением критически важных операций. SELinux является одной из реализаций, построенных на базе LSM. LSM позволяет системе работать не с одной конкретной системой контроля доступа, а с любой системой, которую фреймворк поддерживает.

## Режимы работы SELinux

SELinux может работать в трех режимах:

*   **`Enforcing`**: Режим по умолчанию. Политики безопасности активно применяются, все нарушения блокируются и записываются в лог.
*   **`Permissive`**: Политики не применяются (нарушения не блокируются), но все действия, которые были бы запрещены, записываются в лог. Этот режим полезен для отладки и создания политик.
*   **`Disabled`**: SELinux полностью отключен.

### Управление режимами

*   **Проверить текущий статус и режим:**
    ```bash
    sestatus
    ```
*   **Узнать текущий режим (кратко):**
    ```bash
    getenforce
    ```
*   **Временно переключить режим (до перезагрузки):**
    ```bash
    # Перевести в режим "только логирование"
    sudo setenforce 0 # или sudo setenforce Permissive
    # Вернуть в режим принудительного применения политик
    sudo setenforce 1 # или sudo setenforce Enforcing
    ```
*   **Отключить SELinux навсегда (требуется перезагрузка):**
    1.  Откройте файл `/etc/selinux/config` или `/etc/sysconfig/selinux`.
    2.  Измените значение `SELINUX` на `permissive` или `disabled`.
        ```ini
        SELINUX=disabled
        ```
    3.  Перезагрузите систему: `sudo reboot`.

> В средах с повышенными требованиями к безопасности (например, в государственных учреждениях) может быть настроено принудительное применение политики, игнорирующее этот конфигурационный файл. Это делается для того, чтобы системный администратор не мог самостоятельно ослабить защитные механизмы.

## Инструменты для работы с SELinux

Основные утилиты для управления SELinux:

*   **`setools-console` пакет:**
    *   `semanage`: Управление SELinux-политиками (пользователи, порты, файловые контексты, булевы значения).
    *   `seinfo`: Просмотр информации о политиках.
    *   `sesearch`: Поиск правил в политиках.
    *   `audit2allow`: Генерация правил политики из логов аудита.
*   **`policycoreutils` пакет:**
    *   `restorecon`: Восстановление файловых контекстов по умолчанию.
    *   `setenforce`: Временное переключение режима SELinux.
    *   `sestatus`: Отображение статуса SELinux.
    *   `matchpathcon`: Отображение контекста безопасности для файла/каталога.
*   **`audit` пакет:**
    *   `auditctl`: Управление правилами аудита ядра.
    *   `ausearch`: Поиск событий в логах аудита.
    *   `aureport`: Генерация отчетов из логов аудита.

### Использование `mcstransd` для читаемых меток MLS/MCS

Для более удобного чтения меток MLS/MCS (например, `s0`) можно использовать демон `mcstransd`.

1.  **Установить пакет `mcstrans`:**
    ```bash
    sudo dnf install mcstrans # RHEL/CentOS
    sudo apt install mcstrans # Debian/Ubuntu
    ```
2.  **Запустить демон:**
    ```bash
    sudo systemctl start mcstransd
    ```
3.  **Проверить:** Теперь `ls -Z` будет показывать более читаемые метки (например, `SystemLow` вместо `s0`).
    ```bash
    ls -Z /
    # Вывод: dr-xr-xr-x. root root system_u:object_r:root_t:SystemLow /
    ```
    Для пользователя `vagrant` (в Vagrant-виртуалках) это может быть `system_u:object_r:user_home_t:SystemLow-SystemHigh`.

### Просмотр контекстов безопасности

*   **Для файлов и каталогов:** Используйте `ls -Z` или `ls --context`.
    ```bash
    ls -Z /var/www/html
    # Вывод: drwxr-xr-x. root root system_u:object_r:httpd_sys_content_t:s0 /var/www/html
    ```
    Здесь `system_u` - SELinux user, `object_r` - role, `httpd_sys_content_t` - type, `s0` - sensitivity (MLS/MCS).

*   **Для процессов:** Используйте `ps -Z`.
    ```bash
    ps -Z aux | grep nginx
    # Вывод: system_u:system_r:httpd_t:s0 root      12345  0.0  0.1 123456 1234 ?        Ss   ... nginx
    ```
    Здесь `httpd_t` - домен для процесса Nginx.

### Просмотр и управление SELinux-пользователями

```bash
semanage user -l
```

### Просмотр и управление ролями

```bash
semanage role -l
```

### Просмотр и управление типами (доменами)

```bash
seinfo -t
```

### Просмотр и управление портами

SELinux контролирует, какие процессы могут слушать на определенных портах.

*   **Просмотр разрешенных портов для типа:**
    ```bash
    semanage port -l | grep http_port_t
    # Вывод: http_port_t                    tcp      80, 81, 443, 488, 8008, 8009, 8443, 9000
    ```
*   **Добавление нового порта для типа (например, 5080 для Nginx):**
    ```bash
    sudo semanage port -a -t http_port_t -p tcp 5080
    ```
    *   `-a`: добавить.
    *   `-t`: указать тип.
    *   `-p`: указать протокол (tcp/udp).
*   **Удаление порта:**
    ```bash
    sudo semanage port -d -t http_port_t -p tcp 5080
    ```

### Управление файловыми контекстами

SELinux определяет, какой контекст должен быть у файлов и каталогов в зависимости от их пути.

*   **Просмотр правил файловых контекстов:**
    ```bash
    semanage fcontext -l | grep '/var/www'
    # Вывод: /var/www(/.*)?                 all files          system_u:object_r:httpd_sys_content_t:s0
    ```
*   **Изменение контекста для существующего файла/каталога:**
    1.  **Добавление/изменение правила:**
        ```bash
        # Разрешить Nginx читать файлы в /srv/my_app
        sudo semanage fcontext -a -t httpd_sys_content_t "/srv/my_app(/.*)?"
        ```
        *   `-a`: добавить правило.
        *   `-t`: указать тип.
        *   `"/srv/my_app(/.*)?"`: регулярное выражение для пути.
    2.  **Применение нового контекста к файлам:**
        ```bash
        sudo restorecon -Rv /srv/my_app
        ```
        *   `-R`: рекурсивно.
        *   `-v`: подробный вывод.

### Булевы значения (Booleans)

Булевы значения — это параметризованные политики, которые позволяют включать или отключать определенные функции SELinux без изменения всей политики. Они часто используются для разрешения или запрета общих сценариев.

*   **Просмотр всех булевых значений:**
    ```bash
    getsebool -a
    ```
*   **Просмотр конкретного булева значения:**
    ```bash
    getsebool httpd_can_network_connect
    ```
*   **Включение/отключение булева значения (временно):**
    ```bash
    sudo setsebool httpd_can_network_connect on
    ```
*   **Включение/отключение булева значения (постоянно):**
    ```bash
    sudo setsebool -P httpd_can_network_connect on
    ```
    *   `-P`: делает изменение постоянным после перезагрузки.

**Примеры использования булевых значений:**
*   `httpd_can_network_connect`: Разрешает HTTP-серверу (Apache/Nginx) устанавливать сетевые соединения. Полезно, если веб-серверу нужно обращаться к базе данных или API на другом хосте.
*   `samba_enable_home_dirs`: Разрешает Samba расшаривать домашние каталоги пользователей.
*   `allow_ftpd_full_access`: Разрешает FTP-серверу полный доступ к файловой системе.
*   `samba_share_nfs`: Разрешает Samba расшаривать NFS-ресурсы.
*   `allow_mount_fuse`: Разрешает монтирование файловых систем через FUSE.

## Диагностика и устранение проблем

Когда приложение не работает с включенным SELinux, первое, что нужно сделать, это проверить логи аудита.

### Логи аудита

SELinux записывает все свои отказы в системный журнал аудита, который обычно находится в `/var/log/audit/audit.log`.

*   **Просмотр логов SELinux:**
    ```bash
    sudo tail -f /var/log/audit/audit.log | grep AVC
    ```
    Или с помощью `journalctl`:
    ```bash
    sudo journalctl -f -t audit
    ```

### Использование `audit2allow`

`audit2allow` — это мощный инструмент, который анализирует логи аудита и генерирует правила политики SELinux, необходимые для разрешения заблокированных действий.

1.  **Сгенерировать правила из лога:**
    ```bash
    sudo grep "AVC" /var/log/audit/audit.log | audit2allow -M my_custom_policy
    ```
    *   `-M my_custom_policy`: Создает модуль политики с именем `my_custom_policy`. В результате будут созданы два файла: `my_custom_policy.te` (исходный код политики) и `my_custom_policy.pp` (скомпилированный модуль).
2.  **Установить модуль политики:**
    ```bash
    sudo semodule -i my_custom_policy.pp
    ```
    *   `-i`: установить модуль.

### Пример: Изменение порта SSH

1.  **Изменить порт в `/etc/ssh/sshd_config` (например, на 5022).**
2.  **Попытаться перезапустить `sshd`:**
    ```bash
    sudo systemctl restart sshd
    ```
    SELinux заблокирует запуск `sshd` на нестандартном порту.
3.  **Проверить логи аудита:**
    ```bash
    sudo ausearch -c sshd --raw | audit2allow -M sshd_custom_port
    ```
    Это сгенерирует модуль политики.
4.  **Установить модуль:**
    ```bash
    sudo semodule -i sshd_custom_port.pp
    ```
5.  **Добавить порт в SELinux:**
    ```bash
    sudo semanage port -a -t ssh_port_t -p tcp 5022
    ```
6.  **Перезапустить `sshd`:** Теперь сервис должен запуститься без проблем.

### Пример: Изменение контекста для MySQL

Предположим, вы изменили каталог данных MySQL с `/var/lib/mysql` на `/srv/mysql`.

1.  **Изменить контекст каталога:**
    ```bash
    sudo semanage fcontext -a -t mysqld_db_t "/srv/mysql(/.*)?"
    sudo restorecon -Rv /srv/my_sql    
    ```
2.  **Перезапустить MySQL:**
    ```bash
    sudo systemctl restart mysqld
    ```
    Если возникнут проблемы, используйте `audit2allow` для генерации дополнительных правил.

### Пример: Постоянное изменение контекста по умолчанию

Если вы хотите, чтобы новые файлы или каталоги, созданные в определенном месте, автоматически получали нужный контекст безопасности, можно изменить правила контекста по умолчанию.

1.  **Добавить правило контекста для нового каталога (например, `/srv/my_app`):**
    ```bash
    sudo semanage fcontext -a -t httpd_sys_content_t "/srv/my_app(/.*)?"
    ```
    Это правило указывает, что все файлы и подкаталоги в `/srv/my_app` должны иметь тип `httpd_sys_content_t`.
2.  **Применить новый контекст к существующим файлам:**
    ```bash
    sudo restorecon -Rv /srv/my_app
    ```
    Теперь, если вы создадите новый файл в `/srv/my_app`, он автоматически получит правильный контекст.
    Если вы изменили контекст вручную с помощью `chcon`, то `restorecon` вернет его к значению, определенному в правилах `semanage fcontext`.

### SELinux и Docker

SELinux взаимодействует с Docker, контролируя доступ контейнеров к файловой системе хоста. По умолчанию Docker использует SELinux для маркировки файлов, создаваемых контейнерами, что обеспечивает дополнительный уровень изоляции.

*   **Маркировка файлов:** Файлы, созданные Docker-контейнерами, получают контекст `system_u:object_r:container_file_t:s0`.
*   **Монтирование томов:** При монтировании томов в контейнеры может потребоваться явное указание контекста.
    *   `z`: Позволяет контейнеру иметь приватный, неразделяемый контекст для тома.
    *   `Z`: Позволяет контейнеру иметь общий, разделяемый контекст для тома.

    Пример: `docker run -v /host/path:/container/path:z my_image`

## Заключение

SELinux — мощный инструмент безопасности, который, несмотря на свою сложность, значительно повышает защищенность системы. Вместо того чтобы отключать его, рекомендуется изучить основы работы, использовать инструменты диагностики (`audit2allow`) и параметризованные политики (булевы значения) для адаптации к потребностям приложений.

**Важно:** Пользователь `root` с контекстом `unconfined_t` не ограничен SELinux. Это означает, что SELinux не применяет политики к процессам, запущенным от имени `root` в этом контексте.
