# Linux Capabilities

## Определения

**Linux Capabilities** — это механизм ядра Linux, который разделяет полные привилегии суперпользователя (`root`, UID 0) на отдельные, гранулярные единицы доступа. В традиционной модели безопасности Unix процессы делятся на две категории:
1.  **Непривилегированные** (UID != 0): подвергаются строгой проверке прав доступа (DAC).
2.  **Привилегированные** (UID == 0): обходят все проверки безопасности ядра.

Подход "всё или ничего" создает серьезные риски: если приложение, работающее от `root`, будет скомпрометировано, злоумышленник получит полный контроль над системой. Capabilities позволяют реализовать **принцип наименьших привилегий**, выдавая процессу только те специфические права, которые необходимы для его работы (например, только право слушать 80-й порт).

## Основные концепции

### Наборы возможностей (Capability Sets)

Ядро отслеживает пять наборов capabilities для каждого процесса:

*   **`Permitted` (Разрешенные):** Максимальный набор возможностей, которые процесс может использовать или перевести в эффективный набор.
*   **`Effective` (Эффективные):** Набор прав, которые ядро фактически проверяет в данный момент при выполнении системных вызовов.
*   **`Inheritable` (Наследуемые):** Возможности, которые могут быть переданы через вызов `execve()`. Требуют наличия соответствующих `file capabilities` у запускаемого файла.
*   **`Bounding` (Ограничивающий):** Маска, ограничивающая возможности, которые процесс может получить. Удаление возможности из этого набора делает невозможным её получение в будущем (даже если файл имеет SUID или file capabilities).
*   **`Ambient` (Окружающие):** Современный набор (начиная с ядра 4.3), который позволяет непривилегированным процессам передавать свои capabilities дочерним процессам, не имеющим специальных атрибутов на файле. Это решило проблему "потери привилегий" при запуске скриптов или программ, не знающих о capabilities.

### Типы возможностей (Thread vs File)

1.  **Thread Capabilities:** Привязаны к конкретному потоку исполнения в памяти.
2.  **File Capabilities:** Хранятся в расширенных атрибутах файла (`xattrs`) и активируются при его запуске. Позволяют заменить SUID-бит более безопасным механизмом.

## Практические сценарии

### 1. Просмотр текущих привилегий

Вместо чтения битовых масок из `/proc`, рекомендуется использовать утилиту `capsh`.

```bash
# Просмотр возможностей текущего процесса
capsh --print
# → Current: = cap_chown,cap_dac_override,cap_setgid,cap_setuid...
# → Bounding set =cap_chown,cap_dac_override...
```

Для просмотра возможностей другого процесса:
```bash
getpcaps <PID>
```

### 2. Управление возможностями файлов (setcap/getcap)

Утилита `setcap` позволяет назначать права исполняемым файлам.

```bash
# Разрешить веб-серверу занимать порты < 1024 без запуска от root
sudo setcap 'cap_net_bind_service=+ep' /usr/bin/node

# Проверка назначенных прав
getcap /usr/bin/node
# → /usr/bin/node cap_net_bind_service=ep

# Удаление всех capabilities с файла
sudo setcap -r /usr/bin/node
```

**Флаги наборов в setcap:**
*   `e`: Effective (активировать сразу).
*   `p`: Permitted (разрешить использование).
*   `i`: Inheritable (разрешить наследование).

### 3. Использование libcap-ng (filecap)

Альтернативный набор инструментов `libcap-ng` предоставляет утилиту `filecap`, которая удобнее для аудита системы.

```bash
# Список всех файлов в системе с назначенными capabilities
filecap -a

# Назначение прав (синтаксис проще, чем у setcap)
filecap /path/to/binary net_bind_service
```

### 4. Поиск векторов эскалации привилегий

Злоумышленники ищут файлы с избыточными правами для получения полного доступа.

```bash
# Поиск всех файлов с capabilities в системе
getcap -r / 2>/dev/null
```

**Опасные возможности:**

| Capability | Описание риска |
| :--- | :--- |
| `CAP_SETUID` | Позволяет менять UID процесса на 0 (полный root). |
| `CAP_DAC_OVERRIDE` | Обход всех проверок прав доступа к файлам (чтение `/etc/shadow`). |
| `CAP_SYS_ADMIN` | "Новый root". Дает массу прав: монтирование, настройка сети, отладка. |
| `CAP_SYS_PTRACE` | Позволяет отлаживать другие процессы и внедрять в них код. |
| `CAP_CHOWN` | Смена владельца любых файлов (например, `/etc/passwd`). |

**Пример эксплуатации `CAP_SETUID` на Python:**
Если на интерпретатор python по ошибке установлен `cap_setuid+ep`:
```bash
python3 -c 'import os; os.setuid(0); os.system("/bin/sh")'
# → # (получен root shell)
```

## Дополнительная информация

*   **Контейнеризация:** В Docker и Kubernetes capabilities являются ключевым слоем изоляции. По умолчанию большинство возможностей отключено. Рекомендуется использовать `drop: ["ALL"]` и добавлять только нужные. Подробнее: [Security Context в Kubernetes](../../../Kubernetes/Security/pod_security_context.md).
*   **User Namespaces:** Внутри пользовательского пространства имен (User Namespace) процесс может иметь "полные" capabilities, которые не имеют силы за пределами этого пространства имен. Это основа работы rootless-контейнеров.
*   **Взаимодействие с SUID:** При установке file capabilities на файл, имеющий SUID-бит, приоритет отдается capabilities, а SUID-бит может быть проигнорирован ядром (зависит от настроек).
*   **Документация:** `man 7 capabilities` — подробный список всех доступных прав в текущей версии ядра.
