# AppArmor

## Определения

**AppArmor (Application Armor)** — модуль безопасности ядра Linux (LSM), реализующий систему принудительного контроля доступа (Mandatory Access Control, MAC). Разработан компанией **Canonical** и является стандартом для дистрибутивов Ubuntu, Debian и openSUSE.

В отличие от SELinux, AppArmor ориентирован на простоту администрирования:
*   **Идентификация по путям:** объекты (файлы) идентифицируются по их расположению в файловой системе, что делает профили интуитивно понятными.
*   **Избирательность:** механизм ограничивает только те приложения, для которых явно создан профиль. Остальные процессы работают без дополнительных ограничений (unconfined).
*   **Особенность:** привязка к путям создает потенциальную уязвимость перед жесткими ссылками (hard links), позволяющими получить доступ к файлу через альтернативный путь, не описанный в профиле.

Основная задача — минимизация поверхности атаки. Даже если злоумышленник получит права `root` через уязвимость в приложении, AppArmor предотвратит доступ к неразрешённым файлам, сетевым сокетам или системным вызовам.

### Ключевые термины

| Термин | Описание |
| :--- | :--- |
| **Профиль (Profile)** | Текстовый файл с набором правил для конкретного исполняемого файла. |
| **Абстракции (Abstractions)** | Переиспользуемые наборы правил (например, доступ к шрифтам или сети), подключаемые через `#include`. |
| **Enforce (Принуждение)** | Режим, в котором нарушения политики активно блокируются ядром. |
| **Complain (Жалоба)** | Режим обучения: действия разрешены, но нарушения логируются. |
| **Unconfined (Без ограничений)** | Процесс запущен без профиля AppArmor (обычно для большинства системных утилит). |

## Архитектура и компоненты

AppArmor работает на уровне системных вызовов через интерфейс **LSM**. Он идентифицирует объекты по **путям в файловой системе**, что делает его проще в настройке по сравнению с метками в SELinux.

### Структура профиля

Профили хранятся в `/etc/apparmor.d/`. Имя файла обычно совпадает с путем к программе, где `/` заменяется на `.` (например, `/usr/sbin/ntpd` → `usr.sbin.ntpd`).

```text
#include <tunables/global>

/usr/bin/myapp {
  # Подключение стандартных разрешений
  #include <abstractions/base>
  #include <abstractions/nameservice>

  # Разрешения на файлы
  /etc/myapp/config.yaml r,
  /var/log/myapp/*.log rw,
  /var/lib/myapp/** rwk,    # r=read, w=write, k=lock

  # Сеть
  network inet tcp,
  network inet stream,

  # Современные контроли (сигналы и ptrace)
  signal (receive) set=("term", "kill") peer=unconfined,
  ptrace (trace) peer=/usr/bin/debug_tool,

  # Выполнение других программ
  /usr/bin/helper px,      # p = Discrete Profile (выполнение с собственным профилем)
}
```

**Флаги доступа к файлам:**
- `r` (read): чтение.
- `w` (write): запись.
- `a` (append): дозапись.
- `k` (lock): блокировка файла.
- `l` (link): создание жестких ссылок.
- `x` (execute): выполнение.
- `m` (mmap): отображение в память.

## Практические сценарии

### 1. Проверка статуса

```bash
# Текущий статус и список профилей
sudo aa-status

# Краткий отчет (только загруженные профили)
sudo aa-enabled # → Yes
```

### 2. Создание и обучение профиля

Рекомендуемый цикл разработки профиля:

1. **Инициализация:**
   ```bash
   sudo aa-genprof /usr/bin/myapp
   ```
2. **Обучение:** Запустите приложение и выполните все штатные операции. AppArmor запишет события в логи.
3. **Анализ и сохранение:** В интерфейсе `aa-genprof` просмотрите предложенные правила и сохраните профиль.

### 3. Диагностика и отладка

Если приложение ведет себя странно, проверьте логи на наличие отказов (`denied`):

```bash
# Просмотр логов в реальном времени
sudo journalctl -fx | grep -i apparmor

# Интерактивный разбор логов и обновление профиля
sudo aa-logprof
```

**Нюанс Ubuntu 24.04+:**
В новых версиях Ubuntu введено ограничение на создание неинициализированных пользовательских пространств имен (unprivileged user namespaces). Если приложение (например, Docker Rootless или браузеры) падает с ошибкой доступа, может потребоваться настройка:
```bash
# Временное разрешение
sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0
```

### 4. Управление режимами профиля

```bash
# Перевод в режим обучения (Complain)
sudo aa-complain /etc/apparmor.d/usr.bin.myapp

# Перевод в режим блокировки (Enforce)
sudo aa-enforce /etc/apparmor.d/usr.bin.myapp

# Отключение профиля
sudo aa-disable /etc/apparmor.d/usr.bin.myapp
```

## AppArmor в контейнеризации

### Docker
Docker использует профиль по умолчанию (`docker-default`), который блокирует опасные операции (монтирование ФС, доступ к `/proc` и т.д.).
- Проверка профиля контейнера: `docker inspect <id> --format '{{.AppArmorProfile}}'`.
- Запуск со своим профилем: `docker run --security-opt apparmor=my-custom-profile ...`.

### Kubernetes
В K8s AppArmor настраивается на уровне `securityContext` пода (v1.30+) или через аннотации (старые версии).
```yaml
securityContext:
  appArmorProfile:
    type: Localhost
    localhostProfile: my-node-profile
```

## Дополнительная информация

### Инструменты (пакет apparmor-utils)

| Утилита | Назначение |
| :--- | :--- |
| `aa-status` | Просмотр текущего состояния системы. |
| `aa-genprof` | Генерация профиля на основе поведения программы. |
| `aa-logprof` | Обновление существующего профиля по данным из логов. |
| `aa-complain` / `aa-enforce` | Смена режимов работы профилей. |
| `aa-notify` | Отправка уведомлений о нарушениях на рабочий стол. |
