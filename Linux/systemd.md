# Systemd: Управление системой и службами

`systemd` — это современный менеджер системы и служб для Linux, который стал стандартом для большинства дистрибутивов. Он отвечает за инициализацию системы после загрузки ядра, а также за управление службами (демонами), сокетами, точками монтирования и другими системными ресурсами.

## Архитектура 

-   **`systemd` (PID 1)**: Главный демон, который запускается ядром и управляет всеми остальными процессами в системе.
-   **`systemctl`**: Основной инструмент командной строки для взаимодействия с `systemd`. Отправляет команды демону через шину **D-Bus**.
-   **`journald`**: Демон, отвечающий за сбор и хранение логов в структурированном бинарном формате.
-   **`udev`**: Управляет файлами устройств в `/dev` и обрабатывает события подключения/отключения оборудования.
-   **`networkd`, `timedated`, `logind`**: Специализированные демоны для управления сетью, временем и пользовательскими сессиями.

### Юниты (Units)

**Расположение юнит-файлов:**
-   `/usr/lib/systemd/system/`: Юниты, поставляемые с установленными пакетами. **Не изменяйте их напрямую.**
-   `/etc/systemd/system/`: Юниты, созданные или измененные системным администратором. Эти файлы имеют приоритет над файлами в `/usr/lib/`.

**Основные типы юнитов:**
-   `.service`: Системная служба (демон).
-   `.socket`: Сетевой сокет, который может активировать службу при поступлении соединения (socket activation).
-   `.target`: Группа юнитов, аналог "уровней выполнения" (runlevels).
-   `.timer`: Юнит для запуска других юнитов по расписанию, замена `cron`.
-   `.mount` / `.automount`: Точки монтирования файловых систем. `.automount` обеспечивает монтирование по требованию.
-   `.path`: Активирует юнит при изменении в файловой системе (например, появлении файла).

### Таргеты (Targets)

Таргет — это точка синхронизации, которая группирует другие юниты. В `systemd` таргеты являются современной заменой **уровней выполнения (runlevels)** из старой системы инициализации SysV.

**Управление таргетами:**

```bash
# Посмотреть текущий таргет по умолчанию
systemctl get-default

# Установить графический режим как таргет по умолчанию
sudo systemctl set-default graphical.target

# Переключиться в другой таргет "на лету"
sudo systemctl isolate multi-user.target
```

Основные таргеты:

-   `multi-user.target`: Стандартный многопользовательский режим без графического интерфейса (аналог runlevel 3).
-   `graphical.target`: Многопользовательский режим с графическим интерфейсом (аналог runlevel 5).

### Control Groups (cgroups)

Это фундаментальное отличие `systemd` от старых систем. `systemd` помещает каждый сервис в его собственную **контрольную группу (cgroup)**. Это позволяет:
1.  **Надежно отслеживать процессы**: Все дочерние процессы сервиса остаются внутри его cgroup, что позволяет `systemd` видеть их все.
2.  **Ограничивать ресурсы**: Можно легко задать лимиты на CPU, память и I/O для каждого сервиса.
3.  **Гарантированно завершать процессы**: При остановке сервиса `systemd` убивает все процессы в его cgroup, не оставляя "зомби".

**Практические инструменты для cgroups:**
-   `systemd-cgls`: Показывает иерархию cgroups в виде дерева.
-   `systemd-cgtop`: Мониторит потребление ресурсов (CPU, память) по cgroups в реальном времени.

# Перечитать конфигурацию systemd

```bash
sudo systemctl daemon-reload
```

## Управление службами (`systemctl`)

```bash
# Запустить, остановить или перезапустить службу
sudo systemctl start nginx.service
sudo systemctl stop nginx.service
sudo systemctl restart nginx.service

# Перечитать конфигурацию службы без полного перезапуска (если служба это поддерживает)
sudo systemctl reload nginx.service

# Включить или отключить автозапуск службы при загрузке системы
sudo systemctl enable nginx.service
sudo systemctl disable nginx.service

# Показать детальный статус службы, последние логи и иерархию cgroup
systemctl status nginx.service
```

### Разница между `reload` и `restart`

- **`reload`**: "Вежливо" просит службу перечитать свой конфигурационный файл без прерывания работы. Существующие соединения не разрываются. Этот метод работает, только если служба его поддерживает.
- **`restart`**: "Жестко" останавливает все процессы службы и запускает их заново. Это всегда работает, но приводит к кратковременному простою.

```bash
# Сообщить systemd о внесенных изменениях в юнит-файлы
sudo systemctl daemon-reload
```

### Переопределение юнитов (`systemctl edit`)

Чтобы изменить параметры существующей службы, не трогая ее оригинальный файл, используйте `systemctl edit`. Эта команда создаст файл-дополнение (override) в `/etc/systemd/system/имя.service.d/override.conf`, который будет иметь приоритет над основным файлом юнита.

```bash
sudo systemctl edit nginx.service
```

### Управление автозапуском

```bash
# Включить автозапуск службы при загрузке системы
# (создает символическую ссылку в .wants/ каталоге нужного таргета)
sudo systemctl enable nginx.service

# Отключить автозапуск (удаляет симлинк)
sudo systemctl disable nginx.service

# Проверить, включен ли автозапуск (enabled, disabled, static, masked)
systemctl is-enabled nginx.service
```
*Статус `static` означает, что юнит не имеет секции `[Install]` и обычно запускается как зависимость другого юнита.*

### Маскировка служб

Маскировка — это "абсолютный запрет". Она создает символическую ссылку из юнита на `/dev/null`, что делает невозможным его запуск вручную или как зависимость. Это полезно для предотвращения конфликтов (например, между `NetworkManager` и `systemd-networkd`).

```bash
# Полностью запретить запуск службы
sudo systemctl mask NetworkManager.service

# Отменить маскировку
sudo systemctl unmask NetworkManager.service
```

### Просмотр состояния и зависимостей

```bash
# Показать все активные юниты
systemctl list-units

# Показать все установленные юнит-файлы и их статус автозагрузки
systemctl list-unit-files --type=service

# Показать юниты, от которых зависит служба (прямые зависимости)
systemctl list-dependencies nginx.service

# Показать юниты, которые зависят от этой службы (обратные зависимости)
systemctl list-dependencies --reverse nginx.service

# Показать все юниты, которые не смогли запуститься
systemctl --failed
```

## Просмотр логов (`journalctl`)

`systemd` включает в себя мощную подсистему логирования `journald`. Для просмотра и анализа логов используется утилита `journalctl`.

Подробное описание `journalctl` и других утилит для работы с логами находится в документе [logs.md](./logs.md).

### Типы сервисов (`Type=`)

-   `simple` (по умолчанию): `ExecStart` — это главный процесс. `systemd` считает сервис запущенным сразу после его старта.
-   `forking`: `ExecStart` запускает процесс, который создает своего потомка (fork) и завершается. `systemd` считает главным дочерний процесс. Требует указания `PIDFile=`. Используется для "старых" демонов (nginx, httpd).
-   `oneshot`: Для скриптов, которые должны выполниться один раз и завершиться. `systemd` ждет их завершения. Часто используется с `RemainAfterExit=yes`, чтобы сервис считался активным даже после завершения процесса.
-   `notify`: Сервис сам уведомляет `systemd` о готовности через `sd_notify()`. Самый надежный способ управления зависимостями.
-   `dbus`: Сервис считается готовым, когда его имя появляется на шине D-Bus.

### Зависимости между юнитами

- **`After=` / `Before=`**: Управляют только **порядком** запуска, но не создают реальной зависимости.
- **`Wants=`**: "Мягкая" зависимость. `systemd` попытается запустить указанный юнит, но если тот не запустится, это не повлияет на основной юнит.
- **`Requires=`**: "Жёсткая" зависимость. Если юнит, указанный в `Requires=`, не сможет запуститься, то и зависимый от него юнит тоже не запустится.
- **`BindsTo=`**: Самая сильная связь. Работает как `Requires=`, но дополнительно привязывает жизненные циклы. Если связанный юнит останавливается или падает, `systemd` немедленно остановит и этот юнит.
- **`PartOf=`**: Похоже на `BindsTo=`, но работает в одну сторону. Если юнит, указанный в `PartOf=`, останавливается или перезапускается, то же самое произойдёт и с этим юнитом.

### Задачи по расписанию: Timers

Таймеры в `systemd` — это современная и более гибкая замена традиционному `cron`. Они позволяют запускать задачи (юниты `.service`) по расписанию или через определённые промежутки времени. В отличие от `cron`, таймеры лучше интегрированы в систему, поддерживают зависимости и обеспечивают более надёжное логирование через `journald`.

Для планирования задачи с помощью `systemd` требуется два файла:

1.  **Файл службы (`.service`):** Описывает, *что* нужно сделать. Например, `/etc/systemd/system/my_backup.service`.
2.  **Файл таймера (`.timer`):** Описывает, *когда* это нужно сделать. Имя должно совпадать с файлом службы.

**Пример (`/etc/systemd/system/my_backup.timer`):**
```ini
[Unit]
Description=Run backup script daily at 2 AM

[Timer]
# Запускать ежедневно в 2 часа ночи.
OnCalendar=*-*-* 02:00:00
# Если система была выключена, запустить сразу после загрузки
Persistent=true

[Install]
WantedBy=timers.target
```

**Управление таймером:**
```bash
# Включить и запустить таймер (не сервис!)
sudo systemctl enable --now my_backup.timer

# Проверить активные таймеры и время их следующего запуска
systemctl list-timers
```

### Анализ производительности загрузки

`systemd-analyze` помогает выявить узкие места при загрузке системы.

```bash
# Общее время загрузки (ядро + userspace)
systemd-analyze

# Время запуска каждого юнита, отсортированное по убыванию
systemd-analyze blame

# Показать критическую цепь зависимостей, замедливших загрузку таргета
systemd-analyze critical-chain graphical.target
```

### Пользовательские службы

`systemd` может управлять службами для конкретного пользователя. Юниты хранятся в `~/.config/systemd/user/`. Управлять ими можно флагом `--user`.

```bash
systemctl --user start my_app.service
systemctl --user enable my_app.service
```

## Синхронизация времени (NTP)

Точное время критически важно для работы многих системных служб, логирования и криптографии. `systemd` предоставляет встроенные инструменты для управления временем и его синхронизацией по сети с помощью протокола NTP (Network Time Protocol).

### `timedatectl`: Управление временем и датой

`timedatectl` — это основной инструмент для просмотра и изменения системного времени, даты и часового пояса.

```bash
# Показать текущий статус времени, включая статус синхронизации NTP
timedatectl status

# Включить или отключить синхронизацию по NTP
sudo timedatectl set-ntp true

# Установить часовой пояс
sudo timedatectl set-timezone Europe/Moscow
```

### `systemd-timesyncd`: Встроенный клиент NTP

`systemd-timesyncd` — это легковесный клиент SNTP (простая версия NTP), который встроен в `systemd`. Он предназначен для простых задач синхронизации и подходит для большинства клиентских машин и серверов, не требующих высочайшей точности.

-   **Статус:** Управляется через `timedatectl`.
-   **Конфигурация:** `/etc/systemd/timesyncd.conf`. Здесь можно указать кастомные NTP-серверы.

### `Chrony`: Продвинутый демон NTP

Для серверов, требующих высокой точности времени или работающих в сложных сетевых условиях, `chrony` является предпочтительной реализацией NTP. Он работает лучше при нестабильном интернет-соединении и быстрее синхронизирует время.

-   **Установка:** `sudo apt install chrony` или `sudo dnf install chrony`.
-   **Конфигурация:** `/etc/chrony/chrony.conf` (для RHEL-based систем) или `/etc/chrony.conf` (для Debian-based).
-   **Управление и диагностика (`chronyc`):**
    ```bash
    # Проверить источники времени и их статус
    chronyc sources

    # Показать детальную информацию о синхронизации
    chronyc tracking
    ```
-   **Важно:** При установке `chrony` он обычно автоматически отключает `systemd-timesyncd`, чтобы избежать конфликтов. `Chrony` является предпочтительным демоном времени для большинства современных систем благодаря своей точности и способности быстро адаптироваться к изменяющимся условиям сети.


## `systemd-nspawn`: Контейнеризация

`systemd-nspawn` — это утилита, которую можно рассматривать как "chroot на стероидах". Она использует современные технологии ядра Linux ([пространства имён](./namespaces.md), [контрольные группы (cgroups)](./cgroups.md)) для создания легковесных контейнеров.

**Преимущества перед `chroot`:**
-   **Полная изоляция:** Автоматически создаёт отдельные пространства имён для сети, PID, IPC и т.д.
-   **Простота использования:** Может работать с готовыми образами системы или простыми директориями.
-   **Интеграция с `systemd`:** Управляется через `machinectl`, имеет интеграцию с логами (`journald`) и сетью (`networkd`).

**Пример использования:**
```bash
# Запустить контейнер из директории /srv/my-container
sudo systemd-nspawn -D /srv/my-container

# Запустить контейнер и получить для него приватную сеть
sudo systemd-nspawn -D /srv/my-container --network-veth
```

Управлять запущенными контейнерами можно с помощью `machinectl`:
```bash
# Показать список запущенных контейнеров
machinectl list

# Войти в работающий контейнер
machinectl shell <имя_машины>
```
