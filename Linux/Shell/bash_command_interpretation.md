### Общая логика обработки команд в Shell

Чтобы понимать любой сложный случай, держите в голове следующий алгоритм, по которому действует оболочка (bash, zsh и т.д.).

#### Шаг 0: Чтение всей строки
Оболочка считывает **всю** командную строку целиком перед тем, как начать ее интерпретировать.

#### Шаг 1: Настройка перенаправлений ввода/вывода (`>`, `<`, `>>`)

Это **первое, что происходит, еще до запуска самой команды**. Оболочка ищет операторы перенаправления и настраивает файловые дескрипторы.

В стандартном варианте работы программы существуют три основных потока данных, каждый из которых связан с файловым дескриптором:
*   **`0` (stdin)**: Стандартный ввод. Программа читает данные из этого потока.
*   **`1` (stdout)**: Стандартный вывод. Программа записывает обычные результаты своей работы в этот поток.
*   **`2` (stderr)**: Стандартный вывод ошибок. Программа записывает сообщения об ошибках в этот поток.

По умолчанию все эти потоки связаны с терминалом.

*   **Перенаправление стандартного вывода (`>` и `>>`)**
    *   `>`: Перенаправляет `stdout` команды в файл, **перезаписывая** его содержимое, если файл существует. Если файла нет, он будет создан.
    *   `>>`: Перенаправляет `stdout` команды в файл, **добавляя** содержимое в конец файла. Если файла нет, он будет создан.

    **Пример:** `ls -l > output.txt`
    1.  Оболочка видит `> output.txt`.
    2.  Она немедленно пытается открыть `output.txt` для записи. Если нет прав, выдаст ошибку.
    3.  Если права есть, она **очищает файл** `output.txt` (или создает его).
    4.  Только после этого запускается команда `ls -l`, чей `stdout` уже направлен в `output.txt`.

*   **Перенаправление стандартного вывода ошибок (`2>`)**
    *   Для перенаправления `stderr` необходимо явно указать файловый дескриптор `2`.
    *   **Пример:** `ls /nonexistent 2> errors.log` — ошибки `ls` будут записаны в `errors.log`.

*   **Объединение потоков (`2>&1` и `&>`)**
    *   `2>&1`: Перенаправляет `stderr` (дескриптор 2) туда же, куда направлен `stdout` (дескриптор 1). Порядок важен: `> file 2>&1` сначала перенаправит `stdout` в `file`, а затем `stderr` туда же. Если написать `2>&1 > file`, то `stderr` будет направлен туда, куда `stdout` был направлен *до* перенаправления в `file`.
    *   `&>`: Сокращенная форма для перенаправления `stdout` и `stderr` в один и тот же файл. `command &> file` эквивалентно `command > file 2>&1`.

*   **Перенаправление стандартного ввода (`<`)**
    *   `command < input.txt`: Команда будет читать свой `stdin` из файла `input.txt`.

*   **Особый файл `/dev/null`**
    *   `/dev/null` — это специальный "пустой" файл в Unix-подобных системах, который действует как "черная дыра". Все, что в него записывается, исчезает, а при чтении из него не возвращается ничего.
    *   Часто используется для подавления нежелательного вывода: `command > /dev/null 2>&1` (подавить весь вывод).

*   **Дублирование вывода с `tee`**
    *   Команда `tee` позволяет одновременно направлять стандартный вывод команды как в файл, так и на стандартный вывод (консоль).
    *   **Пример:** `ls -l | tee output.txt` — вывод `ls -l` будет показан на экране и сохранен в `output.txt`.
    *   **Пример с добавлением:** `ls -l | tee -a output.txt` — добавит вывод в конец `output.txt`.
    *   **Дублирование `stderr`:** Для дублирования `stderr` необходимо сначала перенаправить его в `stdout`: `command 2>&1 | tee errors.txt`.

*   **Критический порядок интерпретации перенаправлений (проблема `tail file > file`)**
    *   **Важно:** Перенаправления обрабатываются оболочкой **до** выполнения самой команды. Это может привести к потере данных, если входной и выходной файл совпадают.
    *   **Пример фатальной ошибки:** `tail -n 10 large_log.txt > large_log.txt`
        1.  Оболочка считывает всю командную строку.
        2.  Она видит оператор перенаправления `> large_log.txt` и **немедленно приступает к его обработке**.
        3.  Если файл `large_log.txt` существует, он **обнуляется (очищается)**. Если не существует, создается пустой файл.
        4.  Только после этого запускается команда `tail -n 10 large_log.txt`. Но поскольку `large_log.txt` уже пуст, `tail` не находит данных для чтения.
        5.  В результате `large_log.txt` становится пустым.
    *   **Решение:** Чтобы избежать такой потери данных, используйте временный файл или подстановку команд:
        ```bash
        # Использование временного файла
        tail -n 10 large_log.txt > /tmp/temp_log.txt && mv /tmp/temp_log.txt large_log.txt

        # Использование подстановки команд (для некоторых случаев)
        # Например, для ротации логов в одну команду:
        # (head -n 10 large_log.txt > large_log.txt) # НЕПРАВИЛЬНО, head тоже прочитает пустой файл
        # Правильный подход - использовать временный файл или утилиты, которые умеют работать in-place (например, sed -i)
        # Или, как было показано в вебинаре, через переменную:
        # VAR=$(tail -n 10 large_log.txt); echo "$VAR" > large_log.txt
        ```


#### Шаг 2: Группировка в конвейеры (`|`)
Оболочка находит команды, соединенные пайпами (`|`), и группирует их в конвейеры. Важно понимать, что **конвейер имеет более высокий приоритет, чем управляющие операторы `&&` и `||`**.

*   **Пример:** `команда1 && команда2 | команда3`
    Оболочка видит это как: `(команда1) && (команда2 | команда3)`.
    Сначала будет выполнена `команда1`. Если она успешна, будет запущен конвейер `команда2 | команда3`.

*   **Перенаправление STDERR в STDIN конвейера**
    По умолчанию конвейер (`|`) перенаправляет только `stdout` предыдущей команды в `stdin` следующей. Чтобы перенаправить `stderr` в `stdin` следующей команды, можно использовать следующую конструкцию:
    ```bash
    # Пример: перенаправить stderr команды 'docker' в 'grep'
    docker run non_existent_image 2>&1 | grep "Error"
    ```
    Здесь `2>&1` перенаправляет `stderr` (`2`) в `stdout` (`1`), который затем передается по конвейеру в `grep`.

### Порядок поиска и интерпретации команд

Когда вы вводите команду в Bash, оболочка следует строго определенному порядку для ее поиска и интерпретации. Понимание этого порядка критически важно для отладки и предсказуемого поведения скриптов.

1.  **Проверка алиасов (псевдонимов)**
    *   Bash сначала проверяет, не является ли введенная команда **алиасом**. Алиасы — это короткие, настраиваемые псевдонимы для более длинных команд или последовательностей команд.
    *   Если алиас найден, он заменяется на свою полную форму, и процесс интерпретации продолжается с этой новой командой.
    *   **Пример:** `ls` часто является алиасом для `ls --color=auto` или `ls -F`.
    *   Просмотреть текущие алиасы можно командой `alias`. Удалить алиас — `unalias <имя_алиаса>`.
    *   **Важно:** Алиасы действуют только в текущей сессии, если не прописаны в конфигурационных файлах (`.bashrc`, `.bash_profile`).

2.  **Проверка встроенных команд (built-ins)**
    *   Если команда не является алиасом, Bash проверяет, не является ли она **встроенной командой** (shell built-in). Это команды, которые являются частью самой оболочки Bash и не являются отдельными исполняемыми файлами на диске.
    *   **Примеры:** `cd`, `echo`, `pwd`, `type`, `export`, `source`.
    *   Встроенные команды выполняются быстрее, так как не требуют запуска нового процесса.
    *   **Определение типа команды:** Команда `type <команда>` (или `type -a <команда>`) поможет определить, является ли команда встроенной, алиасом или внешней.
        *   **Пример:** `type -a echo` может показать, что `echo` является как встроенной командой оболочки, так и внешней программой (`/usr/bin/echo`). В таких случаях Bash сначала выполнит встроенную версию.
        *   **Пример:** `type -a cd` покажет, что `cd` является встроенной командой оболочки (`cd is a shell builtin`).
        *   **Пример:** `type -a ls` может показать, что `ls` является алиасом, а затем внешней командой (`/usr/bin/ls`).

3.  **Проверка хеш-таблицы команд**
    *   Если команда не является алиасом и не является встроенной, Bash проверяет свою внутреннюю **хеш-таблицу** ранее найденных исполняемых файлов.
    *   Это оптимизация: если команда уже была найдена и выполнена ранее, Bash "помнит" ее полный путь и не тратит время на повторный поиск в `$PATH`.
    *   Просмотреть хеш-таблицу можно командой `hash`. Очистить ее — `hash -r`.
    *   **Важно:** Хеш-таблица значительно ускоряет выполнение команд, но может привести к неожиданному поведению, если исполняемый файл был перемещен, удален или заменен после того, как его путь был закеширован. В таком случае Bash может попытаться выполнить несуществующую команду или старую версию, пока хеш не будет очищен.

4.  **Поиск в переменной окружения `$PATH` (внешние команды)**
    *   Если команда не найдена на предыдущих шагах, Bash начинает поиск исполняемого файла в директориях, перечисленных в переменной окружения `$PATH`.
    *   `$PATH` — это список директорий, разделенных двоеточиями, в которых Bash ищет исполняемые файлы.
    *   **Примеры:** `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`.
    *   Поиск происходит **слева направо**. Как только первый исполняемый файл с таким именем найден, он и будет выполнен.
    *   **Внешние команды** — это обычные исполняемые файлы, расположенные на диске в одной из директорий, указанных в `$PATH`.
    *   **Примеры:** `ls`, `rm`, `grep`, `find`.
    *   **Важно:** Если в `$PATH` есть несколько файлов с одинаковым именем, будет выполнен тот, который находится в директории, указанной раньше в `$PATH`. Это может привести к неожиданному поведению, если, например, пользователь создал свой исполняемый файл с именем системной команды и поместил его в директорию, которая стоит раньше в `$PATH`.

5.  **Ошибка "command not found"**
    *   Если команда не найдена ни на одном из предыдущих шагов, Bash выдает ошибку `command not found`.

#### Внутренние vs. Внешние команды

*   **Внутренние команды (Built-ins):**
    *   Являются частью самой оболочки Bash.
    *   Выполняются непосредственно оболочкой, не требуют запуска нового процесса.
    *   Примеры: `cd`, `echo`, `pwd`, `type`, `export`, `source`.
    *   Всегда доступны, пока работает Bash.

*   **Внешние команды:**
    *   Являются отдельными исполняемыми файлами на диске.
    *   Bash находит их через `$PATH` (или по полному пути) и запускает как отдельные процессы.
    *   Примеры: `ls`, `rm`, `grep`, `find`, `vim`.
    *   Могут отсутствовать в системе (например, если файл удален или не установлен).

#### Нюансы работы с алиасами

*   Алиасы могут быть очень полезны для сокращения часто используемых команд или для добавления к ним стандартных опций.
*   **Создание алиаса:** `alias ll='ls -alF'`
*   **Удаление алиаса:** `unalias ll`
*   **Просмотр алиасов:** `alias`
*   **Важно:** Алиасы не являются рекурсивными. То есть, если вы создадите `alias a='ls'` и затем `alias b='a'`, то `b` не будет работать как `ls`. Алиас `a` будет заменен на `ls`, но затем `ls` не будет заменена на `ls -alF` (если `ls` сам является алиасом). Для вложенных алиасов или более сложной логики лучше использовать функции Bash.
*   **Потенциальные проблемы:** Злоумышленник может создать вредоносный алиас для системной команды (например, `alias rm='rm -rf /'`), что может привести к серьезным последствиям. Будьте осторожны с алиасами, особенно в общих системах.


### Код возврата (`$?`)

Каждая команда после своего завершения возвращает **код возврата** (exit code) — число от 0 до 255, которое сообщает о том, как она отработала. Это основа для всей логики в shell.

-   **`0`** — команда завершилась **успешно**.
-   **Любое другое число (не `0`)** — в процессе выполнения произошла **ошибка**.

Узнать код возврата последней выполненной команды можно с помощью специальной переменной `$?`.

```bash
# Выполняем успешную команду
ls /etc/hosts
# /etc/hosts

# Проверяем код возврата
echo $?
# 0

# Выполняем команду с ошибкой
ls /не/существует
# ls: cannot access '/не/существует': No such file or directory

# Проверяем код возврата
echo $?
# 2 (или другое ненулевое значение в зависимости от системы и типа ошибки)
```

**Важно:** Переменная `$?` хранит код возврата только **самой последней** команды. Сразу после `echo $?` ее значение станет `0`, так как сама команда `echo` выполнилась успешно.

Именно на значении кода возврата (`0` или не `0`) основана работа управляющих операторов `&&` и `||`.

#### Шаг 3: Выполнение с учетом управляющих операторов (`&&`, `||`, `;`)
Эти операторы выполняются **последовательно, слева направо**, и определяют, будет ли запущена следующая команда (или конвейер).

*   **`&&` (Логическое "И")**
    *   **Логика:** `cmd1 && cmd2` -> Выполнить `cmd2` **только если** `cmd1` завершилась успешно (с кодом выхода 0).
    *   **Пример:** `mkdir backup && cp *.log backup/`
        1.  Выполняется `mkdir backup`.
        2.  Если папка успешно создана (код 0), выполняется `cp`.
        3.  Если `mkdir` выдает ошибку (например, папка уже есть), `cp` **не выполняется**.

*   **`||` (Логическое "ИЛИ")**
    *   **Логика:** `cmd1 || cmd2` -> Выполнить `cmd2` **только если** `cmd1` завершилась с ошибкой (код выхода не 0).
    *   **Пример:** `ping -c 1 google.com || echo "Хост недоступен"`
        1.  Выполняется `ping`.
        2.  Если `ping` успешен (код 0), `echo` **не выполняется**.
        3.  Если `ping` провалился (нет сети), `echo` **выполняется**.

#### Группировка команд: `( ... )` и `{ ...; }`

Иногда нужно сгруппировать несколько команд, чтобы применить к ним общее действие (например, перенаправление) или контролировать их окружение.

*   **`( ... )` (Subshell / дочерняя оболочка)**
    *   **Логика:** Команды внутри круглых скобок выполняются в **новом, дочернем процессе оболочки (subshell)**.
    *   **Эффект:** Любые изменения окружения (смена каталога через `cd`, экспорт переменных) происходят только внутри этого subshell и **не влияют** на родительскую оболочку.
    *   **Пример:** `(cd /tmp && rm log.txt)`. Команда `rm` выполнится в `/tmp`, но ваш основной терминал останется в прежнем каталоге.

*   **`{ ...; }` (Grouping / группировка)**
    *   **Логика:** Команды внутри фигурных скобок выполняются в **текущей оболочке**.
    *   **Эффект:** Изменения окружения **сохраняются** после выполнения группы.
    *   **Синтаксис:** Требует пробела после `{` и точки с запятой `;` (или переноса строки) перед `}`.
    *   **Пример:** `{ cd /tmp; rm log.txt; }`. После выполнения этой группы ваш терминал будет находиться в каталоге `/tmp`.

#### Подстановка: `$()` и `<()`

*   **Подстановка команд: `$(команда)` или `` `команда` ``
    *   **Логика:** Оболочка сначала выполняет команду внутри `$(...)` (или обратных кавычек `` `...` ``), забирает её стандартный вывод (`stdout`) и подставляет его как текст в основную команду.
    *   **Пример:** `echo "Будет удалено: $(find . -name '*.tmp')"`
    *   **Примечание:** Синтаксис `$(...)` предпочтительнее, чем обратные кавычки (`` ` ``), так как он более читаем, может быть вложенным и лучше обрабатывает специальные символы. Обратные кавычки считаются устаревшим синтаксисом.

*   **Подстановка процессов: `<(команда)`**
    *   **Логика:** Это более продвинутая техника. Оболочка выполняет команду и предоставляет её вывод в виде специального временного файла. Основная команда видит этот "файл" как один из своих аргументов.
    *   **Пример:** `diff <(sort file1.txt) <(sort file2.txt)`. Вместо создания двух отсортированных файлов вручную, `diff` напрямую сравнивает выводы двух `sort`-процессов. Это эффективнее и чище.

#### Фоновые процессы: `&`

*   **Логика:** Оператор `&` в конце команды говорит оболочке запустить её в **фоновом режиме**.
*   **Эффект:** Оболочка не ждет завершения команды, а сразу возвращает вам управление (приглашение для ввода). Команда продолжает работать "сзади".
*   **Пример:** `sleep 300 &`
*   **Управление:** Командами `jobs` (посмотреть список фоновых задач), `fg` (вернуть на передний план) и `bg` (возобновить в фоне) можно управлять этими процессами.

### Расширенная таблица-шпаргалка

| Оператор | Тип | Порядок выполнения | Пример |
| :--- | :--- | :--- | :--- |
| `|` | Конвейер | **Одновременный** запуск. Данные текут слева направо. | `cat file \| grep word` |
| `&&` | Управляющий | **Последовательный**. Вторая команда выполняется, если первая успешна. | `mkdir d && cd d` |
| `||` | Управляющий | **Последовательный**. Вторая команда выполняется, если первая провалилась. | `ping host \|\| echo 'down'` |
| `;` | Управляющий | **Последовательный**. Вторая команда выполняется всегда. | `cmd1 ; cmd2` |
| `&` | Управляющий | Запускает команду в **фоновом режиме**. | `sleep 10 &` |
| `>` `>>` `<` | Перенаправление | **Настраивается оболочкой до запуска команды.** | `ls > file.txt` |
| `$(...)` | Подстановка | Выполняется **до** основной команды. Результат подставляется как аргумент. | `rm $(find . -name "*.tmp")` |
| `<(...)` | Подстановка | Выполняется **одновременно** с основной командой, результат виден как файл. | `diff <(sort f1) <(sort f2)` |
| `( ... )` | Группировка | Команды выполняются в **дочерней оболочке (subshell)**. | `(cd /tmp && pwd)` |
| `{ ...; }` | Группировка | Команды выполняются в **текущей оболочке**. | `{ cd /tmp; pwd; }` |

### Переменные: локальные и переменные окружения

В Bash существует два основных типа переменных, и понимание разницы между ними критически важно.

1.  **Локальные переменные (`VAR="VALUE"`)**
    -   **Область видимости:** Такая переменная доступна **только в текущем процессе оболочки**, где она была объявлена.
    -   **Наследование:** Дочерние процессы (например, скрипты или команды, запущенные из текущей оболочки) **не унаследуют** эту переменную.

    **Пример:**
    ```bash
    # Объявляем локальную переменную
    MY_VAR="local_value"

    # В текущей оболочке она доступна
    echo $MY_VAR
    # Вывод: local_value

    # Запускаем новый дочерний процесс bash и пытаемся прочитать переменную
    bash -c 'echo $MY_VAR'
    # Вывод: (пустая строка)
    ```

2.  **Переменные окружения (`export VAR="VALUE"`)**
    -   **Область видимости:** Команда `export` "продвигает" локальную переменную до переменной окружения. Она становится доступна не только в текущей оболочке, но и во **всех дочерних процессах**, которые будут из нее запущены.
    -   **Наследование:** Дочерние процессы наследуют все экспортированные переменные родительской оболочки.

    **Пример:**
    ```bash
    # Объявляем и экспортируем переменную
    export MY_EXPORTED_VAR="exported_value"

    # В текущей оболочке она доступна
    echo $MY_EXPORTED_VAR
    # Вывод: exported_value

    # Запускаем новый дочерний процесс bash
    bash -c 'echo $MY_EXPORTED_VAR'
    # Вывод: exported_value
    ```

**Ключевое правило:**
-   Используйте `VAR="VALUE"` для временных переменных, которые нужны только в текущем скрипте или сессии.
-   Используйте `export VAR="VALUE"` для переменных, которые должны быть доступны программам или скриптам, запускаемым из текущей оболочки (например, `JAVA_HOME`, `PATH`, конфигурационные параметры).

### Выполнение скриптов: source vs. subshell

Помимо объявления переменных, способ запуска скрипта также влияет на окружение.

1.  **Запуск в дочерней оболочке (`./script.sh`)**
    -   **Механизм:** Когда вы делаете скрипт исполняемым (`chmod +x script.sh`) и запускаете его (`./script.sh`), оболочка создает **новый дочерний процесс (subshell)**, в котором и выполняются команды из скрипта.
    -   **Эффект:** Все изменения окружения (объявленные переменные, `cd`) остаются внутри этого дочернего процесса и **исчезают** после его завершения. Родительская оболочка остается неизменной. Это безопасный способ запуска, который не загрязняет текущее окружение.

2.  **Выполнение в текущей оболочке (`source script.sh` или `. script.sh`)**
    -   **Механизм:** Команда `source` (или ее короткий псевдоним `.`) выполняет команды из скрипта **в контексте текущей оболочки**, как если бы вы вводили их вручную. Новый процесс не создается.
    -   **Эффект:** Все изменения окружения, сделанные в скрипте (экспорт переменных, `cd`), **сохраняются** в вашей текущей сессии после завершения скрипта.
    -   **Основное применение:** Этот метод используется для загрузки конфигурационных файлов, файлов с переменными окружения (`source .env`) или для активации виртуальных окружений (например, `source venv/bin/activate` в Python).

**Наглядный пример:**

Допустим, `my_script.sh` содержит:
```bash
#!/bin/bash
MY_VAR="hello"
cd /tmp
```

Теперь сравним два способа запуска:

```bash
# 1. Запуск в subshell
$ pwd
/home/user
$ ./my_script.sh
$ echo $MY_VAR
# Вывод: (пустая строка)
$ pwd
/home/user
# Ничего не изменилось

# 2. Выполнение через source
$ pwd
/home/user
$ source ./my_script.sh
$ echo $MY_VAR
# Вывод: hello
$ pwd
/tmp
# Окружение изменилось!
```

## Bash-скрипты: Основы написания

**Bash-скрипт** — это обычный текстовый файл, содержащий последовательность команд для командного интерпретатора.

### Создание и запуск скрипта

1.  **Создайте файл:** `touch my_script.sh`
2.  **Добавьте команды:** Откройте файл в текстовом редакторе и добавьте команды, например:
    ```bash
    echo "Привет, мир!"
    ls -l
    ```
3.  **Запуск с указанием интерпретатора:** Вы можете запустить скрипт, передав его в качестве аргумента `bash`:
    ```bash
    bash my_script.sh
    ```

### Shabang (`#!`) и исполняемый файл

Чтобы запускать скрипт напрямую (как `./my_script.sh`), необходимо сделать две вещи:

1.  **Установить права на исполнение:**
    ```bash
    chmod +x my_script.sh
    ```

2.  **Указать интерпретатор с помощью "shabang":**
    **Shabang** — это специальная конструкция `#!` в самой первой строке файла, которая указывает операционной системе, какой интерпретатор использовать для выполнения этого скрипта.

    -   **`#!/bin/bash`** — самая распространенная форма. Она жестко указывает путь к `bash`.
    -   **`#!/usr/bin/env bash`** — более гибкая и предпочтительная форма. Она использует утилиту `env` для поиска `bash` в каталогах, перечисленных в переменной окружения `$PATH`. Это делает скрипт более переносимым между системами, где `bash` может находиться в другом месте (например, `/usr/local/bin/bash`).

    **Пример файла `my_script.sh` с shabang:**
    ```bash
    #!/usr/bin/env bash

    echo "Этот скрипт выполняется с помощью bash!"
    ```

    Теперь его можно запустить напрямую:
    ```bash
    ./my_script.sh
    ```

**Важно:** `shabang` работает только тогда, когда вы запускаете скрипт как исполняемый файл (`./my_script.sh`). Если вы запускаете его через `bash my_script.sh`, то `shabang` игнорируется, так как вы явно указали интерпретатор (`bash`).

## Поиск по содержимому файлов: grep

Одной из самых мощных возможностей командной строки Linux является поиск текста внутри файлов. Основным инструментом для этой задачи является утилита **`grep`** (Global Regular Expression Print).

`grep` сканирует содержимое файлов на наличие строк, соответствующих заданному шаблону (обычному тексту или регулярному выражению), и выводит найденные строки.

### Базовое использование

```bash
# Найти слово "error" в файле "app.log"
grep "error" app.log
```

### Поиск в нескольких файлах и директориях

-   **Рекурсивный поиск (`-r` или `-R`):**
    Искать текст во всех файлах внутри директории и ее поддиректорий.
    ```bash
    # Найти "database connection failed" во всех файлах в /var/log/
    grep -r "database connection failed" /var/log/
    ```

-   **Поиск без учета регистра (`-i`):**
    ```bash
    grep -ri "database" /var/log/
    ```

-   **Показать только имена файлов (`-l`):**
    Вывести список файлов, в которых найдено совпадение, без самих строк.
    ```bash
    grep -rl "database" /etc/
    ```

-   **Показать номера строк (`-n`):**
    ```bash
    grep -n "main" my_script.py
    ```

-   **Инвертировать поиск (`-v`):**
    Найти все строки, которые **не** содержат шаблон.
    ```bash
    # Показать все строки в логе, кроме отладочных сообщений
    grep -v "DEBUG" app.log
    ```

### Комбинация `find` и `grep`

Для более сложного поиска (например, по файлам с определенным расширением) `grep` часто используется в связке с командой `find`.

```bash
# Найти текст "TODO" во всех файлах с расширением .py в текущей директории
find . -name "*.py" -exec grep -Hn "TODO" {} +
```
-   `find . -name "*.py"`: Находит все файлы, заканчивающиеся на `.py`.
-   `-exec ... {} +`: Выполняет команду `grep` для найденных файлов.
    -   `-H`: Показывает имя файла (нужно, так как `grep` получает файлы по одному).
    -   `{}`: Подставляет имя найденного файла.
    -   `+`: Выполняет `grep` для группы файлов за раз, что эффективнее, чем `\;`.
