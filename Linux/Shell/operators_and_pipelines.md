# Операторы потоков данных и конвейеры в Shell

## Определения

- **Конвейер (Pipeline)** — механизм Shell (`|`), связывающий стандартный вывод (`stdout`) одной команды со стандартным вводом (`stdin`) следующей. Команды в конвейере запускаются параллельно.
- **Философия Unix «одна утилита — одна задача»** — принцип проектирования, лежащий в основе конвейеров: каждая утилита выполняет одно действие хорошо, а конвейер связывает их в сложные цепочки обработки данных.
- **Подстановка процессов (Process Substitution)** — механизм (`<( )`, `>( )`), позволяющий использовать вывод команды или поток данных как путь к временному файлу (через `/dev/fd/`). Оболочка создает именованный канал (FIFO) или использует `/dev/fd/N`, и передает путь как аргумент команде.
- **Именованный канал (Named Pipe / FIFO)** — специальный тип файла (`mkfifo`), работающий как буфер в оперативной памяти для асинхронного обмена данными между независимыми процессами. Запись в FIFO атомарна до размера `PIPE_BUF` (обычно 65536 байт).
- **xargs** — утилита для формирования командных строк на основе данных из `stdin`, позволяющая обходить ограничения `ARG_MAX` на суммарный размер аргументов и переменных окружения.
- **Сопроцесс (Co-process)** — механизм (команда `coproc`), запускающий процесс в фоне с созданием двустороннего канала связи (pipe) между родительским Shell и дочерним процессом. Доступ к дескрипторам осуществляется через массивы `coproc[0]` (чтение) и `coproc[1]` (запись).
- **GNU Parallel** — инструмент для параллельного выполнения задач на одном или нескольких узлах, обеспечивающий группировку вывода, продвинутое управление очередями и возобновление после сбоев.
- **tee** — утилита, дублирующая `stdin` в `stdout` и один или несколько файлов одновременно. Позволяет сохранять поток для последующего анализа без прерывания конвейера.
- **pee** — утилита из пакета `moreutils`, разветвляющая один `stdin` на несколько команд параллельно (аналог `tee` для процессов).
- **pv** — утилита (Pipe Viewer) для визуализации прогресса, скорости и ETA внутри конвейера. Особенно полезна при работе с большими объемами данных или устройствами блочного ввода-вывода.
- **ARG_MAX** — максимальный суммарный размер аргументов командной строки и переменных окружения, который может быть передан программе через `exec()`. В Linux обычно составляет 2 МБ (2097152 байт), но зависит от архитектуры и настроек ядра.
- **Backpressure** — механизм обратного давления в канале: когда буфер pipe заполняется, пишущий процесс блокируется до освобождения места, предотвращая переполнение.

## Базовые концепции

### Механика работы конвейера

1.  **Параллельное выполнение**: Все команды в конвейере запускаются одновременно. Скорость всей цепочки ограничена самым медленным звеном (bottleneck).
2.  **Буферизация**: Данные передаются через буферы ядра. В Linux размер буфера канала по умолчанию составляет **64 КБ** (начиная с ядра 2.6.11). Если буфер заполнен, пишущий процесс блокируется (Backpressure).
3.  **Subshells**: Каждая часть конвейера выполняется в отдельной подоболочке.
    - *Проблема*: Изменения переменных внутри конвейера теряются.
    - *Решение*: Использование `shopt -s lastpipe` (в неинтерактивных скриптах) или перенаправление ввода через подстановку процессов: `done < <(command)`.
4.  **Атомарность записей**: В Linux запись в pipe размером не более `PIPE_BUF` (65536 байт) является атомарной: ядро гарантирует, что данные не перемешаются с записями других процессов, пишущих в тот же канал.

### Опция `lastpipe`

В Bash (неинтерактивные скрипты) опция `shopt -s lastpipe` заставляет последнюю команду в конвейере выполняться в текущей оболочке, а не в subshell. Это сохраняет изменения переменных:

```bash
#!/bin/bash
shopt -s lastpipe

total=0
for num in 1 2 3 4 5; do
    echo "$num"
done | while read -r n; do
    total=$((total + n))
done
echo "Сумма: $total"  # total доступна, так как while выполняется в текущем shell
```

**Важно:** `lastpipe` работает только в неинтерактивных скриптах (`#!/bin/bash`), не работает в интерактивной оболочке и не влияет на опцию `-e`.

### Управление кодами возврата и ошибками

- **`$?`**: По умолчанию содержит код только **последней** команды конвейера. Если одна из команд в середине конвейера завершилась ошибкой, но последняя выполнилась успешно, `$?` будет равен `0`.
- **`PIPESTATUS`**: Массив Bash, хранящий коды возврата всех этапов последнего конвейера.
  ```bash
  cmd1 | cmd2 | cmd3
  echo "${PIPESTATUS[@]}" # → 0 127 0 (пример: вторая команда не найдена)
  ```
- **`set -o pipefail`**: Заставляет конвейер возвращать код самой правой команды, завершившейся с ошибкой (а не просто последней). В связке с `set -e` это позволяет немедленно прервать скрипт при сбое в любой части конвейера. Рекомендуемый заголовок для production-скриптов: `set -euo pipefail`.
- **Поведение при ошибках**:
    - По умолчанию скрипт продолжит выполнение, даже если команда в середине конвейера упала.
    - **`set -e`**: Прекращает выполнение скрипта при ошибке команды. Однако для конвейера он ориентируется только на код **последней** команды. Если упала первая команда в `cat file | grep text`, скрипт пойдет дальше.
    - В CI/CD пайплайнах (GitLab CI) рекомендуется всегда использовать `set -eo pipefail` для предотвращения ложноположительных результатов сборки.

## Операторы ветвления и параллелизма

### tee: дублирование потока

- **`tee file`**: Записывает `stdin` в `file` и одновременно в `stdout`.
- **`tee -a file`**: Дописывает в конец файла, не перезаписывая.
- **`tee -i`**: Игнорирует `SIGINT` (`Ctrl+C`), позволяя прервать `tee` без разрыва pipe. Остальные сигналы (`SIGTERM`, `SIGPIPE`) обрабатываются по умолчанию.

```bash
# Логирование конвейера без потери данных
tar -czf /tmp/backup.tar.gz /data | tee /var/log/backup.log | gzip > /tmp/backup.tar.gz
```

### pee: разветвление на несколько команд (moreutils)

- **`pee cmd1 cmd2`**: Направляет один `stdin` на вход нескольким командам параллельно. Каждая команда получает полную копию входного потока.

```bash
# Одновременная проверка лога на ошибки и архивация
tail -f app.log | pee "grep 'ERROR' > alerts.txt" "gzip > log_backup.gz"
```

### xargs: мост между pipe и exec

`xargs` решает проблему `ARG_MAX`, читая аргументы из `stdin` и формируя командные строки. В отличие от `find -exec`, `xargs` может группировать аргументы и запускать команды параллельно.

- **`-0` (null)**: Использование разделителя NUL (`\0`). Критично для корректной обработки файлов с пробелами или переносами.
- **`-I {}`**: Замена маркера `{}` аргументом в любой части команды.
- **`-n N`**: Группировка по N аргументов за один вызов.
- **`-P N`**: Параллельное выполнение до N процессов.
- **`-r` (no-run-if-empty)**: Не запускать команду, если ввод пуст.
- **`--max-procs=+N`**: Использовать до N параллельных jobs (GNU xargs).

### GNU Parallel vs xargs -P

| Возможность | `xargs -P N` | `GNU Parallel` |
| :--- | :--- | :--- |
| Группировка вывода | По командам | Группирует вывод по задаче |
| Продолжение после сбоя | Нет | `--resume` |
| Удаленное выполнение | Нет | `ssh` из коробки |
| Передача переменных | Ограничена | `{}` и `env_parallel` |
| Прогресс-бар | Нет | Встроенный |
| Разделитель | Пробел/NUL | Любой, включая NUL |

### Coproc: двусторонний обмен

`coproc` запускает процесс в фоне и создает два файловых дескриптора:
- `coproc_name[0]` — чтение вывода процесса
- `coproc_name[1]` — запись в процесс

```bash
# Запуск калькулятора как сопроцесса
coproc MYCALC { bc; }
# Отправка данных (MYCALC[1] - дескриптор для записи)
echo "10 + 20" >&"${MYCALC[1]}"
# Чтение результата (MYCALC[0] - дескриптор для чтения)
read -r result <&"${MYCALC[0]}"
echo "Результат: $result"
# Завершение сопроцесса
exec {MYCALC[0]}>&- {MYCALC[1]}>&-
wait $MYCALC_PID 2>/dev/null || true
```

## Продвинутые механизмы

### Сопроцессы (coproc)

Позволяют организовать интерактивный диалог с утилитой (например, `bc` или `openssl`) в фоновом режиме. После завершения работы дескрипторы должны быть явно закрыты (`exec {fd}>&-`), иначе процесс-потомок может остаться в состоянии зомби.

```bash
# Запуск калькулятора как сопроцесса
coproc MYCALC { bc; }
# Отправка данных (MYCALC[1] - дескриптор для записи)
echo "10 + 20" >&"${MYCALC[1]}"
# Чтение результата (MYCALC[0] - дескриптор для чтения)
read -r result <&"${MYCALC[0]}"
echo "Результат: $result"
```

### Управление буферизацией (stdbuf)

Утилиты типа `grep` или `sed` часто буферизируют вывод при работе через pipe, что мешает мониторингу в реальном времени. `stdbuf` работает через обертки `LD_PRELOAD` и не влияет на статически скомпонованные бинарники.
- **`stdbuf -oL`**: Принудительное линейное (line-buffered) буферирование для `stdout`.
- **`stdbuf -i0 -o0`**: Полное отключение буферизации.
- **Обходной путь**: `unbuffer` из пакета `expect` для утилит, игнорирующих `stdbuf`.

```bash
# Принудительное линейное буферирование
stdbuf -oL grep "ERROR" /var/log/app.log | awk '{print $1}'
```

### Подстановка процессов (Process Substitution)

Позволяет передавать поток данных командам, которые принимают только пути к файлам. Оболочка создает временный FIFO или `/dev/fd/N`, и команда получает путь как обычный аргумент.

```bash
# Сравнение двух удаленных конфигов через SSH
diff <(ssh srv1 "cat /etc/app.conf") <(ssh srv2 "cat /etc/app.conf")

# Ввод из подстановки в цикл (сохраняет переменные в текущем shell)
while read -r line; do
    count=$((count + 1))
done < <(grep "pattern" file.txt)
echo "Найдено: $count"
```

### Именованные каналы (FIFO) для сложных топологий

Именованные каналы создаются через `mkfifo` и существуют в файловой системе как специальные файлы. Они позволяют связывать процессы, запущенные в разное время или в разных терминалах.

- **Блокировка при открытии**: `open()` на FIFO блокируется, пока не откроется обе стороны (чтение и запись).
- **Атомарность**: Записи размером до `PIPE_BUF` (65536 байт) не перемешиваются.
- **Несброшенный буфер**: Если писатель закрывает FIFO, читатель получает EOF, но данные, уже находящиеся в буфере, не теряются.

```bash
mkfifo /tmp/data_stream
# В терминале 1 (читатель):
cat < /tmp/data_stream | process_data
# В терминале 2 (писатель):
generate_data > /tmp/data_stream
```

## Практические сценарии

### SRE: Валидация пайплайнов с pipefail

В production-скриптах всегда используйте `set -euo pipefail` и явно проверяйте `PIPESTATUS` после критических операций:

```bash
#!/bin/bash
set -euo pipefail

# Если grep упадет, скрипт прервется, даже если wc успешен
cat /var/log/app.log | grep "CRITICAL" | wc -l || {
    echo "Критическая ошибка в пайплайне"
    exit 1
}

# Или с сохранением кодов всех команд
results=("${PIPESTATUS[@]}")
if [ "${results[0]}" -ne 0 ]; then
    echo "cat не смог прочитать файл"
fi
if [ "${results[1]}" -ne 0 ]; then
    echo "grep не нашел совпадений или упал"
fi
```

### SRE: Параллельный сбор логов с xargs -P

```bash
# Параллельный поиск ERROR на 8 серверах через ssh
cat /tmp/hosts.txt | xargs -P 8 -I {} ssh {} "grep -h 'ERROR' /var/log/app.log" | \
    sort | uniq -c | sort -rn | head -20
```

### Sysadmin: Клонирование диска с прогрессом (pv)

```bash
# Копирование диска с отображением скорости и прогресса
dd if=/dev/sdb | pv -s 500G | dd of=/dev/sdc
# Или через gzip для сжатия на лету
dd if=/dev/sdb | pv -s 500G | gzip -1 | dd of=/backup/sdb.img.gz
```

### DevOps: Параллельный deployment через GNU Parallel

```bash
# Параллельный перезапуск сервисов на группах хостов
parallel -S ssh:srv1,srv2,srv3 --jobs 3 --tag --linebuffer \
    'systemctl restart app && systemctl status app' ::: service1 service2 service3
```

### Sysadmin: Агрегация логов через FIFO

```bash
# Несколько процессов пишут в FIFO, один читает
mkfifo /tmp/log_aggregator
# Читатель (в терминале 1):
grep --line-buffered "ERROR" < /tmp/log_aggregator | tee -a /var/log/aggregated_errors.log
# Писатели (в терминалах 2..N):
tail -F /var/log/nginx/access.log > /tmp/log_aggregator &
tail -F /var/log/app/app.log > /tmp/log_aggregator &
```

### SRE: Health-check пайплайн

```bash
# Проверка доступности сервисов и парсинг результата
curl -s -o /dev/null -w "%{http_code}" http://srv1:8080/health http://srv2:8080/health | \
    tr ' ' '\n' | \
    awk '$1 != 200 {print "FAIL:", $1}' | \
    tee /tmp/health_errors.txt

# Проверка: если есть строки с FAIL — пайплайн завершится с ошибкой
[ -s /tmp/health_errors.txt ] && exit 1 || exit 0
```

### Sysadmin: Сравнение конфигов через подстановку процессов

```bash
# Diff без временных файлов
diff <(ssh srv1 "cat /etc/nginx/nginx.conf") <(ssh srv2 "cat /etc/nginx/nginx.conf")

# Поиск отличий в бинарниках через ssh
cmp <(ssh srv1 "md5sum /usr/local/bin/app | awk '{print $1}'") \
    <(ssh srv2 "md5sum /usr/local/bin/app | awk '{print $1}'")
```

### DevOps: Параллельный scp через xargs

```bash
# Параллельная загрузка файлов на 5 хостов
cat /tmp/deploy_hosts.txt | xargs -P 5 -I {} scp /tmp/release.tar.gz {}:/opt/app/
```

### SRE: Потоковая обработка логов (awk + sed + tee)

```bash
# Одновременный анализ и сохранение сырых логов
tail -F /var/log/app/app.log | \
    tee -a /var/log/raw_backup.log | \
    awk '/ERROR/ {print $1, $2, $0}' | \
    sort | uniq -c | sort -rn | \
    head -20 > /tmp/top_errors.txt
```

### Sysadmin: Интерактивный coproc для SQL-запросов

```bash
# Двусторонний обмен с PostgreSQL через coproc
coproc PGPIPE { psql -U readonly -d metrics_db -t -A; }

echo "SELECT count(*) FROM users WHERE active = true;" >&"${PGPIPE[1]}"
read -r count <&"${PGPIPE[0]}"
echo "Активных пользователей: $count"

# Завершение
exec {PGPIPE[0]}>&- {PGPIPE[1]}>&-
wait $PGPIPE_PID 2>/dev/null || true
```

### Просмотр длинного вывода через less

```bash
# Обычный вывод ls может улететь за пределы экрана
ls -la /etc

# Через конвейер в less — комфортный постраничный просмотр
ls -la /etc | less
# Стрелки вверх/вниз для навигации, Q — для выхода
```

Количество команд в цепочке не ограничено: можно последовательно связать три, четыре или больше утилит для построения сложных конвейеров обработки данных.

### Различение операторов на экзамене (LPIC-1 103.2)

Ключевое отличие: конвейер `|` соединяет **программы**, а операторы ввода-вывода (`>`, `>>`, `<`) работают с **файлами**.

```bash
# Правильно: связь двух программ
history | less

# Неправильно: попытка связать программы через >
history > less  # Создаст файл "less" или выдаст ошибку
```

| Оператор | Назначение | Пример |
| :--- | :--- | :--- |
| `\|` (pipe) | Передача `stdout` одной команды в `stdin` следующей | `ls \| grep txt` |
| `>` | Запись вывода в файл (перезапись) | `echo "data" > file.txt` |
| `>>` | Добавление вывода в конец файла | `echo "new" >> file.txt` |
| `<` | Чтение ввода из файла | `sort < unsorted.txt` |

## Best Practices

1.  **Используйте `set -eo pipefail`** в production-скриптах. Это предотвращает ложноположительное выполнение, когда команда в середине конвейера упала, но последняя завершилась успешно.
2.  **Используйте `-print0 | xargs -0`** при работе с именами файлов, содержащими пробелы, переносы строк или специальные символы.
3.  **Предпочитайте `find -exec ... {} +`** вместо `find | xargs`, когда команда принимает несколько файлов за раз. Это избавляет от проблем с пробелами и лишних процессов.
4.  **Используйте `stdbuf -oL` или `unbuffer`** для утилит, буферизирующих вывод при работе через pipe. Это критично для мониторинга в реальном времени.
5.  **Используйте `tee` для аудита**, когда нужно одновременно сохранять поток в файл и передавать его дальше по конвейеру.
6.  **Проверяйте `PIPESTATUS`** после критических пайплайнов, если точный код возврата каждой команды важен для логики скрипта.
7.  **Закрывайте дескрипторы `coproc`** явно (`exec {fd}>&-`) и вызывайте `wait`, чтобы избежать зомби-процессов.
8.  **Используйте `pv -s SIZE`** для операций с известным размером данных. Без указания размера `pv` не может рассчитать процент выполнения и ETA.
9.  **Для сложной параллелизации используйте `GNU Parallel`** вместо `xargs -P`: он группирует вывод, поддерживает возобновление после сбоев и удаленное выполнение.
10. **Кавычивайте переменные в `xargs -I` и `find -exec`**: `find ... -exec sh -c 'cmd "$1"' _ {} \;` предотвращает инъекции и ошибки при пробелах в именах.

## Limitations

1.  **Потеря переменных в subshell**: Изменения переменных внутри конвейера теряются, так как каждая команда выполняется в отдельном процессе. Обход: `lastpipe` или `done < <(command)`.
2.  **Фиксированный размер буфера pipe**: Стандартный буфер 64 КБ. При высокой скорости записи и низкой скорости чтения происходит блокировка (Backpressure), что ограничивает пропускную способность.
3.  **SIGPIPE и Broken pipe**: При закрытии читающей стороны pipe процесс-писатель получает `SIGPIPE` и завершается по умолчанию. В скриптах можно игнорировать: `trap '' PIPE`.
4.  **Ограничение ARG_MAX**: Суммарный размер аргументов и окружения ограничен (обычно 2 МБ). Большие списки файлов требуют `xargs` или `find -exec ... {} +`.
5.  **`stdbuf` и статические бинарники**: Работает через `LD_PRELOAD`. Статически скомпонованные программы (например, `busybox` статический) игнорируют `stdbuf`.
6.  **Блокировка FIFO на открытие**: `open()` на именованном канале блокируется, пока не появятся и читатель, и писатель. В скриптах используйте `cat < fifo &` или открывайте FIFO для чтения и записи в фоне.
7.  **`coproc` — расширение Bash**: Недоступно в POSIX `sh` и `dash`. Для переносимости используйте временные FIFO или `/dev/fd/`.
8.  **`pipefail` — расширение Bash/Ksh**: В POSIX `sh` (например, `dash` в Debian/Ubuntu) опция недоступна. В `set -e` скриптах без `pipefail` ошибки в середине конвейера не детектируются.
9.  **`tee -i` игнорирует только SIGINT**: Сигналы `SIGTERM` и `SIGPIPE` прерывают `tee` по умолчанию. Для полного игнорирования сигналов используйте `trap`.

## Troubleshooting

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Пайплайн возвращает `0`, хотя команда в середине упала | `$?` показывает только код последней команды | Добавьте `set -o pipefail` или проверяйте `${PIPESTATUS[@]}` |
| `Argument list too long` | Превышен `ARG_MAX` при передаче тысяч аргументов | Используйте `find -print0 \| xargs -0` или `find -exec ... {} +` |
| Нет вывода до завершения всей команды | Утилита переключилась на блокировную буферизацию при записи в pipe | Используйте `stdbuf -oL`, `unbuffer` или `--line-buffered` (если поддерживается) |
| FIFO зависает при открытии | Одна из сторон (читатель/писатель) не запущена | Откройте FIFO с обеих сторон или используйте `cat < fifo &` в фоне |
| Переменные пусты после пайплайна | Команды в конвейере выполняются в subshell | Используйте `shopt -s lastpipe` (скрипты) или `done < <(command)` |
| `xargs` разбивает имена файлов с пробелами | Нет `-print0` и `-0` | `find ... -print0 \| xargs -0 ...` |
| `coproc` закрывает дескрипторы при ошибке | Фоновый процесс завершился, дескрипторы закрыты | Проверяйте `$coproc_PID` и вызывайте `wait` для диагностики |
| `tee` разрывает pipe при `Ctrl+C` | По умолчанию `tee` завершается на `SIGINT` | Используйте `tee -i` или оборачивайте в `trap` |
| `pv` показывает 0% или неправильный ETA | Не указан полный размер данных (`-s`) | Укажите `-s $(stat -c%s file)` или `-s 10G` для устройств |
| `parallel` не найден | Пакет не установлен | Установите `parallel` (Debian/Ubuntu: `apt install parallel`) |
