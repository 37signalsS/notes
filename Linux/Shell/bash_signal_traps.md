# Обработка сигналов и команда trap в Bash

## Определения

- **Сигнал (Signal)** — асинхронное уведомление, отправляемое процессу ядром или другим процессом для сообщения о событии (прерывание, завершение, ошибка).
- **Ловушка (Trap)** — механизм Bash для перехвата сигналов и выполнения заданного кода (обработчика) вместо стандартного системного действия.
- **EXIT** — псевдосигнал (внутреннее событие Bash), возникающий при завершении работы оболочки (скрипта) по любой причине (явный `exit`, конец файла или получение терминирующего сигнала).
- **Graceful Shutdown** — паттерн проектирования, при котором процесс корректно завершает текущие задачи и освобождает ресурсы перед остановкой.
- **SIGPIPE** — сигнал 13, отправляемый процессу при записи в pipe или сокет, чья читающая сторона закрыта. По умолчанию завершает процесс.
- **SIGCHLD** — сигнал 17, отправляемый родительскому процессу при изменении состояния дочернего (завершение, остановка, продолжение). Используется для перехвата статуса завершения детей.
- **SIGUSR1 / SIGUSR2** — пользовательские сигналы 10 и 12, не имеющие предопределенного действия. Используются для кастомной логики (rotating logs, dumping state, triggering reload) без изменения кода приложения.
- **DEBUG** — псевдосигнал Bash, возникающий перед выполнением каждой простой команды, функции или конструкции. Используется для трассировки.
- **RETURN** — псевдосигнал Bash, возникающий при возврате из функции или source-скрипта. Используется для аудита и восстановления контекста.

## Основные концепции

### Синтаксис команды trap

Команда `trap` регистрирует действия для одного или нескольких сигналов.

```bash
trap 'команда' СИГНАЛ    # Выполнить команду при сигнале
trap функция СИГНАЛ      # Вызвать функцию при сигнале
trap -l                  # Список всех доступных сигналов в системе
trap -p                  # Просмотр текущих установленных обработчиков
trap - СИГНАЛ            # Сброс обработчика к системному по умолчанию
trap '' СИГНАЛ           # Игнорировать сигнал (процесс его не увидит)
```

**Рекомендация:** Используйте имена сигналов (`INT`, `TERM`), а не их номера (2, 15), для лучшей переносимости и читаемости кода.

### Ключевые сигналы и события

Полный справочник по сигналам Linux см. в: [Сигналы процессов](../Core/processes/signals.md).

| Событие | Номер | Описание | Типичный сценарий |
| :--- | :---: | :--- | :--- |
| **EXIT** | 0 | Завершение сессии | Универсальный способ очистки временных файлов. |
| **HUP** | 1 | Отключение (Hangup) | Двойное назначение: (1) разрыв управляющего терминала (SSH-разрыв, закрытие окна) — по умолчанию завершает процесс; (2) запрос на перезагрузку конфигурации без остановки сервиса (например, `kill -HUP $(cat /var/run/nginx.pid)`). |
| **INT** | 2 | Прерывание (Interrupt) | `Ctrl+C` в терминале. Прерываемый сигнал, позволяющий приложению корректно завершиться. |
| **QUIT** | 3 | Выход (Quit) | `Ctrl+\`. Экстренный выход с созданием Core Dump. |
| **USR1** | 10 | Пользовательский сигнал 1 | Нет предопределенного действия. Используется для кастомных сценариев: принудительный ротацию логов, дамп состояния, повторное открытие файлов. |
| **USR2** | 12 | Пользовательский сигнал 2 | Аналогично SIGUSR1. Применяется для второй линии кастомной логики (например, переключение уровня логирования). |
| **PIPE** | 13 | Запись в pipe без читателя | Отправляется при записи в broken pipe. В shell-скриптах часто игнорируется (`trap '' PIPE`), чтобы пайплайн не падал при закрытии downstream-процесса. |
| **CHLD** | 17 | Статус дочернего процесса | Отправляется при завершении/остановке ребенка. Критичен для реализации кастомного `waitpid()` и предотвращения зомби-процессов. |
| **TERM** | 15 | Завершение (Terminate)| **Прерываемый** сигнал. Стандарт для **Graceful Shutdown**. Дает приложению время закрыть соединения и сохранить данные. |
| **STOP** | 19 | Остановка (Stop) | Приостановка выполнения процесса (непрерываемый, `Ctrl+Z` в shell). |

**Прерываемые vs Непрерываемые сигналы:**
* **Прерываемые (Trappable)**: Процесс может перехватить сигнал (через `trap` в bash или обработчик в коде) и выполнить определенные действия перед выходом. Примеры: `TERM`, `INT`, `HUP`.
* **Непрерываемые (Non-trappable)**: Ядро обрабатывает их безусловно, процесс даже не "узнает" о получении сигнала. Примеры: `KILL`, `STOP`.

### Сохранение состояния в обработчике

При входе в `trap` значение `$?` соответствует коду возврата последней выполненной команды **перед** получением сигнала. Чтобы итоговый код выхода скрипта был корректным, его нужно сохранить.

```bash
cleanup() {
    local status=$?
    echo "Очистка... (последний статус: $status)"
    # Логика удаления ресурсов
    exit "$status"
}
trap cleanup EXIT
```
 
 ### Специальные события Bash (ERR, DEBUG, RETURN)
 
 Bash предоставляет три псевдосигнала, отсутствующие в POSIX `sh`. Они перехватываются только внутри самой оболочки.
 
 #### ERR trap
 
 Выполняется при любой команде, завершившейся с ненулевым кодом возврата. Не срабатывает для:
 - Условий `if`, `while`, `until`
 - Команд в списке после `&&` или `||`
 - Кодов возврата `[` в `!` контексте (inverted exit status)
 
 ```bash
 #!/bin/bash
 set -E  # Обязательно: наследование ERR trap функциями
 
 trap 'echo "Ошибка в строке $LINENO, команда: $BASH_COMMAND, код: $?"' ERR
 
 fail_cmd() {
     false  # Ненулевой код
 }
 
 fail_cmd
 # → Ошибка в строке 12, команда: false, код: 1
 ```
 
 **Важно:** `set -E` (**errtrace**) должен быть установлен **до** объявления `trap '...' ERR`, иначе обработчик не наследуется функциями.
 
 #### DEBUG trap
 
 Выполняется **перед** каждой простой командой, функцией или конструкцией. Используется для трассировки выполнения.
 
 ```bash
 #!/bin/bash
 trap 'echo "[DEBUG] $BASH_COMMAND (строка $LINENO)"' DEBUG
 
 for i in {1..3}; do
     echo "Итерация $i"
 done
 # → [DEBUG] for i in {1..3}; do (строка 6)
 # → [DEBUG] echo "Итерация $i" (строка 7)
 # → Итерация 1
 # → ...
 ```
 
 **Практическое ограничение:** DEBUG trap замедляет выполнение. Используйте его точечно:
 - `trap '' DEBUG` — отключить трассировку в "шумных" блоках (циклы по строкам логов).
 - `trap -p DEBUG` — просмотреть текущий обработчик.
 
 #### RETURN trap
 
 Выполняется при возврате из функции или source-скрипта.
 
 ```bash
 #!/bin/bash
 my_func() {
     trap 'echo "Выход из $FUNCNAME (строка $LINENO)"' RETURN
     echo "Внутри функции"
 }
 
 my_func
 # → Внутри функции
 # → Выход из my_func (строка 5)
 ```
 
 **Отличие от EXIT:** RETURN срабатывает при каждом возврате из функции, а EXIT — только при завершении всего скрипта.

 ## Наследование и контекст

### Подпроцессы и Subshell

Поведение ловушек при создании новых процессов:
1.  **Внешние команды**: Не наследуют ловушки оболочки (сбрасываются к системным).
2.  **Subshell `( )`**: Наследуют ловушки, но они сбрасываются при вызове `exec`.
3.  **Функции**: Наследуют все ловушки родительской оболочки.

**Наследование специальных событий (`ERR`, `DEBUG`, `RETURN`):**
По умолчанию они **не** наследуются функциями и подоболочками. Для включения используйте:
- `set -E` (**errtrace**): наследование `ERR`.
- `set -T` (**functrace**): наследование `DEBUG` и `RETURN`.

### Блокирующие команды и wait

Если скрипт выполняет блокирующую команду (например, `sleep 100` или `wait`), обработчик `trap` выполнится:
- Для большинства команд: только **после** завершения блокирующей команды.
- Для команды **`wait`**: немедленно. При получении сигнала `wait` прерывается, выполняется обработчик, и управление возвращается к следующей строке скрипта.

### Взаимодействие trap с exec, PID 1 и окружением

#### exec сбрасывает trap

Команда `exec` заменяет текущий процесс Shell на новую программу. Все trap-обработчики теряются, так как в памяти больше нет кода Bash.

```bash
#!/bin/bash
trap 'echo "Очистка перед выходом"' EXIT
exec /usr/bin/python3 /opt/script.py
# Trap EXIT здесь НЕ сработает — процесс теперь является Python
```

**Исключение:** `exec` с `env -i` или `env VAR=val` сохраняет PID, но трапы сбрасываются, потому что оболочка заменяется.

#### PID 1 и проблема сигналов в контейнерах

В Docker-контейнере процесс с PID 1 имеет особую семантику сигналов в Linux:
- По умолчанию ядро игнорирует сигналы для PID 1 (`SIGTERM`, `SIGINT` и др.).
- Если PID 1 — это shell-скрипт без явного trap, контейнер не завершится по `docker stop`.

```bash
# ПРАВИЛЬНО: entrypoint-скрипт, который пробрасывает сигнал дочернему процессу
#!/bin/bash
set -e

CHILD_PID=""

cleanup() {
    if [ -n "$CHILD_PID" ]; then
        kill -TERM "$CHILD_PID" 2>/dev/null
        wait "$CHILD_PID" 2>/dev/null
    fi
}

trap cleanup EXIT INT TERM

# Запускаем основное приложение в фоне
/usr/local/bin/app &
CHILD_PID=$!

# Ждем завершения ребенка
wait "$CHILD_PID"
```

**Для production** используйте `tini` или `dumb-init` — они решают эту проблему на уровне init-процесса, включая перехват сигналов и переиспользование зомби-процессов.

#### trap и source

При `source script.sh` или `. script.sh` trap-ы добавляются к текущей оболочке. Если source-скрипт завершается (EXIT), его trap выполняется, но родительская оболочка продолжает работать.

```bash
# В текущем shell:
source ./setup_env.sh
# trap из setup_env.sh установлен в текущем shell
```

#### trap в subshell

Subshell `( ... )` наследует trap родителя, но обратно не передает изменения:

```bash
parent_trap=''

( 
    trap 'echo "Subshell got HUP"' HUP
    parent_trap=$(trap -p HUP)  # Захватываем в переменную
    kill -HUP $$  # Ожидаем, что сработает
)
echo "$parent_trap"
# → trap -- 'echo "Subshell got HUP"' HUP  (записана в переменную)
# Но в родителе trap не изменился
```

## Практические сценарии

### Комплексная очистка фоновых процессов

Скрипт должен убивать своих "детей" при выходе.

```bash
#!/bin/bash
set -m  # Включаем управление задачами (Job Control)

cleanup() {
    echo "Завершение фоновых задач..."
    # Убиваем все процессы в текущей группе процессов
    kill -TERM -$$ 2>/dev/null
}

trap cleanup EXIT INT TERM

./long_running_task_1 &
./long_running_task_2 &

wait
```

### Безопасное создание временных файлов

```bash
#!/bin/bash
TEMP_FILE=$(mktemp /tmp/script.XXXXXX)

# Удаление файла гарантировано при любом выходе
trap 'rm -f "$TEMP_FILE"' EXIT

# Работа с файлом...
```

### Многократные обработчики (Stacking)

Если нужно добавить действие к существующей ловушке без её перезаписи:

```bash
# Функция для добавления команды в существующий trap
add_trap() {
    local cmd=$1
    local sig=$2
    local old_trap=$(trap -p "$sig" | sed "s/trap -- '\(.*\)' $sig/\1/")
    trap "${old_trap}; ${cmd}" "$sig"
}

add_trap "echo 'First cleanup'" EXIT
add_trap "echo 'Second cleanup'" EXIT
```

### SRE: Graceful shutdown systemd-сервиса

Systemd отправляет `SIGTERM` при остановке юнита, ждет `TimeoutStopSec` (по умолчанию 90s), затем отправляет `SIGKILL`. Bash-обертка должна корректно обработать `SIGTERM` и завершить дочерние процессы.

```ini
# /etc/systemd/system/my-app.service
[Service]
Type=simple
ExecStart=/usr/local/bin/my-app-wrapper.sh
KillMode=mixed
KillSignal=SIGTERM
TimeoutStopSec=30
```

```bash
#!/bin/bash
# /usr/local/bin/my-app-wrapper.sh
set -euo pipefail

CHILD_PID=""
terminating=0

on_terminate() {
    terminating=1
    echo "Получен SIGTERM, завершаю ребенка..."
    if [ -n "$CHILD_PID" ]; then
        kill -TERM "$CHILD_PID" 2>/dev/null
        wait "$CHILD_PID" 2>/dev/null
    fi
}

trap on_terminate TERM INT

/usr/local/bin/my-app &
CHILD_PID=$!

wait "$CHILD_PID"
exit $?
```

**Ключевые моменты:**
- `KillMode=mixed`: systemd отправляет `SIGTERM` только главному процессу, а `SIGKILL` — всей контрольной группе.
- `trap on_terminate TERM INT`: перехватываем оба сигнала, так как systemd может использовать любой из них в зависимости от конфигурации.
- `set -euo pipefail`: strict mode дляProduction-скриптов.

### SRE: Обработка SIGPIPE в пайплайнах

При записи в pipe, чья читающая сторона закрыта (например, `head -n 5` завершился), Bash получает `SIGPIPE` и завершается с кодом 141 (128 + 13). В long-running скриптах это нежелательно.

```bash
#!/bin/bash
# Игнорируем SIGPIPE, чтобы пайплайн не падал
trap '' PIPE

while read -r line; do
    echo "$line" | head -n 1
done < /var/log/large_file.log
```

**Диагностика:**
```bash
# Проверяем код возврата после пайплайна
echo $?
# 141 = SIGPIPE
# 0 = успех (если trap '' PIPE активен)
```

### SRE: Hot-reload через SIGUSR1

Многие демоны (Nginx, haproxy, PostgreSQL) используют `SIGHUP` для перезагрузки конфигурации. Для кастомных приложений можно использовать `SIGUSR1`.

```bash
#!/bin/bash
CONFIG_FILE="/etc/myapp/config.conf"
reload() {
    echo "[$(date)] Получен SIGUSR1, перезагружаю конфигурацию..."
    if [ -f "$CONFIG_FILE" ]; then
        source "$CONFIG_FILE"
        echo "Новый параметр: MAX_CONNECTIONS=$MAX_CONNECTIONS"
    else
        echo "Конфиг не найден: $CONFIG_FILE" >&2
    fi
}

trap reload USR1

while true; do
    # Работа приложения
    sleep 1
done &
APP_PID=$!

# Отправляем reload
kill -USR1 "$APP_PID"

wait "$APP_PID"
```

### SRE: Аудит функций через RETURN trap

RETURN trap полезен для логирования входа/выхода из функций без явного вызова `log` в каждой функции.

```bash
#!/bin/bash
set -T  # Обязательно: наследование RETURN trap функциями

trap 'echo "[AUDIT] Выход из $FUNCNAME (строка $LINENO), статус: $?"' RETURN

get_data() {
    local url=$1
    curl -sf "$url"
}

process_data() {
    local data=$1
    echo "$data" | jq .
}

get_data "https://api.example.com/status" | process_data
# → [AUDIT] Выход из process_data (строка 15), статус: 0
# → [AUDIT] Выход из get_data (строка 11), статус: 0
```

**Важно:** `set -T` (**functrace**) должен быть установлен **до** объявления `trap '...' RETURN`.

### Sysadmin: Trap в интерактивных оболочках (`.bash_logout`, `.bash_profile`)

Trap срабатывает не только в скриптах, но и в интерактивных сессиях. Полезно для очистки при выходе.

```bash
# ~/.bash_profile или ~/.bashrc
SESSION_START=$(date +%s)

trap '{
    SESSION_END=$(date +%s)
    DURATION=$((SESSION_END - SESSION_START))
    echo "Сессия завершена. Длительность: ${DURATION}s"
    # Очистка временных файлов текущего пользователя
    rm -f /tmp/myapp-$$-*
}' EXIT
```

### Sysadmin: Защита cron-скриптов от зависания

Cron не отправляет сигналы напрямую, но скрипт может зависнуть на блокирующей команде. Используйте `timeout` + trap.

```bash
#!/bin/bash
set -euo pipefail

TMPFILE=$(mktemp)
trap 'rm -f "$TMPFILE"' EXIT

# timeout завершит команду через 300s, отправив SIGTERM, затем SIGKILL
timeout --kill-after=10 300 /usr/local/bin/backup.sh > "$TMPFILE" 2>&1
STATUS=$?

case $STATUS in
    0)   echo "Бэкап успешен" ;;
    124) echo "Бэкап завершен по таймауту (SIGTERM)" ;;
    137) echo "Бэкап принудительно убит (SIGKILL)" ;;
    *)   echo "Ошибка бэкапа: код $STATUS" ;;
esac
```

### SRE: Отладка с DEBUG trap и ограничением глубины

DEBUG trap полезен для отладки, но в production его нужно ограничивать по глубине вызова или контексту.

```bash
#!/bin/bash
DEBUG_DEPTH=0
MAX_DEBUG_DEPTH=3

debug_trace() {
    if (( DEBUG_DEPTH > MAX_DEBUG_DEPTH )); then
        return
    fi
    echo "[DEBUG $DEBUG_DEPTH] $BASH_COMMAND (строка $LINENO, файл ${BASH_SOURCE[1]})"
}

trap '((DEBUG_DEPTH++))' DEBUG
trap '((DEBUG_DEPTH--))' RETURN

outer() {
    inner
}

inner() {
    echo "Глубина 2"
    deepest
}

deepest() {
    echo "Глубина 3 — DEBUG здесь не печатается"
}

outer
```

## Best Practices, Troubleshooting и ограничения

### Best Practices

1.  **Используйте имена сигналов:** `trap '...' TERM` вместо `trap '...' 15` для переносимости между архитектурами и Unix-подобными системами.
2.  **Сохраняйте `$?` в обработчике EXIT:** Итоговый код возврата скрипта должен отражать результат работы, а не успешность очистки.
3.  **Идемпотентность обработчиков:** Обработчик EXIT может вызываться несколькожды (например, при `exec` с ошибкой). Гарантируйте, что повторный вызов безопасен.
4.  **Избегайте неинтерактивных выводов в trap:** В интерактивном shell вывод обработчика перемешивается с промптом. Используйте `logger` или файл для production-скриптов.
5.  **`set -E` и `set -T` до trap:** Если вам нужно наследование `ERR`/`DEBUG`/`RETURN` в функциях, установите эти опции **до** объявления обработчика.
6.  **TMOUT для интерактивных сессий:** Переменная `TMOUT` автоматически завершает сессию бездействия, генерируя `SIGTERM`/`EXIT`.
7.  **`trap -p` для диагностики:** Перед отладкой выводите текущие trap: `trap -p` или `trap -p EXIT TERM INT`.
8.  **Не используйте `kill -9` как первую меру:** `SIGTERM` дает приложению шанс сохранить данные. `SIGKILL` — только когда процесс завис или игнорирует `SIGTERM`.
9.  **Учитывайте `set -e`:** При `set -e` скрипт завершается до обработки `ERR` trap, если ошибка не в условии. Используйте `trap ... ERR` в связке с `set -E`.
10. **Обработка `SIGPIPE` в пайплайнах:** Если скрипт часть пайплайна (`cat file | my_script | head`), добавьте `trap '' PIPE`, чтобы избежать преждевременного завершения.

### Ограничения и edge cases

1.  **SIGKILL (9) и SIGSTOP (19):** Невозможно перехватить или проигнорировать. Процесс убивается ядром безусловно.
2.  **Гонка сигналов:** Если два сигнала приходят одновременно, Bash может выполнить обработчики последовательно или объединить их, если это один и тот же сигнал.
3.  **Интерактивность:** В интерактивном режиме Bash игнорирует `TERM` по умолчанию. Для тестирования отправляйте сигнал фоновому заданию (`kill -TERM %1`).
4.  **Смерть от сигнала:** Если скрипт завершился по сигналу (например, `INT`), хорошей практикой считается сброс ловушки и повторная отправка сигнала самому себе в конце обработчика.
5.  **DEBUG trap и производительность:** DEBUG trap выполняется перед **каждой** командой. В циклах с тысячами итераций это критично замедляет скрипт. Используйте `trap '' DEBUG` внутри интенсивных блоков.
6.  **RETURN trap и `source`:** При `source` RETURN trap срабатывает при выходе из sourced-скрипта, а не из вызывающей функции. Это может привести к неожиданному поведению, если обработчик изменяет глобальное состояние.
7.  **Subshell и переменные:** trap в subshell не виден в родителе, но **side effects** (создание файлов, отправка сетевых запросов) внутри обработчика влияют на систему.
8.  **`exec` сбрасывает все trap:** Никакие trap не переживают `exec`. Если нужна очистка после `exec`, используйте обертку-скрипт.
9.  **Порядок обработки сигналов:** Bash обрабатывает сигналы последовательно. Если во время выполнения обработчика придет тот же сигнал, он будет отложен. Для массовой отправки сигналов используйте очереди или `kill` с задержкой.

### Troubleshooting

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Trap не срабатывает | Обработчик объявлен после сигнала или в другом процессе | Убедитесь, что `trap` стоит **до** потенциальной генерации сигнала. Внешние команды не наследуют trap. |
| `docker stop` не завершает контейнер | PID 1 — shell-скрипт без trap, или `exec` использован неправильно | Добавьте trap в entrypoint-скрипт или используйте `tini` (`docker run --init`). |
| Скрипт зависает на `wait` | `wait` без `-n` ждет все фоновые задачи, включая зависшие | Используйте `wait -n` (Bash 4.3+) с таймаутом или отправляйте сигналы всей группе (`kill -TERM -$$`). |
| Core dump при `SIGQUIT` | `Ctrl+\` по умолчанию генерирует core dump | Игнорируйте `SIGQUIT` (`trap '' QUIT`) или перенаправьте вывод core dump (`ulimit -c 0`). |
| Обработчик EXIT не видит `$?` | `$?` перезаписан внутри обработчика | Сохраняйте `$?` в локальную переменную **первой строкой** обработчика. |
| `ERR` trap не срабатывает в функциях | `set -E` не установлен или установлен после `trap` | Установите `set -E` **перед** `trap '...' ERR`. |
| `DEBUG` trap вызывает бесконечный цикл | В обработчике есть команды, которые генерируют новые DEBUG-события | Используйте `trap '' DEBUG` внутри самого обработчика или ограничивайте глубину recursion. |
| Сигнал не доходит до дочернего процесса | Дочерний процесс в другой process group или PID namespace | Используйте `kill -TERM -$PGID` для группы или настраивайте `set -m` (job control). |
