# Выполнение скриптов в Bash: Subshell, Source и Shabang

## Определения

- **Bash-скрипт**: Текстовый файл с последовательностью команд для интерпретатора Bash.
- **Интерпретатор**: Программа, выполняющая команды построчно. Bash — интерпретируемый язык (в отличие от компилируемых C++, Go).
- **Контекст выполнения**: Среда (оболочка), в которой выполняются команды. Определяет влияние переменных, `cd` и других команд на текущую сессию.
- **Subshell (дочерняя оболочка)**: Изолированный дочерний процесс. Изменения окружения не влияют на родительский процесс. Подробнее: [Группировка команд](bash_command_execution.md#группировка-команд--и--).
- **Shabang (`#!`)**: Последовательность в начале файла (`#!/path/to/interpreter`), указывающая ОС, какую программу использовать для выполнения.

## Базовые концепции

### Способы запуска скрипта

#### Способ 1: Subshell (`./script.sh`)

1. `chmod +x my_script.sh` — права на исполнение.
2. Первая строка: `#!/usr/bin/env bash` (shabang).
3. Запуск: `./my_script.sh`.

**Механизм:** создается дочерний процесс. Изменения окружения (переменные, `cd`) **исчезают** после завершения. Родительская оболочка неизменна.

#### Способ 2: Текущая оболочка (`source`)

- `source my_script.sh` или `. ./my_script.sh`.

**Механизм:** команды выполняются **в контексте текущей оболочки**, новый процесс не создается. Все изменения (переменные, `cd`) **сохраняются**.

См. также: [Конструкции для скриптов](bash_scripting_constructs.md), [Сигналы и trap](bash_signal_traps.md).

## Практические сценарии

### Subshell vs `source`

`setup_env.sh`:

```bash
#!/bin/bash
export MY_APP_VERSION="1.2.3"
cd /tmp
```

```bash
# Subshell — изменения потеряны
$ ./setup_env.sh
$ echo $MY_APP_VERSION  # (пусто)
$ pwd                   # /home/user

# Source — изменения сохранены
$ source ./setup_env.sh
$ echo $MY_APP_VERSION  # 1.2.3
$ pwd                   # /tmp
```

**Правило:** `./script.sh` — для задач, `source script.sh` — для загрузки конфигурации.

### Фоновый запуск и `nohup`

Команда `nohup` (no hang up) используется для запуска процессов, которые должны продолжать выполнение после закрытия терминала или завершения сессии (игнорирует сигнал `SIGHUP`).

```bash
# Запустить скрипт в фоне и игнорировать закрытие терминала
nohup ./long_task.sh &

# Вывод по умолчанию перенаправляется в файл nohup.out
```

**Отличие от обычного `&`:** простое добавление `&` запускает процесс в фоне, но при закрытии оболочки (logout) процесс может получить `SIGHUP` и завершиться. `nohup` гарантирует выживание процесса. Современные `systemd`-системы часто автоматически завершают все процессы пользователя при logout, поэтому для надежности лучше использовать `systemd-run` или `screen`/`tmux`.

## Дополнительная информация

### Файлы инициализации оболочки

Порядок и условия загрузки конфигурационных файлов зависят от типа оболочки:

| Файл | Тип оболочки | Описание |
| :--- | :--- | :--- |
| **`/etc/profile`** | Login | Системные настройки для всех пользователей при входе. |
| **`/etc/profile.d/*.sh`** | Login | Скрипты инициализации пакетов (лучшее место для системных переменных). |
| **`/etc/bash.bashrc`** | Interactive | Системные настройки Bash для интерактивных сессий. |
| **`~/.bash_profile`** | Login | Пользовательские настройки при входе. |
| **`~/.bashrc`** | Interactive | Настройки для каждого нового окна терминала. |
| **`/etc/environment`** | Все | Простой список `KEY=VALUE`, не поддерживает скрипты и условия. |

### Отладка и строгий режим (Strict Mode)

Для написания надежных скриптов рекомендуется использовать "строгий режим" в начале файла:

```bash
#!/bin/bash
set -euo pipefail
IFS=$'\n\t'
```

**Разбор опций `set`**:

- **`-e` (errexit)**: немедленно завершить скрипт, если команда завершилась с ошибкой (код ≠ 0).
- **`-u` (nounset)**: считать ошибкой обращение к неопределенным переменным.
- **`-o pipefail`**: возвращать код ошибки конвейера, если хотя бы одна команда в нем провалилась (по умолчанию возвращается код последней команды).
- **`-x` (xtrace)**: выводить каждую команду перед ее выполнением (трассировка, удобно для отладки).

Для временного включения/выключения отладки:

```bash
set -x
# проблемный участок кода
set +x
```

### Роль `shabang` (`#!`)

**Shebang** (или hashbang) — это специальная последовательность символов (`#!`) в самом начале текстового файла скрипта. Она указывает ядру операционной системы, какую программу-интерпретатор следует запустить для обработки этого файла.

#### Как это работает
Когда вы запускаете файл как исполняемый (`./script.sh`), ядро Linux считывает первые байты. Если оно видит `#!`, оно берет остальную часть первой строки как путь к программе и запускает её, передавая путь к вашему скрипту в качестве аргумента.

#### Популярные примеры
- `#!/bin/bash` — жестко заданный путь к Bash.
- `#!/bin/sh` — запуск системной оболочки (может быть Dash в Ubuntu).
- `#!/usr/bin/python3` — запуск конкретной версии Python.
- `#!/usr/bin/env bash` — поиск Bash в переменной окружения `$PATH` (наиболее переносимый способ).

#### Нюансы использования
- **Прямой вызов:** Если запустить скрипт через интерпретатор явно (`bash my_script.sh`), строка с шебангом игнорируется и воспринимается как обычный комментарий.
- **Пустые строки:** Шебанг **обязательно** должен быть на первой строке, без пробелов перед `#!`.
- **Windows-формат:** Если файл сохранен с окончаниями строк `CRLF` (Windows), скрипт может не запуститься, так как ОС будет искать интерпретатор с лишним символом `\r` в пути.

### Влияние конвейеров (`|`) на область видимости

Каждая команда в конвейере (`cmd1 | cmd2`) выполняется в **отдельном subshell** — переменные не видны за пределами конвейера.

```bash
last_line=""
cat file.txt | while read line; do
    last_line=$line
done
echo "$last_line"  # (пусто) — изменения в subshell
```

**Решение:** перенаправление ввода (без subshell):

```bash
last_line=""
while read line; do
    last_line=$line
done < file.txt
echo "$last_line"  # корректный результат
```
