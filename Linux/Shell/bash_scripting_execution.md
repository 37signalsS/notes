# Выполнение скриптов в Bash: Subshell, Source и Shabang

## Определения

- **Bash-скрипт:** Текстовый файл с последовательностью команд, предназначенных для выполнения интерпретатором Bash.
- **Интерпретатор:** Программа, которая выполняет команды из скрипта построчно. Bash — интерпретируемый язык, в отличие от компилируемых (C++, Go), где код сначала полностью преобразуется в машинный, а затем исполняется.
- **Контекст выполнения:** Среда (оболочка), в которой выполняются команды. От контекста зависит, как переменные, `cd` и другие команды влияют на текущую сессию терминала.
- **Subshell (дочерняя оболочка):** Изолированный дочерний процесс оболочки, создаваемый для выполнения команд. Более детальное описание приведено в разделе [Группировка команд: (...) и {...;}](bash_command_execution.md#группировка-команд--и--) файла [Логика обработки команд в Shell](bash_command_execution.md). Изменения окружения в subshell не влияют на родительский процесс.
- **Shabang (`#!`):** Специальная последовательность символов в начале файла (`#!/path/to/interpreter`), которая указывает операционной системе, какую программу использовать для выполнения этого файла.

## Базовые концепции

### 1. Способы запуска скрипта

Существует два основных способа запустить скрипт, и они принципиально различаются по своему влиянию на текущую сессию.

#### Способ 1: Запуск в дочерней оболочке (Subshell)

Это стандартный и наиболее безопасный метод.

- **Как это работает:**
  1.  Скрипту предоставляются права на исполнение: `chmod +x my_script.sh`.
  2.  В первой строке скрипта указывается интерпретатор через **shabang**: `#!/usr/bin/env bash`.
  3.  Скрипт запускается по имени: `./my_script.sh`.

- **Механизм:** Оболочка создает новый дочерний процесс (subshell) для выполнения скрипта. Подробнее о создании subshell см. в [Логика обработки команд в Shell](bash_command_execution.md#группировка-команд--и--).
- **Эффект:** Все изменения окружения (объявленные переменные, переход в другой каталог с помощью `cd`) остаются внутри этого subshell и **исчезают** после его завершения. Родительская оболочка остается неизменной.

#### Способ 2: Выполнение в текущей оболочке (`source`)

Этот метод используется для изменения текущей среды.

- **Как это работает:**
  - Команда `source` (или ее короткий псевдоним `.`) читает и выполняет команды из файла.
  - `source my_script.sh` или `. ./my_script.sh`.

- **Механизм:** Команды из скрипта выполняются **в контексте текущей оболочки**, как если бы вы вводили их вручную. Новый процесс не создается.
- **Эффект:** Все изменения окружения, сделанные в скрипте (экспорт переменных, `cd`), **сохраняются** в вашей текущей сессии после завершения скрипта.

> После того как вы разобрались со способами выполнения, изучите [конструкции для написания скриптов](bash_scripting_constructs.md), чтобы наполнить их логикой.

## Практические сценарии

### Сценарий 1: Стандартный скрипт vs `source`

Допустим, файл `setup_env.sh` содержит:
```bash
#!/bin/bash
export MY_APP_VERSION="1.2.3"
cd /tmp
echo "Переменная окружения установлена, каталог изменен."
```

Сравним два способа запуска:

```bash
# 1. Запуск в subshell
$ pwd
/home/user
$ ./setup_env.sh
Переменная окружения установлена, каталог изменен.

$ echo $MY_APP_VERSION
# Вывод: (пустая строка)
$ pwd
/home/user
# Ничего не изменилось в текущей сессии.

# 2. Выполнение через source
$ pwd
/home/user
$ source ./setup_env.sh
Переменная окружения установлена, каталог изменен.

$ echo $MY_APP_VERSION
# Вывод: 1.2.3
$ pwd
/tmp
# Окружение текущей сессии изменилось!
```
**Вывод:** Используйте `./script.sh` для выполнения задач и `source script.sh` для загрузки конфигурации.

### Сценарий 2: Активация виртуального окружения Python

Файл `venv/bin/activate` — это скрипт, который экспортирует переменные окружения, такие как `PATH` и `VIRTUAL_ENV`. Его нужно выполнять именно через `source`, чтобы изменить текущую оболочку и "активировать" окружение.

```bash
# Правильно. Изменяет текущую оболочку.
source venv/bin/activate

# Неправильно. Переменные будут установлены в subshell, который тут же закроется.
# Виртуальное окружение не активируется.
./venv/bin/activate
```

## Дополнительная информация

### Роль `shabang` (`#!`)

- **При запуске как `./my_script.sh`:** `shabang` **критически важен**. Операционная система читает первую строку, запускает указанный интерпретатор (например, `/bin/bash`) и передает ему файл скрипта для выполнения.
- **При запуске как `bash my_script.sh`:** `shabang` **игнорируется**. Вы явно указываете, какой интерпретатор (`bash`) должен выполнить файл. Строка `#!` воспринимается им просто как комментарий.

### Влияние конвейеров (`|`) на область видимости

В соответствии с [логикой обработки команд в Shell](bash_command_execution.md), каждая команда в конвейере (`command1 | command2`) выполняется в **отдельном subshell**. Это означает, что переменные, измененные в одной части конвейера, не будут видны в другой или в родительской оболочке.

**Пример проблемы:**
```bash
last_line=""
cat my_file.txt | while read line; do
    last_line=$line
done
echo "Последняя строка: $last_line" # Выведет пустую строку
```
Цикл `while` выполняется в subshell, поэтому изменения `last_line` не "протекают" наружу.

**Решение (перенаправление):**
```bash
last_line=""
while read line; do
    last_line=$line
done < my_file.txt
echo "Последняя строка: $last_line" # Выведет корректный результат
```
Здесь subshell не создается, и цикл `while` выполняется в текущей оболочке.
