# Коды возврата в Shell

## Определения

**Код возврата (Exit Code, Exit Status)** — целочисленное значение в диапазоне от **0** до **255**, возвращаемое процессом родительской оболочке или операционной системе при завершении работы. Это фундаментальный механизм межпроцессного взаимодействия для передачи результата выполнения.

- **Переменная `$?`** — специальный параметр оболочки, который хранит код возврата последней выполненной команды (или конвейера). Значение обновляется немедленно после выполнения любой операции, включая проверки `[` или команды вывода `echo`.
- **PIPESTATUS** — внутренний массив Bash, содержащий коды возврата всех команд в последнем выполненном конвейере (pipeline).

## Базовые концепции

### Интерпретация значений

- **`0`** — **Успех (Success)**. Команда выполнена корректно.
- **`1–255`** — **Ошибка (Failure)**. Любое ненулевое значение сигнализирует о сбое. Конкретное число часто указывает на тип возникшей проблемы.

### Механизм переполнения и 8-битное ограничение

Коды возврата в Unix ограничены 8 битами. Если процесс вызывает `exit` со значением больше 255, результат вычисляется по формуле `N % 256`.
- `exit 256` → вернет **0** (может быть ошибочно воспринято как успех).
- `exit 257` → вернет **1**.
- `exit -1` → вернет **255** (циклическое смещение).

### Механизм передачи кода возврата

При завершении процесса ядро сохраняет код возврата в структуре **task_struct**. Родительский процесс собирает его через системный вызов `wait()`/`waitpid()`.

1. **`fork()`**: создаётся дочерний процесс-копия родителя.
2. **`exec()`**: дочерний процесс заменяет своё тело образом новой программы.
3. **`_exit(N)` / `exit(N)`**: процесс завершается, передавая ядру код `N` (младшие 8 бит).
   - `_exit()` — немедленный выход, без вызова деструкторов stdio (`atexit`, `fclose`).
   - `exit()` — корректное завершение C-библиотеки, с flush буферов и вызовом обработчиков.
4. **`waitpid()`**: родитель собирает статус завершения. Если родитель не вызывает `wait()`, дочерний процесс становится **зомби** (Zombie) — запись в таблице процессов сохраняется, пока статус не будет прочитан.

**Важно:** Если родительский процесс завершается раньше дочернего, инициатором `wait()` становится процесс с PID 1 (init/systemd), который собирает статусы всех осиротевших процессов.

### Сохранение кода возврата

Так как `$?` меняется после каждой команды, для анализа кода конкретной операции его необходимо сохранить в переменную сразу после вызова.

```bash
# Пример корректного сохранения
ls /nonexistent_file
rc=$?
# Теперь переменную rc можно анализировать многократно
if [ $rc -ne 0 ]; then
    echo "Ошибка! Код возврата: $rc"
fi
```

### Коды выхода и системные сигналы (128 + N)

Если процесс завершается принудительно под воздействием сигнала, оболочка устанавливает код возврата по формуле **128 + номер_сигнала**.

| Сигнал | Номер | Код выхода | Причина |
| :--- | :--- | :--- | :--- |
| **SIGINT** | 2 | **130** | Прервано пользователем (`Ctrl+C`). |
| **SIGKILL** | 9 | **137** | Принудительно убито (`kill -9`) или OOM Killer. |
| **SIGTERM** | 15 | **143** | Запрос на мягкое завершение (стандарт для `docker stop`). |

### Коды завершения и состояния процессов

- **Zombie (Z):** Процесс завершился, но родитель ещё не вызвал `wait()`. Процесс занимает запись в таблице процессов, но не потребляет CPU/RAM.
- **Orphan (сирота):** Родительский процесс завершился до дочернего. Процесс «усыновляется» PID 1, который гарантированно вызовет `wait()`.
- **SIGCHLD:** При завершении дочернего процесса родитель получает SIGCHLD. Если обработчик не установлен, дочерний процесс становится зомби до явного `wait()`.

### Различия POSIX sh и Bash

- **POSIX sh:** Не поддерживает `${PIPESTATUS[@]}`, `set -o pipefail`, массивы, `[[ ]]`.
- **Bash:** Добавляет `PIPESTATUS`, `pipefail`, `set -E` (наследование trap функциями), расширенные арифметические операции.
- **Shebang:** Используйте `#!/bin/sh` для максимальной переносимости, `#!/usr/bin/env bash` или `#!/bin/bash` при необходимости Bash-расширений.

### Таблица общепринятых и зарезервированных кодов

| Код | Значение | Описание |
| :--- | :--- | :--- |
| **0** | Успех | Команда завершена без ошибок. |
| **1** | Общая ошибка | Неспецифический сбой (деление на ноль, ошибки выполнения скрипта). |
| **2** | Неправильное использование | Ошибки синтаксиса или неверные аргументы встроенных команд Bash. |
| **64–78** | sysexits.h | Стандартизированные коды для системных утилит (например, 64 — ошибка параметров, 77 — нет прав). |
| **126** | Невыполнимая команда | Файл найден, но права на исполнение отсутствуют (`Permission denied`) или это директория. |
| **127** | Команда не найдена | Опечатка в имени или файл отсутствует в путях `$PATH`. |
| **128** | Неверный аргумент выхода | Передан `exit` с нечисловым аргументом. |
| **130** | SIGINT | Завершение через прерывание (128 + 2). |
| **137** | SIGKILL | Принудительное завершение, часто нехватка памяти (128 + 9). |
| **139** | SIGSEGV | Ошибка сегментации, доступ к невалидной памяти (128 + 11). |
| **141** | SIGPIPE | Запись в закрытый pipe (128 + 13). |
| **143** | SIGTERM | Корректное завершение по сигналу (128 + 15). |

## Продвинутая работа с кодами возврата

### Конвейеры и массив PIPESTATUS

По умолчанию `$?` хранит код только **последней** команды в конвейере.

```bash
# Пример обманчивого успеха
cat nonexistent_file | sort
echo $? # → 0 (так как sort отработал успешно)
```

В Bash для доступа к кодам всех команд используется массив `${PIPESTATUS[@]}`:

```bash
cat nonexistent_file | sort
# Сохраняем массив сразу, так как он обновится при следующей команде
results=("${PIPESTATUS[@]}")
echo "cat: ${results[0]}, sort: ${results[1]}"
```

### Стабильность скриптов: set -e, set -u и pipefail

- `set -e` (errexit): Оболочка прекращает выполнение скрипта при любой ошибке (кроме проверок в `if`, `while` и логических И/ИЛИ).
- `set -u` (nounset): Ошибка при обращении к необъявленной переменной. Защищает от опечаток в именах переменных.
- `set -o pipefail`: Кодом возврата конвейера станет код самой правой команды, завершившейся с ошибкой (а не просто последней).

Рекомендуемый заголовок: `set -euo pipefail`.

### Trap и обработчики выхода

- **`trap 'commands' EXIT`**: выполняется при любом завершении скрипта (успешном или по ошибке). Используется для очистки временных файлов.
- **`trap 'commands' ERR`**: выполняется при любой ошибке команды (в Bash). Требует `set -E`.
- **`trap 'commands' INT TERM`**: перехват сигналов для корректного завершения.

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
TMPFILE=$(mktemp)
trap 'rm -f "$TMPFILE"' EXIT

# При любом завершении (включая Ctrl+C) временный файл удалится
process_data > "$TMPFILE"
```

### Разница между exit и return

- **`exit N`**: Завершает работу текущей оболочки (скрипта или сабшелла). Если вызвано в `( ... )`, основной скрипт продолжит работу.
- **`return N`**: Завершает выполнение функции или скрипта, вызванного через `source`, возвращая код в вызывающую среду, но не завершая процесс.

### Фоновые задачи и wait

- **`$!`** — PID последнего запущенного фонового процесса (`cmd &`).
- **`wait $!`** — дождаться завершения фонового процесса и вернуть его exit code.
- **`wait` без аргументов** — дождаться всех фоновых задач.
- **`wait -n`** (Bash 4.3+): дождаться любой одной завершившейся фоновой задачи.

```bash
long_running_task &
PID=$!
# ... параллельная работа ...
wait $PID
rc=$?
if [ $rc -ne 0 ]; then
    echo "Фоновая задача упала с кодом $rc"
fi
```

### Команды-заглушки: true и false

- `true` (или `:`): всегда возвращает **0**.
- `false`: всегда возвращает **1**.

### Process substitution и subshell

- **Process substitution** `<(cmd)` и `>(cmd)`: код возврата самой подстановки обычно **0**, даже если внутренняя команда упала. Код упавшей команды теряется.
- **Subshell** `( cmd )`: код возврата subshell — это код возврата последней команды внутри него.

```bash
# Process substitution: код 0, даже если grep упал
read var < <(grep pattern file)
# Правильнее проверять явно:
result=$(grep pattern file) || exit 1
```

## Практические сценарии

### Проверки в скриптах

```bash
# Идемпотентная проверка наличия пользователя
if grep -q "^admin:" /etc/passwd; then
    echo "Пользователь существует"
else
    echo "Пользователь не найден"
fi
```

### Контроль качества в CI/CD

```bash
# Запуск тестов
npm test
if [ $? -ne 0 ]; then
    echo "Тесты провалены! Прекращение сборки."
    exit 1
fi
```

### Systemd: обработка exit codes сервисов

Systemd использует код возврата главного процесса (MainPID) для определения состояния сервиса:

```ini
# /etc/systemd/system/myapp.service
[Service]
Type=simple
ExecStart=/usr/local/bin/myapp
Restart=on-failure
RestartSec=5

# systemd считает 0 = успех, всё остальное = неудача.
# Для сложных сценариев используйте Type=notify или Type=exec
```

Диагностика:
```bash
systemctl status myapp
# ↑ показывает ExitCode=0/1/137/...

journalctl -u myapp --since "10 minutes ago"
# Логи вместе с кодом возврата
```

### Cron: фиксация exit codes

Cron отправляет вывод на email по умолчанию, но лучше логировать exit code явно:

```bash
# /etc/cron.d/backup
0 2 * * * root /opt/scripts/backup.sh >> /var/log/backup.log 2>&1 || echo "Backup failed with exit $?" | mail -s "Backup alert" ops@example.com
```

Или в скрипте:
```bash
#!/bin/bash
set -euo pipefail
/opt/scripts/do_backup
rc=$?
logger -p local0.info "backup_job exit=$rc"
exit $rc
```

### SSH и удалённое выполнение

При запуске команды через SSH локальный `ssh` возвращает код завершения удалённой команды:

```bash
ssh user@host "/opt/scripts/check_remote.sh"
rc=$?
if [ $rc -ne 0 ]; then
    echo "Удалённая проверка провалилась: $rc"
fi
```

Для конвейеров через SSH обязательно используйте `pipefail`:
```bash
ssh user@host "cat /var/log/app.log | grep ERROR | wc -l"
# Без pipefail локальный bash увидит только код ssh (0), даже если grep упал
ssh user@host "bash -o pipefail -c 'cat /var/log/app.log | grep ERROR | wc -l'"
```

### sudo: коды возврата и без密码ный режим

- **`0`**: команда выполнена успешно.
- **`1`**: Generic error (неправильные аргументы, несуществующая команда).
- **`126`**: команда найдена, но не исполняема.
- **`127`**: команда не найдена (похоже на оболочку, но для sudo специфично).

В `/etc/sudoers`:
```bash
# Без запроса пароли для конкретной команды:
%admin ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx
```

### timeout: управление долгими командами

Утилита `timeout` из coreutils завершает команду по истечении времени:

| Код | Значение |
| :--- | :--- |
| **0–124** | Код возврата самой команды |
| **124** | Команда завершена по таймауту |
| **125** | Ошибка запуска `timeout` (неверные аргументы) |
| **126** | Команда найдена, но не может быть запущена |
| **127** | Команда не найдена (внутри timeout) |
| **128+signal** | Команда завершена сигналом (обычно 143 = SIGTERM) |

```bash
# Жёсткий таймаут с SIGKILL через 10 секунд
timeout --kill-after=10 5s long_running_task

# Проверка: 124 = таймаут, 143 = принудительный SIGTERM
rc=$?
case $rc in
    0)   echo "Успех" ;;
    124) echo "Таймаут: команда не завершилась за 5с" ;;
    143) echo "Принудительно остановлен после SIGTERM" ;;
    *)   echo "Другая ошибка: $rc" ;;
esac
```

### xargs: коды возврата

| Код | Значение |
| :--- | :--- |
| **0** | Успех |
| **1–125** | Код возврата упавшей команды |
| **126** | Команда найдена, но не исполняема |
| **127** | Команда не найдена |
| **124** | Команда завершена по таймауту (с `--timeout`) |
| **125** | Ошибка запуска самой `xargs` (например, слишком длинная команда) |
| **123** | Несовпадение версий `xargs` и GNU Parallel при совместном использовании |

```bash
find /var/log -name "*.log" -print0 | xargs -0 grep -l "ERROR"
rc=$?
if [ $rc -eq 0 ]; then
    echo "Найдены логи с ERROR"
elif [ $rc -eq 1 ]; then
    echo "Совпадений нет (но xargs отработал)"
else
    echo "Ошибка xargs или grep: $rc"
fi
```

### Мониторинг и health-check скрипты

Скрипты для Nagios/Icinga/Prometheus exporters должны следовать конвенции:

```bash
#!/bin/bash
# check_service_health.sh — пример health-check для мониторинга

set -euo pipefail

SERVICE_URL="http://localhost:8080/health"
TIMEOUT=3

response=$(curl -s -o /dev/null -w "%{http_code}" --max-time $TIMEOUT "$SERVICE_URL") || {
    echo "CRITICAL: curl failed with exit $?"
    exit 2
}

if [ "$response" -eq 200 ]; then
    echo "OK: service healthy (HTTP $response)"
    exit 0
elif [ "$response" -ge 500 ]; then
    echo "CRITICAL: service error (HTTP $response)"
    exit 2
else
    echo "WARNING: degraded (HTTP $response)"
    exit 1
fi
```

### Ansible: ожидаемые ненулевые коды

В playbook Ansible часто требуется явно разрешить ненулевой exit code:

```yaml
- name: Проверить наличие пакета (grep вернёт 1, если не найдёт)
  command: dpkg -l package-name
  register: pkg_check
  failed_when: pkg_check.rc not in [0, 1]
  changed_when: false

- name: Убедиться, что строка НЕ присутствует (grep 1 = успех для нас)
  shell: grep -q "FORBIDDEN" /etc/config || exit 0
  register: grep_result
  failed_when: grep_result.rc == 2  # только системная ошибка grep
```

### Логические операторы (&& и ||)

- `cmd1 && cmd2` — выполнить `cmd2`, если `cmd1` успешна (**0**).
- `cmd1 || cmd2` — выполнить `cmd2`, если `cmd1` завершилась ошибкой (**не 0**).
