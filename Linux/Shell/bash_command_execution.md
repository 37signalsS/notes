# Логика обработки и выполнения команд в Shell

## Определения

- **Жизненный цикл команды (Command Lifecycle)** — последовательность этапов, которые проходит строка ввода от парсинга до завершения процесса.
- **Подстановка (Expansion)** — замена специальных символов (`*`, `$`, `$( )`) на их значения перед выполнением команды.
- **Разбиение на слова (Word Splitting)** — процесс разделения результата подстановок на отдельные аргументы на основе переменной `$IFS`.
- **Префиксное присваивание (Variable Assignment)** — задание переменных окружения непосредственно перед командой (`VAR=val cmd`), влияющее только на этот вызов.
- **Хеш-таблица (Hash Table)** — внутренний кеш Shell, хранящий пути к исполняемым файлам для ускорения поиска в `$PATH`.
- **Токенизация (Tokenization)** — первичное разбиение строки ввода на лексемы: слова, операторы (`|`, `&&`, `;`, `&`) и управляющие символы.
- **Генерация строк (Brace Expansion)** — обработка конструкций вида `{a,b,c}` или `{1..5}` до любых других подстановок. Bash-specific расширение.
- **Подстановка тильды (Tilde Expansion)** — замена `~` и `~user` на соответствующие пути в домашних директориях.
- **Арифметическая подстановка (Arithmetic Expansion)** — вычисление целочисленных выражений внутри `$(( ))` с поддержкой C-подобного синтаксиса.
- **Подстановка команд (Command Substitution)** — выполнение команды внутри `$( )` или `` ` `` и замена конструкций её выводом.
- **Подстановка имен файлов (Pathname Expansion / Globbing)** — раскрытие wildcard-символов (`*`, `?`, `[ ]`) в реальные пути файловой системы.
- **Удаление кавычек (Quote Removal)** — финальный этап, на котором внешние кавычки (`'`, `"`) удаляются после завершения всех подстановок.
- **Перенаправление (Redirection)** — настройка дескрипторов файлов (`<`, `>`, `>>`, `<<`, `<<<`, `&>`, `>&`) до запуска команды.

## Жизненный цикл выполнения команды

Когда вы нажимаете `Enter`, Bash обрабатывает строку в строго определенном порядке. Нарушение этого порядка — частая причина ошибок в скриптах.

1.  **Токенизация**: Разбиение строки на слова и операторы (`|`, `&&`, `;`, `&`).
2.  **Генерация строк (Brace Expansion)**: Обработка `{a,b}`. Выполняется первой, так как не зависит от значений переменных.
3.  **Подстановка тильды (Tilde Expansion)**: Замена `~` на путь к `$HOME`.
4.  **Подстановка параметров и переменных**: Замена `$VAR` и `${VAR}`.
5.  **Арифметическая подстановка**: Вычисление `$(( expression ))`.
6.  **Подстановка команд**: Обработка `$(command)` или `` `command` ``. Выполняется путем запуска подоболочки.
7.  **Разбиение на слова (Word Splitting)**: Применяется к результатам этапов 4, 5 и 6, если они **не** заключены в двойные кавычки.
8.  **Подстановка имен файлов (Globbing)**: Обработка `*`, `?`, `[ ]`.
9.  **Удаление кавычек (Quote Removal)**: Убираются внешние кавычки (`'`, `"`), защищавшие текст на предыдущих этапах.
10. **Перенаправления**: Настройка дескрипторов файлов (`<`, `>`, `>>`).
11. **Выполнение**: Определение типа команды и её запуск.

> **SRE-заметка:** Для трассировки жизненного цикла включите `set -x` в скрипте. Bash выводит каждую команду после всех подстановок, но **до** выполнения. Для отладки конкретного этапа (например, Globbing) используйте `echo` с `printf '%q\n'` для безопасного вывода аргументов.

## Приоритет поиска и управления командами

### Порядок поиска (Command Lookup)

Если команда введена без пути (не содержит `/`), Bash ищет её в следующем порядке:
1.  **Алиасы (Aliases)**: Только в интерактивных оболочках.
2.  **Ключевые слова (Keywords)**: Резервированные слова (`if`, `then`, `function`).
3.  **Функции (Functions)**: Определенные пользователем в текущей сессии.
4.  **Встроенные команды (Built-ins)**: Команды внутри бинарного файла самого Bash (`cd`, `echo`, `read`).
5.  **Внешние команды (External)**: Поиск в директориях переменной `$PATH`. Путь кешируется в `hash`.

### Хеш-таблица (Hash Table)

Bash кеширует полные пути найденных внешних команд. Повторный вызов той же команды происходит мгновенно, без повторного обхода `$PATH`.

- **`hash`**: Выводит содержимое хеш-таблицы.
- **`hash -r`**: Очищает кеш. Полезно после установки нового ПО (`apt install`, `dnf install`).
- **`hash -d name=dir`**: Создает псевдоним директории (аналогично `hash -d` в Zsh, но в Bash работает только с командой, а не с путями).
- **`enable [-n] name`**: Включает (`enable name`) или отключает (`enable -n name`) встроенную команду, возвращая или скрывая её из поиска.

### Инструменты диагностики
- **`type -a <cmd>`**: Показывает все доступные версии команды (алиас, функция, файл). Рекомендуется вместо `which`.
- **`command -v <cmd>`**: Возвращает путь к команде или её имя, если она встроена. Удобно для скриптов.
- **`type -t <cmd>`**: Возвращает тип команды (`alias`, `keyword`, `function`, `builtin`, `file`).

### Обход приоритетов
- **`\command`**: Обратный слэш перед именем отключает алиасы.
- **`command <cmd>`**: Игнорирует алиасы и функции.
- **`builtin <cmd>`**: Форсирует использование встроенной команды.

### Управление PATH
- **`PATH` просматривается слева направо**. Первое совпадение побеждает.
- Наличие `.` (текущей директории) в начале `$PATH` — критическая уязвимость.
- Изменение `PATH` в текущем shell не затрагивает уже запущенные процессы.

## Продвинутые механизмы выполнения

### Команда exec

`exec` заменяет текущий процесс оболочки новым процессом. Текущий скрипт или Shell **завершается**, и управление передается новой программе без создания дочернего процесса.

```bash
# Текущий Shell заменяется на htop
exec htop
```

**Варианты использования в DevOps/SRE:**

```bash
# 1. Entrypoint-скрипт для контейнера (корректный проброс сигналов)
#!/bin/sh
# Очистка перед запуском
rm -f /var/run/app.pid
# exec заменяет shell на PID 1 процесса, сигналы доходят напрямую
exec /usr/bin/myapp --config /etc/app.conf

# 2. Запуск с очищенным окружением (security hardening)
exec env -i PATH=/usr/bin:/bin HOME=$HOME /usr/bin/myapp

# 3. Использование в systemd-сервисе (Type=exec)
# /etc/systemd/system/myapp.service
[Service]
Type=exec
ExecStart=/usr/local/bin/myapp
# systemd ожидает, что ExecStart заменит процесс (аналогично exec)

# 4. Перенаправление вывода на весь скрипт (персистентно)
exec > >(logger -t myscript) 2>&1
echo "Этот вывод уйдет в syslog, а не в терминал"

# 5. Открытие persistent file descriptor
exec 3>/var/log/myapp.log
echo "Статус: OK" >&3
exec 3>&-
```

> **Важно:** `exec` сбрасывает все `trap`. Если скрипту нужна очистка (например, удаление временных файлов), используйте обертку-скрипт, который выполняет очистку, а затем вызывает `exec`.

### Команда eval

Заставляет оболочку выполнить строку дважды: сначала провести все подстановки, а затем выполнить получившуюся строку как команду. **Опасно** при работе с пользовательским вводом.

```bash
VAR="ls -l"
eval $VAR  # Корректно выполнит ls -l
```

**Альтернативы и безопасность:**

```bash
# ОПАСНО: injection через переменную окружения
EVAL_CMD='echo pwned; rm -rf /tmp/important'
eval "$EVAL_CMD"

# БЕЗОПАСНЕЕ: явный вызов функции/команды
run_cmd() { "$@"; }
run_cmd ls -l

# БЕЗОПАСНЕЕ: массивы для аргументов
cmd=(ls -l "$1" "$2")
"${cmd[@]}"

# БЕЗОПАСНЕЕ: printf вместо eval для форматирования
printf -v formatted "%(%Y-%m-%d)T" "$timestamp"
```

> **SRE-заметка:** Используйте `eval` только при абсолютной необходимости (например, динамическое создание алиасов). В production-скриптах предпочитайте массивы `("${args[@]}")` и явные функции.

### Подстановка процессов (Process Substitution)

Создает временный именованный канал (pipe) и передает его путь как аргумент.
- **`<(cmd)`**: Позволяет читать вывод `cmd` как файл.
- **`>(cmd)`**: Позволяет записывать в `cmd` как в файл.

```bash
# Сравнение двух удаленных конфигов без временных файлов
diff <(ssh server1 cat /etc/nginx/nginx.conf) <(ssh server2 cat /etc/nginx/nginx.conf)

# Параллельная запись в tee и файл
tee >(logger -t myapp) > /var/log/myapp.log

# Фильтрация вывода команды, принимающей только файл
# (например, grep не может читать из pipe напрямую в некоторых сценариях)
grep ERROR <(journalctl -u myservice --since "1 hour ago")
```

**Особенности в DevOps:**

```bash
# Сравнение производительности двух версий приложения
hyperfine --warmup 3 "./app-v1" "./app-v2"

# Использование в conjunction с diff для audit
diff -u <(cat /etc/config.bak) <(cat /etc/config) | less

# Подсчет строк параллельно
wc -l <(find /var/log -name "*.log" -print0 | xargs -0 cat)
```

> **Примечание:** Код возврата самой подстановки обычно **0**, даже если внутренняя команда упала. Код упавшей команды теряется. Для надежной обработки ошибок используйте `result=$(cmd)` и проверяйте `$?`.

## Группировка команд и контексты выполнения

### Логические связи
- **`&&`**: Выполнить следующую, только если предыдущая успешна (`exit 0`).
- **`||`**: Выполнить следующую, только если предыдущая завершилась с ошибкой.

### Группировка
- **`( commands )`**: Запуск в **Subshell**. Создает копию процесса. Переменные и `cd` внутри не влияют на родителя.
- **`{ commands; }`**: Запуск в текущей оболочке. Влияет на состояние текущего Shell.

### Subshell в конвейерах

Каждая часть конвейера `|` выполняется в отдельном subshell. Это означает, что переменные, установленные внутри конвейера, теряются.

```bash
# ПРОБЛЕМА: переменная внутри while теряется
cat /var/log/syslog | while read line; do
    count=$((count + 1))
done
echo "Всего строк: $count"  # count пустой или 0

# РЕШЕНИЕ 1: перенаправление ввода через process substitution
while read line; do
    count=$((count + 1))
done < <(cat /var/log/syslog)
echo "Всего строк: $count"

# РЕШЕНИЕ 2: bash 4.2+ shopt -s lastpipe (только в неинтерактивных скриптах)
shopt -s lastpipe
cat /var/log/syslog | while read line; do
    count=$((count + 1))
done
echo "Всего строк: $count"
```

### Уровни вложенности subshell

Переменная `$BASH_SUBSHELL` отслеживает глубину вложенности:
- `0` — основная оболочка
- `1` — первый subshell `( ... )` или `$()`
- `2` — вложенный subshell внутри subshell

```bash
echo "Уровень: $BASH_SUBSHELL"  # 0
( echo "Уровень: $BASH_SUBSHELL" )  # 1
( ( echo "Уровень: $BASH_SUBSHELL" ) )  # 2
```

### BASH_ENV для неинтерактивных скриптов

В неинтерактивных скриптах (cron, systemd, Ansible) не читаются `~/.bashrc` и `~/.profile`. Для инициализации окружения используйте `BASH_ENV`:

```bash
# В cron или systemd-юните
BASH_ENV=/home/deploy/.bash_env /opt/scripts/backup.sh

# /home/deploy/.bash_env
export PATH="/usr/local/bin:/opt/bin:$PATH"
export AWS_DEFAULT_REGION="eu-west-1"
alias k="kubectl"
```

## Практические сценарии

### Изоляция окружения для одной команды

```bash
# Установка переменной только для этого вызова приложения
LOG_LEVEL=debug ./my_app
# LOG_LEVEL здесь снова не определена

# Множественные переменные
NODE_ENV=production PORT=3000 ./node_server.js
```

### Сравнение удаленных и локальных файлов

```bash
diff <(ssh server "cat /etc/nginx/nginx.conf") /etc/nginx/nginx.conf
```

### Проверка наличия команды в скрипте

```bash
if command -v docker &>/dev/null; then
    docker ps
else
    echo "Docker не установлен"
fi
```

### Graceful shutdown через exec в systemd

```ini
# /etc/systemd/system/myapp.service
[Service]
Type=simple
ExecStart=/opt/myapp/entrypoint.sh
KillSignal=SIGTERM
TimeoutStopSec=30

# entrypoint.sh
#!/bin/sh
# trap не нужен: exec передает SIGTERM напрямую процессу
exec /usr/bin/myapp --config /etc/myapp.conf
```

### Управление PATH в production-скриптах

```bash
# Безопасное добавление пути (без дубликатов, в конец PATH)
case ":${PATH}:" in
    *":/opt/myapp/bin:"*) ;;
    *) export PATH="/opt/myapp/bin:${PATH}" ;;
esac

# Временная модификация для одной команды
PATH="/opt/special/bin:${PATH}" special-tool --check
```

### Parallel execution с xargs

```bash
# Параллельный запуск проверок на 4 хостах
cat hosts.txt | xargs -P 4 -I {} ssh {} 'hostname && uptime'

# Параллельный backup баз данных
databases=(db1 db2 db3 db4)
printf "%s\n" "${databases[@]}" | xargs -P 2 -I {} mysqldump {} > {}.sql
```

### Timeout для неотзывчивых команд

```bash
# Автоматическое завершение команды через 10 секунд
timeout 10s curl -s http://unresponsive-service:8080/health

# Сustom exit code при таймауте
timeout --kill-after=5s 3s long-running-task
exit_code=$?
if [ $exit_code -eq 124 ]; then
    echo "Команда превысила таймаут"
fi
```

### Управление буферизацией вывода

```bash
# Отключение буферизации для real-time логов
stdbuf -i0 -o0 -e0 ./myapp | grep --line-buffered ERROR

# Использование unbuffer (expect)
unbuffer ssh server1 'tail -f /var/log/syslog' | grep ERROR
```

### Запись сессии для аудита

```bash
# Запись всего вывода команды в файл с таймстампами
script -q -c "ansible-playbook deploy.yml" /var/log/ansible-$(date +%Y%m%d).log

# Продолжение записи в существующий файл
script -a -q -c "terraform apply" /var/log/terraform.log
```

### Работа в chroot/namespace

```bash
# Выполнение команды в namespace через ip netns
sudo ip netns exec isolated-ns chroot /opt/service-chroot /usr/bin/myapp

# Exec в уже запущенном контейнере
docker exec -it web-container bash -c 'cd /app && ./run-tests.sh'
```

## Best Practices

1.  **Всегда используйте `set -euo pipefail`** в production-скриптах для раннего прерывания при ошибках.
2.  **Избегайте `eval`**: предпочитайте массивы `("${args[@]}")` и явные функции.
3.  **Используйте `command -v` вместо `which`**: `command -v` является POSIX-совместимым builtin, а `which` — внешней утилитой, поведение которой различается между системами.
4.  **Проверяйте команды перед выполнением**: `command -v git >/dev/null || { echo "git missing"; exit 1; }`.
5.  **Используйте `exec` в entrypoint-скриптах** для корректного проброса сигналов (особенно в контейнерах и systemd).
6.  **Не полагайтесь на `cd` в subshell**: используйте явные пути или `(cd /dir && cmd)`.
7.  **Используйте `timeout` для всех внешних вызовов** в production-скриптах для предотвращения зависаний.
8.  **Будьте осторожны с Word Splitting**: всегда заключайте переменные в двойные кавычки: `"$VAR"`.
9.  **Используйте `printf` вместо `echo`** для переносимого форматирования вывода.
10. **Очищайте хеш-таблицу после установки ПО**: `hash -r` после `apt install` или `dnf install`, чтобы Bash увидел новые команды.

## Ограничения и edge cases

1.  **Brace Expansion** является Bash-specific и не работает в POSIX-оболочках (`dash`, `sh`).
2.  **Process substitution** требует поддержки `/dev/fd` или именованных каналов (FIFO). На некоторых минимальных системах (BusyBox) может отсутствовать.
3.  **`exec` полностью заменяет процесс**: после него не выполняется никакой код в текущем shell, включая `trap EXIT`.
4.  **`eval` выполняет двойной парсинг**: любая ошибка в переменной приводит к выполнению произвольного кода.
5.  **Word Splitting** зависит от `IFS`: изменение `IFS` влияет на обработку всех незакавыченных подстановок.
6.  **Globbing** не затрагивает скрытые файлы (начинающиеся с `.`) без явного указания `.*`.
7.  **Хеш-таблица** не обновляется автоматически: после установки новой версии команды в другом PATH, Bash может продолжать использовать старый кешированный путь до `hash -r`.
8.  **Subshell в конвейере** не сохраняет изменения переменных: используйте `shopt -s lastpipe` или process substitution.
9.  **`$PATH`** копируется при `fork()`, но не наследуется при `exec` без явного указания окружения. При запуске через `sudo` PATH может сбрасываться к secure_path.

## Troubleshooting

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `command not found` после установки | Хеш-таблица устарела | Выполните `hash -r` или запустите новую сессию shell |
| Переменная пустая внутри цикла `while` | Цикл выполняется в subshell (конвейер) | Используйте `while ... done < <(cmd)` или `shopt -s lastpipe` |
| `Permission denied` при запуске скрипта | Нет бита исполнения или неверный shebang | `chmod +x script.sh`; проверьте первую строку `#!/bin/bash` |
| `eval` выполняет неожиданные команды | Injection через переменную окружения | Замените `eval` на массивы или явные функции |
| Команда работает в терминале, но падает в cron | Отсутствует окружение (PATH, переменные) | Укажите полный путь к команде или настройте `BASH_ENV` |
| Процесс не получает SIGTERM в Docker | Entrypoint-shell без `exec` перехватывает сигнал | Добавьте `exec` перед основной командой в entrypoint-скрипте |
| `cd` не работает внутри `sudo` | `cd` — builtin, не передается через sudo | Используйте `sudo -s` или `sudo su -` для интерактивной сессии |
| `docker exec` возвращает `oci runtime error` | Контейнер остановлен или нет исполняемого файла | Проверьте `docker ps` и наличие `/bin/sh` или указанного `exec` |
| `find ... -exec cd {} \;` не меняет директорию | `cd` выполняется в subshell | Используйте `-execdir` или явные пути в команде |
| Скрипт работает при `bash -x`, но падает без | Зависимость от неинициализированной переменной | Включите `set -u` для отлова необъявленных переменных |

Переменная `$PATH` просматривается слева направо. Наличие `.` (текущей директории) в начале `$PATH` является критической уязвимостью, так как позволяет выполнить вредоносный файл вместо системной утилиты.
