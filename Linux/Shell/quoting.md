# Экранирование и использование кавычек в Shell

## Определения

**Экранирование (Quoting)** — механизм управления интерпретацией специальных символов оболочкой. Он определяет, будет ли символ обработан Shell как управляющая конструкция (например, `$` как начало подстановки) или воспринят как обычный текстовый символ (литерал).

- **Разбиение на слова (Word Splitting)** — процесс разделения строки на отдельные аргументы на основе символов-разделителей (переменная `IFS`). Кавычки позволяют объединять текст с пробелами в один аргумент.
- **Подстановка (Expansion)** — процесс замены конструкций (переменных, результатов команд) на их значения. Кавычки управляют тем, на каком этапе и какие именно подстановки будут выполнены.
- **Продолжение строки (Line Continuation)** — обработка обратного слэша `\` непосредственно перед символом новой строки. Символ новой строки удаляется, а следующая строка склеивается с текущей. Это позволяет разбивать длинные команды на несколько физических строк без выполнения подстановок.

## Базовые концепции

### Основные механизмы экранирования

| Механизм | Символы | Описание | Пример |
| :--- | :--- | :--- | :--- |
| **Одинарные кавычки** | `'...'` | Полная изоляция. Все символы внутри воспринимаются буквально. | `'$VAR'` → `$VAR` |
| **Двойные кавычки** | `"..."` | Частичная изоляция. Разрешают подстановки `$`, `` ` ``, `\` и `!`. | `"$VAR"` → `значение` |
| **Обратный слэш** | `\` | Экранирование следующего одиночного символа. | `\$` → `$` |
| **ANSI-C Quoting** | `$'...'` | Интерпретация escape-последовательностей (`\n`, `\t`, `\xHH`, `\uHHHH`). Синтаксис специфичен для Bash и Zsh; не поддерживается в POSIX `sh`. | `$'\t'` → символ табуляции |
| **Локализация** | `$"..."` | Перевод строки через `gettext` (зависит от локали). Используется редко; в большинстве интерактивных скриптов эквивалентен двойным кавычкам. | `$"Message"` → `Сообщение` |

### Поведение внутри двойных кавычек

Двойные кавычки подавляют разбиение на слова и глоббинг (подстановку имен файлов), но сохраняют:
- **Подстановку переменных**: `"$VAR"`, `"${VAR}"`.
- **Подстановку команд**: `"$(command)"`, `` "`command`" ``.
- **Арифметические вычисления**: `"$((1 + 1))"`.
- **Обратный слэш (`\`)**: сохраняет специальное значение только перед символами `$`, `` ` ``, `"`, `\` и символом новой строки. В остальных случаях `\` остается литералом (например, `"\n"` выведет `\n`, а не новую строку).
- **Историческое расширение (`!`)**: в интерактивных оболочках (`bash`, `zsh`) внутри двойных кавычек `!` может активировать подстановку истории (например, `!!` → предыдущая команда). В скриптах, выполняемых неинтерактивно, этот механизм отключен по умолчанию.

### Взаимодействие с IFS и глоббингом

Кавычки и переменная `IFS` (Internal Field Separator) управляют разными фазами обработки строки, но их взаимодействие определяет конечный набор аргументов.

- **Без кавычек**: результат подстановки проходит через разбиение по `IFS`, затем глоббинг.
- **В двойных кавычках**: разбиение по `IFS` подавляется, глоббинг подавляется; переменная воспринимается как единый аргумент.
- **В одинарных кавычках**: никаких подстановок и разбиений не происходит вообще.
- **Опция `set -f` (noglob)**: глоббинг отключается глобально для текущей оболочки. Это альтернатива кавычкам, когда нужно запретить раскрытие `*` и `?` во всех аргументах без заключения каждого в кавычки.
- **Опции `nullglob` и `failglob`** (через `shopt -s`): управляют поведением при отсутствии совпадений для глоб-шаблонов. `nullglob` заменяет несовпавший шаблон на пустую строку; `failglob` вызывает ошибку. Обе опции действуют только на неэкранированные шаблоны.

### Продолжение строки и комментарии

- **Обратный слэш в конце строки**: экранирует символ новой строки, склеивая следующую физическую строку с текущей. Подстановки при этом не выполняются.
- **`#` внутри кавычек**: не запускает комментарий. Только неэкранированный `#` в начале слова (после пробела или в начале строки) воспринимается как начало комментария.

### Экранирование в Heredoc, Herestring и Process Substitution

Поведение блока данных (`<<EOF`) зависит от кавычек в **ограничителе**:
- **`<<EOF` (без кавычек)**: переменные и команды внутри блока вычисляются.
- **`<<'EOF'`**: блок передается "как есть", без каких-либо подстановок.
- **`<<"EOF"`**: двойные кавычки в ограничителе удаляются оболочкой до обработки блока, поэтому переменные и команды внутри блока **вычисляются** (поведение идентично `<<EOF`).
- **`<<-EOF`**: как `<<EOF`, но ведущие символы табуляции в блоке удаляются. Удобно для отступов в скриптах.

**Herestring** (`<<<`) передает строку в `stdin` команды. Кавычки вокруг строки защищают её от подстановок до попадания в `stdin`:
```bash
# БЕЗ кавычек: $VAR раскрывается до передачи в grep
grep "pattern" <<< $VAR

# С кавычками: grep получает литерал "$VAR"
grep "pattern" <<< "$VAR"
```

**Process Substitution** (`<(cmd)`, `>(cmd)`) создает временный именованный канал. Кавычки вокруг конструкций `<( )` или `>( )` обязательны, если вывод команды содержит пробелы или специальные символы, иначе оболочка попытается интерпретировать путь к временному файлу как несколько аргументов:
```bash
# ПРАВИЛЬНО: кавычки защищают путь к /dev/fd/*
diff "$(sed 's/ /\n/g' file1)" "$(sed 's/ /\n/g' file2)"
# или
diff <(sed 's/ /\n/g' file1) <(sed 's/ /\n/g' file2)
```

### Специфика [ ... ] и [[ ... ]]

- В устаревшем тесте `[ "$VAR" = "val" ]` кавычки вокруг переменной **строго обязательны**. Если `$VAR` пуста или содержит пробелы, команда завершится с ошибкой `unary operator expected`.
- В расширенном тесте `[[ $VAR == "val" ]]` кавычки для переменной **необязательны** (но допустимы), так как `[[` — это ключевое слово Bash, которое само обрабатывает пустые значения. Однако кавычки в правой части (`== "pattern"`) отключают сопоставление по шаблону (wildcards).
- В обоих случаях кавычки вокруг литералов (`"val"`) обязательны, если литерал содержит пробелы или символы, интерпретируемые оболочкой.

## Практические сценарии

### Защита от разбиения на слова (Word Splitting)

Всегда используйте двойные кавычки при обращении к переменным, особенно содержащим пути к файлам.

```bash
# ОПАСНО: если в имени файла есть пробел, rm получит два аргумента
rm $FILE

# ПРАВИЛЬНО: файл будет удален как единый объект
rm "$FILE"
```

### Подготовка данных для повторного выполнения

Если нужно передать переменную в другую команду или сохранить её так, чтобы Shell мог снова её прочитать как один токен, используйте встроенные механизмы экранирования.

```bash
# Bash 4.4+: использование флага @Q
SAFE_VAL="${VAR@Q}"

# POSIX-совместимый способ (через printf)
SAFE_VAL=$(printf '%q' "$VAR")

# Пример: передача сложной строки через SSH
ssh user@host "ls ${VAR@Q}"
```

### Экранирование при удаленном выполнении (SSH)

SSH создает минимум два уровня оболочки: локальную (где строится команда) и удаленную (которая её выполняет). Это требует двойного или тройного экранирования.

```bash
# УРОВЕНЬ 1: Локальная оболочка парсит строку
# УРОВЕНЬ 2: Удаленная оболочка парсит строку ДВАЖДЫ (sh -c "cmd")

# ПРАВИЛЬНО: локальная кавычка + одинарные кавычки на удаленной стороне
ssh user@host 'systemctl restart nginx && echo "OK"'

# Если нужно передать локальную переменную на удаленный хост:
ssh user@host "echo '${LOCAL_VAR@Q}'"

# Сложный пример: передача конфига через heredoc
ssh user@host << 'REMOTE_EOF'
set -euo pipefail
cat > /etc/myapp/config.conf << 'INNER_EOF'
[database]
host = localhost
port = 5432
INNER_EOF
systemctl restart myapp
REMOTE_EOF
```

### Экранирование в sudo

По умолчанию `sudo` запускает команду через минимальную оболочку. Кавычки защищают переменные на уровне локальной оболочки, но `sudo` сам по себе не изменяет интерпретацию кавычек.

```bash
# ПРАВИЛЬНО: локальная переменная защищена кавычками
sudo systemctl restart "$SERVICE_NAME"

# ОПАСНО: если SERVICE_NAME пуста, systemctl получит пустой аргумент
sudo systemctl restart $SERVICE_NAME

# При необходимости передать окружение:
sudo -E env "MY_VAR=$MY_VAR" /usr/local/bin/my_script.sh
```

### Экранирование в find, xargs и -exec

Утилиты `find` и `xargs` используют разделитель `\0` (null byte) как безопасную границу между именами файлов. Кавычки внутри `-exec` защищают от раскрытия `{}` и пробелов в именах файлов.

```bash
# ОПАСНО: xargs разобьет по пробелам в именах файлов
find /var/log -name "*.log" | xargs grep -l "error"

# ПРАВИЛЬНО: -print0 + xargs -0
find /var/log -name "*.log" -print0 | xargs -0 grep -l "error"

# ПРАВИЛЬНО: find -exec ... {} + (встроенная передача в xargs)
find /var/log -name "*.log" -exec grep -l "error" {} +

# Если команда сложная, используйте sh -c:
find /var/log -name "*.log" -exec sh -c 'grep -l "error" "$1" && echo "Found in $1"' _ {} \;
```

### Экранирование в systemd unit-файх

В директиве `ExecStart` оболочка не запускается автоматически. Если команда содержит несколько токенов или переменные окружения, требуется явный вызов `sh -c`.

```ini
[Service]
ExecStart=/usr/bin/myapp --config /etc/myapp.conf

# Если нужна оболочка (кавычки, перенаправления, переменные):
ExecStart=/bin/sh -c 'exec /usr/bin/myapp --config "/etc/path with spaces.conf" >> /var/log/myapp.log 2>&1'

# Передача переменных:
Environment="CONFIG_PATH=/etc/myapp.conf"
Environment="LOG_LEVEL=debug"
```

### Экранирование в cron

Cron выполняет команду через `/bin/sh -c`. Кавычки внутри строки crontab защищают аргументы, но сама строка команды должна быть корректно заключена, если содержит специальные символы (`%`, пробелы, `$`).

```bash
# В crontab: % интерпретируется как новая строка, поэтому экранируется как \%
# $ требует экранирования, если не нужно подстановка

# ПРАВИЛЬНО: двойные кавычки защищают пробелы и $, \% экранирует %
0 2 * * * /bin/sh -c 'tar -czf /backup/$(date +\%Y\%m\%d).tar.gz /data'

# ИЛИ: обертка в скрипт (надежнее)
0 2 * * * /usr/local/bin/backup.sh
```

### Обработка массивов и позиционных параметров

Различие между `"$*"` и `"$@"` является фундаментальным при передаче аргументов.

```bash
# "$*" — склеивает все аргументы в одну строку через первый символ IFS
# "$@" — сохраняет каждый аргумент как отдельное слово в кавычках (безопасно)

for arg in "$@"; do
    process "$arg"
done
```

### Экранирование в операторе case

В конструкции `case` кавычки определяют, будет ли правая часть шаблоном или литералом.

```bash
case "$VAR" in
    "$PATTERN") echo "Точное совпадение со строкой из переменной PATTERN" ;;
    $PATTERN)   echo "Сопоставление по глоб-шаблону из переменной PATTERN" ;;
esac
```

### Вложенные кавычки в $(...)

Конструкция `$(...)` (в отличие от старых обратных кавычек `` `...` ``) создает новый контекст экранирования. Кавычки внутри неё не конфликтуют с внешними.

```bash
# Это корректно и безопасно
output="$(grep "pattern" "$(ls "$dir")")"
```

### Работа с конфигурационными данными и JSON

При передаче shell-переменных в утилиты, работающие с JSON (curl, jq, mysql, psql), избегайте строковой интерполяции. Используйте параметризованные флаги.

```bash
# ОПАСНО: инъекция через двойные кавычки и интерполяцию
curl -X POST -d "{\"user\":\"$USERNAME\",\"pass\":\"$PASSWORD\"}" https://api.example.com/login

# ПРАВИЛЬНО: jq сборка JSON
curl -X POST -d "$(jq -n --arg u "$USERNAME" --arg p "$PASSWORD" '{user:$u, pass:$p}')" https://api.example.com/login

# Для psql: используйте переменные окружения или параметризованные запросы
psql -v user="$USERNAME" -c "SELECT * FROM users WHERE name = :'user'"

# Для awk: передавайте через -v, а не через интерполяцию
awk -v search="$PATTERN" '$0 ~ search {print NR": "$0}' /var/log/app.log
```

## Безопасность

### Риски использования eval

Команда `eval` повторно парсит строку. Если данные в переменной не экранированы должным образом, это ведет к инъекции команд.

```bash
# УЯЗВИМО: если VAR="; rm -rf /", eval выполнит удаление
eval "echo $VAR"

# БЕЗОПАСНЕЕ (но все равно требует осторожности)
eval "echo ${VAR@Q}"
```

### Инъекции через переменные окружения и внешний ввод

В контексте DevOps/SRE quoting является первой линией защиты при передаче данных между системами. Любая переменная, полученная извне (факты Ansible, вывод API, пользовательский ввод), должна считаться потенциально вредоносной.

```bash
# ОПАСНО: непроверенный факт Ansible, внедренный в shell
ansible.builtin.shell: "grep {{ search_pattern }} /var/log/app.log"

# БЕЗОПАСНО: фильтр quote экранирует специальные символы
ansible.builtin.shell: "grep {{ search_pattern | quote }} /var/log/app.log"

# ОПАСНО: подстановка переменной в SQL через shell
mysql -e "SELECT * FROM users WHERE name = '$USER_INPUT'"

# БЕЗОПАСНО: параметризованные запросы или подготовленные выражения
mysql -e "SELECT * FROM users WHERE name = ?" --execute "$USER_INPUT"
```

### Типичные ошибки

| Ошибка | Последствие | Исправление |
| :--- | :--- | :--- |
| `echo 'It's a trap'` | Синтаксическая ошибка (одинарная кавычка внутри одинарных) | `"It's a trap"` или `'It'\''s a trap'` |
| `VAR="*"; echo $VAR` | Вывод списка всех файлов в текущей директории (глоббинг) | `echo "$VAR"` |
| `cmd "$VAR1 $VAR2"` | Две переменные передаются как ОДИН аргумент | `cmd "$VAR1" "$VAR2"` |
| `ssh host $CMD` | `$CMD` разбивается на слова локальной оболочкой до отправки | `ssh host "$CMD"` |
| `find ... | xargs rm` | Имена файлов с пробелами или кавычками ломают команду | `find ... -print0 \| xargs -0 rm` |
| `<<\"EOF\"` с переменными | Ожидание отсутствия подстановок, но подстановки выполняются | `<<'EOF'` для полной изоляции |
| `cron: * * * * * cmd $VAR` | `$` раскрывается в пустоту (cron не имеет shell-переменных) | Используйте полные пути или оберните в `sh -c` с определением переменных |
