# Управление задачами по расписанию: Cron, Anacron, At, Systemd Timers

## Определения

- **Cron:** Классический системный демон в Unix-подобных системах, предназначенный для выполнения задач (команд или скриптов) в указанное время или через заданные интервалы.
- **Crontab (Cron Table):** Текстовый файл, содержащий список задач и расписание их выполнения для конкретного пользователя или для всей системы.
- **Anacron:** Планировщик задач, ориентированный на периоды времени, а не на конкретное время суток. Предназначен для систем, которые не работают круглосуточно (например, ноутбуки или десктопы). Если компьютер был выключен во время запланированного выполнения, задача будет запущена при следующем включении.
- **At:** Утилита для запуска команд один раз в будущем в указанное время. Предназначена для разовых задач, в отличие от регулярного cron.
- **Batch:** Утилита для запуска команд, когда средняя нагрузка системы падает ниже определенного порога.
- **Systemd Timers:** Современная альтернатива cron в системах с systemd. Позволяет запускать юниты systemd по расписанию с более гибкими возможностями (монотонные таймеры, календарные события, зависимость от других юнитов). Подробнее: [Systemd Timers](../../Core/systemd/timers.md).

## Базовые концепции

### Структура файла Crontab

Каждая строка в файле `crontab` представляет собой одну задачу и состоит из двух частей: расписания и команды.

```
┌───────────── минута (0 - 59)
│ ┌───────────── час (0 - 23)
│ │ ┌───────────── день месяца (1 - 31)
│ │ │ ┌───────────── месяц (1 - 12)
│ │ │ │ ┌───────────── день недели (0 - 6) (Воскресенье=0 или 7)
│ │ │ │ │
* * * * * команда_для_выполнения
```

**Специальные символы:**

- `*`: Любое значение.
- `,`: Перечисление значений (например, `0,15,30,45`).
- `-`: Диапазон значений (например, `8-17`).
- `/`: Шаг значения (например, `*/15` — каждые 15 минут).

Для упрощения составления расписаний можно использовать онлайн-инструменты, такие как [crontab.guru](https://crontab.guru/).

### Контекст выполнения

- **Переменные окружения:** Задачи, запущенные через cron, выполняются в минимальном окружении, которое **не наследует** переменные из вашего интерактивного шелла (например, из `~/.bashrc` или `~/.profile`). `PATH` также обычно ограничен (`/usr/bin:/bin`).
- **Рабочий каталог:** По умолчанию, команды выполняются из домашнего каталога пользователя (`$HOME`).

Из-за этих особенностей в скриптах, запускаемых по крону, рекомендуется:

1. Использовать **абсолютные пути** к командам и файлам.
2. Явно определять или `source`-ить необходимые переменные окружения внутри самого скрипта.

## Практические сценарии

### 1. Управление пользовательскими задачами (`crontab`)

Команда `crontab` позволяет управлять задачами текущего пользователя.

- `crontab -l`: Посмотреть текущие задачи.
- `crontab -e`: Редактировать задачи. При сохранении изменений файл автоматически проверяется на синтаксис и устанавливается в систему.
- `crontab -r`: Удалить все задачи пользователя.

**Пример:** Запускать скрипт резервного копирования каждый день в 02:30 ночи.

```crontab
30 2 * * * /home/user/scripts/backup.sh
```

### 2. Управление системными задачами (`/etc/cron.d`)

Для системных задач, которые не привязаны к конкретному пользователю, предпочтительным способом является создание отдельных файлов конфигурации в каталоге `/etc/cron.d/`. Этот подход более удобен для управления конфигурацией с помощью систем, как [Ansible](../../Ansible/ansible_introduction.md).

Файлы в `/etc/cron.d` имеют тот же формат, что и `crontab`, но с одним дополнением: **после расписания указывается имя пользователя**, от имени которого должна выполниться команда.

**Пример:** Создадим файл `/etc/cron.d/disk-utilization` для запуска скрипта мониторинга диска каждую минуту от имени пользователя `q`.

```
# /etc/cron.d/disk-utilization

* * * * * q /home/q/scripts/check_disk_utilization.sh
```

### 3. Решение проблемы с переменными окружения

Рассмотрим скрипт, который отправляет уведомления в Telegram и использует переменные `BOT_ID` и `CHAT_ID`. При запуске через `cron` эти переменные будут пустыми.

**Плохое решение:** Жестко прописать токен в скрипте.
**Хорошее решение:** Поместить переменные в отдельный файл (например, `/etc/environment` или специальный `env`-файл) и подгружать их в скрипте.
**Простое решение (для примера):** Явно определить переменные в начале скрипта или передать их в команду.

**Пример скрипта `check_disk_utilization.sh`:**

```bash
#!/usr/bin/env bash

# Явно загружаем переменные, если они не заданы
if [[ -z "$BOT_ID" ]] || [[ -z "$CHAT_ID" ]]; then
    # Предполагаем, что переменные лежат в этом файле
    source /home/q/.telegram_env
fi

# ... остальная логика скрипта ...
```

Другой вариант — добавить их прямо в файл в `/etc/cron.d`:

```
# /etc/cron.d/disk-utilization
BOT_ID=...
CHAT_ID=...

* * * * * q /home/q/scripts/check_disk_utilization.sh
```

Однако этот способ менее безопасен, если у файла не настроены строгие права доступа.

### 4. Просмотр логов выполнения Cron

Чтобы проверить, был ли выполнен скрипт и были ли ошибки, можно использовать системный журнал.

```bash
# Для systemd-систем
journalctl -u cron.service

# В старых системах можно смотреть в /var/log/cron или /var/log/syslog
grep CRON /var/log/syslog
```

В выводе `journalctl` можно увидеть записи о запуске команд, пользователя и времени выполнения.

## Дополнительная информация

### Системные директории Cron

Помимо пользовательских crontab, в системе существуют директории для скриптов, которые должны выполняться регулярно:

- `/etc/cron.hourly/` — скрипты выполняются раз в час
- `/etc/cron.daily/` — скрипты выполняются раз в день
- `/etc/cron.weekly/` — скрипты выполняются раз в неделю
- `/etc/cron.monthly/` — скрипты выполняются раз в месяц

В современных дистрибутивах запуск этих скриптов часто управляется через **anacron**, а не напрямую через демон cron.

### Утилита `at` (разовые задачи)

Утилита `at` позволяет выполнить команду один раз в будущем в указанное время.

```bash
# Запланировать выполнение в 23:00
at 23:00

# Запланировать выполнение через 10 минут
at now +10 minutes

# Запланировать выполнение в полночь
at midnight

# Запланировать выполнение 21 марта в 01:00
at 1am March 21
```

После ввода команды `at` откроется интерактивная оболочка для ввода команд. Введите команды для выполнения, затем нажмите `Enter`, затем `Ctrl+D` для завершения ввода.

**Просмотр задач:**

```bash
at -l        # Список задач
atq          # То же, что и at -l
at -d 3     # Удалить задачу с номером 3
atrm 3      # То же, что и at -d
```

**Управление доступом:**

- `/etc/at.allow` — список пользователей, которым разрешено использовать `at` (если файл существует, только перечисленные пользователи могут использовать at)
- `/etc/at.deny` — список пользователей, которым запрещено использовать `at` (по умолчанию пустой, т.е. всем разрешено)
- Если нет ни одного файла, только root может использовать `at`

### Утилита `batch` (выполнение при низкой нагрузке)

Утилита `batch` похожа на `at`, но не требует указания времени. Команда выполняется, когда средняя нагрузка системы (load average) падает ниже указанного порога (по умолчанию 0.8).

```bash
# Запустить команду, когда нагрузка упадет ниже 0.8
batch
```

**Настройка порога нагрузки:**
Изменяется в `/etc/sysconfig/atd`.

### Anacron

Anacron предназначен для систем, которые не работают постоянно. В отличие от cron, он работает с периодами времени, а не с конкретным временем суток.

**Ключевое отличие от cron:**

- **Cron:** Жестко привязан к времени. Если система выключена в момент выполнения задачи, задача будет пропущена до следующего запланированного запуска.
- **Anacron:** Ориентирован на периоды. Если компьютер был выключен во время запланированного выполнения (например, в полночь), задача будет запущена при следующем включении системы.

Это делает anacron идеальным выбором для настольных компьютеров и ноутбуков, которые не работают круглосуточно.

**Конфигурация:** `/etc/anacrontab`

**Пример формата:**

```conf
# Период (дней)  Задержка (минут)  Идентификатор  Команда
1                5                 cron.daily     /usr/bin/run-parts /etc/cron.daily
```

- **Период:** Как часто выполнять задачу (1 = ежедневно, 7 = еженедельно)
- **Задержка:** Задержка после включения компьютера перед выполнением (чтобы не нагружать систему сразу после загрузки)
- **Идентификатор:** Уникальное имя для логов
- **Команда:** Команда для выполнения

**Переменные в anacron:**

- `START_HOURS_RANGE` — диапазон часов, в который разрешен запуск задач (например, 3-22)
- `RANDOM_DELAY` — максимальная случайная задержка в минутах (по умолчанию 45), чтобы избежать одновременной нагрузки на сеть при массовом включении компьютеров

### Пользовательские задачи Cron и At

Задачи пользователей (не root) не лежат в `/etc`. Они хранятся в:

- `/var/spool/cron/crontabs/` — для cron
- `/var/spool/at/` — для at

Просмотр задач конкретного пользователя возможен через команду `crontab -u username -l`, но для полного списка всех запланированных задач на системе нужно анализировать эти директории (требуются права root).

## Дополнительная информация

### Сравнение Cron и Systemd Timers

| Критерий | Cron | Systemd Timers |
| :--- | :--- | :--- |
| **Точность** | До минуты | До секунды |
| **Типы таймеров** | Только календарные | Календарные + монотонные (относительные) |
| **Зависимости** | Нет | Может зависеть от других юнитов |
| **Логирование** | Через syslog/journald | Интегрировано с journald |
| **Отложенный запуск** | Через `@reboot` или anacron | `OnBootSec`, `OnUnitActiveSec` |
| **Пропущенные задачи** | Пропускаются | `Persistent=true` выполняет при включении |
| **Контекст выполнения** | Минимальное окружение | Полная среда systemd |
| **Аудит** | Через логи cron | Через `journalctl -u <timer>` |

**Когда использовать Cron:**

- Простые сценарии, совместимость со старыми системами
- Скрипты, требующие минимального окружения
- Быстрая настройка без создания systemd-юнитов

**Когда использовать Systemd Timers:**

- Сложные зависимости между сервисами
- Требуется точное логирование и мониторинг
- Нужны монотонные таймеры (например, "каждые 5 минут после запуска")
- Интеграция с другими systemd-юнитами

**Пример миграции с cron на systemd timer:**

Cron-задача:

```crontab
0 2 * * * /usr/local/bin/backup.sh
```

Systemd timer (см. [Systemd Timers](../../Core/systemd/timers.md)):

```ini
# /etc/systemd/system/backup.timer
[Unit]
Description=Daily backup timer

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
```
