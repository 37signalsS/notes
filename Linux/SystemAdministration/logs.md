# Системные журналы (логи) в Linux

Системные журналы (логи) — это файлы, в которые записываются системные сообщения и события, происходящие в операционной системе. Анализ логов является ключевым навыком для диагностики проблем, отслеживания производительности и расследования инцидентов безопасности.

В Linux существует две основные системы логирования:
1.  **`rsyslog`**: Классический демон, который собирает текстовые логи из разных источников и записывает их в файлы в `/var/log`.
2.  **`systemd-journald`**: Современная система, которая собирает все логи в централизованный бинарный журнал.

Часто эти системы работают вместе: `journald` собирает все сообщения, а `rsyslog` забирает их из журнала для дальнейшей отправки на удаленный сервер.

## Основные файлы логов

Вне зависимости от системы логирования, стандартные логи чаще всего можно найти в директории `/var/log/`.

-   `/var/log/syslog` (Debian/Ubuntu) или `/var/log/messages` (CentOS/RHEL): Главный системный лог, куда попадает большинство событий от ядра и служб.
-   `/var/log/auth.log` (Debian/Ubuntu) или `/var/log/secure` (CentOS/RHEL): События аутентификации (входы по SSH, `sudo`, неудачные попытки). **Ключевой файл для анализа безопасности.**
-   `/var/log/dmesg`: Сообщения ядра при загрузке. Подробное описание утилиты `dmesg` находится в файле [kernel.md](../Core/kernel.md#инструмент-dmesg).
-   `/var/log/boot.log`: Лог процесса загрузки.
-   `/var/log/apt/` (Debian/Ubuntu) или `/var/log/yum.log` (CentOS/RHEL): Логи менеджера пакетов.
-   **Логи приложений:** Многие приложения (например, `nginx`, `apache2`, `postgresql`) создают свои собственные поддиректории в `/var/log/` или пишут в общие системные логи. Если не настроен иной путь, по умолчанию логи приложений часто попадают в `/var/log/` или его поддиректории.

## Недостатки локального логирования и необходимость централизации

Хранение логов локально на каждом хосте имеет ряд существенных недостатков:

-   **Потребление дискового пространства и I/O:** Логи постоянно растут, занимая место на диске и создавая нагрузку на подсистему ввода-вывода.
-   **Угроза безопасности:** Локальные логи проще удалить или подделать злоумышленником, получившим доступ к системе.
-   **Сложность анализа:** В больших инфраструктурах (десятки или сотни серверов) анализ логов на каждом хосте вручную становится неэффективным и трудоемким.
-   **Отсутствие агрегации:** Сложно получить общую картину происходящего в системе, коррелировать события между разными хостами.

Для решения этих проблем применяется **централизованное логирование**, когда логи со всех хостов собираются на одном или нескольких выделенных серверах. Это упрощает анализ, повышает безопасность и позволяет использовать специализированные инструменты для обработки и визуализации логов (например, ELK Stack, Loki, OpenSearch).

## Традиционная система: `rsyslog`

`rsyslog` — это мощная и гибкая служба для сбора и обработки логов. Она может читать сообщения из различных источников (файлы, сокеты, ядро) и направлять их в файлы или на удаленный сервер.

### Архитектура и модули

`rsyslog` имеет модульную архитектуру, что позволяет ему быть очень гибким. Существуют четыре основных типа модулей:

-   **Модули ввода (Input Modules, `im`):** Отвечают за сбор информации из различных источников. Начинаются с префикса `im` (например, `imudp` для UDP, `imtcp` для TCP, `imuxsock` для Unix-сокетов, `imjournal` для `systemd-journald`).
-   **Модули вывода (Output Modules, `om`):** Отвечают за отправку логов в различные места назначения (файлы, удаленные серверы, базы данных). Начинаются с префикса `om` (например, `omfile` для файлов, `omfwd` для пересылки).
-   **Модули фильтрации (Filter Modules, `fm`):** Используются для фильтрации сообщений по различным параметрам.
-   **Модули парсинга (Parsing Modules, `pm`):** Предоставляют дополнительные возможности для синтаксического анализа сообщений.

### Конфигурация (`/etc/rsyslog.conf`)

Правила сортировки логов описываются в `/etc/rsyslog.conf` и файлах в `/etc/rsyslog.d/`.

**Структура правила:** `источник.приоритет действие`

-   **Источник (Facility):** Категория сообщения (`auth`, `cron`, `kern`, `mail`, `local0-7`).
-   **Приоритет (Severity):** Уровень важности (`debug`, `info`, `notice`, `warning`, `err`, `crit`, `alert`, `emerg`). Звездочка `*` означает любой уровень.
-   **Действие (Action):** Куда отправить лог (путь к файлу, `@` или `@@` для удаленного хоста).

**Пример правил:**
```conf
# Все сообщения, связанные с аутентификацией, писать в /var/log/auth.log
auth,authpriv.*         /var/log/auth.log

# Все сообщения, кроме auth, cron и mail, писать в /var/log/syslog
*.*;auth,authpriv.none;cron.none;mail.none -/var/log/syslog
```
*Знак `-` перед путем к файлу (например, `-` `/var/log/syslog`) означает **асинхронную запись**. Это повышает производительность, так как `rsyslog` не ждет сброса данных на диск после каждой записи. Однако это несет риск потери последних сообщений при внезапном сбое системы.*

### Настройка удаленного логирования (Centralized Logging)

`rsyslog` позволяет настроить централизованный сбор логов с нескольких машин на один сервер.

#### Настройка сервера (получателя логов)

1.  **Включите прием логов.** В файле `/etc/rsyslog.conf` или в новом файле `/etc/rsyslog.d/50-remote.conf` раскомментируйте или добавьте:
    ```conf
    # Включаем прием логов по UDP
    module(load="imudp")
    input(type="imudp" port="514")

    # Включаем прием логов по TCP
    module(load="imtcp")
    input(type="imtcp" port="514")
    ```
2.  **Создайте шаблон для сохранения.** Чтобы логи с разных хостов не смешивались, используется шаблон, который создает отдельные файлы для каждого хоста.
    ```conf
    # Создаем шаблон: /var/log/remote/HOSTNAME/PROGRAM.log
    template(name="RemoteHostLog" type="string"
             string="/var/log/remote/%HOSTNAME%/%PROGRAMNAME%.log")

    # Применяем шаблон ко всем входящим сообщениям
    *.* action(type="omfile" dynaFile="RemoteHostLog")
    ```
3.  **Перезапустите rsyslog и откройте порт в брандмауэре.**
    ```bash
    sudo systemctl restart rsyslog
    # Пример для firewalld
    sudo firewall-cmd --add-port=514/tcp --permanent
    sudo firewall-cmd --add-port=514/udp --permanent
    sudo firewall-cmd --reload
    ```

#### Настройка клиента (отправителя логов)

1.  **Настройте пересылку.** В `/etc/rsyslog.d/50-remote-client.conf` добавьте правило, заменяя `remote-log-server` на IP вашего сервера.
    ```conf
    # Для TCP (надежно, с подтверждением доставки)
    *.* @@remote-log-server:514

    # Для UDP (быстро, но без гарантии доставки)
    # *.* @remote-log-server:514
    ```
    - `@@` указывает на использование протокола TCP.
    - `@` указывает на использование протокола UDP.

2.  **Перезапустите rsyslog.**
    ```bash
    sudo systemctl restart rsyslog
    ```

## Современная система: `systemd-journald`

`journald` — это централизованная служба, которая собирает логи от всех компонентов системы (ядро, службы, приложения) в структурированном бинарном формате. Основной инструмент для работы — `journalctl`.

### Просмотр логов (`journalctl`)

-   **Просмотр в реальном времени:**
    ```bash
    # Следить за всеми логами
    journalctl -f
    ```

-   **Фильтрация по службе (unit):**
    ```bash
    # Показать логи только для nginx и следить за ними
    journalctl -u nginx.service -f
    ```

-   **Фильтрация по времени:**
    ```bash
    # Логи за последний час
    journalctl --since "1 hour ago"

    # Логи за определённый период
    journalctl --since "2024-10-20 10:00:00" --until "2024-10-20 11:00:00"
    ```

-   **Фильтрация по уровню приоритета:**
    ```bash
    # Показать только ошибки (err) и более критичные сообщения
    journalctl -p err
    ```
    **Уровни (от высшего к низшему):** `emerg` (0), `alert` (1), `crit` (2), `err` (3), `warning` (4), `notice` (5), `info` (6), `debug` (7).

-   **Просмотр логов ядра (аналог `dmesg`):**
    ```bash
    journalctl -k
    ```

-   **Структурированный вывод:**
    `journald` хранит метаданные для каждого сообщения. Их можно вывести в формате JSON.
    ```bash
    # Вывести последние 5 сообщений в формате JSON
    journalctl -n 5 -o json-pretty
    ```

### Постоянное хранение и ограничение размера

По умолчанию `journald` хранит логи в `/run/log/journal` (очищается при перезагрузке).

1.  **Включение постоянного хранения:**
    Чтобы логи сохранялись после перезагрузки, необходимо изменить параметр `Storage` в `/etc/systemd/journald.conf` на `persistent` или создать директорию `/var/log/journal`.
    ```bash
    # Создание директории для постоянного хранения логов
    sudo mkdir -p /var/log/journal
    # Применение изменений (systemd-tmpfiles создаст необходимые файлы и установит права)
    sudo systemd-tmpfiles --create --prefix /var/log/journal
    sudo systemctl restart systemd-journald
    ```
    После этого `journald` будет автоматически использовать `/var/log/journal` для постоянного хранения.

2.  **Ограничение размера журнала:**
    Чтобы логи не заняли весь диск, настройте лимиты в `/etc/systemd/journald.conf`:
    ```ini
    [Journal]
    # Максимальный общий размер журнала (например, 4 ГБ)
    SystemMaxUse=4G

    # Минимальный объем свободного места, который должен оставаться
    SystemKeepFree=15%

    # Максимальный размер одного файла журнала
    SystemMaxFileSize=200M
    ```
    После изменения файла перезапустите службу: `sudo systemctl restart systemd-journald`.
    Проверить текущий размер журнала можно командой: `journalctl --disk-usage`.

## Интеграция journald и rsyslog

В современных системах `rsyslog` часто работает совместно с `journald`, забирая из него логи для дальнейшей пересылки или обработки. Для этого используется модуль `imjournal`.

1.  **Настройка `rsyslog`:**
    Убедитесь, что в `/etc/rsyslog.conf` или в `/etc/rsyslog.d/` загружается модуль `imjournal`.
    ```conf
    # Загружаем модуль для чтения из journald
    module(load="imjournal")
    ```
2.  **Перезапустите `rsyslog`:**
    ```bash
    sudo systemctl restart rsyslog
    ```

Теперь `rsyslog` будет получать все сообщения из `journald` и обрабатывать их согласно своим правилам, включая отправку на удаленный сервер. Это позволяет сочетать преимущества структурированного локального хранения `journald` с мощными возможностями `rsyslog` по фильтрации и пересылке.

## Ротация логов (`logrotate`)

Чтобы текстовые лог-файлы (такие как `/var/log/syslog` или логи приложений) не занимали все место на диске, утилита `logrotate` периодически их архивирует и удаляет.

-   **Основной конфиг:** `/etc/logrotate.conf`
-   **Конфиги для отдельных служб:** `/etc/logrotate.d/`

**Пример конфигурации для Nginx (`/etc/logrotate.d/nginx`):**
```
/var/log/nginx/*.log {
    daily
    missingok
    rotate 14
    compress
    delaycompress
    notifempty
    create 0640 nginx adm
    sharedscripts
    postrotate
        [ -f /var/run/nginx.pid ] && kill -USR1 `cat /var/run/nginx.pid`
    endscript
}
```
-   `daily` / `weekly` / `monthly` / `yearly` / `hourly`: Частота ротации (ежедневно, еженедельно, ежемесячно, ежегодно, ежечасно).
-   `rotate 14`: Хранить 14 старых лог-файлов.
-   `compress`: Сжимать старые логи (обычно с помощью `gzip`).
-   `delaycompress`: Не сжимать предпоследний лог, чтобы его было удобнее анализировать.
-   `missingok`: Не выдавать ошибку, если лог-файл не существует.
-   `notifempty`: Не ротировать пустые файлы.
-   `create 0640 nginx adm`: Создать новый пустой лог-файл с указанными правами (`0640`), владельцем (`nginx`) и группой (`adm`) после ротации.
-   `sharedscripts`: Указывает, что скрипты `prerotate`/`postrotate` должны быть выполнены только один раз для всех логов, соответствующих шаблону, а не для каждого файла отдельно.
-   `postrotate...endscript`: Команды, которые нужно выполнить после ротации (в данном случае, "переоткрыть" лог-файлы в Nginx).
-   `copytruncate`: Создать копию лог-файла, а затем обрезать оригинал до нуля. Полезно для приложений, которые не умеют переоткрывать свои лог-файлы после ротации.
-   `maxsize 100M`: Ротировать лог, если его размер превышает 100 МБ, независимо от частоты ротации.
-   `mail user@example.com`: Отправить ротированный лог на указанный адрес электронной почты.

**Проверка конфигурации:**
```bash
# Выполнить "сухой запуск" для отладки
sudo logrotate -d /etc/logrotate.conf
```

## Аудит доступа: `auditd`

`auditd` — это система, которая отслеживает события на уровне ядра (системные вызовы). Она отвечает на вопросы: **кто, когда, что и с каким файлом сделал**. Это мощный инструмент для отслеживания изменений в системе и расследования инцидентов безопасности.

### Пример: отслеживание изменений файла

1.  **Установить правило для отслеживания.**
    Отследим, кто изменяет (`w`) или меняет атрибуты (`a`) файла `/etc/passwd`.
    ```bash
    # -w /path/to/file: путь к файлу
    # -p wa: права доступа (w - write, r - read, x - execute, a - attribute change)
    # -k key_name: уникальный ключ для поиска
    sudo auditctl -w /etc/passwd -p wa -k passwd_changes
    ```

2.  **Найти события в логе.**
    Для поиска по ключу используется `ausearch`. Логи хранятся в `/var/log/audit/audit.log`.
    ```bash
    sudo ausearch -k passwd_changes
    ```
    Вывод покажет `uid` (ID пользователя), `pid` (ID процесса) и команду, которая изменила файл.

3.  **Сгенерировать отчет (опционально).**
    Утилита `aureport` помогает создавать сводные отчеты из логов аудита.
    ```bash
    # Отчет о событиях аутентификации
    sudo aureport -au
    ```

**Важно:** Правила, добавленные через `auditctl`, сбрасываются после перезагрузки. Для постоянного хранения добавляйте их в файл `/etc/audit/rules.d/audit.rules`.

## Инструменты для анализа логов

Для просмотра и анализа логов используются различные утилиты командной строки:

-   **`tail`**: Просмотр конца файла в реальном времени.
    ```bash
    # Показать последние 50 строк и следить за обновлениями
    tail -f -n 50 /var/log/syslog
    ```
    Полезен для мониторинга активных логов.

-   **`cat`**: Выводит содержимое файла целиком.
    ```bash
    cat /var/log/syslog
    ```
    Подходит для небольших файлов. Для больших логов (десятки мегабайт и более) использование `cat` может быть неэффективным и даже привести к зависанию терминала.

-   **`less`**: Мощный просмотрщик с поиском и фильтрацией.
    ```bash
    less /var/log/syslog
    ```
    **Полезные команды в `less`:**
    -   `Shift + F`: Режим `tail -f`.
    -   `/шаблон`: Поиск вперед.
    -   `?шаблон`: Поиск назад.
    -   `&шаблон`: Показать только строки, содержащие "шаблон".
    -   `&!шаблон`: Скрыть строки, содержащие "шаблон".

-   **`grep`**: Поиск текста по шаблону в файлах. Часто используется в связке с `tail` или `cat`.
    ```bash
    grep "error" /var/log/syslog
    ```

-   **`zcat` / `zgrep`**: Утилиты для работы со сжатыми логами (например, `.gz` файлами), которые часто создаются `logrotate`. Позволяют просматривать или искать в сжатых файлах без предварительной распаковки.
    ```bash
    zcat /var/log/syslog.1.gz | less
    zgrep "error" /var/log/syslog.1.gz
    ```

-   **`lnav`**: Интерактивный просмотрщик логов с подсветкой синтаксиса, фильтрацией и возможностью просмотра сжатых файлов.

-   **`lsof`**: Показывает, какие процессы используют определенные файлы.
    ```bash
    # Найти все процессы, использующие файлы в /var/log
    sudo lsof +D /var/log
    ```
    **Основные колонки вывода `lsof`:**
    -   `COMMAND`: Имя команды (процесса).
    -   `PID`: Идентификатор процесса.
    -   `USER`: Пользователь, от имени которого запущен процесс.
    -   `FD`: Файловый дескриптор (`cwd`, `txt`, `mem` или число).
    -   `TYPE`: Тип файла (`REG` - обычный файл, `DIR` - директория).
    -   `NAME`: Полный путь к файлу.

## Другие инструменты для анализа ошибок и сбоев

Помимо систем логирования, существуют специализированные инструменты для анализа критических ошибок и сбоев:

-   **`abrt` (Automatic Bug Reporting Tool):** Инструмент для автоматического создания отчетов об ошибках приложений. Он перехватывает сбои, собирает информацию (трассировки стека, дампы памяти) и может автоматически отправлять отчеты разработчикам или в баг-трекеры. Особенно полезен для мониторинга собственного прикладного ПО.

-   **`kdump`:** Механизм ядра Linux для сбора дампов памяти (crash dumps) в случае критического сбоя ядра (Kernel Panic). Он загружает второе, минимальное ядро в зарезервированную область памяти, которое сохраняет образ памяти основного ядра на диск для последующего анализа. Подробнее см. в [kernel.md](../Core/kernel.md#kernel-panic-анализ-и-отладка).

-   **`coredumpctl`:** Утилита для работы с дампами памяти процессов, управляемая `systemd`. Позволяет просматривать, извлекать и анализировать дампы процессов, которые аварийно завершились. Подробнее см. в [processes.md](../Core/processes.md#анализ-сбоев-coredump).
