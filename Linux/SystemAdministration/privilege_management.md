# Управление привилегиями: su, sudo и Polkit

## Определения

* **Суперпользователь (`root`)**: Пользователь с UID 0, обладающий неограниченными правами в системе Linux. Его домашний каталог — `/root`.
* **`su` (Switch User / Substitute User)**: Команда для полного переключения сессии на другого пользователя или `root`.
* **`sudo` (Superuser Do)**: Команда для выполнения одной или нескольких команд от имени другого пользователя (по умолчанию `root`), без переключения всей сессии.
* **PolicyKit (Polkit)**: Фреймворк для управления привилегированными действиями для непривилегированных пользователей, часто используется в графических средах.
* **`setuid()`**, **`seteuid()`**, **`setreuid()`**: Системные вызовы, позволяющие процессу изменять идентификаторы пользователя (EUID, RUID, SUID) для управления привилегиями.
* **Login shell vs Non-login shell**: Тип оболочки, определяющий какие файлы конфигурации читаются при входе. Login shell сначала читает `/etc/profile`, затем `~/.bash_profile` (который может ссылаться на `~/.bashrc` и `/etc/bashrc`). Non-login shell читает только `~/.bashrc` и `/etc/bashrc`.
* **`visudo`**: Утилита для безопасного редактирования `/etc/sudoers`. Создает временную копию файла, проверяет синтаксис перед сохранением и предотвращает блокировку системы из-за ошибок.

## Базовые концепции

### Принцип наименьших привилегий

Фундаментальный принцип безопасности, требующий, чтобы любой процесс или пользователь имел только те права, которые абсолютно необходимы для выполнения его задач. Запуск сервисов от имени `root`, когда это не требуется, является серьезным риском безопасности.

### `su` (Switch User / Substitute User)

Команда `su` позволяет полностью переключить сессию на другого пользователя. Без указания имени пользователя по умолчанию переключает на `root`.

* `su <имя_пользователя>`: Переключение на указанного пользователя, требуется пароль целевого пользователя.
* `su -` или `su -l`: Переключение на `root` с полной инициализацией окружения (login shell). Переменные окружения, домашний каталог и рабочая директория меняются на целевого пользователя.
* `su <имя_пользователя> -c "<команда>"`: Запустить команду от имени другого пользователя без переключения сессии.

**Определение типа оболочки:** Проверьте переменную `$0`. При non-login shell значение будет `bash`, при login shell — `-bash`.

Основной недостаток `su` — необходимость делиться паролем `root`, что является плохой практикой. Использование `root` напрямую снижает безопасность и затрудняет аудит действий.

### `sudo` (Superuser Do)

Команда `sudo` позволяет выполнить одну или несколько команд от имени другого пользователя (по умолчанию `root`), не переключая всю сессию.

* **Пароль**: Запрашивает пароль текущего пользователя.
* **Принцип работы**: `sudo` проверяет `/etc/sudoers` для определения прав текущего пользователя на выполнение команды.
* **Логирование**: Каждое действие через `sudo` записывается в системный журнал (например, `/var/log/auth.log`), создавая аудиторский след.

Основные команды `sudo`:

* `sudo <команда>`: Выполнить команду с правами `root`.
* `sudo -l`: Просмотреть разрешенные команды.
* `sudo -u <имя_пользователя> <команда>`: Выполнить команду от имени другого пользователя.
* `sudo !!`: Выполнить последнюю команду с правами `sudo`.

#### Влияние на текущую оболочку

Встроенные команды Bash (например, `cd`, `export`), запущенные через `sudo <команда>`, выполняются в отдельной подоболочке. Изменения, внесенные в этой подоболочке, не сохраняются в родительской оболочке. Для выполнения нескольких команд, влияющих на привилегированную оболочку, используйте `sudo -i` или `sudo -s`.

### Конфигурация `sudo`: файл `/etc/sudoers`

Этот файл определяет права пользователей и групп на использование `sudo`.

#### Редактирование и структура: `visudo` и `/etc/sudoers.d`

**`visudo`**
: **Всегда** используйте команду `visudo` для редактирования файла `/etc/sudoers`. `visudo` открывает файл в текстовом редакторе и, что самое важное, **проверяет синтаксис перед сохранением**. Если вы допустите ошибку, `visudo` предупредит вас и не позволит сохранить некорректные изменения, которые могли бы полностью заблокировать работу `sudo` в системе.

При запуске `visudo` создает временный файл (`/etc/sudoers.tmp`). При сохранении с ошибкой программа предложит варианты: `e` (вернуться к редактированию), `x` (выйти без сохранения), `q` (сохранить с предупреждением). Настройте переменную `EDITOR` (например, `export EDITOR=nano` в `~/.bashrc`) для выбора предпочитаемого редактора.

**Директория `/etc/sudoers.d`**
: Современный и рекомендуемый подход — не изменять основной файл `/etc/sudoers` напрямую. Вместо этого следует создавать отдельные файлы для каждого пользователя или сервиса в директории `/etc/sudoers.d/`.

* **Преимущества:**
  * **Модульность:** Каждая конфигурация изолирована в своем файле.
  * **Простота управления:** Легко добавлять, удалять и отключать правила.
  * **Безопасность:** Снижается риск повредить основной файл конфигурации.

Файл в `/etc/sudoers.d` должен иметь имя без точек и тильд и иметь такие же права, как у `/etc/sudoers`.

```bash
# Пример создания правила для пользователя 'developer'
sudo visudo -f /etc/sudoers.d/developer
# Внутри файла:
# developer ALL=(ALL) NOPASSWD: /usr/bin/apt update
```

#### Базовый синтаксис правил

```
кто     хост=(от_имени_кого) что_делать
```

* `кто`: Имя пользователя или `%имя_группы` (для групп используется префикс `%`).
* `хост`: Хост, на котором действует правило (обычно `ALL` или совпадает с `hostname`).
* `от_имени_кого`: От имени какого пользователя (обычно `ALL` для `root`).
* `что_делать`: Команда или список команд. Префикс `!` запрещает команду.

**Группы `wheel` и `sudo`:** В CentOS/RHEL группа `wheel` дает полные права `sudo`. В Debian/Ubuntu аналогичную роль выполняет группа `sudo`. Добавить пользователя в группу: `usermod -aG wheel username`.

**Комбинация `sudo su`:** Выполнение `sudo su` позволяет стать `root`, не зная его пароля — `sudo` выполняет команду `su` от имени `root`, а `root` может переключаться без пароля.

## Практические сценарии

### Примеры правил в `/etc/sudoers`

1. **Права для пользователя:**

    ```
    alice ALL=(ALL) ALL
    ```

    Позволяет `alice` выполнять любые команды от имени любого пользователя на всех хостах.

2. **Предоставление прав группе:**
    Используется префикс `%`. Группа `sudo` или `wheel` (в Debian/Ubuntu и CentOS соответственно) дает полные права `sudo`.

    ```bash
    usermod -aG sudo username # Добавить пользователя в группу sudo
    ```

    В `/etc/sudoers`:

    ```
    %sudo ALL=(ALL:ALL) ALL
    ```

3. **Выполнение команд без пароля (`NOPASSWD`):**
    Удобно для скриптов, но требует осторожности.

    ```
    # Пользователь charlie может перезапускать nginx без пароля
    charlie ALL=(ALL) NOPASSWD: /usr/sbin/service nginx restart, /usr/sbin/service nginx status
    ```

4. **Ограничение и запрет команд:**

    ```
    # Разрешить joe запускать только определенные команды
    joe ALL=(ALL) /usr/sbin/useradd, /usr/sbin/userdel, /usr/bin/passwd

    # Запретить определенные команды (восклицательный знак)
    joe ALL=(ALL) ALL, !/usr/bin/passwd root
    ```

5. **Использование алиасов:**

    ```bash
    # Определение алиасов
    User_Alias    DEVELOPERS = alice, bob, charlie
    Host_Alias   SERVERS = web01, web02, db01
    Runas_Alias  WEBUSER = www-data, nginx
    Cmnd_Alias   WEB_CMDS = /usr/sbin/service nginx *, /usr/bin/htop

    # Применение
    DEVELOPERS SERVERS=(WEBUSER) NOPASSWD: WEB_CMDS
    ```

### Укрепление безопасности

1. **Ограничение доступа к `su` (группа `wheel`)**
    Разрешите использование `su` только членам группы `wheel` через PAM. Подробнее в [PAM (Pluggable Authentication Modules)](../Security/pam_overview.md). Раскомментируйте `auth required pam_wheel.so` в `/etc/pam.d/su`.

2. **Запрет прямого входа для `root` по SSH**
    Установите `PermitRootLogin no` в `/etc/ssh/sshd_config`. Это заставит администраторов использовать свои учетные записи и повышать привилегии через `sudo`, обеспечивая логирование.

3. **Корректные права на файлы SSH**
    Сервер SSH (`sshd`) требует строгих прав на файлы в директории `~/.ssh`. Слишком широкие права приведут к тому, что аутентификация по ключам будет проигнорирована из соображений безопасности, и сервер запросит пароль.

    ```bash
    # Неправильные права (например, 777) на authorized_keys приведут к отказу в аутентификации по ключу.
    # sshd[...]: Authentication refused: bad ownership or modes for file /home/user/.ssh/authorized_keys

    # Рекомендуемые права:
    chmod 700 ~/.ssh
    chmod 600 ~/.ssh/authorized_keys
    ```

4. **Опасность вредоносных алиасов и PATH**
    Не выполняйте неизвестные команды копированием-вставкой. Злоумышленник может замаскировать опасную команду под алиас или разместить вредоносную программу в директории, указанной в начале `PATH` пользователя. Если злоумышленник создаст подмену команды (например, `htop` → `su`) и получит право выполнять `sudo htop`, это может привести к эскалации привилегий. `sudo` требует полный путь к команде и проверяет директории через `secure_path` в `sudoers`.

5. **Опасные команды**
    Избегайте предоставления `sudo` на команды, позволяющие выполнять произвольные команды: `less`, `vim`, `nano`, `emacs`, `git`, `hg` и др. Они имеют механизмы запуска шелла (например, `!command` в `less`, `:!` в `vim`). Используйте опцию `noexec` в `sudoers` для предотвращения запуска подпроцессов.

6. **Использование `sudoedit`**
    Для безопасного редактирования файлов используйте `sudoedit` (или `sudo -e`). Он копирует файл во временный location, открывает в редакторе от имени пользователя, а при сохранении заменяет оригинальный файл. Это предотвращает атаки через возможность запуска команд из редактора.

7. **Привилегии в сетевых ФС (`root_squash`)**
    В NFS `root_squash` предотвращает получение прав `root` на сервере клиентом с правами `root`, понижая их до `nobody`.

8. **Логирование и аудит**
    Все действия через `sudo` логируются в `/var/log/auth.log` (или `/var/log/secure`). Инструмент `sudo replay` позволяет воспроизводить сессии sudo с записью ввода/вывода. Использование `sudo` вместо `root` обеспечивает аудиторский след и индивидуальную ответственность.

9. **Избегайте `NOPASSWD` без необходимости**
    Опция `NOPASSWD` удобна для скриптов, но повышает риск. Применяйте только для конкретных, проверенных команд.

10. **Принцип разрешений, а не запретов**
    Не стройте правила на основе "разрешить все, потом запретить опасные команды". Всегда разрешайте только строго необходимые команды. Используйте алиасы для упрощения управления:
    * `User_Alias`, `Host_Alias`, `Runas_Alias`, `Cmnd_Alias`

### Получение интерактивной оболочки через `sudo`

* `sudo -i [-u <имя_пользователя>]`: Запускает **интерактивную login-оболочку**, полностью симулируя вход пользователя. Окружение будет таким же, как если бы пользователь вошел в систему. Аналогично `su -`.
* `sudo -s [-u <имя_пользователя>]`: Запускает **интерактивную non-login оболочку**, используя `$SHELL`, но без полной симуляции входа.

Без `<имя_пользователя>` используется `root`.

### Ограничение доступа через PolicyKit (Polkit)

Polkit позволяет гибко настраивать права на системные действия, например, запрещать обычным пользователям выключать систему.
Пример (`/etc/polkit-1/localauthority/50-local.d/noshutdown.pkla`):

```ini
[Disable shutdown for users]
Identity=unix-user:*
Action=org.freedesktop.login1.power-off;org.freedesktop.login1.reboot
ResultActive=no
```

### Системный вызов `setuid()` и безопасность

`setuid()` — системный вызов, позволяющий процессу изменять свой эффективный идентификатор пользователя (EUID). Этот механизм, совместно с `setuid`-битом на исполняемых файлах, является основой временного повышения привилегий в Unix-системах. Подробнее о `SUID/SGID` битах: [Права доступа к файлам в Linux](../../Security/Concepts/authentication_vs_authorization.md).

* **`setuid(uid_t uid)`**: Устанавливает RUID, EUID и SUID процесса. Привилегированный процесс может изменить UID на любой, непривилегированный — только на свой RUID или SUID.
* **`seteuid(uid_t euid)`**: Изменяет только эффективный идентификатор пользователя (EUID), позволяя временно получать или сбрасывать привилегии.
* **`setreuid(uid_t ruid, uid_t euid)`**: Позволяет одновременно изменить реальный и эффективный идентификаторы пользователя.

#### Аспекты безопасности `setuid`

1. **`setuid` на скриптах игнорируется:** Ядро Linux игнорирует `setuid`-бит на скриптах (`.sh`, `.py`) для предотвращения эскалации привилегий. Бит работает только на скомпилированных бинарных файлах.
2. **Риск утечки данных через Core Dumps:** Чтобы предотвратить утечку чувствительных данных из `setuid/setgid` программ через core dumps, установите `sudo sysctl -w fs.suid_dumpable=0`. Для постоянного изменения добавьте `fs.suid_dumpable = 0` в `/etc/sysctl.conf`.

### Аудит действий с sudo

Для отслеживания всех действий через sudo используйте auditd:

```bash
# Добавить правило для отслеживания sudo
sudo auditctl -w /usr/bin/sudo -p x -k sudo_execution

# Поиск событий
sudo ausearch -k sudo_execution

# Отчет
sudo aureport -su
```
