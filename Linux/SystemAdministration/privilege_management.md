# Управление привилегиями: su, sudo и Polkit

## Определения

*   **Суперпользователь (`root`)**: Пользователь с UID 0, обладающий неограниченными правами в системе Linux. Его домашний каталог — `/root`.
*   **`su` (Switch User / Substitute User)**: Команда для полного переключения сессии на другого пользователя или `root`.
*   **`sudo` (Superuser Do)**: Команда для выполнения одной или нескольких команд от имени другого пользователя (по умолчанию `root`), без переключения всей сессии.
*   **PolicyKit (Polkit)**: Фреймворк для управления привилегированными действиями для непривилегированных пользователей, часто используется в графических средах.
*   **`setuid()`**, **`seteuid()`**, **`setreuid()`**: Системные вызовы, позволяющие процессу изменять идентификаторы пользователя (EUID, RUID, SUID) для управления привилегиями.

## Базовые концепции

### Принцип наименьших привилегий

Фундаментальный принцип безопасности, требующий, чтобы любой процесс или пользователь имел только те права, которые абсолютно необходимы для выполнения его задач. Запуск сервисов от имени `root`, когда это не требуется, является серьезным риском безопасности.

### `su` (Switch User / Substitute User)

Команда `su` позволяет полностью переключить сессию на другого пользователя. Без указания имени пользователя по умолчанию переключает на `root`.

*   `su <имя_пользователя>`: Переключение на указанного пользователя, требуется пароль целевого пользователя.
*   `su -` или `su -l`: Переключение на `root` с полной инициализацией окружения (переменные, профиль, домашний каталог `root`).

Основной недостаток `su` — необходимость делиться паролем `root`, что является плохой практикой.

### `sudo` (Superuser Do)

Команда `sudo` позволяет выполнить одну или несколько команд от имени другого пользователя (по умолчанию `root`), не переключая всю сессию.

*   **Пароль**: Запрашивает пароль текущего пользователя.
*   **Принцип работы**: `sudo` проверяет `/etc/sudoers` для определения прав текущего пользователя на выполнение команды.
*   **Логирование**: Каждое действие через `sudo` записывается в системный журнал (например, `/var/log/auth.log`), создавая аудиторский след.

Основные команды `sudo`:
*   `sudo <команда>`: Выполнить команду с правами `root`.
*   `sudo -l`: Просмотреть разрешенные команды.
*   `sudo -u <имя_пользователя> <команда>`: Выполнить команду от имени другого пользователя.
*   `sudo !!`: Выполнить последнюю команду с правами `sudo`.

#### Влияние на текущую оболочку

Встроенные команды Bash (например, `cd`, `export`), запущенные через `sudo <команда>`, выполняются в отдельной подоболочке. Изменения, внесенные в этой подоболочке, не сохраняются в родительской оболочке. Для выполнения нескольких команд, влияющих на привилегированную оболочку, используйте `sudo -i` или `sudo -s`.

### Конфигурация `sudo`: файл `/etc/sudoers`

Этот файл определяет права пользователей и групп на использование `sudo`. Редактировать его следует только с помощью команды `visudo` для проверки синтаксиса.

Синтаксис правила:
```
кто     хост=(от_имени_кого) что_делать
```
*   `кто`: Имя пользователя или `%имя_группы`.
*   `хост`: Хост, на котором действует правило (обычно `ALL`).
*   `от_имени_кого`: От имени какого пользователя (обычно `ALL` для `root`).
*   `что_делать`: Команда или список команд.

## Практические сценарии

### Примеры правил в `/etc/sudoers`

1.  **Права для пользователя:**
    ```
    alice ALL=(ALL) ALL
    ```
    Позволяет `alice` выполнять любые команды от имени любого пользователя на всех хостах.

2.  **Предоставление прав группе:**
    Используется префикс `%`. Группа `sudo` или `wheel` (в Debian/Ubuntu и CentOS соответственно) дает полные права `sudo`.
    ```bash
    usermod -aG sudo username # Добавить пользователя в группу sudo
    ```
    В `/etc/sudoers`:
    ```
    %sudo ALL=(ALL:ALL) ALL
    ```

3.  **Выполнение команд без пароля (`NOPASSWD`):**
    Удобно для скриптов, но требует осторожности.
    ```
    # Пользователь charlie может перезапускать nginx без пароля
    charlie ALL=(ALL) NOPASSWD: /usr/sbin/service nginx restart, /usr/sbin/service nginx status
    ```

### Укрепление безопасности

1.  **Ограничение доступа к `su` (группа `wheel`)**
    Разрешите использование `su` только членам группы `wheel` через PAM. Подробнее в [PAM (Pluggable Authentication Modules)](../Security/pam_overview.md). Раскомментируйте `auth required pam_wheel.so` в `/etc/pam.d/su`.

2.  **Запрет прямого входа для `root` по SSH**
    Установите `PermitRootLogin no` в `/etc/ssh/sshd_config`. Это заставит администраторов использовать свои учетные записи и повышать привилегии через `sudo`, обеспечивая логирование.

3.  **Опасность вредоносных алиасов**
    Не выполняйте неизвестные команды копированием-вставкой. Злоумышленник может замаскировать опасную команду под алиас.

4.  **Привилегии в сетевых ФС (`root_squash`)**
    В NFS `root_squash` предотвращает получение прав `root` на сервере клиентом с правами `root`, понижая их до `nobody`.

### Получение интерактивной оболочки через `sudo`

*   `sudo -i [-u <имя_пользователя>]`: Запускает **интерактивную login-оболочку**, полностью симулируя вход пользователя. Окружение будет таким же, как если бы пользователь вошел в систему. Аналогично `su -`.
*   `sudo -s [-u <имя_пользователя>]`: Запускает **интерактивную non-login оболочку**, используя `$SHELL`, но без полной симуляции входа.

Без `<имя_пользователя>` используется `root`.

### Ограничение доступа через PolicyKit (Polkit)

Polkit позволяет гибко настраивать права на системные действия, например, запрещать обычным пользователям выключать систему.
Пример (`/etc/polkit-1/localauthority/50-local.d/noshutdown.pkla`):
```ini
[Disable shutdown for users]
Identity=unix-user:*
Action=org.freedesktop.login1.power-off;org.freedesktop.login1.reboot
ResultActive=no
```

## Дополнительная информация

### Системный вызов `setuid()` и безопасность

`setuid()` — системный вызов, позволяющий процессу изменять свой эффективный идентификатор пользователя (EUID). Этот механизм, совместно с `setuid`-битом на исполняемых файлах, является основой временного повышения привилегий в Unix-системах. Подробнее о `SUID/SGID` битах: [Права доступа к файлам в Linux](../Security/Concepts/Linux_File_Permissions.md#suid-set-user-id).

*   **`setuid(uid_t uid)`**: Устанавливает RUID, EUID и SUID процесса. Привилегированный процесс может изменить UID на любой, непривилегированный — только на свой RUID или SUID.
*   **`seteuid(uid_t euid)`**: Изменяет только эффективный идентификатор пользователя (EUID), позволяя временно получать или сбрасывать привилегии.
*   **`setreuid(uid_t ruid, uid_t euid)`**: Позволяет одновременно изменить реальный и эффективный идентификаторы пользователя.

#### Аспекты безопасности `setuid`

1.  **`setuid` на скриптах игнорируется:** Ядро Linux игнорирует `setuid`-бит на скриптах (`.sh`, `.py`) для предотвращения эскалации привилегий. Бит работает только на скомпилированных бинарных файлах.
2.  **Риск утечки данных через Core Dumps:** Чтобы предотвратить утечку чувствительных данных из `setuid/setgid` программ через core dumps, установите `sudo sysctl -w fs.suid_dumpable=0`. Для постоянного изменения добавьте `fs.suid_dumpable = 0` в `/etc/sysctl.conf`.
