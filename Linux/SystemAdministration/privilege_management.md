# Управление привилегиями: su, sudo и Polkit

## Определения

*   **Суперпользователь (`root`)**: Специальный пользователь с UID 0, обладающий неограниченными правами в системе Linux. Его домашний каталог — `/root` (в отличие от `/home/<username>` у обычных пользователей), что обеспечивает доступ к нему даже при сбое раздела `/home`.
*   **`su` (Switch User / Substitute User)**: Команда для полного переключения сессии на другого пользователя или `root`.
*   **`sudo` (Superuser Do)**: Команда для выполнения одной или нескольких команд от имени другого пользователя (по умолчанию `root`), без переключения всей сессии.
*   **PolicyKit (Polkit)**: Фреймворк для управления привилегированными действиями для непривилегированных пользователей, часто используется в графических средах.
*   **`setuid()`**, **`seteuid()`**, **`setreuid()`**: Системные вызовы, позволяющие процессу изменять свой эффективный, реальный и сохраненный идентификаторы пользователя (EUID, RUID, SUID) для управления привилегиями.

## Базовые концепции

### Принцип наименьших привилегий

Фундаментальный принцип безопасности, который гласит, что любой процесс или пользователь должен иметь только те права, которые абсолютно необходимы для выполнения его задач. **Запуск сервисов от имени `root`, когда это не требуется, является серьёзным риском безопасности.** Если такой сервис будет скомпрометирован, злоумышленник немедленно получит полный контроль над системой.

### `su` (Switch User / Substitute User)

Команда `su` позволяет **полностью переключить сессию** на другого пользователя. Если имя пользователя не указано, по умолчанию предпринимается попытка переключения на `root`.

*   `su <имя_пользователя>`: Переключение на указанного пользователя. Потребуется пароль **целевого пользователя** (того, на кого вы переключаетесь).
*   `su -` или `su -l`: Переключение на пользователя `root` с полной инициализацией окружения (загружаются переменные окружения, профиль и домашний каталог `root`).

Основной недостаток `su` — необходимость делиться паролем `root` со всеми, кому нужны права администратора, что является плохой практикой.

### `sudo` (Superuser Do)

Команда `sudo` позволяет **выполнить одну или несколько команд** от имени другого пользователя (по умолчанию `root`), не переключая всю сессию.

*   **Пароль**: Запрашивает пароль **текущего пользователя**.
*   **Принцип работы**: `sudo` проверяет файл `/etc/sudoers`, чтобы определить, имеет ли **текущий пользователь** право выполнять указанную команду.
*   **Логирование**: Каждое действие, выполненное через `sudo`, записывается в системный журнал (например, `/var/log/auth.log`), создавая полный аудиторский след.

Основные команды `sudo`:
*   `sudo <команда>`: Выполнить команду с правами `root`.
*   `sudo -l`: Просмотреть список разрешенных команд для вашего пользователя.
*   `sudo -u <имя_пользователя> <команда>`: Выполнить команду от имени **любого другого пользователя**.
*   `sudo !!`: Выполнить последнюю введенную команду с правами `sudo`.

#### Влияние на текущую оболочку

Встроенные команды Bash (например, `cd`, `export`, `alias`) или функции оболочки, запущенные через `sudo <команда>`, выполняются в отдельной подоболочке с повышенными привилегиями. Изменения, внесенные этой подоболочкой (например, изменение текущего каталога, установка переменных окружения, создание алиасов), не сохраняются в родительской оболочке после завершения выполнения команды `sudo`.

Например:
*   `sudo cd /root` не изменит текущий каталог в вашей пользовательской оболочке.
*   `sudo export MY_VAR=value` не установит `MY_VAR` в вашей пользовательской оболочке.

Для выполнения нескольких команд, которые должны влиять на состояние привилегированной оболочки, используйте `sudo -i` или `sudo -s` для получения интерактивной оболочки.

### Конфигурация `sudo`: файл `/etc/sudoers`

Этот файл определяет, какие пользователи и группы могут использовать `sudo`. **Его следует редактировать только с помощью команды `visudo`**, которая проверяет синтаксис перед сохранением, чтобы не заблокировать систему.

Синтаксис правила:
```
кто     хост=(от_имени_кого) что_делать
```
*   `кто`: Имя пользователя или `%имя_группы`.
*   `хост`: Хост, на котором действует правило (обычно `ALL`).
*   `от_имени_кого`: От имени какого пользователя можно выполнять команду (обычно `ALL` для `root`).
*   `что_делать`: Команда или список команд.

## Практические сценарии

### Примеры правил в `/etc/sudoers`

1.  **Права для пользователя:**
    ```
    # Пользователь alice может выполнять любые команды от имени root
    alice ALL=(ALL) ALL
    ```
    Позволяет пользователю `alice` выполнять любые команды от имени любого пользователя на всех хостах.

2.  **Предоставление прав группе:**
    Для предоставления прав группе используется префикс `%`. В большинстве современных дистрибутивов (Debian, Ubuntu, CentOS) существует группа `sudo` или `wheel`, членство в которой дает полные права `sudo`. Добавление пользователя в эту группу — стандартный способ предоставления прав администратора.
    ```bash
    # Добавить пользователя в группу sudo (Debian/Ubuntu)
    usermod -aG sudo username
    ```
    Соответствующая строка в `/etc/sudoers`:
    ```
    # Все пользователи в группе sudo могут выполнять любые команды
    %sudo ALL=(ALL:ALL) ALL
    ```

3.  **Выполнение команд без пароля (`NOPASSWD`):**
    Удобно для скриптов, но требует осторожности.
    ```
    # Пользователь charlie может перезапускать nginx без пароля
    charlie ALL=(ALL) NOPASSWD: /usr/sbin/service nginx restart, /usr/sbin/service nginx status
    ```

### Укрепление безопасности

1.  **Ограничение доступа к `su` (группа `wheel`)**
    Чтобы разрешить использование `su` только определенным администраторам, их следует добавить в группу `wheel`. Эта проверка контролируется через Pluggable Authentication Modules (PAM). Подробнее о механизме можно прочитать в документе [**PAM (Pluggable Authentication Modules)**](../Security/pam_overview.md). Затем в файле `/etc/pam.d/su` нужно раскомментировать строку:
    ```
    auth required pam_wheel.so
    ```
    Теперь только члены группы `wheel` смогут переключиться на `root` через `su`.

2.  **Запрет прямого входа для `root` по SSH**
    Это фундаментальная мера безопасности. В файле `/etc/ssh/sshd_config` установите:
    ```
    PermitRootLogin no
    ```
    Это заставит администраторов подключаться под своими учетными записями и повышать привилегии через `sudo`, что обеспечивает логирование действий.

3.  **Опасность вредоносных алиасов**
    Никогда не выполняйте неизвестные команды копированием-вставкой. Злоумышленник может замаскировать опасную команду под алиас, например: `alias sudo='rm -rf /'`.

4.  **Привилегии в сетевых ФС (`root_squash`)**
    В сетевых файловых системах, таких как NFS, `root` на клиенте может получить права `root` на сервере. Механизм `root_squash` предотвращает это, "понижая" права удаленного `root` до непривилегированного пользователя `nobody`.

### Получение интерактивной оболочки через `sudo`

*   `sudo -i [-u <имя_пользователя>]`: Запускает **интерактивную login-оболочку**. Это лучший способ "стать" другим пользователем. Окружение будет таким же, как если бы этот пользователь вошел в систему: загрузятся его `.profile`, `.bashrc`, а текущим каталогом станет его домашний каталог. Аналогично `su -`.
*   `sudo -s [-u <имя_пользователя>]`: Запускает **интерактивную non-login оболочку**. Запускает оболочку, указанную в переменной `SHELL`, но не симулирует полный вход в систему (не считывает `.profile`) и оставляет вас в текущем каталоге.

Если `<имя_пользователя>` не указано, используется `root`.

### Ограничение доступа через PolicyKit (Polkit)

Polkit позволяет гибко настраивать права на системные действия. Например, можно запретить обычным пользователям выключать систему.
Пример (`/etc/polkit-1/localauthority/50-local.d/noshutdown.pkla`):
```ini
[Disable shutdown for users]
Identity=unix-user:*
Action=org.freedesktop.login1.power-off;org.freedesktop.login1.reboot
ResultActive=no
```

## Дополнительная информация

### Системный вызов `setuid()` и безопасность

`setuid()` — это системный вызов, который позволяет процессу изменить свой эффективный идентификатор пользователя (EUID). Этот механизм, вместе с `setuid`-битом на исполняемых файлах, является основой для временного повышения привилегий в Unix-системах. Подробнее о самих `SUID/SGID` битах см. в документе [**Права доступа к файлам в Linux**](../Security/Concepts/Linux_File_Permissions.md#suid-set-user-id).

*   **`setuid(uid_t uid)`**: Устанавливает RUID, EUID и SUID процесса в значение `uid`. Если процесс имеет привилегии `root`, он может изменить свой UID на любой другой. Если процесс непривилегированный, он может изменить свой UID только на свой RUID или SUID.
*   **`seteuid(uid_t euid)`**: Изменяет только эффективный идентификатор пользователя (EUID). Это позволяет процессу временно получить или сбросить привилегии.
*   **`setreuid(uid_t ruid, uid_t euid)`**: Позволяет одновременно изменить реальный и эффективный идентификаторы пользователя.

#### Аспекты безопасности `setuid`

1.  **`setuid` на скриптах игнорируется:** Ядро Linux намеренно игнорирует `setuid`-бит на скриптах (`.sh`, `.py`), чтобы предотвратить простую эскалацию привилегий. Бит работает только на скомпилированных бинарных файлах.

2.  **Риск утечки данных через Core Dumps:** Если `setuid`-программа аварийно завершится, ее core dump (снимок памяти) может содержать чувствительные данные. Чтобы предотвратить это для `setuid/setgid` программ, можно установить параметр ядра:
    ```bash
    # Запретить core dump для setuid/setgid процессов
    sudo sysctl -w fs.suid_dumpable=0
    ```
    Для постоянного изменения добавьте `fs.suid_dumpable = 0` в `/etc/sysctl.conf`.
