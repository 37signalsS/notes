# Управление привилегиями: su, sudo и Polkit

## Определения

- **Суперпользователь (root):** Учетная запись с идентификатором UID (User Identifier) 0, обладающая абсолютными правами в системе. Подробнее: [Определения пользователей](Users/users_definitions.md).
- **su (Switch User):** Утилита для переключения текущей сессии на другого пользователя или root.
- **sudo (Superuser Do):** Программа для выполнения команд от имени другого пользователя (обычно root) с контролем прав через конфигурационный файл.
- **Polkit (PolicyKit):** Системная служба для управления привилегиями непривилегированных процессов, широко используемая в графических средах и для системных действий (выключение, управление сетью).
- **visudo:** Специализированный редактор для безопасного изменения файла `/etc/sudoers` с автоматической проверкой синтаксиса.
- **Интерактивная оболочка входа (Login Shell):** Оболочка, которая считывает профили конфигурации (`/etc/profile`, `~/.bash_profile`) при запуске, полностью инициализируя окружение пользователя.

## Основные концепции

### Принцип наименьших привилегий

Фундаментальное правило информационной безопасности: субъект (пользователь или процесс) должен обладать только тем набором прав, который минимально необходим для выполнения текущей задачи. Использование `sudo` вместо постоянной работы под учетной записью `root` является практической реализацией этого принципа.

### Механизмы повышения прав

1. **su (Switch User):**
   - Требует пароль **целевого** пользователя (обычно root).
   - По умолчанию не меняет переменные окружения. Использование `su -` (login shell) рекомендуется для полной инициализации окружения.
   - **Недостаток:** Необходимость передачи пароля администратора другим пользователям.

2. **sudo (Superuser Do):**
   - Требует пароль **текущего** пользователя.
   - Позволяет гранулярно настраивать разрешения (кто, где и какие команды может запускать).
   - Все действия через `sudo` автоматически логируются, создавая аудиторский след.

### Конфигурация sudoers

Файл `/etc/sudoers` определяет политики доступа. Для обеспечения модульности и безопасности рекомендуется использовать директорию `/etc/sudoers.d/`.

**Синтаксис правил:**
`Субъект Хост=(Запуск_от_имени) Команды`

Пример: `%wheel ALL=(ALL) ALL` (Группа wheel может выполнять любые команды от имени любого пользователя на всех хостах).

## Практические сценарии

### 1. Запись в защищённые файлы: sudo tee vs sudo bash -c

При попытке дописать данные в файл, доступный только root, распространённая ошибка — использование `sudo echo ... >> file`. Этот вариант не сработает, так как перенаправление вывода (`>>`) выполняется от имени текущего пользователя, а `sudo` применяется только к `echo`.

**Правильные варианты:**

```bash
# Через tee (запись из stdin от root)
echo "new line" | sudo tee -a /etc/some/file

# Через sudo bash -c (вся строка выполняется от root)
sudo bash -c 'echo "new line" >> /etc/some/file'
```

**Разница:** `tee` добавляет вывод в файл от root, а `sudo bash -c` запускает целую оболочку с правами root, внутри которой работает и перенаправление.

### 2. Безопасное редактирование прав

Всегда используйте `visudo` для предотвращения ошибок, которые могут заблокировать доступ к системе.

```bash
# Редактирование основного файла
sudo visudo

# Создание модульного правила для конкретной задачи
sudo visudo -f /etc/sudoers.d/web-admin
# Содержимое: webuser ALL=(root) NOPASSWD: /usr/sbin/nginx -t, /usr/bin/systemctl reload nginx
```

### 3. Использование псевдонимов (Aliases)

Для упрощения управления большим количеством правил используются псевдонимы:

```text
# Определение групп команд и пользователей
User_Alias    ADMINS = alice, bob
Cmnd_Alias   NET_TOOLS = /usr/sbin/ip, /usr/sbin/tcpdump

# Применение правила
ADMINS ALL=(root) NET_TOOLS
```

### 4. Укрепление безопасности (Hardening)

- **Ограничение su:** Разрешите использование `su` только определенным группам (например, `wheel`) через модули PAM (Pluggable Authentication Modules). Подробнее: [Обзор PAM](../Security/pam_overview.md).
- **Запрет root в SSH:** Отключите прямой вход `PermitRootLogin no` в конфигурации SSH, заставляя использовать `sudo`.
- **Использование sudoedit вместо sudo vim:** Запуск полноценного редактора через `sudo` (например `sudo vim /etc/file`) — антипаттерн. Редактор работает целиком от root, а из vim можно выйти в оболочку (`:shell`) или выполнить произвольную команду (`:!команда`), получив root-shell в обход ограничений sudoers. `sudoedit` (она же `sudo -e`) решает проблему:

  1. Копирует файл во временную директорию
  2. Открывает **копию** от имени текущего пользователя в его редакторе
  3. После сохранения копирует результат обратно от root

  Редактор выбирается из переменных окружения (порядок): `SUDO_EDITOR` → `VISUAL` → `EDITOR`.
  
  Примеры:
  ```bash
  sudoedit /etc/nginx/nginx.conf
  sudo -e /etc/hosts                 # то же самое
  export SUDO_EDITOR=nano && sudoedit /etc/fstab
  ```

  В sudoers можно разрешить `sudoedit` и запретить `sudo vim`:
  ```
  user ALL=(ALL) sudoedit /etc/nginx/nginx.conf
  user ALL=(ALL) !sudo vim /etc/nginx/nginx.conf
  ```

  Проверка разрешённых команд: `sudo -l`

### 5. Опасные команды (GTFOBins)

Избегайте предоставления прав `sudo` на утилиты, имеющие встроенные функции выполнения команд (например, `vim`, `less`, `find`, `git`). Злоумышленник может использовать их для получения полноценной оболочки root.
Методы эксплуатации собраны в проекте [GTFOBins](../../Security/Tools/gtfobins.md).

## Дополнительная информация

### Системные механизмы

- **SUID/SGID:** Специальные биты прав доступа, позволяющие запускать файлы с правами владельца. Подробнее: [Специальные права доступа](../Security/Concepts/File_Permissions/special_permissions.md).
- **Аудит:** Для детального отслеживания действий пользователей рекомендуется настройка подсистемы аудита ядра. Подробнее: [auditd — аудит событий](./Logging/auditd.md).

### Сравнение оболочек через sudo

- `sudo -i`: Запуск интерактивной оболочки входа (login shell).
- `sudo -s`: Запуск оболочки без полной инициализации профилей.
- `sudo su -`: Устаревший, но часто встречающийся метод получения root-оболочки.
