# `systemd-journald`: Централизованный сбор логов

## Определения

* **`systemd-journald`** — системная служба, централизованно собирающая логи от всех компонентов ОС (ядро, службы, приложения, stdout/stderr) в структурированном бинарном формате.
* **`journalctl`** — утилита для просмотра и анализа логов, собранных `systemd-journald`. **Подробное описание утилиты `journalctl` находится в [journalctl.md](../../Diagnostics/Logging/journalctl.md).**

## Основные концепции

### Архитектура и принцип работы

`systemd-journald` работает как демон, запускаемый systemd. Основные компоненты:

1. **Сбор логов:**
   * Перехватывает сообщения ядра через `kmsg`
   * Получает логи от служб systemd через Unix-сокеты
   * Собирает stdout/stderr сервисов, запущенных через systemd
   * Принимает сообщения через `syslog`-совместимый сокет (если включен)

2. **Структурированное хранение:**
   * Каждое сообщение — набор пар `ключ=значение`
   * Автоматически добавляемые поля: `_PID`, `_UID`, `_COMM`, `_EXE`, `CODE_FILE`, `CODE_LINE`, `MESSAGE_ID`
   * Индексация по времени, PID, UID, приоритету для быстрого поиска

3. **Формат хранения:**
   * Бинарные файлы в `/run/log/journal/` (volatile) или `/var/log/journal/` (persistent)
   * Файлы называются по UUID машины: `machine-id.journal`
   * Автоматическая ротация при достижении лимитов

### Поля журнала (metadata fields)

Каждое сообщение в журнале содержит стандартные поля:

| Поле | Описание |
| :--- | :--- |
| `MESSAGE` | Текст сообщения |
| `PRIORITY` | Уровень приоритета (0-7, см. syslog severities) |
| `_PID` | ID процесса, отправившего сообщение |
| `_UID` | ID пользователя, от имени которого запущен процесс |
| `_COMM` | Имя исполняемого файла (короткое) |
| `_EXE` | Полный путь к исполняемому файлу |
| `_SYSTEMD_UNIT` | Имя systemd-юнита (сервиса) |
| `_HOSTNAME` | Имя хоста |
| `_MACHINE_ID` | UUID машины |
| `_BOOT_ID` | UUID текущей загрузки |
| `CODE_FILE`, `CODE_LINE`, `CODE_FUNC` | Позиция в исходном коде (если доступно) |
| `MESSAGE_ID` | Уникальный идентификатор типа сообщения |

Полный список доступных полей: `journalctl --fields`

### Уровни приоритета (syslog severities)

Стандартные уровни приоритета (RFC 5424):

| Код | Уровень | Описание |
| :--- | :--- | :--- |
| 0 | `emerg` | Система неработоспособна |
| 1 | `alert` | Требуется немедленное действие |
| 2 | `crit` | Критические условия |
| 3 | `err` | Ошибки |
| 4 | `warning` | Предупреждения |
| 5 | `notice` | Нормальные, но значимые события |
| 6 | `info` | Информационные сообщения |
| 7 | `debug` | Отладочные сообщения |

### Хранение логов

1. **Энергозависимое (Volatile):** По умолчанию логи хранятся в `/run/log/journal`. Директория монтируется как `tmpfs` и очищается при перезагрузке.
2. **Постоянное (Persistent):** При создании директории `/var/log/journal`, `journald` автоматически начинает использовать её для постоянного хранения.

**Проверка режима хранения:**

```bash
# Проверить текущий режим
ls -la /var/log/journal/ 2>/dev/null && echo "Persistent" || echo "Volatile"

# Проверить размер журнала
journalctl --disk-usage
```

## Практические сценарии

### Настройка постоянного хранения

Чтобы логи сохранялись после перезагрузки:

```bash
# 1. Создание директории для постоянного хранения
sudo mkdir -p /var/log/journal

# 2. Установка правильных прав (группа systemd-journal)
sudo chown root:systemd-journal /var/log/journal
sudo chmod 2755 /var/log/journal

# 3. Перезапуск службы для применения изменений
sudo systemctl restart systemd-journald
```

**Проверка:**

```bash
# Убедиться, что логи записываются в persistent-директорию
ls -la /var/log/journal/

# Проверить размер журнала
journalctl --disk-usage
```

### Ограничение размера журнала

Настройка в `/etc/systemd/journald.conf` (секция `[Journal]`):

```ini
[Journal]
# Максимальный общий размер журнала (старые логи удаляются при превышении)
SystemMaxUse=4G

# Минимальный объем свободного места на диске
SystemKeepFree=15%

# Максимальный размер одного файла журнала
SystemMaxFileSize=200M

# Режим хранения: auto, persistent, volatile, none
Storage=auto

# Ограничение скорости записи (защита от интенсивного логирования)
RateLimitIntervalSec=5s
RateLimitBurst=10000
```

**Применение настроек:**

```bash
sudo systemctl restart systemd-journald
```

**RateLimiting:** параметры `RateLimitIntervalSec` и `RateLimitBurst` защищают систему от интенсивного логирования одним сервисом. Превышающие лимит сообщения отбрасываются.

### Очистка журнала (vacuum)

**Ручная очистка через `journalctl`:**

```bash
# Оставить только последние 500 МБ
sudo journalctl --vacuum-size=500M

# Оставить логи только за последние 2 дня
sudo journalctl --vacuum-time=2d

# Оставить только 5 последних файлов журнала
sudo journalctl --vacuum-files=5
```

**Автоматическая очистка через `systemd-tmpfiles`:**

Создать файл `/etc/tmpfiles.d/systemd-journald.conf`:

```conf
# Тип  Путь                     Режим Владелец Группа Возраст
R    /var/log/journal          -      -       -       -
e    /var/log/journal          -      -       -       14d
```

Параметр `Age` (14d) указывает, что файлы старше 14 дней будут удаляться при запуске `systemd-tmpfiles --clean`.

### Интеграция с syslog (совместимость)

`journald` может принимать сообщения через syslog-сокет:

```ini
# В /etc/systemd/journald.conf
[Journal]
# Включить прием syslog-сообщений
ForwardToSyslog=yes
```

Это позволяет legacy-приложениям, пишущим в syslog, работать без изменений.

## Дополнительная информация

### Безопасность и целостность логов

* **Защита от подделки:** Бинарный формат усложняет ручное редактирование логов.
* **FSS (Forward Secure Sealing):** Криптографическое подписывание логов для обнаружения изменений (требует настройки).
* **ACL (Access Control List):** Доступ к логам ограничен пользователями группы `systemd-journal` и `wheel`.

```bash
# Проверить права доступа к файлам журнала
ls -la /var/log/journal/*/
```

### Производительность

* **Асинхронная запись:** По умолчанию используется асинхронная запись для минимизации влияния на производительность.
* **Синхронная запись:** Для критически важных систем можно включить синхронную запись:

```ini
# В /etc/systemd/journald.conf
[Journal]
SyncIntervalSec=5m  # Принудительная синхронизация каждые 5 минут
```

### Типичные проблемы

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| Логи не сохраняются после перезагрузки | Не настроен persistent storage | Создать `/var/log/journal` (см. выше) |
| Журнал занимает слишком много места | Не настроены лимиты | Настроить `SystemMaxUse` в `journald.conf` |
| Сервис не пишет в journal | Сервис настроен на запись в файл | Проверить конфигурацию сервиса или настроить `StandardOutput=journal` в unit-файле |
| `systemd-journald` потребляет много CPU | Интенсивное логирование от приложения | Найти источник: `journalctl -f`, настроить уровень логирования приложения |
| Сообщения отбрасываются | Превышен RateLimit | Настроить `RateLimitIntervalSec` и `RateLimitBurst` |
| Файлы журнала повреждены | Внезапное выключение, сбой ФС | Удалить поврежденный файл в `/var/log/journal/`, служба создаст новый |

### Интеграция с другими системами

* **rsyslog:** Модуль `imjournal` позволяет `rsyslog` забирать сообщения из `journald` для фильтрации и пересылки. Настройка в [rsyslog.md](./rsyslog.md).
* **Fluentd/Fluent Bit:** Агенты для сбора и пересылки логов в централизованные системы (Elasticsearch, Loki).
* **systemd-coredump:** Компонент для обработки дампов памяти (coredump), интегрирован с `journald`.
