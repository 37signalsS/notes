# Анализ ошибок и сбоев (Error and Crash Analysis)

## Определения

**Анализ сбоев (Crash Analysis)** — процесс диагностики причин аварийного завершения программного обеспечения или операционной системы. В отличие от стандартного логирования (которое фиксирует штатные события и предупреждения), этот процесс сфокусирован на критических инцидентах, приводящих к полной остановке процесса (SIGSEGV, SIGABRT) или всей системы (Kernel Panic).

**Основные типы сбоев:**

| Тип сбоя | Суть проблемы | Механизм сохранения данных | SSoT-документ |
| :--- | :--- | :--- | :--- |
| **Application Crash** | Процесс выполнил недопустимую операцию (например, обращение к чужой памяти — Segmentation Fault) | Coredump (дамп памяти процесса) | [Отладка через Coredump](../../Core/processes/Troubleshooting/debugging.md#анализ-сбоев-coredump) |
| **OOM (Out Of Memory)** | Ядро принудительно убило процесс из-за критической нехватки RAM (SIGKILL) | Системный лог (dmesg / journald) | [OOM Killer](../../Core/processes/oom_killer_mechanism.md) |
| **Kernel Panic** | Критическая ошибка в самом ядре (баг драйвера, отказ оборудования). Система заморожена | kdump (дамп памяти ядра) | [Паника ядра](../../Core/kernel/kernel_panic.md) |

## Базовые концепции

### Сбои пространства пользователя (User Space Crashes)

Происходят, когда приложение нарушает правила изоляции памяти или вызывает функцию `abort()`. Ядро операционной системы перехватывает такое нарушение, отправляет процессу фатальный сигнал (чаще всего `SIGSEGV` - Signal Segmentation Violation) и завершает его.

**Современный подход к сбору дампов (`systemd-coredump`):**
В современных дистрибутивах (на базе systemd) обработка дампов централизована. При крахе приложения:
1. Ядро передает дамп памяти утилите `systemd-coredump`.
2. Утилита сохраняет сжатый дамп в `/var/lib/systemd/coredump/`.
3. Утилита записывает метаданные о сбое в бинарный журнал `journald`.
4. Администратор использует команду `coredumpctl` для поиска и извлечения дампа.

### Сбои пространства ядра (Kernel Space Crashes)

В отличие от пользовательских процессов, ядро не изолировано. Если драйвер устройства или модуль ядра обратится к неверной памяти, ядро не может просто "убить" этот модуль. Возникает состояние **Kernel Panic**, и система немедленно останавливается для предотвращения повреждения данных.

**Механизм `kdump` (Kernel Crash Dump):**
Чтобы сохранить состояние упавшего ядра для последующего анализа, используется `kdump`. Он резервирует небольшой участок памяти для второго (аварийного) ядра. При панике основное ядро передает управление аварийному ядру через `kexec`. Аварийное ядро загружается, копирует содержимое памяти упавшего ядра (создавая файл `vmcore` в `/var/crash/`) и перезагружает сервер.

## Практические сценарии

### Быстрая диагностика причин сбоя сервера

Если сервер внезапно перезагрузился или приложение перестало работать, используйте этот алгоритм для первичной локализации проблемы.

```bash
# 1. Проверить системный лог на наличие критических ошибок перед сбоем
journalctl -p err -b -1  # Логи за предыдущую (-1) загрузку

# 2. Найти следы работы OOM Killer (самая частая причина "исчезновения" процессов)
journalctl -k | grep -iE "oom|killed process"

# 3. Проверить наличие сохраненных дампов упавших пользовательских процессов
coredumpctl list

# 4. Проверить наличие дампов памяти упавшего ядра (доказательство Kernel Panic)
ls -lh /var/crash/
```

### Анализ краха приложения (Application Crash)

1. **Идентификация сбоя:**
   ```bash
   coredumpctl list
   # Вывод покажет время, PID, пользователя, сигнал (напр. SIGSEGV) и исполняемый файл.
   ```

2. **Получение деталей из журнала (backtrace без отладчика):**
   ```bash
   coredumpctl info <PID>
   ```

3. **Глубокий анализ в отладчике GDB:**
   ```bash
   # Команда автоматически распакует дамп и загрузит его в gdb
   coredumpctl debug <PID>
   
   # Внутри gdb выполните команду bt (backtrace) для просмотра стека вызовов
   (gdb) bt
   ```

Подробное руководство по отладке: [Анализ сбоев: Coredump](../../Core/processes/Troubleshooting/debugging.md#анализ-сбоев-coredump)

### Анализ паники ядра (Kernel Panic)

1. **Анализ логов предшествующих сбою:**
   Стандартный системный лог (`journald`) может не успеть записать саму ошибку паники, так как ядро останавливается мгновенно. Однако стоит проверить события за секунду до краха.
   ```bash
   journalctl -k -b -1
   ```

2. **Анализ дампа ядра (kdump):**
   Если файлы в `/var/crash/` присутствуют (например, `vmcore`), их анализируют специальной утилитой `crash` в связке с отладочными символами ядра (`kernel-debuginfo`).
   ```bash
   # Запуск интерактивного анализатора
   crash /usr/lib/debug/lib/modules/$(uname -r)/vmlinux /var/crash/127.0.0.1-.../vmcore
   
   # Внутри crash выполните команды:
   crash> log     # Вывести буфер сообщений ядра (dmesg) на момент паники
   crash> bt      # Показать стек вызовов процесса, вызвавшего панику
   ```

Подробное руководство: [Паника ядра: анализ и отладка](../../Core/kernel/kernel_panic.md)

## Дополнительная информация

### Автоматизированные системы отчетов (Automated Bug Reporting)

В enterprise-дистрибутивах поверх базовых механизмов (coredump/kdump) работают системы автоматического сбора логов, дампов памяти и отправки отчетов разработчикам ОС.

* **ABRT (Automatic Bug Reporting Tool):** Стандарт для RHEL, CentOS, Fedora. Перехватывает сбои C/C++, Python, паники ядра. Может автоматически открывать тикеты в Bugzilla. Управление через CLI `abrt-cli`.
* **Apport:** Стандарт для Ubuntu. Собирает информацию о сбоях и предлагает пользователю отправить отчет (через всплывающее окно в Desktop или команду `ubuntu-bug` на сервере). Отчеты сохраняются в `/var/crash/` с расширением `.crash`.
