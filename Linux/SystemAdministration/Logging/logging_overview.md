# Обзор системы логирования в Linux

## Определения

**Системные журналы (логи)** — структурированные или текстовые файлы и базы данных, в которые записываются системные сообщения, ошибки и события аудита. Анализ логов — ключевой навык для диагностики проблем, отслеживания производительности и расследования инцидентов безопасности.

**Архитектура логирования в современных Linux:**

| Компонент | Назначение | Основной документ |
| :--- | :--- | :--- |
| `systemd-journald` | **Ядро современного логирования.** Централизованный сбор логов в бинарном формате от всех компонентов системы. | [journald](./journald.md) |
| `journalctl` | Утилита командной строки для просмотра, фильтрации и анализа логов `journald`. | [journalctl](../../Diagnostics/journalctl/journalctl_overview.md) |
| `rsyslog` | Традиционный демон для фильтрации, текстовой обработки и пересылки логов по сети. | [rsyslog](./rsyslog.md) |
| `auditd` | Отдельная подсистема для строгого аудита событий безопасности на уровне ядра. | [auditd](./auditd.md) |
| `logrotate` | Автоматизация ротации, сжатия и удаления старых текстовых логов. | [logrotate](#ротация-логов) |

**Схема взаимодействия:** Ядро и службы отправляют данные в `journald`. Если установлен `rsyslog`, он забирает поток из `journald` для создания текстовых файлов в `/var/log/`. `logrotate` периодически сжимает и очищает эти текстовые файлы.

## Базовые концепции

### Расположение логов в Linux

В системах на базе `systemd` логи находятся в двух основных хранилищах: бинарном (управляется journald) и текстовом (управляется rsyslog/приложениями).

| Расположение | Описание |
| :--- | :--- |
| `/var/log/journal/` | Постоянные (persistent) журналы `systemd-journald` — бинарные файлы. |
| `/run/log/journal/` | Временные (volatile) журналы `systemd-journald` — очищаются при перезагрузке (используется, если `/var/log/journal/` не создан). |
| `/var/log/syslog` (Debian/Ubuntu) или `/var/log/messages` (RHEL/CentOS) | Главный системный лог в текстовом формате (копия данных journald от rsyslog). |
| `/var/log/auth.log` (Debian/Ubuntu) или `/var/log/secure` (RHEL/CentOS) | События аутентификации (SSH — Secure Shell, sudo — Substitute User and do, PAM). |
| `/var/log/kern.log` | Сообщения ядра (дублируются из `dmesg`). |
| `/var/log/dmesg` | Сообщения ядра, сгенерированные при загрузке системы. |
| `/var/log/audit/audit.log` | Журнал аудита безопасности (`auditd`). |
| `/var/log/nginx/`, `/var/log/postgresql/` | Логи конкретных приложений (пишут файлы самостоятельно, минуя syslog). |
| `/var/log/wtmp`, `/var/run/utmp`, `/var/log/btmp` | Журналы сессий и входов пользователей (специальные двоичные файлы). |

### Форматы журналов

Эволюция логирования движется от неструктурированного текста к структурированным машиночитаемым форматам.

| Формат | Где используется | Описание |
| :--- | :--- | :--- |
| **Бинарный журнал (structured binary)** | `systemd-journald` | Каждая запись — набор пар `ключ=значение` с метаданными (PID, UID, юнит, приоритет, время). База индексирована для быстрого поиска. |
| **Syslog (RFC 5424 / RFC 3164)** | `rsyslog`, legacy-инфраструктура | Текстовый формат: `<приоритет>дата хост процесс[PID]: сообщение`. Требует сложного парсинга регулярными выражениями. |
| **Plain text (произвольный)** | Приложения (nginx, apache, db) | Каждая строка — отдельная запись. Формат задается приложением (например, Common Log Format). |
| **JSON (структурированный)** | Современные Cloud-Native приложения, Docker | `{"timestamp":"...", "level":"info", "message":"..."}`. Идеален для автоматизации и систем вроде ELK/Loki. |
| **Узкоспециализированный двоичный** | `wtmp`, `utmp`, `btmp` | Не читаемы текстовыми редакторами, требуют специальных утилит (`last`, `who`). |

> **Best Practice (Лучшая практика):** Для современных (Cloud-Native) систем рекомендуется настраивать вывод всех приложений в `stdout/stderr` в формате **JSON**. Это позволяет Docker/Kubernetes или systemd собирать логи как структурированные данные без необходимости писать парсеры.

### Инструменты для просмотра логов

Выбор инструмента зависит от источника лога.

| Инструмент | Назначение | Документация |
| :--- | :--- | :--- |
| **`journalctl`** | Основной инструмент современного администратора. Просмотр бинарных логов systemd с мощной фильтрацией. | [journalctl](../../Diagnostics/journalctl/journalctl_overview.md) |
| **`dmesg`** | Чтение кольцевого буфера ядра (ring buffer). Критично для диагностики аппаратных проблем и сбоев драйверов. | [dmesg](../../Diagnostics/Kernel/dmesg/index.md) |
| **`tail -f` / `less`** | Традиционный просмотр текстовых файлов (например, логов Nginx) в реальном времени или с постраничной навигацией. | [tac](../../Shell/tac.md), `less` |
| **`grep` / `zgrep`** | Поиск текста по паттернам в текущих и архивированных (сжатых) логах. | [grep](../../Shell/grep.md) |
| **`last` / `who` / `w`** | Анализ специальных двоичных файлов входов пользователей (`wtmp`, `utmp`). | См. ниже |
| **`ausearch`** | Фильтрация событий подсистемы аудита ядра. | [auditd](./auditd.md) |

### Категории журналов безопасности

В контексте безопасности Linux журналы делятся на три основные категории:

| Категория | Файлы/Источники | Назначение | Инструменты просмотра |
| :--- | :--- | :--- | :--- |
| **Журналы входа пользователей** | `/var/log/wtmp`, `/var/run/utmp`, `/var/log/btmp` | История успешных и неудачных входов, текущие сессии. | `last`, `who`, `lastb` |
| **Журналы событий аутентификации** | `/var/log/auth.log`, `/var/log/secure`, `journalctl -t sshd` | Детальный аудит SSH, sudo, конфигурации PAM. | `journalctl`, `grep` |
| **Системный аудит ядра** | `/var/log/audit/audit.log` | Глубокий мониторинг системных вызовов и доступа к файлам. | `ausearch`, `aureport` |

#### Анализ журналов входа (wtmp/utmp/btmp)

| Команда | Источник | Назначение | Пример вывода |
| :--- | :--- | :--- | :--- |
| `last` | `/var/log/wtmp` | История успешных входов и перезагрузок | `user pts/0 192.168.1.10 Mon Jan 01 10:00 still logged in` |
| `lastb` | `/var/log/btmp` | История **неудачных** попыток входа (требует root) | `user ssh:notty 192.168.1.11 Mon Jan 01 11:00 - 11:00 (00:00)` |
| `who` / `w` | `/var/run/utmp` | Кто сейчас в системе (и чем занят - для `w`) | `user pts/0 2026-01-01 10:00 (192.168.1.10)` |
| `lastlog` | `/var/log/lastlog`| Время последнего входа каждого пользователя | `root pts/0 192.168.1.10 Mon Jan 01 10:00:00 +0000 2026` |

**Примеры анализа событий аутентификации:**

```bash
# Поиск успешных входов по SSH через journalctl (предпочтительный современный метод)
journalctl -u ssh -g "Accepted"

# Поиск неудачных попыток sudo в классических логах
grep sudo /var/log/auth.log | grep failed

# Поиск подозрительной активности по ключевым словам
grep -iE "failed|invalid|error" /var/log/auth.log
```

### Централизованное логирование

**Проблемы локального хранения логов:**
- **Исчерпание ресурсов:** Логи могут заполнить весь диск (ошибка "No space left on device").
- **Уязвимость:** При взломе сервера атакующий первым делом удаляет локальные логи (`rm -rf /var/log/*`), скрывая следы.
- **Сложность анализа:** Невозможно искать ошибки одновременно на 100+ серверах без единого интерфейса.

**Современные решения (Observability Stack):**
1. **Агенты сбора логов (Shippers):** Устанавливаются на серверах. Парсят файлы, собирают journald и отправляют по сети. Примеры: **Vector** (написан на Rust, очень быстрый), **Fluent Bit**, **Promtail** (для Loki).
2. **Системы хранения и поиска:**
   - **ELK Stack (Elasticsearch, Logstash, Kibana):** Тяжеловесный стандарт индустрии, индексирует весь текст лога.
   - **Loki:** Легковесный (индексирует только метаданные-лейблы, как Prometheus), интегрирован с Grafana. Подробнее в [Observability and Monitoring](../../../Concepts/Observability_and_Monitoring/observability_definitions.md).

### Ротация логов (`logrotate`)

Утилита **`logrotate`** предотвращает переполнение диска текстовыми логами. Она переименовывает старые файлы, сжимает их (`.gz`), удаляет устаревшие копии и дает команду приложению начать писать в новый файл.

- **Запуск:** Утилита работает не как демон. Она запускается ежедневно через cron (`/etc/cron.daily/logrotate`) или systemd-таймер (`logrotate.timer`).
- **Конфигурация:** Глобальные настройки в `/etc/logrotate.conf`, специфичные для сервисов — в `/etc/logrotate.d/`.

#### Стратегии ротации (Критически важно понимать разницу)

| Стратегия | Механизм действия | Плюсы | Минусы и ограничения |
| :--- | :--- | :--- | :--- |
| **`postrotate` (с SIGHUP)** | `mv app.log app.log.1` → Отправка сигнала сервису (переоткрыть файл) | Без потерь данных. Самый надежный метод. | Сервис **обязан** уметь обрабатывать сигнал (например, `kill -USR1 nginx`). |
| **`copytruncate`** | Копирование содержимого файла в `app.log.1` → Обнуление `app.log` (`> app.log`) | Не требует перезапуска сервиса. Дескриптор файла не меняется. | **Возможна потеря строк**, записанных в долю секунды между копированием и обнулением. |

> **Проблема "Удаленных открытых файлов":** Если `logrotate` использует простую замену файлов (без `copytruncate` и без сигнала SIGHUP), приложение продолжит писать в файловый дескриптор удаленного файла. Место на диске не освободится, `df` покажет 100% заполнения, а `du` не найдет больших файлов. Подробнее: [Диагностика дискового пространства](../../Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md#механизм-удалённых-открытых-файлов).

## Практические сценарии

### Отправка тестовых сообщений: `logger`

```bash
# Базовое сообщение
logger "Тестовое сообщение"

# С указанием facility и priority
logger -t myscript -p local0.info "Скрипт выполнен успешно"

# На удаленный сервер
logger -n 192.168.1.100 -p local0.info "Удаленное сообщение"
```

**Параметры:**

- `-t tag` — тег сообщения (имя скрипта/процесса)
- `-p facility.priority` — категория и уровень (например, `local0.info`)
- `-n server` — отправка на удаленный хост

### Анализ логов: базовые утилиты

| Утилита | Назначение |
| :--- | :--- |
| `tail -f` | Просмотр в реальном времени |
| `tac` | Вывод файла задом наперёд (свежие записи сверху) |
| `less` | Поиск (`/`, `?`), фильтрация (`&`) |
| `grep` | Поиск по шаблону |
| `zcat` / `zgrep` | Работа со сжатыми логами (`.gz`) |

### Методология диагностики проблем (Порядок действий)

В современных системах диагностика всегда должна начинаться с инструментов `systemd`, так как они предоставляют единый интерфейс.

| Категория проблемы | Рекомендуемый порядок действий |
| :--- | :--- |
| **Служба (юнит) не запускается** | 1. `systemctl status <сервис>` (быстрый статус)<br>2. `journalctl -u <сервис> -b` (полный лог за текущую загрузку)<br>3. Чтение локального файла лога приложения в `/var/log/<app>/` |
| **Отказ в аутентификации (SSH, sudo)** | 1. `journalctl -t sshd` или `journalctl -t sudo`<br>2. `grep failed /var/log/auth.log`<br>3. `ausearch -m USER_LOGIN` (если включен auditd) |
| **Сбои железа или драйверов (Ядро)** | 1. `dmesg -H` или `dmesg --level=err,warn` (сообщения кольцевого буфера)<br>2. `journalctl -k -b` (логи ядра за текущую загрузку) |
| **Закончилось место на диске** | 1. `journalctl --disk-usage` (проверка размера journald)<br>2. [Очистка журнала journalctl](../../Diagnostics/journalctl/journalctl_management.md)<br>3. `du -sh /var/log/*` (поиск пухлых файлов)<br>4. Проверка конфигов `logrotate` |
| **Перезагрузки и Kernel Panic** | 1. `journalctl --list-boots` (поиск предыдущих загрузок)<br>2. `journalctl -b -1 -p crit` (логи прошлой загрузки перед падением)<br>3. Анализ дампов памяти (kdump) |

## Дополнительная информация

### Пример конфигурации `logrotate`

**Пример для веб-сервера (требует SIGHUP):**

```conf
/var/log/nginx/*.log {
    daily                   # Проверять каждый день
    missingok               # Не выдавать ошибку, если файла нет
    rotate 14               # Хранить 14 старых копий
    compress                # Сжимать в .gz
    delaycompress           # Не сжимать самый свежий архив (оставить как .log.1)
    notifempty              # Не ротировать, если лог пуст
    create 0640 nginx adm   # Создать новый файл с такими правами
    sharedscripts           # Выполнить скрипт 1 раз, а не для каждого файла
    postrotate
        [ -f /var/run/nginx.pid ] && kill -USR1 `cat /var/run/nginx.pid`
    endscript
}
```

**Пример для приложения (использует copytruncate):**

```conf
/var/log/myapp/*.log {
    daily
    rotate 7
    maxsize 100M            # Ротировать принудительно, если размер > 100МБ
    compress
    copytruncate            # Копировать и обнулять (если app не понимает SIGHUP)
    missingok
}
```

**Команды управления `logrotate`:**

```bash
# Проверить конфиг без реальных изменений (dry-run)
logrotate -d /etc/logrotate.d/myapp

# Принудительно запустить ротацию (игнорируя расписание daily/weekly)
sudo logrotate -f /etc/logrotate.d/myapp
```

### Принудительная синхронизация: `sync`

```bash
sync  # Запись буферов из RAM на диск
```
Команда полезна перед жестким выключением (hard reset) или при подозрении на панику ядра, чтобы гарантировать запись последних логов на накопитель.
