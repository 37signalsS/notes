# Определения пользователей и групп в Linux

## Определения

- **Пользователь (User)** — уникальная учетная запись, идентифицирующая субъект (человека, системный процесс или сетевой сервис) для разграничения прав доступа и аудита действий.
- **UID (User Identifier)** — уникальный числовой идентификатор, используемый ядром Linux для проверки прав доступа.
    - **Природа UID:** Внутри ядра пользователь — это всегда число (обычно 32-битное, что позволяет иметь до 4.2 млрд идентификаторов). Текстовые имена существуют исключительно для удобства человека.
    - **Связь с ФС:** В файловых системах (ext4, XFS) в метаданных файла (Inode) хранится именно UID владельца, а не его имя.
    - **UID 0:** Специальный идентификатор суперпользователя. Ядро проверяет именно равенство UID нулю для обхода стандартных проверок прав доступа. Любой пользователь с UID 0 обладает абсолютными полномочиями.
- **Группа (Group)** — логическое объединение пользователей для упрощения управления коллективным доступом к ресурсам (файлам, устройствам, системным вызовам).
- **GID (Group Identifier)** — числовой идентификатор группы, сопоставляемый с именем в `/etc/group` или внешних каталогах.
- **GECOS** — текстовое поле комментария в `/etc/passwd` (поле 5), historically содержащее информацию о пользователе (полное имя, номер комнаты, рабочий телефон). В современных системах используется для хранения полного имени и контактных данных.
- **Суперпользователь (root)** — учетная запись с идентификатором **UID 0**, обладающая абсолютными полномочиями в рамках пространства имен.
- **Nobody / Nogroup** — специальная непривилегированная учетная запись (обычно UID 65534), используемая для запуска процессов без владения ресурсами, что минимизирует ущерб при компрометации.
- **UPG (User Private Groups)** — архитектурная схема, при которой для каждого пользователя создается персональная группа с идентичным именем и GID = UID. Это современный стандарт, реализующий принцип наименьших привилегий. *Подробнее:* [Приватные группы (UPG)](./user_private_groups.md).
- **Supplementary Groups (Дополнительные группы)** — группы, в которые добавлен пользователь помимо первичной. Используются для делегирования прав на специфические ресурсы (Docker, sudo, KVM).
- **Dynamic User (Динамический пользователь)** — пользователь, чьи учетные данные существуют только в рантайме и не записываются в `/etc/passwd`. Реализуется через `DynamicUser=yes` в unit-файлах systemd.
- **Golden Image (Эталонный образ)** — воспроизводимый образ ОС или контейнера, содержащий предопределенный набор пользователей и групп.

## Базовые концепции

### Типы идентификаторов процесса (Credentials)

Для каждого процесса ядро отслеживает набор идентификаторов, определяющих его полномочия:

1.  **Real UID (RUID):** Идентификатор пользователя, запустившего процесс. Используется для учета и сигналов.
2.  **Effective UID (EUID):** Основной идентификатор, по которому проверяются права доступа (чтение/запись файлов). Меняется при использовании **[SUID-бита](../../Security/Concepts/File_Permissions/special_permissions.md)** или `sudo`.
3.  **Saved Set-UID (SUID):** Позволяет процессу временно переключаться между EUID и RUID (например, сбрасывать права root и возвращать их при необходимости).
4.  **FileSystem UID (FSUID):** Специфичный для Linux ID, используемый исключительно для проверок прав на файлы (редко отличается от EUID).

**Технический нюанс:** FSUID был введен для поддержки NFS-серверов, которые должны проверять права доступа от лица запрашивающего клиента, а не от своего EUID. В современных системах без NFS FSUID обычно равен EUID.

### Современная архитектура: systemd-userdbd (2026)

В современных системах традиционные файлы (`/etc/passwd`) перестали быть единственным источником правды. Сервис **`systemd-userdbd.service`** выступает в роли агрегатора, объединяя данные из:
- Локальных файлов;
- **[systemd-homed](./systemd-homed.md)** (портативные JSON-записи);
- **[SSSD/LDAP](./LDAP_SSSD/index.md)** (сетевые каталоги);
- Динамических пользователей (DynamicUser в systemd).

Утилиты (например, `ls` или `id`) получают данные через унифицированный API (D-Bus), что обеспечивает консистентность метаданных.

**Важность для автоматизации:** При использовании `getent passwd` система автоматически опрашивает все источники, указанные в `nsswitch.conf`. Это означает, что скрипты, работающие с `getent`, корректно работают и в гибридных средах (локальные + LDAP + homed).

### Классификация диапазонов ID

| Категория | Диапазон ID | Описание |
| :--- | :--- | :--- |
| **Суперпользователь** | 0 | Полный контроль (UID 0). |
| **Системные** | 1–999 | Учетные записи служб (изоляция процессов). Обычно заблокированы для входа. |
| **Обычные пользователи** | 1000–60000 | Предназначены для интерактивных сессий людей. |
| **Nobody** | 65534 | Бесправный пользователь (NFS root-squashing). |
| **64-bit / High Range** | 100000+ | Используются в контейнерах и **[User Namespaces](../../Podman/podman_rootless.md)**. |

**Политика дистрибутивов (2026):**
- **RHEL/CentOS/Fedora:** Системные UID < 1000, обычные 1000–60000.
- **Debian/Ubuntu:** Исторически системные UID < 500, но современные версии используют 1–999 для совместимости с RHEL.
- **Arch Linux:** Системные UID < 1000, обычные 1000+.
- **Gentoo:** Системные UID < 1000, обычные 1000+.

При переносе пользователей между дистрибутивами учитывайте разницу в пороговых значениях.

### Supplementary Groups (дополнительные группы)

Дополнительные группы расширяют права пользователя без изменения первичной группы. Модель доступа в Linux определяется пересечением прав всех групп, в которых состоит процесс (primary + supplementary).

**Ключевые моменты:**
- При создании файла GID наследуется от **первичной** группы.
- При доступе к ресурсу (например, `/var/run/docker.sock`) проверяется членство в **всех** группах пользователя.
- Ограничение: процесс не может иметь больше 32 supplementary groups по умолчанию (можно увеличить через `CONFIG_NGROUPS_MAX` в ядре).

### Взаимодействие с DynamicUser=

Unit-файлы systemd могут содержать директиву `DynamicUser=yes`. В этом случае `systemd-sysusers` не создает запись в `/etc/passwd`, а systemd управляет пользователем полностью в рантайме через cgroup и капсулы. Это исключительно для сервисов, которым не требуется стабильный UID между перезагрузками.

**Преимущества:**
- Иммутабельность: не требует изменений в `/etc/passwd`.
- Безопасность: UID выделяется динамически из диапазона, предотвращая конфликты.
- Ограничение: не подходит для сервисов, которые сохраняют UID в базе данных или файловой системе.

### NSS и PAM контекст

При наличии `systemd-userdbd` в `nsswitch.conf` порядок поиска может выглядеть так:

```text
passwd: files systemd
group: files systemd
shadow: files
```

Это означает, что запросы к `id`, `getent passwd` сначала проверяют локальные файлы, затем — виртуальную базу systemd-userdbd, куда могут входить пользователи homed, SSSD и динамические аккаунты.

## Идентификация и Изоляция

### Пространства имен (User Namespaces)

Критически важный механизм современной безопасности (Podman, Docker Rootless, LXC):
- **UID Mapping:** Позволяет отображать UID 0 («внутренний root») контейнера на обычный UID 1000 на хосте.
- **Результат:** Процесс думает, что он root, но ядро хоста ограничивает его права полномочиями обычного пользователя.
- **subuid / subgid:** Файлы, определяющие диапазоны идентификаторов, которыми может распоряжаться обычный пользователь для маппинга внутри контейнеров.

**Важность для SRE:** User Namespaces позволяют запускать rootless-контейнеры без SUID-битов, что критично для хостов, где запрещены привилегированные режимы (Kubernetes nodes, shared hosting).

### Конвенции именования (2026)

- **Системные аккаунты:** Рекомендуется префикс подчеркивания (`_nginx`, `_prometheus`) для визуального отделения от людей.
- **Человеческие аккаунты:** Строчные латинские буквы, цифры и дефис.
- **Регистр:** Linux чувствителен к регистру (Case-sensitive), но для совместимости с сетевыми протоколами (AD/LDAP) всегда используйте нижний регистр.
- **Длина имени:** до 32 символов (ограничение NSS).

### Supplementary Groups и безопасность

Избыточное членство в группах является нарушением принципа наименьших привилегий. Типичные ошибки:
- Добавление всех пользователей в группу `docker` без необходимости.
- Назначение `wheel`/`sudo` группам, не требующим привилегий.
- Использование общей группы `users` для доступа к чувствительным ресурсам.

## Практические сценарии

### Глубокая диагностика идентификаторов

```bash
# Информация о текущем пользователе и всех группах
id

# Проверка идентификаторов процесса (включая RUID/EUID/Saved)
grep -E 'Uid|Gid' /proc/self/status
# → Uid: 1000 1000 1000 1000

# Поиск всех пользователей с UID 0 (проверка на бэкдоры)
awk -F: '$3 == 0 {print $1}' /etc/passwd

# Проверка источника данных через NSS
getent passwd username
```

### Анализ принадлежности к группам

```bash
# Список имен всех групп пользователя
groups username

# Список всех членов конкретной группы
getent group sudo | cut -d: -f4

# Числовые идентификаторы (включая supplementary)
id -u username
id -g username
id -G username
```

### Валидация соответствия стандартам

```bash
#!/bin/bash
# validate_users.sh — базовый аудит соответствия CIS-подобным стандартам

echo "=== Пользователи с UID 0 ==="
awk -F: '($3 == 0) {print $1}' /etc/passwd

echo "=== Пустые пароли ==="
sudo awk -F: '($2 == "" || $2 == "!") {print $1}' /etc/shadow

echo "=== Системные пользователи с интерактивным shell ==="
awk -F: '($3 < 1000 && $3 != 0 && $7 != "/usr/sbin/nologin" && $7 != "/bin/false") {print $1}' /etc/passwd

echo "=== Пользователи без домашней директории ==="
awk -F: '($6 == "" || $6 == "/") {print $1}' /etc/passwd

echo "=== Дубликаты UID ==="
awk -F: '{print $3}' /etc/passwd | sort | uniq -d

echo "=== Дубликаты GID ==="
awk -F: '{print $3}' /etc/group | sort | uniq -d
```

### Аудит качества данных (GECOS)

```bash
# Пользователи с пустым полем GECOS
awk -F: '($5 == "") {print $1}' /etc/passwd

# Пользователи, у которых в GECOS нет полного имени (только один токен без пробелов)
awk -F: '($5 != "" && $5 !~ / /) {print $1, $5}' /etc/passwd

# Поиск чувствительных данных в GECOS (телефоны, внутренние номера)
awk -F: '($5 ~ /[0-9]{3,}/) {print $1, $5}' /etc/passwd
```

### Проверка NSS-консистентности

```bash
# Сравнение локальных и сетевых пользователей
echo "=== Локальные пользователи ==="
cut -d: -f1 /etc/passwd | sort > /tmp/local_users

echo "=== Пользователи через NSS (включая LDAP) ==="
getent passwd | cut -d: -f1 | sort > /tmp/nss_users

echo "=== Есть в NSS, но нет локально (сетевые) ==="
comm -23 /tmp/nss_users /tmp/local_users | head -n 20

echo "=== Есть локально, но не в NSS (аномалия) ==="
comm -13 /tmp/nss_users /tmp/local_users | head -n 20

rm -f /tmp/local_users /tmp/nss_users
```

### Обнаружение конфликтов UID/GID

```bash
# Поиск пользователей с одинаковым UID
echo "=== Дублирующиеся UID ==="
awk -F: '{print $3}' /etc/passwd | sort | uniq -d

# Поиск групп с одинаковым GID
echo "=== Дублирующиеся GID ==="
awk -F: '{print $3}' /etc/group | sort | uniq -d

# Проверка соответствия UID=GID для UPG
echo "=== Нарушения UPG (UID != GID) ==="
while IFS=: read -r user _ uid gid _; do
    if [ "$uid" != "$gid" ]; then
        echo "$user: UID=$uid GID=$gid"
    fi
done < /etc/passwd
```

### Валидация golden image

```bash
#!/bin/bash
# validate_golden_image.sh — проверка фиксированного набора пользователей

EXPECTED_USERS=("root" "bin" "daemon" "_nginx" "_postgres" "_prometheus")
EXPECTED_GROUPS=("root" "bin" "daemon" "_nginx" "_postgres" "_prometheus")

echo "=== Проверка наличия сервисных пользователей ==="
for user in "${EXPECTED_USERS[@]}"; do
    if ! id "$user" &>/dev/null; then
        echo "ОТСУТСТВУЕТ: $user"
    fi
done

echo "=== Проверка UID системных пользователей ==="
for user in "${EXPECTED_USERS[@]}"; do
    uid=$(id -u "$user" 2>/dev/null)
    if [ -n "$uid" ] && [ "$uid" -ge 1000 ]; then
        echo "WARNING: $user имеет UID $uid (ожидалось < 1000)"
    fi
done

echo "=== Проверка supplemental групп ==="
id -Gn root | tr ' ' '\n' | sort > /tmp/root_groups
getent group | cut -d: -f1 | sort > /tmp/all_groups
comm -23 /tmp/root_groups /tmp/all_groups
rm -f /tmp/root_groups /tmp/all_groups
```

### Подготовка к миграции (Pre-flight)

```bash
#!/bin/bash
# preflight_migration.sh — проверка готовности к миграции пользователей

TARGET_UID_RANGE="1000-60000"

echo "=== Проверка конфликтов UID в целевом диапазоне ==="
getent passwd | awk -F: -v range="$TARGET_UID_RANGE" '
    BEGIN { split(range, a, "-"); min=a[1]; max=a[2] }
    ($3 >= min && $3 <= max) { print $1, $3 }
' | sort -k2 -n

echo "=== Проверка subuid/subgid покрытия ==="
while IFS=: read -r user _; do
    uid=$(id -u "$user")
    if [ "$uid" -ge 1000 ] && [ "$uid" -lt 60000 ]; then
        grep -q "^$user:" /etc/subuid || echo "WARNING: $user отсутствует в /etc/subuid"
        grep -q "^$user:" /etc/subgid || echo "WARNING: $user отсутствует в /etc/subgid"
    fi
done < <(getent passwd | awk -F: '$3 >= 1000 && $3 < 60000 {print $1}')

echo "=== Проверка орфанных домашних директорий ==="
while IFS=: read -r user _ uid home shell; do
    if [ "$uid" -ge 1000 ] && [ "$home" != "/" ] && [ "$home" != "" ]; then
        [ ! -d "$home" ] && echo "ОТСУТСТВУЕТ: $home ($user)"
    fi
done < /etc/passwd
```

## Дополнительная информация

### Безопасность и Принципы

1.  **Принцип наименьших привилегий (POLP):** Любой процесс должен запускаться под минимально возможным UID.
2.  **Изоляция ID:** Никогда не используйте один и тот же UID для разных независимых сервисов.
3.  **Контроль UID 0:** Наличие любого пользователя с UID 0, кроме `root`, считается критической уязвимостью.
4.  **Именование:** Системные аккаунты всегда должны начинаться с подчеркивания (`_`) для визуального отделения от человеческих аккаунтов.
5.  **UPG по умолчанию:** Для новых пользователей всегда используйте схему User Private Groups (UID = GID).
6.  **Supplementary Groups:** Избегайте массового назначения дополнительных групп. Каждая группа должна иметь обоснованное назначение.
7.  **Атомарность изменений:** Изменения в `/etc/passwd`, `/etc/shadow`, `/etc/group` должны быть атомарными. Используйте `vipw`/`vigr` для предотвращения повреждения баз при одновременном редактировании.

### Жизненный цикл учетной записи

| Этап | Событие | Ответственные | Контроль |
| :--- | :--- | :--- | :--- |
| **Provisioning** | Создание аккаунта | Импер: `useradd`/Деклар: `systemd-sysusers` | Валидация GECOS, shell, домашней директории |
| **Active** | Работа пользователя | Пользователь | Мониторинг через `lastlog`, `faillock` |
| **Privilege Escalation** | Получение временных прав | `sudo`, `run0` | Аудит через `journalctl` |
| **Offboarding** | Удаление/архивация | Администратор | Архивирование данных, отзыв прав |
| **Post-mortem** | Аудит после удаления | Security team | Проверка на остаточные данные, SUID-файлы |

### Типичные проблемы и диагностика

| Проблема | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| `chown: invalid user` | UID существует, но не найден в NSS | `getent passwd <uid>` | Создать пользователя или проверить `nsswitch.conf` |
| Файлы принадлежат `nobody` | Несовпадение UID между хостами (NFS) | `stat <file>` | Синхронизировать UID или настроить `idmapd` |
| `su: Authentication failure` | Неверный пароль или PAM блокировка | `faillock --user username` | Сбросить счетчик или разблокировать |
| `Permission denied` на SUID-файл | Отсутствует членство в группе | `ls -la <file>` | Добавить в supplementary group |
| Процесс запускается с неверным EUID | Неправильный SUID-бит | `ls -la <binary>` | Проверить владельца и биты |
