# Определения пользователей и групп в Linux

## Определения

- **Пользователь (User)** — уникальная учетная запись, идентифицирующая субъекта (человека или системный процесс) для разграничения прав доступа и аудита действий.
- **UID (User Identifier)** — уникальный числовой идентификатор, используемый ядром Linux для проверки прав доступа. 
    - **Природа UID:** Внутри системы пользователь — это всегда число. Текстовые имена существуют исключительно для удобства человека и сопоставляются с UID через файл `/etc/passwd`. При выполнении команд (например, `ls -l`) система обращается к этому файлу для «перевода» числа в имя.
- **Группа (Group)** — логическое объединение пользователей для упрощения управления коллективным доступом к файлам, устройствам и системным вызовам.
- **GID (Group Identifier)** — числовой идентификатор группы, сопоставляемый с именем в `/etc/group`. У каждого файла всегда два владельца: конкретный пользователь и группа-владелец.
- **Суперпользователь (root)** — учетная запись с идентификатором **UID 0**, обладающая абсолютными полномочиями.
    - **Магия нуля:** Именно равенство UID нулю дает неограниченную власть. Технически можно создать вторую запись с UID 0 или переименовать `root`, но это критическая дыра в безопасности и источник путаницы.
    - **Границы власти:** Даже root не всесилен — например, он не может запустить файл, если у того не установлен бит исполнения (`x`).
- **Nobody / Nogroup** — специальная непривилегированная учетная запись (обычно UID 65534), используемая для запуска процессов, которым не требуется владение какими-либо файлами (например, NFS или некоторые демоны), для минимизации ущерба при компрометации.

## Базовые концепции

### Типы идентификаторов (UID/GID)

Для каждого процесса ядро отслеживает набор идентификаторов, что позволяет безопасно временно повышать или понижать привилегии:

1. **Real UID (RUID):** Идентификатор пользователя, запустившего процесс. Используется в основном для учета (кто на самом деле владеет процессом).
2. **Effective UID (EUID):** Текущий идентификатор, по которому ядро проверяет права доступа в данный момент. Именно EUID меняется при использовании SUID-бита или `sudo`.
3. **Saved Set-UID (SUID):** «Парковочное место» для прав. Позволяет процессу временно сбросить привилегии (перейти с root на обычного юзера) и позже вернуть их обратно, забрав из этого хранилища.

**Пример смены прав:** Программа входа (`login`) запускается как root, проверяет пароль, меняет свой UID на пользовательский и запускает оболочку. После смены UID процесс проходит «точку невозврата» — он не может самостоятельно вернуть права root, если только не использует механизм SUID.

### Классификация учетных записей

| Категория | Диапазон ID | Описание |
| :--- | :--- | :--- |
| **Суперпользователь** | 0 | Полный контроль над системой (UID 0). |
| **Системные (Псевдопользователи)** | < 1000 | Учетные записи для изоляции системных служб. Вход под ними заблокирован (`*` в `/etc/shadow`), а в качестве оболочки установлен `/usr/sbin/nologin`. Это позволяет безопасно делегировать владение ресурсами (файлы БД, веб-контент) без предоставления полных привилегий root. |
| **Обычные пользователи** | 1000+ | Предназначены для людей и интерактивного входа. |
| **Nobody (UID 65534)** | 65534 | Специальная учетная запись для «обезличивания» доступа. В NFS используется для маппинга (`root_squash`) удаленного root в бесправного пользователя. |

**Особенности системных аккаунтов:**
*   **Изоляция:** Каждая служба (MySQL, Apache, Nginx) работает под своим ID, имея доступ только к своим данным.
*   **Защита от входа:** Отсутствие валидного пароля и интерактивной оболочки предотвращает использование этих аккаунтов для входа в систему (даже через SSH-ключи).

### Конвенции именования (2025–2026)

Для предотвращения путаницы между системными и человеческими аккаунтами рекомендуется следовать правилам:
- **Системные пользователи:** Префикс подчеркивания (`_nginx`, `_prometheus`). Это стандарт для многих современных дистрибутивов и облачных образов.
- **Человеческие пользователи:** Строчные латинские буквы, цифры и дефис (`kebab-case`).

### Пространства имен пользователей (User Namespaces)

В современной контейнеризации (Docker, Podman, Kubernetes) используется механизм **UID Mapping**:
- Пользователь `root` (UID 0) внутри контейнера может быть отображен на обычного пользователя (например, UID 1000) на хосте.
- Это гарантирует, что «побег» из контейнера не даст злоумышленнику реальных прав `root` на физическом сервере.

## Практические сценарии

### Диагностика текущих идентификаторов

```bash
# Информация о текущем пользователе (UID, GID и все группы)
id

# Проверка конкретного пользователя
id username

# Вывод всех имен пользователей в системе
cut -d: -f1 /etc/passwd

# Поиск всех учетных записей с UID 0 (проверка на дубликаты root)
awk -F: '$3 == 0 {print $1}' /etc/passwd
```

### Фильтрация пользователей по типам

```bash
# Вывод только обычных (человеческих) пользователей
awk -F: '$3 >= 1000 && $3 != 65534 {print $1}' /etc/passwd

# Вывод системных пользователей
awk -F: '$3 < 1000 && $3 != 0 {print $1}' /etc/passwd
```

### Проверка принадлежности к группам

```bash
# Список групп, в которых состоит пользователь
groups username

# Просмотр всех членов конкретной группы через базу NSS
getent group sudo
```

## Дополнительная информация

### Безопасность

- **Принцип наименьших привилегий:** Избегайте запуска приложений от имени `root`. Всегда создавайте выделенного системного пользователя для каждого сервиса.
- **Контроль UID 0:** Наличие любого пользователя с UID 0, кроме `root`, является критической уязвимостью или признаком взлома (backdoor).
- **Конфликты при миграции:** При переносе данных между серверами всегда проверяйте соответствие числовых UID, так как имена могут совпадать, а ID — нет. Подробнее: [Миграция пользователей](./user_migration.md).
