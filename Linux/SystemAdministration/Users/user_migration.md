# Перенос пользователей между системами Linux

## Определения

- **Миграция пользователей** — комплексный процесс переноса учетных данных (логин, пароль, UID/GID), домашних директорий, системных квот и специфических настроек (например, subuid/subgid) между различными инстансами ОС Linux.
- **Идентификаторы (UID/GID)** — числовые значения, используемые ядром для идентификации владельца процесса или файла.
- **Remapping (Переназначение)** — процесс изменения UID/GID пользователя при миграции для предотвращения конфликтов с существующими учетными записями на целевой системе.

## Базовые концепции

### Типы миграции

| Тип | Описание | Применимость |
| :--- | :--- | :--- |
| **Локальная (Imperial)** | Прямое копирование записей из `/etc/passwd`, `/etc/shadow`, `/etc/group`. | Малые системы, отсутствие домена. |
| **Декларативная** | Использование инструментов автоматизации (Ansible, SaltStack) для создания идентичных учетных записей. | Масштабируемые инфраструктуры. |
| **Портативная** | Использование механизмов типа `systemd-homed`, где данные и метаданные пользователя хранятся в одном образе/диске. | Современные рабочие станции, облака. |
| **Централизованная** | Переход на сетевые службы каталогов (LDAP, Active Directory, FreeIPA). | Корпоративные среды. |

### Ключевые риски и факторы (2025–2026)

1. **Конфликты идентификаторов:** Если UID на целевой системе занят, простая синхронизация файлов через `rsync` приведет к потере доступа или неверному наследованию прав.
2. **Алгоритмы хэширования:** При переносе из старых систем (например, CentOS 7 с `SHA512`) в современные (например, Ubuntu 24.04/26.04 с `YESCRYPT`) необходимо убедиться, что целевая система поддерживает старый формат хэша в PAM.
3. **Расширенные атрибуты:** Игнорирование SELinux-контекстов или ACL-списков при копировании данных может нарушить работу политик безопасности на целевой системе.
4. **Дополнительные ID (subuid/subgid):** Для работы контейнеров (Podman, Docker Rootless) требуется перенос соответствующих диапазонов из `/etc/subuid` и `/etc/subgid`.

## Практические сценарии

### Подготовка

1.  **Аудит идентификаторов:**
    Проверьте, не занят ли UID/GID на целевой системе:
    ```bash
    getent passwd <UID_OR_NAME>
    getent group <GID_OR_NAME>
    ```
2.  **Проверка хэша:**
    Убедитесь, что алгоритм хэширования пароля из `/etc/shadow` (например, `$y$` для yescrypt) поддерживается на новом сервере.

### Метод 1: Ручной перенос через экспорт/импорт

Подходит для переноса 1–5 пользователей.

#### Шаг 1: Экспорт данных на исходном сервере
```bash
# Извлечение записей
export TARGET_USER="username"
grep "^${TARGET_USER}:" /etc/passwd > user_passwd.txt
grep "^${TARGET_USER}:" /etc/shadow > user_shadow.txt
grep "^${TARGET_USER}:" /etc/group > user_group.txt
# Не забываем про дополнительные ID для контейнеров
grep "^${TARGET_USER}:" /etc/subuid > user_subuid.txt || true
grep "^${TARGET_USER}:" /etc/subgid > user_subgid.txt || true
```

#### Шаг 2: Синхронизация файлов
Используйте `rsync` с флагами для сохранения метаданных и расширенных атрибутов:
- `-a` (архивный режим)
- `-H` (сохранение жестких ссылок)
- `-A` (сохранение ACL)
- `-X` (сохранение расширенных атрибутов/SELinux)

```bash
rsync -aHAXz --progress /home/username/ root@new-server:/home/username/
```

#### Шаг 3: Импорт на целевом сервере
```bash
sudo cat user_passwd.txt >> /etc/passwd
sudo cat user_shadow.txt >> /etc/shadow
sudo cat user_group.txt >> /etc/group
sudo cat user_subuid.txt >> /etc/subuid
sudo cat user_subgid.txt >> /etc/subgid

# Финальное восстановление владельца (на случай смены UID)
sudo chown -R username:username /home/username
```

### Метод 2: Массовая миграция (newusers)

Если нужно перенести сотни пользователей, используйте утилиту `newusers`, которая принимает файл в формате `/etc/passwd`.

1.  Подготовьте файл со списком пользователей.
2.  Запустите:
    ```bash
    sudo newusers < users_list.txt
    ```
    *Примечание: Пароли в этом файле должны быть либо в открытом виде (если система их захеширует), либо уже захешированы согласно настройкам системы.*

### Метод 3: Перенос портативных аккаунтов (systemd-homed)

Если используется `systemd-homed`, миграция сводится к копированию образа домашней директории.

```bash
# На исходной системе (экспорт в tarball)
homectl export username /tmp/username.homedir

# На целевой системе (импорт)
homectl import username /tmp/username.homedir
```

## Дополнительная информация

### Проверка после миграции

После завершения переноса выполните диагностику:
```bash
# Проверка входа
su - username -c "ls -la"

# Проверка идентификаторов
id username

# Проверка дополнительных диапазонов (для Podman)
podman system migrate
```

### Распространенные проблемы

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| Ошибка аутентификации | Неподдерживаемый формат хэша пароля. | Сбросьте пароль через `passwd` или обновите настройки PAM. |
| Permission Denied в SSH | Неверные права на `.ssh` (должно быть 700) или `authorized_keys` (600). | `chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys`. |
| Файлы принадлежат другому пользователю | UID на новом сервере совпал с другим аккаунтом. | Смените UID пользователя и выполните `chown -R`. |
| Не работают sudo-права | Записи в `/etc/sudoers.d/` не были перенесены. | Скопируйте соответствующие файлы из `/etc/sudoers.d/`. |
