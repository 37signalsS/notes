# Эксплуатация и отладка LDAP и SSSD

## Определения

- **SSSD (System Security Services Daemon)** — системная служба, обеспечивающая доступ к удаленным базам данных пользователей с поддержкой кэширования и работы в автономном режиме.
- **LDB (Lightweight Database)** — встраиваемая база данных на основе LDAP-подобного движка, используемая SSSD для локального хранения кэша пользователей, групп и атрибутов.
- **`sssctl`** — унифицированная утилита для инспекции состояния SSSD, проверки конфигурации и управления онлайн-статусом доменов.
- **`sss_override`** — инструмент для локального переопределения атрибутов пользователей (UID, GID, домашняя папка), полученных из внешнего каталога.
- **GSSAPI (Generic Security Service Application Program Interface)** — программный интерфейс для приложений, позволяющий использовать Kerberos для безопасной сетевой аутентификации.
- **SASL (Simple Authentication and Security Layer)** — метод добавления поддержки аутентификации в протоколы на основе соединений (например, LDAP).

## Базовые концепции

### Структура хранения данных (Кэш)

SSSD разделяет кэширование на два уровня для обеспечения производительности и надежности:
1.  **Кэш в оперативной памяти (`/var/lib/sss/mc/`)**: Файлы маппинга (`passwd`, `group`), обеспечивающие мгновенный отклик для системных вызовов `getpwnam` и `getgrnam`.
2.  **Дисковый кэш LDB (`/var/lib/sss/db/`)**: Полноценная база данных для каждого домена. Позволяет SSSD выполнять сложные поисковые запросы и аутентифицировать пользователей при отсутствии связи с сервером.

### Режимы работы домена

SSSD автоматически переключает состояние домена в зависимости от доступности сетевого ресурса:
- **Online**: Все запросы направляются к серверу каталогов, кэш обновляется в фоновом режиме.
- **Offline**: Запросы обрабатываются исключительно из локального кэша LDB. Пользователи могут входить, если их хэши паролей были ранее сохранены (cached credentials).

### Уровни отладки (Debug Levels)

Параметр `debug_level` в `sssd.conf` определяет детализацию логов в `/var/log/sssd/`:
- **0–2**: Критические ошибки.
- **3–5**: Информация о запросах и предупреждения (режим для Production).
- **6–9**: Глубокая трассировка всех внутренних функций и состояний конечного автомата. Вызывает значительную нагрузку на I/O.

## Практические сценарии

### Глубокая диагностика через sssctl

Утилита `sssctl` является предпочтительным инструментом в современных дистрибутивах (RHEL 8/9, Ubuntu 22.04+).

```bash
# Проверка общего состояния всех доменов
sudo sssctl domain-status -a

# Проверка данных конкретного пользователя (откуда получены, срок жизни кэша)
sudo sssctl user-check username

# Проверка членства в группах
sudo sssctl group-check groupname

# Инспекция конфигурации на наличие синтаксических ошибок
sudo sssctl config-check
```

### Управление кэшем и базой данных LDB

Если данные в системе не соответствуют данным в LDAP (например, после смены GID), необходимо выполнить сброс кэша.

```bash
# Инвалидация конкретного пользователя
sudo sss_cache -u username

# Полная очистка всех записей (пользователи, группы, netgroups)
sudo sss_cache -E

# Восстановление при повреждении базы данных (радикальный метод)
sudo systemctl stop sssd
sudo rm -f /var/lib/sss/db/*.ldb
sudo rm -f /var/lib/sss/mc/*
sudo systemctl start sssd
```

### Локальное переопределение атрибутов (sss_override)

Полезно, когда необходимо изменить UID или Shell для пользователя LDAP только на конкретном сервере без изменения данных в центральном каталоге.

```bash
# Переопределение Shell для пользователя
sudo sss_override user-add username -s /bin/zsh

# Переопределение UID/GID
sudo sss_override user-add username -u 2000 -g 2000

# Применение изменений (требует очистки кэша nss)
sudo sss_cache -u username

# Просмотр всех действующих переопределений
sudo sss_override user-show username

# Удаление переопределения
sudo sss_override user-del username
```

### Поиск и устранение неисправностей (Troubleshooting)

| Симптом | Вероятная причина | Метод решения |
| :--- | :--- | :--- |
| Ошибка `System Error` при логине | Повреждение LDB или нехватка места | Очистите `/var/lib/sss/db/` и проверьте дисковые квоты. |
| Ошибка `Permission Denied` для UID 0 | Фильтрация в [nss] | Проверьте `filter_users = root` в `sssd.conf`. SSSD не должен обрабатывать root. |
| Долгая задержка при `ls -l` | Слишком большой `entry_cache_timeout` | Уменьшите таймауты кэширования или используйте `sss_cache`. |
| Ошибка TLS `Unknown CA` | CA-сертификат не в доверенных | Проверьте путь в `ldap_tls_cacert`. Используйте `openssl s_client -connect host:636` для проверки цепочки. |
| Не работает SSO (Kerberos) | Время рассинхронизировано | Разница во времени с DC не должна превышать 5 минут. Используйте `chronyc sources`. |

## Дополнительная информация

### Безопасность эксплуатации

1.  **Права доступа**: Файл `/etc/sssd/sssd.conf` содержит пароль Bind DN в открытом виде (если не используется Kerberos). Обязательны права `600` и владелец `root:root`.
2.  **Защита логов**: Логи SSSD могут содержать чувствительную информацию о структуре каталогов. Ограничьте доступ к `/var/log/sssd/`.
3.  **Аутентификация через Keytab**: Для максимальной безопасности настройте провайдер `ad` или `ipa`, чтобы SSSD использовал системный Keytab вместо хранения паролей.

### Мониторинг производительности

Для систем с количеством пользователей > 10 000 рекомендуется:
- Выносить `/var/lib/sss/db/` на быстрые носители (SSD/NVMe).
- Увеличивать размер кэша в памяти через параметры в секции `[nss]`.
- Отключать перечисление всех пользователей (`enumerate = false`), так как это создает огромную нагрузку на LDAP и CPU.
