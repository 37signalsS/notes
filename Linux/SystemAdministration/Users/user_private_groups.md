# Приватные группы пользователей (UPG)

## Определения

- **UPG (User Private Groups)** — архитектурная схема организации групп в Linux, при которой для каждого нового пользователя автоматически создается персональная группа с идентичным именем и числовым идентификатором (UID = GID).
- **Первичная группа (Primary Group)** — группа, GID которой зафиксирован в `/etc/passwd`. Все файлы, создаваемые пользователем, по умолчанию наследуют идентификатор этой группы.
- **`umask` (User File-Creation Mask)** — системная битовая маска, определяющая права доступа, которые **запрещены** для новых файлов и директорий.
- **SGID (Set Group ID) на директорию** — специальный бит прав доступа (значение `2`), форсирующий наследование группы родительской директории для всех создаваемых внутри объектов.
- **USERGROUPS_ENAB** — параметр в `/etc/login.defs`, управляющий автоматическим созданием группы при создании пользователя и её удалением при ликвидации аккаунта.
- **USERGROUPS_MOD** — параметр в `/etc/login.defs`, задающий `umask` для новых пользователей в схеме UPG (обычно `002`).
- **`useradd -U` / `-N`** — флаги управления UPG: `-U` принудительно включает UPG, `-N` отключает создание приватной группы.
- **`groupmems`** — утилита для делегирования прав пользователю на управление своей первичной группой без `sudo`.
- **`newgidmap`** — утилита маппинга GID для User Namespaces (rootless-контейнеры).

## Базовые концепции

### Механизм работы и архитектурная цель UPG

Традиционная модель Unix использовала общие группы (например, `users` или `staff`) в качестве первичных. Это создавало дилемму безопасности:
1.  При `umask 022` файлы защищены от записи коллегами по группе, но совместная работа в общих папках требует ручного изменения прав (`chmod g+w`).
2.  При `umask 002` (права на запись для группы по умолчанию) файлы в домашних директориях пользователей становились уязвимы для всех членов общей группы `users`.

Схема UPG устраняет этот конфликт через связку **«Персональная группа + umask 002»**:
- Поскольку пользователь является единственным членом своей первичной группы, `umask 002` (права `rw-rw-r--`) абсолютно безопасен в его домашней директории — никто другой не входит в эту группу.
- При переходе в общую проектную директорию с установленным битом **SGID**, тот же `umask 002` позволяет пользователям мгновенно обмениваться файлами с правом на запись, так как новые файлы автоматически получают GID проекта, а не персональный GID создателя.

#### Исторический контекст

Механизм UPG появился в SVR4 и был formalized в Linux через пакет `shadow-utils` в начале 1990-х. До этого каждый пользователь был принудительно приписан к общей группе `users` (GID 100 в большинстве дистрибутивов). Это было адекватно в эпоху разделяемых мультипользовательских серверов, но стало узким местом при переходе к индивидуальным рабочим станциям и модели «один пользователь — одно приложение».

Современный sysadmin должен понимать, что UPG — это не просто «удобство», а реализация принципа наименьших привилегий (POLP) на уровне идентификаторов доступа к файловой системе.

### Ключевые параметры конфигурации (/etc/login.defs)

Поведение подсистемы определяется в файле `/etc/login.defs`:

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| **`USERGROUPS_ENAB`** | `yes` | При создании пользователя `useradd` создаст группу с тем же именем. При удалении пользователя `userdel` удалит группу, если в ней нет других членов. |
| **`USERGROUPS_MOD`** | `002` | Если UID=GID, система использует `umask 002` вместо дефолтного `022`. Требует поддержки `pam_umask`. |
| **`SYS_GID_MIN`** / **`MAX`** | `100-999` | Диапазон GID для системных приватных групп (используется для изоляции сервисов). |

#### Взаимодействие с PAM: pam_umask

Параметр `USERGROUPS_MOD` работает только при подключенном модуле **`pam_umask.so`** в `/etc/pam.d/common-session` (Debian/Ubuntu) или `/etc/pam.d/system-auth` (RHEL/Fedora):

```text
session optional pam_umask.so
```

Без этого модуля `umask` для нового пользователя остается глобальным (`022`), даже если `USERGROUPS_ENAB=yes` и UID=GID. Это частая причина неработающего `umask 002` на production-хостах.

#### Флаги `useradd` для управления UPG

```bash
# Принудительно создать приватную группу (даже если USERGROUPS_ENAB=no)
sudo useradd -U newuser

# Создать пользователя без приватной группы (используется группа из /etc/default/useradd)
sudo useradd -N legacy_user

# Явно указать первичную группу, отключив UPG для этого аккаунта
sudo useradd -g developers shared_user
```

### Безопасность и изоляция сервисов

Использование UPG критично для серверной безопасности:
- **Разделение привилегий:** Каждый системный сервис (например, `nginx`, `postgres`) получает свою приватную группу.
- **Защита от латерального перемещения:** Компрометация одного сервиса не дает прав на запись в директории других сервисов через общие системные группы.

#### Делегирование управления UPG: groupmems

Утилита `groupmems` позволяет пользователям добавлять/удалять членов в своей **первичной** группе без `sudo`. Это полезно в средах с самообслуживанием (например, shared hosting):

```bash
# Alice добавляет bob в свою персональную группу alice
groupmems -g alice -a bob

# Просмотр членов группы
groupmems -g alice -l
```

Ограничение: работает только с первичной группой вызывающего пользователя.

## Практические сценарии

### Диагностика и проверка состояния

```bash
# Проверка текущих идентификаторов и членства
id
# → uid=1001(alice) gid=1001(alice) groups=1001(alice),27(sudo)

# Проверка маски в текущей сессии
umask
# → 0002

# Проверка записей в системных базах (совпадение UID/GID)
grep "alice" /etc/passwd
# alice:x:1001:1001::/home/alice:/bin/bash

grep "alice" /etc/group
# alice:x:1001:
```

### Организация совместной работы (Модель UPG + SGID)

Это основной технический сценарий, ради которого внедрялась схема UPG.

```bash
# 1. Подготовка группы проекта и участников
sudo groupadd developers
sudo usermod -aG developers alice
sudo usermod -aG developers bob

# 2. Создание общей директории с правильными атрибутами
sudo mkdir -p /srv/shared_dev
sudo chown root:developers /srv/shared_dev

# 3. Установка SGID бита и прав доступа
# 2000 — SGID, 775 — rwxrwxr-x
sudo chmod 2775 /srv/shared_dev

# 4. Проверка совместной работы
# От имени alice:
touch /srv/shared_dev/config.yaml
# Файл автоматически получит группу developers и права -rw-rw-r--
# Bob сможет редактировать этот файл без дополнительных chmod/chgrp
```

### Продвинутая настройка: Использование Default ACL

Для гарантии прав записи при любом `umask` пользователя (например, если кто-то принудительно поставил `022` в `.bashrc`):

```bash
# Установка дефолтных прав на директорию
sudo setfacl -d -m g:developers:rwx /srv/shared_dev
sudo setfacl -m g:developers:rwx /srv/shared_dev
```

### Ручное управление и исключения

В некоторых случаях требуется обойти механизм UPG (например, при миграции со старых систем).

```bash
# Создание пользователя без приватной группы (флаг -N)
# Будет использована группа из /etc/default/useradd (обычно users/100)
sudo useradd -N legacy_user

# Создание пользователя с принудительным назначением конкретной группы
sudo useradd -g users common_user

# Отключение UPG глобально (в /etc/login.defs)
# USERGROUPS_ENAB no
```

### Взаимодействие с Rootless-контейнерами

В Docker/Podman (rootless) схема UPG расширяется через `/etc/subgid`:
- Каждый пользователь получает диапазон GID (например, 100000–165535).
- Эти ID используются для маппинга приватных групп внутри контейнера, сохраняя изоляцию на хосте.

#### Маппинг GID через newgidmap

Утилита `newgidmap` управляет маппингом GID в User Namespace для rootless-контейнеров:

```bash
# Проверка текущего маппинга
newgidmap $(id -u)

# Пример вывода:
# 0    100000   65536
# Это означает, что GID 0 внутри контейнера маппируется на 100000 на хосте
```

### Compliance и аудит (PCI-DSS, CIS)

В регулируемых средах (финансы, госсектор) требуется доказать, что схема UPG применена ко всем интерактивным пользователям.

#### Скрипт валидации соответствия CIS

```bash
#!/bin/bash
# validate_upg_cis.sh — проверка требования CIS Ubuntu/CentOS

echo "=== UPG Validation (CIS) ==="
violations=0

while IFS=: read -r user _ uid gid _; do
    # Пропуск системных пользователей (UID < 1000)
    [ "$uid" -lt 1000 ] && continue

    # Пропуск nobody/nfsnobody
    [ "$user" = "nobody" ] && continue

    if [ "$uid" -ne "$gid" ]; then
        echo "VIOLATION: $user (UID=$uid, GID=$gid) — UPG не применяется"
        violations=$((violations+1))
    fi
done < /etc/passwd

echo "---"
if [ "$violations" -eq 0 ]; then
    echo "PASS: Все интерактивные пользователи следуют UPG"
else
    echo "FAIL: Найдено $violations нарушений"
    exit 1
fi
```

#### Правила auditd для отслеживания изменений

```bash
# /etc/audit/rules.d/upg-changes.rules
-w /etc/passwd -p wa -k identity_changes
-w /etc/group -p wa -k identity_changes
-w /etc/login.defs -p wa -k upg_config
-w /etc/default/useradd -p wa -k upg_config
```

### Fleet-wide управление (Ansible)

При масштабировании на сотни хостов ручная проверка UPG невозможна. Ansible-роль обеспечивает единообразие:

```yaml
# tasks/main.yml
- name: Ensure USERGROUPS_ENAB is set to yes
  lineinfile:
    path: /etc/login.defs
    regexp: '^USERGROUPS_ENAB'
    line: 'USERGROUPS_ENAB yes'
  notify: restart systemd-userdbd

- name: Validate UPG for all interactive users
  shell: |
    awk -F: '$3 >= 1000 && $1 != "nobody" {if ($3 != $4) exit 1}' /etc/passwd
  register: upg_check
  failed_when: upg_check.rc != 0
  changed_when: false
```

### Golden Image и валидация при сборке образа

В Dockerfile или Packer-шаблоне UPG должно быть зафиксировано до первого запуска:

```dockerfile
# Dockerfile — фиксация политики UPG
RUN sed -i 's/^USERGROUPS_ENAB.*/USERGROUPS_ENAB yes/' /etc/login.defs && \
    grep -q "^USERGROUPS_ENAB yes" /etc/login.defs
```

### Сборка контейнеров и UPG

При `docker build` или `podman build` пользователь внутри контейнера обычно root. UPG актуальна только для multi-stage сборок или при запуске нескольких сервисов в одном контейнере:

```dockerfile
# Создание непривилегированного пользователя с UPG
RUN groupadd -r appuser && useradd -r -g appuser -m appuser
# → appuser:x:1000:1000::/home/appuser:/bin/sh
```

### NFS и квотирование: Edge Cases

UPG в сочетании с NFS имеет особенности:
- При `all_squash` в `/etc/exports` все UID/GID маппируются на `nobody`/`nogroup`. UPG теряет смысл, так как все файлы становятся принадлежать `nobody`.
- Решение: использовать `no_root_squash` только для management-хостов, или настроить `idmapd.conf` для стабильного маппинга UID/GID между сервером и клиентами.

#### Проверка NFS-маппинга

```bash
# На клиенте NFS
stat -c '%u:%g' /mnt/nfs/shared/file
# → 1001:1001  (должен совпадать с UID/GID на сервере)

# Проверка, что UPG не сбилась
id $(stat -c '%u' /mnt/nfs/shared/file)
```

### Автоматизация: Скрипт создания пользователя с проверкой UPG

```bash
#!/bin/bash
# create_user_safe.sh - автоматизация с учетом UPG

USERNAME=$1
COMMENT=$2

if [[ -z "$USERNAME" ]]; then
    echo "Использование: $0 <username> [комментарий]"
    exit 1
fi

# Проверка глобальной настройки
UPG_ENABLED=$(grep "^USERGROUPS_ENAB" /etc/login.defs | awk '{print $2}')
echo "Статус USERGROUPS_ENAB: $UPG_ENABLED"

# Создание пользователя
sudo useradd -m -c "$COMMENT" "$USERNAME"

# Техническая проверка результата
UID_VAL=$(id -u "$USERNAME")
GID_VAL=$(id -g "$USERNAME")

if [ "$UID_VAL" -eq "$GID_VAL" ]; then
    echo "OK: Схема UPG применена (UID $UID_VAL = GID $GID_VAL)"
else
    echo "WARNING: Схема UPG не сработала. UID($UID_VAL) != GID($GID_VAL)"
fi
```

### Troubleshooting

| Симптом | Возможная причина | Решение |
| :--- | :--- | :--- |
| `useradd` создает пользователя с GID из `/etc/default/useradd`, а не с именем пользователя | `USERGROUPS_ENAB=no` в `/etc/login.defs` | Включите `USERGROUPS_ENAB=yes` или используйте флаг `-U` |
| Новые файлы создаются с правами `rw-r--r--` (022) вместо `rw-rw-r--` (002) | Отсутствует `pam_umask.so` в PAM-сессии | Добавьте `session optional pam_umask.so` в `/etc/pam.d/common-session` |
| `userdel` не удаляет группу пользователя | В группе есть дополнительные члены | Выполните `gpasswd -d <user> <group>` перед удалением |
| `id` показывает GID, не совпадающий с именем пользователя | Пользователь создан с флагом `-N` или `-g` | Проверьте `/etc/passwd` и пересоздайте аккаунт при необходимости |
| `chmod 2775` не наследует группу для новых файлов | Отсутствует SGID на директории или используется `mv` вместо `cp` | Убедитесь, что `ls -ld` показывает `s` в позиции группы; используйте `cp` для копирования |
| В контейнере `newgidmap` возвращает ошибку `cannot set groups` | Не настроен `/etc/subgid` или отсутствует `newuidmap` | Добавьте строку `username:100000:65536` в `/etc/subgid` |
| `groupmems` возвращает `Permission denied` | Пользователь не является членом целевой группы | Проверьте `id -Gn` и добавьте пользователя через `usermod -aG` |
| UID=GID при ручном редактировании `/etc/passwd` | Ошибка синхронизации между `/etc/passwd` и `/etc/group` | Используйте `groupadd` вместо ручного редактирования |
| На NFS все файлы принадлежат `nobody` | `all_squash` в экспорте или несогласованные UID | Настройте `idmapd` или отключите `all_squash` |
| `systemd-homed` игнорирует локальную UPG | Профиль homed использует отдельный JSON-бэкенд | Проверьте `loginctl list-sessions` и конфигурацию `homectl`

### Best practices (2026)

1. **Универсальность UPG:** Применяйте UPG ко всем интерактивным пользователям (UID >= 1000). Для сервисных аккаунтов используйте `useradd -r` (системные UID).
2. **pam_umask обязателен:** В production всегда проверяйте наличие `pam_umask.so` в PAM-цепи. Без него UPG не даёт эффекта `umask 002`.
3. **Декларативность:** Для сервисных аккаунтов используйте `systemd-sysusers` с типом `u` вместо ручного `useradd`.
4. **Валидация в CI/CD:** Добавляйте проверку UPG (`uid == gid`) в пайплайн сборки golden image.
5. **Атомарные бэкапы:** Для `/etc/passwd`, `/etc/group`, `/etc/gshadow` используйте файловые дескрипторы (`cp --reflink=auto` или `tar --xattrs`) для обеспечения целостности.
6. **Избегайте all_squash на NFS:** При использовании shared storage настройте стабильный UID/GID маппинг через `idmapd.conf`.
7. **Аудит изменений:** Включите `auditd` с правилами на `/etc/passwd`, `/etc/group`, `/etc/login.defs` для отслеживания несанкционированных изменений.
8. **Rootless-контейнеры:** Для каждого пользователя, запускающего контейнеры, пропишите диапазон в `/etc/subgid` и `/etc/subuid`.
9. **Минимизируйте supplementary groups:** Каждая дополнительная группа расширяет blast radius. Используйте их только для явно делегированных прав (docker, libvirt).
10. **Документируйте исключения:** Если UPG отключена для интеграции с AD/IPA, зафиксируйте это в Runbook и регулярно пересматривайте необходимость.

### Технические рекомендации по применению

| Сценарий | Стратегия | Техническое обоснование |
| :--- | :--- | :--- |
| **Рабочие станции** | UPG + umask 002 | Изоляция личных данных + гибкость совместной работы. |
| **Серверы приложений** | UPG (для каждого сервиса) | Гарантирует, что логи сервиса A недоступны на запись сервису B. |
| **Файловые серверы** | UPG + SGID + ACL | Предотвращение «ада прав» при глубокой вложенности папок. |
| **Интеграция с доменом** | Отключение UPG | В AD/IPA используются централизованные GID; локальные UPG вызывают конфликты. |
| **systemd-homed** | JSON-профили | Сохраняет логику UPG, но делает её переносимой между хостами. |
| **Rootless-контейнеры** | UPG + /etc/subgid + newgidmap | Каждый пользователь получает изолированный диапазон GID внутри контейнера. |
| **Делегирование без sudo** | UPG + groupmems | Пользователь управляет своей первичной группой для совместных папок. |

#### Выбор между UPG и общей группой

UPG — стандарт по умолчанию, но есть сценарии, где общая группа оправдана:
- **Shared hosting:** группа `developers` для доступа к `/srv/www`.
- **CI/CD runners:** группа `runners` для доступа к кэшу артефактов.
- В этих случаях UPG остается для первичной группы (изоляция домашней директории), а общая группа добавляется как supplementary.

### Инструменты аудита и поиска аномалий

```bash
# Поиск пользователей, у которых первичная группа не совпадает с именем пользователя
awk -F: '$1 != $4 {print "Аномалия: пользователь " $1 " имеет первичную группу " $4}' /etc/passwd

# Проверка групп в /etc/group, содержащих более одного участника (не являются приватными)
awk -F: 'NF==4 && $4!="" {n=split($4,a,","); if(n>1) print "Общая группа: " $1 " (члены: " $4 ")"}' /etc/group

# Делегирование прав через groupmems (проверка членов первичной группы)
while IFS=: read -r user _ uid gid _; do
    members=$(groupmems -g "$user" -l 2>/dev/null)
    if [ -n "$members" ]; then
        echo "Первичная группа $user ($user) делегирована: $members"
    fi
done < /etc/passwd
```

### Тренды (2025–2026)

Современный стандарт — **декларативное управление**. Утилита **`systemd-sysusers`** по умолчанию реализует логику UPG для системных аккаунтов (тип `u`), создавая пару пользователь-группа с идентичным ID. Это подтверждает жизнеспособность архитектуры UPG как метода минимизации привилегий.

В дистрибутивах на основе systemd (RHEL 9+, Debian 12+, Ubuntu 24.04+) наблюдается переход от императивных скриптов к:
- **JSON-профилям** `systemd-homed` для переносимых аккаунтов;
- **`sysusers.d/*.conf`** для reproducible-сборок образов;
- **`authselect`** для централизованного управления NSS/PAM в корпоративных средах.
