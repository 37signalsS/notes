# Приватные группы пользователей (UPG)

## Определения

- **UPG (User Private Groups)** — архитектурная схема организации групп в Linux, при которой для каждого нового пользователя автоматически создается персональная группа с идентичным именем и числовым идентификатором (UID = GID).
- **Первичная группа (Primary Group)** — группа, GID которой зафиксирован в `/etc/passwd`. Все файлы, создаваемые пользователем, по умолчанию наследуют идентификатор этой группы.
- **`umask` (User File-Creation Mask)** — системная битовая маска, определяющая права доступа, которые **запрещены** для новых файлов и директорий.
- **SGID (Set Group ID) на директорию** — специальный бит прав доступа (значение `2`), форсирующий наследование группы родительской директории для всех создаваемых внутри объектов.
- **USERGROUPS_ENAB** — параметр в `/etc/login.defs`, управляющий автоматическим созданием группы при создании пользователя и её удалением при ликвидации аккаунта.

## Базовые концепции

### Механизм работы и архитектурная цель UPG

Традиционная модель Unix использовала общие группы (например, `users` или `staff`) в качестве первичных. Это создавало дилемму безопасности:
1.  При `umask 022` файлы защищены от записи коллегами по группе, но совместная работа в общих папках требует ручного изменения прав (`chmod g+w`).
2.  При `umask 002` (права на запись для группы по умолчанию) файлы в домашних директориях пользователей становились уязвимы для всех членов общей группы `users`.

Схема UPG устраняет этот конфликт через связку **«Персональная группа + umask 002»**:
- Поскольку пользователь является единственным членом своей первичной группы, `umask 002` (права `rw-rw-r--`) абсолютно безопасен в его домашней директории — никто другой не входит в эту группу.
- При переходе в общую проектную директорию с установленным битом **SGID**, тот же `umask 002` позволяет пользователям мгновенно обмениваться файлами с правом на запись, так как новые файлы автоматически получают GID проекта, а не персональный GID создателя.

### Ключевые параметры конфигурации (/etc/login.defs)

Поведение подсистемы определяется в файле `/etc/login.defs`:

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| **`USERGROUPS_ENAB`** | `yes` | При создании пользователя `useradd` создаст группу с тем же именем. При удалении пользователя `userdel` удалит группу, если в ней нет других членов. |
| **`USERGROUPS_MOD`** | `002` | Если UID=GID, система использует `umask 002` вместо дефолтного `022`. Требует поддержки `pam_umask`. |
| **`SYS_GID_MIN`** / **`MAX`** | `100-999` | Диапазон GID для системных приватных групп (используется для изоляции сервисов). |

### Безопасность и изоляция сервисов

Использование UPG критично для серверной безопасности:
- **Разделение привилегий:** Каждый системный сервис (например, `nginx`, `postgres`) получает свою приватную группу.
- **Защита от латерального перемещения:** Компрометация одного сервиса не дает прав на запись в директории других сервисов через общие системные группы.

## Практические сценарии

### Диагностика и проверка состояния

```bash
# Проверка текущих идентификаторов и членства
id
# → uid=1001(alice) gid=1001(alice) groups=1001(alice),27(sudo)

# Проверка маски в текущей сессии
umask
# → 0002

# Проверка записей в системных базах (совпадение UID/GID)
grep "alice" /etc/passwd
# alice:x:1001:1001::/home/alice:/bin/bash

grep "alice" /etc/group
# alice:x:1001:
```

### Организация совместной работы (Модель UPG + SGID)

Это основной технический сценарий, ради которого внедрялась схема UPG.

```bash
# 1. Подготовка группы проекта и участников
sudo groupadd developers
sudo usermod -aG developers alice
sudo usermod -aG developers bob

# 2. Создание общей директории с правильными атрибутами
sudo mkdir -p /srv/shared_dev
sudo chown root:developers /srv/shared_dev

# 3. Установка SGID бита и прав доступа
# 2000 — SGID, 775 — rwxrwxr-x
sudo chmod 2775 /srv/shared_dev

# 4. Проверка совместной работы
# От имени alice:
touch /srv/shared_dev/config.yaml
# Файл автоматически получит группу developers и права -rw-rw-r--
# Bob сможет редактировать этот файл без дополнительных chmod/chgrp
```

### Продвинутая настройка: Использование Default ACL

Для гарантии прав записи при любом `umask` пользователя (например, если кто-то принудительно поставил `022` в `.bashrc`):

```bash
# Установка дефолтных прав на директорию
sudo setfacl -d -m g:developers:rwx /srv/shared_dev
sudo setfacl -m g:developers:rwx /srv/shared_dev
```

### Ручное управление и исключения

В некоторых случаях требуется обойти механизм UPG (например, при миграции со старых систем).

```bash
# Создание пользователя без приватной группы (флаг -N)
# Будет использована группа из /etc/default/useradd (обычно users/100)
sudo useradd -N legacy_user

# Создание пользователя с принудительным назначением конкретной группы
sudo useradd -g users common_user

# Отключение UPG глобально (в /etc/login.defs)
# USERGROUPS_ENAB no
```

### Взаимодействие с Rootless-контейнерами

В Docker/Podman (rootless) схема UPG расширяется через `/etc/subgid`:
- Каждый пользователь получает диапазон GID (например, 100000–165535).
- Эти ID используются для маппинга приватных групп внутри контейнера, сохраняя изоляцию на хосте.

### Автоматизация: Скрипт создания пользователя с проверкой UPG

```bash
#!/bin/bash
# create_user_safe.sh - автоматизация с учетом UPG

USERNAME=$1
COMMENT=$2

if [[ -z "$USERNAME" ]]; then
    echo "Использование: $0 <username> [комментарий]"
    exit 1
fi

# Проверка глобальной настройки
UPG_ENABLED=$(grep "^USERGROUPS_ENAB" /etc/login.defs | awk '{print $2}')
echo "Статус USERGROUPS_ENAB: $UPG_ENABLED"

# Создание пользователя
sudo useradd -m -c "$COMMENT" "$USERNAME"

# Техническая проверка результата
UID_VAL=$(id -u "$USERNAME")
GID_VAL=$(id -g "$USERNAME")

if [ "$UID_VAL" -eq "$GID_VAL" ]; then
    echo "OK: Схема UPG применена (UID $UID_VAL = GID $GID_VAL)"
else
    echo "WARNING: Схема UPG не сработала. UID($UID_VAL) != GID($GID_VAL)"
fi
```

## Дополнительная информация

### Технические рекомендации по применению

| Сценарий | Стратегия | Техническое обоснование |
| :--- | :--- | :--- |
| **Рабочие станции** | UPG + umask 002 | Изоляция личных данных + гибкость совместной работы. |
| **Серверы приложений** | UPG (для каждого сервиса) | Гарантирует, что логи сервиса A недоступны на запись сервису B. |
| **Файловые серверы** | UPG + SGID + ACL | Предотвращение «ада прав» при глубокой вложенности папок. |
| **Интеграция с доменом** | Отключение UPG | В AD/IPA используются централизованные GID; локальные UPG вызывают конфликты. |
| **systemd-homed** | JSON-профили | Сохраняет логику UPG, но делает её переносимой между хостами. |

### Инструменты аудита и поиска аномалий

```bash
# Поиск пользователей, у которых первичная группа не совпадает с именем пользователя
awk -F: '$1 != $4 {print "Аномалия: пользователь " $1 " имеет первичную группу " $4}' /etc/passwd

# Проверка групп в /etc/group, содержащих более одного участника (не являются приватными)
awk -F: 'NF==4 && $4!="" {n=split($4,a,","); if(n>1) print "Общая группа: " $1 " (члены: " $4 ")"}' /etc/group
```

### Тренды (2025–2026)

Современный стандарт — **декларативное управление**. Утилита **`systemd-sysusers`** по умолчанию реализует логику UPG для системных аккаунтов (тип `u`), создавая пару пользователь-группа с идентичным ID. Это подтверждает жизнеспособность архитектуры UPG как метода минимизации привилегий.
