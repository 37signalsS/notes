# Декларативное управление пользователями (systemd-sysusers)

## Определения

- **systemd-sysusers** — системная утилита и одноименная служба, предназначенные для создания системных пользователей и групп на основе декларативных конфигурационных файлов.
- **sysusers.d** — формат и набор директорий (`/usr/lib/sysusers.d/`, `/etc/sysusers.d/`), где хранятся описания необходимых пользователей.
- **systemd-userdbd** — сервис-агрегатор (2025–2026), объединяющий записи пользователей из различных источников (SSSD, homed, sysusers) в единый API через D-Bus.
- **Идемпотентность** — свойство утилиты, позволяющее запускать её многократно без риска дублирования записей или изменения уже корректно настроенных идентификаторов.
- **GECOS** — текстовое поле комментария в `/etc/passwd`, содержащее описание учетной записи.
- **Supplementary Groups** — дополнительные группы, в которые добавляется пользователь помимо первичной.
- **Dynamic User** — пользователь, чьи учетные данные существуют только в рантайме и не записываются в `/etc/passwd` (реализуется через `DynamicUser=yes` в unit-файлах systemd).
- **Golden Image** — эталонный образ ОС или контейнера, воспроизводимо разворачиваемый на множество узлов.

## Основные концепции

В отличие от традиционных императивных команд (`useradd`), `systemd-sysusers` реализует декларативный подход: администратор описывает *желаемое состояние* (какие пользователи должны быть), а система гарантирует их наличие.

### Архитектура и интеграция с systemd-userdbd

`systemd-sysusers` работает в паре с `systemd-userdbd.service`. Утилита создает и изменяет записи в локальных базах (`/etc/passwd`, `/etc/group`), а `systemd-userdbd` агрегирует их с данными из:

- Локальных файлов `/etc/passwd`, `/etc/group`
- **[systemd-homed](./systemd-homed.md)** (портативные JSON-записи на диске)
- **SSSD/LDAP** (сетевые каталоги)
- Динамических пользователей (`DynamicUser=yes` в unit-файлах)

Все потребители (NSS, PAM, утилиты `id`, `getent`) получают данные через единый D-Bus API, что обеспечивает консистентность даже при отсутствии физических записей в файлах на диске.

### Ключевые особенности (2025–2026)

1.  **Воспроизводимость:** Гарантирует идентичный набор системных аккаунтов на всех узлах кластера или в образах ОС.
2.  **Иммутабельность:** Основной инструмент для систем с неизменяемой корневой ФС (Fedora CoreOS, Silverblue, SteamOS), где `/etc/passwd` может быть защищен от прямой записи.
3.  **Отложенная инициализация:** Пользователи могут создаваться в момент первой загрузки (через `systemd-firstboot`) или при динамической установке пакетов.
4.  **Интеграция с пакетами:** Разработчики ПО поставляют `.conf` файлы вместе с бинарными файлами, избавляя скрипты установки от необходимости ручного вызова `useradd`.
5.  **Безопасность по умолчанию:** Создаваемые аккаунты автоматически получают заблокированный пароль (`!`) и оболочку `/usr/sbin/nologin`, если не указано иное.
6.  **Идемпотентность на уровне ядра:** Повторный запуск не изменяет существующие записи и не дублирует UID/GID.

### Механизм выбора идентификаторов

Утилита работает преимущественно в системном диапазоне (обычно UID < 1000). 

- **Автовыбор (`-`):** Если конкретный UID/GID не указан, `systemd-sysusers` выберет первый свободный номер, начиная **сверху** системного диапазона (например, 999, 998...). Это минимизирует конфликты с пользователями, созданными вручную в начале диапазона.
- **Синхронизация по пути (file path):** В поле ID можно указать абсолютный путь к файлу. В этом случае пользователь или группа получит ID, совпадающий с владельцем указанного файла. Это полезно при создании аккаунтов для доступа к конкретным ресурсам (например, сокетам или устройствам).
- **Диапазон (range):** Для резервирования поддерживается синтаксис `start-end` (например, `500-510`).

### Supplementary Groups (дополнительные группы)

Тип записи `m` добавляет существующего пользователя в указанную группу. Для назначения пользователя в несколько групп используйте отдельные строки `m` для каждой пары пользователь-группа.

### Взаимодействие с DynamicUser=

Unit-файлы systemd могут содержать директиву `DynamicUser=yes`. В этом случае `systemd-sysusers` не создает запись в `/etc/passwd`, а systemd управляет пользователем полностью в рантайме через cgroup и капсулы. Это исключительно для сервисов, которым не требуется стабильный UID между перезагрузками.

### NSS и PAM контекст

При наличии `systemd-userdbd` в `nsswitch.conf` порядок поиска может выглядеть так:

```bash
passwd: files systemd
group: files systemd
shadow: files
```

Это означает, что запросы к `id`, `getent passwd` сначала проверяют локальные файлы, затем — виртуальную базу systemd-userdbd, куда могут входить пользователи homed, SSSD и динамические аккаунты.

## Формат конфигурации

Файлы в `sysusers.d` состоят из строк, определяющих типы объектов и их атрибуты. Имена файлов должны оканчиваться на `.conf`. Пустые строки и строки, начинающиеся с `#`, игнорируются.

| Поле | Описание | Значение по умолчанию |
| :--- | :--- | :--- |
| **Type** | Тип записи (`u`, `g`, `m`, `r`). | — |
| **Name** | Имя пользователя или группы. | — |
| **ID** | UID/GID (число, диапазон `start-end`, `-` для автовыбора, путь к файлу, или список supplementary groups через запятую). | Автовыбор |
| **GECOS** | Описание (комментарий) в кавычках. | `System user/group` |
| **Home** | Домашняя директория. | `/` |
| **Shell** | Командная оболочка. | `/usr/sbin/nologin` |

### Типы записей

- **`u`**: Создать пользователя и первичную группу с тем же именем. Это стандартный тип для системных аккаунтов, автоматически реализующий архитектуру UPG (User Private Groups).
- **`g`**: Создать только группу.
- **`m`**: Добавить существующего пользователя в группу (членство).
- **`r`**: Зарезервировать диапазон UID/GID (предотвращает их автоматическое назначение другим пользователям).

### Именование и соглашения

- Системные пользователи и группы должны начинаться с подчеркивания (`_nginx`, `_postgres`).
- Имена чувствительны к регистру; используйте нижний регистр для совместимости с LDAP/AD.
- Длина имени: до 32 символов, латиница, цифры, дефис.

## Справочник CLI

```bash
systemd-sysusers [OPTIONS...] [CONFIGFILE...]
```

| Опция | Описание |
| :--- | :--- |
| `--cat-config` | Вывести объединенную конфигурацию из всех директорий в порядке приоритета. |
| `--dry-run` | Тестовый прогон без внесения изменений в систему. |
| `--root=PATH` | Выполнить операции в указанном корне (Offline Mode). Используется при сборке образов. |
| `--json=MODE` | Вывести результат в формате JSON (`short`, `pretty`). Полезно для автоматизации и CI. |
| `--scope=` | Ограничить обработку только указанной директорией (например, `--scope=/usr/lib/sysusers.d/`). |

## Практические сценарии

### 1. Создание пользователя для фонового сервиса

Создадим пользователя `_web-app` с выделенной домашней директорией и shell.

```bash
# /etc/sysusers.d/web-app.conf
u _web-app - "Web Application Service" /var/lib/web-app /bin/bash
```

### 2. Применение конфигурации и валидация

Хотя система применяет настройки при загрузке, администратор может сделать это вручную:

```bash
# Просмотр итоговой объединенной конфигурации
sudo systemd-sysusers --cat-config

# Проверка и создание (Verbose режим)
sudo systemd-sysusers --dry-run # Тестовый прогон без записи
sudo systemd-sysusers
# → Creating group _web-app with gid 975.
# → Creating user _web-app (Web Application Service) with uid 975 and gid 975.

# Проверка результата
id _web-app
```

### 3. Управление членством и резервированием

```bash
# /etc/sysusers.d/infra.conf
g _audit-logs - -
m _web-app _audit-logs
# Резервирование ID для легаси-совместимости
r _legacy-service 500-510
```

### 4. Подготовка образа (Offline Mode)

При создании контейнеров или образов ОС можно наполнить `/etc/passwd` без запуска самой системы:

```bash
sudo systemd-sysusers --root=/mnt/image_root/
```

### 5. GitOps и CI-валидация конфигураций

В конвейере CI проверяйте корректность `.conf` файлов до мержа:

```bash
#!/bin/bash
set -euo pipefail

# Создать временный корень для dry-run
TMPROOT=$(mktemp -d)

# Скопировать конфиги во временный корень
mkdir -p "$TMPROOT/etc/sysusers.d"
cp configs/sysusers.d/*.conf "$TMPROOT/etc/sysusers.d/"

# Проверить синтаксис
if ! systemd-sysusers --root="$TMPROOT" --dry-run; then
    echo "ОШИБКА: Некорректные конфигурации sysusers"
    exit 1
fi

echo "Конфигурации sysusers валидны"
```

### 6. Ansible-автоматизация

```yaml
- name: Развертывание системных пользователей через sysusers
  copy:
    dest: "/etc/sysusers.d/{{ item.name }}.conf"
    content: "{{ item.line }}"
    owner: root
    group: root
    mode: '0644'
  loop:
    - { name: 'prometheus', line: 'u _prometheus - "Prometheus Monitoring" /var/lib/prometheus /usr/sbin/nologin' }
    - { name: 'grafana', line: 'u _grafana - "Grafana Dashboard" /var/lib/grafana /usr/sbin/nologin' }

- name: Применение конфигураций sysusers
  command: systemd-sysusers
  register: sysusers_result
  changed_when: "'Creating' in sysusers_result.stdout"

- name: Проверка созданных пользователей
  command: id _prometheus
  changed_when: false
```

### 7. Миграция с useradd на systemd-sysusers

```bash
#!/bin/bash
# migrate_to_sysusers.sh — миграция существующих системных пользователей

# Экспорт существующих пользователей в sysusers формат
awk -F: '$3 < 1000 && $3 != 0 {print $1}' /etc/passwd | while read -r user; do
    entry=$(getent passwd "$user")
    uid=$(echo "$entry" | cut -d: -f3)
    gid=$(echo "$entry" | cut -d: -f4)
    gecos=$(echo "$entry" | cut -d: -f5)
    home=$(echo "$entry" | cut -d: -f6)
    shell=$(echo "$entry" | cut -d: -f7)
    
    # Генерация конфигурации
    cat <<EOF > "/etc/sysusers.d/migrated-${user}.conf"
u ${user} ${uid} "${gecos}" ${home} ${shell}
EOF
    
    # Удалить старого пользователя (оставив данные)
    # userdel -r "$user"  # Раскомментировать после проверки
done
```

### 8. Интеграция с systemd-firstboot

При первом запуске системы (например, в OEM-образах или виртуальных машинах) `systemd-firstboot` может создавать базовых пользователей на основе sysusers-конфигураций:

```bash
# Создание базового пользователя при первом запуске
sudo systemd-firstboot --create-accounts --root=/mnt/image_root
```

### 9. Проверка оркестрации (Kubernetes node provisioning)

При подготовке физических серверов или виртуальных машин для Kubernetes:

```bash
# Предусмотреть сервисных пользователей для container runtime и CNI плагинов
# /etc/sysusers.d/k8s.conf
u _containerd - "Container Runtime" /var/lib/containerd /usr/sbin/nologin
u _crio - "CRI-O Runtime" /var/lib/crio /usr/sbin/nologin

# После применения проверить UID стабильность (важно для volume permissions)
systemd-sysusers
id -u _containerd
```

### 10. Подготовка PXE/Preseed/Kickstart окружения

В автоматизированных сценариях развертывания (Preseed для Debian/Ubuntu, Kickstart для RHEL/Fedora) sysusers-конфигурации копируются в `${root}/etc/sysusers.d/` до первого запуска `systemd-sysusers`:

```bash
# Пример для kickstart %post секции
%post --log=/root/ks-post.log
# Копирование кастомных sysusers
cp /tmp/sysusers-custom/*.conf /etc/sysusers.d/
# Применение
/usr/bin/systemd-sysusers
%end
```

### 11. Создание пользователей в Dockerfile (для хоста)

В Dockerfile для контейнеров, где systemd работает как PID 1 (например, для CI-тестов Ansible):

```dockerfile
FROM ubuntu:24.04
RUN apt-get update && apt-get install -y systemd dbus
COPY sysusers.d/*.conf /etc/sysusers.d/
RUN systemd-sysusers
```

## Валидация и диагностика

### Проверка синтаксиса и целостности

```bash
# Просмотр объединенной конфигурации
sudo systemd-sysusers --cat-config

# JSON-вывод для парсинга
sudo systemd-sysusers --json=short

# Проверка наличия конфликтов с существующими записями
sudo systemd-sysusers --dry-run 2>&1 | grep -i 'already exists'

# Проверка права на запись в /etc (особенно для immutable OS)
sudo touch /etc/sysusers.d/test_write && rm /etc/sysusers.d/test_write
```

### Проверка NSS-интеграции

```bash
# Убедиться, что systemd-userdbd зарегистрирован в NSS
grep systemd /etc/nsswitch.conf
# → passwd: files systemd
# → group: files systemd

# Проверить, что утилиты видят пользователя
getent passwd _web-app
id _web-app

# Проверить D-Bus сервис
busctl --system list | grep userdb
```

### Верификация после создания

```bash
# Проверка записи в passwd/group
getent passwd _web-app
getent group _web-app

# Проверка членства в группах
id -nG _web-app

# Проверка домашней директории (если не systemd-tmpfiles)
ls -ld /var/lib/web-app
```

### Проверка идемпотентности

```bash
# Двойной запуск не должен изменять существующие записи
sudo systemd-sysusers
sudo systemd-sysusers
# → Второй запуск не выводит сообщений "Creating"
```

## Диагностика и устранение неполадок

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `Permission denied` при запуске | Отсутствуют права root или `/etc` на read-only FS. | Запустите через `sudo`; для immutable OS используйте `/etc` overlay. |
| `sysusers.d/` не обрабатывается | Отсутствует `systemd-sysusers.service` или он disabled. | Проверьте `systemctl status systemd-sysusers.service`. |
| Пользователь существует, но не виден в `id` | NSS не содержит `systemd` или `systemd-userdbd` не запущен. | Проверьте `nsswitch.conf` и `systemctl status systemd-userdbd`. |
| Дубликат UID после `useradd` | Ручное создание конфликтует с автовыбором sysusers. | Используйте `systemd-sysusers` как источник правды; удалите дубликат. |
| `sysusers.conf` не применяется после boot | Файл некорректного формата или синтаксическая ошибка. | Проверьте `journalctl -u systemd-sysusers -b`. |
| Маскировка не работает | Файл в `/etc/sysusers.d/` не пустой или имеет другое имя. | Убедитесь, что файл точно совпадает по имени и является пустым. |
| Supplementary groups не применяются | Используется тип `u` вместо `m`, или группы еще не созданы. | Создайте группы через тип `g` или `m` перед добавлением членов. |

### Просмотр логов

```bash
# Логи systemd-sysusers за текущую загрузку
journalctl -u systemd-sysusers -b

# Постоянный мониторинг
journalctl -u systemd-sysusers -f
```

## Безопасность и соответствие

### Рекомендации по hardening

1.  **Оболочка и пароли:** Всегда указывайте `/usr/sbin/nologin` для сервисных аккаунтов. Поле пароля автоматически заполняется значком `!`, предотвращающим аутентификацию.
2.  **Именование:** Используйте префикс `_` для визуального отделения системных аккаунтов от человеческих. Это снижает риск случайного использования сервисного аккаунта для входа.
3.  **Минимальные привилегии:** Создавайте отдельного пользователя для каждого сервиса. Не запускайте несколько сервисов от одного аккаунта.
4.  **Права на конфигурации:** Файлы в `/etc/sysusers.d/` должны иметь права `0644` и принадлежать `root:root`. Изменение прав может привести к игнорированию или переопределению.
5.  **Иммутабельность:** На системах с неизменяемой корневой ФС размещайте кастомные конфигурации в `/etc/sysusers.d/` (перекрывающие `/usr/lib/`), а не редактируйте системные файлы.
6.  **Аудит:** Периодически сверяйте фактические записи в `/etc/passwd` с декларативными конфигурациями:

```bash
# Поиск системных пользователей, не управляемых sysusers
comm -23 \
    <(awk -F: '$3 < 1000 && $3 != 0 {print $1}' /etc/passwd | sort) \
    <(find /usr/lib/sysusers.d /etc/sysusers.d -name '*.conf' -exec grep -h '^u' {} \; | awk '{print $2}' | sort)
```

### Соответствие требованиям

- **Traceability:** D-Bus API `systemd-userdbd` позволяет получать полный список пользователей и их источников для аудита.
- **Reproducibility:** Декларативные файлы можно хранить в Git, обеспечивая追溯мость изменений.
- **Isolation:** Каждый сервисный аккаунт с уникальным UID позволяет применять Mandatory Access Control (SELinux, AppArmor) на уровне пользователя.

## Миграция и обратная совместимость

### Миграция с useradd / groupadd

При переходе на декларативный подход:

1. **Инвентаризация:** Создайте перечень всех системных пользователей (`awk -F: '$3 < 1000 && $3 != 0' /etc/passwd`).
2. **Генерация конфигураций:** Преобразуйте существующие записи в формат sysusers.
3. **Тестирование:** Примените конфигурации в staging-среде и проверьте идемпотентность.
4. **Развертывание:** Разместите файлы в `/etc/sysusers.d/` на production.
5. **Очистка:** Удалите ручные скрипты `useradd` из пост-инсталляционных хуков пакетов (они конфликтуют с sysusers).

### Откат

Если необходимо вернуться к императивному подходу:

1. Удалите или переместите `.conf` файлы из `/etc/sysusers.d/`.
2. Используйте `userdel`/`groupdel` для удаления ненужных аккаунтов.
3. Восстановите скрипты установки пакетов.

**Важно:** Удаление `.conf` файла **не удаляет** уже созданного пользователя автоматически. Это защита от случайной потери данных.

## Взаимодействие с systemd-tmpfiles

`systemd-sysusers` только создает записи в базе данных пользователей (`/etc/passwd`, `/etc/group`). Он **не создает** физические директории. Для создания домашних папок с правильными правами (`chown`) необходимо использовать **[systemd-tmpfiles](../../Core/systemd/tmpfiles.md)**.

Типичная комбинация для полной инициализации окружения сервиса:

```bash
# /usr/lib/sysusers.d/myapp.conf
u _myapp - "My Application" /var/lib/myapp /usr/sbin/nologin

# /usr/lib/tmpfiles.d/myapp.conf
d /var/lib/myapp 0750 _myapp _myapp -
```

## Сравнение подходов

| Критерий | useradd (Императивный) | systemd-sysusers (Декларативный) |
| :--- | :--- | :--- |
| **Место вызова** | Скрипты, Post-install шаги | Статические конфигурационные файлы |
| **Удаление** | `userdel` удаляет запись | Удаление `.conf` **не удаляет** пользователя автоматически |
| **Идемпотентность** | Требует ручных проверок (`id user \|\| ...`) | Встроена на уровне архитектуры |
| **Целостность** | Риск "загрязнения" системы | Идеально для GitOps и CI/CD |
| **Воспроизводимость** | Зависит от порядка выполнения скриптов | Гарантирована на всех узлах |
| **Иммутабельность** | Требует прав на запись в `/etc` | Работает через overlay на immutable OS |
| **Валидация** | Post-hoc проверки (`id`, `getent`) | `--dry-run` и `--cat-config` до применения |

## Дополнительная информация

### Иерархия, приоритеты и Маскировка

Systemd обрабатывает файлы в лексикографическом порядке из следующих директорий:

1.  `/usr/lib/sysusers.d/` — настройки от дистрибутива и пакетов (не изменять).
2.  `/run/sysusers.d/` — временные настройки (создаваемые в рантайме).
3.  `/etc/sysusers.d/` — локальные настройки администратора (**наивысший приоритет**).

**Маскировка (Masking):** Если создать в `/etc/sysusers.d/` пустой файл с тем же именем, что и в `/usr/lib/`, системное правило будет полностью отключено.

### Новое в версиях 255 и 256

- **Поддержка `.v/` директорий:** `systemd-sysusers` теперь поддерживает версионированные директории, автоматически выбирая наиболее подходящую версию конфигурации для текущего ядра или релиза ОС.
- **Интеграция с systemd-repart:** Декларативно созданные пользователи могут быть использованы в `repart.d` для установки владельца создаваемых разделов диска.
- **JSON-вывод:** Добавлен флаг `--json=` для интеграции с инструментами автоматизации и валидации.

### Производительность и масштабирование

- **Пакетная обработка:** `systemd-sysusers` обрабатывает все файлы за одну транзакцию, минимизируя обращения к диску.
- **Кэширование NSS:** `systemd-userdbd` кэширует результаты, снижая нагрузку на D-Bus при массовых запросах (`id`, `getent`).
- **Ограничения:** Для систем с >1000 сервисными аккаунтов рекомендуется мониторить время выполнения `systemd-sysusers` и размер базы NSS.

### Политика поддержки дистрибутивами

| Дистрибутив | systemd-sysusers как дефолт | Примечание |
| :--- | :--- | :--- |
| Fedora (38+) | Да | Полный переход на декларативное управление |
| RHEL/CentOS Stream (9+) | Да | Рекомендуется для rpm-пакетов |
| Debian (12+) | Да | Используется для системных пользователей |
| Ubuntu (22.04+) | Да | `_apt`, `_runtime` создаются через sysusers |
| Arch Linux | Да | Полная интеграция с pacman |
