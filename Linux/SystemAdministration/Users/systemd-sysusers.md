# Декларативное управление пользователями (systemd-sysusers)

## Определения

- **systemd-sysusers** — системная утилита и одноименная служба, предназначенные для создания системных пользователей и групп на основе декларативных конфигурационных файлов.
- **sysusers.d** — формат и набор директорий (`/usr/lib/sysusers.d/`, `/etc/sysusers.d/`), где хранятся описания необходимых пользователей.
- **systemd-userdbd** — сервис-агрегатор (2025–2026), объединяющий записи пользователей из различных источников (SSSD, homed, sysusers) в единый API через D-Bus.
- **Идемпотентность** — свойство утилиты, позволяющее запускать её многократно без риска дублирования записей или изменения уже корректно настроенных идентификаторов.

## Основные концепции

В отличие от традиционных императивных команд (`useradd`), `systemd-sysusers` реализует декларативный подход: администратор описывает *желаемое состояние* (какие пользователи должны быть), а система гарантирует их наличие.

### Ключевые особенности (2025–2026)
1.  **Воспроизводимость:** Гарантирует идентичный набор системных аккаунтов на всех узлах кластера или в образах ОС.
2.  **Иммутабельность:** Основной инструмент для систем с неизменяемой корневой ФС (Fedora CoreOS, Silverblue, SteamOS), где `/etc/passwd` может быть защищен от прямой записи.
3.  **Отложенная инициализация:** Пользователи могут создаваться в момент первой загрузки (через `systemd-firstboot`) или при динамической установке пакетов.
4.  **Интеграция с пакетами:** Разработчики ПО поставляют `.conf` файлы вместе с бинарными файлами, избавляя скрипты установки от необходимости ручного вызова `useradd`.
5.  **Безопасность по умолчанию:** Создаваемые аккаунты автоматически получают заблокированный пароль (`!`) и оболочку `/usr/sbin/nologin`, если не указано иное.

### Механизм выбора идентификаторов
Утилита работает преимущественно в системном диапазоне (обычно UID < 1000). 
- **Автовыбор:** Если конкретный UID не указан (`-`), `systemd-sysusers` выберет первый свободный номер, начиная **сверху** диапазона (например, 999, 998...). Это минимизирует конфликты с пользователями, созданными вручную в начале диапазона.
- **Синхронизация по пути:** В поле ID можно указать путь к файлу. В этом случае пользователь получит UID, совпадающий с владельцем указанного файла.

## Формат конфигурации

Файлы в `sysusers.d` состоят из строк, определяющих типы объектов и их атрибуты.

| Поле | Описание | Значение по умолчанию |
| :--- | :--- | :--- |
| **Type** | Тип записи (`u`, `g`, `m`, `r`). | — |
| **Name** | Имя пользователя или группы. | — |
| **ID** | UID/GID (число, диапазон, `-` для автовыбора, или путь к файлу). | Автовыбор |
| **GECOS** | Описание (комментарий) в кавычках. | `System user/group` |
| **Home** | Домашняя директория. | `/` |
| **Shell** | Командная оболочка. | `/usr/sbin/nologin` |

### Типы записей
- **`u`**: Создать пользователя и первичную группу с тем же именем.
- **`g`**: Создать только группу.
- **`m`**: Добавить существующего пользователя в группу (членство).
- **`r`**: Зарезервировать диапазон UID/GID (предотвращает их автоматическое назначение другим пользователям).

## Практические сценарии

### 1. Создание пользователя для фонового сервиса
Создадим пользователя `_web-app` с выделенной домашней директорией и shell.

```bash
# /etc/sysusers.d/web-app.conf
u _web-app - "Web Application Service" /var/lib/web-app /bin/bash
```

### 2. Применение конфигурации и валидация
Хотя система применяет настройки при загрузке, администратор может сделать это вручную:

```bash
# Просмотр итоговой объединенной конфигурации
sudo systemd-sysusers --cat-config

# Проверка и создание (Verbose режим)
sudo systemd-sysusers --dry-run # Тестовый прогон без записи
sudo systemd-sysusers
# → Creating group _web-app with gid 975.
# → Creating user _web-app (Web Application Service) with uid 975 and gid 975.

# Проверка результата
id _web-app
```

### 3. Управление членством и резервирование
```bash
# /etc/sysusers.d/infra.conf
g _audit-logs - -
m _web-app _audit-logs
# Резервирование ID для легаси-совместимости
r _legacy-service 500-510
```

### 4. Подготовка образа (Offline Mode)
При создании контейнеров или образов ОС можно наполнить `/etc/passwd` без запуска самой системы:
```bash
sudo systemd-sysusers --root=/mnt/image_root/
```

## Дополнительная информация

### Иерархия, приоритеты и Маскировка
Systemd обрабатывает файлы в лексикографическом порядке из следующих директорий:
1.  `/usr/lib/sysusers.d/` — настройки от дистрибутива и пакетов (не изменять).
2.  `/run/sysusers.d/` — временные настройки (создаваемые в рантайме).
3.  `/etc/sysusers.d/` — локальные настройки администратора (**наивысший приоритет**).

**Маскировка (Masking):** Если создать в `/etc/sysusers.d/` пустой файл с тем же именем, что и в `/usr/lib/`, системное правило будет полностью отключено.

### Новое в версиях 255 и 256
- **Поддержка `.v/` директорий:** `systemd-sysusers` теперь поддерживает версионированные директории, автоматически выбирая наиболее подходящую версию конфигурации для текущего ядра или релиза ОС.
- **Интеграция с systemd-repart:** Декларативно созданные пользователи могут быть использованы в `repart.d` для установки владельца создаваемых разделов диска.

### Взаимодействие с systemd-tmpfiles
`systemd-sysusers` только создает записи в базе данных пользователей (`/etc/passwd`, `/etc/group`). Он **не создает** физические директории. Для создания домашних папок с правильными правами (`chown`) необходимо использовать **[systemd-tmpfiles](../../Core/systemd/tmpfiles.md)**.

### Сравнение подходов

| Критерий | useradd (Императивный) | systemd-sysusers (Декларативный) |
| :--- | :--- | :--- |
| **Место вызова** | Скрипты, Post-install шаги | Статические конфигурационные файлы |
| **Удаление** | `userdel` удаляет запись | Удаление `.conf` **не удаляет** пользователя автоматически |
| **Идемпотентность** | Требует ручных проверок (`id user || ...`) | Встроена на уровне архитектуры |
| **Целостность** | Риск "загрязнения" системы | Идеально для GitOps и CI/CD |
