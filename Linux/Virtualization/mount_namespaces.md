# Пространства имён монтирования (Mount Namespaces)

В данном файле рассматриваются механизмы изоляции файловых систем в Linux с использованием **Mount Namespaces** и управление распространением событий монтирования (**Mount Propagation**). Общий обзор всех типов пространств имен доступен в [Пространства имён (namespaces)](../Core/namespaces.md).

## Определения

**Mount namespace (`CLONE_NEWNS`)** — первое пространство имен, появившееся в Linux (2002 год). Оно изолирует таблицу точек монтирования, видимую группой процессов. Это позволяет процессам иметь собственный вид иерархии файловой системы (например, подменять `/tmp` или `/proc` без влияния на хост).

**Mount propagation (Распространение монтирования)** — механизм, определяющий, как события монтирования или размонтирования (`mount`/`umount`) «путешествуют» между пространствами имен. Без этого механизма создание нового namespace приводило бы к полной статической изоляции, что мешало бы, например, автоматическому монтированию USB-дисков во все контейнеры.

**Shared Subtree (Разделяемые поддеревья)** — технология, позволяющая объединять точки монтирования в группы для обмена событиями.

**Peer group (Группа равных)** — группа точек монтирования, которые являются зеркалами друг друга. Любое событие в одной точке группы автоматически повторяется во всех остальных точках этой группы.

**Bind mount (Монтирование с привязкой)** — создание альтернативного пути доступа к уже смонтированной директории или файлу.

## Базовые концепции

### Группы Peer Groups и идентификация

Для отслеживания связей между пространствами имен ядро использует идентификаторы групп. Их можно увидеть в `/proc/self/mountinfo`:

- **`shared:X`**: Точка монтирования является частью peer group с ID `X`. Она отправляет и получает события.
- **`master:X`**: Точка является «рабом» (slave) группы `X`. Она только получает события от мастеров группы `X`, но не отправляет свои.

### Флаги распространения монтирования (Propagation flags)

Тип распространения определяется флагами при выполнении операции монтирования:

| Флаг | Поведение | Направление распространения |
| :--- | :--- | :--- |
| **`MS_SHARED`** | События распространяются на все точки монтирования в рамках peer group. | Двустороннее (Parent ↔ Child) |
| **`MS_PRIVATE`** | События монтирования внутри этой точки не выходят за пределы namespace. | Изолированное (по умолчанию) |
| **`MS_SLAVE`** | Точка получает события от «мастера» (parent), но не отправляет свои события обратно. | Одностороннее (Parent → Child) |
| **MS_UNBINDABLE** | Точка монтирования, которую запрещено использовать в качестве источника для bind mount. | — |

### Таблица взаимодействия Parent и Child

Поведение при выполнении монтирования в зависимости от флагов (при условии, что Child является копией Parent):

| Флаг у Child | Операция в Parent | Операция в Child | Результат |
| :--- | :--- | :--- | :--- |
| **private** | `mount /dev/sdb /mnt` | — | Child **не видит** `/mnt` |
| **private** | — | `mount /dev/sdc /data` | Parent **не видит** `/data` |
| **shared** | `mount /dev/sdb /mnt` | — | Child **видит** `/mnt` (и наоборот) |
| **slave** | `mount /dev/sdb /mnt` | — | Child **видит** `/mnt` |
| **slave** | — | `mount /dev/sdc /data` | Parent **не видит** `/data` |

### Наследование при создании namespace

При вызове `clone(CLONE_NEWNS)` или `unshare --mount`:

1. Новый namespace получает точную копию таблицы монтирования родителя.
2. Вместе с точками монтирования копируются их флаги распространения (propagation flags).
3. Дальнейшая изоляция зависит от того, были ли точки помечены как `shared`, `private` или `slave` в родительском namespace.

### Механизмы смены корня: chroot vs pivot_root

Для создания полноценного контейнера недостаточно просто изолировать точки монтирования, нужно сменить корневую директорию.

- **`chroot`**: Меняет корень для текущего процесса. **Небезопасно**, так как процесс может «выпрыгнуть» из chroot, используя `..` или открытые файловые дескрипторы директорий вне chroot. Не отмонтирует старый корень.
- **`pivot_root`**: Перемещает текущую корневую ФС в другую директорию и делает новую директорию новым корнем. Это позволяет **полностью отмонтировать** старую корневую ФС, делая невозможным доступ к ресурсам хоста. Используется во всех современных рантаймах (Docker, LXC).

## Диагностика и анализ

### Формат /proc/[pid]/mountinfo

Это основной источник истины о состоянии пространств имен. Каждая строка содержит:
`ID parent-ID major:minor root mount-point options [optional-fields] separator fs-type source super-options`

**Пример (peer group):**
`156 35 8:1 / /shared-dir rw,relatime shared:1 - ext4 /dev/sda1 rw`
- `shared:1` — точка входит в peer group #1.

**Пример (slave):**
`157 35 8:1 / /slave-dir rw,relatime master:1 - ext4 /dev/sda1 rw`
- `master:1` — точка получает события от группы #1, но не шлет свои.

### Инструменты управления

```bash
# Просмотр всех точек монтирования с деревом зависимостей
findmnt --tree

# Создание нового namespace и запуск в нем оболочки
unshare --mount /bin/bash

# Выполнение команды в namespace другого процесса
nsenter -t <PID> -m <command>
```

## Практические сценарии

### Изоляция в системных службах (systemd)

`systemd` активно использует Mount Namespaces для повышения безопасности служб (Sandboxing).

Параметры в юнит-файле (`[Service]`):
- **`MountFlags=shared|slave|private`**: Управляет propagation для всего namespace службы. Обычно используется `slave`, чтобы служба видела монтирования хоста, но не могла на них влиять.
- **`ReadOnlyPaths=` / `InaccessiblePaths=`**: systemd создает новый mount namespace и монтирует указанные пути как Read-Only или пустые директории.
- **`PrivateTmp=yes`**: Создает изолированные `/tmp` и `/var/tmp` через mount namespace.

### Взаимодействие с Docker и Kubernetes

Docker и K8s используют `Mount Propagation` для управления томами:

- **`None` (`private`)**: Изменения внутри контейнера не видны на хосте, и наоборот (после старта контейнера).
- **`HostToContainer` (`rslave`)**: Контейнер видит новые монтирования, сделанные на хосте внутри этого тома.
- **`Bidirectional` (`rshared`)**: Изменения синхронизируются в обе стороны. Требуется для запуска контейнеров-хранилищ (например, GlusterFS, Ceph), которые монтируют диски для использования хостом.

## Дополнительная информация

### Системные вызовы ядра

| Вызов | Назначение |
| :--- | :--- |
| `clone(CLONE_NEWNS, ...)` | Создание нового процесса в новом mount namespace. |
| `unshare(CLONE_NEWNS)` | Вывод текущего процесса в новое пространство имен монтирования. |
| `setns(fd, CLONE_NEWNS)` | Присоединение процесса к существующему mount namespace. |
| `mount(..., MS_REC | MS_SHARED, ...)` | Изменение флагов распространения для точки монтирования. |
| `pivot_root(new_root, put_old)` | Атомарная смена корневой файловой системы. |
