# Образы ВМ — Основные концепции

В данном файле рассматриваются стратегии организации дискового пространства для виртуальных машин (ВМ), архитектурные подходы к хранению данных, внутреннее строение форматов и механизмы оптимизации производительности. Глоссарий терминов доступен в [Образы ВМ — Определения](./definitions.md).

## Способы организации хранилища

Выбор метода доступа к данным определяет баланс между производительностью I/O, гибкостью управления и возможностями масштабирования.

### 1. Файловые образы (File-based)
Виртуальный диск представлен в виде файла (`.qcow2`, `.raw`) в файловой системе хоста.
- **Преимущества:** Простота резервного копирования (копирование файла), поддержка цепочек снапшотов, легкая миграция.
- **Особенности:** Зависимость от производительности и фрагментации файловой системы хоста (ext4, XFS, ZFS).

### 2. Прямой блочный доступ (Block Device Passthrough)
Проброс физического диска, раздела или LVM-тома напрямую в ВМ.
- **Преимущества:** Минимальные задержки (отсутствие слоя ФС хоста), прямой доступ к аппаратным функциям.
- **Недостатки:** Сложность «живой» миграции, риск конфликтов при доступе к одному устройству со стороны хоста и гостя.

### 3. Сетевые блочные устройства (Network Block Storage)
Использование протоколов iSCSI, Fibre Channel или распределенных систем (Ceph RBD).
- **Преимущества:** Высокая доступность (HA), независимость данных от конкретного узла, централизованное управление.
- **Сценарии:** Корпоративные кластеры и облачные платформы.

### Критерии выбора метода хранилища

| Критерий | Файловые образы | Прямой блок | Сетевое хранилище |
| :--- | :--- | :--- | :--- |
| **Производительность** | Средняя (зависит от ФС хоста) | Максимальная | Зависит от сети |
| **Миграция** | Простая (копирование файла) | Сложная | Прозрачная (shared storage) |
| **Снапшоты** | Встроенные (qcow2) | Требуют LVM/блочный уровень | Зависят от бэкенда |
| **Сложность управления** | Низкая | Средняя | Высокая |
| **Рекомендуемый сценарий** | Разработка, тестирование, шаблоны | Базы данных, высоконагруженные сервисы | Кластеры, HA-среды |

## Форматы виртуальных дисков

| Формат | Поддержка | Особенности |
| :--- | :--- | :--- |
| **`raw`** | Все гипервизоры | Максимальная скорость. Нет метаданных. Поддерживает Sparse-файлы. |
| **`qcow2`** | KVM / QEMU | Поддержка снапшотов, CoW, сжатия (zstd), шифрования (LUKS) и динамического расширения. |
| **`vmdk`** | VMware / ESXi | Стандарт для корпоративного сегмента. Поддерживается в KVM через конвертацию. |
| **`vhdx`** | Hyper-V | Поддержка дисков до 64 ТБ, устойчивость к сбоям питания через логирование метаданных. |

### Особенности формата qcow2 (v3)
Современный стандарт `qcow2` в QEMU 5.1+ и выше (актуально для 2024–2026 гг.) включает:
- **Тип сжатия zstd:** Значительно превосходит `zlib` по скорости декомпрессии (до 5 раз быстрее), что ускоряет запуск ВМ из сжатых образов.
- **Шифрование LUKS:** Встроенная поддержка шифрования на уровне блоков внутри образа.
- **Extended L2 Tables:** Оптимизация для работы с очень большими образами и разреженными данными.

### Внутреннее строение формата qcow2

Понимание внутренней структуры формата необходимо для диагностики проблем производительности и планирования емкости.

**Структура на диске:**
- **Заголовок (Header):** 96 байт, содержит magic (`QFI\xfb`), версию, виртуальный размер, размер кластера, флаги (encryption, compression).
- **L1-таблица:** Указатель на L2-таблицы. Хранится в метаданных, не в данных.
- **L2-таблицы:** Карта кластеров образа. Каждая запись указывает на физический кластер данных или на следующий уровень CoW.
- **Refcount-блоки:** Счетчики ссылок на кластеры. Критичны для безопасного удаления снапшотов и consolidation.
- **Данные:** Фактические кластеры виртуального диска (по умолчанию 64 КБ каждый).

**Размер кластера:**
- По умолчанию: 64 КБ (оптимальный баланс для большинства workloads).
- До 2 МБ: для workloads с большими последовательными операциями (базы данных, видео).
- Влияние: меньший кластер = меньше внутренней фрагментации, больше накладных расходов на L2-таблицы.

**Производительные последствия:**
- При последовательном чтении QEMU должен проходить через L1 → L2 → данные. Длинные цепочки увеличивают латентность на наносекунды на каждый уровень, но при больших I/O это может суммироваться.
- Refcount-блоки обновляются при каждой записи CoW, что добавляет overhead на случайные записи.

### Sparse-файлы и hole punching

Формат `raw` и разреженные области `qcow2` используют механизм sparse-файлов файловой системы хоста.

**Как это работает:**
- Последовательности нулевых байтов не записываются на диск, а только в метаданные файла.
- Фактический размер файла (`actual-size`) может значительно отличаться от виртуального (`virtual-size`).

**Hole punching:**
```bash
# Просмотр разреженных областей (требуется ядро 5.1+ с FIBMAP)
filefrag -v disk.qcow2

# Обнуление свободного пространства внутри образа для последующего сжатия
virt-sparsify --inplace --compress disk.qcow2
```

**Взаимодействие с ФС хоста:**
- ext4/XFS/Btrfs поддерживают sparse-файлы нативно.
- При удалении данных внутри ВМ файл на хосте не уменьшается автоматически — требуется `virt-sparsify` или `fstrim` внутри гостя + `discard=unmap` в конфигурации диска.

## Интерфейсы ввода-вывода (Virtio)

Выбор драйвера контроллера определяет функциональность и предел производительности I/O.

### Virtio-blk
Оптимизированный драйвер блочного устройства с минимальным стеком обработки.
- **Плюсы:** Наивысшая производительность для одиночных дисков, минимальные задержки (latency).
- **Минусы:** Ограниченная масштабируемость (каждый диск занимает PCI-слот), отсутствие поддержки сложных SCSI-команд.
- **Современность (QEMU 9.0+):** Поддержка `iothread-vq-mapping` позволяет распределять очереди одного диска между несколькими потоками (IOThreads) хоста.

### Virtio-scsi
Промышленный стандарт для сложных конфигураций.
- **Плюсы:** Огромная масштабируемость (тысячи дисков на один контроллер), поддержка SCSI UNMAP (для TRIM), SCSI Reservations (для кластеров).
- **Минусы:** Чуть больший оверхед стека по сравнению с blk (нивелируется в современных версиях).
- **Рекомендация:** Использование режима `virtio-scsi-single` обеспечивает баланс между изоляцией ресурсов и функциональностью SCSI.

### Выбор шины диска по сценарию

| Сценарий | Шина | Обоснование |
| :--- | :--- | :--- |
| **Одиночный диск, максимальная скорость** | `virtio-blk` | Минимальный оверхед, прямой доступ к блокам. |
| **Несколько дисков (>4)** | `virtio-scsi` | Один контроллер на все диски, поддержка UNMAP. |
| **Кластерные ФС (OCFS2, GFS2)** | `virtio-scsi` | Требуется SCSI Persistent Reservations. |
| **Legacy ОС без Virtio-драйверов** | `IDE` / `SATA` | Совместимость, низкая производительность. |

## Механизмы оптимизации и управления

### Тонкое выделение и TRIM/Discard
**Thin Provisioning** позволяет выделять виртуальный объем (напр. 100 ГБ), фактически занимая лишь 1 ГБ.
- **Проблема:** При удалении файлов внутри ВМ файл-образ на хосте не уменьшается автоматически.
- **Решение:** Механизм **Discard/TRIM**. Гостевая ОС отправляет сигнал о неиспользуемых блоках, гипервизор освобождает их. Требует контроллера с поддержкой UNMAP (рекомендуется `virtio-scsi`) и опции `-drive ...,discard=unmap`.

### Практические ограничения thin provisioning

**Overcommit:**
- При создании диска 100 ГБ на хранилище 50 ГБ ВМ работает до первого заполнения.
- При переполнении все гости на этом хранилище получают `No space left on device`, что может привести к повреждению ФС.
- **Безопасный overcommit:** не превышать 150–200% от физического объема без активного мониторинга.

**Мониторинг:**
```bash
# Пороговое значение для алертинга
ALERT_THRESHOLD=85

# Проверка заполнения пула
df -h /var/lib/libvirt/images | awk -v thresh=$ALERT_THRESHOLD '
NR==2 {
  gsub(/%/, "", $5);
  if ($5 > thresh) {
    print "CRITICAL: Storage pool usage is " $5 "%";
    exit 1
  }
}'
```

### Режимы кэширования (Caching Modes)
- **`none`:** Кэш хоста игнорируется, используется прямой ввод-вывод (O_DIRECT). Рекомендуется для большинства рабочих нагрузок.
- **`writethrough`:** Запись подтверждается только после фиксации на физическом носителе. Максимальная безопасность, низкая скорость.
- **`writeback`:** Подтверждение сразу после записи в кэш хоста. Высокая скорость, риск потери данных при сбое.

### Взаимодействие кэша хоста и гостевой ОС

Проблема двойного кэширования возникает при использовании режимов `writeback` или `writethrough`:
1. Гостевая ОС записывает данные в свой файловый кэш.
2. Гипервизор кэширует запись в кэш страниц ядра хоста.
3. Данные физически записываются на диск.

При `cache=none` (рекомендуется для баз данных) оба кэша пропускаются, что исключает двойное кэширование и снижает латентность.

### Уровни асинхронного ввода-вывода (AIO)
- **Native:** Использование нативного Linux AIO. Эффективно, но требует `cache=none`.
- **io_uring:** Стандарт 2024–2026 годов. Обеспечивает минимальный оверхед на системные вызовы через разделяемые кольцевые буферы. Значительно ускоряет IOPS на NVMe-накопителях.

### Планировщик I/O хоста и его влияние на ВМ

Планировщик ядра хоста управляет очередью запросов к блочным устройствам. При неправильном выборе ВМ могут испытывать лишние задержки.

**Доступные планировщики:**
- **`mq-deadline` (по умолчанию на многих дистрибутивах):** Стандартный планировщик с fair queuing. Хорошо подходит для смешанных workloads.
- **`bfq` (Budget Fair Queuing):** Предназначен для настольных систем и workstation. Обеспечивает низкую латентность для интерактивных задач, но может снижать общую пропускную способность.
- **`none`:** Отключение планировщика на уровне ядра. Прямая передача запросов устройству. Рекомендуется для NVMe и высоконагруженных SSD, когда libvirt управляет throttling через `iotune`.

**Рекомендации:**
```bash
# Проверка текущего планировщика
cat /sys/block/nvme0n1/queue/scheduler
# → [mq-deadline] none bfq

# Для NVMe в продакшн обычно достаточно 'none'
echo none | sudo tee /sys/block/nvme0n1/queue/scheduler

# Постоянная настройка через tuned
sudo tuned-adm profile virtual-host
```

### Предварительное выделение (Preallocation)
- **`metadata`:** Создает структуру метаданных заранее. Снижает фрагментацию при сохранении экономии места.
- **`falloc` / `full`:** Резервирует все физическое пространство. Исключает задержки при первом обращении к блоку.

**Взаимодействие с ФС хоста:**
- `falloc` использует `fallocate(2)` и работает только на файловых системах, поддерживающих punched holes (ext4, XFS, Btrfs, tmpfs). На FAT/NTFS (если используется) игнорируется и эквивалентен `full`.
- `metadata` безопасно для всех ФС.

## Жизненный цикл данных и снапшоты

### Copy-on-Write (CoW) и цепочки образов
Механизм CoW лежит в основе снапшотов и связанных клонов:
1. Базовый образ (Backing File) открыт только для чтения.
2. Все записи идут в новый слой (Delta).
3. При чтении: если данных нет в Delta, они считываются из Backing File.
4. **Оптимизация:** Длинные цепочки (`backing chains`) замедляют чтение. Рекомендуется периодическое выполнение `block-stream` для консолидации данных.

### Read amplification в длинных цепочках

При каждом чтении блока, отсутствующего в текущем слое, QEMU последовательно опрашивает все базовые файлы цепочки. При 4–6 уровнях это добавляет 5–10 мкс латентности на операцию. При глубине >10 уровней может возникнуть заметное снижение пропускной способности.

### Dirty flag и безопасное отключение

Флаг `dirty-flag` в заголовке qcow2 указывает, что образ не был корректно закрыт (например, при `kill -9` или отключении питания).
- **Проверка:** `qemu-img info disk.qcow2` покажет `dirty-flag: true`.
- **Восстановление:** `qemu-img check -r all disk.qcow2` исправляет inconsistencies в refcount-блоках и L2-таблицах.
- **Профилактика:** Всегда используйте `virsh shutdown` вместо `virsh destroy`, чтобы гостевая ОС успела сбросить кэш и закрыть файлы.

## Прямой проброс дисков (NVMe/PCIe Passthrough)

Вместо эмуляции контроллера и драйвера virtio, физическое блочное устройство напрямую передается в ВМ через VFIO.

**Когда использовать:**
- Высоконагруженные базы данных на NVMe, где каждая микросекунда латентности важна.
- Специализированное оборудование (NVMe с высокой IOPS, SAS-диски).
- Работа с данными, требующими максимальной пропускной способности без оверхеда виртуализации.

**Недостатки:**
- Нет возможности «живой» миграции.
- Устройство занято одной ВМ на время работы.
- Требует включенного IOMMU (VT-d/AMD-Vi) и драйвера `vfio-pci`.

**Альтернатива:** Для большинства production workloads `virtio-blk` с `io_uring` и `cache=none` дает 95–99% производительности прямого доступа при сохранении гибкости управления.

## Влияние файловой системы хоста на производительность и надежность

Выбор файловой системы для директории с образами ВМ критически влияет на стабильность и скорость работы.

### ext4
- **Преимущества:** Стабильность, широкое тестирование, быстрый mount.
- **Недостатки:** Фрагментация разреженных файлов (qcow2/raw sparse) со временем растет, особенно при динамическом расширении.
- **Рекомендация:** Подходит для большинства задач. Используйте `e4defrag` для periodic дефрагментации хостового файла образа (ВМ должна быть выключена).

### XFS
- **Преимущества:** Лучшая масштабируемость на больших файлах (>100 ГБ), отложенное выделение (delayed allocation) уменьшает фрагментацию sparse-файлов.
- **Недостатки:** Дефрагментация offline сложнее, чем у ext4.
- **Рекомендация:** Предпочтительна для хранилищ с большими образами и высокой нагрузкой на запись.

### ZFS
- **Преимущества:** End-to-end checksumming (обнаружение silent data corruption), сжатие lz4/zstd на уровне пула, снапшоты без участия qcow2.
- **Недостатки:** Высокое потребление RAM (минимум 8–16 ГБ на пул), сложность tuning.
- **Рекомендация:** Для HA-сред и критичных данных, где целостность важнее максимальной скорости.

### Btrfs
- **Преимущества:** Поддержка снапшотов и сжатия, аналогичная ZFS.
- **Недостатки:** В 2026 году для production VM images на одном диске считается технологическим превью (стабильность ниже, чем у ZFS/ext4).
- **Рекомендация:** Только для тестовых сред или если требуется snapshot-ы на уровне ФС без дополнительных инструментов.

## Изменение размера дисков

Расширение диска ВМ включает два этапа: изменение виртуального размера образа и расширение раздела/ФС внутри гостя.

### Offline-изменение (ВМ выключена)

```bash
# 1. Увеличение файла qcow2
qemu-img resize web-server.qcow2 +20G
# → Image resized.

# 2. Замена диска в XML (если используется libvirt)
virsh edit web-server-01
# Измените <target dev='vda' bus='virtio'/> — размер обновится автоматически

# 3. Запуск ВМ и расширение ФС внутри гостя
# Внутри гостя (Linux):
sudo growpart /dev/vda 1
sudo resize2fs /dev/vda1
```

### Онлайн-изменение (hot-resize)

```bash
# 1. Увеличение тома в пуле libvirt (ВМ работает)
virsh vol-resize default web-server-01.qcow2 40G --pool default

# 2. Внутри гостя (требуется virtio-blk и recent kernel):
echo 1 | sudo tee /sys/class/block/vda/device/rescan

# 3. Расширение раздела и ФС
sudo growpart /dev/vda 1
sudo resize2fs /dev/vda1
```

## Валидация и тестирование хранилища

Перед вводом хранилища в эксплуатацию и при диагностике проблем производительности выполните тестирование.

### Проверка целостности образа

```bash
# Проверка метаданных (только чтение)
qemu-img check web-server.qcow2
# → No errors were found on the image.

# Восстановление при ошибках
qemu-img check -r all web-server.qcow2
# → Repairing broken clusters...
```

### Тестирование производительности (fio)

```bash
# Последовательные чтение/запись (4K block, 1MiB depth)
fio --name=seq-read --rw=read --bs=1M --iodepth=32 --size=1G --filename=/dev/nvme0n1

# Случайный чтение/запись (4K, 100% mixed, typical VM workload)
fio --name=rand-rw --rw=randrw --bs=4k --iodepth=16 --size=1G --filename=/var/lib/libvirt/images/test.qcow2

# Оценка latency (p99, p999)
fio --name=latency --rw=randread --bs=4k --iodepth=1 --size=1G --filename=/var/lib/libvirt/images/test.qcow2 --output-format=json
```

### Проверка фрагментации хоста

```bash
# Для ext4 (требует e2fsprogs)
sudo e2fsck -T -f /dev/nvme0n1

# Внутри гостевой ОС (Linux):
sudo e4defrag -c /dev/vda1
```

## Безопасность и шифрование

### Шифрование образа (LUKS внутри qcow2)

Хранение чувствительных данных (логи, кэши) внутри образа в зашифрованном виде.

```bash
# Создание зашифрованного qcow2 (LUKS)
qemu-img create -f qcow2 \
  --object secret,id=sec0,data=$(openssl rand -base64 32) \
  -o encrypt.format=luks,encrypt.key-secret=sec0 \
  secure-disk.qcow2 20G

# Информация о зашифрованном образе
qemu-img info --object secret,id=sec0,data=MyPassword123 secure-disk.qcow2
```

**Влияние на производительность:**
- Шифрование добавляет ~5–15% overhead на CPU (зависит от размера блока и наличия AES-NI).
- Для CPU-intensive workloads на хосте используйте отдельный thread pool или аппаратное ускорение.

### Атрибуты только для чтения

Защита шаблонов от случайного изменения:
```bash
chattr +i /var/lib/libvirt/images/ubuntu-24.04-template.qcow2
# Для отключения:
chattr -i /var/lib/libvirt/images/ubuntu-24.04-template.qcow2
```
