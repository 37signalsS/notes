# Диагностика и решение проблем KVM

В данном файле рассматриваются методы выявления и устранения типовых проблем при работе с KVM: деградация производительности, ошибки миграции и некорректная настройка устройств. Архитектурные основы эмуляции описаны в [KVM — Обзор и архитектура](./overview.md).

## Определения

**TCG (Tiny Code Generator)** — механизм программной трансляции инструкций QEMU. Используется как резервный метод при невозможности аппаратного ускорения KVM. Подробнее: [Архитектура QEMU/KVM](./overview.md#взаимодействие-qemu-и-kvm).

**CPU Mode** — конфигурация проброса функций физического процессора в виртуальную машину. Влияет на производительность и возможность «живой» миграции.

**Живая миграция (Live Migration)** — процесс переноса работающей ВМ между физическими хостами без остановки гостевой операционной системы.

## Базовые концепции

### Причины деградации производительности

| Симптом | Вероятная причина | Инструмент диагностики |
| :--- | :--- | :--- |
| Резкое падение FPS/отклика | Откат на TCG-эмуляцию | `virsh dominfo`, логи QEMU |
| Отсутствие поддержки инструкций (AES, AVX) | Неоптимальный CPU Mode | `virsh capabilities` |
| Медленный ввод-вывод (I/O) | Использование эмуляции вместо virtio | `virsh dumpxml` |

### Режимы CPU в libvirt

| Режим | Описание | Совместимость |
| :--- | :--- | :--- |
| **`host-passthrough`** | Полный проброс CPU хоста | Только идентичные процессоры |
| **`host-model`** | Проброс максимально возможного набора функций | Гетерогенные кластеры (разные CPU) |
| **`custom`** | Выбор конкретной модели (напр. `Haswell`) | Максимальная стабильность миграции |

### Механизм отката на TCG (Fallback)

Если при запуске или миграции KVM не может обеспечить запрошенные функции процессора, QEMU может автоматически переключиться в режим программной эмуляции (TCG). Это приводит к снижению производительности в десятки и сотни раз.

**Признак проблемы в логах (`/var/log/libvirt/qemu/<имя_вм>.log`):**

```text
kvm: host doesn't support requested feature...
falling back to tcg
```

## Практические сценарии

### Сценарий 1: Исправление производительности после миграции

Если после переноса ВМ стала работать медленно, необходимо проверить режим работы CPU.

**1. Проверка текущего состояния:**

```bash
virsh dominfo <имя_вм> | grep "CPU mode"
# → Ожидаемый результат: host-passthrough или host-model
# → Признак проблемы: custom (qemu64, kvm64)
```

**2. Анализ поддержки KVM на целевом хосте:**
Подробные инструкции по проверке аппаратной поддержки приведены в [Установка KVM — Проверка](./installation.md#сценарий-1-проверка-поддержки-аппаратной-виртуализации).

**3. Смена режима в конфигурации:**

```bash
virsh edit <имя_вм>
```

В секции `<cpu>` установите рекомендуемый режим:

```xml
<cpu mode='host-model' check='partial'/>
```

### Сценарий 2: ВМ не запускается (ошибки совместимости)

При попытке запуска ВМ на другом хосте может возникнуть ошибка несоответствия ресурсов.

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `CPU model not found` | Целевой хост слабее исходного | Сменить `passthrough` на `host-model` |
| `Network bridge not found` | Разные имена мостов на хостах | Создать мост с идентичным именем (напр. `br0`) |
| `Permission denied` | Ошибки доступа к образу | Проверить владельца файла и права (группа `libvirt`) |

### Сценарий 3: Диагностика производительности I/O

Если диск или сеть работают медленно, убедитесь, что включена паравиртуализация.

**Проверка использования virtio:**

```bash
virsh dumpxml <имя_вм> | grep -E "model.*virtio"
```

Если в выводе отсутствуют упоминания `virtio`, необходимо изменить модель устройства в XML-конфигурации или через `virt-manager`. Подробнее о преимуществах механизма: [KVM — Virtio](./overview.md#паравиртуализация-virtio).
