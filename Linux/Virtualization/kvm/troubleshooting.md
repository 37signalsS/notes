# Диагностика и решение проблем KVM

В данном файле рассматриваются методы выявления и устранения типовых проблем при работе с KVM: деградация производительности, ошибки прав доступа (MAC), проблемы управления и сетевые сбои. Архитектурные основы эмуляции описаны в [KVM — Обзор и архитектура](./overview.md).

## Термины и концепции диагностики

Основные определения (KVM, QEMU, CPU Mode) представлены в разделе **[KVM — Обзор и архитектура](./overview.md#определения)**. Для глубокой диагностики важны следующие понятия:

**sVirt (Secure Virtualization)** — технология интеграции гипервизора с системами мандатного управления доступом (AppArmor, SELinux). Позволяет изолировать процессы каждой ВМ на уровне ядра.

**QEMU Guest Agent (QGA)** — демон, работающий внутри гостевой ОС. Обеспечивает выполнение команд хоста (заморозка ФС, получение IP, сброс пароля) через специальный канал (virtio-serial).

**VM-Exit** — событие выхода процессора из режима выполнения гостевого кода в режим гипервизора. Большое количество VM-Exit свидетельствует о неоптимальной эмуляции.

## Базовые концепции

### Основные источники диагностической информации

| Ресурс | Путь / Команда | Описание |
| :--- | :--- | :--- |
| **Логи конкретной ВМ** | `/var/log/libvirt/qemu/<имя_вм>.log` | Вывод процесса QEMU, ошибки эмуляции и устройств. |
| **Системный журнал** | `journalctl -u libvirtd` | Ошибки демона управления, проблемы с мостами и хранилищами. |
| **Аудит безопасности** | `dmesg | grep -iE 'apparmor|selinux'` | Блокировки доступа к файлам образов или сокетам. |
| **Статистика домена** | `virsh domstats <имя_вм>` | Метрики использования CPU, RAM, I/O и сети. |

### Механизм отката на TCG (Fallback)

Если аппаратное ускорение KVM недоступно (например, из-за настроек BIOS или вложенной виртуализации), QEMU может автоматически переключиться в режим **TCG (Tiny Code Generator)**.
**Признак проблемы:** Процессор хоста загружен на 100%, но внутри ВМ всё работает крайне медленно. В логах ВМ присутствует строка: `falling back to tcg`.

## Практические сценарии

### Сценарий 1: Исправление ошибок прав доступа (Permission Denied)

Даже при наличии прав на уровне файловой системы (chmod/chown), AppArmor или SELinux могут блокировать доступ QEMU к образам дисков.

**1. Диагностика:**
Если ВМ не запускается с ошибкой `Permission denied`, проверьте системный журнал на наличие блокировок MAC-системы.

**2. Решение для AppArmor (Ubuntu/Debian):**
Если образы лежат вне `/var/lib/libvirt/images`, добавьте путь в исключения:
```bash
# Добавление пути в пользовательский конфиг
echo '/mnt/storage/vms/** rwk,' | sudo tee /etc/apparmor.d/abstractions/libvirt-qemu.d/custom-paths
sudo systemctl restart apparmor
```

**3. Решение для SELinux (RHEL/CentOS/Fedora):**
Установите правильный контекст безопасности для файлов образов:
```bash
sudo semanage fcontext -a -t virt_image_t "/mnt/storage/vms(/.*)?"
sudo restorecon -Rv /mnt/storage/vms
```

### Сценарий 2: Исправление работы консоли (virsh console)

Если команда `virsh console` подключается, но не отображает вывод, значит гостевая ОС не настроена для вывода в последовательный порт.

**Настройка гостя (Linux):**
Отредактируйте `/etc/default/grub` внутри виртуальной машины:
```text
GRUB_CMDLINE_LINUX_DEFAULT="console=tty0 console=ttyS0,115200n8"
```
Выполните `sudo update-grub` и перезагрузитесь. Теперь вывод ядра и приглашение входа будут доступны через `virsh`.

### Сценарий 3: Проблемы с QEMU Guest Agent

Если команды вроде `virsh domifaddr` или `virsh shutdown` (в режиме агента) не работают.

**1. Проверка наличия канала в XML:**
```xml
<channel type='unix'>
  <target type='virtio' name='org.qemu.guest_agent.0'/>
</channel>
```

**2. Установка и запуск в госте:**
- **Linux:** `sudo apt install qemu-guest-agent && sudo systemctl enable --now qemu-guest-agent`
- **Windows:** Установите `virtio-win-guest-tools` из официального ISO-образа драйверов.

### Сценарий 4: Исправление производительности дисков/сети

Если наблюдается высокая задержка или низкая пропускная способность.

**1. Проверка использования virtio:**
```bash
virsh dumpxml <имя_вм> | grep -E "model.*virtio"
```
**2. Активация vhost:**
Для сетевых интерфейсов убедитесь, что включен ядерный драйвер `vhost-net`. Подробнее: [Архитектура KVM — Ускорение I/O](./overview.md#паравиртуализация-virtio-и-ускорение-io).
