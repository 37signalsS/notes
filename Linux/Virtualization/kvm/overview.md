# KVM — Обзор и архитектура

В данном файле описывается архитектура KVM (Kernel-based Virtual Machine), взаимодействие с QEMU и механизм virtio. Общие принципы виртуализации (типы гипервизоров, контейнеры против ВМ) представлены в [Виртуализация: Обзор](../virtualization_overview.md).

## Определения

**KVM (Kernel-based Virtual Machine)** — модуль ядра Linux, обеспечивающий инфраструктуру для аппаратной виртуализации. Превращает ядро в гипервизор 1-го типа (bare-metal), позволяя гостевым операционным системам выполнять инструкции напрямую на физическом процессоре (CPU) через расширения Intel VT-x или AMD-V.

**QEMU (Quick Emulator)** — эмулятор и виртуализатор с открытым исходным кодом. В связке с KVM отвечает за эмуляцию периферийных устройств (диски, сеть, PCI), в то время как KVM обеспечивает высокопроизводительное выполнение кода гостя. Может работать и без KVM в режиме **TCG (Tiny Code Generator)** — программной трансляции инструкций, что значительно медленнее.

**libvirt** — стандартный уровень абстракции (API), демон `libvirtd` и набор инструментов (`virsh`, `virt-install`) для управления виртуализацией. Позволяет работать с ВМ единообразно независимо от гипервизора (KVM, Xen, LXC).

**Virtio** — стандарт паравиртуализированных драйверов для оптимизации операций ввода-вывода (I/O). Вместо полной эмуляции оборудования использует механизм обмена данными через общую память (virtqueues).

**CPU Mode** — конфигурация проброса функций физического процессора в виртуальную машину. Влияет на производительность и возможность «живой» миграции.

**sVirt (Secure Virtualization)** — технология интеграции гипервизора с системами мандатного управления доступом (SELinux, AppArmor) для изоляции процессов ВМ друг от друга и от хоста.

**Живая миграция (Live Migration)** — процесс переноса работающей ВМ между физическими хостами без остановки гостевой операционной системы.

## Базовые концепции

### Взаимодействие QEMU и KVM

KVM и QEMU дополняют друг друга, создавая полноценную среду виртуализации. Взаимодействие происходит через файл устройства `/dev/kvm` с использованием системных вызовов (ioctl).

| Компонент | Роль | Функции |
| :--- | :--- | :--- |
| **KVM** | Гипервизор (ядро) | Выполнение инструкций CPU гостя, управление памятью (EPT/NPT), обработка прерываний. |
| **QEMU** | Эмулятор (userspace) | Эмуляция чипсета, шин (PCIe), устройств ввода-вывода и управление жизненным циклом ВМ. |

**Механизм работы:**
1. QEMU открывает `/dev/kvm`.
2. С помощью ioctl `KVM_CREATE_VM` создается контекст виртуальной машины.
3. Команда `KVM_RUN` переключает процессор в режим выполнения гостевого кода (VM-Entry).
4. При возникновении события, которое KVM не может обработать самостоятельно (например, доступ к эмулируемому порту I/O), происходит выход в userspace (VM-Exit), и QEMU обрабатывает запрос.

### Архитектура и процессная модель QEMU

QEMU работает как пользовательский процесс, который управляет виртуальной машиной через взаимодействие с модулем KVM. Понимание его внутренней структуры важно для диагностики производительности.

**Процессная модель:**
- **Основной поток QEMU:** Отвечает за обработку VM-Exit, эмуляцию устройств, управление жизненным циклом ВМ и взаимодействие с libvirt через QMP (QEMU Machine Protocol) на сокете `/var/run/libvirt/qemu/<domain>.xml`.
- **Потоки vCPU:** Для каждого виртуального процессора создается отдельный поток, который выполняет бесконечный цикл `KVM_RUN`. При VM-Exits поток возвращается в основной контекст.
- **IOThreads (QEMU I/O потоки):** Выделенные потоки для обработки операций ввода-вывода дисков и сети. Позволяют распараллелить обработку запросов, снижая нагрузку на основной поток и уменьшая задержки. Привязываются к физическим ядрам хоста через `cputune`.
- **Поток эмулятора (Emulator Thread):** Обрабатывает устройства, которые не могут быть обработаны в контексте vCPU (например, таймеры, ACPI). Рекомендуется изолировать его на отдельные ядра через `<emulatorpin>`.

**Интерфейс управления QMP:**
QEMU exposes JSON-based интерфейс QMP на Unix-сокете или TCP-порту для программного управления. Libvirt использует его для выполнения команд (пауза, старт, изменение конфигурации). Пример подключения:
```bash
echo '{"execute": "qmp_capabilities"}' | sudo socat - /var/run/libvirt/qemu/<domain>.sock
```

### Подробнее о libvirt

Хотя libvirt упомянут в определениях, его архитектурная роль заслуживает отдельного рассмотрения в контексте KVM.

**Компоненты:**
- **libvirtd (daemon):** Центральный процесс, работающий как системный сервис. Открывает Unix-сокет `/var/run/libvirt/libvirt-sock` и, при включенной удаленной активации, TCP-порт 16509 (TLS) или 16508 (TCP). Обрабатывает аутентификацию, авторизацию (polkit, SASL) и маршрутизацию запросов к драйверам.
- **Драйверы:** Модульная архитектура. Для KVM используется драйвер `QEMU`, который общается с QEMU через QMP. Также существуют драйверы для Xen, LXC, VMware.
- **URI (Uniform Resource Identifier):** Определяет, к какому гипервизору подключаться:
  - `qemu:///system` — локальный системный демон (основной для KVM).
  - `qemu+tcp://host/system` — удаленный доступ по TCP (не рекомендуется без TLS).
  - `qemu+ssh://host/system` — удаленный доступ через SSH.

**Инструменты:**
- `virsh` — основная CLI-утилита для управления доменами. Поддерживает интерактивный режим и пакетное выполнение скриптов.
- `virt-install` — утилита для автоматизированного развертывания новых ВМ. Поддерживает установку из ISO, сетевых репозиториев и автоматическую настройку через `cloud-init`.
- `virt-xml` — инструмент для изменения XML-конфигурации ВМ с помощью CLI-параметров без необходимости ручного редактирования файлов.
- `virt-clone` — создание клона существующей ВМ с новым уникальным идентификатором и MAC-адресом.

**Хранилище и сети libvirt:**
- **Storage Pool:** Логическое пространство (директория, LVM-группа, iSCSI-target, NFS-экспорт), в котором размещаются образы дисков. Подробнее: [Образы ВМ — Форматы и утилиты](../vm_images/definitions.md).
- **Storage Volume:** Виртуальный диск (обычно файл `qcow2` или LVM LV) внутри пула.
- **Virtual Network:** Программный коммутатор (Bridge, NAT, Isolated), через который ВМ обмениваются трафиком.

### Кольца защиты и аппаратное ускорение

Благодаря технологиям Intel VT-x и AMD-V, KVM вводит дополнительный уровень привилегий — **VMX Root Mode** (часто называемый Ring -1).
- **Хост (KVM):** Работает в VMX Root Mode.
- **Гость (Ядро ОС):** Думает, что работает в Ring 0, но фактически выполняется в VMX Non-Root Mode, что позволяет гипервизору перехватывать критические инструкции.

Подробнее о механизме колец защиты: [Виртуализация: Кольца защиты](../virtualization_overview.md#кольца-защиты-protection-rings).

### Паравиртуализация Virtio и ускорение I/O

Для минимизации накладных расходов на VM-Exit при операциях ввода-вывода используются механизмы паравиртуализации и разгрузки (offloading):

1. **vhost-net:** Перенос обработки сетевых пакетов Virtio из userspace (QEMU) напрямую в ядро Linux. Это исключает лишние переключения контекста между ядром и пользователем.
2. **vhost-user:** Позволяет QEMU взаимодействовать с высокопроизводительными сетевыми стеками в пространстве пользователя (например, DPDK) через Unix Domain Sockets.
3. **io_uring:** Современный интерфейс асинхронного I/O в Linux, который QEMU использует для эффективной работы с дисковыми образами, снижая нагрузку на CPU при интенсивных операциях записи/чтения.
4. **vDPA (VirtIO Data Path Acceleration):** Проброс аппаратного ускорения Virtio (например, в SmartNIC) напрямую в гостевую ОС, сохраняя при этом стандартный интерфейс драйверов Virtio.

**Основные типы устройств Virtio:**
- `virtio-net`: Сетевой адаптер.
- `virtio-blk` / `virtio-scsi`: Дисковые контроллеры.
- `virtio-fs`: Современный механизм совместного использования файлов между хостом и гостем (быстрее и надежнее, чем virtio-9p).
- `virtio-balloon`: Динамическое управление оперативной памятью гостя.
- `virtio-rng`: Проброс энтропии (генератора случайных чисел) с хоста.

### Хранилище: бэкенды и режимы кэширования

Выбор бэкенда хранения и режима кэширования напрямую влияет на производительность, безопасность данных и возможность миграции.

**Файловые образы (qcow2/raw):**
- **qcow2** — основной формат KVM. Поддерживает динамическое расширение, снапшоты, сжатие (zstd) и шифрование (LUKS). Ведет себя как разреженный файл (sparse file), увеличиваясь по мере записи данных.
- **raw** — простой побайтовый образ без метаданных. Максимальная скорость, но отсутствуют возможности CoW и снапшотов на уровне формата.

**Режимы кэширования (drive cache):**
- **`none` (O_DIRECT):** Прямой ввод-вывод, минуя кэш страниц ядра хоста. Рекомендуется для большинства рабочих нагрузок, особенно баз данных. Исключает двойное кэширование (хост + гость).
- **`writeback`:** Данные записываются в кэш хоста и подтверждаются гостевым ОС сразу. Высокая скорость, но риск потери данных при сбое питания хоста.
- **`writethrough`:** Запись подтверждается только после фиксации на физическом носителе. Максимальная безопасность, низкая скорость.
- **`directsync`:** Компромисс между `none` и `writeback`. Использует кэш QEMU, но не кэш страниц ядра. Подходит для workloads с высокой нагрузкой на запись, где важен баланс скорости и надежности.

**Прямой блочный доступ (Block Device Passthrough):**
Проброс физического диска, раздела или LVM-тома напрямую в ВМ.
- **Преимущества:** Минимальные задержки (отсутствие слоя ФС хоста).
- **Недостатки:** Сложность «живой» миграции, риск конфликтов при одновременном доступе.
- **Сценарии:** Базы данных на выделенных дисках, высоконагруженные логические тома.

**Сетевые блочные устройства (iSCSI, Ceph RBD, NBD):**
Используются в корпоративных кластерах для централизованного хранения. Подробнее об архитектуре сетевых хранилищ: [Образы ВМ — Основные концепции](../vm_images/basic_concepts.md).

### Сетевые архитектуры и бэкенды

Virtio-net является стандартным драйвером сети, но выбор бэкенда определяет производительность и функциональность.

**Типы виртуальных сетей libvirt:**
- **NAT (Default):** ВМ находятся в изолированной подсети, выход во внешний мир осуществляется через NAT хоста. Автоматически включает firewall и DHCP.
- **Bridge (Мост):** ВМ подключается напрямую к физическому сетевому сегменту хоста. Позволяет ВМ иметь IP из той же сети, что и хост. Подробнее: [Linux Bridge: Концепции](../../Networking/Concepts/linux_bridge.md).
- **Isolated:** Трафик разрешен только между ВМ внутри этой сети и хостом. Используется для изолированных сервисных сегментов.

**Сетевые устройства и бэкенды:**
- **virtio-net (состояние 2026):** Поддерживает Multi-Queue (MQ), multiqueue vhost, и offloading (TSO, GSO). Количество очередей должно соответствовать количеству vCPU для максимальной пропускной способности.
- **macvtap:** Позволяет ВМ подключаться напрямую к физическому интерфейсу хоста в режиме bridge, bypassing linux bridge. Эффективно для высоконагруженных сетевых workloads.
- **vhost-user:** Используется для high-performance userspace networking (DPDK, OVS-DPDK). Обмен данными через Unix Domain Sockets.
- **SR-IOV (Single Root I/O Virtualization):** Создание виртуальных функций (VF) сетевой карты для ВМ. Достигает производительности уровня bare-metal. Требует поддержки VT-d/AMD-Vi (IOMMU).

### Топология CPU, NUMA и планировщик ядер

На современных процессорах (AMD EPYC Turin, Intel Granite Rapids) топология играет критическую роль в производительности ВМ.

**Структура ВМ в libvirt (CPU topology):**
В XML-конфигурации ВМ топология CPU задается через:
```xml
<cpu mode='host-passthrough'>
  <topology sockets='1' dies='1' clusters='1' cores='8' threads='2'/>
</cpu>
```
- **sockets:** Количество физических процессоров, видимых гостем.
- **cores:** Количество ядер на сокет.
- **threads:** Количество потоков (SMT) на ядро.
- **check='none':** Отключает проверку совместимости топологии при миграции, полезно для гетерогенных кластеров.

**NUMA (Non-Uniform Memory Access):**
В NUMA-системах время доступа к памяти зависит от физического расположения памяти относительно ядер CPU. В современных чиплетных процессорах эффекты NUMA возникают даже внутри одного сокета (AMD CCD, Intel tiles).
- **numatune:** Секция XML, привязывающая память ВМ к конкретному NUMA-узлу хоста.
- **vCPU pinning:** Жесткое закрепление vCPU за физическими ядрами (pCPU) внутри одного NUMA-узла для минимизации задержек межъядерного взаимодействия.

**Параметры ядра хоста для изоляции:**
- **`isolcpus`:** Исключает указанные ядра из планировщика Linux для ручного управления. Используется для ВМ с жесткими требованиями к задержкам.
- **`nohz_full`:** Отключает периодические прерывания планировщика на указанных ядрах, снижая джиттер для latency-sensitive workloads.

### Миграция виртуальных машин (Live Migration)

Миграция позволяет перенести работающую ВМ между хостами без остановки. Процесс involves сохранение состояния памяти, регистров CPU и состояния устройств, передачу их по сети и возобновление выполнения на целевом хосте.

**Методы миграции:**
- **Pre-copy (по умолчанию):** Гипервизор итеративно передает измененные страницы памяти пока ВМ работает. При достижении порога изменения (<10% страниц за итерацию) происходит краткая остановка и финальная передача.
- **Post-copy:** ВМ сначала останавливается, передается минимальный набор состояний, и запускается на целевом хосте. Оставшиеся страницы подгружаются по demand с исходного хоста. Минимизирует общее время миграции, но требует надежной низко задержочной сети.
- **Auto-converge:** Если guest пишет в память быстрее, чем она передается (migration does not converge), гипервизор замедляет vCPU гостя, чтобы снизить скорость изменения памяти.

**Протоколы:**
- **ssh:** Безопасный, но с накладными расходами шифрования. Подходит для редких миграций.
- **tcp:** Быстрый, не требует шифрования. Используется внутри доверенных кластеров.
- **rdma:** Минимальная задержка для высокопроизводительных кластеров (требует специализированной сетевой карты и драйверов).

**Ограничения:**
- ВМ с устройствами, состояние которых нельзя передать (например, GPU через VFIO), не поддерживают live migration.
- Режим `host-passthrough` ограничивает миграцию хостами с одинаковым CPU.

### Управление памятью гостя (Ballooning и Hotplug)

**Virtio-balloon:**
Драйвер `virtio-balloon` позволяет гипервизору динамически запрашивать возврат неиспользуемой памяти гостевой ОС. Это критично для перераспределения памяти между ВМ в условиях недетерминированной нагрузки.

**Принцип работы:**
1. ВМ загружается с запасом памяти (например, 4 ГБ из 8 ГБ доступных).
2. При дефиците памяти на других ВМ, гипервизор "надувает" balloon, заставляя гостевую ОС освободить страницы.
3. Освобожденные страницы возвращаются в пул хоста и могут быть выделены другим ВМ.

**Memory Hotplug:**
Позволяет увеличивать объем RAM работающей ВМ без перезагрузки. Требует наличия `qemu-guest-agent` и поддержки hotplug в гостевом ядре.

### Watchdog и автоматический перезапуск

Watchdog — механизм мониторинга "зависания" гостевой ОС. Если ВМ перестает отвечать на heartbeat, гипервизор выполняет заранее настроенное действие.

**Реализация в KVM:**
- Используется виртуальное устройство `i6300esb` (Intel watchdog).
- В XML конфигурации:
```xml
<devices>
  <watchdog model='i6300esb' action='poweroff'/>
</devices>
```

**Действия (action):**
- `poweroff`: Выключение ВМ.
- `reset`: Перезагрузка ВМ.
- `shutdown`: Корректное выключение (требует guest-agent).
- `pause`: Приостановка выполнения (для диагностики).

**Интеграция с HA:** В кластерных средах (Pacemaker/Corosync) watchdog часто используется в комбинации с `fence_virt` или `fence_xvm` для гарантированного отключения "мертвого" узла при split-brain.

### Консоль и удаленный доступ (SPICE/VNC/Serial)

Для управления ВМ без графического рабочего стола используются виртуальные консоли.

**Типы графических интерфейсов:**
- **VNC (Virtual Network Computing):** Стандартный протокол. Доступен по умолчанию. Поддерживается всеми клиентами.
- **SPICE (Simple Protocol for Independent Computing Environments):** Более производительный протокол от Red Hat. Поддерживает двухнаправленный аудио, буфер обмена, смарткарты. Предпочтителен для интерактивной работы.
- **none:** Только serial console. Используется для headless серверов и автоматизации.

**Serial Console:**
Асинхронный последовательный порт, доступный через `virsh console <domain>` или сетевые соединения (telnet, TCP). Подходит для headless ВМ, диагностики загрузки и автоматизации.

**Virtio-serial:**
Паравиртуализированный канал связи между хостом и гостем. Используется для:
- QEMU Guest Agent (основной канал).
- Передачи файлов (virtio-serial port).
- Сторонних агентов мониторинга.

### QEMU Guest Agent (QGA)

Демон `qemu-ga` (QEMU Guest Agent) запускается внутри гостевой ОС и обеспечивает bidirectional связь с гипервизором через канал `virtio-serial`.

**Ключевые возможности:**
- **`guest-fsfreeze-freeze` / `guest-fsfreeze-thaw`:** Заморозка/разморозка файловых систем гостя для создания консистентных снапшотов.
- **`guest-get-host-name`:** Получение имени хоста.
- **`guest-get-users`:** Получение списка активных пользователей в гостевой ОС.
- **`guest-get-osinfo`:** Получение информации об ОС (версия, архитектура).
- **`guest-set-user-password`:** Смена пароля пользователя.
- **`guest-set-time`:** Синхронизация времени с хостом.

**Установка в гостевой ОС:**
- **Debian/Ubuntu:** `apt install qemu-guest-agent`
- **RHEL/CentOS:** `dnf install qemu-guest-agent`
- **Windows:** Устанавливается через virtio-win ISO или интегрируется в golden image.

**Проверка работоспособности:**
```bash
virsh domifaddr <domain> --source agent
# → Должен вернуть IP-адреса гостевой ОС.
```

### IOMMU и прямой проброс PCI (VFIO)

IOMMU (Input-Output Memory Management Unit) — аппаратный блок в чипсете, обеспечивающий трансляцию адресов DMA и изоляцию устройств.

**Роль в виртуализации:**
- VT-d (Intel) и AMD-Vi (AMD) позволяют напрямую передавать физические PCI-устройства (видеокарты, сетевые адаптеры, контроллеры NVMe) в виртуальную машину, минуя эмуляцию.
- Обеспечивают аппаратную изоляцию, предотвращая доступ устройства к памяти других ВМ или хоста.

**VFIO (Virtual Function I/O):**
Стандартный драйвер ядра Linux для управления IOMMU и проброса устройств. В связке с KVM позволяет использовать `vfiio-pci` для захвата устройства.

**Типичные сценарии:**
- **GPU Passthrough:** Передача видеокарты в ВМ для аппаратного ускорения (гейминг, ML inference, CAD). Требует ASPM, Resettable Device и ACS override.
- **SR-IOV:** Создание виртуальных функций (VF) на совместимой NIC. VF могут быть напрямую переданы в ВМ через `virsh attach-interface --hostdev`.

**Требования:**
1. Включение IOMMU в BIOS/UEFI (Intel VT-d / AMD-Vi).
2. Параметры ядра: `intel_iommu=on iommu=pt` (Intel) или `amd_iommu=on iommu=pt` (AMD).
3. Драйвер `vfio-pci` загружен и владеет устройством.
4. Отключение conflicting драйверов (например, ` nouveau` для NVIDIA).

### Ресурсные ограничения (I/O Throttling и CPU Quotas)

Для предотвращения влияния одной ВМ на производительность других (Noisy Neighbor) используются механизмы ограничения ресурсов.

**I/O Throttling:**
Ограничение пропускной способности дискового устройства в reads/writes bytes per second (BPS) и IOPS.
```xml
<disk type='file' device='disk'>
  <driver name='qemu' type='qcow2'/>
  <source file='/var/lib/libvirt/images/vm.qcow2'/>
  <target dev='vda' bus='virtio'/>
  <iotune>
    <read_bytes_sec>10485760</read_bytes_sec>      <!-- 10 MB/s -->
    <write_bytes_sec>5242880</write_bytes_sec>     <!-- 5 MB/s -->
    <read_iops_sec>1000</read_iops_sec>
    <write_iops_sec>500</write_iops_sec>
  </iotune>
</disk>
```

**CPU Quotas:**
Ограничение виртуальных процессоров через cgroups v2 (встроенные в libvirt):
- **`<vcpu>`:** Жесткое количество vCPU, выделенных ВМ.
- **`<cputune>` с `shares`:** Относительный вес при конкуренции за CPU (например, `shares='1024'` для критичной ВМ против `512` для фоновой).
- **`<cputune>` с `quota` и `period`:** Абсолютное ограничение в микросекундах за период (например, `quota='50000' period='100000'` = 50% одного ядра).

### Параметры ядра хоста для виртуализации

Гостевые нагрузки накладывают специфические требования на планировщик ядра хоста (L0).

**Рекомендуемые параметры GRUB:**
- **`intel_pstate=disable`** + **`acpi-cpufreq`:** На системах Intel позволяет полный контроль над частотой CPU через `cpufreq`. Полезно для фиксированной производительности, но снижает энергоэффективность.
- **`nohz_full=<cores>`:** Отключает периодические tick на указанных ядрах для снижения джиттера.
- **`isolcpus=<cores>`:** Исключает ядра из планировщика CFS для ручного управления (через `cset` или `taskset`).
- **`rcu_nocbs=<cores>`:** Перенос обработки RCU callbacks на отдельные ядра, снижая прерывания на ядрах, выделенных под ВМ.

**Политика частот (CPUFreq):**
- **performance:** Фиксированная максимальная частота. Минимальные задержки, максимальное энергопотребление.
- **ondemand / schedutil:** Динамическое масштабирование в зависимости от загрузки. Предпочтительно для гетерогенных нагрузок.

### Резервное копирование виртуальных машин

Стратегия бэкапа определяется SLA, размером ВМ и допустимым окном простоя.

**Подходы:**
1. **Снапшот + Копирование:** Создание снапшота `qcow2`, копирование базового и дельты-файлов, удаление снапшота.
   - **Плюсы:** Минимальное downtime, консистентность данных (с guest-agent).
   - **Минусы:** Длинные цепочки снапшотов замедляют производительность.
2. **Полное копирование диска:** Остановка ВМ, копирование файла образа.
   - **Плюсы:** Простота, гарантированная консистентность.
   - **Минусы:** Требует downtime.
3. **Экспорт в стандартный формат:** `virt-v2v` для конвертации в VMware, Hyper-V или OVA.
4. **Replication:** Синхронная или асинхронная репликация дисков (DRBD, Ceph RBD mirroring) для высокой доступности.

**Валидация бэкапа:**
- Проверка целостности образа: `qemu-img check <image>.qcow2`.
- Тестовый запуск ВМ из образа бэкапа на изолированном хосте.

### Transparent Hugepages (THP) против Hugepages

**Transparent Hugepages (THP):**
Механизм ядра Linux, который автоматически объединяет стандартные страницы 4KB в Hugepages 2MB в фоновом режиме. Включен по умолчанию в большинстве дистрибутивов.
- **Проблемы для виртуализации:** THP может вызывать задержки (latency spikes) при дефрагментации, что недопустимо для latency-sensitive workloads (базы данных, real-time).
- **Рекомендация:** Отключить THP для хостов, специализированных под ВМ с базами данных.

**Явное выделение Hugepages:**
Резервирование страниц 2MB или 1GB при загрузке системы через параметры GRUB (`hugepagesz=1G hugepages=64`).
- **Преимущества:** Гарантированная доступность, отсутствие задержек дефрагментации.
- **Недостатки:** Память зарезервирована и не может быть использована другими процессами.

**Проверка:**
```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
# → [always] madvise never — THP включен по умолчанию
grep HugePages /proc/meminfo
```

## Практические сценарии

### Сценарий 1: Выбор режима CPU для производительности и мобильности

Настройка режима CPU определяет, какие инструкции процессора будут доступны внутри ВМ.

| Режим | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **`host-passthrough`** | Полный проброс флагов CPU хоста. | Максимальная производительность (AES-NI, AVX-512). | Миграция возможна только на идентичное оборудование. |
| **`host-model`** | Проброс максимального набора функций, известных libvirt. | Оптимальный баланс, лучшая совместимость. | Чуть выше накладные расходы на эмуляцию некоторых флагов. |
| **`custom`** | Выбор конкретной архитектуры (напр. `Haswell`). | Гарантированная Live Migration в гетерогенном кластере. | Новые инструкции CPU могут быть недоступны. |

**Проверка текущего режима через libvirt:**
```bash
virsh dominfo <имя_вм> | grep "CPU mode"
```

### Сценарий 2: Использование HugePages для высоконагруженных систем

Для повышения производительности памяти можно выделить HugePages на хосте и пробросить их в ВМ.

```bash
# Резервирование HugePages (2MB) на хосте
echo 1024 | sudo tee /proc/sys/vm/nr_hugepages

# Проверка выделения
grep HugePages /proc/meminfo
```

В XML-конфигурации ВМ:
```xml
<memoryBacking>
  <hugepages/>
</memoryBacking>
```

### Сценарий 3: CPU Pinning для минимизации Jitter

Привязка виртуальных ядер (vCPU) к конкретным физическим ядрам хоста исключает переключение контекста и повышает предсказуемость производительности.

```xml
<vcpu placement='static'>4</vcpu>
<cputune>
  <vcpupin vcpu='0' cpuset='1'/>
  <vcpupin vcpu='1' cpuset='2'/>
  <emulatorpin cpuset='0-1'/>
</cputune>
```

### Сценарий 4: Проверка аппаратной поддержки и модулей

```bash
# Проверка загрузки модулей
lsmod | grep -i kvm
# → kvm_intel  (для процессоров Intel)
# → kvm_amd    (для процессоров AMD)

# Проверка прав доступа к устройству
ls -l /dev/kvm
# → crw-rw---- 1 root kvm ...
```

### Сценарий 5: Живая миграция с post-copy fallback

При миграции ВМ между хостами с высокой скоростью изменения памяти (memory write-intensive workload) стандартный pre-copy может не завершаться (non-convergence).

```bash
# Стандартная миграция с auto-converge (замедление vCPU)
virsh migrate --live --auto-converge web-server-01 qemu+ssh://dest-host/system

# Post-copy: минимальное downtime, но риск падения при потере сети
virsh migrate --live --postcopy web-server-01 qemu+ssh://dest-host/system

# Проверка статуса миграции
virsh migrate --getmaxbandwidth web-server-01
```

### Сценарий 6: Настройка virtiofs для совместного доступа к файлам

Virtiofs — современный механизм обмена файлами между хостом и гостем через разделяемую память. Значительно быстрее virtio-9p и NFS для однохостовых сценариев.

В XML-конфигурации ВМ:
```xml
<devices>
  <filesystem type='mount' accessmode='passthrough'>
    <source dir='/srv/shared'/>
    <target dir='shared'/>
    <driver type='virtiofs'/>
  </filesystem>
</devices>
```

Внутри гостевой ОС (Linux):
```bash
sudo mount -t virtiofs shared /mnt/shared
```

### Сценарий 7: Ограничение дискового I/O (I/O Throttling)

Предотвращение влияния "шумного соседа" (Noisy Neighbor) через ограничение пропускной способности диска.

```xml
<disk type='file' device='disk'>
  <driver name='qemu' type='qcow2' io='io_uring' queues='4'/>
  <source file='/var/lib/libvirt/images/vm.qcow2'/>
  <target dev='vda' bus='virtio'/>
  <iotune>
    <read_bytes_sec>10485760</read_bytes_sec>
    <write_bytes_sec>5242880</write_bytes_sec>
    <read_iops_sec>1000</read_iops_sec>
    <write_iops_sec>500</write_iops_sec>
  </iotune>
</disk>
```

### Сценарий 8: Резервное копирование ВМ через снапшоты

Создание точки восстановления перед критическими изменениями (обновление ОС, патчи).

```bash
# Создание снапшота с консистентной ФС (требует qemu-guest-agent)
virsh snapshot-create-as web-server-01 "pre-patch-v1" "Before kernel update" --atomic --quiesce

# Список снапшотов
virsh snapshot-list web-server-01

# Откат к снапшоту с запуском
virsh snapshot-revert web-server-01 "pre-patch-v1" --running

# Удаление снапшота (слияние с базовым диском)
virsh snapshot-delete web-server-01 "pre-patch-v1"
```

### Сценарий 9: Проверка и отключение Transparent Hugepages

Для баз данных и приложений с требованием к минимальным задержкам THP должен быть отключен.

```bash
# Текущий режим THP
cat /sys/kernel/mm/transparent_hugepage/enabled
# → [always] madvise never

# Отключение THP (до перезагрузки)
echo madvise | sudo tee /sys/kernel/mm/transparent_hugepage/enabled

# Постоянное отключение через GRUB
echo 'transparent_hugepage=never' | sudo tee -a /etc/default/grub.d/99-thp.cfg
sudo update-grub
```
