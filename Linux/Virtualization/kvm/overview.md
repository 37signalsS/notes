# KVM — Обзор и архитектура

В данном файле описывается архитектура KVM (Kernel-based Virtual Machine), взаимодействие с QEMU и механизм virtio. Общие принципы виртуализации (типы гипервизоров, контейнеры против ВМ) представлены в [Виртуализация: Обзор](../virtualization_overview.md).

## Определения

**KVM (Kernel-based Virtual Machine)** — модуль ядра Linux, обеспечивающий инфраструктуру для аппаратной виртуализации. Превращает ядро в гипервизор 1-го типа (bare-metal), позволяя гостевым операционным системам выполнять инструкции напрямую на физическом процессоре (CPU) через расширения Intel VT-x или AMD-V.

**QEMU (Quick Emulator)** — эмулятор и виртуализатор с открытым исходным кодом. В связке с KVM отвечает за эмуляцию периферийных устройств (диски, сеть, PCI), в то время как KVM обеспечивает высокопроизводительное выполнение кода гостя. Может работать и без KVM в режиме **TCG (Tiny Code Generator)** — программной трансляции инструкций, что значительно медленнее.

**libvirt** — стандартный уровень абстракции (API), демон `libvirtd` и набор инструментов (`virsh`, `virt-install`) для управления виртуализацией. Позволяет работать с ВМ единообразно независимо от гипервизора (KVM, Xen, LXC).

**Virtio** — стандарт паравиртуализированных драйверов для оптимизации операций ввода-вывода (I/O). Вместо полной эмуляции оборудования использует механизм обмена данными через общую память (virtqueues).

**CPU Mode** — конфигурация проброса функций физического процессора в виртуальную машину. Влияет на производительность и возможность «живой» миграции.

**Живая миграция (Live Migration)** — процесс переноса работающей ВМ между физическими хостами без остановки гостевой операционной системы.

## Базовые концепции

### Взаимодействие QEMU и KVM

KVM и QEMU дополняют друг друга, создавая полноценную среду виртуализации. Взаимодействие происходит через файл устройства `/dev/kvm` с использованием системных вызовов (ioctl).

| Компонент | Роль | Функции |
| :--- | :--- | :--- |
| **KVM** | Гипервизор (ядро) | Выполнение инструкций CPU гостя, управление памятью (EPT/NPT), обработка прерываний. |
| **QEMU** | Эмулятор (userspace) | Эмуляция чипсета, шин (PCIe), устройств ввода-вывода и управление жизненным циклом ВМ. |

**Механизм работы:**
1. QEMU открывает `/dev/kvm`.
2. С помощью ioctl `KVM_CREATE_VM` создается контекст виртуальной машины.
3. Команда `KVM_RUN` переключает процессор в режим выполнения гостевого кода (VM-Entry).
4. При возникновении события, которое KVM не может обработать самостоятельно (например, доступ к эмулируемому порту I/O), происходит выход в userspace (VM-Exit), и QEMU обрабатывает запрос.

### Кольца защиты и аппаратное ускорение

Благодаря технологиям Intel VT-x и AMD-V, KVM вводит дополнительный уровень привилегий — **VMX Root Mode** (часто называемый Ring -1).
- **Хост (KVM):** Работает в VMX Root Mode.
- **Гость (Ядро ОС):** Думает, что работает в Ring 0, но фактически выполняется в VMX Non-Root Mode, что позволяет гипервизору перехватывать критические инструкции.

Подробнее о механизме колец защиты: [Виртуализация: Кольца защиты](../virtualization_overview.md#кольца-защиты-protection-rings).

### Паравиртуализация Virtio и ускорение I/O

Для минимизации накладных расходов на VM-Exit при операциях ввода-вывода используются механизмы паравиртуализации и разгрузки (offloading):

1. **vhost-net:** Перенос обработки сетевых пакетов Virtio из userspace (QEMU) напрямую в ядро Linux. Это исключает лишние переключения контекста между ядром и пользователем.
2. **vhost-user:** Позволяет QEMU взаимодействовать с высокопроизводительными сетевыми стеками в пространстве пользователя (например, DPDK) через Unix Domain Sockets.
3. **io_uring:** Современный интерфейс асинхронного I/O в Linux, который QEMU использует для эффективной работы с дисковыми образами, снижая нагрузку на CPU при интенсивных операциях записи/чтения.
4. **vDPA (VirtIO Data Path Acceleration):** Проброс аппаратного ускорения Virtio (например, в SmartNIC) напрямую в гостевую ОС, сохраняя при этом стандартный интерфейс драйверов Virtio.

**Основные типы устройств Virtio:**
- `virtio-net`: Сетевой адаптер.
- `virtio-blk` / `virtio-scsi`: Дисковые контроллеры.
- `virtio-balloon`: Динамическое управление оперативной памятью гостя.
- `virtio-rng`: Проброс энтропии (генератора случайных чисел) с хоста.

### Конфиденциальные вычисления (Confidential Computing)

Современные версии KVM поддерживают технологии аппаратного шифрования памяти, защищающие данные гостя даже от администратора хоста и скомпрометированного гипервизора:
- **AMD SEV-SNP:** Secure Encrypted Virtualization с защитой целостности страниц.
- **Intel TDX:** Trust Domain Extensions для изоляции ВМ в доверенных доменах (Realms).

## Практические сценарии

### Сценарий 1: Выбор режима CPU для производительности и мобильности

Настройка режима CPU определяет, какие инструкции процессора будут доступны внутри ВМ.

| Режим | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **`host-passthrough`** | Полный проброс флагов CPU хоста. | Максимальная производительность (AES-NI, AVX-512). | Миграция возможна только на идентичное оборудование. |
| **`host-model`** | Проброс максимального набора функций, известных libvirt. | Оптимальный баланс, лучшая совместимость. | Чуть выше накладные расходы на эмуляцию некоторых флагов. |
| **`custom`** | Выбор конкретной архитектуры (напр. `Haswell`). | Гарантированная Live Migration в гетерогенном кластере. | Новые инструкции CPU могут быть недоступны. |

**Команда для проверки текущего режима через libvirt:**
```bash
virsh dominfo <имя_вм> | grep "CPU mode"
```

### Сценарий 2: Проверка аппаратной поддержки и модулей

KVM требует загрузки специфичных для производителя модулей ядра.

```bash
# Проверка загрузки модулей
lsmod | grep -i kvm
# → kvm_intel  (для процессоров Intel)
# → kvm_amd    (для процессоров AMD)

# Проверка прав доступа к устройству
ls -l /dev/kvm
# → crw-rw---- 1 root kvm ...
```

### Сценарий 3: Активация vhost для сетевых интерфейсов

При использовании libvirt `vhost-net` обычно включается автоматически при выборе модели `virtio`. Проверить это можно в XML-конфигурации:

```xml
<interface type='bridge'>
  <model type='virtio'/>
  <driver name='vhost'/> <!-- Явное указание vhost -->
</interface>
```
