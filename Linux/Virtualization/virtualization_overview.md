# Виртуализация и изоляция в Linux

Данный файл содержит обзор технологий виртуализации и механизмов изоляции в среде Linux, их архитектуру, сравнение и современные тренды развития (2025–2026).

## Определения

**Виртуализация** — процесс создания программного (виртуального) представления физических ресурсов (CPU, RAM, Storage, Network). Позволяет запускать несколько независимых операционных систем или сред на одном физическом сервере.

**Изоляция** — механизм ограничения доступа процесса к системным ресурсам и видимости других процессов без создания полноценной виртуальной машины. В Linux реализуется на уровне ядра через разделение пространств имен.

**Эмуляция** — имитация аппаратного обеспечения одной архитектуры на другой с помощью программной трансляции инструкций (например, запуск x86 на ARM через QEMU TCG). Значительно медленнее виртуализации из-за накладных расходов на интерпретацию кода.

**Гипервизор (VMM — Virtual Machine Monitor)** — специализированное ПО для управления виртуальными машинами и распределения ресурсов хоста.

### Классификация по типу взаимодействия

- **Тип 1 (Bare-Metal):** Работает напрямую на аппаратном обеспечении. Является тонким слоем между железом и гостевыми ОС. Примеры: **KVM** (модуль ядра делает Linux гипервизором 1-го типа), **Xen**, **VMware ESXi**.
- **Тип 2 (Hosted):** Работает как приложение внутри основной (хостовой) ОС. Примеры: **VirtualBox**, **VMware Workstation**, **QEMU** (без KVM).

### Методы виртуализации

- **Полная виртуализация (Full Virtualization):** Гостевая ОС не знает, что она виртуализирована. Требует аппаратной поддержки (VT-x/AMD-V) для выполнения привилегированных инструкций.
- **Паравиртуализация (Paravirtualization):** Гостевая ОС модифицирована для взаимодействия с гипервизором через специальные вызовы (Hypercalls) или использует специализированные драйверы (**VirtIO**). Это исключает необходимость эмуляции сложных инструкций и повышает производительность I/O.
- **Вложенная виртуализация (Nested Virtualization):** Возможность запускать гипервизор внутри виртуальной машины.
  - **L0:** Физический хост.
  - **L1:** Первая виртуальная машина (гость для L0, хост для L2).
  - **L2:** Вложенная виртуальная машина.

## Современные архитектуры гипервизоров (2025–2026)

### Стандартные и облачные решения

- **KVM (Kernel-based Virtual Machine):** Стандарт де-факто в Linux. Интегрирован в ядро, обеспечивает нативную производительность CPU и памяти.
- **Xen:** Поддерживает глубокую паравиртуализацию. Используется в облаках (ранее AWS) и проектах с высокими требованиями к безопасности (Qubes OS).
- **AWS Nitro:** Аппаратная разгрузка гипервизора. Функции сети, хранилища и безопасности вынесены на выделенные чипы (ASIC/SmartNIC), что минимизирует "налог на виртуализацию" (virtualization tax) до <1%.

### Rust-based VMM (Безопасность памяти)

Современные VMM пишутся на языке **Rust** для исключения целых классов уязвимостей, связанных с управлением памятью (buffer overflow, use-after-free).
- **Firecracker (MicroVM):** Минималистичный VMM от AWS, оптимизированный для Serverless (Lambda, Fargate). Запуск за <125 мс, минимальное потребление RAM (~5MB на ВМ).
- **Cloud Hypervisor:** Совместный проект Intel и Linux Foundation. Ориентирован на облачные нагрузки, поддерживает современные фичи (Live Migration, VFIO) при минимальном коде.
- **Stratovirt:** Решение от Huawei для высокоплотных вычислений и AI-инфраструктур, оптимизированное под архитектуру ARM (Kunpeng).

### Конфиденциальные вычисления (Confidential Computing)

Защита данных непосредственно во время выполнения через аппаратное шифрование памяти ВМ.
- **Intel TDX (Trust Domain Extensions)** и **AMD SEV-SNP**: Изолируют память и состояние регистров ВМ даже от гипервизора и администратора хоста.

## Базовые концепции

### Кольца защиты (Protection Rings)

Аппаратная виртуализация добавляет режим **Ring -1** (VMX Root Mode), в котором работает гипервизор. Это позволяет гостевой ОС работать в **Ring 0** (VMX Non-Root), не конфликтуя с хостом и выполняя большинство инструкций напрямую.

### Механизмы изоляции ядра

Изоляция в Linux строится на трех столпах:
- **Namespaces (Пространства имен):** Изолируют видимость ресурсов (PID, Network, Mount, User, UTS, IPC). Подробнее: [Пространства имён (namespaces)](../Core/namespaces.md).
- **Cgroups (Control Groups):** Ограничивают потребление ресурсов (CPU, RAM, I/O). Современный стандарт **cgroup v2** использует единую иерархию. Подробнее: [Контрольные группы (cgroups)](../Core/cgroups.md).
- **LSM (Linux Security Modules):** AppArmor, SELinux для принудительного контроля доступа (MAC).

### Аппаратная поддержка

| Технология | Intel | AMD | Назначение |
| :--- | :--- | :--- | :--- |
| **CPU Virtualization** | VT-x | AMD-V | Выполнение инструкций гостя на физическом CPU без эмуляции. |
| **Memory Virtualization** | EPT | RVI | Ускорение трансляции адресов (Nested Paging) без VM-Exit. |
| **I/O Virtualization** | VT-d | AMD-Vi | Изоляция прерываний и DMA для прямого проброса PCI (IOMMU). |
| **Network Offloading** | SR-IOV | SR-IOV | Создание виртуальных функций (VF) сетевой карты для ВМ. |
| **Confidentiality** | TDX | SEV-SNP | Аппаратное шифрование памяти и изоляция от гипервизора. |

## Критерии выбора

### Используйте контейнеры (Docker/Podman/Kubernetes), если требуется:
- Микросервисная архитектура и легкая изоляция приложений.
- Быстрое развертывание и масштабирование (CI/CD).
- Максимальная плотность размещения приложений на одном хосте.

### Используйте системные контейнеры (LXC/Incus), если требуется:
- Замена легким ВМ для инфраструктурных сервисов (DHCP, DNS, VPN).
- Stateful-нагрузки (базы данных), требующие полноценного окружения ОС (systemd).
- Общее ядро с хостом для минимальных задержек I/O.

### Используйте виртуальные машины (KVM/Cloud Hypervisor), если требуется:
- Запуск разных ОС (Windows, BSD) на одном Linux-хосте.
- Полная изоляция на уровне ядра для работы с недоверенным кодом.
- Проброс физического оборудования (GPU, HBA) через VFIO.
- Глубокая кастомизация ядра внутри гостевой системы.

### Гибридные решения (Sandboxed Containers)

- **Kata Containers:** Запускает каждый контейнер в легкой MicroVM. Обеспечивает аппаратную изоляцию при сохранении совместимости с экосистемой Kubernetes (CRI).
- **gVisor (Google):** Перехватывает системные вызовы приложения и обрабатывает их в изолированном ядре в userspace (Sentry), защищая ядро хоста.

## Рекомендации по выбору (DevOps Roadmap)

1. **Docker/Podman:** Стандарт для разработки и CI/CD.
2. **LXC/Incus:** Оптимально для домашних лабораторий и внутренних сервисов компании вместо тяжелых ВМ.
3. **Kata Containers:** Рекомендуется для Multi-tenant Kubernetes кластеров (запуск чужого кода).
4. **Proxmox/KVM:** Промышленный стандарт для серверной виртуализации и корпоративных ИТ-инфраструктур.
