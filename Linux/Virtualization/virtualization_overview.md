# Виртуализация и изоляция в Linux

Данный файл содержит обзор технологий виртуализации и механизмов изоляции в среде Linux, их сравнение и критерии выбора. Детальные инструкции по конкретным решениям приведены в соответствующих подразделах.

## Определения

**Виртуализация** — процесс создания программного (виртуального) представления физических ресурсов (процессоров, памяти, дисков, сетей). Позволяет запускать несколько независимых операционных систем на одном физическом сервере.

**Изоляция** — механизм ограничения доступа процесса к системным ресурсам и видимости других процессов без создания полноценной виртуальной машины.

**Эмуляция** — имитация аппаратного обеспечения одной архитектуры на другой с помощью программной трансляции инструкций (например, запуск x86 на ARM).

**Гипервизор (VMM — Virtual Machine Monitor)** — специализированное ПО для управления виртуальными машинами и распределения ресурсов хоста.

### Классификация по типу взаимодействия

- **Тип 1 (Bare-Metal):** работает напрямую на аппаратном обеспечении. Является тонким слоем между железом и гостевыми ОС (KVM, Xen, ESXi).
- **Тип 2 (Hosted):** работает как приложение внутри основной (хостовой) ОС (VirtualBox, VMware Workstation).

### Методы виртуализации

- **Полная виртуализация (Full Virtualization):** гостевая ОС не знает, что она виртуализирована. Требует аппаратной поддержки (VT-x/AMD-V) для выполнения привилегированных инструкций.
- **Паравиртуализация (Paravirtualization):** гостевая ОС модифицирована для взаимодействия с гипервизором через специальные вызовы (Hypercalls). Это исключает необходимость эмуляции сложных инструкций и повышает производительность (например, драйверы **VirtIO**).

## Современные архитектуры гипервизоров

### Стандартные решения

- **KVM (Kernel-based Virtual Machine):** стандарт де-факто в Linux. Превращает ядро в гипервизор 1-го типа.
- **Xen:** поддерживает глубокую паравиртуализацию. Используется в проектах с высокими требованиями к безопасности (Qubes OS).

### Специализированные и облачные решения

- **AWS Nitro:** аппаратная разгрузка гипервизора. Функции сети и I/O вынесены на выделенные чипы (ASIC), что минимизирует накладные расходы.
- **MicroVM (Firecracker):** минималистичные виртуальные машины, написанные на Rust. Оптимизированы для мгновенного запуска (миллисекунды) в Serverless-средах (AWS Lambda).

## Базовые концепции

### Кольца защиты (Protection Rings)

Аппаратная виртуализация добавляет уровень **Ring -1** (VMX Root Mode), в котором работает гипервизор. Это позволяет гостевой ОС работать в **Ring 0**, не конфликтуя с хостом.

### Механизмы изоляции ядра

Изоляция в Linux (контейнеризация) строится на двух столпах:

- **Namespaces (Пространства имен):** изолируют видимость ресурсов (PID, Network, Mount, User, UTS, IPC).
- **Cgroups (Control Groups):** ограничивают потребление ресурсов (CPU, RAM, I/O).

Подробнее: [Пространства имён (namespaces)](../Core/namespaces.md) и [Контрольные группы (cgroups)](../Core/cgroups.md).

### Аппаратная поддержка (x86)

| Технология | Intel | AMD | Назначение |
| :--- | :--- | :--- | :--- |
| **CPU Virtualization** | VT-x | AMD-V | Выполнение инструкций гостя на физическом CPU |
| **Memory Virtualization** | EPT | RVI | Ускорение трансляции адресов (Nested Paging) |
| **I/O Virtualization** | VT-d | AMD-Vi | Прямой проброс PCI-устройств (IOMMU) |

## Сравнение технологий изоляции

Основное архитектурное различие между виртуальными машинами и контейнерами заключается в уровне абстракции ресурсов.

- **Абстракция оборудования (ВМ):** гипервизор создает виртуальный набор аппаратных средств (CPU, RAM, NIC). Каждая ВМ запускает полноценную гостевую ОС, что обеспечивает максимальную изоляцию, но требует значительных ресурсов.
- **Абстракция ОС (Контейнеры):** контейнеры используют общее ядро хостовой ОС. Изоляция достигается на уровне пространств имен (namespaces), что делает их на порядки легче и быстрее в запуске.

| Критерий | Docker (App) | LXC (System) | Kata Containers | Виртуальные машины |
| :--- | :--- | :--- | :--- | :--- |
| **Абстракция** | ОС (Shared Kernel) | ОС (Shared Kernel) | Гибридная (MicroVM) | Аппаратная (VMM) |
| **Тип** | Контейнер | Контейнер | Sandboxed Container | VM |
| **Изоляция** | Namespaces/Cgroups | Namespaces/Cgroups | Аппаратная (MicroVM) | Аппаратная (VMM) |
| **Ядро** | Общее | Общее | Своё (легкое) | Своё (полное) |
| **Безопасность** | Средняя | Средняя | Высокая | Максимальная |
| **Скорость** | Мгновенно | Мгновенно | Очень быстро | Медленно |

### Критерии выбора

#### Используйте контейнеры, если требуется:
- Микросервисная архитектура и легкая изоляция.
- Быстрое и последовательное развертывание (CI/CD).
- Высокая горизонтальная масштабируемость.
- Эффективное использование системных ресурсов (высокая плотность размещения).

#### Используйте виртуальные машины, если требуется:
- Запуск приложений на разных операционных системах на одном хосте.
- Полная изоляция на уровне ядра (для соображений безопасности или специфических системных вызовов).
- Приложения, требующие прямого управления аппаратными ресурсами или специфических конфигураций ядра.
- Запуск монолитов, не адаптированных к контейнеризации.

### Гибридные решения (Sandboxed Containers)

- **Kata Containers:** запускает каждый контейнер в легкой MicroVM. Обеспечивает аппаратную изоляцию при сохранении совместимости с экосистемой Kubernetes (CRI).
- **gVisor (Google):** перехватывает системные вызовы приложения и обрабатывает их в изолированном ядре в userspace (Sentry), защищая ядро хоста.

## Рекомендации по выбору

1. **Docker/Podman:** стандарт для микросервисов и CI/CD.
2. **LXC/LXD:** замена легким ВМ для инфраструктурных сервисов (DHCP, DNS) и Stateful-нагрузок. Подробнее: [Обзор LXC](./lxc_overview.md).
3. **Kata Containers:** запуск недоверенного кода (untrusted workloads) в облачных средах.
4. **KVM (ВМ):** запуск Windows, глубокая кастомизация ядра, жесткая изоляция ресурсов.
