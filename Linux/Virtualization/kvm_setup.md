# Установка и настройка KVM

## Определения

Эта заметка является практическим руководством по настройке KVM. Основные теоретические концепции виртуализации описаны в файле [**Обзор виртуализации в Linux**](./virtualization_overview.md).

**KVM (Kernel-based Virtual Machine)** — это решение для полной виртуализации, встроенное в ядро Linux. Оно превращает ядро в гипервизор 1-го типа, позволяя ему напрямую управлять виртуальными машинами. Для эмуляции устройств и управления ВМ KVM обычно используется вместе с **QEMU**.

**QEMU (Quick Emulator)** — это виртуализированный эмулятор, который запускает программы и операционные системы, созданные для одной машины, на другой машине в процессе эмуляции. Он может достичь очень хорошей производительности с помощью динамического перевода. QEMU эмулирует различные периферийные устройства: сетевые карты, HDD, видеокарты, PCI, USB, серийные порты и другие, которые "видят" и с которыми работают гости.

**libvirt** — это набор инструментов (API, демон `libvirtd` и утилиты) для управления виртуализацией. Он предоставляет единый уровень абстракции для работы с различными гипервизорами, включая KVM.

## Базовые концепции

### Гипервизор vs Эмулятор

* **Гипервизор** — это "менеджер виртуальных машин" (VMM – Virtual Machine Manager, например, KVM). Он работает в виде модуля на ОС Linux (для KVM) и выполняет роль "прокладки" между физическим железом (хостом) и виртуальной ОС (гостем). Его основная задача – запускать софт в несуществующей (виртуальной) среде, при этом скрывая от этого софта реальное физическое железо. Гипервизор позволяет нескольким операционным системам **одной и той же архитектуры** (например, x86 на x86) совместно использовать ресурсы одного физического компьютера. Инструкции гостевой ОС выполняются **напрямую** на физическом процессоре, что обеспечивает высокую производительность.

* **Эмулятор** — это "симулятор" другой аппаратной платформы (например, QEMU в чистом виде). Он позволяет запускать ОС или программы, созданные для **другой архитектуры** (например, ARM на x86). Для этого он "на лету" **транслирует** каждую инструкцию с гостевого CPU на язык хостового CPU, что приводит к значительным потерям производительности.

Когда KVM и QEMU работают вместе, KVM берет на себя роль гипервизора и выполняет процессорные инструкции гостя напрямую, предоставляя гостям доступ к Ring 0. При этом QEMU эмулирует остальное оборудование (диски, сетевые карты, видео, PCI, USB, серийные порты и т.д.), которое "видят" и с которым работают гости.

| Характеристика | Гипервизор (KVM) | Эмулятор (QEMU) |
| :--- | :--- | :--- |
| **Задача** | Запуск ОС той же архитектуры | Запуск ОС **другой** архитектуры |
| **Процессор** | Инструкции выполняются **напрямую** | Инструкции **транслируются** |
| **Скорость** | Очень высокая, близкая к нативной | Значительно медленнее |

### Механизм паравиртуализации `virtio`

**Virtio** — это стандарт для паравиртуализированных драйверов и устройств в средах виртуализации. В отличие от полной эмуляции аппаратного обеспечения (когда гостевая ОС "думает", что работает с реальной сетевой картой или диском), `virtio` предоставляет стандартизированный и оптимизированный интерфейс.

**Как это работает:**

1. **Осведомлённость:** И гостевая ОС (через драйверы `virtio-*`) и гипервизор (например, QEMU/KVM) "знают", что работают в виртуализированной среде.
2. **Оптимизация:** Вместо эмуляции сложного реального оборудования они обмениваются данными через простые и эффективные общие области памяти.

**Преимущества `virtio`:**
* **Высокая производительность:** Значительно сокращаются накладные расходы на операции ввода-вывода (I/O) для сети и дисков. Производительность приближается к "родной" (bare-metal).
* **Универсальность:** Является стандартом де-факто и поддерживается большинством современных гипервизоров (KVM, VirtualBox, VMware).
* **Гибкость:** Позволяет добавлять и удалять устройства "на лету".

Основные типы устройств `virtio`:
* `virtio-net`: Сетевой адаптер.
* `virtio-blk`: Дисковый контроллер.
* `virtio-scsi`: SCSI контроллер для более сложных дисковых конфигураций.
* `virtio-balloon`: Устройство для динамического управления памятью гостевой ОС.

## Практические сценарии

### Установка и предварительная настройка

#### Шаг 1: Проверка поддержки аппаратной виртуализации

Сначала необходимо убедиться, что ваш процессор поддерживает аппаратную виртуализацию.

```bash
egrep -c '(vmx|svm)' /proc/cpuinfo
```

Если результат выполнения команды — число больше 0, виртуализация поддерживается.

Дополнительно можно использовать утилиту `kvm-ok`. Если она отсутствует, установите пакет `cpu-checker`:

```bash
sudo apt install cpu-checker
```

Затем выполните проверку:

```bash
sudo kvm-ok
```

#### Шаг 2: Установка компонентов KVM

После подтверждения поддержки виртуализации установите необходимые пакеты:

```bash
sudo apt install -y qemu qemu-kvm libvirt-daemon libvirt-clients bridge-utils virt-manager
```

* `qemu`: Эмулятор и виртуализатор.
* `qemu-kvm`: Основной пакет KVM.
* `libvirt-daemon`: Демон для управления виртуализацией.
* `libvirt-clients`: Утилиты для управления виртуальными машинами (например, `virsh`).
* `bridge-utils`: Инструменты для создания сетевых мостов.
* `virt-manager`: Графический интерфейс для управления ВМ.

#### Шаг 3: Настройка пользователя и служб

Добавьте вашего пользователя в группу `libvirt`, чтобы управлять виртуальными машинами без `sudo`:

```bash
sudo gpasswd -a $USER libvirt
```

**Примечание:** После этого необходимо перелогиниться в систему, чтобы изменения вступили в силу.

Проверьте статус демона `libvirtd`:

```bash
sudo systemctl status libvirtd
```

Включите его автоматический запуск при загрузке системы:

```bash
sudo systemctl enable libvirtd
```

#### Шаг 4: Проверка установки

Убедитесь, что модули KVM загружены:

```bash
lsmod | grep -i kvm
```

При установке KVM создается сетевой мост по умолчанию, обычно `virbr0`. Проверить доступные сетевые интерфейсы можно командой:

```bash
ip link
```

### Создание и управление виртуальными машинами

Существует два основных подхода к созданию ВМ: напрямую через QEMU (быстро, без сохранения) и через `libvirt` (рекомендуемый, с управлением жизненным циклом).

#### Создание VM одной командой (через QEMU)

**Преимущество:** Максимально быстро и минималистично, но без персистентности — закрыли терминал = ВМ остановилась.

```bash
qemu-system-x86_64 \
  -enable-kvm \
  -m 1G \
  -cpu host \
  -drive file=focal-server-cloudimg-amd64-disk-kvm.img,format=qcow2 \
  -netdev user,id=net0 \
  -device virtio-net-pci,netdev=net0 \
  -nographic
```

Где:

* `-enable-kvm` — используем аппаратное ускорение
* `-m 1G` — выделяем 1 ГБ памяти
* `-cpu host` — пробрасываем CPU хоста без эмуляции
* `-nographic` — запускаем без GUI (для серверов)

#### Создание управляемой ВМ (через libvirt)

Это рекомендуемый способ, который обеспечивает персистентность конфигурации и управление через `virsh`.

**Шаг 1: Загрузка образа ОС**
Скачайте установочный образ операционной системы. Рекомендуется хранить образы в директории `/var/lib/libvirt/boot/`.
Пример для Ubuntu Server 24.04 LTS:

```bash
sudo wget -O /var/lib/libvirt/boot/ubuntu24.iso https://releases.ubuntu.com/24.04/ubuntu-24.04-live-server-amd64.iso
```

**Шаг 2: Определение варианта ОС**
Для корректного создания ВМ необходимо указать правильный идентификатор ОС. Установите утилиту `libosinfo-bin`:

```bash
sudo apt install libosinfo-bin
```

Найдите нужный идентификатор в списке:

```bash
osinfo-query os | grep -i ubuntu | grep 24.04
```

**Шаг 3: Создание виртуальной машины с помощью `virt-install`**
Используйте команду `virt-install` для создания ВМ. Образы дисков виртуальных машин по умолчанию хранятся в `/var/lib/libvirt/images/`.

Пример создания ВМ с Ubuntu 24.04:

```bash
sudo virt-install \
    --name=ubuntu-lts-vm \
    --os-variant=ubuntu24.04 \
    --vcpu=1 \
    --ram=2048 \
    --graphics vnc \
    --cdrom=/var/lib/libvirt/boot/ubuntu24.iso \
    --network bridge:virbr0,model=virtio \
    --disk path=/var/lib/libvirt/images/ubuntu-lts-vm.qcow2,size=20,bus=virtio,format=qcow2
```

В данном примере используется образ диска в формате `qcow2`. Подробнее о различных форматах образов (`qcow2`, `raw`, `vmdk`), создании снапшотов и управлении ими с помощью `qemu-img` можно прочитать в заметке [**Образы Виртуальных Машин (virtual_machine_images.md)**](./virtual_machine_images.md).

* `--name`: Имя виртуальной машины.
* `--os-variant`: Идентификатор ОС, полученный ранее.
* `--vcpu`: Количество виртуальных процессоров.
* `--ram`: Объем оперативной памяти (в МБ).
* `--cdrom`: Путь к установочному ISO-образу.
* `--network`: Настройки сети.
* `--disk`: Настройки виртуального диска (путь, размер в ГБ, шина, формат).

После выполнения команды запустится стандартный процесс установки ОС в консоли.

#### Управление виртуальной машиной (virsh)

`virsh` — основная утилита командной строки для управления ВМ.

* **Список запущенных ВМ:**

    ```bash
    sudo virsh list
    ```

* **Список всех ВМ (включая выключенные):**

    ```bash
    sudo virsh list --all
    ```

* **Информация для подключения по VNC:**

    ```bash
    sudo virsh vncdisplay имя_машины
    ```

* **Запуск ВМ:**

    ```bash
    sudo virsh start имя_машины
    ```

* **Штатное выключение ВМ (требует ACPI):**

    ```bash
    sudo virsh shutdown имя_машины
    ```

* **Принудительное выключение ВМ (аналог выдергивания шнура):**

    ```bash
    sudo virsh destroy имя_машины
    ```

* **Перезагрузка:**

    ```bash
    sudo virsh reboot имя_машины
    ```

* **Приостановка (сон):**

    ```bash
    sudo virsh suspend имя_машины
    ```

* **Возобновление:**

    ```bash
    sudo virsh resume имя_машины
    ```

* **Редактирование конфигурации:**

    ```bash
    virsh edit имя_машины
    ```

* **Удаление ВМ (но не дисков):**

    ```bash
    virsh undefine имя_машины
    ```

**Примечание:** Команда `destroy` только останавливает ВМ. Файл образа диска в `/var/lib/libvirt/images/` необходимо удалять вручную, если он больше не нужен.

## Дополнительная информация

### Решение проблем (Troubleshooting)

#### Снижение производительности ВМ после миграции

Иногда после миграции виртуальной машины на другой хост KVM наблюдается резкое падение производительности: увеличиваются задержки, отзывчивость интерфейса и приложений падает, хотя ресурсы CPU и памяти на хосте свободны.

**Причина:**

Почти всегда причина кроется в том, что после миграции гостевая система перестает использовать аппаратную виртуализацию и откатывается на программную эмуляцию процессора. Это происходит, когда CPU на новом хосте не может предоставить гостю идентичный набор функций (CPU model), который был на исходном хосте. В этом случае QEMU включает резервный механизм эмуляции **TCG (Tiny Code Generator)**, который в сотни раз медленнее прямого выполнения инструкций на физическом CPU.

В логах это может выглядеть так:

```log
kvm: host doesn't support requested feature...
falling back to tcg
```

**Диагностика:**

1. **Проверьте возможности домена:**

    ```bash
    virsh domcapabilities --domain <имя_вм>
    ```

2. **Проверьте информацию о домене и модели CPU:**

    ```bash
    virsh dominfo <имя_вм>
    ```

    Обратите внимание на строку `CPU-mode`. Если там указано `qemu64`, `kvm64` или другое абстрактное значение вместо `host-model` или `host-passthrough`, это верный признак того, что ВМ не использует все возможности физического процессора.

**Решение:**

Необходимо привести модель CPU к единому виду на обоих хостах (исходном и целевом).

1. **Отредактируйте конфигурацию ВМ:**

    ```bash
    virsh edit <имя_вм>
    ```

2. **Измените или добавьте конфигурацию CPU.**

    * Если процессоры на хостах идентичны (одна модель, один производитель), используйте режим `host-passthrough`, который пробрасывает все флаги CPU хоста напрямую в гостевую систему:

        ```xml
        <cpu mode="host-passthrough"/>
        ```

    * Если процессоры на хостах разные (например, разные поколения Intel), используйте `host-model`. Этот режим определяет модель CPU хоста и выбирает наиболее совместимый и функциональный набор инструкций, который `libvirt` может гарантировать на другом хосте. Это более безопасный вариант для гетерогенных кластеров.

        ```xml
        <cpu mode="host-model"/>
        ```

3. **Перезагрузите ВМ**, чтобы изменения вступили в силу.

**Дополнительная проверка:**

Убедитесь, что аппаратная виртуализация (VT-x/AMD-V) включена на обоих хостах:

```bash
egrep -c '(vmx|svm)' /proc/cpuinfo
```

Если команда возвращает `0`, виртуализация отключена в BIOS/UEFI.
