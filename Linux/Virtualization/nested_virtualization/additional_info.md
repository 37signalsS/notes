# Вложенная виртуализация — Дополнительная информация

В данном файле собраны сведения о производительности, безопасности и альтернативных решениях для вложенной виртуализации. Основные настройки приведены в [Вложенная виртуализация: Практические сценарии](./practical_scenarios.md).

## Определения

**Hugepages** — механизм ядра Linux, позволяющий использовать страницы памяти большего размера (например, 2 МБ вместо 4 КБ), что снижает нагрузку на таблицу страниц при вложенной виртуализации.

**CPU Pinning** — привязка виртуальных процессоров ВМ к конкретным физическим ядрам хоста для исключения задержек при переключении контекста.

**DinD (Docker-in-Docker)** — метод запуска контейнеров Docker внутри другого контейнера Docker, не требующий вложенной виртуализации на уровне гипервизора.

## Базовые концепции

### Оценка производительности

Вложенность неизбежно приводит к снижению производительности из-за дополнительных уровней абстракции:

| Уровень иерархии | CPU (относительно L0) | I/O (относительно L0) |
| :--- | :--- | :--- |
| **L0 (Host)** | 100% | 100% |
| **L1 (Guest)** | 90–95% | 85–95% |
| **L2 (Nested)** | 70–85% | 60–80% |

**Факторы деградации:**

- Отсутствие поддержки **EPT/RVI** на хосте.
- Интенсивные операции ввода-вывода (Interrupts/VM-Exits).
- Использование программной эмуляции вместо аппаратных флагов.

### Ограничения технологии

1. **Функциональность:** Некоторые расширенные инструкции (напр. Intel SGX) могут не пробрасываться до уровня L2.
2. **Управление:** Изменение ресурсов ВМ «на горячую» (Hotplug) на уровне L2 часто ограничено.
3. **Обслуживание:** Требуется синхронное обновление гипервизоров на всех уровнях для обеспечения безопасности.

### Безопасность

Вложенная виртуализация увеличивает поверхность атаки:

- **Уязвимости гипервизора:** Ошибки в коде L1 могут быть использованы для компрометации L0.
- **Изоляция:** Рекомендуется использовать механизмы **SELinux** или **AppArmor** для ограничения прав процессов ВМ первого уровня.

### Альтернативные подходы к изоляции

Если вложенная виртуализация архитектурно избыточна, применяются более легкие методы:

- **Kata Containers** — запуск контейнеров в легковесных microVM.
- **Firecracker** — специализированный гипервизор для бессерверных вычислений и микро-ВМ.
- **LXC/LXD** — системные контейнеры (без вложенности ядра).

## Практические сценарии

### Сценарий 1: Мониторинг и диагностика

Для базовой проверки доступности KVM на уровнях L0 и L1 используйте методику из [Установка KVM — Проверка](../../kvm/installation.md#сценарий-1-проверка-поддержки-аппаратной-виртуализации).

Для мониторинга запущенных вложенных сред:

```bash
# Просмотр загрузки ресурсов ВМ (libvirt)
virt-top
```

### Сценарий 2: Решение типичных проблем (Troubleshooting)

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| Не применяется `nested=1` | Модуль ядра занят | Остановить все ВМ и перезагрузить модуль `kvm_intel/amd`. |
| Ошибка `VMX disabled` в L1 | BIOS/UEFI хоста L0 | Включить поддержку виртуализации в BIOS физического сервера. |
| L2 работает крайне медленно | Использование эмуляции | Проверить наличие `-cpu host` в параметрах запуска L1. |
