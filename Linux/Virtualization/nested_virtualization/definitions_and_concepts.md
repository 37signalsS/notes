# Вложенная виртуализация (Nested Virtualization) — Определения и концепции

В данном файле рассматриваются теоретические основы вложенной виртуализации, иерархия уровней, архитектурные требования, механизмы аппаратного ускорения и современные оптимизации для реализации в Linux (KVM).

## Определения

**Вложенная виртуализация (Nested Virtualization)** — технология, позволяющая запускать гипервизор (L1) внутри виртуальной машины, которая сама работает под управлением другого гипервизора (L0) на физическом оборудовании. Это создаёт многоуровневую среду выполнения, где каждый уровень добавляет свой слой абстракции и накладные расходы.

**Иерархия уровней:**

| Уровень | Описание | Роль |
| :--- | :--- | :--- |
| **L0** | Bare-Metal | Физический сервер и основной гипервизор (KVM). Работает в **VMX Root Mode** (Ring -1) или **SVM Root** (AMD). |
| **L1** | Guest Hypervisor | Виртуальная машина первого уровня, внутри которой запущен собственный гипервизор. |
| **L2** | Nested Guest | Вложенная виртуальная машина, запущенная внутри L1. |

*Примечание: Теоретически количество уровней (L3, L4...) может быть больше, но на практике это редко используется из-за экспоненциального роста накладных расходов и ограничений ядра Linux.*

## Базовые концепции

### Аппаратная поддержка и требования к L0

Для эффективной работы вложенной виртуализации на уровне L0 необходима поддержка расширений CPU, IOMMU и соответствующих версий ядра Linux и QEMU.

#### x86_64 — Intel VT-x

**Обязательные расширения:**
- **VT-x (VMX):** Режим корневого и не корневого операций. L0 работает в Root Mode, L1 — в Non-Root Mode.
- **EPT (Extended Page Tables):** Аппаратная двухуровневая трансляция физических адресов (2D Paging). Без EPT используется программный Shadow Page Tables с накладными расходами до 30%.
- **VPID (Virtual Processor ID):** Идентификатор для кэширования TLB записей L1/L2. Позволяет L0 сохранять TLB записи при переключении между гостями без принудительного сброса.
- **EPT AD (Access/Dirty bits):** Поддержка битов доступа и модификации в EPT, необходима для ballooning, KSM и миграции.

**Рекомендуемые расширения:**
- **Posted Interrupts:** Прямая доставка прерываний в L2 vCPU без участия L1.
- **Flex Priority:** Ускорение обработки APIC TPR, снижающее количество VM-Exits при изменении приоритета прерываний.
- **PMU (Performance Monitoring Unit) L2:** Возможность сбора счётчиков производительности для L2 через L0.

**Поддерживаемые процессоры (2025–2026):**
- Intel Core 5th gen+ (Broadwell и новее)
- Intel Xeon Scalable (Skylake, Ice Lake, Sapphire Rapids, Granite Rapids)
- Intel Atom (Snow Lake+)

**Требуемые версии ПО:**
- Ядро Linux: 5.15+ (базовая поддержка), 6.12+ (Virtual EPT для L2), 6.15+ (оптимизации guest_memfd)
- QEMU: 7.0+ (базовая), 8.0+ (живая миграция L1 с L2)
- libvirt: 9.0+ (полная поддержка XML конфигурации)

#### x86_64 — AMD-V

**Обязательные расширения:**
- **SVM (Secure Virtual Machine):** Архитектура аппаратной виртуализации AMD.
- **RVI (Rapid Virtualization Indexing) / NPT (Nested Page Tables):** Аналог EPT у Intel. Обеспечивает аппаратную трансляцию адресов для L2.
- **ASIDs (Address Space Identifiers):** Аналог VPID. Позволяют поддерживать отдельные TLB записи для каждого адресного пространства L1/L2.

**Рекомендуемые расширения:**
- **Pause Loop Filtering (PLP):** Позволяет L0 завершать busy-wait циклы в L1/L2, снижая ненужные VM-Exits.
- **BRK_INTO_DEBUG:** Оптимизация для отладчика, снижающая накладные расходы при трассировке.
- **IOMMU (AMD-Vi):** Аппаратная трансляция DMA для проброшенных устройств.

**Поддерживаемые процессоры (2025–2026):**
- AMD Ryzen (Zen 2, Zen 3, Zen 4, Zen 5)
- AMD EPYC (Rome, Milan, Genoa, Bergamo, Turin)
- AMD Ryzen Threadripper

**Особенности архитектуры:**
- AMD имеет более агрессивную аппаратную оптимизацию вложенности («world switch» требует меньше инструкций по сравнению с VT-x).
- Архитектура SVM изначально проектировалась с учётом поддержки вложенности, что даёт преимущество в производительности на поколения Zen 3+.

#### ARM64 — FEAT_NV и FEAT_NV2

**FEAT_NV (Nested Virtualization):** Расширение ARMv8.4+, позволяющее гипервизору L1 работать в режиме EL1 (kernel space), перехватывая системные регистры без обязательного участия L0.

**FEAT_NV2 (enhanced nested virtualization):** Внедрено в ARMv9, радикально ускоряет доступ к структурам управления в памяти за счёт аппаратной поддержки вложенных таблиц страниц и сокращения цепочек VM-Exits.

**Требования:**
- Ядро Linux: 6.16+ (полная поддержка FEAT_NV2)
- QEMU: 10.1+
- Параметр загрузки: `kvm-arm.mode=nested`

### Архитектура Nested KVM

Механизм Nested KVM базируется на минимизации вмешательства L0 через аппаратные оптимизации и умное перехватывание только критичных событий.

#### VM-Exits (Выходы из гостевого режима)

**VM-Exit** — событие переключения контекста с гостевого режима на режим гипервизора. Основной источник задержек во вложенных средах.

**Классификация VM-Exits по критичности для вложенности:**

| Тип Exit | Описание | Влияние на L2 | Минимизация |
| :--- | :--- | :--- | :--- |
| **EPT Violation** | Промах таблицы страниц L2 | Среднее | Virtual EPT — L0 обрабатывает напрямую |
| **MSR Write** | Запись в Model-Specific Register | Высокое | MSR bitmap в VMCS — L0 перехватывает, но L1 настраивает |
| **I/O Port** | Доступ к портам ввода-вывода | Высокое | VirtIO forwarding — исключает портовый I/O |
| **HLT** | Остановка CPU (idle) | Низкое | Парный halt — L0 может не пробуждать L1 |
| **CPUID** | Идентификация CPU | Среднее | Кэширование — L0 возвращает без L1 |
| **APIC** | Доступ к локальному APIC | Среднее | Virtual APIC — L0 обрабатывает напрямую |

**Цепочки VM-Exits (Exit Chains):** Наихудший сценарий — когда L2 вызывает Exit, который L0 не может обработать самостоятельно и передаёт в L1, а L1, в свою очередь, не может обработать и возвращает управление L0. Каждое звено добавляет 1–5 мкс задержки.

#### VMCS Shadowing (Intel) / SVM Optimization (AMD)

**VMCS (Virtual Machine Control Structure)** — структура данных в памяти, содержащая состояние виртуального процессора (регистры, флаги, указатели на таблицы страниц).

**Проблема без Shadowing:** Когда L2 выполняет привилегированную инструкцию, происходит VM-Exit в L0. L0 не знает о VMCS L2, поэтому не может корректно обработать Exit без участия L1. L1 должна быть запущена для обработки, что создаёт цепочку Exit L2 → L0 → L1 → L0.

**VMCS Shadowing:** Технология, при которой L0 создаёт «теневые» VMCS для L1, содержащие информацию об L2-гостях. L1 может изменять VMCS L2 напрямую, а L0 лишь валидирует изменения. Это разрывает цепочку Exit и снижает накладные расходы в 2–5 раз.

**Требования к аппаратуре:**
- Intel: VMCS Shadowing поддерживается на CPU семейств Broadwell+ (5th gen) и новее.
- AMD: Встроенная оптимизация «world switch» делает явное Shadowing менее критичным, но наличие RVI/NPT обязательно.

#### Virtual EPT / NPT (Two-Dimensional Paging, TDP)

**Extended Page Tables (EPT)** — аппаратная трансляция физических адресов. В обычной (не вложенной) виртуализации EPT содержит один уровень трансляции: Guest Virtual → Guest Physical → Host Physical.

**В вложенной среде:** L1 управляет EPT для L2. Когда L2 обращается к памяти, происходит двойной Walk:
1. L2: Guest Virtual → Guest Physical (через L1 EPT)
2. L1: Guest Physical → Host Physical (через L0 EPT)

**Virtual EPT:** L0 получает доступ к EPT L1 и может обрабатывать промахи страниц L2 напрямую, минуя L1. Это критично для производительности, так как исключает переключение контекста на каждый промах.

**NPT (Nested Page Tables) — AMD:** Аналог Virtual EPT у AMD. Работает через Reverse Map Table (RMP), что обеспечивает дополнительную защиту от атак на подмену страниц.

**guest_memfd (Guest Memory File Descriptor):** Механизм ядра Linux 6.15+, позволяющий управлять памятью гостя через файловые дескрипторы. Исключает отображение защищённой памяти в пространство пользователя хоста и снижает накладные расходы на обработку Page Faults в защищённых вложенных средах на 20–30%.

#### Posted Interrupts (PI)

Технология, позволяющая L0 доставлять прерывания (IRQ) напрямую в регистры L2 vCPU, минуя обработку в L1.

**Как работает:**
1. Устройство (например, сетевая карта) генерирует IRQ.
2. L0 получает IRQ и проверяет вектор в Posted Interrupt Descriptor (PID).
3. Если L2 vCPU активна и не блокирует прерывания — L0 записывает вектор напрямую в регистр виртуального APIC L2.
4. L1 не пробуждается, не происходит VM-Exit.

**Требования:** VT-d (Intel) или AMD-Vi (AMD), IOMMU в режиме `pt` (passthrough).

#### vCPU ASIDs / VPID

**ASID (Address Space Identifier) / VPID (Virtual Processor ID):** 16–20-битный идентификатор, присваиваемый каждому адресному пространству L1 или L2.

**Назначение:** Позволяет аппаратуре TLB кэшировать трансляции адресов для разных гостевых пространств параллельно. При переключении между L1 и L2 не требуется принудительный сброс (flush) TLB, что экономит 10–30 мкс на переключение.

**Поддержка:**
- Intel VPID: Broadwell+ (5th gen)
- AMD ASIDs: Все процессоры с AMD-V (SVM)

### Производительность и накладные расходы

Налог на вложенность (nested tax) — дополнительные задержки, вносимые каждым уровнем виртуализации. В 2026 году благодаря зрелости аппаратных расширений и оптимизациям в ядре Linux (6.15+) налог значительно снизился.

| Метрика | Оверхед L1 (vs Bare Metal) | Оверхед L2 (Nested vs L1) | Технология оптимизации |
| :--- | :--- | :--- | :--- |
| **CPU (вычисления)** | 1–2% | 5–8% | VMCS Shadowing, FEAT_NV2, PLP |
| **Память (latency)** | 3–5% | 10–12% | Virtual EPT, guest_memfd |
| **Сетевой I/O** | 5–7% | 12–18% | Posted Interrupts, vCPU ASIDs, virtio-forwarding |

**Факторы, влияющие на производительность L2:**
- **CPU mode L1:** При режиме `host-passthrough` потери минимальны. Эмуляция CPU (`qemu64`) увеличивает оверхед до 300%.
- **VMCS Shadowing / Virtual EPT:** Отсутствие увеличивает количество VM-Exits в 3–10 раз.
- **IOMMU:** Включение `iommu=pt` убирает адресную трансляцию DMA из критического пути.
- **SMT (Hyper-Threading):** Использование гипертредов для L1/L2 снижает производительность на 20–40% из-за contention на кэш L1.
- **Overcommit CPU:** Превышение отношения vCPU/pCPU > 1.5 на L0 приводит к росту `steal_time` и непредсказуемым задержкам для L2.

### Модель памяти и NUMA-топология

Каждый уровень виртуализации добавляет слой виртуализации ресурсов, что усложняет управление памятью и топологией NUMA.

#### Двухуровневая NUMA

1. **NUMA L0 → L1:** Если L1 размещена на NUMA-узле 0, а её vCPU привязаны к ядрам узла 1, каждый доступ к памяти добавляет 30–50 нс задержки через межъузловой интерconnect (UPI у Intel, Infinity Fabric у AMD).
2. **NUMA L1 → L2:** Гипервизор L1 видит только виртуальную топологию. `lscpu` и `numactl` внутри L1 покажут виртуальные ядра, а не физические pCPU L0. Для корректного пиннинга L2 используйте `<cputune>` в XML L1 с привязкой к конкретным vCPU L1.

**Практическое правило:** Размещайте L1 и её L2 на одном NUMA-узле L0. Используйте `numactl --hardware` на L0 для построения карты топологии перед размещением.

#### Кэширование и таблицы страниц

- **L0 EPT:** Управляет трансляцией Guest Physical (L1) → Host Physical.
- **L1 EPT:** Управляет трансляцией Guest Virtual (L2) → Guest Physical (L1).
- **TLB:** Каждый уровень имеет собственный TLB. При переключении контекста без VPID/ASIDs требуется глобальный flush TLB, добавляющий задержку.
- **Hugepages:** Для L1 резервируйте Hugepages на L0 с запасом 20% сверх потребностей L1, чтобы L1 могло выделять Hugepages для L2.

### Безопасность и поверхность атаки

Вложенная виртуализация расширяет поверхность атаки, так как компрометация L2 может привести к компрометации L1, а затем и L0.

**Угрозы:**
- **VM Escape из L2 в L1:** Ошибки в эмуляции устройств или обработке VM-Exits позволяют коду L2 выполнить привилегированные инструкции в контексте L1.
- **VM Escape из L1 в L0:** Аналогичная угроза на уровне L1. Чем больше поверхность атаки L1 (больше устройств, драйверов), тем выше риск.
- **DMA-атаки через проброшенные устройства:** Без IOMMU устройство, проброшенное в L1, может получить прямой доступ к памяти L0.

**Мероприятия по снижению рисков:**
- **sVirt (SELinux) / AppArmor:** Каждый процесс QEMU/KVM, исполняющий L1, должен быть помечен уникальным меткой (SELinux) или профилем (AppArmor). Это ограничивает доступ к ресурсам L0 при успешном VM Escape.
- **IOMMU:** Включите `intel_iommu=on iommu=pt` или `amd_iommu=on iommu=pt` в параметры загрузки L0. Режим `pt` убирает аппаратную трансляцию DMA из критического пути, но сохраняет изоляцию.
- **Минимизация поверхности L1:** Запускайте в L1 только необходимые сервисы. Используйте минималистичные гостевые ОС (Alpine, Ubuntu Core) для L1, если L1 используется только как промежуточный гипервизор.
- **Изоляция L2 внутри L1:** Аналогично L0, на L1 применяйте sVirt/AppArmor для процессов QEMU, исполняющих L2.

### Обязательные условия конфигурации L1

Для работы вложенной виртуализации конфигурация ВМ L1 должна удовлетворять следующим требованиям:

1. **Режим CPU:**
   - Обязательно `host-passthrough` (Intel/AMD) или `host` (Proxmox).
   - В XML libvirt: `<cpu mode='host-passthrough' check='none'>`.
   - Без этого режима L1 не получит VT-x/AMD-V флаги, и вложенность невозможна.

2. **Обязательные флаги CPU:**
   - Intel: `<feature policy='require' name='vmx'/>`
   - AMD: `<feature policy='require' name='svm'/>`

3. **Hyper-V Enlightenments (для Windows L1):**
   ```xml
   <features>
     <hyperv>
       <relaxed state='on'/>
       <vapic state='on'/>
       <spinlocks state='on' retries='8191'/>
       <evmcs state='on'/>
     </hyperv>
   </features>
   ```

4. **IOThreads (для I/O производительности):**
   ```xml
   <iothreads>4</iothreads>
   <cputune>
     <iothreadpin iothread='1' cpuset='2'/>
   </cputune>
   ```

5. **NUMA-привязка:**
   - `<numatune>` с `mode='strict'` и указанием `nodeset` для предотвращения миграции памяти между NUMA-узлами.

### Экспресс-проверка аппаратной готовности L0

Перед настройкой убедитесь, что аппаратная виртуализация доступна и активирована в ядре.

**1. Проверка флагов CPU (x86_64):**
```bash
egrep -c '(vmx|svm)' /proc/cpuinfo
# → 0: Поддержка отсутствует или выключена в BIOS
# → 1+: Аппаратная поддержка присутствует
```

**2. Проверка статуса в модуле ядра (Intel):**
```bash
cat /sys/module/kvm_intel/parameters/nested
# → Y или 1: Вложенность включена
# → N или 0: Вложенность выключена
```

**3. Проверка статуса в модуле ядра (AMD):**
```bash
cat /sys/module/kvm_amd/parameters/nested
# → 1: Вложенность включена
# → 0: Вложенность выключена
```

**4. Проверка IOMMU:**
```bash
# Intel
dmesg | grep -iE 'DMAR|IOMMU'
# → DMAR: IOMMU enabled

# AMD
dmesg | grep -iE 'AMD-Vi|IOMMU'
# → AMD-Vi: IOMMU enabled
```

**5. Проверка для ARM64 (FEAT_NV):**
```bash
dmesg | grep -i "kvm.*nested"
# → [    1.234567] kvm [1]: VHE+NV2 mode initialized successfully
```

### Конфигурационный чеклист L1 (теоретическая валидация)

Перед запуском L1 проверьте, что XML-конфигурация содержит:

| Элемент | Обязателен | Назначение |
| :--- | :--- | :--- |
| `<cpu mode='host-passthrough'>` | Да | Передача полного аппаратного контекста L1 |
| `<feature policy='require' name='vmx'/>` | Да (Intel) | Гарантия наличия VT-x в L1 |
| `<feature policy='require' name='svm'/>` | Да (AMD) | Гарантия наличия AMD-V в L1 |
| `<hyperv><evmcs state='on'/></hyperv>` | Да (Windows L1) | Аппаратное ускорение Hyper-V |
| `<numatune>` | Рекомендован | Изоляция NUMA для L1 |
| `<cputune><vcpupin .../></cputune>` | Рекомендован | Жёсткий пиннинг vCPU L1 к pCPU L0 |
| `<iothreads>` | Рекомендован | Выделенные потоки для обработки I/O |

### Мониторинг

- [Мониторинг KVM: Prometheus, libvirt_exporter, Grafana](../kvm/kvm_monitoring.md) — построение стека мониторинга, ключевые метрики, алерты.
- **Ключевые метрики для вложенных сред:** steal time (>5% = проблема), VM-Exits (>100k/s = bottleneck), balloon.actual < balloon.current * 0.8 = дефицит памяти.

### Безопасность

- [Безопасность KVM-хостов: Hardening, sVirt, polkit, LUKS](../kvm/kvm_security_hardening.md) — изоляция через SELinux/AppArmor, шифрование, nwfilter.
- **Важно для вложенности:** Расширенная поверхность атаки (L2 → L1 → L0). Обязательно включайте sVirt для L1 и L2, IOMMU (`iommu=pt`), минимальную поверхность L1.

### Сеть

- [Сетевые основы KVM: libvirt networks, dnsmasq, nwfilter](../kvm/kvm_networking_fundamentals.md) — NAT, bridge, фильтрация.
- [Продвинутая сеть KVM: OVS, VXLAN, SR-IOV](../kvm/kvm_networking_advanced.md) — топологии для production.
- **Особенности вложенности:** Multi-level bridging, MTU при оверлейных сетях (1400–1450), Posted Interrupts для снижения latency.

### Хранение и резервное копирование

- [Резервное копирование и восстановление ВМ (KVM)](../kvm/vm_backup_dr.md) — стратегии бэкапа, RPO/RTO, инкрементальное копирование.
- **Для вложенных сред:** Бэкап L1 включает все L2. Используйте shared storage (NFS/Ceph) для live-migration.

### Высокая доступность

- [Высокая доступность KVM: Pacemaker, DRBD, Fencing](../kvm/kvm_ha.md) — кластеризация, failover, STONITH.
- **Для вложенных сред:** HA для L1 автоматически перезапускает все L2. Тестируйте failover на тестовом стенде.
