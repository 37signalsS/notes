# Приватный Apt-репозиторий с reprepro: Определения и концепции

## Определения

Ниже приведены ключевые термины, необходимые для понимания архитектуры и эксплуатации внутренних хранилищ пакетов в формате DEB.

**`reprepro`** — автономный инструмент командной строки (CLI) для создания и управления репозиториями пакетов Debian. Генерирует статическую структуру индексов и метаданных, что исключает необходимость в специализированных серверных приложениях (достаточно Nginx или Apache).

**GPG (GNU Privacy Guard) и подпись репозитория** — механизм обеспечения доверия к источнику ПО.
- **`Release.gpg`** — отсоединённая бинарная подпись файла `Release`.
- **`InRelease`** — файл, содержащий метаданные `Release` и встроенную текстовую подпись (clear-signed).
- **Подпись пакетов** — в отличие от подписи репозитория, выполняется на этапе сборки `.deb` (рекомендуется для сквозной проверки целостности).

**Pool (Пул)** — глобальное хранилище всех файлов пакетов (`.deb`, `.dsc`, `.tar.gz`) внутри репозитория. Файлы организуются в иерархию по начальным буквам их названий, что позволяет использовать один и тот же файл в разных дистрибутивах без дублирования на диске.

**Дистрибутив (Distribution)** — логическая группа пакетов, предназначенная для конкретного выпуска ОС или ветки разработки.
- **Codename** — техническое имя релиза (например, `bookworm`, `jammy`, `noble`). Является первичным ключом для поиска.
- **Suite** — алиас для дистрибутива (например, `stable`, `testing`, `lts`).

**Компонент (Component)** — логический раздел внутри дистрибутива (например, `main`, `contrib`, `non-free`). Позволяет разделять ПО по лицензиям или назначению.

**Berkeley DB (BDB)** — встроенная база данных, которую `reprepro` использует для хранения текущего состояния репозитория, отслеживания версий пакетов и связей между ними. Файлы БД хранятся в директории `dbs/`.

**Override-файлы** — механизмы переопределения метаданных (приоритет, секция) для пакетов без изменения самого `.deb`-файла.

## Основные концепции

### Архитектура файловой системы

Репозиторий `reprepro` имеет фиксированную структуру, где разделены конфигурация, метаданные и данные:

```text
my-repo/
├── conf/                 # Конфигурация (distributions, updates, incoming)
│   └── distributions     # Единственный обязательный файл
├── dbs/                  # База данных состояний (Berkeley DB)
├── dists/                # Публичные индексы (Packages, Release)
│   └── <codename>/
│       ├── main/
│       │   ├── binary-amd64/
│       │   └── source/
│       └── InRelease     # Подписанный индекс
├── pool/                 # Фактические данные (дедуплицированные .deb)
│   └── main/             # Группировка по компоненту
│       └── a/            # Группировка по первой букве пакета
│           └── app/      # Группировка по имени пакета
└── incoming/             # (Опционально) Буфер для автоматического импорта
```

### Параметры конфигурации дистрибутивов

Файл `conf/distributions` определяет «лицо» репозитория. Каждый блок настроек описывает один целевой релиз.

| Поле | Описание | Примеры |
| :--- | :--- | :--- |
| **Origin** | Имя создателя репозитория | `CompanyCorp`, `SRE-Team` |
| **Label** | Название репозитория | `Internal Tools`, `Custom Builds` |
| **Codename** | Техническое имя (ключевое) | `jammy`, `noble`, `bookworm` |
| **Suite** | Функциональный алиас | `stable`, `prod` |
| **Architectures** | Поддерживаемые платформы | `amd64`, `arm64`, `all`, `source` |
| **Components** | Секции репозитория | `main`, `dev`, `restricted` |
| **SignWith** | GPG Fingerprint для подписи | `0xABC123...` или `yes` (ключ по умолчанию) |
| **Contents** | Генерация индексов содержимого | `udeb`, `nodev` (поддержка `apt-file`) |

### Механизм обновлений (Updates)

Через файл `conf/updates` `reprepro` может выступать в роли селективного зеркала. Это позволяет импортировать пакеты из внешних репозиториев (например, официальных зеркал Debian) во внутренний репозиторий, применяя фильтры по имени или версии.

### Автоматизация входящих пакетов (Incoming)

Файл `conf/incoming` позволяет настроить директорию «горячего» приема. При поступлении файлов в этот каталог и вызове команды `reprepro processincoming`, утилита автоматически проверяет подписи `.changes` файлов и перемещает пакеты в соответствующие дистрибутивы.

### Взаимодействие с Apt Pinning

Для обеспечения приоритета внутреннего репозитория над официальными используются поля `Origin` и `Label`. В файлах `/etc/apt/preferences` на стороне клиента задается вес (`Pin-Priority`), что позволяет принудительно устанавливать версии от `CompanyCorp`, даже если в интернете доступна более новая версия. Подробнее в документе **[Apt Pinning](../deb_apt_pinning.md)**.

## Практические сценарии

### Проектирование иерархии для Enterprise-среды

При планировании структуры рекомендуется:
1. **Использование компонентов для стадий:** вместо создания отдельных репозиториев для `test` и `prod`, можно использовать компоненты `main` (stable) и `unstable` внутри одного дистрибутива.
2. **Унификация Codename:** если компания использует фиксированную версию ОС (например, Ubuntu 22.04), все внутренние инструменты должны публиковаться под кодовым именем `jammy`.
3. **Архитектура `all`:** для скриптов и конфигураций (независимых от архитектуры) обязательно указывать `Architectures: all`, чтобы не дублировать метаданные для amd64/arm64.

### Обеспечение отказоустойчивости

Поскольку `reprepro` генерирует статику, репозиторий легко масштабируется:
- **CDN/Object Storage:** файлы из `dists/` и `pool/` могут быть синхронизированы с S3-совместимым хранилищем.
- **ReadOnly-зеркала:** достаточно выполнить `rsync` директорий `dists/` и `pool/` на вторичные веб-серверы. Директории `conf/` и `dbs/` при этом должны оставаться приватными.
