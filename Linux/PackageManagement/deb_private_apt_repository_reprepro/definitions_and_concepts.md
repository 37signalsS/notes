# Приватный Apt-репозиторий с reprepro: Определения и концепции

## Определения

Ниже приведены основные термины, используемые при создании и эксплуатации внутренних хранилищ программного обеспечения для систем на базе DEB (Debian Package).

**`reprepro`** — специализированная утилита интерфейса командной строки (CLI) для создания и управления репозиториями пакетов формата `.deb`. В отличие от динамических серверов, `reprepro` генерирует статическую структуру файлов и индексов, которую можно раздавать любым веб-сервером (Nginx, Apache).

**GPG (GNU Privacy Guard) — подпись репозитория** — механизм обеспечения целостности и подлинности данных.
- **`Release.gpg`** — отдельный файл отсоединенной подписи для файла `Release`.
- **`InRelease`** — современный формат, объединяющий метаданные и подпись в одном файле.
Гарантирует, что пакеты не были изменены третьей стороной (защита от атак MitM).

**Pool (Пул)** — механизм хранения файлов в `reprepro`, обеспечивающий дедупликацию. Все `.deb` пакеты хранятся в иерархии каталогов `pool/` на основе первой буквы имени пакета. Если один и тот же пакет (с идентичной контрольной суммой) используется в нескольких дистрибутивах, он хранится на диске в единственном экземпляре.

**Дистрибутив (Distribution)** — логическое объединение пакетов для конкретной версии ОС.
- **Codename** — уникальное кодовое имя релиза (например, `jammy`, `noble`, `bookworm`).
- **Suite** — функциональное состояние (например, `stable`, `testing`).

**Компонент (Component)** — подраздел дистрибутива, определяющий категорию или лицензионную чистоту ПО (например, `main`, `contrib`, `non-free`).

## Основные концепции

### Архитектура репозитория

При инициализации `reprepro` формирует строго детерминированную структуру каталогов:

```text
my-repo/
├── conf/
│   └── distributions      # Основной конфигурационный файл
├── dbs/                   # Внутренняя база данных состояний (Berkeley DB)
├── dists/                 # Метаданные и индексы (Packages, Release)
│   └── <codename>/
│       ├── main/
│       │   ├── binary-amd64/
│       │   └── source/
│       └── InRelease      # Подписанный индекс дистрибутива
├── pool/                  # Единое хранилище фактических .deb пакетов
│   └── main/
│       └── a/
│           └── app/       # Группировка по имени пакета
└── incoming/              # (Опционально) Каталог для автоматического импорта
```

### Конфигурация дистрибутивов

Файл `conf/distributions` определяет правила публикации. Каждый блок настроек описывает один целевой релиз.

| Поле | Описание | Типовое значение |
| :--- | :--- | :--- |
| **Origin** | Идентификатор организации/автора | `CompanyCorp` |
| **Label** | Человекочитаемое описание | `Internal Tools` |
| **Codename** | Кодовое имя ОС (уникальный ключ) | `jammy`, `noble`, `bookworm` |
| **Suite** | Алиас для Codename | `stable` |
| **Architectures** | Поддерживаемые платформы | `amd64 arm64 source` |
| **Components** | Секции репозитория | `main contrib` |
| **SignWith** | ID GPG-ключа для подписи | `0xABCDEF1234567890` |
| **Description** | Краткая справка о назначении | `Internal repository for SRE tools` |

### Механизм обновления и зеркалирования

`reprepro` поддерживает концепцию **Updates**, позволяя использовать репозиторий как «умное зеркало». Через файл `conf/updates` можно настроить фильтрацию пакетов из официальных источников, объединяя их с собственными сборками в рамках одного внутреннего `Codename`.

### Интеграция с Apt Pinning

Параметры `Origin` и `Label` являются ключевыми селекторами для механизма **[Apt Pinning](../deb_apt_pinning.md)**. Это позволяет администраторам задавать приоритет `P > 1000` для внутреннего репозитория, гарантируя установку корпоративных версий пакетов даже при наличии более новых версий в официальных репозиториях ОС.

## Практические сценарии

### Сценарий: Проектирование иерархии репозитория

При планировании архитектуры следует учитывать:

1. **Жизненный цикл ОС:** поддержка актуальных (LTS) версий. На 2024–2025 гг. это Ubuntu `noble` (24.04), `jammy` (22.04) и Debian `bookworm` (12).
2. **Изоляция окружений:** использование разных компонентов (например, `main` для prod, `dev` для тестирования) внутри одного дистрибутива вместо создания множества отдельных репозиториев.
3. **Безопасность ключей:** использование отдельных GPG-ключей для разных сред (Staging/Production).
