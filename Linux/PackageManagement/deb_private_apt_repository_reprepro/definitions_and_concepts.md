# Приватный Apt-репозиторий с reprepro: Определения и концепции

## Определения

Ниже приведены ключевые термины, необходимые для понимания архитектуры и эксплуатации внутренних хранилищ пакетов в формате DEB.

**`reprepro`** — автономный инструмент командной строки (CLI) для создания и управления репозиториями пакетов Debian. Генерирует статическую структуру индексов и метаданных, что исключает необходимость в специализированных серверных приложениях (достаточно Nginx или Apache). В отличие от `aptly`, не требует постоянной работы базы данных, что упрощает резервное копирование и восстановление. Поддерживает множественные дистрибутивы и архитектуры, фильтрацию пакетов, hook-скрипты и автоматический импорт из входящей очереди.

**GPG (GNU Privacy Guard) и подпись репозитория** — механизм обеспечения доверия к источнику ПО.
- **`Release.gpg`** — отсоединённая бинарная подпись файла `Release`.
- **`InRelease`** — файл, содержащий метаданные `Release` и встроенную текстовую подпись (clear-signed).
- **Подпись пакетов** — в отличие от подписи репозитория, выполняется на этапе сборки `.deb` (рекомендуется для сквозной проверки целостности).

**Pool (Пул)** — глобальное хранилище всех файлов пакетов (`.deb`, `.dsc`, `.tar.gz`) внутри репозитория. Файлы организуются в иерархию по начальным буквам их названий, что позволяет использовать один и тот же файл в разных дистрибутивах без дублирования на диске. Для дедупликации `reprepro` использует жёсткие ссылки (hardlinks).

**Дистрибутив (Distribution)** — логическая группа пакетов, предназначенная для конкретного выпуска ОС или ветки разработки.
- **Codename** — техническое имя релиза (например, `bookworm`, `jammy`, `noble`). Является первичным ключом для поиска.
- **Suite** — алиас для дистрибутива (например, `stable`, `testing`, `lts`).

**Компонент (Component)** — логический раздел внутри дистрибутива (например, `main`, `contrib`, `non-free`). Позволяет разделять ПО по лицензиям или назначению. В корпоративной среде компоненты часто используются для разделения стадий разработки (`main` для stable, `unstable` для тестирования).

**Berkeley DB (BDB)** — встроенная база данных, которую `reprepro` использует для хранения текущего состояния репозитория, отслеживания версий пакетов и связей между ними. Файлы БД хранятся в директории `dbs/`. Важно: `reprepro` использует BDB версии 1.85, что накладывает ограничения на параллельный доступ и требует аккуратного резервного копирования.

**Override-файлы** — механизмы переопределения метаданных (приоритет, секция) для пакетов без изменения самого `.deb`-файла.

**`dists/`** — директория с публичными индексами репозитория. Содержит файлы `Packages`, `Sources`, `Release` и их подписи. Именно эти файлы читает `apt update` на клиенте. Файлы из `dists/` отдаются через веб-сервер и могут кэшироваться длительно благодаря неизменяемости после `export`.

**`Packages`** — текстовый индекс всех доступных пакетов в дистрибутиве/компоненте/архитектуре. Содержит имя пакета, версию, зависимости, размер, контрольные суммы. Генерируется автоматически при каждом `reprepro export` или `reprepro update`.

**`Release`** — главный мета-файл репозитория, содержащий контрольные суммы всех индексных файлов (`Packages`, `Sources`), дату сборки и информацию о дистрибутиве (Origin, Label, Codename, Suite). Подписывается GPG-ключом для обеспечения целостности.

**`conf/distributions`** — основной конфигурационный файл `reprepro`, определяющий список дистрибутивов, их метаданные и параметры подписи. Без этого файла `reprepro` не может функционировать.

**`conf/updates`** — конфигурационный файл для селективного зеркалирования внешних репозиториев. Позволяет автоматически импортировать пакеты из upstream-источников с фильтрацией.

**`conf/incoming`** — конфигурация директории «горячего» приёма для автоматического импорта пакетов.

**Hook-скрипты** — исполняемые файлы, которые `reprepro` вызывает на определённых этапах обработки пакетов (до или после добавления, удаления). Используются для интеграции с CI/CD, отправки уведомлений, запуска дополнительных проверок.

**Apt Pinning** — механизм управления приоритетами пакетов на стороне клиента. Позволяет задать вес (Pin-Priority) определённым репозиториям или версиям, что принудительно устанавливает версии из внутреннего репозитория, даже если в официальных источниках доступна более новая версия.

## Основные концепции

### Предварительные требования

| Категория | Требование | Примечание |
| :--- | :--- | :--- |
| **ОС** | Debian 11+, Ubuntu 20.04+ | Для production рекомендуются LTS-релизы |
| **Пакеты** | `reprepro`, `gnupg`, `nginx`/`apache2` | Минимальный набор для раздачи репозитория |
| **Пользователь** | Dedicated-пользователь без shell | Например, `reprepro:x` с `/usr/sbin/nologin` |
| **Файловая система** | ext4, xfs или btrfs | Должна поддерживать hardlinks для дедупликации pool |
| **Энтропия** | ≥ 1000 бит в `/proc/sys/kernel/random/entropy_avail` | На виртуальных машинах без `haveged` генерация ключей может зависнуть |
| **Сеть** | HTTPS для клиентского доступа | TLS-сертификат от внутреннего CA или публичного |
| **Хранилище** | Отдельный раздел или LVM LV | Рекомендуется отдельный от корневого раздела для роста |

**Начальное состояние системы перед настройкой:**
```bash
# Создание dedicated-пользователя
useradd -r -s /usr/sbin/nologin -m reprepro

# Создание структуры
mkdir -p /srv/repo/{conf,dists,pool,incoming,dbs}
chown -R reprepro:reprepro /srv/repo
chmod 0700 /srv/repo/conf
chmod 0700 /srv/repo/dbs
chmod 0755 /srv/repo/pool
chmod 0755 /srv/repo/dists
chmod 0750 /srv/repo/incoming
```

### Архитектура файловой системы

Репозиторий `reprepro` имеет фиксированную структуру, где разделены конфигурация, метаданные и данные:

```text
my-repo/
├── conf/                 # Конфигурация (distributions, updates, incoming)
│   └── distributions     # Единственный обязательный файл
├── dbs/                  # База данных состояний (Berkeley DB)
├── dists/                # Публичные индексы (Packages, Release)
│   └── <codename>/
│       ├── main/
│       │   ├── binary-amd64/
│       │   └── source/
│       └── InRelease     # Подписанный индекс
├── pool/                 # Фактические данные (дедуплицированные .deb)
│   └── main/             # Группировка по компоненту
│       └── a/            # Группировка по первой букве пакета
│           └── app/      # Группировка по имени пакета
└── incoming/             # (Опционально) Буфер для автоматического импорта
```

**Важно для SRE:**
- Директории `conf/` и `dbs/` должны быть доступны только пользователю `reprepro` (режим `0700`). Публичное чтение этих директорий приведёт к утечке конфигурации и секретных ключей.
- Директория `incoming/` должна иметь отдельные права (например, `0750` с группой `reprepro`) для разрешения загрузки файлов CI/CD-системами без полного доступа ко всему репозиторию.
- Файлы в `pool/` могут отдаваться через Nginx/Apache с долгим TTL (недели/месяцы), так как они не меняются после публикации.

### Жизненный цикл пакета

1. **Сборка** — `.deb` создаётся через `dpkg-buildpackage` или `debuild` в изолированной среде (sbuild, pbuilder).
2. **Подпись** — `.changes`-файл подписывается GPG-ключом разработчика (`debsign`).
3. **Импорт** — `reprepro includedeb` или `processincoming` перемещает пакет в `pool/` и обновляет `dbs/`.
4. **Экспорт** — `reprepro export` перегенерирует `Packages` и `Release`, подписывает их.
5. **Распространение** — клиенты получают файлы через `apt update`.

### Параметры конфигурации дистрибутивов

Файл `conf/distributions` определяет «лицо» репозитория. Каждый блок настроек описывает один целевой релиз.

| Поле | Описание | Примеры |
| :--- | :--- | :--- |
| **Origin** | Имя создателя репозитория | `CompanyCorp`, `SRE-Team` |
| **Label** | Название репозитория | `Internal Tools`, `Custom Builds` |
| **Codename** | Техническое имя (ключевое) | `jammy`, `noble`, `bookworm` |
| **Suite** | Функциональный алиас | `stable`, `prod` |
| **Architectures** | Поддерживаемые платформы | `amd64`, `arm64`, `all`, `source` |
| **Components** | Секции репозитория | `main`, `dev`, `restricted` |
| **SignWith** | GPG Fingerprint для подписи | `0xABC123...` или `yes` (ключ по умолчанию) |
| **Contents** | Генерация индексов содержимого | `udeb`, `nodev` (поддержка `apt-file`) |

**Для SRE:** Поля `Origin` и `Label` критически важны для Apt Pinning на стороне клиента. Рекомендуется использовать уникальные и стабильные значения, которые не меняются между релизами.

### Механизм обновлений (Updates)

Через файл `conf/updates` `reprepro` может выступать в роли селективного зеркала. Это позволяет импортировать пакеты из внешних репозиториев (например, официальных зеркал Debian) во внутренний репозиторий, применяя фильтры по имени или версии.

**Важно:** При использовании `updates` рекомендуется хранить копию конфигурации в системе управления версиями, чтобы можно было воссоздать фильтры при восстановлении.

### Автоматизация входящих пакетов (Incoming)

Файл `conf/incoming` позволяет настроить директорию «горячего» приема. При поступлении файлов в этот каталог и вызове команды `reprepro processincoming`, утилита автоматически проверяет подписи `.changes` файлов и перемещает пакеты в соответствующие дистрибутивы.

**Для SRE:** `incoming` удобен для интеграции с CI/CD, но требует строгого контроля доступа. Рекомендуется использовать отдельного пользователя с ограниченными правами для загрузки и регулярно проверять логи на предмет неавторизованных пакетов.

### Взаимодействие с Apt Pinning

Для обеспечения приоритета внутреннего репозитория над официальными используются поля `Origin` и `Label`. В файлах `/etc/apt/preferences` на стороне клиента задается вес (`Pin-Priority`), что позволяет принудительно устанавливать версии от `CompanyCorp`, даже если в интернете доступна более новая версия. Подробнее в документе **[Apt Pinning](../deb_apt_pinning.md)**.

### Безопасность и изоляция

**Привилегии:**
- Запускайте `reprepro` от dedicated-пользователя (например, `reprepro`) без shell-доступа (`/usr/sbin/nologin`).
- Директория `conf/` должна иметь режим `0700` — доступ только для владельца.
- Директория `dbs/` должна иметь режим `0700` — защита от несанкционированного доступа к состоянию репозитория.
- GPG-ключи должны храниться в защищённом хранилище (`~reprepro/.gnupg/` с правами `0700`).

**Сетевые ограничения:**
- Через веб-сервер (Nginx/Apache) отдавайте только `dists/` и `pool/`.
- Запретите доступ к `conf/`, `dbs/`, `incoming/` на уровне веб-сервера или firewall.

### Резервное копирование и восстановление

Поскольку `reprepro` генерирует статику, репозиторий легко резервируется:
- **Полная копия:** `tar czf repo-backup.tar.gz --exclude='dbs/__db.*' -C /srv/repo .`
- **БД Berkeley DB:** копируется лучше всего при отсутствии активных операций записи. Используйте `cp -a dbs/ backup/dbs/` после остановки `reprepro`.
- **Инкрементальные бэкапы:** `rsync -avz --delete /srv/repo/ /mnt/backup/repo/`
- **Восстановление:** `tar xzf` + `cp -a dbs/` + `reprepro check` + `reprepro export`

## Практические сценарии

### Проектирование иерархии для Enterprise-среды

При планировании структуры рекомендуется:
1. **Использование компонентов для стадий:** вместо создания отдельных репозиториев для `test` и `prod`, можно использовать компоненты `main` (stable) и `unstable` внутри одного дистрибутива.
2. **Унификация Codename:** если компания использует фиксированную версию ОС (например, Ubuntu 22.04), все внутренние инструменты должны публиковаться под кодовым именем `jammy`.
3. **Архитектура `all`:** для скриптов и конфигураций (независимых от архитектуры) обязательно указывать `Architectures: all`, чтобы не дублировать метаданные для amd64/arm64.
4. **Изоляция компонентов:** используйте отдельные компоненты для пакетов с разным уровнем доступа (например, `public` для открытых пакетов, `restricted` для внутренних инструментов).

### Обеспечение отказоустойчивости

- **Вторичные серверы:** достаточно выполнить `rsync` директорий `dists/` и `pool/` на вторичные веб-серверы. Директории `conf/` и `dbs/` при этом должны оставаться приватными.
- **Мониторинг:** проверяйте целостность репозитория через `reprepro check` и `reprepro verify` в рамках мониторинговых скриптов.
- **Резервное копирование:** следуйте процедуре, описанной в разделе «Резервное копирование и восстановление».
