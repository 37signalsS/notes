# Зеркалирование YUM/DNF-репозиториев

## Определения

Ниже приведены основные термины, используемые в процессе создания локальных копий репозиториев для систем на базе RPM (Red Hat Package Manager).

**Локальное зеркало (Local Mirror)** — полная или частичная копия удалённого репозитория пакетов, размещённая в локальной сети или на изолированном сервере. Позволяет экономить внешний трафик и обеспечивать доступ к ПО в закрытых контурах.

**Репозиторий-источник (Upstream Repository)** — официальный или доверенный удалённый сервер, с которым выполняется синхронизация локального зеркала.

**Синхронизация (Synchronization)** — процесс обновления данных локального зеркала до состояния, идентичного источнику. Включает загрузку новых пакетов и удаление устаревших.

**Метаданные репозитория** — набор служебных файлов (обычно в формате XML), содержащих информацию о версиях пакетов, их зависимостях и контрольных суммах. Ключевой файл — `repomd.xml`.

## Основные концепции

### Назначение зеркалирования

Использование локальных зеркал для пакетных менеджеров DNF (Dandified YUM) и YUM (Yellowdog Updater, Modified) необходимо для решения следующих задач:

- **Ускорение обновлений**: Передача данных в локальной сети (1–40 Gbps) значительно быстрее загрузки через интернет.
- **Инфраструктура Air-Gapped**: Обеспечение работы серверов в изолированных сетях без прямого доступа к интернету.
- **Контроль версий**: Возможность заморозки состояния репозитория на определенную дату для обеспечения идентичности окружений (Staging/Production).

### Архитектура процесса (DNF Reposync)

В современных дистрибутивах (RHEL 8/9, Fedora) `reposync` является плагином DNF. Процесс создания зеркала состоит из этапов:

1.  **Загрузка (reposync)**: Скачивание RPM-пакетов и, при необходимости, метаданных.
2.  **Индексация (createrepo_c)**: Генерация файлов индексов для скачанной структуры. Для репозиториев AppStream требуется дополнительная обработка метаданных модулей (`modules.yaml`).
3.  **Публикация**: Предоставление доступа по протоколу HTTP/HTTPS через веб-сервер (Nginx или Apache).

### Особенности AppStream и модульности

Репозитории типа `AppStream` в RHEL-подобных системах содержат метаданные модулей. При зеркалировании важно использовать флаг `--download-metadata`, чтобы `reposync` сохранил оригинальные модульные зависимости, иначе простым `createrepo_c` их не восстановить.

## Практические сценарии

### Сценарий 1: Создание зеркала на базе RHEL 9 / AlmaLinux 9

#### 1. Подготовка инструментария

```bash
# Установка утилит синхронизации, индексации и веб-сервера
sudo dnf install dnf-plugins-core createrepo_c nginx
```

#### 2. Синхронизация репозитория

```bash
# Создание базовой директории
sudo mkdir -p /var/www/html/repos/alma9

# Синхронизация BaseOS (только новейшие версии пакетов для экономии места)
sudo dnf reposync --repoid=baseos --download-path=/var/www/html/repos/alma9 --newest-only --download-metadata
# → result: загрузка RPM-файлов и метаданных в указанный путь
```

#### 3. Генерация метаданных

Если `reposync` загрузил метаданные (`--download-metadata`), `createrepo_c` может не потребоваться для базового использования, но для создания кастомных срезов он необходим:

```bash
# Инициализация метаданных (если они не были загружены автоматически)
sudo createrepo_c \
    --general-compress-type zstd \
    --no-database \
    /var/www/html/repos/alma9/baseos
```

#### 4. Настройка публикации (Nginx)

```bash
# Пример конфигурации Nginx (/etc/nginx/conf.d/repo.conf)
server {
    listen 80;
    server_name repo.local;
    root /var/www/html/repos;
    location / {
        autoindex on; # Разрешить просмотр структуры директорий
    }
}

# Запуск сервиса
sudo systemctl enable --now nginx
```

### Сценарий 2: Использование зеркала на клиентах (Air-Gapped)

На клиентских машинах необходимо создать файл конфигурации репозитория.

```ini
# /etc/yum.repos.d/local-mirror.repo
[local-baseos]
name=Local AlmaLinux 9 BaseOS
baseurl=http://repo.local/alma9/baseos/
enabled=1
gpgcheck=1
# Путь к локальной копии ключа или URL на сервере зеркала
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-AlmaLinux
```

---

### Сценарий 3: Автоматизация через systemd timer

Вместо `cron` рекомендуется использовать таймеры systemd для более гибкого управления (например, запуск только при наличии сети).

```ini
# /etc/systemd/system/repo-sync.service
[Unit]
Description=RPM Repository Synchronization

[Service]
Type=oneshot
ExecStart=/usr/bin/dnf reposync --repoid=baseos --download-path=/var/www/html/repos/alma9 --newest-only --delete --download-metadata
ExecStartPost=/usr/bin/createrepo_c --update --general-compress-type zstd --no-database /var/www/html/repos/alma9/baseos
```

```ini
# /etc/systemd/system/repo-sync.timer
[Unit]
Description=Daily RPM Repo Sync

[Timer]
OnCalendar=daily
Persistent=true

[Install]
WantedBy=timers.target
```

## Дополнительная информация

### Требования к дисковому пространству (ориентировочно на 2025 г.)

| Дистрибутив | BaseOS | AppStream | Полное зеркало (+Extras, CRB) |
| :--- | :--- | :--- | :--- |
| **AlmaLinux 9** | ~15 GB | ~55 GB | ~120 GB |
| **Fedora 41** | ~80 GB | — | ~350 GB |

*Примечание: Использование флага `--newest-only` сокращает объем в 2–3 раза.*

### Рекомендации по эксплуатации

1.  **GPG-ключи**: Всегда синхронизируйте и распространяйте GPG-ключи вместе с пакетами. Без них `gpgcheck=1` заблокирует установку.
2.  **Очистка (--delete)**: Обязательно используйте этот флаг, чтобы удалять пакеты, исключенные из официального репозитория, предотвращая бесконтрольное разрастание зеркала.
3.  **Инкрементальность**: `reposync` и `createrepo_c --update` работают инкрементально, загружая/обрабатывая только изменившиеся файлы.
