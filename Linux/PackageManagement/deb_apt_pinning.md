# Управление приоритетами пакетов в Apt (Pinning)

## Определения

Ниже приведены основные термины, используемые в механизме управления приоритетами пакетов в системах на базе DEB (Debian Package).

**Pinning (Приоритизация пакетов)** — механизм системы APT (Advanced Package Tool), позволяющий администратору вручную переопределять стандартный алгоритм выбора версии пакета. Используется для фиксации версий, выбора пакетов из конкретных репозиториев (например, backports) или блокировки нежелательного ПО.

**Pin-запись (Pin Entry)** — блок конфигурации, определяющий правила для конкретного пакета (`Package`) или группы пакетов (маска `*`), критерии выбора (`Pin`) и числовой приоритет (`Pin-Priority`).

**Приоритет (Pin Priority / P-value)** — знаковое целое число, определяющее предпочтительность версии. APT всегда выбирает версию с наивысшим приоритетом.

**Кандидат на установку (Candidate Version)** — версия пакета, имеющая наивысший приоритет среди доступных и предназначенная для автоматической установки или обновления.

**Поле Explanation** — необязательное, но рекомендуемое поле в Pin-записи для документирования причин установки приоритета.

## Основные концепции

### Расположение конфигурации

Правила Pinning могут быть заданы в двух местах:
1.  **/etc/apt/preferences** — основной файл (устаревший подход, не рекомендуется для автоматизации).
2.  **/etc/apt/preferences.d/** — директория для модульных конфигураций. Файлы в ней обрабатываются в алфавитно-цифровом порядке. Рекомендуется использовать префиксы (например, `10-local-repo.pref`, `99-block-snap.pref`).

### Критерии выбора (Pin-Type)

Правила основываются на характеристиках, указываемых в поле `Pin`:

1.  **version**: Фиксация конкретной версии или диапазона (например, `Pin: version 1.2.3*`).
2.  **release**: Выбор по атрибутам файла `Release` (дистрибутив, кодовое имя, компонент).
3.  **origin**: Выбор по имени хоста источника (например, `Pin: origin "download.docker.com"`).

#### Атрибуты поля Release
- `a` (Archive/Suite) — тип дистрибутива (`stable`, `testing`, `noble-backports`).
- `n` (Codename) — кодовое имя релиза (`bookworm`, `noble`).
- `c` (Component) — секция репозитория (`main`, `universe`).
- `l` (Label) — метка репозитория (например, `Debian`, `Docker`).
- `o` (Origin) — организация-издатель.

### Расширенная шкала приоритетов

| Приоритет (P) | Поведение системы |
| :--- | :--- |
| **P ≥ 1000** | **Принудительная установка (Downgrade):** APT установит эту версию, даже если она старше текущей. |
| **990 ≤ P < 1000** | **Целевой релиз:** Устанавливается, даже если в других источниках есть более новая версия, но не вызывает понижение версии (downgrade). |
| **500 ≤ P < 990** | **Стандартный:** Значение по умолчанию для большинства репозиториев — **500**. Выбирается новейшая доступная версия. |
| **100 ≤ P < 500** | **Низкий:** Версия будет установлена только если нет альтернатив в более приоритетных источниках. Приоритет **100** обычно имеют уже установленные пакеты. |
| **0 < P < 100** | **Только ручная установка:** Пакет не будет установлен автоматически, если он еще не присутствует в системе. |
| **P < 0** | **Блокировка (Blacklist):** Запрет на установку пакета или использование источника. |

### Репозитории Not-Automatic

Репозитории с флагом `Not-Automatic: yes` (например, `backports`) автоматически получают приоритет **1**. Если установлен флаг `But-Automatic-Upgrades: yes`, то пакеты будут автоматически обновляться, только если они уже установлены в системе.

### Логика обработки и конфликты

1.  **Специфичность:** Правила для конкретных пакетов (`Package: nginx`) имеют приоритет над общими правилами (`Package: *`).
2.  **Первое совпадение:** Если для одного пакета определено несколько Pin-записей, APT использует первую найденную запись в файле (или в первом файле по алфавиту в `preferences.d/`).
3.  **Равенство приоритетов:** При одинаковом `Pin-Priority` выбирается версия с наибольшим номером версии.

## Практические сценарии

### Диагностика: Просмотр политики

Перед применением правил всегда проверяйте текущее состояние:

```bash
# Показать общие приоритеты всех подключенных репозиториев
apt-cache policy

# Показать приоритеты для конкретного пакета
apt policy nginx
# → result: список версий, их источников и назначенных P-значений
```

### Сценарий 1: Фиксация конкретной версии (Version Locking)

Используется для предотвращения обновления критически важного ПО (например, БД).

```bash
# /etc/apt/preferences.d/postgresql.pref
Explanation: Lock PostgreSQL to minor version 16.3
Package: postgresql-16
Pin: version 16.3*
Pin-Priority: 1001
```

*Альтернатива:* Для простой блокировки обновления без использования Pinning можно использовать команду `sudo apt-mark hold <package>`.

### Сценарий 2: «Безопасный» Backports

Установка только одного конкретного пакета из Backports без риска обновления всей системы до экспериментальных версий.

```bash
# /etc/apt/preferences.d/neovim-backports.pref
Explanation: Allow Neovim from backports automatically
Package: neovim
Pin: release a=bookworm-backports
Pin-Priority: 900
```

### Сценарий 3: Блокировка пакета (Anti-Snap)

Полный запрет на установку пакета `snapd` и связанных с ним компонентов.

```bash
# /etc/apt/preferences.d/nosnap.pref
Explanation: Disable snapd installation
Package: snapd*
Pin: release *
Pin-Priority: -1
```

### Сценарий 4: Приоритет внутреннего репозитория

Гарантия того, что пакеты из корпоративного репозитория всегда будут иметь преимущество перед официальными.

```bash
# /etc/apt/preferences.d/internal.pref
Explanation: Prefer internal builds over official ones
Package: *
Pin: release l="Internal Repo Label"
Pin-Priority: 1001
```

## Дополнительная информация

### Продвинутая отладка

Если APT ведет себя непредсказуемо, используйте отладочные флаги для анализа логики решателя зависимостей:

```bash
# Эмуляция установки с выводом процесса принятия решений
apt-get install -s -o Debug::pkgProblemResolver=1 <package>
```

### Рекомендации (Best Practices)

1.  **Принцип наименьших привилегий:** Вместо повышения приоритета основного репозитория до 1000, лучше понизьте приоритет стороннего до 100-400.
2.  **Кавычки в атрибутах:** Если значения в `release` или `origin` содержат пробелы, обязательно заключайте их в двойные кавычки.
3.  **Использование Glob-паттернов:** Поле `Package` поддерживает маски (например, `libmysql*`), что позволяет группировать правила.
4.  **Валидация:** После любого изменения в `preferences.d/` обязательно запускайте `apt update` и `apt policy <package>`, чтобы убедиться, что правила применились корректно.
