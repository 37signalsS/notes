## Архитектура пакетного менеджера

### Эволюция: от YUM к DNF 5

Пакетный менеджер DNF (Dandified YUM) является развитием YUM, направленным на устранение проблем производительности, высокого потребления памяти и неэффективного разрешения зависимостей.

*   **DNF 4 (текущий стандарт):**
    *   **Ядро:** Написано на Python. Использует библиотеку `hawkey` в качестве интерфейса к `libsolv`.
    *   **Разрешение зависимостей:** Библиотека `libsolv` (C) использует алгоритм SAT-solver для быстрого нахождения решений в сложных графах зависимостей.
    *   **Метаданные:** Обрабатываются через `librepo` (C), обеспечивающую эффективную загрузку и проверку GPG-подписей.
*   **DNF 5 (новое поколение):**
    *   **Ядро:** Полностью переписано на C++ (библиотека `libdnf5`). Это исключает зависимость от интерпретатора Python и значительно снижает потребление RAM.
    *   **Унификация:** Единая библиотека используется для CLI, плагинов и внешних инструментов (например, Cockpit), что гарантирует идентичное поведение системы во всех интерфейсах.
    *   **Производительность:** Ускорен процесс загрузки метаданных и расчета транзакций за счет исключения промежуточных уровней абстракции.

### Ключевые компоненты инфраструктуры

1.  **Libsolv:** Библиотека, обеспечивающая быструю и корректную обработку зависимостей. Она строит граф пакетов и находит оптимальный путь установки или обновления.
2.  **Metadata Cache:** Локальная копия данных из репозиториев (списки пакетов, контрольные суммы, описания). DNF минимизирует количество сетевых запросов, используя кэш до истечения срока `metadata_expire`.
3.  **Transaction Database:** База данных истории операций (SQLite в `/var/lib/dnf/history`). Хранит сведения о пакетах, времени операции и результатах выполнения скриптов.
4.  **RPMDB:** Низкоуровневая база данных установленных пакетов (`/var/lib/rpm`), с которой DNF взаимодействует через `librpm` для внесения изменений в систему.

## Конфигурация системы

### Иерархия и переменные

Конфигурация DNF строится на основе объединения глобальных настроек и специфических параметров репозиториев. В путях (URL) часто используются переменные:
- `$releasever` — версия дистрибутива (например, `9`).
- `$basearch` — архитектура системы (например, `x86_64`, `aarch64`).
- `$infra` — тип инфраструктуры (например, `stock`, `container`).

### Глобальный файл конфигурации (dnf.conf)

Файл `/etc/dnf/dnf.conf` (секция `[main]`) определяет общее поведение менеджера:

```ini
[main]
gpgcheck=1              # Обязательная проверка подписей всех пакетов
installonly_limit=3     # Лимит версий ядра (старые удаляются автоматически)
clean_requirements_on_remove=true  # Автоматическое удаление неиспользуемых зависимостей
best=True               # Всегда пытаться установить версию с максимальным номером
skip_if_unavailable=False  # Прерывать операцию, если репозиторий недоступен

# Оптимизация производительности
max_parallel_downloads=10  # Количество одновременных потоков загрузки
fastestmirror=True      # Выбор зеркала с минимальным временем отклика
metadata_expire=6h      # Время жизни кэша метаданных
deltarpm=True           # Использование Delta RPM для минимизации трафика (только DNF 4)

# Безопасность
protected_packages=dnf, glibc, systemd  # Список пакетов, которые нельзя удалить
```

### Структура каталогов

| Путь | Назначение |
| :--- | :--- |
| `/etc/dnf/dnf.conf` | Основной конфигурационный файл. |
| `/etc/yum.repos.d/` | Директория для файлов репозиториев (`.repo`). |
| `/etc/dnf/vars/` | Пользовательские переменные для подстановки в `.repo`. |
| `/var/cache/dnf/` | Кэш метаданных и скачанные RPM-пакеты. |
| `/var/lib/dnf/` | Системные данные (история транзакций, состояния модулей). |

## Механизмы работы

### Жизненный цикл транзакции

Каждая операция изменения состояния системы проходит через строго определенные этапы:

1.  **Инициализация:** Загрузка конфигурации, определение переменных и проверка прав доступа (root).
2.  **Синхронизация метаданных:** Проверка актуальности кэша. При необходимости загружается `repomd.xml` и индексы.
3.  **Разрешение зависимостей (Solver):** Построение графа транзакции в памяти. Если решение найдено, формируется список действий (install, upgrade, erase).
4.  **Transaction Check:** Тестовый прогон. DNF проверяет наличие конфликтов файлов, блокировку RPMDB и наличие свободного места на диске.
5.  **Скачивание:** Загрузка RPM-пакетов в кэш.
6.  **Исполнение (Transaction Run):** Передача управления `librpm`. Выполняются скрипты (`pre/post`), устанавливаются файлы.
7.  **Финализация:** Запись результата в историю транзакций и обновление кэша модулей.

### Обработка GPG-проверок

DNF обеспечивает безопасность через многоуровневую проверку:
1.  **GPG-подпись метаданных:** Проверка файла `repomd.xml` (если включен `repo_gpgcheck`).
2.  **GPG-подпись пакета:** Проверка каждого `.rpm` файла перед установкой по публичному ключу, импортированному в систему.

## Практические сценарии

Краткий обзор задач. Командный справочник доступен в файле **[Практические сценарии DNF](./practical_scenarios.md)**.

| Сценарий | Техническая реализация |
| :--- | :--- |
| **Ускорение работы** | Тюнинг `max_parallel_downloads` и настройка `metadata_expire`. |
| **Изолированный контур** | Создание локального репозитория через `createrepo_c` и настройка пути в `.repo`. |
| **Управление версиями ядра** | Параметр `installonly_limit` для контроля количества загрузочных записей. |
| **Диагностика сбоев** | Анализ `/var/log/dnf.log` и использование `dnf history info`. |
