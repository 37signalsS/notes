## Архитектура пакетного менеджера

### Эволюция: от YUM к DNF 5

Пакетный менеджер DNF (Dandified YUM) является развитием YUM, направленным на устранение проблем производительности, высокого потребления памяти и неэффективного разрешения зависимостей.

*   **DNF 4 (текущий стандарт):**
    *   **Ядро:** Написано на Python. Использует библиотеку `hawkey` в качестве интерфейса к `libsolv`.
    *   **Разрешение зависимостей:** Библиотека `libsolv` (C) использует алгоритм SAT-solver для быстрого нахождения решений в сложных графах зависимостей.
    *   **Метаданные:** Обрабатываются через `librepo` (C), обеспечивающую эффективную загрузку и проверку GPG-подписей.
*   **DNF 5 (новое поколение):**
    *   **Ядро:** Полностью переписано на C++ (библиотека `libdnf5`). Это исключает зависимость от интерпретатора Python и значительно снижает потребление RAM.
    *   **Унификация:** Единая библиотека используется для CLI, плагинов и внешних инструментов (например, Cockpit), что гарантирует идентичное поведение системы во всех интерфейсах.
    *   **Производительность:** Ускорен процесс загрузки метаданных и расчета транзакций за счет исключения промежуточных уровней абстракции.

### Ключевые компоненты инфраструктуры

1.  **Libsolv / Libsolv5:** Библиотека, обеспечивающая быструю и корректную обработку зависимостей. Она строит граф пакетов и находит оптимальный путь установки или обновления. В DNF 5 используется `libsolv5` с улучшенной поддержкой булевых зависимостей и модульности.
2.  **Librepo:** C-библиотека для загрузки, кэширования и проверки метаданных репозиториев. Отвечает за сетевое взаимодействие, retry-логику, TLS-верификацию и контрольные суммы. Именно `librepo` управляет кэшем `/var/cache/dnf/`.
3.  **Hawkey:** Высокоуровневая Python/C-обертка над `libsolv`, используемая в DNF 4 как интерфейс между Python-логикой менеджера и низкоуровневым решателем.
4.  **Libdnf / Libdnf5:** Основная логика работы с репозиториями, пакетами и транзакциями. В DNF 4 — `libdnf` (C++ библиотека, вызываемая из Python). В DNF 5 — `libdnf5` (C++), единый для CLI, плагинов и внешних инструментов (например, Cockpit), что исключает расхождения в поведении.
5.  **Librpm:** Низкоуровневая библиотека для физической установки/удаления RPM-пакетов, выполнения scriptlets и работы с RPMDB.
6.  **Metadata Cache:** Локальная копия данных из репозиториев (списки пакетов, контрольные суммы, описания). DNF минимизирует количество сетевых запросов, используя кэш до истечения срока `metadata_expire`.
7.  **Transaction Database:** База данных истории операций (SQLite в `/var/lib/dnf/history`). Хранит сведения о пакетах, времени операции и результатах выполнения скриптов.
8.  **RPMDB:** Низкоуровневая база данных установленных пакетов (`/var/lib/rpm`), с которой DNF взаимодействует через `librpm` для внесения изменений в систему.

## Конфигурация системы

### Иерархия и переменные

Конфигурация DNF строится на основе объединения глобальных настроек и специфических параметров репозиториев. В путях (URL) часто используются переменные:
- `$releasever` — версия дистрибутива (например, `9`).
- `$basearch` — архитектура системы (например, `x86_64`, `aarch64`).
- `$infra` — тип инфраструктуры (например, `stock`, `container`).

### Глобальный файл конфигурации (dnf.conf)

Файл `/etc/dnf/dnf.conf` (секция `[main]`) определяет общее поведение менеджера. Все параметры могут быть переопределены в отдельных `.repo` файлах.

```ini
[main]
# Безопасность
gpgcheck=1              # Обязательная проверка подписей всех пакетов
repo_gpgcheck=0         # Проверка подписи repomd.xml (включайте для доверенных зеркал)
protected_packages=dnf, glibc, systemd  # Защищенные пакеты, которые нельзя удалить

# Управление ядрами
installonly_limit=3     # Максимум параллельно хранимых версий ядра (старые удаляются автоматически)
installonlypkgs=kernel  # Пакеты, к которым применяется installonly_limit

# Поведение транзакций
skip_if_unavailable=False  # Прерывать операцию, если репозиторий недоступен
best=True               # Всегда выбирать максимальную доступную версию
clean_requirements_on_remove=true  # Удалять неиспользуемые зависимости при удалении пакета

# Производительность
max_parallel_downloads=10  # Количество одновременных потоков загрузки
fastestmirror=True      # Выбор зеркала с минимальным временем отклика
metadata_expire=6h      # Время жизни кэша метаданных
deltarpm=True           # Использование Delta RPM для минимизации трафика (только DNF 4)

# Сеть
ip_resolve=4            # Принудительное использование IPv4 (если IPv6 нестабилен)
retries=6               # Количество повторных запросов при сетевых ошибках
timeout=30              # Тайм-аут запроса в секундах
```

### Структура каталогов

| Путь | Назначение |
| :--- | :--- |
| `/etc/dnf/dnf.conf` | Основной конфигурационный файл. |
| `/etc/yum.repos.d/` | Директория для файлов репозиториев (`.repo`). |
| `/etc/dnf/vars/` | Пользовательские переменные для подстановки в `.repo`. |
| `/var/cache/dnf/` | Кэш метаданных и скачанные RPM-пакеты. |
| `/var/lib/dnf/` | Системные данные (история транзакций, состояния модулей). |

## Механизмы работы

### Жизненный цикл транзакции

Каждая операция изменения состояния системы проходит через строго определенные этапы:

1.  **Инициализация:** Загрузка конфигурации, определение переменных и проверка прав доступа (root).
2.  **Синхронизация метаданных:** Проверка актуальности кэша. При необходимости загружается `repomd.xml` и индексы.
3.  **Разрешение зависимостей (Solver):** Построение графа транзакции в памяти. Если решение найдено, формируется список действий (install, upgrade, erase).
4.  **Transaction Check:** Тестовый прогон. DNF проверяет наличие конфликтов файлов, блокировку RPMDB и наличие свободного места на диске.
5.  **Скачивание:** Загрузка RPM-пакетов в кэш.
6.  **Исполнение (Transaction Run):** Передача управления `librpm`. Выполняются скрипты (`pre/post`), устанавливаются файлы.
7.  **Финализация:** Запись результата в историю транзакций и обновление кэша модулей.

### Обработка GPG-проверок

DNF обеспечивает безопасность через многоуровневую проверку:
1.  **GPG-подпись метаданных:** Проверка файла `repomd.xml` (если включен `repo_gpgcheck`).
2.  **GPG-подпись пакета:** Проверка каждого `.rpm` файла перед установкой по публичному ключу, импортированному в систему.

### Механизм Delta RPM (DRPM)

Delta RPM — пакет, содержащий бинарную разницу между старой и новой версией RPM. При установке DNF скачивает только дельту, а затем применяет её к уже установленной версии пакета, реконструируя полный RPM локально. Это уменьшает трафик в 2–10 раз для небольших исправлений.

**Ограничения:**
- Работает только если требуемая стартовая версия пакета уже присутствует в кэше или установлена.
- В DNF 5 поддержка DRPM удалена из-за низкой эффективности на современных скоростях сетей и накладных расходов на вычисление дельт.
- При недоступности дельты DNF автоматически скачивает полный RPM без ошибок.

### Управление ядрами: installonly_limit

Пакеты, перечисленные в `installonlypkgs` (по умолчанию `kernel`), не удаляются при `dnf upgrade`. Вместо этого DNF хранит несколько последних версий параллельно, ограничиваясь `installonly_limit` (по умолчанию 3). При превышении лимита самая старая версия удаляется автоматически, включая её запись в загрузчик. Это предотвращает ситуации, когда обновление ядра делает систему не загружаемой.

### Защищенные пакеты (protected_packages)

Параметр `protected_packages` в `[main]` секции содержит список пакетов, которые DNF не удалит даже при явном запросе `dnf remove`. По умолчанию включает `dnf`, `glibc`, `systemd`. Для снятия защиты требуется ручная правка конфигурации или использование `--setopt=protected_packages=`.

### Блокировка RPMDB и изоляция транзакций

На этапе Transaction Check DNF пытается получить эксклюзивную блокировку (`flock`) на `/var/lib/rpm/.rpm.lock`. Это предотвращает параллельное изменение базы пакетов другими процессами (`rpm`, `yum`, другой экземпляр `dnf`). При обнаружении блокировки операция прерывается с ошибкой. Изоляция гарантирует, что частичная установка не оставит базу в несогласованном состоянии.

### Выполнение RPM-scriptlets

Во время фазы Transaction Run DNF через `librpm` выполняет скрипты пакетов в строгом порядке:
1.  `pre-install` (устанавливаемого пакета)
2.  `pre-uninstall` (удаляемого пакета)
3.  Файловая операция (копирование, удаление)
4.  `post-install` (устанавливаемого пакета)
5.  `post-uninstall` (удаляемого пакета)

Сбой любого скрипта прерывает всю транзакцию, и RPMDB откатывается к исходному состоянию. DNF фиксирует ошибки в `/var/log/dnf.log` и `/var/lib/dnf/history.sqlite`.

### Кэширование и инвалидация

DNF минимизирует сетевые запросы через многоуровневое кэширование:

1.  **Кэш метаданных** (`/var/cache/dnf/`): хранит `repomd.xml`, `primary.xml`, `filelists.xml`.
2.  **Скачанные пакеты**: RPM-файлы, загруженные в кэш, используются при повторной установке без повторного скачивания.
3.  **Инвалидация по времени**: параметр `metadata_expire` определяляет срок актуальности кэша. По истечении срока DNF принудительно обновляет метаданные.

Принудительное обновление кэша: `sudo dnf clean all && sudo dnf makecache`.

В офлайн-средах или при нестабильном соединении параметр `metadata_expire=0` отключает автоматическую проверку актуальности, позволяя работать только с локальным кэшем.

## Практические сценарии

Раздел содержит операционные паттерны для DevOps/SRE/sysadmin. Полный справочник команд доступен в файле **[Практические сценарии DNF](./practical_scenarios.md)**.

### Управление ядрами и загрузчик

```bash
# Просмотр установленных ядер
dnf list installed kernel

# Просмотр загрузочных записей (что видит GRUB2)
sudo grubby --info=ALL | grep -E "^title|^kernel"

# Ручное удаление старого ядра, если installonly_limit не сработал
sudo dnf remove kernel-<old_version>

# Проверка, сколько ядер будет сохранено после следующего upgrade
dnf install --assumeno kernel
```

### Блокировка версий (Versionlock)

Плагин `python3-dnf-plugin-versionlock` предотвращает обновление критичных пакетов.

```bash
# Установка плагина
sudo dnf install python3-dnf-plugin-versionlock

# Блокировка конкретной версии пакета
sudo dnf versionlock add kernel-6.1.20

# Просмотр заблокированных пакетов
dnf versionlock list

# Снятие блокировки
sudo dnf versionlock delete kernel-6.1.20
```

### Пакетная автоматизация через DNF Shell

Интерактивная оболочка `dnf shell` ускоряет выполнение последовательности команд, разделяя общую синхронизацию метаданных и разрешение зависимостей.

```bash
# Запуск оболочки
sudo dnf shell

# Внутри оболочки (несколько команд без повторной загрузки метаданных)
> install vim curl wget
> upgrade
> run
> exit
```

### Работа в офлайн-средах и CI

```bash
# Создание локального репозитория из скачанных пакетов
sudo dnf install createrepo_c
mkdir -p /var/www/html/local-repo/{pkgs,repodata}
cp /path/to/*.rpm /var/www/html/local-repo/pkgs/
createrepo_c /var/www/html/local-repo

# Настройка .repo файла для локального зеркала
cat <<EOF | sudo tee /etc/yum.repos.d/local.repo
[local]
name=Local Repository
baseurl=file:///var/www/html/local-repo
enabled=1
gpgcheck=0
EOF

# Установка только из кэша (без сети)
sudo dnf upgrade --cacheonly

# Проверка, что все зависимости можно удовлетворить из кэша
dnf repoquery --requires <package_name> | dnf repoquery --whatprovides -
```

### Исправление дрейфа версий (Distro-Sync)

В крупных окружениях или после ручного вмешательства пакеты могут "перемешаться" между версиями. `distro-sync` приводит систему к состоянию, соответствующему текущим репозиториям.

```bash
# Приведение всех пакетов к версиям репозиториев
sudo dnf distro-sync

# Только конкретный пакет
sudo dnf distro-sync <package_name>

# Dry-run для проверки действий
sudo dnf distro-sync --assumeno
```

### Валидация целостности зависимостей репозитория

```bash
# Проверка кастомного репозитория на "разорванные" зависимости
dnf repoclosure --repoid=<repo_id>
```

### Аудит установленной базы

```bash
# Пакеты, установленные не из репозиториев (локальные RPM, сторонние)
dnf list extras

# Поиск пакетов, предоставляющих конкретный файл или capability
dnf provides /usr/bin/python3
dnf repoquery --whatprovides "libssl.so.1.1()(64bit)"

# Обратные зависимости: кто зависит от указанного пакета
dnf repoquery --installed --whatrequires <package_name>

# Проверка целостности базы RPMDB
sudo dnf check

# История транзакций: поиск, что сломалось после последнего обновления
dnf history info last
```

### Откат транзакций

```bash
# Просмотр истории транзакций
dnf history list

# Откат конкретной транзакции по ID
sudo dnf history undo <transaction_id>

# Полный откат к предыдущему состоянию
sudo dnf history rollback
```

### Управление репозиториями в промышленной эксплуатации

```bash
# Включение репозитория только для одной сессии (без сохранения в .repo)
sudo dnf --enablerepo=<repo_id> install <package_name>

# Включение repo с указанием приоритета (плагин priorities)
sudo dnf config-manager --setopt=<repo_id>.priority=1 --save

# Проверка приоритетов
dnf repolist -v
```

### Диагностика нехватки места

DNF проверяет свободное место на диске перед загрузкой и установкой. При недостатке места транзакция прерывается на этапе Transaction Check.

```bash
# Проверка места в /var/cache/dnf и /var/lib/rpm
df -h /var/cache /var/lib

# Очистка устаревших кэшей
sudo dnf clean all
```
