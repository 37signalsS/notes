## Переменные окружения и кастомные переменные

### Системные переменные окружения

Переменные окружения позволяют изменять поведение DNF без правки конфигурационных файлов (например, в CI/CD или скриптах автоматизации).

| Переменная | Назначение |
| :--- | :--- |
| `DNF_CONF_FILE` | Переопределяет путь к основному файлу конфигурации (по умолчанию `/etc/dnf/dnf.conf`). |
| `DNF_PLUGIN_PATH` | Путь к дополнительным плагинам DNF (Python-скриптам). |
| `RELEASEVER` | Переопределяет значение `$releasever` для всех репозиториев. |

### Пользовательские переменные (DNF_VAR_)

DNF позволяет определять собственные переменные, которые могут быть использованы внутри файлов `.repo` для подстановки в URL.
Любая переменная окружения, начинающаяся с `DNF_VAR_`, становится доступной в DNF.

**Пример:**
Если задать `export DNF_VAR_CUSTOM_REPO_VER=1.2`, то в файле репозитория можно использовать `$custom_repo_ver`.

## Расширение функциональности через плагины

Плагины в DNF 4 написаны на Python, в то время как в **DNF 5** архитектура переходит на C++ (через `libdnf5`), сохраняя возможность написания Python-оберток.

### Популярные плагины и их назначение

| Плагин | Назначение |
| :--- | :--- |
| `dnf-plugins-core` | Базовый набор: `config-manager` (управление репозиториями), `copr` (подключение кастомных репозиториев), `debuginfo-install`. |
| `dnf-plugin-versionlock` | Фиксация конкретных версий пакетов (запрет обновления). |
| `dnf-plugin-system-upgrade` | Стандартный инструмент для обновления версии всей ОС (например, переход с Fedora 40 на Fedora 41). |
| `dnf-plugin-priorities` | Управление приоритетами репозиториев (важно при использовании сторонних источников, таких как EPEL). |
| `dnf-plugin-post-transaction-actions` | Выполнение произвольных команд/скриптов после завершения транзакции для конкретных пакетов. |
| `dnf-plugin-needs-restarting` | Анализ системы на предмет необходимости перезагрузки после обновлений. |

## Практические сценарии использования плагинов

### Использование post-transaction-actions

Этот плагин полезен для автоматизации действий после обновления специфического ПО (например, очистка кэша приложения или уведомление в мессенджер).

Файл конфигурации действий: `/etc/dnf/plugins/post-transaction-actions.d/my_action.action`
```text
# Синтаксис: <package_name>:<action_type>:<command>
# action_type: install, update, remove, any
nginx:update:systemctl reload nginx
```

### Обновление версии ОС (system-upgrade)

```bash
# 1. Обновление текущих пакетов до актуального состояния
sudo dnf upgrade --refresh

# 2. Установка плагина
sudo dnf install dnf-plugin-system-upgrade

# 3. Загрузка пакетов новой версии (например, Fedora 41)
sudo dnf system-upgrade download --releasever=41

# 4. Запуск процесса обновления (система уйдет в перезагрузку)
sudo dnf system-upgrade reboot
```

## Сравнение синтаксиса DNF и YUM

Для администраторов, привыкших к классическому YUM, DNF обеспечивает высокую степень обратной совместимости, однако есть различия в логике и названиях команд.

| Операция | Команда YUM | Команда DNF | Комментарий |
| :--- | :--- | :--- | :--- |
| **Установка** | `yum install` | `dnf install` | Полная совместимость. |
| **Обновление** | `yum update` | `dnf upgrade` | В DNF `update` является алиасом к `upgrade`. |
| **Очистка кэша** | `yum clean all` | `dnf clean all` | DNF также очищает кэш метаданных. |
| **Группы** | `yum groupinstall` | `dnf group install` | DNF требует явную подкоманду `group`. |
| **История** | `yum history` | `dnf history` | DNF хранит более детальную историю транзакций в SQLite. |
