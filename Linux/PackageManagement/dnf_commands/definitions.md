# DNF — Глоссарий и определения

## Определения

Ниже приведены определения терминов, специфичных для пакетного менеджера DNF и RPM-экосистемы. Базовые понятия пакетного управления описаны в **[общем обзоре пакетных менеджеров](../linux_package_management_overview.md)**.

### Основные компоненты

**DNF (Dandified YUM)** — современный высокоуровневый пакетный менеджер для RPM-based систем. Решает проблемы YUM с производительностью и разрешением зависимостей.

**DNF 5** — следующее поколение DNF на C++. Обеспечивает максимальную производительность, унификацию API и уменьшение зависимостей самого менеджера (не требует Python).

**Libsolv** — библиотека разрешения зависимостей (SAT-solver), используемая в DNF, Zypper и других менеджерах.

**Libdnf / Libdnf5** — низкоуровневая библиотека, реализующая основную логику работы с репозиториями, пакетами и транзакциями.

**Hawkey** — высокоуровневая библиотека-обертка над `libsolv` для Python/C (используется в DNF 4).

**RPM (Red Hat Package Manager)** — формат пакетов и низкоуровневая утилита для их установки.

**Repoquery** — утилита для выполнения сложных SQL-подобных запросов к базе установленных и доступных пакетов. Входит в состав `dnf-plugins-core`.

**Config-manager** — встроенный инструмент CLI для динамического управления репозиториями без редактирования `.repo` файлов вручную.

**Createrepo_c** — утилита на C для создания локальных RPM-репозиториев. Генерирует `repodata` и индексы. Наследник `createrepo` на Python.

**Reposync** — плагин DNF для синхронизации содержимого удаленного репозитория в локальную копию (используется для создания зеркал).

### Механизмы репозиториев

**Repodata (Метаданные)** — набор XML или SQLite файлов в репозитории, содержащий информацию о пакетах, зависимостях, контрольных суммах и GPG-подписям.

**Metadata Cache (Кэш метаданных)** — локальная копия `repodata` на машине пользователя. Позволяет выполнять поиск и расчет зависимостей без обращения к сети.

**Repository Priority (Приоритет репозитория)** — числовое значение, определяющее предпочтительный источник пакета при наличии одной и той же версии в разных репозиториях.

**COPR (Cool Other Package Repo)** — облачный сервис для сборки и хранения сторонних пользовательских репозиториев (аналог PPA).

**AppStream / BaseOS** — разделение репозиториев в RHEL 8+: `BaseOS` содержит ядро и базовую систему, `AppStream` — приложения и модули.

**Mirrorlist / Metalink** — механизмы динамического выбора зеркал. `mirrorlist` возвращает список URL, `metalink` — XML с метаданными о зеркалах, контрольными суммами и приоритетами.

### Управление пакетами и зависимости

**Модуль (Module)** — логическая группа пакетов, представляющая конкретное приложение или стек (например, `nodejs`).
- **Stream (Поток)** — версия или ветка модуля (например, `nodejs:20`).
- **Profile (Профиль)** — вариант установки модуля (`common`, `minimal`, `development`).

**Слабые зависимости (Weak Dependencies)**:
- **Recommends** — устанавливаются по умолчанию, но не обязательны для работы.
- **Suggests** — дополнительные пакеты, предлагаемые пользователю.

**Boolean Dependencies (Булевы зависимости)** — использование логических выражений (`and`, `or`, `if`) в зависимостях пакета.

**Capabilities (Возможности)** — абстрактные имена (например, `webserver`), которые пакеты могут "предоставлять" (`Provides`) или "требовать" (`Requires`). Позволяют заменять пакеты (например, `nginx` и `httpd` оба предоставляют `webserver`).

**Obsoletes (Устаревание)** — механизм, позволяющий пакету объявить другой пакет устаревшим и заменить его при обновлении.

**DRPM (Delta RPM)** — пакет, содержащий только разницу между старой и новой версией RPM, что экономит трафик.

**Debuginfo** — пакеты с отладочной информацией (символы `.debug`), необходимые для трассировки ядра и core dump-анализа. Устанавливаются через `dnf debuginfo-install`.

**Source RPM (SRPM)** — исходный код пакета, доступный для скачивания через `dnf download --source`.

### Состояния и операции

**Транзакция** — атомарный набор операций по установке, удалению или обновлению пакетов. Гарантирует, что либо все операции выполнены, либо система осталась в исходном состоянии.

**Transaction History (История)** — база данных всех выполненных транзакций, позволяющая выполнять откат (`rollback`) или отмену (`undo`).

**Environment Group (Группа окружения)** — верхнеуровневый набор групп пакетов (например, "Server with GUI").

**Package Group (Группа пакетов)** — именованный набор пакетов для конкретной задачи (например, "Development Tools").

**Distro-sync** — операция приведения установленных пакетов к версиям, доступным в текущих репозиториях дистрибутива. Устраняет смешение версий из разных источников.

**Swap** — атомарная замена одного пакета другим в рамках одной транзакции (например, `dnf swap mysql-server mariadb-server`).

**Protected Packages** — список пакетов, защищенных от удаления через параметр `protected_packages` в `dnf.conf` (по умолчанию включает `dnf`, `glibc`, `systemd`).

**Installonly Limit** — параметр `installonly_limit`, контролирующий максимальное количество версий одного пакета (обычно ядра), которые хранятся в системе параллельно.

**Skip If Unavailable** — параметр `skip_if_unavailable`, определяющий, прерывать ли транзакцию при недоступности репозитория.

**Best** — параметр `best`, заставляющий DNF всегда выбирать максимальную доступную версию пакета, даже если установлена более старая.

**Repoclosure** — проверка целостности зависимостей в репозитории. Обнаруживает "разорванные" зависимости, когда пакет требует другой, отсутствующий в том же репозитории.

**Repomanage** — утилита для управления пакетами в каталоге репозитория (поиск дубликатов, определение старых версий, ликвидация). Используется при обслуживании локальных зеркал.

**Yumdownloader** — утилита для скачивания RPM-пакетов и их зависимостей без установки. Полезна для подготовки пакетов в офлайн-средах.

## Основные концепции

### Атомарность транзакций и безопасность

DNF обеспечивает целостность системы через атомарные транзакции. Перед внесением изменений DNF создает тестовый план транзакции (Transaction Check), который включает:

1.  Проверку конфликтов файлов между пакетами.
2.  Проверку блокировки RPMDB (исключает параллельное изменение другим процессом).
3.  Проверку свободного места на диске.
4.  Валидацию контрольных сумм и GPG-подписей.

Если любой из этапов завершается с ошибкой, транзакция прерывается полностью, и система остается в исходном состоянии. Это особенно критично для production-систем, где частичная установка может привести к недоступности сервисов.

### SAT-солвер и разрешение зависимостей

DNF использует библиотеку `libsolv`, реализующую алгоритм SAT (Boolean Satisfiability Problem). Вместо последовательного перебора вариантов, SOLVER строит граф пакетов и применяет логический вывод для нахождения оптимального решения. Это обеспечивает:

- Корректное разрешение даже в сложных графах с тысячами пакетов.
- Отсутствие субоптимальных решений, характерных для итеративных алгоритмов.
- Поддержку булевых зависимостей (`and`, `or`, `if`) в RPM-спецификациях.

### Кэширование и инвалидация

DNF минимизирует сетевые запросы через многоуровневое кэширование:

1.  **Кэш метаданных** (`/var/cache/dnf/`): хранит `repomd.xml`, `primary.xml`, `filelists.xml`.
2.  **Скачанные пакеты**: RPM-файлы, загруженные в кэш, используются при повторной установке без повторного скачивания.
3.  **Инвалидация по времени**: параметр `metadata_expire` определяляет срок актуальности кэша. По истечении срока DNF принудительно обновляет метаданные.

Принудительное обновление кэша: `dnf clean all && dnf makecache`.

### Модульность: жизненный цикл потока

В RHEL 8+ и Fedora модули позволяют сосуществовать несколько версий одного приложения. Жизненный цикл:

1.  **Доступность**: Пакет поставляется в виде модуля с одним или несколькими потоками.
2.  **Включение**: Администратор выбирает поток (`dnf module enable nodejs:20`).
3.  **Установка**: Устанавливаются пакеты, соответствующие профилю выбранного потока.
4.  **Переключение**: При смене потока DNF автоматически выполняет замену пакетов, сохраняя зависимости.
5.  **Сброс**: `dnf module reset` отменяет выбор потока, возвращая модуль в состояние "не выбран".

### GPG-верификация и цепочка доверия

DNF реализует двухуровневую проверку:

1.  **Метаданные репозитория**: Подпись `repomd.xml` открытым ключом репозитория (если `repo_gpgcheck=1`).
2.  **Пакеты**: Подпись каждого `.rpm` файла открытым ключом, импортированным в RPMDB.

Для импорта ключа используется `rpm --import /etc/pki/rpm-gpg/RPM-GPG-KEY`. DNF автоматически проверяет подписи при установке, если `gpgcheck=1` в `.repo` файле или `dnf.conf`.

## Практические сценарии

Ниже приведены практические команды и сценарии для администрирования RPM-систем. Детальный справочник команд и расширенных примеров доступен в файле **[Практические сценарии DNF](./practical_scenarios.md)**.

### Управление репозиториями

```bash
# Список активных репозиториев с статусом и количеством пакетов
dnf repolist

# Подробная информация о конкретном репозитории
dnf repoinfo <repo_id>

# Включение/отключение репозитория на постоянной основе
sudo dnf config-manager --set-enabled <repo_id>
sudo dnf config-manager --set-disabled <repo_id>

# Добавление репозитория (DNF 4)
sudo dnf config-manager --add-repo https://example.com/repo.repo

# Добавление репозитория (DNF 5)
sudo dnf config-manager addrepo --from-repofile=https://example.com/repo.repo

# Импорт GPG-ключа репозитория
sudo rpm --import https://example.com/RPM-GPG-KEY
```

### Обслуживание кэша

```bash
# Очистка всего кэша (метаданные и скачанные пакеты)
sudo dnf clean all

# Очистка только метаданных
sudo dnf clean metadata

# Принудительное обновление кэша
sudo dnf makecache

# Проверка актуальности кэша без внесения изменений
dnf check-update
```

### Загрузка пакетов без установки

```bash
# Скачивание одного пакета
dnf download --destdir=/tmp <package_name>

# Скачивание пакета со всеми зависимостями
yumdownloader --destdir=/tmp --resolve <package_name>

# Скачивание исходного RPM (SRPM)
dnf download --source <package_name>
```

### Отладочные пакеты (Debuginfo)

```bash
# Установка отладочных пакетов для конкретного приложения
sudo dnf debuginfo-install <package_name>

# Установка debuginfo для ядра (требует включение репозитория debug)
sudo dnf debuginfo-install kernel-$(uname -r)
```

### Информация об обновлениях безопасности

```bash
# Список всех доступных обновлений
dnf updateinfo list

# Только обновления безопасности
dnf updateinfo list security

# Обновления с указанием критичности
dnf updateinfo list --security --severity=Critical
```

### Проверка целостности зависимостей репозитория

```bash
# Проверка, все ли зависимости репозитория могут быть удовлетворены
dnf repoclosure --repoid=<repo_id>
```

### Проверка необходимости перезапуска сервисов

```bash
# Список процессов, требующих перезапуска после обновления
dnf needs-restarting -s

# Список установленных пакетов, после обновления которых требуется перезагрузка
dnf needs-restarting -r
```

### Поиск и аудит пакетов

```bash
# Поиск пакета по имени файла (что установило /usr/bin/python3)
dnf provides /usr/bin/python3

# Список установленных пакетов, не входящих в репозитории
dnf list extras

# Список всех доступных версий пакета
dnf list --showduplicates <package_name>

# Поиск пакетов, оставшихся после удаления приложения (кандидаты на удаление)
dnf leaves
```

### Восстановление системы после сбоев

```bash
# Переустановка критического пакета (например, coreutils после повреждения)
sudo dnf reinstall coreutils

# Проверка целостности базы RPM
sudo dnf check

# Полная синхронизация с репозиторием (исправление "смешанных" версий)
sudo dnf distro-sync
```

### Работа в офлайн-режиме

```bash
# Обновление только из локального кэша (без доступа к сети)
sudo dnf upgrade --cacheonly

# Создание списка пакетов для офлайн-установки
dnf download --resolve --alldeps <package_name> -o /tmp/packages/
```
