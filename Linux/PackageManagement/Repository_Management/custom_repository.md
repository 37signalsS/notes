# Создание собственных RPM-репозиториев

## Определения

Ниже приведены основные термины, используемые при организации внутренних хранилищ программного обеспечения. Базовые сведения о репозиториях и механизмах GPG приведены в разделе **[Управление репозиториями](./index.md)**.

**Собственный репозиторий (Custom Repository)** — локальный или сетевой каталог, содержащий специально подготовленные пакеты формата RPM и файлы метаданных, предназначенный для распространения программного обеспечения внутри организации.

**Метаданные (Repodata)** — набор XML/zstd индексов, описывающих зависимости, контрольные суммы и списки файлов всех пакетов. Располагаются в поддиректории `repodata/`.

**Подпись метаданных (Metadata Signing)** — создание GPG-подписи для файла `repomd.xml` (обычно `repomd.xml.asc`). Гарантирует клиенту, что индекс репозитория не был подменен.

**Группы пакетов (Comps)** — XML-файл (обычно `comps.xml`), описывающий логические объединения пакетов (например, "Development Tools") для пакетной установки через `dnf group install`.

**Модульные метаданные (AppStream Metadata)** — описание модульных потоков (streams) и профилей (profiles) в формате YAML, позволяющее управлять версиями ПО независимо от ОС.

**modifyrepo_c** — утилита для изменения существующего репозитория: добавление модульных метаданных (`--mdtype=modules`), changelog-индексов или произвольных XML-файлов в `repodata/` без полной перегенерации.

**repomanage** — утилита из пакета `yum-utils` для управления версиями пакетов в локальном репозитории. Позволяет оставить только последнюю N версий или фильтровать по дате перед переиндексацией, экономя место.

**Zchunk** — формат дельта-сжатия для файлов метаданных репозитория. Позволяет клиентам скачивать только изменения в `repomd.xml` и индексах, а не полный файл, что сокращает трафик при частых обновлениях индексов.

**Директория `incoming/`** — каталог «горячего приёма» для новых `.rpm`-файлов. Используется в автоматизированных сценариях: пакеты помещаются в `incoming/`, после чего скрипт перемещает их в `Packages/` и перестраивает индексы.

**Жёсткая ссылка (Hardlink)** — файловая сущность, указывающая на те же данные на диске, что и исходный файл. В контексте репозиториев позволяет хранить несколько копий каталогов с разными наборами пакетов, не дублируя фактические `.rpm`-файлы. Идеально подходит для создания снапшотов состояния репозитория.

**База данных createrepo_c (SQLite cache)** — локальный кэш в формате SQLite, который `createrepo_c` создаёт для ускорения последующих перестроений. По умолчанию хранится в каталоге репозитория и переиспользуется при запуске с флагом `--update`. Отключение (`--no-database`) ускоряет первичную генерацию, но замедляет инкрементальные обновления.

## Основные концепции

### Структура и LAYOUT репозитория

Для корректной работы DNF/YUM необходимо соблюдать стандартную иерархию каталогов:

```text
/var/www/html/repo/
├── x86_64/                 # Директория архитектуры (рекомендуется)
│   ├── Packages/           # (Опционально) Хранилище .rpm файлов
│   │   ├── app-1.0.rpm
│   │   └── lib-2.0.rpm
│   ├── repodata/           # Генерируется автоматически через createrepo_c
│   │   ├── repomd.xml      # Индекс индексов
│   │   └── *.xml.zst      # Сжатые таблицы пакетов
│   └── comps.xml           # Файл групп (если используется)
└── RPM-GPG-KEY-myrepo      # Публичный ключ для клиентов
```

### Современные стандарты (2025–2026)

1.  **Производительность:** Использование `createrepo_c` (реализация на C) вместо устаревшего `createrepo` (Python).
2.  **Сжатие:** Переход на **zstd** (`--general-compress-type zstd`) для метаданных.
3.  **Безопасность:** Обязательное использование `repo_gpgcheck=1` вместе с `gpgcheck=1` для защиты от атак типа "Downgrade".
4.  **Дельты метаданных:** Использование **Zchunk** (`--zck`) для минимизации трафика при обновлении больших индексов.

### Справочник ключевых флагов `createrepo_c`

| Флаг | Назначение | Рекомендация |
| :--- | :--- | :--- |
| `--general-compress-type zstd` | Сжатие индексных файлов (`*.xml.zst`) | Обязательно для production |
| `--zck` | Генерация дельта-файлов Zchunk для `repomd.xml` | Включите, если клиенты обновляются часто |
| `--groupfile comps.xml` | Интеграция файла групп пакетов | Требуется для `dnf group install` |
| `--update` | Инкрементальное обновление на основе существующих индексов | Используйте для каждого деплоя новых пакетов |
| `--no-database` | Отключение кэша SQLite (ускоряет первичную генерацию) | Используйте только для разовых однократных генераций |
| `--workers N` | Количество параллельных потоков индексации | Установите `$(nproc)` для многопроцессорных систем |
| `--cachedir /path` | Каталог для хранения кэша (при `--no-database`) | Полезно при генерации на сетевой файловой системе |
| `--unique-md-filenames` | Добавляет хэш в имена файлов метаданных | Включайте, если планируете CDN с долгим TTL |
| `--checksum sha256` | Алгоритм контрольных сумм в индексах | `sha256` — стандарт по умолчанию в современных версиях |
| `--allow-unsigned` | Пропустить пакеты без GPG-подписи при индексации | Никогда не используйте в production |
| `--changelog-limit N` | Ограничить количество записей changelog в индексе | Уменьшает размер `other.xml` для крупных репозиториев |
| `--skip-symlinks` | Игнорировать симлинки при обходе каталога | Включите, если в `Packages/` есть симлинки |

### Жизненный цикл метаданных и кэш SQLite

`createrepo_c` по умолчанию создаёт в каталоге репозитория базу данных SQLite (`repodata/createrepo_c.db` или аналогичную), которая содержит информацию о всех проиндексированных пакетах. При повторном вызове с флагом `--update` утилита читает эту базу, определяет новые/изменённые пакеты и перестраивает только необходимые индексы. Это сокращает время переиндексации с десятков секунд до долей секунды на репозиториях с тысячами пакетов.

Отключение базы (`--no-database`) оправдано только в следующих случаях:
- Репозиторий генерируется один раз и больше не обновляется (образы контейнеров, статические артефакты).
- Каталог размещён на сетевой файловой системе (NFS), где SQLite может давать сбои при конкурентном доступе.
- Необходимо снизить footprint на диске (база может занимать 5–15% от объёма всех RPM).

### Стратегия инкрементальных перестроений

Полная перегенерация (`createrepo_c /path/to/repo`) требуется только при:
- Изменении `comps.xml` или `modules.yaml`.
- Изменении флагов сжатия или формата индексов.
- Повреждении кэша SQLite.

Для обычного депоя пакетов используйте инкрементальный режим:
```bash
createrepo_c --update --general-compress-type zstd /var/www/html/repo/x86_64/
```

### Жёсткие ссылки и иммутабельные снапшоты

Для создания пространственно-эффективных снапшотов состояния репозитория используйте жёсткие ссылки:
```bash
# Первичная копия
cp -al /var/www/html/repo/x86_64 /var/www/html/snapshots/2025-09-13

# Последующие снапшоты добавляют только новые пакеты
cp -al /var/www/html/repo/x86_64 /var/www/html/snapshots/2025-09-20
```

При таком подходе неизменённые `.rpm`-файлы физически хранятся в одном экземпляре на диске, а каталоги `repodata/` для каждого снапшота rebuildятся независимо. Это позволяет хранить месяцы истории при росте диска только на размер новых пакетов.

### Иерархия ключей для автоматизированной подписи

В корпоративной среде для автоматизации CI/CD-пайплайнов применяют двухуровневую архитектуру:
1.  **Мастер-ключ (offline):** Создаётся на машине без доступа к сети, хранится в зашифрованном хранилище (HSM, smart-card, зашифрованный USB). Используется только для сертификации субключей.
2.  **Субключ (online):** Создаётся мастер-ключом, имеет срок действия (например, 1 год), импортируется на сервер репозитория. Используется для подписи `repomd.xml` в автоматических скриптах.

Преимущество: при компрометации субключа достаточно отозвать его и выдать новый, не трогая мастер-ключ.

## Практические сценарии

### Сценарий 1: Создание репозитория с группами и модулями

Этот сценарий описывает создание полноценного AppStream-совместимого репозитория.

#### 1. Подготовка метаданных групп (`comps.xml`)
Создайте файл описания групп для удобной установки стеков ПО:
```xml
<comps>
  <group>
    <id>my-web-stack</id>
    <name>My Web Stack</name>
    <packagelist>
      <packagereq type="mandatory">nginx</packagereq>
      <packagereq type="default">php-fpm</packagereq>
    </packagelist>
  </group>
</comps>
```

#### 2. Генерация репозитория
```bash
# Генерация базовых индексов с поддержкой групп и zstd
createrepo_c \
    --general-compress-type zstd \
    --groupfile comps.xml \
    --no-database \
    /var/www/html/repo/x86_64/
```

#### 3. Добавление модульности (`modules.yaml`)
Для поддержки модульных потоков (например, `nodejs:20` vs `nodejs:22`):
```bash
# Внедрение метаданных модулей в существующий репозиторий
modifyrepo_c --mdtype=modules modules.yaml /var/www/html/repo/x86_64/repodata/
```

### Сценарий 2: Обеспечение безопасности (GPG подпись)

#### 1. Подпись пакетов
```bash
# Настройка макроса в ~/.rpmmacros: %_gpg_name "My Org <admin@example.com>"
rpmsign --addsign /var/www/html/repo/x86_64/Packages/*.rpm
```

#### 2. Подпись индекса репозитория
Это предотвращает подмену списка пакетов злоумышленником.
```bash
cd /var/www/html/repo/x86_64/
gpg --detach-sign --armor repodata/repomd.xml
```

#### 3. Настройка клиента
Файл `/etc/yum.repos.d/internal.repo`:
```ini
[internal-repo]
name=Internal Corporate Repository
baseurl=http://repo.corp.local/x86_64/
enabled=1
gpgcheck=1
repo_gpgcheck=1
gpgkey=http://repo.corp.local/RPM-GPG-KEY-myrepo
```

### Сценарий 3: Автоматизация обновления (Cron/Timer)

Сценарий для автоматической пересборки индексов при появлении новых файлов в папке `incoming/`.

```bash
#!/bin/bash
REPO_DIR="/var/www/html/repo/x86_64"
INCOMING="/opt/repo-drop"

if [ "$(ls -A $INCOMING)" ]; then
    mv $INCOMING/*.rpm $REPO_DIR/Packages/
    # Инкрементальное обновление значительно быстрее полной пересборки
    createrepo_c --update --general-compress-type zstd $REPO_DIR
    gpg --detach-sign --armor --yes $REPO_DIR/repodata/repomd.xml
fi
```

### Сценарий 4: Валидация репозитория после создания

После генерации индексов и подписи обязательно проверьте корректность репозитория с клиентской стороны.

```bash
# 1. Доступность индексов
curl -s -o /dev/null -w "%{http_code}" http://repo.corp.local/repo/x86_64/repodata/repomd.xml
# → 200

# 2. Проверка подписи метаданных
gpg --verify /var/www/html/repo/x86_64/repodata/repomd.xml.asc \
         /var/www/html/repo/x86_64/repodata/repomd.xml
# → Good signature from ...

# 3. Проверка консистентности зависимостей (repoclosure)
sudo dnf repoclosure --repoid=internal-repo --repofrompath="internal-repo,http://repo.corp.local/repo/x86_64/"
# → Должен завершиться с кодом 0; в выводе не должно быть неудовлетворённых зависимостей

# 4. Установка тестового пакета
sudo dnf install --disablerepo="*" --enablerepo=internal-repo <test-package-name>
# → Пакет устанавливается без ошибок GPG
```

> **Важно:** `repoclosure` требует, чтобы все зависимости тестового пакета также присутствовали в проверяемом репозитории. Если вы создаёте специализированный репозиторий, добавьте `--check=rdep` или используйте `--includepkgs` на стороне клиента для подключения базовых репозиториев.

### Сценарий 5: Удаление устаревших пакетов и очистка

При ротации версий в репозитории необходимо удалять старые пакеты и перестраивать индексы.

```bash
REPO_DIR="/var/www/html/repo/x86_64"

# 1. Оставить только последние 2 версии каждого пакета
repomanage -o $REPO_DIR/Packages/ | xargs rm -f

# 2. Перестроить индексы (полная перегенерация требуется при изменении состава пакетов)
createrepo_c --general-compress-type zstd $REPO_DIR

# 3. Подписать обновлённые индексы
gpg --detach-sign --armor --yes $REPO_DIR/repodata/repomd.xml

# 4. Проверить, что старые версии удалены
dnf repoquery --available --repofrompath="my-repo,file://$REPO_DIR" --repoid=my-repo <package-name>
```

Для крупных репозиторий используйте `--newest-only` в `reposync` (если вы зеркалите upstream) или `repomanage --keep 2` для тонкого контроля.

### Сценарий 6: Раздача репозитория через Nginx

Минимальная конфигурация для раздачи RPM-репозитория по HTTP/HTTPS. Детальную конфигурацию с mTLS и ограничением доступа см. в документе **[Nginx: Настройка защищённого репозитория](../../../WebServers/Nginx/Scenarios/secure_apt_repository_guide.md)**.

```nginx
# /etc/nginx/conf.d/rpm-repo.conf
server {
    listen 80;
    server_name repo.corp.local;
    root /var/www/html/repo;
    
    # Отключаем листинг — раскрывает структуру
    autoindex off;
    
    # Правильные MIME-типы для RPM
    types {
        application/x-rpm rpm;
        application/octet-stream drpm;
    }
    
    # Кэширование статических индексов
    location ~* \.(xml|zst|asc)$ {
        expires 6h;
        add_header Cache-Control "public, immutable";
    }
    
    # Пакеты — кэшируем дольше (имя содержит хэш)
    location ~* \.rpm$ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }
    
    # repodata — короткий кэш, так как обновляется часто
    location /x86_64/repodata/ {
        expires 10m;
        add_header Cache-Control "public, must-revalidate";
    }
}
```

Для HTTPS добавьте `listen 443 ssl;` и параметры `ssl_certificate`/`ssl_certificate_key`. Для внутренних сетей достаточно самоподписанного сертификата с распространением через `gpg --export` публичного ключа CA.

### Сценарий 7: Подпись репозитория в CI/CD (иерархия ключей)

Для автоматизированных пайплайнов используйте субключ с ограниченным сроком действия. Мастер-ключ храните офлайн.

#### 1. Подготовка мастер-ключа (выполняется один раз на офлайн-машине)

```bash
# Создание мастер-ключа (офлайн)
gpg --full-generate-key
# → Выберите RSA (экспертный режим), 4096 бит, без срока действия или срок 2–3 года

# Создание субключа для подписи
gpg --edit-key <master-key-id>
gpg> addkey
# → Выберите "RSA (подпись только)", 4096 бит, срок действия 1 год

gpg> save
```

#### 2. Экспорт субключа на сервер репозитория

```bash
# Экспорт субключа (только ключ подписи)
gpg --export --armor <subkey-fingerprint> > /etc/pki/rpm-gpg/RPM-GPG-KEY-internal-sub

# Импорт на сервер
sudo rpm --import /etc/pki/rpm-gpg/RPM-GPG-KEY-internal-sub
```

#### 3. Автоматическая подпись в пайплайне

```bash
#!/bin/bash
REPO_DIR="/var/www/html/repo/x86_64"
GPG_KEY="Internal CI <ci@corp.local>"

# После перемещения новых пакетов и перестроения индексов:
createrepo_c --update --general-compress-type zstd $REPO_DIR

# Подпись от имени субключа
gpg --batch --yes --passphrase-file /run/secrets/gpg-passphrase \
    --default-key "$GPG_KEY" --armor --detach-sign $REPO_DIR/repodata/repomd.xml
```

> **Важно:** Файл с парольной фразой должен храниться в защищённом хранилище CI/CD (Vault, sealed secrets), а не в репозитории кода.

### Сценарий 8: Мультиархитектурный layout

Для поддержки нескольких архитектур (x86_64, aarch64) используйте плоскую структуру с подкаталогами или separate репозитории.

#### Вариант A: Единый репозиторий с подкаталогами

```text
/var/www/html/repo/
├── x86_64/
│   ├── Packages/
│   └── repodata/
└── aarch64/
    ├── Packages/
    └── repodata/
```

Преимущество: единый `baseurl` на клиенте с подстановкой архитектуры.

#### Вариант B: Separate репозитории (рекомендуется для крупных инфраструктур)

```text
/var/www/html/repo/
├── x86_64/
│   └── ...
└── aarch64/
    └── ...
```

На стороне клиента:
```ini
[internal-repo]
name=Internal Repository
baseurl=http://repo.corp.local/repo/$basearch/
enabled=1
gpgcheck=1
repo_gpgcheck=1
gpgkey=http://repo.corp.local/RPM-GPG-KEY-myrepo
```

DNF автоматически подставит `$basearch` (`x86_64` или `aarch64`) при запросе. Для архитектур, не требующих полного зеркала, используйте `includepkgs` в `.repo` файле.

### Сценарий 9: Производительность при больших репозиториях

При количестве пакетов >10 000 или размере репозитория >50 ГБ используйте следующие параметры:

```bash
# 1. Параллельная индексация (используйте все ядра)
createrepo_c \
    --general-compress-type zstd \
    --workers $(nproc) \
    --cachedir /var/cache/createrepo \
    --update \
    /var/www/html/repo/x86_64/

# 2. Разделение на подрепозитории по компоненту (base, updates, extras)
#    вместо одного монолитного репозитория
createrepo_c --update /var/www/html/repo/x86_64/baseos/
createrepo_c --update /var/www/html/repo/x86_64/appstream/
createrepo_c --update /var/www/html/repo/x86_64/extras/

# 3. Отключение changelog-индекса, если он не требуется клиентами
createrepo_c --changelog-limit 0 --update /var/www/html/repo/x86_64/
```

Для распределённых сред рассмотрите использование CDN или кэширующего реверс-прокси (Varnish) перед веб-сервером репозитория. Разделяйте статические пакеты (`.rpm`) и динамические индексы (`repodata/`) по разным доменам/хостам для независимого кэширования.

---
 
### Сценарий 10: Иммутабельные снапшоты для воспроизводимости

Для критичных инфраструктур (производственные кластеры, медицинские системы) создавайте снапшоты репозитория с фиксированной датой.

```bash
SNAPSHOT_DIR="/var/www/html/snapshots"
DATE=$(date +%Y-%m-%d)
REPO_DIR="/var/www/html/repo/x86_64"

# 1. Создание снапшота через жёсткие ссылки (быстро, экономит место)
mkdir -p $SNAPSHOT_DIR/$DATE
cp -al $REPO_DIR/Packages $SNAPSHOT_DIR/$DATE/
cp -al $REPO_DIR/repodata $SNAPSHOT_DIR/$DATE/

# 2. Подпись снапшота (отдельный ключ или тот же)
gpg --detach-sign --armor --yes $SNAPSHOT_DIR/$DATE/repodata/repomd.xml

# 3. Публикация snapshot-индекса
ln -sfn $SNAPSHOT_DIR/$DATE $SNAPSHOT_DIR/latest
```

На стороне клиента зафиксируйте конкретный снапшот:
```ini
[internal-repo]
name=Internal Repository (Snapshot)
baseurl=http://repo.corp.local/snapshots/2025-09-13/x86_64/
enabled=1
gpgcheck=1
repo_gpgcheck=1
gpgkey=http://repo.corp.local/RPM-GPG-KEY-myrepo
```

Для обновления клиента замените `baseurl` на более новый снапшот. Никогда не изменяйте содержимое уже опубликованного снапшота — это нарушает воспроизводимость.

## Дополнительная информация

### Рекомендации по оптимизации

- **Инкрементальность:** Флаг `--update` заставляет `createrepo_c` читать только новые или измененные пакеты, используя существующий кэш.
- **Удаление старых версий:** Для экономии места используйте `repomanage` (из `yum-utils`) для удаления устаревших версий пакетов перед запуском `createrepo_c`.
- **Проверка консистентности:** Используйте `dnf repoclosure --repoid=my-repo` для поиска неудовлетворенных зависимостей внутри вашего репозитория.
- **Кэширование Nginx:** Настройте длительный `expires` для `.rpm` и короткий для `repodata/`, чтобы минимизировать нагрузку на сервер.
- **Жёсткие ссылки:** Для нескольких релизных каналов (baseos, appstream, extras) используйте общий каталог `Packages/` с hardlinks, чтобы не дублировать одинаковые пакеты на диске.
- **База данных SQLite:** Не удаляйте файлы `.db` в `repodata/` вручную — они ускоряют последующие перестроения. Если репозиторий на NFS, используйте `--no-database`.

### Типичные проблемы и решения при создании репозитория

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **`createrepo_c: error: could not find package`** | В каталоге нет `.rpm`-файлов или права доступа ограничены. | Проверьте `ls -la $REPO_DIR/Packages/` и права на каталог. |
| **`repomd.xml signature verification failed`** (клиент) | `gpg --detach-sign` не был вызван или ключ изменён. | Переподпишите индексы и проверьте, что `gpgkey` в `.repo` указывает на актуальный ключ. |
| **`repoclosure: Error: Unable to find a match`** | В репозитории отсутствуют зависимости тестового пакета. | Убедитесь, что базовые репозитории подключены через `--repofrompath` или добавьте недостающие пакеты. |
| **`dnf install: Nothing matches`** после загрузки пакета | Пакет добавлен в `Packages/`, но не перестроены индексы. | Запустите `createrepo_c --update` и подпишите `repomd.xml`. |
| **`Metadata conflict`** | Клиент использует устаревший кэш или индексы были перестроены с другими флагами. | `sudo dnf clean metadata --repo=<repo_id>` на клиенте; проверьте, что флаги `createrepo_c` не изменились. |
| **`Permission denied` на `repodata/`** | Веб-сервер (nginx/httpd) не имеет прав на чтение индексов. | `chown -R nginx:nginx $REPO_DIR/repodata/`, `chmod 644 $REPO_DIR/repodata/*`. |
| **Нет места на диске** | Накопление старых снапшотов или дублирование пакетов без hardlinks. | Используйте `repomanage --keep 2` и перейдите на снапшоты через `cp -al`. |
| **GPG: secret key not available** при подписи | Субключ не импортирован в локальное хранилище `gpg` пользователя, от имени которого работает скрипт. | `gpg --list-secret-keys`, импортируйте субключ или используйте `--default-key` с правильным fingerprint. |
| **`createrepo_c` зависает на больших репозиториях** | Недостаточно памяти или не установлен `--workers`. | Добавьте `--workers $(nproc)` и увеличьте `--cachedir` на диск с достаточным местом. |
| **`sqlite3.OperationalError: database is locked`** | Concurrent access к кэшу SQLite (например, параллельные запуски скриптов). | Используйте `flock` вокруг `createrepo_c` или перейдите на `--no-database`. |

### Рекомендации по безопасности

1.  **GPG-верификация:** Никогда не отключайте `gpgcheck` и `repo_gpgcheck`. Скопируйте GPG-ключи на сервер зеркала и указывайте путь к ним в `gpgkey` (через HTTP или локально). Подписывайте `repomd.xml` через `gpg --detach-sign --armor`.
2.  **Изоляция стороннего ПО:** При использовании репозиториев с широким составом пакетов (например, EPEL) используйте параметр `includepkgs` в `.repo`, чтобы разрешить установку только нужных вам программ.
3.  **Архитектуры:** Используйте флаг `--arch` (RPM) или архитектурные каталоги в URL, чтобы не выкачивать пакеты для неиспользуемых архитектур.
4.  **HTTPS:** Всегда предпочитайте `https://` для защиты от перехвата и инъекций (даже если используется проверка GPG).
5.  **Сетевая изоляция:** Размещайте внутренние зеркала в отдельном VLAN. Используйте mTLS (`sslclientcert` + `sslclientkey`) для критичных контуров.
6.  **Очистка кэша:** При удалении стороннего ПО не забывайте удалять соответствующие файлы из `/etc/yum.repos.d/` и устаревшие ключи через `rpm -e gpg-pubkey-<id>`.
7.  **Жёсткие ссылки:** При синхронизации нескольких репозиториев используйте общий пул и hardlinks для экономии дискового пространства.
8.  **Воспроизводимость:** Для критичных систем используйте снапшоты зеркал с фиксированной датой, чтобы гарантировать одинаковые версии пакетов.
9.  **Верификация после изменений:** После добавления/изменения репозитория всегда выполняйте `dnf repolist` и `dnf repoinfo <repo_id>` для проверки корректности конфигурации.
10. **Иерархия ключей:** Для автоматизации используйте субключ с ограниченным сроком действия; мастер-ключ храните офлайн.
