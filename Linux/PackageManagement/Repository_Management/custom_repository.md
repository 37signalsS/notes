# Создание собственных RPM-репозиториев

## Определения

Ниже приведены основные термины, используемые при организации внутреннего хранилища программного обеспечения. Базовые сведения о репозиториях и механизмах GPG приведены в разделе **[Управление репозиториями](./index.md)**.

**Собственный репозиторий** — локальный или сетевой каталог, содержащий специально подготовленные пакеты формата RPM и файлы метаданных, предназначенный для распространения программного обеспечения внутри организации или проекта.

**Метаданные репозитория** — набор файлов в формате XML (или сжатых бинарных форматов), расположенных в директории `repodata/`, которые описывают зависимости, контрольные суммы и списки файлов всех пакетов в репозитории.

**Подпись метаданных (Metadata Signing)** — процесс создания цифровой подписи для файла `repomd.xml`. Позволяет клиенту убедиться не только в подлинности отдельных пакетов, но и в целостности всего индекса репозитория, защищая от атак подмены (downgrade attacks).

**zstd (Zstandard)** — современный алгоритм сжатия, обеспечивающий высокую скорость декомпрессии при хорошем уровне сжатия. Является стандартом для метаданных в новых версиях Fedora и RHEL-based систем.

## Основные концепции

### Отличие от зеркалирования

Необходимо различать процесс создания уникального репозитория и зеркалирования существующего внешнего источника.

| Характеристика | Зеркалирование | Создание собственного репозитория |
| :--- | :--- | :--- |
| **Цель** | Локальная копия внешнего источника | Распространение собственного ПО |
| **Источник данных** | Удаленный upstream-репозиторий | Собранные вручную .rpm пакеты |
| **Ключевые утилиты** | `reposync`, `createrepo_c` | `createrepo_c`, `rpmsign`, `gpg` |
| **Источник информации** | **[Зеркалирование YUM/DNF](../../yum_dnf_repository_mirror.md)** | Данный документ |

### Инструментарий и современные стандарты (2024–2025)

Для обеспечения высокой производительности и безопасности при создании репозиториев следует придерживаться следующих практик:

1.  **Использование `createrepo_c`**: современная реализация на языке C, значительно превосходящая старый `createrepo` (Python) по скорости.
2.  **Отказ от SQLite**: пакетные менеджеры DNF4 и DNF5 более не требуют базы данных SQLite внутри метаданных. Отключение этой функции (`--no-database`) ускоряет генерацию индексов и уменьшает их объем.
3.  **Сжатие zstd**: использование `--general-compress-type zstd` ускоряет работу клиентов при обновлении метаданных.
4.  **Двойная проверка GPG**: настройка репозитория на проверку подписей как самих пакетов (`gpgcheck=1`), так и метаданных (`repo_gpgcheck=1`).

## Практические сценарии

### Сценарий 1: Первичная инициализация и публикация

#### 1. Подготовка структуры и пакетов

```bash
# Создание каталога репозитория
mkdir -p /var/www/html/repos/my-project/x86_64

# Копирование собранных пакетов
cp ~/build/*.rpm /var/www/html/repos/my-project/x86_64/
```

#### 2. Генерация метаданных (современный метод)

```bash
cd /var/www/html/repos/my-project/x86_64/

# Генерация с использованием zstd и без лишних SQLite БД
createrepo_c \
    --general-compress-type zstd \
    --no-database \
    --unique-md-filenames \
    .
```

#### 3. Настройка веб-сервера (Nginx)

Рекомендуется использовать Nginx для раздачи статического контента репозитория.

```nginx
server {
    listen 80;
    server_name repo.example.local;
    root /var/www/html/repos;

    location / {
        autoindex on; # Разрешить просмотр структуры для отладки
    }
}
```

### Сценарий 2: Обеспечение безопасности (GPG подпись)

#### 1. Подпись пакетов

Для подписи используется утилита `rpmsign`. Предварительно необходимо сгенерировать GPG-ключ.

```bash
# Настройка ~/.rpmmacros для автоматизации
# %_gpg_name My Company <admin@example.local>

# Подпись всех пакетов в директории
rpmsign --addsign *.rpm

# Проверка подписи
rpm -K app-1.0-1.el9.x86_64.rpm
```

#### 2. Подпись метаданных репозитория

После выполнения `createrepo_c` необходимо подписать файл `repomd.xml`.

```bash
cd /var/www/html/repos/my-project/x86_64/

# Создание отсоединенной подписи в формате ASCII
gpg --detach-sign --armor repodata/repomd.xml
```

#### 3. Конфигурация клиента

Файл `/etc/yum.repos.d/my-project.repo` с максимальным уровнем безопасности:

```ini
[my-project]
name=My Project Repository
baseurl=http://repo.example.local/my-project/$basearch/
enabled=1
gpgcheck=1
repo_gpgcheck=1
gpgkey=http://repo.example.local/RPM-GPG-KEY-myrepo
metadata_expire=1h
```

### Сценарий 3: Автоматизация через CI/CD (GitLab CI)

Пример этапа публикации репозитория в пайплайне.

```yaml
publish-repo:
  stage: deploy
  script:
    - # 1. Импорт приватного ключа из переменной окружения
    - echo "$GPG_PRIVATE_KEY" | gpg --import
    - # 2. Подпись пакетов
    - rpmsign --addsign build/*.rpm
    - # 3. Обновление метаданных репозитория (инкрементально)
    - createrepo_c --update --general-compress-type zstd --no-database repo/
    - # 4. Подпись метаданных
    - gpg --detach-sign --armor --yes repo/repodata/repomd.xml
    - # 5. Синхронизация с сервером публикации
    - rsync -avz --delay-updates repo/ web-server:/var/www/html/repos/my-project/
```

## Дополнительная информация

### Рекомендации по эксплуатации

- **Инкрементальные обновления**: всегда используйте флаг `--update` при добавлении новых пакетов в существующий репозиторий. Это позволяет `createrepo_c` переиспользовать старые метаданные, обрабатывая только новые файлы.
- **Очистка кэша**: при частом обновлении репозитория на сервере, клиентам может потребоваться команда `dnf clean metadata` для принудительной загрузки свежих индексов, если `metadata_expire` еще не истек.
- **Zchunk**: для очень больших репозиториев рассмотрите возможность включения поддержки zchunk (`--zck`), что позволит клиентам скачивать только дельты метаданных.
