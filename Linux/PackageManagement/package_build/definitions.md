# Сборка пакетов: Определения

## Определения

### Основные термины

**Сборка пакета (Package Building)** — процесс преобразования исходного кода программы в бинарный пакет (`.deb` или `.rpm`) с использованием специализированного инструментария дистрибутива. В контексте SRE сборка пакетов обеспечивает контроль над версиями ПО, безопасность цепочки поставок (Supply Chain Security) и возможность кастомизации под инфраструктуру.

**Исходный пакет (Source Package)** — архив, содержащий исходный код, патчи, метаданные и инструкции для сборки.
- **Формат DEB:** состоит из файлов `.dsc` (описание), `.orig.tar.gz` (оригинальный апстрим) и `.debian.tar.xz` (изменения дистрибутива). Основные форматы: `3.0 (quilt)` для стороннего ПО и `3.0 (native)` для ПО, разрабатываемого специально под дистрибутив.
- **Формат RPM:** представлен файлом `.src.rpm` (SRPM), объединяющим исходный код и spec-файл.

**Бинарный пакет (Binary Package)** — скомпилированный и упакованный файл программы, готовый к установке. Содержит исполняемые файлы, библиотеки, документацию и конфигурационные файлы. В отличие от исходных пакетов, бинарные пакеты предназначены для конечного развертывания на целевых системах.

**Апстрим (Upstream)** — оригинальный разработчик или источник программного обеспечения. Апстрим-архив содержит неизмененный код, распространяемый автором программы.

**Дистрибутивный патч (Downstream Patch)** — изменения, внесенные командой сопровождения дистрибутива (дистрибьютором) для адаптации апстрим-кода под стандарты, политики безопасности и специфику ОС.

**Метаданные (Metadata)** — структурированная информация о пакете: название, версия, зависимости, описание, информация о лицензии и контрольные суммы файлов. Метаданные хранятся в управляющих файлах и используются пакетными менеджерами для разрешения зависимостей.

**Эпоха (Epoch)** — числовой префикс версии (например, `1:2.3.4`), используемый для форсирования обновления пакета, если новая схема версионирования апстрима нарушает логику сравнения (например, переход с `20240101` на `1.0.0`). Epoch позволяет дистрибутиву переопределить порядок версий.

**Релиз (Release)** — номер пересборки пакета в дистрибутиве. Увеличивается при каждом изменении патчей, управляющих файлов или параметров сборки без изменения апстрим-версии. Например, `1:2.3.4-1ubuntu3` означает третью пересборку пакета версии `2.3.4`.

### Управляющие файлы и структуры

**Спецификация (Spec File)** — текстовый файл с расширением `.spec`, описывающий метаданные, зависимости, инструкции сборки и установки для RPM-пакета. Включает секции `%prep` (распаковка), `%build` (компиляция), `%install` (установка в BuildRoot), `%files` (состав пакета), `%changelog` (история изменений).

**Директория debian (Debian Directory)** — каталог `debian/` в корне исходного кода, содержащий управляющие файлы для сборки DEB-пакета:
- **`control`**: метаданные и зависимости.
- **`rules`**: сценарий сборки (Makefile).
- **`changelog`**: история изменений и версия.
- **`copyright`**: информация о лицензиях.
- **`patches/`**: серия патчей quilt.

**Макросы RPM (RPM Macros)** — предопределённые переменные в системе RPM (например, `%{_bindir}` для `/usr/bin`, `%{_sysconfdir}` для `/etc`), обеспечивающие переносимость spec-файлов между дистрибутивами. Макросы определены в файлах `/usr/lib/rpm/macros.d/*.macros` и могут переопределяться в `~/.rpmmacros`.

**Helper Tools (debhelper / dh)** — набор автоматизированных скриптов в системе DEB (вызываемых через команду `dh`), упрощающих написание файла `debian/rules` за счёт автоматизации типовых задач (анализ зависимостей, сжатие man-страниц, установка прав доступа). Современный стандарт использует `dh $@` в `debian/rules`.

**fakeroot** — утилита, симулирующая привилегии root для создания файлов с правильными правами владельца и режимами без реального повышения привилегий. Используется в процессе сборки DEB-пакетов для имитации установки в корневую ФС.

**debootstrap** — инструмент для установки базовой системы Debian/Ubuntu в указанную директорию. Создает минимальный chroot с пакетным менеджером и базовыми пакетами. Используется для создания сборочных окружений и базовых контейнерных образов.

### Окружение и процесс сборки

**Чистое окружение (Clean Build Environment)** — изолированная среда (`chroot` или контейнер), гарантирующая отсутствие скрытых зависимостей хост-системы. Использование чистых сред обеспечивает воспроизводимость и исключает проблему «загадочных» зависимостей, когда сборка проходит на одной машине и fails на другой.
- **Инструменты:** `sbuild`, `pbuilder`, `cowbuilder` (DEB); `mock` (RPM).
- **Реализация:** Инструменты создают минимальную ОС в оперативной памяти или временной директории, в которую устанавливаются только явно указанные в `Build-Depends`/`BuildRequires` зависимости.

**Фиктивный корень сборки (Build Root)** — временная директория (`%{buildroot}` в RPM или `debian/tmp` в DEB), имитирующая корневую файловую систему (`/`), куда устанавливаются файлы программы перед их упаковкой. Это позволяет изолировать файлы будущего пакета от хостовой системы.

**Зависимости сборки (Build Dependencies)** — пакеты, необходимые для компиляции (компиляторы, заголовочные файлы библиотек `-dev` или `-devel`, утилиты генерации кода). Указываются в `Build-Depends` (DEB) или `BuildRequires` (RPM). В отличие от runtime-зависимостей, build-dependencies не устанавливаются на целевую систему вместе с пакетом.

**Зависимости выполнения (Runtime Dependencies)** — пакеты, необходимые для работы программы после установки. Вычисляются автоматически инструментами `shlibs` (DEB) или `find-requires` (RPM) на основе анализа разделяемых библиотек.

**Скрипты сопровождения (Maintainer Scripts)** — исполняемые сценарии, запускаемые на этапах жизненного цикла: `preinst`/`postinst` (до/после установки), `prerm`/`postrm` (до/после удаления). В RPM называются scriptlets (`%pre`, `%post`, `%preun`, `%postun`). Скрипты должны быть идемпотентными, так как могут запускаться повторно при сбоях.

**Патч (Patch)** — файл с изменениями исходного кода, созданный утилитой `diff`. В DEB управляется через систему `quilt`, в RPM — через директивы `Patch:` в spec-файле. Патчи применяются к апстрим-источникам для адаптации под дистрибутив, исправления уязвимостей или добавления функционала.

**Серия патчей (Patch Series)** — упорядоченный набор патчей, применяемых последовательно. В DEB управляется через `debian/patches/series` и quilt. Правильный порядок патчей критичен: более общие изменения должны предшествовать специфичным.

**Метапакет (Meta Package)** — пакет, не содержащий файлов, но объявляющий зависимости от других пакетов. Используется для управления группами ПО. В DEB создается через `equivs`; в RPM — через spec-файл с пустой секцией `%files` и перечислением зависимостей в `Requires`.

### Артефакты и архитектура

**Архитектура пакета (Package Architecture)**:
- **Архитектурно-зависимые:** `x86_64`, `aarch64`, `i386`, `armhf`, `arm64`.
- **Архитектурно-независимые:** `all` (DEB) или `noarch` (RPM) — пакеты с архитектурно-независимым содержимым (скрипты, документация, Java-приложения).

**Multiarch (Multi-Architecture)** — механизм в Debian/Ubuntu, позволяющий параллельно устанавливать пакеты для разных архитектур (например, `libc6:amd64` и `libc6:arm64` для кросс-компиляции). Включается через `dpkg --add-architecture <arch>`.

**Debuginfo / Debugsource** — дополнительные пакеты, содержащие отладочные символы (`.debug` файлы) и исходный код соответственно. Генерируются автоматически при сборке для облегчения трассировки ошибок (например, через `gdb` или `crash`). В RPM создаются через `%debug_package`.

**Подпись пакета (Package Signing)** — использование GPG для создания цифровой подписи, гарантирующей подлинность пакета и целостность его содержимого. Подпись проверяется пакетным менеджером перед установкой. Для корпоративных сред рекомендуется использовать отдельные ключи для signing и daily operations.

**Воспроизводимость сборки (Reproducible Build)** — свойство процесса, при котором повторная сборка из тех же исходников дает побитово идентичный результат. Регулируется переменной `SOURCE_DATE_EPOCH`. Критично для безопасности цепочки поставок и аудита.

**Файловая иерархия (FHS — Filesystem Hierarchy Standard)** — стандарт, определяющий структуру каталогов в Linux-системах (`/usr/bin`, `/etc`, `/var`). Пакеты должны соблюдать FHS для совместимости между дистрибутивами. Нарушение приводит к ошибкам сборки (`lintian`/`rpmlint`) или некорректной работе ПО.

### Типы зависимостей периода выполнения

| Тип (DEB) | Тип (RPM) | Описание |
| :--- | :--- | :--- |
| **Depends** | **Requires** | Обязательные зависимости для работы. |
| **Pre-Depends** | **Requires(pre)** | Пакеты, которые должны быть полностью настроены ДО начала установки текущего пакета. |
| **Recommends** | **Suggests** (совм. с `--recommends`) | Сильные, но не обязательные зависимости (устанавливаются по умолчанию). |
| **Suggests** | **Suggests** | Дополнительные пакеты, расширяющие функционал. |
| **Enhances** | **Supplements** | Пакеты, которые расширяют функционал текущего пакета. |
| **Conflicts** | **Conflicts** | Запрещает одновременную установку с указанным пакетом. |
| **Breaks** | **Breaks** | Указывает, что пакет несовместим с указанным (деструктивный конфликт). |
| **Provides** | **Provides** | Позволяет пакету объявить, что он предоставляет функционал другого виртуального пакета. |
| **Replaces** | **Obsoletes** | Указывает, что пакет заменяет или поглощает функционал другого (старого) пакета. |

### Сопровождение и политики

**Сопровождающий (Maintainer)** — человек или команда, ответственная за обновление пакета в дистрибутиве. Отвечает за актуальность патчей, исправление уязвимостей и взаимодействие с апстримом.

**Политика дистрибутива (Distribution Policy)** — набор правил и стандартов, которым должны соответствовать пакеты (Debian Policy, Fedora Packaging Guidelines). Включает требования к структуре пакетов, именованию, зависимостям, безопасности и документации. Соблюдение политики проверяется линтерами (`lintian`, `rpmlint`).

**Security Tracker** — система отслеживания уязвимостей в пакетах дистрибутива (например, Debian Security Tracker, Red Hat CVE Database). Позволяет SRE-командам быстро определять, в какие пакеты включены исправления для конкретных CVE.

**Транзакция (Transaction)** — атомарная последовательность действий по изменению состава ПО. В контексте сборки транзакция означает полный цикл: от подготовки исходников до подписи и публикации артефакта. В RPM-based системах DNF поддерживает откат транзакций; в DEB-системах откат реализуется через логирование.

## Основные концепции

### Ценность сборки пакетов для DevOps/SRE

Для инженеров DevOps и SRE сборка пакетов — не академическое упражнение, а практический инструмент решения операционных задач:

1. **Безопасность цепочки поставок (Supply Chain Security):** Сборка из проверенных исходников с собственными патчами снижает риск внедрения вредоносного кода через скомпрометированные репозитории или пакеты.
2. **Кастомизация и бэкпортирование:** Возможность добавить патчи, изменить параметры компиляции (флаги hardening) или перенести новую версию ПО в стабильный релиз дистрибутива.
3. **Соответствие и аудит:** Корпоративные политики часто требуют, чтобы все устанавливаемое ПО собиралось из исходников с подтверждаемой целостностью.
4. **Производительность:** Оптимизация бинарных файлов под конкретное железо (SSE, AVX, ARM NEON) или исключение ненужных модулей.
5. **Воспроизводимость:** Гарантия, что одна и та же версия ПО будет собираться идентично на любом окружении, что критично для compliance и отладки.

### Архитектура процесса сборки

Процесс создания пакета — это строго регламентированная последовательность действий, направленная на получение воспроизводимого программного артефакта, который может быть безопасно установлен и удален в рамках экосистемы дистрибутива.

#### Этапы жизненного цикла сборки

Типовой процесс сборки (как для DEB, так и для RPM) проходит через следующие критические стадии:

1.  **Распаковка и подготовка (Preparation):** Распаковка оригинального архива (upstream source) и применение специфичных для дистрибутива патчей.
2.  **Анализ зависимостей (Dependency Analysis):** Проверка наличия инструментов (`gcc`, `cmake`) и библиотек (`libssl-dev`), необходимых для компиляции. Если зависимости `Build-Depends` (DEB) или `BuildRequires` (RPM) не удовлетворены, сборка прерывается.
3.  **Компиляция (Build):** Выполнение команд сборки. На этом этапе формируются бинарные файлы и библиотеки. Важно использовать флаги компиляции дистрибутива для обеспечения безопасности (например, `PIE`, `stack-protector`, `FORTIFY_SOURCE`).
4.  **Установка в BuildRoot (Installation):** Команда `make install` направляет файлы не в реальную систему, а во временную директорию (фиктивный корень). Это позволяет изолировать файлы будущего пакета.
5.  **Анализ состава и линтинг (Inspection):** Автоматическая проверка полученных файлов. Например, проверка наличия man-страниц, корректности прав доступа, соблюдения FHS и отсутствия конфликтов.
6.  **Генерация метаданных (Metadata Generation):** Вычисление динамических зависимостей (например, поиск всех используемых `.so` библиотек и добавление их в `Depends` или `Requires`).
7.  **Упаковка (Packaging):** Сжатие файлов и метаданных в итоговый формат (`.deb` — `ar`, `.rpm` — `cpio`).
8.  **Подпись (Signing):** Создание цифровой подписи GPG для подтверждения доверия.

#### DEB vs RPM: принципиальные различия

| Аспект | DEB (Debian/Ubuntu) | RPM (RHEL/Fedora) |
| :--- | :--- | :--- |
| **Центральный управляющий файл** | Директория `debian/` с набором файлов | Один `.spec` файл |
| **Система патчей** | `quilt` (серия `.patch` файлов в `debian/patches/`) | Директивы `Patch0`, `Patch1` в `.spec` |
| **Сборка** | `dpkg-buildpackage` (инкапсулирует `debian/rules`) | `rpmbuild` (вызывает секции `.spec`) |
| **Изоляция** | `sbuild`, `pbuilder`, `cowbuilder` | `mock` |
| **Линтинг** | `lintian` | `rpmlint` |
| **Версионирование** | `<epoch>:<upstream>-<debian_revision>` | `<epoch>:<upstream>-<release>` |
| **Хранилище БД** | `/var/lib/dpkg/status` (текстовые файлы) | `/var/lib/rpm/` (Berkeley DB / SQLite) |

#### Изоляция и чистое окружение

Сборка в "загрязненной" системе (где установлены лишние библиотеки или другие версии toolchain) — главная причина невоспроизводимых ошибок и артефактов, которые работают на машине разработчика, но fails на сервере.

1.  **Изоляция (Chroot/Namespaces):** Инструменты `mock` (RPM) и `sbuild` (DEB) создают минимальную ОС в оперативной памяти или временной директории. В эту среду устанавливаются **только** те зависимости, которые явно указаны в управляющих файлах. Это исключает влияние хостовой среды.
2.  **Воспроизводимость (Reproducible Builds):** Гарантирует, что побитово идентичный результат получается независимо от времени сборки, пути к директории или версии ядра хоста. Это достигается путем фиксации временных меток через `SOURCE_DATE_EPOCH`, нормализации прав доступа и исключения недетерминированных данных из артефакта.

### Архитектура DEB-пакетов (Debian/Ubuntu)

В системе Debian инструкции по сборке сосредоточены в каталоге `debian/`.

*   **Система quilt:** Стандарт `3.0 (quilt)` разделяет оригинальный код и правки дистрибутива. Все изменения хранятся в виде патчей в `debian/patches/`, что позволяет легко обновлять версию программы (upstream), просто заменяя основной архив и пересобиравая patch series.
*   **Скрипты сопровождения (Maintainer Scripts):**
    *   `preinst`/`postinst`: выполняются до и после распаковки файлов.
    *   `prerm`/`postrm`: выполняются до и после удаления пакета.
    *   *Важно:* скрипты должны быть идемпотентными, так как они могут запускаться повторно при сбоях.
*   **Формат dh (debhelper):** Современная абстракция над этапами сборки. Файл `rules` обычно содержит одну строку `dh $@`, которая сама вызывает нужные утилиты (`dh_link`, `dh_compress`, `dh_strip`) в правильном порядке.

### Архитектура RPM-пакетов (RHEL/Fedora)

Центральным элементом является `.spec` файл, работающий на основе макросов и секций.

*   **Макроопределения:** Конструкции вида `%{_bindir}` позволяют спек-файлу быть переносимым. Например, на одной системе это может быть `/usr/bin`, а на другой — `/bin`.
*   **Секции жизненного цикла:**
    *   `%prep`: автоматизирует распаковку (`%setup`) и применение патчей (`%patch`).
    *   `%build`: содержит логику компиляции.
    *   `%install`: выполняет установку в `%{buildroot}`.
    *   `%files`: содержит жесткий список файлов. Любой лишний или отсутствующий файл в BuildRoot приведет к ошибке сборки (метод "Fail-Fast").
*   **Скриптлеты (%pre, %post, %preun, %postun):** Аналоги Maintainer Scripts в DEB. Часто включают вызовы макросов для регистрации сервисов (например, `%systemd_post`).

## Практические сценарии

### Предварительные требования и настройка окружения

Перед сборкой пакетов необходимо подготовить сборочное окружение.

#### DEB (Debian/Ubuntu)

```bash
# Установка инструментов сборки
sudo apt update
sudo apt install -y build-essential devscripts debhelper fakeroot \
    lintian pbuilder sbuild quilt

# Инициализация pbuilder (создание базового chroot)
sudo pbuilder create --debootstrapopts --variant=buildd --distribution bookworm

# Инициализация sbuild
sudo sbuild-createchroot bookworm /srv/chroot/bookworm-amd64-sbuild http://deb.debian.org/debian
```

#### RPM (RHEL/Fedora/AlmaLinux/Rocky Linux)

```bash
# Установка инструментов сборки
sudo dnf install -y rpm-build rpmdevtools rpmlint mock dnf-plugins-core

# Инициализация дерева rpmbuild
rpmdev-setuptree

# Инициализация mock
sudo mock -r epel-9-x86_64 --init
```

### Пошаговый процесс сборки (универсальный)

1.  **Получение исходников:**
    - DEB: `apt-get source <package_name>` или загрузка `.dsc` + архивов.
    - RPM: `dnf download --source <package_name>` и распаковка `rpm -i <package>.src.rpm`.
2.  **Установка build-зависимостей:**
    - DEB: `sudo apt-get build-dep <package_name>`.
    - RPM: `sudo dnf builddep ~/rpmbuild/SPECS/<package_name>.spec`.
3.  **Применение патчей (при необходимости):**
    - DEB: `quilt push -a && quilt new fix.patch && quilt add file && ... && quilt refresh`.
    - RPM: размещение `.patch` файлов в `~/rpmbuild/SOURCES/` и добавление директив `Patch0: fix.patch` в `.spec`.
4.  **Обновление версии (changelog):**
    - DEB: `dch -i "New patch for ..."`.
    - RPM: обновление `%changelog` секции в `.spec`.
5.  **Сборка:**
    - DEB: `dpkg-buildpackage -us -uc -b` (только бинарный) или `-S` (только исходный).
    - RPM: `rpmbuild -ba ~/rpmbuild/SPECS/<package_name>.spec` (бинарный + исходный) или `-bb` (только бинарный).
6.  **Линтинг:**
    - DEB: `lintian ../<package>_*.changes`.
    - RPM: `rpmlint ~/rpmbuild/SPECS/<package>.spec`.

### Быстрая проверка собранного пакета

После сборки пакет должен пройти базовую проверку перед распространением.

#### DEB

```bash
# Проверкаlintian (политика Debian)
lintian ../package_1.0-1_amd64.deb

# Просмотр содержимого
dpkg-deb --contents package_1.0-1_amd64.deb
dpkg-deb --info package_1.0-1_amd64.deb

# Проверка контрольных сумм
debsums -s package_1.0-1_amd64.deb

# Установка и проверка работоспособности
sudo dpkg -i package_1.0-1_amd64.deb
# → result: пакет установлен без ошибок зависимостей
```

#### RPM

```bash
# Проверка rpmlint (политика Fedora/RHEL)
rpmlint ~/rpmbuild/RPMS/x86_64/package-1.0-1.el9.x86_64.rpm

# Просмотр содержимого
rpm -qpl ~/rpmbuild/RPMS/x86_64/package-1.0-1.el9.x86_64.rpm

# Проверка GPG подписи (если подписана)
rpm -K ~/rpmbuild/RPMS/x86_64/package-1.0-1.el9.x86_64.rpm
# → result: digests signatures OK

# Установка
sudo rpm -ivh ~/rpmbuild/RPMS/x86_64/package-1.0-1.el9.x86_64.rpm
```

### Типичные ошибки и быстрые решения

| Симптом / Ошибка | Причина | Быстрое решение |
| :--- | :--- | :--- |
| **Missing Build-Depends** | Не установлен заголовочный файл или утилита. | DEB: `apt-get build-dep <pkg>`; RPM: `dnf builddep <.spec>`. |
| **Installed but unpackaged files** | Файл создан в BuildRoot, но не указан в `%files`. | Добавьте путь в секцию `%files` (RPM) или `debian/<pkg>.install` (DEB). |
| **Symbol lookup error** | Несоответствие версий разделяемых библиотек. | Проверьте runtime-зависимости и используйте чистое окружение. |
| **Permission denied in BuildRoot** | Попытка записи вне фиктивного корня. | Проверьте `DESTDIR` (DEB) или `%{buildroot}` (RPM). |
| **File not found: /bin/sh** | В chroot отсутствует `/bin/sh` или `.` не монтируется. | Проверьте наличие `bash`/`dash` и смонтированных `/proc`, `/sys`, `/dev`. |
| **No matching manifest** | Встроенный макро `%{_arch}` не совпадает с целевой архитектурой. | Проверьте `--target` или `--arch` параметры сборки. |

### Интеграция с конфигурационным управлением

В корпоративных средах сборка пакетов часто интегрируется с Ansible для автоматизации подготовки сборочных окружений:

```yaml
- name: Установка инструментов сборки DEB
  apt:
    name:
      - build-essential
      - devscripts
      - debhelper
      - fakeroot
      - sbuild
    state: present
  when: ansible_facts['os_family'] == 'Debian'

- name: Создание chroot окружения для сборки
  command: >
    sbuild-createchroot bookworm /srv/chroot/bookworm-amd64-sbuild
    http://deb.debian.org/debian
  args:
    creates: /srv/chroot/bookworm-amd64-sbuild
  become: true
```

## Дополнительная информация

### Безопасность и подпись

**Управление GPG-ключами в корпоративной среде:**

1.  **Разделение ключей:** Используйте отдельные ключи для ежедневной подписи и для CI/CD. Ключ CI должен иметь ограниченный срок действия и храниться в HSM или секрет-менеджере (HashiCorp Vault, SOPS).
2.  **Алгоритмы:** Предпочитайте RSA 4096 или Ed25519. Избегайте DSA (устарел) и RSA < 2048.
3.  **Резервное копирование:** Храните резервные копии секретных ключей в защищенном хранилище (offline, зашифрованном).
4.  **Отзыв:** Подготовьте отзывной сертификат (revocation certificate) заранее — на случай компрометации ключа.

```bash
# Создание ключа (офлайн, на air-gapped машине)
gpg --full-generate-key
# → RSA (встроить только подпись) / 4096 бит / срок действия 2 года

# Экспорт открытого ключа для распространения
gpg --armor --export <key-id> > public-key.asc

# Подпись DEB-пакета
debsign -k<key-id> ../package_1.0-1_amd64.changes

# Подпись RPM-пакета
echo "$GPG_PRIVATE_KEY" | gpg --import
rpmsign --addsign --key-id=<key-id> package-1.0-1.el9.x86_64.rpm
```

### Аудит и соответствие

В regulated environments (финансы, госсектор) требуется доказательство того, что устанавливаемое ПО собрано из проверенных исходников:

1.  **Воспроизводимые сборки:** Включите `SOURCE_DATE_EPOCH` и протестируйте reproducible builds через `diffoscope`.
2.  **Трассируемость:** Каждый собранный пакет должен содержать в metadata ссылку на коммит исходников, время сборки и ID сборщика.
3.  **Сканирование уязвимостей:** Интегрируйте `trivy`, `grype` или `clair` в пайплайн сборки для сканирования артефактов.
4.  **SBOM (Software Bill of Materials):** Генерируйте SBOM для каждого пакета (форматы SPDX, CycloneDX). Инструменты: `syft`, `spdx-sbom-generator`.
