# Обзор управления пакетами в Linux: RPM и DEB

## Определения

Ниже приведены основные термины, используемые в экосистеме управления программным обеспечением в дистрибутивах Linux.

**Пакет (Package)** — архив специального формата, содержащий файлы программного обеспечения, метаданные (версия, зависимости, контрольные суммы), а также скрипты для автоматизации установки и удаления.

**Зависимость (Dependency)** — внешний пакет или библиотека, которые необходимы для работы установленной программы. Если требуемая зависимость отсутствует в системе, программа не запустится. Пакетные менеджеры существуют именно для автоматизации поиска и установки зависимостей.

**Низкоуровневая утилита (Backend)** — инструмент для прямой работы с файлами пакетов и локальной базой данных: `rpm` для формата RPM (Red Hat Package Manager) или `dpkg` для формата DEB (Debian Package). Позволяет устанавливать и удалять конкретные файлы, но не умеет автоматически разрешать зависимости через сеть.

**Высокоуровневая утилита (Frontend / Пакетный менеджер)** — надстройка, упрощающая управление программным обеспечением: `dnf` (Dandified YUM) / `yum` для RPM или `apt` (Advanced Package Tool) для DEB. Работает с репозиториями, автоматически вычисляет граф зависимостей и управляет системными обновлениями.

**Универсальный формат (Universal / Sandbox Package)** — системы распространения ПО (Snap, Flatpak, AppImage), которые включают в себя все необходимые зависимости и рантаймы, работая изолированно от пакетного менеджера дистрибутива.

**Репозиторий (Repository)** — структурированное хранилище пакетов и их метаданных (индексов). Позволяет пакетным менеджерам находить и скачивать актуальные версии ПО.

**Транзакция (Transaction)** — атомарная последовательность действий по изменению состава ПО. Позволяет отслеживать историю изменений и выполнять откат (rollback) в случае сбоев (наиболее полно реализовано в DNF).

**SAT-солвер (SAT Solver)** — алгоритм разрешения зависимостей, используемый для поиска непротиворечивого набора пакетов при сложных графах связей. В RPM-системах применяется библиотека `libsolv`, в DEB — встроенный решатель APT (Solver3 в версиях 2.x/3.x).

**Кэш метаданных (Metadata Cache)** — локальная копия индексов репозиториев (`/var/lib/apt/lists/` для DEB, `/var/cache/dnf/` для RPM). Ускоряет операции поиска и позволяет работать при отсутствии сети.

**installonlypkgs** — специальный класс пакетов в RPM (по умолчанию `kernel`), которые не удаляются при `dnf upgrade`. Вместо этого DNF хранит несколько последних версий параллельно, ограничиваясь `installonly_limit` (по умолчанию 3). При превышении лимита самая старая версия удаляется автоматически.

## Основные концепции

### Сравнение традиционных систем пакетов

| Характеристика | RPM (Red Hat Package Manager) | DEB (Debian Package) |
| :--- | :--- | :--- |
| **Ключевые дистрибутивы** | Fedora, RHEL, AlmaLinux, Rocky Linux | Debian, Ubuntu, Linux Mint, Kali |
| **Формат архива** | `cpio` (внутри `.rpm`) | `ar` + `tar` (внутри `.deb`) |
| **Низкоуровневая утилита** | `rpm` | `dpkg` |
| **Высокоуровневая утилита** | `dnf` (DNF 4 / DNF 5) | `apt` (APT 2.x / 3.x) |
| **Системная база данных** | `/var/lib/rpm/` (SQLite / BDB) | `/var/lib/dpkg/` (status файлы) |

> **Важно:** экосистемы RPM и DEB **взаимно несовместимы**. Утилиты `apt`/`dpkg`
> работают только на дистрибутивах Debian/Ubuntu и не применимы к RHEL/CentOS/Fedora.
> Аналогично, `dnf`/`rpm` не работают на Debian/Ubuntu. Для кросс-платформенной
> установки используйте универсальные форматы (Snap, Flatpak, AppImage) или
> контейнеризацию.

### Ад зависимостей (Dependency Hell)

В ранних дистрибутивах Linux отсутствовали автоматические менеджеры зависимостей. Системный администратор вручную искал, скачивал и доставлял сотни общих библиотек, необходимых для работы программы. Эта трудоёмкая и error-prone практика получила название «ад зависимостей» (dependency hell). Современные высокоуровневые менеджеры (`apt`, `dnf`) решают эту проблему, автоматически строя граф зависимостей и загружая недостающие пакеты из репозиториев.

### Специальные типы зависимостей

Пакетные менеджеры различают несколько категорий зависимостей, что влияет на автоматическую установку:

| Тип | DEB | RPM | Поведение |
| :--- | :--- | :--- | :--- |
| **Жёсткие (Hard/Required)** | `Depends` | `Requires` | Обязательны для работы; пакет не установится без них. |
| **Рекомендуемые (Recommends)** | `Recommends` | `Recommends` | Устанавливаются по умолчанию, но могут быть отключены. |
| **Предлагаемые (Suggests)** | `Suggests` | `Suggests` | Не устанавливаются автоматически; информационный характер. |
| **Конфликты (Conflicts)** | `Conflicts` | `Conflicts` | Пакет несовместим с указанными пакетами. |
| **Замены (Breaks/Obsoletes)** | `Breaks` | `Obsoletes` | Пакет замещает/ломает другой пакет при обновлении. |

### Универсальные форматы: Snap, Flatpak, AppImage

Современные методы доставки ПО, решающие проблему «ада зависимостей» и фрагментации дистрибутивов через изоляцию (sandboxing).

| Формат | Изоляция (Sandboxing) | Обновления | Основное применение |
| :--- | :--- | :--- | :--- |
| **Snap** | AppArmor / Cgroups / Seccomp | Автоматические | Серверное и десктопное ПО (Ubuntu) |
| **Flatpak** | Bubblewrap / OSTree | Ручные/Авто | Десктопные приложения (GUI) |
| **AppImage** | Опционально (через Type 2) | Ручные | Портативное ПО (один файл) |

### Принцип работы высокоуровневых менеджеров

Процесс установки пакета (например, через `apt install` или `dnf install`) включает следующие этапы:

1.  **Обновление метаданных**: Загрузка свежих индексов из репозиториев (файлы `Packages.gz` или `repomd.xml`) в локальный кэш.
2.  **Анализ дерева зависимостей**: Построение графа связей. Использование SAT-солверов (например, `libsolv`) для поиска непротиворечивого решения.
3.  **Планирование транзакции**: Оценка объема загрузки, проверка конфликтов и требуемого места на диске.
4.  **Исполнение**:
    *   Загрузка архивов в `/var/cache/apt/archives/` или `/var/cache/dnf/`.
    *   Проверка целостности и подлинности через GPG-подписи.
    *   Вызов низкоуровневой утилиты (`dpkg`/`rpm`) для распаковки.
    *   Выполнение скриптов жизненного цикла (`preinst`, `postinst`, `%pre`, `%post`).
5.  **Регистрация**: Обновление локальной базы данных установленного ПО и триггеров (например, `ldconfig`).

### Технологические особенности APT (Advanced Package Tool)

#### Решатель зависимостей Solver3 (APT 3.0+)

В современных версиях (Debian 13 "Trixie", Ubuntu 24.10 "Oracular") внедрен новый алгоритм разрешения зависимостей:
- **Интеллектуальный backtracking**: Быстрый поиск альтернативных путей при возникновении конфликтов зависимостей.
- **Инструментарий анализа**: Команды `apt why <pkg>` и `apt why-not <pkg>` позволяют визуализировать логику принятия решений менеджером.

#### Микроархитектурные уровни x86-64-v2/v3/v4

Начиная с APT 3.2, поддерживается автоматический выбор пакетов, скомпилированных под конкретные наборы инструкций CPU (AVX, AVX2, AVX-512). Система автоматически скачивает наиболее производительную версию пакета для текущего процессора.

### Эволюция RPM: DNF 5

DNF 5 (Fedora 41+, RHEL 10) представляет собой полную перезапись менеджера на C++:
- **Производительность**: Исключение интерпретатора Python значительно ускоряет обработку метаданных и запуск команд.
- **Унификация**: Все компоненты используют единую библиотеку `libdnf5`, что гарантирует идентичное поведение CLI и API.
- **Легковесность**: Уменьшение объема зависимостей самого пакетного менеджера, что критично для минимальных контейнерных образов.

### Механизм транзакций и откат

Транзакционный механизм различается между RPM и DEB экосистемами, что критически важно для SRE при проектировании процедур обновления и аварийного восстановления.

**RPM (DNF):**
- Каждая транзакция записывается в базу данных истории (`/var/lib/dnf/history/` в SQLite).
- Поддерживает нативный откат: `dnf history undo <id>` — полностью восстанавливает состояние системы на момент до транзакции.
- При прерывании транзакции (отключение питания, `SIGKILL`) RPM оставляет пакеты в промежуточных статусах (`uninstalled`, `post-install`), но БД остается консистентной. DNF автоматически определяет и исправляет такие состояния при следующем запуске.

**DEB (APT/dpkg):**
- Не имеет встроенного механизма отката транзакций. История фиксируется в текстовых логах `/var/log/dpkg.log` и `/var/log/apt/history.log`.
- При прерывании транзакции пакеты остаются в состояниях `half-installed`, `half-configured` или `unpacked`. Команда `sudo dpkg --configure -a` доразворачивает все пакеты, оставленные в незавершённом состоянии.
- Для ручного отката требуется восстановление из резервной копии `/var/lib/dpkg/status-old` или использование инструментов вроде `etckeeper` для отслеживания изменений конфигураций.

### Особенности управления ядром

В RPM-системах ядро относится к классу `installonlypkgs`. Это означает, что при обновлении старое ядро не удаляется автоматически. DNF хранит до `installonly_limit` версий (по умолчанию 3), после чего самая старая удаляется. Это предотвращает ситуации, когда сбойное обновление ядра делает систему не загружаемой.

В DEB-системах аналогичного автоматического поведения нет. Каждое новое ядро (`linux-image-*`) устанавливается как обычный пакет, и старое ядро удаляется только при выполнении `apt autoremove` или ручного `apt remove`.

### Проверка подлинности и целостности пакетов

Перед установкой любой пакетный менеджер выполняет двухуровневую проверку:

1. **GPG-подпись репозитория**: Проверяется подпись метаданных репозитория (`Release` для DEB, `repomd.xml` для RPM). Это гарантирует, что индексы не были изменены в пути.
2. **GPG-подпись пакета**: Каждый пакет подписан maintainer'ом. Проверка осуществляется через цепочку доверия: системные ключи (`/usr/share/keyrings/`) → ключи репозитория → ключи пакетов.

Конфигурация параметров безопасности:

```ini
# /etc/dnf/dnf.conf (RPM)
[main]
gpgcheck=1
repo_gpgcheck=1
protected_packages=dnf, glibc, systemd

# /etc/apt/apt.conf.d/ (DEB)
APT::Get::AllowUnauthenticated "false";
```

### Утилита dpkg: низкоуровневая работа с пакетами DEB

Утилита `dpkg` (Debian Package) — фундаментальный низкоуровневый менеджер пакетов в дистрибутивах Debian/Ubuntu.
Она является слоем, непосредственно взаимодействующим с файлами `.deb` и локальной базой данных в `/var/lib/dpkg/`.
Высокоуровневый менеджер `apt` использует `dpkg` во время фазы установки (см. пункт 4 «Исполнение» в секции «Принцип работы высокоуровневых менеджеров»),
но сам по себе `dpkg` не выходит в интернет и не умеет разрешать зависимости.
Она работает **только** с теми файлами `.deb`, которые уже скачаны на локальный диск.

> **Главная ловушка `dpkg`:** если пакет требует для работы внешнюю библиотеку или другой пакет,
> `dpkg` не станет её искать и скачивать. Установка будет остановлена с ошибкой зависимостей:
> «Необходима зависимость, но где её взять, я не знаю».
> Разрешением зависимостей занимает `apt` (или `aptitude`), которые скачивают недостающие пакеты из репозиториев,
> а затем вызывают `dpkg` для фактической распаковки.
> Поэтому `dpkg` применяют для **локальной работы** с уже скачанными файлами, а `apt` — для **работы с репозиториями**.

#### Ключевые команды dpkg

| Флаг | Расшифровка | Назначение |
| :--- | :--- | :--- |
| `dpkg -i <file.deb>` | install | Распаковка и установка локального `.deb`-файла. |
| `dpkg -l` | list | Вывод таблицы всех установленных пакетов (аудит). |
| `dpkg -L <pkg>` | list files | Список файлов, принадлежащих уже установленному пакету. |
| `dpkg -s <pkg>` | status | Метаданные и статус установленного пакета. |
| `dpkg -r <pkg>` | remove | Удаление пакета (конфиги сохраняются). |
| `dpkg -P <pkg>` | purge | Полное удаление пакета вместе с конфигурационными файлами. |
| `dpkg --configure -a` | configure all | Доразворачивает пакеты, оставленные в незавершённом состоянии. |

```bash
# Установка локального .deb-файла (без разрешения зависимостей)
sudo dpkg -i /tmp/example.deb
# → result: файлы распакованы и установлены; если есть незаполненные зависимости — ошибка

# Список всех установленных пакетов (ключевой инструмент аудита)
dpkg -l
# → result: таблица с колонками: статус (ii, rc, iF), имя, версия, архитектура, описание

# Список файлов конкретного установленного пакета
dpkg -L nginx
# → result: пути к файлам: /usr/sbin/nginx, /etc/nginx/nginx.conf, /usr/share/doc/nginx/...

# Статус конкретного пакета
dpkg -s nginx
# → result: информация о статусе, версии, зависимостях, размере и т.п.

# Если установка была прервана — завершить конфигурацию всех пакетов
sudo dpkg --configure -a
```

> **Важно для экзамена (LPIC-1):** экзаменаторы часто проверяют внимание к регистру букв.
> Строчные флаги (`-i`, `-l`) выполняют установку и вывод списка.
> Заглавные `-I` (информация о `.deb`-файле) и `-L` (список файлов установленного пакета)
> делают совершенно другое. На экзамене всегда обращайте внимание,
> является ли буква в флаге строчной или заглавной.

С подробным разбором состояния базы данных `dpkg`, структурой `/var/lib/dpkg/` и методами
восстановления повреждённого `status`-файла см. [База данных пакетов](./package_database.md).

### Рабочий процесс APT: update, upgrade и установка

Команды `apt update` и `apt upgrade` выполняют разные задачи, и их путаница является типичной ошибкой при работе с DEB-системами.

**`apt update`** — загружает свежие текстовые индексы (списки доступных пакетов и версий) из официальных репозиториев в локальный кэш (`/var/lib/apt/lists/`). Эта команда **не обновляет** уже установленные программы. Она лишь синхронизирует информацию о доступном ПО, подготавливая систему к установке или обновлению.

**`apt upgrade`** — скачивает и устанавливает новые версии пакетов, уже присутствующих в системе. Для этого APT использует индексы, загруженные предшествующим `apt update`. Если обновление требует удаления одного пакета и установки другого (изменение графа зависимостей), используйте **`apt full-upgrade`**.

**`apt install <name>`** — устанавливает новый пакет и автоматически разрешает зависимости. При наличии всех зависимостей в репозиториях APT загружает их, проверяет целостность через GPG-подписи и выводит план установки для подтверждения. Пример установки медиаплеера VLC:
```bash
sudo apt update
sudo apt install vlc
# → APT выводит список пакетов для установки и запрашивает подтверждение
```

Для неинтерактивного режима (скрипты, CI/CD, Docker-сборки) используется флаг `-y` (от слова `yes`), подавляющий запросы подтверждения:
```bash
sudo apt install -y vlc
```

**Практическое правило:** Перед любой установкой или обновлением пакетов выполняйте `sudo apt update`, чтобы индексы репозиториев были актуальны.

### Рабочий процесс DNF: update, upgrade и установка

DNF использует архитектуру с явным разделением обновления метаданных и установки пакетов, аналогичную APT, но с расширенными возможностями управления транзакциями.

**`dnf check-update`** — проверяет доступные обновления, загружая метаданные репозиториев. Не изменяет систему. Используется для мониторинга и планирования.

**`dnf upgrade`** — скачивает и устанавливает обновления для всех установленных пакетов. В отличие от `apt upgrade`, DNF по умолчанию удаляет устаревшие зависимости и может обрабатывать транзакции с изменением архитектуры.

**`dnf install <name>`** — устанавливает пакет с автоматическим разрешением зависимостей через `libsolv`. Поддерживает `--setopt=install_weak_deps=False` для установки только жёстких зависимостей.

```bash
# Обновление метаданных и установка nginx (RHEL/Fedora)
sudo dnf check-update
sudo dnf install -y nginx
# → DNF вычисляет граф зависимостей, загружает пакеты и выводит план транзакции
```

Для dry-run (просмотр плана без применения):
```bash
sudo dnf upgrade --assumeno
# → показывает, какие пакеты будут обновлены, но не выполняет установку
```

Для пакетной загрузки обновлений без установки:
```bash
sudo dnf upgrade --downloadonly --downloaddir=/tmp/updates
# → пакеты загружаются в /tmp/updates для последующего ручного применения
```

С подробным справочником операций DNF, включая модульность, группы пакетов и продвинутые сценарии, см. [Команды DNF](./dnf_commands/practical_scenarios.md).

### Неинтерактивная установка (Automation)

Для предотвращения блокировки скриптов или Docker-сборок интерактивными запросами (debconf) используются следующие методы:

**Debian/Ubuntu:**
```bash
# Современный синтаксис apt
sudo apt install -y nginx

# Классический синтаксис apt-get с подавлением debconf
sudo DEBIAN_FRONTEND=noninteractive apt-get install -y nginx
```

**RHEL/Fedora:**
```bash
# Флаг -y автоматически подтверждает установку
sudo dnf install -y nginx
```

### Откат транзакций

**RPM (DNF):** нативный откат через историю транзакций:
```bash
# Просмотр истории транзакций
sudo dnf history list
# → ID     | Date and time    | Action(s)   | Altered
# →   123  | 2024-01-15 10:30 | install     |   5

# Откат конкретной транзакции
sudo dnf history undo 123
# → система возвращается в состояние до транзакции 123
```

**DEB (APT/dpkg):** ручной откат через логи и восстановление:
```bash
# Просмотр истории
less /var/log/apt/history.log
grep "install nginx" /var/log/dpkg.log

# Откат: удаление пакетов, установленных в конкретной транзакции
sudo apt remove nginx
# Если конфигурационные файлы нужно удалить:
sudo apt purge nginx
```

> **Важно:** В DEB нет атомарного отката всей транзакции. Требуется ручное удаление каждого пакета, установленного в рамках транзакции. Для автоматизации используйте `etckeeper` или контейнеризацию.

### Восстановление после прерванной транзакции

**Симптомы:**
- `dpkg` сообщает о незавершённой конфигурации пакетов.
- `apt` блокируется файлом `/var/lib/dpkg/lock-frontend`.
- `dnf` сообщает: `Another app is currently holding the yum lock; waiting for it to exit...`

**Решение (DEB):**
```bash
# 1. Завершить зависший процесс (если есть)
sudo kill -9 $(sudo lsof -t /var/lib/dpkg/lock-frontend)

# 2. Доразвернуть все незавершённые пакеты
sudo dpkg --configure -a

# 3. Проверить и исправить зависимости
sudo apt --fix-broken install

# 4. Обновить индексы и продолжить обновление
sudo apt update
sudo apt upgrade
```

**Решение (RPM):**
```bash
# DNF автоматически исправляет промежуточные состояния при следующем запуске
sudo dnf upgrade

# Если требуется принудительная проверка базы данных
sudo rpm --rebuilddb
sudo dnf clean all && sudo dnf upgrade
```

### Аудит и сравнение пакетов между серверами

Для DevOps/SRE критически важно поддерживать одинаковый состав пакетов на всех серверах инфраструктуры.

**DEB: экспорт и сравнение**
```bash
# Экспорт списка пакетов с версиями
dpkg-query -W -f='${Package}\t${Version}-${Revision}\t${Architecture}\n' | sort > /tmp/packages_deb.txt

# Сравнение двух серверов через SSH
diff --side-by-side --suppress-common-lines \
  <(ssh server1 "dpkg-query -W -f='${Package}\t${Version}\n' | sort") \
  <(ssh server2 "dpkg-query -W -f='${Package}\t${Version}\n' | sort")
```

**RPM: экспорт и сравнение**
```bash
# Экспорт списка пакетов с версиями
rpm -qa --queryformat='%{NAME}\t%{VERSION}-%{RELEASE}\t%{ARCH}\n' | sort > /tmp/packages_rpm.txt

# Сравнение двух серверов через SSH
diff --side-by-side --suppress-common-lines \
  <(ssh server1 "rpm -qa --queryformat='%{NAME} %{VERSION}-%{RELEASE}\n' | sort") \
  <(ssh server2 "rpm -qa --queryformat='%{NAME} %{VERSION}-%{RELEASE}\n' | sort")
```

### Массовое обновление инфраструктуры (Maintenance Window)

Планирование и выполнение массовых обновлений требует учёта особенностей экосистемы и минимизации простоев.

**Debian/Ubuntu:**
```bash
# Планирование: dry-run показывает влияние на зависимости
sudo apt upgrade --dry-run
# → APT выводит список пакетов для обновления/удаления/установки

# Принудительное обновление ядра (если требуется перезагрузка)
sudo apt install --only-upgrade linux-image-amd64

# Автоматическая очистка ненужных зависимостей
sudo apt autoremove -y
```

**RHEL/Fedora:**
```bash
# Исключение конкретных пакетов из массового обновления
sudo dnf upgrade --exclude=kernel*,docker*

# Обновление только security-пакетов (с использованием dnf-plugin-security)
sudo dnf update --security

# Принудительная синхронизация с репозиторием (аналог dist-upgrade)
sudo dnf distro-sync
```

> **Примечание:** Поддержка `--security` флага зависит от наличия `dnf-plugin-security` (RHEL 8+) или `dnf5` с встроенным фильтром по advisory ID.

### Управление обновлениями безопасности

Для compliance и эксплуатации критически важно иметь возможность точечного применения только security-обновлений.

**Debian/Ubuntu:**
```bash
# Просмотр доступных security-обновлений
apt list --upgradable 2>/dev/null | grep -i security

# Установка только security-пакетов (Debian 12+)
sudo apt upgrade -y --only-upgrade $(apt list --upgradable 2>/dev/null | grep -i security | cut -d/ -f1)
```

**RHEL/Fedora:**
```bash
# Список advisory, применимых к системе
sudo dnf updateinfo list

# Установка только security-обновлений
sudo dnf update --security

# Просмотр деталей конкретного advisory
sudo dnf updateinfo info CVE-2024-XXXX
```

### Очистка кэша и управление дисковым пространством

Кэши пакетных менеджеров со временем могут занимать значительный объём диска (гигабайты на серверах с частыми обновлениями).

**Debian/Ubuntu:**
```bash
# Очистка кэша загруженных .deb-архивов
sudo apt clean
# → удаляет /var/cache/apt/archives/*.deb

# Очистка устаревших индексов
sudo apt autoclean
# → удаляет только устаревшие версии пакетов из кэша

# Удаление неиспользуемых зависимостей
sudo apt autoremove -y
```

**RHEL/Fedora:**
```bash
# Полная очистка всех кэшей
sudo dnf clean all
# → очищает /var/cache/dnf/, включая метаданные и пакеты

# Очистка только устаревших кэшей
sudo dnf clean expire-cache
```

## Дополнительная информация

### Типичные проблемы и решения

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **`Hash Sum mismatch`** | Повреждённый кэш индексов или нестабильное сетевое соединение | `apt clean && apt update` (DEB) или `dnf clean all && dnf upgrade` (RPM) |
| **`dpkg: error: parsing file`** | Повреждённый файл в `/var/lib/dpkg/updates/` | Удаление временных файлов: `sudo rm /var/lib/dpkg/updates/*` |
| **`GPG error: The following signatures were invalid`** | Истёкший ключ или неправильная дата/время | `sudo apt-key update` или переустановка ключа репозитория |
| **`dnf: command not found`** | DNF не установлен (минимальный образ) | `sudo apt install dnf` (Debian) или `yum install dnf` (RHEL 7) |
| **` Held packages`** | Пакет заблокирован (`apt-mark hold` / `versionlock`) | `apt-mark unhold <pkg>` или `dnf versionlock delete <pkg>` |
| **`broken dependency`** | Частичная установка/удаление | `sudo apt --fix-broken install` или `sudo dnf distro-sync` |
| **`No space left on device`** | Переполненный кэш или корневой раздел | `apt clean` / `dnf clean all` + проверка `/var/log/` |

### Управление историей транзакций

В системах на базе RPM механизм транзакций позволяет не только просматривать изменения, но и безопасно их отменять. В системах DEB основной упор сделан на подробное логирование в `/var/log/dpkg.log` и `/var/log/apt/history.log`, что требует ручного вмешательства для отката сложной цепочки изменений.

Для тонкой настройки DNF (экспорт, модули, retention policies) см. [Команды DNF](./dnf_commands/practical_scenarios.md) и [Конфигурация DNF](./dnf_commands/basic_concepts.md).

Для зеркалирования репозиториев и air-gapped сред см. [Зеркалирование APT](./apt_mirror/practical_scenarios.md) и [Управление репозиториями DEB](./deb_repositories_sources_list.md).

Для тонкого управления приоритетом пакетов (Pinning) см. [Управление приоритетами пакетов в Apt (Pinning)](./deb_apt_pinning.md).

### Рекомендации по эксплуатации

1. **Никогда не смешивайте высокоуровневые и низкоуровневые утилиты в одной транзакции.** Используйте `apt`/`dnf` для всех операций с репозиториями. `dpkg`/`rpm` применяйте только для локальных файлов.
2. **Всегда выполняйте `apt update` или `dnf check-update` перед установкой/обновлением.** Устаревшие индексы приводят к установке неправильных версий.
3. **Используйте `--dry-run` или `--assumeno` перед массовыми обновлениями** для оценки влияния на систему.
4. **Настраивайте `installonly_limit` в RPM-системах** для защиты от заполнения раздела `/boot` при частых обновлениях ядра.
5. **Внедряйте аудит пакетов в CI/CD:** регулярно сравнивайте установленные версии с baseline.
6. **Используйте GPG-проверку (`gpgcheck=1`)** и никогда не отключайте её на production-серверах.
7. **Настраивайте ротацию логов** (`/var/log/apt/`, `/var/log/dnf/`) для предотвращения заполнения диска.
