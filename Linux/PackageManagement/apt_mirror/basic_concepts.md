## Основные концепции

### Назначение локального зеркала

Локальное зеркало репозитория является критическим элементом инфраструктуры в следующих случаях:

| Преимущество | Описание |
| :--- | :--- |
| **Экономия WAN-трафика** | Пакеты скачиваются из внешних сетей однократно, затем распространяются по LAN. Актуально для крупных парков серверов. |
| **Скорость доставки** | Установка и обновление пакетов происходят на скорости локальной сети (1–10+ Гбит/с). |
| **Air-Gapped среды** | Единственный способ доставки ПО в изолированные контуры, не имеющие физического доступа к интернету. |
| **Воспроизводимость (Snapshot)** | Фиксация состояния репозитория позволяет гарантировать, что все серверы установят одинаковую версию пакета, независимо от обновлений в upstream. |
| **Безопасность и комплаенс** | Возможность аудита и предварительного тестирования пакетов перед их допуском во внутренний контур. |

### Цепочка доверия (Chain of Trust)

Безопасность APT-репозиториев базируется на каскадной проверке цифровых подписей:

1.  **Upstream Signature**: Издатель (Debian/Ubuntu) подписывает файл `Release` своим закрытым ключом.
2.  **Integrity**: Файл `Release` содержит хэш-суммы всех файлов индексов (`Packages`).
3.  **Mirror Validation**: Локальное зеркало при синхронизации проверяет подпись upstream. Если зеркало изменено (подменено), проверка на клиенте провалится.
4.  **Client Trust**: На клиентских машинах должен быть установлен публичный GPG-ключ издателя. При выполнении `apt update` клиент проверяет подпись файла `InRelease` и соответствие хэш-сумм всех скачиваемых пакетов.

> **Важно**: Локальное зеркало по умолчанию не переподписывает пакеты — оно транслирует подпись издателя. Для переподписи используются механизмы приватных репозиториев (например, через `aptly publish -gpg-key=...`).

### Архитектура и топология

Зеркалирование может быть организовано по различным схемам в зависимости от масштаба сети.

#### Типовая схема
```
┌─────────────────┐       ┌──────────────────┐       ┌─────────────────┐
│   Интернет      │       │  Сервер-зеркало  │       │  Клиентские     │
│   Репозитории   │──────▶│ (aptly / mirror) │──────▶│  машины         │
│   (upstream)    │       │                  │       │  (Desktop/Srv)  │
└─────────────────┘       └──────────────────┘       └─────────────────┘
         │                         │                          ▲
         │                         ▼                          │
         │                ┌──────────────────┐        ┌───────┴──────┐
         │                │    Хранилище     │        │  Веб-сервер  │
         └───────────────▶│ (Disk / S3 / NFS)│───────▶│ (Nginx/Apache)│
                          └──────────────────┘        └──────────────┘
```

#### Каскадное зеркалирование (Multi-tier)
В распределенных сетях используется схема **Master-Slave**:
- **Master Mirror**: Единственная точка выхода в интернет, синхронизируется с upstream.
- **Regional Mirrors**: Синхронизируются с Master-зеркалом по локальным или выделенным каналам, обслуживая региональные сегменты сети.

### Механизмы синхронизации

Современные инструменты зеркалирования поддерживают различные стратегии загрузки данных:

1.  **Полное зеркало (Full Mirror)**: Копирование всех релизов, архитектур и компонентов. Требует значительного дискового пространства (терабайты для Debian).
2.  **Частичное зеркало (Selective Mirror)**:
    *   **По архитектуре**: Например, только `amd64` (исключая `arm64`, `i386`, `source`).
    *   **По компонентам**: Только `main` и `security`, исключая `universe` или `multiverse`.
    *   **По пакетам**: Фильтрация с помощью регулярных выражений (только необходимые утилиты).
3.  **Инкрементальное обновление**: Загрузка только новых `.deb` файлов и обновленных индексов. APT использует пулы (`pool/`), что предотвращает повторную загрузку одинаковых файлов для разных релизов.

### Жизненный цикл зеркала

1.  **Конфигурация**: Определение списка upstream-источников, фильтров архитектур и путей хранения.
2.  **Синхронизация (Update)**: Процесс загрузки метаданных и бинарных файлов.
3.  **Снимок (Snapshot)**: Фиксация состояния зеркала. Позволяет избежать ситуации, когда часть серверов обновилась, а часть нет из-за изменений в репозитории во время деплоя.
4.  **Публикация (Publish)**: Создание структуры каталогов, доступной веб-серверу.
5.  **Потребление**: Настройка клиентов через `/etc/apt/sources.list` или формат DEB822.

## Сравнение инструментов и подходов

### Выбор инструмента

| Инструмент | Уровень | Рекомендуемый сценарий |
| :--- | :--- | :--- |
| **aptly** | High | Профессиональное управление: снимки, API, объединение репозиториев, S3. |
| **apt-mirror** | Basic | Простая синхронизация «один-в-один» для небольших сетей. |
| **debmirror** | Medium | Сложная фильтрация пакетов по зависимостям и секциям. |

### Зеркалирование vs Приватный репозиторий

| Критерий | Зеркалирование | Приватный репозиторий |
| :--- | :--- | :--- |
| **Источник данных** | Официальные зеркала | Собственное ПО компании |
| **GPG-подпись** | Подпись издателя (Ubuntu/Debian) | Собственная GPG-подпись |
| **Управление** | Автоматическая синхронизация | Ручное или CI/CD добавление пакетов |
| **Цель** | Доступность и скорость | Распространение внутреннего ПО |
