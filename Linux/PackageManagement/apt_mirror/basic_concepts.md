## Основные концепции

### Назначение локального зеркала

Локальное зеркало репозитория является критическим элементом инфраструктуры в следующих случаях:

| Преимущество | Описание |
| :--- | :--- |
| **Экономия WAN-трафика** | Пакеты скачиваются из внешних сетей однократно, затем распространяются по LAN. Актуально для крупных парков серверов. |
| **Скорость доставки** | Установка и обновление пакетов происходят на скорости локальной сети (1–10+ Гбит/с). |
| **Air-Gapped среды** | Единственный способ доставки ПО в изолированные контуры, не имеющие физического доступа к интернету. |
| **Воспроизводимость (Snapshot)** | Фиксация состояния репозитория позволяет гарантировать, что все серверы установят одинаковую версию пакета, независимо от обновлений в upstream. |
| **Безопасность и комплаенс** | Возможность аудита и предварительного тестирования пакетов перед их допуском во внутренний контур. |

### Цепочка доверия (Chain of Trust)

Безопасность APT-репозиториев базируется на каскадной проверке цифровых подписей:

1.  **Upstream Signature**: Издатель (Debian/Ubuntu) подписывает файл `Release` своим закрытым ключом.
2.  **Integrity**: Файл `Release` содержит хэш-суммы всех файлов индексов (`Packages`).
3.  **Mirror Validation**: Локальное зеркало при синхронизации проверяет подпись upstream. Если зеркало изменено (подменено), проверка на клиенте провалится.
4.  **Client Trust**: На клиентских машинах должен быть установлен публичный GPG-ключ издателя. При выполнении `apt update` клиент проверяет подпись файла `InRelease` и соответствие хэш-сумм всех скачиваемых пакетов.

> **Важно**: Локальное зеркало по умолчанию не переподписывает пакеты — оно транслирует подпись издателя. Для переподписи используются механизмы приватных репозиториев (например, через `aptly publish -gpg-key=...`).

### Верификация целостности на стороне сервера

Помимо GPG-проверки при синхронизации, администратор должен регулярно контролировать, что локальное зеркало полностью соответствует upstream.

**Контрольные точки:**
- **Количество пакетов**: Сравнение числа `.deb`-файлов в `pool/` с upstream через `aptly repo show` или подсчёт строк в индексном файле:
  ```bash
  grep -c '^Package:' /var/www/html/ubuntu/dists/noble/main/binary-amd64/Packages
  ```
- **Свежесть индексов**: Проверка модификации файла `Release` или `InRelease`:
  ```bash
  stat -c %y /var/www/html/ubuntu/dists/noble/InRelease
  ```
- **Сетевая целостность**: После синхронизации выполните быструю проверку на тестовом клиенте, предварительно переключив `sources.list` на локальное зеркало.

> **Важно**: Для производственных сред рекомендуется автоматизировать эти проверки и интегрировать их в пайплайн мониторинга (см. раздел «Мониторинг и оповещения»).

### Форматы индексов и компрессия

APT использует иерархию индексных файлов для минимизации трафика при обновлении:

| Файл | Назначение | Компрессия |
| :--- | :--- | :--- |
| `dists/<codename>/InRelease` | Объединённый файл с подписью и датой релиза. | Без сжатия (OpenPGP) |
| `dists/<codename>/Release` | Метаданные релиза: дата, хэши, компоненты. | Без сжатия |
| `dists/<codename>/Release.gpg` | Отдельная подпись файла `Release` (legacy). | Без сжатия |
| `dists/<codename>/main/binary-amd64/Packages` | Список пакетов для архитектуры `amd64` в компоненте `main`. | `.gz` или `.xz` |
| `dists/<codename>/main/binary-amd64/Packages.xz` | Сжатый индекс пакетов (современный стандарт). | xz |
| `pool/main/.../*.deb` | Сами бинарные пакеты. | Без сжатия (архив внутри) |

**PDiffs (Patch Diffs)**: Дельта-файлы, содержащие только изменения между версиями индексов `Packages`. Позволяют скачивать не весь индекс, а только разницу. Включаются по умолчанию в современном APT; отключаются через `Acquire::PDiffs "false"` при проблемах.

**By-Hash**: Механизм, при котором индексные файлы запрашиваются по хэш-сумме их содержимого, а не по имени. Исключает race condition при обновлении индексов на upstream во время скачивания клиентом. Требует поддержки на стороне mirror (`aptly` поддерживает, `apt-mirror` — частично).

### Архитектура и топология

Зеркалирование может быть организовано по различным схемам в зависимости от масштаба сети.

#### Типовая схема
```
┌─────────────────┐       ┌──────────────────┐       ┌─────────────────┐
│   Интернет      │       │  Сервер-зеркало  │       │  Клиентские     │
│   Репозитории   │──────▶│ (aptly / mirror) │──────▶│  машины         │
│   (upstream)    │       │                  │       │  (Desktop/Srv)  │
└─────────────────┘       └──────────────────┘       └─────────────────┘
          │                         │                          ▲
          │                         ▼                          │
          │                ┌──────────────────┐        ┌───────┴──────┐
          │                │    Хранилище     │        │  Веб-сервер  │
          └───────────────▶│ (Disk / NFS)     │───────▶│ (Nginx/Apache)│
                           └──────────────────┘        └──────────────┘
```

#### Каскадное зеркалирование (Multi-tier)
В распределённых сетях используется схема **Master-Slave**:
- **Master Mirror**: Единственная точка выхода в интернет, синхронизируется с upstream.
- **Regional Mirrors**: Синхронизируются с Master-зеркалом по локальным или выделенным каналам, обслуживая региональные сегменты сети.

#### Балансировка и отказоустойчивость
Для крупных инфраструктур (100+ серверов) рекомендуется разворачивать несколько независимых зеркал и распределять нагрузку:

- **DNS Round-Robin**: Один домен (`mirror.internal`) указывает на IP-адреса нескольких серверов. Простота реализации, но отсутствие health check на уровне DNS.
- **L7-балансировщик (Nginx/HAProxy)**: Позволяет реализовать health check, приоритизацию и отключение неработающих узлов. Пример конфигурации Nginx:
  ```nginx
  upstream apt_backend {
      server mirror-01.internal max_fails=3 fail_timeout=30s;
      server mirror-02.internal max_fails=3 fail_timeout=30s;
  }
  server {
      listen 80;
      server_name apt.internal;
      location /ubuntu {
          proxy_pass http://apt_backend/ubuntu;
          proxy_set_header Host $host;
      }
  }
  ```
- **Anycast**: Несколько серверов advertise один и тот же IP-адрес через BGP. Маршрутизатор направляет трафик на ближайший узел. Сложность в настройке пиринга, но максимальная отказоустойчивость.

### Механизмы синхронизации

Современные инструменты зеркалирования поддерживают различные стратегии загрузки данных:

1.  **Полное зеркало (Full Mirror)**: Копирование всех релизов, архитектур и компонентов. Требует значительного дискового пространства (терабайты для Debian).
2.  **Частичное зеркало (Selective Mirror)**:
    *   **По архитектуре**: Например, только `amd64` (исключая `arm64`, `i386`, `source`).
    *   **По компонентам**: Только `main` и `security`, исключая `universe` или `multiverse`.
    *   **По пакетам**: Фильтрация с помощью регулярных выражений (только необходимые утилиты).
3.  **Инкрементальное обновление**: Загрузка только новых `.deb` файлов и обновленных индексов. APT использует пулы (`pool/`), что предотвращает повторную загрузку одинаковых файлов для разных релизов.

### Взаимодействие клиента с зеркалом

При выполнении `apt update` и `apt install` клиент взаимодействует с зеркалом через HTTP(S). APT поддерживает несколько механизмов оптимизации и отказоустойчивости.

**Конфигурация прокси и прямого доступа:**
```bash
# /etc/apt/apt.conf.d/99-mirror
Acquire::http::Proxy "http://proxy.internal:3128";
Acquire::https::Proxy "http://proxy.internal:3128";

# Исключение для локального зеркала (прямой доступ)
Acquire::http::Proxy::mirror.internal "DIRECT";
```
Подробнее о настройке прокси: **[Управление репозиториями DEB](../deb_repositories_sources_list.md)**.

**Fallback и приоритет источников:**
- Если зеркало недоступно, `apt update` завершается ошибкой. Для отказоустойчивости можно указать несколько источников в `sources.list` (основной + запасной).
- `apt` автоматически выбирает fastest mirror на основе среднего времени ответа при включённых `Acquire::http::Pipeline-Depth` и `Acquire::http::No-Cache`.

**Retry и timeout:**
```bash
# /etc/apt/apt.conf.d/99-retries
Acquire::Retries "5";
Acquire::http::Timeout "30";
Acquire::https::Timeout "30";
```

### Жизненный цикл зеркала

1.  **Конфигурация**: Определение списка upstream-источников, фильтров архитектур и путей хранения.
2.  **Синхронизация (Update)**: Процесс загрузки метаданных и бинарных файлов.
3.  **Снимок (Snapshot)**: Фиксация состояния зеркала. Позволяет избежать ситуации, когда часть серверов обновилась, а часть нет из-за изменений в репозитории во время деплоя.
4.  **Публикация (Publish)**: Создание структуры каталогов, доступной веб-серверу.
5.  **Потребление**: Настройка клиентов через `/etc/apt/sources.list` или формат DEB822.

### Хранение данных и файловые системы

Структура пулов пакетов (`pool/`) и особенности хранения влияют на производительность и надёжность зеркала:

- **Hard Links**: В `pool/` один и тот же `.deb`-файл может быть связан жёсткой ссылкой с нескольких каталогов (например, `pool/main/a/apt/apt_2.6.0_amd64.deb` используется в `focal`, `jammy` и т.д.). Это экономит место, но увеличивает нагрузку на inode.
- **Выбор файловой системы**:
  - **XFS**: Рекомендуется для production. Лучшая масштабируемость при большом количестве файлов, эффективное выделение inodes.
  - **Ext4**: Подходит для средних зеркал. Важно монтировать с `-T largefile4` для оптимального выделения inodes.
  - **Btrfs/ZFS**: Обеспечивают снапшоты на уровне ФС, checksums и сжатие. Избыточны для простого зеркала, но полезны для комбинированных сценариев (зеркало + бэкапы).
- **Мониторинг inodes**: При заполнении inodes синхронизация падает с ошибкой «No space left on device» при наличии свободного места. Проверка:
  ```bash
  df -i /var/spool/aptly
  ```

### Безопасность сервера-зеркала

Сервер-зеркало должен эксплуатироваться по принципу минимальных привилегий:

- **Сетевая изоляция**: Размещайте зеркало в отдельном сегменте сети (VLAN). Разрешите только исходящий HTTPS (443) для upstream и входящий HTTP/HTTPS (80/443) для клиентов. Закройте все остальные порты фаерволлом (`ufw`, `iptables`, `nftables`).
- **HTTPS**: Для корпоративных сред рекомендуется использовать TLS-сертификаты (внутренний CA или Let's Encrypt). Это предотвращает перехват и инъекцию пакетов при передаче по LAN.
- **mTLS**: Для критичных контуров используйте взаимную TLS-аутентификацию (см. [Nginx: Настройка репозитория](../../../WebServers/Nginx/Scenarios/secure_apt_repository_guide.md)).
- **Ограничение доступа**: Веб-сервер (Nginx/Apache) должен иметь доступ только к директории с зеркалом. Запретите выполнение CGI/PHP в корне зеркала.
- **Аудит**: Включите логирование доступа к репозиторию. Для Nginx:
  ```nginx
  access_log /var/log/nginx/apt.access.log combined;
  ```

### Мониторинг и оповещения

Для SRE-подхода к эксплуатации зеркала критичны SLA-метрики:

| Метрика | Порог оповещения | Источник данных |
| :--- | :--- | :--- |
| **Возраст данных (Data Age)** | > 24 ч для `-security`, > 7 дней для `-updates` | Модификация `Release` файла |
| **Доступность** | HTTP 5xx > 1% за 5 минут | Nginx/Apache access logs или Blackbox Exporter |
| **Синхронизация** | Последний успешный `aptly mirror update` > 48 ч | systemd service status / journalctl |
| **Дисковое пространство** | > 85% использования | node_exporter / `df` |
| **Inodes** | > 80% использования | node_exporter / `df -i` |

**Пример интеграции с Prometheus (Textfile Collector):**
```bash
#!/bin/bash
# /usr/local/bin/apt-mirror-metrics.sh
RELEASE_FILE="/var/www/html/ubuntu/dists/noble/Release"
AGE=$(( $(date +%s) - $(stat -c %Y "$RELEASE_FILE") ))
SIZE=$(du -sb /var/spool/aptly | cut -f1)

echo "apt_mirror_last_update_seconds $AGE" > /var/lib/node_exporter/apt_mirror.prom
echo "apt_mirror_size_bytes $SIZE" >> /var/lib/node_exporter/apt_mirror.prom
```

Таймер systemd для периодического запуска:
```ini
# /etc/systemd/system/aptly-metrics.timer
[Unit]
Description=Collect apt mirror metrics

[Timer]
OnCalendar=*:05
Persistent=true

[Install]
WantedBy=timers.target
```

### Резервное копирование и аварийное восстановление

Зеркало является критичным инфраструктурным компонентом; его потеря блокирует обновления всех серверов.

**Стратегии бэкапа:**
- **Реплика на уровне хранилища**: RAID1/RAID6 или ZFS mirror для защиты от сбоя диска.
- **Логическое бэкап**: Регулярное создание archive директории `~/.aptly` (для aptly) или `/var/spool/apt-mirror` через `rsync` или `tar` на внешний диск/NFS.
- **Снэпшот перед обновлением**: Перед `aptly mirror update` создавайте snapshot текущего состояния. При сбое обновления можно мгновенно откатиться:
  ```bash
  aptly snapshot create pre-update-$(date +%F) from mirror noble-main
  ```

**Восстановление:**
1. Разверните чистую ОС на новом сервере.
2. Установите `aptly` и восстановите каталог из бэкапа.
3. Запустите `aptly db recover` (если база была повреждена).
4. Перепубликуйте snapshot и обновите DNS/конфигурацию балансировщика.

## Сравнение инструментов и подходов

### Выбор инструмента

| Инструмент | Уровень | Рекомендуемый сценарий |
| :--- | :--- | :--- |
| **aptly** | High | Профессиональное управление: снимки, API, объединение репозиториев, S3. |
| **apt-mirror** | Basic | Простая синхронизация «один-в-один» для небольших сетей. |
| **debmirror** | Medium | Сложная фильтрация пакетов по зависимостям и секциям. |
| **apt-cacher-ng** | Cache | Кэширующий прокси для средних сетей, где полное зеркало избыточно. |

### Критерии выбора стратегии

| Критерий | Полное зеркало (aptly/apt-mirror) | Кэширующий прокси (apt-cacher-ng) |
| :--- | :--- | :--- |
| **Размер сети** | > 50 серверов или air-gapped | < 50 серверов, есть выход в интернет |
| **Дисковое пространство** | Десятки-сотни ГБ | Несколько ГБ (кэш популярных пакетов) |
| **Воспроизводимость** | Snapshot гарантирует deterministic deploys | Зависит от upstream; нет гарантий |
| **Air-gapped** | Обязательно | Неприменимо |
| **Администрирование** | Требует планирования и обслуживания | Практически zero-config |

### Зеркалирование vs Приватный репозиторий

| Критерий | Зеркалирование | Приватный репозиторий |
| :--- | :--- | :--- |
| **Источник данных** | Официальные зеркала | Собственное ПО компании |
| **GPG-подпись** | Подпись издателя (Ubuntu/Debian) | Собственная GPG-подпись |
| **Управление** | Автоматическая синхронизация | Ручное или CI/CD добавление пакетов |
| **Цель** | Доступность и скорость | Распространение внутреннего ПО |

## Практические сценарии

Краткий обзор сценариев, подробно описанных в **[Практических сценариях](./practical_scenarios.md)**:

- **Создание зеркала Ubuntu**: Базовая настройка `aptly` и публикация через Nginx.
- **Обновление в air-gap**: Перенос данных через внешние носители (Sneakernet).
- **A/B тестирование обновлений**: Использование снимков для тестирования новых патчей на группе Stage перед Prod.

**Операционные паттерны (DevOps/SRE):**
- **Canary-обновление**: Публикация snapshot на подмножестве клиентов для проверки стабильности перед массовым rollout.
- **Immutable Mirror**: Жёсткое правило — зеркало только для чтения. Любые изменения проходят через CI/CD pipeline с тестированием и approval workflow. Подход минимизирует риск компрометации репозитория.
- **Automated Promotion**: Синхронизация → Snapshot → automated tests (проверка подписей, сканирование уязвимостей) → Publish. Реализуется через GitOps: изменения конфигурации зеркала коммитятся в Git, а systemd/Ansible применяет их.
