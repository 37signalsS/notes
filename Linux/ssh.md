# SSH (Secure Shell)

SSH — это сетевой протокол для безопасного удалённого управления системой. Вся информация, включая пароли, передаётся в зашифрованном виде. SSH работает на **прикладном (седьмом) уровне** модели OSI, используя TCP на транспортном уровне для надёжной доставки данных.

Процесс подключения состоит из нескольких ключевых этапов.

1.  **Установка TCP-соединения:** Клиент инициирует TCP-соединение с сервером на указанный порт (по умолчанию 22).
2.  **Обмен версиями протокола:** Клиент и сервер сообщают друг другу поддерживаемые версии протокола SSH и выбирают общую.
3.  **Согласование алгоритмов:** Стороны договариваются об алгоритмах для:
        - Шифрования (AES-256-GCM, ChaCha20)
        - MAC(проверки целостности) (HMAC-SHA2)
        - Сжатия
        - Ключевого обмена (Diffie-Hellman, ECDH, Curve25519)
        - Хост-ключей (RSA, ED25519 и др.)
4.  **Обмен ключами сессии:** С помощью согласованного алгоритма (например, Diffie-Hellman) генерируется общий секретный ключ сессии. Этот ключ шифрует весь дальнейший трафик. На этом же этапе сервер доказывает свою подлинность клиенту, чтобы избежать атак "man-in-the-middle". Клиент проверяет ключ хоста (сервера) по своему файлу `~/.ssh/known_hosts`.
5.  **Аутентификация пользователя:** После установки зашифрованного канала клиент должен подтвердить своё право на доступ.

#### Аутентификация по паролю

1.  Клиент запрашивает у пользователя пароль.
2.  Пароль отправляется на сервер **по уже зашифрованному каналу**.
3.  Сервер проверяет пароль и предоставляет доступ в случае успеха.
> **Примечание:** Этот метод менее безопасен и подвержен атакам перебора (brute-force). Рекомендуется отключать его на сервере.

#### Аутентификация по SSH-ключу

1.  Клиент отправляет на сервер ID своего **публичного ключа**, которым он хочет аутентифицироваться.
2.  Сервер ищет этот ключ в файле `~/.ssh/authorized_keys` того пользователя, под которым происходит вход.
3.  Если ключ найден, сервер создает случайное сообщение (challenge), шифрует его этим **публичным ключом** и отправляет клиенту.
4.  Только владелец соответствующего **приватного ключа** может расшифровать это сообщение. Клиент расшифровывает его.
5.  Клиент вычисляет хеш из расшифрованного сообщения и ключа сессии, отправляя его обратно на сервер.
6.  Сервер выполняет те же вычисления и сравнивает результаты. Если они совпадают, это доказывает, что клиент владеет приватным ключом, и доступ предоставляется. **Приватный ключ при этом никогда не покидает клиентскую машину.**

### Генерация SSH-ключей

Для аутентификации по ключу необходимо сгенерировать пару: публичный (`.pub`) и приватный.

```bash
# Рекомендуется использовать современный и безопасный алгоритм Ed25519
ssh-keygen -t ed25519 -C "your_email@example.com"
```
- `-t ed25519`: Указывает тип ключа.
- `-C "комментарий"`: Помогает идентифицировать ключ.

### Управление ключами с помощью ssh-agent

`ssh-agent` — это фоновый процесс, который хранит приватные ключи в памяти и избавляет от необходимости вводить пароль от ключа при каждом подключении.

```bash
# Запуск агента в текущей сессии
eval "$(ssh-agent -s)"

# Добавление ключа в агент
ssh-add ~/.ssh/id_ed25519
```

### Настройка ssh клиента (`~/.ssh/config`)

```ini
# Алиас для рабочего сервера
Host work
  HostName spb-mx-i3.extrt.int.company.net
  User ivanov_i
  Port 2222
  IdentityFile ~/.ssh/id_work
  Compression yes

# Алиас для домашнего сервера с нестандартным ключом
Host home
  HostName myhome.dyndns.org
  User vasya
  PasswordAuthentication no
  IdentityFile ~/.ssh/id_rsa_home

# Настройки по умолчанию для всех хостов
Host *
  User root
  ForwardX11 yes
  ServerAliveInterval 60
  # Отключает все интерактивные запросы (пароли, подтверждение хостов), используеться только в связке с ssh-ключами.
  # Крайне полезно для скриптов и автоматизации.
  # При необходимости аутентификации, которая требует интерактива(ввод пароля), соединение просто завершится с ошибкой, а не "зависнет".
  BatchMode yes
```

### Копирование публичного ключа на сервер

Содержимое вашего **публичного** ключа (например, `~/.ssh/id_ed25519.pub`) необходимо добавить в файл `~/.ssh/authorized_keys` на сервере в домашней директории нужного пользователя.

**Автоматический способ (рекомендуется):**
```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server
```

**Ручной способ:**
```bash
# На сервере
mkdir -p ~/.ssh
# Вставьте сюда содержимое вашего .pub файла
nano ~/.ssh/authorized_keys
```

### Настройка прав доступа

Крайне важно установить правильные права доступа, иначе SSH-сервер может отказать в подключении из соображений безопасности.

```bash
# На сервере
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

## Безопасность SSH

### Рекомендации по настройке `/etc/ssh/sshd_config`

- `Port 22`: Измените стандартный порт на другой (значение должно быть больше 1024, например, `Port 15134`), чтобы уменьшить количество автоматических атак от ботов.
- `PermitRootLogin no`: Запретите вход от имени `root`. 
  - `prohibit-password`: Эта опция запрещает вход по паролю под пользователем `root`, но разрешает ему вход по ssh-ключу, если он добавлен в `~/.ssh/authorized_keys`.
  - `no`: Эта опция полностью запрещает вход под пользователем `root` как по паролю, так и по ssh-ключу.
- `PermitEmptyPasswords no`: Запрещает вход пользователям с пустыми паролями. Значение по умолчанию (`no`) является безопасным.
- `PasswordAuthentication no`: **(Критически важно)** Отключите аутентификацию по паролю, оставив только более надежный вход по ключам.
- `PubkeyAuthentication yes`: Убедитесь, что аутентификация по ключам включена.
- `MaxAuthTries 3`: Ограничивает количество попыток аутентификации по паролю до 3, для предотвращения брутфорс-атак. **Нужно только при использовании пароля**

После внесения изменений перезапустите SSH-сервис:
```bash
sudo systemctl restart sshd
```

#### Ограничение доступа пользователей

Для более тонкого контроля доступа к SSH-серверу можно использовать директивы `AllowUsers`, `AllowGroups`, `DenyUsers`, `DenyGroups`. Рекомендуется использовать подход "белых списков" (whitelist), явно разрешая доступ только определённым пользователям или группам.

-   `AllowUsers user1 user2@host`: Разрешает вход только указанным пользователям. Можно указать пользователя и хост, с которого разрешен вход.
-   `AllowGroups group1 group2`: Разрешает вход только пользователям, входящим в указанные группы.
-   `DenyUsers user3`: Запрещает вход указанным пользователям.
-   `DenyGroups group3`: Запрещает вход пользователям, входящим в указанные группы.

```ini
# Разрешить вход только пользователям 'admin' и 'devuser'
AllowUsers admin devuser
# Запретить всем остальным
DenyUsers *
```
Или, если нужно разрешить только членам группы `sshusers`:
```ini
AllowGroups sshusers
```
**Важно:** Директивы `Allow` имеют приоритет над `Deny`. Если пользователь указан в `AllowUsers` и `DenyUsers`, ему будет разрешен вход. Рекомендуется использовать только `AllowUsers` или `AllowGroups` для создания "белого списка" и не использовать `Deny` одновременно, чтобы избежать путаницы.


### Защита от брутфорс-атак с помощью Fail2Ban

**Fail2Ban** — это утилита, которая анализирует логи служб (включая SSH) и автоматически блокирует IP-адреса, с которых ведутся атаки перебором (брутфорс).

1.  **Мониторинг логов**: Fail2Ban следит за `/var/log/auth.log` на предмет неудачных попыток входа.
2.  **Обнаружение аномалий**: Если с одного IP-адреса фиксируется несколько неудачных попыток за короткое время, Fail2Ban считает это атакой.
3.  **Блокировка**: Утилита добавляет правило в файрвол (iptables, ufw), блокируя IP-адрес атакующего на заданное время. Подробнее о принципах работы `iptables` можно прочитать в [соответствующем документе](../Security/iptables.md).

1.  **Установка:**
    ```bash
    sudo apt update
    sudo apt install fail2ban
    ```

2.  **Создание локальной конфигурации:**
    Никогда не редактируйте `jail.conf`. Все изменения вносите в его локальную копию `jail.local`, чтобы они не были перезаписаны при обновлении пакета.
    ```bash
    sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
    ```

3.  **Настройка `jail.local`:**
    Откройте файл `sudo nano /etc/fail2ban/jail.local`. Внутри уже есть секция `[sshd]`, которую можно активировать и настроить.
    ```ini
    [sshd]
    enabled = true
    # Количество неудачных попыток до бана
    maxretry = 5
    # Время блокировки (10m - 10 минут, 1h - 1 час, 1d - 1 день)
    bantime = 1h
    # Временное окно, в течение которого считаются попытки
    findtime = 10m
    ```

    Стандартное действие бана (`banaction`) создает отдельное правило `iptables` для каждого заблокированного IP. При большом количестве банов (например, во время DDoS-атаки) это может сильно нагрузить CPU. Для решения этой проблемы рекомендуется использовать `ipset`.

    Для этого в `jail.local` нужно глобально или для конкретной службы изменить `banaction`:
    ```ini
    # Глобально для всех служб
    [DEFAULT]
    banaction = iptables-ipset-proto6

    # Или только для sshd
    [sshd]
    enabled   = true
    banaction = iptables-ipset-proto6
    ```
    Это заставит Fail2Ban добавлять IP в один общий набор `ipset`, а в `iptables` будет всего одно правило для проверки этого набора, что гораздо эффективнее.

4.  **Перезапуск службы:**
    ```bash
    sudo systemctl restart fail2ban
    ```

5.  **Проверка статуса:**
    Эта команда покажет статус защиты SSH и список заблокированных IP-адресов.
    ```bash
    sudo fail2ban-client status sshd
    ```

### Endlessh: SSH-ловушка

**Endlessh** — это простая утилита, которая работает как "ловушка" (tarpit) для SSH-клиентов. Она захватывает SSH-соединения, бесконечно отправляя им баннер SSH, но никогда не завершая хендшейк. Это эффективно "замораживает" автоматизированных ботов и сканеры, которые пытаются подобрать пароли или найти уязвимости.

- **Ссылка:** [skeeto/endlessh on GitHub](https://github.com/skeeto/endlessh)

### Удалённое выполнение команд при помощи ssh

```bash
# Простое выполнение
ssh user@server "ls -l /var/www"

# С запросом псевдо-терминала (для интерактивных команд типа top)
ssh -t user@server "top"
```

### Копирование файлов и монтирование ФС

- **`scp` (Secure Copy):** Простая утилита для копирования файлов.
  ```bash
  # Копирование на сервер
  scp path/to/local/file user@server:/path/to/remote/
  # Копирование с сервера
  scp user@server:/path/to/remote/file /path/to/local/
  ```

- **`rsync` (Remote Sync):** Более мощная утилита для синхронизации файлов и директорий. Эффективнее `scp` при повторной синхронизации, так как передает только изменения.
  ```bash
  # Синхронизация локальной папки с удаленной
  rsync -avz --progress /local/dir/ user@server:/remote/dir/
  ```

- **`sshfs` (SSH File System):** Монтирует удаленную файловую систему локально, позволяя работать с удаленными файлами как с локальными.
  ```bash
  # Установка (для Debian/Ubuntu)
  sudo apt-get install sshfs
  # Монтирование
  mkdir -p /media/remote_server
  sshfs user@server:/remote/path /media/remote_server -o reconnect
  # Отмонтирование
  fusermount -u /media/remote_server
  ```

### SSH-туннелирование (проброс портов)

- **Локальный проброс (`-L`):** Доступ к удаленному ресурсу через локальный порт.
  ```bash
  # ssh -L <локальный_порт>:<целевой_хост>:<целевой_порт> user@ssh_server
  # Пример: доступ к удаленной БД (PostgreSQL) через localhost
  ssh -L 5432:db.internal.host:5432 user@gateway
  ```
  Теперь можно подключаться к `localhost:5432`, и трафик будет безопасно перенаправлен на `db.internal.host`.

- **Удаленный проброс (`-R`):** Доступ к локальному ресурсу через порт на удаленном сервере.
  ```bash
  # ssh -R <удалённый_порт>:<локальный_хост>:<локальный_порт> user@ssh_server
  # Пример: показать локальный веб-сервер (порт 3000) внешнему миру
  ssh -R 8080:localhost:3000 user@public_server
  ```
  Теперь запросы на `public_server:8080` будут перенаправляться на ваш `localhost:3000`.

- **Динамический проброс (`-D`):** Создание SOCKS-прокси.
  ```bash
  ssh -D 8080 -C user@server
  ```
  Настроив браузер на использование SOCKS5-прокси `localhost:8080`, весь его трафик пойдет через `server`.

### Проброс графического интерфейса (X11 Forwarding)

Позволяет запускать графические (GUI) приложения с удаленного сервера на локальной машине.
```bash
# Подключение с пробросом X11
ssh -XYC user@server
# После подключения можно запустить, например, gedit
gedit .bashrc
```

### Проброс аутентификации (Agent Forwarding)

Позволяет использовать ваш локальный `ssh-agent` для аутентификации на следующем сервере в цепочке (`server2`), не оставляя приватный ключ на промежуточном хосте (`server1`).

- **Прямое подключение (`-A`):**
  ```bash
  # Подключаемся к первому серверу с пробросом агента
  ssh -A user@server1
  # С него подключаемся ко второму, аутентификация пройдет через ваш локальный агент
  ssh user@server2
  ```

- **Безопасный проброс через Jump Host (`ProxyCommand`):**
  Этот метод более безопасен, так как промежуточный хост (`jump-server`) просто перенаправляет трафик, не имея доступа к агенту.
  
  **Настройка в `~/.ssh/config`:**
  ```ini
  Host final-server
    HostName 10.1.1.2
    User final_user
    ProxyCommand ssh -W %h:%p jump_user@jump-server.com
  ```
  **Подключение:**
  ```bash
  # Команда прозрачно пройдет через jump-server
  ssh final-server
  ```

### Подключение через Jump Host (Bastion Host)

Узел-бастион — это специально выделенный и защищенный сервер, который служит единственной точкой входа во внутреннюю сеть извне. Подключение к внутренним ресурсам происходит "сквозь" него.

**Общий вид команды:**

```bash
ssh -J user@jump-host.com user@target-server.internal
```

**Этапы соединения:**

1.  **Подключение к Jump Host:** Ваш SSH-клиент устанавливает стандартное зашифрованное SSH-соединение с `jump-host.com`.
2.  **Создание TCP-туннеля:** После успешной аутентификации на jump-хосте, SSH-клиент просит его создать прозрачный TCP-туннель до `target-server.internal` на порт 22. Для этого используется флаг `-W` (`ssh -W target.internal:22`).
3.  **Второе SSH-соединение внутри туннеля:** Поверх этого туннеля ваш клиент инициирует второе, полностью независимое SSH-рукопожатие уже с целевым сервером `target-server.internal`.
4.  **Результат:** Вы получаете интерактивную сессию на целевом сервере. При этом jump-хост выступает только в роли транспортного посредника и не имеет доступа к содержимому вашего трафика до конечного сервера.

## Поиск и устранение неисправностей SSH

#### Проблемы на стороне клиента (ваша машина)
*   **Неправильное имя хоста или IP-адрес:** Убедитесь, что вы используете правильный адрес.
*   **Ошибка разрешения имени (DNS):** Попробуйте подключиться по IP-адресу. Если по IP работает, а по имени нет — проблема в DNS.
    *   Команда: `nslookup <hostname>`
*   **Локальный файрвол:** Ваш собственный файрвол может блокировать исходящие соединения.
*   **Неправильный порт:** Если SSH на сервере работает на нестандартном порту, его нужно указать.
    *   Команда: `ssh user@host -p <port_number>`

#### Проблемы на уровне сети
*   **Отсутствие сетевого подключения:** Проверьте, доступен ли сервер в принципе.
    *   Команда: `ping <server_ip>`
*   **Сетевой файрвол:** Корпоративный или провайдерский файрвол может блокировать 22-й порт.
    *   **Проверка маршрута до хоста:** `traceroute -T -p 22 <server_ip>` (покажет, где на пути к серверу обрывается соединение, если порт фильтруется).
    *   **Проверка доступности порта** с помощью `nc` (netcat) — это современный и предпочтительный способ:
        ```bash
        # Флаг -z сканирует порты, не отправляя данные, -v дает подробный вывод.
        nc -zv <server_ip> 22 
        ```
        *   **Результат, если порт открыт:** `Connection to <server_ip> port 22 [tcp/ssh] succeeded!`
        *   **Результат, если порт закрыт:** `nc: connect to <server_ip> port 22 (tcp) failed: Connection refused`

    *   **Альтернатива с `telnet`(TCP-соединение):**
        ```bash
        telnet <server_ip> 22
        ```
        *   **Если порт открыт:** Соединение установится, и вы увидите `Connected to <server_ip>` или просто мигающий курсор. Это означает успех.
        *   **Если порт закрыт:** Вы получите ошибку `Connection refused` или `Connection timed out`.

#### Проблемы на стороне сервера
*   **Сервер выключен или не загрузился.**
*   **Служба SSH не запущена:** Процесс `sshd` может быть остановлен.
    *   Команда на сервере: `systemctl status sshd`
*   **Служба SSH слушает другой порт:** Проверьте конфигурационный файл `/etc/ssh/sshd_config`.
    *   Команда на сервере: `ss -tlpn | grep sshd` (покажет, какой порт слушает сервис).
*   **Файрвол на сервере:** `iptables`, `nftables` или `firewalld` могут блокировать входящие подключения на 22-й порт.
    *   Команды на сервере: `iptables -L -n`, `nft list ruleset`.
*   **Закончились ресурсы:** Нехватка памяти или места на диске может помешать созданию новых сессий.
    *   Команды на сервере: `free -h`, `df -h`.

#### Проблемы с аутентификацией и доступом
*   **Неправильный логин или пароль.**
*   **Неправильные права на ключ:** Слишком открытые права на файлы ключей на клиенте или на сервере.
    *   На клиенте: `chmod 600 ~/.ssh/id_rsa`
    *   На сервере: `chmod 700 ~/.ssh` и `chmod 600 ~/.ssh/authorized_keys`
*   **Неправильный публичный ключ:** Ключ на клиенте не соответствует ключу в `~/.ssh/authorized_keys` на сервере.
*   **Пользователю запрещен вход:** Настройки в `/etc/ssh/sshd_config` (`AllowUsers`, `DenyUsers`) могут запрещать вход вашему пользователю.
*   **SELinux/AppArmor:** Эти системы безопасности могут блокировать доступ.
    *   Команда на сервере: `sestatus`, `aa-status`.

### Углубленная диагностика

1.  **Детальный вывод клиента (Verbose Mode):**
    *   Это самый важный инструмент. Флаг `-v` заставляет SSH-клиент показывать в реальном времени, что именно он делает.
    *   `ssh -v user@host`: Показывает основные этапы подключения, согласование алгоритмов и попытки аутентификации.
    *   `ssh -vv user@host`: Добавляет информацию о чтении конфигурационных файлов и обмене ключами.
    *   `ssh -vvv user@host`: Максимальный уровень детализации, показывает всё вплоть до отправки и получения каждого пакета. Идеально для отладки проблем с аутентификацией.

2.  **Анализ логов на стороне сервера в реальном времени:**
    *   Позволяет увидеть, как сервер реагирует на вашу попытку подключения.
    *   Команда: `sudo journalctl -u sshd -f` или `sudo tail -f /var/log/auth.log`.
    *   **Что искать:** Сообщения `Accepted publickey for...`, `Failed password for...`, `Invalid user...`, `Connection closed by...`.

3.  **Запуск `sshd` в отладочном режиме на другом порту:**
    *   Это безопасный способ протестировать конфигурацию, не затрагивая основной SSH-сервис.
    *   Команда на сервере: `sudo /usr/sbin/sshd -d -p 2222`.
    *   Сервер запустится на порту 2222, не будет уходить в фон (`-d`) и будет выводить всю отладочную информацию в консоль. После этого можно попробовать подключиться: `ssh user@host -p 2222`.

4.  **Проверка проблем с MTU (фрагментация пакетов):**
    *   Иногда соединение устанавливается, но "зависает" после аутентификации. Это может быть связано с тем, что большие пакеты SSH фрагментируются и теряются по пути (часто бывает при использовании VPN).
    *   **Диагностика:** `ping -s 1472 -M do <server_ip>` (для Linux). Если пинг не проходит, нужно уменьшать размер пакета (`-s 1472`), пока он не начнет проходить. Это поможет определить максимальный размер MTU на пути.
