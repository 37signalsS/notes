## 0. Core Rule — SSoT (Single Source of Truth)

### 0.0 Default Posture

The user provides material or specifies a file/section for changes. The agent acts autonomously, without unnecessary clarification, if the context is obvious. If the context is not obvious — the agent either acts by default according to §0.1–§0.4, or asks one specific question if it cannot continue without an answer.

**Auto-Accept:**
- If the user explicitly specified a file/section — treat it as the SSoT target.
- If the user provided "raw" material — determine the most appropriate SSoT file by domain and specificity.
- If the user said "bring to state", "integrate", "bring to standard" — apply §0.7 (Bring to Standard) without preliminary questions.
- If the user asked to "fill gaps", "complete", "bring to full view" — fill missing sections without unnecessary clarification, subject to the §0.12 bring-to-standard override: when the user explicitly requests "bring to standard", "fill gaps", or "complete", that overrides the do-not-touch rule for already-compliant files.

**Rule Precedence (resolves conflicts between sections):**

> `User Intent (§11)` → `Safety` → `§13 Retrieval Mode (read requests)` → `§0.0 Auto-Accept` → `§0.5 Read Operations` → `§0.2 Anti-Duplicate Pipeline` → `§7 Freshness` → `§0.12 Do Not Touch`

Concretely:
- **A question is not an editing request.** If the user asks about a topic rather than requesting a change, apply §13 and do not modify files.
- **An explicitly specified file path short-circuits the SSoT search.** Do not look for alternative targets.
- **The RAG search is mandatory for content that is new or whose location is unknown.** It is *not* mandatory when the user named the file — in that case targeted `grep` within the thematic directory is sufficient. Rationale: searching a known file does not add knowledge, it only injects unrelated chunks into the context and degrades reasoning.
- **§0.8 is the single authoritative statement of the verification rule.** §0.0, §3 and §7 refer to it and do not restate it.
- **§7 is the single authoritative statement of the metadata-exclusion rule.** §4 refers to it and does not restate it.
- **§5 and §0.7 are not in conflict.** §5 lists the dimensions a document must cover; §0.7 governs the sections it may be organised into. Content coverage never obliges the creation of a heading — see §5's scope paragraph.

### 0.1 Identify SSoT

**BEFORE modify/add/create operations:**

1. **Identify SSoT file** by topic — prefer the file with the most complete content in the most **specific** domain directory
   - Specificity beats level: `Docker/Docker_network/docker_network.md` beats `Networking/ServicesAndTools/open_vswitch.md` for Docker networking topics
   - If two files are equal in completeness **and** specificity — prefer the higher-level directory
   - If still ambiguous — propose 2–3 candidates with reasoning and ask the user
   - If the user explicitly specified a file/section — treat it as the SSoT target, do not look for alternatives.
   - After identifying the SSoT, proceed to §0.2 before any modification, applying the precedence rules in §0.0.

### 0.2 Anti-Duplicate Pipeline — RAG-FIRST RULE

Before any addition, modification, or file creation, perform verification in the following order:

1. **RAG search:** perform semantic search via `AI/rag_system/unified_search.py "<topic or query>" --top-k 5`.
   - Required when: the content is new, or the target file is not yet known.
   - Skippable when: the user named the file explicitly — use targeted `grep` in the thematic directory instead (§0.0).
2. **grep in the thematic directory:** search for key terms first in the domain directory, then in the root of the knowledge base. Do not scan everything at once.
3. Based on the results, determine the SSoT file or confirm that it exists.
4. If RAG or grep found duplicates or intersections — work with the SSoT, remove duplicates in other files, and record the decision in the change report per §0.15.
5. If SSoT is not found — create a new file according to the §0.7 template.

**Parallelism:** no more than three RAG searches may be run in parallel.

### 0.3 Cross-domain Analysis

Topics often overlap — check adjacent domains:
- `Networking` ↔ `Linux/Networking` ↔ `Docker/Docker_network`
- `Security` ↔ `CI-CD/DevSecOps` ↔ `Docker/Docker_security`
- `Kubernetes` ↔ `Prometheus` ↔ `Docker`

### 0.4 Conflict Resolution

1. Choose ONE SSoT file
2. Merge verified info into SSoT
3. In all other files — replace duplicate content with a link to SSoT

**If SSoT does not exist:**
- Create it in the most specific domain directory according to the §0.7 template
- Move verified content from duplicates
- If unsure — create a minimal skeleton according to the template, do not ask the user

**If external/new material contradicts existing SSoT:**
- Verify facts via web search/trusted sources.
- Keep only truthful, up-to-date information.
- Merge the best of both sources into a single verified content.
- If the existing information in SSoT is wrong — update SSoT, do not preserve the error.

**If two knowledge-base files state different values for the same thing** (different port, flag, path, image tag, or version of the same product) — this is a content defect, not a style difference. Resolve it as above, and report the resolution to the user.

**Defect-before-redirect rule.** Before replacing a duplicate with a link to SSoT, check the SSoT for concrete defects: encoding artifacts, broken markdown syntax, wrong defaults, or outdated version-bearing values. If such defects exist, fix the SSoT first, then redirect duplicates to the corrected SSoT. A redirect to a defective SSoT preserves errors instead of removing duplication.

### 0.4.1 Cross-File Fact Consistency

Version drift (§7) is only one species of inconsistency. Files can equally disagree about a timeout, a default limit, a flag name, a port, a directory path, an API field, or the behaviour of a mechanism. Such disagreements are invisible until a reader follows both files and gets two answers.

**Rule 1 — Check on write, not only on read.** Whenever a *specific checkable value* is added, corrected or removed in a file, the same value is searched for in the rest of the knowledge base (`grep` on the literal value, and by meaning where the wording may differ). A value introduced without this check is incomplete work.

**Rule 2 — What counts as the same fact.** Not just identical strings. These are the same fact stated differently and must be reconciled:

- the same parameter, default, limit or timeout for the same tool version
- the same flag or key documented with different names or different defaults
- the same behaviour described with opposite conclusions ("X prevents this" vs "X does not prevent this")
- the same file path, port, or endpoint given with different values
- the same mechanism explained by two incompatible models

**Rule 3 — How to resolve.** Prefer the SSoT file (§0.4) as the authority. If neither file is the SSoT, prefer the more specific and more recently verified, confirm against documentation (§0.11 Rule 1), and make the others link or conform. Apply §0.14 — fixing a contradicting value in a third-party file is a minimal edit, not a rewrite.

**Rule 4 — Escalate genuine ambiguity.** When two files are each internally consistent, both defensible, and they describe different real configurations — for example a value that legitimately differs between versions or deployment modes — do **not** force them to match. Qualify both in place (per §0.9) and report the situation. Silently unifying them would destroy correct information.

**Rule 5 — Report what was found.** Discovered contradictions are listed in the §0.15 report regardless of whether they were fixed, including any resolved by escalation under Rule 4.

### 0.5 Read Operations

- SSoT-analysis is optional for read-only operations
- If duplicates or conflicts are discovered during read — proceed to §0.2–§0.4
- If creating new content during a response — apply full SSoT rules

### 0.6 Stop Condition

**Stop only if:**
- The SSoT file cannot be determined at all (no domain fits)
- The user explicitly asked to stop and clarify
- The action is irreversible and affects >5 files without a preliminary plan

**In all other cases, act by default**, do not stop at every step for confirmation.

**Stop procedure:** inform the user — what is undefined, what options are available, wait for decision.

### 0.7 Bring to Standard — template for creating/bringing a file to the standard view

When creating a new SSoT file or bringing an existing one to the standard, apply this structure. The result must be a **complete file**, ready for use as part of the knowledge base, not a half-adapted copy.

1. **Version Scope Line** — see §0.9. Placed immediately after the H1 when the file documents version-specific behaviour.
2. **Definitions** — key terms, abbreviations (expand only niche tools; do not expand industry-standard terms CI/CD, K8s, API)
3. **Basic Concepts** / **Architecture** / **How it works** — theory, principles of operation, components, lifecycle
4. **Practical Scenarios** / **Installation and Setup** / **Configuration** — step-by-step instructions, prerequisites, commands with expected output
5. **Operations and Commands** — table or list of commands with parameters and examples. Omit this section when the same commands are already documented inline in section 4 with their expected output; a separate section adds nothing in that case.
6. **Troubleshooting** — typical errors, causes, diagnostics, solutions
7. **Best Practices** — industry standards, recommendations, cleanup
8. **Additional Information** — links, related technologies, notes

**The template is a checklist, not a quota.** It lists what a file should contain *when it has something truthful to say on the subject*. It is not a list of boxes to fill.

- **Never create a section to satisfy the template.** A heading with nothing substantive under it is a defect (§0.12 covers empty sections). Omit the section, or write the content it was meant to hold.
- Section 5 ("Operations and Commands") in particular is routinely redundant: when commands are already given inline in section 4 with their expected output, a separate section adds nothing. Omit it.
- **A short file with real content is better than a long file with filler.** Depth per topic is not uniform and must not be padded to a fixed shape. If a topic genuinely warrants only definitions and one example, that is the correct file.
- The one thing that must never be traded away for template completeness is **substance**: theory, the mechanism behind a behaviour, and the reasoning behind a recommendation.

**Styling:**
- All headings in Russian; technology names and established terms in headings in English
- Code blocks with language; commands with expected output (`# → result`)
- Technical terms in English, explanations in Russian
- Inline links only; "See also" — include only directly relevant links

### 0.8 Content Integrity Rules — the single verification rule

*(This section is authoritative. Other sections refer to it instead of restating it.)*

- **Do not rename the file** without explicit user request. If the user provided a file with a name — keep it.
- **Preserve the original meaning** of external materials. If the user provided ready material for integration — do not rewrite it completely, only adapt it to the base style.
- **Verify the entire content before changes**, not only the part being changed: all versions, flags, options, paths, commands, deprecated markers. Relevance, objectivity and truthfulness of all pre-existing information are verified via:
  - internal search across the knowledge base;
  - web search when facts are unclear or outdated.
  Goal — get rid of outdated data by updating, not via placeholders.
- **Scan for concrete defects before editing.** Before any modification, inspect the file for encoding artifacts, broken markdown syntax, unmatched backticks, wrong defaults, and outdated version-bearing values. Fix confirmed defects during the same pass; do not leave known errors untouched.
- **Update to the current version** — but never by blind substitution. Follow §0.9 before changing any version-bearing value.
- **When integrating external material, fix errors.** Fix outdated commands, incorrect paths, non-working flags, even if the user did not ask. Adapt to the base style, but do not leave technical errors.
- **Do not delete information** if it is relevant, objective, and truthful.
- If content overlaps with existing SSoT — duplicate only where necessary for completeness; in other cases, link to SSoT.
- If content contradicts existing SSoT — verify facts via web sources, merge the best of both sources into verified content, update SSoT if necessary.

### 0.9 Version Scope — mandatory rule for version-bearing content

**Problem this solves:** the knowledge base documents several major versions of the same product side by side (for example Helm 3.14 and Helm 4.2, Prometheus 2.x and 3.x, oauth2-proxy 0.15 and 7.7) with no way to tell deliberate legacy coverage from neglect. Without a declared target, "update to the current version" cannot be applied consistently.

**Rule 1 — Declare the target.** If a file contains version-specific behaviour — pinned image tags, feature flags, CLI syntax, API versions, or a documented default that changes between releases — it MUST carry a scope line immediately after the H1:

```markdown
**Актуально для:** Prometheus 3.13.x
```

Permitted forms:
- `**Актуально для:** <Product> <version>` — single target
- `**Актуально для:** <Product> <v1> / <v2>` — deliberately covers several, common in migration and comparison files
- `**Актуально для:** <Product> <legacy> (legacy — <one-line reason>)` — intentionally documents an older line

Omit the line only for genuinely version-agnostic content (pure concepts, protocol theory, architectural principles).

**Existing form is preserved.** The three forms above are for new lines. A file that already carries a version scope in another shape — a blockquote, bold, or a sentence in the opening paragraph — keeps that shape. Do not reformat a scope line to match the templates, and do not add one to a file that has none without cause: that is a change to a compliant file (§0.12), and the absence of the line is reported per §0.15 rather than silently repaired.

**Rule 2 — Never bump a version by substitution.** Changing `prom/prometheus:v2.51.0` to `v3.13.1` is a **substantive content change**, not a cosmetic fix, because major versions may change flags, defaults, output formats and APIs. Before changing any version-bearing value (image tag, package version, `apiVersion`, feature flag, default):
1. Determine which major version the file declares (§0.9 Rule 1). If none is declared — declare it first.
2. Verify via web search whether the described behaviour is still valid in the target version.
3. If it is valid — update the value and the scope line together.
4. If it is not valid — rewrite the affected content for the target version, or mark the file as legacy with a reason (permitted form 3) and tell the user which option was chosen and why.
5. Never leave a value and its scope line disagreeing.

**Rule 3 — Report drift when editing.** When editing a file that has a scope line, compare the declared version against the current release. Report to the user in one line: declared version, current version, and whether the content still applies. Do not silently change versions.

**Rule 4 — Do not manufacture currency.** An old version is not a defect when it is explicitly declared and justified. A version left silently behind the current release *is* a defect, because the reader cannot tell which they are reading.

### 0.10 Overlap Declaration — mandatory for new and substantially rewritten files

Verbatim duplication in this knowledge base is rare, so the real risk is **semantic overlap**: several files covering the same ground in different words, which produces inconsistent facts and defeats RAG retrieval.

When creating a new file, or when a rewrite changes more than half of an existing file's content, the agent MUST declare the overlap decision:

1. List the existing files checked for topic overlap (from §0.2 search results).
2. For each, state in one line how the new content differs — different scope, different depth, different angle — or state that it is a duplicate and must be merged per §0.4.
3. If genuine overlap remains and duplication is required for completeness — say why the duplication is necessary.

An existing file that already covers the topic with equal or greater depth is not extended; it is used as the SSoT target.

### 0.11 Verified Technical Claims — what may and may not be written

**Problem this solves:** the largest quality risk in a technical knowledge base is a plausible-sounding invention — a flag that does not exist, a config key with the wrong name, a default value that was never the default. Such text is worse than a gap, because a reader cannot tell it is wrong. Nothing in the prompt previously forbade it, while §3 (item 7) actively encourages autonomous improvement.

**Rule 1 — Verify specifics before writing.** Every *specific, checkable* technical claim must be confirmed against official documentation or a web search **before** it is written into a file:

- CLI flags, subcommands, short/long option spellings
- Configuration keys, paths, file locations, environment variable names
- Default values, timeouts, limits, port numbers
- API fields, `apiVersion` values, CRD spec properties
- Image tags and package versions (per §0.9)

**Rule 1a — Read the implementation when the claim is about mechanism.** Documentation states the intended rule; the source states the actual one, and the two diverge more often than a reader would guess. Whenever a claim describes *how a tool resolves precedence, order of operations, fallbacks, default paths, or which flags still exist*, documentation alone is not sufficient evidence:

- Resolve the behaviour in the upstream source — the function that implements the resolution order, the flag/option registry, or the deprecation table — not only in the prose that describes it.
- Two concrete classes where this is decisive, both found in this knowledge base by reading source rather than docs: an environment variable's position in a precedence list, and whether a flag was removed in a given major version. Both are stated wrongly in prose while being unambiguous in the code.
- The cost is one file read; the benefit is that a claim the reader cannot check is not written from memory.

**Rule 2 — If it cannot be verified, it does not go in.** Do not write a specific claim that could not be confirmed. Either omit it, or state explicitly that it is unverified and what would be needed to confirm it. Never present an inference as a documented fact.

**Rule 3 — Bounds on proactive improvement.** §3 (item 7) authorizes autonomous improvement. That authorization is bounded:

| Allowed without further verification | NOT allowed without verification |
|---|---|
| Reorganising, restructuring, splitting | Introducing new flags, keys, or parameters |
| Clarifying wording, removing ambiguity | Asserting new defaults or limits |
| Fixing errors found via §0.8 | Adding new factual claims of any kind |
| Expanding existing verified content with reasoning and context | "Modernising" a value per §0.9 Rule 2 |

The distinction: **the agent may make existing knowledge clearer and better organised on its own authority. It may not make the knowledge itself larger in factual scope without checking.** Expanding theory, mechanism and reasoning from material already verified in the file is allowed; introducing a new technical assertion is not.

**Rule 4 — Examples must be real.** Code and configuration examples are either taken from verified documentation or explicitly marked as illustrative with placeholders. A synthesised example presented as working configuration is a defect.

**Rule 5 — Production-ready examples must be internally current.** Before saving or updating a production-ready configuration example, verify that every flag, key, and version-bearing value in it is still valid for the declared scope line (§0.9). If the example contains an outdated flag or value — update the example, do not preserve stale production guidance.

### 0.12 Do Not Touch — files that already meet the standard

A knowledge base of this size is mostly correct. Rewriting correct files is a net loss: it risks introducing error (§0.11), creates churn, and forces needless reindexing.

- **If a file already satisfies §0.7 and §0.8, say so and do not modify it.** "The file meets the standard, no changes needed" is a complete and acceptable outcome — and a correct one.
- Do not restyle, reword, reorder headings, or reformat a compliant file for consistency's sake.
- Do not extend a compliant file just because new material on the topic exists elsewhere; per §0.4 the SSoT rule applies first.
- Modification is warranted when: the user asked for it, a defect is found (§0.8), a version conflict is found (§0.4), or a cascading update requires it (§3, item 6). Absent one of these — leave the file alone.
- **Bring-to-standard overrides do-not-touch.** When the user explicitly requests "bring to standard", "fill gaps", or "complete", §0.12 does not apply; the applicable §5 dimensions are in scope even if the file is otherwise compliant. In all other cases, "do not touch" has priority.
- After any edit, check for **empty sections** (a heading whose body is only whitespace or a bare stub). These are defects; fill them with substance or remove the heading (§0.7).

### 0.13 EOL and Deprecated Technology — declare status, never recommend as current

Legacy technology in the knowledge base is legitimate and often necessary — production still runs it, and an engineer facing an inherited CentOS 7 host needs exactly that knowledge. The defect is not the presence of legacy content; it is legacy content **presented as current advice**.

**Rule 1 — State the status up front.** A file whose primary subject is end-of-life or deprecated MUST declare it before the content:

```markdown
> **Статус:** Docker Swarm не развивается. Применяется только для поддержки существующих
> развёртываний; для новых — Kubernetes.
```

**Rule 2 — Never present deprecated technology as a recommendation.** Phrases that present a deprecated tool as modern or recommended are defects and must be corrected on sight: "современный X", "рекомендуемый стек X", "актуальный подход X" where X is deprecated.

**Rule 3 — Prefer the successor when one exists.** When writing about a deprecated tool, the reader needs to know what replaced it and when to migrate. If the knowledge base covers the successor, link to it.

**Rule 4 — Scope line interaction.** For a deprecated technology the §0.9 scope line takes the legacy form, and the status note appears alongside it. Both express different facts: the version the text describes, and whether that version is still supported.

**Rule 5 — Do not delete legacy coverage on your own initiative.** Removal is a scope decision the user owns. Flag it and let them decide.

### 0.14 Minimal Edit — preserve what is already verified

**Problem this solves:** the knowledge base's existing prose is verified work. When an agent regenerates a whole file to fix one value, it silently re-authors text that was already checked. Paraphrasing verified content loses precision, introduces drift between phrasings of the same fact, and — because rephrasing is itself a new assertion — falls under §0.11 Rule 1 as unverified content. Rewriting a good file to fix one line is a net quality loss.

**Rule 1 — Edit the defect, not the document.** When a file is sound except for specific defects, correct only those parts. Everything else is reproduced **verbatim**, byte for byte, including wording, sentence structure, ordering and formatting.

**Clarification:** This verbatim rule applies to defect correction. It does not override §0.11 Rule 3: reorganising structure, improving clarity, and removing ambiguity from already-verified material are still allowed without additional verification. The prohibition is on changing factual content or rephrasing verified technical claims, not on structural improvements.

| Change | Treatment |
|---|---|
| The defect itself | Rewrite — this is the task |
| Directly dependent wording (a sentence that referenced the corrected value) | Minimal edit, same register as the original |
| Everything else in the file | **Verbatim, untouched** |
| §0.9 scope line / §0.13 status note | Update only if the edit changes what they assert |

**Rule 2 — Rewriting requires cause.** A full rewrite is performed only when the user asked for one, or when the defects are structural — the file is built on a wrong premise, the section organisation is wrong, or §0.7 cannot be satisfied without restructuring. Cosmetic dissatisfaction, added polish, or a different phrasing preference are **not** causes. When in doubt, the edit is minimal.

**Rule 2a — Rewrite must be justified explicitly.** Before regenerating a file, the agent must list the specific structural defects that make a minimal edit insufficient. If the defects are local — typos, wrong defaults, broken links, missing validation blocks — apply minimal edits per Rule 1. A rewrite is permitted only when the file’s organisation or coverage is fundamentally incompatible with §0.7 or §5.

**Rule 2b — Content-incompleteness is a cause.** A file whose section organisation already satisfies §0.7 may still be missing §5 dimensions that apply to the topic — prerequisites, validation, cleanup, edge cases. That is a structural defect of the same order as a wrong section organisation, and it is a legitimate cause for a rewrite when the task is a deliberate bring-to-standard (§0.0, §5). Two limits keep this from becoming a licence to rewrite good files:

- Only **applicable** dimensions count. Incompleteness must be established against the topic, not against the template — an inapplicable dimension is not a defect (§5, §0.7).
- **Verified content only.** The new material must pass §0.11 Rule 1. A rewrite justified by content gaps is still barred from introducing unchecked claims, and the honest gap is reported per §0.15 rather than filled with inference.

A partial rewrite is the normal case: the missing dimension is added and the prose that is already verified stays verbatim under Rule 1. Rule 2a does not license regenerating correct sentences to make room for the addition.

**Rule 2c — Truthfulness outranks verbatim preservation.** Rule 1 preserves verified prose. It does not preserve a pre-existing claim that turns out to be wrong, undocumented, or unverifiable. Where §0.14 and §0.8/§0.11 conflict over such a claim, §0.8 and §0.11 govern: correct the claim, keep the surrounding prose verbatim, and note the change in the §0.15 report. A passage that reads as official advice but is not documented as such is a §0.11 Rule 4 defect, not protected text.

**Rule 3 — Do not "improve" untouched prose.** §3 (item 7) authorizes autonomous improvement; this is its limit. Unrequested rewording of a correct, verified passage is prohibited — this rule addresses §0.11 Rule 3's allowed expansion ("reasoning and context"), not its prohibition on changing factual content. A parallel may exist elsewhere in the file; the original is not the defect.

**Rule 4 — Report if the file needed more than expected.** If a small defect turns out to require changes across many sections, say so before proceeding — this indicates a structural problem (§0.14 Rule 2) rather than a local one.

**Rule 5 — Applied to cascaded updates.** When §3 (item 6) requires updating the same value in other files, the same minimal-edit rule applies to each of them.

### 0.15 Change Report — required output for every editing task

An edit whose result cannot be audited is not verifiable, and unverifiable work does not meet the knowledge base's standard. Every task that modifies files ends with a short report. For a single-file edit this is a few lines; for a bulk operation it is grouped by pattern, not listed file by file.

**The report contains four things:**

1. **What changed** — the specific defects corrected, in technical terms. Not "improved the file" but "`livenessProbe` timeout corrected from 30s to 60s to match `ConfigMap/best_practices.md`".
2. **What was verified and how** — which sources confirmed the corrected values (documentation, web search, or another knowledge-base file per §0.4). Cite them.
3. **What could NOT be verified** — the explicit list of claims left unconfirmed, and why (source unavailable, requires lab testing, unclear which version applies). This is mandatory and may not be omitted; an empty list is stated explicitly as empty. Never let an unverified claim pass silently into the file.
4. **What was deliberately not changed** — content found questionable but left alone, so the user can overrule the agent's judgement. Includes files skipped under §0.12, legacy material flagged under §0.13, and conflicts left for the user to resolve per §0.4.

**Rules for the report:**
- It goes in the **response to the user**, not in the file. §7's metadata prohibition still applies to file content.
- Report only after the work is actually verified — not a plan, not a prediction. A plan is §7's concern; this is the outcome.
- Discrepancies between the file's version scope (§0.9) and the current release are reported here, per §0.9 Rule 3.
- For "no changes needed" outcomes, item 1 reads "no changes — file meets the standard (§0.12)", and items 2–4 are reported as empty or not applicable, since no modification was performed.

## 3. Core Tasks & Guidelines

**Priority of concerns — resolves what to sacrifice when rules collide:**

> **Substance outranks structure. A file that is incomplete but deep is acceptable. A file that is complete but shallow is a defect.**

When template compliance and content quality conflict, keep the content. When depth and file size conflict, keep the depth (§9). When consistency and correctness conflict, keep the correctness. Structure serves content; it is never the reason a file exists.

1. **SSoT-First:** All changes only after SSoT-analysis (§0), applying the precedence rules in §0.0.
2. **Structuring:** `Version Scope (§0.9) → Definitions → Basic Concepts / Architecture / How it works → Practical Scenarios / Installation and Setup / Configuration → Operations and Commands → Troubleshooting → Best Practices → Additional Information`. This is a checklist of what belongs in a file, not a quota to satisfy — see §0.7.
3. **Bring to Standard:** When user provides material for integration — apply §0.7 immediately, do not ask for confirmation of each step.
4. **Integration completeness:** Integrated material must become a full-fledged part of the knowledge base, not a half-adapted copy. The result is a file ready for use, brought to the standard.
5. **Fix external materials:** When integrating external materials, fix technical errors, outdated commands, incorrect paths, non-working flags. Adapt to the base style, but do not leave errors.
6. **Cascading update:** If you updated a version/command/flag/path in one file — find all other knowledge base files where this same outdated value appears, and update them too. The knowledge base must remain consistent. For version-bearing values, each affected file is handled per §0.9, not by blind substitution.
7. **Integrity & Proactivity:** Before any change, verify the file per §0.8. Proactively and independently identify "white spots" (gaps, missing details, or undocumented scenarios) and fix them when user requested improvement/completion. Do not limit yourself to requested fixes: analyze the entire document, identify inaccuracies, weak explanations, or logical gaps, and improve them autonomously. If a change in one section affects others or requires restructuring, perform all necessary systemic edits to maintain document integrity. All information—whether provided by the user or already present in the knowledge base—MUST be verified and actualized before any creation or modification. Validate all internal links after every edit. After making changes, perform a full self-check: ensure the document is complete, logically structured, technically correct, and that no useful information was lost.
   - **Proactivity is bounded by §0.11 Rule 3.** Improving a file's organisation, clarity and depth from already-verified material is done autonomously. Adding new factual claims, flags, or parameters is not — those require verification first.
   - **A file that already meets the standard is left untouched** (§0.12). Reporting "no changes needed" is a correct outcome, not a failure to be thorough.
   - **Edits are minimal by default** (§0.14). Fix the defect, reproduce the rest verbatim. Rewriting a sound file is not thoroughness — it is risk.
   - **Every editing task ends with the §0.15 change report**, including what could not be verified and what was deliberately left alone.
   - **Any specific value written or corrected is checked against the rest of the base** for the same fact stated differently (§0.4.1).

## 4. Language and Style

- **Response language:** Russian (always), regardless of the language of the prompt or system instructions
  - **Exception:** if the user explicitly requests another language — switch for that response only
  - **Exception:** `AGENTS.md` itself is written in English and is never translated — see "About This File".
- **Headings:** ALL headings (`#`, `##`, `###`, etc.) MUST be in Russian
  - Applies to all headings created or modified in knowledge-base files
  - Technology names and established terms within headings may remain in English (e.g., `## Обзор Kubernetes`, `### Docker — сеть`)
  - **Exception — established section names:** when a file already uses a recognised English section name (`Best Practices`, `Troubleshooting`), it MAY be kept rather than translated. Do not rename existing section headings for consistency alone; the content matters more than the label. Use the Russian form for any newly created section.
- **Comments inside code blocks:** default English, because a copy-pasted snippet is most often pasted into tooling, commit messages and tickets where the surrounding language is English, and because identifiers and error strings in the snippet stay English regardless. Use Russian in a code block only when the comment exists to explain the example to the reader (a `# →` result annotation, a "why this step" note) and the snippet is not meant to be pasted verbatim. Follow the language already used in an existing file's snippets rather than switching it (§0.14).
- **Emojis:** DO NOT use emojis in any response, file content, or comments
- **Style:** Professional, technical, comprehensive. **Technical Depth & Theory:** NEVER truncate or remove valid technical details, examples, or theoretical explanations. Explain not just **what** is happening, but **why**. Theory must be sufficient for understanding: include definitions, principles of operation, architecture, lifecycle, component relationships, and reasons for specific approaches. Address important limitations and features to eliminate assumptions. The goal is a complete knowledge base, not a short summary.
- **Maintenance of Technical Content (STRICT RULE):**
  - **Do NOT delete** useful theoretical or practical information. If information is outdated, inaccurate, or poorly structured — **improve, clarify, expand, or relocate** it, but preserve the underlying value and meaning.
  - Deleting technical details is PROHIBITED unless one of the following conditions is met:
     1. **SSoT Integrity:** Removing direct duplicates already present in their authoritative SSoT file.
     2. **Absolute Obsolescence:** The technology, tool, or method is completely defunct, has no successor/replacement, and is no longer relevant for the knowledge base.
     3. **Relocation:** Content is being moved to a more specific or appropriate domain file (transfer, not deletion).
  - File size reduction is allowed ONLY under the conditions above. In all other cases, technical depth must be preserved or improved via updates.
- **Brevity vs. Depth:** Brevity is only for UI/Response fillers. In knowledge-base files, detailed theory, practical scenarios, commands, and architectural nuances take absolute precedence over conciseness.
- **Prohibited:** summarizing detailed technical paragraphs into short bullet points if it leads to loss of context or nuance.
- **Terminology:**
  - Technology terms in English (Kubernetes, Docker, Prometheus, Kafka)
  - Explanations and descriptions in Russian
  - Expand abbreviations on first use in a file ONLY if they are not industry-standard or common in DevOps (e.g., expand niche tools, but no need to expand CI/CD, K8s, API if context is clear)
  - Do NOT translate established terms: deploy, pipeline, container, orchestration
  - **Prohibited in knowledge-base files:** the phrase `SSoT (Single Source of Truth)` and its variants (`SSoT`, `Single Source of Truth`) — this is an internal meta-concept used only in this instruction file; when describing content hierarchy in knowledge-base files, use neutral terms
  - **Prohibited in knowledge-base files:** reliability scores and update dates — see §7, which is the authoritative statement of this rule.
- **Links:** inline only (`[text](url)`)
- **"See also" section:** include only directly relevant links; do not add irrelevant links to pad the list
- **Post-edit link audit:** after completing any edit, remove only broken or clearly irrelevant links. Do not trim a list solely based on length.

## 5. Practical Implementation & Completeness

Documentation MUST enable the reader to independently apply knowledge in practice.

**Scope — this section is a coverage checklist, not a section list.** It names the dimensions a document must cover *where it has truthful content on the subject*. It never requires a heading. Where this section and §0.7 appear to conflict, §0.7 governs structure. Concretely:

- A dimension that does not apply to the topic is omitted, not filled with a stub (§0.7).
- A dimension already covered in prose inside another section counts as covered; it is not duplicated under its own heading (§0.7).
- A file that already covers the applicable dimensions is not extended to cover the inapplicable ones (§0.12).
- A minimal defect fix does not trigger a hunt for missing dimensions (§0.14 Rule 1). Fixing a value is not a licence to restructure the file around it.
- **A minimal defect fix is not the only kind of task.** When the file is being brought to standard deliberately (§0.0 — «привести к стандарту», «заполнить пробелы», «довести до полного»), the applicable dimensions below **are** in scope, whether or not a heading is missing. The two demotions above constrain *how* a dimension is satisfied, not *whether* it must be:
  - Satisfied inline, under the heading that already exists, when the topic belongs there. A file whose section organisation is already correct may still be content-incomplete, and that is the case this section exists to catch.
  - Satisfied under a new heading only when the dimension does not belong to any existing section (§0.7: no heading is created to satisfy the template, and none is created to satisfy this section either).
- **The demotion is bounded by truthfulness, not by effort.** A dimension may be left uncovered when the agent has nothing verified to say on it — the honest gap is reported per §0.15, not filled with inference. It may not be left uncovered merely because covering it would require more than a local edit.

**Dimensions to cover where applicable:**

- **Prerequisites:** Explicitly state hardware/software requirements, tool versions, initial setup, and environment state.
- **Step-by-Step Instructions:** Provide a logical, continuous sequence of actions. Explain every significant step to eliminate guesswork.
- **Configurations & Commands:**
  - Examples must be complete and copy-pasteable (with minimal, clearly marked placeholders).
  - Explain each parameter and variable.
  - Commands and configs must be consistent with the theory described in the file.
- **Validation:** Include expected results and clear methods to verify correct execution (e.g., specific command output, log entry, or status).
- **Troubleshooting:**
  - List typical errors and their causes.
  - Provide diagnostic methods and step-by-step solutions.
- **Best Practices & Cleanup:** Include industry standards for the task and instructions on how to revert changes or clean up the environment.
- **Edge Cases:** Describe limitations, known bugs, and behavior in non-standard or complex scenarios.

## 6. Tool Discipline & Scale Awareness

1. **Read-before-Replace:** Always `read` the file before `replace`/`write` on the same file.
2. **Search Order:** Use `grep`/`search` first in the **thematic domain directory**, then in the **root** of the knowledge base. Do not scan all directories at once.
3. **RAG-first:** RAG search via `unified_search.py` is mandatory for new content or unknown targets, and skippable when the user named the file (§0.0).
4. **Progressive Disclosure:** For complex tasks, show a plan and get confirmation before execution.
5. **Batch Operations:** For operations affecting >5 files, prepare a plan first, then execute sequentially. Do not ask for confirmation on each file.

## 7. Reliability & Freshness

### Reliability scores

**Reliability Scores:** **10** (SSoT + Web), **9** (Internal only), **7–8** (Outdated/Unverified - cap here), **5–6** (Fragmentary), **<4** (Insufficient data).

**Metadata Exclusion Rule:** Reliability Scores, last update dates, and data freshness indicators are for internal agent reasoning and user reporting ONLY. Adding these metadata elements directly into knowledge-base files is STRICTLY PROHIBITED.

**Exception — Version Scope Line:** the `Актуально для:` line (§0.9) is the one permitted declarative marker. It states which software version the content describes — a technical fact, not an editorial judgement about the document's own quality. It does not fall under the prohibition above.

**Stopping formula:**
> Insufficient data for a reliable conclusion. Hypotheses and assumptions are prohibited. Confirmed context is required.

**Freshness Triggers:** Explicit user request, >12 months old, Version EOL, Known vulnerabilities, Proactive identification of "white spots" (gaps). All incoming data (from the user or internal search) MUST be verified for freshness.
**Freshness Classes:** Version/Tool-specific (verify current; cap at 7 if unverified), Best practices (update annually), Conceptual (Evergreen).

### Handling procedure

1. `web_search` / `grep`/`search` for current data
2. Justify the update with source reference
3. Create update plan
4. Apply changes — version-bearing values strictly per §0.9, never by substitution
5. **Update to the current version.** Update content to the current version. Leave the old value only as a historical case, and only if the current version is unavailable for verification. In this case, explicitly inform the user why the information was not updated.
6. Tutorial steps → verify tool availability
7. Links → validate accessibility

**Auto-apply:** If user said «bring to state» / «update» / «actualize» — perform the procedure without additional questions if data is available. If data is unavailable — leave the existing content and inform the user that the update failed.

### Detecting cross-file version drift

A single file can be correct while the knowledge base is inconsistent. When the user asks about the state of a domain, or after a bulk operation, check whether the same product is documented at incompatible major versions across files (e.g. one file on Helm 3.x, another on 4.x; Prometheus 2.x alongside 3.x). Report such sets to the user as a list, with the file and the version found in each — do not rewrite them unilaterally, because deciding which line a file should target is a domain judgement the user owns.

**Versions are not the only kind of drift.** The same sweep is applied to *values* — timeouts, defaults, ports, paths, flag names, limits — where two files disagree about one mechanism. A file that is internally perfect can still hand the reader a second, contradicting answer somewhere else in the base. Detection follows §0.4.1; resolution follows §0.4, including the escalation rule for legitimately differing configurations.

- **Commands:** show expected output inline (`# → result`)
- **Versions:** explicitly state when command/output is version-specific; pin version-bearing values rather than using `latest` in examples intended to be copied

- **Auto-generated files:** skip from knowledge-base tasks

## 9. File Management

1. **Split Rule:** Split if >600 lines AND subtopics are independently useful. **DO NOT split** if topics are tightly coupled (same technology, protocol, or one requires the other for context). Cohesion beats size.
   - **Splitting is relocation, never reduction.** When splitting, every piece of technical content moves intact to one of the resulting files. Reducing depth to satisfy the line limit is PROHIBITED (§4). If a section cannot be moved without losing meaning, keep the file whole and tell the user.
2. **Merge Rule:** Merge files <30 lines or with >50% overlap.
3. **Safety Protocol:** For operations affecting >5 files, show a plan BEFORE execution. Write operations to the same file must be sequential. Link validation is mandatory after any change.

## 10. Cross-Reference Rules

**Link Validation (MANDATORY):** Validate all internal markdown links (relative paths, anchors) after EVERY edit. Fix broken links before completing the task. All link prohibitions: see §5.

**Depth check:** after any bulk move or rename, verify that relative link depth still resolves — a file moved up one directory level breaks every `../` reference it contained.

## 11. Clarifying Questions — When to Ask

**Ask ONLY when:**
- Request has >1 valid interpretation AND tools cannot resolve it (e.g., «update networking» — which file?).
- SSoT choice is ambiguous (>2 candidates) AND no clear specificity rule applies.
- Action is irreversible AND affects >5 files without a pre-approved plan.
- Critical context is missing AND cannot be inferred from domain/topic (version, target dir).
- A file documents a version that is intentionally behind current AND the correct target line cannot be determined from the content — state the options per §0.9 permitted forms and ask which applies.
- User explicitly asked for clarification or confirmation.

**Do NOT ask when:**
- Request is unambiguous or can be resolved with tools.
- User provided file path or explicit target.
- Default action is obvious from context (e.g., «integrate into the base» → apply §0.7).

**Max questions per task:** 1–2. If more are needed — propose the full set at once, do not ask sequentially.

### 11.1 Incorrect Premises in the User's Instruction

The "do not ask, act by default" posture above applies to *ambiguity*, not to *error*. When the user's instruction rests on a factually incorrect premise, the agent must not silently comply.

**Procedure:**
1. Detect the suspect claim — a wrong flag, an obsolete version, a non-existent product behaviour, a deprecated tool presented as current.
2. Verify it per §0.11 Rule 1 (documentation or web search).
3. If it is wrong — **perform the rest of the task in the corrected form**, and report the correction plainly in the response: what was wrong, what is correct, and that this is what the file now contains.
4. If correcting it would change the intent of the task — stop and ask (§11, 1–2 questions).

**This is a report, not a refusal.** The user's goal is a correct knowledge base; a corrected file serves it, a refusal does not. Never argue at length — state the correction and move on. If the user reaffirms the original claim after being shown the evidence, follow their instruction and note the disagreement in the response once.

## 13. Retrieval Mode — answering questions from the knowledge base

The knowledge base's primary value is retrieval, not only maintenance. This section governs read-and-answer requests: a question about a topic, a request to explain or compare, a "what do we have on X".

**Procedure:**

1. **Search the base first.** RAG search per §0.2, then targeted `grep` in the thematic directory. Retrieval quality decides answer quality.
2. **Cite the sources.** Every substantive claim is attributed to a file with an inline link. An answer without sources is not an answer from this knowledge base — it is the model's own recall, and the user cannot tell the difference.
3. **State the version scope of what you relied on.** If the source file carries a §0.9 scope line, quote it. The answer is only as current as the file behind it.
4. **Do not fill gaps from memory.** If the base does not cover the topic, say so explicitly: what is missing, and which file would be the right place for it. Silently supplementing from parametric knowledge defeats the purpose of having a knowledge base — and the user cannot audit what they cannot see.
5. **Flag conflicts between sources.** If two files disagree on a value, present both with their sources and state which one is more likely current and why. Do not pick one silently.
6. **Flag legacy material.** If the answer rests on a deprecated technology (§0.13), say so in the answer.
7. **Propose the fix.** When retrieval reveals a gap, an outdated value, or a conflict, offer the concrete correction — file, section, what to change. Answering the question is step one; leaving the base better is the actual job.

**Scope of this mode:** read-only by default. Retrieval does not authorise edits. If the user asked a question, answer it — then ask before modifying files.

## Appendix A. Priority Order

1. **User Intent** (Explicit request overrides defaults).
2. **Safety** (No secrets, no irreversible actions without confirmation).
3. **Information Preservation** (NEVER delete useful data; improve, expand or relocate instead).
4. **SSoT integrity** (One authoritative source).
5. **Documentation Quality** (Completeness, technical accuracy, and practical applicability).
6. **Content over Structure** (Substance outranks template completeness and file size — see §3).
7. **Efficiency** (Minimize tool calls).
8. **Style** (Naming, language).

**Which of #5 and #6 applies.** The two overlap, and the overlap decided a real case: whether filling an applicable §5 content dimension is Documentation Quality (#5) or "template completeness" (#6). It is **#5**. #6 means that a heading with nothing substantive under it is a defect and that short-and-real beats long-and-padded; it does **not** excuse a file that is structurally compliant and missing every prerequisite, every expected output, and every cleanup instruction. Reading #6 as a licence to leave §5 uncovered made §5 unenforceable in practice — the demotions in §5 are about *how* a dimension is satisfied, and §0.14 Rule 2a is the cause that makes filling it legitimate.
