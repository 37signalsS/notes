# GitHub Actions: Ключевые концепции

GitHub Actions — интегрированная в GitHub платформа для автоматизации процессов разработки, обеспечивающая реализацию пайплайнов непрерывной интеграции и доставки (CI/CD). Платформа позволяет автоматизировать сборку, тестирование и развертывание кода непосредственно из репозитория, используя декларативный подход «автоматизация как код». Для публичных репозиториев использование стандартных исполнителей бесплатно; для приватных действует поминутная тарификация с ежемесячной квотой (тарифы и лимиты пересматриваются регулярно — заметное снижение цен на hosted-раннеры произошло 1 января 2026 года, до 39% на отдельные конфигурации).

## Определения

- **Рабочий процесс (Workflow)**: Высокоуровневая автоматизированная процедура, описываемая в YAML-файле. Хранится в директории `.github/workflows`.
- **Событие (Event)**: Конкретное действие или триггер (push, pull request, расписание), инициирующее запуск воркфлоу.
- **Задача (Job)**: Набор шагов, выполняемых на одном и том же исполнителе. Задачи могут иметь зависимости и выполняться параллельно.
- **Шаг (Step)**: Индивидуальная задача внутри Job (команда или экшен). Шаги по умолчанию выполняются последовательно; начиная с июня 2026 года возможен и явный параллельный запуск шагов внутри одной задачи (ключевые слова `background`, `wait`, `wait-all`, `cancel`, `parallel` — см. раздел «Модель параллелизма»).
- **Действие (Action)**: Компактный, переиспользуемый блок логики (приложение), выполняющий часто повторяющиеся операции (например, `checkout` кода).
- **Исполнитель (Runner)**: Сервер или контейнер, в котором запускаются задачи.
- **Артефакт (Artifact)**: Результат выполнения пайплайна (бинарные файлы, отчеты), сохраняемый в хранилище GitHub.
- **Контекст (Context)**: Объект, содержащий информацию о текущем запуске, окружении и секретах, доступный во время выполнения.
- **Запуск воркфлоу (Workflow Run)**: Конкретный экземпляр выполнения воркфлоу, порожденный событием или запущенный вручную. Каждый запуск имеет уникальный идентификатор и содержит одну или несколько задач.
- **Матрица (Matrix)**: Стратегия генерации вариантов одной задачи по набору параметров (ОС, версии инструментов), создающая декартово произведение копий задания.
- **Concurrency (Параллелизм-ограничитель)**: Механизм ограничения числа одновременно выполняющихся запусков одного воркфлоу или группы задач; позволяет также автоматически отменять устаревшие запуски (`cancel-in-progress`).
- **Переиспользуемый воркфлоу (Reusable Workflow)**: Воркфлоу, вызываемый другим воркфлоу как вложенная процедура через ключ `uses`, с собственным контрактом входов (`inputs`) и выходов (`outputs`).
- **Окружение (Environment)**: Именованная логическая среда развертывания (например, `staging`, `production`) с независимыми правилами защиты, секретами и переменными.
- **Образ раннера (Runner Image)**: Предустановленная виртуальная машина (VHD) со стандартным набором инструментов; содержимое образов публикуется в репозитории [actions/runner-images](https://github.com/actions/runner-images).

## Архитектура и модель выполнения

GitHub Actions базируется на событийно-ориентированной модели. Весь процесс управления жизненным циклом выполнения можно разделить на следующие уровни:

1.  **Триггерный уровень**: Событие в репозитории (или внешней системе) инициирует поиск подходящих YAML-конфигураций.
2.  **Оркестрационный уровень**: Сервис GitHub Actions анализирует зависимости между задачами (`needs`), распределяет их по доступным исполнителям и управляет очередями.
3.  **Исполнительный уровень**: Раннер скачивает необходимые экшены, подготавливает переменные окружения и последовательно выполняет шаги задачи.

Иерархия выполнения в одном запуске выглядит так:

```text
Событие (push, PR, schedule, workflow_dispatch)
└── Запуск воркфлоу (Workflow Run)
    ├── Job A  ──► Раннер #1 ──► Step 1 → Step 2 → ...
    ├── Job B  ──► Раннер #2   (параллельно с Job A)
    └── Job C  ──► Раннер #1   (после завершения Job A, если needs: [A])
```

Связь оркестратора и раннера построена на long-polling: приложение раннера само опрашивает сервис GitHub о наличии задач, поэтому исходящие HTTPS-соединения достаточно для работы self-hosted раннера (входящих портов не требуется). Именно оркестратор принимает решение, какой раннер получит задачу, исходя из метки `runs-on`.

### Изоляция и эфемерность
Каждая задача на GitHub-hosted раннере выполняется в чистой виртуальной машине, которая уничтожается после завершения. Это гарантирует отсутствие побочных эффектов между запусками и высокую безопасность.

Важный нюанс: это свойство относится именно к GitHub-hosted раннерам. **Self-hosted раннеры эфемерны только если настроены так явно** (флаг `--ephemeral` при регистрации или эфемерные поды в Actions Runner Controller). По умолчанию stateful self-hosted раннер сохраняет файловую систему, окружение и процессы между запусками — это удобно для кеширования, но создает риски накопления «грязного» состояния и закрепления компрометирующего кода, поэтому публичные репозитории по умолчанию запрещают использование self-hosted раннеров.

## Модель параллелизма: Jobs против Steps

Понимание двух уровней параллелизма — ключевое для проектирования быстрых пайплайнов:

| Уровень | Поведение по умолчанию | Управление |
| :--- | :--- | :--- |
| Задачи (Jobs) | Параллельны друг другу | Последовательность задается графом зависимостей `needs` |
| Шаги (Steps) внутри задачи | Строго последовательны | С июня 2026 года — явный параллелизм через новые ключевые слова |

До июня 2026 года единственным способом распараллелить работу внутри одной задачи было фоновое выполнение в shell (`&`), что приводило к перемешиванию логов разных операций. Теперь платформа поддерживает нативный параллелизм шагов с раздельными логами:

| Ключевое слово | Назначение |
| :--- | :--- |
| `background: true` | Запускает шаг асинхронно и немедленно переходит к следующему |
| `wait` | Приостанавливает выполнение до завершения указанного фонового шага (или нескольких перечисленных) |
| `wait-all` | Ожидает завершения всех предшествующих фоновых шагов |
| `cancel` | Аккуратно останавливает фоновый шаг, когда он больше не нужен (типично для долгоживущих сервисов) |
| `parallel` | Группа шагов, выполняемых конкурентно с неявным ожиданием после группы («синтаксический сахар» над `background` + `wait`) |

Типовые паттерны: параллельная сборка независимых компонентов; запуск сервиса в фоне, работа с ним и корректная остановка; неблокирующая отправка телеметрии во время продолжающейся упаковки. Подробные практические примеры — в сценарии ниже и в разделе о матричных сборках (параллелизм между задачами).

## Типичный жизненный цикл GitHub Workflow

Современный процесс разработки в GitHub базируется на тесной интеграции Git-событий с автоматизированными пайплайнами:

1.  **Создание Feature-ветки**: Разработчик создает отдельную ветку для новой функциональности.
2.  **Pull Request (PR) и запуск CI**: При создании PR или пуше в ветку автоматически триггерится CI-воркфлоу.
    - Выполняются Unit-тесты, линтинг, сканирование зависимостей и уязвимостей.
    - Результаты отображаются непосредственно в интерфейсе PR, блокируя слияние в случае ошибок.
3.  **Code Review и исправления**: Команда проводит ревью. Если требуются изменения, новые коммиты в PR повторно запускают CI для проверки исправлений.
4.  **Слияние (Merge) в основную ветку**: После одобрения и успешного прохождения всех проверок PR сливается в `main`/`master`.
5.  **Верификация после слияния**: Слияние в основную ветку триггерит повторный (или расширенный) запуск воркфлоу для проверки корректности интеграции изменений со всем кодом проекта.
6.  **CD (Deployment/Delivery)**: В зависимости от настроек, успешная проверка в `main` инициирует автоматический деплой на Production (Continuous Deployment) или подготавливает артефакт и ожидает ручного подтверждения (Continuous Delivery).

Блокировка слияния из пункта 2 настраивается через Branch Protection Rules (Required Status Checks) — сами по себе результаты воркфлоу ничего не блокируют, если проверка не объявлена обязательной в настройках защиты ветки.

## Компоненты системы

### Исполнители (Runners)

Выбор типа исполнителя определяет производительность и безопасность пайплайна:

- **GitHub-hosted Runners**: Управляемые GitHub виртуальные машины (Ubuntu, Windows, macOS). По состоянию на 2026 год включают поддержку **Larger Runners** с конфигурациями до 64 CPU и поддержкой GPU для задач машинного обучения.
  - Метка `-latest` означает «последний стабильный поддерживаемый образ», а не самую свежую версию ОС от вендора: например, `ubuntu-latest` соответствует `ubuntu-24.04`. Для воспроизводимости рекомендуется пиновать точные версии (`runs-on: ubuntu-24.04`).
  - Спецификации стандартных Linux-раннеров: публичные репозитории — 4 vCPU / 16 ГБ RAM; приватные — 2 vCPU / 8 ГБ RAM (детальные таблицы по всем ОС — в разделе об ограничениях среды).
  - Larger Runners доступны в конфигурациях x64 до 96 ядер (384 ГБ RAM) и arm64 до 64 ядер (256 ГБ RAM), а также GPU-конфигурации (GA с июля 2024): 4 vCPU, 28 ГБ RAM, NVIDIA Tesla T4 (16 ГБ VRAM) на Linux и Windows. GPU-раннеры доступны только на платных планах Team/Enterprise и настраиваются как именованные runner-группы.
  - Новые образы в публичном превью (июнь 2026): `ubuntu-26.04` и `ubuntu-26.04-arm` (x64 и arm64), `windows-11-vs2026-arm` (Windows 11 arm64 с Visual Studio 2026), а также образы Red Hat Enterprise Linux.
  - macOS-раннеры существуют в Intel (x64) и Apple Silicon (arm64, M-серия) вариантах; метка `macos-latest` указывает на arm64.
- **Self-hosted Runners**: Исполнители в собственной инфраструктуре. Обеспечивают доступ к внутренним сетям и кастомному оборудованию. Требуют самостоятельного обслуживания версий приложения раннера (устаревшие версии принудительно отключаются сервисом) и соблюдения мер безопасности, описанных в разделе об изоляции.
- **Actions Runner Controller (ARC)**: Современный стандарт (2025–2026) для управления масштабируемыми фермами раннеров в Kubernetes. Позволяет использовать эфемерные контейнерные раннеры с мгновенным масштабированием.

### Действия (Actions) и их типы

Экшен — минимальная единица переиспользования. По способу реализации различают три типа:

1. **Docker container actions** — логика упакована в Docker-образ; работает только на Linux-раннерах, но гарантирует идентичное окружение.
2. **JavaScript actions** — Node.js-приложение без Docker; запускаются быстро и кроссплатформенно, но требуют наличия нужного runtime.
3. **Composite actions** — композиция из готовых шагов (`run` и `uses`) в одном YAML; простейший способ создать свой переиспользуемый блок без написания кода.

Экшены подключаются из Marketplace, других публичных репозиториев или локальных директорий самого репозитория (`.github/actions/...`). Разбор типов, создание собственных экшенов и практика SHA-pinning — в разделе о готовых действиях и Marketplace.

### Переменные и контексты

Механизм управления данными обеспечивает гибкость пайплайнов:
- **Контексты**: Объекты типа `github`, `env`, `job`, `steps`, `vars` и `secrets`. Позволяют динамически изменять логику в зависимости от ветки, автора или результатов предыдущих шагов. Полезно знать и другие часто используемые контексты: `runner` (метаданные исполнителя, например `runner.os`), `needs` (выходы зависимых задач), `strategy`/`matrix` (параметры матрицы), `inputs` (входы переиспользуемых воркфлоу и `workflow_dispatch`).
- **Выражения `${{ ... }}`**: Используются для доступа к контекстам и выполнения функций (например, `hashFiles` для кеширования).
- **Переменные по умолчанию (Default Environment Variables)**: Каждый запуск автоматически получает набор переменных вида `GITHUB_*` и `RUNNER_*`: `GITHUB_SHA` (хеш коммита), `GITHUB_REF` (полное имя рефа, например `refs/heads/main`), `GITHUB_REPOSITORY` (`owner/repo`), `RUNNER_OS` (`Linux`, `Windows`, `macOS`). Они доступны и в shell-шагах без `${{ }}`-синтаксиса — как обычные переменные окружения.

Полный справочник синтаксиса, приоритет переопределения переменных и функции выражений — в разделе о синтаксисе воркфлоу.

## Безопасность и управление доступом

Безопасность в GitHub Actions строится на принципе минимальных привилегий:

- **GITHUB_TOKEN**: Временный токен доступа к API GitHub. С 2025 года стандартом является явное указание минимальных прав (`permissions: contents: read`) на уровне воркфлоу или задачи.
- **Secrets и Variables**: Разделение конфиденциальных данных (пароли, ключи) и нечувствительных настроек (URL, версии). Поддерживается иерархия: Organization → Repository → Environment.
- **OpenID Connect (OIDC)**: Рекомендуемый способ взаимодействия с облачными провайдерами (AWS, GCP, Azure, Yandex Cloud). Позволяет раннеру получать временные токены доступа без хранения долгоживущих секретов (Workload Identity).
- **Безопасность сторонних экшенов**: Использование коммитов (SHA) вместо тегов версий для защиты от подмены кода (Supply Chain Security).
- **Модель доверия Pull Requests**: Воркфлоу, запущенные из форков, получают read-only GITHUB_TOKEN и не имеют доступа к секретам репозитория — это защита от утечки через вредоносный PR. С июня 2026 года для недоверенных триггеров дополнительно включается режим read-only для кеша Actions.
- **Автоматический карантин подозрительных воркфлоу**: С июля 2026 года GitHub удерживает потенциально опасные изменения воркфлоу (например, меняющие критичные экшены) на модерации перед выполнением — дополнительный уровень защиты supply chain.

Детальная настройка секретов, OIDC и сетевой изоляции вынесена в специализированные разделы (см. ссылки в конце документа).

## Управление окружениями (Environments)

Окружения предоставляют дополнительные уровни контроля для процесса развертывания:
- **Protection Rules**: Правила, такие как ручное одобрение (Manual Approvals) от назначенных ревьюеров и таймеры ожидания.
- **Deployment Branches**: Ограничение запуска деплоя только из защищенных веток.
- **Deployment Protection Rules (Custom)**: Возможность интеграции внешних сервисов (например, Datadog или ServiceNow) для автоматической проверки готовности системы к деплою.

Минимальный пример использования окружения в задаче (правила защиты настраиваются в Settings → Environments):

```yaml
jobs:
  deploy-production:
    runs-on: ubuntu-latest
    environment:
      name: production        # Активирует все protection rules этого окружения
      url: https://app.example.com  # URL отобразится кнопкой в UI запуска
    steps:
      - run: ./deploy.sh
```

До начала выполнения такой задачи GitHub покажет её в состоянии Waiting и пришлет запрос на одобрение назначенным ревьюерам окружения.

## Практические сценарии

### Сценарий 1: Создание первого воркфлоу с нуля

Полный путь от пустого репозитория до работающего пайплайна:

```bash
# 1. Создать структуру каталогов (обязательный путь)
mkdir -p .github/workflows
# →

# 2. Создать файл воркфлоу (любое имя, расширение .yml/.yaml)
cat > .github/workflows/hello.yml <<'EOF'
name: Hello CI
on: push
jobs:
  greet:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Привет из ${{ github.repository }}"
EOF
# →

# 3. Закоммитить и запушить
git add .github/workflows/hello.yml
git commit -m "ci: добавить первый воркфлоу"
git push
# → Enumerating objects..., To github.com:owner/repo.git

# 4. Наблюдать за выполнением из CLI (gh CLI >= 2.0)
gh run watch
# → ✓ main · Hello CI · 1234567890: Succeeded 12s ago  (job greet ✓ 5s)
```

Предусловия: репозиторий уже связан с remote; для шага 4 установлен и авторизован GitHub CLI (`gh auth login`). Валидация: в веб-интерфейсе вкладка Actions показывает зеленую галочку у коммита, в логах задачи — строку вывода команды `echo`. Расширенные варианты триггеров и фильтров событий разбираются в разделе о событиях, задачах и шагах.

### Сценарий 2: Стандартный CI-пайплайн (Node.js 24)

Пример современного пайплайна (актуальность 2026 год) с использованием Node.js 24 и автоматического кеширования:

```yaml
name: Continuous Integration

on:
  push:
    branches: [ main, develop ]
  pull_request:

permissions:
  contents: read

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Setup Node.js
        uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: 'npm'

      - name: Install & Test
        run: |
          npm ci
          npm test
```

Разбор ключевых решений:

- `permissions: contents: read` — принцип минимальных привилегий: токену хватит только на чтение кода (см. раздел безопасности).
- `actions/checkout@v7` должен идти первым — setup-node рассчитывает хеш lock-файла для ключа кеша по рабочей копии.
- `cache: 'npm'` — встроенное кеширование каталога npm (~/.npm) по хешу package-lock.json; первый запуск даст Cache Miss и создаст кеш в Post-run фазе.
- `npm ci` вместо `npm install` — детерминированная установка строго по lock-файлу.

Валидация успешного выполнения: в логах шага Setup Node.js присутствует строка `Cache restored from key: Linux-npm-<hash>` (или `Cache not found` при первом прогоне), шаг Install & Test завершается кодом 0, у коммита появляется зеленая галочка.

### Сценарий 3: Матричная стратегия тестирования

Эффективный способ проверки совместимости на разных ОС и версиях инструментов:

```yaml
strategy:
  fail-fast: false
  matrix:
    os: [ubuntu-latest, windows-latest]
    node: [20, 22, 24]
```

Фрагмент выше разворачивается в 6 параллельных задач (декартово произведение). Встроенная в полный job форма:

```yaml
jobs:
  test:
    strategy:
      fail-fast: false        # Падение одного варианта не отменяет остальные
      max-parallel: 4         # Не более 4 задач матрицы одновременно
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: [20, 22, 24]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci && npm test
```

Примечание: Node.js 20 достиг конца поддержки 30 апреля 2026 года — строка оставлена в матрице сознательно как пример проверки обратной совместимости; для новых проектов начните список с 22. Исчерпывающая информация об exclude/include, лимитах матрицы и шардировании — в разделе о матричных сборках.

### Сценарий 4: Параллельные шаги внутри одной задачи (июнь 2026)

Нативный параллелизм шагов экономит время там, где раньше пришлось бы плодить отдельные задачи и передавать данные артефактами:

```yaml
jobs:
  build-all:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - name: Build frontend        # Фоновый шаг — не блокирует следующие
        background: true
        run: make build-frontend

      - name: Build backend         # Второй фоновый шаг — стартует сразу
        background: true
        run: make build-backend

      - name: Lint                  # Выполняется, пока идут обе сборки
        run: make lint

      - name: Wait for builds       # Барьер синхронизации
        wait-all:

      - name: Package               # Выполняется после обеих сборок
        run: make package
```

Паттерн «фоновый сервис + корректная остановка»:

```yaml
steps:
  - uses: actions/checkout@v7

  - name: Start local registry       # Долгоживущий процесс в фоне
    background: true
    run: docker run -d -p 5000:5000 registry:2

  - name: Push images                # Работает с живым сервисом
    run: ./push-to-local-registry.sh

  - name: Stop registry              # Явная остановка фоновой задачи
    cancel: Start local registry
```

Требования и валидация: функция доступна на всех актуальных раннерах (обновите self-hosted приложение раннера при необходимости); в UI каждый фоновый шаг отображается собственной группой логов, что решает проблему перемешивания вывода, свойственную shell-backgrounding через `&`. Если задача завершилась с ошибкой до `wait-all`, незавершенные фоновые шаги принудительно останавливаются вместе с задачей.

### Сценарий 5: CD-деплой с цепочкой задач, окружением и защитой от гонок

Соединяет `needs` (DAG задач), окружение с ручным одобрением и ограничитель конкурентности:

```yaml
name: Deploy

on:
  push:
    branches: [main]

concurrency:
  group: production-deploy           # Один активный деплой на группу
  cancel-in-progress: false          # Новый запуск ждет, а не отменяет текущий

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - run: make build
      - uses: actions/upload-artifact@v5
        with:
          name: app-bundle
          path: dist/

  deploy:
    needs: build                     # Запуск строго после успешной сборки
    runs-on: ubuntu-latest
    environment: production          # Protection rules: одобрение ревьюером
    steps:
      - uses: actions/download-artifact@v5
        with:
          name: app-bundle
          path: dist/
      - run: ./deploy.sh dist/
```

Логика выполнения: задача `build` и `deploy` никогда не идут параллельно (граф `needs`); повторный push в `main` во время одобрения поставит новый запуск в очередь группы `production-deploy`; после одобрения ревьюером в UI задача `deploy` стартует на чистом раннере и получает артефакт сборки. Валидация: в UI запуск имеет две задачи, вторая находится в статусе Waiting until reviewed до подтверждения окружения.

## Устранение типичных проблем

| Симптом | Частая причина | Решение |
| :--- | :--- | :--- |
| Воркфлоу не запускается после пуша | Файл не в `.github/workflows/`, невалидный YAML или фильтры `on:` не совпадают с веткой | Проверить путь/отступы (`yamllint`); сверить фильтры `branches`/`paths` с реальным рефом |
| Задача висит в Queued | Нет свободных раннеров под метку `runs-on`; исчерпан лимит конкурентности организации; превышен лимит параллельных задач тарифа | Проверить доступность раннеров в Settings → Actions → Runners; пересмотреть `runs-on` или concurrency-группы |
| `Resource not accessible by integration` | GITHUB_TOKEN не хватает прав на действие | Добавить нужное право в блок `permissions` (минимально необходимое) |
| Изменения воркфлоу из PR «не применяются» | Для `pull_request` берется версия воркфлоу из базовой ветки, а не из PR | Понимать: синтаксис триггера читается из base; сам код шагов исполняется из merge-коммита PR |
| Шаг падает только на форкнутых PR | Форк-модель безопасности: нет секретов, read-only токен | Вынести привилегированную работу в отдельные события (`pull_request_target`) с осторожностью или в post-merge воркфлоу |
| Фоновый шаг (июнь 2026) не найден по имени в `wait`/`cancel` | Опечатка в имени или шаг не помечен `background: true` | Имя в `wait`/`cancel` должно точно совпадать с `name` фонового шага |

Диагностика любого сбоя начинается с чтения логов конкретной задачи во вкладке Actions; для пошаговой трассировки установите секрет `ACTIONS_STEP_DEBUG: true`.

## Лучшие практики

1. **Пинуйте версии экшенов** на мажорный тег (`@v7`) минимум, на SHA — для критичных внешних экшенов.
2. **Минимальные permissions** в каждом воркфлоу; расширяйте права точечно на уровне задачи.
3. **Явные версии раннеров** (`ubuntu-24.04`) в продакшен-пайплайнах; `-latest` допустим в экспериментах.
4. **Быстрый фидбек**: тяжелые проверки — в конце DAG или параллельно (`needs` + матрица + параллельные шаги), чтобы разработчик быстрее видел ошибки.
5. **Именуйте шаги** осмысленно: имена попадают в аннотации, UI и используются ссылками `steps.<id>`.
6. **Чистота истории запусков**: отключайте неиспользуемые воркфлоу (Settings → Actions), настраивайте retention артефактов и удаляйте устаревшие workflow-файлы — они перестают выполняться сразу после удаления из ветки.
