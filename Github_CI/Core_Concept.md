# GitHub Actions: Ключевые концепции

**GitHub Actions** — встроенная в GitHub платформа для автоматизации полного жизненного цикла разработки ПО, реализующая подходы CI/CD (Continuous Integration / Continuous Deployment — непрерывная интеграция и непрерывное развертывание). Основная идея платформы — «автоматизация как код»: все сценарии описываются в YAML-файлах (Yet Another Markup Language), хранятся непосредственно в репозитории и запускаются в ответ на определенные события.

## Определения

- **Workflow (Рабочий процесс)**: Автоматизированный сценарий, состоящий из одной или нескольких задач (`jobs`). Конфигурация описывается в `.yml` файле и хранится в директории `.github/workflows`.
- **Event (Событие)**: Триггер, инициирующий запуск рабочего процесса. Примеры: `push` в ветку, создание запроса на слияние (`pull request`), запуск по расписанию (`schedule`), вызов через API (Application Programming Interface) или вручную (`workflow_dispatch`).
- **Job (Задача)**: Набор шагов (`steps`), выполняемых в рамках одной среды исполнения (`runner`). Задачи могут выполняться параллельно или последовательно при наличии настроенных зависимостей.
- **Step (Шаг)**: Отдельная атомарная операция: выполнение shell-команды или запуск действия (`action`). Шаги внутри одной задачи выполняются строго последовательно.
- **Action (Действие)**: Переиспользуемый компонент, выполняющий конкретную задачу (например, проверка кода или деплой). Можно создавать свои действия или использовать готовые из [GitHub Marketplace](https://github.com/marketplace?type=actions).
- **Runner (Исполнитель)**: Среда выполнения (сервер), на которой запускаются задачи. GitHub предоставляет готовые виртуальные машины (GitHub-hosted) или позволяет подключать собственные мощности (self-hosted).

## Основные концепции

### Модель выполнения

1. **Событие**: Возникает триггер (например, `git push`).
2. **Инициализация**: GitHub Actions идентифицирует соответствующий файл рабочего процесса.
3. **Выделение ресурсов**: Для каждой задачи (`job`) подготавливается изолированная среда исполнения (`runner`).
4. **Выполнение шагов**: Исполнитель последовательно выполняет все описанные в задаче шаги.
5. **Завершение**: После выполнения всех задач выделенные ресурсы (для GitHub-hosted) уничтожаются.

### Автоматизация как код

Хранение конфигурации автоматизации вместе с исходным кодом проекта обеспечивает:

- **Версионирование**: Изменения в процессах отслеживаются через Git.
- **Прозрачность**: Конфигурация доступна всей команде для аудита и правок.
- **Воспроизводимость**: Пайплайны привязаны к конкретному состоянию кода (коммиту).

### Типы исполнителей (Runners)

**Облачные исполнители (GitHub-hosted runners)**:

- Полностью обслуживаются GitHub.
- Используют актуальные образы ОС (Operating System): Ubuntu, Windows, macOS.
- Гарантируют чистоту окружения (свежая VM для каждой задачи).
- Тарифицируются поминутно (бесплатно для публичных репозиториев).

**Собственные исполнители (Self-hosted runners)**:

- Разворачиваются в локальной инфраструктуре или частном облаке (VPC — Virtual Private Cloud).
- Предоставляют полный контроль над конфигурацией и доступом к сети.
- Позволяют экономить лимиты минут для приватных репозиториев.
- Требуют самостоятельного обновления и обслуживания.

**Actions Runner Controller (ARC)**:

- Решение на базе Kubernetes для управления собственными исполнителями.
- Обеспечивает автоматическое масштабирование и изоляцию через эфемерные (временные) контейнеры.

### Безопасность

- **GITHUB_TOKEN**: Временный токен, автоматически создаваемый для каждого запуска. Его права доступа должны быть ограничены минимально необходимыми через директиву `permissions`.
- **OpenID Connect (OIDC)**: Механизм безопасной аутентификации в облачных провайдерах (Amazon Web Services, Google Cloud Platform, Microsoft Azure) без использования долгосрочных секретов.
- **Secrets (Секреты)**: Зашифрованные переменные для хранения чувствительных данных (пароли, ключи). Они не отображаются в логах и могут настраиваться на разных уровнях (репозиторий, организация, окружение).

## Практические сценарии

### Базовый пайплайн непрерывной интеграции

Пример рабочего процесса для Node.js с автоматическим кешированием зависимостей:

```yaml
name: CI

on:
  push:
    branches: [ main ]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test
```

### Матричные сборки

Запуск тестов одновременно на нескольких версиях платформы:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm test
```
