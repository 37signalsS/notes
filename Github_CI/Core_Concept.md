# GitHub Actions: Ключевые концепции

**GitHub Actions** — это встроенная в GitHub платформа для автоматизации полного жизненного цикла разработки ПО (CI/CD). Её основная идея — «автоматизация как код»: все сценарии описываются в YAML-файлах, хранятся в репозитории и запускаются в ответ на события.

## Определения

- **[Workflow (Рабочий процесс)](./Workflow_Syntax.md)**: Автоматизированный сценарий, состоящий из одной или нескольких задач (`jobs`). Описывается в `.yml` файле в директории `.github/workflows`.
- **[Event (Событие)](./Events_Jobs_Steps.md)**: Триггер, который запускает workflow. Например: `push` в ветку, создание `pull request` или запуск по расписанию.
- **[Job (Задача)](./Events_Jobs_Steps.md)**: Набор шагов (`steps`), который выполняется на одной среде исполнения (`runner`). Задачи могут выполняться параллельно или последовательно.
- **[Step (Шаг)](./Events_Jobs_Steps.md)**: Отдельная команда или действие (`action`). Шаги внутри одной задачи выполняются последовательно.
- **[Action (Действие)](./Marketplace_Actions.md)**: Переиспользуемый компонент, который можно подключить в шаге. Это может быть простая shell-команда или готовый модуль из Marketplace.
- **[Runner (Исполнитель)](./Environment_Limitations.md)**: Cреда выполнения для задач. GitHub предоставляет готовые виртуальные машины или позволяет использовать собственные (self-hosted).

## Основные концепции

### Модель выполнения

1. **Событие**: Происходит триггер (например, `git push`).
2. **Запуск Workflow**: GitHub Actions находит соответствующий workflow-файл.
3. **Выделение Runner'а**: Для каждой задачи (`job`) выделяется свежая виртуальная среда (`runner`).
4. **Выполнение Job**: Runner последовательно выполняет шаги (`steps`) задачи.
5. **Завершение**: После выполнения всех задач runner уничтожается.

Эта модель обеспечивает изоляцию и чистоту окружения для каждой задачи.

### Автоматизация как код

Хранение конфигурации CI/CD вместе с кодом (`.github/workflows/ci.yml`) дает ключевые преимущества:

- **Версионирование**: Изменения в пайплайнах отслеживаются через Git.
- **Прозрачность**: Любой участник команды может видеть и предлагать улучшения для процессов автоматизации.
- **Воспроизводимость**: Конфигурация привязана к конкретному коммиту.

## Практические сценарии

### Минимальный CI-пайплайн

Этот пример workflow запускается при каждом `push` в ветку `main`, устанавливает Node.js, кеширует зависимости и запускает тесты.

```yaml
name: CI

on:
  push:
    branches: [ main ]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: 1. Получение кода из репозитория
        uses: actions/checkout@v4

      - name: 2. Настройка Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: 3. Установка зависимостей
        run: npm ci

      - name: 4. Запуск тестов
        run: npm test
```

Этот базовый шаблон является основой для большинства CI-процессов.
