# Основная идея GitHub Actions

GitHub Actions — это событийно-ориентированный механизм автоматизации, встроенный в экосистему GitHub. Главный принцип: любое событие в репозитории может запускать заранее описанный сценарий (workflow), который выполняет набор задач (jobs и steps) на выделенных исполнителях (runners). Это позволяет описать процессы CI/CD и сопутствующую автоматизацию в виде декларативных файлов в репозитории, рядом с кодом.

## Архитектура и терминология

*   **Событие (event):** триггер запуска. Примеры: push, pull_request, release, schedule (cron), workflow_dispatch (ручной запуск), repository_dispatch (внешний вызов).
*   **Workflow:** файл в .github/workflows/*.yml, описывающий, что и при каких условиях выполнять.
*   **Job:** группа шагов, исполняемая на одном runner. Jobs по умолчанию изолированы и могут идти параллельно; их порядок задается через needs.
*   **Step:** элементарный шаг внутри job: shell-команда или вызов готовой action.
*   **Action:** переиспользуемый модуль шага. Бывает трёх типов: JavaScript action, Docker action и Composite action.
*   **Runner:** среда исполнения job. Доступны GitHub-hosted (ubuntu-latest, windows-latest, macos-latest) и self-hosted (собственные машины).
*   **Контексты и выражения:** доступ к данным о запуске (github, env, secrets, inputs) через синтаксис ${{ ... }}.

Таблица соответствий понятий:

| Понятие | Роль |
| :--- | :--- |
| Event | Определяет, когда запускать workflow |
| Workflow | Верхнеуровневая схема автоматизации |
| Job | Единица параллелизма и изоляции |
| Step | Конкретное действие внутри job |
| Action | Повторно используемый строительный блок |
| Runner | Исполнительная среда |
| Context/Secrets| Данные о запуске и секреты доступа |

## Модель исполнения

При наступлении события GitHub планирует запуск workflow. Каждая job назначается на runner с указанной ОС. Steps внутри job выполняются последовательно, обмениваясь артефактами через файловую систему runner’а. Для передачи данных между job’ами используются артефакты (upload/download) или outputs. Масштабирование достигается матричной стратегией: один шаблон job запускается с разными параметрами.

Права доступа управляются через встроенный GITHUB_TOKEN и блок permissions в workflow. Ограничение конкуренции (concurrency) предотвращает одновременные запуски одного и того же сценария для одной ветки.

## Минимальный пример workflow

Ниже показан типичный workflow, запускающийся на push и по кнопке. Он собирает и тестирует проект на нескольких версиях Node.js, кеширует зависимости и отменяет конкурирующие запуски для одной ветки.

```yaml
name: CI

on:
  push:
    branches: [ main ]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build-test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [18, 20]
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}

      - name: Cache npm
        uses: actions/cache@v4
        with:
          path: ~/.npm
          key: npm-${{ runner.os }}-${{ matrix.node }}-${{ hashFiles('**/package-lock.json') }}
          restore-keys: |
            npm-${{ runner.os }}-${{ matrix.node }}-

      - name: Install
        run: npm ci

      - name: Test
        run: npm test --ci
```

## Ключевые особенности

*   Хранение конфигурации в репозитории обеспечивает версионирование и прозрачность изменений.
*   Богатая экосистема готовых actions ускоряет внедрение типовых задач: checkout, настройка языков, публикация артефактов, контейнеризация.
*   Гибкая оркестрация: параллельные job’ы, матрицы, зависимые цепочки через needs.
*   Управление безопасностью: секреты, минимально необходимые permissions, детализированные контексты.
*   Универсальность триггеров: поддержка событий GitHub, расписаний, ручных запусков и внешних интеграций.
