# GitHub Actions: Готовые действия и Marketplace

Готовые действия (`actions`) — это переиспользуемые блоки автоматизации, составляющие основу экосистемы GitHub Actions. Они позволяют использовать проверенные решения для типовых задач, сокращая время на разработку и поддержку процессов CI/CD (Continuous Integration / Continuous Deployment — непрерывная интеграция и непрерывное развертывание).

## Определения

- **Action (Действие)**: Автономный, переиспользуемый программный компонент, который можно встроить как отдельный шаг (`step`) в задачу (`job`).
- **GitHub Marketplace**: Централизованный публичный реестр для поиска, обмена и публикации готовых действий.

## Основные концепции

### Типы действий

Существует три основных типа реализации действий:

1. **JavaScript Action**: Выполняется непосредственно в среде исполнителя (`runner`) с использованием Node.js. Это наиболее производительный и распространенный тип.
2. **Docker Action**: Запускается внутри изолированного Docker-контейнера. Гарантирует идентичность окружения, но имеет накладные расходы на запуск контейнера.
3. **Composite Action**: Объединяет несколько шагов рабочего процесса в один компонент. Позволяет создавать сложные цепочки автоматизации без написания кода на JavaScript или создания Docker-образов.

### Выбор и версионирование

При выборе действий из [GitHub Marketplace](https://github.com/marketplace?type=actions) следует учитывать активность сообщества, наличие открытого исходного кода и репутацию автора.

**Стратегии версионирования:**

- **Мажорный тег** (например, `uses: actions/checkout@v4`): Рекомендуемый способ. Обеспечивает получение исправлений безопасности и минорных обновлений без риска поломки пайплайна.
- **Хеш коммита** (например, `uses: actions/checkout@5a4ac90...`): Максимальный уровень безопасности и стабильности, защищающий от подмены тега.
- **Ветка** (например, `uses: actions/checkout@main`): Не рекомендуется для производственных сред, так как код может измениться в любой момент.

### Безопасное использование

1. **Минимизация привилегий**: Всегда настраивайте секцию `permissions` для ограничения прав `GITHUB_TOKEN` (например, `contents: read`).
2. **Контроль трафика**: Используйте инструменты мониторинга, такие как **[Harden-Runner](./network-security.md)**, для защиты от утечки секретов на сторонние ресурсы.
3. **Аудит исходного кода**: Перед внедрением нового действия проверяйте его код на наличие подозрительных сетевых вызовов или некорректной обработки секретов.
4. **Риски `pull_request_target`**: Будьте осторожны при использовании этого триггера, так как он запускается в контексте базовой ветки и имеет доступ к секретам репозитория, что может быть использовано при атаках через вредоносные PR (Pull Request).

### Параметры входа и выхода

- **Входы (`with`)**: Позволяют передавать настройки и данные в действие.
- **Выходы (`outputs`)**: Позволяют действию передавать результаты своей работы следующим шагам. Для доступа к результатам шагу необходимо присвоить уникальный идентификатор (`id`).

## Практические сценарии

### Использование популярных действий в CI-пайплайне

Пример настройки рабочего процесса с использованием официальных действий:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read # Ограничение прав только чтением кода
    steps:
      # 1. Действие для загрузки исходного кода
      - name: Checkout code
        uses: actions/checkout@v4

      # 2. Действие для настройки окружения со встроенным кешированием
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm' # Использование встроенного кеширования зависимостей

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test
```

Использование встроенных механизмов кеширования в `setup-*` действиях является предпочтительным методом оптимизации.
