# GitHub Actions: Готовые Действия (Actions) и Marketplace

Готовые действия (`actions`) — это переиспользуемые блоки автоматизации, которые являются основой экосистемы GitHub Actions. Они позволяют не изобретать велосипед для типовых задач, таких как развертывание, настройка рантаймов или отправка уведомлений.

## Определения

- **Action (Действие)**: Инкапсулированный, переиспользуемый скрипт, который можно встроить как шаг (`step`) в задачу (`job`).
- **GitHub Marketplace**: Централизованный репозиторий, где можно найти и опубликовать готовые `actions`.
- **JavaScript Action**: `Action` на Node.js, который выполняется непосредственно на `runner`. Это самый быстрый и распространенный тип.
- **Docker Action**: `Action`, который запускается внутри Docker-контейнера. Обеспечивает максимальную изоляцию и кастомное окружение, но работает медленнее из-за необходимости сборки/загрузки образа.
- **Composite Action**: `Action`, который объединяет несколько шагов (`steps`) в один. Позволяет создавать более сложные и читаемые `actions` без необходимости писать код на JS или использовать Docker.

## Основные концепции

### Выбор и Версионирование

Правильный выбор и фиксация версии `action` — ключ к стабильным пайплайнам.

- **Поиск**: Основной источник — [GitHub Marketplace](https://github.com/marketplace?type=actions). Критерии выбора: популярность, активность поддержки, открытость исходного кода.
- **Версионирование**: `Action` можно подключать по тегу, ветке или хешу коммита.
  - `uses: actions/checkout@v4` — Рекомендуемый способ. Использует мажорный тег, получает исправления, но не ломающие изменения.
  - `uses: actions/checkout@main` — Нестабильно. Использует последнюю версию из ветки `main`, может сломаться в любой момент.
  - `uses: actions/checkout@3df4f17a7b...` — Максимальная стабильность. Жесткая привязка к конкретному коммиту. Используется в критически важных системах.

### Безопасное Использование

Подключение стороннего кода требует осторожности.

1. **Ограничивайте права**: Всегда используйте секцию `permissions` на уровне `job` или `workflow`, чтобы выдать `GITHUB_TOKEN` только минимально необходимые права.
2. **Изучайте исходный код**: Перед использованием `action` просмотрите его код на предмет подозрительных сетевых вызовов или работы с секретами.
3. **Не используйте `actions` в `pull_request` от форков без разбора**: Событие `pull_request_target` имеет доступ к секретам, и вредоносный PR может их похитить.

### Входы и Выходы (`with` и `outputs`)

- **`with`**: Позволяет передавать параметры (входные данные) в `action`.
- **`outputs`**: Позволяет `action` возвращать результат. Для доступа к нему шагу нужно присвоить `id`, после чего его `outputs` будут доступны через контекст `steps`.

## Практический сценарий: Кэширование зависимостей

Этот пример использует три популярных `action` для настройки CI-пайплайна.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read # Даем права только на чтение кода
    steps:
      # 1. Action для клонирования репозитория
      - name: Checkout code
        uses: actions/checkout@v4

      # 2. Action для настройки Node.js, принимает 'node-version' и 'cache' как входы
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      # 3. Action для кэширования, принимает 'path' и 'key'
      - name: Get cached dependencies
        id: cache-npm # Присваиваем ID для доступа к outputs
        uses: actions/cache@v4
        with:
          path: ~/.npm
          key: npm-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}

      # Шаг `if` использует output `cache-hit` из шага с id `cache-npm`
      - name: Notify on cache hit
        if: steps.cache-npm.outputs.cache-hit == 'true'
        run: echo "Cache restored successfully!"

      - name: Install dependencies
        run: npm ci
```
