# GitHub Actions: Сетевая безопасность и контроль трафика

Контроль сетевого взаимодействия исполнителей (runners) является критическим компонентом безопасности CI/CD пайплайнов. Он позволяет устранить «слепую зону» в инфраструктуре автоматизации, предотвращая несанкционированную утечку секретов (Exfiltration) и защищая процесс сборки от компрометации через внешние зависимости (Supply Chain Security).

## Определения

- **Egress Policy (Политика исходящего трафика)**: Набор декларативных правил, определяющих разрешенные внешние эндпоинты (FQDN/IP) и порты для процесса сборки.
- **Harden-Runner**: Инструмент безопасности от Step Security для мониторинга сетевой активности и применения Runtime-политик на GitHub-hosted исполнителях.
- **DNS Filtering**: Механизм блокировки запросов к подозрительным или неавторизованным доменам на уровне резолвера.
- **OpenID Connect (OIDC)**: Протокол федеративной аутентификации, позволяющий раннерам получать временные токены доступа к облачным ресурсам без использования статических паролей через сеть.
- **Private Networking**: Возможность интеграции GitHub раннеров в частные виртуальные сети (VPC/VNet) для доступа к защищенным внутренним ресурсам.
- **Allowlist (Белый список)**: Подход к фильтрации, при котором разрешен только явно перечисленный трафик, а все остальное блокируется по умолчанию (default deny); противоположность blacklist-подхода.
- **IMDS (Instance Metadata Service)**: Внутренний сервис облачного провайдера (например, `169.254.169.254` в AWS/Azure), выдающий виртуальной машине ее учетные данные и конфигурацию; главная цель атакующего, получившего выполнение кода на облачном раннере.
- **Policy Store**: Централизованное хранилище политик Harden-Runner, позволяющее применять egress-правила ко всем задачам без изменения файлов воркфлоу (`use-policy-store: true`).

## Основные концепции

### Задачи контроля сетевого трафика

1.  **Предотвращение утечки данных (Data Exfiltration)**: Блокировка попыток вредоносного ПО отправить секреты (токены, ключи) на командные серверы (C2).
2.  **Защита цепочки поставок (Supply Chain Security)**: Гарантия того, что `npm install`, `pip install` и другие менеджеры пакетов обращаются только к доверенным зеркалам и реестрам.
3.  **Изоляция сред выполнения**: Разграничение доступа к сетевым ресурсам между тестовыми, сборочными и деплой-задачами.

### Ограничения платформы по умолчанию

Прежде чем выбирать механизм защиты, важно понимать, что дает сама платформа:

- **Стандартные GitHub-hosted раннеры** работают со *всем открытым* исходящим трафиком. Встроенных средств egress-фильтрации (групп безопасности, NSG) для них не существует — контроль возможен только средствами уровня ОС на стороне инструмента мониторинга.
- Предустановленная защита: образы раннеров содержат файл `/etc/hosts`, перенаправляющий на `localhost` пулы криптовалютного майнинга и известные вредоносные сайты (MiningMadness.com, cpu-pool.com и другие).
- Прозрачность окружения: GitHub публикует SBOM (список предустановленного ПО) для каждого релиза образа в репозитории `actions/runner-images` (файлы вида `sbom.IMAGE-NAME.json.zip`) — их можно прогонять через сканеры уязвимостей и включать в собственную ведомость компонентов.
- Полный сетевой контроль достижим тремя путями: Larger Runners с приватной сетью (см. ниже), self-hosted раннеры за собственным файрволом либо runtime-агенты вроде Harden-Runner.

### Механизмы защиты исходящего трафика (Egress Control)

На GitHub-hosted исполнителях по умолчанию разрешен весь исходящий трафик. Для ограничения используются два основных подхода:

- **Runtime Monitoring (Harden-Runner)**: Перехват системных вызовов (syscalls) на уровне ОС для анализа сетевых соединений в реальном времени.
- **Белые списки (Allowlists)**: Декларативное описание всех необходимых для сборки внешних ресурсов. Любой запрос вне списка приводит к немедленной остановке пайплайна.

Эти подходы комбинируются: сначала политика запускается в режиме аудита (`audit`) для построения базовой линии соединений, затем переключается в блокирующий режим (`block`) с автоматически сгенерированным списком разрешенных эндпоинтов.

### Сетевые требования к соединениям

При настройке файрвола вокруг раннера (особенно self-hosted за корпоративным периметром) необходимо разрешить коммуникацию с обязательными эндпоинтами GitHub. Соединение с платформой всегда выполняется по HTTPS (порт 443):

| Назначение | Домены |
| :--- | :--- |
| Базовые операции (регистрация, джобы) | `github.com`, `api.github.com`, `*.actions.githubusercontent.com` |
| Скачивание экшенов | `codeload.github.com` |
| Логи, summaries, артефакты, кеш | `results-receiver.actions.githubusercontent.com`, `*.blob.core.windows.net` |
| Обновления версии раннера | `objects.githubusercontent.com`, `objects-origin.githubusercontent.com`, `github-releases.githubusercontent.com`, `github-registry-files.githubusercontent.com` |
| Получение OIDC-токенов | `*.actions.githubusercontent.com` |
| GitHub Packages | `*.pkg.github.com`, `pkg-containers.githubusercontent.com`, `ghcr.io` |
| Git LFS | `github-cloud.githubusercontent.com`, `github-cloud.s3.amazonaws.com` |

Нюансы:
- Некоторые домены настроены через `CNAME`; отдельным файрволам требуется рекурсивное добавление всех записей, а сами `CNAME` могут меняться — стабильны только перечисленные домены верхнего уровня.
- Актуальный список IP-диапазонов раннеров возвращается ключом `actions` в ответе REST API `GET /meta` (например, `curl -s https://api.github.com/meta`); список обновляется **раз в неделю**. Windows и Ubuntu раннеры хостятся в Azure (диапазоны совпадают с датацентрами Azure), macOS — в собственном облаке GitHub.
- Официальная рекомендация: **не использовать** эти диапазоны как allowlist для внутренних ресурсов — их слишком много и они меняются еженедельно. Для стабильного входящего файрвола применяйте Larger Runners со статическими IP или self-hosted раннеры.

### Интеграция с частными сетями (Private Networking)

Для организаций с высокими требованиями к комплаенсу (SOC2, PCI-DSS) GitHub предлагает:

- **VPC Peering / Private Links**: Подключение **Larger Runners** к корпоративным сетям в AWS или Azure. Трафик при этом не выходит в публичный интернет.
- **Static IP Addresses**: Использование фиксированных IP-адресов для раннеров организации, что позволяет настраивать правила файрвола на стороне корпоративных БД и API.
- **Self-hosted Runners в DMZ**: Развертывание собственных раннеров за корпоративным прокси-сервером.

#### Приватная сеть Azure для GitHub-hosted раннеров

Функция доступна на планах Team/Enterprise Cloud (только GitHub Enterprise Cloud) и является GA. Ключевые характеристики:

- **Поддерживаемые раннеры**: Ubuntu и Windows Larger Runners от 2 до 64 vCPU. **macOS не поддерживается** (как и статические IP для macOS-раннеров).
- **Механизм работы**: При запуске задачи сервис GitHub развертывает сетевой интерфейс (NIC) раннера непосредственно в вашей подсети VNet. Все политики сети VNet (NSG, маршруты, файрвол) автоматически применяются к раннеру — включая полный контроль исходящего трафика и наблюдение за сетевыми логами.
- **Входящий трафик**: GitHub никогда не требует входящих соединений к таким машинам, но по умолчанию Azure пропускает трафик внутри VNet (`AllowVNetInBound`). Рекомендуется явно заблокировать все входящие подключения правилами NSG.
- **Размер подсети**: Рекомендуется буфер +30% к максимальной параллельности задач (Azure резервирует 5 адресов подсети): `/24` — примерно 193 раннера, `/26` — около 45.
- **Ограничение совместимости**: Приватная сеть **не поддерживает статические IP** одновременно — используется динамическая адресация. Стабильный внешний egress-IP обеспечивается отдельно: NAT Gateway, Azure Firewall или Load Balancer с outbound-правилами.
- **Важно для планирования**: Azure выводит из эксплуатации default outbound access **31 марта 2026 года** — подсетям с такими раннерами потребуется явный метод исходящей связи.
- **Отказоустойчивость**: VNET failover (публичная превью-функция) позволяет указать вторичную подсеть, опционально в другом регионе, для переключения трафика при региональном сбое.
- **Автоматизация**: REST API для управления раннерами и сетевыми конфигурациями доступны в статусе GA с января 2025 года.
- Типичный подводный камень: при нулевом лимите расходов (spending limit $0) организации такие раннеры просто не запускаются.

#### Статические IP-адреса

Статические IP доступны только для Larger Runners уровня организации/предприятия. Они решают задачу «обратного» файрвола: корпоративная БД или внутренний API открывает доступ одному фиксированному адресу вместо широких облачных диапазонов.

### Безопасность через OIDC и Workload Identity

OIDC устраняет необходимость передачи чувствительных учетных данных через сеть в открытом или зашифрованном виде внутри секретов GitHub.
- **Принцип работы**: Раннер запрашивает JWT-токен у GitHub (Issuer), который затем обменивается на временные права доступа в облаке (AWS/GCP/Azure/Yandex Cloud).
- **Сетевой аспект**: Весь обмен токенами происходит через защищенные каналы с использованием TLS и проверкой идентичности воркфлоу. Запрос токена идет к эндпоинту `*.actions.githubusercontent.com` (переменная `ACTIONS_ID_TOKEN_REQUEST_URL`), поэтому этот домен должен быть открыт в файрволе.
- **Требование к воркфлоу**: право `permissions: id-token: write`.
Полная настройка доверия, claims и примеры для конкретных облаков описаны в разделе [Управление секретами](./secrets_management.md).

### Харденинг self-hosted раннеров

Self-hosted раннеры не дают гарантий эфемерности: скомпрометированная задача сохраняет персистентный доступ к машине, секретам и сети. Сетевой аспект харденинга:

- **Публичные репозитории**: использование self-hosted раннеров практически исключено — любой пользователь может открыть PR и получить выполнение кода на вашем хосте. Для приватных репозиторий риск сохраняется у всех, кто умеет форкать.
- **Группы раннеров**: ограничивают радиус поражения — раннеры организации/предприятия могут получать задачи из нескольких репозиториев, поэтому их распределяют по группам с явными списками доступа.
- **Метаданные облака**: раннер с доступом к IMDS (AWS/Azure/GCP metadata) позволяет укравшему секреты коду запросить роль самой VM (пример атаки и защиты — Сценарий 5).
- **Утечка через аргументы команд**: даже эфемерные раннеры опасно переиспользовать между задачами — секреты, переданные аргументами командной строки, видны следующей задаче через `ps x -w`.
- **Just-in-time (JIT) раннеры**: REST API создает конфигурацию одноразового раннера, который выполняет максимум одну задачу и самоудаляется; запуск — `./run.sh --jitconfig ${encoded_jit_config}`.
- **Минимальная версия агента**: GitHub принудительно требует актуальные версии приложения раннера (политика minimum version enforcement) — устаревшие агенты перестают подключаться.

### Harden-Runner: возможности и уровни

Harden-Runner работает как EDR для CI: агент (eBPF-мониторинг на Linux) коррелирует сетевые события, записи файлов и процессы с шагами задачи. Актуальная линейка версий — v2.x (релизы иммутабельны и подписаны GitHub):

- **Community (бесплатный) уровень**:
  - Мониторинг egress в режимах `audit` и `block` с allowlist-доменами;
  - Автоматическое построение базовой линии соединений по прошлым запускам и детект аномалий;
  - **Global Block List**: список известных вредоносных доменов и IP, поддерживаемый SOC Step Security; обновляется автоматически без смены версии экшена и действует **даже в режиме `audit`**;
  - Детектирование несанкционированного изменения исходного кода во время сборки;
  - Отчеты в Job Summary со ссылкой на Process Monitor View (сеть/файлы/процессы по шагам).
- **Enterprise уровень** (платно): поддержка self-hosted раннеров и приватных репозиториев, интеграция GitHub Checks (изменение базовой линии ломает проверку), мониторинг HTTPS-вызовов GitHub API с рекомендацией минимальных прав `GITHUB_TOKEN`, трекинг каждого записанного файла, запрещающие списки (`denied endpoints`, например блокировка публичных реестров пакетов).
- **Совместимость**: режим блокировки исторически работал только на Linux — начиная с v2.20.0 поддерживаются также Windows и macOS GitHub-hosted раннеры. Сторонние провайдеры раннеров (Depot, Blacksmith, Namespace, WarpBuild — с v2.19.0; Bitrise — с v2.20.0; AWS CodeBuild — с v2.20.1) используют тот же синтаксис.
- **Известное ограничение**: раннер-лейбл `ubuntu-slim` (одноконтейнерная среда без привилегий) **не поддерживается** агентом — мониторинг внутри непривилегированного контейнера невозможен.
- **История уязвимостей самого инструмента** (важно для выбора версии): обход egress-блокировки через DNS-over-TCP (CVE-2026-32946) и туннелирование данных через DNS-over-HTTPS к разрешенным ресолверам (CVE-2026-32947) исправлены в v2.16.0; обход опции `disable-sudo` через группу docker исправлен в v2.12.0. Версии ниже 2.16.0 использовать в блокирующем режиме небезопасно.

## Практические сценарии

### Сценарий 1: Внедрение Harden-Runner в режиме блокировки

Этот сценарий обеспечивает максимальный уровень защиты, разрешая доступ только к необходимым ресурсам.

```yaml
jobs:
  secure-build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - name: Harden Runner
        uses: step-security/harden-runner@v2
        with:
          egress-policy: block
          allowed-endpoints: >
            github.com:443
            api.github.com:443
            registry.npmjs.org:443
            auth.docker.io:443
            production.cloudflare.docker.com:443

      - name: Checkout
        uses: actions/checkout@v7
        
      - name: Build
        run: npm ci && npm run build
```

Разбор решений: экшен ставится **первым шагом** задачи — агент должен начать мониторинг до выполнения любого другого кода. Список эндпоинтов покрывает цепочку сборки Node.js-проекта: реестр npm (`registry.npmjs.org`), аутентификация Docker Hub (`auth.docker.io`) и его CDN (`production.cloudflare.docker.com`); домены `github.com`/`api.github.com` нужны самой платформе. Формат записей — `домен:порт`; wildcard-домены поддерживаются (`*.blob.core.windows.net:443`).

Валидация: при попытке любого процесса соединиться с незанесенным адресом задача упадет, а в логе шага Harden Runner появится заблокированный endpoint. Рабочий процесс внедрения: сначала запустите задачу с `egress-policy: audit` на нескольких прогонах, откройте вкладку Recommended Policy в дашборде Step Security (агрегированный по запускам список) и перенесите её в `allowed-endpoints` — это исключает ложные блокировки. Для продакшена фиксируйте версию по SHA: `step-security/harden-runner@05e31511f85b41b11d1cf0ef85d0992719546e2c # v2.21.0` (см. [обзор Marketplace](./Marketplace_Actions.md)).

### Сценарий 2: Настройка доступа через корпоративный прокси (Self-hosted)

Для раннеров, находящихся за корпоративным файрволом, требуется настройка переменных окружения для корректной работы экшенов и инструментов.

```bash
# Настройка окружения на хосте раннера (.env или системные переменные)
http_proxy=http://proxy.internal.corp:8080
https_proxy=http://proxy.internal.corp:8080
no_proxy=localhost,127.0.0.1,.internal.corp,github.com
```

Два способа задания конфигурации:
1. **Файл `.env`** в директории установки приложения раннера — рекомендуемый вариант для раннеров, работающих как системная служба; переменные читаются при старте агента. На GitHub-hosted раннерах этот способ недоступен.
2. **Системное окружение**: `export` перед первым запуском либо запись в `/etc/environment` (Linux/macOS) или `[Environment]::SetEnvironmentVariable("https_proxy", "...", "Machine")` / `netsh winhttp set advproxy` (Windows) для персистентности.

Критичные нюансы:
- Переменные читаются **только при старте** приложения раннера: после изменения конфигурации службу нужно перезапустить.
- На Linux/macOS приоритет у имен в нижнем регистре (`https_proxy`), если заданы оба варианта; на Windows регистр не важен.
- В `no_proxy` self-hosted раннеры **не поддерживают IP-адреса и CIDR** — только имена хостов.
- Учетные данные прокси со спецсимволами (`!`, `%`, `@`) вызывают ошибку `URI malformed` — пароль необходимо URL-кодировать.
- Для Docker-контейнеров (container actions, service containers) прокси настраивается отдельно — через drop-in конфигурацию демона Docker.
- Для раннеров в Azure добавьте в `no_proxy` адреса служб Azure: `168.63.129.16` и IMDS `169.254.169.254`.

Валидация: перезапустите службу раннера (`systemctl restart actions.runner.<org>-<repo>.<name>.service`), затем в задаче выполните `curl -v https://httpbin.org/ip` — в логе curl должна появиться строка вида `* Uses proxy env variable HTTPS_PROXY = 'proxy.internal.corp:8080'`, а в ответе — внешний IP прокси, а не хоста раннера.

### Сценарий 3: Защита DNS и блокировка вредоносных доменов

Использование `harden-runner` для мониторинга DNS-запросов и обнаружения подозрительной активности (например, DNS Tunneling).

```yaml
- name: DNS Audit
  uses: step-security/harden-runner@v2
  with:
    egress-policy: audit
    # В логах Step Security появится детальный отчет о каждом DNS-запросе
```

Дополнения к сценарию: режим `audit` подходит не только для аудита DNS. Даже без явного allowlist действует Global Block List — обращения к известным вредоносным доменам активных supply-chain атак блокируются и помечаются автоматически, что дает защиту «из коробки» на время сбора базовой линии. В дашборде каждое сетевое событие коррелировано с шагом и процессом-источником, поэтому нетипичный резолвер или неожиданный домен CDN видны сразу. Признак туннелирования — высокая частота запросов к одному домену со случайными поддоменами; такие паттерны стоит проверять вручную в отчете сети.

### Сценарий 4: Доступ к внутренним ресурсам из GitHub-hosted раннера

Задача деплоя должна достучаться до внутренней БД/API в Azure VNet без развертывания self-hosted парка. Решение — Larger Runner организации, привязанный к приватной сети через runner group:

```yaml
# Предварительно (однократно, администратором):
#   Azure: VNet + подсеть (+ NAT Gateway при необходимости стабильного egress IP)
#   GitHub org settings: Hosted Compute Networking -> New network configuration
#   GitHub org settings: Runner groups -> группа с доступом к этой сети
jobs:
  deploy:
    runs-on:
      group: internal-deploy-runners   # группа, привязанная к сетевой конфигурации VNet
      labels: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: Connectivity check
        run: |
          # внутренний сервис доступен напрямую, без публичного интернета
          nc -zv db.internal.corp 5432 && echo "DB reachable"
          # внешний egress идет через NAT Gateway с фиксированным IP
          curl -s https://api.ipify.org && echo " <- static NAT IP"
```

Разбор решений: селектор `runs-on.group` направляет задачу в конкретную группу Larger Runners; сетевая конфигурация назначается группе, поэтому отдельного YAML-ключа для сети не требуется. NSG подсети разрешает только исходящий трафик к БД и GitHub-эндпоинтам из таблицы выше; входящие соединения блокируются явно. Валидация: `hostname -I` покажет приватный адрес из диапазона вашей подсети, а файрвол БД увидит подключения от адресов NAT Gateway. Помните про ограничения: только Enterprise Cloud, только Ubuntu/Windows, подсеть с запасом +30% к пиковой параллельности, нулевой spending limit не даст раннерам стартовать.

### Сценарий 5: Защита self-hosted раннера от кражи облачных метаданных

Классическая цепочка атаки: вредоносный PR получает выполнение кода на self-hosted раннере в облаке, код обращается к IMDS и забирает учетные данные роли VM. Минимальная защита — запретить контейнерам/процессам задачи доступ к link-local адресу метаданных:

```bash
# На хосте раннера (Linux): разрешить IMDS только root, остальным - запретить
sudo iptables -I OUTPUT -d 169.254.169.254 -m owner ! --uid-owner root -j REJECT
# Проверка: под пользователем раннера соединение должно падать
curl --max-time 2 http://169.254.169.254/latest/meta-data/ ; echo "exit=$?"
# → curl: (28) Connection timed out ... exit=28
```

Для AWS дополнительно включите IMDSv2 с hop limit `1` (`aws ec2 modify-instance-metadata-options --instance-id i-xxx --http-tokens required --http-put-response-hop-limit 1`) — тогда запросы из контейнеров (дополнительный сетевой хоп) будут отброшены самим сервисом метаданных. Разбор решений: правило iptables использует модуль owner, чтобы системным службам хоста IMDS остался доступен, а процессам задач — нет. Это сетевое дополнение к организационным мерам: JIT-раннеры, группы раннеров, отказ от запуска непроверенного кода и минимально привилегированные роли VM.

### Сценарий 6: Инцидент с компрометацией self-hosted раннера

**Контекст:** В репозитории обнаружен подозрительный GitHub Action, который отправляет данные на неизвестный адрес. Раннер, на котором выполнялась задача, потенциально скомпрометирован.

**Немедленные действия (первые 5 минут):**

1. **Остановите раннер.** Отключите его от сети и изолируйте — это предотвращает дальнейшую утечку данных и доступ к внутренним ресурсам.
2. **Смените все секреты,** к которым имел доступ раннер: токены доступа к реестрам, облачным провайдерам, API-ключи.
3. **Отключите раннер от репозитория/организации** в настройках GitHub Actions.
4. **Снимите диск скомпрометированного сервера** и заархивируйте для forensics; не уничтожайте evidence до завершения аудита.

**Диагностика:**
- Проверьте `git log` последнего коммита в ветке, где сработал подозрительный экшен; найдите, когда и кем были внесены изменения.
- Просмотрите изменения в workflow-файлах (`.github/workflows/`) — часто злоумышленник модифицирует существующий workflow или добавляет новый.
- Изучите сетевые логи раннера (если включен Harden-Runner или корпоративный файрвол) — обратите внимание на исходящие соединения к неожиданным IP/доменам.

**Восстановление:**
- Разверните новый раннер на чистой машине; зарегистрируйте его с новым токеном.
- Выкатите предыдущий стабильный релиз (до компрометации) или исправленный код.
- Проведите аудит всех секретов, к которым имел доступ раннер, и при необходимости отзовите/перевыпустите их.
- Рассмотрите переход на эфемерные (JIT) или GitHub-hosted раннеры для публичных репозиториев; для критичных пайплайнов используйте harden-runner в блокирующем режиме.

## Устранение типичных проблем

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| Раннер игнорирует обновленный прокси | Переменные прокси читаются только при старте приложения раннера | Перезапустить службу раннера после изменения `.env`/окружения |
| Ошибка `URI malformed` в логах раннера | Спецсимволы в пароле прокси внутри URL | URL-кодировать пароль (`%40` вместо `@` и т.п.) |
| `no_proxy` с IP-адресом не работает | Self-hosted раннеры не поддерживают IP/CIDR в `no_proxy` | Использовать имена хостов |
| Задача падает в block-режиме на легитимном домене | Неполный `allowed-endpoints` (не учтен CDN/аутентификационный хост реестра) | Прогнать задачу в `audit`, собрать Recommended Policy, затем включать `block` |
| Harden-Runner не создает отчеты на `ubuntu-slim` | Непривилегированный контейнер не позволяет агенту мониторить syscalls | Использовать стандартные VM-раннеры (`ubuntu-latest`) или Larger Runners |
| Larger runner не запускается в VNet | Spending limit $0, малая подсеть, отсутствие метода outbound (после ухода default outbound access) | Поднять лимит расходов, расширить подсеть (+30% к параллельности), добавить NAT Gateway/Firewall |
| Стандартный раннер не достучался до внутреннего ресурса | У standard runners нет частной сети — только публичный интернет | Larger Runners + сетевая конфигурация либо self-hosted за VPN/прокси |
| Загрузка артефактов/логов зависает за файрволом | Закрыт `*.blob.core.windows.net` или `results-receiver.actions.githubusercontent.com` | Открыть обязательные эндпоинты из таблицы требований |
| Внутренний API не пускает раннеры по allowlist | Диапазоны `GET /meta` меняются еженедельно и слишком широки | Статические IP (Larger Runners) или фиксированный egress через NAT/proxy |

## Лучшие практики

1. Начинайте с `egress-policy: audit` и переходите к `block` только после стабилизации Recommended Policy — это устраняет ложные блокировки легитимных зависимостей.
2. Ставьте harden-runner первым шагом каждой задачи; фиксируйте версию по полному SHA, а не по мажорному тегу.
3. Держите агент updated: обходы фильтрации (DNS-over-TCP/DoH) исправлялись в минорных версиях — старый агент в block-режиме создает ложное чувство защищенности.
4. Для внутренних ресурсов используйте статические IP или частную сеть, а не еженедельно меняющиеся диапазоны `GET /meta`.
5. Явно блокируйте входящий трафик к раннерам в VNet (GitHub никогда не требует inbound) и закрывайте IMDS для процессов задач на self-hosted.
6. Ограничивайте радиус поражения: группы раннеров с явными списками репозиториев, JIT/эфемерные раннеры для непроверяемого кода.
7. Настройте CODEOWNERS на `.github/workflows/**` — изменения сетевых политик и прав должны проходить ревью владельцев.
8. Регулярно сверяйте фактические права `GITHUB_TOKEN` с рекомендациями Enterprise-отчетов Harden-Runner (мониторинг outbound-вызовов API).
9. Проверяйте прокси-конфигурацию после каждого обновления образа раннера — `/etc/environment` и netsh-настройки легко теряются при пересборке кастомного образа.
