# GitHub Actions: Сетевая безопасность и контроль трафика

Контроль исходящего сетевого трафика (egress traffic) исполнителей (runners) позволяет устранить «слепую зону» в безопасности конвейеров непрерывной интеграции и доставки (CI/CD — Continuous Integration / Continuous Deployment). Это предотвращает несанкционированную утечку секретов и загрузку вредоносного кода во время выполнения задач.

## Определения

- **Egress Policy (Политика исходящего трафика)**: Набор правил, определяющих разрешенные и запрещенные исходящие сетевые соединения для узла или процесса.
- **Harden-Runner**: Специализированное решение с открытым исходным кодом от Step Security для мониторинга сетевой активности и применения политик безопасности на GitHub-hosted исполнителях.
- **Audit Mode (Режим аудита)**: Режим мониторинга, при котором все сетевые соединения фиксируются в логах, но не блокируются. Используется для профилирования нормального поведения пайплайна.
- **Block Mode (Режим блокировки)**: Режим активной защиты, при котором разрешаются соединения только с явно указанными эндпоинтами (белый список), а все остальные попытки связи блокируются.

## Основные концепции

### Задачи контроля сетевого трафика

1. **Предотвращение утечки данных (Data Exfiltration):** Блокировка попыток злоумышленников отправить `GITHUB_TOKEN`, API-ключи или другие секреты на подконтрольные им внешние серверы.
2. **Защита цепочки поставок (Supply Chain Security):** Гарантия того, что во время сборки зависимости загружаются только из доверенных реестров (например, `npmjs.org`, `pypi.org`, `github.com`), а не из скомпрометированных источников.
3. **Обеспечение видимости (Visibility):** Получение детальной информации о том, какие внешние ресурсы запрашиваются каждым шагом сборки, что критично для аудита и соответствия стандартам безопасности.

### Приватные сети для высокопроизводительных исполнителей (Larger Runners)

Для организаций с повышенными требованиями к безопасности GitHub предоставляет возможность подключения высокопроизводительных исполнителей (Larger Runners) к частным виртуальным сетям (VPC в AWS или VNet в Azure).
- **Прямой доступ:** Позволяет исполнителю обращаться к внутренним ресурсам (базам данных, реестрам образов) без публикации их в интернете.
- **Изоляция:** Весь трафик пайплайна проходит через корпоративный периметр и может фильтроваться существующими средствами сетевой защиты (NGFW, IDS/IPS).
- **Статические IP:** Упрощает настройку разрешающих правил на стороне целевых ресурсов.

### Безопасность через OIDC (OpenID Connect)

Использование OIDC (OpenID Connect) минимизирует риски, связанные с передачей и хранением долгоживущих секретов через сеть:
- **Отсутствие статических ключей:** Вместо паролей используются короткоживущие токены, действительные только в рамках одной задачи.
- **Доверительные отношения:** Облачный провайдер доверяет GitHub как издателю токенов, проверяя метаданные запроса (репозиторий, ветка, workflow).

### Идентификация исполнителей (IP-адреса GitHub)

В случаях, когда использование приватных сетей невозможно, GitHub публикует списки актуальных IP-адресов своих исполнителей.
- **API `/meta`:** Актуальный список диапазонов всегда доступен через официальный API GitHub.
- **Динамичность:** Диапазоны могут меняться, поэтому рекомендуется использовать автоматизированные скрипты для обновления правил в файрволах.

## Стратегия внедрения (Поэтапный подход)

Для минимизации риска прерывания легитимных процессов рекомендуется следовать поэтапному подходу:

1. **Этап профилирования (Audit):** Включение мониторинга для сбора данных о реальных сетевых потребностях пайплайна. Обычно занимает от нескольких дней до недели.
2. **Анализ данных:** Формирование минимально необходимого списка (least privilege) эндпоинтов на основе собранных логов.
3. **Этап защиты (Block):** Перевод пайплайна в блокирующий режим с применением сформированного белого списка. Любое отклонение от нормы будет приводить к немедленной остановке задачи.

## Практические сценарии

### Интеграция Harden-Runner в Workflow

Действие `harden-runner` должно быть первым шагом в каждой задаче (`job`) для обеспечения полного покрытия мониторингом. Версия `v2` поддерживает Linux, macOS и Windows исполнителей.

#### Настройка режима аудита

Используется на начальном этапе для изучения сетевой активности без риска падения сборки.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Инициализация контроля трафика (Audit)
        uses: step-security/harden-runner@v2
        with:
          egress-policy: audit # Мониторинг без блокировки
```

#### Настройка режима блокировки

Применяется после формирования списка доверенных адресов для обеспечения реальной защиты.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Инициализация контроля трафика (Block)
        uses: step-security/harden-runner@v2.20.0
        with:
          egress-policy: block
          allowed-endpoints: >
            github.com:443
            registry.npmjs.org:443
            objects.githubusercontent.com:443

      - name: Получение исходного кода
        uses: actions/checkout@v7
        
      - name: Установка зависимостей
        run: npm ci
```
