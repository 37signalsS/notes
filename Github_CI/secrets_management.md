# GitHub Actions: Управление секретами

Управление секретами в GitHub Actions обеспечивает безопасное хранение, маскирование и передачу конфиденциальных данных (пароли, API-ключи, токены) в процессы автоматизации. Секреты шифруются с использованием библиотеки `libsodium` (алгоритм `curve25519-xsalsa20-poly1305`) и передаются исполнителю (`runner`) только в зашифрованном виде, расшифровываясь непосредственно в памяти процесса.

Общие принципы управления секретами на уровне всей CI/CD-практики (ротация, зонирование, Zero Trust) — [Обзор DevSecOps](../CI-CD/DevSecOps/secrets_management.md); этот файл концентрируется на механике именно GitHub Actions.

## Определения

- **GitHub Actions Secrets**: Зашифрованные переменные, хранящиеся на уровнях организации, репозитория или окружения.
- **Маскирование (Masking)**: Автоматическая замена значений секретов на `***` в stdout и stderr.
- **GITHUB_TOKEN**: Временный токен доступа к API GitHub, создаваемый для каждой задачи. Права настраиваются гранулярно через ключ `permissions`.
- **Variables (vars)**: Переменные конфигурации для хранения нечувствительных данных (URL-адреса, имена пользователей), доступные через контекст `${{ vars.KEY }}`.
- **Секрет окружения (Environment Secret)**: Секрет, привязанный к конкретному [окружению](./Core_Concept.md#управление-окружениями-environments); применяется только в задачах, явно назначивших это окружение, и сочетается с protection rules (required reviewers, wait timer).
- **Автоматическая цензура (Auto-redaction)**: Распознавание и скрытие в логах типовых форматов токенов (JWT, `ghp_*`, `gho_*`, строки подключения к БД) даже без регистрации их как секретов.
- **Dependabot Secrets**: Отдельное пространство имён секретов (`Settings > Secrets > Dependabot`), доступных только воркфлоу, запущенным событиями Dependabot; обычные Actions-секреты таким прогонам недоступны вовсе.

## Основные концепции

### Иерархия и доступность секретов и переменных

Данные выбираются по принципу наибольшей специфичности. Механизм доступа идентичен для секретов (`secrets`) и переменных (`vars`):

1.  **Секреты/переменные окружения (Environment)**: Привязаны к конкретному [окружению](./Core_Concept.md#управление-окружениями-environments).
2.  **Секреты/переменные репозитория (Repository)**: Доступны для всех воркфлоу репозитория.
3.  **Секреты/переменные организации (Organization)**: Общие для группы репозиториев.

При совпадении имён на разных уровнях побеждает самый низкий уровень: environment перекрывает репозиторий, репозиторий — организацию. Это позволяет, например, переопределить общий корпоративный эндпоинт локальным значением.

**Синтаксис обращения:**
- Секреты: `${{ secrets.DOCKER_PASSWORD }}`
- Переменные: `${{ vars.DOCKER_USERNAME }}`

**Когда значения считываются**: секреты организации и репозитория фиксируются в момент постановки прогона в очередь; секреты окружения — в момент старта задачи, назначившей это окружение. Следствие: обновление значения не влияет на уже выполняющиеся прогоны, а перезапуск упавшей задачи подхватит новое значение только при повторной постановке в очередь.

**Политики доступа к секретам организации**: при создании секрета уровня организации выбирается политика доступа — все репозитории, только приватные или выбранный список (`private` по умолчанию при создании через CLI). Нюанс тарифного плана: на GitHub Free приватные репозитории организации не имеют доступа к её секретам — требуется платный план либо дублирование секрета на уровне репозитория.

**Важно**: Воркфлоу, запущенные из форков (Pull Requests от внешних контрибьюторов), по умолчанию **не имеют доступа** к секретам базового репозитория. Исключение — `GITHUB_TOKEN`, который выдаётся в режиме read-only. Штатный безопасный паттерн привилегированной обработки форк-PR (через `workflow_run`) разобран в [Events_Jobs_Steps](./Events_Jobs_Steps.md#сценарий-6-безопасная-постобработка-форк-pr-workflow_run).

Ещё одно штатное ограничение: воркфлоу, запущенные событиями Dependabot (например, `pull_request` от Dependabot-ветки), **не получают ни одного секрета**, включая секреты уровня репозитория. Для их нужд существует отдельный набор Dependabot Secrets.

### Управление GITHUB_TOKEN

С 2025 года стандартом является настройка минимальных прав для каждой задачи через секцию `permissions`. Токен создается автоматически при запуске задачи и уничтожается по завершении.

Для новых репозиториев и организаций действует режим **default read-only**: если `permissions` не указан вовсе, токен получает только права чтения. Режим настраивается в Settings > Actions > General > Workflow permissions (`Read repository contents and packages permissions` против `Read and write permissions`). Явно заданный `permissions` всегда переопределяет дефолт; допустимо указать `permissions: {}` для полного отключения прав.

Ключ задаётся на двух уровнях: на уровне воркфлоу (базовое значение для всех задач) и на уровне задачи (сужение/расширение в пределах разрешённого). Предпочтителен шаблон «на уровне воркфлоу — `contents: read`, на задачах, которым нужно больше, — точечное расширение».

**Основные области доступа (Scopes):**
- `contents: read/write` — доступ к коду.
- `id-token: write` — требуется для аутентификации через OIDC.
- `packages: write` — публикация в GitHub Packages.
- `pull-requests: read/write` — работа с PR и комментариями.

Прочие часто используемые области: `issues`, `deployments`, `checks`, `actions` (управление прогонами и артефактами), `statuses` (commit status), `attestations` (подпись артефактов attestations).

Тот же токен доступен внутри выражений как `${{ github.token }}` (и `secrets.GITHUB_TOKEN`). При вызове переиспользуемых воркфлоу права вдоль цепочки могут только сохраняться или сужаться — детали в [Переиспользуемых рабочих процессах](./Reusable_Workflows.md).

### Механизмы защиты и маскирования

- **Автоматическое маскирование**: GitHub пытается найти все вхождения секрета в логах и заменить их на `***`. Важно: маскируются точные совпадения строкового значения; если значение сериализуется (JSON, YAML, Base64), представление меняется и маскирование может не сработать. Официальная рекомендация — избегать структурированных данных в качестве значения секрета.
- **Автоматическая цензура типовых форматов**: помимо пользовательских секретов, из логов скрываются распознанные шаблоны — JWT, GitHub-токены v2 (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`), PAT, ключи Azure (Cache, Container Registry, Function host, Search), пароли клиентских приложений Azure AD, NuGet/NPM-токены, HTTP Bearer заголовки, строки подключения к базам данных.
- **Динамическое маскирование**: Если скрипт генерирует секрет или пароль на лету, его необходимо скрыть с помощью команды:
  ```bash
  echo "::add-mask::$DYNAMIC_SECRET"
  ```
  Маскирование действует с момента регистрации до конца прогона и не распространяется ретроспективно на уже напечатанные строки — вызывайте `::add-mask::` до любого вывода значения.
- **Push Protection**: Блокировка попыток закоммитить секреты в репозиторий на основе паттернов.
- **Отладочные «секреты»**: зарезервированные имена `ACTIONS_STEP_DEBUG` и `ACTIONS_RUNNER_DEBUG` со значением `true` включают пошаговое логирование раннера (используются в диагностике, см. [Кэширование](./Caching.md)).

### Использование секретов в воркфлоу

Передача экшену или шагу — через вход (`with:`) или переменную окружения (`env:`); оба варианта равнозначны:

```yaml
steps:
  - name: Hello world action
    uses: my-org/hello-action@v1
    with:                    # секрет как вход экшена
      super_secret: ${{ secrets.SuperSecret }}
    env:                     # или как переменную окружения
      super_secret: ${{ secrets.SuperSecret }}
```

Ключевые правила использования:

- **Несуществующий секрет возвращает пустую строку**, а не ошибку. Опечатка в имени секрета молча даст пустое значение — частый источник «загадочных» падений деплоя.
- **Контекст `secrets` недоступен в условных выражениях** `if:`. Обходной путь — пробросить секрет в переменную окружения уровня задачи и проверять её:
  ```yaml
  jobs:
    conditional-secret:
      runs-on: ubuntu-latest
      env:
        HAS_TOKEN: ${{ secrets.API_TOKEN != '' }}
      steps:
        - if: env.HAS_TOKEN == 'true'
          run: ./notify.sh
          env:
            API_TOKEN: ${{ secrets.API_TOKEN }}
  ```
- **Не передавайте секреты через аргументы командной строки**: процессы видны другим пользователям системы через `ps` и попадают в журналы аудита ОС. Используйте переменные окружения или STDIN. Если командная строка неизбежна — берите значение из `env` и заключайте в кавычки, поскольку секреты часто содержат спецсимволы оболочки:
  ```yaml
  - shell: bash
    env:
      SUPER_SECRET: ${{ secrets.SuperSecret }}
    run: example-command "$SUPER_SECRET"
  ```
- **Секреты не попадают автоматически внутрь контейнеров и сервисов задачи**: в `container.services` передавайте их явным образом через `env` сервиса.

### Технические лимиты (2026)

- **Размер**: До **48 КБ** на один секрет. Большие данные шифруются отдельно, а парольная фраза хранится как секрет (см. Сценарий 4).
- **Количество**: До **1000** секретов на организацию, **100** на репозиторий и **100** на окружение. Нюанс: если репозиторию назначено более 100 секретов организации, воркфлоу сможет прочитать только первые 100 по алфавиту имён — проектируйте имена так, чтобы критичные попадали в начало алфавита, либо сокращайте количество.
- **Именование**: Только буквы, цифры и `_`. Пробелы запрещены. Регистр не чувствителен (значения нормализуются к верхнему регистру). Имя не может начинаться с цифры и с префикса `GITHUB_`. Имена уникальны в пределах своего уровня.
- **Бинарные данные**: допускается хранение небольших бинарных блобов в Base64 (см. Сценарий 5); кодирование — не шифрование и защиту не добавляет.

### Отключение рабочих процессов

GitHub позволяет временно отключить (Disable) отдельные воркфлоу через интерфейс (Actions -> [Workflow Name] -> ... -> Disable Workflow). Это предотвращает их запуск по событиям `push` или `schedule` без удаления файлов из репозитория.

В контексте работы с секретами эта функция — часть реагирования на инциденты: при подозрении на утечку сначала отключите затронутые воркфлоу (остановив использование скомпрометированных значений), затем выполните ротацию секретов, расследование через audit log и только потом включайте пайплайны обратно.

## Интеграция OIDC (Workload Identity)

OIDC — это современный «золотой стандарт» (Secretless CI/CD). Он устраняет необходимость хранения долгоживущих облачных ключей (AWS Access Keys, GCP Service Account Keys) в секретах GitHub.

**Механизм работы:**
1. Раннер запрашивает у GitHub временный JWT-токен.
2. Этот токен передается облачному провайдеру.
3. Провайдер проверяет подпись GitHub и метаданные (репозиторий, ветка) и выдает временные права доступа.

**Структура токена** (issuer — `https://token.actions.githubusercontent.com`):
- `aud` (audience): по умолчанию URL issuer'а; облачная сторона сверяет его в условии доверия.
- `sub` (subject): несёт контекст запуска в формате `repo:<org>/<repo>:<условие>`. Примеры: `repo:my-org/my-repo:ref:refs/heads/main`, `repo:my-org/my-repo:environment:production`, `repo:my-org/my-repo:pull_request`.
- Дополнительные claims: `job_workflow_ref` (полный путь вызвавшего воркфлоу с рефом — основа для самой строгой политики доверия), `ref`, `sha`, `actor`.

На стороне облака доверие настраивается политикой по `aud` и `sub` (пример для AWS — в Сценарии 1). Организации доступны шаблоны кастомизации `sub`-claim (Settings > Actions > OpenID Connect), позволяющие встроить в subject дополнительные метки. Сетевые аспекты обмена и ограничения трафика — [Сетевая безопасность](./network-security.md).

## Практические сценарии

### Сценарий 1: Аутентификация в AWS через OIDC

Предварительные условия (однократно, на стороне AWS):
1. Создать OIDC identity provider в IAM с URL `https://token.actions.githubusercontent.com` и audience `sts.amazonaws.com`.
2. Создать роль с trust policy, ограничивающей `sub` конкретным репозиторием и веткой:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "https://token.actions.githubusercontent.com",
          "token.actions.githubusercontent.com:sub": "repo:my-org/my-repo:ref:refs/heads/main"
        }
      }
    }
  ]
}
```

Без условия по `sub` роль смогла бы ассюмировать любой репозиторий организации, которому доступен провайдер, — это критично для многорепозиторных организаций.

Воркфлоу:

```yaml
jobs:
  aws-deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write # Обязательно для OIDC
      contents: read
    steps:
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v6 # актуальная мажорная версия (v6.2.x, июль 2026)
        with:
          role-to-assume: arn:aws:iam::123456789:role/github-actions-role
          aws-region: us-east-1
          role-session-name: github-actions-${{ github.run_id }} # читаемая идентификация в CloudTrail
      - run: aws s3 ls
      - name: Проверка идентичности
        run: aws sts get-caller-identity --query 'Arn' --output text
        # → arn:aws:sts::123456789:assumed-role/github-actions-role/github-actions-1234567890
```

Проверка результата: команда `get-caller-identity` должна вернуть ARN вида `arn:aws:sts::<account>:assumed-role/<role>/<session>`; запись об AssumeRoleWithWebIdentity появляется в CloudTrail с указанием session name.

### Сценарий 2: Получение секретов из HashiCorp Vault

Интеграция с внешним хранилищем позволяет централизованно управлять секретами всей компании: Vault остаётся единственным местом хранения и ротации, а GitHub получает значения только на время прогона.

```yaml
jobs:
  fetch-secrets:
    runs-on: ubuntu-latest
    permissions:
      id-token: write   # JWT для аутентификации в Vault методом jwt
      contents: read
    steps:
      - name: Import Secrets from Vault
        uses: hashicorp/vault-action@v4 # актуальная версия (v4.0.0, май 2026, runtime node24)
        with:
          url: https://vault.internal.corp
          role: ci-role                 # роль JWT auth backend в Vault
          method: jwt                   # аутентификация по OIDC/JWT, без VAULT_TOKEN
          secrets: |
              kv/data/ci/service_key password | DB_PASSWORD ;
              kv/data/ci/api_token token | API_TOKEN
      - run: |
          test -n "$DB_PASSWORD" && echo "DB_PASSWORD получен (замаскирован)"
```

Формат строки маппинга: `<путь в KV v2> <ключ> | <имя переменной окружения>`; пути в KV v2 включают префикс `data/`. Экспортированные значения автоматически регистрируются как маскируемые. Настройку роли и bound claims на стороне Vault см. в материалах по Vault этой базы знаний.

### Сценарий 3: Передача секретов в Reusable Workflows

```yaml
jobs:
  call-deploy:
    uses: ./.github/workflows/reusable-deploy.yml
    secrets: inherit # Автоматически передает все доступные секреты
```

`inherit` удобен внутри одной организации; он работает только для вызовов в пределах той же организации или enterprise. Для внешних потребителей и для аудитопригодности предпочтительна явная передача перечня секретов, а промежуточные слои вложенных цепочек должны перепередавать только необходимый минимум. Полный разбор контракта `inputs`/`secrets`/`outputs` — [Переиспользуемые рабочие процессы](./Reusable_Workflows.md).

### Сценарий 4: Хранение больших секретов (gpg)

Для данных свыше 48 КБ (keystore, полный JSON-конфиг с ключами) официальный подход: файл шифруется локально симметричным шифром и коммитится в репозиторий, а в секрете хранится только парольная фраза.

Шифрование на рабочей машине:

```bash
gpg --symmetric --cipher-algo AES256 my_secret.json
# → интерактивный запрос passphrase; результат — файл my_secret.json.gpg
git add my_secret.json.gpg && git commit -m "Add encrypted secret"
```

Скрипт расшифровки `decrypt_secret.sh` в репозитории:

```bash
#!/bin/sh
mkdir -p "$HOME/secrets"
# --batch отключает интерактивность, --yes принимает подтверждения
gpg --quiet --batch --yes --decrypt \
  --passphrase="$LARGE_SECRET_PASSPHRASE" \
  --output "$HOME/secrets/my_secret.json" my_secret.json.gpg
```

Использование в воркфлоу:

```yaml
jobs:
  decrypt-job:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: Decrypt large secret
        run: ./decrypt_secret.sh
        env:
          LARGE_SECRET_PASSPHRASE: ${{ secrets.LARGE_SECRET_PASSPHRASE }}
```

Важно: содержимое расшифрованного файла **не маскируется автоматически** — GitHub знает только парольную фразу. Не выводите расшифрованное содержимое в логи; при необходимости маскируйте поля вручную через `::add-mask::`.

### Сценарий 5: Бинарные секреты (Base64) и динамическое маскирование

Небольшие бинарные блобы (сертификаты `.der`, keystores) удобно хранить закодированными в Base64.

Подготовка и загрузка секрета:

```bash
base64 -w 0 cert.der > cert.base64          # Linux
gh secret set CERTIFICATE_BASE64 < cert.base64
# → Set secret CERTIFICATE_BASE64 for octocat/octorepo
```

Использование на раннере:

```yaml
steps:
  - name: Retrieve the secret and decode it to a file
    env:
      CERTIFICATE_BASE64: ${{ secrets.CERTIFICATE_BASE64 }}
    run: |
      echo "$CERTIFICATE_BASE64" | base64 --decode > cert.der
      openssl x509 -in cert.der -inform DER -text -noout | head -5
      # → Certificate:
      # →   Data:
      # →     Version: 3 ...
```

Если скрипт генерирует чувствительное значение на лету (токен, временный пароль), зарегистрируйте его маску до первого вывода:

```bash
DYNAMIC_SECRET="$(./generate-token.sh)"
echo "::add-mask::$DYNAMIC_SECRET"
echo "Token generated"   # безопасно: само значение нигде не печатается
```

Помните: Base64 — кодирование, а не шифрование; оно лишь решает проблему бинарности формата, но не добавляет защиты.

### Сценарий 6: Условное использование секрета и диагностика пустых значений

Задача: выполнить интеграционные тесты только когда секрет внешнего сервиса заведён, и получить явную диагностику вместо тихой пустой строки.

```yaml
jobs:
  integration-tests:
    runs-on: ubuntu-latest
    env:
      EXTERNAL_API_KEY: ${{ secrets.EXTERNAL_API_KEY }}
    steps:
      - name: Проверка наличия секрета
        id: guard
        run: |
          if [ -z "$EXTERNAL_API_KEY" ]; then
            echo "available=false" >> "$GITHUB_OUTPUT"
            echo "::warning::EXTERNAL_API_KEY не задан — интеграционные тесты пропущены"
          else
            echo "available=true" >> "$GITHUB_OUTPUT"
          fi
      - if: steps.guard.outputs.available == 'true'
        run: npm run test:integration
```

Проверка результата: при незаданном секрете в логе появляется warning-строка `::warning::EXTERNAL_API_KEY не задан…`, задача завершается успехом, шаг тестов отсутствует в списке выполненных. Такой guard устраняет главный риск «пустого секрета» — молчаливое падение в глубине скриптов.

## Устранение типичных проблем

| Симптом | Вероятная причина | Диагностика и решение |
| :--- | :--- | :--- |
| Секрет читается как пустая строка | Опечатка в имени; секрет не существует (несуществующие возвращают `""` без ошибки) | Сверьте имя с `gh secret list`; добавьте guard из Сценария 6 |
| Секреты недоступны из форк-PR | Штатная модель: форк-прогоны получают только read-only `GITHUB_TOKEN` | Привилегированную постобработку выполняйте по паттерну `workflow_run` ([пример](./Events_Jobs_Steps.md#сценарий-6-безопасная-постобработка-форк-pr-workflow_run)) |
| Секреты недоступны в воркфлоу Dependabot | Штатное ограничение: Dependabot-события не получают Actions-секреты | Заведите отдельные Dependabot Secrets или используйте `pull_request_target` с осторожным checkout |
| Маскирование не сработало | Значение сериализовано (JSON/Base64) и изменило представление; строка была выведена до `::add-mask::` | Храните плоские значения; вызывайте `add-mask` до первого вывода; для больших секретов не печатайте расшифровку |
| Ошибка `Unrecognized named-value: 'secrets'` в `if` | Контекст `secrets` запрещён в условных выражениях | Пробросьте секрет в `env` уровня задачи и проверяйте `env.*` |
| Секрет не помещается (лимит 48 КБ) | Размер значения превышает лимит | Зашифруйте файл gpg и храните passphrase как секрет (Сценарий 4) |
| Org-секрет невидим приватному репозиторию | Тарифный план GitHub Free | Перейдите на платный план либо продублируйте секрет на уровне репозитория |
| Часть org-секретов недоступна воркфлоу | Назначено более 100 орг-секретов; доступны первые 100 по алфавиту | Сократите количество или пересмотрите имена; нужные секреты перенесите на уровень репозитория |
| Обновлённый секрет не применился в текущем прогоне | Org/repo-секреты фиксируются при постановке в очередь | Перезапустите прогон заново; для env-секретов — дождитесь старта задачи |
| Требуется пошаговый лог раннера | Диагностика сложной проблемы | Создайте секрет `ACTIONS_STEP_DEBUG: true` (или `ACTIONS_RUNNER_DEBUG`) и перезапустите прогон |

Быстрая инвентаризация секретов из CLI:

```bash
gh secret list
# → NAME                UPDATED
# → DEPLOY_TOKEN        about 2 hours ago
# → REGISTRY_PASSWORD   about 5 days ago
```

## Лучшие практики

1. **OIDC вместо статических ключей**: для AWS/GCP/Azure и поддерживающих OIDC систем исключите долгоживущие секреты вовсе; статические ключи оставляйте только там, где OIDC недоступен.
2. **Минимальные права токена**: `permissions: contents: read` на уровне воркфлоу с точечным расширением на отдельных задачах; никогда не полагайтесь на дефолты репозитория.
3. **Production-секреты — только в Environments**: связка с protection rules (required reviewers, wait timer) даёт ручной барьер и аудит одобрений; environment-секреты непрозрачно отделены от CI-секретов.
4. **Явный контракт вместо `inherit`**: в переиспользуемых воркфлоу перечисляйте секреты декларативно — видно, какие значения покидают репозиторий, и контракт переживает смену механизма передачи.
5. **Никаких секретов в логах и CLI**: переменные окружения и STDIN вместо аргументов командной строки; `::add-mask::` для генерируемых значений до первого вывода.
6. **Ротация и мониторинг**: регулярная ротация статических секретов; alert'ы secret scanning и push protection включены; подозрение на утечку — немедленный Disable воркфлоу, ротация, разбор в audit log.
7. **Откат и очистка**: удаление секрета — `gh secret delete NAME` (для org/env — с флагами `--org`/`--env`); обновление значения применяется ко всем последующим прогонам, отката значения нет — только повторное обновление.
