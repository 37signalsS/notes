# GitHub Actions: Управление секретами

Управление секретами в GitHub Actions позволяет безопасно хранить и использовать конфиденциальную информацию (пароли, API-ключи, токены доступа) в процессах автоматизации. Секреты шифруются на стороне GitHub (с использованием библиотеки `libsodium` и алгоритма `curve25519-xsalsa20-poly1305`) и передаются исполнителю (runner) только в зашифрованном виде, расшифровываясь непосредственно в памяти процесса задачи.

## Определения

- **GitHub Actions Secrets (Секреты)**: Зашифрованные переменные среды, создаваемые на уровне организации, репозитория или конкретного окружения.
- **Маскирование (Masking)**: Автоматический процесс замены значений секретов на символы `***` в логах выполнения воркфлоу. GitHub Actions сопоставляет вывод в stdout и stderr со значениями секретов и блокирует их отображение.
- **GITHUB_TOKEN**: Временный токен безопасности, автоматически создаваемый GitHub для каждой задачи (job). Его жизненный цикл ограничен временем выполнения задачи, а права доступа настраиваются через директиву `permissions`.
- **Variables (Переменные)**: Конфигурационные данные (не чувствительные), которые хранятся открыто и не маскируются в логах. Доступны через контекст `vars`.

## Основные концепции

### Уровни хранения и иерархия

Секреты организованы иерархически, что позволяет гибко управлять доступом и переопределять значения:

1. **Organization secrets (Секреты организации)**: Позволяют совместно использовать общие данные (например, ключи к корпоративному облаку) в нескольких репозиториях. Лимит — **1000** секретов на организацию. Можно ограничить доступ конкретными репозиториями или типами (публичные/приватные).
2. **Repository secrets (Секреты репозитория)**: Доступны для всех воркфлоу в рамках конкретного репозитория. Лимит — **100** секретов.
3. **Environment secrets (Секреты окружения)**: Привязаны к конкретному [окружению](./Core_Concept.md#окружения-и-правила-защиты-environments) (например, `production` или `staging`). Это позволяет использовать одинаковые имена переменных (например, `DB_PASSWORD`) с разными значениями. Требуют явного указания `environment: <name>` в задаче.

### Технические лимиты (спецификации 2026)

- **Размер**: Максимальный размер одного секрета составляет **48 КБ**. Для данных большего размера (например, тяжелых SSL-сертификатов) рекомендуется хранить их в репозитории в зашифрованном виде (GPG), используя секреты GitHub только для хранения пароля расшифровки.
- **Количество**: В одном запуске воркфлоу можно использовать до **100** секретов репозитория, **100** секретов окружения и только первые **100** секретов организации (отсортированных по алфавиту).
- **Именование**: Имена секретов могут содержать только буквы, цифры и подчеркивания. Они не могут начинаться с цифры или префикса `GITHUB_`. Регистр не учитывается (GitHub сохраняет и обращается к ним в верхнем регистре).

### Безопасность и механизмы защиты

- **Одностороннее шифрование**: После создания значение секрета невозможно просмотреть через API или UI; его можно только обновить или удалить.
- **Защита в Fork-репозиториях**: По умолчанию секреты недоступны для воркфлоу, запускаемых из форков сторонними пользователями. Это критическая мера против атак через вредоносные Pull Request, нацеленных на кражу учетных данных.
- **Secret Scanning (Сканирование секретов)**: GitHub автоматически сканирует публичные (и приватные, если включено) репозитории на наличие известных форматов секретов (>200 провайдеров). Функция **Push Protection** блокирует коммиты, содержащие секреты в открытом виде.
- **Scoped Secrets (Контекстные секреты)**: Новое в 2026 году. Позволяют ограничивать использование секретов конкретными ветками, путями файлов воркфлоу или доверенными Reusable Workflows, предотвращая нецелевой доступ к данным.

## Практические сценарии

### Сценарий 1: Использование секрета для SSH-доступа

При выполнении команд на удаленном сервере необходимо передать закрытый ключ. Секрет передается через переменную окружения шага, что обеспечивает его маскирование в логах.

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v7

      - name: Execute remote commands
        env:
          PRIVATE_KEY: ${{ secrets.SERVER_SSH_KEY }}
          HOST_ADDR: ${{ secrets.SERVER_HOST }}
        run: |
          echo "$PRIVATE_KEY" > deploy_key
          chmod 600 deploy_key
          # Использование ключа без вывода его содержимого в логи
          ssh -i deploy_key -o StrictHostKeyChecking=no user@$HOST_ADDR "cd /app && ./update.sh"
          rm -f deploy_key
```

### Сценарий 2: Разделение секретов по окружениям и OIDC

Использование OIDC (OpenID Connect) вместо статических секретов для доступа к облачным провайдерам (AWS, Azure, Google Cloud). Это исключает необходимость хранения долгоживущих паролей в GitHub.

```yaml
jobs:
  deploy-prod:
    runs-on: ubuntu-latest
    environment: production # Подключает секреты и правила одобрения окружения
    permissions:
      id-token: write # Необходимо для генерации OIDC-токена
      contents: read
    steps:
      - name: Authenticate to Cloud
        uses: cloud-provider/auth-action@v1
        with:
          # TOKEN берется динамически, исключая статическое хранение
          workload-identity-provider: ${{ vars.CLOUD_PROVIDER_ID }}
          service-account: ${{ secrets.CLOUD_SERVICE_ACCOUNT }}
      - name: Deploy
        run: ./deploy.sh
```

### Сценарий 3: Принцип минимальных прав (Least Privilege)

Согласно общим принципам безопасности, каждая задача должна иметь доступ только к необходимому минимуму данных. В GitHub Actions это реализуется через изоляцию задач.

```yaml
jobs:
  unit-tests:
    runs-on: ubuntu-latest
    # Задача тестов не имеет доступа к продовым секретам (нет environment: production)
    steps:
      - uses: actions/checkout@v4
      - run: npm test

  deploy-prod:
    runs-on: ubuntu-latest
    needs: unit-tests
    environment: production # Изолированный доступ к секретам + требование ручного подтверждения
    steps:
      - uses: actions/checkout@v4
      - name: Production deployment
        env:
          API_TOKEN: ${{ secrets.PROD_API_TOKEN }}
        run: ./publish.sh
```

В данном примере, если в процессе тестирования произойдет сбой или компрометация окружения, секрет `PROD_API_TOKEN` останется в безопасности, так как он доступен только задаче `deploy-prod` после успешного завершения тестов и (опционально) ручного одобрения.
