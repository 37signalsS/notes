# GitHub Actions: Тест-отчёты и надёжность тестов

**Актуально для:** GitHub Actions (actions/checkout@v7, mikepenz/action-junit-report@v6, nick-fields/retry@v4, dorny/test-reporter@v3), октябрь 2026

Публикация результатов тестов в интерфейс GitHub и борьба с нестабильностью (flaky) — обязательная часть продакшен-CI. Блок охватывает интеграцию JUnit-отчётов с PR, ретраи, автоматические перезапуски и карантин.

Предварительные условия: репозиторий с включённым GitHub Actions и понимание модели прав `GITHUB_TOKEN` — `checks: write` для создания check run, `actions: write` для перезапуска прогонов. Общая теория нестабильности (причины, метрики стабильности, детекция по истории, инструменты pytest/GitLab) — в [Управлении нестабильными тестами](../CI-CD/Testing/flaky_test_management.md); здесь — реализация механик именно в GitHub Actions.

## Определения

- **JUnit XML**: Де-факто универсальный формат отчётов тестовых раннеров (Jest, Pytest, GoTest, JUnit); именно его потребляют экшены публикации отчётов.
- **Check Run / Аннотации**: Объект Checks API: строка «тестов 214, упало 2» в PR и построчные пометки упавших кейсов прямо в diff'е файлов.
- **Flaky Test**: Тест с недетерминированным исходом на одном и том же коде (гонки, время, сеть, порядок данных).
- **Quarantine (Карантин)**: Временное исключение нестабильных тестов из блокирующего набора с сохранением их запуска и наблюдаемости.
- **Retry**: Повтор шага/команды после неудачи; инструмент `nick-fields/retry` оборачивает команду политикой повторов.
- **Re-run Failed Jobs**: Платформенный перезапуск только упавших задач прогона (UI, `gh run rerun --failed` либо `POST .../rerun-failed-jobs`). Окно — 30 дней с исходного прогона, лимит — 50 перезапусков на прогон (полных и частичных суммарно).
- **Annotation Limits**: Платформенные ограничения аннотаций: Checks API — максимум 50 аннотаций на запрос, GitHub Actions — не более 10 warning- и 10 error-аннотаций на шаг; сообщение аннотации — до 64 KB, заголовок — до 255 символов.

## Основные концепции

### Конвейер отчётности

```
Тестовый раннер → JUnit XML → экшен публикации → Check Run + Step Summary
```

- Генерация: каждый раннер пишет XML флагом (`pytest --junitxml=report.xml`, `jest --ci --reporters=jest-junit`, `gotestsum --junitfile`). Вывод Jest настраивается парой `JEST_JUNIT_OUTPUT_DIR` + `JEST_JUNIT_OUTPUT_NAME` (или единым `JEST_JUNIT_OUTPUT_FILE`); устаревшая переменная `JEST_JUNIT_OUTPUT` текущим jest-junit не читается. Каталог генераторов — в [Инструментах отчётности](../Testing/testing_reporting_tools.md).
- Публикация: `mikepenz/action-junit-report@v6` (аннотации + сводка; вход `check_retries` скрывает исходные падения повторов, сводка `flaky_summary` выводит таблицу флаки-результатов) или `dorny/test-reporter@v3` (мультиформат: dotnet-trx, nunit, phpunit, golang-json и др.). Экшену нужны права `checks: write`; публикация выполняется при **любом** исходе (`if: always()`, точнее — `if: ${{ !cancelled() }}`, чтобы не публиковать частичный отчёт при ручной отмене), иначе красные тесты останутся без отчёта.
- Ограничения аннотаций: в PR отображается не более **10 warning- и 10 error-аннотаций на шаг** (Checks API — 50 на запрос). Для больших сьютов аннотации усекаются: источником правды становятся summary-таблицы (`detailed_summary`, `failed_summary_logs`) и артефакт XML, а не построчные пометки.
- Права и форки: у форк-PR токен read-only, check run от имени воркфлоу создать нельзя. Решение то же, что для постобработки форков: артефакт + follow-up воркфлоу на `workflow_run` (готовый паттерн — Сценарий 6 в [Событиях](./Events_Jobs_Steps.md)).

### Шардированные отчёты

При шардировании каждый шард пишет свой XML с **уникальным** именем артефакта (неизменяемость артефактов v4+). Агрегация: скачать все шарды (`pattern` + `merge-multiple: true`) и опубликовать единый отчёт; механика шардинга — в [Матричных сборках](./Matrix_Builds.md), сводка собирается в `$GITHUB_STEP_SUMMARY` через jq.

### Стратегии работы с flaky

1. **Ретрай шага** (`nick-fields/retry@v4`): для внешне-зависимых операций (загрузка фикстур, миграции против shared-стенда) и заведомо флаки-интеграционных кейсов; `warning_on_retry: true` (в v4 — по умолчанию) делает повтор видимым, `retry_on: error|timeout|any` ограничивает повторы нужным классом ошибок, а выходы `total_attempts` и `exit_code` пригодны для метрик.
2. **Авто-rerun задачи**: платформенный перезапуск упавших задач ночного регламента; ограничения — максимум 50 перезапусков прогона (полных и частичных суммарно) и окно в 30 дней с момента исходного прогона (лимит — в [Ограничениях](./Environment_Limitations.md)).
3. **Карантин**: список нестабильных тестов в файле репозитория; они гоняются отдельной некритичной задачей (`continue-on-error`) с алертом. Карантин обязан иметь TTL — просроченный пункт возвращается в основной набор автоматически.
4. **Метрика**: доля флаки-прогонов за период считается по истории выводов rerun'ов; рост метрики — сигнал чинить причину, а не маскировать.

Ретраи не применяются к идемпотентно опасным операциям: публикация релиза, отправка уведомлений, деплой (повтор может удвоить эффект; правила отмен — в [Оптимизации](./Optimization.md)).

## Практические сценарии

### Сценарий 1: JUnit-отчёт с аннотациями в PR

```yaml
name: Tests
on: [pull_request]
permissions:
  checks: write
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - run: npm ci
      - name: Run tests
        run: npx jest --ci --reporters=default --reporters=jest-junit
        env:
          JEST_JUNIT_OUTPUT_DIR: reports
          JEST_JUNIT_OUTPUT_NAME: junit.xml
      - name: Publish report
        if: ${{ !cancelled() }}            # отчёт нужен и при провале, но не при отмене
        uses: mikepenz/action-junit-report@v6
        with:
          report_paths: reports/junit.xml
          require_tests: true              # отсутствие отчёта = ошибка задачи
          annotate_notice: false           # только реальные падения аннотируются
```

- Каждый параметр: `if: ${{ !cancelled() }}` (или `if: always()`) гарантирует публикацию при падении тестов; `require_tests` ловит случай «раннер молча не написал XML»; `checks: write` — минимальное право для создания check run.
- **Валидация**: в PR появляется проверка «JUnit Test Report» со счётчиками; сломанный assert даёт аннотацию с именем кейса и путём к файлу прямо у строки кода. Если упало более ~20 тестов, аннотации усекаются (лимит 10+10 на шаг) — детали в summary-таблице и артефакте XML.

### Сценарий 2: Ретрай нестабильного шага

```yaml
      - name: Migrate against staging DB
        id: migrate
        uses: nick-fields/retry@v4
        with:
          timeout_minutes: 10              # жёсткий потолок одной попытки (в v4 есть и timeout_seconds)
          max_attempts: 3
          retry_wait_seconds: 20
          retry_on: error                  # ретраить только ошибки, не таймауты
          warning_on_retry: true           # повтор виден в логе как warning
          command: ./scripts/migrate.sh
```

- Политика: ретраить только операции с известной природой нестабильности; три попытки с паузой — верхняя граница разумного, дальше нужно чинить причину. Выходы шага (`total_attempts`, `exit_code`) можно писать в `$GITHUB_STEP_SUMMARY` для метрики повторов.
- **Валидация**: лог содержит `Attempt 1 failed` и итоговый успех; задача зелёная, но с warning-строкой, попадающей в метрику качества пайплайна.

### Сценарий 3: Автоперезапуск упавших ночных прогонов

```yaml
name: Nightly Autoretry
on:
  schedule:
    - cron: '23 4 * * *'                   # после основного nightly (02:17)
permissions:
  actions: write                           # обязательное право для перезапуска прогонов
jobs:
  rerun-failed:
    runs-on: ubuntu-latest
    steps:
      - env:
          GH_TOKEN: ${{ github.token }}
        run: |
          RUN_ID=$(gh run list \
            --workflow nightly.yml \
            --created ">=$(date -u -d '12 hours ago' +%Y-%m-%dT%H:%M)" \
            --limit 1 --json databaseId,status \
            --jq '.[] | select(.status=="completed") | .databaseId')
          [ -n "$RUN_ID" ] || { echo "нет завершённых прогонов"; exit 0; }
          FAILED=$(gh api "repos/${GITHUB_REPOSITORY}/actions/runs/${RUN_ID}/jobs" \
            --jq '[.jobs[] | select(.conclusion=="failure")] | length')
          if [ "$FAILED" -gt 0 ]; then
            gh run rerun "$RUN_ID" --failed    # CLI-эквивалент POST .../rerun-failed-jobs
            echo "Перезапущено упавших задач: $FAILED"
          fi
```

- Ограничители обязательны: watcher запускается один раз за ночь, берёт только свежий завершённый прогон и только его failure-задачи — иначе получается бесконечный цикл перезапусков. Без `permissions: actions: write` вызов rerun возвращает 403. Перезапуск возможен в течение 30 дней после исходного прогона и максимум 50 раз на прогон (полных и частичных суммарно); лимиты — в [Ограничениях](./Environment_Limitations.md).
- **Валидация**: у ночного прогона появляется второй attempt (`run_attempt: 2`); в summary видно, какие задачи прошли со второй попытки — кандидаты в карантин.

### Сценарий 4: Карантин нестабильных тестов

```text
# .github/quarantine.txt — по одному селектору в строке, с датой истечения TTL
# tests/auth/session.spec.ts|2026-09-30
# tests/integration/websocket.spec.ts|2026-10-15
```

```bash
# внутри задачи quarantine (continue-on-error: true)
QUARANTINE_FILE=.github/quarantine.txt
TODAY=$(date -u +%F)
while IFS='|' read -r spec expiry; do
  [ -z "$spec" ] && continue
  if [[ "$expiry" < "$TODAY" ]]; then
    echo "::error::Карантин истёк для $spec — верните тест или продлите"
    exit 1                                 # просрочка карантина ломает пайплайн
  fi
  TESTS_TO_RUN="$TESTS_TO_RUN $spec"
done < "$QUARANTINE_FILE"
npx jest $TESTS_TO_RUN                     # → гоняются отдельно, падение не блокирует
```

- Каждый элемент: файл карантина версионируется (PR-ревью на каждое добавление), TTL обязателен, просроченный пункт делает задачу красной — карантин нельзя забыть навсегда.
- **Валидация**: основная задача зелёная при падающем quarantined-тесте; задача `quarantine` показывает фактические падения; при истёкшем TTL пайплайн красный с ошибкой-напоминанием.

## Устранение неполадок

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Отчёт не появился в PR | Не хватает `checks: write`; либо форк-PR | Добавить permission; для форков — паттерн артефакт + `workflow_run` |
| Красные тесты без отчёта | Публикация без `if: always()` | Перенести шаг публикации вне условия успеха |
| `require_tests` валит зелёную сборку | Раннер не записал XML (неверный путь/репортер) | Проверить локально путь отчёта и переменную вывода |
| Дублированные аннотации | Отчёт публикуется дважды (шаг + матрица-агрегатор) | Публиковать один раз: либо per-shard без аннотаций, либо агрегат |
| Watcher перезапускает сам себя | Нет фильтра по времени/воркфлоу | Ограничить выборку свежими завершёнными прогонами целевого workflow |
| Ретрай маскирует регрессию | Повтор применяется к детерминированным тестам | Убрать retry, перевести тесты в карантин с TTL и тикетом на починку |
| Аннотации в PR обрываются на ~20 упавших тестах | Лимит GitHub Actions: 10 warning + 10 error аннотаций на шаг | Ориентироваться на summary-таблицу и артефакт XML; при необходимости — `annotations_limit` в action-junit-report |
| Rerun падает с 403 | У токена нет `actions: write` | Добавить `permissions: actions: write` на уровне воркфлоу или задачи |
| Rerun недоступен для старого прогона | Окно перезапуска — 30 дней с исходного прогона | Запустить новый прогон той же ревизии (`workflow_dispatch` с `ref`) |
| Отчёт пустой, хотя Jest локально пишет XML | Используется устаревшая `JEST_JUNIT_OUTPUT` — текущий jest-junit её не читает и пишет `junit.xml` в корень | Перейти на `JEST_JUNIT_OUTPUT_DIR` + `JEST_JUNIT_OUTPUT_NAME` |

## Лучшие практики

1. Отчёт публикуется всегда (`always()`), а отсутствие отчёта — ошибка (`require_tests`), а не тихий пропуск.
2. Один источник правды об аггрегате: аннотации публикует единственный шаг (агрегирующий), шарды — только XML.
3. Flaky лечится в порядке: причина → карантин с TTL → ретрай; обратный порядок накапливает технический долг.
4. Авто-rerun допустим только для регламентных нагрузок (ночные прогоны), где ложнокрасный дороже лишних минут.
5. Метрика повторных попыток (retries rate) — часть дашборда CI, а не скрытая магия в логах.
6. Для больших сьютов аннотации — не главный источник правды (лимит 10+10 на шаг): итоговая таблица в summary и артефакт XML переживут любое число падений.
