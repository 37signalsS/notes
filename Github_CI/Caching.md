# GitHub Actions: Кеширование

Кеширование — один из самых эффективных способов ускорить выполнение CI/CD (Continuous Integration / Continuous Deployment) пайплайнов в GitHub Actions. Его основная цель — сохранение файлов (например, зависимостей или результатов сборки) между запусками воркфлоу, чтобы избежать их повторного скачивания или повторной генерации.

## Определения

- **Кеш (Cache)**: Выделенное хранилище, привязанное к репозиторию, в котором можно сохранять файлы и директории. Доступ к кешу осуществляется по уникальному ключу.
- **`actions/cache`**: Официальный `action` от GitHub для управления кешированием. Текущая актуальная версия — `v6.1.0` (июль 2026).
- **Cache Service v2**: Обновленный бэкенд сервиса кеширования (внедрен в феврале 2025), обеспечивающий повышенную пропускную способность и надежность. Скорость загрузки увеличена до 80%.

## Основные концепции

### Механизм работы кеширования

Процесс обработки кеша разделен на два основных этапа:

1. **Восстановление (Restore)**: В начале задачи (`job`) действие `actions/cache` ищет существующий кеш по указанному ключу (`key`). При полном совпадении содержимое кеша восстанавливается в целевую директорию (`path`). Если точное совпадение отсутствует, выполняется поиск по префиксам из списка `restore-keys`.
2. **Сохранение (Save)**: В конце выполнения задачи, если на этапе восстановления не было найдено точного совпадения ключа, создается новый кеш с текущим содержимым указанной директории.

**Выходной параметр `cache-hit`**:
Действие `actions/cache` возвращает логическое значение `cache-hit`. Оно равно `true` только при **точном совпадении** ключа. Это позволяет пропускать тяжелые шаги (например, установку зависимостей), если кеш актуален.

**Особенности Cache Service v2 (Сервис кеширования v2)**:

- Обязательно использование `actions/cache@v5` или выше (рекомендуется `v6`).
- Для self-hosted runners (собственные агенты сборки) требуется версия runner ≥2.327.1.
- Возможность раздельного управления через `actions/cache/restore` и `actions/cache/save` для тонкой настройки пайплайнов.

### Управление ключами кеша

Ключ кеша — основной инструмент управления жизненным циклом данных.

- **`key`** (обязательный): Уникальная строка-идентификатор. Кеш восстанавливается только при **полном совпадении** (exact match).
- **`restore-keys`** (опциональный): Упорядоченный список префиксов. Если точный `key` не найден, используется самый свежий кеш, ключ которого начинается с одного из указанных префиксов.
- **`enableCrossOsArchive`** (опциональный): При значении `true` позволяет восстанавливать кеш, созданный на другой операционной системе (например, использовать кеш с Linux на Windows, если содержимое кросс-платформенное).

Типовая структура ключа:
`{{ runner.os }}-{{ tool_name }}-{{ hashFiles('dependency-file') }}`

Использование `hashFiles` гарантирует, что при изменении состава зависимостей (например, в `package-lock.json` или `requirements.txt`) хеш изменится, что приведет к созданию нового актуального кеша.

### Ограничения и политики

- **Объем данных**: Базовый лимит на один кеш — 10 ГБ. Суммарный объем на репозиторий — 10 ГБ бесплатно. Начиная с 2026 года, лимит может быть превышен по модели **pay-as-you-go** (оплата за фактическое использование сверх порога).
- **Время жизни**: Данные удаляются автоматически, если к ним не обращались более 7 дней. Срок хранения может быть настроен в политиках репозитория.
- **Неизменяемость (Immutability)**: Существующий кеш по конкретному ключу нельзя обновить. Изменения фиксируются только созданием нового кеша с новым ключом.
- **Политика вытеснения**: При достижении лимита объема удаляются старые данные по алгоритму **LRU (Least Recently Used — «наименее недавно использовавшийся»)** — первыми удаляются те кеши, к которым дольше всего не было обращений.
- **Безопасность**: Запрещено хранить в кеше чувствительные данные (токены, пароли). Кеш доступен для чтения всем процессам в рамках репозитория, включая запуски из форков для базовой ветки.

### Встроенная поддержка в setup-actions

Многие официальные действия для настройки окружения имеют встроенную поддержку кеширования, что является предпочтительным способом настройки:

| Менеджер пакетов | Action | Параметр `cache` |
| :--- | :--- | :--- |
| npm, Yarn, pnpm | `actions/setup-node@v7` | `cache: 'npm'`, `yarn` или `pnpm` |
| pip, pipenv, Poetry | `actions/setup-python@v7` | `cache: 'pip'`, `pipenv` или `poetry` |
| Gradle, Maven | `actions/setup-java@v5` | `cache: 'gradle'` или `maven` |
| RubyGems | `actions/setup-ruby@v1` | `cache: 'bundler'` |
| Go | `actions/setup-go@v5` | `cache: true` |
| .NET NuGet | `actions/setup-dotnet@v4` | `cache: true` |

## Практические сценарии

### Сценарий 1: Кеширование зависимостей Node.js (npm)

Использование встроенного механизма в `setup-node`:

```yaml
steps:
  - uses: actions/checkout@v7
  - name: Setup Node.js
    uses: actions/setup-node@v7
    with:
      node-version: '22' # Актуальная LTS
      cache: 'npm' # Автоматическое кеширование ~/.npm
      cache-dependency-path: '**/package-lock.json'
  - run: npm ci
```

### Сценарий 2: Ручное управление кешем для специфических путей

Когда требуется кешировать директории, не поддерживаемые стандартными `setup-actions`:

```yaml
steps:
  - uses: actions/checkout@v7
  - name: Cache arbitrary path
    id: cache-custom
    uses: actions/cache@v6
    with:
      path: |
        ~/.cache/custom-tool
        build/temp
      key: ${{ runner.os }}-custom-${{ hashFiles('config/tool-config.json') }}
      restore-keys: |
        ${{ runner.os }}-custom-
```

## Управление кешем через GitHub CLI и веб-интерфейс

Помимо автоматического управления, GitHub предоставляет инструменты для ручного мониторинга и удаления кешей. Это полезно при достижении лимитов объема или необходимости принудительной инвалидации.

### Веб-интерфейс (UI)
1. Перейдите в раздел **Actions** вашего репозитория.
2. В левом меню выберите **Management → Caches**.
3. Доступен просмотр списка кешей, их размера и даты последнего обращения. Здесь же можно удалить конкретные записи или все сразу.

### GitHub CLI (`gh`)
Использование расширения `gh-cache` или встроенных команд (зависит от версии `gh`):
- `gh cache list` — просмотр списка кешей.
- `gh cache delete <cache_id_or_key>` — удаление кеша по идентификатору или ключу.
- `gh cache delete --all` — полная очистка хранилища.
