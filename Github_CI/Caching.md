# GitHub Actions: Кеширование

**Актуально для:** actions/cache v6.x (Cache Service v2, Node.js 24 runtime; self-hosted runner ≥ 2.327.1)

Кеширование — один из самых эффективных способов ускорить выполнение CI/CD (Continuous Integration / Continuous Deployment) пайплайнов в GitHub Actions. Его основная цель — сохранение файлов (например, зависимостей или результатов сборки) между запусками воркфлоу, чтобы избежать их повторного скачивания или повторной генерации. Типичный выигрыш — сокращение времени установки зависимостей с нескольких минут до секунд, поскольку архив распаковывается локально на раннере вместо обращения к внешним реестрам пакетов.

## Определения

- **Кеш (Cache)**: Выделенное временное хранилище, привязанное к репозиторию, позволяющее сохранять и восстанавливать данные по уникальному ключу.
- **`actions/cache`**: Официальный экшен GitHub для управления кешированием. Текущая актуальная версия — `v6.1.0`; линейка v5 также поддерживается. Начиная с v5 экшен работает на Node.js 24 и требует версию раннера не ниже `2.327.1`; начиная с v4 интегрирован с Cache Service v2 (Node.js 20); начиная с v6 экшен мигрирован на ESM. Для раздельного управления существуют подэкшены `actions/cache/restore` и `actions/cache/save` (линейка `v6`).
- **Ключ кеша (Cache Key)**: Уникальная строка, идентифицирующая содержимое кеша. Используется для поиска и восстановления данных. Максимальная длина — 512 символов; более длинный ключ приводит к ошибке экшена.
- **Cache Hit (Попадание)**: Состояние, при котором найден кеш, точно соответствующий значению `key`.
- **Cache Miss (Промах)**: Состояние, при котором точного совпадения `key` не найдено. В этом случае могут быть использованы `restore-keys` или создан новый кеш в конце задачи.
- **Политика вытеснения (Eviction Policy)**: Алгоритм автоматического удаления старых или редко используемых кешей для соблюдения лимитов хранилища.
- **Cache Service v2**: Обновленная инфраструктура сервиса кеширования, обеспечивающая повышенную производительность и надежность. Постепенный rollout начат 1 февраля 2025 года, legacy-сервис отключён в ту же дату; изменения полностью обратно совместимы. Для self-hosted раннеров требуется версия не ниже `2.231.0`.
- **Cache Version**: Служебный хеш, который генерируется из комбинации инструмента сжатия (Gzip или Zstd — зависит от ОС раннера) и списка путей `path`. Кеши с одинаковым ключом, но разными версиями считаются разными записями — именно поэтому кеш, созданный на `windows-latest`, по умолчанию нельзя восстановить на `ubuntu-latest`.
- **Post-run фаза**: Автоматический шаг, который экшен `actions/cache` регистрирует после всех шагов задачи и в котором выполняется сохранение кеша.
- **`cache-hit` (выходной параметр)**: Выход (`output`) шага с экшеном кеширования. Принимает значение `true` только если восстановление произошло по точному совпадению основного ключа `key`; при восстановлении по префиксу `restore-keys` или при отсутствии кеша — `false`.
- **`cache-dependency-path`**: Параметр setup-экшенов и ручного кеширования, указывающий файл(ы) зависимостей для расчета хеша ключа. Необходим в монорепозиториях, где lock-файл лежит не в корне.
- **`lookup-only`**: Режим работы экшена кеширования, при котором проверяется только существование кеша без его скачивания и распаковки. Полезен для условной логики («если кеш есть — пропустить установку»).
- **`fail-on-cache-miss`**: Вход экшена кеширования, при котором отсутствие кеша по основному ключу завершает воркфлоу с ошибкой. Полезен для задач, которые не могут работать без кеша (например, сборка на read-only-раннере). При использовании оставьте `restore-keys` пустым — иначе частичное совпадение по префиксу считается попаданием.
- **`cache-mode`**: Ключ воркфлоу (на уровне `jobs.<job_id>` или самого воркфлоу), управляющий доступом задачи к кешам: `read`, `write`, `write-only`, `none`. Значение на уровне job переопределяет значение на уровне воркфлоу. Раннер экспонирует эффективный режим в переменной окружения `ACTIONS_CACHE_MODE`.
- **Cache poisoning (отравление кеша)**: Класс атаки, при котором недоверенный воркфлоу (например, форк-PR через `pull_request_target`) записывает вредоносное содержимое в кеш, который позже восстанавливается привилегированным воркфлоу (`push`, `schedule`) — путь к выполнению произвольного кода и эксфильтрации секретов. Содержимое кеша не подписано и не верифицируется, поэтому восстановленные файлы следует относить к недоверенному входу.

## Основные концепции

### Механизм работы кеширования

Процесс работы с кешем делится на два основных этапа, выполняемых автоматически экшеном `actions/cache`:

1. **Восстановление (Restore)**:
   - В начале задачи (`job`) выполняется поиск кеша по значению `key`.
   - Если найдено точное совпадение, данные скачиваются и распаковываются в `path`.
   - Если точного совпадения нет, проверяется список `restore-keys` (поиск по префиксу). Используется самый свежий подходящий кеш.
   - Порядок поиска: точное совпадение `key` + Cache Version в текущей ветке → префиксные совпадения `key` в текущей ветке → `restore-keys` + Cache Version в текущей ветке → те же шаги повторяются на ветке по умолчанию.
2. **Сохранение (Save)**:
   - В конце выполнения задачи (в фазе `Post-run`) проверяется наличие точного совпадения ключа на этапе восстановления.
   - Если был Cache Miss, создается новый архив из содержимого `path` и загружается в хранилище под текущим ключом `key`.

Дополнительные детали поведения Post-run фазы:

- Post-шаг сохранения зарегистрирован с условием `post-if: success()`: он выполняется только при успешном завершении задачи. Если один из шагов завершился с ошибкой или задача отменена (cancel), сохранение пропускается. Чтобы сохранить кеш даже при падении тестов, используйте явный шаг `actions/cache/save` с условием `if: always()` (см. раздел о раздельном сохранении). Вход `save-always` экшена deprecated — он не работает как задумано и будет удалён.
- Архив создаётся со сжатием: Zstd на Linux/macOS, Gzip на Windows. Поэтому содержимое кеша — это единый tar-архив, а не копия каталога.
- Режим `lookup-only: true` выполняет только первый этап (проверку наличия), не занимая время и место на распаковку.

### Управление ключами и изоляция

Ключ кеша является неизменяемым идентификатором. Если кеш с таким ключом уже существует, он не будет перезаписан.

- **Структура ключа**: Рекомендуется использовать комбинацию ОС, имени менеджера пакетов и хеша файлов зависимостей.
  `{{ runner.os }}-node-{{ hashFiles('**/package-lock.json') }}`
  Функция `hashFiles` принимает несколько шаблонов через запятую и возвращает хеш конкатенированного содержимого найденных файлов: `hashFiles('**/package-lock.json', '**/npm-shrinkwrap.json')`.
- **Изоляция по веткам**:
  - Кеши изолированы на уровне веток.
  - Задача в ветке `feature` может получить доступ к кешам базовой ветки (например, `main`), но не наоборот.
  - Ветки не могут перезаписывать кеши друг друга.
  - На практике действует иерархия доступа: задача сначала ищет кеш среди записей своей ветки, затем — среди записей ветки по умолчанию. Записи других feature-веток недоступны.
  - Запуски из PR могут восстанавливать кеши текущей ветки, ветки по умолчанию и base-веток (включая base-ветки форкнутых репозиториев). Кеши дочерних и sibling-веток недоступны. Кеши тегов изолированы по имени тега: кеш, созданный для тега `release-a`, недоступен запуску по тегу `release-b`.
- **Pull Requests**: Запуски из форков имеют доступ к кешам основной ветки, но не могут сохранять свои кеши в основное хранилище (в целях безопасности). Для обычных (не форкнутых) PR кеш сохраняется под рефом вида `refs/pull/<номер>/merge` и доступен только перезапускам этого же PR.
- **Reusable Workflows**: Вызываемый воркфлоу использует область видимости (scope) кеша вызывающего репозитория, а не своего собственного. Доступ вызываемого воркфлоу ограничен `cache-mode` вызывающей задачи: если job задаёт максимум `read`, вызываемый воркфлоу не может запросить `write` (запуск не стартует, GitHub сообщает об ошибке валидации).

### Ограничения и политики

- **Лимит объема**: Бесплатный лимит на репозиторий составляет 10 ГБ. Лимит можно увеличить в настройках Actions (enterprise/org/repo-администраторами; для пользовательских репозиториев — до 10 ТБ) по модели pay-as-you-go — за превышение 10 ГБ взимается плата за использованное место. При превышении лимита GitHub сохраняет новый кеш, а затем применяет алгоритм **LRU (Least Recently Used)**, удаляя записи с наиболее старой датой последнего обращения (`last_accessed_at`), пока суммарный размер не окажется в пределах лимита. Частое создание и удаление записей при нехватке места называется cache thrashing — признак того, что лимит нужно поднять или сократить кешируемые пути. Количество записей не ограничено; лимит кеша не расходует квоту хранения артефактов и пакетов — это независимое хранилище.
- **Время жизни (retention)**: Кеш автоматически удаляется, если к нему не было обращений (чтения) более 7 дней. Срок настраивается политикой «cache retention limit (days)» на уровне enterprise, организации или репозитория (политики каскадом сверху вниз).
- **Бюджеты**: При превышении бюджета Actions Cache Storage SKU кеш репозитория переводится в режим read-only до следующего платёжного цикла — восстановление работает, сохранение нет.
- **Rate limits**: До 200 загрузок (upload) и 1500 скачиваний (download) кешей в минуту на репозиторий. При превышении операции падают до сброса лимита; время до сброса возвращается в заголовке ответа `Retry-After`.
- **Неизменяемость**: После создания кеш нельзя изменить. Для обновления данных необходимо изменить ключ (например, обновив файл зависимостей или добавив версию в префикс ключа).
- **Cross-OS Caching**: Параметр `enableCrossOsArchive: true` (начиная с actions/cache v3.2.3) позволяет сохранять и восстанавливать кеши между ОС (например, использовать кеш с Linux на Windows, если это допустимо для конкретных данных). Технически этот параметр отключает учет Cache Version, привязанной к инструменту сжатия конкретной ОС. Флаг должен быть выставлен и на стороне сохранения, и на стороне восстановления. Ограничения: кешируйте только совместимые между ОС файлы; symlinks могут восстанавливаться некорректно (поведение различается между ОС); избегайте абсолютных путей (`~`, `${{ github.workspace }}`) — они резолвятся по-разному на разных ОС.
- **Размер записи и сегментирование**: Нет жесткого официального предела на размер одного архива, но большие архивы (>2 ГБ) медленно упаковываются и восстанавливаются, что нивелирует выгоду. Скачивание разбивается на сегменты; если сегмент зависает, таймаут (10 минут по умолчанию, настраивается переменной `SEGMENT_DOWNLOAD_TIMEOUT_MINS` в минутах) прерывает загрузку, и задача продолжается с Cache Miss. Загрузка больших файлов дробится на чанки (вход `upload-chunk-size`, в байтах).

### Cache Version и совместимость архивов

Помимо пользовательского ключа, каждая запись имеет внутренний атрибут **Cache Version** — хеш от комбинации инструмента сжатия (зависит от ОС раннера) и списка путей `path`. Следствия:

1. Один и тот же ключ `primes` создаст разные записи на Ubuntu и Windows (разное сжатие), а также в задачах с разными списками `path`.
2. Изменение набора путей `path` в воркфлоу делает все прежние кеши недоступными для нового варианта, даже если ключ не изменился — это частая причина «необъяснимых» Cache Miss.
3. Диагностика: атрибут версии можно получить через [REST API списка кешей](https://docs.github.com/en/rest/actions/cache) и сравнить у записей с одинаковым ключом, созданных на разных ОС.

### Встроенная поддержка в setup-actions

Наиболее эффективный способ кеширования зависимостей — использование встроенных параметров в `setup-*` экшенах. Это упрощает конфигурацию и автоматически обрабатывает правильные пути.

| Инструмент | Экшен | Параметр `cache` |
| :--- | :--- | :--- |
| Node.js (npm, yarn, pnpm) | `actions/setup-node@v7` | `npm`, `yarn`, `pnpm` |
| Python (pip, poetry, pipenv) | `actions/setup-python@v7` | `pip`, `poetry`, `pipenv` |
| Java (Maven, Gradle, sbt) | `actions/setup-java@v6` | `maven`, `gradle`, `sbt` |
| Go (modules) | `actions/setup-go@v6` | `true` (включено по умолчанию с v4) |
| Ruby (bundler) | `ruby/setup-ruby@v1` | `bundler-cache: true` |
| .NET (NuGet) | `actions/setup-dotnet@v6` | `true` |

Примечания к таблице:

- Строки таблицы соответствуют актуальным мажорным версиям на момент обновления (октябрь 2026); перед обновлением pinned-версий сверяйтесь со страницей releases каждого экшена (мажорные линеек регулярно переходят на новые runtime-версии Node.js с требованиями к минимальной версии раннера).
- Исторический экшен `actions/setup-ruby@v1` официально deprecated и более не поддерживается — для Ruby используется поддерживаемый сообществом `ruby/setup-ruby` с параметром `bundler-cache: 'true'`; параметр `cache-version` сбрасывает кеш при смене значения (например, при изменении структуры Gemfile).
- Все setup-экшены принимают `cache-dependency-path` — путь или glob до lock-файлов. Обязателен, когда lock-файл не лежит в корне репозитория или менеджеров несколько.
- **setup-go v6 (breaking change)**: ключ кеша по умолчанию строится от `go.mod`; если инвалидация должна зависеть от `go.sum`, укажите `cache-dependency-path: go.sum` явно.
- **setup-dotnet v5+ (breaking change)**: кеширование ищет `packages.lock.json` в корне репозитория и завершается ошибкой при отсутствии lock-файла; для монорепозиториев указывайте `cache-dependency-path`. Размер кеша сокращается переменной `NUGET_PACKAGES: ${{ github.workspace }}/.nuget/packages`.
- В `setup-java` доступны расширенные параметры кеширования: `cache-read-only: true` (только чтение — удобно для матричных задач-потребителей), `cache-path` (кастомные пути кеша), `cache-jdk: true` (кеширование скачанных JDK между задачами, включено по умолчанию при настроенном `cache`). Выходы: `cache-hit` и `cache-primary-key` — вычисленный основной ключ, который можно передать в `actions/cache`/`actions/cache/save` для согласованного кеширования между задачами.
- `actions/checkout@v7` — текущая линейка (v7.0.1); начиная с v6 учётные данные хранятся в отдельном файле под `$RUNNER_TEMP` вместо `.git/config` (для аутентифицированных git-команд из Docker-контейнеров требуется раннер ≥ 2.329.0). Мажоры на Node.js 20 (`@v4` и старше) выдают deprecation-предупреждения на hosted-раннерах — Node 20 удалён с раннеров 16 сентября 2026 года.

### Отличие кеша от артефактов

Кеш и артефакты (artifacts) решают разные задачи, хотя оба являются хранилищами файлов:

| Аспект | Кеш (Cache) | Артефакт (Artifact) |
| :--- | :--- | :--- |
| Назначение | Ускорение повторных сборок | Хранение результатов сборки для последующего использования |
| Гарантия наличия | Не гарантирован (может быть вытеснен LRU или 7-дневным TTL) | Гарантирован на срок retention-политики |
| Доступ между запусками | По неизменяемому ключу, с изоляцией по веткам | По имени внутри конкретного запуска воркфлоу |
| Мутабельность | Иммутабелен | Можно дополнить (в одной линейке версий upload/download) |
| Типичное содержимое | Зависимости, кеши компиляторов, Docker-слои | Бинарники, отчёты тестов, логи, пакеты для деплоя |

Правило выбора: если потеря данных ломает пайплайн — используйте артефакты; если данные можно восстановить пересборкой — используйте кеш.

### Безопасность доступа и `cache-mode`

GitHub разделяет триггеры на доверенные и недоверенные (low-trust) для предотвращения cache poisoning:

- **Доверенные триггеры** (полный read-write доступ к кешам в scope ветки по умолчанию): `push`, `workflow_dispatch`, `repository_dispatch`, `delete`, `registry_package`, `page_build`, `schedule`.
- **Недоверенные триггеры** (`pull_request_target`, `issue_comment`, `workflow_run` и другие события, инициируемые без write-доступа к репозиторию): с июня 2026 года получают **read-only** cache-токен для scope ветки по умолчанию. Восстановление работает, при попытке сохранения экшен логирует предупреждение, а шаг и задача продолжаются без сохранения. Событие `pull_request` не затронуто: его кеши пишутся в merge-ref scope (`refs/pull/.../merge`), а не в scope ветки по умолчанию.
- **`cache-mode`** — явное управление доступом на уровне воркфлоу или job (значение job переопределяет воркфлоу):

| Значение | Восстановление | Сохранение |
| :--- | :--- | :--- |
| `read` | Да | Нет |
| `write` | Да | Да |
| `write-only` | Нет | Да |
| `none` | Нет | Нет |

  Если `cache-mode` не задан, доступ по умолчанию определяется типом триггера: `write` для доверенных, `read` для недоверенных. Пропущенные из-за режима операции логируются информационным сообщением и не падают шаг; пропущенное восстановление трактуется как Cache Miss. Эффективный режим доступен в переменной окружения `ACTIONS_CACHE_MODE`.

- **Reusable Workflows**: `cache-mode` наследуется от вызывающего воркфлоу. Если вызывающий job явно ограничен (например, `read`), вызываемый воркфлоу не может запросить больший доступ — запуск не стартует с ошибкой валидации. Если job не задаёт `cache-mode` явно, вызываемый воркфлоу может запросить `write` даже при недоверенном триггере вызывающего; чтобы ограничить его, задайте `cache-mode: read` на вызывающем job.

> **Внимание:** явное объявление `cache-mode: write` или `write-only` на недоверенном триггере возвращает риск cache poisoning, который read-only-дефолт предотвращает. Если переопределение необходимо — обрабатывайте восстановленный кеш как недоверенный вход и не восстанавливайте его в задачах с секретами или повышенными правами.

**Базовые правила безопасности:** содержимое кеша не подписано и не верифицируется — любой воркфлоу с доступом на чтение может извлечь его. Никогда не храните секреты, токены и креденшелы в кешируемых путях; ограничивайте запись кешей доверенными триггерами; применяйте `cache-mode` по принципу least privilege.

## Практические сценарии

### Сценарий 1: Кеширование Node.js (npm) через setup-node

Самый простой и рекомендуемый способ:

```yaml
steps:
  - uses: actions/checkout@v7
  - uses: actions/setup-node@v7
    with:
      node-version: '22'
      cache: 'npm'
  - run: npm ci
```

Требования и проверка:

- Предусловие: `actions/checkout` должен выполниться **до** setup-экшена, иначе lock-файл недоступен и хеш ключа не рассчитается (кеш молча не сработает).
- Валидация: в логах шага setup-node ожидаемо появится строка вида `Cache restored from key: Linux-npm-<hash>` (первый запуск покажет `Cache not found for input keys: ...` — это нормально, кеш будет создан в Post-run фазе).

Вариант для монорепозитория (lock-файлы в подпапках):

```yaml
steps:
  - uses: actions/checkout@v7
  - uses: actions/setup-node@v7
    with:
      node-version: '22'
      cache: 'npm'
      cache-dependency-path: |
        apps/frontend/package-lock.json
        apps/backend/package-lock.json
  - run: npm ci --workspaces
```

Хеш ключа здесь учитывает оба lock-файла: изменение любого из них порождает новый ключ.

### Сценарий 2: Кеширование Python (Poetry)

```yaml
steps:
  - uses: actions/checkout@v7
  - uses: actions/setup-python@v7
    with:
      python-version: '3.12'
      cache: 'poetry'
      cache-dependency-path: 'poetry.lock'
  - run: poetry install
```

Для остальных менеджеров Python меняется только значение `cache`: `pip` (ключ строится по `requirements*.txt` — при их отсутствии обязательно указать `cache-dependency-path`) или `pipenv` (по `Pipfile.lock`). Важно фиксировать точные версии зависимостей в файлах: если в requirements указаны версии без пинов, установка всегда тянет свежие пакеты, и смысл кеша теряется.

### Сценарий 3: Ручное кеширование произвольных путей

Используется для специфических инструментов или промежуточных результатов сборки:

```yaml
steps:
  - uses: actions/checkout@v7
  - name: Cache Compiler Data
    id: compiler-cache
    uses: actions/cache@v6
    with:
      path: .build-cache
      key: ${{ runner.os }}-build-${{ github.sha }}
      restore-keys: |
        ${{ runner.os }}-build-
```

Разбор параметров:

- `path` — каталоги или файлы для упаковки (можно перечислить многострочно через `|`). Пути относительно рабочей директории; допустимы абсолютные (`~/.cache/go-build`).
- `key` — основной ключ. Здесь он включает SHA коммита, то есть каждый коммит порождает новый кеш, что подходит для артефактов промежуточной сборки.
- `restore-keys` — список префиксов для частичного восстановления (сверху вниз, берётся самое свежее совпадение). Позволяет получить «старую» версию данных вместо полного промаха.
- `id` — необязателен, но нужен для обращения к выходному параметру.

Использование выхода `cache-hit` для условного выполнения тяжелой операции:

```yaml
  - name: Generate Primes
    if: steps.compiler-cache.outputs.cache-hit != 'true'
    run: ./generate-primes.sh -d .build-cache
```

Генерация выполняется только при полном промахе; при попадании по точному ключу данные уже готовы.

### Сценарий 4: Кеширование Docker-слоев (BuildKit)

Современный способ использования кеша GitHub Actions внутри Docker:

```yaml
- name: Set up Docker Buildx
  uses: docker/setup-buildx-action@v4

- name: Build and push
  uses: docker/build-push-action@v6
  with:
    push: true
    tags: user/app:latest
    cache-from: type=gha
    cache-to: type=gha,mode=max
```

Разбор:

- `type=gha` — бэкенд кеширования, использующий то же хранилище GitHub Actions (лимит по умолчанию 10 ГБ, настраиваемый, делится между всеми записями репозитория, включая dependency-кеши).
- `mode=max` — экспортировать слои не только финального образа, но и всех промежуточных стадий multi-stage сборки. Без него кешируется только итоговый результат.
- `scope` (опционально) — именованное пространство внутри gha-бэкенда, чтобы разделить кеши разных образов: `cache-to: type=gha,mode=max,scope=api`.

Альтернатива при исчерпании квоты — кеширование в container registry (не расходует лимит Actions):

```yaml
    cache-from: type=registry,ref=ghcr.io/user/app:buildcache
    cache-to: type=registry,ref=ghcr.io/user/app:buildcache,mode=max
```

### Сценарий 5: Кеширование Go-модулей (setup-go v6)

```yaml
steps:
  - uses: actions/checkout@v7
  - uses: actions/setup-go@v6
    with:
      go-version: '1.25'
      cache: true
  - run: go build ./...
```

Нюансы v6: `cache: true` включён по умолчанию, ключ строится от `go.mod`. Если сборка зависит от точного состава `go.sum` (например, при `go mod verify`), укажите `cache-dependency-path: go.sum` — иначе изменение `go.sum` без изменения `go.mod` не инвалидирует кеш.

### Сценарий 6: Java/Maven — «сеятель + потребители» с read-only кешем

Паттерн для матричных сборок: одна задача заполняет кеш зависимостей, остальные читают его без перезаписи:

```yaml
jobs:
  seed-cache:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '25'
          cache: maven
      - run: mvn dependency:go-offline dependency:resolve-plugins

  build:
    needs: seed-cache
    strategy:
      matrix:
        goal: [test, verify]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '25'
          cache: maven
          cache-read-only: true
      - run: mvn ${{ matrix.goal }}
```

`cache-read-only: true` восстанавливает кеш, но не сохраняет изменения в post-фазе — параллельные матричные задачи не конфликтуют за запись по одному ключу.

## Продвинутые сценарии и оптимизация

### Раздельное сохранение и восстановление

Для сложных пайплайнов можно использовать отдельные экшены `actions/cache/restore` и `actions/cache/save`. Это позволяет:
- Восстановить кеш в одной задаче, а сохранить только в случае успеха тестов.
- Управлять моментом сохранения для предотвращения записи "грязного" кеша.

Полный пример: кеш сохраняется только если тесты прошли успешно.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - name: Restore cache
        id: restore-deps
        uses: actions/cache/restore@v6
        with:
          path: ~/.npm
          key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
          restore-keys: ${{ runner.os }}-node-

      - run: npm ci
      - run: npm test

      - name: Save cache only on success
        if: success()
        uses: actions/cache/save@v6
        with:
          path: ~/.npm
          key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
```

Нюансы:

- `actions/cache/save` требует явный полный `key` (без `restore-keys`), так как не выполняет поиск, а только запись.
- Post-фаза экшена `actions/cache` выполняется с `post-if: success()` — при падении шагов кеш не сохраняется. Явный шаг `actions/cache/save` подчиняется своему `if` (по умолчанию тоже `success()`); без условия он не выполнится после падения тестов — для сохранения при падении укажите `if: always() && steps.<restore-id>.outputs.cache-hit != 'true'`.
- Ключ должен отличаться от уже существующих записей — иначе сохранение молча пропустится (неизменяемость кеша).
- Выход `cache-primary-key` шага restore позволяет переиспользовать вычисленный ключ в save-шаге (`key: ${{ steps.restore-deps.outputs.cache-primary-key }}`) — ключ не пересчитывается в момент сохранения, что важно, когда lock-файлы генерируются в ходе сборки.
- Подэкшены `actions/cache/restore@v6` и `actions/cache/save@v6` ссылаются на директории `restore/` и `save/` в теге `v6` репозитория `actions/cache` (проверено: тег содержит оба `action.yml`); официальные README-примеры по-прежнему показывают `@v5`.

### Предотвращение гонки данных (Race Conditions)

Если несколько параллельных задач пытаются создать кеш с одним и тем же ключом, победит та, которая завершится первой. Остальные получат ошибку "Cache already exists", которая игнорируется экшеном. Чтобы избежать этого, включайте в ключ `github.run_id` или другие уникальные идентификаторы, если кеш специфичен для конкретного запуска.

Обратная ситуация — намеренное совместное использование: для матричных сборок полезен паттерн «сеятель + потребители»: одна задача заполняет кеш, остальные используют его в режиме read-only (см. параметр `cache-read-only` в `setup-java` или `lookup-only`-логику). Подробнее о параллелизме — в разделе о матричных сборках.

### Очистка кешей закрытых Pull Request

Кеши PR занимают квоту репозитория и вытесняют полезные записи основной ветки. Официально рекомендуемая практика — автоматическое удаление кешей при закрытии PR:

```yaml
name: Cleanup caches on closed pull requests
on:
  pull_request:
    types:
      - closed

jobs:
  cleanup:
    runs-on: ubuntu-latest
    permissions:
      actions: write
    steps:
      - name: Cleanup
        run: |
          echo "Fetching list of cache keys"
          cacheKeysForPR=$(gh cache list --ref $BRANCH --limit 100 --json id --jq '.[].id')

          set +e
          echo "Deleting caches..."
          for cacheKey in $cacheKeysForPR
          do
              gh cache delete $cacheKey
          done
          echo "Done"
        env:
          GH_TOKEN: ${{ github.token }}
          GH_REPO: ${{ github.repository }}
          BRANCH: refs/pull/${{ github.event.pull_request.number }}/merge
```

Ключевые моменты: требуется право `permissions: actions: write`; реф PR в CLI формате — `refs/pull/<номер>/merge`; `set +e` гарантирует, что сбой удаления одной записи не уронит задачу. Для форкнутых PR такой воркфлоу следует запускать по событию `pull_request_target` (с учетом связанных рисков безопасности).

## Устранение неполадок

### Кеш не восстанавливается
- **Проблема**: Ключ не совпадает из-за различий в ОС (например, `\r\n` в файлах зависимостей на Windows).
- **Решение**: Используйте `hashFiles` с нормализованными путями или включите `enableCrossOsArchive`.
- **Проблема**: Изоляция веток.
- **Решение**: Проверьте, создан ли кеш в базовой ветке или текущей.
- **Проблема**: Cache Miss из-за внутренней Cache Version — изменился список `path` или ОС раннера при том же ключе.
- **Решение**: Сравните поле версии записей через REST API; убедитесь, что список путей стабилен между запусками.

Диагностика: включите пошаговое логирование, задав секрет `ACTIONS_STEP_DEBUG` в значение `true` — в логах появятся подробности поиска ключей и сопоставления версий. Также `gh cache list --key <prefix>` показывает фактические ключи и ветки существующих записей.

### Кеш не сохраняется
- **Проблема**: Точное совпадение ключа уже найдено (Cache Hit). GitHub не обновляет существующие кеши.
- **Решение**: Измените ключ (например, добавьте инкрементальную версию: `v1`, `v2`).
- **Проблема**: Задача завершилась с ошибкой или была отменена (cancel) — Post-run сохранение пропущено (`post-if: success()`).
- **Решение**: Это штатное поведение; для сохранения при падении используйте явный шаг `actions/cache/save` с `if: always()`.
- **Проблема**: Недоверенный триггер (`pull_request_target`, `issue_comment`, `workflow_run`) получил read-only cache-токен для scope ветки по умолчанию — сохранение пропущено с предупреждением в логе.
- **Решение**: См. раздел о `cache-mode`; поддерживайте актуальность кеша из доверенного воркфлоу (`push`), а недоверенные воркфлоу переключите на restore-only (`actions/cache/restore`).
- **Проблема**: Превышен лимит (10 ГБ по умолчанию) и вытеснение не успевает за записью (cache thrashing).
- **Решение**: Удалите старые кеши вручную, сократите `path` или поднимите лимит в настройках Actions.

### Типичные сообщения об ошибках

| Сообщение в логе | Причина | Действие |
| :--- | :--- | :--- |
| `Cache not found for input keys: ...` | Нет записи ни по ключу, ни по префиксам | Штатный первый запуск; проверить структуру ключа |
| `Warning: Failed to restore: ...` / сегментные ошибки | Таймаут загрузки сегмента, нестабильная сеть | Увеличить таймаут: `env: SEGMENT_DOWNLOAD_TIMEOUT_MINS: '20'` (по умолчанию 10) |
| `Reserving cache failed` / конфликт записи | Параллельная задача уже создала запись с этим ключом | Игнорируется экшеном; см. Race Conditions выше |
| Предупреждение о read-only cache при сохранении | Недоверенный триггер, scope ветки по умолчанию | См. `cache-mode`; обновлять кеш из trusted-воркфлоу |
| Job failed после `fail-on-cache-miss` | Штатный fail-on-cache-miss: кеша по основному ключу нет | Проверить ключ/ветку; отключить `fail-on-cache-miss` для необязательного кеша |
| Медленное восстановление большого кеша | Архив >2 ГБ, низкая скорость сервиса | Раздробить на несколько меньших кешей, исключить лишнее из `path` |

## Управление через интерфейс и CLI

### Веб-интерфейс
Находится в разделе **Actions → Management → Caches**. Позволяет:
- Видеть размер каждого кеша.
- Удалять конкретные записи.
- Оценивать суммарное потребление места.
- Фильтровать записи по ключу (синтаксис `key:<имя>`) и видеть ветку создания и дату последнего использования.

Удаление доступно пользователям с правами `write` на репозиторий.

### GitHub CLI (`gh`)
Команды управления кешем встроены в актуальные версии `gh` (нативная команда `gh cache`, ранее поставлялась как расширение `actions/gh-actions-cache`, которое интегрировано в ядро и больше не требует установки; алиас — `gh cache ls`):

```bash
# Список кешей (JSON-поля: createdAt, id, key, lastAccessedAt, ref, sizeInBytes, version)
gh cache list
# → <id>  <key>  <size>  <created>  <last-accessed>

# Фильтрация: по префиксу ключа, по рефу ветки, сортировка (created_at | last_accessed_at | size_in_bytes)
gh cache list --key linux-node-
gh cache list --ref refs/heads/main
gh cache list --sort size_in_bytes --order desc --limit 100   # --limit по умолчанию 30

# Удаление по id или ключу
gh cache delete 1234
gh cache delete linux-node-a68c45df

# Удаление по ключу и ветке (одинаковые ключи существуют в разных ветках)
gh cache delete my-key --ref refs/heads/feature-branch

# Полная очистка хранилища репозитория
gh cache delete --all
# Возврат кода 0, если кешей нет (обязательно с --all; удобно в скриптах)
gh cache delete --all --succeed-on-no-caches
```

Для авторизации требуется scope `repo`. Один и тот же ключ может соответствовать нескольким записям (разные ветки или разные Cache Version) — удаление по ключу затронет все такие записи в пределах выбранного рефа.

### REST API

Те же операции доступны программно:

```bash
# Список кешей с метаданными (включая внутреннюю версию)
curl -H "Authorization: Bearer $GH_TOKEN" \
  "https://api.github.com/repos/{owner}/{repo}/actions/caches"

# Полная очистка
curl -X DELETE -H "Authorization: Bearer $GH_TOKEN" \
  "https://api.github.com/repos/{owner}/{repo}/actions/caches"
```

Эндпоинты: получение списка и статистики (`GET /repos/{owner}/{repo}/actions/caches`), удаление всех (`DELETE /repos/{owner}/{repo}/actions/caches`), удаление одной записи по id (`DELETE /repos/{owner}/{repo}/actions/caches/{cache_id}`).

## Лучшие практики и очистка

1. **Сначала setup-экшены**: используйте встроенный `cache`-параметр `actions/setup-*` везде, где он есть, и переходите на `actions/cache` только для нестандартных путей.
2. **Компонуйте ключ осмысленно**: ОС + менеджер + хеш lock-файла. Добавляйте статический префикс версии (`v1-...`) для возможности массовой инвалидации сменой одной буквы.
3. **Кешируйте только нужное**: включайте в `path` каталоги зависимостей и кешей инструментов, а не весь `node_modules` вместе с временными файлами — меньше архив, быстрее восстановление.
4. **Никогда не кешируйте секреты**: каталоги типа `~/.ssh`, `~/.aws`, токены и креденшелы не должны попадать в кеш — они доступны всем задачам веток-потомков. Относитесь к восстановленному содержимому как к недоверенному входу: кеш не подписан и не верифицируется.
5. **Применяйте `cache-mode` по принципу least privilege**: задачам-потребителям — `read`, задачам-генераторам — `write`; не объявляйте `write` на недоверенных триггерах без необходимости.
6. **Используйте `fail-on-cache-miss: true`** для задач, которые не могут работать без кеша, — это быстрее обнаружит сломанный ключ, чем тихая переустановка зависимостей.
7. **Следите за квотой**: регулярный `gh cache list --sort size_in_bytes --order desc` выявляет разросшиеся записи; настройте cleanup-воркфлоу для PR.
8. **Пинуйте мажоры экшенов** (`@v6`, а не `@main`) и сверяйте требования к версии self-hosted раннера при обновлении мажорных линеек; мажоры на Node.js 20 на hosted-раннерах устарели — переходите на node24-линеейки.
9. **Откат изменений**: вернуть состояние можно полной очисткой (`gh cache delete --all`) — следующий запуск пересоздаст кеши заново; изменение префикса ключа равносильно началу «чистой истории» кеширования.
