# GitHub Actions: Кеширование

Кеширование — один из самых эффективных способов ускорить выполнение CI/CD (Continuous Integration / Continuous Deployment) пайплайнов в GitHub Actions. Его основная цель — сохранение файлов (например, зависимостей или результатов сборки) между запусками воркфлоу, чтобы избежать их повторного скачивания или повторной генерации.

## Определения

- **Кеш (Cache)**: Выделенное хранилище, привязанное к репозиторию, в котором можно сохранять файлы и директории. Доступ к кешу осуществляется по уникальному ключу.
- **`actions/cache`**: Официальный `action` от GitHub для управления кешированием. Текущая актуальная версия — `v5.0.4` (март 2026).
- **Cache Service v2**: Обновленный бэкенд сервиса кеширования (внедрен в феврале 2025), обеспечивающий повышенную пропускную способность и надежность.

## Основные концепции

### Механизм работы кеширования

Процесс обработки кеша разделен на два основных этапа:

1. **Восстановление (Restore)**: В начале задачи (`job`) действие `actions/cache` ищет существующий кеш по указанному ключу (`key`). При полном совпадении содержимое кеша восстанавливается в целевую директорию (`path`). Если точное совпадение отсутствует, выполняется поиск по префиксам из списка `restore-keys`.
2. **Сохранение (Save)**: В конце выполнения задачи, если на этапе восстановления не было найдено точного совпадения ключа, создается новый кеш с текущим содержимым указанной директории.

**Особенности Cache Service v2**:
- Обязательно использование `actions/cache@v4` или выше.
- Для self-hosted runners (собственные агенты сборки) требуется версия runner ≥2.231.0.
- Возможность раздельного управления через `actions/cache/restore` и `actions/cache/save`.

### Управление ключами кеша

Ключ кеша — основной инструмент управления жизненным циклом данных.

- **`key`** (обязательный): Уникальная строка-идентификатор. Кеш восстанавливается только при **полном совпадении** (exact match).
- **`restore-keys`** (опциональный): Упорядоченный список префиксов. Если точный `key` не найден, используется самый свежий кеш, ключ которого начинается с одного из указанных префиксов.

Типовая структура ключа:
`{{ runner.os }}-{{ tool_name }}-{{ hashFiles('dependency-file') }}`

Использование `hashFiles` гарантирует, что при изменении состава зависимостей (например, в `package-lock.json` или `requirements.txt`) хеш изменится, что приведет к созданию нового актуального кеша.

### Ограничения и политики

- **Объем данных**: Лимит на один кеш — 10 ГБ. Суммарный объем на репозиторий — 10 ГБ по умолчанию (может быть увеличен до 10 ТБ в планах Enterprise).
- **Время жизни**: Данные удаляются автоматически, если к ним не обращались более 7 дней.
- **Неизменяемость (Immutability)**: Существующий кеш по конкретному ключу нельзя обновить. Изменения фиксируются только созданием нового кеша с новым ключом.
- **Политика вытеснения**: При достижении лимита объема удаляются старые данные по алгоритму **LRU (Least Recently Used)** — первыми удаляются те кеши, к которым дольше всего не было обращений.
- **Безопасность**: Запрещено хранить в кеше чувствительные данные (токены, пароли). Кеш доступен для чтения всем процессам в рамках репозитория, включая запуски из форков для базовой ветки.

### Встроенная поддержка в setup-actions

Многие официальные действия для настройки окружения имеют встроенную поддержку кеширования, что является предпочтительным способом настройки:

| Менеджер пакетов | Action | Параметр `cache` |
| :--- | :--- | :--- |
| npm, Yarn, pnpm | `actions/setup-node@v4` | `cache: 'npm'`, `yarn` или `pnpm` |
| pip, pipenv, Poetry | `actions/setup-python@v5` | `cache: 'pip'`, `pipenv` или `poetry` |
| Gradle, Maven | `actions/setup-java@v4` | `cache: 'gradle'` или `maven` |
| RubyGems | `actions/setup-ruby@v1` | `cache: 'bundler'` |
| Go | `actions/setup-go@v5` | `cache: true` |
| .NET NuGet | `actions/setup-dotnet@v4` | `cache: true` |

## Практические сценарии

### Сценарий 1: Кеширование зависимостей Node.js (npm)

Использование встроенного механизма в `setup-node`:

```yaml
steps:
  - uses: actions/checkout@v4
  - name: Setup Node.js
    uses: actions/setup-node@v4
    with:
      node-version: '20'
      cache: 'npm' # Автоматическое кеширование ~/.npm
      cache-dependency-path: '**/package-lock.json'
  - run: npm ci
```

### Сценарий 2: Ручное управление кешем для специфических путей

Когда требуется кешировать директории, не поддерживаемые стандартными `setup-actions`:

```yaml
steps:
  - uses: actions/checkout@v4
  - name: Cache arbitrary path
    id: cache-custom
    uses: actions/cache@v5
    with:
      path: |
        ~/.cache/custom-tool
        build/temp
      key: ${{ runner.os }}-custom-${{ hashFiles('config/tool-config.json') }}
      restore-keys: |
        ${{ runner.os }}-custom-
```
