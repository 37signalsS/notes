# GitHub Actions: Кеширование

Кеширование — один из самых эффективных способов ускорить выполнение CI/CD (Continuous Integration / Continuous Deployment) пайплайнов в GitHub Actions. Его основная цель — сохранение файлов (например, зависимостей или результатов сборки) между запусками воркфлоу, чтобы избежать их повторного скачивания или повторной генерации. Типичный выигрыш — сокращение времени установки зависимостей с нескольких минут до секунд, поскольку архив распаковывается локально на раннере вместо обращения к внешним реестрам пакетов.

## Определения

- **Кеш (Cache)**: Выделенное временное хранилище, привязанное к репозиторию, позволяющее сохранять и восстанавливать данные по уникальному ключу.
- **`actions/cache`**: Официальный экшен GitHub для управления кешированием. Текущая актуальная версия — `v6.1.0` (по состоянию на 2026 год); линейка v5 также поддерживается. Начиная с v5 экшен работает на Node.js 24 и требует версию раннера не ниже `2.327.1`; начиная с v4 интегрирован с Cache Service v2.
- **Ключ кеша (Cache Key)**: Уникальная строка, идентифицирующая содержимое кеша. Используется для поиска и восстановления данных.
- **Cache Hit (Попадание)**: Состояние, при котором найден кеш, точно соответствующий значению `key`.
- **Cache Miss (Промах)**: Состояние, при котором точного совпадения `key` не найдено. В этом случае могут быть использованы `restore-keys` или создан новый кеш в конце задачи.
- **Политика вытеснения (Eviction Policy)**: Алгоритм автоматического удаления старых или редко используемых кешей для соблюдения лимитов хранилища.
- **Cache Service v2**: Обновленная инфраструктура сервиса кеширования (внедрена в 2025 году), обеспечивающая пропускную способность до 1 Гбит/с и повышенную надежность. Старый сервис был отключён одновременно с развертыванием нового; для self-hosted раннеров требуется версия не ниже `2.231.0`.
- **Cache Version**: Служебный хеш, который генерируется из комбинации инструмента сжатия (Gzip или Zstd — зависит от ОС раннера) и списка путей `path`. Кеши с одинаковым ключом, но разными версиями считаются разными записями — именно поэтому кеш, созданный на `windows-latest`, по умолчанию нельзя восстановить на `ubuntu-latest`.
- **Post-run фаза**: Автоматический шаг, который экшен `actions/cache` регистрирует после всех шагов задачи и в котором выполняется сохранение кеша.
- **`cache-hit` (выходной параметр)**: Выход (`output`) шага с экшеном кеширования. Принимает значение `true` только если восстановление произошло по точному совпадению основного ключа `key`; при восстановлении по префиксу `restore-keys` или при отсутствии кеша — `false`.
- **`cache-dependency-path`**: Параметр setup-экшенов и ручного кеширования, указывающий файл(ы) зависимостей для расчета хеша ключа. Необходим в монорепозиториях, где lock-файл лежит не в корне.
- **`lookup-only`**: Режим работы экшена кеширования, при котором проверяется только существование кеша без его скачивания и распаковки. Полезен для условной логики («если кеш есть — пропустить установку»).

## Основные концепции

### Механизм работы кеширования

Процесс работы с кешем делится на два основных этапа, выполняемых автоматически экшеном `actions/cache`:

1. **Восстановление (Restore)**:
   - В начале задачи (`job`) выполняется поиск кеша по значению `key`.
   - Если найдено точное совпадение, данные скачиваются и распаковываются в `path`.
   - Если точного совпадения нет, проверяется список `restore-keys` (поиск по префиксу). Используется самый свежий подходящий кеш.
2. **Сохранение (Save)**:
   - В конце выполнения задачи (в фазе `Post-run`) проверяется наличие точного совпадения ключа на этапе восстановления.
   - Если был Cache Miss, создается новый архив из содержимого `path` и загружается в хранилище под текущим ключом `key`.

Дополнительные детали поведения Post-run фазы:

- Post-шаг сохранения выполняется даже если один из предыдущих шагов задачи завершился с ошибкой — это позволяет закешировать частично загруженные зависимости для следующей попытки. Однако при **отмене** задачи (cancel) сохранение пропускается.
- Архив создаётся со сжатием: Zstd на Linux/macOS, Gzip на Windows. Поэтому содержимое кеша — это единый tar-архив, а не копия каталога.
- Режим `lookup-only: true` выполняет только первый этап (проверку наличия), не занимая время и место на распаковку.

### Управление ключами и изоляция

Ключ кеша является неизменяемым идентификатором. Если кеш с таким ключом уже существует, он не будет перезаписан.

- **Структура ключа**: Рекомендуется использовать комбинацию ОС, имени менеджера пакетов и хеша файлов зависимостей.
  `{{ runner.os }}-node-{{ hashFiles('**/package-lock.json') }}`
  Функция `hashFiles` принимает несколько шаблонов через запятую и возвращает хеш конкатенированного содержимого найденных файлов: `hashFiles('**/package-lock.json', '**/npm-shrinkwrap.json')`.
- **Изоляция по веткам**:
  - Кеши изолированы на уровне веток.
  - Задача в ветке `feature` может получить доступ к кешам базовой ветки (например, `main`), но не наоборот.
  - Ветки не могут перезаписывать кеши друг друга.
  - На практике действует иерархия доступа: задача сначала ищет кеш среди записей своей ветки, затем — среди записей ветки по умолчанию. Записи других feature-веток недоступны.
- **Pull Requests**: Запуски из форков имеют доступ к кешам основной ветки, но не могут сохранять свои кеши в основное хранилище (в целях безопасности). Для обычных (не форкнутых) PR кеш сохраняется под рефом вида `refs/pull/<номер>/merge` и доступен только перезапускам этого же PR.
- **Reusable Workflows**: Вызываемый воркфлоу использует область видимости (scope) кеша вызывающего репозитория, а не своего собственного.

### Ограничения и политики

- **Лимит объема**: Стандартный лимит на репозиторий составляет 10 ГБ. При превышении лимита GitHub применяет алгоритм **LRU (Least Recently Used)**, удаляя старые кеши — первыми удаляются записи с наиболее старой датой последнего обращения (`last_accessed_at`). Лимит кеша не расходует квоту хранения артефактов и пакетов — это независимое хранилище.
- **Время жизни**: Кеш автоматически удаляется, если к нему не было обращений (чтения) более 7 дней.
- **Неизменяемость**: После создания кеш нельзя изменить. Для обновления данных необходимо изменить ключ (например, обновив файл зависимостей или добавив версию в префикс ключа).
- **Cross-OS Caching**: Параметр `enableCrossOsArchive: true` позволяет восстанавливать кеш на разных ОС (например, использовать кеш с Linux на Windows, если это допустимо для конкретных данных). Технически этот параметр отключает учет Cache Version, привязанной к инструменту сжатия конкретной ОС.
- **Размер одной записи**: Нет жесткого официального предела на размер одного архива, но большие архивы (>2 ГБ) медленно упаковываются и восстанавливаются, что нивелирует выгоду. Загрузка разбивается на сегменты; таймаут сегмента настраивается переменной `SEGMENT_DOWNLOAD_TIMEOUT_MINS` (в минутах, по умолчанию — 10).

### Cache Version и совместимость архивов

Помимо пользовательского ключа, каждая запись имеет внутренний атрибут **Cache Version** — хеш от комбинации инструмента сжатия (зависит от ОС раннера) и списка путей `path`. Следствия:

1. Один и тот же ключ `primes` создаст разные записи на Ubuntu и Windows (разное сжатие), а также в задачах с разными списками `path`.
2. Изменение набора путей `path` в воркфлоу делает все прежние кеши недоступными для нового варианта, даже если ключ не изменился — это частая причина «необъяснимых» Cache Miss.
3. Диагностика: атрибут версии можно получить через [REST API списка кешей](https://docs.github.com/en/rest/actions/cache) и сравнить у записей с одинаковым ключом, созданных на разных ОС.

### Встроенная поддержка в setup-actions

Наиболее эффективный способ кеширования зависимостей — использование встроенных параметров в `setup-*` экшенах. Это упрощает конфигурацию и автоматически обрабатывает правильные пути.

| Инструмент | Экшен | Параметр `cache` |
| :--- | :--- | :--- |
| Node.js (npm, yarn, pnpm) | `actions/setup-node@v7` | `npm`, `yarn`, `pnpm` |
| Python (pip, poetry, pipenv) | `actions/setup-python@v7` | `pip`, `poetry`, `pipenv` |
| Java (Maven, Gradle, sbt) | `actions/setup-java@v5` | `maven`, `gradle`, `sbt` |
| Go (modules) | `actions/setup-go@v6` | `true` (включено по умолчанию с v4) |
| Ruby (bundler) | `ruby/setup-ruby` | `bundler-cache: true` |
| .NET (NuGet) | `actions/setup-dotnet@v4` | `true` |

Примечания к таблице:

- Строки таблицы соответствуют актуальным мажорным версиям на момент обновления; перед обновлением pinned-версий сверяйтесь со страницей releases каждого экшена (мажорные линейки регулярно переходят на новые runtime-версии Node.js с требованиями к минимальной версии раннера).
- Исторический экшен `actions/setup-ruby@v1` официально deprecated и более не поддерживается — для Ruby используется поддерживаемый сообществом `ruby/setup-ruby` с параметром `bundler-cache: 'true'`.
- Все setup-экшены принимают `cache-dependency-path` — путь или glob до lock-файлов. Обязателен, когда lock-файл не лежит в корне репозитория или менеджеров несколько.
- В `setup-java` доступны расширенные параметры кеширования: `cache-read-only: true` (только чтение — удобно для матричных задач-потребителей) и `cache-path` (кастомные пути кеша).

### Отличие кеша от артефактов

Кеш и артефакты (artifacts) решают разные задачи, хотя оба являются хранилищами файлов:

| Аспект | Кеш (Cache) | Артефакт (Artifact) |
| :--- | :--- | :--- |
| Назначение | Ускорение повторных сборок | Хранение результатов сборки для последующего использования |
| Гарантия наличия | Не гарантирован (может быть вытеснен LRU или 7-дневным TTL) | Гарантирован на срок retention-политики |
| Доступ между запусками | По неизменяемому ключу, с изоляцией по веткам | По имени внутри конкретного запуска воркфлоу |
| Мутабельность | Иммутабелен | Можно дополнить (в одной линейке версий upload/download) |
| Типичное содержимое | Зависимости, кеши компиляторов, Docker-слои | Бинарники, отчёты тестов, логи, пакеты для деплоя |

Правило выбора: если потеря данных ломает пайплайн — используйте артефакты; если данные можно восстановить пересборкой — используйте кеш.

## Практические сценарии

### Сценарий 1: Кеширование Node.js (npm) через setup-node

Самый простой и рекомендуемый способ:

```yaml
steps:
  - uses: actions/checkout@v7
  - uses: actions/setup-node@v7
    with:
      node-version: '22'
      cache: 'npm'
  - run: npm ci
```

Требования и проверка:

- Предусловие: `actions/checkout` должен выполниться **до** setup-экшена, иначе lock-файл недоступен и хеш ключа не рассчитается (кеш молча не сработает).
- Валидация: в логах шага setup-node ожидаемо появится строка вида `Cache restored from key: Linux-npm-<hash>` (первый запуск покажет `Cache not found for input keys: ...` — это нормально, кеш будет создан в Post-run фазе).

Вариант для монорепозитория (lock-файлы в подпапках):

```yaml
steps:
  - uses: actions/checkout@v7
  - uses: actions/setup-node@v7
    with:
      node-version: '22'
      cache: 'npm'
      cache-dependency-path: |
        apps/frontend/package-lock.json
        apps/backend/package-lock.json
  - run: npm ci --workspaces
```

Хеш ключа здесь учитывает оба lock-файла: изменение любого из них порождает новый ключ.

### Сценарий 2: Кеширование Python (Poetry)

```yaml
steps:
  - uses: actions/checkout@v7
  - uses: actions/setup-python@v7
    with:
      python-version: '3.12'
      cache: 'poetry'
      cache-dependency-path: 'poetry.lock'
  - run: poetry install
```

Для остальных менеджеров Python меняется только значение `cache`: `pip` (ключ строится по `requirements*.txt` — при их отсутствии обязательно указать `cache-dependency-path`) или `pipenv` (по `Pipfile.lock`). Важно фиксировать точные версии зависимостей в файлах: если в requirements указаны версии без пинов, установка всегда тянет свежие пакеты, и смысл кеша теряется.

### Сценарий 3: Ручное кеширование произвольных путей

Используется для специфических инструментов или промежуточных результатов сборки:

```yaml
steps:
  - uses: actions/checkout@v7
  - name: Cache Compiler Data
    id: compiler-cache
    uses: actions/cache@v6
    with:
      path: .build-cache
      key: ${{ runner.os }}-build-${{ github.sha }}
      restore-keys: |
        ${{ runner.os }}-build-
```

Разбор параметров:

- `path` — каталоги или файлы для упаковки (можно перечислить многострочно через `|`). Пути относительно рабочей директории; допустимы абсолютные (`~/.cache/go-build`).
- `key` — основной ключ. Здесь он включает SHA коммита, то есть каждый коммит порождает новый кеш, что подходит для артефактов промежуточной сборки.
- `restore-keys` — список префиксов для частичного восстановления (сверху вниз, берётся самое свежее совпадение). Позволяет получить «старую» версию данных вместо полного промаха.
- `id` — необязателен, но нужен для обращения к выходному параметру.

Использование выхода `cache-hit` для условного выполнения тяжелой операции:

```yaml
  - name: Generate Primes
    if: steps.compiler-cache.outputs.cache-hit != 'true'
    run: ./generate-primes.sh -d .build-cache
```

Генерация выполняется только при полном промахе; при попадании по точному ключу данные уже готовы.

### Сценарий 4: Кеширование Docker-слоев (BuildKit)

Современный способ использования кеша GitHub Actions внутри Docker:

```yaml
- name: Set up Docker Buildx
  uses: docker/setup-buildx-action@v3

- name: Build and push
  uses: docker/build-push-action@v6
  with:
    push: true
    tags: user/app:latest
    cache-from: type=gha
    cache-to: type=gha,mode=max
```

Разбор:

- `type=gha` — бэкенд кеширования, использующий то же хранилище GitHub Actions (лимит 10 ГБ делится между всеми записями репозитория, включая dependency-кеши).
- `mode=max` — экспортировать слои не только финального образа, но и всех промежуточных стадий multi-stage сборки. Без него кешируется только итоговый результат.
- `scope` (опционально) — именованное пространство внутри gha-бэкенда, чтобы разделить кеши разных образов: `cache-to: type=gha,mode=max,scope=api`.

Альтернатива при исчерпании квоты — кеширование в container registry (не расходует лимит Actions):

```yaml
    cache-from: type=registry,ref=ghcr.io/user/app:buildcache
    cache-to: type=registry,ref=ghcr.io/user/app:buildcache,mode=max
```

## Продвинутые сценарии и оптимизация

### Раздельное сохранение и восстановление

Для сложных пайплайнов можно использовать отдельные экшены `actions/cache/restore` и `actions/cache/save`. Это позволяет:
- Восстановить кеш в одной задаче, а сохранить только в случае успеха тестов.
- Управлять моментом сохранения для предотвращения записи "грязного" кеша.

Полный пример: кеш сохраняется только если тесты прошли успешно.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - name: Restore cache
        id: restore-deps
        uses: actions/cache/restore@v6
        with:
          path: ~/.npm
          key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
          restore-keys: ${{ runner.os }}-node-

      - run: npm ci
      - run: npm test

      - name: Save cache only on success
        if: success()
        uses: actions/cache/save@v6
        with:
          path: ~/.npm
          key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
```

Нюансы:

- `actions/cache/save` требует явный полный `key` (без `restore-keys`), так как не выполняет поиск, а только запись.
- Без условия `if: success()` save-шаг выполнится даже после падения тестов (поведение post-фазы по умолчанию).
- Ключ должен отличаться от уже существующих записей — иначе сохранение молча пропустится (неизменяемость кеша).

### Предотвращение гонки данных (Race Conditions)

Если несколько параллельных задач пытаются создать кеш с одним и тем же ключом, победит та, которая завершится первой. Остальные получат ошибку "Cache already exists", которая игнорируется экшеном. Чтобы избежать этого, включайте в ключ `github.run_id` или другие уникальные идентификаторы, если кеш специфичен для конкретного запуска.

Обратная ситуация — намеренное совместное использование: для матричных сборок полезен паттерн «сеятель + потребители»: одна задача заполняет кеш, остальные используют его в режиме read-only (см. параметр `cache-read-only` в `setup-java` или `lookup-only`-логику). Подробнее о параллелизме — в разделе о матричных сборках.

### Очистка кешей закрытых Pull Request

Кеши PR занимают квоту репозитория и вытесняют полезные записи основной ветки. Официально рекомендуемая практика — автоматическое удаление кешей при закрытии PR:

```yaml
name: Cleanup caches on closed pull requests
on:
  pull_request:
    types:
      - closed

jobs:
  cleanup:
    runs-on: ubuntu-latest
    permissions:
      actions: write
    steps:
      - name: Cleanup
        run: |
          echo "Fetching list of cache keys"
          cacheKeysForPR=$(gh cache list --ref $BRANCH --limit 100 --json id --jq '.[].id')

          set +e
          echo "Deleting caches..."
          for cacheKey in $cacheKeysForPR
          do
              gh cache delete $cacheKey
          done
          echo "Done"
        env:
          GH_TOKEN: ${{ github.token }}
          GH_REPO: ${{ github.repository }}
          BRANCH: refs/pull/${{ github.event.pull_request.number }}/merge
```

Ключевые моменты: требуется право `permissions: actions: write`; реф PR в CLI формате — `refs/pull/<номер>/merge`; `set +e` гарантирует, что сбой удаления одной записи не уронит задачу. Для форкнутых PR такой воркфлоу следует запускать по событию `pull_request_target` (с учетом связанных рисков безопасности).

## Устранение неполадок

### Кеш не восстанавливается
- **Проблема**: Ключ не совпадает из-за различий в ОС (например, `\r\n` в файлах зависимостей на Windows).
- **Решение**: Используйте `hashFiles` с нормализованными путями или включите `enableCrossOsArchive`.
- **Проблема**: Изоляция веток.
- **Решение**: Проверьте, создан ли кеш в базовой ветке или текущей.
- **Проблема**: Cache Miss из-за внутренней Cache Version — изменился список `path` или ОС раннера при том же ключе.
- **Решение**: Сравните поле версии записей через REST API; убедитесь, что список путей стабилен между запусками.

Диагностика: включите пошаговое логирование, задав секрет `ACTIONS_STEP_DEBUG` в значение `true` — в логах появятся подробности поиска ключей и сопоставления версий. Также `gh cache list --key <prefix>` показывает фактические ключи и ветки существующих записей.

### Кеш не сохраняется
- **Проблема**: Точное совпадение ключа уже найдено (Cache Hit). GitHub не обновляет существующие кеши.
- **Решение**: Измените ключ (например, добавьте инкрементальную версию: `v1`, `v2`).
- **Проблема**: Превышен лимит 10 ГБ.
- **Решение**: Удалите старые кеши вручную или проверьте, не сохраняются ли лишние временные файлы.
- **Проблема**: Задача была отменена (cancel) — Post-run сохранение пропущено.
- **Решение**: Это штатное поведение; при необходимости сохранять кеш принудительно используйте отдельный шаг `actions/cache/save`.

### Типичные сообщения об ошибках

| Сообщение в логе | Причина | Действие |
| :--- | :--- | :--- |
| `Cache not found for input keys: ...` | Нет записи ни по ключу, ни по префиксам | Штатный первый запуск; проверить структуру ключа |
| `Warning: Failed to restore: ...` / сегментные ошибки | Таймаут загрузки сегмента, нестабильная сеть | Установить `env: SEGMENT_DOWNLOAD_TIMEOUT_MINS: '5'` |
| `Reserving cache failed` / конфликт записи | Параллельная задача уже создала запись с этим ключом | Игнорируется экшеном; см. Race Conditions выше |
| Медленное восстановление большого кеша | Архив >2 ГБ, низкая скорость сервиса | Раздробить на несколько меньших кешей, исключить лишнее из `path` |

## Управление через интерфейс и CLI

### Веб-интерфейс
Находится в разделе **Actions → Management → Caches**. Позволяет:
- Видеть размер каждого кеша.
- Удалять конкретные записи.
- Оценивать суммарное потребление места.
- Фильтровать записи по ключу (синтаксис `key:<имя>`) и видеть ветку создания и дату последнего использования.

Удаление доступно пользователям с правами `write` на репозиторий.

### GitHub CLI (`gh`)
Команды управления кешем встроены в актуальные версии `gh` (нативная команда `gh cache`, ранее поставлялась как расширение `actions/gh-actions-cache`, которое интегрировано в ядро и больше не требует установки):

```bash
# Список кешей (JSON-вывод поддерживает поля id, key, size_in_bytes, created_at, last_accessed_at)
gh cache list
# → <id>  <key>  <size>  <created>  <last-accessed>

# Фильтрация: по префиксу ключа, по рефу ветки, сортировка по размеру
gh cache list --key linux-node-
gh cache list --ref refs/heads/main
gh cache list --sort size --order desc --limit 100

# Удаление по id или ключу
gh cache delete 1234
gh cache delete linux-node-a68c45df

# Удаление по ключу и ветке (одинаковые ключи существуют в разных ветках)
gh cache delete my-key --ref refs/heads/feature-branch

# Полная очистка хранилища репозитория
gh cache delete --all
# Возврат кода 0, если кешей нет (удобно в скриптах)
gh cache delete --all --succeed-on-no-caches
```

Для авторизации требуется scope `repo`. Один и тот же ключ может соответствовать нескольким записям (разные ветки или разные Cache Version) — удаление по ключу затронет все такие записи в пределах выбранного рефа.

### REST API

Те же операции доступны программно:

```bash
# Список кешей с метаданными (включая внутреннюю версию)
curl -H "Authorization: Bearer $GH_TOKEN" \
  "https://api.github.com/repos/{owner}/{repo}/actions/caches"

# Полная очистка
curl -X DELETE -H "Authorization: Bearer $GH_TOKEN" \
  "https://api.github.com/repos/{owner}/{repo}/actions/caches"
```

Эндпоинты: получение списка и статистики (`GET /repos/{owner}/{repo}/actions/caches`), удаление всех (`DELETE /repos/{owner}/{repo}/actions/caches`), удаление одной записи по id (`DELETE /repos/{owner}/{repo}/actions/caches/{cache_id}`).

## Лучшие практики и очистка

1. **Сначала setup-экшены**: используйте встроенный `cache`-параметр `actions/setup-*` везде, где он есть, и переходите на `actions/cache` только для нестандартных путей.
2. **Компонуйте ключ осмысленно**: ОС + менеджер + хеш lock-файла. Добавляйте статический префикс версии (`v1-...`) для возможности массовой инвалидации сменой одной буквы.
3. **Кешируйте только нужное**: включайте в `path` каталоги зависимостей и кешей инструментов, а не весь `node_modules` вместе с временными файлами — меньше архив, быстрее восстановление.
4. **Никогда не кешируйте секреты**: каталоги типа `~/.ssh`, `~/.aws`, токены и креденшелы не должны попадать в кеш — они доступны всем задачам веток-потомков.
5. **Следите за квотой**: регулярный `gh cache list --sort size --order desc` выявляет разросшиеся записи; настройте cleanup-воркфлоу для PR.
6. **Пинуйте мажоры экшенов** (`@v6`, а не `@main`) и сверяйте требования к версии self-hosted раннера при обновлении мажорных линеек.
7. **Откат изменений**: вернуть состояние можно полной очисткой (`gh cache delete --all`) — следующий запуск пересоздаст кеши заново; изменение префикса ключа равносильно началу «чистой истории» кеширования.
