# GitHub Actions: Переиспользуемые рабочие процессы

**Актуально для:** GitHub Actions, октябрь 2026 (actions/checkout v7, actions/setup-node v7; лимиты вложенности — 10 уровней и 50 воркфлоу на прогон, подняты 6 ноября 2025; self-repository синтаксис `$/` требует runner 2.336.0+)

Переиспользуемые рабочие процессы (Reusable Workflows) — это архитектурный механизм в GitHub Actions, позволяющий одному воркфлоу вызывать другой. Это ключевой инструмент для соблюдения принципа DRY (Don't Repeat Yourself), централизации логики CI/CD и стандартизации процессов безопасности во всей организации.

## Определения

- **Reusable Workflow (Переиспользуемый процесс)**: Воркфлоу, предназначенный для вызова. Содержит триггер `on: workflow_call`.
- **Caller Workflow (Вызывающий процесс)**: Воркфлоу, который инициирует выполнение переиспользуемого процесса через ключ `uses`.
- **Workflow Call**: Событие-триггер, активируемое внешним вызовом.
- **`secrets: inherit`**: Механизм автоматической передачи всех доступных секретов вызывающего процесса в переиспользуемый.
- **Вложенный вызов (Nested Call)**: Вызов одного переиспользуемого воркфлоу из другого. Цепочка вида `caller -> r1 -> r2 -> ...` образует дерево вызовов; циклы в нём запрещены.
- **Контракт (Contract)**: Совокупность объявленных `inputs`, `secrets` и `outputs` переиспользуемого процесса — его публичный интерфейс для вызывающих сторон.

## Основные концепции

### Создание переиспользуемого процесса

Для того чтобы файл стал доступным для вызова, он должен находиться в директории `.github/workflows` и содержать триггер `workflow_call`.

Поддиректории внутри `.github/workflows` не поддерживаются — как и для обычных воркфлоу, файл должен лежать непосредственно в этой директории.

Триггер `workflow_call` можно совмещать с другими событиями — например, `push` или `pull_request_target`. Тогда один файл запускается и напрямую (как обычный воркфлоу), и по вызову из другого воркфлоу. Это удобный путь постепенного перевода существующего процесса на шаблон: файл остаётся рабочим, а к нему лишь добавляется точка входа для вызова.

**Параметры конфигурации:**
- **`inputs`**: Входные данные (строки, числа, логические значения). Обязательно указывается `type`. Допустимые типы: `string`, `number`, `boolean` — в отличие от `workflow_dispatch`, типы `choice` и `environment` для `workflow_call` не поддерживаются. Тип передаваемого значения обязан совпадать с объявленным типом входа.
- **`secrets`**: Определение необходимых секретов. Могут быть помечены как `required: true`.
- **`outputs`**: Данные, передаваемые обратно вызывающему процессу на уровне задач. Значение выхода (`value`) должно ссылаться на выход уровня задачи (`jobs.<job_id>.outputs`) — выходы шагов нельзя пробросить напрямую, их нужно сначала смаппить в выходы задачи.

Полный справочник директив — [Синтаксис Workflow](./Workflow_Syntax.md).

Задача внутри переиспользуемого воркфлоу обязана явно указывать `runs-on`: исполнитель вызывающей задачи не наследуется автоматически. Исключений нет — даже если вызывающая задача запускается на self-hosted раннере, переиспользуемый процесс получит тот раннер, который укажет сам (или который ему передадут через `inputs`).

```yaml
name: Reusable Build

on:
  workflow_call:
    inputs:
      node-version:        # произвольный идентификатор входа
        description: 'Node.js версия для сборки'
        required: false    # если true — вызов без этого параметра упадёт при валидации
        type: string       # string | number | boolean
      run-lint:
        required: false
        type: boolean
        default: true      # значение по умолчанию, если вызывающий не передал
    secrets:
      registry_token:
        required: true     # секрет обязателен к передаче

jobs:
  build:
    runs-on: ubuntu-latest # обязательная явная привязка исполнителя
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ inputs.node-version }}
      - if: ${{ inputs.run-lint }}
        run: npm run lint
```

### Вызов переиспользуемого процесса

Ключевой момент: `uses` указывается на уровне задачи (`job`), а не шага. Одна задача вызывает ровно один переиспользуемый процесс; для параллельного вызова нескольких процессов создайте отдельные задачи.

Способы адресации:

| Синтаксис | Применение |
| :--- | :--- |
| `./.github/workflows/file.yml` | Тот же репозиторий; вызывается версия из того же коммита, что и вызывающий воркфлоу |
| `$/.github/workflows/file.yml` | Self-repository синтаксис (с 30 июля 2026) — рекомендуемый способ ссылки на воркфлоу внутри того же репозитория: тот же репозиторий на исполняемом коммите, без предварительного checkout. Работает всюду, где работает `./` (шаги, composite actions, вложенные вызовы, reusable workflows); требует раннер 2.336.0+; недоступен в GitHub Enterprise Server |
| `{owner}/{repo}/.github/workflows/file.yml@{ref}` | Любой публичный или доступный приватный репозиторий |

Правила привязки `{ref}`:
- `{ref}` может быть SHA-коммитом, тегом релиза или именем ветки.
- Если тег и ветка называются одинаково — **тег имеет приоритет** над веткой.
- Самый безопасный вариант — пиннинг на полный SHA: он иммутабелен и защищает от подмены кода в перемещаемом теге.
- Префиксы вроде `refs/heads/main` запрещены — только короткое имя рефа.
- Использовать контексты и выражения (`${{ }}`) в значении `uses` запрещено.

```yaml
jobs:
  call-local:
    uses: ./.github/workflows/reusable-build.yml   # без @ref — берётся текущий коммит

  call-pinned:
    uses: my-org/ci-templates/.github/workflows/reusable-build.yml@172239021f7ba04fe7327647b213799853a9eb89 # SHA — максимальная стабильность

  call-conditionally:
    if: github.event_name == 'push'
    uses: ./.github/workflows/reusable-build.yml   # задача-вызов поддерживает if
```

В задаче-вызове допустим только ограниченный набор ключей: `name`, `uses`, `with` (входы), `secrets` (включая `inherit`), `strategy`, `needs`, `if`, `concurrency`, `permissions`. Ключи `steps`, `container`, `services`, `timeout-minutes`, `environment` на уровне задачи-вызова недоступны — они управляются внутри самого переиспользуемого процесса.

Доступность вызова определяется взаимной видимостью репозиториев:

| Репозиторий вызывающего | Доступные репозитории шаблонов |
| :--- | :--- |
| `private` | `private` и `public` |
| `public` | только `public` |

Дополнительно: настройки Actions в репозитории-шаблоне должны явно разрешать доступ для приватных репозиториев, а все воркфлоу в цепочке вложенных вызовов должны быть доступны самому первому вызывающему.

Предостережение: GitHub Actions не следует redirect'ам при смене владельца или имени репозитория шаблонов — все существующие вызовы по старому имени сломаются сразу после переименования.

### Сравнение: Reusable Workflows vs Composite Actions

Понимание различий критично для выбора правильной архитектуры:

| Характеристика | Reusable Workflows | Composite Actions |
| :--- | :--- | :--- |
| **Уровень** | Задача (`job`) целиком | Шаги (`steps`) внутри задачи |
| **Логирование** | Отдельные задачи в UI GitHub | Все шаги внутри одного блока Action |
| **Секреты** | Доступны через `secrets: inherit` | Требуют явной передачи как `inputs` |
| **Исполнитель** | Можно задать `runs-on` внутри | Использует `runs-on` вызывающей задачи |
| **Окружения** | Поддержка `environment` | Не поддерживают `environment` напрямую |
| **Условия и матрицы** | Задача-вызов поддерживает `if`, `strategy`/матрицу | Нет собственной `strategy`; матрица только снаружи |
| **Версионирование** | Пиннинг по тегу/SHA/ветке репозитория шаблонов | Пиннинг по ref действия; публикация в Marketplace |

Практическое правило выбора: если блок логики должен выполняться как отдельная задача со своим окружением, секретами и правами — это Reusable Workflow. Если это вспомогательная последовательность шагов внутри уже существующей задачи (например, установка инструмента) — Composite Action. Подробнее о Composite Actions — [Готовые действия (Marketplace)](./Marketplace_Actions.md).

### Передача данных и контракты

Три стадии работы с входами и секретами:

1. **Объявление** — в секции `on.workflow_call` описываются ожидаемые `inputs` и `secrets`.
2. **Использование** — внутри переиспользуемого процесса значения доступны через контексты `${{ inputs.* }}` и `${{ secrets.* }}`. При использовании `secrets: inherit` секреты можно читать, даже если они не объявлены в `on`, но явное объявление предпочтительнее: контракт документируется сам.
3. **Передача** — вызывающая задача передаёт значения через `with` (входы) и `secrets` (секреты).

Секреты передаются **только напрямую вызываемому** процессу. В цепочке A → B → C процесс C увидит секреты A лишь в том случае, если A передала их B, а B явно перепередала C.

Переменные окружения (`env`) между границей вызова **не передаются**: workflow-level `env` вызывающего воркфлоу не виден внутри переиспользуемого процесса, и наоборот. По той же причине через `GITHUB_ENV` нельзя передать значение в шаги вызывающего воркфлоу — вызов происходит на уровне задачи, а не шага. Для обмена данными используйте `inputs`/`outputs`, а для общих констант — переменные уровня организации, репозитория или environment через контекст `vars`.

Выходы (`outputs`) работают в обратную сторону: шаг пишет значение в `$GITHUB_OUTPUT` → задача собирает его в `outputs` → воркфлоу маппит выходы задач в свои `outputs` → вызывающий читает через `needs.<job_id>.outputs.<name>`. Полный пример — Сценарий 4.

Особенность при матричном вызове: итоговый выход равен значению из **последней успешно завершившейся** комбинации матрицы, фактически записавшей значение (пустая строка тоже считается записью значения).

### Безопасность и права доступа

- **Наследование секретов**: Использование `secrets: inherit` удобно в рамках одной организации, но требует осторожности в публичных репозиториях. Рекомендуется явно перечислять секреты для повышения прозрачности. Ключевое слово `inherit` работает только при вызове воркфлоу из той же организации или enterprise; для внешних репозиториев секреты передаются только явно.
- **Environment secrets**: Триггер `on.workflow_call` не поддерживает ключевое слово `environment` на уровне триггера, поэтому environment-секреты нельзя передать от вызывающего процесса. Если задача внутри переиспользуемого процесса сама объявляет `environment`, применяются секреты именно этого environment, а не переданные извне.
- **Права GITHUB_TOKEN**: Переиспользуемый процесс наследует права от вызывающей задачи. Однако он может запрашивать собственные `permissions`, если они не превышают права вызывающего процесса. Вдоль всей цепочки вложенных вызовов права могут только сохраняться или сужаться, но не повышаться (пример: у A есть `package: read` — тогда B и C не могут запросить `package: write`). Если задача-вызов не указывает `permissions` вовсе, вызванный процесс получает дефолтные права токена, а не явные права других задач вызывающего.
- **Доступ к кешу**: вызываемый воркфлоу использует область (scope) кеша вызывающего репозитория, а `cache-mode` вызывающей задачи ограничивает доступ — вызываемый процесс не может запросить больше, чем разрешено (при превышении запуск не стартует с ошибкой валидации). Детали — в [Кешировании](./Caching.md).
- **Контекст `github`**: при вызове контекст всегда принадлежит вызывающему воркфлоу; вызванный процесс автоматически получает доступ к `github.token` и `secrets.GITHUB_TOKEN`.
- **Раннеры и биллинг**: назначение GitHub-hosted раннеров оценивается в контексте вызывающего, и минуты списываются с вызывающего репозитория; hosted-раннеры репозитория шаблонов недоступны вызываемому. Self-hosted раннеры доступны, если оба воркфлоу принадлежат одному пользователю или организации.
- **Concurrency**: задача-вызов поддерживает `concurrency`, но не используйте одинаковые группы с `cancel-in-progress: true` в вызывающем и вызываемом процессах — например, группу на основе `${{ github.workflow }}`: поскольку вызванный процесс видит имя *вызывающего*, новый вызов отменит уже идущий родительский прогон.
- **Изоляция**: Задачи в переиспользуемом воркфлоу выполняются в изолированных средах, что предотвращает утечку временных файлов между ними.
- **OIDC**: Для деплоя в облака без долгоживущих ключей переиспользуемый процесс может запрашивать токен через `permissions: id-token: write`; доверие настраивается на стороне облака по subject-claim вызывающего репозитория. См. [Сетевая безопасность](./network-security.md).
- **Сторонние шаблоны**: Вызовы чужих переиспользуемых воркфлоу пиньте на SHA и ревьюйте изменения так же строго, как сторонний код, — вызванный воркфлоу исполняется с вашими правами и секретами.

Детали работы с секретами — [Управление секретами](./secrets_management.md).

## Практические сценарии

### Сценарий 1: Шаблон деплоя в облако (Node.js 24)

Пример переиспользуемого процесса (`reusable-deploy.yml`), который стандартизирует деплой с использованием OIDC. Предполагается наличие секрета `deploy_token` на уровне организации или репозитория и скрипта `scripts/deploy.sh` в вызывающем репозитории.

```yaml
name: Standard Deployment

on:
  workflow_call:
    inputs:
      env:
        required: true
        type: string
    secrets:
      deploy_token:
        required: true

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.env }}   # включает protection rules и environment-секреты
    permissions:
      contents: read                 # минимально необходимые права
    steps:
      - uses: actions/checkout@v7
      - name: Setup Node
        uses: actions/setup-node@v7
        with:
          node-version: '24'
      - name: Deploy
        run: ./scripts/deploy.sh --token ${{ secrets.deploy_token }}
```

Вызов из приложения:

```yaml
jobs:
  deploy-prod:
    uses: ./.github/workflows/reusable-deploy.yml
    with:
      env: production
    secrets:
      deploy_token: ${{ secrets.PROD_DEPLOY_TOKEN }}
```

Проверка результата: в логе прогона задача отображается трёхуровневым именем `<caller-job> / <reusable-name> / <job>`, например `deploy-prod / Standard Deployment / deploy`, а её статус — зелёный (`success`).

### Сценарий 2: Вызов процесса из другого репозитория

Для использования процессов внутри организации рекомендуется создать центральный репозиторий `.github` или `ci-templates`. Вызывающему репозиторию нужен доступ на чтение репозитория шаблонов; в организации настройте это через repository settings или выдайте роль на уровне команды.

```yaml
jobs:
  call-external:
    uses: my-org/ci-templates/.github/workflows/reusable-build.yml@v1
    with:
      build-type: 'release'
    secrets: inherit
```

Более строгий вариант — явная передача секретов вместо наследования (лучше аудитопригодность: видно, какие именно секреты покидают репозиторий):

```yaml
jobs:
  call-external-explicit:
    uses: my-org/ci-templates/.github/workflows/reusable-build.yml@v1
    with:
      build-type: 'release'
    secrets:
      registry_token: ${{ secrets.GHCR_TOKEN }}
```

Примечание: `@v1` удобно использовать как «плавающий» мажорный тег (все патчи двигают `v1.x.x`), но для критичных пайплайнов предпочтителен пиннинг на SHA с контролируемым обновлением через Dependabot.

### Сценарий 3: Использование матриц с переиспользуемыми воркфлоу

Матрица позволяет запускать один и тот же переиспользуемый воркфлоу для разных конфигураций параллельно. Задача-вызов поддерживает полную секцию `strategy`, включая `fail-fast` и `max-parallel`.

```yaml
jobs:
  cross-test:
    strategy:
      fail-fast: false     # падение одной версии не отменяет остальные
      max-parallel: 3      # не более трёх одновременных вызовов
      matrix:
        version: [22, 24, 26]
    uses: ./.github/workflows/node-test.yml
    with:
      node-version: ${{ matrix.version }}
```

Глубокий разбор матриц — [Матричные сборки](./Matrix_Builds.md#матрица-поверх-переиспользуемых-воркфлоу).

### Сценарий 4: Возврат данных через outputs

Переиспользуемый процесс собирает артефакт и возвращает имя версии, которую вызывающий использует в следующей задаче (например, для создания релиза).

Переиспользуемый процесс `.github/workflows/reusable-build.yml`:

```yaml
name: Reusable Build

on:
  workflow_call:
    outputs:
      image-tag:                          # публичное имя выхода воркфлоу
        description: 'Тег собранного образа'
        value: ${{ jobs.build.outputs.tag }}   # маппинг на выход задачи

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      tag: ${{ steps.meta.outputs.tag }}  # маппинг выхода шага на выход задачи
    steps:
      - id: meta
        run: echo "tag=$(git rev-parse --short HEAD)" >> "$GITHUB_OUTPUT"
      - run: docker build -t "app:${{ steps.meta.outputs.tag }}" .
```

Вызывающий воркфлоу:

```yaml
jobs:
  build:
    uses: ./.github/workflows/reusable-build.yml

  release:
    runs-on: ubuntu-latest
    needs: build                         # выходы доступны только после завершения вызова
    steps:
      - run: echo "Releasing app:${{ needs.build.outputs.image-tag }}"
      # → Releasing app:a1b2c3d
```

Частая ошибка — чтение выхода через `${{ jobs.build.outputs.* }}` в вызывающем воркфлоу: там доступен только контекст `needs`. Вторая типичная проблема — выход всегда пустой, потому что шаговый выход не был смапплен в `outputs` задачи или воркфлоу.

### Сценарий 5: Вложенные цепочки и перепередача секретов

Переиспользуемый процесс может сам вызывать другой переиспользуемый процесс. Помните: секреты не проходят сквозь цепочку автоматически — каждый уровень должен перепередать их явно.

```yaml
# A.yml — верхнеуровневый воркфлоу приложения
on:
  workflow_dispatch:

jobs:
  call-b:
    uses: my-org/ci-templates/.github/workflows/B.yml@v2
    secrets: inherit                     # A передаёт все свои секреты B
```

```yaml
# B.yml — промежуточный слой (репозиторий ci-templates)
on:
  workflow_call:
    secrets:
      repo-token:
        required: true

jobs:
  call-c:
    uses: different-org/example-repo/.github/workflows/C.yml@main
    with:
      environment: staging
    secrets:
      repo-token: ${{ secrets.repo-token }}  # B перепередает только этот секрет в C
```

Процесс C получит только `repo-token`, несмотря на то, что B владеет полным набором секретов от A. Это принцип наименьших привилегий в действии — промежуточный слой выступает фильтром. Права `GITHUB_TOKEN` вдоль цепочки аналогично не повышаются.

## Ограничения

- **Глубина вызовов**: Максимум 10 уровней воркфлоу — верхнеуровневый вызывающий плюс до девяти уровней вложенных переиспользуемых процессов (`caller -> r1 -> r2 -> ... -> r9`). Лимит поднят с четырёх уровней 6 ноября 2025. Циклы в дереве вызовов запрещены.
- **Количество вызовов**: Не более 50 уникальных переиспользуемых воркфлоу из одного файла, включая всё дерево вложенных вызовов.
- **Локальные файлы**: Нельзя вызывать Reusable Workflow, созданный динамически в том же запуске.
- **Синтаксис**: Ключ `uses` на уровне задачи несовместим с ключами `steps` или `container` в той же задаче.
- **Адресация**: В `uses` запрещены выражения и контексты; префиксы рефов (`refs/heads/...`, `refs/tags/...`) не допускаются; поддиректории внутри `.github/workflows` не сканируются.
- **Типы входов**: Только `string`, `number`, `boolean`; типы `choice` и `environment` из `workflow_dispatch` недоступны.
- **Секреты окружений**: Environment secrets не передаются через `on.workflow_call`; они применяются только если задача внутри переиспользуемого процесса сама назначит `environment`.
- **Непрозрачность передачи секретов**: Секреты не транзитивны (см. Сценарий 5).
- **Переменные окружения**: `env` не пересекает границу вызова в обе стороны (см. «Передача данных и контракты»).
- **Перезапуски**: При повторном запуске всех задач реф перечитывается заново (может подхватиться уже новый код шаблона); при перезапуске упавшей задачи или отдельной задачи используется SHA из первой попытки — поведение стабильно, но может расходиться с текущим состоянием тега/ветки.

## Устранение типичных проблем

| Симптом | Вероятная причина | Диагностика и решение |
| :--- | :--- | :--- |
| `Can't find 'workflow_call' trigger` | Файл не содержит `on: workflow_call`, лежит вне `.github/workflows` или в поддиректории | Проверьте путь и триггер: `grep -n "workflow_call" .github/workflows/*.yml` |
| Секрет внутри вызова пустой | Секрет не объявлен и не передан; либо это environment-secret, который не передаётся через `workflow_call` | Добавьте объявление в `on.workflow_call.secrets` и передачу в задаче-вызове; для env-секретов назначьте `environment:` на задачу внутри переиспользуемого процесса |
| `secrets: inherit` не сработал | Вызов из другой организации/enterprise без enterprise-плана | Передавайте секреты явно через `secrets:` |
| Выходы `outputs` пустые | Не выполнен маппинг шаг → задача → воркфлоу; чтение до завершения; при матрице последняя успешная комбинация записала пустую строку | Проверьте всю цепочку `GITHUB_OUTPUT` → `jobs.<id>.outputs` → `on.workflow_call.outputs`; читайте только через `needs.<job_id>.outputs` |
| `Resource not accessible by integration` | Запрошенные `permissions` превышают права вызывающего | Снизьте права переиспользуемого процесса или поднимите права задачи-вызова (в пределах допустимого) |
| Вызов приватного шаблонного репозитория падает | У вызывающего репозитория нет доступа на чтение репозитория шаблонов | Выдайте доступ (settings репозитория шаблонов или команда организации) |
| Ошибка валидации YAML при совмещении `uses` и `steps` | Ключи `uses`, `steps`, `container` взаимоисключающие на уровне задачи | Разнесите вызов и локальные шаги по разным задачам, связав их через `needs` |
| `Unrecognized named-value: 'matrix'` в `uses` | Попытка вставить выражение в `uses` | Выражения разрешены только в `with`/`secrets`/`strategy`; адрес вызова статичен |

Быстрая диагностика из CLI (требуется GitHub CLI v2.x):

```bash
gh run view <run-id> --json jobs --jq '.jobs[].name'
# → ["call-external / Reusable Build / build", "release"]
```

Если задача вызова отображается одной строкой с именем вызванного воркфлоу — механизм сработал; отдельного лога «вызова» не существует, шаги видны внутри задачи.

## Лучшие практики

1. **Явный контракт**: объявляйте все используемые секреты в `on.workflow_call.secrets`, даже при `secrets: inherit`, — контракт документирует себя сам и переживает смену механизма передачи.
2. **Версионирование шаблонов**: семантические теги в репозитории шаблонов + плавающий мажорный тег (`v1`) для обычных команд, SHA-пиннинг для критичных путей; старый мажорный тег поддерживайте до миграции всех потребителей, затем помечайте deprecated.
3. **Наименьшие привилегии**: минимальные `permissions` на уровне задачи; в промежуточных слоях цепочек перепередавайте только необходимые секреты.
4. **Именование**: префикс `reusable-` для файлов шаблонов помогает отличать их от обычных воркфлоу в списке прогонов.
5. **Мониторинг**: организации на GitHub Enterprise Cloud отслеживают использование шаблонов через audit log REST API — действие `prepared_workflow_job` фиксирует запуск задачи переиспользуемого воркфлоу. Полезно при планировании breaking changes и инвентаризации потребителей перед депрекацией старого мажорного тега.
6. **Откат изменений**: версионирование по тегам делает откат тривиальным — потребители возвращаются на предыдущий `@vN` одной правкой строки `uses`; локальные вызовы (`./`) откатываются вместе с git revert репозитория.
