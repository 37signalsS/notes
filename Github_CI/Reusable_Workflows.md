# GitHub Actions: Переиспользуемые рабочие процессы

Переиспользуемые рабочие процессы (reusable workflows) — это механизм в GitHub Actions, позволяющий одному рабочему процессу вызывать другой. Это ключевой инструмент для соблюдения принципа DRY (Don't Repeat Yourself — не повторяйся), минимизации дублирования кода и централизации логики процессов CI/CD (Continuous Integration / Continuous Deployment — непрерывная интеграция и непрерывное развертывание).

## Определения

- **Reusable Workflow (Переиспользуемый рабочий процесс)**: Рабочий процесс, предназначенный для вызова другими процессами. Определяется с помощью триггера `on: workflow_call`.
- **Caller Workflow (Вызывающий рабочий процесс)**: Рабочий процесс, который инициирует выполнение переиспользуемого процесса через задачу специального типа (`jobs.<job_id>.uses`).

## Основные концепции

### Создание переиспользуемого рабочего процесса

Для того чтобы сделать файл рабочего процесса доступным для вызова, необходимо в секции `on` указать событие `workflow_call`.

- **Входные параметры (`inputs`)**: Позволяют передавать данные из вызывающего процесса. Описываются аналогично параметрам `inputs` для триггера `workflow_dispatch`.
- **Секреты (`secrets`)**: По умолчанию переиспользуемый процесс не имеет доступа к секретам репозитория. Вызывающий процесс должен явно передать их по отдельности или использовать механизм наследования через `secrets: inherit`.
- **Выходные параметры (`outputs`)**: Позволяют переиспользуемому процессу передавать данные обратно вызывающему процессу. Данные передаются на уровне задач.

**Пример конфигурации (`.github/workflows/reusable-deploy.yml`):**

```yaml
name: Reusable Deployment Logic

on:
  workflow_call:
    inputs:
      target_env:
        required: true
        type: string
    outputs:
      status:
        description: "Статус выполнения деплоя"
        value: ${{ jobs.execute-deploy.outputs.deployment_status }}
    secrets:
      api_token:
        required: true

jobs:
  execute-deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.target_env }}
    outputs:
      deployment_status: ${{ steps.step1.outputs.status }}
    steps:
      - id: step1
        run: echo "status=success" >> $GITHUB_OUTPUT
```

### Механизм вызова

Вызов осуществляется внутри задачи с помощью ключа `uses`. Вся задача делегируется внешнему файлу.

- **`uses`**: Указывает путь. Формат для внешних репозиториев: `{owner}/{repo}/.github/workflows/{filename}@{ref}`. Для локальных файлов: `./.github/workflows/{filename}`.
- **`with`**: Передача `inputs`.
- **`secrets`**: Передача секретов (явно или `inherit`).
- **Права доступа (`permissions`)**: Переиспользуемый процесс наследует права `GITHUB_TOKEN` от вызывающей задачи, если они не заданы явно в вызывающем процессе.

### Ограничения и лимиты

- **Вложенность**: Максимальная глубина вложенности вызовов составляет **4 уровня** (caller -> reusable 1 -> reusable 2 -> reusable 3 -> reusable 4).
- **Матрицы**: Вызывающий процесс может использовать матрицу для запуска переиспользуемого процесса несколько раз с разными параметрами.
- **Окружения**: Переиспользуемый процесс может использовать `environment`, но вызывающий процесс должен иметь соответствующие права доступа.

## Практические сценарии

### Сценарий 1: Централизация стратегий развертывания

Использование единого процесса деплоя для всех микросервисов организации. Это гарантирует, что все сервисы разворачиваются по единому стандарту безопасности и качества.

### Сценарий 2: Вызов переиспользуемого процесса в матрице

```yaml
jobs:
  test-across-versions:
    strategy:
      matrix:
        node: [18, 20, 22]
    uses: ./.github/workflows/reusable-test.yml
    with:
      node-version: ${{ matrix.node }}
```
