# GitHub Actions: Матричные Сборки (Matrix Builds)

Матрица сборок — это мощный механизм в GitHub Actions для параллельного выполнения одной и той же задачи (`job`) с различными параметрами. Это основной инструмент для кросс-платформенного и мультивёрсионного тестирования.

## Определения

- **Матрица сборок (Build Matrix)**: Конфигурация в секции `strategy`, которая позволяет определить набор переменных (осей). GitHub Actions автоматически создает и запускает отдельную задачу для каждой возможной комбинации значений этих переменных.

## Основные концепции

### Принцип работы

Вы определяете "оси" матрицы, например, операционную систему и версию языка. GitHub Actions генерирует декартово произведение этих наборов.

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    node: [18, 20]
```

Эта конфигурация создаст 4 независимые задачи:

1. `os: ubuntu-latest`, `node: 18`
2. `os: ubuntu-latest`, `node: 20`
3. `os: windows-latest`, `node: 18`
4. `os: windows-latest`, `node: 20`

Внутри шагов (`steps`) к значениям матрицы можно обращаться через контекст `${{ matrix. }}` (например, `${{ matrix.os }}`).

### Управление стратегией

Поведение матрицы можно контролировать с помощью дополнительных ключей в `strategy`:

- **`fail-fast: false`**: По умолчанию GitHub отменяет все задачи в матрице, как только одна из них завершается с ошибкой. Установка `false` заставляет GitHub дождаться завершения всех задач, независимо от их статуса. Это полезно, чтобы увидеть все сломанные комбинации сразу.
- **`max-parallel`**: Ограничивает количество одновременно выполняемых задач в матрице. Помогает, если у вас ограниченное количество runner'ов или вы не хотите создавать избыточную нагрузку на внешние сервисы.

### Расширение матрицы

- **`exclude`**: Позволяет удалить определенные комбинации из матрицы. Удобно, если какая-то версия языка не поддерживается на определенной ОС.
- **`include`**: Позволяет добавить в матрицу новые комбинации, в том числе с дополнительными переменными. Это используется для "особых" сборок (например, экспериментальной) или для добавления метаданных к комбинации.

## Практические сценарии

### Сценарий 1: Кросс-платформенное тестирование

Классический пример: тестирование Python-проекта на разных ОС и версиях Python, с исключениями и специальными случаями.

```yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]
        python-version: ['3.9', '3.11', '3.12']
        # Исключаем несовместимую комбинацию
        exclude:
          - os: windows-latest
            python-version: '3.12'
        # Добавляем экспериментальную сборку
        include:
          - os: ubuntu-latest
            python-version: '3.12'
            experimental: true
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - run: pip install -r requirements.txt
      - run: pytest
      - name: Experimental build may fail
        if: matrix.experimental
        continue-on-error: true
```

### Сценарий 2: Распараллеливание тестов (Sharding)

Матрицу можно использовать не только для разных окружений, но и для разделения большого набора тестов на части (шарды) для ускорения CI.

```yaml
jobs:
  test-sharded:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4] # Создаем 4 шарда
    steps:
      - uses: actions/checkout@v4
      - run: pip install pytest
      - name: Run tests for shard ${{ matrix.shard }}
        run: |
          # Получаем список всех тестов и делим его на 4 части
          # Каждый шард выполняет свою часть (1/4, 2/4, и т.д.)
          pytest --shard-id ${{ matrix.shard }} --shard-total 4
```
