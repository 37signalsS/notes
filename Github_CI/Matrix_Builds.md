# GitHub Actions: Матричные сборки

Матрица сборок (Matrix Strategy) — это механизм в GitHub Actions для автоматической генерации набора задач (`jobs`) на основе комбинаций различных параметров. Это фундаментальный инструмент для кросс-платформенного тестирования, обеспечения совместимости версий и оптимизации пайплайнов за счет распараллеливания выполнения. Одна строка YAML заменяет десятки скопированных задач, а фактическое число одновременных запусков регулируется квотой конкурентности вашего тарифного плана (см. раздел о технических лимитах).

## Определения

- **Матрица сборок (Build Matrix)**: Конфигурация в секции `strategy`, определяющая одну или несколько переменных («осей»), комбинации которых порождают независимые экземпляры задачи.
- **Ось матрицы (Matrix Axis)**: Переменная (например, `os` или `version`), содержащая список значений для перебора.
- **Комбинация (Combination)**: Результирующий экземпляр задачи, созданный из конкретного набора значений осей матрицы.
- **Динамическая матрица**: Матрица, конфигурация которой формируется программно во время выполнения предыдущей задачи и передается через выходные параметры (`outputs`) в связке с функцией `fromJSON`.
- **Fan-out / Fan-in**: Паттерн организации матричного конвейера: одна задача порождает множество параллельных задач (fan-out), после чего отдельная сводная задача собирает и агрегирует их результаты (fan-in) — например, объединяет отчеты о покрытии или артефакты сборки.
- **Экспериментальная задача**: Комбинация матрицы, для которой `continue-on-error` вычисляется из значения оси (например, `continue-on-error: ${{ matrix.experimental }}`); её падение не отменяет соседние задачи и не красит прогон.

## Основные концепции

### Механизм генерации (Декартово произведение)

При определении нескольких осей в секции `matrix`, GitHub Actions генерирует декартово произведение всех значений. Каждая полученная комбинация становится отдельной задачей, которая запускается на исполнителе.

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    version: [20, 22, 24]
```
В данном примере будет создано **6 задач** (2 ОС × 3 версии). Доступ к значениям внутри задачи осуществляется через контекст `${{ matrix.os }}` и `${{ matrix.version }}`.

Порядок генерации детерминирован: последняя объявленная ось перебирается быстрее всего. Для конфигурации выше задачи создаются в порядке `(20, ubuntu) → (20, windows) → (22, ubuntu) → ...`. Это влияет только на нумерацию задач, но помогает читать логи и предсказывать порядок старта.

Отображаемое имя каждой задачи формируется по умолчанию как `идентификатор_задачи (значение1, значение2)`, например `test (ubuntu-latest, 22)`. Для читаемых имен в UI задавайте шаблон явно:

```yaml
jobs:
  test:
    name: Test ${{ matrix.os }} / Node ${{ matrix.version }}
    runs-on: ${{ matrix.os }}
```

Значениями осей могут быть не только строки и числа, но и объекты — это позволяет держать связанные параметры вместе (см. Сценарий 4).

### Управление выполнением

1. **`fail-fast`**:
   - **По умолчанию (`true`)**: Если любая задача в матрице завершается ошибкой, GitHub Actions немедленно отменяет все остальные задачи этой матрицы, которые еще выполняются или стоят в очереди. Это экономит лимиты минут.
   - **Значение `false`**: Гарантирует выполнение всех задач матрицы до конца, независимо от результатов отдельных веток. Рекомендуется для кросс-платформенного тестирования, чтобы получить полный отчет о сбоях.
   - **Взаимодействие с `continue-on-error`**: Отмена срабатывает только при падении задачи с `continue-on-error: false`. Если упала экспериментальная задача (`continue-on-error: true`), остальные задачи продолжают работу, а статус прогона не становится красным. Стандартная связка для нестабильных версий:
     ```yaml
     continue-on-error: ${{ matrix.experimental }}
     ```

2. **`max-parallel`**:
   - Ограничивает количество задач матрицы, которые могут выполняться одновременно. По умолчанию GitHub Actions стремится запустить как можно больше задач параллельно (в рамках общих лимитов аккаунта).
   - Применяется для предотвращения перегрузки внешних ресурсов (например, баз данных или API с лимитами на количество запросов).
   - Фактическая параллельность ограничена сверху квотой конкурентности плана (Free — 20 одновременных задач, Pro — 40, Team — 60, с отдельным потолком для macOS): если матрица шире квоты, лишние задачи ждут в очереди. Детали — в разделе про среды выполнения.

### Модификация состава матрицы

Порядок обработки важен: сначала формируется исходная сетка декартова произведения, затем к ней применяется `exclude` (удаления), и уже к результату применяются записи `include` (дополнения и расширения).

1. **`exclude`**:
   Используется для удаления конкретных комбинаций из декартова произведения. Исключение происходит только при **полном совпадении** всех указанных свойств в объекте `exclude`.
   ```yaml
   strategy:
     matrix:
       os: [ubuntu-latest, windows-latest]
       version: [20, 22]
       exclude:
         - os: windows-latest
           version: 20 # Эта комбинация не будет запущена
   ```
   Важный нюанс: если в объекте `exclude` указаны не все оси, действует правило **частичного совпадения** — удаляются все комбинации, содержащие указанные значения. Запись `exclude: [{os: windows-latest}]` без поля `version` уберет обе windows-задачи сразу. Это же делает частичный `exclude` удобным способом массового удаления: `exclude: [{version: 20}]` вычеркнет версию 20 на всех ОС.

2. **`include`**:
   Позволяет расширять матрицу двумя способами:
   - **Дополнение**: Добавление новых свойств к существующим комбинациям.
   - **Расширение**: Добавление полностью новых комбинаций, не входящих в декартово произведение.
   ```yaml
   strategy:
     matrix:
       os: [ubuntu-latest]
       version: [22]
       include:
         - os: ubuntu-latest
           version: 22
           experimental: true # Дополнение существующей задачи
         - os: macos-latest
           version: 24 # Новая комбинация вне основной сетки
   ```
   Точный алгоритм обработки каждой записи `include`:
   - Если запись не перезаписывает ни одно значение исходной сетки, она **дополняет все** исходные комбинации (`{color: green}` добавит свойство color каждой задаче).
   - Если запись содержит часть осей, она дополняет **только совпадающие** комбинации (`{animal: cat, color: pink}` покрасит в pink только кошачьи задачи), при этом может перезаписать значение, добавленное предыдущей записью `include`.
   - Если запись требует перезаписать **исходное** значение сетки, она не может слиться ни с одной комбинацией и превращается в **отдельную новую** задачу (`{fruit: banana}` при отсутствии banana в сетке даст самостоятельную задачу только со значением fruit).
   - Новые комбинации между собой не комбинируются: две такие записи создадут ровно две задачи, а не их пересечение.

### Значения-объекты

Ключи матрицы могут содержать любые строковые или числовые значения, а также JSON-объекты. Объект группирует связанные параметры одной конфигурации и обращается к ним через вложенный путь:

```yaml
strategy:
  matrix:
    target:
      - { os: ubuntu-24.04, arch: amd64 }
      - { os: ubuntu-24.04-arm, arch: arm64 }
      - { os: macos-15, arch: universal }
runs-on: ${{ matrix.target.os }}
steps:
  - run: build --arch=${{ matrix.target.arch }}
```

Такой подход исключает рассинхронизацию пар «раннер — архитектура», которая часто возникает при двух отдельных осях и ручном `exclude`.

### Матрица поверх переиспользуемых воркфлоу

Задача вызова переиспользуемого воркфлоу (`uses:`) также поддерживает `strategy` — каждая комбинация вызывает воркфлоу отдельным экземпляром:

```yaml
jobs:
  call-test:
    strategy:
      fail-fast: false
      matrix:
        node-version: [20, 22, 24]
    uses: org/shared-workflows/.github/workflows/test.yml@v3
    with:
      node-version: ${{ matrix.node-version }}
```

Это стандартный способ масштабировать единый CI-шаблон на десятки репозиториев: вызывающий репозиторий решает, какие комбинации гонять. Кроме того, вложенность «матрица → переиспользуемый воркфлоу → внутренняя матрица» — единственный способ обойти лимит 256 задач (см. ниже). Подробности — в разделе о переиспользуемых воркфлоу.

### Технические лимиты

- **Максимальное количество задач**: Одна матрица может сгенерировать не более **256 задач** за один прогон воркфлоу. Лимит действует одинаково для hosted и self-hosted раннеров. Важно: превышение лимита **падает весь прогон**, а не обрезается лишнее — следите за размером динамических матриц.
- **Обход через вложенность**: Задача-матрица может вызывать переиспользуемый воркфлоу, внутри которого своя матрица. Каждый уровень умножает доступную емкость: два уровня дают до 65 536 задач, три уровня — теоретически до 16,7 млн. При этом обязательно ограничивайте параллелизм внешнего уровня (`max-parallel: 1`) и настраивайте `concurrency`, иначе легко устроить лавину запросов к API GitHub и получить троттлинг аккаунта.
- **Контекст**: Ключи матрицы могут содержать любые строковые или числовые значения, а также JSON-объекты. В определении матрицы доступны выражения и контексты (например, `matrix: ${{ fromJSON(github.event.client_payload.versions) }}`), но не другие матрицы.

Детальный свод лимитов платформы: **[Среды выполнения и ограничения](./Environment_Limitations.md)**.

## Практические сценарии

### Сценарий 1: Сложное кросс-платформенное тестирование

Проверка совместимости с учетом специфических требований ОС и экспериментальных версий (актуальность — 2026 год).

```yaml
jobs:
  test:
    name: Test on ${{ matrix.os }} / Node ${{ matrix.node }}
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: [20, 22]
        include:
          - os: ubuntu-latest
            node: 24
            experimental: true
        exclude:
          - os: windows-latest
            node: 20
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ matrix.node }}
          cache: 'npm'
      - run: npm ci
      - run: npm test
        continue-on-error: ${{ matrix.experimental || false }}
```

Разбор: сетка 3 × 2 = 6 задач, минус одна исключенная (Windows + Node 20), плюс одна добавленная (Node 24 только на Linux) — итого 6 задач. Экспериментальная комбинация помечена дважды: через `include` задается флаг, а `continue-on-error: ${{ matrix.experimental || false }}` страхует undefined для обычных комбинаций (выражение `|| false` защищает от ошибки сравнения с пустым значением). Валидация: в UI видно 6 задач; падение задачи с Node 24 не красит прогон, но сама задача помечается нейтральным значком с аннотацией.

### Сценарий 2: Шардирование тестов (Parallel Sharding)

Разделение большого набора тестов (например, E2E) на несколько исполнителей для сокращения времени обратной связи.

```yaml
jobs:
  e2e:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4, 5]
    steps:
      - uses: actions/checkout@v7
      - name: Run Sharded Tests
        # Предполагается, что тестовый фреймворк поддерживает параметры шардирования
        run: npx playwright test --shard=${{ matrix.shard }}/5
```

Здесь `fail-fast: false` особенно важен: при падении одного шарда нужно увидеть результаты остальных, чтобы понять масштаб проблемы (упал конкретный тест или инфраструктура). Номер шарда обязателен в имени отчета/артефакта (`blob-report-${{ matrix.shard }}`) — артефакты неизменяемы и требуют уникальных имен. Playwright имеет встроенную команду мержа шардов (`npx playwright merge-reports`), которую стоит выполнять в сводной задаче fan-in.

### Сценарий 3: Динамическая матрица для монорепозитория

Генерация списка задач на основе измененных файлов. Это позволяет запускать тесты только для тех сервисов, которые были затронуты в коммите.

```yaml
jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      services: ${{ steps.filter.outputs.changes }}
    steps:
      - uses: actions/checkout@v7
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          filters: |
            auth: 'services/auth/**'
            billing: 'services/billing/**'
            ui: 'services/ui/**'

  test-dynamic:
    needs: detect-changes
    if: needs.detect-changes.outputs.services != '[]'
    runs-on: ubuntu-latest
    strategy:
      matrix:
        service: ${{ fromJSON(needs.detect-changes.outputs.services) }}
    steps:
      - name: Test ${{ matrix.service }}
        run: |
          echo "Testing service: ${{ matrix.service }}"
          make test SERVICE=${{ matrix.service }}
```

Ключевые детали реализации: экшен `dorny/paths-filter` возвращает измененные категории как JSON-массив строк — именно поэтому он идеален в паре с `fromJSON`. Условие `!= '[]'` обязательна: при отсутствии изменений массив пуст, и без guard'а задача либо упадет, либо породит бессмысленный запуск. Валидация: в списке задач видны только затронутые сервисы; при пуше документации весь воркфлоу завершится мгновенно на этапе detect-changes.

### Сценарий 4: Матрица объектов для мультиплатформенной сборки

Сборка бинарников под несколько архитектур, где пара «раннер — цель сборки» неразрывна:

```yaml
jobs:
  build:
    name: Build ${{ matrix.target.arch }}
    runs-on: ${{ matrix.target.os }}
    strategy:
      fail-fast: false
      matrix:
        target:
          - { os: ubuntu-24.04, arch: amd64, ext: '' }
          - { os: ubuntu-24.04-arm, arch: arm64, ext: '' }
          - { os: windows-2025, arch: amd64, ext: '.exe' }
          - { os: macos-15, arch: universal, ext: '' }
    steps:
      - uses: actions/checkout@v7
      - name: Build binary
        run: make build ARCH=${{ matrix.target.arch }}
      - uses: actions/upload-artifact@v7
        with:
          name: app-${{ matrix.target.arch }}
          path: bin/app${{ matrix.target.ext }}
```

Преимущество перед двумя осями (`os: [...]` + `arch: [...]`) — невозможность получить невалидные комбинации вроде `windows + arm64-native`: каждая запись объекта уже согласована. Расширение `.exe` едет вместе с Windows-конфигурацией и используется в шаге загрузки артефакта. Валидация: четыре задачи, каждая на своем раннере; артефакты называются `app-amd64`, `app-arm64`, `app-universal` — уникально, без конфликтов.

### Сценарий 5: Fan-out/Fan-in с общей матрицей

Официальный паттерн: одна задача определяет список, две другие используют одну и ту же матрицу для создания и потребления артефактов:

```yaml
name: Shared Matrix Pipeline

on: [push]

jobs:
  define-matrix:
    runs-on: ubuntu-slim
    outputs:
      colors: ${{ steps.colors.outputs.colors }}
    steps:
      - id: colors
        run: echo 'colors=["red", "green", "blue"]' >> "$GITHUB_OUTPUT"

  produce:
    needs: define-matrix
    runs-on: ubuntu-latest
    strategy:
      matrix:
        color: ${{ fromJSON(needs.define-matrix.outputs.colors) }}
    steps:
      - run: echo "$color" > color
        env:
          color: ${{ matrix.color }}
      - uses: actions/upload-artifact@v7
        with:
          name: color-${{ matrix.color }}
          path: color

  consume:
    needs: [define-matrix, produce]
    runs-on: ubuntu-latest
    strategy:
      matrix:
        color: ${{ fromJSON(needs.define-matrix.outputs.colors) }}
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: color-${{ matrix.color }}
      - run: cat color
```

Механика: источник правды один — выход задачи `define-matrix`; продюсер и консьюмер гарантированно работают с одинаковым набором комбинаций. Имена артефактов включают значение матрицы (неизменяемость артефактов). Список можно строить сколь угодно сложной логикой: чтением каталога сервисов, ответом API, jq-фильтрацией манифеста. Для полной агрегации «всё в одной задаче» у `download-artifact` есть режим `pattern` + `merge-multiple: true`, собирающий все артефакты префикса в одну папку. Предусловие валидации: вывод шага-источника обязан быть валидным JSON-массивом — проверьте его локально тем же shell-скриптом до пуша.

### Сценарий 6: Матрица деплоя поверх переиспользуемого воркфлоу

Тот же процесс деплоя раскатывается во все окружения одним вызовом:

```yaml
# .github/workflows/deploy-all.yml
jobs:
  deploy:
    strategy:
      fail-fast: false      # Падение staging не должно останавливать prod
      max-parallel: 2       # Не более двух окружений одновременно
      matrix:
        environment: [staging, eu-prod, us-prod]
    uses: ./.github/workflows/deploy.yml
    with:
      environment: ${{ matrix.environment }}
    secrets: inherit
```

Особенности задачи с `uses:`: внутри неё нельзя описать `steps` и `timeout-minutes` — вся логика живет в переиспользуемом воркфлоу, а матричная задача лишь параметризует вызовы. `secrets: inherit` пробрасывает все секреты вызывающего репозитория (для гранулярности используйте явную передачу). Связка `fail-fast: false` + `max-parallel: 2` дает управляемый конвейер: окружения катятся парами независимо друг от друга. Валидация: в UI прогон содержит по одному экземпляру внутреннего воркфлоу на каждое окружение; каждый экземпляр виден как отдельная группа задач с именем комбинации. Для production-окружений добавьте внутрь переиспользуемого воркфлоу привязку к GitHub Environment с ручным одобрением.

## Устранение типичных проблем

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `exclude` не удаляет ожидаемую комбинацию | Опечатка в имени оси или несовпадение типа значения (`20` против `'20'`) | Сверить имена ключей и типы значений с исходной сеткой |
| `include` создал лишнюю задачу вместо дополнения существующих | Запись пытается перезаписать исходное значение оси | Убрать конфликтующее поле из записи или добавить новое свойство, а не менять ось |
| Падение одной версии отменило всю матрицу | Действует `fail-fast: true` по умолчанию | Явно указать `fail-fast: false` или пометить нестабильные комбинации через `continue-on-error: ${{ matrix.experimental }}` |
| Задачи стартуют не все сразу | Исчерпана квота конкурентности плана или задан `max-parallel` | Свериться с лимитами плана; для ускорения — Larger Runners или меньше комбинаций |
| Прогон падает с ошибкой лимита матрицы | Более 256 комбинаций (частая ошибка динамических матриц) | Разбить через вложенный переиспользуемый воркфлоу; ограничить внешний `max-parallel: 1` |
| Динамическая матрица не породила ни одной задачи или упала | Выход предыдущей задачи — не JSON-массив (`''` вместо `'[]'`) | Гарантировать формат выхода; ставить guard `if: needs.x.outputs.y != '[]'` |
| Конфликт при загрузке артефактов из матрицы | Одинаковое имя артефакта у комбинаций (неизменяемость артефактов с v4) | Включить `${{ matrix.* }}` в имя артефакта |

## Лучшие практики

1. **Называйте задачи явно** (`name:` с интерполяцией `${{ matrix.* }}`) — дефолтные подписи плохо читаются в длинных прогонах.
2. **Группируйте связанные параметры в объекты**, а не в отдельные оси с ручным `exclude` — так исчезают невалидные комбинации.
3. **Ставьте `fail-fast: false` для отчётных матриц** (тесты, линтеры) и оставляйте `true` для экономных конвейеров, где первая ошибка делает остальное бессмысленным.
4. **Помечайте нестабильные комбинации** через `continue-on-error: ${{ matrix.experimental }}` вместо удаления — данные о падениях остаются видимыми.
5. **Держите один источник списка комбинаций**: динамическая матрица из outputs вместо копипасты списков между задачами.
6. **Уникальные имена артефактов с индексом матрицы** — всегда, без исключений.
7. **Следите за ростом сетки**: 256 задач — жесткий предел на прогон; динамические матрицы обязаны иметь верхнюю границу.
8. **Для тяжелых комбинаций используйте специализированные раннеры**: arm64-цели собирайте на нативных arm64-раннерах (`ubuntu-24.04-arm`), а не через эмуляцию на x64.
