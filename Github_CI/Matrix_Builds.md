# GitHub Actions: Матричные сборки

Матрица сборок (Matrix Strategy) — это механизм в GitHub Actions для автоматической генерации набора задач (`jobs`) на основе комбинаций различных параметров. Это фундаментальный инструмент для кросс-платформенного тестирования, обеспечения совместимости версий и оптимизации пайплайнов за счет распараллеливания выполнения.

## Определения

- **Матрица сборок (Build Matrix)**: Конфигурация в секции `strategy`, определяющая одну или несколько переменных («осей»), комбинации которых порождают независимые экземпляры задачи.
- **Ось матрицы (Matrix Axis)**: Переменная (например, `os` или `version`), содержащая список значений для перебора.
- **Комбинация (Combination)**: Результирующий экземпляр задачи, созданный из конкретного набора значений осей матрицы.
- **Динамическая матрица**: Матрица, конфигурация которой формируется программно во время выполнения предыдущей задачи и передается через выходные параметры (`outputs`).

## Основные концепции

### Механизм генерации (Декартово произведение)

При определении нескольких осей в секции `matrix`, GitHub Actions генерирует декартово произведение всех значений. Каждая полученная комбинация становится отдельной задачей, которая запускается на исполнителе.

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    version: [20, 22, 24]
```
В данном примере будет создано **6 задач** (2 ОС × 3 версии). Доступ к значениям внутри задачи осуществляется через контекст `${{ matrix.os }}` и `${{ matrix.version }}`.

### Управление выполнением

1. **`fail-fast`**:
   - **По умолчанию (`true`)**: Если любая задача в матрице завершается ошибкой, GitHub Actions немедленно отменяет все остальные задачи этой матрицы, которые еще выполняются или стоят в очереди. Это экономит лимиты минут.
   - **Значение `false`**: Гарантирует выполнение всех задач матрицы до конца, независимо от результатов отдельных веток. Рекомендуется для кросс-платформенного тестирования, чтобы получить полный отчет о сбоях.

2. **`max-parallel`**:
   - Ограничивает количество задач матрицы, которые могут выполняться одновременно. По умолчанию GitHub Actions стремится запустить как можно больше задач параллельно (в рамках общих лимитов аккаунта).
   - Применяется для предотвращения перегрузки внешних ресурсов (например, баз данных или API с лимитами на количество запросов).

### Модификация состава матрицы

1. **`exclude`**:
   Используется для удаления конкретных комбинаций из декартова произведения. Исключение происходит только при **полном совпадении** всех указанных свойств в объекте `exclude`.
   ```yaml
   strategy:
     matrix:
       os: [ubuntu-latest, windows-latest]
       version: [20, 22]
       exclude:
         - os: windows-latest
           version: 20 # Эта комбинация не будет запущена
   ```

2. **`include`**:
   Позволяет расширять матрицу двумя способами:
   - **Дополнение**: Добавление новых свойств к существующим комбинациям.
   - **Расширение**: Добавление полностью новых комбинаций, не входящих в декартово произведение.
   ```yaml
   strategy:
     matrix:
       os: [ubuntu-latest]
       version: [22]
       include:
         - os: ubuntu-latest
           version: 22
           experimental: true # Дополнение существующей задачи
         - os: macos-latest
           version: 24 # Новая комбинация вне основной сетки
   ```

### Технические лимиты

- **Максимальное количество задач**: Одна матрица может сгенерировать не более **256 задач**.
- **Контекст**: Ключи матрицы могут содержать любые строковые или числовые значения, а также JSON-объекты.

## Практические сценарии

### Сценарий 1: Сложное кросс-платформенное тестирование

Проверка совместимости с учетом специфических требований ОС и экспериментальных версий (актуальность — 2026 год).

```yaml
jobs:
  test:
    name: Test on ${{ matrix.os }} / Node ${{ matrix.node }}
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: [20, 22]
        include:
          - os: ubuntu-latest
            node: 24
            experimental: true
        exclude:
          - os: windows-latest
            node: 20
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ matrix.node }}
          cache: 'npm'
      - run: npm ci
      - run: npm test
        continue-on-error: ${{ matrix.experimental || false }}
```

### Сценарий 2: Шардирование тестов (Parallel Sharding)

Разделение большого набора тестов (например, E2E) на несколько исполнителей для сокращения времени обратной связи.

```yaml
jobs:
  e2e:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4, 5]
    steps:
      - uses: actions/checkout@v7
      - name: Run Sharded Tests
        # Предполагается, что тестовый фреймворк поддерживает параметры шардирования
        run: npx playwright test --shard=${{ matrix.shard }}/5
```

### Сценарий 3: Динамическая матрица для монорепозитория

Генерация списка задач на основе измененных файлов. Это позволяет запускать тесты только для тех сервисов, которые были затронуты в коммите.

```yaml
jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      services: ${{ steps.filter.outputs.changes }}
    steps:
      - uses: actions/checkout@v7
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          filters: |
            auth: 'services/auth/**'
            billing: 'services/billing/**'
            ui: 'services/ui/**'

  test-dynamic:
    needs: detect-changes
    if: needs.detect-changes.outputs.services != '[]'
    runs-on: ubuntu-latest
    strategy:
      matrix:
        service: ${{ fromJSON(needs.detect-changes.outputs.services) }}
    steps:
      - name: Test ${{ matrix.service }}
        run: |
          echo "Testing service: ${{ matrix.service }}"
          make test SERVICE=${{ matrix.service }}
```
