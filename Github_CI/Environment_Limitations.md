# GitHub Actions: Среды выполнения (Runners) и их ограничения

Выбор среды выполнения (`runner`) — ключевое архитектурное решение в GitHub Actions. От него зависят доступные ресурсы, скорость, безопасность и возможности CI/CD пайплайнов.

## Определения

- **GitHub-hosted runner**: Виртуальная машина, управляемая и обслуживаемая GitHub. Предоставляется по запросу с предустановленным набором ПО. Среда является эфемерной и уничтожается после завершения задачи (`job`).
- **Self-hosted runner**: Ваш собственный сервер (физический, VM, контейнер), на котором установлено ПО агента GitHub Actions. Вы полностью контролируете его окружение, но также несете ответственность за его обслуживание.

## Основные концепции

### Ключевые различия

| Категория | GitHub-hosted | Self-hosted |
| :--- | :--- | :--- |
| **Обслуживание** | Нет, управляется GitHub | Полностью ваша ответственность |
| **Окружение** | Стандартное, обновляется GitHub | Кастомное, настраивается вами |
| **Ресурсы** | Фиксированные (2-ядерный CPU, 7 ГБ RAM, 14 ГБ SSD) | Ограничены только вашим хостом |
| **Сеть** | Публичные IP-адреса из пула GitHub | Контролируемый доступ (в т.ч. из приватной сети) |
| **Безопасность** | Высокая изоляция, но риски при работе с форками | Полная ответственность на вас, риски доступа к внутренней сети |
| **Стоимость** | Включено в тариф (с лимитами на минуты) | Стоимость вашей инфраструктуры |

### Ограничения GitHub-hosted Runners

- **Время выполнения**: Задачи (`jobs`) ограничены по времени (до 6 часов). Для долгих задач используйте `timeout-minutes` или self-hosted runner'ы.
- **Ресурсы**: Фиксированные ресурсы могут быть недостаточны для "тяжелых" сборок или интенсивных тестов. Для таких задач существуют [Large Runners](https://docs.github.com/en/actions/using-github-hosted-runners/using-larger-runners) (за отдельную плату).
- **Дисковое пространство**: Ограничено. Для работы с большими артефактами или кэшем требуется оптимизация.

### Сеть и Безопасность

- **Доступ к приватным ресурсам**: Hosted-runner'ы имеют динамические IP, что усложняет доступ к ресурсам за файрволом. Эту проблему решают self-hosted runner'ы, размещенные в вашей приватной сети.
- **Безопасность Self-hosted**: Так как self-hosted runner'ы имеют доступ к вашей сети, следует с осторожностью использовать их в публичных репозиториях. Вредоносный код в Pull Request может скомпрометировать среду. Используйте их только в приватных репозиториях или с `workflow_run` / ручным подтверждением для PR.
- **Права доступа (`permissions`)**: Всегда выдавайте `GITHUB_TOKEN` только минимально необходимые права через ключ `permissions` в воркфлоу.

## Практические сценарии

### Сценарий 1: Доступ к приватной сети

**Проблема**: Тестам нужен доступ к staging-базе данных, которая находится в приватной подсети (VPC).

**Решение**: Использовать **self-hosted runner**, развернутый на ВМ в той же подсети.

### Сценарий 2: Управление правами для деплоя

**Проблема**: Для публикации в Google Play требуется OIDC-токен, но другие задачи не должны иметь к нему доступ.

**Решение**: Использовать ключ `permissions` на уровне задачи, чтобы выдать разрешение `id-token: write` только для `build-and-deploy`.

```yaml
jobs:
  build-and-deploy:
    runs-on: macos-latest
    timeout-minutes: 90
    permissions:
      contents: read
      id-token: write # Разрешение на получение OIDC-токена
    steps:
      - name: 'Authenticate to Yandex Cloud'
        uses: 'yandex-cloud/actions/auth@v0'
        with:
          service-account-id: 'sa-xxxxxxxxxxxxxxxxx'
      # ... шаги для деплоя
```

> **Примечание:** Для локального аринта используйте self-hosted runner'ы с прямой аутентификацией через `yc` CLI или kubeconfig.
