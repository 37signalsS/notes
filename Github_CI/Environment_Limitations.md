# GitHub Actions: Среды выполнения и ограничения

Выбор среды выполнения (исполнителя, или runner) является фундаментальным архитектурным решением в GitHub Actions. От этого выбора напрямую зависят доступные вычислительные ресурсы, скорость выполнения этапов, уровень безопасности и итоговая стоимость конвейеров CI/CD (Continuous Integration / Continuous Deployment — непрерывная интеграция и непрерывное развертывание).

## Определения

- **GitHub-hosted runner (Облачный исполнитель)**: Виртуальная машина (VM — Virtual Machine), полностью управляемая GitHub. Предоставляется по требованию с предустановленным программным обеспечением. Среда является эфемерной — она создается для конкретной задачи и полностью уничтожается после её завершения.
- **Self-hosted runner (Собственный исполнитель)**: Выделенный сервер (физический, виртуальная машина или контейнер), на котором установлен агент GitHub Actions. Пользователь самостоятельно управляет операционной системой (OS — Operating System), аппаратными ресурсами и сетевым доступом.

## Основные концепции

### Различия между типами исполнителей

| Категория | GitHub-hosted | Self-hosted |
| :--- | :--- | :--- |
| **Обслуживание** | Полностью на стороне GitHub | Ответственность пользователя |
| **Окружение** | Стандартные образы, обновляются GitHub | Полностью настраиваемое пользователем |
| **Ресурсы** | Фиксированные спецификации | Ограничены только мощностью хоста |
| **Сеть** | Публичные IP-адреса из пулов GitHub | Контролируемый доступ (включая VPC) |
| **Безопасность** | Высокая изоляция каждой задачи | Риски доступа к внутренней сети |
| **Стоимость** | Поминутная тарификация | Бесплатно (инфраструктура пользователя) |

### Технические характеристики (спецификации 2026)

**Стандартные исполнители (Standard runners)**:

| Тип OS | CPU (Центральный процессор) | RAM (Оперативная память) | SSD (Твердотельный накопитель) |
| :--- | :--- | :--- | :--- |
| Ubuntu Linux | 2 ядра | 7 ГБ | 14 ГБ |
| Windows | 2 ядра | 7 ГБ | 14 ГБ |
| macOS | 3–4 ядра (M1/Intel) | 7 ГБ | 14 ГБ |

**Специализированные решения**:
- **Single-CPU runners**: Контейнеры на общей виртуальной машине с 1 ядром и уменьшенным объемом памяти. Стоимость ниже примерно на 50%.
- **Larger runners**: Доступны для планов Team и Enterprise Cloud. Предлагают до 96 ядер процессора и графические ускорители (GPU).

### Временные ограничения и лимиты

- **Максимальная длительность задачи (Job)**: 6 часов. По истечении этого времени процесс принудительно прерывается.
- **Время ожидания в очереди**: Если задача не была принята исполнителем в течение 30–45 минут (в зависимости от типа события), запуск автоматически отменяется.
- **Таймаут по умолчанию**: Составляет 360 минут, но может быть переопределен в конфигурации через параметр `timeout-minutes`.

### Тарификация и изменения в 2026 году

**Облачные исполнители (GitHub-hosted)**:
С 1 января 2026 года введена новая модель ценообразования, предусматривающая снижение стоимости ресурсов до 39%. Базовая цена за использование платформы составляет $0.002 за минуту и включена в итоговый тариф.

**Собственные исполнители (Self-hosted)**:
Ранее анонсированное введение платы за использование платформы ($0.002/мин) с 1 марта 2026 года было **отложено** на неопределенный срок. На текущий момент минуты использования собственных исполнителей остаются бесплатными.

### Сетевое взаимодействие и безопасность

- **Доступ к ресурсам в VPC (Virtual Private Cloud)**: Облачные исполнители имеют динамические публичные IP-адреса, что затрудняет их использование для работы с ресурсами за файрволом. Собственные исполнители могут быть размещены непосредственно внутри приватной сети организации.
- **Риски при работе с Pull Request (PR)**: Использование собственных исполнителей в публичных репозиториях опасно, так как они имеют доступ к внутренней сети. Рекомендуется использовать их только в приватных проектах или требовать ручного подтверждения для внешних запросов на слияние.
- **Минимальные права доступа**: Рекомендуется всегда ограничивать права временного токена `GITHUB_TOKEN` через секцию `permissions` в файле рабочего процесса.

## Практические сценарии

### Сценарий 1: Организация доступа к ресурсам в частной сети

**Проблема**: Тестовому пайплайну необходимо выполнить запрос к базе данных, находящейся в закрытом сегменте облака без публичного доступа.

**Решение**: Развертывание собственного исполнителя (Self-hosted runner) в виде виртуальной машины внутри той же подсети, где находится база данных. Это позволяет избежать открытия портов во внешний интернет.

### Сценарий 2: Управление правами доступа для развертывания

**Проблема**: Процесс деплоя требует OIDC-токена (OpenID Connect) для аутентификации в облачном провайдере, при этом остальные задачи пайплайна не должны иметь доступа к этому механизму.

**Решение**: Использование гранулярных разрешений на уровне конкретной задачи.

```yaml
jobs:
  deploy-to-production:
    runs-on: ubuntu-latest
    timeout-minutes: 60
    permissions:
      contents: read     # Доступ к коду только для чтения
      id-token: write    # Разрешение на генерацию OIDC-токена
    steps:
      - name: Authenticate to Cloud Provider
        uses: cloud-provider/auth-action@v1
        with:
          workload-identity-provider: 'projects/123/locations/global/workloadIdentityPools/my-pool/providers/my-provider'
      # ... шаги развертывания
```
