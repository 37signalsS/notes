# GitHub Actions: Среды выполнения и ограничения

**Актуально для:** GitHub Actions, октябрь 2026 (тарифы hosted-раннеров после снижения цен 1 января 2026; `ubuntu-slim` GA 22 января 2026; спецификации стандартных и Larger runners; Node 20 удалён из Actions, сентябрь 2026)

Выбор среды выполнения (исполнителя, или runner) является фундаментальным архитектурным решением в GitHub Actions. От этого выбора напрямую зависят доступные вычислительные ресурсы, скорость выполнения этапов, уровень безопасности и итоговая стоимость конвейеров CI/CD.

## Определения

- **GitHub-hosted runner (Облачный исполнитель)**: Виртуальная машина (VM), полностью управляемая GitHub. Предоставляется по требованию с предустановленным ПО. Среда является эфемерной.
- **Self-hosted runner (Собственный исполнитель)**: Выделенный сервер или контейнер, управляемый пользователем. Обеспечивает максимальный контроль над железом и сетью.
- **Actions Cloud Platform Charge**: Сбор за использование облачной платформы оркестрации ($0.002/мин), покрывающий control plane (планирование задач, стриминг логов, хранение секретов, аудит). С 1 января 2026 года включён в состав поминутных расценок GitHub-hosted раннеров (отдельной строкой в счёте не выделяется). Отдельный сбор для self-hosted раннеров анонсировался (запуск с 1 марта 2026), но в декабре 2025 был отложён на неопределённый срок и не взимается — self-hosted остаются бесплатными на уровне платформы.
- **API Rate Limit**: Ограничение количества запросов к GitHub API в рамках одного воркфлоу.
- **Runner Label (Метка исполнителя)**: Строковый идентификатор, по которому оркестратор сопоставляет задачу (`runs-on`) с пулом исполнителей. Бывают стандартные (`ubuntu-latest`, `macos-latest`), архивные (`ubuntu-22.04`) и пользовательские (для self-hosted и Larger Runners).
- **Runner Group (Группа исполнителей)**: Контейнер управления доступом, объединяющий раннеры организации. Позволяет ограничить, какие репозитории могут использовать группу, и назначить её политикой по умолчанию.
- **Ephemeral Runner**: Раннер, deregister'ящийся после первой задачи (`--ephemeral` при регистрации либо эфемерные поды в Actions Runner Controller). Гарантирует чистую среду каждой задаче аналогично GitHub-hosted. Подробнее — в **[Самостоятельные раннеры](./self_hosted_runners.md)** и **[Actions Runner Controller](./actions_runner_controller.md)**.

## Основные концепции

### Различия между типами исполнителей

| Категория | GitHub-hosted | Self-hosted |
| :--- | :--- | :--- |
| **Обслуживание** | Полностью на GitHub | Ответственность пользователя |
| **Окружение** | Стандартные образы (Ubuntu 26.04, macOS 26) | Кастомное |
| **Ресурсы** | Фиксированные (Standard/Larger) | Неограничены (мощность хоста) |
| **Безопасность** | Высокая изоляция | Риски доступа к интранету |
| **Стоимость** | Поминутная тарификация | Бесплатно на уровне платформы (анонсированный сбор $0.002 отложён на неопределённый срок); платится только за собственную инфраструктуру |

Дополнительное различие — модель подключения: приложение раннера само опрашивает сервис GitHub по long-polling, поэтому self-hosted раннеру достаточно исходящих HTTPS-соединений (порт 443), входящие порты не требуются. Устаревшие версии приложения раннера принудительно отключаются сервисом — это часть обслуживания, которую пользователь берёт на себя (архитектура оркестрации описана в [Ключевых концепциях](./Core_Concept.md)).

### Метки и маршрутизация задач

Сопоставление задачи и исполнителя происходит по меткам `runs-on`:

- **Стандартные метки**: `ubuntu-latest`, `windows-latest`, `macos-latest` (указатель на свежий стабильный образ), версии без суффикса (`ubuntu-24.04`, `macos-26`), архитектурные варианты (`ubuntu-24.04-arm`).
- **Self-hosted метки**: при регистрации автоматически назначаются `self-hosted`, имя ОС (`linux`, `macOS`, `windows`) и архитектура (`x64`, `ARM64`); любые кастомные метки (например, `gpu`, `arm-build`) добавляются флагом `--labels`.
- **Семантика нескольких меток**: перечисление через запятую — условие «И»: задача попадёт только на раннер со всем набором меток одновременно. Это способ адресации конкретного пула, но частая ошибка — комбинация `self-hosted, gpu` у раннера без метки `gpu`.
- **Larger Runners**: администратор организации создаёт раннер нужного размера и сам задаёт его метки; задача адресуется этой меткой (см. Сценарий 2).
- Если подходящего раннера нет, задача остаётся в очереди до истечения лимита ожидания (см. «Количественные и временные лимиты»).

### Группы раннеров и политика доступа

- В организации раннеры (в первую очередь self-hosted и Larger) объединяются в группы: Organization Settings → Actions → Runner groups. Для группы настраивается Access — какие репозитории могут её использовать.
- Политика безопасности по умолчанию: публичные репозитории запрещают self-hosted раннеры — любой сторонний автор PR мог бы выполнить произвольный код на вашем железе. Меры харденинга self-hosted парка (изоляция, IMDS, прокси, эфемерность) описаны в [Сетевой безопасности](./network-security.md).
- Larger Runners управляются собственными группами с настройками autoscaling, статических IP и приватной сети (Azure VNet).

### Технические характеристики (спецификации 2026)

**Стандартные исполнители (Standard runners)**:
- **Linux/Windows (публичные репозитории)**: 4 ядра CPU, 16 ГБ RAM, 14 ГБ SSD.
- **Linux/Windows (приватные репозитории)**: 2 ядра CPU, 8 ГБ RAM (половина ресурсов публичных), 14 ГБ SSD.
- **macOS Intel**: 4 ядра CPU, 14 ГБ RAM.
- **macOS Apple Silicon (M-серия)**: 3 ядра CPU, 7 ГБ RAM.
- **Linux ARM64 (`ubuntu-24.04-arm`, `ubuntu-22.04-arm`)**: публичные репозитории — 4 ядра CPU, 16 ГБ RAM; приватные — 2 ядра/8 ГБ (форма как у x64). Дешевле x86: $0.005/мин против $0.006/мин (~17%). Windows arm64 (`windows-11-arm`) скидки не даёт — те же $0.010/мин, что и x64.
- **ubuntu-slim (однокорый контейнерный исполнитель)**: 1 vCPU, 5 ГБ RAM, 14 ГБ SSD; тариф $0.002/мин; жёсткий таймаут задачи — 15 минут; GA с 22 января 2026. Доступен и в публичных, и в приватных репозиториях; запуск в контейнере (hypervisor-level 2 изоляция) без elevated privileges — Docker-in-Docker недоступен. Подходит для лёгкой автоматизации (триаж issues, синхронизация меток, нотификации).

**Высокопроизводительные исполнители (Larger runners)** — доступны организациям на планах Team и Enterprise Cloud:
- Линейка Ubuntu/Windows x64: 2 ядра/8 ГБ/75 ГБ SSD (Linux Advanced), 4 ядра/16 ГБ/150 ГБ SSD, 8/32/300 ГБ, 16/64/600 ГБ, 32/128/1200 ГБ, 64/256/2040 ГБ; максимум линейки — **96 ядер CPU, 384 ГБ RAM, 2040 ГБ SSD** (GA с апреля 2025). Arm64-вариант: до 64 ядер/208 ГБ.
- **GPU-исполнитель**: 4 vCPU, NVIDIA Tesla T4 (16 ГБ VRAM), 28 ГБ RAM, 176 ГБ SSD, Ubuntu или Windows.
- **macOS Larger**: 12 vCPU/30 ГБ (x64 Intel), 5 vCPU/14 ГБ (arm64 M2 Pro).
- Возможность использования **статических IP-адресов** и **приватной сети Azure VNet** (VNet injection) — только для Ubuntu/Windows Larger Runners; для macOS Larger статические IP и приватные сети не поддерживаются.
- **Autoscaling**: пул масштабируется под одновременные задачи; лимит параллелизма Larger-парков — 1000 задач (подробнее ниже).
- Нюанс: Windows-вариант на 4 vCPU работает только с образом Windows Server 2025 или базовым Windows 11 Desktop.

Образы обновляются циклично: поддерживаются максимум две GA-версии ОС одновременно, старейшая выводится через анонс, brownout-периоды и полное отключение (пример: Ubuntu 20.04 выведена 15 апреля 2025; миграция `windows-latest`/`windows-2025` на Visual Studio 2026 прошла 8–15 июня 2026). Полный список предустановленного ПО ведётся в открытом репозитории `actions/runner-images`.

### Тарификация и лимиты (GitHub Free)

Для индивидуальных разработчиков и небольших команд GitHub предоставляет бесплатный план с фиксированными лимитами ресурсов:

- **Минуты выполнения**: 2000 бесплатных минут в месяц для приватных репозиториев (публичные репозитории имеют неограниченные минуты на стандартных раннерах).
- **Хранилище**: 500 МБ для артефактов и пакетов (GitHub Packages).
- **Коэффициенты тарификации (Minutes Multiplier)**:
    Затраченное время умножается на коэффициент в зависимости от типа ОС исполнителя:
    - **Linux**: x1 (базовая стоимость).
    - **Windows**: x2 (в два раза дороже Linux).
    - **macOS**: x10 (в десять раз дороже Linux).
- Механика списания: включённые минуты расходуются с учётом множителя (1 минута работы на macOS списывает 10 минут квоты); каждая задача округляется вверх до целой минуты; минуты не переносятся на следующий месяц.

**Актуальные расценки сверх квоты (с 1 января 2026, приватные репозитории)**:

| Исполнитель | Расценка до 2026 | Действующая (2026) | Изменение |
| :--- | :--- | :--- | :--- |
| Linux 2-core (x64) | $0.008/мин | **$0.006/мин** | −25% |
| Linux 2-core (arm64) | — | **$0.005/мин** | новая позиция |
| Linux 1-core (slim) | — | **$0.002/мин** | новая позиция |
| Windows 2-core | $0.016/мин | **$0.010/мин** | −38% |
| macOS 3/4-core | $0.080/мин | **$0.062/мин** | −23% |
| Linux 64-core (arm64) | $0.160/мин | **$0.098/мин** | −39% (максимум снижения) |
| Linux 4/8/16/32/64-core (x64) | $0.016–0.256 | **$0.012 / 0.022 / 0.042 / 0.082 / 0.162** | −25…−36% |
| GPU Linux 4-core (T4) | — | **$0.052/мин** | — |
| macOS 12-core (x64) | — | **$0.077/мин** | — |

Все приведённые расценки уже включают сбор облачной платформы $0.002/мин отдельной строкой он не выставляется. Хранение артефактов сверх квоты тарифицируется по **$0.25/ГБ в месяц** и делит общий пул с GitHub Packages (расход считается по часовому накоплению в ГБ-часах); отдельный лимит кеша — 10 ГБ на репозиторий, превышение стоит **$0.07/ГБ в месяц**. Пользовательский образ Larger Runner тоже тарифицируется отдельно ($0.07/ГБ в месяц сверх включённой квоты).

**Квоты по планам** (минуты в месяц / хранилище артефактов): Free — 2000 / 500 МБ; Pro — 3000 / 1 ГБ; Team — 3000 / 2 ГБ; Enterprise Cloud — 50 000 / 50 ГБ.

**Контроль расходов**: для организаций настраиваются spending limits (Organization Settings → Billing → Spending limits) — жёсткий потолок сверхквотного потребления; без сохранённого способа оплаты превышение квоты просто блокирует запуск задач вместо выставления счёта.

## GitHub Actions vs Jenkins

Выбор между традиционным Jenkins и нативным GitHub Actions часто определяется требованиями к инфраструктуре и скоростью настройки.

| Критерий | Jenkins | GitHub Actions |
| :--- | :--- | :--- |
| **Инфраструктура** | Требует настройки и поддержки VM (Java, Plugins, Firewall) | Управляемая инфраструктура (SaaS), инфраструктура как код |
| **Масштабируемость** | Ручное управление нодами/агентами | Автоматическое масштабирование и выделение ресурсов |
| **Настройка** | Сложная первоначальная конфигурация (Node.js, Docker, Python) | Декларативные YAML-файлы, готовые экшены из Marketplace |
| **Интеграция** | Через плагины и Webhooks | Нативная, глубокая интеграция с событиями репозитория |
| **Безопасность** | Зависит от администратора (обновление плагинов, ОС) | Изолированные эфемерные раннеры, управление через GitHub |

GitHub Actions минимизирует «когнитивную нагрузку» на DevOps-инженеров, позволяя сфокусироваться на логике пайплайна, а не на обслуживании серверов автоматизации.

Экономический нюанс сравнения: после снижения расценок в январе 2026 точка окупаемости self-hosting сдвинулась вверх — для большинства команд до ~100 000 минут в месяц аренда hosted-минут дешевле совокупной стоимости владения собственным парком (администрирование, патчи безопасности, простой).

Развёрнутое сравнение CI/CD-платформ (GitLab CI, GitHub Actions, CircleCI, Jenkins) с деталями по раннерам, артефактам и миграции — в отдельном материале: [Сравнение CI/CD платформ](../CI-CD/ci_cd_platform_comparison.md).

## Количественные и временные лимиты

1.  **Длительность**:
    - Максимальное время выполнения одной задачи (`job`) — **6 часов** (360 минут) на всех GitHub-hosted раннерах; после этого процесс терминируется автоматически.
    - Для задач на **self-hosted** раннерах лимит выполнения другой — до **5 дней** (7200 минут); это то же значение, что и для задачи, но без 6-часового потолка hosted-среды.
    - Исключение: однокорые контейнерные исполнители (`ubuntu-slim`) — таймаут задачи **15 минут**.
    - Максимальное время ожидания в очереди — **45 минут** для GitHub-hosted (прогон, не обработанный раннером за это время, отбрасывается); для задач, адресованных **self-hosted** раннерам, лимит очереди — **24 часа**.
    - Время жизни воркфлоу целиком — до **35 дней** (включая выполнение, ожидание и approvals).
    - Ожидание approval окружения (environment protection rules) — максимум **30 дней**.
    - Повторный запуск (re-run) одного прогона — до **50 раз** (полных или частичных; порог может быть увеличен через обращение в поддержку).
2.  **Параллелизм (Concurrent Jobs)** — применяется только к GitHub-hosted раннерам; self-hosted ограничены мощностью собственного парка:

    | Тип исполнителя | План | Всего параллельных задач | macOS | GPU |
    | :--- | :--- | :--- | :--- | :--- |
    | Standard | Free | 20 | 5 | — |
    | Standard | Pro | 40 | 5 | — |
    | Standard | Team | 60 | 5 | — |
    | Standard | Enterprise | 500 | 50 | — |
    | Larger runner | Team | 1000 | 5 | 100 |
    | Larger runner | Enterprise | 1000 | 50 | 100 |

    Суб-лимит macOS общий для стандартных и Larger-раннеров: максимум одновременных macOS-задач (5 на Free/Pro/Team, 50 на Enterprise) делится между обоими типами. Лимит можно увеличить через обращение в поддержку.

3.  **Матрицы**: Максимум **256 задач** на одну матрицу (подробнее: [Матричные сборки](./Matrix_Builds.md)).
4.  **Очереди concurrency-групп**: по умолчанию группа держит одну выполняющуюся и одну ожидающую единицу работы; с мая 2026 доступен режим `queue: max` — очередь до **100** ожидающих прогонов (несовместимо с `cancel-in-progress: true` — конфигурация будет отклонена при валидации).

### Лимиты хранилища и артефактов

- **Кеш**: Лимит **10 ГБ** на репозиторий (все планы). При превышении применяется LRU-вытеснение (подробнее: [Кеширование](./Caching.md)).
- **Артефакты**: 
    - Срок хранения по умолчанию: 90 дней (настраивается от 1 до 400 дней).
    - Бесплатный объем (Private): Free (500МБ), Pro (1ГБ), Team (2ГБ), Enterprise (50ГБ).
- **Размер файла воркфлоу**: Максимум **5 МБ**.

### Ограничения GitHub API (Rate Limiting)

При использовании `GITHUB_TOKEN` воркфлоу имеет следующие лимиты на запросы к API:
- **1000 запросов в час** на репозиторий (Standard).
- До **15 000 запросов в час** для аккаунтов Enterprise Cloud.
- Использование персональных токенов (PAT) тарифицируется по лимитам пользователя: **5 000 запросов в час**, неаутентифицированные запросы — **60 запросов в час** на IP-адрес.
- Приложения GitHub App/OAuth, принадлежащие организации Enterprise Cloud, получают лимит **15 000 запросов в час**; для остальных установок лимит растёт от числа пользователей и репозиториков (+50 req/hour за каждый свыше 20), потолок — 12 500.
- Помимо primary-лимитов действуют **secondary rate limits** (защита от злоупотреблений: массовые запросы контента, агрессивное создание объектов) — они не конфигурируются и при нарушении дают HTTP 403/429 с заголовком `Retry-After`.

## Практические сценарии

### Сценарий 1: Оптимизация затрат на Self-hosted раннерах

Для приватных проектов с большим количеством мелких задач (линтинг) выгодно использовать собственные раннеры в Docker-контейнерах: на уровне платформы они бесплатны (анонсированный сбор $0.002/мин отложён на неопределённый срок), тогда как облачная VM стоит $0.006+/мин.

**Предварительные требования**: Docker на хосте; токен регистрации (repository scope) — берётся из Settings → Actions → Runners → New self-hosted runner либо через REST API.

```bash
# получить короткоживущий registration token (живёт 1 час)
curl -s -X POST \
  -H "Authorization: Bearer ${GH_PAT}" \
  https://api.github.com/repos/<owner>/<repo>/actions/runners/registration-token \
# → {"token":"XXXXX","expires_at":"2026-08-24T20:49:00Z"}
```

```yaml
# docker-compose.yml — эфемерный раннер: контейнер живёт ровно одну задачу
services:
  runner:
    image: ghcr.io/actions/actions-runner:latest   # официальный образ раннера
    restart: unless-stopped
    environment:
      CONFIG_URL: https://github.com/<owner>/<repo>
      RUNNER_TOKEN: <registration-token>           # ротировать ежечасно либо скриптом
      LABELS: docker,linux,x64
      EPHEMERAL: "true"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock  # если задачам нужен Docker
```

- Каждый параметр: `EPHEMERAL` эквивалентен флагу `--ephemeral` — раннер deregister'ится после первой задачи, а `restart: unless-stopped` пересоздаёт его с новой регистрацией; `LABELS` задаёт метки для `runs-on`; монтирование docker.sock даёт задачам доступ к Docker хоста (осознанно: это уровень доверия root на хосте).
- **Валидация**: Settings → Actions → Runners показывает раннер в состоянии Idle; запуск тестового воркфлоу с `runs-on: [self-hosted, linux]` выполняется на нём; после задачи раннер исчезает из списка и появляется заново (цикл эфемерности).
- **Очистка**: `docker compose down && docker volume rm <project>_runner-work` удаляет раннер и workspace; при отказе от схемы — снять раннер через Settings → Remove runner.
- Экономика: парк из двух VPS по ~$10/мес окупается примерно от 5 000 минут Linux-нагрузки в месяц (после снижения расценок точка безубыточности выросла — считайте свой объём).

### Сценарий 2: Ресурсоёмкие сборки на Larger Runners

Larger Runners создаются администратором организации и адресуются пользовательской меткой.

**Настройка (однократно)**: Organization Settings → Actions → Runners → New runner → New repository runner: выбрать размер (например, Ubuntu, 32-core/128 ГБ), задать Runner group и **метку** (например, `big-build`); опционально включить Static IP и привязать к VNet.

```yaml
jobs:
  heavy-build:
    # Метка, назначенная Larger Runner'у в настройках организации
    runs-on: big-build
    timeout-minutes: 330            # запас до системного лимита 360 минут
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
      - name: Build project
        run: make -j32              # → параллельная сборка на 32 ядрах, кратно быстрее 8-ядерного этапа
```

- Тариф такого раннера — $0.082/мин (x64 32-core, тарифы 2026); GPU-задачи (T4) адресуются меткой GPU-раннера и стоят $0.052/мин.
- **Валидация**: в логе задачи первая строка раздела Set up job указывает образ и размер машины; биллинг Usage подтверждает списание по тарифу выбранного размера, а не базового Linux.
- Откат: удалить раннер в UI — задачи с его меткой уйдут в очередь; держите fallback-метку стандартного раннера для некритичных задач.

### Сценарий 3: Управление сроком жизни артефактов

```yaml
      - name: Upload Logs
        uses: actions/upload-artifact@v7
        with:
          name: logs
          path: output/
          retention-days: 1 # Минимизация потребления хранилища
```

- Диапазон допустимых значений — от 1 до 400 дней (в публичных репозиториях максимум 90 независимо от настройки).
- **Валидация**: страница прогона → Artifacts показывает дату истечения (`Expires in 1 day`); в Settings → Actions отображаются суммарные занятые мегабайты против квоты плана.
- Мониторинг квоты: `GET /repos/{owner}/{repo}/actions/artifacts` возвращает размер каждого артефакта; регулярная чистка старых артефактов через API предотвращает биллинг $0.25/ГБ в месяц.

### Сценарий 4: Выбор исполнителя и оценка стоимости

Пошаговая процедура выбора среды под задачу:

1. Классифицируйте нагрузку: лёгкая автоматизация (slim), типовой CI (standard), ресурсоёмкая сборка (larger), GPU-вычисления (GPU runner), доступ к интранету или кастомное железо (self-hosted).
2. Оцените месячный объём минут и умножьте на коэффициент ОС и тариф размера.

```bash
# пример расчёта: 10 000 мин Linux + 2 000 мин Windows + 500 мин macOS (Team-план)
echo "scale=2; 10000*0.006 + 2000*0.010 + 500*0.062" | bc
# → 111.00  (USD сверх включённых 3000 минут Team)
```

3. Проверьте, не упирается ли решение в лимиты параллелизма плана: матрица 40 задач на Free-плане физически выполнит 20 параллельно, остальные будут ждать в очереди.
4. Для macOS-нагрузок свыше ~5000 минут/месяц просчитайте self-hosted Mac mini: при $0.062/мин hosted-минуты быстро превосходят амортизацию железа.

- **Валидация решения**: после месяца эксплуатации сверьте фактическое потребление (Organization → Billing → Usage, разбивка по ОС и размерам раннеров) с расчётом; расхождение более 20% — повод пересмотреть выбор размеров.

## Устранение неполадок

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Задача висит в `Waiting for a runner to be online` | Self-hosted раннер выключен, сервис не поднят или версия приложения раннера устарела и отключена сервисом | Проверить состояние сервиса раннера на хосте (`systemctl status actions.runner.*`), обновить приложение до актуальной версии, сверить метки `runs-on` |
| Задача отменяется вскоре после постановки в очередь | Истёк лимит ожидания (45 минут для hosted, 24 часа для self-hosted) | Освободить параллелизм плана, добавить capacity (Larger/self-hosted) или снизить fan-out матрицы |
| `The job running on runner X has exceeded the maximum execution time` | Достигнут 6-часовой лимит задачи | Разбить задачу, ускорить шаги (кеш, параллелизм) или явно задать `timeout-minutes` с запасом; для лёгких задач проверить, не попали ли они на `ubuntu-slim` (лимит 15 мин) |
| Задача на self-hosted идёт дольше 6 часов и не падает | Для self-hosted лимит задачи — **5 дней**, а не 6 часов (6-часовой потолок действует только на hosted) | Проверить залипший шаг; даже при большом лимите ставьте `timeout-minutes`; при необходимости отменить прогон вручную |
| macOS Larger не получает статический IP или VNet | Статические IP и приватная сеть поддерживаются только для Ubuntu/Windows Larger Runners | Использовать Ubuntu/Windows Larger Runner либо self-hosted macOS за прокси/шлюзом |
| `API rate limit exceeded` / HTTP 403 c `Retry-After` | Primary или secondary лимиты API | Кешировать ответы, использовать conditional requests (`ETag`/`If-None-Match`), пагинацию с большим `per_page`; для Enterprise-масштаба — GitHub App вместо PAT |
| На Free/Team-плане задачи идут медленно волнами | Исчерпан лимит параллелизма плана (20/40/60) или суб-лимит macOS (5) | Апгрейд плана, перенос части задач на self-hosted/Larger, сокращение одновременных матриц через `max-parallel` |
| Диск переполняется на self-hosted между запусками | Stateful-режим накапливает workspace, образы, логи | Перевести раннер в ephemeral-режим, добавить очистку (`docker system prune`, удаление `_work`) в post-фазу или cron |
| Раннер пропал после ребута хоста | Регистрировался интерактивно без установки службы | Переустановить как службу: `svc.sh install && svc.sh start` (Linux/macOS) либо служба Windows |
| Счёт вырос неожиданно | Множитель macOS x10 / Windows x2, округление каждой задачи вверх до минуты, матрица умножила дорогие задачи | Проверить Usage-разбивку по ОС; консолидировать микрозадачи; вынести тяжёлые шаги на Linux; настроить spending limit |
| Матрица падает целиком при запуске | Сгенерировано более 256 задач | Уменьшить матрицу, применить `include/exclude`, разнести по нескольким воркфлоу или reusable workflows |
| `storage quota exceeded` при загрузке артефактов | Исчерпана квота хранилища плана | Снизить `retention-days`, чистить старые артефакты через API, докупить пакет хранения |

## Лучшие практики

1. **Наименьший достаточный раннер**: подбирайте тип под нагрузку — `ubuntu-slim` для коротких автоматизаций, standard для типового CI, Larger только для ресурсоёмких сборок. Larger Runners платные всегда, даже в публичных репозиториях, поэтому переход на них должен быть обоснован сокращением времени.
2. **Пин версии ОС вместо `-latest`**: в продакшен-пайплайнах указывайте `ubuntu-24.04`/`windows-2025` вместо `-latest`, особенно в окно миграции образов — иначе сборка молча сменит ОС посреди цикла.
3. **Self-hosted — только эфемерными и за группы**: держите раннеры эфемерными (`--ephemeral`), объединяйте в runner groups с ограниченным Access и не открывайте публичным репозиториям (см. Сценарий 1).
4. **Обновляйте приложение self-hosted раннера**: устаревшие версии принудительно отключаются сервисом и перестают получать задачи — это регулярная задача обслуживания, а не разовая настройка.
5. **Учитывайте множители и округление**: macOS (×10) и Windows (×2) дороже Linux, каждая задача округляется вверх до минуты, минуты не переносятся — консолидируйте микрозадачи и выносите тяжёлые шаги на Linux.
6. **Контроль расходов**: настраивайте spending limits (Organization → Billing) и сверяйте фактический Usage с расчётом; для macOS держите собственный порог перехода на self-hosted (см. Сценарий 4).
7. **Дисциплина хранилища**: задавайте короткий `retention-days` для артефактов — хранилище общий пул с GitHub Packages, а кеш имеет отдельный лимит 10 ГБ; чистите старое через API (см. Сценарий 3).
8. **Осознанный выбор hosted vs self-hosted**: self-hosting окупается только при стабильном большом объёме минут и наличии инфраструктурной экспертизы; после снижения цен 2026 точка безубыточности для большинства команд сместилась вверх.
