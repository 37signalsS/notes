# GitHub Actions: Оптимизация воркфлоу

Оптимизация воркфлоу в GitHub Actions направлена на сокращение времени выполнения (TTR — Time To Result), экономию вычислительных ресурсов и повышение надежности процессов CI/CD. Эффективная оптимизация не только ускоряет цикл обратной связи, но и напрямую снижает затраты на инфраструктуру.

## Определения

- **Оптимизация воркфлоу**: Совокупность инженерных техник, направленных на минимизацию времени выполнения пайплайна и потребления ресурсов (CPU, RAM, дисковое пространство, лимиты минут).
- **Критический путь пайплайна**: Самая длинная последовательность зависимых задач, определяющая общее время выполнения процесса от триггера до завершения.
- **Инвалидация кеша (Cache Invalidation)**: Механизм принудительного обновления сохраненных данных при изменении конфигурационных файлов (например, `package-lock.json`).
- **TTR (Time To Result)**: Метрика, измеряющая время от момента инициирования события (push) до получения результата выполнения воркфлоу.

## Основные концепции

### 1. Стратегии кеширования данных

Кеширование — ключевой инструмент оптимизации, исключающий повторение ресурсоемких операций скачивания и компиляции.

- **Зависимости менеджеров пакетов**: Использование встроенных механизмов в `setup-*` экшенах (`actions/setup-node`, `actions/setup-python` и др.) является предпочтительным, так как они автоматически определяют правильные пути кеширования и ключи на основе файлов зависимостей.
- **Docker Layer Caching (gha)**: В современных пайплайнах (2025–2026) использование бэкенда `gha` в экшене `docker/build-push-action` позволяет сохранять слои образов непосредственно в хранилище GitHub Actions, что значительно быстрее, чем использование внешних реестров.
  ```yaml
  cache-from: type=gha
  cache-to: type=gha,mode=max
  ```
- ** CCache и инкрементальная сборка**: Для языков типа C++/Rust использование кеша компилятора позволяет пересобирать только измененные единицы трансляции.

Подробное описание: **[Кеширование зависимостей](./Caching.md)**.

### 2. Параллелизм через стратегию матрицы (Matrix Strategy)

Матрица позволяет запускать одну и ту же задачу с разными параметрами одновременно, эффективно утилизируя пул доступных исполнителей.

- **Директива `fail-fast`**:
  - По умолчанию (`true`): GitHub Actions останавливает все задачи матрицы, если одна из них завершилась ошибкой. Это критично для экономии ресурсов, если успех всего набора обязателен.
  - При значении `false`: Все задачи будут выполнены до конца. Это необходимо для полного кросс-платформенного тестирования, чтобы увидеть все проблемные окружения за один запуск.
- **Max-parallel**: Ограничение количества одновременно запущенных задач в матрице для предотвращения исчерпания лимитов API или ресурсов сторонних сервисов.

Детальное описание: **[Матричные сборки](./Matrix_Builds.md)**.

### 3. Ограничение времени выполнения (Timeout) и лимиты

GitHub Actions накладывает стандартные ограничения, которые необходимо учитывать для стабильности:

- **Лимиты по умолчанию**: Задачи могут выполняться до **6 часов** (360 минут) на GitHub-hosted раннерах. В воркфлоу с самообслуживаемыми раннерами (self-hosted) лимиты могут быть иными, но GitHub также применяет общие ограничения на время жизни токена.
- **Директива `timeout-minutes`**: Позволяет задать более жесткие рамки (например, 15–30 минут). Это предотвращает бесполезную трату минут при зависании тестов или бесконечных циклах в скриптах.
  ```yaml
  jobs:
    test:
      runs-on: ubuntu-latest
      timeout-minutes: 20
  ```

### 4. Выбор и масштабирование исполнителей (Runners)

- **Standard vs Larger Runners**: Стандартные раннеры (2 CPU, 7 GB RAM) подходят для большинства задач. Для сборки тяжелых проектов (например, Java/Android или C++) переход на **Larger Runners** (4–64 CPU) может сократить время компиляции в разы за счет распараллеливания сборки на уровне ОС.
- **Actions Runner Controller (ARC)**: Развертывание раннеров в Kubernetes позволяет использовать «эфемерные» контейнеры, которые масштабируются под нагрузку. Это устраняет очереди на выполнение задач в периоды высокой активности.

Детальное описание: **[Среды выполнения и ограничения](./Environment_Limitations.md)**.

### 5. Контроль одновременных запусков (Concurrency)

Директива `concurrency` критически важна для предотвращения гонок данных (race conditions) при деплое и экономии ресурсов при частых коммитах.

- **Группировка**: Группа создается на основе выражения. Если новый воркфлоу запускается в той же группе, предыдущий может быть отменен.
- **Cancel-in-progress**: Автоматическая отмена устаревших задач в Pull Request при поступлении нового кода.
  ```yaml
  concurrency:
    group: ${{ github.workflow }}-${{ github.ref }}
    cancel-in-progress: true
  ```

### 6. Фильтрация событий и монорепозитории

Оптимизация триггеров позволяет не запускать дорогостоящие проверки, если изменения их не затрагивают.

- **Paths и Paths-ignore**: Обязательная практика для монорепозиториев. Позволяет запускать тесты только для измененного сервиса.
  ```yaml
  on:
    push:
      paths:
        - 'services/api/**'
        - 'shared-lib/**'
  ```
- **Sparse Checkout**: В экшене `actions/checkout` использование `sparse-checkout` позволяет скачивать только необходимые файлы, что значительно ускоряет стадию инициализации в гигантских репозиториях.

### 7. Управление артефактами и хранилищем

Хранение артефактов (билды, логи) потребляет дисковое пространство и может замедлять пайплайн при передаче больших объемов данных.

- **Retention Period**: Срок хранения по умолчанию — 90 дней. Для CI-артефактов рекомендуется устанавливать минимальный срок (например, `retention-days: 1`), чтобы не платить за лишнее хранение.
- **Compression**: Использование параметра `compression-level: 0` (отключение сжатия) в экшене `actions/upload-artifact` может ускорить загрузку, если пропускная способность сети высока, а CPU на раннере ограничен.

### 8. Оптимизация слоев Docker и BuildKit

Правильное написание Dockerfile — основа быстрой сборки в CI.

- **Многоэтапная сборка (Multi-stage)**: Разделение этапа сборки (со всеми инструментами) и финального образа (только артефакты).
- **Порядок инструкций**: Размещение редко меняющихся инструкций (`COPY package.json`, `RUN npm install`) перед часто меняющимся исходным кодом.

Подробнее: **[Оптимизация сборки Docker-образов](../Docker/Dockerfile/Docker_best_practices/build_optimization.md)**.

## Практические сценарии

### Сценарий 1: Продвинутая оптимизация для монорепозитория

Пример пайплайна, который минимизирует время выполнения за счет фильтрации и параллелизма:

```yaml
name: Optimized Monorepo CI

on:
  push:
    branches: [ main ]
    paths: [ 'apps/frontend/**', 'libs/common/**' ]
  pull_request:
    paths: [ 'apps/frontend/**', 'libs/common/**' ]

concurrency:
  group: frontend-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - name: Checkout with Sparse
        uses: actions/checkout@v7
        with:
          sparse-checkout: |
            apps/frontend
            libs/common
      
      - name: Setup Node
        uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: 'npm'
          cache-dependency-path: 'apps/frontend/package-lock.json'

      - name: Build
        run: |
          cd apps/frontend
          npm ci
          npm run build -- --parallel
      
      - name: Upload Artifact
        uses: actions/upload-artifact@v4
        with:
          name: frontend-dist
          path: apps/frontend/dist/
          retention-days: 5 # Оптимизация срока хранения
```

### Сценарий 2: Оптимизация Docker-сборки с gha-кешем

```yaml
jobs:
  docker-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3
      
      - name: Build and Push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: false
          tags: my-app:latest
          cache-from: type=gha # Использование кеша GitHub Actions
          cache-to: type=gha,mode=max # Сохранение всех слоев для будущего использования
```
