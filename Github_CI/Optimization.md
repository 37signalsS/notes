# GitHub Actions: Оптимизация воркфлоу

**Актуально для:** GitHub Actions, октябрь 2026 (тарифы hosted-раннеров после снижения цен 1 января 2026; параллельные шаги — с июня 2026; `queue: max` в concurrency-группах — с мая 2026)

Оптимизация воркфлоу в GitHub Actions направлена на сокращение времени выполнения (TTR — Time To Result), экономию вычислительных ресурсов и повышение надежности процессов CI/CD. Эффективная оптимизация не только ускоряет цикл обратной связи, но и напрямую снижает затраты на инфраструктуру. Для приватных репозиториев это особенно заметно после изменения тарификации 1 января 2026 года: цены на hosted-раннеры снизились до 39% в зависимости от типа машины, а в перечисленные ставки включена платформенная надбавка ($0.002/мин). Отдельная плата за использование self-hosted-раннеров анонсирована, но введена не была — GitHub отложил её после отзывов сообщества; на сегодня self-hosted-раннеры не тарифицируются помимо лимитов плана (см. раздел о раннерах).

## Определения

- **Оптимизация воркфлоу**: Совокупность инженерных техник, направленных на минимизацию времени выполнения пайплайна и потребления ресурсов (CPU, RAM, дисковое пространство, лимиты минут).
- **Критический путь пайплайна**: Самая длинная последовательность зависимых задач, определяющая общее время выполнения процесса от триггера до завершения.
- **Инвалидация кеша (Cache Invalidation)**: Механизм принудительного обновления сохраненных данных при изменении конфигурационных файлов (например, `package-lock.json`).
- **TTR (Time To Result)**: Метрика, измеряющая время от момента инициирования события (push) до получения результата выполнения воркфлоу.
- **Холодный запуск (Cold Start)**: Начальная фаза задачи до выполнения полезной работы: постановка в очередь, выделение виртуальной машины, инициализация приложения раннера, скачивание репозитория и контейнеров/экшенов. Типично занимает от десятков секунд до нескольких минут и является первым кандидатом на сокращение.
- **Шардирование тестов (Test Sharding)**: Разбиение набора тестов на N независимых частей, выполняемых параллельно на разных раннерах, что сокращает время самой длинной тестовой задачи примерно в N раз (минус накладные расходы).
- **Очередь слияний (Merge Queue)**: Механизм GitHub, группирующий Pull Request в очереди и прогоняющий CI на временном коммите слияния до фактического мержа в основную ветку; гарантирует, что каждый коммит в `main` прошел проверки совместно со всеми предшествующими принятыми изменениями.

## Основные концепции

### 1. Стратегии кеширования данных

Кеширование — ключевой инструмент оптимизации, исключающий повторение ресурсоемких операций скачивания и компиляции.

- **Зависимости менеджеров пакетов**: Использование встроенных механизмов в `setup-*` экшенах (`actions/setup-node`, `actions/setup-python` и др.) является предпочтительным, так как они автоматически определяют правильные пути кеширования и ключи на основе файлов зависимостей.
- **Docker Layer Caching (gha)**: В современных пайплайнах (2025–2026) использование бэкенда `gha` в экшене `docker/build-push-action` позволяет сохранять слои образов непосредственно в хранилище GitHub Actions, что значительно быстрее, чем использование внешних реестров.
  ```yaml
  cache-from: type=gha
  cache-to: type=gha,mode=max
  ```
  Важно: кэш Buildx с бэкендом `gha` делит квоту кеша репозитория (по умолчанию 10 ГБ) с обычным кешем `actions/cache`; вытеснение старых записей идет по принципу LRU. Для активной кросс-веточной работы рассмотрите бэкенд `type=registry` (слои хранятся в реестре образов без этой квоты, но требуют push-прав и медленнее при первом скачивании).
- **CCache и инкрементальная сборка**: Для языков типа C++/Rust использование кеша компилятора позволяет пересобирать только измененные единицы трансляции.

Нюанс безопасности (с июня 2026 года): для недоверенных триггеров (PR из форков) кеш Actions работает в режиме read-only — форк не может ни прочитать кеш базовой ветки с подмененным ключом, ни загрязнить его своими записями. Это влияет на стратегии кеширования open-source проектов: первый прогон в форке всегда будет Cache Miss.

Подробное описание: **[Кеширование зависимостей](./Caching.md)**.

### 2. Параллелизм: матрица задач и параллельные шаги

Матрица позволяет запускать одну и ту же задачу с разными параметрами одновременно, эффективно утилизируя пул доступных исполнителей.

- **Директива `fail-fast`**:
  - По умолчанию (`true`): GitHub Actions останавливает все задачи матрицы, если одна из них завершилась ошибкой. Это критично для экономии ресурсов, если успех всего набора обязателен.
  - При значении `false`: Все задачи будут выполнены до конца. Это необходимо для полного кросс-платформенного тестирования, чтобы увидеть все проблемные окружения за один запуск.
- **Max-parallel**: Ограничение количества одновременно запущенных задач в матрице для предотвращения исчерпания лимитов API или ресурсов сторонних сервисов. Матрица генерирует максимум 256 задач на один запуск воркфлоу (hard-лимит GitHub Actions); задачи стартуют в пределах лимитов конкурентности вашего плана.
- **Параллелизм шагов внутри одной задачи (июнь 2026)**: Ранее последовательность шагов была жесткой; теперь нативно поддерживается конкурентное выполнение шагов ключевыми словами `background: true` (асинхронный запуск), `wait`/`wait-all` (барьеры синхронизации), `cancel` (остановка ненужного фонового шага) и `parallel` (группа конкурентных шагов с ожиданием). Это позволяет сократить критический путь внутри задачи, не плодя отдельные задачи и передачу данных артефактами. Полный разбор и примеры — в разделе практических сценариев ниже и в сценарии 4 файла «Ключевые концепции».

Детальное описание матриц: **[Матричные сборки](./Matrix_Builds.md)**.

### 3. Ограничение времени выполнения (Timeout) и лимиты

GitHub Actions накладывает стандартные ограничения, которые необходимо учитывать для стабильности:

- **Лимиты по умолчанию**: Задачи могут выполняться до **6 часов** (360 минут) на GitHub-hosted раннерах. После этого GitHub автоматически терминирует процесс. Полный свод лимитов (очередь, время жизни запуска, конкурентность по планам) — в разделе о средах выполнения.
- **Директива `timeout-minutes`**: Позволяет задать жесткие рамки на уровне задачи (`job`) или конкретного шага (`step`). Это критично для предотвращения бесполезной траты бесплатных минут при зависании сетевых запросов, бесконечных циклах в тестах или утечках памяти.
  ```yaml
  jobs:
    test:
      runs-on: ubuntu-latest
      timeout-minutes: 15 # Задача упадет через 15 минут, если не завершится
      steps:
        - run: ./run-e2e.sh
          timeout-minutes: 5 # Конкретный шаг ограничен 5 минутами
  ```
- **Взаимодействие с отменами**: При отмене задачи через `cancel-in-progress` шаги получают сигнал отмены, однако уже запущенные процессы могут быть завершены принудительно. Поэтому необратимые операции (публикация релиза, деплой) не следует размещать в задачах, допускающих отмену; для них используйте отдельный воркфлоу с `cancel-in-progress: false`.

### 4. Выбор и масштабирование исполнителей (Runners)

Выбор раннера — самый прямой рычаг влияния на время сборки и стоимость минуты:

- **Standard vs Larger Runners**: Спецификация стандартного раннера зависит от видимости репозитория: **публичные** репозитории получают Linux/Windows машины на 4 vCPU / 16 ГБ RAM бесплатно и без ограничений, **приватные** — 2 vCPU / 8 ГБ RAM с списанием минут (историческое значение 7 ГБ устарело). Для сборки тяжелых проектов (Java/Android, C++, Rust) переход на **Larger Runners** дает кратное ускорение за счет распараллеливания сборки на уровне ОС: доступны конфигурации x64 до 96 vCPU / 384 ГБ RAM и arm64 до 64 vCPU / 208 ГБ RAM, включая GPU-конфигурации (NVIDIA Tesla T4, 4 vCPU / 28 ГБ RAM / 16 ГБ VRAM) для GPU-интенсивных нагрузок. Larger Runners поддерживают автоскейлинг, статические IP и группы раннеров.
- **Экономия через архитектуру arm64**: Нативные arm64-раннеры (`ubuntu-24.04-arm`, `windows-11-arm`) доступны во всех репозиториях (в приватных — с 29 января 2026, 2 vCPU). Тариф для Linux arm64 примерно на 17% ниже x64, а сборка arm64-образов без эмуляции QEMU проходит в разы быстрее.
- **Легковесные задачи — `ubuntu-slim`**: Одноядерный контейнерный раннер (1 vCPU / 5 ГБ RAM / 14 ГБ SSD, GA с 22 января 2026) для коротких автоматизаций (линтеры, генерация отчетов, работа с issues) — дешевле полноценной VM ($0.002/мин против $0.006/мин) и быстрее стартует. Жесткий лимит: задача на этом раннере должна уложиться в **15 минут**, иначе принудительно терминируется. Контейнер работает в непривилегированном режиме: DinD, монтирование файловых систем и низкоуровневые возможности ядра недоступны. Не подходит для классических сборок.
- **Ориентировочные тарифы (после снижения цен 1 января 2026)**: Linux x64 — около $0.006/мин, Linux arm64 — около $0.005/мин, Windows — около $0.010/мин, macOS — около $0.062/мин (десятикратная премия). Перенос работы с macOS на Linux там, где это возможно, — крупнейший резерв экономии.
- **Actions Runner Controller (ARC)**: Развертывание раннеров в Kubernetes позволяет использовать «эфемерные» контейнеры, которые масштабируются под нагрузку. Это устраняет очереди на выполнение задач в периоды высокой активности. Подробнее — в **[Actions Runner Controller](./actions_runner_controller.md)**.

Детальное описание: **[Среды выполнения и ограничения](./Environment_Limitations.md)**.

### 5. Контроль одновременных запусков (Concurrency)

Директива `concurrency` критически важна для предотвращения гонок данных (race conditions) при деплое и экономии ресурсов при частых коммитах. Она гарантирует, что в один момент времени выполняется только одна задача или воркфлоу из определенной группы.

- **Группировка**: Группа создается на основе выражения (например, имени воркфлоу и ветки). Имя группы регистронезависимо.
- **Cancel-in-progress**:
  - **`true`**: При запуске нового воркфлоу в той же группе GitHub автоматически отменяет любые уже выполняющиеся воркфлоу этой группы. Это стандарт для CI в Pull Request.
  - **`false`**: Новые запуски встают в очередь (Pending) и ждут завершения текущего. Это необходимо для задач деплоя, которые нельзя прерывать на середине.
  ```yaml
  concurrency:
    group: production-deploy-${{ github.ref }}
    cancel-in-progress: false # Очередь вместо отмены для безопасности деплоя
  ```
- **Критический нюанс — «один ожидающий»**: По умолчанию (`queue: single`) в группе может находиться не более одного ожидающего (pending) запуска. Новый запущенный в очередь запуск **отменяет предыдущий ожидающий** (выполняющийся при этом не трогается). То есть `cancel-in-progress: false` означает «не отменять выполняющийся», а не «выстроить всех в очередь». Для деплоя это обычно желаемое поведение (промежуточные состояния не нужны — деплоится последний), но если требуется настоящая очередь, используйте свойство `queue` (с мая 2026):
  ```yaml
  concurrency:
    group: release-train-${{ github.ref }}
    cancel-in-progress: false
    queue: max   # До 100 ожидающих запусков вместо одного
  ```
  Комбинация `queue: max` с `cancel-in-progress: true` запрещена и вызывает ошибку валидации воркфлоу. При переполнении очереди (более 100 ожидающих) дополнительные запуски отменяются.
- **Условная отмена**: Значение `cancel-in-progress` может быть выражением, чтобы отменять запуски только на части веток:
  ```yaml
  concurrency:
    group: ci-${{ github.workflow }}-${{ github.ref }}
    cancel-in-progress: ${{ !contains(github.ref, 'release/') }}
  ```
- **Изоляция групп по воркфлоу**: Включайте `github.workflow` в ключ группы, иначе разные воркфлоу, случайно получившие одинаковый ключ, начнут отменять друг друга.

### 6. Фильтрация событий и монорепозитории

Оптимизация триггеров позволяет не запускать дорогостоящие проверки, если изменения их не затрагивают.

- **Paths и Paths-ignore**: Обязательная практика для монорепозиториев. Позволяет запускать тесты только для измененного сервиса.
  ```yaml
  on:
    push:
      paths:
        - 'services/api/**'
        - 'shared-lib/**'
  ```
- **Подводный камень required checks**: Если проверка обязательна (Required Status Check), а воркфлоу был полностью отфильтрован по путям, статус не появится и мерж заблокируется. Стандартное решение — отдельный «заглушечный» джоб с условием пропуска (`if: steps.filter.outputs.api == 'true'`) внутри всегда запускаемого воркфлоу, либо паттерн с `dorny/paths-filter` в первом джобе и последующими условными джобами.
- **Sparse Checkout**: В экшене `actions/checkout` использование `sparse-checkout` позволяет скачивать только необходимые файлы, что значительно ускоряет стадию инициализации в гигантских репозиториях.
- **Пропуск по сообщению коммита**: Ключевые слова `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]`, `[actions skip]` в заголовке или описании последнего коммита полностью отменяют запуск воркфлоу — полезно для рутинных коммитов документации. Альтернатива — trailer `skip-checks: true` в конце сообщения коммита (после двух пустых строк). Работает только для событий `push` и `pull_request`.

### 7. Управление артефактами и хранилищем

Хранение артефактов (билды, логи) потребляет дисковое пространство и может замедлять пайплайн при передаче больших объемов данных.

- **Retention Period**: Срок хранения по умолчанию — 90 дней. Для CI-артефактов рекомендуется устанавливать минимальный срок (например, `retention-days: 1`), чтобы не платить за лишнее хранение.
- **Compression**: Использование параметра `compression-level: 0` (отключение сжатия) в экшене `actions/upload-artifact` может ускорить загрузку, если пропускная способность сети высока, а CPU на раннере ограничен. Диапазон значений — от 0 (без сжатия, быстрее всего) до 9 (максимальное сжатие); для уже сжатых форматов (.jar, .zip, .png) сжатие бессмысленно.
- **Неизменяемость артефактов (с версии v4)**: Артефакты неизменяемы после загрузки, а имена должны быть уникальны в рамках задачи. В матрицах добавляйте суффикс: `name: dist-${{ matrix.os }}`. Для объединения частей существует суб-экшен `actions/upload-artifact/merge`.
- **Неупакованные артефакты (февраль 2026)**: Параметр `archive: false` в `upload-artifact@v7` отключает авто-упаковку в zip — файл можно открыть прямо из браузера и исчезает проблема «zip в zip». Ограничения: загружается **ровно один файл** (glob, резолвящийся в несколько файлов, падает ошибкой), параметр `name` при этом **игнорируется** — именем артефакта становится имя файла; для скачивания таких артефактов экшеном нужен `download-artifact@v8`, а `gh run download` пока не поддерживает unzipped-артефакты.

### 8. Оптимизация слоев Docker и BuildKit

Правильное написание Dockerfile — основа быстрой сборки в CI.

- **Многоэтапная сборка (Multi-stage)**: Разделение этапа сборки (со всеми инструментами) и финального образа (только артефакты).
- **Порядок инструкций**: Размещение редко меняющихся инструкций (`COPY package.json`, `RUN npm install`) перед часто меняющимся исходным кодом.
- **Актуальные версии экшенов (2026)**: связка `docker/setup-buildx-action@v4` + `docker/build-push-action@v7` (релиз 5 марта 2026, Node.js 24 runtime, требуются раннеры не старше 2.327.1 — актуально для self-hosted).

Подробнее: **[Оптимизация сборки Docker-образов](../Docker/Dockerfile/Docker_best_practices/build_optimization.md)**.

## Практические сценарии

### Сценарий 1: Продвинутая оптимизация для монорепозитория

Пример пайплайна, который минимизирует время выполнения за счет фильтрации и параллелизма:

```yaml
name: Optimized Monorepo CI

on:
  push:
    branches: [ main ]
    paths: [ 'apps/frontend/**', 'libs/common/**' ]
  pull_request:
    paths: [ 'apps/frontend/**', 'libs/common/**' ]

concurrency:
  group: frontend-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - name: Checkout with Sparse
        uses: actions/checkout@v7
        with:
          sparse-checkout: |
            apps/frontend
            libs/common
      
      - name: Setup Node
        uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: 'npm'
          cache-dependency-path: 'apps/frontend/package-lock.json'

      - name: Build
        run: |
          cd apps/frontend
          npm ci
          npm run build -- --parallel
      
      - name: Upload Artifact
        uses: actions/upload-artifact@v7
        with:
          name: frontend-dist
          path: apps/frontend/dist/
          retention-days: 5 # Оптимизация срока хранения
```

Разбор оптимизаций сверху вниз: двойная фильтрация `paths` отсекает нерелевантные запуски целиком (экономия минут); `concurrency` с отменой убирает накопление устаревших прогонов при серии пушей в одну ветку; sparse-checkout сокращает время клонирования; `cache-dependency-path` привязывает ключ npm-кеша к lock-файлу конкретного приложения (иначе в монорепо ключ будет общим и невалидным для каждого сервиса); таймаут страхует от зависаний; короткий retention уменьшает расходы на хранение.

Валидация: в UI запуска вкладка Usage показывает суммарное время и количество минут; при пушах подряд в одну ветку предыдущие прогоны помечаются значком отмены (Cancelled).

### Сценарий 2: Оптимизация Docker-сборки с gha-кешем

```yaml
jobs:
  docker-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v4
      
      - name: Build and Push
        uses: docker/build-push-action@v7
        with:
          context: .
          push: false
          tags: my-app:latest
          cache-from: type=gha # Использование кеша GitHub Actions
          cache-to: type=gha,mode=max # Сохранение всех слоев для будущего использования
```

Смысл `mode=max`: экспортировать в кеш не только финальные слои образа (режим `min` по умолчанию), а все промежуточные слои многоэтапной сборки — это резко повышает долю попаданий для Dockerfile, где этапы расходятся рано. Первый запуск даст Cache Miss и соберет с нуля; второй должен показать строки `CACHED` у большинства инструкций RUN/COPY в логах BuildKit. Для команд с несколькими активными ветками оцените `type=registry` с общим префиксом кеша — квота `gha` перестает быть узким местом.

### Сценарий 3: Диагностика узких мест TTR

Прежде чем оптимизировать — измерьте. Последовательность действий (нужен установленный `gh` CLI):

```bash
# 1. Найти целевой прогон и его длительность
gh run list --branch main --limit 5
# → completed  success  Deploy  main  push  987654321  14m22s  about 1 hour ago

# 2. Разбивка по задачам (какая задача тянет критический путь)
gh run view 987654321 --json jobs \
  --jq '.jobs[] | "\(.name)\t\(.startedAt) -> \(.completedAt)\t\(.conclusion)"'
# → build    2026-08-24T09:00:01Z -> 2026-08-24T09:03:40Z    success
# → test     2026-08-24T09:00:01Z -> 2026-08-24T09:13:59Z    success
# → deploy   2026-08-24T09:14:02Z -> 2026-08-24T09:14:22Z    success
# Вывод: test занимает 10 из 14 минут — цель для шардирования (см. Сценарий 4)

# 3. Хронометраж шагов самой долгой задачи
gh run view 987654321 --log-failed            # если есть падения
gh run view 987654321 --job <JOB_ID> --log | grep -iE '^(##\[group\]|##\[endgroup\])'
# → ##[group]Run npm ci
# → ##[endgroup]
# Интервалы между group/endgroup в timestamp'ах лога дают время каждого шага;
# наглядная альтернатива — гистограммы шагов во вкладке Summary прогона в UI

# 4. Отладочный прогон с подробными логами
gh secret set ACTIONS_STEP_DEBUG --body true   # временно, на репозиторий
gh run watch                                    # живое наблюдение за прогоном
gh secret delete ACTIONS_STEP_DEBUG             # обязательно убрать после диагностики
```

Предусловия: `gh auth login` выполнен; для шага 3 известен JOB_ID (берется из вывода шага 2 либо `gh run view`). Типичные находки такой диагностики: холодный старт (checkout+setup занимают больше минуты), отсутствие кеша у одного из менеджеров пакетов, последовательные шаги, которые могли бы идти параллельно.

### Сценарий 4: Шардирование медленного набора тестов

Тестовый набор, идущий 20 минут одним куском, разбивается на 4 шарда по номеру:

```yaml
jobs:
  test:
    strategy:
      fail-fast: false           # Увидеть результаты всех шардов за один прогон
      matrix:
        shard: [1, 2, 3, 4]
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: 'npm'
      - run: npm ci
      - name: Run test shard
        env:
          SHARD_INDEX: ${{ matrix.shard }}
          SHARD_COUNT: 4
        run: npm test -- --shard=${{ matrix.shard }}/${{ matrix.shard_count }}
```

Нативную поддержку шардов имеют Jest и Vitest (флаг `--shard=i/n`); для других раннеров тестов шардирование реализуется разделением списка тест-кейсов скриптом по индексу. Имена артефактов с отчетами обязаны включать индекс шарда (`reports-shard-${{ matrix.shard }}`) из-за неизменяемости артефактов. Валидация: четыре задачи завершаются параллельно, каждая — примерно за четверть прежнего времени; сводный отчет собирается суб-экшеном `actions/upload-artifact/merge`. Балансируйте шардирование: если один шард стабильно зеленеет раньше других, перераспределите тесты или увеличьте число шардов.

### Сценарий 5: Параллельные шаги для сокращения критического пути

Независимые статические проверки внутри одной задачи (июнь 2026):

```yaml
jobs:
  quality:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: 'npm'
      - run: npm ci

      - name: Lint                 # Запускается в фоне
        background: true
        run: npm run lint

      - name: Typecheck            # Стартует сразу, не дожидаясь линта
        background: true
        run: npm run typecheck

      - name: Unit tests           # Тесты идут, пока работают обе проверки
        wait-all:
        run: npm test
```

Когда применять: проверки используют общий кеш зависимостей и логически связаны (один статус качества), но вычислительно независимы — тогда параллель шагов выигрывает у матрицы задач за счет отсутствия повторных checkout/npm ci. Если же проверки концептуально независимы и каждая тяжелая — оставляйте отдельные задачи: они параллельны по умолчанию и изолированы по ресурсам. Каждый фоновый шаг получает собственный блок логов в UI, поэтому вывод не перемешивается (главное отличие от shell-backgrounding через `&`).

### Сценарий 6: Merge Queue для загруженной основной ветки

Когда в `main` сливается много PR, каждый мерж ломает проверки следующего («main зеленый у каждого автора по отдельности, но сломан в совокупности»). Очередь слияний решает это прогоном CI на временном групповом коммите:

```yaml
name: CI

on:
  pull_request:
  merge_group:                    # Прогон для группового коммита очереди

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: 'npm'
      - run: npm ci && npm test
```

Настройка: Settings → Branches → правило защиты ветки `main` → включить Require merge queue (доступно для публичных репозиториев и приватных на платных планах). Дополнительно настраиваются размер группировки и таймаут очереди. Логика работы: PR попадает в очередь; GitHub собирает групповой коммит из очереди и головы PR; воркфлоу запускается дважды — сначала по `pull_request` (быстрая проверка самого PR), затем по `merge_group` (валидация комбинации). Валидация: в списке прогонов появляются запуски с меткой merge_group, а история коммитов `main` содержит только проверенные групповые состояния. Стоимость растёт (лишние прогоны для промежуточных позиций очереди), поэтому сочетайте с быстрым CI: тяжёлые e2e-тесты переносите в post-merge воркфлоу.

## Устранение типичных проблем

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| Постоянный Cache Miss у npm/pip | Lock-файл меняется в каждом коммите или `cache-dependency-path` указывает не туда | Зафиксировать зависимости; проверить путь к lock-файлу в монорепо |
| Ошибка конфликта при загрузке артефакта в матрице | Неуникальное имя артефакта (неизменяемость с v4) | Добавить `${{ matrix.os }}`/`${{ matrix.shard }}` в имя |
| Деплой из очереди внезапно отменён | Действие правила «один ожидающий запуск» в concurrency-группе | Явно указать `queue: max`, если нужна полная очередь |
| Обязательная проверка не появилась, PR нельзя смержить | Воркфлоу целиком отфильтрован по `paths` | Заглушечный джоб с условием или paths-filter-паттерн |
| Задачи долго висят в Queued | Исчерпана конкурентность плана или нет свободных раннеров под метку | Проверить Settings → Actions → Runners; снизить max-parallel; пересмотреть тариф |
| Сборка arm64-образов идёт часами | Эмуляция QEMU на x64-раннере | Нативные arm64-раннеры (`runs-on: ubuntu-24.04-arm`) |

## Лучшие практики

1. **Сначала измерение, потом оптимизация**: диагностикой из Сценария 3 найдите реальный критический путь — чаще всего это не то, что кажется.
2. **Комбинируйте уровни параллелизма**: независимые домены — отдельные задачи; варианты одной задачи — матрица; независимые быстрые проверки одной задачи — параллельные шаги.
3. **Всегда задавайте `timeout-minutes`** для задач с внешними зависимостями (e2e, сетевые тесты).
4. **Для PR — отмена устаревших прогонов** (`cancel-in-progress: true`), **для деплоя — очередь** (`cancel-in-progress: false`, при необходимости `queue: max`).
5. **Минимальный retention артефактов** и осознанный выбор между zip и `archive: false`.
6. **Фильтры путей — вместе с заглушками required checks**, иначе фильтрация заблокирует мержи.
7. **Пинуйте версии экшенов** и следите за major-обновлениями (переходы на Node.js 24 требуют свежих self-hosted раннеров).
8. **Считайте деньги**: перенос с macOS на Linux, x64 на arm64 и с VM на `ubuntu-slim` для лёгких задач даёт кратную экономию минут.
