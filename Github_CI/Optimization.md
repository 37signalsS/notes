# GitHub Actions: Оптимизация воркфлоу

Оптимизация воркфлоу в GitHub Actions направлена на сокращение времени выполнения, экономию ресурсов и улучшение поддерживаемости процессов CI/CD (Continuous Integration / Continuous Deployment — непрерывная интеграция и непрерывная доставка).

## Определения

- **Оптимизация воркфлоу**: Практика применения различных техник и стратегий (кеширование, распараллеливание, фильтрация событий) для минимизации времени выполнения и стоимости вычислительных ресурсов CI/CD конвейеров.

## Основные концепции

### 1. Кеширование зависимостей

Сохранение зависимостей (например, директорий `node_modules` или `~/.cache/pip`) между запусками задач для предотвращения их повторного скачивания из интернета. Это одна из наиболее эффективных техник для ускорения большинства сборок.

Детальное описание: **[Кеширование](./Caching.md)**.

### 2. Параллелизация через стратегию матрицы (Matrix Strategy)

Выполнение одной и той же задачи параллельно с использованием различных конфигураций (например, разные версии языков программирования или операционных систем). Это позволяет существенно сократить общее время тестирования за счет одновременного запуска проверок.

**Параметр `fail-fast`**:
По умолчанию GitHub Actions останавливает все задачи в матрице, если одна из них завершилась ошибкой.
- `fail-fast: true` (по умолчанию) — экономит ресурсы, прерывая выполнение при первом сбое.
- `fail-fast: false` — полезно, если важно получить результаты тестов во всех окружениях, даже если одно из них упало.

Детальное описание: **[Матричные сборки](./Matrix_Builds.md)**.

### 3. Ограничение времени выполнения (Timeout)

По умолчанию задачи могут выполняться до 6 часов. Зависшие процессы могут потреблять лимиты минут. Использование директивы `timeout-minutes` позволяет принудительно завершить задачу, если она превысила разумное время выполнения.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15 # Завершить, если выполнение длится более 15 минут
```

### 4. Использование высокопроизводительных исполнителей (Larger Runners)

Для ресурсоемких задач (компиляция больших проектов на C++, обучение моделей машинного обучения) стандартных исполнителей может быть недостаточно. GitHub предоставляет **Larger Runners** с увеличенным количеством CPU (Central Processing Unit — центральный процессор) и RAM (Random Access Memory — оперативная память). Это сокращает время сборки за счет более эффективной параллельной компиляции.

### 5. Переиспользование воркфлоу

Вынос часто повторяющихся шагов или целых цепочек задач в отдельные файлы переиспользуемых воркфлоу. Это уменьшает дублирование кода и упрощает централизованное управление пайплайнами.

Детальное описание: **[Переиспользуемые воркфлоу](./Reusable_Workflows.md)**.

### 6. Контроль одновременных запусков (Concurrency)

Использование директивы `concurrency` для автоматической отмены устаревших или избыточных запусков в рамках одной ветки или Pull Request. Это предотвращает бесполезную трату ресурсов на промежуточные коммиты.

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

Синтаксис и детали: **[Синтаксис Workflow](./Workflow_Syntax.md#concurrency)**.

### 7. Условные триггеры и фильтрация путей (Paths Filter)

Настройка запуска воркфлоу только при изменении определенных файлов или директорий с помощью параметра `paths`. Это исключает запуск тяжелых сборок при изменении документации или других не связанных с кодом файлов.

```yaml
on:
  push:
    paths:
      - 'src/**'
      - '!**.md' # Исключить изменения в markdown-файлах
```

Подробнее о фильтрах: **[События, Задачи и Шаги](./Events_Jobs_Steps.md)**.

### 8. Оптимизация слоев Docker

При использовании Docker в рамках GitHub Actions правильная организация инструкций в Dockerfile позволяет максимально эффективно использовать кеш слоев, что значительно ускоряет сборку образов.

Ключевые практики:

- Размещение редко меняющихся инструкций в начале файла.
- Использование многоэтапной сборки (multi-stage builds).
- Минимизация количества слоев за счет объединения связанных команд.

Детальное описание: **[Оптимизация сборки Docker-образов](../Docker/Dockerfile/Docker_best_practices/build_optimization.md)**.

## Практические сценарии

### Сценарий: Оптимизированный конвейер непрерывной интеграции

Пример конфигурации, объединяющий несколько техник оптимизации для типичного проекта:

```yaml
name: Optimized CI

on:
  push:
    branches: [ main ]
    paths: [ 'src/**', 'package*.json' ]
  pull_request:
    paths: [ 'src/**', 'package*.json' ]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    strategy:
      fail-fast: true
      matrix:
        node-version: [18, 20, 22]
    steps:
      - uses: actions/checkout@v7

      - name: Setup Node.js
        uses: actions/setup-node@v7
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm' # Встроенное кеширование зависимостей

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test
```

В данном примере применены:

- **Фильтрация путей**: запуск только при изменениях в коде или зависимостях.
- **Контроль конкурентности**: отмена старых запусков при новых коммитах в Pull Request.
- **Матрица с `fail-fast`**: параллельное выполнение тестов с быстрой отменой при ошибке.
- **Встроенный кеш**: использование встроенного механизма `setup-node` для кеширования пакетов.
- **Таймауты**: защита от бесконечного выполнения задач.
