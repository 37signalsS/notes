# GitHub Actions: События, Задачи и Шаги

Иерархия автоматизации в GitHub Actions строится на трёх основных функциональных уровнях: **Событие (Event)** → **Задачи (Jobs)** → **Шаги (Steps)**. Вместе они определяют условия активации («когда»), среду исполнения («где») и конкретный набор операций («что»). Такое разделение позволяет независимо менять триггерную логику и содержимое пайплайна: один и тот же набор задач можно запускать по push, расписанию или вручную, не переписывая сами шаги.

## Определения

- **Событие (Event)**: Внешний или внутренний триггер, инициирующий запуск рабочего процесса. Описывает условие «когда». Полезная нагрузка события доступна через контекст `github.event`.
- **Задача (Job)**: Набор шагов, выполняемых на одном и том же исполнителе (runner). Задачи изолированы друг от друга (для каждой выделяется свежая эфемерная среда) и по умолчанию выполняются параллельно. Описывает среду «где».
- **Шаг (Step)**: Минимальная атомарная единица работы внутри задачи (скрипт или экшен). Шаги выполняются строго последовательно и разделяют одну файловую систему рабочей области (workspace). Описывает действие «что».
- **Сервисы (Services)**: Дополнительные контейнеры (sidecars), запускаемые вместе с основной задачей (например, база данных или кеш-сервер).
- **Зависимости задач (Job Dependencies)**: Механизм управления порядком выполнения через ключ `needs`.
- **Раннер (Runner)**: Машина, исполняющая задачу. Бывает GitHub-hosted (облачный, эфемерный) или self-hosted; детали выбора и тарификации — [Среды выполнения и ограничения](./Environment_Limitations.md).
- **Контекст (Context)**: Объект (`github`, `env`, `steps`, `needs`, `inputs` и др.), через который шаги и условия получают доступ к метаданным прогона, событию и результатам соседних единиц работы. Подробный разбор — [Ключевые концепции](./Core_Concept.md).

## Основные концепции

### Классификация событий

Триггеры описываются в секции `on:` и делятся на четыре группы:

1. **Webhook-события репозитория**: реакция на активность в Git/GitHub (`push`, `pull_request`, `release`, `issues` и десятки других).
2. **Расписание**: `schedule` (POSIX cron).
3. **Ручные и внешние запуски**: `workflow_dispatch` (интерфейс/CLI/API) и `repository_dispatch` (внешние системы через REST API).
4. **Программные цепочки**: `workflow_run`, `workflow_call`, `check_run`/`check_suite`, `status`, `deployment` — запуск одного автоматизма в зависимости от результата другого.

Важное ограничение: большинство webhook-событий (`schedule`, `repository_dispatch`, `check_run`, `workflow_run` и др.) запускают воркфлоу, только если его файл существует в ветке по умолчанию. Не все webhook-события GitHub вообще доступны как триггеры Actions.

### Типовые триггеры

| Событие | Назначение | Безопасность и нюансы |
| :--- | :--- | :--- |
| `push` | Пуш коммитов или тегов. Используется для CI в ветках. | Фильтры `branches` игнорируют теги (для тегов — `tags`). При пачке более 3 тегов или более 5000 веток за раз события не создаются вовсе. Удаление ветки также порождает `push` с признаком удаления. |
| `pull_request` | Открытие, обновление или закрытие PR. Работает в контексте временного merge-коммита (`refs/pull/N/merge`). | Нет доступа к секретам (кроме read-only `GITHUB_TOKEN`). По умолчанию срабатывает только на `opened`, `synchronize`, `reopened`. При конфликте с базовой веткой прогон не создаётся. Для форков действует модель одобрения запусков. |
| `pull_request_target` | Активность в PR с контекстом базовой ветки. | **Критично:** имеет доступ к секретам. Запускается даже при конфликте. Опасно при `checkout` кода из PR — см. раздел «Форки и безопасность». |
| `workflow_dispatch` | Ручной запуск из интерфейса, CLI или API. | Поддерживает входные параметры (`inputs`). Файл должен быть в ветке по умолчанию. |
| `schedule` | Запуск по расписанию (POSIX cron). | Только ветка по умолчанию. Минимальный интервал — 5 минут; время в UTC (опционально `timezone`). Возможны задержки и отбрасывание очереди при пиковой нагрузке. В публичных репозиториях отключается после 60 дней неактивности. |
| `workflow_run` | Запуск после старта/завершения другого воркфлоу. | Выполняется в ветке по умолчанию и имеет полный доступ к секретам и токену записи, даже если исходный воркфлоу был непривилегированным. Цепочка длиннее трёх уровней не работает. |
| `workflow_call` | Вызов как [переиспользуемого процесса](./Reusable_Workflows.md). | Принимает `inputs` и `secrets`; полезная нагрузка события наследуется от вызывающего воркфлоу. |
| `repository_dispatch` | Запуск внешней системой через REST API. | Требует `event_type` (до 100 символов) и опциональный `client_payload` (до 10 свойств верхнего уровня, до 65535 символов). Файл должен быть в ветке по умолчанию. |
| `release` | Публикация или изменение релиза. | Типы: `published`, `prereleased`, `released`, `created`, `edited`, `deleted` и др. Для черновиков `created`/`edited`/`deleted` не срабатывают; для стабильных и пре-релизов одновременно используйте `published`. |
| `deployment` / `deployment_status` | Интеграция с внешними системами деплоя через API Deployments. | Часто используется связка с `status`: внешний инструмент сообщает о состоянии, Actions реагирует. |

### Событие push

Помимо обычных коммитов, `push` срабатывает при пуше тегов и при создании репозитория из шаблона. Практические нюансы:

- Фильтр `branches` применяется только к веткам; пуш тега обходит его (нужен фильтр `tags`).
- Массовые операции ограничены платформой: более трёх тегов за один push — события по тегам не генерируются; более 5000 веток — события не создаются.
- В полезной нагрузке вебхука для Actions отсутствуют атрибуты `added`/`removed`/`modified` коммита — полный объект коммита нужно получать через API.

### События pull_request и pull_request_target

Оба события доставляются в **базовый** репозиторий (в форке прогоны по PR-событиям не создаются), но работают в разных контекстах:

- `pull_request`: `GITHUB_REF` = `refs/pull/<номер>/merge`, `GITHUB_SHA` — последний merge-коммит. Поэтому `actions/checkout` по умолчанию проверяет **результат слияния PR с базовой веткой**, а не только код head-ветки — это корректная модель для тестирования интеграции. Если нужен именно последний коммит head-ветки, чекаутите `github.event.pull_request.head.sha`. SHA самого последнего коммита PR отличается от `GITHUB_SHA`.
- `pull_request_target`: контекст базовой ветки (код по умолчанию + секреты). Запускается даже при конфликте слияния, тогда как `pull_request` в этом случае не запускается вообще.

**Активность (activity types).** По умолчанию `pull_request` срабатывает только на `opened`, `synchronize` и `reopened`. Полный набор типов включает также `closed`, `edited`, `labeled`, `unlabeled`, `assigned`, `unassigned`, `converted_to_draft`, `ready_for_review`, `locked`, `unlocked`, `enqueued`, `dequeued`, `milestoned`, `demilestoned`, `review_requested`, `review_request_removed`, `auto_merge_enabled`, `auto_merge_disabled`.

**Детекция факта мержа.** Закрытие PR — это тоже `closed`, поэтому для реакции именно на мерж нужна проверка флага:

```yaml
on:
  pull_request:
    types: [closed]

jobs:
  after-merge:
    if: github.event.pull_request.merged == true
    runs-on: ubuntu-latest
    steps:
      - run: echo "PR был смержен"
```

При закрытии без мержа `GITHUB_REF` остаётся `refs/pull/N/merge`, при мерже — становится целевой веткой (например, `refs/heads/main`).

**Форки и безопасность событий.** Модель защиты GitHub Actions для PR из форков:

- Секреты не передаются на раннер; `GITHUB_TOKEN` выдаётся только с read-only правами.
- Запуски от новых контрибьюторов требуют ручного одобрения пользователем с правами write.
- PR от Dependabot рассматриваются как PR из форка со всеми ограничениями.
- Комбинация `pull_request_target` + `checkout` кода из PR — классический вектор атаки «pwn request» (выполнение недоверенного кода с доступом к секретам). Детали вектора и защита: [Атаки на CI/CD](../CI-CD/DevSecOps/cicd_attacks.md) и [SAST/DAST уязвимости](../CI-CD/DevSecOps/sast_dast_vulnerabilities.md).
- Безопасная альтернатива для привилегированной постобработки — двухфазный паттерн «непривилегированный сбор данных по `pull_request` → привилегированный обработчик по `workflow_run`» (см. Сценарий 6).

### Ручной запуск (Workflow Dispatch)

Событие `workflow_dispatch` позволяет запускать воркфлоу вручную через интерфейс GitHub, GitHub CLI (`gh workflow run`) или REST API. Оно поддерживает определение входных параметров (`inputs`), которые пользователь заполняет перед стартом.

**Типы входных данных:**
- **`choice`**: Выпадающий список предустановленных значений (разрешается в строку).
- **`boolean`**: Чекбокс (true/false).
- **`string`**: Текстовое поле.
- **`number`**: Числовое поле.
- **`environment`**: Выбор целевого окружения из настроек репозитория.

**Ограничения:** максимум 25 входов верхнего уровня; суммарный объём входов — 65535 символов. Воркфлоу должен существовать в ветке по умолчанию, иначе кнопка «Run workflow» не появится.

**Нюанс чтения значений.** Контекст `inputs` сохраняет типы (`boolean` остаётся булевым), тогда как `github.event.inputs` приводит всё к строкам. В выражениях `if:` предпочтителен `inputs`:

```yaml
# github.event.inputs.dryRun == 'false' (строка!) vs inputs.dryRun == false (boolean)
if: ${{ inputs.dryRun == false }}
```

**Пример конфигурации:**
```yaml
on:
  workflow_dispatch:
    inputs:
      logLevel:
        description: 'Log level'
        required: true
        default: 'info'
        type: choice
        options: [info, warning, debug]
      runTests:
        description: 'Run extra tests'
        type: boolean
        default: false
      deployEnv:
        description: 'Target environment'
        type: environment
        required: true
```

**Запуск через CLI с параметрами:**
```bash
gh workflow run deploy.yml -f logLevel=debug -f runTests=true -f deployEnv=staging
# → событие dispatch создано; прогон появится во вкладке Actions
```

### Запуск по расписанию (Schedule)

Расписание описывается массивом cron-выражений в POSIX-синтаксисе (пять полей):

```text
* * * * *
│ │ │ │ │
│ │ │ │ └── день недели (0-6 или SUN-SAT)
│ │ │ └──── месяц (1-12 или JAN-DEC)
│ │ └────── день месяца (1-31)
│ └──────── час (0-23)
└────────── минута (0-59)
```

Поддерживаются операторы `*` (любое значение), `,` (список), `-` (диапазон), `/` (шаг). Нестандартные директивы `@yearly`, `@monthly`, `@weekly`, `@daily`, `@hourly`, `@reboot` **не поддерживаются**.

```yaml
on:
  schedule:
    - cron: '30 5 * * 1-5'          # 05:30 UTC пн-пт
      timezone: "America/New_York"  # опционально: интерпретация времени в зоне IANA
    - cron: '*/15 * * * *'          # каждые 15 минут (минимально допустимый интервал — 5 минут)
```

Ограничения и особенности:

- Запускаются только последние коммиты **ветки по умолчанию**.
- По умолчанию время интерпретируется в **UTC**; параметр `timezone` (строка IANA) включает зонно-осознанное расписание (при переходе на летнее время пропущенные слоты сдвигаются на ближайшее валидное время).
- Минимальный интервал — **раз в 5 минут**.
- В часы пик (особенно на границе часа) возможны **задержки**; при высокой нагрузке часть поставленных в очередь запусков может быть **отброшена** без выполнения. Для критичных задач не ставьте расписание на :00 и предусматривайте самопроверку.
- В **публичных** репозиториях расписание автоматически отключается после **60 дней отсутствия активности** в репозитории. Повторное изменение `cron` пользователем с правами write реактивирует воркфлоу.
- Уведомления о сбоях отправляются пользователю, который последним менял cron в файле.

Для отладки удобно комбинировать `schedule` с `workflow_dispatch` в одном воркфлоу — так ночной регламент можно проверить вручную (см. Сценарий 4). Генерацию синтаксиса удобно проверять сервисом [crontab.guru](https://crontab.guru/).

### Цепочки воркфлоу (workflow_run и workflow_call)

**`workflow_run`** запускает воркфлоу при запросе или завершении другого воркфлоу. Ключевые свойства:

- Выполняется **только в ветке по умолчанию** (файл должен быть там же).
- Имеет доступ к секретам и токену с правами записи, **даже если исходный воркфлоу был непривилегированным** — это штатный механизм эскалации привилегий для обработки недоверенных данных (форк-PR). Обратная сторона — риск: запуск недоверенного кода в таком обработчике ведёт к отравлению кешей и утечке секретов.
- Срабатывает **независимо от результата** исходного воркфлоу; фильтрация по итогу — через `github.event.workflow_run.conclusion` (`success`/`failure`/`cancelled`).
- Типы активности: `requested`, `in_progress`, `completed` (тип `requested` не возникает при повторном запуске/re-run).
- Фильтр `branches` относится к ветке **исходного** воркфлоу.
- Цепочки глубже **трёх уровней не работают** (A → B → C → D → E → F: E и F не запустятся) — для длинных конвейеров используйте одну задачу с `needs`.
- Данные из исходного прогона передаются артефактами; при скачивании артефакта указывайте `run-id: ${{ github.event.workflow_run.id }}` и распаковывайте вне workspace (см. Сценарий 6).

```yaml
on:
  workflow_run:
    workflows: ["Run Tests"]     # точное имя исходного воркфлоу (name), не имя файла
    types: [completed]

jobs:
  on-success:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    runs-on: ubuntu-latest
    steps:
      - run: echo 'Исходный воркфлоу прошёл успешно'
```

**`workflow_call`** превращает воркфлоу в переиспользуемый вызываемый блок: полезная нагрузка события полностью наследуется от вызывающего воркфлоу, параметры и секреты передаются явно. Разбор механики — [Переиспользуемые рабочие процессы](./Reusable_Workflows.md).

### Внешний запуск через API (Repository Dispatch)

Событие для интеграции внешних систем (мониторинг, другой CI, вебхуки сторонних сервисов):

```yaml
on:
  repository_dispatch:
    types: [test_result]
```

Отправка события:

```bash
curl -X POST \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_TOKEN" \
  https://api.github.com/repos/OWNER/REPO/dispatches \
  -d '{"event_type":"test_result","client_payload":{"passed":false,"message":"timeout"}}'
# → HTTP 204 No Content (успех)
```

Полезная нагрузка доступна в воркфлоу как `github.event.client_payload.*` (например, `if: ${{ !github.event.client_payload.passed }}`).

### Фильтрация событий и активность

События поддерживают уточняющие фильтры для оптимизации запусков:

- **`branches` / `branches-ignore`**: Фильтрация по веткам. Поддерживает паттерны (например, `feature/*`, `feature/**` для рекурсии). Символ `!` перед паттерном исключает конкретную ветку.
- **`paths` / `paths-ignore`**: Запуск только при изменении файлов в определённых директориях.
- **`tags` / `tags-ignore`**: Фильтрация по Git-тегам.
- **Activity Types**: Для сложных событий (`pull_request`, `issues`, `release`) конкретные действия задаются ключом `types` — см. раздел про `pull_request` выше.

Правила комбинирования:

- Если заданы и `branches`, и `paths`, прогон создаётся только когда **оба** фильтра выполнены.
- Паттерны оцениваются по порядку; побеждает **последнее совпадение**. Поэтому исключающий паттерн `!` должен идти после включающего: сначала `'releases/**'`, затем `'!releases/**-alpha'`. Список из одних исключений не запустит воркфлоу ни для чего.
- Для реакции на head-ветку PR (а не целевую) используйте условие по `github.head_ref`: `if: startsWith(github.head_ref, 'releases/')` — фильтр `branches` при этом проверяет целевую ветку.

**Пример фильтрации:**
```yaml
on:
  push:
    branches:
      - main
      - 'releases/**'
      - '!releases/**-alpha' # Исключить альфа-релизы (после включающего паттерна)
    paths-ignore:
      - 'docs/**'
      - 'README.md'
```

### Пропуск воркфлоу (Skip Workflow)

GitHub Actions позволяет пропустить запуск пайплайна, если сообщение коммита содержит специальные ключевые слова:
- `[skip ci]`, `[ci skip]`
- `[no ci]`
- `[skip actions]`, `[actions skip]`

Инструкция действует **только на события `push` и `pull_request`**: `[skip ci]` не остановит воркфлоу на `pull_request_target`, `schedule` или `workflow_run`. Пропускается лишь прогон, который был бы вызван этим конкретным коммитом.

Альтернатива — трейлер `skip-checks` в конце сообщения коммита (после двух пустых строк; если есть другие трейлеры, он должен быть последним): `skip-checks: true` или `skip-checks:true`. Так как Git автоматически схлопывает пустые строки, используйте `git commit --cleanup=verbatim`.

Важно: если в правилах ветки требуемые проверки привязаны к пропущенному воркфлоу, они останутся в состоянии **Pending** и заблокируют мерж. Решение — запушить новый коммит без skip-инструкции.

## Задачи: Организация выполнения

Задачи позволяют структурировать процесс и распределять нагрузку.

### Модель выполнения и изоляция

- Каждой задаче выделяется собственный раннер с чистой средой; файловая система одной задачи недоступна другой. Единственные каналы передачи данных между задачами: **outputs** (короткие строки), **артефакты** (файлы), **кеш**, реестры пакетов и внешние хранилища.
- По умолчанию все задачи без взаимных зависимостей стартуют параллельно (в пределах лимитов конкурентности тарифа — см. [Среды выполнения и ограничения](./Environment_Limitations.md)).
- Жёсткий лимит времени жизни задачи на GitHub-hosted раннерах — 6 часов; явный `timeout-minutes` рекомендуется всегда (подробнее: [Оптимизация воркфлоу](./Optimization.md)).

### Зависимости и статусные функции (needs)

1. **Параллелизм и очередность**:
   - По умолчанию задачи независимы.
   - Директива `needs: [job_id]` создает зависимость, превращая параллельное выполнение в последовательное. Зависимости транзитивны: если C зависит от B, а B — от A, то C ждёт завершения всей цепочки.
   - Если зависимая задача упала или была отменена, зависимые от неё задачи получают статус **skipped** (пропущены), а не выполняются.

2. **Статусные функции в условиях `if`**: позволяют управлять поведением при сбоях:
   - `success()` — все предыдущие шаги/зависимости успешны (условие по умолчанию для шагов и задач);
   - `failure()` — какой-либо предыдущий шаг/зависимость упал;
   - `cancelled()` — прогон был отменён;
   - `always()` — выполнить независимо от результата, включая отмены (осторожно: не подходит для шагов с секретами в недоверенных контекстах).

   ```yaml
   notify:
     needs: [build, test]
     if: ${{ failure() }}   # выполнится, если build или test упали
     runs-on: ubuntu-latest
     steps:
       - run: ./send-alert.sh
   ```

3. **Контроль состояния**:
   - `if`: Условный запуск (например, `${{ failure() }}` для отправки уведомления об ошибке).
   - `continue-on-error`: На уровне **шага** — упавший шаг помечается аннотацией, но не роняет задачу; на уровне **задачи** — падение не красит весь прогон. Связка с матрицами разобрана в [Матричных сборках](./Matrix_Builds.md).

4. **Контекст окружения (Environment)**:
   Привязка задачи к [окружению (Environment)](./Core_Concept.md#управление-окружениями-environments) для использования правил защиты (required reviewers, wait timer) и специфических секретов.

5. **Права токена**: уровень доступа `GITHUB_TOKEN` задаётся ключом `permissions` на уровне воркфлоу или задачи; принцип минимальных прав — [Управление секретами](./secrets_management.md).

### Передача данных между задачами (Outputs)

Задачи могут передавать данные друг другу. Шаг устанавливает `output` (через `$GITHUB_OUTPUT`), задача экспортирует его через `outputs`, а следующая задача обращается к нему через контекст `needs`:

```yaml
outputs:
  build_id: ${{ steps.save.outputs.id }}
```

Механика и ограничения:

- Значения — строки; для больших объёмов (логи, бинарники) предназначены артефакты, а не outputs.
- Обязательные элементы цепочки: `id` у записывающего шага, объявление `outputs` на уровне задачи, обращение `needs.<job>.outputs.<name>`.
- Многострочные значения записываются heredoc-синтаксисом; устаревшая команда `::set-output` удалена из платформы. Подробности: [Синтаксис Workflow](./Workflow_Syntax.md).
- Если в потребителе output оказался пустым — проверьте всю цепочку (см. «Диагностика проблем»).

## Шаги: Операционная логика

Шаги — это то, что фактически выполняется на раннере. Все шаги одной задачи используют одну и ту же файловую систему (workspace сохраняется между шагами), но каждый шаг `run` — это **новый процесс**: переменные оболочки и рабочая директория `cd` между шагами не переносятся (мостиками служат `$GITHUB_ENV` и `$GITHUB_OUTPUT`).

- **`run`**: Выполнение команд в shell. Можно указать конкретный интерпретатор через `shell: python` или `shell: bash`.
- **`uses`**: Запуск [экшена из Marketplace](./Marketplace_Actions.md) или локального действия. Ключи `run` и `uses` взаимоисключающи.
- **`with`**: Передача входных параметров в экшен.
- **`env`**: Переменные окружения только для конкретного шага. Иерархия приоритета: `env` шага перекрывает `env` задачи, которая перекрывает `env` воркфлоу.
- **`id`**: Уникальный идентификатор, необходимый для обращения к выводам (`outputs`) шага и его статусам.
- **`working-directory`**: рабочая директория команды `run` (полезно в монорепозиториях).
- **`timeout-minutes`**: индивидуальный таймаут шага (по умолчанию наследует лимиты задачи).

Выбор shell и поведение по умолчанию:

| Платформа | Shell по умолчанию | Явный `shell: bash` |
| :--- | :--- | :--- |
| Linux/macOS | `bash -e {0}` (без pipefail) | `bash --noprofile --norc -eo pipefail {0}` |
| Windows | PowerShell Core (`pwsh`) | WSL-bash с `-eo pipefail` |

Практическое следствие: при явном `shell: bash` падение **любого звена конвейера** (`cmd1 | cmd2`) проваливает шаг благодаря `pipefail`, тогда как дефолтный `bash -e` замечает только код возврата последней команды конвейера.

Разбор статусов шага (`outcome` vs `conclusion`) и файлов `$GITHUB_OUTPUT`/`$GITHUB_ENV` — [Синтаксис Workflow](./Workflow_Syntax.md).

## Практические сценарии

### Сценарий 1: Пайплайн с зависимостями и передачей данных

Пример сборки артефакта и его последующего деплоя с использованием `needs` и `outputs`.

```yaml
name: Build and Deploy

on:
  push:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      artifact_version: ${{ steps.meta.outputs.version }}
    steps:
      - uses: actions/checkout@v7
      - id: meta
        run: echo "version=1.0.${{ github.run_number }}" >> $GITHUB_OUTPUT
      - name: Build
        run: echo "Building version ${{ steps.meta.outputs.version }}"

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production   # правило защиты окружения применится перед запуском
    steps:
      - name: Deploy
        run: echo "Deploying version ${{ needs.build.outputs.artifact_version }}"
```

Валидация: в UI прогон содержит две задачи; `deploy` стартует после успешного `build`; в логах шага Deploy ожидаемо `Deploying version 1.0.<номер прогона>`. Если `build` упадёт, `deploy` получит статус skipped.

### Сценарий 2: Использование сервисов (Sidecars)

Запуск базы данных PostgreSQL для интеграционных тестов.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: password
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
    steps:
      - uses: actions/checkout@v7
      - name: Run Integration Tests
        run: |
          npm ci
          npm test
        env:
          DB_URL: postgres://postgres:password@localhost:5432/postgres
```

Блок `options` задаёт health-check: контейнер публикует порт на `localhost` только после прохождения проверки готовности (`pg_isready`), поэтому приложение не столкнётся с ещё не поднявшейся базой. Без health-check соединение может падать с ошибкой `connection refused` на старте задачи.

### Сценарий 3: Обработка ошибок и условия

Выполнение шага только при падении предыдущих для очистки ресурсов или уведомления.

```yaml
    steps:
      - run: ./run-risky-script.sh
        continue-on-error: true # Задача не упадет, если скрипт вернет ошибку

      - name: Cleanup on failure
        if: failure() # Выполнится только если предыдущие шаги (без continue-on-error) упали;
                      # упавший шаг с continue-on-error: true НЕ активирует failure()
        run: ./cleanup.sh
```

Нюанс: шаг с `continue-on-error: true` имеет `outcome: failure`, но `conclusion: success`, поэтому не переводит задачу в состояние ошибки и не триггерит `failure()`. Для реакции на такой шаг проверяйте `steps.<id>.outcome == 'failure'`.

### Сценарий 4: Ночной регламент с ручным перезапуском

Комбинация `schedule` и `workflow_dispatch` в одном воркфлоу: по ночам аудит безопасности, днём — возможность запустить вручную на выбранной версии.

```yaml
name: Nightly Maintenance

on:
  schedule:
    - cron: '17 2 * * *'            # ежедневно 02:17 UTC (не на границе часа — меньше шанс задержки)
  workflow_dispatch:
    inputs:
      dryRun:
        description: 'Only report, do not change anything'
        type: boolean
        default: true

jobs:
  audit:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v7
      - name: Run dependency audit
        run: npm audit --json > audit.json || true
      - name: Apply fixes (manual runs may opt out)
        if: ${{ github.event_name == 'schedule' || inputs.dryRun == false }}
        run: npm audit fix
```

Валидация: ручной прогон с `dryRun=false` выполняет фиксы; ночной — только отчёт. Условие различает источник запуска через `github.event_name` (для `schedule` оно истинно всегда).

### Сценарий 5: Уведомление при падении деплоя

Задача-«наблюдатель», реагирующая статусной функцией на падение цепочки зависимостей.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: ./build.sh

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh

  alert:
    needs: [build, deploy]           # ждёт всю группу; при сбое любого — не skipped, а выполнен
    if: ${{ failure() }}
    runs-on: ubuntu-latest
    steps:
      - name: Notify
        run: |
          curl -s -X POST -H 'Content-type: application/json' \
            --data '{"text":"Deploy pipeline FAILED: ${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}"}' \
            ${{ secrets.SLACK_WEBHOOK_URL }} > /dev/null
          # → HTTP 200, сообщение появилось в канале Slack
```

Без `if: failure()` задача `alert` была бы пропущена при падении `deploy` (поведение по умолчанию — `success()`).

### Сценарий 6: Безопасная постобработка форк-PR (workflow_run)

Двухфазный паттерн «pwn request»: недоверенный код никогда не исполняется в привилегированном контексте.

Фаза 1 — непривилегированная, по `pull_request` (секретов нет, токен read-only):

```yaml
name: Collect Report
on:
  pull_request:
jobs:
  collect:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - run: ./collect-metrics.sh > report.json
      - uses: actions/upload-artifact@v4
        with:
          name: report
          path: report.json
```

Фаза 2 — привилегированная, по `workflow_run` (секреты доступны, код исполняется из ветки по умолчанию):

```yaml
name: Process Report
on:
  workflow_run:
    workflows: ["Collect Report"]
    types: [completed]
jobs:
  process:
    runs-on: ubuntu-latest
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    steps:
      - name: Download artifact from triggering run
        uses: actions/download-artifact@v5
        with:
          name: report
          path: ${{ runner.temp }}/report     # распаковка ВНЕ workspace — туда мог писать недоверенный код
          run-id: ${{ github.event.workflow_run.id }}
          github-token: ${{ secrets.GITHUB_TOKEN }}
      - name: Post results
        run: |
          cat "${{ runner.temp }}/report/report.json"
          # здесь безопасно использовать секреты: исполняется только доверенный код
```

Валидация: у форк-PR появляется прогон `Collect Report` (возможно, ожидающий одобрения), а после него — прогон `Process Report` в ветке по умолчанию.

## Диагностика проблем

| Симптом | Вероятная причина | Диагностика и решение |
| :--- | :--- | :--- |
| Нет кнопки «Run workflow» | Файл воркфлоу отсутствует в ветке по умолчанию; синтаксическая ошибка YAML; секция `on:` невалидна | Открыть файл в UI на default-ветке; локально проверить YAML-парсер (голый `on:` без значения некоторые парсеры читают как булево `true` — пишите `on:` со списком/словарём событий) |
| Расписание не срабатывает | 60 дней неактивности (public); файл вне default-ветки; задержки/дропы под нагрузкой; путаница UTC | Вкладка Actions → воркфлоу отключён? Реактивировать правкой cron; вынести время с :00; сверять время с UTC |
| Задача имеет статус skipped | Упала/отменена зависимая задача из `needs`; ложное условие `if`; фильтры `paths`/`branches` отсекли прогон | Раскрыть граф задач в UI; проверить вывод условий; посмотреть вкладку Summary прогона (GitHub пишет причину фильтрации) |
| Output пуст в зависимой задаче | Не объявлен `outputs` на уровне задачи; у шага нет `id`; значение писалось в stdout вместо `$GITHUB_OUTPUT`; задача-источник упала | Проверить три элемента цепочки (`id` → шаг-запись → `needs.X.outputs.Y`); добавить отладочный `echo '${{ toJson(needs) }}'` |
| Service: `connection refused` | Health-check не задан или слишком строгий; неверный порт маппинга | Добавить `options` c `--health-cmd`; убедиться, что клиент ходит на `localhost:<порт из ports>` |
| Required checks висят Pending | Прогон пропущен `[skip ci]` или фильтрами путей/веток | Запушить коммит без skip-инструкции; пересмотреть фильтры либо правила обязательных проверок |
| Цепочка `workflow_run` не стартовала | Имя в `workflows:` не совпадает с `name:` исходника; исходный воркфлоу вне default-ветки; цепочка глубже 3 уровней | Сверить имя точно (не имя файла); проверить размещение файлов; спрямить цепочку через `needs` |
| Шаг упал, хотя команда прошла | Конвейер с `pipefail` (явный `shell: bash`); ненулевой код промежуточной команды | Проверить, какой shell реально используется; убрать лишние команды из конвейера или обработать их коды |

## Рекомендации по использованию

1. Минимизируйте поверхность триггеров: `pull_request` вместо `pull_request_target` везде, где не требуется доступ к секретам; привилегированную обработку — по паттерну из Сценария 6.
2. Всегда задавайте `timeout-minutes` для задач с внешними зависимостями и расписание — не на границе часа.
3. Комбинируйте `schedule` с `workflow_dispatch` для возможности ручной проверки регламентов.
4. Фильтруйте `paths` на уровне воркфлоу, а тонкую логику — условиями `if` на задачах: это экономит минуты и снижает шум.
5. Ограничивайте `permissions` токена на уровне задачи; секреты деплоя держите в Environments с правилами защиты.
6. Для длинных конвейеров используйте `needs` внутри одного воркфлоу, а не цепочки `workflow_run` (ограничение в три уровня).
7. Пинуйте версии экшенов (`actions/checkout@v7`) и периодически актуализируйте их.
