# GitHub Actions: События, Задачи и Шаги

Иерархия автоматизации в GitHub Actions строится на трёх основных функциональных уровнях: **Событие (Event)** → **Задачи (Jobs)** → **Шаги (Steps)**. Вместе они определяют условия активации, среду исполнения и конкретный набор операций пайплайна.

## Определения

- **Событие (Event)**: Внешний или внутренний триггер, инициирующий запуск рабочего процесса. Описывает условие «когда».
- **Задача (Job)**: Набор шагов, выполняемых на одном и том же исполнителе (runner). Задачи изолированы друг от друга и по умолчанию выполняются параллельно. Описывает среду «где».
- **Шаг (Step)**: Минимальная атомарная единица работы внутри задачи (скрипт или экшен). Шаги выполняются строго последовательно. Описывает действие «что».
- **Сервисы (Services)**: Дополнительные контейнеры (sidecars), запускаемые вместе с основной задачей (например, база данных или кеш-сервер).
- **Зависимости задач (Job Dependencies)**: Механизм управления порядком выполнения через ключ `needs`.

## Основные концепции

### События: Триггеры и фильтры

События описываются в секции `on`. Они позволяют гибко настраивать запуск пайплайна.

**Типовые триггеры:**

| Событие | Назначение | Безопасность и нюансы |
| :--- | :--- | :--- |
| `push` | Пуш кода или тегов. | Используется для CI в ветках. |
| `pull_request` | Открытие, обновление или закрытие PR. | Работает в контексте временного merge-коммита. Нет доступа к секретам. |
| `pull_request_target` | Активность в PR с контекстом базовой ветки. | **Критично:** имеет доступ к секретам. Опасно при `checkout` кода из PR. |
| `workflow_dispatch` | Ручной запуск из интерфейса GitHub. | Поддерживает входные параметры (`inputs`). |
| `schedule` | Запуск по расписанию (`cron`). | Запускается только в ветке по умолчанию (main). |
| `workflow_run` | Запуск после завершения другого воркфлоу. | Позволяет строить цепочки (например, релиз после тестов). |
| `workflow_call` | Вызов как [переиспользуемого процесса](./Reusable_Workflows.md). | Принимает `inputs` и `secrets`. |

**Фильтрация**:
События `push` и `pull_request` поддерживают уточняющие фильтры:
- `branches` / `branches-ignore`: Фильтр по веткам.
- `paths` / `paths-ignore`: Запуск только при изменении конкретных файлов (оптимизация для монорепозиториев).
- `tags`: Запуск при создании тегов (например, `v*`).

### Задачи: Организация выполнения

Задачи позволяют структурировать процесс и распределять нагрузку.

1. **Параллелизм и очередность**:
   - По умолчанию задачи независимы.
   - Директива `needs: [job_id]` создает зависимость, превращая параллельное выполнение в последовательное.
2. **Передача данных (Outputs)**:
   Задачи могут передавать данные друг другу. Шаг устанавливает `output`, задача экспортирует его через `outputs`, а следующая задача обращается к нему через контекст `needs`.
   ```yaml
   outputs:
     build_id: ${{ steps.save.outputs.id }}
   ```
3. **Контроль состояния**:
   - `if`: Условный запуск (например, `${{ failure() }}` для отправки уведомления об ошибке).
   - `continue-on-error`: Позволяет задаче считаться успешной, даже если она упала.
4. **Контекст окружения (Environment)**:
   Привязка задачи к [окружению (Environment)](./Core_Concept.md#управление-окружениями-environments) для использования правил защиты и специфических секретов.

### Шаги: Операционная логика

Шаги — это то, что фактически выполняется на раннере. Все шаги одной задачи используют одну и ту же файловую систему.

- **`run`**: Выполнение команд в shell. Можно указать конкретный интерпретатор через `shell: python` или `shell: bash`.
- **`uses`**: Запуск [экшена из Marketplace](./Marketplace_Actions.md) или локального действия.
- **`with`**: Передача входных параметров в экшен.
- **`env`**: Переменные окружения только для конкретного шага.
- **`id`**: Уникальный идентификатор, необходимый для обращения к выводам (`outputs`) шага.

## Практические сценарии

### Сценарий 1: Пайплайн с зависимостями и передачей данных

Пример сборки артефакта и его последующего деплоя с использованием `needs` и `outputs`.

```yaml
name: Build and Deploy

on:
  push:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      artifact_version: ${{ steps.meta.outputs.version }}
    steps:
      - uses: actions/checkout@v7
      - id: meta
        run: echo "version=1.0.${{ github.run_number }}" >> $GITHUB_OUTPUT
      - name: Build
        run: echo "Building version ${{ steps.meta.outputs.version }}"

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy
        run: echo "Deploying version ${{ needs.build.outputs.artifact_version }}"
```

### Сценарий 2: Использование сервисов (Sidecars)

Запуск базы данных PostgreSQL для интеграционных тестов.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: password
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
    steps:
      - uses: actions/checkout@v7
      - name: Run Integration Tests
        run: |
          npm ci
          npm test
        env:
          DB_URL: postgres://postgres:password@localhost:5432/postgres
```

### Сценарий 3: Обработка ошибок и условия

Выполнение шага только при падении предыдущих для очистки ресурсов или уведомления.

```yaml
    steps:
      - run: ./run-risky-script.sh
        continue-on-error: true # Задача не упадет, если скрипт вернет ошибку
        
      - name: Cleanup on failure
        if: failure() # Выполнится только если предыдущие шаги (кроме continue-on-error) упали
        run: ./cleanup.sh
```
