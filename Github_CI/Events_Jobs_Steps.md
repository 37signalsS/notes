# GitHub Actions: События, Задачи и Шаги

Иерархия автоматизации в GitHub Actions строится на трёх основных компонентах: **Событие (Event)** → **Рабочий процесс (Workflow)** → **Задачи (Jobs)** → **Шаги (Steps)**. Вместе они определяют условия запуска, среду исполнения и конкретный набор команд.

## Определения

- **Событие (Event)**: Внешний или внутренний триггер, инициирующий запуск рабочего процесса. Определяет условие «когда».
- **Задача (Job)**: Изолированная единица выполнения, работающая на конкретном исполнителе (runner). Задачи в рамках одного процесса по умолчанию выполняются параллельно. Определяет «где».
- **Шаг (Step)**: Минимальная единица работы внутри задачи: запуск скрипта или готового действия (action). Шаги внутри задачи выполняются строго последовательно. Определяет «что».

## Основные концепции

### События: Условия запуска

События описываются в секции `on`. Они могут быть инициированы активностью в Git, расписанием, другими рабочими процессами или внешними системами.

**Расширенный список триггеров:**

| Событие | Описание | Особенности |
| :--- | :--- | :--- |
| `push` | Отправка коммитов или тегов. | Поддерживает фильтры по веткам, тегам и путям. |
| `pull_request` | Активность в PR (открытие, обновление). | Запускается в контексте временного коммита слияния. |
| `pull_request_target` | Активность в PR с правами базовой ветки. | **Опасно:** имеет доступ к секретам. Использовать с осторожностью. |
| `workflow_run` | Запуск после завершения другого процесса. | Позволяет строить цепочки между разными файлами воркфлоу. |
| `workflow_call` | Вызов как [переиспользуемого процесса](./Reusable_Workflows.md). | Позволяет передавать входы (`inputs`) и секреты (`secrets`). |
| `workflow_dispatch` | Ручной запуск через UI или API. | Поддерживает ввод параметров пользователем. |
| `schedule` | Запуск по расписанию (`cron`). | Выполняется только в ветке по умолчанию (обычно `main`). |
| `repository_dispatch` | Запуск через внешний Webhook. | Позволяет интегрировать GitHub с внешними системами. |

**Фильтрация и типы активностей:**
- **Фильтры по путям (`paths`)**: Экономят ресурсы, запуская процесс только при изменении значимых файлов (например, `src/**`).
- **Типы (`types`)**: Позволяют уточнить действие, вызвавшее событие (например, `on: pull_request, types: [labeled, closed]`).

### Задачи: Организация выполнения

Задачи позволяют структурировать процесс, обеспечивать изоляцию и управлять зависимостями.

- **`runs-on`**: Указывает [тип исполнителя](./Environment_Limitations.md).
- **`needs`**: Создает зависимости. Задача начнется только после успешного завершения всех перечисленных в `needs` задач.
- **`environment`**: Указывает [окружение (Environment)](./Core_Concept.md#окружения-и-правила-защиты-environments), к которому привязаны секреты и правила одобрения (Approvals).
- **`concurrency`**: Гарантирует, что только одна задача/процесс из группы выполняется одновременно. Позволяет отменять старые запуски (`cancel-in-progress: true`).
- **`permissions`**: Гранулярная настройка прав токена `GITHUB_TOKEN` для конкретной задачи.
- **`timeout-minutes`**: Принудительное завершение задачи при превышении времени выполнения.
- **`if`**: Условный запуск задачи на основе контекстов (например, `${{ github.ref == 'refs/heads/main' }}`).

### Шаги: Операционная логика

Шаги выполняются последовательно внутри одного исполнителя. Они делят между собой файловую систему и переменные окружения.

- **`uses`**: Запуск [готового действия](./Marketplace_Actions.md).
- **`run`**: Выполнение команд в shell. Можно указать конкретный интерпретатор через `shell`.
- **`env`**: Переменные окружения для конкретного шага.
- **`if`**: Условие выполнения шага. Часто используется функция `success()` (по умолчанию) или `always()`.
- **`continue-on-error`**: Если установлено `true`, задача продолжит выполнение, даже если этот шаг завершился неудачей.
- **`id`**: Уникальный идентификатор шага для обращения к его результатам (`outputs`) из других шагов.

## Практические сценарии

### Пайплайн с проверкой и развертыванием

Пример демонстрирует использование зависимостей, окружений и ручного подтверждения:

```yaml
name: Production Pipeline

on:
  push:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: Run unit tests
        run: npm test

  deploy:
    needs: test
    runs-on: ubuntu-latest
    environment: production # Требует настройки в Settings -> Environments
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v7
      - name: Deploy to Cloud
        run: ./scripts/deploy.sh
```
