# Testcontainers

## 1. Определения

**Testcontainers** — это библиотека с открытым исходным кодом, которая предоставляет временные ("одноразовые"), легковесные экземпляры зависимостей (например, баз данных, брокеров сообщений, веб-браузеров), запускаемые в Docker-контейнерах. Эти экземпляры используются во время выполнения автоматических тестов и автоматически удаляются после их завершения.

Основная цель — обеспечить чистую, изолированную и воспроизводимую среду для каждого тестового запуска.

## 2. Основные концепции

### Принцип работы

1. **Интеграция с тестами:** Библиотека Testcontainers добавляется в проект как зависимость.
2. **Программное управление:** В коде тестов (обычно в хуках `beforeAll` / `afterAll` или `beforeSuite` / `afterSuite`) описывается логика запуска и остановки контейнеров.
3. **Жизненный цикл:**
    * **Перед запуском тестов:** Testcontainers запускает Docker-контейнер с указанным образом (например, `postgres:14` или `redis:7`).
    * **Во время тестов:** Приложение настраивается для подключения к сервису, работающему внутри этого контейнера. Testcontainers предоставляет динамический порт и адрес для подключения.
    * **После завершения тестов:** Контейнер автоматически останавливается и удаляется, не оставляя "мусора" в системе.

### Ключевые преимущества

* **Изоляция:** Каждый тестовый набор выполняется в чистой, изолированной среде, что предотвращает влияние одного теста на другой.
* **Воспроизводимость:** Тесты становятся более надежными, так как окружение всегда одинаковое, независимо от того, где они запускаются (локальная машина разработчика, CI/CD-сервер).
* **Согласованность версий (Version Parity):** Можно использовать те же версии зависимостей, что и в продакшене (например, `redis:7`), что позволяет выявлять проблемы совместимости на ранних этапах.
* **Отсутствие локальных зависимостей:** Нет необходимости вручную устанавливать и настраивать сложные сервисы (PostgreSQL, Kafka и т.д.) на локальной машине. Единственная зависимость — Docker.

## 3. Практические сценарии

### Интеграционное тестирование с несколькими зависимостями

Вместо подключения к общей тестовой базе данных или использования in-memory альтернатив, Testcontainers поднимает реальные экземпляры сервисов в Docker.

**Примерный код (псевдокод на основе Ruby):**

```ruby
# Конфигурация тестового окружения
beforeSuite(() -> {
    // 1. Создание контейнеров для PostgreSQL и Redis
    postgresContainer = new PostgreSQLContainer("postgres:16")
    redisContainer = new RedisContainer("redis:7")

    // 2. Запуск контейнеров
    postgresContainer.start()
    redisContainer.start()

    // 3. Настройка приложения для подключения к этим контейнерам
    App.config.database_url = postgresContainer.getJdbcUrl()
    App.config.redis_url = redisContainer.getUrl()
    
    // 4. Применение миграций базы данных
    App.runMigrations()
});

// Очистка после всех тестов
afterSuite(() -> {
    postgresContainer.stop()
    postgresContainer.remove() // Удаление контейнера
    redisContainer.stop()
    redisContainer.remove()
});
```

### Предотвращение несоответствия версий

Частая проблема — когда локально у разработчика установлена одна версия зависимости (например, Redis 5), а в CI и production используется другая (Redis 7). Это может приводить к ошибкам, которые проявляются только в CI.

**Сценарий:**

1. Разработчик пишет тест, использующий новую команду `LPOP` с дополнительным аргументом, появившуюся в Redis 7.
2. Локально тест падает, потому что его локальный Redis 5 не поддерживает эту команду.
3. С помощью Testcontainers разработчик может указать точную версию Redis прямо в коде теста: `new RedisContainer("redis:7")`.
4. Теперь тест выполняется в окружении, идентичном production, и проходит успешно. Это позволяет отлавливать ошибки несовместимости версий еще до коммита.

## 4. Роль в DevOps и CI/CD

Testcontainers играют важную роль в современных DevOps-практиках.

### Упрощение CI/CD пайплайнов

* **Единственная зависимость — Docker:** Конфигурация CI-пайплайна значительно упрощается. Вместо настройки множества сервисов (например, `services` в GitLab CI) на CI-раннере должен быть установлен только Docker.
* **Надежность:** Устраняются "плавающие" тесты (flaky tests), связанные с использованием общих, изменяемых тестовых окружений.

### Dev/Prod Parity (Паритет сред)

* Testcontainers позволяют разработчикам локально использовать **те же версии** сервисов, что и в production. Это помогает достичь паритета между средой разработки, тестирования и эксплуатации, уменьшая количество ошибок вида "у меня на машине работало".
* **Пример:** Если в production используется PostgreSQL 16, а разработчик локально тестирует на PostgreSQL 14, тесты могут пройти, но приложение упадет в production из-за отсутствия какой-либо новой функции. Testcontainers решает эту проблему, позволяя запустить тест с контейнером `postgres:16`.

### Подход "Shift-Left"

* Разработчики получают возможность запускать полноценные интеграционные тесты на своих локальных машинах **до** отправки кода в систему контроля версий. Это позволяет обнаруживать ошибки на самых ранних этапах, сокращая время и стоимость их исправления.

### Тестовое окружение как код (Test Environment as Code)

* Определение зависимостей и их конфигурация находятся прямо в коде тестов. Это делает окружение версионируемым, самодостаточным и легко воспроизводимым.

## 5. Дополнительная информация

### Модули

Testcontainers предоставляет готовые "модули" для популярных технологий (JMS, Kafka, Nginx, PostgreSQL, Redis и др.), которые являются "синтаксическим сахаром" для упрощения их настройки.

* Модули содержат предопределенные конфигурации, упрощающие запуск (например, не нужно вручную указывать стандартный порт).
* Иногда официальная документация на сайте может отставать. Если нужного модуля нет в списке, стоит проверить репозиторий Testcontainers для конкретного языка (например, для Ruby модули существуют в GitHub-репозитории, но на момент написания не были отражены на основном сайте).

### Поддерживаемые языки (2025–2026)

Testcontainers имеет реализации для множества языков программирования:

* **Java/JVM**: Оригинальная и наиболее зрелая реализация (версия 2.x в 2025)
* **.NET**: Testcontainers.NET
* **Python**: `testcontainers-python`
* **Go**: `testcontainers-go`
* **Node.js**: `testcontainers-node`
* **Rust**: `testcontainers-rs`

### Альтернативы и сравнение

| Инструмент | Описание | Когда использовать |
|---|---|---|
| **Testcontainers** | Реальные сервисы в Docker | Интеграционные тесты с реальными зависимостями |
| **Docker Compose** | Оркестрация контейнеров | Локальное окружение, простые сценарии |
| **In-memory БД** (H2, SQLite) | Эмуляция БД в памяти | Быстрые unit-тесты, прототипирование |
| **WireMock / MockServer** | Мокирование HTTP-сервисов | Тестирование внешних API-зависимостей |
| **LocalStack** | Эмуляция AWS в Docker | Тестирование AWS-зависимостей без реального облака |

### Связь с Docker

Testcontainers полностью зависит от Docker. Для его работы необходимо, чтобы на машине, где запускаются тесты, был установлен и запущен Docker. Ссылка на обзор Docker: [Docker Overview](../Docker/docker_overview.md).
