# Виды тестов: Unit, Integration, E2E

## Определения

**Пирамида тестирования (Testing Pyramid)** — концепция, описывающая оптимальное соотношение тестов разного уровня: основание (много Unit) → середина (меньше Integration) → вершина (минимум E2E). Баланс смещён в сторону быстрых и изолированных проверок.

- **Unit-тесты (Модульные тесты)**: Проверяют минимальную изолированную часть кода — одну функцию, метод или класс. Цель — убедиться, что компонент работает корректно в изоляции от остальной системы.
- **Integration-тесты (Интеграционные тесты)**: Проверяют взаимодействие между несколькими компонентами системы или с внешними сервисами (например, базой данных, очередью сообщений, сторонним API).
- **End-to-End (E2E) тесты (Сквозные тесты)**: Эмулируют поведение реального пользователя и проверяют полный путь выполнения сценария через всю систему, от пользовательского интерфейса до базы данных.
- **Component-тесты (Компонентные тесты)**: Промежуточный уровень между Unit и Integration. Проверяют изолированный компонент с его реальными зависимостями (но без внешних сервисов). Часто используются для тестирования UI-компонентов или микросервисов в изоляции.

## Основные концепции

### Пирамида тестирования и ее пропорции

Концепция пирамиды визуализирует идеальное соотношение тестов разного уровня:

- **Основание (широкое): Unit-тесты.** Их должно быть больше всего. Они быстрые, дешевые в написании и поддержке, надежные и точно указывают на место сбоя.
- **Середина: Integration-тесты.** Их меньше, чем модульных. Они медленнее и дороже, так как требуют взаимодействия с другими компонентами, но они критически важны для проверки корректности связей в системе.
- **Вершина (узкая): E2E-тесты.** Их должно быть минимальное необходимое количество. Они самые медленные, дорогие и хрупкие (flaky), но только они могут проверить работу системы в целом с точки зрения пользователя.

Следование этой модели позволяет получить быструю и надежную обратную связь при минимальных затратах. Перевернутая пирамида (много E2E, мало Unit) считается анти-паттерном, ведущим к медленным и нестабильным сборкам.

### Сравнение уровней

| Критерий | Unit | Integration | E2E | Component |
|---|---|---|---|---|
| **Цель** | Проверка отдельной функции/класса | Взаимодействие модулей и внешних систем | Поведение всей системы «как пользователь» | Проверка изолированного компонента с зависимостями |
| **Гранулярность** | Мелкая | Средняя | Крупная | Средняя |
| **Зависимости** | Изолируются дублёрами (Mocks, Stubs) | Ограниченно реальны (БД, очередь) | Максимально реальны (UI, API, сеть) | Реальные зависимости, мокируются внешние сервисы |
| **Скорость** | Миллисекунды | Секунды | Минуты | Секунды |
| **Надёжность** | Высокая, детерминированная | Средняя | Подвержены нестабильности (flaky) | Высокая |
| **Сигнал о причине** | Точный | Средний | Часто расплывчатый | Точный |
| **Стоимость поддержки** | Низкая | Средняя | Высокая | Средняя |
| **Инструменты** | pytest, unittest, Jest, JUnit | Testcontainers, WireMock | Playwright, Cypress, Selenium | Storybook, React Testing Library |

### Тестовые дублёры и данные

**Тестовые дублёры (Test Doubles)** — объекты, заменяющие реальные зависимости в тестах.

- **Unit-тесты**: Активно используют **Mocks** и **Stubs** для изоляции от внешних зависимостей (I/O, сеть, время). Данные минимальны и синтетичны.
- **Integration-тесты**: Используют минимум моков. Допустимы фейковые реализации инфраструктуры (in-memory БД, локальный брокер). Здесь же применяются контрактные тесты.
- **E2E-тесты**: Требуют реального или максимально приближенного к реальному окружения. Данные фабрикуются или маскируются.
- **Component-тесты**: Используют реальные зависимости компонента, но мокируют внешние сервисы (API, БД).

**Типы дублёров:**
- **Dummy (Заглушка)**: Объект без реализации, передаётся для удовлетворения сигнатуры метода.
- **Stub (Заготовка)**: Возвращает заранее определённые значения для вызовов.
- **Mock (Макет)**: Проверяет, что метод был вызван ожидаемым образом (с определёнными аргументами, нужное количество раз).
- **Fake (Фейк)**: Рабочая реализация с упрощённой логикой (например, in-memory база данных).
- **Spy (Шпион)**: Записывает информацию о вызовах для последующей проверки.

### Организация проекта

Для удобства навигации и запуска тесты разных уровней часто разделяют по каталогам:

- `tests/unit/`
- `tests/integration/`
- `tests/e2e/`

## Практические сценарии

### Unit-пример (pytest)

Проверка чистой функции без внешних зависимостей.

```python
# app/math.py
def add(a, b): return a + b

# tests/unit/test_math.py
from app.math import add

def test_add_simple():
    assert add(2, 3) == 5
```

### Интеграционный пример (pytest с БД)

Тест проверяет чтение из реальной, но временной базы данных.

```python
# app/repo.py
import sqlite3
def get_users(conn): return conn.execute("select name from users").fetchall()

# tests/integration/test_repo.py
import sqlite3
from app.repo import get_users

def test_get_users_with_real_db(tmp_path):
    db = tmp_path / "app.db"
    conn = sqlite3.connect(db)
    conn.execute("create table users(name text)")
    conn.execute("insert into users values ('alice')")
    assert get_users(conn) == [('alice',)]
```

### E2E-пример (shell-скрипт)

Простой smoke-тест, который проверяет доступность сервиса и базовый сценарий авторизации.

```bash
# tests/e2e/smoke.sh
set -euo pipefail
BASE_URL="${BASE_URL:-http://localhost:8080}"
code=$(curl -s -o /dev/null -w "%{http_code}" "$BASE_URL/health")
[ "$code" = "200" ]
token=$(curl -s -X POST "$BASE_URL/login" -d 'u=demo&p=demo')
[ -n "$token" ]
```

### E2E-пример (Playwright — современный инструмент)

**Playwright** — фреймворк для автоматизации браузеров (Chromium, Firefox, WebKit) с поддержкой JavaScript, TypeScript, Python, Java, .NET.

```python
# tests/e2e/test_login.py
from playwright.sync_api import sync_playwright

def test_login_dashboard():
    with sync_playwright() as p:
        browser = p.chromium.launch()
        page = browser.new_page()
        page.goto("https://example.com/login")
        page.fill("#username", "demo")
        page.fill("#password", "demo")
        page.click("button[type='submit']")
        page.wait_for_selector("#dashboard")
        assert page.is_visible("#welcome")
        browser.close()
```

**Сравнение E2E-инструментов (2025–2026):**

| Инструмент | Языки | Браузеры | Скорость | Сложность |
|---|---|---|---|---|
| **Playwright** | JS/TS, Python, Java, .NET | Chromium, Firefox, WebKit | Высокая | Средняя |
| **Cypress** | JS/TS | Chromium, Firefox | Средняя | Низкая |
| **Selenium WebDriver** | Множество | Все основные | Низкая | Высокая |
| **Puppeteer** | JS/TS | Chromium | Высокая | Низкая |

## Дополнительная информация

### FIRST-принципы написания тестов

**FIRST** — акроним, описывающий качества хорошего теста:

- **Fast (Быстрые)**: Тесты должны выполняться быстро. Медленные тесты замедляют разработку.
- **Independent (Независимые)**: Тесты не должны зависеть друг от друга. Любой тест можно запускать в любом порядке.
- **Repeatable (Повторяемые)**: Тесты должны давать одинаковый результат в любом окружении (локально, CI, production).
- **Self-validating (Самопроверяемые)**: Результат теста должен быть однозначным (pass/fail) без ручной интерпретации.
- **Timely (Своевременные)**: Тесты должны писаться вовремя, в идеале — до production-кода (TDD).

### Что такое Flaky-тесты

**Flaky-тест (плавающий или нестабильный тест)** — это тест, который может показывать разные результаты (проходить и падать) без каких-либо изменений в коде. Такое поведение подрывает доверие к тестовому набору и замедляет разработку.

**Основные причины нестабильности:**
- **Асинхронные операции:** Неправильное ожидание завершения сетевых запросов, анимаций или фоновых задач.
- **Зависимость от порядка выполнения:** Тест проходит только в том случае, если перед ним выполнился другой тест.
- **Неизолированные данные:** Тесты изменяют общее состояние (базу данных, файлы), влияя друг на друга.
- **Внешние сервисы:** Зависимость от нестабильных сторонних API или сервисов.
- **Проблемы с ресурсами:** Нехватка памяти или CPU на тестовом агенте.
