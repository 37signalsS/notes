# Виды тестирования: Unit, Integration, E2E

## Определения

- **Пирамида тестирования (Testing Pyramid)** — концепция, описывающая оптимальное количественное соотношение тестов разного уровня. Основание пирамиды составляют многочисленные и быстрые модульные тесты, середину — интеграционные, а вершину — минимальное количество сквозных тестов.
- **Unit-тесты (Модульные тесты)** — проверки минимально возможной изолированной части кода (функции, метода или класса). Цель — верификация корректности компонента в полной изоляции от остальной системы.
- **Integration-тесты (Интеграционные тесты)** — проверки взаимодействия между несколькими компонентами системы или с внешними сервисами, такими как базы данных, брокеры сообщений или сторонние API (Application Programming Interface).
- **End-to-End (E2E) тесты (Сквозные тесты)** — испытания, эмулирующие поведение реального пользователя. Проверяют полный путь выполнения сценария через все слои системы: от UI (User Interface) до базы данных и внешних интеграций.
- **Component-тесты (Компонентные тесты)** — промежуточный уровень, на котором проверяется изолированный крупный компонент (например, микросервис или фронтенд-компонент) с его реальными внутренними зависимостями, но с имитацией внешних сервисов.

## Основные концепции

### Структура пирамиды тестирования

Пирамида визуализирует баланс между скоростью выполнения и стоимостью поддержки тестов:

1. **Основание: Unit-тесты.** Составляют основную массу проверок. Они максимально быстрые, дешевые в написании и обеспечивают точную локализацию ошибки.
2. **Середина: Integration-тесты.** Проверяют "швы" между модулями. Они медленнее модульных, так как требуют настройки окружения (баз данных, сети), но критичны для обнаружения ошибок взаимодействия.
3. **Вершина: E2E-тесты.** Минимальный набор тестов, покрывающий критические бизнес-сценарии. Они самые дорогие в поддержке и часто подвержены нестабильности (flaky), но дают уверенность в работоспособности системы целиком.

Смещение баланса в сторону E2E (инвертированная пирамида или "рожок мороженого") является антипаттерном, так как ведет к замедлению CI/CD (Continuous Integration / Continuous Deployment) и усложнению отладки.

### Сравнение уровней тестирования

| Критерий | Unit | Integration | E2E | Component |
| :--- | :--- | :--- | :--- | :--- |
| **Объект** | Отдельная функция/класс | Взаимодействие модулей | Бизнес-сценарий целиком | Изолированный сервис/блок |
| **Зависимости** | Дублёры (Mocks, Stubs) | Реальные (БД, очередь) | Полная инфраструктура | Реальные внутренние + моки внешних |
| **Скорость** | Миллисекунды | Секунды | Минуты | Секунды |
| **Надёжность** | Детерминированная | Высокая/Средняя | Подвержены flaky-эффекту | Высокая |
| **Локализация ошибки**| Точная | Средняя | Сложная | Точная |
| **Инструменты** | pytest, Jest, JUnit | Testcontainers, WireMock | Playwright, Cypress | Storybook, RTL |

### Тестовые дублёры

**Тестовые дублёры (Test Doubles)** — объекты, заменяющие реальные зависимости в тестах для изоляции или ускорения процесса.

- **Dummy (Заглушка)** — пустой объект для заполнения параметров.
- **Stub (Заготовка)** — возвращает заранее заданные данные на вызовы.
- **Mock (Макет)** — проверяет факт вызова метода с конкретными аргументами.
- **Fake (Фейк)** — упрощенная рабочая реализация (например, SQLite в памяти вместо PostgreSQL).
- **Spy (Шпион)** — записывает информацию о вызовах для последующей проверки.

## Практические сценарии

### Пример Unit-теста (Python / pytest)

Проверка логики без I/O (Input/Output) операций.

```python
# logic.py
def calculate_total(price, tax):
    return price + (price * tax)

# test_logic.py
from logic import calculate_total

def test_calculate_total_success():
    assert calculate_total(100, 0.2) == 120
```

### Пример интеграционного теста (pytest + база данных)

Использование временной базы данных для проверки репозитория.

```python
# repo.py
def save_user(db_session, user_data):
    db_session.add(user_data)
    db_session.commit()

# test_repo.py
import pytest
from repo import save_user

def test_save_user_to_db(db_session):
    user = {"name": "admin"}
    save_user(db_session, user)
    assert db_session.query(User).filter_by(name="admin").first() is not None
```

### Пример E2E-теста (Playwright)

Автоматизация браузера для проверки сценария входа.

```python
from playwright.sync_api import sync_playwright

def test_user_login():
    with sync_playwright() as p:
        browser = p.chromium.launch()
        page = browser.new_page()
        page.goto("https://app.example.com/login")
        page.fill("#user", "admin")
        page.fill("#pass", "secret")
        page.click("text=Log in")
        assert page.is_visible("#dashboard")
        browser.close()
```

## Дополнительная информация

### Принципы FIRST

Качественные тесты должны соответствовать критериям **FIRST**:

- **Fast (Быстрые)** — выполнение за минимальное время.
- **Independent (Независимые)** — отсутствие влияния тестов друг на друга.
- **Repeatable (Повторяемые)** — стабильный результат в любом окружении.
- **Self-validating (Самопроверяемые)** — однозначный статус (pass/fail).
- **Timely (Своевременные)** — написание тестов параллельно или до кода (TDD).

### Проблема Flaky-тестов

**Flaky-тест (нестабильный тест)** — проверка, которая может проходить или падать без изменений в коде.

**Причины:**

- Состояние гонки (race conditions).
- Недетерминированные данные.
- Недостаточная изоляция окружения.
- Зависимость от скорости сети или внешних API.

Методы борьбы описаны в разделе **[Интеграция тестов в CI/CD](./testing_cicd_integration.md)**.
