# Управление тестовыми данными (Test Data Management)

## Определения

**Test Data Management (TDM)** — дисциплина подготовки, генерации, хранения и очистки данных, используемых в автоматизированных и ручных тестах. Цель — стабильность тестов, отсутствие «плавающих» прогонов из-за данных, а также безопасность (защита от утечки персональных данных).

**Fixture** — фиксированный набор входных данных (или их фабрика), создаваемый к выполнению теста и удаляемый после.

**Data Factory / Data Generator** — код/инструмент, генерирующий похожие на боевые данные (валидные, реалистичные, включающие edge-кейсы).

**Masking (деперсонализация)** — замена чувствительных значений (персональные данные, номера карт, телефоны) на синтетические с сохранением валидности и ссылочной целостности.

**Subsetting** — извлечение репрезентативной части большой боевой БД (по суррогатным правилам) вместо копирования целиком.

**Golden Master / Baseline Data** — эталонные наборы для регрессионных сравнений.

## Основные концепции

### Уровни работы с тестовыми данными

| Подход | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Фикстуры в репозитории** | Небольшие статичные файлы (JSON/YAML) | Простота, версионирование | Быстро устаревают, не масштабируются |
| **Фабрики (factory_boy, Faker)** | Код создаёт объекты «на лету» по шаблону | Гибко, контролируемо | Сложнее в поддержке |
| **Снимок (snapshot) БД** | DB dump в тест-стейдж | Реалистично, быстрый старт | Неконсистентность со схемой, риск секретов |
| **Subsetting (subset/mask) из боевой БД** | Частичное/деперсонализированное копирование | Максимальная реалистичность | Нужна инфраструктура (pipeline TDM) |
| **Синтетическая генерация на поток** | Data Gen по требованиям/спекам | Контроль объёмов и распределения | Не всегда соответствует реальным данным |

### Продуктовый код: откуда берутся данные

- **Статические данные** — таблицы-справочники (справочники городов, валют), не меняются между прогонами.
- **Динамические данные** — время, счётчики, случайные значения; их надо генерировать в прогоне.
- **Контекстные данные** — зависят от пользователя/тенанта (сессии, конфиги) — главный источник флакад в параллельных тестах.

### Параллелизм и изоляция тестов

Классический источник «предсказательного» флака — общие данные между параллельными прогонами:

- каждому тесту — свои данные (created per run): `unique`-суффиксы, временные метки;
- транзакционная изоляция + `truncate`/`delete all` на входе в suite;
- правило: **никакого разделяемого mutable state между тестами**; если данные общие — тесты делать идемпотентными (upsert).

### Роль в CI и продакшн

- Тесты в CI — только изолированные данные, ничего неизвестного с «боя».
- Тесты против реального окружения (smoke после деплоя) — использовать **read-only/mark-данные**, не портя боевые записи.
- Хранилища секретов и TDM-пайплайны — обязательный аудит генерации/масирования.

## Практические сценарии

### Сценарий 1: Генерация реалистичных данных (Python)

```python
from faker import Faker
fake = Faker()

users = [
    {
        "email": fake.unique.email(),
        "phone": fake.phone_number(),
        "name": fake.name(),
    }
    for _ in range(100)
]
```

- `Faker` (Python) / `datafaker` — списки атрибутов и локализации; генерация ограниченных распределений (email, phone, address).
- По умолчанию поля уникальны через `.unique`.

### Сценарий 2: Фабрика сущностей (factory_boy)

```python
import factory
from app.models import User

class UserFactory(factory.Factory):
    class Meta:
        model = User

    email = factory.Faker("email")
    name = factory.Faker("name")
    role = "customer"

   @classmethod
    def _after_postgeneration(cls, instance, create, results=None):
        # после создания нужны связи/энричмент
        pass

user = UserFactory.create()
```

Фабрики комбинируют «значение по умолчанию» и гибкость в переопределении: `UserFactory.create(email="qa@example.com")`.

### Сценарий 3: Масихование при дампе продакшн-данных

Типичный сценарий (PostgreSQL) — сделать деперсонализированный subset:

```sql
BEGIN;
UPDATE account SET phone = '7' || substring(md5(random()::text) from 1 for 10);
UPDATE account SET email = 'qa+' || (row_number() over()) || '@example.internal';
COMMIT;
```

или через инструменты: **CloudMask/TDM-платформы**, `pg_dump` + `--exclude-table-data`, утилиты типа `miter`/`subset`, `sqlsmith` для синтетики. Регэксы и детерминированные хэши вместо сырого RANDOM для воспроизводимости.

### Сценарий 4: Снapshot-подход с изоляцией кандидатов

```bash
# взять свежий слепок боевой БД (без PII-hелей)
pg_dump --schema=app --data-only --no-owner -Fc prod_db > qa_snapshot.dump
# поднять в изолированном окружении (test/stage)
pg_restore -d test_db -c qa_snapshot.dump
```

Далее каждую feature-ветку пересоздают базу заново (через `docker compose`/flyway миграции) — схема и данные всегда в актуальном состоянии (см. [тестирование миграций/БД](../Testing/database_testing.md)).

### Сценарий 5: TDM-пайплайн в CI (идемпотентная инициализация)

```yaml
prepare-data:
  stage: test-setup
  image: postgres:16
  script:
    - ./scripts/reset_db.sh
    - ./scripts/seed_base.sh          # статические данные
    - ./scripts/generate_dynamic.sh   # уникальные динамические записи
```

Ключевые правила «зелёного» pipeline: восстановимость из репо без ручных шагов; любое окружение должно подниматься из одного `make setup`.

### Сценарий 6: data-driven параметризация юнит-тестов

```python
@pytest.mark.parametrize(
    "input,expected",
    [
        ("", 0),
        ("a", 1),
        ("ааа"*100000, 300000),   # большой объём
        ("\u0000", 1),            # спец-символ
    ],
)
def test_count(input, expected):
    assert count_chars(input) == expected
```

Параметризация покрывает edge-кейсы, которые не встретятся в «природных» данных.

## Типичные ошибки и диагностика

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| Тесты проходят поодиночке, падают вместе | Общие данные, параллельность | Уникальные данные на тест; изоляция per-suite |
| Флак «data not found» | Данные удалены другим тестом/задачей | Идемпотентность, правильное `after`-удаление |
| Утечка PII в тест-стенде | Дамп с чувствительными полями | Масихование обязательное; маскировать на лету в TDM-пайплайне |
| Снимок БД устарел, тесты падают | Изменение схемы/кода | Версионировать слепки, генерировать по схеме |
| Долгий запуск из-за больших fixtures | Огромные файлы в репо | Subset; generate on demand; сжимать (.gz/parquet) |
| Секреты в fixture-файлах | Захардкоженные credentials | Env-секреты, `secrets`/подключение к хранилищу |
