# CI/CD и автотесты

## Роль автотестов в CI/CD

Автоматизированные тесты встраиваются в конвейер сборки и доставки как механизм непрерывной проверки качества. Они уменьшают время обратной связи, предотвращают регрессии и превращают качество в измеряемую часть процесса, а не в заключительный этап. В контексте CI/CD автотесты выступают «исполняемыми спецификациями», фиксирующими требования к поведению системы и служащими базой для объективных решений о продвижении изменений по этапам.

Автотесты создают «quality gates» — условия, при которых сборка может переходить в следующий этап. Такой подход снижает риск дефектов в продакшене, позволяет безопаснее внедрять частые релизы и поддерживает практику shift-left: чем раньше обнаружен дефект, тем дешевле его устранение.

## Основные роли автотестов в конвейере

- **Предотвращение регрессий**: стабилизируют базовую функциональность при каждом коммите
- **Поддержка рефакторинга**: дают уверенность при изменениях архитектуры и кода
- **Документация поведения**: тесты фиксируют контракт системы лучше неформальных описаний
- **Управление рисками**: освещают критические сценарии до развертывания
- **Автоматизированные контроли**: применяются как проверяемые критерии соответствия требованиям

## Распределение тестов по этапам

| Этап pipeline | Типы тестов | Цель | Время/объем | Критерий прохождения |
|---------------|-------------|------|-------------|---------------------|
| Pre-commit (локально) | Lint, быстрые unit | Мгновенный фидбек | секунды | ноль ошибок |
| Build/CI | Unit, статический анализ | Базовая корректность | < 5 минут | все проверки успешны |
| Test stage | Component/contract, интеграционные | Валидность взаимодействий | 5–20 минут | ключевые сценарии зеленые |
| Pre-deploy (staging) | E2E, smoke UI, миграции | Проверка релиз-кандидата | 10–30 минут | критические пути OK |
| Post-deploy | Канареечные проверки, синтетические метрики | Верификация в реальной среде | минуты | без деградаций |

Чем выше по пирамиде тестов, тем дороже их выполнение и поддержка. Соотношение смещается в сторону быстрых и изолированных тестов на ранних этапах, оставляя дорогостоящие сценарии для точечного подтверждения готовности.

## Примеры конфигураций CI/CD

### Базовая структура пайплайна

```yaml
stages:
  - unit
  - integration
  - e2e

unit:
  stage: unit
  script: pytest -q tests/unit
  cache: { paths: [ .venv, .pytest_cache ] }

integration:
  stage: integration
  needs: [unit]
  services: [postgres:15]
  script:
    - pytest -q tests/integration
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule" || $CI_COMMIT_BRANCH == "main"'

e2e:
  stage: e2e
  needs: [integration]
  script:
    - docker-compose up -d
    - bash tests/e2e/smoke.sh
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
```

Ключевые практики: быстрые unit запускаются всегда; интеграция и e2e — по расписанию и на главной ветке; инфраструктура поднимается декларативно; тесты изолируются и дают воспроизводимые результаты.

### Пример встраивания в GitLab CI

```yaml
stages:
  - lint
  - test
  - package
  - deploy
  - verify

variables:
  JUNIT_REPORT: reports/junit.xml

lint:
  stage: lint
  script:
    - pip install ruff
    - ruff check .
  allow_failure: false

unit_tests:
  stage: test
  script:
    - pip install -r requirements.txt
    - pytest tests/unit -q --junitxml=$JUNIT_REPORT
  artifacts:
    when: always
    reports:
      junit: $JUNIT_REPORT
  retry: 1
  parallel: 4

integration_tests:
  stage: test
  needs: ["unit_tests"]
  services:
    - name: postgres:15
      alias: db
  variables:
    DATABASE_URL: postgres://postgres@db:5432/app
  script:
    - pytest tests/integration -q --maxfail=1
  timeout: 20m

package:
  stage: package
  needs: ["integration_tests"]
  script:
    - docker build -t registry/app:$CI_COMMIT_SHA .
    - docker save registry/app:$CI_COMMIT_SHA -o image.tar
  artifacts:
    paths: [image.tar]

deploy_staging:
  stage: deploy
  needs: ["package"]
  script:
    - ./deploy.sh staging image.tar

smoke_verify:
  stage: verify
  needs: ["deploy_staging"]
  script:
    - ./smoke.sh https://staging.example.com
```

## Практические аспекты надежности

### Борьба с «flaky»-тестами
- Фиксированные сиды
- Изоляция зависимостей
- Контроль времени
- Ретраи с ограничением
- «Карантин» нестабильных сценариев

### Данные для тестов
- Детерминированные фикстуры
- Фабрики
- Ephemeral-окружения на базе контейнеров и временных баз данных

### Параллелизация
- Шардирование по файлам/тегам
- Избегание общих глобальных ресурсов

### Метрики качества
- Длительность конвейера
- Доля падений по типам тестов
- Уровень ложных срабатываний
- Покрытие по критическим путям
- MTTR для красных сборок

### Политики прохода
- Жёсткие пороги для ранних этапов
- Селективные блокеры на поздних (например, обязательно зелёные E2E для checkout-потока, но необязательные для вспомогательных экранов)
