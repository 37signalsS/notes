# Интеграция автоматизированных тестов в CI/CD

## Определения

- **Quality Gates (Ворота качества)**: Автоматические проверки в CI/CD пайплайне, которые определяют, может ли сборка перейти на следующий этап. Тесты являются ключевым элементом ворот качества.
- **Shift-left Testing**: Подход, при котором тестирование сдвигается на более ранние этапы жизненного цикла разработки. Это позволяет обнаруживать дефекты раньше, снижая стоимость их исправления.
- **Shift-right Testing**: Подход, при котором тестирование продолжается в production-среде (канареечные развертывания, A/B-тесты, мониторинг). Дополняет shift-left для полной картины качества.

## Основные концепции

### Роль автотестов в CI/CD

Встраивание тестов в конвейер — это механизм непрерывной проверки качества. Он сокращает время обратной связи и превращает качество в измеряемую часть процесса.

- **Предотвращение регрессий**: Стабилизируют функциональность при каждом коммите.
- **Поддержка рефакторинга**: Дают уверенность при изменениях архитектуры и кода.
- **Документация поведения**: Тесты фиксируют контракт системы лучше неформальных описаний.
- **Управление рисками**: Освещают критические сценарии до развертывания.

### Quality Gates: лучшие практики 2025–2026

**Quality Gates** должны быть:

- **Автоматизированными**: Никаких ручных проверок — только скрипты
- **Быстрыми**: Блокирующие проверки не должны замедлять пайплайн
- **Измеримыми**: Чёткие метрики (покрытие >80%, 0 критических уязвимостей)
- **Прозрачными**: Разработчик сразу видит причину провала

**Типичные ворота качества:**

| Ворота | Критерий | Инструменты |
|---|---|---|
| **Lint** | 0 ошибок линтера | ruff, ESLint, golangci-lint |
| **Unit-тесты** | 100% passing, покрытие >80% | pytest, Jest, JUnit |
| **SAST** | 0 critical/high уязвимостей | SonarQube, Semgrep |
| **SCA** | 0 уязвимостей в зависимостях | Dependabot, Snyk |
| **Интеграционные тесты** | 100% passing | Testcontainers, pytest |
| **E2E-тесты** | Критические сценарии passing | Playwright, Cypress |

### Распределение тестов по этапам пайплайна

Эффективность достигается за счёт правильного выбора типов тестов для каждого этапа. Подробное описание видов тестов находится в файле **[Виды тестов: Unit, Integration, E2E](./testing_types_unit_integration_e2e.md)**.

| Этап pipeline | Типы тестов | Цель |
|---|---|---|
| **Pre-commit** (локально) | Lint, быстрые unit | Мгновенный фидбек разработчику |
| **Build/CI** (при коммите) | Unit, статический анализ | Базовая корректность и качество кода |
| **Test Stage** | Интеграционные, компонентные | Валидность взаимодействий между модулями |
| **Pre-deploy** (staging) | E2E, smoke, UI-тесты | Проверка релиз-кандидата в среде, близкой к production |
| **Post-deploy** | Канареечные проверки, синтетические тесты | Верификация в реальной среде после развертывания |

## Практические сценарии

### Базовая структура пайплайна в GitLab CI

```yaml
stages:
  - lint
  - test
  - package
  - deploy
  - verify

lint:
  stage: lint
  script:
    - ruff check .
  allow_failure: false

unit_tests:
  stage: test
  script:
    - pytest tests/unit --junitxml=reports/junit.xml
  artifacts:
    reports:
      junit: reports/junit.xml

integration_tests:
  stage: test
  needs: ["unit_tests"]
  services:
    - name: postgres:15
      alias: db
  script:
    - pytest tests/integration
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule" || $CI_COMMIT_BRANCH == "main"'

e2e_tests:
  stage: verify
  needs: ["deploy_staging"]
  script:
    - ./tests/e2e/smoke.sh https://staging.example.com
```

Этот пример показывает, как быстрые тесты (lint, unit) запускаются на каждом шаге, а более долгие (интеграционные, e2e) — только на ключевых этапах.

## Дополнительная информация

### Борьба с flaky-тестами: современные практики 2025–2026

**Flaky-тесты** — тесты, которые показывают разные результаты без изменений кода.

**Стратегии борьбы:**

| Стратегия | Описание | Когда применять |
|---|---|---|
| **Фиксированные seed** | Детерминированные случайные данные | Тесты с рандомизацией |
| **Изоляция зависимостей** | Testcontainers, моки | Внешние сервисы |
| **Явные ожидания** | Wait-for вместо sleep() | Асинхронные операции |
| **Ретраи с лимитом** | 1–3 повторения при flaky | Временные проблемы сети |
| **Карантин тестов** | Изоляция flaky в отдельный пайплайн | Хронически нестабильные тесты |
| **Таймауты** | Ограничение времени выполнения | Зависшие тесты |

**Инструменты:**

- **pytest-rerunfailures** — автоматические ретраи для pytest
- **flaky** — декоратор для нестабильных тестов
- **GitLab CI retry** — `retry: { max: 2, when: [runner_system_failure] }`

### Надёжность и метрики

- **Данные для тестов**: Предпочитайте детерминированные фикстуры, фабрики и эфемерные окружения на базе контейнеров.
- **Метрики качества**:
  - Длительность конвейера и MTTR для «красных» сборок.
  - Доля падений по типам тестов.
  - Уровень ложных срабатываний.
  - **[Тестовое покрытие](./testing_coverage_metrics.md)** по критическим путям.
- **Отчётность**: Результаты тестов сохраняются в виде артефактов, как описано в **[Инструменты для генерации отчётов](./testing_reporting_tools.md)**.
