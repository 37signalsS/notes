# Интеграция автоматизированных тестов в CI/CD

## Определения

- **Quality Gates (Ворота качества)** — автоматические проверки в пайплайне CI/CD (Continuous Integration / Continuous Deployment — непрерывная интеграция и непрерывное развёртывание), которые определяют возможность перехода сборки на следующий этап.
- **Shift-left Testing** — подход, подразумевающий перенос тестирования на максимально ранние этапы жизненного цикла разработки для снижения стоимости исправления дефектов.
- **Shift-right Testing** — расширение тестирования на среду эксплуатации (production) через канареечные развёртывания, A/B-тестирование и мониторинг для получения полной картины качества.
- **Flaky-тесты (Нестабильные тесты)** — тесты, которые показывают разные результаты (успех или падение) при неизменном коде и окружении.

## Основные концепции

### Роль автоматизированных тестов в CI/CD

Встраивание тестов в конвейер обеспечивает механизм непрерывной обратной связи, превращая качество в измеряемый показатель процесса разработки.

- **Предотвращение регрессий**: стабилизация функциональности при каждом внесении изменений.
- **Поддержка рефакторинга**: обеспечение уверенности при изменении архитектуры.
- **Документирование поведения**: тесты выступают в роли актуального контракта системы.
- **Управление рисками**: автоматическая верификация критических сценариев до выпуска релиза.

### Ворота качества: лучшие практики

**Ворота качества (Quality Gates)** должны соответствовать следующим критериям:

- **Автоматизация**: исключение ручных проверок в блокирующих этапах.
- **Скорость**: быстрые проверки для минимизации времени ожидания разработчика.
- **Измеримость**: наличие чётких порогов (например, покрытие кода >80%, отсутствие критических уязвимостей).
- **Информативность**: прозрачные причины провала для быстрого исправления.

| Уровень | Критерий прохождения | Инструменты |
| :--- | :--- | :--- |
| **Lint (Анализ стиля)** | 0 ошибок линтера | ruff, ESLint, golangci-lint |
| **Unit-тесты** | 100% пройдено, покрытие >80% | pytest, Jest, JUnit |
| **SAST (Статический анализ безопасности)** | 0 критических уязвимостей | SonarQube, Semgrep |
| **SCA (Анализ сторонних зависимостей)** | Отсутствие уязвимых библиотек | Dependabot, Snyk |
| **Интеграционные тесты** | Успешное взаимодействие компонентов | Testcontainers, pytest |
| **E2E (Сквозные тесты)** | Работоспособность ключевых сценариев | Playwright, Cypress |

### Распределение тестов по этапам пайплайна

Эффективность тестирования достигается за счёт гранулярного распределения проверок. Детальное описание типов проверок приведено в документе **[Виды тестирования](./testing_types_unit_integration_e2e.md)**.

| Этап пайплайна | Типы тестов | Цель |
| :--- | :--- | :--- |
| **Pre-commit** (локально) | Lint, быстрые Unit-тесты | Мгновенная обратная связь разработчику |
| **Build/CI** (при коммите) | Unit, статический анализ (SAST) | Базовая корректность и безопасность кода |
| **Test Stage** | Интеграционные, компонентные тесты | Проверка взаимодействия между модулями |
| **Pre-deploy** (staging) | E2E, Smoke-тесты, UI-тестирование | Проверка релиз-кандидата в среде, близкой к реальной |
| **Post-deploy** | Канареечные проверки, синтетические тесты | Верификация в реальной среде эксплуатации |

## Практические сценарии

### Пример конфигурации пайплайна в GitLab CI

```yaml
stages:
  - lint
  - test
  - package
  - deploy
  - verify

lint_job:
  stage: lint
  script:
    - ruff check .
  allow_failure: false

unit_tests:
  stage: test
  script:
    - pytest tests/unit --junitxml=reports/junit.xml
  artifacts:
    reports:
      junit: reports/junit.xml

integration_tests:
  stage: test
  needs: ["unit_tests"]
  services:
    - name: postgres:15
      alias: db
  script:
    - pytest tests/integration
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule" || $CI_COMMIT_BRANCH == "main"'

e2e_tests:
  stage: verify
  needs: ["deploy_staging"]
  script:
    - ./tests/e2e/smoke.sh https://staging.example.com
```

В данном примере линтинг и модульные тесты запускаются при каждом изменении, а тяжёлые интеграционные и сквозные тесты — по расписанию или при слиянии в основную ветку.

## Дополнительная информация

### Стратегии борьбы с нестабильными тестами

Для минимизации влияния **Flaky-тестов** используются следующие подходы:

| Стратегия | Описание | Сфера применения |
| :--- | :--- | :--- |
| **Детерминизм данных** | Использование фиксированных сидов (seed) | Рандомизированные тесты |
| **Изоляция окружения** | Использование эфемерных контейнеров | Тесты с внешними зависимостями (БД, очереди) |
| **Явные ожидания** | Замена `sleep()` на проверку состояния | Асинхронные операции и UI-тесты |
| **Ограниченные повторы** | 1–3 автоматических перезапуска (retry) | Временные сетевые сбои |
| **Карантин** | Изоляция нестабильных тестов в отдельный поток | Хронически нестабильные сценарии |

**Рекомендуемые инструменты:**

- **pytest-rerunfailures** — плагин для автоматических повторов в pytest.
- **GitLab CI retry** — встроенный механизм перезапуска задач пайплайна.

### Надёжность и метрики качества

- **Управление тестовыми данными**: Рекомендуется использовать эфемерные окружения на базе **[Testcontainers](./testcontainers_overview.md)** или **[Docker Compose](../Docker/Docker_compose/docker_compose_ci_cd_testing.md)**.
- **Ключевые метрики**:
  - **MTTR (Mean Time To Recovery — среднее время восстановления)** — время от падения пайплайна до его восстановления.
  - **Тестовое покрытие** — визуализация полноты проверок, описанная в **[Метриках покрытия](./testing_coverage_metrics.md)**.
  - **Длительность пайплайна** — критический фактор скорости доставки.
- **Отчётность**: Генерация и хранение результатов описаны в **[Инструментах отчётности](./testing_reporting_tools.md)**.
- **Методологии**: Взаимосвязь тестов с процессами разработки приведена в обзоре **[TDD и BDD](../CI-CD/Testing/tdd_bdd_overview.md)**.
- **Инфраструктурные тесты**: Проверка ролей Ansible с помощью Molecule описана в **[руководстве по Molecule](../Ansible/ansible_testing_with_molecule.md)**.
