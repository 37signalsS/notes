# Тестовое покрытие и метрики

## Концепция тестового покрытия

Тестовое покрытие — количественная метрика, показывающая, какая часть исполнимого кода была выполнена во время прогона тестов. Она не отражает качество тестов напрямую, но помогает обнаруживать «слепые зоны», где изменения не подкреплены проверками. Важно отличать покрытие от процента пройденных тестов: первый измеряет, где тесты выполнялись, второй — каков их результат.

## Виды покрытия

Разные метрики отвечают на разные вопросы и зачастую используются совместно.

| Тип покрытия | Что измеряет | Где полезно |
|--------------|--------------|-------------|
| Строк (Line) | Доля строк, достигнутых тестами | Базовая оценка широты тестов |
| Ветвей (Branch) | Доля возможных ветвлений if/else/switch, покрытых тестами | Логика условий и обработка крайних случаев |
| Функций/Методов | Доля вызываемых функций | Сервисные/библиотечные уровни |
| Инструкций | Доля исполнимых операторов | Языки/инструменты со сложной оптимизацией |
| Путей | Доля уникальных путей исполнения | Критичные алгоритмы, но вычислительно дорого |
| Мутационное (доп.) | Доля «убитых» искусственных мутаций кода тестами | Сила проверок, дополнение к классическому покрытию |

Для большинства проектов достаточно сочетания Line + Branch, дополняя мутационным анализом в риск-ориентированных компонентах.

## Отчётность о покрытии

Отчёты создаются инструментами профилирования и используются в локальной разработке и в CI/CD. Принято генерировать:

- Читаемый интерактивный HTML-отчёт для навигации по файлам и подсветки непокрытых участков
- Машиночитаемые отчёты для агрегации и проверок в пайплайне: XML-форматы Cobertura или JaCoCo, а также lcov.info

### Типовые связки инструментов

- **Java/Kotlin**: JaCoCo (XML, HTML)
- **JavaScript/TypeScript**: Istanbul/nyc (lcov, HTML)
- **Python**: coverage.py / pytest-cov (XML, HTML)
- **Go**: go test -coverprofile (profiling file, последующая конвертация в HTML)
- **C/C++**: gcov + lcov (lcov.info, HTML)

### Практика в CI

- Публикование HTML как артефактов сборки
- Экспорт XML/lcov для автоматических проверок и визуализации трендов
- Слияние отчётов из параллельных джобов и разных уровней тестов (unit/integration/e2e)
- Контроль порогов: блокировка merge при падении ниже заданного значения или при регрессии относительно основной ветки
- Дифф-покрытие: фокус на строках, изменённых в ревью

## Пример: генерация и публикация покрытия

### Локальный прогон с контролем порога (Python)

```bash
pip install pytest pytest-cov
pytest -q \
  --cov=app --cov-branch \
  --cov-report=xml:coverage.xml \
  --cov-report=html \
  --cov-fail-under=80
```

### Интеграция в GitLab CI с публикацией артефактов и машинного отчёта

```yaml
stages: [test]

test:coverage:
  image: python:3.11
  stage: test
  script:
    - pip install pytest pytest-cov
    - pytest --cov=app --cov-branch --cov-report=xml:coverage.xml --cov-report=html --cov-fail-under=80
  artifacts:
    when: always
    reports:
      cobertura: coverage.xml
    paths:
      - htmlcov/
    expire_in: 7 days
```

## Нюансы применения

- Не все файлы равнозначны: имеет смысл исключать сгенерированный код, миграции, модели данных без логики
- Порог должен быть реалистичным и пересматриваться по мере роста покрытия; часто используют разные пороги для новых изменений и для всего репозитория
- Слияние отчётов требует одинаковых путей к исходникам и совместимых форматов
- Высокое покрытие не гарантирует обнаружение дефектов: качество проверок улучшается за счёт осмысленных ассершенов, вариативности входных данных и мутационного анализа
- В монорепозиториях полезны отчёты по модулям и дифф-покрытие для ускорения обратной связи
