# Подпись артефактов

## Определения

*   **Подпись артефактов (Artifact Signing):** Криптографический процесс, который обеспечивает проверяемое доказательство происхождения (аутентичность) и целостности программных артефактов (двоичные файлы, контейнерные образы, SBOM).
*   **Аутентичность (Authenticity):** Гарантия того, что артефакт был создан доверенным субъектом (например, разработчиком или CI/CD-системой).
*   **Целостность (Integrity):** Гарантия того, что артефакт не был изменен с момента его подписи.

## Основные концепции

Подпись артефактов — это один из столпов [безопасности цепочки поставок](./overview.md). Она позволяет выстраивать политики допуска, автоматически блокируя развертывание неподписанных или подделанных артефактов.

### Модели подписи
*   **Классическая (GPG/PKI):** Разработчик или система самостоятельно управляет долгоживущими приватными ключами. Требует сложной инфраструктуры для управления ключами.
*   **"Безключевая" (Keyless) с OIDC (Sigstore):** Наиболее современный подход для CI/CD. Используются одноразовые, короткоживущие сертификаты, выданные на основе OIDC-идентичности (например, от GitHub Actions). Запись о подписи публикуется в публичный, неизменяемый лог (Rekor), что делает операцию общедоступной и проверяемой.

### Инструменты
| Инструмент            | Область применения                | Модель ключей              |
| --------------------- | --------------------------------- | -------------------------- |
| **Cosign (Sigstore)** | Контейнеры, файлы, аттестации     | Keyless (OIDC) или ключи   |
| **Notary v2/notation**| Контейнерные образы               | PKI/сертификаты            |
| **GPG/Minisign**      | Файлы, Git-теги                   | Управляемые вручную ключи  |

## Практические сценарии

### Подпись контейнерного образа в CI/CD (Keyless)
Этот сценарий идеален для автоматизированных систем, так как не требует управления статическими секретами.
```bash
# 1. Подписываем образ, используя OIDC-токен от GitHub Actions
cosign sign --keyless ghcr.io/my-org/my-app:v1.0.0

# 2. Проверяем подпись, указывая, что мы ожидаем подпись от конкретного репозитория
cosign verify --keyless \
  --certificate-identity-regexp "https://github.com/my-org/my-repo/.github/workflows/release.yml" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  ghcr.io/my-org/my-app:v1.0.0
```

### Подпись релизного тега в Git с GPG
```bash
# Создание подписанного тега
git tag -s v1.0.0 -m "Release v1.0.0"

# Проверка подписи тега
git verify-tag v1.0.0
```

### Политика допуска в Kubernetes (Kyverno)
Эта политика будет блокировать создание подов, если их образы не подписаны доверенным источником.
```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: check-image-signature
spec:
  validationFailureAction: Enforce
  rules:
  - name: verify-image
    match:
      resources:
        kinds: ["Pod"]
    verifyImages:
    - image: "ghcr.io/my-org/my-app:*"
      keyless:
        issuer: "https://token.actions.githubusercontent.com"
        subjectRegExp: ".*" # Уточнить для production
```

## Дополнительная информация

### Рекомендации
*   **Предпочитайте Keyless:** Для CI/CD всегда используйте "безключевую" модель подписи (OIDC), чтобы избежать управления секретами.
*   **Подписывайте все:** Подписывайте не только образы, но и SBOM, аттестации, Helm-чарты и другие важные артефакты.
*   **Проверяйте везде:** Проверка подписей должна быть обязательным шагом в CI/CD перед развертыванием и на стороне кластера с помощью политик допуска.
*   **Изолируйте среду:** Процесс подписи должен выполняться в защищенной и изолированной среде.
