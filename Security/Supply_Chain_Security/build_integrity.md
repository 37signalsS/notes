# Build Integrity

## Definitions

* **Reproducible Build:** Процесс, при котором из одинаковых входных данных (исходный код, версии зависимостей, инструменты) всегда получается бит-в-бит идентичный артефакт.
* **Hermetic Build:** Сборка, выполняемая в изолированной среде без неконтролируемого доступа к сети. Все зависимости заранее загружены и верифицированы.
* **Provenance (Аттестация происхождения):** Подписанные метаданные о процессе сборки: что собрано, из какого кода, какими инструментами, в какой среде. Формализовано в [SLSA](https://slsa.dev/).
* **SLSA (Supply-chain Levels for Software Artifacts):** Фреймворк стандартов для обеспечения целостности и безопасности артефактов на всех этапах цепочки поставок. Подробнее — в [обзоре Supply Chain Security](./overview.md).

## Basic Concepts

Контроль целостности сборки гарантирует, что разворачиваемый артефакт соответствует исходному коду, прошёл все проверки и не был подменён. Ключевой элемент [безопасности цепочки поставок](./overview.md).

### Ключевые подходы

| Подход | Цель | Преимущества |
| :--- | :--- | :--- |
| **Хеш-суммы** | Проверка неизменности файла | Простота и универсальность |
| **Подписи** | Подтверждение автора и целостности | Криптографическая неотказуемость. Подробнее — в [подписи артефактов](./artifact_signing.md) |
| **Provenance-аттестации** | Доказуемое происхождение сборки | Полная трассируемость цепочки |
| **Воспроизводимость** | Выявление недетерминизма и подмен | Бит-в-бит идентичность при повторных сборках |

### Уровни SLSA (кратко)

Уровни SLSA формализованы в [обзоре Supply Chain Security](./overview.md#уровни-slsa-сводная-таблица). Ключевые для Build Integrity:

| Уровень | Требование | Защита от |
| :--- | :--- | :--- |
| **SLSA 1** | Документированный процесс сборки | Случайных ошибок |
| **SLSA 2** | Использование hosted build-системы, provenance | Несанкционированных изменений |
| **SLSA 3** | Герметичная сборка, изолированная среда | Подмены зависимостей, вредоносных изменений |
| **SLSA 4** | Двухэтапная верификация, воспроизводимость | Компрометации сборочной инфраструктуры |

## Practical Scenarios

### Фиксация версий и хешей зависимостей

Закрепляйте версии и хеши, чтобы избежать неожиданных обновлений.

```dockerfile
# Базовый образ по дайджесту
FROM python@sha256:1f2a3b...c9d
```

```bash
# Проверка хеша загруженной зависимости
expected_sha="3b7c..."
file="lib.tar.gz"
actual_sha=$(sha256sum "$file" | awk '{print $1}')
[ "$expected_sha" != "$actual_sha" ] && { echo "Checksum mismatch!"; exit 1; }
```

### Обеспечение воспроизводимости сборки

Устранение источников недетерминизма: время, случайные числа, различия файловых систем.

```bash
# Reproducible build для Go
export CGO_ENABLED=0
export SOURCE_DATE_EPOCH=$(date +%s)
go build -trimpath -buildvcs=false -ldflags="-w -s" .
```

Флаги:

* `-trimpath` — удаляет локальные пути из бинарника
* `-buildvcs=false` — исключает VCS-метаданные
* `SOURCE_DATE_EPOCH` — стандартизирует метку времени сборки

### Герметизация сборочной среды

Ограничение сетевого доступа во время сборки для предотвращения загрузки неконтролируемых зависимостей.

* **Docker BuildKit:** Сборка без сети через `--network=none` (требует предварительной загрузки зависимостей).
* **GitHub Actions:** Использование инструментов контроля трафика, таких как **[Harden-Runner](../../Github_CI/network-security.md)**, для мониторинга и блокировки несанкционированных внешних соединений.

```dockerfile
# Docker BuildKit: сборка без сети
RUN --network=none pip install --no-index --find-links=./wheels -r requirements.txt
```

### Генерация и подпись SLSA Provenance-аттестации

BuildKit автоматически генерирует provenance-аттестации, соответствующие [SLSA](https://slsa.dev/):

```bash
# Сборка с provenance и SBOM
docker buildx build \
  --tag my-registry/my-app:v1.0.0 \
  --provenance=true \
  --sbom=true \
  --push \
  .
```

Аттестации подписываются и прикрепляются к манифесту образа. Верификация — через [Cosign](../Tools/sigstore.md):

```bash
# Проверка provenance-аттестации
cosign verify-attestation --type=slsaprovenance my-registry/my-app:v1.0.0
```

### Подпись и верификация артефакта

```bash
# Подпись образа (keyless в CI/CD)
cosign sign --yes my-registry/app:v1.0.0

# Верификация перед развёртыванием
cosign verify my-registry/app:v1.0.0
```

## Additional Information

### Рекомендации

* **Исходный код:** Используйте подписанные Git-теги для релизов.
* **Зависимости:** Фиксируйте версии в lock-файлах (`package-lock.json`, `go.sum`). Используйте `npm ci` вместо `npm install` в CI/CD — подробнее в [анализе зависимостей и SBOM](./dependency_and_sbom_analysis.md#безопасная-установка-зависимостей-в-cicd-npm-ci-вместо-npm-install). Для Node.js в Dockerfile — [лучшие практики Node.js](../../Docker/Dockerfile/Docker_best_practices/nodejs.md).
* **Сборка:** Стремитесь к герметичным и воспроизводимым сборкам. Генерируйте и подписывайте provenance-аттестации.
* **Артефакты:** Храните подписи и SBOM рядом с артефактами. Подписывайте образы через [Sigstore/Cosign](../Tools/sigstore.md), фиксируйте базовые образы по дайджесту — [подпись Docker-образов](../../Docker/Docker_security/image_signature_and_verification.md).
* **Развёртывание:** Проверяйте подписи через admission-политики (Kyverno, Gatekeeper) — примеры в [подписи артефактов](./artifact_signing.md).
