# Целостность сборки

## Определения

* **Build Integrity (Целостность сборки):** Свойство процесса сборки, гарантирующее, что выходной артефакт точно соответствует исходному коду и не подвергался несанкционированным изменениям.
* **Reproducible Build (Воспроизводимая сборка):** Методология, при которой из идентичных исходных данных (код, зависимости, инструменты) всегда создается бит-в-бит идентичный артефакт. Позволяет сторонним аудиторам подтвердить отсутствие "закладок".
* **Hermetic Build (Герметичная сборка):** Сборка, выполняемая в полностью изолированной среде без доступа к сети. Все зависимости (библиотеки, компиляторы) должны быть предоставлены внутри среды и верифицированы по хеш-суммам.
* **SLSA (Supply-chain Levels for Software Artifacts):** Фреймворк безопасности (v1.1/v2.0), определяющий уровни зрелости цепочки поставок. В 2026 году разделен на треки: **Build Track** (защита процесса сборки) и **Source Track** (защита исходного кода).
* **Provenance (Аттестация происхождения):** Машиночитаемые метаданные (обычно в формате in-toto), описывающие процесс создания артефакта. Содержит ссылки на исходный код, параметры сборки и использованные инструменты.
* **VSA (Verification Summary Attestation):** Высокоуровневая аттестация, создаваемая верификатором. Позволяет потребителям проверять соответствие уровню SLSA без необходимости анализировать сложные детали сырой провинанс-информации.

## Основные концепции

Обеспечение целостности сборки направлено на защиту от атак типа "компрометация сборочного узла" (Build Node Compromise) и "инъекция зависимостей".

### Ключевые практики защиты

| Практика | Назначение | Реализация |
| :--- | :--- | :--- |
| **Изоляция среды** | Предотвращение влияния внешних факторов и утечек данных | Контейнеризация, микро-ВМ, эфемерные раннеры |
| **Фиксация входов** | Гарантия использования доверенных версий кода и библиотек | Фиксация по SHA-256 (pinning by digest), lock-файлы |
| **Аттестация (Provenance)** | Доказательство того, что артефакт собран в доверенном пайплайне | Генерация аттестаций через SLSA-генераторы (Tekton Chains, slsa-github-generator) |
| **Двухэтапная верификация** | Разделение процессов сборки и проверки | Использование VSA для подтверждения комплаенса перед деплоем |

### Уровни SLSA Build Track (v1.1)

1.  **Уровень 1:** Сборка задокументирована. Наличие аттестации (Provenance).
2.  **Уровень 2:** Сборка в Hosted-среде. Аттестация подписана сервисом (защита от подмены пользователем).
3.  **Уровень 3:** Герметичность и изоляция. Защита от компрометации сборочной инфраструктуры.
4.  **Уровень 4 (v2.0 Roadmap):** Полная воспроизводимость и использование доверенных аппаратных модулей (TPM/HSM) для подписи.

## Практические сценарии

### Настройка герметичной сборки в Docker

Использование BuildKit позволяет минимизировать внешние зависимости.

```dockerfile
# 1. Фиксация базового образа по дайджесту
FROM python@sha256:4a080808a8080808080808080808080808080808080808080808080808080808 AS builder

WORKDIR /app
# 2. Предварительная загрузка зависимостей (vendor или wheels)
COPY ./vendor /app/vendor

# 3. Сборка без доступа к сети
RUN --network=none pip install --no-index --find-links=/app/vendor my-package
```

### Генерация аттестаций в GitHub Actions

Использование официальных генераторов OpenSSF для достижения SLSA Level 3.

```yaml
jobs:
  build:
    outputs:
      hashes: ${{ steps.hash.outputs.hashes }}
    steps:
      - name: Build artifact
        run: |
          # Сборка вашего проекта
          echo "artifact_data" > build/app.bin
      - name: Generate hashes
        id: hash
        run: |
          echo "hashes=$(sha256sum build/app.bin | base64 -w0)" >> "$GITHUB_OUTPUT"

  provenance:
    needs: [build]
    permissions:
      actions: read
      id-token: write
      contents: write
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@v2.0.0
    with:
      base64-subjects: "${{ needs.build.outputs.hashes }}"
      upload-assets: true
```

### Верификация VSA перед развертыванием

В 2026 году корпоративные политики требуют проверки не только подписи, но и VSA через admission-контроллеры.

```bash
# Верификация артефакта через верификатор, выдающий VSA
# Верификатор проверяет SLSA L3 и подписывает результат
cosign verify-vsa \
  --vsa-issuer="https://verifier.corp.local" \
  --attestation-type="https://slsa.dev/verification_summary/v1" \
  my-registry.com/my-app:v1.0.0
```

## Дополнительная информация

### Защита от новых угроз (2026)

*   **AI-Agent PRs:** С развитием ИИ-ассистентов в разработке (Agentic Development) критически важным стало обязательное ревью кода, сгенерированного ИИ. Целостность сборки должна включать проверку того, что в бинарный файл попал только код, прошедший валидацию человеком (или доверенным ИИ-цензором).
*   **AI/ML Model Integrity:** Веса моделей и наборы данных должны рассматриваться как сборочные артефакты. Для них генерируется **Model-Provenance**, фиксирующая параметры обучения и подписываемая через Sigstore.

### Рекомендации по внедрению

1.  **Shift Left:** Начинайте с фиксации зависимостей (lock-файлы) и использования базовых образов по дайджесту.
2.  **Автоматизация аттестаций:** Внедрите автоматическую генерацию SLSA Provenance в CI/CD.
3.  **Централизованная наблюдаемость:** Интегрируйте данные о сборках в системы типа **GUAC** для анализа графа зависимостей.
4.  **Политики допуска:** Используйте Kyverno или OPA для блокировки деплоя артефактов, не соответствующих целевому уровню SLSA.
