# Контроль целостности на этапах сборки

Контроль целостности в цепочке поставки ПО — это набор практик, предотвращающих незаметное изменение исходного кода, зависимостей, инструментов сборки и итоговых артефактов. На этапах сборки основная цель — гарантировать, что артефакт воспроизводим из доверенного источника, собран в предсказуемой среде и снабжен проверяемыми доказательствами происхождения.

## Определения

*   **Хеш-сумма**: криптографический отпечаток содержимого файла, используемый для проверки неизменности.
*   **Цифровая подпись**: криптографическое подтверждение авторства и целостности артефакта.
*   **Аттестация (provenance)**: структурированная метаинформация о процессе сборки (кто, чем, когда и из чего собирал).
*   **Воспроизводимая сборка (Reproducible Build)**: процесс, при котором из одинаковых входных данных и среды получается бит-идентичный артефакт.
*   **Герметичная сборка (Hermetic Build)**: сборка, выполняемая в изолированной среде без сетевого доступа и без недекларированных зависимостей.

## Основные концепции

### Ключевые подходы и их роль

| Подход           | Цель                               | Где применяется              | Преимущества                    | Ограничения                  |
| ---------------- | ---------------------------------- | ---------------------------- | ------------------------------- | ---------------------------- |
| Хеш-суммы        | Проверка неизменности              | Зависимости, артефакты       | Простота                        | Не подтверждает происхождение |
| Подписи          | Подтверждение автора и целостности | Коммиты, теги, образы        | Криптографическая привязка      | Управление ключами           |
| Аттестации       | Доказуемое происхождение           | CI/CD, реестры               | Полная трассируемость           | Интеграции инструментов      |
| Воспроизводимость | Детерминизм сборки                 | Сборочные среды              | Выявление подмен                | Требует дисциплины в настройках |

## Практические сценарии

### Практики по этапам

*   **Исходный код**:
    *   Использование подписанных тегов и политик допуска только проверенных коммитов.
    *   Закрепление конфигураций сборки в репозитории, включая версии инструментов.

*   **Зависимости**:
    *   Фиксация версий и хешей (lock-файлы, checksums).
    *   Использование разрешённых источников и зеркал, периодическая ревальвация хешей.
    *   Вендоринг критичных библиотек при необходимости.

*   **Сборка**:
    *   **Герметичность**: отключение сетевого доступа, разрешение только объявленных входов.
    *   **Детерминизм**: установка переменных среды и флагов компиляторов для устранения недетерминизма.
    *   Запись аттестации: кто/что/чем собирал, идентификаторы входов и инструмента.

*   **Артефакты**:
    *   Контент-адресуемые имена (по хешу).
    *   Подпись артефактов и контейнерных образов.
    *   Генерация и подпись SBOM, связывание с артефактом.

### Примеры техник

**Проверка хеша загруженной зависимости:**
```bash
expected_sha256="3b7c1f..."; file="lib.tar.gz"
actual_sha256=$(sha256sum "$file" | awk '{print $1}')
test "$expected_sha256" = "$actual_sha256"
```

**Закрепление базового образа по дайджесту в Dockerfile:**
```sql
FROM python@sha256:1f2a...c9d
```

**Детерминизм сборки (пример для компиляции Go):**
```bash
export SOURCE_DATE_EPOCH=1700000000
export TZ=UTC
go build -trimpath -buildvcs=false -ldflags="-w -s" ./cmd/app
```

**Подпись и проверка контейнерного образа по дайджесту:**
```perl
# Подпись образа по дайджесту
cosign sign my-registry.example.com/app@sha256:ab12...

# Проверка подписи и соответствия дайджесту
cosign verify my-registry.example.com/app@sha256:ab12...
```

**Сетевые ограничения в задаче сборки (герметичность):**
```nginx
# Запрет исходящих соединений во время сборки
iptables -P OUTPUT DROP
# Разрешить локальные обращения к кэшу пакетов
iptables -A OUTPUT -d 127.0.0.1 -j ACCEPT
```

**Проверка соответствия образа ожидаемому дайджесту в CI:**
```bash
expected="sha256:ab12..."
actual=$(skopeo inspect docker://my-registry.example.com/app:build | jq -r '.Digest')
test "$expected" = "$actual"
```

## Дополнительная информация

### Рекомендации по хранению доказательств

*   Сохранять хеши, подписи и аттестации рядом с артефактами в реестре/репозитории.
*   Версионировать схемы аттестаций и включать идентификаторы инструментов сборки.
*   Разделять права: сборка, подпись и публикация выполняются разными субъектами, ключи и токены изолированы.
