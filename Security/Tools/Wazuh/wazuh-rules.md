# Правила корреляции и обнаружения в Wazuh

## Определения

**Корреляция событий (Event Correlation)** — процесс сопоставления и анализа потока событий в режиме реального времени для выявления логических связей и сложных атак, которые невозможно обнаружить при анализе одиночных событий. В **Wazuh 5.0+** корреляция трансформирована в систему генерации находок (**Findings**), обогащенную данными из глобальной базы угроз.

**Движок детектирования (Detection Engine 5.0)** — гибридная система Wazuh, поддерживающая как классический XML-синтаксис правил, так и нативный формат **Sigma (YAML)** для описания логики обнаружения угроз.

**Маппинг MITRE ATT&CK** — процесс автоматического сопоставления правил с тактиками и техниками атак. В 2026 году Wazuh обеспечивает нативную поддержку **MITRE ATT&CK v16+** с автоматическим обновлением через облачный сервис **Wazuh CTI**.

**Finding (Находка)** — структурированный объект безопасности в Wazuh 5.0+, генерируемый правилом при срабатывании. В отличие от классического Alert, Finding содержит обогащенные контекстные данные и статус жизненного цикла (new, in_progress, resolved, false_positive).

**Rule Level (Уровень серьезности)** — числовой атрибут правила (0–16), определяющий приоритет алерта. Уровень 0–3 служит для информационных событий, 4–6 — низкий, 7–10 — средний, 11–14 — высокий, 15–16 — критический. Уровень 0 с атрибутом `noalert="1"` используется для группировки событий без генерации алерта.

## Основные концепции

### Эволюция правил в Wazuh 5.0 (2026)

Версия 5.0 привносит фундаментальные изменения в процесс описания и обработки угроз:

1.  **Нативная поддержка Sigma**: Wazuh теперь напрямую выполняет правила в формате Sigma (`.yml`). Это позволяет использовать общемировое сообщество правил обнаружения без предварительной конвертации в XML.
2.  **YAML-декодеры**: На смену сложным XML-декодерам пришли иерархические YAML-конфигурации, которые проще в поддержке и поддерживают высокопроизводительный парсинг через регулярные выражения **PCRE2**.
3.  **Findings вместо Alerts**: Правила теперь генерируют структурированные объекты безопасности. События без алертов ("Non-alerted events") остаются видимыми в системе по умолчанию, что упрощает ретроспективный анализ и поиск угроз (**Threat Hunting**).
4.  **Wazuh CTI Streaming**: Правила могут ссылаться на динамические списки индикаторов компрометации (IP, домены, хеши), которые доставляются в менеджер в реальном времени из облака Wazuh.

### Жизненный цикл правила

Понимание lifecycle критично для управления изменениями в production-среде:

1.  **Создание (Draft)**: Правило описывается в локальном файле `local_rules.xml` или директории `sigma/`. Используется уникальный ID из зарезервированного диапазона (100000–299999 для хостов, 300000+ для облака).
2.  **Тестирование**: Валидация через `wazuh-logtest` (XML) или `sigma-checker` (YAML) на сырых логах без перезапуска менеджера.
3.  **Code Review**: Изменения проходят через Pull Request с проверкой на дублирование ID, корректность синтаксиса и соответствие политикам организации.
4.  **Деплой**: Применение через GitOps-пайплайн (Ansible, CI/CD) с атомарной валидацией и rolling restart.
5.  **Мониторинг**: Отслеживание частоты срабатываний (FP rate) через Dashboard "Detection Quality" и внешние системы мониторинга.
6.  **Тюнинг или деактивация**: При высокой доле ложных срабатываний правило корректируется или помечается `disabled="yes"`. Устаревшие правила архивируются с сохранением истории в Git.

### Синтаксис XML-правил

Каждое правило состоит из набора тегов и атрибутов, определяющих условия срабатывания и действия:

**Ключевые атрибуты:**
- `id` — уникальный идентификатор правила. Должен быть уникальным в рамках всего ruleset. Используйте диапазоны: 100000–299999 для кастомных хостовых правил, 300000+ для облака.
- `level` — уровень серьезности (0–16). Определяет приоритет алерта.
- `frequency` — количество срабатываний за интервал `timeframe` (в секундах) для генерации алерта. Используется в корреляционных правилах.
- `timeframe` — окно времени в секундах для подсчета `frequency`.
- `noalert` — если `"1"`, событие группируется, но не генерирует алерт. Используется для parent-правил.
- `overwrite` — если `"yes"`, позволяет переопределить стандартное правило из ruleset.
- `disabled` — если `"yes"`, правило отключено без удаления.

**Основные теги:**
- `<if_sid>` — ссылка на ID родительского или группирующего правила. Правило срабатывает, если предшествующее событие соответствует указанному SID.
- `<if_matched_sid>` — ссылка на ID коррелирующего правила. Правило срабатывает на событии, которое уже было сопоставлено с указанным SID в рамках того же timeframe.
- `<match>` / `<regex>` — текстовое условие срабатывания. `<match>` ищет точную подстроку, `<regex>` поддерживает PCRE2.
- `<same_source_ip>` — корреляция по IP источника. Правило срабатывает только если все предшествующие события в timeframe имеют одинаковый `srcip`.
- `<same_user>` — корреляция по пользователю. Используется для идентификации атак от одного субъекта.
- `<same_field>` — корреляция по произвольному полю (например, `aws.requestID`, `session_id`).
- `<field>` — проверка значения именованного поля, извлеченного декодером. Пример: `<field name="srcip">10.0.0.5</field>`.
- `<list>` — проверка значения по CDB-списку (whitelist/blacklist). Атрибуты: `field` (поле для проверки), `lookup` (`match_key` или `match_value`), `srcip` (опционально).
- `<description>` — описание правила, отображаемое в алерте и Dashboard.
- `<mitre>` — блок маппинга MITRE ATT&CK. Содержит теги `<id>` (техника) и `<tactic>` (тактика).
- `<group>` — категоризация правила для фильтрации и комплаенса. Пример: `<group>authentication_failures,pci_dss_10.2.4,</group>`.
- `<decoded_as>` — привязка правила к конкретному декодеру.
- `<program_name>` — фильтрация по названию программы, записавшей лог.
- `<ignore>` — на уровне правила: если событие соответствует `<ignore>`, правило не срабатывает.

### Типы условий и корреляция

*   **Частота (`frequency`)**: Количество срабатываний за интервал времени (`timeframe`).
*   **Логическое сопоставление**:
    *   `same_source_ip` / `same_user`: Идентификация атак от одного субъекта.
    *   `same_field`: Совпадение любого кастомного поля (например, `client_id` или `request_id`).
*   **Sigma Logic (NEW)**: Возможность использования сложной булевой логики (`selection`, `condition`, `filter`) непосредственно в YAML-правилах.

### Структура и расположение файлов

С переходом на Wazuh 5.0 пути нормализованы:
*   **Стандартные (Ruleset)**: `/var/wazuh-manager/ruleset/rules/` — системные правила, обновляемые через CTI.
*   **Пользовательские (Local)**: `/var/wazuh-manager/etc/rules/local_rules.xml` — приоритетное место для XML-правил.
*   **Sigma-правила**: `/var/wazuh-manager/etc/rules/sigma/` — директория для YAML-правил обнаружения.

**Приоритет загрузки:**
1.  Системные правила из `ruleset/rules/` (низкий приоритет).
2.  Пользовательские правила из `local_rules.xml` (высокий приоритет). Правила с одинаковым ID из `local_rules.xml` переопределяют системные.
3.  Sigma-правила из `sigma/` загружаются параллельно и имеют приоритет выше XML при совпадении логики.

### CDB-списки и интеграция с правилами

CDB (Constant DataBase) — высокопроизводительные файлы для мгновенного поиска по ключу. Используются для создания белых и черных списков. Логика загрузки и приоритеты описаны в [Автоматизация Wazuh через Ansible](./ansible-automation-per-agent.md).

**Пример использования `<list>` в правиле:**
```xml
<rule id="100005" level="10">
  <if_matched_sid>100001</if_matched_sid>
  <list field="process.name" lookup="match_key">etc/lists/agents/web-01-known-apps</list>
  <description>Запущен неизвестный процесс на web-01</description>
</rule>
```

### Правила и Active Response

Правила являются триггерами для автоматизированного реагирования. Привязка выполняется через блок `<active-response>` в `ossec.conf`:
```xml
<active-response>
  <command>firewall-drop</command>
  <location>local</location>
  <rules_id>5720,5760</rules_id>
  <timeout>600</timeout>
</active-response>
```

## Практические сценарии

### 1. Иерархия правил (на примере SSH)

Логика обнаружения часто строится каскадно:

**Шаг А: Группировка (уровень 0)**
Фильтрует все события от конкретного сервиса (`sshd`).
```xml
<rule id="5700" level="0" noalert="1">
  <decoded_as>sshd</decoded_as>
  <description>SSHD messages grouped.</description>
</rule>
```

**Шаг Б: Одиночное событие (уровень 5)**
Детектирует факт неудачной аутентификации, ссылаясь на родительскую группу и подтехнику MITRE.
```xml
<rule id="5716" level="5">
  <if_sid>5700</if_sid>
  <match>^Failed|^error: PAM: Authentication</match>
  <description>sshd: authentication failed.</description>
  <mitre>
    <id>T1110.001</id> <!-- Brute Force: Password Guessing -->
  </mitre>
</rule>
```

**Шаг В: Корреляция по частоте (уровень 10)**
Генерирует критический алерт (Finding) при 5 неудачных попытках с одного IP за 360 секунд.
```xml
<rule id="5720" level="10" frequency="5" timeframe="360">
  <if_matched_sid>5716</if_matched_sid>
  <same_source_ip />
  <description>sshd: Multiple authentication failures.</description>
</rule>
```

### 2. Пример Sigma-правила (YAML)

В Wazuh 5.0 Sigma-правила позволяют описывать логику, которую сложно реализовать в XML (например, проверку нескольких полей с оператором `OR`).

**Файл:** `/var/wazuh-manager/etc/rules/sigma/suspicious_powershell.yml`
```yaml
title: Suspicious PowerShell Download
status: experimental
description: Detects PowerShell downloading content via Net.WebClient
logsource:
    product: windows
    service: powershell
detection:
    selection:
        EventID: 4104
        ScriptBlockText|contains:
            - 'Net.WebClient'
            - 'DownloadFile'
            - 'DownloadString'
    condition: selection
falsepositives:
    - Administrative scripts
level: high
```

### 3. Переопределение (Overwrite) правил

В Wazuh 5.0 при переопределении стандартных правил используйте тег `overwrite="yes"`. Помните, что пути к системным правилам теперь содержат `wazuh-manager`.

1.  Скопируйте оригинал из `/var/wazuh-manager/ruleset/rules/` в `/var/wazuh-manager/etc/rules/local_rules.xml`.
2.  Добавьте атрибут `overwrite="yes"`.

**Сценарий: Повышение уровня серьезности для Brute-force**
```xml
<rule id="5760" level="13" overwrite="yes">
  <if_sid>5700,5716</if_sid>
  <match>Failed password|Failed keyboard|authentication error</match>
  <description>sshd: authentication failed. Critical alert for Telegram/Zabbix.</description>
</rule>
```

### 4. Использование same_field для корреляции по request ID

Для корреляции событий по идентификаторам запросов в JSON-логах:
```xml
<rule id="100002" level="10" frequency="10" timeframe="60">
  <if_matched_sid>100001</if_matched_sid>
  <same_field>aws.requestID</same_field>
  <description>Rate limit exceeded for a specific AWS Request ID</description>
</rule>
```

### 5. Detection as Code: CI/CD пайплайн для правил

В крупных инфраструктурах ручное редактирование `local_rules.xml` ведет к операционным ошибкам. Решение — внедрение pipeline для управления правилами:

**Этапы пайплайна:**
1.  **Lint**: Проверка синтаксиса XML (`xmllint`) и Sigma (`sigma-checker`).
2.  **Unit Test**: Запуск `wazuh-logtest` с эталонными логами в Docker-контейнере.
3.  **ID Registry Check**: Верификация уникальности ID через скрипт, парсящий `local_rules.xml`.
4.  **Staging Deploy**: Деплой на тестовый менеджер, проверка `alerts.log`.
5.  **Canary**: Применение к 1–5% production-агентов через `agent.conf` группы.
6.  **Full Rollout**: Mass deployment после успешного canary.

**Пример GitLab CI этапа:**
```yaml
detect-rules:
  image: python:3.11
  script:
    - xmllint --noout rules/local_rules.xml
    - python3 scripts/sigma_checker.py rules/sigma/
    - python3 scripts/id_registry_check.py rules/local_rules.xml
    - docker run --rm -v $PWD/rules:/rules wazuh/wazuh-logtest:latest /test-logs/
  only:
    - merge_requests
```

### 6. Управление ложными срабатываниями (False Positives)

Снижение FP rate — ключевая задача SRE. Подход:

1.  **Классификация FP**: Разделите FP на категории:
    *   **Whitelisting**: Легитимная активность, которая должна игнорироваться. Решение: CDB-списки или `<ignore>` в правилах.
    *   **Tuning**: Порог срабатывания слишком чувствительный. Решение: повышение `level`, добавление дополнительных условий (`<field>`, `<same_user>`).
    *   **Noise**: Избыточные события от инфраструктурных процессов. Решение: `<ignore>` на уровне декодера или правила.
2.  **Мониторинг**: Используйте Dashboard "Detection Quality" или запросы к Indexer для выявления правил с FP rate > 20%.
3.  **Процесс**: Создание тикета, описание FP, обновление правила, ревью, деплой.

**Пример: добавление исключения для легитимного сканера:**
```xml
<rule id="5716" level="5">
  <if_sid>5700</if_sid>
  <match>^Failed|^error: PAM: Authentication</match>
  <description>sshd: authentication failed.</description>
  <mitre>
    <id>T1110.001</id>
  </mitre>
  <list field="srcip" lookup="match_key">etc/lists/scanners-ips</list>
</rule>
```

### 7. Резервное копирование и версионирование правил

Храните все пользовательские правила и Sigma-конфигурации в Git-репозитории. Минимальный backup включает:

- `/var/wazuh-manager/etc/rules/local_rules.xml`
- `/var/wazuh-manager/etc/rules/sigma/`
- `/var/wazuh-manager/etc/lists/` (CDB-списки)
- `/var/wazuh-manager/etc/decoders/local_decoder.xml` (если используются кастомные декодеры)

**Восстановление после сбоя:**
```bash
# Клонирование репозитория
git clone git@gitlab.company.com:security/wazuh-rules.git /tmp/rules-restore

# Копирование правил
sudo cp /tmp/rules-restore/local_rules.xml /var/wazuh-manager/etc/rules/
sudo cp -r /tmp/rules-restore/sigma /var/wazuh-manager/etc/rules/
sudo cp -r /tmp/rules-restore/lists /var/wazuh-manager/etc/

# Валидация и перезапуск
sudo /var/wazuh-manager/bin/wazuh-logtest -t
sudo systemctl restart wazuh-manager
```

## Дополнительная информация

### Управление и отладка (Wazuh 5.0)

В 2026 году процессы тестирования и применения правил оптимизированы для поддержки гибридных форматов:
*   **Валидация XML**: Используйте `/var/wazuh-manager/bin/wazuh-logtest` для проверки логики срабатывания XML-правил и декодеров.
*   **Валидация Sigma**: Для проверки YAML-правил используйте встроенную утилиту `/var/wazuh-manager/bin/sigma-checker`. Она проверяет синтаксис и маппинг полей на схему данных Wazuh.
*   **Применение**: Требуется перезапуск менеджера для перечитывания конфигурации: `systemctl restart wazuh-manager`.
*   **Мониторинг FP**: Используйте дашборд "Detection Quality" для идентификации правил с аномально высокой частотой срабатываний (False Positives).

### Производительность и масштабирование

- **Количество правил**: Wazuh Manager 5.0 компилирует все правила в память при старте. Рекомендуется поддерживать общее количество правил (системные + кастомные) в пределах 10 000–15 000. При большем объеме используйте модульную загрузку через группы.
- **PCRE2 и `<prematch>`**: Всегда используйте `<prematch>` перед `<regex>`. Поиск подстроки в десятки раз быстрее компиляции регулярного выражения.
- **CDB vs Regex**: Для проверки 100+ значений (IP-списки, хеши) используйте CDB-списки. Поиск в CDB выполняется за O(1), regex — за O(n).
- **Корреляция по частоте**: Правила с `frequency` создают состояние в памяти. Избегайте больших `timeframe` (> 86400 секунд) и высоких `frequency` (> 50) на высоконагруженных менеджерах (> 5000 EPS).
- **Отключение неиспользуемых правил**: Используйте `disabled="yes"` вместо удаления строк. Это сохраняет ID и упрощает аудит.

### Troubleshooting

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Правило не срабатывает** | Неверный SID в `<if_sid>` или декодер не извлек поле | Проверьте `wazuh-logtest` для сырого лога. Убедитесь, что `<decoded_as>` соответствует декодеру. |
| **Ложный срабатывание (FP)** | Слишком широкое условие `<match>` или `<regex>` | Добавьте `<field>` для уточнения контекста. Используйте CDB-список для исключения легитимных источников. |
| **Конфликт ID** | Дублирование `id` в `local_rules.xml` и `ruleset/rules/` | Используйте `overwrite="yes"` для переопределения, или выделите уникальный ID из диапазона 100000+. |
| **Корреляция не работает** | Неверный `timeframe` или события пришли от разных `srcip` | Проверьте логику `same_source_ip`. Убедитесь, что события имеют одинаковый `srcip` в указанном окне. |
| **Sigma-правило игнорируется** | Неверный `logsource` или отсутствует маппинг полей | Проверьте `sigma-checker`. Убедитесь, что `product` и `service` соответствуют декодеру Wazuh. |
| **Высокий CPU на Manager** | Слишком много regex-правил или большие `timeframe` | Переведите тяжелые проверки в CDB-списки. Уменьшите `timeframe`. Используйте `<prematch>`. |
| **Ruleset не обновляется после деплоя** | Отсутствует перезапуск `wazuh-manager` | Проверьте статус: `systemctl status wazuh-manager`. Перезапустите: `systemctl restart wazuh-manager`. |
| **Алерты дублируются** | Два правила с разными ID детектируют одно событие | Объедините логику в одно правило или используйте `noalert="1"` для parent-правила. |

### Ограничения и edge cases

*   **Глубина корреляции**: Цепочки из более чем 3 правил (`if_sid` → `if_matched_sid` → `if_matched_sid`) могут терять контекст из-за ограничений буфера событий в движке. Для сложных сценариев используйте одно правило с несколькими условиями.
*   **Timeframe и часовые пояса**: `timeframe` считается в секундах от времени первого события в цепочке. При несинхронизированном времени между агентом и менеджером корреляция может давать сбои. Используйте NTP.
*   **Regex и PCRE2**: Движок PCRE2 чувствителен к регистру. Используйте флаг `(?i)` для игнорирования регистра. Избегайте жадных квантификаторов `.*` в конце строки — используйте `.*?`.
*   **Ограничение `noalert`**: Правила с `noalert="1"` не видны в стандартном алертинге, но их события остаются в индексе. Для поиска используйте фильтр `data.rule.id: 5700`.
*   **Sigma и кастомные поля**: Sigma-правила не поддерживают пользовательские поля Wazuh (`srcip`, `dstuser`), если они не маппятся на стандартные поля лога. Проверяйте маппинг через `sigma-checker`.

### Best Practices

1.  **Диапазоны ID**: Выделите резервные блоки ID для каждого компонента инфраструктуры:
    *   100000–199999: XML-правила хостов
    *   200000–299999: Кастомные правила приложений
    *   300000–399999: Облачные правила
    *   400000+: Экспериментальные (Sigma)
2.  **Приоритет декодера перед правилом**: Никогда не пишите regex-правило для сырого лога, если можно написать декодер. Декодер извлекает поля один раз, правило использует их многократно.
3.  **Минимизация regex**: Избегайте сложных regex с lookahead/lookbehind в высоконагруженных правилах. Используйте `<prematch>` + простой `<regex>`.
4.  **CDB для статических списков**: Все IP-списки, хеши файлов и имена пользователей (> 20 значений) храните в CDB, а не в `<field>value</field>`.
5.  **Атомарность деплоя**: Всегда валидируйте правила через `wazuh-logtest` перед перезапуском менеджера. Ошибка в одном XML-файле может привести к отказу запуска.
6.  **Документация изменений**: Каждое правило в `local_rules.xml` должно содержать комментарий с датой, автором и ссылкой на тикет/INCIDENT.
7.  **Мониторинг**: Настройте алерты на падение количества правил после деплоя (сравнение `count(local_rules.xml)` vs ожидаемого).
8.  **Ротация CA и правил**: При обновлении инфраструктуры (например, ротации IP) своевременно обновляйте CDB-списки и правила с жесткими привязками к `srcip`.
