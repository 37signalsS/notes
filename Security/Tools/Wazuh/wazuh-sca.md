# Оценка конфигурации безопасности (SCA) в Wazuh

## Определения

**Wazuh SCA (Security Configuration Assessment)** — это ключевой модуль платформы Wazuh, предназначенный для непрерывного мониторинга и оценки защищенности конечных точек (Endpoints) и облачных ресурсов. В версии **Wazuh 5.0+** модуль трансформирован в полноценный инструмент управления состоянием безопасности (**Posture Management**), обеспечивающий проверку соответствия стандартам харденинга (CIS Benchmarks), нормативным требованиям (PCI-DSS, NIST, GDPR) и внутренним политикам организации.

**CSPM (Cloud Security Posture Management)** — расширение возможностей SCA для аудита облачных инфраструктур (AWS, Azure, GCP) и сред оркестрации (Kubernetes) через прямую интеграцию с Cloud API.

**Политика SCA (SCA Policy)** — декларативный файл в формате YAML, содержащий набор проверок (checks), критериев оценки и метаданных для анализа конфигурации хоста или сервиса.

**Сканирование (Scan)** — процесс оценки конфигурации агента против загруженных политик SCA. Результатом является набор passed/failed/not-applicable статусов для каждого правила.

**Дельта-сканирование (Delta Scan)** — в Wazuh 5.0+ агент отправляет на менеджер только изменения результатов по сравнению с предыдущим сканированием, что снижает сетевую нагрузку и объем индексации.

**Baseline SCA** — эталонное состояние конфигурации, зафиксированное после успешного прохождения всех проверок политики. Используется для детекции дрейфа (configuration drift).

**Наследование политик (Policy Inheritance)** — механизм распространения политик через группы (`shared` группы и `agent.conf`), при котором агенты автоматически получают политики, соответствующие их групповой принадлежности и требованиям `requirements`.

**Индекс SCA** — набор индексов в OpenSearch/Wazuh Indexer (по умолчанию `wazuh-states-sca`), где хранятся результаты сканирований. Управление жизненным циклом индексов выполняется через ISM (Index State Management).

## Основные концепции

### Архитектура и принцип работы (Wazuh 5.0+)

В современных версиях Wazuh процесс SCA оптимизирован для работы в высоконагруженных средах и гибридных облаках:

1.  **Единая кластерная архитектура**: В 5.0 отсутствует разделение на режимы работы; подсистема кластера активна всегда, что обеспечивает мгновенную синхронизацию состояний SCA между всеми узлами менеджера.
2.  **Сканирование и Delta-отчетность**: Агент Wazuh выполняет локальные проверки и отправляет на сервер только изменения (**diff**) по сравнению с предыдущим сканированием. Это минимизирует сетевой трафик и нагрузку на базу данных (индексатор на базе **OpenSearch 3.x**).
3.  **Контроль целостности политик**: Сервер отслеживает хеш-суммы файлов политик на агентах. При любом изменении файла (или его обновлении через `shared` группы) автоматически инициируется полный перескан для предотвращения расхождения данных.
4.  **Событийная модель (Event-driven Assessment)**: В отличие от старых версий, SCA 5.0 ориентирован на поток событий изменений. Каждое отклонение от политики генерирует алерт в реальном времени, что позволяет использовать SCA для детекции дрейфа конфигурации (**Configuration Drift**).

### Жизненный цикл SCA-сканирования

Понимание lifecycle критично для диагностики и оптимизации:

1.  **Загрузка политик (Manager)**: При старте `wazuh-modulesd` менеджер сканирует каталоги `/var/ossec/etc/shared/*/sca/` и `/var/ossec/etc/sca/`, вычисляет хеши политик и распределяет их по зарегистрированным агентам с учетом групповой принадлежности и секции `requirements`.
2.  **Применение политик (Agent)**: Агент получает список применимых политик. Если `scan_on_start` включен, первое сканирование запускается сразу после подключения. В противном случае — по интервалу `interval`.
3.  **Локальная оценка (Agent)**: Для каждого правила в политике агент выполняет локальную проверку: чтение файлов, выполнение команд (`c:`), проверку процессов (`p:`), анализ реестра Windows (`r:`). Результат записывается в локальный кэш.
4.  **Дельта-отправка (Agent → Manager)**: На следующем цикле отправки агент сравнивает текущие результаты с кэшем и передает только изменившиеся статусы.
5.  **Индексация и сопоставление (Manager)**: Менеджер сохраняет результаты в OpenSearch Indexer, обновляет агрегированные статусы политик и генерирует события `sca` при изменении состояния с `failed` на `passed` или наоборот.
6.  **Визуализация и оповещение (Wazuh Dashboard / Indexer)**: Данные становятся доступны в дашборде, доступны для запросов и могут триггерить Active Response или внешние системы мониторинга.

### Механики оценки и интервалы

- **`scan_on_start`** (`yes/no`): запуск полного сканирования сразу после старта агента или применения новой политики. Рекомендуется `yes` для критически важных хостов, чтобы не ждать первого интервального скана.
- **`interval`**: период между сканированиями (например, `12h`, `1d`). Более частые интервалы увеличивают нагрузку на CPU агента и сеть; слишком редкие — замедляют детекцию дрейфа. Для production-хостов рекомендуется диапазон `12h–24h`, для критических инфраструктур — `6h`.
- **`condition`**: определяет логику оценки политики (`all`, `any`, `none`). Значение `all` является наиболее строгим и подходит для комплаенса; `any` — для сбора инвентаря; `none` — для проверки отсутствия нежелательных состояний.
- **`requirements`**: пре-фильтр. Если условия не выполнены (например, отсутствует `/etc/ssh/sshd_config`), политика пропускается entirely и все проверки получают статус `not applicable`. Это позволяет использовать универсальные политики для гетерогенных сред.

### Хранение результатов и retention

- Результаты SCA хранятся в OpenSearch/Wazuh Indexer. По умолчанию используется индекс `wazuh-states-sca`.
- В Wazuh 5.0 для управления жизненным циклом индексов применяется **ISM (Index State Management)**: настройте политику ISM для автоматического перехода в warm/cold/delete фазы. Например, retention в 90 дней для hot-индекса с последующим удалением.
- При миграции с 4.x на 5.0 обратите внимание: структура индексов SCA изменилась, поэтому старая история не мигрирует автоматически. Архивируйте индексы 4.x перед обновлением, если они нужны для аудита.

### Облачная безопасность (Cloud-Native SCA)

С 2026 года Wazuh SCA поддерживает проверку активов, не имеющих установленного агента:
*   **Agentless Cloud Audit**: Проверка настроек S3-корзин, IAM-политик и сетевых групп через интеграцию с API провайдеров.
*   **Kubernetes Control Plane**: Нативный аудит API-сервера, etcd и манифестов пода на соответствие CIS Kubernetes Benchmark.
*   **Контейнерный аудит**: Оценка безопасности Docker-демона и конфигураций образов в Runtime.

### Анатомия SCA-политики

Любая политика состоит из четырех основных секций:

| Секция | Обязательна? | Описание |
| :--- | :--- | :--- |
| **`policy`** | Да | Паспорт политики: `id`, название, описание, ссылки на стандарты. |
| **`requirements`** | Нет | Условия запуска: если требования не выполнены, сканирование не начнется. |
| **`variables`** | Нет | Переменные (например, `$sshd_config`) для упрощения путей. |
| **`checks`** | Да | Список самих проверок (самый объемный блок). |

### Синтаксис правил

Формула правила: `ТИП:ЛОКАЦИЯ -> ОПЕРАТОР:ЗНАЧЕНИЕ`

**Типы проверок:**
- `f:` — файл (существование или содержимое). Пример: `f:/etc/ssh/sshd_config`.
- `d:` — директория (рекурсивная проверка!). Пример: `d:/etc/ssh/sshd_config.d`.
- `p:` — процесс (проверка факта запуска). Пример: `p:nc -l`.
- `c:` — вывод команды. Пример: `c:sshd -T`.
- `r:` — реестр Windows. Пример: `r:HKEY_LOCAL_MACHINE\...\LimitBlankPasswordUse`.

**Операторы проверки контента:**
- `(без оператора)` — точное совпадение строки.
- `r:` — регулярное выражение (PCRE2). Пример: `r:^Ciphers\s+chacha20-poly1305`.
- `n:` — числовое сравнение. Пример: `n:^MaxAuthTries\s+(\d+) compare <= 4`.
- `!` или `not` — отрицание. Пример: `!r:MD5` или `not f:/bad/file`.
- `&&` — логическое И (цепочки условий). Пример: `!r:^# && r:Port && r:22`.

*Важно: пробелы вокруг `->`, `&&` и `compare` являются обязательными.*

### Логика оценки (Condition)

| condition | Все правила Passed | Есть Failed | Есть Not applicable | Итог |
| :--- | :--- | :--- | :--- | :--- |
| **`all`** | Да | Нет | Нет | **Passed** |
| **`all`** | — | Да | — | **Failed** |
| **`all`** | — | Нет | Да | **Not applicable** |
| **`any`** | Да | — | — | **Passed** |
| **`any`** | Нет | Да | Нет | **Failed** |
| **`any`** | Нет | — | Да | **Not applicable** |
| **`none`** | Нет | Да | — | **Passed** |
| **`none`** | Да | — | — | **Failed** |

## Практические сценарии

### 1. Кастомная политика SSH Hardening

Этот пример объединяет проверку файла на диске и реальной конфигурации в памяти для защиты от «дрейфа конфигурации» (configuration drift).

```yaml
policy:
  id: "ssh_hardening"
  file: "sca_ssh_hardening.yml"
  name: "SSH Hardening Configuration Assessment"
  description: "Аудит SSH по стандартам CIS и NIST."

requirements:
  title: "Требования для запуска"
  condition: any
  rules:
    - 'c:which sshd'
    - 'f:/etc/ssh/sshd_config'

variables:
  $sshd_config: "/etc/ssh/sshd_config"

checks:
  - id: 200000
    title: "SSH: Ciphers настроены безопасно"
    rationale: "Использование слабых шифров может привести к MITM-атакам."
    remediation: "Добавьте в sshd_config: Ciphers chacha20-poly1305@openssh.com,... и перезапустите sshd."
    compliance:
      - cis: ["5.2.12"]
    condition: all
    rules:
      - 'f:$sshd_config -> r:^Ciphers\s+chacha20-poly1305@openssh.com,aes256-gcm@openssh.com'
      - 'c:sshd -T -> r:^ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com'
```

### 2. Аудит облачной инфраструктуры (AWS S3)

В Wazuh 5.0 SCA расширен для проверки манифестов и метаданных облачных ресурсов через интеграцию `wazuh-modulesd`.

```yaml
policy:
  id: "aws_s3_compliance"
  file: "sca_aws_s3.yml"
  name: "AWS S3 Security Posture Assessment"

checks:
  - id: 300001
    title: "S3: Публичный доступ запрещен"
    description: "Проверка BlockPublicAccess для всех корзин."
    condition: all
    rules:
      # Проверка через вывод облачного модуля Wazuh
      - 'c:wazuh-cloud-gatherer --provider aws --service s3 -> r:\"BlockPublicAcls\":\s*true'
```

### 3. Автоматизированное исправление (Remediation)

Wazuh 5.0 позволяет превратить SCA в активную систему защиты. При провале проверки с критическим ID можно инициировать скрипт исправления.

1.  **Настройка Active Response** (`ossec.conf`):
    ```xml
    <active-response>
      <command>fix-ssh-ciphers</command>
      <location>local</location>
      <rules_id>200000</rules_id> <!-- ID правила SCA -->
    </active-response>
    ```
2.  **Результат**: При обнаружении слабого шифра Wazuh автоматически применит эталонный конфиг и перезапустит сервис.

### 4. Централизованное управление политиками

Для масштабного развертывания в Wazuh 5.0 используется концепция **Configuration as Code**:
1.  **На сервере**: Разместите `.yml` в `/var/ossec/etc/shared/<group_name>/`.
2.  **В `agent.conf` группы**:
    ```xml
    <agent_config>
      <sca>
        <enabled>yes</enabled>
        <scan_on_start>yes</scan_on_start>
        <interval>12h</interval>
        <policies>
          <policy>etc/shared/sca_ssh_hardening.yml</policy>
        </policies>
      </sca>
    </agent_config>
    ```
3.  **Важно**: В 5.0 необходимо убедиться, что менеджер имеет права на чтение файлов в `etc/shared/` для корректной генерации контрольных сумм.

### 5. Локальное тестирование и отладка

Перед массовым деплоем используйте режим отладки:
1.  Запустите проверку вручную: `/var/ossec/bin/wazuh-modulesd -f -d`.
2.  Используйте `sca_check` (если доступно в вашей сборке) для валидации синтаксиса YAML.
3.  Проверьте `ossec.log` на наличие записей `sca: DEBUG:`.

### 6. Предварительная валидация и откат политик

Перед применением политики к production-группе агентов выполните:

1.  **Синтаксис YAML**: Проверьте файл через `python3 -c "import yaml; yaml.safe_load(open('policy.yml'))"` или `yamllint`.
2.  **Локальный тест на одном агенте**: Скопируйте политику в `/var/ossec/etc/shared/test-group/sca/`, добавьте тестового агента в группу `test-group` и проверьте `ossec.log` на ошибки парсинга.
3.  **Ожидаемые результаты**: В логе должны появиться записи `sca: INFO: Policy '<name>' loaded successfully` и `sca: INFO: Scan finished`.
4.  **Откат**: В случае проблем удалите политику из `shared` группы или отключите SCA в `agent.conf`:
    ```xml
    <sca>
      <enabled>no</enabled>
    </sca>
    ```
5.  **Сброс кэша результатов**: Если требуется форсировать полное пересканирование после отката, удалите локальный кэш на агенте (путь зависит от версии, обычно `/var/ossec/queue/sca/` или перезапустите агент).

### 7. Управление политиками через Ansible (Detection as Code)

Для соблюдения принципа Infrastructure as Code храните политики в репозитории и развертывайте их через Ansible:

```yaml
- name: Deploy Wazuh SCA policy
  hosts: wazuh_manager
  tasks:
    - name: Ensure SCA policy directory exists
      file:
        path: /var/ossec/etc/shared/linux_servers/sca
        state: directory
        owner: wazuh
        group: wazuh
        mode: '0750'

    - name: Copy SCA policy
      copy:
        src: policies/sca_ssh_hardening.yml
        dest: /var/ossec/etc/shared/linux_servers/sca/sca_ssh_hardening.yml
        owner: wazuh
        group: wazuh
        mode: '0640'

    - name: Restart wazuh-modulesd to apply policy hash
      service:
        name: wazuh-modulesd
        state: restarted
      when: wazuh_sca_policy_changed | default(false)

    - name: Verify policy loaded
      command: /var/ossec/bin/wazuh-control status
      register: wazuh_status
      changed_when: false
```

**Важно**: После копирования политики менеджер должен перечитать конфигурацию. Перезапуск `wazuh-modulesd` гарантирует обновление хеш-сумм. Для больших кластеров используйте rolling restart, чтобы избежать потери событий.

### 8. Интеграция с внешним мониторингом

Для интеграции SCA с Zabbix, Prometheus или другими системами мониторинга используйте Wazuh REST API или запросы к Indexer.

**Пример: получение количества failed-проверок через API (Wazuh 5.x):**

```bash
curl -k -u admin:admin https://wazuh-manager:55000/sca/<agent_id>?status=failed
```

**Пример: запрос к OpenSearch для Prometheus-экспортера:**

```json
GET /wazuh-states-sca-*/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "agent.id": "001" }},
        { "term": { "data.sca.check.status": "failed" }}
      ]
    }
  },
  "aggs": {
    "by_policy": {
      "terms": { "field": "data.sca.policy.name.keyword" }
    }
  }
}
```

На основе этих данных настройте alerts в Grafana или Zabbix triggers.

### 9. Практические политики для Sysadmin/DevOps/SRE

#### 9.1 Аудит параметров sysctl (kernel hardening)

```yaml
policy:
  id: "sysctl_hardening"
  file: "sca_sysctl_hardening.yml"
  name: "Sysctl Kernel Hardening"
  description: "Проверка ключевых параметров ядра."

requirements:
  condition: any
  rules:
    - 'f:/etc/sysctl.conf'
    - 'd:/etc/sysctl.d'

variables:
  $sysctl_cmd: "sysctl -a"

checks:
  - id: 201000
    title: "IPv4 forwarding отключен"
    compliance:
      - cis: ["3.1.1"]
    condition: all
    rules:
      - 'c:$sysctl_cmd -> n:^net.ipv4.ip_forward\s+=\s+0 compare == 0'

  - id: 201001
    title: "Защищенные симлинки включены"
    compliance:
      - cis: ["3.4.2"]
    condition: all
    rules:
      - 'c:$sysctl_cmd -> n:^fs.protected_symlinks\s+=\s+1 compare == 1'
```

#### 9.2 Аудит опций монтирования (noexec, nosuid, nodev)

```yaml
policy:
  id: "mount_options"
  file: "sca_mount_options.yml"
  name: "Filesystem Mount Options"
  description: "Проверка безопасности точек монтирования /tmp и /var/tmp."

checks:
  - id: 202000
    title: "/tmp смонтирован с noexec,nosuid,nodev"
    condition: all
    rules:
      - 'c:findmnt -n -o OPTIONS /tmp -> r:noexec'
      - 'c:findmnt -n -o OPTIONS /tmp -> r:nosuid'
      - 'c:findmnt -n -o OPTIONS /tmp -> r:nodev'

  - id: 202001
    title: "/home смонтирован с noexec (если применимо)"
    condition: any
    rules:
      - '!c:findmnt -n -o TARGET /home'
      - 'c:findmnt -n -o OPTIONS /home -> r:noexec'
```

#### 9.3 Аудит политик паролей

```yaml
policy:
  id: "password_policy"
  file: "sca_password_policy.yml"
  name: "Password Aging Policy"
  description: "Проверка параметров устаревания паролей."

requirements:
  condition: any
  rules:
    - 'f:/etc/login.defs'
    - 'f:/etc/default/useradd'

checks:
  - id: 203000
    title: "PASS_MAX_DAYS <= 90"
    condition: all
    rules:
      - 'c:grep ^PASS_MAX_DAYS /etc/login.defs -> n:(\d+) compare <= 90'

  - id: 203001
    title: "PASS_MIN_DAYS >= 1"
    condition: all
    rules:
      - 'c:grep ^PASS_MIN_DAYS /etc/login.defs -> n:(\d+) compare >= 1'
```

#### 9.4 Аудит cron-заданий и сервисов

```yaml
policy:
  id: "cron_and_services"
  file: "sca_cron_services.yml"
  name: "Cron and Critical Services"
  description: "Проверка критических сервисов и планировщика."

checks:
  - id: 204000
    title: "sshd включен и запущен"
    condition: all
    rules:
      - 'p:sshd'
      - 'c:systemctl is-enabled sshd -> r:enabled'

  - id: 204001
    title: "Отсутствуют аномальные cron-задачи в /etc/cron.d"
    condition: all
    rules:
      - 'd:/etc/cron.d -> !r:^.*\s+.*\s+root\s+.*\s+&\s*$'
```

### 10. Troubleshooting

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| **SCA события не появляются в дашборде** | Политика не применена или `enabled=no` | Проверьте `agent.conf` группы и `ossec.log` на наличие `sca: INFO: Policy loaded`. |
| **Все проверки имеют статус `not applicable`** | Секция `requirements` не выполнена или `sca.remote_commands=0` | Установите `sca.remote_commands=1` в `local_internal_options.conf`; проверьте пути в `requirements`. |
| **Hash Mismatch (5.0+)** | Политика обновлена, но агент не переподключился | Перезапустите агент: `/var/ossec/bin/wazuh-control restart`. Для массового обновления используйте rolling restart. |
| **Ложные срабатывания из-за regex** | Неудачный паттерн `r:` или жадное отрицание `!r:` | Используйте явные positive-regex: `r:^Param\s+no` вместо `!r:Param`. Тестируйте паттерны через `pcre2test`. |
| **Высокая нагрузка на агент при сканировании** | Слишком большой интервал или слишком много политик | Увеличьте `interval` до `12h–24h`; разделите политики по критичности; исключите волатильные директории через `exclusions` (в 5.0+). |
| **Конфликт ID** | Дублирование `id` в разных политиках | Используйте диапазон ID 100000–299999 для кастомных правил хоста и 300000+ для облака. |
| **OpenSearch Mapping Error** | Шаблоны индексов устарели после обновления на 5.0 | Обновите шаблоны индексов через REST API или переустановите Wazuh Indexer. |
| **Политика не применяется к конкретному агенту** | Агент не в нужной группе или `requirements` фильтруют его | Проверьте группу агента в Wazuh Dashboard; выполните `agent-info` для просмотра присвоенных политик. |

## Дополнительная информация

### Чек-лист частых ошибок

| Ошибка | Последствия | Исправление |
| :--- | :--- | :--- |
| **`sca.remote_commands=0`** | Тип `c:` выдает Not applicable | Установить `=1` в `local_internal_options.conf` (глобально для агента). |
| **Hash Mismatch (5.0+)** | Старые результаты не очищаются | Убедитесь, что политика обновлена через `shared` группы; перезапустите агента для форсирования хеширования. |
| **OpenSearch 3.x Mapping** | Ошибки визуализации в дашборде | Проверьте `wazuh-indexer` на соответствие новой схеме данных 5.x; обновите шаблоны индексов. |
| **Жадное отрицание `!r:`** | Ложные срабатывания Passed | Использовать явные regex: `r:^Param\s+no` вместо `!r:Param`. |
| **Конфликт ID** | Ошибки при обновлении БД | Использовать диапазон ID 100000–299999 для кастомных правил хоста и 300000+ для облака. |

### Заметки по миграции (4.x -> 5.0)

При обновлении на Wazuh 5.0 учитывайте следующие аспекты:
*   **Данные**: Старая история SCA не мигрирует автоматически из-за смены структуры индексов. Рекомендуется архивировать старые индексы перед обновлением.
*   **Политики**: Формат YAML совместим, но рекомендуется проверить `requirements`, так как логика фильтрации по ОС стала более строгой.
*   **Синхронизация**: В 5.0 значительно снижена нагрузка на CPU при первом сканировании за счет улучшенного алгоритма сравнения состояний.
*   **Конфигурация**: В 5.0 объединены режимы `client` и `server` в единую кластерную архитектуру. Убедитесь, что `ossec.conf` не содержит устаревших параметров разделения ролей.
*   **Индексация**: Проверьте шаблоны индексов и политики ISM. Старые индексы `wazuh-sca` могут потребовать ручного удаления или реиндексации.

### Производительность и масштабирование

- **Разделение политик**: Не храните все проверки в одном файле. Разделите политики по доменам (SSH, sysctl, файловые системы, сервисы) и приоритетам (критический, стандартный, расширенный). Это позволяет назначать разные интервалы и уменьшает размер дельта-отчетов.
- **Интервалы сканирования**: Для инфраструктур >1000 агентов рекомендуется минимизировать количество одновременных сканирований. Используйте `jitter` (если поддерживается версией) или распределите интервалы внутри групп.
- **Исключения**: В больших средах избегайте рекурсивных проверок (`d:`) на директориях с высокой энтропией (`/tmp`, `/var/log`, `/run`). Используйте точечные проверки (`f:`) или перечисление конкретных файлов.
- **Мониторинг здоровья SCA**: Добавьте в observability stack метрики: количество политик на агенте, среднее время сканирования, процент failed-проверок. Можно получать через Wazuh API или парсинг `ossec.log`.

### Best Practices

- **Приоритет eBPF**: Для мониторинга системных вызовов и ядра предпочитайте eBPF-инструменты вместо полного сканирования файлов, где это возможно.
- **Защита diff для секретов**: Если политика проверяет наличие конфиденциальных параметров, убедитесь, что логи и дашборд не экспонируют значения (`rationale` и `remediation` должны содержать только рекомендации, а не фактические значения секретов).
- **Сегментация директорий**: Размещайте политики в `shared` группах по роли хостов (`web-servers`, `db-servers`, `workstations`), а не в едином глобальном каталоге.
- **Комплаенс**: Для проверки PCI DSS, GDPR и ФЗ-152 настройте SCA-политики в дополнение к FIM для полного покрытия требований к отслеживанию изменений.
- **Версионирование**: Храните политики SCA в Git с обязательным code review. Каждый коммит должен содержать описание добавленных/измененных проверок.
- **Тестирование**: Все изменения политик проходят через pipeline: lint YAML → тест на staging-агенте → canary-deployment на 1% production-хостов → полный rollout.
