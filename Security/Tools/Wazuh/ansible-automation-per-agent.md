# Автоматизация Wazuh: управление правилами и CDB-списками через Ansible

## Определения

**Пер-агентная конфигурация (Per-agent configuration)** — архитектурный подход в SIEM Wazuh, при котором для каждой конечной точки (агента) формируется индивидуальный набор правил и исключений на основе ее роли, запущенных сервисов и профиля нагрузки.

**CDB-списки (Constant DataBase)** — высокопроизводительные файлы константных данных в Wazuh, оптимизированные для мгновенного поиска по ключу. Являются основным инструментом создания белых списков (whitelists) для процессов, IP-адресов и пользователей.

**Rule ID Chunking (Чанкование ID)** — метод сегментации пространства идентификаторов правил (обычно в диапазоне 100,000+), при котором каждому агенту выделяется изолированный диапазон ID. Это исключает конфликты при централизованном управлении правилами в крупных инфраструктурах.

## Основные концепции

### Policy-driven подход к безопасности
Традиционное ручное редактирование XML-файлов на Wazuh Manager при масштабировании (200+ хостов) ведет к операционным ошибкам и коллизиям ID. Решение заключается в реализации концепции **Detection as Code**:

1.  **Декларативное описание (IaC)**: Все исключения (whitelists) описываются в YAML-файлах переменных Ansible (Inventory).
2.  **Централизованная сборка**: Wazuh Manager выступает точкой агрегации, где Ansible-контроллер динамически генерирует блоки в `ossec.conf` и фрагменты в `rules.xml`.
3.  **Изоляция и наследование**: Общие правила безопасности применяются ко всей группе хостов, а специфичные "умные" правила уточняют контекст для каждого конкретного агента.

### Архитектура решения

| Компонент | Роль в конвейере |
| :--- | :--- |
| **Ansible Inventory** | Источник правды (SSoT) для разрешенных приложений и сетевых доступов. |
| **ID Registry** | Реестр на менеджере (JSON), фиксирующий привязку `агент ↔ диапазон ID`. |
| **Wazuh Manager** | Выполняет финальную компиляцию правил и CDB-списков. |
| **GitOps Pipeline** | Обеспечивает версионирование правил и автоматический деплой после Pull Request. |

## Практические сценарии

### 1. Управление реестром Rule ID

Для автоматического выделения уникальных ID используется логика Ansible, проверяющая занятые блоки в реестре. Каждому агенту выделяется блок в 1000 ID.

```yaml
- name: "Выделение уникального диапазона ID"
  ansible.builtin.set_fact:
    rule_id_base: "{{ (free_bases | first | default(200000)) | int }}"
  vars:
    # _idreg — словарь из реестра менеджера вида { "hostname": 201000 }
    used_bases: "{{ (_idreg.values() | map('int') | list) }}"
    # Диапазон пользовательских правил от 200k до 999k
    all_bases: "{{ range(200000, 999000, 1000) | list }}"
    free_bases: "{{ (all_bases | difference(used_bases)) | sort }}"
```

### 2. Динамическая генерация CDB-списков

Списки создаются на основе переменных хоста и сохраняются в `/var/ossec/etc/lists/agents/`.

```yaml
- name: "Генерация CDB-списка разрешенных приложений"
  become: true
  ansible.builtin.copy:
    dest: "/var/ossec/etc/lists/agents/{{ wazuh_agent_name }}-known-apps"
    content: |
      {% for app in wazuh_agent_known_apps %}
      {{ app }}:
      {% endfor %}
    mode: "0644"
    owner: root
    group: wazuh
```

### 3. "Умные" правила с использованием наследования

Логика исключений строится на двух уровнях: базовое правило детектирует аномалию, а персональное — проверяет ее по индивидуальному белому списку.

**Общее правило (в `local_rules.xml`):**
```xml
<rule id="101001" level="3">
  <if_sid>221</if_sid> <!-- syscollector: процесс запущен -->
  <field name="type">dbsync_processes</field>
  <description>Обнаружен новый процесс в системе</description>
</rule>
```

**Шаблон персонального правила (Jinja2):**
```xml
<!-- Разрешение процесса из белого списка агента -->
<rule id="{{ rule_id_base + 100 }}" level="0">
  <if_sid>101001</if_sid>
  <hostname>{{ wazuh_agent_name }}</hostname>
  <list field="process.name" lookup="match_key">etc/lists/agents/{{ wazuh_agent_name }}-known-apps</list>
  <description>Легитимный процесс агента</description>
</rule>

<!-- Алерт для неизвестного процесса -->
<rule id="{{ rule_id_base + 101 }}" level="12">
  <if_sid>101001</if_sid>
  <hostname>{{ wazuh_agent_name }}</hostname>
  <description>КРИТИЧЕСКИЙ РИСК: Неизвестный процесс $(process.name) на хосте {{ wazuh_agent_name }}</description>
  <mitre><id>T1059</id></mitre>
</rule>
```

### 4. Деплой и атомарная валидация

Перед перезапуском менеджера Ansible должен убедиться в валидности сгенерированной конфигурации.

```yaml
- name: "Проверка синтаксиса правил Wazuh"
  ansible.builtin.command: "/var/ossec/bin/wazuh-logtest -t"
  register: logtest_result
  failed_when: logtest_result.rc != 0

- name: "Перезапуск Wazuh Manager при успехе"
  ansible.builtin.service:
    name: wazuh-manager
    state: restarted
  when: logtest_result.rc == 0
```

## Дополнительная информация

### Производительность CDB vs Regex
Использование CDB-списков значительно эффективнее регулярных выражений (`<field name="...">...`) при больших объемах данных. Поиск в CDB выполняется за константное время O(1), что критично при обработке потоков в 5000+ EPS.

### Интеграция с GitOps
Рекомендуется хранить все CDB-списки и шаблоны правил в Git. Пайплайны (GitLab CI/Jenkins) при каждом коммите должны запускать Ansible плейбук в режиме `--check`, а после слияния (Merge) выполнять деплой на Production-менеджеры.
