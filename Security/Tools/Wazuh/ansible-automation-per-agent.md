# Автоматизация Wazuh: управление правилами и CDB-списками через Ansible

## Определения

**Пер-агентная конфигурация (Per-agent configuration)** — подход в Wazuh, при котором для каждого агента (хоста) формируются уникальные наборы правил и списков константных данных (CDB), учитывающие специфику запущенных на нем сервисов и процессов.

**CDB-списки (Constant DataBase)** — файлы в Wazuh, оптимизированные для быстрого поиска по ключу. Используются для создания белых списков (whitelists) процессов, IP-адресов, пользователей и портов.

**Распределенные ID правил** — механизм выделения уникальных диапазонов идентификаторов для правил каждого агента, исключающий коллизии в рамках всей инфраструктуры.

## Основные концепции

Традиционное управление Wazuh на больших парках машин (200+) сталкивается с проблемой "ручной рутины" и рисками ошибок в XML-конфигурациях. Решение заключается в переходе к **Policy-driven подходу** через Ansible:

1.  **Декларативное описание**: Все исключения (whitelists) описываются в IaC (Ansible/Terraform).
2.  **Автоматическая сборка**: Менеджер Wazuh выступает точкой сборки, где Ansible динамически генерирует блоки в `ossec.conf` и фрагменты в `rules.xml`.
3.  **Изоляция ID**: Каждому агенту выделяется "чанк" (например, 1000 ID) в диапазоне пользовательских правил (200,000–999,999).

### Архитектура автоматизации

| Компонент | Роль в автоматизации |
| :--- | :--- |
| **Ansible Inventory** | Хранит переменные для каждого хоста (списки разрешенных приложений, IP и т.д.). |
| **Registry (ID Registry)** | JSON-файл на менеджере, фиксирующий привязку `имя_агента -> начальный_ID`. |
| **Wazuh Manager** | Принимает сгенерированные конфиги, CDB-списки и перезапускается для применения. |

## Практические сценарии

### 1. Выделение чанков ID для агентов

Чтобы правила разных агентов не конфликтовали, используется реестр ID. Таска Ansible проверяет наличие агента в реестре и выделяет первый свободный блок.

```yaml
- name: "Выделение диапазона ID для агента"
  ansible.builtin.set_fact:
    rule_id_base: "{{ (free_bases | first | default(200000)) | int }}"
  vars:
    used_bases: "{{ (_idreg.values() | map('int') | list) }}"
    all_bases: "{{ range(200000, 999999 - 1000 + 1, 1000) | list }}"
    free_bases: "{{ (all_bases | difference(used_bases)) | sort }}"
```

### 2. Генерация CDB-списков (Known-apps)

Списки формируются динамически для каждого агента и сохраняются в `/var/ossec/etc/lists/agents/`.

```yaml
- name: "Создание CDB-списка для агента"
  become: true
  ansible.builtin.copy:
    dest: "/var/ossec/etc/lists/agents/{{ wazuh_agent_name }}-known-apps"
    content: |
      {% for app in wazuh_agent_known_apps %}
      {{ app }}:
      {% endfor %}
    mode: "0644"
```

### 3. "Умные" правила для мониторинга процессов

Логика строится на наследовании: общее правило ловит все процессы, а персональное правило агента проверяет их по его уникальному CDB-списку.

**Базовое правило (общая конфигурация):**
```xml
<rule id="101001" level="3">
  <if_sid>221</if_sid> <!-- syscollector event -->
  <field name="type">dbsync_processes</field>
  <list field="process.name" lookup="not_match_key">etc/lists/agents/common-known-apps</list>
  <description>Процесс не из базового белого списка</description>
</rule>
```

**Персональное правило (генерируется для каждого агента):**
```xml
<rule id="{{ rule_id_base + 100 }}" level="3">
  <if_sid>101001</if_sid>
  <hostname>{{ wazuh_agent_name }}</hostname>
  <list field="process.name" lookup="match_key">etc/lists/agents/{{ wazuh_agent_name }}-known-apps</list>
  <description>Процесс из кастомного белого списка агента</description>
</rule>

<rule id="{{ rule_id_base + 101 }}" level="12">
  <if_sid>101001</if_sid>
  <hostname>{{ wazuh_agent_name }}</hostname>
  <list field="process.name" lookup="not_match_key">etc/lists/agents/{{ wazuh_agent_name }}-known-apps</list>
  <description>КРИТИЧЕСКИЙ АЛЕРТ: Неизвестный процесс $(process.name)</description>
</rule>
```

## Дополнительная информация

### Преимущества подхода
- **Масштабируемость**: Обслуживание 200+ серверов без ручного вмешательства.
- **Детерминированность**: Вся конфигурация безопасности описана в Git (IaC).
- **Снижение шума**: Точные белые списки для каждого типа нагрузки (БД, Web, Cache) минимизируют ложные срабатывания.
