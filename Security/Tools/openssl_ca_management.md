# Управление центром сертификации (CA) на OpenSSL: подробное руководство

Это руководство поможет вам создать и управлять собственным центром сертификации (CA) с помощью OpenSSL. Такой CA необходим для выпуска доверенных SSL/TLS-сертификатов для внутренних сервисов, разработки, тестирования и реализации взаимной аутентификации (mTLS).

> Для более сложных и безопасных инсталляций, требующих повышенной безопасности, рекомендуется использовать [двухуровневую архитектуру CA](./openssl_ca_management_two_tier.md).

> **Что такое двухуровневая архитектура?** В этой модели **корневой CA (Root CA)** используется исключительно для подписи одного или нескольких **промежуточных CA (Intermediate CA)**. Приватный ключ Root CA после этого убирается в безопасное, отключенное от сети хранилище (офлайн). Повседневный выпуск и отзыв сертификатов для конечных сервисов (веб-серверов, клиентов) выполняет Intermediate CA. Такой подход значительно повышает безопасность: даже если ключ промежуточного CA будет скомпрометирован, корневой ключ останется в безопасности, что позволит отозвать скомпрометированный CA и выпустить новый, сохранив доверие ко всей инфраструктуре.

Мы рассмотрим два подхода:
1.  **Формальный метод**: создание полноценной структуры CA с базой данных сертификатов. Рекомендуется для управления множеством сертификатов в организации.
2.  **Быстрый метод**: упрощенный выпуск сертификата для быстрых тестов и разовых задач.

## Основные понятия и форматы файлов

*   `.key`: Приватный (закрытый) ключ. **Храните его в строжайшем секрете.** Используется для подписи данных и расшифровки.
*   `.csr` (Certificate Signing Request): Запрос на подпись сертификата. Содержит открытый ключ и информацию о владельце (домен, организация). Отправляется в CA для получения сертификата.
*   `.crt` или `.cer`: Подписанный сертификат (X.509). Содержит открытый ключ, информацию о владельце и цифровую подпись CA, которая подтверждает его подлинность.
*   `.pem` (Privacy-Enhanced Mail): Текстовый формат-контейнер, кодированный в Base64. Может содержать ключ, сертификат, цепочку сертификатов или всё сразу. Легко определить по заголовкам `-----BEGIN...-----` и `-----END...-----`.

## Формальный метод: Создание полноценного CA

Этот метод включает создание иерархической структуры и базы данных для отслеживания выпущенных сертификатов.

### 1.1. Структура директорий CA

Создадим изолированное окружение для нашего CA.

```bash
# Основная директория
mkdir -p ca

# Вложенная структура для базы данных и сертификатов
mkdir -p ca/db/{newcerts,crl}
touch ca/db/index.txt   # База данных выданных сертификатов
echo "1000" > ca/db/serial # Начальный серийный номер в hex
echo "1000" > ca/db/crlnumber # Начальный номер для CRL
```
- `db/index.txt`: Главная база данных CA. OpenSSL хранит здесь информацию о каждом сертификате: его статус (`V` — действителен, `R` — отозван), срок истечения, серийный номер и subject. Пример записи: `V		270126151041Z		1000	unknown	/C=RU/ST=Moscow/O=My Private Org/OU=Service/CN=site1.local`.
- `db/serial`: Текстовый файл, который содержит серийный номер для **следующего** сертификата, который будет выпущен. После каждого выпуска `openssl ca` считывает номер и увеличивает его.
- `db/crlnumber`: Аналогично `serial`, но для списков отзыва (CRL). Каждый новый CRL должен иметь уникальный номер.
- `db/newcerts/`: Архив всех выданных сертификатов. После успешной подписи `openssl ca` сохраняет сюда копию сертификата, называя файл его серийным номером (например, `1000.pem`).
- `crl/`: Директория для хранения сгенерированных списков отзыва сертификатов (`.crl` файлов).

В результате выполнения этих шагов создается полноценная структура центра сертификации:
```
ca/
├── ca.key         приватный ключ CA
├── ca.crt         корневой сертификат
├── openssl.cnf    правила работы CA
└── db/
    ├── index.txt  база сертификатов
    ├── serial     счётчик сертификатов
    ├── crlnumber  счётчик CRL
    ├── newcerts/  архив выданных cert
    └── crl/       списки отзыва
```

### 1.2. Конфигурационный файл openssl.cnf

Создадим файл `ca/openssl.cnf`, который будет содержать все настройки нашего CA. Это упростит все последующие команды.

```ini
# ca/openssl.cnf

[ ca ]
default_ca = CA_default

[ CA_default ]
dir             = .
certs           = $dir/certs                # Не используется, но должно быть
crl_dir         = $dir/crl                  # Директория для CRL
database        = $dir/db/index.txt         # Путь к базе данных сертификатов
new_certs_dir   = $dir/db/newcerts          # Куда сохранять новые сертификаты

certificate     = $dir/ca.crt               # Корневой сертификат CA
serial          = $dir/db/serial            # Файл с серийным номером
crlnumber       = $dir/db/crlnumber         # Файл с номером CRL
crl             = $dir/crl.pem              # Текущий CRL (создается позже)
private_key     = $dir/ca.key               # Приватный ключ CA
RANDFILE        = $dir/db/.rand             # Файл со случайными данными

default_md      = sha512                    # Алгоритм хеширования по умолчанию
default_days    = 365                       # Срок действия сертификата по умолчанию (1 год)
preserve        = no                        # Поля в CSR должны совпадать с полями CA
policy          = policy_match              # Политика проверки полей

# Политика, требующая совпадения страны, региона и организации
# с данными корневого CA.
[ policy_match ]
countryName             = match
stateOrProvinceName     = match
organizationName        = match
organizationalUnitName  = optional
commonName              = supplied
emailAddress            = optional

# Объяснение политики:
# match    - поле в CSR должно в точности совпадать со значением в сертификате CA.
#            Это строгая политика, гарантирующая, что все сертификаты,
#            например, принадлежат одной организации и стране.
# supplied - поле должно присутствовать в CSR. Его значение может быть любым.
#            Используется для уникальных имен, таких как Common Name.
# optional - поле может отсутствовать в CSR. Если оно есть, его значение не проверяется.

[ req ]
default_bits        = 4096                  # Длина ключа RSA по умолчанию
default_md          = sha512                # Алгоритм хеширования
distinguished_name  = req_distinguished_name
x509_extensions     = v3_ca                 # Расширения для корневого CA
prompt              = no                    # Не задавать вопросы при создании CSR

[ req_distinguished_name ]
C  = RU
ST = Moscow
L  = Moscow
O  = My Private Org
OU = IT Department
CN = My Private Root CA

# Расширения для корневого сертификата (v3_ca)
[ v3_ca ]
# Идентификатор ключа субъекта (Subject Key Identifier, SKI)
# Генерирует уникальный хэш открытого ключа самого сертификата.
# Позволяет отличать разные сертификаты, выданные одному и тому же лицу.
subjectKeyIdentifier   = hash

# Идентификатор ключа центра сертификации (Authority Key Identifier, AKI)
# Копирует SKI из сертификата CA, который подписывает данный сертификат.
# Это позволяет построить цепочку доверия: AKI дочернего сертификата
# должен совпадать с SKI родительского. `keyid:always` гарантирует
# его наличие, `issuer` добавляет имя и серийный номер CA.
authorityKeyIdentifier = keyid:always,issuer

# Основные ограничения (Basic Constraints)
# `critical` означает, что это расширение должно быть понято и обработано.
# `CA:true` — это то, что делает сертификат сертификатом CA. Он может подписывать другие.
basicConstraints       = critical, CA:true

# Использование ключа (Key Usage)
# Определяет, для каких криптографических операций может быть использован этот ключ.
# `digitalSignature`: проверка подписей (кроме сертификатов и CRL)
# `cRLSign`: подпись списков отзыва (CRL)
# `keyCertSign`: подпись других сертификатов
keyUsage               = critical, digitalSignature, cRLSign, keyCertSign

# Расширения для сертификатов клиентов/серверов (конечных сущностей)
[ v3_req ]
# `CA:FALSE` означает, что этот сертификат не может подписывать другие.
basicConstraints       = CA:FALSE
# `nonRepudiation`: для неотрекаемости
# `digitalSignature`: для цифровой подписи
# `keyEncipherment`: для шифрования ключей (например, в TLS handshake)
keyUsage               = nonRepudiation, digitalSignature, keyEncipherment
subjectKeyIdentifier   = hash
authorityKeyIdentifier = keyid,issuer
# Назначение: аутентификация сервера и/или клиента
extendedKeyUsage       = serverAuth, clientAuth
# Указываем, что альтернативные имена субъекта (SAN) нужно брать из секции [alt_names]
subjectAltName         = @alt_names

# Секция для альтернативных имен субъекта (SAN)
# --- ВАЖНО ---
# Современные браузеры (Chrome >= 58, Firefox >= 48) и стандарты (RFC 2818)
# требуют, чтобы доменные имена и IP-адреса находились в расширении
# Subject Alternative Name (SAN). Поле Common Name (CN) считается устаревшим
# для этой цели и игнорируется, если присутствует SAN.
#
# ЭТУ СЕКЦИЮ НУЖНО РЕДАКТИРОВАТЬ ПЕРЕД ВЫПУСКОМ КАЖДОГО СЕРТИФИКАТА.
[alt_names]
DNS.1 = my-service.local
DNS.2 = www.my-service.local
IP.1  = 192.168.1.10
```

### 1.3. Создание корневого ключа и сертификата CA

Корневой сертификат — это основа доверия всей системы. Мы создаем его и подписываем собственным ключом (самоподписанный).

> **О безопасности ключа CA**
> Флаг `-nodes` (no DES) отключает шифрование приватного ключа паролем. Это удобно для тестов, но **абсолютно недопустимо в производственной среде**. Компрометация приватного ключа корневого CA означает компрометацию всей инфраструктуры доверия. В реальности ключ корневого CA должен:
> 1.  Быть защищен сложным паролем.
> 2.  Храниться на физически изолированном носителе (Air-gapped-система, аппаратный модуль безопасности HSM), который никогда не подключается к сети.

```bash
cd ca

# Создаем приватный ключ (ca.key) и самоподписанный сертификат (ca.crt)
openssl req -new -x509 \
    -config openssl.cnf \
    -newkey rsa:4096 -sha512 -nodes \
    -keyout ca.key \
    -out ca.crt \
    -days 3650 # Срок действия 10 лет

# Вернемся в родительскую директорию
cd ..
```
- `-x509`: Создать самоподписанный сертификат вместо запроса (CSR).
- `-newkey rsa:4096`: Сгенерировать новый 4096-битный RSA-ключ.
- `-nodes`: (No DES) Не шифровать приватный ключ паролем.
- `-config`: Использовать наш конфигурационный файл. Поля из секции `[req_distinguished_name]` будут подставлены автоматически.

### 1.4. Выпуск сертификата (с поддержкой SAN)

Это централизованный и наиболее правильный подход. Заявитель (клиент) создает простой запрос, а администратор CA определяет, какие доменные имена (SAN) будут включены в сертификат.

**Шаг 1: Создание ключа и простого CSR на стороне клиента**

Клиент генерирует приватный ключ и CSR, указывая только основную информацию (DN). Никаких расширений на этом этапе не требуется.

```bash
# Создаем приватный ключ для нашего сервиса
openssl genrsa -out my-service.key 4096

# Создаем простой CSR. 
# CN здесь важен для идентификации запроса.
openssl req -new -key my-service.key -out my-service.csr \
  -subj "/C=RU/ST=Moscow/O=My Private Org/OU=Service/CN=my-service.local"
```
Далее файл `my-service.csr` передается администратору CA.

**Шаг 2: Редактирование `openssl.cnf` и подпись CSR в центре сертификации**

Администратор CA перед подписью должен отредактировать файл `ca/openssl.cnf` и вписать правильные DNS-имена и/или IP-адреса в секцию `[alt_names]`.

```ini
# ca/openssl.cnf -> [alt_names]
[alt_names]
DNS.1 = my-service.local
DNS.2 = my-app.local
IP.1 = 192.168.10.20
# Можно добавить больше имен: DNS.3, DNS.4 и т.д.
```

После этого администратор подписывает запрос:

```bash
cd ca

# Команда для подписи запроса
openssl ca -config openssl.cnf -in ../my-service.csr -out ../my-service.crt \
  -extensions v3_req -notext

cd ..
```
- `-extensions v3_req`: Эта опция указывает OpenSSL применить расширения из секции `[v3_req]` конфигурационного файла `openssl.cnf`. Поскольку в этой секции есть строка `subjectAltName = @alt_names`, OpenSSL автоматически добавит в сертификат все имена из секции `[alt_names]`.

Этот метод гарантирует, что CA полностью контролирует содержимое сертификатов, включая критически важное расширение SAN.

После выполнения этой команды в файле `ca/db/index.txt` появится новая строка, а `ca/db/serial` обновится. Убедиться в наличии SAN можно командой `openssl x509 -in my-service.crt -noout -text`.

## Глава 2. Жизненный цикл сертификата

### 2.1. Проверка цепочки доверия

Убедимся, что выданный сертификат действителен и подписан нашим CA.

```bash
openssl verify -CAfile ca/ca.crt my-service.crt
```
Ожидаемый вывод: `my-service.crt: OK`. Это означает, что подпись сертификата `my-service.crt` соответствует открытому ключу из `ca.crt`.

### 2.2. Добавление корневого сертификата в системное хранилище

Чтобы браузеры и утилиты (curl, wget) доверяли нашим сертификатам, корневой сертификат `ca.crt` нужно добавить в системное хранилище.

**Для Debian/Ubuntu:**
```bash
sudo cp ca/ca.crt /usr/local/share/ca-certificates/my-private-ca.crt
sudo update-ca-certificates
```

**Для RHEL/CentOS/Fedora:**
```bash
sudo cp ca/ca.crt /etc/pki/ca-trust/source/anchors/
sudo update-ca-trust
```

> **Примечание о браузерах:** Большинство браузеров (Chrome, Edge, Opera) используют системное хранилище доверенных сертификатов. Однако некоторые приложения, например **Firefox**, по умолчанию используют собственное хранилище. Для таких приложений может потребоваться импортировать корневой сертификат `ca.crt` непосредственно в их настройках безопасности.

### 2.3. Отзыв скомпрометированного сертификата

Если приватный ключ сертификата был украден или сертификат больше не нужен, его необходимо отозвать. Эта функция доступна только при использовании **формального метода**.

**Шаг 1: Отзыв сертификата**

```bash
cd ca

# Указываем путь к сертификату, который нужно отозвать
openssl ca -config openssl.cnf -revoke ../my-service.crt
```
В базе `db/index.txt` статус сертификата изменится с `V` (valid) на `R` (revoked).

**Шаг 2: Генерация списка отозванных сертификатов (CRL)**

```bash
# Создаем/обновляем файл crl.pem
openssl ca -config openssl.cnf -gencrl -out crl.pem

cd ..
```
Файл `ca/crl.pem` теперь содержит серийный номер отозванного сертификата. Веб-серверы и другие службы можно настроить на проверку этого списка.

> **Как работает CRL и что такое OCSP?**
> *   **CRL (Certificate Revocation List)** — это "черный список" серийных номеров сертификатов, которые были отозваны до истечения их срока действия. Клиент (например, веб-сервер или браузер) должен периодически скачивать этот список по URL, указанному в поле *CRL Distribution Points* сертификата, и проверять, нет ли в нем серийного номера проверяемого сертификата. Недостаток CRL в том, что он может быть большим и не всегда актуальным (обновляется периодически).
> *   **OCSP (Online Certificate Status Protocol)** — более современный механизм. Вместо скачивания всего списка клиент отправляет онлайн-запрос к специальному OCSP-серверу (адрес которого также указан в сертификате), чтобы узнать статус конкретного сертификата. Это быстрее и эффективнее, но создает нагрузку на OCSP-сервер и требует его постоянной доступности.

## Глава 3. Быстрый метод: выпуск сертификата для тестов

Этот метод не требует ведения базы данных и подходит для быстрых задач. Подпись выполняется напрямую с помощью корневого сертификата и ключа.

```bash
# 1. Создаем ключ и CSR для тестового сайта
# Для SAN в быстром методе нужно использовать временный конфиг или переменные окружения.
# Пример с CN:
openssl req -new -newkey rsa:2048 -nodes \
            -keyout test.key -out test.csr \
            -subj "/C=RU/ST=Test/L=Test/O=Test/CN=test.local"

# 2. Подписываем CSR, используя корневой CA
# Важно: для добавления SAN здесь потребуется опция -extfile с описанием расширений.
openssl x509 -req -in test.csr \
    -CA ca/ca.crt -CAkey ca/ca.key -CAcreateserial \
    -out test.crt -days 90 -sha256
```
- `-CAcreateserial`: Создает файл `ca.srl` (если его нет), который хранит последний использованный серийный номер. Это упрощенная замена `db/serial`.
- **Недостаток**: этот метод не позволяет вести полноценный учёт и отзывать сертификаты, а также сложнее в использовании с SAN.

## Приложение A: Практический пример — mTLS в Nginx

Настроим Nginx так, чтобы он требовал от клиентов валидный сертификат, подписанный нашим CA.

```nginx
server {
    listen 443 ssl;
    server_name my-service.local;

    ssl_certificate         /path/to/my-service.crt;
    ssl_certificate_key     /path/to/my-service.key;

    # --- Клиентская аутентификация ---

    # 1. Корневой сертификат для проверки клиентов
    ssl_client_certificate  /path/to/ca/ca.crt;

    # 2. Файл со списком отозванных сертификатов
    ssl_crl                 /path/to/ca/crl.pem;

    # 3. Включить проверку клиента
    # on: Строгая проверка. Клиент обязан предоставить валидный сертификат.
    #     Если сертификат не предоставлен или не прошел проверку, соединение разрывается.
    # optional: Запрашивать сертификат, но не требовать.
    #           Результат проверки доступен в переменной $ssl_verify_result.
    #           Позволяет реализовать логику, когда доступ для клиентов
    #           с сертификатом и без него отличается.
    # optional_no_ca: Запрашивать сертификат, но не проверять его по CA.
    #                 Используется в редких случаях, когда проверка выполняется
    #                 на уровне приложения.
    ssl_verify_client       on;

    location / {
        # Переменная $ssl_client_s_dn содержит DN (Distinguished Name) клиента
        # Например: /C=RU/ST=Moscow/O=My Private Org/OU=IT Department/CN=user1
        # Можно использовать для авторизации.
        if ($ssl_verify_result != "SUCCESS") {
            return 403;
        }

        # Можно извлечь CN клиента и использовать для логгирования или
        # передачи в backend.
        # map $ssl_client_s_dn $ssl_client_cn {
        #    ~,CN=(?<cn>[^,]+) $cn;
        # }
        # proxy_set_header X-Client-CN $ssl_client_cn;

        proxy_pass http://backend;
    }
}
```

## Приложение B: Полезные команды для проверки

**Просмотреть содержимое сертификата:**
```bash
openssl x509 -in my-service.crt -noout -text
```

**Просмотреть содержимое CSR:**
```bash
openssl req -in my-service.csr -noout -text
```

**Проверить соответствие ключа и сертификата:**
(Хеши модулей должны совпадать)
```bash
openssl rsa -noout -modulus -in my-service.key | openssl md5
openssl x509 -noout -modulus -in my-service.crt | openssl md5
```

**Просмотреть содержимое CRL:**
```bash
openssl crl -in ca/crl.pem -noout -text
```

**Проверить дату окончания срока действия сертификата:**
```bash
openssl x509 -in my-service.crt -noout -enddate
```

**Подключиться к TLS-серверу и показать его сертификат:**
```bash
# Замените my-service.local:443 на нужный адрес и порт
openssl s_client -connect my-service.local:443 -showcerts < /dev/null
```
