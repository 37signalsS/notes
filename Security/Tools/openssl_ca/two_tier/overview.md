# Обзор двухуровневого центра сертификации (CA) на OpenSSL

## Определения

**CA (Certificate Authority, Центр сертификации)** — доверенная сущность, выпускающая цифровые сертификаты для подтверждения подлинности открытых ключей.

**Двухуровневый CA** — архитектура центра сертификации, состоящая из корневого узла и одного или нескольких подчиненных узлов. Обеспечивает баланс между безопасностью и удобством эксплуатации.

**Root CA (Корневой CA)** и **Intermediate CA (Промежуточный CA)** — ключевые элементы иерархии доверия. Их определения, а также понятия **Цепочки доверия (Chain of Trust)**, **CSR (Certificate Signing Request, Запрос на подпись сертификата)** и механизмов отзыва сертификатов (**CRL**, **OCSP**) подробно описаны в **[обзоре PKI](../../../../Concepts/pki_overview.md)**.

**mTLS (Mutual TLS, Взаимный TLS)** — механизм двусторонней аутентификации, требующий наличия сертификатов как у сервера, так и у клиента ([подробнее](../../../../WebServers/Nginx/Security/TLS_SSL/nginx_tls_ssl_overview.md#mutual-tls-mtls)).

## Базовые концепции

### Архитектура двухуровневого CA

Рекомендованная схема для производственных сред (production) предполагает четкое разделение ролей:

```
Root CA (самоподписанный, офлайн-хранение, срок 10–20 лет)
    └── Intermediate CA (подписан Root CA, онлайн-выпуск, срок 3–5 лет)
            ├── Сертификаты сервисов (serverAuth)
            └── Сертификаты клиентов (clientAuth)
```

**Изоляция Root CA:** после подписания промежуточного CA приватный ключ корневого узла (`ca.key`) переносится на физически изолированный носитель (air-gapped) и извлекается только для исключительных операций (выпуск нового Intermediate CA или отзыв существующего).

**Операционный уровень:** все повседневные запросы обрабатываются Intermediate CA. Его ключ хранится в защищенной онлайн-среде (например, в HashiCorp Vault или специализированной CI/CD-системе).

### Сравнение с одноуровневым CA

| Критерий | Одноуровневый CA | Двухуровневый CA |
| :--- | :--- | :--- |
| **Безопасность** | Низкая — корень всегда под угрозой | Высокая — Root CA офлайн |
| **Сложность** | Минимальная | Средняя |
| **Риск компрометации** | Полная потеря доверия к PKI | Локализован уровнем Intermediate |
| **Применение** | Тесты, разработка | Production, корпоративные сети |

Подробности об упрощенном подходе см. в **[обзоре одноуровневого CA](../single_tier/overview.md)**.

### Компоненты и структура

Для корректной работы требуется разделение конфигураций и баз данных для каждого уровня.

**Файл ca-chain.crt:** критически важный компонент, объединяющий сертификат промежуточного CA и корневой сертификат. Он необходим TLS-серверам для передачи полной цепочки клиентам, которые доверяют только Root CA.

**Ключевые расширения X.509:**

- **`pathlen`:** ограничивает глубину иерархии (для Root CA обычно `1`, для Intermediate — `0`).
- **SAN (Subject Alternative Name, Альтернативное имя субъекта):** современный стандарт указания доменов и IP-адресов, заменяющий устаревшее поле Common Name (CN).

## Практические сценарии

### Порядок развёртывания инфраструктуры

Создание полноценной PKI выполняется строго последовательно:

1. **[Создание Root CA](./root_ca_setup.md)** — генерация корня и перевод ключа в офлайн-режим.
2. **[Настройка Intermediate CA](./intermediate_ca_setup.md)** — подготовка рабочего узла и выпуск цепочки `ca-chain.crt`.
3. **[Управление сертификатами сервисов](./service_certificate_management.md)** — приём CSR, подпись с использованием SAN и выпуск CRL.
4. **[Утилиты и диагностика](./common_utilities.md)** — верификация цепочек и отладка TLS-соединений.

### Сценарии использования

- **Защита межсервисного взаимодействия:** выпуск TLS-сертификатов для микросервисов внутри кластера.
- **Внутренний mTLS:** идентификация пользователей и устройств при доступе к критичным API.
- **Корпоративные VPN-сети:** выдача сертификатов для аутентификации в защищенных туннелях.
