# Настройка Root CA

## Определения

**PKI (Public Key Infrastructure, Инфраструктура открытых ключей)** — совокупность технологий, стандартов, политик и процедур, необходимых для создания, управления, распределения, использования, хранения и отзыва цифровых сертификатов. Основная цель — обеспечить доверенную среду для обмена данными и идентификации субъектов через асимметричную криптографию.

**Root CA (Корневой центр сертификации)** — вершина иерархии доверия. Самоподписанный сертификат с расширением `CA:true`, используемый исключительно для подписи промежуточных центров сертификации. Его приватный ключ является наиболее критичным активом и должен находиться в максимально изолированной среде.

**Air-gapped система** — компьютер или среда, физически изолированная от любых сетей (Ethernet, Wi-Fi, Bluetooth). Применяется для защиты приватных ключей от удалённых атак. После использования операционная система загружается с Read-Only носителя (Live USB) для предотвращения компрометации после завершения операций.

**Intermediate CA (Промежуточный центр сертификации)** — подчинённый удостоверяющий центр, сертификат которого подписан корневым CA. В двухуровневой архитектуре он является единственным узлом, выпускающим конечные сертификаты. Его безопасность обеспечивается через ограничение `pathlen:0` в расширении Basic Constraints.

**ca-chain.crt (Bundle)** — PEM-файл, объединяющий сертификат Intermediate CA и Root CA. TLS-серверы обязаны отдавать полную цепочку клиентам, так как клиенты доверяют только корневому якорю и не знают о промежуточном звене.

**HSM (Hardware Security Module, Аппаратный модуль безопасности)** — специализированное устройство для генерации и безопасного хранения криптографических ключей, обеспечивающее защиту от физического и логического извлечения. Рекомендуется для хранения корневого ключа в production-средах.

**TPM (Trusted Platform Module)** — аппаратный модуль безопасности, интегрированный в материнскую плату. Поддерживает хранение ключей и криптографические операции. Может использоваться для защиты ключей Intermediate CA.

**OpenSSL 3.0+** — версия инструментария, в которой архитектура перешла на использование провайдеров (Default, FIPS, Legacy), были депрецированы устаревшие параметры конфигурации (например, `RANDFILE`), и внедрена поддержка гибридных схем и постквантовой криптографии.

**mTLS (Mutual TLS, Взаимный TLS)** — стандарт безопасности для взаимодействия микросервисов, требующий обязательной аутентификации как сервера, так и клиента с помощью сертификатов. В двухуровневой схеме mTLS реализуется через промежуточные CA.

**CRL (Certificate Revocation List)** — список серийных номеров отозванных сертификатов, подписанный CA. Клиенты проверяют сертификаты по этому списку для подтверждения, что они не были отозваны.

**OCSP (Online Certificate Status Protocol)** — протокол проверки статуса конкретного сертификата в реальном времени. Снижает нагрузку по сравнению с CRL, но требует доступности OCSP-responder.

**Shamir's Secret Sharing** — схема разделения секрета на части, при которой для восстановления исходного секрета необходимо наличие минимального количества частей (порогового значения). Применяется для разделения парольной фразы Root CA между доверенными администраторами.

> Базовые понятия (ключ, **CSR (Certificate Signing Request)**, X.509, цепочка доверия, CRL, OCSP, расширения X.509, алгоритмы 2026, PQC) подробно описаны в **[обзоре PKI](../../../Concepts/pki_overview.md)**. Об архитектуре двухуровневого CA и сравнении с одноуровневой см. **[обзор двухуровневого CA](./overview.md)**.

## Базовые концепции

### Назначение и безопасность

В двухуровневой архитектуре Root CA является наиболее критичным компонентом. Его единственная задача — выпуск и отзыв сертификатов Intermediate CA.

**Золотые правила безопасности Root CA:**
- **Офлайн-хранение:** приватный ключ должен находиться на air-gapped системе. Операционная система должна загружаться с Read-Only носителя (например, Live USB с отключенной записью).
- **Минимальный доступ:** ключ извлекается только для редких операций (выпуск нового промежуточного CA или генерация списка отзыва).
- **Физическая защита:** носители с ключами должны храниться в сейфах с ограниченным доступом.
- **Долговечность:** срок действия корня обычно составляет 20–25 лет (RSA-4096) или 15–20 лет (ECDSA P-384).

**Почему Root CA должен быть офлайн:**
Компрометация корневого ключа равносильна компрометации всей инфраструктуры доверия. Даже при использовании Intermediate CA, злоумышленник, получивший доступ к корневому ключу, может выпускать доверенные сертификаты для любого домена или сервиса. Изоляция от сети (air-gapping) и физическая защита исключают удалённые атаки и снижают поверхность воздействия.

### Архитектура и изоляция

Приватный ключ корневого узла (`ca.key`) является наиболее ценным активом. После выпуска промежуточного CA он должен храниться на физически отсоединённом носителе (air-gapped) или в аппаратном модуле **HSM (Hardware Security Module)** или **TPM 2.0**.

**Требования к среде Root CA:**
- Отсутствие сетевых интерфейсов (Ethernet, Wi-Fi, Bluetooth) или их полное отключение в BIOS/UEFI.
- Загрузка ОС с Read-Only носителя (Live USB) с отключенной записью.
- Отсутствие диспетчера swap-раздела или его шифрование (ключи не должны попадать в swap).
- Использование аппаратного RNG (TrueRNG, TPM, HAVEKE в `/dev/random`) при генерации ключей.

**OpenSSL 3.0+ и провайдеры:**
В OpenSSL 3.0 архитектура перешла на модульную систему провайдеров. Для работы с legacy-алгоритмами или FIPS-режимом необходимо явно указывать провайдеры в конфигурации или через переменную окружения `OPENSSL_CONF`. Параметр `RANDFILE` депрецирован; вместо него используйте `RANDFILE` в секции `[ CA_default ]` только для совместимости, но предпочитайте указание явного устройства энтропии.

### Алгоритмы и сроки действия (2026)

| Уровень | Алгоритм | Рекомендация | Срок действия |
| :--- | :--- | :--- | :--- |
| **Root CA** | RSA-4096 | Максимальная совместимость со всеми ОС и браузерами | 20–25 лет |
| **Root CA** | ECDSA P-384 | Современный стандарт, меньший размер ключа | 15–20 лет |
| **Intermediate CA** | ECDSA P-384 | Оптимальный баланс производительности и совместимости | 3–5 лет |
| **Intermediate CA** | Ed25519 | Высокая производительность, но меньшая совместимость с legacy | 3–5 лет |

**Примечание:** Для корневых CA не рекомендуется использовать Ed25519 из-за проблем совместимости с некоторыми legacy-клиентами (старые Java-приложения, встроенные системы). RSA-4096 или ECDSA P-384 остаются стандартом для корневых узлов.

### Структура директорий

```text
root-ca/
├── openssl.cnf          # Конфигурация для Root-уровня
├── ca.key               # Приватный ключ Root CA (зашифрован, права 600)
├── ca.crt               # Корневой сертификат
└── db/
    ├── index.txt        # База данных выданных Intermediate CA
    ├── serial           # Счётчик серийных номеров (hex)
    ├── newcerts/        # Архив выданных сертификатов
    ├── crlnumber        # Счётчик номеров CRL
    └── crl/             # Списки отзыва (CRL)
```

### Предварительные требования

#### Железо и ОС

- **Root CA:** выделенный air-gapped хост (физический ноутбук/сервер без сетевых интерфейсов или с отключенными) или HSM с поддержкой PKCS#11/KMIP. Операционная система загружается с Read-Only носителя (Live USB) для предотвращения компрометации после использования.
- **Клиенты/серверы:** любая ОС с OpenSSL 3.0+ и возможностью обновления доверенного хранилища.

#### Программное обеспечение

- **OpenSSL 3.0+** с включенными провайдерами Default и Legacy (при необходимости).
- **HSM firmware/software** (если используется аппаратный модуль): PKCS#11 библиотека от производителя.
- **Система резервного копирования** для носителей с ключами (зашифрованные бэкапы).
- **Аудит:** доступ к системному журналированию (`journalctl` или `/var/log/syslog`).

#### Требования к оператору

- Парольная фраза Root CA должна быть разделена по схеме Shamir (минимум 2 из 3) между доверенными администраторами.
- Учетные записи с доступом к Intermediate CA должны быть защищены MFA.
- Журнал операций (`index.txt`) должен периодически реплицироваться на SIEM-сервер.

## Практические сценарии

### Порядок развёртывания инфраструктуры

Создание полноценной двухуровневой PKI выполняется строго последовательно:

1. **[Создание Root CA](./root_ca_setup.md)** — подготовка конфигурации, самоподпись корня и уход в офлайн.
2. **[Настройка Intermediate CA](./intermediate_ca_setup.md)** — генерация CSR промежуточного узла и подпись его корневым ключом.
3. **[Управление сертификатами сервисов](./service_certificate_management.md)** — операционная работа: выпуск, ротация и отзыв.
4. **[Утилиты и диагностика](./common_utilities.md)** — верификация цепочек доверия и отладка TLS.

### 1. Подготовка air-gapped хоста и Live USB

Перед генерацией корневого ключа подготовьте изолированную среду:

```bash
# На машине с доступом в интернет: создание загрузочного Live USB
# (Debian/Ubuntu)
sudo dd if=debian-12.iso of=/dev/sdX bs=4M status=progress && sync

# На air-gapped хосте: загрузка с Live USB
# 1. Отключите все сетевые интерфейсы в BIOS/UEFI
# 2. Загрузитесь с Live USB в режиме только для чтения
# 3. Создайте рабочий каталог на внешнем USB-накопителе
mkdir -p /mnt/usb/root-ca && cd /mnt/usb/root-ca
```

**Проверка энтропии на air-gapped системе:**
```bash
# Проверка доступного энтропийного пула
cat /proc/sys/kernel/random/entropy_avail
# → ожидается > 1000 для генерации ключей без блокировки

# При нехватке энтропии используйте аппаратный генератор
# или подключите /dev/random через USB-устройство
```

### 2. Подготовка конфигурации openssl.cnf

Файл настроек для Root CA должен быть максимально строгим. OpenSSL 3.0+ требует явного указания провайдеров и отсутствия устаревших параметров.

```ini
[ ca ]
default_ca = CA_default

[ CA_default ]
dir             = .
database        = $dir/db/index.txt
new_certs_dir   = $dir/db/newcerts
serial          = $dir/db/serial
crlnumber       = $dir/db/crlnumber
certificate     = $dir/ca.crt
private_key     = $dir/ca.key
default_md      = sha512
default_days    = 7300
policy          = policy_strict

[ policy_strict ]
countryName             = match
stateOrProvinceName     = match
organizationName        = match
organizationalUnitName  = optional
commonName              = supplied

[ req ]
default_bits        = 4096
distinguished_name  = req_distinguished_name
x509_extensions     = v3_ca
prompt              = no

[ req_distinguished_name ]
C  = RU
ST = Moscow
L  = Moscow
O  = My Private Corp
CN = My Private Root CA

# Расширения для самого Root CA
[ v3_ca ]
subjectKeyIdentifier   = hash
authorityKeyIdentifier = keyid:always,issuer
basicConstraints       = critical, CA:true
keyUsage               = critical, digitalSignature, cRLSign, keyCertSign

# Расширения для подписи Intermediate CA
[ v3_intermediate_ca ]
subjectKeyIdentifier   = hash
authorityKeyIdentifier = keyid:always,issuer
basicConstraints       = critical, CA:true, pathlen:0
keyUsage               = critical, digitalSignature, cRLSign, keyCertSign
```

**Важные замечания по конфигурации:**
- `default_days = 7300` — срок действия корневого сертификата (20 лет).
- `pathlen:0` в `v3_intermediate_ca` запрещает Intermediate CA создавать подчинённые CA.
- `CRLSign` в `keyUsage` обязателен для корневого CA, так как он подписывает CRL для отзыва Intermediate CA.
- В OpenSSL 3.0+ не используйте `RANDFILE`; если требуется совместимость, добавьте пустую строку `RANDFILE =` для подавления предупреждений.

### 3. Инициализация структуры базы данных

```bash
mkdir -p db/{newcerts,crl}
touch db/index.txt
echo "1000" > db/serial
echo "1000" > db/crlnumber
```

**Описание структуры:**
- `db/index.txt` — текстовый реестр всех выпущенных сертификатов (статус, дата, DN). Должен быть защищён от изменений.
- `db/serial` — определяет ID следующего сертификата. Автоматически инкрементируется OpenSSL.
- `db/newcerts/` — каталог, куда OpenSSL сохраняет копии всех подписанных сертификатов.
- `db/crlnumber` — счётчик номеров CRL.
- `db/crl/` — каталог для хранения подписанных CRL.

### 4. Генерация корневого узла

#### Сценарий А: Классический RSA-4096 (Рекомендуется для корня)

```bash
# Генерация зашифрованного ключа и самоподписанного сертификата
openssl req -new -x509 -config openssl.cnf \
    -newkey rsa:4096 -sha512 -aes256 \
    -keyout ca.key -out ca.crt -days 7300
# → Система запросит пароль (passphrase). Обязательно используйте сложный пароль.
```

**Почему `-aes256` обязателен для Root CA:**
Зашифрование приватного ключа парольной фразой предотвращает его использование при компрометации носителя. Для Root CA пароль должен быть максимально сложным и храниться отдельно от ключа (например, разделён по схеме Шамира между несколькими доверенными лицами).

#### Сценарий Б: Современный ECDSA P-384

```bash
# Генерация зашифрованного ключа и самоподписанного сертификата
openssl req -new -x509 -config openssl.cnf \
    -newkey ec:<(openssl ecparam -name secp384r1) -sha512 -aes256 \
    -keyout ca.key -out ca.crt -days 7300
# → Система запросит пароль (passphrase).
```

#### Сценарий В: Ed25519 (не рекомендуется для Root CA)

```bash
# Ed25519 имеет меньшую совместимость с legacy-системами
# Используется только для Intermediate CA или конечных сертификатов
openssl genpkey -algorithm ed25519 -out ca.key
openssl req -new -x509 -config openssl.cnf \
    -key ca.key -out ca.crt -days 7300
```

**Установка прав доступа:**
```bash
# Приватный ключ: только для владельца, без группового/всеобщего доступа
chmod 600 ca.key
# Корневой сертификат: публичный, но защищён от случайного удаления
chmod 644 ca.crt
```

### 5. Подпись Intermediate CA

Операция выполняется при получении CSR от промежуточного узла. На air-gapped системе:

```bash
# Проверка CSR перед подписью
openssl req -in ../intermediate-ca/csr/intermediate.csr -noout -text

# Подпись с расширениями Intermediate CA
openssl ca -config openssl.cnf \
    -extensions v3_intermediate_ca \
    -days 3650 -notext -md sha512 \
    -in ../intermediate-ca/csr/intermediate.csr \
    -out ../intermediate-ca/intermediate.crt

# Верификация подписи корневым ключом
openssl verify -CAfile ca.crt ../intermediate-ca/intermediate.crt
# → intermediate.crt: OK
```

**Важно:** При подписи Intermediate CA убедитесь, что:
- CSR подписан корректным приватным ключом.
- Расширения `v3_intermediate_ca` применены (включая `pathlen:0`).
- Срок действия Intermediate CA не превышает срок действия Root CA.

### 6. Генерация и распространение CRL

Root CA отвечает за подпись CRL, содержащих отозванные Intermediate CA:

```bash
# Генерация CRL (если есть отозванные Intermediate CA)
openssl ca -config openssl.cnf -gencrl -out crl/crl.pem

# Просмотр CRL
openssl crl -in crl/crl.pem -noout -text
# → Last Update: ...
# → Next Update: ...
# → Revoked Certificates: ...
```

### 7. Вывод в офлайн и защита

1. **Резервное копирование:** Сохраните `ca.key` и `ca.crt` на 2–3 USB-накопителях разных производителей. Ключ должен быть зашифрован (`-aes256`).
2. **Верификация:** Проверьте контрольную сумму ключа: `sha512sum ca.key`.
3. **Шамир:** Разделите парольную фразу по схеме Shamir (минимум 2 из 3) между доверенными администраторами (см. practical-примеры ниже).
4. **Уничтожение:** Если использовалась временная ОС, выполните `shred -u ca.key` на временных копиях.
5. **Безопасное хранение:** Носители должны находиться в запечатанных конвертах в банковской ячейке или сейфе.

#### Разделение парольной фразы по схеме Шамира (ssss)

Инструмент `ssss` (Shamir's Secret Sharing Scheme) позволяет разделить секрет на N частей, из которых достаточно K для восстановления. Например, разделение на 3 части с порогом 2: для восстановления пароля достаточно 2 из 3 частей.

**Установка:**

```bash
# Debian/Ubuntu
sudo apt-get install ssss

# RHEL/CentOS/Fedora
sudo dnf install ssss

# macOS (Homebrew)
brew install ssss
```

**Разделение парольной фразы Root CA (2 из 3):**

```bash
# На air-gapped хосте: разделение пароля на 3 части, достаточно 2 для восстановления
echo "MyStr0ngR00tP@ssphrase2026" | ssss-split -t 2 -n 3
# → 1-<hex>: 1a2b3c4d5e6f...
# → 2-<hex>: 7f8e9d0c1b2a...
# → 3-<hex>: 3d4e5f6a7b8c...
```

**Рекомендации:**

- Распечатайте каждую часть на бумаге и передайте доверенному администратору.
- Храните распечатки в запечатанных конвертах в разных физических локациях.
- Никогда не храните все части в одном месте.
- Используйте `-w` для ввода пароля интерактивно (не через echo):

```bash
ssss-split -t 2 -n 3 -w
# → Введите секрет: [вводим пароль]
# → Введите подтверждение: [вводим пароль повторно]
```

**Восстановление парольной фразы (при необходимости):**

```bash
# Когда нужно расшифровать ca.key (например, для ротации Intermediate CA)
# Введите 2 из 3 частей (порядок не важен)
ssss-combine -t 2
# → Введите часть 1: [вставляем первую часть]
# → Введите часть 2: [вставляем вторую часть]
# → Reconstruction: MyStr0ngR00tP@ssphrase2026
```

**Восстановление и расшифровка ca.key:**

```bash
# 1. Восстановить парольную фразу
PASSPHRASE=$(ssss-combine -t 2 -q)

# 2. Расшифровать ca.key
openssl rsa -in ca.key -out /tmp/ca_decrypted.key -passin pass:"$PASSPHRASE"

# 3. Выполнить необходимую операцию (например, подпись нового Intermediate CA)
openssl ca -config openssl.cnf -extensions v3_intermediate_ca \
    -key /tmp/ca_decrypted.key -in intermediate.csr -out intermediate.crt

# 4. Немедленно удалить расшифрованный ключ
shred -u /tmp/ca_decrypted.key
unset PASSPHRASE
```

**Проверка:**

```bash
# Проверка, что ssss установлен и работает
ssss-split -v
# → ssss-0.5 (Shamir's Secret Sharing Scheme)

# Проверка: восстановление из 2 частей должно дать исходный пароль
echo "test_secret" | ssss-split -t 2 -n 3 > /tmp/shares.txt
SHARE1=$(sed -n '1p' /tmp/shares.txt | awk '{print $2}')
SHARE2=$(sed -n '2p' /tmp/shares.txt | awk '{print $2}')
echo -e "$SHARE1\n$SHARE2" | ssss-combine -t 2 -q
# → test_secret
```

## Типичные ошибки проектирования

1. **Отсутствие шифрования `ca.key` парольной фразой** — при компрометации носителя ключ может быть использован немедленно. Исправление: перегенерировать ключ с флагом `-aes256` и обновить все сертификаты.
2. **Использование `-nodes` для Root CA** — отключает шифрование приватного ключа. Исправление: никогда не используйте `-nodes` для корневых ключей.
3. **Хранение `ca.key` на промежуточном узле или в репозитории** — корневой ключ должен быть только на air-gapped хосте или в HSM. Исправление: вынести ключ, отозвать и перевыпустить Intermediate CA.
4. **Отсутствие `pathlen:0` в Intermediate CA** — позволяет создавать бесконтрольную иерархию подчинённых CA. Исправление: перевыпуск Intermediate CA с правильными расширениями.
5. **Использование SHA-1 или устаревших алгоритмов** — снижает стойкость всей инфраструктуры. Исправление: переход на SHA-256/512 и RSA-3072/4096 или ECDSA P-384.
6. **Нет CRL Distribution Points или AIA в расширениях** — клиенты не могут проверить отзыв или получить OCSP-ответ. Исправление: добавить расширения в `v3_intermediate_ca`.
7. **Недостаточная защита Intermediate CA** — доступ к ключу через insecure-канал или хранение в unprotected директории. Исправление: изоляция сети, права `600`, HSM/Vault.
8. **Отсутствие резервного копирования ключей** — потеря `ca.key` равносильна компрометации. Исправление: зашифрованные копии на независимых носителях.

## Ограничения и крайние случаи

- **Число Intermediate CA:** для сред с более чем 1000 конечными узлами рекомендуется создание нескольких Intermediate CA с разными политиками для распределения нагрузки.
- **Ротация Root CA:** каждые 10–20 лет. Требует полной перевыпуск всей цепочки и обновления доверенных хранилищ на всех клиентах. Планируйте отдельное окно обслуживания.
- **Совместимость с legacy-системами:** некоторые старые Java-приложения (до Java 8) и hardware appliances требуют RSA-ключей и специфических расширений (Key Usage без `keyAgreement`).
- **Регуляторные требования:** в финансовой и медицинской отраслях может требоваться использование сертифицированных средств криптозащиты (СКЗИ) с поддержкой ГОСТ.
- **Ограничение `pathlen`:** после установки `pathlen:0` в Intermediate CA невозможно создать подчинённый CA без перевыпуска Intermediate.
- **Энтропия в виртуальных средах:** генерация ключей на ВМ без аппаратного RNG может блокироваться. Используйте HAVEKE или подключение к `/dev/random` через virtio-rng, но для Root CA предпочтительна физическая машина.
- **Post-Quantum Cryptography (PQC):** текущий OpenSSL 3.x имеет ограниченную поддержку гибридных схем. Для защиты от квантовых компьютеров будущего используйте гибридные ключи (ECDSA + ML-DSA) при выпуске Intermediate CA, когда поддержка станет стабильной.

## Жизненный цикл эксплуатации

### 1. Развертывание и инициализация

- Подготовка air-gapped хоста для Root CA.
- Генерация ключа и самоподписанного сертификата с расширением `CA:true`.
- Выпуск Intermediate CA и формирование `ca-chain.crt`.
- Установка корневого сертификата во все доверенные хранилища целевых ОС.

### 2. Эксплуатация

- Выпуск нового Intermediate CA только при истечении срока его действия или компрометации.
- Поддержание актуального CRL для отзыва скомпрометированных Intermediate CA.
- Ведение журнала выпусков в `db/index.txt`.
- Плановая ротация корневого сертификата за 1–2 года до истечения срока.

### 3. Ротация и обновление

- **Ротация Intermediate CA:** каждые 3–5 лет. Требует повторного подписания корневым CA и обновления `ca-chain.crt` на всех серверах.
- **Ротация корневого CA:** каждые 10–20 лет. Требует полной перевыпуск всей цепочки.
- **Аварийная ротация:** при потере или компрометации ключа Intermediate CA — выпуск нового Intermediate, отзыв старого, обновление клиентов.

### 4. Аварийное реагирование

- Отзыв скомпрометированных Intermediate CA через `openssl ca -revoke`.
- Генерация и распространение обновленного CRL.
- При компрометации корневого ключа — полная перевыпуск инфраструктуры.

### 5. Деактивация и архивация

- Удаление корневого и промежуточных сертификатов из доверенных хранилищ всех клиентов.
- Архивирование или безопасное уничтожение ключей в соответствии с политикой данных организации.
- Сохранение `index.txt` и `serial` для аудита.

## Очистка и откат изменений

### Удаление Root CA и всех сертификатов

```bash
# Полное удаление директории Root CA (необратимо!)
rm -rf root-ca/

# Удаление установленных корневых сертификатов из доверенных хранилищ ОС
# Debian/Ubuntu
sudo update-ca-certificates --fresh

# RHEL/CentOS/Fedora
sudo update-ca-trust

# Windows Server
certutil -delstore "Root" "CN=My Private Root CA"
```

### Отзыв всех Intermediate CA (экстренный сценарий)

```bash
cd root-ca

# Отзыв всех сертификатов через скрипт (аккуратно!)
for cert in db/newcerts/*.pem; do
    openssl ca -config openssl.cnf -revoke "$cert"
done

# Генерация нового CRL
openssl ca -config openssl.cnf -gencrl -out crl/crl.pem

# Распространение нового CRL на все сервисы
```

### Очистка тестовой среды

```bash
# Удаление тестовых сертификатов и ключей
rm -f ca.key ca.crt intermediate.crt intermediate.csr

# Очистка кэша OpenSSL
rm -rf ~/.openssl/
```

## Аварийное восстановление (Disaster Recovery)

### Сценарий 1: Потеря Intermediate CA

1. Подготовить новую машину для Intermediate CA.
2. Скопировать `root-ca/ca.crt` и `root-ca/ca.key` с air-gapped хоста (или использовать HSM).
3. Выпустить новый Intermediate CA и новый Bundle.
4. Отозвать старый Intermediate CA через корневой ключ.
5. Обновить `ca-chain.crt` на всех серверах.

### Сценарий 2: Потеря Root CA

1. Восстановить `ca.key` и `ca.crt` из зашифрованного бэкапа.
2. Если восстановление невозможно — требуется полная перевыпуск всей PKI.
3. Выпустить новый Root CA и новый Intermediate CA.
4. Отозвать все старые сертификаты.
5. Распространить новый Root CA через все доверенные хранилища.

### Сценарий 3: Компрометация ключа

1. Немедленно отозвать скомпрометированный сертификат.
2. Сгенерировать новый CRL и обеспечить его доступность.
3. Выпустить новый ключ и сертификат.
4. Обновить все сервисы, использующие старый сертификат.

## Мониторинг и оповещение

### Проверка срока действия Root CA

```bash
#!/usr/bin/env bash
# Проверка срока действия Root CA
CA_CRT="root-ca/ca.crt"
DAYS_WARN="${1:-365}"
DAYS_CRIT="${2:-30}"

EXP_DATE=$(openssl x509 -in "$CA_CRT" -noout -enddate 2>/dev/null \
  | cut -d= -f2)

if [ -z "$EXP_DATE" ]; then
  echo "FAIL: Не удалось прочитать сертификат $CA_CRT"
  exit 1
fi

EXP_EPOCH=$(date -j -f "%b %d %H:%M:%S %Y %Z" "$EXP_DATE" +%s 2>/dev/null || \
            date -d "$EXP_DATE" +%s)
NOW_EPOCH=$(date +%s)
DAYS_LEFT=$(( (EXP_EPOCH - NOW_EPOCH) / 86400 ))

if [ "$DAYS_LEFT" -lt 0 ]; then
  echo "CRITICAL: Root CA истёк $(( -DAYS_LEFT )) дней назад"
  exit 2
elif [ "$DAYS_LEFT" -lt "$DAYS_CRIT" ]; then
  echo "CRITICAL: Root CA истекает через $DAYS_LEFT дней"
  exit 2
elif [ "$DAYS_LEFT" -lt "$DAYS_WARN" ]; then
  echo "WARNING: Root CA истекает через $DAYS_LEFT дней"
  exit 1
else
  echo "OK: Root CA действителен ещё $DAYS_LEFT дней"
fi
```

**Интеграция с мониторингом:**
- Добавьте скрипт в cron для ежедневной проверки.
- Настройте оповещение в Slack/Telegram/PagerDuty при достижении критического порога.
- Для enterprise-сред интегрируйте с Prometheus Blackbox Exporter, указав `server_name`, соответствующий внутреннему домену (см. **[обзор PKI](../../../Concepts/pki_overview.md)**).

## Best Practices

- **Приватные ключи всегда offline:** Root CA ключ никогда не должен находиться на машине с сетевым доступом.
- **Шифрование ключа:** всегда используйте `-aes256` при генерации корневого ключа. Парольная фраза разделена по схеме Shamir.
- **HSM/TPM для корневых ключей:** использование аппаратных модулей исключает возможность извлечения ключа.
- **Права доступа:** `ca.key` должен иметь права `600` и принадлежать выделенному пользователю (например, `root` или `ca`).
- **Резервное копирование:** зашифрованные копии ключей хранятся отдельно от сертификатов, с использованием отдельного пароля или шифрования GPG.
- **Аудит:** ведение журнала всех операций подписи через `index.txt` и отправка событий в SIEM.
- **Ротация по расписанию:** ротация Root CA каждые 10–20 лет, Intermediate CA — каждые 3–5 лет.
- **CRL Distribution Points:** всегда указывайте доступные URL для CRL в расширениях сертификата.
- **Тестовый выпуск:** перед использованием в production выпускайте тестовый сертификат и проверяйте его через `openssl verify`.
- **Документация:** поддерживайте актуальную схему инфраструктуры и список ответственных администраторов.
