# Управление сертификатами сервисов (одноуровневый CA)

## Практические сценарии

### Выпуск сертификата (с поддержкой SAN)

Это централизованный и наиболее правильный подход. Заявитель (клиент) создает простой запрос, а администратор CA определяет, какие доменные имена (SAN) будут включены в сертификат.

#### Шаг 1: Создание ключа и простого CSR на стороне клиента

Клиент генерирует приватный ключ и CSR, указывая только основную информацию (DN). Никаких расширений на этом этапе не требуется.

```bash
# Создаем приватный ключ для нашего сервиса
openssl genrsa -out my-service.key 4096

# Создаем простой CSR.
# CN здесь важен для идентификации запроса.
openssl req -new -key my-service.key -out my-service.csr 
  -subj "/C=RU/ST=Moscow/O=My Private Org/OU=Service/CN=my-service.local"
```
Далее файл `my-service.csr` передается администратору CA.

#### Шаг 2: Редактирование `openssl.cnf` и подпись CSR в центре сертификации

Администратор CA перед подписью должен отредактировать файл `ca/openssl.cnf` и вписать правильные DNS-имена и/или IP-адреса в секцию `[alt_names]`.

```ini
# ca/openssl.cnf -> [alt_names]
[alt_names]
DNS.1 = my-service.local
DNS.2 = my-app.local
IP.1 = 192.168.10.20
# Можно добавить больше имен: DNS.3, DNS.4 и т.д.
```

После этого администратор подписывает запрос:

```bash
cd ca

# Команда для подписи запроса
openssl ca -config openssl.cnf -in ../my-service.csr -out ../my-service.crt 
  -extensions v3_req -notext

cd ..
```
- `-extensions v3_req`: Эта опция указывает OpenSSL применить расширения из секции `[v3_req]` конфигурационного файла `openssl.cnf`. Поскольку в этой секции есть строка `subjectAltName = @alt_names`, OpenSSL автоматически добавит в сертификат все имена из секции `[alt_names]`.

Этот метод гарантирует, что CA полностью контролирует содержимое сертификатов, включая критически важное расширение SAN.

После выполнения этой команды в файле `ca/db/index.txt` появится новая строка, а `ca/db/serial` обновится. Убедиться в наличии SAN можно командой `openssl x509 -in my-service.crt -noout -text`.

### Жизненный цикл сертификата

#### Проверка цепочки доверия

Убедимся, что выданный сертификат действителен и подписан нашим CA.

```bash
openssl verify -CAfile ca/ca.crt my-service.crt
```
Ожидаемый вывод: `my-service.crt: OK`. Это означает, что подпись сертификата `my-service.crt` соответствует открытому ключу из `ca.crt`.

#### Добавление корневого сертификата в системное хранилище

Чтобы браузеры и утилиты (curl, wget) доверяли нашим сертификатам, корневой сертификат `ca.crt` нужно добавить в системное хранилище.

**Для Debian/Ubuntu:**
```bash
sudo cp ca/ca.crt /usr/local/share/ca-certificates/my-private-ca.crt
sudo update-ca-certificates
```

**Для RHEL/CentOS/Fedora:**
```bash
sudo cp ca/ca.crt /etc/pki/ca-trust/source/anchors/
sudo update-ca-trust
```

> **Примечание о браузерах:** Большинство браузеров (Chrome, Edge, Opera) используют системное хранилище доверенных сертификатов. Однако некоторые приложения, например **Firefox**, по умолчанию используют собственное хранилище. Для таких приложений может потребоваться импортировать корневой сертификат `ca.crt` непосредственно в их настройках безопасности.

#### Отзыв скомпрометированного сертификата

Если приватный ключ сертификата был украден или сертификат больше не нужен, его необходимо отозвать. Эта функция доступна только при использовании **формального метода**.

##### Шаг 1: Отзыв сертификата

```bash
cd ca

# Указываем путь к сертификату, который нужно отозвать
openssl ca -config openssl.cnf -revoke ../my-service.crt
```
В базе `db/index.txt` статус сертификата изменится с `V` (valid) на `R` (revoked).

##### Шаг 2: Генерация списка отозванных сертификатов (CRL)

```bash
# Создаем/обновляем файл crl.pem
openssl ca -config openssl.cnf -gencrl -out crl.pem

cd ..
```
Файл `ca/crl.pem` теперь содержит серийный номер отозванного сертификата. Веб-серверы и другие службы можно настроить на проверку этого списка.

> **Как работает CRL и что такое OCSP?**
> *   **CRL (Certificate Revocation List)** — это "черный список" серийных номеров сертификатов, которые были отозваны до истечения их срока действия. Клиент (например, веб-сервер или браузер) должен периодически скачивать этот список по URL, указанному в поле *CRL Distribution Points* сертификата, и проверять, нет ли в нем серийного номера проверяемого сертификата. Недостаток CRL в том, что он может быть большим и не всегда актуальным (обновляется периодически).
> *   **OCSP (Online Certificate Status Protocol)** — более современный механизм. Вместо скачивания всего списка клиент отправляет онлайн-запрос к специальному OCSP-серверу (адрес которого также указан в сертификате), чтобы узнать статус конкретного сертификата. Это быстрее и эффективнее, но создает нагрузку на OCSP-сервер и требует его постоянной доступности.
