# Управление сертификатами сервисов в одноуровневом CA

## Определения

Базовые понятия PKI (Public Key Infrastructure, Инфраструктура открытых ключей), такие как **CSR (Certificate Signing Request, Запрос на подпись сертификата)**, **SAN (Subject Alternative Name, Альтернативное имя субъекта)** и **CRL (Certificate Revocation List, Список отзыва сертификатов)**, подробно описаны в **[обзоре PKI](../../../Concepts/pki_overview.md)**.

В контексте управления сервисами:

- **DN (Distinguished Name, Отличительное имя)** — набор атрибутов (страна, организация, CN), однозначно идентифицирующих владельца сертификата.
- **CN (Common Name, Общее имя)** — основное имя субъекта в сертификате (например, полное доменное имя сервера).

## Базовые концепции

### Жизненный цикл сертификата сервиса

Процесс управления сертификатом по формальному методу включает следующие этапы:

1. **Генерация ключа и CSR:** выполняется на стороне сервиса (клиента).
2. **Передача запроса:** клиент отправляет CSR администратору CA (Certificate Authority, Центр сертификации).
3. **Валидация и подпись:** администратор проверяет данные, настраивает SAN и подписывает запрос.
4. **Установка:** готовый сертификат и цепочка доверия устанавливаются на целевой сервер.
5. **Мониторинг:** отслеживание срока действия для своевременного перевыпуска.
6. **Отзыв:** аннулирование сертификата в случае компрометации приватного ключа.

### Принципы управления

- **Разделение ответственности:** приватный ключ сервиса генерируется локально и никогда не передаётся администратору CA.
- **Централизованный контроль SAN:** администратор CA имеет приоритетное право определять список альтернативных имён (DNS-имен и IP-адресов) при подписи, чтобы исключить несанкционированный выпуск сертификатов на чужие домены.
- **Аудит:** все операции выпуска и отзыва фиксируются в базе данных CA (`db/index.txt`).

## Практические сценарии

### Выпуск сертификата с SAN

#### Шаг 1: Создание ключа и CSR на стороне клиента

Клиент генерирует приватный ключ и запрос на подпись. На данном этапе SAN указывать не обязательно, так как они будут переопределены администратором.

```bash
# Генерация приватного ключа RSA 4096 бит
openssl genrsa -out my-service.key 4096

# Создание запроса CSR
openssl req -new -key my-service.key -out my-service.csr \
    -subj "/C=RU/ST=Moscow/O=My Private Org/OU=Service/CN=my-service.local"
```

#### Шаг 2: Настройка расширений и подпись запроса

Администратор CA вносит актуальные DNS-имена и IP-адреса в конфигурационный файл `ca/openssl.cnf` (секция `[alt_names]`):

```ini
# ca/openssl.cnf
[alt_names]
DNS.1 = my-service.local
DNS.2 = api.my-service.local
IP.1  = 192.168.10.20
```

Затем выполняется подпись с использованием расширений для конечных сущностей (`v3_req`):

```bash
cd ca

# Подпись запроса (extensions v3_req активирует использование SAN из alt_names)
openssl ca -config openssl.cnf -in ../my-service.csr -out ../my-service.crt \
    -extensions v3_req -notext

cd ..
```

После выпуска необходимо проверить наличие расширения SAN в готовом сертификате:

```bash
openssl x509 -in my-service.crt -noout -text | grep -A1 "Subject Alternative Name"
```

### Установка корневого сертификата в доверенные хранилища

Для того чтобы клиенты (браузеры, утилиты) доверяли выпущенным сертификатам, корневой сертификат `ca.crt` должен быть добавлен в системное хранилище ОС.

**Debian / Ubuntu:**

```bash
sudo cp ca/ca.crt /usr/local/share/ca-certificates/my-private-ca.crt
sudo update-ca-certificates
```

**RHEL / CentOS / Fedora:**

```bash
sudo cp ca/ca.crt /etc/pki/ca-trust/source/anchors/
sudo update-ca-trust
```

### Отзыв сертификата и обновление CRL

В случае компрометации ключа сертификат необходимо отозвать и обновить список отзыва, чтобы клиенты могли узнать о его недействительности.

```bash
cd ca

# 1. Отзыв сертификата в базе данных
openssl ca -config openssl.cnf -revoke ../my-service.crt

# 2. Генерация обновленного файла CRL
openssl ca -config openssl.cnf -gencrl -out crl.pem

cd ..
```

Файл `ca/crl.pem` должен быть доступен клиентам для проверки (обычно через HTTP-ссылку, указанную в расширении сертификата).
