# Быстрый метод выпуска сертификатов

## Определения

**Быстрый метод** — упрощённый способ подписи сертификата напрямую через команду `openssl x509 -req`. В отличие от формального метода, он не требует ведения базы данных CA (Certificate Authority, Центр сертификации) и конфигурационного файла, но ограничивает возможности по учёту и отзыву.

**CA (Certificate Authority, Центр сертификации)** — доверенная сторона, подтверждающая подлинность открытых ключей путём выпуска цифровых сертификатов.

**CSR (Certificate Signing Request, Запрос на подпись сертификата)** — электронный документ, содержащий открытый ключ и информацию о владельце (Subject), отправляемый в CA для генерации сертификата.

**X.509** — стандарт, определяющий формат сертификатов открытых ключей.

**OpenSSL 3.0+** — современная версия инструментария, в которой многие команды подписи были упрощены, а поддержка алгоритмов на эллиптических кривых (ECDSA/Ed25519) стала стандартной практикой.

**SAN (Subject Alternative Name, Альтернативное имя субъекта)** — расширение сертификата, позволяющее указать несколько доменных имен и IP-адресов. В OpenSSL 3.x SAN можно передавать через CLI или временный файл расширений.

**CRL (Certificate Revocation List, Список отзыва сертификатов)** — механизм отзыва, недоступный в быстром методе из-за отсутствия базы данных CA.

## Базовые концепции

### Области применения

Быстрый метод ориентирован на сценарии, где скорость и простота приоритетнее строгого аудита:

- Прототипирование и разовые тесты (например, локальная настройка Nginx).
- Временные сертификаты для локальных сред разработки.
- Окружения, где механизмы отзыва (CRL/OCSP) не требуются.
- Генерация mTLS-сертификатов для краткосрочных сессий.
- Контейнеризированные окружения (Docker), где инфраструктура CA отсутствует и сертификат требуется "на лету".

### Структура пары SSL (Certificate Pair)

При генерации самоподписанного сертификата создается пара ключей:

- **Приватный ключ (Private Key, `.key`):** Хранится на сервере в строжайшем секрете. Используется сервером для расшифровки сообщений и подписи ответов.
- **Сертификат с публичным ключом (Public Key/Certificate, `.crt`):** Содержит информацию о сервере и открытый ключ. Передается всем клиентам (браузерам) для шифрования трафика перед отправкой на сервер.

### Ограничения

Поскольку быстрый метод не ведёт реестр выданных сертификатов, его применение имеет фундаментальные ограничения:

- **Отсутствие учёта:** невозможно отследить историю выпусков, так как данные не фиксируются в `index.txt`.
- **Невозможность отзыва:** без ведения базы данных нельзя сформировать полноценный CRL (Certificate Revocation List). Если ключ сервиса утерян или сертификат скомпрометирован, единственное решение — удаление сертификата с целевого сервера вручную.
- **Ручное управление SAN:** добавление альтернативных имён субъекта требует передачи параметров через CLI или временные файлы расширений.
- **Отсутствие аудита:** нет журнала операций, что недопустимо для compliance и forensic-анализа.
- **Риск коллизии серийных номеров:** при повторном запуске команды с флагом `-CAcreateserial` создаётся новый `.srl`-файл, что может привести к дублированию серийных номеров при параллельной работе.

Для долгосрочных проектов и производственных сред (production) используйте **[формальный метод управления CA](./overview.md#формальный-метод-подготовка-инфраструктуры)**.

### Принцип работы быстрого метода

В отличие от формального метода, который использует `openssl ca` с конфигурационным файлом и базой данных, быстрый метод выполняет подпись напрямую через `openssl x509 -req`. Команда читает CSR, применяет указанные расширения и подписывает его корневым ключом CA. Результат — готовый сертификат, но без записи в реестр. Флаг `-CAcreateserial` создаёт минимальный файл `.srl` с серийным номером, но это не заменяет полноценную базу данных.

## Практические сценарии

### Предварительные требования

#### Аппаратные и программные требования

- **ОС:** Linux (Debian/Ubuntu, RHEL/CentOS/Fedora, Alpine) или macOS. Инструкции tested на Linux x86_64.
- **OpenSSL:** версия 3.0.0 или выше. Проверка: `openssl version -a`.
- **Права:** доступ пользователя с возможностью чтения файлов CA (`ca/ca.crt`, `ca/ca.key`). Для установки сертификатов в системные хранилища требуются права `root` или `sudo`.
- **Дисплей:** для операций с парольной фразой (если ключ CA шифруется) требуется терминал с поддержкой ввода пароля.
- **Оболочка:** команды с процессной подстановкой `<(printf ...)` требуют оболочки Bash. В POSIX-совместимых окружениях (Alpine, dash) используйте временные файлы расширений.

#### Проверка окружения

```bash
# Проверка версии OpenSSL
openssl version -a
# → OpenSSL 3.0.x ...

# Проверка доступных провайдеров (OpenSSL 3.0+)
openssl list -providers
# → Providers:
# →  ... (default provider)
# →  ... (legacy provider, при необходимости)
```

#### Установка зависимостей

```bash
# Debian/Ubuntu
sudo apt update && sudo apt install -y openssl libssl-dev

# RHEL/CentOS/Fedora
sudo dnf install -y openssl openssl-devel

# Alpine
sudo apk add openssl openssl-dev
```

### Однострочная генерация «Ключ + Самоподписанный сертификат»

Самый быстрый способ создать пару для локального веб-сервера без отдельного CA.

```bash
# Генерация ключа RSA 4096 и самоподписанного сертификата на 1 год
openssl req -x509 -newkey rsa:4096 -sha256 -nodes \
    -keyout server.key -out server.crt \
    -days 365 \
    -subj "/C=RU/ST=Moscow/L=Moscow/O=Dev/CN=localhost"
# → Certificate and private key created
```

- `-x509`: создать самоподписанный сертификат вместо CSR.
- `-newkey rsa:4096`: сгенерировать новый 4096-битный RSA-ключ.
- `-nodes`: не шифровать приватный ключ паролем.
- `-days 365`: срок действия — 365 дней.
- `-subj`: задать Subject в одну строку, чтобы OpenSSL не запрашивал ввод интерактивно.

> **Важно:** самоподписанный сертификат не будет доверен клиентами автоматически. Его нужно добавить в доверенные хранилища целевых ОС вручную.

### Базовая подпись запроса (Flow: Key -> CSR -> CRT)

Процесс состоит из генерации пары «ключ + запрос» и последующей подписи вашим внутренним CA.

#### Шаг 1: Подготовка запроса

```bash
# Вариант А: RSA 4096 (Классика)
openssl req -new -newkey rsa:4096 -nodes \
    -keyout service.key -out service.csr \
    -subj "/CN=service.local"
# → Generating a RSA private key
# → Writing new private key to 'service.key'
# → -----
# → Certificate Request:
# →     Data:
# →         Version: 0 (0x0)
# →         ...

# Вариант Б: ECDSA P-384 (Современно, 2026)
openssl req -new -newkey ec:<(openssl ecparam -name secp384r1) -nodes \
    -keyout service.key -out service.csr \
    -subj "/CN=service.local"
```

- `-new`: создать новый CSR.
- `-newkey rsa:4096` / `-newkey ec:<(...)>`: сгенерировать новый ключ указанного типа.
- `-nodes`: не шифровать приватный ключ паролем.
- `-subj`: задать Subject без интерактивного ввода.

> **Примечание:** вариант с ECDSA использует процессную подстановку Bash `<( ... )`. В окружениях без Bash используйте отдельную команду для генерации параметров кривой:
> ```bash
> openssl ecparam -name secp384r1 -out secp384r1.pem
> openssl req -new -newkey ec:secp384r1.pem -nodes -keyout service.key -out service.csr -subj "/CN=service.local"
> ```

#### Шаг 2: Подпись корневым сертификатом

```bash
openssl x509 -req -in service.csr \
    -CA ca/ca.crt -CAkey ca/ca.key -CAcreateserial \
    -out service.crt -days 90 -sha384
# → Certificate created
```

- `-req`: входной файл — CSR, а не сертификат.
- `-CA`: путь к сертификату CA, который будет подписывать.
- `-CAkey`: путь к приватному ключу CA.
- `-CAcreateserial`: создать файл `service.srl` (или указанный вручную) с серийным номером. Если файл уже существует, номер будет инкрементирован.
- `-days 90`: срок действия подписанного сертификата.
- `-sha384`: алгоритм хеширования подписи.

**Ожидаемый результат:** в текущей директории появляются `service.crt`, `service.key` и `service.srl` (если его ещё нет).

### Выпуск сертификата с SAN через CLI

В OpenSSL 3.x можно передать альтернативные имена напрямую в командной строке, не создавая временный `.ext` файл.

```bash
openssl x509 -req -in service.csr \
    -CA ca/ca.crt -CAkey ca/ca.key -CAcreateserial \
    -out service.crt -days 90 -sha384 \
    -extfile <(printf "subjectAltName=DNS:service.local,DNS:www.service.local,IP:10.0.0.5")
# → Certificate created
```

**Пояснение:** параметр `-extfile` принимает данные в формате OpenSSL. `subjectAltName` является обязательным для современных браузеров и сервисов; поле `CN` в Subject игнорируется при наличии SAN.

> **Важно:** процессная подстановка `<(printf ...)` работает только в Bash. Для других оболочек создайте временный файл:
> ```bash
> echo "subjectAltName=DNS:service.local,DNS:www.service.local,IP:10.0.0.5" > /tmp/san.ext
> openssl x509 -req -in service.csr -CA ca/ca.crt -CAkey ca/ca.key -CAcreateserial -out service.crt -days 90 -sha384 -extfile /tmp/san.ext
> rm -f /tmp/san.ext
> ```

### Верификация результата

После выпуска необходимо убедиться в корректности цепочки доверия:

```bash
# Проверка цепочки (service.crt должен быть подписан ca.crt)
openssl verify -CAfile ca/ca.crt service.crt
# → service.crt: OK

# Просмотр расширений и алгоритма подписи
openssl x509 -in service.crt -noout -text | grep -E "Signature Algorithm|Subject Alternative Name" -A 1
# → Signature Algorithm: sha384WithRSAEncryption
# →             X509v3 Subject Alternative Name:
# →                 DNS:service.local, DNS:www.service.local, IP Address:10.0.0.5
```

### Верификация соответствия ключа и сертификата

```bash
# Для RSA
openssl x509 -noout -modulus -in service.crt | openssl sha256
openssl rsa -noout -modulus -in service.key | openssl sha256
# Хеши должны совпасть

# Для ECDSA/Ed25519
openssl x509 -in service.crt -pubkey -noout -outform DER | openssl sha256
openssl pkey -in service.key -pubout -outform DER | openssl sha256
# Хеши должны совпасть
```

### Очистка временных файлов

```bash
# Удаление серийного файла и временных расширений (если создавались)
rm -f service.srl /tmp/san.ext
```

## Типичные ошибки и диагностика

### Ошибка: `unable to load certificate` / `certificate verify failed`

**Причина:** Путь к `ca.crt` или `ca.key` указан неверно, файлы повреждены или у процесса нет прав на чтение.

**Диагностика:**
```bash
# Проверка доступности файлов
ls -la ca/ca.crt ca/ca.key

# Проверка читаемости
file ca/ca.crt ca/ca.key
openssl x509 -in ca/ca.crt -noout -text
```

### Ошибка: `signature routines::unsupported algorithm`

**Причина:** Алгоритм хеширования, указанный в `-sha384`, не поддерживается провайдером OpenSSL 3.0+.

**Решение:** используйте `-sha256` или явно укажите провайдер Legacy:
```bash
openssl x509 -req -in service.csr -CA ca/ca.crt -CAkey ca/ca.key -CAcreateserial -out service.crt -days 90 -sha256 -provider legacy
```

### Ошибка: `Error loading extension` / `invalid extension`

**Причина:** Синтаксис `subjectAltName` в `-extfile` указан неверно (отсутствуют `DNS:` или `IP:`, некорректные пробелы).

**Решение:** проверьте синтаксис:
```bash
# Корректный формат
subjectAltName=DNS:service.local,DNS:www.service.local,IP:10.0.0.5

# Некорректные примеры:
# subjectAltName=service.local           ← нет префикса DNS:
# subjectAltName=DNS:service.local IP:10.0.0.5  ← запятая вместо пробела
```

### Ошибка: `serial file already exists` / `trying to commit certificate twice`

**Причина:** Файл `.srl` с серийным номером уже существует, и OpenSSL не может его прочитать или записать.

**Решение:**
```bash
# Проверка содержимого
cat service.srl

# Переинициализация (если нет конфликта с другими сертификатами)
echo "1000" > service.srl
```

### Ошибка: `No value for key` / `unable to find key`

**Причина:** Флаг `-CAkey` указан, но ключ зашифрован парольной фразой, и OpenSSL не может его прочитать в неинтерактивном режиме.

**Решение:** либо вводите парольную фразу при запросе, либо используйте незашифрованный ключ для тестовых сред.

## Рекомендации и лучшие практики

### Когда использовать быстрый метод

- Локальная разработка и CI-конвейеры, где trust store управляется отдельно.
- Временные сертификаты для тестирования совместимости TLS.
- Генерация корневых сертификатов для встроенных устройств (IoT) в закрытых сетях.
- Документированные POC-сценарии, где требуется минимальная сложность развертывания.

### Когда НЕ использовать

- Производственные сервисы с требованием compliance (PCI DSS, HIPAA, 152-ФЗ).
- Среды с более чем 50 конечными сертификатами, где требуется централизованный аудит.
- Системы, где требуется возможность экстренного отзыва без переустановки сертификатов.
- Любые сценарии, где корневой ключ CA защищен парольной фразой и хранится в офлайн.

### Безопасность при работе с быстрым методом

- **Никогда не передавайте приватный ключ CA по сети.** Все операции с `ca.key` выполняйте на машине, где хранится CA.
- **Храните `service.key` с правами `600`.** Утечка приватного ключа сервиса позволяет impersonate-атаки.
- **Используйте `-days` разумно.** Сертификаты на 365 дней облегчают ротацию, но требуют напоминаний о перевыпуске.
- **Шифруйте ключи для production.** Если используете быстрый метод в production, защищайте ключ парольной фразой и извлекайте его из систем управления секретами (Vault, HashiCorp Vault) только во время подписи.

## Ограничения и крайние случаи

- **Число сертификатов:** для сред с более чем 100 конечными узлами рекомендуется переход на двухуровневую архитектуру из-за нагрузки на корневой ключ.
- **Сервисы с жесткими требованиями к совместимости:** некоторые устаревшие системы (например, старые Java-приложения до версии 8) могут требовать RSA-ключей и специфических расширений.
- **Автоматизация:** без использования HSM или систем управления секретами (Vault) автоматизация подписи в production не рекомендуется из-за риска несанкционированного доступа к ключу.
- **Регуляторные требования:** в некоторых отраслях (финансы, медицина) требуется использование двухуровневой архитектуры и сертифицированных криптографических средств (СКЗИ).
- **Совместимость оболочек:** команды с `<(printf ...)` требуют Bash. В Alpine Linux, Ubuntu/Debian (где `/bin/sh` → dash) используйте явный вызов Bash или временные файлы.
- **Кодировка:** при использовании не-ASCII символов в `-subj` (кириллица, иероглифы) убедитесь, что терминал работает в UTF-8, иначе OpenSSL может создать некорректный DN.

## Очистка и откат изменений

### Удаление сгенерированных сертификатов и ключей

```bash
# Удаление сервисных файлов
rm -f service.crt service.key service.csr service.srl

# Удаление установленных корневых сертификатов из доверенных хранилищ ОС
# Debian/Ubuntu
sudo update-ca-certificates --fresh

# RHEL/CentOS/Fedora
sudo update-ca-trust
```

### Откат тестового окружения

Если сертификат был установлен в приложение (Nginx, Apache, Java Keystore), выполните откат в обратном порядке:

1. Удалите сертификат из конфигурации сервиса.
2. Перезапустите сервис.
3. Удалите корневой сертификат из доверенного хранилища ОС/контейнера.
4. Удалите файлы CA и сгенерированные ключи.
