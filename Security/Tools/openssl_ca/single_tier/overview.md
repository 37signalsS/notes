# Обзор одноуровневого центра сертификации (CA) на OpenSSL

## Определения

**CA (Certificate Authority, Центр сертификации)** — доверенная сущность, выпускающая цифровые сертификаты для подтверждения подлинности открытых ключей.

**Одноуровневый CA** — простейшая архитектура PKI, в которой один корневой CA напрямую подписывает сертификаты конечных сущностей (серверов, клиентов, пользователей). В этой схеме отсутствует разделение на корневой (Root) и выпускающий (Issuing/Intermediate) уровни.

**OpenSSL 3.0+** — актуальное поколение криптографического тулсета, в котором архитектура перешла на использование провайдеров (Default, FIPS, Legacy). Параметр `RANDFILE` не нужен с OpenSSL 1.1.1 и сохраняется лишь для обратной совместимости.

**mTLS (Mutual TLS, Взаимный TLS)** — стандарт безопасности для взаимодействия микросервисов, требующий обязательной аутентификации как сервера, так и клиента с помощью сертификатов.

**Криптографические стандарты (2026)** — для внутренних систем и mTLS рекомендуется переход с классического RSA на **ECDSA (кривая P-384)** или **Ed25519**, что обеспечивает высокую производительность при меньшем потреблении ресурсов CPU.

Подробные базовые понятия PKI (CSR, SAN, CRL, OCSP) описаны в **[обзоре PKI](../../../Concepts/pki_overview.md)**.

## Базовые концепции

### Назначение одноуровневого CA

Внутренний CA необходим для обеспечения доверенной среды внутри инфраструктуры организации. Одноуровневая архитектура применяется в следующих случаях:
- Среды разработки (Dev) и тестирования (QA/Staging).
- Малые изолированные сети с ограниченным числом узлов.
- Начальные этапы внедрения mTLS.
- Временные инфраструктуры для POC (Proof of Concept).

### Сравнение с двухуровневой архитектурой

| Критерий | Одноуровневый CA | Двухуровневый CA |
| :--- | :--- | :--- |
| **Безопасность** | Низкая — компрометация ключа требует смены всех сертификатов. | Высокая — Root CA находится в офлайне, компрометация Intermediate ограничена. |
| **Сложность** | Минимальная — один конфиг, одна база данных. | Средняя — иерархия баз данных и цепочек доверия. |
| **Управление** | Онлайн (ключ постоянно доступен для подписи). | Гибрид (Root — офлайн, Intermediate — онлайн). |
| **Производительность** | Высокая (короткая цепочка проверки). | Ниже (проверка всей цепочки до корня). |
| **Применение** | Внутренние тесты, IoT, малые сети. | Production, Enterprise, Cloud. |

Для критических производственных систем (Production) строго рекомендуется **[двухуровневая архитектура](../two_tier/overview.md)**.

### Подходы к управлению CA

В рамках OpenSSL одноуровневого CA выделяют два метода:

1. **Формальный метод (Standard)**:
   - Использует `openssl ca`.
   - Требует конфигурационный файл и базу данных (`index.txt`).
   - Позволяет вести историю выпусков, отзывать сертификаты и генерировать списки отзыва (CRL).
   - **Вывод**: Рекомендуется для долгосрочного использования.

2. **Быстрый метод (Lightweight)**:
   - Использует `openssl x509 -req`.
   - Не требует базы данных.
   - Минимальный набор флагов в командной строке.
   - **Вывод**: Только для разовых задач, так как механизм отзыва практически нереализуем.

### Доверительная модель и цепочка доверия

В одноуровневой архитектуре цепочка доверия состоит из двух звеньев:
- Конечный сертификат сервиса (подписан корневым CA).
- Корневой сертификат CA (самоподписанный, `ca.crt`).

Клиент (браузер, ОС, сервис) доверяет сертификату сервиса, если он может проследить цепочку до корневого CA, который присутствует в его доверенном хранилище. В отличие от двухуровневой схемы, здесь отсутствует промежуточное звено, что упрощает верификацию, но увеличивает риск при компрометации корня.

### Безопасность и риски

**Ключевой риск — компрометация корневого ключа.**
Поскольку корневой CA постоянно доступен онлайн для подписи новых сертификатов, его приватный ключ (`ca.key`) является единственной точкой отказа. При утечке или потере этого ключа:
- Все сертификаты, выданные данным CA, становятся ненадежными.
- Требуется полная перевыпуск всей инфраструктуры доверия (отзыв всех сертификатов, генерация нового корня, распространение нового корня на всех клиентов).

**Меры смягчения рисков:**
- **Ограничение доступа:** доступ к директории CA только для пользователя `root` или выделенного сервисного аккаунта.
- **Шифрование ключа:** в production-средах ключ `ca.key` должен быть защищен парольной фразой (флаг `-aes256` при генерации).
- **Аудит:** ведение журнала всех операций подписи через `index.txt` и `db/`.
- **Изоляция сети:** размещение CA в отдельном сегменте с доступом только для администраторов.

### Производительность и масштабирование

**Преимущества одноуровневой схемы:**
- **Скорость верификации:** цепочка состоит из одного звена, что снижает накладные расходы при TLS-handshake.
- **Простота управления:** один конфигурационный файл, одна база данных, один набор инструментов.

**Ограничения:**
- **Нагрузка на ключ:** при более чем 100 конечных сертификатах операция подписи может стать узким местом, так как все запросы обрабатываются одним ключом.
- **Отсутствие отказоустойчивости:** для обеспечения высокой доступности (HA) требуется организация горячего резерва (replica) CA с синхронизацией базы данных, что усложняет архитектуру и приближает ее к двухуровневой.

## Практические сценарии

### Предварительные требования

Перед началом работы убедитесь, что окружение соответствует минимальным требованиям:
- **OpenSSL 3.0+** с поддержкой провайдеров Default и Legacy.
- **Права root** или выделенного пользователя с доступом к файловой системе CA.
- **Терминал** с поддержкой ввода парольной фразы (если ключ шифруется).

Подробные инструкции по установке и проверке окружения приведены в **[Настройка CA и конфигурация openssl.cnf](./ca_setup.md#предварительные-требования)**.

### Формальный метод: подготовка инфраструктуры

Для корректной работы формального метода OpenSSL 3.x необходимо создать структуру директорий и инициализировать служебные файлы.

```bash
# Основная директория проекта
mkdir -p internal-ca && cd internal-ca

# Создание структуры БД
mkdir -p db/{newcerts,crl}
touch db/index.txt          # База данных
echo "1000" > db/serial     # Hex-счетчик серийных номеров
echo "1000" > db/crlnumber   # Hex-счетчик номеров CRL
```

**Описание структуры:**
- `db/index.txt` — текстовый реестр всех выпущенных сертификатов (статус, дата, DN).
- `db/serial` — определяет ID следующего сертификата. Автоматически инкрементируется OpenSSL.
- `db/newcerts/` — каталог, куда OpenSSL сохраняет копии всех подписанных сертификатов.

**Жизненный цикл одноуровневого CA:**
1. **[Настройка CA и создание корня](./ca_setup.md)** — подготовка `openssl.cnf` и генерация самоподписанного сертификата.
2. **[Выпуск сертификатов сервисов](./service_certificate_management.md)** — обработка CSR, работа с SAN и отзыв.
3. **[Утилиты и диагностика](./common_utilities.md)** — команды для проверки валидности и отладки TLS-соединений.

### Быстрый метод: экспресс-выпуск

Для создания сертификата "на лету" (например, для локального Nginx в Docker) используйте упрощенный подход. Инструкции и примеры команд находятся в разделе **[быстрый метод выпуска](./quick_method.md)**.

### Жизненный цикл инфраструктуры

Полный цикл эксплуатации одноуровневого CA включает следующие этапы:

1. **Планирование и развертывание:**
   - Выбор алгоритма (RSA-4096, ECDSA P-384, Ed25519) в зависимости от совместимости и производительности.
   - Создание структуры директорий и базы данных (`index.txt`, `serial`).
   - Генерация корневого ключа и самоподписанного сертификата с расширениями `CA:true`.

2. **Эксплуатация:**
   - Прием CSR от сервисов, проверка SAN и подпись через `openssl ca`.
   - Ведение журнала выданных сертификатов в `db/index.txt`.
   - Плановая ротация сертификатов (рекомендуется за 10–20% до истечения срока).
   - Мониторинг срока действия корневого сертификата (обычно 10 лет).

3. **Аварийное реагирование:**
   - Отзыв скомпрометированных сертификатов через `openssl ca -revoke`.
   - Генерация и распространение обновленного CRL.
   - При компрометации корневого ключа — полная перевыпуск инфраструктуры.

4. **Деактивация:**
   - Удаление корневого сертификата из доверенных хранилищ всех клиентов.
   - Архивирование или безопасное уничтожение ключей в соответствии с политикой данных организации.

### Верификация на архитектурном уровне

После развертывания CA необходимо проверить целостность всей инфраструктуры:

- **Верификация корневого сертификата:** `openssl verify -CAfile ca/ca.crt ca/ca.crt` должен возвращать `OK`.
- **Проверка соответствия ключа и сертификата:** сравнение хешей публичного ключа (для ECDSA/Ed25519) или модуля (для RSA).
- **Тестовый выпуск:** создание тестового сертификата и проверка его подписи через `openssl verify`.
- **Проверка в ОС:** убедитесь, что корневой сертификат присутствует в доверенном хранилище целевых ОС.

### Типичные ошибки проектирования

1. **Использование одноуровневой архитектуры в Production** — приводит к необходимости полной перевыпуск при любом инциденте с корневым ключом. Для Production используйте **[двухуровневую архитектуру](../two_tier/overview.md)**.
2. **Отсутствие SAN в конфигурации** — современные браузеры и сервисы игнорируют поле CN, если отсутствует SAN.
3. **Хранение ключа в репозитории или backup без шифрования** — приватный ключ должен быть защищен парольной фразой и храниться на физически изолированных носителях.
4. **Использование устаревших алгоритмов** (SHA-1, RSA-1024) — снижает стойкость всей инфраструктуры.
5. **Отсутствие CRL или OCSP** — при компрометации сертификата клиенты не смогут проверить его отзыв.

### Ограничения и крайние случаи

- **Число сертификатов:** для сред с более чем 100 конечными узлами рекомендуется переход на двухуровневую архитектуру из-за нагрузки на корневой ключ.
- **Сервисы с жесткими требованиями к совместимости:** некоторые устаревшие системы (например, старые Java-приложения до версии 8) могут требовать RSA-ключей и специфических расширений.
- **Автоматизация:** без использования HSM или систем управления секретами (Vault) автоматизация подписи в production не рекомендуется из-за риска несанкционированного доступа к ключу.
- **Регуляторные требования:** в некоторых отраслях (финансы, медицина) требуется использование двухуровневой архитектуры и сертифицированных криптографических средств (СКЗИ).

### Очистка и откат изменений

#### Удаление CA и всех сертификатов

```bash
# Полное удаление директории CA (необратимо!)
rm -rf ca/

# Удаление установленных корневых сертификатов из доверенных хранилищ ОС
# Debian/Ubuntu
sudo update-ca-certificates --fresh

# RHEL/CentOS/Fedora
sudo update-ca-trust
```

#### Отзыв всех сертификатов (экстренный сценарий)

```bash
# Переход в директорию CA
cd ca

# Отзыв всех сертификатов через скрипт (аккуратно!)
for cert in db/newcerts/*.pem; do
    openssl ca -config openssl.cnf -revoke "$cert"
done

# Генерация нового CRL
openssl ca -config openssl.cnf -gencrl -out crl.pem

# Распространение нового CRL на все сервисы
```
