# Обзор одноуровневого центра сертификации (CA) на OpenSSL

## Определения

**CA (Certificate Authority, Центр сертификации)** — доверенная сущность, выпускающая цифровые сертификаты для подтверждения подлинности открытых ключей.

**Одноуровневый CA** — простейшая архитектура PKI, в которой один корневой CA напрямую подписывает сертификаты конечных сущностей (серверов, клиентов, пользователей). В этой схеме отсутствует разделение на корневой (Root) и выпускающий (Issuing/Intermediate) уровни.

**OpenSSL 3.0+** — актуальное поколение криптографического тулсета, в котором архитектура перешла на использование провайдеров (Default, FIPS, Legacy) и были депрецированы многие устаревшие параметры конфигурации (например, `RANDFILE`).

**mTLS (Mutual TLS, Взаимный TLS)** — стандарт безопасности для взаимодействия микросервисов, требующий обязательной аутентификации как сервера, так и клиента с помощью сертификатов.

**Криптографические стандарты (2026)** — для внутренних систем и mTLS рекомендуется переход с классического RSA на **ECDSA (кривая P-384)** или **Ed25519**, что обеспечивает высокую производительность при меньшем потреблении ресурсов CPU.

Подробные базовые понятия PKI (CSR, SAN, CRL, OCSP) описаны в **[обзоре PKI](../../../Concepts/pki_overview.md)**.

## Базовые концепции

### Назначение одноуровневого CA

Внутренний CA необходим для обеспечения доверенной среды внутри инфраструктуры организации. Одноуровневая архитектура применяется в следующих случаях:
- Среды разработки (Dev) и тестирования (QA/Staging).
- Малые изолированные сети с ограниченным числом узлов.
- Начальные этапы внедрения mTLS.
- Временные инфраструктуры для POC (Proof of Concept).

### Сравнение с двухуровневой архитектурой

| Критерий | Одноуровневый CA | Двухуровневый CA |
| :--- | :--- | :--- |
| **Безопасность** | Низкая — компрометация ключа требует смены всех сертификатов. | Высокая — Root CA находится в офлайне, компрометация Intermediate ограничена. |
| **Сложность** | Минимальная — один конфиг, одна база данных. | Средняя — иерархия баз данных и цепочек доверия. |
| **Управление** | Онлайн (ключ постоянно доступен для подписи). | Гибрид (Root — офлайн, Intermediate — онлайн). |
| **Производительность** | Высокая (короткая цепочка проверки). | Ниже (проверка всей цепочки до корня). |
| **Применение** | Внутренние тесты, IoT, малые сети. | Production, Enterprise, Cloud. |

Для критических производственных систем (Production) строго рекомендуется **[двухуровневая архитектура](../two_tier/overview.md)**.

### Подходы к управлению CA

В рамках OpenSSL одноуровневого CA выделяют два метода:

1. **Формальный метод (Standard)**:
   - Использует `openssl ca`.
   - Требует конфигурационный файл и базу данных (`index.txt`).
   - Позволяет вести историю выпусков, отзывать сертификаты и генерировать списки отзыва (CRL).
   - **Вывод**: Рекомендуется для долгосрочного использования.

2. **Быстрый метод (Lightweight)**:
   - Использует `openssl x509 -req`.
   - Не требует базы данных.
   - Минимальный набор флагов в командной строке.
   - **Вывод**: Только для разовых задач, так как механизм отзыва практически нереализуем.

## Практические сценарии

### Формальный метод: подготовка инфраструктуры

Для корректной работы формального метода OpenSSL 3.x необходимо создать структуру директорий и инициализировать служебные файлы.

```bash
# Основная директория проекта
mkdir -p internal-ca && cd internal-ca

# Создание структуры БД
mkdir -p db/{newcerts,crl}
touch db/index.txt          # База данных
echo "1000" > db/serial     # Hex-счетчик серийных номеров
echo "1000" > db/crlnumber   # Hex-счетчик номеров CRL
```

**Описание структуры:**
- `db/index.txt` — текстовый реестр всех выпущенных сертификатов (статус, дата, DN).
- `db/serial` — определяет ID следующего сертификата. Автоматически инкрементируется OpenSSL.
- `db/newcerts/` — каталог, куда OpenSSL сохраняет копии всех подписанных сертификатов.

**Жизненный цикл одноуровневого CA:**
1. **[Настройка CA и создание корня](./ca_setup.md)** — подготовка `openssl.cnf` и генерация самоподписанного сертификата.
2. **[Выпуск сертификатов сервисов](./service_certificate_management.md)** — обработка CSR, работа с SAN и отзыв.
3. **[Утилиты и диагностика](./common_utilities.md)** — команды для проверки валидности и отладки TLS-соединений.

### Быстрый метод: экспресс-выпуск

Для создания сертификата "на лету" (например, для локального Nginx в Docker) используйте упрощенный подход. Инструкции и примеры команд находятся в разделе **[быстрый метод выпуска](./quick_method.md)**.
