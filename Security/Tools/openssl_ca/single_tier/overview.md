# Обзор одноуровневого CA на OpenSSL

## Определения

**Одноуровневый CA** — архитектура центра сертификации, в которой корневой CA напрямую подписывает сертификаты конечных сущностей (серверов, клиентов) без промежуточного звена. Подходит для тестовых сред и небольших организаций.

**Форматы файлов** (подробнее в [обзоре PKI](../../../Concepts/pki_overview.md)):

- `.key` — приватный ключ. Хранить в секрете.
- `.csr` (Certificate Signing Request) — запрос на подпись сертификата.
- `.crt` / `.cer` — подписанный сертификат X.509.
- `.pem` — текстовый Base64-контейнер для ключей, сертификатов, цепочек.

**Ключевые расширения и механизмы** (подробнее в [обзоре PKI](../../../Concepts/pki_overview.md#механизмы-отзыва-сертификатов)):

- **SAN (Subject Alternative Name)** — расширение, позволяющее указать несколько доменов/IP в одном сертификате.
- **CRL (Certificate Revocation List)** — список отозванных сертификатов.
- **OCSP (Online Certificate Status Protocol)** — протокол онлайн-проверки статуса отзыва.

**mTLS (Mutual TLS)** — взаимная аутентификация, при которой клиент и сервер проверяют сертификаты друг друга ([подробнее](../../../../WebServers/Nginx/Security/TLS_SSL/nginx_tls_ssl_overview.md#mutual-tls-mtls)).

## Базовые концепции

### Назначение одноуровневого CA

OpenSSL CA необходим для выпуска доверенных SSL/TLS-сертификатов для внутренних сервисов, разработки, тестирования и реализации mTLS. Одноуровневая архитектура — простейший вариант, где один ключ выполняет функции и корневого, и выпускающего CA.

### Сравнение с двухуровневой архитектурой

| Критерий | Одноуровневый CA | Двухуровневый CA |
| :--- | :--- | :--- |
| **Безопасность** | Низкая — один ключ для всего | Высокая — Root CA офлайн |
| **Сложность** | Минимальная | Средняя |
| **Отзыв сертификатов** | Да (формальный метод) | Да, с изоляцией уровней |
| **Применение** | Тесты, dev, малые сети | Production, enterprise |

Для production-сред настоятельно рекомендуется [двухуровневая архитектура](../two_tier/overview.md), где корневой ключ используется один раз и убирается в офлайн (air-gapped).

### Подходы к управлению CA

В рамках одноуровневого CA доступны два подхода:

1. **Формальный метод** — полноценная структура CA с базой данных сертификатов (`db/index.txt`, `db/serial`, `db/newcerts/`). Рекомендуется для управления множеством сертификатов, поддерживает учёт и отзыв.
2. **Быстрый метод** — упрощённая подпись CSR напрямую через `openssl x509 -req` без ведения базы данных. Подходит для разовых тестов.

## Практические сценарии

### Формальный метод: создание структуры CA

```bash
# Основная директория
mkdir -p ca

# Вложенная структура для базы данных и сертификатов
mkdir -p ca/db/{newcerts,crl}
touch ca/db/index.txt        # База данных выданных сертификатов
echo "1000" > ca/db/serial   # Начальный серийный номер в hex
echo "1000" > ca/db/crlnumber # Начальный номер для CRL
```

**Назначение файлов базы данных:**

- `db/index.txt` — главная база данных CA. OpenSSL хранит информацию о каждом сертификате: статус (`V` — действителен, `R` — отозван), срок истечения, серийный номер и subject. Пример: `V  270126151041Z  1000 unknown /C=RU/ST=Moscow/O=My Private Org/CN=site1.local`.
- `db/serial` — серийный номер для **следующего** сертификата. После каждого выпуска `openssl ca` считывает номер и инкрементирует его.
- `db/crlnumber` — аналог `serial`, но для списков отзыва (CRL).
- `db/newcerts/` — архив всех выданных сертификатов. `openssl ca` сохраняет сюда копию под именем `<serial>.pem`.
- `crl/` — директория для сгенерированных списков отзыва (`.crl` файлов).

Итоговая структура:

```
ca/
├── ca.key         # Приватный ключ CA
├── ca.crt         # Корневой сертификат
├── openssl.cnf    # Правила работы CA
├── crl.pem        # Текущий CRL (после генерации)
└── db/
    ├── index.txt  # База сертификатов
    ├── serial     # Счётчик серийных номеров
    ├── crlnumber  # Счётчик CRL
    ├── newcerts/  # Архив выданных cert
    └── crl/       # Списки отзыва
```

После подготовки структуры выполняются:

1. [Создание корневого ключа и сертификата CA](./ca_setup.md)
2. [Выпуск сертификатов сервисов](./service_certificate_management.md)
3. [Утилиты и диагностика](./common_utilities.md)

### Быстрый метод: упрощённая подпись CSR

Без ведения базы данных, напрямую через `openssl x509 -req`. Подходит для быстрых тестов, но не поддерживает учёт и отзыв сертификатов. Подробнее — [быстрый метод выпуска](./quick_method.md).
