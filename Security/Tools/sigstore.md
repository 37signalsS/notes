# Sigstore: Безопасность цепочки поставок ПО

## Определения

**Sigstore** ([sigstore.dev](https://www.sigstore.dev/)) — это открытая экосистема и набор стандартов для безопасной подписи, верификации и обеспечения прозрачности программных артефактов (образов контейнеров, бинарных файлов, SBOM, весов ИИ-моделей). Sigstore устраняет необходимость управления долгоживущими закрытыми ключами, заменяя их краткосрочными сертификатами на основе идентичности пользователя.

В 2026 году Sigstore является индустриальным стандартом де-факто для обеспечения безопасности цепочки поставок (**Supply Chain Security**), поддерживая спецификации OCI 1.1 и постквантовую криптографию (**PQC**).

## Основные концепции

### Компоненты экосистемы

Sigstore объединяет три ключевые технологии для создания доверенной среды:

1.  **Fulcio (CA для Keyless-подписи):**
    *   Корневой удостоверяющий центр (CA), который выдает краткосрочные (10–20 минут) сертификаты X.509.
    *   Основан на **OpenID Connect (OIDC)**: сертификат привязывается к подтвержденной личности (email, GitHub/GitLab раннер, workload identity).
    *   Использует **SCT (Signed Certificate Timestamp)** для доказательства включения в лог прозрачности сертификатов.
2.  **Rekor (Журнал прозрачности / Transparency Log):**
    *   Неизменяемый реестр (Immutable Ledger) для записи всех событий подписи и метаданных.
    *   Базируется на структуре **дерева Меркла** (Merkle Tree), что позволяет криптографически доказать наличие записи без загрузки всего лога.
    *   Генерирует **SET (Signed Entry Timestamp)** — доказательство того, что подпись была зафиксирована в логе в определенное время.
3.  **Cosign (CLI-инструмент):**
    *   Основная утилита для подписи и проверки артефактов.
    *   В 2026 году полностью поддерживает **OCI 1.1 Referrers API**, что позволяет хранить подписи как связанные объекты реестра, а не через дополнительные теги.

### Keyless-подпись: Механизм работы

1.  **Генерация:** Пользователь (или CI) генерирует эфемерную пару ключей (только в памяти).
2.  **Аутентификация:** Получение OIDC токена от провайдера (GitHub, Google и т.д.).
3.  **Сертификация:** Fulcio проверяет OIDC токен и выдает сертификат, где в поле `Subject` указана личность пользователя, а публичный ключ — сгенерированный на этапе 1.
4.  **Публикация:** Метаданные (сертификат + подпись) отправляются в Rekor.
5.  **Подписание:** Артефакт подписывается эфемерным закрытым ключом, который затем уничтожается.

### Gitsign: Подпись коммитов без ключей

**Gitsign** — это расширение Sigstore для Git, которое позволяет подписывать коммиты с использованием OIDC идентичности вместо традиционных GPG/SSH ключей. Это предотвращает атаки на подмену авторства в репозиториях без оверхеда на управление ключами разработчиков.

## Практические сценарии

### Keyless-подпись в GitHub Actions (2026)

В современных пайплайнах Cosign автоматически использует "Ambient Credentials" (OIDC токены раннера).

```yaml
jobs:
  build-and-sign:
    permissions:
      contents: read
      packages: write
      id-token: write # Обязательно для Keyless/Fulcio
    steps:
      - uses: sigstore/cosign-installer@v3
      - name: Sign the container image
        # В 2026 Cosign по умолчанию использует OCI 1.1 и ML-DSA (PQC)
        run: cosign sign --yes ghcr.io/${{ github.repository }}:latest
```

### Проверка подписи с контролем идентичности

Просто проверки факта наличия подписи недостаточно. Важно проверять **кто** подписал артефакт.

```bash
cosign verify \
  --certificate-identity "https://github.com/my-org/my-repo/.github/workflows/release.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  ghcr.io/my-org/my-app:latest
```

### Подпись и аттестация SBOM

Sigstore позволяет связывать SBOM с образом, создавая проверяемое доказательство состава ПО.

```bash
# Привязка SBOM в формате CycloneDX 1.6+ к образу
cosign attest --yes --predicate sbom.json --type cyclonedx ghcr.io/my-org/my-app:latest
```

### Использование PQC-алгоритмов

Для защиты от будущих квантовых атак рекоменуется использовать алгоритмы семейства **ML-DSA** (FIPS 204). Поддержка ML-DSA в Cosign находится в экспериментальной фазе (на 2026 год не включена в стабильные релизы). Для PQC-подписи используйте KMS с поддержкой ML-DSA (HashiCorp Vault, AWS KMS, GCP KMS) с аннотациями:

```bash
# Гибридная подпись: ECDSA (keyless через Fulcio) + ML-DSA (через KMS)
cosign sign --yes --tlog-upload=true my-registry.com/image:v1
cosign sign --yes --key "hashivault://mldsa-signing-key" \
  --annotations "signing.dev/algorithm=ML-DSA-65" \
  my-registry.com/image:v1
```

## Дополнительная информация

### Интеграция с Kubernetes и Policy Controllers

Для обеспечения безопасности в рантайме подписи должны проверяться автоматически перед запуском пода.
*   **Kyverno:** Лидирующее решение для верификации подписей и аттестаций (VSA/VEX) через `verifyImages`.
*   **Sigstore Policy Controller:** Нативный контроллер Sigstore для реализации политик допуска.
*   **Ratify:** Проект для верификации подписей в Azure/AWS средах с поддержкой OCI 1.1.

### Сравнение: Sigstore vs Notation

| Характеристика | Sigstore (Cosign) | Notation (Notary v2) |
| :--- | :--- | :--- |
| **Управление ключами** | Преимущественно Keyless (OIDC) | Традиционные X.509 / KMS / HSM |
| **Прозрачность** | Встроенный Rekor Log | Опционально через внешние логи |
| **Сфера применения** | Open Source, Cloud Native CI/CD | Enterprise PKI, закрытые контуры |
| **Хранение** | OCI Referrers / Tags | OCI Referrers |

### Рекомендации по эксплуатации

1.  **OCI 1.1 Referrers:** Всегда используйте современные реестры (Harbor v2.15+, GHCR, ECR) для хранения подписей без создания лишних тегов.
2.  **Short-lived certs:** Не увеличивайте время жизни сертификатов Fulcio выше 10–15 минут.
3.  **TUF (The Update Framework):** Помните, что Sigstore обеспечивает целостность *конкретного* артефакта, в то время как TUF защищает систему дистрибуции в целом (откаты, подмены репозитория).
