# Роль журналов (logs) в аудите и обеспечении соответствия требованиям

Журналы (логи) — основной источник доказательств при проверке соответствия требованиям регуляторов и внутренних политик. Они позволяют восстановить ход событий, подтвердить соблюдение контролей, обнаружить несанкционированные действия и обосновать управленческие решения. Для аудита важны не столько «все логи», сколько корректно спроектированная система протоколирования, гарантирующая целостность, полноту и интерпретируемость записей.

## Ключевые свойства аудиторских логов

- **Полнота**: Фиксируются все существенные события в пределах определенного периметра (идентификация, аутентификация, авторизация, изменения конфигурации, доступ к чувствительным данным, действия с повышенными привилегиями, выпуск в прод).
- **Точность времени**: Синхронизация по NTP, единый формат времени (UTC, ISO 8601), монотонность и указание источника времени.
- **Неизменяемость и целостность**: Использование WORM-хранилищ, версионирование, контрольные суммы/хеш‑цепочки, цифровые подписи, фиксация цепочки хранения (chain of custody).
- **Контекст и структурированность**: Единая схема полей, идентификаторы корреляции (`trace_id`), информация о субъекте, объекте и результате действия.
- **Доступность и безопасность**: Централизованная доставка (агенты/форвардеры) по защищенным каналам, контроль доступа по принципу наименьших привилегий, шифрование «в полете» и «на диске».
- **Конфиденциальность и минимизация**: Маскирование PII/секретов, псевдонимизация, политики хранения и удаления в соответствии с требованиями.

## Что логировать для аудита

| Тип события | Что фиксировать | Зачем аудиту |
| :--- | :--- | :--- |
| Аутентификация/сессии | субъект, метод, источник, результат | доказательство контроля доступа |
| Привилегированные действия | команда/операция, объект, контекст | подотчетность и неотказуемость |
| Изменения конфигурации/IaC | кто, что, из какой ветки/релиза | прослеживаемость изменений |
| Доступ к данным | тип данных, объем, цель, статус | соблюдение принципов минимизации |
| Выпуск и операции CI/CD | пайплайн, артефакт, среда, одобрения | соответствие процессам change management |
| Сетевые и K8s политики | правило, субъект, эффект | соответствие сегментации и RBAC |

## Схема записи и пример

Единая схема облегчает анализ и проверку контролей. Минимальный набор полей: `timestamp`, `subject`, `action`, `object`, `outcome`, `reason`, `source` (ip/agent), `env`, `trace_id`, `integrity_hash`.

Пример структурированного события:

```json
{
  "ts": "2025-04-12T10:15:30Z",
  "subject": "alice",
  "action": "update",
  "object": "k8s/deployment/payments",
  "status": "success",
  "ip": "203.0.113.5",
  "trace_id": "4f2b8c1f...",
  "env": "prod",
  "reason": "pipeline#248",
  "integrity_hash": "sha256:9a..."
}
```

## Централизация и доказательная сила

- **Транспорт**: Надежная доставка с подтверждением, буферизация на узлах, повтор при сбоях, TLS/mTLS между агентами и приёмниками.
- **Хранилище**: Разделение ролей на чтение/запись, неизменяемые бакеты, политики ретенции по классам данных.
- **Доказывание целостности**: Периодические дайджесты за окна времени, подпись и внешняя фиксация хеша (например, в отдельном журнале/реестре).
- **Корреляция**: Совместное использование `trace_id`/`span_id` с системой трассировки, сопоставление с изменениями в Git и артефактами сборок.

## Соответствие и минимизация рисков

Логи должны явно соотноситься с контрольными требованиями (например, контроль действий администраторов, управление изменениями, события безопасности). Для персональных данных применяются правила маскирования и ограничение доступа аудиторских ролей. Настройки ретенции и географического размещения согласуются с правовыми нормами, а политики пересматриваются при изменении архитектуры или рисков.
