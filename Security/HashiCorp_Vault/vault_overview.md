# HashiCorp Vault

## Обзор

HashiCorp Vault — это инструмент для безопасного управления секретами. Секретами может быть что угодно, к чему вы хотите контролировать доступ, например, ключи API, пароли, сертификаты или токенизированные данные. Vault предоставляет единый интерфейс для доступа к секретам, обеспечивая при этом строгий контроль доступа и ведение подробного журнала аудита.

Он разработан для управления секретами в современных динамичных инфраструктурах, таких как облачные среды, контейнеры и микросервисы.

## Ключевые возможности

*   **Безопасное хранение секретов (Secure Secret Storage):** Vault шифрует секреты перед их записью в постоянное хранилище. В качестве бэкенда хранения могут выступать Consul, различные облачные хранилища (S3, GCS), базы данных или локальная файловая система.
*   **Динамические секреты (Dynamic Secrets):** Vault может генерировать секреты "на лету" для доступа к таким системам, как базы данных (PostgreSQL, MySQL), облачные платформы (AWS, Azure) и другие. Эти секреты имеют ограниченный срок действия и автоматически отзываются, что снижает риски, связанные с утечкой долгоживущих учетных данных.
*   **Шифрование как услуга (Encryption as a Service):** Vault может шифровать и расшифровывать данные для приложений, не сохраняя их у себя. Это позволяет разработчикам безопасно обрабатывать конфиденциальные данные (например, номера кредитных карт или персональные данные), не реализуя сложную криптографию самостоятельно.
*   **Управление жизненным циклом сертификатов (PKI Certificate Management):** Vault может выступать в роли центра сертификации (CA), генерируя и подписывая сертификаты для установления TLS-соединений между сервисами.
*   **Идентификационно-ориентированный доступ (Identity-Based Access):** Vault аутентифицирует пользователей и приложения через различные источники (LDAP, Active Directory, Kubernetes, облачные IAM) и использует политики для контроля доступа к секретам.

## Архитектура и основные концепции

*   **Storage Backend:** Физическое хранилище, где Vault хранит зашифрованные данные. Vault сам не хранит данные, а делегирует это другим системам.
*   **Secret Engine:** Компоненты, которые управляют различными типами секретов. Например, `kv` (key-value), `database` (для динамических секретов БД), `pki` (для сертификатов).
*   **Auth Method:** Компоненты, отвечающие за аутентификацию клиентов (пользователей, машин). Примеры: `userpass`, `ldap`, `kubernetes`.
*   **Policies:** Правила, которые определяют, какие действия и по каким путям может выполнять аутентифицированный клиент.
*   **Seal / Unseal:** При запуске Vault находится в "запечатанном" (sealed) состоянии. Это означает, что он знает, где находятся данные, но не знает, как их расшифровать. Процесс "распечатывания" (unsealing) — это предоставление Vault мастер-ключей для расшифровки данных. Обычно мастер-ключ разделяется на несколько частей (Shamir's Secret Sharing), и для распечатывания требуется кворум из этих частей.
*   **Токены (Tokens):** Основной механизм для аутентификации в Vault. После успешной аутентификации клиент получает токен с привязанными к нему политиками.

## Процесс работы

1.  **Аутентификация:** Клиент (пользователь или приложение) аутентифицируется в Vault с помощью одного из настроенных методов.
2.  **Авторизация:** Vault возвращает токен, к которому привязаны политики, определяющие права доступа.
3.  **Получение секрета:** Клиент использует свой токен для чтения или записи секрета по определенному пути.
4.  **Аудит:** Все действия клиента записываются в журнал аудита.

## Варианты использования

*   **Централизованное хранилище для CI/CD:** Хранение токенов, паролей и ключей, используемых в пайплайнах.
*   **Управление секретами для микросервисов:** Каждый сервис получает свои уникальные учетные данные для доступа к базам данных и другим сервисам.
*   **Автоматизация PKI:** Автоматическая выдача и ротация TLS-сертификатов для внутренней инфраструктуры.

## Интеграция с Docker и Docker Compose

Когда у вас десятки микросервисов и окружений (dev, staging, production), Vault позволяет централизовать управление секретами и гибко настраивать политики доступа.

**Общая схема работы:**
1.  **Настройка Vault:** Устанавливается и настраивается Vault (как отдельный сервис).
2.  **Хранение секретов:** Секреты помещаются в хранилище Vault (например, `kv-v2`).
3.  **Политики доступа:** Создаются политики, ограничивающие доступ к секретам. Например, сервис `webapp` может читать секреты только по пути `secret/webapp/*`.
4.  **Аутентификация приложения:** Приложение при старте аутентифицируется в Vault (например, через механизм `AppRole` или `Kubernetes`), получает токен с нужными политиками и запрашивает свои секреты.

### Варианты интеграции

Существует несколько подходов для передачи секретов из Vault в контейнеры:

#### 1. Vault Agent (Рекомендуемый подход)

**Vault Agent** — это легковесный клиентский демон, который решает две основные задачи:
1.  **Аутентификация в Vault:** Автоматически аутентифицируется и управляет жизненным циклом токена.
2.  **Рендеринг секретов:** Запрашивает секреты из Vault и записывает их в файлы, используя шаблоны.

Он может быть запущен как:
-   **Sidecar-контейнер:** В Kubernetes или Docker Compose, работая рядом с основным приложением.
-   **Процесс-инициализатор:** Запускается перед основным приложением, получает секреты и завершает работу.

**Преимущества:**
-   Приложение становится "неосведомленным" о Vault. Ему не нужно содержать логику для аутентификации или запроса секретов; оно просто читает готовые файлы.
-   Автоматическая ротация секретов. Vault Agent может отслеживать истечение срока действия секрета и обновлять его без перезапуска основного приложения (если приложение умеет "на лету" перечитывать конфигурационные файлы).

#### 2. Прямой доступ к API

Приложение может использовать официальные библиотеки Vault для вашего языка программирования, чтобы напрямую обращаться к API Vault.

-   **Плюсы:** Полный контроль над процессом.
-   **Минусы:** Усложняет код приложения, так как в нем появляется логика для аутентификации, хранения токена и запроса секретов.

#### 3. Использование с Docker Compose

В окружениях без Kubernetes или Swarm, где используется `docker-compose up`, можно применять следующий "entrypoint" подход:

1.  Создается скрипт-обертка (`entrypoint.sh`), который будет точкой входа для контейнера.
2.  Этот скрипт сначала обращается к Vault (например, с помощью утилиты `curl` или `vault-cli`), получает необходимые секреты и экспортирует их как переменные окружения.
3.  После этого скрипт запускает основной процесс приложения (`exec "$@"`).

**Пример `entrypoint.sh`:**
```bash
#!/bin/sh
set -e

# Получаем токен для доступа к секретам (например, через AppRole)
VAULT_TOKEN=$(curl -s --request POST \
  --data '{"role_id": "'"$APP_ROLE_ID"'", "secret_id": "'"$APP_SECRET_ID"'"}' \
  $VAULT_ADDR/v1/auth/approle/login | jq -r .auth.client_token)

# Запрашиваем секреты и экспортируем их
export DB_PASSWORD=$(curl -s --header "X-Vault-Token: $VAULT_TOKEN" \
  $VAULT_ADDR/v1/secret/data/myapp/database | jq -r .data.data.password)

# Запускаем основной процесс приложения
exec "$@"
```

### Практические советы
-   **Минимизируйте время жизни (TTL):** Для динамических секретов или токенов устанавливайте короткое время жизни. Это снижает ущерб в случае утечки.
-   **Сегментируйте доступ:** Принцип наименьших привилегий — каждый сервис должен иметь доступ только к необходимому ему набору секретов.
-   **Ведите журнал аудита:** Включайте и регулярно просматривайте логи аудита Vault, чтобы отслеживать, кто, когда и к каким секретам получал доступ.
-   **Обновляйте секреты без перезагрузки:** Если ваше приложение поддерживает "горячую" перезагрузку конфигурации (например, Nginx, Prometheus), используйте Vault Agent для обновления секретов без простоя.
