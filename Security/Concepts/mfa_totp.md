# MFA и TOTP — многофакторная аутентификация

## Определения

### MFA (Multi-Factor Authentication)

**MFA (Multi-Factor Authentication)** — метод аутентификации, требующий предоставления двух или более независимых факторов подтверждения личности из разных категорий.
- **2FA (Two-Factor Authentication)** — частный случай MFA, использующий ровно два фактора.

### TOTP и HOTP

- **TOTP (Time-Based One-Time Password)** — алгоритм генерации временных одноразовых паролей ([RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238)), основанный на общем секрете и текущем времени.
- **HOTP (HMAC-Based One-Time Password)** — алгоритм ([RFC 4226](https://datatracker.ietf.org/doc/html/rfc4226)), использующий счётчик (counter) вместо времени. Код меняется при каждом успешном использовании или генерации.

### Современные стандарты (FIDO2 и Passkeys)

- **FIDO2 (Fast Identity Online 2)** — проект, включающий стандарт WebAuthn и протокол CTAP. Позволяет использовать аппаратные ключи (YubiKey) или биометрию устройств для беспарольного входа.
- **WebAuthn (Web Authentication)** — API в браузерах для аутентификации пользователей через криптографию с открытым ключом.
- **Passkeys (Пасс-ключи)** — реализация FIDO2, при которой криптографические ключи синхронизируются между устройствами пользователя (например, через iCloud Keychain или Google Password Manager), обеспечивая баланс между безопасностью и удобством.

## Основные концепции

### Категории факторов аутентификации

| Категория | Технический термин | Описание | Примеры |
| :--- | :--- | :--- | :--- |
| **Знание** | Knowledge factor | То, что пользователь знает | Пароль, PIN-код, графический ключ |
| **Владение** | Possession factor | То, чем пользователь владеет | Смартфон (TOTP), USB-токен, смарт-карта |
| **Сущность** | Inherence factor | Биометрические данные | Отпечаток пальца, FaceID, рисунок вен |
| **Местоположение** | Location factor | Географический контекст | Доверенный IP-адрес, GPS-координаты |

### Математическая база TOTP

Алгоритм TOTP является расширением HOTP. Основные параметры:
- **Shared Secret (K)** — секретный ключ в кодировке Base32.
- **Time Step (X)** — интервал жизни кода (обычно 30 секунд).
- **Unix Time (T0)** — точка отсчета (0 в эпоху Unix).

**Формула:**
`T = floor((CurrentUnixTime - T0) / X)`
`TOTP = Truncate(HMAC-SHA1(K, T))`

### Сравнение методов второго фактора

| Метод | Уровень безопасности | Защита от фишинга | Удобство (UX) |
| :--- | :--- | :--- | :--- |
| **SMS / Email** | Низкий | Нет | Высокое |
| **TOTP (Google Auth)** | Средний | Нет | Среднее |
| **Push-уведомления** | Средний/Высокий | Нет (риск Fatigue атаки) | Высокое |
| **FIDO2 / WebAuthn** | Высокий | **Да** | Среднее/Высокое |
| **Passkeys** | Высокий | **Да** | Высокое |

### Проблема AitM (Adversary-in-the-Middle) фишинга

Традиционные методы (SMS, TOTP, Push) уязвимы к атакам через обратный прокси-сервер (например, Evilginx). Злоумышленник перехватывает пароль и OTP-код в реальном времени и сразу использует их для создания сессии.
**Решение:** Только FIDO2/WebAuthn защищают от AitM, так как криптографический ответ (assertion) привязан к домену сайта (Origin) на уровне протокола.

## Практические сценарии

### Реализация TOTP на Python (библиотека pyotp)

Пример создания секрета и проверки кода с учетом временного окна (skew):

```python
import pyotp
import qrcode # для генерации QR-кода

# 1. Генерация секрета и URI для приложения
secret = pyotp.random_base32()
uri = pyotp.totp.TOTP(secret).provisioning_uri(
    name="user@example.com", 
    issuer_name="MyAwesomeApp"
)

# 2. Генерация QR-кода (визуализация для пользователя)
# qr = qrcode.make(uri)
# qr.save("totp_qr.png")

# 3. Верификация кода на сервере
totp = pyotp.TOTP(secret)
# valid_window=1 позволяет принять код из предыдущего или следующего 30-сек интервала
is_valid = totp.verify("123456", valid_window=1)

if is_valid:
    print("Доступ разрешен")
```

### Управление резервным доступом

1. **Static Recovery Codes:** Генерация списка из 10 одноразовых 8-значных кодов. Хранить только в хэшированном виде (bcrypt/argon2).
2. **Account Recovery:** Процедура восстановления доступа через проверку личности (ID verification), если все факторы утеряны.

### Рекомендации по безопасности (Hardening)

- **Encryption at Rest:** Секретные ключи (Shared Secrets) в БД должны быть зашифрованы симметричным алгоритмом (AES-256-GCM).
- **Rate Limiting:** Блокировка попыток ввода OTP после 3-5 ошибок. TOTP-коды легко перебираются (всего 10^6 комбинаций).
- **Skew Tolerance:** Допускайте расхождение времени не более чем на ±1 интервал (30-60 секунд).
- **MFA Fatigue Prevention:** При использовании Push-уведомлений внедряйте "Number Matching" (пользователь должен ввести число, показанное на экране входа, в мобильном приложении).

## Дополнительная информация

### Инструменты и реализации

- **Приложения:** Aegis Authenticator (Open Source, Android), Raivo OTP (Open Source, iOS), Bitwarden (интегрированный менеджер).
- **Корпоративные решения:** Keycloak (поддержка TOTP/WebAuthn), HashiCorp Vault (TOTP secrets engine).
- **Аппаратные ключи:** YubiKey (Yubico), Nitrokey (Open Hardware), Google Titan.

### Типовые проблемы

- **Clock Skew (Рассинхронизация):** Если время на сервере или клиенте неверно, коды не совпадут. Решение: использование `chrony` или `ntp`.
- **Secret Leakage:** Компрометация БД с секретами позволяет атакующему генерировать коды для всех пользователей.
