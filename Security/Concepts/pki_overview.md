# Инфраструктура открытых ключей (PKI)

## Определения

**PKI (Public Key Infrastructure)** — совокупность технологий, политик и процедур, необходимых для управления цифровыми сертификатами и ключами шифрования. PKI обеспечивает безопасный обмен данными через сеть за счёт использования асимметричного шифрования.

**Центр сертификации (CA - Certificate Authority)** — доверенная организация или сервис, который выпускает, подписывает и отзывает цифровые сертификаты. CA является якорем доверия в PKI.

**Регистрационный центр (RA - Registration Authority)** — промежуточное звено между пользователем и CA. RA проверяет личность заявителя и передаёт подтверждённые запросы в CA для выпуска сертификатов.

**Цифровой сертификат (X.509)** — электронный документ, который связывает открытый ключ с идентификатором владельца (домен, организация, человек). Содержит:
- Открытый ключ владельца
- Идентификатор (subject)
- Срок действия
- Цифровую подпись CA

**CRL (Certificate Revocation List)** — список отозванных сертификатов, которые больше не являются доверенными до истечения срока действия.

**OCSP (Online Certificate Status Protocol)** — протокол для проверки статуса отзыва сертификата в режиме реального времени. Альтернатива CRL.

## Основные концепции

### Компоненты PKI

| Компонент | Назначение |
| :--- | :--- |
| **Центр сертификации (CA)** | Выпуск и подписание сертификатов, управление отзывом |
| **Регистрационный центр (RA)** | Верификация заявителей, приём запросов (CSR) |
| **Хранилище сертификатов** | База данных выданных сертификатов и их статусов |
| **Система управления ключами** | Генерация, хранение, архивирование и уничтожение ключей |
| **Политики и процедуры (CPS)** | Документы, регламентирующие работу PKI |

### Иерархия доверия

PKI строится по иерархическому принципу:

```
Root CA (самоподписанный)
    └── Intermediate CA 1
    │       └── Серверные сертификаты
    │       └── Клиентские сертификаты
    │
    └── Intermediate CA 2
            └── Сертификаты для IoT
            └── Сертификаты для кода
```

**Root CA (Корневой CA):**
- Самоподписанный сертификат
- Хранится офлайн (air-gapped система)
- Используется только для подписи промежуточных CA
- Срок действия: 10–25 лет

**Intermediate CA (Промежуточный CA):**
- Сертификат подписан Root CA
- Используется для повседневной выдачи сертификатов
- Может быть несколько уровней вложенности
- Срок действия: 5–10 лет

> **Важно:** Разделение на Root и Intermediate CA повышает безопасность. При компрометации Intermediate CA можно отозвать его сертификат, не затрагивая корневой ключ.

### Цепочка доверия (Chain of Trust)

Цепочка доверия — это путь от конечного сертификата к корневому CA через промежуточные сертификаты:

1. **Серверный сертификат** → подписан Intermediate CA
2. **Intermediate CA** → подписан Root CA
3. **Root CA** → самоподписанный, встроен в ОС/браузер

При проверке сертификата клиент строит цепочку до корня и проверяет подпись на каждом уровне.

**Форматы файлов цепочки:**
- `server.crt` — только сертификат сервера
- `ca-bundle.crt` — промежуточные сертификаты
- `fullchain.pem` — серверный + промежуточные (для сервера)
- `ca-certificates.crt` — все доверенные корневые CA (для клиента)

### Жизненный цикл сертификата

```
Генерация ключей → CSR → Выпуск → Использование → Продление/Отзыв
```

1. **Генерация пары ключей:** Клиент создаёт приватный и открытый ключи
2. **CSR (Certificate Signing Request):** Запрос на подпись с открытым ключом и данными владельца
3. **Верификация:** RA/CA проверяет право владения (DV), организацию (OV) или расширенную проверку (EV)
4. **Выпуск:** CA подписывает сертификат и возвращает клиенту
5. **Использование:** Сертификат используется для TLS, подписи кода, аутентификации
6. **Продление:** За 30 дней до истечения выпускается новый сертификат
7. **Отзыв:** При компрометации сертификат добавляется в CRL/OCSP

### Типы проверки домена

| Тип | Описание | Применение |
| :--- | :--- | :--- |
| **DV (Domain Validation)** | Проверка владения доменом (DNS/HTTP/email) | Публичные сайты, Let's Encrypt |
| **OV (Organization Validation)** | Проверка организации + домена | Корпоративные сервисы |
| **EV (Extended Validation)** | Расширенная проверка организации | Банки, финансовые организации |

### Механизмы отзыва сертификатов

#### CRL (Certificate Revocation List)

- **Принцип:** CA публикует периодический список отозванных сертификатов
- **Формат:** Файл `.crl`, доступный по HTTP/LDAP
- **Плюсы:** Простота реализации, кэширование
- **Минусы:** Задержка обновления, размер растёт со временем

```bash
# Проверка CRL
openssl crl -in intermediate.crl -text -noout

# URL в сертификате
crlDistributionPoints = URI:http://pki.example.com/intermediate.crl
```

#### OCSP (Online Certificate Status Protocol)

- **Принцип:** Клиент запрашивает статус конкретного сертификата у OCSP-респондера
- **Формат:** Запрос/ответ в реальном времени
- **Плюсы:** Актуальная информация, компактный ответ
- **Минусы:** Зависимость от доступности респондера, приватность

```bash
# Проверка через OCSP
openssl ocsp -issuer intermediate.crt \
             -cert server.crt \
             -url http://ocsp.example.com
```

#### OCSP Stapling

- **Принцип:** Сервер сам запрашивает OCSP-ответ и "прикрепляет" его к TLS-рукопожатию
- **Плюсы:** Клиент не зависит от OCSP-респондера, быстрее, приватнее
- **Требование:** Поддержка на сервере (Nginx, Apache)

## Практические сценарии

### Сценарий 1: Развёртывание внутреннего CA для организации

**Задача:** Обеспечить доверенными сертификатами внутренние сервисы компании.

**Решение:**
1. Создать [двухуровневую архитектуру CA](../Tools/openssl_ca/two_tier/overview.md)
2. Root CA хранить офлайн
3. Intermediate CA использовать для выдачи сертификатов
4. Развернуть корневой сертификат на всех клиентах (GPO, MDM, `/etc/pki/ca-trust/`)

### Сценарий 2: Взаимная аутентификация (mTLS)

**Задача:** Обеспечить аутентификацию клиентов и серверов в микросервисной архитектуре.

**Решение:**
1. Выпустить серверные сертификаты для каждого сервиса
2. Выпустить клиентские сертификаты для сервисов-клиентов
3. Настроить серверы на проверку клиентских сертификатов
4. Руководство: [mTLS в Nginx](../../WebServers/Nginx/Security/TLS_SSL/nginx_mtls_configuration.md)

### Сценарий 3: Проверка цепочки сертификатов

```bash
# Проверить цепочку сервера
openssl verify -CAfile ca-bundle.crt server.crt

# Просмотреть сертификат
openssl x509 -in server.crt -text -noout

# Проверить дату истечения
openssl x509 -in server.crt -noout -dates

# Извлечь открытый ключ
openssl x509 -in server.crt -noout -pubkey
```

### Сценарий 4: Диагностика проблем доверия

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **"Certificate not trusted"** | Отсутствует корневой/промежуточный CA в доверенных | Установить CA в хранилище доверия клиента |
| **"Certificate expired"** | Истёк срок действия | Перевыпустить сертификат |
| **"Hostname mismatch"** | CN/SAN не совпадает с доменом | Выпустить сертификат с правильным SAN |
| **"Revoked certificate"** | Сертификат отозван | Проверить CRL/OCSP, выпустить новый |
| **"Incomplete chain"** | Сервер не отдаёт промежуточные | Настроить `fullchain.pem` на сервере |

## Дополнительная информация

### Сравнение: Публичные vs Приватные CA

| Критерий | Публичные CA (Let's Encrypt, DigiCert) | Приватные CA (OpenSSL, HashiCorp Vault) |
| :--- | :--- | :--- |
| **Доверие** | Встроены в ОС/браузеры | Требуют ручной установки корня |
| **Стоимость** | Бесплатно или платно | Бесплатно (OpenSSL), платно (Vault PKI) |
| **Срок выпуска** | Минуты (DV) | Мгновенно |
| **Срок действия** | 90 дней (Let's Encrypt), 1–2 года | Любой |
| **Применение** | Публичные сайты | Внутренние сервисы, mTLS, IoT |

### Инструменты управления PKI

| Инструмент | Назначение |
| :--- | :--- |
| **OpenSSL** | Ручное управление CA, скрипты |
| **HashiCorp Vault PKI** | Автоматизированная выдача, динамические сертификаты |
| **EJBCA** | Корпоративный CA с веб-интерфейсом |
| **cert-manager (Kubernetes)** | Автоматический выпуск в K8s (Let's Encrypt, Vault) |
| **Smallstep CA** | Современный CA с ACME-поддержкой |

### Стандарты и спецификации

- **X.509** — формат сертификатов и CRL
- **RFC 5280** — профиль сертификатов X.509
- **RFC 6960** — протокол OCSP
- **ACME (RFC 8555)** — протокол автоматической выдачи (Let's Encrypt)
- **PKCS#7/CMS** — формат криптографических сообщений
- **PKCS#12** — формат хранения ключей с сертификатами (`.p12`, `.pfx`)
