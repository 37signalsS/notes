# PKI — инфраструктура открытых ключей

## Определения

**PKI (Public Key Infrastructure)** — совокупность технологий, политик и процедур для управления цифровыми сертификатами и ключами шифрования. Обеспечивает безопасный обмен данными через асимметричное шифрование и проверку подлинности сторон.

**CA (Certificate Authority)** — доверенный удостоверяющий центр, выпускающий, подписывающий и отзывающий цифровые сертификаты. Является «якорем доверия» в архитектуре PKI.

**RA (Registration Authority)** — регистратор, выступающий посредником между пользователем и CA. Проверяет личность заявителя и передаёт подтверждённые запросы (CSR) в CA.

**Цифровой сертификат (X.509)** — электронный документ, связывающий открытый ключ с идентификатором владельца (домен, организация, персона). Содержит:

- Открытый ключ владельца
- Данные субъекта (Subject)
- Срок действия (Validity)
- Цифровую подпись CA

**CRL (Certificate Revocation List)** — список серийных номеров сертификатов, отозванных CA до истечения срока их действия.

**OCSP (Online Certificate Status Protocol)** — протокол для проверки статуса отзыва сертификата в реальном времени ([RFC 6960](https://datatracker.ietf.org/doc/html/rfc6960)).

## Основные концепции

### Компоненты инфраструктуры

| Компонент | Назначение |
| :--- | :--- |
| **CA** | Выпуск, подписание и отзыв сертификатов |
| **RA** | Верификация заявителей и приём CSR |
| **Хранилище (Repository)** | База данных выданных сертификатов и актуальных CRL |
| **Ключевой менеджмент** | Генерация, хранение, архивация и уничтожение ключей |
| **CPS (Certificate Practice Statement)** | Регламент, описывающий политики и процедуры работы PKI |

### Иерархия доверия

Для повышения безопасности используется многоуровневая структура:

```
Root CA (самоподписанный, air-gapped, срок 10–25 лет)
    └── Intermediate CA 1 (подписан Root CA, срок 5–10 лет)
    │       ├── Серверные сертификаты (TLS)
    │       └── Клиентские сертификаты (mTLS)
    │
    └── Intermediate CA 2 (подписан Root CA)
            ├── Сертификаты для подписи кода (Code Signing)
            └── Сертификаты для IoT-устройств
```

- **Root CA:** корневой узел, хранится в изолированной среде (offline). Используется только для выпуска промежуточных CA.
- **Intermediate CA:** промежуточные узлы, используемые для повседневной выдачи сертификатов. При компрометации одного из них корень остаётся в безопасности.

### Цепочка доверия

Путь проверки от конечного сертификата до доверенного корня:

1. **Конечный сертификат** → проверяется подписью Intermediate CA.
2. **Intermediate CA** → проверяется подписью Root CA.
3. **Root CA** → должен находиться в локальном доверенном хранилище ОС или браузера.

**Форматы файлов:**

- `server.crt`: только сертификат конечного сервера.
- `ca-bundle.crt`: файл с промежуточными сертификатами CA.
- `fullchain.pem`: объединение сертификата сервера и промежуточных CA (рекомендуется для настройки веб-серверов).
- `ca-certificates.crt`: системное хранилище всех доверенных корневых сертификатов.

### Жизненный цикл сертификата

1. **Генерация:** создание пары ключей (приватный + открытый).
2. **CSR (Certificate Signing Request):** формирование запроса, содержащего открытый ключ и данные владельца.
3. **Верификация:** проверка данных заявителя со стороны RA/CA.
4. **Выпуск:** подписание сертификата ключом CA.
5. **Использование:** установка на серверы или устройства.
6. **Обновление:** выпуск нового сертификата до истечения срока текущего.
7. **Отзыв:** аннулирование сертификата при компрометации ключа.

### Уровни проверки домена

| Тип | Описание | Применение |
| :--- | :--- | :--- |
| **DV** (Domain Validation) | Проверка владения доменом через DNS/HTTP/Email | Личные сайты, Let's Encrypt |
| **OV** (Organization Validation) | Проверка юридического лица и владения доменом | Корпоративные ресурсы |
| **EV** (Extended Validation) | Глубокая проверка организации (зелёная строка в старых браузерах) | Банки, финансовые системы |

### Механизмы проверки отзыва

- **CRL:** CA публикует периодический список отозванных сертификатов (`.crl`). Минус — задержка обновления и рост размера файла.
- **OCSP:** клиент запрашивает статус конкретного сертификата у ответчика (responder). Плюс — актуальность и экономия трафика.
- **OCSP Stapling:** сервер сам запрашивает статус своего сертификата и передаёт его клиенту в TLS-рукопожатии. Наиболее эффективный и приватный метод.

## Практические сценарии

### Создание внутреннего CA

Для внутренних нужд (mTLS, VPN, локальные сервисы) рекомендуется развёртывание собственной PKI:

1. [Двухуровневая архитектура CA](../Tools/openssl_ca/two_tier/overview.md) на базе OpenSSL.
2. Использование [HashiCorp Vault PKI](../../Vault/concepts.md) для автоматизации выдачи короткоживущих сертификатов.

### Проверка сертификатов через CLI

```bash
# Просмотр содержимого сертификата
openssl x509 -in server.crt -text -noout

# Проверка валидности цепочки
openssl verify -CAfile ca-bundle.crt server.crt

# Проверка статуса через OCSP
openssl ocsp -issuer intermediate.crt -cert server.crt -url http://ocsp.example.com -text
```

### Диагностика типичных ошибок

- **Expired Certificate:** срок действия истёк — требуется перевыпуск.
- **Self-signed Certificate:** корень не добавлен в доверенные хранилища клиентов.
- **Incomplete Chain:** сервер не отдаёт промежуточные сертификаты (нужно использовать `fullchain`).
- **Hostname Mismatch:** имя в сертификате (CN или SAN) не совпадает с URL сайта.

## Дополнительная информация

### Инструменты управления

- **OpenSSL:** базовый инструмент для работы с ключами и сертификатами.
- **cert-manager:** стандарт для Kubernetes, автоматизирует получение сертификатов от Let's Encrypt и Vault.
- **Step-ca:** современный и быстрый CA с поддержкой протокола ACME.
- **EJBCA:** мощная корпоративная система управления PKI.

### Стандарты

- **X.509:** стандарт, определяющий формат сертификатов.
- **[RFC 5280](https://datatracker.ietf.org/doc/html/rfc5280):** базовый профиль для X.509 в интернете.
- **ACME ([RFC 8555](https://datatracker.ietf.org/doc/html/rfc8555)):** протокол автоматизации управления сертификатами.
- **PKCS#12 (.p12, .pfx):** формат для защищённого хранения ключей и сертификатов в одном файле.
