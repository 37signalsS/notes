# PKI — инфраструктура открытых ключей

## Определения

**PKI (Public Key Infrastructure)** — совокупность технологий, политик и процедур для управления цифровыми сертификатами и ключами шифрования. Обеспечивает безопасный обмен данными через асимметричное шифрование и проверку подлинности сторон.

**CA (Certificate Authority)** — доверенный удостоверяющий центр, выпускающий, подписывающий и отзывающий цифровые сертификаты. Является «якорем доверия» в архитектуре PKI.

**RA (Registration Authority)** — регистратор, выступающий посредником между пользователем и CA. Проверяет личность заявителя и передаёт подтверждённые запросы (CSR) в CA.

**Цифровой сертификат (X.509)** — электронный документ, связывающий открытый ключ с идентификатором владельца (домен, организация, персона).

**CSR (Certificate Signing Request)** — запрос на подпись сертификата, содержащий открытый ключ и идентификационные данные субъекта.

**CT (Certificate Transparency)** — открытая система логирования всех выпущенных публичных сертификатов. Позволяет владельцам доменов обнаруживать ошибочно или злонамеренно выпущенные сертификаты.

**CRL (Certificate Revocation List)** — список серийных номеров сертификатов, отозванных CA до истечения срока их действия.

**OCSP (Online Certificate Status Protocol)** — протокол для проверки статуса отзыва сертификата в реальном времени.

## Основные концепции

### Иерархия доверия

Для обеспечения безопасности используется многоуровневая структура, позволяющая изолировать наиболее критичные ключи:

- **Root CA:** корневой узел, хранится в изолированной среде (offline/air-gapped). Используется только для подписания промежуточных CA. Срок действия: 10–25 лет.
- **Intermediate CA:** промежуточные узлы, используемые для операционной выдачи сертификатов. В случае компрометации отзывается только промежуточный узел, а не вся иерархия. Срок действия: 5–10 лет.
- **End-Entity Certificates:** конечные сертификаты (серверные, клиентские, для подписи кода). Срок действия: от 24 часов до 1 года (стандарт 2026 года — минимизация срока жизни для повышения безопасности).

### Цепочка доверия (Chain of Trust)

Процесс валидации от конечного узла до корня:
1. **End-Entity** → проверяется подписью Intermediate CA.
2. **Intermediate CA** → проверяется подписью Root CA.
3. **Root CA** → должен находиться в локальном доверенном хранилище ОС или браузера.

### Алгоритмы и криптография 2026

- **RSA (Rivest-Shamir-Adleman):** классический алгоритм, минимальная длина ключа — 3072 бита.
- **ECDSA (Elliptic Curve Digital Signature Algorithm):** более эффективен, стандарт P-256 или P-384.
- **EdDSA (Edwards-curve Digital Signature Algorithm):** рекомендуемый стандарт (Ed25519) благодаря высокой производительности и устойчивости к ряду атак.
- **PQC (Post-Quantum Cryptography):** внедрение алгоритмов, устойчивых к квантовым компьютерам (например, ML-DSA), в гибридных схемах.

### Форматы файлов

| Расширение | Тип | Описание |
| :--- | :--- | :--- |
| **.key / .pem** | Приватный ключ | Должен храниться в секрете (права 600 или HSM). |
| **.crt / .cer** | Сертификат | Публичный документ. |
| **.csr** | Запрос | Временный файл для отправки в CA. |
| **.p12 / .pfx** | Контейнер (PKCS#12) | Объединяет ключ и сертификат, защищен паролем. |
| **fullchain.pem** | Цепочка | Сертификат сервера + все промежуточные CA. |

## Практические сценарии

### Жизненный цикл и автоматизация

1. **Генерация и запрос:** создание ключа и CSR.
2. **Выпуск:** проверка и подписание в CA.
3. **Развертывание:** установка на конечный узел.
4. **Автоматизация (ACME):** протокол автоматического выпуска (Let's Encrypt, ZeroSSL).
5. **ACME ARI (Renewal Information):** современное расширение, позволяющее CA сигнализировать клиенту (например, cert-manager) о необходимости досрочного продления сертификата (например, из-за внепланового отзыва).

### Работа с OpenSSL в CLI

```bash
# Генерация ключа Ed25519 и CSR
openssl genpkey -algorithm ed25519 -out server.key
openssl req -new -key server.key -out server.csr -subj "/CN=example.com"

# Просмотр данных сертификата
openssl x509 -in server.crt -text -noout

# Проверка соответствия ключа и сертификата (сравнение модулей)
# Для RSA:
openssl rsa -noout -modulus -in server.key | openssl md5
openssl x509 -noout -modulus -in server.crt | openssl md5
```

### Дистрибуция доверия (Trust Distribution)

В распределенных системах и Kubernetes для доставки корневых сертификатов во все контейнеры используются специализированные инструменты:
- **trust-manager:** аддон для cert-manager, который автоматически распространяет `Bundle` с корневыми сертификатами в виде ConfigMap во все Namespaces.
- **Системные хранилища:** `/etc/ssl/certs` (Linux), Keychain (macOS).

## Дополнительная информация

### Инструменты управления (2026)

- **cert-manager:** де-факто стандарт для Kubernetes.
- **HashiCorp Vault PKI:** идеален для генерации короткоживущих внутренних сертификатов (TTL < 24ч).
- **step-ca:** легкое решение для частных сетей с поддержкой ACME.
- **Облачные CAS:** AWS Private CA, Google Cloud Certificate Authority Service.

### Типовые ошибки

- **Incomplete Chain:** сервер не передает промежуточные сертификаты. Решение: использовать `fullchain.pem`.
- **Name Constraints Violation:** сертификат выдан для домена, не разрешенного вышестоящим CA.
- **Key Usage Violation:** использование сертификата сервера для подписи кода или наоборот.
