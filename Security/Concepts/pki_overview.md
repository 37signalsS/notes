# PKI (Public Key Infrastructure)

## Definitions

**PKI** — совокупность технологий, политик и процедур для управления цифровыми сертификатами и ключами шифрования. Обеспечивает безопасный обмен данными через асимметричное шифрование и проверку подлинности.

**CA (Certificate Authority)** — доверенная организация, выпускающая, подписывающая и отзывающая цифровые сертификаты. Якорь доверия в PKI.

**RA (Registration Authority)** — промежуточное звено между пользователем и CA. Проверяет личность заявителя и передаёт подтверждённые запросы в CA.

**Цифровой сертификат (X.509)** — электронный документ, связывающий открытый ключ с идентификатором владельца (домен, организация, человек). Содержит:

- Открытый ключ владельца
- Subject (идентификатор)
- Срок действия
- Цифровую подпись CA

**CRL (Certificate Revocation List)** — список отозванных сертификатов, недействительных до истечения срока.

**OCSP (Online Certificate Status Protocol)** — протокол проверки статуса отзыва сертификата в реальном времени ([RFC 6960](https://datatracker.ietf.org/doc/html/rfc6960)).

## Basic Concepts

### Компоненты PKI

| Компонент | Назначение |
| :--- | :--- |
| **CA** | Выпуск, подписание, отзыв сертификатов |
| **RA** | Верификация заявителей, приём CSR |
| **Хранилище сертификатов** | База выданных сертификатов и их статусов |
| **Система управления ключами** | Генерация, хранение, архив, уничтожение ключей |
| **CPS (Certificate Practice Statement)** | Политики и процедуры работы PKI |

### Иерархия доверия

```
Root CA (самоподписанный, air-gapped, 10–25 лет)
    └── Intermediate CA 1 (подписан Root CA, 5–10 лет)
    │       ├── Серверные сертификаты
    │       └── Клиентские сертификаты
    │
    └── Intermediate CA 2 (подписан Root CA, 5–10 лет)
            ├── Сертификаты для IoT
            └── Сертификаты для кода
```

**Root CA:** самоподписанный, хранится офлайн (air-gapped), используется только для подписи промежуточных CA.

**Intermediate CA:** подписан Root CA, используется для повседневной выдачи. При компрометации отзывается без затрагивания корневого ключа.

### Цепочка доверия (Chain of Trust)

Путь от конечного сертификата к корневому CA:

1. **Серверный сертификат** → подписан Intermediate CA
2. **Intermediate CA** → подписан Root CA
3. **Root CA** → самоподписанный, встроен в ОС/браузер

Клиент строит цепочку до корня и проверяет подпись на каждом уровне.

**Форматы цепочки:**

- `server.crt` — только сертификат сервера
- `ca-bundle.crt` — промежуточные сертификаты
- `fullchain.pem` — серверный + промежуточные (для сервера)
- `ca-certificates.crt` — все доверенные корневые CA (для клиента)

### Жизненный цикл сертификата

```
Генерация ключей → CSR → Верификация → Выпуск → Использование → Продление/Отзыв
```

1. **Генерация ключей:** приватный + открытый ключ
2. **CSR (Certificate Signing Request):** запрос с открытым ключом и данными владельца
3. **Верификация:** DV (домен), OV (организация), EV (расширенная)
4. **Выпуск:** CA подписывает сертификат
5. **Использование:** TLS, подпись кода, аутентификация
6. **Продление:** за 30 дней до истечения
7. **Отзыв:** при компрометации — в CRL/OCSP

### Типы проверки домена

| Тип | Описание | Применение |
| :--- | :--- | :--- |
| **DV** (Domain Validation) | Проверка владения доменом (DNS/HTTP/email) | Публичные сайты, Let's Encrypt |
| **OV** (Organization Validation) | Проверка организации + домена | Корпоративные сервисы |
| **EV** (Extended Validation) | Расширенная проверка организации | Банки, финорганизации |

### Механизмы отзыва сертификатов

**CRL:** CA публикует периодический список отозванных сертификатов (`.crl`, HTTP/LDAP). Плюсы — простота, кэширование. Минусы — задержка обновления, рост размера.

```bash
openssl crl -in intermediate.crl -text -noout
```

**OCSP:** клиент запрашивает статус конкретного сертификата у OCSP-респондера. Плюсы — актуальность, компактность. Минусы — зависимость от доступности, приватность.

```bash
openssl ocsp -issuer intermediate.crt -cert server.crt -url http://ocsp.example.com
```

**OCSP Stapling:** сервер сам запрашивает OCSP-ответ и прикрепляет к TLS-рукопожатию. Плюсы — клиент не зависит от OCSP-респондера, быстрее, приватнее. Требует поддержки на сервере.

## Practical Scenarios

### Развёртывание внутреннего CA

1. Создать [двухуровневую архитектуру CA](../Tools/openssl_ca/two_tier/overview.md)
2. Root CA хранить офлайн
3. Intermediate CA — для повседневной выдачи
4. Развернуть корневой сертификат на клиентах (GPO, MDM, `/etc/pki/ca-trust/`)

### Взаимная аутентификация (mTLS)

1. Выпустить серверные сертификаты для каждого сервиса
2. Выпустить клиентские сертификаты для сервисов-клиентов
3. Настроить серверы на проверку клиентских сертификатов
4. Руководство: [mTLS в Nginx](../../WebServers/Nginx/Security/TLS_SSL/nginx_mtls_configuration.md)

### Проверка цепочки сертификатов

```bash
# Проверить цепочку
openssl verify -CAfile ca-bundle.crt server.crt

# Просмотреть сертификат
openssl x509 -in server.crt -text -noout

# Проверить дату истечения
openssl x509 -in server.crt -noout -dates
```

### Диагностика проблем доверия

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **Certificate not trusted** | Отсутствует CA в доверенных | Установить CA в хранилище |
| **Certificate expired** | Истёк срок действия | Перевыпустить |
| **Hostname mismatch** | CN/SAN ≠ домен | Выпустить с правильным SAN |
| **Revoked certificate** | Сертификат отозван | Проверить CRL/OCSP, выпустить новый |
| **Incomplete chain** | Сервер не отдаёт промежуточные | Настроить `fullchain.pem` |

## Additional Information

### Публичные vs Приватные CA

| Критерий | Публичные CA (Let's Encrypt, DigiCert) | Приватные CA (OpenSSL, Vault PKI) |
| :--- | :--- | :--- |
| **Доверие** | Встроены в ОС/браузеры | Требуют ручной установки корня |
| **Стоимость** | Бесплатно/платно | Бесплатно (OpenSSL), платно (Vault) |
| **Срок выпуска** | Минуты (DV) | Мгновенно |
| **Срок действия** | 90 дней (Let's Encrypt), 1–2 года | Любой |
| **Применение** | Публичные сайты | Внутренние сервисы, mTLS, IoT |

### Инструменты управления PKI

| Инструмент | Назначение |
| :--- | :--- |
| **OpenSSL** | Ручное управление CA, скрипты |
| **HashiCorp Vault PKI** | Автоматизированная выдача, динамические сертификаты |
| **EJBCA** | Корпоративный CA с веб-интерфейсом |
| **cert-manager (K8s)** | Автоматический выпуск в Kubernetes (Let's Encrypt, Vault) |
| **Smallstep CA** | Современный CA с ACME-поддержкой |

### Стандарты и спецификации

- **X.509** — формат сертификатов и CRL
- **[RFC 5280](https://datatracker.ietf.org/doc/html/rfc5280)** — профиль сертификатов X.509
- **[RFC 6960](https://datatracker.ietf.org/doc/html/rfc6960)** — протокол OCSP
- **[RFC 8555](https://datatracker.ietf.org/doc/html/rfc8555)** — ACME (автоматическая выдача, Let's Encrypt)
- **PKCS#7/CMS** — формат криптографических сообщений
- **PKCS#12** — формат хранения ключей с сертификатами (`.p12`, `.pfx`)
