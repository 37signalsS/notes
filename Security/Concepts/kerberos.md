# Kerberos — сетевая аутентификация

## Определение

**Kerberos** — протокол сетевой аутентификации, обеспечивающий защищённую передачу данных в ненадёжных сетях с помощью симметричного шифрования и системы билетов (tickets). Разработан в MIT в 1980-х годах. Назван в честь трёхглавого пса Цербера, что символизирует три стороны процесса: клиент, сервер и центр распределения ключей.

Основной принцип: **пароли никогда не передаются по сети** — вместо них используются зашифрованные билеты с ограниченным временем жизни.

## Основные концепции

### Ключевые термины

| Термин | Описание |
| :--- | :--- |
| **Principal** | Уникальный идентификатор пользователя или сервиса в формате `name[/instance]@REALM`. |
| **Realm** | Область аутентификации (домен), обычно совпадает с DNS-именем в верхнем регистре (например, `EXAMPLE.COM`). |
| **Ticket** | Зашифрованная структура данных, подтверждающая идентичность владельца для конкретного ресурса. |
| **Authenticator** | Временный токен, зашифрованный сессионным ключом, для защиты от атак повторного воспроизведения. Содержит метку времени. |
| **SPN (Service Principal Name)** | Уникальное имя сервиса в сети, используемое клиентом для идентификации конкретного экземпляра службы (например, `HTTP/web.example.com`). |
| **Keytab** | Файл, содержащий секретные ключи (пароли) сервисов или пользователей, позволяющий проходить аутентификацию без интерактивного ввода пароля. |

### Компоненты инфраструктуры

| Компонент | Описание |
| :--- | :--- |
| **Client** | Пользователь или служба, запрашивающая доступ к ресурсу. |
| **KDC (Key Distribution Center)** | Центр распределения ключей, доверенная третья сторона, владеющая базой данных всех секретных ключей. |
| **AS (Authentication Server)** | Сервер первичной аутентификации в составе KDC, проверяет личность клиента и выдаёт TGT. |
| **TGS (Ticket Granting Server)** | Сервер выдачи сервисных билетов в составе KDC, обменивает TGT на билеты к конкретным службам. |
| **SS (Service Server)** | Целевой сервер, предоставляющий конечную услугу. |

### Процесс аутентификации (Шаги)

1.  **Запрос TGT (AS Request):**
    - Клиент отправляет запрос к **AS**.
    - AS возвращает **TGT** (зашифрован ключом TGS) и **Session Key** (зашифрован секретным ключом клиента, производным от его пароля).
2.  **Запрос сервисного билета (TGS Request):**
    - Клиент отправляет к **TGS** свой TGT и аутентификатор (зашифрован сессионным ключом).
    - TGS проверяет TGT, создаёт новый сессионный ключ для сервиса и возвращает **Service Ticket** (зашифрован ключом целевого сервиса).
3.  **Доступ к ресурсу (AP Request):**
    - Клиент отправляет сервисный билет и новый аутентификатор к **SS**.
    - SS расшифровывает билет своим ключом, проверяет аутентификатор и предоставляет доступ.

### Расширенные механизмы

-   **Delegation (Делегирование):** Позволяет сервису выступать от имени пользователя для доступа к другому сервису.
    - *Unconstrained:* Сервис получает полную копию TGT пользователя (небезопасно).
    - *Constrained:* Ограничение списка сервисов, к которым можно обращаться от имени пользователя.
-   **PKINIT:** Расширение, позволяющее использовать сертификаты X.509 (смарт-карты) вместо паролей для получения TGT.
-   **FAST (Flexible Authentication Secure Tunneling):** Создаёт защищённый туннель между клиентом и KDC для защиты обмена данными (предотвращает офлайн-перебор паролей).

## Практические сценарии

### Работа с билетами в CLI

Для управления билетами в Linux используются утилиты пакета `krb5-user` (Debian/Ubuntu) или `krb5-workstation` (RHEL/CentOS).

**1. Получение билета (Аутентификация):**
```bash
kinit username@EXAMPLE.COM
# Ввод пароля → билет получен
```

**2. Просмотр текущих билетов:**
```bash
klist
# Ticket cache: FILE:/tmp/krb5cc_1000
# Default principal: username@EXAMPLE.COM
#
# Valid starting       Expires              Service principal
# 28/07/2026 10:00:00  28/07/2026 20:00:00  krbtgt/EXAMPLE.COM@EXAMPLE.COM
```

**3. Проверка ключей в Keytab:**
```bash
ktutil
ktutil: read_kt /etc/krb5.keytab
ktutil: list
# slot KVNO Timestamp           Principal
# ---- ---- ------------------- ------------------------------------------------------
#    1    2 2026-07-28 09:00:00 host/srv.example.com@EXAMPLE.COM
```

### Примеры интеграции

-   **Active Directory:** Kerberos является фундаментом безопасности в доменах Windows, обеспечивая SSO для всех корпоративных приложений.
-   **FreeIPA:** Полноценная замена AD для Linux-инфраструктуры, объединяющая LDAP и Kerberos.
-   **NFSv4:** Использование параметров `sec=krb5p` обеспечивает полное шифрование сетевого трафика файловой системы.
-   **SSH (GSSAPI):** Позволяет заходить на серверы по SSH без ввода пароля и ключей, используя текущий билет Kerberos.

## Дополнительная информация

### Технические особенности и безопасность

-   **Шифрование:** В 2026 году обязательным является использование **AES-256-CTS-HMAC-SHA1-96**. Алгоритмы DES, 3DES и RC4 считаются небезопасными и должны быть отключены на уровне KDC.
-   **Порты:** Работает через порт `88` (UDP — основной, TCP — при больших размерах билетов).
-   **Синхронизация времени:** Критическое условие. Если разница между часами клиента и KDC превышает 5 минут (по умолчанию), аутентификация завершится ошибкой `KRB5KRB_AP_ERR_SKEW`.

### Типовые ошибки и диагностика

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **Clock skew too great** | Разница во времени > 5 мин. | Настроить [Chrony](../../Linux/Core/systemd/time_synchronization.md). |
| **Preauthentication failed** | Неверный пароль или имя пользователя. | Проверить учетные данные. |
| **Key table entry not found** | Отсутствует нужный ключ в `keytab`. | Перегенерировать `keytab` с корректным SPN. |
| **KDC reply too big** | Билет не влезает в UDP-пакет. | Форсировать использование TCP (параметр `udp_preference_limit = 1`). |
