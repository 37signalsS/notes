# JWT (JSON Web Token)

## Определение

**JWT (JSON Web Token)** — открытый стандарт ([RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519)) для безопасной передачи информации между сторонами в виде объекта JSON. Информация может быть проверена и является доверенной, так как она подписана цифровой подписью.

**Структура токена:** состоит из трёх частей в кодировке Base64Url, разделённых точкой (`.`):
- **Header (Заголовок):** тип токена (`JWT`) и алгоритм подписи (например, `RS256`).
- **Payload (Полезная нагрузка):** утверждения (**Claims**) — данные о субъекте и метаданные.
- **Signature (Подпись):** криптографическое подтверждение целостности первых двух частей.

## Основные концепции

### Типы утверждений (Claims)

Утверждения — это пары ключ-значение, содержащиеся в Payload:
- **Зарегистрированные (Registered):** стандартные поля, такие как `iss` (issuer — издатель), `sub` (subject — субъект), `aud` (audience — получатель), `exp` (expiration — время истечения), `iat` (issued at — время выпуска).
- **Публичные (Public):** произвольные имена, которые должны быть уникальными (часто используются URI).
- **Приватные (Private):** пользовательские данные для обмена между конкретными системами (например, `role`, `user_id`).

### Алгоритмы подписи

| Алгоритм | Тип | Описание |
| :--- | :--- | :--- |
| **HS256** (HMAC + SHA256) | Симметричный | Один секретный ключ для подписи и проверки. Быстро, но секрет должен быть у всех сторон. |
| **RS256** (RSA + SHA256) | Асимметричный | Подпись приватным ключом, проверка публичным. Стандарт для OIDC. |
| **EdDSA** (Ed25519) | Асимметричный | Рекомендуемый стандарт 2026 года. Более высокая производительность и безопасность при меньшем размере ключа. |

### JWKS (JSON Web Key Set)

**JWKS** ([RFC 7517](https://datatracker.ietf.org/doc/html/rfc7517)) — это набор публичных ключей, доступных по HTTP-эндпоинту. Позволяет сервисам автоматически скачивать публичные ключи сервера авторизации для валидации JWT и обеспечивает бесшовную **ротацию ключей** без перезагрузки приложений.

## Практические сценарии

### Паттерн Access и Refresh Token

JWT часто используется в связке для обеспечения безопасности и удобства:
1. **Access Token:** Короткоживущий (5–15 минут), передается в заголовке `Authorization: Bearer`.
2. **Refresh Token:** Долгоживущий (дни/недели), хранится в `HttpOnly Cookie`. Используется только для получения нового Access Token.

### Пример проверки токена на стороне API (Go-style)

```go
token, err := jwt.Parse(tokenString, func(token *jwt.Token) (interface{}, error) {
    // 1. Проверка алгоритма (защита от 'alg: none')
    if _, ok := token.Method.(*jwt.SigningMethodRSA); !ok {
        return nil, fmt.Errorf("unexpected signing method")
    }
    // 2. Получение публичного ключа (например, из JWKS)
    return publicKey, nil
})

if claims, ok := token.Claims.(jwt.MapClaims); ok && token.Valid {
    // 3. Проверка обязательных полей
    if !claims.VerifyAudience("my-api", true) {
        return nil, fmt.Errorf("invalid audience")
    }
}
```

### Передача в HTTP

Токен должен передаваться строго в заголовке Authorization для защиты от CSRF:
```http
Authorization: Bearer <base64_header>.<base64_payload>.<signature>
```

## Дополнительная информация

### Безопасность и уязвимости

- **Критическая уязвимость `alg: none`:** Обязательно проверяйте алгоритм в коде, не доверяйте полю в заголовке JWT.
- **KID (Key ID) Injection:** Атакующий может подменить `kid` в заголовке, чтобы сервер использовал неверный ключ для проверки. Используйте строгий маппинг `kid` на доверенные ключи.
- **Хранение на клиенте:** Никогда не храните JWT в `localStorage` (риск XSS). Используйте `HttpOnly`, `Secure`, `SameSite=Strict` Cookies.
- **Отзыв токенов:** JWT невозможно отозвать "из коробки" (stateless). 
    - **Решение А:** Короткий TTL + Refresh Token.
    - **Решение Б:** Черный список (Blacklisting) `jti` (JWT ID) в Redis.

### Сравнение с сессиями

| Характеристика | Сессии (Stateful) | JWT (Stateless) |
| :--- | :--- | :--- |
| Хранение | В базе данных сервера / Redis | На клиенте (в токене) |
| Масштабирование | Требует синхронизации сессий | Масштабируется горизонтально без доп. настроек |
| Отзыв | Мгновенный | Сложен, требует доп. механизмов |
