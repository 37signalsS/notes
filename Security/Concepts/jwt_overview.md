# JWT (JSON Web Token)

## Определения

**JWT (JSON Web Token)** — открытый стандарт ([RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519)) для безопасной передачи информации между сторонами в виде объекта JSON. Информация может быть проверена и является доверенной, так как она подписана цифровой подписью.

**Структура JWT:** состоит из трёх частей, разделённых точкой (`.`):

1. **Header (Заголовок):** содержит тип токена (`JWT`) и алгоритм подписи (например, `HS256` или `RS256`).
2. **Payload (Полезная нагрузка):** содержит утверждения (**Claims**) — данные о пользователе и дополнительные метаданные.
3. **Signature (Подпись):** используется для проверки того, что сообщение не было изменено по пути.

Формат: `base64(Header).base64(Payload).Signature`

## Основные концепции

### Утверждения (Claims)

Существует три типа утверждений:

- **Зарегистрированные (Registered):** стандартные поля (рекомендуемые): `iss` (issuer), `exp` (expiration time), `sub` (subject), `aud` (audience).
- **Публичные (Public):** определяются пользователями, должны быть устойчивы к коллизиям (обычно URI).
- **Приватные (Private):** пользовательские данные для обмена между конкретными системами (например, `user_id`, `role`).

### Подпись и верификация

- **Симметричное шифрование (HMAC):** сервер и клиент используют один и тот же секретный ключ. Быстро, но требует передачи секрета.
- **Асимметричное шифрование (RSA/ECDSA):** сервер подписывает приватным ключом, клиент проверяет публичным. Безопаснее для распределённых систем.

### Stateless-природа

JWT самодостаточен: он содержит всю необходимую информацию, поэтому серверу не нужно хранить состояние сессии в базе данных или кеше (например, Redis). Это упрощает масштабирование.

## Практические сценарии

### Использование в HTTP-заголовках

Токен передаётся в заголовке `Authorization` с префиксом `Bearer`:

```http
Authorization: Bearer <token>
```

### Пример полезной нагрузки (Payload)

```json
{
  "sub": "1234567890",
  "name": "John Doe",
  "admin": true,
  "iat": 1516239022,
  "exp": 1516242622
}
```

### Алгоритм проверки на сервере

1. Извлечь токен из заголовка.
2. Разделить на три части.
3. Декодировать Header и Payload из Base64.
4. Вычислить подпись на основе полученных Header, Payload и секретного ключа сервера.
5. Сравнить вычисленную подпись с подписью из токена.
6. Проверить срок действия (`exp`).

## Дополнительная информация

### Безопасность и риски

- **Алгоритм `none`:** Уязвимость, при которой сервер принимает токены без подписи. Должна быть отключена в библиотеках.
- **Секретный ключ:** Должен быть длинным и сложным. Для HMAC рекомендуется минимум 256 бит.
- **Хранение на клиенте:** `localStorage` уязвим для XSS. Рекомендуется использовать `HttpOnly` и `Secure` Cookies.
- **Отзыв токенов:** Поскольку JWT stateless, его сложно отозвать до истечения `exp`. Решение — использование короткоживущих Access Tokens и Refresh Tokens с механизмом чёрных списков (Blacklisting) в Redis.

### Инструменты

- **jwt.io:** Дебаггер и отладчик JWT.
- **Библиотеки:** `jose`, `jsonwebtoken` (Node.js), `PyJWT` (Python), `golang-jwt/jwt` (Go).
