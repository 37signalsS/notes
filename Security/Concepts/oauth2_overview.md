# Обзор OAuth 2.0

## 1. Определения

**OAuth 2.0** — открытый протокол авторизации ([RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749)), позволяющий приложениям получать ограниченный доступ к учётным записям пользователей на HTTP-сервисах. Делегирует аутентификацию сервису, где находится аккаунт, и выдаёт клиенту токен с ограниченными правами вместо пароля.

**OAuth 2.1** — консолидированная спецификация (2025), объединяющая RFC 6749, RFC 6750 и security best practices. Не является обратной совместимой версией — удаляет устаревшие и небезопасные механизмы ([подробнее](#эволюция-oauth-20--oauth-21)).

## 2. Основные концепции

### Роли в OAuth 2.0

* **Владелец ресурса (Resource Owner):** Пользователь.
* **Клиент (Client):** Приложение, запрашивающее доступ.
* **Сервер авторизации (Authorization Server):** Сервер, выдающий токены.
* **Сервер ресурсов (Resource Server):** Сервер, где хранятся защищенные ресурсы (API).

### Токены: Access Token и Refresh Token

* **Access Token:** Краткосрочный токен, который клиент использует для доступа к защищенным ресурсам. Он содержит информацию об авторизации и области действия (scopes). Access Token обычно не шифруется, но подписывается сервером авторизации.
* **Refresh Token:** Долгосрочный токен, который используется клиентом для получения нового Access Token, когда предыдущий истекает. Refresh Token обычно выдается только доверенным клиентам и хранится более безопасно.

### Области действия (Scopes)

Scopes определяют, к каким частям пользовательских данных или функциям приложение может получить доступ. Например, `email`, `profile`, `read:tweets`, `write:tweets`. Пользователь должен дать согласие на запрашиваемые scopes во время авторизации.

### Общая схема работы

1. Клиент запрашивает авторизацию у пользователя на определенные **scopes**.
2. Пользователь дает согласие.
3. Клиент запрашивает **Access Token** у сервера авторизации.
4. Сервер авторизации выдает токен.
5. Клиент использует токен для доступа к ресурсам на сервере ресурсов.

### Регистрация клиента

Перед использованием протокола клиент регистрируется на сервере авторизации и получает **Client ID** (публичный) и **Client Secret** (конфиденциальный). Также указывается **Redirect URI** — адрес, на который пользователь будет перенаправлен после авторизации.

## 3. Практические сценарии

### Типы авторизации (Grant Types)

Это различные способы получения токена доступа.

#### 1. Authorization Code

Наиболее распространенный и безопасный тип для веб-приложений.

1. Клиент перенаправляет пользователя на сервер авторизации.
2. Пользователь логинится и дает разрешение.
3. Сервер авторизации возвращает пользователя на `Redirect URI` с **кодом авторизации**.
4. Клиент обменивает этот код (вместе со своим `Client Secret`) на **Access Token** и, опционально, **Refresh Token**.

#### 2. Implicit (Неявный) — **УДАЛЁН в OAuth 2.1**

Упрощённый вариант для SPA-приложений, где токен доступа передавался напрямую в URL-фрагменте. **Полностью удалён из OAuth 2.1** из-за критических уязвимостей: токен в URL подвержен утечке через Referer-заголовки, историю браузера и логи серверов.

**Замена:** `Authorization Code` + `PKCE` для всех типов клиентов, включая SPA.

#### 3. Resource Owner Password Credentials (ROPC) — **УДАЛЁН в OAuth 2.1**

Пользователь передаёт логин и пароль напрямую клиенту. **Полностью удалён из OAuth 2.1** — нарушает принцип делегирования, подвержен фишингу, не поддерживает MFA.

**Замена:** `Authorization Code` + `PKCE`. Для legacy-систем, где ROPC неизбежен, использовать только в изолированных сетях с дополнительным мониторингом.

#### 4. Client Credentials

Используется для межсерверного взаимодействия, когда приложение запрашивает доступ к своим собственным ресурсам (аутентификация приложения, а не пользователя).

### Использование и обновление токена

* **Доступ к ресурсам:** Клиент передаёт токен доступа в заголовке `Authorization: Bearer ACCESS_TOKEN`.
* **Обновление токена:** Когда `access_token` истекает, клиент использует `refresh_token` для получения нового `access_token` без участия пользователя.

### Эволюция OAuth 2.0 → OAuth 2.1

OAuth 2.1 — не новая версия, а консолидация RFC 6749, RFC 6750 и security best practices в единую спецификацию. Ключевые отличия:

| Изменение | OAuth 2.0 | OAuth 2.1 |
| :--- | :--- | :--- |
| **PKCE** | Рекомендован для публичных клиентов | **Обязателен для всех клиентов** |
| **Implicit Grant** | Устарел | **Полностью удалён** |
| **ROPC** | Не рекомендован | **Полностью удалён** |
| **Redirect URI** | Частичная валидация | **Строгое exact-match сравнение** |
| **Refresh Token для SPA** | Не поддерживался | **Поддерживается через Authorization Code + PKCE** |
| **Token Best Practices** | Bearer-токены | **DPoP рекомендован** |

**Миграция:** Существующие реализации OAuth 2.0, использующие Authorization Code + PKCE, совместимы с OAuth 2.1. Приложения, использующие Implicit или ROPC, требуют перехода на Authorization Code + PKCE.

## 4. Дополнительная информация

### Аспекты безопасности и лучшие практики

* **Использование HTTPS/TLS:** Все коммуникации между клиентом, сервером авторизации и сервером ресурсов — только по HTTPS.
* **PKCE (Proof Key for Code Exchange):** **Обязателен для всех клиентов** в OAuth 2.1. Предотвращает атаку перехвата кода авторизации (authorization code interception). В OAuth 2.0 был рекомендован только для публичных клиентов.
* **Валидация Redirect URI:** Сервер авторизации должен выполнять **строгое exact-match сравнение** Redirect URI, зарегистрированного клиентом, с фактическим. Частичное совпадение (prefix, substring) — вектор атаки code injection.
* **Замена Implicit и ROPC:** Вместо удалённых в OAuth 2.1 `Implicit Grant` и `ROPC` — всегда использовать `Authorization Code` + `PKCE`.
* **Срок действия токенов:** Access Tokens — короткий срок (минуты), Refresh Tokens — долговечные (дни/месяцы) с обязательным механизмом отзыва.
* **Проверка токенов:** Сервер ресурсов проверяет: подпись, срок действия, issuer (`iss`), аудиторию (`aud`), scopes.
* **DPoP (Demonstrating Proof-of-Possession):** Альтернатива Bearer-токенам — токен привязывается к криптографическому ключу клиента через заголовок `DPoP`. Предотвращает использование украденного токена злоумышленником. Рекомендован в OAuth 2.1 для сценариев с повышенными требованиями к безопасности.
* **Client Secret хранение:** Никогда не хранить в коде клиентских приложений (SPA, мобильные). Использовать серверную часть или PKCE для публичных клиентов.
