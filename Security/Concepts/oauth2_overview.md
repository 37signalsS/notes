# OAuth 2.0 и OpenID Connect

## Определения

**OAuth 2.0** — открытый протокол авторизации ([RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749)), позволяющий приложениям получать ограниченный доступ к ресурсам пользователя без передачи пароля. Основная идея — делегирование прав доступа через использование токенов.

**OpenID Connect (OIDC)** — уровень идентификации, построенный поверх OAuth 2.0. Добавляет понятие **ID Token** и стандартизированный способ получения информации о профиле пользователя.

**OAuth 2.1** — консолидированная спецификация (2025), объединяющая лучшие практики безопасности и удаляющая устаревшие механизмы (Implicit Grant, ROPC).

## Основные концепции

### Роли в протоколе

| Роль | Описание |
| :--- | :--- |
| **Resource Owner** | Владелец ресурса (пользователь), который дает разрешение на доступ. |
| **Client** | Приложение (веб, мобильное, сервис), запрашивающее доступ. |
| **Authorization Server** | Сервер, который аутентифицирует пользователя и выдаёт токены. |
| **Resource Server** | API или сервис, хранящий защищённые данные и принимающий токены. |

### Токены

- **Access Token:** Краткосрочный токен (обычно JWT) для доступа к API. Содержит права доступа (**Scopes**).
- **Refresh Token:** Долгосрочный токен для получения нового Access Token без участия пользователя.
- **ID Token:** (только в OIDC) Содержит информацию о пользователе (имя, email, sub).

### Области действия (Scopes)

Определяют границы доступа клиента. Примеры: `openid`, `profile`, `email`, `read:files`. Пользователь должен подтвердить согласие на использование конкретных scopes в процессе авторизации.

## Практические сценарии

### Типы авторизации (Grant Types)

| Метод | Применение | Безопасность |
| :--- | :--- | :--- |
| **Authorization Code + PKCE** | Веб-сайты (SPA, SSR), мобильные приложения | Высокая (рекомендовано) |
| **Client Credentials** | Межсерверное взаимодействие (M2M) | Высокая |
| **Device Code** | Устройства без браузера или с ограниченным вводом (Smart TV) | Средняя |
| **Implicit / ROPC** | Устаревшие методы | **Низкая (удалены в OAuth 2.1)** |

### Процесс Authorization Code + PKCE

1. **Клиент** генерирует случайный код (`code_verifier`) и его хеш (`code_challenge`).
2. Перенаправление пользователя на **Authorization Server** с передачей `code_challenge`.
3. После аутентификации сервер возвращает временный `authorization_code`.
4. Клиент обменивает `authorization_code` + `code_verifier` на токены. Сервер проверяет соответствие верификатора и челленджа.

### Использование токенов

Токен передаётся в заголовке запроса к API:
`Authorization: Bearer <access_token>`

## Дополнительная информация

### Безопасность и лучшие практики

- **PKCE (Proof Key for Code Exchange):** Обязателен для всех типов приложений в OAuth 2.1 для предотвращения перехвата кода.
- **Redirect URI:** Сервер должен использовать строгое сравнение (exact match) обратных адресов.
- **DPoP (Demonstrating Proof-of-Possession):** Привязка токена к криптографическому ключу клиента для защиты от использования украденных Bearer-токенов.
- **HTTPS:** Использование TLS обязательно для всех этапов взаимодействия.

### Инструменты

- **Keycloak:** Полнофункциональный Identity Provider (IdP) с открытым кодом.
- **Dex:** Легковесный OIDC-провайдер для Kubernetes и небольших систем.
- **Ory Hydra:** Высокопроизводительный сервер только для OAuth 2.0 и OIDC.
- **Auth0 / Okta:** Облачные решения (SaaS).
