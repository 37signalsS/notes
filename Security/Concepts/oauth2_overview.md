# Обзор OAuth 2.0

## 1. Определения

**OAuth 2.0** — это открытый протокол авторизации, который позволяет приложениям получать ограниченный доступ к учетным записям пользователей на HTTP-сервисах. Он делегирует процесс аутентификации сервису, где находится аккаунт пользователя, и выдает клиенту токен с ограниченными правами вместо пароля.

## 2. Основные концепции

### Роли в OAuth 2.0
*   **Владелец ресурса (Resource Owner):** Пользователь.
*   **Клиент (Client):** Приложение, запрашивающее доступ.
*   **Сервер авторизации (Authorization Server):** Сервер, выдающий токены.
*   **Сервер ресурсов (Resource Server):** Сервер, где хранятся защищенные ресурсы (API).

### Токены: Access Token и Refresh Token
- **Access Token:** Краткосрочный токен, который клиент использует для доступа к защищенным ресурсам. Он содержит информацию об авторизации и области действия (scopes). Access Token обычно не шифруется, но подписывается сервером авторизации.
- **Refresh Token:** Долгосрочный токен, который используется клиентом для получения нового Access Token, когда предыдущий истекает. Refresh Token обычно выдается только доверенным клиентам и хранится более безопасно.

### Области действия (Scopes)
Scopes определяют, к каким частям пользовательских данных или функциям приложение может получить доступ. Например, `email`, `profile`, `read:tweets`, `write:tweets`. Пользователь должен дать согласие на запрашиваемые scopes во время авторизации.

### Общая схема работы
1.  Клиент запрашивает авторизацию у пользователя на определенные **scopes**.
2.  Пользователь дает согласие.
3.  Клиент запрашивает **Access Token** у сервера авторизации.
4.  Сервер авторизации выдает токен.
5.  Клиент использует токен для доступа к ресурсам на сервере ресурсов.

### Регистрация клиента
Перед использованием протокола клиент регистрируется на сервере авторизации и получает **Client ID** (публичный) и **Client Secret** (конфиденциальный). Также указывается **Redirect URI** — адрес, на который пользователь будет перенаправлен после авторизации.

## 3. Практические сценарии

### Типы авторизации (Grant Types)
Это различные способы получения токена доступа.

#### 1. Authorization Code
Наиболее распространенный и безопасный тип для веб-приложений.
1.  Клиент перенаправляет пользователя на сервер авторизации.
2.  Пользователь логинится и дает разрешение.
3.  Сервер авторизации возвращает пользователя на `Redirect URI` с **кодом авторизации**.
4.  Клиент обменивает этот код (вместе со своим `Client Secret`) на **Access Token** и, опционально, **Refresh Token**.

#### 2. Implicit (Неявный) - *Устарел*
Упрощенный вариант для SPA-приложений, где `client_secret` не может храниться безопасно. Токен доступа передается напрямую клиенту в URL. **Считается устаревшим и небезопасным.**

#### 3. Resource Owner Password Credentials (ROPC)
Пользователь предоставляет логин и пароль напрямую клиенту. **Используется только для полностью доверенных приложений** (например, официальное мобильное приложение сервиса).

#### 4. Client Credentials
Используется для межсерверного взаимодействия, когда приложение запрашивает доступ к своим собственным ресурсам (аутентификация приложения, а не пользователя).

### Использование и обновление токена
- **Доступ к ресурсам:** Клиент передает токен доступа в заголовке `Authorization: Bearer ACCESS_TOKEN`.
- **Обновление токена:** Когда `access_token` истекает, клиент использует `refresh_token` для получения нового `access_token` без участия пользователя.

## 4. Дополнительная информация

### Аспекты безопасности и лучшие практики
- **Использование HTTPS/TLS:** Все коммуникации между клиентом, сервером авторизации и сервером ресурсов должны осуществляться по HTTPS для защиты токенов от перехвата.
- **PKCE (Proof Key for Code Exchange):** Обязательное к использованию расширение для `Authorization Code` flow, которое предотвращает атаку перехвата кода авторизации. Особенно критично для публичных клиентов (мобильные и SPA-приложения), где `Client Secret` не может быть безопасно сохранен.
- **Замена неявного потока:** Вместо устаревшего `Implicit Grant Type` следует всегда использовать `Authorization Code` с `PKCE`.
- **Срок действия токенов:** Access Tokens должны иметь короткий срок действия (минуты) для минимизации ущерба в случае их компрометации. Refresh Tokens могут быть более долговечными (дни, месяцы), но должны быть надежно защищены и иметь механизм отзыва.
- **Проверка токенов:** Сервер ресурсов должен всегда проверять Access Token (его подпись, срок действия, issuer и аудиторию) перед предоставлением доступа.
