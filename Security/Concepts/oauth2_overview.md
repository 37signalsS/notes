# Обзор OAuth 2.0

**OAuth 2.0** — это открытый протокол авторизации, целью которого является настройка ограничений доступа. Это можно делать, в том числе, на GitHub и подобных сервисах. Протокол делегирует процесс аутентификации сервису, где находится пользовательский аккаунт, и позволяет приложениям получать ограниченный доступ к учетным записям пользователей на HTTP-сервисах, обеспечивая доступ к ним какого-либо иного сервиса.

## Роли в OAuth 2.0

*   **Владелец ресурса (Resource Owner):** Пользователь, который предоставляет доступ к своей учетной записи.
*   **Клиент (Client):** Приложение, которое запрашивает доступ к учетной записи владельца ресурса.
*   **Сервер авторизации (Authorization Server):** Сервер, который аутентифицирует владельца ресурса и выдает токены доступа после получения его согласия.
*   **Сервер ресурсов (Resource Server):** Сервер, на котором хранятся защищенные ресурсы. Он принимает и проверяет токены доступа.

## Общая схема работы

1.  **Запрос авторизации:** Клиент запрашивает авторизацию у владельца ресурса.
2.  **Предоставление разрешения:** Владелец ресурса предоставляет разрешение клиенту.
3.  **Запрос токена доступа:** Клиент запрашивает токен доступа у сервера авторизации, предоставляя разрешение.
4.  **Выдача токена доступа:** Сервер авторизации аутентифицирует клиента и выдает токен доступа.
5.  **Запрос ресурса:** Клиент запрашивает ресурс у сервера ресурсов, предъявляя токен доступа.
6.  **Предоставление ресурса:** Сервер ресурсов проверяет токен и, в случае успеха, предоставляет доступ к ресурсу.

## Регистрация клиента

Перед использованием OAuth 2.0 клиент должен быть зарегистрирован на сервере авторизации. В процессе регистрации указываются:
*   Имя приложения.
*   Сайт приложения.
*   **Redirect URI (Callback URL):** URL, на который сервер авторизации перенаправляет пользователя после предоставления (или отказа в предоставлении) разрешения.

После регистрации клиент получает:
*   **Client ID:** Публичный идентификатор клиента.
*   **Client Secret:** Конфиденциальный ключ, используемый для аутентификации клиента.

## Типы авторизации (Grant Types)

### 1. Authorization Code

Наиболее распространенный и безопасный тип авторизации. Используется для веб-приложений, работающих на стороне сервера.

**Шаг 1: Запрос кода авторизации**
Клиент перенаправляет пользователя на сервер авторизации:
```
https://anyapplication.com/v1/oauth/authorize?response_type=code&client_id=CLIENT_ID&redirect_uri=CALLBACK_URL&scope=read
```

**Шаг 2: Пользователь предоставляет разрешение**
Пользователь авторизуется на сервере авторизации и разрешает приложению доступ.

**Шаг 3: Сервер перенаправляет пользователя обратно к клиенту**
Сервер авторизации перенаправляет пользователя на `redirect_uri` с кодом авторизации:
```
https://anyapplication.com/callback?code=AUTHORIZATION_CODE
```

**Шаг 4: Клиент обменивает код на токен доступа**
Клиент отправляет POST-запрос на сервер авторизации с кодом авторизации, Client ID и Client Secret:
```
https://anyapplication.com/v1/oauth/token?client_id=CLIENT_ID&client_secret=CLIENT_SECRET&grant_type=authorization_code&code=AUTHORIZATION_CODE&redirect_uri=CALLBACK_URL
```

**Шаг 5: Сервер возвращает токен доступа**
```json
{
  "access_token": "ACCESS_TOKEN",
  "token_type": "bearer",
  "expires_in": 2431000,
  "refresh_token": "REFRESH_TOKEN",
  "scope": "read"
}
```

### 2. Implicit (Неявный)

Упрощенный вариант, предназначенный для JavaScript-приложений (Single Page Applications) и мобильных приложений, где `client_secret` не может храниться безопасно. Токен доступа передается напрямую клиенту через Redirect URI. **Этот тип считается устаревшим и менее безопасным.**

**Шаг 1: Запрос токена**
```
https://anyapplication.com/v1/oauth/authorize?response_type=token&client_id=CLIENT_ID&redirect_uri=CALLBACK_URL&scope=read
```

**Шаг 2: Пользователь предоставляет разрешение**

**Шаг 3: Сервер перенаправляет пользователя с токеном**
```
https://anyapplication.com/callback#token=ACCESS_TOKEN
```
Клиент извлекает токен из URL. `refresh_token` в этом потоке не выдается.

### 3. Resource Owner Password Credentials (ROPC)

Пользователь предоставляет свои учетные данные (логин и пароль) напрямую клиенту. Клиент использует их для получения токена доступа. **Этот тип следует использовать только для полностью доверенных приложений** (например, официальных приложений самого сервиса).

**Запрос токена:**
```
https://oauth.anyapplication.com/token?grant_type=password&username=USERNAME&password=PASSWORD&client_id=CLIENT_ID
```

### 4. Client Credentials

Используется для межсерверного взаимодействия, когда клиент запрашивает доступ к своим собственным ресурсам, а не от имени пользователя.

**Запрос токена:**
```
https://oauth.anyapplication.com/token?grant_type=client_credentials&client_id=CLIENT_ID&client_secret=CLIENT_SECRET
```

## Использование и обновление токена

### Доступ к ресурсам

Клиент передает токен доступа в заголовке `Authorization`:
```sh
curl -X POST -H "Authorization: Bearer ACCESS_TOKEN" "https://api.anyapplication.com/v2/$OBJECT"
```

### Обновление токена (Refresh Token)

Когда `access_token` истекает, клиент может использовать `refresh_token` (полученный в потоке Authorization Code) для получения нового `access_token` без участия пользователя.

**Запрос нового токена:**
```
https://anyapplication.com/v1/oauth/token?grant_type=refresh_token&client_id=CLIENT_ID&client_secret=CLIENT_SECRET&refresh_token=REFRESH_TOKEN
```
