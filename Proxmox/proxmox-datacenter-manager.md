# Proxmox Datacenter Manager (PDM) — центр управления виртуальной инфраструктурой

**Актуально для:** Proxmox Datacenter Manager 1.0 / 1.1

## Определения

**Proxmox Datacenter Manager (PDM)** — централизованное решение для управления несколькими независимыми Proxmox-окружениями: серверами Proxmox VE (PVE), кластерами PVE и серверами Proxmox Backup Server (PBS). Предоставляет единый интерфейс (single pane of glass) для администрирования, мониторинга и масштабирования распределённой инфраструктуры. Ближайший аналог — VMware vCenter, но для хостов, не объединённых в общий кластер.

**Remote** — подключённый к PDM внешний компонент: узел PVE, кластер PVE или экземпляр PBS. PDM опрашивает remotes через API и собирает метрики RRD, статусы задач и логи.

**Endpoint** — конкретный адрес (IP/hostname) внутри remote, через который PDM выполняет операции. У одиночного узла PVE — один endpoint; у кластера — по одному на каждую ноду; при миграции выбирается, через какой endpoint выполнять перенос.

**API Token (auto-generated)** — токен, который PDM автоматически создаёт на remote при первом подключении для работы через API. При повторном подключении к тому же серверу с тем же именем конфликтует со старым токеном.

**Guest** — виртуальная машина (QEMU/KVM) или контейнер (LXC), учтённый в PDM.

**Fingerprint pinning** — механизм доверия к сертификату remote: если сертификат не в системном хранилище (как самоподписанные сертификаты Proxmox по умолчанию), PDM запоминает fingerprint, принятый при подключении. При ротации сертификата на remote pinned fingerprint перестаёт совпадать с предъявленным, и все подключения к remote падают.

## Основные концепции

### Что это и зачем нужен

PDM объединяет в одном месте многие Proxmox-сервера, кластеры и backup-сервера, где ими можно управлять, и упрощает ряд повседневных задач:

- **Один Proxmox-сервер** — PDM не даёт преимуществ: его функционал дублирует веб-интерфейс самого сервера.
- **Несколько серверов/кластеров** — реальная ценность: единый дашборд по всем системам, центральное управление пользователями, апдейты всех систем сразу, миграция гостей между независимыми хостами.

### Архитектура взаимодействия с remotes

- PDM сам инициирует соединения к remotes (API-запросы, метрики нагрузки и использования). Remotes не обязаны подключаться к PDM обратно.
- Reverse proxy между PDM и PVE-remote **не поддерживается**; для хостов, которые не должны быть открыты в неприватную сеть, рекомендуется туннелирование (WireGuard, OpenVPN).
- Минимальные поддерживаемые версии remotes: **PVE 8.4**, **PBS 3.4**.
- Полностью написан на Rust (backend API, CLI-утилиты, новый frontend на собственном widget toolkit). Лицензия — GNU AGPLv3.
- Тестировался с 5000+ remotes и 10000+ гостями.

## Установка и настройка

### Системные требования

| | Минимум (только для оценки) | Рекомендуется (production) |
|---|---|---|
| CPU | x86-64/AMD64, 1+ ядер | современный AMD/Intel 64-bit, 2+ ядра |
| RAM | 1 GiB | 4 GiB+ для ОС |
| Диск | >10 GB | 40 GB+; hardware RAID с BBU или избыточный ZFS |
| Сеть | NIC | избыточные multi-GBit/s NIC |

Установка возможна на bare-metal, в VM (в видео-демо: 15 GB диск, 2 ядра, 4 GB RAM — достаточно для ознакомления) или поверх Debian. Установка совместно с PVE/PBS на одном хосте возможна, но не рекомендуется (только для экспертов).

### Установка с ISO

1. Скачать ISO с https://www.proxmox.com/downloads. Образ гибридный: готов к записи на DVD или на USB-флешку (≥2 GB; для USB — `dd`, UNetbootin не поддерживается; Rufus — в DD-режиме).
2. Создать VM (Create VM): имя (например, PDM), ISO-образ, диск 15 GB+, 2 ядра, 4 GB RAM, сеть с доступом ко всем компонентам Proxmox (сервера, кластеры, PBS).
3. Запустить консоль — инсталлятор аналогичен инсталлятору PVE: лицензия → диск → часовой пояс (важен для корректных логов и cron-задач) → пароль + email → IP (по умолчанию от DHCP-сервера) → сетевые интерфейсы.
4. После установки — автоматическая перезагрузка; на экране отображается IP-адрес и порт. Веб-интерфейс: `https://<ip>:8443`.
5. Первый вход — пароль из установки. Язык интерфейса можно сменить, но рекомендуется оставить английский — проще искать решения возникающих проблем.

### Установка поверх Debian

```bash
# Минимальная установка (сохраняет текущий kernel Debian)
apt update
apt install proxmox-datacenter-manager-container-meta

# С Proxmox-ядром и поддержкой ZFS
apt install proxmox-datacenter-manager-meta
```

### Репозитории и первая настройка

По умолчанию включён `pdm-enterprise` (стабильный, требует subscription key; remote-ноды должны иметь подписку Basic и выше). Без подписки — в Administration отключить enterprise-репозиторий и добавить no-subscription:

```text
# /etc/apt/sources.list.d/pdm-no-subscription.sources
Types: deb
URIs: http://download.proxmox.com/debian/pdm
Suites: trixie
Components: pdm-no-subscription
Signed-By: /usr/share/keyrings/proxmox-archive-keyring.gpg
```

Затем Administration → Updates → Refresh — обновления становятся доступны. В Administration также доступны статус PDM, логи, таски и Shell.

## Добавление remotes

Remotes → Add (или меню → Remotes → Add): Proxmox VE / Proxmox Backup Server.

### Proxmox VE сервер

1. IP-адрес и порт **8006** → Next — проверяется физическая доступность (IP и порт открыты).
2. Подтвердить fingerprint сертификата.
3. Имя remote (например, PMX01), пользователь и пароль для подключения.
4. Summary: endpoints — у одиночного сервера один IP и fingerprint → Finish.

После подключения в дашборде сразу видны все ВМ и контейнеры remote с тегами.

### Кластер Proxmox VE

1. IP любого нода кластера, порт 8006, имя (например, cluster-01), пользователь, пароль.
2. PDM обнаруживает все ноды — endpoints по одному на ноду (первый по IP, остальные по hostname нод).
3. Если ноды не резолвятся по hostname — заменить hostnames на IP-адреса в списке endpoints, иначе подключение завершится ошибками.
4. Finish — видна вся конфигурация нод кластера.

### Proxmox Backup Server

1. IP и порт **8007**, имя remote (например, PBS-01) → Finish.
2. Отображается информация по бэкапам и контенту на PBS; из PDM есть быстрые переходы в веб-интерфейс PBS и в shell.

### Решение конфликта API-токена

Ошибка при подключении, если PDM ранее уже подключался к этому серверу с таким же именем: на remote остаётся auto-generated токен от старого подключения.

Решение: на PVE-сервере — Datacenter → API Tokens → удалить auto-generated токен (Remove) → в PDM нажать Finish ещё раз.

## Dashboard, Views и Guests

### Dashboard

- Количество ВМ (запущено/остановлено/всего), контейнеров, подключённых backup-серверов.
- Потребление ресурсов: какие системы потребляют больше всего CPU и памяти (масштабирование виджета ресурсов не очень удобно).
- Клик по элементу — переход к этой ВМ/контейнеру на конкретном хосте в отдельном окне.
- Джобы, таски и SDN-зоны всех подключённых компонентов.

### Views — пользовательские дашборды

Views → Add View: имя вида, выбор remotes (все или конкретные) → Edit → Add Row → виджеты (Proxmox ноды, ВМ, контейнеры, ресурсы) → Save.

### Guests (с 1.1)

Единый список всех ВМ и контейнеров всех remotes: плоский список (имя, ID, статус, remote, нода, теги, CPU, память, uptime) или дерево по remotes. Фильтр поддерживает квалификаторы `field:value`: `tag:`, `remote:`, `node:`, `status:`, `type:` (qemu/lxc); несколько терминов комбинируются через AND. Действия: Start, Resume (только для QEMU в paused/suspended), Shutdown, Snapshots, Migrate (внутри remote или между remotes; для шаблонов недоступна), Open in PVE UI.

### Notes и Configuration

- Notes — одно текстовое поле для комментариев коллегам (ограниченная полезность).
- Configuration — информация по сети PDM и её изменение.

## Центральное управление

- **Access Control** — центральное управление пользователями для всех подключённых PVE-серверов (раньше — добавлять на каждом сервере отдельно).
- **Certificates / Subscriptions** — сертификаты и информация о подписках всех систем.
- **Обновления** — Remotes → Updates → Refresh All: статус апдейтов и версии всех PVE-серверов и нод кластеров; апгрейд из одного места.
- **Firewall** — просмотр правил на всех системах (полезно при использовании Proxmox Firewall; при внешнем firewall всё и так централизовано).
- **SDN** — общий обзор SDN-зон всех компонентов. В 1.0 доступны только VPN-зоны; в 1.1 — EVPN-зоны и VNets между remotes.
- **Ceph (с 1.1)** — унифицированный мониторинг Ceph-кластеров.

## Миграция гостей между remotes

Ключевая возможность PDM: live-миграция ВМ/контейнеров между независимыми хостами и кластерами — без требований к кластерной сети. Раньше для переноса между серверами использовалась схема «backup на PBS → подключение PBS к другому Proxmox → восстановление».

Порядок действий:

1. Выбрать гостя на source-remote → Migrate.
2. В диалоге: source endpoint, target endpoint (для кластера — конкретная нода; гость появится на выбранной ноде), опция удаления source (включена — оригинал удаляется после переноса; выключена — остаётся копией), VM ID, storage и сеть на target.
3. **VM ID должен быть свободен на target** — проверить на самом target-сервере; автоматической проверки свободных ID нет. При занятом ID — ошибка `VM10 already exist`, процесс начинается заново.
4. Storage — целевое хранилище (например, XFS); сеть — bridge на target (vmbr0/vmbr1, могут указывать на разные физические интерфейсы).
5. Migrate — скорость зависит от сети; контейнеры мигрируют быстро.

Ограничения (1.0): миграция невозможна, если у гостя есть снапшоты (`nonmigratable snapshot`) — сначала удалить снапшоты; конфигурация ВМ в PDM доступна только для чтения; создание ВМ/контейнеров из PDM недоступно (частично расширено в 1.1).

## Типичные проблемы и диагностика

| Проблема | Причина | Решение |
|---|---|---|
| Ошибка подключения remote с тем же именем | остался auto-generated API-токен от предыдущего подключения | Datacenter → API Tokens на remote → Remove старого токена → Finish в PDM |
| `VM10 already exist` при миграции | ID занят на target | выбрать свободный ID на target и повторить |
| `nonmigratable snapshot` | у гостя есть снапшоты | удалить снапшоты и повторить |
| Ошибки endpoints при добавлении кластера | ноды не резолвятся по hostname | заменить hostnames на IP-адреса в списке endpoints |
| `connection failed: Could not establish a TLS connection... certificate verify failed` | сертификат remote обновлён/ротирован, pinned fingerprint не совпадает | remote → Check Certificate (предварительно подтвердить новый сертификат по доверенному каналу) или CLI: `proxmox-datacenter-manager-client remote probe-certificate <remote> <node>`, затем `set-fingerprint <remote> <node> <fingerprint>` |

## Лучшие практики

- PDM оправдан при нескольких PVE-серверах/кластерах/PBS; для одного сервера не нужен.
- Часовой пояс при установке указывать точно — иначе логи и cron-задачи будут в неверном времени.
- Интерфейс оставить на английском для поиска решений проблем.
- Сеть PDM должна иметь доступ ко всем компонентам (сервера, кластеры, PBS); для удалённых хостов — туннели (WireGuard/OpenVPN), reverse proxy не поддерживается.
- Для production — рекомендуемые требования (40 GB+, ZFS/RAID с BBU, избыточные NIC); enterprise-репозиторий только при наличии subscription.
- Перед миграцией — проверить свободные ID на target и отсутствие снапшотов у гостя.
