# Кластеризация и High Availability в Proxmox

**Актуально для:** Proxmox VE 9.2 (ветка 9.x; HA-группы устарели с 9.0 в пользу affinity-правил)

## Определения

**Proxmox Cluster** — это объединение нескольких независимых серверов Proxmox Virtual Environment (PVE) в единую систему с централизованным управлением через веб-интерфейс или Command Line Interface (CLI).

**High Availability (HA, Высокая доступность)** — механизм, обеспечивающий автоматический перезапуск виртуальных машин (VM) или контейнеров (LXC) на другом узле в случае сбоя текущего хоста.

**Corosync** — основной сервис обмена сообщениями и контроля состояния (Cluster Engine), обеспечивающий работу кластера и отслеживание доступности нод. В PVE используется транспорт **knet (Kronosnet)**, поддерживающий несколько независимых линков между нодами и шифрование.

**pve-ha-manager** — собственный HA-стек Proxmox, состоящий из двух демонов на каждой ноде:
- **pve-ha-crm (Cluster Resource Manager)** — демон, принимающий кластерные решения. На каждой ноде есть экземпляр, но активен только один (master): именно он распределяет ресурсы между узлами, обрабатывает отказы и инициирует fencing.
- **pve-ha-lrm (Local Resource Manager)** — локальный демон, исполняющий команды CRM (start/stop/migrate) для ресурсов на своей ноде и сбрасывающий watchdog.

**Fencing (изоляция узла)** — принудительная перезагрузка неисправного узла, чтобы исключить конкурентный доступ к общим данным.

**Split-Brain (разделение кластера)** — состояние, при котором ноды теряют связь друг с другом, но продолжают работать. Без механизмов кворума и fencing обе части могут одновременно запустить одни и те же ресурсы.

## Основные концепции

### Требования и правила создания кластера

- **Версионность**: Все узлы должны иметь одинаковую мажорную версию Proxmox (актуальная ветка — 9.x, последний релиз 9.2; PVE 8.x достиг конца поддержки (EOL) 31 августа 2026 и больше не получает исправлений безопасности). Допускается временное смешивание версий только в процессе апгрейда. Процедура обновления кластера описана в **[Обновление систем Proxmox](./proxmox_updates.md)**.
- **Имена узлов**: короткие, без пробелов; должны корректно резолвиться по DNS. Имя задается один раз при установке и не меняется в процессе эксплуатации.
- **Синхронизация времени**: Использование `chrony` или `systemd-timesyncd` (NTP) обязательно для предотвращения рассинхронизации кворума и логов.
- **Сеть Corosync**: Рекомендуется выделять отдельную физическую сеть с задержками менее 2 мс и корректным MTU (см. раздел «Ошибки Corosync»).
- **Кворум (Quorum)**: Минимальное количество голосов для принятия решений. Кластер работоспособен (quorate), если доступно >50% голосов.
- **Портовая доступность** (при включенном firewall):
  - Corosync (knet): UDP 5405–5412;
  - QDevice/QNetd: TCP 5403;
  - живая миграция и передача данных: TCP 60000–60050;
  - веб-интерфейс: TCP 8006, SSH: TCP 22.

### Резервирование Corosync (Multi-link / knet)

Proxmox поддерживает до 8 линков (интерфейсов) для Corosync. Это критически важно для предотвращения развала кластера при сбое одного коммутатора или кабеля.
- **Priority**: Каждому линку можно назначить приоритет (`knet_link_priority`, 0–255). В пассивном режиме (`link_mode: passive`, по умолчанию) трафик идёт по линку с **наивысшим** номером приоритета; при его потере — по следующему по приоритету. Если приоритеты не заданы или равны, используется линк с **наименьшим** номером (`linknumber`), а failover идёт вверх по номерам.
- **Рекомендация**: Использовать как минимум два независимых сетевых пути (разные коммутаторы/подсети), так как одиночный линк является единой точкой отказа для всего кластера.
- **Задача приоритетов при создании кластера** (приоритет выше → используется первым):

```bash
pvecm create my-cluster \
  --link0 10.10.10.1,priority=15 \
  --link1 10.20.20.1,priority=20
# link1 используется первым: приоритет 20 > 15
```

Если кластер создавался без приоритетов, их можно прописать в `/etc/pve/corosync.conf` (секции `interface`) и перезапустить `corosync` на всех нодах. При добавлении узла в кластер с выделенной cluster-сетью укажите адрес узла в этой сети: `pvecm add <IP> --link0 <LOCAL_IP_LINK0> [--link1 <LOCAL_IP_LINK1>]`.

### Конфигурация Corosync (corosync.conf)

Хотя PVE генерирует и управляет `/etc/pve/corosync.conf` автоматически, понимание его структуры важно для диагностики и продвинутой настройки.

Пример файла с двумя линками knet:

```text
totem {
    version: 2
    cluster_name: my-cluster
    transport: knet
    interface {
        linknumber: 0
        knet_link_priority: 10
        # IP-адрес первой подсети Corosync (приоритет 10)
    }
    interface {
        linknumber: 1
        knet_link_priority: 20
        # IP-адрес второй подсети Corosync (приоритет 20 — используется первой)
    }
}

nodelist {
    node {
        nodeid: 1
        name: node1
        ring0_addr: 10.0.0.1
        ring1_addr: 10.0.1.1
    }
    node {
        nodeid: 2
        name: node2
        ring0_addr: 10.0.0.2
        ring1_addr: 10.0.1.2
    }
}

quorum {
    provider: corosync_votequorum
    two_node: 0
}

logging {
    to_logfile: yes
    logfile: /var/log/corosync/corosync.log
    to_syslog: yes
    debug: off
}
```

- **ring0_addr / ring1_addr**: IP-адреса для каждого линка. В GUI эти адреса настраиваются при создании кластера.
- **knet_link_priority**: чем больше число, тем выше приоритет линка (в пассивном режиме используется линк с наивысшим приоритетом; при равенстве — с наименьшим номером linknumber).
- **two_node**: `1` только для кластеров из 2 нод без QDevice (включает two_node режим votequorum).
- **Изменение конфигурации**: PVE может перезаписывать файл при изменении состава кластера. Предпочтительный способ задать приоритеты — параметр `priority` в `pvecm create` (см. раздел «Резервирование Corosync»); для ручных правок редактируйте файл с осторожностью, проверяя синтаксис через `corosync-cfgtool -s`.

### Кворум и голоса (Quorum)

Количество голосов определяется составом кластера и наличием внешнего голоса:
- **Expected votes** — ожидаемое число голосов по конфигурации (по умолчанию по одному на ноду + голос QDevice).
- **Total votes** — сумма голосов участников, видимых в данный момент.
- **Quorum** — порог кворума: `floor(Expected votes / 2) + 1`. Кластер остается quorate, пока `Total votes` не опускается ниже этого порога.
- **Примеры порогов**:
  - **2 ноды** → порог 2, нужно 2/2 голосов. При падении одной ноды кворум теряется;
  - **3 ноды** → порог 2, достаточно 2/3 голосов. Потеря одной ноды не ломает кластер;
  - **4 ноды** → порог 3, нужно 3/4 голосов;
  - **5 нод** → порог 3, достаточно 3/5 голосов.
- **Quorate / Not quorate** — статус работоспособности: при `Quorate: No` блокируется управление кластером, включая запись в `/etc/pve` (pmxcfs).
- **`pvecm expected <n>`** — временно задает ожидаемое число голосов для восстановления кворума (подробнее в разделе «Диагностика»).

### QDevice (Quorum Device)

Используется для кластеров из 2-х нод или при четном количестве узлов для обеспечения нечетного количества голосов.
- **Split-Brain**: QDevice предотвращает одновременный запуск ресурсов на обеих сторонах: голос получает та партиция, которая сохранила связь с QDevice.
- **Внешний голос**: QDevice работает на стороннем сервере (не члене кластера) и предоставляет дополнительный голос. Хост QNetd должен быть независим по питанию и сети от обоих узлов кластера, иначе его голос бессмысленен.
- **Типичный хост QNetd**: легковесная платформа — отдельный мини-ПК, одноплатный компьютер (например, Raspberry Pi) или небольшая VM. Демон QNetd не требует мощного сервера и может работать под ОС, отличной от PVE.
- **Алгоритмы**: `ffsplit` (fifty-fifty split, по умолчанию) — при разделении на равные партиции голос получает партиция с большим числом живых нод, иначе применяется tie-breaker; `lms` (last man standing) — голос получает единственная нода, сохранившая связь с QNetd.
- **Tie-breaker**: `lowest` (по умолчанию) — голос получает партиция с наименьшим node id; `highest` — с наибольшим; либо указывается конкретный node id.
- **Порт**: QNetd слушает TCP 5403. Один QNetd-сервер может обслуживать несколько независимых кластеров (изоляция по сертификатам).

### Fencing и Watchdog

Механизм изоляции сбойного узла.
- **Watchdog**: Аппаратный (IPMI/BMC, iTCO_wdt) или программный (`softdog`) таймер. Если `pve-ha-lrm` не сбрасывает таймер (нода зависла или потеряла кворум), узел принудительно перезагружается. Доступ к `/dev/watchdog` держит сервис **watchdog-mux** — его нельзя убивать вместе с `pve-ha-crm`/`pve-ha-lrm`, иначе возможна немедленная перезагрузка ноды.
- **Выбор модуля watchdog**: по умолчанию `softdog`; аппаратный watchdog включается в `/etc/default/pve-ha-manager`:

```ini
# /etc/default/pve-ha-manager
WATCHDOG_MODULE=iTCO_wdt
```

Файл читает сервис watchdog-mux, загружающий указанный модуль при старте. По умолчанию большинство аппаратных watchdog-модулей заблокированы по соображениям безопасности.
- **Режим fencing**: `fencing=<watchdog|hardware|both>` в `/etc/pve/datacenter.cfg` (по умолчанию `watchdog`); режимы `hardware` и `both` (дополнительно `/etc/pve/ha/fence.cfg`) — EXPERIMENTAL.
- **Self-Fencing**: Автоматическая перезагрузка узла при потере кворума для защиты общих данных от конкурентной записи.
- **Тайминги failover**: типичное время обнаружения сбоя и переноса ресурсов (error detection + failover) в ha-manager — около 2 минут.
  - *Наблюдаемая последовательность при тесте отказа* (отключение ноды от сети в 3-нодном кластере): нода переходит в `offline` через ~20 с; master (CRM) переизбирается на другой ноде через ~2 минуты; HA-ресурсы переносятся и запускаются ещё через ~1 минуту. Итого от потери сети до работающих сервисов на другой ноде проходит ~3 минуты.
- После fencing ресурсы неисправного узла перезапускаются на другом доступном узле в состоянии `recovery`. Общие принципы механизмов failover см. в **[Механизмы Failover и Heartbeat](../Concepts/High_Availability/ha_failover_mechanisms.md)**.

### HA-стек: роли и состояния ресурсов

HA-ресурс (VM или LXC) в любой момент находится в одном из состояний, определяемых CRM (официальная нумерация):
- **stopped / request_stop / stopping** — ресурс остановлен либо ожидает/выполняет запрос на остановку (CRM подтверждает через LRM);
- **started / starting** — ресурс работает либо ожидает подтверждения запуска от LRM; при падении сервиса LRM перезапускает его согласно Start Failure Policy;
- **fence** — узел с ресурсом вне quorate-партиции, ожидается его fencing; после успешного изоляции ресурс переходит в `recovery`;
- **recovery** — менеджер ищет новый узел (среди online/quorate с учётом affinity-правил) и запускает ресурс там;
- **freeze** — состояние заморожено (например, при перезагрузке ноды или рестарте LRM);
- **migrate** — выполняется живая миграция на другой узел;
- **ignored** — ресурс исключён из управления HA, но остаётся в конфигурации (полный ручной контроль);
- **error** — ошибка LRM, ресурс отключен от HA (выводится из error-состояния только вручную);
- **queued** — ресурс только добавлен, CRM ещё не обработал его;
- **disabled** — ресурс переведён в stopped и помечен как отключённый.

Запрошенные состояния задаются через `ha-manager set <sid> --state ...`; фактические отслеживаются в `ha-manager status`.

Состояния самого **pve-ha-lrm**: `wait for agent lock` (простой/ожидание блокировки), `active` (владеет блокировкой, ведёт ресурсы; параллельно работает до 4 воркеров, лимит — параметр `max_worker` в `datacenter.cfg`), `lost agent lock` (потеря блокировки/кворума).

Конфигурация хранится на кластерной ФС `/etc/pve/ha/`: `resources.cfg` (список HA-ресурсов), `groups.cfg` (устаревшие группы), `rules.cfg` (affinity-правила, PVE 9.0+) и `manager_status` (текущее состояние стека).

### Группы HA (HA Groups, устарели с PVE 9.0)

> **Статус:** HA-группы устарели (deprecated) с Proxmox VE 9.0 и мигрированы в **HA-правила node affinity** — семантически эквивалентный механизм. Группы по-прежнему работают и поддерживаются CLI (`ha-manager groupadd`), но для новых конфигураций используйте affinity-правила (следующий раздел).

Позволяют гибко управлять распределением ресурсов в кластере.
- **Nodes**: Список узлов, на которых разрешен запуск ресурсов группы, с приоритетами (`node1:2,node2:1` — чем **выше** число, тем выше приоритет узла).
- **Restricted**: Если включено, ресурс может работать *только* на узлах из списка. Если выключено — может запуститься на любом узле, если приоритетные недоступны.
- **NoFailback**: Предотвращает автоматический возврат ресурса на более приоритетный узел после его восстановления (полезно для тяжелых БД).

### HA-правила (Affinity Rules, PVE 9.0+)

Правила ограничивают размещение, восстановление и миграцию HA-ресурсов. Конфигурация — `/etc/pve/ha/rules.cfg`; в GUI: **Datacenter → HA → Affinity Rules**. Типы правил:

- **node-affinity** — привязка ресурсов к узлам: `affinity positive` (по умолчанию) — ресурс должен/предпочитает работать на указанных узлах; `affinity negative` — должен избегать их. Свойство `strict` (по умолчанию `0`): мягкое ограничение («предпочитает») либо жёсткое («только эти узлы, иначе — стоп»). Приоритеты узлов задаются как `node1:2,node2:1` — **чем выше число, тем выше приоритет**.
- **resource-affinity** — отношение между ресурсами: `affinity positive` — держаться на одном узле («вместе»), `affinity negative` — на разных узлах («раздельно»). В отличие от node-affinity, resource-правила **жёсткие (strict) по умолчанию** — планировщик ждёт, пока сможет выполнить ограничение.

```bash
# Ресурс vm:100 предпочитает node1 (мягко)
ha-manager rules add node-affinity ha-rule-vm100 --resources vm:100 --nodes node1

# То же, но жёстко: только node1, иначе ресурс будет остановлен
ha-manager rules set node-affinity ha-rule-vm100 --strict 1

# Каскад приоритетов: node1 предпочтительнее, затем node2/node3, затем node4
ha-manager rules add node-affinity priority-cascade \
  --resources vm:400,ct:500 --nodes "node1:2,node2:1,node3:1,node4"

# Избегать node3 (opt-out)
ha-manager rules add node-affinity ha-rule-negative \
  --affinity negative --resources ct:200,vm:300 --nodes node3

# Две реплики БД должны быть на разных узлах; веб+API — на одном
ha-manager rules add resource-affinity keep-separate --affinity negative --resources vm:200,ct:300
ha-manager rules add resource-affinity keep-together --affinity positive --resources vm:100,vm:200
```

Применять правила можно только к HA-ресурсам (добавленным в `resources.cfg`); для неуправляемых HA гостей команда завершится ошибкой `cannot use unmanaged resource(s)`. Ручная миграция, нарушающая node-affinity-правило, в PVE 9.2 блокируется (ресурс немедленно возвращается на разрешённый узел).

### Планирование ресурсов (CRS) и возможности PVE 9.x

- **Cluster Resource Scheduler (CRS)** — алгоритм выбора узла для старта/восстановления HA-ресурса. Режимы (`crs: ha=...` в `/etc/pve/datacenter.cfg`, либо Datacenter → Options → CRS):
  - `basic` (по умолчанию) — учитывается только количество сервисов на узле;
  - `static` — учитываются статические конфигурации CPU и памяти сервисов;
  - `dynamic` (PVE 9.2) — учитываются статические и динамические метрики использования CPU/памяти узлами и гостями.
- **Dynamic Load Balancer** (PVE 9.2) — в режиме `dynamic` CRS автоматически мигрирует HA-ресурсы для снижения дисбаланса кластера, соблюдая affinity-правила. Настройка чувствительности (`crs: ha-auto-rebalance=1` и параметры в `/etc/pve/datacenter.cfg` или GUI-панели HA): порог дисбаланса `ha-auto-rebalance-threshold` (по умолчанию 30%), минимальное улучшение для миграции `ha-auto-rebalance-margin` (10%), число раундов до срабатывания `ha-auto-rebalance-hold-duration` (3), метод оценки `ha-auto-rebalance-method` (`bruteforce` | `topsis`), автобалансировка при старте `ha-rebalance-on-start`.
- **HA arm/disarm** (PVE 9.2) — кластерное отключение HA-стека для обслуживания (например, переконфигурация сети/corosync) без риска fencing: `ha-manager crm-command disarm-ha freeze|ignore` / `ha-manager crm-command arm-ha`. Режим ресурсов при disarming: `freeze` — ресурсы замораживаются в текущем состоянии; `ignore` — снимаются с HA-учёта и управляются вручную. Состояния стека: `disarming` → `disarmed` (все watchdog освобождены, fencing/failover отключены) → после `arm-ha` — обычный режим; исходные состояния и размещение ресурсов восстанавливаются автоматически.

### Кластерная файловая система pmxcfs

**pmxcfs** (Proxmox Cluster File System) — распределенная файловая система на базе FUSE, обеспечивающая единое представление конфигурации `/etc/pve` на всех узлах кластера. Вся конфигурация кластера (хранилища, сети, HA, права доступа, резервные копии) хранится в pmxcfs и автоматически синхронизируется между нодами.

- **Ограничения размера**: pmxcfs хранит данные в SQLite-БД (`/var/lib/pve-cluster/config.db`) с копией в RAM. Лимиты: максимальный размер одного файла — **1 МиБ**, общий размер файловой системы — **128 МиБ** (этого хватает на конфигурации тысяч VM/CT). Крупные скрипты или бинарники в `/etc/pve/` хранить нельзя.
- **Режим только чтения**: при нехватке кворума (`Quorate: No`) pmxcfs монтируется в режиме `read-only`. Любые попытки записи (включая `pvecm expected`) завершаются ошибкой `EROFS`. В этот момент невозможно изменять конфигурацию через GUI или CLI, пока кворум не будет восстановлен.
- **Отсутствие симлинков**: в pmxcfs не поддерживаются символические ссылки внутри `/etc/pve/` — это следует учитывать при ручном переносе конфигурации.
- **Структура**: `/etc/pve/` содержит подкаталоги `nodes/` (конфигурация конкретных нод), `storage.cfg`, `datacenter.cfg`, `ha/`, `sdn/`, `priv/` (ключи и сертификаты), `subscription/`.
- **Staging-механизм**: GUI не пишет напрямую в конфигурацию. Изменения сначала записываются в временный файл (например, `/etc/network/interfaces.new`), а применяются только после явного подтверждения (Apply Configuration). Это защищает от потери доступа к узлу при ошибке сетевой конфигурации.

### Управление сертификатами кластера

Proxmox использует собственный CA (Certificate Authority) для каждого кластера. Сертификаты хранятся в `/etc/pve/` и автоматически синхронизируются через pmxcfs.

- **Структура сертификатов**:
  - CA-корень: `/etc/pve/pve-root-ca.pem` (ключ: `/etc/pve/priv/pve-root-ca.key`)
  - Узловой сертификат по умолчанию: `/etc/pve/nodes/<node>/pve-ssl.pem` + `pve-ssl.key` (подписан кластерным CA)
  - Custom/ACME-сертификат pveproxy: `/etc/pve/local/pveproxy-ssl.pem` + `pveproxy-ssl.key` (`/etc/pve/local` — симлинк на узел); управление — `pvenode cert` / `pvenode acme`, не прямой `cp`
  - Секреты узлов: `/etc/pve/.members/<node>.secret`
- **Ротация**: При добавлении новой ноды в кластер (`pvecm add`) сертификат CA автоматически копируется на новый узел, и для него генерируется новый сертификат. Ротация узловых сертификатов — `pvecm updatecerts` (в PVE 9.x).
- **Срок действия**: Кластерный CA генерируется на **10 лет**; узловые `pve-ssl.pem` — максимум на **2 года**. Истечение узлового сертификата или CA приводит к TLS-ошибкам веб-интерфейса/API — требуется регенерация (`pvecm updatecerts` / регенерация CA). Подробности и мониторинг — в [ACME и SSL-сертификаты](./proxmox_acme_ssl.md).
- **Восстановление после потери секрета**: Если узел потерял файл секрета (например, при переустановке ОС без сохранения `/etc/pve`), его можно восстановить на оставшихся узлах кластера командой `pvecm delnode <node>` (узел должен быть выключен), а затем повторно добавить узел через `pvecm add`.

### Миграция и репликация

- **Live Migration (Живая миграция)**: Перенос запущенной ВМ без остановки. Требует наличия Shared Storage (NFS, SMB, Ceph) или использования локальных дисков с одновременным копированием данных по сети (Storage Migration).
- **Storage Migration**: При использовании локальных дисков данные переносятся вместе с памятью (онлайн) или отдельно (офлайн); используется TCP-диапазон 60000–60050.
- **Миграция LXC-контейнеров**: В отличие от VM, контейнеры мигрируют в режиме restart (GUI: диалог Migrate с галочкой **Restart Mode**; CLI: `pct migrate <VMID> <node> --restart 1 --timeout 180`): контейнер останавливается (таймаут корректного shutdown по умолчанию 180 с), переносится и запускается на целевой ноде. Флаг `--online` существует, но runtime-состояние контейнера (процессы, файловые дескрипторы, сокеты) не является образом памяти, как у VM, — checkpoint/restore ненадёжен для нетривиальных нагрузок. Практическое правило: планируйте миграцию контейнера как «остановка + запуск» и закладывайте это время в окно обслуживания. Практический сценарий миграции VM/CT с shared storage — в разделе **[Подключение NFS-хранилища TrueNAS к кластеру](./proxmox_storage.md#подключение-nfs-хранилища-truenas-к-кластеру)**.
- **ZFS Storage Replication**: Асинхронное копирование снимков (snapshots) дисков ВМ между локальными ZFS-пулами нод по расписанию (от 1 минуты).
  - *Ограничение*: При сбое ноды данные на новом хосте будут в состоянии последнего успешного сеанса репликации (возможна потеря данных за последнюю минуту). Для HA с репликацией применяется режим offline migration (stop + copy + start), так как ZFS-репликация не обеспечивает согласованности в реальном времени. Для нагрузок с БД это означает необходимость ставить гостя на паузу перед копированием; при десятках VM репликация создаёт заметную нагрузку на сеть и диски, тогда как shared storage лишён этих ограничений.

## Практические сценарии

### Предварительные требования к развертыванию кластера

Перед созданием кластера необходимо обеспечить выполнение следующих условий:

1.  **Версия PVE**: Все узлы должны иметь одинаковую мажорную версию Proxmox VE (актуальная ветка 9.x, последний релиз 9.2). PVE 8.x достиг конца поддержки (EOL) 31 августа 2026 — новые кластеры на 8.x разворачивать нельзя, существующие необходимо обновлять. Смешивание версий допустимо только в процессе контролируемого апгрейда.
2.  **Сеть**:
    - Выделенная сеть Corosync с задержкой менее 2 мс и стабильным MTU (рекомендуется 9000 для jumbo frames, если поддерживается всеми коммутаторами).
    - Открытые порты: UDP 5405–5412 (Corosync/knet), TCP 5403 (QDevice/QNetd), TCP 60000–60050 (миграция), TCP 8006 (веб-интерфейс), TCP 22 (SSH).
    - Корректное разрешение имен узлов по DNS или через `/etc/hosts`.
3.  **Синхронизация времени**: На всех узлах должен быть настроен `chrony` или `systemd-timesyncd`. Существенное расхождение времени (сотни миллисекунд и более) между узлами приводит к некорректной работе кворума и проблемам с сертификатами.
4.  **Диски**: Локальное хранилище на узлах не обязательно должно быть одинаковым, но для корректной работы HA без Shared Storage рекомендуется использовать ZFS с включенным Storage Replication.
5.  **Доступ**: root-доступ на всех узлах (SSH-ключи или пароль). Для GUI-создания кластера требуется доступ к веб-интерфейсу на каждом узле.

### Создание кластера через CLI

Создание кластера на первой ноде:

```bash

# → Writing corosync config to /etc/pve/corosync.conf
```

Добавление новой ноды в существующий кластер (выполняется на новой ноде):

# → Stopping pve-cluster and corosync...
# → Starting corosync...

### Создание кластера через веб-интерфейс

GUI предоставляет альтернативный способ создания и присоединения к кластеру, удобный для операторов, не работающих напрямую с CLI.

**Создание нового кластера:**

1. Войти на первый узел через веб-интерфейс (порт 8006).
2. Перейти в `Datacenter` → `Cluster` → кнопка `Create Cluster`.
3. Указать имя кластера, выбрать сетевой интерфейс для Corosync (рекомендуется выделенный интерфейс).
4. Нажать `Create`. PVE автоматически сгенерирует конфигурацию Corosync и SSH-ключи.

**Присоединение узла к существующему кластеру:**

1. На **существующем** узле: `Datacenter` → `Cluster` → кнопка `Join Information` → `Copy Information` (в буфер обмена копируется строка с конфигурацией кластера; есть также QR-код).
2. На **новом** узле: `Datacenter` → `Cluster` → кнопка `Join Cluster`.
3. Вставить скопированную информацию (Join Information) и подтвердить отпечаток сертификата; указать пароль root узла-источника (или настроенный SSH-доступ).
4. Нажать `Join`. PVE автоматически скопирует конфигурацию и сертификаты, добавит узел в corosync и перезапустит кластерные сервисы.

**Валидация через GUI:**

После создания или присоединения узла проверьте:
- `Datacenter` → `Cluster` → вкладка `Nodes`: все узлы должны иметь статус `online`.
- `Datacenter` → `Cluster` → `Quorum`: статус `Quorate: Yes`.
- `Datacenter` → `HA`: раздел доступен только при quorate-статусе.

### Проверка работоспособности после создания кластера

После создания кластера или добавления новой ноды выполните следующие проверки:

```bash
# 1. Статус кластера и кворум
pvecm status
# → Quorate: Yes
# → Expected votes совпадают с количеством узлов

# 2. Состав нод
pvecm nodes
# → Все ноды в состоянии online (X)

# 3. Статус коросинка
corosync-cfgtool -s
# → Все ring status: active with no faults

# 4. Проверка pmxcfs
df -h /etc/pve
# → proxmox-fuse on /etc/pve type fuse.proxmox (rw,nosuid,nodev,relatime,...)

# 5. Список сервисов на всех нодах
for node in node1 node2 node3; do
  echo "=== $node ==="
  ssh $node "systemctl status pve-cluster corosync pvedaemon pveproxy --no-pager"
done
```

### Настройка QDevice (для 2-х нод)

1. На внешнем сервере (Debian/Ubuntu, не член кластера):

   ```bash
   apt update && apt install corosync-qnetd
   ```

2. На каждой ноде Proxmox:

   ```bash
   apt update && apt install corosync-qdevice
   ```

3. Инициализация с любой ноды кластера (SSH-ключ кластера автоматически копируется на QNetd; для root на QNetd требуется ключевой доступ или временное разрешение входа по паролю):

   ```bash
   pvecm qdevice setup <IP_QNETD_SERVER>
   # → Done
   ```

4. Проверка:

   ```bash
   pvecm status
   # → Votequorum information
   # → Expected votes:   3
   # → Total votes:      3
   # → Quorum:           2
   # → Flags:            Quorate Qdevice

   pvecm qdevice status
   # → Qdevice information
   # → Status:           Qdevice started
   # → Algorithm:        ffsplit
   # → Tie-breaker:      lowest
   # → Node IDs:         1, 2
   ```

Диагностика соединения: `corosync-qdevice-tool -s` (на ноде кластера) и `corosync-qnetd-tool -s` (на хосте QNetd). Если в `pvecm status` флаг QDevice показывает `NA` (Not Alive), проверьте доступность порта TCP 5403.

Удаление QDevice: `pvecm qdevice remove`. Важно: перед добавлением или удалением узлов кластера с настроенным QDevice сначала удалите QDevice, затем измените состав кластера.

### Исключение ноды из кластера (подробно)

Удаление ноды из кластера — операция, требующая аккуратности. Рекомендуемый способ после удаления — переустановка узла; ниже — процедура вывода без переустановки (Separate A Node Without Reinstalling, официальная документация).

**Подготовка (критично):**
1. **Общие хранилища.** Узел, выходящий из кластера, должен быть отвязан от общих хранилищ: PVE не позволяет двум кластерам работать с одним и тем же хранилищем (ломается блокировка дисков, возможны конфликты VMID). Создайте для уходящего нода отдельное хранилище (экспорт NFS, отдельный Ceph-пул) и перенесите на него данные/VM.
2. **QDevice.** Если настроен QDevice — сначала удалите его (`pvecm qdevice remove`), затем меняйте состав кластера.
3. Переведите ноду в режим обслуживания (`ha-manager crm-command node-maintenance enable <node>`) и убедитесь, что все HA-ресурсы с этой ноды мигрировали на другие узлы (`ha-manager status --verbose`). Ресурсы с локальными дисками переносите осознанно (storage migration / ZFS replication).
4. Удалите ноду из HA-правил (affinity) и групп, ссылающихся на него.

**Вывод узла из кластера (на самой ноде):**

```bash
systemctl stop pve-cluster
systemctl stop corosync
pmxcfs -l                 # запуск pmxcfs в локальном режиме (без кластера)
rm /etc/pve/corosync.conf
rm -r /etc/corosync/*     # остатки конфигурации corosync
killall pmxcfs
systemctl start pve-cluster
# → узел теперь работает автономно (local mode)
```

**Удаление из оставшегося кластера (на любой оставшейся ноде):**

```bash
pvecm delnode node3
# → removing node3 from the cluster...
# Ошибка «could not kill node (error = cs_err_not_exist)» при офлайн-ноде — безобидна:
# это неудачная попытка corosync «убить» уже отсутствующий узел, удаление прошло.
# Если оставшийся узел потерял кворум: pvecm expected 1, затем повторить pvecm delnode.
```

**Пост-очистка:**

1. На выведенном из кластера узле удалите остатки чужой кластерной конфигурации (иначе повторное добавление в другой кластер будет проблематичным):
   ```bash
   rm -r /var/lib/corosync/*
   ```
2. На оставшихся нодах уберите конфигурацию удалённого нода: удалите каталог `/etc/pve/nodes/<имя_удалённого>` (убедившись в правильности имени).
3. Если узел с тем же IP/hostname будет добавляться заново и SSH выдаёт ошибку по ключам — выполните `pvecm updatecerts` на передобавленном узле (обновит fingerprint кластерно). Устаревший симлинк known_hosts снимается через `pvecm updatecerts --unmerge-known-hosts`.
4. Локальные диски VM, оставшиеся на узле, при повторном добавлении видны как `unused` и прикрепляются вручную.

### Резервное копирование и восстановление конфигурации кластера

Конфигурация кластера (`/etc/pve/`) критична для восстановления после сбоя. Хотя pmxcfs синхронизирует данные между нодами, это не заменяет резервное копирование: при потере всех нод или повреждении БД восстановить кластер можно только из резервной копии.

**Что копировать:**
- **`/var/lib/pve-cluster/config.db`** — SQLite-база pmxcfs, единственный источник данных конфигурации. Это основной объект резервного копирования.
- **Снимок `/etc/pve/`** (tar при работающем pve-cluster) — человекочитаемая копия файлового вида конфигурации (включая `/etc/pve/corosync.conf`, `priv/` с ключами) для справки; восстановление идёт через config.db, не через распаковку tar в `/etc/pve`.

**Методы резервного копирования:**

1. **Ручное копирование** (быстрый способ для небольшого кластера):
   ```bash
   cp -a /var/lib/pve-cluster/config.db /var/backups/config.db-$(date +%Y%m%d)
   tar czf /var/backups/pve-config-$(date +%Y%m%d).tar.gz /etc/pve/
   # Скопируйте архивы на внешний носитель или в отдельное хранилище
   ```

2. **Скрипт автоматизации через cron** (на каждой ноде):
   ```bash
   cat > /etc/cron.daily/pve-backup << 'EOF'
   #!/bin/bash
   cp -a /var/lib/pve-cluster/config.db /var/backups/config.db-$(date +%Y%m%d)
   tar czf /var/backups/pve-config-$(date +%Y%m%d).tar.gz /etc/pve/
   find /var/backups/ \( -name "pve-config-*.tar.gz" -o -name "config.db-*" \) -mtime +30 -delete
   EOF
   chmod +x /etc/cron.daily/pve-backup
   ```

3. **Восстановление на новом/заменяющем узле** (процедура из документации pmxcfs — перенос БД конфигурации):
   ```bash
   # 1. Установите PVE той же версии на новом узле; убедитесь, что кластерные сервисы не работают
   systemctl stop pve-cluster

   # 2. Замените БД конфигурации из резервной копии
   cp -a /var/backups/config.db-20261001 /var/lib/pve-cluster/config.db
   chmod 600 /var/lib/pve-cluster/config.db

   # 3. Приведите идентичность узла к оригиналу
   #    /etc/hostname и /etc/hosts должны соответствовать восстанавливаемому узлу

   # 4. Запустите сервис и проверьте
   systemctl start pve-cluster
   pvecm status
   ```

**Важно:** hostname узла должен совпадать с тем, что было в оригинальной конфигурации, иначе `pve-cluster` и `pmxcfs` работать корректно не будут. Не «распаковывайте» tar-снимок `/etc/pve` поверх смонтированной pmxcfs — данные читаются из config.db, а не из обычных файлов каталога. После восстановления проверьте не только кластер, но и доступность данных VM/CT (диски и образы НЕ входят в config.db — их локация перечислена в конфигурациях гостей и хранилищ).

### Включение HA для ресурса

1. Добавление VM в управление HA (через `ha-manager`; параметры `--state`, `--group`, `--max_restart`, `--max_relocate` — дефолты последних двух равны 1):

   ```bash
   ha-manager add vm:101 --state started --group cluster1 --max_restart 2 --max_relocate 3
   # → update VM 101: -ha state=started,group=cluster1,max_restart=2,max_relocate=3
   ```

   В PVE 9 предпочтительнее задавать размещение affinity-правилами (см. «HA-правила»), а не устаревшими группами; `--group` при этом остаётся рабочим параметром.

2. Просмотр конфигурации и статуса:

   ```bash
   ha-manager config
   # → vm:101
   # →         state started
   # →         group cluster1

   ha-manager status
   # → quorum OK
   # → master node1 (active)
   # → lrm node1 (active)
   # → service vm:101 (node1, started)
   ```

3. Управление запрошенным состоянием:

   ```bash
   ha-manager set vm:101 --state stopped
   ha-manager set vm:101 --state started
   ```

4. Миграция ресурса:
   - Онлайн-миграция (без остановки): `ha-manager migrate vm:101 node2` (alias команды `ha-manager crm-command migrate`).
   - Перенос с остановкой и перезапуском: `ha-manager relocate vm:101 node2`.
   - Остановка с таймаутом (0 — принудительная): `ha-manager crm-command stop vm:101 60`.

5. Исключение ресурса из HA (не останавливает и не запускает ресурс):

   ```bash
   ha-manager remove vm:101
   ```

### Управление группами HA и правилами через CLI

Группы (устарели, работают):
```bash
# Создание группы с приоритетами узлов (чем выше число, тем выше приоритет)
ha-manager groupadd cluster1 --nodes "node1:2,node2:1,node3:1" --restricted --nofailback
# → update ha groups: cluster1

# Изменение группы
ha-manager groupupdate cluster1 --nodes "node1:2,node2:1" --nofailback

# Удаление группы
ha-manager groupdelete cluster1
```

Правила (PVE 9.0+, предпочтительный механизм) — см. примеры в разделе «HA-правила (Affinity Rules)»; справочный синопсис: `ha-manager rules add|set node-affinity|resource-affinity <name> ...` с опциями `--resources`, `--nodes`, `--affinity positive|negative`, `--strict 0|1`.

### Режим обслуживания (Maintenance Mode)

Появился в PVE 8.x. Позволяет безопасно выводить узел из работы без срабатывания HA: все ресурсы под управлением HA мигрируют на другие узлы, а при отключении режима автоматически возвращаются обратно. Режим не снимается автоматически при перезагрузке ноды. Обычные (не HA) VM в этом случае переносятся вручную.

Включение и отключение:

```bash
ha-manager crm-command node-maintenance enable node1
# → Requesting maintenance mode for node 'node1'
ha-manager crm-command node-maintenance disable node1
```

Поведение узла при **shutdown/reboot** настраивается отдельно — политика завершения работы (Shutdown Policy): Datacenter → Options → HA Settings, либо в `/etc/pve/datacenter.cfg`:

```ini
ha: shutdown_policy=migrate
```

Режимы политики (официальная нумерация, по умолчанию `conditional`):
- **conditional** (по умолчанию): поведение зависит от типа завершения — при *reboot* ресурсы «замораживаются» (freeze) на ноде, при *poweroff* остаются как есть и восстанавливаются на других узлах примерно через 2 минуты, если узел не вернулся;
- **migrate**: Все работающие ресурсы живьем мигрируют на другие узлы перед остановкой ноды;
- **failover**: ресурсы не помечаются frozen и восстанавливаются на других узлах, если остановленная нода не поднялась быстро (порядка 1 минуты) — быстрее failover при большом количестве нод и ВМ;
- **freeze**: ресурсы останавливаются и «замораживаются» без переноса (HA-менеджер их не восстанавливает).

### Проактивный мониторинг кластера (SRE-перспектива)

Для обеспечения SLA и оперативного реагирования на сбои настройте мониторинг следующих метрик и событий (реализация textfile-скриптов и правил алертинга — в **[Мониторинг Proxmox через Prometheus и Grafana](./proxmox_monitoring.md)**):

**Ключевые метрики для сбора (Prometheus-стеки):**
- **Кворум кластера**: `pvecm status` либо `corosync-quorumtool -s` (для скриптов удобен машиночитаемый вывод `corosync-quorumtool -p`) — собирается через `node_exporter` (textfile collector) или кастомный скрипт.
- **Состояние нод**: `pvecm nodes` — отслеживайте переходы в состояние offline/unknown.
- **Статус Corosync**: анализ логов `journalctl -u corosync`, статус линков `corosync-cfgtool -s`.
- **Статус HA-сервисов**: `ha-manager status --verbose` — количество сервисов в состояниях `started`, `error`, `fence`/`recovery`.
- **Ресурсы узла**: CPU, память, диск (через `node_exporter`), сетевые линки Corosync (throughput, ошибки).
- **Watchdog**: сервисы `pve-ha-lrm` и `watchdog-mux` активны и не выдают ошибок; `/dev/watchdog` удерживается watchdog-mux (попытка открыть устройство завершается ошибкой «Device or resource busy» — это норма при работающем HA-стеке).

**Рекомендуемые алерты:**
1. `Quorate: No` в `pvecm status` — критический алерт, требуется немедленная реакция.
2. Нода перешла в `offline` или `unknown` — проверить сеть и доступность.
3. `pve-ha-crm` или `pve-ha-lrm` не запущены на любой ноде.
4. HA-ресурс перешел в состояние `error` или ожидает fencing (`fence`/`recovery` дольше нормы).
5. Watchdog не сбрасывается более 30 секунд (`systemctl status pve-ha-lrm`).
6. Размер pmxcfs (`/etc/pve`, лимит 128 МиБ) приближается к пределу.
7. Истечение сертификатов PVE (предупреждение за 30 дней).

**Интеграция с внешними системами:**
- **Prometheus + Alertmanager**: Сбор метрик через `node_exporter` и кастомные скрипты (textfile collector) — см. **[Мониторинг Proxmox](./proxmox_monitoring.md)**.
- **Grafana**: Дашборды с топологией кластера, статусом нод и HA-ресурсов.
- **NetBox**: Хранение инвентарных данных (IP-адреса, роли узлов, местоположение) — см. **[NetBox — Обзор](../Networking/NetBox/overview.md)**.
- **PagerDuty/OpsGenie**: Маршрутизация алертов на инженеров SRE.

## Диагностика и устранение неисправностей

### Проблемы с кворумом

Если `pvecm status` показывает `Quorate: No`, управление кластером (включая запись в `/etc/pve`) блокируется.
- **Причина**: Потеря сетевой связности между нодами или падение сервиса `corosync`.
- **Диагностика**: `corosync-quorumtool -s` (или `pvecm status`) — кворум, голоса, состав; `corosync-quorumtool -p` — машиночитаемый вывод для скриптов (код возврата 0 — quorate, 2 — not quorate).
- **Временное решение** (для восстановления доступа до устранения причины):
  ```bash
  pvecm expected 1
  ```
- **Проверка QDevice**: убедитесь, что QDevice alive (`pvecm qdevice status`, `corosync-qdevice-tool -s`) и доступен порт TCP 5403.
- **Исключение неисправной ноды**: после восстановления кворума offline-ноду можно удалить из состава кластера командой `pvecm delnode <node>`.

### Ошибки Corosync

Проверка конфигурации:
```bash
corosync-cfgtool -s
# → Printing ring status.
# → Local node ID 1
# → RING ID 0
# →     id  = 10.0.0.1
# →     status  = ring 0 active with no faults
```

Если статус `faulty`, проверьте:
- настройки MTU (Corosync чувствителен к фрагментации пакетов; используйте одинаковый MTU в подсети Corosync);
- настройки Firewall — UDP порты 5405–5412 (для knet) и TCP 5403 для QNetd;
- рассинхронизацию времени между нодами (NTP);
- целостность линков knet при настроенном multi-link;
- разрешение имён: ошибка в логе `nodelist or quorum.expected_votes must be configured!` обычно означает, что hostname из `ringX_addr` в corosync.conf не резолвится на ноде — проверьте DNS/`/etc/hosts`.

После ручного вмешательства в `/etc/pve/corosync.conf` перезапустите corosync на всех нодах (`systemctl restart corosync`) и проверьте, что все линки снова `active with no faults`.

### Split-Brain и восстановление

При разделении кластера на две партиции:
1. Определите сторону, сохранившую связь с QDevice (она останется quorate и получит голос).
2. На стороне без кворума **не выполняйте** запись в конфигурацию — pmxcfs перейдет в режим только чтения.
3. Восстановите сетевую связность; при необходимости временно поднимите кворум командой `pvecm expected <n>`.
4. После восстановления проверьте, что fencing отработал и ресурсы вернулись на свои узлы (`ha-manager status`).

## Лучшие практики

1. **Два независимых сетевых линка для Corosync**: Используйте knet с двумя интерфейсами в разных подсетях (разные коммутаторы/разные uplinks). Одиночный линк является единой точкой отказа для всего кластера. Настройте приоритеты линков в `/etc/pve/corosync.conf` (knet_link_priority).
2. **QDevice для четных кластеров и 2-нодных конфигураций**: В кластере из 2 узлов без QDevice потеря одного нода лишает второй кворум. Для production сред с 2 узлами QDevice обязателен. Для четного числа узлов (4, 6) QDevice предотвращает deadlock при сетевом разделении.
3. **Синхронизация времени**: Настройте `chrony` с несколькими серверами времени. Существенное расхождение времени между нодами (сотни миллисекунд и более) приводит к проблемам с кворумом, корректностью сертификатов и логов. Избегайте зависимости от единственного NTP-сервера.
4. **Watchdog**: В production используйте аппаратный watchdog (IPMI/BMC, iTCO_wdt). Программный watchdog (`softdog`) не сработает при kernel panic или зависании ядра. Проверьте доступность IPMI на всех узлах до создания кластера.
5. **Не используйте геораспределенный кластер**: Даже при RTT 1.5 мс Corosync/knet деградирует. Для меж-датцентрового DR используйте независимые кластеры + асинхронную репликацию хранилищ.
6. **Резервное копирование конфигурации**: Регулярно копируйте `/etc/pve/` на внешнее хранилище. При восстановлении ноды из бэкапа убедитесь, что hostname совпадает с оригинальным.
7. **Апгрейд кластера**: Обновляйте кластер по очереди, начиная с Ceph (если используется), затем узлы PVE. Не держите смешанные версии дольше необходимого окна обслуживания. Процедура описана в **[Обновление систем Proxmox](./proxmox_updates.md)**.
8. **Мониторинг кворума и Corosync**: Настройте алерты на:
   - `Quorate: No` в `pvecm status`
   - Ошибки Corosync в `journalctl -u corosync`
   - Статус QDevice (`pvecm qdevice status`)
   - Состояние watchdog (`systemctl status watchdog-mux pve-ha-lrm`; `/dev/watchdog` должен быть занят watchdog-mux)
9. **Тестирование failover**: Планово тестируйте перезагрузку узлов и отказ сети Corosync. Убедитесь, что:
   - HA-ресурсы перезапускаются на других узлах в рамках `max_restart` и `max_relocate`.
   - Fencing срабатывает корректно (аппаратная перезагрузка через IPMI).
   - После восстановления ресурсы возвращаются на приоритетные узлы (если не включен NoFailback).
10. **Изменение состава кластера**: При добавлении/удалении узлов с настроенным QDevice сначала удалите QDevice, выполните операцию, затем настройте QDevice заново.

## Граничные случаи и ограничения

- **Кластер из 2 узлов без QDevice**: При падении одного узла второй теряет кворум (`Expected votes: 2`, `Quorum: 2`, `Total votes: 1`). Решение: добавить QDevice или увеличить количество узлов до 3.
- **Рассинхронизация времени**: Corosync может неверно детектировать сбои и ошибки аутентификации, логи становятся несогласованными по времени. Всегда настраивайте `chrony` с минимальным offset.
- **Потеря связи с QDevice при разделении кластера**: Если QDevice недоступен (сеть или сам сервер упал), кластер из 2 узлов потеряет кворум при любом разделении. Убедитесь, что хост QNetd независим по питанию и сети от обоих узлов.
- **Локальные диски и отказ узла**: Если VM использует локальный диск (не Shared Storage) и узел отказывает, VM не может быть запущена на другом узле без Storage Migration или ZFS Replication. HA для таких VM настроить можно, но при сбое данных можно потерять.
- **Переполнение LVM-Thin**: При 100% заполнении пула все VM на этом хранилище получат ошибки I/O, что приведет к падению файловых систем и повреждению данных. Настройте мониторинг свободного места и алерты на `> 80%`.
- **Self-Fencing при нехватке памяти**: Если узел не может сбросить watchdog из-за нехватки памяти (OOM), он будет принудительно перезагружен. Убедитесь, что на хостах достаточно swap и память не перераспределяется полностью VM.
- **Миграция с разными версиями PVE**: Live Migration между узлами с разными минорными версиями PVE возможна, но не рекомендуется для production. При миграции VM с узла PVE 8 на PVE 9 убедитесь, что CPU-флаги совместимы.
- **Смешанный режим Ceph + локальное хранилище**: При отказе узла данные на его локальных дисках недоступны. HA-ресурсы на локальных дисках не перезапустятся без репликации. Для критичных workloads используйте Ceph RBD.
- **Изменение hostname узла**: После создания кластера hostname ноды не должен меняться. При изменении hostname pmxcfs перестает корректно работать, и узел нужно удалять из кластера и заново добавлять.
- **Большое количество нод**: Корректного кворума требует минимум 3 узла (или 2 + QDevice). Жёсткого официального лимита на число узлов PVE не публикует, но с ростом состава увеличивается нагрузка на corosync (обмен сообщениями на каждой ноде) и на pmxcfs (транзакции конфигурации); на практике кластеры в несколько десятков узлов разбивают на несколько независимых кластеров с Ceph-репликацией между ними.

## Дополнительная информация

### Предупреждение: геораспределенный кластер (Geo-Cluster)

Создание единого кластера Proxmox между двумя удаленными дата-центрами — **антипаттерн**. Даже при низкой задержке (от ~1.5 мс) кластер начинает деградировать:
- Corosync/knet не предназначен для WAN-сетей с задержками выше 1–2 мс;
- при росте латентности кластер перестает устойчиво держать кворум и начинаются случайные перезагрузки нод (self-fencing);
- разделение кластера (split-brain) в WAN происходит значительно чаще, чем в LAN.

**Рекомендуемое решение:**
- Разделите инфраструктуру на **независимые кластеры** по одному на дата-центр.
- Для DR используйте асинхронную репликацию хранилищ (ZFS send/recv, Ceph replication) и миграцию ВМ вручную при плановых работах.
- Храните конфигурацию каждого кластера в **отдельном репозитории** Terraform; объединение в один репозиторий усложняет управление и увеличивает риск пересечения изменений.

### Изменение состава кластера: добавление и удаление нод

**Добавление** — см. «Создание кластера через CLI» (`pvecm add`) и «Создание кластера через веб-интерфейс». При добавлении узла в кластер с выделенной cluster-сетью используйте `pvecm add <IP> --link0 <LOCAL_IP>` (см. «Резервирование Corosync»).

**Правила изменения состава:**
- При настроенном QDevice сначала удалите его (`pvecm qdevice remove`), выполните операцию с составом, затем настройте QDevice заново.
- Нода, удаляемая из кластера, не должна владеть общими хранилищами и должна быть отвязана от HA-правил/групп — подробная процедура в разделе «Исключение ноды из кластера (подробно)».
- После передобавления узла с тем же IP/hostname при SSH-ошибках выполните `pvecm updatecerts` (обновление fingerprint кластерно).
- Состав нод и их голоса проверяются через `pvecm status` / `pvecm nodes`; при `delnode` офлайн-ноды ошибка `could not kill node (error = cs_err_not_exist)` безобидна.

### QDevice в production: рекомендации

Для кластеров с четным количеством узлов QDevice критически важен:

| Сценарий | Тип QDevice | Рекомендация |
| :--- | :--- | :--- |
| **2 ноды** | corosync-qnetd | Обязателен; без него при падении одной ноды второй теряет кворум |
| **4 ноды** | corosync-qnetd | Рекомендуется; предотвращает потерю кворума при 2+ отказах (2 из 4 — не большинство) |
| **6+ нод** | corosync-qnetd | Опционально; кворум без QDevice достаточен при отказе меньшей части нод |

```bash
# Мониторинг QDevice
pvecm qdevice status
corosync-qdevice-tool -s

# Тестирование failover QDevice
# 1. Остановите corosync-qdevice на одной ноде
systemctl stop corosync-qdevice
# 2. Проверьте кворум на остальных нодах
pvecm status
# 3. Запустите заново
systemctl start corosync-qdevice
```

### Гибридный кластер из разного железа

Proxmox не требует одинакового оборудования для кластера. Вы можете объединить серверы с ECC-памятью, мини-ПК (Intel NUC), старые рабочие станции или иной `x86_64` совместимый хостинг.

Однако есть нюансы:

1.  **CPU compatibility и миграция**: если процессоры сильно отличаются (`Intel` ↔ `AMD`), потребуется настройка `CPU Type = host` или миграция не будет возможна из-за различий в набор инструкций. В GUI/CLI можно задать тип CPU для ВМ: `host`, `kvm64`, `core2duo` и т. д. Для гетерогенных кластеров используйте наиболее совместимый тип CPU.
2.  **Производительность**: слабые ноды не смогут выдержать ту же нагрузку, что и серверные. При миграции нескольких ВМ с мощной ноды на маломощную последняя может стать неработоспособной из-за перегрузки. Используйте CRS режим `static` или `dynamic` для учёта ресурсных характеристик при планировании.
3.  **Сеть и диски**: для оптимальной работы обеспечьте единый быстрый канал (`1/10/25 Гбит`) и одинаковые хранилища или Shared Storage (NFS, Ceph). Локальные диски на сильно различающихся нодах усложняют HA и миграцию.

Такой гибридный кластер часто применяют для домашнего лабораторного окружения, где экономия важнее единообразия.
