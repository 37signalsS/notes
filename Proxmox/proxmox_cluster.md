# Кластеризация и High Availability в Proxmox

## Определения

**Proxmox Cluster** — это объединение нескольких независимых серверов Proxmox VE (нод) в единую систему с централизованным управлением.

**High Availability (HA)** — функция обеспечения высокой доступности. При выходе из строя одной из нод кластера виртуальные машины и контейнеры автоматически перезапускаются на рабочих нодах.

## Основные концепции

### Требования и правила создания кластера
- Все узлы должны иметь одинаковую мажорную версию Proxmox и синхронизированное время (NTP).
- Рекомендуется использовать для миграции и коммуникации (Corosync) отдельную сеть/сетевой интерфейс, изолированный от трафика ВМ.
- В кластере должно быть нечетное количество голосов (кворум) для корректного принятия решений. Минимальное количество серверов для работы HA — 3 ноды.

### QDevice (Quorum Device)
Для построения кластера из двух нод (или четного числа) необходимо использовать **QDevice**. В качестве QDevice может выступать любое внешнее слабое устройство (например, виртуальная машина в другом облаке или Raspberry Pi), на котором не запускаются полезные нагрузки, но которое дает дополнительный голос (vote) для обеспечения кворума.
- Использует сервис `corosync-qnetd` на стороннем устройстве и `corosync-qdevice` на нодах кластера.
- Позволяет избежать состояния "Split-Brain" в кластере из двух узлов.

### Миграция и репликация
- **Online/Live Migration**: Перенос запущенной ВМ на другую ноду без простоя. Требует одинаковых семейств процессоров (Intel/AMD) или использования совместимых режимов эмуляции CPU.
- **Storage Replication**: Асинхронное копирование виртуальных дисков ВМ и LXC между локальными ZFS-хранилищами нод. Настраивается по расписанию (от 1 минуты).
- Репликация является компромиссным вариантом для HA. В случае падения ноды данные ВМ "откатятся" к состоянию последней успешной репликации. Для систем реального времени рекомендуется использовать централизованные сетевые хранилища (Shared Storage) или Ceph.

## Практические сценарии

### Создание кластера
1. На первой ноде создается кластер (`Datacenter -> Cluster -> Create Cluster`), выбирается сеть для Corosync.
2. Генерируется `Join Information`.
3. На остальных нодах используется кнопка `Join Cluster` с вводом скопированной информации и root-пароля первой ноды.

### Подключение QDevice (для 2-х нод)
1. На стороннем сервере (не члене кластера) установить: `apt install corosync-qnetd`.
2. На каждой ноде кластера установить: `apt install corosync-qdevice`.
3. С одной из нод кластера выполнить инициализацию: `pvecm qdevice setup <IP_QNETD_SERVER>`.

### Настройка High Availability (HA)
После того как хранилища ВМ стали доступны всем нодам (через репликацию ZFS, Shared Storage или Ceph):
1. Перейти в `Datacenter -> HA -> Resources`.
2. Добавить необходимую ВМ или контейнер, указать целевое состояние (Started), а также лимиты попыток рестарта и миграции.
3. При отказе ноды, через заданный тайм-аут (около 5 минут по умолчанию), система автоматически перенесет и запустит ВМ на другой доступной ноде.
