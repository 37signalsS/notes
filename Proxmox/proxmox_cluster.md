# Кластеризация и High Availability в Proxmox

## Определения

**Proxmox Cluster** — это объединение нескольких независимых серверов Proxmox Virtual Environment (PVE) в единую систему с централизованным управлением через веб-интерфейс или Command Line Interface (CLI).

**High Availability (HA, Высокая доступность)** — механизм, обеспечивающий автоматический перезапуск виртуальных машин (VM) или контейнеров (LXC — Linux Containers) на другой работающей ноде в случае аппаратного или программного сбоя текущего хоста.

**Corosync** — основной сервис обмена сообщениями и контроля состояния (Cluster Engine), обеспечивающий работу кластера и отслеживание доступности нод.

## Основные концепции

### Требования и правила создания кластера

- **Версионность**: Все узлы должны иметь одинаковую мажорную версию Proxmox (например, все на 8.x).
- **Синхронизация времени**: Обязательное использование NTP (Network Time Protocol) для предотвращения рассинхронизации логов и работы кворума.
- **Сеть Corosync**: Рекомендуется выделять отдельную физическую или логическую (VLAN) сеть для трафика Corosync с минимальными задержками. Высокие задержки в этой сети приводят к потере кворума и перезагрузке нод.
- **Кворум (Quorum)**: Минимальное количество голосов, необходимое для принятия решений в кластере. Кластер считается работоспособным (quorate), если доступно более 50% голосов.

### QDevice (Quorum Device)

Для отказоустойчивых конфигураций из двух нод (или четного числа узлов) используется **QDevice**. Это внешняя служба, которая не является полноценной нодой кластера, но дает дополнительный голос для обеспечения кворума.

- **Split-Brain**: Состояние, когда две части кластера теряют связь друг с другом и обе пытаются управлять одними и теми же ресурсами. QDevice предотвращает это, отдавая голос только одной из сторон.
- **Компоненты**: Сервис `corosync-qnetd` на стороннем Linux-сервере и `corosync-qdevice` на каждой ноде кластера Proxmox.

### Fencing и Watchdog

Для корректной работы HA в Proxmox используется механизм **Fencing** (изоляция). Если нода перестает отвечать, кластер должен быть уверен, что она действительно выключена и не имеет доступа к общим данным, прежде чем запускать ее ВМ на другом узле.

- **Self-Fencing**: В Proxmox реализовано через программный или аппаратный Watchdog. Если сервис `pve-ha-lrm` теряет связь с кластером, он инициирует немедленную перезагрузку ноды (через `/dev/watchdog`), чтобы предотвратить повреждение данных при конкурентном доступе.

### Миграция и репликация

- **Live Migration (Живая миграция)**: Перенос запущенной ВМ без остановки. Требует наличия Shared Storage (NFS, SMB, Ceph) или использования локальных дисков с одновременным копированием данных по сети (Storage Migration).
- **ZFS Storage Replication**: Асинхронное копирование снимков (snapshots) дисков ВМ между локальными ZFS-пулами нод по расписанию (от 1 минуты).
  - *Ограничение*: При сбое ноды данные на новом хосте будут в состоянии последнего успешного сеанса репликации (возможна потеря данных за последнюю минуту).

## Практические сценарии

### Создание кластера через CLI

Создание кластера на первой ноде:

```bash
pvecm create my-cluster
```

Получение информации для подключения других нод:

```bash
pvecm status
```

Добавление новой ноды в существующий кластер (выполняется на новой ноде):

```bash
pvecm add <IP_ADDRESS_OR_HOSTNAME_OF_FIRST_NODE>
```

### Настройка QDevice (для 2-х нод)

1. На внешнем сервере (Debian/Ubuntu):

   ```bash
   apt update && apt install corosync-qnetd
   ```

2. На каждой ноде Proxmox:

   ```bash
   apt update && apt install corosync-qdevice
   ```

3. Инициализация с любой ноды кластера:

   ```bash
   pvecm qdevice setup <IP_QNETD_SERVER>
   ```

### Мониторинг и управление HA

Проверка статуса менеджера ресурсов:

```bash
ha-manager status
```

Пример вывода:

```bash
# → quorum OK
# → master node1 (active)
# → lrm node1 (active)
# → service vm:101 (started, node1)
```

Логи работы HA для отладки:

```bash
journalctl -u pve-ha-lrm -f
journalctl -u pve-ha-crm -f
```
