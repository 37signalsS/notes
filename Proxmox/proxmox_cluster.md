# Кластеризация и High Availability в Proxmox

## Определения

**Proxmox Cluster** — это объединение нескольких независимых серверов Proxmox Virtual Environment (PVE) в единую систему с централизованным управлением через веб-интерфейс или Command Line Interface (CLI).

**High Availability (HA, Высокая доступность)** — механизм, обеспечивающий автоматический перезапуск виртуальных машин (VM) или контейнеров (LXC) на другом узле в случае сбоя текущего хоста.

**Corosync** — основной сервис обмена сообщениями и контроля состояния (Cluster Engine), обеспечивающий работу кластера и отслеживание доступности нод.

## Основные концепции

### Требования и правила создания кластера

- **Версионность**: Все узлы должны иметь одинаковую мажорную версию Proxmox (например, 8.x). Допускается временное смешивание версий только в процессе апгрейда.
- **Синхронизация времени**: Использование `chrony` или `systemd-timesyncd` (NTP) обязательно для предотвращения рассинхронизации кворума и логов.
- **Сеть Corosync**: Рекомендуется выделять отдельную физическую сеть с задержками менее 2 мс.
- **Кворум (Quorum)**: Минимальное количество голосов для принятия решений. Кластер работоспособен (quorate), если доступно >50% голосов.

### Резервирование Corosync (Multi-link)

Proxmox поддерживает до 8 линков (интерфейсов) для Corosync. Это критически важно для предотвращения развала кластера при сбое одного коммутатора или кабеля.
- **Priority**: Каждому линку можно назначить приоритет. Corosync использует линк с самым низким номером, пока он доступен.
- **Рекомендация**: Использовать как минимум два независимых сетевых пути.

### QDevice (Quorum Device)

Используется для кластеров из 2-х нод или при четном количестве узлов для обеспечения нечетного количества голосов.
- **Split-Brain**: Состояние разделения кластера. QDevice предотвращает одновременный запуск ресурсов на обеих сторонах.
- **Внешний голос**: QDevice работает на стороннем сервере (не члене кластера) и предоставляет дополнительный голос.

### Fencing и Watchdog

Механизм изоляции сбойного узла.
- **Watchdog**: Аппаратный (IPMI) или программный таймер. Если `pve-ha-lrm` не сбрасывает таймер, узел принудительно перезагружается.
- **Self-Fencing**: Автоматическая перезагрузка узла при потере кворума для защиты общих данных от конкурентной записи.

### Группы HA (HA Groups)

Позволяют гибко управлять распределением ресурсов в кластере.
- **Nodes**: Список узлов, на которых разрешен запуск ресурсов группы.
- **Restricted**: Если включено, ресурс может работать *только* на узлах из списка. Если выключено — может запуститься на любом узле, если приоритетные недоступны.
- **NoFailback**: Предотвращает автоматический возврат ресурса на более приоритетный узел после его восстановления (полезно для тяжелых БД).

### Миграция и репликация

- **Live Migration (Живая миграция)**: Перенос запущенной ВМ без остановки. Требует наличия Shared Storage (NFS, SMB, Ceph) или использования локальных дисков с одновременным копированием данных по сети (Storage Migration).
- **ZFS Storage Replication**: Асинхронное копирование снимков (snapshots) дисков ВМ между локальными ZFS-пулами нод по расписанию (от 1 минуты).
  - *Ограничение*: При сбое ноды данные на новом хосте будут в состоянии последнего успешного сеанса репликации (возможна потеря данных за последнюю минуту).

## Практические сценарии

### Создание кластера через CLI

Создание кластера на первой ноде:

```bash
pvecm create my-cluster
# → Generating public/private rsa key pair...
# → Writing corosync config to /etc/pve/corosync.conf
```

Добавление новой ноды в существующий кластер (выполняется на новой ноде):

```bash
pvecm add <IP_ADDRESS_OR_HOSTNAME_OF_FIRST_NODE>
# → Copying certificates...
# → Stopping pve-cluster and corosync...
# → Starting corosync...
```

Проверка статуса кластера:

```bash
pvecm status
# → Quorum information
# → ------------------
# → Date:          Mon Jul 27 12:00:00 2026
# → Quorum:        2 Votes needed, 3 Votes available
# → Membership information
# → ----------------------
# →     Nodeid      Votes Name
# →          1          1 node1 (local)
# →          2          1 node2
# →          3          1 node3
```

### Настройка QDevice (для 2-х нод)

1. На внешнем сервере (Debian/Ubuntu):

   ```bash
   apt update && apt install corosync-qnetd
   ```

2. На каждой ноде Proxmox:

   ```bash
   apt update && apt install corosync-qdevice
   ```

3. Инициализация с любой ноды кластера:

   ```bash
   pvecm qdevice setup <IP_QNETD_SERVER>
   ```

### Режим обслуживания (Maintenance Mode)

Появился в PVE 8.x. Позволяет безопасно выводить узел из работы без срабатывания HA.
- **Migrate**: Все ВМ автоматически мигрируют на другие узлы перед входом в режим.
- **Shutdown**: Узел выключается после миграции.

Команда установки режима (через API/GUI или `ha-manager`):
```bash
ha-manager set-maintenance node1 --mode migrate
```

### Мониторинг и управление HA

Проверка статуса менеджера ресурсов:

```bash
ha-manager status
# → quorum OK
# → master node1 (active)
# → lrm node1 (active)
# → service vm:101 (started, node1)
```

Логи работы HA для отладки:

```bash
journalctl -u pve-ha-lrm -f
journalctl -u pve-ha-crm -f
```

## Диагностика и устранение неисправностей

### Проблемы с кворумом

Если `pvecm status` показывает `Quorum: No`, управление кластером (включая запись в `/etc/pve`) блокируется.
- **Причина**: Потеря сетевой связности между нодами или падение сервиса `corosync`.
- **Временное решение** (для восстановления доступа):
  ```bash
  pvecm expected 1
  ```

### Ошибки Corosync

Проверка конфигурации:
```bash
corosync-cfgtool -s
# → Printing ring status.
# → Local node ID 1
# → RING ID 0
# →     id  = 10.0.0.1
# →     status  = ring 0 active with no faults
```

Если статус `faulty`, проверьте настройки MTU (Corosync чувствителен к фрагментации) и настройки Firewall (UDP порты 5405-5407).
