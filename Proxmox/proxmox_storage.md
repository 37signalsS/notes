# Хранилища и Ceph в Proxmox

## Определения

**Storage (Хранилище)** в Proxmox Virtual Environment (PVE) — это абстрактный слой управления данными для подключения физических и сетевых накопителей. Используется для хранения дисков виртуальных машин (VM), контейнеров (LXC), образов ISO и резервных копий. Все хранилища описываются в общем конфигурационном файле `/etc/pve/storage.cfg`, который автоматически синхронизируется между узлами кластера через кластерную файловую систему pmxcfs.

**Content Types (Типы контента)** — фильтры, определяющие назначение хранилища (для одного хранилища можно указать несколько типов):
- **images**: Диски VM (KVM/QEMU).
- **rootdir**: Корневые файловые системы контейнеров (LXC).
- **iso**: Установочные образы ОС.
- **vztmpl**: Шаблоны LXC.
- **backup**: Резервные копии (`vzdump` или PBS).
- **snippets**: Скрипты (Cloud-Init, хуки виртуальных машин).
- **import**: OVA-образы и файлы дисков, которые можно импортировать в PVE (добавлен в PVE 8.3).

**Shared Storage (Общее хранилище)** — хранилище, доступное всем узлам кластера одновременно (NFS, SMB/CIFS, iSCSI, Ceph). Флаг `shared` в конфигурации **не делает** локальное хранилище общим — он лишь помечает уже совместно используемое хранилище, чтобы PVE корректно включил его в кластерные операции (Live Migration без копирования данных).

**Volume ID (VOLID)** — уникальный идентификатор тома в формате `<STORAGE_ID>:<путь/имя>`, например `local:230/example-image.raw`, `local:iso/debian-netinst.iso` или `local-lvm:vm-101-disk-0`. Используется во всех командах работы с томами.

**Thin Provisioning (Тонкое выделение)** — режим, при котором на хранилище записываются только реально используемые гостем блоки, а не весь виртуальный размер диска. Поддерживается qcow2 и всеми типами хранилищ с поддержкой снапшотов. Опасность: при переполнении хранилища все гости, использующие его тома, получают ошибки I/O.

## Основные концепции

### Типы локальных хранилищ {#типы-локальных-хранилищ}

- **Directory**: Обычная папка (ext4/XFS). Универсальна, поддерживает все типы контента. Диски хранятся как файлы `.qcow2` или `.raw`. Снапшоты возможны только для qcow2 (внутренние или как цепочка томов).
- **LVM**: Блочные устройства. Быстрый доступ без накладных расходов на формат файла. До PVE 8.x не поддерживал снапшоты в PVE; **с PVE 9 снапшоты VM на LVM доступны через цепочку томов** (`snapshot-as-volume-chain`) — снимки данных создаются в отдельных томах и наслаиваются без блокировки работы VM.
- **LVM-Thin**: Тонкое выделение и снапшоты на уровне пула. Идеально для локальных VM. Не поддерживает Storage Replication. Подробнее о механиках — **[LVM Thin Provisioning](../Linux/FileSystems/LVM/thin-provisioning.md)**.
- **ZFS**: Рекомендуется для High Availability. Поддерживает компрессию, снапшоты и Storage Replication (репликация по расписанию через `zfs send/receive`). В PVE 9 поставляется ZFS 2.4, **с PVE 9.0 доступно расширение RAIDZ-массивов** без пересоздания пула. ZFS-тома (zvol) для VM хранятся в пуле как блочные устройства.
- **BTRFS**: Поддерживается с PVE 7.x. Альтернатива ZFS для одиночных дисков, поддерживает снапшоты и компрессию. В PVE 9.x относится к **технологическому превью** (best-effort поддержка со стороны Proxmox).

#### Рекомендуемые параметры ZFS для VM-хранилищ

ZFS в PVE поставляется с конфигурацией, подходящей для большинства сценариев, но для production-рабочих нагрузок рекомендуется явно задавать параметры:

- **ashift**: должен соответствовать физическому сектору диска (обычно `12` для 4K секторов, `13` для 8K). Неправильное значение приводит к read-modify-write и повышенному износу SSD. Проверка: `zfs get ashift poolname`.
- **compression**: `lz4` (по умолчанию в PVE 9) или `zstd` (с ZFS 2.4). `zstd` дает выше сжатие, но больше нагрузки на CPU. Для большинства VM-нагрузок `lz4` оптимален.
- **recordsize**: максимальный размер блока записи. Для VM-дисков (raw/qcow2) рекомендуется `64K` или `128K` — уменьшает фрагментацию и улучшает случайный I/O. Для файловых данных (ISO, backup) можно оставить `128K` или `1M`. Изменить можно только для новых файлов: `zfs set recordsize=64K pool/data`.
- **atime**: отключите (`zfs set atime=off poolname`) — убирает лишние записи при каждом чтении.
- **xattr**: `sa` (system attribute) по умолчанию в PVE, ускоряет доступ к ACL и extended attributes.
- **SLOG (ZIL)**: отдельное быстрое устройство (NVMe) для синхронной записи. Дает существенный прирост для баз данных и приложений с интенсивным `fsync`. Для обычных VM без синхронной нагрузки не требуется.
- **L2ARC**: кэш чтения на SSD/NVMe. Полезен при повторяющемся чтении (шаблоны, общие образы). Не нужен, если основной пул уже построен на NVMe.

#### Аппаратные конфигурации и планирование

- **HBA vs RAID**: Ceph и ZFS требуют прямого доступа к дискам (JBOD). Используйте HBA в IT mode; RAID-контроллеры с маскировкой дисков недопустимы.
- **Multipath**: Для iSCSI и Fibre Channel обязательно. В PVE настраивается через пакет `multipath-tools` с policy `multibus` и `failback immediate`.
- **I/O Scheduler**: Для NVMe используйте `none` (по умолчанию `mq-deadline` также подходит). Для SATA SSD — `mq-deadline` или `bfq`. Для HDD — `bfq`.
- **TRIM / DISCARD**: Для SSD/NVMe включите `discard=on` в конфигурации диска VM (`qm set <vmid> --scsi0 <storage>:<disk>,discard=on`). На уровне хоста включите `fstrim` timer (`systemctl enable fstrim.timer`).
- **RAIDZ vs Mirror**: RAIDZ (parity) экономит место, но дольше восстанавливается после отказа диска. 2-way mirror дает 50%usable space, но выше производительность и скорость recovery. Для малых кластеров mirror предпочтительнее.

### Сетевые и общие хранилища (Shared Storage)

Позволяют выполнять **Live Migration** без перемещения данных.

- **NFS**: Простая настройка, поддержка всех типов контента. Рекомендуется использовать NFS v4.1 и выше. Снапшоты на NFS выполняются средствами qcow2 и крайне медленны на больших дисках — на сетевых хранилищах их лучше создавать при выключенной VM. Монтируется автоматически через mount-опции (`--options`).
- **SMB/CIFS**: Общие файловые ресурсы Windows/TrueNAS/Samba. Поддерживает все типы контента и снапшоты qcow2. SMB1 не поддерживается по соображениям безопасности (по умолчанию SMB3).
- **iSCSI**: Передача блочных данных. В PVE два плагина: `iscsi` (через ядро, krbd/kernel) и `iscsidirect` (через libiscsi). Для многопользовательского доступа и разбиения LUN на виртуальные диски поверх iSCSI требуется LVM. Для отказоустойчивости рекомендуется multipath.
- **FC/SAS**: Fibre Channel и SAS-хранилища обслуживаются хостом напрямую, без специального плагина PVE; поверх LUN используется LVM.
- **ZFS over iSCSI**: Тип `zfs` — блочное общее хранилище, предоставляемое по iSCSI, со снапшотами на уровне ZFS.
- **Ceph (RBD/CephFS)**: Распределенное программно-определяемое хранилище (см. ниже).
- **Proxmox Backup Server (PBS)**: Инкрементальные дедуплицированные бэкапы с шифрованием (см. **[Proxmox Backup Server](./proxmox_backup_server.md)**).

### Storage Replication

Репликация дисков VM между локальными ZFS-пулами разных узлов кластера по расписанию. Основана на `zfs send/receive` инкрементальных снимков. Критична для HA без Shared Storage.

**Особенности:**
- Работает только с ZFS-хранилищами.
- Реплицируются только диски VM (`images`), не rootdir LXC.
- После сбоя узла реплика позволяет запустить VM на другом узле с актуальными данными.
- Минимальный интервал — 1 минута.

**Практическое ограничение:** replication не заменяет общее хранилище (Shared Storage) для Live Migration — при миграции VM данные физически не перемещаются, а replication обеспечивает только асинхронную копию.

### Сводная таблица типов хранилищ (PVE 9.x)

| Тип | Плагин | Уровень | Shared | Снапшоты | Статус |
|---|---|---|---|---|---|
| ZFS (локальный) | zfspool | файл/блок | нет | да | stable |
| Directory | dir | файл | нет | да (qcow2) | stable |
| BTRFS | btrfs | файл | нет | да | tech preview |
| NFS | nfs | файл | да | да (qcow2) | stable |
| CIFS | cifs | файл | да | да (qcow2) | stable |
| Proxmox Backup | pbs | файл/блок | да | n/a | stable |
| CephFS | cephfs | файл | да | да | stable |
| LVM | lvm | блок | нет | да (PVE 9+) | stable |
| LVM-thin | lvmthin | блок | нет | да | stable |
| iSCSI (kernel/libiscsi) | iscsi, iscsidirect | блок | да | да (через LVM) | stable |
| FC/SAS | native | блок | да | да (через LVM) | stable |

> **Примечание по поддержке версий**: GlusterFS удален из поддерживаемых типов, а плагин Linstor (технологическое превью в PVE 8.2/8.3) исключен в PVE 9. Для отказоустойчивых распределенных файловых хранилищ используйте CephFS.

## Хранилища для High Availability

### Роль хранилища в High Availability

В кластере Proxmox VE механизм **High Availability (HA)** должен автоматически перезапускать виртуальные машины и контейнеры на другом узле при сбое исходного хоста. Звучит просто, но всё держится ровно на одном условии: тип хранилища, на котором лежит диск VM.

Когда узел падает, соседний узел должен успеть:

- получить доступ к диску упавшей VM/CT — без переноса файлов, без "подождите, я скопирую";
- прочитать актуальную конфигурацию;
- поднять машину без рассинхронизации данных — то есть без риска запустить VM со старой версией диска, пока где-то параллельно висит новая.

Если хранилище физически привязано к упавшему узлу (обычный локальный диск, LVM-thin на локальном SSD и т.п.) — вот и всё, дальше можно даже не настраивать HA, она просто не сработает: сосед физически не может достать диск из мёртвого сервера.

#### Что должно уметь хранилище для HA

1. **Shared access** — диск VM физически доступен с нескольких узлов одновременно, а не скопирован туда "на всякий случай".
2. **Кластерная согласованность** — блокировки, защита от split-brain, синхронная или близкая к синхронной репликация.
3. **Failover без ручных телодвижений** — Proxmox сам стартует VM на другом узле, без вашего "ну сейчас я быстренько смонтирую диск руками".
4. **Отдельная сеть под хранилище** — трафик storage и трафик управления/VM лучше не смешивать, желательно 10GbE и выше, особенно для Ceph.
5. **Надёжность на уровне данных** — RAID, репликация Ceph, DRBD, отказоустойчивый NAS/SAN — что-то, что переживёт не только падение узла, но и падение одного диска.
6. **Поддержка в самом Proxmox HA stack** — Ceph, iSCSI, NFS, ZFS replication.

### Один узел + требование HA

На одном узле HA не бывает физически. Минимум — два узла с общим доступом к хранилищу.

#### Локальное хранилище (ZFS RAID или аппаратный RAID)

Плюсы понятны: защита от отказа отдельного диска, простота, хорошая производительность. Минус один, но фатальный для нашей темы: **failover в принципе невозможен**, потому что весь массив физически стоит в одном корпусе. Упал сервер — упал и RAID вместе с ним.

#### Репликация ZFS на "пассивный" узел

ZFS-репликация в Proxmox копирует снапшоты диска на соседнюю ноду по расписанию (минимальный интервал — минуты, не секунды). Это даёт вам "холодный резерв" — в случае аварии можно руками поднять VM на второй ноде с потерей данных за последний интервал репликации. Но это **не HA**: автоматического старта нет, восстановление — ручная операция, и вы теряете всё, что записалось после последнего снапшота.

#### Репликация на внешний NAS

Годная схема для бэкапов, но сам NAS в этом случае становится **SPOF** (single point of failure, единая точка отказа) — вы просто переносите риск с одного сервера на другой, а не убираете его.

#### Snapshots + vzdump

Это резервное копирование, а не HA. Восстановление возможно, но не автоматическое и не мгновенное — пока вы разворачиваете бэкап, сервис уже недоступен, и это никак не соответствует смыслу High Availability.

**Итог по разделу:** на одном узле HA не бывает физически, точка. Минимум — два узла с общим доступом к хранилищу, и даже тут, как сейчас увидим, есть нюансы.

### Два узла + quorum / witness

#### Проблема двух узлов: split-brain

Если у вас всего два узла и между ними пропадает связь, каждый из них видит ситуацию как "я один живой, второй, видимо, умер" — и оба могут попытаться поднять одну и ту же VM одновременно. Это классический **split-brain**, и именно кластерный кворум должен его предотвращать. Проблема в том, что у двух узлов кворума в чистом виде просто не существует — 1 голос против 1 голоса, большинства нет никогда. Подробно про сам механизм кворума и голосов — в разделе **[Кластеризация и High Availability](./proxmox_cluster.md)**.

#### Хранилище для HA в 2-узловом кластере

| Storage | Годится для HA | SPOF | Нужен QDevice | Производительность |
|---|---|---|---|---|
| ZFS Local + Replication | Частично (потеря данных за интервал репликации) | Узел | Да | Средняя |
| NFS / iSCSI / NAS | Да | NAS/SAN | Да | Средняя |
| Ceph | Да | Нет (при 3+ мониторах) | Да | Высокая |
| DRBD9 | Да* | Нет | Да | Средняя |

> *В PVE 9 плагин LINSTOR исключен; ручная настройка DRBD9 без менеджера возможна, но требует значительных усилий.

### Три и более узлов с общим хранилищем

#### Почему от трёх узлов всё внезапно проще

С тремя узлами кворум работает нативно и без костылей: большинство — это 2 из 3, split-brain при потере одного узла невозможен просто по арифметике голосов, никакого QDevice не требуется. HA-группы настраиваются штатно через интерфейс, без танцев с бубном.

#### Сводка по архитектурам

| Архитектура | SPOF | Производительность | Требования | Масштабируемость |
|---|---|---|---|---|
| NFS | NAS | Средняя | Низкие | Средняя |
| iSCSI | SAN (без резервирования) | Высокая | Средние | Средняя |
| Ceph | Нет | Высокая | Высокие (сеть, диски, узлы) | Отличная |

Ceph здесь выделяется не просто "хорошими цифрами в таблице" — это единственный вариант из трёх, где при правильной настройке в принципе нет единой точки отказа: данные размазаны по всем узлам, а не лежат на одном внешнем устройстве.

### Гиперконвергентное хранилище: Ceph и альтернативы

**Hyperconverged** в данном контексте означает, что хранилище и вычисления живут на одних и тех же узлах кластера, без отдельного NAS/SAN как самостоятельного устройства.

**Ceph** — самый зрелый вариант такого рода в экосистеме Proxmox: RBD-тома для дисков VM, CephFS — для ISO, шаблонов и бэкапов. Данные распределяются между узлами и умеют "самоисцеляться" (self-healing) при выходе диска или узла из строя. Цена вопроса — минимум 3 узла, отдельная выделенная сеть под Ceph-трафик и желательно SSD/NVMe, а не HDD (Ceph на вращающихся дисках — это боль, о которой знает каждый, кто пробовал). Подробнее о развертывании — в разделе **[Гиперконвергентный Ceph](#гиперконвергентный-ceph)**.

Альтернативы Ceph по духу (не по конкретной реализации) — тот же DRBD9, разобранный в разделе про 2-узловые кластеры, только он масштабируется и на 3+ узлов.

### Внешние SAN/NAS решения

| Тип | Описание | Годится для HA | Примечание |
|---|---|---|---|
| NAS (NFS) | Файловое хранилище | Да | Годится и под диски VM, и под ISO |
| NAS (SMB/CIFS) | Файловое хранилище | Только для ISO/шаблонов | Диски VM через SMB не подключить |
| SAN (iSCSI/Fibre Channel) | Блочный доступ | Да | Multipath строго обязателен |
| Unified Storage (NFS + iSCSI) | Комбинированный | Да | Сам NAS/SAN должен быть отказоустойчивым (кластеризация на его стороне) |

Ключевая мысль этого раздела повторяется не случайно: **HA вашего кластера Proxmox никогда не будет надёжнее, чем то единственное устройство, на котором лежат диски VM**, если это устройство — одна коробка без собственного резервирования. Кластер Proxmox из пяти нод с единственным несбойным NAS позади — это HA с одним большим, жирным SPOF.

### Что для HA не годится вообще

| Storage | Годится для HA | Причина |
|---|---|---|
| Local LVM / Directory | Нет | Виден только одному узлу |
| CIFS/SMB | Нет | Только ISO/шаблоны, не диски VM |
| ZFS локальный без репликации | Нет | Нужна как минимум репликация, а лучше — shared storage |
| Rsync / ручная репликация | Нет | Нет автоматического failover, всё руками |

Если что-то из этой таблицы — основа вашего текущего хранилища, а HA в интерфейсе Proxmox при этом "включена" — она включена только формально. Реального failover не будет, вы узнаете об этом в самый неподходящий момент.

### Рекомендации

Если сводить всю тему до практических советов:

- Минимум **3 узла** для нормального кворума без QDevice — двумя узлами можно обойтись, но с явным пониманием, что третий голос всё равно нужен откуда-то.
- Используйте **shared или hyperconverged storage** — никаких "локальных дисков + надежда".
- Отдельная сеть под хранилище, желательно 10GbE, особенно если это Ceph.
- Настройте HA-группы в самом Proxmox осознанно, а не "включил галочку и забыл".
- Регулярные бэкапы через [Proxmox Backup Server](./proxmox_backup_server.md) — HA защищает от падения узла, а не от человеческой ошибки внутри VM или от повреждения данных.
- Периодически **проверяйте failover руками** — выключите ноду намеренно и посмотрите, что произойдёт. Лучше неприятный сюрприз на тесте, чем ночью на проде.
- Для критичных VM — синхронная репликация, а не "раз в час снапшотом".
- Документируйте архитектуру — через полгода вы сами не вспомните, почему настроили именно так.

### Общие параметры хранилищ

Пример стандартной конфигурации (`/etc/pve/storage.cfg`) после установки:

```ini
dir: local
        path /var/lib/vz
        content iso,vztmpl,backup

lvmthin: local-lvm
        thinpool data
        vgname pve
        content rootdir,images

zfspool: local-zfs
        pool rpool/data
        sparse
        content images,rootdir
```

Ключевые общие параметры:

- **nodes**: список узлов кластера, на которых хранилище доступно (ограничение доступа).
- **content**: набор типов контента (images/rootdir/iso/vztmpl/backup/snippets/import).
- **shared**: флаг общего хранилища (см. определение выше).
- **disable**: полностью отключает хранилище.
- **prune-backups**: политика хранения резервных копий (`keep-last`, `keep-daily`, `keep-weekly`, `keep-monthly`, `keep-yearly`, `keep-hourly`).
- **format**: формат образов по умолчанию (raw/qcow2/vmdk) для файловых хранилищ.
- **preallocation**: режим предварительного выделения (off/metadata/falloc/full); для сетевых хранилищ с большими qcow2 рекомендуется `off` во избежание таймаутов.

> Не рекомендуется использовать один и тот же пул хранилища одновременно в разных кластерах PVE: операции с томами требуют эксклюзивной блокировки, которая работает только внутри одного кластера.

### Гиперконвергентный Ceph

**Ceph** объединяет локальные диски всех нод в единый отказоустойчивый пул. В PVE Ceph устанавливается и управляется непосредственно на гипервизорах (через GUI или CLI `pveceph`), превращая кластер в гиперконвергентную систему.

**Версии Ceph в PVE:**
- **PVE 9.0** (авг 2025) поставляется с **Ceph Squid (19.2.3)**.
- **PVE 9.2** (май 2026): для **новых** установок по умолчанию предлагается **Ceph Tentacle (20.2.1)**; существующие кластеры остаются на своей версии — новые ноды выравниваются под версию, уже запущенную в кластере.
- **Ресурсы жизненного цикла**: поддержка Ceph Squid заканчивается ориентировочно **19 сентября 2026**; Ceph Reef (18.x) архивирован и больше не сопровождается. PVE 8.x (ветка до EOL — август 2026) использует Quincy/Reef.
- **Порядок обновления гиперконвергентного кластера**: сначала Ceph на Squid → затем переход PVE 8→9 → затем Ceph на Tentacle (после PVE 9.1). Специфика обновления кластера с Ceph — **[Обновление систем Proxmox](./proxmox_updates.md)**.

> **Внимание**: следите за сроками поддержки версий Ceph в используемом PVE. Продление жизни кластера за пределами EOL версии Ceph небезопасно — обновление Ceph практически никогда не умещается в одно окно обслуживания.

**Компоненты:**
- **MON (Monitors)**: Хранят карту состояния кластера (Cluster Map). Минимум 3 для кворума; больше 3 обычно не нужно.
- **MGR (Managers)**: Мониторинг, метрики, telemetry, PG-автоскейлинг. Один активный, остальные standby.
- **OSD (Object Storage Daemon)**: Управляет физическим диском (один OSD на диск). Репликация и распределение данных идут между OSD. Начиная с Ceph Luminous OSD использует хранилище **BlueStore** (по умолчанию), для которого можно выделять отдельные устройства DB/WAL.
- **MDS (Metadata Server)**: Требуется для CephFS. Активный + standby; можно несколько активных (multi-MDS) при высокой нагрузке на клиенты.
- **RBD (RADOS Block Device)**: Блочное хранилище для дисков VM.
- **CephFS**: Файловая система для ISO, шаблонов и бэкапов (требует MDS), POSIX-совместимая и распределенная между MDS.

**Архитектура данных:**
- **Pools (пулы)** — логические группы объектов. Пулу назначаются число реплик (size, по умолчанию 3), минимальное число реплик (min_size, по умолчанию 2) и число Placement Groups (PG). Не устанавливайте min_size=1: при деградации реплик это ведет к потере данных.
- **PG (Placement Groups)** — группы объектов, единица распределения и восстановления. По умолчанию PVE создает 128 PG на пул. Рекомендуется включать **PG Autoscaler** (`ceph mgr module enable pg_autoscaler`, режимы `warn`/`on`/`off`).
- **CRUSH** — алгоритм распределения объектов по OSD без центрального индекса. Пул можно ограничить классом дисков (hdd/ssd/nvme) через правила CRUSH и device classes.
- **Erasure Coding (EC)** — альтернатива репликации: данные разбиваются на k фрагментов + m контрольных; допускает потерю m OSD. Больше полезного места, ниже производительность. Для RBD обязателен отдельный реплицированный metadata-пул.

#### Расчет Placement Groups (PG)

Количество PG влияет на производительность распределения и нагрузку на MON. Формула推荐的:
```
total PGs = (OSDs × 100) / max_replication_count
```
Результат округляют до ближайшего значения из набора {8, 16, 32, 64, 128, 256, 512, 1024, 2048}. Для 12 OSD с репликацией 3: (12×100)/3 = 400 → 512. PG Autoscaler обычно подбирает оптимальное значение автоматически.

#### CRUSH Tunables и Device Classes

- **device classes**: явно назначайте класс дисков (`hdd`, `ssd`, `nvme`) через `ceph osd crush set-device-class`. CRUSH правила затем ограничивают пул определенным классом.
- **crush tunables**: оптимальные значения зависят от версии Ceph. В Squid/Tentacle используйте `recovery_size_autoset` и `select_recency_count` для адаптации.
- **PG count per OSD**: поддерживайте не более 100–150 PG на один OSD. При добавлении новых OSD перебалансировка PG автоматически выполняется через `ceph pg osd-load`.

#### Erasure Coding профили и FastEC

- **EC профили**: создаются через `ceph osd erasure-code-profile set`. Пример для k=2, m=1:
  ```
  ceph osd erasure-code-profile set ec-profile \
    k=2 m=1 crush-failure-domain=host \
    plugin=jerasure technique=reed_sol_van
  ```
- **FastEC** (Ceph Tentacle): включает оптимизации частичных чтений/записей для EC-пулов. Включается через `ceph config set osd allow_ec_optimizations true`. Требует stripe unit, кратного 4 КБ. Переключатель односторонний — после включения откат без пересоздания пула невозможен.

**Рекомендации по железу и сети (для гиперконвергентного кластера):**
- Минимум 3 одинаковых сервера; минимум 12 OSD (по 4 на ноду), равномерно распределенных.
- **Сеть**: выделенная полоса не менее 10 Гбит/с только для Ceph. Для высокопроизводительных конфигураций — три отдельных сети: внутренняя кластерная (25+ Гбит/с), публичная (10+ Гбит/с) и для latency-чувствительного corosync (1 Гбит/с). Трафик ребалансировки может «съедать» полосу и ломать кворум кластера при общих сетях.
- **Память**: OSD требует по умолчанию 4 ГиБ, рекомендовано 8 ГиБ на OSD. Оставляйте запас на recovery/backfill.
- **CPU**: минимум 1 ядро на каждый сервис Ceph; NVMe-OSD может утилизировать 4–6 потоков CPU.
- **Диски**: избегайте RAID-контроллеров — используйте HBA (host bus adapter), Ceph сам управляет избыточностью. В малых кластерах предпочтительны SSD для быстрого восстановления.
- **Firewall**: при включенном межсетевом экране откройте порты Ceph (проще всего — макрос firewall).

**FastEC (Ceph Tentacle)**: новый путь I/O для EC-пулов (`allow_ec_optimizations`), добавляющий частичные чтения/записи и существенно улучшающий мелкий случайный I/O. Требует tentacle-релиз OSD, профиль EC `reed_sol_van` и stripe unit кратный 4 КБ. Переключатель односторонний — включив, откатить без пересоздания пула нельзя.

### Объединение `local-lvm` и `local` в единое файловое хранилище {#объединение-local-lvm-и-local}

После установки Proxmox VE на LVM-разметке по умолчанию создаются два локальных хранилища:

- **`local`** — директория `/var/lib/vz` (тип `dir`), где хранятся ISO-образы, шаблоны LXC и резервные копии.
- **`local-lvm`** — LVM-thin пул `pve/data` (тип `lvmthin`), где хранятся диски VM и контейнеров.

Такое разделение создает административные сложности: размер `local-lvm` фиксирован и не виден в обычной файловой системе, расширить его без миграции данных затруднительно.

#### Определения

- **LVM-thin pool** — тонко-провижненный пул LVM, в котором тома выделяются динамически из общего пула. В стандартной установке PVE это `/dev/pve/data`.
- **Directory storage (`dir`)** — файловое хранилище, при котором диски VM хранятся как обычные файлы (`.qcow2` или `.raw`) в указанной директории.
- **Content types (типы контента)** — набор флагов, определяющих, для чего может использоваться хранилище (`images`, `rootdir`, `iso`, `vztmpl`, `backup`, `snippets`, `import`).

#### Предпосылки и ограничения

**Подходит для:**
- Новых установок Proxmox VE на LVM без важных данных на `local-lvm`.
- Сценариев, где требуется единое файловое пространство для всех типов данных.

**Не подходит для:**
- ZFS-установок (у ZFS своя архитектура пулов, процедура отличается).
- Установок с существующими VM/CT на `local-lvm`, если вы не планируете предварительную миграцию дисков на другое хранилище.

> **Важно:** удаление LVM-thin пула `pve/data` приведет к потере всех дисков, хранящихся в нем. Перед выполнением убедитесь, что на `local-lvm` нет рабочих VM/CT, либо перенесите их на внешнее хранилище.

#### Варианты решения

1. **Удалить LVM-thin пул и расширить корневой логический том** (проще для новых установок).
2. **Перенести диски с `local-lvm` на `local`, а затем удалить пул** (для уже работающих сред).

Ниже описан первый вариант, так как он безопаснее для новых установок и не требует миграции данных.

#### Шаг 1. Удаление хранилища `local-lvm` из конфигурации PVE

Удаление записи из `/etc/pve/storage.cfg` через GUI или CLI. Это действие не удаляет данные с диска, а только убирает хранилище из списка Datacenter.

```bash
# Через CLI
pvesm remove local-lvm
```

Или через GUI: **Datacenter → Storage → local-lvm → Remove**.

После этого в списке хранилищ остается только `local`, но физическое пространство еще не освобождено.

#### Шаг 2. Удаление LVM-thin пула

Удалите логический том `pve/data`. Подтвердите действие, когда система запросит подтверждение.

```bash
lvremove /dev/pve/data
# → Do you really want to remove active LV "data"? [y/n]: y
# → Logical volume "data" successfully removed
```

#### Шаг 3. Расширение корневого логического тома

Добавьте всё свободное пространство группы томов `pve` к корневому логическому тому:

```bash
lvresize -l +100%FREE /dev/pve/root
# → Size of logical volume pve/root successfully changed from ... to ...
```

- `-l +100%FREE` — добавить всё оставшееся нераспределённое пространство в VG `pve`.
- `/dev/pve/root` — корневой логический том, на котором установлена ОС.

#### Шаг 4. Расширение файловой системы

Команда зависит от типа файловой системы корневого раздела.

**Для ext4:**
```bash
resize2fs /dev/mapper/pve-root
# → filesystem size ...
```

**Для XFS** (если использовалась при установке):
```bash
xfs_growfs /
```

> **Примечание:** XFS можно только увеличивать, уменьшение не поддерживается. `xfs_growfs` принимает точку монтирования, а не блочное устройство.

#### Шаг 5. Обновление типов контента хранилища `local`

После освобождения места хранилище `local` должно принимать все типы данных, включая те, что раньше принадлежали `local-lvm` (`images` и `rootdir`).

Через GUI: **Datacenter → Storage → local → Edit → Content** — отметьте все нужные типы.

Через CLI отредактируйте `/etc/pve/storage.cfg`:

```ini
dir: local
        path /var/lib/vz
        content iso,vztmpl,backup,images,rootdir
```

#### Шаг 6. Перенос существующих дисков (если требуется)

Если у вас были диски на `local-lvm`, которые нужно сохранить, перед удалением пула перенесите их:

```bash
# Остановить VM
qm stop 101

# Экспортировать диск
qm disk export 101 local-lvm:vm-101-disk-0 /var/lib/vz/backup/vm-101-disk-0.raw

# Импортировать в local
qm importdisk 101 /var/lib/vz/backup/vm-101-disk-0.raw local --format raw
qm set 101 --scsi0 local:101/vm-101-disk-0.raw
```

#### Шаг 7. Проверка результата

```bash
pvesm status
# → Name   Type  Status  Total   Used   Available  %
# → local  dir   active  ...     ...    ...        ...

lsblk
# → sda3  (PV)
#   └─pve-root  (LV)  размер равен всему доступному пространству

df -h /
# → /dev/mapper/pve-root  ...  (весь доступный объем)
```

Если `pvesm status` не показывает `local-lvm` и корневой раздел занял всё пространство — преобразование завершено.

#### Типичные ошибки и решения

| Ошибка / ситуация | Причина | Решение |
|---|---|---|
| `lvremove: failed to remove active LV "data"` | Thin pool используется запущенными VM/CT | Остановите все гости, использующие `local-lvm`, или выполните миграцию дисков |
| `resize2fs: Bad magic number in super-block` | Файловая система не ext4 (например, XFS) | Используйте `xfs_growfs /` вместо `resize2fs` |
| `device is busy` при `lvremove` | Логический том все еще открыт | `lsof /dev/pve/data` или `fuser -v /dev/pve/data`; остановите процессы или перезагрузитесь в rescue |
| После расширения место не появилось | Не выполнен `resize2fs` / `xfs_growfs` | Размер LV увеличен, но ФС не расширена — выполните команду роста ФС |
| `local` не принимает `images` | Не обновлен `content` в `storage.cfg` | Добавьте `images,rootdir` в конфигурацию `local` |

#### Лучшие практики

1. **Бэкап перед LVM-операциями**: создайте резервные копии всех VM (через PBS или `vzdump`) и сохраните `/etc/pve/storage.cfg` и `/etc/lvm/backup/` вне ноды.
2. **Свежий rootfs в rescue**: если операция выполняется на рабочей ноде, имейте Rescue-режим PVE или Live CD на случай неудачи.
3. **ZFS вместо LVM для production**: для новых установок, где требуется единое хранилище, рассмотрите ZFS (`zfspool`) вместо LVM+ext4 — он предоставляет снапшоты, проверку целостности и replication из коробки.
4. **Не смешивайте назначение пулов**: после объединения все диски VM и файлы данных живут в одной файловой системе; используйте отдельные datasets ZFS или директории для изоляции, если требуется.
5. **Импорт дисков через `qm importdisk`**: для перемещения существующих дисков между хранилищами используйте встроенный импорт, а не копирование файлов в обход PVE.

### Развертывание и настройка Ceph через CLI (pveceph)

**Установка пакетов Ceph** (на каждой ноде; настраивает apt-репозиторий `ceph.sources`):
```bash
pveceph install
```

**Начальная конфигурация** (один раз на одной ноде; создает `/etc/pve/ceph.conf`, симлинк `/etc/ceph/ceph.conf`):
```bash
pveceph init --network 10.10.10.0/24
```

**Мониторы и менеджеры:**
```bash
pveceph mon create
pveceph mgr create
# Минимум 3 MON для кворума; MGR рекомендуется устанавливать на MON-нодах
```

**Статус кластера:**
```bash
pveceph status
# → health: HEALTH_OK
# → osds: 6 up, 6 in
```

**Создание OSD** (по одному на диск; по умолчанию BlueStore):
```bash
pveceph osd create /dev/nvme0n1
# → create OSD on /dev/nvme0n1 (bluestore)
```

**OSD с отдельными устройствами DB/WAL** (для производительности NVMe-кластеров):
```bash
pveceph osd create /dev/sda -db_dev /dev/nvme0n1 -wal_dev /dev/nvme0n1 \
  -db_size 20G -wal_size 2G
```

**Подготовка бывшего в использовании диска** (полное уничтожение данных!):
```bash
ceph-volume lvm zap /dev/sdX --destroy
```

**Безопасное удаление OSD:**
```bash
ceph osd out <id>                          # исключить из распределения данных
ceph osd ok-to-stop <id>                   # проверить, что остановка безопасна
pveceph stop --service osd.<id>
pveceph osd destroy <id> --cleanup         # очистка partition table для переиспользования
```

**Создание пула** (по умолчанию: 128 PG, size=3, min_size=2):
```bash
pveceph pool create <pool-name> --add_storages
# → создаст пул и автоматически зарегистрирует его как RBD-хранилище в PVE
```

**Erasure Coded пул** (k=2, m=1 → size=3, min_size=2; создаются пулы `<name>-data` и `<name>-metadata`):
```bash
pveceph pool create <pool-name> --erasure-coding k=2,m=1
```

**Добавление существующего EC-пула как хранилища:**
```bash
pvesm add rbd ec-storage --pool <replicated-pool> --data-pool <ec-pool>
```

**Удаление пула:**
```bash
pveceph pool destroy <name>
```

**Правило CRUSH по классу дисков (nvme/ssd/hdd):**
```bash
ceph osd crush rule create-replicated nvme-rule default host nvme
ceph osd pool set <pool-name> crush_rule nvme-rule
```

**Метаданные и CephFS:**
```bash
pveceph mds create
pveceph fs create --pg_num 128 --add-storage
# → cephfs (data: cephfs_data / 128 PG; metadata: cephfs_metadata / 32 PG)
```

**Конфигурация через MON DB** (прецеденция выше локального ceph.conf):
```bash
ceph config set osd osd_memory_target 8G
ceph config dump
ceph config get mon osd_pool_default_erasure_code_profile
```

**PG Autoscaler:**
```bash
ceph mgr module enable pg_autoscaler
ceph osd pool set <pool-name> pg_autoscale_mode warn|on|off
```

### Подключение внешнего Ceph-кластера

Для Ceph-кластера, не управляемого локальным PVE, при добавлении RBD-хранилища укажите адреса мониторов и keyring:

```bash
pvesm add rbd external-ceph --monhost 10.0.0.1,10.0.0.2,10.0.0.3 \
  --pool <pool-name> --keyring /etc/pve/priv/ceph/external-ceph.keyring
```

Keyring для внешнего кластера размещается в `/etc/pve/priv/ceph/<storage_id>.keyring` (для гиперконвергентного кластера это делается автоматически).

### Настройка NFS-сервера на стороне хранилища

Пример минимальной конфигурации на сервере хранилища (Debian/TrueNAS):

```bash
# Установка
apt install nfs-kernel-server -y

# /etc/exports
/mnt/pve 10.0.0.0/24(rw,sync,no_subtree_check,no_root_squash)

# Применение
exportfs -ra
showmount -e
# → Export list for host: /mnt/pve 10.0.0.0/24
```

На стороне PVE:
```bash
pvesm add nfs shared-nfs --server 10.0.0.50 --export /mnt/pve \
  --content images,iso,backup
```

> Используйте NFS v4.1 и выше. Снапшоты на NFS (qcow2) выполняются при выключенной VM для больших дисков.

### Настройка iSCSI Target (LIO)

Минимальный пример на стороне storage-сервера (Linux targetcli):

apt install targetcli-fb -y

На хосте PVE LUN подключается через `iscsiadm`, как описано в **[iSCSI + Proxmox VE](../Linux/Networking/iSCSI/iscsi_proxmox.md)**.

### Создание ZFS пула с учетом параметров

```bash
# Пример: пул на 2x NVMe с учетом ashift, compression, recordsize
zpool create -o ashift=12 \
            -o atime=off \
            -O compression=lz4 \
            -O recordsize=64K \
            -O xattr=sa \
            -O acltype=posixacl \
            tank mirror /dev/nvme0n1 /dev/nvme1n1

# Создание datasets для разных типов данных
zfs create tank/vm
zfs set mountpoint=/tank/vm tank/vm
zfs create tank/backup
zfs set recordsize=1M tank/backup
```

### Настройка Storage Replication

```bash
# 1. На ноде-источнике: создание задания репликации
pvesr create my-job \
  --source local-zfs \
  --target node2:local-zfs \
  --vmid 100 \
  --type sync \
  --schedule "*/15"

# 2. Проверка статуса
pvesr status
# → JobID: my-job, State: running, Next: ...

# 3. Принудительный запуск
pvesr run my-job
```

> Replication работает только с ZFS. Для HA без Shared Storage включите replication на все VM, которые должны работать после отказа узла.

### Миграция VM между хранилищами

```bash
# Offline миграция (диск копируется)
qm migrate 100 node2 --targetstorage local-nfs --online 0

# Online миграция (требует Shared Storage)
qm migrate 100 node2 --targetstorage shared-nfs --online 1
```

При отсутствии Shared Storage используйте Storage Replication + `pvecm expected` для перезапуска на другом узле.

### Очистка неиспользуемых (orphaned) дисков

```bash
# Поиск дисков, не подключенных ни к одной VM/LXC
pvesm path local:vm-100-disk-0
ls -la /var/lib/vz/images/100

# Удаление неиспользуемого диска
qm set 100 --delete unused0
pvesm free local:vm-100-disk-0
```

## Диагностика и обслуживание

### Проблемы с производительностью (IO Delay)

Высокий "IO Delay" в GUI указывает на ожидание узлом дисковых операций.
1. Проверьте статус ZFS/Ceph: `zpool status` или `pveceph status` (ищите `HEALTH_*`).
2. Проверьте нагрузку на диски: `iostat -x 1`.
3. Убедитесь, что LVM-Thin пул не заполнен на 100% (это блокирует запись всех VM).
4. Для Ceph: `ceph osd df tree` — проверьте перекос загрузки между OSD и уровень заполнения относительно `nearfull_ratio` (по умолчанию 85%).

### Переполнение хранилища

- Тонкое выделение (qcow2, LVM-Thin, Ceph RBD) позволяет создавать диски больше физического объема — при исчерпании места **все гости** на этом хранилище получают ошибки I/O, что может привести к повреждению файловых систем.
- При заполнении Ceph-пулов до `nearfull`/`full` блокируется запись в кластер в целом. Контролируйте заполнение и оставляйте запас для восстановления (recovery/backfill).

### Мониторинг состояния Ceph

```bash
ceph -s                       # общий статус и health
ceph versions                 # версии демонов
ceph osd df tree              # заполнение и распределение OSD
ceph osd tree                 # топология и классы дисков
ceph config dump              # конфигурация в MON DB
```

Совместно с общесистемными метриками (`ceph-exporter`, Prometheus) — см. **[Администрирование Ceph — Обзор](../Kubernetes/Storage/Ceph/Administration/index.md)**.

### Восстановление после сбоя диска

1. Выполните `ceph osd out <id>` — данные начнут перераспределяться на здоровые OSD.
2. Дождитесь завершения ребалансировки (в малых кластерах это может занять длительное время — риск повторного отказа диска в период восстановления).
3. Замените диск, при необходимости затрите его `ceph-volume lvm zap /dev/sdX --destroy` и создайте новый OSD `pveceph osd create /dev/sdX`.

### Capacity Planning и мониторинг хранилищ

**Ключевые метрики для планирования:**
- **Свободное место**: для LVM-Thin и тонких qcow2 оставляйте запас минимум 20% от общего размера пула. Для Ceph — не менее 15–20% свободного места на пул (для recovery/backfill).
- **IOPS**: оцените нагрузку на диски (`iostat -xmt 1`). Для HDD — 80–120 IOPS на диск, для SATA SSD — 5 000–10 000, для NVMe — 50 000–200 000.
- **Пропускная способность**: учитывайте сеть для NFS/iSCSI/Ceph (10 Гбит/с минимум для Ceph).
- **Retention**: для PBS учитывайте коэффициент дедупликации (обычно 3–10x). Для ZFS snapshots — оценка роста данных за период retention.

**Пороги алертов:**
- `>80%` заполнения любого пула — warning
- `>90%` заполнения — critical, готовность к отказу
- Ceph `nearfull_ratio` (85%) и `full_ratio` (95%) — встроенные пороги
- IO delay `>50ms` — warning, `>200ms` — critical

### Лучшие практики

1. **ZFS по умолчанию для локальных VM**: используйте ZFS вместо Directory/LVM для production — снапшоты, compression, checksums, Storage Replication.
2. **Отдельный пул для ISO/backup**: создавайте отдельные datasets с `recordsize=1M` для файловых хранилищ, чтобы не фрагментировать пул VM.
3. **SSD кэш для HDD-пулов**: если используете HDD для больших объемов, добавьте отдельный SSD-пул для L2ARC и SLOG.
4. **Не превышайте 100–150 PG на OSD**: перегруженный OSD замедляет восстановление и увеличивает нагрузку на MON.
5. **Мониторинг фрагментации**: для Directory-хранилищ с qcow2 используйте `qemu-img check` и конвертируйте в `qcow2` с `-o cluster_size=64K`.
6. **Бэкап storage.cfg**: храните `/etc/pve/storage.cfg` в системе контроля версий или регулярно копируйте на PBS.
7. **Политика prune-backups**: настройте политику хранения для каждого PBS-хранилища, чтобы избежать неконтролируемого роста.
8. **Тестирование восстановления**: периодически проверяйте восстановление из PBS и перезапуск VM после эмуляции отказа узла.
9. **Отдельная сеть для Ceph**: выделите физическую сеть 10+ Гбит/с только для Ceph, не смешивайте с пользовательским трафиком.
10. **Документация схемы**: ведите актуальную схему пулов, OSD, CRUSH правил и replication job'ов.

### Граничные случаи и ограничения

- **LVM-Thin pool full**: при 100% заполнении пул переходит в режим только чтения. Восстановление: удалите снапшоты или расширьте пул. Автоматическое расширение thin pool не предусмотрено.
- **Ceph full/nearfull**: при `full` запись блокируется. Восстановление: настройте `full_ratio` и `nearfull_ratio` или удалите неиспользуемые снапшоты/образы. `ceph osd set norebalance` может помочь при восстановлении места.
- **ZFS pool degraded**: при отказе диска pool переходит в `DEGRADED`. Замена диска: `zpool replace poolname olddisk newdisk`. Ditto-блоки ускоряют resilver.
- **Stale NFS mount**: при падении сервера NFS mount может зависнуть. Используйте опции `hard,intr,timeo=14` и `systemd automount` или `autofs`.
- **iSCSI session failure**: потеря пути приводит к зависанию VM. Используйте multipath и `dev_loss_tmo=30` в `iscsiadm`.
- **Mixed disk sizes в RAIDZ**: эффективный размер пула ограничен наименьшим диском. При расширении RAIDZ добавление дисков другого размера может потребовать пересоздания пула.
- **PG stuck**: при долгой ребалансировке PG могут застрять в состоянии `active+remapped`. Проверьте `ceph pg stat` и `ceph pg <pgid> query`. Иногда помогает `ceph pg repair`.
- **Storage Replication и snapshots**: replication копирует только последний snapshot. При удалении промежуточных снапшотов на источнике репликация может не успеть завершиться и потребовать полной синхронизации.
- **qcow2 на NFS**: большие диски (>500 ГБ) с тонким выделением на NFS работают медленно из-за фрагментации и отсутствия fallocate на многих NAS. Для production используйте iSCSI или Ceph RBD.
- **Изменение hostname узла**: после создания кластера hostname ноды не должен меняться. При изменении hostname pmxcfs перестает корректно работать, и узел нужно удалять из кластера и заново добавлять.
