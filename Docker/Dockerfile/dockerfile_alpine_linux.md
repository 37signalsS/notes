# Alpine Linux в Docker

## Определения

**Alpine Linux** — минималистичный, безопасный и легковесный дистрибутив для Docker-контейнеров.

## Основные концепции

### Преимущества

- **Малый размер образа:** Alpine-образы значительно меньше аналогов на базе Debian или Ubuntu, что ускоряет загрузку и развертывание.
- **Повышенная безопасность:** Минимальный набор предустановленных пакетов уменьшает поверхность атаки.

### Ключевые отличия

- **Стандартная библиотека C:** Alpine использует `musl libc`, а не `glibc` (стандарт для большинства дистрибутивов). `musl` легче, но не полностью совместим с `glibc`.
  - **Последствия:** Бинарные файлы, скомпилированные с `glibc`, не запустятся в Alpine. Пакеты для языков программирования (Python, Node.js) с C-расширениями могут потребовать перекомпиляции во время сборки образа.
- **Инструменты:** Alpine использует `BusyBox` (набор урезанных Unix-утилит) и оболочку `ash` вместо `bash`. Может потребоваться адаптация скриптов.

### Виртуальные пакеты (`.build-deps`)

**Виртуальные пакеты** — временные группы пакетов, которые можно установить для выполнения задачи (например, компиляции), а затем удалить одной командой. Ключевой паттерн для сохранения минимального размера итогового образа.

Подробное сравнение библиотек: **[Glibc vs Musl](../../Linux/Core/glibc_vs_musl.md)**.

## Практические сценарии

### Сценарий 1: Установка и удаление зависимостей для сборки

Классический пример использования виртуального пакета `.build-deps` для компиляции Python-зависимостей.

```dockerfile
FROM python:3.13-alpine

WORKDIR /app

COPY requirements.txt .

# 1. Устанавливаем зависимости для сборки как виртуальный пакет
RUN apk add --no-cache --virtual .build-deps gcc musl-dev libxml2-dev libxslt-dev && \
    # 2. Используем их для установки Python-пакетов
    pip install --no-cache-dir -r requirements.txt && \
    # 3. Удаляем весь виртуальный пакет вместе с зависимостями
    apk del .build-deps

COPY . .

CMD ["python", "app.py"]
```

**Процесс:**

1. `apk add --virtual .build-deps ...` — создает временную группу `.build-deps` с компиляторами и библиотеками.
2. `pip install ...` — компилирует и устанавливает пакеты.
3. `apk del .build-deps` — полностью удаляет временную группу, очищая образ от ненужных на этапе выполнения файлов.

### Сценарий 2: Условная установка зависимостей

Паттерн позволяет использовать один Dockerfile для production и разработки, управляя зависимостями через аргументы сборки (`ARG`).

```dockerfile
# Определяем аргументы для временных и постоянных сборочных зависимостей
ARG BUILD_DEPS
ARG TEMP_BUILD_DEPS

# Устанавливаем постоянные зависимости, если они переданы
RUN if [ -n "$BUILD_DEPS" ]; then \
      apk add --no-cache $BUILD_DEPS; \
    fi

# Устанавливаем временные зависимости как виртуальную группу, если они переданы
RUN if [ -n "$TEMP_BUILD_DEPS" ]; then \
      apk add --no-cache --virtual .build-deps $TEMP_BUILD_DEPS; \
    fi

# ... (команды, использующие зависимости, например, компиляция) ...

# Удаляем временные зависимости, если они были установлены
RUN if [ -n "$TEMP_BUILD_DEPS" ]; then \
      apk del .build-deps; \
    fi
```

**Примеры сборки:**

```sh
# Сборка для production (без доп. пакетов)
docker build .

# Сборка для разработки (с временной установкой git и curl)
docker build --build-arg TEMP_BUILD_DEPS="git curl" .
```

Команды `if` в `RUN` проверяют, были ли переданы аргументы. Если да, создается виртуальная группа `.build-deps`, которая затем удаляется после использования.
