# Alpine Linux в Docker

## Определения

**Alpine Linux** — минималистичный, ориентированный на безопасность дистрибутив Linux, основанный на `musl libc` и `BusyBox`. Благодаря крайне малому размеру (около 5–7 МБ для базового образа) является стандартом де-факто для создания компактных Docker-контейнеров.

## Базовые концепции

### Преимущества использования

- **Минимальный размер:** Уменьшает время сборки, загрузки и развертывания образов.
- **Безопасность:** Минимальный набор предустановленных компонентов и утилит сокращает поверхность атаки.
- **Быстрый запуск:** Легковесность дистрибутива обеспечивает мгновенный старт контейнеров.

### Ключевые компоненты и отличия

- **Стандартная библиотека C (musl libc):** В отличие от большинства дистрибутивов, использующих `glibc`, Alpine базируется на `musl`. Это делает систему легче, но может вызывать проблемы совместимости с бинарными файлами, скомпилированными под `glibc`. Подробнее: **[Glibc vs Musl](../../Linux/Core/glibc_vs_musl.md)**.
- **BusyBox:** Объединяет крошечные версии многих стандартных Unix-утилит в один исполняемый файл.
- **Оболочка ash:** По умолчанию в Alpine используется `ash` (Almquist shell), которая является более легковесной заменой `bash`. Скрипты, использующие "башизмы", могут потребовать адаптации.
- **Менеджер пакетов apk:** Использует собственный менеджер пакетов `apk` (Alpine Package Keeper).

### Управление пакетами (apk)

- **`apk add`** — установка пакетов.
- **`--no-cache`** — флаг, позволяющий устанавливать пакеты без сохранения индекса на диске. Это избавляет от необходимости выполнять `rm -rf /var/cache/apk/*` и уменьшает размер образа.
- **Виртуальные пакеты (`.build-deps`)** — механизм группировки пакетов (например, компиляторов и заголовочных файлов), необходимых только на этапе сборки. После использования вся группа удаляется одной командой.

## Практические сценарии

### Сценарий 1: Оптимизированная установка зависимостей сборки

Использование виртуальных пакетов для установки инструментов компиляции Python-пакетов с последующей очисткой.

```dockerfile
FROM python:3.13-alpine

WORKDIR /app

COPY requirements.txt .

# 1. Устанавливаем зависимости для сборки как виртуальный пакет .build-deps
RUN apk add --no-cache --virtual .build-deps \
        gcc \
        musl-dev \
        libxml2-dev \
        libxslt-dev \
    && \
    # 2. Используем их для компиляции и установки Python-пакетов
    pip install --no-cache-dir -r requirements.txt && \
    # 3. Удаляем всю группу .build-deps одним действием
    apk del .build-deps

COPY . .

CMD ["python", "app.py"]
```

### Сценарий 2: Условная установка пакетов через ARG

Позволяет гибко управлять составом образа (например, добавлять инструменты отладки только в dev-сборки).

```dockerfile
FROM alpine:3.21

# Аргументы для постоянных и временных зависимостей
ARG BUILD_DEPS
ARG TEMP_BUILD_DEPS

# Установка постоянных системных зависимостей
RUN if [ -n "$BUILD_DEPS" ]; then \
      apk add --no-cache $BUILD_DEPS; \
    fi

# Установка временных зависимостей сборки (виртуальная группа)
RUN if [ -n "$TEMP_BUILD_DEPS" ]; then \
      apk add --no-cache --virtual .build-deps $TEMP_BUILD_DEPS; \
    fi

# ... Выполнение операций сборки ...

# Очистка временных зависимостей
RUN if [ -n "$TEMP_BUILD_DEPS" ]; then \
      apk del .build-deps; \
    fi
```

**Команды сборки:**

- `docker build --build-arg TEMP_BUILD_DEPS="git curl" .` — сборка с временными инструментами.
- `docker build .` — стандартная сборка без дополнительных пакетов.
