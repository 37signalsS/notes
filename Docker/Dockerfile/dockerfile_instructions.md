# Dockerfile Instructions

This document provides detailed explanations of individual Dockerfile instructions.

## Основные инструкции Dockerfile

#### FROM

Определяет базовый образ для сборки нового образа. Для повышения безопасности от подмены образа (например, на Docker Hub) рекомендуется указывать хэш образа (`FROM <image>@sha256:<digest>`). Дайджест (хэш) образа можно получить из вывода команды `docker pull my-image:tag`.

Если тег не указан (например, `FROM debian`), Docker по умолчанию использует тег `latest`. **Важно:** При изменении образа, на который указывает тег `latest`, образ будет пересобираться.

#### MAINTAINER (Устаревшая инструкция)

Инструкция `MAINTAINER` использовалась для указания автора образа.

```dockerfile
FROM ubuntu:14.04
MAINTAINER "Вася Пупкин <vasya@example.com>"
RUN apt-get update
```

**Важно:** Эта директива была помечена как устаревшая (`deprecated`) в Docker-версии 1.13 и её использование не рекомендуется. Причина в том, что `MAINTAINER` была слишком специфичной и позволяла указать только автора.

#### LABEL

Используется для добавления метаданных (меток) к образу. Это современный и гораздо более гибкий подход по сравнению с `MAINTAINER`. `LABEL` позволяет добавлять любую информацию в формате `ключ-значение`, что помогает в автоматизации, управлении и отслеживании образов.

**Пример правильного использования метаданных:**

```dockerfile
FROM ubuntu:22.04
LABEL maintainer="vasya@example.com"
LABEL version="1.0.0"
LABEL description="Мой крутой микросервис"
LABEL org.opencontainers.image.source="https://github.com/vasya/my-app"
```

**Зачем это нужно?**
Когда в production-среде работает множество контейнеров, метаданные становятся критически важными. Они позволяют быстро определить автора, версию, исходный код и другую информацию об образе, что особенно ценно при инцидентах. Многие CI/CD-системы и сканеры безопасности также используют эти метки для автоматизации своих процессов.

#### ARG и ENV

- **`ARG` (переменная времени сборки):**
  - Доступна **только** в процессе сборки образа (`docker build`).
  - Не сохраняется в конечном образе и недоступна для запущенного контейнера.
  - Используется для параметризации сборки: передачи версий, токенов или для включения отладочных инструментов.
  - Пример:
    ```dockerfile
    ARG APP_VERSION=1.0
    RUN echo "Собирается версия: $APP_VERSION"
    ```
    Переопределить значение можно командой: `docker build --build-arg APP_VERSION=2.1 .`

- **`ENV` (переменная среды выполнения):**
  - Устанавливает переменные окружения, которые доступны как во время сборки, так и внутри запущенного контейнера.
  - Сохраняется в образе.
  - Используется для конфигурации приложения: URL базы данных, порты, ключи API.
  - Пример:
    ```dockerfile
    ENV DB_HOST=localhost
    CMD ["echo", "Подключение к $DB_HOST"]
    ```
    Переопределить значение можно командой: `docker run -e DB_HOST=db.example.com my-image`

**Совместное использование:**
Часто `ARG` используют для установки значения `ENV` по умолчанию.
```dockerfile
ARG APP_PORT=8080
ENV PORT=${APP_PORT}
EXPOSE ${PORT}
```

#### ENV PYTHONUNBUFFERED=1

Эта инструкция особенно важна для Python-приложений. По умолчанию Python буферизирует потоки `stdout` и `stderr`. Это означает, что данные, выводимые вашим приложением (например, через `print()`), не сразу появляются в логах Docker. Они накапливаются в буфере и выводятся только при его заполнении или при завершении процесса.

Установка `ENV PYTHONUNBUFFERED=1` отключает эту буферизацию, и все выводы сразу направляются в логи контейнера. Это критически важно для отладки, так как позволяет видеть логи в реальном времени.

#### RUN

Определяет команду, которая будет выполнена во время сборки образа, создавая новый слой.

- **Надежные скрипты с `set -ex` при написании многострочных `RUN` команд**
  ```dockerfile
  RUN set -ex && \
      apt-get update && \
      apt-get install -y curl && \
      rm -rf /var/lib/apt/lists/*
  ```
  *   `set -e`: **Exit Immediately.** Если какая-либо команда завершится с ошибкой (ненулевым кодом выхода), выполнение всей `RUN` инструкции немедленно прекратится. Без этого флага Docker продолжит выполнение следующих команд, как будто ничего не произошло, и сборка может успешно завершиться, скрыв проблему.
  *   `set -x`: **Print Commands.** Перед выполнением каждой команды она будет напечатана в лог сборки. Это помогает четко видеть, какая именно команда выполняется в данный момент и какие у нее аргументы, что неоценимо при отладке.

- **Кэширование зависимостей:**
  `--mount=type=cache` позволяет монтировать кэш в процессе выполнения `RUN`. Это ускоряет повторные сборки, так как зависимости будут взяты из кэша, хранящегося на хосте. Кэш не попадает в финальный образ, но доступен для повторного использования.
  ```dockerfile
  RUN --mount=type=cache,target=/root/.cache/pip \
      pip install -r requirements.txt
  ```

- **Bind mounts при сборке:**
  `--mount=type=bind` позволяет монтировать директорию или файл с хостовой системы в контейнер во время выполнения команды `RUN`. В отличие от `COPY`, данные не копируются в образ, а временно подключаются с хоста для процесса сборки.
  ```dockerfile
  RUN --mount=type=bind,source=./src,target=/app/src \
      go build -o app ./src
  ```

- **Работа с секретами:**
  `--mount=type=secret` временно монтирует секрет с хоста и не хранит его в финальном образе.
  ```dockerfile
  RUN --mount=type=secret,id=ssh,target=/root/.ssh/id_rsa \
      git clone git@github.com:user/repo.git .
      
  RUN --mount=type=secret,id=api_key,target=/run/secrets/api_key \
      export API_KEY=$(cat /run/secrets/api_key) && \
      pip install --extra-index-url "$API_KEY"@private-repo.com/packages some-package
  ```

#### COPY и ADD

Обе инструкции служат для копирования файлов в образ, но имеют ключевые различия.

*   **`COPY`**:
    *   **Назначение:** Простое копирование файлов и директорий из контекста сборки в файловую систему контейнера.
    *   **Пример:** `COPY ./app.py /app/`

*   **`ADD`**:
    *   **Возможности:** Включает в себя всю функциональность `COPY`, но с двумя дополнительными возможностями:
        1.  **Загрузка по URL:** Может скачивать файлы из интернета (`ADD http://example.com/file /dest/`).
        2.  **Распаковка архивов:** Автоматически распаковывает локальные архивы в форматах `tar`, `gzip`, `bzip2` или `xz` в директорию назначения (`ADD archive.tar.gz /dest/`).
    *   **Риски:** Автоматическая распаковка и загрузка по URL могут приводить к непредсказуемым результатам и создавать угрозы безопасности.

> **Лучшая практика (Best Practice):**
> Официальная документация Docker рекомендует **всегда отдавать предпочтение `COPY`**, если вам не требуется дополнительная функциональность `ADD`. `COPY` более прозрачен и предсказуем. Для загрузки и распаковки файлов лучше использовать явные команды в инструкции `RUN`, например, `RUN curl -SL ... | tar -xz`. Это делает `Dockerfile` более читаемым и безопасным.

#### WORKDIR

Устанавливает текущий рабочий каталог для всех последующих инструкций `RUN`, `CMD`, `ENTRYPOINT`, `COPY` и `ADD`. Если каталог не существует, он будет создан.

#### EXPOSE

Инструция `EXPOSE` информирует Docker о том, что контейнер прослушивает указанные сетевые порты во время выполнения. Важно понимать, что `EXPOSE` — это исключительно **декларативная** инструкция (не открывает и не публикует порты). Она выполняет две функции:

1.  **Документация:** Служит подсказкой для пользователя, который будет запускать образ, о том, какие порты предназначены для публикации.
2.  **Автоматическая публикация:** При использовании флага `-P` (публикация всех *exposed* портов) в команде `docker run`, Docker использует эту информацию для автоматического проброса портов на случайные порты хоста.

#### VOLUME

Директива `VOLUME` в Dockerfile позволяет прямо в образе указать, что и куда монтировать, обеспечивая автоматическое создание и управление томами для персистентности данных. Это декларативная инструкция, которая сообщает Docker о том, что указанный путь внутри контейнера должен быть внешним томом.

**Синтаксис:**
```dockerfile
VOLUME /path/to/directory/inside/container
```
Или для нескольких точек монтирования:
```dockerfile
VOLUME ["/path1", "/path2"]
```

**Примеры использования:**
-   **Для логов веб-сервера:**
    ```dockerfile
    FROM nginx:alpine
    VOLUME /var/log/nginx
    ```
    Эта директива говорит Docker создать анонимный том с уникальным ID и автоматически примонтировать его к `/var/log/nginx` внутри контейнера. Данные в таком томе переживут смерть и воскрешение контейнера.
-   **Для пользовательских файлов и кеша:**
    ```dockerfile
    FROM node:16
    WORKDIR /app
    VOLUME ["/app/uploads", "/app/cache"]
    ```
    Здесь создаются две точки монтирования для `/app/uploads` и `/app/cache`.

**Важно:** Директива `VOLUME` создает **анонимные тома**, которыми Docker управляет автоматически. Это отличается от `bind mount` (например, через флаг `-v` в `docker run`), где вы вручную указываете, что и куда монтировать. Анонимные тома удобны для стандартизации и "защиты от дурака", так как гарантируют персистентность данных без дополнительных действий пользователя при запуске.

**Зачем это нужно?**
-   **Автоматическая персистентность данных:** Гарантирует, что данные (например, логи, пользовательские загрузки) будут сохраняться независимо от жизненного цикла контейнера, даже если пользователь забыл явно указать тома при запуске.
-   **Стандартизация точек монтирования:** Позволяет стандартизировать, куда должны сохраняться определенные типы данных (например, логи в `/var/log/app`, конфигурации в `/etc/app/`, изображения в `/app/images`). Это упрощает управление множеством однотипных сервисов.
-   **Упрощение оркестрации:** В контексте Docker Compose или Kubernetes, `VOLUME` в Dockerfile работает как значение по умолчанию. Даже если в файле `docker-compose.yml` не прописаны тома, они все равно будут созданы Docker, обеспечивая базовую персистентность.
-   **Изоляция данных от слоя контейнера:** Данные, хранящиеся в томах, не являются частью записываемого слоя контейнера. Это важно при бэкапировании состояния контейнера через `docker export`, так как данные томов не будут включены в экспорт, что позволяет гибко управлять данными и образами отдельно.

Директива `VOLUME` тесно связана с [типами томов в Docker](../../docker_overview.md#Слоеная-файловая-система:-OverlayFS), секцией `volumes` в [Docker Compose](../../Docker_compose/docker_compose_overview.md) и директивой [COPY](./COPY_and_ADD.md) для копирования данных в образ.

В целом, `VOLUME` служит отличной "защитой от дурака", минимизируя количество необходимых флагов или инструкций при запуске контейнера и упрощая рабочие процессы.

#### ENTRYPOINT vs CMD

Эти инструкции `Dockerfile` задают команду, исполняемую при запуске контейнера. 

**Основные правила использования:**
- Должна быть минимум одна из этих инструкций (`CMD` или `ENTRYPOINT`) в `Dockerfile`.
- Если контейнер используется как исполняемый файл (например, утилита), `ENTRYPOINT` должна быть определена.
- Если контейнер запускается с другими аргументами, `CMD` будет переопределена, а аргументы будут добавлены к `ENTRYPOINT`.

**Инструкция CMD:**
Позволяет установить **команду по умолчанию**, которая будет выполняться только тогда, когда вы запускаете контейнер без указания команды. Если контейнер Docker запускается с командой (например, `docker run <image> <команда>`), команда по умолчанию из `CMD` будет игнорироваться. Если `Dockerfile` содержит более одной инструкции `CMD`, все инструкции `CMD`, кроме последней, игнорируются.

`CMD` имеет три формы:
1.  `CMD ["executable","param1","param2"]` (исполняемая форма, предпочтительнее)
2.  `CMD ["param1","param2"]` (устанавливает дополнительные параметры по умолчанию для `ENTRYPOINT` в форме `exec`)
3.  `CMD command param1 param2` (форма оболочки)

**Пример переопределения CMD:**
При запуске `docker run -it <image> /bin/bash`, если в образе есть `CMD`, она будет проигнорирована, и вместо нее будет запущен `/bin/bash`.

**Инструкция ENTRYPOINT:**

Позволяет настроить контейнер, который будет работать как исполняемый файл. Он похож на `CMD` тем, что также позволяет указать команду с параметрами. Ключевая разница заключается в том, что команда `ENTRYPOINT` и ее параметры **не игнорируются**, когда контейнер Docker запускается с параметрами командной строки (в отличие от `CMD`). Вместо этого аргументы, переданные при запуске контейнера, **добавляются** к `ENTRYPOINT`.

**Взаимодействие ENTRYPOINT и CMD:**
`CMD` предоставляет *аргументы по умолчанию* для `ENTRYPOINT`. Это позволяет создавать гибкие образы, где `ENTRYPOINT` определяет основную команду, а `CMD` — параметры по умолчанию для нее, которые легко переопределить.

**Пример взаимодействия:**
```dockerfile
ENTRYPOINT ["/bin/echo", "Hello"]
CMD ["world"]
```
- Когда контейнер запускается командой `docker run -it <image>`, будет произведен вывод: `Hello world` (где `world` — это значение из `CMD`, переданное в `ENTRYPOINT`).
- Когда контейнер запускается командой `docker run -it <image> John`, будет произведен вывод: `Hello John` (где `John` — это аргумент, переданный при запуске, который переопределил `CMD` и был добавлен к `ENTRYPOINT`).

**Краткий ответ:**
`CMD` подставляется после `ENTRYPOINT` при запуске, тем самым позволяя запускать контейнер с настраиваемыми параметрами по умолчанию. То есть, в `ENTRYPOINT` можно передать бинарный файл или основную программу, а в `CMD` — параметры по умолчанию для этой программы. `CMD` может быть легко перетерта аргументами, переданными при запуске контейнера, в то время как `ENTRYPOINT` остается неизменной (если явно не переопределена флагом `--entrypoint`).

**Золотое правило:** `docker-compose.yml` (или `docker run`) всегда имеет приоритет над `Dockerfile`.

1.  `command:` в `compose.yml` (или аргументы в `docker run`) **заменяет** `CMD` из `Dockerfile`.
2.  `entrypoint:` в `compose.yml` (или `--entrypoint` в `docker run`) **заменяет** `ENTRYPOINT` из `Dockerfile`.

| В `Dockerfile` | В `docker-compose.yml` / `docker run` | Что в итоге запустится |
| :--- | :--- | :--- |
| `ENTRYPOINT ["/app/run"]`<br>`CMD ["--default"]` | (ничего не указано) | `/app/run --default`<br>*(Используются оба значения из Dockerfile)* |
| `ENTRYPOINT ["/app/run"]`<br>`CMD ["--default"]` | `command: --prod` | `/app/run --prod`<br>*(**`command` заменил `CMD`**. ENTRYPOINT остался)* |
| `ENTRYPOINT ["/app/run"]` | `entrypoint: /app/debug` | `/app/debug`<br>*(entrypoint заменил ENTRYPOINT. CMD исчез)* |
| `ENTRYPOINT ["/app/run"]`<br>`CMD ["--default"]` | `entrypoint: /app/debug`<br>`command: --verbose` | `/app/g/debug --verbose`<br>*(Заменились и ENTRYPOINT, и CMD)* |

**Практический пример**

Допустим, у вас есть `Dockerfile`:
```dockerfile
FROM alpine:3.20.0
ENTRYPOINT ["ping", "-c", "3"]
CMD ["localhost"]
```
По умолчанию этот контейнер будет пинговать `localhost`.

Теперь в `docker-compose.yml` вы хотите пинговать другой хост:

```yaml
services:
  pinger:
    build: .
    command: google.com
```

Когда вы запустите `docker compose up`, выполнится команда `ping -c 3 google.com`, потому что `command: google.com` из `compose.yml` заменил `CMD ["localhost"]` из `Dockerfile`.

**Запуск приложений в режиме Foreground:**

Ключевой практикой в Docker является запуск основного процесса в режиме "переднего плана" (foreground), а не в режиме демона (background).

*   **Почему это важно?** Docker отслеживает основной процесс (CMD или ENTRYPOINT), запущенный в контейнере (тот, у которого PID 1). Как только этот процесс завершается, Docker считает, что работа контейнера окончена, и останавливает его.
*   **Что происходит с демонами?** Процесс, запущенный в режиме демона, сразу же отсоединяется от терминала и уходит в фон. Для Docker это выглядит так, как будто основной процесс завершился, и контейнер будет немедленно остановлен.

### Формы записи: Shell vs. Exec

Инструкции `RUN`, `CMD` и `ENTRYPOINT` поддерживают две формы записи: `shell` и `exec`. Выбор между ними критически важен, особенно при работе с минималистичными образами (`distroless`, `scratch`).

*   **Shell-форма:**
    *   **Как выглядит:** `CMD myapp --config prod.yaml`
    *   **Как работает:** Команда выполняется внутри оболочки. Docker оборачивает вашу команду в `/bin/sh -c "..."`.
    *   **Преимущества:** Удобна для простых команд, позволяет использовать переменные окружения (`$VAR`) и другие возможности shell.
    *   **Недостатки:** Требует наличия `/bin/sh` в образе.

*   **Exec-форма:**
    *   **Как выглядит:** `CMD ["/myapp", "--config", "prod.yaml"]` (предпочтительная форма в JSON-массиве).
    *   **Как работает:** Команда запускается напрямую, без оболочки. Docker выполняет системный вызов `execve`, запуская указанный исполняемый файл с переданными аргументами.
    *   **Преимущества:** Работает в любых образах, даже в тех, где нет shell (например, `distroless` или `scratch`). Это более предсказуемый и безопасный способ, так как он избегает проблем с интерпретацией команд оболочкой.
    *   **Недостатки:** Переменные окружения не подставляются автоматически. Если нужна подстановка, необходимо использовать `ENTRYPOINT` со скриптом-оберткой.

**Почему это важно для `distroless` и `scratch` образов?**

В образах `gcr.io/distroless/static` и `FROM scratch` **отсутствует оболочка `/bin/sh`**. Поэтому любая инструкция в shell-форме приведет к ошибке `exec /bin/sh: no such file or directory`.

**Золотое правило:** В минималистичных образах **всегда** используйте `exec`-форму.

#### STOPSIGNAL

Определяет сигнал операционной системы, который будет отправлен основному процессу (PID 1) внутри контейнера при его остановке. По умолчанию Docker отправляет сигнал `SIGTERM` (15), чтобы корректно завершить процесс. Если процесс не завершается после отправки `SIGTERM`, через некоторое время (по умолчанию 10 секунд) Docker отправляет сигнал `SIGKILL` (9), который принудительно завершает процесс.

#### SHELL

Выбор оболочки по умолчанию для выполнения команд в инструкциях `RUN`, `CMD` и `ENTRYPOINT` в формате shell.

#### HEALTHCHECK

Инструкция `HEALTHCHECK` встраивает в образ механизм для проверки работоспособности приложения внутри контейнера. Docker периодически выполняет указанную команду, и на основе ее кода завершения определяет состояние контейнера:

- `0`: `healthy` (здоров)
- `1`: `unhealthy` (нездоров)

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost/ || exit 1
```
