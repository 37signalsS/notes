# Docker Buildx: Мультиплатформенная сборка

## Определения

**Docker Buildx** — это плагин CLI, который расширяет возможности команды `docker build` с помощью движка **BuildKit**. Он позволяет создавать независимые инстансы сборщиков (builders) для различных сценариев, включая сборку образов для нескольких архитектур одновременно.

В современных версиях Docker (начиная с 23.0) стандартная команда `docker build` является алиасом для `docker buildx build`.

## Основные концепции

### Драйверы сборщиков
Выбор драйвера определяет среду исполнения BuildKit и доступный функционал.

1. **`docker` (по умолчанию)**:
   - Интегрирован непосредственно в демон `dockerd`.
   - Использует стандартное хранилище образов (`Docker image store`).
   - **Ограничение**: Не поддерживает мультиархитектурные манифесты локально (требуется включение `containerd image store`).
   - **Ограничение**: Позволяет собирать образ только под одну платформу за один раз.

2. **`docker-container`**:
   - Запускает BuildKit в отдельном контейнере (на базе `moby/buildkit`).
   - Позволяет собирать под несколько платформ одновременно.
   - Поддерживает расширенные функции: экспорт кэша (S3, Registry), генерацию аттестаций.

3. **`kubernetes`**:
   - Запускает инстансы сборщика как поды в кластере Kubernetes.
   - Позволяет масштабировать сборку на ресурсах кластера.

4. **`remote`**:
   - Позволяет подключаться к уже запущенному инстансу BuildKit через TCP или SSH.

### Механизм мультиплатформенности
Для выполнения инструкций «чужой» архитектуры (например, запуск `RUN` для ARM64 на процессоре x86_64) используются:
- **`binfmt_misc`**: Механизм ядра Linux, позволяющий ОС выбирать нужный интерпретатор для запуска бинарных файлов.
- **QEMU**: Эмулирует инструкции целевой архитектуры. В Docker Desktop эмуляторы предустановлены.
- **Native Cross-compilation**: Использование инструментов (Go, Rust, C++), которые поддерживают кросс-компиляцию. Это значительно быстрее эмуляции.

### Управление кэшем
Buildx позволяет экспортировать и импортировать кэш сборки через флаги `--cache-to` и `--cache-from`:
- **`type=inline`**: Кэш встраивается прямо в образ (удобно для Registry).
- **`type=registry`**: Кэш хранится в реестре как отдельный артефакт.
- **`type=local`**: Кэш сохраняется в локальную директорию на хосте.
- **`type=gha`**: Оптимизировано для использования в GitHub Actions.

## Процесс работы с билдерами

### Управление инстансами
По умолчанию используется драйвер `docker`, который имеет ограниченный функционал. Для полноценной работы обычно создается новый билдер:

1. **Создание**: `docker buildx create --name my-builder --driver docker-container --use`
2. **Инициализация**: `docker buildx inspect --bootstrap` (запускает контейнер BuildKit).
3. **Просмотр списка**: `docker buildx ls`
4. **Удаление**: `docker buildx rm my-builder`

## Ограничения и решения хранилища

### Проблема Legacy Store
Историческое хранилище Docker (`/var/lib/docker/`) привязывает один тег к одному Image ID. Оно не умеет хранить «манифест-лист» (указатель на несколько образов разных архитектур) под одним именем.

### Решение 1: Registry
Отправка результата напрямую в реестр с флагом `--push`. Реестр (Docker Hub, GHCR) поддерживает OCI-манифесты и корректно сохраняет все версии образа.

### Решение 2: Containerd Image Store
В настройках Docker можно включить **containerd image store**. Это современное хранилище полностью поддерживает OCI и позволяет сохранять мультиплатформенные образы локально с помощью флага `--load`.

## Встроенные переменные платформы
BuildKit автоматически заполняет набор переменных `ARG` при использовании флага `--platform`:
- `TARGETPLATFORM`: Полное название целевой платформы (например, `linux/arm64`).
- `TARGETOS` / `TARGETARCH` / `TARGETVARIANT`: ОС, архитектура и вариант отдельно.
- `BUILDPLATFORM` / `BUILDOS` / `BUILDARCH`: Данные хоста, на котором идет сборка.

## Практические сценарии

### Сценарий 1: Мультиплатформенная сборка (Go)
Использование кросс-компиляции (быстрее, чем эмуляция через QEMU).

```dockerfile
# syntax=docker/dockerfile:1
# Используем платформу хоста для запуска компилятора
FROM --platform=$BUILDPLATFORM golang:1.23-alpine AS builder

ARG TARGETOS TARGETARCH
WORKDIR /app
COPY . .

# Компилируем под целевую архитектуру
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /app/myapp .

# Финальный образ для целевой платформы
FROM alpine:3.21
COPY --from=builder /app/myapp /usr/local/bin/myapp
CMD ["myapp"]
```
**Команда сборки:**
```bash
docker buildx build --platform linux/amd64,linux/arm64 -t user/app:latest --push .
```

### Сценарий 2: Использование Bake
**Bake** — это высокоуровневый инструмент Buildx для управления сложными сборками через конфигурационные файлы (`docker-bake.hcl`, `docker-compose.yml`).

Пример `docker-bake.hcl`:
```hcl
group "default" {
  targets = ["webapp"]
}

target "webapp" {
  platforms = ["linux/amd64", "linux/arm64"]
  tags = ["user/app:latest", "user/app:v1.0"]
  output = ["type=registry"]
}
```
**Запуск:** `docker buildx bake`

## Дополнительная информация

### Аттестации (SBOM и Provenance)
Buildx позволяет прикреплять к образу данные о его составе (SBOM) и процессе сборки:
```bash
docker buildx build \
  --sbom=true \
  --provenance=mode=max \
  --push -t user/app:v1 .
```

### Полезные команды
- `docker buildx prune`: Очистка кэша сборки билдера.
- `docker buildx stop`: Остановка контейнера сборщика.
- `docker buildx imagetools inspect`: Просмотр манифестов и метаданных образа в реестре.
