# Инструкции Dockerfile: WORKDIR и SHELL

## Определения

**`WORKDIR`** — инструкция Dockerfile, устанавливающая текущий рабочий каталог для всех последующих инструкций `RUN`, `CMD`, `ENTRYPOINT`, `COPY` и `ADD`. Она действует аналогично команде `cd`, но в отличие от нее, эффект `WORKDIR` сохраняется между слоями сборки.

**`SHELL`** — инструкция Dockerfile, позволяющая переопределить оболочку (shell) по умолчанию, которая используется для выполнения команд в формате строки (shell form). Она позволяет использовать альтернативные интерпретаторы (bash, powershell, python, node) для выполнения шагов сборки.

## Рабочая директория: WORKDIR

Инструкция устанавливает контекст выполнения и автоматически создает директорию (аналог `mkdir -p`), если она не существует.

### Синтаксис и подстановка переменных

```dockerfile
# Использование абсолютного пути (рекомендуется)
WORKDIR /app

# Использование переменных окружения
ENV APP_HOME=/opt/myapp
WORKDIR $APP_HOME
```

### Нюансы вложенности и относительных путей

Если вы используете относительный путь, он будет разрешен относительно пути предыдущей инструкции `WORKDIR`.

```dockerfile
WORKDIR /a
WORKDIR b
WORKDIR c
RUN pwd # → /a/b/c
```

> **Важно (Best Practice 2026):** Избегайте накопления относительных путей. Это делает Dockerfile хрупким при рефакторинге. Используйте либо абсолютные пути, либо явную конкатенацию переменных: `WORKDIR $APP_HOME/src`.

### Взаимодействие с правами доступа (BuildKit vs Classic)

Поведение при автоматическом создании директории критично для безопасности:

| Сборщик | Поведение при наличии `USER` | Владелец директории |
| :--- | :--- | :--- |
| **Classic Builder** | Игнорирует текущего пользователя | `root:root` |
| **BuildKit** | Наследует текущего пользователя | Текущий `USER` |

**Рекомендация по безопасности:** Всегда устанавливайте `WORKDIR` до переключения на не-root пользователя или явно задавайте владельца, чтобы избежать ошибок `Permission Denied` при записи данных приложением.

## Оболочка выполнения: SHELL

Инструкция полезна для настройки строгого режима выполнения или использования языков высокого уровня в качестве "оболочки".

### Синтаксис (только Exec-форма)

```dockerfile
SHELL ["executable", "parameters"]
```

### Настройка надежности (pipefail)

В Linux-образах оболочкой по умолчанию является `["/bin/sh", "-c"]`. Она не останавливает выполнение при ошибке в середине конвейера (`pipe`). Для повышения надежности рекомендуется переключаться на `bash` с флагом `pipefail`.

```dockerfile
# Сборка упадет, если упадет любая часть пайпа (например, curl | tar)
SHELL ["/bin/bash", "-o", "pipefail", "-c"]
```

### Кастомные интерпретаторы как SHELL

Вы можете использовать Python или Node.js для выполнения сложной логики сборки без создания отдельных `.sh` файлов.

```dockerfile
# Использование Python для сложных манипуляций
FROM python:3.11-slim
SHELL ["python", "-c"]
RUN """
import os
print(f'Current dir: {os.getcwd()}')
"""
```

> **Ограничение:** При использовании кастомных интерпретаторов стандартные функции оболочки (пайпы `|`, перенаправления `>`) будут недоступны, если они не реализованы в самом языке.

## Практические сценарии

### Сценарий 1: Предсказуемая структура (Variables First)

Использование переменных для управления путями во всех стадиях сборки.

```dockerfile
ENV APP_ROOT=/usr/src/app
WORKDIR $APP_ROOT

# Копирование в текущий WORKDIR
COPY package.json .
RUN npm install
COPY . .
```

### Сценарий 2: PowerShell в Windows-контейнерах

Стандартная оболочка Windows (`cmd`) ограничена. Переключение на PowerShell — стандарт для современных Windows-образов.

```dockerfile
FROM mcr.microsoft.com/windows/servercore:ltsc2022
SHELL ["powershell", "-Command", "$ErrorActionPreference = 'Stop';"]
RUN New-Item -Path 'C:\App' -ItemType Directory
```

### Сценарий 3: Multi-stage и сброс контекста

Помните, что каждая новая стадия (`FROM`) сбрасывает `WORKDIR` в корень (`/`).

```dockerfile
# Stage 1
FROM golang:1.22 AS builder
WORKDIR /build
COPY . .
RUN go build -o app

# Stage 2
FROM alpine
# Сбрасываем в корень явно для чистоты
WORKDIR /app
COPY --from=builder /build/app .
ENTRYPOINT ["./app"]
```

## Дополнительная информация

### Отладка путей

Если вы не уверены, какая директория является текущей, используйте временный слой для проверки:
```bash
docker build --target=check-path -t path-debug .
# В Dockerfile:
# FROM builder AS check-path
# RUN pwd && ls -la
```

### Резюме по использованию
1. **Используйте абсолютные пути** для `WORKDIR`.
2. **Устанавливайте `WORKDIR` до `COPY`**, чтобы упростить пути назначения.
3. **Используйте `SHELL` с `pipefail`** для критических сборок в CI/CD.
4. **Избегайте `RUN cd`**, так как его эффект ограничен одним слоем.
