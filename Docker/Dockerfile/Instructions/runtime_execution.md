# Инструкции Dockerfile: Выполнение Команд При Запуске Контейнера

### Выполнение команд при запуске

#### `ENTRYPOINT` vs `CMD`

Эти инструкции `Dockerfile` задают команду, исполняемую при запуске контейнера.

**Основные правила использования:**

- Должна быть минимум одна из этих инструкций (`CMD` или `ENTRYPOINT`) в `Dockerfile`.
- Если контейнер используется как исполняемый файл (например, утилита), `ENTRYPOINT` должна быть определена.
- Если контейнер запускается с другими аргументами, `CMD` будет переопределена, а аргументы будут добавлены к `ENTRYPOINT`.

**Инструкция CMD:**
Позволяет установить **команду по умолчанию**, которая будет выполняться только тогда, когда вы запускаете контейнер без указания команды. Если контейнер Docker запускается с командой (например, `docker run <image> <команда>`), команда по умолчанию из `CMD` будет игнорироваться. Если `Dockerfile` содержит более одной инструкции `CMD`, все инструкции `CMD`, кроме последней, игнорируются.

`CMD` имеет три формы:

1. `CMD ["executable","param1","param2"]` (исполняемая форма, предпочтительнее)
2. `CMD ["param1","param2"]` (устанавливает дополнительные параметры по умолчанию для `ENTRYPOINT` в форме `exec`)
3. `CMD command param1 param2` (форма оболочки)

**Пример переопределения CMD:**
При запуске `docker run -it <image> /bin/bash`, если в образе есть `CMD`, она будет проигнорирована, и вместо нее будет запущен `/bin/bash`.

**Инструкция ENTRYPOINT:**
Позволяет настроить контейнер, который будет работать как исполняемый файл. Он похож на `CMD` тем, что также позволяет указать команду с параметрами. Ключевая разница заключается в том, что команда `ENTRYPOINT` и ее параметры **не игнорируются**, когда контейнер Docker запускается с параметрами командной строки (в отличие от `CMD`). Вместо этого аргументы, переданные при запуске контейнера, **добавляются** к `ENTRYPOINT`.

**Взаимодействие ENTRYPOINT и CMD:**
`CMD` предоставляет *аргументы по умолчанию* для `ENTRYPOINT`. Это позволяет создавать гибкие образы, где `ENTRYPOINT` определяет основную команду, а `CMD` — параметры по умолчанию для нее, которые легко переопределить.

**Пример взаимодействия:**

```dockerfile
ENTRYPOINT ["/bin/echo", "Hello"]
CMD ["world"]
```

- Когда контейнер запускается командой `docker run -it <image>`, будет произведен вывод: `Hello world` (где `world` — это значение из `CMD`, переданное в `ENTRYPOINT`).
- Когда контейнер запускается командой `docker run -it <image> John`, будет произведен вывод: `Hello John` (где `John` — это аргумент, переданный при запуске, который переопределил `CMD` и был добавлен к `ENTRYPOINT`).

**Краткий ответ:**
`CMD` подставляется после `ENTRYPOINT` при запуске, тем самым позволяя запускать контейнер с настраиваемыми параметрами по умолчанию. То есть, в `ENTRYPOINT` можно передать бинарный файл или основную программу, а в `CMD` — параметры по умолчанию для этой программы. `CMD` может быть легко перетерта аргументами, переданными при запуске контейнера, в то время как `ENTRYPOINT` остается неизменной (если явно не переопределена флагом `--entrypoint`).

#### Формы записи: Shell vs. Exec

Инструкции `RUN`, `CMD` и `ENTRYPOINT` поддерживают две формы записи: `shell` и `exec`. Выбор между ними критически важен, особенно при работе с минималистичными образами (`distroless`, `scratch`).

- **Shell-форма:**
  - **Как выглядит:** `CMD myapp --config prod.yaml`
  - **Как работает:** Команда выполняется внутри оболочки. Docker оборачивает вашу команду в `/bin/sh -c "..."`.
  - **Преимущества:** Удобна для простых команд, позволяет использовать переменные окружения (`$VAR`) и другие возможности shell.
  - **Недостатки:** Требует наличия `/bin/sh` в образе.

- **Exec-форма:**
  - **Как выглядит:** `CMD ["/myapp", "--config", "prod.yaml"]` (предпочтительная форма в JSON-массиве).
  - **Как работает:** Команда запускается напрямую, без оболочки. Docker выполняет системный вызов `execve`, запуская указанный исполняемый файл с переданными аргументами.
  - **Преимущества:** Работает в любых образах, даже в тех, где нет shell (например, `distroless` или `scratch`). Это более предсказуемый и безопасный способ, так как он избегает проблем с интерпретацией команд оболочкой.
  - **Недостатки:** Переменные окружения не подставляются автоматически. Если нужна подстановка, необходимо использовать `ENTRYPOINT` со скриптом-оберткой.

**Почему это важно для `distroless` и `scratch` образов?**

В образах `gcr.io/distroless/static` и `FROM scratch` **отсутствует оболочка `/bin/sh`**. Поэтому любая инструкция в shell-форме приведет к ошибке `exec /bin/sh: no such file or directory`.

**Золотое правило:** В минималистичных образах **всегда** используйте `exec`-форму.

#### Запуск приложений в режиме Foreground

Ключевой практикой в Docker является запуск основного процесса в режиме "переднего плана" (foreground), а не в режиме демона (background).

- **Почему это важно?** Docker отслеживает основной процесс (CMD или ENTRYPOINT), запущенный в контейнере (тот, у которого PID 1). Как только этот процесс завершается, Docker считает, что работа контейнера окончена, и останавливает его.
- **Что происходит с демонами?** Процесс, запущенный в режиме демона, сразу же отсоединяется от терминала и уходит в фон. Для Docker это выглядит так, как будто основной процесс завершился, и контейнер будет немедленно остановлен.
