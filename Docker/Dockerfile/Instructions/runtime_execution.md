# Инструкции Dockerfile: CMD, ENTRYPOINT и USER

## Определения

**`CMD`** — инструкция Dockerfile, задающая команду по умолчанию и/или её аргументы, которые будут выполнены при запуске контейнера, если в командной строке `docker run` не указаны другие аргументы.

**`ENTRYPOINT`** — инструкция, определяющая исполняемый файл, который будет запущен при старте контейнера. Аргументы, переданные при запуске контейнера, не заменяют `ENTRYPOINT`, а добавляются к нему в качестве параметров.

**`USER`** — инструкция, устанавливающая имя пользователя (или UID) и, опционально, группу (или GID), от имени которых будут выполняться все последующие инструкции `RUN`, `CMD` и `ENTRYPOINT`.

## Основные концепции

### Команда запуска: CMD против ENTRYPOINT

Обе инструкции определяют, какой процесс будет запущен внутри контейнера, но они различаются по способу взаимодействия с аргументами командной строки.

- **`CMD`**: Служит для задания параметров по умолчанию. Если пользователь указывает аргументы при вызове `docker run`, инструкция `CMD` полностью игнорируется.
- **`ENTRYPOINT`**: Позволяет настроить контейнер так, чтобы он вел себя как исполняемый файл. Аргументы из командной строки всегда передаются в `ENTRYPOINT`.

**Взаимодействие при совместном использовании:**

Если в Dockerfile указаны обе инструкции, `CMD` используется для задания аргументов по умолчанию для `ENTRYPOINT`.

```dockerfile
ENTRYPOINT ["/bin/echo", "Привет,"]
CMD ["Мир"]
```

- `docker run <image>` → Вывод: `Привет, Мир`
- `docker run <image> Пользователь` → Вывод: `Привет, Пользователь`

**Таблица комбинаций (Exec-форма):**

| ENTRYPOINT | CMD | Итоговая команда |
| :--- | :--- | :--- |
| Не указано | `["cmd", "p1"]` | `cmd p1` |
| `["entry", "p1"]` | Не указано | `entry p1` |
| `["entry", "p1"]` | `["cmd", "p2"]` | `entry p1 cmd p2` |

> **Важно:** В Dockerfile должна быть указана хотя бы одна инструкция — `CMD` или `ENTRYPOINT`. Если инструкция одного типа встречается несколько раз, учитывается только последняя из них.

### Формы записи: Shell и Exec

| Характеристика | Shell-форма | Exec-форма (рекомендуется) |
| :--- | :--- | :--- |
| **Синтаксис** | `CMD команда аргумент` | `CMD ["команда", "аргумент"]` |
| **Оболочка** | Выполняется через `/bin/sh -c` | Выполняется напрямую (execve) |
| **Переменные** | Поддерживает `$VAR` | Не поддерживает подстановку напрямую |
| **Сигналы** | PID 1 получает оболочка (sh) | PID 1 получает само приложение |

**Проблема PID 1 и сигналов:**
При использовании Shell-формы приложение не является процессом с PID 1 и не получает сигнал `SIGTERM` от Docker при остановке. Это приводит к принудительному убийству процесса (`SIGKILL`) через 10 секунд. Всегда используйте **Exec-форму** для корректного завершения (Graceful Shutdown).

В минималистичных образах (например, `scratch` или `distroless`) Shell-форма не работает, так как в них отсутствует `/bin/sh`.

### Инструкция USER: Безопасность выполнения

По умолчанию процессы в контейнере запускаются от имени `root`. Согласно принципу наименьших привилегий, рекомендуется переключаться на непривилегированного пользователя.

**Синтаксис:**

```dockerfile
USER <user>[:<group>]
# Или через числовые ID (рекомендуется для Kubernetes)
USER <UID>[:<GID>]
```

**Особенности:**

- Инструкция `USER` только переключает контекст, но **не создает** пользователя. Пользователь должен быть создан заранее через `RUN useradd` или аналогичные команды.
- Влияет на все последующие инструкции `RUN`, `CMD` и `ENTRYPOINT`.
- При использовании числовых UID Docker не проверяет существование пользователя в `/etc/passwd`.

Подробные рекомендации по созданию безопасных пользователей см. в разделе **[Запуск процессов от непривилегированного пользователя](../Docker_security/container_hardening.md#1-запуск-процессов-от-непривилегированного-пользователя)**.

## Практические сценарии

### Сценарий 1: Веб-сервер Nginx (Foreground)

Docker отслеживает только процесс с PID 1. Если этот процесс завершается (например, уходит в фоновый режим), контейнер останавливается.

```dockerfile
FROM nginx:alpine
# Запуск в фоновом режиме (daemon) приведет к остановке контейнера
# Поэтому используем 'daemon off'
CMD ["nginx", "-g", "daemon off;"]
```

### Сценарий 2: Скрипт-обертка (Entrypoint script)

Используется для предварительной настройки окружения перед запуском основного приложения.

**Dockerfile:**

```dockerfile
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
CMD ["python", "app.py"]
```

**entrypoint.sh (универсальный):**

```bash
#!/bin/sh
# Выполнение подготовительных действий (например, миграций)
echo "Инициализация..."
# Использование exec гарантирует, что приложение заменит shell и получит PID 1
exec "$@"
```

В production-сценариях скрипт часто содержит явные шаги инициализации и запускает приложение напрямую, без делегирования в `CMD`:

```bash
#!/bin/sh
python -c "from app import init_db; init_db()"
exec gunicorn -w 4 -b 0.0.0.0:5000 app:app
```

```dockerfile
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
CMD ["/entrypoint.sh"]
```

Использование `exec` (**exec-форма**) заменяет процесс оболочки на Gunicorn, делая его процессом с PID 1. Это обеспечивает корректную передачу сигналов (SIGTERM) от Docker при остановке контейнера, что необходимо для надежной работы в production.

### Сценарий 3: Переопределение пользователя для Node.js

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY . .
# Создаем пользователя (в Alpine используется adduser)
RUN adduser -D -S appuser && chown -R appuser /app
USER appuser
CMD ["node", "server.js"]
```

### Сценарий 4: ENTRYPOINT для утилит командной строки

Создание образа, который ведет себя как бинарный файл (например, `ping`).

```dockerfile
FROM alpine
ENTRYPOINT ["ping", "-c", "3"]
CMD ["localhost"]
```

- `docker run my-ping` → выполнит `ping -c 3 localhost`
- `docker run my-ping google.com` → выполнит `ping -c 3 google.com`
