# Инструкции Dockerfile: CMD, ENTRYPOINT и USER

## Определения

**`CMD`** — инструкция Dockerfile, задающая команду по умолчанию и/или её аргументы, которые будут выполнены при запуске контейнера, если в командной строке `docker run` не указаны другие аргументы.

**`ENTRYPOINT`** — инструкция, определяющая исполняемый файл, который будет запущен при старте контейнера. Аргументы, переданные при запуске контейнера, не заменяют `ENTRYPOINT`, а добавляются к нему в качестве параметров.

**`USER`** — инструкция, устанавливающая имя пользователя (или UID) и, опционально, группу (или GID), от имени которых будут выполняться все последующие инструкции `RUN`, `CMD` и `ENTRYPOINT`.

## Основные концепции

### Определение версии рантайма перед сборкой

Для корректного выбора базового образа и обеспечения Graceful Shutdown, DevOps-инженеру необходимо определить целевую версию языка программирования на основе файлов в репозитории.

| Язык | Файл манифеста | Где искать версию |
| :--- | :--- | :--- |
| **Java** | `pom.xml`, `build.gradle` | `<java.version>`, `sourceCompatibility` |
| **Node.js** | `package.json`, `.nvmrc` | `"engines"`, содержимое файла |
| **Python** | `pyproject.toml`, `.python-version` | `requires-python`, содержимое файла |
| **Go** | `go.mod` | Строка `go 1.xx` |
| **Ruby** | `.ruby-version`, `Gemfile` | Содержимое файла, строка `ruby "..."` |
| **PHP** | `composer.json` | Секция `"require": { "php": "..." }` |

### Команда запуска: CMD против ENTRYPOINT

Обе инструкции определяют, какой процесс будет запущен внутри контейнера, но они различаются по способу взаимодействия с аргументами командной строки.

- **`CMD`**: Служит для задания параметров по умолчанию. Если пользователь указывает аргументы при вызове `docker run`, инструкция `CMD` полностью игнорируется.
- **`ENTRYPOINT`**: Позволяет настроить контейнер так, чтобы он вел себя как исполняемый файл. Аргументы из командной строки всегда передаются в `ENTRYPOINT`.

**Взаимодействие при совместном использовании:**

Если в Dockerfile указаны обе инструкции, `CMD` используется для задания аргументов по умолчанию для `ENTRYPOINT`.

```dockerfile
ENTRYPOINT ["/bin/echo", "Привет,"]
CMD ["Мир"]
```

- `docker run <image>` → Вывод: `Привет, Мир`
- `docker run <image> Пользователь` → Вывод: `Привет, Пользователь`

**Таблица комбинаций (Exec-форма):**

| ENTRYPOINT | CMD | Итоговая команда |
| :--- | :--- | :--- |
| Не указано | `["cmd", "p1"]` | `cmd p1` |
| `["entry", "p1"]` | Не указано | `entry p1` |
| `["entry", "p1"]` | `["cmd", "p2"]` | `entry p1 cmd p2` |

> **Важно:** В Dockerfile должна быть указана хотя бы одна инструкция — `CMD` или `ENTRYPOINT`. Если инструкция одного типа встречается несколько раз, учитывается только последняя из них.

### Формы записи: Shell и Exec

| Характеристика | Shell-форма | Exec-форма (рекомендуется) |
| :--- | :--- | :--- |
| **Синтаксис** | `CMD команда аргумент` | `CMD ["команда", "аргумент"]` |
| **Оболочка** | Выполняется через `/bin/sh -c` | Выполняется напрямую (execve) |
| **Переменные** | Поддерживает `$VAR` | Не поддерживает подстановку напрямую |
| **Сигналы** | PID 1 получает оболочка (sh) | PID 1 получает само приложение |

**Проблема PID 1 и сигналов:**
При использовании Shell-формы приложение не является процессом с PID 1 и не получает сигнал `SIGTERM` от Docker при остановке. Это приводит к принудительному убийству процесса (`SIGKILL`) через 10 секунд. Всегда используйте **Exec-форму** для корректного завершения (Graceful Shutdown).

В минималистичных образах (например, `scratch` или `distroless`) Shell-форма не работает, так как в них отсутствует `/bin/sh`.

### Инструкция USER: Безопасность выполнения

По умолчанию процессы в контейнере запускаются от имени `root`. Согласно принципу наименьших привилегий, рекомендуется переключаться на непривилегированного пользователя.

**Синтаксис:**

```dockerfile
USER <user>[:<group>]
# Или через числовые ID (рекомендуется для Kubernetes)
USER <UID>[:<GID>]
```

**Особенности:**

- Инструкция `USER` только переключает контекст, но **не создает** пользователя. Пользователь должен быть создан заранее через `RUN useradd` или аналогичные команды.
- Влияет на все последующие инструкции `RUN`, `CMD` и `ENTRYPOINT`.
- При использовании числовых UID Docker не проверяет существование пользователя в `/etc/passwd`.

Подробные рекомендации по созданию безопасных пользователей см. в разделе **[Запуск процессов от непривилегированного пользователя](../Docker_security/container_hardening.md#1-запуск-процессов-от-непривилегированного-пользователя)**.

## Практические сценарии

### Сценарий 1: Веб-сервер Nginx (Foreground)

Docker отслеживает только процесс с PID 1. Если этот процесс завершается (например, уходит в фоновый режим), контейнер останавливается.

```dockerfile
FROM nginx:alpine
# Запуск в фоновом режиме (daemon) приведет к остановке контейнера
# Поэтому используем 'daemon off'
CMD ["nginx", "-g", "daemon off;"]
```

### Сценарий 2: Скрипт-обертка (Entrypoint script)

Используется для предварительной настройки окружения (миграции БД, проверка доступности зависимостей) перед запуском основного процесса.

#### Выбор стратегии: CMD против ENTRYPOINT

Выбор между `CMD` и `ENTRYPOINT` для скрипта-обертки определяет, как контейнер будет реагировать на аргументы запуска.

| Подход | Dockerfile | Результат `docker run <image> bash` |
| :--- | :--- | :--- |
| **Только CMD** | `CMD ["/entrypoint.sh"]` | Запустится `bash`. Скрипт `entrypoint.sh` **не будет выполнен**. |
| **ENTRYPOINT + CMD** | `ENTRYPOINT ["/entrypoint.sh"]`<br>`CMD ["python", "app.py"]` | Запустится `entrypoint.sh bash`. Благодаря `exec "$@"` выполнится инициализация, а затем запустится `bash` вместо приложения. |

**Рекомендуемый подход:** использование `ENTRYPOINT` для скрипта гарантирует, что инициализация будет выполнена всегда, независимо от того, какая команда передана при старте.

#### Пример реализации

**Dockerfile:**

```dockerfile
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh

# Скрипт всегда выполняется первым
ENTRYPOINT ["/entrypoint.sh"]

# Аргументы по умолчанию для скрипта
CMD ["python", "app.py"]
```

**entrypoint.sh (универсальный):**

```bash
#!/bin/sh
set -e # Прекратить выполнение при ошибке

echo "Инициализация окружения..."
# Пример: выполнение миграций
# python manage.py migrate --noinput

# exec "$@" выполняет команду, переданную в CMD или через CLI
# Это позволяет:
# 1. Сохранить PID 1 для основного процесса (обработка сигналов)
# 2. Гибко заменять приложение на shell для отладки
exec "$@"
```

#### Почему это важно:
1. **Предсказуемость:** С `ENTRYPOINT` вы уверены, что контейнер не запустится без необходимой подготовки (например, без пролитых миграций).
2. **Отладка:** Выполняя `docker run -it <image> sh`, вы попадаете в shell внутри уже настроенного окружения, так как `entrypoint.sh` отработал и передал управление в `sh` через `exec "$@"`.
3. **Graceful Shutdown:** Использование `exec` заменяет процесс оболочки (`entrypoint.sh`) на целевой процесс, сохраняя за ним PID 1. Это критично для корректной обработки сигналов `SIGTERM`.

В простых сценариях, где инициализация не требуется, можно запускать приложение напрямую через `CMD`. Но для сложных production-систем связка `ENTRYPOINT + CMD` является индустриальным стандартом.
### Сценарий 3: Создание системного пользователя

Запуск от `root` — одна из главных уязвимостей. Рекомендуется создавать системного пользователя. **Важно:** синтаксис команды `adduser` различается в зависимости от базового образа.

#### Вариант А: Debian / Ubuntu (Shadow-utils)

```dockerfile
# --system: создание системного пользователя
# --group: создание группы с тем же именем
RUN adduser --system --group appuser

USER appuser
```

#### Вариант Б: Alpine Linux (BusyBox)

```dockerfile
# -S: создание системного пользователя (System)
# -G: добавление в группу (необязательно, если группа не создана отдельно)
RUN adduser -S appuser

USER appuser
```

#### Почему это важно:
...
1. **Безопасность:** Параметр `--system` создает пользователя без пароля, домашней директории (по умолчанию) и shell-доступа (зависит от дистрибутива), что минимизирует поверхность атаки.
2. **Предсказуемость в K8s:** Использование числового UID (`USER 1001`) вместо имени позволяет Kubernetes применять `securityContext` без необходимости резолвить имя пользователя внутри образа.
3. **Права на тома:** Фиксированный UID позволяет заранее настроить права доступа на внешние монтируемые директории на хосте.

### Сценарий 4: ENTRYPOINT для утилит командной строки

Создание образа, который ведет себя как бинарный файл (например, `ping`).

```dockerfile
FROM alpine
ENTRYPOINT ["ping", "-c", "3"]
CMD ["localhost"]
```

- `docker run my-ping` → выполнит `ping -c 3 localhost`
- `docker run my-ping google.com` → выполнит `ping -c 3 google.com`

## Проверка и отладка

Для верификации того, какие именно инструкции `ENTRYPOINT` и `CMD` прописаны в образе (или в запущенном контейнере), используется команда `docker inspect`.

### Извлечение данных через jq

Использование `jq` позволяет быстро получить значения в формате JSON-массива (Exec-форма):

```bash
# Проверка ENTRYPOINT
docker inspect <image_name> | jq .[0].Config.Entrypoint

# Проверка CMD
docker inspect <image_name> | jq .[0].Config.Cmd
```

### Использование встроенных фильтров Go Templates

Если `jq` не установлен, можно воспользоваться встроенным механизмом форматирования Docker:

```bash
# Вывод ENTRYPOINT
docker inspect --format='{{json .Config.Entrypoint}}' <image_name>

# Вывод CMD
docker inspect --format='{{json .Config.Cmd}}' <image_name>
```
