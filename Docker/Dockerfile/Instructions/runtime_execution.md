# Инструкции Dockerfile: CMD, ENTRYPOINT и USER

## Определения

**`ENTRYPOINT`** — инструкция, определяющая основной исполняемый файл (процесс), который будет запущен при старте контейнера. Аргументы запуска добавляются к нему в качестве параметров.

**`CMD`** — инструкция, задающая команду или аргументы по умолчанию. Если пользователь передает аргументы при `docker run`, `CMD` полностью игнорируется.

**`USER`** — инструкция, устанавливающая имя пользователя (или UID) и группу (или GID), от имени которых будут выполняться все последующие инструкции сборки и сам процесс в контейнере.

## Основные концепции

### Формы записи: Exec против Shell

Выбор формы записи критически влияет на обработку сигналов и переменные окружения.

| Характеристика | Exec-форма (рекомендуется) | Shell-форма |
| :--- | :--- | :--- |
| **Синтаксис** | `ENTRYPOINT ["exec", "p1"]` | `ENTRYPOINT exec p1` |
| **Запуск** | Напрямую (`execve`) | Через `/bin/sh -c` |
| **PID 1** | Приложение получает PID 1 | Оболочка получает PID 1 |
| **Сигналы** | Получает напрямую | Не получает (блокируются оболочкой) |
| **Переменные** | Не подставляются напрямую | Подставляются оболочкой |

> **Важно:** Всегда используйте **Exec-форму** (JSON-массив) для основных процессов. Это гарантирует корректное завершение приложения (**Graceful Shutdown**) при получении сигнала `SIGTERM`.

### Взаимодействие ENTRYPOINT и CMD

Когда в Dockerfile присутствуют обе инструкции, они образуют «матрицу» параметров: `ENTRYPOINT` становится неизменяемой частью команды (исполняемым файлом), а `CMD` — набором аргументов по умолчанию, которые легко переопределить при запуске.

| ENTRYPOINT | CMD | Итоговая команда |
| :--- | :--- | :--- |
| `["/app"]` | `["--help"]` | `/app --help` |
| `["/app"]` | Не указано | `/app` |
| Не указано | `["/app", "--help"]` | `/app --help` |

> **Graceful Shutdown:** В оркестраторах (например, Kubernetes) при использовании Shell-формы сигнал `SIGTERM` от кублета не дойдет до приложения. Кубернетес подождет (по умолчанию 30с) и принудительно убьет процесс (`SIGKILL`), что может привести к потере данных (особенно в БД) или незавершенным транзакциям.

### Инструкция USER и права доступа

Запуск от `root` (по умолчанию) нарушает принцип наименьших привилегий.

**Особенности:**
- **Числовые UID:** Рекомендуется использовать `USER 1001:1001`. Это позволяет Kubernetes проверять права без доступа к `/etc/passwd` образа (политика `runAsNonRoot`).
- **Создание:** Инструкция только переключает контекст, пользователь должен быть создан заранее через `RUN`.
- **Взаимодействие с WORKDIR:** В BuildKit, если `USER` объявлен до `WORKDIR`, автоматически создаваемая директория будет принадлежать этому пользователю. В классическом сборщике владельцем всегда будет `root`.

### Подготовка: Определение версии рантайма

Перед выбором базового образа (`FROM`) определите целевую версию языка на основе файлов проекта:

| Язык | Файл манифеста | Параметр версии |
| :--- | :--- | :--- |
| **Node.js** | `package.json`, `.nvmrc` | `"engines": { "node": "..." }` |
| **Python** | `pyproject.toml`, `.python-version` | `requires-python`, `python_version` |
| **Go** | `go.mod` | `go 1.xx` |
| **Java** | `pom.xml`, `build.gradle` | `<java.version>`, `sourceCompatibility` |

## Практические сценарии

### Сценарий 1: Entrypoint-скрипт (Паттерн инициализации)

Используется для настройки окружения (миграции, прогрев кэша) перед запуском основного процесса.

**Dockerfile:**
```dockerfile
COPY entrypoint.sh /usr/local/bin/
RUN chmod +x /usr/local/bin/entrypoint.sh
ENTRYPOINT ["entrypoint.sh"]
CMD ["python", "app.py"]
```

**entrypoint.sh:**
```bash
#!/bin/bash
set -e

echo "Выполнение миграций..."
# python manage.py migrate

# exec "$@" заменяет процесс оболочки процессом приложения.
# Это сохраняет PID 1 и позволяет корректно обрабатывать SIGTERM.
exec "$@"
```

### Сценарий 2: Создание системного пользователя (Hardening)

Пример для разных дистрибутивов.

**Debian/Ubuntu:**
```dockerfile
RUN groupadd --system appgroup && \
    useradd --system --gid appgroup --no-create-home --shell /bin/false appuser
USER appuser
```

**Alpine:**
```dockerfile
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
```

### Сценарий 3: Образ-утилита

Создание контейнера, который ведет себя как команда.

```dockerfile
FROM alpine:3.20
RUN apk add --no-cache curl
ENTRYPOINT ["curl", "-s"]
CMD ["https://ifconfig.me"]
```
- `docker run my-curl` → вернет IP.
- `docker run my-curl google.com` → выполнит запрос к Google.

## Дополнительная информация

### Просмотр метаданных запуска

Для проверки того, как сформирован образ, используйте `docker inspect`:

```bash
# Получение ENTRYPOINT и CMD в формате JSON
docker inspect --format='{{json .Config.Entrypoint}} {{json .Config.Cmd}}' <image_id>
```
