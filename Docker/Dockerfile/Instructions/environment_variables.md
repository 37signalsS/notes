# Инструкции Dockerfile: Переменные (ENV и ARG)

## Определения

**`ARG` (Build Argument)** — временная переменная, предназначенная исключительно для процесса сборки образа (`docker build`). Она не сохраняется в итоговом образе, не видна в `docker inspect` и недоступна в рантайме (запущенном контейнере).

**`ENV` (Environment Variable)** — постоянная переменная окружения, доступная как на этапе сборки, так и во время работы контейнера (рантайм). Значения `ENV` жестко записываются в конфигурацию образа (`config.json`), видны в `docker inspect` и наследуются всеми последующими слоями и контейнерами.

## Основные концепции

### Сравнение областей видимости

| Характеристика | ARG | ENV |
| :--- | :--- | :--- |
| **Доступна при сборке (build time)** | Да | Да |
| **Доступна в контейнере (runtime)** | Нет | Да |
| **Видна в `docker inspect`** | Нет | Да |
| **Видна в `docker history`** | Да | Да |

### Инструкция ARG: Область видимости (Scope)

Это критически важный аспект BuildKit в многоэтапных сборках:
1. **Глобальная область (до первого `FROM`):** Переменная доступна только в инструкциях `FROM`. Она не видна внутри этапов сборки.
2. **Область этапа (внутри `FROM` ... `FROM`):** Чтобы использовать глобальный `ARG` или аргумент из командной строки внутри этапа, его нужно объявить повторно внутри этого этапа без значения.

```dockerfile
# Глобальный ARG (виден только для FROM)
ARG BASE_TAG=3.21
FROM alpine:${BASE_TAG}

# Импорт в текущий этап (теперь доступен для RUN)
ARG BASE_TAG
RUN echo "Building on Alpine ${BASE_TAG}"
```

### Паттерн: Проброс ARG в рантайм через ENV

Если значение (например, версия приложения) нужно иметь и при сборке, и внутри работающего контейнера, используется связка:

```dockerfile
ARG APP_VERSION=1.0.0
# Копируем значение ARG в ENV для сохранения в метаданных образа
ENV APP_VERSION=${APP_VERSION}
```

### Инструкция ENV: Конфигурация рантайма

Используется для настройки системных путей, параметров приложения и глобальных флагов.

**Синтаксис:**
```dockerfile
# Рекомендуемая форма (объединение в один слой)
ENV APP_VERSION=1.2.3 \
    APP_HOME=/opt/myapp \
    PATH=${APP_HOME}/bin:${PATH}
```

**Особенности поведения:**
- **Персистентность:** Значения сохраняются в метаданных образа и видны через `docker inspect`.
- **Наследование:** Переменные доступны во всех последующих инструкциях `RUN`, а также при запуске контейнера.
- **Инвалидация кэша:** Изменение значения `ENV` приводит к пересборке всех слоев, расположенных ниже в Dockerfile.

### Инструкция ARG: Параметризация сборки

Позволяет изменять поведение сборки (например, версии пакетов) через флаг `--build-arg`.

**Область видимости в многоэтапных сборках (Scope):**

Это критически важный аспект BuildKit:
1. **Глобальная область (до `FROM`):** Переменная доступна только в инструкциях `FROM`. Она не видна внутри этапов сборки.
2. **Область этапа (после `FROM`):** Чтобы использовать глобальный `ARG` внутри этапа, его нужно объявить повторно без значения.

```dockerfile
# Глобальный ARG (виден только для FROM)
ARG BASE_TAG=3.21
FROM alpine:${BASE_TAG}

# Импорт в текущий этап (теперь доступен для RUN)
ARG BASE_TAG
RUN echo "Building on Alpine ${BASE_TAG}"
```

### Предопределенные переменные BuildKit

BuildKit автоматически пробрасывает набор переменных для кросс-платформенной сборки. Их не нужно объявлять в `ARG` явно.

| Переменная | Описание | Пример |
| :--- | :--- | :--- |
| `TARGETPLATFORM` | Целевая платформа | `linux/amd64` |
| `TARGETOS` | Целевая ОС | `linux` |
| `TARGETARCH` | Целевая архитектура | `arm64` |
| `BUILDPLATFORM` | Платформа хоста сборки | `darwin/arm64` |

### Синтаксис подстановки и экранирование

Docker поддерживает подмножество bash-синтаксиса для интерполяции:

- `${variable:-word}`: если переменная не задана или пуста, использовать `word`.
- `${variable:+word}`: если переменная задана, использовать `word`, иначе пустую строку.
- **Экранирование:** Чтобы использовать литеральный символ `$`, используйте обратный слэш: `\$`.

```dockerfile
ENV LOG_DIR=/var/log
# Результат: "Logs are in /var/log"
RUN echo "Logs are in ${LOG_DIR}"
# Результат: "This costs $100" (без расширения переменной)
RUN echo "This costs \$100"
```

## Безопасность и секреты

| Аспект | ARG | ENV |
| :--- | :--- | :--- |
| **История слоев** | Видна в `docker history` | Видна в `docker history` |
| **Инспекция образа** | **Не видна** | Видна в `docker inspect` |
| **Рекомендация** | **Запрещено** для паролей/ключей | **Запрещено** для паролей/ключей |

**Решение (2026):** Используйте временное монтирование секретов BuildKit, которое не оставляет следов в образе:
`RUN --mount=type=secret,id=api_token API_KEY=$(cat /run/secrets/api_token) ./build.sh`

## Практические сценарии

### Сценарий 1: Управление версиями через ARG

Централизованное управление версиями базовых образов.

```dockerfile
ARG PY_VERSION=3.12
FROM python:${PY_VERSION}-slim AS base

# Переиспользование версии в LABEL
ARG PY_VERSION
LABEL python.version=${PY_VERSION}
```

### Сценарий 2: Гибкие пути через ENV

Использование переменных в инструкциях `WORKDIR` и `COPY`.

```dockerfile
ENV APP_ROOT=/usr/src/app
WORKDIR ${APP_ROOT}

# Подстановка в пути копирования
COPY . ${APP_ROOT}/src
```

### Сценарий 3: Адаптация под архитектуру (BuildKit)

Выполнение специфичных команд в зависимости от целевого процессора.

```dockerfile
FROM alpine
ARG TARGETARCH
RUN if [ "$TARGETARCH" = "arm64" ]; then \
        apk add --no-cache libhook-arm64; \
    fi
```

### Сценарий 4: Обязательные аргументы без значений по умолчанию

Если вы хотите, чтобы сборка падала при отсутствии аргумента, не задавайте ему значение в Dockerfile.

```dockerfile
ARG MANDATORY_TOKEN
# Сборка упадет на этом этапе, если --build-arg MANDATORY_TOKEN=... не передан
RUN test -n "$MANDATORY_TOKEN"
```

## Дополнительная информация

### Приоритеты (Precedence)

При совпадении имен действует следующий приоритет (от высшего к низшему):
1. Инструкция `ENV` внутри Dockerfile (перекрывает `ARG` с тем же именем после точки объявления).
2. Флаг `--build-arg` (для `ARG`).
3. Значение по умолчанию в `ARG`.
