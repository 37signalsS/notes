# Инструкции Dockerfile: Переменные (ENV и ARG)

**Актуально для:** Docker 20.10+, BuildKit v1.4+

## Определения

**`ARG` (Build Argument)** — временная переменная, предназначенная исключительно для процесса сборки образа (`docker build`). Она не сохраняется в итоговом образе, не видна в `docker inspect` и недоступна в рантайме (запущенном контейнере).

**`ENV` (Environment Variable)** — постоянная переменная окружения, доступная как на этапе сборки, так и во время работы контейнера (рантайм). Значения `ENV` жестко записываются в конфигурацию образа (`config.json`), видны в `docker inspect` и наследуются всеми последующими слоями и контейнерами.

## Основные концепции

### Жизненный цикл переменных

Понимание жизненного цикла `ARG` и `ENV` критически важно для отладки сборки и обеспечения безопасности:

| Этап | ARG | ENV |
| :--- | :--- | :--- |
| **Сборка (build time)** | Доступна в `FROM` и `RUN` | Доступна в `RUN`, `COPY`, `ADD` |
| **Рантайм (runtime)** | **Недоступна** | Доступна в `CMD`, `ENTRYPOINT`, приложении |
| **docker inspect** | Не видна | Видна в `.Config.Env` |
| **docker history** | Видна (если использовалась в `RUN`) | Видна (в слое с `ENV`) |
| **Слои образа** | Не сохраняется | Сохраняется в метаданных образа |

**Ключевое следствие для SRE:** При аудите образов переменные `ENV` всегда доступны для инспекции, в то время как `ARG` исчезают после сборки. Это определяет, какие данные можно хранить в каждом типе переменной.

### Сравнение областей видимости

| Характеристика | ARG | ENV |
| :--- | :--- | :--- |
| **Доступна при сборке (build time)** | Да | Да |
| **Доступна в контейнере (runtime)** | Нет | Да |
| **Видна в `docker inspect`** | Нет | Да |
| **Видна в `docker history`** | Да | Да |

### Инструкция ARG: Область видимости (Scope)

Это критически важный аспект BuildKit в многоэтапных сборках:
1. **Глобальная область (до первого `FROM`):** Переменная доступна только в инструкциях `FROM`. Она не видна внутри этапов сборки.
2. **Область этапа (внутри `FROM` ... `FROM`):** Чтобы использовать глобальный `ARG` или аргумент из командной строки внутри этапа, его нужно объявить повторно внутри этого этапа без значения.

```dockerfile
# Глобальный ARG (виден только для FROM)
ARG BASE_TAG=3.21
FROM alpine:${BASE_TAG}

# Импорт в текущий этап (теперь доступен для RUN)
ARG BASE_TAG
RUN echo "Building on Alpine ${BASE_TAG}"
```

### Паттерн: Проброс ARG в рантайм через ENV

Если значение (например, версия приложения) нужно иметь и при сборке, и внутри работающего контейнера, используется связка:

```dockerfile
ARG APP_VERSION=1.0.0
# Копируем значение ARG в ENV для сохранения в метаданных образа
ENV APP_VERSION=${APP_VERSION}
```

### Инструкция ENV: Конфигурация рантайма

Используется для настройки системных путей, параметров приложения и глобальных флагов.

**Синтаксис:**
```dockerfile
# Рекомендуемая форма (объединение в один слой)
ENV APP_VERSION=1.2.3 \
    APP_HOME=/opt/myapp \
    PATH=${APP_HOME}/bin:${PATH}
```

**Особенности поведения:**
- **Персистентность:** Значения сохраняются в метаданных образа и видны через `docker inspect`.
- **Наследование:** Переменные доступны во всех последующих инструкциях `RUN`, а также при запуске контейнера.
- **Инвалидация кэша:** Изменение значения `ENV` приводит к пересборке всех слоев, расположенных ниже в Dockerfile.

### Предопределенные переменные BuildKit

BuildKit автоматически пробрасывает набор переменных для кросс-платформенной сборки. Их не нужно объявлять в `ARG` явно.

| Переменная | Описание | Пример |
| :--- | :--- | :--- |
| `TARGETPLATFORM` | Целевая платформа | `linux/amd64` |
| `TARGETOS` | Целевая ОС | `linux` |
| `TARGETARCH` | Целевая архитектура | `arm64` |
| `BUILDPLATFORM` | Платформа хоста сборки | `darwin/arm64` |

### Синтаксис подстановки и экранирование

Docker поддерживает подмножество bash-синтаксиса для интерполяции:

- `${variable:-word}`: если переменная не задана или пуста, использовать `word`.
- `${variable:+word}`: если переменная задана, использовать `word`, иначе пустую строку.
- **Экранирование:** Чтобы использовать литеральный символ `$`, используйте обратный слэш: `\$`.

```dockerfile
ENV LOG_DIR=/var/log
# Результат: "Logs are in /var/log"
RUN echo "Logs are in ${LOG_DIR}"
# Результат: "This costs $100" (без расширения переменной)
RUN echo "This costs \$100"
```

## Безопасность и секреты

| Аспект | ARG | ENV |
| :--- | :--- | :--- |
| **История слоев** | Видна в `docker history` | Видна в `docker history` |
| **Инспекция образа** | **Не видна** | Видна в `docker inspect` |
| **Рекомендация** | **Запрещено** для паролей/ключей | **Запрещено** для паролей/ключей |

**Решение (2026):** Используйте временное монтирование секретов BuildKit, которое не оставляет следов в образе:
`RUN --mount=type=secret,id=api_token API_KEY=$(cat /run/secrets/api_token) ./build.sh`

Подробнее о управлении секретами: **[Управление секретами в Docker](../../Docker_security/secrets_management.md)**.

## Лучшие практики

### Безопасность

1. **Никогда не передавайте секреты через `ENV` или `ARG`.** Переменные окружения фиксируются в метаданных образа и видны через `docker inspect`, `docker history` и `/proc/1/environ`. В production-средах 2026 года это считается грубым нарушением. Используйте `--mount=type=secret` на этапе сборки и Docker Secrets / tmpfs на этапе запуска.

2. **Используйте паттерн `_FILE` для приложений, поддерживающих чтение секретов из файлов.** Это исключает утечку через переменные окружения:
   ```dockerfile
   ENV DB_PASSWORD_FILE=/run/secrets/db_pass
   ```

3. **Не храните токены, пароли или ключи API в `ARG` с значениями по умолчанию.** Даже если `ARG` не попадает в рантайм, значение по умолчанию остается в истории сборки и может быть извлечено через `docker history`.

4. **Верифицируйте базовые образы.** Переменные `ENV` в базовых образах (например, `PATH`) наследуются вашим образом. Проверяйте их через `docker inspect` перед использованием в production:
   ```bash
   docker inspect --format='{{.Config.Env}}' python:3.12-slim
   ```

### Производительность и кэширование

1. **Минимизируйте изменения `ENV`.** Каждое изменение `ENV` инвалидирует кэш для всех последующих слоев. Группируйте объявления в одну инструкцию:
   ```dockerfile
   # ПЛОХО: 3 инвалидации кэша
   ENV APP_HOME=/app
   ENV APP_VERSION=1.0
   ENV PATH=$APP_HOME/bin:$PATH

   # ХОРОШО: 1 инвалидация кэша
   ENV APP_HOME=/app \
     APP_VERSION=1.0 \
     PATH=$APP_HOME/bin:$PATH
   ```

2. **Используйте `ARG` для параметров, меняющихся между сборками.** Это не инвалидирует кэш предыдущих слоев и позволяет переиспользовать результаты сборки.

3. **Не злоупотребляйте `ENV` для настроек, которые можно передать через CLI.** Если параметр нужен только для одного запуска, используйте `docker run -e` или `docker compose` environment — это не меняет образ.

### Наблюдаемость и аудит

1. **Документируйте все `ENV` в README.** SRE-команды должны знать, какие переменные ожидает контейнер, их значения по умолчанию и допустимые диапазоны.

2. **Используйте соглашения об именовании.** Префиксы `APP_`, `DB_`, `CACHE_` упрощают отладку и аудит:
   ```dockerfile
   ENV APP_NAME=myapp \
     APP_VERSION=1.2.3 \
     DB_HOST=postgres \
     DB_PORT=5432
   ```

3. **Интегрируйте проверку переменных в CI/CD.** Добавьте шаг, который извлекает `ENV` из собранного образа и проверяет их на соответствие политикам:
   ```bash
   docker inspect --format='{{json .Config.Env}}' myapp:latest | jq .
   ```

### Воспроизводимость сборок

1. **Фиксируйте версии через `ARG`.** Это позволяет воспроизводить сборку и отслеживать, какая версия зависимостей использовалась:
   ```dockerfile
   ARG PYTHON_VERSION=3.12.4
   FROM python:${PYTHON_VERSION}-slim
   ```

2. **Используйте `SOURCE_DATE_EPOCH` для воспроизводимых сборок.** Фиксирует временные метки в слоях и гарантирует одинаковые digest:
   ```dockerfile
   ARG SOURCE_DATE_EPOCH=1735689600
   FROM alpine:3.24
   RUN touch /build-$(date -u -d "@$SOURCE_DATE_EPOCH" +"%Y-%m-%d")
   ```

## Практические сценарии

### Сценарий 1: Управление версиями через ARG

Централизованное управление версиями базовых образов.

```dockerfile
ARG PY_VERSION=3.12
FROM python:${PY_VERSION}-slim AS base

# Переиспользование версии в LABEL
ARG PY_VERSION
LABEL python.version=${PY_VERSION}
```

### Сценарий 2: Гибкие пути через ENV

Использование переменных в инструкциях `WORKDIR` и `COPY`.

```dockerfile
ENV APP_ROOT=/usr/src/app
WORKDIR ${APP_ROOT}

# Подстановка в пути копирования
COPY . ${APP_ROOT}/src
```

### Сценарий 3: Адаптация под архитектуру (BuildKit)

Выполнение специфичных команд в зависимости от целевого процессора.

```dockerfile
FROM alpine
ARG TARGETARCH
RUN if [ "$TARGETARCH" = "arm64" ]; then \
        apk add --no-cache libhook-arm64; \
    fi
```

### Сценарий 4: Обязательные аргументы без значений по умолчанию

Если вы хотите, чтобы сборка падала при отсутствии аргумента, не задавайте ему значение в Dockerfile.

```dockerfile
ARG MANDATORY_TOKEN
# Сборка упадет на этом этапе, если --build-arg MANDATORY_TOKEN=... не передан
RUN test -n "$MANDATORY_TOKEN"
```

> **Примечание:** Сценарии переопределения переменных при запуске (`docker run -e`, `--env-file`, `compose.yaml`) описаны в **[Инструкции Dockerfile: Практические сценарии переопределения](./practical_scenarios.md)**.

## Типичные ошибки и решение

### Ошибка 1: Секреты в ENV попадают в образ

**Проблема:** Значения `ENV` фиксируются в `config.json` образа и видны через `docker inspect`.

```dockerfile
ENV API_KEY=super-secret-key
```

```bash
# Извлечение секрета из образа
docker inspect --format='{{.Config.Env}}' myapp | grep API_KEY
# → API_KEY=super-secret-key
```

**Решение:** Используйте `--mount=type=secret` на этапе сборки или Docker Secrets на этапе запуска. Подробнее: **[Управление секретами в Docker](../../Docker_security/secrets_management.md)**.

### Ошибка 2: Изменение ENV сбрасывает кэш

**Проблема:** Любое изменение `ENV` инвалидирует кэш для всех последующих слоев, даже если они не используют эту переменную.

```dockerfile
ENV APP_ENV=production
RUN apt-get update  # Кэш сброшен, даже если APP_ENV не используется здесь
```

**Решение:** Объявляйте `ENV` как можно ближе к концу Dockerfile, после всех зависимостей. Используйте `ARG` для параметров сборки, которые не нужны в рантайме.

### Ошибка 3: ENV с `$VAR` не интерполируется при сборке

**Проблема:** Docker интерполирует переменные окружения хоста только если они экспортированы. В CI/CD переменные часто передаются как `ARG`.

```dockerfile
# ОЖИДАНИЕ: $HOME интерполируется из хоста
ENV APP_HOME=$HOME/app
```

**Решение:** Явно передавайте значения через `ARG` или задавайте литеральные пути:
```dockerfile
ARG APP_HOME=/app
ENV APP_HOME=${APP_HOME}
```

### Ошибка 4: Утечка ARG в рантайм через ENV без намерения

**Проблема:** Паттерн `ARG ... ENV ...=${ARG}` делает сборочную переменную доступной в рантайме, что может быть нежелательно для чувствительных данных.

```dockerfile
ARG API_TOKEN
ENV API_TOKEN=${API_TOKEN}  # Теперь токен виден в docker inspect!
```

**Решение:** Не пробрасывайте чувствительные `ARG` в `ENV`. Используйте `--mount=type=secret` и оставляйте `ARG` только для нечувствительных параметров (версии, флаги сборки).

### Ошибка 5: Многословные ENV инвалидируют кэш при каждом изменении

**Проблема:** Если `ENV` содержит динамические значения (даты, git SHA), кэш перестает работать между сборками.

```dockerfile
ENV BUILD_DATE=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
```

**Решение:** Используйте `LABEL` для метаданных сборки вместо `ENV`. `LABEL` не инвалидирует кэш предыдущих слоев:
```dockerfile
ARG BUILD_DATE
LABEL org.opencontainers.image.created="${BUILD_DATE}"
```

### Ошибка 6: ARG глобальной области не виден внутри этапов

**Проблема:** Глобальный `ARG` (до `FROM`) виден только в инструкциях `FROM`. Внутри этапа сборки он недоступен.

```dockerfile
ARG BASE_TAG=3.21
FROM alpine:${BASE_TAG}
RUN echo "Tag: ${BASE_TAG}"  # ОШИБКА: BASE_TAG не определен!
```

**Решение:** Объявите `ARG` повторно внутри этапа без значения:
```dockerfile
ARG BASE_TAG=3.21
FROM alpine:${BASE_TAG}
ARG BASE_TAG  # Импорт в текущий этап
RUN echo "Tag: ${BASE_TAG}"  # Теперь работает
```

## Граничные случаи и ограничения

### Scope в многоэтапных сборках

Каждая стадия `FROM` создает изолированный контекст. `ARG` и `ENV`, объявленные в одной стадии, не наследуются автоматически в следующей:

```dockerfile
# Стадия 1: ENV доступна здесь
FROM alpine
ENV APP_ENV=production
RUN echo $APP_ENV  # → production

# Стадия 2: ENV из стадии 1 НЕ доступна
FROM alpine
RUN echo $APP_ENV  # → пусто
```

**Решение:** Явно объявляйте необходимые `ENV` в каждой стадии или пробрасывайте значения через `ARG`.

### Влияние ENV на размер образа

Каждое объявление `ENV` добавляет строки в `config.json` образа. При большом количестве переменных это влияет на размер:

```bash
# Проверка размера конфигурации
docker inspect --format='{{len .Config.Env}}' myapp:latest
# → Количество переменных окружения
```

**Ограничение:** Нет технического лимита на количество `ENV`, но большое количество усложняет отладку и аудит. Рекомендуется: до 50 переменных на образ.

### Взаимодействие с security-профилями

Переменные окружения контейнера доступны через `/proc/1/environ` и могут быть считаны процессами с `CAP_SYS_PTRACE` или изнутри контейнера с монтированным `/proc`. В окружениях с высокими требованиями к безопасности:

- **AppArmor/SELinux:** Не блокируют доступ к `/proc/1/environ` по умолчанию. Для ограничения доступа требуются кастомные профили.
- **Seccomp:** Стандартный профиль Docker блокирует `ptrace`, что предотвращает чтение окружения из других контейнеров.
- **userns-remap:** Изменяет UID/GID, но не скрывает переменные окружения.

### Воспроизводимость и даты

Использование динамических значений в `ENV` (даты, временные метки) нарушает воспроизводимость сборок. Разные сборки в разное время будут иметь разные digest:

```dockerfile
# НЕВОСПРОИЗВОДИМО: каждый build дает новый digest
ENV BUILD_DATE=$(date +%s)
```

**Решение:** Используйте `ARG` с фиксированным значением и `LABEL` для метаданных:
```dockerfile
ARG BUILD_DATE=2026-01-01T00:00:00Z
LABEL org.opencontainers.image.created="${BUILD_DATE}"
```

### ENV в базовых образах

Базовые образы часто содержат预定义ленные `ENV` (например, `PATH`, `LANG`, `HOME`). При наследовании они автоматически подставляются:

```bash
# Проверка унаследованных переменных
docker inspect --format='{{json .Config.Env}}' python:3.12-slim | jq .
# → ["PATH=/usr/local/bin:/usr/local/sbin:/usr/sbin:/usr/bin:/sbin:/bin", ...]
```

**Риск:** Уязвимости в базовых образах могут распространяться через унаследованные `ENV`. Регулярно аудируйте базовые образы через `docker scout` или Trivy.

## Валидация

### Проверка переменных в собранном образе

```bash
# Извлечение всех ENV из образа
docker inspect --format='{{json .Config.Env}}' myapp:latest | jq .

# Проверка конкретной переменной
docker inspect --format='{{.Config.Env}}' myapp:latest | grep APP_VERSION

# Проверка отсутствия секретов в ENV
docker inspect --format='{{json .Config.Env}}' myapp:latest | jq -r '.[]' | grep -iE 'password|secret|key|token'
```

### Проверка ARG на этапе сборки

```bash
# Передача ARG и проверка их использования
docker build --build-arg APP_VERSION=1.2.3 --build-arg BUILD_DATE=2026-01-01 -t myapp .

# Анализ истории слоев на наличие ARG
docker history myapp:latest
# → Проверьте, нет ли секретов в командах RUN
```

### Аудит переменных окружения в running-контейнерах

```bash
# Список всех переменных окружения running-контейнера
docker exec my-container env

# Поиск конкретной переменной
docker exec my-container env | grep APP_VERSION

# Проверка через /proc (альтернативный метод)
docker exec my-container cat /proc/1/environ | tr '\0' '\n' | grep APP_VERSION
```

### Проверка на утечку секретов

```bash
# Сканирование образа на секреты (Trivy)
trivy image --scanners secret myapp:latest

# Проверка истории слоев на наличие секретов
docker history myapp:latest --no-trunc | grep -iE 'password|secret|key|token'

# Извлечение всех переменных и проверка
docker inspect --format='{{json .Config.Env}}' myapp:latest | grep -iE 'PASSWORD|SECRET|KEY|TOKEN'
```

### Проверка кэширования и производительности

```bash
# Анализ влияния ENV на кэш
docker build --progress=plain . 2>&1 | grep -A2 "CACHED"

# Проверка количества слоев
docker inspect myapp:latest --format '{{len .RootFS.Layers}}'
# → Оптимально: 5-10 для большинства приложений

# Размер образа
docker images myapp:latest --format "{{.Size}}"
```

### Интеграция с CI/CD пайплайнами

```yaml
# GitHub Actions: проверка переменных после сборки
- name: Inspect image ENV
  run: |
    docker inspect --format='{{json .Config.Env}}' myapp:${{ github.sha }} | jq .

- name: Scan for secrets
  run: |
    trivy image --scanners secret myapp:${{ github.sha }} --exit-code 1
```

## Дополнительная информация

### Иерархия приоритетов переменных

При совпадении имен действует следующий приоритет (от высшего к низшему):

1. Флаги командной строки (`docker run -e VAR=val`).
2. Секция `environment` в `compose.yaml`.
3. Файлы переменных (`env_file`) в `compose.yaml`.
4. Переменные окружения хоста.
5. Инструкция `ENV` в `Dockerfile`.
6. Значения по умолчанию в приложении.
