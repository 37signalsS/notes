# Инструкции Dockerfile: Обзор

## Определения

**Инструкции Dockerfile** — зарезервированные ключевые слова, используемые в файле `Dockerfile` для описания процесса сборки образа. Каждая инструкция представляет собой отдельный шаг, который либо создает новый слой файловой системы, либо изменяет метаданные образа.

**Директивы парсера (Parser Directives)** — специальные инструкции, которые должны находиться в самых первых строках Dockerfile. Они управляют тем, как BuildKit будет интерпретировать файл (выбор синтаксиса, линтинг, символы экранирования).

## Основные концепции

### Директивы парсера

С 2024 года использование директив парсера является стандартом для обеспечения безопасности и доступа к новым функциям без обновления самого Docker Engine.

| Директива | Назначение | Пример |
| :--- | :--- | :--- |
| **`# syntax`** | Выбор версии синтаксиса Dockerfile | `# syntax=docker/dockerfile:1` |
| **`# check`** | Нативная проверка (линтинг) сборки | `# check=error=true` |
| **`# escape`** | Символ переноса строк (важно для Windows) | `# escape=` ` (backtick) |

> **Инструкция `ONBUILD`** позволяет выполнить команду не во время текущей сборки, а позже — когда созданный образ будет использован как базовый (`FROM`) для другого образа. Идеально для автоматизации сборки кода в базовых образах языков (например, Node.js образах).

### Сводная таблица характеристик

| Инструкция | Создает слой | Влияет на кэширование | Описание |
| :--- | :--- | :--- | :--- |
| `FROM` | Да | Да | Инициализирует стадию сборки |
| `RUN` | Да | Да | Выполняет команду в новом слое |
| `COPY` | Да | Да | Копирует файлы в образ |
| `ADD` | Да | Да | Копирует/распаковывает файлы |
| `WORKDIR` | Нет | Да | Устанавливает рабочую директорию |
| `ENV` | Нет | Да | Устанавливает переменную окружения |
| `ARG` | Нет | Да | Задает переменную для сборки |
| `EXPOSE` | Нет | Нет | Описывает сетевой интерфейс |
| `VOLUME` | Нет | Да | Создает точку монтирования |
| `LABEL` | Нет | Нет* | Добавляет метаданные |
| `USER` | Нет | Да | Устанавливает UID/GID |
| `SHELL` | Нет | Да | Меняет оболочку по умолчанию |
| `STOPSIGNAL` | Нет | Нет | Указывает сигнал завершения |
| `CMD` | Нет | Нет | Задает команду по умолчанию |
| `ENTRYPOINT` | Нет | Нет | Задает точку входа |
| `HEALTHCHECK` | Нет | Нет | Настраивает мониторинг контейнера |

> **\* Влияние на дайджест:** Инструкции `LABEL` и `EXPOSE` не инвалидируют кэш сборки (build cache), но изменяют метаданные в `config.json` образа. Это означает, что **image digest** (SHA256) изменится, даже если файлы внутри образа остались прежними. Подробнее: **[Влияние LABEL на дайджест](./base_image_and_metadata.md#сценарий-3-влияние-label-на-дайджест)**.

## Практические сценарии

### Сценарий 1: Использование Heredocs (Multi-line)

Современный способ написания длинных скриптов (требует `# syntax=docker/dockerfile:1`), избавляющий от необходимости цепочек `&& \`.

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim
RUN <<EOF
    apt-get update
    apt-get install -y --no-install-recommends git
    rm -rf /var/lib/apt/lists/*
EOF
```

### Сценарий 2: Нативная проверка сборки (Build Checks)

Включение строгого режима линтинга прямо в Dockerfile (доступно с версии v1.8+).

```dockerfile
# syntax=docker/dockerfile:1
# check=error=true
FROM alpine:3.20
# При сборке Docker выдаст ошибку, если нарушены best practices 
# (например, использование sudo в RUN или отсутствие WORKDIR)
RUN apk add curl
CMD ["curl", "https://google.com"]
```

## Дополнительная информация

### Правила именования и расположения

- **Имя файла:** по умолчанию `Dockerfile` (без расширения, первая буква заглавная).
- **Расположение:** рекомендуется размещать в корне проекта (контексте сборки).
- **Игнорирование файлов:** используйте `.dockerignore` для исключения ненужных файлов.
