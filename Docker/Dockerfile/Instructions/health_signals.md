# Инструкции Dockerfile: HEALTHCHECK и STOPSIGNAL

## Определения

**`HEALTHCHECK`** — инструкция Dockerfile, предназначенная для мониторинга работоспособности приложения внутри контейнера. Она позволяет Docker Engine (или оркестратору, например Docker Swarm) автоматически определять статус контейнера: `starting` (запуск), `healthy` (исправен) или `unhealthy` (неисправен).

**`STOPSIGNAL`** — инструкция, устанавливающая системный сигнал, который Docker будет отправлять основному процессу контейнера (PID 1) для его корректного завершения при выполнении команды `docker stop`.

## Основные концепции

### Проверка здоровья: HEALTHCHECK

Инструкция встраивает логику проверки готовности приложения непосредственно в образ, обеспечивая самодокументируемость и автоматизацию управления жизненным циклом.

**Синтаксис:**

```dockerfile
# Выполнение команды (exec-форма)
HEALTHCHECK [OPTIONS] CMD command

# Выполнение через оболочку (shell-форма)
HEALTHCHECK [OPTIONS] CMD-SHELL command

# Отключение проверок, унаследованных от базового образа
HEALTHCHECK NONE
```

**Доступные параметры (Options):**

| Параметр | Описание | По умолчанию |
| :--- | :--- | :--- |
| `--interval` | Время между плановыми проверками | `30s` |
| `--timeout` | Максимальное время ожидания ответа | `30s` |
| `--start-period` | "Льготный период" для старта приложения (ошибки не засчитываются) | `0s` |
| `--start-interval`| Интервал проверок **только** во время старта (Docker 25.0+) | `5s` |
| `--retries` | Количество неудач подряд до смены статуса на `unhealthy` | `3` |

**Коды возврата (Exit Codes):**

Команда проверки обязана возвращать следующие значения:
- `0`: **Успех** (healthy).
- `1`: **Ошибка** (unhealthy).
- `2`: **Зарезервировано** (не используйте этот код).

**Важное замечание по Kubernetes:**
Kubernetes **полностью игнорирует** инструкцию `HEALTHCHECK` из Dockerfile. В K8s необходимо использовать нативные механизмы: `livenessProbe`, `readinessProbe` и `startupProbe`. Подробнее см. **[Пробы в Kubernetes](../../Kubernetes/Base/Pod/health_checks.md)**.

### Сигнал остановки: STOPSIGNAL

Обеспечивает **Graceful Shutdown** (корректное завершение), позволяя приложению закрыть соединения, сохранить данные и освободить ресурсы.

**Синтаксис:**

```dockerfile
STOPSIGNAL <signal>
```
Пример: `STOPSIGNAL SIGTERM`, `STOPSIGNAL 9`, `STOPSIGNAL SIGQUIT`.

**Механизм работы:**
1. При `docker stop` Docker отправляет приложению сигнал из `STOPSIGNAL` (по умолчанию `SIGTERM`).
2. Приложение должно перехватить этот сигнал и начать процедуру завершения.
3. Если процесс (PID 1) не завершился в течение таймаута (default: 10с), Docker отправляет `SIGKILL`.

**Распространенные сигналы:**
- `SIGTERM` (15): Стандарт для большинства приложений.
- `SIGQUIT` (3): Часто используется для Nginx (быстрый выход) и JVM.
- `SIGINT` (2): Аналог Ctrl+C.

> **Ловушка PID 1:** Если ваше приложение запущено через shell-скрипт без использования `exec`, оно не получит сигнал остановки напрямую, так как shell-оболочка (sh/bash) не пробрасывает сигналы дочерним процессам. Всегда используйте `exec` в Entrypoint-скриптах.

## Практические сценарии

### Сценарий 1: Быстрое обнаружение готовности (Docker 25.0+)
Использование `--start-interval` позволяет Docker зафиксировать переход в `healthy` за считанные секунды после старта, не ожидая основного длинного интервала.

```dockerfile
# Проверяем каждые 2 секунды во время старта, затем раз в 1 минуту
HEALTHCHECK --interval=1m --timeout=3s --start-period=30s --start-interval=2s \
  CMD curl -f http://localhost:8080/health || exit 1
```

### Сценарий 2: Веб-сервер Nginx
Проверка доступности порта через `curl` или `wget`.

```dockerfile
FROM nginx:alpine
# spider - не скачивать файл, только проверить наличие
HEALTHCHECK --interval=30s --timeout=3s \
  CMD wget --no-verbose --tries=1 --spider http://localhost/ || exit 1
```

### Сценарий 3: База данных PostgreSQL
Использование специализированной утилиты `pg_isready`.

```dockerfile
FROM postgres:16-alpine
# SIGINT для немедленной, но корректной остановки БД
STOPSIGNAL SIGINT
HEALTHCHECK --interval=10s --timeout=5s --start-period=20s \
  CMD pg_isready -U postgres || exit 1
```

## Дополнительная информация

### Рекомендации
1. **Легковесность:** Команда проверки не должна нагружать CPU/IO. Избегайте тяжелых скриптов.
2. **Локальность:** Обращайтесь к `localhost` или `127.0.0.1`, чтобы избежать сетевых задержек и проблем с DNS.
3. **Безопасность:** Если проверка требует прав `root`, убедитесь, что это оправдано.
4. **Видимость:** Результаты последних проверок можно увидеть в `docker inspect <id>`.
