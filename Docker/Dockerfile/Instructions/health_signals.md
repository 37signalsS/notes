# Инструкции Dockerfile: HEALTHCHECK и STOPSIGNAL

## Определения

**`HEALTHCHECK`** — инструкция Dockerfile, предназначенная для проверки работоспособности приложения внутри контейнера. Она позволяет Docker автоматически определять, находится ли сервис в рабочем состоянии (healthy) или столкнулся с проблемами (unhealthy).

**`STOPSIGNAL`** — инструкция, устанавливающая системный сигнал, который Docker будет отправлять основному процессу контейнера (PID 1) для его корректного завершения при остановке.

## Основные концепции

### Проверка здоровья: HEALTHCHECK

Инструкция позволяет встроить логику проверки готовности приложения непосредственно в образ.

**Синтаксис:**

```dockerfile
# Выполнение команды (exec-форма)
HEALTHCHECK [OPTIONS] CMD command

# Выполнение через оболочку (shell-форма)
HEALTHCHECK [OPTIONS] CMD-SHELL command

# Отключение проверок, унаследованных от базового образа
HEALTHCHECK NONE
```

**Доступные параметры (Options):**

| Параметр | Описание | По умолчанию |
| :--- | :--- | :--- |
| `--interval` | Время между запусками проверок | `30s` |
| `--timeout` | Время ожидания завершения команды проверки | `30s` |
| `--start-period` | Период инициализации после запуска (ошибки в это время не влияют на статус) | `0s` |
| `--retries` | Количество последовательных неудач до смены статуса на `unhealthy` | `3` |

**Коды возврата команды:**

Команда, указанная в `HEALTHCHECK`, должна возвращать определенные коды:

- `0`: Успешно (healthy) — контейнер работает корректно.
- `1`: Ошибка (unhealthy) — контейнер неисправен.

**Мониторинг статуса:**

Текущий статус можно увидеть в выводе `docker ps` в колонке `STATUS` или через детальный осмотр:

```bash
# Получение только статуса здоровья
docker inspect --format='{{.State.Health.Status}}' my_container

# Получение полной истории проверок в формате JSON
docker inspect --format='{{json .State.Health}}' my_container
```

### Сигнал остановки: STOPSIGNAL

Обеспечивает корректное завершение работы приложения (Graceful Shutdown).

**Синтаксис:**

```dockerfile
STOPSIGNAL <signal>
```

Сигнал можно указывать по имени (`SIGTERM`), по номеру (`15`) или через переменную окружения (`${STOP_SIG}`).

**Стандартное поведение:**

- По умолчанию Docker отправляет `SIGTERM` (15).
- Если процесс не завершился в течение льготного периода (по умолчанию 10 секунд), отправляется `SIGKILL` (9).
- Время ожидания можно переопределить при запуске контейнера или через команду остановки: `docker stop --time 30 <container>`.

**Распространенные сигналы:**

| Сигнал | Описание |
| :--- | :--- |
| `SIGTERM` | Стандартный сигнал для вежливой остановки процесса. |
| `SIGINT` | Прерывание с терминала (аналог сочетания клавиш Ctrl+C). |
| `SIGQUIT` | Выход с созданием дампа памяти. Часто используется для Nginx и приложений на Java Virtual Machine (JVM). |
| `SIGKILL` | Принудительное немедленное завершение. Процесс не может обработать этот сигнал. |

## Практические сценарии

### Сценарий 1: Проверка веб-сервера Nginx

Использование `wget` для проверки доступности главной страницы.

```dockerfile
FROM nginx:alpine
HEALTHCHECK --interval=30s --timeout=3s \
  CMD wget --no-verbose --tries=1 --spider http://localhost/ || exit 1
```

### Сценарий 2: Ожидание готовности PostgreSQL

Использование встроенной утилиты `pg_isready` с увеличенным периодом инициализации.

```dockerfile
FROM postgres:16-alpine
HEALTHCHECK --interval=10s --timeout=5s --start-period=10s --retries=5 \
  CMD pg_isready -U postgres || exit 1
```

### Сценарий 3: Корректная остановка Java-приложения

Для Java Virtual Machine (JVM) часто рекомендуется использовать `SIGQUIT` для корректного сброса потоков.

```dockerfile
FROM eclipse-temurin:21-jre-alpine
STOPSIGNAL SIGQUIT
COPY app.jar .
CMD ["java", "-jar", "app.jar"]
```

### Сценарий 4: Отключение проверок базового образа

Если вы строите образ на базе, где уже настроен `HEALTHCHECK`, но он вам не нужен.

```dockerfile
FROM my-base-image-with-healthcheck
HEALTHCHECK NONE
```

## Дополнительная информация

### Рекомендации по использованию

- **Идемпотентность:** Команда проверки здоровья не должна изменять состояние данных или приложения.
- **Минимализм:** Проверка должна быть быстрой и потреблять минимум ресурсов, так как она выполняется постоянно.
- **Локальность:** Выполняйте проверку внутри контейнера, обращаясь к `localhost`, чтобы не зависеть от внешней сетевой связности.
- **Оркестрация:** В Docker Compose параметры `healthcheck` могут быть переопределены для настройки зависимостей между сервисами (условие `service_healthy`).

Подробности использования в сценариях развертывания см. в разделах **[Пример файла Docker Compose](../../Docker_compose/docker_compose_file_example.md)** и **[Директивы Docker Compose](../../Docker_compose/docker_compose_directives.md)**.
