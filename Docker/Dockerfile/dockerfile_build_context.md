# Контекст сборки Docker и .dockerignore

## Определения

**Контекст сборки (Build Context)** — набор файлов и директорий по указанному пути, который Docker CLI упаковывает в архив и отправляет демону Docker перед началом сборки образа. Демон может использовать любой из этих файлов в инструкциях `COPY` или `ADD`.

**`.dockerignore`** — файл, аналогичный `.gitignore`, который позволяет исключить файлы и директории из контекста сборки. Предотвращает отправку ненужных или чувствительных данных демону Docker.

## Основные концепции

### Важность управления контекстом

- **Ускорение сборки:** Меньший контекст быстрее отправляется демону.
- **Уменьшение размера образа:** Исключение ненужных файлов предотвращает их случайное попадание в образ.
- **Безопасность:** Предотвращает утечку секретов, ключей и других чувствительных файлов в образ.
- **Оптимизация кэширования:** Исключение часто меняющихся, но не нужных для сборки файлов (например, `README.md`, логов) предотвращает необоснованную инвалидацию кэша слоев.

### Форматы указания контекста

1. **`PATH` (локальная директория):**
   - Команда: `docker build .`
   - Наиболее распространенный способ. В качестве контекста используется текущая или указанная директория.

2. **`URL` (Git-репозиторий):**
   - Команда: `docker build github.com/user/repo`
   - Docker автоматически клонирует репозиторий во временную директорию и использует её как контекст.

3. **`-` (стандартный ввод, STDIN):**
   - Команда: `docker build - < context.tar.gz`
   - Позволяет передать контекст через `STDIN` в виде `tar`-архива. Полезно для автоматизации, так как не требует записи файлов на диск.

## Практические сценарии

### Сценарий 1: Dockerfile в отдельной директории

Часто `Dockerfile` располагают в поддиректории (например, `build/` или `docker/`), чтобы не загромождать корень проекта.

**Структура проекта:**

```
/my-project
├── docker/
│   └── Dockerfile
├── src/
│   └── ...
├── .dockerignore
└── ...
```

**Процесс сборки:**

1. Команда выполняется из корня проекта (`/my-project`), чтобы он стал контекстом сборки.
2. Путь к `Dockerfile` указывается явно с помощью флага `-f` (`--file`).

```bash
# Находясь в /my-project, запускаем сборку:
# '.' указывает, что контекст сборки — текущая директория.
# '-f' указывает на нестандартное расположение Dockerfile.
docker build -f docker/Dockerfile .
```

**Ключевой момент:** Файл `.dockerignore` **должен** находиться в корне проекта (в нашем примере — `/my-project`), а не рядом с `Dockerfile`. Это связано с тем, что `.dockerignore` применяется к **контексту сборки**, которым является корневая директория проекта (`.`), а не директория, где лежит `Dockerfile`.

### Сценарий 2: Пример .dockerignore для типичного проекта

```dockerignore
# Git
.git
.gitignore

# Документы
README.md
*.md
docs/

# Логи и временные файлы
*.log
tmp/
temp/

# Зависимости (устанавливаются внутри контейнера)
node_modules/
vendor/
__pycache__/
.venv/

# IDE и редакторы
.idea/
.vscode/
*.swp
*.swo

# Тесты и CI
tests/
.coverage
.pytest_cache/

# Секреты (никогда не должны попадать в образ)
.env
*.pem
*.key
secrets/

# Артефакты сборки
dist/
build/
*.pyc
```
