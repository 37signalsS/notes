# Контекст сборки Docker и .dockerignore

## Определения

**Контекст сборки (Build Context)** — набор файлов и директорий по указанному пути, который Docker-клиент упаковывает и отправляет демону Docker перед началом сборки образа. Демон использует эти файлы для выполнения инструкций `COPY` и `ADD`.

**`.dockerignore`** — конфигурационный файл, позволяющий исключить определенные файлы и директории из контекста сборки. Он работает аналогично `.gitignore`, предотвращая отправку ненужных, временных или конфиденциальных данных демону Docker.

## Базовые концепции

### Значение управления контекстом

Эффективное управление контекстом сборки критически важно для:

- **Ускорения процесса сборки:** Уменьшение объема данных, передаваемых демону Docker (особенно актуально при сборке на удаленных серверах или в облачных CI/CD).
- **Минимизации размера образа:** Исключение файлов, которые не должны попасть в итоговый образ, предотвращает их случайное включение через инструкции `COPY . .`.
- **Обеспечения безопасности:** Защита от попадания секретов, ключей доступа (`.env`, `.pem`) и локальных конфигураций в слои образа.
- **Оптимизации кэширования:** Исключение часто меняющихся файлов, не влияющих на сборку (например, документации или логов), предотвращает преждевременную инвалидацию кэша слоев.

### Способы указания контекста

При запуске команды `docker build` контекст указывается в конце:

1. **Локальный путь (PATH):**
   - `docker build .` — текущая директория становится контекстом.
2. **Git-репозиторий (URL):**
   - `docker build https://github.com/user/project.git` — Docker клонирует репозиторий и использует его как контекст.
3. **Стандартный ввод (STDIN):**
   - `docker build - < context.tar.gz` — передача упакованного контекста напрямую в CLI.

## Практические сценарии

### Сценарий 1: Расположение Dockerfile в поддиректории

Часто `Dockerfile` хранят в отдельной папке (например, `docker/`), чтобы не загромождать корень проекта. При этом контекстом сборки должен оставаться корень проекта, чтобы инструкции `COPY` имели доступ к исходному коду.

**Структура проекта:**
```
/my-project
├── docker/
│   └── Dockerfile
├── src/
│   └── ...
├── .dockerignore
└── ...
```

**Команда сборки:**
Выполняется из корня проекта (`/my-project`):
```bash
# '.' — контекст сборки (текущая директория)
# '-f' — явный путь к файлу Dockerfile
docker build -f docker/Dockerfile .
```

**Важно:** Файл `.dockerignore` всегда должен находиться в корне **контекста сборки** (в данном случае — в `/my-project`), а не рядом с `Dockerfile`.

### Сценарий 2: Оптимальный .dockerignore для типичного проекта

Ниже приведен пример содержимого `.dockerignore`, подходящий для большинства веб-проектов:

```dockerignore
# Система контроля версий
.git
.gitignore

# Документация и текстовые файлы
README.md
*.md
docs/

# Логи и временные файлы приложений
*.log
tmp/
temp/

# Зависимости (должны устанавливаться внутри образа)
node_modules/
vendor/
__pycache__/
.venv/

# Конфигурации IDE и редакторов
.idea/
.vscode/
*.swp

# Тесты и отчеты о покрытии
tests/
.coverage
.pytest_cache/

# Секреты и конфиденциальные данные
.env
*.pem
*.key
secrets/

# Артефакты локальной сборки
dist/
build/
*.pyc
```
