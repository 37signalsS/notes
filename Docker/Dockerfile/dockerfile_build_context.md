# Контекст сборки (Build Context) и .dockerignore

### Определения

- **Контекст сборки (Build Context):** Это набор файлов и директорий по указанному пути, который Docker CLI упаковывает в архив и отправляет демону Docker перед началом сборки образа. Демон может использовать любой из этих файлов в инструкциях `COPY` или `ADD`.

- **`.dockerignore`:** Файл, аналогичный `.gitignore`, который позволяет исключить файлы и директории из контекста сборки. Это предотвращает отправку ненужных или чувствительных данных демону Docker.

### Основные концепции

#### Важность управления контекстом
Правильная настройка контекста сборки с помощью `.dockerignore` критически важна для:
- **Ускорения сборки:** Меньший контекст быстрее отправляется демону.
- **Уменьшения размера образа:** Исключение ненужных файлов помогает избежать их случайного попадания в образ.
- **Безопасности:** Предотвращает утечку секретов, ключей и других чувствительных файлов в образ.
- **Оптимизации кэширования:** Исключение часто меняющихся, но не нужных для сборки файлов (например, `README.md`, логов) предотвращает необоснованную инвалидацию кэша слоев.

#### Способы указания контекста сборки
Контекст можно передать демону тремя способами:

1.  **`PATH` (локальная директория):**
    -   Команда: `docker build .`
    -   Наиболее распространенный способ. В качестве контекста используется текущая или указанная директория.

2.  **`URL` (Git-репозиторий):**
    -   Команда: `docker build github.com/user/repo`
    -   Docker автоматически клонирует репозиторий во временную директорию и использует её как контекст.

3.  **`-` (стандартный ввод, STDIN):**
    -   Команда: `docker build - < context.tar.gz`
    -   Позволяет передать контекст через `STDIN` в виде `tar`-архива. Полезно для автоматизации, так как не требует записи файлов на диск.

### Практические сценарии

#### Сценарий: Dockerfile в отдельной директории

Часто `Dockerfile` располагают в поддиректории (например, `build/` или `docker/`), чтобы не загромождать корень проекта, при этом исходный код приложения находится в корне.

**Структура проекта:**
```
/my-project
├── docker/
│   └── Dockerfile
├── src/
│   └── ...
├── .dockerignore
└── ...
```

**Процесс сборки:**
1.  **Команда** выполняется из корня проекта (`/my-project`), чтобы он стал контекстом сборки.
2.  Путь к `Dockerfile` указывается явно с помощью флага `-f` (`--file`).

```bash
# Находясь в /my-project, запускаем сборку:
# '.' указывает, что контекст сборки — текущая директория.
# '-f' указывает на нестандартное расположение Dockerfile.
docker build -f docker/Dockerfile .
```

**Ключевой момент:** Файл `.dockerignore` **должен** находиться в корне проекта (в нашем примере — `/my-project`), а не рядом с `Dockerfile`. Это связано с тем, что `.dockerignore` применяется к **контексту сборки**, которым является корневая директория проекта (`.`), а не директория, где лежит `Dockerfile`.
