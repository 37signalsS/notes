# BuildKit: Современный движок сборки Docker

## Определения

**BuildKit** — это современный бэкенд для выполнения сборки образов, который полностью заменяет устаревший (legacy) движок Docker. Он представляет собой высокоуровневый оркестратор, преобразующий инструкции Dockerfile в эффективный граф выполнения (LLB).

В современных версиях Docker (начиная с v23.0) BuildKit является единственным стандартом. Команда `docker build` теперь работает через плагин `buildx`, который по умолчанию использует BuildKit.

## Эволюция: BuildKit против Legacy Builder

До появления BuildKit процесс сборки сопровождался рядом проблем, которые делали работу медленной и приводили к избыточному размеру образов.

### 1. Граф зависимостей против линейного списка
- **Legacy:** Читал Dockerfile как простой список покупок (линейно: 1, 2, 3...). Если пункт 2 изменился — всё, что ниже, инвалидировалось.
- **BuildKit:** Перешел к **графу зависимостей (LLB — Low-Level Builder)**. Он видит дерево связей и понимает, какие инструкции независимы. Это позволяет запускать стадии (multi-stage) или команды **параллельно**, значительно сокращая время сборки.

### 2. Маунты против коммитов (Дилемма размера и скорости)
- **Legacy:** Каждая команда `RUN` создавала неизменяемый слепок файловой системы («фотографию»). Весь мусор (кэш pip, apt), созданный во время команды, навсегда оставался в слое образа, даже если его удаляли в следующей строке.
- **BuildKit:** Ввел временные **маунты (Mounts)**. Это концепция «внешней флешки», которая подключается к контейнеру только на время работы `RUN`. Когда команда завершается, BuildKit «выдергивает флешку». Все данные кэша остаются в «кармане» BuildKit на хосте, а слой образа остается чистым.

### 3. Безопасность секретов
- **Legacy:** Для передачи ключей доступа приходилось использовать `ARG` или `ENV`, что навсегда сохраняло секреты в истории слоев образа.
- **BuildKit:** Позволяет безопасно прокидывать токены через `--mount=type=secret`. Они монтируются в оперативную память и никогда не записываются на диск внутри образа.

## Техническая архитектура

BuildKit — это независимый проект (**moby/buildkit**), который может работать даже без Docker-демона.

### LLB (Low-Level Builder)
BuildKit работает не с Dockerfile напрямую, а с промежуточным двоичным форматом **LLB**. Это позволяет создавать различные «фронтенды»:
- **Фронтенды:** Компоненты, превращающие высокоуровневый код (Dockerfile, HCL, Buildpacks) в LLB-граф.
- **Директива `# syntax`:** Указывает версию фронтенда в первой строке Dockerfile. Это позволяет использовать новейшие функции (новые типы монтирований) без обновления самого Docker Engine.

### Режимы работы
1. **Standalone (buildkitd):** Работает как отдельный процесс. Позволяет собирать образы в Kubernetes без доступа к `docker.sock` через утилиту `buildctl`.
2. **Rootless:** Изначально поддерживает запуск от имени обычного пользователя, что исключает риск получения прав root на хосте при «побеге» из контейнера во время сборки.

## Сравнение с альтернативами

| Критерий | BuildKit (buildx) | Kaniko | Buildah |
| :--- | :--- | :--- | :--- |
| **Кэш в Registry** | Экспорт отдельного манифеста (`mode=max`) | Поддерживается | Ограниченно |
| **Параллелизм** | Нативный (между стадиями) | Последовательно | Последовательно |

| **Безопасность** | Rootless, Standalone | Userspace | Daemonless, Rootless |

## Практические сценарии

### Сценарий 1: Использование секретов и отладка

Безопасная передача ключей без сохранения в слоях.

```dockerfile
# syntax=docker/dockerfile:1
FROM alpine:3.21

# Секрет доступен только в этой команде RUN
RUN --mount=type=secret,id=mysecret \
    token=$(cat /run/secrets/mysecret) && \
    wget --header="Authorization: Bearer $token" https://internal.repo/package.tar
```

**Механизм работы:**
- **ID:** Псевдоним в Dockerfile (`id=mysecret`), который связывает инструкцию с реальным файлом в CLI.
- **CLI команда:** `docker build --secret id=mysecret,src=~/.ssh/token.txt .`
- **Отладка:** По умолчанию BuildKit скрывает вывод успешных команд. Чтобы увидеть логи (например, для проверки путей), используйте `--progress=plain`.

### Сценарий 2: Кэширование зависимостей (механизм «флешки»)

Радикальное ускорение сборки при изменении кода, но сохранении зависимостей.

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.13-alpine
WORKDIR /app
COPY requirements.txt .

# Кэш pip сохраняется во внешнем хранилище BuildKit
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

COPY . .
```

**Почему это важно:**
1. **Экономия места:** Даже если `builder`-стадия отбрасывается, использование кэш-маунтов предотвращает раздувание временных образов на CI-сервере.
2. **Persistent Storage:** BuildKit создает на хосте изолированную директорию, которая переживает удаление контейнеров и используется повторно при следующих сборках.

### Сценарий 3: Удаленный кэш в Registry

Идеально для распределенных CI/CD систем (GitHub Actions, GitLab CI), где у раннеров нет общего локального диска.

```bash
docker buildx build \
  --cache-from type=registry,ref=my-reg.com/app:build-cache \
  --cache-to type=registry,ref=my-reg.com/app:build-cache,mode=max \
  --push -t my-reg.com/app:latest .
```
- `mode=max`: сохраняет кэш абсолютно для всех промежуточных стадий, обеспечивая максимальное ускорение при повторных запусках.

### Сценарий 4: SSH-монтирование

Позволяет использовать SSH-ключи хоста без их копирования в контекст сборки.

```dockerfile
# syntax=docker/dockerfile:1
FROM alpine:3.21
RUN apk add --no-cache openssh-client
# Использует SSH-агент хоста
RUN --mount=type=ssh git clone git@github.com:myorg/private-repo.git
```
Запуск: `docker build --ssh default .` (требует запущенного `ssh-agent` на хосте).
