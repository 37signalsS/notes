# Dockerfile: Лучшие практики для Java

## Определения

- **JVM (Java Virtual Machine):** Виртуальная машина, исполняющая Java-байт-код. Управляет памятью и ресурсами для Java-приложений.
- **Куча (Heap):** Основная область оперативной памяти, используемая JVM для хранения объектов, создаваемых приложением. Размер задается флагами `-Xms` (начальный) и `-Xmx` (максимальный).
- **cgroups (Control Groups):** Функция ядра Linux, которую Docker использует для ограничения ресурсов (ЦП, память) для контейнеров.
- **JRE (Java Runtime Environment):** Среда выполнения Java, необходимая для запуска приложений. Включает JVM и стандартные библиотеки.
- **JDK (Java Development Kit):** Комплект разработчика Java, включающий JRE, компилятор (`javac`) и инструменты сборки.
- **OOM (Out Of Memory) Killed:** Событие принудительной остановки контейнера операционной системой из-за превышения лимита выделенной памяти.

## Основные концепции

### Осведомленность JVM о лимитах контейнера

Старые версии Java (до JDK 8u191 и JDK 10) **не учитывали лимиты контейнеров**. JVM считывала ресурсы хост-машины, а не ограничения `cgroups`, что приводило к выделению избыточного объема памяти и аварийному завершению контейнера через OOM Killed.

Современные версии (JDK 8u191+, JDK 10+) корректно определяют лимиты контейнера и адаптируются к ним благодаря встроенному механизму `UseContainerSupport`.

### Управление памятью JVM

Общий объем памяти, потребляемый JVM, превышает размер кучи (`-Xmx`). Он также включает:

- **Metaspace:** область для метаданных классов.
- **Стеки потоков:** память, выделяемая под каждый поток выполнения.
- **Собственная (native) память:** используется для внутренних нужд виртуальной машины.

Поэтому **лимит памяти контейнера всегда должен быть больше**, чем максимальный размер кучи. Рекомендуется выделять контейнеру на 25–50% больше памяти, чем значение `-Xmx`.

### Многоэтапная сборка

Для Java-приложений критически важно использовать [многоэтапную сборку](./build_optimization.md). Паттерн заключается в использовании JDK для компиляции на первом этапе и JRE для запуска на втором. Это позволяет уменьшить размер финального образа на 40–50%.

## Практические сценарии

### Сценарий 1: Многоэтапная сборка с кешированием зависимостей

Демонстрация многоэтапной сборки с использованием кеша Maven (`~/.m2`) для ускорения повторных запусков. Для повышения безопасности рекомендуется использовать непривилегированного пользователя — см. [Безопасность в Dockerfile](./security.md).

```dockerfile
# --- Этап 1: Сборка с Maven (builder) ---
FROM maven:3.9.11-eclipse-temurin-25 AS builder
WORKDIR /app

# Сначала копируем только pom.xml, чтобы закешировать слой с зависимостями
COPY pom.xml .

# Монтирование кеша Maven ускоряет последующие сборки
# mvn dependency:go-offline скачивает все зависимости
RUN --mount=type=cache,target=/root/.m2 mvn dependency:go-offline

# Копируем исходный код и собираем проект
COPY src ./src
RUN mvn package

# --- Этап 2: Финальный образ ---
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

# Копируем только собранный JAR-файл из этапа "builder"
COPY --from=builder /app/target/*.jar app.jar

EXPOSE 8080

# Запускаем приложение
CMD ["java", "-jar", "app.jar"]
```

### Сценарий 2: Spring Boot приложение с Maven Wrapper

Пример использования Maven Wrapper (`mvnw`), который автоматически загружает нужную версию Maven, исключая зависимость от предустановленных инструментов в базовом образе.

```dockerfile
# --- Этап 1: Сборка (builder) ---
FROM eclipse-temurin:21-jdk AS builder
WORKDIR /app

# Копируем Maven Wrapper и pom.xml для кеширования зависимостей
COPY .mvn/ .mvn
COPY mvnw pom.xml ./

# Скачиваем зависимости (без сборки) — слой кешируется
RUN ./mvnw dependency:go-offline

# Копируем исходный код и собираем JAR (Java Archive)
COPY src ./src
RUN ./mvnw clean package -DskipTests

# --- Этап 2: Финальный образ (production) ---
FROM eclipse-temurin:21-jre
WORKDIR /app

# Копируем JAR из builder
COPY --from=builder /app/target/*.jar app.jar

EXPOSE 8080

# Запуск с указанием максимальной доли RAM для кучи
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]
```

### Сценарий 3: Настройка параметров памяти

- **Современные версии (JDK 10+):**
  Используйте процентные значения. JVM автоматически рассчитает размер кучи на основе лимита памяти контейнера.

  ```bash
  # JVM выделит под кучу 75% от памяти контейнера
  CMD ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]
  ```

- **Старые версии (до JDK 8u191):**
  Необходимо задавать размер кучи явно через флаги `-Xmx` и `-Xms`, так как JVM не видит лимиты контейнера.

  ```bash
  # Явное выделение 256 МБ под кучу
  # Лимит контейнера должен быть минимум 384 МБ
  CMD ["java", "-Xmx256m", "-jar", "app.jar"]
  ```
