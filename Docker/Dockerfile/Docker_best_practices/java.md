# Dockerfile: Лучшие практики для Java

## Определения

- **JVM (Java Virtual Machine):** Виртуальная машина, исполняющая Java-байт-код. Управляет памятью и ресурсами для Java-приложений.
- **Куча (Heap):** Основная область памяти, используемая JVM для хранения объектов, создаваемых приложением. Ее размер задается флагами `-Xms` (начальный) и `-Xmx` (максимальный).
- **cgroups (Control Groups):** Функция ядра Linux, которую Docker использует для ограничения ресурсов (ЦП, память) для контейнеров.

## Основные концепции

### Проблема №1: Осведомленность JVM о лимитах контейнера

Старые версии Java (до JDK 8u191 и JDK 10) **не были "осведомлены" о контейнерах**. Они смотрели на память и процессор хост-машины, а не на лимиты, установленные для контейнера через `cgroups`. Это приводило к тому, что JVM могла попытаться выделить больше памяти, чем разрешено контейнеру, что вызывало его аварийное завершение (OOMKilled).

Современные версии Java корректно определяют лимиты контейнера и адаптируются к ним.

### Проблема №2: Управление памятью JVM

Память, потребляемая JVM, состоит не только из кучи (`-Xmx`). Она также включает:

- **Metaspace:** для метаданных классов.
- **Память под стеки потоков.**
- **Собственную (native) память** для внутренних нужд.

Поэтому **лимит памяти контейнера всегда должен быть больше**, чем максимальный размер кучи. Общепринятая практика — выделять контейнеру примерно на 25-50% больше памяти, чем значение `-Xmx`.

## Практические сценарии

### Сценарий 1: Многоэтапная сборка с кешированием зависимостей

Этот `Dockerfile` демонстрирует две лучшие практики: **[многоэтапную сборку](./build_optimization.md)** для создания легковесного образа и **кеширование `~/.m2`** для ускорения установки зависимостей.

```dockerfile
# --- Этап 1: Сборка с Maven (builder) ---
# Используем образ с полным JDK и Maven
FROM maven:3.9.11-eclipse-temurin-25 AS builder
WORKDIR /app

# Сначала копируем только pom.xml, чтобы закешировать слой с зависимостями
COPY pom.xml .

# Используем --mount=type=cache для монтирования кеша Maven.
# Это значительно ускоряет последующие сборки.
# mvn dependency:go-offline скачивает все зависимости.
RUN --mount=type=cache,target=/root/.m2 mvn dependency:go-offline

# Копируем исходный код и собираем проект
COPY src ./src
RUN mvn package

# --- Этап 2: Финальный образ ---
# Используем минималистичный образ только со средой выполнения Java (JRE)
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

# Копируем только собранный JAR-файл из этапа "builder"
COPY --from=builder /app/target/*.jar app.jar

EXPOSE 8080

# Запускаем приложение
CMD ["java", "-jar", "app.jar"]
```

### Сценарий 2: Корректная настройка памяти

- **Современные версии Java (JDK 10+):**
    Используйте процентные значения. JVM сама рассчитает размер кучи на основе лимита памяти контейнера.

    ```shell
    # JVM выделит под кучу не более 75% от памяти, доступной контейнеру
    CMD ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]
    ```

- **Старые версии Java (JDK 8):**
    Задавайте размер кучи вручную через флаг `-Xmx`.

    ```shell
    # Явно выделяем 256 мегабайт под кучу
    # При этом лимит памяти контейнера должен быть больше (например, 384MB)
    CMD ["java", "-Xmx256m", "-jar", "app.jar"]
    ```

    Если вы используете версию Java до 8u191, вы **обязаны** вручную задавать размер кучи через флаги `-Xmx` и `-Xms`, иначе JVM не будет учитывать лимиты контейнера.
