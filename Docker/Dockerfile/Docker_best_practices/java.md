# Dockerfile: Лучшие практики для Java

## Определения

- **JVM (Java Virtual Machine):** Виртуальная машина, исполняющая Java-байт-код. Управляет памятью и ресурсами для Java-приложений.
- **Куча (Heap):** Основная область памяти, используемая JVM для хранения объектов, создаваемых приложением. Ее размер задается флагами `-Xms` (начальный) и `-Xmx` (максимальный).
- **cgroups (Control Groups):** Функция ядра Linux, которую Docker использует для ограничения ресурсов (ЦП, память) для контейнеров.
- **JRE (Java Runtime Environment):** Среда выполнения Java, необходимая для запуска Java-приложений. Включает JVM и стандартные библиотеки.
- **JDK (Java Development Kit):** Комплект разработчика Java, включающий JRE, компилятор (`javac`) и инструменты для сборки.

## Основные концепции

### Осведомленность JVM о лимитах контейнера

Версии Java до JDK 8u191 и JDK 10 **не учитывали лимиты контейнеров**. JVM считывала ресурсы хост-машины, а не ограничения `cgroups`, что приводило к превышению лимитов и аварийному завершению контейнера (OOMKilled).

Современные версии Java (JDK 8u191+, JDK 10+) корректно определяют лимиты контейнера и адаптируются к ним.

### Управление памятью JVM

Память, потребляемая JVM, состоит не только из кучи (`-Xmx`). Она также включает:

- **Metaspace:** для метаданных классов.
- **Память под стеки потоков.**
- **Собственную (native) память** для внутренних нужд.

Поэтому **лимит памяти контейнера всегда должен быть больше**, чем максимальный размер кучи. Общепринятая практика — выделять контейнеру примерно на 25-50% больше памяти, чем значение `-Xmx`.

### Многоэтапная сборка

Для Java-приложений рекомендуется использовать многоэтапную сборку: JDK для компиляции на первом этапе, JRE для запуска на втором. Это уменьшает размер финального образа на 40-50%. Подробнее — в [Оптимизация сборки Dockerfile](./build_optimization.md).

## Практические сценарии

### Сценарий 1: Многоэтапная сборка с кешированием зависимостей

Этот `Dockerfile` демонстрирует многоэтапную сборку и кеширование `~/.m2` для ускорения установки зависимостей. Для повышения безопасности рекомендуется запускать приложение от непривилегированного пользователя — см. [Безопасность в Dockerfile](./security.md).

```dockerfile
# --- Этап 1: Сборка с Maven (builder) ---
FROM maven:3.9.11-eclipse-temurin-25 AS builder
WORKDIR /app

# Сначала копируем только pom.xml, чтобы закешировать слой с зависимостями
COPY pom.xml .

# Монтирование кеша Maven ускоряет последующие сборки
# mvn dependency:go-offline скачивает все зависимости
RUN --mount=type=cache,target=/root/.m2 mvn dependency:go-offline

# Копируем исходный код и собираем проект
COPY src ./src
RUN mvn package

# --- Этап 2: Финальный образ ---
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

# Копируем только собранный JAR-файл из этапа "builder"
COPY --from=builder /app/target/*.jar app.jar

EXPOSE 8080

# Запускаем приложение
CMD ["java", "-jar", "app.jar"]
```

### Сценарий 2: Spring Boot приложение с Maven Wrapper

Пример для Spring Boot приложений с Maven Wrapper (`mvnw`). Этот подход не требует предустановленного Maven — wrapper сам скачает нужную версию:

```dockerfile
# --- Этап 1: Сборка (builder) ---
FROM eclipse-temurin:21-jdk AS builder
WORKDIR /app

# Копируем Maven Wrapper и pom.xml для кеширования зависимостей
COPY .mvn/ .mvn
COPY mvnw pom.xml ./

# Скачиваем зависимости (без сборки) — слой кешируется
RUN ./mvnw dependency:go-offline

# Копируем исходный код и собираем JAR
COPY src ./src
RUN ./mvnw clean package -DskipTests

# --- Этап 2: Финальный образ (production) ---
FROM eclipse-temurin:21-jre
WORKDIR /app

# Копируем JAR из builder
COPY --from=builder /app/target/*.jar app.jar

EXPOSE 8080

# Запуск с указанием максимальной доли RAM для кучи
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]
```

**Ключевые моменты:**

- Maven Wrapper (`mvnw`) — скрипт, автоматически загружающий нужную версию Maven
- Файл `.mvn/wrapper/maven-wrapper.properties` определяет версию Maven и JDK
- Раздельное копирование `.mvn/`, `mvnw`, `pom.xml` и `src/` позволяет кешировать слой зависимостей
- Флаг `-DskipTests` ускоряет сборку; для production рекомендуется запускать тесты

**Типичный размер образа:**

- Без многоэтапной сборки (с JDK): ~800-900 МБ
- С многоэтапной сборкой (JRE only): ~400-450 МБ
- С jlink (кастомный JRE): ~150-250 МБ

### Сценарий 3: Корректная настройка памяти

- **Современные версии Java (JDK 10+):**
    Используйте процентные значения. JVM сама рассчитает размер кучи на основе лимита памяти контейнера.

    ```shell
    # JVM выделит под кучу не более 75% от памяти, доступной контейнеру
    CMD ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]
    ```

- **Старые версии Java (JDK 8 до 8u191):**
    Задавайте размер кучи вручную через флаг `-Xmx`.

    ```shell
    # Явно выделяем 256 мегабайт под кучу
    # Лимит памяти контейнера должен быть больше (например, 384 МБ)
    CMD ["java", "-Xmx256m", "-jar", "app.jar"]
    ```

    Для версий до 8u191 **обязательно** задавайте размер кучи через `-Xmx` и `-Xms`, иначе JVM не учтет лимиты контейнера.
