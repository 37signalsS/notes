# Dockerfile: Лучшие практики для Node.js

## Определения

- **`package.json`:** Манифест проекта, описывающий его атрибуты и зависимости.
- **`package-lock.json`:** Файл, который "замораживает" дерево зависимостей, записывая точные версии каждого установленного пакета.
- **`npm ci` (Clean Install):** Команда, которая удаляет `node_modules` и устанавливает зависимости строго в соответствии с `package-lock.json`. Гарантирует воспроизводимость сборок.
- **`dependencies`:** Зависимости, необходимые для работы приложения в рабочей (production) среде (например, `express`, `axios`).
- **`devDependencies`:** Зависимости, необходимые только для разработки и тестирования (например, `typescript`, `jest`, `eslint`).
- **CI/CD (Continuous Integration / Continuous Deployment):** Практики автоматизации интеграции и доставки программного обеспечения.

## Основные концепции

### Воспроизводимость сборок

Для сборок в рабочей среде всегда следует использовать `npm ci` вместо `npm install`.

- **`npm install`**: Генерирует `package-lock.json` на основе `package.json` (если lock-файла ещё нет) и может изменять его при обновлениях. Используется для локальной разработки.
- **`npm ci`**: Гарантирует детерминированную и воспроизводимую сборку. Команда устанавливает зависимости, строго по `package-lock.json`, и никогда не изменяет этот файл.

**Важно:** `npm ci` требует, чтобы `package-lock.json` уже существовал в репозитории. Его создают локально через `npm install` и коммитят. Если `package.json` и `package-lock.json` не синхронизированы, `npm ci` завершится с ошибкой.

### Минимизация образа

Флаг `--omit=dev` указывает `npm` не устанавливать `devDependencies` в `node_modules`. Принимает значения `dev`, `optional`, `peer` (можно комбинировать: `--omit=dev --omit=optional`). Начиная с npm 7+ флаг `--only=production` считается устаревшим — вместо него используется `--omit=dev`. Если требуется поддержка npm версии ниже 7, используйте `--only=production` для обратной совместимости. Это критически важно для Docker-образов, так как исключает ненужные инструменты разработки, делая итоговый образ значительно меньше и безопаснее. Эта практика реализуется с помощью [многоэтапной сборки](./build_optimization.md).

`npm ci` читает из кеша npm (`~/.npm/_cacache/`), если нужные tarball'ы уже там есть, и записывает в кеш при скачивании отсутствующих. Параметры `--cache` и кеширование `~/.npm` в CI имеют смысл именно потому, что `npm ci` использует кеш.

Кеш не нужен для работы приложения, но сохраняется в слое образа. Простой `npm cache clean --force` в отдельном `RUN` не уменьшает итоговый образ — данные из предыдущего слоя остаются в истории. Очистка эффективна только в одном `RUN` через `&&`:

```dockerfile
RUN npm ci --omit=dev && npm cache clean --force
```

Более надёжный подход — перенаправить кеш во временную директорию и удалить её:

```dockerfile
RUN npm ci --omit=dev --cache=/tmp/npm-cache && rm -rf /tmp/npm-cache
```

Это гарантированно не оставляет следов кеша в образе.

### NODE_ENV=production

Переменная окружения `NODE_ENV=production` — не аналог `--omit=dev`. Они решают разные задачи:

- `--omit=dev` — влияет на установку пакетов (что попадает в `node_modules`)
- `NODE_ENV=production` — влияет на поведение приложения во время выполнения

Без `NODE_ENV=production` Express отдаёт полный stack trace ошибок, библиотеки включают debug-режим, а код может выполнять ненужные проверки. Это не только небезопасно, но и добавляет лишние накладные расходы.

В Dockerfile `ENV NODE_ENV=production` устанавливается после установки зависимостей, но до запуска приложения.

## Практические сценарии

### Сценарий 1: Оптимизированная многоэтапная сборка

Этот пример демонстрирует [многоэтапную сборку](./build_optimization.md) для типичного Node.js-приложения, которое требует компиляции (например, TypeScript, React, Vue).

```dockerfile
# --- Этап 1: Сборка (Builder) ---
# На этом этапе используется полный образ, содержащий все devDependencies для сборки.
FROM node:24-alpine AS builder
WORKDIR /app

# Кешируем зависимости — копируем только манифесты перед установкой
COPY package.json package-lock.json ./
RUN npm ci --cache=/tmp/npm-cache && rm -rf /tmp/npm-cache

# Копируем исходники и собираем билд
COPY . .
RUN npm run build

# --- Этап 2: Финальный образ (Final) ---
# Начинаем с чистого, легковесного образа
FROM node:24-alpine
WORKDIR /app

# Копируем package.json, чтобы установить ТОЛЬКО зависимости для работы (production)
COPY package.json package-lock.json ./
RUN npm ci --omit=dev --cache=/tmp/npm-cache && rm -rf /tmp/npm-cache

# Копируем скомпилированное приложение из этапа "builder"
COPY --from=builder /app/dist ./dist

# Создаем непривилегированного пользователя для повышения безопасности
RUN adduser -D -S nonroot
USER nonroot

# Устанавливаем production-режим — влияет на поведение Express и библиотек
ENV NODE_ENV=production

EXPOSE 3000
CMD [ "node", "dist/index.js" ]
```

**Ключевые этапы:**

1. **Этап `builder`:**
    - Устанавливаются все зависимости, включая `devDependencies`.
    - Выполняется команда `npm run build` для компиляции TypeScript в JavaScript, сборки фронтенда и т. д.
2. **Этап `final`:**
    - Устанавливаются только `dependencies`, необходимые для запуска. `devDependencies` (компиляторы, линтеры) не попадают в конечный образ.
    - Результат сборки (папка `dist`) копируется из этапа `builder`.
    - Создается и активируется [непривилегированный пользователь](./security.md) для повышения безопасности — переключение на него выполняется после всех операций, требующих прав root.
    - В итоге получается минималистичный и безопасный образ.
