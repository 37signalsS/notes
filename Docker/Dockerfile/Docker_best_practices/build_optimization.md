# Оптимизация сборки Docker-образов

## Определения

- **Кеширование слоев (Layer Caching):** Механизм Docker, который сохраняет результаты выполнения каждой инструкции в `Dockerfile` (слоя). При последующих сборках Docker повторно использует неизмененные слои из кеша, вместо того чтобы выполнять их заново, что значительно ускоряет процесс.
- **Многоэтапные сборки (Multi-stage Builds):** Техника, позволяющая использовать несколько инструкций `FROM` в одном `Dockerfile`. Это дает возможность разделить процесс сборки на несколько этапов (например, компиляция в одном образе и упаковка в другом), копируя только необходимые артефакты между ними.

## Основные концепции

### Принцип работы кеширования слоев

Ключ к быстрой сборке — правильная организация `Dockerfile` для максимального использования кеша. Слой считается невалидным (и требует пересборки), если изменился файл, который он копирует, или изменилась сама инструкция. Все последующие слои также будут пересобраны.

Поэтому инструкции следует располагать в порядке **от наименее часто изменяемых к наиболее часто изменяемым**:

1. Установка системных зависимостей.
2. Установка языковых зависимостей (`requirements.txt`, `package.json`).
3. Копирование исходного кода приложения.

### Проблема, решаемая многоэтапными сборками

Для сборки компилируемых приложений (например, на Go, Java, C++) часто требуется "тяжелый" образ с SDK, компиляторами и сборочными инструментами. Однако для запуска скомпилированного приложения нужен лишь легковесный runtime-образ (например, `alpine` или `distroless`).

Многоэтапная сборка решает эту проблему, позволяя использовать "тяжелый" образ как временный "сборщик" (`builder`), а в финальный, легковесный образ копировать только результат его работы (скомпилированный бинарный файл или JAR-архив). Это кардинально уменьшает размер и поверхность атаки конечного образа.

## Практические сценарии

### Сценарий 1: Эффективное кеширование зависимостей

**Плохой пример (без учета кеша):**

```dockerfile
FROM python:3.13-slim-bookworm
# Копируем все сразу. Любое изменение в коде инвалидирует кеш.
COPY . .

# Устанавливаем зависимости. Эта команда будет выполняться при каждой сборке.
RUN pip install -r requirements.txt

CMD ["python", "main.py"]
```

**Проблема:** При любом изменении в коде приложения слой `COPY . .` становится невалидным. Это делает невалидными все последующие слои, и Docker будет **каждый раз заново** выполнять дорогостоящую команду `RUN pip install`.

**Хороший пример (с оптимизацией кеша):**

```dockerfile
FROM python:3.13-slim
WORKDIR /app

# 1. Копируем только файл с зависимостями, который меняется редко.
COPY requirements.txt .

# 2. Устанавливаем зависимости. Этот слой будет закеширован надолго.
RUN pip install -r requirements.txt

# 3. Только теперь копируем остальной код, который меняется часто.
COPY . .

CMD ["python", "main.py"]
```

**Результат:** Теперь, если вы меняете только код приложения, Docker использует кеш для слоя с `RUN pip install`. Пересборка происходит почти мгновенно, так как пересоздается только последний, очень "легкий" слой `COPY . .`.

### Сценарий 2: Создание минималистичного образа с помощью Multi-stage сборки

```dockerfile
# --- Этап 1: Сборка (Builder) ---
# Начинаем с полного образа Go, который содержит все инструменты для сборки.
# Даем этому этапу имя "builder" для удобства обращения.
FROM golang:1.25.1 AS builder

WORKDIR /app

# Кешируем зависимости
COPY go.mod go.sum ./
RUN go mod download

# Копируем остальной код и собираем статически скомпонованный бинарник.
# CGO_ENABLED=0 отключает использование C-библиотек.
COPY . .
RUN CGO_ENABLED=0 go build -o /app/main .

# --- Этап 2: Финальный образ (Final) ---
# Начинаем с "пустого" образа scratch. В нем нет ничего, даже оболочки.
# Он идеально подходит для запуска одного статически скомпонованного бинарника.
FROM scratch

WORKDIR / 

# Копируем ТОЛЬКО скомпилированный бинарный файл из этапа "builder".
COPY --from=builder /app/main .

ENTRYPOINT ["/main"]
```

Этот подход значительно уменьшает размер конечного образа и повышает его безопасность, так как в нем отсутствуют какие-либо инструменты, которые могли бы использовать злоумышленники.
