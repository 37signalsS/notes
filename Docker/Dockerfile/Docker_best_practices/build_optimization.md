# Оптимизация сборки Docker-образов

## Определения

- **Кеширование слоев (Layer Caching):** Механизм Docker, который сохраняет результаты выполнения каждой инструкции в `Dockerfile` (слоя). При последующих сборках Docker повторно использует неизмененные слои из кеша, что значительно ускоряет процесс.
- **Многоэтапные сборки (Multi-stage Builds):** Техника, позволяющая использовать несколько инструкций `FROM` в одном `Dockerfile`. Это дает возможность разделить процесс сборки на несколько этапов, копируя только необходимые артефакты между ними и создавая минималистичные конечные образы.
- **Контекст сборки (Build Context):** Набор файлов и каталогов, находящихся в указанном пути, который Docker-клиент отправляет демону Docker перед началом сборки. Инструкции `COPY` и `ADD` могут ссылаться только на файлы внутри контекста.

## Базовые концепции

### Эффективное использование кеша слоев

Ключ к быстрой сборке — правильная организация `Dockerfile` для максимального использования кеша. При каждой сборке Docker проверяет, можно ли переиспользовать результат выполнения инструкции из предыдущей сборки. Если слой уже существует и не изменился, Docker использует результат из кеша (в выводе это видно по метке `Using cache`).

**Причины инвалидации кеша (потери кеша):**

1. **Изменение инструкции `RUN`:** любое изменение содержимого команды — добавление пакета, изменение флага, новый аргумент — делает слой новым.
2. **Изменение файлов в `COPY`/`ADD`:** Docker отслеживает содержимое, права доступа (permissions) и владельца (owner/group) копируемых файлов. Даже изменение прав (`chmod`) без изменения содержимого инвалидирует кеш.
3. **Каскадная инвалидация:** если любой предыдущий слой (включая базовый образ или промежуточный слой) был инвалидирован, Docker гарантирует, что **все последующие слои** также будут пересобраны, независимо от того, изменились они или нет.

**Правило:** Располагайте инструкции в порядке **от наименее часто изменяемых к наиболее часто изменяемым**. Это позволяет переиспользовать кеш для верхних слоёв, пересобирая только то, что действительно изменилось. Вниз (в конец) файла выносятся инструкции, которые меняются при каждой сборке (например, `COPY . .` с исходным кодом).

### Минимизация количества и размера слоев

Каждая инструкция `RUN`, `COPY`, `ADD` создает новый слой. Большое количество слоев может незначительно замедлять развертывание. Важнее то, что каждый слой увеличивает общий размер образа, если не производить очистку.

**Правило:** Объединяйте логически связанные `RUN` команды в одну инструкцию с помощью `&&` и удаляйте временные файлы и кеши в той же команде.

### Уменьшение контекста сборки с помощью `.dockerignore`

Перед сборкой Docker-клиент упаковывает все файлы из контекста сборки и отправляет их демону. Большой контекст замедляет начало сборки. Файл `.dockerignore` позволяет исключить ненужные файлы и каталоги (например, `.git`, `node_modules`, `*.log`), уменьшая размер контекста и предотвращая случайное попадание секретов в образ. Подробнее см. [Контекст сборки (Build Context) и .dockerignore](../dockerfile_build_context.md).

### Явное копирование файлов

Избегайте инструкции `COPY . .` без необходимости. Копирование всех файлов из контекста в образ — плохая практика, так как в образ попадают ненужные файлы (документация, тесты, конфигурации IDE, секреты). Копируйте явно только то, что требуется для сборки и запуска приложения:

```dockerfile
# Плохо — копирует всё, включая лишние файлы
COPY . .

# Хорошо — копирует только необходимые файлы явно
COPY requirements.txt .
COPY src/ ./src/
COPY config/ ./config/
```

Такой подход уменьшает размер образа, повышает безопасность и делает Dockerfile документированным — по инструкциям `COPY` видно, какие файлы действительно нужны приложению.

### Использование Multi-stage сборок

Для компилируемых приложений (Go, Java, C++) часто требуется "тяжелый" образ с SDK (Software Development Kit) и инструментами. Для запуска же нужен лишь легковесный runtime. Multi-stage сборка позволяет использовать "тяжелый" образ как временный "сборщик" (`builder`), а в финальный образ копировать только результат его работы (бинарный файл, JAR-архив). Подробнее о выборе минималистичных базовых образов (`scratch`, `distroless`) см. [Лучшие практики безопасности](./security.md).

#### Основные принципы

Каждый stage начинается с инструкции `FROM` и может иметь имя (указывается через `AS <name>`). Имена стейджей используются для копирования артефактов через `COPY --from=<name>`:

```dockerfile
# Этап 1: Сборка — тяжёлый образ с JDK и инструментами
FROM eclipse-temurin:21-jdk AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

# Этап 2: Финальный образ — лёгкий JRE (Java Runtime Environment) только для запуска
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**Ключевые моменты:**

- Стейджи выполняются последовательно сверху вниз
- Последний stage — дефолтный target сборки (если не указан `--target`)
- Артефакты копируются через `COPY --from=<stage_name>`
- Промежуточные стейджи не попадают в финальный образ

#### Выборочная сборка стейджа через `--target`

Docker позволяет собрать только определённый stage, используя флаг `--target`:

```bash
# Собрать только stage "builder" (для отладки или тестирования)
docker build --target builder -t myapp:builder .

# Собрать финальный stage (по умолчанию — последний)
docker build -t myapp:latest .
```

Это полезно для:

- Отладки промежуточных артефактов (проверить содержимое builder)
- Тестирования сборки без создания финального образа
- Создания нескольких вариаций образа из одного Dockerfile

#### Влияние multi-stage на безопасность контейнера

Multi-stage сборка — критическая практика не только для оптимизации размера, но и для **сокращения поверхности атаки** контейнера:

- **Исключение инструментов сборки**: Компиляторы (`gcc`, `g++`, `rustc`), утилиты (`make`, `cmake`), менеджеры зависимостей (`poetry`, `npm`, `maven`) остаются в промежуточных этапах и не попадают в финальный образ.
- **Удаление dev-пакетов**: Заголовочные файлы (`lib*-dev`), отладчики (`gdb`, `strace`) и тестовые зависимости, содержащие CVE (Common Vulnerabilities and Exposures), не устанавливаются в production.
- **Принцип наименьших привилегий**: Финальный образ содержит только runtime-зависимости, необходимые для выполнения приложения, что усложняет эксплуатацию уязвимостей.
- **Упрощение аудита**: Минимальный образ проще сканировать на уязвимости и легче сопровождать. Подробнее о сканировании см. [Сканирование уязвимостей](../../Docker_security/vulnerability_scanning.md).

#### Создание минимального JRE через JLink

Для Java-приложений можно создать кастомный runtime-образ, включающий только необходимые модули JDK (Java Development Kit), используя утилиту `jlink` (начиная с JDK 9+):

```dockerfile
# Этап 1: Сборка приложения
FROM eclipse-temurin:21-jdk AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

# Этап 2: Создание минимального JRE через jlink
FROM eclipse-temurin:21-jdk AS jre-builder
RUN jlink \
    --add-modules java.base,java.logging,java.sql \
    --output /custom-jre \
    --strip-debug \
    --no-man-pages \
    --no-header-files \
    --compress=2

# Этап 3: Финальный образ с кастомным JRE
FROM debian:bookworm-slim
COPY --from=jre-builder /custom-jre /opt/java/jre
COPY --from=builder /app/target/*.jar /app/app.jar
ENV JAVA_HOME=/opt/java/jre
ENTRYPOINT ["/opt/java/jre/bin/java", "-jar", "/app/app.jar"]
```

**Преимущества jlink:**

- Размер JRE может быть уменьшен на 50-80% по сравнению с полным JDK/JRE
- Включаются только необходимые Java-модули
- Повышается безопасность за счёт удаления неиспользуемых компонентов

**Примечание:** Требуется анализ зависимостей приложения для определения необходимых модулей (`java.base` — обязательный модуль).

### Неочевидные источники увеличения размера

- **Изменение прав доступа:** Команды `RUN chmod` или `RUN chown` создают новый слой, который может содержать полную копию файла или директории с новыми правами. Для больших файлов это приводит к значительному увеличению размера итогового образа.
- **"Раздутые" пакеты:** Некоторые пакеты (gems, npm-модули и т.д.) поставляются с ненужными для production-среды файлами: документацией, тестами или бинарными файлами для других операционных систем. Эти файлы следует находить и удалять в том же слое `RUN`, где устанавливается пакет. Для анализа слоев используйте [инструменты оптимизации Dockerfile](../dockerfile_optimization_tools.md) (например, `dive`).

### Использование образа `scratch`

**`scratch`** — это зарезервированное имя в Docker, обозначающее абсолютно пустой образ. Он не содержит файловой системы, библиотек и оболочки (shell).

#### Преимущества:
- **Минимальный размер**: Образ содержит только бинарный файл приложения.
- **Максимальная безопасность**: Отсутствие лишних утилит (curl, sh, apt) сводит поверхность атаки к минимуму. У злоумышленника нет инструментов для закрепления в системе.
- **Скорость**: Мгновенная загрузка и запуск образа.

#### Недостатки и сложности:
- **Отсутствие Shell**: Вы не сможете выполнить `docker exec -it <container> sh`. В образе просто нет командного интерпретатора.
- **Сложность отладки**: Традиционные методы диагностики не работают. Требуется использование **[эфемерных контейнеров](../../Kubernetes/Base/Pod/ephemeral_containers.md)** в Kubernetes или копирование отладочных утилит на этапе сборки.
- **Зависимости от библиотек**: Для работы в `scratch` бинарный файл должен быть скомпилирован статически (например, `CGO_ENABLED=0` для Go), иначе он не запустится из-за отсутствия `libc`.

### Сценарии использования

### Сценарий 1: Эффективное кеширование зависимостей (Node.js/Python)


Этот пример демонстрирует принцип кеширования для приложений с файловыми менеджерами зависимостей (`package.json` + `yarn.lock` / `requirements.txt`). Подробнее о лучших практиках см. [Dockerfile: Лучшие практики для Node.js](./nodejs.md) и [Dockerfile: Лучшие практики для Python](./python.md).

**Плохо (без учёта кеша):**

```dockerfile
COPY . .
RUN yarn install --production
# или: RUN pip install -r requirements.txt
```

*Проблема:* Любое изменение в коде инвалидирует слой `COPY . .`, что вызывает каскадную пересборку всех последующих слоёв. Установка зависимостей выполняется каждый раз заново, даже если `package.json` / `yarn.lock` не менялись.

**Хорошо (с оптимизацией кеша):**

```dockerfile
# 1. Копируем только файлы с зависимостями (меняются редко).
COPY package.json yarn.lock .
# 2. Устанавливаем зависимости (этот слой остаётся в кеше, пока не изменятся файлы зависимостей).
RUN yarn install --production
# 3. Копируем остальной код (меняется часто).
COPY . .
```

*Результат:* Пересборка происходит почти мгновенно — Docker переиспользует кеш для слоёв 1 и 2, пересобирая только последний слой с кодом.

### Сценарий 2: Уменьшение количества слоев и размера образа

Этот пример демонстрирует принцип минимизации слоев для Debian/Ubuntu-образов. Важно помнить: файлы, удаленные в последующих слоях `RUN`, не уменьшают размер итогового образа (см. **[Механизм удаления файлов](../../Docker_fs/images/layer_management.md#персистентность-удаленных-файлов-и-размер-образа)**).

**Плохо (много слоев, пакеты остаются в истории):**

```dockerfile
RUN apt-get update
RUN apt-get install -y curl
RUN curl -o /tmp/data.zip http://example.com/data.zip
RUN unzip /tmp/data.zip -d /app
# Удаление в отдельном слое НЕ уменьшит размер образа!
RUN rm /tmp/data.zip && apt-get purge -y curl
```

*Проблема:* Создается 5 слоев. Файлы, установленные/скачанные в первых четырех слоях, физически остаются в них навсегда. Пятый слой лишь скрывает их.

**Хорошо (один слой с очисткой):**

```dockerfile
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && curl -o /tmp/data.zip http://example.com/data.zip \
 && unzip /tmp/data.zip -d /app \
 && apt-get purge -y --auto-remove curl \
 && rm -rf /var/lib/apt/lists/* /tmp/data.zip
```

*Результат:* Создается один слой, а временные файлы и ненужные пакеты удаляются в той же инструкции, не попадая в итоговый образ. Слой содержит только распакованное содержимое `/app`.

### Сценарий 3: Создание минималистичного образа (Go) с Multi-stage

Это пример использования многоэтапной сборки для Go-приложений. Подробнее о лучших практиках для Go см. [Dockerfile: Лучшие практики для Go](./go.md).

```dockerfile
# --- Этап 1: Сборка (Builder) ---
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app/main .

# --- Этап 2: Финальный образ (Final) ---
# Начинаем с "пустого" образа scratch.
FROM scratch
WORKDIR / 
# Копируем ТОЛЬКО скомпилированный бинарник из этапа "builder".
COPY --from=builder /app/main .
ENTRYPOINT ["/main"]
```

*Результат:* Финальный образ содержит только один бинарный файл, что делает его чрезвычайно маленьким и безопасным. Обратите внимание: отсутствие shell в образах `scratch` и `distroless` усложняет отладку — руководство по решению этой проблемы см. в [Отладка distroless-контейнеров](../../Docker_troubleshooting/debugging_distroless.md).

### Сценарий 4: Установка зависимостей без копирования с помощью `RUN --mount`

При использовании multi-stage сборок часто требуется передать артефакты (например, скомпилированные wheel-пакеты в Python) из одного этапа в другой для установки, но сами артефакты в финальном образе не нужны. Вместо `COPY` можно использовать `--mount=type=bind`, чтобы временно "примонтировать" директорию из другого этапа. Эта возможность требует использования [BuildKit](../dockerfile_buildkit.md) — современного движка сборки, включенного по умолчанию в новых версиях Docker.

```dockerfile
# --- Этап 1: Сборка wheel-пакетов ---
FROM python:3.11-alpine AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip wheel --no-cache-dir --wheel-dir /app/wheels -r requirements.txt

# --- Этап 2: Финальный образ ---
FROM python:3.11-alpine
WORKDIR /app
# Монтируем wheels из builder'а, устанавливаем и сразу забываем о них.
# Папка /wheels не копируется в слой и не попадает в итоговый образ.
RUN --mount=type=bind,from=builder,source=/app/wheels,target=/wheels \
    pip install --no-cache-dir --no-index --find-links=/wheels /wheels/*
COPY . .
CMD ["python", "app.py"]
```

*Результат:* Установка пакетов происходит из временной директории, которая не сохраняется в слоях образа, что значительно уменьшает его итоговый размер.
