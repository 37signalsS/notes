# Оптимизация сборки Docker-образов

## Определения

- **Кэширование слоев (Layer Caching):** Механизм Docker, сохраняющий результат каждой инструкции `Dockerfile` в виде неизменяемого слоя. При повторных сборках Docker переиспользует существующие слои, если инструкция и контекст не изменились.
- **Многоэтапная сборка (Multi-stage Builds):** Техника использования нескольких инструкций `FROM` в одном файле. Позволяет разделить среду сборки (тяжелую, с компиляторами) и среду выполнения (минимальную, только с бинарником).
- **Контекст сборки (Build Context):** Набор локальных файлов, отправляемых Docker-клиентом демону (или инстансу BuildKit) перед началом сборки. Оптимизация контекста напрямую влияет на скорость старта сборки.
- **BuildKit:** Современный движок сборки, использующий граф зависимостей (LLB) для параллельного выполнения команд и поддерживающий расширенные возможности (маунты, секреты, кэширование).
- **Аттестации (Attestations):** Метаданные (SBOM, Provenance), прикрепляемые к образу. Хотя они увеличивают размер метаданных, они оптимизируют процесс аудита безопасности в CI/CD.

## Базовые концепции

### Сравнение: Компилируемые vs Интерпретируемые языки

Оптимизация зависит от природы языка программирования.

| Критерий | Компилируемые (Go, Rust, C++) | Интерпретируемые (Python, Ruby, Node.js) |
| :--- | :--- | :--- |
| **Артефакт** | Одиночный статический бинарник или набор библиотек. | Исходный код и дерево зависимостей в папках типа `node_modules`. |
| **Multi-stage** | **Критически важен.** Образ сборщика весит >1 ГБ, финальный образ — <50 МБ. | **Желателен.** Для удаления инструментов компиляции нативных расширений и кэшей пакетных менеджеров. |
| **Стратегия кэширования** | Кэширование сборочных директорий компилятора (`target`, `build`). | Кэширование директорий менеджеров пакетов (`~/.npm`, `~/.cache/pip`). |

### Механизм инвалидации кэша

Для эффективной сборки инструкции должны располагаться в порядке **от редко изменяемых к часто изменяемым**.

1.  **Инструкции RUN:** Любое изменение текста команды (даже добавление пробела) инвалидирует слой.
2.  **Инструкции COPY/ADD:** Docker проверяет контрольные суммы файлов. Если изменился хотя бы один бит, кэш этого слоя и **всех последующих** сбрасывается.
3.  **Каскадная инвалидация:** Если слой N изменился, слои N+1, N+2 и т.д. будут пересобраны принудительно.

### Оптимизация через BuildKit Mounts

Традиционный `npm install` или `pip install` скачивает пакеты заново при каждом изменении файла манифеста. BuildKit решает это через временные монтирования:

- **`--mount=type=cache`:** Подключает постоянную директорию на хосте к контейнеру сборки. Кэш сохраняется между сборками и не попадает в итоговые слои образа.
- **`--mount=type=bind`:** Позволяет использовать файлы из других стадий без их копирования через `COPY`, что экономит место в слоях.

### Независимые слои с COPY --link

При обычном `COPY` изменение файла в начале `Dockerfile` сбрасывает кэш для всех последующих слоев. Флаг `--link` (требует BuildKit) копирует файлы в абсолютно независимые слои. Если вы измените файл, скопированный через `--link`, Docker просто заменит этот слой в графе, не пересобирая остальные.

### Мультиплатформенность и кросс-компиляция

Для сборки под разные архитектуры (например, ARM64 для облаков и AMD64 для локальной разработки) используйте встроенные переменные:
- `BUILDPLATFORM` — архитектура хоста, где идет сборка.
- `TARGETARCH` — целевая архитектура образа.
Это позволяет запускать компилятор на «родной» скорости хоста, генерируя бинарник для другой платформы без использования медленной эмуляции QEMU.

## Практические сценарии

### Сценарий 1: Профессиональное кэширование зависимостей (Node.js)

Использование монтирования кэша и `COPY --link` для максимальной скорости.

```dockerfile
# syntax=docker/dockerfile:1
FROM node:22-alpine AS builder
WORKDIR /app

# Копируем манифесты в независимый слой
COPY --link package.json package-lock.json ./

# Используем монтирование кэша для папки .npm
# Кэш не сохраняется в образе, но доступен при следующей сборке
RUN --mount=type=cache,target=/root/.npm \
    npm ci

COPY --link . .
RUN npm run build

# Финальный образ
FROM nginx:alpine
COPY --from=builder --link /app/dist /usr/share/nginx/html
```

### Сценарий 2: Минимизация слоев и очистка (Debian/Ubuntu)

Объединение команд и удаление временных файлов в одном слое `RUN`.

```dockerfile
# Плохо: пакеты и кэш apt остаются в скрытых слоях
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# Хорошо: один слой, чистый результат
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*
```

### Сценарий 3: Кросс-компиляция Go без эмуляции

Использование платформенных переменных для ускорения сборки мультиархитектурных образов.

```dockerfile
# syntax=docker/dockerfile:1
FROM --platform=$BUILDPLATFORM golang:1.23-alpine AS builder
WORKDIR /app

# TARGETARCH подставляется BuildKit автоматически при --platform
ARG TARGETARCH
COPY . .

# Компилируем под целевую архитектуру, используя нативный компилятор хоста
RUN CGO_ENABLED=0 GOARCH=$TARGETARCH go build -o /main .

FROM scratch
COPY --from=builder /main /main
ENTRYPOINT ["/main"]
```

### Сценарий 4: Передача артефактов через Bind Mounts

Экономия места за счет монтирования вместо копирования.

```dockerfile
# Стейдж сборки фронтенда
FROM node:22 AS frontend-builder
WORKDIR /web
COPY . .
RUN npm run build

# Стейдж сборки бэкенда (Go)
FROM golang:1.23 AS backend-builder
WORKDIR /app
COPY . .
# Монтируем статику фронтенда только на время встраивания в бинарник
RUN --mount=type=bind,from=frontend-builder,source=/web/dist,target=/app/static \
    go build -o /app/server .
```
