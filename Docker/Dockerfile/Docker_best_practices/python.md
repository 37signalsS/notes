# Dockerfile: Лучшие практики для Python

## Определения

- **`Wheels (*.whl)`:** Предварительно скомпилированный формат дистрибуции пакетов Python. Установка из `wheels` значительно быстрее, чем из исходного кода, так как не требует локальной компиляции.
- **`glibc (GNU C Library)` vs `musl libc`:** Две разные реализации стандартной библиотеки языка C. `Wheels`, скомпилированные для `glibc` (используется в Debian/Ubuntu), несовместимы с `musl` (используется в Alpine), что может приводить к ошибкам сборки или работы приложения.
- **`pip (Preferred Installer Program)`:** Стандартный менеджер пакетов для Python, используемый для установки библиотек из `PyPI (Python Package Index)` или других репозиториев.
- **`venv (virtual environment)`:** Инструмент для создания изолированных окружений Python, позволяющий разделять зависимости разных проектов.
- **ЦП (Центральный процессор):** Основной вычислительный ресурс сервера, лимиты которого настраиваются через `cgroups` в Docker.

## Основные концепции

### Выбор базового образа

- **`python:<version>` (Full Debian)**
  - **Содержимое:** Полноценный дистрибутив Debian с Python и полным набором инструментов для сборки (`SDK` — Software Development Kit, включая `gcc`, `make` и библиотеки).
  - **Плюсы:** Максимальная совместимость. Пакеты с C-расширениями устанавливаются без проблем.
  - **Минусы:** Большой размер образа, широкая поверхность атаки.
  - **Итог:** Использовать только в исключительных случаях, когда сборка на базе `slim` невозможна.

- **`python:<version>-slim` (Slim Debian)**
  - **Содержимое:** Облегчённый Debian с Python, но без предустановленных инструментов сборки.
  - **Плюсы:** Меньший размер и поверхность атаки при сохранении совместимости с большинством `wheels` благодаря `glibc`.
  - **Минусы:** При необходимости компиляции пакетов требуется временная установка пакета `build-essential`.
  - **Итог: Рекомендуемый выбор для большинства приложений.** Оптимальный баланс размера и совместимости.

- **`python:<version>-alpine` (Alpine Linux)**
  - **Содержимое:** Минималистичный дистрибутив на базе `musl libc`.
  - **Плюсы:** Минимальный размер образа.
  - **Минусы:** Проблемы совместимости с бинарными пакетами. Многие `wheels` из `PyPI` требуют `glibc`, что заставляет `pip` компилировать их из исходников, усложняя `Dockerfile` и увеличивая время сборки.
  - **Итог:** Использовать только если размер образа критически важен и зависимости проекта полностью совместимы с `musl`.

### Воспроизводимость и кеширование сборок

1. **Фиксация зависимостей:** Используйте файл `requirements.txt`, сгенерированный через `pip freeze` или специализированные инструменты (Poetry, PDM), для фиксации точных версий.
2. **Оптимизация кеширования слоев:** Сначала копируйте только файл со списком зависимостей, выполняйте установку, и только затем копируйте код приложения. Это позволяет Docker использовать кеш для слоя библиотек при изменении только бизнес-логики. Подробнее см. [Оптимизация сборки Docker-образов](./build_optimization.md).

### Один процесс на контейнер

Контейнер должен выполнять одну задачу. Служебные операции, такие как миграции базы данных, должны выполняться в отдельных запусках (например, через `Init Containers` в Kubernetes или отдельные задачи CI/CD), а не в рамках команды запуска основного веб-сервера.

## Практические сценарии

### Сценарий 1: Оптимизированный Dockerfile для Django/Flask

Пример эффективной настройки для типового веб-приложения на базе `slim`.

```dockerfile
# Используем slim-образ как рекомендованную основу
FROM python:3.13-slim

# Настройка переменных окружения Python
# PYTHONDONTWRITEBYTECODE: запрет генерации .pyc файлов (экономия места)
# PYTHONUNBUFFERED: немедленный вывод логов в stdout/stderr (важно для мониторинга)
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /app

# Создаем непривилегированного пользователя для защиты от эксплойтов
RUN adduser --system --group appuser

# Оптимизируем кеширование: установка зависимостей до копирования кода
COPY requirements.txt .
RUN pip install -r requirements.txt

# Копируем исходный код приложения
COPY . .

# Сборка статики (для Django) выполняется на этапе создания образа
RUN python manage.py collectstatic --no-input

# Переключаемся на пользователя с ограниченными правами
USER appuser

# Запуск через WSGI-сервер (например, Gunicorn)
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "myapp.wsgi:application"]
```

Подробнее о безопасности и минимизации рисков `CVE` (Common Vulnerabilities and Exposures) см. [Безопасность в Dockerfile](./security.md).

### Сценарий 2: Многоэтапная сборка с виртуальным окружением

Используется, когда зависимости требуют компиляции, но инструменты сборки не должны попасть в финальный образ. Подробнее см. [Многоэтапные сборки](./build_optimization.md).

```dockerfile
# --- Этап 1: Сборщик (builder) ---
FROM python:3.12 AS builder
WORKDIR /app
# Создаем изолированное окружение venv
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
# Установка зависимостей (включая компиляцию C-расширений)
COPY requirements.txt .
RUN pip install -r requirements.txt

# --- Этап 2: Финальный образ ---
FROM python:3.12-slim
WORKDIR /app
# Копируем только готовое окружение без инструментов сборки
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1
# Копируем только код приложения
COPY . .
CMD ["python", "./server.py"]
```

### Сценарий 3: Разделение задач (миграции и запуск)

Использование `entrypoint.sh` для управления режимом работы контейнера через переменные окружения.

```sh
#!/bin/sh
set -e # Выход при любой ошибке

if [ "$MODE" = "migrate" ]; then
    echo "Выполнение миграций БД..."
    python manage.py migrate
elif [ "$MODE" = "start" ]; then
    echo "Запуск приложения..."
    exec gunicorn myapp.wsgi:application --bind 0.0.0.0:8000
else
    # Выполнение произвольной команды (например, bash для отладки)
    exec "$@"
fi
```
