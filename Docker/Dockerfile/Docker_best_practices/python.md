# Dockerfile: Лучшие практики для Python

## Определения

- **`Wheels (*.whl)`:** Предварительно скомпилированный формат дистрибуции пакетов Python. Установка из `wheels` значительно быстрее, чем из исходников, так как не требует локальной компиляции.
- **`glibc` vs `musl`:** Две разные реализации стандартной библиотеки языка C. `Wheels`, скомпилированные для одной (например, `glibc` в Debian), несовместимы с другой (`musl` в Alpine), что может приводить к ошибкам сборки.

## Основные концепции

### Концепция 1: Выбор базового образа

- **`python:<version>` (Full Debian)**
  - **Содержимое:** Полноценный Debian с Python и **полным набором инструментов для сборки** (`gcc`, `make` и т.д.).
  - **Плюсы:** Максимальная совместимость. Пакеты, требующие компиляции C-расширений, устанавливаются без проблем.
  - **Минусы:** Очень большой размер, большая поверхность атаки.
  - **Итог:** Использовать только для сложных случаев, когда сборка на `slim` не удается.

- **`python:<version>-slim` (Slim Debian)**
  - **Содержимое:** "Облегченный" Debian с Python, но **без инструментов для сборки**.
  - **Плюсы:** Значительно меньший размер и поверхность атаки, при этом сохраняется совместимость с большинством `wheels` благодаря `glibc`.
  - **Минусы:** Если пакету нужна компиляция, придется временно устанавливать `build-essential`.
  - **Итог: Рекомендуемый выбор для большинства production-приложений.** Отличный баланс размера и совместимости.

- **`python:<version>-alpine` (Alpine Linux)**
  - **Содержимое:** Минималистичный дистрибутив на базе `musl libc` и `BusyBox`.
  - **Плюсы:** Экстремально маленький размер образа.
  - **Минусы:** Проблемы совместимости. Многие `wheels` не работают из-за `musl`, что вынуждает `pip` компилировать пакеты из исходников, приводя к ошибкам и усложнению `Dockerfile`.
  - **Итог:** Использовать, когда размер образа является абсолютно критичным, и вы готовы решать проблемы совместимости.

### Концепция 2: Воспроизводимость и кеширование сборок

1. **Фиксация зависимостей:** Всегда используйте файл `requirements.txt`, сгенерированный командой `pip freeze`, чтобы зафиксировать точные версий всех пакетов.
2. **Оптимизация кеширования слоев:** В `Dockerfile` сначала копируйте только `requirements.txt`, затем устанавливайте зависимости, и только после этого копируйте остальной код. Это позволяет Docker кешировать дорогостоящий слой с установкой пакетов. Подробнее о кешировании см. **[Оптимизация сборки Docker-образов](./build_optimization.md)**.

### Концепция 3: Один процесс на контейнер

Контейнер должен выполнять один основной процесс (например, веб-сервер). Задачи вроде миграции базы данных должны выполняться отдельно, а не вперемешку с запуском приложения в одной `CMD` инструкции.

## Практические сценарии

### Сценарий 1: Оптимизированный Dockerfile для Django/Flask

Этот пример объединяет несколько лучших практик для типичного веб-приложения.

```dockerfile
# Используем slim-образ как рекомендованную основу
FROM python:3.13-slim

# Устанавливаем переменные окружения
# PYTHONDONTWRITEBYTECODE: не создает .pyc файлы
# PYTHONUNBUFFERED: немедленно выводит логи
ENV PYTHONDONTWRITEBYTECODE 1
ENV PYTHONUNBUFFERED 1

WORKDIR /app

# Создаем непривилегированного пользователя для повышения безопасности
RUN adduser --system --group appuser

# Оптимизируем кеширование: сначала копируем только зависимости
COPY requirements.txt .
# --no-cache-dir отключает кеш pip, уменьшая размер слоя
RUN pip install --no-cache-dir -r requirements.txt

# Копируем остальной код
COPY . .

# Собираем статику на этапе сборки, а не при запуске
# --no-input предотвращает интерактивные запросы
RUN python manage.py collectstatic --no-input

# Переключаемся на непривилегированного пользователя
USER appuser

# Запускаем приложение через Gunicorn
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "myapp.wsgi:application"]
```

Подробнее о создании непривилегированных пользователей и минимизации поверхности атаки см. **[Безопасность в Dockerfile](./security.md)**.

### Сценарий 2: Многоэтапная сборка с `venv`

Этот паттерн полезен, когда для установки пакетов нужна компиляция, но финальный образ должен оставаться чистым. Подробнее о технике многоэтапных сборок см. **[Многоэтапные сборки](./build_optimization.md)**.

```dockerfile
# --- Этап 1: Сборщик (builder) ---
# Используем полный образ для установки build-essential и компиляции
FROM python:3.12 AS builder
WORKDIR /app
# Создаем виртуальное окружение
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
# Устанавливаем зависимости в venv
COPY requirements.txt .
RUN pip install -r requirements.txt

# --- Этап 2: Финальный образ ---
FROM python:3.12-slim
WORKDIR /app
# Копируем только venv с уже установленными пакетами из builder-а
COPY --from=builder /opt/venv /opt/venv
# Активируем venv
ENV PATH="/opt/venv/bin:$PATH"
ENV PYTHONUNBUFFERED 1
# Копируем код и запускаем
COPY . .
CMD ["python", "./server.py"]
```

### Сценарий 3: Разделение задач (миграция и запуск)

**`entrypoint.sh`:**

```sh
#!/bin/sh
# Выход при ошибке
set -e

# Если переменная MODE равна "migrate", выполняем миграции
if [ "$MODE" = "migrate" ]; then
    echo "Running database migrations..."
    python manage.py migrate
# Если "start", запускаем приложение
elif [ "$MODE" = "start" ]; then
    echo "Starting the application..."
    gunicorn myapp.wsgi:application --bind 0.0.0.0:8000
# Иначе, выполняем команду, переданную в docker run
else
    exec "$@"
fi
```

**`Dockerfile`:**

```dockerfile
# ...
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
# Команда по умолчанию, если MODE не задана
CMD ["start"]
```

Теперь вы можете запускать разные задачи:

- `docker run my-app` (запустит веб-сервер)
- `docker run -e MODE=migrate my-app` (выполнит миграции)

Этот подход требует правильной настройки контекста сборки — см. **[Контекст сборки (Build Context) и .dockerignore](../dockerfile_build_context.md)**.
