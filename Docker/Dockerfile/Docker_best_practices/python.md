# Dockerfile: Лучшие практики для Python

1.  **Выбор базового образа: `full` vs `slim` vs `alpine`**

    *   **`python:<version>` (Full Debian-based)**
        *   **Основа:** Полноценный дистрибутив Debian (например, `bookworm`).
        *   **Содержимое:** Включает Python, полный набор системных утилит и **инструменты для сборки** (`gcc`, `make`, `g++`, различные заголовки и библиотеки).
        *   **Преимущество:** Максимальная совместимость. Пакеты Python, требующие компиляции из исходного кода (например, многие пакеты с C-расширениями, такие как `psycopg2`, `numpy`, `lxml`), устанавливаются без проблем, так как все необходимые инструменты уже присутствуют.
        *   **Недостатки:**
            *   **Большой размер:** Имеет наибольший размер среди всех вариантов, что увеличивает время скачивания, потребление дискового пространства и потенциально замедляет развертывание.
            *   **Увеличенная поверхность атаки:** Большее количество предустановленного ПО означает больше потенциальных уязвимостей.

    *   **`python:<version>-slim` (Slim Debian-based)**
        *   **Основа:** "Облегченный" дистрибутив Debian.
        *   **Содержимое:** Удалены инструменты для сборки и многие системные утилиты, оставлено только необходимое для **запуска** Python-приложений. Python, стандартные библиотеки и минимум системных зависимостей.
        *   **Преимущество:** Значительно меньший размер и поверхность атаки по сравнению с "full" образом, при этом сохраняется высокая совместимость `glibc` (GNU C Library), что позволяет использовать большинство предварительно скомпилированных Python-пакетов (wheels).
        *   **Особенность:** Если Python-пакету все же нужна компиляция (например, для C-расширений), вам придется временно установить сборочные зависимости (`apt-get install build-essential ...`) и удалить их в том же слое `RUN`, чтобы не увеличивать размер конечного образа. Этот сценарий часто решается с помощью многоэтапной сборки.

    *   **`python:<version>-alpine` (Alpine Linux-based)**
        *   **Основа:** Alpine Linux, минималистичный дистрибутив, построенный на `musl libc` и `BusyBox`.
        *   **Преимущество:** Экстремально маленький размер образа, что обеспечивает максимальную экономию ресурсов и быструю доставку.
        *   **Недостатки:**
            *   **Проблемы совместимости:** Многие pre-compiled Python-пакеты ("wheels") собраны под `glibc` и **не будут работать** на Alpine (так как Alpine использует `musl libc`). Это заставит `pip` пытаться скомпилировать их из исходников, что часто приводит к ошибкам, требует установки специфичных Alpine-зависимостей и увеличивает сложность Dockerfile.
            *   **Требует более глубокой экспертизы:** Решение проблем с зависимостями и компиляцией на Alpine может быть более трудоемким и требует хорошего понимания работы `apk` (пакетного менеджера Alpine) и особенностей `musl libc`.
            *   **Менее привычные инструменты:** Использует `ash` вместо `bash` и урезанные версии утилит.

    *   **Рекомендации по выбору:**
        *   **`python:<version>` (Full):** Используйте, если у вас есть сложные Python-пакеты с C-расширениями, которые трудно скомпилировать на "slim" или "alpine" образах, и размер образа не является критичным фактором. Чаще всего применяется для разработки или в специфических случаях.
        *   **`python:<version>-slim`:** **Рекомендуемый выбор для большинства production-приложений.** Предлагает хороший баланс между размером образа, производительностью и совместимостью. Большинство популярных пакетов работают без проблем. В случае необходимости компиляции, используйте многоэтапную сборку.
        *   **`python:<version>-alpine`:** Используйте, когда размер образа является абсолютно критичным требованием, и вы готовы потратить дополнительное время на решение возможных проблем совместимости и адаптацию сборочных процессов. Отлично подходит для микросервисов, где каждый мегабайт имеет значение. Обязательно используйте многоэтапные сборки и виртуальные пакеты.

2.  **Фиксируйте версии:**
    *   **Базовый образ:** Всегда указывайте конкретный тег версии в инструкции `FROM` (например, `python:3.13-slim`).
    *   **Зависимости:** Используйте `pip freeze > requirements.txt` для создания точного списка зависимостей с версиями. Это обеспечивает воспроизводимость окружения.
3.  **Оптимизируйте кэширование слоев:**
    *   Сначала копируйте только `requirements.txt` и устанавливайте зависимости. Только после этого копируйте остальной код приложения. Это позволяет Docker кэшировать слой с установленными зависимостями.
    ```dockerfile
    WORKDIR /app
    COPY requirements.txt .
    RUN pip install --no-cache-dir -r requirements.txt
    COPY . .
    CMD ["python", "main.py"]
    ```
4.  **Используйте `ENV PYTHONUNBUFFERED=1`:**
    Эта переменная окружения отключает буферизацию потоков `stdout` и `stderr` в Python, что критически важно для отладки и просмотра логов в реальном времени.
5.  **Разделяйте задачи миграции и запуска приложения:**
    *   Не стоит запускать миграции базы данных и веб-сервер одной командой в `CMD` или `ENTRYPOINT`. Контейнер должен выполнять только один основной процесс.
    *   **Вариант 1 (Переменная окружения):** Используйте переменную окружения для выбора действия в `entrypoint.sh`.
      ```dockerfile
      COPY entrypoint.sh /entrypoint.sh
      RUN chmod +x /entrypoint.sh
      ENTRYPOINT ["/entrypoint.sh"]
      ```
      **entrypoint.sh:**
      ```sh
      #!/bin/sh
      set -e
      if [ "$MODE" = "migrate" ]; then
          echo "Running database migrations..."
          python manage.py migrate
      elif [ "$MODE" = "start" ]; then
          echo "Starting the application..."
          gunicorn myapp.wsgi:application --bind 0.0.0.0:8000
      else
          exec "$@"
      fi
      ```
    *   **Вариант 2 (Docker Compose):** Для более сложных сценариев, где задачи (миграция, запуск сервера, воркеры) должны выполняться как отдельные, но связанные процессы, рекомендуется использовать Docker Compose. Подробнее об этом можно прочитать в [документе о Docker Compose](../../Docker_compose/docker_compose.md).
6.  **Multi-stage сборки для Python:**
    *   **Установка зависимостей в `--user`**: Позволяет установить зависимости в домашний каталог пользователя, а затем скопировать их в финальный образ.
      ```dockerfile
      # Этап 1: Сборщик (builder)
      FROM python:3.13 AS builder
      WORKDIR /app
      COPY requirements.txt .
      RUN pip install --user -r requirements.txt
      # Этап 2: Финальный образ
      FROM python:3.12-slim-bookworm
      WORKDIR /app
      COPY --from=builder /root/.local /root/.local
      ENV PATH=/root/.local/bin:$PATH
      ENV PYTHONUNBUFFERED=1
      COPY myapp.py .
      CMD ["python", "myapp.py"]
      ```
    *   **Использование виртуального окружения (`venv`)**: Более изолированный подход, который отделяет зависимости проекта.
      ```dockerfile
      # Этап 1: Сборщик (builder)
      FROM python:3.12 AS builder
      WORKDIR /app
      RUN python3 -m venv /opt/venv
      ENV PATH="/opt/venv/bin:$PATH"
      COPY requirements.txt .
      RUN pip install -r requirements.txt
      # Этап 2: Финальный образ
      FROM python:3.12-slim
      WORKDIR /code
      COPY --from=builder /opt/venv /opt/venv
      ENV PATH="/opt/venv/bin:$PATH"
      ENV PYTHONUNBUFFERED=1
      COPY ./src .
      CMD ["python", "./server.py"]
      ```
7.  **Собирайте статику на этапе сборки (build-time):**
    *   Неправильно запускать `python manage.py collectstatic` в `ENTRYPOINT` или `CMD`. Это замедляет запуск контейнера.
    *   Правильно: Включить сборку статики в `Dockerfile` как одну из `RUN` инструкций.
    ```dockerfile
    # ... (установка зависимостей) ...
    COPY . .
    RUN python manage.py collectstatic --no-input --clear
    CMD ["gunicorn", "myapp.wsgi:application"]
    ```
