# Безопасность в Dockerfile

## Определения

- **Поверхность атаки (Attack Surface):** Совокупность всех компонентов системы (пакеты, библиотеки, открытые порты), которые могут быть использованы злоумышленником для проведения атаки.
- **Образ `scratch`:** Специальный пустой базовый образ Docker. Не содержит файловой системы, библиотек и командной оболочки (`shell`).
- **Образы `distroless`:** Минималистичные образы от Google, содержащие только приложение и его зависимости времени выполнения (runtime), например, `glibc` или `openssl`. В них отсутствуют менеджеры пакетов и `shell`.
- **Непривилегированный пользователь:** Пользователь системы с ограниченными правами доступа, не имеющий полномочий суперпользователя (`root`).
- **CVE (Common Vulnerabilities and Exposures):** Публично известный перечень уязвимостей и дефектов безопасности в программном обеспечении.

## Основные концепции

### Минимизация поверхности атаки

Каждая установленная утилита или библиотека является потенциальным вектором атаки. Использование минимальных базовых образов и удаление временных файлов в процессе сборки уменьшает количество уязвимостей и усложняет жизнь атакующему при успешном взломе.

### Принцип наименьших привилегий

По умолчанию процессы в Docker работают от имени `root`. Если злоумышленник получит контроль над процессом и найдет способ «побега» из контейнера (container escape), он получит полные права на хост-системе. Переключение на непривилегированного пользователя в `Dockerfile` — критическая мера безопасности.

### Неизменность и воспроизводимость

Сборка должна быть детерминированной. Использование команд обновления системы (например, `apt-get upgrade`) в `Dockerfile` делает образ зависимым от состояния внешних репозиториев на момент сборки. Образ должен быть фиксированным слепком проверенного состояния кода и зависимостей.

### Многоэтапная сборка как инструмент безопасности

[Многоэтапная сборка](./build_optimization.md) позволяет разделить процесс подготовки артефактов (где нужны компиляторы, секреты сборки, SSH-ключи) и процесс создания финального образа. В итоговый слой попадает только скомпилированное приложение, что исключает утечку секретов и сборочного инструментария.

## Практические сценарии

### Сценарий 1: Выбор минималистичного базового образа

| Характеристика | `FROM scratch` | `FROM gcr.io/distroless/...` |
| :--- | :--- | :--- |
| **Содержимое** | **Абсолютно пустой.** Нет даже `sh`. | **Минимальный набор.** Только runtime-зависимости. |
| **Размер** | Минимально возможный (размер бинарника). | Десятки мегабайт (меньше `alpine`). |
| **Совместимость** | Только для статических бинарных файлов (Go, Rust). | Поддерживает динамическую линковку (Java, Python, Node.js). |
| **Безопасность** | Поверхность атаки практически равна нулю. | Высокая. Отсутствие shell затрудняет развитие атаки. |

**Рекомендация:**
- Используйте `scratch` для статических приложений (Go с `CGO_ENABLED=0`).
- Используйте `distroless` для приложений, требующих системных библиотек или DNS.

### Сценарий 2: Создание непривилегированного пользователя

Пример создания пользователя с фиксированным UID (User Identifier) для предотвращения работы от имени `root`.

**Для Debian/Ubuntu (`slim` версии):**
```dockerfile
# Создаем системного пользователя без домашней директории и shell
RUN groupadd --system appgroup && \
    useradd --system --gid appgroup --no-create-home --shell /bin/false appuser

WORKDIR /app
COPY --chown=appuser:appgroup . .

# Переключаемся на пользователя. Все последующие CMD/ENTRYPOINT будут выполнены от него.
USER appuser
```

**Для Alpine:**
```dockerfile
# Создаем пользователя без пароля и домашней директории
RUN adduser -D -H -s /bin/false appuser

USER appuser
```

### Сценарий 3: Защита секретов и удаление инструментов

Использование многоэтапной сборки для предотвращения попадания секретов и инструментов сборки в финальный образ.

```dockerfile
# --- Этап 1: Сборка (builder) ---
FROM golang:1.24-alpine AS builder
WORKDIR /app
# Секреты (например, .netrc для приватных репозиториев) копируются только сюда
COPY . .
RUN go build -o /app/myapp main.go

# --- Этап 2: Финальный образ ---
FROM scratch
# Копируем только бинарный файл. Компилятор и исходный код остаются в этапе builder.
COPY --from=builder /app/myapp /myapp
ENTRYPOINT ["/myapp"]
```

### Сценарий 4: Аудит конфигураций (Пример PostgreSQL)

Многие официальные образы имеют «доверительные» настройки для быстрого старта. Например, `postgres` может разрешать локальные подключения без пароля (`trust`).

**Решение:** Всегда переопределяйте опасные настройки по умолчанию через переменные окружения или подмену конфигурационных файлов (например, `pg_hba.conf`). См. также [Безопасная установка СУБД](../../Databases/installation_security.md).
