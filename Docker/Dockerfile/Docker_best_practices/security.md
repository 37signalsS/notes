# Безопасность в Dockerfile

## Определения

- **Поверхность атаки (Attack Surface):** Совокупность всех установленных пакетов, открытых портов и доступных утилит, которые могут быть использованы для эксплуатации системы.
- **Цепочка поставок (Software Supply Chain Security):** Процесс обеспечения безопасности кода на всех этапах: от написания до доставки в production, включая проверку образов.
- **Дайджест (Digest):** Уникальный неизменяемый идентификатор образа по хешу (SHA256). В отличие от тега, дайджест гарантирует, что содержимое образа не изменилось.
- **Аттестация (Attestation):** Метаданные (SBOM, Provenance), прикрепленные к образу и подтверждающие его состав и происхождение.
- **Chiseled-образы:** Ультра-минималистичные образы (от Canonical/Chainguard), не содержащие даже менеджера пакетов и shell, предназначенные только для рантайма конкретных языков (Java, .NET, Python).

## Базовые концепции

### Минимизация через изоляцию стадий

Многоэтапная сборка ([Multi-stage](./build_optimization.md)) — фундаментальный инструмент безопасности. Она гарантирует, что сборочные инструменты (`gcc`, `maven`, `npm`), заголовки библиотек (`-dev`) и секреты сборки (SSH-ключи) не попадут в финальный слой образа.

### Принцип наименьших привилегий

По умолчанию контейнер запускается от `root`. В случае «побега» из контейнера (container escape) злоумышленник получает права суперпользователя на хосте. Переключение на непривилегированного пользователя в `Dockerfile` сводит этот риск к минимуму.

### Неизменность через дайджесты

Использование тегов типа `:latest` или `:20` небезопасно, так как содержимое образа под этим тегом может измениться в реестре без ведома администратора. Фиксация по дайджесту обеспечивает воспроизводимость и защиту от подмены базы.

## Практические сценарии

### Сценарий 1: Выбор и фиксация базового образа

Используйте минимальные образы и фиксируйте их по SHA256.

```dockerfile
# syntax=docker/dockerfile:1

# Плохо: образ может измениться, содержит лишние утилиты
# FROM node:22

# Хорошо: фиксация версии и архитектуры по хешу
FROM node:22.14.0-slim@sha256:074697... AS build

# Идеально (для рантайма): Chiseled или Distroless
FROM gcr.io/distroless/nodejs22-debian12@sha256:6e7...
```

### Сценарий 2: Безопасная работа с секретами (BuildKit Secrets)

Никогда не используйте `ARG` или `ENV` для паролей и ключей — они сохраняются в истории образа. Используйте временное монтирование секретов.

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.14-slim AS builder

WORKDIR /app
COPY requirements.txt .

# Секрет монтируется только на время выполнения команды и не сохраняется в слоях
RUN --mount=type=secret,id=pip_conf,target=/etc/pip.conf \
    pip install --no-cache-dir -r requirements.txt
```
**Запуск сборки:** `docker build --secret id=pip_conf,src=./secrets/pip.conf .`

### Сценарий 3: Управление пользователями и правами

Создание пользователя с фиксированным UID/GID для предсказуемости в системах оркестрации (Kubernetes).

```dockerfile
FROM alpine:3.21

# Создаем системную группу и пользователя
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app

# Копируем файлы с явным указанием владельца
COPY --chown=appuser:appgroup ./dist .

# Удаляем SUID/SGID биты для предотвращения эскалации привилегий
RUN find / -xdev -perm /6000 -type f -exec chmod a-s {} + || true

USER appuser
ENTRYPOINT ["./my-app"]
```

### Сценарий 4: Безопасные инструкции и метаданные

- **COPY vs ADD:** Всегда предпочитайте `COPY`. Инструкция `ADD` может автоматически распаковывать архивы и скачивать файлы по URL, что является вектором атаки.
- **Shell формы:** Используйте JSON-форму для `ENTRYPOINT` и `CMD`, чтобы сигналы (SIGTERM) доходили до процесса напрямую, а не через `/bin/sh`.
- **HEALTHCHECK:** Избегайте использования `curl` в healthcheck, если он не нужен приложению. Используйте встроенные средства или минимальные бинарники.

```dockerfile
# Использование HEALTHCHECK с минимальными привилегиями
HEALTHCHECK --interval=30s --timeout=3s \
  CMD ["/usr/bin/my-app-checker"] || exit 1
```

### Сценарий 5: Генерация SBOM и аттестаций (Buildx)

В 2026 году образ считается «доверенным», только если он снабжен аттестациями.

```bash
# Сборка с генерацией SBOM и данных о происхождении (Provenance)
docker buildx build \
  --sbom=true \
  --provenance=mode=max \
  --tag my-repo/my-app:1.0 \
  --push .
```
Эти данные проверяются сканерами (Trivy, Grype) для подтверждения отсутствия уязвимостей в цепочке поставки. См. подробнее: **[SBOM для Docker-образов](../../Docker_security/docker_sbom.md)**.
