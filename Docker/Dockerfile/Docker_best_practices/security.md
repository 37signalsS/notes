# Безопасность в Dockerfile

Комплексное руководство по всем аспектам безопасности Docker, включая защиту демона, управление секретами и безопасность во время выполнения, находится в документе **[Безопасность Docker](../../Docker_security/overview.md)**.

## Использование минималистичных базовых образов

Чем меньше компонентов в вашем образе, тем меньше поверхность атаки. Следует избегать использования полноценных дистрибутивов (таких как `ubuntu` или `centos`), если они не являются строго необходимыми.

**Distroless-образы от Google** — это базовые образы, которые содержат только ваше приложение и его runtime-зависимости (например, `glibc`, `openssl`). В них отсутствуют оболочки (`bash`), менеджеры пакетов (`apt`) и стандартные утилиты (`ls`, `curl`), что значительно усложняет жизнь злоумышленнику, попавшему в контейнер. Главный компромисс `distroless`-образов — сложность отладки; подробное руководство по решению этой проблемы находится в документе **[Отладка контейнеров без shell (distroless)](../../Docker_troubleshooting/debugging_distroless.md)**.

**Сравнение минималистичных образов: `scratch` vs. `distroless`**

| Характеристика | `FROM scratch` | `FROM gcr.io/distroless/...` |
| :--- | :--- | :--- |
| **Содержимое** | **Абсолютно пустой.** Нет ничего: ни файлов, ни библиотек, ни shell. | **Минимальный набор.** Содержит только приложение и его runtime-зависимости (например, `glibc`, `openssl`, CA-сертификаты). |
| **Размер** | Минимально возможный (размер вашего бинарника). | Чуть больше, чем `scratch`, но значительно меньше, чем `alpine` или `debian`. |
| **Совместимость** | Только для **полностью статических** бинарных файлов (например, Go с `CGO_ENABLED=0`). | Поддерживает динамически-связанные приложения (C++, Java, Python) благодаря наличию `libc`. |
| **Безопасность** | Максимальная. Поверхность атаки равна нулю (кроме вашего приложения). | Очень высокая. Отсутствуют shell и пакетные менеджеры, что сильно затрудняет атаку. |
| **Сложность** | Высокая. Требует аккуратной сборки бинарника и ручного добавления необходимых файлов (например, CA-сертификатов). | Низкая. Работает "из коробки" для большинства приложений. |

**Когда что использовать:**
-   **`scratch`**: Идеальный выбор для приложений на **Go**, которые скомпилированы как статические бинарники.
-   **`distroless`**: Прагматичный выбор для большинства других языков (**Python, Java, Node.js, C++**) и для Go-приложений, которым нужны базовые функции ОС (например, работа с DNS, TLS-сертификаты).

## Создание непривилегированного пользователя

Запуск процессов внутри контейнера от имени пользователя root (по умолчанию) является серьезным риском безопасности. Всегда следует создавать и использовать непривилегированного пользователя.

`groupadd -r user` — Создание изолированной группы

*   **Что делает флаг `-r` (`--system`)?**
    Этот флаг указывает, что мы создаем **системную** группу. В Linux принято разделять сущности на "пользовательские" и "системные".

`useradd -r -s /bin/false -g user user` — Создание "бесправного" пользователя

*   **Что делает флаг `-r` (`--system`)?**
    Аналогично `groupadd`, этот флаг создает **системного пользователя** с UID из системного диапазона (1-999). Обычно для таких пользователей не создается домашняя директория и не устанавливается срок действия пароля.

*   **Что делает флаг `-s /bin/false`?**
    *   **`-s` (`--shell`)** задает пользователю **командную оболочку** (shell).
    *   **`/bin/false`** — блокирует любую возможность интерактивного входа. Если кто-то попытается войти в систему под этим пользователем, сессия тут же завершится. От имени пользователя можно запускать процессы, но залогиниться им нельзя.

*   **Что делает флаг `-g user`?**
    *   **`-g` (`--gid`)** устанавливает **основную группу** пользователя. Когда этот пользователь будет создавать файлы, они по умолчанию будут принадлежать группе `user`.
    *   Мы привязываем пользователя к специально созданной для него группе, что позволяет гибко настраивать права доступа.

**Альтернатива для Alpine: `adduser`**

В образах на базе Alpine Linux часто используется утилита `adduser`, которая является более высокоуровневой. Команда `adduser -D -H -s /bin/false nonroot` делает то же самое:

*   **`-D` (`--no-password`):** Создает пользователя без пароля.
*   **`-H` (`--no-create-home`):** Не создает домашнюю директорию.
*   **`-s /bin/false`:** Устанавливает оболочку в `/bin/false`.
*   **`nonroot`:** Имя пользователя.

**Заключительный шаг: `USER`**

После создания пользователя, в `Dockerfile` обязательно следует команда `USER nonroot` (или `USER user`), которая переключает контекст. Все последующие инструкции (`COPY`, `CMD`, `ENTRYPOINT`) будут выполняться уже от имени нашего нового, безопасного, непривилегированного пользователя.

## Обновление пакетов (`apt-get upgrade`) — плохая практика

Выполнение `apt-get upgrade` (или аналогичных команд для других пакетных менеджеров) в Dockerfile является плохой практикой по нескольким причинам:

1.  **Нарушение воспроизводимости (Broken Reproducibility):** Выполнение `apt-get upgrade` во время сборки делает образ зависимым от состояния репозиториев в данный конкретный момент. Повторная сборка того же Dockerfile через некоторое время может привести к установке других версий пакетов, что ведет к непредсказуемому поведению.
2.  **Проблемы с кешированием (Cache Busting):** Команда `apt-get upgrade` инвалидирует кеш для этого слоя и всех последующих слоев, что приводит к полной пересборке всех последующих шагов при малейшем изменении в Dockerfile.

*   **Решение:** Используйте актуальный базовый образ. Вместо того чтобы обновлять старый образ, используйте более новую версию базового образа, в котором уже есть некоторые обновления (например, `debian:12.5` вместо `debian:12`). Если требуется установка специфичных версий пакетов, указывайте их явно.

## Аудит конфигураций по умолчанию

Никогда слепо не доверяйте настройкам по умолчанию, даже в официальных образах. Они часто оптимизированы для простоты запуска, а не для безопасности.

> #### Пример: Небезопасные настройки в официальном образе PostgreSQL
> 
> Официальный образ `postgres` по умолчанию использует метод аутентификации `trust` для всех локальных подключений. Это означает, что любой пользователь или процесс, имеющий доступ к контейнеру (даже из другого контейнера в той же Docker-сети), может подключиться к базе данных с правами суперпользователя **без пароля**.
> 
> **Выдержка из `pg_hba.conf` по умолчанию в контейнере:**
> ```conf
> # "local" is for Unix domain socket connections only
> local   all             all                                     trust
> # IPv4 local connections:
> host    all             all             127.0.0.1/32            trust
> # IPv6 local connections:
> host    all             all             ::1/128                 trust
> ```
> 
> Это серьезная уязвимость в production-среде.
> 
> **Решение:** Всегда переопределяйте конфигурацию, предоставляя свой, более строгий файл `pg_hba.conf` и монтируя его в контейнер. Подробнее о настройке можно прочитать в руководстве [**Развертывание PostgreSQL в Docker**](../../../Databases/PostgreSQL/Operations/docker_deployment.md).
