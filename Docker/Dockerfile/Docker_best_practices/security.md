# Безопасность в Dockerfile

## Определения

- **Поверхность атаки (Attack Surface):** Совокупность всех компонентов системы, которые могут быть атакованы злоумышленником. В контексте Docker-образа это включает в себя все установленные пакеты, утилиты, библиотеки и открытые порты.
- **Образ `scratch`:** Специальный, абсолютно пустой базовый образ в Docker. Он не содержит файловой системы, библиотек или утилит.
- **Образы `distroless`:** Минималистичные базовые образы от Google, которые содержат только приложение и его runtime-зависимости (например, `glibc`, `openssl`). В них отсутствуют shell и менеджеры пакетов.
- **Непривилегированный пользователь:** Пользователь системы с ограниченными правами, который не может выполнять административные задачи (например, устанавливать ПО или изменять системные файлы).

## Основные концепции

### Принцип 1: Минимизация поверхности атаки

Чем меньше компонентов в образе, тем меньше потенциальных уязвимостей и тем сложнее злоумышленнику, попавшему в контейнер, развить атаку. Следует всегда выбирать наиболее минималистичный базовый образ, который подходит для вашего приложения.

### Принцип 2: Принцип наименьших привилегий

Процессы в контейнере должны выполняться с минимально необходимыми им правами. Запуск от имени `root` (пользователя по умолчанию) создает серьезный риск: если злоумышленник сможет "сбежать" из контейнера, он может получить права `root` на хост-системе.

### Принцип 3: Воспроизводимость и неизменность сборок

Сборка Docker-образа должна быть детерминированной: один и тот же `Dockerfile` должен всегда производить идентичный образ. Использование команд вроде `apt-get upgrade` нарушает этот принцип, так как результат сборки начинает зависеть от состояния внешних репозиториев в момент времени.

### Принцип 4: Недоверие к настройкам по умолчанию

Никогда не следует слепо доверять конфигурациям по умолчанию, даже в официальных образах. Они часто оптимизированы для удобства и быстрого старта, а не для безопасности.

## Практические сценарии

### Сценарий 1: Выбор минималистичного базового образа

| Характеристика | `FROM scratch` | `FROM gcr.io/distroless/...` |
| :--- | :--- | :--- |
| **Содержимое** | **Абсолютно пустой.** Нет ничего: ни файлов, ни библиотек, ни shell. | **Минимальный набор.** Содержит runtime-зависимости (например, `glibc`, `openssl`, CA-сертификаты). |
| **Размер** | Минимально возможный (размер вашего бинарника). | Чуть больше, чем `scratch`, но значительно меньше, чем `alpine` или `debian`. |
| **Совместимость** | Только для **полностью статических** бинарных файлов (например, Go с `CGO_ENABLED=0`). | Поддерживает динамически-связанные приложения (Java, Python, Node.js) благодаря наличию `libc`. |
| **Безопасность** | Максимальная. Поверхность атаки равна нулю (кроме вашего приложения). | Очень высокая. Отсутствуют shell и пакетные менеджеры. |

**Когда что использовать:**

- **`scratch`**: Идеальный выбор для приложений на **Go**, скомпилированных как статические бинарники.
- **`distroless`**: Прагматичный выбор для большинства других языков (**Python, Java, Node.js, C++**) и для Go-приложений, которым нужны базовые функции ОС (например, работа с DNS, TLS-сертификаты).

> **Примечание:** Отсутствие shell в `distroless`-образах усложняет отладку. Руководство по решению этой проблемы находится в документе **[Отладка контейнеров без shell (distroless)](../../Docker_troubleshooting/debugging_distroless.md)**.

### Сценарий 2: Создание и использование непривилегированного пользователя

**Для образов на базе Debian/Ubuntu:**

```dockerfile
# Создаем системную группу и системного пользователя без домашней директории и shell
RUN groupadd --system nonroot && \
    useradd --system --gid nonroot --no-create-home --shell /bin/false nonroot

# ... другие инструкции ...

# Переключаемся на созданного пользователя.
# Все последующие команды (COPY, CMD, ENTRYPOINT) будут выполняться от его имени.
USER nonroot
```

**Для образов на базе Alpine:**

```dockerfile
# Создаем пользователя без пароля и домашней директории
RUN adduser -D -H -s /bin/false nonroot

# ... другие инструкции ...

USER nonroot
```

### Сценарий 3: Аудит конфигурации на примере PostgreSQL

Официальный образ `postgres` по умолчанию использует метод аутентификации `trust` для всех локальных подключений. Это означает, что любой процесс в той же Docker-сети может подключиться к базе данных с правами суперпользователя **без пароля**.

**Решение:** Никогда не используйте эту конфигурацию в production. Всегда предоставляйте свой собственный, более строгий файл `pg_hba.conf`, требующий аутентификацию по паролю (`scram-sha-256` или `md5`), и монтируйте его в контейнер.
