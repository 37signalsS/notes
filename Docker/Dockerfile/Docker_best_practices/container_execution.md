# Выполнение приложений в контейнере

## Определения

- **PID (Process Identifier) 1:** Первый процесс в пространстве имен (Namespace), обладающий особыми полномочиями и обязанностями в Linux (управление сигналами, очистка «зомби»).
- **Форма записи Exec (JSON form):** Синтаксис `CMD ["executable", "param1"]`, запускающий процесс напрямую без оболочки. Единственный способ сделать процесс PID 1.
- **Форма записи Shell:** Синтаксис `CMD executable param1`, запускающий процесс как дочерний для `/bin/sh -c`. Препятствует пробросу сигналов.
- **Процесс-зомби (Zombie Process):** Завершенный процесс, запись о котором висит в таблице процессов, так как родитель (PID 1) не обработал сигнал `SIGCHLD`.
- **Graceful Shutdown (Плавное завершение):** Паттерн, при котором приложение получает сигнал остановки, завершает текущие транзакции и только после этого закрывается.

## Базовые концепции

### Проблема PID 1 и систем инициализации

В стандартной ОС за очистку ресурсов и управление процессами отвечает `systemd` или `init`. В контейнере роль PID 1 берет на себя ваше приложение.
1.  **Управление сигналами:** Если процесс PID 1 не имеет встроенного обработчика сигналов (как большинство приложений на Python, Node.js), сигналы `SIGTERM` или `SIGINT` будут проигнорированы.
2.  **Очистка зомби:** Если приложение порождает дочерние процессы и они завершаются, PID 1 обязан выполнить системный вызов `wait()`, иначе таблица процессов переполнится «зомби».

### Exec Form vs Shell Form

Выбор формы записи в `Dockerfile` критически влияет на выполнение.

| Характеристика | Exec Form (`["app"]`) | Shell Form (`app`) |
| :--- | :--- | :--- |
| **PID процесса** | PID 1 | Случайный PID (ребенок `/bin/sh`) |
| **Проброс сигналов** | Напрямую приложению | Блокируется оболочкой |
| **Переменные окружения** | Не подставляются автоматически | Подставляются через `/bin/sh` |

**Рекомендация:** Всегда используйте **Exec Form**. Если приложение запущено через Shell Form, оно не получит сигнал `SIGTERM`.
- **Пример в Kubernetes:** Кублет посылает `SIGTERM`, оболочка его игнорирует, приложение продолжает работать. Через 30 секунд (default terminationGracePeriodSeconds) Кубернетес посылает `SIGKILL`. Это лишает приложение возможности выполнить **Graceful Shutdown** (закрыть соединения, сбросить буферы), что критично для баз данных.

Если нужны переменные окружения, вызывайте оболочку явно: `CMD ["/bin/sh", "-c", "echo $VAR && exec /app/bin"]`. Использование `exec` в конце заменит процесс оболочки вашим приложением, сохранив PID 1.

### Принцип одного процесса

Контейнер предназначен для изоляции одной функциональной единицы.
- **Масштабируемость:** Проще масштабировать 10 веб-серверов и 2 БД отдельно.
- **Логирование:** Docker собирает `stdout/stderr` основного процесса. Если процессов много, логи перемешиваются.
- **Жизненный цикл:** Если в контейнере 3 процесса и один упал, Docker может не узнать об этом, если PID 1 все еще жив.

## Практические сценарии

### Сценарий 1: Корректный Graceful Shutdown (Go)

Приложение должно перехватывать сигналы, чтобы не прерывать запросы пользователей при деплое.

```go
// Пример на Go
sigChan := make(chan os.Signal, 1)
signal.Notify(sigChan, syscall.SIGTERM, syscall.SIGINT)

<-sigChan // Блокировка до получения сигнала
log.Println("Завершение работы...")
server.Shutdown(ctx) // Закрытие соединений
```

В `Dockerfile` это требует:
```dockerfile
# Использование JSON-формы обязательно
ENTRYPOINT ["/app/server"]
```

### Сценарий 2: Использование Tini (решение проблем PID 1)

Если вы используете Node.js или Java, которые плохо справляются с ролью PID 1, добавьте `tini`.

```dockerfile
# Установка для Debian/Ubuntu
RUN apt-get update && apt-get install -y tini
# Tini становится PID 1, приложение — его прямым потомком
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["node", "app.js"]
```

### Сценарий 3: Запуск «демонизированных» сервисов

Если сервис (например, Nginx) по умолчанию уходит в фон, контейнер мгновенно остановится. Нужно явно запретить режим демона.

```dockerfile
# Nginx должен работать на переднем плане (foreground)
CMD ["nginx", "-g", "daemon off;"]
```

### Сценарий 4: Ограничения ресурсов и OOM

Процесс в контейнере ограничен лимитами Docker/Kubernetes.
- **CPU:** Если лимит 0.5 ядра, а приложение многопоточное, оно может начать тормозить из-за троттлинга.
- **Memory:** Если приложение превысит лимит, ядро пришлет **OOM Kill**.

Подробнее о кодах завершения (например, 137 при OOM) см. в разделе **[Коды завершения контейнеров](../../Docker_troubleshooting/docker_exit_codes.md)**.
