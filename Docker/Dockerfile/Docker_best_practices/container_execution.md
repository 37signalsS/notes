# Выполнение приложений в контейнере

## Определения

- **PID (Process Identifier) 1:** Первый процесс в пространстве имен (Namespace), обладающий особыми полномочиями и обязанностями в Linux. Он отвечает за управление сигналами и очистку «процессов-сирот» (reaping).
- **Форма записи Exec (JSON form):** Синтаксис `CMD ["executable", "param1"]`, запускающий процесс напрямую через системный вызов `execve` без участия командной оболочки. Это единственный надежный способ сделать процесс PID 1.
- **Форма записи Shell:** Синтаксис `CMD executable param1`, запускающий процесс как дочерний для `/bin/sh -c`. Оболочка становится PID 1 и часто блокирует проброс сигналов приложению.
- **Процесс-зомби (Zombie Process):** Завершенный процесс, который уже не выполняется, но запись о нем остается в таблице процессов, так как родитель (PID 1) не выполнил системный вызов `wait()` для сбора статуса завершения (`SIGCHLD`). **Зомби нельзя «убить» напрямую** через `SIGKILL`. Подробности см. в [Руководстве по отладке процессов](../../../Linux/Core/processes/Troubleshooting/debugging.md#устранение-зомби-и-сирот).
- **Graceful Shutdown (Плавное завершение):** Паттерн, при котором приложение при получении сигнала остановки прекращает прием новых запросов, завершает текущие транзакции, сохраняет состояние и только после этого закрывается.
- **STOPSIGNAL:** Инструкция Dockerfile, задающая конкретный системный сигнал (например, `SIGTERM`, `SIGQUIT`), который Docker будет отправлять процессу PID 1 при выполнении команды `docker stop`.
- **Init-система (Tini / dumb-init):** Легковесные менеджеры процессов, которые берут на себя роль PID 1, корректно пробрасывают сигналы дочерним процессам и очищают зомби.

## Базовые концепции

### Проблема PID 1 и систем инициализации

В стандартной ОС за очистку ресурсов и управление процессами отвечает полноценная система инициализации (`systemd`, `OpenRC`). В контейнере роль PID 1 ложится на ваше приложение, что порождает две проблемы:

1.  **Игнорирование сигналов:** Процесс PID 1 в Linux является особенным. Он не имеет обработчиков сигналов по умолчанию. Если приложение (например, на Python, Node.js) не зарегистрировало обработчик `SIGTERM` явно, ядро не применит стандартное поведение "завершиться", и сигнал будет проигнорирован.
2.  **Накопление зомби:** Если приложение порождает дочерние процессы (например, через `shell_exec` или `subprocess`), и они завершаются, PID 1 обязан "пожинать" их. Если этого не происходит, таблица процессов переполняется, что приводит к отказу в запуске новых процессов.

### Exec Form против Shell Form

Выбор формы записи в `Dockerfile` (для `CMD` и `ENTRYPOINT`) критически влияет на жизненный цикл приложения.

| Характеристика | Exec Form (`["app"]`) | Shell Form (`app`) |
| :--- | :--- | :--- |
| **Запуск** | Напрямую (`execve`) | Через `/bin/sh -c` |
| **PID процесса** | PID 1 | Случайный PID (потомок оболочки) |
| **Проброс сигналов** | Напрямую приложению | Блокируется оболочкой |
| **Зомби-процессы** | Требует init-систему | Частично обрабатываются оболочкой |
| **Переменные окружения** | Не подставляются автоматически | Подставляются через `/bin/sh` |

**Рекомендация:** Всегда используйте **Exec Form**. Если приложению нужны переменные окружения, используйте явный вызов:
`CMD ["/bin/sh", "-c", "echo $VAR && exec /app/bin"]`
Использование `exec` в конце команды `sh` заменит процесс оболочки вашим приложением, сохраняя за ним PID 1 и возможность получения сигналов.

### Механизм STOPSIGNAL

По умолчанию `docker stop` отправляет `SIGTERM`, ждет 10 секунд и, если контейнер не остановился, отправляет `SIGKILL`. Однако некоторым приложениям требуются другие сигналы:
- **Nginx:** Использует `SIGQUIT` для Graceful Shutdown.
- **PostgreSQL:** Предпочитает `SIGINT` (Fast Shutdown) вместо стандартного Smart Shutdown.

```dockerfile
# Установка правильного сигнала в Dockerfile
STOPSIGNAL SIGQUIT
```

### Флаг --init

Если образ не содержит `tini`, но вам нужно решить проблему PID 1, Docker предоставляет встроенную поддержку:
- **CLI:** `docker run --init ...`
- **Compose:** `init: true`
Это автоматически вставляет `tini` как PID 1 внутрь контейнера.

### Принцип одного процесса

Контейнер спроектирован для изоляции одной функциональной единицы.
- **Масштабируемость:** Микросервисы должны масштабироваться независимо.
- **Логирование:** Docker агрегирует `stdout/stderr` PID 1. Несколько процессов в одном контейнере перемешивают логи.
- **Мониторинг:** Если упадет второстепенный процесс, а основной (PID 1) останется жив, оркестратор не узнает о сбое.

**Исключения:** Использование sidecar-контейнеров в Kubernetes или легковесных менеджеров вроде `supervisord`, если процессы неразрывно связаны (например, `Nginx + PHP-FPM`).

## Практические сценарии

### Сценарий 1: Корректный Graceful Shutdown (Go)

Приложение должно перехватывать сигналы, чтобы не прерывать активные соединения.

```go
// Пример на Go
sigChan := make(chan os.Signal, 1)
signal.Notify(sigChan, syscall.SIGTERM, syscall.SIGINT)

<-sigChan // Ожидание сигнала
log.Println("Завершение работы...")
// ctx с таймаутом дает время на закрытие соединений
server.Shutdown(ctx) 
```

### Сценарий 2: Использование Tini (рекомендуемый подход)

Для приложений на Node.js, Java или Python, которые не умеют корректно работать как PID 1.

```dockerfile
FROM node:22-alpine
RUN apk add --no-cache tini
# Tini становится PID 1, приложение — его прямым потомком
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "app.js"]
```

### Сценарий 5: Graceful Shutdown воркеров (Consumer Pattern)

Для приложений, разбирающих очереди (RabbitMQ, Kafka, Redis), простого перехвата `SIGTERM` недостаточно. При резком переключении трафика (например, при миграции между серверами) важно не допустить потери или дублирования неидемпотентных задач.

1.  **Обработка сигнала:** При получении `SIGTERM` воркер переходит в режим «завершения».
2.  **Флаг готовности:** Устанавливается внутренний флаг (например, `is_accepting = false`).
3.  **Перераспределение:** Все новые сообщения, приходящие из очереди, воркер возвращает обратно (`nack` или `reject` с параметром `requeue=true`), чтобы их подхватили другие активные инстансы (например, на новом сервере).
4.  **Завершение текущих задач:** Воркер продолжает обрабатывать те задачи, которые уже взял в работу, до их полного выполнения.
5.  **Таймаут:** В `compose.yml` или манифесте Pod необходимо увеличить `stop_grace_period` до времени выполнения самой долгой задачи.

### Сценарий 6: Entrypoint-скрипт с сохранением сигналов

Типичный сценарий для подготовки окружения перед запуском.

**Dockerfile:**
```dockerfile
COPY entrypoint.sh /
ENTRYPOINT ["/entrypoint.sh"]
CMD ["my-app", "--arg1"]
```

**entrypoint.sh:**
```bash
#!/bin/sh
set -e
# Выполняем миграции или проверку БД
python manage.py migrate
# exec "$@" заменяет текущую оболочку (PID 1) приложением
exec "$@"
```

### Сценарий 4: Ограничения ресурсов и OOM

Процесс в контейнере жестко ограничен лимитами Docker/Kubernetes.
- **CPU Throttling:** Если лимит процессора превышен, ядро ограничивает кванты времени (throttling), что выглядит как резкое замедление приложения.
- **OOM Kill (Exit Code 137):** Если приложение превышает лимит памяти (RSS), ядро отправляет `SIGKILL`. Приложение **не может** перехватить этот сигнал и завершается мгновенно.

## Дополнительная информация

### Взаимодействие с Kubernetes

Kubernetes игнорирует `HEALTHCHECK` и `STOPSIGNAL` из Dockerfile. Все параметры управления жизненным циклом задаются в манифесте Pod:
- `terminationGracePeriodSeconds`: Время на завершение (аналог таймаута `docker stop`).
- `preStop hook`: Команда, выполняемая **до** отправки `SIGTERM`.
