# Kaniko: Сборка Docker-образов без демона

> [!WARNING]
> **Статус проекта (2025):** Официальный репозиторий Google (`GoogleContainerTools/kaniko`) был **архивирован 3 июня 2025 года** и переведен в режим "только для чтения". Новые функции и официальные патчи безопасности от Google более не выпускаются. Для новых систем рекомендуется миграция на **[BuildKit (Standalone)](./dockerfile_buildkit.md)** или **Buildah**.

## Определения

**Kaniko** — инструмент от Google для сборки образов контейнеров из `Dockerfile` без зависимости от Docker-демона. Он выполняет инструкции внутри пользовательского пространства (userspace), что делает его идеальным для CI/CD и Kubernetes-кластеров, где использование привилегированных контейнеров или монтирование Docker Socket запрещено политиками безопасности.

Официальный репозиторий (архив): **[github.com/GoogleContainerTools/kaniko](https://github.com/GoogleContainerTools/kaniko)**.

## Базовые концепции

### Принцип работы Kaniko (пошагово)

Главное отличие Kaniko от классического Docker заключается в том, что он **вообще не запускает контейнеры** для сборки. Вместо механизмов ядра (namespaces) он использует эмуляцию в пользовательском пространстве.

1.  **Распаковка базового образа:** При обработке инструкции `FROM`, Kaniko скачивает образ и просто **распаковывает** его файловую систему в обычную директорию (обычно `/kaniko/workspace/rootfs`).
2.  **Выполнение команд (RUN) через chroot:** Для выполнения команд Kaniko использует механизм **chroot**. Процессу (например, `apk` или `apt`) сообщается, что его корневая директория — это папка с распакованным образом. 
    - Процесс "считает", что он находится в реальной ОС.
    - На самом деле он просто меняет файлы в папке на диске.
    - При этом не создаются новые namespaces и не требуются привилегии ядра.
3.  **Снапшоты (Snapshots):** После каждой команды `RUN` Kaniko сравнивает текущее состояние файлов с предыдущим состоянием, вычисляет разницу и упаковывает измененные файлы в новый слой (`tar.gz`).
4.  **Multi-stage сборки и оптимизация:** 
    - **Статический анализ (Built cross stage deps):** Перед началом работы Kaniko строит карту зависимостей между стадиями. Это позволяет заранее знать, какие файлы из ранних стадий понадобятся позже.
    - **Сохранение артефактов:** При завершении стадии Kaniko физически копирует нужные файлы (логи: `Saving file <path> for later use`) во внутреннее временное хранилище.
    - **Полная очистка (Deleting filesystem):** Перед началом новой стадии Kaniko полностью удаляет содержимое рабочего пространства, оставляя только сохраненные артефакты. Это гарантирует изоляцию стадий и отсутствие лишнего мусора в финальном образе.
5.  **Формирование и отправка:** В конце процесса Kaniko собирает все слои и манифест, отправляя их в реестр через HTTP API.

### Модель эшелонированной защиты (Defense-in-depth)

Поскольку `chroot` сам по себе не является абсолютным барьером безопасности (особенно для root), Kaniko применяет многослойный подход:

1.  **Эшелон 1: Non-root запуск.** Побег из `chroot` технически невозможен для непривилегированного пользователя (UID 1000), так как техники escape требуют прав `CAP_SYS_ADMIN`.
2.  **Эшелон 2: Отсутствие привилегий ядра.** Контейнер Kaniko запускается без `--privileged` и без опасных capabilities. У него нет прав на монтирование устройств или изменение параметров ядра хоста.
3.  **Эшелон 3: Ограничения оркестратора.** Полная совместимость с **Pod Security Standards (Restricted)**. Kubernetes принудительно запрещает доступ к хосту.
4.  **Эшелон 4: Сетевая изоляция.** Kaniko использует сеть пода. В Kubernetes это контролируется через **NetworkPolicy**, которую процесс сборки не может обойти.

#### Разбор сценариев атак

-   **Вредоносный скрипт в `RUN`:** В Docker (DinD) скрипт может попытаться смонтировать `/dev/sda1` хоста. В Kaniko он ограничен правами пользователя внутри `chroot` и может испортить только файлы текущей сборки. Побег на хост невозможен.
-   **Сканирование сети:** Kaniko использует сеть Pod'а, что позволяет жестко ограничивать его сетевую активность стандартными средствами Kubernetes.

### Особенности кэширования

Логика кэширования в Kaniko фундаментально отличается от Docker:
-   **Удаленный кэш (Remote-only):** Kaniko по умолчанию хранит кэшированные слои в удаленном Registry (`--cache-repo`). Локального постоянного кэша на диске не существует (контейнер удаляется после сборки).
-   **Транзитная природа:** Контейнер полностью удаляется вместе со всеми данными. Кэш "внутри себя" Kaniko сохранить не может.
-   **Логика "все или ничего":** Для работы кэша (`--cache=true`) обязательно требуется внешний реестр, даже если финальный образ не пушится (`--no-push`).
-   **Оптимизация (v1.24+):** Поддержка флага `--no-push-cache=false` (по умолчанию) позволяет пушить кэш даже при использовании `--no-push` для основного образа.

### Контекст сборки

Параметр `--context` определяет источник исходного кода. Для локальной файловой системы Kaniko требует префикс протокола:
-   `dir://` — локальная директория (например, `--context=dir:///workspace`).
-   `git://` — Git-репозиторий. Начиная с v1.22+, поддерживаются расширенные опции: `--git=branch=main,recursive=true` и использование `GIT_TOKEN`.
-   `s3://`, `gs://` — облачные хранилища.

## Сравнение методов сборки

| Критерий | DinD (Docker-in-Docker) | BuildKit (Standalone) | Kaniko |
| :--- | :--- | :--- | :--- |
| **Демон Docker** | Нужен | Не нужен (`buildkitd`) | Не нужен |
| **Привилегии** | Нужны (`--privileged`) | Не нужны (rootless) | Не нужны |
| **Безопасность** | Низкая | Высокая | Высокая |
| **Кэширование** | Локальное | Локальное / Remote | Только Remote |
| **Совместимость** | 100% | Высокая | Средняя (~95%) |
| **BuildKit функции** | Поддерживаются | Полная поддержка | Игнорируются |

## Практические сценарии

### Сценарий 1: Сборка в GitLab CI (v1.24.0)

```yaml
build-app:
  stage: build
  image:
    # Debug-образ содержит shell для выполнения скриптов
    name: gcr.io/kaniko-project/executor:v1.24.0-debug
    entrypoint: [""]
  script:
    # Аутентификация в реестре
    - echo "{\"auths\":{\"$CI_REGISTRY\":{\"username\":\"$CI_REGISTRY_USER\",\"password\":\"$CI_REGISTRY_PASSWORD\"}}}" > /kaniko/.docker/config.json
    # Запуск сборки
    - /kaniko/executor \
        --context "dir://${CI_PROJECT_DIR}" \
        --dockerfile "${CI_PROJECT_DIR}/Dockerfile" \
        --destination "${CI_REGISTRY_IMAGE}:${CI_COMMIT_SHA}" \
        --cache=true \
        --cache-repo "${CI_REGISTRY_IMAGE}/cache" \
        --use-new-run
```

### Сценарий 2: Локальная отладка через Docker

Позволяет проверить сборку в среде, идентичной CI, без пуша в репозиторий.

```bash
docker run \
    -v $(pwd):/workspace \
    gcr.io/kaniko-project/executor:v1.24.0 \
    --dockerfile=/workspace/Dockerfile \
    --context=dir:///workspace \
    --build-arg APP_VERSION=1.0.0 \
    --no-push
```

## Работа с результатом сборки

Поскольку Kaniko не сохраняет образ в `docker images` локально, существуют специальные методы извлечения результата.

### Метод 1: Экспорт в TAR-архив
Позволяет сохранить образ в файл для последующей загрузки через `docker load`.

```bash
/kaniko/executor \
    --context=dir:///workspace \
    --destination=my-app:latest \
    --tar-path=/workspace/my-app.tar \
    --no-push
```

### Метод 2: Использование локального реестра
Идеально для имитации CI/CD среды.

1. Запуск реестра: `docker run -d -p 5000:5000 --name registry registry:2`
2. Сборка с пушем (используйте свой IP):
   ```bash
   /kaniko/executor \
       --context="dir:///workspace" \
       --destination="192.168.1.100:5000/my-app:latest" \
       --insecure
   ```

## Недостатки и ограничения

-   **Игнорирование `--mount`:** Kaniko распознает синтаксис BuildKit (`--mount=type=cache`), но **игнорирует** механизмы монтирования. Это приводит к потере производительности или ошибкам доступа к секретам.
-   **Отсутствие параллелизма:** В отличие от BuildKit, стадии сборки выполняются строго последовательно.
-   **Multi-arch:** Поддержка сборки под несколько архитектур реализована значительно слабее, чем в `docker buildx`.
-   **Сложность отладки:** Ошибки внутри `chroot` могут быть неочевидны (например, специфичные права доступа к `/dev`).
