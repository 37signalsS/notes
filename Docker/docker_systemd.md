# Systemd в Docker

## Определения

- **Systemd в Docker:** Запуск системы инициализации `systemd` в качестве первого процесса (PID 1) внутри контейнера.
- **PID 1 (Init):** Первый процесс в пространстве пользователя, отвечающий за управление службами, сбор "зомби-процессов" и корректное завершение работы системы.
- **Zombie Process:** Процесс, который завершил выполнение, но остался в таблице процессов, так как родительский процесс не считал его код возврата.
- **Cgroup v2 (Unified Hierarchy):** Современная иерархия групп управления Linux, требующая специфических настроек для работы вложенных менеджеров ресурсов.

## Основные концепции

### Почему запуск systemd в Docker считается анти-паттерном

1. **Нарушение принципа атомарности:** Docker спроектирован для запуска одного приложения в одном контейнере. `systemd` превращает контейнер в "микро-виртуалку" с набором служб, что усложняет мониторинг и логирование.
2. **Проблемы с привилегиями:** По умолчанию `systemd` требует `CAP_SYS_ADMIN` и доступа к `/sys/fs/cgroup`, что снижает изоляцию и безопасность.
3. **Сложность жизненного цикла:** Контейнеры должны быстро запускаться и корректно завершаться по `SIGTERM`. `systemd` имеет сложный процесс инициализации и требует специфического сигнала для завершения (`SIGRTMIN+3`).

### Сравнение подходов для работы с процессами

| Характеристика | systemd (внутри) | Tini / dumb-init | Supervisord / s6 |
| :--- | :--- | :--- | :--- |
| **Назначение** | Полноценная ОС в контейнере | Решение проблемы PID 1 | Групповой запуск служб |
| **Сложность** | Высокая | Минимальная | Средняя |
| **Изоляция** | Требует `CAP_SYS_ADMIN` | Стандартная (rootless-friendly) | Стандартная |
| **Сбор зомби** | Да | Да | Да |
| **Управление службами**| Да (`systemctl`) | Нет | Да |

## Практические сценарии

### Сценарий 1: Решение проблемы PID 1 (Рекомендуется)

Если вам нужно просто запускать один процесс и корректно обрабатывать сигналы, используйте `tini` (встроен в Docker через флаг `--init`).

```dockerfile
# В Dockerfile
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["my-app"]
```
Или при запуске: `docker run --init my-image`.

### Сценарий 2: Запуск нескольких служб без systemd

Для запуска связанных процессов (например, Nginx + PHP-FPM) используйте `supervisord`. Это позволяет избежать привилегированного режима.
Подробнее см. **[Паттерн "Multi-Process" в Docker](./Docker_logs/docker_multi_process_logging.md)**.

### Сценарий 3: "Хирургический" запуск systemd (2024+)

Если запуск `systemd` неизбежен (например, для тестирования Ansible-ролей или legacy-монолитов), используйте минимально необходимые привилегии вместо `--privileged`.

**Требования для Cgroup v2:**
1. Монтирование `/sys/fs/cgroup` в режиме `rw`.
2. Установка `STOPSIGNAL SIGRTMIN+3`.
3. Использование `tmpfs` для `/run` и `/tmp`.

```bash
docker run -d \
    --name systemd-node \
    --tmpfs /tmp --tmpfs /run --tmpfs /run/lock \
    -v /sys/fs/cgroup:/sys/fs/cgroup:rw \
    --cgroupns=private \
    --cap-add SYS_ADMIN \
    --security-opt seccomp=unconfined \
    my-systemd-image
```

### Сценарий 4: Использование специализированных рантаймов (Sysbox)

Рантайм **Sysbox** позволяет запускать `systemd` (и даже Docker в Docker) внутри контейнера без флагов `--privileged` или `SYS_ADMIN`, обеспечивая при этом изоляцию через User Namespaces.

```bash
docker run --runtime=sysbox-runc -d my-systemd-image
```

## Дополнительная информация

### Рекомендации по выбору

- **Для Production:** Используйте принцип "один контейнер — один процесс". Управляйте контейнерами через `systemd` на хосте. См. **[Интеграция Docker с systemd](../Linux/Core/systemd/docker_integration.md)**.
- **Для тестирования инфраструктуры (Ansible/Molecule):** Допускается использование `systemd` с хирургическими флагами или специализированных образов (например, `geerlingguy/docker-ubuntu2404-ansible`).
- **Для полной изоляции:** Если приложению требуется полноценная ОС, рассмотрите **[Альтернативные среды выполнения (Kata Containers)](./alternative_runtimes_and_tools.md)**.
