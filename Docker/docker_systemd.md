# Запуск systemd в Docker: анти-паттерн и его решения

## Определение

**Анти-паттерн "systemd в Docker"** — это попытка запустить `systemd` в качестве менеджера служб (PID 1) внутри Docker-контейнера. Такой подход нарушает базовый принцип контейнеризации "один процесс на контейнер" и создает ряд технических трудностей, связанных с безопасностью и изоляцией.

## Основные концепции: почему `systemd` не работает?

`systemd` спроектирован как фундаментальная основа операционной системы, а не как обычное приложение. Его запуск в контейнере "из коробки" невозможен по следующим причинам:

1.  **Требование PID 1**: `systemd` должен быть первым процессом в системе (PID 1), чтобы корректно управлять дочерними процессами и собирать "зомби". В Docker эту роль по умолчанию выполняет основной процесс, указанный в `CMD` или `ENTRYPOINT`.
2.  **Доступ к `cgroups`**: Для управления ресурсами `systemd` требует прямого и полного доступа к файловой системе `cgroups` хоста. Docker предоставляет контейнеру лишь ограниченное, виртуализированное представление в `/sys/fs/cgroup`, что недостаточно для `systemd`.
3.  **Требование специальных файловых систем**: `systemd` ожидает, что директории `/run`, `/run/lock` и `/tmp` будут смонтированы как `tmpfs`.
4.  **Требование привилегий**: Для выполнения своих задач `systemd` требует расширенных прав ядра Linux (capabilities), таких как `CAP_SYS_ADMIN`. В целях безопасности Docker по умолчанию отбирает эти права у контейнеров.

## Практические сценарии: решения и альтернативы

### Сценарий 1: Запуск нескольких процессов (рекомендуемый подход)

Если основной задачей является запуск нескольких процессов в одном контейнере, использование `systemd` не является правильным решением. Вместо этого следует применять легковесные менеджеры процессов (супервизоры), такие как `supervisord`.

Этот подход решает проблему управления дочерними процессами и агрегации их логов, не требуя небезопасных привилегий и не нарушая ключевые принципы работы Docker.

> **Подробное руководство по реализации этого паттерна, включая примеры конфигурации, находится в документе:**
> **[Паттерн "Multi-Process" в Docker](./Docker_logs/docker_multi_process_logging.md)**

### Сценарий 2: Принудительный запуск `systemd` (не рекомендуется)

**Внимание:** Этот метод значительно снижает уровень изоляции и безопасности контейнера. Используйте его только для тестирования или миграции легаси-систем, когда нет другого выбора.

Чтобы заставить `systemd` работать, необходимо вернуть ему все привилегии, которых его лишил Docker.

```bash
docker run -d --name systemd-container \
  --privileged \
  -v /sys/fs/cgroup:/sys/fs/cgroup:ro \
  my-systemd-image /sbin/init
```

*   `--privileged`: Дает контейнеру права, почти эквивалентные root-доступу на хосте. **Это создает значительную угрозу безопасности.**
*   `-v /sys/fs/cgroup:/sys/fs/cgroup:ro`: Пробрасывает `cgroups` хоста в контейнер в режиме "только чтение".
*   `/sbin/init`: Явно указывает `systemd` в качестве точки входа (PID 1).

## Дополнительная информация

Важно не путать запуск `systemd` *внутри* контейнера с использованием `systemd` на *хост-системе* для управления жизненным циклом самих контейнеров. Второй подход не является анти-паттерном и, наоборот, является хорошей практикой для интеграции контейнеров в существующую инфраструктуру.

Этот метод позволяет запускать, останавливать и управлять Docker-контейнерами как обычными системными службами.
