# Сетевой драйвер ipvlan

## Определения

- **Драйвер ipvlan** — это высокопроизводительный сетевой драйвер Docker, позволяющий контейнерам иметь уникальные IP-адреса, разделяя при этом **единый MAC-адрес** родительского физического интерфейса хоста.
- **Network L3 Routing** — режим передачи данных, при котором пакеты направляются на основе IP-адресов без использования ARP-запросов и широковещательных рассылок уровня L2.

## Основные концепции

В 2026 году (Docker v28+, ядра Linux 6.x) `ipvlan` стал основным выбором для высокоплотных микросервисных архитектур и публичных облаков (AWS, Azure, GCP). Он решает проблему ограничений на количество MAC-адресов на одном физическом порту или виртуальном интерфейсе (ENI).

### Режимы работы

1. **L2 (Layer 2 — по умолчанию)**:
   - Контейнеры находятся в том же широковещательном домене, что и хост.
   - Требуется наличие внешнего шлюза в той же подсети.
   - Поддерживает стандартный ARP.
2. **L3 (Layer 3 — маршрутизация)**:
   - Работает как маршрутизатор: трафик между контейнерами и внешней сетью передается на уровне IP.
   - **Преимущество**: Полное отсутствие ARP-штормов и широковещательного трафика, что критично при запуске более 1000 контейнеров на одном хосте.
   - **Особенности**: Не поддерживает DHCP; требует статической настройки или внешнего IPAM-контроллера.
3. **L3S (Layer 3 Symmetric)**:
   - Симметричный режим L3, пропускающий трафик через сетевой стек хоста.
   - **Зачем нужен**: Позволяет использовать **Stateful Firewalls** (nftables) и политики безопасности (Network Policies) для фильтрации трафика контейнеров.
   - Совместим с современными CNI-плагинами (Cilium, Calico) для обеспечения безопасности Zero-Trust.

### Производительность и технологии (Состояние на 2026 год)

- **BIG TCP (Linux 6.8+)**: Поддержка пакетов до 512 КБ существенно снижает нагрузку на CPU при передаче больших объемов данных (например, в базах данных или AI-воркloadах).
- **Hardware GRO (Generic Receive Offload)**: Позволяет достигать скорости 100+ Гбит/с на современных сетевых картах с минимальным оверхедом.
- **Облачная совместимость**: В отличие от `macvlan`, `ipvlan` не вызывает срабатывания Port Security в облаках, так как не меняет MAC-адрес источника.

### Сравнение с [macvlan](./macvlan.md)

| Характеристика | ipvlan | [macvlan](./macvlan.md) |
| :--- | :--- | :--- |
| **MAC-адрес** | MAC хоста (общий) | Уникальный для контейнера |
| **Уровень OSI** | L2 или L3 | L2 (Ethernet) |
| **Совместимость** | Высокая (Cloud, Wi-Fi) | Низкая (часто блокируется) |
| **Связь Хост-Контейнер**| Нативная в L3/L3S | Требует sub-interface |
| **Масштабируемость** | Экстремальная (тысячи узлов) | Ограничена CAM-таблицей |

## Практические сценарии

### Сценарий 1: Создание сети ipvlan L3 для высокой плотности

Используется для исключения накладных расходов на L2-трафик.

```bash
docker network create -d ipvlan \
  --subnet=10.100.0.0/24 \
  -o parent=eth0 \
  -o ipvlan_mode=l3 \
  --ipv6 --subnet=2001:db8:abc::/64 \
  ipvlan_l3_net
# → Сеть создана с поддержкой Dual-Stack
```

### Сценарий 2: Конфигурация через Docker Compose

Пример развертывания высокопроизводительного API в облачной среде.

```yaml
services:
  app:
    image: my-high-load-app:latest
    networks:
      cloud-net:
        ipv4_address: 10.100.0.50

networks:
  cloud-net:
    driver: ipvlan
    driver_opts:
      parent: eth0
      ipvlan_mode: l3
    ipam:
      config:
        - subnet: 10.100.0.0/24
```

### Сценарий 3: Использование VLAN (802.1Q)

Разделение трафика через тегированные интерфейсы.

```bash
# Привязка к VLAN 20 через eth0.20
docker network create -d ipvlan \
  --subnet=172.20.0.0/24 \
  -o parent=eth0.20 \
  vlan20_net
```

## Дополнительная информация

### Облачные нюансы (AWS/GCP/Azure)

- **AWS ENI**: При использовании `ipvlan` в AWS необходимо убедиться, что дополнительные IP-адреса, назначенные контейнерам, также зарегистрированы во вторичных IP-адресах соответствующего Elastic Network Interface (ENI).
- **IPAM**: Рекомендуется использовать плагины, интегрированные с API облачного провайдера, для автоматического резервирования адресов.

### Ограничения и DNS

- **DHCP**: Не работает из-за общего MAC. Требуется статический IP.
- **Service Discovery**: Встроенный DNS Docker не поддерживает автоматическое разрешение имен для `ipvlan` так же эффективно, как для `bridge`. Рекомендуется использовать внешние Consul/CoreDNS или записи в `/etc/hosts`.
- **Port Security**: На некоторых коммутаторах требуется настройка "IP Source Guard", чтобы разрешить трафик с нескольких IP через один MAC.
