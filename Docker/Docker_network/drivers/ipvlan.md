# Сетевой драйвер ipvlan

**Актуально для:** Docker Engine 29.x

## Определения

- **Драйвер ipvlan** — высокопроизводительный сетевой драйвер Docker, позволяющий контейнерам иметь уникальные IP-адреса, разделяя при этом единый MAC-адрес родительского физического интерфейса хоста.
- **Parent Interface (Родительский интерфейс)** — физический или виртуальный сетевой интерфейс хоста (например, `eth0` или `bond0`), на базе которого создаются ipvlan-интерфейсы.
- **IPAM (IP Address Management)** — механизм распределения IP-адресов в Docker-сетях. Для ipvlan требуется статическое назначение или внешний IPAM-контроллер.
- **Mode L2/L3/L3S** — режимы работы ipvlan: L2 (прозрачный мост), L3 (маршрутизация на уровне IP), L3S (симметричный L3 с прохождением через стек хоста).
- **Promiscuous Mode (Смешанный режим)** — режим сетевой карты, при котором она принимает все пакеты независимо от адресата. Требуется для macvlan, для ipvlan обычно не нужен.
- **nftables** — современный фреймворк фильтрации пакетов в Linux, заменяющий iptables. Docker Engine 29.x использует nftables по умолчанию.

## Основные концепции

### Архитектура и принцип работы

Драйвер `ipvlan` создает виртуальные интерфейсы на базе родительского интерфейса хоста. Все интерфейсы имеют один MAC-адрес, но разные IP-адреса. Это отличает его от `macvlan`, где каждому интерфейсу назначается уникальный MAC.

**Что происходит при запуске:**
1. Docker создает пару `ipvlan` (родительский + дочерний интерфейс) на хосте через `ip link add`.
2. Контейнер подключается к дочернему интерфейсу и получает IP из заданной подсети.
3. Трафик контейнера выходит в сеть с MAC-адресом родителя, но с собственным IP-адресом контейнера.
4. В режиме L3/L3S пакеты маршрутизируются на уровне IP без ARP-запросов между контейнерами.

**Поток пакета в режиме L3:**
```
Контейнер A (10.100.0.2) → ipvlan-интерфейс → Стек хоста (L3 routing) → eth0 → Сеть
```
- Отсутствует широковещательный домен между контейнерами.
- Нет ARP-запросов для коммуникации между контейнерами на одном хосте.
- Требует наличия маршрута в сети к подсети контейнеров.

### Режимы работы

При создании сети можно указать режим через `-o ipvlan_mode=`:

1. **L2 (Layer 2 — по умолчанию)**:
   - Контейнеры находятся в том же широковещательном домене, что и хост.
   - Требуется внешний шлюз в той же подсети.
   - Поддерживает стандартный ARP.
   - **Применение**: Когда контейнеры должны быть видимыми в L2-сети как отдельные узлы.

2. **L3 (Layer 3 — маршрутизация)**:
   - Трафик между контейнерами и внешней сетью передается на уровне IP.
   - **Преимущество**: Полное отсутствие ARP-штормов и широковещательного трафика, критично при высокой плотности контейнеров на хосте.
   - **Ограничение**: Не поддерживает DHCP; требует статической настройки или внешнего IPAM.
   - **Применение**: Высокоплотные микросервисные архитектуры, где каждый контейнер имеет уникальный IP.

3. **L3S (Layer 3 Symmetric)**:
   - Симметричный режим L3, пропускающий трафик через сетевой стек хоста.
   - **Зачем нужен**: Позволяет использовать Stateful Firewalls (nftables) и политики безопасности для фильтрации трафика контейнеров.
   - **Особенность**: Поддерживает connection tracking, что необходимо для NAT и stateful-правил.
   - **Применение**: Среды с требованиями Zero Trust, где трафик должен проходить через файервол хоста.

### Производительность и технологии

В современных ядрах Linux (6.x+) и Docker Engine 29.x `ipvlan` поддерживает:

- **XDP (eXpress Data Path)**: Обработка пакетов на раннем этапе сетевого стека с минимальной задержкой. Доступно через eBPF-программы. [eBPF в Linux](../../../Linux/Core/kernel/ebpf.md)
- **BIG TCP (Linux 6.8+)**: Поддержка пакетов до 512 КБ, снижающая нагрузку на CPU при передаче больших объемов данных.
- **Hardware GRO (Generic Receive Offload)**: Агрегация приходящих пакетов на уровне NIC, позволяет достигать скорости 100+ Гбит/с.
- **Zero-copy**: Минимальное копирование данных между пространствами ядра, снижающее задержку.

**Сравнение с [macvlan](./macvlan.md):**

| Характеристика | ipvlan | [macvlan](./macvlan.md) |
| :--- | :--- | :--- |
| **MAC-addr** | MAC хоста (общий) | Уникальный для контейнера |
| **Уровень OSI** | L2 или L3 | L2 (Ethernet) |
| **Совместимость** | Высокая (Wi-Fi, on-prem, облака) | Низкая (Wi-Fi, Port Security) |
| **Связь Хост-Контейнер** | Нативная в L3/L3S | Требует sub-interface |
| **Масштабируемость** | Экстремальная (тысячи узлов) | Ограничена CAM-таблицей |
| **Promiscuous Mode** | Обычно не требуется | Требуется на гипервизорах |
| **DHCP** | Ограничен (требует Relay) | Полноценная поддержка |

**Рекомендация**: Используйте `macvlan`, если вашим приложениям критически важны уникальные MAC-адреса (лицензирование, DHCP-резервации, легаси-мониторинг). В остальных случаях, особенно при высокой плотности контейнеров, используйте **[ipvlan](./ipvlan.md)** в режиме L3 или L3S.

### Взаимодействие со Swarm и Compose

- **Docker Compose**: Драйвер `ipvlan` поддерживается через `driver: ipvlan` и `driver_opts`.
- **Docker Swarm**: Для многохостовых конфигураций используйте config-only сети с `--config-from` для избежания дублирования IPAM-параметров.
- **Важно**: В Swarm ipvlan требует предварительного создания родительского интерфейса на каждом узле кластера.

## Практические сценарии

### Сценарий 1: Создание сети ipvlan L3 для высокой плотности

Используется для исключения накладных расходов на L2-трафик.

```bash
docker network create -d ipvlan \
  --subnet=10.100.0.0/24 \
  --gateway=10.100.0.1 \
  -o parent=eth0 \
  -o ipvlan_mode=l3 \
  ipvlan_l3_net
# → Сеть создана
```

Валидация:
```bash
# Проверка создания сети
docker network inspect ipvlan_l3_net -f '{{.Driver}}'
# → ipvlan

# Проверка режима
docker network inspect ipvlan_l3_net -f '{{.Options.ipvlan_mode}}'
# → l3
```

Очистка:
```bash
docker network rm ipvlan_l3_net
```

### Сценарий 2: Конфигурация через Docker Compose

Пример развертывания сервиса с прямым доступом в сеть.

```yaml
services:
  api:
    image: nginx:alpine
    networks:
      lan:
        ipv4_address: 10.100.0.50

networks:
  lan:
    driver: ipvlan
    driver_opts:
      parent: eth0
      ipvlan_mode: l3
    ipam:
      config:
        - subnet: 10.100.0.0/24
          gateway: 10.100.0.1
```

Валидация:
```bash
docker compose up -d
# → Создан сервис api
docker compose ps
# → api running

# Проверка IP контейнера
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' <container>
# → 10.100.0.50
```

Очистка:
```bash
docker compose down
```

### Сценарий 3: Использование VLAN (802.1Q)

Разделение трафика через тегированные интерфейсы.

```bash
# Привязка к VLAN 20 через eth0.20
docker network create -d ipvlan \
  --subnet=172.20.0.0/24 \
  --gateway=172.20.0.1 \
  -o parent=eth0.20 \
  -o ipvlan_mode=l3 \
  vlan20_net
```

Валидация:
```bash
# Проверка, что контейнер виден в VLAN 20
docker run --rm --network vlan20_net alpine ip route show
# → default via 172.20.0.1 dev eth0
```

Очистка:
```bash
docker network rm vlan20_net
```

### Сценарий 4: Режим L3S для Stateful Firewall

Использование симметричного L3 для прохождения трафика через nftables.

```bash
docker network create -d ipvlan \
  --subnet=10.100.0.0/24 \
  --gateway=10.100.0.1 \
  -o parent=eth0 \
  -o ipvlan_mode=l3s \
  ipvlan_l3s_net
```

Валидация:
```bash
# Проверка connection tracking
sudo conntrack -L -p tcp --dport 80
# → Должен видеть соединения контейнеров

# Проверка nftables
sudo nft list ruleset
# → Должны быть правила для ipvlan-интерфейсов
```

Очистка:
```bash
docker network rm ipvlan_l3s_net
```

### Сценарий 5: Диагностика производительности

Замер latency и throughput между контейнерами.

```bash
# Запуск двух контейнеров
docker run -d --name container1 --network ipvlan_l3_net alpine sleep 3600
docker run -d --name container2 --network ipvlan_l3_net alpine sleep 3600

# Замер latency
docker exec container1 ping -c 10 10.100.0.50
# → Должен показать минимальную задержку (<1 мс)

# Замер throughput с iperf3
docker run -d --name iperf-server --network ipvlan_l3_net \
  netstatic/iperf3 -s
docker run --rm --network ipvlan_l3_net netstatic/iperf3 -c <server-ip>
# → Должен показать высокую скорость (>10 Гбит/с в зависимости от NIC)
```

Очистка:
```bash
docker rm -f container1 container2 iperf-server
docker network rm ipvlan_l3_net
```

### Сценарий 6: Захват трафика на ipvlan-интерфейсе

Диагностика с использованием tcpdump.

```bash
# Запуск контейнера
docker run -d --name web --network ipvlan_l3_net nginx:alpine

# Захват трафика на хосте
sudo tcpdump -i ipvl0 -c 20
# → Захватит 20 пакетов с интерфейса ipvlan

# Или через nsenter
PID=$(docker inspect -f '{{.State.Pid}}' web)
sudo nsenter -t $PID -n tcpdump -i any -c 10
# → Захватит 10 пакетов из namespace контейнера
```

Очистка:
```bash
docker rm -f web
```

## Устранение неисправностей

### Типичные ошибки

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `Cannot find device "eth0"` | Родительский интерфейс не существует на хосте | Проверьте `ip link show` и укажите корректный интерфейс |
| `network ipvlan_l3_net is not compatible with network host` | Попытка подключения host-сети к ipvlan | Используйте `--network ipvlan_l3_net` или создайте отдельный контейнер |
| `Address already in use` | IP-адрес конфликтует с существующим интерфейсом | Проверьте `ip addr show` и используйте свободный IP |
| `RTNETLINK answers: File exists` | Интерфейс уже создан | Удалите старый интерфейс: `sudo ip link delete <iface>` |
| `operation not permitted` | Недостаточно прав для создания интерфейса | Запустите Docker с необходимыми capabilities или проверьте SELinux/AppArmor |
| `No DHCP offered` | DHCP не работает в режиме L3/L3S | Используйте статический IP или внешний IPAM |
| `ping: bad address` | Неверный формат IP или подсети | Проверьте CIDR в `docker network create` |
| `Container cannot reach gateway` | Отсутствует маршрут до шлюза | Добавьте маршрут: `sudo ip route add <subnet> via <gateway> dev <parent>` |

### Диагностика

- **Проверка родительского интерфейса**: `ip link show <parent>` — интерфейс должен существовать и быть UP.
- **Проверка ipvlan-интерфейсов**: `ip -brief link show type ipvlan` — список созданных интерфейсов.
- **Проверка маршрутов**: `ip route show` — убедитесь, что есть маршрут до подсети контейнеров.
- **Проверка ARP**: В режиме L3 ARP-запросы между контейнерами отсутствуют. `arp -a` должен показывать только шлюз.
- **Проверка iptables/nftables**: `sudo nft list ruleset` — убедитесь, что нет блокирующих правил для трафика контейнеров.
- **Логи демона**: `journalctl -u docker` — ошибки инициализации сети.
- **Capturing трафика**: `tcpdump -i <parent>` или `tcpdump -i <ipvlan_iface>` для захвата трафика.

## Рекомендации

### Безопасность

- **Изоляция**: ipvlan не предоставляет L2-изоляции между контейнерами на одном хосте. Используйте L3S с nftables для фильтрации.
- **Политики**: В Docker Swarm используйте Network Policies для ограничения коммуникации между сервисами. Для на-prem сред Cilium может обеспечивать L7-политики. [Cilium](../../../Kubernetes/Networking/Network/CNI/cilium.md)
- **MAC-адрес**: Так как MAC общий, невозможно использовать MAC-based аутентификацию или лицензирование.
- **SELinux/AppArmor**: Профили безопасности применяются, но не compensate за отсутствие L2-изоляции.

### Производительность

- **XDP/eBPF**: Для максимальной производительности рассмотрите XDP-программы для обработки пакетов на раннем этапе. [eBPF в Linux](../../../Linux/Core/kernel/ebpf.md)
- **Выбор режима**: L3/L3S исключают ARP-штормы, что критично при высокой плотности. Используйте L2 только если нужен прозрачный L2-доступ.
- **NIC Offload**: Убедитесь, что Hardware GRO/GSO включены на NIC: `ethtool -k <parent>`.
- **Для высоконагруженных сервисов** ipvlan обеспечивает производительность, близкую к нативной, минуя bridge и NAT.

### Управление жизненным циклом

- **Проверяйте родительский интерфейс** перед созданием сети: `ip link show <parent>`.
- **Не переименовывайте** родительский интерфейс без обновления конфигурации сети Docker.
- **Используйте `--config-from`** в Swarm для macvlan/ipvlan вместо дублирования параметров IPAM.
- **Удаление сети** возможно только если к ней не подключены контейнеры. Принудительное отключение: `docker network disconnect -f <network> <container>`.

### Отладка

- **Используйте Go-шаблоны** для `docker inspect`: `docker inspect -f '{{.NetworkSettings.Networks}}' <container>`.
- **Для захвата трафика** используйте `tcpdump` или `tshark` на родительском интерфейсе. [tcpdump](../../../Linux/Diagnostics/Networking/tcpdump.md)
- **Проверяйте DNS**: В режиме L3/L3S встроенный DNS работает, но разрешение имен может зависеть от внешнего DNS.
- **Мониторинг throughput**: Используйте `iperf3` для замера скорости между хостами. [iperf3](../../../Linux/Diagnostics/Networking/iperf3.md)

## Особенности и ограничения

### Драйверы

- **ipvlan**: Флаги `--ip` и `--alias` работают только если IP находится в пределах подсети сети.
- **macvlan**: Для сравнения и ограничений см. [macvlan.md](./macvlan.md).

### Переименование и удаление

- Docker CLI **не поддерживает** команду `rename` для сетей. Для изменения имени удалите сеть (`docker network rm`) и создайте новую.
- Удаление сети (`docker network rm`) возможно только если к ней **не подключены контейнеры**.

### Конфликты и пересечения

- Docker проверяет пересечение подсетей **только внутри своего демона**. Он не знает о внешних маршрутах хоста, существующих VLAN или маршрутах, добавленных вручную.
- В режиме L3 убедитесь, что сеть контейнеров маршрутизируется через родительский интерфейс хоста.

### Ограничения режимов

- **L2**: Зависит от ARP; не подходит для сетей с большим количеством контейнеров на хосте.
- **L3**: Не поддерживает DHCP; требует статического IP или внешнего IPAM; не поддерживает широковещательный трафик.
- **L3S**: Может иметь меньшую производительность, чем L3, из-за прохождения через стек хоста.

### Имена сетей

- Имя сети может содержать только буквы (a-z, A-Z), цифры (0-9), знаки подчёркивания (`_`), точки (`.`) и дефисы (`-`).
- Имена чувствительны к регистру.
- Длина имени: от 1 до 63 символов.

### Публичные сети

- ipvlan не является драйвером `host` или `none`. Контейнеры получают изолированное сетевое пространство, но с доступом к физической сети через родительский интерфейс.
- В отличие от `bridge`, ipvlan не выполняет NAT. Контейнеры видны в сети напрямую.

## Дополнительная информация

### Производительность и MTU

- **MTU**: ipvlan наследует MTU родительского интерфейса. При использовании инкапсуляции (VXLAN, GRE) убедитесь, что MTU уменьшен соответствующим образом.
- **BIG TCP**: Для пакетов > 4096 байт требуется поддержка ядром Linux 6.8+ и включенный BIG TCP на родительском интерфейсе.
- **Анализ интерфейса**: `ethtool -S <ipvlan_iface>` — статистика пакетов и ошибок.

### Интеграция с CNI и orchestrators

- **Kubernetes**: Docker не является стандартным runtime для Kubernetes, но ipvlan может использоваться в Cilium в режиме `--ipvlan`. [Cilium](../../../Kubernetes/Networking/Network/CNI/cilium.md)
- **IPVS**: В Docker Swarm Routing Mesh использует IPVS для балансировки. Для ipvlan-сетей VIP балансировка работает через IPVS. [IPVS](../../../Kubernetes/Networking/Network/CNI/ipvs.md)
- **Rootless Docker**: ipvlan поддерживается, но требует настройки `netlink` capabilities в rootless-режиме.
