# Сетевой драйвер host

**Актуально для:** Docker Engine 29.x

## Определения

- **Host-режим (`--network host`)** — сетевая модель Docker, при которой контейнер не получает изолированного сетевого пространства имен (Network Namespace) и использует сетевой стек хост-машины напрямую.
- **Network Namespace (Сетевое пространство имен)** — механизм ядра Linux, обеспечивающий изоляцию сетевых ресурсов (интерфейсов, таблиц маршрутизации, портов). В режиме `host` эта изоляция для контейнера отключается.
- **Port Binding (Публикация порта)** — механизм, делающий порт контейнера доступным снаружи. В режиме `host` флаги `-p`/`-P` игнорируются, так как контейнер слушает порты хоста напрямую.
- **Docker Desktop (macOS/Windows)** — десктопный клиент Docker, реализующий сетевой стек через виртуализацию. Начиная с версии 4.34+, поддерживает режим `host` на уровне L4 (TCP/UDP).
- **Rootless Docker** — режим запуска демона Docker без прав root. С 29.5 (moby/moby#47103) режим `host` корректно разделяет сетевой namespace хоста и обходит userspace-стек RootlessKit. Выбор сетевого драйвера для остальных контейнеров — см. «[Rootless: сетевой стек](../docker_network.md#rootless-сетевой-стек)».

## Основные концепции

### Архитектура и принцип работы

Драйвер `host` полностью отключает сетевую изоляцию между контейнером и хостом. Вместо создания отдельного Network Namespace с veth-парой и мостом, Docker запускает контейнер в сетевом пространстве имен хоста.

**Что происходит при запуске:**
1. Docker не создает veth-пару и не подключает контейнер к `docker0` или пользовательскому мосту.
2. Процессы внутри контейнера видят все сетевые интерфейсы хоста (`eth0`, `lo`, `wlan0` и т.д.).
3. Приложение в контейнере может привязаться к любому порту хоста напрямую, без NAT и без `docker-proxy`.
4. Контейнер наследует `hostname`, `/etc/hosts` и `/etc/resolv.conf` хоста.

**Почему это производительнее bridge:**
- Отсутствует NAT в цепочках `POSTROUTING`/`PREROUTING`.
- Отсутствует `docker-proxy` для каждого опубликованного порта.
- Отсутствует виртуальный мост и veth-пара.
- Пакеты не проходят через дополнительные слои сетевого стека.

### Поддержка платформ (Состояние на 2026 год)

- **Linux (Docker Engine)**: Полноценная поддержка. Контейнер имеет прямой доступ к интерфейсам хоста.
- **Docker Desktop (macOS/Windows)**: Начиная с версии 4.34+, поддерживается как опциональная функция.
  - **Ограничение**: Работает только на уровне L4 (TCP/UDP). Протоколы ниже TCP/UDP (ICMP, кастомные L3-протоколы) не поддерживаются.
  - **Ограничение**: Не совместим с Enhanced Container Isolation (ECI), так как изоляция контейнера от хоста и прямой доступ к сети хоста противоречат друг другу.
  - **Ограничение**: Работает только с Linux-контейнерами. Windows-контейнеры не поддерживаются.
- **Rootless Docker**: с 29.5 режим `host` разделяет сетевой namespace хоста и обходит userspace-стек RootlessKit, поэтому производительность сопоставима с root-режимом. До 29.5 демон находился внутри сетевого namespace RootlessKit и поведение было неожиданным. Обратная сторона — потеря изоляции namespace.

### Взаимодействие со Swarm и Compose

- **Docker Compose**: Для активации режима используется параметр `network_mode: host` на уровне сервиса. Параметр `networks` при этом игнорируется.
- **Docker Swarm**: Режим `host` поддерживается при создании сервисов через `docker service create --network host`.
  - **Критическое ограничение**: Если сервис слушает фиксированный порт, на одном узле кластера может быть запущена только **одна реплика** этого сервиса. При попытке запустить вторую реплику на том же узле возникнет конфликт портов.
  - Управляющий трафик (control traffic) Swarm продолжает передаваться через overlay-сеть, но данные сервиса используют сеть хоста.

## Практические сценарии

### Сценарий 1: Высокопроизводительный веб-сервер (NGINX)

Используется для исключения задержек NAT при обработке тысяч запросов в секунду.

```bash
docker run -d --name high-perf-nginx --network host nginx:alpine
# → Контейнер запущен, процесс NGINX привязан напрямую к порту 80 хоста
```

Валидация:
```bash
# Проверка, что контейнер слушает порт 80
docker exec high-perf-nginx ss -tulpn | grep :80
# → LISTEN 0 128 *:80 *:* users:(("nginx",pid=1,fd=6))

# Проверка интерфейсов изнутри контейнера
docker exec high-perf-nginx ip addr show
# → Выведет все физические интерфейсы хоста (eth0, docker0 и т.д.)

# Проверка доступности снаружи
curl -I http://localhost/
# → HTTP/1.1 200 OK
```

Очистка:
```bash
docker stop high-perf-nginx && docker rm high-perf-nginx
```

### Сценарий 2: Мониторинг ресурсов (Prometheus Node Exporter)

Агенты мониторинга должны иметь доступ к сетевым метрикам всех интерфейсов хоста.

```bash
docker run -d \
  --name node-exporter \
  --network host \
  --pid host \
  prom/node-exporter:latest
# → Node Exporter видит реальную статистику сетевых интерфейсов хоста
```

Валидация:
```bash
# Проверка метрик
curl -s http://localhost:9100/metrics | grep node_network_receive_bytes_total
# → node_network_receive_bytes_total{device="eth0",...} 123456789
```

### Сценарий 3: Docker Compose конфигурация

Пример использования в стеке мониторинга или для высоконагруженных API.

```yaml
services:
  api:
    image: my-app:latest
    network_mode: host
    restart: always
    volumes:
      - /sys/fs/cgroup:/sys/fs/cgroup:ro
```

Валидация:
```bash
docker compose up -d
# → Создан сервис api
docker compose ps
# → api  running  host network
```

### Сценарий 4: Диагностика сетевого стека

Поскольку контейнер использует сеть хоста, инструменты внутри контейнера видят весь трафик хоста.

```bash
# Проверка открытых портов хоста из контейнера
docker run --rm --network host alpine:latest ss -tulpn
# → Выведет все слушающие сокеты хоста

# Захват трафика на интерфейсе хоста
docker run --rm --network host --cap-add NET_RAW alpine:latest tcpdump -i any -c 10
# → Захватит 10 пакетов с любого интерфейса хоста
```

### Сценарий 5: Тестирование локальных сервисов

Доступ к сервисам, запущенным на хосте, из контейнера через `localhost`.

```bash
# Предположим, на хосте запущен PostgreSQL на порту 5432
docker run --rm --network host postgres:17-alpine pg_isready -h localhost -p 5432
# → localhost:5432 - accepting connections
```

## Устранение неисправностей

### Типичные ошибки

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `WARNING: Published ports are discarded when using host network mode` | Флаги `-p`/`-P` не работают в режиме `host` | Уберите флаги публикации портов; приложение слушает порты хоста напрямую |
| `port is already allocated` | Порт занят другим процессом на хосте | Найдите процесс: `sudo ss -tulpn \| grep :<PORT>`. Остановите конфликтующий процесс или используйте другой порт |
| `bind: permission denied` | Попытка привязаться к порту < 1024 без прав | Запустите контейнер с `--cap-add NET_BIND_SERVICE` или используйте порт > 1024 |
| `network host not supported` | Docker Desktop без включенной опции или Enhanced Container Isolation | Включите `Enable host networking` в Settings → Resources → Network. Отключите ECI |
| `Cannot connect to localhost` (Docker Desktop) | Host networking работает через виртуализированный стек, а не напрямую | На Docker Desktop используйте `host.docker.internal` для доступа к хосту, или включите host networking |

### Диагностика

- **Проверка занятых портов**: `sudo ss -tulpn \| grep :<PORT>` или `sudo netstat -tulpn \| grep :<PORT>`.
- **Проверка Network Namespace**: В режиме `host` у контейнера нет отдельного namespace. Проверка: `docker inspect -f '{{.HostConfig.NetworkMode}}' <container>` → должно быть `host`.
- **Проверка доступа к хосту**: Внутри контейнера `curl http://localhost:<PORT>` должен работать для сервисов хоста.
- **Логи демона**: `/var/log/docker.log` или `journalctl -u docker` для ошибок инициализации сети.

## Рекомендации

### Безопасность

- **Изоляция**: Режим `host` полностью отключает сетевую изоляцию. Используйте только для доверенных приложений.
- **Доступ к loopback**: Контейнер может обращаться к `127.0.0.1` хоста. Это позволяет обходить аутентификацию для сервисов, доверяющих локальным подключениям (Redis, PostgreSQL).
- **CAP_NET_RAW**: Если контейнеру не нужна возможность перехвата трафика (tcpdump), явно отбросьте capability: `--cap-drop NET_RAW`.
- **Файервол**: Docker не управляет `iptables/nftables` для режима `host`. Вся ответственность за фильтрацию входящего трафика ложится на системного администратора.
- **SELinux/AppArmor**: Профили безопасности (например, `docker-default`) применяются, но не compensate за отсутствие сетевой изоляции.

### Производительность

- **Zero Overhead**: Отсутствие NAT, моста и `docker-proxy` минимизирует задержки и нагрузку на CPU.
- **Для высоконагруженных сервисов** на одном хосте рассмотрите драйвер `host`. Это убирает NAT и мост из пути пакета, снижая задержку.
- **Для overlay-сетей** в Swarm используйте `--network host` только для критически важных сервисов, где каждая микросекунда на счету.

### Управление жизненным циклом

- **Проверяйте порты перед запуском**: Убедитесь, что нужные порты свободны на хосте.
- **Используйте `docker network connect/disconnect` с осторожностью**: В режиме `host` эти команды не работают, так как контейнер уже находится в сети хоста.
- **Не храните критичные данные** в контейнерах, подключённых к `host` сетям, без backup. При удалении контейнера все данные теряются.

### Отладка

- **Используйте Go-шаблоны** для `docker inspect`: `docker inspect -f '{{.HostConfig.NetworkMode}}' <container>`.
- **Для захвата трафика** на интерфейсе хоста используйте `tcpdump` или `tshark` внутри контейнера с `--cap-add NET_RAW`.
- **Проверяйте DNS**: В режиме `host` контейнер использует `/etc/resolv.conf` хоста. Если DNS не работает, проверьте конфигурацию хоста.

## Особенности и ограничения

### Драйверы

- **`host`**: Флаги `--ip` и `--alias` игнорируются, так как контейнер использует сетевой стек хоста напрямую. Контейнер не может быть подключён к другим сетям одновременно.
- **`none`**: После запуска контейнера с `--network none` его можно подключить к другим сетям через `docker network connect`.

### Переименование и удаление

- Docker CLI **не поддерживает** команду `rename` для сетей. Для изменения имени необходимо удалить сеть (`docker network rm`) и создать новую с нужным именем.
- Удаление сети (`docker network rm`) возможно только если к ней **не подключены контейнеры**. Принудительное отключение: `docker network disconnect -f <network> <container>`.

### Конфликты и пересечения

- Docker проверяет пересечение подсетей **только внутри своего демона**. Он не знает о внешних маршрутах хоста, существующих VLAN или маршрутах, добавленных вручную. Это может привести к потере связи при совпадении CIDR с корпоративной сетью.

### Имена сетей

- Имя сети может содержать только буквы (a-z, A-Z), цифры (0-9), знаки подчёркивания (`_`), точки (`.`) и дефисы (`-`).
- Имена чувствительны к регистру.
- Длина имени: от 1 до 63 символов.

### Ограничения Docker Desktop

- **Layer 4 только**: Поддерживаются только TCP и UDP. ICMP, GRE и другие протоколы ниже L4 не работают.
- **Enhanced Container Isolation (ECI)**: Не совместим с host networking. Если ECI включен, host networking отключается автоматически.
- **Только Linux-контейнеры**: Windows-контейнеры не поддерживаются.
- **Включение требуется вручную**: Функция отключена по умолчанию и требует включения в Settings → Resources → Network.

## Дополнительная информация

### Связь с другими компонентами

- **Docker Desktop**: Host networking требует явного включения в настройках. Без включения контейнеры с `--network host` завершатся с ошибкой.
- **Rootless Docker**: с 29.5 (moby/moby#47103) `--network host` разделяет сетевой namespace хоста и обходит userspace-стек RootlessKit, поэтому производительность сопоставима с root-режимом. Цена — потеря изоляции namespace.
- **Kubernetes**: Не поддерживает режим `host` напрямую через Docker. Используйте `hostNetwork: true` в манифесте Pod.
