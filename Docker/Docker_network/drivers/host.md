# Сетевой драйвер host

## Определения

- **Host-режим (`--network host`)** — это сетевая модель Docker, при которой контейнер не получает изолированного сетевого пространства имен (Network Namespace) и использует сетевой стек хост-машины напрямую.
- **Network Namespace (Сетевое пространство имен)** — механизм ядра Linux, обеспечивающий изоляцию сетевых ресурсов (интерфейсов, таблиц маршрутизации, портов). В режиме `host` эта изоляция для контейнера отключается.

## Основные концепции

Драйвер `host` является наиболее производительным сетевым решением в экосистеме Docker, так как он полностью устраняет уровни абстракции, характерные для режимов `bridge` или `overlay`.

### Архитектурные особенности

1. **Отсутствие изоляции**: Процессы в контейнере видят те же сетевые интерфейсы (например, `eth0`, `lo`, `wlan0`), что и пользователь на хосте.
2. **Производительность (Zero Overhead)**: Трафик не проходит через `docker-proxy`, виртуальные мосты (bridge) или правила NAT (IP Masquerade). Это минимизирует задержки (latency) и нагрузку на CPU, что критично для высоконагруженных систем.
3. **Управление портами**: Флаги `-p` (`--publish`) и `-P` игнорируются. Если приложение в контейнере слушает порт 80, оно автоматически занимает порт 80 на всех интерфейсах хоста.
4. **IPv6**: Нативная поддержка IPv6 без необходимости дополнительной настройки `daemon.json` или параметров сети Docker, так как используется конфигурация хоста.

### Поддержка платформ (Состояние на 2026 год)

- **Linux**: Полноценная поддержка всех функций (L2/L3).
- **Docker Desktop (macOS/Windows)**: Начиная с версии 4.34+, добавлена официальная поддержка режима `host`. 
  - **Ограничение**: Реализация работает на уровне **Layer 4 (TCP/UDP)** через виртуализированный стек. Низкоуровневые протоколы (ICMP, кастомные L3-протоколы) могут работать некорректно.
- **Rootless Docker**: В современных версиях (v28+) драйвер `host` по умолчанию использует **pasta** (Process-Address-Space-Translation). Это обеспечивает производительность, сопоставимую с Root-режимом, сохраняя при этом безопасность за счет отсутствия привилегий root.

### Взаимодействие со Swarm и Compose

- **Docker Compose**: Для активации режима используется параметр `network_mode: host` на уровне сервиса. Параметр `networks` при этом игнорируется.
- **Docker Swarm**: Режим `host` поддерживается, но имеет критическое ограничение: если сервис слушает фиксированный порт, на одном узле кластера может быть запущена только **одна реплика** этого сервиса. При попытке запустить вторую реплику на том же узле возникнет конфликт портов.

## Практические сценарии

### Сценарий 1: Высокопроизводительный веб-сервер (NGINX)

Используется для исключения задержек NAT при обработке тысяч запросов в секунду.

```bash
docker run -d --name high-perf-nginx --network host nginx:alpine
# → Контейнер запущен, процесс NGINX привязан напрямую к порту 80 хоста
```

Проверка интерфейсов изнутри контейнера:
```bash
docker exec high-perf-nginx ip addr show
# → Выведет все физические интерфейсы хоста (eth0, docker0 и т.д.)
```

### Сценарий 2: Мониторинг ресурсов (Prometheus Node Exporter)

Агенты мониторинга должны иметь доступ к сетевым метрикам всех интерфейсов хоста.

```bash
docker run -d \
  --name node-exporter \
  --network host \
  --pid host \
  prom/node-exporter
# → Node Exporter видит реальную статистику сетевых интерфейсов хоста
```

### Сценарий 3: Docker Compose конфигурация

Пример использования в стеке мониторинга или для высоконагруженных API.

```yaml
services:
  api:
    image: my-app:latest
    network_mode: host
    restart: always
```

### Сценарий 4: Диагностика сетевого стека

Поскольку контейнер использует сеть хоста, инструменты внутри контейнера (например, `tcpdump` или `ss`) видят весь трафик хоста.

```bash
# Проверка открытых портов хоста из контейнера
docker run --rm --network host alpine:latest ss -tulpn
```

## Дополнительная информация

### Безопасность и риски

Использование драйвера `host` существенно снижает уровень безопасности системы:
- **Доступ к локальным сервисам (Loopback)**: Контейнер может обращаться к `127.0.0.1` хоста. Это позволяет обходить аутентификацию для баз данных (например, Redis или PostgreSQL), настроенных на доверие локальным подключениям.
- **Linux Capabilities**: Процесс в контейнере может получить доступ к низкоуровневым операциям. Например, при наличии `CAP_NET_RAW` контейнер может перехватывать (sniffing) трафик других контейнеров на этом же хосте.
- **Файервол**: Docker не управляет правилами `iptables/nftables` для режима `host`. Вся ответственность за фильтрацию входящего трафика ложится на системного администратора.

### Сравнение с другими драйверами

| Характеристика | Bridge (дефолт) | Host | Overlay (Swarm) |
| :--- | :--- | :--- | :--- |
| **Изоляция** | Высокая (L2/L3) | Отсутствует | Высокая (L2) |
| **Производительность** | Средняя (NAT overhead) | Максимальная (Native) | Средняя (VXLAN overhead) |
| **Сложность настройки** | Низкая | Минимальная | Средняя |
| **Сценарий** | Обычные приложения | Высокая нагрузка | Кластеры / Микросервисы |

### Взаимодействие и DNS

- **Hostname**: По умолчанию контейнер наследует `hostname` хост-машины. Изменение hostname внутри контейнера может повлиять на конфигурацию хоста (в зависимости от настроек `/etc/hosts`).
- **Service Discovery**: Контейнеры в режиме `host` **не могут** использовать встроенный DNS Docker для обращения к контейнерам в других сетях (например, `bridge`) по их именам. Для связи необходимо использовать внешние DNS-резолверы или IP-адреса.
