# Драйвер сети: bridge

## Определения

**Bridge** — сетевой драйвер Docker, работающий по принципу сетевого моста. Он создает изолированную внутреннюю сеть на хосте, позволяя контейнерам взаимодействовать друг с другом и с внешним миром через NAT. Это драйвер по умолчанию для отдельных контейнеров.

## Основные концепции

**Принцип работы**

При запуске Docker создает на хосте виртуальный сетевой мост (по умолчанию `docker0`), который функционирует как коммутатор и шлюз для контейнеров. Каждому контейнеру, подключенному к этой сети, назначается IP-адрес из внутренней подсети.

Для каждого контейнера создается пара виртуальных Ethernet-интерфейсов (`veth`):

- Один конец (`eth0`) помещается в сетевое пространство имен контейнера.
- Другой конец подключается к мосту `docker0` (или другому мосту в случае пользовательской сети).

Эти `veth`-пары действуют как виртуальные "патч-корды", соединяя контейнер с мостом и обеспечивая сетевую связность.

**Почему bridge, а не отдельные veth-пары:**

При использовании только veth-пар без bridge для нескольких контейнеров в одной подсети возникает **конфликт маршрутов**:

```bash
# Контейнер 1: маршрут 172.18.0.0/16 dev veth0
# Контейнер 2: маршрут 172.18.0.0/16 dev veth1
```

Оба маршрута указывают на одну сеть — первый маршрут перехватывает весь трафик, нарушая связность со вторым контейнером.

**Bridge решает проблему:**

- Работает на уровне L2 (Ethernet), а не L3 (IP)
- Контейнеры общаются напрямую через MAC-адреса
- В таблице маршрутизации хоста — один маршрут: `172.18.0.0/16 dev br0`
- Масштабируется на десятки контейнеров без конфликтов

**Виды bridge-сетей**

1. **Сеть по умолчанию (`bridge`)**: Создается автоматически. В этой сети **разрешение имен контейнеров по DNS не работает**, и взаимодействие возможно только по IP-адресам.
2. **Пользовательские сети (`user-defined bridge`)**: Создаются вручную командой `docker network create`. **Это рекомендуемый подход**. Они предоставляют [встроенный DNS-сервер](../dns_and_service_discovery.md) для разрешения имен контейнеров и лучшую изоляцию.

**Связь и доступ**

- **Внутренняя связь**: Контейнеры в одной **пользовательской** bridge-сети могут обращаться друг к другу по именам. В сети по умолчанию — только по IP-адресам.
- **Доступ извне**: Для предоставления доступа к сервису извне требуется явный проброс портов с хоста в контейнер (`-p ХОСТ:КОНТЕЙНЕР` или `-P`).

## Практические сценарии

### Создание и использование пользовательской сети

1. **Создать сеть:**

    ```bash
    docker network create my-bridge-net
    ```

2. **Запустить контейнер-сервер:**
    Запустим `nginx` и назовем его `web-server`.

    ```bash
    docker run -d --name web-server --network my-bridge-net nginx
    ```

3. **Обратиться к серверу по имени из другого контейнера:**
    Из временного контейнера `alpine` в той же сети "пропингуем" `web-server` по имени.

    ```bash
    docker run --rm --network my-bridge-net alpine ping -c 4 web-server
    ```

    В выводе будет виден успешный обмен пакетами, подтверждающий, что имя `web-server` было разрешено в IP-адрес.

### Анализ bridge-сетей с помощью `brctl`

Для детального анализа сетевых мостов на хосте можно использовать утилиту `brctl`.

1. **Установка (если требуется):**

    ```bash
    sudo apt-get update && sudo apt-get install -y bridge-utils
    ```

2. **Просмотр мостов:**
    Команда `brctl show` отображает все активные мосты и подключенные к ним интерфейсы.

    ```sh
    brctl show
    # Вывод:
    # bridge name     bridge id               STP enabled     interfaces
    # docker0         8000.0242ac110002       no              vethXXXXXX
    # br-a1b2c3d4e5f6  8000.0242ab120001       no              vethYYYYYY
    ```

    - `bridge name`: Имя моста (`docker0` для сети по умолчанию, `br-<id>` для пользовательских).
    - `interfaces`: Список `veth`-интерфейсов, соответствующих подключенным контейнерам.

## Дополнительная информация

### Производительность и `docker-proxy`

Проброс портов в режиме `bridge` осуществляется через userspace-прокси-процесс (`docker-proxy`). Этот процесс может создавать значительные накладные расходы для приложений с высокой частотой коротких запросов (high QPS), например, для баз данных. В таких сценариях падение производительности может достигать 50% и более.

Для критичных к производительности приложений рекомендуется использовать сетевой режим [`host`](./host.md) или [`macvlan`](./macvlan.md).

### Ограничения

- В сети `bridge`, созданной **по умолчанию**, отсутствует разрешение имен контейнеров через DNS.
- Производительность может быть ниже по сравнению с режимом `host` из-за NAT и `docker-proxy`.
