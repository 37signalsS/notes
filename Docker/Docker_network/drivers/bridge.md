# Сетевой драйвер bridge

**Актуально для:** Docker Engine 29.x

## Определения

- **Bridge (`--network bridge`)** — сетевой драйвер Docker, реализующий программный мост (коммутатор) на хосте. Позволяет контейнерам в одной сети общаться между собой и с внешним миром через NAT.
- **veth-пара (Virtual Ethernet)** — пара виртуальных сетевых интерфейсов, работающих как "труба": пакет, вошедший в один конец, мгновенно выходит из другого. Используется для связи Network Namespace контейнера с мостом на хосте.
- **NAT (Network Address Translation)** — механизм преобразования IP-адресов. В Docker используется для предоставления контейнерам доступа в интернет через IP-адрес хоста и для публикации портов.
- **MTU (Maximum Transmission Unit)** — максимальный размер пакета данных, передаваемого за один раз по сетевому интерфейсу без фрагментации. В Docker стандартное значение — 1500 байт.
- **IPAM (IP Address Management)** — подсистема управления IP-адресным пространством Docker (подсети, шлюзы, диапазоны выдачи, резервные адреса).
- **DNS (Domain Name System)** — система доменных имён. Встроенный DNS-сервер Docker (`127.0.0.11`) обеспечивает автоматическое разрешение имён контейнеров в пользовательских сетях.
- **ICC (Inter-Container Communication)** — параметр, управляющий возможностью контейнеров в одной bridge-сети общаться напрямую через неопубликованные порты.
- **DOCKER-USER chain** — специальная цепочка в `iptables`, зарезервированная для пользовательских правил файревола, обрабатываемая до автоматических правил Docker.
- **nftables** — современный фреймворк файревола Linux, начиная с Docker 29.0 поддерживаемый как нативный бэкенд вместо iptables.

## Основные концепции

### Архитектура и принцип работы

Драйвер `bridge` является стандартом для запуска одиночных контейнеров и небольших приложений. Он обеспечивает баланс между изоляцией и удобством настройки.

При запуске Docker создает виртуальный мост (по умолчанию `docker0`). Процесс подключения контейнера выглядит следующим образом:
1. Создается **veth-пара**.
2. Один конец (`eth0`) помещается внутрь Network Namespace контейнера.
3. Второй конец (называется `vethXXXX`) остается на хосте и подключается к мосту.
4. Контейнер получает IP-адрес из подсети моста (например, `172.17.0.0/16`).

**Почему используется мост, а не прямая маршрутизация?**
Использование моста позволяет контейнерам общаться на уровне L2 (Ethernet) через MAC-адреса. Это избавляет хост от необходимости управлять десятками маршрутов в таблице маршрутизации L3, что повышает масштабируемость и исключает конфликты при использовании одинаковых подсетей в разных сетях Docker.

### Жизненный цикл пакета (Packet Flow)

Ниже описан детальный путь пакета при обращении к опубликованному порту контейнера (Port Publishing) на примере взаимодействия клиента и Nginx.

#### Сценарий: Запрос клиента к сервису Nginx
- **Хост**: `eth0` (192.168.1.10), `lo` (127.0.0.1), `docker0` (172.18.0.1).
- **Контейнер Nginx**: IP `172.18.0.10`, внутренний порт `3000`, опубликован как `8080`.

**Путь "Туда" (Запрос клиента → Nginx):**
1. **Вход на хост**: Пакет приходит на интерфейс `lo` (127.0.0.1:8080) или `eth0` (192.168.1.10:8080).
2. **DNAT в iptables/nftables**: В таблице `nat` (цепочка `PREROUTING`) происходит трансляция назначения: `Destination IP:Port` меняется с внешнего IP хоста на внутренний IP контейнера — `172.18.0.10:3000`.
3. **Мост `docker0`**: Пакет направляется в виртуальный мост `docker0` (L2-коммутатор).
4. **Интерфейс `veth`**: Мост пересылает пакет в соответствующий внешний конец veth-пары (`veth0` на хосте).
5. **Переход в контейнер**: Через veth-пару пакет мгновенно оказывается на интерфейсе `eth0` внутри Network Namespace контейнера.
6. **Обработка**: Пакет достигает процесса `nginx`, слушающего порт `3000`.

**Путь "Обратно" (Ответ Nginx → Клиент):**
7. **Ответ сервиса**: Nginx формирует ответ и отправляет его через свой `eth0`.
8. **Переход на хост**: Пакет проходит через veth-пару обратно в пространство имен хоста.
9. **Мост `docker0`**: Пакет проходит через мост.
10. **SNAT в iptables/nftables**: В таблице `nat` (цепочка `POSTROUTING`) происходит обратная трансляция: адрес источника (`Source IP`) меняется с внутреннего IP контейнера на внешний IP хоста с сохранением опубликованного порта (`192.168.1.10:8080`).
11. **Выход с хоста**: Пакет уходит через `eth0` (внешний интерфейс).
12. **Получение**: Клиент (`curl`) получает ответ.

### Эволюция и безопасность (Docker Engine 29.x)

Работа драйвера `bridge` эволюционировала в сторону повышения безопасности и производительности:

1. **Secure by Default (v28+)**: Docker по умолчанию блокирует (DROP) входящий трафик к IP-адресам контейнеров из локальной сети (LAN), если порты не были явно опубликованы через `-p`. Это закрывает старую проблему безопасности, когда внутренние сервисы могли быть доступны соседям по дата-центру.
2. **Переход на nftables (v29.0+)**: Docker поддерживает нативный **nftables** как бэкенд файревола. При включении создаются таблицы `ip docker-bridges` и `ip6 docker-bridges`. Цепочка `DOCKER-USER` отсутствует в nftables-режиме; фильтрация осуществляется через пользовательские nftables-правила с приоритетом выше, чем у таблиц Docker.
3. **IPv6 Routed Mode (v28.0+)**: Параметр `com.docker.network.bridge.gateway_mode_ipv6=routed` позволяет контейнерам получать публичные IPv6-адреса и работать без NAT66, обеспечивая прямую маршрутизацию трафика. В версиях до 28.0 опция принималась, но поведение не применялось. Полный набор режимов шлюза — в разделе «[Публикация портов](../docker_network.md#gateway-modes-что-выбрать-для-изоляции)».

### IPAM и DNS в bridge-сетях

- **IPAM**: Docker выделяет IP-адреса из указанной подсети автоматически. Поддерживаются фиксированные IP (`--ip`), диапазоны выдачи (`--ip-range`) и резервные адреса (`--aux-address`).
- **DNS**: В пользовательских bridge-сетях Docker автоматически настраивает `/etc/resolv.conf` с DNS-сервером `127.0.0.11`. В дефолтной сети `bridge` автоматическое разрешение имён по имени контейнера **не работает** — только по IP или через `--link` (deprecated).
- **Несколько адресов под одним именем**: при обращении к имени, объявленному на нескольких контейнерах, DNS возвращает все их IP, но порядок **случайно перемешивается при каждом ответе** — это не round-robin. Балансировку выполняет клиент, перебирающий все адреса. Подробности — в [DNS и Service Discovery](../dns_and_service_discovery.md#порядок-адресов-при-нескольких-контейнерах-под-одним-именем).

### Типы мостов

- **Дефолтный (`bridge`)**: Создается автоматически. **Минусы**: нет встроенного DNS (связь только по IP), все контейнеры по умолчанию попадают в одну сеть.
- **Пользовательский (`user-defined bridge`)**: Создается вручную. **Плюсы**: автоматический DNS-сервер (обращение по именам), лучшая изоляция, возможность "горячего" подключения.

## Практические сценарии

### Сценарий 1: Создание сети с расширенными настройками (MTU и IPAM)

Создание изолированной сети с фиксированной подсетью и кастомным MTU для совместимости с VPN или физической сетью.

```bash
docker network create \
  --driver bridge \
  --subnet 10.10.0.0/24 \
  --gateway 10.10.0.1 \
  --opt com.docker.network.driver.mtu=1450 \
  my-custom-net
# → Создана сеть с MTU 1450 и кастомной подсетью
```

Валидация:
```bash
# Проверка параметров сети
docker network inspect my-custom-net -f '{{.Driver}} {{.Scope}} {{json .IPAM.Config}}'
# → bridge local [{"Gateway":"10.10.0.1","Subnet":"10.10.0.0/24"}]

# Проверка MTU
docker run --rm --network my-custom-net alpine ip link show eth0 | grep mtu
# → mtu 1450
```

Очистка:
```bash
docker network rm my-custom-net
```

### Сценарий 2: Изолированная внутренняя сеть (--internal)

Создание сети, где контейнеры могут общаться между собой, но не имеют выхода в интернет. Используется для баз данных и других критичных сервисов.

```bash
docker network create --internal private-db-net
docker run -d --name secure-db --network private-db-net mariadb:latest
# → Контейнер может общаться с другими в этой сети, но доступ к 8.8.8.8 закрыт
```

Валидация:
```bash
# Проверка доступности другого контейнера в той же сети
docker run --rm --network private-db-net alpine ping -c 1 secure-db
# → 1 packets transmitted, 1 received

# Проверка блокировки выхода в интернет (должен таймаутить)
docker run --rm --network private-db-net alpine ping -c 1 8.8.8.8 || true
# → timeout или ошибка соединения
```

### Сценарий 3: Статический IP для контейнера

Назначение фиксированного IP-адреса контейнеру для совместимости с legacy-системами или конфигурационными файлами.

```bash
docker run -d \
  --name static-web \
  --network my-custom-net \
  --ip 10.10.0.50 \
  nginx:alpine
# → Контейнер всегда будет получать адрес 10.10.0.50
```

Валидация:
```bash
# Проверка IP
docker inspect static-web -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
# → 10.10.0.50

# Проверка доступности по IP
docker run --rm --network my-custom-net alpine ping -c 1 10.10.0.50
# → 1 packets transmitted, 1 received
```

Очистка:
```bash
docker stop static-web && docker rm static-web
```

### Сценарий 4: Управление связностью (ICC)

Отключение прямого общения между контейнерами в одной сети для повышения безопасности.

```bash
docker network create -o "com.docker.network.bridge.enable_icc=false" isolated-bridge
# → Контейнеры в этой сети не могут пинговать друг друга напрямую
```

Валидация:
```bash
# Запуск двух контейнеров
docker run -d --name web --network isolated-bridge nginx:alpine
docker run -d --name app --network isolated-bridge alpine sleep 3600

# Проверка: прямая связь блокирована (неопубликованный порт)
docker exec app ping -c 1 web
# → timeout или 100% packet loss

# Проверка: связь через опубликованный порт работает
docker run --rm --network isolated-bridge alpine wget -qO- http://web:80
# → HTML-код nginx
```

Очистка:
```bash
docker stop web app && docker rm web app
docker network rm isolated-bridge
```

### Сценарий 5: Диагностика MTU и фрагментации

Диагностика проблем с MTU, приводящих к зависающим SSH-сессиям или медленной загрузке файлов через VPN.

```bash
# 1. Проверка MTU физического интерфейса
ip link show eth0 | grep mtu
# → mtu 1500

# 2. Проверка MTU bridge-интерфейса
ip link show docker0 | grep mtu
# → mtu 1500

# 3. Проверка MTU внутри контейнера
docker run --rm alpine ip link show eth0 | grep mtu
# → mtu 1500

# 4. Тест фрагментации (с флагом DF)
docker run --rm alpine ping -c 1 -M do -s 1472 8.8.8.8
# → 1472 + 28 (ICMP header) = 1500 — должно работать
```

Если пинг с `-s 1472` не проходит, а с `-s 1400` проходит — проблема в MTU. Решение: настройте MTU моста через `--opt com.docker.network.driver.mtu=1400`.

### Сценарий 6: Многосетевое подключение контейнера

Запуск контейнера в одной сети и подключение к второй с алиасами и статическим IP.

```bash
# Создание сетей
docker network create frontend-net
docker network create backend-net

# Запуск контейнера в frontend
docker run -d --name my-app --network frontend-net nginx:alpine

# Подключение к backend со статическим IP и алиасами
docker network connect \
  --ip 10.40.0.20 \
  --alias api \
  --alias app-internal \
  backend-net my-app
```

Валидация:
```bash
# Проверка: контейнер виден в обеих сетях
docker network inspect frontend-net -f '{{range .Containers}}{{.Name}}{{"\n"}}{{end}}'
# → my-app

docker network inspect backend-net -f '{{range .Containers}}{{.Name}} -> {{.IPv4Address}}{{"\n"}}{{end}}'
# → my-app -> 10.40.0.20/24

# Проверка изнутри контейнера
docker exec my-app sh -c "ip route | grep 10.40"
# → 10.40.0.0/24 via 10.40.0.1 dev eth1

# Проверка алиаса (DNS)
docker exec my-app getent hosts api
# → 10.40.0.20 api
```

Очистка:
```bash
docker stop my-app && docker rm my-app
docker network rm frontend-net backend-net
```

### Сценарий 7: Захват трафика на bridge-интерфейсе

Диагностика сетевого взаимодействия контейнеров через захват пакетов на мосте.

```bash
# 1. Запуск контейнеров
docker run -d --name web --network my-net nginx:alpine
docker run -d --name app --network my-net alpine sleep 3600

# 2. Захват трафика на bridge-интерфейсе хоста
sudo tcpdump -i br-$(docker network inspect my-net -f '{{.Id}}' | cut -c 1-12) -nn -c 20
# → Захват первых 20 пакетов между контейнерами

# 3. Захват трафика внутри namespace контейнера
PID=$(docker inspect -f '{{.State.Pid}}' app)
sudo nsenter -t $PID -n tcpdump -i eth0 -nn -c 10
# → Захват изнутри контейнера
```

Очистка:
```bash
docker stop web app && docker rm web app
```

## Устранение неисправностей

### Типичные ошибки

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `Error response from daemon: network ... not found` | Сеть удалена или опечатка в имени | Проверьте имя: `docker network ls --filter name=<prefix>` |
| `Error response from daemon: network ... is in use` | К сети подключены контейнеры | Отключите контейнеры: `docker network disconnect <network> <container>` или используйте `disconnect -f` |
| `Error response from daemon: invalid subnet` | Пересечение с существующей сетью или неверный CIDR | Проверьте существующие подсети: `docker network inspect <network> -f '{{.IPAM.Config}}'` |
| `Cannot resolve container name` | Контейнер в дефолтном `bridge` или DNS отключен | Используйте пользовательскую bridge-сеть для DNS или обратитесь по IP |
| `Connection timed out` | MTU mismatch, файервол, или контейнер не слушает порт | Проверьте MTU, правила `DOCKER-USER`, `docker logs <container>` |
| `wget/curl: couldn't connect to host` | Контейнер не имеет сетевого доступа или порт не опубликован | Проверьте `docker network connect`, `-p` флаг, `docker ps` |
| `network-scoped alias ... does not match the current network` | При подключении указан IP, но алиас из другой сети | Укажите `--alias` только для целевой сети |
| `invalid MTU` | MTU меньше 68 или больше 65535, или конфликт с физическим интерфейсом | Укажите корректный MTU (рекомендуется 1450-1500) |

### Диагностика

- **Проверка режима сети**: `docker inspect -f '{{.HostConfig.NetworkMode}}' <container>` → должно быть `bridge` или имя пользовательской сети.
- **Проверка интерфейсов**: `docker exec <container> ip addr show` → `eth0` с IP из подсети моста.
- **Проверка DNS**: `docker exec <container> cat /etc/resolv.conf` → должен содержать `nameserver 127.0.0.11`.
- **Проверка DNS резолвинга**: `docker exec <container> getent hosts <имя_контейнера>` → должен вернуть IP.
- **Проверка таблицы маршрутизации**: `docker exec <container> ip route` → шлюз по умолчанию через `eth0`.
- **Проверка bridge-интерфейсов**: `ip link show type bridge` → список всех мостов.
- **Проверка veth-пар**: `ip link show master br-<ID>` → интерфейсы, подключенные к мосту.
- **Проверка правил файревола**: `iptables -L DOCKER-USER -v -n` или `sudo nft list ruleset`.
- **Логи демона**: `/var/log/docker.log` или `journalctl -u docker` для ошибок инициализации сети.

## Рекомендации

### Безопасность

- **Используйте пользовательские сети** вместо дефолтного `bridge`. Дефолтный `bridge` не поддерживает автоматическое DNS-резолвинг по именам контейнеров.
- **Отключайте ICC** в продакшне на уровне отдельных сетей: `-o com.docker.network.bridge.enable_icc=false`. Глобальное отключение через `daemon.json` рекомендуется только если все приложения готовы к работе с опубликованными портами.
- **Изолируйте базы данных** через `--internal`. Это предотвращает утечку данных наружу при компрометации контейнера.
- **Используйте цепочку `DOCKER-USER`** для кастомных правил файревола. В nftables-режиме создайте таблицу с приоритетом выше, чем у таблиц Docker. Детали: [Сетевые политики Docker](../docker_network_policies.md).
- **Не публикуйте порты без необходимости**. Если сервис доступен только внутри сети, не используйте `-p`.
- **Метки (`--label`)**: Используйте метки для всех сетей. Это упрощает аудит (`docker network ls --filter label=env=prod`) и автоматическую очистку.

### Производительность

- **MTU**: При использовании VPN-туннелей, VXLAN или инкапсуляции настройте MTU моста через `--opt com.docker.network.driver.mtu=<значение>`. Стандартный MTU 1500 работает только на "чистых" физических сетях без инкапсуляции. Для VXLAN overhead = 50 байт, поэтому MTU overlay сети = 1450 при физическом MTU 1500.
- **Для высоконагруженных сервисов** на одном хосте рассмотрите драйвер `host` (`--network host`). Это убирает NAT и мост из пути пакета, снижая задержку. Детали: [Сетевой драйвер host](./host.md).
- **nftables**: При использовании Docker 29.0+ включите нативный nftables-бэкенд для снижения нагрузки на CPU при большом количестве правил.

### Управление жизненным циклом

- **Проверяйте параметры после создания** через `docker network inspect`. Это позволяет отловить опечатки в CIDR или незаданные опции до запуска контейнеров.
- **Используйте `docker network prune` с фильтрами**, а не без фильтров. Без фильтров prune удалит все неиспользуемые сети, включая те, что были созданы скриптами развёртывания.
- **Не храните критичные данные в контейнерах**, подключённых к `--internal` сетям, без backup. При удалении сети все подключённые контейнеры отключаются, и если они зависят от этой сети для связи — могут потерять доступ к зависимостям.
- **Используйте `--config-from`** для macvlan/ipvlan в Swarm вместо дублирования параметров IPAM на каждом узле.

### Отладка

- **Используйте Go-шаблоны** вместо `grep` на полном JSON. Шаблоны работают быстрее и дают структурированный вывод.
- **Для сложных запросов** используйте `--format json` + `jq`. Это позволяет фильтровать, сортировать и группировать данные.
- **Для захвата трафика** на bridge-интерфейсе используйте `nsenter` или `--net=host`, чтобы избежать проблем с правами доступа к network namespace.
- **Проверяйте DNS внутри контейнера** через `nslookup` или `getent hosts`, если контейнер не может разрешить имена других контейнеров в той же сети. Детали: [DNS и Service Discovery](../dns_and_service_discovery.md).

## Особенности и ограничения

### Драйверы и подключение

- **`host`**: Флаги `--ip` и `--alias` игнорируются, так как контейнер использует сетевой стек хоста напрямую. Контейнер не может быть подключён к другим сетям одновременно.
- **`none`**: Полностью отключает сеть. После запуска контейнера с `--network none` его можно подключить к другим сетям через `docker network connect`.
- **`overlay`**: Требует активированного Swarm-режима (`docker swarm init` или `docker swarm join`). Без Swarm создание overlay-сети завершится ошибкой.
- **`macvlan` / `ipvlan`**: Требуют предварительного создания интерфейса на хосте (`ip link add`) и настройки promiscuous mode на физическом интерфейсе (для macvlan). В Swarm используйте config-only сети.

### Переименование и удаление

- Docker CLI **не поддерживает** команду `rename` для сетей. Для изменения имени необходимо удалить сеть (`docker network rm`) и создать новую с нужным именем.
- Удаление сети (`docker network rm`) возможно только если к ней **не подключены контейнеры**. Принудительное отключение: `docker network disconnect -f <network> <container>`.

### Ограничения режима

- **Дефолтный bridge**: Разрешение имён по именам контейнеров **не работает**. Используйте пользовательские bridge-сети для service discovery.
- **DNS**: В дефолтном `bridge` контейнеры используют DNS-серверы хоста, а не встроенный `127.0.0.11`. Для автоматического разрешения имён контейнеров необходима пользовательская сеть.
- **Port Mapping**: Параметры `-p` и `-P` работают только для опубликованных портов. Внутренние порты не опубликованы по умолчанию (v28+).
- **Имена сетей**: Имя сети может содержать только буквы (a-z, A-Z), цифры (0-9), знаки подчёркивания (`_`), точки (`.`) и дефисы (`-`). Имена чувствительны к регистру. Длина имени: от 1 до 63 символов.

### Конфликты и пересечения

- Docker проверяет пересечение подсетей **только внутри своего демона**. Он не знает о внешних маршрутах хоста, существующих VLAN или маршрутах, добавленных вручную. Это может привести к потере связи при совпадении CIDR с корпоративной сетью.
- При использовании `--config-from` убедитесь, что целевая сеть существует и имеет тип `config-only`. Попытка использовать обычную сеть как источник конфигурации приведёт к ошибке.

### Edge cases

- **ICC и DNS**: При отключении ICC (`enable_icc=false`) контейнеры не могут резолвить имена через внутренний DNS Docker (`127.0.0.11`), так как DNS использует неопубликованный UDP-порт 53. Решение: опубликуйте DNS-сервер или используйте внешний DNS.
- **--internal и DNS**: В `--internal` сети внешние DNS-серверы недоступны, но внутренний DNS Docker (`127.0.0.11`) работает автоматически.
- **Порты < 1024**: Публикация портов ниже 1024 не требует специальных прав в Docker — NAT выполняется на уровне хоста. Однако, если контейнер сам пытается привязаться к привилегированному порту, требуется `--cap-add NET_BIND_SERVICE`.
- **Docker Desktop (Windows/macOS)**: Режим `--network bridge` работает через виртуализацию. Контейнеры изолированы от хоста дополнительным слоем VM. MTU может отличаться от физического интерфейса хоста.
- **Rootless Docker**: сетевой стек реализуется в userspace через драйвер RootlessKit. С 29.5 дефолтом является `gvisor-tap-vsock`; официальная таблица throughput относит его и `slirp4netns`/`pasta` к **низкой** пропускной способности сети при высокой пропускной способности портов. Значения и порядок выбора — в разделе «[Rootless: сетевой стек](../docker_network.md#rootless-сетевой-стек)».

## Дополнительная информация

### Производительность и MTU

Несоответствие MTU между мостом Docker и физическим интерфейсом хоста — частая причина "зависающих" SSH-сессий или медленной загрузки файлов.
- **Стандарт Docker**: 1500.
- **Рекомендация**: При использовании инкапсуляции (VPN, VXLAN) уменьшайте MTU с учётом overhead (обычно 1450).

### Анализ интерфейсов (ip link)

Утилита `brctl` устарела. В 2026 году используйте `iproute2`.

```bash
# Просмотр интерфейсов конкретного моста
ip link show master br-$(docker network inspect my-net -f '{{.Id}}' | cut -c 1-12)

# Просмотр всех bridge-интерфейсов
ip link show type bridge
```

### Сравнение с другими драйверами

| Характеристика | Bridge | Host | Overlay | Macvlan |
| :--- | :--- | :--- | :--- | :--- |
| **Изоляция** | Средняя | Нет | Высокая | Высокая (L2) |
| **NAT** | Да | Нет | Да (VXLAN) | Нет |
| **DNS** | Да (User-defined) | Нет | Да | Нет |
| **Сценарий** | Одиночный хост | High Load | Кластер | Legacy сети |

### Связь с другими компонентами

- **iptables/nftables**: Docker автоматически управляет правилами фильтрации и NAT. Для кастомных правил используйте цепочку `DOCKER-USER` (iptables) или пользовательские таблицы (nftables). Детали: [Сетевые политики Docker](../docker_network_policies.md), [Интеграция с iptables](../troubleshooting/iptables_integration.md).
- **DNS**: Встроенный DNS-сервер (`127.0.0.11`) обеспечивает service discovery по именам контейнеров. Детали: [DNS и Service Discovery](../dns_and_service_discovery.md).
- **Swarm**: Для кластерного режима используется overlay-сети и Routing Mesh. Детали: [Docker Swarm: Сетевое взаимодействие](../../../Docker_swarm/swarm_networking.md).
- **Конфигурация демона**: Глобальные параметры (`icc`, `userland-proxy`, `firewall-backend`) задаются в `daemon.json`. Детали: [Настройка демона Docker](../../../Docker/docker_daemon_config.md).
