# Сетевой драйвер bridge

## Определения

- **Bridge (`--network bridge`)** — сетевой драйвер Docker, реализующий программный мост (коммутатор) на хосте. Позволяет контейнерам в одной сети общаться между собой и с внешним миром через NAT.
- **veth-пара (Virtual Ethernet)** — пара виртуальных сетевых интерфейсов, работающих как "труба": пакет, вошедший в один конец, мгновенно выходит из другого. Используется для связи Network Namespace контейнера с мостом на хосте.
- **NAT (Network Address Translation)** — механизм преобразования IP-адресов. В Docker используется для предоставления контейнерам доступа в интернет через IP-адрес хоста и для публикации портов.

## Основные концепции

Драйвер `bridge` является стандартом для запуска одиночных контейнеров. Он обеспечивает баланс между изоляцией и удобством настройки.

### Архитектура и принцип работы

При запуске Docker создает виртуальный мост (по умолчанию `docker0`). Процесс подключения контейнера выглядит следующим образом:
1. Создается **veth-пара**.
2. Один конец (`eth0`) помещается внутрь Network Namespace контейнера.
3. Второй конец (называется `vethXXXX`) остается на хосте и подключается к мосту.
4. Контейнер получает IP-адрес из подсети моста (например, `172.17.0.0/16`).

**Почему используется мост, а не прямая маршрутизация?**
Использование моста позволяет контейнерам общаться на уровне L2 (Ethernet) через MAC-адреса. Это избавляет хост от необходимости управлять десятками маршрутов в таблице маршрутизации L3, что повышает масштабируемость и исключает конфликты при использовании одинаковых подсетей в разных сетях Docker.

### Эволюция и безопасность (Состояние на 2026 год)

Начиная с версий Docker Engine **v27** и **v28**, работа драйвера `bridge` значительно изменилась:

1. **Secure by Default (v28+)**: Теперь Docker по умолчанию блокирует (DROP) входящий трафик к IP-адресам контейнеров из локальной сети (LAN), если порты не были явно опубликованы через `-p`. Это закрывает старую проблему безопасности, когда внутренние сервисы могли быть доступны соседям по дата-центру.
2. **Переход на nftables**: Docker постепенно отказывается от legacy-команд `iptables` в пользу нативного **nftables**. Правила фильтрации стали более компактными и производительными.
3. **IPv6 Routed Mode (v27+)**: Появилась возможность использовать параметр `com.docker.network.bridge.gateway_mode_ipv6=routed`. Это позволяет контейнерам получать публичные IPv6-адреса и работать без NAT66, обеспечивая прямую маршрутизацию трафика (при поддержке провайдером).

### Типы мостов

- **Дефолтный (`bridge`)**: Создается автоматически. **Минусы**: нет встроенного DNS (связь только по IP), все контейнеры по умолчанию попадают в одну сеть, что снижает изоляцию.
- **Пользовательский (`user-defined bridge`)**: Создается вручную. **Плюсы**: автоматический DNS-сервер (обращение по именам), лучшая изоляция (контейнеры в разных сетях не видят друг друга), возможность "горячего" подключения/отключения контейнеров.

## Практические сценарии

### Сценарий 1: Создание пользовательской сети и проверка DNS

```bash
# 1. Создание сети
docker network create my-secure-net

# 2. Запуск сервера базы данных
docker run -d --name db-server --network my-secure-net redis:alpine
# → Контейнер db-server запущен и доступен по имени внутри сети

# 3. Обращение к серверу из другого контейнера
docker run --rm --network my-secure-net alpine ping -c 2 db-server
# → PING db-server (172.18.0.2): 56 data bytes
# → 64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.082 ms
```

### Сценарий 2: Анализ сетевых интерфейсов (ip link)

Утилита `brctl` считается устаревшей, в 2026 году рекомендуется использовать `ip link` и `ip addr`.

```bash
# Поиск моста, соответствующего сети
ip link show type bridge
# → 4: br-a1b2c3d4e5f6: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...

# Просмотр интерфейсов, подключенных к мосту
ip link show master br-a1b2c3d4e5f6
# → 12: veth789abc@if11: <BROADCAST,MULTICAST,UP,LOWER_UP> master br-a1b2c3d4e5f6 ...
```

### Сценарий 3: Публикация портов (NAT)

```bash
docker run -d -p 8080:80 --name web-nginx nginx:alpine
# → Порт 8080 хоста проброшен на порт 80 контейнера через DNAT и docker-proxy
```

## Дополнительная информация

### Производительность и docker-proxy

Трафик к опубликованным портам обрабатывается двумя механизмами:
1. **Ядро (DNAT)**: Основная часть трафика перенаправляется на уровне ядра через правила `nftables/iptables`.
2. **Userspace (`docker-proxy`)**: Используется как запасной вариант для трафика, который ядро не может обработать корректно (например, обращения с самого хоста к `localhost:8080`).

**Критическая заметка**: В высоконагруженных системах `docker-proxy` может стать узким местом. При миллионах соединений рекомендуется рассмотреть драйверы [`host`](./host.md) или [`macvlan`](./macvlan.md).

### IPv6 в bridge-сетях

В 2026 году для включения IPv6 в bridge-сети достаточно одной опции:
```bash
docker network create --ipv6 --subnet fd00::/64 my-ipv6-net
```
При использовании `Routed Mode` контейнеры становятся полноправными участниками IPv6-сети без накладных расходов на NAT, что является стандартом для современных микросервисных архитектур.
