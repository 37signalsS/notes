# Сетевой драйвер bridge

## Определения

**Bridge** — сетевой драйвер Docker, работающий по принципу сетевого моста. Он создает изолированную внутреннюю сеть на хосте, позволяя контейнерам взаимодействовать друг с другом и с внешним миром через NAT (Network Address Translation). Это драйвер по умолчанию для одиночных контейнеров.

## Основные концепции

### Принцип работы

При запуске Docker создает на хосте виртуальный сетевой мост (по умолчанию `docker0`), который функционирует как коммутатор и шлюз для контейнеров. Каждому контейнеру, подключенному к этой сети, назначается IP-адрес (Internet Protocol) из внутренней подсети.

Для каждого контейнера создается пара виртуальных Ethernet-интерфейсов (`veth`):

- Один конец (`eth0`) помещается в сетевое пространство имен контейнера.
- Другой конец подключается к мосту `docker0` (или другому мосту в случае пользовательской сети).

Эти `veth`-пары действуют как виртуальные "патч-корды", соединяя контейнер с мостом и обеспечивая сетевую связность.

### Почему bridge, а не отдельные veth-пары

При использовании только veth-пар без bridge для нескольких контейнеров в одной подсети возникает **конфликт маршрутов**:

```bash
# Контейнер 1: маршрут 172.18.0.0/16 dev veth0
# Контейнер 2: маршрут 172.18.0.0/16 dev veth1
```

Оба маршрута указывают на одну сеть — первый маршрут перехватывает весь трафик, нарушая связность со вторым контейнером.

**Bridge решает проблему:**

- Работает на уровне L2 (Layer 2 — Ethernet), а не L3 (Layer 3 — IP)
- Контейнеры общаются напрямую через MAC-адреса (Media Access Control)
- В таблице маршрутизации хоста присутствует один маршрут: `172.18.0.0/16 dev br0`
- Технология масштабируется на десятки контейнеров без конфликтов

### Виды bridge-сетей

1. **Сеть по умолчанию (`bridge`)**: Создается автоматически. В этой сети **разрешение имен контейнеров по DNS (Domain Name System) не работает**, и взаимодействие возможно только по IP-адресам.
2. **Пользовательские сети (`user-defined bridge`)**: Создаются вручную командой `docker network create`. **Это рекомендуемый подход**. Они предоставляют [встроенный DNS-сервер](../dns_and_service_discovery.md) для разрешения имен контейнеров и лучшую изоляцию.

### Связь и доступ

- **Внутренняя связь**: Контейнеры в одной **пользовательской** bridge-сети могут обращаться друг к другу по именам. В сети по умолчанию — только по IP-адресам.
- **Доступ извне**: Для предоставления доступа к сервису извне требуется явный проброс портов с хоста в контейнер (`-p ХОСТ:КОНТЕЙНЕР` или `-P`).

## Практические сценарии

### Создание и использование пользовательской сети

1. **Создание сети:**

    ```bash
    docker network create my-bridge-net
    ```

2. **Запуск контейнера-сервера:**
    Запустим `nginx` и назовем его `web-server`.

    ```bash
    docker run -d --name web-server --network my-bridge-net nginx:alpine
    ```

3. **Обращение к серверу по имени из другого контейнера:**
    Из временного контейнера `alpine` в той же сети проверим связь с `web-server` по имени.

    ```bash
    docker run --rm --network my-bridge-net alpine ping -c 4 web-server
    # → PING web-server (172.18.0.2): 56 data bytes
    # → 64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.045 ms
    ```

### Анализ bridge-сетей с помощью brctl

Для детального анализа сетевых мостов на хосте используется утилита `brctl`.

1. **Установка (для Debian/Ubuntu):**

    ```bash
    sudo apt-get update && sudo apt-get install -y bridge-utils
    ```

2. **Просмотр активных мостов:**
    Команда `brctl show` отображает все мосты и подключенные к ним интерфейсы.

    ```bash
    brctl show
    # → bridge name     bridge id               STP enabled     interfaces
    # → docker0         8000.0242ac110002       no              vethXXXXXX
    # → br-a1b2c3d4e5f6  8000.0242ab120001       no              vethYYYYYY
    ```

    - `bridge name`: Имя моста (`docker0` для сети по умолчанию, `br-<id>` для пользовательских).
    - `interfaces`: Список `veth`-интерфейсов подключенных контейнеров.
    - `STP enabled`: Статус протокола STP (Spanning Tree Protocol) для предотвращения петель.

## Дополнительная информация

### Производительность и docker-proxy

Проброс портов в режиме `bridge` осуществляется через прокси-процесс в пространстве пользователя (userspace) — **`docker-proxy`**.

**Как это работает:**

1. Когда вы запускаете контейнер с `-p 8080:80`, Docker запускает отдельный процесс `docker-proxy`.
2. Этот процесс слушает порт `8080` на хосте и пересылает трафик на порт `80` внутри контейнера.
3. Помимо проксирования, Docker создает цепочки правил в сетевом фильтре.

**Проблемы производительности:**

- `docker-proxy` может создавать значительные накладные расходы для приложений с высокой частотой коротких запросов (QPS).
- В высоконагруженных сценариях падение производительности может достигать **20-50%** из-за переключения контекста между пространством пользователя и ядром.
- Использование `bridge` подразумевает прохождение трафика через мост и NAT, что также добавляет задержки.

**Сетевой фильтр (iptables vs nftables):**
Docker управляет правилами через классические команды `iptables`. В современных системах (например, Ubuntu 24.04+) эти правила транслируются в **nftables** через слой совместимости `iptables-nft`. При отладке важно помнить, что команды `iptables -L` могут не показывать все нюансы, и для полной картины стоит использовать `nft list ruleset`.

Для критичных к сетевым задержкам приложений рекомендуется использовать режимы [`host`](./host.md) или [`macvlan`](./macvlan.md).

### Ограничения

- В сети `bridge` по умолчанию отсутствует встроенный механизм разрешения имен через DNS.
- Производительность ниже по сравнению с режимом `host` из-за использования NAT и `docker-proxy`.
