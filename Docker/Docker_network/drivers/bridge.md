# Сетевой драйвер bridge

## Определения

- **Bridge (`--network bridge`)** — сетевой драйвер Docker, реализующий программный мост (коммутатор) на хосте. Позволяет контейнерам в одной сети общаться между собой и с внешним миром через NAT.
- **veth-пара (Virtual Ethernet)** — пара виртуальных сетевых интерфейсов, работающих как "труба": пакет, вошедший в один конец, мгновенно выходит из другого. Используется для связи Network Namespace контейнера с мостом на хосте.
- **NAT (Network Address Translation)** — механизм преобразования IP-адресов. В Docker используется для предоставления контейнерам доступа в интернет через IP-адрес хоста и для публикации портов.

## Основные концепции

Драйвер `bridge` является стандартом для запуска одиночных контейнеров и небольших приложений. Он обеспечивает баланс между изоляцией и удобством настройки.

### Архитектура и принцип работы

При запуске Docker создает виртуальный мост (по умолчанию `docker0`). Процесс подключения контейнера выглядит следующим образом:
1. Создается **veth-пара**.
2. Один конец (`eth0`) помещается внутрь Network Namespace контейнера.
3. Второй конец (называется `vethXXXX`) остается на хосте и подключается к мосту.
4. Контейнер получает IP-адрес из подсети моста (например, `172.17.0.0/16`).

**Почему используется мост, а не прямая маршрутизация?**
Использование моста позволяет контейнерам общаться на уровне L2 (Ethernet) через MAC-адреса. Это избавляет хост от необходимости управлять десятками маршрутов в таблице маршрутизации L3, что повышает масштабируемость и исключает конфликты при использовании одинаковых подсетей в разных сетях Docker.

### Жизненный цикл пакета (Packet Flow)

Ниже описан детальный путь пакета при обращении к опубликованному порту контейнера (Port Publishing) на примере взаимодействия клиента и Nginx.

#### Сценарий: Запрос клиента к сервису Nginx
- **Хост**: `eth0` (192.168.1.10), `lo` (127.0.0.1), `docker0` (172.18.0.1).
- **Контейнер Nginx**: IP `172.18.0.10`, внутренний порт `3000`, опубликован как `8080`.

**Путь "Туда" (Запрос клиента → Nginx):**
1.  **Вход на хост**: Пакет приходит на интерфейс `lo` (127.0.0.1:8080) или `eth0` (192.168.1.10:8080).
2.  **DNAT в iptables**: В таблице `nat` (цепочка `PREROUTING`) происходит трансляция назначения: `Destination IP:Port` меняется с внешнего IP хоста на внутренний IP контейнера — `172.18.0.10:3000`.
3.  **Мост `docker0`**: Пакет направляется в виртуальный мост `docker0` (L2-коммутатор).
4.  **Интерфейс `veth`**: Мост пересылает пакет в соответствующий внешний конец veth-пары (`veth0` на хосте).
5.  **Переход в контейнер**: Через veth-пару пакет мгновенно оказывается на интерфейсе `eth0` внутри Network Namespace контейнера.
6.  **Обработка**: Пакет достигает процесса `nginx`, слушающего порт `3000`.

**Путь "Обратно" (Ответ Nginx → Клиент):**
7.  **Ответ сервиса**: Nginx формирует ответ и отправляет его через свой `eth0`.
8.  **Переход на хост**: Пакет проходит через veth-пару обратно в пространство имен хоста.
9.  **Мост `docker0`**: Пакет проходит через мост.
10. **SNAT в iptables**: В таблице `nat` (цепочка `POSTROUTING`) происходит обратная трансляция: адрес источника (`Source IP`) меняется с внутреннего IP контейнера на внешний IP хоста с сохранением опубликованного порта (`192.168.1.10:8080`).
11. **Выход с хоста**: Пакет уходит через `eth0` (внешний интерфейс).
12. **Получение**: Клиент (`curl`) получает ответ.

### Эволюция и безопасность (Состояние на 2026 год)

Начиная с версий Docker Engine **v27** и **v28**, работа драйвера `bridge` значительно изменилась:

1. **Secure by Default (v28+)**: Теперь Docker по умолчанию блокирует (DROP) входящий трафик к IP-адресам контейнеров из локальной сети (LAN), если порты не были явно опубликованы через `-p`. Это закрывает старую проблему безопасности, когда внутренние сервисы могли быть доступны соседям по дата-центру.
2. **Переход на nftables**: Docker полностью перешел на нативный **nftables**. Правила фильтрации (`DOCKER-USER`, `DOCKER-ISOLATION-STAGE-1`) стали более эффективными, снижая нагрузку на CPU при большом количестве правил.
3. **IPv6 Routed Mode (v27+)**: Параметр `com.docker.network.bridge.gateway_mode_ipv6=routed` позволяет контейнерам получать публичные IPv6-адреса и работать без NAT66, обеспечивая прямую маршрутизацию трафика.

### Типы мостов

- **Дефолтный (`bridge`)**: Создается автоматически. **Минусы**: нет встроенного DNS (связь только по IP), все контейнеры по умолчанию попадают в одну сеть.
- **Пользовательский (`user-defined bridge`)**: Создается вручную. **Плюсы**: автоматический DNS-сервер (обращение по именам), лучшая изоляция, возможность "горячего" подключения.

## Практические сценарии

### Сценарий 1: Создание сети с расширенными настройками (MTU и IPAM)

В облачных средах часто требуется ограничить MTU или задать фиксированный диапазон IP.

```bash
docker network create \
  --driver bridge \
  --subnet 10.10.0.0/24 \
  --gateway 10.10.0.1 \
  --opt com.docker.network.driver.mtu=1450 \
  my-custom-net
# → Создана сеть с MTU 1450 и кастомной подсетью
```

### Сценарий 2: Изолированная внутренняя сеть (--internal)

Используется для баз данных, которым запрещен любой выход в интернет.

```bash
docker network create --internal private-db-net
docker run -d --name secure-db --network private-db-net mariadb:latest
# → Контейнер может общаться с другими в этой сети, но доступ к 8.8.8.8 закрыт
```

### Сценарий 3: Статический IP для контейнера

```bash
docker run -d \
  --name static-web \
  --network my-custom-net \
  --ip 10.10.0.50 \
  nginx:alpine
# → Контейнер всегда будет получать адрес 10.10.0.50
```

### Сценарий 4: Управление связностью (ICC)

По умолчанию контейнеры в одной сети могут общаться (`--icc=true`). Для максимальной безопасности это можно отключить на уровне драйвера.

```bash
docker network create -o "com.docker.network.bridge.enable_icc=false" isolated-bridge
# → Контейнеры в этой сети не могут пинговать друг друга напрямую
```

## Дополнительная информация

### Производительность и MTU

Несоответствие MTU (Maximum Transmission Unit) между мостом Docker и физическим интерфейсом хоста — частая причина "зависающих" SSH-сессий или медленной загрузки файлов.
- Стандарт Docker: 1500.
- Облака (GCP/AWS/Azure): Часто требуют 1460 или 1450 из-за заголовков инкапсуляции.

### Анализ интерфейсов (ip link)

Утилита `brctl` устарела. В 2026 году используйте `iproute2`.

```bash
# Просмотр интерфейсов конкретного моста
ip link show master br-$(docker network inspect my-net -f '{{.Id}}' | cut -c 1-12)
```

### Сравнение с другими драйверами

| Характеристика | Bridge | Host | Overlay | Macvlan |
| :--- | :--- | :--- | :--- | :--- |
| **Изоляция** | Средняя | Нет | Высокая | Высокая (L2) |
| **NAT** | Да | Нет | Да (VXLAN) | Нет |
| **DNS** | Да (User-defined) | Нет | Да | Нет |
| **Сценарий** | Одиночный хост | High Load | Кластер | Legacy сети |
