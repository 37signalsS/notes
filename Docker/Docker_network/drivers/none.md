# Сетевой драйвер none

**Актуально для:** Docker Engine 29.x

## Определения

- **Драйвер none (`--network none`)** — сетевая модель Docker, при которой контейнер получает изолированный сетевой стек (Network Namespace), но лишается всех внешних сетевых интерфейсов.
- **Air-Gapped Isolation (Физическая изоляция)** — концепция безопасности, при которой информационная система не имеет соединений с внешними сетями (интернетом или локальной сетью) для предотвращения утечек данных.
- **VSOCK (`AF_VSOCK`)** — семейство адресов в ядре Linux, обеспечивающее коммуникацию между гостевой средой и хостом минуя сетевой стек TCP/IP. Используется в аппаратных анклавах и доверенных средах выполнения.
- **Default Gateway (Шлюз по умолчанию)** — IP-адрес маршрутизатора, через который трафик отправляется за пределы локальной подсети. В режиме `none` шлюз по умолчанию отсутствует.
- **Network Stack (Сетевой стек)** — совокупность компонентов ядра ОС, отвечающих за сетевую коммуникацию (интерфейсы, маршрутизация, транспортные протоколы). В режиме `none` стек присутствует, но без внешних интерфейсов.

## Основные концепции

### Архитектура и принцип работы

Драйвер `none` обеспечивает максимальный уровень сетевой изоляции, доступный в Docker. В отличие от других драйверов, он не создает `veth`-пару и не подключает контейнер к программному мосту (bridge).

**Что происходит при запуске:**
1. Docker создаёт для контейнера отдельный Network Namespace.
2. Внутри namespace создаётся только интерфейс `lo` (loopback) в состоянии `UP`.
3. Интерфейс `eth0` и другие внешние интерфейсы не создаются.
4. Таблица маршрутизации остаётся пустой: шлюз по умолчанию отсутствует.
5. DNS-сервер Docker (`127.0.0.11`) недоступен, `/etc/hosts` содержит только запись `localhost`.

**Результат:**
- Процессы внутри контейнера могут взаимодействовать только через локальные сокеты (`127.0.0.1`).
- Любой входящий или исходящий трафик через TCP/IP невозможен.
- Контейнер не видит интерфейсы хоста и другие контейнеры.

### Механизм изоляции

| Компонент | Bridge | None |
| :--- | :--- | :--- |
| Network Namespace | Отдельный | Отдельный |
| veth-пара | Да | Нет |
| Docker bridge (`docker0`) | Да | Нет |
| Внешние интерфейсы (`eth0`) | Да (виртуальный) | Нет |
| Loopback (`lo`) | Да | Да |
| Default Gateway | Да | Нет |
| DNS (`127.0.0.11`) | Да | Нет |

### Применение и технологии

1. **Генерация ключей и сертификатов**: Выполнение криптографических операций (CA, PKI) в изолированной среде гарантирует, что приватные ключи не покидают контейнер.
2. **Обработка конфиденциальных данных (PII)**: Задачи по маскированию, токенизации или хэшированию данных, где контейнер читает входные данные из тома и записывает результат обратно, без сетевого доступа.
3. **Защита от Supply Chain атак**: Обязательный запуск инструментов сборки (compilers, linters) в CI/CD без доступа к сети гарантирует, что вредоносный код в зависимостях не сможет отправить секреты на удалённые серверы.
4. **Офлайн-валидация артефактов**: Проверка контрольных сумм, подписьrelease-ов, верификация образов в air-gapped средах.
5. **Аппаратные анклавы и VSOCK**: В средах с аппаратной изоляцией (Intel TDX, AMD SEV-SNP, KVM/QEMU с VSOCK) режим `none` является стандартом для контейнеров внутри доверенной среды. Связь с хостом осуществляется через `AF_VSOCK`, минуя сетевой стек TCP/IP.

### Взаимодействие с другими сетями

- **Подключение после запуска**: Контейнер с `--network none` может быть подключён к другим сетям через `docker network connect <network> <container>`. После подключения контейнер получает обычный сетевой доступ через указанную сеть.
- **Отключение**: `docker network disconnect` работает как для других драйверов. Драйвер `none` не имеет специального поведения при отключении.
- **Ограничение**: Контейнер с `--network none` не может одновременно находиться в нескольких сетях при запуске; дополнительные сети подключаются явно после старта.

## Практические сценарии

### Сценарий 1: Проверка изоляции и loopback

Запуск контейнера для выполнения локальных вычислений без риска утечки.

```bash
docker run -d --name secure-calc --network none alpine sleep 3600
# → Контейнер запущен в полностью изолированном пространстве
```

Валидация:
```bash
# Проверка интерфейсов
docker exec secure-calc ip addr
# → 1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN qlen 1000
# →     inet 127.0.0.1/8 scope host lo
# → Другие интерфейсы (eth0) отсутствуют

# Проверка таблицы маршрутизации
docker exec secure-calc ip route
# → (пустой вывод)

# Проверка исходящего трафика (должен таймаутить)
docker exec secure-calc wget -T 2 -qO- http://example.com || true
# → таймаут или ошибка соединения

# Проверка loopback (должен работать)
docker exec secure-calc sh -c "echo test | nc -l -p 8080 &"
docker exec secure-calc sh -c "sleep 1 && echo hello | nc 127.0.0.1 8080"
# → hello
```

Очистка:
```bash
docker stop secure-calc && docker rm secure-calc
```

### Сценарий 2: Обработка конфиденциальных данных (PII)

Контейнер читает данные из тома, обрабатывает их и записывает результат, без сетевого доступа.

```bash
# 1. Создание тома с входными данными
docker volume create pii-input

# 2. Запись тестовых данных (на хосте)
echo '{"ssn":"***-**-****","name":"test"}' > /tmp/pii_sample.json
sudo cp /tmp/pii_sample.json /var/lib/docker/volumes/pii-input/_data/

# 3. Создание тома для результатов
docker volume create pii-output

# 4. Запуск контейнера с none
docker run -d \
  --name pii-processor \
  --network none \
  -v pii-input:/input:ro \
  -v pii-output:/output \
  my-secure-app:latest \
  /app/process.sh
# → Контейнер запущен без сетевого доступа
```

Валидация:
```bash
# Проверка, что контейнер не имеет сетевых интерфейсов
docker exec pii-processor ip addr show
# → Только lo

# Проверка результата обработки
docker exec pii-processor ls -la /output
# → Обработанные файлы в /output

# На хосте: проверка результата
cat /var/lib/docker/volumes/pii-output/_data/result.json
# → {"masked_ssn":"***-****","status":"ok"}
```

Очистка:
```bash
docker stop pii-processor && docker rm pii-processor
docker volume rm pii-input pii-output
```

### Сценарий 3: Защита от Supply Chain атак в CI/CD

Запуск сборки артефактов без доступа к сети гарантирует, что вредоносные зависимости не смогут эксфильтрировать данные.

```bash
# 1. Создание volume для кэша сборки (опционально)
docker volume create build-cache

# 2. Запуск контейнера сборки без сети
docker run --rm \
  --name secure-builder \
  --network none \
  -v "$PWD":/src \
  -v build-cache:/cache \
  -w /src \
  golang:1.24-alpine \
  sh -c "go build -mod=readonly -o /src/output ./..."
# → Сборка завершена, сетевой доступ отсутствовал
```

Валидация:
```bash
# Проверка артефакта
ls -la ./output
# → -rwxr-xr-x 1 root root 12345678 Sep 1 12:00 output

# Проверка, что контейнер не имел сетевого доступа
docker inspect secure-builder --format '{{.HostConfig.NetworkMode}}'
# → none
```

### Сценарий 4: Ручная инъекция сетевого интерфейса

Используется для создания кастомных топологий или отладки, когда стандартные механизмы Docker недостаточны.

```bash
# 1. Запуск контейнера с none
docker run -d --name custom-net-app --network none alpine sleep 3600

# 2. Создание veth-пары на хосте (требуются права root)
sudo ip link add veth-h type veth peer name veth-c

# 3. Перенос конца veth в сетевое пространство имен контейнера
PID=$(docker inspect -f '{{.State.Pid}}' custom-net-app)
sudo ip link set veth-c netns $PID

# 4. Настройка интерфейса внутри контейнера
docker exec -u 0 custom-net-app ip link set veth-c up
docker exec -u 0 custom-net-app ip addr add 10.0.0.2/24 dev veth-c
# → Контейнер получил интерфейс, созданный вручную, который Docker не видит
```

Валидация:
```bash
# Проверка интерфейса внутри контейнера
docker exec custom-net-app ip addr show veth-c
# → 3: veth-c: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP
# →     inet 10.0.0.2/24 scope global veth-c

# Проверка доступности хоста через ручной интерфейс
docker exec custom-net-app ping -c 1 10.0.0.1
# → 1 packets transmitted, 1 received
```

Очистка:
```bash
# Удаление интерфейса на хосте
sudo ip link del veth-h
docker stop custom-net-app && docker rm custom-net-app
```

### Сценарий 5: Локальная обработка данных с sidecar-логированием

Контейнер с `--network none` выполняет вычисления и записывает логи в том. Sidecar-контейнер с сетевым доступом монтирует тот же том и отправляет логи в систему мониторинга.

```yaml
services:
  worker:
    image: my-secure-worker:latest
    network_mode: none
    volumes:
      - worker-data:/data
      - worker-logs:/logs

  log-shipper:
    image: fluent/fluent-bit:latest
    volumes:
      - worker-logs:/logs:ro
    networks:
      - monitoring
```

Валидация:
```bash
docker compose up -d
# → worker запущен без сетевого доступа
# → log-shipper запущен с доступом к сети monitoring

docker compose ps
# → worker   running   none network
# → log-shipper   running   monitoring

# Проверка логов
docker exec <log-shipper-container> ls -la /logs
# → Файлы логов от worker
```

## Устранение неисправностей

### Типичные ошибки

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `network host not supported` | Docker Desktop без включенной опции | Включите `Enable host networking` в Settings → Resources → Network. Отключите ECI |
| `Cannot connect to localhost` | Контейнер не имеет сетевого доступа | Это ожидаемое поведение. Используйте `docker network connect` для подключения к сети |
| `Name or service not known` | DNS недоступен | В режиме `none` DNS отключён. Используйте IP-адреса после подключения к сети, или настройте `/etc/hosts` вручную |
| `wget/curl: couldn't connect to host` | Отсутствие сетевого доступа | Ожидаемое поведение. Подключите контейнер к сети через `docker network connect` |
| `network-scoped alias ... does not match the current network` | Алиас указан для другой сети | Укажите `--alias` только для целевой сети при `docker network connect` |

### Диагностика

- **Проверка режима сети**: `docker inspect -f '{{.HostConfig.NetworkMode}}' <container>` → должно быть `none`.
- **Проверка интерфейсов**: `docker exec <container> ip addr show` → только `lo`.
- **Проверка таблицы маршрутизации**: `docker exec <container> ip route` → пустой вывод.
- **Проверка DNS**: `docker exec <container> cat /etc/resolv.conf` → отсутствует или содержит только локальные записи.
- **Проверка доступности**: `docker exec <container> ping -c 1 127.0.0.1` → работает; `ping -c 1 <внешний_IP>` → таймаут.
- **Логи демона**: `/var/log/docker.log` или `journalctl -u docker` для ошибок инициализации сети.

## Рекомендации

### Безопасность

- **Изоляция**: Режим `none` обеспечивает максимальную изоляцию. Используйте для контейнеров, обрабатывающих конфиденциальные данные (PII, ключи, сертификаты).
- **Доступ к loopback**: Контейнер может обращаться к `127.0.0.1`. Это безопасно, так как loopback изолирован внутри namespace контейнера.
- **Volumes для данных**: Используйте тома для обмена данными с sidecar-контейнерами. Никогда не храните конфиденциальные данные в writable layer.
- **Файервол**: Docker не управляет `iptables/nftables` для режима `none`. Вся ответственность за фильтрацию ложится на системного администратора.
- **Уровень привилегий**: Даже в режиме `none` контейнер может быть запущен с дополнительными capabilities. Используйте `--cap-drop ALL` для минимальных привилегий.

### Производительность

- **Zero Overhead**: Отсутствие veth-пары, моста и NAT eliminates overhead полностью. Режим `none` имеет минимальную задержку среди всех драйверов.
- **Для CPU-интенсивных задач**: Используйте `--network none` для batch-обработки, где сеть не требуется. Это снижает нагрузку на демон Docker.
- **Для CI/CD runners**: Отсутствие сетевого стека ускоряет создание и уничтожение контейнеров в пайплайнах.

### Управление жизненным циклом

- **Подключение к сети после запуска**: Используйте `docker network connect <network> <container>` для динамического предоставления сетевого доступа. Это позволяет запускать контейнер без сети и подключать её только при необходимости.
- **Очистка**: Удаление контейнера с `--network none` не оставляет следов в виде orphaned интерфейсов или правил iptables.
- **Volumes**: Данные в томах сохраняются после удаления контейнера. Используйте `docker volume rm` для очистки.

### Отладка

- **Используйте Go-шаблоны**: `docker inspect -f '{{.HostConfig.NetworkMode}}' <container>` для проверки режима.
- **Для захвата трафика**: В режиме `none` нет внешнего трафика для захвата. Если нужно отлаживать общение через VSOCK, используйте specialised tools (`vscp`, `nc -l` на хосте).
- **Проверяйте loopback**: `docker exec <container> nc -l -p 8080` на одном конце и `docker exec <container> nc 127.0.0.1 8080` на другом.

## Особенности и ограничения

### Драйверы и подключение

- **`none`**: Полностью отключает сеть. После запуска контейнера с `--network none` его можно подключить к другим сетям через `docker network connect`.
- **`host`**: После запуска контейнера с `--network host` команды `docker network connect/disconnect` не работают, так как контейнер уже находится в сети хоста.
- **`bridge`**: Стандартный драйвер. Поддерживает `docker network connect/disconnect` для добавления контейнера к нескольким сетям.

### Переименование и удаление

- Docker CLI **не поддерживает** команду `rename` для сетей. Для изменения имени необходимо удалить сеть (`docker network rm`) и создать новую с нужным именем.
- Удаление сети (`docker network rm`) возможно только если к ней **не подключены контейнеры**. Принудительное отключение: `docker network disconnect -f <network> <container>`.

### Ограничения режима

- **Отсутствие DNS**: Встроенный DNS-сервер Docker (`127.0.0.11`) недоступен. Разрешение имён контейнеров по имени сервиса невозможно.
- **Hostname Resolution**: Разрешение имён других контейнеров в инфраструктуре невозможно без явного подключения к сети.
- **Port Mapping**: Параметры `-p` и `-P` полностью игнорируются, так как порты не на чем пробрасывать.
- **Отсутствие внешнего доступа**: Контейнер не может ни принимать, ни инициировать входящие/исходящие TCP/UDP-соединения.
- **Имена сетей**: Имя сети может содержать только буквы (a-z, A-Z), цифры (0-9), знаки подчёркивания (`_`), точки (`.`) и дефисы (`-`). Имена чувствительны к регистру. Длина имени: от 1 до 63 символов.

### Конфликты и пересечения

- Docker проверяет пересечение подсетей **только внутри своего демона**. Он не знает о внешних маршрутах хоста, существующих VLAN или маршрутах, добавленных вручную. Это может привести к потере связи при совпадении CIDR с корпоративной сетью.

###edge cases

- **Sidecar-паттерн с `none`**: При использовании sidecar для логирования убедитесь, что sidecar имеет доступ к сети для отправки данных. Сам контейнер с `--network none` не может инициировать соединение.
- **Порты < 1024**: В режиме `none` привязка к портам хоста невозможна. Если контейнер подключается к сети через `docker network connect`, привязка к привилегированным портам требует `--cap-add NET_BIND_SERVICE`.
- **Докер-десктоп (Windows/macOS)**: Режим `--network none` работает в Docker Desktop так же, как на Linux. Однако, поскольку Docker Desktop использует виртуализацию, контейнеры изолированы от хоста дополнительным слоем VM.

## Дополнительная информация

### Связь с другими компонентами

- **Sidecar-паттерн**: Для логирования и мониторинга контейнеров с `--network none` используйте sidecar-контейнеры с доступом к сети, разделяющие тома через [Сетевой режим container](../container_network.md).
- **Обзор сетевых моделей**: Сравнение всех драйверов см. в [Обзор сетевых моделей Docker](../docker_network.md).
- **Docker Compose**: Параметр `network_mode: none` на уровне сервиса. При необходимости сетевого доступа подключайте сервис к overlay-сети или используйте `network_mode: service:<имя>` для совместного использования сети с другим контейнером.
- **Volumes**: Для обмена данными между контейнером с `--network none` и внешним миром используйте [Управление томами Docker](../../Docker_fs/docker_volumes.md).
