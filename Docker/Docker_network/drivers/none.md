# Сетевой драйвер none

## Определения

- **Драйвер none (`--network none`)** — это сетевая модель Docker, при которой контейнер получает изолированный сетевой стек (Network Namespace), но лишается всех внешних сетевых интерфейсов.
- **Air-Gapped Isolation (Физическая изоляция)** — концепция безопасности, при которой информационная система не имеет соединений с внешними сетями (интернетом или локальной сетью) для предотвращения утечек данных.

## Основные концепции

Драйвер `none` обеспечивает максимальный уровень сетевой изоляции, доступный в Docker. В отличие от других драйверов, он не создает `veth`-пару и не подключает контейнер к программному мосту (bridge).

### Механизм работы

При использовании `--network none` Docker настраивает сетевое пространство имен контейнера следующим образом:
- **Loopback (`lo`)**: Интерфейс `127.0.0.1` создается и переводится в состояние `UP`. Процессы внутри контейнера могут взаимодействовать друг с другом через локальные сокеты.
- **Отсутствие внешних интерфейсов**: Интерфейс `eth0` не создается.
- **Пустая таблица маршрутизации**: В контейнере отсутствует шлюз по умолчанию (Default Gateway), что делает невозможным любой входящий или исходящий трафик за пределы контейнера через стек TCP/IP.

### Применение и технологии

1. **Confidential Computing и VSOCK**: Режим `none` является стандартом для работы внутри аппаратных анклавов (AWS Nitro Enclaves, Intel TDX). Связь с внешним миром осуществляется через протокол **VSOCK** (`AF_VSOCK`). Это позволяет приложению обмениваться данными с хостом, минуя сетевой стек ядра Linux и избегая атак на уровне TCP/IP.
2. **Sidecar-паттерны для логирования**: В высокозащищенных средах контейнер с `--network none` записывает логи и метрики в **[именованные тома](../../Docker_fs/docker_volumes.md)**. Другой контейнер (Sidecar) с доступом к сети монтирует эти же тома и отправляет данные в систему мониторинга.
3. **Zero-Trust Batch Processing**: Выполнение критических задач (генерация сертификатов, обработка PII), где контейнер взаимодействует только с файловой системой.
4. **Защита от Supply Chain атак**: Обязательный запуск инструментов сборки (compilers, linters) в CI/CD без доступа к сети гарантирует, что вредоносный код в зависимостях не сможет отправить секреты на удаленные серверы.

## Практические сценарии

### Сценарий 1: Проверка изоляции и loopback

Запуск контейнера для выполнения локальных вычислений без риска утечки.

```bash
docker run -d --name secure-calc --network none alpine sleep 3600
# → Контейнер запущен в полностью изолированном пространстве
```

Проверка состояния интерфейсов:
```bash
docker exec secure-calc ip addr
# → 1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN qlen 1000
# →     inet 127.0.0.1/8 scope host lo
# → Другие интерфейсы (eth0) отсутствуют
```

### Сценарий 2: Использование в Docker Compose

Для активации режима в Compose используется параметр `network_mode`.

```yaml
services:
  secure-worker:
    image: my-secure-app:latest
    network_mode: none
    volumes:
      - task-data:/data
```

### Сценарий 3: Продвинутая настройка (ручная инъекция veth)

Используется для создания кастомных топологий или отладки, когда стандартные механизмы Docker недостаточны.

```bash
# 1. Запуск контейнера с none
docker run -d --name custom-net-app --network none alpine sleep 3600

# 2. Создание veth-пары на хосте (требуются права root)
sudo ip link add veth-h type veth peer name veth-c

# 3. Перенос конца veth в сетевое пространство имен контейнера
PID=$(docker inspect -f '{{.State.Pid}}' custom-net-app)
sudo ip link set veth-c netns $PID

# 4. Настройка интерфейса внутри контейнера
docker exec -u 0 custom-net-app ip link set veth-c up
docker exec -u 0 custom-net-app ip addr add 10.0.0.2/24 dev veth-c
# → Контейнер получил интерфейс, созданный вручную, который Docker не видит
```

## Дополнительная информация

### Ограничения

- **Отсутствие DNS**: Встроенный DNS-сервер Docker (`127.0.0.11`) недоступен.
- **Hostname Resolution**: Разрешение имен других контейнеров в инфраструктуре невозможно.
- **Port Mapping**: Параметры `-p` и `-P` полностью игнорируются, так как порты не на чем пробрасывать.

### Сравнение с другими драйверами

| Характеристика | None | Bridge | Host |
| :--- | :--- | :--- | :--- |
| **Изоляция сети** | Максимальная | Средняя (L2/L3) | Отсутствует |
| **Доступ в интернет** | Нет | Да (через NAT) | Да (нативный) |
| **Loopback (`lo`)** | Доступен | Доступен | Доступен (хоста) |
| **Сценарий** | Безопасность / Анклавы | Стандартные приложения | Высокая нагрузка |

### Сравнение с `--internal`
Режим `--internal` (для драйвера `bridge`) позволяет контейнерам общаться друг с другом в рамках одной сети, но блокирует выход во внешний мир (через `iptables`). Драйвер `none` гораздо радикальнее: он удаляет саму возможность сетевого общения на уровне ОС (Network Stack), оставляя только локальный интерфейс `lo`.
