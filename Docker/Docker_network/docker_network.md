# Docker: Обзор сетевых моделей

## Определения

- **Docker Networking**: Система, которая обеспечивает сетевые возможности для контейнеров, позволяя им взаимодействовать друг с другом, с хостом и с внешними сетями.
- **Container Network Model (CNM)**: Архитектурная модель, лежащая в основе Docker Networking. Она определяет три ключевых компонента:
  - **Sandbox (Песочница)**: Изолированное сетевое окружение для контейнера, включающее собственный сетевой стек (интерфейсы, таблицы маршрутизации, DNS). Как правило, реализуется через сетевое пространство имён (network namespace).
  - **Endpoint (Конечная точка)**: Виртуальный сетевой интерфейс, который соединяет "песочницу" с "сетью".
  - **Network (Сеть)**: Программный коммутатор (switch), который объединяет эндпоинты, позволяя им общаться. Реализация сети обеспечивается сетевым драйвером.
- **Сетевой драйвер (Network Driver)**: Плагин, который реализует определенный тип сети в соответствии с моделью CNM (например, `bridge`, `overlay`).

## Основные концепции

### Обзор основных сетевых драйверов

Docker предоставляет несколько встроенных драйверов для разных сценариев. Выбор драйвера определяет, как контейнеры подключаются друг к другу и к внешним сетям.

| Драйвер | Изоляция | Производительность | Основной сценарий использования |
| :--- | :--- | :--- | :--- |
| **[`bridge`](./drivers/bridge.md)** | ✅ Высокая (своя подсеть) | Хорошая (через NAT) | **Сеть по умолчанию.** Изолированные контейнеры на одном хосте, локальная разработка. |
| **[`host`](./drivers/host.md)** | ❌ Отсутствует | Максимальная | Когда нужна высокая производительность, и контейнер может использовать сетевой стек хоста напрямую (например, для мониторинга). |
| **[`overlay`](./drivers/overlay.md)** | ✅ Высокая (между хостами) | Хорошая | **Docker Swarm.** Для связи контейнеров, запущенных на разных хостах в составе кластера. |
| **[`macvlan`](./drivers/macvlan.md)**|  L2 (уровень MAC) | Высокая | Когда контейнеру нужен свой MAC-адрес, чтобы он выглядел как физическое устройство в локальной сети. |
| **[`ipvlan`](./drivers/ipvlan.md)**| L2/L3 | Высокая | Альтернатива macvlan без проблем с MAC-фильтрацией на коммутаторах. Контейнеры используют MAC хоста. |
| **[`none`](./drivers/none.md)** | ✅ Полная | N/A | Для полной сетевой изоляции или при использовании кастомных сетевых решений (например, CNI-плагинов). |

### Пользовательские сети vs. Сеть `bridge` по умолчанию

При установке Docker создает сеть `bridge`, в которую по умолчанию попадают все контейнеры. Однако **лучшей практикой является создание собственных, пользовательских `bridge`-сетей** для каждого приложения.

**Ключевые преимущества пользовательских сетей:**

1. **Автоматическое разрешение имен (DNS)**: Контейнеры в одной пользовательской сети могут обращаться друг к другу по именам. В сети `bridge` по умолчанию это не работает.
2. **Лучшая изоляция**: Контейнеры, не подключенные к одной сети, не могут взаимодействовать. В сети `bridge` по умолчанию все контейнеры потенциально могут общаться друг с другом (хотя и только по IP).
3. **Динамическое подключение/отключение**: Контейнеры можно подключать и отключать от пользовательских сетей на лету без пересоздания.

**Критичное отличие — DNS:**

| Сеть | DNS-разрешение имён | Изоляция |
| :--- | :--- | :--- |
| `bridge` (по умолчанию) | **Не работает**. Контейнеры видят друг друга только по IP. | Слабая — все контейнеры в одной сети |
| Пользовательская `bridge` | **Работает автоматически** по имени контейнера и `--network-alias` | Высокая — только подключенные контейнеры |

**Практический пример проблемы:**

```bash
# Запуск в сети по умолчанию
docker run -d --name postgres postgres:14
docker run -d --name app myapp:latest

# Контейнер app НЕ сможет подключиться к postgres по имени "postgres"
# Ошибка: "could not translate host name 'postgres' to address"
```

**Решение:** Создать пользовательскую сеть:

```bash
docker network create myapp-net
docker run -d --name postgres --network myapp-net postgres:16-alpine
docker run -d --name app --network myapp-net myapp:latest

# Теперь app может подключиться к postgres по имени "postgres"
```

Подробнее о настройке сети для БД см. **[Развертывание PostgreSQL в Docker](../../Databases/PostgreSQL/Operations/docker_deployment.md)**.

### Поддержка IPv6 в Docker

По умолчанию Docker работает в режиме IPv4-only. Для включения поддержки IPv6 необходимо настроить демон и создать сети с поддержкой IPv6.

**1. Настройка демона (`/etc/docker/daemon.json`):**

```json
{
  "ipv6": true,
  "fixed-cidr-v6": "2001:db8:abc:1::/64"
}
```

**2. Создание сети с IPv6:**

```bash
docker network create --ipv6 --subnet=2001:db8:abc:2::/64 my-ipv6-net
```

**Особенности:**

- Контейнеры получают глобально маршрутизируемые IPv6-адреса (если префикс публичный).
- Необходимо настраивать [ip6tables](../../Linux/Networking/Settings/ipv6_configuration/firewall.md) для защиты контейнеров.

## Практические сценарии

### Сценарий 1: Управление сетями (CLI)

Все основные команды управления сетями (создание, инспекция, удаление, подключение контейнеров на лету) и их параметры вынесены в отдельный справочник:
**[Управление сетями Docker: CLI-справочник](./cli.md)**.

### Сценарий 2: Преимущество DNS в пользовательской сети

1. **Запустим два контейнера в сети `bridge` по умолчанию:**

    ```bash
    docker run -d --name nginx1 nginx:alpine
    docker run -it --rm alpine sh
    
    # Внутри второго контейнера пытаемся "достучаться" до первого по имени
    / # ping nginx1
    # ping: bad address 'nginx1' -> НЕ РАБОТАЕТ
    ```

2. **Теперь создадим свою сеть и запустим контейнеры в ней:**

    ```bash
    docker network create my-test-net
    docker run -d --name nginx2 --network my-test-net nginx:alpine
    docker run -it --rm --network my-test-net alpine sh

    # Внутри второго контейнера
    / # ping nginx2
    # PING nginx2 (172.19.0.2): 56 data bytes
    # 64 bytes from 172.19.0.2: seq=0 ttl=64 time=0.082 ms -> РАБОТАЕТ!
    ```

    Это демонстрирует, что **встроенное сервис-дискавери через DNS работает только в пользовательских сетях**.

### Сценарий 3: Использование сети host

Режим `host` отключает сетевую изоляцию контейнера, позволяя ему использовать сетевой стек хоста напрямую. Это обеспечивает максимальную производительность, но снижает безопасность.

Подробное описание режима, практические примеры и ограничения платформы см. в специализированном разделе:
**[Сетевой драйвер host](./drivers/host.md)**.

### Сценарий 4: PostgreSQL в кастомной сети с изоляцией

По умолчанию контейнеры подключаются к сети `bridge` и могут общаться только по IP-адресам. В кастомной сети контейнеры резолвят друг друга по имени.

```bash
# 1. Создание кастомной сети
docker network create my-network

# 2. Запуск PostgreSQL в кастомной сети
docker run -d \
  --name pg-isolated \
  -e POSTGRES_PASSWORD=secret \
  -p 127.0.0.1:5434:5432 \
  --network my-network \
  postgres:16-alpine

# 3. Проверка подключения
docker network inspect my-network
# → Containers: pg-isolated (172.19.0.2)

# 4. Запуск второго контейнера в той же сети — DNS-резолвинг работает
docker run -it --rm --network my-network alpine sh
/ # ping pg-isolated
# → PING pg-isolated (172.19.0.2) — резолвится по имени!
```

**Ключевые различия стандартной и кастомной сети:**

| Возможность | `bridge` (по умолчанию) | Кастомная сеть |
|:------------|:------------------------|:---------------|
| DNS-резолвинг | Только по IP (флаг `--link` устарел) | По имени контейнера и `--network-alias` |
| Изоляция | Все контейнеры в одной сети | Только подключённые контейнеры |

## Дополнительная информация

### Безопасность публикации портов

**Критичная проблема:** Публикация портов (`-p <порт>:<порт>`) делает сервис доступным **во всех сетевых интерфейсах хоста**, включая внешний (публичный) интерфейс, если хост имеет выход в Интернет.

**Типичные ошибки:**

| Сервис | Порт | Риск |
| :--- | :--- | :--- |
| PostgreSQL | 5432 | Прямой доступ к БД, брутфорс паролей |
| Redis | 6379 | Доступ к кэшу, сессиям, данным |
| MongoDB | 27017 | Прямой доступ к данным, ransomware-атаки |
| Elasticsearch | 9200/9300 | Утечка данных, удаление индексов |

**Последствия:** Любое сканирование портов обнаружит эти сервисы. Если у сервиса нет аутентификации (как Redis по умолчанию) или используется слабый пароль, злоумышленник получит полный доступ к данным.

**Рекомендации по безопасности:**

1. **Не публикуйте порты без необходимости:**
   - Базы данных, кэши, внутренние сервисы **не должны** иметь опубликованные порты
   - Используйте пользовательские сети для связи между контейнерами

2. **Публикация только на localhost:**

   ```bash
   # Доступно только с хоста (127.0.0.1)
   docker run -d -p 127.0.0.1:5432:5432 postgres:16-alpine
   ```

3. **Используйте firewall хоста:**
   - Настройте `iptables` или `ufw` для ограничения доступа к опубликованным портам
   - Разрешайте доступ только с доверенных IP-адресов

4. **Пример безопасной конфигурации:**

   ```bash
   # Создаем сеть для приложения
   docker network create myapp-net

   # Запускаем БД без публикации порта (только внутри сети)
   docker run -d --name postgres \
     --network myapp-net \
     -e POSTGRES_PASSWORD=secret \
     postgres:16-alpine

   # Запускаем приложение с доступом к БД
   docker run -d --name app \
     --network myapp-net \
     -p 8080:8080 \
     myapp:latest
   ```

В этом примере:

- PostgreSQL доступен **только** из контейнера `app` по имени `postgres`
- Порт 5432 **не опубликован** наружу
- Приложение доступно извне на порту 8080

### Механизм публикации портов

Чтобы сделать сервис, работающий в `bridge`-сети, доступным извне, используется механизм публикации портов (`-p <порт_хоста>:<порт_контейнера>`), который Docker реализует с помощью правил `iptables` (DNAT).

**Как работает публикация портов:**

Docker добавляет два правила DNAT для каждого опубликованного порта:

```bash
# Для внешнего трафика (цепочка PREROUTING)
iptables -t nat -A PREROUTING -d <IP_хоста> -p tcp --dport 5000 \
  -j DNAT --to-destination 172.18.0.10:5000

# Для локального трафика (цепочка OUTPUT)
iptables -t nat -A OUTPUT -d <IP_хоста> -p tcp --dport 5000 \
  -j DNAT --to-destination 172.18.0.10:5000
```

**Почему два правила:**

- `PREROUTING` обрабатывает пакеты до маршрутизации (внешний трафик)
- `OUTPUT` обрабатывает пакеты, созданные на хосте (локальный трафик)

> **Внимание: Обход UFW/Firewall хоста**
> Поскольку Docker добавляет правила напрямую в цепочку `PREROUTING` (DNAT), эти правила отрабатывают **раньше**, чем запрещающие правила `UFW` (в цепочке `INPUT` или `FORWARD`). В результате опубликованный порт контейнера будет доступен извне, даже если в UFW по умолчанию установлен запрет на входящие соединения. Для безопасного ограничения доступа публикуйте порты только на `127.0.0.1` и проксируйте через Nginx/Traefik, либо используйте цепочку `DOCKER-USER` в `iptables` для фильтрации трафика. Подробнее см. в **[UFW — Uncomplicated Firewall](../../Linux/Networking/Settings/tools/ufw.md)**.

Также Docker включает обработку bridge-трафика: `modprobe br_netfilter`

**Выход контейнеров в Интернет:**

1. Включает IP-форвардинг: `net.ipv4.ip_forward=1` (подробнее в [sysctl](../../Linux/Core/kernel/sysctl.md))
2. Добавляет правило MASQUERADE: `iptables -t nat -A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE`

### Режимы Docker и реализация в Linux

| Режим Docker | Реализация в Linux | Описание |
| :--- | :--- | :--- |
| `bridge` (по умолчанию) | network namespace + veth + bridge | Изолированная сеть с NAT |
| `host` | Без network namespace | Стек хоста напрямую |
| `none` | network namespace без интерфейсов | Только loopback |
| **[`container:<name>`](./container_network.md)** | Разделение namespace с другим контейнером | Общий IP и localhost |
