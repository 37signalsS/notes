# Docker: обзор сетевой модели

**Актуально для:** Docker Engine 29.x

## Определения

- **Docker Networking** — подсистема Docker, обеспечивающая сетевое взаимодействие контейнеров между собой, с хостом и с внешними сетями.
- **CNM (Container Network Model)** — архитектурная модель сетевого стека Docker, состоящая из трёх сущностей:
  - **Sandbox (песочница)** — изолированное сетевое окружение контейнера: его интерфейсы, таблицы маршрутизации, `/etc/resolv.conf`. Реализуется через **network namespace** ядра Linux.
  - **Endpoint (эндпоинт)** — привязка sandbox к конкретной сети. Один эндпоинт принадлежит ровно одной сети, поэтому контейнер, подключённый к двум сетям, имеет два эндпоинта.
  - **Network (сеть)** — набор эндпоинтов, которые видят друг друга напрямую. Физически реализуется программным мостом, VXLAN-туннелем или прямой маршрутизацией — в зависимости от драйвера.
- **Драйвер сети** — плагин, реализующий логику конкретного типа сети: `bridge`, `host`, `overlay`, `macvlan`, `ipvlan`, `none` плюс сторонние плагины.
- **Gateway mode (режим шлюза)** — политика внешней связности bridge-сети, задаётся опциями `com.docker.network.bridge.gateway_mode_ipv4` / `_ipv6`. Определяет, применяется ли NAT, ставятся ли правила фильтрации портов и какой адрес используется в исходящих пакетах.
- **Опубликованный порт (published port)** — порт контейнера, проксируемый на адрес хоста через `-p` / `--publish`. Только опубликованные порты доступны извне хоста; неопубликованные блокируются.
- **Service Discovery** — разрешение имён контейнеров и сетевых алиасов через встроенный DNS-резолвер Docker на `127.0.0.11`. Работает только в пользовательских сетях.
- **Routing Mesh (маршрутная сетка)** — механизм Docker Swarm, позволяющий любому узлу кластера принимать трафик на опубликованный порт любого сервиса и направлять его к живой реплике, даже если на самом узле реплики нет.

## Архитектура сетевого стека

### Уровни абстракции

Сетевой запрос проходит четыре уровня, и на каждом из них его можно ограничить независимо:

```
внешний клиент / соседний контейнер / хост
        │
        ▼
[2] Правила файрвола и NAT          ← что вообще пропускается (безопасность)
        │
        ▼
[1] Опубликованные порты (-p)        ← как трафик попадает внутрь
        │
        ▼
[3] Endpoint контейнера (veth)       ← какой интерфейс и какого контейнера
        │
        ▼
[4] Sandbox контейнера (netns)       ← процесс, его сокеты и DNS
```

Практическое следствие: **контейнер может быть полностью изолированным и при этом доступным извне** — если его сеть создана с `gateway_mode=isolated` и `--internal`, а порт опубликован. Изоляция на уровне сети и доступность снаружи регулируются разными механизмами.

### Что Docker создаёт на хосте для пользовательской bridge-сети

Одна команда `docker network create` порождает сразу несколько объектов в разных подсистемах:

| Объект | Где живёт | Зачем |
| :--- | :--- | :--- |
| Linux-мост (`br-<ID>`) | сетевое пространство хоста | коммутатор L2 между эндпоинтами |
| Правила `iptables` / `nftables` | сетевой стек ядра | изоляция сетей, NAT, проброс портов |
| Встроенный DNS-резолвер | процесс демона, слушает `127.0.0.11` | Service Discovery внутри сети |
| Записи об именах | `/etc/hosts` контейнера | разрешение имён без DNS |
| Правила conntrack / `ipset` | ядро | учёт соединений и доступ к `routed`-сетям |

Отсюда практическое правило: **проблема в сети Docker — это проблема в одном из этих пяти мест.** Диагностика начинается с определения, какой из уровней не работает, а не с проверки приложения.

### Три независимых измерения доступа

Одна из главных причин путаницы в сетевом стеке Docker — ожидание, что «сети изолированы» означает одно и то же для всех случаев. На деле доступ контролируется тремя независимыми механизмами:

| Измерение | Механизм | Что даёт |
| :--- | :--- | :--- |
| **Видимость по имени** | встроенный DNS `127.0.0.11` | разрешение `имя-контейнера` внутри одной пользовательской сети |
| **Видимость по IP** | изоляция на мостах и правилах фильтрации | контейнеры из разных сетей не видят IP друг друга |
| **Доступ извне** | публикация порта (`-p`) | единственный легальный вход в контейнер снаружи хоста |

Эти измерения не коррелируют. Два контейнера в одной сети видят друг друга по имени **и** напрямую по всем портам, даже непубликованным: связность внутри одной bridge-сети эквивалентна «плоской сети» с полным доверием. Обратное тоже верно: опубликованный порт не делает контейнер видимым для соседей по хостовой сети — он открывает вход, а не взаимную видимость.

## Драйверы сетей

### Сравнение

| Драйвер | Уровень изоляции | Топология | Ключевое ограничение | Файл |
| :--- | :--- | :--- | :--- | :--- |
| **`bridge`** | по сети, с правилами фильтрации | один хост | не работает между хостами | [bridge](./drivers/bridge.md) |
| **`host`** | отсутствует (общий сетевой стек) | хост | конфликт портов с хостом, обход всех правил Docker | [host](./drivers/host.md) |
| **`overlay`** | по сети, VXLAN | несколько хостов | только для Swarm; требует UDP/4789 между узлами | [overlay](./drivers/overlay.md) |
| **`macvlan`** | L2, отдельный MAC | один хост, L2-сегмент | хост не видит контейнер без promiscuous-режима; не работает на Wi-Fi | [macvlan](./drivers/macvlan.md) |
| **`ipvlan`** | L3, общий MAC | один хост, высокая плотность | нельзя общаться между контейнерами на одном хосте | [ipvlan](./drivers/ipvlan.md) |
| **`none`** | полная (только loopback) | нет сети | приложение без сети не запустит сетевой код | [none](./drivers/none.md) |

### Как выбирать

1. **Один хост, контейнеры должны видеть друг друга по имени** → пользовательская `bridge`-сеть. Это вариант по умолчанию для production; дефолтная сеть `bridge` для этого не подходит (см. ниже).
2. **Нужен доступ к хостовым сервисам или к localhost хоста** → `host`, если приемлема потеря изоляции. Альтернатива — `bridge` плюс `extra_hosts` с `host-gateway`.
3. **Нужна маршрутизация на L2 без NAT и с собственными MAC** → `macvlan`. Убедитесь, что порт коммутатора разрешает promiscuous-режим, либо используйте `ipvlan L2`.
4. **Много хостов, оркестратор — Swarm** → `overlay`. Вне Swarm `overlay` не обеспечивает межхостовую связность: standalone-контейнеры на разных хостах в одной overlay-сети не увидят друг друга.
5. **Плотность выше, чем даёт macvlan** → `ipvlan`. Плата — контейнеры на одном хосте не могут общаться между собой напрямую.
6. **Сборочная задача или обработка данных без сети** → `none`.

### Сети, создаваемые автоматически

Демон создаёт три сети при старте, и они не удаляются вместе с контейнерами:

| Имя | Драйвер | Резолвер | Service Discovery |
| :--- | :--- | :--- | :--- |
| `bridge` | `bridge` | наследует `/etc/resolv.conf` хоста | нет |
| `host` | `host` | сетевой стек хоста | нет |
| `none` | `null` | отсутствует | нет |

Сеть `bridge` по умолчанию — **legacy-режим**. Она не имеет встроенного DNS: контейнеры в ней не разрешают друг друга по имени, работают только по IP, а разделять контейнеры, не задав `--network`, невозможно. Единственный механизм имен — `--link`, объявленный устаревшим: с Docker Engine 28.0 его использование в сети `bridge` выдаёт предупреждение.

```bash
docker run --link db:database alpine:3 sh
# → WARNING: Links on the default bridge network are deprecated and will be
#   removed in a future release. Use a custom network instead.
```

## Сети: область действия и жизненный цикл

### Локальные и swarm-сети

Колонка `SCOPE` в `docker network ls` показывает, где сеть существует:

- **`local`** — сеть принадлежит одному хосту, видна только ему. Все пользовательские `bridge`, `macvlan`, `ipvlan`-сети имеют этот scope.
- **`swarm`** — сеть управляется кластером и реплицируется на все узлы. Только `overlay`-сети могут иметь этот scope.

Создать swarm-сеть из локального драйвера можно, повысив scope до `swarm`, но такая сеть не обеспечивает межхостовую маршрутизацию — она существует только ради единообразия конфигурации. Для драйверов, требующих разной настройки на каждом узле (например, `macvlan` с разными подсетями), используется пара «config-only сеть + `--config-from`»:

```bash
# На каждом узле — своя локальная конфигурация
node1$ docker network create --config-only --subnet 192.168.100.0/24 mv-config
node2$ docker network create --config-only --subnet 192.168.200.0/24 mv-config
# На первом узле — рабочая swarm-сеть, копирующая конфигурацию
node1$ docker network create -d macvlan --scope swarm --config-from mv-config --attachable swarm-net
```

### Подключение контейнера к сетям

Контейнер может состоять в нескольких сетях одновременно, и это основной механизм сегментации:

```bash
# Одна сеть на этапе создания, остальные — подключением
docker run -d --name app --network frontend app:1.0
docker network connect backend app
docker network connect --ip 10.40.0.20 --alias api backend app
```

Проверенные на Docker Engine 29.8.1 свойства:

- **Подключения переживают `docker restart`.** Сети фиксируются в конфигурации контейнера, а не в его runtime-состоянии, поэтому перезапуск их не теряет. Но `docker rm` с последующим `docker run` без `--network` их теряет.
- **`docker network disconnect` работает и для сети `bridge` по умолчанию.** Документация утверждает, что для удаления из дефолтной сети контейнер нужно остановить и пересоздать. На практике команда принимается, и контейнер остаётся только с `lo` — то есть фактически переходит в состояние, эквивалентное `--network none`, при этом Docker не считает контейнер неработоспособным. Проверяйте результат через `docker inspect`, а не по коду возврата.
- **Отключение последней сети допустимо.** Контейнер продолжает работать, но не имеет ни одного интерфейса, кроме loopback.
- **Удалить сеть с подключёнными контейнерами нельзя** — сначала `docker network disconnect`.

Правило проектирования: чем больше сетей у контейнера, тем больше `veth`-пар и правил фильтрации на хосте. Двухсетевая схема (публичная + приватная) — норма; три и более на одном контейнере стоит обосновывать.

### Режим `container:`

Контейнер может разделить сетевой стек с другим контейнером, а не получить собственный:

```bash
docker run -d --name sidecar --network container:app alpine:3 sleep 3600
```

Это способ не создавать вторую пару `veth` для прокси или отладочного агента, который должен видеть тот же localhost. Часть параметров **отклоняется** на этапе создания контейнера:

- `--publish`, `--publish-all`, `--expose`
- `--dns`, `--hostname`, `--add-host`

```bash
docker run --network container:app --dns 8.8.8.8 alpine:3 true
# → Error response from daemon: conflicting options: dns and the network mode
```

Ещё три параметра — `--mac-address`, `--dns-search`, `--dns-option` — в Engine 29.8.1 **принимаются, но молча не применяются**: MAC остаётся адресом целевого, а `/etc/resolv.conf` — конфигурацией целевого. Docker Docs перечисляют их как неподдерживаемые, поэтому опираться на них нельзя. Полный список, точные сообщения об ошибках и поведение при остановке целевого — в файле [«Режим сети `container:`»](./container_network.md).

Практический вывод: если sidecar-контейнеру нужен собственный DNS или собственный порт, режим `container:` не подходит — либо настраивайте DNS у основного контейнера, либо добавляйте отдельную сеть.

## Публикация портов

Это второй по значимости блок после выбора драйвера: именно он определяет, что вообще доступно снаружи.

### Два независимых механизма

Для каждого опубликованного порта Docker задействует два механизма, и они включаются раздельно:

1. **Правила NAT/PAT в `iptables` или `nftables`** — основной путь: переадресация с адреса хоста на адрес контейнера.
2. **`docker-proxy` — пользовательский процесс демона** — резервный путь в userspace. Запускается автоматически при `userland-proxy: true` (дефолт). Именно поэтому `docker ps` показывает живой сокет на хосте даже тогда, когда путь через NAT отключён.

Проверено на Docker Engine 29.8.1: при двух опубликованных портах активен ровно один процесс `docker-proxy`, обслуживающий оба.

Отключение userspace-прокси (`"userland-proxy": false` в `daemon.json`) убирает процесс, но оставляет NAT. Практические следствия: ниже потребление CPU и памяти на хосте, и одновременно пропадает ряд диагностических возможностей, а IPv4-порт на IPv6-адресе хоста перестаёт работать (механизм полагался именно на прокси).

### Формы записи

```bash
docker run -p 8080 nginx:alpine                    # хост:8080 → контейнер:80, все адреса
docker run -p 127.0.0.1:8080:80 nginx:alpine       # только loopback хоста
docker run -p 10.0.0.5:8080:80 nginx:alpine        # только этот адрес хоста
docker run -p 8080:80/udp nginx:alpine             # явно указать протокол
docker run -p 19093 nginx:alpine                   # эфемерный порт хоста → 19093
docker run -P nginx:alpine                         # все EXPOSE-порты на эфемерные
```

Полная форма: `HOST_IP:HOST_PORT:CONTAINER_PORT/PROTO`.

Проверенные особенности:

- **Без `HOST_IP` порт слушает все адреса — и IPv4, и IPv6 одновременно** (`0.0.0.0` и `[::]`). Это поведение по умолчанию, и оно же является главным источником неожиданной доступности сервиса наружу.
- **`127.0.0.1` в `HOST_IP` действительно ограничивает доступ.** Проверено: порт, привязанный к `127.0.0.1`, доступен с loopback и недоступен по адресу LAN-интерфейса хоста.
- **`-P` не создаёт явных привязок.** В `docker inspect` поле `HostConfig.PortBindings` будет пустым объектом `{}` — работает флаг `PublishAllPorts`, а не список привязок. Фактическое распределение портов видно только в `NetworkSettings.Ports` и в выводе `docker ps`. Не ищите привязки в `PortBindings`, если используете `-P`.
- **`--expose` в `Dockerfile` ничего не открывает.** Это декларация ожидаемого порта, которая становится рабочей только через `-P` или `-p`. Подробно — в [инструкции `EXPOSE`](../Dockerfile/Instructions/networking_ports.md).

### Блокировка неопубликованных портов

По умолчанию демон блокирует доступ к портам, которые **не** опубликованы, и для IPv4, и для IPv6. Механизм различается для двух случаев и это принципиально:

- **Обращение к адресу контейнера напрямую** (direct routing) блокируется правилом в цепочке `raw` таблицы на хуте `prerouting`. Оно срабатывает **до** таблицы `filter`, поэтому пакет не доходит до цепочки `DOCKER-USER` — и правило в `DOCKER-USER` не может его разрешить. Это поведение менялось в Docker Engine 28.0 (moby/moby#48724): ранее прямой доступ к неопубликованным портам работал, если политика цепочки `FORWARD` на хосте оставалась `ACCEPT`.
- **Прямой доступ с самого хоста** к адресу контейнера в режиме `nat` по умолчанию разрешён.

Следствие для планирования обновления до 28.0+: инфраструктура, которая обращалась к IP-адресам контейнеров напрямую (а не к опубликованным портам), перестанет работать после обновления.

Чтобы разрешить direct routing к **опубликованным** портам, есть два способа:

| Способ | Гранулярность | Требует перезапуска демона |
| :--- | :--- | :--- |
| опция сети `com.docker.network.bridge.trusted_host_interfaces` | одна сеть, список интерфейсов через `:` | нет |
| опция демона `allow-direct-routing` | все bridge-сети, все порты | да |

`--bridge-accept-fwmark` (демон, 28.0+) позволяет пометить пакеты и принять их мостом вопреки правилам `DROP` — но он **не действует** на drop в `raw`-цепочке `prerouting`, так как выполняется раньше.

### Gateway modes: что выбрать для изоляции

Это самый прямой рычаг управления тем, кто и как достаёт до контейнера снаружи. Задаётся для IPv4 и IPv6 независимо.

| Режим | NAT для входящих | Фильтрация портов | Адрес в исходящих | Доступ из других сетей | Когда нужен |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`nat`** (по умолчанию) | да | только опубликованные | адрес хоста | только через опубликованные адреса хоста | стандарт |
| **`nat-unprotected`** | да | **нет** правил | адрес хоста | только через опубликованные адреса хоста | возврат к поведению до 28.0; небезопасно |
| **`routed`** | нет | только опубликованные | **адрес контейнера** | напрямую, в обход адреса хоста | есть маршрут до подсети контейнеров |
| **`isolated`** | нет | только опубликованные | адрес контейнера | нет | изоляция БД; требует `--internal` |

Ключевые различия:

- **`nat-unprotected` снимает фильтрацию портов полностью.** Любой порт любого контейнера в этой сети становится доступен при прямой маршрутизации. Режим добавлен в 28.0 (moby/moby#48597) исключительно для совместимости со старым поведением и не предназначен для использования.
- **`routed` убирает NAT для входящих и маскарадинг для исходящих.** Пакеты от контейнера выходят с его собственным адресом, поэтому апстрим-сервисы видят реальный IP клиента, а логи и квоты работают корректно. Требует, чтобы у удалённых хостов был маршрут до подсети контейнеров. Хосты в том же L2-сегменте получают direct routing автоматически; хосты за маршрутизатором — только если маршрут настроен на маршрутизаторе.
- **В режиме `routed` номер порта в `-p` не используется.** Он применяется только к IPv4 или IPv6; хостовый порт из Mapping не имеет эффекта, и в лог пишется предупреждение. Если режим `routed` задан, указывайте только `0.0.0.0` или `::` и не задавайте порт.
- **`isolated` работает только вместе с `--internal`.** Иначе демон отклоняет сеть с ошибкой. В обычной `--internal`-сети адрес шлюза всё равно назначается мосту, из-за чего процессы на хосте видят сеть, а контейнеры видят хостовые сервисы на этом адресе (включая слушающие на `0.0.0.0`). `isolated` убирает адрес с моста, закрывая эту связность.
- **Режимы `nat-unprotected` и `isolated` появились в 28.0**; `routed` стал рабочим в 28.0 — в более ранних версиях опция принималась, но поведение не применялось.

```bash
# Проверка режима
docker network create -o com.docker.network.bridge.gateway_mode_ipv4=isolated \
  --internal db-isolated
# → Error response from daemon: gateway mode 'isolated' can only be used for
#   an internal network
```

### Адрес привязки и маскарадинг

| Что настроить | Опция |
| :--- | :--- |
| адрес хоста по умолчанию для публикуемых портов | `com.docker.network.bridge.host_binding_ipv4` (допускает и IPv6) |
| отключить маскарадинг исходящих | `com.docker.network.bridge.enable_ip_masquerade=false` |
| задать адрес SNAT вручную | `com.docker.network.host_ipv4` / `_host_ipv6` (требует `enable_ip_masquerade=true`) |
| не назначать мосту адрес шлюза | `com.docker.network.bridge.inhibit_ipv4=true` (только пользовательские сети) |
| имя интерфейса моста | `com.docker.network.bridge.name` |
| MTU | `com.docker.network.driver.mtu` |
| префикс имён интерфейсов в контейнере | `com.docker.network.container_iface_prefix` (по умолчанию `eth`) |

Значение `0.0.0.0` для адреса привязки означает «все адреса IPv4 **и** IPv6», а `::` — «только адреса IPv6». Чтобы ограничить конкретный порт только IPv4, адрес нужно указать явно: `-p 0.0.0.0:8080:80`.

С 28.0 адрес шлюза не резервируется там, где он не нужен: в `--internal`-сетях с `inhibit_ipv4`, в `ipvlan`/`macvlan` без родительского интерфейса и в режиме `ipvlan` L3 (moby/moby#49261). Проверяйте `docker network inspect`, а не рассчитывайте на наличие адреса.

## IPv6 в Docker

IPv6 **не включается по умолчанию** и требует явной настройки на двух уровнях: демона и сети.

### Включение на пользовательской сети

```bash
docker network create --ipv6 --subnet 2001:db8:1234::/64 my-net
# Только IPv6 — отключить адресацию IPv4:
docker network create --ipv6 --ipv4=false v6net
```

Если `--subnet` не задан, Docker выбирает префикс ULA (`fd00::/8`) автоматически, используя 40-битный Global ID на основе случайно сгенерированного ID демона. Отключить IPv4 в сети `bridge` по умолчанию нельзя.

### Включение в сети `bridge` по умолчанию

Эти опции относятся **только** к дефолтной сети и не влияют на пользовательские:

```json
{
  "ipv6": true,
  "bip6": "2001:db8::1111/64",
  "fixed-cidr-v6": "2001:db8::/64",
  "default-gateway-v6": "2001:db8:abcd::89"
}
```

`ipv6` обязателен, остальные опциональны. Если `bip6` не задан, подсеть определяется через `fixed-cidr-v6`; если не заданы оба, выбирается ULA-префикс. Маршрут IPv6 для подсети Docker по умолчанию добавляется в таблицу маршрутизации, а шлюз по умолчанию — первый адрес подсети. Изменения требуют перезапуска демона.

### Режим `routed` для IPv6

```bash
docker network create --ipv6 --subnet 2001:db8::/64 \
  -o com.docker.network.bridge.gateway_mode_ipv6=routed my-net
```

Контейнеры получают глобально маршрутизируемые адреса, NAT66 не применяется, и адрес контейнера сохраняется на выходе. Требует, чтобы инфраструктура маршрутизации уже имела маршрут до выделенного префикса. Планируйте префиксы по правилам: `/64` на хост, `/80` на контейнеры — тогда адрес заканчивается MAC-адресом, что предотвращает инвалидацию кэша соседей (NDP) на уровне Docker.

### Особенности окружения

- На хосте с legacy-бэкендом `xtables` для создания IPv6-сети нужен загруженный модуль ядра `ip6_tables`. Обычно он загружается автоматически при старте Docker, но в Docker-in-Docker может потребоваться `modprobe ip6_tables` на хосте, либо отключение `ip6tables` для контейнеризированного демона.
- Планирование адресации на крупных хостах требует `default-address-pools` в `daemon.json` — иначе подсети выделяются из пула по умолчанию и могут пересечься с корпоративными диапазонами.

## Rootless: сетевой стек

В режиме без root демон работает внутри user namespace и RootlessKit, поэтому сетевой стек целиком реализуется в userspace. Это меняет и производительность, и модель портов.

### Выбор драйвера

`dockerd-rootless.sh` выбирает драйвер по первому найденному в системе: `slirp4netns` (≥ 0.4.0) → `pasta` → `vpnkit` → `gvisor-tap-vsock`. Начиная с **Docker Engine 29.5** (`gvisor-tap-vsock` — новый дефолт; moby/moby#52319) пакеты Docker больше не устанавливают `slirp4netns`, поэтому на практике чаще всего используется `gvisor-tap-vsock`. Значение по умолчанию задаётся через `DOCKERD_ROOTLESS_ROOTLESSKIT_NET`, портовый драйвер — через `DOCKERD_ROOTLESS_ROOTLESSKIT_PORT_DRIVER` (`implicit` для `pasta`, `builtin` для остальных).

| Драйвер сети | Драйвер портов | Пропускная способность сети | Пропускная способность портов | Проброс Source IP | Статус |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `gvisor-tap-vsock` | `builtin` | низкая | высокая | да | дефолт при отсутствии `slirp4netns` |
| `slirp4netns` | `builtin` | низкая | высокая | да | дефолт при наличии `slirp4netns` |
| `pasta` | `implicit` | низкая | высокая | да | экспериментальный |
| `pasta` | `pesto` | низкая | высокая | да | только IPv4, Docker Engine 29.8+ |
| `vpnkit` | `builtin` | низкая | высокая | да | устаревший |
| `lxc-user-nic` | `builtin` | высокая | высокая | да | экспериментальный |

Важно не путать две вещи: официальная таблица относит `pasta` и `gvisor-tap-vsock` к **низкой** пропускной способности сети, несмотря на отдельные замеры вполсилы. Единственные драйверы с высокой пропускной способностью — `lxc-user-nic` и `bypass4netns`, и оба экспериментальные (второй вообще не интегрирован в RootlessKit и требует отдельного seccomp-профиля). Пропускная способность **портов** при этом высокая у всех вариантов с `builtin`/`implicit`.

Значения, действующие в rootless-режиме:

- **MTU по умолчанию — 65520** для `slirp4netns`, `pasta` и `gvisor-tap-vsock`; 1500 для остальных. Это принципиально отличается от rootful-конфигурации и объясняет часть расхождений в результатах `ping -M do`.
- **Проброс Source IP** работает с RootlessKit v3.0+ и требует отключённого `userland-proxy`. Без этого исходящий IP не сохраняется, и логи апстрим-сервисов увидят один и тот же адрес.
- **`--net=host` в rootless** с 29.5 (moby/moby#47103) действительно разделяет сетевой namespace хоста и обходит userspace-стек. До 29.5 демон находился внутри сетевого namespace RootlessKit, и поведение было неожиданным. Обратная сторона — потеря изоляции namespace.
- **Файрвол не управляется.** В rootless-режиме демон не может изменять `iptables`/`nftables` хоста, поэтому `DOCKER-USER` может отсутствовать или быть пустым. Правила фильтрации применяются на уровне сети RootlessKit.

```bash
# Явный выбор драйвера через drop-in systemd
mkdir -p ~/.config/systemd/user/docker.service.d
cat > ~/.config/systemd/user/docker.service.d/override.conf <<'EOF'
[Service]
Environment="DOCKERD_ROOTLESS_ROOTLESSKIT_NET=gvisor-tap-vsock"
Environment="DOCKERD_ROOTLESS_ROOTLESSKIT_PORT_DRIVER=builtin"
EOF

systemctl --user daemon-reload
systemctl --user restart docker
```

## Swarm: routing mesh

Этот блок касается только Docker Swarm. Режим Swarm не объявлен устаревшим: он не числится в списке deprecated-функций Docker, не имеет EOL и получает исправления в каждом релизе движка. Устарел и удалён был **Docker Classic Swarm** (отдельный продукт 2015 года, deprecated в 20.10, удалён в 23.0) — его регулярно путают с режимом Swarm.

- **Ingress Network** — специальная overlay-сеть, автоматически создаваемая при инициализации Swarm. Каждый узел слушает опубликованные порты **всех** сервисов кластера, даже если реплик на нём нет, и перенаправляет трафик на живой узел.
- **IPVS** — балансировщик L4 в ядре, на котором построены Routing Mesh и VIP-режим endpoint. Тонкая настройка таймаутов — в разделе про Swarm.
- **Обход routing mesh** — `--publish mode=host,target=80,published=8081` привязывает порт к узлу с задачей и отказывается от mesh. Нужен, когда требуется реальный IP клиента.
- **Без routing mesh** — `--endpoint-mode dnsrr` возвращает список адресов через DNS, но несовместим с `mode=ingress` и требует собственного балансировщика.

Практическое ограничение для администраторов: **бэкенд `nftables` нельзя включить на узле с включённым Swarm.** Поддержка nftables появилась в 29.0 как экспериментальная, и правила overlay-сетей на неё не мигрированы. Планируя переход на `firewall-backend=nftables`, сначала выводите узлы из кластера.

## Практические сценарии

### Сценарий 1: сегментация приложения на три сети

Типовая схема: публичный слой, внутренний слой и изолированная база данных.

```bash
# 1. Создание сетей с явными подсетями
docker network create --subnet 10.10.0.0/24 --driver bridge frontend
docker network create --subnet 10.20.0.0/24 --driver bridge backend
docker network create --subnet 10.30.0.0/24 --driver bridge \
  --internal \
  -o com.docker.network.bridge.gateway_mode_ipv4=isolated \
  database

# 2. База данных — только в изолированной сети
docker run -d --name pg --network database postgres:17-alpine

# 3. API — во frontend (публичный) и backend
docker run -d --name api --network frontend -p 127.0.0.1:8080:8080 app:1.0
docker network connect --alias db backend api
docker network connect --alias postgres database api

# 4. Веб — только во frontend
docker run -d --name web --network frontend -p 80:80 nginx:alpine
```

**Валидация** — каждый шаг проверяется отдельной командой, а не предположением:

```bash
# API действительно состоит в трёх сетях
docker inspect api --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
# → frontend backend database

# Каждая сеть содержит ожидаемый набор контейнеров
docker network inspect frontend --format '{{range .Containers}}{{.Name}} {{end}}'
# → web api
docker network inspect database --format '{{range .Containers}}{{.Name}} {{end}}'
# → api pg

# Из frontend в database — нет маршрута (разные сети)
docker exec web getent hosts postgres
# → (пусто, exit code 2)

# Из backend в database — по алиасу работает
docker exec api getent hosts postgres
# → 172.30.0.2   postgres

# У базы данных нет выхода в интернет: default route отсутствует
docker exec pg ip route
# → (пусто)
```

Обратите внимание на `-p 127.0.0.1:8080:8080`: без явного адреса порт был бы доступен на всех интерфейсах хоста, включая LAN. Это самая частая ошибка при публикации сервисов.

### Сценарий 2: выбор режима шлюза под требования изоляции

```bash
# Сеть только для базы данных: полная изоляция от хоста и извне
docker network create --internal \
  -o com.docker.network.bridge.gateway_mode_ipv4=isolated \
  db-strict

# Сеть с собственными глобальными адресами, без NAT, с сохранением IP клиента
docker network create --ipv6 --subnet 2001:db8:1::/80 \
  -o com.docker.network.bridge.gateway_mode_ipv6=routed \
  routed-net

# Фиксированный SNAT-адрес для исходящих пакетов всей сети
docker network create \
  -o com.docker.network.host_ipv4=10.0.0.1 \
  -o com.docker.network.bridge.enable_ip_masquerade=true \
  snat-net
```

**Валидация:**

```bash
docker network inspect routed-net \
  -f '{{index .Options "com.docker.network.bridge.gateway_mode_ipv6"}}'
# → routed

# В routed-сети исходящий пакет сохраняет адрес контейнера
docker run --rm --network routed-net alpine:3 \
  sh -c 'ip -6 route get 2001:db8::1 | head -1'
# → 2001:db8:1::2 dev eth0 src 2001:db8:1::2

# В обычной nat-сети адрес подменяется на адрес хоста
docker run --rm --network frontend alpine:3 \
  sh -c 'ip route get 10.0.0.1 | head -1'
# → 10.0.0.1 via 10.10.0.1 dev eth0 src 10.10.0.1
```

### Сценарий 3: трассировка пути пакета

Понимание порядка прохождения пакета экономит больше времени, чем любая отдельная команда диагностики.

Исходящий пакет от контейнера к внешнему адресу:

1. Выходит из sandbox-контейнера через `eth0` (один конец `veth`-пары).
2. Второй конец `veth` попадает в мост `br-<ID>` на хосте.
3. Правило `FORWARD` цепочки `DOCKER` проверяет, разрешён ли выход; цепочка `DOCKER-USER` (если она есть) проверяется раньше.
4. Правило `nat`/`POSTROUTING` подменяет адрес источника на адрес хоста (masquerading), если не задан явный SNAT.
5. Пакет уходит через физический интерфейс.

Входящий пакет на опубликованный порт:

1. Пакет приходит на физический интерфейс и попадает в `PREROUTING`.
2. Правило `raw`-таблицы отбрасывает пакеты, адресованные напрямую IP-контейнера, — если direct routing не разрешён явно.
3. Правило `nat`/`PREROUTING` выполняет DNAT на адрес и порт контейнера.
4. Пакет маршрутизируется в bridge-сеть, проходит `FORWARD` и попадает на `veth` контейнера.
5. Ответ проходит обратный путь; `conntrack` узнаёт соединение и применяет обратную трансляцию.

Пошаговая схема с указанием всех уровней и описанием IPv6-варианта приведена в заметке **[Сетевой драйвер bridge](./drivers/bridge.md#жизненный-цикл-пакета-packet-flow)**.

## Устранение неисправностей

### Симптомы и их причины

| Симптом | Вероятная причина | Диагностика |
| :--- | :--- | :--- |
| `ping: bad address 'name'` | контейнер в сети `bridge` по умолчанию, а не в пользовательской | `docker inspect c --format '{{.HostConfig.NetworkMode}}'` |
| Сервис доступен с хоста, но не из соседнего контейнера | соседний контейнер в другой сети; нужен опубликованный порт, а не прямой IP | `docker network inspect <net> --format '{{range .Containers}}{{.Name}} {{end}}'` |
| Порты не видны в `HostConfig.PortBindings` | использован `-P`, а не `-p` | `docker inspect c --format '{{json .NetworkSettings.Ports}}'` |
| Контейнер не может обратиться к сервису на хосте | сервис слушает `127.0.0.1`, а не `0.0.0.0` | проверить адрес прослушивания; использовать `host-gateway` |
| Прямой доступ к IP контейнера не работает | с 28.0 блокируется правилом в `raw`-таблице | `sudo iptables -t raw -S PREROUTING` |
| `gateway mode 'isolated' can only be used for an internal network` | не задан `--internal` | добавить `--internal` |
| Медленный обмен в rootless | userspace-сетевой стек | сменить `DOCKERD_ROOTLESS_ROOTLESSKIT_NET` |
| Запросы DNS занимают 5 секунд | AAAA-запрос не возвращается | `dig -4` / `dig -6` для сравнения |

### Проверка состояния сети

```bash
# Общая картина: драйвер, scope, подсети, шлюз, MTU, режим шлюза, контейнеры
docker network inspect my-net

# Кратко по всем сетям
docker network ls

# Сколько эндпоинтов в сети — оценка нагрузки на мост
docker network inspect my-net --format '{{len .Containers}}'
# → 12

# Проверка фактического режима резолвера
docker exec c cat /etc/resolv.conf
# nameserver 127.0.0.11     ← пользовательская сеть
# options ndots:0
# nameserver 10.0.0.2       ← сеть bridge: наследование хоста
```

### Ограничения, о которых нужно знать заранее

- **Лимит bridge-сети — 1000 контейнеров.** Из-за ограничений ядра Linux bridge-сети становятся нестабильными, и связь между контейнерами начинает рваться при 1000 и более контейнерах в одной сети (moby/moby#44973). Планируйте шардирование по сетям заранее: это не аварийная ситуация, а свойство архитектуры.
- **Сервис-дискавери разрешает только заданные имена.** Автоматически сгенерированные имена вида `e3a1b2c3d4` не резолвятся — в ответе DNS будут только те имена, что вы задали через `--name`, `--network-alias` или `hostname`.
- **Удаление сети требует отключения всех контейнеров.** `docker network rm` на сети с эндпоинтами завершается ошибкой; удалите их сначала через `docker network disconnect`.
- **Правила фильтрации пересоздаются демоном.** Любые правки правил Docker в таблицах `nat`/`filter`/`raw` будут потеряны при перезапуске демона или пересоздании сети. Свои правила добавляйте в `DOCKER-USER` (в режиме iptables).
- **UFW и Docker несовместимы в части маршрутизации.** Трафик контейнеров divertируется в таблице `nat` и обрабатывается до цепочек `INPUT`/`OUTPUT` UFW, поэтому правила UFW на него не действуют.
- **Docker Desktop ограничивает `host` и `macvlan`.** На Docker Desktop `host`-сеть реализована через виртуализированный стек: `localhost` хоста недоступен, а `macvlan` работает не так, как на нативном Linux. Проверяйте на целевом хосте.

## Рекомендации

### Проектирование сетей

- **Используйте пользовательские `bridge`-сети вместо дефолтной `bridge`.** Это даёт Service Discovery, изоляцию между стеками и возможность менять настройки сети без перезапуска демона.
- **Одна сеть — один уровень доверия.** Сети `frontend`, `backend`, `database` должны отражать границы, а не названия сервисов.
- **Публикуйте порт с явным адресом.** `-p 127.0.0.1:8080:8080` для локального доступа, `-p 10.0.0.5:8080:80` для конкретного интерфейса. Без адреса порт открывается на всех интерфейсах.
- **Не публикуйте базы данных и административные интерфейсы.** Если контейнеру нужен доступ к внешнему сервису, используйте `host-gateway`, а не публикацию порта БД.
- **Планируйте подсети явно.** Задавайте `--subnet` при создании сети и настройте `default-address-pools`, чтобы не столкнуться с пересечением диапазонов при десятках сетей на хосте.
- **Держите число сетей на контейнере минимальным.** Каждая дополнительная сеть — это `veth`-пара, эндпоинт, правила фильтрации и отдельная запись в DNS.

### Безопасность

- **Используйте `isolated` для сетей с данными.** `--internal` вместе с `gateway_mode=isolated` убирает и внешний доступ, и видимость со стороны хоста.
- **Не используйте `nat-unprotected`.** Режим снимает фильтрацию портов и открывает все порты всех контейнеров сети при прямой маршрутизации.
- **Ограничивайте связность через `DOCKER-USER`, а не правкой правил Docker.** Только `DOCKER-USER` переживает перезапуск демона и пересоздание сети.
- **Учитывайте, что прямой доступ к IP контейнера заблокирован.** Правило в `raw`-таблице нельзя обойти из `DOCKER-USER`; для легального direct routing используйте `trusted_host_interfaces` или `allow-direct-routing`.
- **Помните, что в одной bridge-сети все порты открыты взаимно.** Сеть — это единица доверия, а не единица приложения.

### Эксплуатация

- **Проверяйте фактический режим, а не задуманный.** `docker network inspect` показывает реальные gateway mode, подсети, MTU и наличие эндпоинтов.
- **Считайте эндпоинты.** Ближе к 1000 контейнеров в одной сети — раньше планируйте шардирование.
- **Держите daemon.json под контролем версий.** `firewall-backend`, `icc`, `default-address-pools`, `userland-proxy` меняют поведение существующих сетей; после изменения нужен перезапуск демона и проверка `docker network ls`.
- **В rootless явно задавайте драйвер.** Поведение зависит от того, какие пакеты присутствуют в системе, и меняется между версиями.
- **Мониторьте conntrack.** Переполнение таблицы проявляется как периодические потери соединений при высокой нагрузке.

### Откат изменений

```bash
# 1. Удалить добавленное подключение
docker network disconnect backend api

# 2. Убрать публикацию порта: контейнер пересоздаётся
docker rm -f api
docker run -d --name api --network frontend app:1.0   # без -p

# 3. Откатить gateway mode: сеть пересоздаётся
docker network disconnect frontend web
docker network rm frontend
docker network create --subnet 10.10.0.0/24 --driver bridge frontend
docker run -d --name web --network frontend -p 80:80 nginx:alpine

# 4. Откатить глобальные опции демона
sudo cp /etc/docker/daemon.json.bak /etc/docker/daemon.json
sudo systemctl restart docker
```

Правило: **опции сети необратимы без пересоздания сети** (пересоздание теряет статические IP и алиасы), а **опции демона** требуют перезапуска и затрагивают все сети сразу. Снимайте `daemon.json.bak` до правки, а не после.
