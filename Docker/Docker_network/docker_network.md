# Docker: Обзор сетевых моделей

## Определения

- **Docker Networking**: Система, обеспечивающая сетевое взаимодействие контейнеров между собой, с хост-системой и внешними сетями.
- **Container Network Model (CNM — модель сети контейнеров)**: Архитектурная спецификация Docker для организации сетевого стека. Состоит из трёх компонентов:
  - **Sandbox (Песочница)**: Изолированное сетевое окружение контейнера (сетевые интерфейсы, таблицы маршрутизации, DNS-настройки). Реализуется через сетевые пространства имён Linux (network namespaces).
  - **Endpoint (Конечная точка)**: Виртуальный интерфейс (veth-пара), соединяющий Sandbox с конкретной сетью.
  - **Network (Сеть)**: Программный коммутатор (bridge) или логическая группа эндпоинтов, позволяющая им обмениваться пакетами.
- **Сетевой драйвер (Network Driver)**: Программный модуль (плагин), реализующий конкретный тип сети (например, `bridge`, `overlay`).
- **DNS (Domain Name System — система доменных имён)**: В Docker используется для автоматического разрешения имён контейнеров в IP-адреса внутри пользовательских сетей.

## Основные концепции

### Обзор сетевых драйверов

Docker предоставляет встроенные драйверы для различных сценариев. Выбор драйвера определяет уровень изоляции и производительность.

| Драйвер | Изоляция | Производительность | Сценарий использования |
| :--- | :--- | :--- | :--- |
| **[`bridge`](./drivers/bridge.md)** | Высокая (своя подсеть) | Хорошая (через NAT) | **По умолчанию.** Изолированные контейнеры на одном хосте. |
| **[`host`](./drivers/host.md)** | Отсутствует | Максимальная | Прямое использование сетевого стека хоста (высокопроизводительные сервисы). |
| **[`overlay`](./drivers/overlay.md)** | Высокая (между хостами) | Средняя/Хорошая | **Docker Swarm.** Связь контейнеров на разных физических узлах. |
| **[`macvlan`](./drivers/macvlan.md)**| L2 (уровень MAC) | Высокая | Контейнеру нужен свой MAC-адрес в физической сети. |
| **[`ipvlan`](./drivers/ipvlan.md)**| L2/L3 | Высокая | Альтернатива macvlan; контейнеры используют MAC-адрес хоста. |
| **[`none`](./drivers/none.md)** | Полная | Н/Д | Отключение сети или использование сторонних плагинов. |

### Пользовательские сети и автоматическое разрешение имён (DNS)

При установке Docker создает стандартную сеть `bridge`. Рекомендуемой практикой является создание **пользовательских сетей** (user-defined networks) для каждой группы сервисов.

**Критическое отличие:**

1. **Service Discovery**: В пользовательских сетях встроенный DNS-сервер Docker позволяет контейнерам обращаться друг к другу по имени (`ping web-app`). В стандартной сети `bridge` это не работает (только по IP-адресам).
2. **Изоляция**: Контейнеры в разных пользовательских сетях изолированы друг от друга на уровне L3.
3. **Безопасность**: Стандартная сеть `bridge` подключает все новые контейнеры в одну общую "кучу", что менее безопасно.

### Поддержка IPv6 в Docker (v27+)

Начиная с Docker Engine v27 (2024), поддержка IPv6 значительно упрощена.

- **Автоматическая настройка**: Больше не требуется обязательная правка `daemon.json` для активации IPv6, если хост поддерживает этот протокол.
- **Routed Mode**: Docker поддерживает нативный режим маршрутизации IPv6 без использования NAT66, что повышает производительность.
- **Docker Compose**: Для включения IPv6 в проекте достаточно указать `enable_ipv6: true` в описании сети.

### Сетевое взаимодействие в Rootless-режиме

В режиме без прав суперпользователя (Rootless) сетевой стек реализуется через пользовательское пространство (User-space).

- **`slirp4netns` (Устаревший)**: Использовался долгое время, имеет высокие накладные расходы на NAT и ограниченную производительность (~3 Гбит/с).
- **`pasta` / `passt` (Современный)**: Внедрён в 2024-2025 гг. Обеспечивает производительность до 15 Гбит/с, сохраняет исходные IP-адреса отправителей и не требует NAT внутри пространства имён.

## Практические сценарии

### Сценарий 1: Управление сетями через CLI

Все основные команды (создание, удаление, инспекция) собраны в отдельном справочнике:
**[Управление сетями Docker: CLI-справочник](./cli.md)**.

### Сценарий 2: Изоляция базы данных и приложения

Пример создания топологии, где БД доступна приложению, но скрыта от внешнего мира.

```bash
# 1. Создание сети
docker network create my-app-net

# 2. Запуск PostgreSQL (порт 5432 доступен только внутри сети)
docker run -d --name pg-db --network my-app-net \
  -e POSTGRES_PASSWORD=secret postgres:17-alpine

# 3. Запуск веб-приложения (публикуем только HTTP порт)
docker run -d --name web-app --network my-app-net \
  -p 80:8080 my-web-app:latest
```

### Сценарий 3: Трассировка пакета (veth-пары)

Схематичный путь пакета между контейнерами A и B на одном хосте:
`Контейнер A (eth0) → veth-интерфейс (хост) → Bridge (docker0) → veth-интерфейс (хост) → Контейнер B (eth0)`

Подробная отладка с использованием `nsenter` и `bridge fdb` описана в разделе CLI.

## Дополнительная информация

### Безопасность и публикация портов

**Критическая особенность:** Публикация портов (`-p 80:80`) по умолчанию открывает доступ ко **всем** сетевым интерфейсам хоста. Если сервер имеет публичный IP, сервис станет доступен всему интернету.

- **Рекомендация**: Всегда указывайте интерфейс привязке для внутренних сервисов: `-p 127.0.0.1:5432:5432`.
- **UFW**: Docker обходит стандартные правила UFW/IPTABLES. Для фильтрации используйте цепочку `DOCKER-USER`.

### Сводная таблица режимов и реализации

| Режим Docker | Реализация в Linux | Особенности |
| :--- | :--- | :--- |
| `bridge` | Network NS + veth + bridge | Изоляция + NAT |
| `host` | Без Network NS | Сеть хоста напрямую |
| `none` | Network NS без интерфейсов | Только loopback |
| **[`container`](./container_network.md)** | Общий Network NS | Один IP на несколько контейнеров |
