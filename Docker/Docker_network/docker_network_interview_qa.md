# Docker Networking: Вопросы на собеседованиях

**Актуально для:** Docker Engine 29.x. Ответы верифицированы по документации Docker и содержимому базы знаний; теория и практика — в смежных файлах (ссылки в конце).

## Определения

**Задачи этого файла** — краткие, точные ответы на типичные вопросы DevOps/SRE-собеседований по сетям Docker. Каждый ответ содержит ключевой факт и, где нужно, команду для проверки.

## Основы сетевой модели

**Q: Что такое Docker Networking и из чего состоит CNM?**
A: Подсистема Docker для сетевого взаимодействия контейнеров. CNM (Container Network Model) — три сущности: **Sandbox** (изолированное сетевое окружение контейнера: интерфейсы, таблицы маршрутизации, `/etc/resolv.conf`, реализуется через network namespace), **Endpoint** (привязка sandbox к сети; один эндпоинт принадлежит ровно одной сети), **Network** (набор эндпоинтов, видящих друг друга напрямую). Проверка: `docker network ls`.

**Q: Чем отличается дефолтная сеть `bridge` от пользовательской?**
A: Дефолтная `bridge` — legacy-режим: нет встроенного DNS (контейнеры не резолвят друг друга по имени, только по IP), все контейнеры без `--network` попадают в одну сеть, имена — только через deprecated `--link`. Пользовательская bridge-сеть: встроенный DNS `127.0.0.11`, Service Discovery, изоляция между стеками, настраиваемые опции без перезапуска демона. Проверка режима: `docker inspect <c> --format '{{.HostConfig.NetworkMode}}'`.

**Q: Что такое `127.0.0.11` и почему именно этот адрес?**
A: Встроенный DNS-резолвер Docker, слушает UDP+TCP порт 53 в netns контейнера. Адрес из блока `127.0.0.0/8` — loopback-only, не маршрутизируется: резолвер недоступен из других контейнеров и с хоста, и его нельзя перехватить маршрутными изменениями. IPv6-эквивалента нет. Работает только в пользовательских сетях.

**Q: Что такое Service Discovery?**
A: Разрешение имён контейнеров и сетевых алиасов через встроенный DNS на `127.0.0.11`. Реестр содержит: имя контейнера (`--name`), сетевой алиас (`--network-alias`, `--alias`, Compose `aliases`), имя сервиса Swarm. Автоматически сгенерированные имена (`e3a1b2c3d4`) **не** резолвятся. Проверка: `docker exec <c> getent hosts <name>`.

**Q: Что такое network alias и какова его область действия?**
A: Дополнительное имя контейнера в конкретной сети. Алиас действует **только** в той сети, где объявлен. Один алиас может быть объявлен на нескольких контейнерах — тогда имя резолвится в несколько адресов, и какой именно контейнер имеется в виду, не гарантировано. Проверка: `docker inspect <c> --format '{{json .NetworkSettings.Networks.<net>.Aliases}}'`.

## Драйверы

**Q: Как выбрать драйвер сети?**
A: Один хост, контейнеры должны видеть друг друга по имени → пользовательская `bridge` (вариант по умолчанию для production). Нужен доступ к localhost хоста → `host` (ценой изоляции) или `bridge` + `host-gateway`. Маршрутизация на L2 без NAT → `macvlan`. Много хостов + Swarm → `overlay`. Плотность выше macvlan → `ipvlan` (но контейнеры на одном хосте не общаются). Сборка без сети → `none`.

**Q: Чем `macvlan` отличается от `ipvlan`?**
A: `macvlan` — L2: каждый контейнер получает уникальный MAC, виден в сети как отдельное устройство; хост не видит контейнер без promiscuous-режима; не работает на Wi-Fi. `ipvlan` — L3: общий MAC, выше плотность; контейнеры на одном хосте не могут общаться напрямую. Оба требуют настройки promiscuous на физическом интерфейсе (для macvlan) и не работают на некоторых облачных сетях.

**Q: Что такое режим `--network container:<id>`?**
A: Контейнер не получает собственный netns, а присоединяется к netns целевого через `setns(2)`. Разделяются: интерфейсы, IP, MAC, `/etc/hosts`, `/etc/resolv.conf`, имя хоста. Не разделяются: PID, IPC, mount namespaces, ФС. Нельзя: публиковать порты, задавать `--hostname`, `--dns`, `--add-host`, алиасы, статические IP. `docker restart` целевого **не** восстанавливает сеть sidecar — требуется пересоздание.

**Q: Что такое overlay-сеть и VXLAN?**
A: Overlay — драйвер для нескольких хостов, инкапсулирует Ethernet-кадры в UDP-пакеты (VXLAN, порт 4789). Требует активированного Swarm (`docker swarm init`); без Swarm создание завершится ошибкой. Standalone-контейнеры подключаются только к `--attachable` overlay-сетям. Шифрование трафика между узлами — опция `encrypted` (IPsec, протокол 50 ESP). MTU по умолчанию 1450 при физическом 1500.

**Q: Чем `host`-сеть отличается от `bridge` по производительности?**
A: `host` убирает NAT, мост и `docker-proxy` из пути пакета — ниже задержка, выше throughput. Цена: нет изоляции (контейнер видит все интерфейсы хоста), конфликты портов с хостом, обход всех правил Docker. В Swarm на одном узле может быть только одна реплика сервиса с фиксированным портом в `host`-режиме.

## Публикация портов

**Q: Какие формы записи у `-p`?**
A: Полная форма `HOST_IP:HOST_PORT:CONTAINER_PORT/PROTO`. `-p 8080:80` — все адреса хоста (IPv4 **и** IPv6 одновременно); `-p 127.0.0.1:8080:80` — только loopback; `-p 8080:80/udp` — явный протокол; `-p 19093` — эфемерный порт хоста; `-P` — все EXPOSE-порты на эфемерные. Без `HOST_IP` порт слушает `0.0.0.0` и `[::]` — главный источник неожиданной доступности наружу.

**Q: Чем `--expose` отличается от `-p`?**
A: `--expose` (и `EXPOSE` в Dockerfile) — декларация ожидаемого порта, ничего не открывает. Работает только через `-P` или `-p`. Проверка: `docker inspect <c> --format '{{json .NetworkSettings.Ports}}'`.

**Q: Что такое `docker-proxy` и `userland-proxy`?**
A: `docker-proxy` — userspace-процесс демона, резервный путь для опубликованных портов (запускается при `userland-proxy: true`, дефолт). Именно поэтому `docker ps` показывает живой сокет даже при отключённом NAT. Отключение (`"userland-proxy": false`) убирает процесс (ниже CPU/память), но ломает IPv4-порт на IPv6-адресе хоста.

**Q: Почему опубликованный порт доступен на всех интерфейсах и как это ограничить?**
A: Без `HOST_IP` привязка идёт на `0.0.0.0` и `[::]`. Ограничение: явный адрес (`-p 127.0.0.1:8080:80` — проверено, порт недоступен по LAN-интерфейсу) или адрес привязки по умолчанию для сети (`com.docker.network.bridge.host_binding_ipv4`). Для IPv4-only: `-p 0.0.0.0:8080:80`.

## DNS и балансировка

**Q: Что такое TTL ответов встроенного резолвера?**
A: 600 секунд — не «TTL 0». Приложение вправе кэшировать адрес контейнера до 10 минут, тогда как `docker compose up -d` может выдать другой адрес. Обнаружится лавиной отказов. Решения: уникальные имена, healthcheck с проверкой разрешения имени, клиентский резолвер с перебором всех адресов.

**Q: Что такое `ndots` и почему по умолчанию `0`?**
A: Порог числа точек в имени, при котором оно считается абсолютным. Docker выставляет `ndots:0`, чтобы одноуровневые имена (`db`, `api`) резолвились как есть, без перебора `search`-суффиксов. При `ndots > 0` резолвер перестаёт проксировать одноуровневые имена наверх и возвращает пустой успешный ответ — ломает обращение к внешним доменам. Отличие от Kubernetes: там `ndots:5` по умолчанию.

**Q: Как балансируется нагрузка между контейнерами под одним именем?**
A: Резолвер возвращает **все** адреса, порядок **случайно перемешивается** при каждом ответе (алгоритм Фишера—Йетса) — это не round-robin. Балансировка ложится на клиента: приложение, всегда берущее первый адрес, ничего не распределяет. Если ответ не помещается в UDP-пакет, резолвер выставляет флаг `TC` и удаляет записи по одной — клиент обязан повторить запрос по TCP.

**Q: Чем VIP отличается от dnsrr в Swarm?**
A: `vip` (по умолчанию): имя резолвится в один виртуальный адрес, балансировка на IPVS в ядре каждого узла, работает с routing mesh. `dnsrr`: имя резолвится в список адресов задач, балансировка на клиенте, несовместим с `mode=ingress`, требует собственного балансировщика. Переключение: `docker service update --endpoint-mode dnsrr <svc>`.

## Безопасность и фильтрация

**Q: Что такое ICC и чем `--icc=false` отличается от `--internal`?**
A: ICC (Inter-Container Communication) — прямой доступ контейнеров одной сети к неопубликованным портам. `enable_icc=false` (опция сети) блокирует **весь** трафик внутри сети, включая обращение через адрес хоста, но **не** блокирует DNS и выход в интернет. `--internal` — блокирует выход во внешнюю сеть (нет маршрута по умолчанию), но имена внутри резолвятся. `enable_icc=false` — не инструмент микросегментации: он не различает приложения внутри сети.

**Q: Что такое `DOCKER-USER` и почему свои правила добавляют туда?**
A: Цепочка в таблице `filter`, зарезервированная Docker, вызывается первой в `FORWARD`. Единственная цепочка, которую Docker не перезаписывает. Важно: к моменту входа пакета в `DOCKER-USER` уже выполнен DNAT (`--dport` — порт контейнера, не хоста) и уже отработан `raw` PREROUTING (блокировка direct routing), поэтому правило в `DOCKER-USER` не может разрешить неопубликованный порт.

**Q: Почему UFW/firewalld не защищает опубликованные порты?**
A: Docker выполняет DNAT в таблице `nat`, которая обрабатывается **до** `filter`. Пакет, адресованный опубликованному порту, перенаправляется на порт контейнера и не пересекает цепочки `INPUT`/`OUTPUT`, которыми управляет UFW. Правило `ufw deny 443` не влияет на `docker run -p 443:443`. Фильтрацию Docker-трафика ведут в `DOCKER-USER`. Подробно: [UFW — интеграция с Docker](../../Linux/Networking/Settings/tools/ufw.md).

**Q: Как изолировать базу данных от интернета?**
A: Сеть с `--internal` (нет маршрута по умолчанию, внешний DNS не резолвится — `SERVFAIL`, это замысел) + gateway mode `isolated` (убирает адрес шлюза с моста, закрывая связность хост↔контейнер через адрес моста). `isolated` работает только вместе с `--internal`. Для внешнего доступа контейнер должен быть подключён минимум к двум сетям.

## Диагностика

**Q: Как отладить сеть контейнера без shell в приложении?**
A: `docker run --rm -it --network container:<id> nicolaka/netshoot` — вход в netns приложения с полным набором утилит (`tcpdump`, `mtr`, `nmap`, `iperf3`, `ss`, `dig`). Альтернатива с хоста: `nsenter` по пути `/var/run/docker/netns/<id>`. Проверка принадлежности к netns: `readlink /proc/self/ns/net` — одинаковый inode означает один namespace.

**Q: Как проверить, в каких сетях контейнер и какие у него адреса?**
A: `docker inspect <c> --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'` — список сетей; `docker inspect <c> --format '{{json .NetworkSettings.Ports}}'` — привязки портов. Для sidecar в режиме `container:` поля `NetworkSettings.Networks` и `PortBindings` пусты (`{}`) — инвентаризация по `docker ps` их пропустит.

**Q: Контейнер не резолвует имя соседа. Что проверить?**
A: 1) Сеть: `docker inspect <c> --format '{{.HostConfig.NetworkMode}}'` — если `bridge` (дефолтная), встроенного DNS нет, только IP. 2) Резолвер: `docker exec <c> cat /etc/resolv.conf` — `nameserver 127.0.0.11` означает пользовательскую сеть. 3) Путь приложения: `getent hosts <name>` (через NSS и `/etc/hosts`), а не `dig` (обходит `/etc/hosts`). 4) Алиас объявлен в той же сети.

**Q: Что такое `docker events` для сетевой диагностики?**
A: Поток событий жизненного цикла в реальном времени. Сетевые события: `docker events --filter type=network --filter event=connect` — отслеживание подключений контейнеров к сетям. Полный разбор: [Отладка с помощью Docker Events](../Docker_troubleshooting/debugging_with_docker_events.md).

## Продакшен

**Q: Какой лимит контейнеров в одной bridge-сети?**
A: 1000 контейнеров. Из-за ограничений ядра Linux bridge-сети становятся нестабильными, связь между контейнерами начинает рваться при 1000+ (moby/moby#44973). Это свойство архитектуры, не аварийная ситуация: планируйте шардирование по сетям заранее.

**Q: Как планировать адресное пространство на крупных хостах?**
A: `default-address-pools` в `daemon.json` — иначе подсети выделяются из пула по умолчанию (`172.17.0.0/16` и далее) и могут пересечься с корпоративными диапазонами. Задавайте `--subnet` явно при создании сети. Подробно: [IPAM и планирование подсетей](./docker_network_ipam_scale.md).

**Q: Что меняется в rootless-режиме?**
A: Демон работает внутри user namespace и RootlessKit, сетевой стек реализуется в userspace (`slirp4netns` → `pasta` → `vpnkit` → `gvisor-tap-vsock`; с 29.5 дефолт `gvisor-tap-vsock`). MTU по умолчанию 65520 (не 1500). Демон не может менять `iptables`/`nftables` хоста — `DOCKER-USER` может отсутствовать. Проброс Source IP требует RootlessKit v3.0+ и отключённого `userland-proxy`.

**Q: Что нужно знать перед обновлением до Engine 28+?**
A: С 28.0 Docker блокирует direct routing к неопубликованным портам (правило в `raw` PREROUTING с 28.2) — инфраструктура, обращавшаяся к IP контейнеров напрямую, перестанет работать. Режимы `nat-unprotected` и `isolated` появились в 28.0; `routed` стал рабочим в 28.0. Бэкенд `nftables` (29.0, экспериментальный) нельзя включать на узле с работающим Swarm.
