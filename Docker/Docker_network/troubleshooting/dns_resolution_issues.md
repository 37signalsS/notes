# Решение проблем с DNS в Docker (Troubleshooting)

## Определения

- **DNS (Domain Name System)** — система доменных имён, преобразующая буквенные имена хостов в IP-адреса.
- **Встроенный DNS-сервер Docker (Embedded DNS)** — локальный резолвер на адресе **`127.0.0.11`**, работающий в пользовательских сетях. Он отвечает за Service Discovery и проксирование внешних запросов.
- **ndots** — параметр конфигурации резолвера, определяющий количество точек в имени, при котором оно считается абсолютным (FQDN) и не дополняется доменами из списка `search`.

## Основные концепции

### Взаимодействие с хостом (systemd-resolved)

В современных дистрибутивах (Ubuntu, Debian, RHEL) DNS управляется службой `systemd-resolved`, которая предоставляет заглушку на `127.0.0.53`.

**Критическая проблема:**
Docker Engine по умолчанию пытается копировать `/etc/resolv.conf` хоста. Если в нем указан `127.0.0.53`, Docker обнаруживает это (так как этот адрес не будет работать внутри контейнера) и автоматически подставляет публичные DNS (`8.8.8.8`, `9.9.9.9`).
- **Последствие:** Контейнер теряет доступ к внутренним доменам компании, которые разрешаются только через корпоративные DNS-серверы.

### Параметр ndots: разница между Docker и Kubernetes

Это одна из самых частых причин "медленного DNS":
- **В Docker (по умолчанию):** используется `ndots:0`. Имена сразу запрашиваются как абсолютные.
- **В Kubernetes (по умолчанию):** используется `ndots:5`. Любое имя с числом точек меньше 5 (например, `google.com`) сначала дополняется всеми локальными суффиксами поиска, что порождает каскад лишних запросов.

**Важно:** Если Docker копирует `resolv.conf` с хоста, где установлено `ndots:5`, контейнер унаследует это поведение, что приведет к задержкам до 500 мс на каждый новый запрос.

### Проблемы IPv6 и "Happy Eyeballs"

Современные библиотеки (glibc, Go) запрашивают одновременно записи `A` (IPv4) и `AAAA` (IPv6). Если сетевое оборудование или DNS-апстрим некорректно обрабатывает IPv6-запросы (отбрасывает их вместо ответа `NXDOMAIN`), приложение будет "висеть" до наступления таймаута (обычно 5 секунд).

## Практические сценарии

### Сценарий 1: Диагностика резолвера ( netshoot)

Если стандартный `nslookup` не дает ответа, используйте расширенную диагностику.

```bash
# 1. Запуск диагностического контейнера в сети проблемного приложения
docker run --rm -it --network <network_name> nicolaka/netshoot

# 2. Проверка прохождения запросов с трассировкой
dig +trace google.com

# 3. Проверка конкретно встроенного DNS Docker
dig @127.0.0.11 <container_name>
```

### Сценарий 2: Решение проблем в корпоративной сети / VPN

**Симптом:** Контейнер пингует `google.com`, но не видит `gitlab.company.local`.

**Решение:** Принудительное указание корпоративных DNS-серверов в `daemon.json` (применяется ко всем контейнерам) или через флаги запуска.

```json
// /etc/docker/daemon.json
{
  "dns": ["10.0.0.10", "10.0.0.11"],
  "dns-search": ["company.local", "dev.internal"]
}
```

### Сценарий 3: Оптимизация таймаутов (ndots и параллелизм)

Если приложение выполняет много внешних запросов, оптимизируйте настройки резолвера.

```yaml
# docker-compose.yml
services:
  api:
    image: my-app:latest
    dns_opt:
      - ndots:1
      - timeout:2
      - attempts:2
      - single-request-reopen # Решает проблемы с некорректными NAT/Firewalls
```

### Сценарий 4: Таймауты AAAA (IPv6) в сетях без IPv6

**Симптом:** `curl` работает мгновенно с флагом `-4`, но без него "задумывается" на 5 секунд.

**Решение:**
1. Настройте `dns_opt: ["single-request-reopen"]`.
2. Если проблема сохраняется, а IPv6 не нужен, отключите его на уровне ядра в контейнере (через `sysctls`) или используйте прокси-резолвер.

## Дополнительная информация

### Чеклист диагностики 2026

1. **Версия Docker:** В версии 29.1.0 был обнаружен регресс в обработке DNS-кэша. Рекомендуется обновиться до **29.1.1+**.
2. **Alpine Linux:** Помните, что Alpine использует `musl libc`, которая выполняет запросы A и AAAA параллельно по UDP и не поддерживает параметр `options rotate`.
3. **Конфликты с локальным кэшем:** Если на хосте запущен `dnsmasq` или `unbound` на интерфейсе `docker0`, убедитесь, что они не блокируют запросы от подсетей контейнеров.
4. **MTU:** Слишком большой MTU в сети (особенно в VPN/Overlay) может приводить к тому, что большие DNS-ответы (например, с множеством IP или DNSSEC) будут отбрасываться. Установите MTU 1450 для проверки.
