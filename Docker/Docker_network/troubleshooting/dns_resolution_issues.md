# Решение проблем с DNS в Docker (Troubleshooting)

## Определения

**DNS (Domain Name System)** — система доменных имён, преобразующая имена хостов в IP-адреса.

**Встроенный DNS-сервер Docker (Embedded DNS)** — локальный резолвер, доступный внутри контейнеров по адресу **`127.0.0.11`**. Он обеспечивает:
1. Разрешение имён контейнеров по их названиям или алиасам (Service Discovery).
2. Проксирование запросов к внешним DNS-серверам хост-системы.

**Проблемы с DNS** — ситуации, когда приложение внутри контейнера не может разрешить внешние или внутренние доменные имена, что приводит к ошибкам связности.

---

## Основные концепции

### Взаимодействие с хостом (systemd-resolved)

Большинство современных Linux-дистрибутивов используют `systemd-resolved`, который создаёт заглушку-резолвер на `127.0.0.53`.

**Ловушка:** Docker часто копирует `/etc/resolv.conf` хоста в контейнер. Если там указан `127.0.0.53`, контейнер пытается обратиться к самому себе (loopback), где DNS-сервера нет. Docker Engine пытается автоматически исправлять это, подставляя общедоступные DNS (8.8.8.8), но это не всегда работает в корпоративных сетях или за VPN.

### Параметр ndots и производительность

Опция `ndots` определяет количество точек в имени, после которого оно считается абсолютным (FQDN).
- По умолчанию в Docker часто наследуется `ndots:5`.
- Если вы ищете `google.com` (1 точка), резолвер сначала добавит все домены поиска (search domains) из конфигурации, что порождает цепочку лишних запросов и задержки до 100–500 мс.

### Проблемы IPv6 (AAAA записи)

Современные приложения (Node.js, Go) используют алгоритм "Happy Eyeballs", запрашивая одновременно `A` (IPv4) и `AAAA` (IPv6) записи. Если встроенный DNS Docker некорректно обрабатывает IPv6-запросы, это может привести к таймаутам, даже если IPv4 работает исправно.

## Практические сценарии

### Сценарий 1: Диагностика резолвера

**Задача:** Проверить, какой DNS-сервер видит контейнер и как он работает.

```bash
# 1. Проверка конфигурации внутри контейнера
docker exec my_container cat /etc/resolv.conf
# → nameserver 127.0.0.11

# 2. Тест разрешения имени с детализацией
docker exec my_container dig +short google.com
# → 142.250.185.142

# 3. Проверка времени ответа
time docker exec my_container getent hosts ya.ru
# → 87.250.250.242 ya.ru
# → real 0m0.050s (Если >0.5s — проблема в ndots или таймаутах вышестоящих серверов)
```

### Сценарий 2: Конфликт с systemd-resolved

**Симптом:** `ping google.com` выдаёт `Temporary failure in name resolution`, а `cat /etc/resolv.conf` внутри контейнера показывает `nameserver 127.0.0.53`.

**Решение:** Укажите Docker-демону использовать "честный" `resolv.conf` системы, который содержит реальные IP-адреса апстримов.

```json
# /etc/docker/daemon.json
{
  "dns": ["1.1.1.1", "8.8.8.8"]
}
```
Или при запуске:
```bash
docker run --dns 8.8.8.8 my_image
```

### Сценарий 3: Оптимизация ndots (DNS Lookup Storms)

**Симптом:** Приложение работает медленно при каждом первом сетевом запросе к новому хосту.

**Решение:** Установите `ndots:1` в настройках контейнера.

```yaml
# docker-compose.yml
services:
  app:
    image: my-app
    dns_opt:
      - ndots:1
```

**Лайфхак:** Используйте точку в конце имени в коде приложения (`google.com.`), чтобы сразу указать на абсолютное имя.

### Сценарий 4: Таймауты из-за IPv6 (AAAA)

**Симптом:** Команда `curl` внутри контейнера "висит" несколько секунд перед началом загрузки.

**Диагностика:**
```bash
# Принудительный запрос IPv4
docker exec my_container curl -4 -v https://google.com
# Если -4 работает мгновенно, а без него — висит, проблема в IPv6.
```

**Решение:** Если IPv6 не настроен на хосте/в Docker, принудительно отключите его или настройте `dns-opt: ["single-request-reopen"]` (решает проблемы с некоторыми файрволами, которые плохо обрабатывают параллельные запросы A/AAAA).

## Дополнительная информация

### Чеклист диагностики 2026
1. Проверить версию: Docker 29.1.0 имел баг с DNS, обновитесь до **29.1.1+**.
2. Проверить `resolv.conf`: нет ли там `127.0.0.53` или `::1`.
3. Использовать `netshoot`: `docker run --rm -it --net container:<id> nicolaka/netshoot` для глубокой отладки (tcpdump, dig).
4. Проверить `daemon.json`: настройки `dns` и `dns-opts` должны быть валидными.
