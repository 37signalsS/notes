# Решение проблем с DNS в Docker

**Актуально для:** Docker Engine 29.x

## Определения

- **DNS (Domain Name System)** — система доменных имён, преобразующая буквенные имена хостов в IP-адреса.
- **Встроенный DNS-сервер Docker (Embedded DNS)** — локальный резолвер на адресе **`127.0.0.11`**, работающий в сетевом пространстве имён контейнера, подключённого к пользовательской (user-defined) сети. Он отвечает за Service Discovery и проксирует внешние запросы на upstream-серверы. Адрес выбран внутри диапазона `127.0.0.0/8` намеренно: этот блок является loopback-only, поэтому резолвер недоступен из других контейнеров и с хоста, а маршрутными изменениями его нельзя перехватить. IPv6-эквивалента нет — адрес `127.0.0.11` работает даже в контейнерах, работающих только по IPv6.
- **Upstream DNS (внешние серверы)** — серверы, в которые встроенный резолвер пересылает запросы, не найденные среди контейнеров. Docker берёт их из `/etc/resolv.conf` хоста либо из переопределений `--dns` / `"dns"`.
- **Legacy-режим (сеть `bridge` по умолчанию)** — поведение, при котором контейнер получает **копию** `/etc/resolv.conf` хоста и обращается к upstream напрямую, минуя встроенный резолвер.
- **Internal resolver mode** — поведение контейнеров в пользовательских сетях: `nameserver 127.0.0.11`, все запросы проходят через демон Docker.
- **ndots** — порог числа точек в имени, при котором оно считается абсолютным (FQDN) и не дополняется доменами из списка `search`.
- **resolv.conf (в контейнере)** — файл, генерируемый Docker Engine. Он содержит комментарии-трассировку (`# Based on host file`, `# Overrides`, `# Option ndots from`), которые указывают, каким источником взято каждое значение, и потому являются первым местом, где нужно искать причину сбоя.

## Как это работает

### Два пути, по которым формируется `/etc/resolv.conf` в контейнере

Docker Engine реализует **два принципиально разных механизма**, и путать их — источник большинства ошибочных диагнозов.

| | Сеть `bridge` по умолчанию (legacy) | Пользовательская сеть (internal resolver) |
| :--- | :--- | :--- |
| `nameserver` в `resolv.conf` | Адреса upstream напрямую из файла хоста | `127.0.0.11` |
| Маркер в комментариях | `# Based on host file: '...' (legacy)` | `# Based on host file: '...' (internal resolver)` |
| Service Discovery по имени контейнера | **Не работает** | Работает (имя контейнера, сетевой алиас) |
| Обработка нескольких upstream-серверов | Решает **клиентская** резолверная библиотека приложения | Демон Docker: опрашивает **последовательно**, останавливаясь на успехе или `NXDOMAIN` |
| Куда уходят запросы | Из сетевого пространства контейнера | Loopback-адреса — из сетевого пространства **хоста** |

Практический вывод: в legacy-режиме musl опрашивает все серверы параллельно и берёт первый ответ, тогда как во встроенном резолвере Docker опрашивает их по очереди. Поэтому один и тот же список `nameserver`, объявленный через `daemon.json`, ведёт себя по-разному в зависимости от типа сети.

### Порядок разрешения имени во встроенном резолвере

1. Демон получает запрос и определяет его тип.
2. Для `A`, `AAAA`, `MX`, `PTR`, `SRV` выполняется поиск по реестру подключённых контейнеров. Если запись найдена — ответ формируется локально, upstream **не опрашивается**.
3. Если локальной записи нет, выполняется проксирование на upstream.
4. Демон опрашивает серверы последовательно. `SERVFAIL` или `REFUSED` от сервера переключают на следующий; успешный ответ завершает цепочку. `NXDOMAIN` завершает её **только если ответ авторитетный** (флаг `AA`, RFC 8020) — неавторитетный `NXDOMAIN` от сервера-кэша переключает на следующий сервер.
5. Если ни один сервер не ответил, клиент получает `SERVFAIL`.

**Ответы на имена контейнеров имеют TTL 600 секунд** (`respTTL` в коде демона). Это не «TTL 0»: приложения вправе кэшировать адрес до 10 минут. Если этого недостаточно, помогает healthcheck, который проверяет разрешение имени, — иначе смена IP контейнера обнаруживается только по факту отказа приложения.

Обратите внимание на обработку `MX`: если имя найдено среди контейнеров, Docker отвечает пустым списком с кодом `NOERROR`, чтобы почтовый клиент трактовал это как «implicit MX» (RFC 5321, раздел 5.1) и выполнил отдельный запрос `A`/`AAAA`.

### Специальное поведение при явно заданном ndots

Если пользователь задал `ndots` со значением больше нуля, встроенный резолвер **не проксирует одноуровневые имена** (без точек) на upstream и возвращает пустой успешный ответ. Логика: клиент должен повторить запрос, присоединив домен из `search`. Это защищает от отправки во внешний мир запросов вида `db`, `redis`, `api`, которые без `search` бессмысленны и являются удобным вектором DNS-туннелирования.

Побочный эффект: при `ndots > 0` имя `example.com` (одна точка) сначала будет опробовано с каждым суффиксом из `search`, и только потом — как есть. Поэтому для сетей, где внутренние имена короткие, `ndots` стоит держать равным 0 (значение по умолчанию).

### Лимиты встроенного резолвера

Демон Docker ограничивает исходящую нагрузку, и при превышении лимита клиент получает `REFUSED`, а не таймаут:

| Параметр | Значение | Поведение при превышении |
| :--- | :--- | :--- |
| Максимум upstream-серверов | 3 | Лишние игнорируются |
| Таймаут обмена с upstream | 4 с | Переход к следующему серверу |
| Одновременных внешних запросов | 1024 | `REFUSED` клиенту, в лог — `[resolver] more than 1024 concurrent queries` |
| TTL локальных ответов | 600 с | — |

Практическое следствие: если в логах демона появляется сообщение о 1024 одновременных запросах, проблема не в сети — это локальный всплеск нагрузки, и лечится кэшированием на стороне приложения, а не тюнингом таймаутов.

### Взаимодействие с systemd-resolved

В современных дистрибутивах (Ubuntu, Debian, RHEL, Fedora) DNS управляется службой `systemd-resolved`, которая предоставляет **заглушку (stub)** на `127.0.0.53`. Этот адрес имеет смысл только в сетевом пространстве хоста.

Docker **не подставляет** `127.0.0.11` и не «заменяет» его на публичные DNS. Механизм следующий:

1. Если в `/etc/resolv.conf` хоста указан **ровно один** nameserver и это `127.0.0.53`, libnetwork считает, что DNS обслуживает `systemd-resolved`, и читает **другой** файл — `/run/systemd/resolve/resolv.conf`, который содержит реальные upstream-адреса. В лог демона при этом пишется:
   ```text
   detected 127.0.0.53 nameserver, assuming systemd-resolved, so using resolv.conf: /run/systemd/resolve/resolv.conf
   ```
2. Loopback-адреса (`127.*`, `::1`) удаляются из итогового `resolv.conf` контейнера — в его сетевом пространстве они бесполезны.
3. **Только если после этого не осталось ни одного nameserver**, добавляются серверы Google по умолчанию:
   - IPv4: `8.8.8.8`, `8.8.4.4`
   - IPv6 (только если IPv6 включён): `2001:4860:4860::8888`, `2001:4860:4860::8844`

   В лог при этом пишется `No non-localhost DNS nameservers are left in resolv.conf. Using default external servers: ...`.

**Когда это происходит начиная с Docker 28.0.** Начиная с этой версии адреса, прочитанные из `/etc/resolv.conf` хоста, всегда опрашиваются **из сетевого пространства хоста**, а fallback на серверы Google для сетей со встроенным резолвером отменён. Google DNS остаётся только для сети `bridge` по умолчанию и для контейнеров сборки (`buildkit`, у которых нет встроенного резолвера).

Практическое следствие: если после обновления до 28.x контейнеры в пользовательских сетях перестали резолвить внешние имена, проверьте, что `/etc/resolv.conf` хоста вообще существует. Известный случай — оборванная символическая ссылка на `stub-resolv.conf` или отключённый `systemd-resolved`: файл отсутствует, upstream-серверы не выявляются, и `resolv.conf` контейнера остаётся практически пустым:

```bash
# → Broken symbolic link to /run/systemd/resolve/stub-resolv.conf
ls -la /etc/resolv.conf

# → nameserver 127.0.0.53
grep ^nameserver /run/systemd/resolve/resolv.conf
```

Адреса из `--dns` ведут себя иначе: они опрашиваются **из сетевого пространства контейнера**. Поэтому указать в `daemon.json` DNS-сервер, доступный только через VPN-туннель хоста, неработоспособно — из контейнера маршрута к нему нет.

### Параметр ndots: разница между Docker и Kubernetes

Это одна из самых частых причин «медленного DNS» при переносе нагрузок между платформами.

- **В Docker (по умолчанию):** `ndots:0`. Любое имя запрашивается как есть, без предварительного перебора суффиксов. Значение выставляет сам демон — в `resolv.conf` это видно по комментарию `# Option ndots from: internal`.
- **В Kubernetes (по умолчанию):** `ndots:5`. Имя с числом точек меньше пяти сначала дополняется всеми локальными суффиксами из `search`, что порождает каскад лишних запросов к CoreDNS.

Если в `resolv.conf` контейнера стоит `ndots:5`, Docker не переопределяет это значение. Причина почти всегда одна: в `daemon.json` задан ключ `"dns-opts"`, либо у контейнера переопределён поиск. Проверить происхождение значения можно по комментарию-трассировке: `# Option ndots from: override` означает явное переопределение, `# Option ndots from: internal` — значение по умолчанию от демона.

### IPv6, запросы A/AAAA и разница между glibc и musl

Современные резолверные библиотеки запрашивают записи `A` и `AAAA` одновременно. Если сетевое оборудование, NAT или DNS-апстрим некорректно обрабатывает пару запросов с одного порта, приложение будет ждать таймаут по умолчанию — 5 секунд.

**glibc** (Debian, Ubuntu, RHEL, CentOS, все образы на `glibc`):

- Начиная с glibc 2.9 запросы `A` и `AAAA` выполняются параллельно **с одного сокета**.
- `single-request-reopen` (с glibc 2.9) — при неполучении второго ответа сокет закрывается и открывается заново перед следующим запросом. Это обходной путь для оборудования, возвращающего ответ только на один из двух запросов.
- `single-request` (с glibc 2.10) — запросы выполняются **последовательно**, цена — замедление резолвинга.
- Поддерживает `rotate` — циклический выбор сервера из списка, распределяющий нагрузку.
- Значения опций молча ограничиваются: `ndots` — 15, `timeout` — 30, `attempts` — 5.

**musl** (Alpine Linux и все образы на `alpine`):

- **Не поддерживает `single-request` и `single-request-reopen` вообще.** Это не «отключаемая» опция — резолвер их не читает. Указание `dns_opt: ["single-request-reopen"]` в сервисе на Alpine не даёт никакого эффекта.
- Поддерживает из опций только `ndots`, `attempts` и `timeout`; `rotate` и `edns0` игнорируются. Значения ограничиваются жёстче: `ndots` — 15, `attempts` — 10, `timeout` — 60.
- Опрашивает **все** nameserver'ы параллельно и принимает первый ответ, даже если он `NXDOMAIN`, пока не отвечают остальные. Максимум три сервера.
- Отправляет `A` и `AAAA` параллельно с одного сокета — так же, как glibc, но изменить это поведение средствами `resolv.conf` нельзя.

Отсюда практическое правило: **если образ на Alpine, проблему нельзя решить опцией в `resolv.conf`**. Варианты — перейти на базовый образ на glibc, добавить локальный кэширующий резолвер со стороны хоста, либо смириться с особенностью NAT/оборудования.

## Практические сценарии

### Сценарий 1: Базовая диагностика — с чего начинать

Прежде чем менять конфигурацию, нужно установить, **в каком режиме находится контейнер** и работает ли DNS на хосте. Почти все дальнейшие развилки зависят от этих двух ответов.

```bash
# 1. Тип сети и режим резолвера
docker inspect <container> --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{"\n"}}{{end}}'
# → Если в выводе только "bridge" — это legacy-режим, встроенного DNS нет.
# → Любая пользовательская сеть означает internal resolver.

# 2. Что именно записано в resolv.conf контейнера
docker exec <container> cat /etc/resolv.conf
# Ожидаемый результат для пользовательской сети:
#   # Based on host file: '/etc/resolv.conf' (internal resolver)
#   # ExtServers: [host(10.0.0.2)]
#   nameserver 127.0.0.11
#   options ndots:0
# Ожидаемый результат для сети bridge:
#   # Based on host file: '/etc/resolv.conf' (legacy)
#   nameserver 10.0.0.2

# 3. Работает ли DNS на хосте — если нет, это не проблема Docker
getent hosts example.com
# → example.com has address 93.184.216.34

# 4. Проверка тем же путём, каким пойдёт приложение (NSS + /etc/hosts)
docker exec <container> getent hosts example.com
# → example.com has address 93.184.216.34
```

**Почему `getent hosts`, а не `nslookup`:** `getent` проходит через `getaddrinfo`, `nsswitch.conf` и `/etc/hosts` — тот же путь, что и приложение. `nslookup` и `dig` обращаются к DNS напрямую и намеренно **обходят** `/etc/hosts` и NSS. Расхождение результатов — само по себе диагностический сигнал: если `nslookup` падает, а `getent` работает, ответ даёт `/etc/hosts` (то есть `--add-host` или `extra_hosts`), а не DNS.

### Сценарий 2: Расширенная диагностика (netshoot)

Если в образе нет `dig`, `nslookup` или `curl`, запускается диагностический контейнер в **той же сети**, что и проблемный.

```bash
# Запуск в сети проблемного приложения
docker run --rm -it --network <network_name> nicolaka/netshoot

# Внутри контейнера:

# 1. Опрос именно того резолвера, который есть в приложении
dig @127.0.0.11 <container_name>
# → Для имени контейнера: найдена запись A
# → Для внешнего имени: 93.184.216.34

# 2. Сравнение с прямым обращением к upstream
dig @10.0.0.2 example.com
# → Если здесь ответ есть, а через 127.0.0.11 — SERVFAIL,
#   проблема в цепочке проброса, а не в upstream

# 3. Проверка конкретного upstream-сервера изнутри namespaces контейнера
dig +trace example.com
# → Трассировка иерархии. Внутри контейнера часто не проходит:
#   требуется исходящий UDP/53 к корневым серверам, который обычно закрыт.
#   В этом случае используйте dig @<upstream> без +trace.

# 4. Проверка достижимости порта 53 по TCP (многие сети фильтруют только UDP)
nc -zv <upstream_ip> 53
```

Альтернативный способ зайти в то же сетевое пространство имён, что и у работающего контейнера, — подключить netshoot к нему напрямую:

```bash
docker run --rm -it --net container:<container_id> nicolaka/netshoot
```

### Сценарий 3: Корпоративный DNS и VPN

**Симптом:** контейнер разрешает `example.com`, но не видит `gitlab.company.local`. С хоста то же имя разрешается.

**Диагностика.** Сравните, что видит хост и что попало в контейнер:

```bash
# На хосте
grep ^nameserver /etc/resolv.conf
# → nameserver 127.0.0.53

# Реальные upstream-серверы, которые знает systemd-resolved
grep ^nameserver /run/systemd/resolve/resolv.conf
# → nameserver 10.0.0.10
# → nameserver 10.0.0.11

# В контейнере
docker exec <container> cat /etc/resolv.conf
# → nameserver 127.0.0.11
# → # ExtServers: [host(10.0.0.10) host(10.0.0.11)]
```

Если в строке `ExtServers` корпоративных серверов нет, демон не смог их выявить. Демон использует **не более трёх** upstream-серверов, и они должны быть достижимы из сетевого пространства хоста.

**Решение 1 — указать серверы явно (для всех контейнеров на хосте):**

```json
// /etc/docker/daemon.json
{
  "dns": ["10.0.0.10", "10.0.0.11"],
  "dns-search": ["company.local", "dev.internal"]
}
```

```bash
sudo systemctl restart docker

# Проверка: пересоздание контейнера обязательно,
# файл resolv.conf генерируется при создании
docker compose up -d --force-recreate
docker exec <container> cat /etc/resolv.conf
# → # Overrides: [nameservers]
# → nameserver 10.0.0.10
# → nameserver 10.0.0.11
# → search company.local dev.internal
```

**Решение 2 — для отдельного контейнера или сервиса:**

```bash
docker run -d --dns 10.0.0.10 --dns 10.0.0.11 \
  --dns-search company.local myapp
```

```yaml
# docker-compose.yml
services:
  api:
    image: my-app
    dns:
      - 10.0.0.10
      - 10.0.0.11
    dns_search:
      - company.local
```

**Важные ограничения:**

- В режиме `host` и `container:<id>` флаги `--dns`, `--dns-search`, `--dns-option` **не поддерживаются**: контейнер не создастся, демон вернёт ошибку `conflicting options: dns and the network mode`. Контейнер делит сетевое пространство, а значит и резолвер, с хостом или с другим контейнером.
- `--dns` опрашивается из сетевого пространства **контейнера**. VPN-сервер, доступный с хоста только через его интерфейс туннеля, из контейнера недоступен.
- `--dns-search` **не** стирает `search`, унаследованный от хоста, если не переопределён явно. Чтобы убрать все домены поиска, укажите одну точку: `--dns-search=.`
- `--dns` переопределяет только `nameserver`. Для `search` и `options` нужны отдельные флаги — либо соответствующие ключи `"dns-search"` и `"dns-opts"` в `daemon.json`.

### Сценарий 4: `SERVFAIL` от 127.0.0.11 при работающем DNS на хосте

**Симптом:** `nslookup` внутри контейнера возвращает `server can't find ...: SERVFAIL`, при этом на хосте то же имя разрешается.

**Диагностика по логам демона:**

```bash
sudo journalctl -u docker --since "10 min ago" | grep -i resolver
```

Типичные сообщения и их смысл:

| Сообщение | Причина |
| :--- | :--- |
| `No non-localhost DNS nameservers are left in resolv.conf. Using default external servers: ...` | На хосте нет ни одного не-loopback nameserver. Обычно оборвана ссылка `/etc/resolv.conf` или отключён `systemd-resolved`. |
| `detected 127.0.0.53 nameserver, assuming systemd-resolved, so using resolv.conf: /run/systemd/resolve/resolv.conf` | Информационное сообщение. Демон прочитал корректный файл. Если следом идёт `SERVFAIL` — смотрите следующую строку. |
| `[resolver] failed to query external DNS server ... i/o timeout` | Upstream не отвечает из сетевого пространства хоста. Проверяйте маршруты и firewall. |
| `[resolver] external DNS 10.0.0.10:53 returned failure` | Upstream ответил `SERVFAIL` или `REFUSED`; демон переключился на следующий. Если все три вернули отказ — смотрите их логи. |
| `[resolver] more than 1024 concurrent queries` | Исчерпан лимит одновременных внешних запросов. Проблема в нагрузке, а не в сети. |

**Известная регрессия: Docker 29.1.0.** Эта версия ломала разрешение **внешних** имён на всех пользовательских bridge-сетях. Механизм: при обновлении движок ошибочно считал `/etc/resolv.conf` существующих контейнеров изменённым пользователем (хеш-файл рассинхронизирован с содержимым, записанным предыдущей версией), из-за чего пропускал и копирование файла хоста, и — что важно — извлечение списка upstream-серверов во встроенный резолвер. Результат выглядел обманчиво: `resolv.conf` содержал корректный `nameserver 127.0.0.11`, но список внешних серверов оставался пустым, и любой запрос наружу возвращал `SERVFAIL`. Имена контейнеров продолжали разрешаться, поэтому симптом выглядел как «внутренние имена работают, внешние нет».

Исправлено в **29.1.1** (28 ноября 2025) откатом PR moby/moby#51615. Обходной путь без обновления — пересоздать контейнеры (`docker compose down && docker compose up -d`); перезапуск демона или контейнера сам по себе не помогает.

**Проверка наличия регрессии:**

```bash
docker network create test-net
docker run --rm --network test-net alpine:3 nslookup example.com
docker run --rm --network bridge alpine:3 nslookup example.com
# → Если на test-net NXDOMAIN/SERVFAIL, а на bridge всё работает,
#   и версия движка 29.1.0 — это именно эта регрессия
docker network rm test-net
```

### Сценарий 5: Задержки 5 секунд и проблемы A/AAAA (Happy Eyeballs)

**Симптом:** `curl -4` работает мгновенно, а без флага «задумывается» примерно на 5 секунд. Или: соединение устанавливается, но зависает на чтении.

**Диагностика:**

```bash
# Сравнить время ответа с IPv4 и без ограничений
docker exec <container> time nslookup example.com
docker exec <container> curl -4 -sS -o /dev/null -w '%{time_total}\n' https://example.com
# → 0.02 (IPv4)
# → 5.01 (без -4)

# Проверить, доходят ли оба запроса
dig +short A example.com
dig +short AAAA example.com
# → Если AAAA приходит, а A — нет (или наоборот),
#   проблема в обработке пары запросов с одного порта
```

**Решение для образов на glibc:**

```yaml
# docker-compose.yml
services:
  api:
    image: my-app
    dns_opt:
      - timeout:2
      - attempts:2
      - single-request-reopen
```

`single-request-reopen` закрывает и заново открывает сокет, если на два запроса с одного порта пришёл только один ответ. `single-request` делает запросы последовательно — вариант более надёжный, но с замедлением; в Docker Compose он указывается так же, через `dns_opt`.

**Для образов на Alpine (musl) этих опций не существует.** Работающие альтернативы:

1. **Сменить базовый образ** на дистрибутив с glibc. Это единственное решение, устраняющее саму причину.
2. **Локальный кэширующий резолвер на хосте** (например, `dnsmasq` или `unbound`), слушающий не только `127.0.0.1`, но и адрес моста Docker, и указанный через `daemon.json`. Помогает с задержками, но не с параллельностью запросов.
3. **Явно отключить IPv6 в контейнере**, если сеть IPv6 не используется и запросы AAAA не нужны:
   ```yaml
   services:
     api:
       image: my-app
       sysctls:
         net.ipv6.conf.all.disable_ipv6: "1"
   ```
   Это убирает сами запросы `AAAA`, а не задержку на них. Требует, чтобы базовая ОС действительно собиралась с поддержкой IPv6, иначе sysctl недоступен.

**Ограничения `sysctls` в Docker:** разрешён только набор параметров, безопасный для namespaced-контейнеров. Попытка выставить параметр вне этого набора приводит к ошибке запуска контейнера, а не к тихому игнорированию.

### Сценарий 6: Имена контейнеров не разрешаются

**Симптом:** в пользовательской сети `nslookup <container_name>` возвращает `NXDOMAIN`, хотя контейнер запущен и виден в `docker ps`.

**Причина 1 — контейнер в сети `bridge` по умолчанию.** Встроенного резолвера на этой сети нет, имена контейнеров не разворачиваются никогда. Выход — перенести контейнер в пользовательскую сеть:

```bash
docker network create app-net
docker network connect app-net <container>
```

**Причина 2 — контейнеры в разных сетях.** Service Discovery работает только внутри одной сети; имя из другой сети не видно, а запрос уходит на upstream и возвращает `NXDOMAIN`.

**Причина 3 — `ndots` переопределён вверх.** В этом случае одноуровневое имя не проксируется, а клиент получает пустой успешный ответ, который `dig` показывает как ответ без записей. Проверьте комментарий `# Option ndots from: override` в `resolv.conf`.

**Проверка:**

```bash
docker network inspect app-net --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
# → api 172.18.0.3/16

docker run --rm --network app-net alpine:3 nslookup api
# → Name:    api
# → Address: 172.18.0.3

# Псевдонимы видны только в своей сети
docker inspect api --format '{{json .NetworkSettings.Networks}}'
```

### Сценарий 7: DNS при сборке образов

Контейнеры сборки (`buildkit`) **не имеют встроенного резолвера** — в отличие от контейнеров в пользовательских сетях, они идут по legacy-пути. Поэтому серверы Google по умолчанию применяются к ним даже начиная с Docker 28.

Симптом проявляется на этапе `RUN`, когда нужно обратиться к внешнему адресу:

```bash
docker build --network=host -t my-app .
# → Запросы резолвятся в сетевом пространстве хоста,
#   где /etc/resolv.conf всегда корректен
```

Для buildkit с билдером `docker-container`:

```bash
docker buildx create --driver docker-container --use
docker buildx build --network=host -t my-app .
```

Альтернатива — задать адреса DNS на уровне сборки через конфигурацию билдера (`buildkitd.toml`), но `--network=host` проще и покрывает большинство случаев, включая обращения к корпоративным серверам.

## Best Practices

### Конфигурация

1. **Никаких production-контейнеров в сети `bridge` по умолчанию.** Встроенного резолвера и Service Discovery там нет. В Docker Compose пользовательская сеть создаётся автоматически; при `docker run` нужен явный `--network`.

2. **Указывайте корпоративные DNS явно, а не полагайтесь на наследование от хоста.** Наследование работает не всегда: демон читает `/run/systemd/resolve/resolv.conf`, а не `/etc/resolv.conf`, и берёт не более трёх серверов. Явное перечисление в `daemon.json` — воспроизводимая конфигурация, а не результат состояния systemd на конкретной машине.

3. **Проверяйте доступность upstream из сетевого пространства контейнера, а не с хоста.** Адреса из `--dns` опрашиваются изнутри контейнера, адреса из файла хоста — с хоста. Для VPN-сетей это принципиально.

4. **Не редактируйте `/etc/resolv.conf` в работающем контейнере как метод правки.** Docker перезапишет файл при пересоздании, а диагностировать расхождение будет сложно. Используйте `daemon.json`, `--dns` или Compose.

5. **Оставляйте `ndots:0` для внешних доменов.** В Docker это значение по умолчанию, и менять его стоит только подтверждённым замером: каждый лишний суффикс из `search` — это дополнительный запрос к upstream на каждое разрешение.

6. **Держите число upstream-серверов не больше трёх.** Демон всё равно использует не более трёх, а лишние записи в `daemon.json` создают ложное ощущение резервирования.

7. **Для образов на Alpine помните о невозможности решить проблему опцией `resolv.conf`.** `single-request-reopen` и `single-request` musl не поддерживает. Если проявления некорректной обработки A/AAA нельзя устранить на уровне сети, меняйте базовый образ.

### Диагностика и наблюдаемость

1. **Валидация после любого изменения** — полный цикл: пересоздать контейнер, прочитать `resolv.conf`, проверить разрешение через `getent hosts`, затем замерить задержку.

   ```bash
   docker compose up -d --force-recreate
   docker exec <container> cat /etc/resolv.conf
   docker exec <container> getent hosts example.com
   for i in 1 2 3 4 5; do
     docker exec <container> nslookup example.com >/dev/null && echo ok
   done
   ```

2. **Держите `journalctl -u docker` с фильтром по `[resolver]`** под рукой при разборе инцидентов. Сообщения демона однозначно указывают направление поиска: неизвестный upstream, отказ upstream, исчерпание лимита.

3. **Добавьте healthcheck, проверяющий разрешение имени**, если приложение обращается к соседнему сервису по имени. Иначе смена адреса контейнера обнаруживается только по лавине ошибок в приложении, а не как отказ одного контейнера.

4. **Проверяйте обновления движка в staging на реальной нагрузке.** Регрессия 29.1.0 затронула только контейнеры, созданные предыдущей версией, и только на пользовательских сетях, — то есть ровно тот случай, когда функциональные тесты на свежей установке проходят, а production ломается. Тест, воспроизводящий регрессию, нужно запускать после обновления на существующем окружении.

5. **Не ориентируйтесь на `nslookup` как на проверку работоспособности приложения.** Он обходит `/etc/hosts` и NSS. Проверяйте тем же механизмом, которым пользуется приложение, — `getent hosts`.

### Откат изменений

Все описанные изменения обратимы, но требуют пересоздания контейнеров:

```bash
# Откат daemon.json
sudo cp /etc/docker/daemon.json.bak /etc/docker/daemon.json
sudo systemctl restart docker

# Пересоздание контейнеров, получивших настройки при создании
docker compose down && docker compose up -d

# Проверка, что имена снова разрешаются
docker exec <container> getent hosts <service_name>
```

Откат на уровне Compose — удалить ключи `dns`, `dns_search`, `dns_opt` из сервиса и выполнить `docker compose up -d --force-recreate`. Удаление этих ключей возвращает поведение к унаследованному от хоста, а не к состоянию «до явной настройки», — учитывайте это при планировании отката.

## Дополнительная информация

### Ограничения, о которых стоит знать заранее

- **TTL ответов встроенного резолвера — 600 секунд.** Приложение вправе кэшировать адрес контейнера до 10 минут, а `docker compose up -d` с тем же именем может получить другой IP. Решения: уникальные имена, отсутствие агрессивного кэша на стороне клиента либо архитектура, не требующая стабильности адреса.
- **Встроенный резолвер обрабатывает `A`, `AAAA`, `MX`, `PTR` и `SRV`.** Остальные типы запросов проксируются на upstream без локального разбора.
- **IPv6-эквивалента у `127.0.0.11` нет.** Адрес работает в контейнерах, работающих только по IPv6, но указать его как IPv6 nameserver нельзя.
- **`--dns`, `--dns-search`, `--dns-option`, `--add-host`, `--hostname` не поддерживаются** в режимах `host` и `container:<id>`. Значения не применяются, но и контейнер не создастся: демон отклоняет команду с ошибкой `conflicting options`. Неверная конфигурация обнаруживается сразу, а не «тихо».
- **В сети `bridge` по умолчанию Service Discovery не появился.** Встроенный резолвер на ней отключён: в NetworkManager добавление внутреннего резолвера на сеть по умолчанию откатывалось из-за взаимодействия с buildkit.
