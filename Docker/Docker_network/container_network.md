# Режим сети container

## Определения

- **`--network container:<имя|id>`**: Специальный режим Docker, при котором контейнер запускается внутри сетевого пространства имён (network namespace) уже существующего контейнера.
- **Sidecar-паттерн (Паттерн «коляска»)**: Архитектурный подход, при котором вспомогательный контейнер (sidecar) расширяет возможности основного приложения (мониторинг, логирование, безопасность), разделяя с ним ресурсы.
- **Инфраструктурный контейнер (Pause container)**: Минималистичный контейнер, который служит исключительно для удержания сетевого пространства имён и других ресурсов, позволяя другим контейнерам подключаться к ним и отключаться без потери IP-адреса.
- **Loopback (Петлевой интерфейс)**: Виртуальный сетевой интерфейс (`127.0.0.1`), через который контейнеры в этом режиме могут общаться друг с другом с околонулевой задержкой.

## Основные концепции

### Принцип совместного использования ресурсов

При использовании режима `container:` Docker не выделяет новый IP-адрес и не создает новую пару veth-интерфейсов. Вместо этого процесс нового контейнера подключается к сетевому стеку целевого контейнера через системный вызов `setns()`.

**Ключевые характеристики:**

| Характеристика | Описание |
| :--- | :--- |
| **Сетевая идентичность** | Контейнеры имеют одинаковый IP, MAC-адрес и таблицу маршрутизации. |
| **Связь через Localhost** | Контейнеры обращаются к портам друг друга через `127.0.0.1`. |
| **Hostname и DNS** | Sidecar наследует `hostname`, `/etc/hosts` и `/etc/resolv.conf` целевого контейнера. |
| **Порты** | Нельзя запустить два процесса на одном порту (ошибка `EADDRINUSE`). |
| **Публикация портов** | Параметры `-p` игнорируются; порты публикуются только при запуске "владельца" сети. |

### Продвинутые Sidecar-паттерны (2026)

1. **Proxy Sidecar (Ambient-подобный)**: Использование `envoy` или `nginx` в сети приложения для обеспечения mTLS, терминирования TLS или реализации сложных правил маршрутизации без изменения кода приложения.
2. **Log/Metric Shipping**: Агенты (например, **[Vector](../../Vector/vector_overview.md)** или **[Fluent Bit](../../ELK_Stack/filebeat_overview.md)**) собирают данные через общие тома или локальные сокеты, не нагружая сетевой интерфейс хоста.
3. **Security/WAF**: Фильтрация входящего трафика перед тем, как он попадет в основной стек приложения.

### Совместное использование PID и IPC

Для глубокой интеграции sidecar-контейнера часто требуется разделение других пространств имён:
- **`--pid container:<имя>`**: Позволяет sidecar-контейнеру видеть дерево процессов (`/proc`) основного контейнера. Критично для `top`, `gdb`, `strace`.
- **`--ipc container:<имя>`**: Позволяет использовать общую память (**Shared Memory**) через `/dev/shm`. Это на порядок быстрее, чем сетевое взаимодействие, при передаче больших объемов данных между контейнерами.

## Практические сценарии

### Сценарий 1: Отладка Distroless-приложения

Позволяет диагностировать проблемы в образах без оболочки и утилит.

```bash
# 1. Запуск основного приложения
docker run -d --name app-backend nginx:alpine

# 2. Подключение netshoot (швейцарский нож сетевой отладки)
docker run --rm -it --network container:app-backend nicolaka/netshoot
# Внутри: ss -tulpn (видим порты nginx)
```

### Сценарий 2: Использование инфраструктурного контейнера (Pause)

Паттерн, пришедший из Kubernetes, позволяющий обновлять приложение, не разрывая сетевые соединения sidecar-ов.

```bash
# 1. Запуск pause-контейнера (держит сеть)
docker run -d --name network-holder -p 8080:80 mirror.gcr.io/google_containers/pause:3.9

# 2. Запуск приложения и sidecar-ов в этой сети
docker run -d --name main-app --network container:network-holder my-app:latest
docker run -d --name sidecar-proxy --network container:network-holder envoy-proxy:latest
```

### Сценарий 3: Docker Compose (Compose Spec)

Пример современной конфигурации (без указания версии).

```yaml
services:
  app:
    image: my-app:latest
    ports:
      - "8080:8080"

  sidecar-logger:
    image: fluent/fluent-bit:latest
    network_mode: "service:app"
    pid: "service:app" # Опционально: доступ к процессам
    volumes:
      - app-logs:/var/log/app

volumes:
  app-logs:
```

## Дополнительная информация

### Безопасность и Capabilities

Для полноценной отладки в режиме `container:` (например, через `gdb` или `tcpdump`) sidecar-контейнеру могут потребоваться дополнительные привилегии:
- `--cap-add SYS_PTRACE`: Для доступа к памяти процессов другого контейнера.
- `--cap-add NET_ADMIN`: Для изменения настроек сети (например, добавления правил iptables внутри общего неймспейса).

### Жизненный цикл

1. **Фатальность остановки**: Если целевой контейнер упадет или будет перезапущен, сетевой неймспейс исчезнет. Sidecar-контейнеры "повиснут" в неопределенном состоянии (сетевые вызовы будут возвращать ошибку).
2. **Атомарность обновлений**: В стандартном Docker (без Swarm/K8s) обновление "владельца" сети требует перезапуска всех зависимых контейнеров.
