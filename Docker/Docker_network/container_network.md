# Режим сети `container:<name>`

## Определения

- **`--network container:<имя>`**: Специальный режим Docker, при котором контейнер запускается в сетевом пространстве имен (network namespace) другого контейнера. Оба контейнера разделяют один сетевой стек.
- **Network namespace**: Изолированное сетевое окружение процесса с собственным стеком (интерфейсы, таблицы маршрутизации, DNS (Domain Name System)).
- **Sidecar-паттерн**: Архитектурный паттерн, при котором вспомогательный контейнер присоединяется к основному для расширения функциональности (отладка, мониторинг, проксирование).

## Основные концепции

### Принцип работы

При запуске с `--network container:<имя>` Docker не создает новый сетевой стек, а подключает контейнер к существующему namespace целевого контейнера.

**Характеристики режима:**

| Характеристика | Описание |
| :--- | :--- |
| **IP-адрес (Internet Protocol)** | Общий с целевым контейнером |
| **Интерфейс localhost** | Общий — контейнеры видят процессы друг друга на `127.0.0.1` |
| **Сетевая изоляция** | Отсутствует между контейнерами в одном namespace |
| **Проброс портов** | Флаги `-p` и `-P` игнорируются, порты открываются на целевом контейнере |

### Отличия от других режимов

| Режим | Сетевой стек | IP-адрес | Изоляция |
| :--- | :--- | :--- | :--- |
| `bridge` (по умолчанию) | Собственный namespace | Уникальный | Высокая |
| `host` | Стек хоста | IP хоста | Отсутствует |
| `none` | Собственный namespace без интерфейсов | Только loopback | Полная |
| `container:<name>` | Namespace другого контейнера | Общий с целевым | Отсутствует между контейнерами |

### Жизненный цикл

Sidecar-контейнер зависит от целевого:

- При остановке/удалении целевого контейнера сетевой стек исчезает
- Sidecar теряет сетевое подключение
- Перезапуск целевого контейнера требует перезапуска sidecar

## Практические сценарии

### Отладка сетевого трафика

Анализ трафика без установки утилит в основной контейнер:

```bash
# Запуск основного приложения
docker run -d --name my-app nginx

# Запуск sidecar для отладки
docker run --rm -it --network container:my-app nicolaka/netshoot
```

**Доступные команды внутри sidecar:**

- `tcpdump -i lo` — перехват трафика на loopback
- `netstat -tulpn` — просмотр активных соединений
- `ss -tulpn` — альтернатива netstat
- `curl http://localhost:80` — проверка доступности сервиса

### Мониторинг и сбор метрик

Sidecar-агент собирает метрики основного приложения:

```bash
# Основное приложение
docker run -d --name app myapp:latest

# Sidecar для экспорта метрик
docker run -d --name metrics \
  --network container:app \
  prom/prometheus:latest
```

### Проксирование трафика

Sidecar как sidecar-прокси (например, Envoy, Linkerd):

```bash
# Основное приложение
docker run -d --name backend api-service:latest

# Sidecar-прокси
docker run -d --name proxy \
  --network container:backend \
  envoyproxy/envoy:v1.25-latest
```

### Отладка distroless-контейнеров

Distroless-образы не содержат shell и утилит. Sidecar позволяет диагностировать проблемы:

```bash
# Целевой distroless-контейнер
docker run -d --name distro-app gcr.io/distroless/base

# Подключение для отладки
docker run --rm -it --network container:distro-app nicolaka/netshoot
```

См. также: [Отладка distroless-контейнеров](../Docker_troubleshooting/debugging_distroless.md).

## Дополнительная информация

**Связь с Kubernetes:** Режим `container:<name>` — основа сетевой модели Kubernetes Pods. Все контейнеры в поде разделяют один network namespace, что обеспечивает:

- Общее обращение к сервисам через `localhost`
- Единый IP-адрес у всех контейнеров пода
- Координацию жизненного цикла

**Ограничения:**

- Нельзя пробрасывать порты на sidecar — только на целевой контейнер
- Зависимость от жизненного цикла целевого контейнера
- Требуется ручное управление порядком запуска
