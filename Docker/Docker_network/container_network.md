# Режим сети container:

## Определения

- **`--network container:<имя|id>`**: Специальный режим Docker, при котором контейнер запускается внутри сетевого пространства имён (network namespace) уже существующего контейнера.
- **Сетевое пространство имён (Network Namespace)**: Изолированный стек протоколов, интерфейсов и таблиц маршрутизации в ядре Linux.
- **Sidecar-паттерн (Паттерн «коляска»)**: Архитектурный подход, при котором вспомогательный контейнер (sidecar) расширяет возможности основного приложения (мониторинг, логирование, безопасность), разделяя с ним ресурсы.
- **Loopback (Петлевой интерфейс)**: Виртуальный сетевой интерфейс (`127.0.0.1`), через который контейнеры в этом режиме могут общаться друг с другом с минимальной задержкой.

## Основные концепции

### Принцип совместного использования ресурсов

При использовании режима `container:` Docker не выделяет новый IP-адрес и не создает новую пару veth-интерфейсов для запускаемого контейнера. Вместо этого он подключает новый процесс к существующему сетевому стеку целевого контейнера.

**Ключевые характеристики:**

| Характеристика | Описание |
| :--- | :--- |
| **Сетевая идентичность** | Контейнеры имеют одинаковый IP-адрес, MAC-адрес и таблицу маршрутизации. |
| **Связь через Localhost** | Контейнеры могут обращаться к портам друг друга через `127.0.0.1`. |
| **Hostname и DNS** | Sidecar-контейнер наследует имя хоста (`hostname`) и содержимое файлов `/etc/hosts`, `/etc/resolv.conf` целевого контейнера. |
| **Порты** | Нельзя запустить два процесса, слушающих один и тот же порт (возникнет конфликт `Address already in use`). |
| **Публикация портов** | Параметры `-p` / `-P` игнорируются. Порты должны быть опубликованы при запуске целевого (первого) контейнера. |

### Расширение паттерна: PID и IPC namespaces

Для полноценной работы sidecar-контейнера (особенно для отладки или сбора метрик) часто требуется разделение не только сети, но и других пространств имён:

- **`--pid container:<имя>`**: Позволяет sidecar-контейнеру видеть дерево процессов основного контейнера (через `/proc`). Необходимо для инструментов отладки (`gdb`, `strace`, `top`).
- **`--ipc container:<имя>`**: Позволяет использовать общие механизмы межпроцессного взаимодействия (Shared Memory, Semaphore) между контейнерами.

## Практические сценарии

### Сценарий 1: Отладка без изменения образа приложения

Позволяет диагностировать проблемы в «минималистичных» или distroless-контейнерах, где отсутствуют оболочка (shell) и утилиты.

```bash
# 1. Запуск основного приложения (целевой контейнер)
docker run -d --name app-backend nginx:alpine

# 2. Запуск отладочного контейнера в сети целевого
docker run --rm -it --network container:app-backend nicolaka/netshoot sh
# → Теперь внутри netshoot:
# # ss -tulpn (видим порты nginx)
# # curl localhost:80 (обращаемся к приложению по loopback)
```

### Сценарий 2: Сбор метрик через sidecar-экспортер

Использование специализированного контейнера для экспорта метрик приложения в Prometheus.

```bash
# Запуск приложения
docker run -d --name main-app my-app:latest

# Запуск экспортера в той же сети
docker run -d --name metrics-exporter \
  --network container:main-app \
  prom/statsd-exporter:latest
```

### Сценарий 3: Реализация в Docker Compose

В Docker Compose режим `container:` реализуется через параметр `network_mode`.

```yaml
version: "3.9"
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"

  debugger:
    image: nicolaka/netshoot
    network_mode: "service:web" # Или "container:web_container_name"
    stdin_open: true
    tty: true
```

### Сценарий 4: Полная инспекция процесса (Сеть + PID)

Для глубокой диагностики, когда нужно сопоставить сетевые соединения с конкретными процессами.

```bash
docker run --rm -it \
  --network container:app-backend \
  --pid container:app-backend \
  --cap-add SYS_PTRACE \
  nicolaka/netshoot
```

## Дополнительная информация

### Жизненный цикл и зависимости

Режим `container:` создает жесткую зависимость:
1. **Порядок запуска**: Целевой контейнер должен быть запущен первым.
2. **Остановка**: Если целевой контейнер останавливается, сетевой стек уничтожается. Sidecar-контейнер теряет связь, но его процессы продолжают работать (если не используются другие пространства имён), что может привести к ошибкам ввода-вывода.
3. **Обновление**: Для изменения сетевых настроек (например, добавление нового порта) необходимо пересоздать оба контейнера.

### Связь с Kubernetes

Этот режим является фундаментальным для **Kubernetes Pod**. Все контейнеры внутри одного Pod всегда разделяют сетевое пространство имён (а в некоторых конфигурациях и PID/IPC) через инфраструктурный контейнер (pause-container).
