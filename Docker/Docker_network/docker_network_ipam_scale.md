# IPAM и планирование ёмкости сетей Docker

**Актуально для:** Docker Engine 29.x

## Определения

- **IPAM (IP Address Management)** — подсистема Docker, управляющая адресным пространством сетей: выделение подсетей, шлюзов, диапазонов выдачи и резервных адресов. Реализуется драйвером IPAM (по умолчанию `default`).
- **`default-address-pools`** — пул адресов в `daemon.json`, из которого демон выделяет подсети для сетей без явного `--subnet`. Заданные пулы **заменяют** встроенный пул целиком (не дополняют его). Без настройки используется встроенный пул (состав — в разделе «Дефолтный пул адресов»).
- **Глобальный пул (global-scope)** — пул для overlay-сетей Swarm: `10.0.0.0/8` с `size: 24`, то есть /24 на сеть (исходники moby, `daemon/libnetwork/ipamutils/utils.go`).
- **`--ip-range`** — поддиапазон внутри подсети, из которого выдаются динамические адреса; адреса вне диапазона (но внутри подсети) доступны для статического назначения. Значение приводится к содержащему его CIDR-блоку с границей маски (см. «Граничные случаи»).
- **`--aux-address`** — резервные адреса, исключаемые из динамической выдачи (DNS, сервисы).
- **ULA (Unique Local Address)** — префикс из `fd00::/8`. Для IPv6-сетей без `--subnet` демон выводит ULA /48 из SHA-256 идентификатора хоста (алгоритм RFC 4193 §3.2.2, L-бит установлен) и выделяет /64 из неё; префикс стабилен, пока не меняется hostID.
- **Config-only сеть** — сеть, содержащая только конфигурацию IPAM и опции драйвера, без создания data-plane; используется для macvlan/ipvlan в многохостовых конфигурациях через `--config-from`.
- **Шардирование сетей** — разбиение большого числа контейнеров на несколько сетей для обхода лимита стабильности bridge-сети (1000 контейнеров).

## Основные концепции

### Как Docker выделяет адреса

При создании сети без `--subnet` демон берёт следующий свободный блок из настроенных или встроенных пулов и назначает его сети. При создании с `--subnet` используется заданная подсеть. Динамические адреса выдаются из `--ip-range` (или всей подсети, если диапазон не задан). Шлюз по умолчанию — первый адрес подсети.

```
default-address-pools (daemon.json) или встроенный пул
        │
        ▼
docker network create (без --subnet)
        │
        ▼
подсеть сети (например 172.30.0.0/24)
        │
        ├── шлюз (172.30.0.1)
        ├── --aux-address (резерв)
        ├── --ip-range (динамическая выдача)
        └── остаток подсети (статические --ip)
```

Проблема без планирования: на хосте с десятками сетей подсети выделяются последовательно из пула и могут пересечься с корпоративными диапазонами или VPN-подсетями. Docker проверяет пересечение **только внутри своего демона** — он не знает о внешних маршрутах хоста и вручную добавленных маршрутах.

### Дефолтный пул адресов

Состав встроенного пула (Docker 29.x; исходники moby `daemon/libnetwork/ipamutils/utils.go`, подтверждено эмпирически на 29.8.2):

| Базовый блок | size | Сетей из блока | Назначение |
| :--- | :--- | :--- | :--- |
| `172.17.0.0/16` | 16 | 1 | дефолтный bridge (`docker0`) |
| `172.18.0.0/16` | 16 | 1 | пользовательские сети |
| `172.19.0.0/16` | 16 | 1 | пользовательские сети |
| `172.20.0.0/14` | 16 | 4 (172.20–172.23) | пользовательские сети |
| `172.24.0.0/14` | 16 | 4 (172.24–172.27) | пользовательские сети |
| `172.28.0.0/14` | 16 | 4 (172.28–172.31) | пользовательские сети |
| `192.168.0.0/16` | 20 | 16 (блоки /20) | пользовательские сети |

Итого ~30 пользовательских сетей без явного `--subnet` (каждая — отдельный /16 или /20). Порядок выделения: сначала /16-блоки 172.18→172.31, затем /20-блоки 192.168.0.0/20→192.168.240.0/20. На хостах с Docker Desktop часть /20-блоков может быть занята инфраструктурой VM (наблюдалось 192.168.64.0/20) — доступных сетей меньше.

Overlay-сети Swarm без `--subnet` получают /24 из глобального пула `10.0.0.0/8` (до 65536 сетей).

### Лимит 1000 контейнеров на bridge-сеть

Из-за ограничений ядра Linux bridge-сети становятся нестабильными при 1000 и более контейнеров в одной сети: связь между контейнерами начинает рваться (документация Docker, [moby/moby#44973](https://github.com/moby/moby/issues/44973)). Это свойство архитектуры, не аварийная ситуация. Стратегия — шардирование: распределять контейнеры по нескольким сетям заранее, а не ждать деградации.

Детали из issue #44973 (Docker 23.0, наблюдение автора): деградация проявилась при 1002+ контейнерах в одной сети; лимит **на сеть, а не на хост** — две сети по 1001 контейнеру (2002 суммарно) работали корректно. Issue закрыт как `not planned`, корневая причина официально не подтверждена — поэтому практический порог проектирования ниже наблюдаемого.

### Статические vs динамические адреса

| Подход | Когда | Ограничение |
| :--- | :--- | :--- |
| Динамический (по умолчанию) | stateless-сервисы, веб-фермы | адрес меняется при пересоздании; TTL DNS 600 с |
| Статический (`--ip`) | БД, очереди, сервисы с белыми списками | адрес должен быть вне `--ip-range`; занятость проверяется вручную |
| Фиксированный через Compose | декларативные стеки | `ipv4_address` в `networks.<name>` сервиса |

## Предварительные условия

- **Доступ root/sudo** — `daemon.json` и `sysctl` меняются на хосте, не внутри контейнера; изменение `default-address-pools` требует перезапуска демона.
- **Версия Engine** — состав дефолтного пула проверен для 29.x; в более старых версиях пул мог отличаться (проверьте эмпирически: создайте сеть без `--subnet` и посмотрите `docker network inspect`).
- **Утилиты хоста** — `ip route show` для проверки пересечений; `jq` для чтения `docker network inspect -f '{{json .IPAM.Config}}'`.
- **Свободное адресное пространство** — пул не должен пересекаться с корпоративными подсетями, VPN и маршрутами хоста (Docker внешние маршруты не видит).

## Практические сценарии

### Сценарий 1: Планирование адресного пространства

Иерархия подсетей для хоста с десятками стеков. Принцип: один `/16` на Docker, `/24` на сеть, слои по функции.

```json
// /etc/docker/daemon.json
{
  "default-address-pools": [
    {"base": "172.30.0.0/16", "size": 24},
    {"base": "172.31.0.0/16", "size": 24}
  ],
  "bip": "172.17.0.1/16",
  "fixed-cidr": "172.17.0.0/24"
}
```

Важно: заданные `default-address-pools` **заменяют** встроенный пул целиком — в примере выше доступны только /24-сети из `172.30.0.0/16` и `172.31.0.0/16` (по 256 сетей в каждом), а встроенные блоки 172.18–172.31 и 192.168.0.0/16 использоваться не будут.

Схема выделения:

| Диапазон | Назначение |
| :--- | :--- |
| `172.17.0.0/16` (`bip`) | дефолтная сеть `bridge` (legacy, только для одиночных контейнеров) |
| `172.30.0.0/16` | пользовательские bridge-сети, слой frontend |
| `172.31.0.0/16` | пользовательские bridge-сети, слой backend |
| `10.40.0.0/16` | macvlan/ipvlan (L2-сегмент физической сети) |

Синтаксис `default-address-pools` и остальные сетевые ключи `daemon.json` — в [полном референсе daemon.json](../docker_daemon_config.md).

### Сценарий 2: Сеть с разделением динамического и статических диапазонов

```bash
# Подсеть /24: .1 — шлюз, .2 — резерв (aux), .3-.127 — статика, .128-.254 — динамика (/25)
docker network create \
  --subnet 172.30.1.0/24 \
  --gateway 172.30.1.1 \
  --aux-address "dns=172.30.1.2" \
  --ip-range 172.30.1.128/25 \
  app-net

# Валидация IPAM
docker network inspect app-net -f '{{json .IPAM.Config}}'
# → [{"Subnet":"172.30.1.0/24","Gateway":"172.30.1.1",
#     "IPRange":"172.30.1.128/25","AuxiliaryAddresses":{"dns":"172.30.1.2"}}]

# Динамический адрес — из диапазона .128-.254
docker run -d --name web --network app-net nginx:alpine
docker inspect web -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
# → 172.30.1.128

# Статический адрес из диапазона .3-.127
docker run -d --name db --network app-net --ip 172.30.1.50 postgres:17-alpine
docker inspect db -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
# → 172.30.1.50
```

Ёмкость подсети: 256 − 3 резервных адреса (сетевой, шлюз, broadcast) = **253** адреса. Формула для любой подсети: `2^(32−mask) − 3`.

### Сценарий 3: Шардирование при росте за 1000 контейнеров

Три сети по 300 контейнеров вместо одной на 900 — стабильнее и изолированнее.

```bash
# Три шарда вместо одной сети
docker network create --subnet 172.30.10.0/24 shard-a
docker network create --subnet 172.30.11.0/24 shard-b
docker network create --subnet 172.30.12.0/24 shard-c

# Контейнер подключается к одному шарду
docker run -d --name worker-1 --network shard-a my-worker
docker network connect shard-b worker-1   # при необходимости — ко второму

# Контроль плотности: число эндпоинтов в каждой сети
for n in shard-a shard-b shard-c; do
  printf '%s: %s endpoints\n' "$n" \
    "$(docker network inspect $n --format '{{len .Containers}}')"
done
# → shard-a: 300 endpoints
# → shard-b: 300 endpoints
# → shard-c: 300 endpoints
```

Правило проектирования: держите каждую сеть заметно ниже 1000 эндпоинтов (практический порог — 500), чтобы оставался запас на пик и на сети, которые нельзя пересоздать без простоя.

### Сценарий 4: Обнаружение пересечения подсетей

```bash
# Все подсети Docker на хосте
docker network ls --format '{{.Name}}' | while read n; do
  docker network inspect "$n" --format \
    '{{range .IPAM.Config}}{{.Subnet}}{{"\n"}}{{end}}' | sed "s/^/$n: /"
done

# Пересечение с маршрутами хоста (внешние подсети, о которых Docker не знает)
ip route show | grep -E '172\.(1[6-9]|2[0-9]|3[01])\.'
# → Если вывод непуст — подсеть Docker пересекается с существующим маршрутом
```

Пересечение с корпоративной сетью проявляется как «контейнер пингует шлюз, но не достаёт до внешнего хоста» — пакет уходит в мост Docker, а не в физический маршрутизатор.

### Сценарий 5: Многохостовой IPAM через config-only сети

Для macvlan/ipvlan с разными подсетями на узлах — пара «config-only + `--config-from`» (подробно: [CLI-справочник](./cli.md) и [драйвер macvlan](./drivers/macvlan.md)).

```bash
# На каждом узле — своя локальная конфигурация
node1$ docker network create --config-only --subnet 192.168.100.0/24 mv-config
node2$ docker network create --config-only --subnet 192.168.200.0/24 mv-config

# Рабочая swarm-сеть, копирующая конфигурацию
node1$ docker network create -d macvlan --scope swarm \
  --config-from mv-config --attachable swarm-net
```

### Сценарий 6: Исчерпание адресов

Два разных режима отказа с разными ошибками — важно различать по тексту:

```bash
# Режим A: исчерпана подсеть существующей сети — ошибка при запуске контейнера
docker run -d --network app-net --name new-svc my-app
# → Error response from daemon: failed to set up container networking:
#   no available IPv4 addresses on this network's address pools: app-net (<id>)

# Диагностика: сколько адресов занято и какой размер подсети
docker network inspect app-net --format '{{len .Containers}}'
# → 253   (подсеть /24: 256 − 3 резервных = 253 адреса)

# Режим B: исчерпан дефолтный пул — ошибка при создании сети
docker network create another-net
# → Error response from daemon: could not find an available, non-overlapping
#   IPv4 address pool among the defaults to assign to the network

# Решение для A: сеть с большей подсетью — только пересоздание
docker network create --subnet 172.30.1.0/23 app-net-large
# → /23 даёт 509 адресов (512 − 3); существующие контейнеры нужно переподключить
```

### Сценарий 7: IPv6-адресация

```bash
# IPv6-сеть: ULA-префикс выбирается автоматически из пула, выведенного из hostID
docker network create --ipv6 my-v6-net
docker network inspect my-v6-net --format '{{json .IPAM.Config}}'
# → [{"Subnet":"172.18.0.0/16","Gateway":"172.18.0.1"},
#     {"Subnet":"fdde:3276:abd2::/64","Gateway":"fdde:3276:abd2::1"}]
#   (пример с конкретного хоста: ULA /48 выводится из SHA-256 hostID,
#    стабильна для хоста, из неё выделяются /64 — до 65536 сетей)

# IPv6-only сеть (без IPv4)
docker network create --ipv6 --ipv4=false v6-only-net
docker network inspect v6-only-net --format '{{json .IPAM.Config}}'
# → [{"Subnet":"fdde:3276:abd2::/64","Gateway":"fdde:3276:abd2::1"}]

# IPv6 для дефолтного bridge — только через daemon.json (перезапуск демона)
# {"ipv6": true, "bip6": "2001:db8::1111/64", "fixed-cidr-v6": "2001:db8::/64"}
```

## Граничные случаи

- **`--ip-range` нормализуется к CIDR-блоку.** Значение с не-граничным адресом приводится к содержащему его блоку: `--ip-range 172.30.1.11/25` сохраняется как `172.30.1.0/25` (проверено эмпирически). Произвольные диапазоны вроде «.11–.200» задать нельзя — только выровненные CIDR-блоки.
- **Две разные ошибки исчерпания.** «no available IPv4 addresses on this network's address pools» — кончились адреса в подсети сети (ошибка при `docker run`); «could not find an available, non-overlapping IPv4 address pool» — кончился дефолтный пул или все блоки пересекаются (ошибка при `docker network create`).
- **Лимит 1000 — на сеть, не на хост.** Две сети по 1001 контейнеру работали корректно (issue #44973); шардирование решает проблему без изменения подсети.
- **Docker Desktop занимает часть пула.** На macOS/Windows-хостах часть /20-блоков (наблюдалось 192.168.64.0/20) занята инфраструктурой VM — доступных сетей из дефолтного пула меньше, чем ~30.
- **`default-address-pools` заменяет встроенный пул.** Если задать один пул, остальные встроенные блоки недоступны — планируйте ёмкость с учётом только заданных блоков.
- **ULA стабильна per-hostID.** Авто-выделенные IPv6-подсети детерминированы для хоста (SHA-256 hostID); смена hostID меняет префикс и, соответственно, адреса новых сетей.
- **Перезагрузка демона с кастомными пулами.** В версиях до 29.8.2 `docker info` мог падать с ошибкой «invalid Prefix» после reload демона с настроенными `default-address-pools` (исправлено в 29.8.2, moby/moby#53812).

## Устранение неисправностей

| Симптом | Причина | Диагностика |
| :--- | :--- | :--- |
| `no available IPv4 addresses on this network's address pools` (при `docker run`) | исчерпана подсеть сети | `docker network inspect <net> --format '{{len .Containers}}'` против `2^(32−mask) − 3` |
| `could not find an available... address pool` (при `docker network create`) | исчерпан пул или пересечение | `docker network ls` + `ip route show` |
| `invalid subnet` | пересечение с существующей сетью Docker | `docker network inspect <net> -f '{{.IPAM.Config}}'` |
| Контейнер не получает IP | `--ip` внутри `--ip-range` или уже занят | `docker network inspect <net> --format '{{range .Containers}}{{.IPv4Address}}{{end}}'` |
| Пересечение с корпоративной сетью | `default-address-pools` не настроен | `ip route show` против подсетей Docker |
| Деградация при >1000 контейнеров | лимит bridge-сети | `docker network inspect <net> --format '{{len .Containers}}'` |
| Адрес не из ожидаемой подсети | сеть создана без `--subnet`, взята из пула | `docker network inspect <net> -f '{{json .IPAM.Config}}'` |
| `--ip-range` не совпадает с заданным | нормализация к CIDR-блоку | `docker network inspect <net> -f '{{json .IPAM.Config}}'` |

## Валидация

```bash
# 1. Состав дефолтного пула: подсеть, выданная сети без --subnet
docker network create pool-probe >/dev/null && \
  docker network inspect pool-probe --format '{{range .IPAM.Config}}{{.Subnet}}{{end}}'
# → 172.18.0.0/16 (первый пользовательский блок; далее 172.19, 172.20, ...)
docker network rm pool-probe >/dev/null

# 2. Ёмкость подсети: занято против размера − 3
docker network inspect app-net --format '{{len .Containers}}'
# → 253 при /24 — подсеть полностью занята

# 3. Разделение диапазонов: динамика и статика из разных блоков
docker network inspect app-net -f '{{json .IPAM.Config}}'
# → "IPRange":"172.30.1.128/25" — динамика в старшей половине,
#   статика (.3-.127) вне диапазона

# 4. Отсутствие пересечения с маршрутами хоста
ip route show | grep -E '172\.(1[6-9]|2[0-9]|3[01])\.|192\.168\.'
# → пустой вывод — пересечений нет

# 5. IPv6: ULA-префикс сети
docker network inspect my-v6-net --format '{{range .IPAM.Config}}{{.Subnet}} {{end}}'
# → 172.18.0.0/16 fdde:3276:abd2::/64
```

## Рекомендации

- **Настройте `default-address-pools` на каждом хосте** — иначе подсети выделяются из встроенного пула и рано или поздно пересекутся с корпоративными диапазонами. Помните: заданные пулы заменяют встроенные целиком.
- **Задавайте `--subnet` явно** для production-сетей — воспроизводимость и контроль адресного пространства.
- **Разделяйте динамический и статический диапазоны** через `--ip-range` — статические адреса не будут конфликтовать с динамической выдачей. Диапазон должен быть выровненным CIDR-блоком.
- **Шардируйте заранее** — держите каждую сеть ниже 500 эндпоинтов, чтобы лимит 1000 не стал аварией.
- **Резервируйте служебные адреса** через `--aux-address` — DNS, мониторинг не должны выдаваться контейнерам.
- **Держите схему адресации в Git** — `daemon.json` и скрипты создания сетей под контролем версий; изменение `default-address-pools` требует перезапуска демона.
- **Проверяйте пересечение с внешними маршрутами** — Docker не знает о маршрутах хоста, проверка `ip route show` обязательна перед внедрением.
- **Откат изменений** — удалите тестовые сети (`docker network rm <net>`; сначала отключите контейнеры), верните `daemon.json` из Git и перезапустите демон: `sudo systemctl restart docker`.

### Ограничения

- Docker не обнаруживает пересечения с маршрутами хоста и вручную добавленными подсетями — проверка `ip route show` лежит на администраторе.
- Расширение подсети существующей сети невозможно — только пересоздание сети и переподключение контейнеров.
- Лимит 1000 контейнеров — свойство ядра Linux для bridge-сетей; для overlay/macvlan/ipvlan ограничения иные.
- Корневая причина лимита 1000 официально не подтверждена (issue #44973 closed as not planned) — порог 500 эндпоинтов на сеть является эвристикой, а не гарантированным пределом.
