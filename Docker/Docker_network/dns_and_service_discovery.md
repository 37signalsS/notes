# DNS и Service Discovery в Docker

**Актуально для:** Docker Engine 29.x, Docker Compose v5+ (Compose Specification)

## Определения

- **DNS (Domain Name System)** — система доменных имён, преобразующая имена хостов в IP-адреса.
- **Встроенный DNS-сервер (Embedded DNS)** — резолвер, работающий внутри демона Docker и доступный контейнеру по адресу `127.0.0.11` в его собственном сетевом пространстве имён. Обслуживает Service Discovery и проксирует запросы, не найденные среди контейнеров, на внешние серверы.
- **Service Discovery (обнаружение сервисов)** — разрешение имени контейнера, сетевого псевдонима или сервиса Swarm в IP-адрес без ручной настройки адресов. Механизм существует только внутри пользовательских сетей.
- **Network Alias (сетевой псевдоним)** — дополнительное имя, заданное контейнеру в конкретной сети через `--network-alias`, `--alias` (`docker network connect`) или `aliases` (Compose). Псевдоним действует только в той сети, где объявлен.
- **Endpoint DNS** — способ разрешения имени сервиса Swarm: `VIP` (по умолчанию, имя резолвится в виртуальный адрес) либо `dnsrr` (имя резолвится в список адресов задач).
- **Round-robin на стороне клиента** — распределение нагрузки, при котором клиент по очереди обращается к каждому из полученных адресов. Сам Docker так не работает: см. [Порядок адресов при нескольких контейнерах под одним именем](#порядок-адресов-при-нескольких-контейнерах-под-одним-именем).
- **`resolv.conf` внутри контейнера** — файл, генерируемый Docker при создании контейнера. Содержит комментарии-трассировку (`# Based on host file`, `# Overrides`, `# ExtServers`, `# Option ndots from`), по которым определяется источник каждого значения.

## Архитектура и как это работает

### Почему адрес `127.0.0.11`

Резолвер слушает адрес из блока `127.0.0.0/8` — этот диапазон обслуживается ядром как loopback-only и не маршрутизируется. Отсюда три практических следствия:

1. Из другого контейнера резолвер недоступен: имя `127.0.0.11` там указывает на loopback **самого** контейнера, где ничего не слушает.
2. С хоста резолвер также недоступен — проверить его можно только изнутри контейнера.
3. Маршрутными средствами его нельзя перехватить или подменить: переадресация с `127.0.0.11` на внешний адрес — типовой вектор перехвата DNS-запросов, и Docker от него защищён самим выбором адреса.

**IPv6-эквивалента у `127.0.0.11` нет.** Указать его как IPv6-nameserver нельзя, но сам адрес работоспособен в контейнерах, сетевой стек которых ограничен только IPv6.

Резолвер поднимает одновременно UDP- и TCP-сокеты на порту 53, поэтому работает и для обычных запросов, и для ответов, не помещающихся в UDP-пакет.

### Что именно входит в пространство имён

Встроенный DNS обслуживает **пространство имён конкретной сети**. Каждый контейнер, подключённый к пользовательской сети, автоматически регистрирует в её реестре:

| Имя | Источник | Видно |
| :--- | :--- | :--- |
| Имя контейнера | `--name` | В этой сети |
| Сетевой псевдоним | `--network-alias`, `--alias`, Compose `aliases` | Только в сети, где объявлен |
| Имя сервиса Swarm | `docker service create` | В swarm-сети, на всех узлах |
| `tasks.<сервис>.<задача>` | Swarm | Только в swarm-сети |

**Что в пространство имён не входит:**

- **Автоматически сгенерированные имена** вида `e3a1b2c3d4`. Разрешаются только явно заданные имена — это ограничение зафиксировано в документации Docker и часто становится причиной «оно работало у меня на прошлой неделе».
- **Имя из `--hostname`**, если оно отличается от `--name`. `--hostname` прописывается в `/etc/hosts` самого контейнера, но запись в реестре DNS не создаёт. Чтобы соседние контейнеры видели это имя, нужен `--name` или `--network-alias`.
- **Записи из `--add-host` / Compose `extra_hosts`.** Они попадают в `/etc/hosts` и обходят DNS целиком. Проверка через `dig` такую запись не увидит — см. [Проверка тем же путём, что и приложение](#сценарий-4-валидация-разрешения-имен).

**Псевдоним может быть неоднозначным.** Один и тот же алиас может быть объявлен на нескольких контейнерах и даже на нескольких сервисах. Compose Specification формулирует это прямо: если алиас разделяется, имя разрешается не в один адрес, а в несколько, и какой именно контейнер имеется в виду — не гарантировано.

### Типы запросов, обслуживаемые локально

Резолвер разбирает **только** `A`, `AAAA`, `MX`, `PTR` и `SRV`. Любой другой тип запроса уходит на внешние серверы без локального поиска — даже если в сети есть контейнер с подходящим именем.

Особенности обработки:

- **`MX`** при найденном имени возвращает пустой ответ с кодом `NOERROR`, чтобы почтовый клиент трактовал его как «implicit MX» (RFC 5321, раздел 5.1) и выполнил отдельный запрос `A`/`AAAA`.
- **`PTR`** обслуживается для IPv4 (`in-addr.arpa`) и IPv6 (`ip6.arpa`) и возвращает имя, под которым endpoint зарегистрирован первым.
- **`SRV`** используется Swarm: возвращает порт и цель вместе с дополнительными A-записями.

### Проксирование на внешние серверы

Если локальной записи нет, запрос пересылается на upstream. Механика жёстко ограничена и это важно при планировании нагрузки:

| Параметр | Значение | Поведение |
| :--- | :--- | :--- |
| Максимум upstream-серверов | 3 | Лишние записи в `daemon.json` игнорируются |
| Таймаут обмена с upstream | 4 с | Переход к следующему серверу |
| Одновременных внешних запросов | 1024 | Клиент получает `REFUSED`, в лог — `[resolver] more than 1024 concurrent queries` |
| TTL локальных ответов | 600 с | Для всех типов локальных записей |

Серверы опрашиваются **последовательно**, а не параллельно. Правила переключения:

- `SERVFAIL` или `REFUSED` — переход к следующему серверу;
- успешный ответ — цепочка завершается;
- `NXDOMAIN` — цепочка **завершается только если ответ авторитетный** (флаг `AA`, RFC 8020). Неавторитетный `NXDOMAIN` от сервера-кэша переключает на следующий сервер.

Если ни один сервер не дал ответа, клиент получает `SERVFAIL`. Превышение лимита в 1024 запроса даёт `REFUSED`, а не таймаут, — это разные симптомы с разными причинами: `REFUSED` означает всплеск локальной нагрузки на резолвер и лечится кэшированием на стороне приложения.

### Порядок адресов при нескольких контейнерах под одним именем

Если под одним именем несколько контейнеров, резолвер возвращает **все** их адреса. Если адресов больше одного, порядок **случайно перемешивается** при каждом ответе (алгоритм Фишера — Йетса). Это не round-robin: позиция адреса в ответе не зависит от предыдущего ответа.

Практические следствия:

- Балансировка ложится на клиента — приложение, всегда берущее первый адрес из ответа, не распределяет ничего.
- Распределение получается только при фактическом переборе всех адресов, как это делают DNS-резолверы Java, Go и curl.
- Рассчитывать на равномерность нельзя: перемешивание случайно и при двух адресах способно вернуть один и тот же первым несколько раз подряд.
- Ограничение на размер ответа: если записи не помещаются в запрошенный размер, резолвер выставляет флаг усечения (`TC`) по UDP и **удаляет записи по одной** из раздела ответа, пока сообщение не уложится. Часть реплик в ответе просто не появится. Клиент обязан повторить запрос по TCP — приложения, которые этого не делают, при большом числе реплик работают нестабильно.

### IPv6 и запросы `AAAA`

Поведение встроенного резолвера при запросе `AAAA` на имя контейнера несимметрично случаю `A`:

- Если у контейнера есть IPv6-адрес — запись возвращается.
- **Если имя найдено в домене Docker, но IPv6-адреса у контейнера нет, резолвер отвечает пустым успешным ответом и запрос наверх не отправляет.**

Это осознанное поведение: иначе одноуровневое имя, для которого в Docker есть только IPv4-контейнер, уходило бы во внешний DNS и могло разрешиться в чужой адрес. Цена решения — приложение, отправившее `AAAA` без пары `A`, получает «пусто» вместо ошибки, и при отсутствии fallback-логики не заметит этого.

Пара `A` + `AAAA` на одном сокете разбирается по-разному в зависимости от libc — glibc и musl отправляют её параллельно, и некорректная обработка такой пары NAT-оборудованием даёт таймаут в 5 секунд. Разбор по платформам и варианты обхода: [Решение проблем с DNS](./troubleshooting/dns_resolution_issues.md).

### Значение `ndots`

Демон по умолчанию выставляет `ndots:0`, чтобы одноуровневые имена разрешались как есть, без перебора `search`-суффиксов. Источник значения виден в комментарии `# Option ndots from: internal` в `resolv.conf` контейнера; при явном переопределении комментарий меняется на `# Option ndots from: override`.

Если пользователь задал `ndots` со значением больше нуля, резолвер **перестаёт проксировать одноуровневые имена** наверх и возвращает пустой успешный ответ, чтобы клиент повторил запрос с доменом из `search`. Для сетей с короткими внутренними именами это ломает обращение к внешним доменам. Полный разбор, включая отличие от Kubernetes (`ndots:5` по умолчанию) и поведение musl, — в [Решении проблем с DNS](./troubleshooting/dns_resolution_issues.md).

### Сеть `bridge` по умолчанию и `--link`

Встроенного резолвера на сети `bridge` по умолчанию нет. Контейнер получает копию `resolv.conf` хоста и обращается к upstream напрямую; имя контейнера не разрешается никогда. Единственный механизм имён — `--link`, объявленный устаревшим: с 29.6.0 движок возвращает предупреждение об устаревании при создании контейнера с `links` в сети `bridge` по умолчанию.

Docker официально называет сеть `bridge` по умолчанию legacy-конструкцией и не рекомендует её для production. Полный список технических ограничений — в документации драйвера `bridge`; архитектурный обзор сетевого стека — в [Обзоре сетевых моделей Docker](./docker_network.md).

### Сети `--internal`

В сети, созданной с `--internal`, Service Discovery **работает в полном объёме** — контейнеры разрешают друг друга по имени. Отключается только проксирование запросов на внешние серверы: контейнер, подключённый только к внутренней сети, не может получить ответ на запрос внешнего имени, и получает `SERVFAIL`.

Это было изменением поведения после CVE-2024-29018 (исправлено в 25.0.5 и 26.0.1): ранее запросы всё же пересылались наверх, если адрес DNS-сервера хоста был loopback-адресом вроде `127.0.0.53` из `systemd-resolved`, что позволяло извлечь данные о сети из изолированного контейнера.

Практическое следствие для эксплуатации: `SERVFAIL` на внешнем имени внутри `--internal`-сети — **не поломка**, а замысел. Если контейнеру действительно нужен выход, добавьте ему вторую сеть; если не нужен — не добавляйте `--dns`, он всё равно не поможет.

### Платформенные различия

- **Windows-контейнеры.** Имена разрешаются и в сети `nat` по умолчанию. Это поведение восстанавливалось дважды: в 25.0.5 (moby/moby#47490) и в 26.0.0 (moby/moby#47375) после того, как изменения в сетевом стеке Windows его ломали. При обновлении Docker на Windows-хосте проверку имён стоит повторить.
- **Rootless.** Встроенный резолвер работает так же, но набор сетевых драйверов ограничен; в 29.5.0 драйвером rootless по умолчанию стал `gvisor-tap-vsock` (ранее `slirp4netns`).

### TTL и смена адреса контейнера

Ответы на имена контейнеров возвращаются с TTL 600 секунд — это не «TTL 0». Приложение вправе кэшировать адрес контейнера до 10 минут, тогда как `docker compose up -d` с тем же именем вполне может получить другой адрес. Обнаружится это только по лавине отказов в приложении, а не как отказ одного контейнера.

Три рабочих решения, от простого к правильному:

1. **Уникальные имена** на каждый инстанс, если приложение позволяет.
2. **Healthcheck, проверяющий разрешение имени**, — смена адреса обнаруживается как отказ одного контейнера, а не как отказ системы.
3. **Клиентский резолвер с собственным кэшем** и перебором всех адресов вместо использования первого.

## Практические сценарии

### Сценарий 1: имена и псевдонимы на `docker run`

Предварительные требования: активная пользовательская сеть. Всё, что ниже, не работает в сети `bridge` по умолчанию.

```bash
# 1. Создать сеть и запустить узлы под общим псевдонимом
docker network create app-net
docker run -d --name node-1 --network app-net --network-alias worker my-worker
docker run -d --name node-2 --network app-net --network-alias worker my-worker

# 2. Проверить разрешение по имени контейнера и по псевдониму
docker run --rm --network app-net nicolaka/netshoot dig +short @127.0.0.11 node-1
# → 172.18.0.2

docker run --rm --network app-net nicolaka/netshoot dig +short @127.0.0.11 worker
# → 172.18.0.2
# → 172.18.0.3
# → Порядок адресов меняется от запроса к запросу — это перемешивание, а не round-robin.

# 3. Повторить запрос 5 раз и убедиться, что порядок меняется
docker run --rm --network app-net nicolaka/netshoot \
  sh -c 'for i in 1 2 3 4 5; do dig +short @127.0.0.11 worker | tr "\n" " "; echo; done'
# → 172.18.0.3 172.18.0.2
# → 172.18.0.2 172.18.0.3
# → 172.18.0.3 172.18.0.2
# → 172.18.0.2 172.18.0.3
# → 172.18.0.2 172.18.0.3

# 4. Очистка
docker rm -f node-1 node-2 && docker network rm app-net
```

Добавление псевдонима к уже работающему контейнеру — через `docker network connect`, а не `--network-alias`:

```bash
docker network connect --alias cache app-net redis
docker inspect redis --format '{{json .NetworkSettings.Networks.app-net.Aliases}}'
# → ["redis","cache"]

docker network disconnect app-net redis
```

Флаг `--alias` можно указать несколько раз — контейнер получает столько псевдонимов, сколько указано. Команда поддерживает `--gw-priority` и `--link-local-ip`, но не `--network-alias`: имя флага зависит от подкоманды.

### Сценарий 2: псевдонимы в Docker Compose

Псевдонимы в Compose объявляются на уровне сети, поэтому одна служба может иметь разные имена в разных сетях.

```yaml
services:
  frontend:
    image: nginx:alpine
    networks:
      - front-tier
      - back-tier

  backend:
    image: postgres:16
    networks:
      back-tier:
        aliases:
          - database

  monitoring:
    image: prom/prometheus
    networks:
      - admin
    depends_on:
      backend:
        condition: service_healthy

networks:
  front-tier: {}
  back-tier: {}
  admin: {}
```

```bash
# frontend видит backend как backend и как database — в сети back-tier
docker compose exec frontend getent hosts database
# → 172.20.0.3   database

# monitoring не видит псевдоним database: сети admin и back-tier разные
docker compose exec monitoring getent hosts database
# → (пусто, exit code 2)

# Имя службы разрешается по умолчанию — без указания networks
docker compose exec frontend getent hosts backend
# → 172.20.0.3   backend
```

**`depends_on` с `condition: service_healthy` — это readiness для Service Discovery.** Без него Compose ждёт только факта запуска контейнера, и frontend может начать обращаться к базе до того, как она способна принять соединения. Healthcheck при этом должен проверять реальную готовность, а не факт работы процесса:

```yaml
  backend:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d app"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
```

В связке с `restart: true` в длинной форме `depends_on` Compose перезапускает потребителя после обновления зависимости — полезно при выкатывании новой версии базы.

**Устаревшая альтернатива — `links`.** Compose Specification оставляет атрибут, но помечает его как «реализация специфична для платформы», а Docker Engine с 29.6.0 выдаёт предупреждение об устаревании при использовании в сети `bridge` по умолчанию. В пользовательской сети `links` не даёт ничего, чего не даёт одноуровневое имя службы, но добавляет неявную зависимость — дублируя `depends_on` и затеняя реальную топологию.

### Сценарий 3: балансировка на клиенте, а не в DNS

Раз у встроенного резолвера нет настоящего round-robin, балансировку нужно строить на стороне клиента. Проверить, что клиент действительно перебирает все адреса, можно так:

```bash
# Развернуть 3 реплики под одним псевдонимом
docker run -d --name api-1 --network app-net --network-alias api my-api
docker run -d --name api-2 --network app-net --network-alias api my-api
docker run -d --name api-3 --network app-net --network-alias api my-api

# Проверить, что ответ содержит все три
docker run --rm --network app-net nicolaka/netshoot dig +short @127.0.0.11 api
# → 172.18.0.2
# → 172.18.0.3
# → 172.18.0.4
```

Для nginx и Angie внутри контейнера резолвер указывается на `127.0.0.11` — это единственный адрес, по которому встроенный DNS доступен изнутри контейнера:

```nginx
location /api/ {
    resolver 127.0.0.11 valid=10s ipv6=off;
    set $backend "api";
    proxy_pass http://$backend:8080;
}
```

Механика `resolver`/`proxy_pass` через переменную, версии nginx, на которых доступна нативная динамика без переменных, `zone`, диагностика и типовые ошибки — в [Динамическое разрешение DNS в Nginx](../../WebServers/Nginx/Proxy/Load_Balancing/dynamic_dns_resolution.md). Здесь зафиксирован только специфичный для Docker момент: адрес резолвера и то, что он существует лишь в пользовательских сетях.

### Сценарий 4: валидация разрешения имен

Прежде чем отлаживать приложение, нужно убедиться, что имя разрешается тем же путём, каким пойдёт само приложение.

```bash
# 1. Какой режим резолвера: пользовательская сеть или legacy-режим bridge
docker inspect <container> --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
# → Любая пользовательская сеть означает встроенный DNS. Только "bridge" — legacy.

# 2. Что именно попало в resolv.conf контейнера
docker exec <container> cat /etc/resolv.conf
# → # Based on host file: '/etc/resolv.conf' (internal resolver)
# → # ExtServers: [host(10.0.0.2)]
# → nameserver 127.0.0.11
# → options ndots:0

# 3. Разрешение тем же механизмом, что и у приложения
docker exec <container> getent hosts api
# → 172.18.0.4   api

# 4. То же имя напрямую у резолвера
docker exec <container> dig +short @127.0.0.11 api
# → 172.18.0.4

# 5. Расхождение результатов 3 и 4 означает, что ответ даёт /etc/hosts, а не DNS
docker exec <container> cat /etc/hosts
```

**Почему `getent hosts`, а не `dig`:** `getent` проходит через `getaddrinfo`, `nsswitch.conf` и `/etc/hosts` — тот же путь, что и приложение. `dig` и `nslookup` обращаются к DNS напрямую и намеренно обходят `/etc/hosts` и NSS. Расхождение результатов — сам по себе диагностический сигнал.

### Сценарий 5: закрытый контур с внешним DNS

Контейнеру нужен доступ к ресурсам внутренней сети компании, а имя хоста за интерфейсом туннеля из контейнера недостижимо.

```bash
# Явно указать корпоративные серверы и суффикс поиска
docker run -d --name my-app \
  --network corp-net \
  --dns 10.0.0.10 \
  --dns 10.0.0.11 \
  --dns-search company.local \
  my-business-app

docker exec my-app cat /etc/resolv.conf
# → # Overrides: [nameservers]
# → nameserver 10.0.0.10
# → nameserver 10.0.0.11
# → search company.local

docker exec my-app getent hosts gitlab.company.local
# → 10.0.0.40   gitlab.company.local
```

```yaml
# То же самое в Compose
services:
  my-app:
    image: my-business-app
    networks:
      - corp-net
    dns:
      - 10.0.0.10
      - 10.0.0.11
    dns_search:
      - company.local
```

Ограничения, о которых стоит знать до настройки:

- В режимах `host` и `container:<id>` флаги `--dns`, `--dns-search`, `--dns-option` **не поддерживаются**: демон отклоняет команду с ошибкой `conflicting options: dns and the network mode`. Контейнер делит сетевое пространство, а значит и резолвер, с хостом или с другим контейнером.
- Адреса из `--dns` опрашиваются **из сетевого пространства контейнера**, а адреса из файла хоста — из сетевого пространства хоста. VPN-сервер, доступный с хоста только через его туннель, из контейнера недоступен.
- `--dns-search` не стирает `search`, унаследованный от хоста. Чтобы убрать все домены поиска, укажите одну точку: `--dns-search=.`
- `--dns` переопределяет только `nameserver`. Для `search` и `options` нужны отдельные ключи `"dns-search"` и `"dns-opts"` в `daemon.json`.

Подробный разбор взаимодействия с `systemd-resolved`, поведение флага `ndots` и диагностика по логам демона — в [Решении проблем с DNS](./troubleshooting/dns_resolution_issues.md).

### Сценарий 6: Swarm — VIP и DNSRR

Выбор режима определяет, что вернёт запрос по имени сервиса.

```bash
# По умолчанию VIP: имя резолвится в виртуальный адрес, балансировка на IPVS
docker service create --name api --network app-net my-api
docker run --rm --network app-net nicolaka/netshoot dig +short @127.0.0.11 api
# → 10.0.1.5   (один адрес)

# DNSRR: имя резолвится в список адресов задач, балансировка на клиенте
docker service update --endpoint-mode dnsrr api
docker run --rm --network app-net nicolaka/netshoot dig +short @127.0.0.11 api
# → 10.0.2.7
# → 10.0.2.8
```

| Режим | Что возвращает DNS | Балансировка | Ограничения |
| :--- | :--- | :--- | :--- |
| `vip` (по умолчанию) | Один виртуальный адрес | IPVS на каждом узле | Работает с `mode=ingress`, с routing mesh |
| `dnsrr` | Список адресов задач | На клиенте | Несовместим с `mode=ingress`, нужен собственный балансировщик |

Подробно — включая routing mesh, `docker_gwbridge`, attachable-сети и нагрузочные сценарии — в [Docker Swarm: сетевое взаимодействие](../../Docker_swarm/swarm_networking.md).

### Сценарий 7: Паттерны балансировки нагрузки

Встроенный резолвер не балансирует — он только возвращает адреса (в случайном порядке). Распределение нагрузки строится на одном из трёх паттернов:

| Паттерн | Механизм | Когда |
| :--- | :--- | :--- |
| **Client-side LB** | клиент перебирает все адреса из DNS-ответа | приложение с собственным резолвером (Go, Java, curl) |
| **Reverse proxy (L7)** | nginx/Angie с `resolver 127.0.0.11` и `proxy_pass` через переменную | L7-балансировка, TLS-терминация |
| **HAProxy / балансировщик (L4/L7)** | выделенный контейнер-балансировщик перед группой контейнеров | TCP/L4, sticky sessions, health checks |

Client-side LB — единственный паттерн без дополнительного компонента, но требует, чтобы клиент перебирал **все** адреса, а не брал первый (см. [порядок адресов](#порядок-адресов-при-нескольких-контейнерах-под-одним-именем)).

Reverse proxy в контейнере — резолвер указывается на `127.0.0.11` (единственный адрес, по которому встроенный DNS доступен изнутри контейнера); механика `resolver`/`proxy_pass` через переменную, `zone`, диагностика — в [Динамическом разрешении DNS в Nginx](../../WebServers/Nginx/Proxy/Load_Balancing/dynamic_dns_resolution.md).

HAProxy как отдельный сервис — балансировка TCP/HTTP перед группой контейнеров, sticky sessions, health checks; конфигурация и примеры — в [Веб-серверы и reverse proxy в Docker](../Dockerfile/Docker_best_practices/web_servers.md) и [Балансировка нагрузки HTTP](../../Networking/Protocols/HTTP/http_load_balancing.md). Для отказоустойчивости самого балансировщика — keepalived с VRRP на двух хостах.

## Устранение неисправностей

Полный разбор диагностики, сводная таблица симптомов и разбор сообщений демона находятся в [Решении проблем с DNS](./troubleshooting/dns_resolution_issues.md). Здесь — симптомы, специфичные именно для обнаружения сервисов.

| Симптом | Причина | Проверка | Решение |
| :--- | :--- | :--- | :--- |
| Имя контейнера не разрешается | Сеть `bridge` по умолчанию | `docker inspect <c> --format '{{.NetworkSettings.Networks}}'` | Перенести контейнер в пользовательскую сеть |
| Имя разрешается при обращении из одной сети, но не из другой | Service Discovery работает только внутри одной сети | `docker network inspect <net>` для обоих контейнеров | Подключить оба контейнера к общей сети |
| Имя не разрешается, хотя `docker ps` показывает контейнер | Не задано явное имя, используется сгенерированное | `docker inspect <c> --format '{{.Name}}'` | Задать `--name` при создании |
| `--add-host` не работает, а `dig` проходит | `extra_hosts` пишет в `/etc/hosts`, минуя DNS | `docker exec <c> cat /etc/hosts` | Проверять через `getent hosts`, а не `dig` |
| Нагрузка не распределяется, приложение всегда попадает в один узел | Резолвер перемешивает адреса, клиент берёт первый | `dig +short @127.0.0.11 <alias>` несколько раз | Перебор всех адресов на клиенте, а не использование первого |
| Часть реплик отсутствует в ответе | Ответ не помещается в UDP-пакет, записи удалены при усечении | `dig +noedns +qr @127.0.0.11 <alias>` — обрезаны ли ответы | Клиент должен повторять запрос по TCP при флаге `TC` |
| `AAAA` возвращает пустой ответ, `A` — адрес | У контейнера нет IPv6-адреса; запрос наверх не уходит намеренно | `docker inspect <c> --format '{{.NetworkSettings.Networks}}'` → нет IPv6 | Запросить пару `A` + `AAAA` либо включить IPv6 на сети |
| `SERVFAIL` на внешнее имя внутри `--internal`-сети | Проксирование на upstream отключено намеренно | `docker network inspect <net> --format '{{.Internal}}'` | Добавить контейнеру вторую сеть с выходом |
| После `docker compose up -d` клиент идёт на старый адрес | TTL 600 с, адрес контейнера изменился | `docker exec <c> getent hosts <alias>` | Healthcheck с проверкой разрешения, уникальные имена |
| Имя разрешается, соединение не устанавливается | Проблема не в DNS | `nc -zv <ip> <port>` из контейнера | См. диагностику сетевых проблем |

Версии движка, в которых исправлялись ошибки именно этого контура:

| Версия | Что исправлено |
| :--- | :--- |
| 29.8.0 | Имена сервисов Swarm переставали разрешаться на узле после пропуска анонса членства в сети (moby/moby#53437) и после кратковременного отказа узла (moby/moby#53142) |
| 29.6.0 | Гонка при массовой синхронизации overlay-сети давала задержки разрешения около 30 с на новых узлах Swarm (moby/moby#52862). Добавлено предупреждение об устаревании `links` в сети `bridge` |
| 29.5.0 | Устаревшие VIP DNS-записи псевдонимов сервисов Swarm не удалялись при rolling update (moby/moby#52236) |
| 29.3.0 | Повреждение DNS-конфигурации при `docker daemon reload` (moby/moby#52060) |
| 29.1.1 | Исправлена регрессия 29.1.0: разрешение **внешних** имён переставало работать на пользовательских сетях при пустом списке upstream |

Обновляйте движок и после обновления прогоняйте сценарий 4 на существующем окружении: часть этих регрессий проявляется только на контейнерах, созданных предыдущей версией.

## Рекомендации

### Проектирование

1. **Никаких production-контейнеров в сети `bridge` по умолчанию.** Встроенного резолвера там нет. В Compose пользовательская сеть создаётся автоматически, при `docker run` нужен явный `--network`.
2. **Задавайте псевдонимы явно и проверяйте, что они не пересекаются.** Неоднозначный псевдоним разрешается в несколько адресов, и какой контейнер имеется в виду, не гарантировано.
3. **Не рассчитывайте на балансировку средствами Docker.** Встроенный резолвер возвращает все адреса в случайном порядке. Балансировку реализуйте на клиенте, с перебором всех адресов.
4. **Планируйте клиентский кэш.** TTL 600 с означает, что приложение вправе десять минут держать адрес уже несуществующего контейнера.
5. **Отделяйте сеть с данными от сети с выходом.** `--internal` даёт и изоляцию, и отключение DNS-проксирования — второй эффект обычно ошибочно принимают за поломку.
6. **Имена, генерируемые автоматически, не разворачиваются.** Если имя должно быть адресуемым, задавайте его явно.

### Эксплуатация и наблюдаемость

1. **Добавляйте healthcheck, проверяющий разрешение имени**, если приложение обращается к соседнему сервису по имени. Это превращает смену адреса из лавины ошибок в отказ одного контейнера.
2. **Держите `journalctl -u docker` с фильтром по `[resolver]`** под рукой. Сообщения демона однозначно указывают направление поиска: неизвестный upstream, отказ upstream, исчерпание лимита в 1024 запроса.
3. **Проверяйте обновления движка в staging на реальной нагрузке.** Функциональные тесты на свежей установке проходят, а production ломается именно на контейнерах, созданных предыдущей версией.
4. **Не ориентируйтесь на `dig` как на проверку работоспособности приложения.** Он обходит `/etc/hosts` и NSS.
5. **Указывайте корпоративные DNS явно, а не полагайтесь на наследование от хоста.** Явное перечисление в `daemon.json` — воспроизводимая конфигурация, а не результат состояния `systemd-resolved` на конкретной машине.

### Откат изменений

Все перечисленные изменения обратимы, но требуют пересоздания контейнеров: `resolv.conf` и реестр имён формируются при создании, а не применяются к работающему контейнеру.

```bash
# Откат daemon.json
sudo cp /etc/docker/daemon.json.bak /etc/docker/daemon.json
sudo systemctl restart docker

# Пересоздание контейнеров, получивших настройки при создании
docker compose down && docker compose up -d

# Проверка, что имена снова разрешаются
docker exec <container> getent hosts <service_name>
# → 172.18.0.4   api

# Очистка сетевых артефактов
docker network disconnect app-net redis && docker network rm app-net
```

На уровне Compose откат — удалить ключи `dns`, `dns_search`, `dns_opt` из сервиса и выполнить `docker compose up -d --force-recreate`. Удаление этих ключей возвращает поведение к унаследованному от хоста, а не к состоянию «до явной настройки».

## Дополнительная информация

### Ограничения, о которых стоит знать заранее

- **TTL ответов встроенного резолвера — 600 секунд.** Адрес контейнера может быть устаревшим до 10 минут после пересоздания.
- **Локально обслуживаются только `A`, `AAAA`, `MX`, `PTR` и `SRV`.** Остальные типы запросов всегда уходят наверх.
- **Резолвер проксирует запросы последовательно, максимум на 3 сервера, с таймаутом 4 с.** Параллельного опроса, как в musl, нет.
- **Лимит 1024 одновременных внешних запросов** даёт `REFUSED`, а не таймаут.
- **Ответы по UDP усекаются удалением записей**, а не флагом обрезки отдельных RR. Часть реплик может не попасть в ответ.
- **Порядок адресов при нескольких контейнерах под именем перемешивается случайно** при каждом запросе.
- **IPv6-эквивалента у `127.0.0.11` нет**, и сам резолвер недоступен ни с хоста, ни из других контейнеров.
- **`--dns`, `--dns-search`, `--dns-option`, `--add-host` не принимаются** в режимах `host` и `container:<id>` — демон возвращает ошибку `conflicting options` на этапе создания, а не игнорирует значения молча.
- **Алиас не работает в сети `bridge` по умолчанию.** Ошибка `network-scoped aliases are only supported for user-defined networks`.
