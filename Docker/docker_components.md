### Что такое контейнер?

**Контейнер** — это изолированный процесс (PID) (или группа процессов), работающий в собственном окружении, отделенном от основной операционной системы. Эта изоляция достигается с помощью двух ключевых механизмов ядра Linux: **namespaces** и **cgroups**.

Важно понимать, что **процессы в контейнере — это обычные процессы хост-системы**. Docker лишь создает для них иллюзию работы в отдельной машине. Если найти PID процесса внутри контейнера (`docker top <имя_контейнера>`) и затем поискать его на хосте (`ps aux | grep <PID>`), вы увидите тот же самый процесс.

### Образ и Контейнер

Это ключевые понятия, которые удобно объяснять через аналогию с программированием:

> **Образ (Image)** — это неизменяемый (immutable) шаблон, который содержит все необходимое для запуска приложения: код, библиотеки, переменные окружения и конфигурационные файлы. Образы состоят из слоев, доступных только для чтения. **Это как класс в ООП.**

> **Контейнер (Container)** — это запущенный экземпляр образа. При запуске Docker добавляет поверх неизменяемых слоев образа один **записываемый слой (writable layer)**, где хранятся все изменения. **Это как объект (экземпляр класса).**

### Ключевое отличие от виртуальных машин

| Характеристика | Контейнеры | Виртуальные машины (ВМ) |
| :--- | :--- | :--- |
| **Ядро ОС** | Используют ядро хост-системы | Имеют собственное, гостевое ядро ОС |
| **Изоляция** | На уровне процессов (namespaces, cgroups) | Полная, на уровне аппаратной эмуляции |
| **Ресурсы** | Легковесные, минимальные накладные расходы | Потребляют значительные ресурсы (RAM, CPU) |
| **Запуск** | Мгновенный (миллисекунды) | Медленный (минуты) |

Из-за общего ядра **невозможно** запустить контейнер, созданный для одной ОС, на ядре другой. Например, Windows-контейнеры(Docker на Windows это вообще контейнер так как ядро Linux надо где-то запустить) требуют системных вызовов ядра Windows NT, которых нет в ядре Linux.

### До контейнеров: `chroot`

До появления современных контейнерных технологий для изоляции файловой системы использовалась утилита `chroot` (change root). Она позволяла изменить корневой каталог для процесса, делая невозможным доступ к файлам за его пределами.

Однако у `chroot` были существенные ограничения:
*   **Неполная изоляция:** Процесс все еще мог взаимодействовать с другими процессами, использовать тот же сетевой стек и не имел ограничений по ресурсам.
*   **Только файловая система:** Изоляция касалась только видимости файлов, но не других системных ресурсов.

### Namespaces

**Namespaces (пространства имен)** создают для процесса изолированное представление о системных ресурсах. Каждый контейнер получает свой набор пространств имен, не пересекающийся с хостом.

- **PID Namespace:** Изоляция процессов. Процесс внутри контейнера видит себя как PID 1.
- **Mount Namespace:** Изоляция файловой системы. У контейнера свой корневой каталог (`/`).
- **Network Namespace:** Изоляция сети. Свой сетевой стек, IP-адреса и порты.
- **UTS Namespace:** Изоляция имени хоста и домена (`hostname`).
- **IPC Namespace:** Изоляция межпроцессного взаимодействия (System V IPC, POSIX message queues).
- **User Namespace:** Изоляция ID пользователей и групп. Позволяет маппинг пользователя root в контейнере на обычного пользователя на хосте.
- **Cgroup Namespace:** Изоляция представления о cgroups.
- **Time Namespace:** Изоляция системного времени.

### Cgroups: Управление ресурсами

**Control Groups (cgroups)** — это механизм ядра, который ограничивает и учитывает потребление ресурсов группой процессов (CPU, память, IO и т.д.). Если `namespaces` изолируют видимость, то `cgroups` лимитируют использование.

## Архитектура Docker

Docker использует клиент-серверную архитектуру. Важно понимать, какие компоненты и как именно общаются друг с другом:

**`docker` (CLI)  <-[ `REST API` ]->  `dockerd` (демон)  <-[ `gRPC` ]->  `containerd`  ->  `runc`**

1.  **Клиент (`docker` CLI) и Демон (`dockerd`):**
    *   **Протокол:** `REST API`.
    *   **Как:** Клиент `docker` **не общается с демоном напрямую**. Он отправляет HTTP-запросы на REST API, который слушает демон `dockerd`.
    *   **Сокет:** По умолчанию это локальный Unix-сокет `/var/run/docker.sock`. Именно в этот файл `docker` CLI пишет свои API-запросы. Однако, демон можно настроить на прослушивание сетевого TCP-сокета (например, `tcp://0.0.0.0:2375`), что позволяет удаленно управлять Docker, но необходимо задуматься о безопасности этого соединения.

2.  **Демон (`dockerd`) и `containerd`:**
    *   **Протокол:** `gRPC`. 
    *   **Как:** `dockerd` больше не управляет контейнерами напрямую. Он выступает в роли API-сервера и менеджера сетей/вольюмов. Для всех операций с жизненным циклом контейнеров (создать, запустить, остановить) `dockerd` обращается к другому демону — `containerd`.
    *   **Сокет:** Это общение происходит через другой Unix-сокет, обычно `/run/containerd/containerd.sock`.

Такое разделение (`dockerd` и `containerd`) было сделано для соответствия стандарту **CRI (Container Runtime Interface)**, что позволило отделить логику Docker от универсальной логики управления контейнерами. Это также повышает стабильность: перезапуск демона `dockerd` не останавливает уже запущенные контейнеры, так как ими продолжает управлять `containerd`.

### Ключевые стандарты: CRI и OCI

*   **Open Container Initiative (OCI) spec:** Определяет стандартизированный формат образа контейнера и его среды выполнения (runtime). Это позволяет различным инструментам (Docker, Podman, etc.) работать с одними и теми же образами. OCI также предлагает эталонную реализацию runtime — `runc`.

*   **Container Runtime Interface (CRI):** Это API, который позволяет `kubelet` (агенту Kubernetes) взаимодействовать с различными средами выполнения контейнеров (`containerd`, `CRI-O`). До появления CRI, `kubelet` был тесно интегрирован с Docker. CRI абстрагирует эту зависимость.

Схема работы в Kubernetes:

1.  `kubelet` делает `gRPC` вызов через **CRI API** к демону (`containerd` или `CRI-O`).
2.  CRI-совместимый демон принимает запрос.
3.  Демон вызывает низкоуровневую, **OCI**-совместимую среду выполнения (`runc`, `crun`, `kata-runtime`).
4.  OCI-runtime создает контейнер.

Подробнее о различных средах выполнения, совместимых с OCI и CRI, можно прочитать в документе об **[альтернативных средах выполнения и инструментах](./alternative_runtimes_and_tools.md)**.

### Компоненты и их роли

*   **Docker Daemon (`dockerd`):** Высокоуровневый компонент.
    *   Предоставляет `REST API` для клиентов.
    *   Управляет образами, сетями, томами (volumes) и секретами.
    *   Передает команды на управление контейнерами демону `containerd`.

*   **`containerd`**: Универсальный демон-менеджер контейнеров.
    *   Принимает команды от `dockerd` по `gRPC`.
    *   Управляет полным жизненным циклом контейнеров: загрузка и хранение образов, создание, запуск и остановка контейнеров.
    *   Является проектом [CNCF](../cncf_overview.md) и может использоваться независимо от Docker, например, в Kubernetes через свой `cri plugin`.
    *   Для фактического запуска контейнера вызывает низкоуровневый OCI-совместимый runtime.

*   **`runc`**: Низкоуровневая среда выполнения (runtime).
    *   Это эталонная реализация спецификации **OCI (Open Container Initiative)**, написанная на Go.
    *   Получает от `containerd` конфигурацию контейнера и непосредственно взаимодействует с ядром Linux для создания `namespaces` и `cgroups`, запуская изолированный процесс.
    *   Существуют и альтернативные OCI-совместимые среды выполнения, такие как `crun` (написана на C, отличается высокой производительностью и низким потреблением памяти).

**Итоговый процесс запуска:**

1.  Пользователь выполняет `docker run ...`.
2.  CLI `docker` отправляет `POST` запрос на `/containers/create` и `/containers/{id}/start` на `REST API` демона `dockerd` через сокет `/var/run/docker.sock`.
3.  `dockerd` получает запрос, обрабатывает его и делает `gRPC` вызов к `containerd` через сокет `/run/containerd/containerd.sock`.
4.  `containerd` использует `runc` для создания и запуска контейнера с нужными `namespaces` и `cgroups`.
5.  `runc` запускает процесс внутри контейнера.

### **Слоеная файловая система: OverlayFS**

Docker использует **storage drivers** для управления слоями образов. Самый распространенный драйвер — **[OverlayFS](./docker_overlayfs.md)**. Он "накладывает" файловую систему контейнера поверх файловой системы образа.

*   **Нижние слои (lowerdir):** Слои образа, доступны только для чтения.
*   **Верхний слой (upperdir):** Записываемый слой контейнера. Все изменения (создание, изменение, удаление файлов) происходят здесь.
*   **Результат (merged):** Виртуальное объединение всех слоев, которое видит процесс в контейнере.

Эта система позволяет эффективно хранить образы (общие слои переиспользуются) и мгновенно создавать контейнеры.

### **Docker Registry: Хранилище образов**

**Registry** — это сервис для хранения и распространения образов Docker.
*   **[Docker Hub](./docker_registries.md):** Публичный реестр по умолчанию.
*   Существуют и частные (private) решения, такие как Harbor, GitLab Container Registry или Nexus.
