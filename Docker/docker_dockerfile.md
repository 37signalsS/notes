# Dockerfile

Добавить пользователя в группу `docker` для безпарольного использования docker-ом:

```sh
sudo usermod -aG docker ubuntu
```

Подробнее о компонентах Docker, включая детальное описание контейнеров, можно прочитать в [соответствующем документе](./docker_components.md).

### Слои (Layers) и Rootfs

**Слои (Layers):** Основные команды, создающие слои:

*   **`RUN`**: Выполняет команду и фиксирует изменения в новом слое.
*   **`COPY`**: Копирует файлы с хоста в контейнер, создавая новый слой.
*   **`ADD`**: Аналогично `COPY` создает слой.

Инструкции, которые не изменяют файловую систему (например, `ENV`, `EXPOSE`, `CMD`, `ENTRYPOINT`, `LABEL`), не создают новых слоев, а лишь добавляют метаданные к образу.

**Rootfs (корневая файловая система)** — это совокупность всех слоев, из которых состоит [образ](./docker_images.md). Когда вы запускаете контейнер, Docker берет эту файловую систему (которая доступна только для чтения) и добавляет поверх нее еще один, записываемый слой. Все изменения, которые происходят во время работы контейнера (создание, изменение, удаление файлов), записываются именно в этот верхний слой. За техническую реализацию этого механизма отвечает драйвер хранения, чаще всего **[OverlayFS](./docker_overlayfs.md)**.

### Контекст сборки (Build Context) и .dockerignore

**Контекст сборки** — это набор файлов, которые Docker CLI отправляет демону Docker для создания образа. Демон может использовать любой из этих файлов в инструкциях `COPY` или `ADD`. Контекст можно указать тремя способами:

1.  **`PATH` (локальная директория):**
    -   `docker build .`
    -   Самый распространенный способ. В качестве контекста используется текущая директория. Все ее содержимое (с учетом `.dockerignore`) упаковывается в tar-архив и отправляется демону.

2.  **`URL` (Git-репозиторий):**
    -   `docker build github.com/user/repo`
    -   Docker автоматически клонирует репозиторий по указанному URL во временную директорию и использует ее как контекст сборки.

3.  **`-` (стандартный ввод, STDIN):**
    -   `docker build - < context.tar.gz`
    -   Позволяет передать контекст сборки через стандартный ввод, обычно в виде сжатого архива. Это полезно для автоматизации и сложных сборочных пайплайнов, так как не требует записи файлов на диск.

**.dockerignore:** Файл `.dockerignore` работает по аналогии с `.gitignore`. Он позволяет исключить файлы и директории из контекста сборки, который отправляется демону Docker.

**Практический пример организации:**

Часто `Dockerfile` хранят в отдельной поддиректории (например, `docker/` или `build/`), чтобы не загромождать корень проекта. Однако, сборку обычно запускают из корня проекта, чтобы контекст сборки включал все исходные файлы приложения.

-   **Команда сборки из корня:**
    ```bash
    # Указываем путь к Dockerfile с помощью флага -f
    docker build -f docker/Dockerfile .
    ```
-   **Расположение `.dockerignore`:** В этом сценарии файл `.dockerignore` **должен** находиться в корне проекта (рядом с `src/`, `package.json` и т.д.), а не рядом с `Dockerfile`. Это связано с тем, что контекст сборки (`.` в команде выше) — это корень проекта, и `.dockerignore` применяется именно к нему.

### BuildKit: Современный движок сборки

**BuildKit** — это современный движок для сборки образов, который предоставляет множество улучшений по сравнению со старым сборщиком:

- **Параллельное выполнение:** Этапы сборки, которые не зависят друг от друга, выполняются параллельно.
- **Улучшенное кэширование:** Более эффективно определяет, какие слои можно взять из кэша.
- **Работа с секретами:** Позволяет безопасно использовать секреты во время сборки без их сохранения в финальном образе (`--mount=type=secret`).

В современных версиях Docker (Docker Desktop, Docker Engine v23.0+) BuildKit **включен по умолчанию**. В более старых версиях его можно было активировать, установив переменную окружения `DOCKER_BUILDKIT=1` перед вызовом команды `docker build`.

Для интерактивной отладки Dockerfile, основанной на BuildKit, существует инструмент **[buildg](./alternative_runtimes_and_tools.md#инструменты-для-сборки-и-отладки)**.

## Основные инструкции Dockerfile

#### FROM

Какой базовый образ взять. Для большей безопасности от подмены образа(на Docker Hub могут перезаписать, но хэш будет другим) можно указать хэш образа (`FROM <image>@sha256:<digest>`). Дайджест (хэш) образа можно увидеть в выводе команды `docker pull my-image:tag`.

Если тег не указан (например, `FROM debian`), Docker по умолчанию будет использовать тег `latest`. **Важно:** при изменении образа latest(что будет происходить очень часто) образ будет билдиться по-новой.

#### LABEL

Присвоение меток.

#### ARG и ENV

- **`ARG` (переменная времени сборки):**

  - Доступна **только** в процессе сборки образа (`docker build`).
  - Не сохраняется в конечном образе и недоступна для запущенного контейнера.
  - Используется для параметризации сборки: передачи версий, токенов или для включения отладочных инструментов.
  - Пример:
    ```dockerfile
    ARG APP_VERSION=1.0
    RUN echo "Собирается версия: $APP_VERSION"
    ```
    Переопределить значение можно командой: `docker build --build-arg APP_VERSION=2.1 .`

- **`ENV` (переменная среды выполнения):**

  - Устанавливает переменные окружения, которые доступны как во время сборки, так и внутри запущенного контейнера.
  - Сохраняется в образе.
  - Используется для конфигурации приложения: URL базы данных, порты, ключи API.
  - Пример:
    ```dockerfile
    ENV DB_HOST=localhost
    CMD ["echo", "Подключение к $DB_HOST"]
    ```
    Переопределить значение можно командой: `docker run -e DB_HOST=db.example.com my-image`

**Совместное использование:**

Часто `ARG` используют для установки значения `ENV` по умолчанию.

```dockerfile
ARG APP_PORT=8080
ENV PORT=${APP_PORT}
EXPOSE ${PORT}
```

#### ENV PYTHONUNBUFFERED=1

Эта инструкция особенно важна для Python-приложений. По умолчанию Python буферизирует потоки `stdout` и `stderr`. Это означает, что данные, выводимые вашим приложением (например, через `print()`), не сразу появляются в логах Docker. Они накапливаются в буфере и выводятся только при его заполнении или при завершении процесса.

Установка `ENV PYTHONUNBUFFERED=1` отключает эту буферизацию, и все выводы сразу направляются в [логи](./docker_logs_and_metrics.md) контейнера. Это критически важно для отладки, так как позволяет видеть логи в реальном времени.

#### RUN

Какая команда выполнится во время сборки данного образа.

- **Надежные скрипты с `set -ex` при написании многострочных `RUN` команд**

```dockerfile
RUN set -ex && \
    apt-get update && \
    apt-get install -y curl && \
    rm -rf /var/lib/apt/lists/*
```

*   `set -e`: **Exit Immediately.** Если какая-либо команда завершится с ошибкой (ненулевым кодом выхода), выполнение всей `RUN` инструкции немедленно прекратится. Без этого флага Docker продолжит выполнение следующих команд, как будто ничего не произошло, и сборка может успешно завершиться, скрыв проблему.
*   `set -x`: **Print Commands.** Перед выполнением каждой команды она будет напечатана в лог сборки. Это помогает четко видеть, какая именно команда выполняется в данный момент и какие у нее аргументы, что неоценимо при отладке.

- **Кэширование зависимостей:**

`--mount=type=cache` позволяет монтировать кэш в процессе выполнения `RUN`. Это ускорит повторные сборки, так как, например, зависимости будут взяты из кэша, который хранится на хосте. Кэш не попадёт в финальный образ, но будет доступен для повторного использования.

```dockerfile
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
```

- **Bind mounts при сборке:**

`--mount=type=bind` позволяет монтировать директорию или файл с хостовой системы в контейнер во время выполнения команды `RUN`. В отличие от `COPY`, данные не копируются в образ, а временно подключаются с хоста для процесса сборки.

```dockerfile
RUN --mount=type=bind,source=./src,target=/app/src \
    go build -o app ./src
```

- **Работа с секретами:**

`--mount=type=secret` временно монтирует секрет с хоста и не хранит его в финальном образе.

```dockerfile
RUN --mount=type=secret,id=ssh,target=/root/.ssh/id_rsa \
    git clone git@github.com:user/repo.git .\
    
RUN --mount=type=secret,id=api_key,target=/run/secrets/api_key \
    export API_KEY=$(cat /run/secrets/api_key) && \
    pip install --extra-index-url https://$API_KEY@private-repo.com/packages some-package
```

#### COPY и ADD

Обе инструкции служат для копирования файлов в образ, но имеют ключевые различия.

*   **`COPY`**:

    *   **Назначение:** Простое копирование файлов и директорий из контекста сборки в файловую систему контейнера.
    *   **Пример:** `COPY ./app.py /app/`

*   **`ADD`**:

    *   **Возможности:** Включает в себя всю функциональность `COPY`, но с двумя дополнительными возможностями:
        1.  **Загрузка по URL:** Может скачивать файлы из интернета (`ADD http://example.com/file /dest/`).
        2.  **Распаковка архивов:** Автоматически распаковывает локальные архивы в форматах `tar`, `gzip`, `bzip2` или `xz` в директорию назначения (`ADD archive.tar.gz /dest/`).
    *   **Риски:** Автоматическая распаковка и загрузка по URL могут приводить к непредсказуемым результатам и создавать угрозы безопасности.

> **Лучшая практика (Best Practice):**
> Официальная документация Docker рекомендует **всегда отдавать предпочтение `COPY`**, если вам не требуется дополнительная функциональность `ADD`. `COPY` более прозрачен и предсказуем. Для загрузки и распаковки файлов лучше использовать явные команды в инструкции `RUN`, например, `RUN curl -SL ... | tar -xz`. Это делает `Dockerfile` более читаемым и безопасным.

#### WORKDIR

Текущий каталог при старте контейнера (если каталога не существует, то он будет создан).

#### EXPOSE

Инструкция `EXPOSE` информирует Docker о том, что контейнер прослушивает указанные сетевые порты во время выполнения. Важно понимать, что `EXPOSE` — это исключительно **декларативная** инструкция(не открывает и не публикует порты). Она выполняет две функции:

1.  **Документация:** Служит подсказкой для пользователя, который будет запускать образ, о том, какие порты предназначены для публикации.
2.  **Автоматическая публикация:** При использовании флага `-P` (публикация всех *exposed* портов) в команде `docker run`, Docker использует эту информацию для автоматического проброса портов на случайные порты хоста.

#### ENTRYPOINT vs CMD

*   **`CMD`**: Определяет **команду по умолчанию** и/или параметры/аргументы для того что запускаеться в `ENTRYPOINT`. Эту инструкцию **легко переопределить** при запуске контейнера.
*   **`ENTRYPOINT`**: Определяет **основной исполняемый файл/программа/бинарник**, который запускается всегда. Аргументы из `docker run` или `command` в Compose **добавляются** к `ENTRYPOINT`.

**Золотое правило:** `docker-compose.yml` (или `docker run`) всегда имеет приоритет над `Dockerfile`.

1.  `command:` в `compose.yml` (или аргументы в `docker run`) **заменяет** `CMD` из `Dockerfile`.
2.  `entrypoint:` в `compose.yml` (или `--entrypoint` в `docker run`) **заменяет** `ENTRYPOINT` из `Dockerfile`.

| В `Dockerfile` | В `docker-compose.yml` / `docker run` | Что в итоге запустится |
| :--- | :--- | :--- |
| `ENTRYPOINT ["/app/run"]`<br>`CMD ["--default"]` | (ничего не указано) | `/app/run --default`<br>*(Используются оба значения из Dockerfile)* |
| `ENTRYPOINT ["/app/run"]`<br>`CMD ["--default"]` | `command: --prod` | `/app/run --prod`<br>*(**`command` заменил `CMD`**. ENTRYPOINT остался)* |
| `ENTRYPOINT ["/app/run"]` | `entrypoint: /app/debug` | `/app/debug`<br>*(entrypoint заменил ENTRYPOINT. CMD исчез)* |
| `ENTRYPOINT ["/app/run"]`<br>`CMD ["--default"]` | `entrypoint: /app/debug`<br>`command: --verbose` | `/app/g/debug --verbose`<br>*(Заменились и ENTRYPOINT, и CMD)* |

**Практический пример**

Допустим, у вас есть `Dockerfile`:
```dockerfile
FROM alpine:3.20.0
ENTRYPOINT ["ping", "-c", "3"]
CMD ["localhost"]
```
По умолчанию этот контейнер будет пинговать `localhost`.

Теперь в `docker-compose.yml` вы хотите пинговать другой хост:

```yaml
services:
  pinger:
    build: .
    command: google.com
```

Когда вы запустите `docker compose up`, выполнится команда `ping -c 3 google.com`, потому что `command: google.com` из `compose.yml` заменил `CMD ["localhost"]` из `Dockerfile`.

**Запуск приложений в режиме Foreground:**

Ключевой практикой в Docker является запуск основного процесса в режиме "переднего плана" (foreground), а не в режиме демона (background).

*   **Почему это важно?** Docker отслеживает основной процесс (CMD или ENTRYPOINT), запущенный в контейнере (тот, у которого PID 1). Как только этот процесс завершается, Docker считает, что работа контейнера окончена, и останавливает его.
*   **Что происходит с демонами?** Процесс, запущенный в режиме демона, сразу же отсоединяется от терминала и уходит в фон. Для Docker это выглядит так, как будто основной процесс завершился, и контейнер будет немедленно остановлен.

#### STOPSIGNAL

Определяет сигнал операционной системы, который будет отправлен основному процессу (PID 1) внутри контейнера при его остановке. По умолчанию Docker отправляет сигнал `SIGTERM` (15), чтобы корректно завершить процесс. Если процесс не завершается после отправки `SIGTERM`, через некоторое время (по умолчанию 10 секунд) Docker отправляет сигнал `SIGKILL` (9), который принудительно завершает процесс.

#### SHELL

Выбор оболочки для выполнения `RUN`.

#### HEALTHCHECK

Инструкция `HEALTHCHECK` встраивает в образ механизм для проверки работоспособности приложения внутри контейнера. Docker периодически выполняет указанную команду и на основе ее кода завершения определяет состояние контейнера:

- `0`: `healthy` (здоров)
- `1`: `unhealthy` (нездоров)

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost/ || exit 1
```

## Оптимизация Сборки

### Оптимизация кеширования слоёв

- **Зависимости меняются редко:** Файл с перечислением зависимостей (`requirements.txt`, `package.json`, `go.mod` и т.д.) обновляется гораздо реже, чем исходный код приложения.
- **Код меняется постоянно:** Вы меняете код при каждом исправлении бага или добавлении новой функции.

Разделяя эти два шага, вы создаете отдельный, долгоживущий кешированный слой для зависимостей, который не будет пересобираться при каждом изменении кода.

**Плохой пример:**

```dockerfile
FROM python:3.13-slim-bookworm
COPY . .

# Устанавливаем зависимости
RUN pip install -r requirements.txt

CMD ["python", "main.py"]
```
**Проблема:** При любом изменении в коде приложения, слой `COPY . .` становится невалидным. Это делает невалидными все последующие слои, и Docker будет **каждый раз заново** выполнять дорогостоящую команду `RUN pip install...`.

**Хороший пример:**

```dockerfile
FROM python:3.13-slim
WORKDIR /app

# 1. Копируем только файл с зависимостями
COPY requirements.txt .

# 2. Устанавливаем зависимости. Этот слой будет закеширован.
RUN pip install -r requirements.txt

# 3. Только теперь копируем остальной код приложения
COPY . .

CMD ["python", "main.py"]
```
**Результат:** Теперь, если вы меняете только код приложения, Docker использует кеш для слоя с `RUN pip install`. Пересборка происходит почти мгновенно, так как пересоздается только последний, очень "легкий" слой `COPY . .`.

Этот принцип можно развить дальше. Если у вас несколько инструкций `COPY`, их следует упорядочить **от наименее часто изменяемых файлов к наиболее часто изменяемым**.

**Пример для Node.js: `npm ci` для воспроизводимых сборок**

Для production-сборок **всегда следует использовать `npm ci` вместо `npm install`**.

-   **`npm install`**: Может изменять `package-lock.json`, если `package.json` был обновлен. Это подходит для разработки, но опасно для CI/CD, так как сборки могут быть непредсказуемыми.
-   **`npm ci` (Clean Install)**: Гарантирует **воспроизводимую сборку**. Команда удаляет `node_modules`, устанавливает зависимости **строго** по версиям из `package-lock.json` и никогда не изменяет этот файл. Если `package.json` и `package-lock.json` не синхронизированы, `npm ci` завершится с ошибкой, предотвращая сборку с некорректными зависимостями.

#### `dependencies` vs `devDependencies`

В файле `package.json` зависимости делятся на два типа:

-   **`dependencies`**: Пакеты, необходимые для работы приложения в production (например, `express`, `react`).
-   **`devDependencies`**: Пакеты, нужные только для разработки и тестирования (например, `jest`, `eslint`, `nodemon`).

Флаг `--only=production` (или его аналог `--production`) указывает `npm` устанавливать **только** пакеты из раздела `dependencies`. Это критически важно для Docker-образов, так как исключает ненужные инструменты разработки, делая итоговый образ меньше и безопаснее.

Оптимизированный `Dockerfile` для Node.js-приложения:

```dockerfile
# 1. package.json и package-lock.json меняются редко
COPY package.json package-lock.json ./

# 2. Устанавливаем ТОЛЬКО production-зависимости. Слой кешируется.
# Используем npm ci для быстрых и надежных сборок.
RUN npm ci --only=production

# 3. Копируем остальной код приложения
COPY . .
```
Таким образом, изменение в коде не приведет к переустановке `node_modules`, а `npm ci` обеспечит идентичность зависимостей в каждой сборке.

### Сборка без Docker-демона: Kaniko

**Проблема:** В некоторых средах, особенно в CI/CD-пайплайнах (например, GitLab CI, Jenkins) или внутри Kubernetes-подов, отсутствует доступ к демону Docker. Запуск "Docker-in-Docker" (dind) для решения этой проблемы является сложным, небезопасным и ресурсоемким.

**Решение:** **Kaniko** — это инструмент от Google, написанный на Go, который собирает образы из `Dockerfile` **без какой-либо зависимости от Docker-демона**.

**Как это работает:**
Kaniko выполняет каждую команду из `Dockerfile` внутри пользовательского пространства (userspace) внутри своего же контейнера. Он извлекает файловую систему базового образа, применяет команды для создания слоев и в конце отправляет собранный образ в указанный реестр.

**Преимущества:**
-   **Безопасность:** Не требует привилегированного доступа или монтирования Docker-сокета.
-   **Простота:** Запускается как обычный контейнер одной командой.
-   **Идеально для Kubernetes:** Позволяет собирать образы прямо в кластере без предоставления рабочим узлам доступа к Docker-демону.

**Пример использования в CI/CD:**
```yaml
# Пример задачи для GitLab CI
build_image:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:v1.9.0-debug
    entrypoint: [""]
  script:
    # Создаем файл аутентификации для реестра
    - echo "{\"auths\":{\"$CI_REGISTRY\":{\"username\":\"$CI_REGISTRY_USER\",\"password\":\"$CI_REGISTRY_PASSWORD\"}}}" > /kaniko/.docker/config.json
    # Запускаем сборку
    - /kaniko/executor
      --context $CI_PROJECT_DIR
      --dockerfile $CI_PROJECT_DIR/Dockerfile
      --destination $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
```

### Многоэтапные (Multi-stage) сборки


**Проблема:**

Для сборки компилируемых приложений (например, на Go или Java) нужен "тяжелый" образ с компилятором и SDK. Для запуска скомпилированного приложения нужен только легковесный образ (например, `alpine` или `scratch`).

```dockerfile
# --- Этап 1: Сборка (Builder) ---
# Начинаем с полного образа Go, который содержит все инструменты для сборки.
# Даем этому этапу имя "builder" для удобства.
FROM golang:1.25.1 AS builder

WORKDIR /app

COPY go.mod go.sum ./
RUN go mod download

COPY . .

# Собираем статически скомпонованный бинарник.
RUN CGO_ENABLED=0 go build -o /app/main .

# --- Этап 2: Финальный образ (Final) ---
# Начинаем с "пустого" образа scratch. В нем нет ничего, даже оболочки.
FROM scratch

WORKDIR / 

# Копируем ТОЛЬКО скомпилированный бинарный файл из этапа "builder".
COPY --from=builder /app/main .

ENTRYPOINT ["/main"]
```

## Безопасность

В этом разделе рассматриваются лучшие практики безопасности, применимые непосредственно при написании `Dockerfile`. Комплексное руководство по всем аспектам безопасности Docker, включая защиту демона, управление секретами и безопасность во время выполнения, находится в документе **[Безопасность Docker](./docker_security.md)**.

### Практика безопасности: Создание непривилегированного пользователя

`groupadd -r user` — Создание изолированной группы

*   **Что делает флаг `-r` (`--system`)?**
    Этот флаг указывает, что мы создаем **системную** группу. В Linux принято разделять сущности на "пользовательские" и "системные".

`useradd -r -s /bin/false -g user user` — Создание "бесправного" пользователя

*   **Что делает флаг `-r` (`--system`)?**
    Аналогично `groupadd`, этот флаг создает **системного пользователя** с UID из системного диапазона (1-999). Обычно для таких пользователей не создается домашняя директория и не устанавливается срок действия пароля.

*   **Что делает флаг `-s /bin/false`?**
    *   **`-s` (`--shell`)** задает пользователю **командную оболочку** (shell).
    *   **`/bin/false`** — блокирует любую возможность интерактивного входа. Если кто-то попытается войти в систему под этим пользователем, сессия тут же завершится. От имени пользователя можно запускать процессы, но залогиниться им нельзя.

*   **Что делает флаг `-g user`?**
    *   **`-g` (`--gid`)** устанавливает **основную группу** пользователя. Когда этот пользователь будет создавать файлы, они по умолчанию будут принадлежать группе `user`.
    *   Мы привязываем пользователя к специально созданной для него группе, что позволяет гибко настраивать права доступа.

#### Альтернатива для Alpine: `adduser`

В образах на базе Alpine Linux (как в примере) используется утилита `adduser`, которая является более высокоуровневой. Команда `adduser -D -H -s /bin/false nonroot` делает то же самое:

*   **`-D` (`--no-password`):** Создает пользователя без пароля.
*   **`-H` (`--no-create-home`):** Не создает домашнюю директорию.
*   **`-s /bin/false`:** Устанавливает оболочку в `/bin/false`.
*   **`nonroot`:** Имя пользователя.

#### Заключительный шаг: `USER`

После создания пользователя, в `Dockerfile` обязательно следует команда `USER nonroot` (или `USER user`), которая переключает контекст. Все последующие инструкции (`COPY`, `CMD`, `ENTRYPOINT`) будут выполняться уже от имени нашего нового, безопасного, непривилегированного пользователя.

### Обновление пакетов (`apt-get upgrade`) — плохая практика

1.  **Нарушение воспроизводимости (Broken Reproducibility):**
    *   Выполнение `apt-get upgrade` во время сборки делает образ зависимым от состояния репозиториев в данный конкретный момент. Повторная сборка того же Dockerfile через некоторое время может привести к установке других версий пакетов, что ведет к непредсказуемому поведению.

2.  **Проблемы с кешированием (Cache Busting):**
    *   Команда `apt-get upgrade` инвалидирует кеш для этого слоя и всех последующих слоев.

*   **Используйте актуальный базовый образ:** Вместо того чтобы обновлять старый образ, используйте более новую версию базового образа, в котором уже есть некоторые обновления (например, `debian:12.5` вместо `debian:12`).

### Python

1.  **Фиксируйте версии:**

    *   **Базовый образ:** Всегда указывайте конкретный тег версии в инструкции `FROM`.
    *   **Зависимости:** Используйте `pip freeze > requirements.txt` для создания точного списка зависимостей с версиями. Это обеспечивает воспроизводимость окружения.

2.  **Оптимизируйте кэширование слоев:**

    *   Сначала копируйте только `requirements.txt` и устанавливайте зависимости. И только потом копируйте остальной код приложения.
    *   Это позволяет Docker кэшировать слой с установленными зависимостями. Если вы меняете только код приложения, а не зависимости, сборка будет проходить значительно быстрее, так как слой с `pip install` не будет пересобираться.

    ```dockerfile
    WORKDIR /app

    # Сначала копируем только зависимости
    COPY requirements.txt .

    # Устанавливаем зависимости (этот слой будет кэширован)
    RUN pip install --no-cache-dir -r requirements.txt

    # Теперь копируем остальной код
    COPY . .

    CMD ["python", "main.py"]
    ```

3.  **Используйте `PYTHONUNBUFFERED=1`:**

4.  **Разделяйте задачи миграции и запуска приложения:**

    *   Не стоит запускать миграции базы данных и веб-сервер одной командой в `CMD` или `ENTRYPOINT`.
    *   **Причина:** Контейнер должен выполнять только один процесс. Если миграции завершатся с ошибкой, сервер все равно может запуститься, и наоборот.*
        *   **Вариант 1 (Переменная окружения):** Используйте переменную окружения для выбора действия.

          ```dockerfile
          # ...
          COPY entrypoint.sh /entrypoint.sh
          RUN chmod +x /entrypoint.sh
          ENTRYPOINT ["/entrypoint.sh"]
          ```

          **entrypoint.sh:**
          ```sh
          #!/bin/sh
          set -e

          if [ "$MODE" = "migrate" ]; then
              echo "Running database migrations..."
              python manage.py migrate
          elif [ "$MODE" = "start" ]; then
              echo "Starting the application..."
              gunicorn myapp.wsgi:application --bind 0.0.0.0:8000
          else
              exec "$@"
          fi
          ```

          Запуск:
          ```sh
          # Запуск миграций
          docker run -e MODE=migrate my-app

          # Запуск приложения
          docker run -e MODE=start -p 8000:8000 my-app
          ```

        *   **Вариант 2 ([Docker Compose](./docker_compose.md)):** Для более сложных сценариев, где задачи (миграция, запуск сервера, воркеры) должны выполняться как отдельные, но связанные процессы, рекомендуется использовать Docker Compose. Он позволяет определить несколько сервисов, использующих один и тот же образ, но с разными командами. Подробнее об этом можно прочитать в [документе о Docker Compose](./docker_compose.md).

5.  **Multi-stage сборки для Python:**

    **Установка зависимостей в `--user`**

    Этот подход позволяет установить зависимости в домашний каталог пользователя, а затем скопировать их в финальный образ. Это проще, чем работа с `venv`.

    ```dockerfile
    # Этап 1: Сборщик (builder)
    FROM python:3.13 AS builder
    WORKDIR /app
    COPY requirements.txt .
    # Устанавливаем зависимости в локальный каталог пользователя
    RUN pip install --user -r requirements.txt

    # Этап 2: Финальный образ
    FROM python:3.12-slim-bookworm
    WORKDIR /app
    # Копируем установленные зависимости из сборочного образа
    COPY --from=builder /root/.local /root/.local
    # Добавляем директорию с бинарными файлами в PATH
    ENV PATH=/root/.local/bin:$PATH
    ENV PYTHONUNBUFFERED=1
    COPY myapp.py .
    CMD ["python", "myapp.py"]
    ```

    **Использование виртуального окружения (`venv`)**

    Этот подход более изолированный и считается лучшей практикой в мире Python. Виртуальное окружение полностью отделяет зависимости проекта.

    ```dockerfile
    # Этап 1: Сборщик (builder)
    FROM python:3.12 AS builder
    WORKDIR /app
    # Создаем виртуальное окружение
    RUN python3 -m venv /opt/venv
    # Активируем venv
    ENV PATH="/opt/venv/bin:$PATH"
    COPY requirements.txt .
    RUN pip install -r requirements.txt

    # Этап 2: Финальный образ
    FROM python:3.12-slim
    WORKDIR /code
    # Копируем виртуальное окружение из сборочного образа
    COPY --from=builder /opt/venv /opt/venv
    # Активируем venv в финальном образе
    ENV PATH="/opt/venv/bin:$PATH"
    # Вывод python логов в docker log в режиме реального времени
    ENV PYTHONUNBUFFERED=1
    COPY ./src .
    CMD ["python", "./server.py"]
    ```

6.  **Собирайте статику(файлы, которые не изменяются и не генерируются логикой вашего приложения в реальном времени. Они отдаются пользователю в том виде, в котором хранятся на диске) на этапе сборки (build-time):**

    *   **Неправильно:** Запускать `python manage.py collectstatic` в `ENTRYPOINT` или `CMD`. Это замедляет запуск контейнера и нарушает принцип неизменяемости, так как контейнер изменяет сам себя при старте.
    *   **Правильно:** Включить сборку статики в `Dockerfile` как одну из `RUN` инструкций. Это гарантирует, что все статические файлы уже "запечены" в образ.

    ```dockerfile
    # ... (установка зависимостей) ...

    COPY . .

    # Собираем статику на этапе сборки
    RUN python manage.py collectstatic --no-input --clear

    # CMD просто запускает веб-сервер
    CMD ["gunicorn", "myapp.wsgi:application"]
    ```
    `ENTRYPOINT` можно использовать для запуска проверок или миграций, но не для сборки статики.

### Java

1.  **Осведомленность о cgroups (Cgroup Awareness):**

    *   **Проблема:** Старые версии Java (до 8u131, например, Java 7) **не поддерживают [cgroups](./docker_components.md#cgroups-управление-ресурсами)**.
    *   **Решение:** Если вы вынуждены использовать старую, несовместимую с cgroups версию, вы **обязаны** вручную задавать размер кучи через флаги `-Xmx` и `-Xms`, чтобы JVM не выходила за рамки лимитов контейнера.

2.  **Multi-stage сборка:**

    Этот подход решает проблему "раздутых" образов, которые содержат ненужные для запуска артефакты: исходный код, компиляторы, сборочные инструменты (Maven/Gradle) и промежуточные файлы.

    -   **Этап 1 (builder):** Используется "тяжелый" образ с полным JDK и сборочным инструментом (например, `maven`). На этом этапе компилируется исходный код и собирается финальный артефакт (например, `.jar`-файл).
    -   **Этап 2 (final):** Используется минималистичный образ только со средой выполнения (например, `eclipse-temurin-jre`). С помощью `COPY --from=builder` из первого этапа копируется **только** скомпилированный `.jar`-файл.

    В итоге получается очень чистый и маленький образ, в котором нет ничего лишнего — только JRE и само приложение, что является лучшей практикой.

    ```dockerfile
    # Этап 1: Сборка с Maven
    FROM maven:3.9.11-eclipse-temurin-25 AS builder
    WORKDIR /app
    COPY pom.xml .
    # Используем кэширование зависимостей Maven
    RUN --mount=type=cache,target=/root/.m2 mvn dependency:go-offline
    COPY src ./src
    RUN mvn package

    # Этап 2: Финальный образ с OpenJDK
    FROM eclipse-temurin:21-jre-alpine
    WORKDIR /app
    # Копируем только собранный jar-файл
    COPY --from=builder /app/target/*.jar app.jar
    EXPOSE 8080
    CMD ["java", "-jar", "app.jar"]
    ```

3.  **Управление памятью:**

    *   **Ограничивайте размер кучи (heap):** Даже с современными версиями Java, рекомендуется явно задавать максимальный размер кучи. Это делает поведение приложения более предсказуемым.
        *   `-Xmx<size>`: Устанавливает максимальный размер кучи (например, `-Xmx512m`).
        *   `-XX:MaxRAMPercentage`: (Java 8u191+) Устанавливает максимальный процент от доступной контейнеру памяти, который будет использован для кучи. Например, `-XX:MaxRAMPercentage=75.0`.
    *   **Дайте контейнеру больше памяти:** Выделяйте контейнеру примерно на 25% больше памяти, чем вы установили в `-Xmx`. Это необходимо для нужд самой JVM (metaspace, потоки, нативная память).

4.  **Кэширование зависимостей:**

    *   Как показано в примере выше, используйте `--mount=type=cache` для кэширования директории `.m2` (для Maven) или `.gradle` (для Gradle). Это значительно ускоряет повторные сборки, так как зависимости не будут скачиваться каждый раз заново.

### Go

- **`FROM scratch`:** Можно запускать собранный бинарный файл в минималистичном образе `FROM scratch` для уменьшения размера и поверхности атаки.
- **`Makefile`:** При локальной сборке часто применяют `Makefile` для автоматизации шагов.

```dockerfile
# --- Этап 1: Сборка бинарного файла (builder) ---
FROM golang:1.25.1-alpine AS builder

# Устанавливаем git для скачивания зависимостей
RUN apk update && apk add --no-cache git

# Создаем пользователя без привилегий для безопасности
RUN adduser -D -u 10001 appuser

WORKDIR /app

# Копируем файлы зависимостей и загружаем их
# Этот слой кэшируется, если файлы не меняются
COPY go.mod go.sum ./
RUN go mod download
RUN go mod verify

# Копируем остальной исходный код
COPY . .

# Собираем статически скомпонованный бинарный файл
# Флаги -w -s удаляют отладочную информацию, уменьшая размер
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /app/main .

# --- Этап 2: Финальный образ ---
FROM scratch

# Копируем файлы пользователя и группы из builder'а,
# так как в scratch нет утилит для создания пользователей
COPY --from=builder /etc/passwd /etc/passwd
COPY --from=builder /etc/group /etc/group

# Копируем скомпилированный бинарный файл
COPY --from=builder /app/main /main

# Устанавливаем пользователя, от имени которого будет работать приложение
USER appuser

# Указываем порт, который слушает приложение (для информации)
EXPOSE 9292

# Точка входа: запускаем наше приложение
ENTRYPOINT ["/main"]
```

#### Решение проблемы "no such file or directory" в Alpine

При использовании многоэтапной сборки с Go, где на этапе сборки используется образ на базе Debian (например, `golang:1.25.1`), а на финальном этапе — `alpine`, вы можете столкнуться с ошибкой: `standard_init_linux.go:228: exec user process caused: no such file or directory`.

Эта ошибка означает не отсутствие исполняемого файла, а **отсутствие необходимых ему динамических библиотек**.

- Образ `golang` использует стандартную библиотеку C — **`glibc`**.
- Образ `alpine` использует легковесную альтернативу — **`musl libc`**.

Бинарный файл, скомпилированный в `glibc`-окружении, не может найти свои зависимости в `musl`-окружении.

Необходимо скомпилировать **полностью статически связанный (statically linked)** бинарный файл. Хотя `CGO_ENABLED=0` часто бывает достаточно, более надежный способ — явно указать линкеру флаги для статической сборки.

```dockerfile
FROM golang:1.25.1 AS builder

WORKDIR /app

COPY go.mod go.sum ./
RUN go mod download

COPY . .

# Собираем полностью статический бинарник, отключая Cgo и используя флаги линкера.
# -a: принудительно пересобрать все пакеты.
# -ldflags '-extldflags "-static"': указывает линкеру на статическую компоновку.
RUN CGO_ENABLED=0 GOOS=linux go build -a -ldflags '-extldflags "-static"' -o /app/main .

# Используем scratch или alpine для минимального размера
FROM alpine:3.22.2

# Копируем ТОЛЬКО скомпилированный бинарный файл из этапа "builder".
COPY --from=builder /app/main /main

# Добавляем права на исполнение (на всякий случай)
RUN chmod +x /main

ENTRYPOINT ["/main"]
```

### Ruby on Rails

```dockerfile
FROM ruby:3.4.6-slim-bookworm AS builder

# Устанавливаем системные зависимости для сборки гемов
RUN apt-get update -qq && \
    apt-get install --no-install-recommends -y build-essential git libpq-dev

WORKDIR /usr/src/app

# Устанавливаем Bundler
RUN gem install bundler

# Копируем Gemfile и устанавливаем зависимости
# Это кэшируется, если Gemfile не меняется
COPY Gemfile Gemfile.lock ./
RUN bundle config set --local without 'development test' && \
    bundle install --jobs $(nproc) --retry 3

FROM ruby:3.4.6-slim-bookworm

# Системные зависимости для работы приложения
RUN apt-get update -qq && \
    apt-get install --no-install-recommends -y curl libpq5 postgresql-client && \
    rm -rf /var/lib/apt/lists/*

WORKDIR /usr/src/app

# Копируем установленные гемы из builder'а
COPY --from=builder /usr/local/bundle/ /usr/local/bundle/

# Копируем код приложения
COPY . .

# Запускаем приложение от имени пользователя без root-прав
RUN useradd -m --uid 1001 rails
USER rails

# Открываем порт
EXPOSE 3000

# Основная команда для запуска сервера
CMD ["bundle", "exec", "puma", "-C", "config/puma.rb"]
```

```dockerfile
        libffi-dev \
        readline \
        sqlite && \
    rm -rf /var/cache/apk/*

WORKDIR /tmp

COPY Gemfile Gemfile.lock ./

# Устанавливаем build-time зависимости, ставим гемы и удаляем build-time зависимости
RUN set -ex && \
    apk add --virtual .build-deps \
        build-base \
        openssl-dev \
        postgresql-dev \
        libc-dev \
        linux-headers \
        libxml2-dev \
        libxslt-dev \
        readline-dev && \
    bundle install --clean --no-cache --without development test --jobs=$(getconf _NPROCESSORS_ONLN) && \
    rm -rf /var/cache/apk/* && \
    apk del .build-deps

ENV APP_HOME /app
COPY . $APP_HOME
WORKDIR $APP_HOME

ENV RAILS_ENV=production RACK_ENV=production

EXPOSE 3000

CMD ["bundle", "exec", "puma"]
```

### PostgreSQL

Официальный Docker-образ `postgres` предоставляет специальный механизм для инициализации базы данных при первом запуске контейнера.

Любые файлы с расширениями `.sh`, `.sql` или `.sql.gz`, помещенные в каталог `/docker-entrypoint-initdb.d/` внутри контейнера, будут выполнены в алфавитном порядке при его создании.

Это позволяет автоматически создавать базы данных, пользователей, таблицы и наполнять их начальными данными.

```dockerfile
FROM postgres:15

COPY init.sql /docker-entrypoint-initdb.d/
```

### Использование Alpine Linux

*   **Проблемы совместимости из-за `musl libc`:**

    *   Большинство ПО в мире Linux скомпилировано с использованием `glibc`. `musl` — это альтернативная, легковесная реализация стандартной библиотеки C, но она не на 100% совместима с `glibc`.
    *   **Проблемы могут возникнуть с:**
        *   **Python, Ruby, Node.js:** Некоторые пакеты, использующие C-расширения, могут потребовать компиляции во время сборки, что усложняет Dockerfile.
        *   **Готовые бинарные файлы:** Бинарные файлы, скомпилированные с `glibc`, не запустятся на Alpine.
        *   **DNS:** В `musl` есть отличия в обработке DNS-запросов, что может вызывать проблемы в сложных сетевых окружениях.

*   **Менее привычные инструменты:**

    *   Alpine использует `BusyBox`, который предоставляет урезанные версии стандартных утилит Unix.
    *   Оболочка по умолчанию — `ash`, а не `bash`.

**Виртуальные пакеты в Alpine**

Виртуальные пакеты — это временные группы пакетов, которые можно установить для выполнения задачи (например, компиляции), а затем удалить одной командой, чтобы не раздувать итоговый образ.

```dockerfile
FROM python:3.13-alpine

WORKDIR /app

COPY requirements.txt .

RUN apk add --no-cache --virtual .build-deps gcc musl-dev libxml2-dev libxslt-dev && \
    pip install --no-cache-dir -r requirements.txt && \
    apk del .build-deps

COPY . .

CMD ["python", "app.py"]
```

1.  `apk add --no-cache --virtual .build-deps gcc musl-dev ...`: Создает виртуальный пакет `.build-deps` и устанавливает в него зависимости для компиляции.
2.  `pip install ...`: Устанавливает Python-пакеты, используя установленные зависимости.
3.  `apk del .build-deps`: Удаляет виртуальный пакет со всеми его зависимостями, оставляя образ чистым.

#### Условная установка сборочных зависимостей

Этот паттерн можно сделать еще более гибким с помощью `ARG`. Это позволяет использовать один и тот же Dockerfile для создания как production-образа, так и образа для разработки (например, с дополнительными утилитами для отладки).

```dockerfile
# Определяем аргументы для временных и постоянных сборочных зависимостей
ARG BUILD_DEPS
ARG TEMP_BUILD_DEPS

# Устанавливаем постоянные зависимости, если они переданы
RUN if [ -n "$BUILD_DEPS" ]; then \
      apk add --no-cache $BUILD_DEPS; \
    fi

# Устанавливаем временные зависимости как виртуальную группу, если они переданы
RUN if [ -n "$TEMP_BUILD_DEPS" ]; then \
      apk add --no-cache --virtual .build-deps $TEMP_BUILD_DEPS; \
    fi

# ... (команды, использующие зависимости, например, компиляция) ...

# Удаляем временные зависимости, если они были установлены
RUN if [ -n "$TEMP_BUILD_DEPS" ]; then \
      apk del .build-deps; \
    fi
```

*   При сборке вы можете передать нужные пакеты через флаг `--build-arg`:
    ```sh
    # Сборка для production (без доп. пакетов)
    docker build .

    # Сборка для разработки (с временной установкой git и curl)
    docker build --build-arg TEMP_BUILD_DEPS="git curl" .
    ```
*   Команды `if` в `RUN` проверяют, был ли передан аргумент `TEMP_BUILD_DEPS`. Если да, то создается виртуальная группа `.build-deps`, а после выполнения необходимых шагов она удаляется.

### Анализ и Оптимизация Образов

- Добавить в `RUN` удаление кэша пакетного менеджера, например: `rm -rf /var/lib/apt/lists/*`.
- Выбрать `alpine` и при установке использовать `apk add --no-cache`. Можно также при установке создать `ENV NGINX_VERSION=номер_версии` и передать `apk add --no-cache nginx=${NGINX_VERSION}`.
- Чтобы образ быстрее собирался, можно перенести части `Dockerfile`, которые часто меняются, в конец файла (если какой-то слой изменился, то все последующие будут пересобираться).
- Чтобы образ меньше весил, можно при сборке `Dockerfile` в конце добавить флаг `--squash`, который объединяет все слои в один. Это может быть полезно для уменьшения итогового размера образа, но используйте с осторожностью, так как это нарушает кэширование слоев.
- Использовать `dive` для анализа слоёв, `Slim` для автоматического уменьшения размера и повышения безопасности, `strip` для удаления отладочной информации из бинаря.

### Линтинг и Безопасность

- Применять линтер **`hadolint`** для статического анализа `Dockerfile`. Он проверяет файл на соответствие лучшим практикам, находит ошибки и неидиоматичные конструкции. Пример запуска: `docker run --rm -i hadolint/hadolint < Dockerfile`.
- Изучить рекомендации по [безопасности](./docker_security.md) и использовать специализированные инструменты:
  - **`dockle`**: Проверяет образ на соответствие лучшим практикам безопасности (CIS Benchmarks), находит уязвимости и "толстые" слои. Пример: `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock goodwithtech/dockle:v0.4.15 my-image:latest`.
  - **`docker-bench-security`**: Скрипт, который проверяет конфигурацию самого демона Docker.

### Интеграция с Kubernetes

- Для конвертации файлов [docker-compose](./docker_compose.md) в манифесты Kubernetes используйте инструмент **`kompose`**. Он анализирует `docker-compose.yml` и генерирует соответствующие ресурсы Kubernetes (Deployments, Services и т.д.).

### Выбор базового образа Python: `full` vs `slim` vs `alpine`

#### 1. `python:3.11` 

*   **Основа:** Полноценный Debian.
*   **Содержимое:** Включает Python, системные утилиты и **инструменты для сборки** (`gcc`, `make` и т.д.).
*   **Преимущество:** Максимальная совместимость. Пакеты, требующие компиляции из исходного кода, устанавливаются без проблем.
*   **Недостатки:** Большой размер (увеличивает время скачивания и поверхность атаки).

#### 2. `python:3.11-slim` 

*   **Основа:** "Облегченный" Debian.
*   **Содержимое:** Удалены инструменты для сборки и многие утилиты, оставлено только необходимое для **запуска** Python-приложений.
*   **Преимущество:** Значительно меньший размер и поверхность атаки при сохранении высокой совместимости `glibc`.
*   **Особенность:** Если пакету нужна компиляция, вам придется временно установить сборочные зависимости (`apt-get install build-essential ...`) и удалить их в том же слое `RUN`.

#### 3. `python:3.11-alpine`

*   **Основа:** Alpine Linux, дистрибутив, построенный на `musl libc` и `BusyBox`.
*   **Преимущество:** Экстремально маленький размер.
*   **Недостатки:**
    *   **Проблемы совместимости:** Многие pre-compiled Python-пакеты ("wheels") собраны под `glibc` и **не будут работать** на Alpine. Это заставит `pip` пытаться скомпилировать их, что часто приводит к ошибкам.
    *   Требует более глубокой экспертизы для решения проблем с зависимостями.
