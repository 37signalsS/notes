# Устранение проблем с доступом Docker-контейнеров к локальной сети

## Базовые концепции

Для успешной работы сети Docker-контейнеров важно понимать взаимодействие нескольких ключевых компонентов:

* **`iptables` / `nftables`**: Системы файрвола Linux, которые управляют фильтрацией и маршрутизацией пакетов. Docker активно использует их для изоляции сети и проброса портов. Конфликты с другими службами файрвола могут нарушать сетевую связность.
* **`NetworkManager`**: Служба управления сетевыми интерфейсами в Linux. Может конфликтовать с Docker, если ошибочно пытается управлять внутренними интерфейсами Docker, такими как `docker0`.
* **`docker0`**: Виртуальный сетевой мост, создаваемый Docker по умолчанию для соединения контейнеров с хостом и внешней сетью.
* **`IPv4 forwarding`**: Параметр ядра Linux, разрешающий пересылку IP-пакетов между сетевыми интерфейсами. Должен быть включен для маршрутизации трафика из контейнеров во внешние сети.

## Практические сценарии

### Сценарий 1: Конфликт `iptables` и `nftables`

**Проблема:** В современных дистрибутивах Linux (`Debian 10+`, `Ubuntu 20.04+`) `nftables` является фреймворком по умолчанию. Если Docker настроен на использование старого `iptables-legacy`, а другие службы (например, `firewalld`) управляют `nftables`, правила Docker могут «затираться» или не работать, что приводит к нарушению сетевой связности.

**Решение:** Эта проблема, её диагностика и способы решения (например, принудительное переключение Docker на `iptables-legacy`) подробно описаны в основной заметке: **[Решение проблем: Docker и `iptables`](../Docker_network/troubleshooting/iptables_integration.md)**.

### Сценарий 2: `NetworkManager` управляет мостом `docker0`

**Проблема:** `NetworkManager` может ошибочно начать управлять сетевым интерфейсом `docker0`, который Docker создает для своего внутреннего моста. Это приводит к сбросу или изменению правил маршрутизации, установленных Docker.

**Диагностика:**
Проверьте, управляет ли `NetworkManager` интерфейсом `docker0`:

```bash
nmcli dev show | grep docker
```

Если в выводе есть `docker0`, значит, `NetworkManager` его контролирует.

**Решение:**
Запретите `NetworkManager` управлять интерфейсом `docker0`. Создайте файл `/etc/NetworkManager/conf.d/docker.conf` со следующим содержимым:

```ini
[keyfile]
unmanaged-devices=interface-name:docker0
```

Затем перезапустите `NetworkManager`:

```bash
sudo systemctl restart NetworkManager
```

### Сценарий 3: Отключен `IPv4 forwarding`

**Проблема:** Для того чтобы контейнеры могли обращаться к внешним сетям, ядро хоста должно разрешать пересылку IP-пакетов (IP forwarding). Если эта опция отключена, Docker не сможет маршрутизировать трафик из контейнеров наружу. Подробнее о параметрах ядра можно узнать в [заметке о `sysctl`](../../Linux/Core/kernel/sysctl.md).

**Диагностика:**
Проверьте текущее значение параметра `net.ipv4.ip_forward`:

```bash
sysctl net.ipv4.ip_forward
```

Если вывод `net.ipv4.ip_forward = 0`, пересылка отключена.

**Решение:**
Включите `ip_forward` немедленно:

```bash
sudo sysctl -w net.ipv4.ip_forward=1
```

Чтобы настройка сохранилась после перезагрузки, добавьте `net.ipv4.ip_forward=1` в файл `/etc/sysctl.conf` или в новый файл в директории `/etc/sysctl.d/`. После этого примените изменения командой:

```bash
sudo sysctl -p
```
