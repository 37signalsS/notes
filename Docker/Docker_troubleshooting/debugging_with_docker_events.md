# Отладка с помощью Docker Events

## Определения

**`docker events`** — CLI-команда для просмотра потока системных событий Docker Engine в реальном времени. Она позволяет отслеживать изменения состояния объектов (контейнеров, образов, сетей, томов) на уровне управления демоном.

**Gordon AI Integration (2026):** В современных версиях Docker поток событий может быть передан встроенному помощнику Gordon (`docker ai`) для автоматической корреляции событий рестарта с логами ядра и приложения.

**Management vs Data Plane:** Команда `docker events` фиксирует события **Management Plane** (создание, остановка, подключение сети). Для отладки **Data Plane** (прохождение отдельных пакетов) рекомендуется использовать инструменты на базе eBPF, такие как `Inspektor Gadget`.

## Основные концепции

### Области применения

Инструмент незаменим в ситуациях, когда:
- Контейнер завершается слишком быстро (Flapping), не позволяя подключиться через `exec`.
- Нужно подтвердить причину остановки (внешний `docker stop` vs внутреннее падение).
- Происходят изменения в сетевой топологии (подключение/отключение интерфейсов).
- Требуется аудит действий пользователей (кто запустил `exec` или `kill`).

### Типы объектов и событий

| Категория | Объект (`type`) | Типичные события (`event`) |
| :--- | :--- | :--- |
| **Контейнеры** | `container` | `create`, `start`, `die`, `oom-kill`, `health_status`, `commit`, `rename` |
| **Образы** | `image` | `pull`, `push`, `tag`, `untag`, `delete` |
| **Сети** | `network` | `create`, `connect`, `disconnect`, `destroy` |
| **Тома** | `volume` | `create`, `mount`, `unmount`, `destroy` |
| **Узлы (Swarm)** | `node` | `create`, `update`, `remove` |

## Практические сценарии

### Сценарий 1: Диагностика циклического перезапуска (Flapping)

**Симптомы:** Контейнер постоянно перезапускается, логи приложения пусты или обрываются.

```bash
# Мониторинг событий конкретного контейнера
docker events --filter container=web-app --filter event=die --filter event=health_status
```

**Пример вывода при провале Healthcheck:**
```text
2026-07-19T10:00:05Z container health_status: unhealthy actor.name=web-app
2026-07-19T10:00:06Z container die exitCode=143 actor.name=web-app
```
**Анализ:** Код 143 (SIGTERM) после статуса `unhealthy` подтверждает, что контейнер был корректно остановлен оркестратором или `autoheal` на основе данных проверки здоровья.

### Сценарий 2: Идентификация OOM Killer

**Симптомы:** Контейнер внезапно переходит в статус `Exited (137)`.

```bash
# Поиск событий нехватки памяти за последний час
docker events --filter event=oom-kill --since 1h
```

**Действия:**
1. Если событие зафиксировано, проверьте лимиты: `docker inspect <id> --format '{{.HostConfig.Memory}}'`.
2. Сопоставьте время события с выводом `dmesg -T | grep -i "oom-killer"`.

### Сценарий 3: Анализ сетевых подключений (Docker 28+)

**Задача:** Убедиться, что контейнер успешно подключился к пользовательской сети.

```bash
docker events --filter type=network --filter event=connect
```

**Пример вывода:**
```text
2026-07-19T12:30:00Z network connect id=... (container=app, name=prod-net)
```

### Сценарий 4: Потоковый анализ через Gordon AI

**Задача:** Автоматически интерпретировать поток событий без ручного разбора логов.

```bash
docker events --format '{{json .}}' | docker ai analyze --stream
# → [Gordon] Обнаружена аномалия: контейнер "db" упал 3 раза за 30 секунд.
# → [Gordon] Возможная причина: Исчерпание лимита файловых дескрипторов на хосте.
```

## Дополнительная информация

### Основные флаги и форматирование

| Флаг | Описание | Пример |
| :--- | :--- | :--- |
| `--filter` | Фильтрация по типу, событию или метке | `--filter label=stage=prod` |
| `--since` | События после указанного времени | `--since 10m` |
| `--format` | Вывод в JSON для обработки скриптами | `--format '{{json .}}'` |

### Сравнение инструментов отладки

| Инструмент | Фокус | Преимущество |
| :--- | :--- | :--- |
| **`docker events`** | Жизненный цикл | Минимальная нагрузка, ловит "мгновенные" падения. |
| **`docker logs`** | Логика кода | Детальный вывод ошибок приложения. |
| **`docker debug`** | Интерактивность | Возможность проверить ФС и сеть "изнутри". |
| **eBPF (ig)** | Трафик и системные вызовы | Анализ Data Plane без внедрения в контейнер. |

### Особенности в разных средах

- **Производительность:** Команда является пассивным слушателем API и практически не потребляет CPU/RAM.
- **Docker Swarm:** На конкретном узле видны только локальные события. Для мониторинга всего кластера запускайте команду на менеджере с фильтрами `type=service` или `type=node`.
- **Буферизация:** Демон не хранит события вечно. При высокой интенсивности (тысячи событий в секунду) рекомендуется перенаправлять вывод в `syslog` или специализированный коллектор.
