# Использование алиасов хоста в Docker-контейнерах

## Определения

**Алиасы хоста в контейнере** — это метод проброса пользовательских псевдонимов (aliases) и функций из командной оболочки хост-системы (например, из `.bashrc` или `.zshrc`) во внутреннюю среду Docker-контейнера.

**Проблема:** По умолчанию Docker обеспечивает полную изоляцию окружения. Контейнер не наследует конфигурационные файлы оболочки пользователя, поэтому привычные команды (например, `ll`, `gs`, `k`) внутри него не работают.

## Основные концепции

### Почему конфигурация не наследуется

При запуске оболочки внутри контейнера (через `docker exec` или `ENTRYPOINT`), она считывает только внутренние файлы образа.

| Тип оболочки | Файлы конфигурации | Состояние в контейнере |
| :--- | :--- | :--- |
| **Login shell** | `/etc/profile`, `~/.bash_profile` | Не наследуются с хоста |
| **Interactive shell** | `~/.bashrc`, `~/.zshrc` | Не наследуются с хоста |
| **Non-interactive** | `$BASH_ENV` | Не наследуются с хоста |

### Подходы к решению в 2025-2026 гг.

1.  **Монтирование (Bind Mount):** Прямое подключение файлов конфигурации хоста к ФС контейнера.
2.  **Декларативное описание (Dev Containers):** Настройка среды через `devcontainer.json` (стандарт для современной разработки).
3.  **Внедрение при сборке (Dockerfile):** Прописывание алиасов в системные файлы образа.
4.  **Динамическая инъекция:** Передача алиасов через переменные окружения или временные файлы.

## Практические сценарии

### Сценарий 1: Интерактивное монтирование (Ad-hoc отладка)

Самый простой способ быстро получить свои алиасы в контейнере.

```bash
docker run -it \
  -v ~/.bashrc:/root/.bashrc:ro \
  ubuntu bash
# → Внутри контейнера:
# # alias ll
# → alias ll='ls -la'
```

**Критически важно:**
- Используйте флаг `:ro` (read-only), чтобы контейнер не мог случайно изменить ваш основной файл на хосте.
- Этот метод работает, только если в контейнере есть оболочка `bash` и она настроена на чтение `~/.bashrc`.

### Сценарий 2: Использование в Docker Compose

Позволяет зафиксировать наличие алиасов для всей команды разработчиков.

```yaml
services:
  app:
    image: python:3.12-slim
    volumes:
      - ./.bashrc_dev:/root/.bashrc:ro
    environment:
      - BASH_ENV=/root/.bashrc
```

### Сценарий 3: VS Code Dev Containers (Рекомендуемый для разработки)

VS Code автоматически пробрасывает локальные настройки оболочки, если это настроено в `devcontainer.json`.

```json
{
  "name": "My Project",
  "build": { "dockerfile": "Dockerfile" },
  "customizations": {
    "vscode": {
      "settings": {
        "terminal.integrated.shellArgs.linux": ["-l"]
      }
    }
  },
  "mounts": [
    "source=${localEnv:HOME}/.bashrc,target=/root/.bashrc,type=bind,readonly"
  ]
}
```

### Сценарий 4: Кастомный образ с предустановленными алиасами

Метод для командной работы, когда нужно обеспечить одинаковый набор инструментов для всех.

```dockerfile
FROM ubuntu:24.04

# Добавляем алиасы в системный файл, доступный всем пользователям
RUN echo 'alias ll="ls -la"' >> /etc/bash.bashrc && \
    echo 'alias gs="git status"' >> /etc/bash.bashrc

# Для Zsh
RUN [ -f /etc/zsh/zshrc ] && echo 'alias k="kubectl"' >> /etc/zsh/zshrc || true
```

### Сценарий 5: Перенос функций и Zsh-конфигурации

Сложные функции и Zsh требуют монтирования дополнительных директорий (например, `.oh-my-zsh`).

```bash
docker run -it \
  -v ~/.zshrc:/root/.zshrc:ro \
  -v ~/.oh-my-zsh:/root/.oh-my-zsh:ro \
  --env ZDOTDIR=/root \
  my-zsh-image zsh
```

**Нюанс:** Если `.zshrc` ссылается на плагины по абсолютным путям хоста, внутри контейнера они могут не найтись.

## Дополнительная информация

### Сравнение методов

| Метод | Плюсы | Минусы | Применимость |
| :--- | :--- | :--- | :--- |
| **Bind Mount** | Мгновенно, без правок образа | Зависит от хоста, небезопасно | Личная отладка |
| **Dockerfile** | Переносимо, безопасно | Нужно пересобирать образ | Production, CI/CD |
| **Dev Containers** | Идеально для IDE | Только для разработки | Локальная разработка |
| **BASH_ENV** | Гибко для скриптов | Сложно для интерактивности | Автоматизация |

### Предупреждения по безопасности

1.  **Утечка секретов:** В вашем `.bashrc` на хосте могут быть прописаны ключи доступа (`export AWS_ACCESS_KEY_ID=...`). При монтировании они станут доступны внутри контейнера.
2.  **Зависимости:** Алиасы, вызывающие внешние утилиты (например, `bat`, `exa`, `fzf`), не будут работать, если эти утилиты не установлены внутри контейнера.
3.  **Абсолютные пути:** Алиасы вида `alias logs='cat /var/log/myapp.log'` будут пытаться найти файл внутри контейнера, а не на хосте.

### Альтернатива: Docker Debug

В 2026 году для отладки рекомендуется использовать `docker debug`. Он автоматически предоставляет богатый инструментарий (Nix-пакеты) и удобную оболочку, избавляя от необходимости пробрасывать грязные конфиги хоста.
