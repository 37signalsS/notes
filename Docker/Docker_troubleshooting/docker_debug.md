# Отладка контейнеров (Docker Debug)

## Определения

**`docker debug`** — CLI-команда для интерактивной отладки контейнеров, образов и процессов сборки. Она создаёт эфемерную среду (sidecar-контейнер), которая подключается к целевому объекту, предоставляя полноценный shell и расширенный набор инструментов (Toolbox), даже если в исходном образе отсутствуют базовые утилиты (например, в distroless или scratch).

**Gordon (Docker AI)** — интегрированный интеллектуальный помощник, доступный через команду `docker ai` или внутри сессии `docker debug`. Он обладает доступом к контексту локального Docker Engine, анализирует логи, состояние контейнеров и предлагает готовые команды для исправления ошибок.

**Build Debugging** — функциональность (доступна с Docker Desktop 4.61+), позволяющая устанавливать точки остановки (breakpoints) в `Dockerfile` и подключаться к промежуточным слоям сборки для диагностики сбоев на этапе `RUN`.

**Ключевое преимущество:** Полная изоляция инструментов отладки от исполняемой среды приложения. Утилиты Nix не видны процессам приложения и не увеличивают размер production-образа.

## Основные концепции

### Принцип работы

При запуске `docker debug`:
- **Создание среды:** Создаётся временный контейнер с файловой системой на базе **Nix**, содержащей Toolbox.
- **Слияние ФС (MergerFS):** Файловая система целевого контейнера/образа монтируется и накладывается (overlay) на среду отладки. Это позволяет использовать, например, `vim` из Toolbox для редактирования файлов, находящихся внутри целевого контейнера.
- **Изоляция Namespaces:** Процессы отладки запускаются в тех же пространствах имен (PID, Network, IPC), что и целевой контейнер, что дает полный доступ к его внутреннему состоянию.
- **Zero Interference:** Инструменты отладки (директория `/nix`) физически недоступны для основного приложения, что исключает побочные эффекты.

### Инструментарий (Toolbox)

Среда отладки по умолчанию содержит: `vim`, `nano`, `htop`, `curl`, `dig`, `jq`, `ps`, `ip`.

**Управление инструментами и командами:**

| Команда | Описание |
| :--- | :--- |
| `install <pkg>` | Динамическая установка любого пакета из репозитория Nix (например, `nmap`, `strace`) |
| `uninstall <pkg>` | Удаление установленного пакета |
| `entrypoint --print` | Вывод текущего Entrypoint/CMD целевого объекта |
| `entrypoint --lint` | Статический анализ скрипта entrypoint на типичные ошибки |
| `entrypoint --run` | Тестовый запуск entrypoint в изолированной среде отладки |
| `ai <вопрос>` | Запрос к Gordon AI для анализа текущего контекста (логи, конфиги, ошибки) |

### Доступность и требования

- **Версия:** Docker CLI 27.0+ / Docker Desktop 4.33+ (Build Debugging с 4.61+).
- **Лицензия:** Включено во все планы подписки Docker (включая Personal).
- **Сеть:** Для команды `install` требуется доступ к `https://cache.nixos.org`. Для работы в закрытых контурах (Air-gapped) требуется предварительная загрузка Nix-кэша.

## Практические сценарии

### Сценарий 1: Отладка distroless-контейнера

**Задача:** Получить доступ к ФС и сети образа, в котором нет даже `/bin/sh`.

```bash
docker debug my-distroless-app:latest
# → Вы попадаете в подготовленную среду (zsh/bash) с доступом к ФС образа
```

### Сценарий 2: Горячее исправление конфигурации Nginx

**Задача:** Изменить `nginx.conf` в работающем контейнере без его перезапуска.

```bash
docker debug web-server

# Внутри сессии debug:
# Редактируем файл (vim берется из Toolbox, файл — из контейнера)
vim /etc/nginx/nginx.conf

# Проверяем синтаксис (бинарный файл nginx берется из целевого контейнера)
nginx -t
# → nginx: the configuration file /etc/nginx/nginx.conf syntax is ok

# Перезагружаем конфиг без остановки процесса
nginx -s reload
```

### Сценарий 3: Автоматическая диагностика с Gordon AI

**Задача:** Быстро определить причину падения приложения (Crash Loop).

```bash
docker debug failing-app

# Внутри сессии debug:
ai "Почему контейнер завершается с ошибкой?"
# → Gordon анализирует логи, dmesg и переменные окружения. 
# → Ответ: "Обнаружена ошибка подключения к БД: неверный пароль в ENV DB_PASSWORD"
```

### Сценарий 4: Анализ сетевых соединений

**Задача:** Проверить доступность внешнего API изнутри контейнера.

```bash
docker debug app-container

# Устанавливаем необходимый инструмент на лету
install nmap

# Выполняем сканирование
nmap -p 443 api.external-service.com
```

### Сценарий 5: Удалённая отладка через SSH

**Задача:** Диагностика контейнера на удаленном сервере.

```bash
docker debug --host ssh://user@remote-host container-name
```

### Сценарий 6: Отладка процесса сборки (Build Debugging)

**Задача:** Понять, почему инструкция `RUN npm install` завершается с ошибкой в середине сборки.

1. В `Dockerfile` добавьте точку остановки (требуется поддержка IDE, например, VS Code):
   ```dockerfile
   RUN # --debug
   npm install
   ```
2. Запустите сборку в режиме отладки. Сборка остановится на указанной строке.
3. Подключитесь к промежуточному слою:
   ```bash
   docker debug build-session-id
   ```
4. Исследуйте состояние ФС и сетевую связность перед выполнением команды.

### Сценарий 7: Диагностика, когда приложение «не открывается»

**Задача:** Контейнер запущен (`docker ps` показывает `Up`), но по адресу `localhost:8080` (или внешнему IP) приложение не отвечает.

```bash
# 1. Проверяем, что порт действительно опубликован
docker ps
# → Поле PORTS должно содержать 0.0.0.0:8080->8080/tcp

# 2. Проверяем, слушает ли приложение внутри контейнера
docker exec <container_id> ss -tlnp
# → Должен быть LISTEN на 0.0.0.0:8080 или 127.0.0.1:8080

# 3. Проверяем сеть контейнера
docker inspect <container_id> | jq '.[0].NetworkSettings'
# → IPAddress, Ports, NetworkMode

# 4. Если приложение слушает только 127.0.0.1 внутри контейнера,
#    внешний доступ будет недоступен. Нужно изменять конфигурацию приложения
#    на 0.0.0.0 или использовать сеть host.

# 5. Проверяем firewall на хосте
sudo iptables -L -n -v | grep -i drop
sudo ufw status

# 6. Проверяем логи на предмет падений после старта
docker logs --tail 100 <container_id>

# 7. Вход в контейнер для проверки файлов конфигурации
docker exec -it <container_id> sh
# → cat /etc/app/config.yaml
# → env | grep BIND
```

Если контейнер слушает на `127.0.0.1`, исправьте конфигурацию приложения на `0.0.0.0` и перезапустите контейнер. Для быстрой проверки без изменения конфигурации можно использовать `network_mode: host`, но это снижает изоляцию.

## Дополнительная информация

### Сохранение состояния

| Объект | Сохранение изменений |
| :--- | :--- |
| **Файлы приложения** | Сохраняются в работающем контейнере (до его удаления) |
| **Утилиты (install)** | Удаляются при завершении сессии `docker debug` |
| **Образы / Слои сборки** | Не изменяются напрямую (требуется `docker commit` для сохранения) |

### Параметры запуска (Флаги)

| Флаг | Описание | Пример |
| :--- | :--- | :--- |
| `--shell <type>` | Выбор оболочки (`bash`, `zsh`, `fish`, `auto`) | `--shell zsh` |
| `--command "<cmd>"` | Выполнение команды в среде отладки и выход | `--command "df -h"` |
| `--ai-off` | Отключение интеграции с Gordon AI | `--ai-off` |

### Безопасность и ограничения

- **Привилегии:** `docker debug` требует прав на создание привилегированных контейнеров (для доступа к namespaces).
- **Архитектура:** Toolbox должен соответствовать архитектуре целевого образа (проблемы при эмуляции x86 на Apple Silicon).
- **Ресурсы:** Динамическая установка тяжелых пакетов через Nix может потреблять значительный трафик и дисковое пространство во временном хранилище Docker.

**Глубокое изучение:**
- **[Performance Degradation](../../Linux/Diagnostics/Networking/iperf3.md)** — диагностика производительности. В Docker: `docker stats` для CPU/memory, `docker exec <c> cat /proc/1/sched` для планировщика, PSI метрики через `/proc/pressure/` для обнаружения bottleneck.
- **[Permission Denied](../../Linux/Security/Concepts/File_Permissions/special_permissions.md)** — проблемы с правами. В Docker: `COPY --chown=user:group` для правильного ownership, `--user` в `docker run` для запуска от нужного UID, /etc/passwd в контейнере.
