# Docker: Коды завершения контейнеров (Exit Codes)

## Определения

**Код завершения (Exit Code)** в Docker — это целочисленное значение, которое возвращает главный процесс (PID 1) в контейнере после своего завершения. Этот код является основным индикатором того, почему контейнер остановился.

- **Код `0`**: Успешное завершение. Процесс завершил свою работу без ошибок.
- **Коды `1`-`255`**: Завершение с ошибкой.

Docker не придумывает эти коды, а лишь транслирует код завершения от процесса, который был запущен в контейнере.

## Базовые концепции

### Стандартные коды ошибок

Хотя конкретные коды ошибок (`1-125`) зависят от самого приложения, существуют общепринятые конвенции, унаследованные от Linux:

- **`1`**: Общая ошибка. Часто используется для обозначения неуказанной проблемы.
- **`2`**: Неправильное использование (например, неверные аргументы командной строки).
- **`126`**: Команда найдена, но не может быть выполнена (Command invoked cannot execute). Чаще всего это проблема с правами на исполнение файла (`chmod +x`).
- **`127`**: Команда не найдена (Command not found). Указанный в `CMD` или `ENTRYPOINT` исполняемый файл отсутствует в `PATH` или по указанному пути.

### Коды завершения, вызванные сигналами

Если процесс был принудительно завершен системным сигналом, его код завершения вычисляется по формуле **`128 + N`**, где `N` — номер сигнала.

- **`130 (128 + 2)`**: Завершение по `SIGINT`. Процесс был прерван, аналогично нажатию `Ctrl+C`.
- **`137 (128 + 9)`**: Завершение по `SIGKILL`. Процесс был "убит" немедленно и без возможности очистки ресурсов. Это наиболее распространенный код при:
  - **`OOMKilled` (Out of Memory)**: Контейнер превысил свой лимит по памяти, и ядро системы принудительно завершило процесс. Проверить это можно командой `docker inspect`, где в секции `State` поле `OOMKilled` будет `true`.
  - Выполнении команды `docker kill`.
- **`139 (128 + 11)`**: Завершение по `SIGSEGV` (Segmentation Fault). Произошла ошибка сегментации, указывающая на серьезную проблему в приложении (например, обращение к невалидной области памяти). Часто встречается в приложениях на C/C++ или в нативных расширениях для других языков.
- **`143 (128 + 15)`**: Завершение по `SIGTERM`. Процесс получил сигнал о "вежливом" завершении, но не смог или не успел его обработать. Это стандартный сигнал, который отправляет команда `docker stop`. Корректно написанное приложение должно перехватывать `SIGTERM` для graceful shutdown.

Общее описание кодов завершения в Linux можно найти в заметке [**Коды завершения (Exit codes)**](../../Linux/Shell/exit_codes.md).

## Практические сценарии: План диагностики

При падении контейнера с ненулевым кодом следует придерживаться следующего плана:

1. **Сбор фактов:**
    - **Проверить логи контейнера:** `docker logs <container_id>`. Часто приложение само сообщает о причине ошибки перед падением.
    - **Изучить состояние контейнера:** `docker inspect <container_id>`. Обратите внимание на поля `State`, `ExitCode`, `Error`, и особенно `OOMKilled`.

2. **Определение природы ошибки по коду:**
    - **`1-125`**: Проблема в логике приложения или его конфигурации. Изучайте логи.
    - **`126`**: Проблема в `Dockerfile`. Проверьте права на исполнение у entrypoint/cmd скрипта.
    - **`127`**: Проблема в `Dockerfile`. Проверьте, что команда существует и доступна в `PATH`.
    - **`137 (SIGKILL)`**:
        - Если `OOMKilled: true` — увеличьте лимит памяти для контейнера (`-m` или `memory` в `docker-compose.yml`) или оптимизируйте потребление памяти приложением.
        - Если `OOMKilled: false` — ищите внешнюю причину: ручной вызов `docker kill`, вмешательство системных мониторов или оркестратора.
    - **`139 (SIGSEGV)`**: Проблема в коде приложения или его нативных зависимостях. Требуется глубокая отладка, возможно, с использованием `core dump`.
    - **`143 (SIGTERM)`**: Приложение не обрабатывает сигнал `SIGTERM`. Реализуйте "graceful shutdown", чтобы приложение корректно завершало работу при `docker stop`.
