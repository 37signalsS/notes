# Коды завершения контейнеров (Docker Exit Codes)

## Определения

**Exit Code (Код завершения)** — целочисленное значение (0–255), возвращаемое главным процессом контейнера (**PID 1**) операционной системе при завершении работы. Docker транслирует этот код без изменений для информирования пользователя или оркестратора о результате выполнения задачи.

- **`0`** — успешное завершение (Success)
- **`1–255`** — завершение с ошибкой или по внешнему сигналу

Общие коды Linux и Bash описаны в разделе **[Коды завершения Linux](../../Linux/Shell/exit_codes.md)**.

## Основные концепции

### Классификация кодов

| Код | Описание | Источник |
| :--- | :--- | :--- |
| **0** | Успешное выполнение процесса | Приложение |
| **1** | Общая ошибка (Catch-all) | Приложение / Скрипт |
| **2** | Неправильное использование встроенных команд (Syntax error) | Shell (bash/sh) |
| **125** | Ошибка самого Docker (например, неверный флаг в `docker run`) | Docker Engine |
| **126** | Команда найдена, но не может быть выполнена (нет прав) | ОС / Контейнер |
| **127** | Команда не найдена (отсутствует в `$PATH`) | Shell |
| **128** | Недопустимый аргумент для выхода (exit n, где n > 255) | Приложение |
| **128+N** | Завершение по системному сигналу `N` | Ядро Linux |
| **255** | Статус выхода вне диапазона (или общая ошибка среды выполнения) | Приложение / Runtime |

### Сигналы и формула `128 + N`

Если процесс убит сигналом, код завершения рассчитывается как `128` плюс номер сигнала.

| Код | Сигнал | Название | Типичная причина |
| :--- | :--- | :--- | :--- |
| **130** | 2 | **SIGINT** | Прерывание пользователем (`Ctrl+C`) |
| **131** | 3 | **SIGQUIT** | Дамп ядра / Быстрый выход (Nginx `STOPSIGNAL`) |
| **137** | 9 | **SIGKILL** | Принудительная остановка (**OOMKilled** или `docker kill`) |
| **139** | 11 | **SIGSEGV** | Ошибка сегментации (баг в памяти, C/C++) |
| **141** | 13 | **SIGPIPE** | Запись в закрытый канал (Pipe) |
| **143** | 15 | **SIGTERM** | Запрос на корректное завершение (`docker stop`) |

### Превышение лимита памяти (OOMKilled)

**OOMKilled** — индикатор того, что контейнер был убит ядром Linux за превышение установленного лимита оперативной памяти (`--memory`).

```bash
# Проверка флага OOMKilled
docker inspect <container_id> --format '{{.State.OOMKilled}}'
# → true (если убит по памяти)
```

**Важно:** Код `137` не всегда означает OOM. Если `OOMKilled: false`, значит контейнер был убит вручную командой `docker kill` или внешней системной утилитой.

## Практические сценарии

### Сценарий 1: Диагностика состояния

Для быстрого анализа причин падения контейнера используйте `docker inspect`.

```bash
# Получение кода и ошибки одной командой
docker inspect <id> --format 'ExitCode: {{.State.ExitCode}}, Error: "{{.State.Error}}", OOM: {{.State.OOMKilled}}'
# → ExitCode: 137, Error: "", OOM: true
```

### Сценарий 2: Код 137 (SIGKILL) — Нехватка памяти (OOM)

**Симптомы:** Контейнер падает при высокой нагрузке.

**Анализ:**
```bash
# Просмотр системных логов на хосте
dmesg | grep -i "oom-killer"
# → [1234.56] psql invoked oom-killer: gfp_mask=0x..., order=0, oom_score_adj=0
```

**Решение:**
1. Проверьте лимиты: `docker inspect <id> --format '{{.HostConfig.Memory}}'`.
2. Увеличьте лимит или настройте Swap (если применимо).
3. Оптимизируйте приложение (профилирование памяти).

### Сценарий 3: Код 143 (SIGTERM) — Корректное завершение (Graceful Shutdown)

**Симптомы:** При `docker stop` контейнер ждет 10 секунд и выходит с кодом 137 вместо 0/143.

**Причина:** Процесс PID 1 не обрабатывает сигнал `SIGTERM` (часто из-за запуска через shell-оболочку без `exec`).

**Решение:**
В Dockerfile используйте JSON-форму для `CMD` или `ENTRYPOINT`, либо `exec` в скриптах.
```dockerfile
# Правильно (JSON-форма)
CMD ["node", "app.js"]

# Правильно (скрипт с exec)
# ENTRYPOINT ["/entrypoint.sh"]
# --- в entrypoint.sh ---
# exec node app.js
```
Подробнее см. **[HEALTHCHECK и STOPSIGNAL](../Dockerfile/Instructions/health_signals.md)**.

### Сценарий 4: Код 126 — Ошибка прав доступа

**Симптомы:** Контейнер не запускается, код 126.

**Причина:** Файл entrypoint.sh не имеет флага исполнения или ФС примонтирована с `noexec`.

**Решение:**
```dockerfile
COPY entrypoint.sh /
RUN chmod +x /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
```

### Сценарий 5: Код 127 — Команда не найдена

**Симптомы:** Ошибка `executable file not found in $PATH`.

**Диагностика:**
```bash
# Проверьте содержимое образа
docker run --rm <image_name> ls -la /path/to/binary
```

**Решение:** Убедитесь, что бинарный файл установлен и путь к нему указан верно (лучше абсолютный путь).

### Сценарий 6: Код 139 (SIGSEGV) — Ошибка сегментации

**Симптомы:** Приложение падает "молча" без логов в `stdout`.

**Причина:** Попытка обращения к неавторизованному участку памяти. Часто встречается в Python/Node.js при использовании native-модулей (C/C++).

**Решение:**
1. Обновите зависимости.
2. Используйте `gdb` или `valgrind` внутри контейнера для отладки.
3. Проверьте совместимость библиотек (glibc vs musl). См. **[Совместимость Alpine и glibc](./alpine_glibc_compatibility.md)**.

### Сценарий 7: Мгновенное завершение после запуска (Exited)

**Симптомы:** Контейнер переходит в статус `Exited (0)` сразу после старта.

**Причина:** Основной процесс (PID 1) завершил свою работу. Контейнер — это изоляция вокруг процесса; если процесс закончен, изоляция схлопывается.

**Решение:**
Если это веб-сервер, убедитесь, что он запущен в **foreground** режиме.
- Nginx: `nginx -g 'daemon off;'`
- Apache: `httpd -D FOREGROUND`

## Дополнительная информация

### Сводная таблица действий

| Код | Приоритетное действие |
| :--- | :--- |
| **1** | Проверить логи: `docker logs <id>` |
| **125** | Проверить команду запуска (флаги, параметры) |
| **126** | Проверить права: `chmod +x` |
| **127** | Проверить наличие файла в образе и `$PATH` |
| **137** | Проверить `OOMKilled` и лимиты памяти |
| **139** | Проверить `dmesg` и совместимость библиотек |
| **143** | Проверить обработку сигналов (PID 1, `exec`) |
