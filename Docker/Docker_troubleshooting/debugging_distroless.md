# Отладка контейнеров без shell (distroless)

## Определения

**`Distroless`-образы** — это базовые образы, содержащие только приложение и его runtime-зависимости. В них отсутствуют shell, менеджеры пакетов и стандартные утилиты, что повышает безопасность, но усложняет отладку, так как стандартный подход `docker exec -it <container> /bin/sh` не работает.

## Базовые концепции

Отладка `distroless`-контейнеров основана на двух ключевых подходах:

1.  **Использование существующей оболочки**: Если в образе есть shell, но он недоступен текущему пользователю, можно попытаться получить к нему доступ с правами `root`.
2.  **Подключение внешних инструментов**: Запуск временного "отладочного" контейнера, который разделяет одно или несколько пространств имён (network, PID) с целевым контейнером. Это позволяет использовать утилиты из отладочного контейнера для анализа проблемного.

## Практические сценарии

### Сценарий 1: Проверка доступа с повышенными привилегиями

Самый простой способ, который стоит попробовать в первую очередь.

```sh
# Попытка зайти в контейнер от пользователя root
docker exec -it --user root <container_name> /bin/sh
```

### Сценарий 2: Использование эфемерных отладочных контейнеров

Рекомендуемый способ для большинства случаев. Запускается временный контейнер с утилитами, подключенный к пространствам имен целевого контейнера.

*   **Анализ сети:**
    ```sh
    # nicolaka/netshoot содержит множество сетевых утилит (ss, tcpdump и т.д.)
    docker run --rm -it --network=container:<target_container_name> nicolaka/netshoot
    ```

*   **Анализ процессов:**
    ```sh
    # Позволяет видеть процессы целевого контейнера (ps, top, strace)
    docker run --rm -it --pid=container:<target_container_name> alpine
    ```

### Сценарий 3: Универсальная отладка через `nsenter`

Этот мощный подход позволяет "войти" в пространства имён работающего контейнера, даже если `docker exec` недоступен. Он использует `nsenter` из привилегированного отладочного контейнера. Подробнее о механизме читайте в заметке о [пространствах имён](../../Linux/Core/namespaces.md).

**Шаги:**
1.  **Узнайте PID целевого контейнера:**
    ```bash
    PID=$(docker inspect -f '{{.State.Pid}}' <container>)
    ```
2.  **Войдите в его пространства имён через отладочный образ:**
    ```bash
    # Запускаем ubuntu, входим во все пространства имен процесса с PID
    docker run --rm -it --pid=host --net=host --privileged ubuntu bash -lc \
    "nsenter -t $PID -m -u -i -n -p bash"
    ```
    После выполнения этой команды вы окажетесь внутри окружения целевого контейнера, но с полным набором утилит из образа `ubuntu`.

### Сценарий 4: Использование `docker debug`

Современный и наиболее удобный способ отладки, который создает копию контейнера и позволяет переопределить `entrypoint` или добавить инструменты.

Подробное описание и практические сценарии использования, включая редактирование файлов в реальном времени, вынесены в отдельную заметку: **[Отладка и редактирование контейнеров с помощью Docker Debug](./docker_debug.md)**.


## Дополнительная информация

### Копирование файлов с хоста

Если нужно проанализировать логи или файлы конфигурации, их можно скопировать на хост-машину.

```sh
docker cp <container_name>:/path/to/file /local/path/
```
