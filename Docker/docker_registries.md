# Реестры Docker: хранение и распространение артефактов

## Определения

- **Реестр Docker (Registry):** Сервис для хранения и распространения образов и OCI-артефактов. Является специализированным типом **[репозитория артефактов](../CI-CD/artifact_management.md)**.
- **OCI Artifacts:** Стандарт, позволяющий хранить в реестре не только образы, но и любые бинарные объекты (Helm-чарты, SBOM, подписи, политики OPA, веса ИИ-моделей).
- **Дайджест (Digest):** Неизменяемый уникальный идентификатор содержимого (обычно SHA-256). Использование дайджеста вместо тега гарантирует скачивание именно той версии артефакта, которая была протестирована.
- **Referrers (OCI 1.1):** Механизм связи между артефактами. Позволяет «прикреплять» метаданные (например, отчет о сканировании или аттестацию) к образу через поле `subject` без изменения самого образа.
- **artifactType:** Поле в манифесте OCI 1.1, определяющее тип контента (например, `application/vnd.example.sbom.v1+json`). Позволяет реестрам фильтровать связанные артефакты.
- **Credential Helper:** Внешняя утилита для безопасного хранения учетных данных реестра в системном хранилище ключей (вместо открытого текста в `config.json`).

## Основные концепции

### Эволюция в универсальное хранилище (OCI 1.1)

Современные реестры (2024–2026) перешли от простого хранения слоев к модели **графа зависимостей**. Благодаря стандарту OCI 1.1 реестр выполняет функции базы данных метаданных:
- **Связывание метаданных:** При публикации образа CI-пайплайн автоматически прикрепляет к нему **SBOM** (состав пакетов) и **Provenance** (доказательство сборки) через поле `subject`.
- **Referrers API:** Позволяет клиентам запрашивать список всех артефактов, ссылающихся на конкретный дайджест образа. Инструменты безопасности (Trivy, Docker Scout, ORAS) используют это для верификации образов перед запуском.
- **Индексация связей:** Для обеспечения производительности реестры 2026 года используют Key-Value хранилища (Redis, BoltDB) для индексации связей «образ-метаданные», исключая необходимость сканирования всего хранилища.

### Архитектура хранилища (Storage Backends)

Реестры поддерживают различные типы бэкендов для хранения данных:
- **Облачные хранилища (S3, GCS, Azure Blob):** Стандарт для масштабируемых систем. Обеспечивают высокую доступность и долговечность.
- **Локальные файловые системы:** Используются для небольших инсталляций или кэширующих прокси.
- **Дедупликация на уровне контента:** Реестр хранит только одну копию каждого слоя (blob), даже если он используется в сотнях разных образов и репозиториев.

### Разделение сред и жизненный цикл

1. **Развлекательные/Dev-реестры (Ephemeral):** Предназначены для промежуточных сборок. Требуют агрессивных политик очистки (**Garbage Collection**) для удаления неиспользуемых слоев.
2. **Продуктовые реестры (Trusted):** Содержат только проверенные артефакты.
   - **Promotion:** Перенос образа из Dev в Prod реестр через `retag` и `push` без пересборки (гарантия неизменности бинарного кода).
   - **Immutable Tags:** Запрет перезаписи существующих тегов для обеспечения воспроизводимости инфраструктуры.
   - **Signing:** Обязательная проверка подписи (Cosign/Notation) через Admission Controllers в кластере.

### Проксирование и кэширование (Pull-through Cache)

Для обхода лимитов Docker Hub (Rate Limiting) и ускорения деплоя:
- **Registry Mirror:** Настройка демона Docker на автоматическое использование локального зеркала.
- **Proxy Cache:** Реестр (например, Harbor или Zot) прозрачно кэширует внешние образы при первом запросе, снижая нагрузку на внешний канал и ускоряя последующие скачивания.

## Практические сценарии

### Сценарий 1: Работа с OCI-артефактами (Helm)

Современный способ распространения манифестов Kubernetes без использования традиционных HTTP-репозиториев.

```bash
# Упаковка и пуш чарта в OCI-реестр
helm package ./my-chart
helm push my-chart-0.1.0.tgz oci://registry.example.com/charts

# Установка напрямую из OCI
helm install my-app oci://registry.example.com/charts/my-chart --version 0.1.0
```

### Сценарий 2: Аутентификация через Credential Helpers

Обеспечение безопасности учетных данных на рабочих станциях и серверах.

```bash
# Установка хелпера (например, для macOS)
# В ~/.docker/config.json:
{
  "credsStore": "osxkeychain"
}

# После docker login пароль будет сохранен в системной связке ключей
```

### Сценарий 3: Harbor — корпоративный стандарт

Используется для On-premise инсталляций с требованиями к RBAC, сканированию и репликации. Подробнее см. в разделе **[работа с Harbor](./Docker_registries/Harbor/usage.md)**.

## Диагностика (Troubleshooting)

### Проблемы с Referrers API

- **Ошибка 404 на пути `/referrers/`:** Означает, что реестр или прокси перед ним не поддерживают OCI 1.1. Docker Engine может пытаться интерпретировать HTML-страницу ошибки как JSON.
  - **Решение:** Проверьте версию реестра. Используйте ORAS для ручной проверки поддержки API.
- **Высокая задержка (Latency) при запросах метаданных:** Возникает, если реестр не индексирует поле `subject` и выполняет поиск по всему хранилищу манифестов.
  - **Решение:** Убедитесь, что в реестре включена индексация метаданных (Key-Value бэкенд).
- **Пропажа подписей при параллельных сборках:** Часто связана с использованием «Fallback Tag» (схема `sha256-<digest>.tag`) в реестрах без нативной поддержки Referrers API.
  - **Решение:** Перейдите на нативную поддержку OCI 1.1 (Harbor 2.10+, Zot, ECR).

### Очистка места (Garbage Collection)

- **Манифесты удалены, но место не освободилось:** Удаление манифеста через API лишь помечает его. Слои (blobs) остаются на диске.
  - **Решение:** Запустите процедуру Garbage Collection. Учтите, что в старых реализациях реестр должен находиться в режиме **read-only** во время GC.

## Дополнительная информация

### Сравнение функциональности реестров

| Реестр | Поддержка OCI 1.1 | Типы артефактов | Особенности |
| :--- | :--- | :--- | :--- |
| **Docker Hub** | Полная | Любые OCI | Интеграция Docker Scout, официальные образы |
| **Harbor** | Полная (с v2.10+) | Любые OCI | RBAC, Сканирование Trivy, Репликация, GC |
| **GitHub (GHCR)** | Полная | Любые OCI | Бесшовная интеграция с GitHub Actions |
| **Amazon ECR** | Полная | Любые OCI | Интеграция с IAM, AWS Inspector |
| **Zot** | Полная | Любые OCI | Сверхлегкий, фокус на производительности OCI 1.1 |

**Глубокое изучение:**
- **[Docker Hub](https://hub.docker.com)** — официальный реестр. В Docker: rate limit 100 pulls/6h (anonymous), 200 pulls/6h (auth), Docker Scout для анализа, официальные образы.
- **[GitHub Container Registry (GHCR)](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)** — интеграция с GitHub. В Docker: `docker buildx build --push -t ghcr.io/owner/repo:tag`, OIDC keyless signing через GitHub Actions.
- **[GitLab Container Registry](https://docs.gitlab.com/ee/user/packages/container_registry/)** — встроенный реестр. В Docker: автоматическая очистка через Cleanup Policy, интеграция с GitLab CI/CD.
- **[crane](https://github.com/google/go-containerregistry/blob/main/cmd/crane/README.md)** — манипуляции с образами. В Docker: `crane ls`, `crane copy`, `crane mutate` для управления тегами и слоями без daemon.
- **[skopeo](https://github.com/containers/skopeo)** — копирование образов. В Docker: `skopeo copy docker://src docker://dst` для миграции между реестрами, проверка подписей.
