# Реестры Docker: Хранение и распространение артефактов

## Определения

- **Реестр Docker (Registry):** Сервис для хранения и распространения образов и OCI-артефактов. Является специализированным типом **[репозитория артефактов](../CI-CD/artifact_management.md)**.
- **OCI Artifacts:** Стандарт, позволяющий хранить в реестре не только образы, но и любые бинарные объекты (Helm-чарты, SBOM, подписи, политики OPA, веса ИИ-моделей).
- **Дайджест (Digest):** Неизменяемый уникальный идентификатор содержимого (SHA-256). Использование дайджеста вместо тега гарантирует, что будет скачан именно тот набор байтов, который был протестирован.
- **Referrers (OCI 1.1):** Механизм связи между артефактами. Позволяет "прикреплять" метаданные (например, отчет о сканировании или аттестацию) к образу без изменения самого образа.
- **Credential Helper:** Внешняя утилита для безопасного хранения учетных данных реестра (вместо открытого текста в `config.json`).

## Основные концепции

### Эволюция в Универсальное Хранилище (OCI 1.1)

Современные реестры (2024–2026) перешли от простого хранения слоев к модели **графа зависимостей**. Благодаря стандарту OCI 1.1 реестр позволяет:
- **Связывать метаданные:** При публикации образа CI-пайплайн автоматически "прикрепляет" к нему **SBOM** (состав пакетов) и **Provenance** (доказательство сборки).
- **Использовать Referrers API:** Инструменты безопасности (Trivy, Docker Scout) могут опрашивать реестр о наличии связанных аттестаций для конкретного дайджеста.
- **Хранить Helm-чарты:** Реестр заменяет традиционные Chart-репозитории, позволяя управлять инфраструктурой и кодом в одном месте.

### Разделение сред и жизненный цикл

1. **Dev-реестры (Ephemeral):** Предназначены для промежуточных сборок. Требуют агрессивных политик очистки (**Garbage Collection**) для экономии места.
2. **Prod-реестры (Trusted):** Содержат только проверенные артефакты.
   - **Promotion:** Образ перемещается из Dev в Prod реестр без пересборки (Retag & Push).
   - **Immutable Tags:** Запрет перезаписи тегов в Prod-репозиториях для обеспечения воспроизводимости.
   - **Signing:** Обязательная проверка подписи (Notary/Cosign) перед деплоем в кластер.

### Безопасное управление учетными данными

Хранение паролей в `~/.docker/config.json` в формате Base64 небезопасно. Рекомендуется использовать:
- **Docker Credential Helpers:** `osxkeychain` (macOS), `pass` (Linux), `secretservice` (GNOME/KDE).
- **Короткоживущие токены:** В CI/CD используйте временные токены (например, `id_token` в GitHub Actions) или IAM-роли (в облаках).

### Проксирование и кэширование (Pull-through Cache)

Для обхода лимитов Docker Hub (Rate Limiting) и ускорения деплоя внутри закрытых контуров:
- **Registry Mirror:** Настройка демона Docker на использование внутреннего зеркала.
- **Proxy Cache (Harbor/Zot):** Реестр сам скачивает и кэширует образы из внешних источников при первом запросе.

## Практические сценарии

### Сценарий 1: Работа с OCI-артефактами (Helm)

Современный способ распространения манифестов Kubernetes.

```bash
# Упаковка и пуш чарта в реестр
helm package ./my-chart
helm push my-chart-0.1.0.tgz oci://registry.example.com/charts

# Скачивание
helm pull oci://registry.example.com/charts/my-chart --version 0.1.0
```

### Сценарий 2: Использование GitHub Container Registry (GHCR)

Стандарт для Open Source и проектов на GitHub. Поддерживает OCI 1.1 и Referrers.

```bash
# Аутентификация через временный токен в GitHub Actions
echo ${{ secrets.GITHUB_TOKEN }} | docker login ghcr.io -u ${{ github.actor }} --password-stdin

# Публикация с аттестациями (Buildx + Scout)
docker buildx build --push \
  --attest type=sbom \
  --attest type=provenance \
  -t ghcr.io/owner/repo:v1.0.0 .
```

### Сценарий 3: Harbor — корпоративный стандарт

Идеален для On-premise инсталляций и строгих требований ИБ.
- **Project Quotas:** Ограничение места для команд.
- **Replication:** Автоматическая синхронизация образов между филиалами.
- **P2P Distribution:** Интеграция с Dragonfly или Kraken для быстрой раздачи образов на тысячи нод.

### Сценарий 4: Локальное зеркало (Pull-through Cache)

Для экономии внешнего трафика и стабильности CI.

```yaml
# Пример настройки Harbor как прокси для Docker Hub
# 1. Создать "Registry Endpoint" для docker.io
# 2. Создать проект "docker-hub" с включенным "Proxy Cache"
# 3. В настройках демона на серверах:
# /etc/docker/daemon.json
{
  "registry-mirrors": ["https://harbor.example.com/v2/docker-hub"]
}
```

## Дополнительная информация

### Сравнение функциональности

| Реестр | OCI 1.1 / Referrers | Artifacts | Особенности |
| :--- | :--- | :--- | :--- |
| **Docker Hub** | Полная | Да | Docker Scout, официальные образы |
| **Harbor** | Полная | Да | RBAC, Сканирование Trivy, P2P, GC |
| **GHCR** | Полная | Да | Тесная интеграция с GitHub Actions |
| **AWS ECR** | Полная | Да | IAM-интеграция, сканирование Inspector |
| **Zot** | Полная | Да | Сверхлегкий, фокус на OCI 1.1 |

### Очистка и обслуживание (Garbage Collection)

Удаление манифеста через API не освобождает место на диске. В реестрах (особенно self-hosted) необходимо:
1. Удалить неиспользуемые теги/манифесты.
2. Запустить процедуру **Garbage Collection** для удаления "осиротевших" (orphaned) слоев.
   *Внимание: во время GC в режиме "read-only" запись в реестр обычно невозможна.*
