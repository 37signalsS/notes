# Docker Context — управление профилями подключения

## Определения

- **Docker Context:** Механизм Docker CLI для управления профилями подключения к различным окружениям (Docker Engine, Swarm, Kubernetes). Контекст инкапсулирует адрес хоста (Endpoint), сертификаты безопасности и метаданные в именованный профиль.
- **Endpoint:** Точка входа для взаимодействия с Docker API. Поддерживаются локальные сокеты (`unix://`), удаленный доступ через `ssh://` и защищенный `tcp://` (mTLS).
- **Docker Offload:** (Новинка 2024+) Возможность делегировать ресурсоемкие задачи (например, вычисления для ИИ с использованием GPU) с локальной машины на удаленный контекст.
- **Context Switching:** Мгновенное переключение активного профиля в CLI, определяющее, какому демону будут отправляться команды по умолчанию.

## Основные концепции

### Назначение и преимущества

1. **Безопасное удаленное управление:** Использование SSH как основного транспорта позволяет управлять серверами без открытия портов Docker-демона в сеть.
2. **Управление гибридными средами:** Удобное переключение между Docker Desktop, Colima, OrbStack, Rootless Docker и удаленными VPS/облаками.
3. **Оптимизация сборок (Build Cloud):** Подключение к облачным контекстам Docker Build Cloud для ускорения сборки за счет распределенного кэша.
4. **Абстракция инфраструктуры:** Команды развертывания (`docker stack deploy`, `docker compose up`) остаются неизменными; меняется только целевой контекст.

### Компоненты контекста

- **Метаданные:** Имя профиля, описание, текущий стек (orchestrator).
- **Конфигурация (Endpoints):**
  - **Docker:** Параметры подключения к движку (host, сертификаты CA/Cert/Key).
  - **Kubernetes:** (Legacy) Поддержка интеграции с K8s через Docker CLI считается устаревшей; рекомендуется использовать нативные контексты `kubectl`.

### Хранение конфигурации

Docker хранит данные о контекстах в домашней директории пользователя:
- **`~/.docker/config.json`:** Содержит поле `"currentContext"`, которое определяет активный профиль. Если поле отсутствует, используется `default`.
- **`~/.docker/contexts/`:** Директория со всеми созданными контекстами. Каждый контекст хранится в папке с уникальным хешем, содержащей:
  - `meta.json` — описание эндпоинтов и метаданные.
  - `tls/` — (опционально) клиентские сертификаты и ключи.

## Практические сценарии

### Сценарий 1: Удаленное управление через SSH (Рекомендуемый)

Самый безопасный способ управления удаленным сервером. Использует существующую SSH-инфраструктуру.

1. Создайте контекст, указав SSH-адрес:
   ```bash
   docker context create remote-vps --docker "host=ssh://user@server-ip"
   ```
2. Переключитесь на него:
   ```bash
   docker context use remote-vps
   ```
3. Для выполнения разовой команды без переключения используйте флаг `--context`:
   ```bash
   docker --context remote-vps ps
   ```

**Совет по безопасности (2025):** Используйте выделенный SSH-ключ для Docker и ограничьте его на сервере в `authorized_keys` через префикс `command="docker system dial-stdio"`.

### Сценарий 2: Использование Docker Build Cloud

Для ускорения локальных сборок можно использовать контекст, подключенный к облаку:

```bash
# Создание облачного контекста (требуется аутентификация в Docker Hub)
docker buildx create --use --driver cloud my-org/my-builder
```

### Сценарий 3: Локальные рантаймы и Rootless

Переключение между стандартным Docker Desktop и легковесными альтернативами (Colima) или режимом без root-прав:

```bash
# Переключение на Colima
docker context use colima

# Настройка контекста для Rootless Docker
docker context create rootless --docker "host=unix:///run/user/1000/docker.sock"
```

### Сценарий 4: Удаленное управление через mTLS (Корпоративный стандарт)

Используется, когда SSH недоступен или требуется строгая аутентификация через PKI (подробнее см. в **[Docker Context для CI/CD](../Docker_swarm/CI_CD/docker_context_setup.md)**).

```bash
docker context create prod-swarm \
  --docker "host=tcp://manager:2376,ca=ca.pem,cert=cert.pem,key=key.pem"
```

## Дополнительная информация

### Справочник CLI

| Команда | Описание |
|:---|:---|
| `docker context ls` | Список всех контекстов (активный отмечен `*`) |
| `docker context show` | Показать имя текущего активного контекста |
| `docker context use <NAME>` | Установить контекст по умолчанию |
| `docker context create <NAME>` | Создать новый профиль |
| `docker context update <NAME>` | Изменить параметры существующего контекста |
| `docker context inspect <NAME>` | Подробная информация в формате JSON |
| `docker context export <NAME> <FILE>.tar` | Экспорт контекста (включая TLS-ключи) в архив |
| `docker context import <NAME> <FILE>.tar` | Импорт контекста из архива |
| `docker context rm <NAME>` | Удаление профиля |

### Приоритет переменных окружения

Важно помнить иерархию приоритетов Docker CLI:
1. Флаг `--context` или переменная `DOCKER_CONTEXT` (высший приоритет).
2. Переменная `DOCKER_HOST` (если установлена, **игнорирует** активный контекст, кроме случаев использования флага `--context`).
3. Активный контекст, установленный через `docker context use` (хранится в `config.json`).

**Рекомендация:** Если команды Docker ведут себя неожиданно, проверьте `env | grep DOCKER`. Для корректной работы контекстов рекомендуется выполнить `unset DOCKER_HOST`.

### Визуализация в терминале

Для предотвращения ошибок рекомендуется интегрировать имя текущего контекста в prompt оболочки.
- **Starship:** Автоматически отображает значок Docker и имя контекста.
- **Oh My Zsh:** Используйте плагин `docker` и тему, поддерживающую отображение контекста.

### Диагностика (Troubleshooting)

- **Ошибка "Permission denied":** При использовании SSH убедитесь, что пользователь на удаленной машине входит в группу `docker` или имеет права на чтение/запись в `/var/run/docker.sock`.
- **Контекст игнорируется:** Проверьте переменную `DOCKER_HOST`. Она перекрывает настройки контекста.
- **Ошибка подключения к сокету:** Если вы переключились на контекст, который использует локальный сокет (например, после удаления Colima), Docker CLI будет выдавать ошибку. Вернитесь на дефолтный: `docker context use default`.

### Docker Context vs Build Context

Не путайте эти понятия:
- **Docker Context:** Определяет, **куда** (на какой сервер) отправляются команды CLI.
- **Build Context:** Набор локальных файлов, передаваемых демону для сборки образа. Подробнее см. **[Контекст сборки (Build Context)](./Dockerfile/dockerfile_build_context.md)**.
