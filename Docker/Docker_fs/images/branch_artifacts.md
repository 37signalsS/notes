# Docker: Идентичность и неизменяемость артефактов в CI/CD

## Определения

- **Артефакт сборки (Build Artifact)**: Docker-образ, созданный в процессе непрерывной интеграции (CI — Continuous Integration). В идеальном мире каждый артефакт должен быть уникальным, отслеживаемым и неизменяемым.
- **Неизменяемый артефакт (Immutable Artifact)**: Принцип, согласно которому однажды созданный артефакт (образ) никогда не изменяется. Любые изменения приводят к созданию **нового** артефакта с новой версией или тегом.
- **Воспроизводимость сборки (Build Reproducibility)**: Возможность воссоздать байт в байт идентичный артефакт при запуске того же процесса сборки с теми же входными данными.

## Основные концепции

### Проблема идентичности образов между окружениями

Часто возникает вопрос: если взять один и тот же `Dockerfile` и собрать его сначала для ветки `dev`, а затем для ветки `stage`, будет ли это один и тот же артефакт?

**Ответ: Категорически нет.**

Даже при идентичном файле `Dockerfile` результат сборки почти всегда будет разным. Это связано с тем, что на итоговый Docker-образ влияет не только сценарий сборки, но и весь **контекст сборки**.

### Факторы, влияющие на идентичность артефакта

| Фактор | Почему он создает различия |
| :--- | :--- |
| **Исходный код** | Команда `COPY . .` копирует содержимое директории. Код в ветках `dev` и `stage` почти всегда различается. |
| **"Плавающие" теги** | Инструкция `FROM ubuntu:latest` в разное время может указывать на разные версии (`digest`) базового образа. |
| **Зависимости ОС** | Команда `RUN apt-get install -y my-package` без указания версии сегодня и завтра может установить разные версии пакета. |
| **Аргументы сборки**| Переменные, передаваемые через `--build-arg` (например, `ENV=development` vs `ENV=production`), могут менять логику внутри `Dockerfile`. |
| **Контекст сборки** | Содержимое директории, из которой запускается сборка, включая файлы, не указанные в `.dockerignore`. |

Из-за этих факторов сборка одного и того же `Dockerfile` в разных ветках или в разное время создает **разные, несовместимые артефакты**. Продвигать по контурам нужно **один и тот же, единожды собранный** образ.

## Практические сценарии

### Создание неизменяемого и отслеживаемого артефакта

Для гарантии наличия уникального и неизменяемого артефакта для каждого коммита необходимо следовать практикам детерминированной сборки.

**Шаг 1: Подготовка `Dockerfile` для воспроизводимости**

```dockerfile
# 1. Используйте базовый образ с пиннингом по digest (sha256)
FROM ubuntu:20.04@sha256:8ae9bafbb64f63a50caab9601b890875452b34b5b953d085023963284594f417

# 2. Передавайте метаданные сборки через ARG
ARG GIT_COMMIT
ARG BUILD_DATE
ARG APP_VERSION=unknown

# 3. Фиксируйте версии пакетов
RUN apt-get update && apt-get install -y --no-install-recommends \
    python3=3.8.10-0ubuntu1~20.04.1 \
 && rm -rf /var/lib/apt/lists/*
# → Пакеты установлены с фиксированными версиями

# 4. Копируйте код
WORKDIR /app
COPY . .

# 5. Внедряйте метаданные в LABEL для отслеживаемости
LABEL \
    org.opencontainers.image.source="https://github.com/my-org/my-app" \
    org.opencontainers.image.created=$BUILD_DATE \
    org.opencontainers.image.revision=$GIT_COMMIT \
    org.opencontainers.image.version=$APP_VERSION
```

**Шаг 2: Сборка в CI/CD с правильным тегированием**

В конвейере CI/CD (Continuous Integration/Continuous Deployment) образ собирается **один раз** (например, при пуше в `main` или создании тега) и получает уникальный идентификатор.

```bash
# Пример команды сборки в CI-пайплайне
export GIT_COMMIT=$(git rev-parse HEAD)
export BUILD_DATE=$(date -u +'%Y-%m-%dT%H:%M:%SZ')
export APP_VERSION="1.2.3"

docker build \
  --build-arg GIT_COMMIT=$GIT_COMMIT \
  --build-arg BUILD_DATE=$BUILD_DATE \
  --build-arg APP_VERSION=$APP_VERSION \
  -t my-registry/my-app:${APP_VERSION}-${GIT_COMMIT::7} \
  .
# → Собирается образ с тегом 1.2.3-a9c8e7f и внедренными метаданными
```

*Результат:* Вы получаете образ, например, `my-registry/my-app:1.2.3-a9c8e7f`, который жестко привязан к конкретной версии кода. Именно этот неизменяемый артефакт должен использоваться во всех средах.
