# Идентичность и неизменяемость артефактов Docker в CI/CD

## Определения

- **Артефакт сборки (Build Artifact)** — Docker-образ, созданный в процессе непрерывной интеграции (CI). Является материальным результатом сборки, имеющим фиксированное содержимое и уникальный идентификатор.
- **Неизменяемость (Immutability)** — принцип, согласно которому артефакт никогда не изменяется после создания. Любое исправление или обновление требует сборки нового образа с новым тегом/дайджестом.
- **Воспроизводимость сборки (Reproducible Build)** — процесс, при котором из идентичных исходных данных (код, зависимости, инструменты) всегда получается побайтово идентичный артефакт (совпадающий SHA256 дайджест).
- **Дайджест (Digest / Immutable Identifier)** — уникальный криптографический хэш содержимого образа (обычно SHA256), вычисляемый по его манифесту. Гарантирует, что образ не был подменен или изменен.
- **Аттестация (Attestation)** — дополнительные метаданные (например, SBOM или Provenance), прикрепляемые к дайджесту образа, которые подтверждают его состав и условия сборки.

## Основные концепции

### Проблема идентичности образов между ветками и окружениями

Одной из критических ошибок в CI/CD является повторная сборка образа для разных контуров (например, сборка из `develop` для `staging` и затем повторная сборка из `main` для `production`).

**Проблема:** Даже при идентичном коде и `Dockerfile`, результат двух разных запусков `docker build` почти никогда не будет бинарно идентичным. Это нарушает принцип **Build Once, Deploy Anywhere** и может привести к ситуации, когда протестированный артефакт ведет себя иначе в эксплуатации из-за незаметных различий в слоях.

### Факторы, нарушающие детерминизм сборки

| Фактор | Причина различий | Способ устранения |
| :--- | :--- | :--- |
| **Плавающие теги (Floating Tags)** | `FROM ubuntu:latest` сегодня и завтра может указывать на разные версии ОС. | Фиксация по мажорной версии или дайджесту (`@sha256:...`). |
| **Временные метки (Timestamps)** | Docker по умолчанию записывает время создания каждого слоя. | Использование `SOURCE_DATE_EPOCH` в BuildKit для фиксации времени. |
| **Недетерминированные пакеты** | `apt-get install -y nginx` установит актуальную версию, если она не зафиксирована. | Жесткая фиксация версий пакетов (`nginx=1.24.0-1`). |
| **Порядок файлов** | Команда `COPY . .` может упаковывать файлы в разном порядке в зависимости от ФС. | BuildKit автоматически нормализует порядок файлов при сборке. |
| **Контекст сборки** | Лишние файлы (логи, кэш), не попавшие в `.dockerignore`. | Строгая настройка `.dockerignore` и использование multi-stage сборок. |
| **Метаданные (Labels)** | Изменение текста `LABEL` (даже даты сборки) меняет дайджест конфигурации образа. | Использование внешних аттестаций для динамических метаданных. |

## Практические сценарии

### Создание детерминированного Docker-образа

Для обеспечения 100% идентичности артефакта необходимо минимизировать влияние внешних факторов на каждом этапе.

**Шаг 1: Подготовка Dockerfile для воспроизводимости**

```dockerfile
# 1. Фиксация базового образа по дайджесту (рекомендуется для Production)
FROM ubuntu:24.04@sha256:72297848457d5d37d126263012759e6d3e707bc4ef415303ee5b40cf3957cc98

# 2. Передача метаданных сборки через ARG (только статичные данные)
ARG GIT_COMMIT
ARG APP_VERSION=unknown

# 3. Фиксация версий системных пакетов
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl=8.5.0-2ubuntu10.1 \
 && rm -rf /var/lib/apt/lists/*
# → Пакеты зафиксированы, кэш очищен

WORKDIR /app
COPY . .

# 4. Внедрение стандартизированных метаданных (OCI Labels)
LABEL \
    org.opencontainers.image.source="https://github.com/my-org/my-app" \
    org.opencontainers.image.revision=$GIT_COMMIT \
    org.opencontainers.image.version=$APP_VERSION
```

**Шаг 2: Использование BuildKit для воспроизводимых меток времени**

Современный движок **BuildKit** позволяет фиксировать время создания слоев через переменную `SOURCE_DATE_EPOCH`.

```bash
# Использование фиксированной метки времени (например, время последнего коммита)
export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)

docker buildx build \
  --build-arg GIT_COMMIT=$(git rev-parse HEAD) \
  --build-arg SOURCE_DATE_EPOCH=$SOURCE_DATE_EPOCH \
  --attest type=sbom \
  --attest type=provenance,mode=max \
  -t my-registry.com/my-app:1.0.0 \
  --push .
```
*Использование `--attest` позволяет вынести информацию о сборке (Provenance) и составе (SBOM) в отдельные метаданные, не меняя основной дайджест слоев при повторных запусках с теми же исходниками.*

### Проверка идентичности через дайджесты

Чтобы убедиться, что образ в `dev` и `prod` идентичен, сравнивайте не теги, а **RepoDigests**.

```bash
# Получение дайджеста образа
docker inspect --format='{{index .RepoDigests 0}}' my-app:1.0.0
# → my-registry.com/my-app@sha256:a1b2c3d4...

# Если SHA256 совпадают — артефакты бинарно идентичны.
```

## Дополнительная информация

### Иерархия идентификации артефактов

1.  **RepoDigest (SHA256):** Наивысший приоритет. Гарантирует идентичность манифеста и всех слоев в конкретном реестре.
2.  **Image ID:** Идентификатор конфигурации. Может совпадать для разных тегов, если слои идентичны.
3.  **Tags (v1.2.3):** Мутабельные ссылки. Удобны для людей, но должны использоваться только как указатели на проверенные дайджесты.

### Рекомендации по эксплуатации

- **Принцип одного раза:** Никогда не запускайте `docker build` для продвижения кода в Production. Используйте `docker tag` / `docker push` или специализированные инструменты (Skopeo/Crane).
- **Анализ SBOM:** Автоматизируйте генерацию SBOM при сборке для упрощения аудита безопасности без необходимости сканирования работающих контейнеров.
- **Целостность:** Для обеспечения цепочки доверия используйте фреймворк **[SLSA](../../Security/Supply_Chain_Security/overview.md)**.
