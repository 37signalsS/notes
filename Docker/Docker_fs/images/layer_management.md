# Docker: Анализ и управление слоями образа

## Определения

- **Слой образа (Image Layer)** — неизменяемый слепок файловой системы, создаваемый каждой инструкцией `RUN`, `COPY` или `ADD` в `Dockerfile`. Образ представляет собой упорядоченный набор таких слоев.
- **Анализ слоев (Layer Analysis)** — процесс инспекции содержимого, размера и метаданных каждого слоя для выявления неэффективности (например, временных файлов или дубликатов).
- **Сжатие образа (Squashing)** — процесс объединения нескольких слоев в один для уменьшения размера и упрощения структуры образа.
- **Механизм Whiteout** — специальный маркер в файловой системе (используемый **[OverlayFS](../docker_overlayfs.md)**), который скрывает файл в верхнем слое, если он был удален, фактически оставляя его физически присутствующим в нижних слоях.

## Основные концепции

### Персистентность данных и механизм удаления

В Docker удаление файла в новом слое не освобождает место, занятое им в предыдущих слоях. Это связано с тем, что слои доступны только для чтения (read-only).

**Как это работает:**
1. Инструкция `RUN apt-get install` создает слой с бинарными файлами.
2. Инструкция `RUN apt-get remove` в следующем шаге не удаляет данные из первого слоя, а лишь создает **whiteout-файл** в текущем слое.
3. При запуске контейнера OverlayFS объединяет слои и, видя маркер whiteout, "прячет" файл от пользователя.
4. Итоговый размер образа остается равным сумме всех слоев, включая уже "удаленные" файлы.

**Рекомендация:** Всегда выполняйте установку и очистку в рамках одной инструкции `RUN`, объединяя их через `&&`. Подробнее см. в разделе **[Оптимизация сборки Docker-образов](../../Dockerfile/Docker_best_practices/build_optimization.md)**.

### Сжатие (Squashing): за и против

Сжатие позволяет объединить все слои, созданные в текущем `Dockerfile`, в один финальный слой поверх базового образа.

| Преимущества | Недостатки |
| :--- | :--- |
| **Минимальный размер:** Полное удаление файлов, созданных и стертых в разных слоях. | **Потеря кэширования:** Любое изменение в коде требует полной пересборки "сжатого" блока. |
| **Безопасность:** Гарантированное удаление секретов, если они были случайно добавлены и удалены в разных слоях. | **Низкая эффективность Pull/Push:** Слои нельзя переиспользовать между разными образами в реестре. |

**Вывод:** Используйте сжатие только для финальных артефактов (Production) или при создании "золотых" базовых образов организации.

## Практические сценарии

### Сценарий 1: Инспекция через `docker history`

Команда `docker history` — базовый инструмент для оценки структуры образа.

```bash
docker history my-app:latest
```

**Анализ вывода:**
- **`<missing>`**: Указывает на слои, созданные в среде BuildKit или загруженные из реестра. Это нормальное поведение, означающее, что локально доступны только метаданные промежуточных шагов.
- **SIZE**: Ищите слои с аномально большим весом (например, установка зависимостей без очистки кэша).
- **CREATED BY**: Позволяет сопоставить слой с конкретной строкой в `Dockerfile`.

### Сценарий 2: Глубокий анализ с помощью `dive`

Инструмент `dive` позволяет интерактивно исследовать изменения файловой системы между слоями.

```bash
# Запуск анализа
dive my-app:latest
```

**Ключевые показатели в `dive`:**
- **Efficiency Score**: Коэффициент полезного использования пространства. Низкий балл указывает на наличие "мусора" (файлов, которые были изменены или удалены в последующих слоях).
- **Wasted Space**: Объем данных, которые можно сэкономить при правильной оптимизации или сжатии.
- **Layer Tree**: Позволяет переключаться между слоями и видеть, какие именно файлы были добавлены (желтый цвет) или удалены (красный цвет) в текущем шаге.

### Сценарий 3: Сжатие образа через Docker Buildx

Современный способ сжатия использует возможности BuildKit через плагин `buildx`. Флаг `--squash` объединяет все слои приложения в один.

```bash
# Сборка со сжатием слоев
docker buildx build --squash -t my-app:prod .
```

*Примечание:* Это наиболее надежный метод, заменяющий устаревшие экспериментальные флаги стандартного демона и сторонние утилиты вроде `docker-squash`.

## Дополнительная информация

### Сравнение методов оптимизации

| Метод | Сложность | Влияние на кэш | Эффективность |
| :--- | :--- | :--- | :--- |
| **RUN && (цепочки)** | Низкая | Сохраняется | Средняя |
| **Multi-stage builds** | Средняя | Сохраняется | **Высокая** |
| **Squashing** | Низкая | Уничтожается | Высокая |

**Multi-stage builds** является "золотым стандартом", так как обеспечивает минимальный размер без потери преимуществ кэширования. См. **[Практические примеры Multi-stage](../../Dockerfile/Docker_best_practices/build_optimization.md#использование-multi-stage-сборок)**.
