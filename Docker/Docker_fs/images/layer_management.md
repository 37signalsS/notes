# Docker: Анализ и управление слоями образа

Управление слоями — это продвинутая техника, направленная на анализ и оптимизацию размера и структуры Docker-образов. Основные практики включают анализ содержимого слоев и их сжатие (squashing).

## Определения

- **Анализ слоев (Layer Analysis)**: Процесс инспекции содержимого и размера каждого слоя в Docker-образе для выявления неэффективности, ненужных файлов или временных данных, оставшихся от процесса сборки.
- **Сжатие образа (Image Squashing)**: Процесс объединения нескольких слоев Docker-образа в один новый слой. Это может уменьшить итоговый размер образа, но имеет ряд ограничений в процессе разработки.

## Основные концепции

### Цели анализа слоев

Анализ слоев помогает ответить на следующие вопросы:

- **Какие слои имеют наибольший вес?** Позволяет найти этапы сборки, которые вносят наибольший вклад в итоговый размер.
- **Что находится внутри каждого слоя?** Помогает обнаружить ненужные файлы: кэши пакетных менеджеров, временные файлы, журналы логов, неоптимизированные ресурсы.
- **Есть ли избыточность данных?** Можно увидеть, если файл был добавлен в одном слое, а затем скрыт в другом.

### Персистентность удаленных файлов и размер образа

Один из ключевых аспектов: если установить пакет в одном слое (`RUN apt-get install ...`), а удалить его в следующем (`RUN apt-get remove ...`), он все равно будет занимать место в финальном образе.

**Причины и последствия:**

1. **Неизменяемость слоев:** Каждый слой в Docker — это неизменяемый снимок файловой системы. Инструкция `RUN` создает новый слой.
2. **Механизм Whiteout:** Когда файл удаляется в новом слое, Docker (используя драйвер файловой системы **[OverlayFS](../docker_overlayfs.md)**) не удаляет его физически из предыдущего слоя. Вместо этого в текущем слое создается специальный маркер удаления (whiteout), который скрывает файл при объединении слоев.
3. **Итоговый размер:** Размер образа — это сумма размеров **всех** его слоев. Слой с установкой пакета добавляет свой вес, а слой с удалением добавляет размер маркера whiteout, не освобождая место, занятое пакетом.

**Рекомендация:**
Для минимизации размера образа установку и очистку необходимо выполнять в рамках **одной инструкции `RUN`**, объединяя команды через `&&`. Подробнее см. в разделе **[Оптимизация сборки Docker-образов](../../Dockerfile/Docker_best_practices/build_optimization.md)**.

### Концепция сжатия (Squashing) и ее особенности

Сжатие объединяет несколько слоев, созданных из `Dockerfile`, в один. Слои от команд `RUN`, `COPY`, `ADD` сливаются, в то время как слои базового образа (`FROM ...`) остаются нетронутыми.

| Преимущества | Недостатки |
| :--- | :--- |
| **Уменьшение размера:** Позволяет физически исключить файлы, которые были созданы и удалены в разных слоях. | **Уничтожение кэша сборки:** Изменение любой команды в "сжатом" блоке приводит к полной пересборке всего блока, что замедляет разработку. |
| **Упрощение истории:** Создает плоскую историю образа, скрывая промежуточные шаги сборки. | **Снижение эффективности совместного использования:** Другие образы не смогут переиспользовать отдельные слои из сжатого блока, что увеличивает нагрузку на хранилище. |

**Вывод:** Сжатие — это инструмент для финальной оптимизации образов для промышленной эксплуатации (production), где минимальный размер важнее скорости пересборки. Его не следует использовать на этапе активной разработки.

## Практические сценарии

### Сценарий 1: Анализ слоев с помощью `docker history` и `dive`

1. **Первичный анализ через интерфейс командной строки (CLI — Command Line Interface)**:
    Команда `docker history` показывает структуру слоев, команды их создания и размер.

    ```bash
    docker history my-app:latest
    # → IMAGE          CREATED          CREATED BY                                      SIZE
    # → <hash>         10 minutes ago   /bin/sh -c #(nop)  CMD ["node" "app.js"]        0B
    # → <hash>         10 minutes ago   /bin/sh -c npm install                          150MB
    ```

2. **Глубокий анализ с использованием `dive`**:
    `dive` предоставляет интерактивный пользовательский интерфейс (UI — User Interface) для исследования слоев.

    ```bash
    # Анализ образа
    dive my-app:latest
    # → Анализ слоев, обнаружение неэффективных файлов (wasted space)
    ```

    Возможности `dive`:
    - Просмотр изменений файловой системы в каждом слое.
    - Поиск файлов, созданных и удаленных в разных слоях.
    - Расчет коэффициента эффективности использования пространства.

### Сценарий 2: Сжатие образа при сборке через флаг `--squash`

Это экспериментальная функция Docker, требующая активации в настройках демона.

1. **Включение экспериментального режима:**
    В файле конфигурации `/etc/docker/daemon.json` добавьте:

    ```json
    {
      "experimental": true
    }
    ```

    Затем перезапустите службу Docker.

2. **Сборка со сжатием:**

    ```bash
    docker build --squash -t my-app:squashed .
    # → Образ собран, слои приложения объединены в один
    ```

### Сценарий 3: Использование утилиты `docker-squash`

Внешний инструмент `docker-squash` позволяет сжимать слои уже готового образа.

```bash
# Установка утилиты через менеджер пакетов Python (pip)
pip install docker-squash
# → Утилита установлена

# Сжатие последних 3 слоев образа
docker-squash -f 3 my-app:latest -t my-app:squashed
# → Создан новый образ my-app:squashed с тремя объединенными верхними слоями
```

## Дополнительная информация

- **Когда применять сжатие?**
  - При подготовке базовых ("золотых") образов организации.
  - Для финальной сборки артефактов перед развертыванием в production.
- **Альтернативы сжатию:**
  Использование **многоэтапных сборок (multi-stage builds)** является более предпочтительным методом. Они позволяют получить компактный образ, не теряя преимуществ кэширования на этапах разработки.
