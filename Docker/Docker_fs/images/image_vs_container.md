# Docker: Сравнение образа и контейнера

**Актуально для:** Docker 24.x–29.x, Kubernetes 1.29.x–1.32.x, CI/CD-раннеры на основе Linux

Разграничение понятий образа и контейнера является фундаментальным для понимания архитектуры Docker. Образ представляет собой статический шаблон, в то время как контейнер — это его динамическое, исполняемое воплощение.

## Предварительные требования

Перед выполнением практических сценариев из этого файла убедитесь, что соблюдены следующие условия:

- **Docker Engine** версии **24.0+** (актуальные стабильные релизы: 27.x, 28.x, 29.x). Проверка: `docker version --format '{{.Server.Version}}'` → `27.3.1`.
- **Запущенный демон `dockerd`** (или Docker Desktop / Rootless-окружение). Проверка доступности: `docker info` → в выводе `Server Version` и `Storage Driver` (например, `overlay2`).
- **Права на управление Docker**: пользователь состоит в группе `docker`, либо используется `root`, либо настроен Rootless-режим. Без прав: `docker: permission denied while trying to connect to the Docker daemon socket`.
- **Доступ к файловой системе хоста** для инспекции слоёв (требует прав `root` для штатного `graph root` `/var/lib/docker`, либо доступа к каталогу Rootless — `~/.local/share/docker`).
- **Тестовые образы** для экспериментов: `nginx:latest`, `redis:alpine` (скачаются при первом `docker run`).
- **Базовые навыки Linux**: `ps`, `cat`, `du`, понимание понятий процесса, файловой системы и прав доступа.

> Версии команд и поведение отдельных механизмов (например, хранилище образов на базе containerd) зависят от релиза Docker — см. раздел «Примечания по версиям».

## Определения

- **Образ (Image)** — неизменяемый (read-only) пакет, содержащий всё необходимое для запуска приложения: код, среду выполнения, системные библиотеки и настройки. Является "чертежом" или снимком файловой системы.
- **Контейнер (Container)** — запущенный экземпляр образа. Это изолированный процесс (или группа процессов), который использует ресурсы хоста, но имеет собственное изолированное окружение (файловую систему, сеть, дерево процессов).
- **Записываемый слой (Writable Layer)** — тонкий слой файловой системы, который добавляется поверх неизменяемых слоев образа при запуске контейнера. Все изменения, внесенные в работающем контейнере (новые файлы, модификация существующих), сохраняются именно здесь.
- **Жизненный цикл (Lifecycle)** — совокупность состояний, через которые проходит контейнер от момента создания до полного удаления из системы.
- **Дайджест образа (Digest)** — криптографический хэш (SHA256) содержимого образа, вычисляемый по схеме контентно-адресуемого хранилища (content-addressable storage). Однозначно идентифицирует конкретное содержимое; в отличие от тега, дайджест неизменен. Формат: `sha256:<hex>`.
- **Тег (Tag)** — изменяемая (мутабельная) текстовая метка, указывающая на конкретный дайджест. Один тег может со временем указывать на разный образ (например, после повторного `docker pull nginx:latest` содержимое за тегом меняется).
- **Графический драйвер / Graph Driver** — подсистема Docker, управляющая тем, как слои образа и записываемый слой контейнера объединяются в единую файловую систему (например, `overlay2`). Для каждого контейнера драйвер выделяет на хосте каталоги `upperdir` (записываемый слой), `workdir` (вспомогательный) и `merged` (итоговое смонтированное представление).

## Основные концепции

### Сборка (Build-time) против Выполнения (Run-time)

- **Build-time (Этап сборки)**: Вы описываете инструкции в `Dockerfile` и выполняете `docker build`. Результатом является **образ** — артефакт, который можно хранить в реестре и передавать между серверами.
- **Run-time (Этап выполнения)**: Вы выполняете `docker run`. Docker берет образ и запускает на его основе один или несколько **контейнеров**.

Ключевое отличие: на этапе сборки формируется статичный, неизменяемый набор слоёв; на этапе выполнения образ "оживает" — поверх него создаётся записываемый слой, и процесс начинает потреблять CPU, память и сетевые ресурсы хоста. Образ можно запустить сколько угодно раз, и каждый запуск даст независимый контейнер.

### Состояния контейнера

Контейнер может находиться в одном из следующих состояний:
1. **Created**: Контейнер создан (выделены ресурсы, подготовлена ФС), но процесс еще не запущен.
2. **Running**: Основной процесс контейнера (Entrypoint) выполняется.
3. **Paused**: Все процессы контейнера приостановлены (сигнал `SIGSTOP` через cgroups freezer), память "заморожена". Контейнер продолжает занимать память и сетевые ресурсы, но не потребляет CPU.
4. **Exited**: Процесс завершился (с кодом 0 или ошибкой). Файловая система (записываемый слой) сохраняется.
5. **Dead**: Контейнер в процессе удаления или произошла критическая ошибка при попытке остановки. Переходное (транзиентное) состояние — в `docker ps` обычно не видно, доступно только через `docker inspect` (`State.Status` = `removalInProgress` / `dead`).

Посмотреть текущее состояние конкретного контейнера:
```bash
docker inspect --format '{{.State.Status}}' my-app-cont
# → running

# Список контейнеров в конкретном состоянии (например, завершённых):
docker ps --filter status=exited
# → CONTAINER ID   IMAGE     COMMAND                  CREATED          STATUS                      PORTS     NAMES
# → a1b2c3d4e5f6   nginx     "/docker-entrypoint.…"   2 minutes ago    Exited (0) 2 minutes ago              my-app-cont
```

### Механизм Copy-on-Write (CoW)

Docker использует стратегию "Копирование при записи" для эффективного управления ресурсами.
1. Все слои образа доступны только для чтения.
2. Если процесс в контейнере хочет изменить файл, существующий в образе, Docker копирует этот файл из нижних слоев (image layers) в верхний записываемый слой (writable layer).
3. Изменения происходят в копии, не затрагивая исходный образ.
4. Это позволяет запускать сотни контейнеров на базе одного образа, потребляя минимум дискового пространства. Подробнее см. в разделах **[Управление слоями](./layer_management.md)** и **[Драйвер хранения OverlayFS](../docker_overlayfs.md)**.

Важный нюанс производительности (операция **copy-up**): при первой модификации файла из нижнего слоя весь файл копируется целиком в верхний слой, даже если меняется лишь несколько байт. Для больших файлов (например, журналов, баз данных внутри образа) это вызывает заметную задержку ввода-вывода при первой записи. Поэтому «горячие» файлы, интенсивно изменяемые на лету, следует выносить в **[тома (Volumes)](../docker_volumes.md)**, минуя CoW.

### Эфемерность и безопасность

- **Statelessness**: Контейнеры по своей природе временны. При удалении контейнера (`docker rm`) его записываемый слой уничтожается навсегда. Для сохранения данных используйте **[тома (Volumes)](../docker_volumes.md)**.
- **ReadOnlyRootfs**: Лучшая практика безопасности — запуск контейнера с флагом `--read-only`. Это запрещает запись в Writable Layer, защищая систему от изменений вредоносным ПО. Все временные данные в этом режиме должны писаться в `tmpfs`.

Различайте **перезапуск** и **удаление** контейнера: при `docker restart` (и перезагрузке хоста) записываемый слой сохраняется — данные остаются на месте; при `docker rm` записываемый слой безвозвратно удаляется. Подробнее и с примерами — в разделе «Практические сценарии».

### Дрейф состояния: writable layer как источник неконсистентности

Поскольку каждый контейнер имеет независимый writable layer, два контейнера из одного образа могут diverging состояния:
- **Конфигурационный дрейф:** изменения файлов конфигурации в running контейнере (например, `/etc/nginx/nginx.conf`) не отражаются в образе. При перезапуске из того же тега `latest` изменения теряются.
- **Дисковый дрейф:** временные файлы, логи, кэши в writable layer накапливаются между деплоями. На CI-раннерах это приводит к заполнению `/var/lib/docker` между задачами.
- **Безопасность:** установка пакетов `apt-get install` в running контейнере фиксируется только в writable layer и не воспроизводится при следующем `docker run` из того же образа.

Для SRE: writable layer — это **ephemeral state**, который не должен использоваться для персистентных данных или конфигурации. Всё, что нужно пережить перезапуск, должно быть вынесено в volumes или зафиксировано в образе через `Dockerfile`/`docker commit`.


### Сравнение характеристик

| Характеристика | Образ (Image) | Контейнер (Container) |
| :--- | :--- | :--- |
| **Изменяемость** | Неизменяемый (Read-Only) | Изменяемый (через Writable Layer) |
| **Жизненный цикл** | Собирается, хранится, удаляется | Проходит через состояния (Created...Exited) |
| **Идентификатор** | Дайджест (SHA256), теги | ID (Long/Short), Имя |
| **Дисковое пространство** | Занимает место постоянно | Занимает место только для изменений (CoW) |
| **Производительность I/O** | Нативная (при чтении) | Замедление при первой записи (Copy-up) |
| **Назначение** | Шаблон для доставки ПО | Среда для выполнения ПО |
| **Переносимость** | Высокая — переносится между хостами и реестрами как единый артефакт | Привязан к хосту и рантайму; не переносится напрямую, только через фиксацию в образ (`commit`) |
| **Хранение данных** | Не предназначено (статичен) | Изменения в Writable Layer; для постоянства — внешние тома |

### Операционный инвентарь: образы и контейнеры с точки зрения SRE

Для эксплуатации hosts и CI-раннеров важно различать образы и контейнеры как разные категории объектов в инвентаре:

- **Образы (`docker images`)** — артефакты доставки, занимают место на диске постоянно. Их количество отражает разнообразие развёртываний; один и тот же базовый слой может использоваться десятками образов.
- **Контейнеры (`docker ps -a`)** — исполняемые единицы, потребляющие CPU, память, сеть и дисковый I/O через writable layer. Остановленные контейнеры продолжают занимать место под `upperdir` и должны учитываться при планировании диска.
- **`docker system df`** — ключевая команда для SRE: разделяет потребление на `Images`, `Containers`, `Local Volumes`, `Build Cache`. Высокий `Reclaimable` в строке `Images` указывает на осиротевшие слои; высокий `Containers` — на остановленные контейнеры с активными writable layers.
- **Связь с мониторингом:** количество running vs exited контейнеров, размер writable layers и доля reclaimable space должны быть метриками в дашборде хоста (node-exporter + cAdvisor).


## Практические сценарии

Все примеры предполагают выполнение от пользователя с правами на Docker (см. «Предварительные требования»). Символ `# →` обозначает ожидаемый результат.

### Жизненный цикл контейнера

1. **Создание без запуска**:
   ```bash
   docker create --name my-app-cont nginx:latest
   # → a1b2c3d4e5f6789...   (возвращается полный ID контейнера)
   # Состояние: Created
   docker inspect --format '{{.State.Status}}' my-app-cont
   # → created
   ```

2. **Запуск**:
   ```bash
   docker start my-app-cont
   # → my-app-cont
   # Состояние: Running
   docker inspect --format '{{.State.Status}}' my-app-cont
   # → running
   ```

3. **Пауза и разморозка**:
   ```bash
   docker pause my-app-cont    # Состояние: Paused (процессы не потребляют CPU)
   # → my-app-cont
   docker inspect --format '{{.State.Status}}' my-app-cont
   # → paused
   docker unpause my-app-cont  # Состояние: Running
   # → my-app-cont
   ```

4. **Остановка и просмотр изменений**:
   ```bash
   docker stop my-app-cont
   # → my-app-cont
   # Состояние: Exited
   docker inspect --format '{{.State.Status}}' my-app-cont
   # → exited
   docker diff my-app-cont     # Показывает изменения в Writable Layer
   # → C /root/.bash_history
   # → A /usr/share/nginx/html/index.html
   # → D /tmp/stale.lock
   #   A = файл/каталог добавлен (Added)
   #   C = изменён (Changed)
   #   D = удалён (Deleted) относительно слоёв образа
   ```

### Отношение Один-ко-Многим

Один образ может служить основой для неограниченного количества контейнеров.
```bash
docker run -d --name web1 nginx
# → <container_id_web1>
docker run -d --name web2 nginx
# → <container_id_web2>
```
Оба контейнера используют одни и те же 100+ MB слоев образа `nginx` в режиме чтения, но имеют независимые записываемые слои размером в несколько килобайт.

Проверить, сколько места занимают образы и контейнеры, и как они делят слои:
```bash
docker system df
# → TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
# → Images          5         3         1.2GB     600MB (50%)
# → Containers      3         1         12.3kB    12.3kB
# → Local Volumes   2         1         50MB      25MB
# → Build Cache     10        0         300MB     300MB
```
Строка `Images` показывает общий вес слоёв (разделяемый между контейнерами), `Containers` — суммарный размер индивидуальных записываемых слоёв.

### Где физически живёт записываемый слой

Чтобы увидеть, какой каталог на хосте соответствует записываемому слою конкретного контейнера:
```bash
docker inspect --format '{{.GraphDriver.Data.UpperDir}}' my-app-cont
# → /var/lib/docker/overlay2/abc123.../diff        (для штатного демона, от root)
# → /home/user/.local/share/docker/overlay2/.../diff (для Rootless-режима)

docker inspect --format '{{.GraphDriver.Data.MergedDir}}' my-app-cont
# → /var/lib/docker/overlay2/abc123.../merged      (итоговое смонтированное дерево)
```
`UpperDir` — это и есть записываемый слой (то, что показывает `docker diff`). Если записать файл в контейнер, он появится в `UpperDir` на хосте; слои образа (`LowerDir`) при этом не меняются.

### Запуск в режиме только для чтения (--read-only)

```bash
docker run -d --name ro-nginx --read-only --tmpfs /tmp --tmpfs /run nginx
# → <container_id>

# Запись во временную ФС разрешена (tmpfs):
docker exec ro-nginx sh -c 'touch /tmp/ok && echo WRITTEN'
# → WRITTEN

# Запись в корень (read-only) блокируется ядром:
docker exec ro-nginx touch /usr/share/nginx/html/x
# → touch: cannot touch '/usr/share/nginx/html/x': Read-only file system
```
Режим `--read-only` делает весь корень контейнера неизменяемым; любые пути, куда приложение должно писать (кэш, сессии, сокеты), нужно явно монтировать как `tmpfs` (или том), иначе процесс упадёт с ошибкой записи.

### Преобразование контейнера в образ (docker commit)

Подробное описание команды, флагов, механизма работы и практических сценариев см. в **[Создание образов через Docker Commit](../docker_commit.md)**.

### Экспорт контейнера против сохранения образа

Это частая точка путаницы между понятиями «контейнер» и «образ»:
```bash
# Экспорт ФС КОНТЕЙНЕРА — плоский tar без истории слоёв и метаданных образа:
docker export my-app-cont -o container-fs.tar
# → (файл container-fs.tar появляется; содержит только дерево файлов)

# Сохранение ОБРАЗА — полный артефакт со слоями, манифестом и тегами:
docker save nginx:latest -o nginx-image.tar
# → (файл nginx-image.tar; можно импортировать через docker load на другом хосте)
```
`docker export` даёт «сплющенную» файловую систему (история слоёв и image metadata теряются); `docker save` сохраняет образ полностью и переносим. Для импорта `export`-архива используется `docker import`, который создаёт образ из одного слоя.

### Перезапуск против удаления (демонстрация эфемерности)

```bash
docker run --name db -d redis
# → <id>
docker exec db sh -c 'echo mydata > /data/note.txt'

# Перезапуск сохраняет записываемый слой:
docker restart db
docker exec db cat /data/note.txt
# → mydata

# Удаление уничтожает записываемый слой безвозвратно:
docker rm -f db
docker run --name db2 -d redis
docker exec db2 cat /data/note.txt
# → cat: /data/note.txt: No such file or directory
```
Этот эксперимент наглядно показывает: чтобы данные пережили удаление контейнера, их нужно размещать в **[томах](../docker_volumes.md)**, а не в записываемом слое.

## Устранение неполадок

| Симптом | Вероятная причина | Диагностика и решение |
| :--- | :--- | :--- |
| Контейнер сразу переходит в `Exited` | Основной процесс завершился (нет долгоживущего процесса, ошибка в `CMD`/`ENTRYPOINT`) | `docker logs <id>` — см. причину падения; `docker inspect --format '{{.State.ExitCode}}' <id>` — код выхода. Запустите интерактивно для отладки: `docker run -it --rm <image> sh` |
| `no space left on device` | Заполнен диск из-за слоёв образов и/или записываемых слоёв контейнеров | `docker system df` — оцените размер; удалите неиспользуемое: `docker container prune`, `docker image prune -a`, `docker system prune` (см. «Рекомендации и очистка») |
| Изменения в контейнере «исчезли» | Контейнер был удалён (`docker rm`) и создан заново — записываемый слой потерян | Используйте том (`-v`) для персистентных данных; перезапуск (`restart`) сохраняет слой, удаление — нет |
| Медленная первая запись в файл из образа | Операция copy-up: весь файл копируется из нижнего слоя в верхний | Для «горячих» файлов (БД, логи) используйте тома; избегайте правки больших файлов внутри образа на лету |
| `docker commit` даёт слишком большой образ | Фиксируется весь записываемый слой + сохраняется ссылка на базу | Останавливайте контейнер перед `commit`; очищайте временные файлы; предпочитайте сборку через `Dockerfile` |
| Процесс внутри видит ресурсы хоста (CPU/RAM) | `/proc` не изолирован по умолчанию; приложение читает хостовые данные | Смотрите реальное потребление контейнера через `docker stats <id>`; задайте лимиты `--cpus`, `--memory` |
| `permission denied` при обращении к Docker socket | Пользователь не в группе `docker`, не root, не Rootless-сессия | `sudo usermod -aG docker $USER` (с перелогином) либо настройте Rootless; не запускайте команды от чужого пользователя |
| Высокий Reclaimable в `docker system df` (Containers) | Остановленные контейнеры с активными writable layers | `docker ps -a --filter status=exited` — удалите не нужные: `docker container prune` или `docker rm <id>` |
| Диск хоста заполнен, хотя `docker images` мало | Много остановленных контейнеров с большими writable layers | `docker system df -v` — проверьте строку Containers; `docker ps -a --filter status=exited --format "{{.ID}} {{.Size}}"` |
| Контейнеры после деплоя diverging по состоянию | Изменения в writable layer, не зафиксированные в образе | `docker diff <id>` — проверьте изменения; для детерминированности собирайте образ заново |

## Рекомендации и очистка

**Лучшие практики:**
- Разделяйте понятия: образ — неизменяемый артефакт доставки, контейнер — эфемерный экземпляр выполнения. Не храните важные данные в записываемом слое.
- Запускайте контейнеры с минимально необходимыми правами: `--read-only`, `--cap-drop=ALL`, добавляя только нужные capabilities через `--cap-add` (подробнее — в **[жёстком закаливании контейнеров](../../Docker_security/container_hardening.md)**).
- Выносите персистентные и «горячие» данные в **[тома](../docker_volumes.md)**, минуя CoW.
- Для воспроизводимых изменений образа используйте `Dockerfile`, а не `docker commit`.
- Фиксируйте образы по дайджесту (`image@sha256:...`), а не только по тегу, когда важна детерминированность.

**SRE-паттерны для инвентаря образов и контейнеров:**
- Устанавливайте лимиты на количество остановленных контейнеров на хосте (cron + `docker container prune --filter "until=72h"`).
- В CI/CD пайплайнах используйте `--rm` по умолчанию, чтобы writable layer удалялся автоматически после job.
- Для production фиксируйте образы по дайджесту (`image@sha256:...`), а не только по тегу — это исключает дрейф при повторном pull.
- Мониторьте соотношение `docker images` vs `docker ps -a`: рост stopped containers без соответствующего роста images указывает на проблемы с cleanup или сorbitory.
- На Kubernetes-узлах: `kubectl get pods -A` показывает Podы, но writable layer живёт на узле; при диагностике используйте `docker ps` на узле или `crictl`.

**Очистка окружения (revert / cleanup):**
```bash
# Удалить конкретный контейнер (и его записываемый слой):
docker rm -f my-app-cont
# → my-app-cont

# Удалить только остановленные контейнеры (освобождает их Writable Layer):
docker container prune
# → WARNING! This will remove all stopped containers.
# → Total reclaimed space: 12.3kB

# Удалить неиспользуемые образы (не привязанные к контейнерам):
docker image prune -a
# → Total reclaimed space: 600MB

# Полная очистка: контейнеры, сети, образы без ссылок и кэш сборки:
docker system prune -a --volumes
# (флаг --volumes также удаляет неиспользуемые тома — будьте осторожны с данными)
```
Любую очистку можно откатить только восстановлением из реестра/бэкапа тома — удалённые записываемые слои и образы безвозвратны.

## Особые случаи и ограничения

- **Copy-up целиком**: даже при изменении одного байта весь файл копируется из нижнего слоя в верхний. Для очень больших файлов (ГБ) первая запись может быть крайне медленной.
- **`--read-only` без `tmpfs`**: приложения, которым нужно писать во временные пути внутри корня, упадут. Явно монтируйте `tmpfs` для таких путей.
- **Непоследовательное состояние при `commit` из запущенного контейнера**: если процесс активно пишет, снимок может захватить «рваное» состояние ФС. Останавливайте контейнер перед фиксацией.
- **Совместное использование слоёв**: базовые слои образа реально не дублируются между контейнерами, но каждый контейнер получает собственный `upperdir`. Десятки тысяч контейнеров дадут много мелких `upperdir`, хотя база общая — место растёт линейно по числу изменений, не по числу контейнеров.
- **Мутабельность тега**: образ под тегом `latest` может измениться после повторного `pull`, хотя имя то же. Для воспроизводимости используйте дайджест.
- **`export` теряет слои и метаданные**: архив от `docker export` нельзя использовать как полноценный образ (нет истории, exposed ports, entrypoint). Импорт через `docker import` создаёт однослойный образ.
- **Rootless Docker**: `graph root` находится в домашнем каталоге пользователя (`~/.local/share/docker`), пути из `docker inspect` отличаются от штатных `/var/lib/docker`.
- **containerd image store (Docker 29.0+ fresh installs / containerd 2.3.x)**: образы хранятся нативно в containerd; поведение `docker save`, `docker image inspect` (`RepoDigests`) и интеграция с Kubernetes изменяются — см. «Примечания по версиям».
- **Остановка не равна удалению**: `Paused`/`Exited` контейнеры продолжают занимать место под `upperdir`; очищайте их явно (`container prune`).
- **Windows-контейнеры**: используют иную изоляцию (process/Hyper-V) и иные драйверы хранения; описанное здесь (overlay2, CoW) относится к Linux-контейнерам.

## Примечания по версиям

- **Docker Engine 24.0+**: концепции образа/контейнера, CoW, состояния жизненного цикла стабильны и применимы ко всем современным версиям. BuildKit (сборка образов) включён по умолчанию с 23.0+.
- **Docker Engine 29.x**: начиная с Docker 29.0 доступен `containerd-snapshotter` как альтернатива классическому graph driver; с Docker 29.1 включён нативный containerd image store по умолчанию. Это влияет на пути хранения образов (`/var/lib/containerd` вместо `/var/lib/docker`) и поведение `docker save`/`docker inspect` (`RepoDigests`). Для SRE: при миграции на containerd image store проверьте скрипты, парсящие `/var/lib/docker`, и мониторинг диска.
- **`docker system df`**: доступна начиная с Docker 1.13 (в современных версиях расширена выводом по Build Cache).
- **`--read-only` и `tmpfs`**: поддерживаются во всех актуальных версиях; `tmpfs` монтируется только в память (не пишется на диск).
- **containerd image store**: по умолчанию с Docker 29.1 (на базе containerd 2.0). Влияет на то, как образы физически хранятся и как работают `docker save`/`skopeo`/`buildx`; для большинства сценариев работа с образами и контейнерами прозрачна.
- **Rootless**: стабильный режим запуска Docker от обычного пользователя; пути хранилища и привязки портов (эпемерные диапазоны) отличаются от штатного режима.
- **Kubernetes:** `kubectl get pods` показывает состояния Pod/Container, но не отражает writable layer на узле; для деталей используйте `docker ps` на узле или `crictl`.
