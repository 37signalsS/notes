# Docker: Образ vs. Контейнер

Это самое фундаментальное различие в Docker. Понимание этой разницы — ключ ко всей дальнейшей работе.

## Определения

- **Образ (Image): Это "чертеж" или шаблон.**
  - **Аналогия:** Класс в объектно-ориентированном программировании или рецепт блюда.
  - **Сущность:** Пассивный, неизменяемый (read-only) пакет, содержащий все необходимое для запуска приложения: код, runtime, системные утилиты, библиотеки и настройки.

- **Контейнер (Container): Это "здание" или запущенный экземпляр.**
  - **Аналогия:** Объект (экземпляр класса) или торт, испеченный по рецепту.
  - **Сущность:** Активный, работающий процесс (или группа процессов), созданный из образа. У него есть свое состояние (работает, остановлен), жизненный цикл и собственный, изолированный слой файловой системы для записи.

> Проще говоря: **Образ — это то, что вы собираете (`build`). Контейнер — это то, что вы запускаете (`run`).**

## Основные концепции

### Build-time vs. Run-time

- **Образ существует на этапе сборки (Build-time).** Он создается командой `docker build` из `Dockerfile` и хранится в вашем локальном репозитории образов или в удаленном Docker Registry.
- **Контейнер существует на этапе выполнения (Run-time).** Он создается командой `docker run` из конкретного образа. Вы можете создать множество контейнеров из одного и того же образа, и каждый из них будет работать в своей изолированной среде.

### Сравнение по ключевым аспектам

| Аспект | Образ (Image) | Контейнер (Container) |
| :--- | :--- | :--- |
| **Состояние** | Неизменяемый (Read-Only) | Изменяемый (имеет Read-Write слой) |
| **Жизненный цикл** | `build`, `pull`, `push`, `tag`, `rmi` | `create`, `run`, `start`, `stop`, `rm` |
| **Идентификатор** | Дайджест (`sha256:...`), теги | Уникальный ID (64 символа), имя (явное или автоматически сгенерированное) |
| **Файловая система**| Набор неизменяемых слоев | Наследует слои образа + свой записываемый слой |
| **Назначение** | Шаблон для развертывания | Исполняемый экземпляр приложения |
| **Данные** | Не хранит изменяемые данные | Может хранить данные в своем слое (теряются при удалении) или в **[томах](../docker_volumes.md)** (персистентно) |

## Практические сценарии

### Жизненный цикл: от "чертежа" к "зданию" и его сносу

Давайте проследим весь путь на командах.

1. **Создаем "чертеж" (Образ):**
    Собираем `Dockerfile` в новый образ с тегом `my-app:1.0`.

    ```bash
    docker build -t my-app:1.0 .
    ```

2. **Проверяем наличие "чертежа":**
    Убедимся, что наш образ появился в локальном списке образов.

    ```bash
    docker images | grep my-app
    # REPOSITORY   TAG      IMAGE ID       CREATED          SIZE
    # my-app       1.0      a1b2c3d4e5f6   10 seconds ago   150MB
    ```

3. **Строим "здание" (Контейнер):**
    Запускаем контейнер из нашего образа. Теперь у нас есть работающий экземпляр.

    ```bash
    docker run -d --name my-running-app my-app:1.0
    ```

4. **Проверяем список "зданий":**
    Команда `ps` показывает только запущенные контейнеры.

    ```bash
    docker ps | grep my-running-app
    # CONTAINER ID   IMAGE        COMMAND                  CREATED         STATUS         PORTS     NAMES
    # 01a2b3c4d5e6   my-app:1.0   "npm start"              5 seconds ago   Up 4 seconds             my-running-app
    ```

5. **"Сносим здание", но "чертеж" остается:**
    Удалим контейнер.

    ```bash
    docker stop my-running-app
    docker rm my-running-app
    ```

    Процесс исчез (`docker ps` будет пуст), но образ остался нетронутым (`docker images` все еще покажет `my-app:1.0`).
