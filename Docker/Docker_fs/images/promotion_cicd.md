# Продвижение образов Docker в CI/CD

## Определения

- **Продвижение образа (Image Promotion)** — процесс квалификации одного и того же неизменяемого Docker-образ для использования в последующих, более критичных окружениях (например, перемещение из `Dev` в `Staging`, а затем в `Production`).
- **Build Once, Deploy Anywhere** (Собери один раз, развертывай везде) — фундаментальный принцип CI/CD, согласно которому артефакт (образ) должен быть собран только один раз в начале конвейера. Все дальнейшее движение по окружениям происходит через перетегирование (re-tagging) или копирование, но **никогда** через пересборку.

## Основные концепции

### Почему пересборка — это антипаттерн

Пересборка образа для каждого окружения нарушает гарантию идентичности артефакта. Факторы, которые могут привести к различиям между "идентичными" сборками:
- Обновление базового образа в публичном реестре (например, выход новой версии `alpine:latest`).
- Изменение версий пакетов, устанавливаемых через `apt`, `npm` или `pip`, если они не зафиксированы жестко.
- Различия в конфигурации сборочных узлов (CI Runners).

**Результат:** образ, успешно прошедший тесты в Staging, может отличаться от образа, собранного для Production, что ведет к трудноуловимым багам в эксплуатации.

### Стратегии продвижения

1.  **Продвижение внутри одного реестра (Re-tagging)**: Образ остается в том же репозитории, ему просто добавляются новые теги (например, `:staging` -> `:1.2.3`).
2.  **Продвижение между реестрами (Promotion by Copy)**: Образ копируется из "недоверенного" или временного реестра (Dev/Build) в "доверенный" (Production). Это лучший подход для обеспечения безопасности и изоляции окружений.

## Практические сценарии

### Сценарий 1: Продвижение через перетегирование (Стандартный CLI)

Этот метод требует наличия образа локально на CI-агенте.

```bash
# 1. Присваиваем новый тег существующему образу
docker tag my-app:build-42 my-app:staging

# 2. Пушим новый тег в реестр
docker push my-app:staging
```

### Сценарий 2: Продвижение без скачивания (Skopeo)

Для больших образов или распределенных систем неэффективно скачивать образ (`docker pull`) и загружать его снова (`docker push`) только для смены тега. Утилита **Skopeo** позволяет копировать образы напрямую между реестрами или внутри одного реестра без участия Docker-демона.

```bash
# Копирование образа из dev-registry в prod-registry напрямую
skopeo copy \
  docker://dev-registry.com/my-app:1.2.3-beta \
  docker://prod-registry.com/my-app:1.2.3
```
*Это значительно ускоряет пайплайны и экономит сетевой трафик.*

### Сценарий 3: Использование дайджестов для максимальной надежности

Теги — это изменяемые ссылки (mutable references). Для гарантии того, что в Production попадет именно та версия, которая прошла аудит, в манифестах развертывания (Kubernetes, Compose) рекомендуется использовать **дайджест (Digest/SHA256)**.

```bash
# Получение неизменяемого идентификатора образа
docker inspect --format='{{index .RepoDigests 0}}' my-app:staging
# → my-registry.com/my-app@sha256:71676f4...

# Сравнение дайджестов в разных окружениях гарантирует 100% бинарную идентичность.
```

## Дополнительная информация

- **Инструменты для продвижения**: 
    - **[Skopeo](https://github.com/containers/skopeo)**: Работает с реестрами напрямую.
    - **Crane (go-containerregistry)**: Быстрая утилита для манипуляций с образами и тегами.
- **Очистка (Cleanup)**: Продвижение через хеш-теги (`commit-sha`) порождает множество образов. Настройте политики очистки (Retention Policies) в вашем реестре (Harbor, Artifactory), чтобы автоматически удалять старые образы из Dev-окружения.
- **Реверс-инжиниринг**: Если Dockerfile утерян, можно попытаться восстановить его инструкции с помощью утилит вроде `dfimage`.
