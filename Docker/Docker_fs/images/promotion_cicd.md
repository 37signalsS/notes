# Продвижение образов Docker в CI/CD

## Определения

- **Продвижение образа (Image Promotion)** — процесс переноса и квалификации одного и того же неизменяемого артефакта через цепочку окружений (например, `Dev` → `Staging` → `Production`) после успешного прохождения проверок (тестов, сканирований).
- **Build Once, Deploy Anywhere** (Собери один раз, развертывай везде) — фундаментальный принцип CI/CD, согласно которому Docker-образ собирается только в начале конвейера. Дальнейшее движение осуществляется через смену метаданных (тегов) или физическое копирование манифестов, но никогда через повторный запуск `docker build`.
- **Quality Gates (Ворота качества)** — набор автоматизированных критериев (покрытие тестами, отсутствие критических уязвимостей CVE), которые должен выполнить образ для получения права на продвижение в следующее окружение.

## Основные концепции

### Проблема идемпотентности сборки

Повторная сборка образа для каждого окружения («сборка для прода») является критическим антипаттерном. Факторы риска при пересборке:
- **Дрейф зависимостей:** базовые образы (например, `node:18-alpine`) могут обновиться в публичном реестре между сборками.
- **Внешние пакеты:** `apt update`, `npm install` или `pip install` могут загрузить разные минорные версии пакетов, если они не зафиксированы жестко (lock-файлы).
- **Окружение сборки:** различия в версиях компиляторов или библиотек на разных CI-раннерах.

**Результат:** образ, протестированный в QA, может бинарно отличаться от образа в Production, что сводит на нет ценность предварительного тестирования.

### Модели продвижения

1.  **Внутри одного реестра (Promotion by Tagging):**
    - Образ остается в том же репозитории.
    - Продвижение осуществляется добавлением нового тега (например, `:sha-abcdef` → `:staging` → `:1.2.3`).
    - Подходит для небольших команд с единым доверенным реестром.

2.  **Между разными реестрами (Promotion by Copy):**
    - Копирование из «недоверенного» реестра (Build/Dev) в «доверенный» (Production).
    - Обеспечивает строгую изоляцию: доступ к Production-реестру имеют только проверенные артефакты.
    - Реализуется инструментами `skopeo` или `crane`.

3.  **Использование неизменяемых дайджестов (Digest-based):**
    - Использование `sha256` вместо тегов в манифестах Kubernetes/Compose.
    - Гарантирует 100% бинарную идентичность независимо от того, был ли перезаписан тег в реестре.

## Практические сценарии

### Сценарий 1: Продвижение через стандартный Docker CLI

Метод требует скачивания всех слоев на CI-агент (`docker pull`), что замедляет пайплайн.

```bash
# 1. Загрузка проверенного образа
docker pull my-reg.com/app:sha-abcdef

# 2. Добавление целевого тега
docker tag my-reg.com/app:sha-abcdef my-reg.com/app:staging

# 3. Пуш в реестр
docker push my-reg.com/app:staging
```

### Сценарий 2: Продвижение без Docker-демона (Skopeo)

**Skopeo** работает напрямую с реестрами. Это позволяет копировать образы между реестрами (например, из GitLab Registry в AWS ECR) без необходимости скачивать слои локально.

```bash
# Прямое копирование между реестрами
skopeo copy \
  --src-creds $DEV_USER:$DEV_PASS \
  --dest-creds $PROD_USER:$PROD_PASS \
  docker://registry-dev.com/app:v1.2-beta \
  docker://registry-prod.com/app:v1.2
```

### Сценарий 3: Работа с Multi-arch образами (Google Crane)

**Crane** — современный инструмент от Google для манипуляций с образами. Он эффективнее Skopeo при работе с индексами манифестов (multi-arch), так как копирует только JSON манифеста, если слои уже есть в целевом реестре.

```bash
# Быстрое перетегирование multi-arch образа внутри реестра
crane tag my-reg.com/app:build-42 staging

# Копирование по дайджесту (самый надежный способ)
crane copy \
  my-reg.com/app@sha256:71676f4... \
  my-reg.com/app:production
```

### Сценарий 4: Продвижение в GitOps (ArgoCD / Flux)

В GitOps-модели продвижение образа часто означает обновление тега в Git-репозитории с конфигурацией (Helm или Kustomize).

1. **Автоматический Image Updater:** Инструмент (например, ArgoCD Image Updater) отслеживает реестр и сам коммитит новый тег в Git при появлении новой версии, подходящей под маску (SemVer).
2. **Ручное продвижение через CI:**
```bash
# В конце CI-пайплайна обновляем версию в Helm chart
sed -i "s/tag: .*/tag: v1.2.3/" ./deploy/values.yaml
git add ./deploy/values.yaml && git commit -m "Bump version to v1.2.3" && git push
```

## Дополнительная информация

### Безопасность и проверка подписи

Перед продвижением образа в Production рекомендуется выполнять:
1. **Vulnerability Scanning:** Проверка на критические CVE (Trivy, Grype).
2. **Image Signing (Cosign):** Подпись образа после прохождения Quality Gates. В Prod-кластере контроллер (например, Kyverno) запретит запуск образа без подписи "QA-Approved".

```bash
# Подпись образа перед продвижением
cosign sign --key cosign.key my-reg.com/app:staging
```

### Политики очистки (Retention Policies)

Продвижение через уникальные теги (например, по SHA коммита) создает тысячи артефактов. Настройте политики в реестре (Harbor, Artifactory):
- **Keep last N:** Оставлять только 10 последних тегов для каждой ветки.
- **Delete untagged:** Автоматически удалять слои, на которые больше не ссылаются теги.
