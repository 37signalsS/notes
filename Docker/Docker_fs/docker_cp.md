# Docker: Копирование файлов между хостом и контейнером (docker cp)

**Актуально для:** Docker 24.x–29.x

## Определения

- **docker cp** — команда копирования файлов и директорий между хостом и контейнером в обе стороны, а также между контейнерами через потоковую передачу tar-архива. Поведение аналогично `cp -a`: директории копируются рекурсивно с сохранением прав, если это возможно.
- **Представление ФС контейнера** — то, с чем работает демон при копировании: корневая ФС контейнера (образные слои + записываемый слой) **плюс** примонтированные тома (volumes) и bind-маунты, указанные при создании контейнера. tmpfs, `/proc`, `/sys`, `/dev` и маунты, созданные внутри контейнера в рантайме, в представление **не входят**. В Docker ≤23 тома в представление не входили — поведение изменилось в 24.0.
- **Archive mode (`-a`)** — режим копирования с сохранением uid/gid источника. Без `-a` владельцы не сохраняются: файлы в контейнере создаются с uid/gid root, на хосте — с uid/gid пользователя, запустившего `docker cp`.
- **Потоковый режим (`-`)** — использование `-` в качестве `SRC_PATH` или `DEST_PATH` для передачи tar-архива через STDIN/STDOUT. Единственный способ передать данные между двумя контейнерами: прямое копирование контейнер↔контейнер CLI отклоняет с ошибкой.

## Предварительные требования

- **Docker Engine** 24.x–29.x. Проверка: `docker version --format '{{.Server.Version}}'`.
- **Доступ к Docker socket**: `/var/run/docker.sock` или `DOCKER_HOST`. Без прав — `permission denied while trying to connect to the Docker daemon socket`.
- **Контейнер**: `docker cp` работает как с работающими, так и с **остановленными** контейнерами — это позволяет извлекать файлы из «упавшего» контейнера без его запуска.
- **`tar` внутри контейнера** — только для обхода ограничений (tmpfs, `/proc`, `/sys`, `/dev`); сам `docker cp` tar на хосте не требует.

## Базовые концепции

### 1. Модель работы

```
[Хост] <-- docker cp --> [Представление ФС: rootfs (слои) + volumes + bind-маунты]
```

- Демон монтирует rootfs контейнера и bind-маунтит его тома в приватный mount namespace, затем работает с этим представлением. Поэтому пути внутри примонтированных томов копируются напрямую — промежуточный контейнер не нужен.
- Символические ссылки копируются **как ссылки** (не разыменовываются). Флаг `-L, --follow-link` заставляет следовать симлинкам в `SRC_PATH`. Симлинк в `DEST_PATH` разыменовывается всегда; симлинк на директорию в `SRC_PATH` с `/` или `/.` на конце тоже разыменовывается.
- Копирование **в** контейнер с `--read-only` rootfs невозможно для путей вне томов; в путь внутри read-write тома — возможно.

### 2. Флаги

| Флаг | Описание |
| :--- | :--- |
| `-a, --archive` | Archive mode: копирует всю информацию о uid/gid |
| `-L, --follow-link` | Всегда следовать симлинку в `SRC_PATH` |
| `-q, --quiet` | Подавить вывод прогресса. Прогресс автоматически подавляется, если нет терминала |

### 3. Семантика путей

- Пути контейнера отсчитываются от `/`; ведущий слеш опционален: `ctr:/tmp/foo` и `ctr:tmp/foo` идентичны.
- Локальные пути — абсолютные или относительно текущей директории, где запущен `docker cp`.
- Локальный путь, содержащий `:`, нужно задавать явно: `./file:name.txt` или `/path/to/file:name.txt` (иначе `:` трактуется как разделитель контейнера).
- `docker cp` **не создаёт** родительские директории для `DEST_PATH`: последний компонент создаётся по правилам ниже, но родитель должен существовать.
- Правила для `SRC_PATH` (файл/директория) × `DEST_PATH`:
  - файл → несуществующий путь: создаётся файл; несуществующий путь с `/` на конце: ошибка (`the destination directory must exist`); существующий файл: перезаписывается; существующая директория: файл копируется внутрь с basename из `SRC_PATH`.
  - директория → несуществующий путь: создаётся директория, в неё копируется **содержимое** источника; существующий файл: ошибка (`cannot copy a directory to a file`); существующая директория: источник копируется внутрь, кроме случая `SRC_PATH` с `/.` на конце — тогда копируется содержимое.

### 4. Владельцы файлов

- Без `-a`: uid/gid назначения (в контейнере — `0:0`, на хосте — invoking user).
- С `-a`: uid/gid источника.

### 5. Потоковый режим и контейнер ↔ контейнер

Прямого копирования между контейнерами нет — CLI возвращает `copying between containers is not supported`. Решение — поток через хост:

```
[Контейнер A] --docker cp--> [STDOUT хоста] --docker cp--> [Контейнер B]
```

- `-` как `SRC_PATH` — tar-архив в STDOUT; `-` как `DEST_PATH` — tar-архив из STDIN, при этом `DEST_PATH` в контейнере должен быть директорией.

### 6. Вывод прогресса

- При подключённом терминале (stderr) — строка `Copying to container - <размер>` / `Copying from container - <размер>` с обновлением каждые 75 мс и итог `Successfully copied <размер> to <назначение>`.
- Вывод идёт в **stderr**; в скриптах (нет терминала) подавляется автоматически, `-q` гарантирует подавление.

## Практические сценарии

### Сценарий 1: Хост → контейнер и обратно

```bash
# Файл на хост → контейнер
docker cp ./config.json my-container:/app/config.json
# → (файл скопирован; при терминале в stderr: Successfully copied 1.02kB to my-container:/app/config.json)

# Директория на хост → контейнер (рекурсивно)
docker cp ./conf.d my-container:/etc/nginx/
# → (директория conf.d скопирована в /etc/nginx/conf.d)

# Файл из контейнер → хост
docker cp my-container:/app/logs/app.log ./logs/
# → (файл скопирован в ./logs/app.log)

# Директория из контейнер → хост
docker cp my-container:/var/log ./container-logs/
# → (директория log скопирована в ./container-logs/log)
```

### Сценарий 2: Извлечение данных из остановленного контейнера

```bash
# Контейнер упал
docker ps -a
# → my-container   Exited (1)  2 minutes ago

# Копирование лога из остановленного контейнера
docker cp my-container:/var/log/app/error.log ./debug-logs/
# → (файл скопирован)

# Копирование всей директории для форензики
docker cp my-container:/app ./forensics-my-container/
```

### Сценарий 3: Контейнер → контейнер через поток

```bash
# Передача файла между контейнерами через STDIN/STDOUT
docker cp container-a:/data/file.tar - | docker cp - container-b:/data/
# → (файл передан; tar-архив streamed через хост)

# То же для директории
docker cp container-a:/data/ - | docker cp - container-b:/backup/

# Поток в STDOUT можно обрабатывать без промежуточного файла
docker cp my-container:/var/log/app.log - | tar x -O | grep "ERROR"
# → (строки с ERROR из лога; tar читает архив из STDIN)
```

### Сценарий 4: Копирование данных из тома

Том, примонтированный в контейнер, виден `docker cp` напрямую — промежуточный контейнер не нужен:

```bash
# Том my-data примонтирован в my-container:/data
docker cp my-container:/data/export.csv ./exports/
# → (файл скопирован из тома)

# Копирование в том (том должен быть read-write)
docker cp ./import.csv my-container:/data/import.csv
```

Если том не примонтирован ни в одном контейнере — монтируем его в helper:

```bash
# 1. Запуск промежуточного контейнера с примонтированным томом
docker run --rm -d --name cp-helper \
  --mount type=volume,source=my-data,target=/data \
  alpine sleep 300

# 2. Копирование из тома на хост
docker cp cp-helper:/data/export.csv ./exports/

# 3. Остановка helper'а
docker stop cp-helper
```

Копирование в read-only том невозможно: `mounted volume is marked read-only`.

### Сценарий 5: Сохранение владельцев файлов (`-a`)

```bash
# Копирование с сохранением uid/gid
docker cp -a my-container:/etc/passwd ./passwd-backup

# Проверка владельца
ls -ln ./passwd-backup
# → -rw-r--r-- 1 0 0 1520 Aug 22 10:00 passwd-backup
```

### Сценарий 6: Инъекция файла в `--read-only` контейнер через RW-том

```bash
# Контейнер с --read-only rootfs и read-write томом /config
docker cp ./app.conf read-only-container:/config/app.conf
# → (файл скопирован в том; проверка на запись не блокирует пути внутри RW-тома)
```

### Сценарий 7: tmpfs, /proc, /sys, /dev — обход через docker exec + tar

`docker cp` не работает с tmpfs и виртуальными ФС. Обход — tar внутри контейнера:

```bash
# Копирование из tmpfs-контейнера на хост
docker exec my-container tar Ccf /tmp - myfile | tar Cxf ./host-dir -
# → (файл myfile из /tmp контейнера скопирован на хост)

# Копирование с хоста в tmpfs-контейнер
tar Ccf ./host-dir - myfile | docker exec -i my-container tar Cxf /tmp -
# → (файл myfile записан в /tmp контейнера)
```

### Сценарий 8: Скриптинг с `-q`

```bash
# Гарантированно тихое копирование в CI/скриптах
docker cp -q ./config.json my-container:/app/config.json
# → (stdout и stderr пусты; код возврата 0 при успехе)
```

## Устранение неполадок

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| **`Could not find the file <path> in container <id>`** | Путь не существует (или родитель `DEST_PATH` не создан) | Проверьте путь через `docker exec <ctr> ls <path>`; `docker cp` не создаёт родительские директории |
| **`container rootfs is marked read-only`** при копировании в контейнер | Контейнер запущен с `--read-only`, путь вне тома | Копируйте в примонтированный read-write том или снимите `--read-only` |
| **`mounted volume is marked read-only`** | Том примонтирован с `:ro` | Копируйте в read-write том или перемонтируйте |
| **`permission denied`** | Нет прав на чтение/запись внутри контейнера | Выполните `docker exec` от нужного пользователя; проверьте права |
| **`copying between containers is not supported`** | Оба аргумента — контейнеры | Поток через хост: `docker cp a:/p - \| docker cp - b:/p` |
| **`must specify at least one container source`** | Оба аргумента — локальные пути | Один из аргументов должен быть `CONTAINER:PATH` |
| **`destination "<ctr>:<path>" must be a directory`** | Поток из STDIN (`-` как источник), а назначение — не директория | Укажите директорию как `DEST_PATH` |
| **`the destination directory must exist`** | `DEST_PATH` с `/` на конце, но не существует | Создайте директорию или уберите `/` |
| **Симлинк ведёт в никуда** | Симлинки копируются как ссылки | Используйте `-L` для разыменования в `SRC_PATH` |
| **Файл не виден в контейнере после копирования** | Копирование в путь, перекрытый томом, или в tmpfs | Проверьте `docker inspect <ctr> .Mounts`; tmpfs не виден для `docker cp` — используйте сценарий 7 |
| **Копирование большого файла медленное** | `docker cp` передаёт tar без сжатия | Для больших данных используйте тома или `docker export`/`import` |

## Валидация результатов

```bash
# Проверка, что файл появился в контейнере
docker exec my-container ls -l /app/config.json
# → -rw-r--r-- 1 root root 1024 Aug 22 10:00 /app/config.json

# Проверка контрольной суммы (хост ↔ контейнер)
sha256sum ./config.json
docker exec my-container sha256sum /app/config.json
# → одинаковые хеши = копия корректна

# Проверка владельцев при -a
docker exec my-container stat -c '%u:%g' /etc/passwd
# → 0:0
```

## Граничные случаи

### Остановленные контейнеры

`docker cp` работает с остановленными контейнерами — единственный способ извлечь данные из контейнера, который не запускается (например, из-за повреждённого `ENTRYPOINT`).

### Контейнеры с `--read-only`

Корневая ФС смонтирована только для чтения. Копирование внутрь невозможно для путей вне томов; пути внутри read-write тома доступны для записи (сценарий 6). Чтение из `--read-only` контейнера работает всегда.

### tmpfs, /proc, /sys, /dev и маунты, созданные в рантайме

Не входят в представление ФС, с которым работает демон: копирование в tmpfs-путь запишет данные в приватный tmpfs представления (невидим контейнеру), чтение из tmpfs вернёт пустое содержимое. Для этих путей — `docker exec` + `tar` (сценарий 7). То же касается маунтов, созданных внутри контейнера после запуска (например, через `docker exec ... mount`).

### Большие объёмы данных

`docker cp` передаёт tar-архив без сжатия. Для передачи больших объёмов (> 1 ГБ) предпочтительнее тома или `docker export`/`docker import` (tar всей ФС контейнера).

### Имена файлов с пробелами, спецсимволами и двоеточием

Пути с пробелами экранируйте как обычно в shell: `docker cp "my container:/path/with space/file.txt" ./`. Локальный путь с `:` задавайте явно: `./file:name.txt`.

### Windows-контейнеры

Пути задаются как `c:/windows/system32/...`; `docker cp` работает и с Windows-контейнерами (проверка типов файлов и симлинков различается по платформе).

## Лучшие практики

- **`docker cp` — инструмент ad-hoc и форензики**, не механизм доставки конфигов в production: конфиги вкладывайте в образ или монтируйте томами. Копирование в работающий контейнер не отслеживается оркестратором и теряется при пересоздании.
- **Проверяйте контрольные суммы** (`sha256sum`) при переносе критичных данных — `docker cp` не проверяет целостность.
- **Используйте `-a`**, когда важны владельцы (например, `/etc/passwd`, ключи): без `-a` uid/gid заменяются на uid/gid назначения.
- **Не копируйте файлы из контейнеров с непроверенным происхождением**: `docker cp` выполняется с правами root на хосте (история: CVE-2019-14271 — см. **[Побеги и CVE контейнеров](../Docker_security/container_escape_cves.md)**).
- **Для больших данных — тома**, а не `docker cp`: без сжатия и прогресса в неинтерактивном режиме.
- **Убирайте helper-контейнеры** после копирования из тома (`docker rm -f cp-helper` или `--rm`).

### Частые ошибки

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| Копирование в путь, перекрытый томом | Том монтируется поверх директории | Копируйте в том или в другую директорию |
| Потеря владельцев при копировании | Забыт флаг `-a` | Используйте `docker cp -a` |
| Ожидание, что `docker cp` видит tmpfs | tmpfs приватен для представления демона | `docker exec` + `tar` (сценарий 7) |

| Ожидание создания родительских директорий | `docker cp` их не создаёт | Создайте родителя через `docker exec mkdir -p` |
