# Docker: Анализ изменений файловой системы контейнера (docker diff)

**Актуально для:** Docker 24.x–29.x

## Определения

- **docker diff** — команда, показывающая изменения файлов и директорий в файловой системе контейнера относительно базового образа (состояния на момент создания контейнера). Выводит список путей с префиксами `A` (added), `C` (changed), `D` (deleted).
- **A/C/D** — типы изменений: **A**dded (файл/директория созданы), **C**hanged (содержимое или метаданные изменены), **D**eleted (файл/директория удалены).
- **Writable layer** — записываемый слой контейнера (`upperdir` в OverlayFS / snapshot в containerd snapshotter), в котором фиксируются все изменения; именно его и анализирует `docker diff`.
- **Whiteout** — служебный файл (`.wh.<имя>`) в OverlayFS-слое, маскирующий файл из нижележащего слоя; именно так в слое представляются удаления.

## Предварительные требования

- **Docker Engine** 24.x–29.x.
- **Доступ к Docker socket**: `/var/run/docker.sock` или `DOCKER_HOST`.
- **Контейнер**: `docker diff` работает с работающими, приостановленными (paused) и остановленными контейнерами. Ограничение: для Windows-контейнеров diff работающего контейнера не поддерживается — только остановленного (демон возвращает `Windows does not support diff of a running container`).

## Базовые концепции

### 1. Модель работы

```
[Образ (lowerdir)] + [Writable layer (upperdir)] → docker diff показывает изменения в upperdir
```

- `docker diff` анализирует **только записываемый слой** контейнера — итоговое состояние файловой системы относительно базового образа, а не историю операций.
- Вычисление выполняется **на стороне демона**: CLI отправляет запрос `GET /containers/{id}/changes`, демон обходит rw layer (`archive.Changes` в moby) и для каждого файла проверяет его наличие в родительских слоях образа: файл есть в слое образа → `C`, отсутствует → `A`, whiteout-файл → `D`.
- Вывод содержит **пути**, но не содержимое файлов, не размеры и не временные метки.
- Порядок вывода **не гарантирован** — это порядок обхода файловой системы, не сортировка.
- Команда **не** показывает изменения в томах (volumes), bind mount'ах и tmpfs — только файловую систему контейнера (см. «Граничные случаи»).
- Diff **не атомарен**: если контейнер продолжает писать во время выполнения diff, вывод может отражать промежуточное состояние (оговорка в исходниках moby, `pkg/archive/changes.go`).

### 2. Формат вывода

| Префикс | Значение | Пример |
| :--- | :--- | :--- |
| `A` | Добавлен (файл или директория созданы) | `A /app/cache` |
| `C` | Изменён (содержимое или метаданные) | `C /etc/nginx/nginx.conf` |
| `D` | Удалён (файл существовал в базовом образе) | `D /tmp/old.log` |

- Родительские директории добавленных/изменённых/удалённых файлов также фиксируются как `C`: при создании `/opt/data/f` в выводе появятся `C /opt`, `A /opt/data`, `A /opt/data/f`.
- Изменения метаданных (chmod, chown, mtime) отражаются как `C`.
- Симлинки фиксируются как `A`.

### 3. Семантика итогового состояния

`docker diff` сравнивает **текущее** состояние с базовым образом, а не отслеживает историю операций:

- Файл создан → `A`.
- Файл из образа изменён → `C`.
- Файл из образа удалён → `D`.
- Файл создан и затем удалён → **записи нет вообще** (чистый эффект относительно образа нулевой); `D` появляется только для файлов, существовавших в базовом образе.

## Практические сценарии

### Использование

```
docker diff CONTAINER
```

- **Алиасы**: `docker container diff`, `docker diff`.
- **Аргумент**: полный ID, короткий (уникальный префикс) ID или имя контейнера.
- **Флаги**: отсутствуют — команда не принимает опций (`docker diff --help` показывает только usage и алиасы).
- **Коды возврата**: `0` — успех; `1` — ошибка (например, `docker: 'docker diff' requires 1 argument` при отсутствии аргумента; `Error response from daemon: No such container: <name>` для неизвестного контейнера).

### Сценарий 1: Базовая диагностика — что написало приложение

```bash
# Запуск контейнера
docker run -d --name web nginx:alpine

# Изменения после старта и активности
docker exec web sh -c "echo hi > /tmp/new.txt; mkdir -p /opt/data; echo x > /opt/data/f"
docker diff web
# → C /run
# → A /run/nginx.pid
# → C /opt
# → A /opt/data
# → A /opt/data/f
# → C /tmp
# → A /tmp/new.txt
# → C /var
# → C /var/cache
# → C /var/cache/nginx
# → A /var/cache/nginx/proxy_temp
# → A /var/cache/nginx/scgi_temp
# → A /var/cache/nginx/uwsgi_temp
# → A /var/cache/nginx/client_temp
# → A /var/cache/nginx/fastcgi_temp
# → C /etc
# → C /etc/nginx
# → C /etc/nginx/conf.d
# → C /etc/nginx/conf.d/default.conf

# Фильтрация по типу изменения
docker diff web | grep '^A'
```

Вывод выше — реальный вывод Docker Engine 29.8.2 (overlayfs). Обратите внимание: `/etc/hostname`, `/etc/hosts`, `/etc/resolv.conf` и `/dev` в выводе **не появляются** — это bind mount'ы и tmpfs, а не rw layer. Пример в официальной документации показывает устаревший вывод с записями вида `C /dev`, `C /dev/console`, характерный для старых версий Docker; на текущих версиях таких записей нет.

### Сценарий 2: Форензика упавшего контейнера

```bash
# Контейнер упал
docker ps -a
# → crashy   Exited (137)  5 minutes ago

# Что изменилось до падения
docker diff crashy
# → A /tmp/core.dump
# → C /var/log/app/error.log
# → A /app/heapdump.bin

# Извлечение изменённых файлов для анализа
docker cp crashy:/tmp/core.dump ./forensics/
```

### Сценарий 3: Дрейф конфигурации (configuration drift)

```bash
# Сравнение текущего состояния с ожидаемым
docker diff config-server | grep -E '^C /etc'
# → C /etc/nginx/nginx.conf

# Проверка, что критичные файлы не менялись
docker diff prod-app | grep -E '^C /usr' || echo "OK: /usr не изменялся"
# → OK: /usr не изменялся
```

### Сценарий 4: Поиск утечек диска — куда пишутся данные

```bash
# Контейнер растёт по диску
docker diff log-heavy | awk '{print $2}' | cut -d/ -f2 | sort | uniq -c | sort -rn
# →   120 var
# →    45 tmp
# →     3 app
# → вывод показывает, что приложение пишет в /var и /tmp
```

### Сценарий 5: Аудит безопасности

```bash
# Проверка неожиданных изменений в системных директориях
docker diff payment-service | grep -E '^A /(etc|usr|root|home)'
# → A /root/.ssh
# → A /etc/cron.d/backdoor  ← тревожный сигнал
```

### Сценарий 6: Программный доступ через Engine API

```bash
# Тот же результат через Engine API (JSON)
curl --unix-socket /var/run/docker.sock \
  http://localhost/v1.43/containers/web/changes
# → [{"Path":"/run","Kind":0},{"Path":"/run/nginx.pid","Kind":1},{"Path":"/opt","Kind":0}, ...]
```

| `Kind` в JSON | Константа moby (`archive.ChangeType`) | Префикс CLI |
| :--- | :--- | :--- |
| `0` | `ChangeModify` | `C` |
| `1` | `ChangeAdd` | `A` |
| `2` | `ChangeDelete` | `D` |

JSON-вывод удобен для автоматизации (скрипты, аудит): он не зависит от форматирования CLI и явно кодирует тип изменения.

## Устранение неполадок

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| **Пустой вывод** | Контейнер не изменял ФС; все изменения в томах/tmpfs; контейнер запущен с `--read-only` | Проверьте `docker inspect <ctr> .Mounts`; изменения в volumes/tmpfs не видны |
| **Огромный вывод** | Приложение пишет много временных файлов; родительские директории дублируются как `C` | Фильтруйте по директории; выносите логи/кэш в тома |
| **`D` для файла, который «существует»** | Whiteout в OverlayFS скрывает файл из нижнего слоя | Файл удалён в writable layer; в образе он остался |
| **Нет записи для созданного и удалённого файла** | diff показывает итоговое состояние относительно образа, а не историю | Это нормальное поведение; промежуточные состояния не отслеживаются |
| **Нет информации о времени/размере** | `docker diff` показывает только пути | Используйте `docker exec <ctr> stat <path>` для деталей |
| **Медленная работа** | Обход rw layer с проверкой каждого файла по слоям образа | Ожидаемо для контейнеров с большим числом файлов; не запускайте в горячем цикле мониторинга |
| **`Windows does not support diff of a running container`** | Ограничение Windows-контейнеров | Остановите контейнер перед diff |

## Валидация результатов

```bash
# Создание файла в контейнере
docker exec web sh -c "echo test > /tmp/probe.txt"

# Проверка через diff
docker diff web | grep probe
# → A /tmp/probe.txt

# Удаление созданного файла — записи нет (файла не было в образе)
docker exec web rm /tmp/probe.txt
docker diff web | grep probe
# → (пусто: итоговый эффект относительно образа нулевой)

# Удаление файла из образа — уже показывает D
docker exec web rm /etc/alpine-release
docker diff web | grep alpine-release
# → D /etc/alpine-release

# Очистка
docker rm -f web
```

## Граничные случаи

### Контейнеры с `--read-only`

При `--read-only` запись в rootfs невозможна, поэтому `docker diff` показывает пустой вывод. Записи в tmpfs-монтах (например, `--tmpfs /tmp:rw`) в выводе не появляются — tmpfs не является частью rw layer. Исключение: если точка монтирования tmpfs или volume указана в пути, которого нет в образе, сама точка монтирования создаётся в rw layer при создании контейнера и появляется как `A` (проверено: `--tmpfs /mnt/scratch` → `C /mnt`, `A /mnt/scratch`).

### Изменения в томах и bind mount'ах не видны

`docker diff` оперирует только ФС контейнера. Данные, записанные в named volume или bind mount, в выводе не появляются — используйте `du`/`find` внутри контейнера или на хосте для анализа томов. Точка монтирования тома появляется как `A` только если путь не существовал в образе; содержимое тома никогда не показывается (проверено: volume в `/var` → пустой вывод, volume в новом `/data` → `A /data`).

### Служебные файлы демона не видны

`/etc/hosts`, `/etc/hostname`, `/etc/resolv.conf` — bind mount'ы с хоста, управляемые демоном; изменения в них не попадают в rw layer и не показываются. `/dev`, `/proc`, `/sys` — tmpfs и virtual FS, тоже не показываются.

### Многослойные изменения

Если файл создан, изменён и удалён — в `docker diff` записи не будет вообще: diff фиксирует итоговое состояние относительно базового образа, промежуточные состояния не отслеживаются. `D` появляется только для файлов, существовавших в базовом образе.

### Порядок вывода и согласованность

Вывод не отсортирован (порядок обхода файловой системы). Diff не атомарен: при активной записи в контейнере во время выполнения команды вывод может отражать промежуточное состояние.

## Лучшие практики

- **Перед `docker commit`** запускайте `docker diff` для аудита того, что попадёт в образ (см. [docker_commit.md](./docker_commit.md)).
- **Для извлечения изменённых файлов** комбинируйте с `docker cp` (см. [docker_cp.md](./docker_cp.md)): `docker diff` показывает пути, `docker cp` копирует содержимое.
- **Не используйте для мониторинга томов** — данные в volumes/tmpfs не видны; для этого `du -sh` внутри контейнера или `docker system df`.
- **В скриптах** используйте API (`/containers/{id}/changes`) вместо парсинга CLI-вывода — стабильный JSON с явным `Kind`.
- **Ограничивайте вывод** фильтрами (`grep '^A /var'`) на контейнерах с большим числом изменений.
- **Очищайте тестовые контейнеры** после диагностики: `docker rm -f <ctr>`.
