# OverlayFS

**OverlayFS** — это современная **объединяющая файловая система** (union filesystem), которую Docker использует по умолчанию. Она позволяет "накладывать" одну файловую систему поверх другой, создавая единое представление из нескольких слоев.

Представьте, что вы накладываете друг на друга прозрачные пленки:

- **Нижние слои (`lowerdir`)**: Это базовые пленки с исходным изображением (например, ОС Ubuntu). Они доступны **только для чтения**.
- **Верхний слой (`upperdir`)**: Это прозрачная пленка поверх остальных, на которой вы можете рисовать. Все изменения (создание, изменение, удаление файлов) записываются именно сюда.
- **Объединенное представление (`merged`)**: То, что вы видите в итоге — объединенное изображение со всех пленок. Это и есть файловая система внутри вашего контейнера.

```
+---------------------------------+
| Merged View (ФС Контейнера)     | <--- То, что вы видите
+---------------------------------+
               ^
 (запись идет в upperdir)
               |
+---------------------------------+
| Upperdir (Слой контейнера R/W)  | <--- Все изменения здесь
+---------------------------------+
| Lowerdir 1 (Слой образа RO)     | <--- Неизменяемые слои
+---------------------------------+
| Lowerdir 2 (Слой образа RO)     |
+---------------------------------+
```

## Принцип Copy-on-Write (CoW)

В основе эффективности OverlayFS и, как следствие, всего Docker, лежит стратегия **"Копирование при записи" (Copy-on-Write, CoW)**. Этот механизм определяет, как система обращается с файлами при их чтении и изменении.

*   **Операция ЧТЕНИЯ (Read):**
    *   Когда процесс читает файл, который существует только в неизменяемых(read only слои выбранного базового образа нижних слоях (`lowerdir`), он получает к нему прямой доступ. Это происходит мгновенно, без каких-либо накладных расходов на копирование.

*   **Операция ЗАПИСИ или ИЗМЕНЕНИЯ (Write/Modify):**
    1.  Когда процесс впервые пытается изменить файл из `lowerdir`, ядро перехватывает эту операцию.
    2.  Происходит **"copy up"**: файл копируется из `lowerdir` в верхний, записываемый слой контейнера (`upperdir`).
    3.  Изменения вносятся в эту новую копию в `upperdir`. Оригинальный файл в `lowerdir` остается нетронутым.
    4.  Все последующие операции чтения этого файла будут обращаться уже к измененной копии в `upperdir`, так как она "перекрывает" собой оригинал.

*   **Операция УДАЛЕНИЯ (Delete):**
    1.  Когда процесс удаляет файл, который существует в `lowerdir`, он не может быть физически стерт (так как слои образа read-only).
    2.  Вместо этого в `upperdir` создается специальный маркер — **"whiteout"** файл. Этот маркер указывает, что файл удален, и скрывает его из итогового объединенного представления (`merged`).

Именно этот механизм обеспечивает **эффективное использование диска** (слои переиспользуются) и **высокую скорость запуска контейнеров** (копируются только те данные, которые изменяются).

## Как OverlayFS используется в Docker

- **[Слои образа](./docker_images.md) → `lowerdir`**: Все слои Docker-образа (из `Dockerfile`) монтируются как нижние слои (`lowerdir`), доступные **только для чтения**.
- **Слой контейнера → `upperdir`**: При запуске контейнера (`docker run`) Docker создает для него новый пустой верхний слой (`upperdir`), куда будут записываться все изменения.
- **Файловая система контейнера → `merged`**: То, что видит процесс внутри контейнера, — это и есть объединенное представление (`merged`), которое прозрачно объединяет неизменяемый образ и записываемый слой контейнера.

**Где это хранится?**

Docker хранит все слои и директории в `/var/lib/docker/overlay2/`. Каждому слою и контейнеру соответствует своя директория.

## Преимущества для Docker

1.  **Экономия места на диске**: Если у вас есть 10 контейнеров, запущенных из одного образа, его [слои](./docker_images.md) хранятся на диске **в одном экземпляре**. Записываются только уникальные изменения для каждого контейнера.

2.  **Мгновенный запуск контейнеров**: Docker не нужно копировать всю файловую систему. Он просто создает новый пустой `upperdir`, что занимает миллисекунды. Подробнее об этом в [компонентах Docker](../docker_overview.md).

3.  **Гарантия неизменяемости (Immutability)**: Механизм CoW гарантирует, что базовые образы никогда не изменяются, что делает окружение предсказуемым и стабильным.

## Требования, история и сравнение драйверов

### Требования к ядру и файловой системе

Драйверы `overlay` и `overlay2` работают поверх файловой системы `OverlayFS`.

*   **Основное ядро Linux:**

    *   `overlay`: Поддержка появилась в ядре **3.18**.
    *   `overlay2`: Рекомендуется ядро **4.0** и новее.

*   **CentOS / RHEL:**

    *   Red Hat **бэкпортировала** функциональность `OverlayFS` в свое ядро версии `3.10`.
    *   Поддержка `overlay2` доступна начиная с **CentOS 7.4** (ядро `3.10.0-514` и выше).

*   **Требование для XFS:** При использовании `overlay2` поверх файловой системы XFS (которая является ФС по умолчанию в CentOS/RHEL 7), необходимо, чтобы она была отформатирована с опцией `ftype=1`. Проверить это можно командой `xfs_info / | grep ftype`. Если `ftype=0`, `overlay2` работать не будет.

### `overlay` vs `overlay2`

*   **`overlay`:** Первая реализация. Имела серьезный недостаток: при большом количестве слоев происходил быстрый расход inode'ов, что могло привести к проблемам на файловой системе.
*   **`overlay2`:** Оптимизированная версия, которая решила проблему с inode'ами. Является текущим стандартом. **Всегда следует использовать `overlay2`, а не `overlay`.**

### Сравнение с другими драйверами

*   **AUFS:** Был первым union-драйвером в Docker, но так и не вошел в основное ядро Linux, что создавало проблемы с поддержкой.
*   **Device Mapper:** Работал на **блочном уровне**, а не на файловом. Для production требовал сложной настройки LVM (`direct-lvm`), а его реализация Copy-on-Write была медленнее для типичных контейнерных нагрузок по сравнению с `OverlayFS`.

`OverlayFS` (`overlay2`) стал стандартом, так как предложил лучший компромисс: он был включен в ядро Linux, прост в использовании и обеспечивал высокую производительность для большинства сценариев.
