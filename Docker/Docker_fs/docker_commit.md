# Docker Commit — создание образа из контейнера

## Определения

**`docker commit`** — команда, создающая новый Docker-образ на основе изменений в файловой системе запущенного или остановленного контейнера. Она фиксирует текущее состояние верхнего (записываемого) слоя контейнера и сохраняет его как новый статический слой в новом образе.

### Основные флаги

- `-a, --author` — позволяет указать автора образа (например, `"John Doe <john@example.com>"`).
- `-m, --message` — комментарий к коммиту, описывающий внесенные изменения.
- `-c, --change` — применяет инструкции Dockerfile к создаваемому образу. Поддерживаются: `CMD`, `ENTRYPOINT`, `ENV`, `EXPOSE`, `LABEL`, `ONBUILD`, `USER`, `VOLUME`, `WORKDIR`.
- `-p, --pause` — (по умолчанию `true`) приостанавливает работу контейнера на время создания снимка, чтобы обеспечить целостность данных.

## Основные концепции

Использование `docker commit` в производственной среде (Production) считается **анти-паттерном**. Команда предназначена в первую очередь для быстрой отладки или сохранения промежуточного состояния "сломанного" контейнера для последующего анализа.

### Почему стоит избегать в эксплуатации

- **Отсутствие прозрачности**: Образ превращается в «черный ящик». В отличие от `Dockerfile`, невозможно точно отследить, какие команды выполнялись, какие зависимости установлены и какие настройки изменены вручную.
- **Раздувание объема (Image Bloat)**: Команда сохраняет абсолютно все изменения, включая временные файлы, логи и кэши (например, `/var/cache/apt`), которые в `Dockerfile` обычно удаляются в том же слое (`RUN`).
- **Проблемы безопасности**: При ручном изменении контейнера легко забыть в истории команд или временных файлах секреты, ключи доступа или пароли, которые навсегда останутся в слое образа.
- **Нарушение воспроизводимости**: Невозможно гарантировать, что повторный ручной запуск и коммит приведут к идентичному результату на другой машине.
- **Неэффективность слоев**: Все ручные изменения объединяются в один массивный слой, что ухудшает работу механизма кэширования Docker.

## Практические сценарии

### Сценарий 1: Создание базового образа с установленным ПО

Этот сценарий демонстрирует, как создать собственный базовый образ, который в дальнейшем можно использовать для других приложений.

**Шаг 1: Запуск базового контейнера и установка ПО**

```bash
docker run --name base-container -it ubuntu bash

# Внутри контейнера:
apt update && apt install -y nodejs

# Проверка установки:
node -e "console.log('Hello World')"
# → Hello World
```

**Шаг 2: Фиксация изменений в новый образ**

В отдельном терминале фиксируем изменения:

```bash
docker commit -m "Add Node.js" base-container node-base
```

**Шаг 3: Проверка слоёв нового образа**

```bash
docker history node-base

# IMAGE          CREATED         CREATED BY                      SIZE      COMMENT
# <missing>      2 minutes ago   docker commit -m Add Node.js    137MB     Add Node.js
# <missing>      ...             /bin/sh -c #(nop) CMD ["bash"]   0B
# <missing>      ...             ...                              ...
```

Видим новый слой размером ~137 МБ — это установленный Node.js и зависимости.

**Шаг 4: Проверка работоспособности**

```bash
docker run node-base node -e "console.log('Hello again')"
# → Hello again
```

**Шаг 5: Удаление временного контейнера**

```bash
docker rm -f base-container
```

### Сценарий 2: Расширение базового образа в приложение

Теперь используем созданный `node-base` как основу для приложения.

**Шаг 1: Запуск контейнера из базового образа**

```bash
docker run --name app-container -it node-base bash

# Внутри контейнера:
echo "console.log('Hello from node app')" > app.js
```

**Шаг 2: Фиксация с установкой команды по умолчанию**

Флаг `-c` позволяет задать конфигурацию образа, включая `CMD` — команду, которая будет выполняться при запуске контейнера:

```bash
docker commit -c 'CMD ["node", "app.js"]' -m "Add app" app-container sample-app
```

**Шаг 3: Проверка нового слоя**

```bash
docker history sample-app

# IMAGE          CREATED        CREATED BY                         SIZE      COMMENT
# <missing>      1 minute ago   docker commit -c CMD ["node"...    33B       Add app
# <missing>      ...            docker commit -m Add Node.js        137MB     Add Node.js
# ...
```

Новый слой занимает всего 33 байта — это файл `app.js`.

**Шаг 4: Запуск приложения**

```bash
docker run sample-app
# → Hello from node app
```

Контейнер автоматически выполняет `CMD ["node", "app.js"]`, указанную при комите.

**Шаг 5: Удаление временного контейнера**

```bash
docker rm -f app-container
```

> **Важно:** описанный подход с `docker commit` используется редко. В production-среде образы собираются через `Dockerfile`, который обеспечивает воспроизводимость, версионирование и прозрачность сборки.

### Сценарий 3: Корректное использование (Отладка)

Представьте, что контейнер с вашим приложением работает некорректно в тестовой среде, и у вас нет к нему прямого доступа. Вы просите коллегу помочь с диагностикой.

1. **Коллега заходит в контейнер и устанавливает утилиты для отладки:**

    ```bash
    docker exec -it my-app-container bash
    
    # Внутри контейнера
    apt-get update && apt-get install -y curl dnsutils
    curl -v http://some-internal-service:8080
    # ... проводит другие диагностические действия ...
    ```

2. **Сохранение состояния для анализа:**
    После установки инструментов и сбора первичной информации коллега может сохранить это состояние в новый образ, чтобы передать его вам для более глубокого анализа, не "загрязняя" оригинальный образ и не требуя повторной установки утилит.

    ```bash
    docker commit my-app-container my-app:debug-snapshot
    ```

    Теперь вы можете запустить контейнер `my-app:debug-snapshot` в своем локальном окружении и продолжить анализ с того же места, где остановился ваш коллега.

### Сценарий 4: Анти-паттерн (сборка production-образа)

Это пример того, **как делать не следует**.

1. **Запуск базового образа и ручная установка ПО:**

    ```bash
    docker run -it --name web-manual ubuntu:22.04 bash
    
    # Внутри контейнера
    apt-get update && apt-get install -y nginx
    echo "<h1>Hello from manual container</h1>" > /var/www/html/index.html
    exit
    ```

2. **Создание образа через `commit`:**

    ```bash
    docker commit web-manual my-nginx:manual-build
    ```

    *Проблема:* Этот образ непрозрачен, содержит кеш `apt` и не может быть автоматически воспроизведен.

#### Правильный подход с `Dockerfile`

Вместо ручных действий создается `Dockerfile`:

```dockerfile
FROM ubuntu:22.04

# Установка Nginx и очистка кеша в одной инструкции
RUN apt-get update \
 && apt-get install -y nginx \
 && rm -rf /var/lib/apt/lists/*

# Копирование контента
COPY index.html /var/www/html/

# Запуск Nginx
CMD ["nginx", "-g", "daemon off;"]
```

Этот файл версионируется, автоматически собирается и всегда дает предсказуемый результат.

## Дополнительная информация

- **Разница между `commit` и `export`**:
  - `docker commit` создает **образ** со всей историей слоев и метаданными, сохраняя возможность запуска контейнера из него.
  - `docker export` создает "плоский" **tar-архив** файловой системы контейнера, при этом вся история слоев и метаданные (например, `ENV`, `EXPOSE`) теряются.

- **Анализ изменений (`docker diff`)**: Перед выполнением коммита рекомендуется запустить `docker diff <container_name>`, чтобы просмотреть список измененных файлов:
  - `A` (Added) — файл добавлен;
  - `C` (Changed) — файл изменен;
  - `D` (Deleted) — файл удален.

- **Проверка слоев (`docker history`)**: После коммита новый слой можно увидеть с помощью команды `docker history <image_name>`. Это поможет оценить реальный размер внесенных изменений.
