# Docker Commit: Создание образа из контейнера

## Определения

**`docker commit`** — это команда, которая создает новый Docker-образ из изменений, сделанных в файловой системе запущенного или остановленного контейнера. Она, по сути, делает "снимок" верхнего, записываемого слоя контейнера и сохраняет его как новый слой образа.

## Основные концепции

Хотя команда `docker commit` выглядит как простой способ сохранить изменения, в производственной среде она считается **анти-паттерном**. Её использование оправдано только в очень узких сценариях, в основном связанных с отладкой.

Ключевые недостатки `docker commit` в сравнении с использованием `Dockerfile`:

- **Непрозрачность и отсутствие воспроизводимости**:
  - **`docker commit`**: Создает "черный ящик". Невозможно понять, какие команды были выполнены внутри контейнера, чтобы достичь его текущего состояния. Воспроизвести такой образ на другой машине или в будущем практически невозможно.
  - **`Dockerfile`**: Является декларативным, версионируемым кодом, который пошагово описывает процесс сборки. Он самодокументируем и гарантирует, что сборка будет идентичной в любом окружении.

- **Раздувание образа (Image Bloat)**:
  - **`docker commit`**: Захватывает все изменения в файловой системе, включая временные файлы, логи, кеши пакетных менеджеров (`apt`, `npm` и т.д.) и ненужные артефакты. Это приводит к созданию неоправданно больших образов.
  - **`Dockerfile`**: Позволяет точно контролировать, что попадает в образ. Правильно написанный `Dockerfile` включает шаги по очистке кешей и удалению временных файлов в той же `RUN` инструкции, где они были созданы.

- **Неэффективное использование слоев**:
  - **`docker commit`**: Все изменения "схлопываются" в один большой, непрозрачный слой. Это ломает механизм кеширования Docker, так как любое малейшее изменение потребует создания нового огромного слоя.
  - **`Dockerfile`**: Каждая инструкция создает отдельный, кешируемый слой. Это позволяет Docker повторно использовать неизменённые слои при последующих сборках, значительно ускоряя процесс разработки.

- **Непригодность для CI/CD**:
  - **`docker commit`**: Это ручная, императивная команда, которая не вписывается в автоматизированные конвейеры сборки и развертывания.
  - **`Dockerfile`**: Идеально интегрируется в системы CI/CD. Сборка запускается одной командой (`docker build`), а сам `Dockerfile` хранится в системе контроля версий вместе с кодом приложения.

> **Вывод:** `docker commit` — это инструмент для ручного вмешательства, а не для системной сборки образов.

## Практические сценарии

### Сценарий 1: Корректное использование (Отладка)

Представьте, что контейнер с вашим приложением работает некорректно в тестовой среде, и у вас нет к нему прямого доступа. Вы просите коллегу помочь с диагностикой.

1. **Коллега заходит в контейнер и устанавливает утилиты для отладки:**

    ```bash
    docker exec -it my-app-container bash
    
    # Внутри контейнера
    apt-get update && apt-get install -y curl dnsutils
    curl -v http://some-internal-service:8080
    # ... проводит другие диагностические действия ...
    ```

2. **Сохранение состояния для анализа:**
    После установки инструментов и сбора первичной информации коллега может сохранить это состояние в новый образ, чтобы передать его вам для более глубокого анализа, не "загрязняя" оригинальный образ и не требуя повторной установки утилит.

    ```bash
    docker commit my-app-container my-app:debug-snapshot
    ```

    Теперь вы можете запустить контейнер `my-app:debug-snapshot` в своем локальном окружении и продолжить анализ с того же места, где остановился ваш коллега.

### Сценарий 2: Анти-паттерн (Сборка production-образа)

Это пример того, **как делать не следует**.

1. **Запуск базового образа и ручная установка ПО:**

    ```bash
    docker run -it --name web-manual ubuntu:22.04 bash
    
    # Внутри контейнера
    apt-get update && apt-get install -y nginx
    echo "<h1>Hello from manual container</h1>" > /var/www/html/index.html
    exit
    ```

2. **Создание образа через `commit`:**

    ```bash
    docker commit web-manual my-nginx:manual-build
    ```

    *Проблема:* Этот образ непрозрачен, содержит кеш `apt` и не может быть автоматически воспроизведен.

#### Правильный подход с `Dockerfile`

Вместо ручных действий создается `Dockerfile`:

```dockerfile
FROM ubuntu:22.04

# Установка Nginx и очистка кеша в одной инструкции
RUN apt-get update \
 && apt-get install -y nginx \
 && rm -rf /var/lib/apt/lists/*

# Копирование контента
COPY index.html /var/www/html/

# Запуск Nginx
CMD ["nginx", "-g", "daemon off;"]
```

Этот файл версионируется, автоматически собирается и всегда дает предсказуемый результат.

## Дополнительная информация

- **Разница между `commit` и `export`**:
  - `docker commit` создает **образ** со всей историей слоев и метаданными.
  - `docker export` создает "плоский" **tar-архив** файловой системы контейнера, теряя всю историю слоев и метаданные.

- **`docker diff`**: Перед тем как сделать `commit`, полезно выполнить команду `docker diff <container_name>`, чтобы увидеть, какие файлы были добавлены (`A`), изменены (`C`) или удалены (`D`) в файловой системе контейнера.

- **Основной инструмент для сборки**: Для всех производственных и разработочных нужд используйте **[Dockerfile](../../Docker/Dockerfile/Instructions/overview_definitions.md)**.
- **Лучшие практики**: Следуйте руководству по **[оптимизации сборок](../Dockerfile/Docker_best_practices/build_optimization.md)** для создания эффективных и безопасных образов.
