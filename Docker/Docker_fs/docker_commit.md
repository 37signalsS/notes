# Docker Commit: Создание образа из контейнера

## Определения

Команда `docker commit <контейнер> <новый_образ>` создает новый образ на основе текущего состояния запущенного контейнера.

## Зачем использовать docker commit

*   Быстрое прототипирование: зафиксировать эксперименты и ручные донастройки в работающем контейнере.
*   Сохранение состояния отладки: перенести «рабочую» конфигурацию и инструменты диагностики в образ.
*   Снэпшот перед обновлениями: заморозить текущее состояние для возврата.
*   Миграция легаси-окружений: перенести то, что создавалось вручную, в образ для дальнейшей автоматизации.

## Как это работает

Контейнер имеет верхний записываемый слой поверх слоев базового образа. Команда commit преобразует содержимое этого записываемого слоя плюс выбранные метаданные в новый образ (создавая дополнительный слой). История слоев сохраняется, а новые метаданные (CMD, LABEL, EXPOSE и др.) могут быть заданы опцией --change. По умолчанию контейнер кратко приостанавливается (--pause) для консистентного снимка.

## Базовый сценарий

```bash
# 1) Запустить контейнер для изменений
docker run -it --name webtest ubuntu:22.04 bash

# 2) Внутри контейнера установить ПО и очистить кэш
apt-get update && apt-get install -y nginx
rm -rf /var/lib/apt/lists/*

# При необходимости внести правки в конфиги, затем выйти
exit

# 3) Зафиксировать изменения в новый образ с метаданными
docker commit \
  -a "DevOps Team <devops@example.com>" \
  -m "Добавлен nginx, базовая конфигурация" \
  --change 'EXPOSE 80' \
  --change 'CMD ["nginx","-g","daemon off;"]' \
  webtest myrepo/nginx:proto

# 4) Проверить историю слоёв и запустить контейнер из образа
docker history myrepo/nginx:proto
docker run -d -p 8080:80 myrepo/nginx:proto
```

## Базовые концепции

## Метаданные через --change

Опция --change применяет подмножество инструкций Dockerfile, формируя метаданные образа.

| Инструкция | Пример | Назначение |
| :--- | :--- | :--- |
| CMD | CMD ["nginx","-g","daemon off;"] | Команда по умолчанию |
| ENTRYPOINT | ENTRYPOINT ["/entrypoint.sh"] | Точка входа |
| ENV | ENV APP_ENV=prod | Переменные окружения |
| EXPOSE | EXPOSE 80 | Документация порта |
| LABEL | LABEL maintainer="DevOps Team" | Метки для поиска и политики |
| WORKDIR | WORKDIR /app | Рабочая директория |
| USER | USER nginx | Пользователь процесса |
| VOLUME | VOLUME ["/data"] | Декларация томов |
| HEALTHCHECK | HEALTHCHECK CMD curl -f http://... | | exit 1 | Проверка работоспособности |

Поддержка конкретных инструкций зависит от версии Docker; обычно используются CMD, ENTRYPOINT, ENV, EXPOSE, LABEL, WORKDIR, USER, VOLUME, HEALTHCHECK.

## Сравнение: commit и сборка из Dockerfile

| Критерий | commit | Dockerfile |
| :--- | :--- | :--- |
| Воспроизводимость | Низкая, шаги не описаны в коде | Высокая, декларативная история сборки |
| Контроль слоёв | Ограниченный | Точный контроль RUN/ADD/COPY |
| Code review | Сложно ревьюить | Обычные практики ревью |
| Кеширование сборки | Нет повторного использования команд | Есть, ускоряет сборку |
| Скорость прототипа | Очень высокая | Требуется написать Dockerfile |
| Безопасность и политика | Меньше прозрачности | Полная видимость и проверки |

### `docker commit`: анти-паттерн

Хотя `docker commit` позволяет быстро создать образ из текущего состояния контейнера, **это считается плохой практикой (анти-паттерном)** для большинства производственных сценариев, потому что:

- **Нарушает воспроизводимость (Reproducibility):** Невозможно понять, как образ был создан, в отличие от пошагового и версионируемого [Dockerfile](../Dockerfile/dockerfile_instructions.md).
- **Раздувает образ (Image Bloat):** Включает в себя временные файлы, логи и кэш.
- **Скрывает историю (History Obscurity):** Заменяет понятную историю слоев одной непрозрачной командой `commit`.

**Всегда используйте [Dockerfile](../Dockerfile/dockerfile_instructions.md) для всех сборок, чтобы обеспечить прозрачность, воспроизводимость и управляемость образов.**

## Практические нюансы

*   Перед commit удаляйте временные файлы и кэши, чтобы уменьшить размер слоя. Полезно проверить изменения: docker diff webtest.
*   При наличии требований к аптайму используйте --pause=false, понимая риск несогласованного состояния.
*   Не включайте секреты: удалите ключи, токены, историю оболочки из /root/.ssh, ~/.bash_history и т. п.
*   Тегируйте осмысленно: myrepo/app:2025-10-10 или myrepo/app:exp1; при готовности отправьте в реестр: docker push myrepo/app:tag.
*   Отличайте commit от export/import: docker export контейнер → tar-файлы ФС без историй и метаданных; commit создаёт образ со слоями и метаданными.
*   Для анализа веса слоёв используйте docker history и docker image inspect; при необходимости пересоберите по Dockerfile, зафиксировав шаги в коде.
