# Образы Docker (Images)

## Определения

**Образ (Image)** — это неизменяемый (immutable) шаблон, логическая группировка слоев и метаданных, содержащий все необходимое для запуска приложения и инструкции по его сборке и работе. Параметры образа определяются в [Dockerfile](../Dockerfile/dockerfile_instructions.md).

Подробное определение и ключевое отличие образа от контейнера с аналогией "Класс -> Объект" находится в документе **[Компоненты Docker](../docker_overview.md#образ-и-контейнер)**.

## Основные понятия

### Концепция слоев (Layers)

Образ Docker состоит из набора слоев, которые накладываются друг на друга. Каждый слой представляет собой результат выполнения одной из команд в `Dockerfile` (например, `RUN`, `COPY`, `ADD`), которая изменяет файловую систему.

- **Неизменяемость (Read-Only)**: Все слои образа, кроме самого верхнего, являются неизменяемыми (read-only). Они кэшируются и могут переиспользоваться между разными образами, что экономит место и ускоряет сборку.
- **Наложение**: Слои образуют единую файловую систему благодаря технологии **OverlayFS** (которая является одним из вариантов [UnionFS](./docker_overlayfs.md)). Если файл существует в нескольких слоях, будет видна версия из самого верхнего слоя. Если файл удаляется в верхнем слое, он просто помечается как удаленный с помощью специальных файлов-маркеров ("whiteout"), но продолжает существовать в нижних слоях.
- **Слой контейнера (Writable Layer)**: Когда из образа запускается контейнер, поверх всех слоев образа добавляется еще один, тонкий **записываемый слой (writable layer)**. Все изменения, происходящие в работающем контейнере (создание, изменение, удаление файлов), записываются именно в этот слой.

Эта архитектура позволяет:

1. **Экономить место**: Десятки контейнеров, запущенных из одного образа, переиспользуют общие слои, и для каждого создается лишь небольшой уникальный записываемый слой.
2. **Обеспечивать изоляцию**: Изменения в одном контейнере не затрагивают ни образ, ни другие контейнеры.
3. **Быстро запускать контейнеры**: Не нужно копировать всю файловую систему; достаточно создать новый записываемый слой.

Команда `docker history <имя_образа>` позволяет увидеть все слои, из которых состоит образ.

### Многоархитектурные образы (Multi-Arch)

Современные CI/CD-системы позволяют собирать образы, которые могут работать на разных архитектурах процессоров (например, `amd64` и `arm64`). Это достигается с помощью `docker buildx`.

**Пример сборки:**

```sh
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t my-app:1.1.0 \
  --push .
```

Docker-демон на хосте автоматически выберет и запустит версию образа, соответствующую его архитектуре.

Команда `docker manifest` позволяет инспектировать и управлять манифестами — документами, описывающими мультиархитектурные образы. С её помощью можно точно увидеть, под какие платформы собран образ (например, `AMD64` для облачных серверов и `ARM64` для edge-устройств), и все это под одним тегом.

Это особенно важно для гибридных деплоев. Например, ваш бэкенд крутится в облаке на `AMD64`, а edge-шлюзы или IoT-устройства работают на `ARM`. Проверяя манифест, вы гарантируете, что одна и та же версия контейнера будет корректно работать везде, без необходимости вручную собирать и тегировать отдельные образы.

## Образ vs. Контейнер: Ключевые различия

Образ и контейнер — два уровня одной модели, но с разными свойствами и назначением. Понимание границы между ними критично для воспроизводимости, кэширования и корректного управления состоянием приложения.

### Образ: неизменяемый шаблон
Образ — это неизменяемый артефакт, собранный из слоёв с помощью union-файловых систем (например, overlay2). Каждый слой содержит разницу относительно предыдущего и идентифицируется контент-адресуемым хэшем (sha256). Образ включает:

*   Файловые слои (rootfs).
*   Конфигурацию: CMD, ENTRYPOINT, ENV, EXPOSE, VOLUME, WORKDIR, LABELS.
*   Манифест и digest; теги (latest, 1.0) — лишь удобные указатели, а не идентификаторы.

Ключевое свойство — неизменяемость: после сборки содержимое не меняется. Это делает образы кешируемыми и переносимыми, позволяет реплицировать среды через регистри.

### Контейнер: исполняемый экземпляр
Контейнер — это процесс(ы), запущенные из образа, с дополнительным writable-слоем и изоляцией (namespaces, cgroups). Он наследует все слои образа, но имеет собственное состояние выполнения: PID, сеть, монтирования, переменные окружения, аргументы запуска, логи, временные файлы.

Жизненный цикл контейнера включает состояния created, running, paused, exited. Один образ может порождать множество контейнеров с разными параметрами.

### Сравнение по ключевым аспектам
| Аспект | Образ | Контейнер |
| :--- | :--- | :--- |
| **Состояние** | Неизменяемый артефакт | Исполняемое и изменяемое состояние |
| **Идентификатор** | Digest (sha256), теги | Уникальный container ID, имя |
| **Файловая система** | Набор слоёв (read-only) | Наследованные слои + writable-слой (copy-on-write) |
| **Назначение** | Шаблон развёртывания | Экземпляр выполнения |
| **Переносимость** | Перемещается через registry | Привязан к конкретному хосту/рантайму |
| **Конфигурация** | ENTRYPOINT, CMD по умолчанию | Переопределение: аргументы, env, сети, монтирования |
| **Данные** | Не хранит рабочие данные | Данные через тома/монты, иначе теряются при удалении |

## Практические сценарии

### Жизненный цикл образа: основные команды

| Команда | Описание |
| :--- | :--- |
| `docker build -t <имя образа>:<тег> .` | Собирает образ из [`Dockerfile`](../Dockerfile/dockerfile.md) в текущей директории. |
| `docker images` | Показывает все образы, имеющиеся на хосте. |
| `docker pull <имя>:<тег>` | Скачивает образ из [registry](./docker_registries.md) (например, Docker Hub). |
| `docker push <имя>:<тег>` | Загружает образ в [registry](./docker_registries.md). |
| `docker rmi <имя>:<тег>` | Удаляет образ. |
| `docker tag <исходный> <целевой>` | Создает новый тег (алиас) для существующего образа. |
| `docker history <имя>:<тег>` | Показывает слои, из которых состоит образ, и команды их создания. |

### Диагностика слоёв

Посмотреть, как образ разбит на слои и что в них менялось, можно командами:

```bash
docker history --no-trunc <image>
```

Получение сведений о драйвере и путях overlay2:

```bash
docker inspect <container> \
  --format '{{ json .GraphDriver }}' | jq .
```

Типичная структура GraphDriver для overlay2 включает поля LowerDir, UpperDir, WorkDir и MergedDir, отражающие соответствующие каталоги.

### Перенос образов (save/load, export/import)

Для переноса образов и контейнеров между системами без использования [реестра](../docker_registries.md) существуют две пары команд с принципиальными различиями: `save`/`load` для образов и `export`/`import` для контейнеров.

#### `docker save` и `docker load`: Работа с образами

Эти команды работают с **образами**, сохраняя всю их структуру, включая слои, историю и метаданные. Это предпочтительный способ для резервного копирования и переноса образов.

- **`docker save`**: Создает `.tar`-архив из одного или нескольких образов.

  ```sh
  docker save -o my_images.tar my-image:1.1.0 another-image:1.1
  ```

- **`docker load`**: Загружает образы из `.tar`-архива, восстанавливая их в исходном виде со всеми слоями.

  ```sh
  docker load -i my_images.tar
  ```

#### `docker export` и `docker import`: Работа с файловой системой

Эти команды работают с **файловой системой контейнера**, а не с образом. Они создают "плоский" (flattened) архив, объединяя все слои в один и теряя историю и метаданные.

- **`docker export`**: Создает `.tar`-архив файловой системы запущенного или остановленного контейнера.

  ```sh
  docker export my-container > my_container.tar
  ```

- **`docker import`**: Создает **новый** образ из `.tar`-архива файловой системы.

  ```sh
  cat my_container.tar | docker import - my-new-image:1.1.0
  ```

#### Ключевые различия `save`/`load` и `export`/`import`

| Критерий | `save`/`load` | `export`/`import` |
| :--- | :--- | :--- |
| **Объект** | **Образ (Image)** | **Файловая система контейнера** |
| **Слои** | **Сохраняются** | Теряются (объединяются в один) |
| **История** | Сохраняется (`docker history`) | Теряется |
| **Метаданные** | Сохраняются (CMD, EXPOSE и т.д.) | Теряются |
| **Назначение** | Перенос/бекап полноценных образов | Создание "чистого" базового образа из существующего контейнера |

### Управление слоями

#### Объединение слоев (`--squash`)

Флаг `docker build --squash` объединяет все слои, созданные в `Dockerfile`, в один новый слой.

- **Плюс:** Может незначительно уменьшить размер финального образа за счет удаления неиспользуемых файлов из промежуточных слоев.
- **Минус:** Уничтожает кэш для объединенных слоев. Если базовый образ остается неизменным, он будет по-прежнему кэшироваться, но любые изменения в `Dockerfile` приведут к повторной сборке всех объединенных слоев, что замедляет итеративные сборки.

#### Схлопывание слоев с помощью `docker-squash`

Встроенный флаг `docker build --squash` имеет существенный недостаток: он уничтожает весь кэш слоев. Более гибкой и мощной альтернативой является внешняя утилита **`docker-squash`**.

Она позволяет "схлопнуть" уже собранный образ, объединяя только нужные слои и сохраняя базовые слои нетронутыми. Это позволяет уменьшить размер образа, удалив временные файлы (например, кэш `apt` или `npm`), не жертвуя при этом кэшем базового образа.

1. **Установка:**

    ```bash
    pip install docker-squash==1.2.2
    ```

2. **Использование:**

    ```bash
    # Схлопнуть последние 2 слоя
    docker-squash -f 2 my-image:1.1.0 -t my-image:squashed

    # Схлопнуть все слои, начиная с определенного (ID слоя можно взять из `docker history`)
    docker-squash -from 5a5295c74599 my-image:1.1.0 -t my-image:squashed
    ```

**Преимущества перед `docker build --squash`:**

- **Сохранение кэша:** Не затрагивает базовые слои, позволяя Docker переиспользовать их при последующих сборках.
- **Гибкость:** Позволяет точно указать, какие слои нужно объединить.
- **Работа с существующими образами:** Можно оптимизировать образы, даже не имея доступа к их `Dockerfile`.

## Дополнительная информация

### Практические нюансы: Уровни взаимодействия

*   **Переопределения:** Контейнер может изменить CMD и частично ENTRYPOINT без пересборки образа.
    ```bash
    docker run --rm --entrypoint /bin/sh alpine -c 'echo ok'
    ```
*   **Избегайте `docker commit`:** Превращать контейнер в источник образа через `commit` без контроля — плохая практика, нарушающая воспроизводимость. Подробнее см. **[Docker Commit: Создание образа из контейнера](./docker_commit.md)**.
    ```sql
    docker commit app1 app:drifted
    ```
*   **Кэш:** Повторное использование слоёв образа ускоряет сборку и деплой, но изменения в верхних слоях инвалидацию кэша вызывают чаще.
*   **Разделение ответственности:** Образ фиксирует среду и зависимости; контейнер задаёт параметры выполнения и подключение к окружению (сеть, секреты, тома).


### Реверс-инжиниринг образов

**Внимание:** Это метод "последней надежды", если `Dockerfile` утерян безвозвратно.

Эти утилиты анализируют слои образа и генерируют `Dockerfile`, который мог бы его создать. Они **не обновлялись много лет и не рекомендуются к использованию**, так как могут быть несовместимы с последними версиями Docker.

- **[dduvnjak/dockerfile-from-image](https://github.com/dduvnjak/dockerfile-from-image)**

  ```sh
  # Образ не обновлялся с 2018 года
  sudo docker run -v /var/run/docker.sock:/var/run/docker.sock --rm dduvnjak/dockerfile-from-image:1.0 <IMAGE_ID>
  ```

- **[laniksj/dfimage](https://github.com/LanikSJ/dfimage)**

  ```sh
  # Образ не обновлялся с 2021 года
  sudo docker run -v /var/run/docker.sock:/var/run/docker.sock --rm laniksj/dfimage:0.1.0 <IMAGE_ID>
  ```

### Подписание образов и безопасность

Для обеспечения целостности и аутентичности образов используется механизм цифровых подписей. Это позволяет гарантировать, что образ не был изменен с момента его создания доверенным издателем.

Подробнее о механизмах подписи, таких как **Docker Content Trust** и **Cosign**, можно прочитать в руководстве по [безопасности Docker](./Docker_security/docker_security_overview.md).

## Docker-образы в разных бранчах

### Вопрос: Один артефакт или разные?

**Сценарий:** Dockerfile добавлен в бранч `dev`, образ собран и в `dev`, и в `stage`.

**Ответ:** Это будут **разные артефакты**, даже если Dockerfile одинаковый.

### Почему разные артефакты?

```
Бранч dev:
┌─────────────────────────────────────────────────────────────┐
│  dev: Dockerfile ──► docker build ──► myapp:dev-{hash}     │
│                                                              │
│  Контекст сборки:                                           │
│  - Git commit: abc123 (dev)                                 │
│  - Base image: ubuntu:20.04 (latest на момент сборки)      │
│  - Build args: ENV=development                              │
│  - Слои: [base]─[deps]─[code@abc123]─[config-dev]          │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ Разные!
                              ▼
Бранч stage:
┌─────────────────────────────────────────────────────────────┐
│  stage: Dockerfile ──► docker build ──► myapp:stage-{hash} │
│                                                              │
│  Контекст сборки:                                           │
│  - Git commit: def456 (stage)                               │
│  - Base image: ubuntu:20.04 (возможно другой digest!)      │
│  - Build args: ENV=staging                                  │
│  - Слои: [base]─[deps]─[code@def456]─[config-stage]        │
└─────────────────────────────────────────────────────────────┘
```

### Факторы, создающие различия

| Фактор | Влияние | Результат |
|--------|---------|-----------|
| **Git-история** | Разные коммиты = разный код | Разные слои COPY |
| **Base image** | `ubuntu:latest` меняется | Может быть разный base layer |
| **Build args** | `ENV=dev` vs `ENV=prod` | Разные инструкции RUN |
| **Build context** | Разные файлы в бранче | Разные слои COPY |
| **Multi-stage** | TARGETPLATFORM и др. | Разные финальные образы |
| **Тегирование** | dev-v1.0 vs stage-v1.0 | Разные манифесты в registry |

### Immutable артефакты: Лучшая практика

```dockerfile
# Dockerfile с явным версионированием
FROM ubuntu:20.04@sha256:abc123...  # Пиним digest!

ARG APP_VERSION
ARG BUILD_ENV

# Установка зависимостей (кэшируется)
RUN apt-get update && apt-get install -y \
    python3=3.8.10-0ubuntu1 \
    && rm -rf /var/lib/apt/lists/*

# Копирование кода
COPY . /app

# Сборка с версией
RUN echo "Building ${APP_VERSION} for ${BUILD_ENV}"

LABEL git.commit=$GIT_COMMIT \
      build.env=$BUILD_ENV \
      build.date=$BUILD_DATE
```

```bash
# Сборка с полным контролем
DOCKER_BUILDKIT=1 docker build \
  --build-arg APP_VERSION=1.2.3 \
  --build-arg BUILD_ENV=dev \
  --build-arg GIT_COMMIT=$(git rev-parse HEAD) \
  --build-arg BUILD_DATE=$(date -u +'%Y-%m-%dT%H:%M:%SZ') \
  -t myapp:1.2.3-dev-$(git rev-parse --short HEAD) \
  -t myapp:1.2.3-dev-latest \
  .
```

### Промоция образов между окружениями

```
РЕКОМЕНДУЕМЫЙ ПОДХОД (Promotion):

Dev бранч:
  docker build -t myapp:dev-abc123 .
  docker tag myapp:dev-abc123 registry/app:dev-abc123
  
Тестирование в dev...
  ✓ Пройдены unit tests
  ✓ Пройдены integration tests
  
Stage бранч (merging dev → stage):
  # НЕ пересобираем! Промоутим проверенный образ
  docker pull registry/app:dev-abc123
  docker tag registry/app:dev-abc123 registry/app:stage-abc123
  docker push registry/app:stage-abc123
  
  # ИЛИ используем immutable digest
  docker buildx imagetools inspect \
    registry/app:dev-abc123 --format '{{ json .Manifest }}'
  
Production (merging stage → main):
  docker pull registry/app:stage-abc123
  docker tag registry/app:stage-abc123 registry/app:prod-abc123
  docker tag registry/app:stage-abc123 registry/app:1.2.3
  docker push registry/app:1.2.3
```

### Проверка идентичности образов

```bash
# Сравнение digests (SHA256)
docker inspect --format='{{index .RepoDigests 0}}' myapp:dev
docker inspect --format='{{index .RepoDigests 0}}' myapp:stage

# Если разные — разные артефакты!

# Просмотр всех слоев
docker history myapp:dev
docker history myapp:stage

# Сравнение с помощью dive
dive myapp:dev
dive myapp:stage

# Извлечение SBOM и сравнение
syft myapp:dev -o json > dev.sbom.json
syft myapp:stage -o json > stage.sbom.json
diff dev.sbom.json stage.sbom.json
```

### Когда образы одинаковые?

Образы **могут быть одинаковыми**, если:

1. **Одинаковый git-commit** в обоих бранчах (fast-forward merge)
2. **Пиннинг всех зависимостей** (FROM ubuntu:20.04@sha256:...)
3. **Одинаковые build args** и context
4. **Multi-stage с одинаковым финальным stage**

```dockerfile
# Multi-stage: финальный образ может быть идентичен
FROM golang:1.19 AS builder
WORKDIR /app
COPY . .
RUN go build -o myapp

FROM scratch AS production
COPY --from=builder /app/myapp /myapp
ENTRYPOINT ["/myapp"]

# Сборка разными способами дает одинаковый результат:
# docker build --target=production .
# Но только если builder stage не влияет на финальный бинарь!
```

### CI/CD стратегии

**Стратегия 1: Сборка в каждом бранче (простая)**
```yaml
# .gitlab-ci.yml
build:
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_REF_SLUG-$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_REF_SLUG-$CI_COMMIT_SHORT_SHA
  # Результат: разные образы в каждом бранче
```

**Стратегия 2: Сборка один раз, промоция между окружениями**
```yaml
# Сборка только в dev
build:
  only:
    - dev
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

# Промоция в stage
promote_to_stage:
  only:
    - stage
  script:
    - docker pull $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    - docker tag $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA $CI_REGISTRY_IMAGE:stage
    - docker push $CI_REGISTRY_IMAGE:stage

# Промоция в prod
promote_to_prod:
  only:
    - main
  script:
    - docker pull $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    - docker tag $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA $CI_REGISTRY_IMAGE:latest
    - docker tag $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA $CI_REGISTRY_IMAGE:$CI_COMMIT_TAG
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_TAG
```
