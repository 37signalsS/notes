# Шифрование томов Docker: Подходы

## Определения

Шифрование данных в томах контейнеров применяется для защиты информации «на покое» (at rest), в бэкапах и при выводе дисков из эксплуатации. Вопрос не имеет единственного «правильного» решения: выбор зависит от модели угроз, среды (локальная машина, сервер, облако), типа хранилища и требований к производительности.

## Уровни шифрования

*   **Блочное (на уровне устройства)**
    *   `dm-crypt/LUKS`: шифрует целый диск/раздел/loop-устройство, прозрачно для файловой системы и приложений.
    *   Подходит для локальных SSD/HDD, когда требуется полное покрытие и простая операционная поддержка.

*   **Файловая система**
    *   `fscrypt` (для ext4/f2fs), `ZFS native encryption`: шифрование на уровне файлов/деревьев каталогов.
    *   Гранулярный контроль, возможна отдельная ротация ключей для разных иерархий.

*   **Прикладной уровень**
    *   Шифрование в приложении (например, библиотеки OpenSSL/libsodium), форматы с встроенным шифрованием (SQLCipher).
    *   Максимальный контроль над моделью угроз; сложнее эксплуатационно и требует изменений кода.

*   **Плагины томов и облачные драйверы**
    *   `Docker Volume Plugins` (например, слои поверх `gocryptfs`) или облачные диски с нативным шифрованием (EBS, PD) на стороне провайдера.
    *   Минимальные изменения в конфигурации, однако доверие переносится на поставщика/плагин.

*   **Для сетевых томов дополнительно**
    *   Шифрование «в полёте» (например, `NFS over TLS`, `SMB encryption`, `iSCSI + IPsec`) дополняет, но не заменяет шифрование «на покое».

## Сравнение подходов

| Подход | Уровень | Примеры | Плюсы | Минусы |
| :--- | :--- | :--- | :--- | :--- |
| Блочное | OS | LUKS/dm-crypt | Полное покрытие, прозрачно | Нельзя скрыть метаданные ФС; один ключ — весь том |
| ФС | FS | fscrypt, ZFS | Гранулярность, ротация по деревьям | Требует поддержки ФС и утилит |
| Прикладной | App | SQLCipher | Точная модель доступа | Изменения в коде, сложность ключей |
| Плагины/облако | Driver/Cloud | Volume plugin, EBS enc | Быстрый старт, управляемые ключи | Зависимость от провайдера/плагина |

## Управление ключами

*   Источники: аппаратные модули, KMS облака, менеджеры секретов.
*   Ротация: периодическая смена ключей и ре-шифрование, план миграции.
*   Жизненный цикл: загрузка ключа при старте узла, защита в памяти, минимизация экспозиции в переменных окружения.
*   Аудит: журналирование операций с ключами и доступов к томам.

## Примеры: LUKS-том и fscrypt для каталога с данными

### Пример: LUKS-том и bind mount

```bash
dd if=/dev/zero of=/secure.img bs=1M count=2048
losetup -fP /secure.img
LOOP=$(losetup -j /secure.img | awk -F: '{print $1}')
cryptsetup luksFormat $LOOP
cryptsetup open $LOOP secure_vol
mkfs.ext4 /dev/mapper/secure_vol
mkdir -p /mnt/secure
mount /dev/mapper/secure_vol /mnt/secure

docker run --rm -v /mnt/secure:/data busybox sh -c 'echo secret > /data/file'
```

После перезагрузки требуется повторно открыть и смонтировать том перед запуском контейнеров.

### Пример: fscrypt для каталога с данными

```bash
apt-get update && apt-get install -y fscrypt
fscrypt setup
mkdir -p /data/projects
fscrypt encrypt /data/projects  # будет создан защитный ключ
docker run --rm -v /data/projects:/app alpine sh -c 'ls -la /app'
```

Каталог читаем в контейнере только если ключ разблокирован на хосте.

## Эксплуатационные аспекты

*   Производительность: шифрование добавляет нагрузку на CPU; AES-NI снижает оверхед.
*   Бэкапы: зашифрованные бэкапы требуют управления ключами отдельно от данных.
*   Удалённый доступ: для сетевых томов комбинируют шифрование «на покое» и «в полёте».
*   Автоматизация: скрипты разблокировки при старте узла, интеграция с менеджером секретов, health-check томов до запуска контейнеров.
