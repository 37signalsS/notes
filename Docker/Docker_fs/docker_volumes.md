# Docker: Тома и персистентное хранение данных (Volumes)

## Определения

Контейнеры по своей природе **эфемерны**. Важно различать два сценария:

- **Перезапуск контейнера** (`docker restart` или перезагрузка хоста): Данные в записываемом слое (`upperdir`) **сохраняются**. Контейнер просто останавливается и запускается снова с тем же записываемым слоем.
- **Удаление контейнера** (`docker rm`): Все данные в записываемом слое **безвозвратно теряются**.

> **Критично:** Любые перезапуски (включая перезагрузку хоста) не удаляют writable layer. Однако `docker system prune`, `docker rm` или пересоздание контейнера приведут к потере данных, если они не вынесены во внешнее хранилище.

Для приложений, которым требуется сохранять состояние (базы данных, пользовательские файлы, логи), необходим механизм персистентного хранения.

Docker решает эту проблему, предоставляя три основных способа монтирования данных из хост-системы в контейнер:

1. **Volume (Том)**: Ресурс хранения данных, которым **полностью управляет Docker**. Физически это директория на хосте (по умолчанию в `/var/lib/docker/volumes/`), но ее жизненный цикл и конфигурация контролируются через Docker API и CLI. **Это предпочтительный способ для хранения данных приложений.**
2. **Bind Mount (Монтирование привязкой)**: Прямое монтирование файла или директории с **произвольного пути на хосте** в контейнер. Docker не управляет этими данными.
3. **tmpfs Mount**: Временное хранилище, которое создается в **оперативной памяти (RAM)** хоста и не записывается на диск.

## Основные концепции

### Зачем использовать внешнее хранилище?

1. **Сохранение данных (Персистентность)**: Данные в `volume` или `bind mount` "переживают" удаление контейнера.
2. **Высокая производительность**: Запись данных в `volume` или `bind mount` происходит напрямую в файловую систему хоста, **в обход медленного механизма [Copy-on-Write (CoW)](./docker_overlayfs.md)**, который используется для записываемого слоя контейнера. Исследования (2026) показывают, что производительность последовательной записи в OverlayFS может быть в **100-177 раз ниже**, чем при использовании томов (0.006-0.010× от скорости volume на SSD/HDD). Это критически важно для баз данных и других I/O-интенсивных приложений.
3. **Совместное использование данных**: Один и тот же `volume` или `bind mount` может быть одновременно подключен к нескольким контейнерам, что позволяет им обмениваться данными. Типичные сценарии:
   - **Агрегация логов**: Несколько приложений пишут логи в общий volume, а контейнер-агрегатор (например, Fluentd, Filebeat) читает и отправляет их в центральное хранилище.
   - **Data Pipelines**: Контейнер-генератор создаёт файлы данных в общий volume, а пайплайн-обработчик считывает и трансформирует их.
   - **Event-Driven архитектуры**: Приложение создаёт файлы-триггеры в volume, а другие контейнеры следят за появлением новых файлов и реагируют на события (например, запуск обработки при появлении файла определённого формата).

### Концептуальная модель Volume

Volume можно представлять как **ссылку (symlink)**, которая "одной ногой" находится в контейнере, а "другой" — на хост-машине. Когда контейнер записывает файлы в примонтированную директорию, данные физически сохраняются на хосте, а не в записываемом слое контейнера. Это позволяет данным существовать независимо от жизненного цикла любого конкретного контейнера.

**Технические детали хранения:**
По умолчанию в Linux именованные тома хранятся по пути:
`/var/lib/docker/volumes/<volume_name>/_data`

## Сравнение типов монтирования

| Характеристика | Тома (Volumes) | Монтирование привязкой (Bind Mounts) | Монтирование в память (tmpfs) |
| :--- | :--- | :--- | :--- |
| **Управление** | **Docker** | **Пользователь/Система** | **Docker** |
| **Расположение** | Директория Docker (`/var/lib/docker/volumes/`) | Произвольный путь на хосте | Оперативная память (RAM) |
| **Персистентность** | **Да** (сохраняются после удаления) | **Да** (файлы остаются на хосте) | **Нет** (теряются при остановке) |
| **Безопасность** | **Высокая.** Изоляция через Docker | **Низкая.** Прямой доступ к ФС хоста | **Высокая.** Данные не пишутся на диск |
| **Сценарий** | Данные приложений (БД, статика) | Разработка (код), конфиги | Временные данные, кэш, секреты |

### Типы томов

- **Именованные тома (Named Volumes)**: Пользователь явно задает имя (например, `postgres-data`). Это рекомендуемый способ: ими легко управлять, они поддерживают драйверы и их можно переиспользовать между контейнерами.
- **Анонимные тома (Anonymous Volumes)**: Docker создает том с хеш-именем. Обычно возникают, если указать только путь внутри контейнера или использовать инструкцию **[VOLUME](../Dockerfile/Instructions/data_storage.md)** в Dockerfile. Их сложнее отслеживать и они требуют регулярной очистки (`docker volume prune`).

### Риски монтирования привязкой (Bind Mounts)

Этот метод полезен для разработки, но требует осторожности в эксплуатации:

- **Безопасность**: Контейнер (особенно запущенный от имени `root`) может изменять системные файлы хоста, что потенциально ведет к эскалации привилегий.
- **Конфликты прав**: Идентификаторы UID/GID процесса в контейнере могут не совпадать с владельцем файлов на хосте, что вызывает ошибки `Permission Denied`.
- **Зависимость от инфраструктуры**: Пути на хосте должны быть идентичны на всех серверах, что усложняет переносимость.

## Настройка прав доступа

### Проблема UID/GID

Процессы внутри контейнера работают с конкретными UID/GID. Если они не совпадают с владельцем директории на хосте, запись будет заблокирована.

**Варианты решения:**

1.  **Использование томов (Рекомендуется)**: Docker автоматически настраивает права для именованных томов.
2.  **Флаг `--user`**: Запуск контейнера с UID, совпадающим с владельцем файлов на хосте (`docker run --user $(id -u):$(id -g) ...`).
3.  **SELinux контекст**: Использование суффиксов `:z` (общий доступ) или `:Z` (эксклюзивный доступ) для автоматической смены меток безопасности.
4.  **Entrypoint-скрипты**: Применение `chown` при старте (требует прав `root` в момент запуска).

#### Влияние User Namespaces (`userns-remap`)

Если в Docker включен механизм **User Namespaces**, то UID `0` (root) внутри контейнера отображается на непривилегированного пользователя на хосте (например, с UID `100000`).

В этом случае:
- При использовании **Bind Mount** файлы на хосте должны принадлежать пользователю из диапазона `subuid` хоста, иначе контейнер не сможет в них писать.
- **Volumes** обрабатываются Docker автоматически: он меняет владельца директории на хосте так, чтобы переназначенный пользователь имел доступ.

Подробнее см. **[Защита хоста и демона Docker (Hardening)](../Docker_security/host_daemon_hardening.md)**.

## Практические сценарии

Docker поддерживает два синтаксиса монтирования: старый (`-v` или `--volume`) и новый, более явный и **рекомендуемый** (`--mount`).

### Сценарий 1: Управление томами (CLI)

```bash
# Создать именованный том с метками
docker volume create --label project=web-stack my-app-data

# Показать список томов, отфильтрованный по метке
docker volume ls --filter label=project=web-stack

# Посмотреть детальную информацию (включая путь на хосте)
docker volume inspect my-app-data

# Удалить том (он не должен использоваться ни одним контейнером)
docker volume rm my-app-data

# Удалить все неиспользуемые ("dangling") тома
docker volume prune

# Удалить неиспользуемые тома старше определенного времени
docker volume prune --filter "until=24h"
```

**Автоматическое удаление томов:**
При удалении контейнера тома по умолчанию сохраняются. Чтобы удалить анонимные тома вместе с контейнером, используйте флаг `-v`:
```bash
docker rm -v my-container
```
*Внимание: этот флаг удаляет только анонимные тома. Именованные тома всегда сохраняются.*

**Наследование монтирований:**
...
```bash
docker run -d --name container2 --volumes-from container1 my-image
```
*Этот метод позволяет новому контейнеру получить доступ к тем же томам и bind-mount'ам, что и у исходного контейнера.*

### Сценарий 2: Хранение данных PostgreSQL (Volume)

Для баз данных использование томов является критически важным не только для сохранения данных, но и для обеспечения производительности I/O.

**Пример запуска:**

```bash
docker run -d --name my-postgres \
  -e POSTGRES_PASSWORD=mysecretpassword \
  --mount type=volume,source=postgres-db-data,target=/var/lib/postgresql/data \
  postgres:16-alpine
```

*В этом примере Docker автоматически создаст именованный том `postgres-db-data`, если он не существует. PostgreSQL при первом запуске выполнит инициализацию в указанной директории.*

Подробные инструкции по деплою, настройке безопасности и инициализации БД в Docker приведены в **[Деплой PostgreSQL в Docker](../../Databases/PostgreSQL/Operations/docker_deployment.md)**.

> **Важно:** Переменная `POSTGRES_PASSWORD` требуется **только при первичной инициализации** новой базы данных. При повторном запуске контейнера с существующего volume (где данные уже есть) эта переменная не нужна.

### Сценарий 3: Разработка с "живой" перезагрузкой (Bind Mount)

```bash
# Запускаем Node.js приложение, монтируя исходный код из текущей директории
docker run -d --name my-node-app \
  -p 3000:3000 \
  --mount type=bind,source=$(pwd),target=/app \
  node:18-alpine
```

*Теперь изменения в исходном коде на хосте сразу же отражаются внутри контейнера.*

### Сценарий 3.1: Нюансы монтирования привязкой

**Разница в поведении `-v` и `--mount` при отсутствии источника на хосте:**

| Флаг | Если путь не существует на хосте |
| :--- | :--- |
| `-v /host/path:/container/path` | **Автоматически создаёт** директорию на хосте |
| `--mount type=bind,source=/host/path,target=/container/path` | **Ошибка** — путь должен существовать |

> **Рекомендация:** Используйте `--mount` для исключения случайного создания пустых директорий из-за опечаток.

### Сценарий 3.2: Распространение монтирования (Mount Propagation)

При монтировании директорий, которые сами являются точками монтирования на хосте, важно управлять тем, как изменения в структуре монтирования передаются между хостом и контейнером.

**Режимы распространения:**

| Режим | Описание |
| :--- | :--- |
| **`private`** | (По умолчанию) Монтирования внутри контейнера не видны на хосте, и наоборот. |
| **`rprivate`** | Рекурсивный `private`. |
| **`shared`** | Монтирования на хосте видны в контейнере, и наоборот. |
| **`rshared`** | Рекурсивный `shared`. |
| **`slave`** | Монтирования на хосте видны в контейнере, но не наоборот. |
| **`rslave`** | Рекурсивный `slave`. |

**Пример использования:**
```bash
docker run -d \
  --name my-container \
  --mount type=bind,source=/path,target=/container-path,bind-propagation=rshared \
  my-image
```
*Это необходимо, если вы монтируете `/proc` или другие системные директории, где монтирования могут происходить динамически.*

### Сценарий 3.3: Эфемерность контейнера без томов

1.  **Только чтение (`readonly`)**: Запрещает контейнеру изменять файлы на хосте.
    ```bash
    --mount type=bind,source=$(pwd)/config,target=/app/config,readonly
    ```
2.  **Оптимизация для macOS/Windows (`consistency`)**:
    - `consistent`: Полная синхронизация (по умолчанию, медленно).
    - `cached`: Хост является эталоном, контейнер может видеть изменения с задержкой (быстрее чтение).
    - `delegated`: Контейнер является эталоном, хост видит изменения с задержкой (быстрее запись).
3.  **Ограничения файловой системы**:
    - `noexec`: Запрет на выполнение бинарных файлов в примонтированном томе.
    - `nosuid`: Игнорирование set-user-identifier битов.
    - `nodev`: Запрет на интерпретацию специальных символьных или блочных устройств.

### Сценарий 3.2: Эфемерность контейнера без томов

Для понимания важности томов — пример с потерей данных:

```bash
# Запуск контейнера без volume
docker run -d --name temp-postgres \
  -e POSTGRES_PASSWORD=secret \
  postgres:14

# Подключаемся и создаём таблицу
docker exec -it temp-postgres psql -U postgres -c "CREATE TABLE tasks (id SERIAL PRIMARY KEY, description TEXT);"
docker exec -it temp-postgres psql -U postgres -c "INSERT INTO tasks (description) VALUES ('Finish work'), ('Have fun');"

# Удаляем контейнер
docker rm -f temp-postgres

# Пересоздаём контейнер без volume
docker run -d --name temp-postgres-2 \
  -e POSTGRES_PASSWORD=secret \
  postgres:14

# Проверяем — таблица tasks больше не существует
docker exec -it temp-postgres-2 psql -U postgres -c "SELECT * FROM tasks;"
# → Ошибка: relation "tasks" does not exist
```

*Без volume все данные хранятся в записываемом слое контейнера и удаляются вместе с ним. Это демонстрирует необходимость использования томов для персистентного хранения.*

### Сценарий 4: Хранение временных файлов (tmpfs)

```bash
docker run -d --name nginx-cache \
  --mount type=tmpfs,target=/var/cache/nginx \
  nginx:latest
```

*Кеш Nginx будет храниться в оперативной памяти, что ускорит работу и не будет "захламлять" диск.*

### Сценарий 5: Резервное копирование и восстановление тома

1. **Создание бэкапа** (том `my-app-data` архивируется в `backup.tar.gz`):

    ```bash
    docker run --rm \
      --mount type=volume,source=my-app-data,target=/data,readonly \
      --mount type=bind,source=$(pwd),target=/backup \
      alpine \
      tar -czvf /backup/backup.tar.gz -C /data .
    ```

2. **Восстановление из бэкапа** (в новый том `my-app-data-restored`):

    ```bash
    docker run --rm \
      --mount type=bind,source=$(pwd)/backup.tar.gz,target=/backup.tar.gz,readonly \
      --mount type=volume,source=my-app-data-restored,target=/data \
      alpine \
      tar -xzvf /backup.tar.gz -C /data
    ```

### Сценарий 6: Диагностика через docker inspect

Для просмотра деталей о точках монтирования и путях на хосте используйте `docker inspect`:

```bash
docker inspect <container_name_or_id> | grep -A 20 '"Mounts"'
```

**Пример вывода:**

```json
"Mounts": [
  {
    "Type": "volume",
    "Name": "postgres-db-data",
    "Source": "/var/lib/docker/volumes/postgres-db-data/_data",
    "Destination": "/var/lib/postgresql/data",
    "Driver": "local",
    "Mode": "z",
    "RW": true,
    "Propagation": ""
  }
]
```

Также можно посмотреть на процесс контейнера через `/proc`:

```bash
# Найти PID процесса контейнера
docker inspect --format '{{.State.Pid}}' <container>

# Посмотреть mount namespace процесса
ls -l /proc/<PID>/ns/mnt

# Просмотреть смонтированные файловые системы из perspective контейнера
docker exec <container> mount
```

**Служебные файлы, автоматически создаваемые Docker:**

При запуске контейнера Docker автоматически монтирует три служебных файла в `/etc` для работы сети:

| Файл | Назначение |
| :--- | :--- |
| `/etc/hostname` | Имя хоста контейнера (задаётся через `--hostname` или `--name`) |
| `/etc/hosts` | Список хостов в той же сети (добавляются через `--link` или `--add-host`) |
| `/etc/resolv.conf` | DNS-серверы (по умолчанию `127.0.0.11` — встроенный DNS Docker) |

Эти файлы хранятся в специальной временной файловой системе в памяти и создаются индивидуально для каждого контейнера.

### Сценарий 7: Устранение проблем

**Проблема:** Не удается удалить том (`docker volume rm`) или размонтировать директорию, так как «target is busy» или «volume is in use».

**Решение:**

1. **Найти контейнеры, использующие том:**

   ```bash
   docker ps -a --filter volume=my-app-data
   ```

2. **Найти процессы на хосте, удерживающие файлы в томе:**
   Если контейнеры остановлены, но том все равно занят (например, при использовании NFS или внешних драйверов), используйте `lsof`:

   ```bash
   # Путь к данным тома можно узнать через docker volume inspect
   sudo lsof +D /var/lib/docker/volumes/my-app-data/_data
   ```

Подробнее о диагностике открытых файлов см. в [`lsof` — список открытых файлов](../../Linux/Diagnostics/Processes/lsof.md).

## Дополнительная информация

### Интеграция с `docker-compose.yml`

Определение томов и монтирований в `docker-compose.yml` — стандарт индустрии.

```yaml
version: '3.8'

services:
  db:
    image: postgres:14
    environment:
      - POSTGRES_PASSWORD=mysecretpassword
    # Используем именованный том
    volumes:
      - db-data:/var/lib/postgresql/data

  web:
    image: node:18-alpine
    # Используем bind mount для кода
    volumes:
      - .:/app

# Объявляем том на верхнем уровне для централизованного управления
volumes:
  db-data:
    driver: local # Драйвер по умолчанию
```

### Драйверы томов (Volume Drivers)

Docker позволяет использовать **драйверы томов** для хранения данных не только на локальном хосте, но и на внешних системах, таких как NFS, или в облачных хранилищах (AWS EBS, GCP Persistent Disk). Это настраивается при создании тома или в секции `volumes` в `docker-compose.yml`.

#### Пример: Монтирование NFS как тома Docker

Это позволяет контейнерам на разных хостах использовать одну и ту же сетевую папку:

```bash
docker volume create --driver local \
  --opt type=nfs \
  --opt o=addr=192.168.1.10,rw,nfsvers=4 \
  --opt device=:/export/shared_data \
  nfs-shared-vol
```

В `docker-compose.yml`:

```yaml
volumes:
  nfs-data:
    driver: local
    driver_opts:
      type: nfs
      o: addr=192.168.1.10,rw,nfsvers=4
      device: ":/export/shared_data"
```

### Сравнение Docker Volumes и Kubernetes Volumes

Docker-тома и тома Kubernetes решают одну задачу — персистентное хранение данных для контейнеров — но на разных уровнях абстракции:

| Характеристика | Docker Volume | Kubernetes Volume |
| :--- | :--- | :--- |
| **Управление** | Docker Engine (локальный хост) | Kubernetes API (кластер) |
| **Жизненный цикл** | Переживает удаление контейнера | Зависит от типа: эфемерные — с подом, персистентные (PVC) — независимо |
| **Масштаб** | Один хост (или swarm-кластер с overlay driver) | Многоузловой кластер, абстракция от физической инфраструктуры |
| **Типы хранилищ** | `local`, NFS, облачные диски (через drivers) | `emptyDir`, `hostPath`, `configMap`, `secret`, `persistentVolumeClaim`, `projected` и др. |
| **Персистентность** | Всегда персистентны | Зависит от типа: `emptyDir` — эфемерный, `PVC` — персистентный |
| **Совместное использование** | Между контейнерами на одном хосте | Между подами (через RWX PVC, ReadWriteMany) |
| **Провайдингом** | Ручной (`docker volume create`) | Static provisioning или Dynamic (через StorageClass + CSI) |

**Ключевое отличие:** Docker volume — это конкретный ресурс хранения на хосте, управляемый демоном Docker. Kubernetes volume — абстракция, которая может указывать на множество бэкендов (локальный диск, NFS, облачные хранилища, Ceph, Longhorn) через единый API. Kubernetes PVC запрашивает хранилище декларативно, без привязки к конкретной ноде или технологии.

> **См. также:** [Тома в Kubernetes](../../Kubernetes/Base/Pod/volume_types/volume_types.md), [PV и PVC](../../Kubernetes/Storage/pv_and_pvc.md)

### Производительность и безопасность

- **Производительность**: Для I/O-интенсивных нагрузок (БД, логирование) всегда используйте volumes — см. [Драйвер хранения OverlayFS](./docker_overlayfs.md) для понимания работы CoW.
- **Безопасность**: Риски `bind mounts` и управление правами доступа рассмотрены в [Укреплении безопасности контейнеров](../Docker_security/container_hardening.md).
- **Шифрование**: Подходы к защите данных "на покое" (at rest) описаны в [Шифровании томов](./volume_encryption.md).
