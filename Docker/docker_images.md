## Что такое образ Docker?

**Образ (Image)** — это неизменяемый (immutable) шаблон, состоящий из слоев и содержащий все необходимое для запуска приложения.

### Концепция слоев (Layers)

Образ Docker состоит из набора слоев, которые накладываются друг на друга. Каждый слой представляет собой результат выполнения одной из команд в `Dockerfile` (например, `RUN`, `COPY`, `ADD`), которая изменяет файловую систему.

- **Неизменяемость (Read-Only)**: Все слои образа, кроме самого верхнего, являются неизменяемыми (read-only). Они кэшируются и могут переиспользоваться между разными образами, что экономит место и ускоряет сборку.
- **Наложение**: Слои образуют единую файловую систему благодаря технологии **OverlayFS**. Если файл существует в нескольких слоях, будет видна версия из самого верхнего слоя. Если файл удаляется в верхнем слое, он просто помечается как удаленный, но продолжает существовать в нижних слоях.
- **Слой контейнера (Writable Layer)**: Когда из образа запускается контейнер, поверх всех слоев образа добавляется еще один, тонкий **записываемый слой (writable layer)**. Все изменения, происходящие в работающем контейнере (создание, изменение, удаление файлов), записываются именно в этот слой.

Эта архитектура позволяет:

1.  **Экономить место**: Десятки контейнеров, запущенных из одного образа, переиспользуют общие слои, и для каждого создается лишь небольшой уникальный записываемый слой.
2.  **Обеспечивать изоляцию**: Изменения в одном контейнере не затрагивают ни образ, ни другие контейнеры.
3.  **Быстро запускать контейнеры**: Не нужно копировать всю файловую систему; достаточно создать новый записываемый слой.

Команда `docker history <имя_образа>` позволяет увидеть все слои, из которых состоит образ.

Подробное определение и ключевое отличие образа от контейнера с аналогией "Класс -> Объект" находится в документе **[Компоненты Docker](./docker_components.md#образ-и-контейнер)**.

## Жизненный цикл образа: основные команды

| Команда | Описание |
| :--- | :--- |
| `docker build -t <имя образа>:<тег> .` | Собирает образ из [`Dockerfile`](./dockerfile.md) в текущей директории. |
| `docker images` | Показывает все образы, имеющиеся на хосте. |
| `docker pull <имя>:<тег>` | Скачивает образ из [registry](./docker_registries.md) (например, Docker Hub). |
| `docker push <имя>:<тег>` | Загружает образ в [registry](./docker_registries.md). |
| `docker rmi <имя>:<тег>` | Удаляет образ. |
| `docker tag <исходный> <целевой>` | Создает новый тег (алиас) для существующего образа. |
| `docker history <имя>:<тег>` | Показывает слои, из которых состоит образ, и команды их создания. |

### `docker commit`: анти-паттерн

Команда `docker commit <контейнер> <новый_образ>` создает образ из текущего состояния контейнера. **Это считается плохой практикой, потому что:**

- **Нарушает воспроизводимость:** Невозможно понять, как образ был создан, в отличие от `Dockerfile`.
- **Раздувает образ:** Включает в себя временные файлы, логи и другие артефакты.
- **Скрывает историю:** Заменяет понятную историю слоев одной командой `commit`.

**Используйте `Dockerfile` для всех сборок.**

### Объединение слоев (`--squash`)

Флаг `docker build --squash` объединяет все слои, созданные в `Dockerfile`, в один новый слой.

- **Плюс:** Может незначительно уменьшить размер финального образа за счет удаления неиспользуемых файлов из промежуточных слоев.
- **Минус:** Уничтожает кэш для объединенных слоев. Если базовый образ остается неизменным, он будет по-прежнему кэшироваться, но любые изменения в `Dockerfile` приведут к повторной сборке всех объединенных слоев, что замедляет итеративные сборки.

### Схлопывание слоев с помощью `docker-squash`

Встроенный флаг `docker build --squash` имеет существенный недостаток: он уничтожает весь кэш слоев. Более гибкой и мощной альтернативой является внешняя утилита **`docker-squash`**.

Она позволяет "схлопнуть" уже собранный образ, объединяя только нужные слои и сохраняя базовые слои нетронутыми. Это позволяет уменьшить размер образа, удалив временные файлы (например, кэш `apt` или `npm`), не жертвуя при этом кэшем базового образа.

1.  **Установка:**

    ```bash
    pip install docker-squash==1.2.2
    ```
2.  **Использование:**

    Утилита выгружает образ, схлопывает слои и загружает его обратно в Docker.
    ```bash
    # Схлопнуть последние 2 слоя
    docker-squash -f 2 my-image:1.1.0 -t my-image:squashed

    # Схлопнуть все слои, начиная с определенного (ID слоя можно взять из `docker history`)
    docker-squash -from 5a5295c74599 my-image:1.1.0 -t my-image:squashed
    ```

**Преимущества перед `docker build --squash`:**

*   **Сохранение кэша:** Не затрагивает базовые слои, позволяя Docker переиспользовать их при последующих сборках.
*   **Гибкость:** Позволяет точно указать, какие слои нужно объединить.
*   **Работа с существующими образами:** Можно оптимизировать образы, даже не имея доступа к их `Dockerfile`.

### Реверс-инжиниринг образов

**Внимание:** Это метод "последней надежды", если `Dockerfile` утерян безвозвратно, а не стандартная практика.

Эти утилиты анализируют слои образа и генерируют `Dockerfile`, который мог бы его создать. Они запускаются как Docker-контейнеры и требуют доступа к Docker-сокету хоста.

**Важно:** Оба представленных ниже инструмента не обновлялись много лет и **не рекомендуются к использованию**. Они могут быть несовместимы с последними версиями Docker, а их образы могут быть удалены из Docker Hub. Используйте их с крайней осторожностью и только в исследовательских целях.

- **[dduvnjak/dockerfile-from-image](https://github.com/dduvnjak/dockerfile-from-image)**

  ```sh
  # Образ не обновлялся с 2018 года
  sudo docker run -v /var/run/docker.sock:/var/run/docker.sock --rm dduvnjak/dockerfile-from-image:1.0 <IMAGE_ID>
  ```

- **[laniksj/dfimage](https://github.com/LanikSJ/dfimage)**

  ```sh
  # Образ не обновлялся с 2021 года
  sudo docker run -v /var/run/docker.sock:/var/run/docker.sock --rm laniksj/dfimage:0.1.0 <IMAGE_ID>
  ```

### Многоархитектурные образы (Multi-Arch)

Современные CI/CD-системы позволяют собирать образы, которые могут работать на разных архитектурах процессоров (например, `amd64` и `arm64`). Это достигается с помощью `docker buildx`.

**Пример сборки:**
```sh
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t my-app:1.1.0 \
  --push .
```
Docker-демон на хосте автоматически выберет и запустит версию образа, соответствующую его архитектуре.

Нужно понимать, действительно ли образ поддерживает несколько архитектур, и здесь помогает `docker manifest`. Команда `docker manifest` позволяет инспектировать и управлять мультиархитектурными образами.

С её помощью можно точно увидеть, под какие платформы собран образ, например, `AMD64` для облачных серверов и `ARM64` для edge-устройств, всё это под одним тегом. Это простой способ убедиться, что образ, который вы тянете, будет стабильно работать в разных окружениях.

Это особенно важно для гибридных деплоев. Например, ваш бэкенд крутится в облаке на `AMD64`, а edge-шлюзы или IoT-устройства работают на `ARM`.

Проверяя манифест, вы гарантируете, что одна и та же версия контейнера будет корректно работать везде, без необходимости вручную собирать и тегировать отдельные образы.

Для команд, которые доставляют приложения на разнородное железо, использование `docker manifest` – простой способ избежать ситуации, когда работает на одной машине, но не работает на другой.

## Подписание образов и безопасность

Для обеспечения целостности и аутентичности образов используется механизм цифровых подписей. Это позволяет гарантировать, что образ не был изменен с момента его создания доверенным издателем.

Подробнее о механизмах подписи, таких как **Docker Content Trust** и **Cosign**, можно прочитать в руководстве по [безопасности Docker](./docker_security.md).
