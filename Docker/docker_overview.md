# Обзор Docker — платформа контейнеризации

**Актуально для:** Docker Engine 29.x (актуальный релиз — 29.8.x, сентябрь 2026). Docker Engine 28.x и ранее достигли EOL (май 2026) и не получают исправлений безопасности.

## Определения

- **Docker:** Платформа для разработки, доставки и запуска приложений в контейнерах. Использует механизмы изоляции ядра Linux для создания легковесных, переносимых окружений.
- **Контейнер (Container):** Изолированный экземпляр образа — обычный процесс хоста, запущенный в собственных namespaces и cgroups. Обычно выполняет один процесс (точку входа), но может включать и несколько (через init-системы вроде `tini` или `supervisord`). Включает код, среду выполнения, системные библиотеки и настройки.
- **Образ (Image):** Неизменяемый многослойный шаблон, служащий чертежом для создания контейнеров. Каждый слой соответствует инструкции в `Dockerfile` и реализуется через механизм Copy-on-Write.
- **Реестр (Registry):** Сервис для хранения и распространения образов (Docker Hub, Harbor, GitHub Packages).
- **Docker Engine:** Основной программный компонент, работающий по клиент-серверной архитектуре (демон `dockerd`, REST API и CLI).
- **containerd:** Высокоуровневый демон управления контейнерами (проект CNCF): скачивание образов, snapshot-слои, жизненный цикл контейнеров. Сетевое взаимодействие в Docker реализует `dockerd` (libnetwork), а не containerd.

## Основные концепции

### Решение проблемы зависимостей и изоляция

Docker упаковывает приложение вместе с его окружением, устраняя конфликты версий библиотек между разными сервисами и хост-системой. Изоляция обеспечивается на уровне:
1. **Внутренней среды:** Все зависимости фиксированы внутри образа.
2. **Внешних ресурсов:** Доступ к сети, портам и файловой системе строго контролируется через конфигурацию запуска.

### Ключевые преимущества

1.  **Согласованность (Consistency):** Гарантия идентичного поведения приложения на всех этапах жизненного цикла (разработка, тестирование, продакшн).
2.  **Эффективность ресурсов:** Контейнеры используют общее ядро ОС, запускаются за миллисекунды и потребляют значительно меньше ресурсов по сравнению с виртуальными машинами.
3.  **Изоляция:** Каждый контейнер работает в собственном пространстве имён, что предотвращает влияние процессов друг на друга. **Важно:** namespaces и cgroups сами по себе не являются границей безопасности (security boundary) — для защиты от злонамеренного кода требуются дополнительные механизмы (Linux Capabilities, seccomp, AppArmor). Подробнее см. **[Изоляция в Linux: Namespaces и Cgroups](./Concepts/linux_isolation.md)**.
4.  **Масштабируемость:** Малый размер образов и высокая скорость запуска позволяют динамически изменять количество экземпляров приложения под нагрузку.

### Архитектура и компоненты

Современная архитектура Docker модульная и соответствует стандартам **OCI (Open Container Initiative)**.

```
docker CLI ←[REST API]→ dockerd ←[gRPC]→ containerd → runc/crun → контейнер
                            ↓
                         buildkitd (сборка образов)
```

- **Docker CLI:** Интерфейс командной строки для взаимодействия с пользователем.
- **dockerd (Docker Daemon):** Обеспечивает высокоуровневое управление (сети, тома, API), делегируя работу с процессами нижестоящим компонентам. Начиная с 29.x, dockerd использует встроенный containerd, если системный сервис containerd не сконфигурирован и не установлен (moby#53388).
- **containerd:** Проект CNCF, управляющий образами и жизненным циклом контейнеров. Начиная с Docker 29.0, **containerd image store** используется по умолчанию при свежей установке, что обеспечивает нативную совместимость с Kubernetes. При обновлении с более ранних версий демон продолжает использовать классические драйверы (overlay2) до ручного включения; store недоступен при включённом `userns-remap` (moby#47377). Docker 29.x поставляется со встроенным containerd 2.3.x.
- **runc / crun:** Низкоуровневые рантаймы, создающие пространства имён (namespaces) и контрольные группы (cgroups). `crun` (на языке C) является более быстрым и эффективным аналогом стандартного `runc`. Wasm-рантаймы (wasmedge, wasmtime) подключаются опционально через containerd/runwasi, а не входят в основной цепочку.
- **BuildKit / Buildx:** Современный движок сборки (отдельный демон `buildkitd`), поддерживающий параллельное выполнение стадий, расширенное кэширование и мультиплатформенные сборки.

### Технологии изоляции ядра Linux

Функционирование контейнеров базируется на фундаментальных механизмах ядра:

1.  **Namespaces (Пространства имен):** Виртуализируют системные ресурсы для процесса (`pid`, `net`, `mnt`, `ipc`, `uts`, `user`, а в современных ядрах также `cgroup` и `time`). Полная таблица — в **[Изоляция в Linux: Namespaces и Cgroups](./Concepts/linux_isolation.md)**.
2.  **Cgroups v2 (Контрольные группы):** Ограничивают потребление ресурсов (CPU, RAM, I/O).
    *   **Типы CPU-лимитов:** `--cpus` и `--cpu-quota` задают **жёсткий** лимит через CFS bandwidth control (`cpu.max` в cgroups v2): при превышении квоты процесс приостанавливается (throttling) до конца периода. `--cpu-shares` задаёт **относительный вес** (`cpu.weight`) и действует только при конкуренции за CPU. Это разные механизмы, не путайте их. Подробнее см. **[Ограничение ресурсов контейнеров](./Docker_security/resource_limits.md)**.
    *   **Проблема видимости ядер:** Утилиты `lscpu` и файл `/proc/cpuinfo` показывают данные хостовой системы (не изолированы), а `nproc` учитывает маску CPU affinity (отражает `--cpuset-cpus`). Приложения, читающие `/proc/cpuinfo`, могут создать количество потоков по числу ядер хоста (например, 64), имея лимит в 2 ядра, что приведёт к деградации производительности. Современные рантаймы (JVM 8u191+, Go) читают лимиты cgroups корректно.
3.  **Union File Systems (OverlayFS):** Объединяют слои образа в единую файловую систему. Реализуют механизм **Copy-on-Write (CoW)** — данные копируются в записываемый слой контейнера только при необходимости их модификации.

### Слоеная файловая система и хранение

Образы Docker состоят из неизменяемых слоев (Read-Only). При запуске контейнера сверху добавляется записываемый слой (Writable Layer).
- **Эффективность:** Слои переиспользуются между разными образами, что экономит место на диске.
- **Containerd image store (Docker 29.0+):** При использовании нового хранилища слои управляются snapshotter'ами containerd (по умолчанию `overlayfs`), что добавляет поддержку мультиплатформенных образов и аттестаций. Существующие образы overlay2 при переходе остаются на диске, но становятся невидимыми до возврата на overlay2.
- **Lazy Pulling:** «Ленивая» загрузка образов через containerd snapshotters (stargz, Nydus) позволяет запускать контейнер до того, как весь образ будет физически скачан — слои загружаются по мере первого обращения.

## Предварительные требования

- **ОС:** Linux с ядром 5.10+ (рекомендуется 6.1+ для стабильной работы cgroups v2 и PSI). RHEL/CentOS 9+, Debian 12+, Ubuntu 22.04+.
- **Docker Engine:** 29.x. Установка и настройка см. **[Установка Docker на Ubuntu](./docker_install_ubuntu.md)**.
- **cgroups:** Рекомендуется cgroups v2. Проверка: `stat -fc %T /sys/fs/cgroup/` → `cgroup2fs`.
- **macOS/Windows:** Docker Desktop или альтернативы (Colima, OrbStack — см. ниже).

**Валидация окружения:**
```bash
docker version --format '{{.Server.Version}}'
# → 29.8.0

docker info --format '{{.Driver}} {{.CgroupDriver}}'
# → overlay2 systemd   (или containerd-снапшоттер при включённом image store)
```

## Практические сценарии

### Анализ процесса запуска (docker run)

При выполнении `docker run -it --rm ubuntu:24.04 bash` происходят следующие этапы:
1. **Pull:** Поиск образа локально или скачивание из реестра (через containerd).
2. **Create:** Создание файловой системы контейнера (snapshot-слои через containerd).
3. **Network:** Настройка сетевого стека (IP, интерфейсы, маршруты) — dockerd/libnetwork.
4. **Start:** Запуск процесса через `runc` внутри изолированных пространств имён.

### Сравнение с виртуальными машинами

| Характеристика | Контейнеры | Виртуальные машины |
|:---|:---|:---|
| **Абстракция** | Уровень ОС (Shared Kernel) | Аппаратный уровень (Hypervisor) |
| **Изоляция** | Уровень процессов (Namespaces) | Полная (Гостевая ОС) |
| **Вес образа** | Десятки/сотни МБ | Гигабайты |
| **Накладные расходы** | Минимальные | Значительные (ресурсы на гостевую ОС) |

**Когда использовать:**
- **Контейнеры:** микросервисы, CI/CD, высокая плотность размещения приложений.
- **ВМ:** полная изоляция на уровне ядра, запуск приложений на другой ОС, работа с монолитами, требующими прямого доступа к ядру.

### Рабочий процесс сборки и доставки

1.  **Написание `Dockerfile`:** Описание желаемого состояния образа.
2.  **Сборка (Build):** Использование `docker buildx` для создания многослойного артефакта.
3.  **Сканирование (Scan):** Проверка образа на уязвимости перед публикацией (Docker Scout или Trivy).
4.  **Публикация (Push):** Отправка образа в централизованный реестр.
5.  **Развертывание (Run):** Запуск контейнеров на целевых хостах.

## Устранение неполадок

| Симптом | Причина | Решение |
|:---|:---|:---|
| `docker: command not found` | CLI не установлен или не в `PATH` | Установка см. **[docker_install_ubuntu.md](./docker_install_ubuntu.md)** |
| `permission denied ... /var/run/docker.sock` | Пользователь не в группе `docker` | `sudo usermod -aG docker $USER` и перелогин; см. **[Docker_security/overview.md](./Docker_security/overview.md)** |
| Контейнеры не резолвят DNS | Конфликт с `systemd-resolved` | Явный DNS в `daemon.json` или проброс `/etc/resolv.conf`; см. **[docker_install_ubuntu.md](./docker_install_ubuntu.md)** |
| CPU-лимит не ограничивает нагрузку | Путаница `--cpu-shares` (вес) и `--cpus` (квота) | Используйте `--cpus` для жёсткого лимита; см. **[resource_limits.md](./Docker_security/resource_limits.md)** |
| Образы «пропали» после обновления до 29.x | Переход на containerd image store: образы overlay2 скрыты, но не удалены | Вернуться на overlay2 или перезалить образы в реестр; см. **[docker_daemon_config.md](./docker_daemon_config.md)** |
| `docker info` показывает `Storage Driver: overlay2` после обновления | При обновлении store не мигрирует автоматически — это ожидаемое поведение | Для миграции включите containerd image store вручную |

## Дополнительная информация

### Инструменты и альтернативы

- **Docker Desktop:** Полноценная среда для разработки с поддержкой K8s и Docker Scout. Коммерческий продукт: для компаний крупнее порога (более 250 сотрудников или оборот более $10M) требуется платная подписка.
- **Rootless Docker:** Режим запуска без привилегий суперпользователя (повышение безопасности).
- **Docker Scout:** Система анализа безопасности, SBOM и поиска уязвимостей (Docker Desktop и CLI-плагин). См. **[vulnerability_scanning.md](./Docker_security/vulnerability_scanning.md)**.
- **Colima:** Лёгкий CLI-рантайм для macOS и Linux (на базе Lima VM), без GUI.
- **OrbStack:** Нативное macOS-приложение (только macOS), быстрая замена Docker Desktop с Rosetta-эмуляцией x86.
- **Podman / Buildah / Skopeo:** Daemonless-альтернативы Docker CLI. См. **[alternative_runtimes_and_tools.md](./alternative_runtimes_and_tools.md)**.
- **TUI/GUI-инструменты** (lazydocker, ctop, Portainer): см. **[docker_tools.md](./docker_tools.md)**.
