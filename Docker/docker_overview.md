# Обзор Docker

## Определения

- **Контейнер (Container)**: Изолированный процесс (или группа процессов), работающий в собственном окружении, отделенном от основной операционной системы. Важно понимать, что **процессы в контейнере — это обычные процессы хост-системы**. Docker лишь создает для них иллюзию работы в отдельной машине.
- **Образ (Image)**: Неизменяемый (immutable) шаблон, который содержит все необходимое для запуска приложения: код, библиотеки, переменные окружения и конфигурационные файлы. Образы состоят из слоев, доступных только для чтения.
- **Слоеная файловая система (Layered File System)**: Механизм, позволяющий Docker эффективно хранить образы и управлять ими. Docker использует драйверы хранения, такие как **[OverlayFS](./Docker_fs/docker_overlayfs.md)**, чтобы "накладывать" файловую систему контейнера поверх файловой системы образа. Этот механизм основан на принципе **[Copy-on-Write (CoW)](../Linux/Core/processes/overview.md#copy-on-write-cow)**.
- **Реестр (Registry)**: Сервис для хранения и распространения образов Docker.
- **Namespaces (пространства имен)**: Механизм ядра Linux, который создает для процесса изолированное представление о системных ресурсах.
- **Control Groups (cgroups)**: Механизм ядра, который ограничивает и учитывает потребление ресурсов (CPU, память, IO и т.д.) группой процессов.
- **Docker Daemon (`dockerd`)**: Высокоуровневый компонент. Предоставляет `REST API` для клиентов, управляет образами, сетями, томами и передает команды на управление контейнерами демону `containerd`.
- **`containerd`**: Универсальный демон-менеджер контейнеров. Принимает команды от `dockerd` по `gRPC`, управляет полным жизненным циклом контейнеров и вызывает низкоуровневый OCI-runtime для их запуска. Является проектом CNCF.
- **`runc`**: Низкоуровневая среда выполнения (runtime). Эталонная реализация спецификации **OCI**, которая непосредственно взаимодействует с ядром Linux для создания `namespaces` и `cgroups`.
- **Open Container Initiative (OCI) spec**: Определяет стандартизированный формат образа контейнера и его среды выполнения (runtime). Это позволяет различным инструментам (Docker, Podman) работать с одними и теми же образами.
- **Container Runtime Interface (CRI)**: Это API, который позволяет `kubelet` (агенту Kubernetes) взаимодействовать с различными средами выполнения контейнеров (`containerd`, `CRI-O`).

## Основные понятия

### Образ и Контейнер

- **Образ (Image)** — это шаблон.
- **Контейнер (Container)** — это запущенный экземпляр образа. При запуске Docker добавляет поверх неизменяемых слоев образа один **записываемый слой (writable layer)**, где хранятся все изменения.

> **Что происходит с файлами, созданными в контейнере?**
>
> Любые файлы, созданные или измененные внутри запущенного контейнера, сохраняются в его записываемом слое. Если остановить контейнер (`docker stop`), этот слой и все данные в нем **сохраняются**. При повторном запуске (`docker start`) контейнер продолжит работу с тем же состоянием файловой системы. Данные теряются только при полном удалении контейнера (`docker rm`).

#### Ключевое отличие от виртуальных машин

Контейнеры и виртуальные машины решают схожую задачу — изоляцию и упаковку приложений, — но достигают её разными техническими средствами.

> **Подробнее:** [Виртуализация и изоляция в Linux](../Linux/Virtualization/virtualization_overview.md#сравнение-контейнеры-vs-вм)

##### Модель изоляции

Виртуальная машина запускает полноценную гостевую операционную систему поверх гипервизора. У каждой ВМ — собственное ядро, виртуализированное оборудование и независимый стек драйверов. Гипервизор создаёт сильную границу между гостями и хостом, имитируя аппаратный слой.

Контейнер использует виртуализацию на уровне ОС: процессы изолируются пространствами имён и ограничиваются cgroups, а файловая система строится с помощью копирующих слоёв. Ядро хоста общее для всех контейнеров; изоляция реализуется в пределах одной ОС.

##### Ключевые различия

| Критерий | Контейнеры | Виртуальные машины |
| :--- | :--- | :--- |
| **Уровень изоляции** | Процессная, уровнем ядра | Аппаратная, через гипервизор |
| **Ядро ОС** | Общее с хостом | Собственное в каждой ВМ |
| **Время старта** | Секунды и меньше | Десятки секунд и минуты |
| **Плотность на хосте** | Высокая | Ниже из-за накладных расходов |
| **Образы** | Слойные OCI-образы | Монолитные диски (qcow2/vmdk) |
| **Совместимость** | Общая версия ядра | Любая гостевая ОС |
| **Обновления** | Обновляется образ/слои | Обновляется гостевая ОС |
| **Снимки** | Слойность/commit | Снапшоты диска/памяти |
| **Безопасность** | Усиленная конфигурацией ядра | Сильная граница гипервизора |

Из-за общего ядра **невозможно** запустить контейнер, созданный для одной ОС, на ядре другой. Например, Windows-контейнеры требуют системных вызовов ядра Windows NT, которых нет в ядре Linux.

##### Производительность и ресурсы

Контейнеры минимизируют накладные расходы на CPU и память, особенно при высокой плотности сервисов. Диск и сеть часто используют файловые драйверы copy-on-write и overlay, что ускоряет развёртывание и экономит место. ВМ дают стабильную производительность и более предсказуемую изоляцию NUMA/CPU pinning, что важно для нагрузок с жёсткими SLO и специализированных драйверов.

##### Безопасность

Контейнеры полагаются на механизмы ядра: namespaces, cgroups, seccomp, а также MAC-политики (AppArmor/SELinux) и rootless-режим. ВМ обеспечивают изоляцию через гипервизор и отдельное ядро, снижая риск уязвимостей ядра хоста. В облаках часто применяется комбинированный подход: контейнеры внутри ВМ для многоарендной безопасности.

##### Жизненный цикл и образы

Контейнерные образы воспроизводимы и кэшируемы по слоям, что ускоряет CI/CD. Версионирование и продвижение через registry упрощают откат. ВМ управляются через шаблоны “golden image”, снапшоты и конфигурацию гостя; миграция включает больше состояния (полная ОС, пакеты, конфиги).

##### Когда что выбирать

- **Контейнеры:** микросервисы, CI/CD, масштабирование, высокая плотность, быстрые релизы, неизменяемые образы.
- **Виртуальные машины:** смешанные ОС, наследованные монолиты, требовательные к изоляции и драйверам нагрузки, строгие границы безопасности.
- **Гибрид:** контейнеры внутри ВМ при многоарендности и регуляторных требованиях.

#### Слоеная файловая система: OverlayFS

- **Нижние слои (lowerdir):** Слои образа, доступны только для чтения.
- **Верхний слой (upperdir):** Записываемый слой контейнера. Все изменения (создание, изменение, удаление файлов) происходят здесь.
- **Результат (merged):** Виртуальное объединение всех слоев, которое видит процесс в контейнере.

Эта система позволяет эффективно хранить образы (общие слои переиспользуются) и мгновенно создавать контейнеры.

### Внутренняя структура образа (OCI Image Format)

Если сохранить образ с помощью команды `docker save my-image -o image.tar` и распаковать полученный архив, можно увидеть его внутреннее устройство, соответствующее спецификации OCI (Open Container Initiative).

- **`manifest.json`**: Основной файл манифеста. Содержит информацию об образе, включая ссылку на его конфигурационный файл и перечисление всех слоев.
- **`config.json`**: JSON-файл с метаданными образа. Здесь хранятся такие сведения, как:
  - Переменные окружения (`ENV`).
  - Рабочий каталог (`WORKDIR`).
  - Команда по умолчанию (`CMD`, `ENTRYPOINT`).
  - История создания слоев.
- **Каталог со слоями**: Набор каталогов с именами, соответствующими хэшам (`sha256:...`). Каждый такой каталог представляет собой один слой файловой системы и содержит:
  - `layer.tar`: Tar-архив с файлами и каталогами, добавленными в этом слое.
  - `json`: Дополнительные метаданные о слое.

**Важный нюанс:** не все инструкции `Dockerfile` создают слои (`layer.tar`).

- **Инструкции, создающие слои**: `RUN`, `COPY`, `ADD`. Они изменяют файловую систему, и эти изменения упаковываются в `layer.tar`.
- **Инструкции, изменяющие метаданные**: `ENV`, `WORKDIR`, `CMD`, `EXPOSE`, `ENTRYPOINT`. Они не создают новых файловых слоев, а лишь модифицируют `config.json` образа.

Это объясняет, почему слои с метаданными в выводе `docker history` имеют размер 0 байт — они не добавляют данных в файловую систему, а только обновляют конфигурацию. Понимание этой структуры помогает в отладке и оптимизации размеров образов.

#### Технологии изоляции: `namespaces` и `cgroups`

- **`namespaces`** отвечают за **изоляцию видимости**. Они создают для процесса иллюзию, что он работает в собственной, отдельной системе со своим деревом процессов, сетью и монтированиями.
- **`cgroups`** отвечают за **ограничение потребления**. Они позволяют установить лимиты на ресурсы (CPU, память, I/O), которые может использовать группа процессов.

Если `namespaces` говорят процессу: "Ты видишь только это", то `cgroups` говорят: "Ты можешь использовать только столько".

**Типы Namespaces:**

- **PID Namespace:** Изоляция процессов. Процесс внутри контейнера видит себя как PID 1.
- **Mount Namespace:** Изоляция файловой системы. У контейнера свой корневой каталог (`/`).
- **Network Namespace:** Изоляция сети. Свой сетевой стек, IP-адреса и порты.
- **UTS Namespace:** Изоляция имени хоста и домена (`hostname`).
- **IPC Namespace:** Изоляция межпроцессного взаимодействия (System V IPC, POSIX message queues).
- **User Namespace:** Изоляция ID пользователей и групп. Позволяет маппинг пользователя root в контейнере на обычного пользователя на хосте.
- **Cgroup Namespace:** Изоляция представления о cgroups.
- **Time Namespace:** Изоляция системного времени.

> Подробнее о том, как Docker использует эти механизмы, читайте в документе **[Изоляция процессов в Linux: cgroups и namespaces](./Concepts/linux_isolation.md)**.

#### Клиент-серверная архитектура

**`docker` (CLI)  <-[ `REST API` ]->  `dockerd` (демон)  <-[ `gRPC` ]->  `containerd`  ->  `runc`**

1. **Клиент (`docker` CLI) и Демон (`dockerd`):**
    - **Протокол:** `REST API`.
    - **Как:** Клиент `docker` отправляет HTTP-запросы на REST API, который слушает демон `dockerd`, по умолчанию через локальный Unix-сокет `/var/run/docker.sock`.

2. **Демон (`dockerd`) и `containerd`:**
    - **Протокол:** `gRPC`.
    - **Как:** `dockerd` для всех операций с жизненным циклом контейнеров обращается к `containerd` через другой Unix-сокет, обычно `/run/containerd/containerd.sock`.

Такое разделение повышает стабильность: перезапуск демона `dockerd` не останавливает уже запущенные контейнеры, так как ими продолжает управлять `containerd`.

## Практические сценарии

### Итоговый процесс запуска `docker run`

1. Пользователь выполняет `docker run ...`.
2. CLI `docker` отправляет `POST` запрос на `/containers/create` и `/containers/{id}/start` на `REST API` демона `dockerd`.
3. `dockerd` получает запрос, обрабатывает его и делает `gRPC` вызов к `containerd`.
4. `containerd` использует `runc` для создания и запуска контейнера с нужными `namespaces` и `cgroups`.
5. `runc` запускает процесс внутри контейнера.

#### Зачем это знать?

- **Отладка проблем:** Позволяет системно искать неисправности: проблема в `dockerd`, `containerd` или `runc`?
- **Оптимизация производительности:** Зная, что `containerd` отвечает за управление образами, можно точечно настраивать `snapshotter` для ускорения запуска.
- **Глубокий мониторинг:** Можно собирать метрики не только с `dockerd`, но и напрямую с `containerd`.
- **Безопасность:** Можно настраивать политики изоляции на уровне `runc` или использовать альтернативные OCI-среды выполнения.

#### Схема работы в Kubernetes

1. `kubelet` делает `gRPC` вызов через **CRI API** к демону (`containerd` или `CRI-O`).
2. CRI-совместимый демон принимает запрос.
3. Демон вызывает низкоуровневую, **OCI**-совместимую среду выполнения (`runc`, `crun`).
4. OCI-runtime создает контейнер.

## Дополнительная информация

### Docker Registry: Хранилище образов

- **[Docker Hub](./docker_registries.md):** Публичный реестр по умолчанию.
- Существуют и частные (private) решения, такие как Harbor, GitLab Container Registry или Nexus.

#### До контейнеров: `chroot`

До появления современных контейнерных технологий для изоляции файловой системы использовалась утилита `chroot` (change root). Она позволяла изменить корневой каталог для процесса, делая невозможным доступ к файлам за его пределами.

Однако у `chroot` были существенные ограничения:

- **Неполная изоляция:** Процесс все еще мог взаимодействовать с другими процессами, использовать тот же сетевой стек и не имел ограничений по ресурсам.
- **Только файловая система:** Изоляция касалась только видимости файлов, но не других системных ресурсов.
