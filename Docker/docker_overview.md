# Обзор Docker

## Определения

**Docker** — платформа для разработки, доставки и запуска приложений в контейнерах. Использует механизмы изоляции ядра Linux для создания легковесных, переносимых окружений.

**Ключевые компоненты:**

| Компонент | Описание |
| :--- | :--- |
| **Контейнер** | Изолированная среда выполнения. Часто реализуется как процесс с собственным окружением (namespaces + cgroups), но может быть и виртуальной машиной (VM-контейнеры, см. [Альтернативные среды](./alternative_runtimes_and_tools.md)) |
| **Образ (Image)** | Неизменяемый шаблон с кодом, библиотеками, зависимостями |
| **Реестр (Registry)** | Хранилище образов (Docker Hub, Harbor, GitLab Registry) |
| **Docker Daemon (`dockerd`)** | Демон, управляющий контейнерами, образами, сетями, томами |
| **`containerd`** | Демон жизненного цикла контейнеров (проект CNCF). С версии Docker 29.1 по умолчанию используется **containerd image store** для хранения слоев |
| **`runc`** | OCI (Open Container Initiative)-совместимый runtime для запуска контейнеров |
| **OCI spec** | Стандарт формата образа и среды выполнения (Open Container Initiative) |
| **CRI (Container Runtime Interface)** | API Kubernetes для взаимодействия с runtime (`containerd`, `CRI-O`) |

## Основные концепции

### Зависимости и окружение (Концептуальный фундамент)

Популярность Docker обусловлена его способностью решать проблему **зависимостей окружения**. Любое приложение имеет два типа зависимостей:

1. **Внутренние зависимости:** библиотеки (`.jar`, `.dll`, `.so`), которые можно упаковать вместе с приложением.
2. **Внешние зависимости:** компоненты, которые приложение ожидает найти в системе (специфическая версия JRE/Python, системные файлы типа `/etc/hosts`, порты, графический дисплей, сетевые интерфейсы).

**Проблемы без контейнеров:**
- **Отсутствие зависимости:** приложение падает, не найдя JVM или нужную библиотеку в `PATH`.
- **Неоднозначность:** в системе несколько IP-адресов или мониторов, и приложение выбирает не тот.
- **Конфликты:** два приложения требуют эксклюзивного доступа к одному порту или файлу.

**Принцип Docker — «Окружение внутри окружения»:**
Docker создает изолированный «замкнутый мир» внутри хостовой ОС. Мы явно определяем, какие внешние ресурсы (порты, файлы, сети) «пробрасываются» внутрь этого мира. Это устраняет неопределенность: приложение всегда видит ровно то окружение, которое ему необходимо для работы.

### Преимущества Docker (Почему Docker?)

Популярность Docker обусловлена решением четырех критических проблем разработки и эксплуатации:

1. **Воспроизводимость окружения (Environment Reproducibility):** устраняет проблему «на моей машине работает». Если контейнер запущен и протестирован в одной среде, он будет идентично работать в любой другой (dev, test, prod, cloud).
2. **Управление зависимостями (Dependency Management):** каждое приложение изолировано вместе со своими библиотеками и рантаймом. Это позволяет запускать на одном хосте приложения, требующие разных версий одной технологии (например, Python 2.7 и Python 3.11) без конфликтов.
3. **Переносимость (Portability):** контейнер — это самодостаточный юнит. Его можно легко перенести с локального ноутбука в облако (AWS, Azure, GCP) или на собственные серверы (on-premises) практически мгновенно.
4. **Версионный контроль и скриптование (Version Control):** конфигурация Docker описывается в текстовых файлах (`Dockerfile`, `docker-compose.yml`), которые можно хранить в Git. Это позволяет отслеживать изменения инфраструктуры так же, как и изменения кода.

### Образ и контейнер

- **Образ** — неизменяемый шаблон (read-only)
- **Контейнер** — запущенный экземпляр образа с записываемым слоем (writable layer)

**Жизненный цикл writable layer:**

- При остановке (`docker stop`) — данные сохраняются
- При перезапуске (`docker start`) — данные доступны
- При удалении (`docker rm`) — данные теряются (если не вынесены в volumes)

Подробнее: [Тома и хранение данных](./Docker_fs/docker_volumes.md)

### Контейнеры vs Виртуальные машины

Контейнеризация и виртуализация — два разных подхода к изоляции приложений. В то время как виртуальные машины (VM) виртуализируют аппаратное обеспечение (через гипервизор), контейнеры виртуализируют операционную систему на уровне ядра Linux (Namespaces и Cgroups).

Подробное сравнение Docker, системных контейнеров (LXC) и виртуальных машин (KVM/VirtualBox) приведено в едином источнике: **[Контейнеры vs Виртуальные машины: подробное сравнение](../Linux/Virtualization/virtualization_overview.md#выбор-технологии-контейнеры-vs-виртуальные-машины)**.

### Слоеная файловая система

Docker использует драйверы хранения (OverlayFS) для эффективной работы с образами:

- **lowerdir** — слои образа (read-only)
- **upperdir** — записываемый слой контейнера
- **merged** — объединенное представление

С версии 29.1 слои управляются через **containerd image store**, что обеспечивает унификацию с экосистемой Kubernetes, но может приводить к временному дублированию данных (хранение в сжатом и распакованном виде).

Подробнее: [OverlayFS в Docker](./Docker_fs/docker_overlayfs.md)

### Структура образа (OCI Format)

При сохранении образа (`docker save -o image.tar`) архив содержит:

- **`manifest.json`** — манифест образа со слоями
- **`config.json`** — метаданные (ENV, WORKDIR, CMD, ENTRYPOINT)
- **Слои (`sha256:.../layer.tar`)** — файловая система по слоям

**Инструкции Dockerfile:**

- Создают слои: `FROM`, `RUN`, `COPY`, `ADD`
- Изменяют метаданные: `LABEL`, `ENV`, `WORKDIR`, `CMD`, `EXPOSE`

Подробное описание каждой инструкции приведено в соответствующих SSoT-файлах (например, **[Базовый образ и Метаданные](./Dockerfile/Instructions/base_image_and_metadata.md)**). Для анализа состава слоев используйте [dive](./Dockerfile/dockerfile_optimization_tools.md).

### Технологии изоляции

**Namespaces** — изоляция видимости ресурсов:

- PID, Mount, Network, UTS, IPC, User, Cgroup, Time

**Cgroups** — ограничение потребления ресурсов:

- CPU, память, I/O, количество процессов

> **Изоляция по умолчанию:** процесс в контейнере не видит процессы, файловую систему, сеть хоста и других контейнеров (благодаря namespaces). Однако это **не является полноценной границей безопасности**. Для production используйте совместно с capabilities, seccomp, AppArmor/SELinux.

Подробнее: [Изоляция в Linux: Namespaces и Cgroups](./Concepts/linux_isolation.md)

### Архитектура Docker

```
docker CLI ←[REST API]→ dockerd ←[gRPC]→ containerd → runc → контейнер
```

| Компонент | Протокол | Описание |
| :--- | :--- | :--- |
| **CLI ↔ Daemon** | REST API (Unix-сокет `/var/run/docker.sock`) | Клиент отправляет команды |
| **Daemon ↔ containerd** | gRPC (Unix-сокет `/run/containerd/containerd.sock`) | Управление жизненным циклом и хранилищем образов (v29+) |
| **containerd ↔ runc** | OCI runtime spec | Запуск процесса контейнера |

**Сетевая фильтрация:**
Docker манипулирует правилами сетевого экрана через команды `iptables`. В современных дистрибутивах (Ubuntu 24.04+) эти команды транслируются в **nftables** через слой совместимости `iptables-nft`. Прямая поддержка nftables в Docker на данный момент ограничена.

**Преимущество разделения:** перезапуск `dockerd` не останавливает запущенные контейнеры.

## Практические сценарии

### Подробный разбор `docker run -it ubuntu /bin/bash`

Команда `docker run -it ubuntu /bin/bash` — типичный способ интерактивного подключения к контейнеру. Разберём по шагам, что происходит:

1. **Проверка локального образа** — если `ubuntu` отсутствует локально, Docker загружает его из реестра по умолчанию (Docker Hub). Эквивалентно предварительному `docker pull ubuntu`
2. **Создание контейнера** — `dockerd` создаёт новый контейнер (аналог `docker container create`)
3. **Выделение файловой системы** — на локальном диске создаются файлы контейнера на основе слоёв образа
4. **Настройка сети** — создаётся сетевой интерфейс, контейнер подключается к сети по умолчанию (`bridge`), получает IP-адрес
5. **Запуск процесса** — стартует `/bin/bash` с интерактивным терминалом

**Флаги:**

- `-i` (`--interactive`) — держит STDIN (standard input) открытым даже без подключения
- `-t` (`--tty`) — выделяет псевдо-TTY (teleTYpewriter), позволяя работать с терминалом полноценно

**Что происходит при выходе:**

- `exit` или `Ctrl+D` — процесс bash завершается, контейнер останавливается
- `Ctrl+P`, `Ctrl+Q` — отключение от контейнера без остановки (контейнер продолжает работать)
- После остановки контейнер **не удаляется автоматически** — его можно запустить снова (`docker start`) или удалить (`docker rm`)

> **Важно:** все изменения, внесённые внутри контейнера в runtime (установка пакетов, правка конфигов), сохраняются в writable layer. При удалении контейнера эти данные теряются.

### Лучшие практики: не изменять контейнеры, а пересобирать образы

Изменение работающего контейнера и последующий коммит (`docker commit`) — антипаттерн.

Подробный разбор причин, сценариев использования и правильных подходов см. в разделе: **[Docker Commit — создание образа из контейнера](./Docker_fs/docker_commit.md)**.

### Процесс запуска `docker run` (технический)

1. CLI (Command Line Interface) отправляет `POST /containers/create` и `/start` на REST API `dockerd`
2. `dockerd` делает gRPC-вызов к `containerd`
3. `containerd` вызывает `runc` для создания namespaces и cgroups
4. `runc` запускает процесс контейнера

**Зачем это знать:**

- **Отладка:** локализация проблем (dockerd, containerd, runc)
- **Мониторинг:** метрики с `dockerd` и `containerd`
- **Безопасность:** настройка isolation на уровне runc

### Работа в Kubernetes

```
kubelet ←[CRI API/gRPC]→ containerd/CRI-O ←[OCI]→ runc/crun → контейнер
```

`kubelet` взаимодействует с runtime через CRI API, runtime вызывает OCI-совместимый runtime для создания контейнера.

Подробнее: [Альтернативные среды выполнения](./alternative_runtimes_and_tools.md)

### Docker Desktop

**Docker Desktop** — официальная GUI (Graphical User Interface)-платформа для управления контейнерами. Доступен для macOS, Windows и Linux.

**Возможности:**

- Визуальное управление контейнерами, образами, томами и сетями
- Встроенный терминал для доступа к контейнерам
- Просмотр логов в реальном времени
- Интеграция с Docker Compose и Kubernetes (встроенный одноузловой кластер)
- Автоматическая установка Docker Engine и CLI

**Когда использовать:**

- Удобно для разработчиков, предпочитающих графический интерфейс
- Быстрый прототипинг и отладка контейнеров
- Обучение и демонстрация

**Ограничения:**

- Избыточен для production — достаточно CLI-клиента (`docker`) и демона (`dockerd`)
- Потребляет дополнительные ресурсы системы
- На Linux обычно достаточно установить `docker-ce` через пакетный менеджер
