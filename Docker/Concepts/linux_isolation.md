# Изоляция контейнеров: Namespaces и Cgroups

## Определения

**Изоляция контейнеров** — процесс ограничения видимости и потребления ресурсов для процессов, запущенных в контейнере. В Linux это реализуется на уровне ядра через два основных механизма:

- **Namespaces** (Пространства имён) — обеспечивают **логическую изоляцию** (что процесс *видит*).
- **Cgroups** (Контрольные группы) — обеспечивают **ресурсную изоляцию** (что процесс *использует*).

Подробнее о фундаментальных механизмах ядра: [Namespaces](../../Linux/Core/namespaces.md), [Cgroups](../../Linux/Core/cgroups.md).

## Базовые концепции

### Роль механизмов ядра в контейнеризации

Docker и Podman не являются "виртуальными машинами" в классическом смысле. Это обычные процессы в Linux, к которым применены специфические ограничения.

#### 1. Пространства имён (Namespaces)

Создают иллюзию работы в отдельной операционной системе. Каждый контейнер получает свой набор пространств имён:

- **PID:** изолирует дерево процессов. Процесс внутри контейнера видит себя как PID 1.
- **NET:** изолирует сетевой стек (интерфейсы, IP-адреса, таблицы маршрутизации).
- **MNT:** изолирует точки монтирования. Контейнер видит только свою файловую систему.
- **UTS:** изолирует имя хоста (hostname) и домена.
- **IPC:** изолирует механизмы межпроцессного взаимодействия (разделяемая память, очереди сообщений).
- **USER:** мапирует UID/GID внутри контейнера на другие UID/GID на хосте. Основа **rootless** режима.
- **CGROUP:** изолирует видимость самой иерархии контрольных групп.
- **TIME:** изолирует системное время (позволяет контейнерам иметь разное время).

#### 2. Контрольные группы (Cgroups)

Предотвращают захват всех ресурсов хоста одним контейнером (проблема «шумного соседа»).

- **Cgroup v1:** исторически первая реализация с раздельной иерархией для каждого ресурса.
- **Cgroup v2:** современный стандарт (унифицированная иерархия). Поддерживается Docker с версии 20.10. В современных дистрибутивах (Ubuntu 22.04+, RHEL 9+) используется по умолчанию. Обеспечивает лучшую изоляцию и управление ресурсами (особенно памятью и I/O).

### Дополнительные уровни безопасности

Сами по себе Namespaces и Cgroups не обеспечивают полной защиты. Для усиления изоляции Docker использует:

- **Capabilities:** ограничивают права пользователя root внутри контейнера (например, запрет на изменение времени или загрузку модулей ядра). Подробнее: [Linux Capabilities](../../Linux/Security/Mechanisms/Capabilities.md).
- **Seccomp:** ограничивает доступные контейнеру системные вызовы. Подробнее: [Seccomp](../../Linux/Security/Mechanisms/Seccomp.md).
- **AppArmor / SELinux:** системы принудительного управления доступом (MAC), ограничивающие действия контейнера на уровне файлов и сети. Подробнее: [Механизмы безопасности Linux](../../Linux/Security/Linux_Security_Mechanisms_Overview.md).

## Практические сценарии

### Сравнение низкоуровневых механизмов и Docker

Низкоуровневые утилиты позволяют вручную создать изоляцию, но Docker автоматизирует этот процесс, добавляя управление образами и сетью.

| Функция | Ручной подход (`unshare`, `cgcreate`) | Docker / Podman |
| :--- | :--- | :--- |
| **Изоляция** | Требует ручного указания флагов для каждого типа | Автоматически применяет полный набор |
| **Файловая система** | Использует хостовую (требует `chroot` или `pivot_root`) | Монтирует `rootfs` из слоёв образа (Overlay2) |
| **Сеть** | Пустой namespace (требует настройки `veth` и мостов) | Автоматически настраивает bridge/overlay сети |
| **Ресурсы** | Требует ручного создания записей в `/sys/fs/cgroup` | Применяет лимиты через флаги `--memory`, `--cpus` |

### Жизненный цикл запуска контейнера (`docker run`)

При запуске контейнера демон Docker выполняет следующую последовательность действий:

1. **Подготовка ресурсов (Cgroups):** создает группу в `/sys/fs/cgroup` и записывает лимиты.
2. **Создание изоляции (Namespaces):** вызывает `clone()` или `unshare()` для порождения процесса в новых пространствах имён.
3. **Монтирование (MNT Namespace):** объединяет слои образа (OverlayFS) и монтирует их как корень ФС контейнера.
4. **Настройка сети (NET Namespace):** создает виртуальный интерфейс, выделяет IP и подключает к мосту `docker0`.
5. **Финальное ограничение:** сбрасывает ненужные привилегии (Capabilities) и применяет Seccomp-профиль.

### Изоляция в режиме Rootless

Docker и Podman поддерживают запуск без прав root на хосте. В этом режиме активно используется **User Namespace**.
- Внутри контейнера процесс считает себя root (UID 0).
- На хосте этот же процесс работает от имени обычного непривилегированного пользователя (например, UID 1000).
- Это критически важно для безопасности: даже если злоумышленник "вырвется" из контейнера, он не получит прав root на хосте.

Подробнее для Podman: [Rootless режим в Podman](../../Podman/podman_rootless.md).

### Практическая инспекция механизмов изоляции

Механизмы изоляции можно увидеть напрямую через файловую систему `/proc`.

**1. Получение PID процесса контейнера:**

```bash
# Через docker inspect
PID=$(docker inspect --format '{{.State.Pid}}' <container_name>)
echo $PID
# → 47865
```

**2. Просмотр пространств имён (Namespaces):**

```bash
# Список всех пространств имён процесса
ls -la /proc/$PID/ns/
# → net -> net:[4026532920]
# → pid -> pid:[4026532921]
# → mnt -> mnt:[4026532922]

# Использование lsns для человекочитаемого вывода
lsns -p $PID
```

**3. Вход в пространство имён для отладки:**

```bash
# Просмотр сетевых настроек контейнера «снаружи»
nsenter -t $PID -n ip addr

# Запуск shell внутри пространств имён контейнера (без docker exec)
nsenter -t $PID -n -p -m -- bash
```

**4. Проверка контрольных групп (Cgroups):**

```bash
# Просмотр cgroup процесса
cat /proc/$PID/cgroup

# Проверка лимита памяти напрямую в cgroup v2
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/memory.max
```
