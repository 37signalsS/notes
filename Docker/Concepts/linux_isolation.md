# Изоляция в Linux: Namespaces и Cgroups

## Определения

**Изоляция контейнеров** — это ключевой механизм, который позволяет процессам, запущенным внутри контейнера, работать в собственном, ограниченном окружении, не затрагивая хост-систему или другие контейнеры. В Linux эта изоляция достигается за счет комбинации двух фундаментальных технологий ядра: **пространств имён (Namespaces)** и **контрольных групп (Cgroups)**.

-   **Namespaces** отвечают за **логическую изоляцию** и ограничивают то, что процесс может *видеть*.
-   **Cgroups** отвечают за **ресурсную изоляцию** и ограничивают то, что процесс может *использовать*.

## Основные концепции

### 1. Пространства имён (Namespaces)

Процесс в контейнере выполняется в наборе собственных пространств имён, что создает иллюзию работы на отдельной машине.

**Основные типы и их назначение:**

| Namespace | Что изолируется                                                                                               | Примеры объектов                    |
| :-------- | :------------------------------------------------------------------------------------------------------------ | :---------------------------------- |
| `pid`     | Дерево процессов                                                                                              | PID, родительские/дочерние связи    |
| `net`     | Сетевой стек                                                                                                  | Интерфейсы, маршруты, iptables      |
| `mnt`     | Таблица монтирования                                                                                          | Точки монтирования, корень FS       |
| `ipc`     | Межпроцессное взаимодействие                                                                                  | POSIX/System V очереди, семафоры    |
| `uts`     | Узловое имя и домен                                                                                           | hostname, NIS domain                |
| `user`    | Идентичности и права                                                                                          | UID/GID, capabilities               |
| `cgroup`  | Привязка к иерархии cgroups                                                                                   | Видимость cgroup-дерева             |

> Ключевой нюанс **user namespace** позволяет реализовать модель “root внутри, не-root снаружи”: процесс получает административные права (`capabilities`) внутри своего user-namespace, не имея их в хостовой системе. Это основа `rootless` режима в [Podman](../../Podman/podman_rootless.md).

### 2. Контрольные группы (Cgroups)

Для предотвращения монополизации ресурсов одним контейнером его процессы помещаются в контрольную группу. Это позволяет устанавливать жесткие и мягкие лимиты на потребление системных ресурсов. В современной версии **cgroup v2** используется единая иерархия, что упрощает управление.

**Основные контроллеры, используемые в контейнеризации:**
-   **`memory`**: Ограничение использования RAM и swap (`memory.max`, `memory.high`).
-   **`cpu`**: Ограничение процессорного времени (`cpu.max`, `cpu.weight`).
-   **`pids`**: Ограничение количества дочерних процессов (`pids.max`).
-   **`io`**: Ограничение операций ввода-вывода на блочных устройствах (`io.max`).

> **Важно:** Сами по себе `namespaces` и `cgroups` не являются полноценной границей безопасности. Для надежного снижения привилегий их используют совместно с `capabilities`, `seccomp` и `AppArmor/SELinux`. Подробнее: [Обзор механизмов безопасности Linux](../../Linux/Security/Linux_Security_Mechanisms_Overview.md).

## Практические сценарии

### 1. Ручное управление изоляцией

#### Просмотр и создание Namespaces

```bash
# Посмотреть пространства имен текущего процесса
ls -l /proc/$$/ns

# Запустить shell в новых пространствах имен с помощью unshare
# --fork запускает дочерний процесс, чтобы не изменять текущую оболочку
unshare --uts --pid --net --mount --ipc --fork /bin/bash

# Внутри новой оболочки:
hostname container  # Имя хоста изменится только здесь
ps -ef              # Вы увидите изолированное дерево процессов (только bash и ps)
ip link             # Будет виден только изолированный сетевой интерфейс lo
```

#### Ручное создание Cgroup (v2)

```bash
# Для выполнения требуются права root
cd /sys/fs/cgroup

# Создаем новую группу
mkdir -p demo/sandbox

# Включаем контроллеры pids и memory для дочерних групп
echo "+pids +memory" > demo/sandbox/cgroup.subtree_control

# Устанавливаем лимиты
echo 50 > demo/sandbox/pids.max       # не более 50 процессов
echo 200M > demo/sandbox/memory.max  # не более 200 МБ памяти

# Помещаем текущий процесс в созданную группу
echo $$ > demo/sandbox/cgroup.procs

# Запускаем "тяжелую" команду, которая будет ограничена
stress --cpu 1 --vm 1 --vm-bytes 512M --timeout 10s # Команда будет завершена OOM Killer'ом
```

### 2. Применение в контейнерных средах

Хотя базовые механизмы одни и те же, их применение в Docker и Podman имеет свои особенности.

#### Жизненный цикл `docker run`

1.  **Cgroup**: Docker создает новую `cgroup` и применяет лимиты (`--memory`, `--cpus`).
2.  **Namespaces**: Создается набор новых `namespaces`.
3.  **Root FS**: В `mnt` пространстве монтируется корневая ФС из слоев образа.
4.  **Сеть**: В `net` пространстве создается пара `veth`, один из которых подключается к `docker0` bridge.
5.  **Запуск**: Процесс стартует внутри всех созданных `namespaces`.
6.  **Безопасность**: Урезаются `capabilities` и применяется `seccomp`-профиль.

#### Жизненный цикл `podman run`

1.  **Namespaces**: Podman создает `namespaces`. Для **rootless-контейнеров** обязательно используется **user namespace**.
2.  **Cgroups**: Процессы помещаются в cgroup, управляемую через `systemd` (в современных системах), что обеспечивает лучшую интеграцию с ОС.
3.  **Сеть**: В rootful-режиме используется `netavark` для `bridge`-сетей. В rootless-режиме — `slirp4netns` или `pasta`, создающие сетевой стек в пространстве пользователя без привилегий `root`.
4.  **Безопасность**: Podman по умолчанию работает с более минимальным набором `capabilities` и тесно интегрируется с `SELinux`.
