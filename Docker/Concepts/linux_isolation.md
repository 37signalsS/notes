# Изоляция контейнеров: Namespaces и Cgroups

## Определения

**Изоляция контейнеров** — процесс ограничения видимости и потребления ресурсов для процессов, запущенных в контейнере. В Linux это реализуется на уровне ядра через два основных механизма:

- **Namespaces** (Пространства имён) — обеспечивают **логическую изоляцию** (что процесс *видит*).
- **Cgroups** (Контрольные группы) — обеспечивают **ресурсную изоляцию** (что процесс *использует*).

Подробнее о фундаментальных механизмах ядра: [Namespaces](../../Linux/Core/namespaces.md), [Cgroups](../../Linux/Core/cgroups.md).

## Базовые концепции

### Роль механизмов ядра в контейнеризации

Docker и Podman не являются "виртуальными машинами" в классическом смысле. Это обычные процессы в Linux, к которым применены специфические ограничения.

1. **Namespaces:** создают иллюзию работы в отдельной ОС. Каждый контейнер получает свой набор пространств имён (`pid`, `net`, `mnt` и др.).
    - **User Namespace:** позволяет реализовать модель "root внутри, не-root снаружи". Это основа **rootless** режима в [Podman](../../Podman/podman_rootless.md).
2. **Cgroups:** предотвращают "захват" всех ресурсов хоста одним контейнером (Noisy Neighbor problem). Они позволяют устанавливать жесткие (hard) и мягкие (soft) лимиты на RAM, CPU и I/O.
    - В современных дистрибутивах используется **Cgroup v2** (унифицированная иерархия), которая полностью поддерживается Docker (20.10+) и Podman.

> **Важно:** Сами по себе `namespaces` и `cgroups` не обеспечивают 100% безопасности. Для надёжной изоляции они используются совместно с [Capabilities](../../Linux/Security/Mechanisms/Capabilities.md), [Seccomp](../../Linux/Security/Mechanisms/Seccomp.md) и [AppArmor/SELinux](../../Linux/Security/Linux_Security_Mechanisms_Overview.md).

## Практические сценарии

### Сравнение низкоуровневых механизмов и Docker

Низкоуровневая утилита `unshare` позволяет вручную создать пространство имён, но Docker автоматизирует этот процесс и добавляет уровень управления файловой системой и сетью.

| Функция | Ручной подход (`unshare`) | Docker / Podman |
| :--- | :--- | :--- |
| **Изоляция** | Требует ручного указания флагов | Автоматически применяет полный набор |
| **Файловая система** | Использует хостовую (требует `chroot`) | Монтирует `rootfs` из слоёв образа |
| **Сеть** | Пустой namespace (требует ручной настройки `veth`) | Автоматически настраивает bridge/overlay сети |
| **Ресурсы** | Не ограничивает (нужен отдельный `mkdir` в cgroup) | Применяет лимиты через флаги `--memory`, `--cpus` |

### Жизненный цикл `docker run`

Когда вы запускаете контейнер, Docker выполняет следующую последовательность действий:

1. **Cgroup:** создает новую группу в `/sys/fs/cgroup` и записывает туда лимиты.
2. **Namespaces:** вызывает `clone()` или `unshare()` для создания новых пространств имён.
3. **Root FS:** в `mnt` namespace монтирует файловую систему контейнера (UnionFS).
4. **Сеть:** настраивает виртуальный сетевой интерфейс и подключает его к сетевому стеку контейнера.
5. **Безопасность:** сбрасывает ненужные `capabilities` и применяет `seccomp`-профиль.

### Особенности изоляции в Podman (Rootless)

Podman активно использует механизмы **User Namespace** и интеграцию с **systemd** для обеспечения безопасности без прав root. Подробный разбор механизмов изоляции, специфичных для Podman, доступен в разделе: **[Изоляция в Podman](../../Podman/linux_isolation.md)**.

### Практическая инспекция namespace и cgroups

Механизмы изоляции — не абстракция. Их можно увидеть напрямую через файловую систему `/proc` для любого запущенного контейнера.

**1. Получить PID процесса контейнера:**

```bash
# Через docker inspect
docker inspect --format '{{.State.Pid}}' <container_name>
# → 47865

# Или через ps + grep
ps aux | grep <process_name>
```

**2. Просмотр namespace контейнера:**

```bash
# Прямой просмотр файлов namespace
PID=47865
ls -la /proc/$PID/ns/
# → lrwxrwx... net -> net:[4026532920]
# → lrwxrwx... pid -> pid:[4026532921]
# → lrwxrwx... mnt -> mnt:[4026532922]

# Человекочитаемый вывод через lsns
lsns -p $PID
# → 4026532920  net   47865 ... /usr/sbin/nginx
# → 4026532921  pid   47865 ... /usr/sbin/nginx
```

Каждый namespace имеет уникальный inode-номер. Если у двух процессов совпадают номера для конкретного типа namespace — они находятся в одном пространстве имён.

**3. Вход в namespace контейнера:**

```bash
# Выполнить команду в сетевом namespace контейнера
nsenter -t $PID -n ip addr

# Запустить shell внутри namespace контейнера
nsenter -t $PID -n -p -m -- sh
```

`nsenter` позволяет зайти в namespace любого процесса, что полезно для отладки сети, процессов или ФС контейнера без `docker exec`.

**4. Просмотр cgroups контейнера:**

```bash
# Сырые данные cgroups процесса
cat /proc/$PID/cgroup

# Использование ресурсов контейнера
docker stats <container_name>
# → CONTAINER  CPU%   MEM USAGE / LIMIT
# → nginx     0.01%  3.2 MiB / 256 MiB
```

`docker stats` читает данные из cgroup (память, CPU, I/O), которые были созданы при запуске контейнера. Лимиты, заданные через `--memory` или `--cpus`, можно проверить в cgroup-файлах напрямую.
