# Управление часовым поясом (TimeZone) в контейнерах

## 1. Определения

**Проблема:** По умолчанию большинство контейнерных образов настроены на использование времени **UTC (Coordinated Universal Time)**. Это приводит к тому, что логи приложений, запущенных в контейнерах, также пишутся в UTC. Когда разработчики или системные администраторы анализируют эти логи в другой временной зоне (например, в `Europe/Moscow`, UTC+3), возникает путаница из-за расхождения во времени.

**Цель:** Синхронизировать часовой пояс внутри контейнера с часовым поясом хоста или любой другой требуемой зоной для упрощения анализа логов и выполнения задач, зависящих от времени.

## 2. Базовые Концепты

Существует два фундаментальных подхода к решению этой проблемы:

### Подход 1: Оставить UTC и делать поправку ("Забить")

Это самый простой и часто используемый в эксплуатации подход. Он заключается в том, чтобы принять как данность, что все сервисы работают и пишут логи в UTC.

- **Реализация:** Внешние системы, такие как агрегаторы логов (Fluent Bit, Logstash) или системы мониторинга (Prometheus, Grafana), настраиваются на парсинг времени с учетом UTC. При необходимости они могут на лету конвертировать временные метки в локальный часовой пояс пользователя.
- **Пример (Fluent Bit):** При настройке парсера можно указать смещение (offset) для корректной обработки времени.
- **Преимущества:**
  - Универсальность: не требуется модифицировать образы или конфигурацию приложений.
  - Стандартизация: UTC является глобальным стандартом и избавляет от путаницы при работе в распределенных командах.

### Подход 2: Установить часовой пояс внутри контейнера

Этот подход нацелен на изменение конфигурации самого контейнера, чтобы приложения внутри него "видели" локальное время.

- **Основное требование:** В контейнерном образе должен быть установлен пакет `tzdata` (или его аналог, например `timedate`, в зависимости от дистрибутива). Этот пакет содержит файлы с информацией о различных часовых поясах. Если его нет, изменить зону не получится.

- **Правильный способ:** Использование переменной окружения `TZ`.
- **Неправильный способ:** Монтирование файла `/etc/localtime` с хоста в контейнер. Этот метод считается устаревшим, сложным и нарушающим портативность контейнеров.

## 3. Практические Сценарии

### Установка TimeZone через переменную окружения `TZ`

Это наиболее корректный и простой способ. Переменная окружения `TZ` имеет более высокий приоритет, чем системный файл `/etc/localtime`.

#### Пример с Docker CLI

Чтобы запустить контейнер с московским временем:

```bash
# Запускаем контейнер и устанавливаем переменную окружения TZ
docker run -d -e TZ="Europe/Moscow" nginx:latest

# Проверяем дату внутри контейнера
docker exec <container_id> date
# Вывод: Сб фев 28 12:30:00 MSK 2026
```

#### Пример с Kubernetes

Переменная окружения задается в спецификации `Deployment`, `Pod` или другого контроллера.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-app-container
        image: openresty/openresty:latest
        env:
        - name: TZ
          value: "Europe/Moscow"
        ports:
        - containerPort: 80
```

После применения этого манифеста логи, генерируемые приложением `my-app-container`, будут использовать московское время.

#### Пример с Kubernetes DownwardAPI (автоматически с хоста)

Для автоматического наследования часового пояса с ноды (где работает под) можно использовать `downwardAPI`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: timezone-auto
spec:
  containers:
  - name: app
    image: alpine:latest
    command: ["sleep", "3600"]
    env:
    - name: TZ
      valueFrom:
        fieldRef:
          fieldPath: spec.nodeName
```

> **Примечание:** Этот метод требует, чтобы имя ноды соответствовало часовому поясу (например, `node-msk-01`), что не всегда удобно. Альтернатива — использовать `hostPath` монтирование `/etc/localtime`.

## 4. Дополнительная информация

### Ограничения переменной TZ

Не все приложения корректно обрабатывают переменную `TZ`. Исключения:

- **Java** (JVM): Читает `TZ`, но требует правильной настройки `JAVA_OPTS`
- **PostgreSQL**: Использует `PGTZ` или настройки в `postgresql.conf`
- **Nginx**: Требует директиву `env TZ;` в конфиге и установку `tzdata`

Для JVM в Kubernetes:

```yaml
env:
- name: TZ
  value: "Europe/Moscow"
- name: JAVA_TOOL_OPTIONS
  value: "-Duser.timezone=Europe/Moscow"
```

### Установка `tzdata`

Если базовый образ не содержит `tzdata`, его необходимо добавить при сборке Docker-образа.

**Пример для Alpine Linux (`Dockerfile`):**

```dockerfile
FROM alpine:latest

# Установка tzdata
RUN apk --no-cache add tzdata

# Установка переменной окружения по умолчанию
ENV TZ="Europe/Moscow"

# ... остальные инструкции
```

Этот подход гарантирует,
что любой, кто использует ваш образ, по умолчанию получит правильный часовой пояс, но при этом сможет переопределить его при запуске контейнера.
