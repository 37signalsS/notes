# Альтернативные инструменты и среды выполнения контейнеров

| Инструмент/Среда выполнения | Уровень изоляции | Поддержка Rootless | Daemonless | Основной сценарий |
| :--- | :--- | :--- | :--- | :--- |
| **runc** | Процесс (namespaces, cgroups) | Да | Нет | Запуск контейнеров (стандарт OCI) |
| **crun** | Процесс (namespaces, cgroups) | Да | Нет | Запуск контейнеров (быстрая и легкая альтернатива runc) |
| **containerd** | Процесс (namespaces, cgroups) | Да | Нет | Демон-менеджер жизненного цикла контейнеров (используется Docker и Kubernetes) |

| **Kata Containers** | Виртуальная машина (аппаратная виртуализация) | Да | Нет | Запуск контейнеров с максимальной изоляцией |

### Podman: Архитектура и сравнение с Docker

Podman — это инструмент для управления контейнерами и образами, который позиционируется как прямая замена Docker. Он полностью совместим с командами Docker CLI (`docker` можно заменить на `podman`), но предлагает несколько ключевых архитектурных отличий, направленных на повышение безопасности и улучшение интеграции с современными Linux-системами.

| Характеристика | Docker | Podman |
| :--- | :--- | :--- |
| **Архитектура** | Клиент-серверная (демон `dockerd`) | Без-демонная (Daemonless) |
| **Права доступа** | Требует `root` для демона | Полноценный `rootless` режим |
| **Безопасность** | Демон `root` - потенциальная точка отказа и вектор атаки | Изоляция на уровне пользователя, снижение рисков |
| **Интеграция с ОС** | Ограниченная (управляет всем сам) | Глубокая (интеграция с `systemd`) |
| **Процессы** | Контейнеры - дочерние процессы демона `dockerd` | Контейнеры - дочерние процессы `podman CLI` |

#### Ключевые отличия от Docker

-   **Архитектура без демона (Daemonless):** В отличие от Docker, который использует центральный демон (`dockerd`), работающий с правами `root`, Podman работает напрямую. Каждый контейнер запускается как дочерний процесс самого `podman`, что устраняет единую точку отказа и значительно повышает безопасность. Если демон Docker зависнет, вся система управления контейнерами становится неработоспособной. Podman лишен этого недостатка.

-   **Полноценный Rootless режим:** Podman изначально спроектирован для работы без прав суперпользователя. Обычный пользователь может запускать контейнеры, которые полностью изолированы в его пользовательском пространстве имен (`user namespace`). Это означает, что даже если злоумышленник "сбежит" из контейнера, он получит права обычного пользователя, а не `root` на хосте. В Docker, где контейнеры управляются `root`-демоном, такой побег может привести к полной компрометации системы.

-   **Совместимость:** Поддерживает Dockerfile, команды `docker run`, `docker build` и другие, что обеспечивает легкий переход с Docker.

-   **Инфра-контейнер:** Поскольку у Podman нет демона, который бы постоянно следил за состоянием контейнеров, для реализации некоторых функций (например, `healthcheck` или политики перезапуска) он использует легковесный "инфра" контейнер. Этот контейнер запускается рядом с основным и берет на себя задачи мониторинга, имитируя поведение, которое в Docker обеспечивает демон.

#### Интеграция с `systemd`

Одним из главных преимуществ без-демонной архитектуры Podman является его нативная интеграция с `systemd` — стандартным менеджером служб в большинстве дистрибутивов Linux.

-   **Генерация Unit-файлов:** Podman может автоматически сгенерировать `systemd` unit-файл для контейнера или пода. Это позволяет управлять контейнерами как обычными системными службами.

    ```bash
    # Сгенерировать unit-файл для существующего контейнера
    podman generate systemd --name my-container > /etc/systemd/system/my-container.service

    # Перезагрузить systemd и запустить сервис
    systemctl daemon-reload
    systemctl start my-container.service
    systemctl enable my-container.service # Включить автозапуск при загрузке системы
    ```

-   **Надежность:** Этот подход устраняет необходимость в опции `restart: always` из мира Docker. Управление жизненным циклом контейнера (запуск, остановка, перезапуск при сбое) полностью передается `systemd`, который является стандартным и надежным инструментом для этих задач в Linux. Это более "родной" и предсказуемый способ обеспечить автозапуск контейнеров после перезагрузки сервера.

### Buildah

Buildah — это инструмент, который специализируется на сборке OCI-совместимых образов контейнеров. Его ключевая особенность — возможность сборки образов без необходимости запускать Docker-демон и без root-прав.

- **Сборка по Dockerfile:** Buildah может использовать существующие Dockerfile для создания образов.
- **Гибкость:** Позволяет создавать образы с нуля или на основе других образов, предоставляя детальный контроль над процессом.

## Среды выполнения (Runtimes)

Существует несколько OCI-совместимых сред выполнения, которые отвечают за непосредственный запуск контейнеров. Основные из них, `runc` и `crun`, а также высокоуровневый менеджер `containerd`, подробно описаны в документе о **[компонентах Docker](./docker_components.md#компоненты-и-их-роли)**.

### Kata Containers

Kata Containers — это среда выполнения, которая использует аппаратную виртуализацию для обеспечения максимального уровня изоляции. Вместо того чтобы напрямую использовать ядро хост-системы, Kata Containers запускает каждый контейнер (или под) в собственной легковесной виртуальной машине (microVM).

Ключевой вехой стал выпуск версии 3.0, в которой среда выполнения была переписана на Rust, что значительно снизило потребление ресурсов. Kata полностью совместима с CRI и поддерживает различные гипервизоры (QEMU, Firecracker, Cloud Hypervisor), что делает ее популярным выбором в Kubernetes для запуска недоверенных нагрузок.

### Интеграция с Docker

Kata Containers можно настроить в качестве runtime в Docker. Это позволяет запускать контейнеры с изоляцией на уровне VM, но управлять ими через привычный Docker CLI.

**Пример конфигурации `daemon.json` для Docker:**

```json
{
  "default-runtime": "kata-runtime",
  "runtimes": {
    "kata-runtime": {
      "path": "/usr/bin/kata-runtime"
    }
  }
}
```

С такой конфигурацией можно указывать, какой runtime использовать при запуске:

```bash
# Запуск контейнера с использованием Kata
docker run --runtime=kata-runtime ...

# Запуск контейнера с использованием стандартного runc
docker run ...
```

Если запустить через Kata два контейнера с разными дистрибутивами, ядро будет одной версии, так как архитектура Kata Containers предполагает, что каждый **под** (группа контейнеров, аналог пода в Kubernetes) запускается в собственной, изолированной легковесной виртуальной машине (microVM). У этой microVM есть свое собственное, оптимизированное ядро.

- **Если вы запускаете несколько контейнеров в составе одного пода**, они будут работать внутри одной и той же microVM и, следовательно, будут использовать **одно и то же ядро** этой виртуальной машины, а не ядро хоста.
- **Если вы запускаете два контейнера как два отдельных пода**, Kata создаст для каждого из них **отдельную microVM со своим собственным ядром**.

### gVisor

`gVisor` — это среда выполнения от Google, реализованная как "ядро приложения" на языке Go. Она создает "песочницу", перехватывая системные вызовы (syscalls) от контейнера и обрабатывая их в пользовательском пространстве (userspace). Это обеспечивает строгую изоляцию от ядра хоста, значительно уменьшая поверхность атаки. `gVisor` интегрируется с Docker и Kubernetes через свою реализацию OCI runtime под названием `runsc`. Э.

## CRI-совместимые среды: containerd и CRI-O

После отказа Kubernetes от прямой интеграции с Docker (`dockershim`), ключевую роль заняли две CRI-совместимые среды: `containerd` и `CRI-O`. Обе являются проектами [CNCF](../cncf_overview.md) и служат слоем абстракции между `kubelet` и низкоуровневой средой выполнения.

Роль `containerd` как универсального менеджера контейнеров подробно описана в **[архитектуре Docker](./docker_components.md#архитектура-docker)**. `CRI-O` является его легковесной альтернативой, созданной специально для Kubernetes.

| Характеристика | **containerd** | **CRI-O** |
| :--- | :--- | :--- |
| **Назначение** | Универсальная среда выполнения, используется в Docker, Kubernetes и других проектах. | Легковесная среда, созданная *специально* для Kubernetes. |
| **Функциональность** | Управление полным жизненным циклом контейнера: образы, хранилище, сеть. | Только то, что требует Kubernetes CRI: запуск подов и управление ими. |
| **Экосистема** | Широкая, так как является компонентом Docker. | Сфокусирована на Kubernetes и облачных технологиях (например, Red Hat OpenShift). |
| **Минимализм** | Более многофункциональна. | Более легковесна и минималистична. |

## Инструменты для сборки и отладки

### buildg

`buildg` — это интерактивный отладчик для Dockerfile, основанный на BuildKit. Он решает проблему отладки сложных Dockerfile, позволяя пошагово выполнять инструкции и инспектировать состояние сборки на каждом этапе.

**Ключевые возможности:**

- **Пошаговое выполнение и точки останова:** Позволяет устанавливать точки останова (`# break`) прямо в Dockerfile и выполнять сборку шаг за шагом.
- **Интерактивная оболочка:** Предоставляет доступ к интерактивной оболочке (`exec sh`) на любом шаге сборки, что дает возможность исследовать файловую систему и выполнять команды внутри промежуточного контейнера.
- **Интеграция с IDE:** Поддерживает протокол DAP (Debug Adapter Protocol), что позволяет использовать графические отладчики в VS Code, Emacs и Neovim для визуальной отладки Dockerfile.

### Интеграция с Kubernetes: CRI и OCI

Взаимодействие между Kubernetes (`kubelet`) и различными средами выполнения контейнеров происходит через стандартизированные интерфейсы.

Подробное описание стандартов **CRI (Container Runtime Interface)** и **OCI (Open Container Initiative)**, а также схема их совместной работы, находятся в основном документе о **[компонентах Docker](./docker_components.md#ключевые-стандарты-cri-и-oci)**.
