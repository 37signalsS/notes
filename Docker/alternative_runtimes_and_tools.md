# Альтернативные среды выполнения и инструменты

## Определения

* **runc**: Низкоуровневая среда выполнения контейнеров, эталонная реализация стандарта **OCI**. Отвечает за непосредственный запуск контейнеров, используя пространства имен (namespaces) и группы контроля (cgroups) Linux.
* **crun**: Альтернативная низкоуровневая OCI-совместимая среда выполнения. Написана на C, отличается высокой производительностью и низким потреблением ресурсов.
* **containerd**: Высокоуровневый демон, управляющий полным жизненным циклом контейнеров: от скачивания образов до управления хранилищем и сетевыми интерфейсами. Является проектом CNCF и стандартом для Kubernetes.
* **CRI-O**: Легковесная, CRI-совместимая среда выполнения, созданная специально для Kubernetes. Альтернатива `containerd`.
* **Podman**: Инструмент для управления контейнерами и образами, полная замена Docker CLI. Работает без демона (daemonless) и поддерживает режим "без рута" (rootless).
* **Buildah**: Инструмент для сборки OCI-совместимых образов контейнеров. Позволяет создавать образы без Docker-демона и без root-прав.
* **Kata Containers**: OCI-совместимая среда выполнения, использующая аппаратную виртуализацию (microVM) для запуска контейнеров с максимальной изоляцией и повышенной безопасностью.
* **gVisor**: Среда выполнения от Google, создающая "песочницу" (userspace kernel) для перехвата системных вызовов контейнера, обеспечивая строгую изоляцию от ядра хоста.
* **buildg**: Интерактивный отладчик для Dockerfile, основанный на BuildKit, позволяющий пошагово выполнять сборку и инспектировать ее состояние.
* **Skopeo**: Инструмент для копирования, инспектирования и проверки контейнерных образов между реестрами без необходимости запуска полноценного контейнерного демона. Работает напрямую с репозиториями Docker, OCI-совместимыми реестрами и локальными архивами.

## Основные концепции

Экосистему можно условно разделить на несколько уровней: высокоуровневые менеджеры, низкоуровневые среды выполнения и вспомогательные инструменты. Взаимодействие между ними регулируется двумя ключевыми стандартами: CRI и OCI.

### Стандарты: CRI и OCI

* **OCI (Open Container Initiative):** В раннюю эру контейнеризации существовало множество несовместимых друг с другом систем управления. Эта разрозненность привела к созданию **Open Container Initiative (OCI)** под эгидой Linux Foundation. OCI согласует и публикует два ключевых стандарта:
    1. **Спецификация формата образа (Image Specification)**.
    2. **Спецификация среды выполнения (Runtime Specification)**.

    Эталонной реализацией обеих спецификаций в Linux является утилита `runc`.

    Ключевой концепцией OCI является **"bundle"** (пакет), который представляет собой стандартный формат для запуска контейнера на диске. `runc` и другие низкоуровневые среды выполнения потребляют именно этот формат. OCI bundle состоит из двух частей:
    1. **`config.json`**: Файл, описывающий конфигурацию контейнера: какой процесс запускать, какие `namespaces` использовать, какие `cgroups` применять и т.д.
    2. **`rootfs`**: Директория, содержащая корневую файловую систему будущего контейнера.

    Когда вы используете `docker run`, Docker (через `containerd`) преобразует свой образ в OCI bundle, который затем передается `runc` для исполнения. Это гарантирует, что образ, созданный любым OCI-совместимым инструментом (например, `Buildah`), запустится любой OCI-совместимой средой выполнения.

* **CRI (Container Runtime Interface):** API Kubernetes, который позволяет `kubelet` единообразно взаимодействовать с различными средами выполнения (`containerd`, `CRI-O`).

### Высокоуровневые среды выполнения (CRI)

После отказа Kubernetes от прямой интеграции с Docker (`dockershim`), ключевую роль заняли две CRI-совместимые среды: `containerd` и `CRI-O`. Обе являются проектами [CNCF](../Kubernetes/kubernetes_overview.md) и служат слоем абстракции между `kubelet` и низкоуровневой средой выполнения.

| Характеристика | **containerd** | **CRI-O** |
| :--- | :--- | :--- |
| **Назначение** | Универсальная среда, используется в Docker, Kubernetes и др. | Легковесная среда, созданная *специально* для Kubernetes. |
| **Функциональность**| Управление полным жизненным циклом контейнера. | Только то, что требует Kubernetes CRI: запуск подов. |
| **Экосистема** | Широкая, т.к. является компонентом Docker. | Сфокусирована на Kubernetes и OpenShift. |

Роль `containerd` как универсального менеджера контейнеров подробно описана в [архитектуре Docker](./docker_overview.md#архитектура-docker).

### Низкоуровневые среды выполнения (OCI)

Эти среды отвечают за непосредственный запуск контейнера.

* **runc и crun**: Стандартные реализации OCI, которые напрямую работают с ядром Linux. Подробно их роль описана в документе о [компонентах Docker](./docker_overview.md#компоненты-и-их-роли).
* **Kata Containers**: Запускает каждый контейнер в собственной легковесной виртуальной машине (microVM), используя аппаратную виртуализацию для максимальной изоляции. Версия 3.0, переписанная на Rust, значительно снизила потребление ресурсов.
* **gVisor**: Создает "ядро приложения" на Go, которое перехватывает системные вызовы контейнера и обрабатывает их в пользовательском пространстве (`userspace`), изолируя от ядра хоста.

### Инструменты для управления и сборки

* **Podman**: Предлагает архитектуру без демона (daemonless), что повышает безопасность и упрощает интеграцию с `systemd`. Каждый контейнер — прямой дочерний процесс `podman`, а не центрального демона. Полное сравнение с Docker: [Podman vs Docker](../Podman/podman_vs_docker.md).

* **Buildah**: Специализированный инструмент для сборки OCI-образов без Docker-демона и root-прав. Предоставляет полный контроль над содержимым слоев образа.
* **buildg**: Интерактивный отладчик для `Dockerfile`, который позволяет выполнять сборку по шагам, ставить точки останова и исполнять команды внутри промежуточных контейнеров.
* **Skopeo**: Утилита для копирования, инспектирования и проверки контейнерных образов между реестрами без необходимости запуска полноценного контейнерного демона.
* **[TUI инструменты управления (lazydocker, oxker)](./docker_tools.md)**: Интерактивные консольные клиенты для повседневной работы с контейнерами.

## Практические сценарии

### Podman: Интеграция с `systemd`

Одним из главных преимуществ архитектуры Podman является его нативная интеграция с `systemd`. Это позволяет управлять контейнерами как обычными системными службами, что надежнее, чем `restart: always` в Docker.

* **Генерация Unit-файлов:** `podman` может автоматически сгенерировать `.service` файл для контейнера или пода.

    ```bash
    # Сгенерировать unit-файл для существующего контейнера
    podman generate systemd --name my-container > /etc/systemd/system/my-container.service

    # Перезагрузить systemd и запустить сервис
    systemctl daemon-reload
    systemctl start my-container.service
    systemctl enable my-container.service # Включить автозапуск
    ```

### Buildah: Гибкая сборка образов

Buildah может как использовать `Dockerfile`, так и собирать образы с нуля с помощью скриптов.

* **Сборка по Dockerfile**: `buildah bud -t my-image .`
* **Продвинутый сценарий**: Для более сложных сценариев, например, для унификации сборки образов с помощью Ansible, смотрите руководство [Сборка образов с помощью Buildah и Ansible-bender](../Ansible/ansible_buildah_image_building.md).

### Kata Containers: Запуск с повышенной изоляцией

Kata Containers можно интегрировать с Docker, чтобы выборочно запускать контейнеры в microVM.

1. **Настройка Docker (`/etc/docker/daemon.json`):**

    ```json
    {
      "default-runtime": "runc",
      "runtimes": {
        "kata-runtime": {
          "path": "/usr/bin/kata-runtime"
        }
      }
    }
    ```

2. **Запуск контейнера с Kata:**

    ```bash
    # Запуск контейнера с использованием Kata для максимальной изоляции
    docker run --runtime=kata-runtime my-untrusted-app

    # Обычный запуск с runc
    docker run my-trusted-app
    ```

* **Поведение ядра:** Каждый **под** (или отдельный контейнер в мире Docker) с `runtime=kata-runtime` запускается в своей microVM с собственным ядром. Контейнеры внутри одного пода разделяют общее ядро этой microVM.

### buildg: Интерактивная отладка Dockerfile

`buildg` позволяет отлаживать `Dockerfile` так же, как исходный код.

* **Точки останова:** Добавьте комментарий `# break` в `Dockerfile` перед проблемной инструкцией.

* **Запуск отладки:** `buildg debug --image my-app .`

* **Интерактивная сессия:** На точке останова `buildg` предоставит командную строку внутри контейнера, где можно проверить файловую систему, переменные окружения и выполнить любые команды для диагностики.

* **Интеграция с IDE:** Поддерживает Debug Adapter Protocol (DAP) для визуальной отладки в VS Code и других редакторах.

### Skopeo: Управление образами без демона

Skopeo — это мощный инструмент для работы с контейнерными образами, который не требует запущенного Docker-демона. Это делает его идеальным для CI/CD, автоматизации и работы в средах с повышенными требованиями к безопасности, где установка полноценного Docker-демона нежелательна или невозможна.

**Ключевой функционал:**

* **`skopeo copy`**: Копирование образов между различными типами хранилищ (реестры, локальные архивы, директории) без промежуточной выгрузки на локальную машину.

    ```bash
    # Копирование образа из одного реестра в другой
    skopeo copy docker://registry.example.com/my-image:latest \
                docker://another.registry.com/my-image:latest

    # Копирование образа в локальную директорию (в формате OCI)
    skopeo copy docker://registry.example.com/my-image:latest \
                oci:my-local-image:latest
    ```

* **`skopeo inspect`**: Просмотр метаданных образа (теги, слои, переменные окружения) без необходимости скачивания всего образа. Это экономит дисковое пространство и время.

    ```bash
    # Инспектирование образа в удаленном реестре
    skopeo inspect docker://registry.example.com/my-image:latest

    # Просмотр конкретных метаданных (например, размера образа)
    skopeo inspect --format "{{.Size}}" docker://registry.example.com/my-image:latest
    ```

* **`skopeo sync`**: Массовое копирование и синхронизация репозиториев образов.
* **Конвертация форматов**: Поддержка конвертации между Docker Image Manifest v2 и OCI.
* **Работа с аутентификацией**: Поддержка `~/.docker/config.json`, отдельных учетных данных и сертификатов.

**Преимущества:** Daemonless, экономия ресурсов, проверка подписей, гибкость источников.
