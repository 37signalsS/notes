# Альтернативные среды выполнения и инструменты контейнеризации

## Определения

* **runc:** Низкоуровневая среда выполнения контейнеров, эталонная реализация стандарта **OCI**. Отвечает за непосредственный запуск контейнеров, используя пространства имен (namespaces) и группы контроля (cgroups) Linux.
* **crun:** Высокопроизводительный аналог `runc`, написанный на языке C. Отличается минимальным потреблением ресурсов и нативной поддержкой **WebAssembly (Wasm)** через интеграцию с `wasmedge` или `wasmtime`.
* **containerd:** Высокоуровневый демон управления жизненным циклом контейнеров (скачивание образов, snapshotters, управление томами и сетью). Является отраслевым стандартом и основным рантаймом для Kubernetes.
* **CRI-O:** Легковесная среда выполнения, реализующая исключительно спецификацию **CRI** для Kubernetes. Архитектурно проще, чем `containerd`, так как не содержит лишнего функционала, необходимого для Docker.
* **Podman:** Инструмент для управления контейнерами без центрального демона (daemonless). Поддерживает запуск без привилегий суперпользователя (rootless) по умолчанию и является архитектурной заменой Docker CLI.
* **Buildah:** Специализированный инструмент для сборки образов, соответствующих стандартам OCI. Позволяет создавать образы без Docker-демона, без root-прав и даже без использования `Dockerfile` (через скрипты).
* **Kata Containers:** Среда выполнения, использующая аппаратную виртуализацию (microVM, например Firecracker или QEMU) для запуска контейнеров. Обеспечивает изоляцию на уровне ядра ОС.
* **gVisor:** Рантайм-песочница от Google, реализующий ядро в пространстве пользователя (Sentry). Перехватывает системные вызовы контейнера, обеспечивая строгую границу безопасности между приложением и хостом.
* **Sysbox:** Специализированный рантайм, позволяющий запускать системные службы (systemd) и Docker внутри контейнеров с высокой степенью изоляции через User Namespaces без использования привилегированного режима.
* **buildg:** Интерактивный отладчик для `Dockerfile`, основанный на BuildKit, позволяющий пошагово выполнять сборку и инспектировать состояние слоев в реальном времени.
* **Skopeo:** Утилита для удаленных манипуляций с образами (копирование, инспекция, проверка) напрямую в реестрах без необходимости скачивания слоев на локальный диск и запуска демона.
* **runwasi:** Проект CNCF, предоставляющий shim-интерфейсы для запуска Wasm-модулей напрямую через `containerd` без создания полноценной Linux-среды.

## Основные концепции

Экосистему контейнеризации можно разделить на несколько уровней: высокоуровневые менеджеры, низкоуровневые среды выполнения и специализированные инструменты. Взаимодействие между ними регулируется стандартами CRI и OCI.

### Стандарты: CRI и OCI

* **OCI (Open Container Initiative):** Стандарт, определяющий формат образа и спецификацию среды выполнения.
  * **Image Spec:** Описывает структуру образа (слои, манифест, конфигурация).
  * **Runtime Spec:** Описывает жизненный цикл и конфигурацию контейнера на диске (**bundle**).
  * Концепция **bundle**: Директория с `config.json` (описание изоляции и ресурсов) и `rootfs` (файловая система).

* **CRI (Container Runtime Interface):** API Kubernetes, позволяющий `kubelet` взаимодействовать с различными высокоуровневыми средами выполнения (`containerd`, `CRI-O`).

### Высокоуровневые среды выполнения (CRI)

Эти компоненты управляют образами, сетями и передают команды низкоуровневым рантаймам.

| Характеристика | containerd | CRI-O |
| :--- | :--- | :--- |
| **Назначение** | Универсальная среда для Docker, Kubernetes и др. | Оптимизирована только под Kubernetes. |
| **Функциональность**| Полный жизненный цикл (образы, snapshotters). | Только функции, необходимые для CRI. |
| **Экосистема** | Проект CNCF, стандарт де-факто. | Часть стека Red Hat / OpenShift. |

Роль `containerd` в экосистеме Docker описана в **[архитектуре Docker](./docker_overview.md#архитектура-docker)**.

### Низкоуровневые среды выполнения (OCI)

Отвечают за непосредственное создание пространств имен и групп контроля Linux.

* **Стандартные (runc, crun):** Прямая изоляция через ядро хоста. `crun` в 2026 году предпочтительнее для высоконагруженных систем благодаря поддержке Wasm и более быстрому запуску. Подробнее см. в разделе **[Архитектура Docker](./docker_overview.md#архитектура-docker)**.
* **Безопасные (Sandbox):**
  * **Kata Containers:** Использует аппаратную виртуализацию (microVM). Каждый контейнер (или под) запускается со своим ядром. Идеально для Multi-tenancy облаков.
  * **gVisor:** Реализует прослойку (Sentry), которая перехватывает и обрабатывает системные вызовы в пользовательском пространстве. Эффективно для untrusted кода.
* **Специализированные (Wasm):**
  * **runwasi:** Позволяет запускать Wasm-модули как легковесные задачи без оверхеда на полноценную ОС внутри контейнера.

### Инструменты экосистемы

* **Podman:** Альтернатива Docker без центрального демона. Подробное сравнение приведено в **[Podman vs Docker](../Podman/podman_vs_docker.md)**.
* **Buildah:** Позволяет собирать образы как по `Dockerfile`, так и через скрипты управления слоями.
* **Skopeo:** Работает напрямую с API реестров, позволяя копировать образы между облаками без промежуточного сохранения на диск.
* **TUI инструменты (lazydocker, oxker):** Интерактивные интерфейсы для мониторинга. Подробнее см. **[Инструменты Docker](./docker_tools.md)**.

## Практические сценарии

### Сценарий 1: Интеграция Podman с systemd

Архитектура без демона позволяет управлять контейнерами как обычными системными службами.

```bash
# Генерация unit-файла для контейнера
podman generate systemd --name my-container --files --new

# Управление через стандартный systemctl
systemctl enable --now container-my-container.service
```

### Сценарий 2: Сборка образов через Buildah (монтирование rootfs)

Buildah предоставляет гранулярный контроль над слоями без необходимости запуска Docker.

```bash
# Создание базового контейнера
container=$(buildah from alpine:latest)

# Монтирование файловой системы образа в хост
mountpoint=$(buildah mount $container)

# Прямая установка пакетов или копирование файлов
apk add --root $mountpoint --initdb nginx
cp index.html $mountpoint/var/www/localhost/htdocs/

# Завершение сборки
buildah commit $container my-nginx-image
```
Подробный разбор концепций см. в **[Buildah: Концепции и практика](../Podman/buildah_overview.md)**.

### Сценарий 3: Запуск Kata Containers

Для использования Kata с Docker необходимо настроить рантайм в конфигурации демона.

1. **Настройка `/etc/docker/daemon.json`:**
    ```json
    {
      "runtimes": {
        "kata": { "path": "/usr/bin/kata-runtime" }
      }
    }
    ```
2. **Запуск с повышенной изоляцией:**
    ```bash
    docker run --runtime=kata -d nginx
    ```

### Сценарий 4: Интерактивная отладка через buildg

Позволяет инспектировать процесс сборки на любом этапе, запуская shell в промежуточном слое.

```bash
# Запуск отладки Dockerfile
buildg debug .

# Команды отладчика:
# list  - показать текущую строку Dockerfile
# step  - выполнить один шаг (инструкцию)
# exec  - запустить интерактивный shell в текущем контексте сборки
# break - установить точку остановки
```

### Сценарий 5: Манипуляции образами через Skopeo

Полезно для CI/CD и синхронизации реестров без скачивания всех слоев на диск.

```bash
# Инспекция образа в удаленном реестре без скачивания
skopeo inspect docker://registry.redhat.io/ubi8/ubi

# Копирование между реестрами напрямую (Cloud-to-Cloud)
skopeo copy docker://source.reg/image:v1 docker://target.reg/image:v1

# Удаление тега из удаленного реестра
skopeo delete docker://registry.example.com/repo:tag
```
Подробнее см. **[Skopeo: Манипуляции образами](../Podman/skopeo_overview.md)**.

## Дополнительная информация

### Рекомендации по выбору инструментов сборки

#### Детальное сравнение: BuildKit vs Buildah

| Критерий | Выбирай **[BuildKit (Docker)](./Dockerfile/dockerfile_buildkit.md)**, если: | Выбирай **[Buildah (Podman)](../Podman/buildah_overview.md)**, если: |
| :--- | :--- | :--- |
| **Приоритет** | **Скорость и удобство CI/CD.** | **«Хирургический» контроль и безопасность.** |
| **Кэширование** | Нужно пушить кэш в Registry как отдельный артефакт (`mode=max`). | Достаточно локального кэша или кэширования через Registry (через Skopeo). |
| **Формат сборки** | Используешь стандартные **Dockerfile** с современными фичами (`RUN --mount`). | Нужна сборка **без Dockerfile** (через bash-скрипты и нативное монтирование). |
| **Архитектура** | Нужна нативная мультиплатформенная сборка через **buildx**. | Создаешь сверхмалые **Distroless** образы (через прямой `buildah mount`). |
| **Экосистема** | Стандартный Docker / Kubernetes. | Экосистема Red Hat / OpenShift / Podman. |
| **Демон** | Готов запускать `buildkitd` (или использовать встроенный в Docker). | Требуется **daemonless** подход (чистый CLI без фоновых процессов). |
| **Безопасность** | Нужна изоляция через `userns` (Rootless Docker). | Используешь **Rootless** по умолчанию в полностью непривилегированной среде. |

Эмпирические данные по производительности тройки инструментов в одинаковых условиях кластерного стенда с registry-кэшем — в [Бенчмарк Kaniko vs BuildKit vs Buildah в кластере](./Dockerfile/dockerfile_build_tools_benchmark.md).

### Рекомендации по выбору сред выполнения (Runtimes)

* **Для Kubernetes:** `containerd` является стандартом индустрии (SSoT). `CRI-O` — если вы работаете в экосистеме OpenShift.
* **Для обеспечения безопасности (Untrusted Workload):** 
    - Используйте **gVisor** для изоляции приложений с интенсивными системными вызовами, требующих минимального оверхеда.
    - Используйте **Kata Containers** для полной изоляции на уровне ядра, если позволяет оборудование (поддержка вложенной виртуализации).
* **Для Edge Computing и Serverless:** Рассмотрите **runwasi** или **crun** с поддержкой Wasm для достижения субсекундного времени старта и минимального потребления памяти.
