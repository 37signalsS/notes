# Альтернативные инструменты и среды выполнения контейнеров

| Инструмент/Среда выполнения | Уровень изоляции | Поддержка Rootless | Daemonless | Основной сценарий |
| :--- | :--- | :--- | :--- | :--- |
| **runc** | Процесс (namespaces, cgroups) | Да | Нет | Запуск контейнеров (стандарт OCI) |
| **crun** | Процесс (namespaces, cgroups) | Да | Нет | Запуск контейнеров (быстрая и легкая альтернатива runc) |
| **containerd** | Процесс (namespaces, cgroups) | Да | Нет | Демон-менеджер жизненного цикла контейнеров (используется Docker и Kubernetes) |
| **Podman** | Процесс (namespaces, cgroups) | Да | Да | Управление контейнерами и образами (замена Docker CLI) |
| **Buildah** | Процесс (namespaces, cgroups) | Да | Да | Сборка образов |
| **Kata Containers** | Виртуальная машина (аппаратная виртуализация) | Да | Нет | Запуск контейнеров с максимальной изоляцией |
| **gVisor** | Ядро в userspace ("песочница") | Да | Нет | Запуск контейнеров с повышенной безопасностью (изоляция syscalls) |

---

### Podman

Podman — это инструмент для управления контейнерами и образами, который работает без демона (daemonless). Он полностью совместим с командами Docker CLI (`docker` можно заменить на `podman`) и предлагает ключевые улучшения в области безопасности, в частности, полноценную работу без root-прав (rootless).

### Buildah

Buildah — это инструмент, который специализируется на сборке OCI-совместимых образов контейнеров. Его ключевая особенность — возможность сборки образов без необходимости запускать Docker-демон и без root-прав.

- **Сборка по Dockerfile:** Buildah может использовать существующие Dockerfile для создания образов.
- **Гибкость:** Позволяет создавать образы с нуля или на основе других образов, предоставляя детальный контроль над процессом.

## Среды выполнения (Runtimes)

Существует несколько OCI-совместимых сред выполнения, которые отвечают за непосредственный запуск контейнеров. Основные из них, `runc` и `crun`, а также высокоуровневый менеджер `containerd`, подробно описаны в документе о **[компонентах Docker](./docker_components.md#компоненты-и-их-роли)**.

### Kata Containers

Kata Containers — это среда выполнения, которая использует аппаратную виртуализацию для обеспечения максимального уровня изоляции. Вместо того чтобы напрямую использовать ядро хост-системы, Kata Containers запускает каждый контейнер (или под) в собственной легковесной виртуальной машине (microVM).

Ключевой вехой стал выпуск версии 3.0, в которой среда выполнения была переписана на Rust, что значительно снизило потребление ресурсов. Последующие релизы сфокусированы на улучшении безопасности, производительности и поддержке нового оборудования (включая GPU). Kata полностью совместима с CRI и поддерживает различные гипервизоры (QEMU, Firecracker, Cloud Hypervisor), что делает ее популярным выбором в Kubernetes для запуска недоверенных нагрузок.

### Интеграция с Docker

Kata Containers можно настроить в качестве runtime в Docker. Это позволяет запускать контейнеры с изоляцией на уровне VM, но управлять ими через привычный Docker CLI.

**Пример конфигурации `daemon.json` для Docker:**

```json
{
  "default-runtime": "kata-runtime",
  "runtimes": {
    "kata-runtime": {
      "path": "/usr/bin/kata-runtime"
    }
  }
}
```

С такой конфигурацией можно указывать, какой runtime использовать при запуске:

```bash
# Запуск контейнера с использованием Kata
docker run --runtime=kata-runtime ...

# Запуск контейнера с использованием стандартного runc
docker run ...
```

Если запустить через Kata два контейнера с разными дистрибутивами, ядро будет одной версии, так как архитектура Kata Containers предполагает, что каждый **под** (группа контейнеров, аналог пода в Kubernetes) запускается в собственной, изолированной легковесной виртуальной машине (microVM). У этой microVM есть свое собственное, оптимизированное ядро.

**Если вы запускаете несколько контейнеров в составе одного пода**, они будут работать внутри одной и той же microVM и, следовательно, будут использовать **одно и то же ядро** этой виртуальной машины, а не ядро хоста.
- **Если вы запускаете два контейнера как два отдельных пода**, Kata создаст для каждого из них **отдельную microVM со своим собственным ядром**.

### gVisor

`gVisor` — это среда выполнения от Google, реализованная как "ядро приложения" на языке Go. Она создает "песочницу", перехватывая системные вызовы (syscalls) от контейнера и обрабатывая их в пользовательском пространстве (userspace). Это обеспечивает строгую изоляцию от ядра хоста, значительно уменьшая поверхность атаки.

`gVisor` интегрируется с Docker и Kubernetes через свою реализацию OCI runtime под названием `runsc`. Это хороший выбор для запуска частично доверенного или недоверенного кода, где важна безопасность, но производительность полноценной виртуализации избыточна.

## CRI-совместимые среды: containerd и CRI-O

После отказа Kubernetes от прямой интеграции с Docker (`dockershim`), ключевую роль заняли две CRI-совместимые среды: `containerd` и `CRI-O`. Обе являются проектами CNCF и служат слоем абстракции между `kubelet` и низкоуровневой средой выполнения.

Роль `containerd` как универсального менеджера контейнеров подробно описана в **[архитектуре Docker](./docker_components.md#архитектура-docker)**. `CRI-O` является его легковесной альтернативой, созданной специально для Kubernetes.

| Характеристика | **containerd** | **CRI-O** |
| :--- | :--- | :--- |
| **Назначение** | Универсальная среда выполнения, используется в Docker, Kubernetes и других проектах. | Легковесная среда, созданная *специально* для Kubernetes. |
| **Функциональность** | Управление полным жизненным циклом контейнера: образы, хранилище, сеть. | Только то, что требует Kubernetes CRI: запуск подов и управление ими. |
| **Экосистема** | Широкая, так как является компонентом Docker. | Сфокусирована на Kubernetes и облачных технологиях (например, Red Hat OpenShift). |
| **Минимализм** | Более многофункциональна. | Более легковесна и минималистична. |

Выбор между ними часто зависит от экосистемы и требований: `containerd` является более универсальным и распространенным решением, в то время как `CRI-O` предлагает более узкоспециализированный и оптимизированный для Kubernetes подход.

### Интеграция с Kubernetes: CRI и OCI

Взаимодействие между Kubernetes (`kubelet`) и различными средами выполнения контейнеров происходит через стандартизированные интерфейсы.

Подробное описание стандартов **CRI (Container Runtime Interface)** и **OCI (Open Container Initiative)**, а также схема их совместной работы, находятся в основном документе о **[компонентах Docker](./docker_components.md#ключевые-стандарты-cri-и-oci)**.
