# Альтернативные среды выполнения и инструменты

## Определения

* **runc** — низкоуровневая среда выполнения контейнеров, эталонная реализация стандарта **OCI**. Отвечает за непосредственный запуск контейнеров, используя пространства имен (namespaces) и группы контроля (cgroups) Linux.
* **crun** — альтернативная низкоуровневая OCI-совместимая среда выполнения. Написана на C, отличается высокой производительностью и крайне низким потреблением ресурсов.
* **containerd** — высокоуровневый демон, управляющий полным жизненным циклом контейнеров: от скачивания образов до управления хранилищем и сетевыми интерфейсами. Является проектом CNCF и стандартом для Kubernetes.
* **CRI-O** — легковесная, CRI-совместимая среда выполнения, созданная специально для Kubernetes. Альтернатива `containerd`.
* **Podman** — инструмент для управления контейнерами и образами, архитектурная замена Docker CLI. Работает без демона (daemonless) и поддерживает режим "без рута" (rootless) по умолчанию.
* **Buildah** — инструмент для сборки OCI-совместимых образов контейнеров. Позволяет создавать образы без Docker-демона и без root-прав.
* **Kata Containers** — OCI-совместимая среда выполнения, использующая аппаратную виртуализацию (microVM) для запуска контейнеров с максимальной изоляцией и повышенной безопасностью.
* **gVisor** — среда выполнения от Google, создающая "песочницу" (userspace kernel) для перехвата системных вызовов контейнера, обеспечивая строгую изоляцию от ядра хоста.
* **buildg** — интерактивный отладчик для Dockerfile, основанный на BuildKit, позволяющий пошагово выполнять сборку и инспектировать ее состояние.
* **Skopeo** — инструмент для копирования, инспектирования и проверки контейнерных образов между реестрами без запуска полноценного контейнерного демона.

## Основные концепции

Экосистему контейнеризации можно разделить на несколько уровней: высокоуровневые менеджеры, низкоуровневые среды выполнения и специализированные инструменты. Взаимодействие между ними регулируется стандартами CRI и OCI.

### Стандарты: CRI и OCI

* **OCI (Open Container Initiative):** Стандарт, определяющий формат образа и спецификацию среды выполнения.
  * **Image Spec:** Описывает структуру образа (слои, манифест).
  * **Runtime Spec:** Описывает жизненный цикл и конфигурацию контейнера на диске (**bundle**).
  * Концепция **bundle**: Директория с `config.json` (описание изоляции и ресурсов) и `rootfs` (файловая система).

* **CRI (Container Runtime Interface):** API Kubernetes, позволяющий `kubelet` взаимодействовать с различными высокоуровневыми средами выполнения (`containerd`, `CRI-O`).

### Высокоуровневые среды выполнения (CRI)

Эти компоненты управляют образами, сетями и передают команды низкоуровневым рантаймам.

| Характеристика | containerd | CRI-O |
| :--- | :--- | :--- |
| **Назначение** | Универсальная среда для Docker, Kubernetes и др. | Оптимизирована только под Kubernetes. |
| **Функциональность**| Полный жизненный цикл (образы, snapshotters). | Только функции, необходимые для CRI. |
| **Экосистема** | Проект CNCF, стандарт де-факто. | Часть стека Red Hat / OpenShift. |

Роль `containerd` в экосистеме Docker описана в **[архитектуре Docker](./docker_overview.md#архитектура-docker)**.

### Низкоуровневые среды выполнения (OCI)

Отвечают за непосредственное создание пространств имен и групп контроля Linux.

* **Стандартные (runc, crun):** Прямая изоляция через ядро хоста. Подробнее см. в разделе **[Архитектура Docker](./docker_overview.md#архитектура-docker)**.
* **Безопасные (Sandbox):**
  * **Kata Containers:** Использует аппаратную виртуализацию (microVM). Каждый контейнер (или под) запускается со своим ядром.
  * **gVisor:** Реализует прослойку (Sentry), которая перехватывает и обрабатывает системные вызовы в пользовательском пространстве.

### Инструменты экосистемы

* **Podman:** Альтернатива Docker без центрального демона. Подробное сравнение приведено в **[Podman vs Docker](../Podman/podman_vs_docker.md)**.
* **Buildah:** Позволяет собирать образы как по Dockerfile, так и через скрипты управления слоями.
* **Skopeo:** Работает напрямую с API реестров, позволяя копировать образы без `docker pull` / `docker push`.
* **[TUI инструменты (lazydocker, oxker)](./docker_tools.md):** Интерактивные интерфейсы для мониторинга.

## Практические сценарии

### Интеграция Podman с systemd

Архитектура без демона позволяет управлять контейнерами как обычными системными службами.

```bash
# Генерация unit-файла для контейнера
podman generate systemd --name my-container > /etc/systemd/system/container-app.service

# Управление через стандартный systemctl
systemctl enable --now container-app.service
```

### Сборка образов через Buildah

Buildah предоставляет гранулярный контроль над слоями без необходимости запуска Docker. Подробный разбор концепций и практических примеров см. в отдельном руководстве:

**[Buildah: Концепции и практика](../Podman/buildah_overview.md)**

### Запуск Kata Containers

Для использования Kata с Docker необходимо настроить рантайм в конфигурации демона.

1. **Настройка `/etc/docker/daemon.json`:**

    ```json
    {
      "runtimes": {
        "kata": { "path": "/usr/bin/kata-runtime" }
      }
    }
    ```

2. **Запуск с повышенной изоляцией:**

    ```bash
    docker run --runtime=kata -d nginx
    ```

### Интерактивная отладка через buildg

Позволяет инспектировать процесс сборки на любом этапе.

```bash
# Запуск отладки Dockerfile
buildg debug .

# Доступные команды в отладчике:
# list - показать текущую строку Dockerfile
# step - выполнить один шаг
# exec - запустить shell в текущем слое
```

### Манипуляции образами через Skopeo

Полезно для CI/CD и синхронизации реестров без скачивания всех слоев на диск.

```bash
# Инспекция образа в удаленном реестре
skopeo inspect docker://registry.redhat.io/ubi8/ubi

# Копирование между реестрами напрямую
skopeo copy docker://source.reg/image:v1 docker://target.reg/image:v1

# Синхронизация репозиториев
skopeo sync --src docker --dest docker source.reg/project target.reg/project
```

## Дополнительная информация

### Рекомендации по выбору

* **Для Kubernetes:** `containerd` является стандартом. `CRI-O` — если используется OpenShift.
* **Для безопасности:** Используйте `gVisor` для untrusted workload с интенсивными системными вызовами или `Kata Containers` для максимальной изоляции.
* **Для сборки в CI/CD:** `Buildah` и `Skopeo` предпочтительнее Docker, так как не требуют привилегированного демона.
