## Сетевые драйверы Docker

**По умолчанию существуют/создаються три вида сетей в докере: bridge, none, host**

| Драйвер | Изоляция | Производительность | Основной сценарий использования |
| :--- | :--- | :--- | :--- |
| `bridge` | Высокая (своя подсеть) | Хорошая (через NAT) | **Сеть по умолчанию.** Изолированные контейнеры на одном хосте. |
| `host` | Отсутствует | Максимальная | Когда нужна высокая производительность и не важна изоляция. |
| `none` | Полная | N/A | Для контейнеров, которым не требуется сеть (например, для пакетных заданий). |
| `overlay` | Высокая (между хостами) | Хорошая | **Docker Swarm.** Для связи контейнеров, запущенных на разных хостах. |
| `macvlan` | Средняя (на уровне L2) | Высокая | Интеграция контейнеров в физическую сеть как полноценных устройств. |

### Bridge: Сеть по умолчанию

- **Принцип работы:** Создает на хосте виртуальный сетевой мост (обычно `docker0`), который действует как шлюз для контейнеров. Каждому контейнеру выдается IP-адрес из внутренней подсети.
- **Связь:** Контейнеры в одной bridge-сети могут общаться друг с другом по IP-адресам. В пользовательских сетях (`docker network create`) — и по именам.
- **Доступ извне:** Требуется явный проброс портов (`-p ХОСТ:КОНТЕЙНЕР`).
- **Реализация:** Для каждого контейнера создается пара виртуальных Ethernet-интерфейсов (`veth`): один конец находится в сетевом пространстве имен контейнера (`eth0`), а другой подключен к мосту `docker0` на хосте.

### Host: Прямой доступ к сети хоста

- **Принцип работы:** Отключает сетевую изоляцию. Контейнер использует сетевой стек хост-машины напрямую.
- **Порты:** Все порты, открытые приложением в контейнере, открываются на IP-адресе хоста.
- **Недостатки:** Снижается безопасность, возможны конфликты портов.

### Overlay: Сети для кластеров (глубокое погружение)

Overlay-сети используются в [Docker Swarm](./docker_swarm.md) для связи контейнеров, запущенных на разных хостах. Виртуальная сеть "накладывается" поверх физической, позволяя контейнерам на разных машинах общаться так, будто они находятся в одной подсети.

Когда вы запускаете сервис в Swarm, по умолчанию к нему присоединяется несколько сетей, каждая из которых решает свои задачи.

#### Принцип работы Overlay и VXLAN

Overlay-сеть создает общую подсеть для контейнеров, даже если они запущены на разных физических хостах. Это достигается с помощью технологии **VXLAN (Virtual Extensible LAN)**.

**Как работает VXLAN:**

1.  Docker инкапсулирует L2-фреймы (Ethernet-кадры) от контейнеров в L4-пакеты (UDP/IP).
2.  Эти UDP-пакеты отправляются между хостами Swarm через стандартную физическую сеть. Docker использует для этого порт `4789`.
3.  На принимающем хосте Docker "распаковывает" UDP-пакет, извлекает из него исходный Ethernet-кадр и направляет его в нужный контейнер.

Для контейнеров этот процесс полностью прозрачен — они видят друг друга так, будто подключены к одному виртуальному свитчу.

**Пример на практике:**

Если запустить `tcpdump` на одном из хостов Swarm во время пинга между контейнерами на разных машинах, можно увидеть два слоя трафика:
-   **Внешний слой:** UDP-трафик между IP-адресами хостов по порту 4789.
-   **Внутренний слой:** ICMP-трафик (пинг) между IP-адресами контейнеров.

#### Шифрование Overlay-сетей

По умолчанию трафик внутри VXLAN-туннелей не шифруется. Это значит, что любой, кто может перехватить трафик между хостами, увидит и трафик между контейнерами.

Чтобы это исправить, Docker позволяет включить автоматическое IPSec-шифрование при создании сети:

```bash
docker network create --driver overlay --opt encrypted my-secure-overlay
```
При использовании этой опции весь трафик внутри VXLAN-туннеля будет зашифрован.

#### Системные сети в Swarm: ingress и docker_gwbridge

Помимо пользовательских overlay-сетей, в Swarm-кластере по умолчанию создаются две важные системные сети.

1.  **`ingress`**
    -   **Тип:** `overlay`.
    -   **Назначение:** Обработка **входящего трафика из внешнего мира** к сервисам кластера.
    -   **Балансировка нагрузки:** Когда вы публикуете порт сервиса (например, `-p 8080:80`), Swarm Routing Mesh направляет трафик с порта `8080` *любого* из хостов кластера на нужный контейнер, даже если он работает на другой машине. Балансировка нагрузки выполняется с помощью **IPVS (IP Virtual Server)**, который работает внутри специального контейнера, подключенного к `ingress`-сети.

2.  **`docker_gwbridge`**
    -   **Тип:** `bridge`.
    -   **Назначение:** Служит шлюзом для **исходящего трафика** из контейнеров во внешний мир (например, когда контейнер обращается к внешнему API или базе данных в интернете).
    -   На каждом хосте кластера создается свой bridge-интерфейс `docker_gwbridge`, который соединяет overlay-сети с физической сетью хоста.

#### Заключение

Контейнер, запущенный в Swarm, обычно подключен к нескольким сетям одновременно:

-   **Пользовательская `overlay`-сеть:** Для прямой связи между контейнерами одного сервиса на разных хостах.
-   **`ingress` (overlay):** Для получения трафика извне и его балансировки.
-   **`docker_gwbridge` (bridge):** Для доступа контейнеров во внешний мир.

### Macvlan: Контейнер как физическое устройство

- **Принцип работы:** Позволяет присвоить контейнеру собственный MAC-адрес. Контейнер подключается напрямую к физической сети через интерфейс хоста и получает IP-адрес из той же подсети.
- **Сценарий:** Полезно для легаси-приложений или сетевых инструментов, которые должны быть видны в сети как отдельные устройства.

### Совместное использование сетевого пространства имен: `--network container:`

Помимо стандартных драйверов, Docker предоставляет мощную возможность запустить контейнер в сетевом пространстве имен (network namespace) другого, уже существующего контейнера. Это позволяет им разделять один и тот же сетевой стек, включая IP-адрес и интерфейс `localhost`.

```bash
docker run --network container:<имя_или_ID_целевого_контейнера> ...
```

**Как это работает:**

1.  Вы запускаете первый, "целевой" контейнер (например, `my-app`). Docker создает для него сетевое пространство имен.
2.  Вы запускаете второй, "присоединяемый" контейнер с флагом `--network container:my-app`. Docker не создает для него новый сетевой стек, а помещает его процессы в пространство имен контейнера `my-app`.

**Результат:**

*   Оба контейнера имеют один и тот же IP-адрес.
*   Процессы из одного контейнера могут обращаться к портам, открытым в другом контейнере, через `localhost`. Например, если `my-app` слушает порт `8080`, второй контейнер может подключиться к нему по `localhost:8080`.
*   Сетевая изоляция между этими двумя контейнерами отсутствует.

**Практические кейсы:**

1.  **Sidecar-контейнеры для отладки и мониторинга:**

    *   Вы можете запустить контейнер с набором сетевых утилит (`tcpdump`, `netstat`, `ping`) и присоединить его к работающему контейнеру приложения, чтобы анализировать его трафик, не устанавливая эти утилиты в основной образ.
    *   **Пример:**
        ```bash
        # Запускаем основной контейнер(имя контейнера будет my-app и собираеться он из образа nginx:1.25.5)
        docker run -d --name my-app nginx:1.25.5

        # Запускаем "sidecar" для отладки в том же network namespace
        # Утилита nicolaka/netshoot содержит множество сетевых инструментов
        docker run --rm -it --network container:my-app nicolaka/netshoot:v0.12.0
        ```
        Теперь внутри контейнера `netshoot` вы можете выполнять команды вроде `tcpdump -i lo` или `netstat -tulpn` и видеть сетевую активность контейнера `my-app`.

## DNS и разрешение имен

В сетях `bridge`, созданных пользователем, Docker предоставляет встроенный DNS-сервер (`127.0.0.11`), который позволяет контейнерам обращаться друг к другу по именам.

1.  При подключении к сети Docker прописывает свой DNS-сервер в файл `/etc/resolv.conf` внутри контейнера.
2.  Когда один контейнер (например, `web`) пытается обратиться к другому (например, `db`), он отправляет DNS-запрос на `127.0.0.11`.
3.  Docker DNS разрешает имя `db` в его внутренний IP-адрес, позволяя установить соединение.

> **NOTE:** В сети `bridge` по умолчанию разрешение имен не работает. Всегда создавайте собственные сети для приложений.

### Утилита `brctl` для анализа bridge-сетей

Для более глубокого анализа сетей типа `bridge` на хосте можно использовать утилиту `brctl`. Она позволяет просматривать существующие сетевые мосты и интерфейсы, подключенные к ним.

```bash
sudo apt-get update && sudo apt-get install -y bridge-utils
```

Команда `brctl show` отображает все активные сетевые мосты на хосте.

```sh
brctl show
```
```
bridge name     bridge id               STP enabled     interfaces
docker0         8000.0242ac110002       no              veth1a2b3c4
                                                        veth5d6e7f8
```
*   **`bridge name`**: Имя сетевого моста. По умолчанию Docker создает мост с именем `docker0`.
*   **`bridge id`**: Уникальный идентификатор моста.
*   **`STP enabled`**: Показывает, включен ли протокол STP (Spanning Tree Protocol).
*   **`interfaces`**: Самая важная колонка в контексте Docker. Здесь перечислены все сетевые интерфейсы, подключенные к мосту. Для каждого запущенного контейнера, использующего сеть `bridge`, здесь будет отображаться его виртуальный Ethernet-интерфейс (`veth`).

Эти `veth`-интерфейсы представляют собой **виртуальные "патч-корды"** (вет-пары): один конец "кабеля" подключен к сетевому пространству имен контейнера (и виден внутри него как `eth0`), а другой — к мосту `docker0` на хосте. Именно через эту связь контейнеры в bridge-сети общаются друг с другом и с внешним миром (через NAT).

## Управление сетями: Основные команды

| Команда | Описание |
| :--- | :--- |
| `docker network ls` | Показать все сети. |
| `docker network create <имя>` | Создать новую сеть (по умолчанию `bridge`). |
| `docker network create --driver bridge --subnet=... --gateway=... <имя>` | Создать сеть с указанием драйвера, подсети и шлюза. |
| `docker network inspect <имя>` | Показать детальную информацию о сети, включая подключенные контейнеры. |
| `docker network connect <сеть> <контейнер>` | Подключить работающий контейнер к сети. |
| `docker network disconnect <сеть> <контейнер>` | Отключить контейнер от сети. |
| `docker run --network <сеть> ...` | Запустить контейнер, сразу подключив его к указанной сети. |

## Решение проблем: Docker и `iptables`

Docker активно использует `iptables` для реализации сетевой изоляции и проброса портов. Глубокое понимание `iptables` необходимо для решения сложных сетевых проблем. Подробное руководство находится в документе [IPTables: Основы и настройка файрвола](../Security/iptables.md).

**Проблема:** Вы настроили `iptables` с политикой по умолчанию `DROP` для цепочки `FORWARD`. После запуска контейнера с пробросом порта (`-p 8080:80`) он доступен по `localhost:8080`, но недоступен извне.

**Причина:** Трафик, перенаправляемый в контейнер, проходит через цепочку `FORWARD` в `iptables`. Политика `DROP` блокирует эти пакеты.

```sh
# Проверьте счетчики пакетов. Вы увидите, что они растут в цепочке FORWARD.
sudo iptables -L FORWARD -v -n
```

Необходимо явно разрешить `iptables` перенаправлять трафик, связанный с Docker. Docker создает собственную цепочку `DOCKER-USER` именно для таких правил.

```sh
# Разрешить установленные и связанные соединения к контейнерам
# Это наиболее безопасный и рекомендуемый способ.
sudo iptables -I DOCKER-USER -i <внешний_интерфейс> -o docker0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

# Разрешить трафик из контейнеров наружу
sudo iptables -I DOCKER-USER -i docker0 -o <внешний_интерфейс> -j ACCEPT
```
*Замените `<внешний_интерфейс>` на имя вашего реального сетевого интерфейса (например, `eth0`).*

### Docker, `iptables` и `nftables`

В современных дистрибутивах Linux (Debian 10+, Ubuntu 20.04+) `nftables` является фреймворком межсетевого экрана по умолчанию, заменяя `iptables`. Однако для обратной совместимости используется утилита `iptables`, которая работает поверх `nftables`.

Docker (начиная с версии 20.10) определяет, какой бэкенд используется в системе, и взаимодействует с ним.

**Проблемы совместимости**

Иногда могут возникать конфликты, если другие службы (например, `firewalld`) напрямую управляют `nftables`, а Docker пытается управлять правилами через `iptables-nft` (слой совместимости). Это может приводить к «затиранию» правил Docker после перезапуска `firewalld`.

**Решение: Использование `iptables-legacy`**

Если вы сталкиваетесь с такими проблемами, вы можете явно указать Docker использовать «классический» `iptables-legacy` вместо `iptables-nft`.

1.  **Переключите системные утилиты на `iptables-legacy`:**
    ```bash
    # Для Debian/Ubuntu
    sudo update-alternatives --set iptables /usr/sbin/iptables-legacy
    sudo update-alternatives --set ip6tables /usr/sbin/ip6tables-legacy
    ```

2.  **Перезапустите Docker:**
    ```bash
    sudo systemctl restart docker
    ```

После этого Docker будет создавать свои правила в `iptables-legacy`, изолируя их от `nftables` и служб, которые им управляют. Это решает большинство проблем совместимости на современных системах.
