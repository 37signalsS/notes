# Обзор команд Docker CLI

## Управление жизненным циклом контейнера

### Определения

- **Жизненный цикл контейнера**: Процесс от создания и запуска до остановки и удаления контейнера.
- **Интерактивные команды**: Команды, позволяющие взаимодействовать с запущенным контейнером.

### Основные понятия и команды

#### Создание, запуск и остановка

| Команда | Описание |
| :--- | :--- |
| `docker run <образ>` | Создает и запускает контейнер. Флаги: `-d` (фоновый режим), `--rm` (удалить после завершения). |
| `docker start <контейнер>` | Запускает остановленный контейнер. |
| `docker stop <контейнер>` | Корректно останавливает контейнер (сначала `SIGTERM`, затем `SIGKILL`). |
| `docker restart <контейнер>`| Перезапускает контейнер. |
| `docker pause / unpause` | "Замораживает" и "размораживает" все процессы в контейнере. |
| `docker rm <контейнер>` | Удаляет остановленный контейнер. Флаг `-f` для принудительного удаления. |

#### Взаимодействие с контейнером

| Команда | Описание |
| :--- | :--- |
| `docker exec -it <контейнер> <команда>` | Выполняет команду внутри запущенного контейнера (например, `bash`). |
| `docker attach <контейнер>` | Подключается к основному процессу (PID 1). Для отсоединения без остановки: **`Ctrl+P`, `Ctrl+Q`**. |
| `docker cp <откуда> <куда>` | Копирует файлы между хостом и контейнером. |
| `docker update <контейнер>` | Обновляет ресурсы (CPU, память) запущенного контейнера без его перезапуска. |

### Практические сценарии

#### Сценарий 1: Быстрое изменение конфига на лету

1. **Зайти в контейнер:** `docker exec -it my_container /bin/sh`
2. **Внести правки в конфиг.**
3. **Перезапустить контейнер:** `docker restart my_container`

Изменения будут применены, так как они сохраняются в `writable layer` контейнера, и при перезапуске процесс приложения перечитывает конфиг.

#### Сценарий 2: Динамическое обновление ресурсов

В production-среде контейнер может начать потреблять слишком много RAM. Для ограничения памяти без остановки контейнера:

```bash
docker update --memory 1G my-container
```

Это установит новый лимит памяти в 1GB. Также можно управлять ресурсами CPU (`--cpus`, `--cpu-shares`).

#### Сценарий 3: Зачем `docker start` нужен в реальной жизни?

- **Сохранение состояния:** `docker start` сохраняет данные в `writable layer` между перезапусками. Критично для stateful-приложений, если данные не вынесены в volume.
- **Экономия ресурсов в CI/CD:** Переиспользование контейнеров с предустановленными зависимостями (`stop`/`start`) ускоряет тестовые среды.
- **Отладка инцидентов:** Можно быстро остановить проблемный контейнер для анализа, а затем запустить его снова без пересоздания, минимизируя простой.
- **Управление ресурсами:** В средах с ограниченными ресурсами позволяет временно останавливать неиспользуемые сервисы и запускать их по требованию.

### Дополнительная информация

#### `docker stop` vs `docker pause`

- **`docker pause`**: "Замораживает" все процессы в контейнере. Состояние сохраняется в RAM, но CPU не потребляется. Используется для временного освобождения процессорных ресурсов без потери состояния.
- **`docker stop`**: Инициирует корректное завершение работы (`SIGTERM`). Если процесс не завершается за 10 секунд, Docker принудительно "убивает" его (`SIGKILL`). Память и CPU полностью освобождаются.

## 2. Управление образами

### Определения

- **Образ (Image)**: Неизменяемый read-only шаблон, содержащий все необходимое для запуска приложения (код, зависимости, системные библиотеки).
- **Тег (Tag)**: Метка-алиас, обычно обозначающая версию образа (например, `nginx:1.21`, `ubuntu:latest`).
- **Слой (Layer)**: Часть файловой системы образа, создаваемая одной инструкцией в `Dockerfile`. Слои переиспользуются для кэширования и экономии места.

### Основные понятия и команды

| Команда | Описание |
| :--- | :--- |
| `docker images` или `docker image ls` | Показывает все образы на хосте. |
| `docker build -t <имя>:<тег> .` | Собирает образ из `Dockerfile`. |
| `docker pull <образ>:<тег>` | Скачивает образ из registry. |
| `docker push <образ>:<тег>` | Загружает образ в registry. |
| `docker rmi <образ>` | Удаляет образ. |
| `docker tag <source> <target>` | Создает новый тег (алиас) для существующего образа. |
| `docker history <образ>` | Показывает слои, из которых состоит образ. |

### Практические сценарии

#### Анализ слоев образа (`history`)

Команда `docker history` показывает все слои, их размер и команды, которыми они были созданы. Это полезный инструмент для оптимизации `Dockerfile`, так как позволяет выявить "тяжелые" или ненужные слои.

**Пример вывода:**

```
IMAGE          CREATED         CREATED BY                                      SIZE
a2491d99c52f   3 weeks ago     /bin/sh -c #(nop)  CMD ["/bin/sh"]              0B
<missing>      3 weeks ago     /bin/sh -c #(nop) ADD file:7d565a58bb...       5.53MB
```

Здесь видно, что добавление файла на втором слое увеличило размер образа на 5.53MB.

## 3. Инспекция и мониторинг

### Определения

- **Инспекция**: Процесс получения детальной низкоуровневой информации об объектах Docker (контейнерах, образах, сетях) в формате JSON.
- **Мониторинг**: Процесс наблюдения за метриками производительности и логами работающих контейнеров.

### Основные понятия и команды

| Команда | Описание |
| :--- | :--- |
| `docker ps` | Показывает запущенные контейнеры. Флаг `-a` для отображения всех. |
| `docker inspect <объект>` | Выводит подробную информацию об объекте в JSON. |
| `docker stats <контейнер>` | Показывает потребление ресурсов (CPU, RAM, I/O) в реальном времени. |
| `docker top <контейнер>` | Показывает процессы, запущенные внутри контейнера. |
| `docker port <контейнер>` | Отображает маппинг портов контейнера на хост. |

#### Команды для работы с логами

| Команда | Описание |
| :--- | :--- |
| `docker logs <контейнер>` | Показать все логи для контейнера. |
| `docker logs -f <контейнер>` | Выводить логи в реальном времени (режим `follow`). |
| `docker logs --tail N <контейнер>`| Показать последние `N` строк логов. |
| `docker logs --since 10m <контейнер>` | Показать логи за последние 10 минут. |

### Практические сценарии

#### Сценарий 1: Получение IP-адреса контейнера

С помощью `docker inspect` и Go-шаблонов можно извлекать конкретные поля из JSON-вывода.

```bash
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' my-container
```

#### Сценарий 2: Логирование Nginx в Docker

Чтобы `docker logs` мог собирать логи, приложение должно писать их в `STDOUT` и `STDERR`. Nginx по умолчанию пишет в файлы. Чтобы перенаправить его логи в стандартные потоки, добавьте в `Dockerfile` следующие команды:

```dockerfile
# Перенаправляем access и error логи Nginx в stdout и stderr
RUN ln -sf /dev/stdout /var/log/nginx/access.log && \
    ln -sf /dev/stderr /var/log/nginx/error.log
```

### Дополнительная информация

#### Best practice: логирование в `STDOUT`/`STDERR`

Приложения в контейнерах должны писать логи в стандартные потоки вывода `STDOUT` и `STDERR`. Это центральная концепция Docker-логирования, позволяющая собирать, агрегировать и обрабатывать логи с помощью стандартных инструментов Docker (`docker logs`) или специализированных драйверов логирования.

## 4. Управление сетями и томами

### Определения

- **Сеть (Network)**: Обеспечивает сетевую изоляцию и возможность коммуникации между контейнерами и с внешним миром.
- **Том (Volume)**: Механизм для персистентного хранения данных, управляемый Docker. Данные в томах сохраняются даже после удаления контейнера.

### Основные понятия и команды

| Команда | Описание |
| :--- | :--- |
| `docker volume ls` / `create` / `inspect` | Управление томами. |

## 5. Управление и очистка системы

### Определения

- **Очистка (Prune)**: Процесс удаления неиспользуемых объектов Docker (контейнеров, образов, томов, сетей) для освобождения дискового пространства.
- **"Висячие" образы (Dangling Images)**: Слои образа, которые существуют на хосте, но на них больше не ссылается ни один тегированный образ. В выводе `docker images` они отображаются с тегом `<none>`.

### Основные понятия и команды

| Команда | Описание |
| :--- | :--- |
| `docker system prune` | **Основная команда.** Удаляет все остановленные контейнеры, "висячие" образы и неиспользуемые сети. |
| `docker container prune` | Удаляет все остановленные контейнеры. |
| `docker image prune` | Удаляет "висячие" образы. С флагом `-a` удаляет все неиспользуемые образы. |
| `docker volume prune` | Удаляет все неиспользуемые тома. |
| `docker system prune -a --volumes` | **(Опасно)** Глобальная очистка: удаляет всё, что не используется, включая тома. |

### Практические сценарии

#### Поиск и удаление "висячих" образов

"Висячие" образы безвредны, но занимают дисковое пространство. Их рекомендуется периодически удалять.

1. **Найти "висячие" образы:**

    ```bash
    docker images -f "dangling=true"
    ```

2. **Удалить "висячие" образы:**

    ```bash
    docker image prune
    ```

### Дополнительная информация

#### Причины появления "висячих" образов

1. **Пересборка образа с тем же тегом:** Когда вы пересобираете образ с существующим тегом, старый образ теряет тег и становится "висячим".
2. **Промежуточные слои:** Во время сборки `Dockerfile` создаются временные слои. Если сборка прерывается, они могут остаться без ссылок.
3. **Изменение базового образа:** Если вы обновили базовый образ в `FROM` и пересобрали приложение, старые зависимые слои могут стать "висячими".
