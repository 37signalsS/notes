# Команды Docker CLI

## Определения

**Docker CLI** — интерфейс командной строки для управления контейнерами, образами, сетями и томами. Работает через REST API демона dockerd.

## Основные концепции

### Идентификация контейнеров

**Container ID:** при запуске контейнера Docker выводит полный ID (64 символа). Для работы с контейнером достаточно указать уникальную подстроку (обычно 3-12 символов) — Docker сам найдёт нужный контейнер.

```bash
# Полный ID: a1f74bbb327c...
# Эти команды эквивалентны (если нет других контейнеров, начинающихся с a1f):
docker stop a1f74bbb327c
docker stop a1f
docker stop a1
```

Если несколько контейнеров имеют одинаковый префикс ID, нужно указать больше символов для уникальности.

**Автоматические имена:** если не указать `--name`, Docker назначит случайное имя (например, `gracious_celshine`, `romantic_thompson`). Это гарантирует уникальность, но для автоматизации и скриптов лучше использовать явные имена.

### Запуск контейнера и проброс портов

```bash
# Запуск контейнера в фоновом режиме с пробросом портов
docker run -d -p 8080:80 nginx:latest
```

**Флаг `-p` (port mapping):**

Формат: `-p <порт_хоста>:<порт_контейнера>`

- **Порт хоста** (8080) — порт на машине, где запущен Docker. Должен быть свободен — если другой процесс уже слушает этот порт, Docker вернёт ошибку `port is already allocated`
- **Порт контейнера** (80) — порт, на котором работает приложение внутри контейнера. Если указать неверный порт, запросы будут уходить в никуда (`Connection Refused`)
- Сетевое пространство хоста единое — два контейнера не могут пробросить один и тот же порт хоста
- По умолчанию контейнер изолирован — без `-p` доступ к его портам извне невозможен

**Важно знать порт приложения:** приложение внутри контейнера должно слушать тот порт, на который вы проксируете трафик. Если приложение работает на порту 8080, а вы сделали `-p 8080:80`, трафик будет уходить на порт 80, где никто не слушает. Узнать порт приложения можно через:

- Инструкцию `EXPOSE` в Dockerfile
- Конфигурационные файлы приложения
- `docker inspect <контейнер>` — подробная информация о конфигурации контейнера
- Проверку открытых портов запущенного процесса внутри контейнера

```bash
# Проверка: запрос к хосту на проброшенный порт — получим ответ от Nginx
curl localhost:8080  # → HTTP 200 от Nginx

# Запрос напрямую к порту контейнера (не сработает без проброса)
curl localhost:80  # → Connection Refused (если Nginx не запущен на хосте)

# Проверка доступности после остановки контейнера
curl localhost:8080  # → Connection Refused (контейнер остановлен)
```

**Флаг `-d` (detached):** запускает контейнер в фоновом режиме. Без этого флага контейнер работает в foreground и завершается вместе с процессом терминала.

### Основные команды

| Команда | Описание |
| :--- | :--- |
| `docker run <образ>` | Создает и запускает контейнер. Флаги: `-d` (фон), `-p` (проброс портов), `--rm` (удалить после) |
| `docker start <контейнер>` | Запускает остановленный контейнер |
| `docker stop <контейнер>` | Останавливает (`SIGTERM`, затем `SIGKILL` через 10с) |
| `docker restart <контейнер>` | Перезапускает контейнер |
| `docker pause / unpause` | Замораживает/размораживает процессы с сохранением текущего состояния в RAM |
| `docker rm <контейнер>` | Удаляет остановленный контейнер |
| `docker exec -it <контейнер> <команда>` | Выполняет команду внутри контейнера |
| `docker attach <контейнер>` | Подключается к PID 1 (отсоединение: `Ctrl+P`, `Ctrl+Q`) |
| `docker update <контейнер>` | Обновляет ресурсы (CPU, память) без перезапуска |
| `docker cp <откуда> <куда>` | Копирует файлы между хостом и контейнером |

**Политики перезапуска (`--restart`):**

| Политика | Поведение |
| :--- | :--- |
| `no` (по умолчанию) | Никогда не перезапускать |
| `on-failure[:max-retries]` | Только при ошибке (exit code ≠ 0) |
| `always` | Всегда перезапускать, даже после `docker stop` |
| `unless-stopped` | Всегда, кроме случаев явной остановки (**рекомендуется для production**) |

### Управление образами

| Команда | Описание |
| :--- | :--- |
| `docker images` | Список локальных образов |
| `docker build -t <имя>:<тег> .` | Сборка образа из `Dockerfile` (Legacy) |
| `docker buildx build` | Современная мультиплатформенная сборка (**рекомендуется**) |
| `docker pull <образ>:<тег>` | Скачивание из реестра |
| `docker push <образ>:<тег>` | Загрузка в реестр |
| `docker rmi <образ>` | Удаление образа |
| `docker tag <source> <target>` | Добавление тега |
| `docker history <образ>` | Показывает слои образа |

**Рекомендация:** начиная с версии Docker 23.0, используйте `buildx` для кросс-платформенной сборки (например, AMD64 и ARM64 одновременно). Подробнее: **[BuildKit и Buildx](./Dockerfile/dockerfile_buildkit.md)**.


### Инспекция и мониторинг

| Команда | Описание |
| :--- | :--- |
| `docker ps` | Запущенные контейнеры (`-a` — все, включая остановленные) |
| `docker inspect <объект>` | Детальная информация в JSON |
| `docker stats <контейнер>` | Метрики ресурсов в реальном времени |
| `docker top <контейнер>` | Процессы внутри контейнера |
| `docker port <контейнер>` | Маппинг портов |
| `docker logs <контейнер>` | Вывод логов (`-f` — follow, `--tail N`, `--since 10m`) |

### Очистка системы (Prune)

| Команда | Описание |
| :--- | :--- |
| `docker system prune` | Удаление остановленных контейнеров, dangling образов, сетей |
| `docker container prune` | Удаление остановленных контейнеров |
| `docker image prune` | Удаление dangling образов (`-a` — все неиспользуемые) |
| `docker volume prune` | Удаление неиспользуемых томов |
| `docker system prune -a --volumes` | **Опасно:** удаляет всё, включая тома |

**Dangling images** — образы без тега (`<none>`), появляются при пересборке с тем же тегом.

## Практические сценарии

### Быстрое изменение конфигурации

```bash
# Вход в контейнер
docker exec -it my_container /bin/sh

# Внести правки в конфиг

# Перезапуск
docker restart my_container
```

Изменения сохраняются в writable layer, приложение перечитывает конфиг при старте.

### Динамическое обновление ресурсов

```bash
# Ограничение памяти без остановки
docker update --memory 1G my-container

# Ограничение CPU
docker update --cpus 1.5 my-container
```

### Публикация портов: эфемерные и `-P`

**Эфемерные порты** — когда неважно, на каком порту хоста будет доступен сервис, Docker самостоятельно выбирает свободный порт из диапазона эфемерных портов ОС.

```bash
# Указан только порт контейнера — Docker выберет порт хоста автоматически
docker run -d -p 80 nginx:latest

# Проверить маппинг
docker ps
# → PORTS: 0.0.0.0:54772->80/tcp (случайный порт хоста 54772)
```

**Флаг `-P` (или `--publish-all`)** — публикует все порты, указанные в инструкции `EXPOSE` Dockerfile, на случайные эфемерные порты хоста.

```bash
# Все EXPOSE-порты образа будут опубликованы на случайных портах
docker run -d -P nginx:latest

# Проверка маппинга
docker port <container>
# → 80/tcp -> 0.0.0.0:32768
```

> **Важно:** опубликованный порт доступен на **всех сетевых интерфейсах** хоста по умолчанию. Для чувствительных сервисов (БД, Redis) используйте привязку к localhost: `-p 127.0.0.1:5432:5432`. Подробнее — [Docker Networking](./Docker_network/docker_network.md).

### Переменные окружения (`-e` и `--env-file`)

**Флаг `-e`** — устанавливает переменную окружения в контейнере. Каждый флаг задаёт одну переменную.

```bash
# Установка одной переменной
docker run -d -e FOO=bar alpine env

# Несколько переменных — каждый через отдельный флаг
docker run -d -e POSTGRES_PASSWORD=secret -e POSTGRES_USER=admin postgres:16-alpine
```

Подробнее о переменных окружения PostgreSQL см. **[Развертывание PostgreSQL в Docker](../Databases/PostgreSQL/Operations/docker_deployment.md)**.

**Флаг `--env-file`** — загружает переменные из файла. Удобно, когда переменных много и команда становится громоздкой.

```bash
# Файл my.env:
# DB_HOST=postgres
# DB_PORT=5432
# APP_MODE=production

docker run -d --env-file my.env myapp:latest
```

> **Безопасность:** не храните секреты в `.env`-файлах в открытом доступе. Для секретов используйте [Docker Secrets](./Docker_security/secrets_management.md).

### Ограничение ресурсов при запуске

По умолчанию контейнеры не ограничены в потреблении ресурсов. На shared-хостах это может привести к тому, что один контейнер заберёт всю память или CPU.

| Флаг | Описание |
|:-----|:---------|
| `--memory` / `-m` | Лимит оперативной памяти (например, `512m`, `1g`) |
| `--cpus` | Квота CPU в ядрах (`0.5` = половина ядра, `1.5` = полтора ядра) |

```bash
# Ограничение: 512 МБ RAM, 0.5 CPU
docker run -d \
  --name pg-prod \
  --memory 512m \
  --cpus 0.5 \
  -e POSTGRES_PASSWORD=secret \
  -p 127.0.0.1:5432:5432 \
  postgres:16-alpine
```

**Поведение при превышении лимитов:**

- **Память:** если контейнер превышает `--memory`, OOM-killer убивает процесс. Контейнер перезапускается согласно политике `--restart`.
- **CPU:** при превышении `--cpus` контейнер не убивается — процессы просто тротлятся (замедляются).

**Мониторинг в реальном времени:**

```bash
docker stats
# → CONTAINER   CPU %   MEM USAGE / LIMIT   MEM %
#   python-app  12.5%   256MiB / 512MiB     50%
```

Подробнее о встроенных средствах мониторинга: [Нативные метрики Docker](./Docker_metrics/docker_native_metrics.md).

### Переопределение CMD и ENTRYPOINT

При запуска контейнера можно переопределить команды, указанные в образе.

**Переопределение CMD** — указывается после имени образа:

```bash
# Образ по умолчанию запускает nginx, но мы хотим bash
docker run -it nginx:latest /bin/bash

# Переопределение с флагами
docker run -d postgres:16-alpine postgres -c listen_addresses='0.0.0.0'
```

**Переопределение ENTRYPOINT** — флаг `--entrypoint` указывается **до** имени образа:

```bash
# Заменяем ENTRYPOINT на /bin/sh
docker run -it --entrypoint /bin/sh nginx:latest

# Проверка текущего ENTRYPOINT и CMD
docker inspect --format='{{.Config.Entrypoint}}' <image>
docker inspect --format='{{.Config.Cmd}}' <image>
```

> **Порядок важен:** `--entrypoint` ставится до образа, а команда (CMD) — после образа.

Подробнее о наследовании и переопределении см. в разделе **[Практические сценарии переопределения](./Dockerfile/Instructions/practical_scenarios.md)**.

### Запуск нескольких инстансов одного сервиса

```bash
# Первый инстанс PostgreSQL
docker run -d --name pg1 -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres:16-alpine

# Второй инстанс — другой порт хоста, чтобы избежать конфликта
docker run -d --name pg2 -e POSTGRES_PASSWORD=secret -p 5433:5432 postgres:16-alpine

# Третий — ещё один порт
docker run -d --name pg3 -e POSTGRES_PASSWORD=secret -p 5434:5432 postgres:16-alpine
```

### Получение IP-адреса контейнера

```bash
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' my-container
```

### Логирование Nginx в STDOUT/STDERR

Приложения должны писать логи в стандартные потоки для сбора через `docker logs`:

```dockerfile
RUN ln -sf /dev/stdout /var/log/nginx/access.log && \
    ln -sf /dev/stderr /var/log/nginx/error.log
```

### Поиск и удаление dangling образов

```bash
# Найти
docker images -f "dangling=true"

# Удалить
docker image prune
```

## Дополнительная информация

**Различия `stop` vs `pause`:**

- `pause` — замораживает процессы (сохраняет RAM, не потребляет CPU)
- `stop` — корректная остановка (`SIGTERM` → `SIGKILL`), память и CPU освобождаются
