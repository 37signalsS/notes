# Лучшие практики сборки образов

## 1. Используйте минималистичные образы

Чем меньше компонентов в вашем образе, тем меньше поверхность атаки. Избегайте использования полноценных дистрибутивов (таких как `ubuntu` или `centos`), если они не являются строго необходимыми.

**Distroless-образы от Google** — это базовые образы, которые содержат только ваше приложение и его runtime-зависимости (например, `glibc`, `openssl`).

**Что в них отсутствует:**
-   Оболочки (`/bin/sh`, `bash`)
-   Менеджеры пакетов (`apt`, `apk`)
-   Стандартные утилиты (`ls`, `ps`, `curl`, `wget`)

Это значительно усложняет жизнь злоумышленнику, попавшему в контейнер, так как у него нет привычных инструментов для разведки и атаки.

**Пример: Сборка Go-приложения с помощью Distroless**
```dockerfile
# Этап 1: Сборка
# Используем полноценный образ Go для компиляции
FROM golang:1.25.1-bookworm as builder

WORKDIR /app
COPY . .

# Собираем статически скомпилированный бинарный файл
RUN CGO_ENABLED=0 GOOS=linux go build -o my-app .

# Этап 2: Создание финального образа
# Используем базовый образ distroless
FROM gcr.io/distroless/static-debian12

# Копируем только скомпилированный бинарный файл из этапа сборки
COPY --from=builder /app/my-app /

# Указываем команду для запуска
CMD ["/my-app"]
```

**Главный компромисс: Сложность отладки**
Поскольку в образе нет shell, стандартная команда `docker exec -it my-container /bin/sh` не сработает. Эта проблема решаема с помощью специальных техник.

> **Подробное руководство по отладке distroless-контейнеров находится в [руководстве по отладке](../docker_troubleshooting.md#отладка-контейнеров-без-shell-distroless).**

#### `scratch` vs. `distroless`

И `scratch`, и `distroless` нацелены на создание минималистичных образов, но подходят для разных сценариев.

| Характеристика | `FROM scratch` | `FROM gcr.io/distroless/...` |
| :--- | :--- | :--- |
| **Содержимое** | **Абсолютно пустой.** Нет ничего: ни файлов, ни библиотек, ни shell. | **Минимальный набор.** Содержит только приложение и его runtime-зависимости (например, `glibc`, `openssl`, CA-сертификаты). |
| **Размер** | Минимально возможный (размер вашего бинарника). | Чуть больше, чем `scratch`, но значительно меньше, чем `alpine` или `debian`. |
| **Совместимость** | Только для **полностью статических** бинарных файлов (например, Go с `CGO_ENABLED=0`). | Поддерживает динамически-связанные приложения (C++, Java, Python) благодаря наличию `libc`. |
| **Безопасность** | Максимальная. Поверхность атаки равна нулю (кроме вашего приложения). | Очень высокая. Отсутствуют shell и пакетные менеджеры, что сильно затрудняет атаку. |
| **Сложность** | Высокая. Требует аккуратной сборки бинарника и ручного добавления необходимых файлов (например, CA-сертификатов). | Низкая. Работает "из коробки" для большинства приложений. |

**Когда что использовать:**
-   **`scratch`**: Идеальный выбор для приложений на **Go**, которые скомпилированы как статические бинарники.
-   **`distroless`**: Прагматичный выбор для большинства других языков (**Python, Java, Node.js, C++**) и для Go-приложений, которым нужны базовые функции ОС (например, работа с DNS, TLS-сертификаты).

## 2. Проверяйте конфигурацию по умолчанию в базовых образах

Никогда слепо не доверяйте настройкам по умолчанию, даже в официальных образах. Они часто оптимизированы для простоты запуска, а не для безопасности.

> #### Пример: Небезопасные настройки в официальном образе PostgreSQL
>
> Официальный образ `postgres` по умолчанию использует метод аутентификации `trust` для всех локальных подключений. Это означает, что любой пользователь или процесс, имеющий доступ к контейнеру (даже из другого контейнера в той же Docker-сети), может подключиться к базе данных с правами суперпользователя **без пароля**.
>
> **Выдержка из `pg_hba.conf` по умолчанию в контейнере:**
> ```conf
> # "local" is for Unix domain socket connections only
> local   all             all                                     trust
> # IPv4 local connections:
> host    all             all             127.0.0.1/32            trust
> # IPv6 local connections:
> host    all             all             ::1/128                 trust
> ```
>
> Это серьезная уязвимость в production-среде.
>
> **Решение:** Всегда переопределяйте конфигурацию, предоставляя свой, более строгий файл `pg_hba.conf` и монтируя его в контейнер. Подробнее об этом можно прочитать в руководстве [**PostgreSQL в Docker**](../../Databases/PostgreSQL/postgresql_in_docker.md).
