# Проверка подлинности и целостности образов

## Определения

**Проверка подлинности и целостности** — это процесс, гарантирующий, что Docker-образ был получен из доверенного источника (подлинность) и не был изменён во время передачи (целостность).

## Базовые концепции

### 1. Целостность: Закрепление по дайджесту (Digest Pinning)

Клиенты контейнеров и рантаймы по умолчанию проверяют, что загруженные слои соответствуют дайджестам (sha256), указанным в манифесте образа. Это гарантирует, что слой не был изменён «по пути», если вы ссылаетесь на иммутабельный дайджест вместо изменяемого тега.

Эта проверка обеспечивает целостность, но не подтверждает, кто создал или подписал образ.

### 2. Подлинность: Цифровые подписи

Цифровые подписи криптографически доказывают, что образ был подписан определённым ключом или удостоверением. Это позволяет настроить политики, разрешающие запуск образов только от доверенных разработчиков.

Основные технологии:
- **Sigstore/Cosign**: Современный стандарт для подписи OCI-артефактов.
- **Notary v1 / Docker Content Trust (DCT)**: Устаревший механизм Docker.
- **Simple signing (GPG)**: Используется в экосистеме Podman/Skopeo.

### 3. Аттестации

Аттестации — это дополнительные метаданные, подписанные и прикреплённые к образу. Они содержат информацию о сборке (provenance) или составе ПО (SBOM).

## Практические сценарии

### 1. Закрепление образов по дайджесту

Всегда используйте дайджест вместо тега в production-окружениях.

**Docker:**
```bash
# Получить дайджест для тега
docker inspect alpine:latest --format '{{index .RepoDigests 0}}'
# docker.io/library/alpine@sha256:21a3deaa0d32a8057914f36584b5288d2e5ecc984380bc0118285c70fa8c9300

# Использовать дайджест
docker pull alpine@sha256:21a3deaa0d32a8057914f36584b5288d2e5ecc984380bc0118285c70fa8c9300
```

**containerd:**
```bash
ctr images pull docker.io/library/alpine@sha256:21a3deaa0d32a8057914f36584b5288d2e5ecc984380bc0118285c70fa8c9300
```

### 2. Политики доверия в экосистеме Podman/Skopeo

Инструменты `podman` и `skopeo` используют системный файл `/etc/containers/policy.json` для определения политик доверия. Можно требовать подписи от конкретного ключа или поставщика.

**Пример `policy.json`, требующий Sigstore-подпись:**
```json
{
  "default": [{"type": "insecureAcceptAnything"}],
  "transports": {
    "docker": {
      "my-registry.example.com": [
        {
          "type": "sigstoreSigned",
          "keyPath": "/etc/containers/cosign.pub"
        }
      ]
    }
  }
}
```
Проверка выполняется автоматически при `pull`:
```bash
podman pull my-registry.example.com/app@sha256:…
```

Подпись при публикации через `skopeo`:
```bash
skopeo copy 
  --sign-by developer@example.com 
  docker-daemon:app:1.2.3 
  docker://my-registry.example.com/app:1.2.3
```

### 3. Docker Content Trust (Notary v1)

Исторический механизм Docker для работы с подписями. Активируется через переменную окружения.

```bash
# Включить проверку
export DOCKER_CONTENT_TRUST=1

# Push подпишет образ (потребуется сгенерировать ключи)
docker push my-registry.example.com/app:1.2.3

# Pull проверит подпись
docker pull my-registry.example.com/app:1.2.3

# Просмотр информации о подписях
docker trust inspect --pretty my-registry.example.com/app:1.2.3
```
> **Примечание:** Этот механизм считается устаревшим в пользу Sigstore/Cosign.

### 4. Создание аттестаций (provenance) с помощью BuildKit

BuildKit может автоматически генерировать и прикреплять к образу аттестации о его происхождении (provenance), что соответствует спецификации [SLSA](https://slsa.dev/).

```bash
# Включить генерацию provenance
docker buildx build 
  --provenance=mode=max 
  -t my-registry.example.com/app:1.2.3 .
```

### Сопоставление механизмов

*   **Целостность по дайджесту**: Встроено в Docker/containerd; защищает от подмены контента.
*   **Подлинность по подписи**: Встроены политики в Podman/containers-image; подтверждают источник.
*   **Аттестации**: Встроены в BuildKit; расширяют доверие за счёт метаданных о сборке.
