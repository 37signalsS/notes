# Подписание и верификация Docker-образов

Данный документ описывает методы обеспечения безопасности цепочки поставок для контейнерных образов через механизмы контроля целостности и подтверждения подлинности.

## Определения

**Подписание и верификация образов** — криптографический процесс, гарантирующий, что образ был создан доверенным источником и не подвергался изменениям.

*   **Целостность (Integrity)** — гарантия неизменности содержимого образа (слоев, конфигурации). Реализуется через **дайджесты (digests)**.
*   **Подлинность (Authenticity)** — подтверждение авторства образа. Реализуется через цифровые подписи (Cosign, notation).
*   **Аттестация (Attestation)** — подписанные метаданные, описывающие процесс сборки (**Provenance**) или состав ПО (**[SBOM](./docker_sbom.md)**).

## Базовые концепции

### 1. Фиксация дайджеста (Digest Pinning) — основа целостности

Docker-образы используют контентно-адресуемое хранилище. Каждый образ имеет уникальный неизменяемый идентификатор — **дайджест** (SHA256).

В отличие от мутабельных **тегов** (например, `latest`, `v2.1`), которые могут быть переназначены на другой образ, дайджест гарантирует, что вы запускаете именно те байты, которые были проверены.
**Рекомендация:** В продуктивных средах и `docker-compose` файлах всегда используйте дайджесты.

### 2. Гарантия подлинности через подписи

Цифровая подпись связывает дайджест образа с идентичностью (разработчиком или CI/CD-системой).

| Технология | Статус | Описание |
| :--- | :--- | :--- |
| **Sigstore / Cosign** | **Рекомендуется** | Современный стандарт. Поддерживает "Keyless" подпись на базе OIDC (GitHub Actions, GitLab). |
| **Notary v2 / notation** | Актуально | Отраслевой стандарт (Microsoft, AWS). Ориентирован на классическую инфраструктуру PKI и сертификаты. |
| **Docker Content Trust (DCT)** | **Legacy** | Первая версия Notary. Сложна в управлении ключами, считается устаревшей. |

## Практические сценарии

### 1. Использование дайджестов (Digest Pinning)

```bash
# Получение дайджеста для образа
docker pull nginx:latest
docker inspect --format='{{index .RepoDigests 0}}' nginx:latest
# Результат: nginx@sha256:0cae2...

# Использование в Dockerfile
FROM nginx@sha256:0cae2...
```

### 2. Генерация аттестаций (Docker Buildx)

Современный BuildKit позволяет прикреплять SBOM и Provenance напрямую к манифесту образа как аттестации.

```bash
docker buildx build \
  --tag my-registry.com/app:v1 \
  --sbom=true \
  --provenance=mode=max \
  --push .
```
*Подробнее про состав компонентов:* **[Docker SBOM](./docker_sbom.md)**.

### 3. Подписание образа (Cosign Keyless)

Рекомендуемый способ для CI/CD, не требующий хранения секретных ключей. Использует OIDC-токен среды выполнения (например, GitHub Actions).

```bash
# Подписание в CI/CD (GitHub Actions автоматически предоставит токен)
cosign sign --yes my-registry.com/app:v1

# Верификация подписи
cosign verify \
  --certificate-identity "https://github.com/my-org/my-repo/.github/workflows/release.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  my-registry.com/app:v1
```
*Инструкции по установке и ключам:* **[Sigstore: Безопасность цепочки поставок](../../Security/Tools/sigstore.md)**.

### 4. Верификация в кластере (Admission Control)

Проверка подписей "руками" через CLI недостаточна. В Kubernetes для этого используются контроллеры допуска (**Kyverno**, **Ratify**, **Gatekeeper**).

Политика верификации в кластере гарантирует, что в `runtime` попадут только те образы, которые:
1.  Находятся в белом списке реестров.
2.  Имеют валидную подпись от доверенного издателя.
3.  Имеют прикрепленный SBOM и отчет об отсутствии уязвимостей.

## Дополнительная информация

**Docker Content Trust (DCT):**
Включается через `export DOCKER_CONTENT_TRUST=1`. Ограничивает `docker pull/run/build` только подписанными образами в рамках Notary v1. Не рекомендуется для новых проектов из-за жесткой привязки к ключам и отсутствия гибкости.
