# Усиление защиты хоста и демона Docker (Hardening)

## Определения

**Усиление защиты хоста и демона Docker (Host and Daemon Hardening)** — это процесс настройки хостовой ОС и демона `dockerd` для минимизации поверхности атаки. Основная цель — не допустить, чтобы уязвимость в контейнере привела к компрометации хоста. Эти практики являются частью рекомендаций стандарта **CIS Docker Benchmark**.

## Основные концепции

### 1. Изоляция пользователей: User Namespaces (`userns-remap`)

**User namespaces** изолируют UID/GID внутри контейнера от хоста. Процесс с UID 0 (root) в контейнере отображается в непривилегированного пользователя на хосте, что резко снижает ущерб при эскалации привилегий.

* **В контейнере:** UID 0..65535.
* **На хосте:** UID 100000..165536 (пример).

### 2. Режим Rootless Docker

**Rootless Docker** — наиболее надёжный подход, при котором и демон Docker (`dockerd`), и контейнеры запускаются от имени **непривилегированного пользователя**. Это кардинально снижает риски, так как компрометация демона не приводит к получению root-доступа к хосту. Этот подход является ключевым преимуществом альтернативных сред, таких как **[Podman](../../Podman/podman_vs_docker.md)**.

| Атака/риск | Docker с root-доступом | Rootless Docker |
| :--- | :--- | :--- |
| **Побег из контейнера** | Потенциальная эскалация до root на хосте | Ограничение прав до обычного пользователя |
| **Компрометация демона** | Root-операции над системой | Отсутствие прямого доступа к системным ресурсам |

### 3. Изоляция на уровне ядра: LSM (Linux Security Modules)

Docker использует встроенные модули безопасности Linux для принудительной изоляции.

* **[Seccomp](../../Linux/Security/Mechanisms/Seccomp.md)**: Ограничивает набор системных вызовов (`syscalls`), доступных контейнеру. Docker применяет профиль по умолчанию, блокирующий опасные вызовы.
* **[AppArmor](../../Linux/Security/Mechanisms/AppArmor.md)** и **[SELinux](../../Linux/Security/Mechanisms/SELinux.md)**: Механизмы мандатного управления доступом (MAC), которые ограничивают доступ процессов к файлам и другим ресурсам, дополняя стандартную модель прав.

### 4. Защита API демона: Docker Socket

Проброс сокета `/var/run/docker.sock` в контейнер эквивалентен предоставлению `root`-доступа к хосту. Подробный анализ этой угрозы описан в документе **[Обзор безопасности Docker](./overview.md#docker-socket-varrundockersock)**.

## Практические сценарии

### 1. Настройка User Namespaces (`daemon.json`)

1. Создайте пользователя и выделите ему диапазоны subuid/subgid:

    ```bash
    sudo usermod --add-subuids 100000-165536 --add-subgids 100000-165536 dockremap
    ```

2. Активируйте `userns-remap` в `/etc/docker/daemon.json`:

    ```json
    {
      "userns-remap": "default"
    }
    ```

3. Перезапустите Docker. **Особенность**: для bind-монтов может потребоваться `chown` файлов на хосте.

### 2. Установка и запуск Rootless Docker

1. Установите необходимые пакеты:

    ```bash
    sudo apt-get update && sudo apt-get install -y uidmap slirp4netns
    ```

2. Запустите установочный скрипт от имени обычного пользователя:

    ```bash
    dockerd-rootless-setuptool.sh install
    ```

3. Настройте переменные окружения для сессии:

    ```bash
    export XDG_RUNTIME_DIR=/run/user/$(id -u)
    export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock
    ```

4. Проверьте: `docker info | grep Rootless` должен показать `Rootless: true`.

### 3. Использование AppArmor и SELinux

* **Проверка статуса**: `docker info | egrep -i 'apparmor|selinux'`
* **Применение профиля AppArmor**:

    ```bash
    docker run --rm --security-opt apparmor=my-custom-profile nginx
    ```

* **Работа с SELinux и томами**: При монтировании томов используйте флаг `:z` (общий доступ) или `:Z` (эксклюзивный доступ) для автоматической смены контекста безопасности.

    ```bash
    docker run -v /srv/data:/data:Z ubuntu bash
    ```

### 4. Безопасная конфигурация демона (`/etc/docker/daemon.json`)

```json
{
  "icc": false,
  "userns-remap": "default",
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  },
  "no-new-privileges": true,
  "disable-legacy-registry": true
}
```

* `"icc": false"`: Запрещает сетевое взаимодействие между контейнерами по умолчанию.
* `"no-new-privileges": true"`: Запрещает процессам внутри контейнера повышать свои привилегии через `setuid` или `setgid` бинарники.

## Дополнительная информация

### Сравнение режимов безопасности

| Режим | Привилегии на хосте | Простота | Ограничения |
| :--- | :--- | :--- | :--- |
| **Стандартный** | `root` в контейнере = `root` на хосте | Высокая | Минимальные. **Опасно.** |
| **`userns-remap`** | `root` в контейнере → непривилегированный UID | Средняя | Требует `chown` для томов. |
| **Rootless Docker** | Демон и контейнеры без `root` | Ниже | Ограничения сети, ядра, `privileged` режим недоступен. |
