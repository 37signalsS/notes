# Защита хоста и демона Docker (Hardening)

## Определения

**Защита хоста и демона Docker (Host and Daemon Hardening)** — настройка хостовой ОС и демона `dockerd` для минимизации поверхности атаки. Цель — не допустить компрометацию хоста через уязвимость в контейнере. Практики входят в стандарт **CIS Docker Benchmark**.

## Базовые концепции

### 1. User Namespaces (`userns-remap`)

**User namespaces** изолируют UID/GID контейнера от хоста. Процесс с UID 0 (root) в контейнере отображается на непривилегированного пользователя на хосте.

- **В контейнере:** UID 0..65535
- **На хосте:** UID 100000..165536 (пример)

### 2. Rootless Docker

**Rootless Docker** — демон и контейнеры запускаются от непривилегированного пользователя. Компрометация демона не дает root-доступ к хосту. Подробнее: **[Rootless режим в Podman](../../Podman/podman_rootless.md)** (архитектурные принципы).

| Риск | Docker (root) | Rootless Docker |
| :--- | :--- | :--- |
| **Побег из контейнера** | Эскалация до root на хосте | Ограничение до обычного пользователя |
| **Компрометация демона** | Root-операции над системой | Нет доступа к системным ресурсам |

### 3. LSM (Linux Security Modules)

Docker использует модули ядра для принудительной изоляции:

- **[Seccomp](../../Linux/Security/Mechanisms/Seccomp.md)**: Ограничивает `syscalls` контейнера (профиль по умолчанию блокирует опасные вызовы).
- **[AppArmor](../../Linux/Security/Mechanisms/AppArmor.md)** / **[SELinux](../../Linux/Security/Mechanisms/SELinux.md)**: MAC-механизмы, ограничивающие доступ к файлам и ресурсам.

### 4. Docker Socket и группа docker (Векторы эскалации привилегий)

Доступ к демону Docker эквивалентен `root`-доступу к хосту. Анализ угрозы: **[Обзор безопасности Docker](./overview.md)**. Основные векторы:

1. **Группа `docker`:** Пользователь, добавленный в группу `docker`, может запустить контейнер, примонтировать корневую файловую систему хоста и стать на ней `root`:

    ```bash
    docker run -v /:/mnt -it ubuntu chroot /mnt
    # Внутри chroot можно редактировать /etc/shadow, /etc/sudoers или добавить пользователя
    ```

2. **Открытый сокет (`/var/run/docker.sock`):** Сокет — это основной интерфейс управления демоном (по сути REST API). Если сокет имеет права, позволяющие чтение/запись (например, `777`), любой локальный пользователь или скомпрометированный сервис может общаться с демоном напрямую через `curl` (даже без установленного клиента `docker`) и получить права `root`.
    Пример прямого запроса:

    ```bash
    curl --unix-socket /var/run/docker.sock http://localhost/containers/json
    ```

    Злоумышленник может отправить POST-запрос на создание привилегированного контейнера с подмонтированным корнем хоста.
3. **SUID-бит на бинарнике `docker`:** Если исполняемый файл `docker` имеет SUID-бит от `root`, он позволит любому пользователю системы запускать контейнеры с повышенными привилегиями.

**Рекомендации:** Относитесь к группе `docker` как к `wheel`/`sudo`. Используйте Rootless-режим или выдавайте доступ только через защищенные CI/CD-пайплайны. Никогда не открывайте сокет Docker наружу по TCP (`-H tcp://0.0.0.0:2375`). Для удаленного управления безопасно используйте **Docker Context через SSH**:

```bash
# Создание контекста для управления удаленным демоном по SSH
docker context create remote-host --docker "host=ssh://user@remote-ip"
docker context use remote-host
# Теперь все команды docker (run, ps) будут безопасно выполняться на удаленном сервере
```

### 5. Контейнерно-ориентированные ОС (Container-Optimized OS)

Лучший способ защитить хост — использовать специализированные, иммутабельные (immutable) операционные системы, созданные исключительно для запуска контейнеров (например, **Talos Linux**, Flatcar Container Linux). В них вырезано всё лишнее (нет пакетных менеджеров, нет SSH, нет shell). Это полностью исключает целый вектор атак на хостовую ОС и упрощает управление обновлениями ядра (которое является наиболее критичным элементом защиты при разделении ядра контейнерами).

## Практические сценарии

### 1. Настройка User Namespaces (`daemon.json`)

1. Создайте пользователя и выделите ему диапазоны subuid/subgid:

    ```bash
    sudo usermod --add-subuids 100000-165536 --add-subgids 100000-165536 dockremap
    ```

2. Активируйте `userns-remap` в `/etc/docker/daemon.json`:

    ```json
    {
      "userns-remap": "default"
    }
    ```

3. Перезапустите Docker. **Особенность**: для bind-монтов может потребоваться `chown` файлов на хосте.

### 2. Установка и запуск Rootless Docker

1. Установите необходимые пакеты:

    ```bash
    sudo apt-get update && sudo apt-get install -y uidmap slirp4netns
    ```

2. Запустите установочный скрипт от имени обычного пользователя:

    ```bash
    dockerd-rootless-setuptool.sh install
    ```

3. Настройте переменные окружения для сессии:

    ```bash
    export XDG_RUNTIME_DIR=/run/user/$(id -u)
    export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock
    ```

4. Проверьте: `docker info | grep Rootless` должен показать `Rootless: true`.

### 3. Использование AppArmor и SELinux

- **Проверка статуса**: `docker info | egrep -i 'apparmor|selinux'`
- **Применение профиля AppArmor**:

    ```bash
    docker run --rm --security-opt apparmor=my-custom-profile nginx
    ```

- **Работа с SELinux и томами**: При монтировании томов используйте флаг `:z` (общий доступ) или `:Z` (эксклюзивный доступ) для автоматической смены контекста безопасности.

    ```bash
    docker run -v /srv/data:/data:Z ubuntu bash
    ```

### 4. Безопасная конфигурация демона (`/etc/docker/daemon.json`)

```json
{
  "icc": false,
  "userns-remap": "default",
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  },
  "no-new-privileges": true,
  "disable-legacy-registry": true
}
```

- `"icc": false"`: Запрещает сетевое взаимодействие между контейнерами по умолчанию. Это критически важно для защиты от бокового перемещения (lateral movement): при компрометации одного контейнера атакующий не увидит соседние в стандартной "плоской" сети Docker. Контейнерам, которым необходимо общаться между собой, следует явно назначать изолированные пользовательские сети (`docker network create`).
- `"no-new-privileges": true"`: Запрещает процессам внутри контейнера повышать свои привилегии через `setuid` или `setgid` бинарники (митигация атак через GTFOBins).

## Дополнительная информация

**Сравнение режимов:**

| Режим | Привилегии на хосте | Простота | Ограничения |
| :--- | :--- | :--- | :--- |
| **Стандартный** | `root` в контейнере = `root` на хосте | Высокая | Минимальные, **опасно** |
| **`userns-remap`** | `root` в контейнере → непривилегированный UID | Средняя | Требует `chown` для томов |
| **Rootless Docker** | Демон и контейнеры без `root` | Ниже | Ограничения сети, ядра, нет `privileged` |
