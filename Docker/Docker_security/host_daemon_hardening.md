# Защита хоста и демона Docker

## 1. Не монтируйте Docker-сокет в контейнеры

Это одна из самых опасных практик. Монтирование сокета `/var/run/docker.sock` внутрь контейнера эквивалентно предоставлению `root`-доступа к хосту.

Если это абсолютно необходимо (например, для CI/CD агентов), используйте прокси с авторизацией, которые ограничивают доступные команды API. Примеры таких инструментов:
-   [Tecnativa/docker-socket-proxy](https://github.com/Tecnativa/docker-socket-proxy)

## 2. Включите `seccomp` и `AppArmor`/`SELinux`

Эти встроенные в ядро Linux механизмы безопасности обеспечивают дополнительный, мощный уровень изоляции.

-   **Seccomp (Secure Computing Mode):** Ограничивает системные вызовы (`syscalls`), которые может делать процесс. Docker по умолчанию использует `seccomp` профиль, который блокирует около 44 наиболее опасных системных вызовов из более чем 300. Вы можете создавать и применять собственные, более строгие профили.
-   **AppArmor / SELinux:** Это Mandatory Access Control (MAC) системы, которые ограничивают доступ программ к файлам, сети и другим ресурсам на основе заданных политик. Docker может автоматически генерировать и применять профили `AppArmor` для контейнеров.

Включение и правильная настройка этих профилей значительно снижают поверхность атаки в случае компрометации контейнера.

## 3. Изоляция с помощью User Namespaces (`userns-remap`)

Эта функция Docker позволяет запускать контейнеры в отдельном пространстве имен пользователя, что кардинально повышает безопасность.

#### Проблема: `root` в контейнере = `root` на хосте

По умолчанию, если процесс в контейнере запущен от `root` (UID 0), для ядра хоста это тот же самый `root`. Если злоумышленник сможет "сбежать" из контейнера, он получит полные права `root` на хост-машине.

**Решение:**
`userns-remap` решает эту проблему, "переназначая" пользователей. `root` (UID 0) внутри контейнера сопоставляется с обычным, непривилегированным пользователем на хост-машине (например, с UID > 100000). Если злоумышленник сбегает из контейнера, он получает права не `root`, а этого непривилегированного пользователя.

Для включения достаточно добавить строку в конфигурационный файл демона (`/etc/docker/daemon.json`):
```json
{
  "userns-remap": "default"
}
```
После этого Docker автоматически создаст на хосте пользователя `dockremap` и будет управлять диапазонами UID/GID.

**Проблемы такого подхода:**
-   **Монтирование томов (`bind mounts`):** `userns-remap` усложняет работу с `bind mounts`. Файлы, созданные `root` в контейнере, на хосте будут принадлежать пользователю `dockremap`, что может вызвать проблемы с правами доступа. Рекомендуется использовать именованные тома (`named volumes`).
-   **Совместимость:** Не все функции Docker (например, некоторые сетевые режимы) полностью совместимы с `userns-remap`.

## 4. Rootless Docker: Современное решение

**Rootless Docker** — это режим, в котором и демон Docker, и контейнеры запускаются от имени **непривилегированного пользователя**. Это наиболее эффективный способ защиты от атак, связанных с повышением привилегий.

-   **Как это работает:** Используются **пространства имен пользователей (user namespaces)** ядра Linux. UID `root` (0) внутри контейнера сопоставляется с UID непривилегированного пользователя на хосте, от имени которого запущен `dockerd`.
-   **Преимущества:** Даже если злоумышленник сбежит из контейнера или получит доступ к сокету, он получит права не `root` на хосте, а лишь права того пользователя, от имени которого запущен Rootless Docker.

**Установка:**
```sh
# Устанавливаем необходимые утилиты
sudo apt-get install -y uidmap
# Запускаем установочный скрипт от обычного пользователя
dockerd-rootless-setuptool.sh install
```

-   **Ограничения:** Rootless-режим имеет некоторые ограничения, связанные с работой сети (например, невозможность пробрасывать порты ниже 1024 без дополнительных настроек) и драйверов хранения.

## 5. Безопасная конфигурация демона (`daemon.json`)

**Рекомендуется** управлять конфигурацией демона Docker через файл `/etc/docker/daemon.json`, а не через флаги командной строки в `systemd` unit-файле.

**Проблема: Конфликт конфигураций**
Если один и тот же параметр задан и как флаг при запуске, и в `daemon.json`, Docker-демон не сможет запуститься.

**Пример безопасной конфигурации `/etc/docker/daemon.json`:**
```json
{
  "icc": false,
  "userns-remap": "default",
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  },
  "no-new-privileges": true,
  "insecure-registries": [],
  "disable-legacy-registry": true
}
```
-   `"icc": false` (**Inter-Container Communication**): Запрещает контейнерам в сети `bridge` по умолчанию общаться друг с другом. Это важная мера изоляции, не позволяющая скомпрометированному контейнеру атаковать "соседей".
-   `"no-new-privileges": true`: Устанавливает флаг `no-new-privileges` для всех запускаемых контейнеров по умолчанию.
-   `"disable-legacy-registry": true`: Запрещает взаимодействие со старыми (v1) и потенциально небезопасными Docker-реестрами.

## 6. Изоляция сети

-   **Не используйте сеть по умолчанию (`bridge`):** Вместо этого создавайте выделенные сети для групп контейнеров, которым необходимо общаться.
    ```sh
    docker network create my-app-net
    docker run --network=my-app-net ...
    ```
-   **Отключите межконтейнерное взаимодействие на `bridge`:** В файле `/etc/docker/daemon.json` установите `"icc": false`.
-   **Не используйте `--net=host`:** Этот режим отключает сетевую изоляцию, позволяя контейнеру получить доступ ко всем сетевым интерфейсам хоста.
