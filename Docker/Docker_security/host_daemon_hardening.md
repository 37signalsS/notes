# Усиление защиты хоста и демона Docker

## Определения

**Усиление защиты хоста и демона Docker (Host and Daemon Hardening)** — это процесс настройки хостовой операционной системы и демона `dockerd` для минимизации поверхности атаки и снижения рисков, связанных с компрометацией контейнеров. Основная цель — не допустить, чтобы уязвимость в контейнере привела к получению контроля над хостом.

## Базовые концепции

### 1. Принцип наименьших привилегий: `userns-remap` и `Rootless Docker`

Ключевая стратегия защиты — запускать контейнеры и сам демон с минимально необходимыми правами, чтобы "побег" из контейнера не давал атакующему `root`-доступ к хосту.

*   **Изоляция с помощью `userns-remap`**: Эта встроенная функция Docker "переназначает" `root`-пользователя (UID 0) внутри контейнера на непривилегированного пользователя с высоким UID на хосте. Таким образом, даже если процесс выйдет за пределы контейнера, он получит права обычного пользователя, а не `root`. Главный недостаток — усложнение работы с монтируемыми томами (`bind mounts`) из-за проблем с правами доступа к файлам.

*   **`Rootless Docker`**: Наиболее современный и надёжный подход, при котором и демон Docker (`dockerd`), и контейнеры запускаются от имени **непривилегированного пользователя**. Это кардинально снижает риски эскалации привилегий, так как ни один компонент Docker не имеет `root`-прав.

### 2. Изоляция на уровне ядра: `Seccomp`, `AppArmor` и `SELinux`

Linux предоставляет встроенные модули безопасности (LSM), которые Docker использует для принудительной изоляции контейнеров на уровне системных вызовов и доступа к файлам.

-   **[Seccomp](../../Linux/Security/Mechanisms/Seccomp.md)**: Ограничивает набор системных вызовов (`syscalls`), доступных контейнеру. Docker по умолчанию применяет профиль, блокирующий наиболее опасные вызовы.
-   **[AppArmor](../../Linux/Security/Mechanisms/AppArmor.md)** и **[SELinux](../../Linux/Security/Mechanisms/SELinux.md)**: Системы принудительного контроля доступа (MAC), которые ограничивают доступ контейнера к файлам, сети и другим ресурсам на основе политик безопасности.

### 3. Защита API демона: Docker Socket

Проброс сокета `/var/run/docker.sock` в контейнер является одной из самых опасных практик, так как это эквивалентно предоставлению `root`-доступа к хосту. Подробный анализ этой угрозы и методов её смягчения (например, использование прокси с фильтрацией API-вызовов) описан в документе **[Обзор безопасности Docker](./overview.md#docker-socket-varrundockersock)**.

## Практические сценарии

### 1. Безопасная конфигурация демона (`/etc/docker/daemon.json`)

Централизованная настройка демона через `daemon.json` предпочтительнее флагов командной строки. Конфликт параметров в `daemon.json` и флагах запуска приведёт к сбою старта демона.

**Пример безопасной конфигурации:**
```json
{
  "icc": false,
  "userns-remap": "default",
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  },
  "no-new-privileges": true,
  "insecure-registries": [],
  "disable-legacy-registry": true
}
```
-   `"icc": false"`: Запрещает сетевое взаимодействие между контейнерами в сети `bridge` по умолчанию, изолируя их друг от друга.
-   `"userns-remap": "default"`: Включает переназначение пространств имен пользователей.
-   `"no-new-privileges": true`: Запрещает процессам внутри контейнера повышать свои привилегии.
-   `"disable-legacy-registry": true"`: Отключает поддержку старых и потенциально небезопасных реестров Docker (v1).

### 2. Настройка сетевой изоляции

-   **Создавайте выделенные сети:** Не используйте сеть `bridge` по умолчанию.
    ```sh
    docker network create my-app-net
    docker run --network=my-app-net ...
    ```
-   **Не используйте `--net=host`:** Этот режим отключает сетевую изоляцию, давая контейнеру полный доступ к сетевым интерфейсам хоста.

### 3. Включение режима `Rootless Docker`

Rootless Docker позволяет запускать и демон Docker, и контейнеры без прав `root` на хосте, что кардинально снижает риск эскалации привилегий. 

#### Установка

Установка выполняется от имени обычного пользователя.

```sh
# Установка зависимостей (для Debian/Ubuntu)
sudo apt-get install -y uidmap
# Запуск установочного скрипта от обычного пользователя
dockerd-rootless-setuptool.sh install
```

#### Запуск и проверка

1.  **Запуск демона в rootless-режиме:**
    ```sh
    dockerd-rootless.sh --experimental
    ```

2.  **Проверка статуса:**
    Убедитесь, что Docker работает в rootless-режиме, проверив вывод `docker info`.
    ```sh
    docker info | grep Rootless
    # Ожидаемый вывод: Rootless: true
    ```

#### Особенности и ограничения

У Rootless-режима есть ряд особенностей, которые нужно учитывать:

*   **Сеть и порты:**
    *   **Привилегированные порты:** Rootless Docker не может напрямую использовать порты ниже 1024. Для обхода этого ограничения используйте перенаправление с непривилегированного порта (например, `-p 8080:80`).
    *   **Сетевой стек:** Используется `slirp4netns` для создания пользовательского сетевого пространства имен, что может влиять на производительность.
    *   **Проверка сетевых интерфейсов:**
        ```sh
        docker run --rm --net=bridge alpine ip addr
        ```

*   **Драйверы хранения (Storage Drivers):**
    *   Поддерживаются `overlayfs` и `fuse-overlayfs`. Выбор зависит от версии ядра хоста.
    *   **Проверка используемого драйвера:**
        ```sh
        docker info | grep 'Storage Driver'
        ```
