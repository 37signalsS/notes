# Защита хоста и демона Docker (Hardening)

Данный документ описывает методы настройки хостовой операционной системы и демона `dockerd` для минимизации поверхности атаки и предотвращения компрометации хоста через контейнеры. Рекомендации основаны на стандартах **CIS Docker Benchmark (v1.7.0/1.8.0)**.

## Определения

**Защита хоста и демона Docker (Host and Daemon Hardening)** — комплекс мер по настройке ОС и конфигурации Docker для обеспечения максимальной изоляции.

**Пространства имен пользователей (User Namespaces)** — механизм ядра Linux, позволяющий изолировать идентификаторы пользователей и групп (**UID/GID**) контейнера от хоста.

**Модули безопасности Linux (LSM — Linux Security Modules)** — модули ядра (AppArmor, SELinux), обеспечивающие мандатное управление доступом (**MAC — Mandatory Access Control**).

**Cgroup v2 (Control Groups version 2)** — обновленная подсистема ядра для управления ресурсами, необходимая для полноценной работы Rootless-режима и лучшей изоляции.

**Аудит (Audit)** — процесс регистрации системных событий (обращения к файлам, системные вызовы) для последующего анализа безопасности.

## Базовые концепции

### 1. Пространства имен пользователей (`userns-remap`)

Изоляция **User Identifier (UID)** и **Group Identifier (GID)** позволяет сопоставить пользователя `root` (UID 0) внутри контейнера с обычным непривилегированным пользователем на хосте.

- **В контейнере:** UID 0..65535
- **На хосте:** UID 100000..165536 (пример отображения)

### 2. Безрутовый режим (Rootless Docker)

**Rootless Docker** — режим, в котором демон и контейнеры запускаются от имени непривилегированного пользователя. Это исключает получение прав `root` на хосте даже при полном «побеге» из контейнера.

| Риск | Docker (root) | Rootless Docker |
| :--- | :--- | :--- |
| **Побег из контейнера** | Эскалация до `root` на хосте | Ограничение правами пользователя |
| **Компрометация демона** | Полный контроль над системой | Доступ только к ресурсам пользователя |

*Подробнее:* **[Rootless режим в Podman](../../Podman/podman_rootless.md)** (архитектурные принципы аналогичны).

### 3. Модули безопасности Linux (LSM)

Docker использует механизмы ядра для принудительной изоляции процессов:

- **[Seccomp](../../Linux/Security/Mechanisms/Seccomp.md)**: фильтрация системных вызовов (**syscalls**). Профиль по умолчанию блокирует около 40–44 опасных вызовов.
- **[AppArmor](../../Linux/Security/Mechanisms/AppArmor.md)** / **[SELinux](../../Linux/Security/Mechanisms/SELinux.md)**: ограничивают доступ к файловой системе и ресурсам на основе политик.

### 4. Docker Socket и группа docker

Доступ к Docker API фактически эквивалентен полному `root`-доступу к хосту.

1. **Группа `docker`:** Пользователи в этой группе могут управлять демоном без `sudo`, что позволяет запустить привилегированный контейнер и получить доступ к файлам хоста.
2. **Unix-сокет (`/var/run/docker.sock`):** Если сокет проброшен в контейнер, злоумышленник может управлять хостом.
3. **TCP-порт:** Никогда не открывайте сокет по сети без TLS-аутентификации.

### 5. Контейнерно-ориентированные ОС

Использование специализированных иммутабельных (immutable) систем (например, **Talos Linux**, Flatcar, Bottlerocket) исключает лишний инструментарий и минимизирует поверхность атаки.

### 6. Разделение разделов (Partitioning)

Для директории `/var/lib/docker` (или `/home/$USER/.local/share/docker` в Rootless) рекомендуется использовать отдельный раздел или квоты. Это предотвращает атаку типа «отказ в обслуживании» (DoS) через переполнение диска логами или образами.

### 7. Целостность и подписи образов

Docker Content Trust (DCT) считается устаревшим. Современный стандарт — использование **Cosign** для подписи образов в CI/CD и проверки их перед запуском.
*Подробнее:* **[Подпись и проверка образов](./image_signature_and_verification.md)**.

## Практические сценарии

### 1. Настройка аудита (auditd)

Согласно CIS Benchmark, необходимо настроить аудит критических файлов Docker.

1. Установите `auditd`: `sudo apt install auditd`
2. Добавьте правила в `/etc/audit/rules.d/docker.rules`:
    ```bash
    # Аудит исполняемых файлов и сокета
    -w /usr/bin/dockerd -k docker
    -w /var/run/docker.sock -k docker
    -w /usr/bin/docker-containerd -k docker
    -w /usr/bin/docker-runc -k docker

    # Аудит конфигурации
    -w /etc/docker -k docker
    -w /etc/docker/daemon.json -k docker
    -w /lib/systemd/system/docker.service -k docker
    -w /lib/systemd/system/docker.socket -k docker

    # Аудит хранилища (новое в CIS 1.7)
    -w /var/lib/docker -k docker
    ```
3. Перезапустите службу: `sudo systemctl restart auditd`.
4. Проверка логов: `ausearch -k docker`.

### 2. Настройка User Namespaces (`daemon.json`)

1. Выделите диапазоны идентификаторов:
    ```bash
    sudo usermod --add-subuids 100000-165536 --add-subgids 100000-165536 dockremap
    ```
2. Включите режим в `/etc/docker/daemon.json`:
    ```json
    { "userns-remap": "default" }
    ```
3. Перезапустите демон.

#### Детальный разбор работы маппинга

Маппинг работает по формуле: `host_uid = container_uid + base_id`.
При настройке `dockremap:100000:65536` из `/etc/subuid`:
- **UID 0** внутри контейнера = **UID 100000** на хосте.
- **UID 1000** внутри контейнера = **UID 101000** на хосте.

#### Проблема Bind Mount vs Docker Volume

**Bind mount (`/data:/data`)**:
Если хост-директория `/data` принадлежит пользователю с UID 1000, то процесс внутри контейнера (UID 0 -> хост 100000) не сможет писать в нее, так как для хоста это «другой» пользователь.
- `chown` внутри контейнера упадет с `Operation not permitted`, так как ядро видит попытку непривилегированного пользователя (100000) сменить владельца на 101000.
- `mkdir` упадет с `Permission denied`, если права доступа на хосте не 777.

**Docker Volume (`named_vol:/data`)**:
Дизайн: `/var/lib/docker/volumes/.../_data` управляется `dockerd`. При создании тома в режиме `userns` Docker автоматически устанавливает корректные права, и процессы внутри контейнера могут прозрачно работать с ФС.

**Итог:** Bind mount требует ручного согласования UID на хосте (например, `chown 100000:100000 /data`), тогда как Named volume решает проблему автоматически.

| Альтернатива | Проблема |
| :--- | :--- |
| `chown 101000:101000 /data` | UID 101000 может не существовать на хосте; хрупко при смене subuid. |
| `mode: 0777` | Дыра в безопасности; `chown` внутри контейнера все равно упадет. |
| `:idmap` (Docker 25+) | Требует поддержки ФС (например, XFS с reflink) и ядра; пока не везде стабильно. |
| `user: root` в Compose | Контейнер будет root и сможет писать, но это нарушает принцип минимальных привилегий. |

### 3. Установка и запуск Rootless Docker

Для Docker 27+ рекомендуется использовать `pasta` для сетевого взаимодействия (выше производительность).

1. Убедитесь в наличии Cgroup v2: `stat -fc %T /sys/fs/cgroup/` (должно быть `cgroup2fs`).
2. Установите зависимости: `apt install -y dbus-user-session uidmap slirp4netns` (или `passt` для `pasta`).
3. Запустите скрипт: `curl -fsSL https://get.docker.com/rootless | sh`.
4. Настройте автозапуск: `loginctl enable-linger $USER`.
5. Проверка: `docker info | grep -E "Rootless|Cgroup"`.

### 4. Настройка TLS для удаленного доступа

Если необходимо управлять Docker удаленно, используйте TLS с взаимной проверкой сертификатов (mTLS).

1. Генерация ключей (CA, серверный, клиентский).
2. Конфигурация в `daemon.json`:
    ```json
    {
      "tlsverify": true,
      "tlscacert": "/etc/docker/ca.pem",
      "tlscert": "/etc/docker/server-cert.pem",
      "tlskey": "/etc/docker/server-key.pem",
      "hosts": ["tcp://0.0.0.0:2376", "unix:///var/run/docker.sock"]
    }
    ```
3. Использование через [Docker Context](../docker_context.md).

### 5. Безопасная конфигурация демона (`daemon.json`)

Итоговый пример защищенной конфигурации (без учета TLS):

```json
{
  "icc": false,
  "userns-remap": "default",
  "no-new-privileges": true,
  "live-restore": true,
  "userland-proxy": false,
  "disable-legacy-registry": true,
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

- **`userland-proxy: false`**: отключает `docker-proxy`, заменяя его на правила `iptables` (уменьшает поверхность атаки).
- **`disable-legacy-registry`**: запрещает работу со старыми и небезопасными v1-реестрами.
- **`icc: false`**: отключает прямое взаимодействие между контейнерами в сети `bridge`.
- **`live-restore`**: **несовместим со Swarm**.
