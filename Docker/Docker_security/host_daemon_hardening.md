# Защита хоста и демона Docker (Hardening)

Данный документ описывает методы настройки хостовой операционной системы и демона `dockerd` для минимизации поверхности атаки и предотвращения компрометации хоста через контейнеры.

## Определения

**Защита хоста и демона Docker (Host and Daemon Hardening)** — комплекс мер по настройке операционной системы и конфигурации Docker для обеспечения максимальной изоляции. Рекомендации основываются на стандарте **CIS (Center for Internet Security) Docker Benchmark**.

**User Namespaces** — механизм ядра Linux, позволяющий изолировать идентификаторы пользователей и групп (**UID/GID**) контейнера от хоста.

**LSM (Linux Security Modules)** — модули безопасности ядра (AppArmor, SELinux), обеспечивающие мандатное управление доступом (**MAC — Mandatory Access Control**).

## Базовые концепции

### 1. User Namespaces (`userns-remap`)

Изоляция **User Identifier (UID)** и **Group Identifier (GID)** позволяет сопоставить пользователя `root` (UID 0) внутри контейнера с обычным непривилегированным пользователем на хосте.

- **В контейнере:** UID 0..65535
- **На хосте:** UID 100000..165536 (пример отображения)

### 2. Rootless Docker

**Rootless Docker** — режим, в котором демон и контейнеры запускаются от имени непривилегированного пользователя. Это исключает получение прав `root` на хосте даже при полном «побеге» из контейнера или компрометации самого демона. Подробнее см.: **[Rootless режим в Podman](../../Podman/podman_rootless.md)** (описание архитектурных принципов).

| Риск | Docker (root) | Rootless Docker |
| :--- | :--- | :--- |
| **Побег из контейнера** | Эскалация до `root` на хосте | Ограничение правами обычного пользователя |
| **Компрометация демона** | Полный контроль над системой | Доступ только к ресурсам пользователя |

### 3. Модули безопасности Linux (LSM)

Docker использует механизмы ядра для принудительной изоляции процессов:

- **[Seccomp](../../Linux/Security/Mechanisms/Seccomp.md)**: фильтрация системных вызовов (**syscalls**) контейнера. Профиль по умолчанию блокирует около 40 опасных вызовов.
- **[AppArmor](../../Linux/Security/Mechanisms/AppArmor.md)** / **[SELinux](../../Linux/Security/Mechanisms/SELinux.md)**: MAC-механизмы, ограничивающие доступ контейнера к файловой системе и ресурсам на основе политик.

### 4. Docker Socket и группа docker (Векторы эскалации привилегий)

Доступ к Docker API фактически эквивалентен полному `root`-доступу к хосту. Анализ угроз приведен в документе **[Обзор безопасности Docker](./overview.md)**. Ключевые риски:

1. **Группа `docker`:** Пользователи в этой группе могут управлять демоном без `sudo`. Это позволяет запустить привилегированный контейнер и получить доступ к файлам хоста.
2. **Открытый сокет (`/var/run/docker.sock`):** Основной интерфейс управления демоном (через **REST API**). Если сокет проброшен в контейнер или имеет права на запись для всех, злоумышленник может управлять хостом.
3. **SUID (Set User ID) бит:** Наличие SUID-бита на исполняемом файле `docker` позволяет любому пользователю запускать его с правами владельца (обычно `root`).

**Рекомендации:** Относитесь к группе `docker` как к группе `sudo`. Используйте Rootless-режим или ограничьте доступ через защищенные CI/CD пайплайны. Никогда не открывайте сокет Docker наружу по **TCP (Transmission Control Protocol)** без TLS. Для удаленного управления используйте **[Docker Context](../docker_context.md) через SSH (Secure Shell)**.

### 5. Контейнерно-ориентированные ОС (Container-Optimized OS)

Использование специализированных иммутабельных (immutable) операционных систем (например, **Talos Linux**, Flatcar Container Linux) исключает целые классы атак, так как в них отсутствует лишний инструментарий (пакетные менеджеры, оболочки) и минимизирована поверхность атаки.

## Практические сценарии

### 1. Настройка User Namespaces (`daemon.json`)

1. Выделите диапазоны идентификаторов для пользователя `dockremap`:

    ```bash
    sudo usermod --add-subuids 100000-165536 --add-subgids 100000-165536 dockremap
    ```

2. Включите режим в `/etc/docker/daemon.json`:

    ```json
    {
      "userns-remap": "default"
    }
    ```

3. Перезапустите демон. Помните, что для подмонтированных томов (**bind mounts**) может потребоваться коррекция прав (`chown`).

### Дополнительная информация об userns-remap

#### Как работает маппинг UID/GID

На этой системе `dockremap:100000:65536` из `/etc/subuid`. Это значит:
- **UID 0** внутри контейнера = **UID 100000** на хосте
- **UID 1** внутри контейнера = **UID 100001** на хосте, … до UID 65534
- Маппинг работает по формуле: `host_uid = container_uid + base_id`

Проверка командой: `docker info | grep userns`. Поле Security должно содержать `usernames: enabled`.

#### Bind mount vs Docker volume при userns-remap

**Bind mount (`/opt/bookstack/config:/config`) — проблема:**
Хост: `/opt/bookstack/config` владелец **vagrant (UID 1000)** mode 0755.
Внутри контейнера процесс `init` имеет UID в NS = 0, на хосте транслируется как **100000**. Процесс `app` имеет UID в NS = 1000 → на хосте **101000**.

Связка `chown /config 1000:1000` внутри контейнера транслируется ядром в попытку процесса с **хост-UID 100000** сменить владельца файла 1000 → 101000. Процесс 100000 не имеет права менять владельца (только root, т.е. UID 0). Отсюда `Operation not permitted`.

Далее `mkdir /config/keys`: хост-UID **100000** проверяет права на `/config` — файл принадлежит UID 1000 с mode 755 (rwxr-xr-x), у others только r-x, нет w. Отсюда `Permission denied`.

Если бы выставить mode: 0777, mkdir прошёл бы, но chown всё равно упал бы. Однако **lsio-образ продолжает работать** даже после неудачного chown — пишет warning и идёт дальше, но mkdir уже упал, и сервис не стартует.

**Docker volume (`bookstack_config:/config`) — решение:**
Дизайн: `/var/lib/docker/volumes/bookstack_config/_data` создаётся и управляется dockerd. При userns владельцы внутри volume корректно маппятся. Docker сам создаёт volume через свой менеджмент, и файлы внутри него создаются с UID, соответствующими текущему user namespace. Когда контейнер (UID 1000 = хост 101000) создаёт файл в volume, он на диске пишется с UID **101000**. chown внутри NS тоже работает — ядро разрешает, потому что файл лежит в user-namespace-aware storage (volume managed by Docker).

**Итог:** bind mount для userns-remap требует ручного согласования UID на хосте с маппингом контейнера. Named volume решает прозрачно.

#### Альтернативы (почему не использовали)

| Вариант | Проблема |
| :--- | :--- |
| `chown 101000:101000 /opt/bookstack/config` | Сейчас uid **101000** не существует в системе; пришлось бы создавать пользователя и ACL. Работает, но хрупко (при смене subuid сломается). |
| `mode: 0777` | mkdir прошёл бы, но chown всё равно упал бы; плюс дыра в безопасности — любой пользователь хоста может писать в конфиги. |
| Отключить userns-remap | Потеря изоляции контейнеров — основная причина, по которой его включили. |
| `:idmap` опция монтирования (Docker 25+) | Требует поддержки ФС (**xfs** с reflink) и дополнительной настройки; не стабильно во всех дистрибутивах. |
| `user: root` в compose | Контейнер будет **root** и сможет писать в bind mount, но lsio-образ специально понижает привилегии до PUID/PGID — сломаем эту модель. |

### 2. Установка и запуск Rootless Docker

1. Установите зависимости (`uidmap`, `slirp4netns`).
2. Запустите скрипт установки от имени пользователя:

    ```bash
    dockerd-rootless-setuptool.sh install
    ```

3. Настройте переменные окружения:

    ```bash
    export DOCKER_HOST=unix:///run/user/$(id -u)/docker.sock
    ```

4. Убедитесь, что режим активен: `docker info | grep Rootless`.

### 3. Работа с SELinux и AppArmor

- **Проверка статуса в Docker**: `docker info | grep -i security`
- **Монтирование томов с SELinux**: Используйте суффиксы `:z` (общий доступ) или `:Z` (эксклюзивный доступ) для автоматической настройки контекстов файлов:

    ```bash
    docker run -v /data:/data:Z nginx
    ```

### 4. Безопасная конфигурация демона (`daemon.json`)

```json
{
  "icc": false,
  "userns-remap": "default",
  "log-driver": "json-file",
  "no-new-privileges": true,
  "live-restore": true
}
```

- **`icc: false` (Inter-Container Communication)**: отключает прямое сетевое взаимодействие между контейнерами в стандартной сети, защищая от бокового перемещения злоумышленника.
- **`no-new-privileges: true`**: запрещает процессам в контейнерах получать новые привилегии через SUID-бинарники.
- **`live-restore: true`**: сохраняет работающие контейнеры при перезапуске демона. **Несовместим со Swarm** — если узел входит в Swarm-кластер, `live-restore` необходимо удалить из `daemon.json`.
- **Ротация логов**: параметры вынесены в **[Управление ротацией логов Docker](../Docker_logs/docker_log_rotation.md)**.
