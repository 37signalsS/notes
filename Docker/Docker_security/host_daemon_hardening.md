# Усиление защиты хоста и демона Docker

## Определения

**Усиление защиты хоста и демона Docker (Host and Daemon Hardening)** — это процесс настройки хостовой операционной системы и демона `dockerd` для минимизации поверхности атаки и снижения рисков, связанных с компрометацией контейнеров. Основная цель — не допустить, чтобы уязвимость в контейнере привела к получению контроля над хостом.

## Базовые концепции

### 1. Изоляция пользователей: User Namespaces (`userns-remap`)

**User namespaces** изолируют идентичности пользователей и групп внутри контейнера от хоста. Процесс, имеющий UID 0 (root) в контейнере, на самом деле отображается в непривилегированного пользователя на хосте. Это резко снижает ущерб при эскалации привилегий: даже с правами root в контейнере злоумышленник не становится root на узле.

#### Как работает отображение UID/GID

В основе механизма — таблицы соответствия UID/GID, которые сопоставляют диапазоны подстановочных идентификаторов на хосте (`/etc/subuid`, `/etc/subgid`) с контейнерными идентификаторами.

- **В контейнере:** UID 0..65535.
- **На хосте:** UID 100000..165535 (пример).
- **Отображение:** хранится в `/proc/<pid>/uid_map` и `gid_map`.

Проверить активацию user namespaces можно внутри контейнера:
```bash
id
cat /proc/self/uid_map
# Вывод "0 100000 65536" означает, что UID 0 в контейнере соответствует UID 100000 на хосте
```

### 2. Режим Rootless Docker

**Rootless Docker** — это наиболее надёжный подход, при котором и демон Docker (`dockerd`), и контейнеры запускаются от имени **непривилегированного пользователя**. Это кардинально снижает риски эскалации привилегий, так как даже успешный "побег" из контейнера или компрометация самого демона не приводят к получению root-доступа к хосту.

#### Преимущества безопасности

- **Изоляция демона:** Уязвимости в `dockerd` имеют меньший потенциал для эскалации.
- **Меньшая поверхность атаки:** Операции с сетью, файловой системой и cgroups выполняются через пользовательские механизмы, ограничивая доступ к чувствительным системным интерфейсам.
- **Безопасность в мультиарендной среде:** Пользователи могут запускать Docker без `sudo`.

#### Сравнение рисков

| Атака/риск | Docker с root-доступом | Rootless Docker |
| :--- | :--- | :--- |
| **Побег из контейнера** | Потенциальная эскалация до root на хосте | Ограничение прав до обычного пользователя |
| **Компрометация демона** | Root-операции над системой | Отсутствие прямого доступа к системным ресурсам |
| **Привилегированные порты** | Прямая привязка портов &lt;1024 | Прямая привязка недоступна |

### 3. Изоляция на уровне ядра: Seccomp, AppArmor и SELinux

Linux предоставляет встроенные модули безопасности (LSM), которые Docker использует для принудительной изоляции контейнеров на уровне системных вызовов и доступа к файлам.

- **[Seccomp](../../Linux/Security/Mechanisms/Seccomp.md)**: Ограничивает набор системных вызовов (`syscalls`), доступных контейнеру. Docker по умолчанию применяет профиль, блокирующий наиболее опасные вызовы.
- **AppArmor** и **SELinux**: Механизмы мандатного управления доступом (MAC), которые дополняют стандартную модель прав. Они ограничивают процессы контейнера так, чтобы даже при компрометации приложения злоумышленник не смог выйти за заданные рамки.

#### AppArmor vs. SELinux

| Аспект | AppArmor | SELinux |
| :--- | :--- | :--- |
| **Модель** | Путь к файлу (pathname-based) | Метки субъектов/объектов (label-based) |
| **Гранулярность** | Проще для точечных ограничений | Богатая модель TE/MCS, сильная межконтейнерная изоляция |
| **Сложность** | Низкая/средняя | Средняя/высокая |
| **Типовые дистрибутивы** | Ubuntu, Debian | RHEL, Fedora, CentOS |
| **Инструменты** | `aa-status`, `aa-complain` | `getenforce`, `audit2allow` |

### 4. Защита API демона: Docker Socket

Проброс сокета `/var/run/docker.sock` в контейнер является одной из самых опасных практик, так как это эквивалентно предоставлению `root`-доступа к хосту. Подробный анализ этой угрозы и методов её смягчения описан в документе **[Обзор безопасности Docker](./overview.md#docker-socket-varrundockersock)**.

## Практические сценарии

### 1. Настройка User Namespaces

**Глобально для демона (`/etc/docker/daemon.json`):**
1.  Создайте пользователя и выделите ему диапазоны subuid/subgid:
    ```bash
    sudo usermod --add-subuids 100000-165536 --add-subgids 100000-165536 dockremap
    ```
2.  Активируйте `userns-remap`:
    ```json
    {
      "userns-remap": "default"
    }
    ```
3.  Перезапустите Docker и проверьте: `docker info | grep -i userns`.

**Особенности:**
- **Bind-монты:** Файлы на хосте должны принадлежать пользователю из subuid/subgid диапазона. Может потребоваться `chown`.
- **Capabilities:** Возможности, полученные внутри user namespace (например, `CAP_SYS_ADMIN`), не дают прямого контроля над хостом.

### 2. Установка и запуск Rootless Docker

1.  **Подготовка окружения (Debian/Ubuntu):**
    ```bash
    sudo apt-get update
    sudo apt-get install -y uidmap slirp4netns fuse-overlayfs dbus-user-session
    ```
2.  **Настройка диапазонов subuid/subgid для вашего пользователя:**
    ```bash
    grep "$USER" /etc/subuid /etc/subgid || echo "$USER:100000:65536" | sudo tee -a /etc/subuid /etc/subgid
    ```
3.  **Установка и запуск от имени обычного пользователя:**
    ```bash
    dockerd-rootless-setuptool.sh install
    ```
4.  **Настройка переменных окружения:**
    ```bash
    export XDG_RUNTIME_DIR=/run/user/$(id -u)
    export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock
    ```
5.  **Проверка:** `docker info | grep Rootless` должен показать `Rootless: true`.

**Ограничения Rootless Docker:**
- **Сеть:** Используется `slirp4netns`, что может влиять на производительность. Порты ниже 1024 недоступны напрямую.
- **Хранилище:** Используется `fuse-overlayfs` или `overlayfs`.
- **Функции:** `--privileged` недоступен, некоторые `sysctl` и драйверы ограничены.

### 3. Настройка AppArmor и SELinux

**Проверка статуса:**
```bash
docker info | egrep -i 'apparmor|selinux'
aa-status       # для AppArmor
getenforce      # для SELinux
```

**AppArmor:**
Запуск с кастомным профилем:
```bash
docker run --rm --security-opt apparmor=my-custom-profile nginx
```
Отключение (не рекомендуется): `--security-opt apparmor=unconfined`.

**SELinux:**
При работе с bind-монтами используйте флаги `:z` (совместный доступ) или `:Z` (эксклюзивный доступ) для автоматической перемаркировки.
```bash
# Эксклюзивный доступ
docker run -v /srv/data:/data:Z ubuntu bash
# Совместный доступ
docker run -v /shared/logs:/var/log:z myapp
```
Отключение (не рекомендуется): `--security-opt label=disable`.

### 4. Безопасная конфигурация демона (`/etc/docker/daemon.json`)

```json
{
  "icc": false,
  "userns-remap": "default",
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  },
  "no-new-privileges": true,
  "insecure-registries": [],
  "disable-legacy-registry": true,
  "tlscacert": "/etc/docker/certs.d/ca.crt"
}
```
- `"icc": false"`: Запрещает сетевое взаимодействие между контейнерами по умолчанию.
- `"no-new-privileges": true"`: Запрещает процессам внутри контейнера повышать свои привилегии.
- `"disable-legacy-registry": true"`: Отключает поддержку старых реестров (v1).
- `"tlscacert"`: Указывает путь к CA-сертификату для доверия реестрам.

## Дополнительная информация

### Сравнение режимов безопасности

| Режим | Привилегии на хосте | Простота | Ограничения |
| :--- | :--- | :--- | :--- |
| **Без userns** | Контейнерный `root` = `root` на хосте (опасно) | Высокая | Минимальные |
| **`userns-remap`** | `root` в контейнере → непривилегированный UID на хосте | Средняя | Требует управления subuid/subgid, подготовки томов |
| **Rootless Docker** | Демон и контейнеры без `root`-прав на хосте | Ниже | Ограничения ядра, сети и некоторых функций Docker |
