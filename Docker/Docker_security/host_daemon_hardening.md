# Защита хоста и демона Docker (Hardening)

Данный документ описывает методы настройки хостовой операционной системы и демона `dockerd` для минимизации поверхности атаки и предотвращения компрометации хоста через контейнеры. Рекомендации основаны на стандартах **CIS Docker Benchmark (v1.7.0/1.8.0)**.

## Определения

**Защита хоста и демона Docker (Host and Daemon Hardening)** — комплекс мер по настройке операционной системы и конфигурации процесса `dockerd` для минимизации поверхности атаки.

**Пространства имен пользователей (User Namespaces)** — механизм ядра Linux, позволяющий сопоставлять UID/GID внутри контейнера с другими идентификаторами на хосте, предотвращая получение прав root на хосте при компрометации контейнера.

**Модули безопасности Linux (LSM — Linux Security Modules)** — подсистемы ядра (AppArmor, SELinux), обеспечивающие мандатное управление доступом (MAC) на основе политик.

**Cgroup v2 (Control Groups version 2)** — иерархическая система управления ресурсами (CPU, память, I/O), обеспечивающая лучшую изоляцию и необходимая для работы Rootless-режима.

**Rootless Docker** — режим работы, при котором и демон, и контейнеры запускаются без привилегий root, используя `user_namespaces`.

**Сетевые драйверы Rootless (slirp4netns, pasta)** — инструменты для эмуляции сетевого стека в пространстве пользователя. **Pasta** (Process-Address-Space-Translation) является современным стандартом с более высокой производительностью.

**mTLS (Mutual TLS)** — механизм взаимной аутентификации клиента и сервера с помощью сертификатов, критически важный для защиты удаленного Docker API.

**Аудит (Audit)** — регистрация системных вызовов и обращений к критическим файлам через подсистему `auditd`.

## Базовые концепции

### 1. Пространства имен пользователей (`userns-remap`)

Изоляция **User Identifier (UID)** и **Group Identifier (GID)** позволяет сопоставить пользователя `root` (UID 0) внутри контейнера с обычным непривилегированным пользователем на хосте.

- **В контейнере:** UID 0..65535
- **На хосте:** UID 100000..165536 (пример отображения)

### 2. Безрутовый режим (Rootless Docker)

**Rootless Docker** — режим, в котором демон и контейнеры запускаются от имени непривилегированного пользователя. Это исключает получение прав `root` на хосте даже при полном «побеге» из контейнера.

| Риск | Docker (root) | Rootless Docker |
| :--- | :--- | :--- |
| **Побег из контейнера** | Эскалация до `root` на хосте | Ограничение правами пользователя |
| **Компрометация демона** | Полный контроль над системой | Доступ только к ресурсам пользователя |

**Ограничения Rootless-режима:**
Несмотря на высокий уровень безопасности, Rootless Docker имеет ряд практических ограничений:
1.  **Низкоуровневые сервисы:** Приложения, требующие прямого управления сетевым стеком, монтирования файловых систем или доступа к специфическому оборудованию, могут не работать без привилегий реального `root`.
2.  **Legacy-системы:** Устаревшее ПО часто жестко завязано на доступ к защищенным системным директориям или специфическим портам (ниже 1024), что затрудняет миграцию в Rootless.
3.  **Сетевая производительность:** Использование `slirp4netns` или `pasta` вносит небольшие накладные расходы по сравнению с нативным `bridge` в root-режиме.
4.  **Сложность отладки:** Ограничения в namespaces могут усложнить использование инструментов системной диагностики.

Выбор режима должен зависеть от контекста: для большинства бизнес-приложений Rootless является стандартом, тогда как для инфраструктурных компонентов может потребоваться классический режим с усиленной изоляцией (Namespaces, Seccomp).

*Подробнее:* **[Rootless режим в Podman](../../Podman/podman_rootless.md)** (архитектурные принципы аналогичны).

### 3. Модули безопасности Linux (LSM)

Docker использует механизмы ядра для принудительной изоляции процессов:

- **[Seccomp](../../Linux/Security/Mechanisms/Seccomp.md)**: фильтрация системных вызовов (**syscalls**). Профиль по умолчанию блокирует около 40–44 опасных вызовов.
- **[AppArmor](../../Linux/Security/Mechanisms/AppArmor.md)** / **[SELinux](../../Linux/Security/Mechanisms/SELinux.md)**: ограничивают доступ к файловой системе и ресурсам на основе политик.

### 4. Docker Socket и группа docker

Доступ к Docker API фактически эквивалентен полному `root`-доступу к хосту.

1. **Группа `docker`:** Пользователи в этой группе могут управлять демоном без `sudo`, что позволяет запустить привилегированный контейнер и получить доступ к файлам хоста.
2. **Unix-сокет (`/var/run/docker.sock`):** Если сокет проброшен в контейнер, злоумышленник может управлять хостом.
3. **TCP-порт:** Никогда не открывайте сокет по сети без TLS-аутентификации.

### 5. Контейнерно-ориентированные ОС

Использование специализированных иммутабельных (immutable) систем (например, **Talos Linux**, Flatcar, Bottlerocket) исключает лишний инструментарий и минимизирует поверхность атаки.

### 6. Разделение разделов (Partitioning)

Для директории `/var/lib/docker` (или `/home/$USER/.local/share/docker` в Rootless) рекомендуется использовать отдельный раздел или квоты. Это предотвращает атаку типа «отказ в обслуживании» (DoS) через переполнение диска логами или образами.

### 7. Целостность и подписи образов

Docker Content Trust (DCT) считается устаревшим. Современный стандарт — использование **Cosign** для подписи образов в CI/CD и проверки их перед запуском.
*Подробнее:* **[Подпись и проверка образов](./image_signature_and_verification.md)**.

## Практические сценарии

### 1. Настройка аудита (auditd)

Согласно CIS Benchmark, необходимо настроить аудит критических файлов Docker (бинарные файлы, сокет, конфигурация). 

Подробные правила и инструкции по настройке см. в основном документе: **[`auditd`: Аудит событий безопасности — Сценарий для Docker](../../Linux/SystemAdministration/Logging/auditd.md#3-аудит-контейнерной-инфраструктуры-docker)**.


### 2. Настройка User Namespaces (`daemon.json`)

1. Выделите диапазоны идентификаторов:
    ```bash
    sudo usermod --add-subuids 100000-165536 --add-subgids 100000-165536 dockremap
    ```
2. Включите режим в `/etc/docker/daemon.json`:
    ```json
    { "userns-remap": "default" }
    ```
3. Перезапустите демон.

#### Детальный разбор работы маппинга

Маппинг работает по формуле: `host_uid = container_uid + base_id`.
При настройке `dockremap:100000:65536` из `/etc/subuid`:
- **UID 0** внутри контейнера = **UID 100000** на хосте.
- **UID 1000** внутри контейнера = **UID 101000** на хосте.

#### Проблема Bind Mount vs Docker Volume

**Bind mount (`/data:/data`)**:
Если хост-директория `/data` принадлежит пользователю с UID 1000, то процесс внутри контейнера (UID 0 -> хост 100000) не сможет писать в нее, так как для хоста это «другой» пользователь.
- `chown` внутри контейнера упадет с `Operation not permitted`, так как ядро видит попытку непривилегированного пользователя (100000) сменить владельца на 101000.
- `mkdir` упадет с `Permission denied`, если права доступа на хосте не 777.

**Docker Volume (`named_vol:/data`)**:
Дизайн: `/var/lib/docker/volumes/.../_data` управляется `dockerd`. При создании тома в режиме `userns` Docker автоматически устанавливает корректные права, и процессы внутри контейнера могут прозрачно работать с ФС.

**Итог:** Bind mount требует ручного согласования UID на хосте (например, `chown 100000:100000 /data`), тогда как Named volume решает проблему автоматически.

| Альтернатива | Проблема |
| :--- | :--- |
| `chown 101000:101000 /data` | UID 101000 может не существовать на хосте; хрупко при смене subuid. |
| `mode: 0777` | Дыра в безопасности; `chown` внутри контейнера всё равно упадёт. Подробнее: [почему 777 не всегда решает проблему](../../Linux/Security/Concepts/File_Permissions/overview_definitions.md#диагностика-почему-chmod-777-не-всегда-решает-проблему). |
| `:idmap` (Docker 25+) | Требует поддержки ФС (например, XFS с reflink) и ядра; пока не везде стабильно. |
| `user: root` в Compose | Контейнер будет root и сможет писать, но это нарушает принцип минимальных привилегий. |

### 3. Установка и запуск Rootless Docker

Для Docker 27+ рекомендуется использовать `pasta` для сетевого взаимодействия (выше производительность).

1. Убедитесь в наличии Cgroup v2: `stat -fc %T /sys/fs/cgroup/` (должно быть `cgroup2fs`).
2. Установите зависимости: `apt install -y dbus-user-session uidmap slirp4netns` (или `passt` для `pasta`).
3. Запустите скрипт: `curl -fsSL https://get.docker.com/rootless | sh`.
4. Настройте автозапуск: `loginctl enable-linger $USER`.
5. Проверка: `docker info | grep -E "Rootless|Cgroup"`.

### 4. Безопасный удаленный доступ (SSH и TLS)

Существует два основных способа безопасного управления удаленным демоном Docker.

#### Удаленный доступ через SSH (Рекомендуется)
Использование SSH-туннеля является наиболее простым и безопасным методом, так как он использует существующую инфраструктуру ключей SSH и не требует открытия дополнительных портов.

1.  **Настройка:** Убедитесь, что у вас есть доступ по SSH-ключу к удаленному хосту.
2.  **Использование через переменную окружения:**
    ```bash
    export DOCKER_HOST="ssh://user@remote-host"
    docker info
    ```
3.  **Использование через контексты:**
    ```bash
    docker context create remote-ssh --docker "host=ssh://user@remote-host"
    docker context use remote-ssh
    ```

#### Удаленный доступ через TLS (mTLS)
Если необходимо использовать прямое TCP-подключение (например, для интеграции с внешними системами мониторинга), используйте TLS с взаимной проверкой сертификатов.

1.  **Генерация ключей:** Создайте CA, сертификат сервера и сертификат клиента.
2.  **Конфигурация в `daemon.json`:**
    ```json
    {
      "tlsverify": true,
      "tlscacert": "/etc/docker/ca.pem",
      "tlscert": "/etc/docker/server-cert.pem",
      "tlskey": "/etc/docker/server-key.pem",
      "hosts": ["tcp://0.0.0.0:2376", "unix:///var/run/docker.sock"]
    }
    ```
3.  **Использование:** См. **[Docker Context](../docker_context.md)**.

### 5. Безопасная конфигурация демона (`daemon.json`)

| Параметр | Описание | Эффект для безопасности |
| :--- | :--- | :--- |
| `"icc": false` | Отключает Inter-Container Communication. | Контейнеры в сети `bridge` не могут общаться друг с другом напрямую без явного соединения. |
| `"userns-remap": "default"` | Включает маппинг пользователей. | Root в контейнере != root на хосте. |
| `"no-new-privileges": true` | Запрещает получение новых привилегий (SUID/SGID). | Предотвращает эскалацию через уязвимые бинарные файлы внутри контейнера. |
| `"live-restore": true` | Позволяет демону обновляться без остановки контейнеров. | Снижает время простоя при патчинге демона (несовместим со Swarm). |
| `"userland-proxy": false` | Отключает вспомогательный процесс проксирования. | Трафик идет через `iptables`, уменьшая поверхность атаки и потребление ресурсов. |
| `"disable-legacy-registry": true` | Запрещает работу с Docker Registry v1. | Исключает использование устаревших и небезопасных протоколов. |

### 6. Укрепление параметров ядра (sysctl)

Для повышения защиты хоста рекомендуется настроить параметры ядра, ограничивающие сетевые атаки и возможности эскалации.

Создайте файл `/etc/sysctl.d/99-docker-hardening.conf`:
```bash
# Запрет пересылки пакетов, не относящихся к интерфейсам Docker (если не требуется)
net.ipv4.ip_forward = 1 # Необходимо для работы Docker

# Защита от спуфинга
net.ipv4.conf.all.rp_filter = 1
net.ipv4.conf.default.rp_filter = 1

# Запрет приема ICMP-редиректов (защита от MITM)
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.default.accept_redirects = 0

# Ограничение доступа к dmesg для обычных пользователей
kernel.dmesg_restrict = 1

# Запрет доступа к kptr_restrict (скрытие адресов ядра)
kernel.kptr_restrict = 2
```
Примените настройки: `sudo sysctl --system`.
