# Укрепление безопасности контейнеров (Hardening)

Безопасность контейнера во время выполнения — критически важный аспект защиты всей системы. Ниже приведены ключевые практики по укреплению работающих контейнеров.

## 1. Не запускайте процессы от `root` внутри контейнера

Это самая серьезная и распространенная ошибка. Процессы в контейнере выполняются на ядре хост-системы. Хотя контейнеры изолированы, эта изоляция не абсолютна.

-   **Общее ядро:** Если в ядре Linux обнаружится уязвимость, вредоносный процесс, запущенный с правами `root` (UID 0) внутри контейнера, может проэксплуатировать её и получить полный `root`-доступ к хост-системе.
-   **UID 0 = UID 0:** Для ядра Linux пользователь `root` с UID 0 внутри контейнера — это тот же самый `root` с UID 0, что и на хосте. Разница лишь в ограничениях (namespaces, cgroups). Уязвимость в ядре может позволить обойти эти ограничения.

Если же процесс в контейнере запущен от имени непривилегированного пользователя, его возможности для эксплуатации уязвимостей ядра значительно сокращаются.

**Как правильно делать:** Создайте непривилегированного пользователя в `Dockerfile`.

```dockerfile
FROM debian:bookworm-slim

# 1. Выполняем действия от root (установка пакетов)
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*

# 2. Создаем группу и пользователя с фиксированным UID/GID
# Использование фиксированных ID помогает избежать проблем с правами на файловых системах
RUN groupadd --gid 1001 myuser && \
    useradd --uid 1001 --gid 1001 -m myuser

# 3. Копируем файлы и устанавливаем владельца
WORKDIR /app
COPY --chown=myuser:myuser . .

# 4. Переключаемся на созданного пользователя
USER myuser

# 5. Запускаем приложение от его имени
CMD ["./my-application"]
```

#### Запуск контейнера от имени непривилегированного пользователя

Помимо создания пользователя в `Dockerfile`, можно запустить контейнер с флагом `-u`, указав UID. Это особенно полезно для образов, где пользователь не был создан заранее.

```sh
# Запуск от пользователя с UID 3000
docker run -u 3000 <image>
```

## 2. Управление правами на монтированных томах (Volumes)

Когда процесс, запущенный от `root` в контейнере, создает файлы в подключенном томе (`bind mount`), эти файлы на хост-системе также будут принадлежать пользователю `root`.

-   **Последствия:** Обычный пользователь на хосте не сможет редактировать или удалять эти файлы без `sudo`, что создает неудобства и может нарушить работу скриптов.

#### Как решить проблему с правами доступа при Bind Mounts

**Способ 1: Изменить владельца файлов на хосте (Не рекомендуется)**

```bash
# Рекурсивно меняем владельца на текущего пользователя
sudo chown -R $(whoami):$(whoami) /путь/к/вашей/директории
```
-   **Минус:** Это нужно делать каждый раз. Не подходит для автоматизации.

**Способ 2: Синхронизировать UID/GID (Самый частый способ для `bind mounts`)**

Запустите процесс внутри контейнера с тем же UID и GID, что и у вашего пользователя на хосте.

1.  **Узнайте UID/GID на хосте:** `id -u` (например, 1000) и `id -g` (например, 1000).
2.  **Запустите контейнер с флагом `-u`:**

    ```bash
docker run -u "$(id -u):$(id -g)" \
           -v /путь/на/хосте:/app/data \
           my-image:1.0.0
    ```
Теперь файлы, созданные в контейнере, будут принадлежать вам на хосте.

**Способ 3: Использовать Docker Volumes (Рекомендуемый способ)**

Вместо `bind mounts` используйте **именованные тома (named volumes)**. Docker сам управляет правами в своей служебной директории, и такие механизмы как `userns-remap` корректно работают с ними "из коробки".

```bash
docker volume create my-app-data
docker run -v my-app-data:/app/data my-image:1.0.0
```
-   **Плюс:** Более переносимое и управляемое решение.
-   **Минус:** Менее удобно для прямого редактирования файлов с хоста.

## 3. Управление правами (Capabilities)

-   **Никогда не используйте `--privileged`**. Этот флаг отключает почти все механизмы изоляции и предоставляет контейнеру права, эквивалентные `root` на хосте.

    **Что именно делает флаг `--privileged`:**
    -   Дает доступ ко всем capabilities ядра Linux.
    -   Отключает профили безопасности `Seccomp` и `AppArmor`/`SELinux`.
    -   Дает прямой доступ ко всем устройствам в `/dev` на хосте.
    -   Монтирует файловые системы ядра (`/proc`) в режиме чтение-запись (RW).

    > **Пример:** Внутри привилегированного контейнера можно смонтировать файловую систему хоста и получить к ней полный доступ:
    > ```sh
    > # Внутри контейнера, запущенного с --privileged
    > mkdir /mnt/hdd
    > mount /dev/sda1 /mnt/hdd
    > # Теперь в /mnt/hdd доступна корневая ФС хоста
    > ```

-   **Используйте `--cap-drop=ALL` и `--cap-add`**: По умолчанию отключайте все права, а затем добавляйте только те, которые действительно необходимы вашему приложению (например, `NET_BIND_SERVICE` для прослушивания портов ниже 1024).

## 4. Запрет на повышение привилегий

Используйте флаг `--security-opt=no-new-privileges`, чтобы запретить процессам внутри контейнера получать новые привилегии через `suid` или `sgid` бинарные файлы. Это важная мера защиты от атак повышения привилегий.

```sh
docker run --security-opt=no-new-privileges <image>
```

## 5. Ограничение ресурсов

Ограничивайте ресурсы, доступные контейнеру, чтобы предотвратить DoS-атаки на хост-систему.

-   **Память:** `--memory="400m"` (ограничение RAM), `--memory-swap="1g"` (RAM + swap).
-   **CPU:** `--cpus=0.5` (не более половины одного ядра CPU).
-   **Лимиты на процессы и файлы:** `--ulimit nofile=5` (не более 5 открытых файлов), `--ulimit nproc=5` (не более 5 дочерних процессов).
-   **Политика перезапуска:** `--restart=on-failure:5` (перезапускать контейнер при ошибке не более 5 раз).

Пример:
```sh
docker run \
  --memory="400m" \
  --memory-swap="1g" \
  --cpus=0.5 \
  --restart=on-failure:5 \
  --ulimit nofile=5 \
  --ulimit nproc=5 \
  <image>
```

## 6. Файловая система только для чтения

Запускайте контейнеры с файловой системой только для чтения, чтобы предотвратить изменение файлов внутри контейнера.

```sh
docker run --read-only <image>
```

Если приложению требуется временное хранилище, используйте `tmpfs`.

```sh
docker run --read-only --tmpfs /tmp:rw,noexec,nosuid <image>
```
- `rw`: разрешает запись в `/tmp`.
- `noexec`: запрещает выполнение бинарных файлов из `/tmp`.
- `nosuid`: игнорирует `set-user-identifier` или `set-group-identifier` биты.
