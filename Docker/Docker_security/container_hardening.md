# Укрепление безопасности контейнеров (Hardening)

## Определения

**Укрепление контейнеров (Container Hardening)** — это процесс уменьшения поверхности атаки и минимизации уязвимостей контейнера путем применения набора лучших практик и конфигураций безопасности.

## Базовые концепции

### Принцип наименьших привилегий (Principle of Least Privilege)

Ключевая концепция безопасности, согласно которой любой процесс должен обладать только теми привилегиями, которые необходимы для выполнения его задачи. В контексте Docker это означает отказ от запуска контейнеров с правами `root`, ограничение доступа к ресурсам и возможностям ядра.

### Риски общего ядра хоста

Контейнеры, работающие на одном хосте, используют общее ядро Linux. Если в ядре обнаружится уязвимость, вредоносный процесс, запущенный с правами `root` (UID 0) внутри контейнера, может проэксплуатировать её и получить полный `root`-доступ к хост-системе. Для ядра пользователь `root` с UID 0 внутри контейнера — это тот же самый `root`, что и на хосте, с разницей лишь в ограничениях (namespaces, cgroups).

### Механизмы изоляции и их пределы

Docker использует пространства имен (namespaces) и контрольные группы (cgroups) для изоляции контейнеров. Однако эта изоляция не является абсолютной. Неправильные конфигурации, такие как запуск с флагом `--privileged`, практически полностью отключают защитные механизмы.

## Практические сценарии

### 1. Запуск процессов от непривилегированного пользователя

**Никогда не запускайте процессы от `root` внутри контейнера.**

**Решение:** Создайте специального пользователя в `Dockerfile` и переключитесь на него.

```dockerfile
FROM debian:bookworm-slim

# 1. Выполняем действия от root (установка пакетов)
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*

# 2. Создаем группу и пользователя с фиксированным UID/GID
# Использование фиксированных ID помогает избежать проблем с правами на файловых системах
RUN groupadd --gid 1001 myuser && \
    useradd --uid 1001 --gid 1001 -m myuser

# 3. Копируем файлы и устанавливаем владельца
WORKDIR /app
COPY --chown=myuser:myuser . .

# 4. Переключаемся на созданного пользователя
USER myuser

# 5. Запускаем приложение от его имени
CMD ["./my-application"]
```

Также можно запустить контейнер с флагом `-u`, указав UID. Это полезно для образов, где пользователь не был создан заранее.

```sh
# Запуск от пользователя с UID 3000
docker run -u 3000 <image>
```

### 2. Управление правами доступа к томам (Volumes)

Когда процесс от `root` в контейнере создает файлы в `bind mount`, они принадлежат `root` на хосте.

**Решения:**

- **Синхронизация UID/GID (для `bind mounts`):** Запустите контейнер с UID/GID вашего пользователя на хосте.
    1. Узнайте UID/GID: `id -u` и `id -g`.
    2. Запустите контейнер:

```bash
docker run -u "$(id -u):$(id -g)" \
           -v /путь/на/хосте:/app/data \
           my-image:1.0.0
```

- **Использование Docker Volumes (Рекомендуемый способ):** Docker сам управляет правами в своей директории.

```bash
docker volume create my-app-data
docker run -v my-app-data:/app/data my-image:1.0.0
```

### 3. Управление Capabilities ядра

- **Никогда не используйте `--privileged`**. Этот флаг отключает почти все механизмы изоляции и предоставляет контейнеру права, эквивалентные `root` на хосте.

    **Что именно делает флаг `--privileged`:**
  - Дает доступ ко всем capabilities ядра Linux.
  - Отключает профили безопасности `Seccomp` и `AppArmor`/`SELinux`.
  - Дает прямой доступ ко всем устройствам в `/dev` на хосте.
  - Монтирует файловые системы ядра (`/proc`) в режиме чтение-запись (RW).

    > **Пример:** Внутри привилегированного контейнера можно смонтировать файловую систему хоста и получить к ней полный доступ:
>
    > ```sh
    > # Внутри контейнера, запущенного с --privileged
    > mkdir /mnt/hdd
    > mount /dev/sda1 /mnt/hdd
    > # Теперь в /mnt/hdd доступна корневая ФС хоста
    > ```

- **Используйте `--cap-drop=ALL` и `--cap-add`**: По умолчанию отключайте все права, а затем добавляйте только те, которые действительно необходимы вашему приложению (например, `NET_BIND_SERVICE` для прослушивания портов ниже 1024).

### 4. Запрет на повышение привилегий

Используйте флаг `--security-opt=no-new-privileges`, чтобы запретить процессам внутри контейнера получать новые привилегии через `suid` или `sgid` бинарные файлы.

```sh
docker run --security-opt=no-new-privileges <image>
```

### 5. Ограничение ресурсов

Ограничивайте ресурсы, чтобы предотвратить атаки типа "отказ в обслуживании" (DoS).

- **Память:** С помощью параметра `--memory` ограничивается объем оперативной памяти (RAM), доступной контейнеру. Параметр `--memory-swap` разрешает контейнеру использовать данные на диске (подкачку), превышающие выделенный объем RAM. Он работает только в сочетании с `--memory`. Например, если `--memory="400m"` и `--memory-swap="1g"`, то контейнер может использовать 400 МБ оперативной памяти и дополнительно 600 МБ подкачки (1 ГБ - 400 МБ).
- **CPU:** `--cpus=0.5` (не более половины одного ядра CPU).
- **Лимиты на процессы и файлы:** `--ulimit nofile=5` (не более 5 открытых файлов), `--ulimit nproc=5` (не более 5 дочерних процессов).
- **Политика перезапуска:** `--restart=on-failure:5` (перезапускать контейнер при ошибке не более 5 раз).

Пример:

```sh
docker run \
  --memory="400m" \
  --memory-swap="1g" \
  --cpus=0.5 \
  --restart=on-failure:5 \
  --ulimit nofile=5 --ulimit nproc=5 \
  <image>
```

### 6. Файловая система только для чтения

Запускайте контейнеры с файловой системой `read-only`, чтобы предотвратить изменение файлов.

```sh
docker run --read-only <image>
```

Если приложению нужно временное хранилище, используйте `tmpfs`.

```sh
docker run --read-only --tmpfs /tmp:rw,noexec,nosuid <image>
```

- `rw`: разрешает запись.
- `noexec`: запрещает выполнение бинарных файлов.
- `nosuid`: игнорирует `set-user-identifier` / `set-group-identifier` биты.
