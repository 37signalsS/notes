# Укрепление безопасности контейнеров (Hardening)

Данный документ описывает набор практик и конфигураций для минимизации поверхности атаки и усиления изоляции запущенных контейнеров.

## Определения

**Укрепление контейнеров (Container Hardening)** — процесс уменьшения поверхности атаки контейнера путем применения защитных конфигураций на уровне среды выполнения (**runtime**).

**Принцип наименьших привилегий (Principle of Least Privilege)** — предоставление процессу только тех прав и ресурсов, которые необходимы для выполнения его задачи.

**Поверхность атаки (Attack Surface)** — совокупность всех точек входа и механизмов, которые могут быть использованы для компрометации системы.

## Базовые концепции

Безопасность и изоляция контейнеров в Linux строятся на трех фундаментальных механизмах ядра:

1. **Namespaces (Пространства имен)** — обеспечивают логическую изоляцию (сеть, процессы, монтирования). См. подробнее: **[Изоляция контейнеров: Namespaces и Cgroups](../../Docker/Concepts/linux_isolation.md)**.
2. **Cgroups (Контрольные группы)** — ограничивают потребление ресурсов (CPU, RAM, I/O).
3. **Capabilities (Привилегии)** — разделяют полномочия `root` на мелкие части. См. подробнее: **[Linux Capabilities](../../Linux/Security/Mechanisms/Capabilities.md)**.

### Риски общего ядра хоста

Контейнеры используют общее ядро хоста. Компрометация ядра через уязвимость (Zero-Day) или избыточные привилегии контейнера позволяет злоумышленнику совершить **побег из контейнера (container escape)**. Ключевая задача Hardening — предотвратить выход за пределы изоляции.

## Практические сценарии

### 1. Запуск от непривилегированного пользователя

По умолчанию процессы в контейнере работают от `root`. Это создает риск: при побеге злоумышленник получает root-права на хосте.

* **Решение:** Используйте инструкцию `USER` в `Dockerfile` (см. **[Безопасность в Dockerfile](../Dockerfile/Docker_best_practices/security.md)**).
* **Runtime-флаг:** Можно принудительно указать UID при запуске:

    ```bash
    docker run -u 1001 my-image
    ```

### 2. Управление Capabilities ядра

Docker по умолчанию отключает опасные привилегии, но оставляет некоторые (например, `NET_RAW`).

**Ключевой принцип:** root (UID 0) внутри контейнера — это не root на хосте. Docker ограничивает права через Linux Capabilities, разбивая привилегии суперпользователя на отдельные возможности. Опасные capability вроде `SYS_ADMIN`, `SYS_MODULE`, `SYS_PTRACE` исключены по умолчанию.

* **Лучшая практика:** Отключите все возможности и добавьте только необходимые.

    ```bash
    # Отключить всё, разрешить только биндинг портов ниже 1024
    docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE my-image
    ```

* **Проверка списка capabilities контейнера:**

    ```bash
    docker inspect <container> | jq '.[0].HostConfig.CapAdd, .[0].HostConfig.CapDrop'
    ```

* **Запрет `--privileged`:** Этот флаг отключает почти всю изоляцию (Namespaces, Seccomp, Capabilities), предоставляя контейнеру полный доступ к устройствам хоста. **Никогда не используйте его в production.**

### 3. Запрет повышения привилегий

Флаг `no-new-privileges` запрещает процессам внутри контейнера получать новые права через `suid` или `sgid` бинарные файлы (например, через уязвимый `sudo`).

```bash
docker run --security-opt=no-new-privileges my-image
```

### 4. Ограничение ресурсов (Cgroups)

Без лимитов один контейнер может вызвать отказ в обслуживании (**DoS**) всего хоста (Noisy Neighbor problem).

```bash
docker run \
  --memory="512m" \
  --cpus=0.5 \
  --ulimit nofile=1024:1024 \
  --pids-limit 100 \
  my-image
```

* `pids-limit` — защита от fork-бомб.
* `ulimit nofile` — ограничение количества открытых файлов.

### 5. Файловая система только для чтения

Большинство атак требует записи файлов (загрузка майнеров, изменение конфигов). Режим `read-only` блокирует эти действия.

```bash
docker run --read-only --tmpfs /tmp:rw,noexec,nosuid my-image
```

* `--tmpfs` позволяет приложению писать во временную память, не затрагивая образ.
* `noexec` запрещает выполнение файлов из `/tmp`.

### 6. Управление доступом к томам

При использовании **bind mounts** файлы, созданные root-контейнером, принадлежат root-хосту.

* **Рекомендация:** Используйте **Docker Volumes** вместо bind mounts там, где это возможно. Docker сам управляет правами доступа в своей директории.
* Если bind mount необходим, монтируйте его в режиме `ro` (read-only):

    ```bash
    docker run -v /host/data:/app/data:ro my-image
    ```

### 7. Использование минималистичных образов

Использование `Alpine` или `Distroless` сокращает количество установленных утилит (`shell`, `curl`), которые злоумышленник может использовать для развития атаки. См. подробнее: **[Безопасность в Dockerfile](../Dockerfile/Docker_best_practices/security.md)**.

### Аудит и проверка конфигурации

Для проверки текущих настроек безопасности запущенного контейнера используйте:

```bash
docker inspect <container_id> --format='{{json .HostConfig.SecurityOpt}}'
```
