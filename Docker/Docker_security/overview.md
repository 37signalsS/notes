# Безопасность Docker: Обзор угроз и векторов атак

Docker, при всей своей мощи и удобстве, создает новые вызовы в области безопасности. Ключевая проблема заключается в том, что по умолчанию демон Docker (`dockerd`) работает с правами `root`. Это означает, что **любой пользователь или процесс, получивший доступ к управляющему API Docker, фактически получает полный `root`-доступ к хост-системе.**

Этот документ является отправной точкой для понимания основных угроз и содержит ссылки на более подробные руководства по укреплению безопасности.

### Основные механизмы, создающие риски

Два основных механизма непреднамеренно приводят к повышению привилегий:

1.  **Добавление пользователя в группу `docker`**
    -   **Назначение:** Позволяет пользователю выполнять команды `docker` без `sudo`.
    -   **Риск:** Пользователь получает неконтролируемый доступ к Docker API через сокет `/var/run/docker.sock`. Это позволяет ему запустить контейнер с расширенными правами и легко получить `root`-доступ к хосту.

2.  **Прямой доступ к сокету `/var/run/docker.sock`**
    -   **Назначение:** `/var/run/docker.sock` — это UNIX-сокет для взаимодействия с демоном Docker (`dockerd`).
    -   **Риск:** Предоставление контейнеру доступа к этому сокету (например, через монтирование `-v /var/run/docker.sock:/var/run/docker.sock`) позволяет ему управлять демоном Docker на хосте, что является классическим сценарием "побега из контейнера" (container escape).

> Для сценариев, требующих взаимодействия с Docker API (например, CI/CD агенты), рекомендуется использовать прокси, которые фильтруют API-запросы, вместо прямого монтирования сокета.

## Векторы атак

### Docker Socket (`/var/run/docker.sock`)

Ключевой вектор локальной атаки — это доступ к управляющему сокету Docker.

-   **Что это?** Это **[Unix-сокет](../../Networking/Concepts/socket_api.md#unix-сокеты-af_unix)**, который служит локальным API-интерфейсом для демона Docker. Подробное объяснение принципа работы Unix-сокетов находится в основной базе знаний по сетям.
-   **Права доступа:** По умолчанию сокет принадлежит пользователю `root` и группе `docker` с правами `660`.
-   **Основная угроза:** Любой пользователь или процесс, получивший право на запись в этот сокет (например, через членство в группе `docker` или монтирование сокета в контейнер), получает **полный контроль над демоном Docker** и, как следствие, может легко получить `root`-доступ к хост-системе.

Несмотря на риск, прямое использование сокета необходимо для работы инструментов управления (Portainer) и систем CI/CD (GitLab Runner, Jenkins), которые запускаются в контейнерах для управления другими контейнерами. В таких случаях доверие к используемому образу должно быть абсолютным.

#### Альтернативные подходы

-   **Прокси для сокета:** Использование утилит вроде `docker-socket-proxy`, которые фильтруют опасные API-вызовы.
-   **Сборка без демона:** Применение инструментов типа **Kaniko** или **Buildah**, которые не требуют доступа к демону Docker.
-   **Изолированный Docker-in-Docker (dind):** Запуск отдельного, непривилегированного демона Docker внутри контейнера.

### Сетевой доступ (TCP)

Демон можно настроить на прослушивание сетевых портов, что создает дополнительный вектор атаки.

-   **Порт `2375` (HTTP):** Незашифрованный порт. Подключение к нему предоставляет полный контроль над демоном Docker.
-   **Порт `2376` (HTTPS):** Использует TLS для аутентификации и шифрования.
-   **SSH:** Использует аутентификацию по SSH.

## Повышение привилегий и побег из контейнера

Если злоумышленник получил доступ к сокету Docker, повышение привилегий до `root` на хосте становится тривиальной задачей.

### Сценарий 1: Прямой доступ к сокету на хосте

Атака заключается в запуске привилегированного контейнера с монтированием корневой файловой системы хоста.

**Пример получения root-доступа пользователем из группы `docker`:**
```sh
# Пользователю не нужно sudo для этой команды, если он в группе docker
docker run -it --rm --privileged -v /:/host busybox:1.36.1 chroot /host
# Результат: root-шелл на хост-системе
```

### Сценарий 2: Побег из контейнера с проброшенным сокетом

Если сокет Docker монтируется внутрь контейнера, это позволяет процессам внутри него управлять демоном Docker на хосте.

```sh
# 1. Злоумышленник находится в контейнере, куда по ошибке смонтировали сокет
# (docker run -v /var/run/docker.sock:/var/run/docker.sock ...)

# 2. Он устанавливает docker-cli и запускает новый контейнер, 
# монтируя корневую ФС хоста.
docker run -it --rm -v /:/host busybox chroot /host

# 3. Результат: он получает root-шелл на хост-системе.
whoami # -> root
```
