# Обзор безопасности Docker

Демон Docker (`dockerd`) по умолчанию работает от `root`. Любой процесс с доступом к Docker API получает полный `root`-доступ к хосту. Данный документ описывает основные векторы угроз и служит отправной точкой для изучения безопасности в экосистеме Docker.

## Определения

**Поверхность атаки (Attack Surface)** — совокупность точек входа, через которые злоумышленник может скомпрометировать Docker-инфраструктуру (демон, образы, контейнеры, реестры).

**Группа `docker`** — системная группа, пользователи которой могут выполнять команды `docker` без `sudo`. Предоставляет неконтролируемый доступ к Docker API, что эквивалентно правам `root` на хосте.

**Docker Socket (`/var/run/docker.sock`)** — **[Unix-сокет](../../Networking/Concepts/socket_api.md#unix-сокеты-af_unix)** для локального взаимодействия с демоном `dockerd`.

**Software Bill of Materials (SBOM)** — полный перечень всех компонентов, библиотек и зависимостей, входящих в состав Docker-образа. Необходим для анализа цепочки поставок.

## Базовые концепции

Безопасность Docker в 2025 году фокусируется на эшелонированной защите (Defense in Depth) и минимизации доверенной базы (TCB).

### 1. Безопасность демона и хоста

Ошибки конфигурации демона могут привести к полной компрометации сервера. В 2025 году критическими угрозами стали уязвимости в API Docker Desktop (CVE-2025-9074) и побеги через рантайм `runc` (CVE-2025-31133).

- **Изоляция сокета:** Ограничение доступа к `/var/run/docker.sock`.
- **Сетевой доступ:** Отказ от незашифрованного TCP (порт 2375) в пользу TLS (порт 2376).
- **Rootless mode:** Запуск демона и контейнеров без прав root на хосте — основной стандарт защиты.

### 2. Безопасность внутри контейнера

Контейнеры используют общее ядро хоста. Уязвимости в ядре или рантайме (runc, containerd) могут позволить совершить "побег":

- **User Namespaces:** Маппинг root-пользователя контейнера на обычного пользователя хоста.
- **Capabilities и Seccomp:** Ограничение системных вызовов ядра.
- **Read-only FS:** Запуск контейнеров с неизменяемой файловой системой (`--read-only`).

### 3. Безопасность образов и цепочки поставок (Supply Chain)

Современный подход требует перехода к модели Zero-CVE:

- **Микро-дистрибутивы:** Использование Wolfi или Chainguard образов вместо Alpine/Debian для минимизации поверхности атаки.
- **Подписи и аттестации:** Проверка подлинности образов через Cosign и Docker Content Trust.
- **Анализ SBOM:** Автоматическая проверка всех зависимостей на наличие уязвимостей.
