# Мониторинг безопасности контейнеров в Runtime

Данный документ описывает подходы к наблюдению за состоянием запущенных контейнеров для обнаружения аномалий, атак и отклонений от эталонного состояния в реальном времени.

## Определения

**Мониторинг безопасности в Runtime (Runtime Security Monitoring)** — процесс непрерывного наблюдения за поведением запущенных контейнеров для выявления аномалий, подозрительной активности и несанкционированного доступа после этапа развертывания.

**eBPF (Extended Berkeley Packet Filter)** — технология ядра Linux для глубокого мониторинга системных вызовов, сетевых пакетов и файловых операций с минимальными накладными расходами. Является фундаментом современного мониторинга контейнеров. Подробнее см. в [**eBPF — виртуальная машина ядра**](../../Linux/Core/kernel/ebpf.md).

**Обнаружение дрейфа (Drift Detection)** — выявление изменений в файловой системе или процессах контейнера, которые отличают его от исходного состояния образа (например, появление новых бинарных файлов, модификация конфигураций или запуск непредусмотренных процессов).

## Базовые концепции

### Проблема «слепой зоны» стандартного логирования

Стандартные системные логи хоста (`/var/log/syslog`, `auth.log`) не обеспечивают достаточной видимости событий внутри контейнеров. При совершении побега из контейнера (**container escape**) злоумышленник может изменять файлы на хосте, но логи не позволят однозначно связать это действие с конкретным контейнером. Команда `docker logs` собирает только stdout/stderr приложения, полностью игнорируя системную активность (файловые операции, сетевые соединения на низком уровне).

### Принцип «Один процесс на контейнер»

Мониторинг безопасности Docker опирается на предсказуемость поведения контейнеров. Если контейнер запущен для работы Nginx, любое появление процесса `sh` или `curl` внутри него является аномалией, которую легко обнаружить инструментами runtime-мониторинга.

### Эволюция инструментов мониторинга

1.  **Классический аудит (auditd):** Отслеживает системные вызовы, но не понимает контекст контейнеров (Container ID, имя образа). Подробнее: **[`auditd`: Аудит событий безопасности](../../Linux/SystemAdministration/Logging/auditd.md)**.
2.  **Обнаружение (Falco):** Анализ системных вызовов через eBPF и генерация алертов на основе YAML-правил. См. **[Falco](../../Security/Tools/falco.md)**.
3.  **Предотвращение и блокировка (Tetragon, Aqua Tracy):** Современный стандарт. Эти инструменты не только обнаруживают угрозы, но и могут мгновенно завершить процесс или заблокировать сетевое соединение на уровне ядра Linux (**Enforcement**), предотвращая атаку до её завершения.

### Современные тренды 2026 года

- **Runtime SBOM (Dynamic SBOM):** Непрерывное сопоставление запущенных в памяти библиотек с данными SBOM для выявления уязвимостей, которые "проснулись" только при выполнении. Это позволяет обнаружить эксплуатацию 1-day уязвимостей в зависимостях, которые не были выявлены при статическом сканировании образа.
- **Agentless Monitoring:** Использование облачных API и eBPF-зондов на уровне хоста, не требующих установки тяжелых агентов внутрь каждого контейнера. Это повышает скрытность мониторинга и снижает накладные расходы.
- **Интеграция с SIEM/SOAR:** Автоматическое реагирование на инциденты (например, изоляция скомпрометированного контейнера в карантинную сеть или автоматическое снятие дампа памяти для форензики).
- **AI-анализ аномалий:** Использование легковесных ML-моделей для фильтрации «шума» и снижения количества ложноположительных срабатываний.

## Практические сценарии

### Использование нативных инструментов Docker

Для базового мониторинга событий безопасности можно использовать команду `docker events`.

```bash
# Отслеживание попыток выполнения команд внутри контейнеров (exec)
docker events --filter 'event=exec_create' --filter 'event=exec_start'
# → 2026-07-19T14:30:05.123456789+03:00 container exec_create: /bin/bash (container_id=abc123...)
```

### События, подлежащие обязательному мониторингу

Для обнаружения компрометации (установка майнеров, кража учетных данных, закрепление в системе) необходимо отслеживать:

1.  **Доступ к критичным файлам:**
    - Чтение `/etc/shadow` или попытки модификации `/etc/passwd`.
    - Доступ к директориям SSH-ключей (`~/.ssh/`).
    - Модификация доверенных корневых сертификатов (`/etc/ssl/certs`).
2.  **Манипуляции с процессами:**
    - Запуск интерактивных оболочек (`sh`, `bash`) внутри продуктовых контейнеров.
    - Использование утилит `su`, `sudo` или запуск бинарников с установленным SUID-битом.
    - Выполнение кода из памяти (fileless attacks) — отслеживается через eBPF (memfd_create).
3.  **Сетевые аномалии:**
    - Сканирование внутренних сетей из контейнера (**Lateral Movement**).
    - Исходящие соединения к C2-серверам или майнинг-пулам.
    - Попытки обращения к метаданным облачного провайдера (например, `169.254.169.254`).

### Реагирование на дрейф (Drift Prevention)

Использование Tetragon для автоматической блокировки попыток изменения прав доступа (`chmod +x`) для новых файлов или запрета выполнения любых бинарных файлов, не входящих в белый список оригинального образа.
