# Мониторинг безопасности контейнеров в Runtime

## Определения

**Runtime Security Monitoring** — процесс непрерывного наблюдения за поведением запущенных контейнеров для выявления аномалий, подозрительной активности и несанкционированного доступа.

**eBPF (Extended Berkeley Packet Filter)** — технология ядра Linux, позволяющая безопасно выполнять пользовательский код в песочнице внутри ядра, что идеально подходит для мониторинга системных вызовов (syscalls), сетевых пакетов и файловых операций с минимальным overhead (накладными расходами).

## Базовые концепции

### Проблема «слепой зоны» стандартного логирования

Стандартные системные логи (`/var/log/syslog`, `auth.log` и т.д.) не дают достаточной видимости того, что происходит внутри контейнеров.

Если злоумышленник осуществляет побег (container escape) — например, через привилегированный контейнер или смонтированный `docker.sock` — и напрямую изменяет файлы на хосте (например, `/etc/shadow`), стандартные средства логирования могут это пропустить или показать без привязки к конкретному контейнеру. Команда `docker logs` в таких случаях также бесполезна.

### Ограничения auditd

Утилита `auditd` способна отлавливать изменения критичных файлов (например, `/etc/shadow`). Однако при работе с контейнерами она имеет существенный недостаток: `auditd` фиксирует только низкоуровневый процесс (чаще всего `runc` или `containerd`), который обращается к файлу. Из лога `auditd` невозможно понять, *какой именно* контейнер и *какой процесс внутри него* инициировал вредоносное действие.

### Инструменты на базе eBPF (Tetragon, Falco)

Для полноценного мониторинга контейнеров в runtime необходимо использовать инструменты на базе eBPF. Они позволяют отслеживать события с учетом контекста контейнера (namespaces, cgroups).

* **[Falco](../../Security/Tools/falco.md):** Популярный инструмент для обнаружения угроз в runtime, использующий eBPF. Отлично подходит для алертинга.
* **Tetragon:** Инструмент от команды Cilium. Помимо отслеживания системных вызовов, доступа к файлам и сети, Tetragon позволяет **блокировать** вредоносные действия (enforcement) прямо на уровне ядра. Например, можно настроить политику (Tracing Policy), которая немедленно завершит процесс (SIGKILL) при попытке чтения `/etc/shadow`.
* **Cilium:** Если Tetragon используется для системных вызовов и файлов, то Cilium — это Custom Network Policy, управляющая и фильтрующая сетевое взаимодействие на уровне L3-L7 с помощью eBPF.

> **Важно:** Для корректной работы eBPF-инструментам (тому же Tetragon) требуется доступ к пространствам имен (namespaces) хоста (в частности, PID namespace, через флаг `--pid=host`) и доступ к cgroups.

## Практические сценарии

### События, требующие обязательного мониторинга

Для своевременного обнаружения компрометации (например, установки майнеров, сбора кредов, персистентности) рекомендуется отслеживать следующие векторы:

1. **Доступ к критичным файлам и директориям:**
    * `/etc/shadow`, `/etc/passwd` (попытки чтения или создания новых пользователей).
    * `~/.ssh/`, `/root/.ssh/` (кража или добавление ключей).
2. **Удаление логов (сокрытие следов):**
    * Очистка `/var/log/wtmp`, `/var/log/btmp` или bash history (`.bash_history`). Легитимные процессы редко удаляют эти файлы напрямую.
3. **Вмешательство в средства безопасности:**
    * Модификация или удаление правил `auditd`, манипуляции с агентами защиты.
4. **Повышение привилегий и закрепление (Persistence):**
    * Модификация `crontab` на хосте.
    * Использование утилит `su`, `sudo` или изменение SUID/SGID бинарников.
5. **Сетевые аномалии:**
    * Попытки сканирования внутренней сети (Lateral Movement) из контейнера, который не должен этого делать.
    * Обращения к нестандартным портам или майнинг-пулам.
