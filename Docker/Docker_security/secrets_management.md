# Управление секретами в Docker

Данный документ описывает методы безопасного хранения и передачи конфиденциальных данных (паролей, токенов, ключей API) в экосистеме Docker.

## Определения

**Управление секретами (Secrets Management)** — совокупность практик по безопасному хранению, ограничению доступа и ротации чувствительных данных.

**Секрет** — любая информация, компрометация которой может нанести ущерб системе (например, пароль от базы данных или секретный ключ **JWT (JSON Web Token)**).

**Принцип разделения (Separation of Concerns):** секреты должны храниться отдельно от кода и образов. Попадание секретов в слои образа или историю **Git** является критической уязвимостью.

## Базовые концепции

В Docker существует несколько уровней управления секретами в зависимости от режима работы и сложности инфраструктуры:

### 1. Переменные окружения (**ENV**)

Самый простой, но наименее безопасный метод.
- **Риски:** Секреты видны в выводе `docker inspect`, могут попасть в логи контейнера или быть «запечены» в историю образа при использовании инструкции `ENV` в `Dockerfile`.

### 2. Секреты Docker Compose

Механизм для одиночных хостов (Compose V2). Секреты монтируются как файлы во временную файловую систему в оперативной памяти (**tmpfs**) по пути `/run/secrets/`.
- **Преимущества:** Секреты не сохраняются на диске контейнера и не видны в переменных окружения.

### 3. Секреты Docker Swarm

Встроенное решение для кластеров. Секреты шифруются при хранении в базе данных **Raft** и передаются только тем узлам, на которых запущены соответствующие сервисы.
- **SSoT:** Подробные примеры и команды управления описаны в **[Секреты и конфигурации в Swarm](../../Docker_swarm/swarm_secrets_configs.md)**.

### 4. Секреты сборки BuildKit

Механизм для безопасной передачи секретов (например, ключей для скачивания пакетов из приватных репозиториев) во время сборки образа без их сохранения в истории слоев.

## Практические сценарии

### 1. Использование Docker Compose Secrets

Это рекомендуемый метод для локальной разработки и одиночных серверов.

**Пример `docker-compose.yml`:**

```yaml
services:
  app:
    image: my-app:1.0
    secrets:
      - db_password
    environment:
      # Многие приложения поддерживают суффикс _FILE для чтения из секрета
      - DB_PASSWORD_FILE=/run/secrets/db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt  # Файл на хосте (не коммитить в Git!)
```

**Преимущество:** Секрет доступен приложению только как файл. Если злоумышленник получит доступ к выводу `docker inspect`, он увидит только путь к файлу, но не его содержимое.

### 2. Секреты на этапе сборки (BuildKit)

Для использования секретов при сборке необходимо включить **BuildKit** (установлен по умолчанию в современных версиях Docker).

**Пример `Dockerfile`:**

```dockerfile
#syntax=docker/dockerfile:1
FROM python:3.11-slim

# Монтируем секрет только на время выполнения команды RUN
RUN --mount=type=secret,id=pip_conf \
    pip install --config-file /run/secrets/pip_conf my-private-package
```

**Запуск сборки:**
```bash
docker build --secret id=pip_conf,src=~/.pip/pip.conf -t my-app .
```
Секрет не попадет ни в один из слоев итогового образа.

### 3. Интеграция с внешними менеджерами (Vault)

Для крупных production-сред рекомендуется использовать специализированные системы, такие как **HashiCorp Vault**.
- **Преимущества:** Динамическая генерация секретов, детальный аудит, централизованная ротация.
- **Подробнее:** См. **[Интеграция Vault с Docker](../../Vault/guides/vault_docker_integration.md)**.
