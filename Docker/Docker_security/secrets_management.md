# Управление секретами в Docker

Данный документ описывает методы безопасного хранения и передачи конфиденциальных данных (паролей, токенов, ключей API) в экосистеме Docker.

## Определения

**Управление секретами (Secrets Management)** — совокупность практик по безопасному хранению, ограничению доступа, аудиту и ротации чувствительных данных.

**Секрет** — любая информация, компрометация которой может нанести ущерб системе (пароли БД, API-ключи, TLS-сертификаты, секретные ключи **JWT (JSON Web Token)**).

**Принцип разделения (Separation of Concerns):** секреты должны храниться отдельно от кода и образов. Попадание секретов в слои образа или историю **Git** является критической уязвимостью.

## Базовые концепции

В Docker существует несколько уровней управления секретами в зависимости от режима работы и сложности инфраструктуры:

### 1. Переменные окружения (**ENV**)

Самый распространенный, но **наименее безопасный** метод.

- **Риски:** Секреты видны в выводе `docker inspect`, `docker history`, могут попасть в логи контейнера или дампы памяти. Любой процесс внутри контейнера с тем же UID имеет к ним доступ. Секреты могут быть «запечены» в историю образа при использовании инструкции `ENV` в `Dockerfile`.
- **Рекомендация:** Используйте суффикс `_FILE` (например, `DB_PASSWORD_FILE=/run/secrets/db_pass`), чтобы приложение читало секрет из файла, а не из переменной. Это стандарт де-факто для Docker-ориентированных приложений.

### 2. Секреты Docker Compose

Механизм для одиночных хостов (Compose V2). Секреты монтируются как файлы во временную файловую систему в оперативной памяти (**tmpfs**) по пути `/run/secrets/`.

- **Преимущества:** Секреты не сохраняются на диске контейнера и не видны в переменных окружения. Это рекомендуемый метод для локальной разработки и одиночных серверов.

### 3. Секреты Docker Swarm

Встроенное решение для кластеров. Секреты шифруются при хранении в базе данных **Raft** и передаются только тем узлам, на которых запущены соответствующие сервисы. Подробнее см. в **[Секреты и конфигурации в Swarm](../../Docker_swarm/swarm_secrets_configs.md)**.

### 4. Секреты сборки BuildKit

Механизм для безопасной передачи секретов (например, SSH-ключей или токенов NPM) во время сборки образа без их сохранения в истории слоев. В современных версиях Docker BuildKit включен по умолчанию.

## Практические сценарии

### 1. Использование Docker Compose Secrets

Рекомендуемый метод для локальной разработки и небольших инсталляций. Если злоумышленник получит доступ к выводу `docker inspect`, он увидит только путь к файлу, но не его содержимое.

**Пример `docker-compose.yml`:**

```yaml
services:
  app:
    image: my-app:1.1
    secrets:
      - db_password
    environment:
      - DB_PASSWORD_FILE=/run/secrets/db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt # Файл на хосте (должен быть в .gitignore!)
```

### 2. Секреты на этапе сборки (BuildKit)

Исключает попадание токенов доступа в слои образа.

**Пример `Dockerfile`:**

```dockerfile
#syntax=docker/dockerfile:1
FROM python:3.12-slim

# Монтируем секрет только на время выполнения команды RUN
RUN --mount=type=secret,id=pypi_token \
    PIP_INDEX_URL=$(cat /run/secrets/pypi_token) pip install my-private-pkg
```

**Запуск сборки:**
```bash
docker build --secret id=pypi_token,src=token.txt -t my-app .
```

### 3. Шифрование секретов в Git через SOPS

Для GitOps-пайплайнов, где секреты должны храниться рядом с кодом, но в зашифрованном виде.

**Рабочий процесс:**
1. Шифрование файла на стороне разработчика (используя KMS или PGP):
   ```bash
   sops --encrypt --age age1... secrets.yaml > secrets.enc.yaml
   ```
2. Расшифровка в CI/CD или на хосте перед запуском Docker Compose:
   ```bash
   sops -d secrets.enc.yaml > ./secrets/db_password.txt
   docker compose up -d
   ```

### 4. Современные менеджеры для разработки (1Password CLI)

Использование `op run` для динамической инъекции секретов без хранения их на диске:
```bash
op run -- docker compose up -d
```
