# Управление секретами в Docker

## Определения

**Управление секретами** — практики безопасного хранения и использования конфиденциальных данных (пароли, токены, ключи API) в контейнеризированных приложениях.

**Основной принцип:** Секреты хранятся отдельно от кода и образов. Внедрение секретов в образ или Git создает риски утечки.

## Базовые концепции

### 1. Переменные окружения (`.env`)

Передача секретов через переменные окружения.

- **Преимущества:** Простота для локальной разработки.
- **Недостатки:** Небезопасно для production — секреты видны в `docker inspect`, могут попасть в логи.

### 2. Docker Compose Secrets

Встроенный механизм Compose (без Swarm). Секреты монтируются как файлы в `tmpfs` (`/run/secrets/<name>`).

- **Преимущества:** Безопасность для одиночных хостов.
- **Недостатки:** Только один хост, нет кластерной поддержки.

### 3. Docker Swarm Secrets

Встроенный механизм Swarm. Секреты шифруются в Raft-базе, монтируются в `tmpfs`.

- **Преимущества:** Шифрование при хранении и передаче.
- **Недостатки:** Привязка к Swarm.

### 4. BuildKit Secrets

Передача секретов в `Dockerfile` при сборке без сохранения в слоях.

- **Преимущества:** Доступ к приватным репозиториям (`npm`, `pip`, `apt`).
- **Недостатки:** Только для этапа сборки.

### 5. Внешние менеджеры (Vault)

**[HashiCorp Vault](../../Vault/overview.md)** и аналоги для централизованного управления.

- **Преимущества:** Политики доступа, аудит, ротация, динамическая генерация.
- **Недостатки:** Требует инфраструктуры.

## Практические сценарии

### 1. Переменные окружения: Небезопасный паттерн

Несмотря на удобство, этот метод несет риски:

- **Видимость в `docker inspect`:** Любой с доступом к Docker API может прочитать секреты.
- **Утечка в логи:** Ошибки в приложении могут привести к выводу переменных окружения в логи.
- **Сохранение в слоях:** Неосторожное использование `ARG` и `ENV` в `Dockerfile` может "запечь" секрет в историю образа.

> **Правило:** Если использование `.env` файлов неизбежно, **никогда не коммитьте их в Git**. Используйте `.gitignore` и предоставляйте команде `.env.example` в качестве шаблона.

### 2. Docker Compose Secrets: Безопасность без Swarm

В отличие от `Docker Swarm Secrets`, данный механизм работает с обычной командой `docker compose up` и не требует кластера, что делает его идеальным решением для локальной разработки и одиночных хостов.

#### Проблема: Пароли в открытом виде

Классический анти-паттерн — хранение секретов прямо в `Dockerfile` или в `docker-compose.yml` в виде переменных окружения.

```yaml
# Неправильно!
services:
  postgres:
    image: postgres:16
    environment:
      - POSTGRES_PASSWORD=supersecret123
```

Это приводит к утечке секретов в Git, логах CI/CD, образах Docker и выводе `docker inspect`.

#### Решение: Директива `secrets` в Docker Compose

Директива `secrets` создает изолированное хранилище для чувствительных данных. Docker монтирует эти секреты в контейнеры как файлы во временную файловую систему в оперативной памяти (`tmpfs` по пути `/run/secrets/<secret_name>`).

**Пример `docker-compose.yml`:**

```yaml
version: '3.8'

services:
  web:
    image: nginx
    secrets:
      - db_password                      # 1. Подключение секрета к сервису
      - source: api_key                  # 2. Секрет из внешнего источника
        target: /run/secrets/api_token   # 3. Монтирование с другим именем

secrets:
  db_password:
    file: ./secrets/db_password.txt  # Секрет загружается из файла
  api_key:
    external: true                   # Секрет управляется вне этого Compose файла
```

#### Способы определения секретов

- **Из файла (`file`):** Содержимое файла становится секретом.

    ```yaml
    secrets:
      mysql_root_password:
        file: ./mysql_root_password.txt
    ```

- **Из переменной окружения хоста (`environment`):**

    ```yaml
    secrets:
      database_url:
        environment: DATABASE_CONNECTION_STRING
    ```

- **Внешний секрет (`external`):** Используется, когда секрет уже создан внешними инструментами (например, через `docker secret create` в Swarm).

#### Преимущества и недостатки

**Преимущества:**

- **Изоляция:** Секреты не попадают в Git, логи CI/CD, Docker Registry и `docker inspect`.
- **Соответствие стандартам:** Отвечает требованиям политик безопасности, запрещающим хранение паролей в переменных окружения.
- **Гибкость окружений:** Позволяет использовать разные секреты для `dev/staging/prod` без изменения основного `compose.yml`, например, через [override-файлы](../Docker_compose/docker_compose_advanced_topics.md).
- **Безопасность:** Секреты хранятся только в оперативной памяти контейнера и недоступны через файловую систему хоста.

**Недостатки:**

- Нет автоматической ротации.
- Нет централизованного аудита.
- Нет прямой интеграции с enterprise-системами, такими как HashiCorp Vault или AWS Secrets Manager.

Для простых окружений Docker Compose `secrets` — это идеальный баланс простоты и безопасности. Для сложных production-систем рекомендуется использовать специализированные решения.

### 3. Docker Swarm Secrets (в режиме Swarm)

Секреты хранятся в зашифрованной Raft-базе данных Swarm и монтируются в контейнер как файлы в `/run/secrets/`.

1. **Создание секрета:**

    ```bash
    echo "mypassword123" | docker secret create db_password -
    ```

2. **Использование в сервисе (`docker-compose.yml`):**

    ```yaml
    version: "3.7"
    services:
      my-app:
        image: my-app:latest
        secrets:
          - db_password
    secrets:
      db_password:
        external: true
    ```

3. **Доступ в контейнере:** Приложение должно быть готово читать секрет из файла (например, `/run/secrets/db_password`).

### 4. Секреты на этапе сборки (BuildKit)

1. **Активация BuildKit (если не включен по умолчанию):**

    ```bash
    export DOCKER_BUILDKIT=1
    ```

2. **`Dockerfile` с использованием `--mount=type=secret`:**

    ```dockerfile
    #syntax=docker/dockerfile:1
    FROM alpine
    
    # RUN-инструкция получает доступ к секрету, но он не сохраняется в слое
    RUN --mount=type=secret,id=mysecret \
        apk add --no-cache \
        --repository "https://user:$(cat /run/secrets/mysecret)@my.private.repo/apk" \
        my-private-package
    
    # Вне этой команды секрет недоступен
    RUN ls /run/secrets # Директория будет пуста
    ```

3. **Запуск сборки с передачей секрета:**

    ```bash
    # my_secret.txt содержит токен
    docker build --secret id=mysecret,src=my_secret.txt .
    ```
