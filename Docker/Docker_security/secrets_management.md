# Безопасная работа с секретами в Docker

Главный принцип безопасной работы с секретами (пароли, токены, ключи API) — **хранить их отдельно от кода и артефактов сборки**. Внедрение секретов непосредственно в Docker-образ или коммит `.env` файлов в репозиторий создают серьезные риски утечки.

### Подходы к хранению секретов

| Метод | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Переменные окружения (`.env`)** | Самый простой способ, секреты передаются через переменные окружения. | Простота, легкость в использовании для разработки. | **Небезопасно для production.** Секреты видны через `docker inspect`, могут утечь в логи. |
| **Docker Secrets (Swarm)** | Встроенный механизм Docker Swarm. Секреты шифруются и монтируются в контейнер как файлы в `/run/secrets/`. | Высокая безопасность, интеграция со Swarm, шифрование "в покое" и "в движении". | **Привязка к Docker Swarm.** |
| **BuildKit Secrets** | Передача секретов на этапе сборки образа (`docker build`) без сохранения в слоях. | Идеально для доступа к приватным репозиториям (`npm`, `pip`, `apt`) во время сборки. | **Только для этапа сборки.** Не решает проблему хранения секретов во время выполнения. |
| **Внешние менеджеры (Vault и др.)** | Централизованные хранилища, такие как **HashiCorp Vault**, предоставляют API для управления секретами. | Гибкие политики доступа, ротация, аудит, динамические секреты. Лучшее решение для сложных систем. | Требуют развертывания и поддержки отдельной инфраструктуры. |

---

### 1. Переменные окружения: классическая ошибка

-   **Они видны в `docker inspect`:** Любой, у кого есть доступ к Docker API, может прочитать секреты.
-   **Риск утечки в логи:** Если приложение по ошибке выведет переменные окружения, секреты окажутся в логах.
-   **Сохраняются в истории:** При неосторожном использовании `ARG` и `ENV` в `Dockerfile` секреты могут остаться в истории слоев образа.

> Если использование `.env` файлов неизбежно, **никогда не коммитьте их в Git**. Используйте `.gitignore` и предоставьте разработчикам `.env.example` в качестве шаблона.

### 2. Docker Secrets (в режиме Swarm)

Это "фирменный" и безопасный способ управления секретами, если вы используете Docker Swarm. Секреты хранятся в зашифрованном виде в Raft-базе данных Swarm и монтируются в контейнер как обычные файлы.

1.  **Создание секрета:**
    ```bash
    # Секрет создается из файла или stdin
    echo "mypassword123" | docker secret create db_password - 
    ```
2.  **Использование в сервисе (`docker-compose.yml`):**
    ```yaml
    version: "3.7"
    services:
      my-app:
        image: my-app:latest
        secrets:
          - db_password

    secrets:
      db_password:
        external: true # Указывает, что секрет создан заранее
    ```
3.  **Доступ в контейнере:** Секрет будет доступен внутри контейнера как файл `/run/secrets/db_password`. Ваше приложение должно быть готово читать секреты из файлов, а не из переменных окружения.

### 3. Секреты на этапе сборки (BuildKit)

Этот метод позволяет безопасно использовать секреты во время выполнения `RUN` инструкций в `Dockerfile`, не сохраняя их в итоговом образе. Это полезно для доступа к приватным репозиториям пакетов или скачивания артефактов.

1.  **Включите BuildKit:**
    ```bash
    export DOCKER_BUILDKIT=1
    ```

2.  **Создайте файл с секретом:**
    ```bash
    echo "my_super_secret_token" > my_secret.txt
    ```

3.  **Используйте `--mount=type=secret` в `Dockerfile`:**
    ```dockerfile
    #syntax=docker/dockerfile:1
    FROM alpine
    
    # Этот RUN имеет доступ к секрету, смонтированному в /run/secrets/mysecret
    RUN --mount=type=secret,id=mysecret \
        apk add --no-cache \
        --repository "https://user:$(cat /run/secrets/mysecret)@my.private.repo/apk" \
        my-private-package
    
    # Вне этой команды секрет недоступен и в слое образа не сохраняется.
    RUN ls /run/secrets # Эта команда покажет, что директория пуста
    ```

4.  **Запустите сборку, передав секрет:**
    ```bash
    docker build --secret id=mysecret,src=my_secret.txt .
    ```

### 4. Внешние менеджеры секретов (HashiCorp Vault)

Для сложных систем с множеством микросервисов и окружений использование внешнего менеджера, такого как **HashiCorp Vault**, является лучшей практикой. Vault обеспечивает централизованное хранение, строгие политики доступа, аудит и динамическую генерацию секретов "на лету".

Интеграция с Docker обычно происходит по одной из двух схем:
1.  **Init-контейнер:** Специальный контейнер, который запускается перед основным, аутентифицируется в Vault, забирает нужные секреты и передает их основному приложению (например, через общий `emptyDir` том в Kubernetes).
2.  **Vault Agent:** Агент, работающий как sidecar-контейнер, который аутентифицируется в Vault, получает секреты и сохраняет их в файл, доступный приложению. Агент также может автоматически обновлять секреты при их ротации в Vault.

> Подробная информация об интеграции Vault с Docker находится в документе **[Интеграция с Docker и Docker Compose](../../Vault/guides/vault_docker_integration.md)**.
