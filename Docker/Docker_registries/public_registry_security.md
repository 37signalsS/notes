# Безопасность при работе с публичными реестрами

## Определения

* **Угрозы публичных реестров**: Использование публичных репозиториев, таких как Docker Hub, создает риски для [безопасности цепочки поставок ПО](../../Security/Supply_Chain_Security/overview.md). Основные угрозы включают:
  * **Подмена образа (Image spoofing)**: Злоумышленник перезаписывает легитимный изменяемый тег (например, `:latest`).
  * **Typo-squatting**: Публикация вредоносных образов с именами, похожими на официальные (например, `postgresl` вместо `postgresql`).
  * **Уязвимые зависимости**: Использование базовых образов с известными уязвимостями (CVE).
* **Примитивы безопасности**:
  * **Дайджест (Digest)**: Криптографический идентификатор `sha256`, гарантирующий неизменность содержимого образа.
  * **Подпись образа (Image Signature)**: Криптографическое подтверждение издателя и целостности. Детали см. в [подписании и верификации образов](../Docker_security/image_signature_and_verification.md).
  * **SBOM (Software Bill of Materials)**: Подробный перечень всех компонентов ПО внутри образа. Детали см. в [Docker SBOM](../Docker_security/docker_sbom.md).

## Основные концепции

Для минимизации рисков при работе с публичными реестрами применяется многоуровневая защита.

| Риск | Меры контроля |
| :--- | :--- |
| **Подмена/изменение образа** | Использование дайджеста вместо тега (`pull by digest`), проверка подписей. |
| **Typo-squatting** | Белые списки (allow-lists) доверенных реестров и пространств имен. |
| **Уязвимости в слоях** | Обязательное [сканирование уязвимостей](../Docker_security/vulnerability_scanning.md) в CI/CD. |
| **Секреты внутри образа** | Сканирование на наличие секретов, использование многостадийных сборок. |
| **Непрозрачность состава** | Генерация и анализ SBOM, аттестации происхождения (provenance). |

Ключевой стратегией является использование **локального прокси-кэша** (например, [Harbor](./Harbor/overview.md) или Nexus). Он кэширует образы из публичных реестров, позволяя применять централизованные политики безопасности:

* Запрет на использование изменяемых тегов.
* Автоматическое сканирование на уязвимости.
* Блокировка образов с критическими CVE.

## Практические сценарии

### 1. Фиксация по дайджесту вместо тега

```bash
# 1. Получить образ по тегу
docker pull nginx:1.25

# 2. Узнать его неизменяемый дайджест
docker inspect --format='{{index .RepoDigests 0}}' nginx:1.25
# Вывод: nginx@sha256:2a1d...c9e

# 3. Использовать дайджест в манифестах
# image: nginx@sha256:2a1d...c9e
```

### 2. Проверка подписи образа (Cosign)

```bash
# Проверить подпись образа с помощью публичного ключа
cosign verify --key cosign.pub ghcr.io/org/app:1.4.3

# Проверить прикрепленные аттестации (например, SBOM)
cosign verify-attestation --type=spdx --key cosign.pub ghcr.io/org/app:1.4.3
```

### 3. Сканирование на уязвимости (Trivy)

```bash
# Запретить запуск образа при наличии критических уязвимостей
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 ghcr.io/org/app@sha256:2a1d...c9e
```

## Дополнительная информация

### Политики в CI/CD и на платформе

* **CI/CD**: Внедряйте шаги для сканирования, проверки подписей и анализа SBOM на ранних этапах. Сборка должна прерываться при нарушении политик.
* **Admission Control (Kubernetes)**: Используйте контроллеры (например, Kyverno, OPA Gatekeeper) для блокировки развертывания неподписанных образов или образов с критическими уязвимостями прямо на входе в кластер.
* **Аудит**: Логируйте все операции `pull` и `push`. Регулярно проводите аудит используемых образов и их источников.
* **Immutable Tags**: Настройте ваш приватный реестр так, чтобы запретить перезапись уже существующих тегов.
