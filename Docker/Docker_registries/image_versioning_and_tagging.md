# Версионирование и тегирование Docker-образов

## Определения

* **Тэг (Tag)**: Удобочитаемая метка (например, `:1.2.5`, `:latest`), прикрепленная к образу. Тэги являются изменяемыми указателями (mutable pointers) на конкретный манифест образа. Полное имя образа включает опциональный адрес реестра, пространство имен и тэг: `registry.example.com/team/service:2.3.5-alpine`.
* **Дайджест (Digest)**: Неизменяемый идентификатор контента образа, представленный в виде хеша `sha256`. Дайджест однозначно определяет конкретную версию манифеста и всех его слоев, гарантируя, что вы используете именно тот образ, который был задуман. Пример: `service@sha256:3a1f...`.

## Основные концепции

Грамотная стратегия тегирования и версионирования обеспечивает предсказуемость, воспроизводимость сборок и безопасность развертываний.

### Категории тэгов

| Категория | Пример | Назначение | Риски |
| :--- | :--- | :--- | :--- |
| **Полная версия (SemVer)** | `1.2.5` | Однозначная ссылка на конкретный релиз. | Ошибочная перезапись недопустима. |
| **Плавающие алиасы** | `1.2`, `1` | Удобный «канал» для получения последней минорной/мажорной версии. | Изменение тега меняет бинарники у потребителей. |
| **Каналы/предрелизы** | `1.3.0-rc.1`, `beta` | Тестирование, ранний доступ. | Не для производственного использования. |
| **Варианты базового образа** | `alpine`, `slim` | Разные компромиссы (размер/совместимость). | Различия в системных библиотеках и инструментах. |
| **`latest`** | `latest` | Простота для интерактивного использования и примеров. | Непредсказуем в production, может привести к сбоям. |

### Фиксация по дайджесту (Digest Pinning)

Использование дайджеста (`имя_образа@sha256:...`) — лучшая практика для производственных сред. Это гарантирует, что вы всегда используете один и тот же, неизменяемый артефакт, даже если тэг будет случайно или намеренно перезаписан.

### Многоархитектурные образы

Один и тот же тэг (например, `ubuntu:22.04`) может указывать на *манифест-лист*, который содержит ссылки на образы для разных архитектур (`linux/amd64`, `linux/arm64`). Docker клиент автоматически выберет и скачает подходящий образ для текущей платформы.

## Практические сценарии

### 1. Сборка и публикация релиза с алиасами

```bash
# 1. Собрать образ с полным номером версии
docker build -t registry.example.com/team/service:2.3.5 .

# 2. Создать плавающие теги
docker tag registry.example.com/team/service:2.3.5 registry.example.com/team/service:2.3
docker tag registry.example.com/team/service:2.3.5 registry.example.com/team/service:2

# 3. Опубликовать все теги
docker push registry.example.com/team/service:2.3.5
docker push registry.example.com/team/service:2.3
docker push registry.example.com/team/service:2
```

### 2. Фиксация на дайджест для развертывания

```bash
# 1. Получить дайджест после pull или push образа
docker pull registry.example.com/team/service:2.3.5
docker inspect --format='{{index .RepoDigests 0}}' registry.example.com/team/service:2.3.5
# Вывод: registry.example.com/team/service@sha256:3a1f...

# 2. Использовать дайджест в манифесте Kubernetes
```

```yaml
# kubernetes-deployment.yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
      - name: service
        image: registry.example.com/team/service@sha256:3a1f...
        imagePullPolicy: IfNotPresent
```

## Дополнительная информация

### Рекомендации и лучшие практики

* **Публикуйте набор тегов:** На каждый релиз публикуйте как минимум полный SemVer (`1.2.5`) и плавающий минорный тэг (`1.2`).
* **Не перезаписывайте стабильные теги:** Тэг версии (например, `1.2.5`) должен быть неизменяемым после публикации.
* **Используйте дайджесты в production:** Для всех критичных развертываний используйте фиксацию по дайджесту.
* **Автоматизируйте версионирование:** Используйте CI/CD для автоматического тегирования на основе коммитов Git или тегов релиза.
* **Ведите `CHANGELOG`:** Синхронизируйте его с версиями и тегами артефактов.
