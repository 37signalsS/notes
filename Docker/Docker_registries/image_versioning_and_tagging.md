# Версионирование и тегирование Docker-образов

## Определения

* **Тэг (Tag)**: Изменяемая (mutable) текстовая метка, указывающая на конкретный манифест образа. Полное имя включает адрес реестра, пространство имен, имя репозитория и тэг: `registry.example.com/project/service:1.2.5`.
* **Дайджест (Digest)**: Уникальный, неизменяемый (immutable) идентификатор контента образа, вычисляемый как хеш-сумма **SHA (Secure Hash Algorithm)** от манифеста. Гарантирует идентичность артефакта вне зависимости от состояния тегов. Пример: `service@sha256:e3b0c442...`.
* **Манифест (Manifest)**: JSON-файл, описывающий состав образа: слои, конфигурацию и метаданные. Соответствует спецификациям **OCI (Open Container Initiative)**.
* **Манифест-лист (Manifest List)**: Структура, объединяющая манифесты для разных платформ под одним тегом, обеспечивая многоархитектурность.

## Основные концепции

### Категории тэгов

Для эффективного управления жизненным циклом в **CI/CD (Continuous Integration / Continuous Deployment)** используются разные классы тегов:

| Категория | Примеры | Назначение |
| :--- | :--- | :--- |
| **Релизные (SemVer)** | `1.2.5`, `v2.0.0` | Фиксация конкретного выпуска. Должны быть неизменяемыми. |
| **Плавающие (Aliases)** | `1.2`, `1`, `latest` | Автоматическое получение последнего минорного или мажорного обновления. |
| **Временные (Branch/Commit)** | `feat-auth`, `sha-a1b2c3d` | Тестирование веток и привязка к коммиту в Git. |
| **Варианты (Variants)** | `3.12-alpine`, `slim` | Разные базовые образы (размер, наличие инструментов). |

Общие принципы версионирования (SemVer, CalVer) описаны в разделе **[Управление артефактами](../../CI-CD/artifact_management.md)**.

### Фиксация по дайджесту (Digest Pinning)

Использование тега `latest` или плавающих тегов в производственных средах опасно, так как образ может измениться без уведомления. Лучшая практика для production — указание дайджеста. Это исключает атаки подмены и гарантирует воспроизводимость.

### Многоархитектурность (Multi-arch)

Один тег может указывать на разные бинарные сборки для `amd64`, `arm64`, `s390x`. При выполнении `docker pull` демон автоматически запрашивает слой, соответствующий архитектуре хоста.

## Практические сценарии

### 1. Многоуровневое тегирование в CI/CD

При публикации релиза хорошим тоном считается создание набора тегов для удобства потребителей.

```bash
# Тегирование образа для версии 2.3.5
IMAGE="my-reg.com/app"
VER="2.3.5"

docker build -t $IMAGE:$VER .

# Создание алиасов
docker tag $IMAGE:$VER $IMAGE:2.3
docker tag $IMAGE:$VER $IMAGE:2
docker tag $IMAGE:$VER $IMAGE:latest

# Отправка всех тегов
docker push $IMAGE --all-tags
```

### 2. Сборка многоархитектурного образа через Buildx

Использование **Buildx** позволяет собрать образ сразу для нескольких платформ и объединить их в манифест-лист.

```bash
# Создание и использование нового строителя (builder)
docker buildx create --use

# Сборка и отправка образа для x86 и ARM
docker buildx build --platform linux/amd64,linux/arm64 \
  -t registry.example.com/team/service:1.2.5 --push .
```

### 3. Фиксация на дайджест в Kubernetes

Для обеспечения максимальной стабильности в манифестах **Kubernetes (K8s)** следует использовать дайджест.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  template:
    spec:
      containers:
      - name: main
        # Фиксация конкретной сборки по дайджесту
        image: registry.example.com/app@sha256:723c347...
```

## Дополнительная информация

### Рекомендации

* **Иммутабельность:** Никогда не перезаписывайте теги конкретных версий (`1.2.5`). Если в релизе ошибка — выпустите `1.2.6`.
* **Чистка реестра:** Настраивайте политики очистки (**Retention Policies**) для удаления старых веток и коммит-тегов, сохраняя релизные версии.
* **Автоматизация:** Используйте инструменты вроде `semantic-release` для автоматического вычисления следующей версии на основе **Conventional Commits**.
* **Безопасность:** Проверяйте происхождение образа перед деплоем. Подробнее см. **[Подписание и верификация образов](../Docker_security/image_signature_and_verification.md)**.
