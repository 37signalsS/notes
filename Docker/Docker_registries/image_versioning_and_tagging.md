# Структура тэгов образов: организация версий

Тэг в имени образа — это метка после двоеточия, указывающая на конкретный вариант артефакта. Полное имя может включать реестр и пространство имен:
`registry.example.com/team/service:2.3.5-alpine`

Тэги — это удобные, но изменяемые указатели на манифесты. Непосредственный идентификатор содержимого — **digest** (sha256), он неизменяем. Грамотная схема тэгов обеспечивает предсказуемые релизы, воспроизводимость и удобство для пользователей.

## Основные категории тэгов

| Категория | Пример | Назначение | Риски |
| :--- | :--- | :--- | :--- |
| Полная версия (SemVer) | `2.3.5` | Однозначная ссылка на релиз | Ошибочная перезапись недопустима |
| Плавающие алиасы | `2.3`, `2` | Удобный «канал» последней минорной/мажорной | Переезд тега меняет бинарники у потребителей |
| Каналы/предрелизы | `2.4.0-rc.1`, `beta` | Тестирование, ранний доступ | Нельзя использовать в проде |
| Варианты базового образа | `alpine`, `slim`, `distroless` | Разные компромиссы размера/совместимости | Отличия по инструментам и libc |
| Среда/ветка | `dev`, `staging` | Внутренние окружения | Публичное распространение вводит в заблуждение |
| `latest` | `latest` | Простота для интерактива и примеров | Непредсказуем в продакшене |

**Digest-пиновка**: `имя@sha256:...` — стабильная фиксация содержимого, рекомендуема для продакшена и инфраструктурного кода.

## Рекомендации по схеме версионирования

-   Публикуйте набор тегов на каждый релиз:
    -   Полный SemVer: `2.3.5`
    -   Плавающие алиасы: `2.3` и `2`
    -   Вариант образа: `2.3.5-alpine` и соответствующие алиасы
-   Не перезаписывайте тэги версии (`2.3.5`) после публикации.
-   Допускайте обновление плавающих алиасов (`2.3` → `2.3.6`) строго в рамках политики совместимости.
-   В примерах для документации используйте понятные тэги, в манифестах развёртывания — digest.
-   Добавляйте техническую метку сборки: commit SHA или дату, но публикуйте и «человеческие» алиасы.
    -   Пример шаблона: `2.3.5-20241008-abc1234`

## Многоархитектурные образы и варианты

Один и тот же тэг может указывать на манифест‑лист для нескольких платформ (linux/amd64, linux/arm64). Пользователь получает подходящий артефакт автоматически. Для вариативности окружения применяйте суффиксы:

-   `service:2.3.5-alpine`
-   `service:2.3.5-slim`
-   `service:2.3.5-fips`

## Примеры операций

**Сборка и публикация релиза с алиасами:**

```bash
docker build -t registry.example.com/team/service:2.3.5 .
docker tag registry.example.com/team/service:2.3.5 registry.example.com/team/service:2.3
docker tag registry.example.com/team/service:2.3.5 registry.example.com/team/service:2
docker push registry.example.com/team/service:2.3.5
docker push registry.example.com/team/service:2.3
docker push registry.example.com/team/service:2
```

**Создание варианта на базе Alpine:**

```bash
docker build -f Dockerfile.alpine -t registry.example.com/team/service:2.3.5-alpine .
docker push registry.example.com/team/service:2.3.5-alpine
```

**Фиксация на digest и потребление в манифесте:**

```bash
docker pull registry.example.com/team/service:2.3.5
docker inspect --format='{{index .RepoDigests 0}}' registry.example.com/team/service:2.3.5
# registry.example.com/team/service@sha256:3a1f...
```

**Фрагмент для развертывания:**

```yaml
containers:
- name: service
  image: registry.example.com/team/service@sha256:3a1f...
  imagePullPolicy: IfNotPresent
```

## Политики именования

-   Явно фиксируйте несовместимые изменения с увеличением major.
-   Используйте префиксы для окружений только во внутренних реестрах.
-   Ведите changelog, синхронизируя его с тэгами и артефактами.
-   Устанавливайте в реестре запрет на перезапись стабильных тэгов и включайте подписи артефактов.
