# Обзор Docker Compose

**Актуально для:** Docker Compose v5+ (Compose Specification)

## Определения

**Docker Compose** — инструмент для определения и запуска многоконтейнерных Docker-приложений на основе декларативного YAML-файла. Он позволяет описывать всю инфраструктуру приложения (сервисы, сети, тома, переменные окружения, секреты и конфигурации) как единый стек.

**Ключевая идея:** вместо ручного управления каждым контейнером через `docker run`, вы определяете состояние всего приложения в файле `compose.yml` и управляете его жизненным циклом единой командой `docker compose`.

**Compose Specification (Compose v5+):** Современный Docker Compose (начиная с 2025 года — версия 5) полностью базируется на открытом стандарте Compose Specification. Это превратило его из простой утилиты в мощную платформу для оркестрации локальных сред и одноузловых продакшен-стеков с унифицированным Go SDK для автоматизации.

> **Примечание:** Устаревшая Python-утилита `docker-compose` (с дефисом) официально признана EOL (End of Life) в 2025 году и более не поддерживается. Актуальным инструментом является плагин к Docker CLI — `docker compose`.

## Основные концепции

### Проблемы ручного управления контейнерами

При использовании отдельных команд `docker run` для каждого компонента мультиконтейнерного приложения возникают критические сложности:

- **Трудозатратность:** каждый сервис (frontend, backend, база данных) требует отдельной длинной команды с уникальными флагами
- **Сложность зависимостей:** ручной запуск требует соблюдения строгой последовательности (база данных должна быть готова раньше приложения)
- **Сетевая изоляция:** необходимость вручную создавать сети и связывать контейнеры через псевдонимы DNS
- **Фрагментация конфигурации:** настройки портов, томов и переменных окружения разбросаны по разным скриптам или истории команд
- **Отсутствие модульности:** сложно переиспользовать части конфигурации между разными проектами или окружениями (Dev/Prod)

### Ключевые механизмы работы

Современный Docker Compose решает проблемы ручного управления через следующие механизмы:

- **Декларативность:** файл `compose.yml` является "чертежом" системы. Docker гарантирует, что текущее состояние контейнеров соответствует описанному.
- **Сетевая автоматизация:** для каждого проекта Compose по умолчанию создает изолированную сеть типа `bridge`. Сервисы могут обращаться друг к другу по именам, указанным в YAML, которые автоматически преобразуются в IP через встроенный DNS-сервер Docker.
- **Управление данными:** Compose упрощает работу с томами (`volumes`). Вы можете определить именованные тома для персистентности данных (базы данных) или использовать `bind mounts` для проброса кода из хост-системы.
- **Иерархия конфигураций:** поддержка `.env` файлов и интерполяция переменных окружения позволяют динамически изменять настройки без правки основного файла. Приоритет переменных: OS Environment > `.env` файл > значения в `compose.yml`.
- **Умное управление зависимостями:** расширенная директива `depends_on` позволяет ждать не просто старта контейнера, а его полной готовности (`service_healthy`) или успешного завершения (`service_completed_successfully`).
- **Модульность (Include):** возможность импортировать конфигурации из других файлов или удаленных OCI-репозиториев (Compose v2.20+), что позволяет разделять большие проекты на части.
- **Режим разработки (Watch):** автоматическая синхронизация изменений кода между хостом и контейнером в реальном времени без необходимости пересборки образа.
- **Идемпотентность:** команда `docker compose up` пересоздает только те компоненты, чья конфигурация или образы изменились.

### Архитектура и принципы работы

Docker Compose функционирует как слой абстракции над Docker Engine, обеспечивая декларативное управление жизненным циклом многоконтейнерных приложений:

1. **Парсинг и валидация:** Compose читает `compose.yml`, проверяет синтаксис и разрешает все переменные окружения. На этом этапе можно использовать `docker compose config` для предварительной проверки конфигурации без реального запуска.
2. **Разрешение зависимостей:** На основе директив `depends_on` и `healthcheck` Compose строит граф порядка запуска сервисов. В отличие от ранних версий, современный Compose может ждать не только старта контейнера, но и его полной готовности к обслуживанию запросов.
3. **Создание ресурсов:** Compose автоматически создает сети, тома и секреты, определенные в файле. Все именованные ресурсы получают префикс проекта для избежания конфликтов между разными стеками на одном хосте.
4. **Запуск сервисов:** Контейнеры запускаются в порядке, определенном графом зависимостей. Compose применяет настройки перезапуска (`restart`), лимиты ресурсов (`deploy.resources`) и политики безопасности.
5. **Мониторинг состояния:** После запуска Compose continuously отслеживает состояние контейнеров через драйвер событий Docker. При изменении конфигурации или падении сервиса Compose может автоматически пересоздать только затронутые компоненты.

### Терминология

В экосистеме Docker Compose используются следующие базовые понятия:

| Термин | Описание |
| :--- | :--- |
| **Сервис (Service)** | Абстракция над контейнером. Определяет образ, конфигурацию запуска и ресурсы. |
| **Проект (Project)** | Группа связанных сервисов, управляемых как единое целое. Имя проекта по умолчанию берется из имени директории или флага `-p`. |
| **Сеть (Network)** | Изолированный сегмент связи. По умолчанию создается одна сеть `default` для всех сервисов проекта. |
| **Том (Volume)** | Хранилище данных. Может быть именованным (управляется Docker) или примонтированным (`bind mount`). |
| **Стек (Stack)** | Совокупность запущенных ресурсов (сервисов, сетей, томов), определенных в одном проекте. |
| **compose.yml** | Основной файл конфигурации. Поле `version` в современных версиях является необязательным и устаревшим. |
| **Фрагмент (Include)** | Часть конфигурации, импортируемая для переиспользования кода. |

## Практические сценарии

### Пример: современный стек приложения

Пример файла `compose.yml`, демонстрирующий лучшие практики (лимиты ресурсов, проверки здоровья и сетевую изоляцию):

```yaml
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      retries: 5
    networks:
      - backend_net
    deploy:
      resources:
        limits:
          cpus: '0.5'
          memory: 512M

  app:
    build:
      context: ./app
      dockerfile: Dockerfile
    depends_on:
      db:
        condition: service_healthy
    develop:
      watch:
        - action: sync
          path: ./app/src
          target: /app/src
    networks:
      - frontend_net
      - backend_net

networks:
  frontend_net:
  backend_net:
    internal: true

secrets:
  db_password:
    file: ./secrets/db_pass.txt
```

### Многоконфигурационная среда (Dev/Staging/Prod)

Для управления разными окружениями из единого набора файлов используется механизм наложения конфигураций:

```bash
# Development: базовый файл + автоматический override
docker compose up -d

# Staging: базовый файл + явный override
docker compose -f compose.yml -f compose.staging.yml up -d

# Production: базовый файл + профиль + явный override
docker compose --profile monitoring -f compose.yml -f compose.prod.yml up -d
```

Настройки из последующего файла имеют приоритет. Этот паттерн позволяет держать общую конфигурацию в `compose.yml`, а окружение-специфичные параметры — в отдельных файлах.

### Валидация и проверка конфигурации

Перед применением конфигурации в production-среде рекомендуется выполнять валидацию:

```bash
# Проверка синтаксиса и вывод итоговой конфигурации
docker compose config

# Проверка конкретного сервиса
docker compose config db

# Валидация без реального запуска (Compose v5+)
docker compose up --dry-run
```

### Командный интерфейс (CLI)

Основные команды для управления жизненным циклом проекта:

- `docker compose up -d` — запуск всех сервисов в фоновом режиме.
- `docker compose up --wait` — запуск с ожиданием перехода всех сервисов в состояние `healthy`.
- `docker compose watch` — запуск в режиме автоматической синхронизации кода (только для разработки).
- `docker compose down` — остановка и удаление контейнеров, сетей и образов проекта.
- `docker compose down -v` — дополнительно удаляет именованные тома (опасно для персистентных данных).
- `docker compose ps` — отображение статуса всех контейнеров в текущем проекте.
- `docker compose ps --format json` — вывод в формате JSON для автоматизации.
- `docker compose config` — валидация синтаксиса и вывод итоговой конфигурации.
- `docker compose logs -f` — просмотр логов всех сервисов в реальном времени.
- `docker compose logs --tail 100` — последние 100 строк логов без streaming.
- `docker compose exec db psql -U user` — выполнение команды в запущенном контейнере.
- `docker compose run --rm web npm test` — запуск одноразовой задачи с автоматическим удалением контейнера.
- `docker compose stats` — мониторинг потребления ресурсов (CPU, RAM, сеть) сервисами в реальном времени.
- `docker compose top` — вывод запущенных процессов внутри контейнеров сервиса.

## Устранение неполадок

### Типичные ошибки запуска

| Ошибка | Симптом | Решение |
| :--- | :--- | :--- |
| **Port already allocated** | `Bind for 0.0.0.0:8080 failed: port is already allocated` | Освободить порт (`lsof -i :8080`), изменить маппинг в `ports` или удалить старый контейнер (`docker compose down`). Детали и диагностика — **[Конфликты портов](../Docker_troubleshooting/port_conflicts.md)**. |
| **Контейнер падает сразу** | `Exited (1)` или цикл перезапусков | Проверить логи (`docker compose logs <service>`), убедиться в корректности `CMD`/`ENTRYPOINT` в Dockerfile, проверить переменные окружения. |
| **Сервис не готов** | `connection refused` к базе данных | Добавить `depends_on` с `condition: service_healthy`, настроить `healthcheck` в зависимом сервисе. |
| **Permission denied** | `EACCES: permission denied, open '/data/...'` | Исправить владельца тома на хосте (`chown`), указать `user` в сервисе или использовать именованные тома вместо bind mounts. |
| **Нет места на диске** | `no space left on device` | Очистить неиспользуемые образы (`docker image prune`), контейнеры (`docker container prune`), тома (`docker volume prune`). |
| **Ошибка YAML-синтаксиса** | `mapping values are not allowed in this context` | Проверить отступы (только пробелы, без табов), убедиться в корректности структуры файла (`docker compose config`). |
| **Сеть не найдена** | `network ... declared as external, but could not be found` | Создать сеть вручную (`docker network create`) или убрать флаг `external: true`, если сеть должна создаваться Compose. |
| **Недостаточно памяти** | `OOMKilled` | Увеличить лимит памяти в `deploy.resources.limits.memory`, проверить потребление через `docker compose stats`. |
| **Переменная не подставилась** | `${VAR}` остается в конфигурации как есть | Убедиться, что переменная задана в окружении или `.env` файле; экранировать `$` как `$$` для литеральных значений. |

### Диагностический процесс

При возникновении проблем следуйте последовательности:

1. **Проверить статус:** `docker compose ps` — найти сервис в состоянии `exited` или `restarting`.
2. **Изучить логи:** `docker compose logs <service>` — искать ключевые слова `ERROR`, `failed`, `cannot`.
3. **Валидировать конфигурацию:** `docker compose config` — убедиться, что YAML корректен и все переменные подставились.
4. **Инспектировать контейнер:** `docker inspect <container>` — детальный анализ состояния, mounts, environment.
5. **Проверить ресурсы:** `docker compose stats` — убедиться, что сервису выделено достаточно CPU и RAM.
6. **Очистить окружение:** `docker compose down` — исключить проблемы, вызванные устаревшими контейнерами или сетями.

## Рекомендации

### Безопасность

- **Запускайте контейнеры от не-root пользователя:** Используйте директиву `user: "1000:1000"` для минимизации последствий компрометации контейнера.
- **Храните секреты вне репозитория:** Используйте секции `secrets` с файлами, исключенными из Git, или внешние системы управления секретами. Никогда не хардкодите пароли в `compose.yml`.
- **Ограничивайте возможности контейнеров:** Используйте `cap_drop: [ALL]` и `cap_add` только для необходимых возможностей, `read_only: true` для статичных сервисов.
- **Используйте `tmpfs` для чувствительных данных:** Временные файлы с секретами должны существовать только в оперативной памяти.
- **Пингуйте версии образов:** Избегайте тега `latest` в production; используйте конкретные версии или SHA-хэши для воспроизводимости.

### Надежность и отказоустойчивость

- **Определяйте `healthcheck` для каждого критичного сервиса:** Без проверки здоровья Compose не может корректно управлять порядком запуска зависимостей. Устанавливайте `start_period` для сервисов с долгой инициализацией (базы данных).
- **Устанавливайте политики перезапуска:** `restart: unless-stopped` для большинства сервисов, `restart: "no"` для одноразовых задач (миграции).
- **Задавайте лимиты ресурсов:** `deploy.resources.limits` предотвращают деградацию хоста при утечке памяти в одном из контейнеров.
- **Используйте именованные тома для персистентности:** Bind mounts уязвимы к правам доступа и переносу между хостами; именованные тома управляются Docker и переносят данные между контейнерами.
- **Сегментируйте сети:** Разделяйте frontend, backend и данные на разные сети. Используйте `internal: true` для изоляции внутренних сервисов от внешнего доступа.

### Производительность и наблюдаемость

- **Включите централизованное логирование:** Настройте драйверы логирования (`json-file`, `fluentd`, `loki`) с ротацией для предотвращения заполнения диска.
- **Мониторьте потребление ресурсов:** Используйте `docker compose stats` в продакшене или интегрируйте метрики в Prometheus через cAdvisor.
- **Используйте профили для условного запуска:** Выносите мониторинг, отладку и вспомогательные сервисы в отдельные профили, чтобы не запускать их по умолчанию.
- **Валидируйте конфигурацию в CI:** Добавьте `docker compose config` и `docker compose build --no-cache` в pipeline для раннего обнаружения проблем.

### Поддержка и сопровождение

- **Версионируйте `compose.yml`:** Храните конфигурацию в Git с четкими коммитами на каждый изменения стека.
- **Используйте `.env.example`:** Документируйте требуемые переменные окружения без хранения реальных значений.
- **Регулярно обновляйте образы:** Настраивайте политику пересборки (`--pull`) и проверяйте уязвимости (`trivy`, `docker scout`).
- **Тестируйте откат:** Убедитесь, что `docker compose down` и повторный `up` восстанавливают работоспособность; для критичных сервисов предусмотрите скрипты бэкапа томов.
