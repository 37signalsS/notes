# Продвинутые возможности Docker Compose

**Актуально для:** Docker Compose v5+ (Compose Specification)

## Определения

**Продвинутые возможности Docker Compose** — набор технологий для управления сложными инфраструктурными стеками: модульность через `include`, временные окружения через профили, безопасная передача секретов на этапе сборки и декомпозиция конфигурации без дублирования.

**Extension Fields (`x-`)** — ключи YAML с префиксом `x-`, игнорируемые парсером Compose, но используемые как переиспользуемые шаблоны конфигурации через YAML-якоря. Позволяют централизованно определять метки, переменные окружения и ресурсы.

**Build Secrets** — механизм безопасной передачи конфиденциальных данных (токены, ключи) в процесс сборки образа без сохранения их в конечных слоях образа.

**Профиль** — логическая группа сервисов, запускаемых только при явном указании `--profile` в CLI. Используется для разделения окружений разработки, тестирования и эксплуатации внутри одного файла.

**Длинный синтаксис (Long Syntax)** — декларативный формат задания томов, сетей и секретов с явным указанием драйверов, режимов монтирования и прав доступа. Противопоставляется сокращенному строковому синтаксису.

**Override File** — файл `compose.override.yml`, автоматически загружаемый Compose вместе с основным `compose.yml`. Используется для локальных переопределений, не попадающих в контроль версий.

## Архитектура и принципы работы

### Жизненный цикл расширенной конфигурации

1. **Загрузка модулей:** Compose загружает основной файл и все модули из `include` (локальные пути или OCI-артефакты).
2. **Слияние конфигураций:** Все загруженные файлы объединяются по правилам deep merge. Подробнее о правилах слияния см. [**Compose extends, include и правила слияния**](./docker_compose_extends_include.md).
3. **Разрешение переменных:** Интерполяция `${VAR}` из окружения, `.env` файлов и `env_file`. Приоритет: OS Environment > `--env-file` > `env_file` > `.env` > значения в `compose.yml`.
4. **Фильтрация по профилям:** Compose определяет активные профили из CLI и исключает сервисы без совпадения.
5. **Создание ресурсов:** Сети, тома, секреты создаются через Docker API с учетом ограничений из `deploy.resources`.
6. **Запуск сервисов:** Контейнеры запускаются с учетом `depends_on`, `healthcheck` и политик перезапуска.

### Слои конфигурации

```
compose.yml (базовый стек)
├── include/ (модули)
│   ├── infrastructure/database.yml
│   └── infrastructure/monitoring.yml
├── x-common-* (переиспользуемые шаблоны)
├── profiles: ["debug", "admin", "tools"]
├── secrets: (передача конфиденциальных данных)
└── services: (основная логика)
    ├── build: secrets (безопасная сборка)
    └── develop: watch (горячая синхронизация)
```

## Базовые концепции

### Интерполяция переменных

Docker Compose позволяет динамически изменять значения в `compose.yml` на основе переменных окружения.

- **Синтаксис и условия:**
  - `${VAR}` — простая подстановка значения.
  - `${VAR:-default}` — подставить `default`, если переменная пуста или не задана.
  - `${VAR-default}` — подставить `default`, только если переменная не задана (пустое значение допускается).
  - `${VAR:?error}` — завершить выполнение с ошибкой `error`, если переменная не задана.

- **Приоритет источников (от высокого к низкому):**
  1. Переменные системного окружения (Shell).
  2. Переменные, заданные через флаг `--env-file` в CLI.
  3. Файлы, указанные в директиве `env_file` сервиса.
  4. Файл `.env` в текущей директории.
  5. Значения по умолчанию в самом YAML.

- **Практическое применение:**
  - Переключение окружений: `APP_ENV=${APP_ENV:-production}`.
  - Условная загрузка секретов: `API_KEY=${API_KEY:?error: API_KEY required}`.
  - Динамические порты в dev: `PORT=${PORT:-8080}`.

### Модульность через Include

Директива **`include`** (Compose v2.20+) — основной инструмент декомпозиции в современной инфраструктуре.

- **Преимущества:**
  - Полная изоляция ресурсов (сети и тома импортируемого файла не конфликтуют с текущими).
  - Поддержка относительных путей для вложенных структур.
- **Импорт из OCI-реестров:** (Compose v2.20+) Compose позволяет импортировать конфигурации, упакованные как OCI-артефакты.
  ```yaml
  include:
    - oci: my-registry.com/my-project/common-config:v1.2.0
  ```

> **Примечание:** Детальный синтаксис `include`, `extends` и правила слияния описаны в [**Compose extends, include и правила слияния**](./docker_compose_extends_include.md). В этом файле рассматриваются операционные паттерны их использования.

### Расширенные поля (Extension Fields)

Расширенные поля начинаются с префикса `x-` и позволяют определять фрагменты конфигурации, которые игнорируются парсером Docker Compose, но могут использоваться через YAML-якоря.

- **Назначение:** централизованное определение общих настроек (логирование, метки, ресурсы).
- **Пример:**
  ```yaml
  x-common-labels: &labels
    project: "my-app"
    team: "devops"

  services:
    web:
      image: nginx
      labels: *labels
  ```

> **Примечание:** Полное описание синтаксиса и ограничений `x-` полей см. в [**Compose extends, include и правила слияния**](./docker_compose_extends_include.md).

### Профили (Profiles)

Профили позволяют объединять сервисы в логические группы, которые не запускаются автоматически при выполнении `docker compose up`.

- **Назначение:** разделение сервисов для разработки, тестирования, инструментов мониторинга или отладки внутри одного файла.
- **Пример использования:**
  ```yaml
  services:
    app:
      image: app:latest
    
    admin-panel:
      image: admin:latest
      profiles: ["admin", "tools"]
  ```
- **Запуск:** `docker compose --profile admin up -d`. Сервисы без профиля запускаются всегда.

> **Примечание:** Примеры использования профилей для разделения окружений см. в [**Примеры конфигураций**](./docker_compose_file_example.md).

### Секреты на этапе сборки (Build Secrets)

Для безопасной передачи конфиденциальных данных (API-ключи, токены) в процессе сборки образа без сохранения их в слоях:

```yaml
services:
  app:
    build:
      context: .
      secrets:
        - npm_token

secrets:
  npm_token:
    file: ~/.npmrc
```

- **Безопасность:** секрет передается через tmpfs и не попадает в финальный образ.
- **Удаление после сборки:** Compose автоматически удаляет секрет после завершения `build`.

### Длинный синтаксис (Long Syntax)

Для точного управления ресурсами (томами, сетями, секретами) рекомендуется использовать "длинный синтаксис" вместо сокращенных строк.

- **Секреты (Secrets):** управление путем монтирования.
  ```yaml
  services:
    db:
      secrets:
        - source: db_password
          target: /run/secrets/pg_pass
          # uid/gid/mode в Compose не применяются для file:-секретов
          # (bind-mount не меняет права); работают только в Swarm
  ```
- **Тома (Volumes):** настройка драйверов и режимов монтирования (`consistency`, `bind.propagation`).

> **Примечание:** Полный справочник длинного синтаксиса см. в [**Справочник по директивам**](./docker_compose_directives.md).

### Работа с внешними ресурсами (External)

Для взаимодействия с инфраструктурой, созданной вне текущего проекта (например, общей сетью прокси), используются внешние ресурсы.

```yaml
services:
  web:
    networks:
      - global_proxy_net

networks:
  global_proxy_net:
    external: true
    name: common-ingress-network
```

## Практические сценарии

### Сценарий 1: Мульти-файловая конфигурация через Include

Разделение инфраструктуры на модули для командной разработки.

**Структура проекта:**
```
project/
├── compose.yml              # Основной стек
├── infrastructure/
│   ├── database.yml          # PostgreSQL + миграции
│   └── monitoring.yml        # Prometheus + Grafana
└── .env.ci                  # Переменные для CI
```

**`compose.yml`:**
```yaml
include:
  - ./infrastructure/database.yml
  - ./infrastructure/monitoring.yml

services:
  web:
    image: myapp:${TAG:-latest}
    ports:
      - "${PORT:-8080}:8080"
    environment:
      - DATABASE_URL=postgres://${DB_USER}:${DB_PASS}@db:5432/${DB_NAME}
    depends_on:
      db:
        condition: service_healthy
    profiles:
      - debug
```

**Запуск с модулями:**
```bash
docker compose -f compose.yml -f compose.prod.yml up -d
```

**Ожидаемый результат:** Разделение ответственности между командами. Изменения в `database.yml` не затрагивают `web` сервис.

### Сценарий 2: Аварийный откат через переключение профилей

Использование profiles для быстрого переключения между старым и новым стеком без изменения DNS.

```yaml
services:
  web-v2:
    image: myapp:v2.0.0
    ports:
      - "8080:8080"
    profiles:
      - new-version

  web-v1:
    image: myapp:v1.0.0
    ports:
      - "8080:8080"
    profiles:
      - old-version
```

**Переключение:**
```bash
# Развертывание v2
docker compose --profile new-version up -d
# Откат к v1
docker compose --profile old-version up -d
```

**Ожидаемый результат:** Откат выполняется одной командой без изменения DNS-записей или балансировщика.

### Сценарий 3: Безопасная сборка с передачей секретов

Использование `build.secrets` для сборки образа с доступом к приватному реестру.

```yaml
services:
  app:
    build:
      context: .
      secrets:
        - npmrc
    secrets:
      - npmrc

secrets:
  npmrc:
    file: ~/.npmrc
```

**Сборка:**
```bash
docker compose build app
```

**Ожидаемый результат:** Секретный файл доступен только во время сборки и не попадает в итоговый образ.

### Сценарий 4: Диагностика через профиль debug

Запуск вспомогательных инструментов для отладки production-стека.

```yaml
services:
  db:
    image: postgres:16
    volumes:
      - db_data:/var/lib/postgresql/data
    environment:
      - POSTGRES_PASSWORD=${DB_PASSWORD}
    profiles:
      - debug

  db-debug:
    image: nicolaka/netshoot
    network_mode: service:db
    entrypoint: sleep infinity
    profiles:
      - debug
```

**Подключение к базе через debug-контейнер:**
```bash
docker compose --profile debug up -d db-debug
docker compose exec db-debug psql -h db -U postgres
```

**Ожидаемый результат:** Вспомогательный контейнер `db-debug` запускается только при необходимости и не присутствует в production-стеке.

### Сценарий 5: Валидация перед переключением трафика

Проверка работоспособности нового стека через smoke-тесты.

```bash
#!/bin/bash
set -e

# Запуск нового стека в фоне
docker compose -p staging-new -f compose.yml -f compose.prod.yml up -d

# Ожидание готовности
docker compose -p staging-new ps --format json | jq -r 'select(.Health == "healthy") | .Service'

# Smoke-тест
docker compose -p staging-new run --rm test-runner npm test

# Переключение трафика (например, через nginx upstream)
# ...

# Остановка старого стека
docker compose -p staging-old down -v
```

**Ожидаемый результат:** Новый стек проверен на работоспособность до переключения трафика.

## Операции и команды

### Команды для работы с профилями и модулями

| Команда | Назначение | Примечание |
| :--- | :--- | :--- |
| `docker compose --profile <name> up -d` | Запуск сервисов с указанным профилем | Основная команда для запуска dev/debug окружений |
| `docker compose --profile <name> down -v` | Остановка и удаление томов | Используется для очистки после тестирования |
| `docker compose --profile admin up -d` | Запуск сервисов с несколькими профилями | Можно указать несколько `--profile` |
| `docker compose config` | Валидация итоговой конфигурации | Проверка после изменения `include` или переменных |
| `docker compose alpha generate` | Генерация compose-файла из запущенных контейнеров | Подробнее в [**Справочник команд CLI**](./docker_compose_cli_commands.md) |
| `docker compose alpha publish` | Публикация стека как OCI-артефакта | Подробнее в [**Справочник команд CLI**](./docker_compose_cli_commands.md) |

### Переменные окружения

| Переменная | Описание | Пример |
| :--- | :--- | :--- |
| `COMPOSE_PROJECT_NAME` | Имя проекта для изоляции | `staging-app` |
| `COMPOSE_FILE` | Путь к compose-файлам | `compose.yml:compose.prod.yml` |
| `COMPOSE_OVERRIDE_FILE` | Файл переопределений | `compose.override.yml` |
| `COMPOSE_PROFILES` | Активные профили (через запятую) | `debug,admin` |

### Паттерны очистки ресурсов

| Ресурс | Команда | Описание |
| :--- | :--- | :--- |
| Контейнеры | `docker compose down` | Остановка и удаление контейнеров проекта |
| Тома | `docker compose down -v` | Дополнительно удаляет анонимные тома |
| Сети | Автоматически | Compose удаляет сети проекта при `down` |
| Изображения | `docker compose down --rmi local` | Удаление локально собранных образов |
| Орфаны | `docker compose down --remove-orphans` | Удаление контейнеров от предыдущих запусков |

## Устранение неполадок

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| **`include` игнорируется** | Файл не найден или путь указан относительно неправильной директории | Пути в `include` разрешаются относительно включаемого файла, а не относительно корня проекта |
| **Неверные значения переменных** | Приоритет источников нарушен | Проверьте порядок: OS Environment > `--env-file` > `env_file` > `.env` > YAML |
| **`profile` не запускается** | Сервис не найден или профиль не указан | Проверьте имя профиля в `profiles:` сервиса и укажите `--profile <name>` |
| **Конфликт имен ресурсов** | Два `include` импортируют ресурс с одинаковым именем | Используйте уникальные имена или изолируйте в отдельные проекты |
| **Секрет попадает в образ** | `target` не указан или секрет смонтирован в рабочую директорию | Укажите `target: /run/secrets/<name>` и убедитесь, что `WORKDIR` не совпадает с путем секрета |
| **`x-` поля игнорируются** | Ошибка в синтаксисе YAML-якорей | Проверьте, что якорь `&name` определен до использования `*name` |
| **`alpha generate` не включает healthcheck** | Ограничение генератора | Всегда проверяйте сгенерированный файл перед использованием |
| **Профили не работают в CI** | Переменная `COMPOSE_PROFILES` не задана | Задайте `COMPOSE_PROFILES=debug,admin` в окружении CI-раннера |

## Рекомендации

### Модульность

- Используйте `include` вместо `extends` для импорта целых инфраструктурных блоков.
- Держите каждый модуль в отдельном файле с четкой ответственностью (БД, мониторинг, кеш).
- Избегайте циклических зависимостей между модулями.

### Безопасность

- Никогда не передавайте секреты через переменные окружения в production.
- Используйте `build.secrets` только для временных данных (токены сборки).
- Устанавливайте минимальные права на файлы секретов на хосте (`chmod 600`); `mode` в compose-файле в Compose не применяется — только в Swarm.
- Внешние ресурсы (`external: true`) должны иметь четкий владелец и документацию.

### Надежность

- Всегда задавайте `healthcheck` для критичных сервисов.
- Используйте `depends_on` с `condition: service_healthy` вместо внешних скриптов ожидания.
- Ресурсные ограничения (`deploy.resources`) предотвращают эффekt домино при утечке памяти.
- Для production используйте `restart: unless-stopped` или политики оркестратора.

### Производительность

- Используйте `x-` поля для переиспользования конфигурации вместо копирования.
- Избегайте глубокой вложенности `include` (>3 уровня) для сохранения читаемости.
- В CI используйте `COMPOSE_PROFILES` для запуска только необходимых сервисов.
