# Справочник по директивам Docker Compose

## Определения

**Директивы Docker Compose** — это ключевые инструкции в файле `compose.yml`, которые определяют, как Docker должен управлять запуском, конфигурацией и взаимодействием многоконтейнерных приложений. Они делятся на директивы верхнего уровня (определяющие проект) и директивы уровня сервиса.

## Базовые концепции

### Директивы верхнего уровня

Эти директивы находятся в корне `compose.yml` и определяют глобальные настройки проекта. В современных версиях (Compose v5+) поле **`version`** является необязательным и официально признано устаревшим.

- **`name`**: Задает имя проекта, которое используется как префикс для контейнеров, сетей и томов.
- **`include`**: (Compose v2.20+) Позволяет импортировать другие compose-файлы. Это основной способ реализации модульности, заменяющий сложные конструкции с `extends`.
- **`models`**: (Compose v5+) Определяет веса AI-моделей (LLM и др.) как зависимости проекта. Позволяет Docker автоматически загружать и подключать модели к контейнерам.
- **`networks`**: Определяет именованные сети для всего проекта.
- **`volumes`**: Определяет именованные тома. Подробнее в [**Docker Volumes**](../../Docker/Docker_fs/docker_volumes.md).
- **`secrets`**: Определяет внешние файлы секретов.
- **`configs`**: Определяет неконфиденциальные конфигурационные файлы.

### Директивы уровня сервиса (`services`)

#### 1. Сборка и образы
- **`image` vs. `build`**:
  - `image`: Указывает готовый образ из registry.
  - `build`: Параметры сборки образа. Поддерживает `secrets` на этапе сборки.
- **`platform`**: Указывает целевую архитектуру (например, `linux/amd64`, `linux/arm64`). Важно при работе на Apple Silicon или в смешанных кластерах.
- **`pull_policy`**: Определяет логику скачивания образа.
  - `always`: Всегда проверять наличие новой версии в registry.
  - `if_not_present`: Скачивать только если образа нет локально.
  - `build`: Всегда пересобирать локально.

#### 2. Сетевые настройки
- **`ports`**: Пробрасывает порты в формате `IP:ХОСТ_ПОРТ:КОНТЕЙНЕР_ПОРТ`. Допускается сокращенный формат `ХОСТ_ПОРТ:КОНТЕЙНЕР_ПОРТ`.
- **`expose`**: Открывает порты только для связи между контейнерами (без проброса на хост).
- **`networks`**: Подключает сервис к одной или нескольким сетям, определенным на верхнем уровне.
- **`extra_hosts`**: Добавление записей в `/etc/hosts` внутри контейнера.
- **`hostname`** и **`domainname`**: Установка сетевого имени внутри контейнера.
- **`dns`**, **`dns_search`**: Настройка пользовательских DNS-серверов и поисковых доменов.

#### 3. Управление данными и секретами
- **`volumes`**: Монтирует тома или bind-mount'ы в контейнер. `[ИМЯ_ТОМА_ИЛИ_ПУТЬ_НА_ХОСТЕ]:[ПУТЬ_В_КОНТЕЙНЕРЕ]`.
- **`tmpfs`**: Монтирует временную файловую систему в оперативную память.
- **`secrets`**: Позволяет безопасно передавать в сервис секреты, определенные на верхнем уровне. Секреты монтируются как файлы в `/run/secrets/`.
  - > **Подробнее:** [**Безопасное управление секретами в Docker**](../Docker_security/secrets_management.md)
- **`configs`**: Передает неконфиденциальные конфигурационные файлы (аналогично секретам).

#### 4. Окружение и зависимости
- **`environment` и `env_file`**:
  - `environment`: Задает переменные окружения прямо в YAML. Не используйте для секретов.
  - `env_file`: Загружает переменные из файла.
- **`depends_on`**: Определяет зависимости между сервисами. Современный подход — использование расширенной формы с `condition`.
  - **Параметры условия (`condition`):**
    - `service_started`: Запуск после старта контейнера.
    - `service_healthy`: **(Рекомендуется)** Запуск только после прохождения `healthcheck`.
    - `service_completed_successfully`: Ожидание успешного завершения (код 0).
  - **`required: false`**: (Compose v5+) Позволяет сервису запуститься, даже если зависимость недоступна.
  - **`restart: true`**: (Compose v5+) Автоматически перезапускает данный сервис при перезапуске зависимого сервиса.
  - > **Исторический контекст:** В ранних версиях формата v3 поддержка `condition` временно отсутствовала. Сейчас использование внешних скриптов ожидания (`wait-for-it.sh`) считается антипаттерном. Подробнее в [**сравнении версий**](docker_compose_versions_comparison.md).
- **`profiles`**: Позволяет группировать сервисы для выборочного запуска. Сервисы с профилем запускаются только при явном указании профиля в CLI (`--profile`).

#### 5. Жизненный цикл и запуск
- **`command` и `entrypoint`**: Переопределяют `CMD` и `ENTRYPOINT` из `Dockerfile` образа.
  - Подробнее: [Инструкции Dockerfile: ENTRYPOINT vs CMD](../Dockerfile/Instructions/practical_scenarios.md).
- **`restart`**: Определяет политику перезапуска контейнера.
  - `no` — не перезапускать (по умолчанию).
  - `on-failure` — перезапуск только при ненулевом коде выхода (для одноразовых задач).
  - `always` — всегда, включая ручную остановку.
  - `unless-stopped` — перезапуск при любом падении, кроме ручной остановки. **Рекомендуется для production.**
- **`healthcheck`**: Позволяет Docker проверять работоспособность приложения. Крайне важен для `depends_on.condition: service_healthy`.
  - `start_period` — время после старта, в течение которого неудачные проверки не считаются ошибкой (приложению нужно время на инициализацию).
  - Если в образе нет `curl` (Alpine), используйте `wget`:
    ```yaml
    healthcheck:
      test: ["CMD-SHELL", "wget -q --spider http://localhost:8080/health || exit 1"]
    ```
- **`init`**: Если `true`, Docker запускает внутри контейнера процесс `init` (обычно `tini`), который корректно пробрасывает сигналы (SIGTERM) и "усыновляет" процессы-сироты.
- **`stop_signal`**: Сигнал для остановки контейнера (по умолчанию `SIGTERM`).

#### 6. Ресурсы и оборудование
- **`deploy.resources`**: Ограничения ресурсов контейнера (память, CPU).
  - `limits` — жёсткий потолок (при превышении памяти — OOMKilled).
  - `reservations` — гарантированный минимум.
  ```yaml
  deploy:
    resources:
      limits:
        memory: 512M
        cpus: "1.0"
      reservations:
        memory: 256M
  ```
- **`gpus`**: (Compose v5+) Упрощенный синтаксис для проброса GPU (NVIDIA, AMD). Заменяет громоздкие конфигурации в `deploy.resources`.
- **`shm_size`**: Размер разделяемой памяти (`/dev/shm`). Важно для баз данных (PostgreSQL) и браузеров.
- **`ulimits`**: Настройка лимитов ресурсов ядра (например, `nofile` для количества открытых файлов).
- **`sysctls`**: Настройка параметров ядра Linux внутри контейнера.

#### 7. Безопасность и мониторинг
- **`user`**: Запускает процесс от имени указанного пользователя (`user:group`).
- **`logging`**: Настройка драйвера и ротации логов. Без ротации JSON-файлы растут бесконтрольно.
  ```yaml
  logging:
    driver: json-file
    options:
      max-size: "10m"
      max-file: "3"
  ```
- **`privileged`**: Запуск с полными правами root на хосте.
- **`cap_add`**, **`cap_drop`**: Добавление или удаление специфических Linux-способностей (capabilities).
- **`security_opt`**: Настройки SELinux, AppArmor или seccomp.
- **`read_only`**: Делает корневую файловую систему контейнера доступной только для чтения.

#### 8. Разработка и метаданные
- **`develop`**: (Compose v2.22+) Секция для настройки инструментов разработки.
  - **`watch`**: Описывает правила автоматической синхронизации файлов между хостом и контейнером.
    - **`initial_sync`**: (Compose v5+) Если `true`, выполняет полную синхронизацию файлов при запуске.
    ```yaml
    develop:
      watch:
        - action: sync
          path: ./src
          target: /app/src
    ```
- **`labels`**: Метаданные для контейнеров (используются внешними инструментами, например Traefik).
- **`working_dir`**: Переопределение рабочей директории внутри контейнера.

## Практические сценарии

### Пример: Веб-приложение с PostgreSQL (Современный подход)

Пример файла `compose.yml`, демонстрирующий правильное использование директив, включая `depends_on` с `condition`. См. также расширенный [пример compose.yml](./docker_compose_file_example.md).

```yaml
name: my-web-app

services:
  database:
    image: postgres:16
    restart: unless-stopped
    env_file: ./.env
    secrets:
      - db_password
    environment:
      # Образ postgres умеет читать пароль из файла
      - POSTGRES_PASSWORD_FILE=/run/secrets/db_password
    volumes:
      - db_data:/var/lib/postgresql/data
    networks:
      - app_net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
      interval: 10s
      timeout: 5s
      retries: 5

  web_app:
    build: .
    restart: on-failure:3
    ports:
      - "8000:8000"
    env_file: ./.env
    networks:
      - app_net
    # Гарантирует запуск ТОЛЬКО после полной готовности БД.
    # Скрипты wait-for-it.sh больше не нужны.
    depends_on:
      database:
        condition: service_healthy
    command: "python manage.py runserver 0.0.0.0:8000"

volumes:
  db_data:

networks:
  app_net:

secrets:
  db_password:
    file: ./db_password.txt
```

**Пояснение:** Сервис `web_app` не запустит свою `command` до тех пор, пока `healthcheck` сервиса `database` не завершится успешно. Это надежный и декларативный способ управления зависимостями.

### Пример: Самовосстановление с Autoheal

Интеграция внешнего монитора для автоматического перезапуска зависших контейнеров (статус `unhealthy`). Подробнее см. **[Autoheal в Docker](../Docker_troubleshooting/docker_autoheal.md)**.

```yaml
services:
  web:
    image: nginx:alpine
    restart: unless-stopped
    labels:
      - "autoheal=true"
    healthcheck:
      test: ["CMD-SHELL", "wget -q --spider http://localhost/ || exit 1"]
      interval: 30s
      retries: 3

  autoheal:
    image: willfarrell/autoheal:latest
    restart: always
    environment:
      - AUTOHEAL_CONTAINER_LABEL=autoheal
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
```
