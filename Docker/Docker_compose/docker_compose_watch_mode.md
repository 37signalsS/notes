# Режим watch в Docker Compose

## Определения

Режим `watch` в Docker Compose — это функция, предназначенная для **ускорения процесса разработки**. Он позволяет автоматически отслеживать изменения в файлах локальной файловой системы и синхронизировать их с контейнером, а также перезапускать или пересобирать контейнеры при изменении исходного кода или конфигурации. Это избавляет разработчика от необходимости вручную пересобирать образ и перезапускать контейнер при каждом изменении кода.

Режим `watch` включается в конфигурации `docker-compose.yml` в секции `develop` для каждого сервиса.

## Базовые концепции

Настройка режима `watch` осуществляется с помощью списка правил в секции `develop.watch`. Каждое правило определяет, за каким путем следить и какое действие выполнять.

```yaml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    develop:
      watch:
        # Синхронизировать изменения в директории ./src с контейнером
        - path: ./src
          action: sync
          target: /app/src
        # Перезапускать контейнер при изменении Dockerfile
        - path: Dockerfile
          action: rebuild
```

* **`path`**: Обязательный параметр. Указывает путь к файлу или директории в локальной файловой системе хоста, за которыми необходимо наблюдать. Путь может быть относительным (относительно файла `compose.yml`) или абсолютным.
* **`action`**: Обязательный параметр. Определяет действие, которое Docker Compose выполнит при обнаружении изменений по указанному `path`. Доступные действия:
  * `sync`: Синхронизировать изменения файлов в реальном времени между хостом и контейнером. Это самый быстрый вариант, не требующий перезапуска контейнера или пересборки образа.
  * `rebuild`: Пересобрать образ сервиса при изменении файлов, указанных в `path`. Используется, когда изменения требуют обновления образа (например, изменение `Dockerfile` или `requirements.txt`).
  * `recreate`: Пересоздать контейнер сервиса при изменении файлов. Это действие полезно, когда изменения не влияют на образ, но требуют перезапуска контейнера (например, изменение конфигурационного файла приложения).
* **`target`**: Необязательный параметр. Используется только с действием `sync`. Указывает путь внутри контейнера, куда будут синхронизированы изменения с хоста. Если не указан, используется значение `path` относительно корня сборки/контекста сервиса.

## Практические сценарии

```yaml
services:
  app:
    build: .
    ports:
      - "5000:5000"
    develop:
      watch:
        # Синхронизировать исходный код приложения из ./app на хосте в /app в контейнере.
        # Изменения сразу же отображаются в работающем приложении без перезапуска.
        - path: ./app
          action: sync
          target: /app
        # При изменении файла зависимостей (requirements.txt) пересобрать образ.
        # Это необходимо, так как установка новых зависимостей меняет образ.
        - path: requirements.txt
          action: rebuild
        # При изменении файла конфигурации web-сервера (например, nginx.conf для приложения)
        # пересоздать контейнер, чтобы применить новые настройки.
        - path: ./config/nginx.conf
          action: recreate
          target: /etc/nginx/nginx.conf # Можно указать target для recreate, если путь на хосте отличается от пути в контейнере
```

## Дополнительная информация

### Преимущества

1. **Ускорение разработки**: Изменения в коде сразу же отражаются в работающем контейнере, минимизируя цикл обратной связи.
2. **Удобство отладки**: Нет необходимости вручную перезапускать контейнеры или запускать команды сборки после каждого изменения.
3. **Автоматизация**: Автоматическая пересборка или перезапуск при изменении конфигурационных файлов, от которых зависит образ или запуск сервиса.

### Ограничения и рекомендации

1. **Назначение только для разработки**: Режим `watch` категорически не предназначен для использования в production-средах. Его функционал не оптимизирован для производительности и безопасности боевых развертываний.
2. **Влияние на производительность**: Частая синхронизация больших объемов файлов или частые пересборки/пересоздания контейнеров могут негативно сказаться на производительности разработки, особенно на медленных дисковых системах.
3. **Конфликты файлов**: Следует быть осторожным при одновременной работе с файлами как в хостовой системе, так и внутри контейнера, чтобы избежать непредвиденных конфликтов синхронизации.
4. **Файловые системы**: Работа `watch` может отличаться на различных файловых системах и операционных системах хоста.
