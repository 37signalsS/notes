# Режим watch в Docker Compose

## Определения

Режим `watch` в Docker Compose — это функция, предназначенная для **ускорения процесса разработки**. Он позволяет автоматически отслеживать изменения в файлах локальной файловой системы и синхронизировать их с контейнером, а также перезапускать или пересобирать контейнеры при изменении исходного кода или конфигурации. Это избавляет разработчика от необходимости вручную пересобирать образ и перезапускать контейнер при каждом изменении кода.

Режим `watch` включается в конфигурации `compose.yml` в секции `develop` для каждого сервиса.

## Базовые концепции

Настройка режима `watch` осуществляется с помощью списка правил в секции `develop.watch`. Каждое правило определяет, за каким путем следить и какое действие выполнять.

```yaml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    develop:
      watch:
        # Синхронизировать изменения в директории ./src с контейнером
        - path: ./src
          action: sync
          target: /app/src
        # Пересобрать образ и перезапустить контейнер при изменении Dockerfile
        - path: Dockerfile
          action: rebuild
```

* **`path`**: Путь к файлу/директории на хосте для отслеживания.
* **`action`**: Действие при обнаружении изменений:
  * `sync`: Синхронизировать файлы. Самый быстрый вариант, аналог bind mount.
  * `rebuild`: Пересобрать образ сервиса. Используется, когда меняются файлы, влияющие на образ (`Dockerfile`, `requirements.txt`, `package.json`).
  * `recreate`: Пересоздать контейнер. Полезно для применения новых настроек, не требующих пересборки образа (например, изменение переменных окружения или entrypoint скрипта).
* **`target`**: Путь внутри контейнера для `sync`.

## Практические сценарии

### Сценарий 1: Single-service приложение

```yaml
services:
  app:
    build: .
    ports:
      - "5000:5000"
    develop:
      watch:
        # 1. Для исходного кода, который может быть подхвачен "на лету"
        #    (например, в Python с Flask/Django debug mode или JS с HMR),
        #    используем 'sync'.
        - path: ./app
          action: sync
          target: /app

        # 2. При изменении файла зависимостей, нужно пересобрать образ,
        #    чтобы установить их. Используем 'rebuild'.
        - path: requirements.txt
          action: rebuild

        # 3. При изменении конфигурации nginx, достаточно пересоздать
        #    контейнер, чтобы он подхватил новый файл.
        - path: ./config/nginx.conf
          action: recreate
          target: /etc/nginx/nginx.conf
```

### Сценарий 2: Multi-service приложение (TODO App)

Типичное окружение для разработки полнофункционального веб-приложения:

| Сервис | Назначение |
| :--- | :--- |
| **React Frontend** | Фронтенд на React с dev server |
| **Node.js Backend** | Бэкенд с REST API (CRUD операции) |
| **MySQL** | База данных для хранения данных |
| **phpMyAdmin** | Веб-интерфейс управления базой |
| **Traefik Proxy** | Роутинг запросов: `/api` → backend, `/` → frontend |

```yaml
services:
  frontend:
    build:
      context: ./client
      target: development
    develop:
      watch:
        - path: ./client/src
          action: sync
          target: /app/src
        - path: ./client/package.json
          action: rebuild

  backend:
    build:
      context: ./backend
      target: development
    develop:
      watch:
        - path: ./backend/src
          action: sync
          target: /app/src
        - path: ./backend/package.json
          action: rebuild

  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: todo_db
    volumes:
      - mysql_data:/var/lib/mysql

  phpmyadmin:
    image: phpmyadmin/phpmyadmin
    environment:
      PMA_HOST: mysql

  proxy:
    image: traefik:v2.10
    ports:
      - "80:80"
    volumes:
      - ./traefik.yml:/etc/traefik/traefik.yml

volumes:
  mysql_data:
```

**Запуск:**

```bash
docker compose watch
```

**Как работает:**

1. Docker Compose автоматически создаёт сеть для изоляции сервисов
2. Volume `mysql_data` обеспечивает персистентность данных базы при перезапусках
3. Traefik роутит запросы: `localhost/api/*` → backend, `localhost/*` → frontend
4. При изменении файлов в `./client/src` или `./backend/src` изменения синхронизируются в контейнеры в реальном времени
5. При изменении `package.json` происходит автоматическая пересборка образа (кэширование предыдущих слоёв ускоряет процесс)
6. Доступ к приложению — через единый порт 80 (благодаря Traefik), вместо указания отдельных портов для каждого сервиса

**Преимущества такого подхода:**

* Не нужно устанавливать Node.js, MySQL, phpMyAdmin локально
* Одинаковое окружение у всех разработчиков
* Изменения в коде видны мгновенно без ручного перезапуска
* Всё управление — одна команда `docker compose watch`

## Дополнительная информация

### Сравнение с `volumes` (bind mounts)

До появления `watch` для разработки использовались **bind mounts** из секции `volumes`. Важно понимать их отличия. Подробнее о томах см. в [Docker Volumes](../../Docker/Docker_fs/docker_volumes.md).

| Аспект | `volumes: ['./src:/app']` (старый подход) | `develop.watch` (новый подход) |
| :--- | :--- | :--- |
| **Основная функция** | Прямая "прозрачная" привязка файловой системы хоста к контейнеру. | Отслеживание изменений и выполнение **действий**. |
| **Перезапуск процесса** | **Не управляет**. Требуется **внешний инструмент** внутри контейнера (например, `nodemon`, `uvicorn --reload`), который следит за файлами и перезапускает процесс. | **Не управляет** (для `action: sync`). Также требуется `nodemon` или аналог. |
| **Пересборка образа** | **Невозможна**. При изменении `Dockerfile` или `requirements.txt` требуется ручной перезапуск: `docker compose down && docker compose up --build`. | **Встроена** (`action: rebuild`). Автоматизирует полный цикл пересборки и перезапуска. |
| **Пересоздание контейнера** | **Невозможно**. | **Встроено** (`action: recreate`). Автоматизирует перезапуск для применения новых конфигураций. |
| **Производительность** | Может быть низкой на macOS и Windows из-за особенностей реализации файловых систем. | `action: sync` часто предлагает **более высокую производительность** на этих системах, так как использует оптимизированные механизмы синхронизации (например, Mutagen.io). |

**Вывод:** `develop.watch` — это более мощное и "завершенное" решение для разработки. Он берет на себя не только синхронизацию файлов, как `volumes`, но и управление жизненным циклом сервиса (`rebuild`, `recreate`), что раньше требовало ручных действий или сложных скриптов.

### Ограничения и рекомендации

1. **Назначение только для разработки**: Режим `watch` категорически не предназначен для использования в production-средах.
2. **Конфликты**: Не смешивайте `watch` и `volumes` для одних и тех же путей, это может привести к непредсказуемому поведению.
3. **Производительность**: Несмотря на оптимизации, частая синхронизация больших объемов файлов может замедлять работу. Используйте `.dockerignore` для исключения ненужных файлов (`node_modules`, `.git` и т.д.).
