# Режим разработки (Watch Mode) в Docker Compose

**Актуально для:** Docker Compose v2.22.0+ (Compose Specification)

## Определения

**Режим watch** в Docker Compose — это специализированный инструмент для локальной разработки, который автоматически синхронизирует изменения в файлах между хостом и контейнером, а также управляет жизненным циклом сервисов (пересборка, перезапуск) в ответ на эти изменения.

В отличие от стандартных методов запуска, режим `watch` ориентирован на минимизацию времени обратной связи (feedback loop), позволяя разработчику видеть результат правок мгновенно, не прерывая работу стека вручную.

**Команда запуска:** `docker compose watch`

## Архитектура и принципы работы

### Внутренние механизмы

Режим `watch` использует **inotify** на хосте для отслеживания событий файловой системы. Каждый отслеживаемый путь (`path`) потребляет один watch descriptor в ядре Linux (~1 КБ памяти на дескриптор).

**Жизненный цикл watch-сессии:**

1. **Инициализация:** Compose загружает секцию `develop.watch` для каждого сервиса, проверяет существование путей `path` на хосте.
2. **Initial Sync:** Если указано `initial_sync: true`, Compose сравнивает метки времени файлов в контейнере с хостом и копирует измененные файлы перед началом отслеживания.
3. **Регистрация событий:** Для каждого `path` создается inotify-наблюдение. События `IN_MODIFY`, `IN_CLOSE_WRITE`, `IN_CREATE` инициируют соответствующие действия.
4. **Обработка событий:** В зависимости от `action` Compose выполняет:
   - `sync` / `sync+restart` / `sync+exec`: копирование файлов через контекст синхронизации.
   - `rebuild`: пересборка образа через BuildKit и замена контейнера.
5. **Очистка:** При остановке `watch` все inotify-дескрипторы закрываются автоматически.

### Обработка прав доступа и владельца

В режиме `watch` Docker использует оптимизированные механизмы передачи файлов:

- **UID/GID**: Файлы, синхронизированные через `action: sync`, по умолчанию сохраняют владельца, указанного в `Dockerfile` (инструкция `USER`) или в директиве `user` в `compose.yml`.
- **Права доступа (Mode)**: Сохраняются права доступа с хостовой системы. Рекомендуется использовать `chmod` на хосте перед запуском `watch`, если приложению требуются специфические права на исполнение.

## Базовые концепции

### Основные параметры директивы `watch`

Конфигурация режима `watch` описывается в секции `develop` для каждого конкретного сервиса в файле `compose.yml`.

- **`path`**: Относительный путь к файлу или директории на хосте, за изменениями в которых нужно следить.
- **`action`**: Действие, выполняемое при обнаружении изменений:
  - `sync`: (Самый быстрый) Файлы копируются в контейнер в реальном времени. Требует наличия механизма "hot reload" внутри приложения (например, Nodemon или Vite).
  - `sync+restart`: (Compose v2.23.0+) Синхронизирует файлы и затем перезапускает контейнер. Идеально для приложений, которые не умеют подхватывать изменения "на лету" (например, скомпилированные Go-бинарники или Python-скрипты без auto-reload), но не требуют пересборки образа.
  - `sync+exec`: (Compose v2.32.0+) Синхронизирует файлы и выполняет указанную команду внутри контейнера. Полезно для сигналов перезагрузки (например, `kill -HUP 1` для Nginx), когда полный рестарт не нужен.
  - `rebuild`: Выполняет полную пересборку образа и замену контейнера. Используется при изменении `Dockerfile`, файлов зависимостей (`package.json`, `requirements.txt`) или аргументов сборки (`args`).
- **`target`**: Путь внутри контейнера, куда следует синхронизировать файлы (обязателен для `sync`, `sync+restart`, `sync+exec`).
- **`ignore`**: Список паттернов (аналогично `.dockerignore`), которые следует исключить из отслеживания (например, `node_modules`, `.git`, временные файлы).
- **`initial_sync`**: (Compose v2.23.0+) Булево значение. Если `true`, Docker Compose выполнит полную синхронизацию всех указанных путей сразу при запуске команды `watch`. Это гарантирует, что состояние контейнера идентично хосту перед началом отслеживания событий.

### Сравнение с томами (Bind Mounts)

Исторически для разработки использовались `volumes` (bind mounts). Режим `watch` является их эволюционным развитием.

| Характеристика | Bind Mounts (`volumes`) | Compose Watch (`develop.watch`) |
| :--- | :--- | :--- |
| **Механизм** | Прямое монтирование ФС хоста в контейнер. | Событийное отслеживание и синхронизация. |
| **Производительность** | Низкая на macOS/Windows из-за накладных расходов виртуализации ФС. | Высокая за счет оптимизированных механизмов синхронизации. |
| **Управление циклом** | Только данные. Не умеет перезапускать контейнер или пересобирать образ. | Полное управление: `sync`, `rebuild`, `restart`, `exec`. |
| **Очистка контейнера** | Файлы, созданные контейнером, могут принадлежать `root` на хосте. | Файлы передаются через контекст синхронизации, минимизируя проблемы с правами. |
| **Автоматизация** | Требуются внешние скрипты для отслеживания Dockerfile. | Все описано декларативно в одном файле. |

### Ограничения и рекомендации

1. **Только для разработки**: Не используйте секцию `develop` и команду `watch` в производственных средах.
2. **Исключение лишнего**: Всегда настраивайте параметр `ignore`. Отслеживание тысяч файлов в `node_modules` или папках кэша значительно замедляет работу и потребляет ресурсы CPU.
3. **Изоляция**: Режим `watch` работает эффективнее, когда пути синхронизации не перекрываются с путями, объявленными в `volumes`.
4. **Ресурсы**: Каждый отслеживаемый путь потребляет файловые дескрипторы и память процесса Docker. Для очень больших монорепозиториев рекомендуется увеличивать лимиты `inotify` на хосте.

### Ресурсные ограничения inotify

Docker Compose Watch Mode использует inotify на хосте. Каждый отслеживаемый `path` потребляет один watch descriptor (~1 КБ памяти ядра).

**Диагностика исчерпания ресурсов:**
```bash
# Текущее использование watches
sudo lsof | grep inotify | wc -l

# Лимит на хосте
cat /proc/sys/fs/inotify/max_user_watches

# Процессы с наибольшим количеством inotify FD
sudo lsof | grep inotify | awk '{print $1}' | sort | uniq -c | sort -rn | head -5
```

**Временное увеличение лимита для больших монорепозиториев:**
```bash
sudo sysctl -w fs.inotify.max_user_watches=524288
```

## Практические сценарии

### Сценарий 1: Full-stack приложение на Node.js и Python

Пример конфигурации для проекта, где фронтенд требует пересборки при изменении зависимостей, а бэкенд требует перезапуска контейнера для применения изменений в коде.

```yaml
services:
  frontend:
    build: ./frontend
    develop:
      watch:
        # Синхронизация исходников (HMR подхватит изменения)
        - path: ./frontend/src
          action: sync
          target: /app/src
          ignore:
            - node_modules/
        # Пересборка при установке новых пакетов
        - path: ./frontend/package.json
          action: rebuild

  backend:
    build: ./backend
    develop:
      watch:
        # Синхронизация и перезапуск для Python-приложения без auto-reload
        - path: ./backend/api
          action: sync+restart
          target: /app/api
          initial_sync: true
        # Пересборка при изменении Dockerfile
        - path: ./backend/Dockerfile
          action: rebuild
```

### Сценарий 2: Go-приложение с hot reload через сигнал

Для приложений, поддерживающих перезагрузку по сигналу (например, Air для Go), используйте `sync+exec` вместо полного рестарта:

```yaml
services:
  app:
    build: ./app
    command: air -c .air.toml
    develop:
      watch:
        - path: ./app
          action: sync+exec
          target: /app
          exec: ["kill", "-HUP", "1"]
          initial_sync: true
        - path: ./app/go.mod
          action: rebuild
```

### Сценарий 3: Интеграция в CI/CD для smoke-тестов

Хотя `watch` предназначен для локальной разработки, его можно использовать в CI для быстрого запуска smoke-тестов после сборки:

```bash
# Сборка и запуск в фоне
docker compose up -d --build

# Запуск watch для синхронизации тестовых артефактов
docker compose watch &
WATCH_PID=$!

# Выполнение smoke-тестов
curl -f http://localhost:8000/health

# Остановка
kill $WATCH_PID
docker compose down -v
```

**Примечание:** В CI/CD предпочтительнее использовать `docker compose up --wait` для детерминированных окружений.

## Устранение неполадок

### Типичные ошибки режима watch

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| **`watch` не отслеживает файлы** | Указан неверный `path` или директория не существует | Убедитесь, что `path` существует на хосте относительно корня проекта. Используйте относительные пути. |
| **`sync` не работает без `target`** | Параметр `target` не указан для `action: sync` | Для `sync`, `sync+restart` и `sync+exec` параметр `target` обязателен. |
| **Файлы не синхронизируются после `down`/`up`** | Отсутствует `initial_sync: true` | Добавьте `initial_sync: true` для проверки синхронизации при запуске новой сессии. |
| **Высокая нагрузка на CPU/IO** | Отслеживаются `node_modules` или большие директории без `ignore` | Добавьте `ignore` с паттернами для исключения кэша и зависимостей. |
| **`No space left on device` (inotify)** | Исчерпан `fs.inotify.max_user_watches` | Увеличьте лимит: `sudo sysctl -w fs.inotify.max_user_watches=524288`. |
| **Права доступа нарушены после sync** | Файлы на хосте имеют неверные UID/GID | Настройте `user:` в `compose.yml` или используйте `chmod` на хосте перед запуском `watch`. |
| **Конфликт с bind mount** | Пути `watch.path` пересекаются с `volumes` | Разделите пути синхронизации и bind mounts. Режим `watch` работает эффективнее без пересечений. |
| **`sync+exec` не выполняется** | Compose версии младше v2.32.0 | Обновите Docker Compose. Проверьте версию: `docker compose version`. |
| **Изменения теряются при быстром редактировании** | События генерируются быстрее, чем обрабатываются | Увеличьте `max_queued_events` в sysctl. Используйте `sync+restart` вместо чистого `sync` для приложений без HMR. |

### Диагностический процесс

При возникновении проблем с режимом `watch`:

1. **Проверить версию Compose:** `docker compose version` — убедитесь, что используется v2.22.0+ (v2.23.0+ для `initial_sync`, v2.32.0+ для `sync+exec`).
2. **Валидировать конфигурацию:** `docker compose config` — проверьте итоговый YAML.
3. **Проверить inotify-ресурсы:** `sudo lsof | grep inotify | wc -l` и `cat /proc/sys/fs/inotify/max_user_watches`.
4. **Проверить статус:** `docker compose ps` — найти сервис в состоянии `exited` или `restarting`.
5. **Изучить логи:** `docker compose logs <service>` — искать ошибки доступа или синтаксиса.
6. **Инспектировать контейнер:** `docker inspect <container>` — проверить `Mounts` и `Config`.

## Рекомендации

### Безопасность

- **Не используйте в production:** Секция `develop` и команда `watch` предназначены только для локальной разработки. В production используйте статическую сборку образов.
- **Ограничение доступа к путям:** Убедитесь, что отслеживаемые директории не содержат чувствительные данные (ключи, сертификаты), которые могут быть синхронизированы в контейнер.
- **Права на хосте:** Настройте `chmod 700` на директории с исходным кодом, если разработка происходит на shared-хосте.

### Надежность

- **Initial Sync:** Всегда используйте `initial_sync: true` для сервисов с `sync+restart` или `sync+exec`. Это гарантирует консистентность состояния после `docker compose down`/`up`.
- **Healthcheck:** Для сервисов с `sync+restart` определите `healthcheck`, чтобы избежать "race condition" при перезапуске.
- **Валидация в CI:** Добавьте `docker compose config` в pre-commit hooks для проверки корректности секции `develop`.
- **Мониторинг inotify:** Для SRE: настройте алерты на `node_filefd_allocated` (prometheus_node_exporter) и логи ядра `dmesg | grep -i inotify`.

### Производительность

- **Ignore паттерны:** Всегда настраивайте `ignore` для исключения `node_modules`, `.git`, кэшей и временных файлов.
- **Изоляция путей:** Разделите пути для `sync` и `rebuild`. Не отслеживайте одну директорию несколькими правилами с разными `action`.
- **Лимиты inotify:** Для монорепозиториев увеличивайте `fs.inotify.max_user_watches` на хосте. Типичные значения: 524288 для VS Code, 1048576 для IntelliJ.
- **Архитектура:** Используйте `sync` для языков с HMR (JS/TS), `sync+restart` для компилируемых языков без HMR (Go, Python), `rebuild` только для изменений зависимостей.

### Поддержка и эксплуатация

- **Версионирование:** Для reproducibility фиксируйте версию Docker Compose в `docker compose version` или через `COMPOSE_BAKE`.
- **Документация:** Добавляйте комментарии в `develop.watch` для неочевидных правил синхронизации.
- **CI интеграция:** В пайплайнах используйте `docker compose up --wait` вместо `watch` для детерминированных тестов.
- **Очистка ресурсов:** После остановки `watch` проверяйте, что все inotify-дескрипторы освобождены: `sudo lsof | grep inotify | wc -l` должно вернуться к базовому уровню.
