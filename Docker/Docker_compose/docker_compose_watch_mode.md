# Режим разработки (Watch Mode) в Docker Compose

## Определения

**Режим watch** в Docker Compose — это специализированный инструмент для локальной разработки, который автоматически синхронизирует изменения в файлах между хостом и контейнером, а также управляет жизненным циклом сервисов (пересборка, перезапуск) в ответ на эти изменения.

В отличие от стандартных методов запуска, режим `watch` ориентирован на минимизацию времени обратной связи (feedback loop), позволяя разработчику видеть результат правок мгновенно, не прерывая работу стека вручную.

**Команда запуска:** `docker compose watch`

## Базовые концепции

Конфигурация режима `watch` описывается в секции `develop` для каждого конкретного сервиса в файле `compose.yml`.

### Основные параметры директивы `watch`

- **`path`**: Относительный путь к файлу или директории на хосте, за изменениями в которых нужно следить.
- **`action`**: Действие, выполняемое при обнаружении изменений:
  - `sync`: (Самый быстрый) Файлы копируются в контейнер в реальном времени. Требует наличия механизма "hot reload" внутри приложения (например, Nodemon или Vite).
  - `rebuild`: Выполняет полную пересборку образа и замену контейнера. Используется при изменении `Dockerfile`, файлов зависимостей (`package.json`, `requirements.txt`) или аргументов сборки (`args`).
  - `sync+restart`: Синхронизирует файлы и затем перезапускает контейнер. Идеально для приложений, которые не умеют подхватывать изменения "на лету" (например, скомпилированные Go-бинарники или Python-скрипты без auto-reload), но не требуют пересборки образа.
- **`target`**: Путь внутри контейнера, куда следует синхронизировать файлы (обязателен для `action: sync`).
- **`ignore`**: Список паттернов (аналогично `.dockerignore`), которые следует исключить из отслеживания (например, `node_modules`, `.git`, временные файлы).
- **`initial_sync`**: (Compose v5+) Булево значение. Если `true`, Docker Compose выполнит полную синхронизацию всех указанных путей сразу при запуске команды `watch`. Это гарантирует, что состояние контейнера идентично хосту перед началом отслеживания событий.

### Обработка прав доступа и владельца

В режиме `watch` Docker использует оптимизированные механизмы передачи файлов:

- **UID/GID**: Файлы, синхронизированные через `action: sync`, по умолчанию сохраняют владельца, указанного в `Dockerfile` (инструкция `USER`) или в директиве `user` в `compose.yml`.
- **Права доступа (Mode)**: Сохраняются права доступа с хостовой системы. Рекомендуется использовать `chmod` на хосте перед запуском `watch`, если приложению требуются специфические права на исполнение.

### Сравнение с томами (Bind Mounts)

Исторически для разработки использовались `volumes` (bind mounts). Режим `watch` является их эволюционным развитием.

| Характеристика | Bind Mounts (`volumes`) | Compose Watch (`develop.watch`) |
| :--- | :--- | :--- |
| **Механизм** | Прямое монтирование ФС хоста в контейнер. | Событийное отслеживание и синхронизация. |
| **Производительность** | Низкая на macOS/Windows из-за накладных расходов виртуализации ФС. | Высокая за счет оптимизированных механизмов синхронизации. |
| **Управление циклом** | Только данные. Не умеет перезапускать контейнер или пересобирать образ. | Полное управление: `sync`, `rebuild`, `restart`. |
| **Очистка контейнера** | Файлы, созданные контейнером, могут принадлежать `root` на хосте. | Файлы передаются через контекст синхронизации, минимизируя проблемы с правами. |
| **Автоматизация** | Требуются внешние скрипты для отслеживания Dockerfile. | Все описано декларативно в одном файле. |

### Ограничения и рекомендации

1. **Только для разработки**: Не используйте секцию `develop` и команду `watch` в производственных средах.
2. **Исключение лишнего**: Всегда настраивайте параметр `ignore`. Отслеживание тысяч файлов в `node_modules` или папках кэша значительно замедляет работу и потребляет ресурсы CPU.
3. **Изоляция**: Режим `watch` работает эффективнее, когда пути синхронизации не перекрываются с путями, объявленными в `volumes`.
4. **Ресурсы**: Каждый отслеживаемый путь потребляет файловые дескрипторы и память процесса Docker. Для очень больших монорепозиториев рекомендуется увеличивать лимиты `inotify` на хосте.

## Практические сценарии

### Сценарий 1: Full-stack приложение на Node.js и Python

Пример конфигурации для проекта, где фронтенд требует пересборки при изменении зависимостей, а бэкенд требует перезапуска контейнера для применения изменений в коде.

```yaml
services:
  frontend:
    build: ./frontend
    develop:
      watch:
        # Синхронизация исходников (HMR подхватит изменения)
        - path: ./frontend/src
          action: sync
          target: /app/src
          ignore:
            - node_modules/
        # Пересборка при установке новых пакетов
        - path: ./frontend/package.json
          action: rebuild

  backend:
    build: ./backend
    develop:
      watch:
        # Синхронизация и перезапуск для Python-приложения без auto-reload
        - path: ./backend/api
          action: sync+restart
          target: /app/api
          initial_sync: true
        # Пересборка при изменении Dockerfile
        - path: ./backend/Dockerfile
          action: rebuild
```

### Сценарий 2: Оптимизация сборки AI-приложения

Использование `watch` вместе с новыми возможностями Compose v5 для AI-проектов.

```yaml
services:
  ai-model-server:
    image: ai-runner:latest
    models:
      - path: ./models/llama-3.gguf
        target: /models/llama-3.gguf
    develop:
      watch:
        # Обновление скриптов обработки без перезапуска тяжелой модели
        - path: ./scripts/inference.py
          action: sync
          target: /app/inference.py
        # Перезапуск при изменении параметров квантования
        - path: ./config/quantization.json
          action: sync+restart
          target: /app/config.json
```
