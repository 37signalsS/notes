# Сравнение версий Docker Compose

## Определения

**Форматы Docker Compose** эволюционировали от жестких схем версионирования (v2, v3) к открытому стандарту **Compose Specification** и его современной реализации в **Compose v5 (2025–2026)**.

Эволюцию инструмента можно разделить на два ключевых периода:
1.  **Период Python-утилиты (`docker-compose`):** Использовал версии формата (2.x, 3.x), требовал обязательного указания поля `version` и имел ограниченную поддержку современных функций. В 2025 году официально признан устаревшим (EOL).
2.  **Период Go-плагина (`docker compose`):** Базируется на Compose Specification. Поле `version` является необязательным и игнорируется. Инструмент (Compose v5+) предоставляет унифицированные возможности для разработки, оркестрации локальных сред и интеграции с AI/ML.

## Базовые концепции

### Эволюция управления зависимостями (`depends_on`)

Это наиболее динамично развивающаяся часть спецификации, определяющая надежность и порядок запуска стека.

| Параметр | Версии 2.x | Версии 3.0–3.3 | Compose Specification (v5+) |
| :--- | :--- | :--- | :--- |
| **`condition: service_healthy`** | Поддерживалось | Удалено (для Swarm) | **Рекомендуется** |
| **`condition: service_completed_successfully`** | Нет | Нет | Поддерживается (для миграций и задач) |
| **`required: false`** | Нет | Нет | Поддерживается (опциональные зависимости) |
| **`restart: true`** | Нет | Нет | Поддерживается (каскадный рестарт сервисов) |

### Ресурсные ограничения и GPU

- **Версии 2.x:** Лимиты задавались в корне сервиса (`mem_limit`, `cpus`). Поддержка GPU требовала использования `nvidia-docker` и специфичных параметров `devices`.
- **Версии 3.x:** Лимиты ресурсов перенесены в секцию `deploy.resources`. Обычный Docker Compose (до версии 1.27) игнорировал их, если не использовался режим Swarm.
- **Compose Specification (v5+):** Параметры `deploy.resources` (limits и reservations) являются стандартными для всех режимов запуска. Добавлена упрощенная директива верхнего уровня **`gpus`** для нативной поддержки ускорителей NVIDIA и AMD.

### Модульность и переиспользование кода

- **Версии 2.x/3.x:** Использовалась директива `extends` для наследования свойств отдельных сервисов. Имела множество ограничений при работе с именованными ресурсами (сетями и томами).
- **Compose Specification (v5+):** Введена директива **`include`**. Она позволяет импортировать целые проекты с сохранением их внутренней структуры ресурсов, обеспечивая истинную модульность и изоляцию. Также поддерживается импорт конфигураций напрямую из OCI-реестров.

### Инструменты разработки

- **Устаревший подход:** Использование сторонних утилит (Nodemon, Watchman) и монтирование кода через `volumes` (bind mounts), что приводило к проблемам с производительностью на macOS/Windows.
- **Compose Specification (v5+):** Нативная поддержка инструментов разработки в секции **`develop`**. Директива **`watch`** обеспечивает высокопроизводительную синхронизацию кода (`sync`) и автоматическую пересборку (`rebuild`) при изменениях.

## Практические сценарии

### Чек-лист миграции на современный стандарт

Для приведения файлов `compose.yml` к стандарту 2026 года:

1.  **Удалите поле `version`:** Оно больше не несет функциональной нагрузки и может вызывать предупреждения в логах.
2.  **Замените методы ожидания:** Откажитесь от внешних скриптов (`wait-for-it.sh`) в пользу `condition: service_healthy`.
3.  **Используйте `include`:** Разделяйте инфраструктурные части (БД, мониторинг) и код приложения в разные файлы, объединяя их через `include`.
4.  **Настройте Healthcheck:** Всегда определяйте проверку здоровья для критичных компонентов (базы данных, API), чтобы обеспечить корректную работу `depends_on`.

### Пример: Современный стек (PostgreSQL 17 + App)

```yaml
name: modern-app-stack

services:
  db:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      retries: 5
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD_FILE=/run/secrets/db_pass
    secrets:
      - db_pass

  app:
    build: .
    depends_on:
      db:
        condition: service_healthy
        restart: true # Авторестарт приложения при обновлении БД
    develop:
      watch:
        - action: sync
          path: ./src
          target: /app/src

secrets:
  db_pass:
    file: ./db_pass.txt
```
