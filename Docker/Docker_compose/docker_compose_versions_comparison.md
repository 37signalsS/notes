# Сравнение версий Docker Compose

**Актуально для:** Docker Compose v5+ (Compose Specification, 2025–2026)

## Определения

**Форматы Docker Compose** эволюционировали от жестких схем версионирования (v2, v3) к открытому стандарту **Compose Specification** и его современной реализации в **Compose v5 (2025–2026)**.

Эволюцию инструмента можно разделить на два ключевых периода:
1.  **Период Python-утилиты (`docker-compose`):** Использовал версии формата (2.x, 3.x), требовал обязательного указания поля `version` и имел ограниченную поддержку современных функций. В 2025 году официально признан устаревшим (EOL).
2.  **Период Go-плагина (`docker compose`):** Базируется на Compose Specification. Поле `version` является необязательным и игнорируется. Инструмент (Compose v5+) предоставляет унифицированные возможности для разработки и оркестрации локальных сред.

## Базовые концепции

### Эволюция управления зависимостями (`depends_on`)

Это наиболее динамично развивающаяся часть спецификации, определяющая надежность и порядок запуска стека.

| Параметр | Версии 2.x | Версии 3.0–3.3 | Compose Specification (v5+) |
| :--- | :--- | :--- | :--- |
| **`condition: service_healthy`** | Поддерживалось | Удалено (для Swarm) | **Рекомендуется** |
| **`condition: service_completed_successfully`** | Нет | Нет | Поддерживается (для миграций и задач) |
| **`required: false`** | Нет | Нет | Поддерживается (опциональные зависимости) |
| **`restart: true`** | Нет | Нет | Поддерживается (каскадный рестарт сервисов) |

### Ресурсные ограничения и GPU

- **Версии 2.x:** Лимиты задавались в корне сервиса (`mem_limit`, `cpus`). Поддержка GPU требовала использования `nvidia-docker` и специфичных параметров `devices`.
- **Версии 3.x:** Лимиты ресурсов перенесены в секцию `deploy.resources`. Обычный Docker Compose (до версии 1.27) игнорировал их, если не использовался режим Swarm.
- **Compose Specification (v5+):** Параметры `deploy.resources` (limits и reservations) являются стандартными для всех режимов запуска. Добавлена упрощенная директива верхнего уровня **`gpus`** для нативной поддержки ускорителей NVIDIA и AMD.

### Модульность и переиспользование кода

- **Версии 2.x/3.x:** Использовалась директива `extends` для наследования свойств отдельных сервисов. Имела множество ограничений при работе с именованными ресурсами (сетями и томами).
- **Compose Specification (v5+):** Введена директива **`include`**. Она позволяет импортировать целые проекты с сохранением их внутренней структуры ресурсов, обеспечивая истинную модульность и изоляцию. Также поддерживается импорт конфигураций напрямую из OCI-реестров.

### Инструменты разработки

- **Устаревший подход:** Использование сторонних утилит (Nodemon, Watchman) и монтирование кода через `volumes` (bind mounts), что приводило к проблемам с производительностью на macOS/Windows.
- **Compose Specification (v5+):** Нативная поддержка инструментов разработки в секции **`develop`**. Директива **`watch`** обеспечивает высокопроизводительную синхронизацию кода (`sync`) и автоматическую пересборку (`rebuild`) при изменениях.

## Практические сценарии

### Чек-лист миграции на современный стандарт

Для приведения файлов `compose.yml` к стандарту 2026 года:

1.  **Удалите поле `version`:** Оно больше не несет функциональной нагрузки и может вызывать предупреждения в логах.
2.  **Замените методы ожидания:** Откажитесь от внешних скриптов (`wait-for-it.sh`) в пользу `condition: service_healthy`.
3.  **Используйте `include`:** Разделяйте инфраструктурные части (БД, мониторинг) и код приложения в разные файлы, объединяя их через `include`.
4.  **Настройте Healthcheck:** Всегда определяйте проверку здоровья для критичных компонентов (базы данных, API), чтобы обеспечить корректную работу `depends_on`.

### Пример: Современный стек (PostgreSQL 17 + App)

```yaml
name: modern-app-stack

services:
  db:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      retries: 5
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD_FILE=/run/secrets/db_pass
    secrets:
      - db_pass

  app:
    build: .
    depends_on:
      db:
        condition: service_healthy
        restart: true # Авторестарт приложения при обновлении БД
    develop:
      watch:
        - action: sync
          path: ./src
          target: /app/src

secrets:
  db_pass:
    file: ./db_pass.txt
```

## Архитектура и принципы работы

### Жизненный цикл обработки конфигурации

Compose Specification v5+ выполняет одн passing pipeline для каждого `docker compose` вызова:

1. **Загрузка и парсинг:** Читает `compose.yml` и все файлы из `include` (локальные пути или OCI-артефакты). Поле `version` игнорируется, но его наличие не вызывает ошибок.
2. **Валидация схемы:** Проверяет типы значений, обязательные поля и ссылки на ресурсы. В отличие от Python-утилиты, Go-плагин использует строгую типизацию и возвращает детальные ошибки.
3. **Слияние (deep merge):** Несколько файлов объединяются по правилам: скаляры заменяются последним значением, массивы конкатенируются, карты сливаются глубоко. Порядок: базовый `compose.yml` → `compose.override.yml` → файлы из `-f` (последний имеет высший приоритет).
4. **Интерполяция переменных:** Подстановка `${VAR}` из окружения, `.env` файлов и `env_file`. Приоритет: OS Environment > `--env-file` > `env_file` сервиса > `.env` в директории проекта > значения по умолчанию в YAML.
5. **Разрешение зависимостей:** Построение графа `depends_on` с учетом `condition`. При `service_healthy` Compose ожидает успешного прохождения `healthcheck`.
6. **Создание ресурсов:** Сети, тома, секреты создаются через Docker API. В Compose Specification ресурсы верхнего уровня автоматически изолированы между `include`-модулями.
7. **Запуск и мониторинг:** Контейнеры запускаются в порядке графа зависимостей. Compose отслеживает состояние через драйвер событий Docker и применяет политики `restart`.

### Обратная совместимость

- **Python-утилита (`docker-compose`):** EOL с 2025 года. Поддерживает форматы v2 и v3. Поле `version` обязательно. Не поддерживает `include`, `gpus`, `develop.watch`, `condition: service_completed_successfully`.
- **Go-плагин (`docker compose`):** Современный инструмент. Поле `version` необязательно и игнорируется. Поддерживает весь Compose Specification v5+.
- **Миграция:** Файлы, созданные для Python-утилиты, работают в Go-плагине без изменений, за исключением удаленных в v3 функций (`condition` для Swarm).

### Выбор между `extends` и `include`

| Критерий | `extends` | `include` |
| :--- | :--- | :--- |
| **Модульность** | Только сервисы | Сервисы, сети, тома, секреты |
| **Изоляция ресурсов** | Нет | Автоматическая изоляция namespace |
| **Вложенность** | До 10 уровней | Рекомендуется ≤3 уровня |
| **OCI-реестры** | Нет | Поддержка `oci:` (Compose v2.20+) |
| **Рекомендация** | Устаревший | Современный стандарт |

## Валидация

Перед применением конфигурации в продакшене или CI/CD проверяйте итоговый вид стека:

```bash
# Показать объединенную конфигурацию после всех merge и include
docker compose config

# Проверить синтаксис без запуска контейнеров
docker compose config --services
docker compose config --volumes
docker compose config --networks

# Валидация конкретного сервиса
docker compose config app
```

Для автоматической проверки в пайплайнах:
```bash
docker compose config --quiet && echo "OK" || echo "INVALID"
```

## Best Practices

### Организация файлов

- **Один файл — одна ответственность:** разделяйте инфраструктуру (БД, кеш, мониторинг) на отдельные compose-файлы и импортируйте через `include`.
- **Используйте `include` вместо `extends`** для модульности: `extends` не импортирует сети, тома и секреты, что создает скрытые зависимости.
- **Версионируйте OCI-артефакты:** при использовании `include` с реестров тегируйте конфигурации так же, как образы (`:v1.2.0`, `:stable`).
- **`compose.override.yml` только для локальной разработки:** не коммитьте файл с продакшн-переопределениями в репозиторий.
- **Избегайте глубокой вложенности `include` (>3 уровня):** это затрудняет отладку и снижает читаемость.

### Соглашения по именованию

- Используйте осмысленные имена для импортируемых файлов: `database.yml`, `monitoring.yml`, не `base1.yml`.
- Для ресурсов верхнего уровня (сети, тома) используйте префикс проекта: `${PROJECT_NAME}_db_data` вместо `data`.
- В CI/CD окружении задавайте префикс проекта через `-p` или `COMPOSE_PROJECT_NAME`, чтобы избежать коллизий с существующими стеками.

### Операционная безопасность

- **Секреты:** не храните чувствительные данные в compose-файлах. Используйте `secrets:` с внешними провайдерами (Vault, Docker secrets, env-файлы за пределами репозитория).
- **Права доступа:** проверяйте, что файлы, импортируемые через `include`, имеют корректные права доступа (0640 или строже) и не доступны для записи непривилегированным пользователям.
- **Образы:** используйте фиксированные теги вместо `latest` в продакшн-конфигурациях. Проверяйте целостность через `image digest` или подпись образов.

## Безопасность

### Угрозы и mitigate

| Угроза | Вектор атаки | Меры противодействия |
| :--- | :--- | :--- |
| **Утечка секретов в compose-файлах** | Секреты закоммичены в репозиторий | Используйте `secrets:` с внешними провайдерами, проверяйте `.gitignore` |
| **Подмена импортируемого OCI-артефакта** | Атака на реестр, компрометация тега | Подписывайте конфигурации, используйте `COMPOSE_OCI_INSECURE=false`, проверяйте digest |
| **Коллизия имен ресурсов** | Два `include` создают ресурс с одинаковым именем | Используйте уникальные имена, изолируйте в отдельные проекты |
| **Эскалация привилегий через `privileged`** | Контейнер с `privileged: true` имеет доступ к хосту | Отсутствие `privileged` по умолчанию; аудит через `docker compose config` |
| **Неавторизованное изменение `compose.override.yml`** | Локальный файл переопределяет продакшн-настройки | Используйте `--no-auto-compose` в CI, храните конфигурации в VCS |

### Рекомендации

- Никогда не коммитьте файлы `compose.override.yml` с продакшн-значениями. Используйте `.gitignore` или отдельные ветки для локальных изменений.
- Для OCI-артефактов настраивайте доверенные реестры и отключайте небезопасные подключения (`COMPOSE_OCI_INSECURE=false`).
- Регулярно аудите `docker compose config` на наличие неожиданных `privileged`, `network_mode: host` или монтирования корневой файловой системы.

## Edge Cases

### Обратная совместимость с Python-утилитой

Файлы, созданные для `docker-compose` (Python), работают в `docker compose` (Go) без изменений, за исключением удаленных функций:
- `condition: service_completed_successfully` — не поддерживалась в v3, добавлена в Compose Specification.
- `include` — отсутствовала в Python-утилите.
- `gpus` — отсутствовала до Compose Specification v5+.

### Глубина `extends` и производительность

Максимальная глубина 10 уровней является теоретическим лимитом. На практике глубина >3 замедляет валидацию и усложняет отладку. Используйте `docker compose config` для проверки итоговой конфигурации при глубоком наследовании.

### Обработка ошибок в OCI-артефактах

При недоступности OCI-реестра Compose завершает работу с ошибкой и не откатывает частично загруженную конфигурацию. В CI/CD используйте `--dry-run` или предварительную проверку доступности реестра:

```bash
# Проверка доступности OCI-артефакта перед запуском
docker compose --dry-run config
```
