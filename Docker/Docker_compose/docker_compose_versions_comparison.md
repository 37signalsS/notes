# Версии Compose: от `docker-compose` (v2/v3) к Compose Spec

## Определения

Изначально Docker Compose был отдельным инструментом на Python (`docker-compose`), и его файлы конфигурации использовали строгую **версию формата** (`version: '2.4'`, `version: '3.8'`). Разные версии формата поддерживали разный набор директив.

Современный `docker compose` — это плагин, встроенный в основной CLI Docker. Он следует единой **Compose Specification**, которая объединяет лучшие черты предыдущих версий и является текущим стандартом. Указание `version` в файле теперь в основном служит для обратной совместимости и не так строго определяет доступные возможности, как раньше.

## Основные концепции: Ключевые изменения

### 1. Управление зависимостями: `depends_on` и возвращение `condition`

Это самое важное изменение, которое часто понимают неправильно.

- **Версия 2.x:** Поддерживала `condition: service_healthy`, что позволяло сервису ожидать полной готовности зависимости.
- **Ранние версии формата v3 (например, 3.0-3.3):** Поддержка `condition` была **временно убрана**. `depends_on` гарантировал только *порядок запуска*, но не готовность сервиса. Это породило широкое использование обходных путей, таких как скрипты `wait-for-it.sh`.
- **Современная Compose Specification:** **Вернула и расширила** поддержку `condition`. Это предпочтительный способ управления зависимостями сегодня.

**Доступные условия (`condition`):**
- `service_started`: Ожидать только запуска зависимого сервиса (поведение по умолчанию).
- `service_healthy`: Ожидать, пока зависимый сервис не перейдет в состояние `healthy` (требует наличия `healthcheck`).
- `service_completed_successfully`: Ожидать, пока зависимый сервис не завершится с кодом `0`. Идеально для одноразовых задач, таких как миграции.

### 2. Ограничение ресурсов: `cpu_shares`, `mem_limit` vs. `deploy`

- **Версия 2.x:** Лимиты ресурсов задавались напрямую в сервисе (`cpu_shares`, `mem_limit`).
- **Версия 3.x и Compose Spec:** Эти директивы были перенесены в секцию `deploy.resources`.

> **Важно:** Изначально секция `deploy` предназначалась только для **[Docker Swarm](../../Docker_swarm/docker_swarm_overview.md)** и игнорировалась командой `docker compose up`. Однако современные версии `docker compose` **частично поддерживают** применение `deploy.resources.limits` даже без Swarm, что делает управление ресурсами более унифицированным.

## Практические сценарии

### Правильное ожидание зависимостей (Современный подход)

Вместо использования скриптов-оберток, современный Compose позволяет элегантно решить проблему ожидания готовности базы данных с помощью `healthcheck` и `depends_on.condition`.

**Пример `compose.yml` (Современный синтаксис):**

```yaml
# Рекомендуется указывать последнюю версию для совместимости
version: '3.8' 

services:
  database:
    image: postgres:16
    restart: always
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=secret
      - POSTGRES_DB=app_db
    # Healthcheck критически важен для condition: service_healthy
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d app_db"]
      interval: 10s
      timeout: 5s
      retries: 5
  
  web:
    build: .
    image: my-app
    ports:
      - "8000:8000"
    # Эта конфигурация гарантирует, что 'web' запустится только 
    # после того, как 'database' станет 'healthy'.
    depends_on:
      database:
        condition: service_healthy
    # Команда запуска чистая, без оберток
    command: python manage.py runserver 0.0.0.0:8000
```

**Ключевой вывод:** Использование `wait-for-it.sh` и подобных скриптов больше **не является необходимостью** для ожидания готовности баз данных, если сервис `database` имеет корректно настроенный `healthcheck`.

## Дополнительная информация

- **Рекомендация:** Всегда используйте последнюю версию формата (`3.8` или выше) и полагайтесь на возможности Compose Specification, такие как `depends_on.condition`.
- **Директива `version`:** Хотя она и стала менее строгой, ее указание помогает инструментам валидации и анализа правильно интерпретировать ваш файл.
- **Справочник по директивам:** Полный список и описание директив см. в файле [**Директивы Docker Compose**](./docker_compose_directives.md).
