# Сравнение версий Docker Compose

## Определения

**Форматы Docker Compose** прошли путь от жестко заданных схем (v2, v3) до открытого стандарта **Compose Specification** и его современной реализации в рамках **Compose v5 (2025–2026)**.

Эволюцию инструмента можно разделить на два ключевых периода:
1.  **Период Python-утилиты (`docker-compose`):** Использовал версии формата (2.x, 3.x), требовал обязательного указания поля `version` и имел ограниченную поддержку современных функций. В 2025 году официально признан устаревшим (EOL).
2.  **Период Go-плагина (`docker compose`):** Базируется на Compose Specification. Версии формата больше не используются, а инструмент (Compose v5+) предоставляет унифицированные возможности для разработки, тестирования и интеграции с AI/ML.

## Базовые концепции

### Эволюция управления зависимостями (`depends_on`)

Это наиболее динамично развивающаяся часть спецификации, определяющая надежность запуска стека.

| Параметр | Версии 2.x | Версии 3.0–3.3 | Compose Specification (v5+) |
| :--- | :--- | :--- | :--- |
| **`condition: service_healthy`** | Поддерживалось | Удалено (для Swarm) | **Рекомендуется** |
| **`condition: service_completed`** | Нет | Нет | Поддерживается (для миграций) |
| **`required: false`** | Нет | Нет | Поддерживается (опционально) |
| **`restart: true`** | Нет | Нет | Поддерживается (каскадный рестарт) |

### Ресурсные ограничения и GPU

- **Версии 2.x:** Лимиты задавались в корне сервиса (`mem_limit`, `cpus`). Поддержка GPU требовала сторонних расширений.
- **Версии 3.x:** Лимиты перенесены в `deploy.resources`. Игнорировались обычным Compose до версии 1.27.
- **Compose v5+:** Параметры `deploy.resources` работают везде. Добавлена упрощенная директива верхнего уровня **`gpus`** для нативной поддержки NVIDIA и AMD.

### Модульность и переиспользование кода

- **Версии 2.x/3.x:** Использовалась директива `extends`, которая имела множество ограничений при наследовании ресурсов.
- **Compose v5+:** Введена директива **`include`**. Она позволяет импортировать целые проекты, включая их собственные тома и сети, обеспечивая истинную модульность и изоляцию.

### Инструменты разработки

- **Устаревший подход:** Использование внешних инструментов (Nodemon, Watchman) и монтирование кода через `volumes`.
- **Compose v5+:** Нативная секция **`develop.watch`** с поддержкой `sync`, `rebuild` и `initial_sync`.

## Практические сценарии

### Миграция со старых форматов (Checklist)

Для приведения старых файлов `docker-compose.yml` к современному стандарту 2026 года:

1.  **Удалите поле `version`:** Оно больше не обрабатывается и может вызывать предупреждения.
2.  **Обновите `depends_on`:** Замените внешние скрипты ожидания (`wait-for-it.sh`) на `condition: service_healthy`.
3.  **Перейдите на `include`:** Если у вас несколько связанных файлов, используйте `include` вместо объединения через флаг `-f` для лучшей изоляции.
4.  **Добавьте Healthcheck:** Убедитесь, что для баз данных прописаны правила проверки готовности.

### Пример: Современный стек (PostgreSQL 17)

Пример, демонстрирующий возможности Compose Specification v5.

```yaml
name: modern-app-stack

services:
  db:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      retries: 5
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD_FILE=/run/secrets/db_pass
    secrets:
      - db_pass

  app:
    build: .
    depends_on:
      db:
        condition: service_healthy
        restart: true # Перезапустит app, если db упадет и поднимется
    develop:
      watch:
        - action: sync
          path: ./src
          target: /app/src

secrets:
  db_pass:
    file: ./db_pass.txt
```
