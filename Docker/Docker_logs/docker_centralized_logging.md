# Централизованное логирование Docker: Лог-драйверы

## Определения

Ключевые определения, такие как **Лог-драйвер (Log Driver)** и сравнение архитектур, приведены в основном документе: **[Обзор системы логирования в Docker](./docker_logging_drivers_overview.md)**.

**Централизованное логирование** — это практика сбора и агрегации логов из множества источников в единую систему для хранения, анализа и мониторинга.

## Базовые концепции

При использовании лог-драйверов Docker daemon перехватывает вывод запущенного приложения и напрямую отправляет его по сети или в локальную системную службу (например, `journald` или `syslog`).

**Схема работы:**
`Приложение → STDOUT/STDERR → Docker Engine (log driver) → Система назначения (Syslog, GELF, Fluentd, Loki)`

### Современный стандарт: Dual Logging

Начиная с Docker 20.10, по умолчанию включен механизм **Dual Logging** (двойное логирование). Это решает историческую проблему сетевых драйверов — невозможность использовать команду `docker logs`.

**Как это работает:** Docker одновременно отправляет логи в удаленную систему и сохраняет их в локальном кэше на хосте (обычно используя драйвер `local`). Это позволяет:
- Использовать `docker logs <container>` для быстрой отладки последних событий.
- Хранить полную историю логов в централизованном хранилище для глубокого анализа.

### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- |
| **Простота архитектуры**: Не требуется разворачивать агенты на каждом хосте; Docker сам управляет отправкой. | **Риск блокировки (Blocking)**: По умолчанию сетевые драйверы работают в блокирующем режиме. Если сеть недоступна, приложение может зависнуть. *Решение: `mode=non-blocking`.* |
| **Dual Logging**: Поддержка `docker logs` сохраняется даже при использовании сетевых драйверов (через локальный кэш). | **Нагрузка на Docker Engine**: При большом объеме логов и сложных фильтрах Docker daemon может потреблять значительные ресурсы CPU/RAM. |
| **Минимальные ресурсы**: Отсутствие сторонних процессов (агентов) экономит оперативную память хоста. | **Ограниченная гибкость**: Лог-драйверы имеют меньше настроек трансформации и парсинга данных по сравнению с агентами (Vector, Fluent Bit). |

## Глобальные настройки безопасности и стабильности

Для любого сетевого лог-драйвера в продакшене **обязательно** использование неблокирующего режима.

**Рекомендуемый конфиг (`/etc/docker/daemon.json`):**

```json
{
  "log-driver": "gelf",
  "log-opts": {
    "gelf-address": "udp://graylog:12201",
    "mode": "non-blocking",
    "max-buffer-size": "4m"
  }
}
```

- **`mode: non-blocking`**: Docker пишет логи в промежуточный буфер в памяти. Если буфер переполнен (например, Graylog недоступен), новые логи отбрасываются, но приложение **продолжает работу**.
- **`max-buffer-size`**: Размер буфера памяти для режима `non-blocking`. По умолчанию 1 МБ.

## Практические сценарии

### Драйвер `journald`

Интегрируется с `systemd-journald`, позволяя использовать стандартную утилиту [`journalctl`](../../Linux/Diagnostics/journalctl/journalctl_overview.md) для просмотра логов всех контейнеров. Это предпочтительный выбор для систем на базе `systemd`.

**Конфигурация (`/etc/docker/daemon.json`):**

```json
{
  "log-driver": "journald",
  "log-opts": {
    "tag": "{{.ImageName}}/{{.Name}}/{{.ID}}"
  }
}
```

> #### Важно: Тюнинг `journald`
>
> По умолчанию `journald` ограничивает количество принимаемых сообщений, что может привести к их потере при высокой нагрузке.
> **Симптом**: В логах `journald` появляется сообщение `systemd-journald[...]: Suppressed ... messages from ...`.
> **Решение**: Увеличьте лимиты в `/etc/systemd/journald.conf`:
>
> ```ini
> [Journal]
> RateLimitBurst=50000
> ```
>
> После этого перезапустите службу: `sudo systemctl restart systemd-journald` # → OK.

### Драйвер `syslog`

Отправляет логи на Syslog-сервер (локальный или удаленный) по стандартному протоколу Syslog.

**Использование:**

```bash
docker run --log-driver=syslog --log-opt syslog-address=udp://1.2.3.4:514 my_image
# → запуск контейнера с отправкой логов по UDP (User Datagram Protocol)
```

### Драйвер `gelf`

Отправляет логи на GELF-совместимый сервер, такой как Graylog или Logstash. Протокол GELF (Graylog Extended Log Format) позволяет передавать структурированные данные.

**Использование:**

```bash
docker run --log-driver=gelf --log-opt gelf-address=udp://1.2.3.4:12201 my_image
# → запуск контейнера с отправкой логов в формате GELF
```

### Драйвер `fluentd`

Отправляет логи на сервер-агрегатор Fluentd.

**Конфигурация для отдельного контейнера:**

```bash
docker run \
  --log-driver=fluentd \
  --log-opt fluentd-address=localhost:24224 \
  --log-opt tag="docker.my_app.{{.Name}}" \
  your/application_image
# → запуск контейнера с отправкой логов во Fluentd
```

**Пример конфигурации Fluentd (`fluent.conf`):**

```conf
# Источник: Принимает логи от Docker logging driver
<source>
  @type forward
  port 24224
  bind 0.0.0.0
</source>

# Назначение: Вывод логов в stdout (для демонстрации)
<match docker.**>
  @type stdout
</match>
```

#### Обработка многострочных логов в `fluentd`

Для корректного парсинга многострочных записей (например, stack trace) используется плагин `multiline`.

```conf
<filter docker.**>
  @type parser
  key_name log
  <parse>
    @type multiline
    # Новая запись начинается, например, с даты
    format_firstline /^\d{4}-\d{2}-\d{2}/
    # Формат первой строки для извлечения полей
    format1 /^(?<time>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}\.\d{3}) (?<level>\w+) (?<message>.*)/ 
  </parse>
</filter>
```

## Дополнительная информация

Использование лог-драйверов — одна из двух основных архитектур для централизации логов Docker. Она проста, но менее надежна по сравнению с **агентным подходом**.

- **Архитектура с лог-драйвером**: `Docker → Log Driver → Сеть → Приемник`. Проблемы с сетью или приемником могут привести к потере логов.
- **Архитектура с агентом**: `Docker → json-file → Агент → Сеть → Приемник`. Docker всегда пишет логи на локальный диск. Отдельный агент (например, Filebeat или Fluentd) читает эти файлы и отвечает за их надежную доставку, включая буферизацию и повторные отправки.

Агентный подход является **рекомендуемым для production-систем** благодаря своей надежности и гибкости.
