# Паттерн "Multi-Process" в Docker

## 1. Определения и философия Docker

### Философия "Один процесс на контейнер"

Основной и рекомендуемый подход к использованию Docker — **один процесс на контейнер**. Это означает, что каждый контейнер должен иметь одну основную задачу (например, запуск веб-сервера, базы данных или приложения).

**Преимущества этого подхода:**

- **Простота**: Легко отслеживать, что делает контейнер.
- **Масштабируемость**: Можно независимо масштабировать отдельные компоненты системы (например, добавить больше веб-серверов, не затрагивая базу данных).
- **Изоляция**: Сбой в одном компоненте не затрагивает напрямую другие.
- **Прозрачность**: Логи контейнера относятся к одному конкретному процессу.

### Паттерн "Multi-Process Container"

**Multi-Process Container** — это контейнер, в котором намеренно запускается и управляется несколько процессов одновременно. Это считается **анти-паттерном** или исключением, которое следует применять с осторожностью.

**Когда это может быть необходимо:**

- **Миграция устаревших (legacy) приложений**, которые не были спроектированы для разделения на микросервисы.
- **Тесно связанные компоненты**, которые не имеют смысла друг без друга (например, веб-сервер и вспомогательный скрипт для него).

## 2. Основная проблема: PID 1 и сбор логов

Ключевая проблема многопроцессных контейнеров заключается в том, как Docker управляет процессами и логами.

- **Docker отслеживает только PID 1**: Жизненный цикл контейнера привязан к его основному процессу (PID 1). Как только этот процесс завершается, Docker останавливает контейнер.
- **Логи `STDOUT`/`STDERR` только от PID 1**: Команда `docker logs` собирает стандартные потоки вывода (`STDOUT` и `STDERR`) только от процесса с PID 1.

Если ваш основной процесс запускает дочерние процессы, их вывод будет потерян для системы логирования Docker, а сами они могут превратиться в "зомби", если родительский процесс (PID 1) не умеет корректно ими управлять.

## 3. Практические сценарии реализации

### Сценарий 1: Использование легковесного супервизора (Рекомендуемый)

Самое надежное и правильное решение — использовать легковесный менеджер процессов (супервизор), такой как **`supervisord`**, `runit` или `s6`. Супервизор запускается как PID 1, а уже он управляет запуском, мониторингом и перезапуском дочерних процессов.

**Как это решает проблему:**
- **Управление процессами**: `supervisord` берет на себя роль `init`-системы, корректно обрабатывая дочерние процессы.
- **Агрегация логов**: `supervisord` собирает `STDOUT` и `STDERR` всех управляемых им приложений и направляет их в свои собственные потоки вывода. Поскольку `supervisord` является процессом с PID 1, `docker logs` видит все, что выводит супервизор.

**Пример реализации с `supervisord`:**

**`Dockerfile`:**
```dockerfile
FROM ubuntu:22.04

# Устанавливаем supervisor и ваши сервисы
RUN apt-get update && apt-get install -y supervisor nginx

# Копируем файлы приложений и конфигурацию supervisor
COPY supervisord.conf /etc/supervisor/conf.d/supervisord.conf
COPY my-app /usr/local/bin/my-app

# CMD запускает supervisord, который становится PID 1
CMD ["/usr/bin/supervisord", "-c", "/etc/supervisor/conf.d/supervisord.conf"]
```

**`supervisord.conf`:**
```ini
[supervisord]
nodaemon=true ; Запускаем supervisord на переднем плане (критично для Docker)

[program:nginx]
command=/usr/sbin/nginx -g "daemon off;"
autostart=true
autorestart=true
stdout_logfile=/dev/stdout ; Направляем stdout процесса в stdout supervisord
stdout_logfile_maxbytes=0
stderr_logfile=/dev/stderr ; Направляем stderr процесса в stderr supervisord
stderr_logfile_maxbytes=0

[program:my_app]
command=/usr/local/bin/my-app
autostart=true
autorestart=true
stdout_logfile=/dev/stdout
stdout_logfile_maxbytes=0
stderr_logfile=/dev/stderr
stderr_logfile_maxbytes=0
```

### Сценарий 2: Простое перенаправление потоков (Не рекомендуется)

Это "быстрый и грязный" метод, который можно использовать для отладки, но **не для production**. Он заключается в ручном перенаправлении потоков вывода дочерних процессов на потоки процесса с PID 1.

**Пример `entrypoint.sh`:**
```bash
#!/bin/bash

# Запускаем приложение в фоне, перенаправляя его stdout/stderr
# на stdout/stderr процесса entrypoint (который является PID 1)
./my-app-1 > /proc/1/fd/1 2>/proc/1/fd/2 &

# Запускаем второй процесс
./my-app-2 > /proc/1/fd/1 2>/proc/1/fd/2 &

# Ожидаем завершения любого из фоновых процессов
wait -n
```
**Недостатки**: Этот скрипт не решает проблему "зомби-процессов", не управляет перезапуском упавших сервисов и не обрабатывает корректно сигналы от Docker (`SIGTERM`).

## 4. Дополнительная информация

### Сравнение с запуском `systemd`

Не следует путать использование легковесного супервизора с попыткой запустить полноценный `systemd` внутри контейнера. Запуск `systemd` как PID 1 — еще более сильный анти-паттерн, так как требует небезопасного режима `--privileged` и нарушает все принципы изоляции Docker.

> Подробнее об этом: **[Запуск systemd в Docker: анти-паттерн и его решения](../docker_systemd.md)**
