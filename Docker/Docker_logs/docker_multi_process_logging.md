# Паттерн "Multi-Process" в Docker

## Определения

### Философия "Одна микрослужба на контейнер"

В 2026 году классический подход "один процесс на контейнер" эволюционировал в концепцию **один функциональный блок (микрослужба) на контейнер**. Это означает, что запуск нескольких тесно связанных процессов (например, PHP-FPM + Nginx или Node.js + вспомогательный sidecar-агент) внутри одного контейнера считается допустимым, если они разделяют один жизненный цикл.

**Преимущества этого подхода:**
- **Снижение сетевых накладных расходов**: Общение между процессами через Unix-сокеты или `localhost`.
- **Атомарность**: Вы деплоите и масштабируете функционально завершенный узел.
- **Упрощение инфраструктуры**: Меньше контейнеров для управления в простых окружениях (Docker Compose).

### Проблема PID 1: Зомби и сигналы

Запуск нескольких процессов напрямую (через shell-скрипт) порождает две критические проблемы:
1.  **Процессы-зомби (Zombies)**: Процесс с PID 1 обязан "пожинать" (reap) дочерние процессы после их завершения. Обычные приложения или shell-скрипты этого не делают, что ведет к переполнению таблицы процессов.
2.  **Проброс сигналов**: При выполнении `docker stop` Docker отправляет `SIGTERM` только процессу с PID 1. Если это shell-скрипт, он не пробросит сигнал дочерним процессам, что приведет к их принудительному убийству (`SIGKILL`) через 10 секунд.

## Основные концепции

Для корректной работы многопроцессных контейнеров необходимо использовать **Init-систему** или **Супервизор**.

### Инструменты управления процессами (2026)

| Инструмент | Особенности | Вердикт 2026 |
| :--- | :--- | :--- |
| **Tini (`--init`)** | Встроен в Docker. Решает проблему зомби и сигналов для ОДНОГО приложения. | **Стандарт** для одиночных приложений. |
| **s6-overlay** | Специально для контейнеров. Поддерживает зависимости, этапы инициализации и префиксацию логов. | **Выбор для Prod** при запуске 2+ процессов. |
| **Supervisord** | Универсальный, написан на Python. Увеличивает размер образа. | **Legacy.** Использовать только при наличии готовых конфигов. |

## Практические сценарии

### Сценарий 1: Использование s6-overlay v3 (Рекомендуемый)

`s6-overlay` — это набор скриптов и бинарников, которые превращают контейнер в полноценную, но легкую среду управления процессами.

**Пример Dockerfile (на базе Alpine):**

```dockerfile
FROM alpine:3.20

# Установка s6-overlay
ADD https://github.com/just-containers/s6-overlay/releases/download/v3.2.0.2/s6-overlay-noarch.tar.xz /tmp
ADD https://github.com/just-containers/s6-overlay/releases/download/v3.2.0.2/s6-overlay-x86_64.tar.xz /tmp
RUN tar -C / -Jxpf /tmp/s6-overlay-noarch.tar.xz && \
    tar -C / -Jxpf /tmp/s6-overlay-x86_64.tar.xz

# Настройка сервисов (структура s6-rc)
COPY etc/s6-overlay/s6-rc.d/user/contents.d/nginx /etc/s6-overlay/s6-rc.d/user/contents.d/
COPY services/nginx-run /etc/s6-overlay/s6-rc.d/nginx/run

ENTRYPOINT ["/init"]
```

**Особенности s6 для логирования:**
- Автоматически направляет `stdout/stderr` всех сервисов в логи контейнера.
- Позволяет добавлять префиксы к логам каждого процесса для удобства фильтрации.

### Сценарий 2: Использование Tini для одиночных процессов

Если вам нужно запустить один процесс, который порождает "сирот" (например, Java или Python с воркерами), используйте флаг `--init` или `tini`.

```bash
docker run --init my-python-app
# → Docker запускает tini как PID 1, который корректно управляет вашим приложением.
```

### Сценарий 3: Агрегация логов в Supervisord

Если используется `supervisord`, критически важно перенаправлять логи в `/dev/stdout`.

```ini
[program:app]
command=/usr/bin/app
stdout_logfile=/dev/stdout
stdout_logfile_maxbytes=0
stderr_logfile=/dev/stderr
stderr_logfile_maxbytes=0
```

## Рекомендации по логированию (2026)

1.  **JSON везде**: Все процессы внутри контейнера должны выводить логи в JSON.
2.  **Префиксация**: В многопроцессном режиме добавляйте имя процесса в начало строки лога (например, `[nginx] { "msg": "..." }`). Это позволяет парсерам (Vector, Alloy) легко разделять потоки.
3.  **Симлинки**: Если приложение умеет писать только в файлы, создайте симлинки:
    `RUN ln -sf /dev/stdout /var/log/nginx/access.log`.
