# Управление ротацией логов Docker

## Определения

**Ротация логов** — процесс управления файлами журналов для предотвращения их бесконтрольного роста. Включает архивацию, сжатие и удаление старых записей для оптимизации использования дискового пространства.

## Базовые концепции

По умолчанию Docker использует драйвер `json-file`, который записывает логи в формате JSON на диск. Без настройки ротации эти файлы растут неограниченно, что может привести к полному заполнению диска (Disk Exhaustion) и отказу Docker Engine или всей ОС.

### Основные драйверы для локального хранения

*   **`json-file`**: Стандартный драйвер. Записывает логи в текстовом формате. Не имеет ротации по умолчанию, требует ручной настройки `max-size` и `max-file`.
*   **`local`**: Оптимизированный драйвер (рекомендуется с версии 20.10+). Использует внутренний бинарный формат для повышения производительности и имеет **встроенную ротацию** (по умолчанию: 100 МБ на файл, хранение 5 файлов).

### Двойное логирование (Dual Logging)

С версии Docker 18.09 представлена функция **Dual Logging**. Она позволяет использовать команду `docker logs` даже при использовании внешних драйверов (например, `syslog`, `gelf`, `splunk`), которые обычно не поддерживают локальное чтение логов.
*   **Механизм**: Docker параллельно записывает логи в локальное хранилище (используя драйвер `local` или `json-file`) и во внешний приемник.
*   **Преимущество**: Сохранение возможности быстрой отладки через CLI при наличии централизованного сбора логов.

## Практические сценарии

### Сценарий 1: Глобальная настройка через `daemon.json`

Это рекомендуемый способ, так как он обеспечивает защиту всех новых контейнеров "из коробки".

**Настройка в `/etc/docker/daemon.json`:**
```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3",
    "compress": "true"
  }
}
```

*   `max-size`: Максимальный размер одного файла (например, `10m`, `50k`, `1g`).
*   `max-file`: Количество архивных файлов (ротационных копий).
*   `compress`: Сжатие ротированных логов (gzip). Позволяет экономить до 90% места для старых записей.

**Применение изменений:**
1.  Перезапуск демона: `sudo systemctl restart docker` # → OK
2.  **Важно:** Изменения коснутся только **новых** контейнеров. Существующие контейнеры нужно пересоздать:
    ```bash
    docker-compose up -d --force-recreate
    ```

### Сценарий 2: Настройка для конкретного контейнера

Если для определенного приложения требуются специфические лимиты (например, хранить больше логов для БД).

**Через Docker CLI:**
```bash
docker run -d \
  --log-driver json-file \
  --log-opt max-size=50m \
  --log-opt max-file=10 \
  --name my_app nginx
```

**Через Docker Compose:**
```yaml
services:
  app:
    image: my_app:latest
    logging:
      driver: "json-file"
      options:
        max-size: "20m"
        max-file: "5"
```

### Сценарий 3: Проверка и диагностика

**Проверка глобальных настроек демона:**
```bash
docker info --format '{{.LoggingDriver}}'
# → json-file
docker info --format '{{.LogOpts}}'
# → map[max-file:3 max-size:10m]
```

**Проверка настроек конкретного контейнера:**
```bash
docker inspect --format '{{.HostConfig.LogConfig}}' <container_id>
# → {json-file map[max-file:3 max-size:10m]}
```

**Поиск самых "тяжелых" логов на диске (Linux):**
```bash
sudo du -hs /var/lib/docker/containers/*/*-json.log | sort -rh | head -n 5
```

### Сценарий 4: Экстренная очистка логов

Если диск уже переполнен, можно обнулить файлы без остановки контейнеров.
*Внимание: `docker logs` для этого контейнера станет пустым.*

```bash
# Обнуление всех json-логов на хосте
sudo truncate -s 0 /var/lib/docker/containers/*/*-json.log
```

## Дополнительная информация

### Режим `non-blocking` и буферизация

В высоконагруженных системах стандартный (`blocking`) режим записи может замедлять работу приложения, если диск не успевает обрабатывать операции записи.

```json
"log-opts": {
  "mode": "non-blocking",
  "max-buffer-size": "4m"
}
```
*   **Blocking (по умолчанию)**: Приложение ждет, пока лог будет записан на диск. Гарантирует доставку лога, но может вызвать "фризы" приложения.
*   **Non-blocking**: Логи пишутся в промежуточный буфер. Если буфер переполнен (например, при аномальном всплеске логов), новые записи **отбрасываются**. Это критически важно для обеспечения стабильности приложения ценой частичной потери логов.

### Сравнение подходов к ротации

| Критерий | Встроенная ротация Docker | Внешний `logrotate` |
| :--- | :--- | :--- |
| **Надежность** | **Высокая.** Реализовано на уровне Docker Engine. | **Средняя.** Риск потери данных или повреждения JSON при использовании `copytruncate`. |
| **Производительность** | **Высокая.** Нет накладных расходов на внешние процессы. | **Низкая.** Требует копирования файлов при ротации. |
| **Удобство** | Декларативно в `daemon.json` или Compose. | Требует настройки дополнительных конфигурационных файлов в ОС. |
| **Гибкость** | Только по размеру файла. | По времени, по размеру, выполнение скриптов (post-rotate). |

**Рекомендация:** В 99% случаев используйте встроенную ротацию Docker. Внешний `logrotate` допустим только при очень специфических требованиях безопасности или необходимости сложной постобработки архивных файлов.
