# Управление ротацией логов Docker

## Определения

**Ротация логов** — процесс управления файлами журналов для предотвращения их бесконтрольного роста. Включает архивацию, сжатие и удаление старых записей для оптимизации использования дискового пространства.

**Disk Exhaustion** — состояние, при котором лог-файлы контейнеров заполняют всё доступное дисковое пространство на хосте, что приводит к отказу Docker Engine, падению контейнеров и potentially к недоступности ОС.

**Драйвер логирования (Logging Driver)** — компонент Docker Engine, отвечающий за запись потоков `STDOUT` и `STDERR` контейнера в определённое хранилище. Каждый драйвер имеет собственные параметры ротации или полное их отсутствие.

## Предпосылки

- Docker Engine **20.10+** (рекомендуется для Dual Logging и рекомендованного драйвера `local`)
- Доступ root или членство в группе `docker` для редактирования `/etc/docker/daemon.json`
- Достаточно дискового пространства на разделе, где смонтирован `/var/lib/docker` (или кастомный `data-root`)

**Проверка текущей конфигурации:**
```bash
docker info --format '{{.LoggingDriver}}'
# → json-file

docker info --format '{{.DockerRootDir}}'
# → /var/lib/docker
```

## Базовые концепции

### Механизм работы ротации

По умолчанию Docker использует драйвер `json-file`, который записывает логи в формате JSON на диск в директорию `/var/lib/docker/containers/<container_id>/`. Каждый контейнер имеет собственный лог-файл с именем `<container_id>-json.log`.

**Поток данных:**
```
Процесс в контейнере → STDOUT/STDERR → Docker Engine → Лог-драйвер → Локальный диск
```

Ротация работает по принципу ** filesize threshold**: когда текущий файл достигает размера `max-size`, Docker переименовывает его в `<container_id>-json.log.1` (или `.gz` при сжатии), создаёт новый файл и, если количество файлов превышает `max-file`, удаляет самый старый. Механизм аналогичен для драйвера `local`, но файлы хранятся в бинарном формате в поддиректории `local-logs/`.

**Важно:** Ротация выполняется демоном Docker, а не внешней утилитой. Это означает, что файл не переименовывается с отправкой сигнала приложению — Docker Engine просто закрывает текущий файл и открывает новый. Приложение продолжает писать в `STDOUT/STDERR`, и данные автоматически попадают в новый файл.

### Основные драйверы для локального хранения

*   **`json-file`**: Стандартный драйвер. Записывает логи в текстовом JSON-формате. **Не имеет ротации по умолчанию** — без явной настройки `max-size` и `max-file` файлы растут неограниченно. Поддерживает `docker logs`.
*   **`local`**: Оптимизированный драйвер (рекомендуется с версии 20.10+). Использует внутренний бинарный формат для повышения производительности и снижения расхода диска. Имеет **встроенную ротацию по умолчанию** (100 МБ на файл, 5 файлов) и включённое сжатие. Поддерживает `docker logs`.

**Сравнение драйверов:**

| Критерий | `json-file` | `local` |
| :--- | :--- | :--- |
| **Формат** | Текстовый JSON | Бинарный (protobuf) |
| **Ротация по умолчанию** | Отключена | Включена (100 MB / 5 файлов) |
| **Сжатие по умолчанию** | Отключено | Включено |
| **`docker logs`** | Да | Да |
| **Читаемость вручную** | Да (стандартные Unix-утилиты) | Нет (только через `docker logs`) |
| **Производительность записи** | Средняя | Высокая |
| **Расход диска** | Выше (JSON-обёртка на каждой строке) | Ниже (紧凑ный бинарный формат) |
| **Совместимость с агентами** | Прямое чтение файлов (tail) | Требует поддержки формата или Docker API |

**Рекомендация Docker (официальная):** Используйте `local` как драйвер по умолчанию для предотвращения Disk Exhaustion. `json-file` рекомендуется только для Kubernetes-сред (где ротация настраивается на уровне Kubelet) или когда требуется прямое чтение файлов внешними инструментами.

### Двойное логирование (Dual Logging)

С версии Docker 18.09 представлена функция **Dual Logging**. Она позволяет использовать команду `docker logs` даже при использовании внешних драйверов (например, `syslog`, `gelf`, `splunk`, `loki`), которые обычно не поддерживают локальное чтение логов.

*   **Механизм**: Docker параллельно записывает логи в локальный кэш (используя драйвер `local` или `json-file`) и во внешний приемник.
*   **Параметры кэша Dual Logging:**

| Параметр | Описание | Пример |
| :--- | :--- | :--- |
| `cache-disabled` | Отключение локального кэша. По умолчанию `false`. | `"cache-disabled": "true"` |
| `cache-max-size` | Максимальный размер файла кэша перед ротацией. | `"cache-max-size": "20m"` |
| `cache-max-file` | Количество файлов кэша. | `"cache-max-file": "5"` |
| `cache-compress` | Сжатие ротированных файлов кэша. | `"cache-compress": "true"` |

*   **Преимущество**: Сохранение возможности быстрой отладки через CLI при наличии централизованного сбора логов.

### Параметры драйвера `json-file`

| Параметр | Описание | Значение по умолчанию | Пример |
| :--- | :--- | :--- | :--- |
| `max-size` | Максимальный размер одного файла. Поддерживаются суффиксы `k`, `m`, `g`. | `-1` (неограниченно) | `10m`, `50k`, `1g` |
| `max-file` | Максимальное количество файлов. Работает только в паре с `max-size`. | `1` | `3`, `5`, `10` |
| `compress` | Сжатие ротированных файлов (gzip). Занимает до 90% меньше места для текстовых логов. | `false` | `"true"` |
| `labels` | Метки контейнера, включаемые в каждую запись лога (через запятую). | пусто | `"service,env"` |
| `labels-regex` | Регулярное выражение для фильтрации меток. | пусто | `"^service_.*"` |
| `env` | Переменные окружения, включаемые в логи. | пусто | `"APP_VERSION,HOSTNAME"` |
| `env-regex` | Регулярное выражение для фильтрации переменных окружения. | пусто | `"^APP_.*"` |

**Важно:** Все значения в `daemon.json` должны быть строками (в кавычках), включая числовые и булевы.

### Режим `non-blocking` и буферизация

В высоконагруженных системах стандартный (`blocking`) режим записи может замедлять работу приложения, если диск не успевает обрабатывать операции записи.

```json
"log-opts": {
  "mode": "non-blocking",
  "max-buffer-size": "4m"
}
```
*   **Blocking (по умолчанию)**: Приложение ждет, пока лог будет записан на диск. Гарантирует доставку лога, но может вызвать "фризы" приложения при проблемах с диском.
*   **Non-blocking**: Логи пишутся в промежуточный кольцевой буфер в оперативной памяти. Если буфер переполнен (например, при аномальном всплеске логов или недоступности внешнего драйвера), новые записи **отбрасываются** (принцип FIFO). Это критически важно для обеспечения стабильности приложения ценой частичной потери логов.

**Рекомендация по размеру буфера:** `4m` — достаточно для компенсации кратковременных сетевых задержек. Для высоконагруженных систем с炅ными пики рекомендуется `8m`–`16m`.

## Практические сценарии

### Сценарий 1: Глобальная настройка через `daemon.json`

Это рекомендуемый способ, так как он обеспечивает защиту всех новых контейнеров "из коробки".

**Настройка в `/etc/docker/daemon.json`:**
```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3",
    "compress": "true"
  }
}
```

**Рекомендуемые профили:**

| Сценарий | `max-size` | `max-file` | `compress` | Расход диска на контейнер |
| :--- | :--- | :--- | :--- | :--- |
| Разработка | `10m` | `3` | `false` | ~30 МБ |
| Продакшн (умеренный) | `10m` | `5` | `true` | ~50 МБ (сжатые) |
| Продакшн (высокий трафик) | `50m` | `5` | `true` | ~250 МБ (сжатые) |
| Базы данных / критичные сервисы | `100m` | `10` | `true` | ~1 ГБ (сжатые) |

**Применение изменений:**
1.  Перезапуск демона: `sudo systemctl restart docker` # → OK
2.  **Важно:** Изменения коснутся только **новых** контейнеров. Существующие контейнеры нужно пересоздать:
    ```bash
    docker-compose up -d --force-recreate
    ```

**Валидация:**
```bash
# Проверка глобальных настроек
docker info --format '{{.LoggingDriver}}'
# → json-file

docker info --format '{{.LogOpts}}'
# → map[compress:true max-file:3 max-size:10m]
```

### Сценарий 2: Настройка для конкретного контейнера

Если для определенного приложения требуются специфические лимиты (например, хранить больше логов для БД).

**Через Docker CLI:**
```bash
docker run -d \
  --log-driver json-file \
  --log-opt max-size=50m \
  --log-opt max-file=10 \
  --name my_app nginx
```

**Через Docker Compose:**
```yaml
services:
  app:
    image: my_app:latest
    logging:
      driver: "json-file"
      options:
        max-size: "20m"
        max-file: "5"
```

**Через Docker Compose (YAML-якорь для DRY):**
```yaml
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
    compress: "true"

services:
  api:
    image: my_api:latest
    logging: *default-logging

  worker:
    image: my_worker:latest
    logging: *default-logging
```

**Валидация:**
```bash
# Проверка настроек конкретного контейнера
docker inspect --format '{{.HostConfig.LogConfig}}' my_app
# → {json-file map[max-file:10 max-size:50m]}

# Проверка фактического пути к лог-файлу
docker inspect --format '{{.LogPath}}' my_app
# → /var/lib/docker/containers/<id>/<id>-json.log

# Проверка размера лог-файла
ls -lh $(docker inspect --format '{{.LogPath}}' my_app)
# → -rw-r----- 1 root root 4.2M ... /var/lib/docker/containers/<id>/<id>-json.log
```

### Сценарий 3: Проверка и диагностика

**Проверка глобальных настроек демона:**
```bash
docker info --format '{{.LoggingDriver}}'
# → json-file
docker info --format '{{.LogOpts}}'
# → map[max-file:3 max-size:10m]
```

**Проверка настроек конкретного контейнера:**
```bash
docker inspect --format '{{.HostConfig.LogConfig}}' <container_id>
# → {json-file map[max-file:3 max-size:10m]}
```

**Поиск самых "тяжелых" логов на диске (Linux):**
```bash
sudo du -hs /var/lib/docker/containers/*/*-json.log | sort -rh | head -n 5
```

**Проверка всех контейнеров с неограниченными логами (без `max-size`):**
```bash
for cid in $(docker ps -q); do
  driver=$(docker inspect --format '{{.HostConfig.LogConfig.Type}}' "$cid")
  opts=$(docker inspect --format '{{.HostConfig.LogConfig.Config}}' "$cid")
  name=$(docker inspect --format '{{.Name}}' "$cid")
  if [[ "$driver" == "json-file" ]] && [[ "$opts" != *"max-size"* ]]; then
    echo "WARNING: $name — ротация НЕ настроена"
  fi
done
```

**Мониторинг размера логов в реальном времени:**
```bash
watch -n 5 'docker ps --format "{{.ID}} {{.Names}}" | while read id name; do
  size=$(docker inspect --format "{{.LogPath}}" "$id" 2>/dev/null | xargs ls -lh 2>/dev/null | awk "{print \$5}")
  echo "$name: $size"
done'
```

### Сценарий 4: Экстренная очистка логов

Если диск уже переполнен, можно обнулить файлы без остановки контейнеров.
*Внимание: `docker logs` для этого контейнера станет пустым.*

```bash
# Обнуление всех json-логов на хосте
sudo truncate -s 0 /var/lib/docker/containers/*/*-json.log
```

**Более безопасный вариант — очистка с сохранением бэкапа:**
```bash
# Создание директории для бэкапов
sudo mkdir -p /tmp/docker-log-backup

# Копирование и обнуление каждого лог-файла
for logfile in /var/lib/docker/containers/*/*-json.log; do
  container_id=$(basename "$(dirname "$logfile")")
  sudo cp "$logfile" "/tmp/docker-log-backup/${container_id}-backup-$(date +%s).log"
  sudo truncate -s 0 "$logfile"
done

echo "Бэкапы логов сохранены в /tmp/docker-log-backup/"
```

**Для контейнера с драйвером `local`:**
```bash
sudo truncate -s 0 /var/lib/docker/containers/*/local-logs/*
```

### Сценарий 5: Переключение с `json-file` на `local`

Если на хосте уже работают контейнеры с `json-file` и вы хотите перейти на более эффективный `local`:

1.  Настройте `daemon.json`:
    ```json
    {
      "log-driver": "local",
      "log-opts": {
        "max-size": "10m",
        "max-file": "5",
        "compress": "true"
      }
    }
    ```
2.  Перезапустите Docker: `sudo systemctl restart docker`
3.  **Пересоздайте** все контейнеры (драйвер фиксируется при создании):
    ```bash
    docker-compose up -d --force-recreate
    ```

**Важно:** Старые лог-файлы в формате `json-file` не удаляются автоматически. Удалите их вручную после проверки:
```bash
sudo rm /var/lib/docker/containers/*/*-json.log*
```

## Дополнительная информация

### Сравнение подходов к ротации

| Критерий | Встроенная ротация Docker | Внешний `logrotate` |
| :--- | :--- | :--- |
| **Надежность** | **Высокая.** Реализовано на уровне Docker Engine. | **Средняя.** Риск потери данных или повреждения JSON при использовании `copytruncate`. |
| **Производительность** | **Высокая.** Нет накладных расходов на внешние процессы. | **Низкая.** Требует копирования файлов при ротации. |
| **Удобство** | Декларативно в `daemon.json` или Compose. | Требует настройки дополнительных конфигурационных файлов в ОС. |
| **Гибкость** | Только по размеру файла. | По времени, по размеру, выполнение скриптов (post-rotate). |
| **Совместимость с агентами** | `json-file` — прямое чтение; `local` — через API. | Риск повреждения файла при копировании. |

**Рекомендация:** В 99% случаев используйте встроенную ротацию Docker. Внешний `logrotate` допустим только при очень специфических требованиях безопасности или необходимости сложной постобработки архивных файлов.

### Типичные ошибки и решения

| Ошибка / Симптом | Возможная причина | Решение |
| :--- | :--- | :--- |
| **Диск заполнен, логи контейнеров >10 ГБ** | Ротация не настроена (`json-file` по умолчанию без `max-size`). | Настройте `max-size` и `max-file` в `daemon.json`. Пересоздайте контейнеры. |
| **`docker logs` не показывает логи после ротации** | Использование внешнего драйвера (syslog, fluentd) без Dual Logging. | Включите Dual Logging или переключитесь на `local`/`json-file`. |
| **`docker logs -f` зависает при `max-file=1`** | Известная проблема (moby#39235): при единственном файле Docker truncate + open с `O_TRUNC` не генерирует inotify-событие для `docker logs -f`. | Используйте `max-file` >= 2, или переключитесь на драйвер `local`. |
| **Контейнер "падает" с ошибкой "no space left on device"** | Лог-файлы заполнили диск. | Обнулите логи: `sudo truncate -s 0 /var/lib/docker/containers/*/*-json.log`. Настройте ротацию. |
| **После смены `daemon.json` логи старых контейнеров не ротируются** | Настройки применяются только к новым контейнерам. | Пересоздайте контейнеры: `docker-compose up -d --force-recreate`. |
| **Лог-агент (Promtail, Fluent Bit) не читает логи после переключения на `local`** | Бинарный формат `local` несовместим с парсером JSON. | Переключите агент на чтение через Docker API (socket) или обновите конфигурацию парсера. |
| **Сжатие (`compress`) не работает** | Значение `true` указано без кавычек в `daemon.json`. | Используйте строку: `"compress": "true"` (не `true` без кавычек). |

### Ограничения и известные проблемы

1.  **Драйвер фиксируется при создании контейнера.** Невозможно изменить драйвер логирования или параметры ротации для уже запущенного контейнера. Требуется пересоздание.
2.  **`max-file` без `max-size` игнорируется.** Параметр `max-file` работает только если задан `max-size`. Без него логи растут бесконечно.
3.  **Драйвер `local` нечитаем стандартными утилитами.** Файлы в бинарном формате нельзя читать через `cat`, `less`, `tail`. Используйте `docker logs` или агенты с поддержкой Docker API.
4.  **Docker Desktop (macOS/Windows):** Логирование работает через виртуальную машину. Настройки `daemon.json` хоста не применяются напрямую. Используйте UI Docker Desktop (Settings → Docker Engine) или `~/.docker/daemon.json`.
5.  **Ротация не уведомляет приложение.** В отличие от `logrotate` + `SIGHUP`, Docker Engine не отправляет сигнал процессу. Приложение продолжает писать в `STDOUT/STDERR`, и данные автоматически попадают в новый файл. Это безопасно для большинства приложений, но некоторые программы (например, некоторые версии Java-агентов) могут требовать явного переоткрытия файлов.
6.  **Кольцевой буфер в `non-blocking` режиме.** При переполнении буфера данные теряются без уведомления. Для критичных логов (аудит, безопасность) используйте `blocking` режим или агентную сборку с буферизацией на диске.

### Лучшие практики

1.  **Всегда настраивайте ротацию.** Даже для dev-окружения: `max-size: 10m`, `max-file: 3` — минимальная защита.
2.  **Используйте `local` вместо `json-file`** для новых部署, если не требуется прямое чтение файлов внешними инструментами.
3.  **Включайте `compress: true`** — экономия до 90% места для текстовых логов.
4.  **Для критичных сервисов увеличивайте лимиты:** `max-size: 100m`, `max-file: 10` — чтобы хранить достаточно истории для отладки.
5.  **Используйте YAML-якоря в Compose** для дублирования конфигурации логирования между сервисами.
6.  **Настройте мониторинг размера логов** через Prometheus (`container_fs_writes_bytes_total`) или регулярные скрипты проверки.
7.  **Для централизованного сбора логов** комбинируйте встроенную ротацию Docker с агентом (Grafana Alloy, Vector, Fluentd). Подробнее: **[Агентный сбор логов Docker](./docker_agent_based_logging.md)**.
