# Управление ротацией логов Docker

## Определения

**Ротация логов** — это процесс управления файлами журналов для предотвращения их бесконтрольного роста. Он включает периодическую архивацию, сжатие, переименование и удаление старых файлов логов для освобождения дискового пространства.

## Базовые концепции

При использовании лог-драйверов, сохраняющих логи на локальный диск (по умолчанию `json-file`), файлы логов могут быстро расти и занимать все доступное дисковое пространство, что приводит к сбоям в работе системы.

Существует два основных подхода к управлению ротацией логов Docker:

1. **Встроенный механизм Docker**: Конфигурация параметров ротации непосредственно для лог-драйвера. **Это рекомендуемый подход.**
2. **Внешний инструмент (`logrotate`)**: Использование стандартной системной утилиты Linux для управления файлами логов.

## Практические сценарии

### Сценарий 1: Встроенная ротация Docker (Рекомендуемый)

Docker предоставляет встроенные опции для драйверов `json-file` и `local`, позволяющие автоматически управлять ротацией. Этот метод более надежен и производителен, чем `logrotate`.

**Конфигурация для всех контейнеров (`/etc/docker/daemon.json`):**

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

* `max-size`: Максимальный размер одного файла логов (например, `10m` для 10 мегабайт).
* `max-file`: Максимальное количество файлов логов, которые нужно хранить.

После изменения файла необходимо перезапустить Docker: `sudo systemctl restart docker`.

**Конфигурация для отдельного контейнера:**

```bash
docker run -it --log-opt max-size=10m --log-opt max-file=3 nginx
```

### Сценарий 2: Использование `logrotate` (Альтернативный)

Этот метод может быть полезен для унификации управления логами, если в вашей системе `logrotate` уже активно используется для других служб.

**Пример конфигурации (`/etc/logrotate.d/docker-logs`):**

```
/var/lib/docker/containers/*/*.log {
    rotate 5
    daily
    compress
    missingok
    copytruncate
}
```

**Разбор ключевых параметров:**

* `rotate 5`: Хранить 5 последних архивных файлов.
* `daily`: Производить ротацию ежедневно.
* `compress`: Сжимать ротированные файлы (обычно с помощью `gzip`).
* `missingok`: Не выдавать ошибку, если файлы логов отсутствуют.
* `copytruncate`: **Критически важный параметр.** Он указывает `logrotate` сначала скопировать содержимое файла, а затем обрезать (очистить) исходный файл до нулевого размера. Это необходимо, так как Docker держит постоянный файловый дескриптор открытым. Без этой опции Docker продолжит писать в переименованный файл, и логи будут теряться.

## Дополнительная информация

### Сравнение подходов

| Критерий | Встроенная ротация Docker | Внешний `logrotate` |
| :--- | :--- | :--- |
| **Надежность** | **Высокая.** Ротация происходит атомарно внутри Docker. | **Средняя.** `copytruncate` может привести к потере логов, записанных в момент между копированием и обрезкой файла. |
| **Производительность** | **Высокая.** Не требует копирования больших файлов. | **Низкая.** Копирование больших файлов логов создает высокую нагрузку на I/O. |
| **Простота** | **Высокая.** Является частью конфигурации Docker. | **Средняя.** Требует создания и настройки отдельной конфигурации `logrotate`. |
| **Гибкость** | **Низкая.** Ротация только по размеру. | **Высокая.** Ротация по дате, размеру, выполнение скриптов (`post-rotate`), гибкое управление сжатием. |

**Итог:** Для большинства сценариев **настоятельно рекомендуется использовать встроенный механизм ротации Docker** как более простой, надежный и производительный. `logrotate` следует рассматривать только в случаях, когда требуется его специфическая гибкость (например, ротация по дате).

Для детального описания `logrotate` в контексте Linux см. **[Ротация логов в Linux](../../Linux/SystemAdministration/Logging/logging_overview.md#ротация-логов-logrotate)**.
