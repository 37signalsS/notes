# Log Injection и безопасность логов в Docker

**Актуально для:** Docker Engine 29.x; классификации CAPEC-93, CWE-93, CWE-117

## Определения

**Log Injection (инъекция в логи)** — атака (CAPEC-93: Log Injection-Tampering-Forging), при которой злоумышленник внедряет в поток логов управляющие символы или фальшивые записи, чтобы скрыть следы атаки, ввести аналитика в заблуждение или повредить автоматическую обработку логов.

**Log Forging (подделка записей)** — частный случай: внедрение символов новой строки (CRLF, `\r\n`, `\n`) для создания ложных записей, выглядящих как легитимные события (например, «User admin logged in»).

**CWE-93 (CRLF Injection)** — нейтрализация CRLF-последовательностей: продукт использует CRLF как разделитель записей, но не фильтрует их во входных данных.

**CWE-117 (Improper Output Neutralization for Logs)** — нейтрализация вывода для логов: продукт записывает в лог данные, управляемые пользователем, без экранирования управляющих символов.

**ANSI-escape инъекция** — внедрение escape-последовательностей терминала (`\x1b[...`) в лог: при просмотре в терминале атакующий может очистить экран, подменить вывод или вывести из строя эмулятор терминала (terminal emulation attack).

## Предпосылки

- Понимание, что **все данные, попадающие в лог приложения, потенциально управляются атакующим**: HTTP-заголовки (`User-Agent`, `X-Forwarded-For`), URL-параметры, имена пользователей, имена файлов
- **Docker-контейнер** с лог-драйвером `json-file`/`local` (стандартный путь логирования)
- **Централизованное хранилище** (Loki, ELK) и/или терминал для просмотра логов — поверхности, где инъекция реализуется

**Ключевой факт для диагностики:** драйвер `json-file` JSON-кодирует каждую строку, поэтому управляющие символы в сыром файле `*-json.log` хранятся в escaped-виде (`\r` — два символа «обратный слеш + r», ESC — как `\u001b`). Живые управляющие байты появляются только после декодирования записи — в выводе `docker logs`, в агентах (Vector, Fluent Bit) и в хранилище. Поиск по сырым файлам должен использовать escaped-паттерны.

**Быстрая проверка текущих логов на инъекции:**
```bash
# CR-подмена в json-file логах (CR хранится как escaped-последовательность \r)
grep -rP '\\r' /var/lib/docker/containers/*/*-json.log | head -5

# ANSI-escape в json-file логах (ESC хранится как \u001b)
grep -rP '\\u001[bB]' /var/lib/docker/containers/*/*-json.log | head -5

# То же по декодированному потоку docker logs (здесь — сырые байты)
docker logs <container> | grep -P '\r'
docker logs <container> | grep -P '\x1b\['

# Подозрительно длинные строки (попытка переполнения/обфускации)
awk 'length($0) > 10000' /var/lib/docker/containers/*/*-json.log | head -5
```

## Базовые концепции

### Механизм атаки

**1. CRLF-форжинг.** Приложение логирует пользовательский ввод без санации:

```python
# УЯЗВИМО
logger.info(f"Login attempt for user: {username}")
```

Атакующий передаёт username `admin\r\n2026-10-04T12:00:00 INFO User admin logged in successfully`. В текстовом логе появляются две «законные» записи:

```
2026-10-04T11:59:59 INFO Login attempt for user: admin
2026-10-04T12:00:00 INFO User admin logged in successfully
```

Вторая запись — подделка. При расследовании инцидента она маскирует неудачную попытку входа.

**2. ANSI-escape инъекция.** В лог попадает `\x1b[2J` (очистка экрана) или `\x1b[31m` (красный цвет). При `tail -f` в терминале: экран очищается, настоящие записи атаки исчезают из вида; некоторые последовательности могут повредить эмулятор терминала.

**3. XSS через веб-интерфейс логов.** Если логи отображаются в веб-UI (Kibana, Grafana, самописный дашборд) без экранирования, внедрение `<script>` в запись лога даёт XSS аналитика (CAPEC-93, техника script injection).

**4. CSV/Excel formula injection.** Логи, экспортируемые в CSV: запись вида `=cmd|'/C calc'!A0` при открытии в Excel выполняет формулу (техника из CAPEC-93).

**5. Искажение статистики.** Мусорные записи «сбивают» парсеры и метрики (OWASP: «skewing the log file statistics»).

**6. Подделка временных меток.** Атакующий может встроить в текст сообщения ложную метку времени. Важно различать её и реальную метку записи: драйвер `json-file` присваивает полю `time` время приёма строки демоном, а `docker logs --timestamps` показывает именно его. Расхождение встроенной в текст метки с полем `time` — сигнал форжинга.

### Специфика Docker

- **json-file драйвер оборачивает каждую строку в JSON** — внедрение `\n` в сообщение приложения создаёт отдельную JSON-запись, а не слияние строк. Это ограничивает форжинг «новыми строками», но **не защищает** от `\r` и ANSI-последовательностей внутри строки: в сыром файле они хранятся escaped (`\r`, `\u001b`), а при декодировании (`docker logs`, агент, хранилище) снова становятся живыми управляющими байтами.
- **Где проявляется CR-форжинг.** При выводе `docker logs` и в текстовых логах терминал на `\r` возвращает курсор в начало строки и перезаписывает её. `cat` сырого `*-json.log` файла показывает `\r` как два литеральных символа — перезаписи не происходит.
- **TTY-контейнеры** (`tty: true`) передают поток «сырым»: все escape-последовательности приложения попадают в лог-файл как есть.
- **journald-драйвер** записывает сообщение в systemd-journal без санации; `journalctl` рендерит управляющие символы, инъекция переживает транспорт в journald и во все потребители вывода `journalctl`.
- **local-драйвер** хранит записи в бинарном формате с фреймингом; управляющие символы сохраняются «как есть» — поиск по файлу невозможен, диагностика только через `docker logs`.
- **Агенты и хранилища** — инъекция переживает транспорт: если агент не санирует, поддельная запись попадает в Loki/ELK и отображается аналитику.
- **Ротация не санирует.** Ротированные и сжатые файлы сохраняют внедрённое содержимое; ротация управляет объёмом, а не целостностью (см. [Ротация логов](./docker_log_rotation.md)).

## Практические сценарии

### Сценарий 1: Демонстрация инъекции (стенд)

```bash
# Уязвимое приложение: логирует аргумент как есть
docker run --rm -d --name vuln-app alpine sh -c \
  'while true; do echo "user action: $(cat /tmp/input 2>/dev/null)"; sleep 1; done'

# Атакующий: CR-подмена (при выводе строка перезапишется)
docker exec vuln-app sh -c 'printf "ok\rINFO system shutdown completed\n" > /tmp/input'

# Наблюдаем: терминал перезаписывает строку после \r
docker logs vuln-app
# → INFO system shutdown completed
#   (фактически в потоке: "user action: ok\rINFO system shutdown completed")

# Валидация: cat -v показывает управляющие символы в видимом виде (^M = CR)
docker logs vuln-app | cat -v
# → user action: ok^MINFO system shutdown completed

# Очистка стенда
docker rm -f vuln-app
```

### Сценарий 2: Санация на стороне приложения

```python
# Python: нейтрализация управляющих символов перед записью
import re

def sanitize(message: str) -> str:
    # Заменяем CR/LF и управляющие символы (кроме \t) на escaped-вид
    return re.sub(r'[\x00-\x08\x0b\x0c\x0e-\x1f\x7f\r\n]',
                  lambda m: f'\\x{m.group(0).hex()}', message)

logger.info("user action: %s", sanitize(user_input))

# sanitize("ok\rINFO system shutdown completed")
# → 'ok\x0dINFO system shutdown completed'
```

```go
// Go: strings.Map или regexp для вырезания control chars
import "regexp"

var controlChars = regexp.MustCompile(`[\x00-\x08\x0b\x0c\x0e-\x1f\x7f\r\n]`)

func sanitize(s string) string { return controlChars.ReplaceAllString(s, "") }
```

### Сценарий 3: Санация на стороне агента (Vector VRL)

```yaml
# vector.yaml — нейтрализация управляющих символов перед отправкой в Loki
transforms:
  sanitize:
    type: remap
    inputs: [docker]
    source: |
      .message = replace(.message, r'[\x00-\x08\x0b\x0c\x0e-\x1f\x7f\r\n]', '', ignore_empty: false)
      .message = string!(.message)
```

**Fluent Bit** (parser с regex-фильтром):
```ini
# fluent-bit.conf
[FILTER]
    Name   grep
    Match  docker.*
    Exclude log .*[\x1b].*
```

**Ограничение Fluent Bit grep:** `Exclude` отбрасывает запись целиком — легитимные логи, содержащие ESC, тоже будут потеряны. Для точечной санации (замена символов внутри сообщения) используйте Lua-фильтр или Vector.

### Сценарий 4: Обнаружение инъекции в хранилище

```bash
# Поиск CR-подмены в json-file логах (записи с escaped \r внутри)
grep -rlP '\\r' /var/lib/docker/containers/*/*-json.log

# Поиск ANSI-escape в json-file логах (ESC хранится как \u001b)
grep -rlP '\\u001[bB]' /var/lib/docker/containers/*/*-json.log

# Поиск ANSI-escape в Loki (LogQL; агент уже декодировал JSON — байты живые)
# {job="docker"} |~ "\x1b\["

# Поиск подозрительных «успешных» входов сразу после неудачных (форжинг)
# {job="docker"} |~ "logged in successfully"
```

**Корреляция временных меток:** сравнивайте метку времени записи (поле `time` в json-file, `docker logs --timestamps`) с метками, встроенными в текст сообщения. Подделка видна как несовпадение: запись «успешного входа» с текстовой меткой, расходящейся с `time` записи или с соседними записями того же потока.

### Сценарий 5: Безопасный просмотр логов

```bash
# Просмотр с экранированием управляющих символов (cat -v)
docker logs <container> | cat -v

# Или sed: замена ESC на видимый вид
docker logs <container> | sed 's/\x1b/<ESC>/g'

# grep с подавлением ANSI
docker logs <container> | sed 's/\x1b\[[0-9;]*m//g' | grep ERROR
```

### Сценарий 6: Защита от прямой подделки файлов (FIM)

CAPEC-93 включает технику «Manipulate Log Files» — прямую модификацию лог-файлов при доступе к хосту. Санация приложения здесь не помогает; нужна детекция на уровне файловой системы:

```bash
# auditd: мониторинг записи и изменения атрибутов в лог-файлах контейнеров
auditctl -w /var/lib/docker/containers/ -p wa -k docker_logs

# Просмотр событий прямой модификации
ausearch -k docker_logs --interpret | tail -20

# AIDE: контроль целостности снапшота логов
aide --check | grep -i docker
```

Учитывайте ротацию: при ротации файлов правила auditd и базлайны AIDE нужно обновлять на новые имена файлов, иначе контроль разорвётся.

## Дополнительная информация

### Mitigations (сводка)

| Уровень | Мера | Эффект |
| :--- | :--- | :--- |
| **Приложение** | Валидация/allowlist входных данных; экранирование CRLF и control-символов перед записью (CWE-93/117) | Корневое устранение |
| **Приложение** | Structured logging (JSON) — поля сериализуются библиотекой, а не конкатенацией строк | Устраняет форжинг через разделители |
| **Агент** | Санация в pipeline (Vector VRL `replace`, Fluent Bit grep/filter) | Защита транспорта и хранилища |
| **Просмотр** | `cat -v`, просмотрщики с экранированием escape-последовательностей | Блокирует терминал-атаки |
| **Хранилище** | Не рендерить сырые логи как HTML (XSS); экранировать при экспорте в CSV | Блокирует XSS и formula injection |
| **Доступ** | Строгий контроль доступа к лог-файлам и хранилищу (CAPEC-93 mitigation) | Защита целостности |
| **FIM** | auditd/AIDE на `/var/lib/docker/containers/` | Детекция прямой подделки файлов |
| **Процесс** | Статический анализ кода на log forging; security-ревью логирования | Профилактика |

### Troubleshooting

| Симптом | Диагностика | Решение |
| :--- | :--- | :--- |
| «Пропавшие» записи при `tail -f` / `docker logs` | `grep -P '\\r'` на json-file логе или `docker logs <c> \| grep -P '\r'` | Санация CR на стороне приложения/агента |
| Терминал «ломается» при просмотре логов | `grep -P '\\u001[bB]'` на json-file логе; `docker logs <c> \| grep -P '\x1b\['` | Просмотр через `cat -v`; санация ANSI |
| Логи портят дашборд/парсер | Поиск не-JSON записей в json-file логах | Structured logging; валидация парсера |
| Подозрительные «успешные» события | Корреляция `time` записи с метками в тексте, поиск дублей по времени | Расследование как инцидент безопасности |
| Инъекция не находится grep по файлам | Поиск ведётся по сырым escaped-паттернам вместо `\r`/`\u001b` либо по файлам `local`-драйвера | Исправить паттерн; для `local`-драйвера диагностировать через `docker logs` |

### Best Practices

1. **Никогда не логируйте пользовательский ввод «как есть»** — санируйте на границе приложения (allowlist > blocklist).
2. **Structured logging** — JSON-сериализация полей устраняет инъекцию через разделители строк.
3. **Не открывайте сырые логи в терминале** в production-расследованиях — используйте `cat -v` или UI с экранированием.
4. **Санируйте в агенте** как второй рубеж обороны (Vector/Fluent Bit), особенно перед отправкой в SIEM.
5. **Ограничивайте доступ** к `/var/lib/docker/containers/` и хранилищу логов — подделка записей возможна и напрямую (CAPEC-93: «Manipulate Log Files»); контролируйте целостность через auditd/AIDE.
6. **Маскируйте секреты** (пароли, токены) в логах — см. [маскирование в Vector](../../Vector/vrl_language.md) и [секреты в Docker](../Docker_security/secrets_management.md).
7. **Запускайте контейнеры без TTY** (`tty: false`), если приложение не требует интерактивного терминала — это отсекает поток сырых escape-последовательностей.

### Ограничения

1. **json-file драйвер не санирует** — он лишь оборачивает строки в JSON; `\r` и ANSI внутри строки сохраняются (в escaped-виде в файле, живыми — после декодирования).
2. **Санация в агенте — не панацея** — подделка уже произошла к моменту записи; корневая защита — в приложении.
3. **TTY-контейнеры** — полный поток escape-последовательностей; для безопасного логирования запускайте без TTY.
4. **Легитимные многострочные логи** (stack traces) содержат реальные переводы строк и разбиваются json-file драйвером на отдельные записи — не каждая многострочность является инъекцией; контекст (ошибка парсинга, корреляция по `time`) отличает их от форжинга.
5. **NUL-байты и не-UTF8** — некоторые шипперы и парсеры обрезают сообщение на `\x00`; драйвер json-file заменяет невалидные UTF8-последовательности на U+FFFD. Инъекция может прятаться за обрезкой.
6. **Fluent Bit grep-фильтр** отбрасывает запись целиком — непригоден как единственная мера там, где важна полнота логов.
