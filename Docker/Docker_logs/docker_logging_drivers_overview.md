# Обзор системы логирования в Docker

**Актуально для:** Docker Engine 29.x, Loki 3.x, Grafana Alloy/Vector 0.45.x

## Определения

**Лог-драйвер (Logging Driver)** — встроенный механизм Docker Engine, который перехватывает стандартные потоки вывода (`STDOUT`) и ошибок (`STDERR`) контейнера и направляет их в определенное место назначения (локальные файлы, системный журнал или удаленный сервис).

**Централизованное логирование (Centralized Logging)** — архитектурный подход, при котором логи со всех контейнеров и хостов собираются в единое хранилище (Loki, Elasticsearch, ClickHouse) для обеспечения наблюдаемости (Observability) и упрощения отладки.

**Драйвер `json-file`** — стандартный лог-драйвер Docker, записывающий логи в текстовом JSON-формате на диск (`/var/lib/docker/containers/<id>/<id>-json.log`). Поддерживает `docker logs` и Direct Read агентами. **Не имеет ротации по умолчанию** — без явной настройки `max-size` файлы растут неограниченно.

**Драйвер `local`** — оптимизированный лог-драйвер (рекомендуется с Docker 20.10+), использующий внутренний бинарный формат (protobuf) для повышения производительности. Имеет встроенную ротацию по умолчанию (100 МБ / 5 файлов) и сжатие. Файлы не читаются внешними инструментами напрямую — только через `docker logs`.

**Dual Logging (Двойное логирование)** — механизм Docker Engine (с версии 20.10+), при котором логи параллельно записываются в локальный бинарный кэш (драйвер `json-file` или `local`) и во внешний сетевой драйвер. Обеспечивает работоспособность команды `docker logs` даже при использовании удалённых драйверов.

**Non-blocking режим** — режим работы сетевых лог-драйверов, при котором Docker пишет логи в кольцевой буфер в оперативной памяти вместо блокировки контейнера при сетевых сбоях. При переполнении буфера старые записи отбрасываются (FIFO), обеспечивая стабильность приложения ценой частичной потери логов.

**Режим Blocking (по умолчанию)** — режим работы сетевых лог-драйверов, при котором Docker ждет подтверждения (ACK) от приёмника о получении лога. Если сеть нестабильна, Docker daemon приостанавливает (freezes) контейнер, чтобы не потерять данные. Риск каскадных сбоев при недоступности хранилища.

## Предпосылки

- **Docker Engine** версии 29.x (актуальная версия на 2026 год; Dual Logging доступен с 20.10+)
- **Docker CLI** с правами root или членство в группе `docker` для редактирования `/etc/docker/daemon.json`
- **Понимание разницы между локальными и сетевыми драйверами**: локальные (`json-file`, `local`) хранят на диске хоста, сетевые (`loki`, `gelf`, `fluentd`, `splunk`, `syslog`) отправляют по сети
- **Достаточно дискового пространства** на разделе `/var/lib/docker` (или кастомном `data-root`)

**Быстрая диагностика текущей конфигурации:**
```bash
# Глобальный драйвер по умолчанию
docker info --format '{{.LoggingDriver}}'
# → json-file

# Драйвер конкретного контейнера
docker inspect --format '{{.HostConfig.LoggingConfig.Type}}' <container>
# → json-file

# Путь к файлам логов
docker info --format '{{.DockerRootDir}}'
# → /var/lib/docker

# Список доступных драйверов
docker info | grep -A 5 "Logging Driver"
```

## Базовые концепции

### Принцип работы

В Docker реализован стандартный подход: **приложение пишет в стандартные потоки**. Разработчик не должен настраивать внутри приложения запись в файлы или отправку по сети; приложение просто отправляет данные в дескрипторы `1` (stdout) и `2` (stderr).

**Поток данных:**
```
Процесс в контейнере → Ядро Linux (Pipe) → Docker Engine → Лог-драйвер → Место назначения
```

**Формат лог-записи (json-file / local):**
```json
{
  "log": "2026-08-21 12:00:00 [INFO] Application started\n",
  "stream": "stdout",
  "time": "2026-08-21T12:00:00.123456789Z"
}
```

Каждая строка вывода приложения оборачивается в JSON-объект с тремя полями:
- `log` — содержимое строки (с символом новой строки `\n` на конце)
- `stream` — `stdout` или `stderr`
- `time` — ISO 8601 временная метка (всегда UTC, независимо от часового пояса контейнера)

**Расположение файлов логов:**
```
/var/lib/docker/containers/<container_id>/<container_id>-json.log
```

### Основные архитектуры сбора логов

Существует два принципиально разных подхода к организации сбора логов в Docker-окружениях:

#### 1. Агентный сбор (Agent-based) — Рекомендуемый

Docker Engine использует локальный драйвер (`json-file` или `local`) для записи логов на диск хоста. Специализированный агент (например, Grafana Alloy, Vector или Filebeat) читает эти файлы с диска.

*   **Схема**: `Docker → Диск → Агент → Сеть → Хранилище`.
*   **Особенности**: Максимальная надежность. Если сеть или хранилище недоступны, логи сохраняются на диске и будут отправлены агентом позже.
*   **Подробнее**: **[Агентный сбор логов Docker](./docker_agent_based_logging.md)**.

#### 2. Прямая отправка через драйверы (Driver-mediated)

Docker Engine использует сетевой драйвер (`loki`, `gelf`, `fluentd`, `splunk`, `syslog`), который самостоятельно транслирует логи по сети.

*   **Схема**: `Docker → Сеть → Хранилище`.
*   **Особенности**: Простота настройки (не нужны сторонние агенты), но риск блокировки контейнера при сбоях сети (решается режимом `non-blocking`).
*   **Подробнее**: **[Централизованное логирование: Лог-драйверы](./docker_centralized_logging.md)**.

### Сравнение двух архитектур

| Критерий | Агентный сбор | Прямая отправка (Драйверы) |
| :--- | :--- | :--- |
| **Надежность** | **Высокая.** Буферизация на диске хоста. | **Средняя.** Буфер только в оперативной памяти. |
| **Нагрузка на Docker** | Минимальная. Docker просто пишет в файл. | Средняя. Docker Engine выполняет сетевую передачу. |
| **Гибкость обработки** | **Максимальная.** Агенты позволяют парсить, маскировать и фильтровать логи. | Минимальная. Только базовое тегирование. |
| **Простота** | Требует управления агентом. | Настраивается одной строкой в `daemon.json`. |
| **Latency (Задержка)** | 1-5 секунд (агент читает файлы с диском). | Мгновенная (прямая отправка). |
| **Ресурсы хоста** | Агент потребляет RAM/CPU на каждом узле. | Docker daemon выполняет сетевую передачу. |
| **Рекомендация** | Production, Enterprise, критические среды. | Локальная разработка, быстрое прототипирование. |

| Драйвер | Тип | Хранилище | `docker logs` | Dual Logging | Blocking/Non-blocking | Ротация | Сжатие | Примечание |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **`json-file`** | Локальный | Диск | Да | Да | N/A | Ручная настройка | Ручная настройка | Стандартный, читаемый вручную |
| **`local`** | Локальный | Диск | Да | Да | N/A | Автоматическая (100МБ/5) | Автоматическое | Рекомендуется с 20.10+ |
| **`syslog`** | Сетевой | Syslog-сервер | Да | Да | Blocking/Non-blocking | На стороне syslog | На стороне syslog | Стандарт Unix, порт 514 |
| **`journald`** | Сетевой | systemd-journald | Да | N/A (нативно) | N/A | На стороне journald | На стороне journald | Только для Linux с systemd |
| **`gelf`** | Сетевой | Graylog | Да | Да | Blocking/Non-blocking | На стороне Graylog | На стороне Graylog | UDP/TCP, порт 12201 |
| **`fluentd`** | Сетевой | Fluentd-сервер | Да | Да | Blocking/Non-blocking | На стороне Fluentd | На стороне Fluentd | Множество плагинов |
| **`splunk`** | Сетевой | Splunk HEC | Да | Да | Blocking/Non-blocking | На стороне Splunk | На стороне Splunk | Требует токен HEC |
| **`loki`** | Сетевой | Grafana Loki | Да | Да | Blocking/Non-blocking | На стороне Loki | На стороне Loki | Плагин Grafana |
| **`none`** | Нет | Нет | Нет | Нет | N/A | N/A | N/A | Логи отбрасываются |

**Рекомендация:** Для production используйте `local` (локальный) или агентный сбор через `json-file`/`local` + Vector/Alloy. Избегайте `none` в контейнерах для одноразовых задач.

### Настройка лог-драйвера: Глобальная vs Переконтейнерная

Драйвер можно настроить на трёх уровнях:

**1. Глобально (все новые контейнеры) — `/etc/docker/daemon.json`:**
```json
{
  "log-driver": "local",
  "log-opts": {
    "max-size": "10m",
    "max-file": "5"
  }
}
```
*Все значения параметров `log-opts` должны быть строками (в кавычках).*

**2. Для конкретного контейнера — `docker run`:**
```bash
docker run --log-driver=local \
  --log-opt max-size=10m \
  --log-opt max-file=5 \
  my-app
```

**3. В Docker Compose:**
```yaml
services:
  app:
    image: my-app
    logging:
      driver: local
      options:
        max-size: "10m"
        max-file: "5"
```

**Приоритет:** Настройки контейнера > настройки Docker Compose > глобальные настройки daemon.json.

### Совместимость и Dual Logging

Начиная с Docker 20.10+, реализован механизм **Dual Logging** (двойное логирование). Он позволяет использовать команду `docker logs <container_name>` даже при использовании удаленных драйверов (Loki, GELF и др.).

*   **Механизм**: Docker Engine параллельно с отправкой во внешний драйвер пишет логи в локальный бинарный кэш.
*   **Драйверы с поддержкой Dual Logging (2026)**: `syslog`, `gelf`, `fluentd`, `splunk`, `loki`. Драйверы `json-file`, `local` и `journald` читают логи нативно — Dual Logging для них не используется.
*   **Драйверы без Dual Logging**: `none`.
*   **Рекомендация**: Всегда используйте современные версии Docker, чтобы не терять возможность быстрой отладки через CLI при наличии централизованного сбора.

**Проверка Dual Logging для контейнера:**
```bash
# Проверить, что Dual Logging активен
docker inspect --format '{{.HostConfig.LoggingConfig.Type}}' <container>
# → loki (или другой сетевой драйвер)

# Убедиться что docker logs работает
docker logs <container> --tail 5
# → Должны показываться логи даже с сетевым драйвером
```

### Выбор стратегии: Критерии принятия решения

1.  **Production Enterprise**: Рекомендуется **агентный сбор** (Vector или Grafana Alloy). Это гарантирует сохранность логов при сетевых сбоях и позволяет обогащать логи сложными метаданными.
2.  **Локальная разработка и малые стенды**: Достаточно стандартного драйвера `json-file` или `local` с настроенной ротацией.
3.  **Real-time логи (аудит, безопасность)**: Loki Docker Driver или Fluentd — минимальная задержка доставки.
4.  **Микросервисы с несколькими десятками контейнеров**: Агентный сбор (Alloy/Vector) — централизованное управление, единая точка конфигурации.

## Практические сценарии

### Сценарий 1: Быстрый старт с `local` драйвером (Рекомендуется)

**Цель**: Включить логирование по умолчанию с ротацией и сжатием.

**Шаг 1: Настройка daemon.json:**
```json
{
  "log-driver": "local",
  "log-opts": {
    "max-size": "10m",
    "max-file": "5",
    "compress": "true"
  }
}
```

**Шаг 2: Перезапуск Docker daemon:**
```bash
sudo systemctl restart docker
```

**Шаг 3: Проверка:**
```bash
# Создать тестовый контейнер
docker run -d --name test-logging alpine sh -c "while true; do echo log-$(date +%s); sleep 1; done"

# Проверить драйвер
docker inspect --format '{{.HostConfig.LoggingConfig.Type}}' test-logging
# → local

# Проверить файлы логов
ls -la /var/lib/docker/containers/$(docker inspect --format '{{.Id}}' test-logging)/*-json.log
# → Файл существует, но в бинарном формате (local driver)

# Просмотр логов через docker logs
docker logs --tail 5 test-logging

# Очистка
docker rm -f test-logging
```

### Сценарий 2: Глобальная настройка с `json-file` и ротацией

**Цель**: Стандартная настройка для сред, где требуется прямое чтение файлов агентами (Vector, Fluentd).

**`/etc/docker/daemon.json`:**
```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "10",
    "compress": "true",
    "tag": "{{.ImageName}}/{{.Name}}/{{.ID}}"
  }
}
```

**Доступные шаблоны `tag` (json-file):**

| Шаблон | Описание | Пример значения |
| :--- | :--- | :--- |
| `{{.ImageName}}` | Имя образа | `nginx:1.25` |
| `{{.Name}}` | Имя контейнера | `/my-nginx` |
| `{{.ID}}` | Краткий ID контейнера | `a1b2c3d4e5f6` |
| `{{.FullID}}` | Полный SHA256 ID | `sha256:a1b2c3...` |
| `{{.DaemonName}}` | Имя Docker-демона | `docker` |
| `{{.Hostname}}` | Имя хоста | `web-server-01` |

**Проверка:**
```bash
# Создать контейнер с тегом
docker run -d --name test-tag alpine sh -c "while true; do echo test; sleep 1; done"

# Проверить лог-файл с тегом
ls /var/lib/docker/containers/$(docker inspect --format '{{.Id}}' test-tag)/
# → ...-json.log

# Очистка
docker rm -f test-tag
```

### Сценарий 3: Настройка non-blocking для сетевых драйверов

**Цель**: Защитить контейнеры от фризов при сетевых сбоях (Loki, GELF, Fluentd).

**`/etc/docker/daemon.json`:**
```json
{
  "log-driver": "loki",
  "log-opts": {
    "loki-url": "http://loki.example.com:3100/loki/api/v1/push",
    "mode": "non-blocking",
    "max-buffer-size": "4m"
  }
}
```

**Расчёт размера буфера:**
```
Общая RAM буфера = max-buffer-size × количество_контейнеров
```

**Пример:** При 100 контейнерах и `max-buffer-size=4m`:
```
4 МБ × 100 = 400 МБ RAM для буфера логов
```

**Рекомендация:** Не превышайте 5% оперативной памяти хоста на буфер логов. Для хоста с 16 ГБ RAM: максимум ~800 МБ.

**Проверка:**
```bash
# Проверить режим работы драйвера
docker info --format '{{.LoggingDriver}}'
# → loki

# Проверить что non-blocking активен
docker inspect --format '{{json .HostConfig.LogConfig}}' <container>
# → {"Type":"loki","Config":{"mode":"non-blocking","max-buffer-size":"4m"}}
```

### Сценарий 4: Инспекция и отладка логирования

**Цель**: Диагностика проблем с логированием в production.

```bash
# 1. Проверить глобальный драйвер
docker info --format '{{.LoggingDriver}}'
# → json-file

# 2. Проверить драйвер конкретного контейнера
docker inspect --format '{{.HostConfig.LoggingConfig.Type}}' <container>
# → json-file

# 3. Просмотреть логи в формате JSON (raw)
docker logs <container> 2>&1 | head -1
# → {"log":"2026-08-21 12:00:00 ...\n","stream":"stdout","time":"2026-08-21T12:00:00..."}

# 4. Проверить размер лог-файла
ls -lh /var/lib/docker/containers/$(docker inspect --format '{{.Id}}' <container>)/*-json.log
# → -rw-r----- 1 root root 12M ... /var/lib/docker/containers/.../-json.log

# 5. Проверить количество лог-файлов (при ротации)
ls -la /var/lib/docker/containers/$(docker inspect --format '{{.Id}}' <container>)/*-json.log*
# → -json.log, -json.log.1, -json.log.2.gz, ...

# 6. Проверить что Dual Logging работает
docker inspect --format '{{.HostConfig.LoggingConfig.Type}}' <container>
# → loki (сетевой драйвер)
docker logs --tail 3 <container>
# → Должны показываться логи (Dual Logging)

# 7. Проверить буфер non-blocking (для сетевых драйверов)
docker info --format '{{json .LoggingDriver}}'
# → loki
```

### Сценарий 5: Высокая нагрузка (10k+ логов/сек) и планирование мощности

**Оценка объёма логов:**
```
Объём/день ≈ контейнеры × строк/сек × средний размер строки × 86400

Пример: 50 контейнеров × 10 строк/с × 200 Б × 86400 ≈ 8,6 ГБ/день (до сжатия)
Диск с ротацией: объём/день × retention ÷ коэффициент сжатия (~0,1 для текста при compress=true)
RAM (non-blocking): max-buffer-size × количество контейнеров с сетевым драйвером
```

**Профиль для высокой нагрузки:**
- Локальное хранение — драйвер `local`: компактный бинарный формат, нет JSON-overhead на каждой строке
- Доставка — агентный сбор (Vector: Rust, нет GC-пауз, disk-backed буфер) вместо сетевых драйверов
- `mode=non-blocking` с `max-buffer-size` ≥ 8m при пиковых нагрузках
- Снижение объёма: sampling DEBUG/TRACE-логов (см. [Log Volume Reduction в Loki](../../Loki/loki_log_volume_reduction.md)), фильтрация служебных контейнеров

**Мониторинг pipeline:**
```bash
# Рост лог-файлов (оценка скорости записи)
watch -n 5 'du -sh /var/lib/docker/containers/*/*-json.log | sort -rh | head -5'

# Метрики агентов (эндпоинты по умолчанию)
curl -s http://localhost:12345/metrics | head -5   # Grafana Alloy
curl -s http://localhost:9598/metrics | head -5    # Vector
```

## Дополнительная информация

### Поиск и устранение проблем

| Симптом | Диагностика | Решение |
| :--- | :--- | :--- |
| **Диск заполнен логами контейнеров** | `du -sh /var/lib/docker/containers/*/` | Настройте `max-size` и `max-file` в `daemon.json` |
| **`docker logs` не показывает логи** | Проверьте: `docker inspect --format '{{.HostConfig.LoggingConfig.Type}}'` | Обновите Docker до 20.10+ или переключитесь на `json-file`/`local` |
| **Контейнер зависает (фриз)** | `docker inspect --format '{{.HostConfig.LogConfig}}'` | Переключитесь на `non-blocking` режим |
| **Потеря логов в non-blocking** | Проверьте `max-buffer-size` | Увеличьте размер буфера или снизьте частоту логирования |
| **Агент не читает логи local driver** | Проверьте формат: `docker logs` vs прямое чтение файла | Используйте Docker API или `docker logs` для local driver |
| **`json-file` тег не работает** | Проверьте шаблон `tag` в `daemon.json` | Используйте допустимые шаблоны: `{{.ImageName}}`, `{{.Name}}`, `{{.ID}}` |
| **Логи дублируются в Loki** | Проверьте Dual Logging + Loki driver | Отключите Dual Logging или используйте агентный сбор |
| **Переполнение буфера non-blocking** | `max-buffer-size` слишком мал | Увеличьте `max-buffer-size` или снизьте нагрузку |

### Лучшие практики

1.  **Используйте `local` вместо `json-file`** для новых развертываний — автоматическая ротация и сжатие, меньший расход диска.
2.  **Всегда настройте ротацию** для `json-file` — без `max-size` файлы растут бесконтрольно и могут заполнить диск.
3.  **Для production используйте non-blocking** с сетевыми драйверами — стабильность приложения важнее 100% доставки логов.
4.  **Рассчитывайте RAM для non-blocking** — `max-buffer-size` × количество контейнеров не должно превышать 5% RAM хоста.
5.  **Используйте Dual Logging** (Docker 20.10+) — это позволяет отлаживать через `docker logs` даже при централизованном сборе.
6.  **Избегайте `none`** в контейнерах для одноразовых задач — вы теряете все логи без возможности отладки.
7.  **Для Kubernetes** используйте `json-file` — ротация настраивается на уровне Kubelet, а не daemon.json.

### Ограничения и известные проблемы

1.  **`local` driver не читается напрямую**: Файлы в бинарном формате — только через `docker logs` или Docker API. Агенты (Vector, Fluentd) требуют поддержки формата или использования Docker API.
2.  **Dual Logging кэш ограничен**: Локальный кэш Dual Logging ротируется автоматически, но при очень высокой нагрузке (тысячи строк в секунду) может не хватить места.
3.  **Tag-шаблоны только для `json-file`**: Шаблоны `{{.ImageName}}`, `{{.Name}}` и т.д. работают только с драйвером `json-file`. Для других драйверов теги настраиваются на стороне приёмника.
4.  **Non-blocking не guarantee доставки**: При переполнении буфера логи отбрасываются без уведомления. Для критических данных используйте blocking.
5.  **Journald драйвер только для Linux**: На macOS и Windows драйвер `journald` недоступен.

### Безопасность

- **Доступ к файлам логов**: Файлы в `/var/lib/docker/containers/` доступны только root и группе `docker`. Агенты должны быть в группе `docker` или запускаться от root.
- **Docker Socket**: Агенты, использующие Docker API (`/var/run/docker.sock`), имеют полный контроль над Docker. Ограничьте доступ через ACL или TCP-сокет с TLS.
- **Чувствительные данные в логах**: Не логируйте пароли, токены и ключи. Используйте маскирование (redaction) в агентах.
- **Сетевые драйверы**: Используйте TLS для отправки логов по сети (Loki, GELF, Fluentd). Проверяйте сертификаты.

### Производительность и масштабирование

| Параметр | `json-file` | `local` | Сетевой драйвер |
| :--- | :--- | :--- | :--- |
| **Overhead RAM** | Минимальный | Минимальный | Минимальный (но буфер в RAM) |
| **Overhead CPU** | Минимальный | Низкий (сжатие) | Низкий-средний (сеть) |
| **Disk I/O** | Средний (JSON-обёртка) | Низкий (компактный формат) | Нет (отправка по сети) |
| **Рекомендация по масштабу** | До 500 контейнеров | До 1000+ контейнеров | До 200+ контейнеров |

**Рекомендация:** При масштабировании (>200 контейнеров) используйте `local` для локального хранения и агентный сбор (Vector/Alloy) для доставки. Сетевые драйверы рекомендуются только для small/medium сред.

### Мониторинг и алертинг инфраструктуры логирования

**Ключевые метрики для мониторинга:**

| Метрика | Источник | Порог алерта | SRE-практика |
| :--- | :--- | :--- | :--- |
| **Дисковое пространство** | `df -h /var/lib/docker` | >85% | Алерт + автоматическая ротация |
| **Количество лог-файлов** | `ls /var/lib/docker/containers/*/` | >20 файлов | Проверка настроек `max-file` |
| **Размер лог-файла** | `du -sh /var/lib/docker/containers/*/` | >100M | Проверка `max-size` |
| **Зомби-процессы** | `ps aux | grep -c Z` | >0 | Проблема PID 1, смотри `docker_multi_process_logging.md` |
| **Сетевые ошибки драйвера** | `docker info` + логи daemon | >0 | Проверка блокировок фаервола |
| **Non-blocking buffer** | `docker inspect` + метрики | >80% | Увеличение `max-buffer-size` |
| **Docker daemon CPU** | `top -p $(pgrep dockerd)` | >70% | Слишком много сетевых драйверов |
| **Ошибки доставки логов** | Логи агента/драйвера | >0 | Проверка доступности хранилища |

**Мониторинг через `docker events`:**

```bash
# Мониторинг событий логирования в реальном времени
docker events --filter 'type=container' --filter 'event=die' --filter 'event=oom' \
  --format '{{.Time}} {{.Actor.Attributes.name}}: {{.Action}}'
```

**SRE-практики:**
1. **Dashboard**: Создайте дашборд с метриками дискового пространства, количества контейнеров и ошибок логирования.
2. **Алерты**: Настройте алерты на заполнение диска >85% и ошибки доставки логов >1% от общего объёма.
3. **Runbook**: Подготовьте runbook для оперативного реагирования на потерю логирования (переключение на `local` driver, очистка диска).
4. **Регулярный аудит**: Раз в неделю проверяйте конфигурацию логирования на всех узлах кластера.

### Валидация конфигурации

**Чек-лист проверки после изменения конфигурации:**

```bash
#!/bin/bash
# validate-logging.sh — проверка конфигурации логирования

set -euo pipefail

echo "=== Валидация конфигурации логирования ==="

# 1. Проверить синтаксис daemon.json
echo "[1/5] Проверка синтаксиса daemon.json..."
if ! docker info > /dev/null 2>&1; then
  echo "ERROR: Docker daemon не запущен"
  exit 1
fi

# 2. Проверить глобальный драйвер
echo "[2/5] Глобальный драйвер:"
docker info --format '{{.LoggingDriver}}'

# 3. Проверить ротацию
echo "[3/5] Проверка настроек ротации..."
docker inspect --format '{{json .HostConfig.LogConfig}}' $(docker ps -q | head -1) | jq .

# 4. Проверить Dual Logging
echo "[4/5] Проверка Dual Logging..."
docker inspect --format '{{.HostConfig.LoggingConfig.Type}}' $(docker ps -q | head -1)

# 5. Проверить место на диске
echo "[5/5] Дисковое пространство:"
df -h /var/lib/docker

echo "=== Валидация завершена ==="
```

**Ожидаемые результаты:**
- Драйвер соответствует ожидаемому (`local` или `json-file`)
- Ротация настроена (`max-size`, `max-file`)
- Dual Logging активен (если используется сетевой драйвер)
- Свободное место на диске >20%

### Критические сценарии и edge cases

**Сценарий 1: Полное заполнение диска логами**
- **Причина**: Отсутствие ротации или `max-size` на `json-file`
- **Диагностика**: `du -sh /var/lib/docker/containers/*/`
- **Решение**: Немедленно включите `local` driver, очистите старые логи, настройте ротацию
- **Профилактика**: Настройте мониторинг дискового пространства

**Сценарий 2: Потеря логов при перезагрузке хоста**
- **Причина**: Non-blocking буфер в RAM, не записан на диск
- **Диагностика**: Проверьте `docker inspect` на наличие `mode: non-blocking`
- **Решение**: Используйте агентный сбор или blocking режим для критических логов
- **Профилактика**: Настройка `max-buffer-size` и регулярный дамп буфера

**Сценарий 3: Контейнер не стартует из-за ошибки логирования**
- **Причина**: Невалидные `log-opts` в `daemon.json` или Docker Compose
- **Диагностика**: `docker logs <container>`, `journalctl -u docker`
- **Решение**: Исправьте синтаксис `log-opts`, перезапустите Docker
- **Профилактика**: Валидация конфигурации перед применением

**Сценарий 4: Дублирование логов в хранилище**
- **Причина**: Dual Logging + сетевой драйвер, или несколько агентов читают одни файлы
- **Диагностика**: Поиск дубликатов по `trace_id` или временной метке
- **Решение**: Отключите Dual Logging или настройте уникальные теги
- **Профилактика**: Единая стратегия логирования на кластере

**Сценарий 5: Утечка памяти Docker daemon**
- **Причина**: Слишком много контейнеров с сетевыми драйверами, утечки в драйвере
- **Диагностика**: `top -p $(pgrep dockerd)`, `ps aux | grep dockerd`
- **Решение**: Переключение на `local` driver, обновление Docker
- **Профилактика**: Мониторинг памяти dockerd, ограничение количества сетевых драйверов
