# Обзор системы логирования в Docker

## Определения

**Лог-драйвер (Logging Driver)** — это встроенный в Docker Engine механизм, который перехватывает стандартные потоки вывода контейнера (`STDOUT`/`STDERR`) и направляет их в указанное место назначения. Этот механизм позволяет отделить логику работы приложения от инфраструктурных задач сбора и хранения логов.

## Базовые концепции

В Docker реализован принцип **"приложение пишет в стандартные потоки"**. Приложение внутри контейнера не должно управлять файлами логов; оно просто отправляет данные в `STDOUT` и `STDERR`. Docker Engine перехватывает эти потоки и, согласно настройкам, передает их выбранному лог-драйверу.

Существует две основные архитектуры организации централизованного логирования:

### 1. Агентный сбор (Agent-based) — Рекомендуемый

Docker использует локальный драйвер (`local` или `json-file`) для записи логов во внутреннее хранилище хоста. Специализированный агент (Vector, Grafana Alloy, Filebeat) читает эти файлы с диска, обрабатывает их и отправляет в систему хранения.

- **Схема**: `Приложение → STDOUT → Docker Engine (local) → Диск → Агент → Система хранения (Loki, ELK)`
- **Преимущества**: Максимальная надежность (логи на диске), минимальная нагрузка на Docker daemon.
- **Подробное руководство**: **[Агентный сбор логов Docker](./docker_agent_based_logging.md)**

### 2. Прямая отправка (Driver-mediated)

Docker Engine использует сетевой драйвер (`loki`, `gelf`, `fluentd`, `syslog`), который напрямую транслирует логи по сети в удаленную систему агрегации.

- **Схема**: `Приложение → STDOUT → Docker Engine (log-driver) → Сеть → Система хранения`
- **Особенности**: Требует настройки режима `non-blocking` для предотвращения блокировки приложения при сбоях в сети.
- **Подробное руководство**: **[Централизованное логирование: Лог-драйверы](./docker_centralized_logging.md)**

## Практические сценарии

### Сравнение архитектур

| Критерий | Агентный сбор | Прямая отправка (драйвер) |
| :--- | :--- | :--- |
| **Надежность** | **Экстремальная.** Логи буферизируются на диске. Агент гарантирует доставку даже после сбоев. | **Средняя.** Зависит от доступности сети и приемника. Требует тюнинга (`mode=non-blocking`). |
| **Производительность**| Высокая. Работа по отправке вынесена в отдельный процесс. | Средняя. Docker daemon нагружается задачами сериализации и отправки по сети. |
| **Функциональность** | Богатая фильтрация, парсинг и обогащение метаданными на лету. | Базовая. Возможности трансформации данных минимальны. |
| **Простота** | Требует установки и поддержки агента. | Максимальная. Все настраивается через `daemon.json`. |

### Совместимость с командой `docker logs` (Dual Logging)

В современных версиях Docker (20.10+) реализован механизм **Dual Logging**. Он позволяет использовать команду `docker logs <container>` даже в том случае, если основной вывод настроен на удаленный сетевой драйвер (например, `loki` или `fluentd`).

- **Как это работает**: Docker одновременно отправляет логи в удаленную систему и сохраняет их в локальном кэше (драйвер `local`).
- **Когда это не работает**: Только если вы явно отключили кэширование в настройках лог-драйвера (`cache-disabled: "true"`).
- **Рекомендация**: Всегда оставляйте Dual Logging включенным для удобства отладки "на месте" без необходимости переходить в интерфейс Grafana/Kibana для просмотра последних строк.
