# Docker Swarm Mode

## Docker Swarm vs. Docker Compose

Часто возникает путаница между `docker compose` и `docker swarm`. Важно понимать их фундаментальное различие:

*   **Docker Compose:** Это инструмент для определения и запуска **многоконтейнерных приложений на одном хосте**. Он идеален для локальной разработки и простых одноузловых развертываний.
*   **Docker Swarm:** Это инструмент для **оркестрации контейнеров в кластере из нескольких хостов**. Он берет на себя задачи распределения контейнеров (сервисов) по разным машинам, обеспечивает отказоустойчивость и масштабирование.

> **Простое правило:** Если у вас один сервер — используйте `docker compose`. Если у вас несколько серверов, которые нужно объединить в кластер, — используйте `docker swarm`. При этом Swarm может использовать синтаксис `docker-compose.yml` для развертывания приложений с помощью команды `docker stack deploy`.

---

Docker Swarm Mode предоставляет нативную функциональность для создания и управления кластером Docker-движков. Он превращает группу Docker-хостов в единый виртуальный Docker-движок, позволяя развертывать приложения как сервисы, состоящие из множества контейнеров, распределенных по всему кластеру.

**Важно:** Не следует путать **Docker Swarm Mode** с устаревшим проектом **Docker Classic Swarm**, который больше не активно разрабатывается. Docker Swarm Mode является встроенной частью Docker Engine. Он часто рассматривается как "золотая середина" между простым запуском контейнеров на одном хосте и сложной оркестрацией Kubernetes, предлагая баланс между функциональностью и простотой использования.

*   **Простота использования:** Интегрирован в Docker CLI, что упрощает освоение.
*   **Встроенное обнаружение сервисов:** Автоматическое назначение DNS для сервисов и внутреннее балансирование нагрузки.
*   **Высокая доступность:** Автоматическое восстановление сервисов при сбое узла и перезапуск сбойных задач на здоровых узлах.
*   **Масштабируемость:** Легкое горизонтальное масштабирование сервисов.
*   **Декларативное управление:** Описание желаемого состояния приложения.
*   **Встроенная безопасность:** Автоматическая TLS-шифрование между узлами и интегрированное управление секретами и конфигурациями.
*   **Гибкое развертывание:** Поддержка скользящих обновлений и откатов, а также планирование контейнеров на основе доступности ресурсов (CPU, память) и заданных ограничений (constraints).

## Архитектура Docker Swarm

### Менеджеры (Manager Nodes)

*   **Управление кластером:** Отвечают за поддержание желаемого состояния кластера.
*   **Планирование задач:** Распределяют задачи (контейнеры) по рабочим узлам.
*   **Оркестрация:** Обрабатывают запросы API, управляют состоянием сервисов, выполняют операции масштабирования и обновления.
*   **Высокая доступность:** Для обеспечения отказоустойчивости и кворума рекомендуется иметь нечетное количество менеджеров (3 или 5). Кластер остается функциональным, если более половины менеджеров находятся в сети. Если лидер-менеджер выходит из строя, другой менеджер автоматически берет на себя его роль.
*   **Повышение роли:** Рабочий узел может быть повышен до менеджера с помощью команды `docker node promote`.

### Рабочие узлы (Worker Nodes)

*   **Выполнение задач:** Запускают и останавливают контейнеры в соответствии с инструкциями от менеджеров.
*   **Отчетность:** Сообщают о своем состоянии и состоянии выполняемых задач менеджерам.
*   **Масштабируемость:** Можно добавлять или удалять рабочие узлы для изменения вычислительной мощности кластера.

---

### Взаимодействие

Менеджеры и рабочие узлы общаются друг с другом через зашифрованный TLS-канал. Менеджеры используют алгоритм Raft для поддержания консистентного состояния кластера.

---

## Ключевые концепции Docker Swarm

*   **Сервисы (Services):** Определение задачи, которую вы хотите выполнить в Swarm. Сервис описывает, какой образ Docker использовать, сколько реплик должно быть запущено, какие порты должны быть открыты и т.д.
*   **Задачи (Tasks):** Единица работы, выполняемая в Swarm. Задача соответствует одному контейнеру Docker, который запускается на рабочем узле. Менеджеры назначают задачи узлам.
*   **Узлы (Nodes):** Физические или виртуальные машины, на которых запущен Docker Engine и которые являются частью Swarm. Узлы могут быть менеджерами или рабочими.
*   **Балансировка нагрузки (Load Balancing):** Swarm имеет встроенную балансировку нагрузки (Routing Mesh), которая распределяет входящие запросы между репликами сервиса, используя IPVS (IP Virtual Server). Это позволяет обращаться к любому сервису через любой узел Swarm, независимо от того, где запущены его контейнеры.

## Масштабирование сервисов

Для горизонтального масштабирования сервиса (увеличения или уменьшения количества реплик) используется команда `docker service scale`.

```sh
# Установить количество реплик сервиса myservice равным 5
docker service scale myservice=5
```

---

### Инициализация Swarm

Превращает текущий Docker-хост в менеджер Swarm.

```sh
docker swarm init --advertise-addr <MANAGER-IP>
```

### Присоединение к Swarm

Позволяет другому Docker-хосту присоединиться к существующему Swarm как рабочий узел или менеджер.

```sh
docker swarm join --token <TOKEN> <MANAGER-IP>:<PORT>
```

### Управление узлами

*   **Просмотр узлов:**
    ```sh
    docker node ls
    ```
*   **Повышение/понижение роли узла:**
    ```sh
    docker node promote <NODE-ID> # Сделать рабочим узлом менеджером
    docker node demote <NODE-ID> # Сделать менеджера рабочим узлом
    ```
*   **Удаление узла:**
    ```sh
    docker node rm <NODE-ID>
    ```

### Управление сервисами

*   **Создание сервиса:**
    ```sh
    docker service create --name my-web --publish 80:80 --replicas 3 nginx:1.25.5
    ```
*   **Просмотр сервисов:**
    ```sh
    docker service ls
    ```
*   **Просмотр задач сервиса:**
    ```sh
    docker service ps my-web
    ```
    Эта команда показывает, на каких узлах запущены реплики сервиса и их текущее состояние.
*   **Обновление сервиса (например, изменение образа):**
    ```sh
    docker service update --image nginx:1.26.0 my-web
    ```
    Docker Swarm выполняет скользящее обновление, заменяя старые контейнеры новыми без простоя.
*   **Откат сервиса:**
    ```sh
    docker service rollback my-web
    ```
    Позволяет откатить сервис к предыдущей конфигурации в случае проблем с обновлением.
*   **Удаление сервиса:**
    ```sh
    docker service rm my-web
    ```

### Выход из Swarm

Удаляет узел из Swarm.

```sh
docker swarm leave # Для рабочего узла
docker swarm leave --force # Для менеджера (если он последний или вы хотите принудительно удалить)
```

## Развертывание приложений с помощью Docker Compose (Docker Stack)

Docker Swarm Mode позволяет использовать файлы `docker-compose.yml` для развертывания многоконтейнерных приложений как "стеков" (stacks). Это значительно упрощает управление сложными приложениями.

**Ключевые отличия при использовании Compose в Swarm:**

*   **Команда:** Вместо `docker compose up` используется `docker stack deploy`.
*   **Секция `deploy`:** Для Swarm-специфичных настроек (количество реплик, ограничения ресурсов, стратегии обновления) используется секция `deploy` в файле `docker-compose.yml`. Подробнее см. [Docker Compose: Секция Deploy](../docker_compose.md#секция-deploy).
*   **Игнорируемые параметры:** Параметры `container_name` и `restart` игнорируются, так как Swarm управляет именованием контейнеров и их перезапуском.

**Пример `docker-compose.yml` для Swarm:**

```yaml
version: '3.8'
services:
  web:
    image: nginx:1.25.5
    ports:
      - "80:80"
    deploy:
      replicas: 3
      placement:
        constraints:
          - node.role == worker
      update_config:
        parallelism: 1
        delay: 10s
      restart_policy:
        condition: on-failure
  backend:
    image: my-backend-app:1.0
    deploy:
      replicas: 2
      placement:
        constraints:
          - node.labels.app == backend
```

**Развертывание стека:**

```sh
docker stack deploy -c docker-compose.yml my-app-stack
```

**Просмотр стеков:**

```sh
docker stack ls
```

**Просмотр сервисов в стеке:**

```sh
docker stack services my-app-stack
```

**Удаление стека:**

```sh
docker stack rm my-app-stack
```

## Управление секретами (Secrets Management)

Docker Swarm предоставляет встроенный механизм для безопасного хранения и управления чувствительными данными, такими как пароли, токены API и SSH-ключи. Секреты хранятся в зашифрованной базе данных Swarm и доступны только тем сервисам, которым они явно назначены.

*   **Создание секрета:**
    ```sh
    echo "my_super_secret_password" | docker secret create my_secret_password -
    ```
*   **Просмотр секретов:**
    ```sh
    docker secret ls
    ```
*   **Использование секрета в сервисе:**
    ```sh
    docker service create --name my-app --secret my_secret_password my-image
    ```
    Внутри контейнера секрет будет доступен как файл по пути `/run/secrets/my_secret_password`.
*   **Ограничения:**
    *   Секреты монтируются как файлы. Если приложение ожидает секрет в виде переменной окружения, может потребоваться адаптация приложения или использования оберток для чтения секрета из файла и передачи его в переменную окружения.
    *   Секреты не могут быть отредактированы напрямую после создания. Для изменения необходимо удалить существующий секрет и создать новый с обновленными значениями.
*   **Удаление секрета:**
    ```sh
    docker secret rm my_secret_password
    ```

## Управление конфигурациями (Config Management)

Подобно секретам, Docker Swarm позволяет управлять нечувствительными конфигурационными файлами централизованно.

*   **Создание конфигурации:**
    ```sh
    docker config create my_config_file ./app_config.yaml
    ```
*   **Просмотр конфигураций:**
    ```sh
    docker config ls
    ```
*   **Использование конфигурации в сервисе:**
    ```sh
    docker service create --name my-app --config my_config_file my-image
    ```
    Внутри контейнера конфигурация будет доступна как файл по пути `/my_config_file` (или другому указанному пути).
*   **Ограничения:**
    *   Конфигурации, созданные в Swarm, не могут быть отредактированы напрямую. Для изменения необходимо удалить существующую конфигурацию и создать новую с обновленными значениями.
    *   Конфигурации монтируются как файлы внутри контейнера.
*   **Удаление конфигурации:**
    ```sh
    docker config rm my_config_file
    ```

## Настройка удаленного доступа по mTLS

Для интеграции с CI/CD системами, такими как GitLab CI, и для удаленного управления кластером без необходимости использовать SSH, можно настроить доступ к Docker Daemon по TCP с использованием mTLS (взаимной аутентификации по TLS).

**Процесс настройки:**

1.  **Генерация сертификатов:**
    *   Создается корневой сертификат (CA), которым будут подписываться все остальные сертификаты.
    *   Генерируется пара ключ/сертификат для сервера (Docker Daemon). В сертификате сервера в качестве `Common Name` (CN) или `Subject Alternative Name` (SAN) необходимо указать доменное имя или IP-адрес хоста.
    *   Генерируется пара ключ/сертификат для клиента (например, для GitLab Runner).

2.  **Настройка Docker Daemon:**
    *   Необходимо отредактировать конфигурацию systemd для сервиса Docker, чтобы он начал слушать TCP-порт (стандартно 2376 для mTLS) и использовал сгенерированные сертификаты.

    Пример конфигурации для `/etc/systemd/system/docker.service.d/override.conf`:
    ```ini
    [Service]
    ExecStart=
    ExecStart=/usr/bin/dockerd -H fd:// -H tcp://0.0.0.0:2376 --tlsverify --tlscacert=/etc/docker/tls/ca.pem --tlscert=/etc/docker/tls/server-cert.pem --tlskey=/etc/docker/tls/server-key.pem
    ```

3.  **Перезапуск Docker:**
    ```sh
    sudo systemctl daemon-reload
    sudo systemctl restart docker
    ```

4.  **Настройка клиента:**
    *   На клиентской машине (или в CI/CD окружении) необходимо иметь файлы `ca.pem`, `cert.pem` (клиентский сертификат) и `key.pem` (клиентский ключ).
    *   Для удобства можно создать **Docker Context**.

### Использование Docker Context для удаленного управления

Docker Context позволяет легко переключаться между разными Docker-окружениями (локальным, удаленным dev, удаленным prod).

*   **Создание контекста:**
    ```sh
    docker context create prod-swarm \
      --docker "host=tcp://prod.example.com:2376,ca=/path/to/ca.pem,cert=/path/to/cert.pem,key=/path/to/key.pem"
    ```

*   **Переключение на контекст:**
    ```sh
    docker context use prod-swarm
    ```

*   После этого все команды `docker` (например, `docker ps`, `docker service ls`) будут выполняться на удаленном Swarm-кластере.

## Интеграция с GitLab CI для автоматического развертывания

Используя удаленный доступ по mTLS, можно построить эффективный CI/CD пайплайн для автоматического развертывания в Docker Swarm.

**Пример `.gitlab-ci.yml`:**

```yaml
stages:
  - build
  - deploy

build:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:v1.9.0-debug
    entrypoint: [""]
  script:
    # kaniko не требует Docker-in-Docker
    - /kaniko/executor
      --context $CI_PROJECT_DIR
      --dockerfile $CI_PROJECT_DIR/Dockerfile
      --destination $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  only:
    - main
    - dev

deploy_prod:
  stage: deploy
  image: docker:latest
  script:
    # 1. Создаем Docker Context с помощью переменных GitLab CI
    - docker context create swarm-prod --docker "host=${PROD_DOCKER_HOST},ca=${PROD_CA_FILE},cert=${PROD_CERT_FILE},key=${PROD_KEY_FILE}"
    # 2. Переключаемся на созданный контекст
    - docker context use swarm-prod
    # 3. Развертываем стек
    - docker stack deploy -c docker-compose.prod.yml --with-registry-auth my-app
  environment:
    name: production
    url: https://prod.example.com
  only:
    - main

deploy_dev:
  stage: deploy
  image: docker:latest
  script:
    - docker context create swarm-dev --docker "host=${DEV_DOCKER_HOST},ca=${DEV_CA_FILE},cert=${DEV_CERT_FILE},key=${DEV_KEY_FILE}"
    - docker context use swarm-dev
    - docker stack deploy -c docker-compose.dev.yml --with-registry-auth my-app
  environment:
    name: development
    url: http://dev.example.com
  only:
    - dev
```

**Ключевые моменты:**

*   **Сборка с Kaniko:** Для сборки Docker-образов используется [Kaniko](https://github.com/GoogleContainerTools/kaniko), что позволяет избежать сложностей и рисков безопасности, связанных с Docker-in-Docker.
*   **Переменные GitLab CI:** Все секреты (содержимое сертификатов, хосты) хранятся в переменных GitLab CI типа `File` и `Variable`. Это позволяет безопасно передавать их в сборочные задачи.
*   **`docker stack deploy --with-registry-auth`:** Эта опция автоматически передает учетные данные для доступа к приватному Docker Registry (в данном случае, GitLab Registry) на узлы Swarm, чтобы они могли скачать образ.

## Тома в Swarm Mode (Volumes in Swarm Mode)

По умолчанию тома, используемые в Docker Swarm, являются локальными для каждого узла. Это означает, что если задача сервиса перемещается с одного узла на другой, данные, хранящиеся в локальном томе, не будут доступны на новом узле.

*   **Проблема:** Отсутствие персистентности данных при перемещении контейнеров между узлами.
*   **Решения:**
    *   **Сетевые файловые системы (NFS):** Монтирование общих сетевых ресурсов (например, NFS) на все узлы Swarm. Это позволяет контейнерам получать доступ к одним и тем же данным независимо от того, на каком узле они запущены. Однако NFS может иметь ограничения по производительности и не всегда является оптимальным решением для баз данных.
    *   **Драйверы хранения (Storage Drivers):** Использование специализированных драйверов хранения, которые интегрируются с распределенными системами хранения (например, Ceph, GlusterFS) для обеспечения общего персистентного хранения в кластере Swarm.

## Сосуществование с автономными контейнерами

Одной из мощных особенностей Docker Swarm Mode является возможность его сосуществования с обычными автономными контейнерами и проектами Docker Compose на одном и том же хосте.

*   **Гибкость:** Активация Swarm Mode на хосте не влияет на уже запущенные автономные контейнеры или проекты Docker Compose. Они продолжают работать как обычно.
*   **Постепенная миграция:** Это позволяет постепенно мигрировать существующие приложения в Swarm-сервисы или Swarm-стеки, не требуя немедленного перевода всей инфраструктуры. Вы можете запускать Swarm-сервисы параллельно с автономными контейнерами.

## Сеть в Docker Swarm

Docker Swarm использует **оверлейные сети (overlay networks)** для обеспечения связи между контейнерами, запущенными на разных узлах Swarm.

*   **Простота:** Автоматически создаются и управляются Swarm.
*   **Изоляция:** Сетевой трафик между сервисами изолирован.
*   **Балансировка нагрузки:** Встроенная DNS-балансировка нагрузки для сервисов.

### Создание оверлейной сети

```sh
docker network create --driver overlay --attachable --opt encrypted my-overlay-network
```
*   Флаг `--attachable` позволяет автономным контейнерам (не Swarm-сервисам) подключаться к этой сети.
*   Опция `--opt encrypted` включает IPsec-шифрование трафика, но может повлиять на производительность.

### Системные сети в Swarm: ingress и docker_gwbridge

Помимо пользовательских overlay-сетей, в Swarm-кластере по умолчанию создаются две важные системные сети:

*   **`ingress`:** Используется для маршрутизации входящего трафика к сервисам Swarm. Когда вы публикуете порт сервиса (например, `-p 8080:80`), Swarm Routing Mesh направляет трафик с порта `8080` *любого* из хостов кластера на нужный контейнер, даже если он работает на другой машине. Балансировка нагрузки выполняется с помощью IPVS. Эта сеть не является `attachable` по умолчанию.
*   **`docker_gwbridge`:** Служит шлюзом для исходящего трафика из контейнеров Swarm-сервисов во внешний мир (например, когда контейнер обращается к внешнему API или базе данных в интернете).

### Использование сети в сервисе

```sh
docker service create --name my-service --network my-overlay-network --replicas 3 my-image
```

## Безопасность Docker Swarm

*   **TLS-шифрование:** Весь трафик между узлами Swarm по умолчанию шифруется с использованием TLS.
*   **Токены присоединения:** Используются для безопасного присоединения новых узлов к Swarm.
*   **Ролевая модель (RBAC):** Хотя Docker Swarm не имеет встроенной RBAC в том же смысле, что Kubernetes, доступ к API Docker можно контролировать на уровне хоста.
