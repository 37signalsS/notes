# Безопасность Docker: Механизмы и Защита

Предоставление доступа к Docker API эквивалентно предоставлению `root`-доступа к хост-системе.

### Добавление пользователя в группу `docker`

- **Назначение:** Позволяет пользователю выполнять команды `docker` без `sudo`.
- **Риск:** Пользователь получает неконтролируемый доступ к Docker API через сокет `/var/run/docker.sock`. Это позволяет запустить контейнер с расширенными правами, включая монтирование корневой файловой системы хоста.

**Пример получения root-доступа пользователем из группы `docker`:**

```sh
# Пользователю не нужно sudo для этой команды
docker run -it --rm -v /:/host busybox:1.36.1 chroot /host
# Результат: root-шелл на хост-системе
```

### Прямой доступ к сокету `/var/run/docker.sock`

- **Назначение:** `/var/run/docker.sock` — это UNIX-сокет для взаимодействия с демоном Docker (`dockerd`).
- **Риск:** Предоставление контейнеру доступа к этому сокету (например, через монтирование `-v /var/run/docker.sock:/var/run/docker.sock`) позволяет ему управлять демоном Docker на хосте, что может привести к "побегу из контейнера" (container escape).
- **Последствия:** Процесс внутри контейнера может использовать этот доступ для запуска нового, привилегированного контейнера и получения контроля над хостом.

> Для сценариев, требующих взаимодействия с Docker API (например, CI/CD агенты), рекомендуется использовать прокси, которые фильтруют API-запросы, вместо прямого монтирования сокета.

## Основная угроза: Docker и Root-доступ

Демон Docker (`dockerd`) по умолчанию работает с правами `root`. Это означает, что пользователь или процесс, получивший доступ к управляющему сокету Docker, фактически получает `root`-доступ к хост-системе.

## Векторы атак

### Docker Socket (/var/run/docker.sock)

Это основной способ локального взаимодействия с демоном. 

- **Права доступа:** По умолчанию сокет принадлежит пользователю `root` и группе `docker` с правами `660`. Это означает, что любой пользователь, добавленный в группу `docker`, имеет полный, неавторизованный доступ к Docker API.
- **Угроза:** Если злоумышленник получает доступ к сокету (напрямую или пробросив его в контейнер), он может запустить привилегированный контейнер и захватить контроль над хостом.

### Легитимные сценарии использования Docker Socket

Несмотря на огромный риск, существуют легитимные сценарии, в которых монтирование сокета Docker в контейнер является распространенной практикой.

1.  **CI/CD Системы (например, Jenkins, GitLab Runner):**
    Агент CI/CD, запущенный в контейнере, использует сокет для сборки и управления Docker-образами в рамках пайплайна.

2.  **Инструменты управления Docker:**
    Контейнеризированные приложения для мониторинга и управления (например, Portainer) используют сокет для взаимодействия с демоном Docker на хосте.

3.  **Среды для разработки ("Docker-out-of-Docker"):**
    Разработчики монтируют сокет в свой контейнер для разработки, чтобы иметь возможность собирать и запускать другие контейнеры, не выходя из своей изолированной среды.

> Во всех этих случаях доверие к используемому образу должно быть абсолютным.

### Альтернативные подходы

-   **Прокси для сокета:** Использование утилит вроде `docker-socket-proxy`, которые фильтруют опасные API-вызовы.
-   **Сборка без демона:** Применение инструментов типа **Kaniko** или **Buildah**, которые не требуют доступа к демону Docker.
-   **Изолированный Docker-in-Docker (dind):** Запуск отдельного, непривилегированного демона Docker внутри контейнера.

**Сценарий атаки (побег из контейнера с проброшенным сокетом):**

```sh
# 1. Злоумышленник находится в контейнере, куда по ошибке смонтировали сокет
# (docker run -v /var/run/docker.sock:/var/run/docker.sock ...)

# 2. Он устанавливает docker-cli и запускает новый контейнер, 
# монтируя корневую ФС хоста.
docker run -it --rm -v /:/host busybox chroot /host

# 3. Результат: он получает root-шелл на хост-системе.
whoami # -> root
```

### Сетевой доступ (TCP)

Демон можно настроить на прослушивание сетевых портов, что создает дополнительный вектор атаки.

- **Порт `2375` (HTTP):** Незашифрованный порт. Подключение к нему предоставляет полный контроль над демоном Docker.
- **Порт `2376` (HTTPS):** Использует TLS для аутентификации и шифрования.
- **SSH:** Использует аутентификацию по SSH.

## Повышение привилегий и побег из контейнера

Если злоумышленник получил доступ к сокету Docker (напрямую на хосте или пробросив его внутрь контейнера), повышение привилегий до `root` на хосте становится тривиальной задачей.

### Сценарий 1: Прямой доступ к сокету на хосте

Атака заключается в запуске привилегированного контейнера с монтированием корневой файловой системы хоста.

```sh
# Эта команда запускает контейнер, который имеет полный доступ ко всем устройствам хоста
# и монтирует файловую систему хоста в /host внутри контейнера.
docker run -it --rm --privileged -v /:/host busybox chroot /host

# После выполнения этой команды вы окажетесь в оболочке с правами root на хосте.
whoami
# -> root
```

### Сценарий 2: Побег из контейнера с проброшенным сокетом

Если сокет Docker монтируется внутрь контейнера, это позволяет процессам внутри него управлять демоном Docker на хосте.

```sh
# 1. Запускаем контейнер, внутрь которого проброшен сокет
docker run -it --rm -v /var/run/docker.sock:/var/run/docker.sock alpine

# 2. Внутри этого контейнера устанавливаем docker-cli
apk add --no-cache docker-cli

# 3. Выполняем ту же атаку, что и в сценарии 1, но уже изнутри контейнера
docker run -it --rm --privileged -v /:/host busybox chroot /host
```

## Лучшие практики по защите (Hardening)

### Не запускайте процессы от `root` внутри контейнера

### Риск "Побега из контейнера" (Container Escape)

Это самая серьезная угроза. Процессы в контейнере выполняются на ядре хост-системы. Хотя контейнеры изолированы, эта изоляция не абсолютна.
- **Общее ядро:** Если в ядре Linux обнаружится уязвимость, вредоносный процесс, запущенный с правами `root` (UID 0) внутри контейнера, может проэксплуатировать её и получить полный `root`-доступ к хост-системе.
- **UID 0 = UID 0:** Для ядра Linux пользователь `root` с UID 0 внутри контейнера — это тот же самый `root` с UID 0, что и на хосте. Разница лишь в ограничениях (namespaces, cgroups), которые накладывает Docker. Уязвимость в ядре может позволить обойти эти ограничения.

Если же процесс в контейнере запущен от имени непривилегированного пользователя, его возможности для эксплуатации уязвимостей ядра значительно сокращаются.

### Проблемы с правами на файлы в монтированных томах (Volumes)
Когда процесс, запущенный от `root` в контейнере, создает файлы в подключенном томе (volume), эти файлы на хост-системе также будут принадлежать пользователю `root`.
- **Пример:** Вы монтируете директорию `./data` с хоста в контейнер. Приложение в контейнере (работающее от `root`) создает файл `log.txt`. На хост-системе владельцем `log.txt` будет `root`.
- **Последствия:** Вы, как обычный пользователь на хосте, не сможете редактировать или удалять этот файл без использования `sudo`. Это создает неудобства и может нарушить работу скриптов сборки или CI/CD.

**Как правильно делать:** Создайте непривилегированного пользователя в `Dockerfile`.

```dockerfile
FROM debian:bookworm-slim

# 1. Выполняем действия от root (установка пакетов)
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*

    # 2. Создаем группу и пользователя с фиксированным UID/GID
    # Использование фиксированных ID помогает избежать проблем с правами на файловых системах
    RUN groupadd --gid 1001 myuser && \
        useradd --uid 1001 --gid 1001 -m myuser

# 3. Копируем файлы и устанавливаем владельца
WORKDIR /app
COPY --chown=myuser:myuser . .

# 4. Переключаемся на созданного пользователя
USER myuser

# 5. Запускаем приложение от его имени
CMD ["./my-application"]
```

### Используйте минималистичные образы

#### Образы Distroless: Максимальная безопасность

**Distroless-образы от Google** — это базовые образы, которые содержат только ваше приложение и его runtime-зависимости (например, `glibc`, `openssl`). 

**Что в них отсутствует:**
-   Оболочки (`/bin/sh`, `bash`)
-   Менеджеры пакетов (`apt`, `apk`)
-   Стандартные утилиты (`ls`, `ps`, `curl`, `wget`)

**Пример: Сборка Go-приложения с помощью Distroless**
```dockerfile
# === Этап 1: Сборка ===
# Используем полноценный образ Go для компиляции
FROM golang:1.25.1-bookworm as builder

WORKDIR /app
COPY . .

# Собираем статически скомпилированный бинарный файл
RUN CGO_ENABLED=0 GOOS=linux go build -o my-app .

# === Этап 2: Финальный образ ===
# Используем базовый образ distroless
FROM gcr.io/distroless/static-debian12

# Копируем только скомпилированный бинарный файл из этапа сборки
COPY --from=builder /app/my-app /

# Указываем команду для запуска
CMD ["/my-app"]
```

**Главный компромисс: Сложность отладки**

Поскольку в образе нет shell, стандартная команда `docker exec -it my-container /bin/sh` не сработает. Эта проблема решаема с помощью специальных техник.

> **Подробное руководство по отладке distroless-контейнеров находится в [руководстве по отладке](./docker_troubleshooting.md#отладка-контейнеров-без-shell-distroless).**

#### Scratch vs. Distroless

И `scratch`, и `distroless` нацелены на создание минималистичных образов, но подходят для разных сценариев.

| Характеристика | `FROM scratch` | `FROM gcr.io/distroless/...` |
| :--- | :--- | :--- |
| **Содержимое** | **Абсолютно пустой.** Нет ничего: ни файлов, ни библиотек, ни shell. | **Минимальный набор.** Содержит только приложение и его runtime-зависимости (например, `glibc`, `openssl`, CA-сертификаты). |
| **Размер** | Минимально возможный (размер вашего бинарника). | Чуть больше, чем `scratch`, но значительно меньше, чем `alpine` или `debian`. |
| **Совместимость** | Только для **полностью статических** бинарных файлов (например, Go с `CGO_ENABLED=0`). | Поддерживает динамически-связанные приложения (C++, Java, Python) благодаря наличию `libc`. |
| **Безопасность** | Максимальная. Поверхность атаки равна нулю (кроме вашего приложения). | Очень высокая. Отсутствуют shell и пакетные менеджеры, что сильно затрудняет атаку. |
| **Сложность** | Высокая. Требует аккуратной сборки бинарника и ручного добавления необходимых файлов (например, CA-сертификатов). | Низкая. Работает "из коробки" для большинства приложений. |

**Когда что использовать:**

-   **`scratch`**: Идеальный выбор для приложений на **Go**, которые скомпилированы как статические бинарники. Если ваше приложение не имеет абсолютно никаких внешних зависимостей, `scratch` — ваш выбор.
-   **`distroless`**: Прагматичный выбор для большинства других языков (**Python, Java, Node.js, C++**) и для Go-приложений, которым нужны базовые функции ОС (например, работа с DNS, TLS-сертификаты). Это золотая середина между безопасностью и удобством.

### Управляйте правами (Capabilities)

- **Никогда не используйте `--privileged`**. Этот флаг отключает почти все механизмы изоляции и предоставляет контейнеру права, эквивалентные `root` на хосте.

  **Что именно делает флаг `--privileged`?**
  - **Дает доступ ко всем capabilities:** Контейнер получает все возможные права, которые может предоставить ядро Linux.
  - **Отключает профили безопасности:** Полностью отключаются `Seccomp` и `AppArmor`/`SELinux`, которые ограничивают системные вызовы и доступ к файлам.
  - **Дает доступ ко всем устройствам:** Контейнер получает прямой доступ ко всем устройствам в `/dev` на хосте.
  - **Монтирование файловых систем:** Файловые системы ядра, такие как `/proc`, монтируются в режиме чтение-запись (RW), а не только для чтения (RO).

  > **Пример:** Внутри привилегированного контейнера можно смонтировать файловую систему хоста и получить к ней полный доступ:
  > ```sh
  > # Внутри контейнера, запущенного с --privileged
  > mkdir /mnt/hdd
  > mount /dev/sda1 /mnt/hdd
  > # Теперь в /mnt/hdd доступна корневая ФС хоста
  > ```

- **Используйте `--cap-drop=ALL` и `--cap-add`**: По умолчанию отключайте все права, а затем добавляйте только те, которые действительно необходимы вашему приложению (например, `NET_BIND_SERVICE` для прослушивания портов ниже 1024).

### Не монтируйте Docker-сокет в контейнеры

Если это абсолютно необходимо (например, для CI/CD), используйте прокси с авторизацией, которые ограничивают доступные команды API (например, [docker-socket-proxy](https://github.com/Tecnativa/docker-socket-proxy)).

### Включите `seccomp` и `AppArmor`/`SELinux`

Эти профили безопасности ограничивают системные вызовы (syscalls), которые может делать контейнер, обеспечивая дополнительный уровень защиты на уровне ядра.

### Изоляция с помощью User Namespaces (userns-remap)

Включается через конфигурационный файл демона (`/etc/docker/daemon.json`) строкой:

```json
{
  "userns-remap": "default"
}
```

#### Проблема: `root` в контейнере = `root` на хосте

По умолчанию, если процесс в контейнере запущен от `root` (UID 0), для ядра хоста это тот же самый `root`. Если злоумышленник сможет \"сбежать\" из контейнера, он получит полные права `root` на хост-машине.

#### Решение: Переназначение пользователей

`userns-remap` решает эту проблему, "переназначая" пользователей. `root` (UID 0) внутри контейнера сопоставляется с обычным, непривилегированным пользователем на хост-машине (например, с UID 100000). Если злоумышленник сбегает из контейнера, он получает права не `root`, а этого непривилегированного пользователя.

Когда вы указываете значение `"default"`, Docker автоматически создает на хосте пользователя `dockremap` и выделяет ему диапазон из 65,536 UID/GID для управления этими сопоставлениями.

#### Оговорки

- **Монтирование томов (Volumes):** Использование `userns-remap` усложняет работу с `bind mounts`. Файлы, созданные в контейнере от `root`, на хосте будут принадлежать пользователю `dockremap`, что может вызвать проблемы с правами доступа.
- **Совместимость:** Не все функции Docker (например, некоторые сетевые режимы) полностью совместимы с `userns-remap`.

### Конфигурация демона: `daemon.json` против флагов запуска

При настройке демона Docker (`dockerd`) существует два основных способа передачи параметров:
1.  **Флаги командной строки:** Передаются при запуске демона, часто прописываются в `systemd` unit-файле (`/lib/systemd/system/docker.service`).
2.  **Конфигурационный файл:** `/etc/docker/daemon.json`. **Это рекомендуемый способ.**

**Проблема: Конфликт конфигураций**

Очень частая ошибка, особенно при попытке пройти аудит `Docker Bench for Security`, — это **смешивание двух этих способов**. Если один и тот же параметр задан и как флаг при запуске, и в `daemon.json`, Docker-демон не сможет запуститься или применит конфигурацию некорректно, выдав ошибку.

**Пример из реальной жизни:**

Пользователь пытается отключить межконтейнерное взаимодействие (`icc: false`) и использование старых реестров (`disable-legacy-registry: true`).

**Что означают эти параметры?**

-   `"icc": false` (**Inter-Container Communication**): Этот параметр контролирует, могут ли контейнеры, подключенные к одной и той же сети (по умолчанию `bridge`), общаться друг с другом напрямую.
    -   **`true` (по умолчанию):** Все контейнеры могут свободно общаться.
    -   **`false` (рекомендация по безопасности):** Связь между контейнерами в сети `bridge` запрещена. Это важная мера изоляции, которая не позволяет скомпрометированному контейнеру атаковать своих "соседей" по хосту. Для обмена данными между контейнерами следует создавать выделенные сети Docker.

-   `"disable-legacy-registry": true`: Этот параметр запрещает демону Docker взаимодействовать со старыми (v1) registry.
    -   Современные registry, включая Docker Hub, используют API v2, который является более безопасным.
    -   Отключение поддержки v1 реестров — это рекомендация `Docker Bench for Security`, которая снижает вектор атаки и обеспечивает использование только современных, проверенных конечных точек.

-   `"insecure-registries": ["my-registry:5000"]`: Разрешает Docker-демону подключаться к указанным реестрам по незащищенному HTTP. Это снижает безопасность, так как данные передаются в открытом виде, и должно использоваться только в полностью изолированных средах. Подробнее см. в [руководстве по работе с реестрами](./docker_registries.md).

## Подписание образов (Docker Content Trust)

Docker Content Trust (DCT) — это встроенный в Docker механизм, который позволяет использовать цифровые подписи для проверки целостности и издателя образов. Он гарантирует, что образ, который вы используете, был подписан доверенным лицом и не был изменен с момента подписания.

В основе DCT лежит **Notary** — open-source инструмент от Docker для безопасного публикации и верификации контента.

### **Как включить DCT?**

DCT включается установкой переменной окружения:

```sh
export DOCKER_CONTENT_TRUST=1
```

```sh
# Либо для одной команды
sudo DOCKER_CONTENT_TRUST=1 docker pull my-trusted-image:1.0.0

# Либо переключиться в root-shell и установить переменную там, чтобы не из под рута проверка все равно осуществлялась
sudo -s
export DOCKER_CONTENT_TRUST=1
docker pull my-trusted-image:1.0.0
exit
```

### **Что происходит при включенном DCT?**

-   **`docker pull`**: Будут скачиваться только теги образов, которые имеют подпись. Попытка скачать неподписанный или непроверенный образ завершится ошибкой.
-   **`docker push`**: Вы не сможете загрузить образ в репозиторий, если он не подписан. При первой загрузке с подписью вам будет предложено создать ключи.
-   **`docker build`**: Процесс сборки не меняется, но вы не сможете загрузить (push) собранный образ без подписи.

### **Ключевые команды `docker trust`**

-   **`docker trust sign <image>:<tag>`**: Подписать образ.
-   **`docker trust inspect <image>:<tag>`**: Посмотреть информацию о подписях для образа.
-   **`docker trust revoke <image>:<tag>`**: Отозвать подпись.

Использование Docker Content Trust — это важный шаг для построения безопасной цепочки поставок ПО (secure software supply chain), так как он защищает от атак типа "человек посередине" (man-in-the-middle) и использования скомпрометированных образов.

### **Кто подписывает образы и нужно ли мне это делать?**

**Кто подписывает образы на Docker Hub?**

Это зависит от издателя:
-   **Официальные образы (Official Images):** Многие официальные образы (например, `nginx`, `python`, `ubuntu`) подписаны командой Docker. Это одна из причин, почему им стоит доверять.
-   **Проверенные издатели (Verified Publishers):** Крупные вендоры, получившие этот статус, также часто подписывают свои образы.
-   **Все остальные (сообщество, частные лица):** Подавляющее большинство образов на Docker Hub **не подписаны**.

Когда вы включаете `DOCKER_CONTENT_TRUST=1`, вы не сможете скачать ни один неподписанный образ. Ваш мир сужается до небольшого подмножества доверенных, подписанных образов.

**Должен ли я сам подписывать свои образы?**

**Да, если у вас включен `DOCKER_CONTENT_TRUST=1`**.

-   При включенном DCT команда `docker push` завершится ошибкой, если вы попытаетесь загрузить неподписанный тег.
-   Именно вы, как издатель, создаете "корень доверия" для своих образов. При первой попытке `docker push` подписанного тега Docker (Notary) поможет вам сгенерировать необходимые ключи: корневой (root) и ключ репозитория (repository key).
-   **Ваша обязанность** — надежно хранить эти ключи. Потеря корневого ключа приведет к невозможности восстановить контроль над репозиторием в случае утери других ключей.

Таким образом, вы сами становитесь гарантом того, что образы, опубликованные от вашего имени, являются подлинными.

#### Как решить проблему с правами доступа при Bind Mounts?

Это классическая проблема при повышении безопасности. Вот три основных способа ее решения:

**Способ 1: Изменить владельца файлов на хосте (Быстро, но неудобно)**

После того, как контейнер создал файлы, вручную изменить их владельца на хосте:
```bash
# Рекурсивно меняем владельца на текущего пользователя
sudo chown -R $(whoami):$(whoami) /путь/к/вашей/директории
```
*   **Минус:** Это нужно делать каждый раз. Не подходит для автоматизации.

**Способ 2: Синхронизировать UID/GID (Самый частый способ для `bind mounts`)**

Запустить процесс внутри контейнера с тем же UID и GID, что и у вашего пользователя на хосте.
1.  **Узнайте UID/GID на хосте:** `id -u` (например, 1000) и `id -g` (например, 1000).
2.  **Запустите контейнер с флагом `-u`:**

    ```bash
    docker run -u "$(id -u):$(id -g)" \
           -v /путь/на/хосте:/app/data \
           my-image:1.0.0
    ```
Теперь файлы, созданные в контейнере, будут принадлежать вам на хосте.

**Способ 3: Использовать Docker Volumes (Рекомендуемый способ)**

Вместо `bind mounts` используйте **именованные тома (named volumes)**. Docker сам управляет правами в своей служебной директории, и `userns-remap` корректно работает с ними "из коробки".

```bash
docker volume create my-app-data
docker run -v my-app-data:/app/data my-image:1.0.0
```
*   **Плюс:** Более переносимое и управляемое решение.
*   **Минус:** Менее удобно для прямого редактирования файлов с хоста.

### Sigstore/Cosign: Современная альтернатива

Хотя Docker Content Trust (DCT) является встроенным решением, индустрия активно переходит на более гибкий и универсальный стандарт — **Sigstore**, и его основной инструмент **Cosign**.

**Почему Cosign становится стандартом де-факто?**
- **Независимость от Docker:** Cosign работает с любыми OCI-совместимыми образами и реестрами, а не только с Docker Hub.
- **Простота:** Не требует сложной настройки сервера Notary. Подписи хранятся как OCI-артефакты прямо в реестре рядом с образом.
- **Интеграция с Keyless Signing:** Cosign поддерживает "безключевую" подпись, используя OpenID Connect (OIDC) провайдеров (например, Google, GitHub, Microsoft). Это позволяет подписывать образы в CI/CD системах без необходимости управлять долгоживущими секретными ключами.

#### Процесс подписи и верификации с Cosign

  ```bash
  # Загружаем конкретную версию (например, v2.6.0)
  COSIGN_VERSION="v2.6.0"
  curl -sL -o cosign "https://github.com/sigstore/cosign/releases/download/${COSIGN_VERSION}/cosign-linux-amd64"
  sudo mv cosign /usr/local/bin/cosign
  sudo chmod +x /usr/local/bin/cosign
  ```

- **Генерация ключевой пары (классический способ):**

  ```bash
  # Создаст файлы cosign.key (приватный) и cosign.pub (публичный)
  # Вам будет предложено задать пароль для ключа
  cosign generate-key-pair
  ```

- **Подпись образа:**

  ```bash
  # Подписываем образ с помощью приватного ключа
  # Потребуется ввести пароль
  cosign sign --key cosign.key your-registry/your-app:1.0.0
  ```
  Эта команда создаст подпись и загрузит ее в реестр.

- **Верификация образа:**

  ```bash
  # Проверяем подпись с помощью публичного ключа
  cosign verify --key cosign.pub your-registry/your-app:1.0.0
  ```
  Если проверка прошла успешно, команда вернет `0` и выведет информацию о подписи. Это доказывает, что образ не был изменен с момента подписи и был подписан владельцем соответствующего приватного ключа.

### Статический анализ (анализ образов)

#### **Trivy**

**Trivy** — один из самых популярных и простых в использовании сканеров от Aqua Security.

  ```bash
  # Загружаем последнюю версию (или конкретную, например, v0.66.0)
  curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sudo sh -s -- -b /usr/local/bin v0.67.0
  ```

  ```bash
  # 1. Простое сканирование образа
  trivy image python:3.13-slim

  # 2. Сканирование с фильтрацией по уровню уязвимостей (только критические и высокие)
  trivy image --severity HIGH,CRITICAL python:3.13-slim

  # 3. Сохранение отчета в формате JSON для дальнейшей обработки
  trivy image --format json --output report.json python:3.13-slim

  # 4. Сканирование Dockerfile на предмет плохих практик
  trivy config /path/to/your/Dockerfile
  ```

#### **Grype**

**Grype** — мощный сканер от компании Anchore, который также очень популярен и часто используется в связке с Syft (генератором **SBOM**).

> Подробное руководство по SBOM и его генерации с помощью Syft находится в документе [**SBOM: Спецификация Программного Обеспечения**](./docker_sbom.md).

  ```bash
  # Загружаем конкретную версию (например, v0.100.0)
  GRYPE_VERSION="v0.100.0" # Замените на актуальную версию
  wget "https://github.com/anchore/grype/releases/download/${GRYPE_VERSION}/grype_${GRYPE_VERSION#v}_linux_amd64.tar.gz"
  tar -xvzf "grype_${GRYPE_VERSION#v}_linux_amd64.tar.gz"
  sudo mv grype /usr/local/bin/
  rm "grype_${GRYPE_VERSION#v}_linux_amd64.tar.gz"
  ```

  ```bash
  # 1. Простое сканирование образа
  grype python:3.13-slim

  # 2. Завершить выполнение с ошибкой, если найдены уязвимости уровня "high" или выше
  # (полезно для CI/CD)
  grype python:3.13-slim --fail-on high

  # 3. Сканирование с выводом в формате CycloneDX (стандарт для SBOM)
  grype python:3.13-slim -o cyclonedx-json > sbom.json
  ```

#### **Clair**

**Clair** — это open-source проект для статического анализа уязвимостей, который чаще всего используется не как утилита командной строки, а как сервер, интегрированный с Docker-реестрами (например, Harbor, Quay). Он сканирует образы по мере их загрузки в реестр и предоставляет API для получения отчетов об уязвимостях.

#### **Copacetic: Патчинг без пересборки**

**Copacetic** — это инструмент командной строки, который напрямую исправляет уязвимости в образах контейнеров, применяя патчи к существующим слоям без полной пересборки. 

- **Как работает:** Copacetic анализирует отчеты об уязвимостях от сканеров (например, Trivy), определяет необходимые пакеты для обновления и применяет их к образу с помощью BuildKit.
- **Сайт проекта:** [project-copacetic/copacetic](https://github.com/project-copacetic/copacetic)

**Пример использования:**

```bash
# 1. Сканируем образ с помощью Trivy и сохраняем отчет в JSON
trivy image --format json --output trivy-report.json my-vulnerable-app:1.0

# 2. Используем Copacetic для исправления образа на основе отчета
# -i (image): исходный образ
# -r (report): файл отчета от сканера
# -t (tag): имя нового, исправленного образа
copa patch -i my-vulnerable-app:1.0 -r trivy-report.json -t my-vulnerable-app:1.0-patched
```

## Rootless Docker: Современное решение

**Rootless Docker** — это режим, в котором и демон Docker, и контейнеры запускаются от имени **непривилегированного пользователя**. Это наиболее эффективный способ защиты от атак, связанных с повышением привилегий.

- **Как это работает:** Используются **пространства имен пользователей (user namespaces)** ядра Linux. UID `root` (0) внутри контейнера сопоставляется с UID непривилегированного пользователя на хосте (например, 1001).
- **Преимущества:** Даже если злоумышленник сбежит из контейнера или получит доступ к сокету, он получит права не `root` на хосте, а лишь права того пользователя, от имени которого запущен Rootless Docker.

  ```sh
  # Устанавливаем необходимые утилиты
  sudo apt-get install -y uidmap
  # Запускаем установочный скрипт от обычного пользователя
  dockerd-rootless-setuptool.sh install
  ```
  
- **Ограничения:** Rootless-режим имеет некоторые ограничения, связанные с работой сети (например, невозможность пробрасывать порты ниже 1024 без дополнительных настроек) и драйверов хранения.
