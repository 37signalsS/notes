# Docker Swarm: Основные концепции

## Определения

*   **Узел (Node):** Физическая или виртуальная машина с установленным Docker Engine, являющаяся частью Swarm-кластера. Узлы делятся на **менеджеров** и **рабочих**.
*   **Сервис (Service):** Декларативное описание задачи для выполнения в кластере. Определяет, какой Docker-образ использовать, какое количество реплик запустить, какие порты открыть, и другие параметры.
*   **Задача (Task):** Атомарная единица работы в Swarm, представляющая собой один Docker-контейнер, который менеджер запускает на рабочем узле.
*   **Балансировка нагрузки (Routing Mesh):** Встроенный в Swarm механизм, который распределяет входящие запросы между репликами одного сервиса. Он позволяет обратиться к сервису по опубликованному порту на *любом* узле кластера, и запрос будет автоматически перенаправлен на нужный контейнер, даже если он запущен на другой машине.

## Базовые концепции

### Архитектура: Менеджеры и Рабочие узлы

Кластер Docker Swarm состоит из двух типов узлов:

*   **Менеджеры (Manager Nodes):**
    *   **Управление и оркестрация:** Отвечают за поддержание желаемого состояния кластера, распределяют задачи (контейнеры) по рабочим узлам, обрабатывают API-запросы и управляют жизненным циклом сервисов.
    *   **Консенсус и состояние:** Для поддержания консистентного состояния кластера менеджеры используют алгоритм консенсуса **Raft**.
    *   **Высокая доступность:** Для отказоустойчивости рекомендуется использовать нечетное количество менеджеров (3 или 5). Кластер будет работать, пока доступно большинство (кворум) из них.

*   **Рабочие узлы (Worker Nodes):**
    *   **Выполнение задач:** Их единственная цель — запускать и останавливать контейнеры в соответствии с инструкциями, полученными от менеджеров.
    *   **Отчетность:** Сообщают менеджерам о своем состоянии и состоянии запущенных на них задач.

Все узлы в кластере общаются друг с другом через зашифрованный **TLS-канал**.

## Практические сценарии

### Отказоустойчивость лидера-менеджера

Если узел, являющийся лидером, становится недоступным (например, из-за сбоя оборудования), происходит следующий процесс:
1.  Оставшиеся менеджеры, используя протокол **Raft**, выбирают нового лидера из своего числа.
2.  Swarm автоматически переносит сервисы (задачи), работавшие на отказавшем узле, на другие доступные рабочие узлы, чтобы поддержать заданное количество реплик.
3.  После восстановления отказавший узел может снова присоединиться к кластеру, но уже не в роли лидера.

## Дополнительная информация

*   Рабочий узел может быть повышен до роли менеджера с помощью команды `docker node promote <NODE-ID>`.
*   Менеджер может быть понижен до роли рабочего с помощью `docker node demote <NODE-ID>`.
