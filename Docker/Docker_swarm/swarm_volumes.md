# Docker Swarm: Управление томами

## Определения

*   **Локальный том (Local Volume):** Стандартный Docker-том, данные которого хранятся на файловой системе одного конкретного узла Swarm.

## Базовые концепции

### Проблема персистентности
По умолчанию, тома, используемые Docker Swarm, являются **локальными**. Это создает проблему отсутствия персистентности данных при перемещении контейнеров между узлами. Если задача сервиса переносится с одного узла на другой (например, при сбое узла или масштабировании), данные, хранимые в локальном томе, становятся недоступными на новом узле. Это делает стандартные Docker-тома непригодными для stateful-приложений в распределенной среде Swarm без дополнительных решений.

### Подходы к решению

Для обеспечения постоянного доступа к данным независимо от местоположения контейнера используются следующие подходы:

*   **Сетевые файловые системы (NFS):**
    *   **Принцип:** Монтирование общих сетевых ресурсов (например, NFS-шары) на все узлы Swarm. Таким образом, любой контейнер, запущенный на любом узле, может получить доступ к одним и тем же данным.
    *   **Преимущества:** Простота реализации, хорошо подходит для общих файлов конфигурации, статического контента.
    *   **Ограничения:** Может иметь низкую производительность для интенсивных операций ввода/вывода (особенно для баз данных), является единой точкой отказа, требует ручного управления файловой системой вне Docker.

*   **Драйверы хранения (Storage Drivers / Volume Plugins):**
    *   **Принцип:** Использование специализированных плагинов, которые интегрируются с распределенными системами хранения данных (такими как Ceph, GlusterFS, Portworx, Azure Disk, AWS EBS). Эти драйверы позволяют Docker динамически выделять и управлять томами из общей системы хранения, делая их доступными для любого узла Swarm.
    *   **Преимущества:** Высокая доступность и производительность, автоматическое управление томами, устойчивость к отказам узлов, нативная интеграция с оркестратором.
    *   **Ограничения:** Большая сложность настройки и управления самой распределенной системой хранения, дополнительные накладные расходы.

## Практические сценарии

### Пример использования тома с драйвером

Хотя конкретная реализация зависит от выбранного драйвера, общий паттерн выглядит следующим образом:

1.  **Создание тома с указанием драйвера:**
    ```sh
    # Пример для драйвера 'rexray/ebs' (AWS EBS)
    docker volume create --driver rexray/ebs --name my-shared-volume --opt size=10
    ```

2.  **Использование тома в сервисе:**
    ```yaml
    # docker-compose.yml
    version: '3.8'
    
    services:
      database:
        image: postgres:16
        volumes:
          - my-shared-volume:/var/lib/postgresql/data
    
    volumes:
      my-shared-volume:
        external: true
    ```

## Дополнительная информация

*   Выбор между NFS и специализированными драйверами хранения зависит от требований к производительности, сложности и бюджета проекта. Для критически важных баз данных предпочтительнее использовать драйверы хранения.
