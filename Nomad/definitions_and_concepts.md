# Nomad — определения и базовые концепции

## Определения

**Nomad** — легковесный оркестратор от HashiCorp для планирования (scheduling) и запуска приложений (workloads). В отличие от Kubernetes — комплексной платформы «всё в одном» — Nomad придерживается философии UNIX: одна задача, но выполненная хорошо.

**Ключевая особенность:** единый бинарный файл без внешних зависимостей; поддерживает контейнеры, бинарные приложения, Java, QEMU/VM и иные типы workload'ов.

**Job** — основная единица развёртывания в Nomad, описываемая в HCL-файле. Определяет тип (service/batch/system), группы задач, ресурсы, ограничения и политики развёртывания.

**Task Group** — логическая группа задач, размещаемых на одном узле. Параметр `count` задаёт количество реплик. Задачи внутри одной группы совместно используют ресурсы сети и тома.

**Task** — минимальная единица работы, выполняемая конкретным **драйвером** (docker, podman, exec, qemu, java, raw_exec, exec2).

**Allocation (Аллокация)** — экземпляр (инстанс) Task Group, назначенный на конкретный узел. Это атомарная единица планирования: либо вся группа задач размещается на узле, либо нет.

**Evaluation (Эвалюация)** — процесс, в ходе которого сервер Nomad сравнивает желаемое состояние (Job) с текущим состоянием кластера и принимает решение о создании, обновлении или удалении аллокаций.

**Node** — физический или виртуальный узел кластера, на котором запущен Nomad Client агент. Узлы регистрируются в кластере через процесс fingerprinting.

**Plan** — промежуточный результат эвалюации, содержащий предварительные действия планировщика (создание, миграция, удаление аллокаций). План отправляется на утверждение перед применением.

**Constraint** — жёсткое правило размещения, при невыполнении которого задача не будет запущена на узле (например, версия ядра ОС или наличие определённого драйвера).

**Affinity** — мягкое предпочтение размещения; Nomad будет стремиться выполнить аффинность, но может проигнорировать его при дефиците ресурсов.

**Workload Identity** — механизм (введенный в v1.6), позволяющий задачам получать JWT-токены для безопасной аутентификации в Vault и Consul без использования статических секретов.

**Namespace** — логическая изоляция задач внутри кластера. ACL-политики, квоты и параметры планирования могут привязываться к неймспейсу, обеспечивая мультитенантность.

**Quota** — ограничение потребления ресурсов (CPU, memory, задачи) на уровне региона или неймспейса. Применяется при планировании: если квота исчерпана, новые аллокации отклоняются до освобождения ресурсов.

**Drain** — режим узла, при котором Nomad прекращает размещение новых аллокаций и последовательно останавливает/перемещает существующие задачи.

Актуальная информация о версиях: [Nomad — версии и поддержка](./advanced_topics.md#версии-и-поддержка).

## Основные концепции

### Архитектура

Кластер Nomad состоит из двух типов агентов, работающих в рамках одного бинарного файла:

| Компонент | Назначение |
| :--- | :--- |
| **Server** | Управление кластером, хранение состояния (**Raft**), планирование (scheduling), обработка эвалюаций. |
| **Client** | Запуск задач, отчёт о доступных ресурсах (**fingerprinting**), взаимодействие с runtime через драйверы. |

- **Консенсус (Raft):** Серверы используют протокол Raft для обеспечения согласованности данных. Для работы кворума необходимо большинство серверов (`(N/2)+1`).
- **Gossip (Serf):** Агенты используют gossip-протокол для обнаружения друг друга и мониторинга здоровья узлов.
- **Режимы развёртывания:** Standalone (1 сервер), High Availability (3–5 серверов), Federated (связь между регионами).

#### Режимы работы клиента

- **Static:** Фиксированный набор портов и ресурсов. Подходит для Bare Metal с постоянной конфигурацией.
- **Ephemeral:** Динамическое выделение портов и ресурсов. Используется в облачных/автомасштабируемых средах.

#### Федерация кластеров

Федерация объединяет несколько регионов (Region) в единую систему управления. Один регион назначается **Authoritative Region** — источник правды для ACL и глобальных сущностей. Ссылки между регионами устанавливаются через `nomad server join` и секрет federation-ключа.

### Жизненный цикл задачи

Понимание полного цикла необходимо для SRE при диагностике и отладке:

1. **Создание/изменение Job-файла:** Оператор загружает HCL-файл в Nomad (`nomad job run` или через API).
2. **Evaluation:** Сервер создаёт эвалюацию и сравнивает желаемое состояние с текущим.
3. **Plan:** Планировщик вычисляет набор атомарных изменений (create, migrate, stop, update).
4. **Apply:** При ручном или автоматическом подтверждении план применяется.
5. **Allocation:** Клиенты получают задания и запускают задачи через выбранный драйвер.
6. **Service Registration:** При `type = "service"` задача регистрируется в Native Service Discovery или Consul.
7. **Monitoring:** Постоянный контроль health checks; при провале — автоматический перезапуск или маркировка аллокации как unhealthy.
8. **Update/Drain:** При изменении Job или переводе узла в drain происходят миграция/остановка аллокаций.
9. **Completion:** При `type = "batch"` или остановке Job аллокации завершаются и удаляются из планировщика.

### Модель ресурсов

Nomad использует модель ресурсов для гарантированного размещения задач:

- **CPU:** Указывается в MHz (например, `500` = 500 MHz) или cores (например, `1000` = 1 ядро при `reserved_by = "Nomad"`).
- **Memory:** Указывается в MB. Ограничение применяется через cgroups (Linux) или аналоги ОС.
- **Ephemeral Disk:** Временное хранилище для контейнеров/задач. Размер задаётся в MB, поддерживает миграцию (`migrate = true`) для сохранения данных при перезапуске.

**Важно:** Ресурсы резервируются эксклюзивно для аллокации. Oversubscription (размещение больше задач, чем ресурсов) не производится. Если узел не может удовлетворить запрос `resources`, планирование отклоняется.

### Типы задач (Job Types)

| Тип | Назначение | Примеры |
| :--- | :--- | :--- |
| **service** | Долгоживущие процессы (daemon) | Веб-серверы, API, микросервисы |
| **batch** | Одноразовые/периодические задачи | ETL, бэкапы, cron-задачи |
| **system** | Запуск по одной копии на каждом узле | Мониторинг, логи, security agents |
| **sysbatch** | Одноразовые задачи на каждом узле | Массовые обновления, диагностика |

### Драйверы задач (Task Drivers)

Nomad поддерживает широкий спектр рантаймов:

- **Docker / Podman:** Контейнеризация с полной изоляцией.
- **Exec2 (GA v1.9):** Безопасный запуск обычных процессов с использованием Landlock LSM и cgroups v2.
- **Java:** Запуск JAR-файлов без контейнеров с автоматическим обнаружением зависимостей.
- **QEMU / Libvirt (v1.9):** Полноценные виртуальные машины. Используется для legacy-приложений или требующих специфической ОС.
- **Raw Exec:** Запуск команд с правами пользователя Nomad (минимум изоляции, максимум производительности). Требует осторожного применения.

### Ключевые блоки job-файла

- `job` — имя, датацентры, тип, приоритет.
- `group` — параметры репликации (`count`), сети, тома.
- `network` — порты, режимы (static/dynamic/bridge/none/cni).
- `service` — регистрация в Consul или **Native Service Discovery** (v1.6+).
- `task` — выбор драйвера, конфигурация, ресурсы, интеграция с Vault/Consul.
- `identity` — блок для Workload Identity (OIDC), предоставляет JWT задаче без статических секретов.
- `template` — рендеринг конфигураций через Consul Template (Vault, Consul KV, сервисы).
- `variables` — работа с встроенным хранилищем переменных (`nomad var`).
- `periodic` — cron-расписание для batch jobs.
- `update` — стратегия раскатки (canary, rolling, blue-green) и параметры авто-отката.
- `constraint` — жесткие ограничения (OS, kernel version, `attr.unique.hostname`).
- `affinity` — мягкие предпочтения по размещению.
- `spread` — распределение аллокаций по критериям (зоны, датацентры).
- `resources` — CPU (mhz/cores), memory (MB), ephemeral disk.
- `vault` — политики для секретов и Workload Identity.

### Сетевая модель

Nomad предоставляет гибкие варианты сетевой конфигурации:

#### Режимы сети

| Режим | Назначение | Пример |
| :--- | :--- | :--- |
| **bridge** | Виртуальный мост (CNI или встроенный) | Docker-контейнеры с NAT |
| **host** | Прямое использование интерфейса узла | Высокопроизводительные сервисы |
| **none** | Без сети | Фоновые пакетные задачи |
| **cni** | Внешний CNI плагин (Calico, Cilium) | Продвинутые политики сети |

#### Port Allocation

- **Dynamic:** Nomad автоматически назначает свободный порт из указанного диапазона.
- **Static:** Фиксированный порт, требующий отсутствия конфликтов на узле.

```hcl
network {
  port "http" { to = 8080 }  # Dynamic allocation
  port "metrics" { static = 9090 }  # Static
}
```

**Резервирование портов:** Используйте `reserved_ports` в конфигурации клиента для исключения диапазонов из динамического распределения.

### Хранилище и тома

#### Host Volumes

Монтирование путей с локального диска узла. Подходит для состояния, требующего быстрого доступа:

```hcl
volume "local-data" {
  type      = "host"
  source    = "nomad/alloc_mounts"
  read_only = false
}

task "app" {
  volume_mount {
    volume      = "local-data"
    destination = "/var/lib/app"
  }
}
```

#### Ephemeral Storage

Каждая задача получает ephemeral диск (tmpfs или корневой overlay) ограниченного размера. Размер задаётся в блоке `resources`:

```hcl
resources {
  cpu    = 500
  memory = 512
  ephemeral_disk {
    size     = 1024  # MB
    migrate  = true
    sticky   = false
  }
}
```

#### CSI Volumes

Динамическое подключение внешних блочных устройств через Container Storage Interface (подробнее в [advanced_topics.md](./advanced_topics.md)).

### Ограничения и предпочтения

#### Constraints

Жёсткие правила, определяющие, где может быть запущена задача:

```hcl
constraint {
  attribute = "${attr.kernel.name}"
  operator  = "="
  value     = "linux"
}

constraint {
  attribute = "${attr.cpu.arch}"
  operator  = "set_contains"
  value     = "amd64;arm64"
}
```

#### Affinities

Мягкие предпочтения, повышающие вероятность размещения на предпочтительных узлах:

```hcl
affinity {
  attribute = "${attr.unique.hostname}"
  operator  = "set_contains"
  value     = "web-node-"
  weight    = 50
}
```

#### Spread

Распределение аллокаций по критериям для повышения отказоустойчивости:

```hcl
spread {
  attribute = "${attr.platform.az}"
  weight    = 100
}
```

### Service Discovery и health checks

Native Service Discovery (v1.6+) позволяет регистрировать сервисы напрямую в Nomad без отдельного агента Consul. Для продвинутых сценариев (service mesh, multi-datacenter) используется Consul.

```hcl
service {
  name     = "frontend"
  provider = "nomad"
  port     = "http"

  check {
    type     = "http"
    path     = "/health"
    interval = "10s"
    timeout  = "2s"
  }
}
```

**Типы проверок:**
- **Script:** Выполнение команды внутри задачи (`check_script`).
- **HTTP/TCP:** Проверка доступности endpoint.
- **TTL:** Задача самостоятельно сообщает о здоровье через Nomad API.

### Шаблонизация и работа с секретами

Блок `template` использует синтаксис Consul Template для рендеринга конфигураций на лету. Это ключевой механизм интеграции с Vault и Consul.

```hcl
template {
  data        = <<EOH
{{ with secret "kv/data/webapp/config" }}
DB_PASSWORD="{{ .Data.data.db_password }}"
{{ end }}
EOH
  destination = "secrets/env"
  env         = true
  change_mode = "restart"
}
```

**Параметры:**
- `env = true` — экспорт переменных в окружение задачи.
- `change_mode = "restart"` — перезапуск задачи при изменении секрета.
- `splay = "5s"` — случайная задержка для предотвращения thundering herd.

### Приоритеты и вытеснение

Каждому заданию назначается приоритет (0–100, по умолчанию 50). При дефиците ресурсов Nomad может вытеснить (preempt) низкоприоритетные задачи в пользу высокоприоритетных.

**Правила работы:**
- Задания с `priority = 100` reserved для системных задач (`type = "system"`).
- Вытеснение происходит только между заданиями одного типа (service/batch) или при явном указании.
- При вытеснении Nomad отправляет `SIGTERM`, затем `SIGKILL` после `kill_timeout`.

**Рекомендации:**
- Используйте `priority` для разделения критических и фоновых задач.
- Настройте `kill_timeout` и `shutdown_delay` для корректного завершения.
- Для system jobs установите `priority = 100` и `coalesce = true`.

### Интеграция с экосистемой HashiCorp

- **[Consul](../Consul/consul_overview.md):** Service Discovery, Health Checking, Service Mesh (Consul Connect), Native SD (без агента Consul на узле).
- **[Vault](../Vault/overview.md):** Динамические секреты, шифрование (Transit), Workload Identity для OIDC-авторизации.
- **[Terraform](https://developer.hashicorp.com/terraform):** Управление инфраструктурой (nodes) и приложениями (jobs).
- **Boundary:** Безопасный доступ к инстансам без публикации портов наружу.

### Сравнение с другими оркестраторами

| Критерий | **Nomad** | **[Kubernetes](../Kubernetes/kubernetes_overview.md)** | **[Docker Swarm](../Docker_swarm/docker_swarm_overview.md)** |
| :--- | :--- | :--- | :--- |
| **Архитектура** | Единый бинарник, встроенная БД | Множество компонентов, etcd | Встроен в Docker Engine |
| **Workload'ы** | Контейнеры + Legacy (Binaries, Java, VM) | Преимущественно контейнеры | Только Docker-контейнеры |
| **Масштабируемость** | Очень высокая (10k+ узлов) | Высокая (5k узлов официально) | Средняя (~1k узлов) |
| **Сложность** | Низкая/Средняя (Pragmatic) | Высокая (Operational overhead) | Низкая |
| **Service Discovery** | Native SD или Consul | Встроенный (DNS, Services) | Встроенный (Routing Mesh) |
| **Сетевая модель** | CNI, Bridge, Host, Mesh | Преимущественно CNI/Mesh | Overlay (Ingress/Routing Mesh) |

### Преимущества и недостатки

**Преимущества:**

- Единый workflow для любых типов нагрузки (Docker + Legacy).
- Минимальный порог вхождения и легковесность (идеально для Edge/IoT).
- Нативная федерация для мульти-региональных кластеров.
- Глубокая интеграция с Vault и Consul через Workload Identity.
- Поддержка виртуальных машин (QEMU/Libvirt) наравне с контейнерами.

**Недостатки:**

- Меньшая экосистема готовых решений (операторов) по сравнению с Kubernetes.
- Специфичный синтаксис HCL (хотя есть поддержка JSON).
- Для сложных корпоративных функций (Namespaces, Quotas) требуется Enterprise-версия.
- Лицензия Business Source License (BSL) накладывает ограничения на коммерческое использование в сервисах конкурентов.

## Практические сценарии

Подробные примеры и конфигурации доступны в файле **[Nomad — практические сценарии](./practical_scenarios.md)**. Краткий обзор:

1.  **Микросервисы:** Запуск контейнеров с автоматической регистрацией в Service Mesh.
2.  **Высокобезопасная изоляция:** Запуск бинарных файлов через Exec2 + Landlock.
3.  **Пакетная обработка (Batch):** Выполнение ETL-задач и бэкапов по расписанию.
4.  **Оркестрация ВМ:** Использование драйвера QEMU для запуска legacy-приложений.
5.  **Обновления без простоя:** Blue-Green и Canary стратегии.
6.  **Работа с данными:** CSI-тома и host-монтирования.
7.  **Edge Computing:** Размещение клиентов на удалённых устройствах.
8.  **Глобальная федерация:** Управление multi-region кластером.
9.  **Мультитенантность:** Namespaces и Quotas.
10. **Автоматическое масштабирование:** Nomad Autoscaler по метрикам.
11. **Обслуживание узлов:** Безопасный drain и maintenance mode.
12. **Шаблонизация:** Nomad Pack для повторного использования конфигураций.
13. **Безопасность:** Sentinel-политики и ACL.
14. **Disaster Recovery:** Резервное копирование состояния Raft.
15. **Мониторинг:** Интеграция с Prometheus для SRE-дашбордов.
