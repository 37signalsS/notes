# Nomad — Вопросы для собеседования

## Определения

**Типичные вопросы на собеседовании по Nomad** — набор технических вопросов и практических кейсов, проверяющих понимание архитектуры Nomad, работы с кластером, интеграции с экосистемой HashiCorp и production-практик.

## Базовый уровень

### Архитектура

**Q: Что такое Nomad и чем он отличается от Kubernetes?**

> Nomad — легковесный оркестратор от HashiCorp, представляющий собой единый бинарный файл. В отличие от Kubernetes (комплексная платформа с множеством компонентов: etcd, API server, scheduler, kubelet), Nomad реализует всю функциональность в одном процессе. Key differences:
> - Nomad проще в установке и управлении (1 бинарник vs 15+ компонентов K8s).
> - Nomad поддерживает не только контейнеры, но и бинарники, Java, VM (QEMU).
> - Nomad масштабируется до 10K+ узлов (K8s официально ~5K).
> - Nomad использует Raft для консенсуса (как etcd), но встроенный.

**Q: Опиши архитектуру Nomad кластера.**

> Кластер состоит из серверов и клиентов:
> - **Серверы** (3 или 5): управляют кластером, хранят состояние через Raft, выполняют планирование. Кворум — `(N/2)+1`.
> - **Клиенты**: запускают задачи, отчитываются о ресурсах (fingerprinting), взаимодействуют с драйверами.
> - **Связь**: Gossip (Serf) для обнаружения, RPC для коммуникации, HTTP API для клиентов.

**Q: Что такое Allocation и как она связана с Task Group?**

> **Allocation** — атомарная единица планирования, представляющая экземпляр Task Group на конкретном узле. Если в Job указано `count = 3` для группы tasks, Nomad создаст 3 аллокации. Аллокация содержит все задачи группы и гарантирует их совместное размещение на одном узле.

**Q: Как работает Raft в Nomad?**

> Raft — протокол консенсуса для хранения состояния. Ноды выбирают лидера через majority. Лидер принимает записи, реплицирует их на follower'ов. При отказе лидера происходит выбор нового. Для кворума нужно `(N/2)+1` серверов.

### Задачи и драйверы

**Q: Какие типы задач 지원ает Nomad?**

> - **service** — долгоживущие процессы (web-серверы, API).
> - **batch** — одноразовые/периодические задачи (ETL, бэкапы).
> - **system** — по одной копии на каждом узле (мониторинг, агенты).
> - **sysbatch** — одноразовые задачи на каждом узле.

**Q: В чём разница между docker, exec и exec2?**

> - **Docker** — запуск контейнеров, полная изоляция.
> - **Exec** — запуск процессов с изоляцией через user/ns.
> - **Exec2** (v1.9+) — улучшенная безопасность через Landlock LSM и cgroups v2.

### Сеть и хранилище

**Q: Какие режимы сети поддерживает Nomad?**

> - **bridge** — виртуальный мост (как Docker), NAT.
> - **host** — прямой доступ к интерфейсу узла.
> - **none** — без сети.
> - **cni** — внешние CNI-плагины (Calico, Cilium).

**Q: В чём разница между Host Volume и CSI Volume?**

> - **Host Volume** — монтирование с локального диска узла, быстрый доступ, но данные привязаны к узлу.
> - **CSI Volume** — динамическое подключение внешних блочных устройств через Container Storage Interface, поддерживает миграцию.

## Средний уровень

### Безопасность

**Q: Как настроить ACL в Nomad?**

> 1. Инициализация: `nomad acl bootstrap` — создаёт мастер-токен.
> 2. Создание политик в HCL: namespace capabilities, node/agent/operator permissions.
> 3. Применение: `nomad acl policy apply`.
> 4. Создание токенов: `nomad acl token create -policy=<policy>`.

**Q: Что такое Workload Identity и зачем он нужен?**

> Workload Identity (v1.6+) — механизм OIDC-аутентификации. Задачи получают JWT-токены для безопасного взаимодействия с Vault и Consul без статических секретов. Токены автоматически ротируются и привязаны к конкретной аллокации.

**Q: Как работает mTLS в Consul Connect с Nomad?**

> Consul Connect предоставляет Service Mesh. Каждая задача Nomad регистрируется в Consul, получает TLS-сертификат (SVID через SPIFFE). Envoy sidecar перехватывает трафик, шифрует его и проверяет Intentions (политики авторизации).

### Стратегии обновления

**Q: Как работает Canary Deployment в Nomad?**

> В блоке `update` указывается `canary = N`. Nomad запускает N новых аллокаций (canary) параллельно со старыми. После проверки здоровья (health check) выполняется ручной или автоматический промоут. При ошибке — автоматический откат (`auto_revert = true`).

**Q: Как выполняется Rolling Update?**

> `max_parallel` определяет количество одновременно обновляемых аллокаций. Nomad обновляет их последовательно, проверяя `min_healthy_time`. При ошибке — `auto_revert`.

### Диагностика

**Q: Сервис не работает. Как диагностируешь?**

> 1. `nomad job status <job>` — статус джоба.
> 2. `nomad alloc status <alloc-id>` — статус аллокации.
> 3. `nomad alloc logs <alloc-id> <task>` — логи задачи.
> 4. `nomad job plan <job.hcl>` — dry-run для выявления проблем.
> 5. Проверка constraints, quotas, drain status.
> 6. Проверка Consul health check.

**Q: Что делать если "No nodes are available"?**

> - Проверить `constraints` (версия ядра, драйвер).
> - Убедиться, что драйвер установлен: `nomad node status -stats`.
> - Проверить квоты: `nomad quota status`.
> - Убедиться, что узлы не в drain/ineligible.

## Продвинутый уровень

### Production

**Q: Как развернуть Nomad в production?**

> 1. 3 или 5 серверов для HA (кворум).
> 2. TLS на всех серверах и клиентах.
> 3. ACL с минимальными привилегиями.
> 4. Consul для service discovery.
> 5. Vault для секретов.
> 6. Prometheus для мониторинга.
> 7. Регулярные Raft snapshots.
> 8. Drain перед обслуживанием узлов.

**Q: Как обновить Nomad кластер без простоя?**

> 1. Создать Raft snapshot.
> 2. Обновлять серверы по одному (не лидера последним).
> 3. Проверять кворум после каждого обновления.
> 4. Обновлять клиенты с drain.
> 5. Проверять совместимость версий.

**Q: Как настроить multi-region федерацию?**

> 1. Настроить Authoritative Region с ACL.
> 2. Подключить другие регионы: `nomad server join`.
> 3. Настроить replication ACL-токенов.
> 4. Проверить: `nomad federation list`.

### Интеграция с экосистемой

**Q: Как интегрировать Nomad с Terraform?**

> Использовать провайдер `hashicorp/nomad`:
> - `nomad_job` для управления джобами.
> - `nomad_acl_policy` для ACL.
> - `nomad_namespace` для неймспейсов.
> - Workflow: `terraform plan` → `terraform apply`.

**Q: Как настроить CI/CD для Nomad?**

> Варианты:
> 1. Прямой `nomad job run` из CI.
> 2. Nomad Pack через CI.
> 3. Terraform Provider.
> 4. GitOps (Argo CD).
> Рекомендация: минимальный ACL-токен для CI, plan перед apply, auto_revert.

**Q: Как собирать логи из Nomad?**

> - Promtail как system job, монтирующий `/opt/nomad/data/alloc`.
> - Vector для маршрутизации в Loki/Elasticsearch.
> - Structured logging в приложении для эффективного парсинга.

### Кейсы

**Q: Ситуация: Deployment stuck. Что делаешь?**

> 1. `nomad deployment status` — проверка статуса деплоя.
> 2. `nomad alloc status <canary-alloc-id>` — проверка canary.
> 3. Health check не проходит? → Логи задачи.
> 4. Progress deadline превышен? → Увеличить или исправить образ.
> 5. Откат: `nomad deployment fail <id>` или `nomad job rollback`.

**Q: Ситуация: Drain stuck на клиенте.**

> 1. Проверить есть ли system jobs: `nomad job status -type=system`.
> 2. Попробовать `-ignore-system-jobs`.
> 3. Проверить `kill_timeout` задач — возможно, слишком длинный.
> 4. Для аварийного освобождения: `nomad node drain -enable -self -force`.

**Q: Ситуация: Nomad leader lost.**

> 1. Проверить доступность серверов: `nomad server members`.
> 2. Проверить кворум: `(N/2)+1` серверов должны быть alive.
> 3. Если нет кворума — восстановить серверы.
> 4. Если есть кворум — подождать выборов (обычно < 30 сек).
> 5. Проверить сеть между серверами.
