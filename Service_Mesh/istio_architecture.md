# Istio: компоненты и архитектура

## Определения

**Istio** — это открытая и наиболее функционально богатая реализация [Service Mesh](./service_mesh_concepts.md). Платформа предоставляет унифицированные механизмы для безопасного соединения, управления и наблюдения за микросервисами в облачных средах, таких как Kubernetes.

Архитектура Istio разделена на плоскость данных (Data Plane) и плоскость управления (Control Plane).

## Основные концепции

### Плоскость данных (Data Plane)

Состоит из **прокси-серверов Envoy**, развернутых в виде [sidecar-контейнеров](./proxy_sidecar.md) рядом с каждым сервисом. Эти прокси перехватывают весь сетевой трафик и применяют к нему правила, полученные от плоскости управления. Дополнительно используются шлюзы для управления трафиком на границе кластера:

- **Ingress Gateway**: Контролирует входящий трафик.
- **Egress Gateway**: Контролирует исходящий трафик.

### Плоскость управления (Control Plane)

В современных версиях Istio реализована в виде единого монолитного компонента **istiod**. Он выполняет следующие функции:

- **Конфигурация и распространение**: Преобразует высокоуровневые правила маршрутизации и политики из CRD Istio в конфигурацию для Envoy и распространяет ее по протоколу xDS.
- **Сервис-дискавери**: Отслеживает эндпоинты сервисов в кластере.
- **Центр сертификации (CA)**: Выпускает и ротирует сертификаты для обеспечения mTLS между компонентами.

### Модель конфигурации (CRD)

Istio расширяет Kubernetes через набор Custom Resource Definitions (CRD) для декларативного управления сетевым поведением. Ключевые ресурсы:

- `VirtualService`: Определяет правила маршрутизации трафика.
- `DestinationRule`: Задает политики для целевых сервисов (балансировка, подмножества версий).
- `Gateway`: Конфигурирует Ingress/Egress шлюзы.
- `ServiceEntry`: Позволяет добавить в сетку внешние сервисы.
- `AuthorizationPolicy`: Определяет политики доступа.

## Практические сценарии

### Маршрутизация на основе заголовка

В этом примере трафик для пользователей с заголовком `x-user: canary` направляется на версию `v2` сервиса `reviews`. Весь остальной трафик — на `v1`. Это классический пример канареечного тестирования по пользовательской группе.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts: [ "reviews.default.svc.cluster.local" ]
  http:
  - match:
    - headers:
        x-user:
          exact: canary
    route:
    - destination: { host: reviews, subset: v2 }
  - route:
    - destination: { host: reviews, subset: v1 }
---
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews.default.svc.cluster.local
  subsets:
  - name: v1
    labels: { version: v1 }
  - name: v2
    labels: { version: v2 }
```
