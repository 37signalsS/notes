# Архитектура и компоненты Istio

## Определения

**Istio** — открытая реализация [Service Mesh](./service_mesh_concepts.md) с наиболее полным набором функций для управления микросервисами. Платформа обеспечивает безопасное соединение, управление трафиком и наблюдение за рабочими нагрузками в облачных средах (преимущественно Kubernetes).

Архитектура Istio разделена на две плоскости:

- **Control Plane (Плоскость управления)**: управляет конфигурацией и безопасностью сетки.
- **Data Plane (Плоскость данных)**: обрабатывает сетевой трафик между сервисами.

---

## Основные концепции

### Плоскость управления: istiod

В современных версиях Istio плоскость управления представлена единым компонентом **istiod**. Он преобразует высокоуровневые декларативные правила (CRD) в специфичную конфигурацию для прокси-серверов.

Основные функции `istiod`:

- **Конфигурация (xDS)**: преобразует YAML-манифесты в инструкции для прокси и распространяет их по протоколу xDS.
- **Service Discovery**: извлекает информацию об эндпоинтах из реестра Kubernetes.
- **Безопасность (CA)**: выступает в роли центра сертификации, выпуская TLS-сертификаты для аутентификации сервисов (mTLS). Идентификация основана на **ServiceAccount** Kubernetes.

### Модели плоскости данных (Data Plane)

Istio поддерживает две основные модели развертывания прокси-слоя.

#### 1. Модель Sidecar

Классический подход, где [прокси-сервер Envoy](./proxy_sidecar.md) запускается в каждом Pod рядом с основным приложением.

- **Механизм**: трафик перехватывается с помощью `iptables` и направляется в Envoy.
- **Преимущества**: максимальная изоляция ресурсов, поддержка всех L7-функций «из коробки».
- **Недостатки**: высокий оверхед по памяти и CPU (прокси в каждом Pod), сложность обновления без перезапуска приложений.

#### 2. Модель Ambient (Sidecar-less)

Новый режим (доступен с Istio 1.29), разделяющий функции прокси на два уровня для повышения эффективности.

- **L4-слой (Ztunnel)**: DaemonSet на каждой ноде. Обеспечивает mTLS, L4-авторизацию и сбор телеметрии. Использует протокол **HBONE** (HTTP-Based Overlay Network Environment) для передачи трафика.
- **L7-слой (Waypoint Proxy)**: Deployment на базе Envoy в конкретном неймспейсе. Подключается только для тех сервисов, которым нужны сложные функции (маршрутизация, фильтрация заголовков).

**Преимущества Ambient**:

- Снижение потребления ресурсов на 30–50%.
- Возможность внедрения Service Mesh без модификации манифестов приложений и перезапуска Pod.

### Сравнение моделей развертывания

| Критерий | Sidecar | Ambient |
| :--- | :--- | :--- |
| **Изоляция** | Максимальная (на уровне Pod) | Разделяемая (на ноду/неймспейс) |
| **Ресурсы (RAM)** | Высокое (100–300 МБ на под) | Низкое (разделяемые прокси) |
| **Внедрение** | Требует перезапуска Pod | Без перезапуска (label на namespace) |
| **Мультикластер** | Промышленная эксплуатация (GA) | В стадии тестирования (Beta) |

## Практические сценарии

### Включение режима Ambient для неймспейса

Для использования Ambient-режима необходимо установить Istio с соответствующим профилем и пометить неймспейс.

```bash
# Установка Istio с поддержкой Ambient
istioctl install --set profile=ambient -y
# → ✔ Istio core installed
# → ✔ Istiod installed
# → ✔ CNI installed
# → ✔ Ztunnel installed

# Активация Ambient в неймспейсе
kubectl label namespace default istio.io/dataplane-mode=ambient
# → namespace/default labeled
```

### Развертывание Waypoint Proxy для L7-задач

Waypoint Proxy требуется только если в неймспейсе используются L7-ресурсы (например, `HTTPRoute`).

```bash
# Создание Waypoint прокси через Gateway API
kubectl apply -f - <<EOF
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: waypoint
  namespace: default
spec:
  gatewayClassName: istio-waypoint
EOF
# → gateway.gateway.networking.k8s.io/waypoint created
```

### L4-политика безопасности: ограничение доступа

Пример политики, разрешающей доступ к сервису `productpage` только для конкретного `ServiceAccount`. В режиме Ambient эта политика будет исполняться компонентом **ztunnel**.

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-catalog-access
  namespace: default
spec:
  selector:
    matchLabels:
      app: productpage
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/default/sa/catalog-sa"]
```

## Дополнительная информация

### Отказоустойчивость: является ли Ztunnel точкой отказа?

Ztunnel разворачивается как **DaemonSet**, что минимизирует риски:

- При падении Ztunnel на одной ноде, трафик прерывается только для Pod на этой конкретной ноде.
- Kubernetes автоматически перезапускает упавший Pod Ztunnel.
- **Control Plane (`istiod`)** не участвует в передаче трафика; его временная недоступность не разрывает существующие соединения.

### Лучшие практики

1. **Ресурсы**: устанавливайте `Resource Quotas` для неймспейсов, использующих Waypoint Proxy, так как они создают дополнительные Deployment.
2. **Переход на Ambient**: начинайте с L4-функций (mTLS, политики доступа) и добавляйте Waypoint Proxy только при необходимости в L7-маршрутизации.
3. **Обновление**: используйте `Canary` метод обновления `istiod` для безопасного перехода на новые версии Service Mesh.
