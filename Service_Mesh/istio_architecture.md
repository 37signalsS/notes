# Istio: компоненты и архитектура

## Определения

**Istio** — открытая и наиболее функционально богатая реализация [Service Mesh](./service_mesh_concepts.md). Платформа предоставляет унифицированные механизмы для безопасного соединения, управления и наблюдения за микросервисами в облачных средах, таких как Kubernetes.

Архитектура Istio разделена на **плоскость данных (Data Plane)** и **плоскость управления (Control Plane)**.

---

## Основные концепции

### Плоскость управления (Control Plane)

Плоскость управления в современных версиях Istio реализована в виде единого монолитного компонента **istiod**. Он является «мозгом» всей сетки и выполняет следующие функции независимо от архитектурной модели Data Plane:

- **Конфигурация и распространение**: преобразует высокоуровневые правила из CRD Istio в конфигурацию для прокси-серверов (Envoy) и распространяет её по протоколу xDS.
- **Сервис-дискавери**: отслеживает эндпоинты сервисов в кластере.
- **Центр сертификации (CA)**: выпускает и ротирует сертификаты для обеспечения mTLS между компонентами. Идентификация рабочей нагрузки (workload identity) основана на **ServiceAccount** Kubernetes. `istiod` выпускает сертификат для каждого ServiceAccount, который используется для установления `principal` (идентификатора) в mTLS-соединениях.

### Архитектурные модели: Sidecar vs. Ambient

Istio предлагает две взаимоисключающие модели развертывания плоскости данных, каждая со своими компромиссами.

#### 1. Классическая модель (Sidecar)

Традиционный подход: [прокси-серверы Envoy](./proxy_sidecar.md) развёртываются в виде sidecar-контейнеров в каждом поде рядом с каждым сервисом. Эти прокси перехватывают весь сетевой трафик пода и применяют правила, полученные от `istiod`. Дополнительно используются шлюзы для управления трафиком на границе кластера:

- **Ingress Gateway**: контролирует входящий трафик.
- **Egress Gateway**: контролирует исходящий трафик.

**Преимущества:**

- **Изоляция и безопасность**: каждый под имеет собственный прокси, что обеспечивает строгую изоляцию ресурсов и безопасности.
- **Максимальная функциональность**: все L4–L7 возможности Istio доступны для каждого пода.

**Недостатки:**

- **Высокое потребление ресурсов**: запуск sidecar в каждом поде значительно увеличивает потребление CPU и памяти в кластере.
- **Сложность эксплуатации**: требует модификации подов (инъекция sidecar), что усложняет обновления и может приводить к проблемам с жизненным циклом контейнеров.

#### 2. Модель Ambient (без Sidecar-контейнеров)

**Ambient-режим** — новый, более легковесный подход к построению Data Plane, представленный как альтернатива sidecar-модели. Цель — снизить накладные расходы и упростить эксплуатацию.

**Разделённая плоскость данных:** вместо одного прокси на под, Ambient-модель использует два слоя прокси на уровне ноды и неймспейса:

1. **Безопасный оверлей (L4)**: на каждой ноде разворачивается компонент **Ztunnel** (DaemonSet). Он отвечает за базовые L4-функции: mTLS, L4-авторизацию, логирование и телеметрию. Весь трафик подов прозрачно перенаправляется через локальный Ztunnel с помощью CNI-плагина Istio. Ztunnel использует протокол **HBONE** (HTTP-Based Overlay Network Environment) для туннелирования трафика между нодами.
2. **Прокси L7 (Waypoint Proxy)**: для сервисов, которым требуются расширенные L7-функции (как `VirtualService`, `RequestAuthentication` и т. д.), в их неймспейсе разворачивается один или несколько прокси-серверов **Envoy**, называемых **Waypoint Proxy**. Трафик к этим сервисам направляется через Ztunnel на Waypoint Proxy для L7-обработки.

**Компоненты Ambient-режима:**

- **`istio-cni-node`**: DaemonSet, настраивающий сетевое окружение на каждой ноде для прозрачного перехвата трафика и направления его в Ztunnel.
- **`ztunnel`**: DaemonSet, легковесный прокси на Rust, обеспечивающий L4-функциональность (mTLS, L4-политики).
- **`waypoint-proxy`**: Deployment на базе Envoy, разворачиваемый по необходимости в каждом неймспейсе для предоставления L7-политик сервисам. Активация через ресурс `Gateway` с `gatewayClassName: istio-waypoint`.

**Преимущества Ambient:**

- **Эффективность ресурсов**: значительно снижает потребление CPU и памяти, так как прокси разделяются между множеством подов.
- **Простота эксплуатации**: не требует инъекции sidecar-контейнеров; приложения можно вводить в mesh и выводить из него без перезапуска.

**Недостатки Ambient:**

- **Меньшая изоляция L7-политик**: Waypoint Proxy является общим для неймспейса, уровень изоляции ниже, чем в sidecar-модели.
- **Ограниченная поддержка мультикластера**: мультикластерный Ambient в beta (не для production до Istio 1.30+).

### Модель конфигурации (CRD)

Istio расширяет Kubernetes через набор Custom Resource Definitions (CRD) для декларативного управления сетевым поведением.

**Важное замечание о конфигурационных API:** Istio исторически использовал собственный набор CRD (`VirtualService`, `DestinationRule`). С развитием Kubernetes **Gateway API** Istio интегрировал его как основной, предпочтительный способ конфигурации. Существуют два способа настройки:

1. **Kubernetes Gateway API (предпочтительный, GA с 2024)**: использует ресурсы `Gateway` и `HTTPRoute`. Современный, стандартный для Kubernetes подход.
2. **Istio API (legacy)**: использует `VirtualService` и `DestinationRule`. Остаётся для обратной совместимости.

Ключевые ресурсы:

- **`Gateway` и `HTTPRoute`**: стандартные ресурсы Gateway API для управления входящим и внутренним трафиком. `HTTPRoute` может ссылаться как на `Gateway` (north-south трафик), так и на `Service` (east-west трафик, требует Waypoint Proxy).
- **`AuthorizationPolicy`**: определяет политики доступа на основе `principal` (ServiceAccount) и других атрибутов. L4-политики применяются **Ztunnel**, L7-политики (например, на основе JWT) — **Waypoint Proxy** (в Ambient) или Envoy sidecar.
- **`ServiceEntry`**: позволяет добавить в сетку внешние сервисы.
- **`PeerAuthentication`**: глобальная или поуровневая конфигурация mTLS (режимы: `PERMISSIVE`, `STRICT`, `DISABLE`).
- **`RequestAuthentication`**: политики аутентификации на основе JWT.
- **`Telemetry`**: управление сбором и экспортом телеметрии (access logs, metrics, traces).
- **`WasmPlugin`**: расширение функциональности прокси через WebAssembly-модули.
- **`VirtualService` / `DestinationRule` (legacy)**: альтернативный способ определения правил маршрутизации и политик для сервисов. Подробное описание — в [Управлении трафиком](./traffic_management.md).

### Сравнение моделей

| Критерий | Sidecar | Ambient |
| :--- | :--- | :--- |
| **Изоляция** | Максимальная (на под) | Неймспейс (L7), нода (L4) |
| **Ресурсы** | 100–300 МБ RAM, 50–500 mCPU на под | ~30–50 % от sidecar (разделение) |
| **L7-политики** | Все доступны | Только через Waypoint Proxy |
| **Миграция** | Требует перезапуска подов | Без перезапуска (on/off mesh) |
| **Мультикластер** | Production-ready | Beta (не для production) |
| **Рекомендация** | Сложные L7-сценарии, изоляция | Простота, эффективность, массовые развёртывания |

## Практические сценарии

### L4-Авторизация: ограничение доступа по ServiceAccount

`AuthorizationPolicy` позволяет создавать мощные правила доступа. В этом примере разрешаем доступ к сервису `productpage` только от двух источников (principals): `bookinfo-gateway` и `curl-sa`. Любые другие вызовы будут заблокированы на уровне L4 компонентом **Ztunnel** (в Ambient) или Envoy sidecar.

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: productpage-access-policy
  namespace: default
spec:
  selector:
    matchLabels:
      app: productpage
  action: ALLOW
  rules:
  - from:
    - source:
        principals:
        - "cluster.local/ns/default/sa/bookinfo-gateway"
        - "cluster.local/ns/default/sa/curl-sa"
```

### L7-Маршрутизация внутреннего трафика (Ambient Mode)

Стандартные Ingress-ресурсы (включая Gateway API) предназначены для внешнего трафика и не могут управлять потоками *между* сервисами внутри кластера (east-west traffic). Например, они не могут определить, какую версию сервиса `reviews` должен вызывать сервис `productpage`.

Для этого в Ambient-режиме используется связка **Waypoint Proxy** и `HTTPRoute`, ссылающегося на сервис:

1. Создаётся **Waypoint Proxy** для неймспейса через ресурс `Gateway`.
2. Создаётся `HTTPRoute`, в `parentRefs` указывающий на `Service` (не на `Gateway`). Это перехватывает трафик, адресованный сервису `reviews`, и применяет правила маршрутизации.

В примере 80 % запросов к `reviews` направляются на `reviews-v1`, 20 % — на `reviews-v2`. Подробные примеры маршрутизации — в [Управлении трафиком](./traffic_management.md).

### Включение Ambient Mesh для неймспейса

```bash
# 1. Установка istio-cni и ztunnel (требуется до установки приложений)
istioctl install --set profile=ambient -y

# 2. Включение Ambient для неймспейса (вместо sidecar-инъекции)
kubectl label namespace default istio.io/dataplane-mode=ambient

# 3. Создание Waypoint Proxy для L7-политик
kubectl apply -f - <<EOF
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: waypoint
  namespace: default
spec:
  gatewayClassName: istio-waypoint
EOF
```

### Отказоустойчивость: является ли Ztunnel единой точкой отказа (SPOF)?

**Нет, ztunnel не является SPOF.** Архитектура Ambient Mesh спроектирована с учётом отказа отдельных нод — это штатное поведение для распределённых систем.

**Масштаб отказа:**

| Компонент | Развёртывание | При падении |
| :--- | :--- | :--- |
| **ztunnel** | DaemonSet (один pod на ноду) | Трафик затронут только на конкретной ноде |
| **waypoint-proxy** | Deployment (на неймспейс) | Перезапускается Kubernetes, трафик перераспределяется |
| **istiod** | Deployment (Control Plane) | Не влияет на существующие соединения, только на конфигурацию |

**Механизмы восстановления:**

1. **Автоматический перезапуск**: ztunnel развёрнут как DaemonSet — Kubernetes автоматически перезапустит pod при падении.
2. **Изоляция отказа**: при падении ztunnel на ноде pod'ы на этой ноде теряют связь через mesh; pod'ы на других нодах работают нормально через свои локальные ztunnel.
3. **Восстановление трафика**: после перезапуска CNI-плагин автоматически перенаправляет трафик в восстановленный ztunnel, mTLS-соединения восстанавливаются.

**Рекомендации для production:**

- **Pod Disruption Budget (PDB)** для ztunnel: `minAvailable: 1` гарантирует, что хотя бы один экземпляр останется доступен при плановых работах.
- **Мониторинг ztunnel**: алерты на статус pod'ов (`kubectl get daemonset ztunnel -n istio-system`), метрики mTLS-соединений, задержку восстановления после падения ноды.
