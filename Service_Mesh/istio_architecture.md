# Istio: компоненты и архитектура

## Определения

**Istio** — это открытая и наиболее функционально богатая реализация [Service Mesh](./service_mesh_concepts.md). Платформа предоставляет унифицированные механизмы для безопасного соединения, управления и наблюдения за микросервисами в облачных средах, таких как Kubernetes.

Архитектура Istio разделена на **плоскость данных (Data Plane)** и **плоскость управления (Control Plane)**.

## Основные концепции

### Плоскость управления (Control Plane)

Плоскость управления в современных версиях Istio реализована в виде единого монолитного компонента **istiod**. Он является "мозгом" всей сетки и выполняет следующие функции независимо от архитектурной модели Data Plane:

- **Конфигурация и распространение**: Преобразует высокоуровневые правила из CRD Istio в конфигурацию для прокси-серверов (Envoy) и распространяет ее по протоколу xDS.
- **Сервис-дискавери**: Отслеживает эндпоинты сервисов в кластере.
- **Центр сертификации (CA)**: Выпускает и ротирует сертификаты для обеспечения mTLS между компонентами.

## Архитектурные модели: Sidecar vs. Ambient

Istio предлагает две взаимоисключающие модели развертывания плоскости данных, каждая со своими компромиссами.

### 1. Классическая модель (Sidecar)

Это традиционный и наиболее распространенный подход.

#### Плоскость данных (Data Plane)

Состоит из **прокси-серверов Envoy**, развернутых в виде [sidecar-контейнеров](./proxy_sidecar.md) в каждом поде рядом с каждым сервисом. Эти прокси перехватывают весь сетевой трафик пода и применяют к нему правила, полученные от `istiod`. Дополнительно используются шлюзы для управления трафиком на границе кластера:

- **Ingress Gateway**: Контролирует входящий трафик.
- **Egress Gateway**: Контролирует исходящий трафик.

**Преимущества:**
- **Изоляция и безопасность**: Каждый под имеет собственный прокси, что обеспечивает строгую изоляцию ресурсов и безопасности.
- **Максимальная функциональность**: Все L4-L7 возможности Istio доступны для каждого пода.

**Недостатки:**
- **Высокое потребление ресурсов**: Запуск sidecar в каждом поде значительно увеличивает потребление CPU и памяти в кластере.
- **Сложность эксплуатации**: Требует модификации подов (инъекция sidecar), что усложняет обновления и может приводить к проблемам с жизненным циклом контейнеров.

### 2. Модель Ambient (без Sidecar-контейнеров)

**Ambient-режим** — это новый, более легковесный подход к построению Data Plane, представленный как альтернатива sidecar-модели. Его цель — снизить накладные расходы и упростить эксплуатацию.

#### Разделенная плоскость данных

Вместо одного прокси на под, Ambient-модель использует два раздельных слоя прокси на уровне ноды и неймспейса:

1.  **Безопасный оверлей (L4)**: На каждой ноде разворачивается компонент **Ztunnel**. Он отвечает за базовые L4-функции: mTLS, L4-авторизацию, логирование и телеметрию. Весь трафик подов прозрачно перенаправляется через локальный Ztunnel с помощью CNI-плагина Istio.
2.  **Прокси L7 (Waypoint Proxy)**: Для сервисов, которым требуются расширенные L7-функции (как `VirtualService`, `RequestAuthentication` и т.д.), в их неймспейсе разворачивается один или несколько прокси-серверов **Envoy**, называемых **Waypoint Proxy**. Трафик к этим сервисам направляется через Ztunnel на Waypoint Proxy для L7-обработки.

#### Компоненты Ambient-режима
- **`istio-cni-node`**: DaemonSet, который настраивает сетевое окружение на каждой ноде для прозрачного перехвата трафика и его направления в Ztunnel.
- **`ztunnel`**: DaemonSet, легковесный прокси на Rust, обеспечивающий L4-функциональность (mTLS, L4-политики). Использует протокол **HBONE** (HTTP-Based Overlay Network Environment) для туннелирования трафика между нодами.
- **`waypoint-proxy`**: Deployment на базе Envoy, разворачиваемый по необходимости в каждом неймспейсе для предоставления L7-политик сервисам.

**Преимущества:**
- **Эффективность ресурсов**: Значительно снижает потребление CPU и памяти, так как прокси разделяются между множеством подов.
- **Простота эксплуатации**: Не требует инъекции sidecar-контейнеров, что упрощает управление приложениями. Приложения можно вводить в mesh и выводить из него без их перезапуска.

**Недостатки:**
- **Меньшая изоляция L7-политик**: Так как Waypoint Proxy является общим для неймспейса, уровень изоляции ниже, чем в sidecar-модели.

## Модель конфигурации (CRD)

Istio расширяет Kubernetes через набор Custom Resource Definitions (CRD) для декларативного управления сетевым поведением. Ключевые ресурсы используются в обеих моделях, но применяются на разных уровнях:

- `VirtualService`: Определяет правила маршрутизации трафика (требует **Waypoint Proxy** в Ambient-режиме).
- `DestinationRule`: Задает политики для целевых сервисов (балансировка, подмножества версий).
- `Gateway`: Конфигурирует Ingress/Egress шлюзы, часто используется в связке с Kubernetes Gateway API.
- `ServiceEntry`: Позволяет добавить в сетку внешние сервисы.
- `AuthorizationPolicy`: Определяет политики доступа (L4-политики применяются **Ztunnel**, L7 — **Waypoint Proxy**).

## Практические сценарии

### Маршрутизация на основе заголовка

В этом примере трафик для пользователей с заголовком `x-user: canary` направляется на версию `v2` сервиса `reviews`. Весь остальной трафик — на `v1`.
- В **Sidecar-модели** это правило будет применено Envoy-прокси каждого пода `reviews`.
- В **Ambient-модели** это правило потребует развертывания **Waypoint Proxy** для сервиса `reviews` и будет применено на нем.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts: [ "reviews.default.svc.cluster.local" ]
  http:
  - match:
    - headers:
        x-user:
          exact: canary
    route:
    - destination: { host: reviews, subset: v2 }
  - route:
    - destination: { host: reviews, subset: v1 }
---
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews.default.svc.cluster.local
  subsets:
  - name: v1
    labels: { version: v1 }
  - name: v2
    labels: { version: v2 }
```
