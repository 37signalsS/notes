# Istio: компоненты и архитектура

## Определения

**Istio** — открытая и наиболее функционально богатая реализация [Service Mesh](./service_mesh_concepts.md). Платформа предоставляет унифицированные механизмы для безопасного соединения, управления и наблюдения за микросервисами в облачных средах, таких как Kubernetes.

Архитектура Istio разделена на **плоскость данных (Data Plane)** и **плоскость управления (Control Plane)**.

---

## Основные концепции

### Плоскость управления (Control Plane)

Плоскость управления в современных версиях Istio реализована в виде единого монолитного компонента **istiod**. Он является "мозгом" всей сетки и выполняет следующие функции независимо от архитектурной модели Data Plane:

- **Конфигурация и распространение**: Преобразует высокоуровневые правила из CRD Istio в конфигурацию для прокси-серверов (Envoy) и распространяет ее по протоколу xDS.
- **Сервис-дискавери**: Отслеживает эндпоинты сервисов в кластере.
- **Центр сертификации (CA)**: Выпускает и ротирует сертификаты для обеспечения mTLS между компонентами. Идентификация рабочей нагрузки (workload identity) основана на **ServiceAccount** Kubernetes. `istiod` выпускает сертификат для каждого ServiceAccount, который используется для установления `principal` (идентификатора) в mTLS-соединениях.

---

## Архитектурные модели: Sidecar vs. Ambient

Istio предлагает две взаимоисключающие модели развертывания плоскости данных, каждая со своими компромиссами.

### 1. Классическая модель (Sidecar)

Это традиционный и наиболее распространенный подход.

#### Плоскость данных (Data Plane)

Состоит из **прокси-серверов Envoy**, развернутых в виде [sidecar-контейнеров](./proxy_sidecar.md) в каждом поде рядом с каждым сервисом. Эти прокси перехватывают весь сетевой трафик пода и применяют к нему правила, полученные от `istiod`. Дополнительно используются шлюзы для управления трафиком на границе кластера:

- **Ingress Gateway**: Контролирует входящий трафик.
- **Egress Gateway**: Контролирует исходящий трафик.

**Преимущества:**

- **Изоляция и безопасность**: Каждый под имеет собственный прокси, что обеспечивает строгую изоляцию ресурсов и безопасности.
- **Максимальная функциональность**: Все L4-L7 возможности Istio доступны для каждого пода.

**Недостатки:**

- **Высокое потребление ресурсов**: Запуск sidecar в каждом поде значительно увеличивает потребление CPU и памяти в кластере.
- **Сложность эксплуатации**: Требует модификации подов (инъекция sidecar), что усложняет обновления и может приводить к проблемам с жизненным циклом контейнеров.

### 2. Модель Ambient (без Sidecar-контейнеров)

**Ambient-режим** — это новый, более легковесный подход к построению Data Plane, представленный как альтернатива sidecar-модели. Его цель — снизить накладные расходы и упростить эксплуатацию.

#### Разделенная плоскость данных

Вместо одного прокси на под, Ambient-модель использует два раздельных слоя прокси на уровне ноды и неймспейса:

1. **Безопасный оверлей (L4)**: На каждой ноде разворачивается компонент **Ztunnel**. Он отвечает за базовые L4-функции: mTLS, L4-авторизацию, логирование и телеметрию. Весь трафик подов прозрачно перенаправляется через локальный Ztunnel с помощью CNI-плагина Istio.
2. **Прокси L7 (Waypoint Proxy)**: Для сервисов, которым требуются расширенные L7-функции (как `VirtualService`, `RequestAuthentication` и т.д.), в их неймспейсе разворачивается один или несколько прокси-серверов **Envoy**, называемых **Waypoint Proxy**. Трафик к этим сервисам направляется через Ztunnel на Waypoint Proxy для L7-обработки.

#### Компоненты Ambient-режима

- **`istio-cni-node`**: DaemonSet, который настраивает сетевое окружение на каждой ноде для прозрачного перехвата трафика и его направления в Ztunnel.
- **`ztunnel`**: DaemonSet, легковесный прокси на Rust, обеспечивающий L4-функциональность (mTLS, L4-политики). Использует протокол **HBONE** (HTTP-Based Overlay Network Environment) для туннелирования трафика между нодами.
- **`waypoint-proxy`**: Deployment на базе Envoy, разворачиваемый по необходимости в каждом неймспейсе для предоставления L7-политик сервисам. Чтобы активировать Waypoint для сервисов в неймспейсе, создается ресурс `Gateway` с `gatewayClassName: istio-waypoint`.

**Преимущества:**

- **Эффективность ресурсов**: Значительно снижает потребление CPU и памяти, так как прокси разделяются между множеством подов.
- **Простота эксплуатации**: Не требует инъекции sidecar-контейнеров, что упрощает управление приложениями. Приложения можно вводить в mesh и выводить из него без их перезапуска.

**Недостатки:**

- **Меньшая изоляция L7-политик**: Так как Waypoint Proxy является общим для неймспейса, уровень изоляции ниже, чем в sidecar-модели.
- **Ограниченная поддержка мультикластера**: Мультикластерный Ambient в beta (не для production до Istio 1.30+).

## Модель конфигурации (CRD)

Istio расширяет Kubernetes через набор Custom Resource Definitions (CRD) для декларативного управления сетевым поведением.

**Важное замечание о конфигурационных API:**
Istio исторически использовал собственный набор CRD для управления трафиком (`VirtualService`, `DestinationRule`). С развитием Kubernetes **Gateway API**, Istio интегрировал его как основной, предпочтительный способ конфигурации. Таким образом, существует два способа настройки:

1. **Kubernetes Gateway API (предпочтительный, GA с 2024)**: Использует ресурсы `Gateway` и `HTTPRoute`. Это современный, стандартный для Kubernetes подход.
2. **Istio API (legacy)**: Использует `VirtualService` и `DestinationRule`. Этот способ остается для обратной совместимости.

Ключевые ресурсы:

- **`Gateway` и `HTTPRoute`**: Стандартные ресурсы Gateway API для управления входящим и внутренним трафиком. `HTTPRoute` может ссылаться как на `Gateway` (для north-south трафика), так и на `Service` (для east-west трафика, требует Waypoint Proxy).
- **`AuthorizationPolicy`**: Определяет политики доступа на основе `principal` (ServiceAccount) и других атрибутов. L4-политики применяются **Ztunnel**, а L7-политики (например, на основе JWT) — **Waypoint Proxy** (в Ambient) или Envoy sidecar.
- **`ServiceEntry`**: Позволяет добавить в сетку внешние сервисы.
- **`VirtualService` / `DestinationRule` (Legacy)**: Альтернативный способ определения правил маршрутизации и политик для сервисов.
- **`PeerAuthentication`**: Глобальная или поуровневая конфигурация mTLS (режимы: `PERMISSIVE`, `STRICT`, `DISABLE`).
- **`RequestAuthentication`**: Политики аутентификации на основе JWT.
- **`Telemetry`**: Управление сбором и экспортом телеметрии (access logs, metrics, traces).
- **`WasmPlugin`**: Расширение функциональности прокси через WebAssembly-модули.

## Практические сценарии

### L4-Авторизация: Ограничение доступа по ServiceAccount

`AuthorizationPolicy` позволяет создавать мощные правила доступа. В этом примере мы разрешаем доступ к сервису `productpage` только от двух конкретных источников (principals): `bookinfo-gateway` и `curl-sa`. Любые другие вызовы будут заблокированы на уровне L4 компонентом **Ztunnel** (в Ambient) или Envoy sidecar.

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: productpage-access-policy
  namespace: default
spec:
  selector:
    matchLabels:
      app: productpage
  action: ALLOW
  rules:
  - from:
    - source:
        principals:
        - "cluster.local/ns/default/sa/bookinfo-gateway"
        - "cluster.local/ns/default/sa/curl-sa"
```

### L7-Маршрутизация внутреннего трафика (Ambient Mode)

Стандартные Ingress-ресурсы (включая Gateway API), предназначенные для внешнего трафика, не могут управлять потоками данных *между* сервисами внутри кластера (east-west traffic). Например, они не могут определить, какую версию сервиса `reviews` должен вызывать сервис `productpage`.

Для этого в Ambient-режиме используется связка **Waypoint Proxy** и `HTTPRoute`, ссылающегося на сервис.

1. **Создается Waypoint Proxy** для неймспейса с помощью ресурса `Gateway`.
2. **Создается `HTTPRoute`**, который в `parentRefs` указывает не на `Gateway`, а на `Service`. Это перехватывает трафик, адресованный сервису `reviews`, и применяет к нему правила маршрутизации.

В данном примере 80% запросов к сервису `reviews` направляются на `reviews-v1`, а 20% — на `reviews-v2`.

## Отказоустойчивость и SPOF в Ambient Mesh

### Является ли ztunnel единой точкой отказа (SPOF)?

**Нет, ztunnel не является SPOF.** Архитектура Ambient Mesh изначально спроектирована с учётом отказа отдельных нод — это нормальное поведение для распределённых систем.

#### Масштаб отказа

| Компонент | Развертывание | При падении |
| :--- | :--- | :--- |
| **ztunnel** | DaemonSet (один pod на ноду) | Трафик затронут только на конкретной ноде |
| **waypoint-proxy** | Deployment (на неймспейс) | Перезапускается Kubernetes, трафик перераспределяется |
| **istiod** | Deployment (Control Plane) | Не влияет на существующие соединения, только на конфигурацию |

#### Механизмы восстановления

1. **Автоматический перезапуск**: Поскольку ztunnel развернут как **DaemonSet**, Kubernetes автоматически перезапустит pod при падении — так же, как любой другой daemonset.

2. **Изоляция отказа**: При падении ztunnel на ноде:
   - **Затронуты**: pod'ы на этой конкретной ноде теряют возможность отправлять/получать трафик через mesh
   - **Не затронуты**: pod'ы на других нодах продолжают работать нормально через свои локальные экземпляры ztunnel

3. **Восстановление трафика**: После перезапуска ztunnel:
   - CNI-плагин автоматически перенаправляет трафик в восстановленный ztunnel
   - mTLS-соединения восстанавливаются через новый экземпляр
   - Политики безопасности применяются без вмешательства оператора

#### Архитектурные гарантии

- **Нода — единица отказа**: Распределенные системы предполагают, что ноды могут падать. Это штатная ситуация, а не аварийная.
- **Разделение плоскостей**: L4-функциональность (ztunnel) отделена от L7-функциональности (waypoint-proxy) — отказ одного компонента не влияет на другой.
- **Автоматическое восстановление**: Kubernetes обрабатывает перезапуск без участия оператора.

#### Рекомендации для production

1. **Pod Disruption Budget (PDB)** для ztunnel:
   ```yaml
   apiVersion: policy/v1
   kind: PodDisruptionBudget
   metadata:
     name: ztunnel-pdb
     namespace: istio-system
   spec:
     minAvailable: 1
     selector:
       labels:
         app: ztunnel
   ```

2. **Распределение подов**: Используйте `podAntiAffinity` для критичных приложений, чтобы избежать размещения всех реплик на одной ноде с ztunnel.

3. **Мониторинг ztunnel**: Настройте алерты на:
   - Статус pod'ов ztunnel (`kubectl get daemonset ztunnel -n istio-system`)
   - Метрики mTLS-соединений
   - Задержку восстановления после падения ноды

**Вывод**: Понимание архитектурных паттернов Ambient Mesh помогает проектировать надёжные системы и корректно оценивать риски отказоустойчивости при внедрении Service Mesh.

## Включение Ambient Mesh для неймспейса

```bash
# 1. Установить istio-cni и ztunnel (требуется до установки приложений)
istioctl install --set profile=ambient -y

# 2. Включить Ambient для неймспейса (вместо sidecar-инъекции)
kubectl label namespace default istio.io/dataplane-mode=ambient

# 3. Создать Waypoint Proxy для L7-политик
kubectl apply -f - <<EOF
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: waypoint
  namespace: default
spec:
  gatewayClassName: istio-waypoint
EOF
```

## Дополнительная информация

### Сравнение моделей

| Критерий | Sidecar | Ambient |
| :--- | :--- | :--- |
| **Изоляция** | Максимальная (на под) | Неймспейс (L7), нода (L4) |
| **Ресурсы** | 100–300 МБ RAM, 50–500 mCPU на под | ~30–50% от sidecar (разделение) |
| **L7-политики** | Все доступны | Только через Waypoint Proxy |
| **Миграция** | Требует перезапуска подов | Без перезапуска (on/off mesh) |
| **Мультикластер** | Production-ready | Beta (не для production) |
| **Рекомендация** | Сложные L7-сценарии, изоляция | Простота, эффективность, массовые развертывания |
