# Service Mesh: Основные концепции

## Определения

**Service Mesh (Сетка сервисов)** — это выделенный инфраструктурный слой для управления сетевыми взаимодействиями между микросервисами. Его основная задача — вынести логику сети (маршрутизацию, безопасность, наблюдаемость) из кода приложения в платформу.

В контейнерных средах, таких как Kubernetes, это обычно реализуется с помощью **sidecar-прокси**: легковесного сетевого прокси, который запускается рядом с каждым экземпляром сервиса и перехватывает весь его входящий и исходящий трафик.

## Основные концепции

### Архитектура
Service Mesh состоит из двух ключевых компонентов:
*   **Data Plane (Плоскость данных):** Состоит из множества sidecar-прокси (например, Envoy, linkerd-proxy), развернутых рядом с каждым сервисом. Именно они обрабатывают трафик, применяют политики, собирают телеметрию.
*   **Control Plane (Плоскость управления):** Центральный компонент, который управляет всеми прокси в Data Plane. Он предоставляет API для конфигурации, распространяет политики и сертификаты. Примеры: Istiod (в Istio), Linkerd control plane.

### Ключевые возможности
*   **Управление трафиком:**
    *   Динамическая маршрутизация (по версиям, заголовкам, весу).
    *   Канареечные развертывания (Canary releases) и A/B-тестирование.
    *   Таймауты, повторные попытки (retries) и размыкатели цепи (circuit breakers).
*   **Безопасность:**
    *   **mTLS (Mutual TLS):** Автоматическое шифрование всего трафика между сервисами.
    *   **Управление идентичностью:** Каждому сервису предоставляется криптографически подтвержденная идентичность (например, через SPIFFE/SPIRE).
    *   **Политики доступа:** Декларативные правила, определяющие, какие сервисы могут взаимодействовать друг с другом.
*   **Наблюдаемость (Observability):**
    *   **Метрики:** Автоматический сбор "золотых сигналов" (задержка, трафик, ошибки, насыщенность) для всего трафика.
    *   **Трассировка (Tracing):** Генерация и распространение заголовков для распределенной трассировки.
    *   **Топология:** Визуализация карты зависимостей между сервисами.

## Практические сценарии

### Сценарий 1: Канареечное развертывание в Istio
В этом примере 10% трафика направляется на новую версию `v2` сервиса `payments`, а 90% — на стабильную `v1`.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: payments
spec:
  hosts:
    - payments # Имя Kubernetes Service
  http:
  - route:
    - destination:
        host: payments
        subset: v1
      weight: 90
    - destination:
        host: payments
        subset: v2
      weight: 10
---
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: payments
spec:
  host: payments
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2
```

### Сценарий 2: Выбор между Istio и Linkerd

| Аспект | Istio | Linkerd |
| :--- | :--- | :--- |
| **Философия** | Максимальная функциональность и гибкость | Простота, производительность и низкий порог входа |
| **Прокси** | **Envoy** (C++) — очень мощный, но сложный | **linkerd2-proxy** (Rust) — легковесный и быстрый |
| **Сложность** | Высокая. Много CRD и настроек. | Низкая. Установка и настройка "в одну команду". |
| **Накладные расходы**| Выше (CPU/RAM) | Значительно ниже |
| **Основной фокус**| Платформа для построения любых сетевых сценариев | Безопасность и наблюдаемость "из коробки" |

## Дополнительная информация

### Ограничения и операционные аспекты
*   **Дополнительная задержка:** Каждый вызов проходит через два прокси (на стороне клиента и на стороне сервера), что добавляет несколько миллисекунд задержки.
*   **Потребление ресурсов:** Каждый sidecar-прокси потребляет CPU и память, что необходимо учитывать при планировании ресурсов кластера.
*   **Сложность эксплуатации:** Service Mesh — это сложная распределенная система, которая требует экспертизы для правильного развертывания, обновления и отладки.
*   **Совместимость:** Может требовать адаптации для работы с некоторыми протоколами (кроме HTTP/gRPC) или с legacy-системами.
