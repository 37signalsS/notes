# Service Mesh: основные концепции

## Определения

**Service Mesh (Сетка сервисов)** — выделенный инфраструктурный слой для управления сетевыми взаимодействиями между микросервисами на уровнях L4–L7. Основная задача — вынести логику сети (маршрутизацию, безопасность, наблюдаемость) из кода приложения в платформу.

**Ключевые характеристики:**

- **Прозрачность:** приложение не требует изменений кода для интеграции.
- **Децентрализация:** управление трафиком распределено между прокси-серверами.
- **Идентичность:** каждый сервис имеет криптографическую идентичность на основе SPIFFE (Secure Production Identity Framework for Everyone) и SVID (SPIFFE Verifiable Identity Document) или ServiceAccount Kubernetes.

**Паттерн Sidecar:** ключевой элемент архитектуры — **прокси-сайдкар**, легковесный сетевой прокси, который запускается в одном поде рядом с каждым экземпляром сервиса и перехватывает весь входящий и исходящий трафик. Детальное описание паттерна и реализаций представлено в [Proxy Sidecar](./proxy_sidecar.md).

**Альтернатива Ambient:** начиная с Istio 1.29, доступна **Ambient Mesh** — архитектура без sidecar, где прокси разделяются на уровне ноды (Ztunnel) и неймспейса (Waypoint Proxy). Ztunnel не является SPOF (Single Point of Failure) благодаря развертыванию через DaemonSet и автоматическому восстановлению Kubernetes. Подробнее в [Архитектуре Istio](./istio_architecture.md).

## Основные концепции

### CNI и Service Mesh: разделение ответственности

Service Mesh — это слой, работающий **поверх** CNI (Container Network Interface), а не его замена.

- **CNI (Connectivity):** решает базовую задачу — связывает поды, чтобы пакет от пода А дошел до пода Б.
- **Service Mesh (Control и Visibility):** добавляет интеллектуальное управление этим трафиком (шифрование, повторы, метрики).

**Пример (сценарий с сервисом оплаты):**

1. **Без Service Mesh:** сервис заказов отправляет запрос в сервис оплаты. Оплата в этот момент перезапускается. Запрос завершается ошибкой, пользователь видит сбой.
2. **С Service Mesh:** запрос перехватывается прокси-сайдкаром. Прокси обнаруживает, что сервис оплаты не ответил, ждет 100 мс и автоматически повторяет запрос на другой под оплаты. Пользователь не замечает сбоя. Повторная попытка (retry) происходит на уровне платформы.

### Архитектура

Service Mesh состоит из двух независимых плоскостей:

| Компонент | Назначение | Примеры |
| :--- | :--- | :--- |
| **Data Plane (Плоскость данных)** | Прокси-серверы (Envoy, linkerd-proxy, Ztunnel), обрабатывающие трафик и собирающие телеметрию. | Envoy, linkerd2-proxy, Ztunnel |
| **Control Plane (Плоскость управления)** | Централизованное управление: конфигурация xDS, сервис-дискавери, управление сертификатами (CA). | Istiod (Istio), Linkerd control plane |

### Ключевые возможности

#### 1. Управление трафиком

Динамическая маршрутизация на основе L7-атрибутов (хост, путь, заголовки):

- **Маршрутизация:** Canary, Blue-Green, A/B-тестирование.
- **Отказоустойчивость:** таймауты, ретраи, разрыв цепи (Circuit Breaking), Outlier Detection.
- **Зеркалирование:** дублирование трафика для тестирования без влияния на пользователей.

Подробное описание примитивов и примеров — в [Управлении трафиком](./traffic_management.md).

#### 2. Безопасность (Zero Trust)

- **mTLS (Mutual Transport Layer Security) по умолчанию:** автоматическое сквозное шифрование между сервисами.
- **Идентичность:** использование ServiceAccount Kubernetes как основы для идентификации источника (principal).
- **Политики доступа:** авторизация на уровне L7 на основе идентичности (подробнее в [Zero Trust](../Networking/Concepts/zero_trust_overview.md)).

#### 3. Наблюдаемость (Observability)

Автоматический сбор телеметрии:

- **Золотые сигналы:** задержка (latency), трафик, ошибки, насыщенность (saturation).
- **Трассировка:** распределенная трассировка запросов (Jaeger, Tempo).
- **Топология:** визуализация карты зависимостей сервисов (Kiali, Linkerd Viz).

#### 4. Сегментация сети

Микросегментация на уровне сервисов вместо макросегментации на уровне подсетей:

- **Политики:** `AuthorizationPolicy` в Istio, `ServiceProfile` в Linkerd.
- **Гранулярность:** контроль доступа по методам HTTP, путям и заголовкам.

## Практические сценарии

### Выбор реализации: Istio, Linkerd или Consul

| Критерий | Istio | Linkerd | Consul Connect |
| :--- | :--- | :--- | :--- |
| **Философия** | Максимальная функциональность | Простота и производительность | Универсальность (VM + K8s) |
| **Прокси** | Envoy, Ztunnel | linkerd2-proxy | Envoy |
| **mTLS** | Гибкие политики | Включено по умолчанию | Автоматическое |
| **Производительность** | Задержка ~5–10 мс | Задержка ~1–3 мс | Сопоставима с Istio |
| **Сложность** | Высокая (много CRD) | Низкая (быстрый старт) | Средняя |

**Рекомендации по выбору:**

- **Istio:** сложные сценарии маршрутизации, мультикластер, использование Gateway API.
- **Linkerd:** критичность производительности, минимальные накладные расходы, простота эксплуатации.
- **Consul:** гетерогенные среды, где часть сервисов работает вне Kubernetes.

Детальное сравнение представлено в [сравнении Istio и Linkerd](./istio_vs_linkerd.md).

### Интеграция с экосистемой

| Инструмент | Роль в экосистеме Service Mesh |
| :--- | :--- |
| **Prometheus** | Сбор метрик из прокси-серверов. |
| **Grafana** | Визуализация метрик и состояния сетки. |
| **Jaeger/Tempo** | Анализ распределенных трассировок. |
| **Vault** | Управление секретами и интеграция с центром сертификации. |

## Дополнительная информация

### Ограничения и операционные аспекты

- **Задержка:** добавление двух прокси на пути запроса неизбежно увеличивает latency. Режим Ambient позволяет минимизировать этот эффект.
- **Потребление ресурсов:** sidecar-модель требует выделения CPU и RAM для каждого пода. Необходимо настраивать лимиты (Resource Quotas).
- **Сложность отладки:** трафик становится прозрачным, что затрудняет классический захват пакетов (tcpdump). Требуются специализированные инструменты мониторинга.

### Актуальность

На текущий момент основным вектором развития Service Mesh является переход на **Gateway API** как стандарт управления трафиком и внедрение **Sidecar-less** архитектур (Ambient Mesh) для снижения накладных расходов.
