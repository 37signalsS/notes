# Service Mesh: основные концепции

## Определения

**Service Mesh (Сетка сервисов)** — выделенный инфраструктурный слой для управления сетевыми взаимодействиями между микросервисами на уровнях L4–L7. Основная задача — вынести сетевую логику (маршрутизацию, безопасность, наблюдаемость) из кода приложения на уровень платформы.

**Ключевые характеристики:**

- **Прозрачность:** интеграция сервисов не требует изменения кода приложений.
- **Децентрализация:** управление трафиком распределено между прокси-серверами (Data Plane).
- **Идентичность:** каждый сервис обладает криптографической идентичностью на основе стандартов **SPIFFE/Spire**, что позволяет строить политики безопасности независимо от IP-адресов.

**Модели развертывания:**
- **Sidecar Pattern:** прокси запускается в каждом Pod рядом с приложением. Это классическая модель, обеспечивающая максимальную изоляцию. Подробнее: [Proxy Sidecar](./proxy_sidecar.md).
- **Sidecar-less (Ambient Mesh):** архитектура, при которой функции прокси разделены между общим узловым компонентом (L4) и опциональным шлюзом неймспейса (L7). В 2026 году этот режим (Istio Ambient) является стабильным (GA). Подробнее: [Архитектура Istio](./istio_architecture.md).

## Основные концепции

### Взаимодействие с CNI

Service Mesh работает **поверх** CNI (Container Network Interface). В то время как CNI обеспечивает базовую связность (L3/L4), Mesh добавляет интеллектуальное управление и безопасность:

- **CNI:** «Может ли Pod A достучаться до Pod B?»
- **Service Mesh:** «Разрешено ли Pod A вызывать метод GET /auth у Pod B? Зашифрован ли этот трафик? Какова задержка (P99)?»

В современных инфраструктурах (2026) Service Mesh часто интегрируется с CNI через **eBPF**. Это позволяет использовать механизмы вроде **SOCKMAP** для ускорения передачи данных между сокетами, минуя полный стек TCP/IP ядра, что снижает накладные расходы прокси (sidecar tax) на 15–20%.

### Архитектура

Service Mesh состоит из двух плоскостей:

| Компонент | Назначение | Технологии (2026) |
| :--- | :--- | :--- |
| **Data Plane (Плоскость данных)** | Перехват, обработка и пересылка трафика. Сбор телеметрии. | Envoy, Linkerd-proxy, Ztunnel (Rust). |
| **Control Plane (Плоскость управления)** | Централизованное управление конфигурацией, выдача сертификатов, сервис-дискавери. | Istiod (Istio), Linkerd control plane. |

## Ключевые возможности

### 1. Управление трафиком (Gateway API и GAMMA)

В 2026 году основным стандартом управления трафиком стал **Kubernetes Gateway API** (спецификация **GAMMA**). Это позволяет использовать универсальные ресурсы (например, `HTTPRoute`) для настройки меша.

- **Маршрутизация:** Canary (взвешенная), Blue-Green, A/B-тестирование на основе заголовков или cookie.
- **Устойчивость (Resilience):** автоматические ретраи (retry), таймауты, разрыв цепи (**Circuit Breaking**) для предотвращения каскадных сбоев.
- **Балансировка:** интеллектуальное распределение с учетом зон доступности (**HAZL** в Linkerd или Locality Load Balancing в Istio) для минимизации задержек и облачных затрат.
- **AI Gateway:** специализированные фильтры для управления трафиком к LLM-моделям (кэширование промптов, лимиты по токенам).

### 2. Безопасность (Zero Trust)

- **mTLS по умолчанию:** автоматическое двустороннее шифрование трафика. Прокси проверяют сертификаты друг друга при каждом соединении.
- **Workload Identity:** использование SPIFFE-идентификаторов для аутентификации. Безопасность строится на «кто вызывает», а не «с какого IP».
- **Авторизация (L7):** гранулярные политики доступа, запрещающие или разрешающие конкретные методы API (например, `POST` запрещен, `GET` разрешен).

### 3. Наблюдаемость (Observability)

- **Золотые сигналы:** автоматический сбор метрик (RPS, Error Rate, Latency, Saturation) без участия разработчика.
- **Распределенная трассировка:** автоматическая передача контекста (trace context) между сервисами для визуализации пути запроса (OpenTelemetry).
- **Топология:** построение динамической карты связей между микросервисами в реальном времени.

## Практические сценарии

### Выбор реализации: Istio, Linkerd или Cilium

| Критерий | Istio (1.30+) | Linkerd (2.20+) | Cilium Service Mesh |
| :--- | :--- | :--- | :--- |
| **Архитектура** | Ambient (GA) / Sidecar | Native Sidecar / Sidecar | Sidecar-less (eBPF) |
| **Прокси** | Envoy / Ztunnel | Linkerd-proxy (Rust) | Envoy (on-node) |
| **Философия** | Максимальная мощь и гибкость. | Простота, скорость и HAZL. | Сетевая конвергенция (CNI + Mesh). |
| **Производительность** | Высокая (в режиме Ambient). | Экстремальная (Rust-прокси). | Высокая (eBPF-ускорение). |
| **Сложность** | Высокая (богатый API). | Низкая («установил и забыл»). | Средняя (требует eBPF ядра). |

**Рекомендации по выбору:**
- **Istio:** при необходимости сложной L7-маршрутизации, мультикластерных федераций или функций AI Gateway.
- **Linkerd:** для высоконагруженных систем, где критичны минимальные задержки и простота эксплуатации.
- **Cilium:** если требуется глубокая интеграция с сетевым уровнем и минимизация количества агентов на узлах.

## Дополнительная информация

### Операционные аспекты (2026)

1.  **Sidecar Tax (Налог на сайдкар):** даже с оптимизациями добавление прокси увеличивает задержку. В 2026 году это решается через переход на **Ambient Mesh** или использование **eBPF-акселерации**.
2.  **Ресурсное планирование:** прокси потребляют память и CPU. В Sidecar-модели это может составлять до 10–15% ресурсов кластера. Ambient Mesh снижает этот показатель до 1–3%.
3.  **Управление сертификатами:** ротация сертификатов mTLS происходит автоматически (обычно раз в 24 часа), что исключает риски простоя из-за истечения срока действия.

### Актуальность

Основной тренд 2026 года — **унификация**. Использование Gateway API (GAMMA) позволяет переключаться между Istio и Linkerd без полной переработки манифестов управления трафиком.
