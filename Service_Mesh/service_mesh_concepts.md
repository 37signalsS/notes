# Основные концепции Service Mesh

Service Mesh — это выделенный слой инфраструктуры для управления сетевыми взаимодействиями между микросервисами на уровне приложений. Он выносит в инфраструктуру функции маршрутизации, безопасности и наблюдаемости, минимизируя изменения в коде сервисов. В контейнерных платформах mesh чаще всего реализуется через sidecar‑прокси, автоматически подключаемые к каждому Pod.

## Архитектура и термины

-   **Data plane**: набор лёгких прокси рядом с приложениями, которые перехватывают трафик L7/L4. Примеры: Envoy в Istio, linkerd‑proxy.
-   **Control plane**: сервис(ы) управления, распространяющие конфигурацию, политики и сертификаты в data plane. Примеры: istiod, Linkerd control plane.
-   **Sidecar pattern**: прокси помещается в тот же Pod, что и приложение, обеспечивая прозрачную перехватку входящего и исходящего трафика.
-   **Сервисная идентичность**: криптографическая идентификация сервисов (часто X.509 сертификаты, иногда с использованием SPIFFE ID), основа для mTLS и авторизации.
-   **Политики**: декларативные правила маршрутизации, безопасности и квот, распространяемые через CRD и применяемые прокси.

## Ключевые возможности

-   **Управление трафиком**: маршрутизация по заголовкам/пути, взвешенный сплит для canary, timeouts/retries, circuit breaking, outlier detection, тонкая балансировка.
-   **Безопасность**: mTLS по умолчанию между сервисами, автоматическая выдача и ротация сертификатов, аутентификация на уровне соединений и запросов, авторизация с учётом атрибутов L7.
-   **Наблюдаемость**: единообразные метрики (RPS, латентность, коды ответов), трейсинг с пропагацией контекста, структурированные логи прокси.
-   **Интеграция с Kubernetes**: конфигурация через CRD, работа с существующими Service/Endpoints, поддержка ingress/egress шаблонов, мультикластерные сценарии.

Пример декларативного управления трафиком в Istio с канареечным релизом и политикой отказоустойчивости:

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: payments
spec:
  host: payments.default.svc.cluster.local
  subsets:
  - name: v1
    labels: { version: v1 }
  - name: v2
    labels: { version: v2 }
  trafficPolicy:
    connectionPool:
      http: { http1MaxPendingRequests: 100 }
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 5s
      baseEjectionTime: 30s
---
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: payments
spec:
  hosts: [ "payments" ]
  http:
  - route:
    - destination: { host: payments, subset: v1, port: { number: 8080 } }
      weight: 90
    - destination: { host: payments, subset: v2, port: { number: 8080 } }
      weight: 10
    timeout: 2s
    retries: { attempts: 3, perTryTimeout: 500ms }
```

## Сопоставление Istio и Linkerd

| Аспект | Istio | Linkerd |
| :--- | :--- | :--- |
| **Прокси** | Envoy (богатый L7 функционал) | Лёгкий Rust‑прокси, упор на простоту |
| **Конфигурация** | CRD: VirtualService, DestinationRule, AuthorizationPolicy | CRD: ServiceProfile, Server/AuthorizationPolicy, TrafficSplit (через SMI) |
| **Безопасность**| mTLS, строгие политики L7, продвинутые сценарии | mTLS по умолчанию, минималистичный контроль |
| **Накладные расходы** | Выше из‑за универсальности | Ниже, оптимизировано под перформанс |
| **Установка/операции** | Гибкость, больше компонентов и настроек | Быстрая установка, меньше опций по умолчанию |

## Ограничения и операционные аспекты

-   **Дополнительная латентность**: hop через sidecar добавляет миллисекунды, важна проверка SLO.
-   **Потребление ресурсов**: каждый прокси требует CPU/RAM; учитывайте пер‑под overhead и лимиты.
-   **Сложность**: рост числа CRD и политик; необходим контроль версий и единый источник истины.
-   **Точки интеграции**: ingress‑шлюзы, egress‑паттерны, совместимость с CNI и политики L3/L4.
-   **Диагностика**: трейсинг и метрики прокси упрощают расследование, но требуют согласованной корреляции контекстов.
-   **Мультикластер**: федерация идентичностей, шифрование межкластерного трафика и глобальные политики планируются заранее.
