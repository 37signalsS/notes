4.
Управление доступом на основе атрибутов (ABAC). Помимо RBAC, ABAC можно использовать для более
динамический контроль доступа на основе пользовательских атрибутов, меток или пользовательских метаданных.Например,
вы можете определить политики, разрешающие доступ на основе ролей пользователей или принадлежности к проекту.
Вот пример политики ABAC (JSON):
{
"apiVersion": "abac.authorization.kubernetes.io/v1beta1",
"kind": "Политика",
"спецификация": {
"пользователь": "jane.doe@example.com",
"namespace": "dev",
"resource": "pods",
"глагол": "получить"
}
}
Это позволяет jane.doe@example.com получать информацию о модуле в пространстве имен dev.

Давайте рассмотрим пример включения ведения журнала аудита RBAC.
В конфигурации kube-apiserver добавьте следующее:
--audit-log-path=/var/log/kubernetes/audit.log
--audit-policy-file=/etc/kubernetes/audit-policy.yaml
Вот пример политики аудита (YAML):
apiVersion: audit.k8s.io/v1
вид: Политика
правила:
# Регистрируйте все запросы API, связанные с RBAC.
- уровень: Метаданные
глаголы: ["создать", "обновить", "исправить", "удалить", "получить",
"список", "смотреть"]
ресурсы:
- группа: "rbac.authorization.k8s.io"
ресурсы: ["роли", "привязки ролей", "кластерные роли",
"кластерные привязки"]
# Записывать все решения об авторизации
- уровень: Метаданные
ресурсы:
- группа: "authorization.k8s.io"
ресурсы: ["*"]
# Необязательно записывать все изменения configmap
(например, когда RBAC может быть настроен косвенно)
- уровень: запрос
ресурсы:
- группа: ""

# Правило по умолчанию: отказаться от всего остального
- уровень: нет
