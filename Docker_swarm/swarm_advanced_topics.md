# Docker Swarm: Продвинутые темы и внутренняя архитектура

**Актуально для:** Docker Swarm 29.x

## Определения

**mTLS (Mutual TLS)** — механизм взаимной аутентификации и шифрования внутренних коммуникаций. Подробнее: **[Основные концепции](./swarm_core_concepts.md)**.

**Raft Consensus** — алгоритм распределенного консенсуса для согласованности состояния кластера между менеджерами. Подробнее: **[Основные концепции](./swarm_core_concepts.md)**.

**Gossip Protocol (Memberlist)** — протокол "слухов" на базе библиотеки `memberlist` (SWIM), используемый для обнаружения узлов, мониторинга их состояния и распространения информации о топологии сети. Работает по UDP/TCP на порту 7946.

**IPVS (IP Virtual Server)** — компонент ядра Linux (L4 Load Balancer), на котором базируется Routing Mesh и внутренняя балансировка Swarm.

**Swarm Autolock (Автоблокировка)** — функция безопасности, шифрующая ключи TLS и логи Raft на диске. Требует ручного ввода ключа разблокировки после перезагрузки демона Docker на менеджере.

## Базовые концепции

### Внутренняя безопасность и аутентификация

#### Управление сертификатами и mTLS

Docker Swarm автоматически управляет жизненным циклом сертификатов. При инициализации создается корневой CA (Certificate Authority).
- **Ротация сертификатов:** По умолчанию происходит каждые 90 дней. Можно изменить через `docker swarm update --cert-expiry`.
- **Внешний CA:** Swarm поддерживает использование внешнего удостоверяющего центра. Это позволяет интегрировать Swarm в существующую корпоративную PKI.
- **Шифрование Gossip:** Трафик Gossip шифруется с использованием AES-GCM. Ключи шифрования автоматически ротируются менеджерами каждые 12 часов.

#### Механизм Swarm Autolock

Когда Autolock включен, ключи для расшифровки логов Raft и сертификатов TLS не сохраняются на диске в открытом виде.
- При перезапуске Docker менеджер не сможет войти в кластер автоматически.
- Необходимо выполнить `docker swarm unlock` и ввести ключ.
- **Защита данных:** Это критично для предотвращения атак, связанных с кражей физических носителей или образов дисков менеджеров.

### Распределенное состояние и алгоритм Raft

Менеджеры Swarm используют Raft для репликации состояния кластера (сервисы, сети, секреты).
- **Лидер (Leader):** Единственный узел, обрабатывающий запросы на изменение.
- **Кворум:** Для работы кластера требуется наличие `(N/2) + 1` активных менеджеров.
- **Лог репликации:** Каждое изменение записывается в лог Raft (`/var/lib/docker/swarm/raft`). Логи автоматически компактизуются (снапшоты) для экономии места.
- **Разделение ролей:** В больших кластерах рекомендуется использовать выделенные менеджеры, не запускающие воркер-нагрузки (`docker node update --availability drain <NODE>`).

## Предварительные требования

- Docker Engine 29.x на всех узлах кластера
- Сетевую доступность между узлами по портам: `2377/TCP` (управление кластером, Raft), `7946/TCP+UDP` (обнаружение узлов, gossip), `4789/UDP` (трафик Overlay/VXLAN)
- Синхронизация времени через NTP/chrony на всех менеджерах (расхождение >100ms приводит к ошибкам сертификатов mTLS)
- Нечетное количество менеджеров: 3 или 5 (7 — максимальный предел для эффективного Raft)
- Отдельный интерфейс/адрес для плоскости данных (`--data-path-addr`) в мульти-интерфейсных системах
- Для корпоративных сред: открытые порты `2376/TCP` (удаленное управление через mTLS) или `22/TCP` (SSH-контексты)

## Практические сценарии

### Настройка и управление Autolock

```bash
# Включение автоблокировки на существующем кластере
docker swarm update --autolock=true
# → Copy and store this key: SMTKN-1-abc123def...

# Разблокировка менеджера после перезагрузки
docker swarm unlock
# → Please enter unlock key: 
```

**Валидация:**
```bash
docker swarm unlock-key ls
# → показывает текущие ключи; при autolock=true ключ активен
docker info --format '{{.Swarm}}'
# → подтверждение включения autolock в выводе
```

### Тюнинг IPVS для высокой нагрузки

Если наблюдаются обрывы соединений или 504 ошибки на уровне Routing Mesh:

```bash
# Просмотр текущих таймаутов IPVS (в секундах)
ipvsadm --list --timeout
# → TCP 900  TCPFIN 120  UDP 300

# Оптимизация таймаутов через sysctl на всех узлах
sysctl -w net.ipv4.vs.timeout_tcp=300
sysctl -w net.ipv4.vs.timeout_tcpfin=15
```

**Валидация:**
```bash
ipvsadm --list --timeout
# → подтверждение новых значений TCP и TCPFIN
sysctl net.ipv4.vs.timeout_tcp
# → 300
```

### Восстановление после потери кворума (Disaster Recovery)

Если более половины менеджеров вышли из строя:

1. Выберите один из живых менеджеров.
2. Форсируйте создание нового кластера из текущего состояния Raft:
   ```bash
   docker swarm init --force-new-cluster --advertise-addr <IP>
   ```
3. Это действие делает текущий узел единственным менеджером и лидером. Остальные узлы нужно будет переподключить.

**Валидация:**
```bash
docker node ls
# → текущий узел имеет статус Leader
docker info --format '{{.Swarm.Cluster.RemoteManagers}}'
# → подтверждение единственного менеджера
```

### Использование Host Mode для производительности

Для Ingress-контроллеров (Traefik, Nginx), где важен реальный IP клиента и минимальные задержки, используйте `mode: host`:

```yaml
ports:
  - target: 80
    published: 80
    protocol: tcp
    mode: host
```
*Примечание: в этом режиме сервис может быть запущен только по одному экземпляру на узел.*

**Валидация:**
```bash
docker service inspect --format '{{.Endpoint.Ports}}' <service_name>
# → mode: host для опубликованного порта
docker service ps <service_name>
# → убедитесь, что задача размещена на каждом узле отдельно (global mode)
```

## Операции и команды

| Область | Команды | Назначение |
|:---|:---|:---|
| **Безопасность** | `docker swarm update --autolock=true` | Включение автоблокировки Raft/TLS |
| | `docker swarm unlock` | Разблокировка менеджера после перезагрузки |
| | `docker swarm unlock-key ls` | Просмотр текущих ключей разблокировки |
| | `docker swarm ca --rotate` | Ротация корневого CA |
| **Raft и кворум** | `docker node ls --filter role=manager` | Проверка активных менеджеров и лидера |
| | `docker swarm init --force-new-cluster` | Восстановление после потери кворума |
| | `docker info --format '{{.Swarm.Cluster.RemoteManagers}}'` | Список удаленных менеджеров |
| **IPVS и сеть** | `ipvsadm --list --timeout` | Просмотр таймаутов IPVS |
| | `sysctl -w net.ipv4.vs.timeout_tcp=300` | Тюнинг TCP таймаута IPVS |

## Устранение неисправностей

### Диагностика кворума и Raft

```bash
# Проверка статуса менеджеров
docker node ls --filter role=manager
# → Active/Reachable, Leader/Follower

# Детальная информация о кластере
docker info --format '{{.Swarm.Cluster.RemoteManagers}}'
# → адреса менеджеров и их статус
```

### Типичные ошибки

| Проблема | Возможная причина | Решение |
|:---|:---|:---|
| ` swarm unlock required` | Autolock включен, ключ не введен | Выполнить `docker swarm unlock` с сохраненным ключом |
| Кворум недоступен | Потеря связи между менеджерами | Восстановить связь или `docker swarm init --force-new-cluster` |
| Ошибки сертификатов mTLS | Расхождение времени >100ms | Настроить NTP/chrony, `docker swarm ca --rotate` |
| Переполнение conntrack | Высокая нагрузка на Routing Mesh | Увеличить `net.netfilter.nf_conntrack_max`, тюнинг IPVS |
| Gossip-разрыв | Порты 7946 закрыты между зонами | Открыть UDP/TCP 7946 между всеми узлами |

## Лучшие практики

1. **Менеджеры:** используйте 3 или 5 менеджеров. 7 — максимальный предел для эффективного Raft.
2. **NTP:** синхронизируйте время на всех узлах — критично для mTLS и ротации сертификатов.
3. **Бэкап Raft:** регулярно копируйте `/var/lib/docker/swarm/raft` с менеджеров для аварийного восстановления.
4. **Сети:** открывайте порты `2377/TCP`, `7946/TCP+UDP`, `4789/UDP` между всеми узлами.
5. **Rootless:** для публичных хостов и сред с повышенными рисками используйте Rootless режим.
6. **IPVS:** на высоконагруженных системах тюнингуйте `tcp_timeout` и мониторьте `conntrack`.
7. **Autolock:** включайте на всех production-кластерах, храните ключ разблокировки в секрет-менеджере.
8. **Обновления:** обновляйте менеджеров по одному, затем воркеров; перед обновлением проверяйте совместимость CSI-плагинов.
