# Docker Swarm: Продвинутые темы и внутренняя архитектура

## Определения

**mTLS (Mutual TLS, взаимная аутентификация TLS)** — механизм двусторонней аутентификации, при котором и клиент, и сервер проверяют сертификаты друг друга. В Docker Swarm используется для защиты всех внутренних коммуникаций между узлами кластера.

**Join Token (Токен присоединения)** — криптографический секретный ключ, необходимый для безопасного включения новых узлов в состав Swarm-кластера. Различаются токены для рабочих узлов (workers) и менеджеров.

**Raft Consensus (Консенсус Raft)** — алгоритм распределенного консенсуса, обеспечивающий согласованность данных между менеджерами Swarm. Гарантирует, что все менеджеры видят идентичное состояние кластера.

**Кворум (Quorum)** — минимальное количество активных менеджеров, необходимое для принятия решений в кластере. Рассчитывается как `(N/2) + 1`, где `N` — общее число менеджеров.

## Базовые концепции

### Внутренняя безопасность и аутентификация

#### Автоматическое управление TLS
Docker Swarm по умолчанию шифрует весь управляющий трафик. При инициализации кластера создается встроенный Центр сертификации (CA, Certificate Authority), который:
- Выпускает сертификаты для каждого узла.
- Обеспечивает автоматическую ротацию сертификатов (по умолчанию каждые 90 дней).
- Позволяет использовать внешний CA через соответствующие настройки.

#### Управление токенами
Токены присоединения являются первым уровнем защиты периметра кластера. Рекомендуется:
- Регулярно выполнять ротацию токенов командой `docker swarm join-token --rotate`.
- Не хранить токены в открытом виде после использования.

### Управление распределенным состоянием (Raft)

Менеджеры Swarm хранят состояние кластера (сервисы, задачи, сети, секреты) в реплицируемом логе Raft.

- **Строгая согласованность:** Любая запись в состояние кластера требует подтверждения от большинства менеджеров.
- **Отказоустойчивость:** Кластер сохраняет работоспособность при выходе из строя менее половины менеджеров.
- **Секреты:** Секреты Swarm (Secrets) хранятся в Raft-базе в зашифрованном виде и передаются в контейнеры через mTLS только при необходимости.

### Ограничения масштабируемости

Для эффективной эксплуатации Swarm следует учитывать текущие технические пределы:

| Параметр | Рекомендуемый предел |
|:---|:---|
| Количество узлов | до 1000 |
| Количество сервисов | до 5000 |
| Реплик на один сервис | до 1000 |
| Количество менеджеров | 3 или 5 (нечетное число) |

Для инсталляций, превышающих эти пределы, рекомендуется рассмотреть Kubernetes.

## Практические сценарии

### Сосуществование с автономными контейнерами
Docker Swarm Mode работает параллельно со стандартным механизмом Docker. Автономные контейнеры (запущенные через `docker run` или `docker compose` без Swarm) продолжают функционировать независимо. Это позволяет:
- Использовать Swarm только для части инфраструктуры.
- Проводить постепенную миграцию приложений без остановки текущих процессов.

### Восстановление после потери кворума
Если из строя вышло более половины менеджеров, кластер переходит в режим "только чтение". Для восстановления управления необходимо:

1. Выявить работоспособный менеджер.
2. Принудительно инициализировать кластер из текущего состояния:
   ```bash
   docker swarm init --force-new-cluster --advertise-addr <IP_адрес>
   ```
3. После этого остальные узлы необходимо будет переподключить к новой структуре кластера.

### Резервное копирование и восстановление состояния

#### Создание бэкапа (Backup)
Для сохранения состояния Raft необходимо скопировать директорию `/var/lib/docker/swarm/` с одного из менеджеров при остановленном демоне Docker:
```bash
systemctl stop docker
tar -czvf swarm_backup.tar.gz /var/lib/docker/swarm/
systemctl start docker
```

#### Восстановление (Restore)
Восстановление производится на новый узел с тем же IP-адресом:
1. Остановить Docker.
2. Распаковать архив в `/var/lib/docker/swarm/`.
3. Запустить Docker и инициализировать кластер.

### Диагностика внутренних механизмов

#### Проверка статуса TLS
```bash
docker info | grep -A 5 "TLS"
```

#### Инспекция узла для выявления проблем связи
```bash
docker node inspect --pretty self
```
