# Docker Swarm: Продвинутые темы

## Определения

**Mutual TLS (mTLS)** — механизм двусторонней TLS-аутентификации, используемый в Docker Swarm для защиты коммуникации между узлами. Каждый узел имеет автоматически выпущенный сертификат, что обеспечивает шифрование трафика и взаимную проверку подлинности.

**Join Token** — криптографический токен для безопасного присоединения новых узлов к кластеру. Существуют отдельные токены для рабочих узлов и менеджеров.

**Raft Consensus** — алгоритм консенсуса, используемый менеджерами Swarm для поддержания согласованного состояния кластера. Требует кворума (большинства) менеджеров для принятия решений.

## Базовые концепции

### Безопасность и аутентификация

#### TLS-шифрование

Весь трафик между узлами Swarm шифруется по умолчанию. Менеджеры автоматически создают корневой CA и выпускают сертификаты для каждого узла при присоединении. Сертификаты ротируются автоматически (по умолчанию каждые 90 дней).

#### Токены присоединения

Существует два типа токенов:

- **Worker join token** — для присоединения рабочих узлов
- **Manager join token** — для присоединения дополнительных менеджеров

Токены можно ротировать через `docker swarm join-token --rotate <worker|manager>`.

#### RBAC и контроль доступа

Docker Swarm **не имеет встроенной RBAC**. Разграничение доступа реализуется на уровне:

- Защиты Docker Engine API (TLS-сертификаты)
- Операционной системы (пользователи, группы, sudo)
- Контекстов Docker (`docker context`) для управления доступом к разным кластерам

Подробнее о контекстах — в **[swarm_management_cli.md](./swarm_management_cli.md)**.

### Распределенное хранение данных

#### Raft-база данных

Менеджеры хранят состояние кластера в зашифрованной Raft-базе данных. Особенности:

- Данные реплицируются на всех менеджеров
- Для записи требуется кворум (большинство менеджеров)
- Секреты хранятся в зашифрованном виде внутри Raft
- При потере кворума кластер становится неспособен принимать изменения

Рекомендуется **нечетное количество менеджеров** (3 или 5) для обеспечения отказоустойчивости.

#### Лимиты масштабирования

| Параметр | Значение |
|---|---|
| Максимум узлов в кластере | ~1000 |
| Максимум сервисов | ~5000 |
| Максимум реплик на сервис | ~1000 |
| Рекомендуемый размер кластера | до 50 узлов |

Для крупных инсталляций рассмотрите Kubernetes или Nomad (сравнение в **[../Nomad/definitions_and_concepts.md](../Nomad/definitions_and_concepts.md)**).

### Стратегии обновления сервисов

#### Rolling Update (по умолчанию)

Постепенное обновление реплик без простоя:

```sh
docker service update --image nginx:1.27 new-nginx
```

Параметры для контроля процесса:

- `--update-parallelism` — количество реплик, обновляемых одновременно (по умолчанию 1)
- `--update-delay` — задержка между обновлениями групп реплик
- `--update-failure-action` — действие при ошибке (`continue`, `pause`, `rollback`)

#### Canary-развертывание

Ручная реализация через увеличение реплик новой версии:

```sh
# Создать сервис с новой версией (1 реплика)
docker service create --name app-canary --replicas 1 app:v2

# Постепенно увеличивать реплики, уменьшать старый сервис
docker service scale app-canary=3 app-old=7
```

#### Blue-Green развертывание

Развертывание новой версии параллельно со старой:

```sh
# Создать новый сервис
docker service create --name app-green --replicas 10 app:v2

# Переключить трафик (через обновление labels или DNS)
# Удалить старый сервис
docker service rm app-blue
```

Автоматизация через **[Traefik](./swarm_ingress_traefik.md)** с использованием labels.

## Практические сценарии

### Сосуществование с автономными контейнерами

Swarm Mode не влияет на работу standalone-контейнеров:

- Существующие контейнеры продолжают работать
- Docker Compose проекты запускаются в обычном режиме
- Swarm-сервисы используют отдельный namespace

Это позволяет проводить постепенную миграцию приложений в Swarm без остановки инфраструктуры.

### Восстановление после потери кворума

Если недоступно большинство менеджеров:

```sh
# На оставшемся доступном менеджере
docker node demote <недоступный-менеджер>
docker node rm <недоступный-менеджер>

# Или принудительно инициализировать новый кластер
docker swarm init --force-new-cluster
```

**Важно:** После потери кворума невозможно изменять состояние кластера до восстановления менеджеров или выполнения `--force-new-cluster`.

### Отладка и диагностика

#### Проверка состояния кластера

```sh
# Статус узлов
docker node ls

# Детали узла
docker node inspect --pretty <NODE-ID>

# Задачи сервиса
docker service ps <SERVICE_NAME>

# Журналы сервиса
docker service logs <SERVICE_NAME>
```

#### Диагностика сети

```sh
# Список сетей
docker network ls

# Инспекция overlay-сети
docker network inspect <NETWORK_NAME>

# Проверка DNS
docker run --rm alpine nslookup <SERVICE_NAME>
```

#### Проверка сертификатов

```sh
# Информация о сертификатах узла
docker info | grep -A 5 "TLS"

# Расположение сертификатов
ls -la /var/lib/docker/swarm/certificates/
```

### Резервное копирование и восстановление

#### Бэкап состояния Swarm

```sh
# Остановить Docker
systemctl stop docker

# Скопировать данные Swarm
tar -czvf swarm-backup.tar.gz /var/lib/docker/swarm/

# Запустить Docker
systemctl start docker
```

#### Восстановление из бэкапа

```sh
# Остановить Docker
systemctl stop docker

# Восстановить данные
tar -xzvf swarm-backup.tar.gz -C /

# Запустить Docker
systemctl start docker
```

**Важно:** Восстановление работает только на том же узле с тем же IP-адресом.

## Дополнительная информация

### Сравнение с другими оркестраторами

| Функция | Docker Swarm | Kubernetes | Nomad |
|---|---|---|---|
| Встроенная RBAC | ✗ | ✓ | ✓ |
| Автомасштабирование | Ограниченное | HPA/VPA | ✓ |
| Service Mesh | Требуется внешний | Istio/Linkerd | Consul Connect |
| Сложность | Низкая | Высокая | Средняя |
| Экосистема | Ограниченная | Огромная | Растущая |

Подробное сравнение — в **[../Nomad/definitions_and_concepts.md](../Nomad/definitions_and_concepts.md)**.

### Безопасность: лучшие практики

- Регулярная ротация токенов присоединения
- Ограничение доступа к Docker Engine API
- Использование secrets для чувствительных данных
- Сетевая сегментация через overlay-сети
- Мониторинг и логирование событий кластера

Подробнее об управлении секретами — в **[swarm_secrets_configs.md](./swarm_secrets_configs.md)**.

### Миграция на другие платформы

При переходе с Docker Swarm на Kubernetes или Nomad:

- Конвертация `docker-compose.yml` в Helm-чарты или Nomad-джобы
- Замена Swarm-сетей на CNI-плагины
- Адаптация secrets/configs под целевую платформу
