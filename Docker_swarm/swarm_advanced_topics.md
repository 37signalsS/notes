# Docker Swarm: Продвинутые темы и внутренняя архитектура

## Определения

**mTLS (Mutual TLS, взаимная аутентификация TLS)** — механизм двусторонней аутентификации, при котором и клиент, и сервер проверяют сертификаты друг друга. В Docker Swarm используется для защиты всех внутренних коммуникаций и автоматического шифрования трафика управления.

**Raft Consensus (Консенсус Raft)** — алгоритм распределенного консенсуса, используемый менеджерами для поддержания согласованного состояния кластера. Обеспечивает строгую консистентность логов и выбор лидера.

**Gossip Protocol (SWIM)** — протокол "слухов" (Scalable Weakly-consistent Infection-style Process Group Membership), используемый для обнаружения узлов, мониторинга их состояния и распространения информации о топологии сети. Работает по протоколу UDP на порту 7946.

**Swarm Autolock (Автоблокировка)** — функция безопасности, шифрующая ключи TLS и логи Raft на диске. Требует ручного ввода ключа разблокировки после перезагрузки демона Docker на менеджере.

## Базовые концепции

### Внутренняя безопасность и аутентификация

#### Управление сертификатами и mTLS

Docker Swarm автоматически управляет жизненным циклом сертификатов. При инициализации создается корневой CA (Certificate Authority).
- **Ротация сертификатов:** По умолчанию происходит каждые 90 дней. Можно изменить через `docker swarm update --cert-expiry`.
- **Внешний CA:** Swarm поддерживает использование внешнего удостоверяющего центра (например, через протокол управления сертификатами). Это позволяет интегрировать Swarm в существующую корпоративную PKI.

#### Механизм Swarm Autolock

Когда Autolock включен, ключи, необходимые для расшифровки логов Raft и сертификатов TLS, не сохраняются на диске в открытом виде.
- При перезапуске Docker менеджер не сможет войти в кластер автоматически.
- Необходимо выполнить `docker swarm unlock` и ввести ключ.
- Это защищает кластер от атак, связанных с физическим доступом к диску узла.

### Распределенное состояние и алгоритм Raft

Менеджеры Swarm используют Raft для репликации состояния кластера (сервисы, сети, секреты).
- **Лидер (Leader):** Единственный узел, обрабатывающий запросы на изменение.
- **Последователи (Followers):** Реплицируют логи лидера и готовы стать лидерами в случае его сбоя.
- **Лог репликации:** Каждое изменение (например, `service create`) записывается в лог Raft. Изменение считается зафиксированным (committed), когда оно подтверждено большинством менеджеров (кворумом).

### Сетевая архитектура и Gossip

Для эффективного масштабирования Swarm разделяет трафик управления на два уровня:
1. **Raft (TCP 2377):** Высоконадежный трафик между менеджерами для синхронизации состояния.
2. **Gossip (UDP/TCP 7946):** Легковесный трафик между всеми узлами кластера для отслеживания доступности узлов и Service Discovery.

Использование Gossip позволяет Swarm быстро обнаруживать падение узлов без создания чрезмерной нагрузки на менеджеры.

### Ограничения и масштабируемость

| Параметр | Значение / Рекомендация |
|:---|:---|
| Кворум менеджеров | `(N/2) + 1` |
| Максимальное число менеджеров | 7 (дальнейшее увеличение замедляет Raft из-за задержек синхронизации) |
| Время обнаружения сбоя узла | ~5 секунд (настраивается через Gossip-параметры) |
| Rootless Mode | Поддерживается с ограничениями (требует `slirp4netns` или `VPNKit`) |

## Практические сценарии

### Настройка и управление Autolock

```bash
# Включение автоблокировки на существующем кластере
docker swarm update --autolock=true
# → Copy and store this key: SMTKN-1-abc123def...

# Разблокировка менеджера после перезагрузки
docker swarm unlock
# → Please enter unlock key: 

# Ротация ключа разблокировки
docker swarm update --autolock=true
```

### Восстановление после потери кворума

Если более половины менеджеров стали недоступны, кластер перестает принимать изменения. Для восстановления:

1. Выберите один из оставшихся менеджеров.
2. Принудительно создайте новый кластер из текущего состояния:
   ```bash
   docker swarm init --force-new-cluster --advertise-addr <IP>
   # → Swarm initialized: current node (<ID>) is now a manager.
   ```
3. Остальные выжившие узлы (менеджеры и воркеры) должны быть заново присоединены к новому кластеру (через `swarm leave` и `swarm join`).

### Резервное копирование и восстановление Raft

#### Бэкап (Backup)
Бэкап выполняется на любом менеджере. Рекомендуется останавливать Docker для обеспечения целостности файлов Raft.

```bash
# 1. Остановить демон
systemctl stop docker
# 2. Скопировать данные Swarm
tar -czvf swarm-backup.tar.gz /var/lib/docker/swarm
# 3. Запустить демон
systemctl start docker
```

#### Восстановление (Restore)
1. Остановить Docker на целевом узле.
2. Очистить `/var/lib/docker/swarm`.
3. Распаковать бэкап в `/var/lib/docker/swarm`.
4. Запустить Docker и выполнить `docker swarm init --force-new-cluster`.

### Диагностика и глубокая отладка

#### Проверка статуса Raft на менеджере

```bash
# Проверка роли и состояния текущего менеджера
docker info | grep -A 5 "Swarm"
# → Manager Addresses:
# →  10.0.0.1:2377
# →  10.0.0.2:2377

# Инспекция узла для просмотра сертификатов и TLS
docker node inspect self --pretty
```

#### Использование режима Debug
Если Swarm ведет себя некорректно, можно включить расширенное логирование в демоне Docker (`/etc/docker/daemon.json` → `"debug": true`), после чего анализировать логи через `journalctl -u docker`.

## Дополнительная информация

### Сравнение механизмов консенсуса

| Функция | Docker Swarm (Raft) | Kubernetes (etcd) | Nomad (Raft) |
|:---|:---|:---|:---|
| **Хранилище** | Встроено в процесс Docker | Внешнее (etcd) | Встроено в бинарный файл |
| **Сложность** | Минимальная (интегрировано) | Высокая (управление etcd) | Низкая |
| **Производительность** | Высокая для средних кластеров | Максимальная (за счет etcd) | Высокая |
