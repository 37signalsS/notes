# Docker Swarm: Продвинутые темы и внутренняя архитектура

## Определения

**mTLS (Mutual TLS, взаимная аутентификация TLS)** — механизм двусторонней аутентификации, при котором и клиент, и сервер проверяют сертификаты друг друга. В Docker Swarm используется для защиты всех внутренних коммуникаций и автоматического шифрования трафика управления.

**Raft Consensus (Консенсус Raft)** — алгоритм распределенного консенсуса, используемый менеджерами для поддержания согласованного состояния кластера (TCP 2377). Обеспечивает строгую консистентность логов и выбор лидера.

**Gossip Protocol (Memberlist)** — протокол "слухов" на базе библиотеки `memberlist` (SWIM), используемый для обнаружения узлов, мониторинга их состояния и распространения информации о топологии сети. Работает по протоколу UDP/TCP на порту 7946.

**IPVS (IP Virtual Server)** — компонент ядра Linux (L4 Load Balancer), на котором базируется Routing Mesh и внутренняя балансировка Swarm.

**Swarm Autolock (Автоблокировка)** — функция безопасности, шифрующая ключи TLS и логи Raft на диске. Требует ручного ввода ключа разблокировки после перезагрузки демона Docker на менеджере.

## Базовые концепции

### Внутренняя безопасность и аутентификация

#### Управление сертификатами и mTLS

Docker Swarm автоматически управляет жизненным циклом сертификатов. При инициализации создается корневой CA (Certificate Authority).
- **Ротация сертификатов:** По умолчанию происходит каждые 90 дней. Можно изменить через `docker swarm update --cert-expiry`.
- **Внешний CA:** Swarm поддерживает использование внешнего удостоверяющего центра. Это позволяет интегрировать Swarm в существующую корпоративную PKI.
- **Шифрование Gossip:** Трафик Gossip шифруется с использованием AES-GCM. Ключи шифрования автоматически ротируются менеджерами каждые 12 часов.

#### Механизм Swarm Autolock

Когда Autolock включен, ключи для расшифровки логов Raft и сертификатов TLS не сохраняются на диске в открытом виде.
- При перезапуске Docker менеджер не сможет войти в кластер автоматически.
- Необходимо выполнить `docker swarm unlock` и ввести ключ.
- **Защита данных:** Это критично для предотвращения атак, связанных с кражей физических носителей или образов дисков менеджеров.

### Распределенное состояние и алгоритм Raft

Менеджеры Swarm используют Raft для репликации состояния кластера (сервисы, сети, секреты).
- **Лидер (Leader):** Единственный узел, обрабатывающий запросы на изменение.
- **Кворум:** Для работы кластера требуется наличие `(N/2) + 1` активных менеджеров.
- **Лог репликации:** Каждое изменение записывается в лог Raft (`/var/lib/docker/swarm/raft`). Логи автоматически компактизуются (снапшоты) для экономии места.
- **Разделение ролей:** В больших кластерах рекомендуется использовать выделенные менеджеры, не запускающие воркер-нагрузки (`docker node update --availability drain <NODE>`).

### Сетевая архитектура и балансировка (IPVS)

Swarm использует Routing Mesh для распределения трафика.
1. **Ingress Network:** Специальная оверлейная сеть, принимающая трафик на опубликованных портах всех узлов.
2. **IPVS Load Balancing:** На каждом узле Docker настраивает правила IPVS. Когда пакет приходит на опубликованный порт, IPVS перенаправляет его на виртуальный IP (VIP) сервиса, а затем на конкретный контейнер.
3. **Проблема Conntrack:** При очень высокой нагрузке таблица `conntrack` ядра может переполниться, что приведет к отбросу пакетов.

### Топологическое планирование (Topology Awareness)

В отличие от Kubernetes, Swarm не имеет "Topology Aware Hints" как отдельной сущности, но реализует это через:
- **Placement Preferences:** Позволяет равномерно распределять реплики по доменам сбоя (зоны, стойки).
  ```bash
  --placement-pref 'spread=node.labels.zone'
  ```
- **Node Labels:** Пользовательские метки для привязки сервисов к конкретному оборудованию или локациям (например, `region`, `pci-e_ssd`, `arm64`).

### Ограничения и масштабируемость

| Параметр | Рекомендация 2026 |
|:---|:---|
| Число менеджеров | 3 или 5 (7 — максимум, далее Raft замедляется) |
| Лимит узлов | ~1000 узлов (эффективный предел Gossip) |
| MTU Overlay | 1450 (стандарт для VXLAN, чтобы избежать фрагментации) |
| Тюнинг IPVS | Рекомендуется уменьшать `tcp_timeout` для высоконагруженных API |

## Практические сценарии

### Настройка и управление Autolock

```bash
# Включение автоблокировки на существующем кластере
docker swarm update --autolock=true
# → Copy and store this key: SMTKN-1-abc123def...

# Разблокировка менеджера после перезагрузки
docker swarm unlock
# → Please enter unlock key: 
```

### Тюнинг IPVS для высокой нагрузки

Если наблюдаются обрывы соединений или 504 ошибки на уровне Routing Mesh:

```bash
# Просмотр текущих таймаутов IPVS (в секундах)
ipvsadm --list --timeout
# → TCP 900  TCPFIN 120  UDP 300

# Оптимизация таймаутов через sysctl на всех узлах
sysctl -w net.ipv4.vs.timeout_tcp=300
sysctl -w net.ipv4.vs.timeout_tcpfin=15
```

### Восстановление после потери кворума (Disaster Recovery)

Если более половины менеджеров вышли из строя:

1. Выберите один из живых менеджеров.
2. Форсируйте создание нового кластера из текущего состояния Raft:
   ```bash
   docker swarm init --force-new-cluster --advertise-addr <IP>
   ```
3. Это действие делает текущий узел единственным менеджером и лидером. Остальные узлы нужно будет переподключить.

### Использование Host Mode для производительности

Для Ingress-контроллеров (Traefik, Nginx), где важен реальный IP клиента и минимальные задержки, используйте `mode: host`:

```yaml
ports:
  - target: 80
    published: 80
    protocol: tcp
    mode: host
```
*Примечание: в этом режиме сервис может быть запущен только по одному экземпляру на узел.*

## Дополнительная информация

### Сравнение механизмов консенсуса

| Функция | Docker Swarm (Raft) | Kubernetes (etcd) | Nomad (Raft) |
|:---|:---|:---|:---|
| **Хранилище** | Встроено (FDB/Raft) | Внешнее (etcd) | Встроено |
| **Сложность** | Минимальная | Высокая | Низкая |
| **Управление** | Автоматическое | Ручное/Операторы | Полуавтоматическое |
