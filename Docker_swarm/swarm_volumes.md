# Docker Swarm: управление томами

## Определения

**Local Volume (Локальный том)** — стандартный Docker-том, данные которого хранятся на файловой системе одного конкретного узла Swarm. По умолчанию используется в Swarm-сервисах.

**Persistent Volume (Персистентный том)** — том, данные которого сохраняются при перемещении контейнеров между узлами кластера. Требует использования сетевых файловых систем или плагинов хранения.

**Cluster Volume (Кластерный том / CSI)** — современный тип томов в Docker Swarm (начиная с версии 23.0), использующий интерфейс CSI для интеграции с внешними хранилищами. Swarm отслеживает состояние таких томов на уровне всего кластера. Подробнее см. **[Продвинутые тома в Swarm](./swarm_volumes_advanced.md)**.

**Access Mode (Режим доступа)** — характеристика тома, определяющая, сколько узлов и задач могут одновременно использовать его.
- **RWO (ReadWriteOnce):** доступ на чтение/запись только одной задаче на одном узле.
- **RWX (ReadWriteMany):** одновременный доступ на чтение/запись для множества задач на разных узлах.

## Базовые концепции

### Проблема персистентности в Swarm

По умолчанию тома в Docker Swarm являются **локальными**. Это создает проблему при перемещении задач между узлами:

```
[Узел 1] → [Том: /var/lib/docker/volumes/data]
    ↓ (миграция задачи)
[Узел 2] → [Том: ПУСТО]
```

Если задача сервиса переносится на другой узел (сбой, масштабирование), данные в локальном томе становятся недоступны. Это делает стандартные Docker-тома непригодными для stateful-приложений без использования распределенных хранилищ или сетевых ФС.

### Режимы работы томов

| Тип | Сфера применения | Перенос между узлами |
|---|---|---|
| **Local (bind/volume)** | Кэш, временные файлы, логи | Нет (привязан к узлу) |
| **NFS / Shared FS** | Конфигурации, статика, медиа | Да (через сетевое монтирование) |
| **Cluster (CSI)** | Базы данных, блочные устройства | Да (автоматически оркестратором) |

### Топология и размещение (Topology Awareness)

Для Cluster Volumes Swarm учитывает "топологию" (например, зоны доступности в облаке). Если том создан в зоне `us-east-1a`, Swarm автоматически запланирует запуск контейнера именно на узле в этой зоне. Для локальных томов это поведение эмулируется через `placement constraints` и метки узлов.

## Практические сценарии

### Использование Cluster Volumes (CSI)

Для работы требуется установленный CSI-плагин (например, для AWS EBS, Ceph или Hetzner Cloud).

```yaml
version: '3.8'

services:
  db:
    image: postgres:16-alpine
    volumes:
      - type: cluster
        source: pg_data
        target: /var/lib/postgresql/data
        # volume_policy определяет поведение при удалении сервиса
        volume_options:
          cluster_options:
            group: "databases"
    deploy:
      replicas: 1

volumes:
  pg_data:
    external: true # Рекомендуется создавать заранее
```

**Создание тома через CLI (пример):**
```bash
docker volume create --driver <driver-name> \
  --availability active \
  --scope swarm \
  pg_data
```

### Настройка NFS для общих данных

При настройке NFS важно использовать параметр `nocopy`, чтобы Docker не пытался копировать содержимое целевой директории образа в сетевой том при первом запуске.

```yaml
version: '3.8'

services:
  web:
    image: nginx:1.27-alpine
    deploy:
      replicas: 3
    volumes:
      - type: volume
        source: nfs-content
        target: /usr/share/nginx/html
        volume:
          nocopy: true # Отключает копирование данных из образа в том

volumes:
  nfs-content:
    driver: local
    driver_opts:
      type: nfs
      o: addr=nfs.example.com,rw,nfsvers=4.1,nolock,soft
      device: ":/srv/docker/swarm/web-content"
```

### Локальные тома с ограничениями размещения

Если данные могут быть локальными (например, кэш Redis), используйте `placement constraints`:

```yaml
services:
  cache:
    image: redis:7.4-alpine
    volumes:
      - cache-data:/data
    deploy:
      replicas: 1
      placement:
        constraints:
          - node.labels.storage-type == fast-ssd

volumes:
  cache-data:
    driver: local
```

## Безопасность и ограничения

### Ограничение прав доступа (Read-Only)

Если сервису не нужно изменять данные (например, конфиги или статика), монтируйте тома в режиме "только чтение":

```yaml
services:
  web:
    volumes:
      - type: volume
        source: static-assets
        target: /app/static
        read_only: true
```

### Управление владельцем данных

NFS и Bind Mounts часто вызывают проблемы с правами (UID/GID).
- Для NFS используйте опцию `all_squash` на стороне сервера или убедитесь, что UID пользователя внутри контейнера совпадает с владельцем директории на сервере.
- Для Cluster Volumes драйверы обычно управляют правами автоматически.

### Шифрование

Docker Swarm не шифрует данные внутри томов нативно. Шифрование должно обеспечиваться:
1. На уровне СХД (шифрование дисков в AWS/GCP).
2. На уровне файловой системы (LUKS).
3. Приложениями (шифрование на уровне БД).

## Обслуживание и мониторинг

### Очистка неиспользуемых томов

Команда `docker volume prune` работает только **локально** на том узле, где она запущена. Она не удаляет Cluster Volumes, которые видны на уровне всего кластера.

**Алгоритм очистки кластера:**
1. Выполнить `docker volume prune` на всех рабочих узлах (для локальных томов).
2. Использовать `docker volume rm <name>` для удаления Cluster Volumes (с менеджера).

### Инспекция томов

Для Cluster Volumes инспекция на менеджере дает информацию о состоянии монтирования:

```bash
docker volume inspect pg_data
# → Ищите секцию "ClusterVolume" с информацией о NodeID и PublishContext
```

## Устранение неполадок

### Том не монтируется

**Проверка:**
1. Доступность сетевого ресурса: `showmount -e <server-ip>`.
2. Состояние CSI-плагина: `docker plugin ls`.
3. Ошибки в логах Docker Engine: `journalctl -u docker -f`.
4. Для NFS: проверьте наличие пакета `nfs-common` (Debian/Ubuntu) или `nfs-utils` (RHEL/CentOS) на **всех** узлах.

### Ошибка "volume in use"

Часто возникает при переезде задачи, когда старый контейнер еще не полностью освободил диск.
- Проверьте статус задач: `docker service ps <service-name>`.
- Убедитесь, что `stop_grace_period` сервиса достаточно для корректного завершения приложения.

## Дополнительная информация

### Сравнение решений

| Решение | Персистентность | Режим доступа | Сценарий (Use Case) |
|---|---|---|---|
| **Local Volume** | Нет | RWO | Кэш, временные данные |
| **NFS / CIFS** | Да | RWX | Конфиги, статический контент, медиа |
| **Cluster (CSI)** | Да | RWO / RWX | Базы данных, облачные диски |

### Лучшие практики

- **Версия Docker:** используйте **27.x** для стабильной работы CSI.
- **Stateful-приложения:** для БД предпочитайте CSI с поддержкой топологии или привязку к узлу через метки.
- **NFS:** всегда используйте `nfsvers=4.1` или выше для лучшей производительности и стабильности.
- **Имена томов:** используйте префиксы для томов разных стеков (например, `prod_db_data`), чтобы избежать конфликтов.
