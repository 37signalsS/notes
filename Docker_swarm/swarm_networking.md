# Docker Swarm: Сетевое взаимодействие

## Определения

**Overlay Network (Оверлейная сеть)** — виртуальная сеть уровня L2 (Layer 2), созданная поверх физической инфраструктуры уровня L3 (Layer 3) с использованием технологии инкапсуляции VXLAN (Virtual Extensible LAN). Позволяет контейнерам на разных узлах кластера взаимодействовать в едином адресном пространстве.

**Ingress Network (Входящая сеть)** — системная overlay-сеть для управления входящим трафиком. Является основой механизма Routing Mesh (балансировка нагрузки).

**docker_gwbridge** — сеть типа `bridge` на каждом узле Swarm, служащая шлюзом для доступа контейнеров во внешние сети.

**Routing Mesh (Сетчатая маршрутизация)** — механизм Swarm, который направляет входящие запросы на опубликованный порт любого узла кластера к свободной реплике соответствующего сервиса.

## Базовые концепции

### Архитектура overlay-сетей

Сети используют VXLAN для передачи данных (Data Plane) и протокол gossip для синхронизации состояния кластера (Control Plane). Технические подробности реализации драйвера, требования к портам и настройка MTU (Maximum Transmission Unit) описаны в разделе **[Сетевой драйвер overlay](../Docker/Docker_network/drivers/overlay.md)**.

### Сетевые компоненты кластера

| Компонент | Тип | Назначение |
|:---|:---|:---|
| `ingress` | overlay | Прием и балансировка входящего трафика |
| `docker_gwbridge` | bridge | Выход во внешние сети (Internet) |
| `bridge` | bridge | Стандартная локальная сеть узла (не для Swarm-сервисов) |
| Пользовательские сети | overlay | Изоляция микросервисов внутри кластера |

### Обнаружение сервисов (Service Discovery)

Swarm обеспечивает автоматическое разрешение имен через встроенный DNS (Domain Name System).

1. **Virtual IP (VIP)**: По умолчанию каждому сервису назначается виртуальный IP-адрес. DNS-запрос к имени сервиса возвращает этот VIP, который балансирует трафик между репликами.
2. **DNS Round-Robin (DNSRR)**: Альтернативный метод, при котором DNS возвращает список IP-адресов всех реплик. Используется, когда требуется внешняя балансировка (например, через Nginx).

Подробнее о работе DNS в Docker: **[DNS и Service Discovery](../Docker/Docker_network/dns_and_service_discovery.md)**.

## Практические сценарии

### Управление сетями в кластере

Создание сетей для приложений выполняется с помощью драйвера `overlay`.

#### Подключение сервиса к нескольким сетям

Разделение трафика фронтенда и бэкенда:

```bash
# Создание изолированных сетей
docker network create --driver overlay frontend-net
docker network create --driver overlay backend-net

# Развертывание сервиса с доступом к обеим сетям
docker service create \
  --name my-app \
  --network frontend-net \
  --network backend-net \
  --replicas 3 \
  nginx:alpine
```

### Диагностика и проверка связности

Для проверки работы сети рекомендуется использовать специализированные образы (например, `nicolaka/netshoot`).

#### Проверка разрешения имен

```bash
docker run --rm --network my-overlay-network alpine nslookup my-service
# → Server: 127.0.0.11
# → Address: 127.0.0.11#53
# → Name: my-service, Address: 10.0.x.x (VIP)
```

#### Проверка Routing Mesh

Если сервис опубликован на порту 8080, запрос можно отправить на IP любого узла кластера:

```bash
curl http://<любой_узел_кластера>:8080
```

### Устранение неисправностей (Troubleshooting)

- **Контейнеры не видят друг друга**: проверьте, открыты ли порты UDP 4789 и TCP/UDP 7946 в сетевых экранах между узлами.
- **Routing Mesh не работает**: убедитесь в целостности системной сети `ingress` через `docker network inspect ingress`.
- **Проблемы с производительностью**: проверьте настройки MTU, если узлы находятся в облачных сетях (например, AWS или GCP) с нестандартным размером кадра.

## Дополнительная информация

Для продвинутого управления трафиком уровня L7 (Layer 7) и терминирования SSL рекомендуется использовать Ingress-контроллеры.
