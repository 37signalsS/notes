# Docker Swarm: сетевое взаимодействие

## Определения

**Overlay Network (Оверлейная сеть)** — виртуальная сеть уровня L2, созданная поверх физической инфраструктуры с использованием инкапсуляции VXLAN. Это стандартный способ взаимодействия сервисов на разных узлах.

**Ingress Network (Входящая сеть)** — специальная системная оверлейная сеть (по умолчанию `ingress`), управляющая входящим трафиком. Она обеспечивает работу Routing Mesh.

**Routing Mesh (Сетчатая маршрутизация)** — механизм Swarm, позволяющий любому узлу кластера принимать трафик на опубликованный порт сервиса и перенаправлять его к активной реплике, независимо от того, запущена ли она на этом узле.

**Virtual IP (VIP)** — единый IP-адрес сервиса в оверлейной сети. Запросы к VIP балансируются между всеми репликами сервиса на уровне ядра Linux (IPVS).

**DNSRR (DNS Round-Robin)** — альтернативный режим балансировки, при котором встроенный DNS-сервер возвращает список IP-адресов всех задач (tasks) сервиса по его имени.

**docker_gwbridge** — локальный мост на каждом узле, обеспечивающий контейнерам в оверлейных сетях выход во внешнюю сеть.

## Базовые концепции

### Архитектура Routing Mesh и IPVS

Когда вы публикуете порт сервиса (например, `-p 80:80`), Swarm использует **IPVS (IP Virtual Server)** внутри пространства имен `ingress_sbox` для балансировки трафика.

1. Запрос поступает на опубликованный порт любого узла кластера.
2. Routing Mesh перехватывает трафик и направляет его в сеть `ingress`.
3. IPVS выбирает доступную реплику сервиса (алгоритм Round-Robin по умолчанию) и пересылает пакет.

**Ограничение:** Routing Mesh выполняет SNAT (Source NAT), из-за чего приложение видит IP-адрес моста `docker_gwbridge` вместо реального IP клиента. Для сохранения IP используйте режим `mode: host` (минуя Routing Mesh) или Ingress-контроллеры (например, Traefik).

### Обнаружение сервисов (Service Discovery)

Swarm предоставляет встроенный DNS-резолвер по адресу `127.0.0.11`.

#### Режимы Endpoint Mode

| Режим | Как работает | Применение |
|:---|:---|:---|
| **VIP** (дефолт) | Один виртуальный IP на сервис. Балансировка прозрачна для клиента. | Стандартные HTTP-сервисы, базы данных. |
| **DNSRR** | DNS возвращает список IP всех контейнеров. Клиент сам выбирает IP. | Внешние балансировщики (Nginx/Traefik), gRPC с клиентской балансировкой. |

### Безопасность и изоляция

1. **Изоляция сетей:** Контейнеры могут общаться только если они находятся в одной и той же оверлейной сети.
2. **Шифрование (IPsec):** Опция `--opt encrypted` включает шифрование трафика между узлами.
3. **Secure by Default (v28+):** В новых версиях Docker трафик к неопубликованным портам может блокироваться на уровне ядра для повышения безопасности (минимальные привилегии).
4. **IPv6 Dual-Stack (v27+):** Поддержка IPv6 в Swarm стала стабильной, позволяя назначать IPv6 адреса сервисам.

## Практические сценарии

### Создание сети с шифрованием и оптимизацией MTU

Для облачных сред (AWS, GCP) рекомендуется устанавливать MTU 1450, чтобы избежать фрагментации из-за оверхеда VXLAN.

```bash
docker network create \
  --driver overlay \
  --opt com.docker.network.driver.mtu=1450 \
  --opt encrypted \
  --attachable \
  backend-net
```

### Публикация портов в режиме Host

Если приложению критично видеть реальный IP-адрес клиента (например, для систем защиты от DDoS или логирования), порт публикуется в обход Routing Mesh:

```yaml
services:
  nginx:
    image: nginx:1.27-alpine
    ports:
      - target: 80
        published: 80
        mode: host # Порт открывается только на тех узлах, где запущен контейнер
    deploy:
      mode: global # Рекомендуется для host-портов, чтобы занять порт на всех узлах
```

### Разделение трафика управления и данных

Для стабильности крупных кластеров рекомендуется разделить интерфейсы для управления (Raft) и данных (VXLAN).

```bash
docker swarm init \
  --advertise-addr 10.0.1.10 \ # IP для менеджеров
  --data-path-addr 10.0.5.10   # IP для трафика данных
```

## Устранение неполадок

### Требуемые порты (Firewall)

Убедитесь, что между всеми узлами открыты:
- **2377/TCP**: Управление кластером.
- **7946/TCP+UDP**: Gossip-протокол (Service Discovery).
- **4789/UDP**: VXLAN трафик.
- **Protocol 50 (ESP)**: Если включено шифрование `--opt encrypted`.

### Проверка связности и IPVS

Если трафик не доходит до сервиса:
1. Проверьте статус IPVS на узле (требуется `ipvsadm`):
   ```bash
   # Просмотр виртуальных серверов и реальных серверов (контейнеров)
   nsenter --net=/var/run/docker/netns/ingress_sbox ipvsadm -Ln
   ```
2. Проверьте MTU: если `ping` проходит, а `curl` зависает — установите MTU 1450.
3. Логи встроенного DNS: контейнеры должны успешно резолвить имена через `127.0.0.11`.

## Лучшие практики

1. **MTU 1450:** Используйте это значение по умолчанию для всех overlay-сетей в облаках.
2. **Инкапсуляция и железо:** Используйте сетевые карты с поддержкой **VXLAN Offloading** для снижения нагрузки на CPU.
3. **Изоляция:** Не используйте одну сеть для всего кластера. Разделяйте фронтенд, бэкенд и базы данных.
4. **Пропускная способность:** Помните, что Routing Mesh создает дополнительный "прыжок" (hop) в сети. Для высоконагруженных систем (High Throughput) рассмотрите использование `host` режима или прямую маршрутизацию.
