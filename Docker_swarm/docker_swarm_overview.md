# Docker Swarm: Обзор и архитектура

**Актуально для:** Docker Swarm 29.x

## Определения

**Docker Swarm Mode** — встроенный (native) механизм оркестрации контейнеров в Docker Engine. Начиная с версии 1.12, он интегрирован непосредственно в демон Docker, что позволяет превратить группу хостов в единый отказоустойчивый виртуальный кластер без установки дополнительного ПО.

**Swarm Mode vs Classic Swarm** — критическое различие. "Classic Swarm" (версии до 1.12) был отдельным инструментом, требующим внешнего хранилища (например, Consul или etcd). Современный Swarm Mode встроен в Docker и использует внутренний протокол Raft для консенсуса.

**Сервис (Service)** — основная единица управления. Декларативное описание желаемого состояния приложения (образ, реплики, порты, сети). Оркестратор непрерывно следит за соответствием текущего состояния описанному. Подробнее: **[Основные концепции](./swarm_core_concepts.md)**.

**Routing Mesh (Сетчатая маршрутизация)** — встроенный механизм L4-балансировки. Любой узел кластера может принять трафик на опубликованном порту и перенаправить его на реплику, независимо от её местоположения. Подробнее: **[Сетевое взаимодействие в Swarm](./swarm_networking.md)**.

## Базовые концепции

### Архитектура узлов и роли

Кластер строится на двух типах узлов:

- **Менеджеры (Manager Nodes)**: Отвечают за оркестрацию, планирование задач и управление состоянием кластера. Используют алгоритм **Raft** для синхронизации состояния. Рекомендуется иметь нечетное количество менеджеров (3, 5 или 7) для обеспечения отказоустойчивости и избежания ситуации "split-brain".
- **Рабочие узлы (Worker Nodes)**: Принимают и исполняют задачи (контейнеры), назначенные менеджерами. Не участвуют в принятии решений по управлению кластером.

Безопасность взаимодействия обеспечивается автоматическим выпуском сертификатов **mTLS** с ротацией каждые 90 дней (по умолчанию). Подробнее: **[swarm_advanced_topics.md](./swarm_advanced_topics.md)**.

### Управление состоянием узлов (Maintenance)

Для обслуживания серверов Swarm поддерживает режимы доступности:
- **Active**: Узел готов принимать новые задачи.
- **Pause**: Узел продолжает выполнять текущие задачи, но новые на него не назначаются.
- **Drain**: Все задачи принудительно снимаются с узла и переносятся на другие активные узлы. Используется перед выключением сервера или обновлением ОС.

### Ключевые компоненты системы

- **Service Discovery**: Встроенный DNS-сервер и VIP (Virtual IP) для каждого сервиса. Контейнеры общаются друг с другом по именам сервисов, не заботясь об их IP.
- **Оверлейные сети (Overlay)**: Создают виртуальную сеть поверх физических хостов, позволяя контейнерам в разных подсетях общаться напрямую в изолированном сегменте. Подробнее: **[swarm_networking.md](./swarm_networking.md)**.
- **Секреты и конфигурации**: Объекты Swarm для безопасной передачи паролей (через RAM-диск/tmpfs) и файлов настроек без включения их в образ. Подробнее: **[swarm_secrets_configs.md](./swarm_secrets_configs.md)**.
- **Поддержка CSI (Container Storage Interface)**: Начиная с Docker 23.0, Swarm поддерживает CSI-драйверы для интеграции с внешними системами хранения (Ceph, NFS, GlusterFS, локальные блочные устройства). Подробнее: **[Управление томами](./swarm_volumes.md)**.

## Предварительные требования

- Docker Engine 29.x на всех узлах кластера
- Сетевую доступность между узлами по портам: `2377/TCP` (управление кластером, Raft), `7946/TCP+UDP` (обнаружение узлов, gossip), `4789/UDP` (трафик Overlay/VXLAN)
- Синхронизация времени через NTP/chrony на всех менеджерах (расхождение >100ms приводит к ошибкам сертификатов mTLS)
- Нечетное количество менеджеров: 3 или 5 (7 — максимальный предел для эффективного Raft)
- Отдельный интерфейс/адрес для плоскости данных (`--data-path-addr`) в мульти-интерфейсных системах
- Для корпоративных сред: открытые порты `2376/TCP` (удаленное управление через mTLS) или `22/TCP` (SSH-контексты)

## Практические сценарии

### Декларативное развертывание (Stacks)

Использование Docker Compose файлов для управления целыми стеками приложений. Команда `docker stack deploy` обеспечивает идемпотентность: если конфигурация не изменилась, Swarm ничего не тронет; если изменилась — применит только дельту.
**[Инструкция по развертыванию стеков](./swarm_stack_deployment.md)**.

**Валидация:**
```bash
docker stack ls
# → список задеплоенных стеков
docker stack services myapp
# → сервисы стека и их реplica count
docker stack ps myapp --no-trunc
# → статусы задач, узлы размещения, желаемое/текущее состояние
```

### Управление входящим трафиком (L7 Ingress)

Для маршрутизации по доменным именам и управления TLS рекомендуется использовать Ingress-контроллеры с нативной поддержкой Swarm API.
**[Настройка Traefik в Swarm](./swarm_ingress_traefik.md)**.

**Валидация:**
```bash
docker service ls
# → сервис Traefik запущен в режиме global или replicated
curl -H "Host: app.example.com" http://<traefik-ip>
# → трафик маршрутизирован на соответствующий backend
docker network inspect ingress
# → подтверждение подключения сервисов к сети ingress
```

### Безопасность и Rootless Swarm

Docker Swarm поддерживает запуск в режиме **Rootless**, где весь демон Docker и оркестратор работают от имени обычного пользователя. Это минимизирует риски "побега" из контейнера на хост-систему.

**Валидация:**
```bash
docker info --format '{{.SecurityOptions}}'
# → содержит "userns-remap" или "rootless"
swarm_workdir="$(docker info --format '{{.DockerRootDir}}')"
ls -ld "$swarm_workdir"
# → владелец — не root, демон запущен от обычного пользователя
```

## Сравнение: Docker Swarm vs Kubernetes

| Характеристика | Docker Swarm | Kubernetes |
| :--- | :--- | :--- |
| **Сложность установки** | Нулевая (встроено в Docker). | Высокая. Требует глубоких знаний инфраструктуры. |
| **Кривая обучения** | Низкая. Используется знакомый YAML Compose. | Высокая. Множество абстракций (Pods, Deployments, CRD). |
| **Масштабируемость** | До ~1000 узлов (рекомендуется 50–100). Хорошая производительность на средних кластерах. | До 5000+ узлов. Отраслевой стандарт для крупных инсталляций. |
| **Автоматизация отката** | Поддерживается через `rollback_config`. | Продвинутая (Deployment Controller, Argo Rollouts). |
| **Хранение данных** | CSI (предварительное создание томов, начиная с Docker 23.0), Local Volumes, NFS/CIFS. | Глубокая интеграция с CSI, динамический провижининг. |
| **Автоскейлинг** | Нет нативного (требуются внешние скрипты). | Нативный HPA (по CPU/RAM) и VPA. |
| **Управление трафиком** | Routing Mesh (L4), внешние Ingress (L7). | Services, Ingress, Service Mesh, Gateway API. |

### Преимущества и ограничения

**Преимущества:**
- Минимальное потребление ресурсов по сравнению с Kubernetes.
- Стабильность и простота в эксплуатации (один бинарник `docker`).
- Идеально для малого и среднего бизнеса, а также для сред разработки/тестирования.

**Ограничения:**
- Меньшее сообщество и количество готовых решений (Helm-чарты отсутствуют).
- Отсутствие нативной мультиарендности (Namespaces в Swarm — это только лейблы).
- Слабая поддержка сложных Statefull-приложений (баз данных) по сравнению с операторами Kubernetes.

## Операции и команды

| Область | Команды | Назначение |
|:---|:---|:---|
| **Жизненный цикл кластера** | `docker swarm init` | Инициализация кластера на первом менеджере |
| | `docker swarm join --token <token> <manager-ip>:2377` | Присоединение воркера или менеджера к кластеру |
| | `docker swarm leave --force` | Принудительный выход из кластера (на менеджере — разрушает кворум) |
| **Инспекция** | `docker node ls` | Список узлов, их статус и доступность |
| | `docker info --format '{{.Swarm}}'` | Статус Swarm на текущем узле |
| | `docker swarm inspect` | Детальная информация о кластере |
| **Управление узлами** | `docker node update --availability drain <node>` | Перевод узла в режим обслуживания |
| | `docker node promote <node>` | Повышение воркера до менеджера |
| | `docker node demote <node>` | Понижение менеджера до воркера |

## Устранение неисправностей

### Диагностика кластера

```bash
# Проверка статуса кластера и кворума
docker info --format '{{json .Swarm.RemoteManagers}}' | jq

# Статус узлов
docker node ls
# → Active/Pain/Drain, Manager/Worker, версия Engine

# Детальный статус задачи
docker service ps --no-trunc <service_name>
# → ошибки размещения, статусы, повторные попытки
```

### Типичные ошибки

| Проблема | Возможная причина | Решение |
|:---|:---|:---|
| `no suitable node found` | Нет узлов, удовлетворяющих `constraints`/`placement` | Проверить labels узлов: `docker node ls --format "{{.ID}} {{.Labels}}"` |
| Потеря Client IP | Routing Mesh выполняет SNAT | Переключить сервис в `mode: host` или использовать Proxy Protocol |
| Ошибки сертификатов mTLS | Расхождение времени между менеджерами >100ms | Настроить NTP/chrony, проверить `docker swarm ca --rotate` |
| Кворум недоступен | Нечетное количество менеджеров, потеря связи | Восстановить связь или переинициализировать кластер из бекапа Raft |
| Overlay-сеть не работает | Порты 4789/UDP или 7946 закрыты | Открыть порты между всеми узлами кластера |

## Лучшие практики

1. **Менеджеры:** используйте 3 или 5 менеджеров. 7 — максимальный предел для эффективного Raft.
2. **NTP:** синхронизируйте время на всех узлах — критично для mTLS и ротации сертификатов.
3. **Бэкап Raft:** регулярно копируйте `/var/lib/docker/swarm/raft` с менеджеров для аварийного восстановления.
4. **Сети:** открывайте порты `2377/TCP`, `7946/TCP+UDP`, `4789/UDP` между всеми узлами.
5. **Данные:** используйте CSI (начиная с Docker 23.0) или NFS/CIFS для персистентных томов; локальные тома привязывайте к узлам через labels.
6. **Rootless:** для публичных хостов и сред с повышенными рисками используйте Rootless режим.
7. **Мониторинг:** отслеживайте состояние узлов через `docker node ls` и внешние системы мониторинга.
8. **Обновления:** обновляйте менеджеров по одному, затем воркеров; перед обновлением проверяйте совместимость CSI-плагинов.
