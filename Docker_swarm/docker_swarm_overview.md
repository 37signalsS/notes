# Docker Swarm: Обзор

## Определения

**Docker Swarm Mode** — встроенный (native) механизм оркестрации контейнеров в Docker Engine. Начиная с версии 1.12, он интегрирован непосредственно в демон Docker и позволяет объединять несколько хостов в единый виртуальный кластер.

**Swarm Mode vs Classic Swarm** — важно различать современный "Swarm Mode" (встроенный в Docker) и устаревший "Classic Swarm" (отдельный инструмент/образ). Данный раздел посвящен исключительно Swarm Mode.

**Сервис (Service)** — абстракция над группой идентичных контейнеров (задач), распределенных по кластеру. Сервис определяет желаемое состояние: образ, количество реплик, сетевые настройки и ресурсы. Подробнее в **[swarm_core_concepts.md](./swarm_core_concepts.md)**.

**Routing Mesh (Сетчатая маршрутизация)** — механизм, позволяющий любому узлу кластера принимать входящий трафик на опубликованном порту сервиса и перенаправлять его на нужный контейнер, даже если он запущен на другом узле.

## Базовые концепции

### Архитектура узлов

Кластер Swarm состоит из узлов двух ролей:

- **Менеджеры (Manager Nodes)** — "мозг" кластера. Выполняют планирование (scheduling), управление состоянием через алгоритм консенсуса **Raft** и обслуживание API. Менеджеры также могут выполнять функции рабочих узлов, если это не ограничено настройками.
- **Рабочие узлы (Worker Nodes)** — "исполнители". Принимают задачи от менеджеров и запускают контейнеры. Не участвуют в принятии решений и не хранят состояние кластера.

Безопасность обеспечивается автоматическим выпуском и ротацией сертификатов **mTLS** для всех узлов. Подробнее об архитектуре и кворуме — в **[swarm_advanced_topics.md](./swarm_advanced_topics.md)**.

### Современные возможности

1. **Rootless Swarm** — поддержка запуска Swarm-кластера без прав суперпользователя (root), что значительно повышает безопасность изоляции хоста.
2. **Docker Contexts** — стандартный способ управления удаленными кластерами. Позволяет переключаться между локальным Docker и удаленным Swarm-менеджером одной командой `docker context use <name>`.
3. **Совместимость с Compose V2** — хотя для деплоя стеков используется `docker stack deploy`, современные файлы `docker-compose.yml` (спецификация Compose) полностью поддерживаются.

### Ключевые компоненты

- **Service Discovery** — встроенный VIP (Virtual IP) и DNS-сервер. Контейнеры находят друг друга по имени сервиса внутри оверлейной сети.
- **Оверлейные сети (Overlay)** — позволяют контейнерам на разных физических хостах общаться по защищенному каналу. Подробнее в **[swarm_networking.md](./swarm_networking.md)**.
- **Секреты и конфигурации** — безопасная передача паролей и конфигов в контейнеры без сохранения их на диске (tmpfs). Подробнее в **[swarm_secrets_configs.md](./swarm_secrets_configs.md)**.

## Практические сценарии

### Развертывание стеков (Stacks)

Основной способ развертывания приложений в Swarm. Стек объединяет группу связанных сервисов, сетей и томов, описанных в YAML.
**[Инструкция по развертыванию стеков](./swarm_stack_deployment.md)**.

### Управление входящим трафиком (Ingress)

Поскольку Swarm Routing Mesh работает на уровне L4, для маршрутизации L7 (HTTP/HTTPS по доменам) рекомендуется использовать Ingress-контроллеры, такие как **Traefik** или **Nginx**.
**[Настройка Traefik в Swarm](./swarm_ingress_traefik.md)**.

### Полноценный цикл CI/CD

Автоматизация деплоя из GitLab/GitHub в Swarm-кластер с учетом обновления образов без простоя (Rolling Update).
**[Обзор CI/CD для Swarm](./CI_CD/overview.md)**.

## Docker Swarm vs Kubernetes: Подробное сравнение

Выбор между Docker Swarm и Kubernetes зависит от масштаба задач, доступных ресурсов и требований к гибкости.

| Характеристика | Docker Swarm | Kubernetes |
| :--- | :--- | :--- |
| **Настройка и конфигурация** | Максимально простая (встроено в Docker). Быстрый старт с одной команды. | Сложная. Требует установки аддонов, CNI-плагинов и контроллеров. Предлагает высокую универсальность. |
| **Масштабируемость** | Быстрое масштабирование контейнеров (секунды). Нет нативного автоскейлинга. | Автоматическое масштабирование (HPA/VPA) по CPU и кастомным метрикам. Масштабирование может быть медленнее из-за сложности. |
| **Балансировка нагрузки** | Автоматическая (Routing Mesh). Маршрутизация на основе стандартной конфигурации (L4). | Продвинутые функции балансировки (Service, Ingress, Gateway API). Может требовать ручной настройки. |
| **Обновления и откаты** | Поддерживает плавные (rolling) обновления, но отсутствует встроенный автоматический откат. | Поэтапные обновления с автоматическим откатом к стабильной версии («защитная сетка») при обнаружении проблем. |
| **Сеть** | Встроенный DNS-сервер на уровне узла для взаимодействия контейнеров. | Плоская сетевая модель, позволяющая всем подам общаться напрямую, независимо от узла размещения. |
| **Мониторинг и логирование** | Нет встроенных инструментов. Полагается на внешние стеки (например, ELK). | Интегрированные инструменты и глубокая поддержка логирования/мониторинга ресурсов кластера. |
| **Обнаружение сервисов** | DNS (имя сервиса). Балансировка по круговому принципу (Round-robin). | Комплексная система (DNS, IP подов, IP сервисов, EndpointSlices). |
| **Среда выполнения (Runtime)** | Тесно интегрирован с Docker Engine. Требует его наличия. | Не зависит от Docker. Работает с любыми CRI-совместимыми рантаймами (`containerd`, `CRI-O`). |

### Архитектурная устойчивость

*   **Docker Swarm**: Полагается на менеджера для координации. Если единственный менеджер выходит из строя, управление кластером прерывается (хотя сервисы продолжают работать), и для восстановления полной функциональности может потребоваться пересоздание кластера.
*   **Kubernetes**: Использует отказоустойчивую распределенную плоскость управления (Control Plane). Модульная конструкция и поддержка различных сред выполнения (Containerd, CRI-O) через стандарт CRI делают его отраслевым стандартом для масштабных и критических развертываний.

### Преимущества и ограничения

**Преимущества:**
- Нулевая стоимость настройки (встроено в Docker).
- Использование привычного синтаксиса `docker-compose`.
- Стабильность для малых и средних нагрузок (до 1000 узлов).

**Ограничения:**
- Отсутствие встроенного механизма продвинутых стратегий (Canary/Blue-Green) без сторонних прокси.
- Меньшее количество готовых операторов и плагинов по сравнению с экосистемой K8s.
