# Docker Swarm: Основные концепции

## Определения

**Узел (Node)** — физическая или виртуальная машина с установленным Docker Engine, являющаяся частью Swarm-кластера. Узлы делятся на менеджеров и рабочих.

**Сервис (Service)** — декларативное описание задачи для выполнения в кластере. Определяет используемый образ, количество реплик, сетевые настройки и политики обновления.
- **Replicated (Реплицируемый)** — режим по умолчанию, где менеджер распределяет указанное количество реплик по узлам.
- **Global (Глобальный)** — режим, при котором одна задача запускается на каждом узле кластера.

**Задача (Task)** — атомарная единица работы в Swarm, представляющая собой конкретный запущенный Docker-контейнер. Менеджер назначает задачи на рабочие узлы.

**Routing Mesh (Сетчатая маршрутизация)** — встроенный механизм балансировки нагрузки, распределяющий входящие запросы между репликами сервиса. Позволяет обратиться к сервису через опубликованный порт на любом узле кластера.

**Service Discovery (Обнаружение сервисов)** — автоматическое обнаружение сервисов через встроенный DNS. Позволяет контейнерам обращаться друг к другу по именам сервисов без знания их IP-адресов.

## Базовые концепции

### Архитектура кластера

#### Менеджеры (Manager Nodes)

Менеджеры отвечают за оркестрацию и управление состоянием кластера:

- **Поддержание желаемого состояния** — непрерывный мониторинг и исправление расхождений между конфигурацией и текущей ситуацией.
- **Планирование задач (Scheduling)** — распределение задач по рабочим узлам с учетом доступных ресурсов и заданных ограничений.
- **Обработка API-запросов** — прием команд от пользователя и координация их выполнения.
- **Консенсус Raft** — алгоритм, обеспечивающий согласованность данных между менеджерами. Для отказоустойчивости рекомендуется нечетное количество менеджеров (3, 5 или 7). Кластер сохраняет работоспособность, пока доступно большинство (кворум) менеджеров.

#### Рабочие узлы (Worker Nodes)

Рабочие узлы предназначены исключительно для выполнения прикладных задач:

- Запуск и остановка контейнеров по инструкциям от менеджеров.
- Отправка отчетов о состоянии задач и доступных аппаратных ресурсах.
- Менеджеры по умолчанию также выполняют функции рабочих узлов, если их роль не ограничена специально.

### Жизненный цикл задачи (Task Lifecycle)

Задача проходит через ряд состояний в процессе своего выполнения:
1. **New** — задача создана, но еще не назначена на узел.
2. **Pending** — ресурсы для задачи зарезервированы.
3. **Assigned** — задача назначена на конкретный узел.
4. **Accepted** — рабочий узел принял задачу.
5. **Preparing** — подготовка окружения (например, pull образа).
6. **Starting** — запуск контейнера.
7. **Running** — контейнер запущен и работает.
8. **Completed/Failed/Shutdown** — терминальные состояния (успех, ошибка или плановая остановка).

### Сетевая модель

Все узлы кластера взаимодействуют через зашифрованные каналы TLS. Сетевая архитектура включает:

- **Оверлейные сети (Overlay networks)** — виртуальные сети уровня L2, соединяющие контейнеры на разных узлах кластера.
- **Ingress-сеть** — специальная системная оверлейная сеть для входящего трафика, обеспечивающая работу Routing Mesh.
Подробности в **[swarm_networking.md](./swarm_networking.md)**.

### Стратегии обновления (Rolling Updates)

Swarm позволяет обновлять сервисы без простоя:
- **Parallelism** — количество реплик, обновляемых одновременно.
- **Delay** — задержка между обновлением групп реплик.
- **Failure Action** — действие при сбое обновления (`pause`, `continue`, `rollback`).
- **Order** — порядок обновления (`start-first` — запуск новой реплики перед остановкой старой, или `stop-first`).

### Механизмы отказоустойчивости

- **Reconciliation Loop (Цикл согласования)** — процесс, в котором менеджер постоянно сравнивает фактическое состояние с декларативной конфигурацией. Если реплика сервиса падает, Swarm автоматически создает новую.
- **Health Checks (Проверки состояния)** — мониторинг работоспособности через инструкции `HEALTHCHECK` в Dockerfile или проверки по протоколам HTTP/TCP. Неисправные задачи автоматически заменяются здоровыми.

## Практические сценарии

### Отказоустойчивость при сбое менеджера

При выходе из строя лидера кластера (лидера Raft):

1. Оставшиеся менеджеры инициируют выборы нового лидера.
2. После завершения выборов управление кластером полностью возобновляется.
3. Работающие сервисы продолжают функционировать, но внесение изменений в конфигурацию невозможно до восстановления кворума.

### Масштабирование сервиса

Для изменения количества запущенных реплик используется команда `scale` или `update`:

```bash
# Увеличение количества реплик до 10
docker service scale my-service=10
# → my-service scaled to 10

# Альтернативный способ через update
docker service update --replicas 10 my-service
# → my-service

# Просмотр распределения задач по узлам кластера
docker service ps my-service
# → ID            NAME              IMAGE          NODE      DESIRED STATE   CURRENT STATE
# → 123abc456def  my-service.1      nginx:latest   node-1    Running         Running 5 minutes ago
```

### Вывод узла из обслуживания (Draining)

Для проведения технических работ на хосте узел необходимо перевести в режим `drain`:

```bash
# Пометить узел как недоступный для новых задач
docker node update --availability drain <NODE-ID>
# → <NODE-ID>

# Убедиться, что все задачи перемещены на другие узлы
docker node ps <NODE-ID>
# → ID            NAME              IMAGE          NODE      DESIRED STATE   CURRENT STATE
# → (список задач со статусом Shutdown/Moved)

# После завершения работ вернуть узел в активное состояние
docker node update --availability active <NODE-ID>
# → <NODE-ID>
```

## Дополнительная информация

### Управление ролями узлов

Роли узлов можно изменять без остановки кластера:

- **Promote (Повышение)** — превращение рабочего узла в менеджера.
- **Demote (Понижение)** — превращение менеджера в рабочий узел.

### Лимиты и масштабируемость

Swarm оптимизирован для кластеров среднего размера:

- Рекомендуемый размер кластера — до 50–100 узлов.
- Теоретический максимум — до 1000 узлов и 5000 сервисов.
- Для сверхкрупных инсталляций рекомендуется использовать Kubernetes.
