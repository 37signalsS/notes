# Docker Swarm: Основные концепции

## Определения

**Узел (Node)** — физическая или виртуальная машина с установленным Docker Engine, являющаяся частью Swarm-кластера. Узлы делятся на менеджеров и рабочих.

**Сервис (Service)** — декларативное описание задачи для выполнения в кластере. Определяет используемый образ, количество реплик, сетевые настройки и политики обновления.
- **Replicated (Реплицируемый)** — режим по умолчанию, где менеджер распределяет указанное количество реплик по узлам.
- **Global (Глобальный)** — режим, при котором одна задача запускается на каждом узле кластера (подходит для агентов мониторинга, логирования).

**Задача (Task)** — атомарная единица работы в Swarm, представляющая собой конкретный запущенный Docker-контейнер. Менеджер назначает задачи на рабочие узлы. Задачи неизменяемы (immutable): если задача завершилась с ошибкой, создается новая.

**Routing Mesh (Сетчатая маршрутизация)** — встроенный механизм балансировки нагрузки на уровне L4, распределяющий входящие запросы между репликами сервиса. Позволяет обратиться к сервису через опубликованный порт на любом узле кластера.

**Service Discovery (Обнаружение сервисов)** — автоматическое обнаружение сервисов через встроенный DNS (127.0.0.11).

**mTLS (Mutual TLS)** — механизм взаимной аутентификации и шифрования всех внутренних коммуникаций между узлами кластера.

## Базовые концепции

### Архитектура кластера

#### Менеджеры (Manager Nodes)

Менеджеры являются "мозгом" кластера и отвечают за его оркестрацию:

- **Поддержание желаемого состояния** — непрерывный мониторинг и исправление расхождений между конфигурацией и текущей ситуацией (**Reconciliation Loop**).
- **Планирование задач (Scheduling)** — распределение задач по рабочим узлам с учетом ресурсов, меток и ограничений.
- **Обработка API-запросов** — прием команд от пользователя и координация их выполнения.
- **Консенсус Raft** — алгоритм, обеспечивающий согласованность данных между менеджерами.
  - **Роли Raft:**
    - **Leader (Лидер):** единственный узел, принимающий решения и обрабатывающий запросы на изменение.
    - **Follower (Последователь):** реплицирует лог лидера и готов стать кандидатом при сбое лидера.
    - **Candidate (Кандидат):** временное состояние при проведении выборов нового лидера.
  - **Кворум:** минимальное количество работающих менеджеров для принятия решений. Формула: `(N/2) + 1`. При потере кворума кластер переходит в режим "только чтение".
  - **Рекомендация:** используйте нечетное количество менеджеров (3, 5 или 7). Максимально эффективный предел — 7 узлов.

#### Рабочие узлы (Worker Nodes)

Рабочие узлы предназначены исключительно для выполнения прикладных задач:

- Запуск и остановка контейнеров по инструкциям от менеджеров.
- Отправка отчетов о состоянии задач и доступных ресурсах (heartbeats).
- Менеджеры также могут выполнять функции рабочих узлов, если их режим доступности (`Availability`) установлен в `Active`.

### Жизненный цикл задачи (Task Lifecycle)

Полный список состояний задачи:
1.  **New** — задача создана, но еще не назначена на узел.
2.  **Pending** — ресурсы для задачи зарезервированы, ожидается назначение.
3.  **Assigned** — задача назначена на конкретный узел.
4.  **Accepted** — рабочий узел принял задачу и подтвердил готовность.
5.  **Preparing** — подготовка окружения (pull образа, создание томов).
6.  **Starting** — запуск контейнера Docker.
7.  **Running** — контейнер запущен и работает.
8.  **Completed** — задача успешно завершена.
9.  **Failed** — задача завершилась с ошибкой.
10. **Shutdown** — плановая остановка задачи менеджером.
11. **Rejected** — рабочий узел отклонил задачу.
12. **Orphaned** — узел потерял связь с кластером, судьба задачи неизвестна.
13. **Remove** — задача помечена на удаление.

### Планирование и размещение (Scheduling)

Swarm использует систему фильтров и стратегий для выбора узла:
- **Constraints (Ограничения):** жесткие правила, например: `node.role == worker` или `node.labels.storage == ssd`.
- **Preferences (Предпочтения):** мягкие правила распределения (например, `spread=node.labels.zone` для равномерного распределения по зонам доступности).
- **Resource Limits & Reservations:**
  - **Limits:** максимально допустимые ресурсы для контейнера (дросселирование при превышении).
  - **Reservations:** гарантированные ресурсы, которые Swarm резервирует на узле при планировании.

### Сетевая модель и балансировка

- **Overlay networks:** виртуальные сети уровня L2 между хостами. Поддерживают IPv6 (v27+) и mTLS-шифрование трафика.
- **Endpoint Mode:**
  - **VIP (Virtual IP):** балансировка трафика через единый IP и IPVS (по умолчанию).
  - **DNSRR (DNS Round-Robin):** возвращает список IP всех реплик, клиент сам выполняет балансировку.
Подробности в **[swarm_networking.md](./swarm_networking.md)**.

### Стратегии обновления и отката

Конфигурация обновления (`update_config`) и отката (`rollback_config`):
- **Parallelism** — количество реплик, обновляемых одновременно.
- **Delay** — задержка между обновлением групп реплик.
- **Failure Action** — действие при сбое (`pause`, `continue`, `rollback`).
- **Order** — порядок: `start-first` (запуск новой перед стопом старой) или `stop-first`.
- **Monitor** — период наблюдения за новой репликой после старта для подтверждения ее здоровья.
- **Max Failure Ratio** — допустимый процент ошибок при обновлении.

### Отказоустойчивость и безопасность

- **Reconciliation Loop:** непрерывный процесс приведения кластера к желаемому состоянию.
- **Health Checks:** использование инструкции `HEALTHCHECK` для мониторинга работоспособности приложения. Параметры: `interval`, `timeout`, `retries`, `start_period`.
- **Безопасность mTLS:**
  - Автоматический Certificate Authority (CA).
  - Автоматическая ротация сертификатов (по умолчанию каждые 90 дней).
  - Токены присоединения (Join Tokens) для новых узлов.

## Практические сценарии

### Отказоустойчивость при сбое лидера

1. Лидер падает → фолловеры замечают отсутствие heartbeats.
2. Инициируются выборы → кворум менеджеров выбирает нового лидера.
3. Новый лидер восстанавливает состояние из лога Raft и продолжает управление.

### Масштабирование сервиса

```bash
# Масштабирование до 10 реплик
docker service scale web=10
# → web scaled to 10
# → overall progress: 10 out of 10 tasks

# Просмотр распределения
docker service ps web
# → ID            NAME      IMAGE          NODE      DESIRED STATE   CURRENT STATE
# → 8k3j1n...     web.1     nginx:latest   node-1    Running         Running 10 minutes ago
```

### Управление узлом (Draining)

```bash
# Вывод узла из обслуживания
docker node update --availability drain worker-1
# → worker-1
# Все задачи будут перенесены на другие узлы.
```

## Дополнительная информация

### Лимиты и масштабируемость

- **Рекомендованный размер кластера:** 50–100 узлов (баланс производительности Raft и управления).
- **Теоретический максимум:** до 2000 узлов и 5000–10000 сервисов.
- **Ограничения Raft:** не рекомендуется более 7 менеджеров из-за накладных расходов на консенсус.
- Для сверхкрупных или сверхсложных инсталляций (сложные зависимости, State-management) рекомендуется переход на Kubernetes.
