# Docker Swarm: Основные концепции

## Определения

**Узел (Node)** — физическая или виртуальная машина с Docker Engine, являющаяся частью Swarm-кластера. Узлы делятся на **менеджеров** и **рабочих**.

**Сервис (Service)** — декларативное описание задачи для выполнения в кластере. Определяет Docker-образ, количество реплик, сетевые настройки, политики обновления и другие параметры.

**Задача (Task)** — атомарная единица работы в Swarm, представляющая один Docker-контейнер. Менеджер назначает задачи на рабочие узлы и контролирует их выполнение.

**Routing Mesh** — встроенный механизм балансировки нагрузки, распределяющий входящие запросы между репликами сервиса. Позволяет обратиться к сервису по опубликованному порту на *любом* узле кластера.

**Service Discovery** — автоматическое обнаружение сервисов через встроенный DNS. Контейнеры обращаются друг к другу по именам сервисов без знания IP-адресов.

## Базовые концепции

### Архитектура кластера

#### Менеджеры (Manager Nodes)

Менеджеры отвечают за оркестрацию и управление кластером:

- **Поддержание желаемого состояния** — сравнение фактического состояния с декларативной конфигурацией и исправление расхождений
- **Планирование задач (Scheduling)** — распределение задач по рабочим узлам с учетом ограничений (constraints), привязок (affinities) и доступных ресурсов
- **Обработка API-запросов** — прием команд от пользователя и координация их выполнения
- **Консенсус Raft** — поддержание согласованного состояния между менеджерами через алгоритм консенсуса

**Требования к кворуму:**
- Рекомендуется **нечетное количество** менеджеров (3 или 5)
- Кластер работает при доступности **большинства** (кворума)
- При потере кворума невозможно вносить изменения в состояние кластера

#### Рабочие узлы (Worker Nodes)

Рабочие узлы выполняют задачи:

- **Запуск контейнеров** — создание и остановка контейнеров по инструкциям менеджера
- **Отчетность о состоянии** — отправка информации о статусе задач и доступных ресурсах
- **Выполнение health checks** — проверка работоспособности контейнеров

Рабочие узлы **не хранят состояние кластера** и не участвуют в консенсусе Raft.

### Сетевая модель

Все узлы общаются через зашифрованный **TLS-канал**. Сетевая архитектура включает:

- **Overlay-сети** — виртуальные сети (Layer 2), соединяющие контейнеры на разных узлах
- **Ingress-сеть** — специальная overlay-сеть для входящего трафика (основа Routing Mesh)
- **docker_gwbridge** — мост между overlay-сетями и физической сетью хоста

Подробнее в **[swarm_networking.md](./swarm_networking.md)**.

### Планировщик (Scheduler)

Планировщик определяет, на каком узле запустить задачу:

- **Распределение ресурсов** — учет CPU, памяти, дискового пространства
- **Ограничения (Constraints)** — фильтрация узлов по меткам, ОС, драйверам
- **Привязки (Affinities)** — размещение задач рядом с другими задачами или данными
- **Распределение по узлам** — равномерное распределение реплик для отказоустойчивости

### Механизмы отказоустойчивости

#### Reconciliation Loop

Менеджер постоянно сравнивает желаемое состояние с фактическим:

1. Если реплика упала — создается новая на другом узле
2. Если узел стал недоступен — его задачи перераспределяются
3. Если сервис обновлен — применяется rolling update

#### Health Checks

Swarm поддерживает проверки состояния:

- **Container health checks** — через Dockerfile `HEALTHCHECK`
- **HTTP health checks** — проверка HTTP-эндпоинтов
- **TCP health checks** — проверка TCP-портов

Нездоровые задачи автоматически заменяются.

## Практические сценарии

### Отказоустойчивость менеджера

При сбое лидера-менеджера:

1. Оставшиеся менеджеры через **Raft** выбирают нового лидера
2. Сервисы с отказавшего узла перераспределяются на доступные узлы
3. После восстановления узел присоединяется как последователь (не лидер)

**Время восстановления:** Обычно 10–30 секунд для выбора лидера, 1–5 минут для перераспределения задач.

### Масштабирование сервиса

```sh
# Увеличить количество реплик
docker service scale my-service=10

# Проверить распределение задач
docker service ps my-service
```

Swarm автоматически распределит реплики по узлам с учетом доступных ресурсов.

### Дренаж узла (Draining)

Для планового обслуживания узла:

```sh
# Пометить узел как недоступный для новых задач
docker node update --availability drain <NODE-ID>

# Дождаться завершения задач
docker node ps <NODE-ID>

# После обслуживания вернуть узел
docker node update --availability active <NODE-ID>
```

Задачи с drained-узла автоматически перемещаются на другие узлы.

## Дополнительная информация

### Управление ролями узлов

```sh
# Повысить рабочий до менеджера
docker node promote <NODE-ID>

# Понизить менеджера до рабочего
docker node demote <NODE-ID>
```

**Важно:** Понижение активного менеджера может временно повлиять на кворум.

### Лимиты и ограничения

| Параметр | Значение |
|---|---|
| Максимум узлов | ~1000 |
| Максимум сервисов | ~5000 |
| Максимум реплик на сервис | ~1000 |
| Рекомендуемый размер кластера | до 50 узлов |

Для крупных инсталляций рассмотрите Kubernetes или Nomad — сравнение в **[../Nomad/definitions_and_concepts.md](../Nomad/definitions_and_concepts.md)**.
