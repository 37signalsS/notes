# CI/CD в Docker Swarm: Лучшие практики

## Определения

- **Лучшие практики (Best Practices):** Проверенные методы и подходы, обеспечивающие безопасность, надежность и эффективность процессов CI/CD в Docker Swarm.
- **Неизменяемая инфраструктура (Immutable Infrastructure):** Подход, при котором компоненты инфраструктуры заменяются новыми версиями вместо внесения изменений в работающие системы.
- **[GitOps](../../GitOps/GitOps_overview.md):** Методология управления инфраструктурой и приложениями, при которой Git является единственным источником истины.
- **[Принцип минимальных привилегий (Least Privilege)](../../CI-CD/DevSecOps/secrets_management.md#1-принцип-минимальных-привилегий-least-privilege):** Стратегия безопасности, ограничивающая права доступа только необходимым минимумом для выполнения конкретной задачи.

## Базовые концепции

### Принципы безопасного и стабильного CI/CD

1. **Изоляция сборки (Build Isolation):** Использование инструментов типа **[Kaniko](../../Docker/Dockerfile/dockerfile_kaniko.md)** или **Buildah** для сборки образов без доступа к привилегированному Docker-сокету (`/var/run/docker.sock`) на раннерах. Это исключает риск компрометации хоста CI-системы.
2. **Многоуровневое управление секретами:** Разделение секретов на "секреты доставки" (в переменных CI/CD для авторизации в Registry и Swarm API) и "секреты выполнения" (**[Swarm Secrets](../swarm_secrets_configs.md)** для приложения внутри кластера).
3. **Декларативность и идемпотентность:** Описание всей инфраструктуры и параметров запуска в Compose-файлах. Запрет на использование `docker service update` вручную. Любое изменение конфигурации должно проходить через Git и автоматизированный пайплайн.
4. **Строгое версионирование:** Полный отказ от тега `latest` в продуктивных средах. Использование хеша коммита (`CI_COMMIT_SHA`) или семантического версионирования гарантирует повторяемость деплоя и возможность мгновенного отката.
5. **Сборка один раз (Build Once, Deploy Many):** Артефакт (образ) собирается на этапе Build и без изменений проходит через все окружения (Dev → Staging → Prod). Различия между средами реализуются через переменные окружения и секреты.

### Архитектура безопасного конвейера доставки

Рекомендуемая схема доставки:

1. **Сборка:** В изолированной среде (Kaniko) с тегированием на основе хеша коммита.
2. **Публикация:** В приватный реестр (Registry).
3. **Аутентификация:** В Swarm через **[mTLS](./swarm_setup.md)** (порт 2376) с использованием клиентских сертификатов, выдаваемых CI-раннеру.
4. **Развертывание:** Выполнение `docker stack deploy` с обязательным флагом `--with-registry-auth` для безопасной передачи прав доступа к образам на все рабочие узлы (worker nodes).

## Практические сценарии

### Сценарий 1: Управление версиями и динамические переменные

Использование фиксированных тегов гарантирует, что на всех узлах кластера будет запущена идентичная версия кода.

```yaml
services:
  app:
    # Переменная передается из CI-пайплайна
    image: ${CI_REGISTRY_IMAGE}:${CI_COMMIT_SHA}
```

### Сценарий 2: Оптимизация ресурсов (Resource Limits)

Для предотвращения деградации кластера из-за одного сервиса необходимо явно указывать лимиты.

```yaml
services:
  web:
    deploy:
      resources:
        limits:
          cpus: '0.50'     # Лимит использования CPU
          memory: 512M      # Жесткий лимит памяти (OOM при превышении)
        reservations:
          cpus: '0.10'
          memory: 128M      # Гарантированное резервирование ресурсов
```

### Сценарий 3: Безопасный деплой через Registry Auth

Для того чтобы воркеры могли скачать образ из приватного реестра, команда деплоя должна включать флаг передачи токена авторизации.

```bash
# Выполнение деплоя в пайплайне
docker stack deploy -c docker-compose.yml my-app --with-registry-auth
```
# → Результат: Менеджер шифрует учетные данные и безопасно передает их на целевые узлы

### Сценарий 4: Настройка Rolling Updates и Health Checks

Обеспечение Zero Downtime при обновлении требует правильной последовательности запуска (`order`).

```yaml
deploy:
  update_config:
    parallelism: 1         # Количество одновременно обновляемых реплик
    delay: 10s             # Пауза между обновлением групп реплик
    order: start-first     # Сначала запустить новый контейнер, затем остановить старый
    failure_action: rollback # Автоматический откат при неудаче
    monitor: 30s           # Время наблюдения за стабильностью после запуска
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
  interval: 15s
  timeout: 5s
  retries: 3
  start_period: 60s        # Ожидание прогрева приложения перед проверками
```

Подробные рекомендации по настройке — в **[Жизненный цикл приложения в Swarm](./app_lifecycle.md)**.

### Сценарий 5: Логирование и автоматическая очистка системы

Для предотвращения переполнения диска логами и старыми образами на узлах:

1. **Ротация логов:** Настройка драйвера в `docker-compose.yml` или глобально в `daemon.json`.
2. **Очистка данных:** Использование фильтров по времени для удаления неиспользуемых слоев.

```bash
# Удаление всех неиспользуемых образов старше 7 дней
docker image prune -a --force --filter "until=168h"
```

## Дополнительная информация

### Контрольный список безопасности и стабильности (Checklist)

- [ ] Сборка выполняется без привилегированного доступа к Docker-сокету.
- [ ] Тег `latest` не используется в продуктовых конфигурациях.
- [ ] Настроены `limits` и `reservations` для всех сервисов.
- [ ] Используется флаг `--with-registry-auth` в командах деплоя.
- [ ] Включены Health Checks и настроен `start_period`.
- [ ] Настроен автоматический откат (`rollback_config`).
- [ ] Секреты времени выполнения передаются только через `docker secret`.
- [ ] Настроены `placement constraints` для критических нагрузок (например, БД на SSD-узлах).

### Типовые ошибки

| Ошибка | Причина | Способ исправления |
|:---|:---|:---|
| `No such image` на воркерах | Отсутствует флаг `--with-registry-auth` | Добавить флаг при деплое стека |
| Сервис постоянно перезагружается | Слишком короткий `start_period` | Увеличить время ожидания прогрева приложения |
| Обновление не начинается | В кластере нет ресурсов для `start-first` | Проверить лимиты или добавить узлы |
| Утечка секретов в образе | Секреты переданы через `ARG` или `ENV` при сборке | Использовать Swarm Secrets или переменные времени выполнения |
