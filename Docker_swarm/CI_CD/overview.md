# CI/CD в Docker Swarm: Обзор и архитектурные концепции

## Определения

- **[Docker Swarm](../docker_swarm_overview.md):** Нативный режим оркестрации Docker Engine, объединяющий группу хостов в виртуальный кластер. В контексте CI/CD обеспечивает декларативное управление состоянием сервисов через Stack API.
- **[GitLab CI/CD](../../CI-CD/GitLab_CI/Concepts/gitlab_ci_basics.md):** Платформа автоматизации, использующая YAML-конфигурации (`.gitlab-ci.yml`) для сборки, тестирования и деплоя. Часто выступает в роли управляющего узла для Swarm через удаленное API.
- **[GitHub Actions](../../Github_CI/Core_Concept.md):** Система автоматизации на базе событий (workflows). Позволяет использовать Self-hosted раннеры внутри Swarm-кластера для прямого доступа к Docker-сокету или Remote API.
- **[Traefik](../../WebServers/Traefik/traefik_overview.md):** Edge-прокси с нативной поддержкой Docker Swarm. Реализует концепцию "Service Discovery как часть CI/CD", автоматически настраивая маршрутизацию на основе меток (labels) в Stack-файлах.
- **[mTLS (mutual TLS)](../../Networking/Protocols/tls.md#сценарий-2-взаимная-аутентификация-mtls):** Протокол взаимной аутентификации, являющийся стандартом де-факто для безопасного подключения CI-системы к порту 2376 Swarm-менеджера.
- **[Жизненный цикл приложения (App Lifecycle)](./app_lifecycle.md):** Совокупность стратегий развертывания (Rolling Update), проверок готовности (Health Checks) и автоматизированного реагирования на сбои (Rollback).
- **[Секреты и конфигурации (Secrets & Configs)](../swarm_secrets_configs.md):** Объекты Swarm первого класса для безопасной доставки чувствительных данных (пароли, TLS-сертификаты) и статических файлов настроек в контейнеры без их включения в образ.

## Базовые концепции

### Архитектура конвейера доставки

Современный CI/CD для Docker Swarm базируется на четырех "столпах" надежности и безопасности:

1. **Безопасное удаленное управление (Remote API):**
   - Прямой доступ к `/var/run/docker.sock` считается небезопасным (риск Privilege Escalation).
   - Рекомендуется использование TCP-порта 2376 с **mTLS**. CI-раннер получает клиентский сертификат, который дает право на выполнение команд в кластере.
2. **Инфраструктура как код (IaC) и декларативность:**
   - Состояние кластера описывается в Stack-файлах (`docker-compose.yml` версии 3.x).
   - CI/CD пайплайн не "запускает контейнеры", а "приводит состояние стека к описанному в Git".
3. **Динамический Ingress и Service Discovery:**
   - Использование Traefik или Flow Proxy позволяет избежать ручной правки конфигов Nginx/HAProxy.
   - Описание маршрутизации хранится рядом с кодом приложения в виде меток `deploy.labels`.
4. **Изоляция окружений через контексты:**
   - Инструмент `docker context` позволяет абстрагировать адрес кластера и сертификаты.
   - Команда `docker stack deploy` в пайплайне остается идентичной для dev/stage/prod, меняется только активный контекст.

### Обеспечение надежности и наблюдаемости

Развертывание в Swarm требует интеграции с системами мониторинга для подтверждения успеха деплоя:

- **Rolling Updates:** Настройка `parallelism` и `delay` позволяет обновлять сервис постепенно, минимизируя влияние на пользователей.
- **Health Checks:** CI-пайплайн должен дожидаться прохождения проверок здоровья (`docker service ps` → `running`), прежде чем считать этап деплоя успешным.
- **Централизованное логирование:** Использование драйверов `gelf`, `loki` или `fluentd` для сбора логов со всех узлов кластера, что критично для отладки неудачных деплоев.

## Практические сценарии

### Сценарий 1: Защита канала управления кластером

Организация безопасного взаимодействия CI-системы с менеджером:

1. **Генерация сертификатов:** Создание CA, серверного сертификата для менеджера и клиентского для CI-раннера.
2. **Настройка демона:** Запуск Docker с флагами `--tlsverify`, `--tlscacert`, `--tlscert`, `--tlskey` на порту 2376.
3. **Интеграция с CI:** Передача сертификатов через защищенные переменные (Variables/Secrets).
4. **Реализация:** См. **[swarm_setup.md](./swarm_setup.md)**.

### Сценарий 2: Управление базовой инфраструктурой

Развертывание общих сервисов, необходимых для работы приложений:

1. **Инфраструктурный стек:** Отдельный репозиторий для Traefik, Portainer, систем мониторинга (Prometheus/Grafana) и логирования.
2. **Общие сети:** Создание `overlay` сетей с флагом `--attachable` для связи между стеками.
3. **Автоматизация:** Использование выделенного пайплайна для обновления системных компонентов без риска затронуть бизнес-логику.
4. **Детали:** См. **[infra_deployment.md](./infra_deployment.md)**.

### Сценарий 3: Аутентификация в приватных реестрах

Обеспечение доступа узлов кластера к образам:

- **Проблема:** При деплое через Remote API узлы (Workers) должны иметь права на скачивание образа.
- **Решение:** Использование флага `--with-registry-auth`. CI-система передает учетные данные из своего `.docker/config.json` менеджерам, которые распределяют их по кластеру.
- **Безопасность:** Использование временных Deploy Tokens вместо личных паролей разработчиков.

### Сценарий 4: Маршрутизация и SSL через Traefik

Пример описания сервиса в Stack-файле для автоматической публикации:

```yaml
services:
  webapp:
    image: registry.example.com/my-app:${CI_COMMIT_SHA}
    networks:
      - public_net
    deploy:
      replicas: 3
      labels:
        - "traefik.enable=true"
        - "traefik.http.routers.webapp.rule=Host(`webapp.example.com`)"
        - "traefik.http.routers.webapp.entrypoints=websecure"
        - "traefik.http.routers.webapp.tls.certresolver=le" # Авто-SSL через Let's Encrypt
        - "traefik.http.services.webapp.loadbalancer.server.port=80"
```

## Справочная информация

### Сравнение подходов к CI/CD

| Характеристика | Docker Swarm | Kubernetes (K8s) |
|:---|:---|:---|
| **Порог вхождения** | Низкий (стандартный Compose) | Высокий (Manifests, Helm, Kustomize) |
| **Сложность CI-пайплайна** | Минимальная (`stack deploy`) | Средняя/Высокая (управление Tiller/GitOps) |
| **Нативная безопасность** | mTLS, Secrets API | RBAC, Network Policies, KMS |
| **Масштабируемость** | Достаточная для 90% проектов | Неограниченная |

### Рекомендации по эксплуатации

- **Версионирование:** Категорический отказ от `latest`. Использование `${CI_COMMIT_SHA}` или `${CI_TAG}` обеспечивает атомарность и возможность точного отката.
- **Автоматическая очистка:** Настройка `docker system prune` на всех узлах кластера (через `systemd.timer` или Cron) для предотвращения переполнения диска старыми слоями.
- **Мониторинг ресурсов:** Обязательное указание `resources.limits` и `resources.reservations` в Stack-файлах для предсказуемого планирования задач.
- **Проверка конфигурации:** Использование `docker stack config` перед деплоем для валидации итогового YAML-файла с учетом подставленных переменных окружения.
