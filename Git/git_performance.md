# Git: Оптимизация производительности

При работе с большими репозиториями или в средах с ограниченной пропускной способностью (например, в CI/CD пайплайнах) производительность операций Git, особенно `git clone`, становится критически важной. Git предоставляет несколько механизмов для оптимизации.

## Поверхностное клонирование (Shallow Clone)

Поверхностное клонирование (`shallow clone`) позволяет загрузить только часть истории коммитов, а не весь репозиторий целиком. Это значительно сокращает время клонирования и объем передаваемых данных.

**Основная команда:**

```bash
# Клонировать только последний коммит
git clone --depth 1 <url_репозитория>
```

-   `--depth <N>`: Указывает, сколько последних коммитов нужно загрузить. `--depth 1` — самый распространенный вариант для CI/CD, где для сборки и тестирования обычно нужна только последняя версия кода.

**Проблема:**

У поверхностной копии отсутствует полная история, что делает невозможными некоторые операции, требующие анализа истории коммитов (например, `git blame` на старых строках или `git describe`).

**"Разворачивание" поверхностной копии:**

Если вам понадобилась полная история, вы можете "развернуть" репозиторий, загрузив недостающие коммиты:

```bash
git fetch --unshallow
```

## Клонирование без блобов (Blobless Clone) и без деревьев (Treeless Clone)

Это более продвинутые техники, которые стали возможны благодаря механизму "частичного клонирования" (`partial clone`). Они позволяют клонировать репозиторий без содержимого файлов (blobs) или без информации о структуре директорий (trees), загружая эти объекты по мере необходимости.

-   **Treeless Clone:** Клонирует историю коммитов и корневое дерево, но не вложенные деревья. Объекты деревьев и файлов загружаются при `checkout`.

    ```bash
    git clone --filter=tree:0 <url_репозитория>
    ```

-   **Blobless Clone:** Клонирует всю историю коммитов и деревья, но не сами файлы (blobs). Файлы загружаются только тогда, когда к ним происходит обращение (например, при `checkout`).

    ```bash
    git clone --filter=blob:none <url_репозитория>
    ```

Эти методы полезны для очень больших монорепозиториев, когда для конкретной задачи нужна лишь малая часть файлов.

## Использование `git bundle`

Для передачи репозиториев в условиях плохой или отсутствующей сети можно использовать `git bundle`. Это позволяет упаковать объекты Git в один файл, перенести его и распаковать на другой машине. Подробнее см. в [руководстве по устранению неполадок](./git_troubleshooting.md).

## Использование Git LFS для больших бинарных файлов

Если ваш репозиторий содержит большие бинарные файлы (графика, видео, архивы), их хранение напрямую в Git неэффективно. Используйте **Git LFS (Large File Storage)** для хранения таких файлов на отдельном сервере, в то время как в Git будут храниться только легковесные указатели на них. Подробнее см. в [руководстве по Git LFS](./git_lfs.md).
