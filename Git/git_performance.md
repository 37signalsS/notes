# Git: Оптимизация производительности

## Определения

**Оптимизация производительности Git** — комплекс конфигурационных настроек, инструментов и стратегий, направленных на минимизацию времени выполнения операций (clone, fetch, status, log) в репозиториях сверхбольшого объема (монорепозитории) или при работе в условиях ограниченной пропускной способности сети.

**Scalar** — специализированная надстройка (CLI-инструмент), разработанная Microsoft и включенная в состав Git (с версии 2.38). Она автоматически применяет набор «золотых стандартов» конфигурации для работы с огромными репозиториями.

**Multi-pack-index (MIDX)** — сводный индексный файл, объединяющий информацию о расположении объектов во всех существующих pack-файлах. Устраняет необходимость поиска объекта в сотнях отдельных `.idx` файлов.

**Bundle URIs** — механизм ускорения клонирования, позволяющий Git скачивать предварительно подготовленные пакеты данных (bundles) с быстрых CDN перед основным взаимодействием с Git-сервером.

**FSMonitor (File System Monitor)** — встроенный демон или интеграция с ОС (Watchman), отслеживающая изменения файлов. Позволяет `git status` избегать полного сканирования рабочего дерева.

**Sparse-Checkout (Разреженное извлечение)** — механизм, позволяющий «материализовать» на диске только подмножество файлов репозитория, необходимых для конкретной задачи, при сохранении доступа ко всей истории.

## Основные концепции

### Проблемы масштабируемости
С ростом репозитория производительность падает по трем осям:
1.  **Сетевой трафик:** Передача гигабайт истории при `clone` и `fetch`.
2.  **Объем индекса:** Бинарный файл `.git/index` становится слишком тяжелым для чтения/записи.
3.  **Дисковый I/O:** `git status` вынужден проверять `lstat()` для каждого из 100k+ файлов.

### Сводная таблица методов оптимизации

| Метод | Что ускоряет | Целевая область |
| :--- | :--- | :--- |
| **Scalar** | Комплексная скорость | Монорепозитории (>100k файлов). |
| **MIDX & Bitmaps** | `fetch`, `push`, `gc` | Оптимизация поиска объектов. |
| **Commit-Graph** | `log`, `graph`, `merge` | Ускорение обхода истории. |
| **Sparse-Checkout (Cone Mode)** | `status`, `checkout`, `add` | Уменьшение рабочего дерева. |
| **Partial Clone** | `clone` (трафик) | Исключение ненужных blob-объектов. |
| **Bundle URIs** | `clone` (время) | Использование CDN для «разогрева» репозитория. |
| **FSMonitor** | `status` | Устранение сканирования диска. |
| **Reftable** | Работа со ссылками | Репозитории с десятками тысяч веток. |

## Практические сценарии

### Сценарий 1: Использование Scalar для монорепозиториев
Scalar — это самый простой способ включить все оптимизации одной командой.

```bash
# Клонирование с автоматической настройкой оптимизаций
scalar clone <url>

# Регистрация существующего репозитория в Scalar (включает фоновое обслуживание)
cd my-big-repo
scalar register
```
*Scalar автоматически включает: partial clone, sparse-checkout (cone mode), fsmonitor, commit-graph и background maintenance.*

### Сценарий 2: Разреженное извлечение (Sparse-Checkout) в режиме Cone
Режим **Cone** значительно быстрее классического, так как использует хэш-таблицы для сопоставления путей вместо регулярных выражений.

```bash
# Инициализация в режиме Cone
git sparse-checkout init --cone

# Выбор необходимых директорий
git sparse-checkout set src/backend docs/

# Включение разреженного индекса (Sparse Index) для еще большего ускорения
git config core.sparseIndex true
```

### Сценарий 3: Ускорение клонирования через Bundle URIs
Позволяет скачивать основные данные с CDN, снижая нагрузку на основной Git-сервер.

```bash
# Клонирование с использованием внешнего бандла
git clone --bundle-uri=https://cdn.example.com/main.bundle https://github.com/user/repo.git

# Включение автоматического использования бандлов, если сервер их рекламирует
git config --global transfer.bundleURI true
```

### Сценарий 4: Тонкая настройка Staging Area и статуса
Если Scalar не используется, настройки можно применить точечно:

```bash
# Включить встроенный монитор файловой системы (Windows/macOS/Linux)
git config core.fsmonitor true

# Включить кэширование неотслеживаемых файлов
git config core.untrackedCache true

# Использовать версию индекса 4 (сжатие путей, экономит место и время чтения)
git config index.version 4
```

### Сценарий 5: Оптимизация в CI/CD
Для минимизации времени сборки используйте «ленивую» загрузку.

```bash
# Blobless клон: скачивает историю коммитов, но не файлы. 
# Файлы скачиваются только при checkout конкретного коммита.
git clone --filter=blob:none <url>

# Treeless клон: скачивает только структуру дерева текущего коммита.
# Максимально быстрый клон для простой проверки кода.
git clone --filter=tree:0 <url>
```

## Дополнительная информация

### Рекомендации по обслуживанию
- **Фоновое обслуживание:** Используйте `git maintenance start`, чтобы Git обновлял `commit-graph` и упаковывал объекты в фоновом режиме, не прерывая работу.
- **Мониторинг размера:** Используйте утилиту `git-sizer` для анализа проблемных мест репозитория (слишком большие деревья, глубокая история).
