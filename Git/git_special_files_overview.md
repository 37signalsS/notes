# Обзор специальных файлов конфигурации Git

## Определения

**Специальные файлы Git (Git Special Files)** — зарезервированные конфигурационные файлы, которые хранятся в рабочей директории репозитория и отслеживаются системой контроля версий. В отличие от локальных настроек в директории `.git/`, эти файлы распространяются между всеми участниками проекта при клонировании, обеспечивая единую среду разработки.

**`.gitignore`** — список шаблонов путей к файлам и директориям, которые Git должен игнорировать (не предлагать к добавлению в индекс и не отслеживать изменения). Используется для исключения артефактов сборки, зависимостей, временных файлов и секретов.

**`.gitattributes`** — файл для определения атрибутов путей. Используется для управления окончаниями строк (CRLF ↔ LF), фильтрами (LFS, шифрование), драйверами слияния и языковой идентификацией (для GitHub/Linguist).

**`.gitmodules`** — конфигурация подмодулей (submodules). Содержит маппинг локальных путей к URL удаленных репозиториев и конкретным веткам.

**`.mailmap`** — механизм сопоставления имен и email-адресов авторов. Позволяет объединять историю одного человека под разными именами в отчетах `git shortlog` и `git blame`.

**`.git-blame-ignore-revs`** — список хэшей коммитов (обычно массовое переформатирование кода), которые следует игнорировать при выполнении команды `git blame`.

**`.lfsconfig`** — настройки поведения Git LFS (Large File Storage), такие как URL сервера хранения объектов, специфичные для проекта.

**`.gitmessage`** — файл-шаблон сообщения коммита, используемый для предварительного заполнения текстового редактора при выполнении команды `git commit`.

**`.editorconfig`** — конфигурационный файл для определения и поддержания единого стиля форматирования кода (отступы, окончания строк, кодировка) в различных редакторах и IDE.

**`.git/info/exclude`** — локальный список исключений, который не коммитится в общий репозиторий. Используется для индивидуальных настроек разработчика (аналог `.gitignore`, но не версионируется).

## Базовые концепции

### Иерархия и наследование настроек

Git применяет конфигурацию, анализируя файлы в порядке возрастания приоритета (более специфичные переопределяют более общие):

1.  **Системный/Глобальный уровни:** Файлы вне репозитория (например, `~/.config/git/ignore`, `~/.config/git/attributes`).
2.  **Файлы в корне репозитория:** Основные правила для всего проекта (`.gitignore`, `.gitattributes`).
3.  **Файлы в поддиректориях:** Переопределяют правила для конкретной ветки файловой системы (актуально для `.gitignore` и `.gitattributes`).
4.  **Локальные исключения (`.git/info/exclude`):** Индивидуальные настройки разработчика, которые не коммитятся в общий репозиторий.

**Принцип "последнее найденное правило побеждает":** Если для одного пути задано несколько правил в разных файлах, Git использует последнее найденное правило. Это позволяет переопределять общие правила в поддиректориях.

### Сравнение файлов и их назначение

| Файл | Версионируется | Локальный | Назначение |
| :--- | :--- | :--- | :--- |
| `.gitignore` | Да | Нет | Исключение файлов из отслеживания для всей команды |
| `.git/info/exclude` | Нет | Да | Локальные исключения для конкретного разработчика |
| `.gitattributes` | Да | Нет | Единые правила обработки файлов для всей команды |
| `.git/info/attributes` | Нет | Да | Локальные правила обработки файлов |
| `.mailmap` | Да | Нет | Канонизация имен авторов для всей команды |
| `.git-blame-ignore-revs` | Да | Нет | Игнорирование коммитов в blame для всей команды |

### Принцип "Configuration as Code"

Специальные файлы позволяют версионировать инфраструктурные настройки проекта. Это гарантирует, что:
-   Бинарные файлы всегда обрабатываются через LFS (`.gitattributes` + `.lfsconfig`).
-   Окончания строк (`LF` vs `CRLF`) не вызывают конфликтов в кроссплатформенных командах (`.gitattributes`).
-   Сенситивные данные (логи, `.env`) не попадут в публичный доступ по ошибке (`.gitignore`).
-   История коммитов содержит корректные имена авторов (`.mailmap`).
-   Стиль кода единообразен во всей команде (`.editorconfig`).
-   Шаблоны коммитов соответствуют стандартам (`.gitmessage`).

## Практические сценарии

### Сценарий 1: Проверка действующих исключений

Если файл неожиданно игнорируется или, наоборот, не попадает под действие `.gitignore`.

```bash
# Проверить, какое правило и в каком файле игнорирует конкретный путь
git check-ignore -v path/to/my/file.tmp
# → .gitignore:15:*.tmp  path/to/my/file.tmp

# Проверить несколько файлов одновременно
git check-ignore -v src/*.log config/*.tmp
# → .gitignore:10:*.log  src/app.log

# Проверить все игнорируемые файлы в директории
git check-ignore *
```

**Примечание:** Подробные инструкции по отладке правил игнорирования описаны в [Игнорирование файлов в Git](./git_ignore.md#сценарий-1-отладка-невидимых-правил).

### Сценарий 2: Группировка авторов в большом проекте

Если в истории накопилось множество email-адресов одного и того же разработчика.

```bash
# 1. Создать .mailmap
echo "Proper Name <proper@email.com> <old@email.com>" > .mailmap

# 2. Проверить результат
git shortlog -se
```

**Примечание:** Подробные инструкции по маппингу авторов описаны в [Маппинг авторов в Git](./git_mailmap.md).

### Сценарий 3: Игнорирование коммитов форматирования в blame

Позволяет исключить «шумные» коммиты (автоформатирование, рефакторинг) из вывода `git blame`, сохраняя авторство за создателями логики.

```bash
# 1. Создать файл
touch .git-blame-ignore-revs

# 2. Настроить Git для использования этого файла
git config blame.ignoreRevsFile .git-blame-ignore-revs

# 3. Добавить коммит с форматированием
COMMIT_HASH=$(git rev-parse HEAD)
echo "# Mass reformatting with Prettier (2024-05-20)" >> .git-blame-ignore-revs
echo $COMMIT_HASH >> .git-blame-ignore-revs
```

**Примечание:** Подробные инструкции по настройке репозитория, добавлению коммитов и интеграции с IDE доступны в документе: **[Игнорирование коммитов в Git Blame](./git_blame_ignore.md)**.

### Сценарий 4: Настройка локальных исключений

Если разработчику нужны личные исключения, которые не должны влиять на других участников.

```bash
# Добавить правило в .git/info/exclude
echo "*.local" >> .git/info/exclude

# Проверить, что файл игнорируется
git check-ignore -v config/local.yml
# → .git/info/exclude:1:*.local  config/local.yml
```

**Примечание:** Файл `.git/info/exclude` не коммитится и не распространяется между разработчиками. Подробнее — в [Игнорирование файлов в Git](./git_ignore.md#сценарий-5-использование-git_common_dirinfoexclude).

### Сценарий 5: Синхронизация .gitattributes и .editorconfig

Для предотвращения конфликтов окончаний строк (когда Git меняет `LF` на `CRLF` при чекауте, а EditorConfig требует `LF` при сохранении).

```editorconfig
# .editorconfig
[*]
end_of_line = lf
```

```gitattributes
# .gitattributes
* text=auto eol=lf
```

**Примечание:** Подробное описание взаимодействия между EditorConfig и .gitattributes описано в [Атрибуты Git](./git_attributes.md#сценарий-10-синхронизация-с-editorconfig).

### Сценарий 6: Настройка шаблона коммитов

Для использования стандартного шаблона Conventional Commits во всей команде.

```bash
# Настроить глобально
git config --global commit.template ~/.gitmessage

# Или локально для репозитория
git config commit.template .gitmessage
```

**Примечание:** Подробные инструкции по созданию и использованию шаблонов коммитов описаны в [Git Commit Template](./git_commit_template.md).

## Типичные ошибки при работе с конвенциями

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| Файл не игнорируется | Файл уже отслеживается Git | Выполните `git rm --cached <file>` |
| Правило `!` не работает | Родительская директория уже проигнорирована | Исключите родительскую директорию, затем включите нужный путь |
| `.gitattributes` не применяется | Атрибуты изменились после добавления файлов в индекс | Выполните `git add --renormalize .` |
| `git blame` показывает автора форматирования | `blame.ignoreRevsFile` не установлен | `git config --local blame.ignoreRevsFile .git-blame-ignore-revs` |
| `.mailmap` не работает | Имя/email не совпадает с данными коммита | Проверьте точное написание через `git log --format="%aN <%aE>"` |
| `LF will be replaced by CRLF` | На Windows включен `core.autocrlf` без `.gitattributes` | Добавить `* text=auto` в `.gitattributes` |
| LFS-файл не загружается | Отсутствует `filter=lfs` в `.gitattributes` | Добавить `*.bin filter=lfs diff=lfs merge=lfs` |
| `.gitmessage` не отображается | `commit.template` не настроен | `git config commit.template .gitmessage` |

## Дополнительная информация

### Ограничения

- **Необязательность:** Большинство конвенций требуют установки дополнительных инструментов (gitlint, pre-commit) или ручной настройки разработчиком.
- **Разнообразие:** Разные команды могут использовать разные имена файлов (например, `.keep` вместо `.gitkeep`).
- **Версии Git:** Некоторые функции (например, документация `$GIT_COMMON_DIR/info/exclude` для worktrees) доступны только в Git 2.55+.
- **Платформы:** Поддержка `.mailmap` на GitHub/GitLab ограничена (см. [Маппинг авторов](./git_mailmap.md#особенности-инструментов)).

### Рекомендации по использованию

1. **Начните с `.gitignore`:** Создайте файл в начале проекта, используйте готовые шаблоны из [GitHub gitignore](https://github.com/github/gitignore).
2. **Настройте `.gitattributes`:** Для кроссплатформенных проектов обязателен параметр `* text=auto`.
3. **Используйте `.editorconfig`:** Обеспечьте единый стиль кода во всей команде.
4. **Ведите `.mailmap`:** Регулярно обновляйте файл для корректной статистики.
5. **Документируйте `.git-blame-ignore-revs`:** Комментируйте каждый игнорируемый коммит.
