# Git Stash — временное хранение изменений

## Определения

**Stash (git stash)** — механизм временного сохранения незавершённых изменений рабочего каталога и индекса в отдельном хранилище (стеке), позволяющий переключиться на другую ветку без создания «грязного» коммита.

**Физическая реализация:** Stash — это специальный вид коммита, который не принадлежит ни одной ветке. При выполнении `git stash` Git создаёт древовидную структуру из двух или трёх коммитов:
1.  **Коммит индекса (Index Commit):** Состояние Staging Area на момент сохранения.
2.  **Коммит рабочего дерева (Working Tree Commit):** Состояние отслеживаемых файлов в рабочей директории. Его родителем является коммит, на который указывал HEAD, а вторым родителем — коммит индекса.
3.  **Коммит сторонних файлов (Untracked Commit):** Создаётся только при использовании флага `-u` (untracked) или `-a` (all).

Все записи хранятся в `.git/refs/stash` и отслеживаются через рефлог `.git/logs/refs/stash`. Git не синхронизирует это хранилище с удалённым репозиторием, поэтому stash является сугубо локальным инструментом.

### Почему stash существует

Git не позволяет переключиться на другую ветку (`git switch` / `git checkout`), если есть незакоммиченные изменения, которые конфликтуют с состоянием целевой ветки.

| Подход | Проблема |
| :--- | :--- |
| **Создать временный коммит** | Засоряет историю «мусорными» коммитами, требует `reset` при возвращении. |
| **Просто переключиться** | Untracked файлы переносятся между ветками, а изменения в tracked файлах могут вызвать блокирующий конфликт. |
| **Принудительный checkout** | Полная потеря всех незакоммиченных изменений без возможности восстановления. |

Stash решает эти проблемы, изолируя изменения в «карман» и восстанавливая чистое состояние рабочего дерева.

## Базовые концепции

### Механика стека

Stash организован по принципу LIFO (Last In, First Out). Новая запись всегда получает индекс `stash@{0}`, сдвигая остальные вглубь стека.

```bash
# Сохранить изменения (рекомендуемый современный способ)
git stash push -m "Описание контекста"

# Список всех сохранённых состояний
git stash list
# → stash@{0}: On main: fix naming
# → stash@{1}: WIP on feature: add validation

# Применить изменения и удалить из стека
git stash pop stash@{0}

# Применить изменения, сохранив их в стеке
git stash apply stash@{1}
```

### Основные флаги и типы stash

| Флаг | Описание |
| :--- | :--- |
| `-u` / `--include-untracked` | Сохраняет новые, ещё не отслеживаемые файлы. |
| `-a` / `--all` | Сохраняет всё, включая файлы из `.gitignore`. |
| `-p` / `--patch` | Интерактивный режим: выбор конкретных фрагментов кода (hunks) для сохранения. |
| `-k` / `--keep-index` | Сохраняет изменения, но оставляет их в Staging Area (индексе). |
| `-S` / `--staged` | (Git 2.35+) Сохраняет только те изменения, что уже добавлены в индекс. |

### Управление и инспекция

```bash
# Просмотр изменений (diff) без применения
git stash show -p stash@{0}

# Просмотр списка файлов, включая новые (Git 2.31+)
git stash show --include-untracked stash@{0}

# Удалить конкретную запись
git stash drop stash@{0}

# Полная очистка хранилища
git stash clear
```

## Практические сценарии

### Сценарий 1: Срочный перенос контекста (Баг-фикс)

Работа над фичей прервана критическим багом в другой ветке.

```bash
# Сохраняем всё рабочее состояние
git stash -u -m "WIP: auth-module integration"

# Переходим на main и правим баг
git switch main
# ... правки ...
git commit -m "fix: memory leak in session"

# Возвращаемся и восстанавливаем состояние
git switch feature-auth
git stash pop
```

### Сценарий 2: Изоляция untracked файлов при переключении

По умолчанию Git переносит новые файлы между ветками. Это может привести к появлению отладочных логов или конфигов в «чистых» ветках.

```bash
# Файл debug_log.txt создан, но не добавлен в Git
git stash -u
git switch main  # Файл debug_log.txt исчез из рабочей директории
```

### Сценарий 3: Восстановление состояния индекса

По умолчанию `git stash pop` применяет изменения как unstaged. Если важно вернуть файлы именно в Staging Area, используйте флаг `--index`.

```bash
git stash pop --index
```

### Сценарий 4: Создание ветки из конфликтующего stash

Если с момента сохранения ветка сильно ушла вперёд, `pop` может вызвать сложные конфликты. Безопаснее создать новую ветку на основе того коммита, где был сделан stash.

```bash
# Создаёт ветку 'debug-fix', переключается на неё и применяет изменения
git stash branch debug-fix stash@{0}
```

### Сценарий 5: Ручное управление объектами (создание бекапа)

Для автоматизации или создания «невидимых» бекапов можно создавать объекты stash вручную.

```bash
# Создаёт объект коммита и возвращает его SHA (не меняет рабочее дерево)
SHA=$(git stash create)

# Сохраняет созданный коммит в стек под заданным именем
git stash store -m "Snapshot before rebase" $SHA
```

## Особенности и ограничения

- **Локальность:** Stash существует только в `.git/refs/stash`. Команда `git push` его не видит.
- **Глобальность:** Stash доступен из любой ветки репозитория, что позволяет переносить код между ветками без коммитов.
- **Срок жизни:** Данные не удаляются автоматически. Только `drop`, `clear` или агрессивный `git gc` (если на объекты нет ссылок).
- **Конфликты:** Если `stash pop` вызывает конфликт, запись **не удаляется** из стека автоматически, чтобы вы не потеряли данные при неудачном слиянии.

### Сравнение со смежными инструментами

| Критерий | git stash | git worktree |
| :--- | :--- | :--- |
| **Назначение** | Кратковременное (минуты) «припрятывание» кода. | Параллельная работа над задачами в разных папках. |
| **Переключение** | Требует очистки рабочего дерева. | Не требует (разные директории). |
| **Сложность** | Низкая (одна команда). | Средняя (управление папками). |
