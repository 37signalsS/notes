# Git Stash — временное хранение изменений

## Определения

**Stash (git stash)** — механизм временного сохранения незавершённых изменений рабочего каталога и индекса в отдельном хранилище (стеке), позволяющий переключиться на другую ветку без создания «грязного» коммита.

**Физическая реализация:** Stash — это специальный вид коммита, который не принадлежит ни одной ветке. При выполнении `git stash` Git создаёт древовидную структуру из двух или трёх коммитов:
1.  **Коммит индекса (Index Commit):** Состояние Staging Area на момент сохранения.
2.  **Коммит рабочего дерева (Working Tree Commit):** Состояние отслеживаемых файлов в рабочей директории. Его родителем является коммит, на который указывал HEAD, а вторым родителем — коммит индекса.
3.  **Коммит сторонних файлов (Untracked Commit):** Создаётся только при использовании флага `-u` (untracked) или `-a` (all). Третий родитель — HEAD на момент сохранения.

Все записи хранятся в `.git/refs/stash` и отслеживаются через рефлог `.git/logs/refs/stash`. Git не синхронизирует это хранилище с удалённым репозиторием, поэтому stash является сугубо локальным инструментом.

### Почему stash существует

Git не позволяет переключиться на другую ветку (`git switch` / `git checkout`), если есть незакоммиченные изменения, которые конфликтуют с состоянием целевой ветки.

| Подход | Проблема |
| :--- | :--- |
| **Создать временный коммит** | Засоряет историю «мусорными» коммитами, требует `reset` при возвращении. |
| **Просто переключиться** | Untracked файлы переносятся между ветками, а изменения в tracked файлах могут вызвать блокирующий конфликт. |
| **Принудительный checkout** | Полная потеря всех незакоммиченных изменений без возможности восстановления. |

Stash решает эти проблемы, изолируя изменения в «карман» и восстанавливая чистое состояние рабочего дерева.

## Базовые концепции

### Механика стека

Stash организован по принципу LIFO (Last In, First Out). Новая запись всегда получает индекс `stash@{0}`, сдвигая остальные вглубь стека.

```bash
# Сохранить изменения (рекомендуемый современный способ)
git stash push -m "Описание контекста"

# Список всех сохранённых состояний
git stash list
# → stash@{0}: On main: fix naming
# → stash@{1}: WIP on feature: add validation

# Применить изменения и удалить из стека
git stash pop stash@{0}

# Применить изменения, сохранив их в стеке
git stash apply stash@{1}
```

### Основные флаги и типы stash

| Флаг | Описание | Особенности |
| :--- | :--- | :--- |
| `-u` / `--include-untracked` | Сохраняет новые, ещё не отслеживаемые файлы. | Не включает файлы из `.gitignore`. |
| `-a` / `--all` | Сохраняет всё, включая файлы из `.gitignore`. | Полный снимок состояния. |
| `-p` / `--patch` | Интерактивный режим: выбор конкретных фрагментов кода (hunks) для сохранения. | Похоже на `git add -p`. |
| `-k` / `--keep-index` | Сохраняет изменения, но оставляет их в Staging Area (индексе). | Полезно для тестирования только staged изменений. |
| `-S` / `--staged` | (Git 2.35+) Сохраняет только те изменения, что уже добавлены в индекс. | Не затрагирует рабочее дерево. |
| `-q` / `--quiet` | Подавляет вывод сообщений об успешном выполнении. | Для использования в скриптах. |

### Управление и инспекция

```bash
# Просмотр изменений (diff) без применения
git stash show -p stash@{0}

# Просмотр списка файлов, включая новые (Git 2.31+)
git stash show --include-untracked stash@{0}

# Удалить конкретную запись
git stash drop stash@{0}

# Полная очистка хранилища
git stash clear

# Извлечь отдельный stash в новую запись (Git 2.13+)
git stash branch <имя_ветки> stash@{0}
```

### Предварительные требования

* **Версия Git:** Базовый функционал доступен во всех версиях Git. Флаг `--staged` требует Git 2.35+, `--include-untracked` в `show` — Git 2.31+.
* **Начальное состояние:** Для использования stash необходим инициализированный репозиторий с хотя бы одним коммитом.
* **Права доступа:** Stash хранится локально, поэтому не требует доступа к удалённому репозиторию.

## Практические сценарии

### Сценарий 1: Срочный перенос контекста (Баг-фикс)

Работа над фичей прервана критическим багом в другой ветке.

**Предусловия:** Есть незакоммиченные изменения в текущей ветке.

```bash
# Сохраняем всё рабочее состояние
git stash -u -m "WIP: auth-module integration"

# Переходим на main и правим баг
git switch main
# ... правки ...
git commit -m "fix: memory leak in session"

# Возвращаемся и восстанавливаем состояние
git switch feature-auth
git stash pop
# → Restored working tree and index state: WIP: auth-module integration
```

**Валидация:**
```bash
# Убедиться, что stash применён и удалён из стека
git stash list
# → (пусто или без нашей записи)

# Проверить, что файлы восстановлены
git status
# → Changes not staged for commit:
# →   modified:   src/auth.py
```

**Edge cases:**
* Если при применении stash возникает конфликт, запись **не удаляется** из стека. После разрешения конфликта выполните `git stash drop` вручную.
* При использовании `-u` новые файлы будут восстановлены в рабочем каталоге.

### Сценарий 2: Изоляция untracked файлов при переключении

По умолчанию Git переносит новые файлы между ветками. Это может привести к появлению отладочных логов или конфигов в «чистых» ветках.

**Предусловия:** Есть untracked файлы, которые нужно скрыть.

```bash
# Файл debug_log.txt создан, но не добавлен в Git
git stash -u
git switch main  # Файл debug_log.txt исчез из рабочей директории

# Возврат к работе
git switch feature-debug
git stash pop
# → Файл debug_log.txt снова в рабочем каталоге
```

**Валидация:**
```bash
# Проверить, что untracked файлы были сохранены
git stash show -u stash@{0}
# → debug_log.txt | 10 ++++++++++
```

**Edge cases:**
* Файлы из `.gitignore` не сохраняются при использовании `-u`. Для них нужен флаг `-a`.
* При переключении на ветку, где файл уже отслеживается, может возникнуть конфликт применения stash.

### Сценарий 3: Восстановление состояния индекса

По умолчанию `git stash pop` применяет изменения как unstaged. Если важно вернуть файлы именно в Staging Area, используйте флаг `--index`.

**Предусловия:** Был сделан stash с staged изменениями (например, `git add` перед stash).

```bash
# Сохраняем с учётом индекса
git stash push -m "staged changes" --keep-index

# Или восстанавливаем с сохранением индекса
git stash pop --index
```

**Валидация:**
```bash
# Проверить состояние после восстановления
git status
# → Changes to be committed:    (файлы в индексе)
# →   modified:   src/app.py
```

**Edge cases:**
* Если при сохранении использовался `--keep-index`, файлы остаются и в индексе, и в stash. При восстановлении может возникнуть конфликт — используйте `git reset` для очистки индекса перед `pop --index`.

### Сценарий 4: Создание ветки из конфликтующего stash

Если с момента сохранения ветка сильно ушла вперёд, `pop` может вызвать сложные конфликты. Безопаснее создать новую ветку на основе того коммита, где был сделан stash.

**Предусловия:** Stash был создан на старом коммите, текущая ветка продвинулась.

```bash
# Создаёт ветку 'debug-fix', переключается на неё и применяет изменения
git stash branch debug-fix stash@{0}
# → Switched to a new branch 'debug-fix'
```

**Валидация:**
```bash
# Проверить, что мы на новой ветке
git branch
# → * debug-fix

# Проверить, что stash применён
git status
# → Changes not staged for commit:
# →   modified:   src/debug.py
```

**Edge cases:**
* Если применение stash в новой ветке вызывает конфликт, запись остаётся в стеке. После разрешения конфликта выполните `git stash drop`.

### Сценарий 5: Ручное управление объектами (создание бекапа)

Для автоматизации или создания «невидимых» бекапов можно создавать объекты stash вручную.

**Предусловия:** Необходимо сохранить снимок состояния без очистки рабочего дерева.

```bash
# Создаёт объект коммита и возвращает его SHA (не меняет рабочее дерево)
SHA=$(git stash create)

# Сохраняет созданный коммит в стек под заданным именем
git stash store -m "Snapshot before rebase" $SHA
```

**Валидация:**
```bash
# Проверить, что stash создан
git stash list
# → stash@{0}: On main: Snapshot before rebase

# Убедиться, что рабочее дерево не изменилось
git status
# → (исходное состояние)
```

**Edge cases:**
* `git stash create` возвращает пустую строку, если нет изменений для сохранения. Проверяйте результат перед `store`.

### Сценарий 6: Интерактивный частичный stash (patch mode)

Позволяет выбрать только нужные изменения для сохранения, игнорируя остальные.

**Предусловия:** Необходимо сохранить только часть изменений в файлах.

```bash
# Запустить интерактивный режим
git stash push -p -m "partial: auth changes"
# → Hunks будут предложены по одному для выбора
# y - сохранить этот фрагмент
# n - пропустить
# q - завершить выбор
# s - разделить на меньшие части
```

**Валидация:**
```bash
# Проверить, что выбранные изменения сохранены
git stash show -p stash@{0}

# Убедиться, что остальные изменения остались в рабочем дереве
git status
```

**Edge cases:**
* Для бинарных файлов интерактивный режим недоступен — они сохраняются целиком или не сохраняются вообще.
* Очень большие hunks можно разделить командой `s` для более точного выбора.

### Сценарий 7: Сохранение только staged изменений (Git 2.35+)

Новый флаг `--staged` позволяет сохранить только индексированные изменения, оставив рабочее дерево нетронутым.

**Предусловия:** Git 2.35+, есть staged и unstaged изменения.

```bash
# Сохраняем только то, что в индексе
git stash push --staged -m "only staged fixes"
```

**Валидация:**
```bash
# Проверить содержимое stash
git stash show stash@{0}
# → Только staged файлы

# Проверить, что unstaged изменения остались
git status
# → Changes not staged for commit: (unstaged файлы на месте)
```

**Edge cases:**
* При использовании `--staged` без staged изменений команда завершится ошибкой: `No staged changes`.

### Сценарий 8: Восстановление удалённого stash

При случайном удалении stash или сбое можно восстановить его через dangling объекты.

**Предусловия:** Stash был удалён (`drop` или `clear`), но прошло немного времени (до `gc`).

```bash
# Найти висячие коммиты
git fsck --unreachable --no-reflogs 2>/dev/null | grep commit

# Просмотреть содержимое найденного коммита
git log --oneline <sha>

# Восстановить как stash
git stash store -m "Recovered stash" <sha>

# Или создать ветку из коммита
git branch recovery-branch <sha>
```

**Валидация:**
```bash
# Проверить восстановленный stash
git stash show -p stash@{0}
```

**Edge cases:**
* После выполнения `git gc --prune=now` восстановление невозможно.
* Reflog для stash хранится 30–90 дней (настраивается через `gc.reflogExpire`).

## Особенности и ограничения

### Базовые ограничения

* **Локальность:** Stash существует только в `.git/refs/stash`. Команда `git push` его не видит.
* **Глобальность:** Stash доступен из любой ветки репозитория, что позволяет переносить код между ветками без коммитов.
* **Срок жизни:** Данные не удаляются автоматически. Только `drop`, `clear` или агрессивный `git gc` (если на объекты нет ссылок).
* **Конфликты:** Если `stash pop` вызывает конфликт, запись **не удаляется** из стека автоматически, чтобы вы не потеряли данные при неудачном слиянии.

### Поведение в особых случаях

* **Submodules:** Stash не сохраняет изменения в подмодулях автоматически. Для этого требуется использовать `--recurse-submodules` (Git 2.35+) или обрабатывать подмодули вручную.
* **Sparse checkout:** При использовании sparse checkout stash корректно работает только с файлами, попадающими под текущие паттерны.
* **Large files:** Бинарные файлы сохраняются целиком в каждый stash, что может быстро увеличить размер `.git`.
* **Empty stash:** `git stash create` возвращает пустую строку, если нет изменений. Проверяйте результат перед использованием.

### Сравнение со смежными инструментами

| Критерий | git stash | git worktree | Временный коммит |
| :--- | :--- | :--- | :--- |
| **Назначение** | Кратковременное (минуты) «припрятывание» кода. | Параллельная работа над задачами в разных папках. | Сохранение с возможностью отката. |
| **Переключение** | Требует очистки рабочего дерева. | Не требует (разные директории). | Требует `reset`. |
| **Сложность** | Низкая (одна команда). | Средняя (управление папками). | Средняя (нужен cleanup). |
| **История** | Не засоряет историю. | Не засоряет историю. | Засоряет историю. |
| **Долговременность** | Кратковременно (до очистки). | Долговременно. | Долговременно (в истории). |

## Troubleshooting

### Типичные ошибки и решения

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `Cannot save the current index state` | Нет индексированных изменений при использовании `--keep-index`. | Добавьте файлы в индекс или уберите флаг. |
| `CONFLICT (content): Merge conflict` | Stash не может быть применён из-за конфликта. | Разрешите конфликт вручную, выполните `git add`, затем `git stash drop`. |
| `fatal: unable to resolve reference refs/stash` | Повреждён stash ref. | Удалите `.git/refs/stash` и `.git/logs/refs/stash`, пересоздайте при необходимости. |
| `No stash entries found` | Попытка применить несуществующий stash. | Проверьте `git stash list` для актуальных записей. |
| Stash не сохраняет untracked файлы | Не использован флаг `-u`. | Используйте `git stash -u` или `git stash -a`. |
| Stash не удаляется после pop | Применение вызвало конфликт. | Вручную выполните `git stash drop` после разрешения конфликта. |
| `git stash` ничего не делает | Нет изменений для сохранения. | Проверьте `git status`. |

### Диагностика

```bash
# Проверить целостность stash
git stash list
# → Должен показать список записей или быть пустым

# Проверить reflog stash
git reflog show stash
# → История всех изменений stash

# Проверить размер stash
du -sh .git/refs/stash
du -sh .git/logs/refs/stash

# Просмотреть структуру stash-коммитов
git log --oneline --graph stash@{0}
```

### Очистка и обслуживание

```bash
# Удалить конкретный stash
git stash drop stash@{0}

# Очистить весь stash
git stash clear

# Принудительная очистка объектов (освободит место)
git reflog expire --expire=now refs/stash
git gc --prune=now
```

## Best Practices

1. **Используйте описательные сообщения:** Всегда добавляйте `-m "описание"` к `git stash push`. Через неделю вы не вспомните, что было в `WIP on feature`.
2. **Не храните stash долго:** Stash — для кратковременного хранения (минуты-часы). Для долговременного используйте ветки или коммиты.
3. **Проверяйте перед применением:** Используйте `git stash show -p stash@{0}` перед `pop`, чтобы избежать неожиданных конфликтов.
4. **Очищайте регулярно:** Выполняйте `git stash clear` после завершения работы с накопленными stash.
5. **Избегайте stash для важного кода:** Если изменения критичны — создайте ветку и коммит. Stash можно случайно удалить.
6. **Используйте `-u` для полного снимка:** При переключении контекста обычно нужен `-u`, чтобы не потерять новые файлы.
7. **Автоматизируйте очистку:** Настройте `gc.reflogExpire` для автоматической очистки старых stash:
   ```bash
   git config gc.reflogExpire '30 days'
   git config gc.reflogExpireUnreachable '14 days'
   ```
8. **Тестируйте перед stash:** Используйте `--keep-index` для тестирования staged изменений без потери unstaged.
