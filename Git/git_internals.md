# Git — внутреннее устройство

**Актуально для:** Git 2.56.x (локально проверено на 2.54.0). Механизмы объектной модели неизменны с 2019–2024 гг.; статус SHA-256 и reftable отражает состояние на Git 2.56 (сентябрь 2026).

## Определения

**Git** — распределённая система контроля версий, представляющая собой **контентно-адресуемую файловую систему** (content-addressable filesystem) с интерфейсом VCS поверх неё. В основе лежит база данных объектов, к которым обращаются по криптографическому хэшу содержимого.

**Хэш (SHA-1 / SHA-256)** — уникальный идентификатор объекта, вычисляемый от конкатенации заголовка `<тип> <размер>\0` и данных объекта:

- **SHA-1** (40 hex-символов, 160 бит) — хэш по умолчанию для всех репозиториев, созданных до настоящего времени. Для защиты от известных атак на SHA-1 Git по умолчанию использует модификацию **sha1dc** (SHA-1 collision detection), возвращающую иной результат на входах, подпадающих под известные слабости.
- **SHA-256** (64 hex-символа, 256 бит) — поддерживается с Git 2.29 (2020), с Git 2.42 (2023) **не считается экспериментальным**, но по-прежнему не является значением по умолчанию. Между SHA-1- и SHA-256-репозиториями **нет взаимодействия** (нет совместного fetch/push). В Git 3.0 (планируется 2026) default для новых репозиториев сменится на SHA-256 — объявлено в [BreakingChanges](https://git-scm.com/docs/BreakingChanges). Выбор хэша: `--object-format=<sha1|sha256>` у `git init`/`git clone`, переменная `GIT_DEFAULT_HASH`, конфиг `init.defaultObjectFormat` (оба с Git 2.47). Проверить формат репозитория: `git rev-parse --show-object-format`.

**Объектная модель Git** — четыре типа сущностей (blob, tree, commit, tag), из которых строится всё дерево проекта. Все объекты неизменяемы: изменение любого бита создаёт новый объект с другим хэшем.

**Механизмы оптимизации** (подробно — в [Производительность Git](./git_performance.md)):

- **Commit-graph** — бинарный файл `.git/objects/info/commit-graph`, кэш связей коммитов для быстрого обхода истории.
- **Multi-pack-index (MIDX)** — `.git/objects/pack/multi-pack-index`, сводный индекс всех pack-файлов.
- **Reachability Bitmaps** — `.git/objects/pack/*.bitmap`, предвычисленные множества достижимых объектов.

## Архитектура: директория `.git/`

Критически важные компоненты (без них репозиторий не работает):

| Компонент | Обязателен | Назначение |
|-----------|-----------|------------|
| `HEAD` | Да | Указывает на текущую ветку или конкретный коммит |
| `objects/` | Да | База данных всех объектов (хранилище контента) |
| `refs/` | Да | Указатели на коммиты (ветки, теги, удалённые ветки) |

Остальные компоненты (реальный листинг `.git/` после первого коммита):

| Компонент | Назначение |
|-----------|------------|
| `config` | Настройки конкретного репозитория (`git config --local`) |
| `index` | Бинарный файл staging area (область подготовки) |
| `logs/` | Журнал перемещений HEAD и веток (reflog) |
| `hooks/` | Скрипты-хуки (автоматизация) — подробнее в [Git Hooks](./git_hooks.md) |
| `info/` | `exclude` (локальные ignore-правила), `objects/info/` — служебные данные ODB (`alternates`, `commit-graph`, `packs`) |
| `objects/` | Loose-объекты: поддиректории `00/`–`ff/`; `objects/pack/` — pack-файлы |
| `packed-refs` | Упакованные ссылки (один файл вместо тысяч файлов в `refs/`) |
| `reftable/` | Директория бэкенда reftable (при `init --ref-format=reftable`) |
| `modules/` | Метаданные submodule-репозиториев |
| `worktrees/` | Регистрация дополнительных worktree (`git worktree add`) |
| `COMMIT_EDITMSG`, `MERGE_HEAD`, `FETCH_HEAD`, `ORIG_HEAD` | Переходное состояние операций (черновик сообщения, состояние merge/fetch, точка до опасной операции) |

```bash
# Проверка: без objects/ или HEAD Git перестаёт видеть репозиторий
rm -rf .git/objects
git status
# → fatal: not a git repository
```

### Эксперимент: минимальный репозиторий вручную

```bash
mkdir -p .git/objects .git/refs/heads
echo "ref: refs/heads/main" > .git/HEAD
git status
# → On branch main
# → No commits yet
```

Эти две директории и файл воспроизводят `git init`. Git был создан Линусом Торвальдсом примерно за 10 дней в апреле 2005 года; изначально многие команды были bash-скриптами поверх утилит на C, позже переписанные на C.

## Четыре типа объектов

Git хранит четыре вида объектов в `.git/objects/`. Все они сжаты zlib и идентифицируются хэшем (SHA-1 или SHA-256 — в зависимости от формата репозитория).

### Blob (Binary Large Object)

Хранит содержимое файла как есть. Не содержит имени файла — только данные. Одинаковые файлы в разных коммитах хранятся как один blob.

```bash
# Создание blob и вывод его хэша (реальное значение для "hello git" без \n)
echo -n "hello git" | git hash-object --stdin -w
# → f09e9c379f5fe8f4ce718641c356df87906d87a6

# Просмотр blob напрямую
git cat-file -p f09e9c379f5fe8f4ce718641c356df87906d87a6
# → hello git

# Тип объекта
git cat-file -t f09e9c379f5fe8f4ce718641c356df87906d87a6
# → blob
```

Формат хранимых данных: `blob <размер>\0<содержимое>`.

### Tree (Дерево)

Хранит структуру директории: отображение имён файлов в blob-хэши + права доступа. Аналог inode в файловых системах.

```bash
# Просмотр дерева
git cat-file -p <sha_tree>
# → 100644 blob f09e9c379f5fe8f4ce718641c356df87906d87a6    hello.txt
# → 100755 blob 8d0e41234f24b6da002d962a26c2495ea16a425f    script.sh

# Рекурсивный листинг с путями
git ls-tree -r <sha_tree>
```

Запись в дереве: `<режим> <тип> <хэш>\t<имя>`. Режимы: `100644` (обычный файл), `100755` (исполняемый), `120000` (symbolic link), `040000` (поддиректория — ссылка на tree), `160000` (gitlink, submodule).

### Commit (Коммит)

Снимок состояния проекта — ссылается на дерево и хранит метаданные.

```bash
git cat-file -p HEAD
# → tree 58c608a3fa830548019591fc45f307554ca9a57f
# → parent <sha_родителя>   # отсутствует у первого коммита
# → author Vasya <vasya@example.com> 1719000000 +0300
# → committer Vasya <vasya@example.com> 1719000000 +0300
# →
# → my new file
```

Поля коммита:

- `tree` — ссылка на корневое дерево проекта
- `parent` — ссылка на родительский коммит (один для обычного, два и более для merge, отсутствует для root-коммита)
- `author` — автор изменений (имя + email + timestamp)
- `committer` — кто создал коммит (может отличаться от автора при rebase/cherry-pick)
- Пустая строка
- Сообщение коммита

### Tag (Аннотированный тег)

Объект с метаданными, указывающий на коммит (аналог коммита, но без дерева). Лёгкие (lightweight) теги — это просто файл в `refs/tags/` без отдельного объекта.

```bash
git cat-file -p <sha_тега>
# → object <sha_коммита>
# → type commit
# → tag v1.0
# → tagger Vasya <vasya@example.com> 1719000000 +0300
# →
# → Release v1.0
```

Подробнее о тегах: [Git Tags](./git_tags.md).

### Иерархия объектов

```
HEAD → refs/heads/main → commit (метаданные + сообщение)
                               │
                               ▼
                             tree (структура директорий)
                               │
                     ┌─────────┴─────────┐
                     ▼                   ▼
                  blob (file1)        blob (file2)
```

## Формат объекта и хранение

### Формат объекта: заголовок + zlib + хэш

Каждый объект перед записью в базу данных:

1. Формируется заголовок: `<тип> <размер>\0` (например, `blob 9\0`).
2. Вычисляется хэш (SHA-1 или SHA-256) от конкатенации заголовка и данных.
3. Всё содержимое (заголовок + данные) сжимается алгоритмом **zlib** и записывается в `.git/objects/`.

```bash
# Ручное создание blob (реальный хэш для "hello git" без \n)
echo -n "hello git" | git hash-object --stdin -w
# → f09e9c379f5fe8f4ce718641c356df87906d87a6

# Эмуляция вычисления хэша через Python (SHA-1)
python3 -c "
import hashlib
content = b'hello git'
header = f'blob {len(content)}'.encode() + b'\0'
sha = hashlib.sha1(header + content).hexdigest()
print(f'Hash: {sha}')
print(f'Путь: .git/objects/{sha[:2]}/{sha[2:]}')
"
# → Hash: f09e9c379f5fe8f4ce718641c356df87906d87a6
# → Путь: .git/objects/f0/9e9c379f5fe8f4ce718641c356df87906d87a6
```

### Структура директорий (Loose objects)

Для оптимизации работы файловой системы хэш разбивается: первые 2 символа становятся именем поддиректории в `.git/objects/`, а остальные 38 символов (для SHA-1; 62 для SHA-256) — именем файла. Это предотвращает переполнение одной директории тысячами файлов.

Loose-объект удобен для записи, но неэффективен при чтении (много файловых операций) — поэтому Git периодически упаковывает их в pack-файлы.

### Pack-файлы

Когда количество loose-объектов растёт (порог `gc.auto`, по умолчанию ~6700), Git упаковывает их в pack-файлы. Формат (см. [gitformat-pack](https://git-scm.com/docs/gitformat-pack)):

| Файл | Назначение |
|------|------------|
| `pack-<sha>.pack` | Данные: заголовок `PACK` + версия (2; Git читает 2 и 3, генерирует только 2) + число объектов + записи объектов + контрольная сумма |
| `pack-<sha>.idx` | Индекс для быстрого поиска смещения объекта внутри `.pack`. v2 начинается с magic `\377tOc`, содержит fan-out-таблицу, отсортированные имена объектов, CRC32 и таблицы смещений |
| `pack-<sha>.rev` | Reverse index (RIDX): позиция объекта по его смещению в pack — ускоряет запись дельт и repack |
| `pack-<sha>.mtimes` | Времена модификации объектов (для избирательного repack) |
| `pack-<sha>.keep` | Метка: pack не должен консолидироваться `gc` (используется при инкрементальных fetch) |

Типы записей в pack: `OBJ_COMMIT (1)`, `OBJ_TREE (2)`, `OBJ_BLOB (3)`, `OBJ_TAG (4)`, `OBJ_OFS_DELTA (6)`, `OBJ_REF_DELTA (7)`; тип 5 зарезервирован, 0 невалиден. Дельта-компрессия хранит базовый объект и различия:

- **OFS_DELTA** — базовый объект в том же pack, адресуется отрицательным смещением (компактнее).
- **REF_DELTA** — базовый объект адресуется по хэшу; может находиться вне pack (используется для «тонких» pack при передаче по сети).

Имя pack-файла (`pack-<sha>`) — это контрольная сумма его `.idx`. Имена loose- и packed-объектов совпадают: объект один и тот же, меняется только способ хранения.

**Multi-pack-index (MIDX)** и **bitmaps** — сводный индекс и предвычисляемые множества достижимости; их применение, конфигурация и сценарии подробно описаны в [Производительность Git](./git_performance.md).

## Index (Staging Area)

Индекс — бинарный файл `.git/index` с кастомным форматом ([gitformat-index](https://git-scm.com/docs/gitformat-index)). Хранит метаинформацию о файлах, готовых к следующему коммиту: путь, хэш blob, режим, stat-метаданные (для быстрого определения изменений без чтения файлов).

```bash
# Просмотр индекса
git ls-files --stage
# → 100644 f09e9c379f5fe8f4ce718641c356df87906d87a6 0       hello.txt

# Текущая версия формата индекса (2 по умолчанию)
git ls-files --debug | head -3
```

Поддерживаемые версии формата: **2** (по умолчанию), **3** (расширенные флаги) и **4** (пути с prefix-сжатием относительно предыдущей записи — компактнее при длинных путях). Расширения индекса: `TREE` (cache-tree — кэш деревьев для быстрой записи коммитов), `sdir` (sparse directory — свёртка директорий при sparse-checkout в cone mode).

Staging area — исторически отдельная утилита в наборе Git (философия Unix: одна утилита — одна задача). Позволяет:

- Готовить драфт коммита
- Дробить изменения одного файла на несколько коммитов (через `git add -p`)
- Откатывать только часть изменений (`git restore --staged`, `git reset -p`)

## Указатели: HEAD, ссылки и ветки

### HEAD

Текстовый файл `.git/HEAD`, указывающий на текущую позицию в репозитории.

- **Связанный (Attached):** Указывает на ветку (`ref: refs/heads/main`).
- **Отсоединенный (Detached):** Указывает напрямую на SHA коммита (при checkout конкретного коммита или тега). Коммиты в этом состоянии не видны из веток и могут быть потеряны после истечения reflog — выход: создать ветку (`git switch -c <name>`).

### Refs (Ссылки)

Файлы в директории `refs/`, содержащие хэш коммита (по одной строке, с `\n`):

- **Ветки (`refs/heads/`):** Перемещаемые указатели. При новом коммите Git просто обновляет хэш в соответствующем файле.
- **Теги (`refs/tags/`):** Обычно статичные указатели.
- **Удалённые ветки (`refs/remotes/`):** Последнее известное состояние веток на удалённом сервере.
- **`refs/replace/`:** Механизм подмены объектов (`git replace`): ссылка `<sha-оригинала>` указывает на `<sha-замену>`, и все чтения оригинала прозрачно возвращают замену. Полезно для исправления истории без перезаписи (например, замены коммита с секретом).

### Бэкенды ссылок

1. **Files (стандартный):** Каждая ветка — отдельный текстовый файл в `refs/heads/`.
2. **Packed-refs:** Оптимизация для множества веток — один файл `.git/packed-refs` со списком ссылок (используется для уже полученных из remote веток и тегов).
3. **Reftable:** Бинарный бэкенд, интегрированный в Git 2.45 (апрель 2024); с Git 2.47 выбирается конфигом `init.defaultRefFormat`. **Не является экспериментальным** (снятие экспериментального статуса зафиксировано в документации 2026 года). Обеспечивает атомарные транзакции обновлений, prefix-сжатие и O(log n) поиск, объединяя ссылки и reflog в единую структуру `.git/reftable/`. Объявлен как формат по умолчанию для новых репозиториев в Git 3.0. Включение: `git init --ref-format=reftable`, миграция: `git refs migrate --ref-format=reftable`. Подробности: [git_reflog.md](./git_reflog.md), [git_configuration.md](./git_configuration.md).

Обновление refs транзакционно: `git update-ref <ref> <new> <old>` — атомарный compare-and-swap, откажет, если текущий указатель не равен `<old>`. Внутри записи защищаются lock-файлами (`<ref>.lock`), что делает одновременные обновления безопасными.

### Reflog

Журнал всех перемещений HEAD и веток в локальном репозитории (`.git/logs/`). Позволяет восстановить «потерянные» коммиты (те, на которые не указывает ни одна ветка), пока они не удалены сборщиком мусора. Записи expire: `gc.reflogExpire` — 90 дней, `gc.reflogExpireUnreachable` — 30 дней. Полностью освещён в [Git Reflog](./git_reflog.md).

### Служебные указатели

- **`ORIG_HEAD`** — предыдущее положение HEAD перед опасными операциями (merge, reset). Создаётся Git автоматически.
- **`FETCH_HEAD`** — список полученных при последнем `git fetch` ссылок.
- **`MERGE_HEAD`** — коммит, с которым идёт текущий merge (при конфликте).

## Git как направленный ациклический граф (DAG)

История Git — это направленный ациклический граф (Directed Acyclic Graph), где узлами являются коммиты, а ребрами — ссылки на родителей.

**Ключевые свойства:**

- **Иммутабельность:** Один хэш — одно содержимое навсегда. Изменение любого байта меняет хэш и создаёт новый объект.
- **Связность:** Каждый коммит знает о своих предках, но не знает о потомках.
- **Достижимость (reachability):** Объект «жив», если достижим из какой-либо ref или reflog-записи; иначе он мусор для `git gc`.
- **Оптимизация графа (Commit-graph):** Файл `commit-graph` хранит структуру связей в оптимизированном бинарном виде, позволяя Git вычислять отношения между коммитами без чтения отдельных объектов.

## Поиск репозитория и переменные окружения

Git находит репозиторий, поднимаясь от текущей директории вверх до первого `.git` (или файла `.git` с указанием пути — так работают submodules и `git worktree`):

| Переменная / ключ | Назначение |
|-------------------|------------|
| `GIT_DIR` / `git --git-dir=<path>` | Путь к `.git` напрямую (работа вне рабочего дерева, скрипты, CI) |
| `--work-tree=<path>` / `GIT_WORK_TREE` | Рабочее дерево отдельно от `.git` (bare-репозитории) |
| `GIT_OBJECT_DIRECTORY` | Альтернативный ODB (objects dir) |
| `GIT_ALTERNATE_OBJECT_DIRECTORIES` | Список alternate-хранилищ (см. ниже) |
| `git rev-parse --git-dir` / `--show-toplevel` / `--git-common-dir` | Отладка: где Git видит репозиторий, корень дерева, общий `.git` для worktree |

**Alternates** — файл `.git/objects/info/alternates` со списком путей (по одному на строку) к другим ODB. Объекты читаются из alternates, но не записываются туда. Применяется для экономии диска: зеркала, CI-кэши, множественные клоны одной истории. Риск: удаление источника alternate ломает репозиторий — `git gc` в таком репозитории «утяжеляет» объекты, копируя их в локальный ODB.

**Quarantine** — при push полученные объекты сначала пишутся во временную quarantine-директорию (`objects/incoming-XXXX`), и только после успешной проверки refs обновляются. Поэтому неудачный push не оставляет мусора в репозитории.

## Практические сценарии

### Сценарий 1: коммит «под капотом» через plumbing

Реализация `git commit -m "msg"` через низкоуровневые шаги (хэши реальные для `"hello git\n"`):

```bash
# 1. Вычисление хэша и создание blob
echo "hello git" | git hash-object -w --stdin
# → 8d0e41234f24b6da002d962a26c2495ea16a425f

# 2. Обновление индекса (staging)
git update-index --add --cacheinfo 100644 8d0e41234f24b6da002d962a26c2495ea16a425f hello.txt

# 3. Создание дерева из индекса
git write-tree
# → <sha_дерева>

# 4. Создание коммита (ссылка на дерево и родителя)
echo "initial commit" | git commit-tree <sha_дерева> -p <parent_sha>
# → <sha_коммита>

# 5. Перемещение указателя ветки
git update-ref refs/heads/main <sha_коммита>
```

### Сценарий 2: диагностика целостности репозитория

```bash
# Статистика объектов: loose/packed/garbage
git count-objects -v
# → count: 4          # loose-объектов
# → size: 16          # КБ в loose
# → in-pack: 15234    # объектов в pack-файлах
# → packs: 2          # pack-файлов
# → size-pack: 4821   # КБ в pack
# → prune-packable: 0 # loose, дублирующие packed (кандидаты на gc)
# → garbage: 0        # повреждённых/мусорных файлов

# Проверка связи объекта с репозиторием
git cat-file -e <sha> && echo "объект существует" || echo "объект отсутствует"

# Полная проверка базы объектов (dangling, missing, corrupt)
git fsck --full
# → dangling blob <sha>   # не обязательно ошибка: мусор после перезаписи истории
# → (пустой вывод при исправном репозитории)

# Проверка pack-файла и его индекса
git verify-pack -v .git/objects/pack/pack-<sha>.idx

# Проверка графа коммитов
git commit-graph verify

# Проверка MIDX
git multi-pack-index verify
```

## Обслуживание и надёжность

- **Сборка мусора (`git gc`):** Объединяет loose-объекты в pack-файлы, удаляет недостижимые объекты, обновляет индексы (MIDX, commit-graph), expire'ит reflog. Автозапуск (`gc --auto`) при >`gc.auto` (6700) loose-объектах или >`gc.autoPackLimit` (50) pack-файлов без `.keep`.
- **Фоновое обслуживание (`git maintenance`):** Периодические задачи (gc, commit-graph, incremental-repack, prefetch) без участия пользователя (Git 2.30+) — сценарии в [Производительность Git](./git_performance.md).
- **Очистка объектов (`git prune`):** Удаление «осиротевших» (dangling) объектов, на которые не указывает ни одна ссылка и которые отсутствуют в reflog.
- **Проверка целостности (`git fsck`):** Проверка базы данных объектов на предмет повреждений или отсутствующих связей.
- **Git LFS (Large File Storage):** Вместо большого файла Git хранит текстовый указатель с хэшем, контент скачивается по требованию — подробнее в [Git LFS](./git_lfs.md).

## Устранение неполадок

| Симптом | Причина | Решение |
|---------|---------|---------|
| `fatal: loose object <sha> (stored in .git/objects/xx/yy...) is corrupt` | Обрезанный/повреждённый файл loose-объекта (диск, антивирус, прерывание записи) | Если объект есть в pack — удалить повреждённый loose-файл; иначе восстановить из другого клона/remote; `git fsck --full` для полной картины |
| `error: unable to read <sha>` / `fatal: failed to read object` | Отсутствует объект (неполный clone, удалённый alternate) | Проверить `GIT_ALTERNATE_OBJECT_DIRECTORIES` и `objects/info/alternates`; `git fetch` заново |
| `fatal: not a git repository` | Нет `.git` выше по дереву или сломан `GIT_DIR` | `git rev-parse --git-dir` от рабочей директории; проверить переменные окружения |
| `warning: refname 'HEAD' is ambiguous` | Одноимённые ref и файл/тег | Переименовать конфликтующую ссылку (`git branch -m`) |
| `dangling commit/blob` от `git fsck` | Остатки перезаписанной истории (reset, rebase, amend) | Не ошибка. Восстановить через `git reflog`/`git merge --no-ff <sha>` или удалить `git prune` после подтверждения ненужности |
| `git gc` не сокращает репозиторий | Есть `.keep`-файлы или cruft-pack с недавними объектами | Проверить `git count-objects -v` (prune-packable); `.keep` не трогать в репозиториях, питаемых инкрементальным fetch |
| Сторонний инструмент не читает репозиторий | Репозиторий в формате reftable, инструмент старый | Проверить `git rev-parse --show-ref-format`; мигрировать обратно или обновить инструмент |
| `error: bad index file sha1 signature` | Повреждён `.git/index` | `rm .git/index && git reset` (индекс пересоздаётся из HEAD) |

## Лучшие практики

- **Не редактируйте файлы `.git/` вручную** (кроме документированных случаев вроде `HEAD`/`packed-refs`): используйте plumbing-команды — они корректно работают с блокировками и транзакциями.
- **Проверяйте целостность после сбоев диска/дискового пространства:** `git fsck --full` и `git count-objects -v` — быстрая диагностика ODB.
- **Для зеркал и CI-кэшей** используйте alternates (`objects/info/alternates`) с пониманием риска зависимости от источника; для долгоживущих клонов периодически запускайте `git gc` для материализации объектов локально.
- **`.keep` на pack-файлах** — только для pack, получаемых инкрементально (например, на сервере), иначе `gc` не сможет консолидировать историю.
- **Выбор хэш-функции:** для новых изолированных репозиториев допустим `--object-format=sha256` (проверено, не экспериментален с 2.42), но до Git 3.0 это ломает взаимодействие с большинством forges и SHA-1-репозиториями — в общем случае оставляйте SHA-1.
- **Порог обслуживания:** на больших репозиториях выносите `git gc`/`git maintenance` в cron/планировщик вместо ожидания автотриггеров; мониторьте `count-objects -v` (поля `count`, `garbage`) как метрику здоровья.
- **Cleanup после экспериментов:** сценарии выше создают объекты в реальном репозитории — для практики используйте временный каталог (`git init /tmp/git-internals-test`), затем `rm -rf`.
