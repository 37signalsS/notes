# Git Submodules — подмодули

## Определения

**Git Submodule (Подмодуль)** — полноценный Git-репозиторий, вложенный в другой репозиторий (родительский) в качестве подкаталога. Это позволяет использовать сторонний код, общие библиотеки или компоненты инфраструктуры, сохраняя историю коммитов каждого проекта независимой.

**`.gitmodules`** — конфигурационный файл в корне родительского репозитория в формате INI, описывающий маппинг локальных путей к URL удаленных репозиториев, веткам отслеживания и другим параметрам подмодулей.

**Gitlink** — специальный тип записи в индексе Git, содержащий только SHA-1 хеш коммита подмодуля, а не содержимое файлов.

**Detached HEAD (подмодуль)** — состояние, при котором HEAD подмодуля указывает на конкретный коммит по хешу, а не на ветку. Это стандартное состояние после `git submodule update`.

---

## Основные концепции

### Механизм отслеживания (SHA-1 Pinning)

Git не отслеживает содержимое файлов внутри подмодуля напрямую. Вместо этого родительский репозиторий хранит специальный тип записи в индексе (**gitlink**), содержащий только **конкретный SHA-1 хеш коммита**.
- Любое изменение в подмодуле требует явного обновления этого хеша в родительском проекте через `git add`.
- Это обеспечивает воспроизводимость: каждый коммит родительского проекта точно знает, какую версию зависимости он использовал.

### Уровни конфигурации

Работа с подмодулями опирается на две зоны настроек:
1. **Shared Configuration (`.gitmodules`):** Общие настройки (URL, путь, ветка), которые коммитятся и доступны всей команде. Это «декларация» зависимостей.
2. **Local Configuration (`.git/config`):** Локальная регистрация. Команда `git submodule init` копирует данные из `.gitmodules` в локальный конфиг. Это позволяет разработчику выбирать, какие именно подмодули инициализировать на своей машине.

### Формат файла `.gitmodules`

Файл использует синтаксис INI с секциями `[submodule "<путь>"]`:

```ini
[submodule "vendor/logger"]
    path = vendor/logger
    url = https://github.com/org/logger.git
    branch = main
```

Параметры:
- `path` — локальный путь к каталогу подмодуля.
- `url` — URL удаленного репозитория подмодуля.
- `branch` — ветка, которая будет отслеживаться для автоматического обновления (опционально).

Любые параметры, добавленные в секцию, копируются в `.git/config` при инициализации.

### Состояние Detached HEAD

По умолчанию после команды `git submodule update` подмодули находятся в состоянии **Detached HEAD** (отсоединенный указатель), так как они привязаны к конкретному хешу коммита, а не к ветке. Для внесения изменений необходимо явно выполнить `git checkout <branch>`.

Если настроен `branch` в `.gitmodules`, Git автоматически переключает подмодуль на указанную ветку при выполнении `git submodule update --remote`.

### Внутреннее устройство (`.git/modules/`)

В современных версиях Git служебная директория `.git` внутри подмодуля является текстовым файлом-ссылкой. Сами данные объектов и история хранятся в родительском репозитории по пути `.git/modules/<имя_подмодуля>`. Это защищает историю подмодуля от случайного удаления при манипуляциях с рабочим каталогом.

### Взаимодействие с Worktree

Подмодули в новом рабочем дереве (`git worktree add`) не инициализируются автоматически. После создания worktree требуется отдельно выполнить:
```bash
git submodule update --init --recursive
```
При этом `git worktree remove` для деревьев с подмодулями может потребовать флага `--force`.

### Взаимодействие с Stash

По умолчанию `git stash` не сохраняет изменения в подмодулях. Для этого требуется использовать флаг `--recurse-submodules` (Git 2.35+):
```bash
git stash --recurse-submodules
```

### Взаимодействие с Git Hooks

Хуки родительского репозитория не распространяются на подмодули автоматически. Каждый подмодуль имеет собственную директорию `.git/hooks` (или ссылку на нее), и для автоматизации процессов в подмодулях требуется настраивать хуки отдельно внутри каждого подмодуля или использовать скрипты, запускаемые через `git submodule foreach`.

### Сравнение с альтернативами

| Критерий | Git Submodule | Git Subtree | `requirements.yml` (Ansible) |
| :--- | :--- | :--- | :--- |
| **Хранение** | Ссылка (gitlink) на коммит | Полная копия файлов и истории | Ссылка на репозиторий (загрузка при выполнении) |
| **Размер основного репо** | Почти не увеличивается | Увеличивается | Не увеличивается |
| **Независимость истории** | Полная независимость | Интегрированная | Полная независимость |
| **Доступность офлайн** | Требуется инициализация | Полностью доступно | Требуется загрузка |
| **Сложность для коллег** | Выше (нужны доп. команды) | Нулевая (просто файлы) | Средняя (ansible-galaxy install) |
| **Идеально для** | Независимые библиотеки | Ассеты, плагины, вендоринг | Управление ролями Ansible |

## Практические сценарии

### Сценарий 1: Добавление и настройка

При добавлении рекомендуется использовать относительные пути для обеспечения переносимости между протоколами (SSH/HTTPS).

```bash
# Добавить подмодуль с относительным путем
git submodule add ../shared-libs/logger.git vendor/logger

# Настроить отслеживание конкретной ветки
git config -f .gitmodules submodule.vendor/logger.branch main

# Зафиксировать изменения
git add .gitmodules vendor/logger
git commit -m "chore: add logger submodule"
```

**Валидация:**
```bash
# Проверить содержимое .gitmodules
cat .gitmodules
# → [submodule "vendor/logger"]
#     path = vendor/logger
#     url = ../shared-libs/logger.git
#     branch = main

# Проверить, что запись в индексе — gitlink
git ls-files -s vendor/logger
# → 160000 <sha1> 0       vendor/logger
```

### Сценарий 2: Клонирование проекта

Обычный `git clone` не скачивает содержимое подмодулей.

```bash
# Клонирование со всеми вложенными зависимостями в 8 потоков
git clone --recurse-submodules -j 8 <url>

# Если проект уже склонирован без подмодулей
git submodule update --init --recursive -j 8
```

**Валидация:**
```bash
# Проверить, что подмодули инициализированы
git submodule status
# → <sha1> vendor/logger (heads/main)

# Проверить рабочую директорию подмодуля
ls -la vendor/logger/.git
# → gitdir: ../.git/modules/vendor/logger
```

### Сценарий 3: Внесение правок в подмодуль и публикация

Самая частая ошибка — забыть запушить изменения в самом подмодуле, что приводит к «битым» ссылкам у коллег.

**Алгоритм действий:**
1. **Подготовка:** Перейдите в каталог подмодуля и привяжите HEAD к ветке.
    ```bash
    cd vendor/logger
    git checkout main
    ```
2. **Правки:** Внесите изменения, протестируйте их.
3. **Фиксация в подмодуле:**
    ```bash
    git add .
    git commit -m "fix: resolve buffer overflow"
    # ОБЯЗАТЕЛЬНО: Отправьте изменения в удаленный репозиторий ПОДМОДУЛЯ
    git push origin main
    ```
4. **Фиксация в родительском проекте:**
    ```bash
    cd ../..
    # Git увидит изменение указателя (хеша)
    git add vendor/logger
    git commit -m "build: update logger dependency"
    git push
    ```

**Валидация:**
```bash
# Проверить, что хеш подмодуля обновился
git diff --submodule
# → Submodule vendor/logger <old_sha1>..<new_sha1> (main)

# Проверить, что удаленный видит тот же коммит
git ls-remote origin refs/heads/main
# → <new_sha1>        refs/heads/main
```

### Сценарий 4: Групповые операции (Foreach)

Позволяет автоматизировать действия во всех зависимостях одновременно.

```bash
# Проверить статус во всех подмодулях рекурсивно
git submodule foreach --recursive 'git status'

# Подтянуть изменения (fetch) во всех подмодулях
git submodule foreach 'git fetch'

# Выполнить произвольный скрипт сборки
git submodule foreach 'npm install && npm run build'
```

**Валидация:**
```bash
# Выполнить команду и убедиться, что она прошла во всех подмодулях
git submodule foreach 'echo "Entering $name" && git rev-parse --abbrev-ref HEAD'
# → Entering 'vendor/logger'
# → main
# → Entering 'vendor/utils'
# → main
```

### Сценарий 5: Разрешение конфликтов слияния

Конфликт возникает, когда две ветки родительского проекта указывают на разные коммиты подмодуля.

```bash
# Посмотреть разницу в хешах
git diff --submodule

# Вариант А: Выбрать одну из сторон
git checkout --theirs vendor/logger  # Взять версию из вливаемой ветки
# ИЛИ
git checkout --ours vendor/logger    # Оставить текущую версию

# Вариант Б: Ручное разрешение
cd vendor/logger
git checkout <нужный_хеш_или_ветка>
cd ../..
git add vendor/logger
```

**Валидация:**
```bash
# После разрешения проверить статус подмодуля
git status
# → updated: vendor/logger (new commits)

# И посмотреть лог коммитов подмодуля
git log --oneline -3 vendor/logger
```

### Сценарий 6: Удаление подмодуля

Требует очистки как файлов, так и конфигурации Git.

```bash
# 1. Деактивировать подмодуль в локальном конфиге
git submodule deinit -f vendor/logger

# 2. Удалить файлы и запись из .gitmodules
git rm -f vendor/logger

# 3. Очистить внутреннее хранилище (опционально)
rm -rf .git/modules/vendor/logger
```

**Валидация:**
```bash
# Проверить, что запись исчезла из .gitmodules
cat .gitmodules
# → (файл пуст или секция удалена)

# Проверить, что подмодуль больше не в индексе
git ls-files vendor/logger
# → (пусто)

# Проверить, что локальный конфиг очищен
git config --list | grep submodule
# → (подмодуль не найден)
```

### Сценарий 7: Безопасность (CVE-2024-32002)

Критическая уязвимость позволяла выполнять произвольный код при рекурсивном клонировании через манипуляции с путями и хуками.
- **Защита:** Используйте Git версии 2.45.1+ или выше.
- **Аудит:** Проверяйте файлы `.gitmodules` в сторонних проектах на наличие подозрительных путей (например, использование симлинков для подмены каталога `.git/hooks`).

### Сценарий 8: Оптимизация CI/CD

В пайплайнах часто не нужны тяжелые подмодули. Используйте параллельную загрузку и выборочную инициализацию:

```bash
# В CI/CD пайплайне: клонировать без подмодулей, затем подтянуть только нужные
git clone --depth 1 --no-checkout <url> repo
cd repo
git sparse-checkout set --no-cone src/ docs/
git checkout main

# Инициализировать только указанные подмодули
git submodule update --init vendor/logger vendor/utils -j 8
```

### Сценарий 9: Подмодули в Git Worktree

При использовании нескольких рабочих деревьев помните, что подмодули не инициализируются автоматически:

```bash
# Создать новое рабочее дерево
git worktree add ../feature-x feature-x

# Перейти в него и инициализировать подмодули
cd ../feature-x
git submodule update --init --recursive -j 8

# При удалении worktree с подмодулями
git worktree remove ../feature-x --force
```

### Сценарий 10: Stash с учетом подмодулей

По умолчанию `git stash` игнорирует изменения в подмодулях. Для сохранения текущего состояния всех зависимостей:

```bash
# Сохранить изменения в родительском проекте и всех подмодулях
git stash --recurse-submodules

# Вернуть изменения обратно
git stash pop --recurse-submodules
```

## Дополнительная информация

### Типичные ошибки и их решение

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `fatal: reference is not a tree` | Подмодуль указывает на коммит, отсутствующий в удаленном репозитории | Убедиться, что изменения в подмодуле запущены (`git push`), или выбрать другой хеш |
| `detached HEAD` (неожиданно) | Подмодуль не переключен на ветку, а привязан к хешу | Выполнить `git checkout main` внутри подмодуля или настроить `branch` в `.gitmodules` |
| `Authentication failed` при обновлении | URL подмодуля изменился или токен доступа невалиден | Выполнить `git submodule sync --recursive`, проверить credential helper |
| `path '.gitmodules' does not have a version` | Отсутствует секция `[submodule]` или файл поврежден | Проверить синтаксис `.gitmodules`, добавить недостающую секцию |
| `already exists in the index` | Подмодуль уже добавлен в индекс | Удалить запись через `git rm --cached` или `git submodule deinit` |
| `changes not staged for commit` в подмодуле | Изменения внутри подмодуля не зафиксированы | Перейти в каталог подмодуля, выполнить `git add` и `git commit` |
| `Submodule path not configured` | `.git/config` не содержит запись о подмодуле | Выполнить `git submodule init` или вручную добавить секцию в `.git/config` |
| `unable to checkout` в CI/CD | Подмодуль требует интерактивной аутентификации | Настроить SSH-ключи или токены доступа в CI/CD переменных окружения |

### Ограничения и крайние случаи

1. **Большие репозитории с множеством подмодулей:** Каждый подмодуль добавляет сложность в CI/CD пайплайнах. Для проектов с >50 подмодулями рассмотрите subtree или менеджеры пакетов.
2. **Ветвление подмодулей:** Если подмодуль используется в нескольких ветках родительского проекта с разными версиями, управление конфликтами усложняется.
3. **Мерж подмодулей:** Git не выполняет автоматический merge содержимого подмодулей — только обновление ссылок на коммиты.
4. **Бare-репозитории:** На серверах bare-репозитории не содержат рабочих деревьев, поэтому подмодули не могут быть инициализированы до клонирования.
5. **Файлы в подмодуле, игнорируемые родителем:** Если родительский `.gitignore` содержит путь к подмодулю, Git не будет отслеживать изменения gitlink.
6. **Рекурсивный depth:** Клонирование с ограничением глубины (`--depth`) совместно с `--recurse-submodules` может привести к отсутствию нужных коммитов в истории подмодулей.

### Best practices

1. **Явное указание `branch`:** Всегда настраивайте `branch` в `.gitmodules` для подмодулей, версии которых необходимо синхронизировать.
2. **Использование `absorbgitdirs`:** Выполняйте `git submodule absorbgitdirs` после добавления подмодулей для переноса `.git` данных в общее хранилище.
3. **Параллелизм:** Используйте флаг `-j` для ускорения загрузки при наличии множества подмодулей (например, `-j 8`).
4. **CI/CD кэширование:** Кэшируйте директорию `.git/modules` между запусками пайплайна.
5. **Относительные URL:** Используйте относительные пути для переносимости между SSH и HTTPS.
6. **Аудит `.gitmodules`:** Регулярно проверяйте файлы `.gitmodules` на наличие подозрительных URL или путей.
7. **Версии Git:** Поддерживайте Git 2.45.1+ для защиты от CVE-2024-32002.
8. **Альтернативы:** Если подмодули вызывают слишком много проблем, рассмотрите Git Subtree для небольших зависимостей.

### Безопасность

- **Path traversal (CVE-2024-32002):** Злоумышленник может создать вредоносный `.gitmodules` с путями, содержащими `../`, для записи хуков в `.git/hooks` при клонировании. Используйте актуальные версии Git.
- **Аудит URL:** Всегда проверяйте URL в `.gitmodules` сторонних проектов. Подмодуль может указывать на любой Git-сервер, в том числе внутренний.
- **Хуки в подмодулях:** Хуки не наследуются от родительского репозитория. Это может привести к пропуску обязательных проверок (lint, tests) в подмодулях.
- **Доступ к приватным репозиториям:** Убедитесь, что все участники команды имеют доступ ко всем подмодулям, иначе клонирование завершится ошибкой аутентификации.

### Отладка конфигурации

Чтобы увидеть состояние подмодулей и источник настроек:

```bash
# Вывод статуса всех подмодулей с хешами
git submodule status

# Показать конфигурацию конкретного подмодуля
git config -f .gitmodules --list
git config --list | grep submodule

# Проверить источник настройки URL
git config --show-origin submodule.vendor/logger.url

# Принудительное обновление URL из .gitmodules
git submodule sync --recursive

# Проверить, какие файлы относятся к подмодулям
git ls-files --stage | grep 160000

# Ремонт при проблемах с инициализацией
git submodule update --init --recursive --force
```
