# Git Submodules — подмодули

## Определения

**Git Submodule (Подмодуль)** — это полноценный Git-репозиторий, вложенный в другой репозиторий (родительский) в качестве подкаталога. Это позволяет использовать сторонний код, общие библиотеки или компоненты инфраструктуры, сохраняя историю коммитов каждого проекта независимой.

**`.gitmodules`** — конфигурационный файл в корне родительского репозитория, описывающий маппинг локальных путей к URL удаленных репозиториев и настройки отслеживания веток.

---

## Основные концепции

### Механизм отслеживания (SHA-1 Pinning)
Git не отслеживает содержимое файлов внутри подмодуля напрямую. Вместо этого родительский репозиторий хранит специальный тип записи в индексе (**gitlink**), содержащий только **конкретный SHA-1 хеш коммита**.
- Любое изменение в подмодуле требует явного обновления этого хеша в родительском проекте через `git add`.
- Это обеспечивает воспроизводимость: каждый коммит родительского проекта точно знает, какую версию зависимости он использовал.

### Уровни конфигурации
Работа с подмодулями опирается на две зоны настроек:
1. **Shared Configuration (`.gitmodules`):** Общие настройки (URL, путь, ветка), которые коммитятся и доступны всей команде. Это «декларация» зависимостей.
2. **Local Configuration (`.git/config`):** Локальная регистрация. Команда `git submodule init` копирует данные из `.gitmodules` в локальный конфиг. Это позволяет разработчику выбирать, какие именно подмодули инициализировать на своей машине.

### Состояние Detached HEAD
По умолчанию после команды `git submodule update` подмодули находятся в состоянии **Detached HEAD** (отсоединенный указатель), так как они привязаны к конкретному хешу коммита, а не к ветке. Для внесения изменений необходимо явно выполнить `git checkout <branch>`.

### Внутреннее устройство (`.git/modules/`)
В современных версиях Git служебная директория `.git` внутри подмодуля является текстовым файлом-ссылкой. Сами данные объектов и история хранятся в родительском репозитории по пути `.git/modules/<имя_подмодуля>`. Это защищает историю подмодуля от случайного удаления при манипуляциях с рабочим каталогом.

## Практические сценарии

### Сценарий 1: Добавление и настройка
При добавлении рекомендуется использовать относительные пути для обеспечения переносимости между протоколами (SSH/HTTPS).

```bash
# Добавить подмодуль с относительным путем
git submodule add ../shared-libs/logger.git vendor/logger

# Настроить отслеживание конкретной ветки
git config -f .gitmodules submodule.vendor/logger.branch main

# Зафиксировать изменения
git add .gitmodules vendor/logger
git commit -m "chore: add logger submodule"
```

### Сценарий 2: Клонирование проекта
Обычный `git clone` не скачивает содержимое подмодулей.

```bash
# Клонирование со всеми вложенными зависимостями в 8 потоков
git clone --recurse-submodules -j 8 <url>

# Если проект уже склонирован без подмодулей
git submodule update --init --recursive -j 8
```

### Сценарий 3: Внесение правок в подмодуль и публикация
Самая частая ошибка — забыть запушить изменения в самом подмодуле, что приводит к «битым» ссылкам у коллег.

**Алгоритм действий:**
1. **Подготовка:** Перейдите в каталог подмодуля и привяжите HEAD к ветке.
   ```bash
   cd vendor/logger
   git checkout main
   ```
2. **Правки:** Внесите изменения, протестируйте их.
3. **Фиксация в подмодуле:**
   ```bash
   git add .
   git commit -m "fix: resolve buffer overflow"
   # ОБЯЗАТЕЛЬНО: Отправьте изменения в удаленный репозиторий ПОДМОДУЛЯ
   git push origin main
   ```
4. **Фиксация в родительском проекте:**
   ```bash
   cd ../..
   # Git увидит изменение указателя (хеша)
   git add vendor/logger
   git commit -m "build: update logger dependency"
   git push
   ```

### Сценарий 4: Групповые операции (Foreach)
Позволяет автоматизировать действия во всех зависимостях одновременно.

```bash
# Проверить статус во всех подмодулях рекурсивно
git submodule foreach --recursive 'git status'

# Подтянуть изменения (fetch) во всех подмодулях
git submodule foreach 'git fetch'

# Выполнить произвольный скрипт сборки
git submodule foreach 'npm install && npm run build'
```

### Сценарий 5: Разрешение конфликтов слияния
Конфликт возникает, когда две ветки родительского проекта указывают на разные коммиты подмодуля.

```bash
# Посмотреть разницу в хешах
git diff --submodule

# Вариант А: Выбрать одну из сторон
git checkout --theirs vendor/logger  # Взять версию из вливаемой ветки
# ИЛИ
git checkout --ours vendor/logger    # Оставить текущую версию

# Вариант Б: Ручное разрешение
cd vendor/logger
git checkout <нужный_хеш_или_ветка>
cd ../..
git add vendor/logger
```

### Сценарий 6: Удаление подмодуля
Требует очистки как файлов, так и конфигурации Git.

```bash
# 1. Деактивировать подмодуль в локальном конфиге
git submodule deinit -f vendor/logger

# 2. Удалить файлы и запись из .gitmodules
git rm -f vendor/logger

# 3. Очистить внутреннее хранилище (опционально)
rm -rf .git/modules/vendor/logger
```

### Сценарий 7: Безопасность (CVE-2024-32002)
Критическая уязвимость позволяла выполнять произвольный код при рекурсивном клонировании через манипуляции с путями и хуками.
- **Защита:** Используйте Git версии 2.45.1+ или выше.
- **Аудит:** Проверяйте файлы `.gitmodules` в сторонних проектах на наличие подозрительных путей (например, использование симлинков для подмены каталога `.git/hooks`).

## Дополнительная информация

### Полезные команды
- `git submodule sync --recursive` — обновляет URL подмодулей в локальном конфиге, если они изменились в `.gitmodules`.
- `git submodule absorbgitdirs` — переносит `.git` данные в основное хранилище (рекомендуется для всех проектов).
- `git diff --submodule=log` — показывает список коммитов при изменении версии подмодуля.
