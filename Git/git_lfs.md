# Git LFS (Large File Storage)

## Определения

* **Git LFS (Large File Storage):** Расширение для Git, предназначенное для эффективного управления большими бинарными файлами (изображения, видео, датасеты). Оно заменяет реальные файлы в репозитории на текстовые указатели, сохраняя сами данные на удаленном LFS-сервере.

## Базовые концепции

### Механизм работы

Традиционный Git хранит полную историю всех версий каждого файла. Для тяжелых бинарных данных это приводит к экспоненциальному росту размера директории `.git`.

**Git LFS работает следующим образом:**
1. В локальном репозитории вместо файла `image.psd` (например, 500 МБ) хранится текстовый файл-указатель (Pointer File).
2. Указатель содержит версию спецификации, уникальный SHA-256 хеш (OID) и размер оригинального файла.
3. При операциях `checkout` или `pull` Git LFS перехватывает запрос и скачивает нужную версию файла с LFS-сервера в локальный кэш (`.git/lfs/objects`), после чего заменяет указатель на реальные данные.

**Пример структуры файла-указателя:**
```text
version https://git-lfs.github.com/spec/v1
oid sha256:1a2b3c4d5e6f...
size 524288000
```

### Преимущества

* **Производительность:** Клонирование репозитория происходит быстрее, так как по умолчанию скачиваются только указатели для текущей ветки.
* **Экономия места:** На диске разработчика находятся только те версии файлов, которые используются в текущем `checkout`.
* **Масштабируемость:** Позволяет хранить терабайты данных, не нарушая стабильность работы стандартных команд Git.

### Сравнение Git LFS и нативного Partial Clone

| Характеристика | Git LFS | Git Partial Clone |
| :--- | :--- | :--- |
| **Тип** | Внешнее расширение | Нативная функция Git |
| **Хранение** | Отдельный LFS-сервер | Тот же Git-сервер |
| **Механизм** | Файлы-указатели (pointers) | "Ленивая" загрузка объектов (promisor remotes) |
| **Когда использовать** | Огромные бинарные файлы (>100МБ) | Файлы любого размера, нужные выборочно |
| **Сложность** | Требует настройки `.gitattributes` | Проще в использовании (флаг при клонировании) |

## Практические сценарии

### Установка и инициализация

```bash
# Установка хуков LFS в глобальный конфиг Git (делается один раз в системе)
git lfs install
# → Updated Git hooks.
# → Git LFS initialized.
```

### Отслеживание файлов

Правила отслеживания сохраняются в файле `.gitattributes`.

```bash
# Начать отслеживание всех PSD файлов
git lfs track "*.psd"
# → Tracking "*.psd"

# Отслеживание больших текстовых файлов с поддержкой слияния (Git LFS 3.6+)
git lfs track "*.csv" --merge lfs-text
# → Tracking "*.csv"

# Добавить .gitattributes в индекс (обязательно для совместной работы)
git add .gitattributes
git commit -m "chore: configure LFS tracking"
```

### Блокировка файлов (File Locking)

Бинарные файлы невозможно эффективно объединить (merge). Чтобы избежать конфликтов при параллельной работе, используется механизм блокировки на сервере.

```bash
# Заблокировать файл для редактирования
git lfs lock design.psd
# → Locked design.psd

# Список всех заблокированных файлов в репозитории
git lfs locks
# → design.psd  User Name  ID:123

# Разблокировать файл
git lfs unlock design.psd
# → Unlocked design.psd
```

### Оптимизация для CI/CD и пакетные операции

В пайплайнах часто не нужны тяжелые файлы (например, если выполняется только линтинг кода или тесты логики).

```bash
# Пропустить загрузку LFS-объектов при клонировании (через переменную окружения)
export GIT_LFS_SKIP_SMUDGE=1
git clone https://github.com/user/repo.git

# Принудительная загрузка ВСЕХ LFS-объектов для всех веток (актуально для бэкапов)
git lfs fetch --all
# → Fetching objects: 100% (450/450), 12 GB | 15 MB/s
```

### Обслуживание и очистка

Локальный кэш LFS может быстро разрастись за счет хранения старых версий тяжелых файлов.

```bash
# Удалить старые LFS-объекты, на которые не ссылаются локальные коммиты
git lfs prune
# → 12.5 GB removed

# Проверить целостность локальных объектов (поиск битых указателей)
git lfs fsck
```

### Миграция существующих файлов

Если тяжелые файлы уже находятся в истории Git (раздувая `.git`), их нужно перенести в LFS через перезапись истории.

```bash
# Анализ истории на наличие тяжелых файлов (вывод топ-10)
git lfs migrate info --everything --top=10

# Миграция всех ZIP и MP4 файлов во всех ветках
git lfs migrate import --everything --include="*.zip,*.mp4"
# → Rewriting commits...
# → Done!

# После миграции необходим force push (опасно для общих веток!)
git push --force --all
```

## Дополнительная информация

### Ограничения и недостатки

* **Стоимость хранения:** Популярные хостинги (GitHub, GitLab) взимают плату за хранение и трафик LFS сверх бесплатных лимитов.
* **Несовместимость с GitHub Pages:** Файлы, хранящиеся в LFS, не будут отображаться на статических сайтах GitHub Pages.
* **Трудности удаления данных:** Простое удаление файла из коммита не удаляет его физически с LFS-сервера (требуется очистка через API провайдера).
* **Vendor Lock-in:** Перенос LFS-данных между разными Git-хостингами сложнее, чем перенос обычного репозитория.

### Будущее: Promisor Remotes

В современных версиях Git активно развивается механизм **Promisor Remotes** (часть Partial Clone). Он позволяет Git взаимодействовать с внешними хранилищами напрямую через нативный протокол, что в долгосрочной перспективе может сделать LFS избыточным за счет глубокой интеграции "ленивой" загрузки в ядро системы.

### Полезные команды

```bash
# Список файлов, отслеживаемых LFS в текущей ветке
git lfs ls-files
# → 1a2b3c... * image.png

# Показать объем занимаемого места в локальном кэше .git/lfs/objects
git lfs du -h
# → 1.2 GB  .git/lfs/objects

# Вывод статуса LFS в формате JSON (удобно для автоматизации)
git lfs status --json
```
