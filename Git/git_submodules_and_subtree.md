# Git Submodules и Git Subtree: Управление внешними репозиториями

## Определения

**Git Submodule (Подмодуль)** — механизм Git, позволяющий встраивать один Git-репозиторий в другой как подкаталог, сохраняя их независимые истории. Родительский репозиторий хранит только ссылку на конкретный коммит зависимости (gitlink). Подробное руководство — [git_submodules.md](./git_submodules.md).

**Git Subtree (Поддерево)** — стратегия управления зависимостями, при которой содержимое и история внешнего репозитория полностью интегрируются в основной проект. Работает на базе обычных файлов и не требует конфигурации типа `.gitmodules`.

**gitlink** — специальный тип записи в индексе Git (режим `160000`), содержащий только SHA-1 хеш коммита подмодуля. Используется для отслеживания подмодулей в родительском репозитории.

## Базовые концепции

### Когда использовать Submodules или Subtree

При разработке сложных проектов часто возникает необходимость управлять несколькими связанными репозиториями (библиотеки, общие компоненты, ассеты).

**Используйте Submodule, когда:**
- Зависимость разрабатывается независимой командой с собственным релизным циклом
- Библиотека стабильна и редко меняется
- Важно сохранить независимую историю коммитов
- Размер репозитория критичен (не хочу тащить историю зависимости)

**Используйте Subtree, когда:**
- Зависимость — ассеты, плагины или код, который должен быть доступен «из коробки»
- Разработчики не должны выполнять дополнительные команды после клонирования
- Нужно вносить правки в зависимость «на лету» без переключения контекста
- Проект использует монорепозиторий и хочет сохранить все в одном месте

### Decision Tree: выбор между Submodule и Subtree

```text
Нужна внешняя зависимость?
│
├── Да → Зависимость разрабатывается отдельной командой?
│         ├── Да → Submodule (независимые релизы, отдельная история)
│         └── Нет → Зависимость стабильна и редко меняется?
│                   ├── Да → Submodule (минимальный overhead)
│                   └── Нет → Subtree (проще для повседневной работы)
│
└── Нет → Рассмотрите встроенные зависимости (пакетные менеджеры)
```

### Git Submodule: Связанные, но независимые репозитории

Submodule позволяет включить другой репозиторий как подкаталог, но сам этот подкаталог остается отдельным репозиторием.

**Характеристики:**
- **Независимая история:** История каждого подмодуля полностью отделена.
- **Фиксация на коммите (SHA-1 Pinning):** Основной репозиторий указывает на конкретный коммит, обеспечивая стабильность.
- **Хранение конфигурации:** Настройки хранятся в файле `.gitmodules`.

**Преимущества:**
- Не увеличивает размер основного репозитория (хранится только ссылка).
- Позволяет строго фиксировать версии зависимостей.
- Хорошо подходит для огромных независимых библиотек.

**Недостатки:**
- Сложен в управлении (нужны `init`, `update`).
- Требует дополнительных действий после `clone` или `switch`.
- Риск «битых ссылок», если коммит подмодуля не был отправлен в удаленный репозиторий.

### Git Subtree: Интегрированные репозитории

Subtree интегрирует содержимое другого репозитория непосредственно в файловую структуру и историю основного проекта.

**Характеристики:**
- **Интегрированная история:** История внешнего репозитория объединяется с основной (через merge или squash).
- **Обычные файлы:** Содержимое воспринимается как обычные файлы проекта.
- **Самодостаточность:** Все файлы находятся в одном репозитории, что упрощает CI/CD и сборку.

**Преимущества:**
- Проще для потребителей: не требует специальных команд после клонирования.
- Доступно офлайн сразу после загрузки основного проекта.
- Позволяет вносить правки в зависимость «на лету» без переключения контекста.
- Единый репозиторий упрощает CI/CD — не нужно настраивать инициализацию подмодулей.

**Недостатки:**
- Увеличивает размер `.git` директории (хранит копию всех объектов зависимости).
- Операции синхронизации (`push`/`split`) могут быть медленными на больших историях.
- Сложнее отправлять правки обратно в upstream-репозиторий (требуется `split`).
- История основного проекта «загрязняется» коммитами из зависимости.

### Сравнение: Submodule vs. Subtree

| Критерий | Git Submodule | Git Subtree |
| :--- | :--- | :--- |
| **Хранение** | Ссылка (gitlink) на коммит | Полная копия файлов и истории |
| **Размер основного репо** | Почти не увеличивается | Увеличивается |
| **Независимость истории** | Полная независимость | Интегрированная |
| **Доступность офлайн** | Требуется инициализация | Полностью доступно |
| **Сложность для коллег** | Выше (нужны доп. команды) | Нулевая (просто файлы) |
| **CI/CD** | Требует `--recurse-submodules` | Обычное клонирование |
| **Откат изменений** | Простой (обновить хеш) | Требует `revert` merge-коммита |
| **Обратная отправка правок** | Простая (`cd + git push`) | Требует `split` + `push` |
| **Размер .git/modules** | Увеличивается | Не используется |
| **Идеально для** | Независимые библиотеки | Ассеты, плагины, вендоринг |

### Стратегии истории Subtree: Squash vs Non-Squash

1.  **Non-Squash (по умолчанию):** Копирует всю историю коммитов подпроекта.
    - *Плюс:* Идеальный `git bisect` — можно найти баг в зависимости в общей истории.
    - *Минус:* Экспоненциальный рост размера репозитория и «шум» в логах.
2.  **Squash (`--squash`):** Схлопывает историю зависимости в один merge-коммит.
    - *Плюс:* Основной репозиторий остается легким и чистым.
    - *Минус:* Потеря контекста изменений в коде зависимости.

### Справочник команд Subtree

| Команда | Назначение | Ключевые параметры |
| :--- | :--- | :--- |
| `git subtree add` | Добавление внешнего репозитория | `--prefix`, `--squash`, `--branch` |
| `git subtree pull` | Получение изменений из внешнего репозитория | `--prefix`, `--squash`, `--rejoin` |
| `git subtree push` | Отправка изменений обратно | `--prefix` |
| `git subtree split` | Выделение поддерева в отдельную ветку | `--prefix`, `--branch` |
| `git subtree merge` | Слияние ветки поддерева | `--prefix`, `--squash`, `--rejoin` |

**Синтаксис `git subtree add`:**
```bash
git subtree add --prefix=<путь> <URL> <ветка> [--squash] [--branch=<ветка>]
```
- `--prefix=<путь>` — относительный путь в рабочей директории (обязательный)
- `<URL>` — URL внешнего репозитория
- `<ветка>` — ветка или тег для импорта
- `--squash` — схлопнуть историю в один merge-коммит
- `--branch=<ветка>` — отслеживаемая ветка для последующих pull

## Практические сценарии

### Сценарий 1: Работа с подмодулями

- [Внесение правок](./git_submodules.md#сценарий-3-внесение-правок-в-подмодуль-и-публикация)
- [Групповые операции](./git_submodules.md#сценарий-4-групповые-операции-foreach)
- [Удаление подмодуля](./git_submodules.md#сценарий-6-удаление-подмодуля)

### Сценарий 2: Добавление поддерева (Subtree)

```bash
# Добавить внешний репозиторий в папку vendor/lib с объединением истории
git subtree add --prefix=vendor/lib https://github.com/user/lib.git main --squash

# С указанием отслеживаемой ветки для последующих pull
git subtree add --prefix=vendor/lib https://github.com/user/lib.git main --squash --branch=main
```

**Валидация:**
```bash
# Проверить, что файлы добавлены
ls vendor/lib/
# → (содержимое внешнего репозитория)

# Проверить историю коммитов
git log --oneline -3
# → a1b2c3d Squashed commit of the following:
# → e4f5g6h Add vendor/lib from https://github.com/user/lib.git
```

### Сценарий 3: Получение изменений из поддерева

```bash
# Синхронизация изменений из внешнего репозитория
git subtree pull --prefix=vendor/lib https://github.com/user/lib.git main --squash
```

**Если возник конфликт слияния:**
```bash
# 1. Разрешите конфликт в редакторе
# 2. Зафиксируйте результат
git add vendor/lib/
git commit -m "merge: resolve conflict in vendor/lib"
```

### Сценарий 4: Отправка изменений (Push/Split)

Для отправки правок обратно в репозиторий зависимости используется механизм разделения истории:

```bash
# Отправить все изменения поддерева в upstream
git subtree push --prefix=vendor/lib https://github.com/user/lib.git main
```

**Примечание:** Команда `push` автоматически выполняет `split` для выделения истории поддерева, затем отправляет результат.

### Сценарий 5: Оптимизация через --rejoin

При частых операциях `split` и `push` Git вынужден каждый раз сканировать всю историю. Используйте `--rejoin` при слиянии, чтобы создать контрольную точку:

```bash
git subtree merge --prefix=vendor/lib lib-branch --squash --rejoin
```

Это значительно ускорит последующие операции разделения истории.

**Когда использовать `--rejoin`:**
- Вы регулярно делаете `push` изменений в upstream
- История основного проекта большая (10k+ коммитов)
- Вы хотите минимизировать время выполнения `subtree split`

### Сценарий 6: Выделение поддерева в отдельную ветку (split)

Команда `split` выделяет историю определенного поддерева в отдельную ветку. Это полезно для отправки изменений обратно в upstream:

```bash
# Выделить историю vendor/lib в отдельную ветку
git subtree split --prefix=vendor/lib -b lib-only

# Результат: ветка lib-only содержит только коммиты, затрагивающие vendor/lib
git log --oneline lib-only
# → abc1234 update: add new feature to lib
# → def5678 fix: resolve bug in lib
```

**Валидация:**
```bash
# Проверить, что ветка создана
git branch -a | grep lib-only
# → lib-only

# Отправить в upstream
git push https://github.com/user/lib.git lib-only:main
```

### Сценарий 7: Удаление поддерева

Для удаления интегрированного поддерева из основного репозитория:

```bash
# 1. Удалить файлы поддерева из индекса
git rm -r vendor/lib

# 2. Зафиксировать удаление
git commit -m "remove: remove vendor/lib subtree"
```

**Примечание:** История коммитов поддерева останется в основном репозитории. Для полного удаления используйте `git filter-repo`, но это перепишет историю.

### Сценарий 8: Разрешение конфликтов при pull subtree

Если при `subtree pull` возникают конфликты слияния:

```bash
# 1. Выполнить pull с автоматическим merge (без коммита)
git subtree pull --prefix=vendor/lib https://github.com/user/lib.git main --squash --no-commit

# 2. Просмотреть конфликтные файлы
git status
# → Unmerged paths:
# → both modified: vendor/lib/src/core.js

# 3. Разрешить конфликт в редакторе
# (удалить маркеры <<<<<<<, =======, >>>>>>>)

# 4. Зафиксировать результат
git add vendor/lib/
git commit -m "merge: resolve conflict in vendor/lib"
```

## Дополнительная информация

### Типичные ошибки при работе с Subtree

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `fatal: unknown repository prefix` | Неверный или отсутствующий `--prefix` | Проверить путь; он должен быть относительным корня репозитория |
| `Don't know how to create a subtree from '...'` | Команда выполнена не из корня репозитория | Перейти в корень (`cd /path/to/repo`) перед выполнением |
| `Command did not complete successfully` | Конфликт слияния или поврежденная история | Разрешить конфликты или выполнить `git subtree merge` вручную |
| `unable to push unrelated subtree` | Upstream-репозиторий не содержит историю поддерева | Выполнить `subtree add` с того же URL перед первым `push` |
| `The prefix path '...' does not exist` | Указан несуществующий путь | Создать директорию перед `add` или проверить опечатку |
| Медленный `subtree split` | Большая история основного репозитория | Использовать `--rejoin` для создания контрольных точек |

### Типичные ошибки при работе с Submodule

Подробное описание ошибок и решений — в [git_submodules.md](./git_submodules.md#типичные-ошибки-и-их-решение).

### Технические нюансы производительности

- **Сложность `split`:** Команда `git subtree split` имеет вычислительную сложность O(N), где N — общее число коммитов в основном проекте. На гигантских репозиториях (100k+ коммитов) это может занимать минуты.
- **Альтернативы:** Для очень больших монорепозиториев рассмотрите использование `git filter-repo` или специализированных инструментов типа `copybara`.
- **Кэширование split:** Использование `--rejoin` создает ветки-контрольные точки, которые ускоряют последующие операции `split`.

### Best Practices

1. **Используйте `--squash` для subtree:** В большинстве случаев squash-стратегия предпочтительнее — она сохраняет основной репозиторий чистым.
2. **Настройте `--branch`:** Указывайте отслеживаемую ветку при `add` для упрощения последующих `pull`.
3. **Регулярно используйте `--rejoin`:** Если вы часто отправляете правки обратно в upstream.
4. **Документируйте subtree-зависимости:** В README проекта укажите URL и ветки всех subtree-зависимостей.
5. **Для подмодулей настраивайте `branch`:** Всегда указывайте параметр `branch` в `.gitmodules`.
