# Git Submodules и Git Subtree: Управление внешними репозиториями

## Определения

**Git Submodule (Подмодуль)** — механизм Git, позволяющий встраивать один Git-репозиторий в другой как подкаталог, сохраняя их независимые истории. Родительский репозиторий хранит только ссылку на конкретный коммит зависимости. Подробное руководство — [git_submodules.md](./git_submodules.md).

**Git Subtree (Поддерево)** — стратегия управления зависимостями, при которой содержимое и история внешнего репозитория полностью интегрируются в основной проект. Работает на базе обычных файлов и не требует конфигурации типа `.gitmodules`.

---

## Основные концепции

### Когда использовать Submodules или Subtree

При разработке сложных проектов часто возникает необходимость управлять несколькими связанными репозиториями (библиотеки, общие компоненты, ассеты).
- **Submodules** лучше для стабильных, редко меняющихся библиотек, разрабатываемых независимыми командами.
- **Subtree** лучше для вендоринга кода, плагинов или ассетов, которые должны быть доступны «из коробки» всем участникам без настройки окружения.

### Git Submodule: Связанные, но независимые репозитории

Submodule позволяет включить другой репозиторий как подкаталог, но сам этот подкаталог остается отдельным репозиторием.

**Характеристики:**
- **Независимая история:** История каждого подмодуля полностью отделена.
- **Фиксация на коммите (SHA-1 Pinning):** Основной репозиторий указывает на конкретный коммит, обеспечивая стабильность.
- **Хранение конфигурации:** Настройки хранятся в файле `.gitmodules`.

**Преимущества:**
- Не увеличивает размер основного репозитория (хранится только ссылка).
- Позволяет строго фиксировать версии зависимостей.
- Хорошо подходит для огромных независимых библиотек.

**Недостатки:**
- Сложен в управлении (нужны `init`, `update`).
- Требует дополнительных действий после `clone` или `switch`.
- Риск «битых ссылок», если коммит подмодуля не был отправлен в удаленный репозиторий.

### Git Subtree: Интегрированные репозитории

Subtree интегрирует содержимое другого репозитория непосредственно в файловую структуру и историю основного проекта.

**Характеристики:**
- **Интегрированная история:** История внешнего репозитория объединяется с основной (через merge или squash).
- **Обычные файлы:** Содержимое воспринимается как обычные файлы проекта.
- **Самодостаточность:** Все файлы находятся в одном репозитории, что упрощает CI/CD и сборку.

**Преимущества:**
- Проще для потребителей: не требует специальных команд после клонирования.
- Доступно офлайн сразу после загрузки основного проекта.
- Позволяет вносить правки в зависимость «на лету» без переключения контекста.

**Недостатки:**
- Увеличивает размер `.git` директории (хранит копию всех объектов зависимости).
- Операции синхронизации (`push`/`split`) могут быть медленными на больших историях.

### Сравнение: Submodule vs. Subtree

| Критерий | Git Submodule | Git Subtree |
| :--- | :--- | :--- |
| **Хранение** | Ссылка (gitlink) на коммит | Полная копия файлов и истории |
| **Размер основного репо** | Почти не увеличивается | Увеличивается |
| **Независимость истории** | Полная независимость | Интегрированная |
| **Доступность офлайн** | Требуется инициализация | Полностью доступно |
| **Сложность для коллег** | Выше (нужны доп. команды) | Нулевая (просто файлы) |
| **Идеально для** | Независимые библиотеки | Ассеты, плагины, вендоринг |

### Стратегии истории Subtree: Squash vs Non-Squash

1.  **Non-Squash (по умолчанию):** Копирует всю историю коммитов подпроекта.
    - *Плюс:* Идеальный `git bisect` — можно найти баг в зависимости в общей истории.
    - *Минус:* Экспоненциальный рост размера репозитория и «шум» в логах.
2.  **Squash (`--squash`):** Схлопывает историю зависимости в один merge-коммит.
    - *Плюс:* Основной репозиторий остается легким и чистым.
    - *Минус:* Потеря контекста изменений в коде зависимости.

## Практические сценарии

### Сценарий 1: Работа с подмодулями
Для добавления, инициализации и обновления подмодулей используйте детальные инструкции из специализированного файла:
- [Добавление подмодуля](./git_submodules.md#сценарий-1-добавление-и-настройка)
- [Обновление и синхронизация](./git_submodules.md#сценарий-3-обновление-зависимостей)

### Сценарий 2: Добавление поддерева (Subtree)
```bash
# Добавить внешний репозиторий в папку vendor/lib с объединением истории
git subtree add --prefix=vendor/lib https://github.com/user/lib.git main --squash
```

### Сценарий 3: Получение изменений из поддерева
```bash
# Синхронизация изменений из внешнего репозитория
git subtree pull --prefix=vendor/lib https://github.com/user/lib.git main --squash
```

### Сценарий 4: Отправка изменений (Push/Split)
Для отправки правок обратно в репозиторий зависимости используется механизм разделения истории:
```bash
git subtree push --prefix=vendor/lib https://github.com/user/lib.git main
```

### Сценарий 5: Оптимизация через --rejoin
При частых операциях `split` и `push` Git вынужден каждый раз сканировать всю историю. Используйте `--rejoin` при слиянии, чтобы создать контрольную точку:
```bash
git subtree merge --prefix=vendor/lib lib-branch --squash --rejoin
```
Это значительно ускорит последующие операции разделения истории.

## Дополнительная информация

### Технические нюансы производительности
- **Сложность `split`:** Команда `git subtree split` имеет вычислительную сложность $O(N)$, где $N$ — общее число коммитов в основном проекте. На гигантских репозиториях (100k+ коммитов) это может занимать минуты.
- **Альтернативы:** Для очень больших монорепозиториев рассмотрите использование `git filter-repo` или специализированных инструментов типа `copybara`.
