# Git Worktree — параллельные рабочие директории

**Актуально для:** Git 2.56+

## Определения

**Git Worktree (`git worktree`)** — механизм для одновременной работы с несколькими ветками в одном репозитории через отдельные рабочие директории (working trees). Добавлен в Git 2.5 (2015).

Репозиторий Git может поддерживать несколько рабочих деревьев. При этом различаются:

- **Основное рабочее дерево (main working tree)** — то, которое создано `git init` или `git clone`. В репозитории ровно одно (если репозиторий не bare).
- **Связанное рабочее дерево (linked working tree)** — дополнительное дерево, созданное `git worktree add`. Их может быть ноль или несколько.

**Физическая реализация:** каждое связанное дерево — это отдельный каталог с собственным файлом `.git`. В отличие от основного репозитория, этот файл является текстовым и содержит путь к метаданным в основном каталоге:

```text
gitdir: /path/to/main/.git/worktrees/<name>
```

Ключевой момент архитектуры — разделение общего и приватного состояния:

- Все рабочие деревья одного репозитория разделяют **общую директорию метаданных** `$GIT_COMMON_DIR` (для основного дерева это `.git/`, для связанных — тоже `.git/` основного репозитория). В неё входят: база объектов (`.git/objects`), общие ссылки (`refs/`, `packed-refs`), общий `.git/config`, хуки (`.git/hooks`), а также файл `.git/info/exclude`.
- Каждое дерево имеет **собственное** состояние: `HEAD`, индекс (`index`), каталог логов (`logs/`), рабочие файлы и приватный каталог административных метаданных `.git/worktrees/<name>/`.

Таким образом, объекты коммитов не дублируются между деревьями (экономия места), но история и ссылки общие, а рабочее состояние изолировано.

### Зачем нужен worktree

Worktree решает задачи, для которых `git stash` неудобен или недостаточен:

| Сценарий | stash | worktree |
|----------|-------|----------|
| Срочный баг-фикс во время работы | Да | Да (параллельно) |
| Сравнение двух веток в IDE | Нет | Да (два окна) |
| Долгая параллельная работа | Нет | Да (истинная параллельность) |
| Запуск тестов в фоне | Трудно | Да (в отдельном дереве) |
| Проверка чужого PR/ветки | Нет | Да (отдельное дерево) |
| Параллельная работа нескольких ИИ-агентов | Нет | Да (по дереву на подзадачу) |

**Worktree — это не продвинутый stash, а другая абстракция:** stash синхронен (нужно спрятать изменения, переключиться, поработать, вернуть), worktree параллелен (несколько веток доступны одновременно в разных папках). Worktree не заменяет stash полностью — для кратковременного «припрятывания» незакоммиченного кода stash остаётся более подходящим инструментом.

Сценарий параллельной работы нескольких ИИ-агентов добавляет к этому требование: каждому исполнителю нужна собственная копия проекта, иначе параллельная работа вырождается в очередь и конфликты. Само по себе дерево этой задачи не решает — механизм появился в 2015 году, задолго до агентов, — но остаётся самым дешёвым способом получить независимые рабочие каталоги в одном репозитории. Изоляция снимает конфликты правок, но не снимает слияние: какая из параллельных веток и почему попадает в основную, какой набор тестов считается эталонным — решение остаётся за человеком. Распределение ролей между оркестратором и исполнителями описано в **[Методология AI-First разработки](../AI/ai-first-development.md#многоагентная-оркестрация)**.

## Базовые концепции

### Предварительные требования и версии

**Требования к окружению:**

- Установленный Git (версия зависит от нужного набора команд — см. матрицу ниже).
- Репозиторий не должен быть bare, если вы создаёте **основное** дерево (bare-репозиторий не имеет рабочего каталога, но на его основе можно создавать связанные деревья — см. практический сценарий 4).
- Путь для нового дерева должен указывать на **не существующую** директорию (Git создаст её сам). Рекомендуется размещать деревья вне основного рабочего каталога (как сестринские директории, например `../имя-дерева`), чтобы избежать вложенности и случайного попадания файлов одного дерева под управление другого.
- Для работы с удалёнными ветками (`--guess-remote`) требуется настроенный remote (например, `origin`) и актуальные `git fetch`.

**Матрица версий функциональности worktree:**

| Функциональность | Команда / флаг | Появилось в |
|------------------|----------------|-------------|
| Базовый механизм: `add`, `list`, `lock`, `prune`, `unlock` | `git worktree ...` | Git 2.5 (2015) |
| Создание локальной ветки из удалённой при `add` | `--guess-remote` | Git 2.15 (2017) |
| Удаление и перемещение связанных деревьев | `remove`, `move` | Git 2.17 (2018) |
| Изолированная конфигурация на дерево | `extensions.worktreeConfig`, `--worktree` | Git 2.20 (2018) |
| Восстановление повреждённых связей | `repair` | Git 2.22 (2019) |
| Пустое дерево на нерождённой ветке | `--orphan` | Git 2.41 (2023) |
| Относительные пути при связывании | `--relative-paths`, `worktree.useRelativePaths` | Git 2.48 (2025) |
| Явное закрепление `info/exclude` в `$GIT_COMMON_DIR` | документация `gitignore(5)` | Git 2.55 (2026-06-29) |

> Все примеры ниже предполагают, что вы находитесь внутри основного репозитория, если не указано иное. Версия Git проверяется командой `git --version` (`# → git version 2.45.0`).

### Синтаксис и основные команды

Общий синтаксис (актуально для Git 2.56):

```text
git worktree add [-f] [--detach] [--checkout] [--lock [--reason <string>]]
                 [--orphan] [(-b | -B) <new-branch>] [--guess-remote]
                 [--relative-paths] [--track] [--quiet] <path> [<commit-ish>]
git worktree list [-v | --porcelain [-z]]
git worktree lock [--reason <string>] <worktree>
git worktree move <worktree> <new-path>
git worktree prune [-n] [-v] [--expire <expire>]
git worktree remove [-f] <worktree>
git worktree repair [<path>...]
git worktree unlock <worktree>
```

**Создание нового дерева (`add`):**

```bash
# Новое дерево на основе существующей ветки main (ветка остаётся той же)
git worktree add ../hotfix main
# → Preparing ../hotfix (checking out 'main')
# → HEAD is now at a1b2c3d Сообщение последнего коммита

# Создать НОВУЮ ветку от main и сразу связать с ней дерево
git worktree add -b new-feature ../feat main
# → Preparing ../feat (new branch 'new-feature' from 'main')
# → HEAD is now at a1b2c3d Сообщение последнего коммита

# Detached HEAD на конкретном коммите (дерево без привязки к ветке)
git worktree add --detach ../review a1b2c3d
# → Preparing ../review (detached HEAD at a1b2c3d)

# Создать локальную ветку, отслеживающую удалённую (если <branch> есть только в remote)
git worktree add --guess-remote ../pr-123 feature/pr-123
# → флаг --guess-remote доступен в Git 2.15+

# Пустое дерево на новой нерождённой ветке (без чекаута commit)
git worktree add --orphan ../docs docs
# → дерево создано пустым, ветка docs не имеет родительских коммитов
# (флаг --orphan доступен в Git 2.41+)

# Создать дерево без чекаута (для настройки sparse-checkout и т.п.)
git worktree add --no-checkout ../sparse main
# → дерево создано, но рабочие файлы не выгружены
```

Ключевые параметры `add`:

- `<path>` — обязателен; каталог не должен существовать (Git создаст его).
- `<commit-ish>` — необязателен; если не указан, берётся текущий `HEAD`. Может быть именем ветки, тега или коммита. Специальное значение `-` синонимично `@{-1}` (последнее checked-out дерево).
- `-b <new-branch>` — создать новую ветку с указанным именем (и необязательной точкой старта). По умолчанию отказывается, если ветка уже существует.
- `-B <new-branch>` — как `-b`, но пересоздаёт ветку, если она уже существует (сбрасывает её на `<commit-ish>`).
- `--detach` — создать дерево с отсоединённым `HEAD` (полезно для разового просмотра/тестирования коммита).
- `--checkout` / `--no-checkout` — по умолчанию `add` чекаутит `<commit-ish>`. `--no-checkout` подавляет чекаут, чтобы можно было настроить, например, sparse-checkout.
- `--lock` — сразу заблокировать дерево после создания (см. раздел «Управление состоянием»).
- `--orphan` — создать пустое дерево и индекс, привязав их к новому нерождённому (`unborn`) ветке с именем `<new-branch>`.
- `--guess-remote` / `--no-guess-remote` — при отсутствии `<commit-ish>`, вместо создания ветки от `HEAD`, если существует ровно одна отслеживающая ветка в remote с именем, совпадающим с basename `<path>`, базировать новую ветку на ней и пометить её как upstream. По умолчанию — отключено; включается по умолчанию через `worktree.guessRemote`.
- `--relative-paths` / `--no-relative-paths` — связывать деревья относительными или абсолютными путями (по умолчанию абсолютные). Перекрывает `worktree.useRelativePaths`.
- `--track` / `--no-track` — при создании новой ветки, если `<commit-ish>` — ветка, пометить её как upstream от новой ветки. По умолчанию включено, если `<commit-ish>` — remote-tracking branch.
- `--quiet` / `-q` — подавить обратные сообщения.
- `-f` / `--force` — пересоздать запись о дереве, если она «зависла» (stale), или создать поверх уже существующей привязки в метаданных. Для добавления пропущенного, но заблокированного дерева — `--force` дважды.

**Список активных деревьев (`list`):**

```bash
git worktree list
# → /path/to/source   a1b2c3d [main]
# → /path/to/hotfix   e5f6g7h [hotfix]

# Машинно-читаемый формат (для скриптов)
git worktree list --porcelain
# → worktree /path/to/source
# → HEAD a1b2c3d4e5f6...
# → branch refs/heads/main
# →
# → worktree /path/to/hotfix
# → HEAD e5f6g7h8i9j0...
# → branch refs/heads/hotfix
```

**Удаление (`remove` и `prune`):**

```bash
# Корректное удаление (Git 2.17+). Требует чистое дерево (нет незакоммиченных/неотслеживаемых изменений)
git worktree remove ../hotfix
# → (вывод отсутствует при успехе)

# Если дерево «грязное» (есть изменения) — принудительное удаление с потерей правок
git worktree remove -f ../hotfix

# Ручная очистка метаданных, если каталог дерева был удалён через rm -rf
git worktree prune
# → (вывод отсутствует; удаляет записи о деревьях, чьи папки исчезли)
```

> Важно: `remove` корректно очищает метаданные в `.git/worktrees/` и отвязывает ветку. Простое `rm -rf` оставляет «висячие» записи, которые затем нужно убирать командой `git worktree prune`.

### Управление состоянием (Advanced)

- **`git worktree lock`**: Предотвращает автоматическое удаление метаданных worktree сборщиком мусора (`git gc`). Полезно, если дерево находится на сетевом диске, флешке или ином временно недоступном носителе — иначе Git может посчитать его удалённым и стереть служебные данные. Также блокирует `move` и `remove`.

  ```bash
  git worktree lock ../hotfix --reason "On network drive"
  # → (вывод отсутствует; состояние зафиксировано в .git/worktrees/<name>/locked)
  git worktree unlock ../hotfix
  # → (вывод отсутствует; снимает блокировку)
  ```

- **`git worktree move`**: Перемещение рабочего дерева в новый путь. Git сам обновляет все внутренние ссылки (`gitdir`-файлы в `.git/worktrees/<name>/` и запись в основном репозитории). Не применимо к основному дереву и к деревьям с подмодулями; заблокированное дерево требует `--force` дважды.

  ```bash
  git worktree move ../hotfix ../urgent-fix
  # → (вывод отсутствует при успехе)
  ```

- **`git worktree repair`**: Исправляет повреждённые или устаревшие связи между основным репозиторием и рабочими деревьями (Git 2.22+). Типичный случай — основной каталог или само дерево были перемещены вручную без `git worktree move`, из-за чего `gitdir`-файлы стали указывать не туда. Команду можно запустить из основного дерева (чтобы восстановить исходящие связи) или изнутри перемещённого дерева (чтобы восстановить входящую связь), передавая пути к перемещённым деревьям при необходимости.

  ```bash
  # Если переместили основной репозиторий — восстанавливаем связи из него
  git worktree repair
  # Если переместили конкретное связанное дерево — запускаем внутри него
  cd ../hotfix && git worktree repair
  ```

### Привязка к ветке

Каждый worktree привязан к одной ветке. Git блокирует попытку чекаута одной и той же ветки в разных деревьях во избежание конфликтов в индексе и `HEAD` — иначе два дерева с общей базой объектов могли бы одновременно писать коммиты в одну ветку, что ведёт к состоянию гонки (race condition) и рассинхронизации.

- Чтобы открыть ветку `feature` во втором дереве, когда она уже занята первым, нужно либо освободить её в первом дереве (переключиться там на другую ветку), либо во втором дереве использовать `--detach`, чтобы получить detached HEAD без привязки к ветке:

  ```bash
  git worktree add --detach ../feature-review feature
  # → дерево открыто на коммите ветки feature, но без блокировки самой ветки
  ```

- Создание новой уникальной ветки через `-b` всегда допустимо, так как не конфликтует с уже открытыми.

## Практические сценарии

### Сценарий 1: Параллельная работа над фичей и баг-фиксом

```bash
# Текущая работа в main (незакоммиченные изменения остаются на месте)
git worktree add ../bugfix main
cd ../bugfix
# Правим баг, коммитим, пушим
git commit -am "fix: критический баг в main"
git push origin main

# Возвращаемся к основной работе — никакого stash, никаких потерь контекста
cd ../source
# Продолжаем без stash, без коммитов
```

### Сценарий 2: Эксперимент без риска

```bash
git worktree add ../experiment feature
cd ../experiment
# Пробуем радикальные изменения, не боясь сломать основную ветку
# ...эксперименты...

# После эксперимента — корректное удаление (предпочтительно)
cd ../source
git worktree remove ../experiment
# Если вместо remove использовали rm -rf, очистите метаданные:
# rm -rf ../experiment && git worktree prune
```

### Сценарий 3: Отладка через `git bisect`

Использование worktree для `bisect` позволяет не прерывать текущую разработку — основная ветка остаётся рабочей, пока вы ищете проблемный коммит в изолированном дереве:

```bash
git worktree add ../bisect-area main
cd ../bisect-area
git bisect start
git bisect bad HEAD
git bisect good v1.0.0
# Запуск тестов на каждом шаге, поиск коммита...
# После завершения:
git bisect reset
cd ../source
git worktree remove ../bisect-area
```

### Сценарий 4: Работа с Bare-репозиториями

Для серверных скриптов или CI часто удобно использовать bare-репозиторий как базу для множества рабочих деревьев. Bare-репозиторий хранит только метаданные (`.git`) и не имеет рабочего каталога, поэтому он — идеальная «чистая» основа для создания множества равноправных деревьев (production, staging, dev) на одном сервере:

```bash
git clone --bare https://github.com/user/repo.git
cd repo.git
git worktree add ../production main
git worktree add ../staging develop
# Каждое дерево теперь — независимая рабочая копия соответствующей ветки
```

Это позволяет держать метаданные отдельно от кода и легко управлять множеством окружений из одной точки.

### Сценарий 5: Проверка чужого PR / удалённой ветки

Чтобы локально запустить и проверить ветку, которая существует только на удалённом сервере (например, PR коллеги), не засоряя основное дерево:

```bash
# Обновить список удалённых веток
git fetch origin

# Создать локальную ветку, отслеживающую удалённую, и дерево для неё
git worktree add --guess-remote ../pr-123 feature/cool-feature
# → создаётся локальная ветка feature/cool-feature, отслеживающая origin/feature/cool-feature

cd ../pr-123
# Запускаем сборку, тесты, ревью кода из IDE в отдельном окне
```

### Сценарий 6: Сборка артефакта или сравнение двух веток без прерывания работы

Если нужно собрать релиз из ветки `release/1.0` или визуально сравнить её с `main`, пока текущая работа в `feature` не закончена:

```bash
git worktree add ../release-build release/1.0
cd ../release-build
# Собираем артефакт / запускаем тесты под нужной версией кода

# Из основного дерева можно сравнить ветки напрямую без переключений:
cd ../source
git diff release/1.0 main --stat
```

### Сценарий 7: Принудительная очистка «грязного» дерева

Если экспериментальное дерево содержит незакоммиченные правки, которые больше не нужны, и вы готовы их потерять:

```bash
# remove откроет для «грязного» дерева — используйте -f для принудительного удаления
git worktree remove -f ../experiment
# → незакоммиченные изменения будут безвозвратно потеряны

# Если дерево ещё и заблокировано (lock) — требуется --force дважды
git worktree remove -f -f ../experiment
```

### Сценарий 8: Отделённая документация / пустой репозиторий в старом проекте

`--orphan` создаёт дерево без исторического контекста — полезно, когда нужно отдельное рабочее пространство без привязки к существующим коммитам (например, генерация сайта, ведение документации отдельным ветвлением):

```bash
# Создать дерево с новой нерождённой веткой docs (без коммитов)
git worktree add --orphan ../docs docs
# → дерево пусто, ветка docs не имеет родительских коммитов
cd ../docs
git commit --allow-empty -m "Initial docs commit"
```

### Сценарий 9: Проверка prunable-деревьев без удаления

Перед тем как очищать метаданные, можно проверить, какие деревья Git считает пропущенными:

```bash
# Список с пометкой prunable (деревья старше --expire)
git worktree list --expire=3.months.ago
# → /path/to/source   a1b2c3d [main]
# → /path/to/old      e5f6g7h [old-feature]  prunable

# Прежде чем удалить — симуляция (ничего не удаляет)
git worktree prune --dry-run
# → Would prune /path/to/old
```

## Особенности, ограничения и технические нюансы

- **Локальность:** Worktree — сугубо локальная фича. Настройки и список деревьев не передаются через `git push` и не видны другим участникам.
- **Разделяемый `.git/info/exclude`:** Файл `.git/info/exclude` физически располагается в **общей** директории `$GIT_COMMON_DIR` (а не в приватной `$GIT_DIR` конкретного дерева), поэтому его правила исключений применяются ко **всем** рабочим деревьям репозитория. Это поведение не является нововведением какой-либо версии — оно действует во всех версиях Git с поддержкой worktree; официальная документация явно закрепила этот факт начиная с Git 2.55 (2026-06-29, коммит `bd40c65`, слитый 25 мая 2026).
- **Конфигурация:** По умолчанию все деревья используют один общий `.git/config` (переменные `core.bare` и `core.worktree`, если заданы, применяются только к основному дереву). Для разделения настроек (например, разных `user.email` для разных веток) нужно включить `extensions.worktreeConfig` (Git 2.20+):

  ```bash
  git config extensions.worktreeConfig true
  # Теперь параметры пишутся в .git/worktrees/<id>/config.worktree
  # и читаются только этим деревом через флаг --worktree
  git config --worktree user.email "feature-work@dev.com"
  ```

  > Внимание: включение `extensions.worktreeConfig` делает репозиторий нечитаемым для старых версий Git, которые откажутся с ним работать. При включении `core.worktree` и `core.bare` из общего конфига нужно перенести в `config.worktree` основного дерева.

- **Конфигурационные переменные worktree:**
  - `worktree.guessRemote` — по умолчанию включает `--guess-remote` при `git worktree add` без `<commit-ish>`.
  - `worktree.useRelativePaths` — по умолчанию false (абсолютные пути); включается флагом `--relative-paths`.
  - `gc.worktreePruneExpire` — срок, по истечении которого `git gc` удаляет метаданные пропущенных деревьев (по умолчанию `3.months.ago`).

- **Разделяемые и приватные `refs`:** Ссылки по умолчанию общие для всех деревьев, но есть исключения — `refs/bisect`, `refs/worktree` и `refs/rewritten` хранятся приватно (в `$GIT_DIR/<дерево>/refs/...`). Это позволяет, например, запускать `git bisect` в одном дереве, не мешая другому.

- **Подмодули (подробнее — в `git_submodules.md`):** Подмодули в worktree не инициализируются автоматически. Требуется `git submodule update --init --recursive` внутри каждого нового дерева. При этом `git worktree move` и `git worktree remove` для деревьев с подмодулями либо ограничены, либо требуют `--force`. Официальная рекомендация — не делать мультичекауты суперпроекта с подмодулями (экспериментальная функция).
- **Взаимодействие с хуками:** Хуки общие для всех деревьев (находятся в основной `.git/hooks`), но выполняются в контексте того дерева, где инициирована команда. Например, pre-commit запускается с рабочим каталогом и индексом именно этого дерева.
- **Вложенность:** Рекомендуется размещать связанные деревья вне основного рабочего каталога (сестринские папки). Размещение внутри рабочего дерева (вложенность) допустимо, но не рекомендуется: оно усложняет навигацию и может привести к тому, что файлы одного дерева попадут под управление другого (например, при `git add .` из родительского каталога). В ряде случаев Git может отказать в создании вложенного дерева.
- **Автоочистка метаданных:** Записи о деревьях, чьи папки исчезли (например, удалены через `rm -rf`), автоматически удаляются сборщиком мусора (`git gc`) по истечении срока, определяемого `gc.worktreePruneExpire`. Вручную это делает `git worktree prune`.

Сравнение с `git clone`:

| Критерий | git worktree | git clone |
|----------|-------------|-----------|
| Дисковое пространство | Общая база объектов (минимум) | Дублирование истории и объектов |
| Синхронизация | Общие локальные ветки и refs | Независимые репозитории |
| Изоляция настроек | Требует спец. конфига (`extensions.worktreeConfig`) | Полная по умолчанию |
| Скорость создания | Мгновенно (нет копирования истории) | Зависит от размера репозитория |
| Передача через push | Нет (локальная фича) | Да (независимый репозиторий) |

## Устранение неполадок

| Симптом / сообщение | Причина | Решение |
|---------------------|---------|---------|
| `fatal: '<branch>' is already checked out at '<path>'` | Ветка уже открыта в другом дереве | Переключитесь с неё в том дереве, либо используйте `--detach` для нового дерева, либо создайте новую ветку через `-b` |
| `fatal: '<path>' already exists` | Каталог назначения существует | Укажите несуществующий путь или удалите существующий каталог |
| `fatal: '<path>' is a working tree` | Пытаетесь создать/переместить дерево внутрь уже существующего дерева | Выберите путь вне рабочих деревьев (сестриннюю директорию) |
| `cannot move/remove a locked working tree` | Дерево заблокировано (`lock`) | `git worktree unlock <path>`, либо для `move`/`remove` добавьте `--force` дважды |
| `fatal: '<path>' is dirty, use --force` (при `remove`) | В дереве есть незакоммиченные/неотслеживаемые изменения | Закоммитьте или сбросьте изменения, либо удалите принудительно: `git worktree remove -f <path>` (правки будут потеряны) |
| `fatal: '<path>' is a main working tree` (при `move`/`remove`) | Попытка переместить/удалить основное дерево | Основное дерево нельзя переместить или удалить через worktree; перемещайте только связанные |
| Дерево исчезло с диска, но `git worktree list` всё ещё его показывает | Метаданные не очищены после ручного `rm` | Выполните `git worktree prune` из основного или любого связанного дерева |
| Связанное дерево «не видит» основной репозиторий после его перемещения | Устарели `gitdir`-ссылки | Запустите `git worktree repair` из основного репозитория (и/или из перемещённого дерева с указанием путей) |
| Дерево на сетевом диске/флешке было «потеряно» Git | Автоочистка (gc) сочла дерево удалённым | Используйте `git worktree lock --reason "..."` для защиты таких деревьев |

**Методы диагностики:**

- `git worktree list --porcelain` — показать все деревья и их состояние в машиночитаемом виде.
- `git rev-parse --git-common-dir` (из любого дерева) — убедиться, что все деревья действительно используют общий `$GIT_COMMON_DIR`.
- `git rev-parse --git-path info/exclude` — проверить, что `.git/info/exclude` разрешается в общую директорию (один и тот же файл для всех деревьев).

## Лучшие практики и очистка

- **Размещайте деревья снаружи:** создавайте их как сестринские каталоги (`../имя-задачи`), а не внутри основного рабочего каталога.
- **Используйте осмысленные имена:** привязывайте имя папки к задаче/ветке (`../hotfix-123`, `../pr-456`), чтобы легко ориентироваться в `git worktree list`.
- **Всегда удаляйте через `git worktree remove`:** это корректно очищает метаданные в `.git/worktrees/` и освобождает ветку. Простое `rm -rf` оставляет «висячие» записи — не забывайте затем `git worktree prune`.
- **Блокируйте переносимые/сетевые деревья:** если дерево находится на флешке или сетевом диске, выполняйте `git worktree lock --reason "..."`, чтобы сборщик мусора не удалил его метаданные.
- **Регулярно очищайте:** периодически запускайте `git worktree prune`, чтобы убрать записи о деревьях, удалённых вручную.
- **Не передавайте деревья через push:** worktree — локальная структура; для совместной работы используйте ветки и удалённый репозиторий.
- **Откат изменений:** чтобы полностью отменить создание дерева и вернуть окружение в исходное состояние — `git worktree remove <path>` (или `rm -rf <path> && git worktree prune`), а при необходимости и `git worktree unlock <path>`, если оно было заблокировано.
