# Git Worktree — параллельные рабочие директории

## Определения

**Git Worktree (`git worktree`)** — механизм для одновременной работы с несколькими ветками в одном репозитории через отдельные рабочие директории. Добавлен в Git 2.5 (2015).

**Физическая реализация:** Worktree создаёт новый рабочий каталог с файлом `.git`. В отличие от основного репозитория, этот файл является текстовым и содержит путь к метаданным в основном каталоге: `gitdir: /path/to/main/.git/worktrees/<name>`.
- Все worktree разделяют общую базу объектов (`.git/objects`) и индекс, но имеют собственные `HEAD`, `index` и `logs`.
- Общие настройки хранятся в `.git/config` основного репозитория.

### Зачем нужен worktree

Worktree решает задачи, для которых stash неудобен или недостаточен:

| Сценарий | stash | worktree |
|----------|-------|----------|
| Срочный баг-фикс во время работы | Да | Да (параллельно) |
| Сравнение двух веток в IDE | Нет | Да (два окна) |
| Долгая параллельная работа | Нет | Да (истинная параллельность) |
| Запуск тестов в фоне | Трудно | Да (в отдельном дереве) |

**Worktree — это не продвинутый stash, а другая абстракция:** stash синхронен, worktree параллелен.

## Базовые концепции

### Основные команды

```bash
# Создать новый worktree
git worktree add ../hotfix main        # Из ветки main
git worktree add -b new-feature ../feat # Создать новую ветку и worktree

# Список активных рабочих деревьев
git worktree list
# → /path/to/source  a1b2c3d [main]
# → /path/to/hotfix  e5f6g7h [hotfix]

# Удаление (Git 2.17+)
git worktree remove ../hotfix
# Ручное удаление (если папка удалена через rm)
git worktree prune
```

### Управление состоянием (Advanced)

*   **`git worktree lock`**: Предотвращает автоматическое удаление метаданных worktree (полезно, если дерево находится на сетевом диске или временно недоступно).
    ```bash
    git worktree lock ../hotfix --reason "On network drive"
    git worktree unlock ../hotfix
    ```
*   **`git worktree move`**: Перемещение рабочего дерева в новый путь. Обновляет все внутренние ссылки.
    ```bash
    git worktree move ../hotfix ../urgent-fix
    ```
*   **`git worktree repair`**: Исправляет поврежденные ссылки между основным репозиторием и рабочими деревьями (например, если основной каталог был перемещен).

### Привязка к ветке

Каждый worktree привязан к одной ветке. Git блокирует попытку чекаута одной и той же ветки в разных деревьях во избежание конфликтов в индексе и `HEAD`.
- Чтобы все же переключиться на ветку, которая уже занята другим деревом, нужно сначала освободить её в том дереве или использовать `--detach`.

## Практические сценарии

### Сценарий 1: Параллельная работа над фичей и баг-фиксом

```bash
# Текущая работа в main
git worktree add ../bugfix main
cd ../bugfix
# Правим баг, коммитим, пушим

# Возвращаемся к основной работе
cd ../source
# Продолжаем без stash, без коммитов
```

### Сценарий 2: Эксперимент без риска

```bash
git worktree add ../experiment feature
cd ../experiment
# Пробуем радикальные изменения, не боясь сломать основную ветку
# После эксперимента: rm -rf ../experiment && git worktree prune
```

### Сценарий 3: Отладка через `git bisect`

Использование worktree для `bisect` позволяет не прерывать текущую разработку:
```bash
git worktree add ../bisect-area main
cd ../bisect-area
git bisect start
git bisect bad HEAD
git bisect good v1.0.0
# Запуск тестов, поиск коммита...
# После завершения: git bisect reset && cd ../source && git worktree remove ../bisect-area
```

### Сценарий 4: Работа с Bare-репозиториями

Для серверных скриптов или CI часто удобно использовать bare-репозиторий как базу для множества рабочих деревьев:
```bash
git clone --bare https://github.com/user/repo.git
cd repo.git
git worktree add ../production main
git worktree add ../staging develop
```
Это позволяет держать метаданные отдельно от кода и легко управлять множеством окружений из одной точки.

## Особенности и технические нюансы

- **Локальность:** Worktree — сугубо локальная фича. Настройки и список деревьев не передаются через `git push`.
- **Разделяемый `.git/info/exclude`**: Начиная с Git 2.52+, подтверждено, что правила исключений в этом файле применяются ко **всем** рабочим деревьям репозитория.
- **Конфигурация:** По умолчанию все деревья используют один `.git/config`. Для разделения настроек (например, разных email для разных веток) нужно включить `extensions.worktreeConfig`:
  ```bash
  git config extensions.worktreeConfig true
  # Теперь можно использовать --worktree флаг
  git config --worktree user.email "feature-work@dev.com"
  ```
- **Производительность:** Все деревья используют общую базу объектов (`.git/objects`), что экономит место на диске и ускоряет создание новых деревьев по сравнению с `git clone`.
- **Submodules:** Подмодули в worktree не инициализируются автоматически. Требуется `git submodule update --init --recursive` внутри каждого нового дерева.
- **Взаимодействие с хуками:** Pre-commit и другие хуки срабатывают в контексте того дерева, где инициирована команда.
- **Безопасность:** Не забывайте выполнять `git worktree remove` вместо простого `rm -rf`, чтобы Git корректно очистил метаданные в `.git/worktrees/`.

Сравнение с `git clone`:

| Критерий | git worktree | git clone |
|----------|-------------|-----------|
| Дисковое пространство | Общая база объектов (минимум) | Дублирование истории и объектов |
| Синхронизация | Общие локальные ветки и refs | Независимые репозитории |
| Изоляция настроек | Требует спец. конфига | Полная по умолчанию |
| Скорость создания | Мгновенно | Зависит от размера репозитория |
