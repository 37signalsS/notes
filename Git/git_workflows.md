# Рабочие процессы в Git

## Определения

**Рабочий процесс Git (Git Workflow)** — это согласованный набор правил и шагов, который определяет, как команда разработчиков использует Git для совместной работы над кодом. Он регламентирует управление ветками, внесение изменений и выпуск релизов, обеспечивая предсказуемость и эффективность разработки.

**Модель ветвления (Branching Model)** — это ключевая часть рабочего процесса, представляющая собой стратегию создания, именования и слияния веток в репозитории. Популярные модели включают Git Flow, GitHub Flow и Trunk-Based Development.

**Pull/Merge Request (PR/MR)** — это центральный механизм совместной работы в большинстве современных Git-платформ (GitHub, GitLab, Bitbucket). Он представляет собой формальный запрос на слияние изменений из одной ветки в другую, позволяя проводить код-ревью, обсуждение и автоматизированное тестирование перед интеграцией кода.

## Основные концепции

### Pull/Merge Request как центр совместной работы

PR/MR является не просто технической операцией, а ядром коммуникации в команде.

> **Почему все изменения попадают в один Pull Request?**
> PR/MR создается для **ветки**, а не для отдельных коммитов. Он представляет собой всю совокупность изменений в вашей ветке, которых нет в целевой. Это позволяет команде рассматривать и обсуждать фичу или исправление как единое целое.

Процесс код-ревью в рамках PR/MR включает следующие шаги:
1.  **Отправка ветки:** Разработчик публикует свою локальную ветку на удаленном сервере.
2.  **Создание PR/MR:** Через веб-интерфейс или CLI создается запрос на слияние.
3.  **Код-ревью и обсуждение:** Коллеги изучают изменения, оставляют комментарии, одобряют или запрашивают доработки.
4.  **Автоматизированные проверки (CI):** Система CI/CD запускает тесты, линтеры и другие проверки.
5.  **Слияние:** После одобрения и успешного прохождения всех проверок ветка сливается в целевую.

### Принцип единого артефакта

Это один из ключевых принципов CI/CD, который гласит, что **один и тот же артефакт** (например, Docker-образ или бинарный файл) должен проходить через все этапы тестирования и развертывания, от `dev` до `production`.

*   **Проблема при нарушении:** В классическом Git Flow артефакт для `staging` может быть собран из ветки `develop`, а для `production` — из `main`. Так как кодовая база в этих ветках может различаться (например, из-за срочного `hotfix` в `main`), артефакты получаются разными. Это создает риск, что код, успешно протестированный на `staging`, поведет себя иначе в `production`.

*   **Решение (Современная адаптация):**
    1.  Артефакт собирается **один раз** на раннем этапе (например, после слияния `feature`-ветки в `develop`).
    2.  Затем **этот же самый, неизменяемый артефакт** "продвигается" по всем окружениям: `dev` → `staging` → `production`.
    3.  Ветка `main` в этом случае используется не для сборки, а как **указатель на версию кода**, соответствующую развернутому в `production` артефакту.

### Feature Flags (Флаги фич)

**Feature Flags** — это механизм, который позволяет включать или выключать функциональность в приложении без изменения кода и развертывания новых версий. Это мощная техника, которая позволяет безопасно интегрировать незавершенный код в основную ветку, не затрагивая пользователей. Она является неотъемлемой частью Trunk-Based Development, но может применяться и в других рабочих процессах.

## Практические сценарии: Модели ветвления

### 1. Git Flow

Строгая модель ветвления, которая хорошо подходит для проектов с запланированными релизами.

*   **Основные ветки:**
    *   `main` (или `master`): Хранит только стабильный, готовый к выпуску код.
    *   `develop`: Основная ветка для разработки, в которой аккумулируются все завершенные фичи.
*   **Вспомогательные ветки:**
    *   `feature/*`: Для разработки новых функций (от `develop`).
    *   `release/*`: Для подготовки релиза и исправления багов (от `develop`).
    *   `hotfix/*`: Для срочных исправлений в `production` (от `main`).

**Процесс:** Фичи разрабатываются в `feature`-ветках и через PR/MR вливаются в `develop`. Когда `develop` готова к релизу, создается `release`-ветка. После стабилизации она вливается в `main` (с созданием тега релиза) и обратно в `develop`.

### 2. GitHub Flow

Более простая и легковесная модель, оптимизированная для непрерывной доставки (Continuous Delivery).

*   **Принципы:**
    *   Ветка `main` всегда готова к развертыванию.
    *   Любые изменения вносятся через `feature`-ветки, созданные от `main`.
    *   Изменения развертываются на тестовом окружении и проверяются **до слияния** в `main`.
*   **Процесс:** После слияния одобренного PR в `main` автоматически запускается развертывание в `production`.

### 3. Trunk-Based Development (TBD)

Самый динамичный подход, при котором все разработчики работают с единой основной веткой (`trunk`, обычно `main`), интегрируя изменения очень часто через короткоживущие ветки (существующие не более нескольких часов или дней).

*   **Принципы:**
    *   `main` — единственный источник правды.
    *   Непрерывная интеграция (CI) обязательна для каждого коммита в `main`.
    *   Новая или нестабильная функциональность скрывается за **Feature Flags**.

### 4. Forking Workflow (Работа через форки)

Модель, стандартная для open-source проектов. Вместо одного общего репозитория каждый разработчик работает в собственном серверном репозитории — **форке**.

*   **Процесс:**
    1.  Разработчик создает **форк** (полную копию) основного репозитория.
    2.  Клонирует свой форк локально. Локальный репозиторий имеет два `remote`: `origin` (свой форк) и `upstream` (основной проект).
    3.  Изменения вносятся в ветки и отправляются в `origin`.
    4.  Для предложения изменений в основной проект создается **Pull Request** из форка.
*   **Преимущество:** Мейнтейнеры получают чистую историю коммитов, так как вся "грязная" работа остается в форках контрибьюторов.

### Инструменты CLI для работы с PR/MR

Для управления PR/MR из командной строки существуют официальные утилиты.

#### GitHub CLI (`gh`)

```bash
# Создать Pull Request (интерактивно или из коммитов)
gh pr create --fill --web

# Посмотреть список PR
gh pr list

# "Скачать" ветку PR для локального тестирования
gh pr checkout <номер_PR>

# Посмотреть изменения в PR
gh pr diff <номер_PR>

# Одобрить PR
gh pr review <номер_PR> --approve
```

#### GitLab CLI (`glab`)

```bash
# Создать Merge Request (интерактивно или из коммитов)
glab mr create -f -w

# Посмотреть список MR
glab mr list

# "Скачать" ветку MR
glab mr checkout <номер_MR>

# Посмотреть изменения в MR
glab mr diff <номер_MR>

# Одобрить MR
glab mr approve <номер_MR>
```
