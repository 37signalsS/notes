# Рабочие процессы в Git: от Pull Request до Git Flow

Эффективная совместная работа в Git строится на основе согласованных рабочих процессов (workflows). Они определяют, как команда управляет ветками, вносит изменения и выпускает релизы.

## Основа совместной работы: Pull/Merge Request

Центральным элементом большинства современных рабочих процессов является механизм **Pull Request** (PR) на GitHub/Bitbucket или **Merge Request** (MR) на GitLab. Это запрос на слияние изменений из одной ветки в другую (например, из вашей `feature`-ветки в общую `develop`).

> **Почему все изменения попадают в один Pull Request?**
> 
> PR/MR создается для **ветки**, а не для отдельных коммитов. Он представляет собой всю совокупность изменений в вашей ветке, которых нет в целевой. Это позволяет команде рассматривать и обсуждать фичу или исправление как единое целое.

### Процесс создания PR/MR и код-ревью

1.  **Отправка ветки:** Вы отправляете свою локальную ветку на удаленный сервер.
    ```bash
    git push --set-upstream origin имя-вашей-ветки
    ```

2.  **Создание PR/MR:** Вы создаете PR/MR через веб-интерфейс или с помощью CLI-утилит.

3.  **Код-ревью:** Коллеги просматривают ваши изменения, оставляют комментарии и либо одобряют их, либо запрашивают доработки.

4.  **Слияние:** После одобрения ветка сливается в целевую.

### Инструменты CLI для PR/MR

#### GitHub CLI (`gh`)

Официальная утилита от GitHub.

1.  **Создание PR:**
    ```bash
    # Интерактивный режим
    gh pr create
    # Сразу заполнить из коммитов и открыть в браузере
    gh pr create --fill --web
    ```

2.  **Процесс ревью:**
    ```bash
    # Посмотреть список PR
    gh pr list
    # "Скачать" ветку PR для локального тестирования
    gh pr checkout <номер_PR>
    # Посмотреть изменения
    gh pr diff <номер_PR>
    # Одобрить
    gh pr review <номер_PR> --approve
    # Запросить изменения
    gh pr review <номер_PR> --request-changes -b "Комментарии"
    ```

#### GitLab CLI (`glab`)

Официальная утилита для GitLab.

1.  **Создание MR:**
    ```bash
    # Интерактивный режим
    glab mr create
    # Сразу заполнить и открыть в браузере
    glab mr create -f -w
    ```

2.  **Процесс ревью:**
    ```bash
    # Посмотреть список MR
    glab mr list
    # "Скачать" ветку MR
    glab mr checkout <номер_MR>
    # Посмотреть изменения
    glab mr diff <номер_MR>
    # Одобрить
    glab mr approve <номер_MR>
    ```

## Модели ветвления: Git Flow, GitHub Flow и Trunk-Based Development

Существует несколько популярных моделей ветвления, каждая из которых подходит для разных типов проектов и команд. Основные из них — Git Flow, GitHub Flow и Trunk-Based Development. Выбор модели влияет на скорость разработки, стабильность релизов и сложность совместной работы.

---

## 1. Git Flow

Git Flow — это одна из классических и строгих моделей ветвления, которая хорошо подходит для проектов с запланированными релизами.

### Основные ветки

*   `main` (или `master`): Хранит только стабильный, "боевой" код (production-ready). Прямые коммиты в эту ветку запрещены.
*   `develop`: Основная ветка для разработки. В ней аккумулируются все завершенные фичи для следующего релиза.

### Вспомогательные ветки

*   **`feature/*`**: Создаются от `develop`. В них ведется разработка новых функций. После завершения сливаются обратно в `develop`.
*   **`release/*`**: Создаются от `develop`, когда планируется новый релиз. В этой ветке происходит только исправление багов и подготовка к выпуску. После релиза сливается и в `main`, и в `develop`.
*   **`hotfix/*`**: Создаются от `main` для срочных исправлений в продакшене. После завершения сливаются и в `main`, и в `develop`.

### Визуальная схема

```
      hotfix/*
         |
main ------o-----------o-------------------o----->
         / \
       /   \       /   \
release/*   \       /   \         release/*
       |     \     /     \           |
develop ---o----o---o---o---o---o---o---o--->
         \ / \ / \ / \ / \ / \ / \ / \ 
 feature/*     feature/*     feature/*
```

### Процесс разработки по Git Flow

1.  **Feature Branch:** Разработка ведется в отдельной `feature`-ветке, созданной от `develop`.
2.  **Pull/Merge Request (PR/MR):** По завершении работы создается PR в `develop`.
3.  **CI/CD и ревью:** Автоматически запускаются тесты. Код просматривают ревьюеры.
4.  **Merge:** После одобрения ветка сливается в `develop`.
5.  **Release Branch:** Когда `develop` содержит достаточно фич для релиза, от нее создается `release`-ветка.
6.  **Релиз:** После стабилизации `release`-ветка сливается в `main` (ставится тег релиза) и в `develop` (чтобы исправления из `release` попали в разработку).

### Критика и практические соображения: Принцип единого артефакта

Несмотря на свою структурированность, классический Git Flow в его строгом виде может нарушать один из ключевых принципов CI/CD — **принцип единого, неизменяемого артефакта**.

*   **Проблема:** В Git Flow артефакт для `staging`-окружения часто собирается из ветки `develop` (или `release`), а артефакт для `production` — из ветки `main`. Это **два разных артефакта**, собранных в разное время из разных состояний кода. Между этими сборками в `main` мог попасть срочный `hotfix`, которого нет в `develop`, что приводит к рассинхронизации. Вы не можете быть на 100% уверены, что то, что вы протестировали в `staging`, идентично тому, что будет работать в `production`.

*   **Решение (Современная адаптация):** Чтобы следовать принципу единого артефакта, процесс должен быть изменен.
    1.  Артефакт (например, Docker-образ) собирается **один раз** на раннем этапе — например, после слияния feature-ветки в `develop`.
    2.  Затем **этот же самый, неизменяемый артефакт** "продвигается" по всем окружениям: `dev` -> `staging` -> `production`.
    3.  В этом случае ветка `main` используется не для сборки, а скорее как **указатель на версию кода**, соответствующую развернутому в production артефакту. Слияние в `main` означает не "собрать и развернуть", а "этот код теперь в production".

Такой подход сохраняет порядок, привносимый Git Flow, но делает процесс развертывания более надежным и предсказуемым.

## 2. GitHub Flow

GitHub Flow — это более простая и легковесная альтернатива Git Flow, оптимизированная для команд, практикующих непрерывную доставку (Continuous Delivery).

### Основные принципы:
*   Ветка `main` **всегда готова к развертыванию** (deployable).
*   Любые изменения вносятся через `feature`-ветки, созданные от `main`.
*   Изменения тестируются и проверяются **до слияния** в `main`.

### Процесс разработки:
1.  **Создание ветки:** Для любой новой задачи (фича, багфикс) создается ветка с описательным названием от `main`.
2.  **Коммиты:** Разработчик делает коммиты в эту ветку.
3.  **Pull Request:** Как только ветка готова к ревью, создается Pull Request в `main`. Это начало обсуждения.
4.  **Ревью и обсуждение:** Команда обсуждает изменения и проводит код-ревью.
5.  **Тестирование:** Изменения из ветки развертываются в тестовом окружении для проверки.
6.  **Слияние:** После одобрения и успешного тестирования ветка сливается в `main`.
7.  **Развертывание:** Слияние в `main` автоматически запускает развертывание в продакшн.

Этот подход проще, чем Git Flow, и идеально подходит для веб-приложений и сервисов, где релизы происходят часто и без строгого графика.

## 3. Trunk-Based Development (TBD)

Trunk-Based Development (TBD) — это практика, при которой все разработчики работают с единой основной веткой (`trunk`, обычно `main`), внося изменения через очень короткоживущие ветки или напрямую. Это самый динамичный подход, требующий высокого уровня автоматизации.

### Основные принципы:
*   **Единственный источник правды:** `main` — это единственная основная ветка. Нет долгоживущих веток вроде `develop`.
*   **Короткоживущие ветки:** Ветки для фич существуют не более нескольких дней (в идеале — меньше дня), после чего сливаются в `main`.
*   **Непрерывная интеграция (CI):** Каждое слияние с `main` должно проходить через автоматизированную сборку и полный набор тестов. "Сломанный" `main` — это критическая проблема, которую нужно исправлять немедленно.
*   **Feature Flags (флаги фич):** Новая функциональность скрывается за флагами. Это позволяет сливать в `main` даже незаконченный код, не влияя на стабильность продакшена. Фичу "включают" для пользователей только тогда, когда она полностью готова.

### Сравнение с Git Flow:
*   **Простота:** TBD значительно проще, так как нет сложной структуры из множества веток (`release`, `hotfix`).
*   **Скорость:** Способствует очень быстрой доставке изменений и сокращает цикл обратной связи.
*   **Требования:** Требует зрелой инженерной культуры, мощной системы CI/CD и активного использования feature-флагов.

## 4. Forking Workflow (Работа через форки)

Работа через форки принципиально отличается от других популярных методов. Вместо того чтобы использовать один серверный репозиторий, где все разработчики имеют право на push в feature-ветки, здесь каждый разработчик получает свой собственный, независимый серверный репозиторий — **форк**.

Эта модель является стандартом де-факто для крупных публичных open-source проектов (например, на GitHub).

### Основные принципы:

*   **У каждого свой репозиторий:** Каждый разработчик "форкает" (создает полную копию) основного репозитория. Эта копия принадлежит разработчику, и он имеет полный контроль над ней.
*   **Два удаленных репозитория:** Локальная копия разработчика обычно имеет два `remote`:
    *   `origin`: Указывает на его собственный форк (куда он может свободно пушить).
    *   `upstream`: Указывает на основной, "родительский" репозиторий (откуда он забирает обновления).
*   **Pull Request — единственный путь в основной репозиторий:** Никто, кроме мейнтейнеров, не может пушить напрямую в основной репозиторий. Все изменения предлагаются через Pull Request из форка разработчика.

### Процесс разработки:

1.  **Fork:** Разработчик один раз создает форк основного репозитория.
2.  **Clone:** Клонирует свой форк на локальную машину.
3.  **Sync:** Регулярно синхронизирует свою `main` ветку с `upstream/main`, чтобы получать последние изменения.
4.  **Branch:** Создает feature-ветку для новой задачи.
5.  **Push:** Отправляет изменения в свой собственный репозиторий (`origin`).
6.  **Pull Request:** Когда работа готова, создает Pull Request из своего форка в основной репозиторий.
7.  **Review и Merge:** Мейнтейнер проекта рецензирует PR и, если все в порядке, сливает его в основной репозиторий.

Основное преимущество этого подхода — **чистота и безопасность центрального репозитория**. Вся "грязная" работа, эксперименты и промежуточные коммиты остаются в форках разработчиков, не загрязняя историю основного проекта.
