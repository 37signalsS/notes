# Рабочие процессы в Git

## Определения

**Рабочий процесс Git (Git Workflow)** — согласованный набор правил и шагов, определяющий, как команда разработчиков использует Git для совместной работы. Он регламентирует управление ветками, внесение изменений и выпуск релизов.

**Модель ветвления (Branching Model)** — стратегия создания, именования и слияния веток в репозитории. Основные цели использования моделей:
* **Организация рабочего процесса:** задает четкие правила именования, создания веток и слияния кода, обеспечивая дисциплину в команде.
* **Параллельная разработка:** позволяет разработчикам работать над разными задачами в изолированных ветках, минимизируя блокировки и конфликты слияния (Merge Hell).
* **Изоляция кода:** защита стабильных веток (`main`, `production`) от недописанного или сломанного функционала.
* **Управление релизами:** упрощает выпуск исправлений (Hotfixes) для старых версий без остановки разработки новых фич.
* **Интеграция CI/CD:** создает естественные точки для автоматических проверок (тесты, линтеры) и код-ревью перед интеграцией в основную ветку.

**Pull/Merge Request (PR/MR)** — механизм совместной работы на Git-платформах (GitHub, GitLab), представляющий собой запрос на слияние изменений из одной ветки в другую с возможностью код-ревью и автоматизированных проверок.

---

## Базовые концепции

### Механизм Pull/Merge Request

PR/MR создается для **ветки**, а не для отдельных коммитов. Это позволяет рассматривать совокупность изменений как единую логическую задачу (фичу или багфикс).

**Процесс интеграции через PR/MR:**
1. **Публикация ветки:** Разработчик отправляет локальную ветку на сервер.
2. **Создание запроса:** Инициация PR/MR через веб-интерфейс или CLI.
3. **Автоматизация (CI):** Запуск тестов, линтеров и проверок безопасности.
4. **Код-ревью:** Обсуждение кода коллегами, внесение правок.
5. **Одобрение (Approve):** Подтверждение готовности кода к слиянию.
6. **Слияние (Merge):** Интеграция кода в целевую ветку и автоматическое закрытие PR/MR.

### Методы слияния Pull/Merge Request (Merge Strategies)

При закрытии PR/MR платформы предлагают различные стратегии интеграции, влияющие на историю:

* **Create a merge commit (Стандартный Merge):** Все коммиты фича-ветки добавляются в `main`, создается коммит слияния.
  * *Плюсы:* Сохраняется полная история работы и контекст ветки.
  * *Минусы:* История `main` может стать слишком "шумной" из-за мелких промежуточных коммитов (wip, fix typo).
* **Squash and merge (Объединение):** Все коммиты фича-ветки "схлопываются" в один новый коммит, который добавляется в `main`.
  * *Плюсы:* Идеально чистая, линейная история `main`. Один PR = один коммит.
  * *Минусы:* Теряется детализированная история разработки внутри самой фичи.
* **Rebase and merge (Перебазирование):** Коммиты фича-ветки переносятся поверх `main` (меняются хэши) без создания коммита слияния (Fast-Forward).
  * *Плюсы:* Линейная история, сохраняющая отдельные логические шаги (если они были хорошо оформлены).
  * *Минусы:* Требует идеальной дисциплины коммитов от разработчика.

### Лучшие практики проведения Code Review

* **Малый размер:** Оптимальный размер PR — до 400 строк кода. Большие изменения сложнее анализировать, что приводит к поверхностному ревью ("LGTM").
* **Понятное описание:** PR должен отвечать на вопросы "Зачем это сделано?" и "Как это работает?".
* **Единая цель:** Один PR решает строго одну задачу. Не смешивайте рефакторинг и реализацию новой фичи в одном запросе.

### Принцип единого артефакта

Один и тот же артефакт (Docker-образ, бинарный файл) должен проходить через все этапы (Dev → Staging → Prod) без пересборки.

* **Проблема:** Если собирать артефакт для Prod из `main`, а для Staging из `develop`, существует риск несоответствия кода из-за случайных изменений или разницы в окружении сборки.
* **Решение:** Артефакт собирается один раз (например, при создании тега или слиянии в `develop`), помечается версией и продвигается по конвейеру. Ветка `main` в таком случае служит указателем на текущую стабильную версию.

### Флаги функциональности (Feature Flags)

Механизм, позволяющий интегрировать незавершенный код в основную ветку, скрывая его от пользователей в рантайме. Это позволяет избежать долгоживущих веток и "ада слияния" (merge hell).

Подробно: [Feature Toggles — обзор](../CI-CD/Testing/feature_toggles/overview.md).

## Модели ветвления

### 1. Git Flow (Классическая модель)

Строгая, многоуровневая модель для проектов с фиксированным циклом релизов (десктопное ПО, мобильные приложения, Enterprise). Популярность составляет около 20% рынка. Релиз в этой модели воспринимается как значимое событие ("Event").

* **Ветки:**
  * `main` — только стабильный код production-качества.
  * `develop` — основная ветка для интеграции завершенных фич.
  * `feature/*` — разработка новых функций (от `develop`).
  * `release/*` — подготовка релиза, багфиксы перед выпуском (от `develop`).
  * `hotfix/*` — срочные исправления в production (от `main`).
* **Плюсы:**
  * **Изоляция процессов:** возможность одновременно исправлять баги в проде, готовить следующий релиз и разрабатывать новые фичи.
  * **Структурированность:** каждая ветка имеет строго определенную роль, что упрощает онбординг в крупных проектах.
  * **Поддержка нескольких версий:** идеальна для Long Term Support (LTS) и сценариев, когда нужно поддерживать версию 2.x, одновременно работая над 3.x (например, критический багфикс в версии 2.3 при активной разработке 3.0).
  * **Регулируемые отрасли:** жесткая структура и явные ветки релизов облегчают аудит и обеспечение отслеживаемости (traceability) изменений.
* **Минусы:**
  * **Сложность и избыточность:** слишком много ручных действий и накладных расходов на управление ветками ("Branch Overhead").
  * **Медленная поставка:** низкий Time-to-Market из-за долгоживущих веток и многоступенчатого процесса слияний (интеграционный ад).
  * **Устаревание:** сам автор модели позже признал, что Git Flow не подходит для веб-приложений с непрерывной доставкой (Continuous Delivery), так как создает лишние задержки.
  * **Бюрократизация:** требует строгого соблюдения дисциплины, иначе структура веток превращается в хаос.

**Практический пример работы (чистый Git):**
```bash
# Старт новой фичи
git switch develop
git switch -c feature/auth

# Завершение фичи (через CLI или MR/PR)
git switch develop
git merge --no-ff feature/auth # Принудительный merge commit для сохранения контекста
git branch -d feature/auth

# Старт релиза
git switch -c release/1.2.0 develop
# ... внесение исправлений ...

# Завершение релиза (вливается и в main, и обратно в develop)
git switch main
git merge --no-ff release/1.2.0
git tag -a v1.2.0 -m "Release 1.2.0"
git switch develop
git merge --no-ff release/1.2.0
```


### 2. GitHub Flow (Непрерывная доставка)

Максимально простая и самая популярная модель (40–50% рынка). Идеально подходит для веб-приложений, SaaS и Open Source проектов с Continuous Delivery.

* **Принципы:**
  * `main` (или `master`) — всегда стабильная ветка, готовая к развертыванию.
  * Все изменения вносятся через короткоживущие ветки от `main`.
  * Слияние в `main` происходит только после успешного ревью и прохождения CI.
  * Деплой в Production происходит сразу после слияния в `main` (или явно по событию создания **тега**).
* **Плюсы:**
  * **Простота:** минимум правил, понятный процесс даже для новичков.
  * **Теги и стабильность:** тег на `main` ветке служит "снимком" стабильного состояния. Триггеры деплоя на теги защищают от случайного выката кода из мастера.
  * **Минимум PR:** одна фича — один PR, что уменьшает конфликты и очередь слияния.
  * **Скорость:** позволяет доставить фикс или фичу в продакшн максимально быстро (например, исправление бага к обеду).
* **Минусы и вызовы:**
  * **Требования к дисциплине:** культура команды критична — Pull Request'ы не должны быть "необязательными предложениями", а тесты — "забытым домашним заданием".
  * **Масштабирование:** при работе нескольких команд над одной кодовой базой возможны конфликты и сложности в координации ("наступание на пятки").
  * **Отсутствие поддержки версий:** модель рассчитана на наличие только одной (последней) версии в продакшене.
* **Особенности QA:** позволяет реализовать тестирование на отдельном временном стенде (Preview Environment) для каждой фича-ветки еще до слияния в основную ветку. Любая ошибка в `main` останавливает весь конвейер поставки.

### 3. GitLab Flow (Окружения и релизы)

Гибридная модель, ориентированная на соответствие кода инфраструктурным окружениям. Популярна в компаниях с жестким контролем качества и комплаенсом (банки, MedTech). Рыночная доля составляет 10–15%.

* **Принципы:**
  * Код продвигается строго последовательно по веткам окружений: `main` → `test` → `pre-production` → `production`.
  * Каждая ветка жестко привязана к конкретному стенду (ветка окружения = состояние окружения).
  * Для коробочного ПО используются стабильные ветки релизов (например, `2.1-stable`), куда вносятся только критические исправления (cherry-pick из `main`).
* **Плюсы:**
  * **Прозрачность:** состояние ветки всегда равно состоянию окружения; точно понятно, какой код где развернут.
  * **Безопасность:** многоступенчатая защита от случайных релизов — код обязательно проходит через предварительные стенды.
  * **Гибкость:** позволяет поддерживать несколько версий продукта параллельно.
* **Минусы:**
  * **Сложность процесса:** продвижение кода требует строгого соблюдения порядка слияний.
  * **Бюрократизация:** избыточность для маленьких проектов или стартапов с быстрым циклом разработки.
  * **Ручные действия:** часто требует участия релиз-инженера для контроля продвижения изменений по веткам.
* **Подробное описание:** см. в **[руководстве по GitLab Flow](../CI-CD/GitLab_CI/Tutorials/gitlab_flow.md)**.

### 4. Trunk-Based Development (Высокая динамика)

"Формула-1" в мире ветвления: работа в единой основной ветке с максимально быстрой интеграцией. Используется высокопроизводительными командами (20–30% рынка).

* **Принципы:**
  * Разработчики вливают изменения в `main` (trunk) несколько раз в день (непрерывная интеграция).
  * Ветки живут считанные часы (максимум полдня-день).
  * Использование **Feature Flags** (фиче-флагов) обязательно для скрытия незавершенного функционала (код в проде, но функционал выключен).
* **Плюсы:**
  * **Максимальная скорость:** согласно отчету DORA, команды использующие TBD показывают лучшие результаты по всем ключевым метрикам:
      * **Deployment Frequency** (Частота деплоев) — значительно выше.
      * **Lead Time for Changes** (Время цикла изменений) — значительно ниже.
      * **Change Failure Rate** (Доля неудачных изменений) — ниже за счет маленьких коммитов.
      * **Time to Restore Service** (Время восстановления) — значительно быстрее.
  * **Отсутствие Merge Hell:** конфликты решаются мгновенно, так как код интегрируется маленькими порциями.
  * **Быстрый фидбек:** разработчики сразу видят результат своей работы и реакцию системы (короткие петли обратной связи).

  **Практический пример (TBD + Feature Flags):**
  Три разработчика работают над функционалом корзины (checkout). Они ежедневно вливают небольшие части кода в `main`. Код попадает в продакшн, но скрыт от пользователей с помощью **фиче-флага**. Когда разработка завершена (например, в пятницу), флаг переключается, и функционал становится доступен всем. Это исключает гигантские конфликты слияния в конце недели.
* **Минусы и риски:**
  * **Высокие риски:** любой коммит может сломать Production без "непробиваемых" автоматических проверок. Не подходит при отсутствии качественного тестового покрытия.
  * **Культурный сдвиг:** требует изменения мышления — разработчики должны уметь разбивать задачи на мелкие коммиты и работать с фиче-флагами.
  * **Требования к опытности:** неопытные разработчики без должного контроля могут легко нарушить стабильность системы.
* **"Тренировочные колеса":** TBD часто кажется рискованным, пока команда не осознает, что это заставляет их строить автоматизацию, которая должна была быть в любом случае.
* **Требования:**
  * Короткоживущие ветки (максимум 1-2 дня).
  * Высокое покрытие автоматизированными тестами (Unit, Integration) — это критическое условие.
  * Развитая система Continuous Integration (CI) с жесткими Quality Gates.
  * Обязательное использование Feature Flags для крупных фич.

### 5. Forking Workflow (Открытое ПО)

Используется в Open Source проектах, где контрибьюторы не имеют прав на запись (`push`) в оригинальный репозиторий.

* **Процесс:**
  1. Создание **форка** (fork) основного репозитория на сервере (через UI платформы).
  2. Клонирование своего форка локально.
  3. Внесение изменений в фича-ветку.
  4. Создание Pull Request из форка в оригинальный репозиторий (`upstream`).

**Практический пример синхронизации форка:**
```bash
# Добавление оригинального репозитория как 'upstream'
git remote add upstream https://github.com/original-owner/repo.git

# Получение свежих изменений из оригинального проекта
git fetch upstream

# Перебазирование вашей локальной ветки main поверх свежего upstream/main
git switch main
git rebase upstream/main

# Публикация обновленного main в свой форк
git push -f origin main
```

## Гибридные и адаптированные подходы

В реальности многие команды не следуют "учебнику" на 100%, а адаптируют воркфлоу:

* **TBD + Release Branches:** разработчики часто интегрируются в `main`, но для выпуска релиза создается отдельная ветка, где код стабилизируется перед деплоем.
* **Дифференцированный доступ:** основная команда работает по TBD, а внешние контрибьюторы или другие отделы используют Pull Request'ы как дополнительный защитный барьер.
* **GitHub Flow с релизными тегами:** использование тегов на ветке `main` для фиксации версий и триггера CI/CD процессов, что добавляет стабильности простой модели.

## Сравнение рабочих процессов

| Модель | Сложность | Частота релизов | Популярность | Требования к CI/CD | Основная ниша |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **GitHub Flow** | Низкая | Постоянная (CD) | 40-50% | Высокие (проверка PR) | SaaS, Web, Open Source |
| **Trunk-Based** | Средняя | Очень высокая | 20-30% | **Максимальные** | Высокотехнологичные стартапы |
| **Git Flow** | Высокая | Редкая (релизы) | ~20% | Низкие (ручная работа) | Desktop, Mobile, Enterprise |
| **GitLab Flow** | Средняя | Средняя/CD | 10-15% | Средние (Multi-stage) | Банки, MedTech, Комплаенс |

## Влияние на CI/CD пайплайны

Модель ветвления не определяет структуру пайплайна, но диктует **требования** к его функциональности и надежности:

1.  **Trunk-Based Development:** требует самого мощного и быстрого пайплайна. Любой коммит может попасть в прод, поэтому обязательны качественные Quality Gates, мгновенные автотесты и автоматический деплой. Нет права на ошибку.
2.  **GitHub Flow:** пайплайн сосредоточен на проверке PR перед слиянием. Сборка артефактов и деплой обычно триггерятся слиянием в `main` или созданием тега.
3.  **GitLab Flow:** требует пайплайна, умеющего продвигать артефакты между ветками окружений (Promotion), часто включая этапы ручного одобрения (Manual Approval) перед выходом в Production.
4.  **Git Flow:** пайплайн часто используется для стабилизации релиза на ветке `release/*`. Допускает наличие ручных проверок и более медленных тестов, так как релиз — это запланированное событие.

---

## Практические сценарии выбора

*   **SaaS / Web-сервисы:** GitHub Flow (баланс простоты и скорости) или Trunk-Based (если команда обладает высокой зрелостью).
*   **Мобильные / Desktop приложения:** Git Flow (нужна поддержка старых версий и фиксация релизов).
*   **Enterprise / Банковские системы:** GitLab Flow (нужен жесткий контроль продвижения по окружениям и аудит безопасности).
*   **Pet-проекты / Стартапы:** GitHub Flow (минимальные накладные расходы на управление ветками).

## Инструменты командной строки

### GitHub CLI (`gh`)

```bash
# Создать Pull Request
gh pr create --fill --web
# → Opening github.com/user/repo/pull/new/branch in your browser

# Список открытых PR
gh pr list
# → #123  feat: add auth  [feature/auth]
# → #124  fix: bug in ui  [fix/ui]

# Просмотр изменений в PR
gh pr diff 123
# → diff --git a/src/auth.js b/src/auth.js ...

# Одобрение PR
gh pr review 123 --approve
# → Approved pull request #123
```

### GitLab CLI (`glab`)

```bash
# Создать Merge Request
glab mr create -f -w
# → https://gitlab.com/user/repo/-/merge_requests/45

# Список MR
glab mr list
# → !45  Add logging  (feature/logs)

# Одобрение MR
glab mr approve 45
# → Approved Merge Request !45
```

Подробное руководство по использованию CLI для диагностики пайплайнов см. в разделе **[Отладка и устранение неполадок в GitLab CI/CD](../CI-CD/GitLab_CI/Advanced/debugging_and_troubleshooting.md)**.

### Инструменты для Trunk-Based Development

* **TBD Flow** — CLI-инструмент для автоматизации типичных задач TBD (фиксация в main, создание короткоживущих веток, контроль конвенций коммитов).
