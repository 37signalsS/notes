# Рабочие процессы в Git

## Определения

**Рабочий процесс Git (Git Workflow)** — согласованный набор правил и шагов, определяющий, как команда разработчиков использует Git для совместной работы. Он регламентирует управление ветками, внесение изменений и выпуск релизов. Рабочий процесс — это не инструмент, а **социальный контракт команды**: он описывает, кто, когда и как имеет право изменять общий код, и как изменения попадают из рабочей станции разработчика в production.

**Модель ветвления (Branching Model)** — стратегия создания, именования и слияния веток в репозитории. Она задаёт топологию графа коммитов и правила перехода между состояниями кода. Основные цели использования моделей:

* **Организация рабочего процесса:** задает четкие правила именования, создания веток и слияния кода, обеспечивая дисциплину в команде.
* **Параллельная разработка:** позволяет разработчикам работать над разными задачами в изолированных ветках, минимизируя блокировки и конфликты слияния (Merge Hell).
* **Изоляция кода:** защита стабильных веток (`main`, `production`) от недописанного или сломанного функционала.
* **Управление релизами:** упрощает выпуск исправлений (Hotfixes) для старых версий без остановки разработки новых фич.
* **Интеграция CI/CD:** создает естественные точки для автоматических проверок (тесты, линтеры) и код-ревью перед интеграцией в основную ветку.

**Pull/Merge Request (PR/MR)** — механизм совместной работы на Git-платформах (GitHub, GitLab), представляющий собой запрос на слияние изменений из одной ветки в другую с возможностью код-ревью и автоматизированных проверок. На GitHub термин — Pull Request, на GitLab — Merge Request; по смыслу и механике они идентичны.

**Релиз (Release)** — зафиксированное, готовое к поставке состояние продукта (обычно помечается тегом `vX.Y.Z`). Разные модели по-разному трактуют релиз: от «значимого события» (Git Flow) до «побочного эффекта слияния в `main`» (GitHub Flow / Trunk-Based).

## Базовые концепции

### Предварительные требования и окружение

Перед выбором и применением рабочего процесса убедитесь, что выполнены минимальные требования:

* **Git** версии не ниже **2.23** — для команды `git switch` (в старых версиях используйте `git checkout -b`). Актуальные версии Git рекомендуются, так как улучшают работу с `worktree`, partial clone и защитой веток.
* **Удалённый хостинг** (GitHub / GitLab / Bitbucket) с настроенным `remote` `origin`, либо self-hosted экземпляр. Без сервера PR/MR-механика недоступна (остаётся только локальный `git merge`/`git rebase`).
* **CI/CD-сервер** (GitHub Actions, GitLab CI, Jenkins и др.) — опционален, но критичен для GitHub Flow и Trunk-Based, где каждое слияние обязано проходить автоматические проверки.
* **CLI-клиенты** `gh` (GitHub) и/или `glab` (GitLab) — опциональны, но упрощают работу с PR/MR из терминала (см. раздел «Инструменты командной строки»).
* **Права доступа:** понимание модели прав (кто может пушить в `main`, кто — только через PR) задаётся на стороне хостинга, а не Git.

### Механизм Pull/Merge Request

PR/MR создается для **ветки**, а не для отдельных коммитов. Это позволяет рассматривать совокупность изменений как единую логическую задачу (фичу или багфикс) и обсуждать её целиком, а не построчно.

**Почему интеграция идёт через PR/MR, а не прямым пушем:**

* Централизуется точка входа изменений — вся дискуссия, проверки и одобрения привязаны к одному объекту.
* Платформа блокирует слияние, пока не выполнены условия (статусы CI, количество аппрувов, отсутствие конфликтов).
* Сохраняется аудиторный след: кто предложил, кто проверил, какие тесты прошли.

**Процесс интеграции через PR/MR:**

1. **Публикация ветки:** Разработчик отправляет локальную ветку на сервер (`git push -u origin <branch>`).
2. **Создание запроса:** Инициация PR/MR через веб-интерфейс или CLI.
3. **Автоматизация (CI):** Запуск тестов, линтеров и проверок безопасности.
4. **Код-ревью:** Обсуждение кода коллегами, внесение правок (дозапушивание коммитов в ту же ветку автоматически обновляет PR).
5. **Одобрение (Approve):** Подтверждение готовности кода к слиянию.
6. **Слияние (Merge):** Интеграция кода в целевую ветку и автоматическое закрытие PR/MR.

**Проверка статуса (валидация):**

```bash
# Список веток и их состояния относительно origin/main
git status -sb
# → ## feature/auth...origin/main [ahead 3, behind 1]

# Проверить, что локальная ветка не конфликтует с целевой
git fetch origin
git merge --no-commit --no-ff origin/main
# → Auto-merging src/auth.js
# → (если конфликтов нет — ничего не коммитим, отменяем dry-run)
git merge --abort
```

### Защита веток (Branch Protection)

Защита веток — механизм на стороне хостинга, запрещающий прямые изменения критических веток (`main`, `production`) и требующий прохождения PR/MR с проверками. Это **единственный надёжный способ** гарантировать, что в стабильную ветку не попадёт код мимо ревью.

* **Что защищается:** запрет прямого `push`, обязательное количество одобрений, обязательные статус-чеки CI, запрет force-push, запрет удаления ветки.
* **Почему важно:** без защиты любой участник с правами записи может случайно сломать production одним коммитом.

**GitHub — настройка через API (требует прав администратора):**

```bash
# Включить защиту main: 1 аппрув + обязательные CI-чеки + защита от force-push
gh api -X PUT repos/OWNER/REPO/branches/main/protection \
  -f "required_pull_request_reviews[required_approving_review_count]=1" \
  -f "required_status_checks[strict]=true" \
  -f "required_status_checks[contexts][]=ci/tests" \
  -f "enforce_admins=true"
# → возвращает JSON с применёнными настройками защиты ветки
```

**GitLab — аналогично через Settings → Repository → Protected branches** (разрешить merge только для Maintainers, push — «No one»). Через CLI: `glab api -X PUT ...` или конфигурация в `.gitlab-ci.yml` / push rules.

### Методы слияния Pull/Merge Request (Merge Strategies)

При закрытии PR/MR платформы предлагают различные стратегии интеграции, влияющие на историю:

* **Create a merge commit (Стандартный Merge):** Все коммиты фича-ветки добавляются в `main`, создается коммит слияния.
  * *Плюсы:* Сохраняется полная история работы и контекст ветки.
  * *Минусы:* История `main` может стать слишком «шумной» из-за мелких промежуточных коммитов (wip, fix typo).
  * *Когда использовать:* Git Flow (явный `--no-ff`, сохраняющий ветку в истории).
* **Squash and merge (Объединение):** Все коммиты фича-ветки «схлопываются» в один новый коммит, который добавляется в `main`.
  * *Плюсы:* Идеально чистая, линейная история `main`. Один PR = один коммит.
  * *Минусы:* Теряется детализированная история разработки внутри самой фичи (решается сохранением ветки или PR-лога).
  * *Когда использовать:* GitHub Flow, Forking Workflow — когда важна читаемость `main`.
* **Rebase and merge (Перебазирование):** Коммиты фича-ветки переносятся поверх `main` (меняются хэши) без создания коммита слияния (Fast-Forward).
  * *Плюсы:* Линейная история, сохраняющая отдельные логические шаги (если они были хорошо оформлены).
  * *Минусы:* Требует идеальной дисциплины коммитов от разработчика; переписывает хэши (нельзя применять к уже опубликованным общим веткам без согласования).
  * *Когда использовать:* Trunk-Based Development, где история `main` должна быть строго линейной.

### Лучшие практики проведения Code Review

* **Малый размер:** Оптимальный размер PR — до 400 строк кода. Большие изменения сложнее анализировать, что приводит к поверхностному ревью («LGTM»).
* **Понятное описание:** PR должен отвечать на вопросы «Зачем это сделано?» и «Как это работает?».
* **Единая цель:** Один PR решает строго одну задачу. Не смешивайте рефакторинг и реализацию новой фичи в одном запросе.
* **Conventional Commits:** используйте префиксы `feat:`, `fix:`, `chore:`, `docs:` — они упрощают автогенерацию changelog и понимание истории.
* **Автоматизация рутины:** линтеры, форматтеры и тесты должны запускаться в CI, чтобы ревьюер тратил время на архитектуру, а не на стиль.

### Принцип единого артефакта

Один и тот же артефакт (Docker-образ, бинарный файл) должен проходить через все этапы (Dev → Staging → Prod) без пересборки.

* **Проблема:** Если собирать артефакт для Prod из `main`, а для Staging из `develop`, существует риск несоответствия кода из-за случайных изменений или разницы в окружении сборки.
* **Решение:** Артефакт собирается один раз (например, при создании тега или слиянии в `develop`), помечается версией и продвигается по конвейеру. Ветка `main` в таком случае служит указателем на текущую стабильную версию.

### Флаги функциональности (Feature Flags)

Механизм, позволяющий интегрировать незавершенный код в основную ветку, скрывая его от пользователей в рантайме. Это позволяет избежать долгоживущих веток и «ада слияния» (merge hell).

Подробно: [Feature Toggles — обзор](../CI-CD/Testing/feature_toggles/overview.md).

## Модели ветвления

Модель выбирается исходя из частоты релизов, требований к стабильности, зрелости команды и наличия CI/CD. Ниже — пять основных моделей. Для каждой указана **рекомендуемая стратегия слияния** и типичная ниша.

### 1. Git Flow (Классическая модель)

Строгая, многоуровневая модель для проектов с фиксированным циклом релизов (десктопное ПО, мобильные приложения, Enterprise). Популярность составляет около 20% рынка. Релиз в этой модели воспринимается как значимое событие («Event»). Рекомендуемая стратегия слияния — **merge commit с `--no-ff`** (сохраняет ветку в истории).

* **Ветки:**
  * `main` — только стабильный код production-качества.
  * `develop` — основная ветка для интеграции завершенных фич.
  * `feature/*` — разработка новых функций (от `develop`).
  * `release/*` — подготовка релиза, багфиксы перед выпуском (от `develop`).
  * `hotfix/*` — срочные исправления в production (от `main`).
* **Плюсы:**
  * **Изоляция процессов:** возможность одновременно исправлять баги в проде, готовить следующий релиз и разрабатывать новые фичи.
  * **Структурированность:** каждая ветка имеет строго определенную роль, что упрощает онбординг в крупных проектах.
  * **Поддержка нескольких версий:** идеальна для Long Term Support (LTS) и сценариев, когда нужно поддерживать версию 2.x, одновременно работая над 3.x (например, критический багфикс в версии 2.3 при активной разработке 3.0).
  * **Регулируемые отрасли:** жесткая структура и явные ветки релизов облегчают аудит и обеспечение отслеживаемости (traceability) изменений.
* **Минусы:**
  * **Сложность и избыточность:** слишком много ручных действий и накладных расходов на управление ветками («Branch Overhead»).
  * **Медленная поставка:** низкий Time-to-Market из-за долгоживущих веток и многоступенчатого процесса слияний (интеграционный ад).
  * **Устаревание:** сам автор модели позже признал, что Git Flow не подходит для веб-приложений с непрерывной доставкой (Continuous Delivery), так как создает лишние задержки.
  * **Бюрократизация:** требует строгого соблюдения дисциплины, иначе структура веток превращается в хаос.

**Практический пример работы (чистый Git):**

```bash
# Старт новой фичи
git switch develop          # Git 2.23+; в старых версиях: git checkout develop
git switch -c feature/auth
# → Switched to a new branch 'feature/auth'

# Завершение фичи (через CLI или MR/PR)
git switch develop
git merge --no-ff feature/auth   # Принудительный merge commit для сохранения контекста
# → Merge made by the 'recursive' strategy.
git branch -d feature/auth
# → Deleted branch feature/auth (was a1b2c3d).

# Старт релиза
git switch -c release/1.2.0 develop
# ... внесение исправлений ...

# Завершение релиза (вливается и в main, и обратно в develop)
git switch main
git merge --no-ff release/1.2.0
git tag -a v1.2.0 -m "Release 1.2.0"
git switch develop
git merge --no-ff release/1.2.0
git branch -d release/1.2.0
```

> **Почему `--no-ff`:** по умолчанию Git выполнил бы fast-forward (просто сдвинул бы указатель `develop` вперёд), и ветка `feature/auth` исчезла бы из графа истории. Флаг `--no-ff` гарантирует создание merge-коммита, сохраняя связь с веткой — это и есть суть Git Flow.

### 2. GitHub Flow (Непрерывная доставка)

Максимально простая и самая популярная модель (40–50% рынка). Идеально подходит для веб-приложений, SaaS и Open Source проектов с Continuous Delivery. Рекомендуемая стратегия слияния — **squash** (один коммит на PR в чистой истории `main`).

* **Принципы:**
  * `main` (или `master`) — всегда стабильная ветка, готовая к развертыванию.
  * Все изменения вносятся через короткоживущие ветки от `main`.
  * Слияние в `main` происходит только после успешного ревью и прохождения CI.
  * Деплой в Production происходит сразу после слияния в `main` (или явно по событию создания **тега**).
* **Плюсы:**
  * **Простота:** минимум правил, понятный процесс даже для новичков.
  * **Теги и стабильность:** тег на `main` ветке служит «снимком» стабильного состояния. Триггеры деплоя на теги защищают от случайного выката кода из мастера.
  * **Минимум PR:** одна фича — один PR, что уменьшает конфликты и очередь слияния.
  * **Скорость:** позволяет доставить фикс или фичу в продакшн максимально быстро (например, исправление бага к обеду).
* **Минусы и вызовы:**
  * **Требования к дисциплине:** культура команды критична — Pull Request'ы не должны быть «необязательными предложениями», а тесты — «забытым домашним заданием».
  * **Масштабирование:** при работе нескольких команд над одной кодовой базой возможны конфликты и сложности в координации («наступание на пятки»).
  * **Отсутствие поддержки версий:** модель рассчитана на наличие только одной (последней) версии в продакшене.
* **Особенности QA:** позволяет реализовать тестирование на отдельном временном стенде (Preview Environment) для каждой фича-ветки еще до слияния в основную ветку. Любая ошибка в `main` останавливает весь конвейер поставки.

### 3. GitLab Flow (Окружения и релизы)

Гибридная модель, ориентированная на соответствие кода инфраструктурным окружениям. Популярна в компаниях с жестким контролем качества и комплаенсом (банки, MedTech). Рыночная доля составляет 10–15%. Рекомендуемая стратегия слияния — обычный **merge** между ветками окружений (с сохранением контекста продвижения).

* **Принципы:**
  * Код продвигается строго последовательно по веткам окружений: `main` → `test` → `pre-production` → `production`.
  * Каждая ветка жестко привязана к конкретному стенду (ветка окружения = состояние окружения).
  * Для коробочного ПО используются стабильные ветки релизов (например, `2.1-stable`), куда вносятся только критические исправления (cherry-pick из `main`).
* **Плюсы:**
  * **Прозрачность:** состояние ветки всегда равно состоянию окружения; точно понятно, какой код где развернут.
  * **Безопасность:** многоступенчатая защита от случайных релизов — код обязательно проходит через предварительные стенды.
  * **Гибкость:** позволяет поддерживать несколько версий продукта параллельно.
* **Минусы:**
  * **Сложность процесса:** продвижение кода требует строгого соблюдения порядка слияний.
  * **Бюрократизация:** избыточность для маленьких проектов или стартапов с быстрым циклом разработки.
  * **Ручные действия:** часто требует участия релиз-инженера для контроля продвижения изменений по веткам.
* **Подробное описание:** см. в **[руководстве по GitLab Flow](../CI-CD/GitLab_CI/Tutorials/gitlab_flow.md)**.

### 4. Trunk-Based Development (Высокая динамика)

«Формула-1» в мире ветвления: работа в единой основной ветке с максимально быстрой интеграцией. Используется высокопроизводительными командами (20–30% рынка). Рекомендуемая стратегия слияния — **rebase / fast-forward** (строго линейная история `main`).

* **Принципы:**
  * Разработчики вливают изменения в `main` (trunk) несколько раз в день (непрерывная интеграция).
  * Ветки живут считанные часы (максимум полдня-день).
  * Использование **Feature Flags** (фиче-флагов) обязательно для скрытия незавершенного функционала (код в проде, но функционал выключен).
* **Плюсы:**
  * **Максимальная скорость:** согласно отчету DORA, команды использующие TBD показывают лучшие результаты по всем ключевым метрикам:
      * **Deployment Frequency** (Частота деплоев) — значительно выше.
      * **Lead Time for Changes** (Время цикла изменений) — значительно ниже.
      * **Change Failure Rate** (Доля неудачных изменений) — ниже за счет маленьких коммитов.
      * **Time to Restore Service** (Время восстановления) — значительно быстрее.
  * **Отсутствие Merge Hell:** конфликты решаются мгновенно, так как код интегрируется маленькими порциями.
  * **Быстрый фидбек:** разработчики сразу видят результат своей работы и реакцию системы (короткие петли обратной связи).

  **Практический пример (TBD + Feature Flags):**
  Три разработчика работают над функционалом корзины (checkout). Они ежедневно вливают небольшие части кода в `main`. Код попадает в продакшн, но скрыт от пользователей с помощью **фиче-флага**. Когда разработка завершена (например, в пятницу), флаг переключается, и функционал становится доступен всем. Это исключает гигантские конфликты слияния в конце недели.
* **Минусы и риски:**
  * **Высокие риски:** любой коммит может сломать Production без «непробиваемых» автоматических проверок. Не подходит при отсутствии качественного тестового покрытия.
  * **Культурный сдвиг:** требует изменения мышления — разработчики должны уметь разбивать задачи на мелкие коммиты и работать с фиче-флагами.
  * **Требования к опытности:** неопытные разработчики без должного контроля могут легко нарушить стабильность системы.
* **«Тренировочные колеса»:** TBD часто кажется рискованным, пока команда не осознает, что это заставляет их строить автоматизацию, которая должна была быть в любом случае.
* **Требования:**
  * Короткоживущие ветки (максимум 1-2 дня).
  * Высокое покрытие автоматизированными тестами (Unit, Integration) — это критическое условие.
  * Развитая система Continuous Integration (CI) с жесткими Quality Gates.
  * Обязательное использование Feature Flags для крупных фич.

### 5. Forking Workflow (Открытое ПО)

Используется в Open Source проектах, где контрибьюторы не имеют прав на запись (`push`) в оригинальный репозиторий. Рекомендуемая стратегия слияния — **squash** (мейнтейнер схлопывает вклад в один коммит при принятии).

* **Процесс:**
  1. Создание **форка** (fork) основного репозитория на сервере (через UI платформы).
  2. Клонирование своего форка локально.
  3. Внесение изменений в фича-ветку.
  4. Создание Pull Request из форка в оригинальный репозиторий (`upstream`).

**Практический пример синхронизации форка:**

```bash
# Добавление оригинального репозитория как 'upstream'
git remote add upstream https://github.com/original-owner/repo.git

# Получение свежих изменений из оригинального проекта
git fetch upstream
# → From https://github.com/original-owner/repo
# → * [new branch]      main       -> upstream/main

# Перебазирование вашей локальной ветки main поверх свежего upstream/main
git switch main
git rebase upstream/main
# → Successfully rebased and updated refs/heads/main.

# Публикация обновленного main в свой форк
git push -f origin main
# → + a1b2c3d...e5f6g7h main -> main (forced update)
```

> **Важно:** `git push -f` в форк безопасен, так как форк — ваша личная копия. Никогда не делайте force-push в общие ветки (`upstream/main`).

## Гибридные и адаптированные подходы

В реальности многие команды не следуют «учебнику» на 100%, а адаптируют воркфлоу:

* **TBD + Release Branches:** разработчики часто интегрируются в `main`, но для выпуска релиза создается отдельная ветка, где код стабилизируется перед деплоем.
* **Дифференцированный доступ:** основная команда работает по TBD, а внешние контрибьюторы или другие отделы используют Pull Request'ы как дополнительный защитный барьер.
* **GitHub Flow с релизными тегами:** использование тегов на ветке `main` для фиксации версий и триггера CI/CD процессов, что добавляет стабильности простой модели.

---

## Сравнение рабочих процессов

| Модель | Сложность | Частота релизов | Популярность | Требования к CI/CD | Основная ниша | Рекомендуемое слияние |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **GitHub Flow** | Низкая | Постоянная (CD) | 40-50% | Высокие (проверка PR) | SaaS, Web, Open Source | Squash |
| **Trunk-Based** | Средняя | Очень высокая | 20-30% | **Максимальные** | Высокотехнологичные стартапы | Rebase / FF |
| **Git Flow** | Высокая | Редкая (релизы) | ~20% | Низкие (ручная работа) | Desktop, Mobile, Enterprise | Merge `--no-ff` |
| **GitLab Flow** | Средняя | Средняя/CD | 10-15% | Средние (Multi-stage) | Банки, MedTech, Комплаенс | Merge между env |

**Когда НЕ стоит выбирать:**

* Git Flow — для веб-приложений с непрерывной доставкой (слишком медленный).
* Trunk-Based — для команд без зрелого CI и высокого тестового покрытия (риск стабильности).
* GitHub Flow — когда нужна параллельная поддержка множества версий продукта (нет веток релизов).
* GitLab Flow — для маленьких стартапов (избыточная бюрократия окружений).

---

## Влияние на CI/CD пайплайны

Модель ветвления не определяет структуру пайплайна, но диктует **требования** к его функциональности и надежности:

1.  **Trunk-Based Development:** требует самого мощного и быстрого пайплайна. Любой коммит может попасть в прод, поэтому обязательны качественные Quality Gates, мгновенные автотесты и автоматический деплой. Нет права на ошибку.
2.  **GitHub Flow:** пайплайн сосредоточен на проверке PR перед слиянием. Сборка артефактов и деплой обычно триггерятся слиянием в `main` или созданием тега.
3.  **GitLab Flow:** требует пайплайна, умеющего продвигать артефакты между ветками окружений (Promotion), часто включая этапы ручного одобрения (Manual Approval) перед выходом в Production.
4.  **Git Flow:** пайплайн часто используется для стабилизации релиза на ветке `release/*`. Допускает наличие ручных проверок и более медленных тестов, так как релиз — это запланированное событие.

## Практические сценарии

### Выбор модели под задачу

*   **SaaS / Web-сервисы:** GitHub Flow (баланс простоты и скорости) или Trunk-Based (если команда обладает высокой зрелостью).
*   **Мобильные / Desktop приложения:** Git Flow (нужна поддержка старых версий и фиксация релизов).
*   **Enterprise / Банковские системы:** GitLab Flow (нужен жесткий контроль продвижения по окружениям и аудит безопасности).
*   **Pet-проекты / Стартапы:** GitHub Flow (минимальные накладные расходы на управление ветками).

Ниже — пошаговые, копируемые в терминал сценарии с ожидаемым выводом. Все примеры предполагают защищённую ветку `main` и настроенный `origin`.

### Сценарий 1: GitHub Flow — полный цикл от ветки до релиза

```bash
# 1. Ответвляемся от свежего main
git switch main
git pull --ff-only
git switch -c feature/user-profile
# → Switched to a new branch 'feature/user-profile'

# 2. Правки и логичный коммит
git add src/profile.js
git commit -m "feat: add user profile page"
# → [feature/user-profile abc1234] feat: add user profile page

# 3. Публикация ветки и создание PR
git push -u origin feature/user-profile
# → * [new branch]      feature/user-profile -> feature/user-profile
gh pr create --fill --web
# → Opening github.com/owner/repo/pull/123 in your browser

# 4. После прохождения CI и ревью — squash-слияние (один коммит в main)
gh pr merge 123 --squash --delete-branch
# → Merged pull request #123
# → Deleted branch feature/user-profile locally and remotely

# 5. Тег стабильной версии (триггер деплоя)
git switch main
git pull --ff-only
git tag -a v1.4.0 -m "Release 1.4.0"
git push origin v1.4.0
# → * [new tag]         v1.4.0 -> v1.4.0
```

**Валидация:** `git log --oneline -1` показывает единственный коммит фичи в `main`; `gh pr view 123` — статус `MERGED`.

### Сценарий 2: Git Flow — экстренный hotfix в production

```bash
# 1. Ветка hotfix от main
git switch main
git switch -c hotfix/1.2.1
# → Switched to a new branch 'hotfix/1.2.1'

# 2. Исправление и коммит
git commit -am "fix: patch critical auth bypass"
# → [hotfix/1.2.1 e5f6g7h] fix: patch critical auth bypass

# 3. Слияние в main + тег релиза
git switch main
git merge --no-ff hotfix/1.2.1 -m "Merge hotfix 1.2.1"
git tag -a v1.2.1 -m "Hotfix 1.2.1"

# 4. Обязательно вернуть фикс в develop
git switch develop
git merge --no-ff hotfix/1.2.1 -m "Merge hotfix 1.2.1 into develop"
git branch -d hotfix/1.2.1

# 5. Публикация всех изменений и тега
git push origin main develop --tags
# → To github.com/owner/repo
# →    a1b2c3d..v1.2.1  main -> main
# → * [new tag]         v1.2.1 -> v1.2.1
```

**Валидация:** `git branch --contains v1.2.1` показывает и `main`, и `develop` — фикс не потерян для будущих релизов.

### Сценарий 3: Forking Workflow — вклад в Open Source

```bash
# 1. Форк уже создан через UI; клонируем свой форк и настраиваем upstream
git clone https://github.com/your-user/repo.git
cd repo
git remote add upstream https://github.com/original-owner/repo.git

# 2. Свежая ветка для правки
git switch -c fix/typo-in-readme
# → Switched to a new branch 'fix/typo-in-readme'

# 3. Правка, коммит, пуш в свой форк
git commit -am "docs: fix typo in README"
git push -u origin fix/typo-in-readme

# 4. PR из вашего форка в upstream
gh pr create --repo original-owner/repo \
  --head your-user:fix/typo-in-readme \
  --base main --title "Fix typo in README" --body "Описание правки"
# → https://github.com/original-owner/repo/pull/456

# 5. Перед повторной попыткой — синхронизация с upstream (см. пример выше)
git fetch upstream && git rebase upstream/main && git push -f origin fix/typo-in-readme
```

### Сценарий 4: Trunk-Based Development — короткоживущая ветка + Feature Flag

```bash
# Ветка живёт считанные часы
git switch main
git pull --ff-only
git switch -c shortlived/add-request-logging
# → Switched to a new branch 'shortlived/add-request-logging'

# Небольшой, безопасный коммит (функционал скрыт флагом, см. feature_toggles)
git commit -am "chore: add request logging behind flag"
git push -u origin shortlived/add-request-logging

# PR -> rebase-слияние (линейная история main, без merge-коммита)
gh pr create --fill
gh pr merge <n> --rebase --delete-branch
# → Merged pull request #<n>
```

**Валидация:** `git log --oneline main` — строго линейная история без merge-коммитов; функционал в проде, но выключен флагом до готовности.

### Сценарий 5: Разрешение конфликта слияния в PR/MR

```bash
git switch feature/x
git fetch origin
# Переносим свою ветку поверх свежего main
git rebase origin/main
# → CONFLICT (content): Merge conflict in src/app.js
# → Resolve all conflicts manually, then:
# → Auto-merging src/app.js

# После правки конфликтных файлов:
git add src/app.js
git rebase --continue
# → Successfully rebased and updated refs/heads/feature/x.

# Ветка — ваша, не общая => force-push допустим (предпочтительно --force-with-lease)
git push --force-with-lease origin feature/x
# → + abc1234...e5f6g7h feature/x -> feature/x (forced update)
# PR автоматически обновляется, конфликт исчезает
```

> Используйте `--force-with-lease` вместо `-f`: он откажет, если кто-то другой успел запушить в ветку, предотвращая потерю чужих коммитов.

### Сценарий 6: Откат неудачного слияния (revert merge)

```bash
# Найти hash merge-коммита
git log --oneline --merges -5
# → a1b2c3d Merge pull request #123 from feature/broken

# Безопасный откат: создаёт новый коммит, отменяющий слияние (история не переписывается)
git revert -m 1 a1b2c3d -m "Revert #123: broken feature"
# → [main xyz9876] Revert #123: broken feature
git push origin main
# →    a1b2c3d..xyz9876  main -> main
```

Подробнее про переписывание и откат истории — в **[Манипуляции с историей (Reset, Revert, Cherry-pick)](./git_history_manipulation.md)**.

## Инструменты командной строки

### GitHub CLI (`gh`)

```bash
# Создать Pull Request
gh pr create --fill --web
# → Opening github.com/user/repo/pull/new/branch in your browser

# Список открытых PR
gh pr list
# → #123  feat: add auth  [feature/auth]
# → #124  fix: bug in ui  [fix/ui]

# Просмотр изменений в PR
gh pr diff 123
# → diff --git a/src/auth.js b/src/auth.js ...

# Одобрение PR
gh pr review 123 --approve
# → Approved pull request #123

# Слияние: выбор стратегии
gh pr merge 123 --squash --delete-branch     # схлопнуть в 1 коммит
gh pr merge 123 --rebase --delete-branch     # линейно, без merge-коммита
gh pr merge 123 --merge                       # обычный merge commit

# Локально переключиться на ветку PR (для проверки)
gh pr checkout 123
# → branch 'feature/auth' set up to track 'origin/feature/auth'
```

### GitLab CLI (`glab`)

```bash
# Создать Merge Request
glab mr create -f -w
# → https://gitlab.com/user/repo/-/merge_requests/45

# Список MR
glab mr list
# → !45  Add logging  (feature/logs)

# Одобрение MR
glab mr approve 45
# → Approved Merge Request !45

# Слияние MR
glab mr merge 45 --squash --yes
# → Merged Merge Request !45
```

## Устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `fatal: impossible to fast-forward, will need to use --force` при `git push` | Локальная и удалённая ветки расходятся (diverged) | `git pull --rebase origin <branch>` (или `git pull --ff-only`, если локально чисто), затем `git push` |
| `error: The branch '<x>' is not fully merged` при `git branch -d` | Ветка не слита в целевую | Проверить `git branch --merged main`; если слита — повторить `git branch -d`, если точно не нужна — `git branch -D` (с потерей) |
| Локально вижу удалённые ветки, которых уже нет на сервере | Не очищены remote-tracking ссылки | `git fetch --prune` (или `git remote prune origin`) |
| Конфликт при слиянии PR | Параллельные правки одного участка кода | Сделать `rebase` на целевую ветку, разрешить конфликты, `push --force-with-lease` (для своей ветки) |
| Случайный коммит/пуш в `main` | Нет защиты ветки | Безопасно: `git revert <hash>` + push. Рискованно (только если никто не скачал): `git reset --hard HEAD~1` + `git push -f` |
| Счётчик «ahead/behind» растёт | Забыли забрать/слить изменения | `git pull --ff-only` (или `git merge --ff-only`) для выравнивания |
| Force-push сломал историю коллегам | Force-push в общую ветку | Избегать; использовать `--force-with-lease`; восстановить через `git reflog` у пострадавших |
| Форк «уехал» от upstream | Давно не синхронизировали | `git fetch upstream && git rebase upstream/main && git push -f origin main` |

## Лучшие практики и очистка

* **Соглашение об именовании веток:** префиксы `feature/`, `fix/`, `hotfix/`, `release/`, `chore/` повышают читаемость и упрощают автоматизацию.
* **Conventional Commits:** `feat:`, `fix:`, `chore:`, `docs:` — основа чистой истории и автогенерации changelog.
* **Защищайте `main`/`production`** через Branch Protection (обязательные ревью, статус-чеки, запрет force-push).
* **Короткоживущие ветки:** чем дольше живёт ветка, тем выше риск конфликтов. Сливайте как можно быстрее.
* **Осознанный выбор стратегии слияния:** squash для чистой `main`, rebase для линейности, `--no-ff` для Git Flow.
* **Никогда не force-push в общие ветки** (`main`, `develop`); для своих feature-веток — только `--force-with-lease`.
* **Удаляйте слитые ветки**, чтобы не плодить «мертвые» ссылки:

```bash
# Удалить локально слитые в main ветки (кроме main)
git branch --merged main | grep -v '^main$' | xargs git branch -d

# Очистить remote-tracking ссылки на удалённые ветки
git fetch --prune

# Если использовали worktree — очистить метаданные удалённых деревьев
git worktree prune
# → (вывод отсутствует при успехе)
```

Подробнее про worktree — в **[Git Worktree — параллельные директории](./git_worktree.md)**.
