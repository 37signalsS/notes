# Игнорирование коммитов в Git Blame — .git-blame-ignore-revs

## Определения

**`.git-blame-ignore-revs`** — специальный конфигурационный файл в корне репозитория, содержащий список хэшей коммитов, которые команда `git blame` должна пропускать при анализе авторства строк.

**git blame** — инструмент Git для построчного определения автора и коммита, в котором каждая строка файла была изменена в последний раз.

**Шумные коммиты (Churn commits)** — изменения, затрагивающие большое количество строк без изменения бизнес-логики (например, автоформатирование, линтинг, массовое переименование переменных или изменение лицензионных заголовков).

---

## Базовые концепции

### Проблема «шумных» коммитов
При выполнении массового рефакторинга или автоматического форматирования (Prettier, Black, gofmt), стандартный `git blame` начинает указывать автора этих технических изменений как автора всего кода. Это скрывает реальную историю разработки («blame pollution») и затрудняет поиск ответственных за логику.

### Механизм игнорирования
Когда коммит добавлен в список игнорируемых:
1.  Git анализирует изменения в этом коммите.
2.  Для каждой измененной строки он «перематывает» историю назад и приписывает авторство строки тому, кто изменил её в **предыдущем** (родительском) коммите.
3.  Процесс повторяется рекурсивно, если родительский коммит также находится в списке игнорирования.

### Формат файла и технические требования
- **Полные хэши:** Файл должен содержать полные 40-символьные хэши коммитов (SHA-1). Использование коротких хэшей не рекомендуется, так как они могут стать неоднозначными по мере роста репозитория.
- **Комментарии:** Строки, начинающиеся с `#`, игнорируются. Рекомендуется документировать каждый игнорируемый коммит (дата, причина, автор).
- **Пустые строки:** Допускаются для визуального разделения групп коммитов.

## Практические сценарии

### Сценарий 1: Первичная настройка в репозитории
Чтобы команда автоматически использовала файл игнорирования, его нужно зарегистрировать в локальном конфиге.

```bash
# 1. Создать файл в корне проекта
touch .git-blame-ignore-revs

# 2. Настроить Git для использования этого файла локально
git config blame.ignoreRevsFile .git-blame-ignore-revs

# 3. Добавить в индекс и закоммитить настройки
git add .git-blame-ignore-revs
git commit -m "chore: add git-blame-ignore-revs configuration"
```

### Сценарий 2: Добавление коммита с форматированием
После выполнения `npm run format` или массового рефакторинга:

```bash
# Получить хеш последнего коммита
COMMIT_HASH=$(git rev-parse HEAD)

# Добавить его в файл с описанием (рекомендуется делать это отдельным коммитом)
echo "# Mass reformatting with Prettier (2024-05-20)" >> .git-blame-ignore-revs
echo $COMMIT_HASH >> .git-blame-ignore-revs
```

### Сценарий 3: Визуализация и отладка
Git предоставляет флаги для понимания того, как игнорирование влияет на результат.

```bash
# Проверка с индикацией проигнорированных строк
# (проигнорированные строки будут отмечены символом '*' перед хешем)
git blame --mark-ignored path/to/file.py

# Временное отключение игнорирования (увидеть реального автора последнего изменения)
git blame --no-ignore-revs path/to/file.py

# Игнорирование конкретного хеша без редактирования файла
git blame --ignore-rev <hash> path/to/file.py
```

### Сценарий 4: Поддержка в IDE и инструментах

| Инструмент | Поддержка | Настройка |
| :--- | :--- | :--- |
| **VS Code** | Частично | В расширении *GitLens* необходимо включить опцию `gitlens.blame.ignoreRevsFile`. |
| **JetBrains (IntelliJ)** | **Да** | Автоматически обнаруживает `.git-blame-ignore-revs` и предлагает использовать его. |
| **GitHub** | **Да** | Автоматически применяет файл, если он находится в корне и называется `.git-blame-ignore-revs`. |
| **GitLab** | **Да** | Поддерживается с версии 15.4 (автоматически для корня проекта). |

## Дополнительная информация

### Риски и ограничения
- **Несуществующие коммиты:** Если в файл добавлен хэш, которого нет в локальной истории (например, из-за `rebase` или удаления ветки), `git blame` может выдать ошибку. Рекомендуется использовать только хэши, которые уже находятся в основной ветке (`main`/`master`).
- **Локальная природа `git config`:** Настройка `blame.ignoreRevsFile` не передается при `git clone`. Команда должна либо настроить это вручную, либо проект должен содержать скрипт инициализации (например, в `README` или `Makefile`).
- **Производительность:** В огромных репозиториях с тысячами игнорируемых коммитов `git blame` может работать медленнее из-за рекурсивного поиска родителей.

### Советы по эксплуатации
- **Глобальная настройка:** Можно настроить глобальный файл игнорирования (`git config --global blame.ignoreRevsFile ...`), но это может привести к ошибкам в репозиториях, где такого файла нет.
- **Интеграция с CI:** Рекомендуется добавить проверку в CI, чтобы убедиться, что все хэши в `.git-blame-ignore-revs` действительны и присутствуют в истории.
