# Игнорирование коммитов в Git Blame — .git-blame-ignore-revs

**Актуально для:** Git 2.23–2.56 (описанные флаги и ключи стабильны с 2.23; в 2.54–2.56 изменений не было). Основной сценарий — Git 2.54.0 (локально проверено).

## Определения

**`.git-blame-ignore-revs`** — специальный конфигурационный файл в корне репозитория, содержащий список хэшей коммитов, которые команда `git blame` должна пропускать при анализе авторства строк.

**git blame** — инструмент Git для построчного определения автора и коммита, в котором каждая строка файла была изменена в последний раз.

**Шумные коммиты (Churn commits)** — изменения, затрагивающие большое количество строк без изменения бизнес-логики (например, автоформатирование, линтинг, массовое переименование переменных или изменение лицензионных заголовков).

**`.mailmap`** — специальный файл в корне репозитория, содержащий правила канонизации имен и email-адресов авторов. Позволяет объединять историю одного человека под разными именами в отчетах `git shortlog` и `git blame`. Работает комплементарно к `.git-blame-ignore-revs`: `mailmap` исправляет идентичность автора, а `ignore-revs` скрывает технические коммиты.

**`git blame -w`** — флаг команды `git blame`, указывающий игнорировать изменения, затрагивающие только пробельные символы (whitespace). Применим совместно с `.git-blame-ignore-revs` для более точного определения авторства.

**`blame.markIgnoredLines`** / **`blame.markUnblamableLines`** — конфигурационные ключи Git (по умолчанию `false`). Включают пометку строк, затронутых игнорируемым коммитом: `?` — если строка приписана другому коммиту, `*` — если приписать не удалось. Настраиваются на тех же уровнях, что и `blame.ignoreRevsFile`.

**`--ignore-rev <rev>`** / **`--ignore-revs-file <file>`** — флаги командной строки `git blame` (с Git 2.23). Позволяют временно исключить коммит(ы) без изменения конфигурации или файла. `--ignore-revs-file` может повторяться; пустое имя сбрасывает список. Обработка флагов происходит после `blame.ignoreRevsFile`.

## Базовые концепции

### Проблема «шумных» коммитов
При выполнении массового рефакторинга или автоматического форматирования (Prettier, Black, gofmt), стандартный `git blame` начинает указывать автора этих технических изменений как автора всего кода. Это скрывает реальную историю разработки («blame pollution») и затрудняет поиск ответственных за логику.

### Механизм игнорирования
Когда коммит добавлен в список игнорируемых:
1.  Git анализирует изменения в этом коммите.
2.  Для каждой измененной строки он «перематывает» историю назад и приписывает авторство строки тому, кто изменил её в **предыдущем** (родительском) коммите.
3.  Процесс повторяется рекурсивно, если родительский коммит также находится в списке игнорирования.

**Взаимодействие с `.mailmap`:**
- `.git-blame-ignore-revs` скрывает коммиты из вывода blame.
- `.mailmap` переименовывает авторов в выводе blame и shortlog.
- Оба механизма действуют независимо и могут использоваться одновременно: сначала `.mailmap` нормализует имя автора, затем `ignore-revs` пропускает технические коммиты.

**Поведение при мерж-коммитах:**
При игнорировании коммита, содержащего мерж, Git продолжает трассировку от родительского коммита, который соответствует той же строке. Если оба родителя игнорируются, используется общий предок.

**Уровни конфигурации `blame.ignoreRevsFile`:**
- **Локальный** (`.git/config`): файл `.git-blame-ignore-revs` в корне репозитория. Рекомендуется для командных проектов.
- **Глобальный** (`~/.gitconfig`): путь к файлу в домашней директории. Подходит для личных правил, но может привести к ошибкам в репозиториях без такого файла.
- **Системный** (`/etc/gitconfig`): применяется ко всем репозиториям системы. Используется редко.

### Формат файла и технические требования
- **Полные хэши:** Файл должен содержать полные 40-символьные хэши коммитов (SHA-1). Использование коротких хэшей не рекомендуется, так как они могут стать неоднозначными по мере роста репозитория.
- **Комментарии:** Строки, начинающиеся с `#`, игнорируются. Рекомендуется документировать каждый игнорируемый коммит (дата, причина, автор).
- **Пустые строки:** Допускаются для визуального разделения групп коммитов.

## Практические сценарии

### Сценарий 1: Первичная настройка в репозитории
Чтобы команда автоматически использовала файл игнорирования, его нужно зарегистрировать в локальном конфиге.

```bash
# 1. Создать файл в корне проекта
touch .git-blame-ignore-revs

# 2. Настроить Git для использования этого файла локально
git config blame.ignoreRevsFile .git-blame-ignore-revs

# 3. Добавить в индекс и закоммитить настройки
git add .git-blame-ignore-revs
git commit -m "chore: add git-blame-ignore-revs configuration"
```

**Валидация:**
```bash
# Проверить, что переменная установлена
git config --local blame.ignoreRevsFile
# → .git-blame-ignore-revs
```

### Сценарий 2: Добавление коммита с форматированием
После выполнения `npm run format` или массового рефакторинга:

```bash
# Получить хеш последнего коммита
COMMIT_HASH=$(git rev-parse HEAD)

# Добавить его в файл с описанием (рекомендуется делать это отдельным коммитом)
echo "# Mass reformatting with Prettier (2024-05-20)" >> .git-blame-ignore-revs
echo $COMMIT_HASH >> .git-blame-ignore-revs
```

**Валидация:**
```bash
# Проверить, что хеш записан
grep "$COMMIT_HASH" .git-blame-ignore-revs
# → a1b2c3d4e5f6...
```

### Сценарий 3: Визуализация и отладка
Git предоставляет флаги и ключи для понимания того, как игнорирование влияет на результат.

```bash
# Проверка с индикацией проигнорированных строк
# (проигнорированные строки будут отмечены '?' при приписке к другому коммиту
#  и '*' — если приписать не удалось)
git blame --mark-ignored path/to/file.py

# Временное отключение игнорирования (увидеть реального автора последнего изменения)
git blame --no-ignore-revs path/to/file.py

# Игнорирование конкретного хэша без редактирования файла
git blame --ignore-rev <hash> path/to/file.py

# Игнорирование списка хэшей из файла без изменения конфига
git blame --ignore-revs-file .git-blame-ignore-revs path/to/file.py
```

**Ожидаемый результат:**
- `git blame --mark-ignored` показывает `*` перед хэшем проигнорированного коммита (требует `blame.markUnblamableLines=true`; по умолчанию false).
- `git blame --no-ignore-revs` показывает реального автора последнего изменения.
- `git blame --ignore-rev` временно исключает указанный коммит только для текущего вызова.
- `--ignore-revs-file` обрабатывается после `blame.ignoreRevsFile`, пустое имя сбрасывает список.

### Сценарий 4: Поддержка в IDE и инструментах

| Инструмент | Поддержка | Настройка |
| :--- | :--- | :--- |
| **VS Code** | Частично | В расширении *GitLens* необходимо включить опцию `gitlens.blame.ignoreRevsFile`. |
| **JetBrains (IntelliJ)** | **Да** | Автоматически обнаруживает `.git-blame-ignore-revs` и предлагает использовать его. |
| **GitHub** | **Да** | Автоматически применяет файл, если он находится в корне и называется `.git-blame-ignore-revs`. |
| **GitLab** | **Да** | Поддерживается с версии 15.4 (автоматически для корня проекта). |

### Сценарий 5: Комбинированное использование с `.mailmap`
Если в репозитории один автор использовал несколько email-адресов, а также были шумные коммиты форматирования, оба файла используются вместе.

**Создание `.mailmap`:**
```bash
# Объединить два email одного автора под одним каноническим именем
echo "Ivan Ivanov <ivan@company.com> <ivan.old@company.com>" > .mailmap
echo "Ivan Ivanov <ivan@company.com> <ivan@personal.me>" >> .mailmap

# Проверить результат
git shortlog -se
```

**Создание `.git-blame-ignore-revs`:**
```bash
# Игнорировать коммит автоформатирования
COMMIT_HASH=$(git rev-parse HEAD~1)
echo "# Auto-formatting 2024-03-15" >> .git-blame-ignore-revs
echo $COMMIT_HASH >> .git-blame-ignore-revs
```

**Валидация:**
```bash
# Проверить blame с учетом mailmap и ignore-revs
git blame --show-name path/to/file.py
```

### Сценарий 6: Валидация файла в CI/CD
Рекомендуется проверять, что все хэши в `.git-blame-ignore-revs` существуют в истории и принадлежат основной ветке.

```bash
#!/bin/bash
# validate-blame-ignore.sh

FILE=".git-blame-ignore-revs"
ERRORS=0

while IFS= read -r line; do
  # Пропустить комментарии и пустые строки
  [[ "$line" =~ ^# ]] && continue
  [[ -z "$line" ]] && continue

  if ! git cat-file -e "$line^{commit}" 2>/dev/null; then
    echo "Ошибка: коммит $line не найден в истории"
    ERRORS=$((ERRORS + 1))
  fi
done < "$FILE"

if [ $ERRORS -gt 0 ]; then
  echo "Найдено $ERRORS несуществующих коммитов"
  exit 1
fi

echo "Все коммиты в .git-blame-ignore-revs валидны"
```

**Использование в GitHub Actions:**
```yaml
- name: Validate .git-blame-ignore-revs
  run: bash scripts/validate-blame-ignore.sh
```

### Сценарий 7: Глобальная настройка для личных проектов
Для личных репозиториев, где нет общего `.git-blame-ignore-revs`, можно настроить глобальный файл.

```bash
# Создать глобальный файл
touch ~/.git-blame-ignore-revs

# Настроить глобально
git config --global blame.ignoreRevsFile ~/.git-blame-ignore-revs

# Добавить коммит в глобальный список
echo "abc123..." >> ~/.git-blame-ignore-revs
```

**Важно:** Глобальный файл применяется ко всем репозиториям, включая те, где такого файла не существует. Это может привести к незаметному игнорированию коммитов в чужих проектах.

### Сценарий 8: Диагностика «почему коммит всё ещё виден в blame»
Если добавленный в файл коммит продолжает отображаться в выводе `git blame`.

```bash
# 1. Проверить, что переменная blame.ignoreRevsFile установлена
git config blame.ignoreRevsFile

# 2. Проверить, что хэш полный (40 символов) и без пробелов
grep -n "abc123" .git-blame-ignore-revs

# 3. Проверить, что коммит существует в текущей ветке
git log --oneline | grep "abc123"

# 4. Принудительно перечитать конфигурацию
git config --unset blame.ignoreRevsFile
git config blame.ignoreRevsFile .git-blame-ignore-revs

# 5. Выполнить blame с флагом отладки
GIT_TRACE=1 git blame --mark-ignored path/to/file.py
```

### Сценарий 9: Очистка устаревших записей
По мере роста репозитория список игнорируемых коммитов может содержать устаревшие или дублирующиеся записи.

```bash
# Найти все коммиты из файла, которые уже не reachable из main
git rev-list --all --not main | while read commit; do
  grep -q "$commit" .git-blame-ignore-revs && echo "Unreachable: $commit"
done

# Удалить строку с конкретным коммитом
sed -i '' "/a1b2c3d4e5f6/d" .git-blame-ignore-revs

# Удалить все строки, содержащие только хэши (без комментариев)
# для ручной проверки
grep -E "^[0-9a-f]{40}$" .git-blame-ignore-revs
```

## Типичные ошибки и их решение

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `fatal: bad config line` при выполнении blame | В `.git-blame-ignore-revs` есть строка, похожая на хэш, но с опечаткой | Удалить или закомментировать ошибочную строку |
| Коммит всё ещё отображается в blame | Хэш неполный (короткий), или `blame.ignoreRevsFile` не установлен | Использовать полный 40-символьный хэш, проверить `git config blame.ignoreRevsFile` |
| `git blame` работает медленно | Слишком много коммитов в списке (тысячи) | Разделить файл на группы по датам, оставить только актуальные записи |
| Настройка не работает на CI | `blame.ignoreRevsFile` локальная и не передается при clone | Добавить команду `git config blame.ignoreRevsFile .git-blame-ignore-revs` в скрипт инициализации CI |
| Символ `*` не отображается при `--mark-ignored` | `blame.markUnblamableLines` не включён (по умолчанию false) | Включить ключ: `git config blame.markUnblamableLines true` |
| Ошибка при добавлении несуществующего хэша | Коммит был удален через `git filter-repo` или `rebase` | Удалить несуществующий хэш из файла, запустить CI-валидацию |
| `.mailmap` и `.git-blame-ignore-revs` конфликтуют | Неверный порядок применения: mailmap требует, чтобы автор существовал в истории | Убедиться, что `.mailmap` используется только для существующих авторов |
| Глобальный файл влияет на чужие проекты | `git config --global blame.ignoreRevsFile` задан для всех репозиториев | Использовать локальный файл в проектах, где он не нужен |

## Ограничения и крайние случаи

1. **Рекурсивный перебор истории:** В репозиториях с глубокой историей и тысячами игнорируемых коммитов `git blame` может выполнять рекурсивный поиск родителей для каждой строки, что существенно замедляет работу. Для огромных репозиториев рекомендуется ограничивать количество записей или использовать `git blame -S <rev>` для ограничения диапазона поиска.
2. **Взаимодействие с `git log -L`:** Инструмент `git log -L` для отслеживания истории функций не поддерживает `.git-blame-ignore-revs`. Если требуется игнорирование коммитов в forensics-анализе, используйте комбинацию `git log --reverse` с ручной фильтрацией.
3. **Графы с несколькими родителями (merge commits):** При игнорировании мерж-коммитов Git выбирает родительский коммит, который соответствует изменению строки. В сложных графах с несколькими родителями результат может быть неочевидным; рекомендуется проверять вывод через `git blame --no-ignore-revs`.
4. **Плоские merge (`--ff-only`):** При fast-forward мерже игнорируемый коммит полностью пропускается, так как не создает отдельный коммит слияния.
5. **Подмодули:** Файл `.git-blame-ignore-revs` должен существовать в каждом подмодуле отдельно. Он не наследуется от основного репозитория.
6. **Переименованные файлы:** При анализе переименованного файла `git blame` следует историей через механизм rename detection. Игнорируемые коммиты в истории исходного файла также учитываются.

## Операции и команды

| Команда / Настройка | Назначение | Пример |
| :--- | :--- | :--- |
| `git config blame.ignoreRevsFile <path>` | Указать путь к файлу игнорируемых коммитов | `git config --local blame.ignoreRevsFile .git-blame-ignore-revs` |
| `git blame --ignore-rev <hash> <file>` | Временно игнорировать один коммит | `git blame --ignore-rev abc123… file.py` |
| `git blame --ignore-revs-file <file> <file>` | Игнорировать список коммитов из файла | `git blame --ignore-revs-file .git-blame-ignore-revs file.py` |
| `git blame --no-ignore-revs <file>` | Отключить игнорирование для текущего вызова | `git blame --no-ignore-revs file.py` |
| `git blame --mark-ignored <file>` | Показать пометки проигнорированных строк | `git blame --mark-ignored file.py` |
| `git blame -w <file>` | Игнорировать пробельные изменения | `git blame -w file.py` |
| `git config blame.markIgnoredLines true` | Включить пометку `?` | `git config blame.markIgnoredLines true` |
| `git config blame.markUnblamableLines true` | Включить пометку `*` | `git config blame.markUnblamableLines true` |
| `git blame -S <file> <file>` | Использовать произвольный список ревизий | `git blame -S revs.txt file.py` |

## Производительность и масштабирование (SRE-аспект)

Для репозиториев с глубокой историей и тысячами игнорируемых коммитов `git blame` может работать медленно из-за рекурсивного поиска родителей для каждой строки.

- **Ограничение диапазона:** Используйте `git blame -S <rev>` или `git blame <rev>..<rev> -- <file>` для анализа только нужного интервала истории.
- **Количество записей:** Очищайте `.git-blame-ignore-revs` от устаревших коммитов (недостижимых из основных веток) — рекурсивный перебор растёт линейно с числом записей.
- **Измерение:** Для диагностики скорости используйте `GIT_TRACE=1 git blame --progress <file>` или `git blame --progress --abbrev=8 <file>` — укороченные хэши и прогресс-вывод уменьшают накладные расходы.
- **Распределённые команды:** Настройка `blame.ignoreRevsFile` локальна и не передаётся при `git clone`. Для автоматизации в CI/CD добавляйте `git config blame.ignoreRevsFile .git-blame-ignore-revs` в скрипт инициализации, а не полагайтесь на ручную настройку.

## Best practices

1. **Документируйте каждый игнорируемый коммит** в `.git-blame-ignore-revs` с датой и кратким описанием (например, `# Black reformat 2024-06-01`).
2. **Используйте полные 40-символьные хэши** во избежание неоднозначностей при росте репозитория.
3. **Настраивайте `blame.ignoreRevsFile` локально** (`.git/config`) для командных проектов, чтобы настройка была версионирована и доступна всем участникам.
4. **Группируйте коммиты по датам или типам форматирования**, чтобы файл оставался читаемым.
5. **Добавляйте валидацию `.git-blame-ignore-revs` в CI/CD** для проверки существования хэшей в истории.
6. **Комбинируйте с `.mailmap`**, если в проекте есть проблема с канонизацией имен авторов.
7. **Не используйте глобальный `blame.ignoreRevsFile`** в многопроектных окружениях, чтобы избежать побочных эффектов.
8. **Очищайте устаревшие записи** периодически (например, раз в квартал), удаляя коммиты, которые больше не reachable из основных веток.
9. **Используйте `git blame -w`** совместно с `.git-blame-ignore-revs` для исключения форматирования в реальном времени без модификации файла.
10. **Тестируйте настройку после каждого добавления** с помощью `git blame --mark-ignored`, чтобы убедиться, что строки переходят к правильным авторам.

## Безопасность

- **Нет риска утечки данных:** Сам файл `.git-blame-ignore-revs` содержит только хэши коммитов и комментарии, не раскрывающие чувствительные данные.
- **Не влияет на целостность истории:** Игнорирование коммитов в `git blame` является визуальным фильтром и не изменяет объектную модель Git.
- **Риск потери контекста:** При агрессивном игнорировании коммитов пользователи могут потерять понимание, кто и когда вносил изменения. Документируйте причины игнорирования.
- **CI/CD аутентификация:** При добавлении валидации `.git-blame-ignore-revs` в пайплайн убедитесь, что скрипт не выполняет произвольный код из репозитория.

## Дополнительная информация

### Риски и ограничения
- **Несуществующие коммиты:** Если в файл добавлен хэш, которого нет в локальной истории (например, из-за `rebase` или удаления ветки), `git blame` может выдать ошибку. Рекомендуется использовать только хэши, которые уже находятся в основной ветке (`main`/`master`).
- **Локальная природа `git config`:** Настройка `blame.ignoreRevsFile` не передается при `git clone`. Команда должна либо настроить это вручную, либо проект должен содержать скрипт инициализации (например, в `README` или `Makefile`).
- **Производительность:** В огромных репозиториях с тысячами игнорируемых коммитов `git blame` может работать медленнее из-за рекурсивного поиска родителей.
- **Ограниченная поддержка в IDE:** Не все инструменты автоматически применяют `.git-blame-ignore-revs`. Например, VS Code требует включения опции в GitLens.

### Советы по эксплуатации
- **Глобальная настройка:** Можно настроить глобальный файл игнорирования (`git config --global blame.ignoreRevsFile ...`), но это может привести к ошибкам в репозиториях, где такого файла нет.
- **Интеграция с CI:** Рекомендуется добавить проверку в CI, чтобы убедиться, что все хэши в `.git-blame-ignore-revs` действительны и присутствуют в истории.
- **Использование с `git shortlog`:** Файл `.git-blame-ignore-revs` влияет только на `git blame`. Для исключения коммитов из `git shortlog` используйте комбинацию `git shortlog --no-merges` или настройте `.mailmap`.
- **Атомарность изменений:** Добавляйте новые коммиты в `.git-blame-ignore-revs` отдельным коммитом, чтобы изменения в файле были отслеживаемыми.
