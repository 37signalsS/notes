# Синхронизация репозиториев — git fetch, pull, push

## Определения

*   **Удаленный репозиторий (Remote):** Версия проекта, размещенная на сетевом сервере (GitHub, GitLab, локальный сервер). Служит центральным узлом для обмена изменениями.
*   **Синхронизация:** Процесс согласования состояний локального и удаленного репозиториев через передачу объектов (коммитов, деревьев) и обновление указателей веток.
*   **`git fetch`:** Загрузка данных (коммитов, веток, тегов) из удаленного репозитория в локальную базу данных. Обновляет удаленные ветки отслеживания (`origin/main`), но не меняет текущее рабочее состояние.
*   **`git pull`:** Комбинированная команда, выполняющая `fetch` и немедленную интеграцию изменений в текущую ветку (через `merge` или `rebase`).
*   **`git push`:** Отправка локальных объектов в удаленный репозиторий и попытка обновить удаленный указатель ветки.
*   **Удаленная ветка отслеживания (Remote-tracking branch):** Локальная ссылка на состояние ветки в удаленном репозитории (например, `refs/remotes/origin/main`).

## Базовые концепции

### Механизм получения изменений (`fetch` vs `pull`)

*   **`git fetch`** — это безопасная операция. Она позволяет увидеть, что сделали коллеги, без риска возникновения конфликтов в вашей рабочей директории. После `fetch` можно использовать `git log` или `git diff` для анализа изменений.
*   **`git pull`** — это автоматизация. По умолчанию она выполняет `merge`, что часто создает лишние "merge-коммиты". Использование `git pull --rebase` позволяет поддерживать линейную историю проекта.

### Стратегии отправки изменений (`push`)

*   **Fast-forward push:** Стандартная отправка, возможная только если удаленная ветка является прямым предком локальной (вы не "отстали" от сервера).
*   **Force push (`--force`):** Принудительная перезапись удаленной ветки. Удаляет коммиты на сервере, которых нет у вас. Допустимо только в приватных ветках.
*   **Safe force push (`--force-with-lease`):** Проверяет, не появились ли на сервере новые коммиты с момента вашего последнего `fetch`. Если кто-то успел запушить изменения, операция будет отклонена, что предотвращает случайную потерю чужой работы.

### Управление удаленными источниками

Репозиторий может иметь множество remotes. Общепринятые соглашения:
*   **`origin`**: Основной репозиторий, из которого был сделан клон.
*   **`upstream`**: Оригинальный репозиторий, если вы работаете в форке (fork).

## Практические сценарии

### Сценарий 1: Анализ изменений перед интеграцией

Позволяет избежать ошибок при слиянии сложных веток.

```bash
# 1. Получить данные с сервера
git fetch origin

# 2. Посмотреть список новых коммитов
git log main..origin/main --oneline
# → a1b2c3d (origin/main) Исправить ошибку в API
# → e4f5g6h Добавить тесты для авторизации

# 3. Сравнить код локального main и удаленного
git diff main origin/main

# 4. Если все в порядке — интегрировать
git merge origin/main
```

### Сценарий 2: Синхронизация форка с оригиналом (upstream)

Используется в Open Source проектах для актуализации своей копии.

```bash
# 1. Добавить ссылку на оригинальный репозиторий
git remote add upstream https://github.com/original-owner/project.git

# 2. Загрузить изменения
git fetch upstream

# 3. Перебазировать свою ветку на актуальный main из оригинала
git checkout main
git rebase upstream/main

# 4. Обновить свой форк на сервере
git push origin main
```

### Сценарий 3: Чистая синхронизация через Rebase

Рекомендуется для повседневной работы, чтобы избежать "Merge branch 'main' into..." коммитов.

```bash
# Стянуть изменения и перебазировать локальную работу поверх них
git pull --rebase origin main

# Если возникли конфликты:
# 1. Исправить файлы
# 2. git add <file>
# 3. git rebase --continue
```

### Сценарий 4: Очистка устаревших веток

Когда ветки удаляются на сервере, локальные ссылки `origin/*` остаются. Их нужно вычищать.

```bash
# Удалить ссылки на ветки, которых больше нет на сервере origin
git fetch --prune origin

# Проверить состояние синхронизации веток
git remote show origin
# → Local branches configured for 'git pull':
# →   main merges with remote main
```

### Сценарий 5: Безопасное обновление истории на сервере

После `git commit --amend` или `rebase` локальная ветка расходится с удаленной.

```bash
# Попытка обычного push завершится ошибкой
git push origin feature/auth
# → error: failed to push some refs...

# Использовать безопасный принудительный push
git push origin feature/auth --force-with-lease
```

## Дополнительная информация

### Настройка поведения по умолчанию

Рекомендуется настроить Git для более предсказуемой синхронизации:

```bash
# Автоматически делать rebase при каждом pull
git config --global pull.rebase true

# Автоматически выполнять --prune при каждом fetch
git config --global fetch.prune true
```

### Ограничения и риски

*   **Конфликты:** `git pull` может привести к конфликтам. Если вы не уверены в чистоте слияния, всегда делайте сначала `fetch`.
*   **Потеря данных:** `push --force` в общих ветках (main, develop) — критическая ошибка, требующая восстановления репозитория из бэкапов или локальных копий коллег.
*   **Сетевые задержки:** При больших объемах данных (LFS или огромные репозитории) используйте `git fetch --depth 1` (shallow clone) для ускорения, если история не критична.
