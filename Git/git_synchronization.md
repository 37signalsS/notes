# Git: Синхронизация репозиториев

## Определения

* **Синхронизация Git:** Процесс обмена изменениями между локальным и удаленным репозиториями. Включает получение изменений из удаленного репозитория (`fetch`, `pull`) и отправку локальных изменений в удаленный репозиторий (`push`).
* **`git fetch`:** Команда для загрузки коммитов, веток и тегов из удаленного репозитория в локальный, но без автоматического применения этих изменений к вашей рабочей копии или текущей ветке.
* **`git pull`:** Составная команда, которая выполняет `git fetch`, а затем автоматически интегрирует полученные изменения в вашу текущую локальную ветку (по умолчанию через `git merge`).
* **`git push`:** Команда для отправки ваших локальных коммитов в удаленный репозиторий.
* **Удаленный репозиторий (Remote):** Версия вашего репозитория, хранящаяся на другом компьютере или сервере (например, GitHub, GitLab).

## Базовые концепции

### Получение изменений (`fetch` vs `pull`)

* **`git fetch`** загружает изменения из удаленного репозитория, но не интегрирует их в вашу локальную рабочую ветку. Это дает вам возможность просмотреть новые коммиты перед их применением. Это "безопасная" операция для получения информации об удаленном состоянии.
* **`git pull`** является комбинацией `git fetch` и `git merge` (или `git rebase`). Он загружает изменения, а затем автоматически пытается интегрировать их в вашу текущую ветку. Это удобнее, но требует больше внимания к возможным конфликтам слияния.

### Отправка изменений (`push`)

* **`git push`** отправляет ваши локальные коммиты в удаленный репозиторий. Если удаленная ветка содержит коммиты, которых нет в вашей локальной ветке (т.е. ваша локальная ветка "отстала"), Git по умолчанию отклонит `push`, чтобы предотвратить потерю истории.
* **`git push --force`** и **`git push --force-with-lease`** используются для принудительного обновления удаленной ветки, перезаписывая ее историю. Их следует использовать с крайней осторожностью.

### Удаленные репозитории

Вы можете настроить несколько удаленных репозиториев (например, `origin` для вашего основного репозитория, `upstream` для форкнутого проекта) и синхронизироваться с любым из них.

## Практические сценарии

### Получение изменений из удаленного репозитория

#### `git fetch`: Загрузка изменений без слияния

```bash
# Загружает все изменения из удаленного репозитория 'origin'
git fetch origin

# Загружает изменения из конкретного удаленного репозитория
git fetch <имя_репозитория>
```

После `fetch` вы можете просмотреть новые коммиты удаленного репозитория, которые теперь доступны локально в ветках вида `origin/<branch_name>`, но не применены к вашим локальным веткам.

#### `git pull`: Загрузка и автоматическое слияние/перебазирование

```bash
# Загружает изменения из 'origin' и сливает их в текущую ветку
git pull origin

# Загружает изменения из конкретного удаленного репозитория и ветки
git pull <имя_репозитория> <имя_ветки>
```

**Сценарий 1: Pull из другого удаленного репозитория (например, форк)**

Полезно, когда вы работаете с форком и хотите синхронизироваться с основным проектом.

```bash
# 1. Добавляем основной репозиторий как "upstream" (если еще не добавлен)
git remote add upstream https://github.com/original/project.git

# 2. Стягиваем изменения из ветки 'main' основного проекта в нашу текущую ветку
git pull upstream main
```

**Сценарий 2: Pull из другой ветки того же репозитория**

Вы можете стянуть изменения из ветки коллеги (`feature-B`) в свою (`feature-A`).

```bash
# Находясь в ветке feature-A
git pull origin feature-B
```

Это создаст коммит слияния, объединяющий `feature-B` в `feature-A`.

**Сценарий 3: Использование `pull --rebase` для чистой истории**

Чтобы избежать лишних коммитов слияния (`Merge branch 'main' into...`), особенно при обновлении своей feature-ветки из `main`, используйте `pull` с флагом `--rebase`.

```bash
# Находясь в своей feature-ветке
git pull --rebase origin main
```

Это перебазирует ваши локальные коммиты поверх последних изменений из `origin/main`, создавая линейную историю.

#### Как посмотреть изменения после `git fetch`

После `git fetch` вы можете сравнить состояние сервера с вашей локальной работой, прежде чем сливать изменения.

1. **Посмотреть список новых коммитов (краткий обзор):**

    ```bash
    # Показывает коммиты, которые есть в origin/main, но еще нет в вашем локальном main
    git log main..origin/main
    ```

2. **Посмотреть все изменения в коде (детально):**

    ```bash
    # Показывает diff между вашей локальной веткой main и удаленной origin/main
    git diff main..origin/main
    ```

3. **Посмотреть файл целиком (как он выглядит на сервере):**

    ```bash
    # Синтаксис: git show <удаленная_ветка>:<путь_к_файлу>
    git show origin/main:src/app/main.go
    ```

    Эта команда покажет содержимое конкретного файла из удаленной ветки, не затрагивая вашу локальную версию.

### Отправка изменений в удаленный репозиторий

#### `git push`: Отправка локальных коммитов

```bash
# Отправляет локальные коммиты текущей ветки в удаленную ветку с тем же именем на 'origin'
git push origin <имя_ветки>
```

#### Связать локальную ветку с удалённой и отправить изменения

При первом `push` новой локальной ветки:

```bash
git push --set-upstream origin <имя_ветки>
# Или краткая форма: git push -u origin <имя_ветки>
```

Это установит связь между вашей локальной веткой и удаленной, так что последующие `git pull` и `git push` не потребуют указания удаленного репозитория и ветки.

#### Принудительная отправка (Используйте с осторожностью!)

* **`git push --force`**: Перезаписывает историю в удалённой ветке, без проверки. **Крайне опасно**, может привести к потере работы у других разработчиков.
* **`git push --force-with-lease`**: Более безопасная версия принудительной отправки. Она отклонит push, если кто-то другой внёс изменения в удалённую ветку после вашего последнего `fetch`, тем самым предотвращая случайную перезапись чужих изменений.

    > Для глубокого понимания рисков, связанных с принудительной отправкой и переписыванием истории, обратитесь к разделу [Манипуляции с историей: отмена, исправление и переписывание - "Золотое правило" Git](./git_history_manipulation.md#золотое-правило-git-публичная-vs-приватная-история).
