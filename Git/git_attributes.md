# Атрибуты Git — обработка файлов

**Актуально для:** Git 2.49+ (атрибуты `delta` и `builtin_objectmode` добавлены в 2.49.0; `--attr-source`/`--source` — с 2.41.0; проверено по gitattributes(5) из Git 2.56.0)

## Определения

**`.gitattributes`** — декларативный конфигурационный файл Git, определяющий правила обработки конкретных путей (файлов и директорий). Файл хранится в корне репозитория и коммитится в историю, что обеспечивает единые правила обработки для всех участников проекта при клонировании.

Он позволяет управлять:
- Нормализацией окончаний строк (CRLF ↔ LF).
- Внешними фильтрами clean/smudge (LFS, шифрование, сжатие).
- Драйверами сравнения (diff) и слияния (merge) для бинарных и текстовых форматов.
- Метаданными для внешних инструментов (например, GitHub Linguist).
- Исключением файлов из архивов (`git archive`).

Правила применяются на основе сопоставления путей с помощью glob-паттернов; при совпадении нескольких паттернов побеждает последняя строка файла — для каждого атрибута отдельно.

## Базовые концепции

### Принцип работы и иерархия

Git проверяет атрибуты в следующем порядке (от низшего приоритета к высшему):

1. **Системный файл** — `$prefix/etc/gitattributes` (обычно `/etc/gitattributes`), атрибуты для всех пользователей системы.
2. **Глобальный файл** — путь задается через `git config --global core.attributesFile` или используется по умолчанию `$XDG_CONFIG_HOME/git/attributes` (обычно `~/.config/git/attributes`). Атрибуты для всех репозиториев одного пользователя.
3. **`.gitattributes` в директории файла**, затем родительские директории до корня worktree — чем дальше файл `.gitattributes` от проверяемого пути, тем ниже его приоритет. Корневой `/.gitattributes` — базовые правила проекта, распространяемые через Git; вложенные `/path/to/.gitattributes` переопределяют правила для подкаталогов.
4. **`.git/info/attributes`** — локальные правила репозитория, не коммитятся, **высший приоритет**. Предназначены для личных настроек, которые не должны влиять на других участников проекта.

Когда `.gitattributes` отсутствует в рабочей директории, используется его копия из индекса; при check-out сначала читается `.gitattributes` из индекса, а рабочая копия служит fallback'ом.

#### Правила сопоставления путей (Pattern Matching)

Правила сопоставления те же, что и в `.gitignore`, с двумя исключениями: **отрицание (`!pattern`) запрещено**, а паттерн, совпадающий с директорией, **не распространяется рекурсивно** на содержимое (синтаксис `path/` бесполезен — используйте `path/**`).

- `*` — соответствует любому количеству символов внутри одного компонента пути (не пересекает `/`).
- `?` — ровно один символ.
- `**` — рекурсивное соответствие любому количеству директорий и файлов (актуально для сложных монорепозиториев).
- Паттерн, содержащий `/` (не только в начале), считается относительным к директории, в которой лежит сам `.gitattributes`. Паттерн без `/` сопоставляется с именем файла в любой директории.
- Строки, начинающиеся с `#`, — комментарии; начальные и конечные пробелы игнорируются; паттерн в двойных кавычках разбирается в C-стиле (для путей с пробелами и спецсимволами).
- Чувствительность к регистру определяется `core.ignoreCase` (по умолчанию зависит от файловой системы).

**Сброс атрибута:** если нужно вернуть атрибут в состояние `Unspecified` для пути, подпишите имя атрибута восклицательным знаком — `!attr` (например, `generated/*.go !linguist-generated`). Это не отмена паттерна из родительского файла, а переключение состояния атрибута.

#### Механизм фильтрации (Clean & Smudge)

Атрибут `filter` использует два этапа обработки:
- **Clean (Очистка):** Запускается при выполнении `git add`. Преобразует файл из рабочей директории перед сохранением в индекс (например, удаляет секреты, сжимает данные или шифрует содержимое).
- **Smudge (Размазывание):** Запускается при выполнении `git checkout` (или `git pull`). Преобразует файл из индекса перед записью в рабочую директорию (например, вставляет секреты, распаковывает данные или расшифровывает содержимое).

Фильтры регистрируются в `.git/config` (или глобально) и привязаны к имени, указанному в `filter=<name>`. Команды clean/smudge получают содержимое через stdin и пишут результат в stdout — обращаться к файлу на диске нельзя (его версия может отличаться от рабочей директории). В строке команды плейсхолдер `%f` заменяется на имя обрабатываемого файла. Для долгих фильтров есть режим `filter.<name>.process` — один запуск процесса на всю команду Git (long-running process protocol).

**Отсутствие фильтра — не ошибка:** если драйвер не определён в конфиге или завершается с ненулевым кодом, Git молча пропускает его (passthru). Чтобы отсутствие фильтра стало ошибкой, задайте `filter.<name>.required = true`.

**Пример пары фильтров:**
```bash
# .git/config
[filter "remove-timestamp"]
    clean = sed '/^Date: /d'
    smudge = echo "Date: $(date)"
```

```gitattributes
# .gitattributes
documents/*.md filter=remove-timestamp
```
При `git add` строка `Date: ...` удаляется перед сохранением в индекс. При `git checkout` в рабочую директорию добавляется текущая дата.

### Основные атрибуты

| Атрибут | Описание |
| :--- | :--- |
| `text` | Включает нормализацию окончаний строк: при check-in в индексе всегда LF. `text=auto` — Git сам определяет текстовые файлы. Атрибут не задан — применяется `core.autocrlf`. |
| `eol=lf` / `eol=crlf` | Принудительный тип окончаний строк в рабочей директории при check-out. Действует только при заданном `text`/`text=auto`, но сам автоматически задаёт `text`, если тот не указан. |
| `working-tree-encoding=<enc>` | Перекодирование файла при check-in/check-out: хранение в Git как UTF-8, работа в другой кодировке. Значения — из `iconv --list` (например, `UTF-16`, `UTF-16LE`, `UTF-16LE-BOM`). Питфоллы: JGit/libgit2 не поддерживают атрибут; нетривиальные кодировки стоит добавить в `core.checkRoundtripEncoding` (SHIFT-JIS проверяется по умолчанию); перекодирование замедляет операции. |
| `binary` | Макрос: `-diff -merge -text`. Файл обрабатывается как неразбираемый бинарный блок. |
| `crlf` | Legacy-совместимость: `crlf` = `text`, `-crlf` = `-text`, `crlf=input` = `eol=lf`. |
| `ident` | При check-out заменяет `$Id$` на `$Id: <40-символьный SHA blob> $`; при check-in любая последовательность вида `$Id:...$` заменяется обратно на `$Id$`. |
| `filter=<name>` | Применяет внешние фильтры clean/smudge (Git LFS, git-crypt, удаление временных меток). Отсутствие драйвера в конфиге или ненулевой код возврата — не ошибка, а no-op passthru, если не задано `filter.<name>.required = true`. |
| `diff=<name>` | Назначает драйвер генерации diff: внешняя команда (`diff.<name>.command`), преобразование бинарных файлов в текст (`diff.<name>.textconv`), алгоритм (`diff.<name>.algorithm`: `myers`/`patience`/`minimal`/`histogram`) или заголовок hunk (`diff.<name>.xfuncname`). |
| `merge=<name>` | Драйвер слияния. Встроенные: `text` (обычный 3-way), `binary` (оставить версию текущей ветки, но пометить путь конфликтным), `union` (взять строки из обеих версий). `ours` — **не** встроенный: требует определения `[merge "ours"]` в конфиге, иначе Git молча применяет обычный 3-way merge. |
| `conflict-marker-size=<n>` | Длина маркеров конфликтов (по умолчанию 7 символов `<<<<<<<`). Только положительное целое имеет смысл. |
| `export-ignore` | Исключает файл из архива `git archive`. Паттерн, совпадающий с директорией, не распространяется на содержимое — используйте `path/**`. |
| `export-subst` | Подстановка плейсхолдеров `$Format:...$` (формат как у `--pretty=format:`) в файле при архивации. Один плейсхолдер `%(describe)` на архив (защита от DoS). |
| `linguist-*` | Атрибуты для GitHub Linguist: скрытие файлов (`linguist-generated`), изменение статистики языков (`linguist-vendored`), принудительный язык (`linguist-language=<lang>`). |
| `-diff` | Отключает драйвер сравнения для файла (генерируется «Binary files differ» или бинарный патч). Полезно, если паттерн `diff=<name>` задан на уровне директории. |
| `-merge` | Отключает механизм слияния для файла: эквивалентно встроенному драйверу `binary` (наша версия остаётся, путь помечается конфликтным). |
| `-text` | Отключает нормализацию окончаний строк. Используется для файлов, которые должны передаваться без изменений (например, сжатые архивы). На фильтры не влияет. |
| `delta` / `-delta` | `-delta` (`delta=false`) отключает delta-сжатие blob при упаковке в pack (Git 2.49+). Полезно для файлов, которые плохо сжимаются дельтами. |
| `whitespace` | Контроль пробельных ошибок для `diff`/`apply` по пути: set — все ошибки, unset — никаких, не задан — по `core.whitespace`, либо список через запятую (в формате `core.whitespace`). |
| `encoding=<enc>` | Кодировка для GUI-инструментов (gitk, git-gui). Не задан или неверное значение — используется `gui.encoding`. gitk не использует атрибут без явного включения per-file encodings в настройках. |
| `builtin_objectmode=<mode>` | Фильтрация файлов по битовому режиму объекта: `40000`, `120000`, `160000`, `100755`, `100644` — например, `:(attr:builtin_objectmode=160000)` для submodule'ов (Git 2.49+). Проверка: `git check-attr builtin_objectmode -- <file>`. |

### Макро-атрибуты

Макрос — атрибут, который одним именем задаёт сразу несколько других. Встроенный макрос `binary` эквивалентен определению:

```gitattributes
[attr]binary -diff -merge -text
```

Собственные макросы определяются **только в верхнеуровневых** файлах (`$GIT_DIR/info/attributes`, корневой `.gitattributes`, глобальный или системный), но не в `.gitattributes` подкаталогов:

```gitattributes
# Определение макроса
[attr]mybin -text -diff -merge

# Использование
*.psd mybin
```

Макросы могут быть только в состоянии «Set», но эффект может включать set/unset/unspecified других атрибутов (вплоть до возврата в `Unspecified`).

## Практические сценарии

### Сценарий 1: Кроссплатформенная нормализация строк

Рекомендуемая настройка для проектов, где разработчики используют разные ОС (Windows, Linux, macOS).

```gitattributes
# Автоматическое определение текстовых файлов и их нормализация к LF в индексе
* text=auto

# Явное указание для типов файлов
*.sh text eol=lf
*.bash text eol=lf
*.py text

# Файлы, которые должны сохранить CRLF на Windows
*.bat text eol=crlf
*.ps1 text eol=crlf
```

### Сценарий 2: Поддержка специфических кодировок

Иногда инструменты требуют файлы в определенных кодировках (например, PowerShell-скрипты в UTF-16), но в Git их удобнее хранить как UTF-8.

```gitattributes
# Хранить в Git как UTF-8, в рабочей директории — UTF-16 little-endian с BOM
# (при working-tree-encoding документация рекомендует явно задать eol)
*.ps1 text working-tree-encoding=UTF-16LE-BOM eol=crlf
```

Доступные кодировки — `iconv --list`; кодировку существующего файла можно угадать командой `file`. Учтите: JGit и libgit2 не поддерживают `working-tree-encoding`, а нетривиальные кодировки (SHIFT-JIS и др.) стоит добавить в `core.checkRoundtripEncoding`, чтобы Git проверял обратимость конвертации.

### Сценарий 3: Настройка Git LFS и бинарных данных

Подробная информация о LFS — в [git_lfs.md](./git_lfs.md).

```gitattributes
# Обработка изображений и архивов как бинарных данных
*.png binary
*.zip binary

# Передача тяжелых файлов в Git LFS
*.psd filter=lfs diff=lfs merge=lfs
*.mp4 filter=lfs diff=lfs merge=lfs
```

### Сценарий 4: Кастомизация GitHub (Linguist)

Помогает сделать статистику языков в репозитории более точной и скрыть лишние файлы в diff.

```gitattributes
# Пометить директорию как сторонний код (не учитывать в статистике)
vendor/* linguist-vendored
third_party/* linguist-vendored

# Скрывать сгенерированные файлы в pull requests
*.gen.go linguist-generated
api_schema.json linguist-generated

# Принудительно задать язык для файла
*.inc linguist-language=cpp
```

### Сценарий 5: Стратегии слияния для специфических файлов

Помогает избежать конфликтов в файлах, которые генерируются автоматически или имеют специфическую структуру.

Встроенные драйверы слияния: `text` (обычный 3-way), `binary` (оставить версию текущей ветки, но пометить путь конфликтным), `union` (взять строки из обеих версий).

```gitattributes
# Для lock-файлов: при конфликте всегда отдавать предпочтение версии в текущей ветке
package-lock.json merge=ours
yarn.lock merge=ours

# Для файлов, где изменения можно просто объединять (например, списки)
*.iml merge=union
history.log merge=union
```

> **Важно:** `ours` — **не** встроенный драйвер. Без определения в конфиге Git молча применяет обычный 3-way merge (в исходном коде `ll-merge.c`: не найденный драйвер → fallback в `text`). Чтобы `merge=ours` работал, задайте драйвер:

```bash
git config --global merge.ours.name "Keep ours"
git config --global merge.ours.driver true
```

`driver = true` (команда `/bin/true`) ничего не пишет и завершается с кодом 0 — результат остаётся в файле `%A`, то есть наша версия. Альтернатива без конфига: `-merge` (встроенный драйвер `binary`) — тоже оставляет нашу версию, но помечает файл как конфликтный.

**Внимание с `union`:** строки из обеих версий попадают в результат в произвольном порядке — результат нужно проверять вручную.

### Сценарий 6: Управление содержимым архивов

Используется для исключения служебных файлов из релизных архивов `git archive`.

```gitattributes
# Не включать тесты и конфигурацию CI в архив
# (паттерн на директорию не распространяется на содержимое — нужен /**)
/tests/** export-ignore
.github/** export-ignore
.gitignore export-ignore

# Подставлять версию в специальный файл
version.txt export-subst
```
*Файл `version.txt` может содержать: `Last commit: $Format:%H$`.*

### Сценарий 7: Перенормализация существующих файлов

Если вы добавили правила `text=auto` в середине проекта, файлы в репозитории могут остаться с неправильными окончаниями строк. Чтобы применить новые правила ко всему проекту:

```bash
# 1. Добавьте .gitattributes с нужными правилами
# 2. Выполните перенормализацию
git add --renormalize .

# 3. Проверьте статус и закоммитьте изменения
git status
git commit -m "style: переформатирование окончаний строк согласно .gitattributes"
```

### Сценарий 8: Кастомные драйверы сравнения (diff) для бинарных файлов

Позволяет просматривать текстовые отличия в бинарных форматах (например, PDF, Word, EXIF-данные изображений) с помощью внешних утилит `textconv`.

```gitattributes
# .gitattributes
*.pdf diff=pdf
*.jpg diff=exif
```

Затем настройте драйверы в `git config`:
```bash
# Для PDF (требуется pdftotext)
git config diff.pdf.textconv pdftotext

# Для изображений (требуется exiftool)
git config diff.exif.textconv exiftool

# Кэшировать вывод textconv (ускоряет повторные diff)
git config diff.exif.cachetextconv true
```

**Важные ограничения textconv:**
- Конвертация односторонняя: diff из textconv **нельзя применить** (`git apply`). `git format-patch` никогда не использует textconv — отправляйте такой diff отдельно, как комментарий к обычному бинарному патчу.
- Если нужно treat файл как бинарный, но при этом показывать textconv-вывод, задайте `diff.<name>.binary = true` (нельзя одновременно указать `-diff` и `diff=<name>`).
- Для алгоритма diff по пути: `git config diff.<name>.algorithm histogram` (`myers`/`patience`/`minimal`/`histogram`). Для кастомного заголовка hunk: `git config diff.<name>.xfuncname '<regex>'` (встроенные паттерны: `ada`, `bash`, `cpp`, `csharp`, `css`, `golang` и др.).

### Сценарий 9: Прозрачное шифрование секретов (git-crypt)

`git-crypt` позволяет шифровать отдельные файлы при сохранении в репозиторий и расшифровывать их при извлечении, не раскрывая содержимое участникам без ключа. Интегрируется через пару фильтров `clean`/`smudge`.

**1. Инициализация и настройка доступа:**
```bash
git-crypt init
git-crypt add-gpg-user user@email.com
```

**2. Определение файлов в `.gitattributes`:**
```gitattributes
# Шифровать файлы переменных окружения
*.env filter=git-crypt diff=git-crypt

# Шифровать JSON с секретами
config/secrets.json filter=git-crypt diff=git-crypt
```

**3. Проверка статуса:**
```bash
git-crypt status -v
# → documents/secrets.json: encrypted
# → README.md: not encrypted
```

**Валидация:**
```bash
# Убедиться, что в индексе файл зашифрован
git show HEAD:config/secrets.json | head -n 3
# → (двоичные данные, текст нечитаем)

# После checkout файл должен быть расшифрован
cat config/secrets.json
# → {"api_key": "secret-value", ...}
```

### Сценарий 10: Синхронизация с EditorConfig

`EditorConfig` управляет тем, как редактор **пишет** файл, а `.gitattributes` — тем, как Git **хранит** его и обрабатывает при коммите/чекауте. Несинхронизированные настройки приводят к бесконечным изменениям окончаний строк.

**Рекомендуемая конфигурация:**

```editorconfig
# .editorconfig
root = true

[*]
end_of_line = lf
insert_final_newline = true
```

```gitattributes
# .gitattributes
* text=auto eol=lf
```

**Диагностика конфликтов:**
```bash
# Проверить атрибуты Git
git check-attr text eol path/to/file
# → path/to/file: text: set
# → path/to/file: eol: lf

# Проверить, что файл не меняется после checkout
git checkout -- path/to/file
git diff --stat
# → (пусто)
```

**Типичная ошибка:** Если `.gitattributes` не настроен, на Windows Git может автоматически конвертировать `LF` в `CRLF` при чекауте, а EditorConfig вернет `LF` при сохранении — файл будет «грязным» без реальных изменений.

### Сценарий 11: Кастомные фильтры (не LFS)

Помимо Git LFS, фильтры clean/smudge могут использоваться для автоматической обработки содержимого файлов. Типичные сценарии: удаление временных меток, подстановка версий, нормализация форматов.

**Пример: удаление временных меток из документов перед коммитом:**

```bash
# .git/config
[filter "strip-date"]
    clean = sed '/^Date: /d'
    smudge = echo "Date: $(date '+%Y-%m-%d %H:%M:%S')"
```

```gitattributes
# .gitattributes
*.md filter=strip-date
```

При `git add` строка `Date:` удаляется, и в индекс попадает «чистый» документ. При `git checkout` в рабочую директорию добавляется текущая дата.

**Слияние с фильтрами:** если файл имеет clean/smudge-фильтр, слияние веток с разными атрибутами порождает ложные конфликты. Конфиг `merge.renormalize = true` заставляет Git виртуально прогнать все три стадии через clean/smudge перед 3-way слиянием:

```bash
git config merge.renormalize true
```

**Пример: автоматическая подстановка версии:**
```bash
# .git/config
[filter "inject-version"]
    clean = sed 's/{{VERSION}}/1.0.0/g'
    smudge = sed 's/1.0.0/{{VERSION}}/g'
```

```gitattributes
version.h filter=inject-version
```

### Сценарий 12: Валидация `.gitattributes` в CI/CD

Ошибки в атрибутах (неуказанные паттерны, неверные драйверы) часто обнаруживаются только на машинах разработчиков. Добавьте проверку в пайплайн:

```yaml
# .github/workflows/lint.yml
jobs:
  gitattributes:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Verify attributes syntax
        run: |
          # Атрибуты для реальных файлов (check-attr принимает пути, не globs)
          git check-attr -a -- .gitattributes package-lock.json
          # То же, но только из индекса (игнорирует рабочую директорию)
          git check-attr --cached -a -- package-lock.json
          # Атрибуты из другого коммита/ветки (Git 2.41+)
          git check-attr --source=HEAD~1 -a -- package-lock.json

      - name: Ensure LFS tracking is valid
        run: |
          git lfs ls-files
          # Проверить, что tracked-файл имеет filter=lfs в .gitattributes
          git check-attr filter -- path/to/model.psd
```

### Сценарий 13: Кастомные драйверы слияния (merge)

Для бинарных или специализированных форматов, где встроенные стратегии `ours`/`union`/`binary` недостаточны, можно определить собственный драйвер слияния.

**Шаг 1. Определите драйвер в `git config`:**
```bash
git config --global merge.custom-json.name "Custom JSON merge"
git config --global merge.custom-json.driver "custom-json-merge %A %O %B %L"
```

**Шаг 2. Назначьте драйвер в `.gitattributes`:**
```gitattributes
*.json merge=custom-json
```

Драйвер получает аргументы:
- `%O` — версия общего предка (база слияния).
- `%A` — текущая версия файла (наша ветка); **результат драйвер должен записать в этот файл**.
- `%B` — входящая версия (их ветка).
- `%L` — длина маркера конфликта.
- `%P` — путь файла, в который будет записан результат.
- `%S`, `%X`, `%Y` — метки конфликта для предка, локальной и входящей ветки.

Коды возврата: `0` — слияние чистое, результат записывается в индекс; ненулевой — конфликт; больше 128 — драйвер «упал» (например, SEGV), слияние считается проваленным (это не конфликт).

Для драйвера можно задать `merge.<name>.recursive` — драйвер для внутренних слияний при нескольких общих предках (по умолчанию — он сам):

```bash
git config --global merge.custom-json.recursive binary
```

## Дополнительная информация

### .gitattributes vs .gitignore

| Характеристика | .gitignore | .gitattributes |
| :--- | :--- | :--- |
| **Цель** | Исключение файлов из индекса | Определение способа обработки файлов |
| **Влияние** | Файлы не попадают в репозиторий | Файлы в репозитории, но обрабатываются иначе |
| **Сценарии** | Логи, билд-артефакты, зависимости | EOL, LFS, шифрование, кодировки |

### Отладка и диагностика

Для проверки того, какие атрибуты применяются к конкретному файлу, используйте команду `git check-attr`.

```bash
# Проверить все атрибуты для файла
git check-attr -a -- path/to/file
# → path/to/file: text: auto
# → path/to/file: filter: lfs

# Проверить конкретный атрибут для группы файлов
git check-attr diff -- a.json b.json

# Только из индекса (игнорирует рабочую директорию)
git check-attr --cached -a -- path/to/file

# Пути со stdin (по одному на строку)
git ls-files | git check-attr --stdin -a

# Атрибуты из другого дерева/коммита (Git 2.41+)
git check-attr --source=HEAD~1 -a -- path/to/file

# Любая команда — читать атрибуты из заданного дерева (Git 2.41+)
git --attr-source=main diff
GIT_ATTR_SOURCE=main git diff
```

### Работа в bare-репозиториях

В bare-репозиториях нет рабочей директории, поэтому `.gitattributes` из неё не читается. Важная деталь версий: Git 2.43–2.45 по умолчанию читал атрибуты из дерева HEAD в bare-репозиториях, но в Git 2.46 это отменили (сильные последствия для производительности) — сейчас bare-репозиторий по умолчанию **не** читает `.gitattributes` из HEAD.

Явно указать источник атрибутов:

```bash
# Через конфиг (невалидное значение игнорируется — используется пустое дерево)
git config attr.tree main

# Разово для одной команды (Git 2.41+)
git --attr-source=main diff
GIT_ATTR_SOURCE=main git diff

# git archive: использовать атрибуты рабочей директории
git archive --worktree-attributes HEAD
```

Опции `--attr-source` и переменная `GIT_ATTR_SOURCE` имеют приоритет над `attr.tree`. Если `attr.tree` не разрешается в валидный объект, используется пустое дерево (все атрибуты «unspecified»).

### Типичные ошибки и диагностика

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **Фильтр не применяется** | Исполняемый файл фильтра отсутствует в `PATH` или имеет неверные права | Убедитесь, что фильтр установлен и доступен: `which <filter-name>` |
| **LFS-указатель вместо реального файла** | Файл добавлен в индекс до настройки `filter=lfs` или правило `.gitattributes` не закоммичено | Выполнить `git lfs migrate import --include="*.psd" --everything` или добавить правило и перенормализовать |
| **Неверные окончания строк после клонирования** | Отсутствует `* text=auto` в `.gitattributes` или конфликт с `core.autocrlf` | Добавить правило и выполнить `git add --renormalize .` |
| **`merge=ours` не работает** | Драйвер `ours` не определён в конфиге — Git молча применяет обычный 3-way merge | Определить драйвер (`git config merge.ours.driver true`) или использовать `-merge` (встроенный `binary`) |
| **`git archive` включает файлы директории** | Паттерн на директорию (`/tests export-ignore`) не распространяется на содержимое — директории не матчатся рекурсивно | Использовать `/tests/** export-ignore` |
| **Шифрование git-crypt не срабатывает** | GPG-ключ не импортирован или фильтр не настроен в `.git/config` | Выполнить `git-crypt unlock` и проверить `git-crypt status -v` |
| **Производительность падает** | Слишком много правил в `.gitattributes` или сложные glob-паттерны | Упростить паттерны, использовать более специфичные пути, избегать `**` без необходимости |

### Ограничения и крайние случаи

1. **Изменения в индексе:** Атрибуты применяются только к файлам, добавляемым в индекс *после* изменения `.gitattributes`. Чтобы применить новые правила к уже отслеживаемым файлам, используйте `git add --renormalize .`. Без этой команды изменения в индексе не произойдет.

2. **Зависимость от внешних инструментов:** Фильтры (`filter`, `diff`, `merge`) требуют наличия исполняемых файлов на всех машинах. Если разработчик запустит `git checkout` на машине без установленного фильтра, операция завершится ошибкой.

3. **Глобальные атрибуты:** Файл, указанный через `core.attributesFile`, может содержать приватные правила, но они не распространяются через Git. Участники проекта, клонирующие репозиторий, не получат этих правил автоматически.

4. **Negation:** Отрицание паттернов (`!pattern`) **запрещено** в `.gitattributes` (в отличие от `.gitignore`). Вернуть атрибут в состояние `Unspecified` можно записью `!attr` (например, `*.gen.go !linguist-generated`), но это не отмена паттерна из родительского файла.

5. **Case sensitivity:** Чувствительность к регистру паттернов определяется `core.ignoreCase` (по умолчанию зависит от файловой системы). На case-insensitive ФС (Windows, macOS по умолчанию) смешение регистров в именах файлов может давать неожиданные совпадения.

6. **Bare-репозитории и LFS:** В bare-репозиториях отсутствует рабочая директория, поэтому smudge-фильтры (включая LFS) не запускаются автоматически при доступе через `git archive` или веб-интерфейс. С Git 2.46 bare-репозиторий по умолчанию не читает `.gitattributes` из HEAD — для корректной обработки объектов задайте источник атрибутов явно (`attr.tree`, `--attr-source` или `GIT_ATTR_SOURCE`).

7. **Символические ссылки:** Git не следует по символическим ссылкам при доступе к `.gitattributes` в рабочей директории — поведение одинаково при чтении из индекса/дерева и с файловой системы.

### Безопасность

- **Неавторизованные фильтры:** Если в репозитории добавлен `.gitattributes` с фильтром, который выполняет произвольный код при `git add` или `git checkout`, это может привести к выполнению вредоносного кода на машине разработчика. Никогда не добавляйте правила с фильтрами из непроверенных источников.
- **git-crypt и ключи:** Утерянный GPG-ключ делает невозможным расшифровку файлов в репозитории. Рекомендуется использовать несколько ключей (основной + резервный) и регулярно проверять доступ.
- **LFS и размер:** Настройки LFS в `.gitattributes` не предотвращают добавление файлов в обычный индекс, если LFS не инициализирован (`git lfs install`). Файлы, добавленные до инициализации LFS, останутся в истории как обычные объекты, увеличивая размер репозитория.
