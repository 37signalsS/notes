# Маппинг авторов в Git (.mailmap)

**Актуально для:** Git 2.32–2.56

## Определения

**`.mailmap`** — текстовый файл, используемый для сопоставления (маппинга) различных имен и email-адресов авторов с их единой, канонической идентичностью в истории репозитория. Файл обычно версионируется (хранится в корне репозитория), что позволяет всей команде видеть унифицированную историю.

**Каноническая идентичность** — эталонное сочетание имени и email автора, которое Git должен использовать при выводе статистики и истории, даже если в метаданных коммитов указаны другие данные.

---

## Базовые концепции

### Назначение

Механизм `mailmap` решает проблему "раздвоения" личностей в истории проекта, которая возникает из-за:
* Использования разных email-адресов (личный, рабочий, корпоративный).
* Опечаток в имени или email при настройке `git config`.
* Смены фамилии или предпочтительного написания имени.
* Изменения политики корпоративных адресов.
* Объединения нескольких независимых репозиториев в один (monorepo).

### Форматы записей

В файле `.mailmap` поддерживается четыре типа записей. Порядок аргументов: **СНАЧАЛА канонические данные, ЗАТЕМ заменяемые**.

| Формат | Описание |
| :--- | :--- |
| `Proper Name <proper@email.xx>` | Простая форма. Заменяет только email на `proper@email.xx`, оставляя имя без изменений. |
| `<proper@email.xx> <commit@email.xx>` | Заменяет только email для всех коммитов с `commit@email.xx`. |
| `Proper Name <proper@email.xx> <commit@email.xx>` | Заменяет и имя, и email для коммитов с `commit@email.xx`. |
| `Proper Name <proper@email.xx> Commit Name <commit@email.xx>` | Заменяет имя и email, если в коммите указаны именно `Commit Name` и `commit@email.xx`. |

**Особенности синтаксиса:**
* **Комментарии:** Строки, начинающиеся с `#`, игнорируются.
* **Регистр:** Сравнение имен и email-адресов происходит **регистронезависимо** (case-insensitive). Это подтверждено исходным кодом Git — используется `strcasecmp`/`strncasecmp`.
* **Порядок правил:** Если для одного и того же старого email-адреса указано несколько правил, Git использует **последнее найденное** в файле (не первое). Реализация — хэш-таблица по email, где каждая новая запись для того же ключа перезаписывает предыдущую (см. `add_mapping` в `mailmap.c`). При наличии нескольких записей для одного email с разными именами (сложная форма) используется **последняя** такая запись.
* **Символические ссылки:** Git **не следует** по символическим ссылкам при доступе к `.mailmap` в рабочей директории. Это обеспечивает согласованное поведение при доступе к файлу из индекса, дерева или файловой системы.

### Плейсхолдеры для вывода

При использовании `git log --format` важно различать плейсхолдеры, которые учитывают маппинг, и те, что выводят "сырые" данные:

| Тип | Сырые данные | С учетом Mailmap |
| :--- | :--- | :--- |
| **Имя автора** | `%an` | `%aN` |
| **Email автора** | `%ae` | `%aE` |
| **Имя коммиттера** | `%cn` | `%cN` |
| **Email коммиттера** | `%ce` | `%cE` |

### Приоритет и расположение

Git ищет правила в следующем порядке. Каждый последующий источник **перезаписывает** предыдущий для того же email-адреса (внутри одного источника побеждает **последняя** запись для email). Реализация — хэш-таблица по email в `mailmap.c`, где `string_list_insert` заменяет существующую запись:

1.  **Локальный конфиг:** Файл, указанный в `git config mailmap.file`. Высший приоритет.
2.  **Git-объект (Blob):** Объект, указанный в `mailmap.blob`. Позволяет хранить правила в отдельной ветке или ссылаться на конкретный коммит:
    ```bash
    git config mailmap.blob "HEAD:.mailmap"
    ```
3.  **Корень репозитория:** Файл `.mailmap` в рабочей директории. При отсутствии рабочей копии (bare-репозиторий) `.mailmap` не читается — тогда используется `mailmap.blob` со значением по умолчанию `HEAD:.mailmap`.
4.  **Глобальный конфиг:** Файл, указанный в `git config --global mailmap.file`. Низший приоритет.

**Особенности:**
* Источники читаются в порядке 3 → 2 → 1 (и 4 отдельно), но результат складывается с перезаписью: локальный `mailmap.file` всегда побеждает над глобальным и над `.mailmap` в рабочей директории.
* `mailmap.blob` перекрывает `.mailmap` в рабочей директории, но уступает локальному `mailmap.file`.
* Глобальный `mailmap.file` применяется только тогда, когда локальный `mailmap.file` не задан.

### Особенности инструментов

* **Локальные инструменты:** `git log`, `git shortlog`, `git blame` и `git check-mailmap` по умолчанию учитывают `.mailmap`. Флаг `--no-mailmap` (или `--no-use-mailmap`) отключает маппинг для любой команды.
* **GitHub:** Поддержка частичная.
    * **Комиты:** Веб-интерфейс обычно отображает оригинальные данные коммита.
    * **График вклада:** Может использовать `.mailmap` для консолидации (обновление занимает до 24ч), но самый надежный способ — добавить все email в настройки профиля GitHub.
    * **GitHub API:** Запросы к API возвращают сырые данные коммита; маппинг не применяется.
* **GitLab:** Уважает `.mailmap` в статистике проекта, но для корректного связывания коммитов с профилем пользователя email должны быть подтверждены в аккаунте.
* **Bitbucket:** Поддержка `.mailmap` отсутствует; рекомендуется добавлять все email в профиль.
* **IDE (VS Code, IntelliJ, Eclipse):** По умолчанию включают поддержку `.mailmap`. После изменения `.mailmap` может потребоваться перезапуск IDE или инвалидация кэша отображения авторов.

### Предварительные требования

* **Версия Git:** Рекомендуется Git 2.32+ (механизм mailmap введён в 2.32.0 и стабилен до текущей версии 2.56+). Параметры `--mailmap-file` и `--mailmap-blob` для `git check-mailmap` доступны с Git 2.31+.
* **Базовые знания:** Понимание структуры коммитов в Git (автор vs коммиттер, метаданные). Подробнее — в [Основы Git](./git_basics.md).
* **Настройка Git:** Должны быть настроены `user.name` и `user.email`. Подробнее — в [Конфигурация Git](./git_configuration.md).

## Практические сценарии

### Сценарий 1: Объединение истории после смены email

Разработчик использовал личный почтовый ящик до перехода на корпоративный:

```text
# .mailmap
Ivan Petrov <ivan@corp.com> <ivan.p@gmail.com>
Ivan Petrov <ivan@corp.com> <ivan@old-job.com>
```

**Валидация:**
```bash
# Проверить, что старые email маппятся на новый
git check-mailmap "Ivan Petrov <ivan.p@gmail.com>"
# → Ivan Petrov <ivan@corp.com>

git check-mailmap "Ivan Petrov <ivan@old-job.com>"
# → Ivan Petrov <ivan@corp.com>

# Проверить статистику (дубли должны объединиться)
git shortlog -sne --all | grep "Ivan"
# → 215  Ivan Petrov <ivan@corp.com>
```

**Edge cases:**
* Если разработчик коммитил без настроенного email (через дефолтный), маппинг может не сработать — проверьте "сырые" данные через `git log --format="%an <%ae>"`.
* Email в коммите должен точно совпадать (включая регистр домена — сравнение case-insensitive).

### Сценарий 2: Исправление опечаток в именах

```text
# .mailmap
Alexander Ivanov <alex@corp.com> Alex Ivanov <alex@corp.com>
Alexander Ivanov <alex@corp.com> A. Ivanov <alex@corp.com>
```

**Валидация:**
```bash
# Проверить различные варианты написания
git check-mailmap "Alex Ivanov <alex@corp.com>"
# → Alexander Ivanov <alex@corp.com>

git check-mailmap "A. Ivanov <alex@corp.com>"
# → Alexander Ivanov <alex@corp.com>

# Убедиться, что статистика объединилась
git shortlog -sne | grep -i "alexander\|alex\|a."
# → 142  Alexander Ivanov <alex@corp.com>
```

**Edge cases:**
* Если имя содержит спецсимволы (дефисы, апострофы), убедитесь в точном совпадении строк.
* Маппинг работает только для отображения — метаданные коммита не изменяются.

### Сценарий 3: Проверка правил через `check-mailmap`

Инструмент позволяет проверить, как Git преобразует конкретную строку автора (доступен с Git 1.8.4; опции `--mailmap-file` и `--mailmap-blob` — с Git 2.31+):

```bash
# Проверка строки
git check-mailmap "Alex Ivanov <alex@corp.com>"
# → Alexander Ivanov <alex@corp.com>

# Проверка через файл (указать свой .mailmap)
git check-mailmap --mailmap-file=custom-mailmap.txt "Old Name <old@mail.com>"
# → New Name <new@mail.com>

# Проверка через blob из репозитория
git check-mailmap --mailmap-blob=HEAD:.mailmap "Old Name <old@mail.com>"
# → New Name <new@mail.com>

# Проверка нескольких строк из файла
cat authors.txt | git check-mailmap --stdin
# → Proper Name <proper@email.com>
# → Another Name <another@email.com>
```

**Валидация:**
```bash
# Если правило не найдено — возвращается исходная строка
git check-mailmap "Unknown <unknown@mail.com>"
# → Unknown <unknown@mail.com>
```

**Edge cases:**
* `check-mailmap` использует все источники маппинга (локальный `.mailmap`, глобальный, `mailmap.file`, `mailmap.blob`).
* Для проверки конкретного файла используйте `--mailmap-file`.
* `--mailmap-blob` позволяет проверить правила из конкретного коммита/ветки без checkout.
* При одновременном использовании `--mailmap-file` и `--mailmap-blob` приоритет отдаётся `--mailmap-file` (подтверждено в исходном коде `git-check-mailmap.c`).

### Сценарий 4: Глобальная настройка для всех проектов

Если вы хотите видеть свои старые коммиты под новым именем во всех локальных репозиториях:

```bash
# Создать глобальный файл
echo "My Name <me@current.com> <me@old.com>" >> ~/.git-mailmap
echo "My Name <me@current.com> <me@old-job.com>" >> ~/.git-mailmap

# Настроить Git
git config --global mailmap.file ~/.git-mailmap
```

**Валидация:**
```bash
# Проверить настройку
git config --global mailmap.file
# → /Users/username/.git-mailmap

# Проверить маппинг в любом репозитории
cd /some/repo
git check-mailmap "My Name <me@old.com>"
# → My Name <me@current.com>
```

**Edge cases:**
* Глобальный mailmap применяется ко всем репозиториям на машине — используйте для личных данных.
* Локальный `mailmap.file` в репозитории имеет **высший приоритет** над глобальным и над `.mailmap` в рабочей директории. Если в проекте задан локальный `mailmap.file`, глобальный игнорируется для этого email.
* `.mailmap` в рабочей директории перекрывает глобальный `mailmap.file`.

### Сценарий 5: Анализ истории с использованием mailmap

```bash
# Посмотреть топ контрибьюторов с учетом объединения дублей (-e выводит email)
git shortlog -sne --all
# → 150  Ivan Petrov <ivan@corp.com>
# →  80  Maria Sidorova <maria@corp.com>

# Вывод лога с каноническими данными
git log --format="%aN <%aE> — %s"
# → Ivan Petrov <ivan@corp.com> — feat: add new feature
# → Maria Sidorova <maria@corp.com> — fix: resolve bug

# Сравнение: сырые данные vs маппинг
git log --format="%an <%ae> → %aN <%aE>"
# → ivan.p@gmail.com <ivan.p@gmail.com> → Ivan Petrov <ivan@corp.com>

# Подсчет коммитов конкретного автора (с учетом маппинга)
git log --author="Ivan Petrov" --oneline | wc -l
# → 150
```

**Валидация:**
```bash
# Убедиться, что mailmap работает в логе
git log --format="%aN" | sort -u | grep "Ivan"
# → Ivan Petrov
# (только каноническое имя, без дублей)
```

**Edge cases:**
* `git shortlog` по умолчанию использует mailmap.
* `git log --author` ищет по каноническому имени после маппинга.
* Флаг `--no-mailmap` отключает маппинг для любой команды.

### Сценарий 6: Генерация заготовки .mailmap

Для поиска всех уникальных комбинаций имен и email в истории:

```bash
# Сгенерировать шаблон всех авторов
git log --format="%aN <%aE>" | sort -u > .mailmap.template
# → ivan.p@gmail.com <ivan.p@gmail.com>
# → Ivan Petrov <ivan@corp.com>
# → ivan@old-job.com <ivan@old-job.com>

# Или с использованием mailmap (только уникальные канонические имена)
git log --format="%aN <%aE>" | sort -u
# → Ivan Petrov <ivan@corp.com>
# → Maria Sidorova <maria@corp.com>

# Найти дубли email с разными именами (потенциальные проблемы)
git log --format="%ae %aN" | sort -u | awk '{print $1}' | sort | uniq -d
# → alex@corp.com (используется с разными именами)
```

**Валидация:**
```bash
# Проверить содержимое шаблона
cat .mailmap.template
# → (список уникальных авторов)

# После редактирования .mailmap проверить результат
git shortlog -sne
# → (статистика без дублей)
```

**Edge cases:**
* Шаблон требует ручного редактирования — добавьте канонические имена слева.
* Для больших репозиториев генерация может занять время — используйте `--since` для ограничения.

### Сценарий 7: Работа в Bare-репозиториях или CI/CD

В окружениях, где рабочая копия отсутствует (например, на сервере автоматизации), `.mailmap` в рабочей директории не читается — Git переходит к `mailmap.blob` со значением по умолчанию `HEAD:.mailmap`. Это позволяет брать правила напрямую из базы объектов:

```bash
# Явно указать, что mailmap нужно брать из ветки master
git config mailmap.blob "master:.mailmap"

# Или из конкретного коммита
git config mailmap.blob "abc1234:.mailmap"

# Проверка
git check-mailmap "Old Name <old@mail.com>"
# → New Name <new@mail.com>
```

**Валидация:**
```bash
# Проверить текущую настройку
git config mailmap.blob
# → master:.mailmap

# Проверить, что blob существует
git cat-file -e master:.mailmap && echo "OK"
# → OK
```

**Edge cases:**
* `mailmap.blob` требует, чтобы файл был закоммичен в указанной ветке/коммите.
* Полезно в CI/CD, где рабочая копия может быть минимальной (shallow clone).
* В bare-репозитории `.mailmap` в рабочей директории отсутствует, поэтому `mailmap.blob` становится единственным источником правил.

### Сценарий 8: Настройка для патчей (git send-email)

Если вы отправляете патчи через email, можно настроить маппинг специально для этого инструмента. По умолчанию `sendemail.mailmap` равен `false`, то есть `git send-email` **не** применяет mailmap при отправке писем. Три конфигурационных параметра управляют поведением:

```bash
# Включить mailmap для send-email (аналог --mailmap)
git config sendemail.mailmap true

# Использовать отдельный файл для маппинга при отправке писем
git config sendemail.mailmap.file ~/.git-send-email-map

# Использовать mailmap из конкретного blob
git config sendemail.mailmap.blob "HEAD:.mailmap"

# Отключить маппинг для send-email (значение по умолчанию)
git config sendemail.mailmap false
```

**Валидация:**
```bash
# Проверить настройку
git config sendemail.mailmap
# → false

# Проверить send-email без отправки (dry-run)
git send-email --dry-run --to=test@example.com HEAD~1
# → (вывод с оригинальными данными автора, так как mailmap отключён)

# Проверить с включённым mailmap
git config sendemail.mailmap true
git send-email --dry-run --to=test@example.com HEAD~1
# → (вывод с каноническими именами автора)
```

**Edge cases:**
* `sendemail.mailmap` — булев флаг (true/false), **независим** от обычного `mailmap.file`. По умолчанию `false`.
* `sendemail.mailmap.file` и `sendemail.mailmap.blob` добавляют **дополнительные** правила поверх стандартного mailmap; записи в них имеют приоритет над записями в обычном mailmap.
* Отключение (`false`) полезно, если патчи должны содержать оригинальные данные автора (например, для соответствия правилам рассылки).

### Сценарий 9: Массовый импорт истории из другого репозитория

При объединении репозиториев в monorepo разработчики могут иметь разные идентичности:

```bash
# 1. Импортировать историю (например, через git fetch + merge)
git fetch ../old-repo.git main:old-main
git merge old-main --allow-unrelated-histories
# → Merge made by the 'ort' strategy.

# 2. Сгенерировать .mailmap из объединенной истории
git log --format="%aN <%aE>" | sort -u > .mailmap.template

# 3. Отредактировать .mailmap для объединения дублей
cat >> .mailmap << 'EOF'
Ivan Petrov <ivan@corp.com> Ivan P. <ivan@old-repo.com>
Ivan Petrov <ivan@corp.com> ivan.petrov@personal.com
EOF

# 4. Проверить результат
git shortlog -sne | head -20
# → 500  Ivan Petrov <ivan@corp.com>
# → 300  Maria Sidorova <maria@corp.com>
```

**Валидация:**
```bash
# Проверить, что история объединилась корректно
git log --format="%aN <%aE>" | sort | uniq -c | sort -rn | head
# → 500 Ivan Petrov <ivan@corp.com>
# → 300 Maria Sidorova <maria@corp.com>
# → (без дублей)
```

**Edge cases:**
* При импорте через `git filter-branch` или `git filter-repo` метаданные авторов сохраняются — mailmap применяется поверх уже переписанной истории.
* `git filter-repo` (современная замена filter-branch) имеет встроенную поддержку `--mailmap` для переписывания авторов во время фильтрации:
  ```bash
  git filter-repo --mailmap .mailmap
  ```
* Для SVN→Git миграции используйте `git svn clone --authors-file=authors.txt`.
* При очень больших репозиториях (100к+ коммитов) генерация `.mailmap.template` может занять время — используйте `--since` для ограничения диапазона.

### Сценарий 10: Интеграция с IDE и инструментами анализа

Настройка mailmap для корректного отображения в IDE и инструментах:

```bash
# Проверить, что mailmap работает в git blame
git blame README.md | head -5
# → abc1234 (Ivan Petrov 2026-08-20) line content

# Отключить mailmap для blame (если нужны оригинальные данные)
git blame --no-mailmap README.md | head -5
# → abc1234 (ivan.p@gmail.com 2026-08-20) line content

# Проверка через git log с графикой
git log --graph --format="%h %aN <%aE>" --all | head -20
# → * abc1234 Ivan Petrov <ivan@corp.com>
# → * def5678 Maria Sidorova <maria@corp.com>
```

**Валидация:**
```bash
# Убедиться, что IDE (VS Code, IntelliJ) использует mailmap
# Настройки IDE: Git → Enable mailmap (включено по умолчанию)
```

**Edge cases:**
* Некоторые IDE требуют перезапуска для применения изменений `.mailmap`.
* `git blame --no-mailmap` полезен для отладки маппинга.
* Если `.mailmap` является символической ссылкой, Git её **не будет читать** — используйте обычный файл или настройте `mailmap.file`.

### Сценарий 11: Производительность на больших репозиториях

Для репозиториев с большим количеством коммитов (100к+) работа с mailmap может замедляться:

```bash
# Ограничить генерацию шаблона последними N коммитами
git log --since="2 years ago" --format="%aN <%aE>" | sort -u > .mailmap.template

# Использовать mailmap.blob вместо файла в рабочей копии (быстрее в CI)
git config mailmap.blob "HEAD:.mailmap"

# Отключить mailmap для быстрых операций чтения
git --no-mailmap log --oneline | head -1000
```

**Валидация:**
```bash
# Измерить время выполнения с mailmap
time git shortlog -sne --all
# real    0m2.500s

# Измерить время без mailmap
time git --no-mailmap shortlog -sne --all
# real    0m1.800s
```

**Edge cases:**
* `--no-mailmap` ускоряет `git log`, `git shortlog`, `git blame` за счёт пропуска обработки правил.
* В shallow clone mailmap не работает — используйте `mailmap.blob`.
* Для очень больших `.mailmap` (1000+ строк) рассмотрите разбивку по командам/подпроектам.

## Troubleshooting

### Типичные ошибки и решения

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| Mailmap не работает | Файл не в корне репозитория или опечатка в имени. | Убедитесь, что `.mailmap` в корне и закоммичен. |
| Дубли не объединяются | Неправильный порядок аргументов (каноническое имя должно быть первым). | Проверьте синтаксис: `Каноническое <email> Старое <email>`. |
| GitHub не показывает объединение | Обновление занимает до 24ч или email не добавлен в профиль. | Добавьте все email в настройки GitHub. |
| `check-mailmap` возвращает исходную строку | Правило не найдено или не совпадает email. | Проверьте регистр и точное совпадение email. |
| Mailmap не применяется в CI | Используется shallow clone или bare-репозиторий. | Настройте `mailmap.blob` для CI. |
| Mailmap игнорируется | `.mailmap` является символической ссылкой. | Используйте обычный файл или настройте `mailmap.file`. |

### Диагностика

```bash
# Проверить, какой mailmap используется
git config --show-origin mailmap.file
# → file:.git/config  (локальная настройка)
# → file:/Users/username/.gitconfig  (глобальная настройка)

# Проверить mailmap.blob
git config mailmap.blob
# → master:.mailmap

# Отладка: проверить конкретную строку
git check-mailmap "Test User <test@example.com>"
# → (вывод с маппингом или исходная строка)

# Проверить, что .mailmap закоммичен
git ls-files .mailmap
# → .mailmap

# Отключить mailmap для диагностики
git --no-mailmap log --format="%an <%ae>" | sort -u
# → (сырые данные без маппинга)
```

## Best Practices

1.  **Создайте `.mailmap` в начале проекта** — это предотвратит накопление дублей в будущем.
2.  **Документируйте маппинг** — добавьте комментарий в начале `.mailmap` с описанием структуры.
3.  **Используйте `check-mailmap` для проверки** — всегда валидируйте правила после добавления.
4.  **Закоммитьте `.mailmap`** — это обеспечит единое отображение истории у всей команды.
5.  **Добавьте все email в профиль GitHub/GitLab** — это дополнительный уровень консолидации.
6.  **Обновляйте mailmap при смене email** — не забывайте добавлять новые правила при смене работы.
7.  **Используйте глобальный mailmap для личных данных** — чтобы не дублировать правила в каждом проекте.
8.  **Проверяйте статистику после изменений** — `git shortlog -sne` покажет результат маппинга.
9.  **Используйте `mailmap.blob` в CI/CD** — работает в shallow clone и bare-репозиториях.
10. **Не используйте символические ссылки для `.mailmap`** — Git их не следует; используйте обычный файл или `mailmap.file`.
11. **Для переписывания истории используйте `git filter-repo --mailmap`** — это быстрее и безопаснее `filter-branch`.
12. **Группируйте правила по командам/подпроектам** в больших monorepo для удобства поддержки.

### Очистка и откат

* **Удаление устаревших правил:** Регулярно проверяйте `.mailmap` на ненужные записи (например, email бывших сотрудников). Удаление строки из `.mailmap` не влияет на историю коммитов — маппинг просто перестаёт применяться.
* **Откат изменений:** Поскольку `.mailmap` влияет только на отображение, а не на метаданные коммитов, откат не требует переписывания истории. Удалите неправильную строку и закоммитьте обновлённый `.mailmap` — изменения вступят в силу немедленно для всех последующих команд.
* **Очистка дублей:** Используйте `git log --format="%ae %aN" | sort -u | awk '{print $1}' | sort | uniq -d` для поиска email, которые используются с разными именами. Это указывает на потенциальные проблемы маппинга.
* **Комментируйте правила:** Добавляйте комментарии `#` в начале `.mailmap` с описанием структуры и назначения правил. Это помогает новым участникам понять, какие изменения требуются при добавлении нового автора.
* **Версионируйте `.mailmap`:** Храните `.mailmap` в корне репозитория и коммитьте его отдельным коммитом при добавлении или изменении правил. Это позволяет отследить историю изменений маппинга.

### Особые случаи и ограничения

* **Ограниченная поддержка платформами:** GitHub, GitLab и Bitbucket не полностью поддерживают `.mailmap`. Рекомендуется добавлять все email в профиль платформы для корректной консолидации.
* **Символические ссылки:** Git не следует по символическим ссылкам при доступе к `.mailmap`. Используйте обычный файл или настройте `mailmap.file`.
* **Shallow clone:** В shallow clone `.mailmap` в рабочей директории может не работать из-за отсутствия полной истории. Используйте `mailmap.blob` для указания конкретного коммита/ветки.
* **Bare-репозитории:** В bare-репозиториях отсутствует рабочая копия, поэтому `.mailmap` не читается. Используйте `mailmap.blob` со значением по умолчанию `HEAD:.mailmap`.
* **Большие `.mailmap` (1000+ строк):** Маппинг может замедлять команды. Рассмотрите разбивку по командам/подпроектам или использование `mailmap.blob` вместо файла в рабочей директории.
* **Отсутствие email в коммите:** Если коммит сделан без настроенного email (через дефолтный шаблон), маппинг может не сработаться. Проверьте сырые данные через `git log --format="%an <%ae>"`.
* **Спецсимволы в именах:** Имена с дефисами, апострофами или пробелами требуют точного совпадения строк. Проверяйте правила через `git check-mailmap`.
* **Маппинг влияет только на отображение:** `.mailmap` не изменяет метаданные коммитов. Для переписывания истории используйте `git filter-repo --mailmap` или `git filter-branch`.
