# Манипуляции с историей: отмена, исправление и переписывание

## Определения

**Переписывание истории (Rewriting History)** — процесс изменения существующих коммитов (содержимого, сообщений, порядка или авторства). Технически это приводит к созданию новых объектов в базе данных Git и генерации новых хэшей (SHA-1), так как идентификатор коммита зависит от его метаданных и состояния дерева файлов.

**Безопасная отмена (Safe Undo)** — метод отмены изменений путем добавления новых коммитов, которые обращают действие предыдущих. Это не изменяет существующую цепочку истории и является единственно верным способом работы в публичных ветках.

**`git reset`** — команда для перемещения указателя текущей ветки и `HEAD` на конкретный коммит. Является основным инструментом переписывания локальной истории.

**`git revert`** — создание нового коммита, который вносит изменения, прямо противоположные целевому коммиту.

**`git commit --amend`** — модификация самого последнего коммита в текущей ветке.

**`git cherry-pick`** — механизм применения изменений, представленных конкретными коммитами, в текущую ветку.

**`git reflog`** — журнал всех перемещений указателя `HEAD`, позволяющий восстановить коммиты, которые перестали принадлежать какой-либо ветке в результате манипуляций.

**`git-filter-repo`** — инструмент для глобального анализа и переписывания всей истории репозитория (удаление файлов, замена почты авторов и т.д.). Рекомендованная замена устаревшему `git filter-branch`.

**`git range-diff`** — инструмент для сравнения двух диапазонов коммитов (например, до и после rebase), позволяющий убедиться, что логика изменений не нарушена при переписывании истории.

## Базовые концепции

### "Золотое правило" Git: Публичная vs Приватная история

Главное правило при манипуляциях с историей: **Никогда не переписывайте историю, которая уже была отправлена в удаленный репозиторий (`push`) и стала доступна коллегам.**

1.  **Приватная история (локальные коммиты):** Вы можете свободно использовать `reset`, `amend` и интерактивный `rebase`, чтобы сделать историю чистой и логичной перед публикацией.
2.  **Публичная история (общие ветки `main`, `develop`):** Используйте только `git revert`. Переписывание хэшей в общих ветках приведет к рассинхронизации локальных копий у всей команды, вызывая конфликты, которые невозможно разрешить обычным слиянием.

### Уровни отмены изменений

Git позволяет откатываться на разных этапах жизненного цикла изменений:
-   **Рабочий каталог:** Изменения в файлах на диске, еще не добавленные в индекс.
-   **Индекс (Staging Area):** Изменения, добавленные через `git add`, но еще не закоммиченные.
-   **Локальные коммиты:** Зафиксированные изменения, еще не отправленные на сервер.
-   **Опубликованные коммиты:** Изменения, уже находящиеся в удаленном репозитории.

### Режимы работы `git reset`

Действие `reset` зависит от флага, который определяет глубину отката:

| Режим | HEAD | Индекс (Staged) | Рабочий каталог (Unstaged) | Применение |
| :--- | :--- | :--- | :--- | :--- |
| `--soft` | Перемещается | Сохраняет изменения | Сохраняет изменения | Отменить коммит, чтобы переделать его (например, объединить с другими). |
| `--mixed` | Перемещается | Сбрасывается | Сохраняет изменения | **Режим по умолчанию.** Убрать изменения из индекса, сохранив их на диске. |
| `--hard` | Перемещается | Сбрасывается | **Удаляет изменения** | **Опасно.** Полный возврат к состоянию коммита. Все незафиксированные правки теряются. |
| `--keep` | Перемещается | Сбрасывается | Сохраняет изменения (но конфликтует, если они пересекаются с целевым коммитом) | Как `--mixed`, но пытается сохранить незакоммиченные изменения в рабочем каталоге. |

### Сравнение `reset` и `revert`

| Критерий | `git reset` | `git revert` |
| :--- | :--- | :--- |
| **Механизм** | Перемещает указатель ветки на другой коммит | Создает новый коммит, отменяющий изменения |
| **История** | **Переписывает** (commits исчезают из графа ветки) | **Сохраняет** (оба коммита остаются в истории) |
| **Безопасность** | Только для локальных/приватных веток | Безопасно для публичных веток (`main`, `develop`) |
| **Дополнительные флаги** | `--soft`, `--mixed`, `--hard`, `--keep`, `--patch` | `-n` (no-commit), `-m` (mainline для merge), `--no-commit` |
| **Возврат** | Через `git reflog` + `git branch recovery <hash>` | Через новый `git revert` отменяющего коммита |
| **Влияние на индекс** | Зависит от флага (`--soft` сохраняет, `--mixed` сбрасывает) | Изменения попадают в индекс (нужен `git commit`) |
| **Пример** | `git reset --hard HEAD~3` — стереть 3 последних коммита | `git revert HEAD~3..HEAD` — отменить 3 последних коммита новыми коммитами |

### Выбор инструмента: Decision Tree

```
Нужно отменить коммит?
├── Коммит НЕ был запушен (локальная работа)
│   ├── Последний коммит → git commit --amend
│   ├── Несколько последних → git reset --soft HEAD~N
│   └── С потерей изменений → git reset --hard HEAD~N
└── Коммит УЖЕ запушен (общая ветка)
    ├── Один коммит → git revert <hash>
    ├── Серия коммитов → git revert A..B
    └── Merge коммит → git revert -m 1 <merge_hash>
```

## Практические сценарии

### Сценарий 1: Исправление локальных ошибок

#### 1.1 Отмена `git add` (убрать файл из индекса)
```bash
# Современный способ
git restore --staged <file>

# Классический способ
git reset <file>
# → Unstaged changes after reset:
# → M	file.txt
```

#### 1.2 Отмена изменений в файле на диске
Возврат файла к состоянию последнего коммита:
```bash
# Современный способ
git restore <file>

# Классический способ (перезаписывает файл!)
git checkout -- <file>
```

#### 1.3 Исправление последнего коммита (`amend`)
```bash
# Добавить забытый файл
git add forgotten_file.txt
# Объединить с последним коммитом без изменения сообщения
git commit --amend --no-edit
# → [main 1a2b3c4] feat: description
# →  Date: Wed Aug 5 2026 ...
# →  2 files changed, 10 insertions(+)

# Изменить только сообщение последнего коммита
git commit --amend -m "feat: корректное описание функционала"

# Изменить автора последнего коммита (например, при работе от чужого аккаунта)
git commit --amend --author="Name <email@example.com>"

# Добавить файлы и объединить с сообщением из файла
git add *.ts
git commit --amend -F commit_message.txt

# Атомарно: добавить все отслеживаемые изменения + изменить сообщение
git commit --amend -am "feat: исправление логики аутентификации"
```

**Важно:** `--amend` перезаписывает последний коммит. Если он уже был отправлен (`push`), потребуется `git push --force-with-lease`. Не используйте `--amend` для коммитов, которые уже доступны другим разработчикам.

### Сценарий 2: Безопасная отмена в общих ветках (`revert`)

#### 2.1 Отмена обычного коммита
```bash
git revert abc1234
# → [main 5e6f7g8] Revert "feat: problematic change"
# →  1 file changed, 1 deletion(-)
```

#### 2.2 Отмена диапазона коммитов
```bash
# Отменить серию коммитов от A до B (не включая A)
git revert A..B

# Отменить серию коммитов, не создавая сразу коммиты (только изменения в индексе)
git revert -n A..B

# Отменить N последних коммитов (автоматическое определение хешей)
git revert HEAD~3..HEAD
```

#### 2.3 Отмена слияния (Merge Commit)
При отмене мерж-коммита нужно указать Git, какая из родительских веток должна остаться "основной" (mainline).
```bash
# -m 1 указывает на первого родителя (ветка, В КОТОРУЮ сливали)
git revert -m 1 <merge_hash>
```

**Полезные флаги:**

| Флаг | Описание |
| :--- | :--- |
| `-e` / `--edit` | Открыть редактор для изменения сообщения коммита |
| `-m` / `--mainline` | Указать родительский коммит для merge (1 — целевая ветка) |
| `-n` / `--no-commit` | Применить отмену без автоматического создания коммита |
| `--no-edit` | Использовать стандартное сообщение без открытия редактора |
| `--signoff` | Добавить Signed-off-by в сообщение |

**Важное замечание:** После `git revert -m 1 <merge_hash>` повторное слияние той же ветки будет проигнорировано Git (-commits already applied). Чтобы повторно интегрировать отмененные изменения, используйте `git revert <revert_hash>` или `git cherry-pick`.

### Сценарий 3: Интерактивное перебазирование (`rebase -i`)

Позволяет полностью перестроить историю последних коммитов.
```bash
# Редактировать последние 5 коммитов
git rebase -i HEAD~5

# Редактировать коммиты с определенного хеша
git rebase -i abc1234
```

**Команды в интерактивном режиме:**

| Команда | Краткая | Действие |
| :--- | :--- | :--- |
| `pick` | `p` | использовать коммит без изменений |
| `reword` | `r` | использовать коммит, но изменить только сообщение |
| `edit` | `e` | остановиться для редактирования содержимого коммита |
| `squash` | `s` | объединить с предыдущим коммитом, объединив сообщения |
| `fixup` | `f` | объединить с предыдущим, отбросив сообщение текущего |
| `drop` | `d` | полностью удалить коммит из истории |
| `exec` | `x` | выполнить shell-команду после этого коммита |
| `break` | `b` | остановиться (для промежуточного сохранения состояния) |
| `label` | `l` | пометить текущую позицию (для `update-ref`) |

**Использование `exec` для автоматизации:**
```bash
# Запустить тесты после каждого коммита для проверки корректности
git rebase -i HEAD~5
# В редакторе замените "pick" на "exec" для нужных коммитов:
# pick abc1234 feat: add login
# exec npm test
# pick def5678 feat: add validation
# exec npm test
```

**Сравнение squash и fixup:**
```bash
# squash: объединяет коммиты И СКЛЕИВАЕТ сообщения
# pick abc1234 feat: add login form
# squash def5678 fix: typo in login
# → Результат: "feat: add login form\n\nfix: typo in login"

# fixup: объединяет коммиты, отбрасывая сообщение текущего
# pick abc1234 feat: add login form
# fixup def5678 fix: typo in login
# → Результат: "feat: add login form"
```

#### Автоматизация через Fixup и Autosquash
Позволяет "подклеивать" правки к старым коммитам без ручного перетаскивания строк в редакторе.
```bash
# 1. Сделать исправление для конкретного коммита
git add .
git commit --fixup <hash_of_target_commit>
# → [feature 2b3c4d5] fixup! feat: target feature

# 2. Запустить автоматическое слияние
git rebase -i --autosquash <base_hash>
```

### Сценарий 4: Выборочный перенос изменений (`cherry-pick`)

Используется для переноса коммитов между ветками без полного слияния. Типичные сценарии: бэкпорт хотфикса в старую релизную ветку, перенос конкретного фикса без всего контекста ветки.

```bash
# Перенести один коммит
git cherry-pick <hash>

# Перенести коммит без автоматического создания коммита (только в индекс)
git cherry-pick -n <hash>

# Перенести коммит и добавить в сообщение ссылку на оригинал (-x)
git cherry-pick -x <hash>
# → [main 3c4d5e6] feat: important fix
# → (cherry picked from commit 1a2b3c4...)

# Перенести диапазон коммитов (от A до B, не включая A)
git cherry-pick A..B

# Перенести диапазон, включая оба коммита
git cherry-pick A^..B
```

#### Обработка конфликтов при cherry-pick
```bash
# Если возник конфликт:
git cherry-pick <hash>
# → CONFLICT (content): Merge conflict in src/auth.js

# 1. Разрешить конфликты в файлах
# 2. Добавить исправленные файлы
git add src/auth.js

# 3. Продолжить (создаст коммит)
git cherry-pick --continue

# Или пропустить текущий коммит
git cherry-pick --skip

# Или отменить весь cherry-pick
git cherry-pick --abort
```

#### Батчинг: перенос нескольких коммитов за раз
```bash
# Перенести несколько коммитов и схлопнуть их в один
git cherry-pick -n A B C
git commit -m "feat: backported fixes from feature branch"

# Перенести коммит с сохранением порядка и проверкой
git cherry-pick --no-commit A..C
git diff --cached   # Проверить, что попало в индекс
git commit -m "feat: batch backport"
```

### Сценарий 5: Валидация после переписывания (`range-diff`)

После сложного rebase хэши меняются. Чтобы убедиться, что содержательная часть (диффы) осталась прежней:
```bash
# Сравнить состояние ветки до и после манипуляций
git range-diff old_branch_head...HEAD

# Сравнить результат rebase с оригиналом
git range-diff main~3..main  # до rebase
git range-diff main~3..main  # после rebase
```

**Примечание:** `range-diff` доступен начиная с Git 2.17. Для более ранних версий используйте `git diff` между парами коммитов или сторонние инструменты (например, `tig`).

### Сценарий 6: Глобальное переписывание (`git-filter-repo`)

Используется для удаления файлов из всей истории (например, если случайно закоммитили секреты), замены email авторов, полного удаления директорий.

**Установка:**
```bash
pip install git-filter-repo
```

**Типичные операции:**

```bash
# Удалить файл secret.txt из всех коммитов во всех ветках
git filter-repo --path secret.txt --invert-paths

# Удалить директорию из всей истории
git filter-repo --path build/ --invert-paths

# Замена email автора во всей истории
git filter-repo --email-callback 'return email.replace(b"old@example.com", b"new@example.com")'

# Замена текста (секретов) во всей истории
git filter-repo --replace-text <(echo 'SECRET_KEY==>REPLACED')

# Удаление коммитов по сообщению (например, "WIP")
git filter-repo --invert-grep --message-correct 'WIP'
```

**Важные ограничения:**
- `git-filter-repo` изменяет хеши **всех** последующих коммитов — после использования потребуется `force-push` и переклонирование всеми участниками.
- Необходимо предварительно сделать `git clone --mirror` для резервного копирования.
- Для open-source проектов рекомендуется опубликовать инструкцию для контрибьюторов о переклонировании.

**Альтернативы:**
- **BFG Repo-Cleaner** — проще в использовании, быстрее для больших репозиториев: `java -jar bfg.jar --delete-files secrets.env`
- **`git filter-branch`** — устаревший, встроен в Git, но медленный и менее надежный. Подробнее см. в **[Устранение неполадок](./git_troubleshooting.md#сценарий-10-удаление-секретов-из-истории-git)**.

### Сценарий 7: Действия при компрометации секрета

**Критический инцидент ИБ.** Если пароль или токен попал в Git и был отправлен в `origin`.

**Пошаговый алгоритм:**

1. **Ротация секрета (НЕМЕДЛЕННО):** Смените скомпрометированный секрет во внешней системе. Считайте, что его уже скопировали, даже если репозиторий приватный.
2. **Удаление из истории:** Используйте `git-filter-repo` (см. Сценарий 6) или BFG:
   ```bash
   # Вариант 1: git-filter-repo
   git filter-repo --path .env --invert-paths
   # Вариант 2: BFG (для больших репозиториев)
   java -jar bfg.jar --delete-files .env
   ```
3. **Принудительное обновление:**
   ```bash
   git push origin --force-with-lease --all
   git push origin --force-with-lease --tags
   ```
4. **Очистка локальных объектов:**
   ```bash
   git reflog expire --expire=now --all
   git gc --prune=now --aggressive
   ```
5. **Уведомление команды:** Все участники должны переклонировать репозиторий или сделать `git rebase origin/main`.

**Профилактика:**
- Установите `gitleaks`, `trufflehog` или `git-secrets` в качестве [pre-commit хуков](./git_hooks.md).
- Используйте `.gitignore` для файлов с секретами.
- Настройте branch protection с запретом прямых пушей в `main`/`develop` (см. [Рабочие процессы](./git_workflows.md#защита-веток-branch-protection)).
- Для Kubernetes-секретов рассмотрите [шифрование](../GitOps/secrets_encryption.md) или external secret managers.

### Сценарий 8: Очистка неотслеживаемых файлов (`git clean`)

Полезно после `git reset --hard`, при удалении веток или после ошибочных операций, когда в рабочем каталоге остались мусорные файлы.

```bash
# Предварительный просмотр: что будет удалено (без удаления)
git clean -n
# → Would remove build/
# → Would remove temp.log

# Удалить неотслеживаемые файлы (без директорий)
git clean -f

# Удалить неотслеживаемые файлы и директории
git clean -fd

# Удалить файлы, игнорируемые через .gitignore (осторожно!)
git clean -fx

# Удалить файлы и директории, игнорируемые через .gitignore
git clean -fdx

# Интерактивный режим (выборочно удалять)
git clean -fdi
```

**Важно:** `git clean` необратим — удаленные файлы не попадают в `reflog`. Всегда начинайте с `git clean -n` (dry-run).

## Восстановление данных

### `git reflog`: Журнал спасения

Подробное руководство по `git reflog` см. в **[Git Reflog — журнал ссылок](./git_reflog.md)**.

**Краткая справка:**
```bash
# 1. Посмотреть журнал
git reflog
# → 1a2b3c4 HEAD@{0}: reset: moving to HEAD~5
# → 5e6f7g8 HEAD@{1}: commit: feat: very important work (ПОТЕРЯНО)

# 2. Восстановить коммит, создав на нем ветку
git branch recovery-branch 5e6f7g8
```

**Важное ограничение:** reflog — строго локальный. Он никогда не передаётся при `git push`. Reflog каждого участника хранит только его историю HEAD.

### `git fsck`: Поиск "висячих" объектов
Если `reflog` не помог, можно найти объекты, которые не связаны ни с одной ссылкой (dangling objects).
```bash
git fsck --lost-found
# → checking connectivity: 100% (123/123), done.
# → dangling commit 5e6f7g8...
# Результаты будут в .git/lost-found/commit/
```

### `ORIG_HEAD` и резервные ссылки
-   **`ORIG_HEAD`:** Сохраняется перед опасными операциями (`merge`, `rebase`, `reset`). Быстрый откат: `git reset --hard ORIG_HEAD`.
-   **`CHERRY_PICK_HEAD`:** Сохраняется при `cherry-pick` для отслеживания текущего коммита.
-   **Блокировки:** Если Git сообщает о запущенном процессе, удалите `.git/index.lock`.

## Типичные ошибки при манипуляциях с историей

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `fatal: ambiguous argument 'X..Y': unknown revision` | Неверный хеш или имя ветки | Проверьте хеш через `git log --oneline -5` |
| `error: cannot 'squash' without a previous commit` | Squash первого коммита в истории | Используйте `fixup` первого коммита или `rebase -i --root` |
| `fatal: refusing to merge unrelated histories` | Слияние репозиториев с независимыми историями | `git merge --allow-unrelated-histories` (осторожно) |
| `CONFLICT (content): Merge conflict in X` | Конфликт при cherry-pick/rebase/merge | Разрешите конфликты в файлах, `git add`, затем `--continue` |
| `fatal: not a valid object name` | Попытка операции с несуществующим коммитом | Проверьте через `git cat-file -t <hash>` |
| `error: pathspec 'X' did not match` | Неверное имя файла или ветки в команде | Проверьте имя через `git branch` или `git status` |
| `fatal: You are not currently on a branch` | Detached HEAD — коммит без ветки | Создайте ветку: `git switch -c new-branch` |
| `fatal: The branch 'X' is not fully merged` | Попытка удалить неслитую ветку с `-d` | Используйте `-D` для принудительного удаления или слейте ветку |
| `error: cannot lock ref 'X': Unable to create lock file` | Файл ссылки заблокирован другим процессом | Удалите `.git/refs/heads/X.lock` или перезапустите терминал |
| `warning: You ran 'git add' with nothing added` | `git add .` при отсутствии изменений | Проверьте `git status` — возможно, изменения уже в индексе |
