# Манипуляции с историей: отмена, исправление и переписывание

**Актуально для:** Git 2.38–2.56.x (локально проверено на Git 2.54.0/2.56.0). Интерактивный rebase и autosquash стабильны с Git 2.18+; `range-diff` — с 2.19; `restore` — с 2.23; `--force-if-includes` — с 2.30; `--fixup=(amend|reword)` — с 2.32; `rebase --update-refs` — с 2.38.

## Определения

* **Переписывание истории (Rewriting History):** Процесс изменения существующих коммитов (содержимого, сообщений, порядка, времени или авторства). Технически приводит к созданию новых объектов в объектной базе данных Git и генерации новых хэшей (SHA-1 / SHA-256), так как идентификатор коммита криптографически зависит от дерева файлов, метаданных и хэшей родителей.
* **Безопасная отмена (Safe Undo / Inverted Commits):** Метод отмены изменений путем добавления новых инвертирующих коммитов, которые обращают действие предыдущих. Не изменяет существующий направленный ациклический граф (DAG) и является единственно допустимым способом работы в общих и публичных ветках.
* **`git reset`:** Команда для перемещения указателя текущей ветки и `HEAD` на целевой коммит с опциональной синхронизацией индекса (Index/Staging Area) и рабочего каталога (Working Tree).
* **`git revert`:** Создание нового коммита, вносящего изменения, зеркально противоположные выбранному коммиту (или последовательности коммитов), без изменения предшествующей истории.
* **`git commit --amend`:** Механизм модификации последнего коммита в текущей ветке путем создания нового объекта коммита с заменой ссылки на вершину ветки.
* **`git rebase`:** Процесс переноса цепочки коммитов на новую базовую точку. В интерактивном режиме (`rebase -i`) позволяет менять порядок, объединять (squash/fixup), редактировать и удалять коммиты, а также выполнять скрипты автоматизации (`exec`).
* **Autosquash:** Механизм автоматической реорганизации коммитов `fixup!` и `squash!` в очереди интерактивного `rebase` без ручного редактирования списка шагов.
* **`git cherry-pick`:** Механизм извлечения дифф-патча конкретного коммита и применения его к текущей ветке в виде нового независимого коммита.
* **`git reflog`:** Локальный журнал всех перемещений ссылок и указателя `HEAD`, служащий ключевым механизмом спасения данных при ошибочных манипуляциях с историей.
* **`git range-diff`:** Инструмент сравнения двух диапазонов коммитов (до и после rebase/amend), сопоставляющий не только изменения кода, но и метаданные каждого коммита в серии.
* **`git-filter-repo`:** Высокопроизводительный инструмент для глубокого анализа и пакетного переписывания всей истории репозитория (удаление скомпрометированных секретов, отсечение тяжелых бинарных блобов, массовая нормализация email и путей). Официально рекомендован взамен устаревшего `git filter-branch`.
* **Защищенный Force Push (`--force-with-lease`, `--force-if-includes`):** Механизм безопасной принудительной отправки переписанной истории в удаленный репозиторий с проверкой актуальности удаленных ссылок для предотвращения случайного перезаписывания чужой работы.

## Базовые концепции

### "Золотое правило" Git: Публичная vs Приватная история

Главное архитектурное правило при манипуляциях с историей: **Никогда не переписывайте историю, которая уже была отправлена в общий удаленный репозиторий (`push`) и стала основой для работы других инженеров или автоматизированных пайплайнов CI/CD.**

1. **Приватная история (локальные ветки разработчика / feature branches до ревью):** Допускается и приветствуется использование `reset`, `amend` и `rebase -i`. Цель — получить логичную, структурированную и атомарную историю перед слиянием.
2. **Публичная история (общие ветки `main`, `master`, `release/*`, `develop`, стабильные теги):** Допустим **только** `git revert`. Переписывание хэшей в общих ветках ломает деревья зависимостей у всей команды, приводит к конфликтам слияния и может нарушить аудит релизов.

```
                  ┌──────────────────────────────┐
                  │ Нужно отменить или изменить? │
                  └──────────────┬───────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
       [Локальная / Приватная]         [Общая / Продакшн / CI]
                 │                               │
        ┌────────┴────────┐                      │
        ▼                 ▼                      ▼
  Только последний?   Несколько?            git revert
        │                 │            (сохраняет историю DAG)
        ▼                 ▼
   git commit         git reset /
    --amend          git rebase -i
```

### Анатомия коммита и криптографическая цепочка

В объектной базе Git коммит представляет собой неизменяемый (immutable) текстовый объект, содержащий:
* Ссылку на корневой объект дерева файлов (`tree <sha>`).
* Ссылки на родительские коммиты (`parent <sha>`).
* Данные автора (`author Name <email> timestamp`).
* Данные коммитера (`committer Name <email> timestamp`).
* GPG/SSH подпись (при наличии).
* Сообщение коммита.

Любое изменение хотя бы одного бита (даже пробела в сообщении или секунды во времени фиксации) полностью меняет хэш текущего коммита. Поскольку все последующие коммиты ссылаются на родительский хэш, модификация одного коммита каскадно приводит к генерации новых хэшей для **всех** его потомков в графе.

### Уровни отмены изменений

Git разделяет жизненный цикл изменений на четыре состояния:
1. **Рабочий каталог (Working Tree):** Измененные файлы на диске, не внесенные в индекс.
2. **Индекс (Staging Area / Index):** Изменения, подготовленные через `git add` для следующего коммита.
3. **Локальный репозиторий (Local Commits):** Зафиксированные коммиты, существующие в локальной базе `.git`.
4. **Удаленный репозиторий (Remote):** Коммиты, отправленные на сервер (`origin`) и видимые другим инженерам и CI-агентам.

### Режимы работы `git reset`

Команда `git reset` управляет тремя деревьями (`HEAD`, Index, Working Tree). Ее поведение строго определяется флагом:

| Режим | Указатель `HEAD` | Индекс (Staged) | Рабочий каталог (Unstaged) | Сценарий применения |
| :--- | :--- | :--- | :--- | :--- |
| `--soft` | Перемещается | **Сохраняет** состояние | **Сохраняет** состояние | Объединение серии коммитов в один перед коммитом или переделка сообщения. |
| `--mixed` | Перемещается | **Сбрасывается** | **Сохраняет** состояние | **Режим по умолчанию.** Раскоммитить изменения, оставив файлы на диске для доработки. |
| `--hard` | Перемещается | **Сбрасывается** | **Уничтожает** изменения | **Деструктивный.** Полный откат до целевого коммита. Незакоммиченные правки стираются безвозвратно. |
| `--keep` | Перемещается | **Сбрасывается** | Сохраняет локальные правки (если нет конфликта с коммитом) | Безопасный аналог `--hard`: завершается ошибкой, если затрагивает файлы с локальными правками. |
| `--merge` | Перемещается | Сбрасывает индекс | Сохраняет изменения между индексом и рабочей копией | Откат неудачной попытки слияния с сохранением незакоммиченных правок. |

### Сравнение `reset` и `revert`

| Критерий | `git reset` | `git revert` |
| :--- | :--- | :--- |
| **Принцип работы** | Перемещает указатель ветки назад по графу | Создает новый инвертирующий коммит вперед по графу |
| **Влияние на граф** | **Переписывает историю** (коммиты отвязываются от ветки) | **Сохраняет историю** (все промежуточные состояния видны) |
| **Допустимость** | Только локальные/приватные ветки | Безопасно для `main`, релизных веток и окружений CD |
| **Сложные случаи** | Требует `git reflog` при ошибке | Требует явного выбора ветки при откате merge (`-m 1`) |
| **Влияние на команду** | Требует force-push и переклонирования | Обычный `git push`, не нарушает работу коллег и CI/CD |

## Практические сценарии

### Сценарий 1: Локальные исправления изменений

#### 1.1 Отмена индексации файлов (`unstaging`)
```bash
# Современный стандарт (с Git 2.23+)
git restore --staged config/production.yaml

# Классический способ
git reset HEAD config/production.yaml
# → Unstaged changes after reset:
# → M	config/production.yaml
```

#### 1.2 Откат незакоммиченных изменений в рабочем каталоге
```bash
# Возврат конкретного файла к последнему коммиту
git restore deploy/helm/values.yaml

# Возврат всего каталога к состоянию HEAD
git restore .

# Исторический аналог (перезаписывает файлы без подтверждения)
git checkout -- deploy/helm/values.yaml
```

#### 1.3 Исправление последнего коммита (`git commit --amend`)
```bash
# 1. Добавить забытый файл конфигурации без изменения сообщения коммита
git add configs/nginx.conf
git commit --amend --no-edit
# → [feat/auth 9a8b7c6] fix(nginx): update upstream timeout
# →  Date: Mon Oct 12 10:15:00 2026 +0300
# →  2 files changed, 14 insertions(+), 2 deletions(-)

# 2. Изменить только сообщение последнего коммита
git commit --amend -m "fix(ingress): adjust proxy buffer size for heavy payloads"

# 3. Изменить автора коммита (актуально при переключении между рабочими профилями)
git commit --amend --author="DevOps Bot <devops@corp.internal>" --no-edit

# 4. Обновить дату фиксации на текущую
git commit --amend --date="$(date -R)" --no-edit
```

### Сценарий 2: Безопасный откат в общих и продакшн-ветках (`git revert`)

#### 2.1 Отмена одиночного коммита
```bash
git revert c4d5e6f
# → [main 7a8b9c0] Revert "feat(api): enable experimental rate limiter"
# →  1 file changed, 5 deletions(-)
```

#### 2.2 Отмена диапазона коммитов без создания промежуточных сообщений
```bash
# Отменить серию коммитов от A до B (не включая A)
git revert A..B

# Отменить серию коммитов атомарно (внести правки в индекс без немедленного коммита)
git revert -n HEAD~3..HEAD
git commit -m "revert(service): rollback faulty database migration batch"
```

#### 2.3 Откат коммита слияния (Merge Commit)
Коммит слияния имеет двух (или более) родителей. При откате необходимо явно указать флаг `-m` (mainline), определяющий родительскую ветку, состояние которой следует сохранить:
```bash
# -m 1 указывает на первого родителя (ветку, КУДА вливали изменения, например main)
git revert -m 1 3d2f1a0
# → [main 9e8d7c6] Revert "Merge branch 'feature/payment' into main"
```

> **Важно для SRE/DevOps:** После `git revert -m 1 <merge_hash>` повторное слияние той же фича-ветки в `main` не применит ее изменения снова, так как Git считает коммиты ветки уже пройденными. Чтобы вернуть отмененные изменения в будущем, необходимо выполнить `git revert` самого коммита отмены:
> ```bash
> git revert 9e8d7c6  # Отменяет revert, возвращая изменения обратно
> ```

### Сценарий 3: Интерактивный ребейз (`git rebase -i`)

Интерактивный `rebase` позволяет упорядочить цепочку локальных коммитов перед созданием Pull/Merge Request.
```bash
# Запустить интерактивное редактирование последних 4 коммитов
git rebase -i HEAD~4
```

В открывшемся редакторе доступен список команд планировщика:

| Команда | Сокращение | Действие |
| :--- | :--- | :--- |
| `pick` | `p` | Использовать коммит без изменений. |
| `reword` | `r` | Использовать коммит, но остановить процесс для правки сообщения. |
| `edit` | `e` | Остановить процесс на данном коммите для изменения файлов или разделения коммита. |
| `squash` | `s` | Объединить коммит с предыдущим, склеив их описания. |
| `fixup` | `f` | Объединить коммит с предыдущим, отбросив описание текущего. |
| `drop` | `d` | Полностью удалить коммит из графа. |
| `exec` | `x` | Выполнить shell-команду после применения данного коммита (тестирование, линтинг). |
| `break` | `b` | Принудительно приостановить rebase в данной точке. |
| `label` | `l` | Поставить именованную метку на текущее состояние. |
| `reset` | `t` | Сбросить `HEAD` на указанную метку. |
| `merge` | `m` | Воссоздать коммит слияния с сохранением исходного сообщения. |

#### Автоматическая валидация через `exec` (гарантия сборки для `git bisect`)
Чтобы гарантировать, что каждый коммит в ветке компилируется и проходит тесты (что критично для последующего бинарного поиска регрессий через `git bisect`):
```bash
git rebase -i HEAD~5 --exec "make test"
```
Если на каком-либо шаге команда `make test` вернет ненулевой код возврата, Git немедленно остановит rebase, позволяя исправить ошибку прямо на проблемном коммите.

### Сценарий 4: Автоматизация правок: Fixup и Autosquash

Ручное редактирование строк в `rebase -i` подвержено ошибкам. Git поддерживает полностью автоматизированный механизм интеграции исправлений:

```bash
# 1. Находим хэш коммита, требующего исправления (например, 2a3b4c5)
git log --oneline -5

# 2. Вносим правку в код и создаем fixup-коммит
git add internal/auth/jwt.go
git commit --fixup 2a3b4c5
# → [feature/jwt 7c8d9e0] fixup! feat(auth): implement jwt token validator

# 3. При необходимости переписать сообщение старого коммита (с Git 2.32+):
git commit --fixup=reword:2a3b4c5

# 4. Запуск автоматического склеивания поверх базовой ветки
git rebase -i --autosquash origin/main
```
Git автоматически переставит строку с `fixup!` непосредственно под целевой коммит и установит для нее директиву `fixup`.

### Сценарий 5: Стекирование веток и ребейз зависимостей (`--update-refs`)

В крупных репозиториях инженеры часто разрабатывают взаимосвязанные фичи цепочками веток: `main` → `feature-1` → `feature-2` → `feature-3`. 
Исторически при ребейзе `feature-1` поверх `main` все вышестоящие ветки отрывались и требовали ручного переноса.

Начиная с Git 2.38+, флаг `--update-refs` автоматически обновляет все локальные указатели веток, входящие в переносимый диапазон:
```bash
# Находясь на вершине стека (feature-3)
git rebase origin/main --update-refs
# → Successfully rebased and updated refs/heads/feature-1.
# → Successfully rebased and updated refs/heads/feature-2.
# → Successfully rebased and updated refs/heads/feature-3.
```

Глобальное включение в конфигурации для всех веток:
```bash
git config --global rebase.updateRefs true
```

### Сценарий 6: Выборочный перенос изменений (`git cherry-pick`)

Используется инженерами DevOps и SRE для бэкпорта хотфиксов стабильности между версионными релизными ветками без полного слияния кода.

```bash
# 1. Перенос единичного коммита с фиксацией ссылки на оригинал (-x)
git checkout release/v2.4
git cherry-pick -x 5f6a7b8
# → [release/v2.4 8c9d0e1] fix(proxy): prevent memory leak on keepalive timeout
# →  (cherry picked from commit 5f6a7b8a9b0c1d2e3f4a5b6c7d8e9f0a1b2c3d4e)

# 2. Перенос диапазона коммитов от A до B включительно
git cherry-pick A^..B

# 3. Перенос без автоматического создания коммита (только в Staging Area)
git cherry-pick -n 4e5f6a7
git commit -s -m "fix(ssl): backport certificate reload fix"
```

#### Разрешение конфликтов при `cherry-pick`:
```bash
# При возникновении конфликта:
# 1. Исправить конфликтные маркеры в файлах
# 2. Добавить разрешенные файлы
git add src/server.c

# 3. Завершить применение коммита
git cherry-pick --continue

# Или прервать операцию и вернуть исходное состояние
git cherry-pick --abort
```

### Сценарий 7: Автоматизация и валидация истории в CI/CD

#### 7.1 Неинтерактивный rebase в скриптах автоматизации
В CI/CD агентах и bash-скриптах нет интерактивного TTY-терминала. Для применения `autosquash` без открытия редактора используется системная переменная `GIT_SEQUENCE_EDITOR`:
```bash
# Выполнить autosquash без запроса редактора
GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash origin/main
```

#### 7.2 Проверка изменений через `git range-diff`
После сложного перебазирования или склеивания коммитов хэши полностью меняются. Чтобы верифицировать в пайплайне или перед force-push, что содержательная логика кода не изменилась и не было внесено посторонних изменений:
```bash
# Сравнение ветки до rebase (сохраненной в ORIG_HEAD или временном теге) и после rebase (HEAD)
git range-diff ORIG_HEAD...HEAD
# → 1: 4a3b2c1 = 1: 8f7e6d5 feat(db): add connection pool retry
# → 2: 5b4c3d2 ! 2: 9a8b7c6 fix(auth): resolve nil pointer dereference
#     @@ Metadata
#      Author: DevOps Engineer <devops@corp.internal>
#     @@ Commit message
#     -    fix: resolve nil pointer
#     +    fix(auth): resolve nil pointer dereference
```
Символ `=` означает, что патч идентичен; `!` показывает различия в метаданных или строках кода.

### Сценарий 8: Глобальное переписывание репозитория (`git-filter-repo`)

Для очистки истории локальных или on-premise bare-репозиториев (GitLab/Gitea/Forgejo) от случайно добавленных дампов БД, ISO-образов или тяжелых логов используется `git-filter-repo`.

**Установка:**
```bash
pip install --user git-filter-repo
```

**Подготовка и выполнение:**
```bash
# 1. Обязательное создание резервной копии репозитория в режиме mirror
git clone --mirror git@gitlab.internal:infra/monitoring.git monitoring-backup.git

# 2. Клонирование свежей копии для очистки
git clone git@gitlab.internal:infra/monitoring.git monitoring-clean
cd monitoring-clean

# 3. Анализ репозитория (генерирует отчеты о самых тяжелых объектах в .git/filter-repo/analysis/)
git-filter-repo --analyze

# 4. Удаление конкретного тяжелого файла из всех коммитов и веток
git-filter-repo --path dump.sql --invert-paths

# 5. Удаление всех блобов размером более 20 МБ
git-filter-repo --strip-blobs-bigger-than 20M

# 6. Массовая нормализация адресов электронной почты
git-filter-repo --email-callback '
  return email.replace(b"old-domain.com", b"company.org")
'
```

### Сценарий 9: Инцидент безопасности: компрометация секрета в on-premise Git

При попадании приватного ключа, пароля БД или токена инфраструктуры в репозиторий удаление коммита через `reset` недостаточно — объект остается в базе Git и доступен по хэшу.

**Регламент действий DevOps / SRE (On-Premises):**

1. **Немедленная ротация (Revocation):** Скомпрометированный токен/ключ считается скомпрометированным с момента создания коммита. Перевыпустите секрет в целевой системе до начала работ с Git.
2. **Изоляция и удаление из истории:**
   ```bash
   # Замена содержимого секрета во всей истории на заглушку
   echo "EXPIRED_SECRET_VALUE==>REDACTED" > /tmp/replace.txt
   git filter-repo --replace-text /tmp/replace.txt
   rm /tmp/replace.txt
   ```
3. **Принудительная отправка с защитой от гонок:**
   ```bash
   git push origin --force-with-lease --force-if-includes --all
   git push origin --force-with-lease --force-if-includes --tags
   ```
4. **Очистка ссылок и жесткая сборка мусора на сервере (Bare Repository):**
   На стороне сервера (GitLab/Gitea сервер или путь `/var/git/repo.git`):
   ```bash
   git reflog expire --expire=now --all
   git gc --prune=now --aggressive
   ```
5. **Синхронизация инженеров:** Оповестить команду о необходимости удаления старых локальных клонов и повторного клонирования репозитория.

### Сценарий 10: Очистка рабочего дерева от неотслеживаемых файлов (`git clean`)

После операций `reset --hard` или отката слияний в каталоге могут оставаться артефакты сборки, временные логи и сгенерированные файлы.

```bash
# 1. Безопасный предварительный просмотр (Dry-run, ничего не удаляет)
git clean -n -d
# → Would remove build/
# → Would remove terraform.tfstate.backup

# 2. Удаление неотслеживаемых файлов и директорий (-f - force, -d - directories)
git clean -fd

# 3. Полная очистка, включая файлы из .gitignore (-x)
git clean -fdx
```

> **Предупреждение:** `git clean -fd` необратим. Удаленные файлы не сохраняются в объектах Git и отсутствуют в `reflog`. Всегда предварительно запускайте проверку с флагом `-n`.

## Восстановление данных

### Поиск и возврат потерянных коммитов через `git reflog`

`git reflog` хранит историю перемещений указателей `HEAD` и веток за последние 30–90 дней (в зависимости от настроек `gc.reflogExpire`).

```bash
# 1. Просмотр журнала перемещений
git reflog show HEAD -n 10
# → a1b2c3d HEAD@{0}: reset: moving to HEAD~3
# → f4e5d6c HEAD@{1}: commit: feat(sre): configure alertmanager routing
# → 8c7b6a5 HEAD@{2}: checkout: moving from main to feature/alerts

# 2. Мгновенное восстановление потерянного состояния в новую ветку
git branch recovery-alerts f4e5d6c
# → Ветка recovery-alerts успешно создана на коммите f4e5d6c
```

### Откат через резервную ссылку `ORIG_HEAD`
Перед выполнением потенциально деструктивных команд (`merge`, `rebase`, `reset`) Git записывает предыдущее положение `HEAD` в псевдоссылку `ORIG_HEAD`:
```bash
# Мгновенная отмена только что выполненного ошибочного reset --hard
git reset --hard ORIG_HEAD
```

### Поиск "висячих" объектов через `git fsck`
Если коммит не отображается в `reflog` (например, истек срок хранения или запись повреждена):
```bash
git fsck --lost-found --unreachable
# → checking connectivity: 100% (250/250), done.
# → dangling commit 9e8f7a6b5c4d3e2f1a0b9c8d7e6f5a4b3c2d1e0f

# Просмотр содержимого найденного коммита
git show 9e8f7a6b5c4d3e2f1a0b9c8d7e6f5a4b3c2d1e0f
```

## Операции и команды

Сводная матрица команд манипуляции историей:

| Команда / Параметр | Назначение | Область действия | Изменяет SHA-хэши | Обратимость через Reflog |
| :--- | :--- | :--- | :---: | :---: |
| `git restore --staged <file>` | Удалить файл из индекса | Index | Нет | Не требуется (файлы целы) |
| `git restore <file>` | Сбросить изменения файла к HEAD | Working Tree | Нет | **Необратимо** |
| `git commit --amend` | Дополнить последний коммит | Последний коммит | Да | Обратимо (`HEAD@{1}`) |
| `git reset --soft <target>` | Откатить коммиты с сохранением staged | HEAD | Да | Обратимо (`ORIG_HEAD`) |
| `git reset --mixed <target>` | Откатить коммиты с сохранением файлов | HEAD + Index | Да | Обратимо (`ORIG_HEAD`) |
| `git reset --hard <target>` | Полный сброс до коммита | HEAD + Index + WorkTree | Да | Коммиты обратимы, незакоммиченное — нет |
| `git revert <hash>` | Создать инвертирующий коммит | Публичная ветка | Нет (создает новый) | Обратимо (повторный revert) |
| `git rebase -i <base>` | Интерактивное редактирование цепочки | Локальная ветка | Да | Обратимо (`ORIG_HEAD`) |
| `git rebase --update-refs` | Ребейз стека зависимых веток | Множество веток | Да | Обратимо для каждой ветки |
| `git cherry-pick <hash>` | Перенос коммита в текущую ветку | Текущая ветка | Да (новый SHA) | Обратимо (`git reset --hard HEAD~1`) |
| `git-filter-repo` | Глобальная фильтрация репозитория | Весь репозиторий | Да (все хэши) | **Только через backup/mirror** |
| `git clean -fd` | Удаление неотслеживаемого мусора | Working Tree | Нет | **Необратимо** |

## Устранение неполадок

### Матрица диагностических ошибок

| Сообщение об ошибке | Первопричина | Пошаговое решение |
| :--- | :--- | :--- |
| `fatal: ambiguous argument 'X..Y': unknown revision` | Опечатка в хэше или локальная ветка еще не скачана с remote. | Проверьте наличие ревизии через `git rev-parse --verify X` или обновите ссылки через `git fetch origin`. |
| `error: cannot 'squash' without a previous commit` | В файле `rebase -i` первой командой указан `squash` или `fixup` вместо `pick`. | Первый коммит в списке обязан быть `pick` (или используйте `git rebase -i --root` для манипуляций с начальным коммитом). |
| `fatal: refusing to merge unrelated histories` | Попытка связать две независимые базы коммитов. | Добавьте флаг `--allow-unrelated-histories` только если уверены в необходимости слияния двух независимых корней. |
| `CONFLICT (content): Merge conflict in <file>` | Конфликтующие строки при `rebase` или `cherry-pick`. | Откройте файл, устраните маркеры `<<<<<<<`, выполните `git add <file>` и запустите `git rebase --continue` (или `--abort` для отката). |
| `fatal: You are not currently on a branch` | Состояние `Detached HEAD` (указатель стоит прямо на хэше). | Зафиксируйте текущую работу в новой ветке: `git switch -c recovery-branch`. |
| `error: failed to push some refs to <remote>` | Удаленная ветка ушла вперед, либо сработал remote hook. | Проверьте состояние через `git fetch`. Если выполняется force push, используйте `--force-with-lease --force-if-includes`. |
| `fatal: Unable to create '.git/index.lock': File exists` | Завис процесс Git (IDE, фоновый линтер) или сбой системы. | Проверьте активные процессы `ps aux \| grep git`. Если процесс завершился аварийно, удалите файл блокировки: `rm -f .git/index.lock`. |
| `cannot lock ref 'refs/heads/...': Unable to create lock` | Параллельный процесс заблокировал файл ветки. | Удалите зависший файл блокировки в каталоге `.git/refs/heads/<branch>.lock`. |

### Циклический конфликт при `rebase`
Если при `rebase` один и тот же конфликт повторяется на каждом шаге коммита:
1. Включите механизм повторного использования разрешений конфликтов `rerere`:
   ```bash
   git config --global rerere.enabled true
   ```
2. Если ветка слишком запутана, прервите операцию:
   ```bash
   git rebase --abort
   ```

### Случайный `git reset --hard` с незакоммиченными изменениями
Если файлы не были добавлены в коммит, они отсутствуют в `git reflog`. Однако, если перед сбросом выполнялась команда `git add .`, файлы были сохранены как `blob` в базе `.git`:
```bash
# Поиск "висячих" файлов, добавленных в индекс
git fsck --lost-found --unreachable | grep blob
# Просмотр содержимого найденных блобов
git cat-file -p <blob_hash>
```

## Лучшие практики

1. **Никакого слепого `--force` в продакшн-окружениях:**
   Используйте только связку параметров:
   ```bash
   git push origin <branch> --force-with-lease --force-if-includes
   ```
   Это гарантирует, что если коллега отправил коммит в удаленную ветку, пока вы выполняли локальный `rebase`, отправка будет заблокирована, предотвращая потерю чужого кода.

2. **Защита основных веток на уровне Git-сервера:**
   На всех bare-репозиториях (GitLab, Gitea, Forgejo, локальные gitolite-серверы) настройте правила защиты веток (Branch Protection):
   * Запрет `Force Push` для веток `main`, `master`, `release/*`.
   * Запрет прямого удаления веток.
   * Обязательное слияние только через Merge/Pull Requests.

3. **Маркировка точек восстановления перед рискованным rebase:**
   Перед масштабным переписыванием истории создайте временный тег-закладку:
   ```bash
   git tag backup/pre-rebase-$(date +%Y%m%d%H%M)
   ```
   В случае непредвиденного сбоя вы сможете вернуться к исходной точке командой `git reset --hard backup/pre-rebase-...`. После успешного завершения удалите тег: `git tag -d backup/...`.

4. **Атомарность коммитов для стабильности `git bisect`:**
   Не объединяйте несвязанные изменения в один огромный коммит. Каждый коммит в репозитории должен оставлять проект в компилируемом и рабочем состоянии. Автоматизируйте проверку каждого шага через `git rebase -i --exec "make test"`.

5. **Предотвращение утечки секретов до коммита:**
   Устранение секретов из истории — ресурсоемкая операция, требующая остановки работы команды. Предотвращайте попадание паролей и ключей с помощью pre-commit сканеров (`gitleaks`, `trufflehog`) на рабочих машинах инженеров и pre-receive хуков на сервере.
