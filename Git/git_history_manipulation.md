# Манипуляции с историей: отмена, исправление и переписывание

## Определения

**Переписывание истории (Rewriting History)** — процесс изменения существующих коммитов (содержимого, сообщений, порядка или авторства). Технически это приводит к созданию новых объектов в базе данных Git и генерации новых хэшей (SHA-1), так как идентификатор коммита зависит от его метаданных и состояния дерева файлов.

**Безопасная отмена (Safe Undo)** — метод отмены изменений путем добавления новых коммитов, которые обращают действие предыдущих. Это не изменяет существующую цепочку истории и является единственно верным способом работы в публичных ветках.

**`git reset`** — команда для перемещения указателя текущей ветки и `HEAD` на конкретный коммит. Является основным инструментом переписывания локальной истории.

**`git revert`** — создание нового коммита, который вносит изменения, прямо противоположные целевому коммиту.

**`git commit --amend`** — модификация самого последнего коммита в текущей ветке.

**`git cherry-pick`** — механизм применения изменений, представленных конкретными коммитами, в текущую ветку.

**`git reflog`** — журнал всех перемещений указателя `HEAD`, позволяющий восстановить коммиты, которые перестали принадлежать какой-либо ветке в результате манипуляций.

**`git-filter-repo`** — инструмент для глобального анализа и переписывания всей истории репозитория (удаление файлов, замена почты авторов и т.д.). Рекомендованная замена устаревшему `git filter-branch`.

**`git range-diff`** — инструмент для сравнения двух диапазонов коммитов (например, до и после rebase), позволяющий убедиться, что логика изменений не нарушена при переписывании истории.

## Базовые концепции

### "Золотое правило" Git: Публичная vs Приватная история

Главное правило при манипуляциях с историей: **Никогда не переписывайте историю, которая уже была отправлена в удаленный репозиторий (`push`) и стала доступна коллегам.**

1.  **Приватная история (локальные коммиты):** Вы можете свободно использовать `reset`, `amend` и интерактивный `rebase`, чтобы сделать историю чистой и логичной перед публикацией.
2.  **Публичная история (общие ветки `main`, `develop`):** Используйте только `git revert`. Переписывание хэшей в общих ветках приведет к рассинхронизации локальных копий у всей команды, вызывая конфликты, которые невозможно разрешить обычным слиянием.

### Уровни отмены изменений

Git позволяет откатываться на разных этапах жизненного цикла изменений:
-   **Рабочий каталог:** Изменения в файлах на диске, еще не добавленные в индекс.
-   **Индекс (Staging Area):** Изменения, добавленные через `git add`, но еще не закоммиченные.
-   **Локальные коммиты:** Зафиксированные изменения, еще не отправленные на сервер.
-   **Опубликованные коммиты:** Изменения, уже находящиеся в удаленном репозитории.

### Режимы работы `git reset`

Действие `reset` зависит от флага, который определяет глубину отката:

| Режим | HEAD | Индекс (Staged) | Рабочий каталог (Unstaged) | Применение |
| :--- | :--- | :--- | :--- | :--- |
| `--soft` | Перемещается | Сохраняет изменения | Сохраняет изменения | Отменить коммит, чтобы переделать его (например, объединить с другими). |
| `--mixed` | Перемещается | Сбрасывается | Сохраняет изменения | **Режим по умолчанию.** Убрать изменения из индекса, сохранив их на диске. |
| `--hard` | Перемещается | Сбрасывается | **Удаляет изменения** | **Опасно.** Полный возврат к состоянию коммита. Все незафиксированные правки теряются. |

## Практические сценарии

### Сценарий 1: Исправление локальных ошибок

#### 1.1 Отмена `git add` (убрать файл из индекса)
```bash
# Современный способ
git restore --staged <file>

# Классический способ
git reset <file>
# → Unstaged changes after reset:
# → M	file.txt
```

#### 1.2 Отмена изменений в файле на диске
Возврат файла к состоянию последнего коммита:
```bash
# Современный способ
git restore <file>

# Классический способ (перезаписывает файл!)
git checkout -- <file>
```

#### 1.3 Исправление последнего коммита (`amend`)
```bash
# Добавить забытый файл
git add forgotten_file.txt
# Объединить с последним коммитом без изменения сообщения
git commit --amend --no-edit
# → [main 1a2b3c4] feat: description
# →  Date: Wed Aug 5 2026 ...
# →  2 files changed, 10 insertions(+)

# Изменить только сообщение последнего коммита
git commit --amend -m "feat: корректное описание функционала"
```

### Сценарий 2: Безопасная отмена в общих ветках (`revert`)

#### 2.1 Отмена обычного коммита
```bash
git revert abc1234
# → [main 5e6f7g8] Revert "feat: problematic change"
# →  1 file changed, 1 deletion(-)
```

#### 2.2 Отмена диапазона коммитов
```bash
# Отменить серию коммитов от A до B (не включая A)
git revert A..B

# Отменить серию коммитов, не создавая сразу коммиты (только изменения в индексе)
git revert -n A..B
```

#### 2.3 Отмена слияния (Merge Commit)
При отмене мерж-коммита нужно указать Git, какая из родительских веток должна остаться "основной" (mainline).
```bash
# -m 1 указывает на первого родителя (ветка, В КОТОРУЮ сливали)
git revert -m 1 <merge_hash>
```

### Сценарий 3: Интерактивное перебазирование (`rebase -i`)

Позволяет полностью перестроить историю последних коммитов.
```bash
# Редактировать последние 5 коммитов
git rebase -i HEAD~5
```

**Команды в интерактивном режиме:**
- `pick` (p) — использовать коммит без изменений.
- `reword` (r) — использовать коммит, но изменить только сообщение.
- `edit` (e) — остановиться для редактирования содержимого коммита.
- `squash` (s) — объединить с предыдущим коммитом, объединив сообщения.
- `fixup` (f) — объединить с предыдущим, отбросив сообщение текущего.
- `drop` (d) — полностью удалить коммит из истории.
- `exec` (x) — выполнить shell-команду (например, запустить тесты) после этого коммита.

#### Автоматизация через Fixup и Autosquash
Позволяет "подклеивать" правки к старым коммитам без ручного перетаскивания строк в редакторе.
```bash
# 1. Сделать исправление для конкретного коммита
git add .
git commit --fixup <hash_of_target_commit>
# → [feature 2b3c4d5] fixup! feat: target feature

# 2. Запустить автоматическое слияние
git rebase -i --autosquash <base_hash>
```

### Сценарий 4: Выборочный перенос изменений (`cherry-pick`)

Используется для переноса коммитов между ветками без полного слияния.

```bash
# Перенести один коммит
git cherry-pick <hash>

# Перенести коммит без автоматического создания коммита (только в индекс)
git cherry-pick -n <hash>

# Перенести коммит и добавить в сообщение ссылку на оригинал (-x)
git cherry-pick -x <hash>
# → [main 3c4d5e6] feat: important fix
# → (cherry picked from commit 1a2b3c4...)
```

### Сценарий 5: Валидация после переписывания (`range-diff`)

После сложного rebase хэши меняются. Чтобы убедиться, что содержательная часть (диффы) осталась прежней:
```bash
# Сравнить состояние ветки до и после манипуляций
git range-diff old_branch_head...HEAD
```

### Сценарий 6: Глобальное переписывание (`git-filter-repo`)

Используется для удаления файлов из всей истории (например, если случайно закоммитили секреты).

```bash
# Удалить файл secret.txt из всех коммитов во всех ветках
git filter-repo --path secret.txt --invert-paths

# Замена email автора во всей истории
git filter-repo --email-callback 'return email.replace(b"old@example.com", b"new@example.com")'
```
*Примечание: BFG Repo-Cleaner является альтернативой, но `git-filter-repo` официально рекомендован сообществом Git.*

### Сценарий 7: Действия при компрометации секрета

**Критический инцидент ИБ.** Если пароль или токен попал в Git и был отправлен в `origin`.

1.  **Удаление из истории:** Используйте `git-filter-repo` (см. выше).
2.  **Принудительное обновление:** `git push origin --force-with-lease --all`.
3.  **ОБЯЗАТЕЛЬНАЯ ротация:** Смените скомпрометированный секрет во внешней системе. Считайте, что его уже скопировали.
4.  **Профилактика:** Установите `gitleaks` или `trufflehog` в качестве [pre-commit хуков](./git_hooks.md).

## Восстановление данных

### `git reflog`: Журнал спасения
Git хранит историю перемещений `HEAD`. Даже если вы удалили ветку или сделали `reset --hard`, данные можно вернуть.

```bash
# 1. Посмотреть журнал
git reflog
# → 1a2b3c4 HEAD@{0}: reset: moving to HEAD~5
# → 5e6f7g8 HEAD@{1}: commit: feat: very important work (ПОТЕРЯНО)

# 2. Восстановить коммит, создав на нем ветку
git branch recovery-branch 5e6f7g8
```

**Важное ограничение: reflog — строго локальный.** Он никогда не передаётся при `git push`. Reflog каждого участника команды хранит только его собственную историю перемещений HEAD.

### `git fsck`: Поиск "висячих" объектов
Если `reflog` не помог, можно найти объекты, которые не связаны ни с одной ссылкой (dangling objects).
```bash
git fsck --lost-found
# → checking connectivity: 100% (123/123), done.
# → dangling commit 5e6f7g8...
# Результаты будут в .git/lost-found/commit/
```

### `ORIG_HEAD` и резервные ссылки
-   **`ORIG_HEAD`:** Сохраняется перед опасными операциями (`merge`, `rebase`, `reset`). Быстрый откат: `git reset --hard ORIG_HEAD`.
-   **Блокировки:** Если Git сообщает о запущенном процессе, удалите `.git/index.lock`.
