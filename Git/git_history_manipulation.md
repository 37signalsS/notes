# Манипуляции с историей: отмена, исправление и переписывание

## Определения

* **Переписывание истории (Rewriting History):** Изменение существующих коммитов или их порядка, что приводит к созданию новых SHA-1 хешей для затронутых коммитов. Это **опасная операция** для публичных веток.
* **Безопасная отмена (Safe Undo):** Операции, которые отменяют изменения путем добавления новых коммитов, не затрагивая существующую историю.
* **`git revert`:** Команда для безопасной отмены коммита путем создания нового "отменяющего" коммита.
* **`git reset`:** Команда для перемещения указателя ветки (`HEAD`) и, опционально, индекса и рабочей директории, тем самым отменяя коммиты. Перезаписывает историю.
* **`git commit --amend`:** Команда для изменения самого последнего коммита (сообщения или содержимого). Перезаписывает историю.
* **`git reflog`:** Журнал всех перемещений указателя `HEAD`, служащий страховочным механизмом для восстановления "потерянных" коммитов.
* **`git-filter-repo`:** Мощный инструмент для глобального переписывания истории репозитория (например, удаления файлов из всей истории).

## Базовые концепции

### "Золотое правило" Git: Публичная vs. Приватная история

Главное правило при манипуляциях с историей Git: **НИКОГДА не переписывайте историю, которая уже была опубликована (отправлена в удаленный репозиторий) и с которой работают другие люди.**

* **Приватные ветки (локальные, неопубликованные):** В них можно безопасно переписывать историю (`reset`, `amend`, `rebase`), чтобы сделать ее чище и линейнее.
* **Публичные ветки (`main`, `develop`, общие feature-ветки):** Используйте только безопасные операции отмены (`git revert`), которые не изменяют существующую историю, а добавляют к ней новые коммиты. Переписывание публичной истории приводит к конфликтам у других разработчиков и потенциальной потере их работы.

### Методы отмены изменений

Git предлагает различные инструменты для отмены изменений на разных этапах:

* **Рабочая директория:** Отмена изменений в файлах, которые еще не были добавлены в индекс.
* **Индекс (Staging Area):** Отмена добавления файлов в индекс перед коммитом.
* **Локальные коммиты:** Отмена коммитов, которые еще не были отправлены в удаленный репозиторий.
* **Опубликованные коммиты:** Отмена коммитов в общих ветках с сохранением истории.

### `git reset` и его режимы

`git reset` — мощная команда для перемещения указателя `HEAD` и изменения состояния индекса и рабочей директории. Различные режимы определяют, насколько сильно `reset` влияет на индекс и рабочую директорию после перемещения `HEAD`:

* `--soft`: Перемещает `HEAD`. Изменения последнего коммита остаются в индексе (staged). Позволяет сделать новый коммит с теми же изменениями.
* `--mixed` (по умолчанию): Перемещает `HEAD` и сбрасывает индекс. Изменения последнего коммита остаются в рабочей директории (unstaged).
* `--hard`: Перемещает `HEAD`, сбрасывает индекс и рабочую директорию. **Потеря всех незафиксированных изменений.** Крайне опасен.

## Практические сценарии

### Отмена и исправление локальных изменений

#### Отмена `git add` (убрать файл из индекса)

Если вы добавили файл в индекс (`git add`), но передумали включать его в коммит:

```bash
git reset <имя_файла>
```

#### Отмена изменений в рабочей директории

Если вы хотите отменить все локальные изменения в файле и вернуть его к состоянию последнего коммита (независимо от того, был ли он в индексе):

```bash
git restore <имя_файла>
```

### Отмена коммитов

#### `git revert`: Безопасная отмена коммитов

`git revert <хэш_коммита>` создаёт **новый** коммит, который является инверсией указанного коммита.

```bash
# Отменить изменения коммита с указанным хешем
git revert a1b2c3d4

# Отменить изменения последнего коммита (HEAD)
git revert HEAD

# Отменить слияние (merge commit)
git revert -m 1 <хэш_коммита_слияния>
# (-m 1 указывает на "главного" родителя, чья сторона сохраняется)
```

#### `git reset`: Отмена коммитов путем перемещения указателя ветки

`git reset <хэш_коммита>` **перемещает** указатель текущей ветки (`HEAD`) на другой коммит.

```bash
# Переместить HEAD, сохранить изменения в staged
git reset --soft HEAD~1

# Переместить HEAD, сохранить изменения в unstaged (по умолчанию)
git reset --mixed HEAD~1

# Переместить HEAD, удалить изменения (самый опасный)
git reset --hard HEAD~1
```

**Внимание:** Если вы уже сделали `push` до `reset`, вам придётся использовать принудительный `push` (`git push --force-with-lease` или `git push --force`), чтобы обновить удаленную ветку. Это может привести к потере работы у коллег.

#### `git commit --amend`: Исправление последнего коммита

Команда `git commit --amend` позволяет изменить самый последний коммит.

* **Изменение сообщения последнего коммита:**

    ```bash
    git commit --amend -m "Новое, более корректное сообщение"
    ```

* **Добавление забытых файлов в последний коммит:**

    ```bash
    # 1. Добавляем пропущенные файлы в индекс
    git add forgotten_file.py
    # 2. Выполняем amend с опцией --no-edit, чтобы сохранить старое сообщение
    git commit --amend --no-edit
    ```

### Продвинутые техники переписывания истории

#### Автоматическая очистка истории с `--fixup` и `--autosquash`

Используется для объединения мелких исправлений с исходными коммитами.

1. **Создаем fixup-коммит:**

    ```bash
    # Вносим изменения в код, исправляя ошибку в коммите dc4efa9
    git add main.go
    git commit --fixup dc4efa9
    ```

    (или `--squash` для сохранения сообщения fixup-коммита)

2. **Запускаем интерактивный rebase с авто-склеиванием:**

    ```bash
    # <коммит_до_dc4efa9> — это хеш коммита, который предшествует коммиту dc4efa9
    git rebase -i --autosquash <коммит_до_dc4efa9>
    ```

    Git откроет редактор с уже готовым планом `rebase`. Вам останется только сохранить и закрыть его.

#### Глобальное переписывание истории (`git-filter-repo`)

Для удаления файла из всей истории (например, случайно закоммиченного секрета).

**Внимание:** Это мощный и разрушительный инструмент. Обязательно сделайте резервную копию репозитория перед использованием.

```bash
# Пример: удалить файл secret.txt из всей истории
git filter-repo --path secret.txt --invert-paths
```

### Восстановление данных

#### Действия при компрометации секрета в Git

**Сценарий:** Секрет (пароль, API-ключ, токен) случайно попал в коммит и был отправлен в удалённый репозиторий.

**Критичность:** Это **инцидент информационной безопасности**. Секрет считается скомпрометированным, даже если вы сразу удалили коммит.

**Порядок действий:**

1. **Удалить секрет из истории Git:**

   ```bash
   # Использовать git reset для удаления последнего коммита
   git reset --soft HEAD~1
   
   # Или использовать git-filter-repo для удаления файла из всей истории
   git filter-repo --path secret.txt --invert-paths
   ```

2. **Принудительно отправить изменения:**

   ```bash
   # После переписывания истории необходим force push
   git push --force-with-lease
   ```

3. **Сменить скомпрометированный секрет:** **Обязательно!** Даже если вы удалили его из истории, секрет считается раскрытым.

4. **Оповестить службу безопасности/руководителя:** Задокументировать инцидент ИБ.

5. **Обновить секрет во всех местах использования:** Если секрет использовался в продуктиве, обновить его везде.

**Важно:** Простое удаление файла или коммита **не достаточно**. История Git хранит все предыдущие версии, и злоумышленник с доступом к репозиторию может извлечь секрет из старых коммитов.

**Профилактика:**
- Используйте `.gitignore` для исключения файлов с секретами
- Применяйте pre-commit хуки для проверки на секреты (например, [git-secrets](https://github.com/awslabs/git-secrets))
- Храните секреты во внешних хранилищах (Vault, SOPS)
- Подробнее: [Управление секретами](../Security/Concepts/secrets_management_overview.md)

#### `git reflog`: Журнал всех перемещений HEAD

`git reflog` отслеживает все изменения указателя `HEAD`, включая переключения веток, коммиты и `reset`.

```bash
# Показать историю перемещений HEAD
git reflog

# Пример вывода:
# 2a5a921 HEAD@{0}: reset: moving to HEAD~1
# 3b4a1b2 HEAD@{1}: commit: добавил новую фичу
# ...

# Восстановиться к нужному состоянию
git reset --hard HEAD@{1}
```

#### `git fsck`: Поиск "висячих" объектов

Используется для поиска "потерянных" коммитов.

```bash
git fsck --lost-found
```

Эта команда покажет "висячие" коммиты (dangling commits), которые не принадлежат ни одной ветке. Затем вы можете восстановить такой коммит, создав на его основе новую ветку.
