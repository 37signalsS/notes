# Git: Основы системы контроля версий

Git — распределённая система управления версиями, созданная Линусом Торвальдсом в 2005 году для управления разработкой ядра Linux. 

## Что такое Система Контроля Версий (СКВ)?

Система Контроля Версий (СКВ) — это инструмент, который позволяет разработчикам отслеживать изменения в файлах, координировать работу над проектами и управлять различными версиями исходного кода или других документов. Основные функции СКВ включают:

*   **Резервное копирование и история изменений:** СКВ сохраняет каждое изменение файла, позволяя вернуться к любой предыдущей версии. Это своего рода "машина времени" для вашего кода.
*   **Совместная разработка:** Позволяет нескольким людям работать над одним проектом одновременно, избегая конфликтов и легко объединяя изменения.
*   **Автоматизация сборки и развертывания:** Интегрируется с системами CI/CD для автоматической сборки, тестирования и развертывания проектов на основе зафиксированных изменений.
*   **Документация изменений:** Каждый набор изменений (коммит) сопровождается сообщением, объясняющим, что было изменено и почему. Это создает подробную историю проекта, облегчая отладку и понимание эволюции кода.

## Типы Систем Контроля Версий

### Централизованные СКВ (ЦСКВ)

В централизованной системе вся история изменений хранится на одном сервере. Разработчики подключаются к этому серверу, чтобы получить последнюю версию кода и отправить свои изменения. Примеры: SVN (Subversion), Perforce.

**Плюсы:**

*   Простота настройки.
*   Удобное управление правами доступа (все данные в одном месте).

**Минусы:**

*   **Единая точка отказа:** Если сервер выходит из строя, никто не может работать, и есть риск потери данных, если нет резервных копий.
*   **Зависимость от сети:** Для любой операции (коммит, обновление) требуется подключение к центральному серверу.
*   **Проблемы масштабирования:** При большом количестве разработчиков и частых операциях сервер может стать "бутылочным горлышком".

### Распределённые СКВ (РСКВ)

В распределённой системе каждый разработчик имеет полную копию всего репозитория, включая всю историю изменений. Это позволяет работать автономно и синхронизировать изменения напрямую между репозиториями или через общий "центральный" репозиторий (который, тем не менее, является просто одной из копий). Примеры: Git, Mercurial.

**Плюсы:**

*   **Автономная работа:** Можно работать офлайн, создавать коммиты, просматривать историю.
*   **Надёжность и отказоустойчивость:** Если один из репозиториев (даже "центральный") потерян, его легко восстановить из любой другой полной копии.
*   **Высокая скорость:** Большинство операций выполняются локально.
*   **Гибкость:** Поддерживает различные рабочие процессы (workflow).

**Минусы:**

*   Более сложная начальная настройка и понимание концепций для новичков.
*   Полная копия репозитория на каждом компьютере может занимать много места для очень больших проектов.

## Основные термины Git

*   **Репозиторий (Repository):** Место, где Git хранит все изменения проекта, его историю, метаданные и объекты. На локальном диске это скрытая директория `.git` внутри рабочего каталога проекта.
*   **Рабочий каталог (Working Directory):** Каталог, содержащий актуальные файлы вашего проекта, которые вы видите и редактируете. Это файлы, с которыми вы непосредственно работаете.
*   **Индекс / Область подготовленных файлов (Staging Area / Index):** Промежуточная область, куда вы добавляете изменения, которые хотите включить в следующий коммит. Это как "черновик" вашего будущего коммита.
*   **Коммит (Commit):** "Снимок" (snapshot) состояния вашего проекта в определённый момент времени. Каждый коммит содержит изменения файлов, сообщение (описание изменений), информацию об авторе и дату. Коммиты формируют историю проекта.
    *   Для **текстовых файлов** Git отслеживает изменения построчно. Если вы измените хотя бы один символ в строке, Git запишет это как удаление старой строки и добавление новой.
    *   Для **бинарных файлов** (изображения, архивы) Git не может отслеживать изменения построчно. Вместо этого он сохраняет полную новую версию файла при каждом изменении. Для экономии места и эффективности используются механизмы дедупликации и сжатия.
*   **Ветка (Branch):** Перемещаемый указатель на один из коммитов. Когда вы создаете новый коммит, этот указатель автоматически перемещается на новый коммит. Таким образом, ветка всегда указывает на **последний коммит** в цепочке коммитов, которая составляет историю этой ветки.

## Базовая настройка Git

Перед началом работы с Git необходимо настроить ваше имя пользователя и адрес электронной почты. Эта информация будет включена в каждый ваш коммит.

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "ваш@email.com"
```

## Создание и клонирование репозитория

### Инициализация нового репозитория

Для начала работы с Git в существующем каталоге или в новой папке используется команда `git init`. Она создает скрытую директорию `.git`, которая содержит всю необходимую информацию для отслеживания изменений.

```bash
# Создает скрытую директорию .git
git init
# Рекомендуется сразу указывать имя основной ветки (например, main)
git init --initial-branch=main
```

### Клонирование существующего репозитория

Чтобы получить копию существующего репозитория (например, с GitHub или GitLab), используется команда `git clone`.

```bash
git clone <url_репозитория>
```

## Жизненный цикл файлов в Git

Файлы в Git проходят через несколько состояний:

1.  **Неотслеживаемый (untracked):** Git не знает о файле. Это новый файл, который ещё не был добавлен в репозиторий.
2.  **Изменён (modified):** Файл отслеживается Git, но в него были внесены изменения, которые ещё не добавлены в индекс.
3.  **Подготовлен (staged):** Файл (или его изменения) добавлен в индекс и готов к включению в следующий коммит.
4.  **Зафиксирован (committed):** Изменения файла сохранены в репозитории в виде коммита.

## Основные команды Git

### Просмотр статуса

Команда `git status` показывает текущее состояние рабочего каталога и индекса, какие файлы изменены, какие готовы к коммиту, а какие ещё не отслеживаются.

```bash
git status
git status -s # Короткий (summary) формат
```

### Добавление файлов в область подготовленных (индексация)

Команда `git add` используется для добавления изменений в индекс, подготавливая их к следующему коммиту.

```bash
git add <имя_файла> # Добавить конкретный файл
git add .           # Добавить все новые и изменённые файлы в текущей директории
git add -A          # Добавить все изменения (новые, изменённые, удалённые)
```

### Фиксация изменений (коммит)

Команда `git commit` сохраняет подготовленные изменения (из индекса) в репозиторий как новый коммит. Сообщение коммита (`-m`) должно быть осмысленным.

```bash
git commit -m "Краткое описание изменений"
git commit -am "Описание" # Добавляет все отслеживаемые файлы и сразу делает коммит (пропускает git add для отслеживаемых файлов)
```

### Просмотр истории изменений (git log)

Команда `git log` показывает историю коммитов.

```bash
git log
```
**Полезные флаги:**

*   `--oneline`: Показывает каждый коммит в одну строку.
*   `--graph`: Отображает историю в виде ASCII-графа, полезно для веток.
*   `--pretty=format:"%h %s"`: Позволяет настроить формат вывода (`%h` - короткий хэш, `%s` - сообщение).
*   `--stat`: Отображает статистику изменённых файлов для каждого коммита.
*   `-p`: Показывает изменения (diff), внесённые в каждом коммите.
*   `show <ID_коммита>`: Показывает информацию о конкретном коммите и его изменения.

**Фильтрация и поиск:**

*   `-n <число>`: Ограничивает вывод указанным числом коммитов.
*   `--since="YYYY-MM-DD"` и `--until="YYYY-MM-DD"`: Фильтрует по дате.
*   `--author="<имя>"`: Поиск по автору.
*   `--grep="<паттерн>"`: Поиск по сообщению коммита.
*   `-S "<текст>"`: Поиск коммитов, где было добавлено или удалено указанное слово.
*   `--no-merges`: Исключает коммиты слияния.
*   `main..test`: Показывает коммиты, которые есть в ветке `test`, но нет в `main`.

**Работа с файлами:**

*   `-- <путь_к_файлу>`: Показывает историю изменений только для указанного файла.
*   `--follow <файл>`: Отслеживает историю файла, включая его переименования.
*   `--name-only`: Показывает только имена изменённых файлов.

### Просмотр изменений в файлах (git diff)

Команда `git diff` используется для сравнения изменений.

*   `git diff`: Сравнение рабочей директории с областью подготовленных файлов (индексом).
*   `git diff --staged` (или `--cached`): Сравнение подготовленных файлов с последним коммитом (`HEAD`).
*   `git diff HEAD`: Сравнение рабочей директории с последним коммитом.
*   `git diff <branch1>..<branch2>`: Показывает разницу между двумя ветками (все изменения в `branch2`, которых нет в `branch1`).

Команда `git show` показывает информацию о конкретном объекте в Git (коммите, теге и т.д.).
*   `git show <ID_коммита>`: Показывает информацию о коммите и его изменения.
*   `git show HEAD`: Показывает информацию о последнем коммите.

### Управление файлами (переименование, удаление)

**Переименование и перемещение:**

```bash
git mv
```

Если перемещать файлы обычным `mv`, Git вообще не понимает, что произошло. Он воспринимает это как удаление старого файла и появление нового. В результате теряется контекст истории, `git blame` обнуляется для затронутых строк, а `git diff` показывает огромные изменения (удаление старого файла, добавление нового).

Команда `git mv <старое_имя> <новое_имя>` выполняет то же перемещение, но еще и сообщает Git'у: "Это тот же файл, просто теперь он здесь".

*   **Преимущество:** Git регистрирует аккуратное `renamed` изменение, а не двойной `diff`, сохраняя историю файла и облегчая чтение изменений.
*   **Примечание:** Современные IDE (например, Git в JetBrains продуктах) часто выполняют `git mv` под капотом при переименовании или перемещении файлов. При работе в других средах или через командную строку важно помнить об использовании `git mv`.
```

**Удаление:**

```bash
git rm <файл>         # Удаление файла из контроля версий и с диска
git rm --cached <файл> # Удаление файла только из контроля версий (оставить на диске)
```

### Переключение между версиями и ветками

Команда `git checkout` (или `git switch` для переключения веток) позволяет переключаться между различными коммитами или ветками.

```bash
git checkout <ID_коммита> # Переключение к определённому коммиту (состояние "detached HEAD")
git checkout <имя_ветки>  # Переключение на существующую ветку
git switch <имя_ветки>    # Современная команда для переключения на существующую ветку
```

**Состояние "Detached HEAD"**

Когда вы переключаетесь на конкретный коммит с помощью `git checkout <ID_коммита>`, вы попадаете в состояние "detached HEAD" (отсоединённый HEAD). Это означает, что вы больше не находитесь на какой-либо ветке. `HEAD` — это указатель, который обычно ссылается на последней коммит в текущей ветке. В состоянии "detached HEAD" он указывает напрямую на хэш коммита.

Это состояние полезно для:

*   **Просмотра истории:** Вы можете безопасно посмотреть состояние проекта в прошлом.
*   **Экспериментов:** Вы можете вносить временные изменения и даже создавать коммиты.

**Важно:** Если вы создадите новые коммиты в состоянии "detached HEAD" и затем переключитесь обратно на существующую ветку (например, `main`), ваши новые коммиты станут "потерянными", так как на них не будет указывать ни одна ветка, и они будут удалены сборщиком мусора Git.

Чтобы сохранить экспериментальные изменения, создайте из этого состояния новую ветку:

```bash
git switch -c <имя_новой_ветки>
```
Эта команда создаст новую ветку, которая будет начинаться с текущего коммита, и переключит вас на неё, сохраняя вашу работу.

### Отмена изменений

**Отмена `git add` (убрать файл из индекса):**

```bash
git reset <имя_файла>
```

**Отмена локальных изменений в файле:**

```bash
git restore <имя_файла> # Откатывает изменения в рабочей директории к состоянию последнего коммита или индекса
```

**Отмена коммитов (кратко):**

*   **`git revert <ID_коммита>`:** Создаёт *новый* коммит, который отменяет изменения указанного коммита. Это безопасный способ отмены изменений, так как сохраняет историю. **Рекомендуется при работе в команде с общей историей.**
*   **`git reset <ID_коммита>`:** Перемещает указатель ветки (HEAD) на указанный коммит, эффективно удаляя более новые коммиты из истории. *Опасно для публичной истории, так как перезаписывает её.* Используйте с осторожностью только в своих приватных ветках.

### Временное сохранение (Stash)

Иногда требуется временно переключиться на другую задачу, не создавая коммит с незаконченной работой. `git stash` позволяет сохранить незакоммиченные изменения (как в рабочей директории, так и в индексе) во временном хранилище и вернуть рабочую директорию в состояние `HEAD`.

```bash
# Сохранить изменения с сообщением
git stash save "сообщение"
# или короткий вариант
git stash
```

**Основные команды для работы со стеком изменений:**
*   `git stash list`: Показать список всех сохраненных состояний.
*   `git stash apply`: Применить последнее сохраненное состояние, но оставить его в списке.
*   `git stash pop`: Применить последнее сохраненное состояние и удалить его из списка.
*   `git stash clear`: Удалить все сохраненные состояния.

## Работа с удалёнными репозиториями

### Управление удалёнными репозиториями (git remote)

*   `git remote -v`: Список удалённых репозиториев.
*   `git remote add <имя> <url>`: Добавить новый удалённый репозиторий.
*   `git remote remove <имя>`: Удалить.
*   `git remote rename <старое> <новое>`: Переименовать.
*   `git remote set-url <имя> <url>`: Изменить URL.
*   `git remote show <имя>`: Показать подробную информацию об удалённом репозитории (ветки, HEAD).

### Синхронизация изменений

*   **`git fetch <имя_удалённого_репозитория>`:** Загружает изменения (коммиты, ветки, теги) из удалённого репозитория, но *не применяет* их к вашей локальной рабочей ветке. Изменения сохраняются в удалённых отслеживаемых ветках (например, `origin/main`).
*   **`git pull <имя_удалённого_репозитория> <имя_ветки>`:** Составная команда, которая выполняет `git fetch`, а затем автоматически `git merge` (или `git rebase` в зависимости от конфигурации) в вашу текущую локальную ветку. Загружает и применяет изменения.

    ```bash
    git pull origin main # Загрузить и объединить изменения из ветки main удалённого репозитория 'origin'
    git pull --rebase origin main # Использовать rebase вместо merge для более чистой линейной истории
    ```

### Отправка изменений

*   **`git push <имя_удалённого_репозитория> <имя_ветки>`:** Отправляет ваши локальные коммиты из текущей ветки в указанную ветку удалённого репозитория.

    ```bash
    git push origin main # Отправить изменения из локальной main в удалённую main
    git push --set-upstream origin <имя_ветки> # Отправить новую локальную ветку и связать её с удалённой (для первого push)
    ```
*   **`git push --force`** / **`git push --force-with-lease`:** Принудительная отправка. Перезаписывает историю в удалённой ветке. Используйте с крайней осторожностью, так как это может привести к потере работы других разработчиков. `git push --force-with-lease` является более безопасной версией, предотвращая перезапись, если кто-то другой уже отправил изменения.

### Метки (Tags)

Метки используются для обозначения важных точек в истории, чаще всего — релизов (например, `v1.0`).

*   `git tag <имя_тега>`: Создать лёгкий тег (просто указатель на коммит).
*   `git tag -a <имя_тега> -m "сообщение" <хэш_коммита>`: Создать аннотированный тег (содержит метаданные: автора, дату, сообщение). Рекомендуется для релизов.
*   `git show <имя_тега>`: Показать информацию о теге.
*   `git tag -f -a <имя_тега> <хэш_коммита>`: Принудительно переместить (заменить) аннотированный тег на другой коммит.

**Синхронизация меток с удалённым репозиторием:**

*   `git push origin <имя_тега>`: Отправить конкретный тег в удалённый репозиторий.
*   `git push --tags`: Отправить все теги.
*   `git push --delete origin <имя_тега>`: Удалить тег из удалённого репозитория.

## Продвинутые инструменты

### Перенос коммитов (Cherry-pick)

`git cherry-pick` позволяет применить копию коммита из другой ветки в текущую. Это полезно, когда нужно внести конкретное исправление или фичу, не сливая всю ветку целиком.

```bash
git cherry-pick <хэш_коммита_1> <хэш_коммита_2>
```

*   `--no-commit`: Применяет изменения из коммита в рабочую директорию, но не создаёт новый коммит, позволяя внести правки перед фиксацией.

### Поиск ошибок (Bisect)

`git bisect` — это мощный инструмент для автоматического поиска коммита, который внёс ошибку в код. Он использует бинарный поиск по истории коммитов.

**Процесс работы:**

1.  **Начало сессии:**
    ```bash
    git bisect start
    ```
2.  **Обозначение "плохого" и "хорошего" коммитов:**
    ```bash
    git bisect bad <хэш_плохого_коммита>  # Коммит, где ошибка уже есть (часто HEAD)
    git bisect good <хэш_хорошего_коммита> # Коммит, где ошибки еще не было
    ```
3.  **Итерация:** Git автоматически переключится на коммит между "хорошим" и "плохим". На каждом шаге вам нужно проверить наличие ошибки и выполнить:
    *   `git bisect bad` — если ошибка присутствует.
    *   `git bisect good` — если ошибки нет.
4.  **Завершение:** Когда проблемный коммит будет найден, Git сообщит об этом. Завершите процесс, чтобы вернуться в исходное состояние:
    ```bash
    git bisect reset
    ```
