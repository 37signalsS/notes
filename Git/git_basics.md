# Git: Основы

## Определения

### Git и Система Контроля Версий (СКВ)

**Система Контроля Версий (СКВ)** — это инструмент, который позволяет разработчикам отслеживать изменения в файлах, координировать работу над проектами и управлять различными версиями исходного кода или других документов.

**Git** — распределённая система управления версиями, созданная Линусом Торвальдсом в 2005 году для управления разработкой ядра Linux.

Ключевые функции СКВ:

* **Резервное копирование и история изменений:** СКВ сохраняет каждое изменение файла, позволяя вернуться к любой предыдущей версии.
* **Совместная разработка:** Позволяет нескольким людям работать над одним проектом одновременно, избегая конфликтов.
* **Автоматизация:** Интегрируется с системами CI/CD для автоматической сборки, тестирования и развертывания.
* **Документация:** Каждый набор изменений (коммит) сопровождается сообщением, объясняющим, что и почему было изменено.

### Типы Систем Контроля Версий

* **Централизованные (ЦСКВ):** Вся история хранится на одном сервере. Разработчики подключаются к нему для получения и отправки изменений.
  * **Примеры:** SVN (Subversion), Perforce.
  * **Недостаток:** Единая точка отказа и зависимость от сети.
* **Распределённые (РСКВ):** Каждый разработчик имеет полную копию всего репозитория, включая всю историю.
  * **Примеры:** Git, Mercurial.
  * **Преимущество:** Автономная работа, высокая надёжность и скорость.

### Основные термины Git

* **Репозиторий (Repository):** Место, где Git хранит всю историю проекта, метаданные и объекты. На локальном диске это скрытая директория `.git`.
* **Рабочий каталог (Working Directory):** Каталог, содержащий актуальные файлы проекта, которые вы редактируете.
* **Индекс / Область подготовленных файлов (Staging Area):** Промежуточная область, куда добавляются изменения для включения в следующий коммит.
* **Коммит (Commit):** "Снимок" состояния проекта в определённый момент времени. Содержит изменения, сообщение, информацию об авторе и дату. Коммиты формируют историю.
  * **Текстовые файлы:** Git отслеживает изменения построчно.
  * **Бинарные файлы:** Git сохраняет полную новую версию файла при каждом изменении.
* **Ветка (Branch):** Перемещаемый указатель на один из коммитов. Ветка всегда указывает на **последний коммит** в своей цепочке.

## Базовые концепции

### Жизненный цикл файлов в Git

1. **Неотслеживаемый (untracked):** Новый файл, о котором Git ещё не знает.
2. **Изменён (modified):** Отслеживаемый файл, в который были внесены изменения, не добавленные в индекс.
3. **Подготовлен (staged):** Изменения файла добавлены в индекс и готовы к коммиту.
4. **Зафиксирован (committed):** Изменения сохранены в репозитории в виде коммита.

### Состояние "Detached HEAD"

**"Detached HEAD"** — это состояние, когда указатель `HEAD` ссылается не на ветку, а напрямую на хэш коммита. Это происходит при переключении на конкретный коммит.

Этот режим полезен для инспекции старых версий кода, но создание новых коммитов в нём требует осторожности.

* **Подробнее:** [Ветвление в Git → "Отсоединенный HEAD"](./git_branching.md#отсоединенный-head-detached-head)

### Синхронизация: `fetch` против `pull`

* `git fetch`: Загружает новые данные из удалённого репозитория, но не интегрирует их в вашу рабочую копию.
* `git pull`: Загружает и автоматически пытается слить изменения в вашу текущую ветку.

Обе команды используются для синхронизации с удалённым репозиторием, но работают по-разному.

* **Подробнее:** [Синхронизация репозиториев → `fetch` vs `pull`](./git_synchronization.md#получение-изменений-fetch-vs-pull)

### Отмена коммитов: `revert` против `reset`

* `git revert`: Создаёт новый коммит, который отменяет изменения предыдущего. Безопасен для общей истории.
* `git reset`: Перемещает указатель ветки, "удаляя" коммиты из истории. Опасен для общих веток.

Обе команды служат для отмены изменений, но `revert` сохраняет историю, а `reset` её перезаписывает.

* **Подробнее:** [Манипуляции с историей → `revert` и `reset`](./git_history_manipulation.md#методы-отмены-изменений)

### Метки (Tags)

Метки используются для обозначения важных точек в истории, чаще всего — релизов (например, `v1.0`).

* **Лёгкий тег (`git tag <имя_тега>`):** Просто указатель на коммит.
* **Аннотированный тег (`git tag -a <имя_тега> -m "сообщение"`):** Содержит метаданные (автора, дату, сообщение). Рекомендуется для релизов.

## Практические сценарии

### 1. Первоначальная настройка

Эта информация будет встроена в каждый коммит.

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "ваш@email.com"
```

### 2. Создание репозитория

* **Инициализация нового:**

    ```bash
    # Создает скрытую директорию .git в текущей папке
    git init --initial-branch=main
    ```

* **Клонирование существующего:**

    ```bash
    # Создает копию удалённого репозитория
    git clone <url_репозитория>
    ```

### 3. Базовый рабочий процесс

1. **Просмотр статуса:** Узнайте, какие файлы изменены, подготовлены к коммиту или не отслеживаются.

    ```bash
    git status
    git status -s # Короткий формат
    ```

2. **Добавление в индекс:** Подготовьте изменения к коммиту.

    ```bash
    git add <имя_файла> # Добавить конкретный файл
    git add .           # Добавить все новые и изменённые файлы
    ```

3. **Фиксация изменений:** Сохраните подготовленные изменения в репозиторий.

    ```bash
    git commit -m "Краткое и осмысленное описание изменений"
    ```

    * `git commit -am "..."` — совмещает `git add` и `git commit` для уже отслеживаемых файлов.

### 4. Анализ истории и изменений

* **Просмотр истории коммитов (`git log`):**

    ```bash
    git log
    git log --oneline --graph # Показывает историю в виде компактного графа
    git log --stat            # Показывает статистику изменённых файлов
    git log -p <имя_файла>   # Показывает историю изменений для конкретного файла
    ```

* **Просмотр изменений (`git diff`):**
  * `git diff`: Изменения в рабочем каталоге, которых нет в индексе.
  * `git diff --staged`: Изменения в индексе, которых нет в последнем коммите.
  * `git diff HEAD`: Все изменения в рабочем каталоге с момента последнего коммита.
* **Просмотр содержимого коммита (`git show`):**

    ```bash
    git show <ID_коммита> # Показывает информацию о коммите и его изменения
    ```

### 5. Управление файлами

* **Переименование и перемещение:**

    ```bash
    git mv <старое_имя> <новое_имя>
    ```

    *Использование `git mv` вместо системной `mv` позволяет Git отследить переименование, сохраняя историю файла.*
* **Удаление:**

    ```bash
    git rm <файл>          # Удалить файл из репозитория и с диска
    git rm --cached <файл> # Удалить только из репозитория, оставив на диске
    ```

### 6. Отмена изменений

* **Убрать файл из индекса:**

    ```bash
    git reset <имя_файла>
    ```

* **Отменить локальные изменения в файле:**

    ```bash
    git restore <имя_файла>
    ```

* **Временно сохранить незаконченную работу (`git stash`):**

    ```bash
    git stash             # Сохранить изменения во временное хранилище
    git stash list        # Показать список сохраненных состояний
    git stash pop         # Применить последнее состояние и удалить его из списка
    git stash apply       # Применить, но оставить в списке
    ```

### 7. Работа с ветками

* **Переключение между ветками и коммитами:**

    ```bash
    git switch <имя_ветки>    # Современная команда для переключения на ветку
    git checkout <имя_ветки>  # Традиционная команда
    git checkout <ID_коммита> # Переключиться на коммит (состояние "detached HEAD")
    ```

### 8. Работа с удалёнными репозиториями

* **Управление удалёнными репозиториями (`git remote`):**

    ```bash
    git remote -v                 # Список удалённых репозиториев
    git remote add <имя> <url>    # Добавить новый
    git remote show <имя>         # Показать подробную информацию
    ```

* **Синхронизация (`git fetch`, `git pull`):**

    ```bash
    git fetch origin              # Загрузить изменения без слияния
    git pull origin main          # Загрузить и слить изменения из ветки main
    git pull --rebase origin main # Загрузить и перебазировать на ветку main
    ```

* **Отправка изменений (`git push`):**

    ```bash
    git push origin main # Отправить коммиты в ветку main
    # Для новой ветки при первом push:
    git push --set-upstream origin <имя_ветки>
    ```

    *Используйте `git push --force-with-lease` вместо `git push --force` для принудительной отправки. Это более безопасная версия, которая не перезапишет чужие изменения.*
* **Синхронизация меток:**

    ```bash
    git push origin <имя_тега> # Отправить конкретный тег
    git push --tags            # Отправить все теги
    ```

### 9. Продвинутые инструменты

* **Перенос коммитов (`git cherry-pick`):** Применяет копию коммита из другой ветки в текущую.

    ```bash
    git cherry-pick <хэш_коммита>
    ```

* **Поиск ошибок (`git bisect`):** Использует бинарный поиск для автоматического нахождения коммита, который внёс ошибку.
    1. `git bisect start`
    2. `git bisect bad <хэш_плохого_коммита>` (где ошибка есть, часто `HEAD`)
    3. `git bisect good <хэш_хорошего_коммита>` (где ошибки не было)
    4. Git переключается на коммит посередине. Вы проверяете код и выполняете `git bisect bad` или `git bisect good`.
    5. Процесс повторяется, пока не будет найден виновный коммит.
    6. `git bisect reset` — выход из режима `bisect`.
