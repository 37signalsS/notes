# Git — основы

## Определения

**Система контроля версий (СКВ)** — инструмент для отслеживания изменений в файлах, координации совместной работы и управления версиями исходного кода.

**Git** — распределённая система контроля версий, созданная Линусом Торвальдсом в 2005 году для разработки ядра Linux.

**Типы СКВ:**

* **Централизованные (ЦСКВ):** История хранится на одном сервере (SVN, Perforce). Недостаток — единая точка отказа и зависимость от сети.
* **Распределённые (РСКВ):** Каждый разработчик имеет полную копию репозитория со всей историей (Git, Mercurial). Преимущество — автономная работа и высокая скорость.

### Основные термины

* **Репозиторий (Repository):** Хранилище всей истории проекта, метаданных и объектов. На локальном диске — директория `.git`.
* **Рабочий каталог (Working Directory):** Каталог с актуальными файлами проекта, которые редактируются.
* **Индекс / Staging Area:** Промежуточная область, куда добавляются изменения для включения в следующий коммит.
* **Коммит (Commit):** Снимок состояния проекта в определённый момент времени. Содержит изменения, сообщение, автора и дату.
* **Ветка (Branch):** Перемещаемый указатель на последний коммит в цепочке.
* **HEAD:** Указатель на текущую ветку или коммит.
* **Detached HEAD:** Состояние, когда HEAD ссылается напрямую на коммит, а не на ветку. Полезно для инспекции старых версий.

## Базовые концепции

### Жизненный цикл файлов

1. **Untracked** — новый файл, о котором Git не знает
2. **Modified** — отслеживаемый файл с изменениями, не добавленными в индекс
3. **Staged** — изменения добавлены в индекс и готовы к коммиту
4. **Committed** — изменения сохранены в истории репозитория

### Синхронизация: `fetch` против `pull`

* `git fetch` — загружает новые данные из удалённого репозитория без интеграции в рабочую копию
* `git pull` — загружает и автоматически сливает изменения в текущую ветку

Подробно: [git_synchronization.md](./git_synchronization.md).

### Отмена изменений: `revert` против `reset`

* `git revert` — создаёт новый коммит, отменяющий предыдущий. Безопасен для общей истории.
* `git reset` — перемещает указатель ветки, удаляя коммиты из истории. Опасен для общих веток.

Подробно: [git_history_manipulation.md](./git_history_manipulation.md).

### Метки (Tags)

Метки обозначают важные точки в истории, обычно релизы:

* **Лёгкий тег:** Указатель на коммит (`git tag v1.0`)
* **Аннотированный тег:** Содержит метаданные — автора, дату, сообщение (`git tag -a v1.0 -m "Release 1.0"`). Рекомендуется для релизов.

## Практические сценарии

### Сценарий 1: Создание репозитория

```bash
# Инициализация нового репозитория
git init --initial-branch=main

# Клонирование существующего репозитория
git clone <url_репозитория>
```

### Сценарий 2: Базовый рабочий процесс

```bash
# Просмотр статуса репозитория
git status
git status -s  # Короткий формат

# Добавление файлов в индекс
git add <файл>
git add .      # Все новые и изменённые файлы

# Фиксация изменений
git commit -m "Краткое описание изменений"
git commit -am "..."  # add + commit для уже отслеживаемых файлов
```

### Сценарий 3: Анализ истории и изменений

```bash
# История коммитов
git log
git log --oneline --graph  # Компактный граф
git log --stat             # Статистика изменённых файлов
git log -p <файл>          # История изменений конкретного файла

# Просмотр изменений
git diff                   # Рабочий каталог vs индекс
git diff --staged          # Индекс vs последний коммит
git diff HEAD              # Все изменения с последнего коммита

# Содержимое коммита
git show <хэш_коммита>
```

### Сценарий 4: Управление файлами

```bash
# Переименование с сохранением истории
git mv <старое_имя> <новое_имя>

# Удаление из репозитория и с диска
git rm <файл>

# Удаление только из репозитория (файл остаётся на диске)
git rm -r --cached <файл>
```

### Сценарий 5: Отмена изменений

```bash
# Убрать файл из индекса
git restore --staged <файл>

# Отменить локальные изменения в файле
git restore <файл>

# Отменить последний коммит, сохранив изменения
git reset --soft HEAD~1

# Временно сохранить незаконченную работу
git stash                # Сохранить
git stash list           # Список сохранённых состояний
git stash pop            # Применить и удалить из списка
git stash apply          # Применить, оставив в списке
git stash drop           # Удалить последнее состояние
git stash drop stash@{N} # Удалить конкретное состояние
```

### Сценарий 6: Работа с ветками

```bash
# Переключение на ветку
git switch <имя_ветки>       # Современная команда
git checkout <имя_ветки>     # Традиционная команда

# Переключение на коммит (detached HEAD)
git checkout <хэш_коммита>

# Создание и переключение на новую ветку
git switch -c <имя_ветки>
git checkout -b <имя_ветки>
```

### Сценарий 7: Работа с удалёнными репозиториями

```bash
# Список удалённых репозиториев
git remote -v

# Добавить удалённый репозиторий
git remote add origin <url>

# Загрузить изменения без слияния
git fetch origin

# Загрузить и слить изменения
git pull origin main

# Загрузить и перебазировать
git pull --rebase origin main

# Отправить коммиты
git push origin main
git push --set-upstream origin <имя_ветки>  # Первая отправка новой ветки

# Отправка тегов
git push origin <имя_тега>
git push --tags
```

> Используйте `git push --force-with-lease` вместо `git push --force` — это безопасная версия принудительной отправки, которая не перезаписывает чужие изменения.

### Сценарий 8: Продвинутые инструменты

```bash
# Перенос коммита из другой ветки
git cherry-pick <хэш_коммита>

# Бинарный поиск коммита с ошибкой
git bisect start
git bisect bad <хэш_плохого_коммита>   # Коммит с ошибкой (часто HEAD)
git bisect good <хэш_хорошего_коммита> # Коммит без ошибки
# Git переключается на коммит посередине — проверьте код:
git bisect bad   # если ошибка есть
git bisect good  # если ошибки нет
# Повторяйте до нахождения виновного коммита
git bisect reset # Выход из режима bisect
```
