### Создание и управление ветками

*   `git branch`: Список локальных веток.
*   `git branch -a`: Список всех веток (локальные и удалённые).
*   `git branch -vv`: Показывает локальные ветки и их связь с удалёнными.
*   `git branch <имя_ветки>`: Создать новую ветку.
*   `git branch <новая> <существующая>`: Создать новую ветку как копию существующей.
*   `git branch -d <имя_ветки>`: Удалить ветку (только если она полностью слита).
*   `git branch -D <имя_ветки>`: Принудительно удалить ветку.

### Переключение между ветками

**Переключение на другую ветку:**

```bash
git switch <имя_ветки>
# или старый вариант
git checkout <имя_ветки>
```

**Создание новой ветки и переключение на неё:**

```bash
git switch -c <имя_ветки>
# или старый вариант
git checkout -b <имя_ветки>
```

#### Переключение на конкретный коммит (Detached HEAD)

Помимо переключения между ветками, можно переместиться на любой коммит в истории, используя его хэш или тег.

```bash
# Переключиться на конкретный коммит по его хэшу
git checkout a1b2c3d4

# Переключиться на коммит, на который указывает тег
git checkout v1.2.0
```

**Это действие переводит Git в состояние "Detached HEAD"**, потому что `HEAD` теперь указывает не на ветку, а напрямую на хэш коммита. В этом режиме можно просматривать код, создавать временную ветку для экспериментов, но любые новые коммиты, сделанные без создания новой ветки, будут "потеряны" после переключения на другую ветку.

### Слияние веток (merge)

Перейдите на ветку, в которую хотите влить изменения, и выполните:

```bash
git merge <имя_ветки_для_слияния>
```

**Полезные флаги:**
*   `--squash`: Объединяет все коммиты из сливаемой ветки в один, не перенося историю.
*   `--abort`: Отменяет слияние, если возникли конфликты.
*   `--allow-unrelated-histories`: Разрешает слияние веток с несвязанной историей.

Для разрешения конфликтов слияния можно использовать визуальный инструмент:

```bash
git mergetool
```

### Сравнение `merge` и `rebase` 

**Исходное состояние:**
```
      D---E <-- feature
     /
A---B---C <-- main
```

#### `git merge` (сохраняет историю)

`git merge` создает новый "коммит слияния" (`F`), который объединяет истории обеих веток.

```bash
git checkout main
git merge feature
```

**Результат:**
```
      D---E
     /     \
A---B---C---F <-- main, feature
```
*   **Плюсы:** История сохранена, видно, где и когда произошло слияние.
*   **Минусы:** Может создавать "шумную", нелинейную историю.


#### `git rebase` (перезаписывает историю)

`git rebase` перемещает вашу ветку, применяя её коммиты поверх последнего коммита целевой ветки.

```bash
git checkout feature
git rebase main
```

**Что происходит "под капотом":**

1.  Git "отматывает" вашу ветку `feature` до общего предка (`B`).
2.  Временно сохраняет ваши коммиты `D` и `E` (как патчи).
3.  Перемещает указатель `feature` на последний коммит в `main` (`C`).
4.  Применяет ваши сохраненные коммиты один за другим поверх `C`.

**Важно:** Применяя коммиты `D` и `E` на новую "базу" (`C`), Git создает **новые коммиты** (`D'` и `E'`). У них будет то же содержимое и сообщение, но другие хэши (SHA-1 ID), потому что у них другой родительский коммит.

**Результат:**

```
A---B---C---D'---E' <-- feature
```
*   **Плюсы:** Создает линейную и чистую историю.
*   **Минусы:** Перезаписывает историю (создает новые коммиты `D'` и `E'`). **Нельзя использовать для веток, с которыми работают другие люди.**

После `rebase` для обновления `main` потребуется `fast-forward` слияние:

```bash
git checkout main
git merge feature
```

Поскольку `main` является прямым предком `feature`, Git выполнит "перемотку вперед" (fast-forward), просто переместив указатель `main` на `E'`.

**Финальная история:**

```
A---B---C---D'---E' <-- main, feature
```

#### Что выбрать: `merge` или `rebase`?

Выбор между `merge` и `rebase` обусловлен тем, какой вы хотите видеть историю коммитов: линейной или ветвящейся.

*   **Если вы сомневаетесь, используйте `merge`.** Это более безопасная операция, которая не перезаписывает историю.
*   **Используйте `rebase` для локальной "очистки" истории** перед отправкой в общую ветку, чтобы сделать ее линейной и понятной.

**Ключевые факторы при выборе:**

1.  **Публичная или приватная ветка?**
    *   **НИКОГДА не используйте `rebase` для веток, которые доступны другим разработчикам** (например, `main`, `develop` или любая общая feature-ветка). `rebase` создает *новые* коммиты и удаляет старые, что приводит к полной рассинхронизации истории у разных разработчиков. Это "золотое правило" rebase.

2.  **Важна ли история слияния?**
    *   `merge` сохраняет контекст, создавая коммит слияния. Это показывает, что в определенный момент работа из одной ветки была интегрирована в другую. В модели "одна функция — одна ветка" это может быть полезно.
    *   `rebase` создает иллюзию, что вся работа велась последовательно в одной ветке, скрывая факт ветвления.

3.  **Нужна ли возможность отмены?**
    *   Отменить `merge` можно с помощью `git revert -m 1 <хэш_коммита_слияния>`, что создает новый коммит, отменяющий слияние. Это безопасная операция.
    *   Отменить `rebase` значительно сложнее (часто требует использования `reflog`) и может быть невозможно без потери данных, если `rebase` был отправлен в удаленный репозиторий.

### Интерактивное перебазирование

Для полного контроля над историей (объединение, переименование, удаление коммитов) используется интерактивный режим:

```bash
git rebase -i HEAD~3 # Пример для последних 3 коммитов
```

В редакторе можно выбрать действие для каждого коммита:
*   `pick`: использовать коммит.
*   `squash`: объединить коммит с предыдущим.
*   `fixup`: объединить с предыдущим, отбросив сообщение коммита.
*   `reword`: изменить сообщение коммита.
*   `drop`: удалить коммит.

### Разрешение конфликтов при rebase

В отличие от `merge`, где вы решаете все конфликты сразу, `rebase` применяет коммиты по одному и останавливается на каждом, где есть конфликт.

#### Состояние "Detached HEAD" при конфликте

Когда `rebase` останавливается из-за конфликта, Git входит в состояние(не находимся ни в одной из веток), известное как "detached HEAD" (отсоединенный HEAD). Это ключевой момент для понимания процесса.

*   **Почему это происходит?** `rebase` работает путем создания *новых* коммитов. Он временно "отматывает" вашу ветку до общего предка, а затем начинает применять коммиты вашей ветки один за другим поверх целевой ветки. В этот момент вы не находитесь ни на какой ветке. `HEAD` указывает не на имя ветки (как обычно), а напрямую на хэш конкретного коммита, который Git пытается применить. Это временное состояние, существующее только на время разрешения конфликта.

*   **Что это значит?** Вы находитесь на "безымянной" ветке. Любые коммиты, которые вы попытаетесь сделать здесь (кроме как для разрешения конфликта через `rebase --continue`), будут потеряны после завершения `rebase`, так как на них не будет указывать ни одна ветка.

#### Процесс разрешения конфликта

1.  **Возникновение конфликта.** Вы выполняете `git rebase <целевая_ветка>`, и Git останавливается с сообщением о конфликте.

2.  **Анализ конфликта.** Откройте файлы, на которые указывает Git. Вы увидите стандартные маркеры конфликта:

    *   `<<<<<<< HEAD`: Изменения из коммита, который вы пытаетесь применить (ваши изменения).
    *   `=======`: Разделитель.
    *   `>>>>>>> <хэш_коммита>`: Изменения из целевой ветки, с которой возник конфликт.

3.  **Ручное исправление.** Отредактируйте файл, чтобы он принял финальный, корректный вид. **Удалите все маркеры** (`<<<`, `===`, `>>>`) и оставьте только тот код, который должен остаться.

4.  **Добавление в индекс.** После исправления всех конфликтов в файле (или нескольких файлах), сообщите Git, что конфликт разрешен, добавив файлы в индекс:

    ```bash
    git add <путь_к_исправленному_файлу>
    ```

5.  **Продолжение rebase.** Завершите применение текущего коммита и перейдите к следующему:

    ```bash
    git rebase --continue
    ```

    Git применит исправленный коммит и перейдет к следующему. Если в следующем коммите тоже будет конфликт, процесс повторится с шага 2.

#### Важные команды управления

*   **Отмена rebase:** Если вы запутались или передумали, можно в любой момент прервать `rebase` и вернуть ветку в состояние, в котором она была до начала процесса:

    ```bash
    git rebase --abort
    ```

    Это безопасная команда, которая полностью отменяет `rebase`.

*   **Пропуск коммита:** Если вы понимаете, что коммит, вызвавший конфликт, больше не нужен (например, его изменения уже есть в целевой ветке), вы можете его пропустить:

    ```bash
    git rebase --skip
    ```

### Сравнение веток

*   `git log main..test`: Показать коммиты, которые есть в `test`, но нет в `main`.
*   `git cherry -v main`: Показать список коммитов в текущей ветке, которых нет в `main`.

### Защита веток (Branch Protection)

Защита веток — это набор правил, применяемых к ветке для предотвращения нежелательных изменений, таких как случайное удаление или принудительная отправка (force push). Это критически важная функция для основных веток, таких как `main` и `develop`.

#### Основные правила защиты:

*   **Требование Pull Request (Merge Request):** Все изменения должны вноситься через Pull Request, что обеспечивает возможность код-ревью.
*   **Обязательные проверки статуса (Required Status Checks):** Слияние разрешено только после успешного прохождения всех CI/CD проверок (сборка, тесты, линтеры).
*   **Требование ревью (Required Reviews):** Для слияния требуется одобрение как минимум одного или нескольких членов команды.
*   **Ограничение на push (Restrict Pushes):** Разрешает push в ветку только определённым пользователям или командам.
*   **Запрет Force Push:** Блокирует принудительное обновление ветки, чтобы избежать перезаписи истории.
*   **Запрет удаления ветки:** Предотвращает случайное удаление защищённой ветки.

Эти правила настраиваются на стороне хостинг-платформы (GitHub, GitLab, Bitbucket, SourceCraft и т.д.), а не через команды Git.

Пример конфигурации SourceCraft (`.sourcecraft/branches.yaml`):

```yaml
branch_protection:
  policies:
    - target: default_branch
      message: "Нельзя пушить напрямую в main! Создавай Merge Request"
      rules:
        - prevent_non_pr_changes
```

### Feature Flags как альтернатива ветвлению

**Feature Flags (или Feature Toggles)** — это механизм, который позволяет включать или выключать функциональность в приложении без изменения кода и развертывания новых версий. Это мощная альтернатива долгоживущим feature-веткам, тесно связанная с практикой **Trunk-Based Development**.

*   **Принцип:** Вместо создания отдельной ветки для новой функции, код для нее пишется непосредственно в основной ветке (`main`/`master`), но "заворачивается" в условный блок.

```javascript
if (featureFlags.isEnabled('new-experimental-feature')) {
  // Код новой функции
} else {
  // Старая логика
}
```

*   **Преимущества:**
    *   **Устранение "ада слияния" (merge hell):** Код постоянно интегрируется в основную ветку, избегая сложных и болезненных слияний долгоживущих веток.
    *   **Развертывание без релиза:** Новую функциональность можно развернуть в production в выключенном состоянии, а затем включить для определенной группы пользователей (Canary-релиз) или для всех сразу.
    *   **Быстрый откат:** Если новая функция вызывает проблемы, ее можно мгновенно отключить через панель управления feature-флагами, без необходимости отката всего релиза.
    *   **A/B тестирование:** Позволяет легко показывать разные версии функциональности разным сегментам пользователей.

*   **Недостатки:**
    *   **Усложнение кода:** Код может стать более запутанным из-за множества условных блоков.
    *   **Технический долг:** Старые, уже не используемые флаги необходимо регулярно удалять из кода, чтобы он не превратился в "паутину".

**Вывод:** Feature-флаги не заменяют Git-ветки полностью (короткоживущие ветки для небольших задач по-прежнему полезны), но служат отличной стратегией для управления крупными изменениями и снижения рисков, связанных с ветвлением и слиянием.
