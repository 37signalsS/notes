### Создание и управление ветками

*   `git branch`: Список локальных веток.
*   `git branch -a`: Список всех веток (локальные и удалённые).
*   `git branch -vv`: Показывает локальные ветки и их связь с удалёнными.
*   `git branch <имя_ветки>`: Создать новую ветку.
*   `git branch <новая> <существующая>`: Создать новую ветку как копию существующей.
*   `git branch -d <имя_ветки>`: Удалить ветку (только если она полностью слита).
*   `git branch -D <имя_ветки>`: Принудительно удалить ветку.

### Переключение между ветками

**Переключение на другую ветку:**

```bash
git switch <имя_ветки>
# или старый вариант
git checkout <имя_ветки>
```

**Создание новой ветки и переключение на неё:**

```bash
git switch -c <имя_ветки>
# или старый вариант
git checkout -b <имя_ветки>
```

### Слияние веток (merge)

Перейдите на ветку, в которую хотите влить изменения, и выполните:

```bash
git merge <имя_ветки_для_слияния>
```
**Полезные флаги:**
*   `--squash`: Объединяет все коммиты из сливаемой ветки в один, не перенося историю.
*   `--abort`: Отменяет слияние, если возникли конфликты.
*   `--allow-unrelated-histories`: Разрешает слияние веток с несвязанной историей.

Для разрешения конфликтов слияния можно использовать визуальный инструмент:

```bash
git mergetool
```

### Сравнение `merge` и `rebase` 

**Исходное состояние:**
```
      D---E <-- feature
     /
A---B---C <-- main
```

#### `git merge` (сохраняет историю)

`git merge` создает новый "коммит слияния" (`F`), который объединяет истории обеих веток.

```bash
git checkout main
git merge feature
```

**Результат:**
```
      D---E
     /     \
A---B---C---F <-- main, feature
```
*   **Плюсы:** История сохранена, видно, где и когда произошло слияние.
*   **Минусы:** Может создавать "шумную", нелинейную историю.


#### `git rebase` (перезаписывает историю)

`git rebase` перемещает вашу ветку, применяя её коммиты поверх последнего коммита целевой ветки.

```bash
git checkout feature
git rebase main
```

**Что происходит "под капотом":**

1.  Git "отматывает" вашу ветку `feature` до общего предка (`B`).
2.  Временно сохраняет ваши коммиты `D` и `E` (как патчи).
3.  Перемещает указатель `feature` на последний коммит в `main` (`C`).
4.  Применяет ваши сохраненные коммиты один за другим поверх `C`.

**Важно:** Применяя коммиты `D` и `E` на новую "базу" (`C`), Git создает **новые коммиты** (`D'` и `E'`). У них будет то же содержимое и сообщение, но другие хэши (SHA-1 ID), потому что у них другой родительский коммит.

**Результат:**
```
A---B---C---D'---E' <-- feature
```
*   **Плюсы:** Создает линейную и чистую историю.
*   **Минусы:** Перезаписывает историю (создает новые коммиты `D'` и `E'`). **Нельзя использовать для веток, с которыми работают другие люди.**

После `rebase` для обновления `main` потребуется `fast-forward` слияние:
```bash
git checkout main
git merge feature
```

Поскольку `main` является прямым предком `feature`, Git выполнит "перемотку вперед" (fast-forward), просто переместив указатель `main` на `E'`.

**Финальная история:**

```
A---B---C---D'---E' <-- main, feature
```

### Интерактивное перебазирование

Для полного контроля над историей (объединение, переименование, удаление коммитов) используется интерактивный режим:

```bash
git rebase -i HEAD~3 # Пример для последних 3 коммитов
```
В редакторе можно выбрать действие для каждого коммита:
*   `pick`: использовать коммит.
*   `squash`: объединить коммит с предыдущим.
*   `fixup`: объединить с предыдущим, отбросив сообщение коммита.
*   `reword`: изменить сообщение коммита.
*   `drop`: удалить коммит.

### Разрешение конфликтов при rebase

 В отличие от `merge`, где вы решаете все конфликты сразу, `rebase` применяет коммиты по одному и останавливается на каждом, где есть конфликт. 

1.  **Возникновение конфликта.** Вы выполняете `git pull --rebase`, и Git останавливается с сообщением о конфликте.

2.  **Анализ конфликта.** Откройте файлы, на которые указывает Git. Вы увидите маркеры конфликта:
    ```
    <<<<<<< HEAD
    10000
    =======
    100500
    >>>>>>> Обновление файла 5.txt
    ```
    *   `<<<<<<< HEAD`: Начало блока с вашими локальными изменениями.
    *   `=======`: Разделитель.
    *   `>>>>>>> ...`: Конец блока с изменениями, которые пришли с сервера (`origin`).

3.  **Ручное исправление.** Ваша задача — отредактировать файл так, чтобы он принял финальный, корректный вид. Вы должны **удалить все маркеры** (`<<<`, `===`, `>>>`) и оставить только тот код, который должен остаться.

4.  **Фиксация исправления.** После того как вы исправили все конфликты в файле (или нескольких файлах), вы должны сообщить Git, что конфликт разрешен. Для этого используется `git add`.
    ```bash
git add <путь_к_исправленному_файлу>
```

5.  **Продолжение rebase.** Когда все конфликты для **текущего** коммита разрешены и добавлены в индекс, выполните:
    ```bash
git rebase --continue
```
    Git применит исправленный коммит и перейдет к следующему. Если в следующем коммите тоже будет конфликт, процесс повторится с шага 2.

**Как отменить всё?**
Если вы запутались или передумали, вы можете в любой момент прервать `rebase` и вернуть ветку в состояние, в котором она была до начала `git pull --rebase`:
```bash
git rebase --abort
```

### Сравнение веток

*   `git log main..test`: Показать коммиты, которые есть в `test`, но нет в `main`.
*   `git cherry -v main`: Показать список коммитов в текущей ветке, которых нет в `main`.
