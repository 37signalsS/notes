# Ветвление в Git: механизмы, стратегии и управление

## Определения

* **Ветка (Branch):** Подвижный указатель на один из коммитов. Ветка всегда указывает на **последний коммит** в своей цепочке. Это изолированная линия разработки, позволяющая вести параллельную работу над разными задачами.
* **HEAD:** Указатель на текущую позицию в истории коммитов. Обычно `HEAD` указывает на имя текущей ветки.
* **Слияние (Merge):** Процесс интеграции изменений из одной ветки в другую. Результатом является новый "коммит слияния" (merge commit), который имеет двух родителей и объединяет истории обеих веток.
* **Перебазирование (Rebase):** Альтернативный метод интеграции. `rebase` перемещает коммиты из одной ветки и "накладывает" их поверх последнего коммита другой ветки, создавая линейную историю. При этом коммиты **переписываются** (получают новые хэши).

## Базовые концепции

### Состояние "Отсоединенный HEAD" (Detached HEAD)

Это состояние, когда `HEAD` ссылается не на ветку, а напрямую на хэш конкретного коммита. Это происходит при переключении на коммит, не являющийся концом ветки (например, `git switch --detach a1b2c3d` или переключение на тег).

**Технические нюансы:**
* Полезно для инспекции истории, запуска тестов для старой версии или временных экспериментов.
* **Риск:** Новые коммиты, созданные в этом состоянии, не принадлежат ни одной ветке. После переключения на существующую ветку (например, `main`), эти коммиты станут недоступными по имени и будут удалены сборщиком мусора (`git gc`).
* **Решение:** Чтобы сохранить работу, сделанную в состоянии "detached HEAD", необходимо создать новую ветку: `git switch -c <имя_новой_ветки>`.

### Перенос незакоммиченных изменений

В Git ветка — это лишь именованный указатель (ссылка) на конкретный коммит. Рабочее дерево (Working Directory) и индекс (Staging Area) не "принадлежат" конкретной ветке до момента совершения коммита.

**Ключевая особенность:**
Если у вас есть незакоммиченные изменения (dirty state) и вы создаете новую ветку (`git checkout -b` или `git switch -c`), эти изменения "следуют" за вами на новую ветку. Это позволяет начать работу в `main`, осознать необходимость отдельной ветки и перенести все наработки в один шаг, не используя `stash`.

**Условия переноса:**
* Перенос успешен, если изменения в рабочем дереве не конфликтуют с файлами в целевой ветке.
* Если конфликты есть, Git заблокирует переключение и предложит сделать `stash` или `commit`.

### Сравнение Merge и Rebase

#### 1. Механизм Merge (Сохранение истории)
`git merge` создает новый "коммит слияния" (`F`), объединяющий истории обеих веток.

**Исходное состояние:**
```text
      D---E <-- feature
     /
A---B---C <-- main
```
**Результат после `git merge feature` в ветке `main`:**
```text
      D---E
     /     \
A---B---C---F <-- main, feature
```
* **Fast-Forward:** Если в `main` не было новых коммитов с момента ветвления, Git просто передвинет указатель `main` вперед. Чтобы принудительно создать коммит слияния для сохранения структуры, используйте `git merge --no-ff`.

#### 2. Механизм Rebase (Переписывание истории)
`rebase` перемещает коммиты ветки, применяя их поверх последнего коммита целевой ветки.

**Результат после `git rebase main` в ветке `feature`:**
```text
A---B---C---D'---E' <-- feature
```
* **Важно:** Коммиты `D` и `E` заменяются на новые `D'` и `E'` с другими хешами.
* **Золотое правило:** НИКОГДА не используйте rebase для публичных веток (доступных другим разработчикам), так как это разрушает их локальную историю.

### Критерии выбора стратегии

1. **Публичность ветки:** Только merge для общих веток.
2. **Чистота истории:** Rebase дает идеальную линию, Merge сохраняет контекст "когда и что влито".
3. **Сложность отмены:** Merge отменяется легко (`git revert -m 1`), Rebase требует работы с `reflog`.

## Практические сценарии

### Управление ветками

```bash
# Список всех веток (локальные и удаленные)
git branch -a

# Список веток и их связи с удаленными (upstream)
git branch -vv

# Список веток, которые уже слиты в текущую (безопасно удалять)
git branch --merged
# →   feature/login-fix
# → * main

# Удаление ветки
git branch -d feature/name      # Удалить, только если она слита
git branch -D feature/name      # Принудительное удаление
```

### Переключение и создание (Современные команды)

```bash
# Создание и переход
git switch -c feature/cool-stuff
# → Switched to a new branch 'feature/cool-stuff'

# Переключение на существующую
git switch main

# Переключение на коммит (Detached HEAD)
git switch --detach a1b2c3d
```

### Интерактивное перебазирование (Rebase Interactive)

Используется для полной очистки истории перед слиянием.
```bash
git rebase -i HEAD~3
```
**Команды управления:**
* `pick`: использовать коммит.
* `squash`: объединить с предыдущим (сообщения объединяются).
* `fixup`: объединить, отбросив сообщение текущего.
* `reword`: только изменить сообщение.
* `drop`: полностью удалить коммит.

### Разрешение конфликтов при Rebase

В отличие от merge, при rebase конфликты разрешаются пошагово для каждого коммита.

1. **Остановка:** Git останавливается на коммите, который не удалось применить.
2. **Анализ:** Откройте файлы с маркерами конфликта (`<<<<<<<`, `=======`, `>>>>>>>`).
3. **Исправление:** Отредактируйте файлы, выбрав нужный код и удалив маркеры.
4. **Фиксация:**
   ```bash
   git add <файл>
   git rebase --continue
   ```
5. **Отмена:** Если процесс стал слишком сложным: `git rebase --abort`.

### Миграция незакоммиченных изменений в новую ветку

Сценарий, когда работа велась в `main`, но было принято решение вынести её в отдельную ветку, оставив `main` в исходном состоянии.

**Алгоритм действий:**

1.  **Создание и переключение:**
    ```bash
    git checkout -b feature/migration-task
    ```
    *Результат:* Вы на новой ветке, все незакоммиченные изменения перешли с вами. `main` всё ещё указывает на старый коммит.

2.  **Подготовка всех изменений (включая удаления):**
    ```bash
    git add -A
    ```
    *Важно:* Флаг `-A` (или `--all`) индексирует всё: новые файлы, модификации и **удаления**. Это критично, если миграция подразумевает очистку проекта от старых компонентов.

3.  **Фиксация:**
    ```bash
    git commit -m "feat: migrate to docker and cleanup windows-specific files"
    ```
    *Результат:* Снапшот зафиксирован на ветке `feature/migration-task`. Ветка `main` осталась нетронутой и указывает на то же состояние, что и до начала работ.

### Защита веток (Branch Protection)

Настраивается на GitHub/GitLab. Основные правила:
* **Require Pull Request:** запрет прямых пушей, изменения только через ревью.
* **Required Status Checks:** слияние разрешено только после успеха в CI/CD.
* **Required Reviews:** необходимо одобрение от владельцев кода (Code Owners).
* **Restrict Pushes:** ограничение круга лиц, имеющих право на запись.
* **No Force Push:** запрет использования ключа `--force` для защиты истории.

### Feature Flags

Альтернатива долгоживущим веткам. Позволяет сливать код в `main`, но не активировать его в рантайме до готовности.
