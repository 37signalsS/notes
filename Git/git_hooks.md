# Git Hooks: Автоматизация проверок

Git Hooks — это скрипты, которые Git запускает автоматически при определенных событиях в жизненном цикле репозитория (коммит, пуш, мерж и т.д.). Они позволяют автоматизировать рутинные проверки, обеспечивать соблюдение стандартов кодирования и предотвращать попадание ошибок или секретов в кодовую базу.

Хуки хранятся в директории `.git/hooks` вашего репозитория и должны быть исполняемыми.

## Типы хуков

Хуки делятся на две основные категории:

### 1. Клиентские хуки (Client-Side Hooks)

Выполняются на локальной машине разработчика. Позволяют проверять код *до* того, как он попадет в локальный или удаленный репозиторий.

-   **`pre-commit`**: Срабатывает перед созданием коммита. Идеально подходит для:
    -   Линтинга и форматирования кода (`eslint`, `prettier`, `black`).
    -   Проверки синтаксиса.
    -   Поиска отладочных выражений (например, `console.log`).
    Если скрипт завершается с ненулевым кодом, коммит отменяется.

-   **`prepare-commit-msg`**: Вызывается после `pre-commit` для редактирования сообщения коммита по умолчанию.

-   **`commit-msg`**: Проверяет сообщение коммита на соответствие стандартам (например, наличие номера задачи из Jira).

-   **`post-commit`**: Срабатывает после успешного создания коммита. Используется для уведомлений.

-   **`pre-push`**: Срабатывает перед отправкой коммитов на удаленный сервер (`git push`). Это последняя возможность "поймать" проблемы локально, прежде чем они станут видны другим. Подходит для запуска быстрых тестов или сканирования на секреты.

### 2. Серверные хуки (Server-Side Hooks)

Выполняются на удаленном сервере, где хостится репозиторий. Используются для применения политик на уровне всей команды или проекта.

-   **`pre-receive`**: Запускается, когда сервер получает `push`. Здесь можно запустить тесты, проверить права доступа или убедиться, что история не была принудительно перезаписана. Если скрипт завершается неудачно, `push` отклоняется.
-   **`update`**: Похож на `pre-receive`, но выполняется один раз для каждой обновляемой ветки.
-   **`post-receive`**: Срабатывает после успешного `push`. Идеален для запуска CI/CD пайплайнов, отправки уведомлений в Slack или обновления проектного трекера.

## Фреймворки для управления хуками

Ручное управление хуками может быть неудобным. Фреймворки упрощают их установку и синхронизацию в команде.

-   **[pre-commit](https://pre-commit.com/):** Популярный фреймворк для управления `pre-commit` хуками. Позволяет легко подключать готовые проверки для множества языков.
-   **Husky (для JavaScript/Node.js):** Позволяет управлять хуками через `package.json`.

---

## Как поделиться хуками с командой

По умолчанию директория `.git/hooks` не отслеживается системой контроля версий. Чтобы вся команда могла использовать одинаковые хуки, придерживайтесь следующего подхода:

1.  **Создайте директорию для хуков** в вашем репозитории (например, `scripts/git-hooks`).
2.  **Сохраните скрипты хуков** в этой директории.
3.  **Настройте их автоматическое копирование** или создание символических ссылок при инициализации проекта. Это можно сделать с помощью скрипта в `Makefile` или инструкции в `README.md`.

**Пример команды для создания символической ссылки:**

```bash
ln -s -f ../../scripts/git-hooks/pre-push .git/hooks/pre-push
```
