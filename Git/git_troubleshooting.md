# Git: Устранение неполадок и отладка

## Определения

* **Устранение неполадок Git:** Процесс диагностики и решения проблем, возникающих при работе с Git, включая проблемы с подключением, аутентификацией, конфликтами и неожиданным поведением.
* **Отладка транспорта:** Получение подробной информации о коммуникации Git с удаленными репозиториями по протоколам HTTP/HTTPS или SSH для выявления проблем.
* **`git bundle`:** Инструмент для упаковки Git-репозитория или его части в один файл, позволяющий передавать изменения без прямого сетевого подключения.
* **Разрешение конфликтов (Conflict Resolution):** Процесс ручного исправления изменений в файлах, которые Git не смог объединить автоматически.

## Базовые концепции

### Диагностика проблем с подключением (транспортные протоколы)

Git использует HTTP/HTTPS и SSH для обмена данными с удаленными репозиториями. Проблемы с этими протоколами могут проявляться как ошибки при клонировании, получении (`fetch`, `pull`) или отправке (`push`) изменений. Увеличение уровня детализации вывода Git помогает понять, что происходит на уровне сетевого взаимодействия и аутентификации.

* **HTTP/HTTPS:** Для отладки HTTP-соединений Git использует библиотеку cURL. Подробный вывод cURL может показать проблемы с прокси, SSL-сертификатами, учетными данными или ограничениями сети.
* **SSH:** Отладка SSH-соединений выявляет проблемы с SSH-ключами, правами доступа, конфигурацией `ssh-agent` или серверной частью SSH.

### Проблемы с окончаниями строк

Несоответствие в окончаниях строк между операционными системами (`CRLF` в Windows против `LF` в Unix-подобных системах) может привести к неожиданным изменениям в файлах и конфликтам.

Для решения этой проблемы в Git существует механизм автоматического преобразования окончаний строк, который настраивается с помощью параметра `core.autocrlf`.

* **Подробнее:** [Конфигурация Git → Управление окончаниями строк](./git_configuration.md#управление-окончаниями-строк)

### Разрешение конфликтов

Конфликты слияния (merge conflicts) — штатная, хотя и неприятная, часть работы в Git. Они возникают, когда изменения в разных ветках затрагивают одни и те же строки кода, и Git не может автоматически принять решение, какую версию оставить. Понимание процесса разрешения конфликтов является ключевым навыком.

### Работа в офлайн-режиме (`git bundle`)

`git bundle` — это эффективное решение для сценариев, когда сетевое подключение ограничено или отсутствует. Он позволяет "упаковать" коммиты и объекты Git в один бинарный файл, который можно передать по USB или другим способом, а затем "распаковать" на другом компьютере.

## Практические сценарии

### Отладка проблем с транспортом

#### Отладка HTTP/HTTPS-соединений

Используйте переменную окружения `GIT_CURL_VERBOSE` для получения подробного вывода от cURL:

```bash
# Для отладки операций git clone через HTTPS
GIT_CURL_VERBOSE=1 git clone <url_репозитория>

# Для отладки других HTTP/HTTPS операций
GIT_CURL_VERBOSE=1 git pull # или git push
```

Это покажет заголовки запросов/ответов, коды состояния HTTP и возможные ошибки аутентификации или сети.

#### Отладка SSH-соединений

Используйте переменную окружения `GIT_SSH_COMMAND` с флагом `-vvv` для `ssh` для получения подробного вывода:

```bash
# Для отладки операций Git через SSH (например, клонирования)
GIT_SSH_COMMAND="ssh -vvv" git clone <ssh_url_репозитория>

# Или для всех последующих SSH-операций в текущей сессии
export GIT_SSH_COMMAND="ssh -vvv"
git pull # или git push
unset GIT_SSH_COMMAND # Отключить отладку
```

Флаг `-vvv` обеспечивает максимальный уровень детализации, показывая процесс установления соединения, попытки аутентификации (с какими ключами) и любые ошибки.

> Для получения информации о настройке SSH-ключей и файла `~/.ssh/config` обратитесь к руководству по [конфигурации Git](./git_configuration.md#аутентификация-по-ssh).

### Разрешение конфликтов при слиянии

#### Когда и почему возникают конфликты

Конфликт при слиянии возникает, когда Git не может автоматически объединить изменения из двух веток. Типичные случаи:

* одни и те же строки в файле изменены в обеих ветках;
* файл изменен в одной ветке и удален в другой;
* переименование совпало с изменениями содержимого;
* одновременное добавление файла с одинаковым именем.

Конфликты появляются не только при `merge`, но и при `rebase`, `cherry-pick` и `revert`, поскольку везде применяется алгоритм трехстороннего слияния.

#### Как Git отображает конфликт

После неудачного автоматического слияния Git оставляет специальные маркеры в файле:

```markdown
<<<<<<< HEAD
вариант из текущей ветки
=======
вариант из объединяемой ветки
>>>>>>> feature
```

Редактору предстоит вручную выбрать нужные части, удалить маркеры и сохранить итоговую версию.

#### Рабочий процесс разрешения

1. **Инициировать слияние и увидеть конфликт**:

   ```bash
   git merge feature
   # или
   git rebase origin/main
   ```

2. **Просмотреть проблемные файлы**:

   ```bash
   git status
   git diff --name-only --diff-filter=U
   git diff
   ```

3. **Отредактировать файлы**, устранив маркеры, либо выбрать одну из сторон:

   ```bash
   # Выбрать версию из текущей (нашей) ветки
   git checkout --ours path/to/file
   # Выбрать версию из сливаемой (их) ветки
   git checkout --theirs path/to/file

   # Современный аналог с git restore
   git restore --source=HEAD -- path/to/file
   git restore --source=MERGE_HEAD -- path/to/file
   ```

4. **Отметить файлы как решенные** и завершить операцию:

   ```bash
   git add path/to/file
   git commit          # для merge
   git rebase --continue
   git cherry-pick --continue
   ```

5. **При необходимости откатить процесс**:

   ```bash
   git merge --abort
   git rebase --abort
   git cherry-pick --abort
   ```

#### Полезные инструменты и опции

* **Визуальное слияние**:

  ```bash
  git mergetool
  git config --global merge.tool meld
  ```

* **Повторное использование решений (Rerere)**: Git может запоминать, как вы разрешали конфликты, и применять те же решения автоматически в будущем.

  ```bash
  git config --global rerere.enabled true
  ```

* **Настройка стратегии для спорных кусков**: При слиянии можно указать Git, чью версию предпочесть в случае конфликта.

  ```bash
  git merge -X ours feature
  git merge -X theirs feature
  ```

  *Опции `-X ours/theirs` применяются только к конфликтующим фрагментам и не эквивалентны полной подмене файлов. Использовать осторожно.*

#### Типы конфликтов и подходы

| Тип конфликта   | Ситуация                                     | Подход к решению                                                    |
| --------------- | -------------------------------------------- | ------------------------------------------------------------------- |
| `modify/modify` | Одни и те же строки изменены                 | Вручную объединить смысл, удалить маркеры                           |
| `delete/modify` | Ветка A удаляет, B редактирует               | Решить, нужен ли файл; при необходимости восстановить и слить изменения |
| `add/add`       | Обе ветки добавили файл с тем же именем      | Переименовать один из файлов или объединить их содержимое           |
| `rename/modify` | В одной ветке переименование, в другой правки | Принять новое имя и перенести правки вручную                        |
| `rename/rename` | Разные новые имена для одного файла          | Выбрать итоговое имя, подправить ссылки и импорты                   |

### Git Bundle: Работа в офлайн-режиме

#### Создание "бандла" (пакета репозитория)

* **Создание бандла со всей историей:**

    ```bash
    git bundle create repo.bundle --all
    ```

    Эта команда создаст файл `repo.bundle`, содержащий все ветки и их полную историю.

* **Создание инкрементального бандла:**

    ```bash
    git bundle create updates.bundle HEAD ^<хеш_коммита_или_ветки_с_которой_начать_инкрементал>
    ```

    Например, `git bundle create updates.bundle main ^origin/main` создаст бандл с изменениями из ветки `main`, которых нет в `origin/main`.

#### Использование "бандла" (клонирование и обновление)

* **Клонирование репозитория из бандла:**
    На другом компьютере вы можете клонировать репозиторий из бандла, как если бы это был удаленный репозиторий:

    ```bash
    git clone repo.bundle my-repo
    ```

* **Получение обновлений из бандла:**
    Если у вас уже есть репозиторий, и вы хотите получить обновления из другого бандла:

    ```bash
    # Добавление бандла как временного удаленного репозитория
    git remote add offline-updates updates.bundle

    # Получение обновлений из бандла
    git pull offline-updates main

    # Удаление временного удаленного репозитория (опционально)
    git remote remove offline-updates
    ```

    `git bundle` очень полезен для передачи больших репозиториев по медленным сетям, для работы в условиях ограниченной или отсутствующей связи, а также для создания резервных копий.
