# Git: Устранение неполадок и отладка

## Определения

*   **Устранение неполадок Git:** Процесс диагностики и решения технических проблем, связанных с доступом, сетевым взаимодействием, целостностью данных и логическими ошибками в истории.
*   **Отладка транспорта (Transport Debugging):** Получение низкоуровневой информации о коммуникации Git с удаленными репозиториями по протоколам HTTP/HTTPS или SSH для выявления проблем аутентификации, прокси или сети.
*   **Разрешение конфликтов (Conflict Resolution):** Процесс ручного исправления изменений в файлах, которые Git не смог объединить автоматически из-за пересекающихся правок в одних и тех же строках.
*   **`git bundle`:** Инструмент для упаковки объектов и ссылок репозитория в один бинарный файл, позволяющий передавать изменения между изолированными средами (air-gap) без прямого сетевого подключения.
*   **`git bisect`:** Инструмент отладки, использующий бинарный поиск по истории коммитов для нахождения конкретного изменения, внесшего регрессию или ошибку.
*   **`git reflog`:** Журнал всех перемещений указателя `HEAD`, служащий страховочным механизмом для восстановления коммитов, которые стали недоступны через ветки.
*   **`git fsck`:** Утилита проверки целостности файловой системы Git, выявляющая поврежденные объекты и "висячие" (unreachable) ссылки.

## Базовые концепции

### Диагностика сетевых соединений

Проблемы с подключением обычно делятся на две категории:
1.  **Проблемы протокола HTTP/HTTPS:** Часто связаны с SSL-сертификатами, настройками прокси-серверов или неверными заголовками аутентификации. Git использует библиотеку cURL для этих операций.
2.  **Проблемы протокола SSH:** Связаны с правами доступа к приватным ключам, несоответствием алгоритмов шифрования между клиентом и сервером или неверной конфигурацией в `~/.ssh/config`.

### Природа конфликтов слияния

Конфликты возникают, когда алгоритм трехстороннего слияния (3-way merge) не может однозначно определить, какое изменение является приоритетным. Это происходит не только при `git merge`, но и при `rebase`, `cherry-pick`, `revert` и `stash pop`.

**Причины возникновения:**
*   Одни и те же строки изменены в обеих ветках.
*   Файл изменен в одной ветке и удален в другой.
*   Переименование файла совпало с изменениями его содержимого в другой ветке.
*   Одновременное добавление разных файлов с одинаковым именем.

### Механизмы `diff3` и `rerere`

*   **Style `diff3`:** По умолчанию Git показывает только "нашу" и "их" версии. Режим `diff3` добавляет блок `||||||| base`, показывающий, как выглядел текст до того, как обе ветки начали его менять. Это критически важно для понимания контекста изменений.
*   **`rerere` (Reuse Recorded Resolution):** Если включен, Git записывает состояние файла до и после вашего ручного разрешения конфликта. Если вы снова столкнетесь с таким же конфликтом (например, при перебазировании длинной цепочки коммитов), Git применит ваше решение автоматически.

### Восстановление данных и целостность

В Git практически невозможно удалить данные безвозвратно, если они были закоммичены.
*   `reflog` хранит историю перемещений `HEAD` обычно в течение 30-90 дней.
*   `fsck` находит объекты, которые не связаны ни с одной веткой или тегом, позволяя восстановить их.

## Практические сценарии

### Сценарий 1: Отладка сетевого взаимодействия

Если операции `clone`, `fetch` или `push` завершаются с ошибками или зависают.

#### Отладка HTTP/HTTPS (через cURL)
```bash
# Включить подробный вывод заголовков и состояния соединения
GIT_CURL_VERBOSE=1 git clone <url>

# Трассировка cURL с выводом всех переданных пакетов (для отладки прокси/SSL)
GIT_TRACE_CURL=1 git pull origin main
```

#### Отладка SSH
```bash
# Использовать режим максимальной детализации SSH клиента
GIT_SSH_COMMAND="ssh -vvv" git fetch origin

# Проверка, какой ключ предлагается серверу (настройка в сессии)
export GIT_SSH_COMMAND="ssh -i ~/.ssh/id_rsa_work -F /dev/null"
git push origin main
```

### Сценарий 2: Глубокое разрешение конфликтов

#### 1. Идентификация и анализ
```bash
# Список файлов с конфликтами
git status -s | grep "^UU"

# Посмотреть конфликт с учетом общего предка (если включен diff3)
git diff
```

#### 2. Инструменты выбора версий
```bash
# Выбрать версию из текущей ветки (ours)
git checkout --ours path/to/file
# или (современный вариант)
git restore --source=HEAD -- path/to/file

# Выбрать версию из сливаемой ветки (theirs)
git checkout --theirs path/to/file
# или (современный вариант)
git restore --source=MERGE_HEAD -- path/to/file
```

#### 3. Таблица типов конфликтов и подходы к решению

| Тип конфликта | Ситуация | Рекомендуемое действие |
| :--- | :--- | :--- |
| `modify/modify` | Изменены одни и те же строки. | Ручное слияние логики, удаление маркеров. |
| `delete/modify` | Ветка A удалила файл, B изменила его. | Решить: `git rm` (удалить) или `git add` (оставить версию B). |
| `add/add` | Обе ветки создали файл с одним именем. | Объединить содержимое или переименовать один из файлов. |
| `rename/modify` | В A — переименование, в B — правки. | Git обычно справляется, но проверьте правильность путей. |
| `rename/rename` | Разные новые имена для одного файла. | Выбрать одно имя, исправить импорты/ссылки. |

### Сценарий 3: Поиск виновного коммита (Bisect)

Метод бинарного поиска для нахождения коммита, который сломал код.

```bash
# 1. Начать процесс
git bisect start

# 2. Пометить текущее состояние как плохое, а старое (известное) как хорошее
git bisect bad HEAD
git bisect good v2.0.0

# 3. Git переключит вас на середину диапазона. Проверьте код и ответьте:
git bisect good  # Если баг не воспроизводится
# или
git bisect bad   # Если баг есть

# 4. Повторяйте, пока Git не укажет на первый "плохой" коммит.
# 5. Вернуться в исходное состояние:
git bisect reset
```

### Сценарий 4: Восстановление потерянных коммитов

Если вы сделали `git reset --hard` не на тот коммит или удалили ветку с важным кодом.

```bash
# 1. Просмотреть историю перемещений HEAD
git reflog
# → 1a2b3c4 HEAD@{0}: reset: moving to HEAD~1
# → 5e6f7g8 HEAD@{1}: commit: feat: very important feature (ПОТЕРЯНО!)

# 2. Восстановить коммит, создав на нем новую ветку
git branch recovery-branch 5e6f7g8

# 3. Найти совсем старые объекты (не в reflog)
git fsck --lost-found
# Результаты будут в .git/lost-found/commit/
```

### Сценарий 5: Git Bundle (Офлайн работа)

Перенос изменений через физические носители.

#### Создание пакета (Машина A)
```bash
# Бандл со всей историей всех веток
git bundle create repo.bundle --all

# Инкрементальный бандл (только новые изменения в main относительно сервера)
git bundle create updates.bundle main ^origin/main
```

#### Применение пакета (Машина B)
```bash
# Проверить, совместим ли бандл с текущим репозиторием
git bundle verify updates.bundle

# Получить изменения из бандла как из удаленного репозитория
git remote add bundle_file /path/to/updates.bundle
git pull bundle_file main
```

## Дополнительная информация

### Распространенные ошибки

*   **"Filename too long" (Windows):** Ограничение файловой системы.
    `git config --global core.longpaths true`
*   **"LF will be replaced by CRLF":** Проблема окончаний строк.
    См. [git_configuration.md](./git_configuration.md#управление-окончаниями-строк).
*   **"Permission denied (publickey)":** SSH-ключ не найден или не добавлен на сервер. Используйте `ssh-add -l` для проверки загруженных ключей.
