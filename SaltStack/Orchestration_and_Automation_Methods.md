# Оркестрация и методы автоматизации в SaltStack

## Определения

- **Оркестрация (Orchestration)**: Процесс координации задач на множестве узлов с учетом их взаимозависимостей. В отличие от [Highstate](Highstate_and_Execution_Order.md), оркестрация управляет всей инфраструктурой как единым целым.
- **Runner**: Модуль, исполняемый на Salt Master. Раннеры обеспечивают логику управления (например, `state.orchestrate`, `salt.cloud`).
- **Beacon (Маяк)**: Легковесный процесс на Minion, который отслеживает системные события (изменения файлов, нагрузку, логи) и выбрасывает уведомления в шину событий.
- **Reactor (Реактор)**: Компонент на Master, который слушает шину событий и инициирует действия (применение состояний, запуск раннеров) в ответ на сигналы от Beacons или внешних систем.
- **Salt-Cloud**: Инструмент для автоматизированного создания и уничтожения виртуальных машин в облаках (AWS, Azure, GCP, vSphere) и их последующей привязки к мастеру.

## Основные концепции

### Модели автоматизации

| Модель | Назначение | Инструмент |
| :--- | :--- | :--- |
| **Push** | Мгновенное управление «сверху вниз» | `salt`, `state.apply` |
| **Pull** | Автоматическая коррекция дрейфа конфигурации | `schedule` на миньонах |
| **Event-Driven** | Реактивная инфраструктура (Self-healing) | `Beacons` + `Reactor` |
| **Orchestration** | Сложные многошаговые пайплайны | `state.orchestrate` |

### Механизмы оркестрации (`state.orchestrate`)

Оркестрация выполняется через Runner и использует SLS-файлы на мастере. Ключевые возможности:
- **`salt.state`**: Применение состояния к группе миньонов.
- **`salt.function`**: Выполнение произвольной функции (например, очистка кэша).
- **`salt.wait_for_event`**: Остановка пайплайна до получения специфического события с шины.
- **Управление потоком**: Использование параметров `batch` (выполнение по частям), `subset` (выполнение на случайном подмножестве) и `failhard`.

## Практические сценарии

### 1. Многоуровневое развертывание (Blue-Green)
Пример оркестрации для обновления балансировщика только после успешного обновления бэкендов.

```yaml
# /srv/salt/orch/web_update.sls

update_backend_pool:
  salt.state:
    - tgt: 'role:web'
    - tgt_type: grain
    - sls: web.app
    - batch: 20% # Обновлять по 20% серверов за раз
    - failhard: True

reload_load_balancer:
  salt.function:
    - name: service.reload
    - tgt: 'role:lb'
    - tgt_type: grain
    - arg:
      - angie
    - require:
      - salt: update_backend_pool
```

### 2. Автоматическое масштабирование (Event-Driven)
Beacon на миньоне следит за нагрузкой, Reactor на мастере запускает новую ВМ через Salt-Cloud.

**Настройка Beacon (на миньоне):**
```yaml
beacons:
  load:
    - 1m:
        - 0.0: 2.0 # Событие, если Load Average > 2.0
```

**Настройка Reactor (на мастере):**
```yaml
# /srv/salt/reactor/autoscale.sls
{% if data['load']['1m'] > 2.0 %}
provision_new_node:
  runner.cloud.profile:
    - profile: aws_web_node
    - name: web-node-{{ range(1, 1000) | random }}
{% endif %}
```

### 3. Интеграция с CI/CD (Salt-API)
Запуск оркестрации через внешний вебхук (например, из GitLab CI).

```bash
curl -sk https://salt-master:8000/run \
  -H "X-Auth-Token: $TOKEN" \
  -d client='runner' \
  -d fun='state.orchestrate' \
  -d mods='orch.deploy_app' \
  -d pillar='{"version": "v1.2.3"}'
```

## Дополнительная информация

### Оптимизация и масштабирование
- **Batching**: Использование `batch` позволяет избежать «шторма запросов» к базе данных или API при одновременном обновлении тысяч узлов.
- **Throttling**: Ограничение количества одновременно выполняемых заданий на мастере.
- **Event Bus Tuning**: В версии 3008 LTS оптимизирована работа шины событий для высоконагруженных сред с 10,000+ миньонами ([архитектура](Architecture.md)).

### Сравнение подходов

- **Ansible**: Работает преимущественно в Push-модели. Salt Orchestration выигрывает за счет наличия постоянных агентов и шины событий, что позволяет реализовать реактивные сценарии.
- **Terraform**: Лучше подходит для создания базовой инфраструктуры (Networking, VPC). Salt-Cloud и Оркестрация эффективнее для управления жизненным циклом приложений и оперативного масштабирования.

### Best Practices (2026)
1.  **Разделение ответственности**: SLS для миньонов описывают *состояние*, SLS оркестрации — *процесс*.
2.  **Использование Pillar**: Передавайте динамические данные (версии ПО, флаги фич) через Pillar в момент запуска оркестрации.
3.  **Безопасность**: Ограничивайте права eAuth для запуска только конкретных оркестраций ([безопасность](Security_Approaches.md)).
4.  **Мониторинг**: Интегрируйте Beacons со стеком Prometheus/Grafana для визуализации инфраструктурных событий в реальном времени.
