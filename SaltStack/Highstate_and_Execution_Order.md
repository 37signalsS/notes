# Highstate и порядок выполнения

## Определения

- **Highstate**: Процесс применения полного набора состояний (states), назначенных узлу (minion) через `top.sls`. Salt компилирует все SLS-файлы в единый граф зависимостей и выполняет его, приводя систему к целевой конфигурации.
- **`top.sls`**: Файл верхнего уровня, который сопоставляет окружения (`saltenv`) и наборы состояний (SLS) с целевыми узлами (minions) на основе правил таргетинга.
- **Реквизиты (Requisites)**: Директивы, управляющие зависимостями и порядком выполнения состояний. Основные из них: `require`, `watch`, `onchanges`, `prereq`.
- **`include` и `extend`**: Директивы для включения одного SLS-файла в другой и для модификации уже определенных состояний.

---

## Основные концепции

**Порядок выполнения: граф, а не список**

В отличие от скриптов, исполняемых сверху вниз, Salt строит граф зависимостей на основе реквизитов. Если явные зависимости между состояниями отсутствуют, их порядок выполнения не гарантирован, но остается детерминированным при каждом запуске.

**Управление зависимостями через реквизиты**

| Реквизит | Назначение | Пример использования |
|---|---|---|
| `require` | Гарантирует выполнение зависимого состояния *до* текущего | Установка пакета до настройки конфига |
| `watch` | Как `require` + действие при изменении зависимого | Перезапуск сервиса при изменении конфига |
| `onchanges` | Выполняет текущее состояние *только если* зависимое изменилось | Миграция БД при изменении схемы |
| `prereq` | Проверка: зависимое выполняется до текущего, текущее — только если зависимое не изменилось | Валидация перед применением |
| `use` | Наследует параметры из другого состояния | Общие настройки для нескольких файлов |
| `listen` | Как `watch`, но для сервисов — отложенный перезапуск | Перезапуск сервиса после нескольких изменений |
| `require_in` | Обратный `require` — объявляет себя зависимостью для другого | Пакет объявляет `require_in` для конфига |
| `watch_in` | Обратный `watch` — быть наблюдаемым другим состоянием | Конфиг объявляет `watch_in` для сервиса |
| `onchanges_in` | Обратный `onchanges` — быть триггером для другого | Файл-триггер для команды |
| `prereq_in` | Обратный `prereq` — быть проверкой для другого | Предварительная проверка |
| `listen_in` | Обратный `listen` — быть прослушиваемым сервисом | Сервис прослушивает несколько источников |

**Атрибут `order`**

Атрибут `order` используется для тонкой сортировки независимых друг от друга состояний. Состояния с меньшим значением `order` выполняются раньше. Это полезно для задач, не имеющих логической связи, но требующих определенной последовательности.

## Практические сценарии

**1. Классическая цепочка: Пакет → Конфиг → Сервис**

Этот пример гарантирует, что пакет `nginx` будет установлен до управления его конфигурационным файлом, а сервис будет запущен после и перезапущен при изменении конфига.

```yaml
nginx-pkg:
  pkg.installed:
    - name: nginx

nginx-conf:
  file.managed:
    - name: /etc/nginx/nginx.conf
    - source: salt://nginx/nginx.conf.j2
    - template: jinja
    - require:
      - pkg: nginx-pkg

nginx-svc:
  service.running:
    - name: nginx
    - enable: True
    - require: # Сервис зависит от наличия конфига
      - file: nginx-conf
    - watch: # Сервис будет перезапущен, если конфиг изменился
      - file: nginx-conf
```

**2. Использование `onchanges` для миграций**

Команда миграции базы данных выполняется, только если изменился файл конфигурации приложения.

```yaml
migrate-db:
  cmd.run:
    - name: alembic upgrade head
    - cwd: /srv/app
    - onchanges:
      - file: app-config
```

**3. Модификация состояния с помощью `extend`**

Добавление новой `watch`-зависимости к ранее определенному состоянию `nginx-svc`.

```yaml
include:
  - nginx # Подключаем SLS, где определен nginx-svc

extend:
  nginx-svc: # ID состояния для расширения
    service.running:
      - watch:
        - file: /etc/nginx/ssl/certificate.crt # Добавляем новую зависимость
```

## Дополнительная информация

- **Тестовый режим**: Для проверки графа зависимостей и потенциальных изменений без реального применения используется флаг `test=True`: `salt '*' state.highstate test=True`.
- **Частичное применение**: Для применения конкретного SLS-файла вместо полного `highstate` — `state.apply`: `salt '*' state.apply nginx`.
- **Различие с оркестрацией**: `Highstate` управляет состоянием одного узла; для координации между несколькими узлами используется [оркестрация](Orchestration_and_Automation_Methods.md).
- **Отладка**: `state.show_states` — просмотр доступных состояний, `state.show_highstate` — просмотр того, что будет применено.
- **Анализ времени выполнения**: флаг `--profile`.

**Best Practices**

Полагайтесь на реквизиты, а не на явный `order`; избегайте циклических зависимостей (Salt обнаружит и сообщит об ошибке); используйте `include` для переиспользования общих состояний; всегда тестируйте с `test=True` перед применением в продакшене. Простой пример состояния — [создание пользователя](User_Creation.md). Идемпотентность — ключевое свойство декларативных систем ([модели управления конфигурацией](../Concepts/configuration_management_models.md#конвергенция-и-идемпотентность)), как и декларативный подход в целом ([IaC](../Concepts/iac_overview.md#декларативный-vs-императивный-подходы)).
