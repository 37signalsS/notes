# Highstate и порядок выполнения в SaltStack

## Определения

- **Highstate**: Процесс приведения миньона к целевому состоянию, описанному в `top.sls`. Salt компилирует все назначенные SLS-файлы в единый граф зависимостей.
- **`top.sls`**: Файл-индекс, сопоставляющий узлы с их ролями (SLS-файлами) в различных окружениях.
- **Реквизиты (Requisites)**: Директивы, определяющие логические связи и последовательность выполнения состояний (например, `require`, `watch`).
- **Скомпилированное состояние (Low State)**: Внутреннее представление Salt, где все зависимости разрешены, а шаблоны Jinja отрендерены.
- **Failhard**: Глобальный или локальный параметр, останавливающий выполнение всех последующих состояний при возникновении первой же ошибки.

---

## Основные концепции

### Порядок выполнения: Граф vs Список

В SaltStack порядок выполнения детерминирован, но не обязательно соответствует порядку строк в файле. Salt строит **направленный ациклический граф (DAG)**.
- Если зависимости не указаны, Salt выполняет состояния в порядке их появления в SLS-файле (начиная с версии 0.17.0).
- При наличии реквизитов граф перестраивается для соблюдения логики.

### Управление зависимостями (Requisites)

| Реквизит | Тип | Описание |
| :--- | :--- | :--- |
| `require` | Прямой | Текущее состояние выполнится только после успешного завершения целевого. |
| `watch` | Триггер | Как `require`, но вызывает выполнение (или рестарт) текущего, если целевое изменилось. |
| `onchanges` | Реактивный | Выполняется **только** если целевое состояние внесло изменения. |
| `onfail` | Обработка ошибок | Выполняется **только** если целевое состояние завершилось с ошибкой. |
| `prereq` | Проверка | Текущее состояние запускается для проверки изменений; если они есть, выполняется целевое, а затем текущее. |
| `listen` | Отложенный | Аналог `watch`, но действие выполняется в самом конце фазы применения состояний. |

**Инвертированные реквизиты:** `require_in`, `watch_in`, `onchanges_in` позволяют объявить зависимость "от обратного", что полезно при расширении базовых SLS без их модификации.

## Практические сценарии

### 1. Остановка при ошибке (Failhard)
Если критически важно не продолжать настройку при сбое (например, не настраивать БД, если не созданы разделы на диске):

```yaml
# Глобально в /etc/salt/minion: failhard: True

# Локально в SLS:
critical_disk_setup:
  module.run:
    - name: disk.format
    - device: /dev/sdb
    - failhard: True
```

### 2. Параллельное выполнение
Для ускорения работы на мощных узлах можно разрешить параллельное выполнение независимых веток графа:

```yaml
# Включается через параметр parallel в состоянии
long_running_task:
  cmd.run:
    - name: sleep 60
    - parallel: True
```

### 3. Агрегация состояний (State Aggregate)
Позволяет Salt объединять похожие состояния (например, установку множества пакетов через `pkg.installed`) в один вызов пакетного менеджера для оптимизации.

```yaml
# В /etc/salt/minion или в SLS
state_aggregate: True
```

## Дополнительная информация

### Отладка и визуализация графа

Перед применением изменений в продакшене рекомендуется использовать инструменты анализа:
- **`state.show_highstate`**: Показывает результирующую структуру данных, которая будет отправлена на миньон.
- **`state.show_lowstate`**: Показывает плоский список задач в порядке их выполнения.
- **`state.show_sls_ids`**: Выводит только список ID состояний для быстрой проверки включенных файлов.
- **`test=True`**: Эмуляция выполнения (Dry Run). Позволяет увидеть изменения без их применения.

### Оптимизация Highstate
- **`state_verbose: False`**: В конфиге мастера/миньона скрывает успешные состояния, оставляя только изменения и ошибки.
- **`state_output: changes`**: Сокращает вывод, показывая только полезную информацию об изменениях.
- **Runtime Requisites**: Использование Jinja для динамического формирования зависимостей на основе Grains или Pillar.
