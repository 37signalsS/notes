# Highstate и порядок выполнения в SaltStack

## Определения

- **Highstate**: Процесс приведения миньона к целевому состоянию, описанному в `top.sls`. Salt компилирует все назначенные SLS-файлы в единый граф зависимостей.
- **`top.sls`**: Файл-индекс, сопоставляющий узлы с их ролями (SLS-файлами) в различных окружениях. Порядок перечисления SLS-модулей внутри `top.sls` влияет на порядок выполнения при отсутствии реквизитов.
- **Реквизиты (Requisites)**: Директивы, определяющие логические связи и последовательность выполнения состояний (например, `require`, `watch`).
- **Low State (Low Data)**: Внутреннее представление Salt после компиляции и рендеринга шаблонов Jinja — плоский список исполняемых элементов (`__id__`, `__sls__`, `__run_num__`, `state`, `fun` и аргументы). Именно этот список упорядочивается и последовательно выполняется.
- **Failhard**: Глобальный или локальный параметр, останавливающий выполнение всех последующих состояний при возникновении первой же ошибки (жёсткий отказ). Поведение по умолчанию — «мягкий» отказ: выполнение продолжается даже после ошибки состояния.
- **`__run_num__`**: Порядковый номер состояния в рамках одного прогона. Назначается Salt после топологической сортировки графа реквизитов. При равенстве прочих условий состояния сортируются по `__run_num__`, что гарантирует детерминированный порядок выполнения.
- **`saltenv`**: Окружение Salt (environment), определяющее, какая версия SLS-файлов будет использована. При использовании GitFS `saltenv` обычно соответствует Git-ветке. Передаётся при вызове (`salt '*' state.apply webserver saltenv=prod`) или задаётся в конфиге миньона.
- **`pillarenv`**: Окружение Pillar, аналогично `saltenv`, но для данных Pillar. Позволяет изолировать секреты и конфигурации между окружениями. По умолчанию совпадает с `saltenv`.
- **`state.apply`**: Универсальная функция применения состояний. Без аргументов выполняет highstate, с аргументом — применяет конкретный SLS или список SLS. Доступна с версии 2015.5.0.
- **`state.highstate`**: Функция применения полного highstate. Полный аналог `state.apply` без аргументов; сохраняется для обратной совместимости.
- **`state.sls`**: Применение конкретного SLS-файла или списка SLS-файлов без полного highstate.
- **`state.sls_id`**: Применение одного конкретного состояния (ID) из SLS с учётом всех его реквизитов. Полезно для отладки отдельного блока.
- **Runtime Requisites**: Динамически формируемые на основе данных Grains или Pillar реквизиты через Jinja. Позволяют изменять зависимости «на лету» в зависимости от окружения.
- **`retry`**: Параметр состояния (доступен с версии 2019.2.0), автоматически повторяющий выполнение при неудаче заданное количество раз с указанной задержкой.

## Основные концепции

### Порядок выполнения: от High State к Low State

В SaltStack порядок выполнения детерминирован и не обязательно соответствует порядку строк в файле. Работа идёт в два этапа:

1. **Компиляция (High State → Low State)**: Salt собирает все назначенные через `top.sls` SLS-файлы, рендерит шаблоны Jinja и формирует плоский список задач (Low State).
2. **Упорядочивание и выполнение**: список сортируется с учётом реквизитов (топологическая сортировка, реализующая семантику направленного ациклического графа — DAG) и последовательно исполняется.

Это принципиально отличается от инструментов, выполняющих состояния в цикле обработки событий: Salt сначала строит конечный список и лишь затем итерирует его, что гарантирует предсказуемое выполнение.

**Неявный порядок (Implicit Ordering).** Если зависимости не указаны, состояния выполняются в порядке их объявления в SLS-файле. Это поведение управляется опцией `state_auto_order` (по умолчанию `True`, добавлена в версии 0.17.0); при `state_auto_order: False` включается лексикографический (классический) порядок. При highstate порядок между файлами определяется порядком записи модулей в `top.sls`.

**Циклические зависимости.** Salt обнаруживает циклические реквизиты на этапе компиляции и не позволяет их сформировать:

```bash
salt '*' state.highstate
# → Data failed to compile:
#   ----------
#   A recursive requisite was found, SLS "named" ID "dns_install" ID "dns_conf"
```

### Влияние окружений (`saltenv` и `pillarenv`)

Окружения позволяют использовать разные версии SLS-файлов и данных Pillar на разных миньонах или в разных ситуациях. При использовании GitFS `saltenv` сопоставляется с Git-веткой, что дает возможность параллельно поддерживать `base`, `prod`, `staging` и другие окружения.

```bash
salt '*' state.apply webserver saltenv=prod pillarenv=prod
```

Внутри SLS окружение можно получить через `__env__`, а окружение Pillar — через `pillar.get('pillarenv')`. Это позволяет динамически выбирать конфигурации и секреты без изменения кода состояний.

### Управление порядком вручную (`order`)

Параметр `order` переопределяет неявный порядок, задавая числовой приоритет:

```yaml
vim:
  pkg.installed:
    - order: 1   # выполнится раньше состояний без указанного order
```

Состояния без `order` выполняются после всех состояний с заданным `order`. Для отправки состояния в самый конец используется `order: last`:

```yaml
update_status:
  module.run:
    - name: http.query
    - order: last
```

Реквизиты всегда имеют приоритет над `order`, поэтому `order` следует применять только к состояниям, не участвующим в реквизитных связях.

### Управление зависимостями (Requisites)

| Реквизит | Тип | Описание |
| :--- | :--- | :--- |
| `require` | Прямой | Текущее состояние выполнится только после успешного завершения целевого. |
| `watch` | Триггер | Как `require`, но вызывает реакцию (рестарт/перезагрузка через `mod_watch`), если целевое изменилось. Работает только у состояний с реализацией `mod_watch` (например, `service`); у остальных ведёт себя как `require`. Для `service.running` доступен `reload: True` — перезагрузка вместо рестарта. |
| `onchanges` | Реактивный | Выполняется **только** если целевое состояние внесло изменения. В отличие от `watch`, при отсутствии изменений состояние полностью пропускается (например, остановленный сервис не запустится). |
| `onfail` | Обработка ошибок | Выполняется **только** если целевое состояние завершилось с ошибкой (например, уведомление или повторная попытка). |
| `prereq` | Проверка | Целевое состояние предварительно прогоняется в тестовом режиме (`test=True`) для оценки ожидаемых изменений; если изменения предвидятся, текущее состояние выполняется после целевого. Применяется, например, для перезапуска сервиса только при предстоящем изменении его конфигурации. |
| `use` | Наследование | Текущее состояние наследует все аргументы другого состояния (удобно для однотипных конфигураций, например сетевых интерфейсов). |
| `listen` | Отложенный | Аналог `watch`, но не меняет порядок выполнения состояний: все действия `listen` выполняются в самом конце фазы применения, после завершения всех остальных состояний. |

**Инвертированные реквизиты:** `require_in`, `watch_in`, `onchanges_in`, `onfail_in`, `prereq_in`, `use_in`, `listen_in` позволяют объявить зависимость «от обратного», что полезно при расширении базовых SLS-файлов без их модификации.

**Связывание из разных файлов (`sls`).** Для зависимости от целого SLS-файла используется тип реквизита `sls`:

```yaml
include:
  - network

httpd:
  service.running:
    - require:
      - pkg: httpd
      - sls: network        # зависимость от целого SLS-файла
```

**Условное выполнение (`onlyif` / `unless` / `creates`).** Это не реквизиты, а аргументы состояния, управляющие тем, запускать ли его вообще. Они не влияют на порядок выполнения, но могут пропустить состояние:

- `onlyif` — состояние выполняется, только если команда или функция Salt вернула истину.
- `unless` — состояние выполняется, только если команда или функция Salt вернула ложь.
- `creates` — состояние выполняется, только если указанный файл отсутствует.

```yaml
create_config:
  cmd.run:
    - name: cp /srv/templates/app.conf /etc/app/app.conf
    - creates: /etc/app/app.conf

ensure_running:
  service.running:
    - name: app
    - unless:
      - pgrep -f /opt/app/server.js
```

**Множественные реквизиты и `names`.** Реквизиты передаются списком и могут сочетать разные типы и цели одновременно. `names` позволяет применить одно состояние к нескольким именам:

```yaml
python-pkgs:
  pkg.installed:
    - names:
      - python3
      - pip
      - python3-setuptools
```

**Композиция SLS (`include` / `extend`).** `include` подключает другие SLS-файлы, `extend` — изменяет (расширяет) объявленные в них состояния, добавляя параметры или реквизиты без правки исходных файлов.

## Практические сценарии

### 1. Остановка при ошибке (Failhard)

Если критически важно не продолжать настройку при сбое (например, не настраивать БД, если не созданы разделы на диске):

```yaml
# Глобально в /etc/salt/minion.d/failhard.conf: failhard: True
# Локально в SLS:
critical_disk_setup:
  module.run:
    - name: disk.format
    - device: /dev/sdb
    - failhard: True
```

Глобальный `failhard` можно отменить для конкретного состояния значением `- failhard: False`. Также используется комбинация с `onfail`: состояние-обработчик запускается только при ошибке целевого.

### 2. Параллельное выполнение

Для ускорения работы на мощных узлах можно разрешить параллельное выполнение независимых веток графа (параметр `parallel: True` доступен с версии 2017.7.0 — состояние запускается в отдельном процессе):

```yaml
long_running_task:
  cmd.run:
    - name: sleep 60
    - parallel: True
```

Параллельные состояния по-прежнему соблюдают реквизиты: Salt дождётся завершения требуемого состояния перед запуском зависящего. Необходимо избегать конфликтов: параллельная установка пакетов блокирует менеджер пакетов, а параллельное управление одним и тем же файлом может дать непредсказуемый результат.

### 3. Агрегация состояний (State Aggregate)

Позволяет Salt объединять похожие состояния (например, установку множества пакетов через `pkg.installed`) в один вызов пакетного менеджера для оптимизации:

```yaml
# В /etc/salt/minion или глобально в конфиге миньона
state_aggregate: True
```

Опцию можно включать и точечно для отдельных состояний (`- state_aggregate: True` внутри объявления). Агрегация выполняется после учёта реквизитов: сначала группируются зависимости, затем сами функции.

### 4. Реакция на изменения (watch / listen)

Типичный паттерн — рестарт/перезагрузка сервиса при изменении его конфигурационного файла. С помощью `watch_in` связь объявляется со стороны файла:

```yaml
nginx:
  service.running:
    - enable: True
    - reload: True

nginx_config:
  file.managed:
    - name: /etc/nginx/nginx.conf
    - source: salt://nginx/nginx.conf
    - watch_in:
      - service: nginx
```

`listen`/`listen_in` применяются, когда порядок критичен: например, сначала применить все конфиги, а затем в конце прогона выполнить один общий рестарт всех сервисов.

### 5. Изоляция окружений через `saltenv` и `pillarenv`

При использовании GitFS окружения сопоставляются с Git-ветками. Это позволяет иметь параллельные версии конфигураций:

```bash
# Применение состояний из ветки prod
salt 'web-*' state.apply webserver saltenv=prod pillarenv=prod

# Проверка без применения
salt 'web-*' state.apply webserver saltenv=staging test=True
```

Внутри SLS можно динамически выбрать источник файла:

```yaml
app_config:
  file.managed:
    - name: /etc/app/config.yaml
    - source: salt://{{ saltenv }}/app/config.yaml
    - template: jinja
```

### 6. Условный рестарт через `prereq`

`prereq` полезен, когда нужно проверить, будет ли изменение, и только потом выполнить действие. Например, перезапустить сервис только если конфиг изменится:

```yaml
app_config:
  file.managed:
    - name: /etc/app/config.yaml
    - source: salt://app/config.yaml

restart_app:
  service.running:
    - name: app
    - prereq:
      - file: app_config
    - watch:
      - file: app_config
```

Salt сначала проверяет `app_config` в тестовом режиме. Если изменения предвидятся — выполняет `restart_app`. Если изменений нет — `restart_app` пропускается.

### 7. Отладка highstate через `state.show_lowstate`

Перед применением в продакшене проверьте порядок выполнения:

```bash
# Показать итоговый Low State
salt 'web-01' state.show_lowstate

# Показать Low State только для nginx
salt 'web-01' state.show_low_sls nginx

# Показать top.sls, который применится
salt 'web-01' state.show_top

# Показать результирующую структуру High State
salt 'web-01' state.show_highstate
```

`state.show_lowstate` особенно полезен, если порядок выполнения отличается от ожидаемого: он показывает фактический `__run_num__` для каждого состояния.

### 8. Роллинг обновления через `batch`

Для больших сред используйте `batch`, чтобы обновлять миньоны частями и снижать риск каскадного отказа:

```bash
# Обновить по 10% миньонов за раз
salt '*' state.apply batch=10%

# Обновить по 20 узлов
salt '*' state.apply batch=20

# С задержкой 30 секунд между партиями
salt '*' state.apply batch=10% batch_delay=30
```

### 9. Повторные попытки для нестабильных сервисов

Для состояний, которые могут падать по внешним причинам (например, сетевые зависимости), используйте `retry`:

```yaml
wait_for_db:
  module.run:
    - name: cmd.run
    - cmd: 'curl -fsS http://db:5432/health'
    - retry:
      attempts: 5
      interval: 10
    - timeout: 60
```

Если `cmd.run` вернёт ошибку — Salt повторит попытку до 5 раз с интервалом 10 секунд.

### 10. Динамические реквизиты через Jinja (Runtime Requisites)

Реквизиты можно формировать динамически на основе Grains или Pillar. Это позволяет адаптировать зависимости под конкретный миньон без изменения SLS:

```yaml
{% if grains['os'] == 'Ubuntu' %}
nginx_pkg:
  pkg.installed:
    - name: nginx

{% if pillar.get('nginx', {}).get('enable_ssl', False) %}
certbot_pkg:
  pkg.installed:
    - name: certbot
    - require:
      - pkg: nginx_pkg

{% endif %}
{% endif %}
```

Динамические реквизиты расширяются во время компиляции High State, поэтому Salt видит финальные зависимости и строит граф корректно.

## Дополнительная информация

### Отладка и визуализация графа

Перед применением изменений в продакшене рекомендуется использовать инструменты анализа:

- **`state.show_highstate`**: Показывает результирующую структуру данных, которая будет отправлена на миньон.
- **`state.show_lowstate`**: Показывает плоский список задач в порядке их выполнения.
- **`state.show_low_sls`**: Показывает Low State для конкретного SLS-файла (например, `salt '*' state.show_low_sls nginx`).
- **`state.show_sls_ids`**: Выводит только список ID состояний для быстрой проверки включенных файлов.
- **`state.show_state_usage`**: Анализ используемых и неиспользуемых состояний в highstate.
- **`state.show_top`**: Показывает `top.sls`, который миньон применит при highstate.
- **`test=True`**: Эмуляция выполнения (Dry Run). Позволяет увидеть изменения без их применения. Аналог без аргумента — функция `state.test` (принудительно включает `test=True`).

```bash
salt '*' state.show_lowstate
salt '*' state.show_low_sls nginx
salt '*' state.apply test=True   # dry run
salt '*' state.sls nginx test=True
```

**Запуск состояний.** Современный способ — `state.apply` (доступен с 2015.5.0): без аргументов выполняет highstate, с аргументом — применяет конкретный SLS (`state.apply nginx`). `state.highstate` и `state.sls` остаются доступными, `state.sls_id <id> <mods>` выполняет один ID с учётом всех его реквизитов.

### Оптимизация Highstate
- **`state_verbose: False`**: В конфиге мастера/миньона скрывает успешные состояния, оставляя только изменения и ошибки.
- **`state_output: changes`**: Сокращает вывод, показывая только полезную информацию об изменениях.
- **`state_aggregate: True`**: Объединяет одинаковые состояния в один вызов (см. сценарий 3).
- **`parallel: True`**: Для длинных задач на одном узле — отдельный процесс (с версии 2017.7.0).
- **`batch`**: Ограничение количества одновременно обновляемых миньонов для снижения пиковой нагрузки.
- **Cache**: `file_list_cache` для кэширования списка файлов; `pillar_cache` для Pillar; `grains_cache` для Grains.

### Версии и жизненный цикл

- **Актуальная версия:** 3008.2 LTS (июль 2026). Активная поддержка до июня 2027, поддержка по безопасности (CVE) до июня 2028.
- **3006 LTS:** активная поддержка завершилась в июле 2026, критическая поддержка по безопасности — до июня 2027.
- **3007 STS:** достиг EOL 31 июля 2026 и больше не получает обновлений.
- **Ключевые версии функциональности:** `state_auto_order` — 0.17.0, `state.apply` — 2015.5.0, `parallel: True` — 2017.7.0, `retry` — 2019.2.0, новый синтаксис `module.run` по умолчанию — 3005.

## Troubleshooting

### Типичные ошибки и решения

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `A recursive requisite was found` | Циклическая зависимость между состояниями или SLS-файлами | Визуализировать граф через `state.show_lowstate`; найти и разорвать цикл; использовать `prereq` вместо `require` там, где достаточно проверки |
| `Failed to compile SLS` | Синтаксическая ошибка YAML или Jinja | Выполнить `salt-call --local state.apply <sls> test=True` на мастере; проверить отступы и кавычки |
| `State не выполняется в ожидаемом порядке` | Не учтены реквизиты или `order` конфликтует | Включить `state_verbose: True`; проверить `state.show_lowstate`; отдавать приоритет реквизитам перед `order` |
| `state.apply применяет пустой highstate` | Минон не имеет назначений в `top.sls` для текущего `saltenv` | Проверить `salt '*' state.show_top`; убедиться что `top.sls` содержит записи для `id` или `match` миньона |
| `Jinja-ошибка при рендеринге` | Ошибка в шаблоне, отсутствующие переменные Pillar/Grains | Проверить `pillar.get()` с дефолтом; использовать `salt-call --local pillar.items` для отладки |
| `Нестабильное выполнение (flaky)` | Внешние зависимости (сеть, сервисы) или гонки при параллелизме | Добавить `retry`; использовать `onlyif`/`unless`; исключить параллелизм для общих ресурсов |
| `Salt-SSH: highstate не применяется` | Отсутствие ` roster_grains`, неправильный `roster` или `ssh_user` | Проверить `salt-ssh '*' state.show_top`; убедиться что `roster` содержит `sudo: True` при необходимости |
| `Высокое время компиляции` | Слишком большой `top.sls` или сложные Jinja-шаблоны | Включить `cache: True` для `file_client: local`; разбить `top.sls` на окружения; профилировать Jinja |

### Диагностические команды

```bash
salt 'web-01' state.show_lowstate                    # порядок и аргументы всех состояний
salt 'web-01' state.show_highstate                   # скомпилированный High State
salt 'web-01' state.show_top                         # актуальный top.sls для миньона
salt-call --local state.apply <sls> test=True        # локальная проверка SLS на мастере
salt 'web-01' state.apply test=True                  # dry run на миньоне
salt-run state.event pretty=True                     # наблюдение за событиями шины
tail -f /var/log/salt/minion                         # логи миньона
tail -f /var/log/salt/master                         # логи мастера
salt '*' saltutil.refresh_grains                      # принудительное обновление грайнов
salt '*' saltutil.refresh_pillar                      # принудительное обновление Pillar
```

## Best Practices

1. **Всегда ссылайтесь на ID объявления, а не на `name`, в реквизитах.** Это обеспечивает стабильность при переименовании ресурса и делает зависимости явными.

2. **Предпочитайте реквизиты (`require`/`watch`) параметру `order`.** Реквизиты семантически описывают *почему* состояние выполняется после другого, тогда как `order` задаёт только *в какой последовательности*. Реквизиты переопределяют `order` и самодокументируют логику.

3. **Используйте `saltenv` и `pillarenv` для изоляции окружений.** Никогда не храните production-секреты в `base`. Каждая среда (dev, staging, prod) должна иметь отдельную ветку GitFS и набор Pillar-данных.

4. **Всегда запускайте dry run (`test=True`) перед применением в продакшене.** Это позволяет увидеть planned changes без фактического воздействия на систему.

5. **Идемпотентность.** Все состояния должны быть безопасными для повторного запуска. Не должно быть различий между первым и вторым прогоном. Тестируйте идемпотентность регулярно.

6. **Избегайте параллельных состояний, затрагивающих одни и те же ресурсы.** Параллельность (`parallel: True`) ускоряет выполнение, но может привести к гонкам при установке пакетов или редактировании файлов.

7. **Версионируйте SLS и Pillar в Git.** Используйте GitFS или отдельный репозиторий. Ведите changelog оркестрации; для каждого SLS-файла указывайте `__doc__` в YAML.

8. **Мониторьте и логируйте.** Интегрируйте Salt с SIEM (Splunk, Elasticsearch) через `event_return` и `master_job_cache`. Настраивайте алёрты на `failhard` и `onfail`.

9. **Регулярно тестируйте восстановление.** Бэкапите PKI, `file_roots`, `pillar_roots` и Job Cache. Восстанавливайте среду на стенде, чтобы убедиться в работоспособности процедуры.

10. **Используйте `state.show_lowstate` как стандартный шаг проверки.** Перед каждым significant change смотрите итоговый порядок выполнения, чтобы убедиться что зависимости сформированы корректно.

## Edge Cases

### Очень большие `top.sls` (сотни миньонов)

При большом количестве записей в `top.sls` компиляция highstate на мастере может замедляться. Рекомендации:
- Разбейте `top.sls` на окружения (`base/top.sls`, `prod/top.sls`).
- Используйте `compound`-матчинг вместо перечисления отдельных ID.
- Включите кэширование `file_list_cache` и `grains_cache`.

### Циклические зависимости между разными SLS-файлами

Salt обнаруживает циклы на этапе компиляции, но при использовании `include` циклы могут быть неочевидны. Симптом: `Data failed to compile: A recursive requisite was found`. Решение: проверяйте реквизиты между включёнными SLS, особенно при использовании `extend`.

### Salt-SSH против Master-режима

В Salt-SSH highstate выполняется на каждой цели независимо через `salt-call --local state.apply`. Это означает:
- Отсутствие централизованной компиляции: каждый миньон строит свой Low State самостоятельно.
- Нет Event Bus и Reactor в классическом понимании.
- `__context__` не разделяется между миньонами.
- Для отладки используйте `salt-ssh '*' state.show_lowstate` вместо `salt '*' state.show_lowstate`.

### Masterless-режим (`salt-call --local`)

При использовании `salt-call --local state.apply` миньон работает без мастера:
- `top.sls` читается из локального `file_roots`.
- Нет внешних реквизитов (`sls`-реквизиты на другие миньоны недоступны).
- Нет reactor, beacons, schedule (в старом формате) — только локальное применение.
- Идеально для сборки golden images и изолированных сегментов.

### Разделение сети во время highstate

При обрыве связи с миньоном Salt отмечает задание как `Failed`. Если используется `batch` или `failhard`, сбой одного миньона не останавливает весь прогон. Для критичных сценариев комбинируйте `failhard` с `retry` на уровне orchestration runner.

### Гонки при параллелизме

Параллельные состояния (`parallel: True`) или параллельные прогоны на разных миньонах могут конкурировать за общий ресурс (файл, пакет, запись в БД). Симптом: недетерминированные ошибки, частично применённые изменения. Решения:
- Избегайте `parallel: True` для состояний, изменяющих одни и те же ресурсы.
- Используйте `lock`-состояния или внешние блокировки (файл-блокировка, Consul lock).
- Для базы данных используйте миграционные инструменты с идемпотентностью.

### `failhard` в оркестрации против per-state

Глобальный `failhard` в конфиге миньона останавливает весь прогон на миньоне. В оркестрации (`state.orchestrate`) доступен параметр `failhard` на уровне runner, который останавливает весь пайплайн оркестрации при сбое на любом миньоне. Не путайте их: `failhard` в SLS-состоянии действует локально, а `failhard` в `state.orchestrate` — глобально для всей инфраструктуры.
