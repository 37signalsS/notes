# Минионы и мастер: архитектура SaltStack

Архитектура SaltStack построена вокруг связки «мастер—миноны», обеспечивая масштабируемое удалённое исполнение и управление конфигурацией. Мастер координирует операции, хранит состояние и события, а минионы выполняют команды и применяют состояния на целевых узлах.

## Роли и процессы

| Компонент | Назначение |
|---|---|
| Master | Центральный узел: публикация команд, файловый сервер, шина событий, Pillar и топ-файлы |
| Minion | Агент на хосте: собирает grains, выполняет модули, применяет состояния |
| File Server | Доставка SLS, шаблонов и артефактов (локально или через gitfs) |
| Event Bus | Асинхронные события для реакторов и оркестрации |
| Returners | Каналы возврата результатов (в БД, очереди, APM) |
| Runners | Утилиты на мастере для оркестрации на уровне кластера |
| Syndic | Иерархия мастеров для многоуровневых инсталляций |

## Коммуникации и безопасность

Обмен сообщениями между мастером и минионами по умолчанию использует ZeroMQ; альтернативно доступен TCP-транспорт. Аутентификация основана на PKI: минион создает ключевую пару, отправляет публичный ключ мастеру, администратор принимает ключ, после чего устанавливается зашифрованный канал (симметричные сеансовые ключи).

Пример минимальной конфигурации мастера:

```yaml
# /etc/salt/master
interface: 0.0.0.0
file_roots:
  base:
    - /srv/salt
pillar_roots:
  base:
    - /srv/pillar
```

Пример минимальной конфигурации миниона:

```makefile
# /etc/salt/minion
id: web-01.example.com
master: 10.0.0.10
```

Ключи принимаются на мастере:

```css
salt-key -A
```

## Метаданные и целеуказание

*   Grains: статические или редко меняющиеся атрибуты узла (OS, CPU, роли).
*   Pillar: конфиденциальные данные и параметры, выборочно доставляемые минионам.

Целевые выборки поддерживают glob, regex, по grains, nodegroups и compound-выражения:

```nginx
salt -C 'G@os:Debian and E@db|cache' test.ping
```

## Состояния, исполнение и файловый сервер

Salt объединяет два уровня управления:

*   Execution Modules: единичные операции (pkg.install, service.restart, cmd.run).
*   States: декларативные описания желаемого состояния (SLS-файлы), рендеримые через Jinja/YAML и другие рендереры.

Пример топ-файла и состояния:

```csharp
# /srv/salt/top.sls
base:
  'role:web':
    - web.nginx
```

```yaml
# /srv/salt/web/nginx.sls
nginx:
  pkg.installed: []
  service.running:
    - enable: true
```

Файловый сервер может быть локальным или интегрирован с Git (gitfs), что упрощает версионирование состояний.

## Оркестрация и события

Все действия публикуются на шину событий мастера, что позволяет строить реактивные потоки: Reactor сопоставляет события с реакциями (например, автоматически применяет состояние при появлении нового миниона). Runners запускаются на мастере и управляют комплексными сценариями, в том числе state.orchestrate для многоузловых операций.

Упрощённый цикл:
1) Мастер публикует команду; 2) Минионы получают и исполняют; 3) Результаты возвращаются через returners; 4) События доступны реакторам и наблюдателям.

## Топологии развертывания

*   Один мастер: типовой вариант для небольших и средних инсталляций.
*   Мультимастер: минион знает несколько мастеров и переключается при сбоях (failover).
*   Иерархия с Syndic: деревья мастеров для распределённых регионов и сегментации.
*   Masterless (salt-call --local): автономное применение состояний без постоянного мастера, полезно для изолированных сред или образов.
