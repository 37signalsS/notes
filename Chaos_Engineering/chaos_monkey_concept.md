# Концепция Chaos Monkey

## Определения

**Chaos Monkey** — это программный инструмент и архитектурный паттерн, реализующий принцип случайного и преднамеренного внесения сбоев в рабочую среду для проверки устойчивости системы.

*   **Как инструмент:** Оригинальная разработка Netflix (открытый исходный код), предназначенная для случайного завершения экземпляров вычислительных ресурсов в инфраструктуре.
*   **Как паттерн:** Подход «обезьяньего тестирования» (Monkey Testing), при котором инфраструктурные компоненты (серверы, контейнеры, процессы) уничтожаются автоматически и без предупреждения, чтобы вынудить инженеров строить отказоустойчивые системы по умолчанию.

Это базовый элемент **[Chaos Engineering](chaos_engineering_overview.md)**, обеспечивающий практическую проверку гипотез об устойчивости.

### Дополнительные определения

*   **Steady State (Устойчивое состояние):** Нормальное поведение системы, зафиксированное до начала эксперимента.
*   **Blast Radius (Радиус поражения):** Контролируемый масштаб эксперимента — процент ресурсов или пользователей, затронутых сбоем.
*   **kube-monkey:** Реализация паттерна Chaos Monkey для Kubernetes на основе аннотаций в Deployment.
*   **Game Day:** Планируемое мероприятие, в ходе которого команда отрабатывает реагирование на хаос-эксперименты.

## Основные концепции

### Ключевые принципы

*   **Устойчивое состояние (Steady State):** Фиксация нормальных метрик системы до начала эксперимента.
*   **Гипотеза об устойчивости:** Предположение о том, что система продолжит функционировать при конкретном сбое.
*   **Случайность в рабочих часах:** Важнейший аспект — Chaos Monkey работает в рабочее время (например, с 9:00 до 17:00), когда инженеры на месте и могут отреагировать на непредвиденный каскадный сбой.
*   **Радиус поражения (Blast Radius):** Контролируемый масштаб эксперимента.
*   **Автоматизация и регулярность:** Хаос-эксперименты должны быть частью жизненного цикла инфраструктуры.

### Архитектура паттерна

Chaos Monkey работает в рамках цикла:

```
1. Определить группы ресурсов (target group)
2. Настроить вероятность сбоя (chaos schedule)
3. Зафиксировать steady state (метрики)
4. Выполнить инъекцию сбоя (удаление ресурса)
5. Сравнить с steady state
6. Остановить эксперимент при деградации
```

### Управление радиусом поражения

Для предотвращения полной остановки бизнеса используются фильтры:
1. **Группировка (Groups):** Объединение ресурсов по именам, тегам или группам хостов.
2. **Вероятность сбоя (Probability):** Настройка шанса срабатывания (например, 1 раз в день для критичных сервисов).
3. **Исключения (Exceptions):** Белые списки сервисов, которые временно защищены от атак (например, во время глобальных релизов).

### Виды имитируемых сбоев

| Категория сбоя | Метод реализации | Что проверяем |
|:---|:---|:---|
| **Compute (Вычисления)** | Удаление подов/серверов, SIGKILL процесса, выключение ноды | Механизмы самовосстановления, скорость репликации данных |
| **Network (Сеть)** | Внесение задержек (Latency), потеря пакетов, разделение сети (Split-brain) | Корректность таймаутов, Retry-политики, Circuit Breaker |
| **Storage (Хранилище)** | Отключение локальных дисков, замедление ввода-вывода (IOPS throttling) | Устойчивость к потере состояния, корректность работы в Read-only режиме |

## Практические сценарии

### Конфигурация kube-monkey

`kube-monkey` — реализация паттерна для Kubernetes на основе аннотаций в Deployment.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  annotations:
    kube-monkey/enabled: "true"
    kube-monkey/mtbf: "2"       # Среднее время между сбоями в днях
    kube-monkey/kill-mode: "fixed" # Режим убийства: fixed или percent
    kube-monkey/kill-value: "1"   # Убивать по 1 поду за раз
spec:
  ...
```

### Конфигурация PodDisruptionBudget (PDB)

PDB ограничивает количество одновременно недоступных подов.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-gateway-pdb
spec:
  minAvailable: 70% # Chaos Monkey не сможет убить поды, если их станет меньше 70%
  selector:
    matchLabels:
      app: api-gateway
```

### Конфигурация Linux-хостов (on-premises)

На Linux-хостах без Kubernetes chaos-эксперименты организуются через:

```bash
# Добавление сетевой задержки 200мс через tc
sudo tc qdisc add dev eth0 root netem delay 200ms 50ms

# Удаление процесса по PID
kill -9 <PID>

# Внеочередная остановка сервиса
sudo systemctl stop critical-service
```

### Интеграция с Nomad

Для оркестрации Nomad хаос-эксперименты реализуются через убийство аллокаций и drain узлов. Подробнее: **[Chaos Engineering для Nomad](../../Nomad/nomad_chaos_engineering.md)**.

### Сценарий: Проверка каскадного сбоя

1. **Действие:** Chaos Monkey удаляет инстанс сервиса «А».
2. **Ожидание:** Сервис «Б», зависящий от «А», использует кэш или возвращает дефолтный ответ (graceful degradation).
3. **Реальность:** Если сервис «Б» падает вместе с «А», значит обнаружена скрытая жесткая зависимость, которую нужно устранить.

## Операции и команды

### Проверка конфигурации blast radius

```bash
# Kubernetes: проверить аннотации kube-monkey
kubectl get deployments -o yaml | grep kube-monkey

# Linux: проверить активные tc-правила
sudo tc qdisc show dev eth0
```

### Управление исключениями

```bash
# Добавить сервис в белый список (приостановить хаос-эксперименты)
kubectl patch deployment my-app -p '{"spec":{"template":{"metadata":{"annotations":{"kube-monkey/enabled":"false"}}}}}'

# Linux: приостановить системный хаос на время релиза
systemctl mask critical-service
```

### Принудительный запуск эксперимента

```bash
# Kubernetes: убить конкретный под
kubectl delete pod my-app-xxx

# Linux: убить процесс по имени
pkill -9 critical-process

# Nomad: остановить аллокацию
nomad alloc stop <alloc-id>
```

### Валидация steady state

```bash
# Проверить метрики до эксперимента
curl -s http://prometheus:9090/api/v1/query?query=sum(rate(http_requests_total[5m]))

# Сравнить с steady state после эксперимента
```

## Устранение неполадок

| Проблема | Вероятная причина | Решение |
|:---|:---|:---|
| **Неожиданный каскадный сбой** | Скрытая жесткая зависимость между сервисами | Проверить интеграции, добавить Circuit Breaker и Fallback |
| **Blast Radius слишком широкий** | Неверная конфигурация групп хостов | Сузить группы, добавить исключения |
| **Пропуск сбоев (нет экспериментов)** | kube-monkey отключен или неверные аннотации | Проверить аннотации Deployment, логи kube-monkey |
| **Мониторинг не видит сбой** | Пропущенная метрика в steady state | Добавить бизнес-метрики, проверить dashboards |
| **Частые ненужные алерты** | Слишком высокая частота экспериментов | Уменьшить вероятность сбоя (mtbf) |

## Лучшие практики

1. **Начинайте с малого:** Устанавливайте вероятность сбоя 1 раз в неделю, затем увеличивайте частоту.
2. **Всегда ограничивайте Blast Radius:** Начинайте с 1 пода или 1 узла.
3. **Имейте аварийный останов (Emergency Stop):** Интегрируйте с мониторингом для автоматической остановки при критических метриках.
4. **Мониторьте бизнес-метрики:** HTTP 200, latency p99, error rate — это реальное состояние системы.
5. **Проводите Game Days:** Отрабатывайте реагирование на хаос-эксперименты с командой.
6. **Документируйте эксперименты:** Создавайте runbook для каждого сценария.
7. **Не проводите эксперименты во время критических периодов:** Глобальные релизы, маркетинговые акции.

## Дополнительная информация

### Netflix Simian Army (Армия обезьян)

Chaos Monkey был лишь частью экосистемы инструментов Netflix:
*   **Latency Monkey:** Имитировал деградацию сетевого уровня для проверки таймаутов.
*   **Chaos Gorilla:** Симулировал отказ целой подсети или кластера инфраструктуры.
*   **Chaos Kong:** Симулировал отказ всей инфраструктуры или географического сегмента.
*   **Janitor Monkey:** Автоматически удалял неиспользуемые ресурсы (забытые диски, старые образы).

### Интеграция с SRE и мониторингом

Современный Chaos Monkey не работает «вслепую»:
1. **Бюджет ошибок (Error Budget):** Эксперименты должны автоматически прекращаться, если бюджет ошибок на текущий период исчерпан.
2. **SLO-гейты:** Интеграция с Prometheus/Grafana позволяет остановить хаос, если ключевой показатель превышает допустимый предел.
3. **Автоматизированные откаты:** Если сбой привел к критической деградации, система хаос-тестирования должна уметь инициировать восстановление.

### Эволюция и современность

Netflix перевел Chaos Monkey в режим поддержки. Современные платформы предоставляют встроенные средства для Fault Injection. Однако **паттерн** остается актуальным для воспитания культуры надежности в команде.
