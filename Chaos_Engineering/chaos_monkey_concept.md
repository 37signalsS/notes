# Намеренные сбои: концепция chaos monkey

Намеренные сбои — это управляемые эксперименты, искусственно вызывающие отказ части инфраструктуры для проверки устойчивости сервисов. Классическая идея chaos monkey появилась как сервис, который в произвольный момент “вырубает” экземпляры приложений или узлы, принуждая архитектуру переживать потерю ресурсов без деградации пользовательского опыта. Смысл не в разрушении, а в накоплении доказательств, что проектируемые механизмы отказоустойчивости действительно работают под давлением реальных непредвиденных событий.

Chaos monkey фокусируется на простом, но показательно строгом сценарии: завершать процессы, контейнеры, виртуальные машины или поды, чтобы подтверждать корректность автолечения, балансировки, репликации и механизмов перераспределения трафика. Эксперименты проводятся гипотезо-ориентированно: сначала утверждение о поведении системы, затем ограниченный по радиусу взрыва эксперимент и наблюдение метрик.

## Ключевые принципы

*   Гипотеза: формулируется ожидаемое поведение при потере N экземпляров или одного узла.
*   Контроль радиуса: минимальный охват, постепенно расширяемый после успешных итераций.
*   Автоматизация и случайность: репликация сценариев и непредсказуемость момента отказа.
*   Наблюдаемость: метрики, логи, трассировки для подтверждения гипотезы.
*   Страховочные барьеры: условия немедленной остановки, окна запуска, whitelists/blacklists.
*   Регламент: согласованные роли, уведомления и интеграция с процессами инцидент-менеджмента.

## Виды сбоев, имитируемых chaos monkey

| Категория сбоя         | Примеры вмешательства                        | Проверяемые свойства                                       |
| ---------------------- | -------------------------------------------- | ---------------------------------------------------------- |
| Вычислительные ресурсы | Уничтожение VM/подов, рестарт процессов        | Самовосстановление, перезапуски, реплики                   |
| Сеть                   | Потеря пакетов, латентность, разрыв соединений | Таймауты, повторные попытки, деградационные режимы        |
| Хранилище              | Недоступность тома, замедление I/O           | Кэширование, очереди, устойчивость к временной недоступности |
| Зависимости            | Отказ внешнего API, лимиты rate limiting     | Circuit breaker, fallback, изоляция отказов                |

## Ограждения безопасности

*   Чётко определённые SLO-гейты и условия автопрерывания при превышении ошибок.
*   Окна запуска вне пиковых периодов и исключения для критичных сервисов.
*   Лимит на количество одновременных вмешательств и строгая идентификация целей по меткам.
*   Предварительные runbook’и: допустимые действия, пути отмены, контакты on-call.
*   Отдельные окружения и постепенное продвижение: staging → частичный prod → полный prod.

## Минимальный пример для Kubernetes

Поддержание работоспособности при произвольном удалении одного пода часто начинается с базовых защит и управляемого “удушения” нагрузки.

Пример PodDisruptionBudget, запрещающий одновременно терять более одного пода:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: app-pdb
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: frontend
```

Упрощённый CronJob, случайно удаляющий один под по метке раз в час, с аннотациями для безопасного включения/выключения:

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: chaos-monkey-frontend
  annotations:
    chaos/enabled: "true"
spec:
  schedule: "0 * * * *"
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: chaos-operator
          containers:
          - name: killer
            image: bitnami/kubectl:latest
            command:
            - sh
            - -c
            - >
              [ "$CHAOS_ENABLED" = "true" ] &&
              POD=$(kubectl get po -l app=frontend -o jsonpath='{.items[*].metadata.name}' |
                   tr ' ' '
' | shuf -n1) &&
              kubectl delete pod "$POD" --wait=false || echo "chaos disabled";
            env:
            - name: CHAOS_ENABLED
              valueFrom:
                configMapKeyRef:
                  name: chaos-settings
                  key: enabled
          restartPolicy: OnFailure
```

## Встраивание в процессы

*   Планирование экспериментов в календаре изменений с уведомлением заинтересованных команд.
*   Предварительные проверки наблюдаемости и алертинга, готовность к откату.
*   Интеграция с CI/CD: запуск ограниченных тестов устойчивости после деплоя.
*   Постинцидентный разбор результатов эксперимента, закрепление улучшений архитектуры и конфигурации.
*   Каталог гипотез и проведённых сценариев как живой артефакт операционной практики.
