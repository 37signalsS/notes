# Концепция Chaos Monkey

## Определения

**Chaos Monkey** — это сервис или процесс, который намеренно и случайным образом отключает компоненты инфраструктуры (например, виртуальные машины, контейнеры) в продакшене. Это частный, но классический случай **[Chaos Engineering](chaos_engineering_overview.md)**. Его цель — принудить систему быть отказоустойчивой по дизайну, гарантируя, что потеря одного или нескольких узлов не приведёт к деградации сервиса для конечного пользователя.

## Основные концепции

### Ключевые принципы

* **Гипотеза:** Формулируется ожидаемое поведение при потере N экземпляров (например, "потеря одного пода не повлияет на доступность сервиса").
* **Случайность:** Непредсказуемость момента отказа заставляет инженеров строить постоянно устойчивые системы, а не готовиться к запланированным отключениям.
* **Автоматизация:** Эксперименты выполняются автоматически и регулярно.
* **Контроль радиуса:** Вмешательство ограничивается определёнными приложениями или средами, чтобы минимизировать риск.

### Виды имитируемых сбоев

| Категория сбоя | Примеры вмешательства | Проверяемые свойства |
|---|---|---|
| Вычислительные ресурсы | Уничтожение VM/подов, рестарт процессов | Самовосстановление, репликация, балансировка |
| Сеть | Потеря пакетов, разрыв соединений | Таймауты, повторные попытки (retries) |
| Хранилище | Недоступность тома, замедление I/O | Устойчивость к временной недоступности |

## Практические сценарии

### Пример: PodDisruptionBudget и удаление пода в Kubernetes

Чтобы безопасно применять Chaos Monkey в Kubernetes, используется `PodDisruptionBudget` (PDB), который гарантирует минимальное количество доступных реплик. Подробнее о PDB в [Высокая доступность в Kubernetes](../Kubernetes/Base/high_availability.md) и [PodDisruptionBudget](../Kubernetes/Autoscaling/pod_disruption_budget.md).

**1. Ограничение недоступности:**
Этот PDB запрещает одновременную потерю более одного пода для приложения `frontend`.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: app-pdb
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: frontend
```

**2. Автоматическое удаление пода:**
Этот `CronJob` раз в час случайным образом удаляет один под, имитируя работу Chaos Monkey.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: chaos-monkey-frontend
spec:
  schedule: "0 * * * *"
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: chaos-operator
          containers:
          - name: killer
            image: bitnami/kubectl:latest
            command: ["sh", "-c", "POD=$(kubectl get po -l app=frontend -o jsonpath='{.items[*].metadata.name}' | tr ' ' '\n' | shuf -n1) && kubectl delete pod $POD --wait=false"]
          restartPolicy: OnFailure
```

## Дополнительная информация

### Встраивание в процессы

* **Планирование:** Эксперименты вносятся в календарь изменений.
* **Интеграция с CI/CD:** Запуск тестов на устойчивость после каждого деплоя.
* **Анализ:** Результаты анализируются для улучшения архитектуры.

### Безопасность

* Используйте SLO-гейты для автоматической остановки эксперимента.
* Исключайте критичные сервисы из области воздействия на начальных этапах.
* Готовьте `runbook` для ручного отката.
