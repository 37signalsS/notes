# Метрики в Chaos Engineering

## Определения

**Метрики в Chaos Engineering** — это количественные показатели, используемые для валидации гипотез об устойчивости системы. Они позволяют объективно оценить поведение сервиса в условиях контролируемого сбоя, сравнивая его с **устойчивым состоянием (Steady State)**.

Основная цель — подтвердить, что даже при инъекции сбоя ключевые индикаторы качества (**SLI**) остаются в рамках целевых уровней (**SLO**), а механизмы самовосстановления отрабатывают за регламентированное время.

## Основные концепции

### Ключевые категории метрик

| Категория | Примеры | Что показывает (Инсайт) |
|---|---|---|
| **Пользовательские (L1)** | p95/p99 задержка, HTTP 5xx rate | Реальный опыт пользователя. Основной индикатор успеха эксперимента. |
| **Системные (L2)** | CPU Throttling, Memory Usage, Disk I/O | Здоровье инфраструктуры и запас прочности (Headroom). |
| **Бизнесовые (L0)** | Число заказов в минуту, успешные логины | Прямое влияние отказа на прибыль и бизнес-цели. |
| **Метрики восстановления** | MTTD, MTTR, RTO | Скорость обнаружения и автоматического восстановления системы. |
| **Blast Radius Metrics** | Кол-во затронутых подов/пользователей | Эффективность механизмов изоляции и ограничения области поражения. |

### Дизайн сравнения и валидация гипотез

*   **Steady State Baseline:** Фиксация метрик в нормальных условиях. Рекомендуется брать усредненные значения за аналогичный период времени (например, тот же час в прошлый вторник) для учета сезонности.
*   **Confidence Score:** Оценка уверенности команды в системе. Хаос-эксперименты должны повышать этот балл по мере прохождения более сложных тестов.
*   **SLO Error Budget:** Эксперимент не должен «съедать» более 5-10% от доступного месячного бюджета ошибок, если иное не согласовано.
*   **Stop-switch (Аварийная остановка):** Условие, при котором эксперимент немедленно прекращается (например, рост ошибок >5% в течение 30 секунд).

## Практические сценарии

### Примеры вычислений в PromQL

**1. Сравнение p99 задержки с историческим baseline:**
Позволяет увидеть, насколько эксперимент замедлил систему относительно «нормального» состояния.

```promql
# Текущий p99 (за последние 5 минут)
p99_now = histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket{job="api"}[5m])))

# p99 час назад (baseline)
p99_baseline = histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket{job="api"}[5m] offset 1h)))

# Дельта (коэффициент замедления)
slowdown_factor = p99_now / p99_baseline
```

**2. Расчет доли ошибок (Error Rate) во время инъекции сбоя:**
Критическая метрика для срабатывания Stop-switch.

```promql
# Доля 5xx ошибок в процентах
error_rate_pct = sum(rate(http_requests_total{status=~"5.."}[1m])) 
                 / 
                 sum(rate(http_requests_total[1m])) * 100
```

**3. Валидация MTTR (Mean Time to Recovery):**
Измерение времени от пика ошибок до их возвращения к уровню baseline после прекращения воздействия.

```promql
# Упрощенная проверка: ниже ли уровень ошибок порога SLO?
is_recovered = error_rate_pct < 0.1
```

## Дополнительная информация

### Интерпретация и типичные ловушки

*   **Игнорирование "хвостов":** Среднее значение (mean) может быть идеальным, пока 1% пользователей (p99) получает таймауты. В хаос-инженерии всегда ориентируйтесь на квантили высокого порядка.
*   **Маскировка сбоя ретраями:** Если клиент делает 3 попытки, `error_rate` на сервере вырастет, но пользователь может не заметить сбоя. В этом случае следите за ростом общего количества запросов (`RPS`) и `latency`.
*   **Steady State Drift:** Системы меняются. Базовый уровень метрик, зафиксированный месяц назад, сегодня может быть неактуален.
