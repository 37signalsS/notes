# Метрики и сравнение состояния сервиса до и после сбоя

Сравнение состояния сервиса до и после эксперимента в рамках chaos engineering опирается на заранее согласованные SLI/SLO, четкую гипотезу и корректный выбор метрик. Важно зафиксировать базовый уровень (baseline) в сопоставимом окне времени и использовать одинаковые способы агрегирования, чтобы не смешивать эффекты суточной сезонности, кэшей и прогрева.

## Какие метрики сравнивать

*   **Пользовательские (опыт взаимодействия)**
    *   Задержки p50/p95/p99, доля ошибок, таймауты, успешность критических операций.
*   **Системные (ресурсы и насыщение)**
    *   Utilization CPU/Memory/IO, saturation (очереди, retransmits), throughput.
*   **Бизнесовые**
    *   Конверсия, среднее время выполнения бизнес-процесса, отказ от корзины, успешные платежи.

| Категория       | Примеры                | Аспекты сравнения                                  |
| --------------- | ---------------------- | -------------------------------------------------- |
| Пользовательские| p95 latency, error rate| Δ% к baseline, изменение хвостов (p99), timeout ratio |
| Системные       | CPU, GC паузы, queue depth | Пиковые значения, корреляция с задержками          |
| Бизнесовые      | Успешные заказы        | Стабильность конверсии при том же трафике          |

Выбор агрегатов: для задержек — квантили, для ошибок — доли на основе счетчика успешных/всех событий, для ресурсов — p95/максимумы. Среднее (avg) для задержек малоинформативно и маскирует хвосты.

## Окна сравнения и дизайн

*   До эксперимента: baseline-окно ≥ длительности эксперимента, с той же нагрузкой.
*   Во время: исключить прогрев и эффекты планировщика; фиксировать аннотацией начало/конец.
*   Контроль/эксперимент: предпочтительно пропорционально разделять трафик (canary/флаг) и сравнивать параллельные когорты вместо разных моментов времени.
*   Нейтрализация мешающих факторов: одинаковые версии, лимиты, конфигурации; отключенные автоскейлеры или фиксированные реплики.

## Примеры вычислений в PromQL

p95 задержка HTTP с сопоставлением к baseline той же длительности с offset:

```promql
p95_now =
  histogram_quantile(0.95,
    sum by (le) (rate(http_request_duration_seconds_bucket{job="api"}[5m])))

p95_before =
  histogram_quantile(0.95,
    sum by (le) (rate(http_request_duration_seconds_bucket{job="api"}[5m] offset 30m)))

delta_p95_pct = (p95_now - p95_before) / p95_before * 100
```

Доля ошибок и burn rate относительно целевого успеха 99.5%:

```promql
err_rate =
  increase(http_requests_total{job="api",status=~"5.."}[5m])
  /
  increase(http_requests_total{job="api"}[5m])

burn_rate_1h = (avg_over_time(err_rate[1h])) / (1 - 0.995)
```

Очереди и насыщение (признаки скрытой деградации):

```promql
queue_depth = avg(queue_length{queue="ingress"}[5m])
retries = rate(http_client_retries_total{job="api"}[5m])
```

Сравнение когорт при флаговом расколе трафика:

```promql
p99_treated =
  histogram_quantile(0.99, sum by (le)
    (rate(http_request_duration_seconds_bucket{variant="experiment"}[5m])))

p99_control =
  histogram_quantile(0.99, sum by (le)
    (rate(http_request_duration_seconds_bucket{variant="control"}[5m])))

ratio = p99_treated / p99_control
```

## Интерпретация и типичные ловушки

*   Учитывать хвосты: рост p99 без изменения среднего — признак деградации реально важных пользовательских сценариев.
*   Ретраи и таймауты искажают картину: невидимые ошибки «маскируются» повторными запросами, повышая нагрузку и задержки.
*   Пропуски данных: интерполированные нули в метриках счетчиков дают ложное снижение; проверяйте up-серии и статус экспортеров.
*   Сезонность: сравнивать одновременно и/или нормировать по трафику, иначе дневные пики исказят выводы.
*   Связь метрик: рост queue depth и retransmits часто предшествует ухудшению p95; полезна корелляция метрик по времени.

Предварительно определенные триггеры остановки помогают избежать эскалации: порог по p99, доле ошибок, скорости сжигания бюджету ошибок и глубине очередей на заданном интервале.
