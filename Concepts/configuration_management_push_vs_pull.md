# Модели доставки конфигурации: Push против Pull

## Определения

**Модели доставки конфигурации** — это архитектурные подходы, определяющие способ передачи желаемого состояния от центральной системы управления конфигурацией (**Configuration Management, CM**) к целевым узлам.

*   **Push-модель (проталкивание):** Метод, при котором центральный сервер (контроллер) инициирует соединение и активно передает конфигурацию на управляемые узлы.
*   **Pull-модель (вытягивание):** Метод, при котором управляемые узлы самостоятельно запрашивают конфигурацию у центрального сервера через определенные интервалы времени.

Выбор модели напрямую влияет на масштабируемость, сетевую безопасность и скорость реакции инфраструктуры на изменения.

## Базовые концепции

### Push-модель (Проталкивание)

В этой модели управляющий узел (контроллер) является активной стороной. Он подключается к целевым серверам, используя стандартные протоколы удаленного управления, такие как **SSH (Secure Shell)** для Linux или **WinRM (Windows Remote Management)** для Windows.

*   **Принципиальная схема:** `Контроллер → Сеть → Управляемый узел`.
*   **Особенности:** Узлы являются пассивными получателями команд. На них обычно не требуется установка специализированного программного обеспечения (**ПО**), достаточно наличия интерпретатора (например, Python).
*   **Примеры:** Ansible, Fabric.

### Pull-модель (Вытягивание)

В этой модели активной стороной является управляемый узел. На нем устанавливается специальная программа-агент, которая регулярно обращается к центральному серверу (мастеру) за обновлениями.

*   **Принципиальная схема:** `Агент на узле → Сеть → Центральный сервер`.
*   **Особенности:** Агент сам «знает», как привести систему к желаемому состоянию. Если сервер временно недоступен, агент повторит попытку позже.
*   **Примеры:** Puppet, Chef, SaltStack (в стандартном режиме).
*   **Современный контекст (GitOps):** Подход **GitOps** (например, ArgoCD или Flux) является современной реализацией Pull-модели для Kubernetes, где агент отслеживает состояние Git-репозитория.

### Сравнительный анализ

| Характеристика | Push-модель | Pull-модель |
| :--- | :--- | :--- |
| **Инициатор** | Центральный контроллер | Агент на конечном узле |
| **Скорость реакции** | Мгновенная (команда выполняется сразу) | Отложенная (зависит от интервала опроса агента) |
| **Сетевые доступы** | Контроллер должен «видеть» все узлы | Узлы должны «видеть» центральный сервер |
| **Масштабируемость** | Ограничена ресурсами контроллера (параллелизм) | Очень высокая (нагрузка распределена по узлам) |
| **Управление агентами** | Не требуется (Agentless) | Требуется установка и обновление агентов |
| **Автономность** | Низкая (требуется постоянный доступ) | Высокая (узел сам применит конфиг при появлении сети) |
| **Борьба с дрейфом** | Только при запуске плейбука/задачи | Автоматическая (агент постоянно сверяет состояние) |

## Практические сценарии

### Сценарий 1: Экстренное исправление уязвимости (Push)

**Ситуация:** Обнаружена критическая уязвимость в пакете `openssl`. Нужно обновить его на 500 серверах немедленно.
**Решение:** Использование Ansible. Одной командой контроллер запускает обновление на всех узлах параллельно.
**Преимущество:** Вы полностью контролируете момент начала и завершения операции.

### Сценарий 2: Поддержание стандартов комплаенса (Pull)

**Ситуация:** Требуется гарантировать, что файл `/etc/hosts` содержит определенные записи на всех серверах компании, и никто не изменил его вручную.
**Решение:** Использование Puppet. Агент каждые 30 минут проверяет файл. Если системный администратор внес ручную правку, агент перезапишет её эталонной версией из репозитория.
**Преимущество:** Автоматическое исправление **дрейфа конфигурации (Configuration Drift)** без участия человека.

### Сценарий 3: Масштабирование в динамических средах (GitOps/Pull)

**Ситуация:** Автомасштабирование в облаке создает десятки новых экземпляров микросервиса в минуту.
**Решение:** Использование ArgoCD. Новые поды в Kubernetes автоматически «подтягивают» свою конфигурацию, как только они регистрируются в кластере, без необходимости настройки доступа со стороны CI-системы.

## Дополнительная информация

### Безопасность и сетевая топология

*   **Push:** Требует хранения учетных данных (ключей SSH, паролей) на контроллере. Удобен для закрытых корпоративных сетей.
*   **Pull:** Узлы не требуют входящих соединений, что позволяет им находиться за **NAT (Network Address Translation)** или Firewalls. Безопасность обычно строится на базе **PKI (Public Key Infrastructure)** и сертификатов.

### Гибридная модель

Многие современные системы (например, SaltStack) поддерживают гибридный подход: агентское взаимодействие (Pull) сочетается с возможностью немедленной отправки команд (Push) через шину событий. Также часто практикуется схема: Ansible (Push) используется для начальной настройки (**Bootstrap**) и установки агента постоянного управления (Pull).
