# Модели доставки конфигурации: Push против Pull — Сравнение

## Определения

**Модели доставки конфигурации** — это архитектурные подходы, определяющие способ передачи желаемого состояния от центральной системы управления конфигурацией (**Configuration Management, CM**) к целевым узлам (хостам, контейнерам, сетевым устройствам).

*   **Push-модель (проталкивание):** Метод, при котором центральный сервер (контроллер) инициирует соединение и активно передает данные конфигурации на управляемые узлы.
*   **Pull-модель (вытягивание):** Метод, при котором управляемые узлы самостоятельно обращаются к центральному серверу за обновлениями конфигурации через определенные интервалы времени или по событию.

Выбор модели напрямую влияет на сетевую безопасность, масштабируемость и оперативность управления инфраструктурой.

## Базовые концепции

### Push-модель (Проталкивание)

В этой модели управляющий узел (Control Node / Controller) является активной стороной. Он подключается к целевым серверам, используя стандартные протоколы удаленного управления: **SSH (Secure Shell)** для Unix-подобных систем или **WinRM/WinSSH** для Windows.

*   **Принципиальная схема:** `Центральный контроллер → Сеть (L3-L4) → Управляемый узел`.
*   **Особенности:**
    *   **Agentless:** На узлах не требуется установка специализированного ПО, достаточно интерпретатора (Python, PowerShell) и открытого порта для управления.
    *   **Централизация управления:** Все ключи и доступы хранятся на контроллере.
*   **Примеры:** Ansible, Fabric, Terraform (через API провайдеров).

### Pull-модель (Вытягивание)

В этой модели активной стороной является управляемый узел. На нем устанавливается программа-агент, которая регулярно запрашивает у центрального сервера (Master/Server) свою целевую конфигурацию.

*   **Принципиальная схема:** `Агент на узле → Сеть (L3-L4) → Центральный сервер`.
*   **Особенности:**
    *   **Автономность:** Агент сам «знает», как привести систему к желаемому состоянию, и может делать это повторно без команд извне.
    *   **Работа через NAT/Firewall:** Узлам не требуется входящий доступ; достаточно разрешить исходящий трафик к серверу управления.
*   **Примеры:** Puppet, Chef, SaltStack (в режиме Minion), **Ansible Pull**.
*   **Современный контекст (GitOps):** Реализация Pull-модели для Kubernetes, где агенты (ArgoCD, Flux) отслеживают состояние Git-репозитория и применяют изменения в кластер.

## Сравнительный анализ

| Характеристика | Push-модель | Pull-модель |
| :--- | :--- | :--- |
| **Инициатор** | Центральный контроллер | Агент на конечном узле |
| **Скорость реакции** | Мгновенная (команда выполняется немедленно) | Отложенная (зависит от интервала опроса) |
| **Сетевые требования** | Открытый входящий порт на узлах (SSH/WinRM) | Разрешенный исходящий трафик от узлов |
| **Масштабируемость** | Ограничена ресурсами контроллера (CPU, RAM) | Высокая (нагрузка распределена по узлам) |
| **Управление агентами** | Не требуется (удобно для первичной настройки) | Требуется жизненный цикл агента (установка, обновление) |
| **Безопасность** | Риск компрометации контроллера (доступ ко всем узлам) | Риск «дрейфа» при недоступности сервера управления |
| **Борьба с дрифтом** | Требует ручного или запланированного запуска | Встроена в цикл работы агента (каждые N минут) |

## Практические сценарии

### Сценарий 1: Оперативное исправление уязвимостей (Push)
**Задача:** Срочно обновить критический пакет на 500 серверах в ответ на Zero-day уязвимость.
**Решение:** Использование Ansible. Контроллер немедленно инициирует сессии на всех узлах.
**Преимущество:** Полный контроль над временем начала и завершения операции («Здесь и сейчас»).

### Сценарий 2: Поддержание долгосрочного соответствия (Pull)
**Задача:** Гарантировать, что конфигурация веб-серверов на 5000 узлах соответствует корпоративному стандарту безопасности (Compliance).
**Решение:** Использование Puppet. Агенты на узлах каждые 30 минут сверяют локальное состояние с эталоном. Любая ручная правка системного администратора будет автоматически отменена.
**Преимущество:** Автоматическое подавление **дрейфа конфигурации (Configuration Drift)**.

### Сценарий 3: Динамические облачные среды (GitOps/Pull)
**Задача:** Автоматическая настройка новых экземпляров приложения при срабатывании Auto-scaling.
**Решение:** Использование ArgoCD. Новые поды в Kubernetes при появлении сами регистрируются и подтягивают актуальные манифесты из Git.
**Преимущество:** Нет необходимости настраивать доступы от CI-системы внутрь кластера.

## Дополнительная информация

### Безопасность и сетевая топология
*   **Push-безопасность:** Основная проблема — хранение приватных ключей SSH на Control Node. Рекомендуется использовать SSH-агенты и системы JIT-доступа (Just-in-Time). При компрометации контроллера злоумышленник получает доступ ко всей инфраструктуре (Lateral Movement).
*   **Pull-безопасность:** Безопасность строится на взаимной TLS-аутентификации (mTLS). Агент должен иметь сертификат, подписанный доверенным CA (Certificate Authority).

### Гибридные подходы
В современных enterprise-инфраструктурах часто используют обе модели:
1.  **Ansible (Push)** используется для **Bootstrap** (начальной настройки) системы: создание пользователей, настройка сети и установка агента (Puppet/Salt).
2.  **Pull-агент** берет на себя долгосрочное управление и соблюдение политик безопасности.
3.  **SaltStack** предлагает уникальный баланс: постоянные агенты (Pull) связаны с мастером через шину событий (ZeroMQ), что позволяет мастеру мгновенно «проталкивать» команды (Push-over-Pull).
