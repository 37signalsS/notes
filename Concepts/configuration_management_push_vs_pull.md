# Модели доставки конфигурации: Push vs. Pull

## Определения

**Push-** и **Pull-модели** — это два основных способа, которыми системы управления конфигурацией доставляют желаемое состояние на управляемые узлы. Выбор модели влияет на архитектуру, сетевые требования и скорость реакции системы.

Для понимания более широкого контекста рекомендуется ознакомиться с [общими моделями управления конфигурацией](./configuration_management_models.md).

## Основные концепции

### Push-модель

Центральный сервер (контроллер) инициирует соединение с управляемыми узлами (обычно по SSH или WinRM) и принудительно применяет к ним изменения. Узлы пассивны и не знают о своем состоянии до момента "проталкивания" конфигурации.

* **Примеры инструментов:** Ansible, SaltStack (в master-push режиме), Fabric.
* **Как это работает:** `Контроллер → Узел`

### Pull-модель

На каждом управляемом узле работает агент, который через регулярные интервалы времени обращается к центральному серверу (master), запрашивает свою конфигурацию, сравнивает ее с текущим состоянием и, при необходимости, вносит изменения.

* **Примеры инструментов:** Puppet, Chef, CFEngine, SaltStack (в режиме с minion).
* **Как это работает:** `Агент на узле → Сервер`

### Сравнительная таблица

| Критерий | Push-модель | Pull-модель |
| :--- | :--- | :--- |
| **Инициатор** | **Контроллер** | **Агент** на узле |
| **Скорость реакции** | **Немедленная**, по команде | **Отложенная**, по расписанию агента (например, раз в 30 мин) |
| **Сетевые требования**| Контроллер должен иметь доступ к узлам (исходящие соединения) | Узлы должны иметь доступ к серверу (исходящие соединения) |
| **Масштабируемость**| Ограничена производительностью контроллера | Высокая, нагрузка распределена по агентам |
| **Коррекция дрейфа**| Только в момент запуска | **Постоянная**, при каждом запуске агента |
| **Требования к узлу**| Минимальные (часто только SSH) | Требуется установка и настройка **агента** |
| **Безопасность** | Ключи SSH/пароли хранятся на контроллере | Обычно используется PKI с сертификатами для каждого агента |

## Практические сценарии

### Сценарий 1: Push с помощью Ansible

**Задача:** Срочно установить пакет `htop` на все веб-серверы.

```bash
# Команда запускается с управляющего узла
ansible webservers -m apt -a "name=htop state=present" --become
```

* **Результат:** Команда немедленно выполняется на всех целевых серверах. Идеально для быстрых, точечных задач и оркестрации.

### Сценарий 2: Pull с помощью Puppet

**Задача:** Гарантировать, что на всех серверах установлен и работает сервис `ntpd` для синхронизации времени.

**Манифест на Puppet-сервере (`site.pp`):**

```puppet
node default {
  package { 'ntp':
    ensure => installed,
  }
  service { 'ntpd':
    ensure  => running,
    enable  => true,
    require => Package['ntp'],
  }
}
```

* **Результат:** Каждый агент на узлах в течение своего цикла опроса (например, 30 минут) проверит наличие пакета и состояние сервиса и исправит любые отклонения. Идеально для поддержания гомогенности и соответствия стандартам (compliance).

### Выбор стратегии

* **Push** подходит для:
  * Оркестрации многошаговых развертываний.
  * Быстрых, одноразовых команд и экстренных исправлений.
  * Начальной загрузки (bootstrap) серверов.
* **Pull** подходит для:
  * Управления большим и гетерогенным парком машин.
  * Обеспечения постоянной конвергенции и борьбы с дрейфом конфигурации.
  * Сред с высокими требованиями к аудиту и безопасности.

## Дополнительная информация

### Гибридные подходы

На практике часто используются гибридные модели. Например, Ansible (Push) может использоваться для начальной настройки сервера и установки на него агента Puppet (Pull), который затем берет на себя дальнейшее управление.

Системы вроде SaltStack поддерживают оба режима, а также событийную шину, которая позволяет "проталкивать" команды агентам, уже установившим соединение, совмещая скорость Push и масштабируемость Pull.
