# Pull vs Push: различия и практические примеры

В управлении конфигурацией ключевое архитектурное решение — как доставлять желаемое состояние на узлы. Две базовые модели — Push и Pull — различаются инициатором соединения, сетевыми требованиями, скоростью распространения изменений и операционными рисками. Понимание этих различий помогает подобрать инструменты и спроектировать надежный процесс внесения изменений.

## Концепции

-   **Push-модель**
    Контроллер (оркестратор) инициирует соединение к целевым хостам и принудительно применяет конфигурацию. Часто используется безагентный доступ по SSH/WinRM. Примеры: Ansible по SSH, Salt в режиме прямой оркестрации.

-   **Pull-модель**
    На каждом хосте работает агент, который периодически запрашивает и применяет конфигурацию с центрального сервера. Примеры: Puppet, Chef, CFEngine. Агент также выполняет дрейф-коррекцию по расписанию.

## Сравнение по ключевым критериям

| Критерий | Push | Pull |
| :--- | :--- | :--- |
| **Инициатор** | Оркестратор | Агент на узле |
| **Сеть/Фаервол** | Исходящие из оркестратора к хостам | Исходящие из узлов к серверу |
| **Масштабирование** | Ограничено параллельностью контроллера | Горизонтально, нагрузка распределена |
| **Скорость доставки** | Немедленно, по команде | Периодически, по интервалу агента |
| **Устойчивость к временным сбоям** | Требует доступности узла в момент операции | Узел подтянет изменения при восстановлении связи |
| **Дрейф-конвергенция** | Обычно одноразовый прогон | Регулярная самоисправляющаяся конвергенция |
| **Аудит и история** | Логи оркестратора | Централизованные отчеты агентов |
| **Безопасность** | Доступ к множеству хостов, управление ключами SSH | PKI/сертификаты, доверенные каналы с сервером |
| **Онбординг новых узлов** | Инвентарь/доступ сразу | Автоматический при регистрации агента |

## Практические примеры

### Push с Ansible
Сценарий: срочная конфигурация ограниченного набора веб-серверов.

Инвентарь:
```ini
[web]
web1.example.com
web2.example.com
```

Простой playbook:
```yaml
- hosts: web
  become: yes
  tasks:
  - name: Установить NGINX
    apt:
      name: nginx
      state: present
      update_cache: yes
```

Запуск с таргетингом:
```bash
ansible-playbook -i hosts site.yml --limit web
```
**Преимущества**: немедленное применение, отсутствие агентов, хорошо для одноразовых изменений и аварийных операций.

### Pull с Puppet
Сценарий: постоянная конвергенция конфигурации на парке из сотен/тысяч узлов.

Манифест:
```puppet
package { 'nginx':
  ensure => installed,
}

service { 'nginx':
  ensure  => running,
  enable  => true,
  require => Package['nginx'],
}
```

Агент по умолчанию связывается с сервером раз в 30 минут и применяет изменения. Принудительный прогон:
```bash
puppet agent -t
```
**Преимущества**: регулярное исправление дрейфа, предсказуемая нагрузка, удобный аудит.

## Выбор стратегии

### Когда предпочтителен Push:
-   Разовые и срочные изменения, точечные операции.
-   Среды без постоянных агентов или с жесткими требованиями к базовому образу.
-   Начальный бутстрап узла до установки агента.

### Когда предпочтителен Pull:
-   Большие распределенные кластеры с требованием к автоконвергенции.
-   Нестабильные сети и отдаленные площадки.
-   Строгие стандарты аудита и комплаенса.

## Гибридные подходы

Комбинированные схемы встречаются часто: оркестратор в режиме Push выполняет первоначальную подготовку и регистрацию, после чего узел переходит на Pull-конвергенцию. Некоторые системы (например, Salt) поддерживают событийную шину: агент держит исходящее соединение, а управляющие команды доставляются в почти реальном времени, совмещая оперативность с преимуществами агентной модели. В платформенных сценариях GitOps агенты выполняют непрерывную синхронизацию состояния, что логически близко к Pull-подходу.
