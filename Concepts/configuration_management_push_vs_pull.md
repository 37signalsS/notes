# Модели доставки конфигурации: Push vs Pull

## Определения

**Push-** и **Pull-модели** — два основных способа доставки желаемого состояния на управляемые узлы системами управления конфигурацией (Configuration Management, далее — CM). Выбор модели влияет на архитектуру, сетевые требования и скорость реакции системы.

Более широкий контекст: [модели управления конфигурацией](./configuration_management_models.md), [инструменты управления конфигурацией](./configuration_management_tools.md).

## Базовые концепции

### Push-модель (Проталкивание)

Центральный сервер (контроллер) инициирует соединение с управляемыми узлами (обычно по SSH (Secure Shell) или WinRM (Windows Remote Management)) и принудительно применяет изменения. Узлы пассивны и не знают о своем состоянии до момента «проталкивания» конфигурации.

* **Примеры инструментов:** Ansible, SaltStack (в режиме master-push), Fabric.
* **Принцип работы:** `Контроллер → Узел`.

### Pull-модель (Вытягивание)

На каждом управляемом узле работает агент, который через регулярные интервалы обращается к центральному серверу (master), запрашивает конфигурацию, сравнивает с текущим состоянием и при необходимости вносит изменения.

* **Примеры инструментов:** Puppet, Chef, CFEngine, SaltStack (в режиме с агентом-миньоном).
* **Принцип работы:** `Агент на узле → Сервер`.

### Сравнительная характеристика

| Критерий | Push-модель | Pull-модель |
| :--- | :--- | :--- |
| **Инициатор** | **Контроллер** | **Агент** на узле |
| **Скорость реакции** | **Немедленная**, по команде | **Отложенная**, по расписанию агента (например, раз в 30 мин) |
| **Сетевые требования** | Контроллер должен иметь доступ к узлам (исходящие соединения) | Узлы должны иметь доступ к серверу (исходящие соединения) |
| **Масштабируемость** | Ограничена производительностью контроллера | Высокая, нагрузка распределена по агентам |
| **Коррекция дрейфа** | Только в момент ручного или планового запуска | **Постоянная**, при каждом автоматическом цикле агента |
| **Требования к узлу** | Минимальные (часто только SSH) | Требуется установка и настройка **агента** |
| **Безопасность** | Ключи SSH/пароли хранятся на контроллере | Обычно используется PKI (Public Key Infrastructure) с сертификатами |

## Практические сценарии

### Сценарий 1: Push с помощью Ansible

**Задача:** Срочно установить пакет `htop` на все веб-серверы.

```bash
# Команда запускается с управляющего узла
ansible webservers -m apt -a "name=htop state=present" --become
```

**Результат:** Команда немедленно выполняется на всех целевых серверах. Идеально для быстрых точечных задач и оркестрации.

### Сценарий 2: Pull с помощью Puppet

**Задача:** Гарантировать, что на всех серверах установлен и работает сервис `ntpd` для синхронизации времени.

**Манифест на Puppet-сервере (`site.pp`):**

```puppet
node default {
  package { 'ntp':
    ensure => installed,
  }
  service { 'ntpd':
    ensure  => running,
    enable  => true,
    require => Package['ntp'],
  }
}
```

**Результат:** Каждый агент на узлах в течение своего цикла опроса (например, 30 минут) проверит наличие пакета и состояние сервиса и исправит любые отклонения (**дрейф конфигурации**, configuration drift). Идеально для поддержания однородности и соответствия стандартам (compliance).

### Выбор стратегии

* **Push** подходит для:
  * оркестрации многошаговых развертываний;
  * быстрых одноразовых команд и экстренных исправлений;
  * начальной загрузки (bootstrap) серверов.
* **Pull** подходит для:
  * управления большим и гетерогенным парком машин;
  * обеспечения постоянной конвергенции и борьбы с дрейфом конфигурации;
  * сред с высокими требованиями к аудиту и безопасности.

## Дополнительная информация

### Гибридные подходы

На практике часто используются гибридные модели. Например, Ansible (Push) может использоваться для начальной настройки сервера и установки на него агента Puppet (Pull), который затем берет на себя дальнейшее управление.

Системы вроде SaltStack поддерживают оба режима, а также событийную шину, которая позволяет «проталкивать» команды агентам, уже установившим соединение, совмещая скорость Push и масштабируемость Pull.
