# Трассировки: детали

## Определения

**Распределённая трассировка (Distributed Tracing)** — метод отслеживания полного пути выполнения запроса через все компоненты распределённой системы. Визуализируется в виде каскадной диаграммы (диаграммы Ганта), показывающей временные и причинно-следственные связи между операциями.

**Назначение:**

- Выявление узких мест (bottlenecks) в распределённых системах.
- Анализ каскадных задержек и ошибок.
- Понимание зависимостей между микросервисами.
- Обогащение контекста при отладке сложных инцидентов.

**Ключевой принцип Observability:** Трассировки позволяют ответить на вопрос «Где именно возникла проблема?» в цепочке вызовов, дополняя метрики («Что сломалось?») и логи («Что именно случилось?»).

**См. также:** [Четыре столпа Observability](./four_pillars_of_observability.md) — фундаментальные концепции наблюдаемости.

## Базовые концепции

### Основные компоненты

| Компонент | Описание | Пример |
| :--- | :--- | :--- |
| **Trace (Трейс)** | Весь путь одного запроса через систему. Уникально идентифицируется `TraceID`. | Запрос «Оформить заказ» |
| **Span (Спан)** | Единица работы внутри трейса (логическая операция). Имеет `SpanID`, `TraceID`, имя, время начала/окончания, атрибуты и события. | HTTP-вызов, SQL-запрос, чтение из кэша |
| **Trace Context** | Метаданные, передаваемые между сервисами для связки спанов. | Заголовок `traceparent` (W3C Trace Context) |

### Передача контекста (Propagation)

Для сквозного отслеживания используется механизм передачи контекста (Propagation).

**Протоколы и стандарты:**

- **W3C Trace Context:** современный индустриальный стандарт (заголовок `traceparent`). Рекомендуется к использованию.
- **B3 (Zipkin):** исторический стандарт (`X-B3-TraceId`).
- **Jaeger:** заголовок `uber-trace-id`.

**Протокол передачи данных:** в современной инфраструктуре стандартом де-факто является **OTLP** (OpenTelemetry Line Protocol), работающий поверх gRPC или HTTP.

### Сэмплирование (Sampling)

Сбор 100% трассировок в высоконагруженных системах приводит к чрезмерным затратам на хранение и передачу данных.

**Типы архитектур сэмплирования:**

1.  **Head-based Sampling:** Решение о записи принимается в начале пути (entry point).
    - **Плюсы:** Минимальный трафик, простота.
    - **Минусы:** Может пропустить редкие ошибки или аномалии.
2.  **Tail-based Sampling:** Решение принимается после завершения всего трейса (обычно на уровне OTel Collector).
    - **Плюсы:** Позволяет сохранить 100% ошибок и медленных запросов, отбросив «здоровые» данные.
    - **Минусы:** Требует буферизации всех спанов до завершения трейса, сложнее в масштабировании.

**Стратегии:** вероятностная (Probabilistic), по количеству запросов (Rate Limiting), адаптивная.

### Корреляция сигналов

**Трассировки бесполезны в изоляции.** Максимальная ценность достигается при связке:

- **Trace → Logs:** поиск логов по `trace_id`.
- **Metrics → Trace:** переход от аномалии на графике (exemplars) к конкретному трейсу.
- **Trace → Profile:** анализ загрузки CPU конкретным спаном через профилирование.

## Практические сценарии

### Сценарий 1: Диагностика Long Tail Latency (p99)

**Задача:** Понять, почему 1% запросов обрабатывается более 5 секунд.

**Действия:**

1.  В Grafana Tempo выполнить поиск по TraceQL: `{.duration > 5s}`.
2.  Выбрать трейс и изучить "Critical Path" (цепочку спанов, формирующую общую задержку).
3.  Найти спан с максимальной задержкой. Например, `db.postgresql.query`.
4.  Проверить атрибуты спана: `db.statement` (текст запроса) и `db.wait_time`.

### Сценарий 2: Анализ каскадных отказов

**Задача:** Найти первопричину ошибки, если упало 5 связанных сервисов.

**Действия:**

1.  Найти трейс с ошибкой: `{.status_code == error}`.
2.  Найти самый верхний спан в иерархии, имеющий статус ошибки.
3.  Изучить раздел `Events` (события) или `Logs` внутри спана — там часто содержится stack trace или сообщение об исключении.
4.  Проверить атрибуты соседних спанов на предмет таймаутов (`http.status_code = 504`).

### Сценарий 3: Настройка Tail-sampling в OTel Collector

**Задача:** Сохранять 100% трейсов с ошибками и только 1% успешных.

**Пример конфигурации:**

```yaml
processors:
  tail_sampling:
    policies:
      - name: errors-policy
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: slow-policy
        type: latency
        latency: {threshold_ms: 2000}
      - name: probabilistic-policy
        type: probabilistic
        probabilistic: {sampling_percentage: 1}
```

## Дополнительная информация

### Инструментарий

| Инструмент | Роль | Особенности |
| :--- | :--- | :--- |
| **Grafana Tempo** | Хранилище | Хранит данные в объектном хранилище (S3), поддерживает TraceQL. |
| **Jaeger** | Бэкенд + UI | Классическое решение, удобный поиск, встроенный UI. |
| **OpenTelemetry** | SDK + Collector | Единый стандарт сбора и передачи данных. |

### Язык запросов TraceQL (Tempo)

| Запрос | Описание |
| :--- | :--- |
| `{.duration > 1s}` | Трейсы дольше 1 сек |
| `{status = error}` | Все трейсы с ошибками |
| `{span.http.method = "POST"}` | Трейсы с POST-запросами |
| `{resource.service.name = "auth-svc"}` | Фильтр по конкретному сервису |

### Лучшие практики

1.  **Семантические конвенции:** Следуйте [OpenTelemetry Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/) при именовании атрибутов (например, `http.status_code` вместо `status`).
2.  **Сквозной Context Propagation:** Убедитесь, что `traceparent` передаётся во всех заголовках, включая асинхронные очереди (Kafka, RabbitMQ).
3.  **Автоматическое инструментирование:** Используйте OTel Java Agent или Python Auto-instrumentation для быстрого старта, но переходите на ручное для бизнес-критичных операций.
4.  **Сэмплирование:** Настраивайте Tail-sampling на уровне коллектора для высоконагруженных систем.
