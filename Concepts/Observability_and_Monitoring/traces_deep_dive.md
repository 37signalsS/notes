# Трассировки: глубокое погружение

**Актуально для:** OpenTelemetry Collector Contrib 0.162.x, OpenTelemetry Semantic Conventions 1.44.x, Jaeger 2.21.x, Grafana Tempo 3.0.x

## Определения

**Распределённая трассировка (Distributed Tracing)** — метод отслеживания полного пути выполнения запроса через все компоненты распределённой системы. В отличие от логов, фиксирующих атомарные события, трассировка фокусируется на связях (причинно-следственных и временных) между этими событиями. Визуализируется в виде каскадной диаграммы (диаграммы Ганта), иллюстрирующей жизненный цикл запроса.

**Spanset (набор спанов)** — результат фильтрации TraceQL: подмножество спанов одного трейса, удовлетворяющих условию. Именно spanset, а не отдельный спан, является единицей работы структурных операторов TraceQL.

**Critical Path (критический путь)** — последовательность спанов, суммарная длительность которых определяет длительность трейса. Оптимизация спанов вне критического пути не изменяет время ответа пользователю.

**Tail-based sampling (сэмплирование на выходе)** — стратегия, при которой решение о сохранении трейса принимается после того, как все его спаны собраны (в Collector), а не в точке входа. Позволяет сохранять 100% ошибок при 1% сэмплировании «здорового» трафика.

**Zero-code instrumentation (инструментация без изменения кода)** — получение трассировочных данных без модификации приложения: через протокольный уровень (eBPF) либо через автоинструментацию на уровне библиотек (Java/Python/.NET-агенты).

**Назначение:**

- Выявление узких мест (bottlenecks) в распределённых микросервисных архитектурах.
- Анализ каскадных задержек (Long Tail Latency) и сложных отказов.
- Визуализация динамических зависимостей между сервисами и инфраструктурой.
- Реализация **Observability 2.0** — переход от простого сбора данных к контекстуальному анализу всей системы через сквозные идентификаторы.

**Ключевой принцип Observability:** Трассировки позволяют ответить на вопрос «Где именно?» (на каком этапе цепочки) возникла проблема, дополняя метрики («Что именно сломалось / сколько ошибок?») и логи («Что произошло внутри конкретного шага?»).

**См. также:** [Четыре столпа Observability](./four_pillars_of_observability.md) — фундаментальные концепции наблюдаемости.

## Базовые концепции

### Анатомия трассировки (модель данных OpenTelemetry)

| Компонент | Описание | Пример / Техническая деталь |
| :--- | :--- | :--- |
| **Trace (Трассировка)** | Набор спанов, представляющих единый путь запроса. Имеет уникальный `trace_id` (16 байт, 32 hex-символа). | Транзакция «Оформить заказ». |
| **Span (Спан)** | Единица работы (HTTP-вызов, SQL-запрос, выполнение функции). Имеет `span_id` (8 байт, 16 hex-символов), время начала и завершения. | `POST /v1/billing/charge` |
| **Span Kind** | Тип спана, определяющий его роль в распределенной системе. | `Server`, `Client`, `Producer`, `Consumer`, `Internal`. |
| **Status** | Статус спана: `Unset`, `Ok`, `Error`. Управляет поведением политик `status_code` в tail sampling. | `Error` при `HTTP 500`. |
| **Attributes (Атрибуты)** | Метаданные спана (ключ=значение). Обязательны для фильтрации и аналитики. | `http.response.status_code=500`, `db.system.name=postgresql`. |
| **Events (События)** | Временные метки внутри спана для фиксации атомарных действий или ошибок. | `exception` c `exception.stacktrace`. |
| **Span Links (Связи)** | Механизм соединения независимых трейсов. Критичен для асинхронности (Kafka, Batch). | Связь между `producer-trace` и `consumer-trace`. |
| **Resource attributes** | Атрибуты уровня ресурса — общие для всех спанов процесса. | `service.name`, `service.instance.id`, `k8s.pod.name`. |

**Resource против Span.** Атрибуты уровня `resource` описывают сущность, породившую спаны (сервис, под, хост), и не меняются в течение жизни процесса. Атрибуты уровня `span` описывают конкретную операцию. Это разделение определяет не только экономию памяти, но и корректность запросов: в TraceQL `span.foo` ищет только в атрибутах спана, `resource.foo` — только в атрибутах ресурса, а `.foo` — в обоих. Явное указание scope даёт существенный выигрыш в производительности поиска.

### Типы спанов (Span Kind)

Правильная типизация спанов критична для построения корректной топологии сервисов:
- **Server:** Спан на стороне приемника синхронного запроса (например, входящий HTTP в API).
- **Client:** Спан на стороне отправителя синхронного запроса (например, вызов внешней БД или API).
- **Producer:** Спан отправки сообщения в асинхронную очередь (Kafka, RabbitMQ).
- **Consumer:** Спан получения и обработки сообщения из очереди.
- **Internal:** Внутренняя операция процесса (вызов тяжелой функции, вычисления).

### Семантические конвенции и версии атрибутов

Имена атрибутов регулируются [OpenTelemetry Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/). Стабилизация конвенций HTTP и БД привела к **переименованию** атрибутов, и это главный источник «сломанных» запросов в TraceQL и правил в Grafana.

| Устаревшее имя (deprecated) | Стабильное имя | Область |
| :--- | :--- | :--- |
| `http.method` | `http.request.method` | HTTP |
| `http.status_code` | `http.response.status_code` | HTTP |
| `http.url` | `url.full` (частично) / `url.path` + `url.query` | HTTP |
| `http.flavor` | `network.protocol.version` | HTTP |
| `net.peer.name` | `server.address` | Network |
| `net.peer.port` | `server.port` | Network |
| `db.system` | `db.system.name` | БД |
| `db.statement` | `db.query.text` | БД |
| `db.name` | `db.namespace` | БД |
| `db.sql.table` | `db.collection.name` | БД |
| `db.operation` | `db.operation.name` | БД |
| `messaging.destination` | `messaging.destination.name` | Messaging |

**Механизм миграции.** Инструментация не переключается на новые имена одномоментно. Переход выполняется через переменную окружения `OTEL_SEMCONV_STABILITY_OPT_IN`:

```bash
# Только стабильные (новые) конвенции — старая параллельно не выдаётся
OTEL_SEMCONV_STABILITY_OPT_IN=http

# Обе конвенции одновременно — переходный период, помогает искать и старые, и новые спаны
OTEL_SEMCONV_STABILITY_OPT_IN=http/dup
```

Значение `http/dup` имеет приоритет над `http`, если присутствуют оба. Миграцию выполняют в два шага: сначала включают `http/dup` и убеждаются, что дашборды и запросы работают с обоими наборами имён, затем переключают на `http` и удаляют обращения к устаревшим именам.

> **Важно для SRE:** пока включён `http/dup`, в трейсах одновременно присутствуют оба набора атрибутов. Это удваивает количество уникальных ключей атрибутов и увеличивает объём пайплайна. Следите за фактическим объёмом телеметрии и снимайте `dup` после завершения миграции.

**Атрибуты, которых нет в конвенциях.** Время ожидания соединения из пула, время ожидания блокировки, имя хоста БД — стандартизованных атрибутов для них нет. Инструментация может добавлять их в собственном пространстве имён (например, `db.client.connection.pool.name`, `db.client.connection.state` — оба в статусе Development). Рассчитывать на них в запросах и дашбордах можно только если конкретная библиотека инструментации их действительно выдаёт; проверяйте на реальных трейсах, а не по документации.

### Распространение контекста (Context Propagation)

Процесс передачи `trace_id` и `span_id` между службами через заголовки протоколов. Без этого невозможно восстановить дерево вызовов.

**W3C Trace Context** — отраслевой стандарт. Заголовок `traceparent` состоит из четырёх полей `version-traceid-parentid-flags`:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^  ^^
             |            trace_id (32 hex)          parent_id (16 hex)    флаги
             версия (00)
```

Дополнительно используется заголовок `tracestate` — список `key=value` от вендоров для передачи vendor-specific данных, критичный для корректной работы probability sampling (поля `ot=rv:...;th:...`).

**Baggage** — механизм передачи пользовательских метаданных (например, `customer_tier=gold`) через всю цепочку вызовов без обращений к БД в каждом сервисе. Спецификация W3C Baggage (CR от 30 мая 2024) задаёт два предела, которые платформа **обязана** соблюдать при распространении:

| Параметр | Значение | Смысл |
| :--- | :--- | :--- |
| Максимум `list-member` | **180** | `baggage-string = list-member 0*179( OWS "," OWS list-member )` |
| Максимальный размер | **8192 байт** | При превышении платформа `MAY` отбрасывать элементы |

Лимиты — это **минимум** требований к соответствию: реализация вправе определить и более высокие пределы, а `SHOULD` распространять максимально возможный объём. Если лимит превышен, элементы отбрасываются целиком — частичный `list-member` передавать запрещено. Лимит применяется к сумме всех заголовков `baggage`, а не к каждому по отдельности.

**Риск безопасности:** Baggage пересекает границы доверия. Спецификация требует, чтобы владельцы приложений либо не помещали конфиденциальные данные в `baggage`, либо гарантировали отсутствие заголовка в запросах, пересекающих границы доверия. На практике это означает: не кладите в baggage секреты, токены и PII; значения percent-encoder'ятся, но это не шифрование.

### Архитектура сбора трассировок

```text
Приложение (SDK / eBPF) → Агент (OTel Collector) → Транспорт (Kafka) → Обработка → Хранилище (Tempo / ClickHouse)
```

**Backpressure и сброс данных:**

При переполнении буферов агента или коллектора (всплеск трафика, медленная запись в БД, недоступность бэкенда) спаны начинают отбрасываться, и это наблюдаемо на нескольких уровнях:

- **На уровне SDK:** поведение задаётся экспортёром. Синхронный (блокирующий) экспортёр добавляет латентность к самому запросу приложения и не применяется в production.
- **На уровне `memory_limiter`:** процессор отслеживает потребление памяти и переходит в *memory limited mode*, начиная **отказывать** (refuse) данным вместо их отбрасывания, и форсируя GC. Ошибка возвращается предыдущему компоненту пайплайна; корректно реализованный receiver обязан повторить отправку, поэтому `refused` — это сигнал о давлении, а не о безвозвратной потере.
- **На уровне очереди отправки exporter:** при переполнении `sending_queue` данные отбрасываются окончательно. Collector пишет в лог сообщение вида `Dropping data because sending_queue is full`.
- **На уровне tail sampling:** используется кольцевой буфер ограниченного размера (`num_traces`). Если трейс не успел собраться за `decision_wait`, он вытесняется и теряется.

Ключевая метрика для каждого уровня приведена в [сценарии 6](#сценарий-6-мета-мониторинг-пайплайна-трассировок).

### Сэмплирование (Sampling)

В высоконагруженных системах запись 100% данных невозможна из-за затрат на IO и хранение.

**Head-based** — решение принимается в точке входа, в SDK приложения, до того как известен результат выполнения:

- **Probabilistic:** детерминированный отбор по хешу `trace_id` с порогом. Решение согласовано между сервисами, трайс не «рвётся».
- **ParentBased:** обёртка, уважающая решение родителя. `ParentBased(TraceIdRatioBased(0.1))` означает: корень решает 10%, а дочерние сервисы наследуют. Это стандартное поведение — решение об отказе на любом уровне должно распространяться вниз, иначе трейс получится фрагментированным.
- **Rate Limiting:** ограничение количества трейсов в секунду (в SDK реализован через Jaeger Remote Sampler с хранилищем правил).

**Tail-based** — решение принимается после того, как весь трейс собран. Требует, чтобы все спаны одного трейса попали в один экземпляр Collector. Подробно разобрано в [OpenTelemetry: продвинутое сэмплирование](../../OpenTelemetry/advanced_sampling.md); здесь — принципы выбора.

| Свойство | Head-based (SDK) | Tail-based (Collector) |
| :--- | :--- | :--- |
| Где принимается решение | В приложении до обработки | В Collector после сборки трейса |
| Видит результат | Нет | Да: статус спана, фактическая длительность |
| Сохраняет 100% ошибок | Нет (сэмплирование слепо) | Да |
| Согласованность | Трейс либо целиком сохранён, либо целиком отброшен | Трейс целиком сохранён, либо отброшен |
| Требования к инфраструктуре | Нет | Все спаны трейса на одном инстансе; RAM на буфер |
| Что теряется при отказе | Ошибки и медленные запросы теряются вместе со всем остальным | Только «здоровый» трафик |

**Рекомендуемая схема** для сервисов с заметной долей ошибок: head-based сэмплирование с умеренным порогом (1–10%) в SDK плюс tail-based в Collector. Head-based снижает поток, попадающий в сеть и в RAM Collector; tail-based «вытягивает» из оставшегося потока все ошибки и медленные запросы. Одних только head-based недостаточно — они по определению не видят результат.

**Adaptive sampling** — автоматическая регулировка порога под текущую нагрузку. Существует в двух независимых реализациях, которые не следует смешивать:

- Jaeger `remote_sampling` extension — серверная часть, правила хранятся централизованно, решение отдаётся SDK по gRPC. Требует, чтобы все SDK были сконфигурированы на `Remote`-сэмплер. В Jaeger v2 это встроенный компонент с типом `remote_sampling`; в collector-contrib его аналог — отдельный компонент `jaegerremotesampling` (тип `remotesampling`).
- Collector-contrib `probabilistic_sampler` processor — регулирует процент локально, на основе собственной частоты трафика.

### Инструментация: eBPF vs SDK

| Характеристика | OpenTelemetry SDK / языковые агенты | eBPF (OpenTelemetry eBPF Instrumentation, OBI) |
| :--- | :--- | :--- |
| **Сложность внедрения** | Низкая для агентов (без изменения кода), высокая для ручной разметки | Нулевая (zero-code) |
| **Уровень перехвата** | Библиотечный | Протокольный + сетевой стек ядра |
| **Детализация** | Максимальная (внутренние бизнес-события) | Средняя (HTTP/HTTPS, gRPC, SQL, Redis, MongoDB, Kafka, MQTT) |
| **Производительность** | Нагрузка на рантайм приложения | Нагрузка на ядро ОС и минимальный рантайм-оверхед |
| **Видимость TLS** | Нативная (внутри процесса) | Частичная; требует функций в OpenSSL или модулей Go TLS |
| **Языки** | Ограничены наличием официального SDK/агента | Любые скомпилированные в бинарник (Go, Rust, C++) |
| **Требования к ОС** | Нет | Linux **5.8+** (рекомендуется 5.10+), BTF, расширенные capabilities |

**Статус OBI.** Проект OpenTelemetry eBPF Instrumentation (OBI) вырос из Grafana Beyla, переданного в OpenTelemetry в 2025 году. Актуальный модуль — `go.opentelemetry.io/obi`; релизы публикуются как `obi-v<version>-linux-amd64.tar.gz` и `obi-v<version>-linux-arm64.tar.gz`, образ — `ghcr.io/open-telemetry/opentelemetry-ebpf-instrumentation/ebpf-instrument:<version>`. Лицензия Apache-2.0.

**OBI не заменяет SDK.** Документация проекта формулирует это прямо: OBI даёт согласованную картину на уровне протоколов для любых языков, но для кастомных спанов и бизнес-контекста по-прежнему нужны языковые агенты или ручная инструментация. Практический вывод: OBI — способ начать наблюдаемость на существующем стеке без релизного цикла, а не повод демонтировать существующую SDK-инструментацию.

**Sysadmin: системные требования для eBPF-инструментации.** Проверяйте до развёртывания, а не после инцидента:

```bash
# Версия ядра: требуется 5.8+ (рекомендуется 5.10+)
uname -r

# BTF обязателен для CO-RE (Compile Once — Run Everywhere)
ls -l /sys/kernel/btf/vmlinux

# Включён ли BPF в текущем ядре (не во всех дистрибутивах)
sysctl kernel.unprivileged_bpf_disabled

# Лимиты, влияющие на число загружаемых программ и память BPF
sysctl kernel.perf_event_max_stack kernel.bpf_jit_enable
```

В Kubernetes eBPF-агент требует `hostPID: true`, `hostNetwork: true` и capabilities `SYS_ADMIN`, `SYS_RESOURCE`, `NET_ADMIN`, а также монтирования `/sys`, `/proc`, `/sys/kernel/debug` и `/sys/fs/bpf`. В контейнерных runtime с включённым seccomp загрузка проб может блокироваться — симптомом будут молчащие агенты при корректных правах.

**Sysadmin: лимиты процесса Collector.** Collector — обычный процесс Go; убедитесь, что системные лимиты не мешают ему удерживать буферы:

```bash
# Максимальный размер файла, доступный Collector (влияет на sending_queue с file_storage)
ulimit -n            # → дескрипторы: файловая очередь открывает файлы на диске
ulimit -c            # → дампы ядра при OOM-падении коллектора

# Проверка фактического потребления памяти процесса Collector
ps -o pid,rss,vsz,cmd -C otelcol-contrib
# → RSS в пределах 80–90% от limit_mib в memory_limiter — норма;
#   выход за пределы означает, что лимит задан неверно или упирается в cgroup
```

### Преимущества трассировки

1.  **Анализ критического пути (Critical Path Analysis):** Позволяет определить, какая именно часть цепочки вызовов напрямую влияет на итоговое время ответа. Оптимизация спанов вне критического пути не ускорит ответ пользователю.
2.  **Диагностика Long Tail Latency (p99):** Трассировка — единственный способ понять, почему 1% пользователей ждет ответа 10 секунд, когда среднее время (p50) составляет 100мс.
3.  **Zero-code Tracing (eBPF):** eBPF-инструментация позволяет получать трайсы из скомпилированных языков (Go, Rust, C++) без изменения кода и sidecar-контейнеров.
4.  **Trace-based Testing:** Использование трассировочных данных для автоматической проверки архитектурных инвариантов (например, «этот метод не должен делать более 2 запросов к БД»).
5.  **Верификация раскатки:** во время canary-развёртывания трейсы дают прямое доказательство, что новый инстанс обрабатывает запросы корректно, а не только «не упал» — проверяется структура вызовов и значения бизнес-атрибутов, а не только аптайм-метрика.

## Практические сценарии

### Сценарий 1: Диагностика задержек через TraceQL (Tempo 3.0)

**Задача:** Найти медленные запросы к PostgreSQL, где общая длительность трейса превышает 2 секунды.

**Синтаксис TraceQL, без которой не обойтись:**

- **Intrinsics** (встроенные поля) пишутся через двоеточие: `span:name`, `span:duration`, `span:status`, `span:kind`, `span:parentID`, `span:childCount`, `trace:id`, `trace:duration`, `trace:rootName`, `trace:rootService`, `event:name`, `event:timeSinceStart`, `link:spanID`, `link:traceID`, `instrumentation:name`. У scope `resource` нет intrinsics — только атрибуты. `trace:duration`, `trace:rootName` и `trace:rootService` одинаковы для всех спанов трейса и вычисляются дешевле, чем span-level аналоги, — при равном результате предпочитайте их.
- **Атрибуты** пишутся через точку с префиксом scope: `span.foo`, `resource.foo`, `event.foo`, `link.foo`, `instrumentation.foo`. Явный префикс — документированная нормальная форма: он позволяет Tempo сканировать только нужные данные, поэтому предпочитайте его неявным вариантам без префикса. Scope `trace` — исключение: у него нет атрибутов, только intrinsics.
- **Условия внутри одной пары `{}`** объединяются по AND и должны выполняться **на одном и том же спане**. Поэтому смешивать префиксы внутри `{}` можно и нужно: у спана есть и его собственные атрибуты, и атрибуты его resource — запрос `{ resource.service.name = "order-api" && trace:duration > 2s }` корректен. Пустой результат внутри одного `{}` получается, когда условия несовместимы для одного спана (например, `resource.cloud.region = "us-east-1" && resource.cloud.region = "us-west-1"` — у одного спана не может быть оба значения). Условия на **разных** спанах задаются отдельными spanset'ами и соединяются оператором: `{condA} && {condB}`.
- **Структурные операторы** связывают spanset'ы и **всегда возвращают спаны правой части**: `>>` — спаны `{condB}`, являющиеся потомками спана `{condA}` на любую глубину (descendant); `<<` — предки на любую глубину (ancestor); `>` — прямые потомки (child); `<` — непосредственные родители (parent); `~` — спаны, у которых есть сосед, удовлетворяющий `{condA}` (sibling). Логические операторы соединяют spanset'ы: `&&` требует совпадения обоих условий, `||` — это объединение (OR). «Объединённые» структурные варианты `&>>`, `&<<`, `&>`, `&<`, `&~` возвращают спаны, удовлетворяющие **обоим** условиям одновременно.

**Запрос:**

```traceql
{ resource.service.name = "order-api" && span.db.system.name = "postgresql" && duration > 500ms } >> { duration > 2s }
```

> **Внимание, ошибка в порядке операторов.** Направление структурного оператора задаёт направление обхода дерева. `A >> B` означает «спаны B, являющиеся потомками спанов A». Если поставить `duration > 2s` слева, запрос найдёт медленные спаны и их потомков, а не трейсы с медленными запросами к БД. Для задачи «найти трейсы, где ниже медленного запроса к БД есть спан дольше 2с» направление должно быть ровно таким, как в примере выше.

**Вариант, выражающий буквально «общая длительность трейса > 2s».** Условие выше находит трейсы, где длительный спан является потомком медленного запроса к БД, — это не то же самое, что длительность всего трейса. Для неё есть trace-level intrinsic `trace:duration` (`max(end) − min(start)` по спанам трейса); он одинаков для всех спанов трейса и, помимо прочего, вычисляется дешевле агрегаций:

```traceql
{ resource.service.name = "order-api" && span.db.system.name = "postgresql" && trace:duration > 2s }
```

> **Почему не агрегация.** Выражение вида `| max_over_time(duration) by (trace:id) > 2s` здесь не подходит по двум причинам: `duration` — span-level intrinsic, поэтому такая агрегация даёт максимум по **одному** спану, а не по трейсу; кроме того, `*_over_time` — функции TraceQL **metrics**-запросов, тогда как в обычном поисковом запросе доступны агрегаторы `count`, `avg`, `max`, `min`, `sum` (например, `avg(duration) > 20ms`).

**Действия:**

1. Выбрать трейс и изучить атрибуты спана: `db.query.text` (текст SQL-запроса) и `db.query.summary` (низкокардинальное резюме для группировки).
2. Разделить «медленно» на «долго выполнялся» и «долго ждал». Пул соединений: сравнить `db.client.connection.state` (Development) и `db.client.connection.pool.name` — если библиотека инструментации их выдаёт. Проверить `db.operation.batch.size` — батч из 5000 строк исполняется один спан, который выглядит медленным, хотя проблема в размере батча, а не в индексе.

> **Tempo 3.0: ломающее изменение.** Оптимизация AST в Tempo 3.0 изменила семантику `!=` и `!~` при работе с array-атрибутами: `!=` теперь означает `NOT IN` (ранее — «не содержит неравное»), `!~` — `MATCH NONE`. Запросы, написанные для Tempo 2.x, могут вернуть другой результат без ошибки. Перепроверьте все запросы с `!=` / `!~` по array-атрибутам при миграции.

### Сценарий 2: Анализ асинхронного сбоя в Kafka через Span Links

**Задача:** Найти причину, почему сообщение было отправлено, но не обработано.

**Механизм.** В асинхронной цепочке нет непрерывного дерева вызовов: консьюмер стартует новую операцию спустя произвольное время, часто в другом процессе. Связь строится через `Span Links` — ссылку от спана консьюмера на спан продюсера. Ключ для поиска — идентификаторы трейсов, записанные в заголовок сообщения: `traceparent` (или, если недоступен, собственные заголовки с `trace_id`/`span_id`).

**Действия:**

1. Найти трейс консьюмера (по `resource.service.name` и `span.kind = consumer`).
2. В UI перейти по ссылке в разделе **Links** связанного спана в трейс продюсера.
3. В трейсе консьюмера найти `Span Event` с именем `exception`, возникший при десериализации данных; проверить `exception.type` и `exception.stacktrace`.
4. Проверить, дошёл ли `messaging.message.id` в теле сообщения — без него трассировка очереди невозможна в принципе.

**Требование к инфраструктуре.** Пропускать контекст через брокер нужно явно: Kafka не является HTTP-транспортом, и propagator не срабатывает автоматически. Продюсер должен извлекать и инжектить заголовки в headers сообщения, консьюмер — извлекать их обратно. Без этого в трейс попадают изолированные фрагменты, и links остаются пустыми.

### Сценарий 3: Настройка Tail-sampling в OTel Collector

**Задача:** Сохранять все ошибки и запросы дольше 2 секунд, для остального — сэмплировать 1%.

**Конфигурация:**

```yaml
processors:
  tail_sampling:
    # Все спаны одного трейса должны попасть в один инстанс
    decision_wait: 10s
    num_traces: 100000
    expected_new_traces_per_sec: 2000
    policies:
      - name: errors-policy
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: slow-policy
        type: latency
        latency: {threshold_ms: 2000}
      - name: probabilistic-policy
        type: probabilistic
        probabilistic: {sampling_percentage: 1}
```

**Значения по умолчанию**, которые важно знать при отладке: `decision_wait` = **30s**, `num_traces` = **50000**, `expected_new_traces_per_sec` = **0**, `decision_cache.sampled_cache_size` = **0** (кэш выключен), `num_shards` = **1**. Значения из примера — осознанное отклонение от дефолта: `decision_wait` уменьшен, чтобы ускорить отдачу, `num_traces` увеличен, чтобы снизить вытеснение трейсов из кольцевого буфера.

**Процессор группировки.** `tail_sampling` выполняет группировку по `trace_id` самостоятельно, поэтому `groupbytrace` перед ним **не требуется**. Если он присутствует в конфигурации как наследие — он не вредит, но является лишним шагом.

**Политики, доступные в Collector 0.162.x** (выбор шире, чем три базовых):

| Тип | Что делает | Ключевой параметр |
| :--- | :--- | :--- |
| `always_sample` | Сохраняет всё | — |
| `status_code` | По статусу спана | `status_codes: [ERROR, UNSET, OK]` |
| `latency` | По длительности трейса | `threshold_ms`, `upper_threshold_ms` |
| `probabilistic` | Процент трейсов | `sampling_percentage`, `hash_salt` |
| `rate_limiting` | Спаны/сек через token bucket | `spans_per_second`, `burst_capacity` |
| `bytes_limiting` | Байты/сек через token bucket | `bytes_per_second`, `burst_capacity` |
| `string_attribute` | Значение атрибута (в т.ч. regex) | `key`, `values`, `enabled_regex_matching` |
| `numeric_attribute` | Числовой атрибут | `key`, `min_value`, `max_value` |
| `boolean_attribute` | Логический атрибут | `key`, `value` |
| `span_count` | Число спанов в трейсе | `min_spans`, `max_spans` |
| `trace_flags` | По установленному sampled-флагу | — |
| `trace_state` | По значению `tracestate` | `key`, `values` |
| `ottl_condition` | Произвольное условие OTTL | `span`, `spanevent`, `error_mode` |
| `and` / `not` / `drop` | Композиция | `and_sub_policy`, `not_sub_policy`, `drop_sub_policy` |
| `composite` | Квоты по политикам | `max_total_spans_per_second`, `policy_order`, `rate_allocation` |

**Механика решения.** Политика, проголосовавшая «drop», отменяет любое «sample» от других политик. Поэтому `errors-policy` в комбинации с `probabilistic-policy` даёт именно требуемое поведение: ошибка сохраняется всегда, «здоровое» — с вероятностью 1%. Обратный порядок в рассуждении даёт неверный вывод: «drop» важнее, чем «sample», а не наоборот.

> **Устарело: `invert_match`.** Решения `InvertSampled` / `InvertNotSampled` объявлены deprecated. Используйте политику `drop` для явного исключения и `not` для инверсии. Полностью отключить legacy-поведение можно feature gate `processor.tailsamplingprocessor.disableinvertdecisions`.

**Валидация:**

1. Вызвать ошибку в приложении (`curl` на эндпоинт, возвращающий 500). Убедиться, что трейс найден в хранилище, несмотря на 1% сэмплирования.
2. Вызвать искусственную задержку > 2с. Убедиться, что трейс сохранён.
3. Проверить фактическую долю сохранённых трейсов:

```promql
# Доля фактически сохранённых трейсов
otelcol_processor_tail_sampling_global_count_traces_sampled{sampled="true"}
  / otelcol_processor_tail_sampling_global_count_traces_sampled
# → 0.01 при 1% сэмплировании и отсутствии ошибок;
#   скачок выше означает, что ошибок больше, чем ожидалось
```

```promql
# Какая политика чаще всего голосует за сохранение
sum(otelcol_processor_tail_sampling_count_traces_sampled{decision="sampled"}) by (policy)
  / sum(otelcol_processor_tail_sampling_count_traces_sampled) by (policy)
# → наибольшую долю должен давать probabilistic-policy,
#   наименьшую — errors-policy при отсутствии ошибок
```

4. Проверить, что трейсы не вытесняются из буфера до решения:

```promql
rate(otelcol_processor_tail_sampling_sampling_trace_dropped_too_early[5m])
# → ненулевое значение = num_traces недостаточно;
#   увеличивайте num_traces либо уменьшайте decision_wait (оба растят RAM)
```

5. Проверить, не отстаёт ли принятие решений от таймера:

```promql
histogram_quantile(0.99, sum(rate(otelcol_processor_tail_sampling_sampling_decision_timer_latency_bucket[5m])) by (le))
# → p99 > 1s означает, что решения выходят за пределы decision_wait
#   и трейсы начинают вытесняться; сократите стоимость обработки в пайплайне
```

> **Имя метрики, важное для совместимости.** Реальное имя метрики — `otelcol_processor_tail_sampling_sampling_decision_timer_latency` (с `otelcol_` и с `timer` в названии). Встречающиеся в некоторых источниках варианты `processor_tail_sampling_sampling_decision_latency` и `..._decision_latency_count` не соответствуют ни одной существующей метрике Collector.

### Сценарий 4: Генерация метрик на основе спанов (Span-to-Metrics)

**Задача:** Создать метрики латентности и количества вызовов для конкретной SQL-операции без изменения кода приложения.

> **Компонент переименован и переведён в разряд connector.** `spanmetrics` существовал как *processor*. Сейчас это **connector**, и его тип переименован в `span_metrics` (snake_case по конвенции OpenTelemetry). Старое имя `spanmetrics` продолжает работать, но объявлено deprecated и будет удалено. Ниже используется актуальное имя. Пайплайн, кроме того, меняет структуру: connector объявляется в отдельной секции `connectors` и подключается к двум пайплайнам сразу.

**Конфигурация:**

```yaml
connectors:
  span_metrics:
    namespace: span.metrics
    # Атрибуты-разрезы: каждая комбинация значений создаёт свою временную серию
    dimensions:
      - name: db.system.name
      - name: db.operation.name
    histogram:
      explicit:
        buckets: [5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s, 2s, 5s]
    exemplars:
      enabled: true

exporters:
  prometheus:
    endpoint: 0.0.0.0:8889

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [span_metrics]        # ← connector как exporter пайплайна трасс
    metrics/span_metrics:
      receivers: [span_metrics]        # ← тот же connector как receiver
      processors: [memory_limiter, batch]
      exporters: [prometheus]
```

**Следствия, которые нужно учесть:**

- **Единицы измерения.** Единица метрики длительности зависит от feature gate `connector.spanmetrics.useSecondAsDefaultMetricsUnit` (секунды против миллисекунд) и попадает прямо в имя метрики. Сторону по умолчанию стоит проверить на своей версии Collector, а не считать по памяти: смотрите фактическое имя в `/metrics` и в Grafana.
- **Имена метрик.** Connector генерирует имена и атрибуты по модели OpenTelemetry и нормализует их под Prometheus; feature gate `connector.spanmetrics.legacyMetricNames` (выключен по умолчанию) возвращает legacy-имена.
- **Число resource scopes.** Connector создаёт столько metrics resource scopes, сколько их пришло в спанах, вместо одного общего. Это корректнее, но меняет объём и структуру данных в TSDB.
- **Кардинальность.** Каждая уникальная комбинация `service.name` + `span.name` + `span.kind` + значений `dimensions` создаёт отдельную серию. `dimensions` — главный источник взрыва кардинальности; подробности в [управлении кардинальностью](../../OpenTelemetry/cardinality_management.md).
- **Exemplars.** При `exemplars.enabled: true` спаны добавляются в точки метрик как exemplars и держатся только один интервал flush — это прямой путь от графика метрики к конкретному трейсу. При сбросе кэша следующая точка серии будет «разрывом», что при downstream-конвертации delta → cumulative может сбросить счётчик в ноль.

**Валидация:**

```bash
# Получить сгенерированные метрики и проверить наличие серий
curl -s http://localhost:8889/metrics | grep -E '^span_metrics_(calls|duration)' | head -20
# → span_metrics_calls{...db_system_name="postgresql",db_operation_name="SELECT"...}
#   и span_metrics_duration_bucket с заданными границами
```

> Имена атрибутов в метриках приходят нормализованными по Prometheus (`db.system.name` → `db_system_name`), а суффиксы `_total` и единиц измерения зависят от настроек экспортёра. Grep выше намеренно их не предполагает: он сработает и на `..._calls_total`, и на `..._calls`, и на `..._duration_milliseconds_bucket`.

### Сценарий 5: Tenant-aware Routing через Baggage

**Задача:** Пробросить идентификатор клиента (`tenant_id`) через 10 микросервисов для отладки конкретного пользователя без изменения сигнатур функций.

**Go** — baggage хранится в `context.Context`, а не в глобальном состоянии:

```go
package middleware

import (
    "context"
    "net/http"

    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/baggage"
    "go.opentelemetry.io/otel/propagation"
)

// TraceContextInject добавляет baggage на входе в систему
func TraceContextInject(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // Извлекаем входящий контекст (traceparent, tracestate, baggage)
        ctx := otel.GetTextMapPropagator().Extract(r.Context(), propagation.HeaderCarrier(r.Header))

        // Добавляем tenant_id в baggage
        member, err := baggage.NewMember("tenant_id", r.Header.Get("X-Tenant-Id"))
        if err != nil {
            http.Error(w, "invalid tenant id", http.StatusBadRequest)
            return
        }
        b, err := baggage.New(member)
        if err != nil {
            http.Error(w, "baggage rejected", http.StatusBadRequest)
            return
        }
        ctx = baggage.ContextWithBaggage(ctx, b)

        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

// Чтение baggage в любом сервисе цепочки — извлечение из ctx,
// а не из заголовков: значение уже прошло через propagator
func TenantFromContext(ctx context.Context) string {
    return baggage.FromContext(ctx).Member("tenant_id").Value()
}
```

> **Ключевой момент:** `baggage` — часть `context.Context`, а не отдельный параметр. Значение, положенное в контекст на входе, доступно в любом вложенном вызове и автоматически сериализуется в заголовок `baggage` при исходящем HTTP-вызове, если propagator включён. Отдельный код «передачи контекста дальше» не нужен — это устраняет целый класс ошибок, когда вложенный сервис забыл пробросить заголовок.

**Включение propagator** (без этого заголовок `baggage` не будет ни извлечён, ни отправлен):

```go
otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
    propagation.TraceContext{}, // traceparent + tracestate
    propagation.Baggage{},      // baggage
))
```

**Внимание:**

- `baggage` передаётся в HTTP-заголовке (`baggage: tenant_id=client_abc`), поэтому **не храните в нём чувствительные данные**. Заголовок логируется веб-серверами, попадает в APM и иногда кэшируется CDN.
- Соблюдайте лимиты спецификации: не более 180 элементов и 8192 байт суммарно. Превышение приводит к молчаливой частичной потере элементов на границах, где это проверяется.
- Baggage — **не** механизм доставки данных бизнес-логики. Если значение нужно почти везде, это признак того, что оно принадлежит в контексте запроса приложения, а не в телеметрии.
- В Python API другой: `baggage.set_baggage(name, value)` и `baggage.get_baggage(name, ctx)`. Не смешивайте API разных языков в одном примере.

### Сценарий 6: Мета-мониторинг пайплайна трассировок

**Задача:** Обеспечить отказоустойчивость пайплайна сбора трассировок и предотвратить потерю данных.

**Требование к порогу мониторинга.** Список метрик ниже отражает внутреннюю телеметрию Collector. Она доступна на Prometheus-эндпоинте по умолчанию на порту `8888`, а уровень детализации задаётся параметром `service.telemetry.metrics.level` (`none` / `basic` / `normal` — по умолчанию / `detailed`).

**Соглашения об именовании.** Collector по умолчанию настраивает Prometheus-экспортёр с `without_type_suffix: true`, `without_units: true` и `without_scope_info: true` (дефолты выставляет функция `applyPrometheusDefaults`). Поэтому на `/metrics` счётчики отдаются **без** суффикса `_total`, а метрики с единицами — без суффикса единицы: `otelcol_exporter_send_failed_spans`, `otelcol_process_uptime`, `otelcol_process_memory_rss`. Дефолты применяются и к явно заданным `service::telemetry::metrics::readers`, поэтому результат не зависит от того, переопределили вы host/port или нет.

**Суффиксы появляются только при явном opt-out.** Чтобы счётчик снова отдавался как `otelcol_exporter_send_failed_spans_total`, а `otelcol_process_uptime` — как `otelcol_process_uptime_seconds_total`, нужно **явно** выставить `without_type_suffix: false` и `without_units: false`. Если вы задаёте `readers` вручную и хотите гарантировать стабильные имена в правилах алертинга, зафиксируйте эти три флага явно:

```yaml
service:
  telemetry:
    metrics:
      readers:
        - pull:
            exporter:
              prometheus:
                host: 0.0.0.0
                port: 8888
                without_type_suffix: true
                without_units: true
                without_scope_info: true
```

| Метрика (имя на `/metrics`) | Назначение | Порог алерта |
| :--- | :--- | :--- |
| `otelcol_receiver_accepted_spans` | Спаны, принятые в пайплайн | Резкое падение при неизменном трафике сервисов |
| `otelcol_receiver_refused_spans` | Спаны, отклонённые receiver'ом | > 0 устойчиво: клиенты теряют данные или получают ошибки |
| `otelcol_processor_memory_limiter_refused_spans` | Спаны, отклонённые `memory_limiter` (OOM-давление) | > 0: Collector упирается в память |
| `otelcol_processor_memory_limiter_accepted_spans` | Спаны, прошедшие через `memory_limiter` в следующий компонент | Разрыв с `accepted` выше = отказ именно на этом процессоре |
| `otelcol_exporter_sent_spans` | Спаны, отправленные в хранилище | Расхождение с `accepted` сверху означает потерю |
| `otelcol_exporter_send_failed_spans` | Ошибки отправки (с ретраями) | > 0 устойчиво: сеть или бэкенд |
| `otelcol_exporter_enqueue_failed_spans` | Данные не попали в `sending_queue` | > 0: очередь переполнена, потеря необратима |
| `otelcol_exporter_queue_size` / `otelcol_exporter_queue_capacity` | Заполненность очереди отправки | `queue_size` устойчиво близок к `capacity` |
| `otelcol_processor_incoming_items` / `otelcol_processor_outgoing_items` | Вход/выход каждого processor | Разрыв = внутренний дроп |
| `otelcol_processor_batch_batch_send_size` | Реальный размер отправленного батча | Гистограмма; сравнивайте с `send_batch_size` |
| `otelcol_process_memory_rss` | RSS процесса Collector | Базовый уровень для алертов на OOM |
| `otelcol_process_runtime_heap_alloc_bytes` | Занято в куче Go | Базовый уровень для алертов на OOM |
| `otelcol_process_uptime` | Время работы | < expected — рестарты |

**Сопоставление «принято» и «отправлено»** — базовая проверка целостности пайплайна:

```promql
rate(otelcol_receiver_accepted_spans[5m])
  - rate(otelcol_exporter_sent_spans[5m])
# → устойчиво положительное значение = где-то между приёмом и отправкой теряются спаны
```

**Алерт-правила для Prometheus:**

```yaml
groups:
- name: otel-collector-meta-monitoring
  rules:
  - alert: OtelCollectorEnqueueFailedSpans
    expr: rate(otelcol_exporter_enqueue_failed_spans[5m]) > 0
    for: 5m
    labels:
      severity: critical
    annotations:
      summary: "OTel Collector: данные не попадают в sending_queue"
      description: "Очередь отправки переполнена, спаны теряются необратимо. Увеличьте размер очереди, снизьте поток или масштабируйте Collector горизонтально."

  - alert: OtelCollectorMemoryLimiterRefusedSpans
    expr: rate(otelcol_processor_memory_limiter_refused_spans[5m]) > 0
    for: 10m
    labels:
      severity: warning
    annotations:
      summary: "OTel Collector: memory_limiter отклоняет спаны"
      description: "Collector упирается в лимит памяти. Проверьте limit_mib против реального RSS и cgroup-лимита контейнера."

  - alert: OtelCollectorExportFailed
    expr: rate(otelcol_exporter_send_failed_spans[5m]) > 0
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "OTel Collector: ошибки отправки в хранилище"
      description: "Проверьте доступность бэкенда, TLS-сертификаты и сетевую связность. Ретраи могут скрыть длительный отказ."

  - alert: OtelCollectorQueueSaturated
    expr: |
      otelcol_exporter_queue_size
        / otelcol_exporter_queue_capacity > 0.8
    for: 15m
    labels:
      severity: warning
    annotations:
      summary: "OTel Collector: sending_queue заполнена более чем на 80%"

  - alert: OtelCollectorMemoryHigh
    expr: |
      otelcol_process_memory_rss
        / on(instance, job) container_spec_memory_limit_bytes{container_name=~".*otelcol.*"} > 0.8
    for: 10m
    labels:
      severity: warning
    annotations:
      summary: "OTel Collector: RSS превысил 80% лимита контейнера"
      description: "RSS процесса Collector приближается к лимиту cgroup. Алерт срабатывает по внешнему источнику лимита (cAdvisor), а не по метрикам самого Collector."
```

> **Ограничение последнего правила.** Collector не публикует метрику «лимит памяти процесса» — `memory_limiter.limit_mib` живёт только в конфигурации, а не в телеметрии. Поэтому «процент от лимита» вычислить внутри Prometheus нельзя: нужен внешний источник лимита (cgroup-файл `memory.max`, `container_spec_memory_limit_bytes` от cAdvisor или `process_resident_memory_bytes` рядом с `otelcol_process_memory_rss` из того же node_exporter). Практический рабочий вариант — сравнивать `otelcol_process_memory_rss` с лимитом cgroup:

```promql
otelcol_process_memory_rss
  / on(instance) container_spec_memory_limit_bytes{container_name=~".*otelcol.*"} > 0.8
# → приближение к лимиту контейнера;
#   разрыв между этими двумя величинами и есть тот самый зазор,
#   который нельзя получить из метрик самого Collector
```

**Конфигурация Collector, покрывающая описанные режимы отказа:**

```yaml
processors:
  # Всегда первым в пайплайне — должен отклонять данные раньше, чем память реально кончится
  memory_limiter:
    check_interval: 1s
    limit_mib: 4000
    spike_limit_mib: 500

  tail_sampling:
    decision_wait: 10s
    num_traces: 100000
    policies:
      - name: errors-policy
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: slow-policy
        type: latency
        latency: {threshold_ms: 2000}
      - name: probabilistic-policy
        type: probabilistic
        probabilistic: {sampling_percentage: 1}

  batch:
    send_batch_size: 1024
    timeout: 10s

exporters:
  otlp/tempo:
    endpoint: tempo.observability.svc:4317
    tls:
      insecure: true
    # Постоянная файловая очередь: при недоступности Tempo данные переживают рестарт Collector
    sending_queue:
      enabled: true
      num_consumers: 10
      queue_size: 5000
    retry_on_failure:
      enabled: true
      initial_interval: 5s
      max_interval: 30s
      max_elapsed_time: 300s

service:
  telemetry:
    metrics:
      level: normal
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, tail_sampling, batch]
      exporters: [otlp/tempo]
```

**Порядок процессоров имеет значение.** `memory_limiter` обязан идти первым: только тогда он отклоняет данные до того, как остальные процессоры аллоцируют память под батчи. `tail_sampling` ставится после всех процессоров, работающих с контекстом (например, `k8sattributes`), и обязательно **до** `batch` — иначе спаны одного трейса попадут в разные батчи и решение принимается по неполным данным.

**Масштабирование tail sampling.** При добавлении второго экземпляра Collector все спаны одного трейса должны попадать на один инстанс. Рабочая схема — два слоя: агенты отправляют через `loadbalancing` exporter на шардированный слой, а tail sampling живёт на отдельном слое за ним. Один экземпляр с двумя пайплайнами технически возможен, но официально не рекомендуется: слои дают лучшую изоляцию отказов.

**SRE: мониторинг как SLO.** Сбор трассировок — несущая конструкция наблюдаемости; его отказ тише всего остального, потому что приложение продолжает работать. Определите для пайплайна собственный SLI и алертуйте по нему, а не по факту «пользователь заметил»:

| SLI | Формула | Целевое значение |
| :--- | :--- | :--- |
| Полнота доставки | `sent_spans / accepted_spans` | ≥ 0,999 |
| Неизменность сэмплирования | `global_count_traces_sampled{sampled="true"} / global_count_traces_sampled` | В пределах ожидаемой доли |
| Отсутствие ранних потерь | `rate(sampling_trace_dropped_too_early[15m])` | 0 |
| Задержка доступности свежих данных | Время от запроса до появления в UI | В пределах целевого окна |

### Сценарий 7: Корреляция trace_id с логами (Go)

**Задача:** Реализовать сквозную трассировку от HTTP-запроса до SQL-запроса и обратно, обеспечивая корреляцию логов, метрик и трассировок.

**Важно о `ResponseWriter`.** Создание спана — не только `Start`/`End`. Чтобы записать `http.response.status_code`, нужно обернуть `http.ResponseWriter`: иначе стандартная библиотека пишет статус напрямую в сокет, и перехватить его невозможно. Обёртка обязана реализовывать `http.Flusher`, иначе загрузка файлов и SSE-стриминг теряют flush-семантику.

```go
package middleware

import (
    "context"
    "log/slog"
    "net/http"
    "time"

    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/attribute"
    "go.opentelemetry.io/otel/codes"
    "go.opentelemetry.io/otel/propagation"
    "go.opentelemetry.io/otel/trace"
)

type statusRecorder struct {
    http.ResponseWriter
    status int
}

func (r *statusRecorder) WriteHeader(code int) {
    r.status = code
    r.ResponseWriter.WriteHeader(code)
}

func (r *statusRecorder) Flush() {
    if f, ok := r.ResponseWriter.(http.Flusher); ok {
        f.Flush()
    }
}

// Tracer объявляется один раз на уровне пакета — otel.Tracer("...") дешёв,
// но всё же возвращает обёртку, которую не стоит создавать на каждый запрос
var tracer = otel.Tracer("http-server")

func TracingMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // 1. Извлекаем входящий контекст: traceparent, tracestate, baggage
        ctx := otel.GetTextMapPropagator().Extract(r.Context(), propagation.HeaderCarrier(r.Header))

        rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}

        ctx, span := tracer.Start(ctx,
            r.Method+" "+r.URL.Path,
            trace.WithSpanKind(trace.SpanKindServer),
            trace.WithAttributes(
                attribute.String("http.request.method", r.Method),
                attribute.String("url.full", r.URL.String()),
                attribute.String("server.address", r.Host),
                attribute.String("user_agent.original", r.UserAgent()),
            ),
        )
        defer span.End()

        // 2. Ставим trace_id в контекст логгера — теперь каждая запись лога
        //    в этом запросе коррелирована с трейсом
        sc := span.SpanContext()
        logger := slog.Default().With(
            slog.String("trace_id", sc.TraceID().String()),
            slog.String("span_id", sc.SpanID().String()),
        )
        ctx = context.WithValue(ctx, ctxKeyLogger{}, logger)

        next.ServeHTTP(rec, r.WithContext(ctx))

        // 3. Закрываем спан с фактическим статусом ответа
        span.SetAttributes(attribute.Int("http.response.status_code", rec.status))
        if rec.status >= 500 {
            span.SetStatus(codes.Error, http.StatusText(rec.status))
            span.SetAttributes(attribute.String("error.type", "5xx"))
        }
    })
}

// ctxKeyLogger — собственный тип ключа, чтобы избежать коллизий
// с ключами из других пакетов в context.Context
type ctxKeyLogger struct{}

func LoggerFromContext(ctx context.Context) *slog.Logger {
    if l, ok := ctx.Value(ctxKeyLogger{}).(*slog.Logger); ok {
        return l
    }
    return slog.Default()
}
```

**Полный production-ready пример требует также:**

1. Инициализации `TracerProvider` с `BatchSpanProcessor` и OTLP-экспортёром. Без неё SDK создаёт no-op-трейсер, и весь middleware не даёт эффекта:

```go
exporter, err := otlptracegrpc.New(ctx,
    otlptracegrpc.WithEndpoint("otel-collector:4317"),
    otlptracegrpc.WithInsecure(),
)
if err != nil {
    return err
}
tp := sdktrace.NewTracerProvider(
    sdktrace.WithResource(resource.NewSchemaless(
        attribute.String("service.name", "order-api"),
        attribute.String("service.version", "1.4.2"),
    )),
    sdktrace.WithBatcher(exporter),
)
otel.SetTracerProvider(tp)
```

> `resource.NewSchemaless` не проставляет `otel.schema_url` в ресурсе. Если атрибуты ресурса должны сопровождаться схемой, используйте `resource.NewWithAttributes` с пакетом `semconv` той версии, которую вы зафиксировали, — тогда `SchemaURL` попадёт и в ресурс, и во все спаны.

2. Регистрации propagator (иначе `Extract` не прочитает `traceparent`):

```go
otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
    propagation.TraceContext{},
    propagation.Baggage{},
))
```

3. `defer func() { _ = tp.Shutdown(ctx) }()` при остановке процесса — иначе теряется последний батч.

**Что даёт корреляция:**

1. `trace_id` передаётся в дочерние сервисы через заголовки.
2. `trace_id` попадает в структурированные логи, и переход «график → лог → трейс» работает в обе стороны.
3. Exemplars связывают конкретную точку временного ряда с конкретным трейсом.

### Сценарий 8: Выбор хранилища трассировок

**Задача:** Выбрать бэкенд и построить конфигурацию под нагрузку выше 100 тысяч спанов в секунду.

**Сравнение бэкендов:**

| Бэкенд | Когда выбирать | Ограничения |
| :--- | :--- | :--- |
| **Grafana Tempo 3.0** | Основной выбор для Kafka-совместимого, объектного хранения и низкого TCO | Decoupled Read/Write Path требует Kafka в микросервисном режиме |
| **Jaeger 2.21** | Когда нужна готовая Jaeger UI + Query API без отдельного бэкенда | Хранилище подключается расширением `jaeger_storage` |
| **ClickHouse** | Хранение спанов Jaeger; произвольная аналитика по тегам | В Jaeger 2.x — **experimental**, включается feature gate `storage.clickhouse`; поддерживается ClickHouse **26.x** |
| **Elasticsearch / OpenSearch** | Когда хранилище трассировок общее с логами | JVM heap до 31 ГБ, шард 20–50 ГБ; [управление жизненным циклом](../../Jaeger/jaeger_security_hardening.md) обязательно |
| **Cassandra** | Существующие кластеры как legacy-бэкенд | Не развивается как бэкенд Jaeger |
| **Badger / Memory** | Локальная разработка, CI | Данные не переживают рестарт |

**Jaeger 2.x: конфигурация задаётся только файлом.** Jaeger v2 не читает переменные окружения как Jaeger v1. Пример ниже воспроизводит основную структуру официального `config-clickhouse.yaml` (секция `metric_backends` опущена как несущественная для примера):

```yaml
# config-clickhouse.yaml
service:
  extensions: [jaeger_storage, jaeger_query, healthcheckv2]
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [jaeger_storage_exporter]
  telemetry:
    resource:
      service.name: jaeger
    metrics:
      level: detailed
      readers:
        - pull:
            exporter:
              prometheus:
                host: 0.0.0.0
                port: 8888

extensions:
  healthcheckv2:
    use_v2: true
    http:

  jaeger_query:
    storage:
      traces: some-storage
    ui:
      config_file: ./cmd/jaeger/config-ui.json

  jaeger_storage:
    backends:
      some-storage:
        clickhouse:
          addresses:
            - clickhouse:9000
          database: jaeger
          auth:
            basic:
              username: default
              password: ${env:CLICKHOUSE_PASSWORD}
          create_schema: true

receivers:
  otlp:
    protocols:
      grpc:
      http:

processors:
  batch:

exporters:
  jaeger_storage_exporter:
    trace_storage: some-storage
```

**Ключевые отличия от формата Jaeger v1**, которые чаще всего становятся источником ошибки:

- Хранилище описывается в `extensions.jaeger_storage.backends.<имя>`, а не в секции `span_storage`.
- Обращение к бэкенду идёт **по имени** (`trace_storage: some-storage`), а не по типу.
- Поле подключения ClickHouse — **`addresses` (список)**, а не `endpoint` со схемой.
- Переменные окружения в YAML поддерживаются, но как подстановка `${env:NAME}` — не как отдельный механизм конфигурации v1.

**Docker Compose для стенда:**

```yaml
# docker-compose.yml
services:
  jaeger:
    image: jaegertracing/jaeger:2.21.0
    volumes:
      - ./config-clickhouse.yaml:/etc/jaeger/config.yaml:ro
    ports:
      - "4317:4317"    # OTLP gRPC
      - "4318:4318"    # OTLP HTTP
      - "8888:8888"    # внутренняя телеметрия

    depends_on:
      - clickhouse

  clickhouse:
    image: clickhouse/clickhouse-server:26
    environment:
      CLICKHOUSE_DB: jaeger
      CLICKHOUSE_USER: default
      CLICKHOUSE_PASSWORD: ${CLICKHOUSE_PASSWORD}
    volumes:
      - clickhouse-data:/var/lib/clickhouse
    ulimits:
      nofile:
        soft: 262144
        hard: 262144

volumes:
  clickhouse-data:
```

**Валидация:**

```bash
# Схема спанов создана
clickhouse-client --query "SHOW TABLES FROM jaeger"

# Спаны реально пишутся

# → число, сопоставимое с расчётным: RPS × 3600 × доля сэмплирования

# Jaeger принимает OTLP

# → ["order-api","payment-api","shipping"]

```

**Ограничения и предосторожности ClickHouse в Jaeger:**

- Статус хранилища — **experimental**; схема может измениться в будущих релизах. Не берите на себя риск без осознанного решения и плана на миграцию.
- Требуются Bloom-фильтры на часто фильтруемых тегах, иначе поиск по трейсам деградирует до полного сканирования.
- Мониторьте телеметрию Collector: ошибки экспортера (`otelcol_exporter_send_failed_spans`) и отказы `memory_limiter` (`otelcol_processor_memory_limiter_refused_spans`). Отдельных Jaeger-специфичных метрик вроде `jaeger_processor_spans_success_total` нет — официальная документация по метрикам Jaeger 2.x описывает только внутреннюю телеметрию Collector (`otelcol_*`).

**Объёмное хранение и высоконагруженные конфигурации** Jaeger (Kafka-буферизация, ingester, ES-шаблоны, ILM) разобраны отдельно — см. [Jaeger: хранилище подробно](../../Jaeger/jaeger_storage_deep_dive.md) и [Jaeger: анализ производительности](../../Jaeger/jaeger_performance_analysis.md), чтобы не дублировать их здесь.

### Сценарий 9: Автоматическая инструментация Java-приложений через OTel Java Agent

**Задача:** Добавить трассировки в существующее Java-приложение без изменения кода.

**Шаги:**

1. Скачать агент, зафиксировав версию (не `latest` — § 8):

```bash
OTEL_AGENT_VERSION=2.31.1
wget "https://github.com/open-telemetry/opentelemetry-java-instrumentation/releases/download/v${OTEL_AGENT_VERSION}/opentelemetry-javaagent.jar"
# → HTTP 200, файл сохранён как opentelemetry-javaagent.jar
```

2. Запустить приложение с агентом:

```bash
java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=my-java-service \
     -Dotel.service.version=1.0.0 \
     -Dotel.exporter.otlp.endpoint=http://otel-collector:4317 \
     -Dotel.exporter.otlp.protocol=grpc \
     -Dotel.resource.attributes=deployment.environment=production \
     -jar my-application.jar
# → в stderr: "INFO [otel.javaagent] OpenTelemetry Java Agent ... successfully started"
```

3. Эквивалентная конфигурация через переменные окружения:

```bash
# Экспорт
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317
OTEL_EXPORTER_OTLP_PROTOCOL=grpc
OTEL_EXPORTER_OTLP_COMPRESSION=gzip

# Идентификация сервиса
OTEL_SERVICE_NAME=my-java-service
OTEL_RESOURCE_ATTRIBUTES=service.version=1.0.0,deployment.environment=production

# Сэмплирование
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.1   # 10%

# Миграция на стабильные семантические конвенции
OTEL_SEMCONV_STABILITY_OPT_IN=http/dup

# Диагностика
OTEL_LOG_LEVEL=debug
```

**Внимание:** `OTEL_JAVAAGENT_ENABLED` не является переменной для включения агента. Агент включается фактом передачи `-javaagent:`; переменная `OTEL_JAVAAGENT_ENABLED` управляет поведением внутри agent-контейнеров в Kubernetes, а не включает инструментацию в обычном `java -jar`.

**Что инструментируется автоматически:**

- HTTP-серверы и клиенты: Spring MVC/WebFlux, JAX-RS, Jersey, OkHttp, Apache HttpClient, `RestTemplate`
- JDBC-драйверы
- Клиенты очередей: Kafka, RabbitMQ
- Хранилища: Redis, MongoDB, Elasticsearch, Cassandra
- Фреймворки: gRPC, Netty, Reactor

**В Kubernetes** тот же результат достигается оператором OpenTelemetry через CRD `Instrumentation` без изменения манифестов приложения — подробно в [инструментации SDK](../../OpenTelemetry/instrumentation_sdk.md).

**Валидация:**

```bash
# Спаны доходят до Collector
curl -s http://localhost:8888/metrics | grep 'otelcol_receiver_accepted_spans{'
# → otelcol_receiver_accepted_spans{receiver="otlp",...} 128
#   ненулевой и растущий счётчик = трассировки идут

# Заголовок traceparent корректно извлекается
curl -s -o /dev/null -w '%{http_code}\n' \
     -H 'traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01' \
     http://localhost:8080/api/endpoint
# → 200; затем искать трейс 4bf92f3577b34da6a3ce929d0e0e4736 в Tempo/Jaeger —
#   если он найден и содержит вложенные спаны, контекст проходит корректно
```

## Диагностика и устранение неполадок

| Проблема | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Разорванные трейсы** | Отсутствие передачи `traceparent` в одном из узлов | Проверить `traceparent` на каждом сетевом переходе; сверить `OTEL_PROPAGATORS` во всех сервисах | Проверить propagator в SDK всех сервисов. Проверить конфигурацию Ingress/Proxy — они должны пропускать заголовки, а не вырезать их. |
| **Разрыв именно на брокере** | Kafka/AMQP не являются HTTP-транспортом, propagator не срабатывает | Проверить наличие заголовков контекста в headers сообщения | Инжектить контекст в headers на продюсере, извлекать на консьюмере явно. |
| **Clock Skew (сдвиг времени)** | Рассинхронизация NTP на разных серверах | `chronyc tracking`, `chronyc sources`, `timedatectl status` | Спаны могут отображаться в будущем или иметь отрицательную длительность. Синхронизация через `chrony`; расхождение > 1 сек уже портит чтение каскадной диаграммы |
| **Высокая нагрузка на сеть** | Слишком большой объем атрибутов или отсутствие сжатия | Сравнить `otelcol_processor_batch_batch_send_size` с ожидаемым размером батча | Включить сжатие на экспортёре (`gzip`, `zstd`). Ограничить размер атрибутов — не писать полные тела запросов/ответов. |
| **Missing Spans (пропуски)** | Переполнение `memory_limiter` или `sending_queue` | `otelcol_processor_memory_limiter_refused_spans`, `otelcol_exporter_enqueue_failed_spans`, `otelcol_exporter_queue_size / otelcol_exporter_queue_capacity` | Увеличить `limit_mib` (проверив лимит cgroup), расширить `sending_queue.queue_size`, добавить экземпляров Collector |
| **Трейсы теряются до решения сэмплирования** | Кольцевой буфер `tail_sampling` переполнен | `otelcol_processor_tail_sampling_sampling_trace_dropped_too_early`, `otelcol_processor_tail_sampling_sampling_trace_removal_age` | Увеличить `num_traces` или уменьшить `decision_wait`. Оба растят RAM |
| **Трейс приходит по частям** | Спаны одного трейса попали на разные экземпляры Collector | Сравнить число спанов в трейсе с ожидаемым; проверить конфигурацию `loadbalancing` | Ввести два слоя Collector: `loadbalancing` exporter + отдельный слой tail sampling |
| **Высокая задержка записи** | Медленная запись в хранилище | Метрики exporter'а Collector (`otelcol_exporter_queue_size`, `otelcol_exporter_send_failed_spans`) и метрики Kafka в Tempo | Проверить IOPS хранилища, размер батча, параллелизм записи |
| **Дублирование спанов** | Несколько источников инструментации на одном пути | Сравнить число спанов одного трейса с ожидаемым; проверить, не работают ли одновременно SDK и eBPF | Устранить двойную инструментацию либо сузить scope eBPF-агента. Идемпотентность на уровне БД — не решение, а маскировка |
| **`trace_id` не коррелирует с логами** | Отсутствие `trace_id` в логах | `jq 'select(.trace_id==null)'` по потоку логов | Убедиться, что SDK добавляет `trace_id` в логи; использовать structured logging с полем `trace_id` |
| **Высокое потребление RAM в Collector** | `tail_sampling` с большими объемами данных | `otelcol_process_memory_rss` против лимита cgroup | Увеличить `limit_mib`, уменьшить `num_traces`, облегчить политики. **Не увеличивать `limit_mib` выше лимита контейнера** — тогда OOM-убийца придёт раньше, чем сработает `memory_limiter` |
| **Запросы TraceQL не находят то, что есть** | Смешение scopes или устаревшие имена атрибутов | Проверить, `span.` это или `resource.`; сверить имя атрибута с semconv 1.44.x | Привести имена к стабильным (`db.query.text`, а не `db.statement`); указывать scope явно |
| **Запросы работают на Tempo 2.x, но не на 3.0** | Изменение семантики `!=` / `!~` для array-атрибутов | Прогнать те же запросы на обоих бэкендах | Переписать условия; проверить все запросы с `!=` и `!~` по array-атрибутам |
| **Проблемы с eBPF-инструментацией** | Несовместимость версий ядра или отсутствие BTF | `uname -r`, `ls -l /sys/kernel/btf/vmlinux`, логи агента | Ядро 5.8+ (рекомендуется 5.10+), включённый BTF, необходимые capabilities, отключённый seccomp-фильтр |
| **Дрейф часов в кластере** | Разные источники NTP на нодах | Сравнить `chronyc tracking` на нескольких нодах | Единый источник времени; в контейнерах — `chrony` с общим источником, а не `hostTime: true` с рассинхроном хостов |

```text

spanset   := "{" условие "}"
условие   := терм ( ("&&" | "||") терм )*
```

### Планирование ресурсов Collector

Точные коэффициенты «CPU на N спанов в секунду» зависят от состава пайплайна, размера атрибутов и настроек сжатия, поэтому переносить числа из чужого стенда — прямой путь к перерасходу ресурсов. Надёжный порядок — измерение на своём трафике:

1. **Зафиксировать целевой объём.** Измерьте RPS спанов на пике (`otelcol_receiver_accepted_spans`) и долю сэмплирования. Целевой объём хранилища = RPS × доля сэмплирования × средний размер спана × retention.
2. **Измерить стоимость одного спана.** Разверните Collector с одним экземпляром, подайте синтетическую нагрузку и снимите метрики процесса (`otelcol_process_cpu_seconds`, `otelcol_process_memory_rss`, `otelcol_process_runtime_heap_alloc_bytes`) относительно `otelcol_receiver_accepted_spans`. Полученные коэффициенты справедливы для вашего набора процессоров.
3. **Проверить запасы.** `memory_limiter.limit_mib` задавайте ниже лимита cgroup, оставляя запас: резервируйте минимум 20% на фактическое превышение `memory_limiter` и пики при garbage collection. `spike_limit_mib` задаёт размер скачка, при котором начинается отказ, — он должен быть заметно меньше `limit_mib`.
4. **Учесть стоимость tail sampling.** Буфер `num_traces` умножается на средний размер трейса в памяти. Это основной потребитель RAM при tail-based сэмплировании, и он не виден, если смотреть только на «спанов в секунду».
5. **Проверить cgroup, а не только `limit_mib`.** Если OOM-убийца приходит раньше, чем `memory_limiter` успевает отказать в данных, процессор бесполезен — поднимается он только вместе с лимитом контейнера.

| Издержки | SDK / языковой агент | eBPF (OBI) | На что влияет |
| :--- | :--- | :--- | :--- |
| **CPU** | Нагрузка на рантайм приложения | Нагрузка на ядро и минимальный рантайм-оверхед | Число спанов, размер атрибутов, сжатие |
| **Память процесса** | Буфер `BatchSpanProcessor` (`max_queue_size` × средний размер спана) | Наименьшая из вариантов | Объём очереди экспорта |
| **Сеть** | Объём OTLP-трафика до Collector | Тот же объём | Сжатие, размер атрибутов, доля сэмплирования |
| **Хранилище** | Определяется долей сэмплирования и retention | То же | Сжатие в бэкенде (LZ4, zstd) |

### Стоимость и риски

| Решение | Экономит | Цена |
| :--- | :--- | :--- |
| Tail-based сэмплирование | 99% объёма при сохранении 100% ошибок | RAM на Collector, требование sticky-маршрутизации спанов |
| Урезание атрибутов на SDK | Объём сети и хранилища | Потеря диагностической ценности; нужна формализация «безопасного» набора атрибутов |
| `db.query.text` вместо полного тела запроса | Хранилище, риск утечки PII | Нет данных о параметрах — их следует брать из `db.query.parameter.<key>` |
| Отказ от `baggage` на публичных границах | Риск утечки | Теряется сквозная контекстная разметка для внешних вызовов |
| Retention 7–30 дней | Хранилище | Трейсы для расследования старых инцидентов недоступны |

### Лучшие практики

1.  **Семантические конвенции:** Строго используйте [OpenTelemetry Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/) для имен атрибутов. Помните, что `http.method`, `http.status_code`, `db.system`, `db.statement` — **устаревшие** имена; актуальные — `http.request.method`, `http.response.status_code`, `db.system.name`, `db.query.text`. Планируйте миграцию через `OTEL_SEMCONV_STABILITY_OPT_IN` заранее.
2.  **Context Propagation везде:** Убедитесь, что `traceparent` передаётся через все посредники (Proxy, Load Balancers, Queues). Для очередей передача не автоматическая — реализуйте инъекцию и извлечение контекста явно.
3.  **Явный scope в запросах:** Указывайте `span.` или `resource.` в TraceQL-фильтрах. Без явного scope поиск проверяет оба уровня, что и медленнее, и даёт неожиданные совпадения.
4.  **Автоматическое инструментирование как основа:** Используйте языковые агенты для ~80% задач, но вручную размечайте критические бизнес-операции внутри спанов — только так в трейсе появляется контекст, недоступный автоматике.
5.  **Семантические имена спанов:** Имя спана (`span:name`) — это ключ агрегации в Grafana, TraceQL Metrics и правилах алертинга. Используйте шаблон маршрута низкой кардинальности (`GET /orders/{id}`, а не конкретный URL) — иначе каждая серия уникальна.
6.  **Размер атрибутов:** Ограничивайте размер атрибутов. Не записывайте полные тела запросов и ответов — используйте идентификаторы или первые N символов. Параметризованный текст запроса безопасен и полезен; значения параметров — нет.
7.  **Мониторинг пайплайна как production-компонента:** Алертите на `otelcol_exporter_enqueue_failed_spans` (необратимая потеря), `otelcol_processor_memory_limiter_refused_spans` (давление памяти) и на рассогласование `accepted` и `sent`.
8.  **Версионирование схемы:** При внесении breaking changes в имена атрибутов используйте версионирование, чтобы не ломать существующие запросы. Имена вида `http.request.version: 2` — пример такого подхода, но не универсальное решение: полноценная версионированность в semconv выражается через сами спецификации конвенций и `OTEL_SEMCONV_STABILITY_OPT_IN`.
9.  **Тестирование инструментации:** Регулярно проверяйте, что спаны создаются и связываются, а запускайте инструментацию в CI как trace-based testing — это ловит регрессии наблюдаемости до production.
10. **Документирование:** Ведите каталог спанов и их атрибутов. Это критично для командной работы и онбординга.
11. **Два уровня сэмплирования:** Head-based на SDK снижает поток, tail-based в Collector вытягивает ошибки. Одного head-based недостаточно — он по определению не видит результат.
12. **Ограничение Baggage границами доверия:** Не передавайте baggage во внешние системы; соблюдайте лимиты 180 элементов и 8192 байт.

### Чек-лист по внедрению трассировок

- [ ] Определены критические пути запросов для трассировки
- [ ] Выбраны версии OTel SDK, агента и Collector; версии зафиксированы, а не `latest`
- [ ] Настроен OTel Collector с `memory_limiter` первым в пайплайне
- [ ] `tail_sampling` стоит после всех context-aware процессоров и до `batch`
- [ ] Настроена маршрутизация всех спанов трейса на один экземпляр Collector
- [ ] Выбрано хранилище (Tempo 3.0 или Jaeger 2.21 с нужным бэкендом)
- [ ] Настроена Context Propagation во всех сервисах, включая брокеры сообщений
- [ ] Имена спанов низкокардинальны и используют шаблоны маршрутов
- [ ] Атрибуты приведены к стабильным семантическим конвенциям
- [ ] Определён и задокументирован «безопасный набор» атрибутов (без PII и секретов)
- [ ] Baggage не пересекает границы доверия; соблюдены лимиты 180 / 8192 байт
- [ ] `trace_id` добавлен в структурированные логи
- [ ] Настроен мета-мониторинг пайплайна с алертами на потерю спанов
- [ ] Определены политики сэмплирования и проверена фактическая доля сохранённых трейсов
- [ ] Зафиксирован retention в хранилище
- [ ] `limit_mib` Collector меньше лимита cgroup, с запасом
- [ ] Настроены Exemplars для перехода от метрики к трейсу
- [ ] Документированы семантические конвенции для команды
- [ ] Проведено обучение команды работе с трассировками

### Архитектурные паттерны сбора

| Паттерн | Описание | Когда использовать |
| :--- | :--- | :--- |
| **Agent-per-host** | OTel Collector на каждой ноде | Kubernetes DaemonSet, bare-metal серверы |
| **Sidecar** | Collector рядом с каждым подом | Высокая изоляция; помогает eBPF-конфликтам и per-pod лимитам |
| **Gateway** | Централизованный Collector | Малые системы, простые архитектуры |
| **Agent + Gateway** | Комбинация для масштабирования | Крупные системы, много сервисов |
| **Двухслойный (load balancing + tail sampling)** | Агенты шардируют трафик, отдельный слой принимает решения сэмплирования | Любая горизонтально масштабируемая tail-based схема |
