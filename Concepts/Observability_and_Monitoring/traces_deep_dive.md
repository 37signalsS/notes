# Traces Deep Dive

## Определения

**Распределённая трассировка (Distributed Tracing)** — метод отслеживания полного пути выполнения запроса через все компоненты распределённой системы с визуализацией в виде каскадной диаграммы, показывающей временные соотношения между операциями.

**Ключевая ценность:** Возможность увидеть, какие сервисы участвуют в обработке запроса, сколько времени занимает каждый этап, и где возникают задержки или ошибки.

**Место в Observability:** Трассировки — третий столп наблюдаемости (после логов и метрик), обеспечивающий детализацию до уровня отдельных операций в распределённой системе. Подробнее: [`four_pillars_of_observability.md`](./four_pillars_of_observability.md).

## Базовые концепции

### Основные компоненты

| Компонент | Описание | Пример |
| :--- | :--- | :--- |
| **Trace (Трейс)** | Весь путь одного запроса через систему. Уникально идентифицируется `TraceID`. | Запрос "Оформить заказ" в интернет-магазине |
| **Span (Спан)** | Отдельная операция внутри трейса. Имеет `SpanID`, `TraceID`, имя, время начала/окончания, атрибуты. Спаны образуют иерархию "родитель-потомок". | HTTP-вызов к платежному сервису, SQL-запрос к БД |
| **Trace Context** | Механизм передачи контекста между сервисами. Стандарт **W3C Trace Context** определяет HTTP-заголовок `traceparent` с `TraceID`, `ParentID` и флагами сэмплирования. | Заголовок `traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01` |

### Передача контекста (Trace Context Propagation)

Для сквозного отслеживания запроса между сервисами используется механизм передачи контекста — "ниточка", связывающая все спаны одного трейса.

**Принцип работы:**

1. Первый сервис (entry point) генерирует `TraceID` и создаёт корневой спан
2. При вызове следующего сервиса `TraceID` и `ParentID` передаются в заголовках (HTTP, gRPC, messaging)
3. Получивший сервис создаёт дочерний спан с тем же `TraceID` и своим `SpanID`
4. Цепочка продолжается до завершения запроса

**Стандарты propagation:**

- **W3C Trace Context** — современный стандарт (заголовки `traceparent`, `tracestate`)
- **B3 (Zipkin)** — заголовки `X-B3-TraceId`, `X-B3-SpanId`, `X-B3-ParentId`
- **Jaeger** — заголовок `uber-trace-id`

> **Важно:** Использование стандартного W3C Trace Context обеспечивает совместимость между различными инструментами трассировки.

### Сэмплирование (Sampling)

Сбор трассировок для *каждого* запроса избыточно дорог для высоконагруженных систем. Сэмплирование снижает нагрузку путём сбора данных только для доли запросов.

**Стратегии сэмплирования:**

| Стратегия | Описание | Когда использовать |
| :--- | :--- | :--- |
| **Вероятностное (Probabilistic)** | Сбор фиксированной доли запросов (например, 1% или 0.1%) | Постоянный сбор в продакшене |
| **На основе ошибок (Error-based)** | Сбор всех трейсов с ошибками + доля успешных | Расследование инцидентов |
| **Rate-limiting** | Сбор не более N трейсов в секунду | Ограничение нагрузки на хранилище |
| **Адаптивное (Adaptive)** | Динамическое изменение процента сэмплирования на основе нагрузки | Системы с переменной нагрузкой |

**Рекомендации:**

- Для высоконагруженных систем (>1000 RPS на сервис): 0.1–1%
- Для систем средней нагрузки: 5–10%
- Всегда собирать 100% трейсов с ошибками
- Хранить профили минимум 7 дней для анализа постфактум

### Корреляция с другими сигналами

**Корреляция трассировок с логами и метриками** — краеугольный камень современной observability-платформы.

**Типы корреляции:**

| Тип | Описание | Пример |
| :--- | :--- | :--- |
| **Trace → Logs** | Поиск всех логов по `trace_id` | В Loki: `{service="api"} \| json \| trace_id="abc123"` |
| **Metrics → Trace** | Переход от метрики к трейсу через exemplars | Клик по пику на графике latency → открытие трейса в Tempo |
| **Trace → Profile** | Анализ профиля сервиса за время выполнения трейса | Открытие CPU-профиля в Pyroscope за период трейса |

**Техническая реализация:**

- Все сигналы должны содержать общие идентификаторы: `trace_id`, `service_name`, `instance_id`
- Временные метки должны быть синхронизированы (NTP/Chrony)
- Инструменты визуализации (Grafana) должны быть настроены для кросс-сигнальных переходов

## Практические сценарии

### Сценарий 1: Поиск узкого места (bottleneck) в микросервисе

**Ситуация:** Пользователи жалуются на медленную загрузку страницы товара (p95 > 3с).

**Действия:**

| Шаг | Действие | Инструмент |
| :--- | :--- | :--- |
| **1** | Найти трейсы с длительностью > 3с | Tempo (TraceQL: `{.duration > 3s}`) |
| **2** | Открыть диаграмму Ганта для трейса | Tempo/Grafana |
| **3** | Найти самый длинный спан | Визуальный анализ (широкий блок) |
| **4** | Определить сервис и операцию | Например: `recommendation-service.getRecommendations()` (2.1с) |
| **5** | Проверить атрибуты спана: БД, внешний API | Атрибуты: `db.system=postgresql`, `db.statement=SELECT...` |
| **6** | Перейти к логам по `trace_id` | Loki: `{service="recommendation-service"} \| json \| trace_id="..."` |
| **7** | Выявить причину: медленный SQL | Лог: "Slow query: 2.0s — missing index on product_id" |

**Результат:** Добавлен индекс на таблицу `recommendations(product_id)`, задержка снижена до 200мс.

### Сценарий 2: Анализ каскадных ошибок

**Ситуация:** В продакшене периодически возникают ошибки 500 в API заказов.

**Действия:**

| Шаг | Действие | Инструмент |
| :--- | :--- | :--- |
| **1** | Отфильтровать трейсы с ошибками | Tempo (TraceQL: `{status = error}`) |
| **2** | Найти общий паттерн в ошибках | Анализ атрибутов: все ошибки в `payment-service.processPayment()` |
| **3** | Проверить спаны перед ошибкой | Предыдущий спан: `inventory-service.reserveItems()` — таймаут |
| **4** | Изучить логи по `trace_id` | Лог: "Connection timeout to inventory-db after 30s" |
| **5** | Проверить метрики БД | Prometheus: `pg_stat_activity` — блокировки |
| **6** | Выявить корневую причину | Долгая транзакция блокирует таблицу `inventory` |

**Результат:** Оптимизирован запрос в `inventory-service`, добавлены индексы, таймауты настроены корректно.

### Сценарий 3: Настройка сэмплирования для высоконагруженной системы

**Ситуация:** Система обрабатывает 10 000 RPS, хранилище трассировок переполняется.

**Решение:** Настроить многоуровневое сэмплирование в OTel Collector.

**Конфигурация OTel Collector:**

```yaml
processors:
  probabilistic_sampler:
    sampling_percentage: 1  # 1% для обычных запросов
  
  # Всегда собирать ошибки
  span_filter:
    error_mode: always_sample
  
  # Rate limiting для защиты хранилища
  tail_sampling:
    policies:
      - name: error-policy
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: slow-traces
        type: latency
        latency:
          threshold_ms: 5000
      - name: default-sample
        type: probabilistic
        probabilistic:
          sampling_percentage: 0.5

exporters:
  otlp/tempo:
    endpoint: tempo:4317
```

**Результат:**

- Нагрузка на хранилище снижена в 100 раз
- Собираются 100% ошибок и медленных трейсов (>5с)
- 0.5% обычных запросов для статистики

### Сценарий 4: Корреляция метрик и трассировок через Exemplars

**Ситуация:** Нужно быстро переходить от графика метрик к конкретным трейсам.

**Решение:** Настроить Exemplars в Prometheus + Tempo.

**Конфигурация:**

1. **В приложении (Go + OTel):**

```go
// При записи метрики добавлять trace_id как exemplar
histogram.Observe(duration, attribute.String("trace_id", traceID))
```

1. **В Prometheus:**

```yaml
# Включить хранение exemplars
storage:
  tsdb:
    max_exemplars: 100000
```

1. **В Grafana:**

- Добавить datasource Prometheus с поддержкой exemplars
- Добавить datasource Tempo
- Настроить связь: при клике на exemplar открывать Tempo с `trace_id`

**Результат:** Клик по пику на графике latency → мгновенное открытие трейса в Tempo.

## Дополнительная информация

### Сравнение инструментов

| Инструмент | Тип | Хранилище | Масштабируемость | Интеграция |
| :--- | :--- | :--- | :--- | :--- |
| **Grafana Tempo** | Хранилище трассировок | S3/NFS (объектное) | Горизонтальная (микросервисная) | Grafana, Loki, Prometheus, Mimir |
| **Jaeger** | Полная платформа (сбор + хранение + UI) | Elasticsearch/Cassandra | Вертикальная + шардирование | Самостоятельный UI, интеграции через API |
| **Zipkin** | Хранилище трассировок | MySQL/Elasticsearch/Cassandra | Ограниченная | Интеграции через API |
| **AWS X-Ray** | Managed-сервис | DynamoDB (управляемое) | Автоматическая (AWS) | AWS Console, CloudWatch |
| **Datadog APM** | SaaS | Proprietary (управляемое) | Автоматическая | Datadog Platform |

### Язык запросов TraceQL (Tempo)

**TraceQL** — язык запросов для поиска и фильтрации трассировок в Tempo.

**Примеры запросов:**

| Запрос | Описание |
| :--- | :--- |
| `{.duration > 2s}` | Трейсы длительностью более 2 секунд |
| `{status = error}` | Все трейсы с ошибками |
| `{service.name = "payment-service"}` | Трейсы конкретного сервиса |
| `{span.attributes.http.status_code = 500}` | Трейсы с HTTP 500 |
| `{.duration > 1s} && {status = error}` | Комбинированный запрос: медленные ошибки |
| `select duration, service.name by service.name` | Агрегация по сервисам |

### Лучшие практики

1. **Внедряйте трассировки на ранних этапах** — проще добавить инструментирование при разработке, чем рефакторить продакшен-код.

2. **Используйте стандартные атрибуты** — следуйте [OpenTelemetry Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/) для имён атрибутов (`http.method`, `db.system`, `net.peer.name`).

3. **Настройте сэмплирование до продакшена** — без сэмплирования хранилище переполнится при высокой нагрузке.

4. **Обеспечьте сквозную передачу контекста** — все сервисы должны передавать `traceparent` заголовки, включая асинхронные вызовы (очереди, события).

5. **Коррелируйте с логами и метриками** — без корреляции трассировки теряют значительную часть ценности.

6. **Храните трассировки минимум 7 дней** — это позволяет анализировать проблемы постфактум, включая инциденты в выходные.

7. **Настройте алерты на аномалии в трассировках** — например, резкий рост доли ошибок или увеличение latency определённого спана.
