# Мета-мониторинг: Мониторинг систем мониторинга

## Определения

**Мета-мониторинг (Meta-monitoring)** — стратегия и набор инструментов для контроля работоспособности самой системы наблюдаемости (Observability). Основная задача — гарантировать, что при выходе из строя основной системы мониторинга или сбое в цепочке доставки уведомлений, ответственные инженеры будут оповещены через независимые каналы.

**Основные термины:**
- **Self-monitoring (Самомониторинг):** Способность инструмента наблюдать за собственными внутренними показателями (использование кучи/heap, задержки очередей, ошибки парсинга, количество активных временных рядов).
- **Dead Man's Switch (Переключатель мертвеца):** Механизм инвертированного алертинга, который срабатывает при *отсутствии* ожидаемого сигнала (heartbeat) в течение заданного интервала.
- **External Watchdog (Внешний наблюдатель):** Независимая система или сервис (часто SaaS), проверяющая доступность основной системы мониторинга извне.
- **Heartbeat (Сердцебиение):** Регулярный сигнал («keep-alive»), отправляемый компонентом для подтверждения своей жизнеспособности. Теоретические основы механизмов описаны в разделе **[Механизмы Failover и Heartbeat](../High_Availability/ha_failover_mechanisms.md)**.
- **Ingestion Lag (Задержка приема):** Время между моментом возникновения события в источнике и моментом его доступности для запроса в TSDB. Критичный показатель для мета-мониторинга.

## Базовые концепции

### Причины отказа систем мониторинга

Система мониторинга — это высоконагруженное распределенное приложение, подверженное специфическим рискам:
1.  **Переполнение хранилища (Disk Full):** TSDB (Prometheus, VictoriaMetrics, ClickHouse) переходят в режим `read-only` или аварийно завершаются при нехватке места.
2.  **Сетевая изоляция (Network Partition):** Агенты сбора (exporters) доступны, но сервер мониторинга отрезан от сети или системы уведомлений (Slack, PagerDuty).
3.  **Cardinality Explosion (Взрыв кардинальности):** Резкий рост уникальных меток (например, из-за записи IP-адресов клиентов в лейблы) приводит к перерасходу RAM и OOM (Out of Memory).
4.  **Silent Failure (Тихий отказ):** Процесс мониторинга работает, но данные не собираются из-за зависания Service Discovery (например, проблемы с API Kubernetes).
5.  **Ложные сайленсы (Silences):** Ошибочно настроенное правило подавления алертов может "заглушить" критические инциденты на неопределенный срок.

### Иерархия мета-мониторинга

Кто мониторит мониторинг?
- **Уровень 1 (Внутренний):** Экспорт метрик рантайма (Go metrics, GC, Goroutines) и прикладных метрик самого сервера.
- **Уровень 2 (Перекрестный):** Кластеры мониторинга в разных зонах доступности следят друг за другом. Например, Prometheus в `Region-A` опрашивает `/metrics` у Prometheus в `Region-B`.
- **Уровень 3 (Внешний):** Легковесные скрипты (AWS Lambda, Google Cloud Functions) или сторонние сервисы (Grafana OnCall, Healthchecks.io), проверяющие только факт прохождения алертов.

## Архитектурные подходы

### 1. Watchdog Alert (Dead Man's Switch)
Самый надежный метод проверки всей цепочки: `Data Source → Alert Rule → Alertmanager → Notification Provider`.
1.  В системе мониторинга создается алерт с условием, которое *всегда* истинно (например, `vector(1)`).
2.  Этот алерт отправляется во внешнюю систему раз в N минут.
3.  Если внешняя система не получает уведомление в течение окна ожидания (например, 5 минут), она инициирует инцидент через независимый канал (SMS, звонок, Telegram через другого бота).

### 2. Мультирегиональный Cross-monitoring
В распределенных инфраструктурах используется схема «кольцевого» мониторинга:
- **Узел A** мониторит **Узел B**.
- **Узел B** мониторит **Узел C**.
- **Узел C** мониторит **Узел A**.
Это исключает ситуацию, когда мониторинг всей инфраструктуры "ослепнет" из-за падения одной центральной точки.

### 3. Мониторинг пайплайна уведомлений
Важно отслеживать не только наличие данных, но и настройки Alertmanager:
- **Silences Monitoring:** Сбор метрик о количестве активных сайленсов (`alertmanager_silences_active`). Аномальное количество сайленсов — повод для проверки.
- **Inhibition Monitoring:** Проверка того, что правила подавления (Inhibition rules) не блокируют важные алерты из-за широких селекторов.
- **Integration Health:** Отслеживание ошибок HTTP-запросов к провайдерам уведомлений (Pushover, Webhooks).

## Практические сценарии

### Сценарий 1: Watchdog в Prometheus
Настройка алерта, подтверждающего работоспособность пайплайна.

**Правило в Prometheus:**
```yaml
groups:
- name: meta-monitoring
  rules:
  - alert: Watchdog
    expr: vector(1)
    for: 1m
    labels:
      severity: critical
      meta_target: healthchecks_io
    annotations:
      summary: "Healthcheck heartbeat for external monitoring"
```

**Конфигурация Alertmanager:**
Алерт `Watchdog` направляется через Webhook на эндпоинт внешнего сервиса (например, `https://hc-ping.com/<uuid>`).

### Сценарий 2: Самомониторинг VictoriaMetrics (vmagent)
`vmagent` — эффективный сборщик, который должен мониторить себя сам для предотвращения потери данных при Remote Write.

**Ключевые метрики для алертинга:**
- `vm_rpc_errors_total`: Ошибки передачи данных между компонентами.
- `vmagent_remotewrite_queues_filled_percentage`: Заполнение очередей на отправку. Если 100% — данные начинают теряться.
- `vmagent_remotewrite_dropped_rows_total`: Прямой показатель потери данных из-за невозможности отправить их в хранилище.

### Сценарий 3: Самомониторинг Zabbix
Zabbix использует [Internal checks](../../Zabbix/zabbix_troubleshooting_and_performance_tuning.md) для контроля внутренних процессов:
- `zabbix[process,poller,avg,busy]`: Загрузка поллеров.
- `zabbix[wcache,values,avg]`: Скорость записи значений в БД.

**Критический триггер:** `Zabbix queue is too large` — указывает на то, что время обработки метрик превышает скорость их поступления (Bottle-neck в БД или нехватка воркеров).

## Дополнительная информация

### Чек-лист мета-мониторинга
- [ ] Настроен "Watchdog" алерт с проверкой внешней системой (Dead Man's Switch).
- [ ] Мониторится свободное место на дисках всех узлов TSDB и лог-агрегаторов.
- [ ] Настроены алерты на `up == 0` для всех критических экспортеров и агентов.
- [ ] Отслеживается `Ingestion Lag` (задержка появления данных).
- [ ] Мониторится количество активных сайленсов в Alertmanager.
- [ ] Проверяется лимит открытых дескрипторов файлов (`fd_utilization`) для процессов мониторинга.

### SLO для системы мониторинга
Для критических систем рекомендуется внедрять Service Level Objectives (SLO) на сам мониторинг:
- **Availability:** 99.9% времени сервер мониторинга должен отвечать на запросы.
- **Alert Latency:** 95% алертов должны быть доставлены провайдеру уведомлений в течение 30 секунд после срабатывания правила.
- **Data Freshness:** 99% метрик должны иметь возраст не более 60 секунд.
