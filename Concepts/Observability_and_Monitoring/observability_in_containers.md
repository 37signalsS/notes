# Наблюдаемость в контейнерах

## Определения

**Наблюдаемость в контейнерах** — практика обеспечения видимости состояния контейнеризированных приложений и оркестраторов (Docker, Kubernetes), учитывающая их специфические характеристики: изоляцию, динамичность жизненного цикла и распределённую природу.

**Ключевая особенность:** В отличие от традиционных систем, контейнеры требуют автоматизированного сбора телеметрии через механизмы оркестратора и специализированные паттерны (например, sidecar).

## Базовые концепции

### Ключевые вызовы

| Вызов | Описание | Решение |
| :--- | :--- | :--- |
| **«Чёрные ящики»** | Контейнеры изолированы, традиционные методы (SSH, агенты на хосте) ограничены | Сбор телеметрии через оркестратор, sidecar-контейнеры, eBPF |
| **Динамичность** | Короткий жизненный цикл, частые пересоздания | Service Discovery, привязка меток к метаданным пода/контейнера |
| **Мультитенантность** | Соседство контейнеров разных команд на одном узле | Изоляция через labels, namespaces, tenant ID |
| **Эфемерность логов** | Логи теряются при перезапуске контейнера | Централизованный сбор в реальном времени (stdout/stderr) |

### Механизмы обеспечения наблюдаемости

#### 1. Проверки состояния (Probes)

В Kubernetes пробы являются механизмом самоисцеления и управления трафиком, предоставляя базовый уровень наблюдаемости за здоровьем процесса.

| Тип пробы | Назначение | Реакция на сбой |
| :--- | :--- | :--- |
| **`livenessProbe`** | Проверка, что приложение работает и не зависло | Перезапуск контейнера |
| **`readinessProbe`** | Проверка готовности принимать трафик | Исключение из Service |
| **`startupProbe`** | Защита медленно стартующих приложений | Отключение других проб до успеха |

Подробное описание механизмов и параметров настройки приведено в SSoT **[Пробы (Probes)](../../../Kubernetes/Base/probes.md)**.

#### 2. Sidecar-контейнеры для телеметрии

Sidecar-паттерн предполагает запуск вспомогательного контейнера в том же поде для сбора логов, метрик или трассировок без изменения кода основного приложения.

**Преимущества:**

- Общее сетевое пространство (Network Namespace) и тома (Volumes).
- Изоляция ответственности: приложение занимается бизнесом, агент — телеметрией.

Реализации и примеры использования описаны в SSoT **[Sidecar-паттерн](../../../Kubernetes/Base/Pod/pod_sidecar_patterns.md)** и **[Прокси-сайдкары в Service Mesh](../../../Service_Mesh/proxy_sidecar.md)**.

#### 3. Стандартизация через OpenTelemetry

**[OpenTelemetry](../../../OpenTelemetry/opentelemetry_overview.md)** является отраслевым стандартом инструментирования для сбора метрик, трассировок и логов в Cloud Native средах.

**Возможности:**

- Автоматическое инструментирование популярных фреймворков.
- Контекстная корреляция через сквозные идентификаторы.
- Унифицированный экспорт данных в различные бэкенды.

## Практические сценарии

### Сценарий 1: Алертинг для Kubernetes-приложений

Критически важные события, которые должны отслеживаться в контейнеризированной среде:

| Метрика | Выражение (PromQL) | Порог | Описание |
| :--- | :--- | :--- | :--- |
| **Перезапуск контейнера** | `increase(kube_pod_container_status_restarts_total[5m]) > 0` | > 0 | Раннее обнаружение нестабильности |
| **OOM Killed** | `kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1` | 1 | Нехватка выделенной памяти |
| **Недоступность реплик** | `< 90%` доступных реплик | < 90% | Деградация масштабируемости |

Дополнительные рекомендации по алертингу: **[Рекомендации по мониторингу и алертингу](./monitoring_alerting_recommendations.md)**.

### Сценарий 2: Сбор логов через sidecar (Fluent Bit)

Используется, когда приложение пишет логи в локальные файлы, а не в stdout.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-logging
spec:
  volumes:
  - name: logs
    emptyDir: {}
  containers:
  - name: app
    image: my-app:1.0
    volumeMounts:
    - name: logs
      mountPath: /var/log/app
  - name: sidecar
    image: fluent/fluent-bit:latest
    volumeMounts:
    - name: logs
      mountPath: /var/log/app
```

### Сценарий 3: Корреляция данных при инциденте

Алгоритм расследования задержки (latency) в кластере:

1. **Метрики:** Проверка `p99 latency` и состояния подов (`kubectl get pods`).
2. **События:** Анализ `kubectl get events` на предмет ошибок проб или OOM.
3. **Трассировки:** Поиск проблемного пути в Tempo/Jaeger.
4. **Логи:** Извлечение детальной ошибки по `trace_id` в Loki.
5. **Профилирование:** Поиск «горячих» функций в Pyroscope при аномальном потреблении CPU.
