# Наблюдаемость в контейнерах

## Определения

**Наблюдаемость в контейнерах (Container Observability)** — практика обеспечения видимости состояния контейнеризированных приложений и оркестраторов (Docker, Kubernetes), учитывающая их специфические характеристики: изоляцию, динамичность жизненного цикла и распределённую природу.

**Нативный сайдкар (Native Sidecar)** — механизм Kubernetes (1.29+), позволяющий определять вспомогательные контейнеры (логи, прокси, метрики) внутри блока `initContainers` с типом `restartPolicy: Always`. Это гарантирует запуск агентов *до* основного приложения и их корректное завершение.

**Эфемерный контейнер (Ephemeral Container)** — временный контейнер, запускаемый внутри существующего пода для отладки («живая» диагностика) без перезапуска основного приложения. Позволяет использовать инструменты (tcpdump, gdb) в `distroless` образах.

**Ключевая особенность:** В отличие от традиционных систем, контейнеры требуют автоматизированного сбора телеметрии через механизмы оркестратора, так как доступ к внутреннему состоянию процесса ограничен границами изоляции (namespaces, cgroups).

## Базовые концепции

### Ключевые вызовы

| Вызов | Описание | Решение |
| :--- | :--- | :--- |
| **Изоляция («Чёрные ящики»)** | Контейнеры изолированы; традиционные методы (SSH) неудобны или небезопасны. | Сбор телеметрии через stdout/stderr, sidecar-агенты, eBPF-инструментацию. |
| **Динамичность** | Короткий жизненный цикл, частые пересоздания подов. | Автоматический Service Discovery, обогащение метрик метаданными (Pod Name, Namespace). |
| **Эфемерность данных** | Логи и локальные файлы теряются при удалении контейнера. | Централизованный сбор в реальном времени во внешние хранилища (Loki, ClickHouse). |
| **Высокая кардинальность** | Огромное количество эфемерных сущностей порождает взрывной рост временных рядов. | Агрегация на уровне агентов, использование высокопроизводительных TSDB (VictoriaMetrics, Mimir). |

### Механизмы обеспечения наблюдаемости

#### 1. Проверки состояния (Probes)

В Kubernetes пробы являются механизмом самоисцеления и предоставляют базовый уровень наблюдаемости за «здоровьем» процесса.

| Тип пробы | Назначение | Реакция на сбой |
| :--- | :--- | :--- |
| **`livenessProbe`** | Проверка, что приложение не «зависло». | Перезапуск контейнера. |
| **`readinessProbe`** | Готовность принимать входящий трафик. | Исключение из Service (Endpoint). |
| **`startupProbe`** | Защита медленно стартующих приложений. | Блокировка остальных проб до первого успеха. |

Подробное описание параметров приведено в SSoT **[Пробы (Probes)](../../Kubernetes/Base/probes.md)**.

#### 2. Мониторинг ресурсов (Cgroups v2)

В 2026 году мониторинг ресурсов базируется на **Cgroups v2**, что позволяет получать данные о давлении на систему через **[PSI (Pressure Stall Information)](../../Linux/Core/kernel/psi.md)**.
- **CPU Throttling:** Отслеживание метрики `container_cpu_cfs_throttled_seconds_total`. Троттлинг может происходить при утилизации < 100%, если лимиты установлены слишком жестко для многопоточных приложений.
- **Memory Saturation:** Отслеживание разницы между `rss` и `working_set_bytes`. Именно `working_set` является триггером для OOMKiller.

#### 3. Стратегии сбора логов

| Паттерн | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **DaemonSet (Node-level)** | Агент на каждой ноде читает логи из `/var/log/pods`. | Максимальная эффективность, минимальный оверхед. | Требует `hostPath` доступа (риск безопасности). |
| **Sidecar (Pod-level)** | Агент внутри пода (рекомендуется **Native Sidecar**). | Изоляция логов, возможность сложной обработки. | Значительное потребление ресурсов при масштабировании. |
| **Direct Shipping** | Приложение само отправляет логи по сети (OTLP). | Не требует агентов в кластере. | Риск потери логов при сбоях сети; нагрузка на основное приложение. |

#### 4. Sidecar-паттерн и нативные контейнеры

Sidecar-паттерн предполагает запуск вспомогательного контейнера в том же поде для сбора телеметрии или проксирования.
- **Классический Sidecar:** Запускается параллельно с основным. Есть риск, что приложение начнет писать логи до старта агента.
- **Native Sidecar (K8s 1.29+):** Определяется в `initContainers` с `restartPolicy: Always`. Гарантирует, что агент (например, прокси или лог-коллектор) будет готов *до* запуска приложения.

Подробнее: **[Sidecar-паттерн](../../Kubernetes/Base/Pod/pod_sidecar_patterns.md)** и **[Прокси-сайдкары в Service Mesh](../../Service_Mesh/proxy_sidecar.md)**.

#### 5. Наблюдаемость через eBPF (Sidecar-less)

**eBPF** позволяет собирать глубокую телеметрию напрямую из ядра Linux, не изменяя код приложения.
- **Deep Visibility:** Видимость сетевых потоков L7 (HTTP, gRPC) и системных вызовов без внедрения Service Mesh.
- **Инструменты:** **Hubble/Cilium** (сеть), **Falco** (безопасность), **Parca/Pyroscope** (профилирование).

Подробнее: **[eBPF — виртуальная машина ядра](../../Linux/Core/kernel/ebpf.md)**.

#### 6. Стандартизация через OpenTelemetry

**[OpenTelemetry (OTel)](../../OpenTelemetry/opentelemetry_overview.md)** — современный стандарт сбора всех типов данных. В контейнерных средах OTel Collector выступает центральным звеном, агрегируя данные и отправляя их в Tempo, Loki и Prometheus.

## Практические сценарии

### Сценарий 1: Расследование инцидента в кластере

Алгоритм действий при получении алерта о деградации сервиса:

1. **Метрики (RED/USE):** Проверка `p99 latency` и `error rate`. Анализ `container_memory_working_set_bytes`.
2. **События (Events):** `kubectl get events -n <namespace> --sort-by='.metadata.creationTimestamp'` — поиск `OOMKilled` или сбоев проб.
3. **Трассировки (Traces):** Поиск конкретного `trace_id` в Tempo для выявления задержки в цепочке микросервисов.
4. **Логи (Logs):** Поиск детальной ошибки в Loki по `trace_id`.
5. **Профилирование (Profiling):** Если причина в потреблении CPU кодом — анализ Flame Graphs в Pyroscope.

**Валидация:**
- Убедиться, что `trace_id` присутствует во всех сигналах для корректной корреляции.
- Проверить соответствие меток (labels) между метриками пода и его логами.

### Сценарий 2: Отладка пода через Ephemeral Containers

Используется для диагностики «живых» подов без их перезапуска.

**Команда:**
```bash
kubectl debug -it <pod-name> --image=nicolaka/netshoot --target=<container-name>
```
*Внутри контейнера доступны tcpdump, curl, dig, htop для анализа окружения основного процесса.*

### Сценарий 3: Сбор логов через Native Sidecar

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-native-logging
spec:
  volumes:
  - name: shared-logs
    emptyDir: {}
  initContainers:
  - name: logging-agent
    image: fluent/fluent-bit:3.2.0
    restartPolicy: Always # Делает init-контейнер нативным сайдкаром
    volumeMounts:
    - name: shared-logs
      mountPath: /var/log/app
  containers:
  - name: app
    image: my-app:1.5.0
    volumeMounts:
    - name: shared-logs
      mountPath: /var/log/app
```

## Диагностика и устранение неполадок

| Проблема | Причина по метрикам | Решение |
| :--- | :--- | :--- |
| **Скрытый троттлинг** | Рост `throttled_seconds` при CPU < 100% | Увеличить CPU Limits или использовать `CPU Burst` (если поддерживается). |
| **OOMKilled** | `working_set_bytes` достигает лимита | Проверить на утечки памяти в рантайме. Увеличить лимиты RAM. |
| **Пропуски в логах** | Переполнение буфера `stdout` | Увеличить ресурсы агента сбора (Fluent Bit/Vector). Использовать дисковую буферизацию. |
| **Высокая латентность сети** | Высокий `drop` пакетов в метриках CNI | Проверить NetworkPolicy. Использовать eBPF (Cilium/Hubble) для визуализации затыков. |
