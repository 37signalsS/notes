# Проектирование высоконагруженного мониторинга в распределённых системах

## Определения

**Высоконагруженный мониторинг (High-Load Monitoring)** — архитектура системы наблюдаемости, спроектированная для обработки миллионов метрик в секунду (TPS), терабайт логов и миллиардов спанов трассировки. Основная задача такой архитектуры — обеспечить масштабируемость, отказоустойчивость и низкую задержку при обработке телеметрии без превращения стека мониторинга в «бутылочное горлышко» для основной системы.

**Ключевой принцип:** Разделение уровней сбора (Collection), транспортировки (Transport), обработки (Processing) и хранения (Storage).

**См. также:**

- **[Определения Observability](./observability_definitions.md)** — базовые понятия мониторинга и наблюдаемости.
- **[Четыре столпа Observability](./four_pillars_of_observability.md)** — фундаментальные принципы телеметрии.

## Базовые концепции

### 1. Транспорт и буферизация: Kafka

В высоконагруженных системах прямой «пуш» логов или метрик в хранилище опасен потерей данных при всплесках нагрузки (bursts). **Apache Kafka** выступает в роли демпфера.

- **KRaft Mode:** Современный стандарт работы Kafka без ZooKeeper, упрощающий эксплуатацию.
- **Backpressure:** Позволяет консьюмерам (например, Vector или Logstash) вычитывать данные с той скоростью, с которой они способны их обработать.
- **Гарантии доставки:** Настройка `acks=all` и репликации обеспечивает сохранность критически важных аудитных логов.

Подробнее: **[Kafka для мониторинга](../../Kafka/kafka_for_monitoring.md)**.

### 2. Сбор метрик: Prometheus Agent Mode

Для снижения нагрузки на память и диск на «краях» инфраструктуры (Edge/Clusters) рекомендуется использовать **Prometheus Agent Mode** (флаг `--enable-feature=agent`).

- **Stateless:** Агент не хранит данные локально (кроме краткосрочного буфера на диске).
- **Remote Write:** Все собранные метрики немедленно пересылаются в централизованное хранилище по протоколу Prometheus Remote Write.
- **Экономия ресурсов:** Потребляет значительно меньше оперативной памяти по сравнению со стандартным сервером Prometheus.

### 3. Унифицированный сбор: Grafana Alloy

**Grafana Alloy** — наследник Grafana Agent, универсальный коллектор для всех сигналов (метрик, логов, трейсов, профилей).

- **Компонентная архитектура:** Позволяет строить сложные конвейеры обработки данных (Pipelines) декларативно.
- **Совместимость:** Поддерживает форматы Prometheus, OpenTelemetry, Pyroscope и др.
- **Native OTLP:** Полная поддержка протокола OpenTelemetry из коробки.

### 4. Долгосрочное хранение: Remote Write и LTS

Для хранения огромных объемов данных используются системы Long-Term Storage (LTS), построенные на базе объектных хранилищ (S3, GCS, Azure Blob).

| Решение | Особенности |
| :--- | :--- |
| **[Grafana Mimir](../../Mimir/mimir_overview.md)** | Лидер по масштабируемости, нативная поддержка мульти-тенантности. |
| **[VictoriaMetrics](../../VictoriaMetrics/overview.md)** | Экстремальная производительность и плотность упаковки данных. |
| **Thanos** | Идеально для объединения множества разрозненных Prometheus в единое вью (Global View). |

## Практические сценарии

### Архитектура распределенной наблюдаемости (Modern Stack)

Современная схема построения глобальной системы для крупной компании:

| Уровень | Технология | Роль |
| :--- | :--- | :--- |
| **Edge (Clusters)** | **Grafana Alloy** + **Prometheus Agent** | Сбор телеметрии методом Pull/Push, базовая фильтрация. |
| **Transport** | **Kafka (KRaft)** | Буферизация логов и высокоинтенсивных событий. |
| **Processing** | **Vector** | Парсинг JSON, маскирование PII, маршрутизация в разные БД. |
| **Storage (Metrics)** | **Grafana Mimir** | Глобальная агрегация, хранение в S3, дедупликация. |
| **Storage (Logs)** | **Grafana Loki** | Хранение логов с индексацией только метаданных. |
| **Storage (Traces)** | **Grafana Tempo** | Масштабируемое хранилище трейсов в объектном хранилище. |
| **UI / Alerting** | **Grafana** + **Alertmanager** | Единая консоль управления инцидентами. |

### Шардирование сбора данных (Sharding)

При мониторинге кластеров с десятками тысяч подов один инстанс Prometheus/Alloy не справится. Решение — шардирование целей скрейпинга.

- **Hash-based sharding:** Распределение целей между N коллекторами на основе хеша от лейбла инстанса.
- **Prometheus Operator:** В Kubernetes шардирование настраивается параметром `shards` в ресурсе `Prometheus`.

## Дополнительная информация

### Выбор протокола: OpenTelemetry (OTLP)

Рекомендуется переходить на протокол **OTLP** для передачи всех видов сигналов. Это обеспечивает:
- **Единый транспорт:** Один порт/протокол для логов, метрик и трейсов.
- **Correlation:** Нативная поддержка связей между сигналами через общие контексты.
- **Vendor Neutrality:** Легкая смена бэкенда хранения без изменения кода приложений.
