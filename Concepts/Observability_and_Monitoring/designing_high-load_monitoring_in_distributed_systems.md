# Проектирование высоконагруженного мониторинга в распределенных системах

## Определения

**Высоконагруженный мониторинг в распределенных системах** — это процесс проектирования и эксплуатации системы наблюдаемости, способной надежно собирать, обрабатывать, хранить и анализировать большие объемы телеметрических данных (метрики, логи, трассировки) от множества географически или логически распределенных компонентов. Цель такой системы — обеспечить отказоустойчивость, масштабируемость и производительность самого стека мониторинга, предотвращая его превращение в единую точку отказа.

Для построения эффективной системы необходимо понимать фундаментальные концепции. Основные понятия, такие как **Метрики, Логи, Трассировки и Профилирование**, подробно рассмотрены в основной заметке **[Обзор Мониторинга и Observability](observability_overview.md)**.

## Базовые концепции и компоненты

### Транспорт и буферизация данных: Kafka

В высоконагруженных системах прямой сбор данных, особенно логов, от тысяч источников к единому хранилищу ненадёжен. **[Kafka](../../Kafka/kafka_for_monitoring.md)** используется как отказоустойчивый распределенный буфер.

* **Назначение**: Принимает на себя пиковые нагрузки, предотвращая потерю данных при временной недоступности компонентов системы мониторинга. Агенты (продюсеры) отправляют данные в Kafka, а системы хранения (консьюмеры) вычитывают их в своем темпе.
* **Ключевые концепции**:
  * **Топик (Topic)**: Именованный поток данных (например, `prod-app-logs`).
  * **Партиция (Partition)**: Часть топика, обеспечивающая параллелизм. Количество партиций определяет максимальное количество параллельных консьюмеров.
  * **Репликация**: Копии партиций на разных брокерах для отказоустойчивости.
* **Рекомендации**:
  * Использовать современные версии **[Kafka с KRaft](../../Kafka/kafka_for_monitoring.md#kraft-vs-zookeeper-современный-стандарт-для-kafka)** (без ZooKeeper) для упрощения архитектуры и повышения надежности.
  * Заранее планировать количество партиций, так как его нельзя изменить без пересоздания топика.
  * Для доставки логов в Kafka применять легковесные агенты: Vector, Fluent Bit.

### Сбор и обработка метрик: Prometheus

**[Prometheus](../../Prometheus/overview.md)** является промышленным стандартом для сбора метрик в Cloud Native средах.

* **Модель сбора**: Преимущественно используется **pull-модель**, при которой Prometheus сам опрашивает цели (экспортеры). Это делает источники данных независимыми от доступности системы мониторинга. Для кратковременных задач (batch jobs) используется **push-модель** через **[Pushgateway](../../Prometheus/pushgateway.md)**.
* **[Архитектура](../../Prometheus/overview.md#архитектура)**: Состоит из сервера Prometheus (сбор, хранение, обработка), **[экспортеров](../../Prometheus/Exporters/overview.md)** (преобразование метрик), механизмов **[Service Discovery](../../Prometheus/service_discovery_and_relabeling.md)** и **[Alertmanager](../../Prometheus/alertmanager.md)** (оповещения).
* **Федерация**: **[Федерация Prometheus](../../Prometheus/scaling/federation.md)** позволяет создавать иерархическую структуру, где один сервер агрегирует данные с других, что полезно для объединения метрик из разных контуров.

### Долгосрочное хранение метрик: Remote Storage

Встроенное хранилище Prometheus (TSDB) не предназначено для долгосрочного хранения данных и горизонтального масштабирования. Эту задачу решают внешние хранилища.

* **Проблема**: Локальный Prometheus имеет ограниченный срок хранения (retention) и является единой точкой отказа для исторических данных.
* **Решения (Remote Storage)**:
  * **[Mimir](../../Mimir/mimir_overview.md)**: Горизонтально масштабируемое, мульти-тенантное решение от Grafana Labs. Считается предпочтительным выбором для построения глобальной, отказоустойчивой системы.
  * **[VictoriaMetrics](../../VictoriaMetrics/overview.md)**: Высокопроизводительная альтернатива, известная своей эффективностью по использованию ресурсов и простотой в настройке.
  * **Thanos**: Расширение для Prometheus, использующее S3-совместимые объектные хранилища (Ceph, MinIO) для долгосрочного хранения.
* **Принцип работы**: Локальные экземпляры Prometheus настраиваются на короткий `retention` (например, 2-6 часов) и пересылают все метрики через `remote_write` в централизованное хранилище.

### Визуализация и оповещения: Grafana и Alertmanager

* **[Grafana](../../Grafana/grafana_overview.md)**: Стандарт де-факто для визуализации данных из различных источников (Prometheus, Mimir, Loki и др.).
  * **Высокая доступность**: Для отказоустойчивости Grafana разворачивается в кластере за балансировщиком нагрузки, а ее конфигурация (дашборды, источники данных) хранится во внешней реляционной БД (например, PostgreSQL), а не в SQLite. Подробнее см. **[Grafana High Availability](../../Grafana/high_availability.md)**.
* **[Alertmanager](../../Prometheus/alertmanager.md)**: Принимает оповещения от Prometheus и управляет ими.
  * **Функции**: Группировка, дедупликация, подавление (silencing) и маршрутизация алертов в Slack, PagerDuty, email и т.д.
  * **Высокая доступность**: Alertmanager разворачивается в кластере и использует gossip-протокол для синхронизации состояния между экземплярами.

## Практический сценарий: Типовая архитектура

### Основные принципы

* **Распределенность**: Все компоненты системы мониторинга должны быть распределенными, масштабируемыми и отказоустойчивыми.
* **Асинхронность**: Для сбора и обработки больших потоков данных (особенно логов) используются асинхронные механизмы и буферы (Kafka).
* **Независимость**: Мониторируемые системы не должны зависеть от доступности системы мониторинга (достигается pull-моделью).
* **Дедупликация и агрегация**: Применяются на всех уровнях для снижения шума и экономии ресурсов.

### Схема развертывания

1. **Источники данных**: Приложения, инфраструктура, облачные сервисы.
2. **Сбор логов**: Легковесные агенты (Vector, Fluent Bit) собирают логи и отправляют их в Kafka.
3. **Транспорт логов**: Кластер Kafka (на KRaft) служит надежным буфером.
4. **Хранение логов**: [Loki](../../Loki/loki_overview.md) (для индексации по метаданным) или OpenSearch/Elasticsearch (для полнотекстового поиска).
5. **Сбор метрик**: Высокодоступные пары Prometheus-серверов (HA-пары) в каждом контуре/кластере. Они опрашивают экспортеры, локально хранят метрики очень короткое время (например, 2 часа) и отправляют их через `remote_write` в Mimir.
6. **Долгосрочное хранилище метрик**: Кластер Mimir агрегирует метрики со всех контуров, обеспечивая глобальное представление, мульти-тенатность и масштабирование.
7. **Оповещения**: Кластер Alertmanager обрабатывает алерты от всех Prometheus-серверов.
8. **Визуализация**: Кластер Grafana (с бэкендом на PostgreSQL) подключается к Mimir и Loki, предоставляя единый интерфейс для анализа.
9. **Экспортеры**: Специализированные экспортеры (`node-exporter`, `cAdvisor`, `kube-state-metrics` и др.) предоставляют метрики для Prometheus.

### Особенности эксплуатации

* **"Stateless" Prometheus**: Локальные серверы Prometheus становятся практически stateless, так как долгосрочно данные не хранят. Это упрощает их эксплуатацию и снижает последствия сбоя (теряются только данные за последние минуты, уже отправленные в Mimir).
* **Централизованная конфигурация**: Правила алертинга и записи (`recording rules`) управляются централизованно в Mimir/Thanos (компонент `Ruler`), а не на каждом локальном Prometheus.
