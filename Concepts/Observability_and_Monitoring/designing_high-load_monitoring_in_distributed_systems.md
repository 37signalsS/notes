**Актуально для:** Prometheus 3.13.x (LTS) / 3.14.x, Alertmanager 0.34.x, Grafana Alloy, OpenTelemetry Collector 0.162.x, VictoriaMetrics 1.52.x, Mimir, Loki 3.x, Tempo, Kafka 3.x, Vector 0.36.x, Zabbix 7.0 LTS / 7.4, node_exporter 1.12.x, blackbox_exporter 0.28.x

# Проектирование высоконагруженного мониторинга в распределённых системах

## Определения

**Высоконагруженный мониторинг (High-Load Monitoring)** — архитектура системы наблюдаемости, спроектированная для обработки миллионов метрик в секунду (TPS), терабайт логов и миллиардов спанов трассировки. Основная задача такой архитектуры — обеспечить масштабируемость, отказоустойчивость и низкую задержку при обработке телеметрии без превращения стека мониторинга в «бутылочное горлышко» для основной системы.

**Ключевой принцип:** Разделение уровней сбора (Collection), транспортировки (Transport), обработки (Processing) и хранения (Storage). Это позволяет масштабировать каждый компонент независимо и изолировать сбои в одной части системы от других.

**Кардинальность (Cardinality):** количество уникальных комбинаций меток (label set) в системе мониторинга. Каждая уникальная комбинация меток создает отдельный временной ряд (time series). Взрыв кардинальности (cardinality explosion) — резкий рост уникальных рядов — является одной из главных причин отказа высоконагруженных систем мониторинга.

**Контрольная точка (Checkpoint):** механизм сохранения промежуточного состояния пайплайна обработки данных (например, позиция чтения в Kafka или WAL). Позволяет возобновить обработку с момента последнего успешного сохранения после сбоя, а не начинать заново.

**См. также:**
- **[Определения Observability](./observability_definitions.md)** — базовые понятия мониторинга и наблюдаемости.
- **[Четыре столпа Observability](./four_pillars_of_observability.md)** — фундаментальные принципы телеметрии.

## Предварительные требования

Перед проектированием архитектуры высоконагруженного мониторинга необходимо:

- **Оценить объем телеметрии:** определить количество сервисов, экземпляров, метрик на экземпляр и частоту сбора.
- **Определить retention policy:** согласовать сроки хранения метрик, логов и трейсов с командой безопасности и compliance.
- **Выбрать зоны ответственности:** назначить владельцев для каждого `job_name`, пайплайна и алерта.
- **Подготовить сетевую инфраструктуру:** обеспечить маршрутизацию между сегментами (edge, transport, storage), открыть порты для OTLP/gRPC, Remote Write, Kafka.
- **Определить SLO для мониторинга:** например, 99.9% доставки метрик, <5s задержка алертинга, <1% потерь данных.

## Базовые концепции

### 1. Транспорт и буферизация: Kafka

В высоконагруженных системах прямой «пуш» логов или метрик в хранилище опасен потерей данных при всплесках нагрузки (bursts). **Apache Kafka** выступает в роли персистентного демпфера.

- **Декаплинг (Decoupling):** Источники данных не зависят от производительности или доступности хранилища (TSDB).
- **Backpressure:** Позволяет консьюмерам (Vector, Alloy) вычитывать данные с той скоростью, с которой они способны их обработать, предотвращая перегрузку хранилища.
- **KRaft Mode:** Современный стандарт Kafka без ZooKeeper, упрощающий эксплуатацию.

**Практические пороги для Kafka в мониторинге:**

| Метрика | Допустимый порог | Действие |
| :--- | :--- | :--- |
| `consumer_lag` | < 10,000 сообщений | Рост лага > 10K -- масштабировать consumer'ов |
| `under_replicated_partitions` | 0 | > 0 -- проверить доступность брокеров |
| `request_latency_avg` | < 100ms | Рост > 200ms -- проблема с диском/CPU брокера |
| `log_flush_rate` | стабильный | Резкое падение -- проверить IOPS диска |

Подробнее: **[Kafka для мониторинга](../../Kafka/kafka_for_monitoring.md)**.

### 2. Сбор метрик: Stateless-агенты

Для снижения нагрузки на память и диск на «краях» инфраструктуры (Edge/Clusters) рекомендуется использовать **Prometheus Agent Mode** или **Grafana Alloy**.

- **Stateless:** Агенты не хранят данные локально (кроме краткосрочного WAL-буфера на диске).
- **Remote Write 2.0:** Основной протокол снижает трафик на **60%** за счет интернирования строк (String Interning) и пакетного сжатия.
- **Экономия ресурсов:** Потребляет на 30–50% меньше RAM по сравнению со стандартным сервером Prometheus.

**Рекомендуемые ресурсы агента:**

| Компонент | CPU | RAM | Disk (WAL) | Примечание |
| :--- | :--- | :--- | :--- | :--- |
| Prometheus Agent (10K серий) | 0.5 core | 512MB | 1GB SSD | Минимальный edge-кластер |
| Prometheus Agent (100K серий) | 2 cores | 2GB | 10GB SSD | Средний кластер на 100+ узлов |
| Grafana Alloy (100K серий) | 1 core | 1GB | 5GB SSD | Универсальный заменитель Prometheus Agent |
| OTel Collector (1M спанов/мин) | 4 cores | 4GB | 2GB SSD | Тяжелый трейсинг |

### 3. Унифицированный сбор: Grafana Alloy

**Grafana Alloy** — универсальный коллектор, заменяющий множество разрозненных экспортеров.

- **OTLP/Arrow:** Использование колоночного сжатия Apache Arrow для передачи телеметрии снижает нагрузку на сеть в 5-10 раз.
- **Компонентная архитектура:** Позволяет строить декларативные пайплайны обработки данных (фильтрация, релейблинг, маскирование) на уровне агента.

### 4. Масштабирование OTel Collector

OTel Collector является основным компонентом для обработки телеметрии в распределенных системах. Существует три основных паттерна развертывания:

**Паттерн 1: Agent (per-node)**
Каждый узел запускает свой экземпляр Collector. Данные не пересекают сетевые границы кластера.

```ini
# Пример: systemd-юнит для OTel Collector на каждом узле
# /etc/systemd/system/otel-collector-agent.service
[Unit]
Description=OpenTelemetry Collector Agent
After=network.target

[Service]
Type=simple
ExecStart=/usr/bin/otelcol-contrib --config /etc/otelcol/config.yaml
Restart=on-failure
RestartSec=5s
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```

```yaml
# /etc/otelcol/config.yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 5s
    send_batch_size: 10000
  memory_limiter:
    check_interval: 1s
    limit_mib: 512
    spike_limit_mib: 128

exporters:
  prometheusremotewrite:
    endpoint: "http://central-storage:9090/api/v1/write"
  otlp:
    endpoint: "http://central-storage:4317"

service:
  pipelines:
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [prometheusremotewrite, otlp]
```

**Паттерн 2: Gateway (centralized)**
Централизованный кластер Collector'ов для обработки, обогащения и маршрутизации. Принимает данные от Agent'ов через OTLP/gRPC.

**Паттерн 3: Hybrid (Agent + Gateway)**
Agent'ы выполняют базовую фильтрацию и batch, Gateway'и — тяжелую обработку (transform, routing, aggregation). Это рекомендуемый паттерн для систем >100K серий.

**Выбор паттерна:**

| Паттерн | Когда использовать | Пропускная способность | Сложность |
| :--- | :--- | :--- | :--- |
| **Agent** | Малые кластеры, edge | до 50K серий/узел | Низкая |
| **Gateway** | Централизованная обработка | до 5M серий/кластер | Средняя |
| **Hybrid** | Крупные кластеры, multi-tenant | >5M серий | Высокая |

### 5. Долгосрочное хранение: LTS на базе объектных хранилищ

Стандартом является хранение данных в объектных хранилищах (Stateless Storage).

| Решение | Особенности архитектуры |
| :--- | :--- |
| **[Grafana Mimir](../../Mimir/mimir_overview.md)** | Микросервисная архитектура, нативная мульти-тенантность. |
| **[VictoriaMetrics](../../VictoriaMetrics/overview.md)** | Экстремальная плотность упаковки, поддержка MetricsQL. |
| **Thanos** | Прозрачное расширение Prometheus для Global View через Sidecars/Query. |

**Рекомендации по retention:**

| Тип данных | Рекомендуемый retention | Хранилище |
| :--- | :--- | :--- |
| Метрики (hot) | 7-14 дней | Локальный диск (SSD) |
| Метрики (warm) | 30-90 дней | Объектное хранилище (Standard tier) |
| Метрики (cold) | 90-365 дней | Объектное хранилище (Archive tier) |
| Логи (hot) | 3-7 дней | Loki / Elasticsearch (hot node) |
| Логи (warm) | 30-90 дней | Loki (объектное хранилище) |
| Трейсы (hot) | 3-5 дней | Tempo / Jaeger (hot storage) |
| Трейсы (warm) | 7-30 дней | Tempo (объектное хранилище) |

## Управление кардинальностью

### Проблема

Каждая уникальная комбинация меток создает отдельный временной ряд. При 100 сервисах x 10 подов x 5 эндпоинтов x 100 меток = 5M серий. Рост потребления памяти пропорционален количеству серий.

### Формула расчета потребления памяти

```
RAM (MB) = active_series × bytes_per_series
```

Где:
- `active_series` -- количество уникальных серий (в метрике `prometheus_tsdb_head_series`)
- `bytes_per_series` -- ~6-8 байт на серию (включая хеш-таблицу и индексы)

**Пример:** 1M активных серий x 8 байт = ~8MB RAM только для индекса. С учетом значений и WAL: 1M серий x 1KB/сэмпл x 1 сэмпл/15сек = ~67MB/сек = ~2.4GB/час rawData.

### Стратегии контроля кардинальности

**1. Фильтрация на этапе скрейпинга (самый эффективный метод)**

```yaml
scrape_configs:
  - job_name: 'high-cardinality-app'
    metric_relabel_configs:
      # Удалить высоко-кардинальные метки ДО записи в TSDB
      - source_labels: [__name__]
        regex: 'http_request_duration_seconds_bucket'
        target_label: '__tmp_keep'
        action: labelmap
      - source_labels: [__tmp_keep]
        regex: ''
        action: drop
      # Удалить конкретные метки
      - regex: 'request_id|session_id|trace_id'
        action: labeldrop
```

**2. Recording rules для предварительной агрегации**

Вместо хранения сырых гистограмм с высокой кардинальностью используйте recording rules для предварительного вычисления перцентилей:

```yaml
groups:
  - name: cardinality_reduction
    rules:
      - record: job:api:p95_latency:rate5m
        expr: |
          histogram_quantile(0.95,
            sum(rate(http_request_duration_seconds_bucket{job="api"}[5m])) by (le, service)
          )
```

**3. Native Histograms (Prometheus 2.40+)**

Нативные гистограммы позволяют записывать распределение значений в один временной ряд вместо N серий для каждого bucket. Экономия места: до 40% по сравнению с классическими гистограммами.

**4. Мониторинг кардинальности**

```promql
# Количество активных серий по job
prometheus_tsdb_head_series

# Прогноз роста серий на 7 дней
predict_linear(prometheus_tsdb_head_series[1h], 7*24*3600)

# Серии с высокой кардинальностью (>10K уникальных значений)
count by (__name__) (group by (__name__, high_cardinality_label) (my_metric))
```

## Backpressure в пайплайне мониторинга

Backpressure возникает, когда потребитель (storage) не успевает обрабатывать данные от производителя (collection). В мониторинге это приводит к потере данных и пропущенным алертам.

### Паттерны управления Backpressure

**Паттерн 1: Kafka как буфер (рекомендуемый)**

```
Agents → Kafka (retention: 2h) → Consumers (Vector/Alloy) → Storage
```

- Kafka выступает в роли персистентного буфера.
- Consumer'ы вычитывают данные с собственной скоростью.
- Если Storage недоступен, данные остаются в Kafka (до истечения retention).

**Паттерн 2: Disk-based WAL**

```
Agents → WAL (local disk) → Remote Write → Storage
```

- Агенты пишут в локальный WAL.
- При недоступности хранилища WAL накапливает данные.
- При восстановлении связи агент отправляет данные из WAL (FIFO).

**Паттерн 3: Load Shedding (сброс нагрузки)**

При превышении порога нагрузки агент начинает отбрасывать менее важные данные:

```yaml
# Пример: Vector - отбрасывать debug-логи при высокой нагрузке
transforms:
  - type: filter
    inputs: [source]
    condition: |
      .level != "debug" || length(.message) < 1000
```

### Индикаторы Backpressure

| Метрика | Норма | Тревога | Действие |
| :--- | :--- | :--- | :--- |
| `kafka_consumer_lag` | < 1,000 | > 10,000 | Масштабировать consumer'ов |
| `prometheus_remote_storage_samples_pending` | < 1,000 | > 10,000 | Проверить доступность storage |
| `vector_buffer_usage` | < 70% | > 85% | Увеличить buffer или batch |
| `otelcol_exporter_send_failed_spans` | 0 | > 0 за 5мин | Проверить сеть/storage |

## Антипаттерны высоконагруженного мониторинга

| Антипаттерн | Описание | Решение |
| :--- | :--- | :--- |
| **Хранение всего в одном Prometheus** | Один сервер для сбора, хранения и алертинга. При росте -- OOM или потеря данных. | Разделить на Agent (сбор), LTS (хранение), Ruler (алертинг). |
| **Высокая кардинальность в метках** | Запись IP, UUID, session_id в лейблы. Взрыв серий, OOM. | Фильтрация через `metric_relabel_configs`, Native Histograms. |
| **Отсутствие Kafka/buffer** | Прямой Remote Write без промежуточного буфера. Потеря данных при сбое storage. | Добавить Kafka или disk-based WAL между Agent и Storage. |
| **Синхронная запись в объектное хранилище** | Каждый сэмпл записывается отдельно. Огромные задержки и стоимость. | Батчинг (batch) перед записью, использование SSD для hot данных. |
| **Игнорирование meta-monitoring** | Система мониторинга не мониторит сама себя. Тихий отказ. | Watchdog alert, Dead Man's Switch, внешний synthetics. |
| **Stale alerts** | Алерты на метрики, которые больше не существуют (удалены, переименованы). | Периодический аудит: `prometheus_invalid_metric_samples_total`. |
| **Hardcoded scrape_interval** | Одинаковый интервал скрейпинга для всех целей (15сек). Перегрузка при росте. | Дифференцированный scrape_interval: быстрые метрики (5сек), медленные (60сек). |
| **Отсутствие downsampling** | Хранение сырых данных >30 дней. Замедление запросов, рост стоимости. | Downsampling: 5мин для данных >7дней, 1ч для данных >90дней. |
| **Централизованный алертинг без redundancy** | Один Alertmanager, одна точка отказа. Потеря уведомлений при сбое. | Кластер Alertmanager (3+ узла), внешний Dead Man's Switch. |
| **Мониторинг без SLO** | Нет формальных целей по доступности мониторинга. Непонятно, «сколько хорошо». | Определить SLO для мониторинга (например, 99.9% доставки метрик). |

## Практические сценарии

### Сценарий 1: Архитектура распределенной наблюдаемости (Global Stack)

Современная схема построения системы для крупной компании:

| Уровень | Технология | Роль |
| :--- | :--- | :--- |
| **Edge** | **Grafana Alloy** | Сбор всех сигналов (OTLP), базовая фильтрация. |
| **Transport** | **Kafka (acks=all)** | Гарантированная доставка и буферизация. |
| **Processing** | **Vector** | Тяжелая обработка, обогащение контекстом, маршрутизация. |
| **Storage** | **Mimir / Loki / Tempo** | Горизонтально масштабируемое хранение в объектном хранилище. |

**Валидация:**
1. Проверить `consumer lag` в Kafka: рост лага указывает на нехватку ресурсов в слое Processing/Storage.
2. Проверить метрики Remote Write: `prometheus_remote_storage_samples_total` vs `vm_rows_inserted_total`.

### Сценарий 2: Шардирование сбора в сверхкрупных кластерах

При мониторинге >10,000 подов один инстанс агента не справится.

- **Hash-based sharding:** Распределение целей между N коллекторами на основе хеша от лейбла `__address__`.
- **Prometheus Operator:** Настройка через `spec.shards` в ресурсе Prometheus/Alloy.

**Валидация:**
Проверить равномерность распределения: `count by (shard) (up)` — количество целей на каждом шарде должно быть примерно одинаковым.

### Сценарий 3: Отказоустойчивость «Последней мили»

Решение проблемы потери критических данных при падении дата-центра.

1.  **Dual Write:** Отправка наиболее важных алертов и 1% критических метрик одновременно в два географически разнесенных региона.
2.  **LIFO Buffer:** При восстановлении связи после сбоя агенты сначала отправляют самые свежие данные, чтобы инженеры видели текущую ситуацию, а затем — исторические данные из WAL.

### Сценарий 4: Capacity Planning для стека мониторинга

Формулы расчета ресурсов для нового кластера:

**Шаг 1: Оценка объема данных**

```
metrics_per_second = services × instances × metrics_per_instance × scrape_frequency
log_lines_per_second = services × instances × logs_per_instance
spans_per_second = services × instances × requests_per_instance × sample_rate
```

**Пример расчета:**

| Параметр | Значение |
| :--- | :--- |
| Сервисы | 50 |
| Инстансов на сервис | 10 |
| Метрик на инстанс | 200 |
| Частота скрейпинга | 1/15 сек |
| **Итого метрик/сек** | **50 × 10 × 200 / 15 = 6,667** |

**Шаг 2: Расчет ресурсов хранения**

```
storage_GB = metrics_per_second × retention_days × 86400 × bytes_per_sample / 1GB
```

Где `bytes_per_sample ≈ 1-2 байта (сжатые)`.

**Пример:** 6,667 серий x 1 sample/15сек x 86,400 сек/день x 30 дней x 2 байта = ~1.5TB за 30 дней.

**Шаг 3: Расчет ресурсов CPU/RAM агентов**

```
agents_needed = total_metrics / metrics_per_agent
cpu_per_agent = 0.5 + (metrics_per_agent / 100,000) × 1.5 core
ram_per_agent = 256MB + (metrics_per_agent / 1,000) × 2MB
```

**Шаг 4: Расчет ресурсов Kafka**

```
kafka_brokers = max(3, throughput_MB_per_sec / 100MB_per_broker)
kafka_disk = retention_hours × throughput_MB_per_sec × 3600 × replication_factor
```

### Сценарий 5: Тестирование стека мониторинга

**Цель:** проверить, что система мониторинга способна обработать ожидаемую нагрузку перед запуском в продакшен.

**Пример bash-скрипта для нагрузочного тестирования:**

```bash
#!/bin/bash
# Генерация 10,000 метрик для тестирования
for i in $(seq 1 10000); do
  curl -s -X POST http://prometheus:9090/api/v1/write \
    -H "Content-Type: application/x-protobuf" \
    --data-binary @/dev/null &
done

# Проверка: количество серий в Prometheus
curl -s http://prometheus:9090/api/v1/query?query=prometheus_tsdb_head_series
# → {"data":{"result":[{"value":[1234567890,"10000"]}]}}
```

**Пример Prometheus alerting rules для smoke test:**

```yaml
# /etc/prometheus/rules/smoke_test.yml
groups:
  - name: smoke_test
    rules:
      # Проверка: метрики доступны
      - alert: MetricsAvailable
        expr: up == 1
        for: 1m
        labels:
          severity: info
        annotations:
          summary: "Smoke test: метрики доступны"
      # Проверка: алерты отправляются
      - alert: Watchdog
        expr: vector(1)
        for: 0m
        labels:
          severity: none
        annotations:
          summary: "Smoke test: пайплайн алертинга работает"
```

## Оптимизация стоимости

### Стоимость хранения

| Тип хранилища | Стоимость ($/GB/мес) | Скорость чтения | Использование |
| :--- | :--- | :--- | :--- |
| NVMe SSD | 0.10-0.20 | < 1ms | Hot storage (7 дней) |
| HDD | 0.02-0.05 | 5-15ms | Warm storage (30 дней) |
| Объектное хранилище (Standard tier) | 0.023 | 100-500ms | Cold storage (90 дней) |
| Объектное хранилище (Archive tier) | 0.004 | 3-5 часов | Archive (>1 года) |

### Стратегии снижения стоимости

1. **Тиринг (Tiering):** горячие данные на SSD, холодные -- в объектное хранилище с lifecycle policies.
2. **Downsampling:** агрегация данных старше 7 дней с интервалом 5мин, старше 90 дней -- 1ч.
3. **Сжатие:** zstd (лучшее соотношение скорость/компрессия) вместо gzip.
4. **Удаление ненужных метрик:** аудит метрик, удаление неиспользуемых.
5. **OTLP/Arrow:** снижение сетевого трафика в 5-10 раз.

### Формула ROI мониторинга

```
ROI = (Стоимость инцидента без мониторинга × Частота инцидентов) / Стоимость стека мониторинга
```

Если ROI < 1 -- мониторинг окупается. Пример: инцидент стоит $10,000, происходит 2 раза в месяц, стоимость мониторинга $5,000/мес: ROI = ($10,000 × 2) / $5,000 = 4x.

## Диагностика и устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Ingestion Lag** | Медленная запись в объектное хранилище или медленная индексация. | Увеличить количество `ingesters` (Mimir) или `storage-nodes` (VictoriaMetrics). Проверить IOPS хранилища. |
| **WAL Corruption** | Некорректное завершение процесса агента на Edge. | Использовать `--storage.tsdb.wal-compression`. Проверить наличие свободного места на диске агента. |
| **Sharding Hotspots** | Неравномерное распределение нагрузки между шардами. | Изменить ключ шардирования (использовать более вариативный лейбл). |
| **High Network Cost** | Слишком большой объем неструктурированных данных или отсутствие сжатия. | Перейти на OTLP/Arrow. Включить `native_histograms` для снижения количества серий. |
| **OOM в агенте** | Взрыв кардинальности, утечка памяти. | Проверить `prometheus_tsdb_head_series`. Ограничить количество серий через `sample_age_limit`. |
| **Kafka Consumer Lag** | Consumer'ы не успевают обрабатывать данные. | Масштабировать consumer'ов, увеличить parallelism, оптимизировать processing. |
| **Alertmanager не отправляет** | Ошибка подключения к каналу уведомлений. | Проверить `alertmanager_notifications_failed_total`, логи Alertmanager. |
| **Prometheus правила не загружаются** | Синтаксическая ошибка в YAML/PromQL. | `promtool check rules`, проверка логов (`prometheus_rule_evaluation_failures_total`). |
| **Высокий latency запросов в Grafana** | Тяжелые PromQL запросы, большой retention. | Оптимизировать запросы, добавить recording rules, увеличить cache. |
| **Дублирование данных при HA** | Два Prometheus в HA-паре отправляют одни и те же данные. | Дедупликация в Storage (Mimir/VM), настройка `external_labels`. |
| **Ложные алерты на NoData** | Кратковременная недоступность метрик. | Увеличить `for` для `absent()` алертов до 5-10 минут. |
| **Мета-мониторинг не работает** | Система мониторинга не мониторит сама себя. | Настроить Watchdog alert, Dead Man's Switch, внешний synthetics. |

## Лучшие практики

### Принципы проектирования

1. **Разделение зон ответственности:** каждый компонент пайплайна (сбор, транспорт, хранение, алертинг) масштабируется независимо. Изоляция отказов: сбой в транспорте не должен останавливать сбор.
2. **Надежность превыше актуальности:** в критичных инфраструктурах предпочтительна задержка в несколько секунд с гарантией доставки (WAL + retry), чем мгновенная доставка без гарантии.
3. **Единый формат на границе:** OTLP как универсальный формат на границе сбора снижает количество конвертеров и потерь при смене TSDB.
4. **Метамониторинг первого класса:** алерты на сам пайплайн сбора (очереди, dropped rows, scrape failures) должны быть настроены до добавления бизнес-метрик.

### Безопасность

- **Шифрование по умолчанию:** TLS для всех протоколов, кроме явно внутренних (localhost-only StatsD).
- **Минимальные привилегии:** агент сбора должен иметь доступ только к метрикам, а не к управлению целевым хостом.
- **Аутентификация на каждом этапе:** mTLS между агентом и хранилищем, токены для Remote Write, basic auth для Pull-эндпоинтов.
- **Сегментация метрик:** разделение метрик по уровням чувствительности: инфраструктурные (доступны всей команде), бизнес-метрики (ограниченный доступ).

### Производительность

- **Баланс интервала сбора и нагрузки:** интервал 15s -- разумный старт. Уменьшение до 5s оправдано только для latency-critical сервисов.
- **Ограничение кардинальности на входе:** лейблы с >1000 уникальными значениями должны быть отброшены или агрегированы до попадания в TSDB.
- **Использование Native Histograms:** при переходе на Prometheus 3.x включите native histograms для снижения кардинальности и повышения точности перцентилей.
- **Балансировка нагрузки:** при шардировании используйте консистентное хэширование (hashmod) для стабильного распределения целей.

### Эксплуатационная поддержка

- **Версионирование конфигурации:** все конфиги агентов и Prometheus должны храниться в Git.
- **Canary-обновления:** при изменении `scrape_interval` или `remote_write` конфигурации сначала примените к одному шарду и проверьте метрики качества сбора.
- **Резервное копирование WAL:** дисковые буферы агентов должны располагаться на выделенных разделах с отдельным мониторингом заполнения.
- **Документирование владельцев:** каждый `job_name` и `remote_write` конфиг должны иметь указанного владельца (сервис/команда).

## Ограничения и крайние случаи

### Ограничения Pull-модели

- **Невозможность сбора завершенных задач:** задачи, время жизни которых меньше `scrape_interval`, не будут пойманы. Используйте Pushgateway или Push-модель.
- **Зависимость от доступности источника:** если целевой хост недоступен, данные теряются. Push-модель с буферизацией на стороне источника более устойчива к кратковременным сбоям.
- **Сетевые ограничения:** за NAT, SPI firewall или в сегментах с запретом входящих соединений Pull-модель не работает без настройки статических туннелей или VPN.

### Ограничения Push-модели

- **Backpressure и потеря данных:** при резком росте нагрузки источник может отбросить данные, если приемник не успевает. Push-модель не гарантирует доставку без явного retry-механизма на стороне источника.
- **Отсутствие автоматического `up`:** в Push-модели нет встроенного механизма определения "жив" ли источник. Необходимо реализовать heartbeat-метрику или использовать sidecar.
- **Дублирование:** при перезапуске приложения или его масштабировании возможны дублирующиеся series. Требуется дедупликация на стороне TSDB (VictoriaMetrics `-dedup.minScrapeInterval`).

### Ограничения Hybrid (Remote Write)

- **Сложность отладки:** два hops (источник -> агент -> TSDB) усложняют трассировку потерь данных. Требуется метамониторинг на каждом этапе.
- **Задержка на агментирование:** батчинг и WAL добавляют задержку в 1-5 секунд по сравнению с прямой отправкой.
- **Зависимость от дискового пространства агента:** при длительных обрывах связи WAL может заполнить диск. Требуется мониторинг свободного места и ротация.

### Legacy-системы и отсутствие экспортеров

- **Системы без HTTP-эндпоинтов:** многие legacy-приложения не expose `/metrics`. Варианты: SNMP-опрос, агенты уровня ОС (`node_exporter`, `windows_exporter`), парсинг логов (Log-to-Metrics), sidecar-паттерн.
- **Проприетарные протоколы:** монолитное ПО с собственным протоколом телеметрии требует написания кастомного экспортера или использования universal-агентов (Telegraf с plugins).
- **Старые ОС:** на Solaris, AIX, HP-UX отсутствуют современные агенты. Используйте SNMP или legacy-init-скрипты.

### Ресурсные ограничения

- **Low-powered устройства (Edge, IoT):** встроенные системы с ограниченным RAM/CPU требуют облегченных сборщиков (statsd, minimal OTel Collector).
- **High-frequency метрики:** метрики с интервалом <1s создают большую нагрузку на сеть и TSDB. Рассмотрите агрегацию на стороне агента.
- **Большое количество целей:** при >50,000 целей на один агент возможна деградация производительности. Используйте шардирование или несколько инстансов агента.

## Дополнительная информация

### Мета-мониторинг: мониторинг самого мониторинга

Система мониторинга -- это высоконагруженное распределенное приложение, подверженное сбоям. Необходимо обеспечить наблюдаемость за самой системой наблюдаемости:

- **Watchdog alert:** алерт с условием `vector(1)`, который всегда горит. Если он пропадает -- значит сломался весь пайплайн (от сбора до доставки).
- **Cross-region monitoring:** кластеры мониторинга в разных зонах доступности следят друг за другом по кругу (A мониторит B, B мониторит C, C мониторит A).
- **External synthetics:** внешние проверки доступности Grafana UI, Prometheus API, Alertmanager.

Подробнее: **[Meta-Monitoring](./meta-monitoring.md)**.

### Выбор протокола: Почему OTLP?

Переход на **OTLP** (OpenTelemetry Line Protocol) является обязательным для высоконагруженных систем:
- **Унификация:** Один транспорт для метрик, логов, трейсов и профилей.
- **Correlation:** Нативная поддержка связей через `TraceID` во всех слоях.
- **Эффективность:** Бинарный формат с поддержкой сжатия (zstd/gzip) и Arrow.
