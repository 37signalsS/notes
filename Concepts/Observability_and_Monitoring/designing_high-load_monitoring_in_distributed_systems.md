# Проектирование высоконагруженного мониторинга в распределённых системах

## Определения

**Высоконагруженный мониторинг (High-Load Monitoring)** — архитектура системы наблюдаемости, спроектированная для обработки миллионов метрик в секунду (TPS), терабайт логов и миллиардов спанов трассировки. Основная задача такой архитектуры — обеспечить масштабируемость, отказоустойчивость и низкую задержку при обработке телеметрии без превращения стека мониторинга в «бутылочное горлышко» для основной системы.

**Ключевой принцип:** Разделение уровней сбора (Collection), транспортировки (Transport), обработки (Processing) и хранения (Storage). Это позволяет масштабировать каждый компонент независимо и изолировать сбои в одной части системы от других.

**См. также:**
- **[Определения Observability](./observability_definitions.md)** — базовые понятия мониторинга и наблюдаемости.
- **[Четыре столпа Observability](./four_pillars_of_observability.md)** — фундаментальные принципы телеметрии.

## Базовые концепции

### 1. Транспорт и буферизация: Kafka

В высоконагруженных системах прямой «пуш» логов или метрик в хранилище опасен потерей данных при всплесках нагрузки (bursts). **Apache Kafka** выступает в роли персистентного демпфера.

- **Декаплинг (Decoupling):** Источники данных не зависят от производительности или доступности хранилища (TSDB).
- **Backpressure:** Позволяет консьюмерам (Vector, Alloy) вычитывать данные с той скоростью, с которой они способны их обработать, предотвращая перегрузку хранилища.
- **KRaft Mode:** Современный стандарт Kafka без ZooKeeper, упрощающий эксплуатацию в 2026 году.

Подробнее: **[Kafka для мониторинга](../../Kafka/kafka_for_monitoring.md)**.

### 2. Сбор метрик: Stateless-агенты

Для снижения нагрузки на память и диск на «краях» инфраструктуры (Edge/Clusters) рекомендуется использовать **Prometheus Agent Mode** или **Grafana Alloy**.

- **Stateless:** Агенты не хранят данные локально (кроме краткосрочного WAL-буфера на диске).
- **Remote Write 2.0:** Основной протокол в 2026 году снижает трафик на **60%** за счет интернирования строк (String Interning) и пакетного сжатия.
- **Экономия ресурсов:** Потребляет на 30–50% меньше RAM по сравнению со стандартным сервером Prometheus.

### 3. Унифицированный сбор: Grafana Alloy

**Grafana Alloy** — универсальный коллектор, заменяющий множество разрозненных экспортеров.

- **OTLP/Arrow:** Использование колоночного сжатия Apache Arrow для передачи телеметрии снижает нагрузку на сеть в 5-10 раз.
- **Компонентная архитектура:** Позволяет строить декларативные пайплайны обработки данных (фильтрация, релейблинг, маскирование) на уровне агента.

### 4. Долгосрочное хранение: LTS на базе объектных хранилищ

В 2026 году стандартом является хранение данных в S3-совместимых хранилищах (Stateless Storage).

| Решение | Особенности архитектуры |
| :--- | :--- |
| **[Grafana Mimir](../../Mimir/mimir_overview.md)** | Микросервисная архитектура, нативная мульти-тенантность. |
| **[VictoriaMetrics](../../VictoriaMetrics/overview.md)** | Экстремальная плотность упаковки, поддержка MetricsQL. |
| **Thanos** | Прозрачное расширение Prometheus для Global View через Sidecars/Query. |

## Практические сценарии

### Сценарий 1: Архитектура распределенной наблюдаемости (Global Stack)

Современная схема построения системы для крупной компании:

| Уровень | Технология | Роль |
| :--- | :--- | :--- |
| **Edge** | **Grafana Alloy** | Сбор всех сигналов (OTLP), базовая фильтрация. |
| **Transport** | **Kafka (acks=all)** | Гарантированная доставка и буферизация. |
| **Processing** | **Vector** | Тяжелая обработка, обогащение контекстом, маршрутизация. |
| **Storage** | **Mimir / Loki / Tempo** | Горизонтально масштабируемое хранение в S3. |

**Валидация:**
1. Проверить `consumer lag` в Kafka: рост лага указывает на нехватку ресурсов в слое Processing/Storage.
2. Проверить метрики Remote Write: `prometheus_remote_storage_samples_total` vs `vm_rows_inserted_total`.

### Сценарий 2: Шардирование сбора в сверхкрупных кластерах

При мониторинге >10,000 подов один инстанс агента не справится.

- **Hash-based sharding:** Распределение целей между N коллекторами на основе хеша от лейбла `__address__`.
- **Prometheus Operator:** Настройка через `spec.shards` в ресурсе Prometheus/Alloy.

**Валидация:**
Проверить равномерность распределения: `count by (shard) (up)` — количество целей на каждом шарде должно быть примерно одинаковым.

### Сценарий 3: Отказоустойчивость «Последней мили»

Решение проблемы потери критических данных при падении дата-центра.

1.  **Dual Write:** Отправка наиболее важных алертов и 1% критических метрик одновременно в два географически разнесенных региона.
2.  **LIFO Buffer:** При восстановлении связи после сбоя агенты сначала отправляют самые свежие данные, чтобы инженеры видели текущую ситуацию, а затем — исторические данные из WAL.

## Диагностика и устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Ingestion Lag** | Медленная запись в объектное хранилище или медленная индексация. | Увеличить количество `ingesters` (Mimir) или `storage-nodes` (VictoriaMetrics). Проверить IOPS S3. |
| **WAL Corruption** | Некорректное завершение процесса агента на Edge. | Использовать `--storage.tsdb.wal-compression`. Проверить наличие свободного места на диске агента. |
| **Sharding Hotspots** | Неравномерное распределение нагрузки между шардами. | Изменить ключ шардирования (использовать более вариативный лейбл). |
| **High Network Cost** | Слишком большой объем неструктурированных данных или отсутствие сжатия. | Перейти на OTLP/Arrow. Включить `native_histograms` для снижения количества серий. |

## Дополнительная информация

### Выбор протокола: Почему OTLP?

В 2026 году переход на **OTLP** (OpenTelemetry Line Protocol) является обязательным для высоконагруженных систем:
- **Унификация:** Один транспорт для метрик, логов, трейсов и профилей.
- **Correlation:** Нативная поддержка связей через `TraceID` во всех слоях.
- **Эффективность:** Бинарный формат с поддержкой сжатия (zstd/gzip) и Arrow.
