# Рекомендации по мониторингу и алертингу

## Определения

**Алерт (Alert)** — уведомление о событии, требующем внимания оператора. Генерируется при выполнении условия правила алертинга.

**Правило алертинга (Alert Rule)** — выражение, определяющее условие срабатывания алерта на основе метрик, логов или других данных мониторинга.

**Шторм оповещений (Alert Storm)** — ситуация массового срабатывания множества алертов из-за одной корневой проблемы, приводящая к перегрузке операторов.

## Культура алертинга

Главная проблема реального мониторинга — не нехватка алёртов, а их избыток (**Alert Fatigue** / Усталость от алёртов).

### Основные правила SRE для алертов:

1.  **Обязательность действия:** На каждый алерт обязано существовать конкретное действие (Runbook), которое человек должен выполнить. Если на уведомление не нужно реагировать немедленно — это не алерт, а метрика для дашборда.
2.  **Нагрузка на дежурного:** Целевой показатель — не более **2 инцидентов за смену**. Если их больше, систему нужно чинить, а не просто "тушить пожары".
3.  **Безвиновные постмортемы (Blameless Post-mortems):** После каждого серьезного инцидента проводится разбор. Цель — найти системную причину и изменить процесс/код, чтобы проблема не повторилась, а не найти виноватого.

### Продвинутый алертинг: Burn Rate

**Burn Rate** (скорость выгорания) показывает, как быстро тратится бюджет ошибок.

-   **Burn Rate = 1:** Бюджет тратится ровно в соответствии с планом (весь бюджет уйдет к концу периода). Это норма.
-   **Burn Rate > 1:** Бюджет тратится слишком быстро.
-   **Критический алерт:** Настраивается на высокую скорость выгорания (например, бюджет сгорит за несколько часов). Требует немедленной реакции.
-   **Тикет в бэклог:** Если бюджет утекает чуть быстрее нормы, достаточно завести задачу на разбор без ночного звонка дежурному.

Такой подход на порядок снижает шум по сравнению с обычными порогами (`threshold alerts`).

## Практические сценарии

### Рекомендации по настройке оповещений

**Избегайте чрезмерной чувствительности** — настраивайте триггеры на *реальные проблемы*, требующие вмешательства. Используйте параметр `for` и интервалы оценки для фильтрации кратковременных аномалий:

- `for` ≥ 2–3 интервалов оценки.
- Для редких метрик: `NoData=OK`, для критичных: `NoData=Alerting`.

**Определяйте критичность** — классифицируйте события по степени влияния:

- **Критичные:** длительная недоступность (>5 минут или >10 проверок).
- **Предупреждения:** кратковременные деградации, требующие наблюдения.
- **Информационные:** события для дашбордов и аудита.

**Приоритизация триггеров** — назначайте уровни приоритета:

- `critical` / `emergency` — немедленная реакция (PagerDuty, телефон).
- `warning` — реакция в рабочее время (Email, Slack).
- `info` — только дашборды, без уведомлений.

**Зависимости триггеров** — используйте правила подавления для предотвращения штормов:

- При отказе коммутатора — одно оповещение о коммутаторе, а не о каждом сервере.
- При недоступности дата-центра — подавление алертов отдельных сервисов.
- Настройка через `source_match` и `target_match` в Alertmanager.

### Сценарий: Минимальный Production-мониторинг за первый день

**Задача:** стартап запустил первый Production-сервис. Минимальный набор для настройки в первый день:

| Компонент | Что мониторить | Инструмент |
|---|---|---|
| **RED-метрики** | Rate (RPS), Errors (error rate %), Duration (p95 latency) | [RED Method](./monitoring_methodologies.md#3-red-method) |
| **Инфраструктура** | CPU, RAM, Disk usage | [node_exporter](../../Prometheus/Exporters/node_exporter.md) + простые алерты |
| **Uptime** | `up{job="..."} == 0` → немедленная нотификация | [Alertmanager](../../Prometheus/alertmanager.md) |
| **Логи** | Централизованный сбор, Retention минимум 7 дней | Fluent Bit → [Loki](../../Loki/loki_overview.md) |
| **Сэмплирование** | При >1000 RPS: DEBUG на 10%, ERROR на 100% | Fluent Bit / Vector (см. [сценарий 3](./logs_deep_dive.md#сценарий-3-фильтрация-и-агрегация-логов)) |
| **Dashboard** | Базовый: RPS, Error %, p95 latency, CPU, RAM | [Grafana провижининг](../../Grafana/grafana_provisioning.md) |
| **On-call дежурство** | Critical → PagerDuty (24/7), Warnings → Telegram (рабочее время) | [Alertmanager routing tree](../../Prometheus/alertmanager.md) |

**Ключевые принципы с первого дня:**

- **Алерты как код:** PrometheusRule, Recording Rules и Alerting Rules хранятся в Git вместе с манифестами приложения и проходят Code Review — никаких ручных правок в UI Grafana. См. [PrometheusRule CRD](../../Prometheus/kubernetes/operator/crd/prometheusrule.md).
- **SLO через burn-rate:** вместо threshold-алертов (`error_rate > 5%`). Burn-rate точнее: алерт срабатывает при превышении бюджета ошибок за окно (multi-window, multi-burn-rate). Меньше шума, быстрее обнаружение. Подробнее — [SRE: SLO, SLI](../sre_concepts_main.md).
- **Recording rules:** предварительно агрегировать тяжелые PromQL-запросы (например, rate за 5 минут для каждого сервиса) — ускоряет дашборды и снижает нагрузку на Prometheus. См. [Recording Rules](../../Prometheus/rules.md#правила-записи-recording-rules).
- **Retention метрик:** локальный Prometheus хранит данные 15 дней по умолчанию. Для долгосрочного хранения — [VictoriaMetrics](../../VictoriaMetrics/overview.md) или [Thanos](../../Prometheus/scaling/thanos_overview.md) через `remote_write`. См. [Remote Read/Write](../../Prometheus/scaling/remote_read_write.md).
