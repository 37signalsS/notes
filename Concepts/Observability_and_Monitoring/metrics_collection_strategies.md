# Metrics Collection Strategies

## Определения

**Стратегии сбора метрик** — подходы к организации доставки телеметрических данных от источников к системе мониторинга. Выбор стратегии влияет на надёжность, масштабируемость и стоимость системы наблюдаемости.

**Три основных подхода:**

| Стратегия | Принцип | Инициатор |
| :--- | :--- | :--- |
| **Сбор из логов** | Генерация метрик из логов постфактум | Система мониторинга |
| **Push-модель** | Источники отправляют метрики активно | Источник данных |
| **Pull-модель** | Система мониторинга опрашивает источники | Система мониторинга |

**См. также:** [Метрики: детали](./metrics_deep_dive.md) — типы метрик и характеристики; [Четыре столпа Observability](./four_pillars_of_observability.md) — фундаментальные концепции.

## Базовые концепции

### 1. Сбор метрик из логов

**Принцип работы:**

1. Приложения пишут события в лог-файлы
2. Система сбора логов (ELK Stack) парсит и индексирует логи
3. Метрики генерируются запросами к базе данных логов (например, подсчёт строк с "ERROR")

**Преимущества:**

| Преимущество | Описание |
| :--- | :--- |
| **Доступность данных** | Логи уже существуют в любой системе |
| **Концептуальная простота** | Подход легко понять и внедрить |
| **Высокая детализация** | Сохраняется каждое событие |

**Недостатки:**

| Недостаток | Описание |
| :--- | :--- |
| **Высокая стоимость** | Ресурсоёмкий подход (CPU, RAM, диск) из-за парсинга и индексации |
| **Сложность парсинга** | Требуется настройка правил извлечения данных |

**Пример стека:** ELK Stack (**[Elasticsearch](../../../ELK_Stack/Elasticsearch/elasticsearch_overview.md)**, **[Logstash](../../../ELK_Stack/Logstash/logstash_overview.md)**, Kibana).

### 2. Push-модель

**Принцип работы:** источники метрик (приложения, агенты) активно отправляют данные в централизованную систему мониторинга.

```
Источник → Метрика → Коллектор/Хранилище
```

**Преимущества:**

| Преимущество | Описание |
| :--- | :--- |
| **Дешевле, чем из логов** | Отправляются структурированные, небольшие данные |
| **Высокая детализация** | Сохраняется каждое отдельное измерение |
| **Простота реализации** | Прост в реализации с точки зрения клиента |

**Недостатки:**

| Недостаток | Описание |
| :--- | :--- |
| **Риск влияния на приложение** | Сбой мониторинга может привести к потере метрик или сбою приложения |
| **Децентрализованная конфигурация** | Настройки отправки разбросаны по всем источникам |
| **Требует инструментирования** | Необходимо добавлять в код логику отправки метрик |
| **Сложность отладки** | Нужны хитрые запросы, фильтрация по репликам, доступ к хранилищу |

**Примеры систем:** **[Zabbix](../../../Zabbix/definitions_and_concepts.md)** (Zabbix Agent), **StatsD**, **Telegraf**.

### 3. Pull-модель

**Принцип работы:** центральная система мониторинга периодически опрашивает источники метрик через определённые интервалы.

```
Prometheus → GET /metrics → Источник (экспортер)
```

**Как это работает:**

1. Приложение/экспортер предоставляет HTTP-эндпоинт (`/metrics`) с текущими значениями метрик
2. Сервер мониторинга периодически (например, раз в 15 секунд) забирает ("скрапит") данные

Метрики в этой модели, как правило, **кумулятивные**. Например, счётчик запросов (`http_requests_total`) постоянно растёт, а система мониторинга вычисляет скорость изменения через `rate()`.

**Преимущества:**

| Преимущество | Описание |
| :--- | :--- |
| **Надёжность** | Сбой мониторинга не влияет на работу приложений |
| **Централизованное управление** | Вся конфигурация сбора в одном месте |
| **Контроль нагрузки на сервер** | Сервер сам определяет частоту опроса (scrape interval), что предотвращает его перегрузку со стороны клиентов |
| **Эффективность** | Самый дешёвый подход, нагрузка не зависит от количества событий |
| **Легкость обнаружения сбоев** | Если эндпоинт недоступен — это сразу видно |
| **Простота отладки** | Можно зайти в endpoint браузером и увидеть метрики приложения |
| **Дисциплина метрик** | Стимулирует писать только необходимые метрики |

**Недостатки:**

| Недостаток | Описание |
| :--- | :--- |
| **Потеря детализации** | Система видит только агрегированное состояние на момент опроса |
| **Смена парадигмы** | Нужно работать с кумулятивными метриками и функциями `rate()`, `increase()` |
| **Сложнее реализация** | С точки зрения клиента pull сложнее реализовать, чем push |

**Пример системы:** **[Prometheus](../../../Prometheus/overview.md)** — построен вокруг pull-модели.

### Почему Pull-модель требует агрегации

Чтобы метрики не занимали лишнюю память и быстро отдавались, их необходимо агрегировать. Хранение подробностей о каждом запросе быстро исчерпает память приложения. Поэтому ограничиваются минимумом: счётчики запросов и ошибок.

**Результат:** инфраструктура получает уже сжатые данные, обдуманные разработчиками приложения.

Push тоже можно организовать аналогично, но там проще отправлять всё подряд и разбираться потом.

### Сравнительная таблица моделей

| Критерий | Сбор из логов | Push-модель | Pull-модель |
| :--- | :--- | :--- | :--- |
| **Детализация** | Очень высокая (каждое событие) | Высокая (каждое измерение) | Ограничена интервалом сбора |
| **Стоимость** | Очень высокая | Средняя | Низкая |
| **Надёжность** | Высокая (не влияет на приложение) | Низкая (может влиять) | Очень высокая (разделение) |
| **Управление** | Смешанное | Децентрализованное | Централизованное |
| **Отладка** | Сложная | Сложная | Простая |
| **Реализация** | Простая | Простая | Сложнее |

## Практический сценарий: Выбор стратегии

### Сценарий 1: Микросервисы в Kubernetes

**Задача:** организовать сбор метрик с сотен подов в Kubernetes.

**Решение:** Pull-модель с Prometheus.

```yaml
# Prometheus scrape config
scrape_configs:
  - job_name: 'kubernetes-pods'
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: true
```

**Преимущества для Kubernetes:**

- Service Discovery автоматически обнаруживает поды
- Централизованное управление конфигурацией
- Лёгкая отладка через `/metrics` endpoint

### Сценарий 2: Короткоживущие задачи (Batch Jobs)

**Задача:** собрать метрики от cron-скриптов, которые завершаются до очередного опроса Prometheus.

**Решение:** **[Prometheus Pushgateway](../../../Prometheus/pushgateway.md)** — комбинированный подход.

```bash
# Пример отправки метрики в Pushgateway
echo "batch_job_duration_seconds: 42" | \
  curl --data-binary @- http://pushgateway:9091/metrics/job/batch-job
```

**Важно:** Pushgateway следует использовать **только** для короткоживущих batch-задач. Превращение Prometheus в push-систему — анти-паттерн.

**См. также:** **[Методологии мониторинга](./monitoring_methodologies.md)** — Golden Signals, RED, USE для определения ключевых метрик.

### Сценарий 3: Унаследованные системы без экспортеров

**Задача:** мониторить старое приложение, которое не предоставляет метрики.

**Решение:** Сбор метрик из логов.

```logql
# Пример LogQL для Loki — подсчёт ошибок за 5 минут
sum(rate({app="legacy-app"} |= "ERROR" [5m]))
```

**Когда использовать:**

- Нет возможности модифицировать приложение
- Логи уже собираются централизованно
- Требуется быстрый старт мониторинга

## Additional Information

### Гибридные подходы

На практике часто используются комбинации стратегий:

| Комбинация | Описание | Пример |
| :--- | :--- | :--- |
| **Pull + Pushgateway** | Основной сбор через pull, batch-задачи через push | Prometheus + Pushgateway |
| **Pull + Агенты** | Prometheus скрапит агенты (node-exporter) | Node Exporter, cAdvisor |
| **Push + Буфер** | Агенты отправляют в Kafka, потом консьюмеры | Telegraf → Kafka → Prometheus |

### Инструменты по стратегиям

| Стратегия | Инструменты |
| :--- | :--- |
| **Сбор из логов** | ELK Stack, Loki + LogQL, Splunk |
| **Push-модель** | Zabbix, StatsD, Telegraf, InfluxDB |
| **Pull-модель** | Prometheus, VictoriaMetrics, vmagent |

### Рекомендации по выбору

| Ситуация | Рекомендуемая стратегия |
| :--- | :--- |
| **Cloud Native / Kubernetes** | Pull-модель (Prometheus) |
| **Унаследованная инфраструктура** | Push-модель (Zabbix) |
| **Batch-задачи / Cron** | Pushgateway (комбинированный) |
| **Приложение без инструментирования** | Сбор из логов |
| **Высоконагруженная система** | Pull-модель с агрегацией |
