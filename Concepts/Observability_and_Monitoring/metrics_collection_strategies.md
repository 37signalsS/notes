# Стратегии сбора метрик

## Определения

**Стратегии сбора метрик** — подходы к организации доставки телеметрических данных от источников к системе мониторинга. Выбор стратегии влияет на надёжность, масштабируемость и стоимость системы наблюдаемости.

**Три основных подхода:**

| Стратегия | Принцип | Инициатор |
| :--- | :--- | :--- |
| **Сбор из логов** | Генерация метрик из текстовых логов | Система мониторинга |
| **Push-модель** | Активная отправка данных источником | Источник данных |
| **Pull-модель** | Опрос источников системой мониторинга | Система мониторинга |

Подробное описание типов самих метрик приведено в файле **[Метрики: детали](./metrics_deep_dive.md)**.

## Базовые концепции

### 1. Сбор метрик из логов

**Принцип работы:** приложения пишут события в текстовые файлы, которые затем обрабатываются (парсятся) специализированным агентом. На основе вхождений определенных строк или значений в полях (для JSON-логов) формируются числовые показатели.

**Преимущества:**

- **Доступность:** логи существуют почти во всех системах «из коробки».
- **Историчность:** можно пересчитать метрики за прошлый период, если сохранились логи.
- **Детализация:** сохраняется полный контекст события для последующего анализа.

**Недостатки:**

- **Высокая стоимость:** хранение и индексация текстовых данных в разы дороже хранения числовых временных рядов.
- **Задержка:** метрики появляются только после того, как лог будет прочитан, передан и обработан.

**Пример стека:** ELK Stack (**[Elasticsearch](../../ELK_Stack/Elasticsearch/elasticsearch_overview.md)**, **[Logstash](../../ELK_Stack/Logstash/logstash_overview.md)**, Kibana).

### 2. Push-модель

**Принцип работы:** приложение или агент мониторинга самостоятельно инициируют сетевое соединение и отправляют пакеты данных на сервер сбора.

**Преимущества:**

- **Удобство для динамических сред:** не нужно настраивать сервер на опрос каждой новой копии приложения (актуально для Serverless).
- **Сетевая доступность:** легко проходит через NAT и межсетевые экраны (требуется только исходящий трафик).

**Недостатки:**

- **Риск перегрузки:** при резком росте количества источников сервер сбора может не справиться с потоком входящих запросов.
- **Сложность мониторинга «живучести»:** если приложение перестало присылать метрики, серверу сложно отличить падение приложения от проблем с сетью.

**Примеры систем:** **[Zabbix](../../Zabbix/definitions_and_concepts.md)**, StatsD, Telegraf.

### 3. Pull-модель

**Принцип работы:** центральный сервер мониторинга периодически обходит список известных ему целей (targets) и запрашивает текущие значения метрик по HTTP.

**Преимущества:**

- **Надёжность:** сервер сам контролирует частоту опроса и не может быть «завален» входящими данными.
- **Простота отладки:** можно зайти браузером на эндпоинт приложения (обычно `/metrics`) и увидеть данные в текстовом виде.
- **Централизация:** вся конфигурация сбора хранится на сервере мониторинга.

**Недостатки:**

- **Сетевые требования:** сервер должен иметь прямой сетевой доступ к каждому приложению.
- **Агрегация:** модель требует, чтобы приложение хранило текущее состояние метрик в памяти до момента опроса.

**Пример системы:** **[Prometheus](../../Prometheus/overview.md)**.

### Сравнительная таблица моделей

| Критерий | Сбор из логов | Push-модель | Pull-модель |
| :--- | :--- | :--- | :--- |
| **Детализация** | Очень высокая | Высокая | Агрегированная |
| **Стоимость** | Высокая | Средняя | Низкая |
| **Надёжность** | Средняя | Средняя | Высокая |
| **Управление** | Смешанное | Децентрализованное | Централизованное |
| **Отладка** | Сложная | Сложная | Простая |

## Практические сценарии

### Сценарий 1: Cloud Native и микросервисы (Kubernetes)

**Рекомендуемая стратегия:** **Pull-модель**.
В Kubernetes Prometheus автоматически обнаруживает новые поды через API-сервер. Это позволяет поддерживать актуальный список источников без ручного вмешательства.

### Сценарий 2: Короткоживущие задачи (Batch / Cron Jobs)

**Рекомендуемая стратегия:** **Гибридная (через Pushgateway)**.
Поскольку задача может завершиться быстрее, чем наступит время следующего опроса сервера, используется промежуточный буфер — **[Pushgateway](../../Prometheus/pushgateway.md)**. Задача «пушит» в него данные, а сервер мониторинга затем забирает их методом «pull».

### Сценарий 3: Закрытые сегменты сети или IoT

**Рекомендуемая стратегия:** **Push-модель**.
Когда центральный сервер мониторинга не может инициировать соединение с устройствами (например, из-за NAT), устройства сами отправляют данные на доступный им адрес коллектора.

## Дополнительная информация

### Гибридные подходы

В крупных инфраструктурах часто встречаются комбинации:

- **Pull + Агенты:** сервер скрапит локальных агентов (Node Exporter), которые собирают системные данные.
- **Push + Очередь:** агенты отправляют данные в Kafka, из которой они вычитываются сервером мониторинга.
