# Стратегии сбора метрик

## Определения

**Стратегии сбора метрик** — архитектурные подходы к организации передачи телеметрических данных от источников (приложений, серверов, оборудования) к системе мониторинга и хранения (TSDB).

**Основные подходы:**

- **Pull-модель (опрос):** система мониторинга активно запрашивает данные у источников.
- **Push-модель (отправка):** источники или локальные агенты самостоятельно отправляют данные в центральное хранилище.
- **Сбор из логов:** числовые показатели генерируются путем анализа текстовых журналов событий.
- **Hybrid (Remote Write):** локальный агент собирает данные (pull) и пересылает их в удаленное хранилище (push).

Выбор стратегии определяет сетевую архитектуру, требования к безопасности и возможности масштабирования системы наблюдаемости (Observability).

## Базовые концепции

### 1. Pull-модель (Scraping)

Центральный сервер мониторинга (например, Prometheus) периодически опрашивает список известных ему целей (targets) по протоколу HTTP.

**Характеристики:**

- **Централизованное управление:** вся конфигурация (интервалы сбора, правила фильтрации) хранится в одном месте.
- **Защита от перегрузки:** сервер сам контролирует темп сбора и не может быть «завален» входящим трафиком от тысяч инстансов.
- **Простота отладки:** эндпоинты метрик (например, `/metrics`) доступны для ручной проверки обычным браузером или `curl`.
- **Service Discovery:** идеально подходит для сред с динамическим обнаружением сервисов (Kubernetes, Consul).

**Недостатки:** Требует прямого сетевого доступа от сервера к каждому приложению, что затрудняет работу в сегментированных сетях или за NAT.

### 2. Push-модель

Приложение или специализированный агент инициирует сетевое соединение и отправляет пакеты данных на сервер сбора.

**Характеристики:**

- **Работа за NAT:** источникам данных достаточно иметь исходящий доступ в интернет или корпоративную сеть.
- **Serverless и Batch:** единственный способ мониторинга короткоживущих функций (AWS Lambda) или задач, которые завершаются быстрее интервала опроса.
- **Real-time:** данные отправляются сразу после возникновения события (актуально для StatsD).

**Недостатки:** Риск «шторма» входящих данных при резком росте нагрузки, сложность контроля целостности данных (если приложение молчит, непонятно — оно упало или просто нет трафика).

### 3. Гибридный подход и Remote Write

Современный стандарт для высоконагруженных систем. Локальный легковесный агент (vmagent, Grafana Alloy, OpenTelemetry Collector) собирает метрики методом **Pull**, агрегирует их, сжимает и отправляет по протоколу **Remote Write** (Push) в центральное хранилище.

**Преимущества:**

- **Снижение сетевого трафика:** за счет пакетной передачи и эффективного сжатия.
- **Надежность:** агент может буферизировать данные на диске при временной недоступности центрального сервера.
- **Безопасность:** центральное хранилище не нуждается в доступе ко всем сегментам сети.

### Сравнительный анализ моделей

| Критерий | Pull | Push | Remote Write (Hybrid) |
| :--- | :--- | :--- | :--- |
| **Инициатор** | Сервер | Источник | Агент |
| **Сетевой поток** | Входящий к источнику | Исходящий от источника | Исходящий от агента |
| **Контроль нагрузки** | Высокий (на сервере) | Низкий (на клиенте) | Средний (буферизация) |
| **Сложность конфига** | Низкая | Средняя | Высокая |
| **Основной инструмент** | Prometheus | Zabbix, StatsD | VictoriaMetrics, Mimir |

## Практические сценарии

### Сценарий 1: Мониторинг в Kubernetes

**Рекомендуемая стратегия:** **Pull (Prometheus / vmagent)**.
Использование Kubernetes API для автоматического обнаружения подов (Service Discovery). Сбор метрик происходит по внутренней сети кластера, что минимизирует накладные расходы на сетевую связность.

### Сценарий 2: Глобальный мониторинг распределенных ЦОД

**Рекомендуемая стратегия:** **Hybrid (Remote Write)**.
В каждом дата-центре устанавливается локальный коллектор, который собирает метрики со всех ресурсов внутри ЦОД и отправляет их в единое глобальное хранилище (например, VictoriaMetrics Cluster) через защищенный туннель.

### Сценарий 3: IoT и Edge Computing

**Рекомендуемая стратегия:** **Push (OTLP / MQTT)**.
Устройства с нестабильным каналом связи или находящиеся за мобильными провайдерами (NAT) самостоятельно отправляют телеметрию в облачный шлюз по мере доступности сети.

### Сценарий 4: Сбор бизнес-метрик из логов

Используется, когда внесение изменений в код приложения для экспорта метрик невозможно или нецелесообразно. Агент (Vector, Fluent Bit) анализирует логи доступа (Access Logs) и генерирует метрики, такие как `http_requests_total` или `error_rate`, на основе HTTP-кодов ответов.

## Дополнительная информация

### Протоколы передачи

- **Prometheus Text Format:** стандарт де-факто для Pull-модели.
- **OTLP (OpenTelemetry Line Protocol):** унифицированный стандарт для Push/Pull метрик, логов и трасс.
- **StatsD:** текстовый протокол поверх UDP для быстрой отправки счетчиков.
