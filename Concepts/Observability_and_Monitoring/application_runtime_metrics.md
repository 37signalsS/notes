# Метрики рантайма приложений — Языковая специфика

## Определения

**Метрики рантайма (Runtime Metrics)** — системные показатели, генерируемые средой выполнения приложения (виртуальной машиной, интерпретатором или рантаймом языка). Они отражают внутренние механизмы процесса: управление памятью (Heap, Non-Heap), работу планировщика (Scheduler), состояние потоков (Threads) и эффективность сборщика мусора (GC).

**Stop-the-world (STW)** — состояние рантайма (особенно JVM и Go), при котором выполнение всех прикладных потоков приостанавливается для выполнения системных задач, чаще всего — фаз сборки мусора. Длительные STW-паузы напрямую влияют на P99 задержку.

**Конкуренция за потоки (Thread Contention)** — ситуация, когда несколько потоков одновременно пытаются получить доступ к общему ресурсу (мьютексу или секции кода), что приводит к простоям и снижению производительности при росте нагрузки.

**Осведомлённость о контейнерах (Container Awareness)** — способность рантайма корректно определять и соблюдать лимиты ресурсов (CPU, RAM), установленные через механизмы `cgroups` (v1/v2), предотвращая аномальное поведение или принудительное завершение процесса ядром (OOMKiller).

## Основные концепции

В 2026 году мониторинг рантаймов базируется на глубокой интеграции с ядром Linux и современными стандартами наблюдаемости:

1.  **Иерархия ресурсов (Cgroups v2):** Мониторинг должен учитывать не только абсолютные значения, но и «давление» на ресурсы через **[PSI (Pressure Stall Information)](../../Linux/Core/kernel/psi.md)**.
2.  **Методология RED:** Рантайм-метрики позволяют найти причину деградации RED-показателей (например, GC-паузы увеличивают Duration).
3.  **Методология USE:** Применяется для оценки «здоровья» внутренних пулов (например, пула потоков или очереди планировщика).
4.  **Синергия с профилированием:** Метрики рантайма указывают *что* тормозит (например, рост `go_mutex_wait_duration`), а **[непрерывное профилирование](../continuous_profiling.md)** показывает *где именно* в коде находится проблемный мьютекс.

## Метрики по языкам программирования

### 1. Java (JVM)
Современная JVM (Java 21, 25+) ориентирована на низкие задержки и эффективную работу в облаке.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **GC** | `jvm_gc_pause_seconds` | Длительность STW. Для ZGC/Shenandoah норма < 1мс. |
| **Hiccups** | `jvm_runtime_hiccups_seconds` | **Критично для SRE:** Измеряет время «замирания» рантайма из-за внешних факторов (CPU троттлинг). |
| **Safepoints** | `jvm_runtime_safepoint_time_seconds` | Время приостановки всех потоков. Рост указывает на проблемы синхронизации. |
| **Native Memory** | `jvm_native_memory_total_bytes` | Память вне управления JVM (Direct Buffer, JNI). Причина «скрытых» OOM. |

**Валидация (PromQL):**
```promql
# Детекция GC Thrashing (когда GC занимает более 10% времени CPU)
rate(jvm_gc_pause_seconds_sum[5m]) / (rate(container_cpu_usage_seconds_total[5m]) or rate(process_cpu_seconds_total[5m])) > 0.1
```

### 2. Go (Golang)
Метрики Go 1.22+ предоставляют глубокий доступ к планировщику через `runtime/metrics`.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **Планировщик** | `go_sched_latencies_seconds` | Время ожидания горутины в очереди. Рост = нехватка CPU. |
| **Горутины** | `go_goroutines` | Текущее кол-во. Линейный рост = Goroutine Leak. |
| **Мьютексы** | `go_mutex_wait_duration_seconds` | Время простоя на блокировках. Критично для многопоточных API. |

**Валидация (PromQL):**
```promql
# Поиск утечек горутин (рост за час > 20%)
go_goroutines / (go_goroutines offset 1h) > 1.2
```
*Детальный разбор: **[Метрики рантайма Go](../../Prometheus/Exporters/extensibility/go_runtime_metrics.md)**.*

### 3. Node.js
Основной фокус — Event Loop, так как его блокировка парализует все приложение.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **Event Loop** | `nodejs_eventloop_lag_seconds` | Лаг цикла. > 100мс — критическая деградация. |
| **V8 Heap** | `nodejs_heap_space_size_used_bytes` | Расход памяти по сегментам. |
| **External Memory** | `nodejs_external_memory_bytes` | Буферы и C++ объекты. Часто причина утечек. |

**Валидация (PromQL):**
```promql
# Детекция блокирующего I/O (лаг > 200мс)
nodejs_eventloop_lag_seconds > 0.2
```

### 4. Python (3.13+ Free-threaded)
С приходом режима **No-GIL**, мониторинг смещается от GIL к конкуренции потоков.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **GIL** | `python_gil_contention_total` | Время борьбы за блокировку (в GIL-режиме). |
| **Threads** | `python_thread_contention_seconds` | Борьба за общие объекты (в No-GIL режиме). |
| **AsyncIO** | `python_asyncio_active_tasks` | Количество активных корутин. |

### 5. Rust (Tokio)
Асинхронные рантаймы (Tokio) требуют мониторинга планировщика задач.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **Tokio Tasks** | `tokio_task_count` | Количество активных задач. |
| **Scheduling Delay** | `tokio_task_scheduling_delay_seconds` | Задержка перед запуском задачи. Индикатор перегрузки. |

### 6. .NET (Core)
Современный .NET предоставляет богатые метрики через `EventCounters` или `OpenTelemetry`.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **GC** | `dotnet_gc_pause_ratio` | Процент времени, затраченный на GC. |
| **ThreadPool** | `dotnet_threadpool_queue_length` | Глубина очереди задач в пуле потоков. |
| **Exceptions** | `dotnet_exceptions_thrown_total` | Частота выброса исключений. |

## Диагностика и устранение неполадок

| Проблема | Причина по метрикам | Решение |
| :--- | :--- | :--- |
| **Рост P99 при низком CPU** | Рост `go_mutex_wait` или `jvm_runtime_safepoint_time` | Провести профилирование блокировок (Mutex Profiling), оптимизировать критические секции. |
| **OOMKilled при малом Heap** | Рост `jvm_native_memory` или `nodejs_external_memory` | Проверить использование Direct Buffers, JNI или нативных модулей C++. Проверить лимиты cgroup. |
| **GC Thrashing** | Высокий `jvm_gc_pause_seconds_sum` при росте `jvm_memory_used` | Увеличить `-Xmx`, проверить код на создание миллионов короткоживущих объектов, внедрить объектные пулы. |
| **Event Loop Freeze** | Высокий `nodejs_eventloop_lag` | Найти в коде синхронные операции (JSON.parse огромных объектов, синхронное чтение файлов). |

## Практические сценарии

### Интеграция с OpenTelemetry (OTel)
В 2026 году рекомендуется использовать OTel SDK для унификации:
*   **Exemplars:** Связывайте аномальные выбросы метрик с конкретными Trace ID (например, тяжелый SQL-запрос вызвал GC Spike).
*   **Semantic Conventions:** Используйте стандартные префиксы `process.runtime.*`.

### Настройка алертинга на базе SLO
Избегайте алертинга на «шумные» метрики. Используйте комбинированные условия:
1.  **Memory Saturation:** Алертить, если `jvm_memory_used_bytes` > 90% AND `jvm_gc_pause_seconds` > 500мс.
2.  **Thread Exhaustion:** Алертить, если `dotnet_threadpool_queue_length` растет более 5 минут подряд.
