# Метрики рантайма приложений — Языковая специфика

## Определения

**Метрики рантайма (Runtime Metrics)** — системные показатели, генерируемые средой выполнения приложения (виртуальной машиной, интерпретатором или рантаймом языка). Они отражают внутренние механизмы процесса: управление памятью (Heap, Non-Heap), работу планировщика (Scheduler), состояние потоков (Threads) и эффективность сборщика мусора (GC).

**Осведомлённость о контейнерах (Container Awareness)** — способность рантайма корректно определять и соблюдать лимиты ресурсов (CPU, RAM), установленные через механизмы `cgroups` (v1/v2), предотвращая аномальное поведение или принудительное завершение процесса ядром (OOMKiller).

---

## Основные концепции

В 2026 году мониторинг рантаймов базируется на глубокой интеграции с ядром Linux и современными стандартами наблюдаемости:

1.  **Иерархия ресурсов (Cgroups v2):** Мониторинг должен учитывать не только абсолютные значения, но и «давление» на ресурсы через **[PSI (Pressure Stall Information)](../../Linux/Core/kernel/psi.md)**.
2.  **Методология RED:** Rate (частота запросов), Errors (ошибки), Duration (длительность). Рантайм-метрики позволяют найти причину деградации RED-показателей (например, GC-паузы увеличивают Duration).
3.  **Методология USE:** Utilization (утилизация), Saturation (насыщенность), Errors (ошибки). Применяется для оценки «здоровья» внутренних пулов (например, пула потоков или очереди планировщика).

### Почему рантайм-метрики критичны?
*   **Детекция «тихих» утечек:** Линейный рост Heap при стабильном RPS сигнализирует о Memory Leak до того, как сработает OOM.
*   **Анализ Tail Latency (P99):** Всплески задержек часто вызваны Stop-the-world паузами GC или блокировками планировщика (Thread Contention).
*   **Динамическое масштабирование:** Метрики насыщения (Saturation) служат более точным триггером для автоскейлинга (HPA), чем просто загрузка CPU.

## Метрики по языкам программирования

### 1. Java (JVM)
Современная JVM (Java 21, 25+) ориентирована на низкие задержки и эффективную работу в облаке.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **GC** | `jvm_gc_pause_seconds` | Длительность Stop-the-world. Для ZGC/Shenandoah норма < 1мс. |
| **Hiccups** | `jvm_runtime_hiccups_seconds` | **Критично для SRE:** Измеряет время, за которое выполняется код, не делающий ничего. Показывает задержки на уровнях ниже JVM (шумные соседи в K8s, CPU троттлинг, планировщик ОС). |
| **Safepoints** | `jvm_runtime_safepoint_time_seconds` | Время, когда все потоки приостановлены для внутренних нужд JVM. Не всегда связано с GC. |
| **Память** | `jvm_memory_used_bytes` | Heap + Non-Heap (Metaspace, Code Cache). |
| **Native Memory** | `jvm_native_memory_total_bytes` | Память вне управления JVM (Direct Buffer, JNI). Причина «скрытых» OOM. |

*   **Рекомендация:** Используйте концепцию **Hiccups** (Gil Tene) для разделения проблем кода и проблем инфраструктуры. Если Hiccups растут при нормальном GC — проблема в слоях ниже (кубер, железо).
*   **Мониторинг Safepoints:** Требует использования Java Flight Recorder (JFR) или специфических экспортеров. Помогает найти скрытые задержки (Thread Contention, Revoke Bias).
*   **См. также:** **[Управление Java в Linux](../../Linux/Development/java_management.md)**.

### 2. Go (Golang)
Метрики Go 1.22+ предоставляют глубокий доступ к планировщику через `runtime/metrics`.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **Планировщик** | `go_sched_latencies_seconds` | Время ожидания горутины в очереди. Рост = нехватка CPU или блокировки. |
| **Горутины** | `go_goroutines` | Текущее кол-во. Внезапный рост указывает на утечку (Leak). |
| **GC** | `go_gc_pauses_seconds` | Паузы сборщика. В Go обычно крайне низкие, важна частота циклов. |
| **Память** | `go_memstats_heap_sys_bytes` | Память, запрошенная у ОС для кучи. |
| **Мьютексы** | `go_mutex_wait_duration_seconds` | Время простоя на блокировках. Критично для многопоточных API. |

*   **Детальный разбор:** **[Метрики рантайма Go](../../Prometheus/Exporters/extensibility/go_runtime_metrics.md)**.

### 3. Node.js
Основной фокус — Event Loop, так как его блокировка парализует все приложение.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **Event Loop** | `nodejs_eventloop_lag_seconds` | Лаг цикла. > 100мс — критическая деградация (Blocking I/O). |
| **Worker Threads** | `nodejs_worker_threads_active` | Использование пула воркеров для тяжелых вычислений. |
| **Память (V8)** | `nodejs_heap_space_size_used_bytes` | Расход по сегментам (New Space, Old Space). |
| **External Memory** | `nodejs_external_memory_bytes` | Буферы и C++ объекты. Часто являются причиной утечек. |

*   **Рекомендация:** Используйте `prom-client` с включенными нативными аддонами для точного измерения Event Loop Lag.

### 4. Python
С приходом Python 3.13+ и режима **Free-threaded (No-GIL)**, мониторинг смещается в сторону параллелизма.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **GIL** | `python_gil_contention_total` | Только для GIL-режима. Время борьбы за блокировку интерпретатора. |
| **Память (RSS)** | `python_memory_rss_bytes` | Python неохотно отдает память ОС (фрагментация). |
| **Воркеры** | `python_worker_processes_active` | Загрузка процессов Gunicorn/Uvicorn. |
| **AsyncIO** | `python_asyncio_active_tasks` | Кол-во активных корутин в Event Loop. |

*   **Рекомендация:** При использовании Python 3.13 без GIL мониторьте `python_thread_contention` для выявления узких мест в общих данных.

### 5. Rust (Tokio & Allocator)
Хотя Rust компилируется в нативный код, его асинхронные рантаймы (Tokio) требуют тщательного мониторинга.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **Tokio Tasks** | `tokio_task_count` | Количество активных асинхронных задач. |
| **Worker Threads** | `tokio_worker_poll_duration_seconds` | Время, затраченное воркерами на выполнение задач. |
| **Liveness** | `tokio_task_scheduling_delay_seconds` | Задержка перед запуском задачи. Индикатор перегрузки рантайма. |
| **Аллокатор** | `jemalloc_active_bytes` | Реальное потребление памяти аллокатором (если используется jemalloc). |

*   **Рекомендация:** Используйте крейт `console-subscriber` для глубокой отладки Tokio в реальном времени.

### 6. .NET (Core)
Современный .NET предоставляет богатые метрики через `EventCounters` или `OpenTelemetry`.

| Категория | Метрика | Анализ и критические пороги |
| :--- | :--- | :--- |
| **GC** | `dotnet_gc_pause_ratio` | Процент времени, затраченный на GC. |
| **ThreadPool** | `dotnet_threadpool_queue_length` | Глубина очереди задач в пуле потоков. |
| **JIT** | `dotnet_jit_compilation_time_seconds` | Время, затраченное на компиляцию при старте. |
| **Exceptions** | `dotnet_exceptions_thrown_total` | Частота выброса исключений (First-chance exceptions). |

### 7. PHP (PHP-FPM)
Мониторинг PHP-FPM сфокусирован на управлении пулом процессов.

| Категория | Метрика | Что означает / На что смотреть |
| :--- | :--- | :--- |
| **Процессы** | `php_fpm_active_processes` | Текущее кол-во работающих воркеров. |
| **Очередь** | `php_fpm_listen_queue` | Кол-во запросов в очереди (должно быть 0). |
| **Медленные запросы** | `php_fpm_slow_requests` | Счетчик запросов, превысивших `request_slowlog_timeout`. |

*   **Детальный разбор:** **[Мониторинг PHP-FPM](../../WebServers/PHP/php-fpm-monitoring.md)**.

## Практические сценарии

### Интеграция с OpenTelemetry (OTel)
В 2026 году рекомендуется использовать OTel SDK для унификации сбора метрик и их корреляции с трассировками.
*   **Semantic Conventions:** Соблюдайте стандартные именования OTel (например, `process.runtime.jvm.memory.usage`).
*   **Zero-Code Instrumentation:** Используйте OTel Agents (Javaagent, Python Wrapper) для получения метрик без изменения исходного кода.
*   **Exemplars:** Связывайте аномальные выбросы метрик с конкретными Trace ID для мгновенного поиска причины (например, тяжелый SQL-запрос вызвал GC Spike).

### Настройка алертинга на базе SLO
Избегайте алертинга на «шумные» метрики. Используйте комбинированные условия:
1.  **Memory Saturation:** Алертить, если `jvm_memory_used_bytes` > 90% AND `jvm_gc_pause_seconds` > 500мс (признак близкого OOM).
2.  **Thread Exhaustion:** Алертить, если `dotnet_threadpool_queue_length` растет более 5 минут подряд.
3.  **Event Loop Blocking:** Алертить, если `nodejs_eventloop_lag_seconds` > 200мс.
