# Профилирование: глубокое погружение

**Актуально для:** Grafana Pyroscope 1.18.x, Grafana Alloy 1.18.x, async-profiler 4.x, OpenTelemetry Profiles (статус Alpha) / OpenTelemetry Collector Contrib 0.162.x, Java Flight Recorder (OpenJDK 11+), Linux `perf` 6.x

## Определения

**Профилирование (Profiling)** — метод динамического анализа производительности программного обеспечения, позволяющий получить детальную информацию о потреблении ресурсов (CPU, память, I/O, сетевые задержки) и поведении приложения непосредственно во время его выполнения. В отличие от статического анализа, профилирование работает с реальными данными нагрузки, позволяя выявить скрытые узкие места.

**Символизация (Symbolication)** — процесс сопоставления адресов памяти в профиле (hex-коды) с именами функций и номерами строк в исходном коде. Для этого профилировщику требуются таблицы символов или debug-информация (например, DWARF-файлы).

**Стек вызовов (Call Stack)** — упорядоченный список функций, находящихся в процессе выполнения в определенный момент времени. Профилирование «снимает» эти стеки тысячи раз для построения статистической картины.

**On-CPU профиль** — распределение времени, когда поток **выполнял** код. Это то, что измеряет `perf record -e cpu-clock` по умолчанию, `pprof` с `/debug/pprof/profile` и `async-profiler -e cpu`.

**Off-CPU профиль** — распределение времени, когда поток **не выполнял** код: ожидание I/O, блокировка, диспетчеризация, `park`/`sleep`. Именно off-CPU профиль объясняет, почему приложение медленное, но не загружает процессор.

**Развёртка стека (Stack Unwinding / Stack Walking)** — восстановление цепочки вызовов из счётчика программы (PC) в момент сэмплирования. Существует несколько несовместимых механизмов, и от выбранного зависят полнота и глубина стеков (см. [Развёртка стека](#развёртка-стека-unwinding)).

**Safepoint bias (смещение из-за safepoint)** — искажение профиля, при котором JIT-компилятор не может прервать поток для сэмплирования. Потоки, находящиеся в коде без точек safepoint, не попадают в профиль. Устраняется профилерами, не полагающимися на safepoint-механизм JVM (`async-profiler`, JFR).

**Назначение:**

- **Поиск «горячих» участков кода (Hotspots):** Идентификация функций и конкретных строк кода, потребляющих наибольшее количество ресурсов CPU.
- **Оптимизация аллокаций:** Обнаружение неэффективного использования оперативной памяти, частых выделений (allocations) и утечек (memory leaks).
- **Анализ блокировок:** Выявление проблем многопоточности, дедлоков и времени ожидания мьютексов (mutex contention).
- **Анализ off-CPU:** Объяснение задержек, при которых CPU не загружен — ожидание сети, диска, блокировок, очередей.

**Ключевой принцип Observability:** Профилирование отвечает на вопрос «Почему система работает медленно?» (до уровня строки кода), дополняя метрики («Что именно тормозит?») и трассировки («Где именно возникла задержка?»).

**См. также:** [Четыре столпа Observability](./four_pillars_of_observability.md) — фундаментальные концепции наблюдаемости.

## Базовые концепции

### Типы профилирования по режиму работы

| Режим | Описание | Примеры инструментов |
| :--- | :--- | :--- |
| **On-demand** | Запуск вручную для диагностики конкретного инцидента или в процессе разработки. | `pprof`, `py-spy`, `async-profiler`, `perf` |
| **Continuous** | Постоянный сбор профилей в фоне с минимальным оверхедом. | **[Непрерывное профилирование](../continuous_profiling.md)** |

Для глубокого изучения архитектуры, инструментов (Pyroscope, Parca) и практик постоянного сбора данных в продакшене см. основной документ: **[Непрерывное профилирование (Continuous Profiling)](../continuous_profiling.md)**.

### Типы профилей по ресурсам

| Профиль | Что измеряет | Когда использовать |
| :--- | :--- | :--- |
| **CPU Time** | Время, проведенное процессором непосредственно в функции. | Оптимизация тяжелых вычислений, парсинга, сериализации. |
| **Wall-clock Time** | Общее время выполнения (включая ожидание I/O, сети, блокировок). | Поиск задержек при работе с БД, внешними API или диском. |
| **Off-CPU Time** | Время вне CPU с разбивкой по причинам блокировки. | Tail latency, исчерпание пула потоков, диспетчеризация. |
| **Heap Memory** | Снимок объектов в куче (in-use). | Поиск утечек памяти (Memory Leaks) и анализ текущего состава памяти. |
| **Allocations** | Все выделения памяти (даже для удаленных объектов). | Снижение нагрузки на Garbage Collector (GC) и уменьшение фрагментации. |
| **Block / Mutex** | Время ожидания синхроиззации потоков. | Анализ конкурентности, поиск «бутылочных горлышек» в многопоточном коде. |

**Важное уточнение по памяти:** Профили могут отображаться как в **количестве объектов** (count), так и в **объеме памяти** (space). Оптимизация количества мелких объектов часто дает больший прирост производительности GC, чем оптимизация одного крупного массива.

**Правило выбора профиля:** начните с CPU. Если профиль показывает, что процессор занят, — оптимизируйте hot spots. Если профиль пуст или показывает 100% в одном и том же месте, а приложение при этом медленное, — переходите к wall-clock и off-CPU профилям. Смешивать эти два вопроса в один замер — самая частая ошибка при диагностике задержек.

### Мониторинг Garbage Collector (GC)
Профилирование Go, Java и других управляемых языков требует особого внимания к GC из-за эффекта **Stop-the-world** (полная остановка приложения при очистке памяти).

**Ключевые метрики для мониторинга:**
1.  **Частота запуска (GC Frequency):** Как часто срабатывает сборщик. Частые запуски при малом объеме памяти могут указывать на избыточные аллокации.
2.  **Продолжительность (GC Duration / Pause Time):** Сколько времени приложение простаивает. Высокое значение напрямую влияет на P99 задержку.
3.  **Темп аллокаций (Allocation Rate):** Скорость, с которой приложение выделяет память, в байтах в секунду. Это величина, определяющая частоту GC, а не абсолютный объём кучи: приложение с маленькой кучей, но высоким темпом аллокаций, собирает мусор чаще, чем приложение с большой кучей и низким темпом.

**Диагностика:** Если на графике кривые частоты и продолжительности GC сливаются в одну прямую линию, это означает, что приложение попало в «вечный цикл» сборки мусора (GC thrashing) и практически не выполняет полезную работу. Это критический сценарий, требующий немедленного увеличения лимитов памяти или оптимизации аллокаций.

**Связь с профилями:** профиль `alloc` показывает, *откуда* идёт поток аллокаций, а профиль `heap` (`inuse_space`) — *что* занимает память прямо сейчас. Диагностика утечки почти всегда требует обоих: растёт `inuse_space` — утечка; растёт `alloc_space`, а `inuse_space` стабилен — давление на GC без утечки.

### Методы сбора данных

1.  **Сэмплирование (Sampling):** Агент периодически (например, 100 раз в секунду) опрашивает стек вызовов.
    - **Плюсы:** Низкий оверхед, подходит для Production.
    - **Минусы:** Может пропускать очень короткие функции, выполняющиеся реже частоты сэмплирования.
2.  **Инструментирование (Instrumentation):** Вставка кода в начало и конец каждой функции.
    - **Плюсы:** 100% точность, учет каждого вызова.
    - **Минусы:** Огромный оверхед, значительное искажение результатов («эффект наблюдателя»), не рекомендуется для Production.
3.  **eBPF-профилирование:** Сбор стеков на уровне ядра Linux без изменения кода приложения.
    - **Плюсы:** Поддерживает все языки, нулевой оверхед в рантайме, видимость системных вызовов.
    - **Подробнее:** [eBPF — виртуальная машина ядра](../../Linux/Core/kernel/ebpf.md).

**Смещение из-за safepoint.** В JVM классические профилировщики (например, `hprof`) сэмплируют через механизм safepoint: JIT не может прервать поток, пока тот не достигнет точки, безопасной для остановки. Код, редко содержащий safepoint (длинные циклы, горячие методы), выпадает из профиля, а скомпилированный JIT-код попадает в него хуже интерпретируемого. Отсюда профили, в которых 90% времени отдано неожиданным функциям. `async-profiler` и JFR от safepoint-зависимости не зависят: первый использует собственный сигнальный механизм (`AsyncGetCallTrace`), второй — тот же. Если профиль JVM выглядит неправдоподобно, причина почти всегда в этом, а не в баге профилировщика.

### Развёртка стека (Unwinding)

Сэмплирование даёт адрес инструкции (PC). Чтобы получить цепочку вызовов, нужно «отмотать» (unwind) стек от текущего кадра в корневой. Механизмы различаются по точности, скорости и наличию ограничений:

| Механизм | Как работает | Плюсы | Ограничения |
| :--- | :--- | :--- | :--- |
| **Frame pointer (FP)** | Каждый кадр хранит указатель на предыдущий | Быстро, не требует отладочной информации | Требует `-fno-omit-frame-pointer`; компилятор при оптимизации может удалить FP |
| **DWARF unwinding** | Разбор `.eh_frame`/`.debug_frame` бинарника | Работает при `-O2` без FP | Требует не удалённых debug-секций; заметно дороже по CPU |
| **VM unwinding (JVM)** | Метаданные HotSpot о SafePoint и байткоде | Точные Java-стеки, работает с safepoint | Только JVM; может быть медленнее |
| **ctimer / itimer** | `timer_create` / `setitimer` + отдельный обработчик сигнала | Работает в контейнерах, не расходует файловые дескрипторы | Нет kernel-стеков, разрешение ограничено jiffies |
| **perf_events** | Аппаратный счётчик + сигнал по переполнению | Самая высокая точность, только kernel-стеки | Требует `perf_event_paranoid` и прав, конфликтует с seccomp |

**Практическое следствие:** строка `Стеки обрезаны (truncated)` в таблице неполадок почти всегда означает не лимит профилировщика, а неудачный режим развёртки. Проверяется это так:

```bash
# Есть ли frame pointer в собранном бинарнике
readelf --debug-dump=frame <binary> 2>/dev/null | head -5
# → dwarf_fde: 0x... cie=... pc=0x... func=main

# Собирается ли стек в принципе
perf record -F 99 -g --call-graph fp -p <PID> -- sleep 5 && perf report --stdio | head -20
# → Сравните глубину стеков: fp против dwarf
perf record -F 99 -g --call-graph dwarf -p <PID> -- sleep 5 && perf report --stdio | head -20
```

Если `fp` даёт стеки в одну функцию, а `dwarf` — полные, проблема в отсутствии frame pointer, и лечится она флагом сборки, а не настройкой профилировщика. Для C/C++/Rust: `-fno-omit-frame-pointer` в release-сборке либо сохранение `-g` для DWARF-разбора.

### Визуализация: Flame Graphs

**Flame Graph (Граф пламени)** — стандарт визуализации профилей.

- **Ширина блока:** Пропорциональна времени или ресурсам, потраченным функцией и всеми её дочерними вызовами.
- **Ось Y:** Глубина стека вызовов (снизу вверх).
- **Цвет:** Служит для визуального разделения пакетов/модулей или кодирует дифференциальные изменения.
- **Интерпретация:** Самые широкие блоки на верхних уровнях — это «горячие» функции (Hotspots), требующие оптимизации в первую очередь.
- **Дифференциальные Flame Graphs:** Сравнение двух профилей (например, «baseline» и «canary») для визуализации изменений производительности после изменений в коде.
- **Icicle Graph:** Инвертированная ориентация (стек растёт сверху вниз). Удобна, когда корневая функция интересует больше, чем отдельные горячие точки.

**Как читать график пламени за три шага:**

1. **Найти самую широкую платформу.** Она отвечает на вопрос «кто вообще потребил время», но почти никогда не является точкой оптимизации — это цикл обработки запросов или главный цикл.
2. **Спуститься на один уровень ниже внутри этой платформы.** Именно здесь начинается конкретная работа. Несколько широких блоков на этом уровне — независимые узкие места, их можно оптимизировать параллельно.
3. **Проверить форму блока.** Плоский широкий блок — работа внутри одной функции (цикл, парсинг, криптография). Узкий вертикальный «зуб» — частый, но дешёвый вызов (логирование, проверка флага, построение строки), который снижает overhead на каждой итерации.

**Ловушка отображения:** у графа пламени есть явная вертикальная и горизонтальная оси, но **нет числовой шкалы**. Один и тот же визуально идентичный график может означать и 1% и 40% CPU. Всегда сверяйтесь с числовым отчётом (`perf report --stdio`, `top` во встроенном интерфейсе `pprof`, раздел `Top` в отчёте `async-profiler`) прежде чем объявлять функцию узким местом.

### Off-CPU профилирование

Off-CPU профиль — это фундаментальное дополнение к CPU-профилю, а не его разновидность. Различия не в «точности», а в самом вопросе:

| | CPU (on-CPU) | Off-CPU |
| :--- | :--- | :--- |
| **Вопрос** | Где тратится процессорное время? | Где процессорное время **не** тратится? |
| **Метка времени** | Время нахождения на CPU | Время блокировки, с разбивкой по причине |
| **Показывает** | Вычислительные hot spots | I/O, блокировки, очереди, диспетчеризация |
| **Когда нужен** | Узкое место по throughput | Узкое место по latency (P99) |

**Механика сбора.** Off-CPU профиль строится из двух точек: момент постановки потока в состояние ожидания и момент его пробуждения. Ядро Linux отдаёт такие интервалы через трассировочные точки `sched:sched_switch` (причины: `sched_blocked_reason`, упреждение по кванту времени, переключение задачи), а eBPF-агент сопоставляет их со стеками, снятыми в момент блокировки. Отсюда важное ограничение: **реальная причина доступна не всегда** — если причина `WAITQ` или упреждение по таймеру, значит поток ждал на блокировке, но конкретный владелец блокировки находится в другом стеке.

**Как читать:** суммируйте интервалы по верхнему кадру. Широкий блок на уровне сетевого syscall (`read`, `recvmsg`) — приложение ждёт удалённый сервис; широкий блок на `futex` или `pthread_cond_wait` — конкуренция за общий ресурс; широкий блок внутри `io_uring` или прямых AIO-вызовов — диск. Сравнивайте off-CPU профиль с трассировками: если трассировка показывает 200 мс ожидания, а off-CPU профиль — 2 мс, значит задержка накопилась вне процесса (сеть, база, апстрим), и профилировать процесс бессмысленно.

**Инструменты:** `perf record -e sched:sched_switch -g` (подробно — в [perf: обзор](../../Linux/Diagnostics/Performance/perf.md)), `Parca` в режиме off-CPU, `pyroscope.ebpf` в Alloy, `async-profiler -e wall`, Go `block`/`mutex`-профили из `runtime/pprof`.

### Символизация: почему в графике hex-адреса

Отсутствие имён функций в профиле — почти всегда следствие того, что у символизатора нет бинарника нужной сборки. Механизм по умолчанию такой: профилировщик записывает в профиль идентификатор загруженного модуля (для ELF — GNU build ID из секции `.note.gnu.build-id`, для Go — `Go BuildID`), а бэкенд при отрисовке сопоставляет его с локальным бинарником и его DWARF-информацией.

**Язык за языком:**

- **Go.** С версии 1.9 `runtime/pprof` встрачивает имена функций прямо в профиль, поэтому `go tool pprof` читает локальный heap-профиль без бинарника. Но **внешним** бэкендам (Pyroscope, Parca, Grafana) бинарник всё равно нужен: они символизируют профиль у себя, сопоставляя его с локальной копией по build ID. Практические правила: не собирайте с `-ldflags="-s -w"` (флаги удаляют таблицу символов и DWARF — именно это ломает символизацию), сохраняйте бинарник каждого релиза в хранилище символов и добавляйте `-ldflags="-B gobuildid"` (генерация GNU build ID), если профили собирает внешний инструмент вроде `perf`. Флаг `-trimpath` на символизацию **не влияет**: по документации `go build` он «remove all file system paths from the resulting executable», то есть заменяет абсолютные пути на `module@version` или import path. Он ухудшает читаемость путей в `pprof -list` (и это осознанный компромисс в пользу воспроизводимых сборок), но имена функций и строки сохраняются полностью.
- **C / C++ / Rust.** Требуется не удалённая DWARF-информация: собирайте с `-g` (gcc/clang) или `-C debuginfo=2` (rustc) и раздавайте отладочные символы отдельно от бинарника (`objcopy --only-keep-debug`, затем `--strip-debug` у основного). В дистрибутивах Linux символы лежат в пакетах вида `linux-image-*-dbgsym` и подключаются через `/usr/lib/debug/.build-id/`, а удалённые символы приложений — через `debuginfod`.
- **Java.** Классы и методы читаются из JVM напрямую, символизация внешних не нужна. Проблемы возникают только для нативных фреймов (JNI, JDK internals) — там нужен бинарник JDK с символами и режим `--cstack dwarf` в `async-profiler` вместо `vm`.
- **Python.** `py-spy` получает имена из таблиц символов интерпретатора в памяти процесса; отдельные символы не нужны. Номера строк для Cython требуют сгенерированного `.c`/`.cpp` исходника.

**Практический приём:** если профиль пришёл с сервера, а локально символизировать нечего, сначала проверьте, что build ID в профиле совпадает с локальным бинарником — расхождение идентификаторов означает, что вы анализируете другой релиз, и любые выводы ошибочны.

```bash
# Build ID в локальном бинарнике
readelf -n ./app | grep -i 'build.id'
# → Build ID: 4f2c1a9b8e3d7c6a5b4f3e2d1c0b9a8f

# Build ID, записанный в профиль
go tool pprof -raw cpu.prof | grep -A5 Mappings
# → Mappings
# → 1: 0x400000/0x4ac000/0x0 /tmp/app [FN]
```

### OpenTelemetry Profiles (OTLP)

Четвёртый сигнал OpenTelemetry — профили — находится в статусе **Alpha** (объявлен публичным 26 марта 2026 года). Это технический факт, определяющий практические ограничения: сигнал не рекомендуется для критических production-нагрузок, а production-ready бэкенды ещё не появились. Формат данных (`profiles.proto`) построен поверх формата pprof и обеспечивает lossless round-trip между pprof и OTLP Profiles.

**Что это даёт архитектурно:**

- **Унификация сигналов.** Профиль переезжает по тому же OTLP, что и метрики, логи и трейсы, что упрощает корреляцию сигналов — переход от конкретного спана трейса к профилю CPU того же запроса.
- **Дедупликация на уровне словаря.** В отличие от других сигналов, где каждая запись самодостаточна, профили полны повторяющихся данных. Ссылка на общий словарь (`Dictionary`) вместо инлайна радикально сокращает размер полезной нагрузки — именно это, а не «колончатое сжатие Apache Arrow», является причиной экономии трафика.
- **Дедупликация на приёмной стороне.** Поле `original_payload_format` позволяет хранить исходный формат (`pprof`, `jfr`, `linux_perf`) без потерь.

**Обязательные условия работы с сигналом:**

- Collector **v0.148.0 или новее**;
- коллектор запускается с feature gate `--feature-gates=service.profilesSupport` (или `+service.profilesSupport` в виде аргумента);
- пайплайн типа `profiles` в секции `service`.

Без feature gate коллектор стартует, принимает конфигурацию и молча не обрабатывает профили — типичная причина «профили не приходят».

## Предварительные требования

### Права и ограничения ядра

Профилирование почти всегда требует повышенных прав. Минимальный набор проверок перед началом работы:

```bash
# 1. Ограничение perf для непривилегированных пользователей
cat /proc/sys/kernel/perf_event_paranoid
# → 2   (2 = только user-space измерения; -1 = полный доступ)

# Разрешить user-space профилирование обычному пользователю
sudo sysctl -w kernel.perf_event_paranoid=1

# 2. Отладочные символы ядра (для kernel-стеков и символизации)
ls /usr/lib/debug/boot/ 2>/dev/null | head
# → vmlinux-<version>
# Отсутствует? Установите пакет linux-image-<version>-dbgsym

# 3. BTF для eBPF/CO-RE
ls -l /sys/kernel/btf/vmlinux
# → -r--r--r-- 1 root root 5M ... /sys/kernel/btf/vmlinux
# Файла нет — ядро собрано без CONFIG_DEBUG_INFO_BTF

# 4. Запрет непривилегированного BPF
cat /proc/sys/kernel/unprivileged_bpf_disabled
# → 0   (0 = непривилегированный BPF разрешён)

# 5. ptracer: нужен для чтения памяти чужого процесса (py-spy, gdb)
cat /proc/sys/kernel/yama/ptrace_scope
# → 1   (1 = только потомки; 0 = любой процесс)
```

**Про `perf_event_paranoid` и BTF.** Значения этих параметров зависят не столько от версии ядра, сколько от дистрибутива: `CONFIG_DEBUG_INFO_BTF` и генерация `/sys/kernel/btf/vmlinux` пришли в ядро 5.4, но дистрибутивы включали их неравномерно (RHEL 8.2+, Fedora 31+, Ubuntu 20.10+, Debian 11). Ориентироваться нужно на наличие файла, а не на цифру в версии ядра. Если BTF нет, eBPF-профилирование в режиме CO-RE не заработает; варианты — обновление ядра, HWE-ядро или внешний BTF-файл.

### Подготовка приложения

| Требование | Зачем | Как проверить |
| :--- | :--- | :--- |
| Профайлер встроен в рантайм или доступен снаружи | Определяет метод сбора | `pprof -V`, `py-spy --version`, `./asprof --version` |
| Бинарник соответствующего релиза доступен символизатору | Без него в графике hex-адреса | `readelf -n <binary> \| grep -i build.id` |
| Отладочные символы не удалены при сборке | Символизация C/C++/Rust | `readelf -S <binary> \| grep debug` |
| Endpoint профилирования не торчит наружу | pprof на `0.0.0.0:6060` — вектор атаки | `ss -tlnp \| grep 6060` |

**Безопасность endpoint-ов профилирования.** `net/http/pprof` в Go и аналогичные HTTP-интерфейсы других рантаймов дают полный контроль над процессом: heap-профиль раскрывает структуру данных, `goroutine` — внутренние строки и пути, а сам endpoint в старых версиях Go позволял запускать произвольный код. Слушайте только на localhost или на отдельном интерфейсе управления, ограничивайте доступ на сетевом уровне и включайте endpoint только когда он нужен. В контейнерах выносите профилирование в debug-сессию, а не в постоянно включённый порт.

## Практические сценарии

### Сценарий 1: Поиск утечки памяти в Go

**Ситуация:** Постоянный рост RSS (Resident Set Size) процесса, приводящий к OOMKilled.

**Команды:**
```bash
# 1. Снятие текущего снимка кучи (heap)
curl -o heap.prof http://localhost:6060/debug/pprof/heap
# →  сохраняет gzip-сжатый protobuf-профиль

# 2. Визуализация в браузере для анализа аллокаций
go tool pprof -http=:8080 heap.prof
# → Откроется http://localhost:8080 с интерактивным графом вызовов

# 3. Сравнение двух снимков (дифф) для поиска растущих объектов
# Снимаем heap_before.prof, ждем 10 минут, снимаем heap_after.prof
go tool pprof -http=:8080 -base heap_before.prof heap_after.prof
# → Показывает только объекты, выросшие между снимками
```

**Диагностика по представлениям.** `go tool pprof` показывает четыре представления одних и тех же данных, и переключение между ними отвечает на разные вопросы:

```bash
# inuse_space — что занимает память сейчас (по умолчанию)
go tool pprof -http=:8080 -inuse_space heap.prof

# inuse_objects — сколько объектов, полезно против фрагментации
go tool pprof -http=:8080 -inuse_objects heap.prof

# alloc_space — суммарные аллокации за всё время жизни процесса
go tool pprof -http=:8080 -alloc_space heap.prof

# Исходный код горячей функции с подсветкой строк
go tool pprof -http=:8080 -list 'myapp.NewCache' heap.prof
# → Showing nodes accounting for 2.19MB, 71.32% of 3.07MB total
# →   runtime.mallocgc
# →     1.02MB  33.16%  myapp.(*Cache).Put
# →                /src/cache.go:84
```

Растущий `inuse_space` означает утечку (объекты не освобождаются). Растущий `alloc_space` при стабильном `inuse_space` означает не утечку, а давление на сборщик мусора — приложение выделяет и освобождает, но слишком часто.

**Профиль горутин (goroutine) — отдельный инструмент.** Он не про ресурсы, а про зависшие и утекающие горутины:

```bash
curl -o goroutine.prof http://localhost:6060/debug/pprof/goroutine
go tool pprof -http=:8080 goroutine.prof
# → Утечка горутин видна как сотни одинаковых стеков, накопленных в Bottom-up
```

**Валидация:** сравните сумму `inuse_space` с `VmRSS` процесса. Расхождение больше чем в 2 раза означает, что профиль не описывает всю память — смотрите на `heap_inuse` в рантайм-метриках и на `mheap_inuse` (`runtime.ReadMemStats`), чтобы отделить кучу от стеков горутин и метаданных.

### Сценарий 2: Профилирование Python через py-spy

**Ситуация:** Процесс загружает CPU на 100%, нужно понять, какая часть кода тормозит без перезапуска приложения.

```bash
# Просмотр "top" функций в реальном времени (без оверхеда)
py-spy top --pid <PID>
# → PID  Python  %CPU  %GIL  Threads  Thread%  Process%
# → 4821  main   99.0  98.5  1        -       99.0  myapp.worker

# Генерация Flame Graph на 30 секунд
py-spy record -o flamegraph.svg --duration 30 --pid <PID>
# → Recording... done

# Профилирование с учетом нативных C-расширений
py-spy record --native -o native_flame.svg --pid <PID>

# Только потоки, удерживающие GIL (GIL — реальный источник сериализации)
py-spy record --gil -o gil.svg --duration 30 --pid <PID>

# Приложение с multiprocessing/gunicorn — включить дочерние процессы
py-spy record --subprocesses -o all.svg --duration 30 --pid <PID>

# Текущий стек каждого потока + локальные переменные (когда нужно понять, где зависло)
py-spy dump --pid <PID> --locals
```

**Почему py-spy безопасен для production.** Он написан на Rust, запускается вне профилируемого процесса и читает память через `process_vm_readv` (Linux), `vm_read` (macOS) или `ReadProcessMemory` (Windows). Код приложения не изменяется, GIL не блокируется, а сам процесс не останавливается. Если даже это нежелательно, `--nonblocking` читает состояние интерпретатора на лету, вообще не останавливая цель, ценой небольшого числа ошибок сэмплирования и частичных кадров.

**Ограничения, о которых стоит знать заранее:**

- `py-spy` **пропускает потоки, которые считает простаивающими**. Состояние берётся из `/proc/<PID>/stat` до паузы процесса, поэтому возможны ложные срабатывания. Отключается флагом `--idle`.
- Определение GIL опирается на символ `_PyThreadState_Current` / `_PyRuntime`. Если символа нет в вашей сборке Python, определить владельца GIL не удастся.
- Поддержка нативных расширений (`--native`) есть не на всех платформах: на Linux покрыты x86-64, i686 и Aarch64, на Windows — только x86-64. Номера строк для Cython дополнительно требуют сгенерированного `.c`/`.cpp` файла.

### Сценарий 3: Java Profiling (async-profiler)

**Ситуация:** Высокая задержка GC или подозрение на блокировки в многопоточном приложении.

**Команды:**
```bash
# Профилирование CPU на 60 секунд с генерацией HTML-отчета
./asprof -d 60 -f cpu.html <PID>
# → Profiling started, output will be written to cpu.html

# Профилирование аллокаций памяти (поиск источника мусора)
./asprof -d 60 -e alloc -f alloc.html <PID>

# Профилирование Wall-clock (ожидание I/O и блокировок)
./asprof -d 60 -e wall -f wall.html <PID>

# Профилирование конкуренции за блокировки (верхний кадр — класс блокировки)
./asprof -d 60 -e lock -f lock.html <PID>

# Нативные блокировки pthread (не мониторы JVM)
./asprof -d 60 --nativelock 10ms -f nativelock.jfr <PID>

# Несколько событий одновременно (единственный выходной формат — JFR)
./asprof -e cpu --wall 100ms -f combined.jfr <PID>
# → В записи будут jdk.ExecutionSample, jdk.ObjectAllocationInNewTLAB,
# → jdk.ObjectAllocationOutsideTLAB, jdk.JavaMonitorEnter, jdk.ThreadPark
```

**Выбор режима сэмплирования CPU.** В `async-profiler` их три, и они дают разные картины:

| Режим | Механизм | Kernel-стеки | Работает в контейнерах | Ограничения |
| :--- | :--- | :--- | :--- | :--- |
| `-e cpu` | `perf_events` | Да | Нет по умолчанию | Требует доступного `perf_event`, упирается в `perf_event_paranoid`, seccomp и лимит ФД |
| `-e ctimer` | `timer_create` | Нет | Да | Разрешение ограничено jiffies (мин. 4–10 мс) |
| `-e itimer` | `setitimer(ITIMER_PROF)` | Нет | Да | Один сигнал на процесс; распределяется по потокам неравномерно |

`-e cpu` автоматически деградирует до `ctimer`, если kernel-профилирование недоступно. Форсировать user-space-only вариант: `-e cpu-clock --all-user`. В выводе это видно по наличию блоков `vm` / `vmx` во вкладке Threads — они есть только у режимов с VM-развёрткой.

**Валидация:**
1. Открыть `cpu.html` в браузере.
2. Убедиться, что стеки символизированы (видны имена Java-классов).
3. Проверить раздел `Thread View` для выявления потоков, проводящих больше всего времени в состоянии `BLOCKED`.

### Сценарий 3a: JFR против async-profiler

Оба инструмента закрывают Java, но решают разные задачи. Выбор определяется тем, что вы диагностируете.

| Критерий | JFR (Java Flight Recorder) | async-profiler |
| :--- | :--- | :--- |
| **Лицензия** | Включён в OpenJDK с версии 11, бесплатно | Open source (Apache 2.0) |
| **Внешний агент** | Не нужен, работает внутри JVM | Нужен бинарник + доступ к процессу |
| **Overhead** | `default` — постоянный, минимальный; `profile` — заметно выше | Зависит от события; `alloc` и `lock` дороже `cpu` |
| **Формат вывода** | JFR (`.jfr`), открывается в JMC | HTML, текст, JFR, collapsed |
| **Типы замеров** | Событийная модель: CPU, аллокации, GC, I/O, блокировки, потоки, исключения | Сэмплирование по событию: `cpu`, `alloc`, `wall`, `lock`, `nativemem`, perf-счётчики |
| **Защита от safepoint bias** | Да | Да |
| **Когда выбирать** | Постоянная диагностика в production, полная картина состояния JVM, событийный анализ | Точечная задача (hot spots, конкуренция, аллокации), быстрый on-demand замер, wall-clock и нативные блокировки |

**Практическое правило:** JFR — для «что вообще происходит в JVM», `async-profiler` — для «где именно тратится время в этой конкретной функции». JFR даёт событийную картину (частота GC, паузы, состояния потоков, I/O), `async-profiler` — сэмплированную, зато с точностью до строки и без safepoint-искажений. Их выводы расходятся именно там, где safepoint bias наиболее выражен: JFR показывает реальную картину, а «классический» профилировщик с safepoint-зависимостью — искажённую.

Команды `jcmd` для запуска, настройки и остановки JFR, а также работа с ним в JMC разобраны в [Управление и тюнинг Java (JVM) в Linux](../../Linux/Development/java_management.md#jfr-java-flight-recorder--практические-сценарии).

**Минимальный JFR-замер для production-инцидента:**

```bash
# 60 секунд с настройкой profile, с путем к GC roots для поиска утечек
jcmd <PID> JFR.start name=incident settings=profile path-to-gc-roots=true duration=60s filename=/var/tmp/incident.jfr
# → Created recording 1. Use "jcmd <PID> JFR.check" to see the progress

jcmd <PID> JFR.check
# → Recording 1: 24s (of 60s), 41.2 MB

jcmd <PID> JFR.dump name=incident filename=/var/tmp/incident-early.jfr
# → Слить запись на диск до истечения срока

# Сводка по профилю без GUI (быстрый триаж на сервере)
jfr summary /var/tmp/incident.jfr
# → Type                 Samples  Percentage  Event
# → jdk.ExecutionSample     4821        31.4%  Execution Sample
# → jdk.GCPhasePause        1204         7.8%  GC Phase Pause
```

`settings=profile` увеличивает объём данных и оверхед, поэтому применяйте его только на время активной диагностики. Для постоянного фонового профилирования используйте `settings=default` — он рассчитан на длительную запись с минимальным влиянием на приложение.

### Сценарий 4: Настройка сбора профилей в OpenTelemetry Collector

**Ситуация:** Приём профилей через OTLP и отправка в центральное хранилище Pyroscope.

**Критично:** поддержка сигнала profiles — это **alpha**, и она включается feature gate. Коллектор версии ниже 0.148.0 её не знает.

**Конфигурация Collector:**
```yaml
# Запускать с флагом: --feature-gates=service.profilesSupport
# Образ: otel/opentelemetry-collector-contrib:0.162.0 или новее

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 5s
    send_batch_size: 1024
  k8sattributes/profiles:      # стабилизирует имена сервисов и подов
    passthrough: false

exporters:
  # Pyroscope принимает профили по OTLP gRPC на порту 4040
  otlp_grpc/pyroscope:
    endpoint: pyroscope:4040
    tls:
      insecure: true
    sending_queue:
      enabled: true

service:
  pipelines:
    profiles:
      receivers: [otlp]
      processors: [batch, k8sattributes/profiles]
      exporters: [otlp_grpc/pyroscope]
```

**Валидация:**
1. Проверить логи коллектора на отсутствие ошибок `exporting failed`.
2. Зайти в UI Pyroscope и убедиться в наличии новых профилей от соответствующего сервиса.
3. Убедиться, что в профиле есть атрибуты `service.name` и `service.version` — без них профили всех сервисов сливаются в один.

**Альтернатива — eBPF-профилировщик на базе Collector.** Отдельный дистрибутив `otel/opentelemetry-collector-ebpf-profiler` снимает системные CPU-профили со всех процессов хоста через eBPF, минуя агентов в приложениях:

```yaml
receivers:
  profiling:
    samples_per_second: 97     # значение по умолчанию; 100 выравнивает сэмплы
                              # с частотой планировщика и даёт артефакты дифференцирования

exporters:
  otlp_grpc:
    endpoint: pyroscope:4040
    tls:
      insecure: true

service:
  pipelines:
    profiles:
      receivers: [profiling]
      exporters: [otlp_grpc]
```

Такой коллектор требует `privileged: true`, `hostPID: true` и монтирования `/sys/kernel`, `/proc` и `/sys/fs/cgroup` с хоста. В Kubernetes его разворачивают как DaemonSet. Число 97 в `samples_per_second` выбрано не случайно: сэмплирование строго на 100 Гц синхронизируется с тиком планировщика, и дифференциальные профили начинают показывать ложные изменения в потоках, пробуждённых планировщиком.

### Сценарий 5: Диагностика GPU-ускоренных рабочих нагрузок

**Ситуация:** Процесс на сервере с видеокартой (транскодирование, рендеринг, инференс) использует GPU неэффективно: утилизация ниже ожидаемой при нормальной нагрузке, либо CPU-bound вместо GPU-bound.

**Команды (NVIDIA Nsight Systems):**
```bash
# Профилирование процесса на 30 секунд (nsys profile запускает процесс сам)
nsys profile -d 30 -o gpu_report --trace=cuda,nvtx,osrt ./app
# → Generated /tmp/gpu_report.nsys-rep

# Статистика по отчёту
nsys stats gpu_report.nsys-rep
# → CUDA GPU Kernel Summary:
# → Time(%)  Total Time  Instances  Name
# →    82.4%   24.712s      1204  cudaLaunchKernel (device-side)

# Трассировка конкретного приложения в терминале
nsys profile --stats=true -o gpu_report ./app
# → Печатает сводку сразу после завершения
```

**Интерпретация баланса CPU/GPU.** Главный вопрос этого сценария — кто является узким местом:

- **CPU-bound при наличии GPU** — узкое место в подготовке данных, копировании на устройство или в коде хоста. Профиль CPU (`nsys` даёт его в том же отчёте) покажет, где именно теряется время.
- **Низкая утилизация GPU при высокой утилизации CPU** — приложение не успевает наполнять очередь команд. Обычно это `cudaMemcpy` на каждый вызов или отсутствие пакетной обработки.
- **Периодические провалы утилизации** — признак того, что хост-часть цикла содержит блокировки или синхронные ожидания. Проверяется off-CPU профилем.
- **Длинные единичные kernel-вызовы** — кандидаты на оптимизацию алгоритма; проверяется `ncu` (Nsight Compute) с флагом `--set full` для детального разбора одного ядра.

```bash
# Поиск самых длительных ядер (top 10)
nsys stats --report cuda_gpu_kern_sum gpu_report.nsys-rep
# → Сортировка по Total Time, обращать внимание на Instances: большое
# → число коротких вызовов указывает на проблему с батчингом, а не с ядром
```

### Сценарий 6: Профилирование системы на уровне ядра (perf + Linux)

**Ситуация:** Необходимо понять, почему система тормозит на уровне ОС (системные вызовы, контекстные переключения, кэш-промахи).

**Команды:**
```bash
# Профилирование CPU на уровне системы (все процессы)
sudo perf record -F 99 -g -p <PID> -- sleep 30
# → [ perf record: Captured and wrote 3.214 MB perf.data ]

# Генерация Flame Graph из системного профиля
sudo perf script | stackcollapse-perf.pl | flamegraph.pl > system_flame.svg
# → Запишет интерактивный SVG

# Анализ кэш-промахов (cache misses)
sudo perf stat -e cache-misses,cache-references -p <PID> -- sleep 10
# →  Performance counter stats for 12345:
# →             1,234,567      cache-misses
# →            12,345,678      cache-references
# →  Performance counter stats elapsed time: 10.001234789 seconds

# Анализ контекстных переключений
sudo perf stat -e context-switches,cpu-migrations,page-faults -p <PID> -- sleep 10
```

**Интерпретация:**
- Высокий % `cache-misses` → проблемы с локальностью данных (Data Locality)
- Много `context-switches` → чрезмерная конкуренция за CPU между потоками
- Доминирование `system` time → приложение тратит время на syscall (оптимизировать I/O)
- Высокие `cpu-migrations` → поток мигрирует между ядрами и теряет кэш; лечится привязкой (`taskset`) или увеличением размера кэша CPU

Подробный разбор `perf`, включая `perf mem`, `perf c2c`, `perf kmem`, Top-Down анализ и работу с Intel PT, см. в [perf: обзор](../../Linux/Diagnostics/Performance/perf.md).

### Сценарий 7: Профилирование в Docker-контейнере

**Ситуация:** Приложение в контейнере потребляет много CPU, нужно найти горячие точки без перезапуска.

**Вариант A — профилирование с хоста (предпочтительный).** Не требует ни изменения манифеста, ни перезапуска:

```bash
# Найти PID процесса в namespace хоста
docker inspect --format '{{.State.Pid}}' <container_name>
# → 4821

# Профилирование из хостовой системы
py-spy record --pid 4821 -o /tmp/container_flame.svg --duration 30
sudo perf record -F 99 -g -p 4821 -- sleep 30
```

**Вариант B — агент внутри контейнера.** Требует выдачи capability, иначе чтение памяти процесса блокируется:

```bash
# Запуск контейнера с разрешённым ptrace
docker run --cap-add=SYS_PTRACE ...

# Или в docker-compose.yml
# services:
#   app:
#     cap_add:
#       - SYS_PTRACE
```

```bash
# Python: профилирование внутри контейнера
docker exec -it <container> py-spy record -o /tmp/cpu.svg --duration 30 --pid 1

# Go: endpoint pprof слушает только localhost внутри контейнера,
# поэтому снимаем снаружи через IP контейнера
docker inspect --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' <container_name>
curl -o heap.prof http://<container_ip>:6060/debug/pprof/heap
go tool pprof -http=:8080 heap.prof

# Java: запуск async-profiler в контейнере
docker exec -it <container> /path/to/asprof -d 60 -f /tmp/cpu.html <PID>
docker cp <container>:/tmp/cpu.html ./cpu.html
```

**Ограничение `nsenter`.** Команда `nsenter -t <PID> -n ...` входит только в **сетевой** namespace. `py-spy` и `perf` нуждаются в доступе к `/proc` целевого процесса и его памяти, то есть в **mount** и **PID** namespaces. Полный вход выглядит так, а одна только `-n` бесполезна:

```bash
nsenter -t 4821 -m -p --preserve-credentials py-spy top --pid 1
# → -m: mount namespace (/proc)
# → -p: PID namespace (цель становится PID 1)
```

### Сценарий 8: Анализ production-инцидента через профили

**Ситуация:** После деплоя начала расти P99 задержка API. Нужно быстро найти причину.

**Пошаговый алгоритм:**
```bash
# 1. Проверить текущий профиль CPU в реальном времени
# (если включено Continuous Profiling — посмотреть за последние 5 минут)
# Или снять on-demand:
curl -o cpu.prof 'http://localhost:6060/debug/pprof/profile?seconds=30'
# → Фактическая длительность — 30 секунд (значение по умолчанию)

# 2. Построить Flame Graph и найти горячие функции
go tool pprof -http=:8080 cpu.prof

# 3. Сравнить с baseline (до деплоя)
go tool pprof -http=:8080 -base cpu_before_deploy.prof cpu_after_deploy.prof
# → -base вычитает samples базового профиля, оставляя только дельту

# 4. Если нашли подозрительную функцию — посмотреть её source
go tool pprof -http=:8080 -list 'problemFunction' cpu.prof

# 5. Проверить аллокации памяти (если подозрение на GC)
curl -o alloc.prof http://localhost:6060/debug/pprof/allocs
go tool pprof -http=:8080 alloc.prof
```

**Чек-лист диагностики:**
- [ ] Снять CPU profile на 30 секунд
- [ ] Снять Heap profile для анализа памяти
- [ ] Снять Block profile для анализа блокировок
- [ ] Сравнить с baseline (до инцидента или до деплоя)
- [ ] Проверить GC metrics (частота, продолжительность, темп аллокаций)
- [ ] Проверить системные метрики (CPU, RAM, Disk I/O)
- [ ] Если CPU не загружен — снять wall-clock / off-CPU профиль вместо CPU
- [ ] Сверить задержку с трейсами: находятся ли спаны за пределами процесса

### Сценарий 9: Профилирование сетевых задержек (Network Profiling)

**Ситуация:** API-вызовы к внешнему сервису стали медленными, но CPU приложения не загружен.

**Команды:**
```bash
# Анализ TCP-соединений и задержек
ss -ti | grep -E "rtt|retrans"
# → rtt:20.815/6.914 min:20.815 max:23.287
# → retrans:0/12

# Профилирование syscall (включая сетевые)
strace -c -p <PID> -e trace=network
# → вывод счётчика вызовов и времени

# Анализ DNS-задержек
dig +stats example.com
# → Query time: 84 msec

# Мониторинг сетевых соединений в реальном времени по процессам
nethogs -p <PID>
```

**Интерпретация:**
- Высокий `rtt` → проблема на стороне удаленного сервиса или в сети
- Много `retrans` → потеря пакетов, проблема с сетью
- Долгие `connect` → DNS-задержки или проблемы с firewall

**Важно:** этот сценарий — пример задачи, которую не решает CPU-профиль. При 0% CPU wall-clock профиль покажет, что поток находится в `read`/`recvmsg`, и это направит диагностику в сеть, а не в код.

### Сценарий 10: Сбор профилей через Grafana Alloy

**Ситуация:** Настройка непрерывного профилирования на bare-metal серверах.

**Конфигурация Alloy** (язык конфигурации — River, расширение файлов — `.alloy` или `.river`):

```alloy
pyroscope.write "profiles" {
  endpoint {
    // Базовый URL хранилища. Путь /api/v1/write компонент подставляет сам —
    // указывать его вручную не нужно.
    url = "http://pyroscope:4040"
  }
  external_labels = {
    "env" = "production",
  }
}

pyroscope.scrape "default" {
  targets = [
    { "__address__" = "app1:6060", "service_name" = "app1" },
    { "__address__" = "app2:6060", "service_name" = "app2" },
  ]
  scrape_interval      = "15s"    // как часто опрашивать target
  delta_profiling_duration = "14s" // окно сэмплирования, по умолчанию
  forward_to = [pyroscope.write.profiles.receiver]

  profiling_config {
    profile.process_cpu {
      enabled = true
    }
    profile.memory {
      enabled = true
    }
    profile.mutex {
      enabled = true
    }
    profile.block {
      enabled = true
    }
    profile.goroutine {
      enabled = true
    }
  }
}
```

**Ключевые детали конфигурации:**

- `delta_profiling_duration` по умолчанию `14s` при `scrape_interval` `15s`. Значение не должно превышать `scrape_interval`, иначе HTTP-запрос будет усечён. Время простоя между окнами = `scrape_interval - delta_profiling_duration`, то есть в примере выше профиль пишется 14 секунд из каждых 15.
- Блок `profiling_config` определяет, какие типы профилей запрашиваются. По умолчанию включены не все; для Go доступны также `profile.godeltaprof_memory`, `profile.godeltaprof_mutex` и `profile.godeltaprof_block` (альтернативные реализации через Delve с поддержкой inlined-фреймов), которые полезнее стандартных при отладке сложной конкурентности.
- `pyroscope.write` удаляет все метки, начинающиеся с `__`, перед отправкой, — кроме тех, что заданы явно. Поэтому `service_name` в `targets` задаётся как обычная метка и доезжает до хранилища.
- `external_labels` добавляются ко всем профилям этого экземпляра — удобное место для `env`, `region`, `cluster`.

**Валидация:**
1. Проверить логи Alloy: `journalctl -u alloy -f` — ошибки `pyroscope.write` указывают на недоступность хранилища или неверный URL.
2. Открыть UI Pyroscope и проверить наличие данных.
3. Убедиться, что профили отображаются корректно с правильными `service_name`.

**Альтернатива для систем без pprof-эндпоинтов** — компонент `pyroscope.ebpf`, собирающий профили через eBPF:

```alloy
pyroscope.ebpf "system" {
  targets         = discovery.docker.linux.targets
  forward_to      = [pyroscope.write.profiles.receiver]
  collect_interval = "15s"
  sample_rate      = 97        // по умолчанию
  demangle         = "full"    // C++ demangle: none | simplified | templates | full
}

discovery.docker "linux" {
  host             = "/var/run/docker.sock"
  refresh_interval = "5s"
}
```

### Сценарий 11: Анализ блокировок в многопоточном приложении (Go)

**Ситуация:** Приложение с высоким параллелизмом не использует CPU на 100%, подозрение на contention.

**Команды:**
```bash
# Снятие профиля блокировок (требует runtime.SetBlockProfileRate)
curl -o block.prof http://localhost:6060/debug/pprof/block

# Анализ
go tool pprof -http=:8080 block.prof

# Сравнение двух снимков блокировок
go tool pprof -http=:8080 -base block_before.prof block_after.prof
```

**Включение сбора в приложении:**

```go
import "runtime"

func init() {
    // Блокировки: 1 — сэмплировать каждое событие
    runtime.SetBlockProfileRate(1)
    // Мьютексы: сэмплировать конкуренцию из N (N=1 — все события).
    // Значение по умолчанию 0 — профиль мьютексов выключен.
    runtime.SetMutexProfileFraction(1)
}
```

Обе функции **обязаны** быть вызваны до начала работы приложения. `SetBlockProfileRate(1)` безопасен для production (профиль содержит только сэмплы заблокированных горутин), `SetMutexProfileFraction(1)` — заметно дороже, так как отслеживает каждую неудачную попытку захвата.

**Интерпретация:**
- Широкие блоки в Flame Graph на уровне `sync.Mutex.Lock` → проблемные участки кода
- Мало времени в `running` state, много в `waiting` → потоки ждут блокировок
- Широкий блок на уровне `runtime.chanrecv` → узкое место в каналах, а не в мьютексах

### Сценарий 12: Профилирование в контейнерном и bare-metal окружении без агентов

**Ситуация:** Минимальная инфраструктура, нужно профилировать приложение без установки дополнительных агентов.

```bash
# 1. Стандартный инструмент ядра — не требует ничего, кроме пакета linux-tools
sudo perf record -F 99 -g -p <PID> -- sleep 30
sudo perf report --stdio | head -30

# 2. Быстрый анализ через /proc без дополнительных зависимостей
cat /proc/<PID>/status | grep -E "VmRSS|VmSize|Threads"
# → VmRSS:    482304 kB
# → Threads:  64
cat /proc/<PID>/io
# → rchar: 918273645
# → syscr: 1284730

# 3. Построчный профиль потоков
top -p <PID> -H    # -H показывает потоки

# 4. Подсчёт и тайминги системных вызовов
strace -c -p <PID> -e trace=all
# → вывод: количество вызовов, ошибки, время в userspace и ядре

# 5. eBPF-однострочник для OTH-анализа (off-thread), если bpftrace доступен
sudo bpftrace -e 'kprobe:finish_task_switch { @[kstack] = count(); }' > offcpu.folded
```

**Преимущества:** `perf` входит в поставку ядра, `strace` и `bpftrace` ставятся из стандартных репозиториев, `/proc` и `top` присутствуют всегда. Подходит для хостов, куда нельзя поставить агента мониторинга.

**Ограничение `/proc`:** значения в `/proc/<PID>/status` — мгновенный срез, а не профиль. `VmRSS` растёт монотонно и ничего не говорит о том, какой код за это отвечает. Это точка входа, а не инструмент анализа.

### Сценарий 13: Профилирование Node.js

**Ситуация:** Event-loop приложения на Node.js потребляет CPU или накапливает задержку; нужно понять, где тратится время без установки сторонних пакетов.

```bash
# 1. CPU-профиль V8 — пишется при старте, штатный механизм движка
node --cpu-prof --cpu-prof-dir=/var/tmp --cpu-prof-interval=1000 app.js
# → В /var/tmp появится файл вида
# → isolate-0x00007f...-v8-<pid>.<tid>.cpuprofile
# → Формат .cpuprofile — это speedscope, открывается напрямую
# → https://speedscope.app или в Grafana Pyroscope/Phlare

# 2. Встроенный tick-профилировщик Node.js (классический, с C++-разбивкой)
NODE_ENV=production node --prof app.js
# → Создаёт isolate-0x...-v8.log в рабочем каталоге

node --prof-process isolate-0x...-v8.log > processed.txt
# → Покажет разбивку по C++ / JavaScript / GC / Idle и bottom-up
```

**Разбор `processed.txt`.** Секция `[C++]` в выводе `--prof-process` показывает, какую долю времени занимает нативный код. Если она превышает ~90%, почти всё время уходит в нативные расширения (криптография, сериализация, работа с базой) — профилировать нужно их, а не JavaScript-код. Секция `[Bottom up (heavy) profile]` показывает вызывающих: именно она отвечает на вопрос «кто вызывает эту функцию».

**Профилирование по сигналу (без перезапуска и без `--cpu-prof`):**

```bash
# Снять heap snapshot по требованию — файл создаётся, процесс продолжает работать
kill -USR2 <PID>
# → Требует запуска с --heapsnapshot-signal=USR2

# Снять снимок кучи при приближении к лимиту (автоматически)
node --heapsnapshot-near-heap-limit=3 app.js
# → Снимки сбрасываются на диск без участия процесса
```

**Диагностика event loop.** Профилирование CPU не отвечает на вопрос «почему медленно при низкой нагрузке на CPU» — для event-loop приложений этот вопрос решается измерением лага цикла событий, а профилирование используется, когда лаг уже измерен и нужно понять, что его вызывает. Метрики лага и пороги настроены в [Метрики рантайма приложений](./application_runtime_metrics.md#3-nodejs).

### Сценарий 14: Корреляция профиля с трассировкой и метриками

**Ситуация:** P99 вырос, но непонятно, в каком сервисе и в каком запросе. Есть трейсы, есть профили, есть метрики — они не связаны.

**Шаг 1 — сузить область по метрикам.** Найдите сервис и временное окно до обращения к профилям; профилировать «весь кластер» в поисках нужного — дорого.

```promql
# Скорость аллокаций по сервису — коррелирует с давлением на GC
rate(process_runtime_go_memstats_alloc_bytes_total{service="api"}[5m])

# Паузы GC — прямой признак того, что нужен alloc-профиль
rate(jvm_gc_pause_seconds_sum{service="api"}[5m])
```

**Шаг 2 — спуститься от трейса к профилю.** Трейс даёт конкретный `trace_id` медленного запроса. Профили, собранные в том же временном оконе, показывают, какие функции были горячими в этот момент:

1. Выберите медленный спан по `trace_id` в Tempo/Jaeger.
2. Зафиксируйте временной диапазон спана (с учётом часового пояса хранилища — расхождение timezone обесценивает корреляцию).
3. Откройте профиль того же сервиса за этот диапазон в Pyroscope/Grafana.
4. Проверьте, присутствует ли обработчик этого эндпоинта в горячих функциях.

**Шаг 3 — проверить гипотезу дифференциальным профилем.** Самая надёжная связка: снять baseline до деплоя и сравнить.

```bash
# Снять профиль на каждом хосте ДО деплоя
curl -o /var/tmp/cpu_before.prof 'http://localhost:6060/debug/pprof/profile?seconds=30'
# ... деплой ...
# Снять профиль с тем же интервалом нагрузки
curl -o /var/tmp/cpu_after.prof 'http://localhost:6060/debug/pprof/profile?seconds=30'

# Показать только изменения
go tool pprof -http=:8080 -base /var/tmp/cpu_before.prof /var/tmp/cpu_after.prof
```

В дифференциальном графике красным выделены функции, ставшие медленнее, синим — ставшие быстрее. Это единственный способ отличить регрессию от функции, которая всегда была медленной.

**Шаг 4 — зафиксировать baseline для будущих сравнений.** Профиль, снятый в момент деплоя, становится эталоном для следующих релизов. Без регулярного снятия baseline дифференциальный анализ приходится делать постфактум, когда релиз уже переустановлен.

## Диагностика и устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Стеки не символизированы (hex-адреса)** | Нет бинарника нужной сборки, удалены символы или DWARF. | Проверить совпадение build ID в профиле и в локальном бинарнике. Go: не использовать `-ldflags="-s -w"`. C/C++/Rust: собирать с `-g`, раздавать `.debug` отдельно. Java: имена методов символизируются всегда, проблема только у нативных фреймов. |
| **Стеки обрезаны (truncated) или состоящие из одной функции** | Не срабатывает механизм развёртки: нет frame pointer, нет DWARF, недоступен VM unwinder. | Сравнить `--call-graph fp` и `--call-graph dwarf`. Добавить `-fno-omit-frame-pointer` при сборке. Для `async-profiler` переключить `--cstack` (`fp` / `dwarf` / `vm` / `vmx`). Это не лимит профилировщика, а режим развёртки. |
| **Профиль JVM выглядит неправдоподобно** | Safepoint bias: горячий код без точек safepoint выпадает из измерения. | Использовать `async-profiler` или JFR вместо профилировщиков с safepoint-зависимостью. |
| **Слишком высокий оверхед (>10%)** | Слишком высокая частота сэмплирования или дорогое событие (аллокации, блокировки). | Снизить частоту: `pyroscope.ebpf.sample_rate`, `pyroscope.scrape.delta_profiling_duration`, `-i` в `async-profiler`. Отключить профили блокировок на некритичных сервисах. |
| **Профили не доходят до хранилища через Collector** | Не включён feature gate или версия коллектора ниже 0.148.0. | Запустить с `--feature-gates=service.profilesSupport`, обновить коллектор. |
| **Профили не доходят до хранилища (прочее)** | Ошибки аутентификации, сетевые блокировки, неверный URL. | Проверить логи коллектора, доступность эндпоинта из его сети. В Alloy указывать базовый URL без пути `/api/v1/write`. |
| **Пустые Flame Graphs** | Приложение в состоянии ожидания (I/O), а снят только CPU-профиль. | Перейти на wall-clock / off-CPU профилирование. Пустой CPU-профиль при медленном приложении — это результат, а не ошибка. |
| **Высокое потребление RAM при профилировании** | Длинная запись или большое число одновременных сборов. | Сократить окно сэмплирования, уменьшить частоту, настроить retention в хранилище. |
| **Профилирование не запускается** | Нет доступа к `/proc`, `ptrace_scope` ограничивает чтение памяти чужого процесса, нет capability. | Запустить с `sudo`, выдать `SYS_PTRACE` в контейнер, при необходимости выставить `kernel.yama.ptrace_scope=0`. |
| **Профили слишком большие** | Длительное профилирование или высокая частота сэмплирования. | Сократить `duration`, снизить частоту, включить сжатие при хранении. |
| **GC thrashing в профилях** | Приложение в вечном цикле сборки мусора. | Смотреть `alloc`-профиль для поиска источника аллокаций; увеличить лимиты памяти, если рост идёт извне. |
| **Профили смешаны (все сервисы)** | Не задан `service_name` в конфигурации сбора. | Задать `service_name` в `targets` компонента `pyroscope.scrape` или через `k8sattributes`/`resource` процессора. |
| **Профили не коррелируют с метриками** | Расхождение временных диапазонов или timezone. | Синхронизировать часы (NTP), привести хранилища к UTC, проверять границы интервалов вручную. |
| **eBPF-профилирование не работает** | Нет BTF, запрещён непривилегированный BPF, недостаточно прав. | Проверить наличие `/sys/kernel/btf/vmlinux` и `unprivileged_bpf_disabled`. Ориентироваться на наличие BTF, а не на номер версии ядра: `CONFIG_DEBUG_INFO_BTF` появился в 5.4, но включался дистрибутивами неравномерно. |
| **CPU-профиль пуст у процесса с 100% CPU** | Процесс выполняет преимущественно системные вызовы или работает в другом PID namespace. | Снять `perf record` с хоста по PID из `docker inspect`. Проверить, что профилируется именно тот процесс. |
| **Профиль не отражает ожидаемое (систематически)** | Слишком короткое окно: редкие события не попадают в выборку. | Увеличить окно (например, `seconds=60` вместо 30) и повторить замер на репрезентативной нагрузке. |
| **Профили занимают диск и растут** | Не настроена retention в хранилище. | Задать срок хранения и лимиты в настройках Pyroscope, периодически проверять объём. |

## Лучшие практики

### Организация работы

1.  **Always-on Profiling (Continuous Profiling).** Возможность посмотреть профиль «за 5 минут до падения» критически важна для анализа инцидентов — on-demand профилирование даёт картину только после того, как проблема уже воспроизводится. Архитектура и настройка: [Непрерывное профилирование](../continuous_profiling.md).
2.  **Сначала метрики, потом профиль.** Профилирование вслепую дорого. Метрика показывает, *что* деградировало; профиль объясняет *почему*.
3.  **Правильный вопрос — правильный профиль.** CPU — про throughput, wall-clock и off-CPU — про latency. Снимать CPU-профиль у медленного, но незагруженного приложения — самая частая ошибка, приводящая к выводу «профилирование ничего не показало».
4.  **Baseline до деплоя, а не после.** Снимите профиль на каждом хосте в момент релиза. Без эталонного профиля дифференциальный анализ регрессии невозможен.
5.  **Версионирование и тегирование.** Добавляйте `service_name`, `version`, `env` к профилям. Без них исторический анализ и дифференциальное сравнение невозможны — профили всех релизов сливаются в один.
6.  **Символизация — часть релиза.** Символы и бинарники каждого релиза должны быть доступны символизатору *до* того, как из этого релиза придёт первый профиль. Разбираться с этим постфактум дороже, чем настроить хранилище символов один раз.
7.  **Оверхед — измеряйте, а не оценивайте.** Замерьте `pidstat` до и во время профилирования и запишите результат. Оценки «1-2%» из документации относятся к типичным случаям, а не к вашей конфигурации.

### Безопасность и эксплуатация

8.  **Не выставляйте endpoint-ы профилирования в сеть.** Слушайте на localhost, ограничивайте доступ, в контейнерах используйте debug-сессию вместо постоянно открытого порта.
9.  **RBAC на хранилище профилей.** Профили раскрывают внутренние имена функций, пути и структуры данных — это информация для атакующего. Доступ к UI и API ограничивайте отдельно от доступа к метрикам.
10. **Проверка в staging.** Замеряйте реальный оверхед на стенде, сравнивайте с production-нагрузкой, а не с idle-системой.
11. **Автоматизация baseline.** Настройте автоматический сбор профилей при каждом деплое.
12. **Документирование и обучение.** Ведите каталог известных горячих функций и обучите команду читать Flame Graphs — иначе профили будут собраны и никогда не прочитаны.

### Очистка среды

Профилирование оставляет артефакты, которые накапливаются незаметно. Регулярная уборка — часть эксплуатации:

```bash
# Удалить профили старше суток
find /var/tmp -name '*.prof' -mtime +1 -delete
find /var/tmp -name '*.jfr' -mtime +1 -delete

# Проверить, не накопилось ли что-то в рабочем каталоге Node.js
# (--prof и --cpu-prof пишут файлы в cwd процесса)
ls -lh isolate-*-v8.log *.cpuprofile 2>/dev/null

# Проверить объём символов, если раздаёте .debug отдельно
du -sh /var/lib/debug 2>/dev/null

# Отключить отладочные символы, если они были включены временно
sudo sysctl -w kernel.perf_event_paranoid=2
# → вернуть исходное значение в /etc/sysctl.d/, иначе сбросится после перезагрузки

# Вернуть ptrace_scope к исходному значению
sudo sysctl -w kernel.yama.ptrace_scope=1

# Удалить временные capability, если выдавали контейнеру
docker rm -f <container>   # cap_add не наследуется пересозданным контейнерам
```

**Откат изменений.** Большинство настроек профилирования обратимы: параметры `sysctl` возвращаются к значениям по умолчанию, endpoint-ы отключаются удалением импорта `net/http/pprof`, capability-ы исчезают с пересозданием контейнера. Изменения, требующие перезагрузки для отката, — только пользовательские `sysctl` в `/etc/sysctl.d/`, и их следует сопровождать комментарием с исходным значением.

| Паттерн | Описание | Когда использовать |
| :--- | :--- | :--- |

| **Agent-based** | Агент в контейнере/на хосте | Kubernetes, Docker |
| **Hybrid** | Комбинация подходов | Сложные системы |

### Стоимость и производительность

Оверхед зависит не только от способа сбора, но и от типа события. Ниже — порядок величин, из которого следует практическое правило: **сначала включайте CPU, остальное — по необходимости**.

| Метрика | Сэмплирование CPU (100 Гц) | Сэмплирование аллокаций/блокировок | Инструментирование |
| :--- | :--- | :--- | :--- |
| **CPU overhead** | Низкий (единицы процентов) | Заметно выше событие-за-событием | Высокий, часто неприемлемый в production |
| **Memory overhead** | Умеренный (буфер сэмплов) | Умеренный | Значительный |
| **Точность** | Статистическая, окно должно быть репрезентативным | Статистическая | Полная |
| **Применимость** | Все языки | Требует поддержки в рантайме | Языки с runtime |

**Как измерить оверхед на своей системе**, вместо того чтобы полагаться на типовые цифры:

```bash
# Базовое потребление CPU
pidstat -p <PID> 1 10 | tail -1
# → Average: 0.00 0.00 12.50 100.00  12345

# Включить профилирование
py-spy record -o /tmp/p.svg --duration 60 --pid <PID> &
sleep 5
pidstat -p <PID> 1 5 | tail -1
# → Average: 0.00 0.00 13.80 100.00  12345

# Разница по столбцу %CPU и есть оверхед
```

Применяйте те же измерения для `async-profiler -e alloc` и `-e lock` — их оверхед на порядок выше, чем у CPU-профиля, и это основной аргумент за их выборочное применение.

### Инструменты

| Инструмент | Тип | Языки/платформы | Особенности |
| :--- | :--- | :--- | :--- |

| **`async-profiler`** | On-demand | JVM, HotSpot | Нет safepoint bias, `cpu`/`alloc`/`wall`/`lock`, вывод в HTML/JFR |

| **OpenTelemetry** | Стандарт | Универсальный | Сигнал profiles в статусе **Alpha**; требуется Collector ≥ 0.148.0 и feature gate |

### Границы применимости

Профилирование не отвечает на все вопросы, и это стоит проговаривать заранее:

- **Задержка вне процесса.** Если трассировка показывает 200 мс в спане `client`, а off-CPU профиль — 2 мс, задержка накопилась в сети, базе или апстриме. Профилирование процесса тут не поможет.
- **Редкие события.** Короткое окно профиля может просто не поймать событие, повторяющееся раз в час. Увеличивайте окно или используйте событийные инструменты (JFR, счётчики).
- **Среды без поддержки развёртки.** Интерпретаторы и микроконтроллеры часто не дают стеков вовсе. Проверяйте это до того, как потратите время на настройку.
- **Стоимость хранения.** Непрерывное профилирование на уровне организации создаёт значительный объём данных. Retention и семплирование по сервисам — обязательные, а не опциональные настройки.
- **Профилирование БД.** Уровень запросов профилируется отдельно (планы, ожидания, блокировки) — это другая дисциплина со своими инструментами. См. [Ключевые концепции производительности баз данных](../../Databases/Concepts/database_performance_concepts.md).
