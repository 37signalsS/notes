# Профилирование: глубокое погружение

## Определения

**Профилирование (Profiling)** — метод динамического анализа производительности программ, позволяющий получить детальную информацию о потреблении ресурсов (CPU, память, I/O) и поведении приложения во время выполнения.

**Назначение:**

- Поиск «горячих» участков кода (Hotspots), потребляющих больше всего ресурсов.
- Оптимизация алгоритмов и структур данных.
- Обнаружение утечек памяти и неэффективных аллокаций.
- Анализ блокировок и проблем многопоточности.

**Ключевой принцип Observability:** Профилирование отвечает на вопрос «Почему система работает медленно?» (до уровня строки кода), дополняя метрики («Что именно тормозит?») и трассировки («Где именно задержка?»).

**См. также:** [Четыре столпа Observability](./four_pillars_of_observability.md) — фундаментальные концепции наблюдаемости.

## Базовые концепции

### Типы профилирования по режиму работы

| Режим | Описание | Примеры инструментов |
| :--- | :--- | :--- |
| **On-demand** | Запуск вручную для диагностики конкретного инцидента. | `pprof`, `py-spy`, `async-profiler`, [**`perf`**](../../Linux/Diagnostics/Performance/perf.md) |
| **Continuous** | Постоянный сбор профилей в фоне с минимальным оверхедом. | **Grafana Pyroscope**, **Parca** |

### Типы профилей по ресурсам

| Профиль | Что измеряет | Когда использовать |
| :--- | :--- | :--- |
| **CPU Time** | Время, проведенное процессором в функции. | Оптимизация тяжелых вычислений. |
| **Wall-clock Time** | Общее время выполнения (включая ожидание I/O). | Поиск блокировок, задержек сети/диска. |
| **Heap Memory** | Текущие объекты в памяти (снимки кучи). | Поиск утечек памяти (Memory Leaks). |
| **Alloc Memory** | Все выделения памяти (даже если объекты уже удалены). | Снижение нагрузки на Garbage Collector (GC). |
| **Block / Mutex** | Время ожидания синхронизации (блокировки). | Анализ конкурентности и дедлоков. |

### Мониторинг Garbage Collector (GC)
Профилирование Go, Java и других управляемых языков требует особого внимания к GC из-за эффекта **Stop-the-world** (полная остановка приложения при очистке памяти).

**Ключевые метрики для мониторинга:**
1.  **Частота запуска (GC Frequency):** Как часто срабатывает сборщик.
2.  **Продолжительность (GC Duration / Pause Time):** Сколько времени приложение простаивает.

**Диагностика:** Если на графике кривые частоты и продолжительности GC сливаются в одну прямую линию, это означает, что приложение попало в «вечный цикл» сборки мусора и практически не выполняет полезную работу. Это единственный значимый минус активного использования памяти в Go/Java.

### Методы сбора данных

1. **Сэмплирование (Sampling):** Агент периодически (например, 100 раз в секунду) опрашивает стек вызовов.
   - **Плюсы:** Низкий оверхед (<5%), подходит для Production.
   - **Минусы:** Может пропускать очень короткие функции.
2. **Инструментирование (Instrumentation):** Вставка кода в начало и конец каждой функции.
   - **Плюсы:** 100% точность.
   - **Минусы:** Огромный оверхед, искажение результатов («эффект наблюдателя»).
3. **eBPF-профилирование:** Сбор стеков на уровне ядра без изменения кода приложения.
   - **Плюсы:** Поддерживает все языки, нулевой оверхед в рантайме.
   - **Подробнее:** [eBPF — виртуальная машина ядра](../../Linux/Core/kernel/ebpf.md).

### Визуализация: Flame Graphs

**Flame Graph (Граф пламени)** — стандарт визуализации профилей.

- **Ширина блока:** Пропорциональна времени/ресурсам, потраченным функцией.
- **Ось Y:** Глубина стека вызовов (снизу вверх).
- **Интерпретация:** Самые широкие блоки на верхних уровнях — это «горячие» функции, требующие оптимизации.

### OpenTelemetry Profiling

**OTLP Profiles** — новый стандарт (на стадии стабилизации в 2024-2025 гг.) для передачи данных профилирования. Он позволяет объединить профили с метриками и трейсами в рамках единого протокола **OpenTelemetry**, упрощая корреляцию сигналов.

## Практические сценарии

### Сценарий 1: Поиск утечки памяти в Go

**Ситуация:** Постоянный рост RSS (Resident Set Size) процесса.

**Команды:**

```bash
# 1. Снятие текущего снимка кучи
curl -o heap.prof http://localhost:6060/debug/pprof/heap

# 2. Визуализация в браузере
go tool pprof -http=:8080 heap.prof

# 3. Сравнение двух снимков (дифф)
go tool pprof -http=:8080 -base heap_before.prof heap_after.prof
```

### Сценарий 2: Профилирование Python (py-spy)

**Ситуация:** Процесс загружает CPU на 100%, нужно понять, какой скрипт тормозит без перезапуска.

```bash
# Установка py-spy
pip install py-spy

# Просмотр "top" функций в реальном времени
py-spy top --pid <PID>

# Генерация Flame Graph на 30 секунд
py-spy record -o flamegraph.svg --duration 30 --pid <PID>
```

### Сценарий 3: Java Profiling (async-profiler)

**Ситуация:** Высокая задержка GC или блокировки потоков.

```bash
# Запуск профилирования CPU на 60 секунд
./asprof -d 60 -f cpu.html <PID>

# Профилирование аллокаций памяти
./asprof -d 60 -e alloc -f alloc.html <PID>

# Профилирование Wall-clock (ожидание I/O)
./asprof -d 60 -e wall -f wall.html <PID>
```

### Сценарий 4: Корреляция Трейс → Профиль (Grafana)

**Ситуация:** В Grafana Tempo найден медленный спан в сервисе на Java.

1. В интерфейсе Grafana нажать кнопку **«Profiles for this span»**.
2. Grafana автоматически откроет Pyroscope с фильтром по времени и тегам, соответствующим спану.
3. Анализ Flame Graph покажет, на какой строке кода внутри этого спана тратилось время.

## Дополнительная информация

### Сравнение инструментов Continuous Profiling

| Инструмент | База | Особенности |
| :--- | :--- | :--- |
| **Grafana Pyroscope** | Go / eBPF | Глубокая интеграция с Grafana, поддержка многих языков. |
| **Parca** | eBPF / Rust | Фокус на эффективности хранения, нативная поддержка Kubernetes. |
| **Datadog Continuous Profiler** | SaaS | Платное решение, очень простая настройка. |

### Лучшие практики

1. **Continuous Profiling:** Всегда используйте в Production для анализа «посмертных» инцидентов.
2. **Сэмплирование:** Настраивайте частоту сэмплирования (обычно 100Hz) так, чтобы оверхед не превышал 1-2%.
3. **Версионирование:** Добавляйте тег `version` или `git_commit` к профилям для анализа регрессий после деплоя.
4. **Безопасность:** Профили могут содержать чувствительные данные (имена функций, пути к файлам). Ограничивайте доступ к UI профилировщика.
