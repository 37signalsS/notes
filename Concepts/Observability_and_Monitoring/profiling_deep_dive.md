# Профилирование: глубокое погружение

## Определения

**Профилирование (Profiling)** — метод динамического анализа производительности программного обеспечения, позволяющий получить детальную информацию о потреблении ресурсов (CPU, память, I/O, сетевые задержки) и поведении приложения непосредственно во время его выполнения. В отличие от статического анализа, профилирование работает с реальными данными нагрузки, позволяя выявить скрытые узкие места.

**Символизация (Symbolication)** — процесс сопоставления адресов памяти в профиле (hex-коды) с именами функций и номерами строк в исходном коде. Для этого профилировщику требуются таблицы символов или debug-информация (например, DWARF-файлы).

**Стек вызовов (Call Stack)** — упорядоченный список функций, находящихся в процессе выполнения в определенный момент времени. Профилирование "снимает" эти стеки тысячи раз для построения статистической картины.

**Назначение:**

- **Поиск «горячих» участков кода (Hotspots):** Идентификация функций и конкретных строк кода, потребляющих наибольшее количество ресурсов CPU.
- **Оптимизация аллокаций:** Обнаружение неэффективного использования оперативной памяти, частых выделений (allocations) и утечек (memory leaks).
- **Анализ блокировок:** Выявление проблем многопоточности, дедлоков и времени ожидания мьютексов (mutex contention).
- **GPU Profiling:** Анализ производительности ядер CUDA/ROCm для задач машинного обучения и высокопроизводительных вычислений (стандарт 2026 года).

**Ключевой принцип Observability:** Профилирование отвечает на вопрос «Почему система работает медленно?» (до уровня строки кода), дополняя метрики («Что именно тормозит?») и трассировки («Где именно возникла задержка?»).

**См. также:** [Четыре столпа Observability](./four_pillars_of_observability.md) — фундаментальные концепции наблюдаемости.

## Базовые концепции

### Типы профилирования по режиму работы

| Режим | Описание | Примеры инструментов |
| :--- | :--- | :--- |
| **On-demand** | Запуск вручную для диагностики конкретного инцидента или в процессе разработки. | `pprof`, `py-spy`, `async-profiler`, `perf` |
| **Continuous** | **Стандарт 2026.** Постоянный сбор профилей в фоне с минимальным оверхедом. | **[Непрерывное профилирование](../continuous_profiling.md)** |

Для глубокого изучения архитектуры, инструментов (Pyroscope, Parca) и практик постоянного сбора данных в продакшене см. основной документ: **[Непрерывное профилирование (Continuous Profiling)](../continuous_profiling.md)**.

### Типы профилей по ресурсам

| Профиль | Что измеряет | Когда использовать |
| :--- | :--- | :--- |
| **CPU Time** | Время, проведенное процессором непосредственно в функции. | Оптимизация тяжелых вычислений, парсинга, сериализации. |
| **Wall-clock Time** | Общее время выполнения (включая ожидание I/O, сети, блокировок). | Поиск задержек при работе с БД, внешними API или диском. |
| **Heap Memory** | Снимок объектов в куче (in-use). | Поиск утечек памяти (Memory Leaks) и анализ текущего состава памяти. |
| **Allocations** | Все выделения памяти (даже для удаленных объектов). | Снижение нагрузки на Garbage Collector (GC) и уменьшение фрагментации. |
| **Block / Mutex** | Время ожидания синхронизации потоков. | Анализ конкурентности, поиск «бутылочных горлышек» в многопоточном коде. |

**Важное уточнение по памяти:** Профили могут отображаться как в **количестве объектов** (count), так и в **объеме памяти** (space). Оптимизация количества мелких объектов часто дает больший прирост производительности GC, чем оптимизация одного крупного массива.

### Мониторинг Garbage Collector (GC)
Профилирование Go, Java и других управляемых языков требует особого внимания к GC из-за эффекта **Stop-the-world** (полная остановка приложения при очистке памяти).

**Ключевые метрики для мониторинга:**
1.  **Частота запуска (GC Frequency):** Как часто срабатывает сборщик. Частые запуски при малом объеме памяти могут указывать на избыточные аллокации.
2.  **Продолжительность (GC Duration / Pause Time):** Сколько времени приложение простаивает. Высокое значение напрямую влияет на P99 задержку.

**Диагностика:** Если на графике кривые частоты и продолжительности GC сливаются в одну прямую линию, это означает, что приложение попало в «вечный цикл» сборки мусора (GC thrashing) и практически не выполняет полезную работу. Это критический сценарий, требующий немедленного увеличения лимитов памяти или оптимизации аллокаций.

### Методы сбора данных

1.  **Сэмплирование (Sampling):** Агент периодически (например, 100 раз в секунду) опрашивает стек вызовов.
    - **Плюсы:** Низкий оверхед (<2-5%), подходит для Production.
    - **Минусы:** Может пропускать очень короткие функции, выполняющиеся реже частоты сэмплирования.
2.  **Инструментирование (Instrumentation):** Вставка кода в начало и конец каждой функции.
    - **Плюсы:** 100% точность, учет каждого вызова.
    - **Минусы:** Огромный оверхед, значительное искажение результатов («эффект наблюдателя»), не рекомендуется для Production.
3.  **eBPF-профилирование:** Сбор стеков на уровне ядра Linux без изменения кода приложения.
    - **Плюсы:** Поддерживает все языки, нулевой оверхед в рантайме, видимость системных вызовов.
    - **Подробнее:** [eBPF — виртуальная машина ядра](../../Linux/Core/kernel/ebpf.md).

### Визуализация: Flame Graphs

**Flame Graph (Граф пламени)** — стандарт визуализации профилей.

- **Ширина блока:** Пропорциональна времени или ресурсам, потраченным функцией и всеми её дочерними вызовами.
- **Ось Y:** Глубина стека вызовов (снизу вверх).
- **Цвет:** Служит для визуального разделения пакетов/модулей или кодирует дифференциальные изменения.
- **Интерпретация:** Самые широкие блоки на верхних уровнях — это «горячие» функции (Hotspots), требующие оптимизации в первую очередь.
- **Дифференциальные Flame Graphs:** Сравнение двух профилей (например, «baseline» и «canary») для визуализации изменений производительности после изменений в коде.

### OpenTelemetry Profiles (OTLP) и OTLP/Arrow

В 2026 году стандарт **OTLP Profiles** (сигнал профилирования) является основным методом интеграции.
- **Унификация:** Позволяет объединить профили с метриками и трейсами в рамках единого протокола **OpenTelemetry**, упрощая корреляцию сигналов (например, переход от конкретного спана трейса к профилю CPU этого же запроса).
- **OTLP/Arrow:** Использование Apache Arrow для передачи профилей позволяет снизить нагрузку на сеть в 5-10 раз за счет колончатого сжатия данных, что делает Continuous Profiling доступным даже для огромных кластеров.

## Практические сценарии

### Сценарий 1: Поиск утечки памяти в Go

**Ситуация:** Постоянный рост RSS (Resident Set Size) процесса, приводящий к OOMKilled.

**Команды:**
```bash
# 1. Снятие текущего снимка кучи (heap)
curl -o heap.prof http://localhost:6060/debug/pprof/heap

# 2. Визуализация в браузере для анализа аллокаций
go tool pprof -http=:8080 heap.prof

# 3. Сравнение двух снимков (дифф) для поиска растущих объектов
# Снимаем heap_before.prof, ждем 10 минут, снимаем heap_after.prof
go tool pprof -http=:8080 -base heap_before.prof heap_after.prof
```

### Сценарий 2: Профилирование Python через py-spy

**Ситуация:** Процесс загружает CPU на 100%, нужно понять, какая часть кода тормозит без перезапуска приложения.

```bash
# Просмотр "top" функций в реальном времени (без оверхеда)
py-spy top --pid <PID>

# Генерация Flame Graph на 30 секунд
py-spy record -o flamegraph.svg --duration 30 --pid <PID>

# Профилирование с учетом нативных C-расширений
py-spy record --native -o native_flame.svg --pid <PID>
```

### Сценарий 3: Java Profiling (async-profiler)

**Ситуация:** Высокая задержка GC или подозрение на блокировки в многопоточном приложении.

**Команды:**
```bash
# Профилирование CPU на 60 секунд с генерацией HTML-отчета
./asprof -d 60 -f cpu.html <PID>

# Профилирование аллокаций памяти (поиск источника мусора)
./asprof -d 60 -e alloc -f alloc.html <PID>

# Профилирование Wall-clock (ожидание I/O и блокировок)
./asprof -d 60 -e wall -f wall.html <PID>
```

**Валидация:**
1. Открыть `cpu.html` в браузере.
2. Убедиться, что стеки символизированы (видны имена Java-классов).
3. Проверить раздел `Thread View` для выявления потоков, проводящих больше всего времени в состоянии `BLOCKED`.

### Сценарий 4: Настройка сбора профилей в OpenTelemetry Collector

**Ситуация:** Сбор профилей от агентов Alloy и отправка в центральное хранилище Pyroscope.

**Конфигурация Collector:**
```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 5s
    send_batch_size: 1024

exporters:
  pyroscope:
    endpoint: http://pyroscope:4040
    sending_queue:
      enabled: true

service:
  pipelines:
    profiles: # Новый тип пайплайна стандарта 2026
      receivers: [otlp]
      processors: [batch]
      exporters: [pyroscope]
```

**Валидация:**
1. Проверить логи коллектора на отсутствие ошибок `exporting failed`.
2. Зайти в UI Pyroscope и убедиться в наличии новых профилей от соответствующего сервиса.

### Сценарий 5: GPU Profiling (ML workload)

**Ситуация:** Тренировка модели замедлилась, подозрение на неэффективное использование ядер CUDA.

**Команды (NVIDIA Nsight Systems):**
```bash
# Профилирование процесса обучения на 30 секунд
nsys profile -d 30 -o ml_report python train.py

# Анализ загрузки тензорных ядер и пропускной способности памяти
nsys stats ml_report.nsys-rep
```

**Результат:** Визуализация в Nsight UI покажет баланс между CPU и GPU (предотвращение CPU-bound сценариев при подготовке данных).

### Сценарий 6: Профилирование системы на уровне ядра (perf + Linux)

**Ситуация:** Необходимо понять, почему система тормозит на уровне ОС (системные вызовы, контекстные переключения, кэш-промахи).

**Команды:**
```bash
# Профилирование CPU на уровне системы (все процессы)
sudo perf record -g -p <PID> -- sleep 30

# Генерация Flame Graph из системного профиля
sudo perf script | stackcollapse-perf.pl | flamegraph.pl > system_flame.svg

# Анализ кэш-промахов (cache misses)
sudo perf stat -e cache-misses,cache-references -p <PID> -- sleep 10

# Анализ контекстных переключений
sudo perf record -e context-switches -p <PID> -- sleep 10
sudo perf report
```

**Интерпретация:**
- Высокий % `cache-misses` → проблемы с локальностью данных (Data Locality)
- Много `context-switches` → чрезмерная конкуренция за CPU между потоками
- Доминирование `system` time → приложение тратит время на syscall (оптимизировать I/O)

### Сценарий 7: Профилирование в Docker-контейнере

**Ситуация:** Приложение в контейнере потребляет много CPU, нужно найти горячие точки без перезапуска.

**Команды (py-spy извне контейнера):**
```bash
# Найти PID процесса в контейнере
docker inspect --format '{{.State.Pid}}' <container_name>

# Профилирование из хостовой системы
py-spy record --pid <HOST_PID> -o /tmp/container_flame.svg --duration 30

# Или через nsenter для доступа в namespace контейнера
nsenter -t <HOST_PID> -n py-spy top --pid 1
```

**Для Go-приложений в контейнере:**
```bash
# Включить pprof endpoint в контейнере (добавить в Dockerfile)
# EXPOSE 6060

# Снять профиль с хоста
curl -o heap.prof http://localhost:6060/debug/pprof/heap
go tool pprof -http=:8080 heap.prof
```

**Для Java-приложений в контейнере:**
```bash
# Запустить async-profiler в контейнере
docker exec -it <container> /path/to/asprof -d 60 -f /tmp/cpu.html <PID>

# Скопировать результат
docker cp <container>:/tmp/cpu.html ./cpu.html
```

### Сценарий 8: Анализ production-инцидента через профили

**Ситуация:** После деплоя начала расти P99 задержка API. Нужно быстро найти причину.

**Пошаговый алгоритм:**
```bash
# 1. Проверить текущий профиль CPU в реальном времени
# (если включено Continuous Profiling — посмотреть за последние 5 минут)
# Или снять on-demand:
curl -o cpu.prof http://localhost:6060/debug/pprof/profile?seconds=30

# 2. Построить Flame Graph и найти горячие функции
go tool pprof -http=:8080 cpu.prof

# 3. Сравнить сaseline (до деплоя)
go tool pprof -http=:8080 -base cpu_before_deploy.prof cpu_after_deploy.prof

# 4. Если нашли подозрительную функцию — посмотреть её source
go tool pprof -list "problemFunction" cpu.prof

# 5. Проверить аллокации памяти (если подозрение на GC)
curl -o alloc.prof http://localhost:6060/debug/pprof/allocs
go tool pprof -http=:8080 alloc.prof
```

**Чек-лист диагностики:**
- [ ] Снять CPU profile на 30 секунд
- [ ] Снять Heap profile для анализа памяти
- [ ] Снять Block profile для анализа блокировок
- [ ] Сравнить с baseline (до инцидента или до деплоя)
- [ ] Проверить GC metrics (частота и продолжительность)
- [ ] Проверить系統ные метрики (CPU, RAM, Disk I/O)

### Сценарий 9: Профилирование сетевых задержек (Network Profiling)

**Ситуация:** API-вызовы к внешнему сервису стали медленными, но CPU приложения не загружен.

**Команды:**
```bash
# Анализ TCP-соединений и задержек
ss -ti | grep -E "rtt|retrans"

# Профилирование syscall (включая сетевые)
strace -p <PID> -e trace=network -c

# Анализ DNS-задержек
dig +stats example.com

# Мониторинг сетевых соединений в реальном времени
nethogs -p <PID>
```

**Интерпретация:**
- Высокий `rtt` → проблема на стороне удаленного сервера или сети
- Много `retrans` → потеря пакетов, проблема с сетью
- Долгие `connect` → DNS-задержки или проблемы с firewall

### Сценарий 10: Сбор профилей через Grafana Alloy (Continuous Profiling)

**Ситуация:** Настройка непрерывного профилирования в кластере bare-metal серверов.

**Конфигурация Alloy:**
```yaml
// alloy.river
pyroscope.write "profiles" {
  endpoint {
    url = "http://pyroscope:4040/api/v1/write"
  }
}

pyroscope.scrape "default" {
  targets = [
    { "__address__" = "app1:6060", "service_name" = "app1" },
    { "__address__" = "app2:6060", "service_name" = "app2" },
  ]
  forward_to = [pyroscope.write.profiles.receiver]
}
```

**Валидация:**
1. Проверить логи Alloy: `journalctl -u alloy -f`
2. Открыть UI Pyroscope и проверить наличие данных
3. Убедиться, что профили отображаются корректно с правильными service_name

### Сценарий 11: Анализ блокировок в многопоточном приложении (Go)

**Ситуация:** Приложение с высоким параллелизмом не использует CPU на 100%, подозрение на contention.

**Команды:**
```bash
# Снятие профиля блокировок
curl -o block.prof http://localhost:6060/debug/pprof/block

# Анализ
go tool pprof -http=:8080 block.prof

# Сравнение двух снимков блокировок
go tool pprof -http=:8080 -base block_before.prof block_after.prof
```

**Альтернатива — mutex contention profiling:**
```bash
# Включить mutex profiling в Go-приложении
import "runtime"
runtime.SetMutexProfileFraction(1)

# Снять профиль
curl -o mutex.prof http://localhost:6060/debug/pprof/mutex
go tool pprof -http=:8080 mutex.prof
```

**Интерпретация:**
- Широкие блоки в Flame Graph на уровне `sync.Mutex.Lock` → проблемные участки кода
- Мало времени в `running` state, много в `waiting` → потоки ждут блокировок

### Сценарий 12: Профилирование на bare-metal сервере без агентов

**Ситуация:** Минимальная инфраструктура, нужно профилировать приложение без установки дополнительных агентов.

**Команды (только стандартные инструменты):**
```bash
# Использование perf (встроен в Linux kernel)
sudo perf record -g -p <PID> -- sleep 30
sudo perf report

# Или через /proc (для быстрого анализа)
cat /proc/<PID>/status | grep -E "VmRSS|VmSize|Threads"
cat /proc/<PID>/io

# Или через top/htop для базового анализа
top -p <PID> -H  # -H показывает потоки

# Или через strace для анализа syscall
strace -p <PID> -c -e trace=all  # -c для статистики
```

**Преимущества:** Не требует установки дополнительного ПО, работает на любом Linux-сервере.

## Диагностика и устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Стеки не символизированы (hex-адреса)** | Отсутствие отладочных символов (debug symbols) или frame pointers. | В Go использовать `-trimpath=false`, в C++/Rust не удалять символы при сборке (`strip`). Для Java использовать `async-profiler` с `PrintAssembly`. |
| **Слишком высокий оверхед (>10%)** | Слишком высокая частота сэмплирования или использование инструментарования. | Снизить частоту сэмплирования (`-f` в pprof или `interval` в Alloy). Переключиться на eBPF-профилирование. |
| **Профили не доходят до хранилища** | Ошибки аутентификации или сетевые блокировки. | Проверить API-ключи в экспортере. Убедиться, что Collector имеет доступ к эндпоинту хранилища. |
| **Пустые Flame Graphs** | Приложение находится в состоянии ожидания (I/O) при профилировании только CPU. | Использовать Wall-clock профилирование для захвата периодов ожидания. |
| **Высокое потребление RAM при профилировании** | Большой объем данных или длительное профилирование. | Уменьшить длительность профилирования, увеличить частоту сэмплирования, использовать disk-based storage. |
| **Профилирование не запускается** | Нет доступа к /proc или отсутствуют права root. | Проверить права доступа, запустить с sudo, проверить security policies. |
| **Профили слишком большие** | Длительное профилирование или высокая частота сэмплирования. | Уменьшить duration, снизить частоту, использовать компрессию при сохранении. |
| **GC thrashing в профилях** | Приложение в вечном цикле сборки мусора. | Увеличить лимиты памяти, оптимизировать аллокации, проверить heap size. |
| **Профили смешаны (все сервисы)** | Неправильная настройка service_name в профилировщике. | Убедиться, что каждый сервис имеет уникальный service_name в конфигурации. |
| **Стеки обрезаны (truncated)** | Лимит глубины стека в профилировщике. | Увеличить max_stack_depth в конфигурации профилировщика. |
| **Профили не коррелируют с метриками** | Разные временные диапазоны или отсутствие timestamps. | Убедиться, что профили и метрики используют одинаковое время, проверить timezone. |
| **eBPF-профилирование не работает** | Неподдерживаемая версия ядра или отсутствие BTF. | Проверить версию ядра (>=5.10), включить BTF, проверить permissions для eBPF. |

### Диагностические команды

```bash
# pprof: проверка конфигурации

# py-spy: проверка версии
py-spy --version

# async-profiler: проверка установки
./asprof --help

# perf: проверка доступности
perf list

# Проверка debug symbols
readelf --debug-dump=line <binary>  # для C/C++
go tool nm <binary> | head -20      # для Go

# Проверка eBPF
bpftool prog list

# Проверка доступных профилей (Go)
curl -s http://localhost:6060/debug/pprof/ | head -20
```

## Дополнительная информация

### Лучшие практики

1.  **Always-on Profiling (Continuous Profiling):** Всегда используйте в Production. Возможность посмотреть профиль «за 5 минут до падения» критически важна для анализа инцидентов.
2.  **Сэмплирование с умом:** Настраивайте частоту сэмплирования (обычно 100Hz) так, чтобы оверхед не превышал 1-2%. Для критических систем можно снижать до 10Hz.
3.  **Версионирование и тегирование:** Всегда добавляйте теги `version`, `git_commit` и `env` к профилям. Это позволяет проводить дифференциальный анализ между релизами.
4.  **Символизация (Symbolication):** Для скомпилированных языков (C++, Rust, Go) убедитесь, что профилировщик имеет доступ к отладочным символам (debug symbols), иначе Flame Graph будет заполнен адресами памяти вместо имен функций.
5.  **Безопасность:** Профили могут содержать чувствительные данные (имена внутренних функций, пути к файлам). Ограничивайте доступ к UI профилировщика и используйте RBAC.
6.  **Тестирование в staging:** Всегда проверяйте профилирование в staging перед запуском в Production. Убедитесь, что оверхед приемлем.
7.  **Корреляция с деплойами:** Привязывайте профили к конкретным версиям кода. Это позволяет быстро находить регрессии после деплоя.
8.  **Автоматизация:** Настройте автоматический сбор профилей при каждом деплое для создания baseline.
9.  **Документирование:** Ведите каталог горячих функций и известных проблем. Это ускоряет диагностику инцидентов.
10. **Обучение команды:** Убедитесь, что все инженеры могут читать Flame Graphs и анализировать профили.

### Архитектурные паттерны профилирования

| Паттерн | Описание | Когда использовать |
| :--- | :--- | :--- |
| **On-demand** | Запуск по требованию для диагностики | Разработка, инциденты |
| **Continuous (Always-on)** | Постоянный сбор в фоне | Production, мониторинг |
| **eBPF-based** | Профилирование на уровне ядра | Все языки, zero-code |
| **Agent-based** | Агент в контейнере/на хосте | Kubernetes, Docker |
| **Hybrid** | Комбинация подходов | Сложные системы |
