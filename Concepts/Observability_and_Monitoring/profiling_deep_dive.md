# Профилирование: глубокое погружение

---
**Reliability Score: 10** (SSoT + Web 2026)
---

## Определения

**Профилирование (Profiling)** — метод динамического анализа производительности программного обеспечения, позволяющий получить детальную информацию о потреблении ресурсов (CPU, память, I/O, сетевые задержки) и поведении приложения непосредственно во время его выполнения. В отличие от статического анализа, профилирование работает с реальными данными нагрузки, позволяя выявить скрытые узкие места.

**Назначение:**

- **Поиск «горячих» участков кода (Hotspots):** Идентификация функций и конкретных строк кода, потребляющих наибольшее количество ресурсов CPU.
- **Оптимизация аллокаций:** Обнаружение неэффективного использования оперативной памяти, частых выделений (allocations) и утечек (memory leaks).
- **Анализ блокировок:** Выявление проблем многопоточности, дедлоков и времени ожидания мьютексов (mutex contention).
- **GPU Profiling:** Анализ производительности ядер CUDA/ROCm для задач машинного обучения и высокопроизводительных вычислений (стандарт 2026 года).

**Ключевой принцип Observability:** Профилирование отвечает на вопрос «Почему система работает медленно?» (до уровня строки кода), дополняя метрики («Что именно тормозит?») и трассировки («Где именно возникла задержка?»).

**См. также:** [Четыре столпа Observability](./four_pillars_of_observability.md) — фундаментаческие концепции наблюдаемости.

## Базовые концепции

### Типы профилирования по режиму работы

| Режим | Описание | Примеры инструментов |
| :--- | :--- | :--- |
| **On-demand** | Запуск вручную для диагностики конкретного инцидента или в процессе разработки. | `pprof`, `py-spy`, `async-profiler`, `perf` |
| **Continuous** | **Стандарт 2026.** Постоянный сбор профилей в фоне с минимальным оверхедом. | **[Непрерывное профилирование](../continuous_profiling.md)** |

Для глубокого изучения архитектуры, инструментов (Pyroscope, Parca) и практик постоянного сбора данных в продакшене см. основной документ: **[Непрерывное профилирование (Continuous Profiling)](../continuous_profiling.md)**.

### Типы профилей по ресурсам

| Профиль | Что измеряет | Когда использовать |
| :--- | :--- | :--- |
| **CPU Time** | Время, проведенное процессором непосредственно в функции. | Оптимизация тяжелых вычислений, парсинга, сериализации. |
| **Wall-clock Time** | Общее время выполнения (включая ожидание I/O, сети, блокировок). | Поиск задержек при работе с БД, внешними API или диском. |
| **Heap Memory** | Снимок текущих объектов в куче (на момент снятия). | Поиск утечек памяти (Memory Leaks) и анализ состава памяти. |
| **Alloc Memory** | Все выделения памяти за период (даже если объекты уже удалены). | Снижение нагрузки на Garbage Collector (GC) и уменьшение фрагментации. |
| **Block / Mutex** | Время ожидания синхронизации потоков. | Анализ конкурентности, поиск «бутылочных горлышек» в многопоточном коде. |

### Мониторинг Garbage Collector (GC)
Профилирование Go, Java и других управляемых языков требует особого внимания к GC из-за эффекта **Stop-the-world** (полная остановка приложения при очистке памяти).

**Ключевые метрики для мониторинга:**
1.  **Частота запуска (GC Frequency):** Как часто срабатывает сборщик. Частые запуски при малом объеме памяти могут указывать на избыточные аллокации.
2.  **Продолжительность (GC Duration / Pause Time):** Сколько времени приложение простаивает. Высокое значение напрямую влияет на P99 задержку.

**Диагностика:** Если на графике кривые частоты и продолжительности GC сливаются в одну прямую линию, это означает, что приложение попало в «вечный цикл» сборки мусора (GC thrashing) и практически не выполняет полезную работу. Это критический сценарий для Java/Go, требующий немедленного увеличения лимитов памяти или оптимизации аллокаций.

### Методы сбора данных

1.  **Сэмплирование (Sampling):** Агент периодически (например, 100 раз в секунду) опрашивает стек вызовов.
    - **Плюсы:** Низкий оверхед (<2-5%), подходит для Production.
    - **Минусы:** Может пропускать очень короткие функции, выполняющиеся реже частоты сэмплирования.
2.  **Инструментирование (Instrumentation):** Вставка кода в начало и конец каждой функции.
    - **Плюсы:** 100% точность, учет каждого вызова.
    - **Минусы:** Огромный оверхед, значительное искажение результатов («эффект наблюдателя»), не рекомендуется для Production.
3.  **eBPF-профилирование:** Сбор стеков на уровне ядра Linux без изменения кода приложения.
    - **Плюсы:** Поддерживает все языки (включая скомпилированные без frame pointers в 2026 году), нулевой оверхед в рантайме, видимость системных вызовов.
    - **Подробнее:** [eBPF — виртуальная машина ядра](../../Linux/Core/kernel/ebpf.md).

### Визуализация: Flame Graphs

**Flame Graph (Граф пламени)** — стандарт визуализации профилей.

- **Ширина блока:** Пропорциональна времени или ресурсам, потраченным функцией и всеми её дочерними вызовами.
- **Ось Y:** Глубина стека вызовов (снизу вверх).
- **Цвет:** Обычно случаен или кодирует пакеты/модули, не несет метрической нагрузки.
- **Интерпретация:** Самые широкие блоки на верхних уровнях — это «горячие» функции (Hotspots), требующие оптимизации в первую очередь.
- **Дифференциальные Flame Graphs:** Сравнение двух профилей (например, «baseline» и «canary») для визуализации изменений производительности после изменений в коде.

### OpenTelemetry Profiles (OTLP) и OTLP/Arrow

В 2026 году стандарт **OTLP Profiles** (сигнал профилирования) достиг стадии Public Alpha.
- **Унификация:** Позволяет объединить профили с метриками и трейсами в рамках единого протокола **OpenTelemetry**, упрощая корреляцию сигналов.
- **OTLP/Arrow:** Использование Apache Arrow для передачи профилей позволяет снизить нагрузку на сеть в 5-10 раз за счет колончатого сжатия данных, что делает Continuous Profiling доступным даже для огромных кластеров.

## Практические сценарии

### Сценарий 1: Поиск утечки памяти в Go

**Ситуация:** Постоянный рост RSS (Resident Set Size) процесса, приводящий к OOMKilled.

**Команды:**
```bash
# 1. Снятие текущего снимка кучи (heap)
curl -o heap.prof http://localhost:6060/debug/pprof/heap

# 2. Визуализация в браузере для анализа аллокаций
go tool pprof -http=:8080 heap.prof

# 3. Сравнение двух снимков (дифф) для поиска растущих объектов
# Снимаем heap_before.prof, ждем 10 минут, снимаем heap_after.prof
go tool pprof -http=:8080 -base heap_before.prof heap_after.prof
```

### Сценарий 2: Профилирование Python через py-spy

**Ситуация:** Процесс загружает CPU на 100%, нужно понять, какая часть кода тормозит без перезапуска приложения.

```bash
# Просмотр "top" функций в реальном времени (без оверхеда)
py-spy top --pid <PID>

# Генерация Flame Graph на 30 секунд
py-spy record -o flamegraph.svg --duration 30 --pid <PID>

# Профилирование с учетом нативных C-расширений
py-spy record --native -o native_flame.svg --pid <PID>
```

### Сценарий 3: Java Profiling (async-profiler)

**Ситуация:** Высокая задержка GC или подозрение на блокировки в многопоточном приложении.

```bash
# Профилирование CPU на 60 секунд с генерацией HTML-отчета
./asprof -d 60 -f cpu.html <PID>

# Профилирование аллокаций памяти (поиск источника мусора)
./asprof -d 60 -e alloc -f alloc.html <PID>

# Профилирование Wall-clock (ожидание I/O и блокировок)
./asprof -d 60 -e wall -f wall.html <PID>
```

## Дополнительная информация

### Лучшие практики

1.  **Always-on Profiling (Continuous Profiling):** Всегда используйте в Production. Возможность посмотреть профиль «за 5 минут до падения» критически важна для анализа инцидентов.
2.  **Сэмплирование с умом:** Настраивайте частоту сэмплирования (обычно 100Hz) так, чтобы оверхед не превышал 1-2%. Для критических систем можно снижать до 10Hz.
3.  **Версионирование и тегирование:** Всегда добавляйте теги `version`, `git_commit` и `env` к профилям. Это позволяет проводить дифференциальный анализ между релизами.
4.  **Символизация (Symbolication):** Для скомпилированных языков (C++, Rust, Go) убедитесь, что профилировщик имеет доступ к отладочным символам (debug symbols), иначе Flame Graph будет заполнен адресами памяти вместо имен функций.
5.  **Безопасность:** Профили могут содержать чувствительные данные (имена внутренних функций, пути к файлам). Ограничивайте доступ к UI профилировщика и используйте RBAC.
