# Профилирование: детали

## Определения

**Профилирование (Profiling)** — динамический метод анализа производительности программ, позволяющий получить детальную информацию о потреблении ресурсов (CPU, память, I/O) и поведении приложения в производственной среде.

**Ключевое отличие от метрик:** Метрики показывают *что* происходит (например, высокая задержка), профилирование показывает *почему* (какая функция или строка кода вызывает проблему).

**Детализация:** Профилирование обеспечивает детализацию до уровня функции или строки кода, что недоступно другим сигналам Observability.

## Базовые концепции

### Типы профилирования

| Тип | Описание | Когда использовать | Инструменты |
| :--- | :--- | :--- | :--- |
| **On-demand** | Запускается вручную на короткие периоды для исследования конкретной проблемы | Отладка инцидента, оптимизация участка кода | `pprof`, `async-profiler`, `py-spy` |
| **Continuous** | Постоянный сбор данных профилирования в продакшене | Долгосрочный мониторинг, выявление регрессий | Pyroscope, Parca |

> **Подробно:** Непрерывное профилирование описано в **[continuous_profiling.md](../continuous_profiling.md)**.

### Типы профилей по ресурсам

| Тип профиля | Что измеряет | Пример использования |
| :--- | :--- | :--- |
| **CPU** | Время выполнения функций | Поиск «горячих» участков кода, оптимизация алгоритмов |
| **Memory (Heap)** | Выделения памяти, утечки | Обнаружение утечек памяти, оптимизация аллокаций |
| **Memory (Alloc)** | Все выделения памяти (включая собранные GC) | Анализ паттернов аллокаций |
| **Block** | Время ожидания блокировок (мьютексы) | Выявление проблем конкурентного доступа |
| **Goroutine** | Количество активных горутин | Обнаружение утечек горутин |
| **I/O** | Операции ввода-вывода | Оптимизация работы с диском/сетью |

### Методы сбора данных

| Метод | Описание | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **Сэмплирование (Sampling)** | Периодическая запись стека вызовов (например, каждые 10 мс) | Низкие накладные расходы (<5%), подходит для продакшена | Может пропустить редкие события |
| **Инструментирование (Instrumentation)** | Вставка кода для записи каждого вызова функции | Полная точность, все события фиксируются | Высокие накладные расходы (10-50%) |
| **eBPF** | Сбор стеков на уровне ядра без изменения кода | Универсальность, низкий оверхед | См. [**eBPF**](../../Linux/Core/kernel/ebpf.md) |

### Визуализация: Flame Graphs

**Flame Graph (Граф пламени)** — визуализация стеков вызовов для быстрой идентификации «горячих» путей выполнения.

**Структура:**

- **Ось X:** Ширина блока пропорциональна времени/ресурсам, потраченным на функцию и её дочерние вызовы
- **Ось Y:** Глубина стека вызовов (нижний уровень — корневой вызов, верхний — текущая функция)
- **Цвет:** Различает функции или типы ресурсов (CPU, memory, I/O)

**Как читать:**

1. Найти самые широкие блоки на верхнем уровне — это «горячие» функции
2. Проследить путь от корня к «горячей» функции — это критический путь выполнения
3. Сравнить профили за разные периоды времени для выявления регрессий

**Инструменты визуализации:** Pyroscope, Grafana, `flamegraph.pl`, `pprof` web UI.

## Практические сценарии

### Сценарий 1: Поиск утечки памяти в Go-приложении

**Ситуация:** Приложение постепенно потребляет всё больше памяти, через несколько дней происходит OOM Killed.

**Действия:**

| Шаг | Действие | Инструмент |
| :--- | :--- | :--- |
| **1** | Включить сбор heap-профилей в приложении | `runtime/pprof` (Go), `async-profiler` (Java) |
| **2** | Снять два snapshot: сразу после старта и перед OOM | `pprof` endpoint `/debug/pprof/heap` |
| **3** | Сравнить профили, найти растущие аллокации | Pyroscope (diff view), `go tool pprof -base` |
| **4** | Определить функцию-источник утечки | Анализ Flame Graph (широкие блоки в heap profile) |
| **5** | Исправить код (закрыть ресурс, убрать ссылку) | — |
| **6** | Развернуть исправление, подтвердить отсутствие утечки | Continuous profiling (мониторинг тренда памяти) |

**Пример для Go:**

```bash
# Скачать heap profile
curl -o heap_before.prof http://app:8080/debug/pprof/heap

# Через несколько часов
curl -o heap_after.prof http://app:8080/debug/pprof/heap

# Сравнить профили
go tool pprof -base heap_before.prof heap_after.prof
go tool pprof -http=:8000 heap_after.prof
```

### Сценарий 2: Оптимизация CPU-intensive функции

**Ситуация:** Микросервис обработки изображений потребляет 90% CPU, задержка растёт при нагрузке.

**Действия:**

| Шаг | Действие | Инструмент |
| :--- | :--- | :--- |
| **1** | Снять CPU-профиль под нагрузкой | Pyroscope agent, `pprof` |
| **2** | Найти самые широкие блоки на Flame Graph | Визуальный анализ |
| **3** | Идентифицировать функцию: например, `resizeImage()` | — |
| **4** | Проанализировать вложенные вызовы: например, неоптимальный алгоритм | — |
| **5** | Оптимизировать: заменить алгоритм, добавить кэширование | — |
| **6** | Сравнить профили до/после, подтвердить улучшение | Pyroscope (сравнение временных диапазонов) |

**Результат:** Потребление CPU снижено с 90% до 35%, задержка уменьшена в 3 раза.

### Сценарий 3: Расследование инцидента с высокой задержкой

**Ситуация:** Алерт сработал на p99 latency > 2с для API платежей.

**Порядок расследования:**

| Шаг | Действие | Инструмент |
| :--- | :--- | :--- |
| **1** | Проверить метрики: CPU, память, задержки | Grafana + Prometheus |
| **2** | Найти трассировки с высокой задержкой | Tempo/Jaeger (фильтр по `duration > 2s`) |
| **3** | Определить проблемный сервис по трассировке | — |
| **4** | Открыть профиль сервиса за период инцидента | Pyroscope (выбор временного диапазона) |
| **5** | Найти «горячие» функции на CPU/Block profile | Flame Graph анализ |
| **6** | Проверить логи по `trace_id` для контекста | Loki |
| **7** | Выявить причину: например, блокировка мьютекса или медленный SQL | Комбинация данных |

**Результат:** Обнаружено, что 80% времени тратится на ожидание блокировки при доступе к кэшу. Решение: разделить кэш на сегменты (sharding) для снижения конкуренции.

### Сценарий 4: eBPF-профилирование без инструментирования

**Ситуация:** Нужно профилировать монолитное приложение без доступа к коду и возможности перезапуска.

**Решение:** Использовать [**eBPF**](../../Linux/Core/kernel/ebpf.md) для сбора профилей на уровне ядра.

**Преимущества eBPF:**

- Не требует изменения кода или перезапуска приложения
- Работает для любых языков программирования
- Низкие накладные расходы (<3%)
- Показывает системные вызовы и функции ядра

**Инструменты:**

- **Pyroscope eBPF:** Интеграция с Pyroscope для сбора профилей через eBPF
- **Parca:** CNCF-проект для continuous profiling с поддержкой eBPF
- **`perf` (Linux):** Базовый инструмент для сэмплирования стеков

**Пример с Pyroscope eBPF:**

```bash
# Запуск Pyroscope eBPF для процесса с PID 1234
pyroscope ebpf --pid 1234 --output-dir ./profiles

# Просмотр профиля в Pyroscope UI
pyroscope ui ./profiles
```

## Дополнительная информация

### Сравнение инструментов

| Инструмент | Тип | eBPF | Интеграция | Оверхед |
| :--- | :--- | :--- | :--- | :--- |
| **Pyroscope** | Continuous + On-demand | Да | Grafana, Prometheus | <5% |
| **Parca** | Continuous | Да | Kubernetes-native, Grafana | <3% |
| **pprof (Go)** | On-demand | Нет | Встроен в Go runtime | <1% |
| **async-profiler** | On-demand | Нет | Самостоятельный (Java) | <3% |

### Лучшие практики

1. **Continuous profiling в продакшене** — позволяет анализировать проблемы постфактум.
2. **Корреляция с метриками и трассировками** — ускоряет расследование инцидентов.
3. **Сэмплирование для продакшена** — инструментирование слишком затратно.
4. **Хранение профилей минимум 7 дней** — для анализа проблем в выходные.
5. **Сравнение профилей до/после деплоя** — помогает выявлять регрессии.
