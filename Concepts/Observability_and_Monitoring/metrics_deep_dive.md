# Метрики: детали

## Определения

**Метрики (Metrics)** — числовое представление данных о состоянии, работоспособности и поведении системы, собираемых через регулярные промежутки времени в виде **временных рядов** (time series). Они агрегируют информацию, делая её пригодной для статистического анализа, визуализации и автоматического оповещения.

**Назначение и значимость:**
- **Проактивное обнаружение проблем:** Выявление потенциальных сбоев на ранних стадиях через мониторинг отклонений ключевых индикаторов.
- **Оптимизация ресурсов:** Анализ использования ресурсов (например, CPU и памяти в Kubernetes) для повышения эффективности инфраструктуры и сокращения затрат.
- **Настройка производительности:** Регулярный анализ показателей позволяет выполнять точную настройку (Fine-tuning) приложений и системы для обеспечения бесперебойной работы.
- **Комплаенс и аудит:** Поддержание соответствия нормативным требованиям и обеспечение исторической записи для целей аудита.
- **Оценка SLA/SLO:** Контроль соблюдения соглашений об уровне обслуживания на основе числовых данных.

**Ключевой принцип:** Метрики фокусируются на агрегированных показателях («что происходит»), жертвуя детализацией отдельных событий ради масштабируемости и скорости обработки.

**См. также:** [Четыре столпа Observability](./four_pillars_of_observability.md) — фундаментальные концепции наблюдаемости.

## Базовые концепции

### Типы метрик

В современной экосистеме мониторинга (Prometheus, OpenTelemetry) выделяют несколько фундаментальных типов данных:

| Тип | Описание | Особенности |
| :--- | :--- | :--- |
| **Counter** | Монотонно растущий счётчик | Сбрасывается только при перезапуске процесса. Используется с функцией `rate()`. |
| **Gauge** | Текущее значение («термометр») | Может расти и уменьшаться. Используется для моментальных снимков состояния. |
| **Histogram** | Распределение значений по бакетам | Позволяет вычислять перцентили на стороне сервера. Требует выбора границ бакетов. |
| **Summary** | Квантили, вычисленные на клиенте | Точнее гистограмм для одиночных инстансов, но **не подлежит агрегации** между серверами. |
| **Native Histograms** | Гистограммы с плавающей сеткой | Новое в Prometheus (v2.40+). Не требуют ручной настройки бакетов, экономят место. |

### Характеристики метрик

| Характеристика | Описание | Следствие |
| :--- | :--- | :--- |
| **Масштабируемость** | Фиксированный объём данных на ряд | Идеально для высоконагруженных систем. |
| **Низкая задержка** | Данные готовы к запросу сразу | Моментальная реакция алертов. |
| **Агрегация** | Возможность объединения данных | Позволяет видеть общую картину по кластеру. |
| **Отсутствие деталей** | Не содержат контекст запроса | Требуют корреляции с **[логами](./logs_deep_dive.md)** и **[трассировками](./traces_deep_dive.md)**. |

### Проблема кардинальности (Cardinality)

**Кардинальность** — это количество уникальных временных рядов, создаваемых комбинациями лейблов (labels).

**Взрыв кардинальности (Cardinality Explosion):**
Каждая уникальная пара `ключ=значение` в лейблах порождает новый временной ряд. 
- **Низкая кардинальность (хорошо):** `region`, `env`, `status_code`, `method`.
- **Высокая кардинальность (плохо):** `user_id`, `email`, `request_id`, `ip_address`.

**Рекомендация:** Никогда не используйте уникальные идентификаторы пользователей или запросов в лейблах метрик. Это приведет к лавинообразному росту потребления памяти TSDB (Prometheus, VictoriaMetrics) и отказу системы.

### OpenTelemetry Metrics

Современный стандарт **OpenTelemetry (OTel)** унифицирует сбор метрик, позволяя приложению отправлять данные один раз в Collector, который затем распределяет их в Prometheus, Datadog или другие системы. OTel вводит понятие **Temporality** (Cumulative vs Delta), что важно при выборе бэкенда хранения.

## Практические сценарии

### Сценарий 1: Инструментирование приложения (Python)

Пример использования `prometheus_client` для мониторинга HTTP-сервиса.

```python
from prometheus_client import Counter, Histogram, start_http_server
import time

# Имена метрик должны иметь суффиксы единиц измерения или _total
REQUESTS_TOTAL = Counter(
    'http_requests_total', 
    'Total count of HTTP requests', 
    ['method', 'endpoint', 'status']
)

LATENCY_SECONDS = Histogram(
    'http_request_duration_seconds', 
    'HTTP request latency in seconds',
    buckets=[0.1, 0.5, 1.0, 2.0, 5.0]
)

def process_request(method, endpoint):
    start_time = time.time()
    # ... логика обработки ...
    status = "200"
    
    LATENCY_SECONDS.observe(time.time() - start_time)
    REQUESTS_TOTAL.labels(method=method, endpoint=endpoint, status=status).inc()

if __name__ == '__main__':
    start_http_server(8000)
    while True:
        process_request('GET', '/api/v1/order')
        time.sleep(1)
```

### Сценарий 2: Развёртывание Node Exporter

Использование Docker Compose для сбора системных метрик хоста.

```yaml
services:
  node-exporter:
    image: prom/node-exporter:v1.8.2
    container_name: node-exporter
    restart: unless-stopped
    volumes:
      - /proc:/host/proc:ro
      - /sys:/host/sys:ro
      - /:/rootfs:ro
    command:
      - '--path.procfs=/host/proc'
      - '--path.sysfs=/host/sys'
      - '--collector.filesystem.mount-points-exclude=^/(sys|proc|dev|host|etc)($$|/)'
    ports:
      - "9100:9100"
    deploy:
      resources:
        limits:
          memory: 128M
```

## Дополнительная информация

### Выбор методологии

Для эффективного мониторинга рекомендуется следовать одной из установленных методологий:
- **RED:** Requests (RPS), Errors (ошибки), Duration (задержка). Для сервисов.
- **USE:** Utilization (использование), Saturation (насыщение), Errors (ошибки). Для ресурсов.
- **Golden Signals:** Latency, Traffic, Errors, Saturation.

### Лучшие практики

1.  **Именование:** Всегда используйте базовые единицы измерения (seconds, bytes, meters).
2.  **Агрегация:** Выполняйте агрегацию на стороне сервера (PromQL), а не предопределяйте все возможные суммы в коде.
3.  **Защита:** Устанавливайте лимиты на количество рядов (target_limit) в конфигурации Prometheus для защиты от взрыва кардинальности.
4.  **Exemplars:** Используйте Exemplars для прямой связи метрик с конкретными трассировками.
