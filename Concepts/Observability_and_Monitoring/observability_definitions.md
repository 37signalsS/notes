# Определения Observability

## Определения

**Мониторинг (Monitoring)** — процесс сбора, агрегации и анализа числовых показателей (метрик) для отслеживания состояния, производительности и надежности системы. Ориентирован на проверку соответствия системы заданным параметрам («известные неизвестные»). Помогает ответить на вопросы: «Система работает?» и «Насколько эффективно?»

**Значение мониторинга:**
- **Стабильность системы:** Обеспечение бесперебойной работы инфраструктуры и приложений через контроль ключевых параметров.
- **Проактивное обнаружение:** Выявление и устранение потенциальных проблем до того, как они затронут конечных пользователей.
- **Оптимизация ресурсов:** Динамическое распределение мощностей для повышения эффективности и снижения затрат.

**Наблюдаемость (Observability, O11y)** — мера того, насколько хорошо можно понять внутреннее состояние системы, основываясь исключительно на её внешних данных (телеметрии). Это целостный подход, объединяющий логи, метрики и трассировки для обеспечения полного представления о поведении и производительности распределенных систем (особенно в Kubernetes). 

В то время как мониторинг и наблюдаемость часто используются как синонимы, они представляют разные концепции управления системами.

**Цели наблюдаемости:**
- **Понимание поведения системы:** Анализ того, как система действует в различных условиях и как взаимодействуют её компоненты.
- **Упреждающее обнаружение проблем:** Раннее обнаружение потенциальных сбоев до того, как они перерастут в критические инциденты.
- **Оптимизация производительности:** Использование детального обзора для эффективной настройки и повышения общей эффективности.

**Телеметрия (Telemetry)** — совокупность сырых данных (сигналов), генерируемых компонентами системы для внешнего наблюдения.

**Сигналы (Signals)** — стандартизированные типы телеметрических данных. Основные сигналы: метрики, логи, трассировки и профили.

**Кардинальность (Cardinality)** — в контексте мониторинга это количество уникальных временных рядов, создаваемых комбинациями лейблов (меток). Высокая кардинальность (например, `user_id` в метриках) — главная техническая проблема систем мониторинга, требующая перехода к инструментам наблюдаемости.

## Базовые концепции

### Различия между мониторингом и наблюдаемостью

| Критерий | Мониторинг | Наблюдаемость |
| :--- | :--- | :--- |
| **Цель** | Оповещение о сбоях (Alerting) | Исследование причин (Exploration) |
| **Тип проблем** | Предсказуемые (Known Unknowns) | Непредсказуемые (Unknown Unknowns) |
| **Подход** | Пассивный (ждем алерта) | Активный (задаем вопросы данным) |
| **Ключевой вопрос** | Что именно сломалось? | Почему это произошло? |
| **Масштаб данных** | Агрегированные метрики | Детальные события, трейсы, профили |

### Четыре столпа наблюдаемости

Для обеспечения полной наблюдаемости системы необходимо собирать и коррелировать четыре типа данных:

1.  **Метрики (Metrics):** числовые показатели (RPS, Error Rate, Latency). Экономичны, идеальны для алертинга.
2.  **Логи (Logs):** записи о событиях в текстовом или структурированном (JSON) формате. Содержат контекст ошибки.
3.  **Трассировки (Traces):** путь запроса через распределенную систему. Выявляют задержки в микросервисах.
4.  **Профили (Profiles):** детализация потребления ресурсов (CPU, Memory) до уровня строки кода.

Подробный разбор каждого сигнала приведен в файле **[Четыре столпа Observability](./four_pillars_of_observability.md)**.

### Уровни наблюдаемости (Stack Visibility)

| Уровень | Объект наблюдения | Типовые инструменты |
| :--- | :--- | :--- |
| **Инфраструктура** | Железо, виртуализация, сеть | Node Exporter, SNMP, Netflow |
| **Оркестрация** | Контейнеры, Kubernetes | Kube-state-metrics, cAdvisor |
| **Middleware** | Базы данных, очереди, кэш | Postgres Exporter, JMX, Redis Exporter |
| **Приложение (APM)** | Код, внешние вызовы | OpenTelemetry SDK, Jaeger, Pyroscope |
| **Бизнес-логика** | Транзакции, конверсия, выручка | Custom Metrics, SQL-агрегаты |

### Методы оценки со стороны пользователя

-   **Синтетический мониторинг (Synthetics):** регулярная имитация действий пользователя (проверка эндпоинтов, сценарии в браузере). Позволяет выявлять проблемы до того, как их заметят реальные пользователи.
-   **RUM (Real User Monitoring):** сбор телеметрии непосредственно из браузера или мобильного приложения пользователя. Показывает реальную производительность фронтенда и задержки сети «последней мили».

## Практические сценарии

### Сценарий 1: Исследование «фантомной» деградации

**Ситуация:** Метрики показывают рост 95-го перцентиля задержки (p95 latency) на API заказов, но средние значения и загрузка CPU в норме. Стандартных алертов нет.

**Действия:**

1.  **Анализ распределения:** Использование гистограмм в Prometheus для определения, является ли задержка глобальной или касается конкретных эндпоинтов.
2.  **Выборка трейсов:** Переход к Grafana Tempo для просмотра трейсов с длительностью > p95.
3.  **Корреляция с логами:** Поиск логов по `trace_id` из медленного трейса. Обнаружение записи: `Slow query (1.2s) detected in database module`.
4.  **Профилирование:** Если причина не в БД, запуск Pyroscope для анализа «горячих» функций CPU в момент всплеска задержки.

**Результат:** Выявлено, что один из внешних API партнеров начал отвечать медленно в 5% случаев, блокируя потоки в приложении.

### Сценарий 2: Переход на OpenTelemetry (OTEL)

**Задача:** Унифицировать сбор телеметрии и избежать привязки к конкретному вендору (Vendor Lock-in).

**Этапы:**

1.  **Инструментирование:** Добавление OpenTelemetry SDK в приложения (Java Agent, Python Auto-instrumentation и т.д.).
2.  **Сбор данных:** Развертывание **OTEL Collector** как Sidecar (в K8s) или отдельного сервиса.
3.  **Маршрутизация:** Настройка Collector для отправки метрик в VictoriaMetrics, трейсов в Tempo и логов в Loki.
4.  **Стандартизация:** Использование **Semantic Conventions** для именования атрибутов, что обеспечивает автоматическую корреляцию между разными инструментами в Grafana.

### Сценарий 3: Observability-Driven Development (ODD)

**Концепция:** проектирование наблюдаемости на этапе разработки, а не после деплоя. Для каждой бизнес-фичи команда заранее определяет, как её состояние будет измеряться, какие алерты сработают при деградации, и какие дашборды позволят расследовать инциденты.

**Пример:** новая фича регистрации пользователей. Вместо стандартных HTTP-метрик (200 OK, 5xx) добавляются бизнес-метрики:

- `business_registration_attempts_total` — количество попыток регистрации (counter)
- `business_registration_completed_total` — успешные регистрации (counter)
- `business_registration_duration_seconds` — время прохождения регистрации (histogram)

Если какой-то шаг регистрации сломан частично (для 1% пользователей), стандартные метрики «200 OK» этого не покажут — сервис отвечает успешно, но бизнес-логика не завершается. Бизнес-метрика `registration_completed_total` обнаружит падение конверсии.

**Рекомендации:**
- Именование: использовать префикс `business_` (или `biz_`) для отделения бизнес-метрик от инфраструктурных. Это позволяет выгружать бизнес-метрики в долгосрочное хранилище, а инфраструктурные — нет.
- Кардинальность: даже для бизнес-метрик нельзя использовать высококардинальные лейблы (user ID, email). Вместо этого — группы пользователей (plan: gold/premium/free).
- Алерты: строить на основе SLO и error budget, а не на статических порогах (см. [SRE концепции](../sre_concepts_main.md)).
- Процесс: ODD внедряется как этап планирования фичи — «как мы это будем мониторить?». Без этого метрики появляются постфактум, когда инцидент уже произошёл.

## Инструментарий

| Категория | Инструменты (Open Source / Self-hosted) | SaaS / Платные решения |
| :--- | :--- | :--- |
| **Метрики** | **Prometheus**, **VictoriaMetrics**, Mimir | Datadog, New Relic |
| **Логи** | **Grafana Loki**, OpenSearch (ELK Stack) | **Splunk**: корпоративная платформа с продвинутым поиском, индексированием и ML для обнаружения аномалий. |
| **Трассировки** | **Grafana Tempo**, Jaeger | **New Relic**: Full-stack observability с использованием SDK/API для бизнес-метрик и ИИ-аналитики на основе исторических данных. |
| **Профилирование** | **Grafana Pyroscope**, Parca | Datadog Profiler |
| **Коллекторы** | **OpenTelemetry Collector**, Grafana Alloy | Vector, Fluent Bit |
| **Визуализация** | **Grafana** | Kibana, Managed Dashboards |
