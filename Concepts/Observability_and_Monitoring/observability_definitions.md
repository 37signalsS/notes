# Observability Definitions

## Определения

**Мониторинг (Monitoring)** — постоянный сбор и анализ параметров системы для обеспечения стабильности и своевременного обнаружения проблем. Ориентирован на **известные проблемы** («known unknowns»). Цель — знать, *что* сломалось.

**Observability (Наблюдаемость, O11y)** — свойство системы, позволяющее задавать вопросы о её поведении, которые не были предусмотрены при проектировании мониторинга. Исследует **неизвестные проблемы** («unknown unknowns»). Цель — понять, *почему* что-то сломалось.

**Телеметрия (Telemetry)** — данные, собираемые о работе системы: логи, метрики, трассировки, профили.

**Сигналы (Signals)** — стандартизированные типы телеметрических данных в наблюдаемости. Четыре основных сигнала: логи, метрики, трассировки, профилирование.

**Корреляция данных (Data Correlation)** — связывание различных сигналов через общие идентификаторы (`trace_id`, `service_name`, `instance_id`) для получения полной картины инцидента.

## Базовые концепции

### Мониторинг vs Observability: ключевые различия

| Критерий | Мониторинг | Observability |
| :--- | :--- | :--- |
| **Фокус** | Известные сценарии отказа | Исследование неизвестных проблем |
| **Вопрос** | «Что сломалось?» | «Почему сломалось?» |
| **Подход** | Реактивный (алерты) | Исследовательский (запросы) |
| **Данные** | Предопределённые метрики | Любые телеметрические данные |
| **Инструменты** | Prometheus, Zabbix, Nagios | Loki, Jaeger, Tempo, Pyroscope |

### Принципы построения наблюдаемости

1. **Единый контекст:** все сигналы связываются через общие идентификаторы (`trace_id`, `request_id`, `user_id`).

2. **Двусторонний переход:** возможность перехода от метрики → к логам/трассировкам и обратно.

3. **Автоматическая корреляция:** дашборды показывают связанные данные из разных источников без ручного поиска.

4. **Минимальное влияние на приложение:** инструментирование не должно снижать производительность более чем на 5-10%.

5. **Стандартизация:** использование открытых стандартов (OpenTelemetry, W3C Trace Context) для совместимости инструментов.

### Уровни наблюдаемости

| Уровень | Объект наблюдения | Примеры метрик |
| :--- | :--- | :--- |
| **Инфраструктура** | Серверы, сеть, хранилища | CPU, память, диск, сеть |
| **Платформа** | Контейнеры, оркестрация | Pod status, restart count, node capacity |
| **Приложение** | Сервисы, функции | RPS, error rate, latency |
| **Бизнес** | Пользовательские сценарии | Конверсия, успешные заказы, выручка |

## Практические сценарии

### Сценарий 1: Диагностика неизвестной проблемы

**Ситуация:** Пользователи жалуются на замедление загрузки страниц. Стандартные дашборды показывают норму по CPU и памяти, ошибок нет.

**Действия с использованием Observability:**

| Шаг | Действие | Инструмент |
| :--- | :--- | :--- |
| **1** | Проверка перцентилей задержки (p95, p99) | Grafana + Prometheus |
| **2** | Анализ трассировок для выявления узких мест | Tempo / Jaeger |
| **3** | Поиск логов по `trace_id` проблемного запроса | Loki / Elasticsearch |
| **4** | Профилирование сервиса для поиска «горячих точек» | Pyroscope |
| **5** | Выявление корневой причины (медленный SQL, внешний API) | Комбинация данных |

**Результат:** Обнаружено, что один из микросервисов делает N+1 запрос к базе данных. Проблема не была видна на метриках уровня инфраструктуры.

### Сценарий 2: Внедрение наблюдаемости с нуля

**Этапы внедрения:**

1. **Инструментирование приложения:**
   - Добавление OpenTelemetry SDK в код
   - Настройка автоматического сбора трейсов и метрик
   - Генерация `trace_id` для каждого запроса

2. **Настройка сбора телеметрии:**
   - Развёртывание OTel Collector
   - Настройка экспорта в бэкенды (Prometheus, Loki, Tempo)
   - Конфигурация сэмплирования для снижения нагрузки

3. **Создание дашбордов:**
   - Базовые дашборды по RED/Golden Signals
   - Дашборды для каждого сервиса с трассировками
   - Бизнес-метрики на отдельном дашборде

4. **Настройка алертинга:**
   - Алерты на критические метрики (error rate, latency)
   - Мультиоконные алерты для Burn Rate
   - Маршрутизация уведомлений по командам

### Сценарий 3: Корреляция данных при инциденте

**Пример:** Алерт сработал на высокую задержку (p99 > 2с).

**Корреляция через `trace_id`:**

```
Метрика (Prometheus) → trace_id=abc123
    ↓
Трассировка (Tempo) → span: payment-service (1.8с)
    ↓
Логи (Loki) → trace_id=abc123 → "Slow query: 1.5с"
    ↓
Профиль (Pyroscope) → payment-service.getPayment() → 80% CPU в SQL-запросе
```

**Вывод:** Проблема в отсутствии индекса в таблице платежей.
