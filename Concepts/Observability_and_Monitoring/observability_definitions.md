# Определения Observability

## Определения

**Мониторинг (Monitoring)** — процесс непрерывного сбора, агрегации и анализа числовых показателей (метрик) для отслеживания состояния, производительности и надежности системы. Мониторинг ориентирован на проверку соответствия системы заданным параметрам («известные неизвестные») и генерацию оповещений (Alerting) при выходе за их пределы.

**Наблюдаемость (Observability, O11y)** — мера того, насколько глубоко и точно можно понять внутреннее состояние системы, основываясь исключительно на её внешних данных (телеметрии). В 2026 году концепция перешла в стадию **Observability 2.0**, где фокус сместился с разрозненных типов данных (силосов) к «широким событиям» (Wide Events) с общим контекстом. Это позволяет проводить свободный исследовательский анализ (Exploration) и находить причины проблем, которые не были предусмотрены заранее («неизвестные неизвестные»).

**Телеметрия (Telemetry)** — совокупность сырых данных (сигналов), генерируемых компонентами системы для внешнего наблюдения. Телеметрия является фундаментом наблюдаемости и в современных архитектурах рассматривается как стратегический актив, требующий управления стоимостью (FinOps) и контроля экологического следа (Green Monitoring).

**Сигналы (Signals)** — стандартизированные типы телеметрических данных. В 2026 году к классическим «трем столпам» (метрики, логи, трассировки) официально присоединен четвертый — профили.

**Кардинальность (Cardinality)** — количество уникальных временных рядов или объектов данных, создаваемых комбинациями лейблов (меток). Высокая кардинальность (например, миллионы уникальных `user_id` или `order_id`) — главная техническая проблема классических TSDB (Prometheus), решаемая в рамках Observability 2.0 через использование колоночных хранилищ и объектных хранилищ (Data Lakes).

## Базовые концепции

### Различия между мониторингом и наблюдаемостью

| Критерий | Мониторинг | Наблюдаемость 2.0 |
| :--- | :--- | :--- |
| **Цель** | Оповещение о сбоях (Alerting) | Исследование причин (Exploration) |
| **Тип проблем** | Предсказуемые (Known Unknowns) | Непредсказуемые (Unknown Unknowns) |
| **Подход** | Пассивный (ждем алерта) | Активный (задаем вопросы данным) |
| **Ключевой вопрос** | Что именно сломалось? | Почему это произошло? |
| **Масштаб данных** | Агрегированные метрики | Детальные Wide Events, трейсы, профили |
| **Архитектура** | TSDB (локальные диски) | Stateless (S3 / Data Lake / ClickHouse) |

### Четыре сигнала наблюдаемости (OpenTelemetry Standard)

Для обеспечения полной видимости системы необходимо собирать и коррелировать четыре типа сигналов:

1.  **Метрики (Metrics):** числовые показатели (RPS, Error Rate, Latency). Экономичны, идеальны для мгновенного алертинга на базе SLO.
2.  **Логи (Logs):** записи о событиях. В 2026 году стандартом является структурированный JSON с обязательной привязкой к `trace_id`.
3.  **Трассировки (Traces):** путь запроса через распределенную систему. Позволяют визуализировать каскадные задержки и зависимости микросервисов.
4.  **Профили (Profiles):** (Public Alpha 2026) непрерывный анализ потребления ресурсов (CPU, Memory) до уровня строки кода через eBPF с минимальным оверхедом (<1%).

### Уровни наблюдаемости (Stack Visibility)

| Уровень | Объект наблюдения | Технические особенности |
| :--- | :--- | :--- |
| **Инфраструктура** | Железо, VM, Сеть | USE-метод, энергопотребление (Kepler), Netflow. |
| **Оркестрация** | Kubernetes | Kube-state-metrics, cAdvisor, события планировщика. |
| **Middleware** | БД, очереди, кэш | Специфические движки (Postgres, Kafka, Redis), JMX. |
| **Приложение (APM)** | Код, внешние вызовы | OpenTelemetry SDK, профилирование, Span Links. |
| **Бизнес-логика** | Транзакции, конверсия | Custom Metrics, бизнес-события, юнит-экономика. |

### Методы оценки со стороны пользователя

-   **Синтетический мониторинг (Synthetics):** регулярная имитация действий пользователя (проверка эндпоинтов, сложные сценарии в безголовых браузерах). Позволяет выявлять проблемы (например, просроченные SSL-сертификаты или ошибки маршрутизации) до того, как их заметят реальные пользователи.
-   **RUM (Real User Monitoring):** сбор телеметрии непосредственно из браузера или мобильного приложения (например, через Grafana Faro). Показывает реальную производительность фронтенда (Core Web Vitals) и задержки «последней мили» у клиента.

## Практические сценарии

### Сценарий 1: Исследование «фантомной» деградации (Observability 2.0)

**Ситуация:** Метрики показывают рост задержки p95 на API заказов, но средние значения и загрузка ресурсов в норме. Стандартные алерты молчат.

**Алгоритм расследования:**
1.  **Exploratory Query:** выполнение запроса к хранилищу Wide Events с группировкой по *всем* доступным измерениям (`region`, `version`, `customer_tier`, `node_id`).
2.  **Correlation Analysis:** автоматическое выявление измерения, которое наиболее сильно коррелирует с задержкой (выявлено: `customer_tier=gold` + `region=eu-central-1`).
3.  **Trace Analysis:** переход в Grafana Tempo для просмотра трейсов этой группы. Обнаружен медленный вызов внешнего API логистического партнера.
4.  **Profile Check:** переход от спана к Flame Graph через Pyroscope подтверждает, что время тратится на ожидание (Wall-clock time) в сетевом сокете.

### Сценарий 2: Agentic AI Remediation & RCA (Автономное исправление)

**Задача:** Снизить MTTR (Mean Time to Repair) за счет исключения человеческого фактора на первом этапе.

**Процесс 2026 года:**
1.  **Anomaly Detection:** AI-агент обнаруживает аномальное «сжигание» SLO или получает триггер от мониторинга.
2.  **Reasoning Trace (React Loop):** агент самостоятельно запрашивает через MCP логи, конфигурации Kubernetes и документацию из RAG. Он «обдумывает» корреляцию между всплеском ошибок и последними изменениями.
3.  **RCA Report:** агент формирует отчет о корневой причине (Root Cause Analysis) и Remediation Plan (план исправления).
4.  **Automated/Guided Action:** агент инициирует автоматический откат (Rollback) или предлагает инженеру конкретную команду для исправления.
5.  **Human Feedback:** инженер подтверждает успешность и дает фидбек, который сохраняется в **долгосрочной памяти (LTM)** агента.

Подробнее об устройстве систем см. в **[ИИ-агенты](../../AI/agents.md)**.

### Сценарий 3: Observability-Driven Development (ODD)

**Концепция:** Проектирование наблюдаемости на этапе планирования фичи.
-   **Бизнес-метрики:** проектирование счетчиков (`biz_registration_success_total`) до написания кода.
-   **FinOps Tags:** добавление тега `project_id` и `cost_center` ко всей телеметрии для автоматического расчета ROI функции.
-   **Green Metrics:** отслеживание `mtCO2e` (углеродного следа) кода в CI/CD пайплайне для соответствия ESG-стандартам компании.
