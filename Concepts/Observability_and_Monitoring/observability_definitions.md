# Определения Observability

## Определения

**Мониторинг (Monitoring)** — постоянный сбор и анализ параметров системы для обеспечения стабильности и своевременного обнаружения проблем. Ориентирован на **известные проблемы** («known unknowns»). Цель — знать, *что* сломалось.

**Наблюдаемость (Observability, O11y)** — свойство системы, позволяющее задавать вопросы о её поведении, которые не были предусмотрены при проектировании мониторинга. Исследует **неизвестные проблемы** («unknown unknowns»). Цель — понять, *почему* что-то сломалось.

**Телеметрия (Telemetry)** — данные, собираемые о работе системы: логи, метрики, трассировки, профили.

**Сигналы (Signals)** — стандартизированные типы телеметрических данных в наблюдаемости. Четыре основных сигнала: логи, метрики, трассировки, профилирование.

**Корреляция данных (Data Correlation)** — связывание различных сигналов через общие идентификаторы (`trace_id`, `service_name`, `instance_id`) для получения полной картины инцидента.

## Базовые концепции

### Различия между мониторингом и наблюдаемостью

| Критерий | Мониторинг | Наблюдаемость |
| :--- | :--- | :--- |
| **Фокус** | Известные сценарии отказа | Исследование неизвестных проблем |
| **Вопрос** | «Что сломалось?» | «Почему сломалось?» |
| **Подход** | Реактивный (алерты) | Исследовательский (запросы) |
| **Данные** | Предопределённые метрики | Любые телеметрические данные |
| **Инструменты** | Prometheus, Zabbix, Nagios | Loki, Jaeger, Tempo, Pyroscope |

### Столпы наблюдаемости (Pillars)

1.  **Метрики (Metrics):** Числовые временные ряды. Отвечают на вопрос «Что происходит?» (нагрузка выросла, ошибки пошли). Компактные и дешевые.
2.  **Логи (Logs):** Записи о событиях. Отвечают на вопрос «Что именно случилось?» (детали ошибки в конкретный момент).
3.  **Трассировки (Traces):** Путь запроса через цепочку микросервисов. Отвечают на вопрос «Где именно затык?» (в каком сервисе задержка).
4.  **Непрерывное профилирование (Continuous Profiling):** Снятие стека вызовов без остановки сервиса (через **eBPF**). Отвечает на вопрос «Какая строчка кода тормозит?».

### Уровни наблюдаемости

| Уровень | Объект наблюдения | Детали |
| :--- | :--- | :--- |
| **Железо** | CPU, RAM, Диски, Сеть | Температуры, питание, ошибки портов (SNMP) |
| **ОС / Хост** | Ядро, процессы | Load Average, файловые дескрипторы, Swap |
| **Сеть** | Трафик, задержки | Потери пакетов, состояние портов |
| **Приложение (APM)** | Код сервиса | RPS, Error Rate, Latency, Трассировка |
| **Базы данных** | SQL, хранилище | Медленные запросы, пул соединений, лаг репликации |
| **Оркестрация** | Контейнеры, K8s | Статус подов, лимиты ресурсов, перезапуски |
| **Бизнес** | Деньги, пользователи | Регистрации, заказы, конверсия, выручка в минуту |

> **Важно:** Технически здоровая система (все графики "зеленые") может быть фактически сломана. Например, если за час совершено 0 заказов при живых серверах — возможно, сломалась форма оплаты или интеграция, которую не покрывают системные метрики. Бизнес-мониторинг ловит такие инциденты первыми.

### Методы оценки со стороны пользователя

-   **Синтетический мониторинг (Synthetic):** Роботы имитируют действия пользователя из разных точек мира. Помогает поймать проблему до того, как её заметят люди.
-   **RUM (Real User Monitoring):** Сбор телеметрии прямо из браузеров реальных пользователей. Показывает, что реально видят люди.

## Инструментарий

| Категория | Инструменты |
| :--- | :--- |
| **Метрики** | **Prometheus**, **VictoriaMetrics**, Mimir, Thanos |
| **Логи** | **ELK Stack** (Elasticsearch, Logstash, Kibana), **Grafana Loki** |
| **Трассировки** | **Jaeger**, **Grafana Tempo** |
| **Профилирование** | **Parca**, **Pyroscope**, PolarSignals (на базе eBPF) |
| **Визуализация** | **Grafana** (стандарт де-факто) |
| **Всё-в-одном** | **Datadog**, New Relic (платные); **Zabbix**, Nagios (инфраструктурные) |

## Практические сценарии

### Сценарий 1: Диагностика неизвестной проблемы

**Ситуация:** Пользователи жалуются на замедление загрузки страниц. Стандартные дашборды показывают норму по CPU и памяти, ошибок нет.

**Действия с использованием наблюдаемости:**

| Шаг | Действие | Инструмент |
| :--- | :--- | :--- |
| **1** | Проверка перцентилей задержки (p95, p99) | Grafana + Prometheus |
| **2** | Анализ трассировок для выявления узких мест | Tempo / Jaeger |
| **3** | Поиск логов по `trace_id` проблемного запроса | Loki / Elasticsearch |
| **4** | Профилирование сервиса для поиска «горячих точек» | Pyroscope |
| **5** | Выявление корневой причины (медленный SQL, внешний API) | Комбинация данных |

**Результат:** Обнаружено, что один из микросервисов делает N+1 запрос к базе данных. Проблема не была видна на метриках уровня инфраструктуры.

### Сценарий 2: Внедрение наблюдаемости с нуля

**Этапы внедрения:**

1. **Инструментирование приложения:**
   - Добавление OpenTelemetry SDK в код
   - Настройка автоматического сбора трейсов и метрик
   - Генерация `trace_id` для каждого запроса

2. **Настройка сбора телеметрии:**
   - Развёртывание OTel Collector
   - Настройка экспорта в бэкенды (Prometheus, Loki, Tempo)
   - Конфигурация сэмплирования для снижения нагрузки

3. **Создание дашбордов:**
   - Базовые дашборды по методологиям RED / Golden Signals
   - Дашборды для каждого сервиса с трассировками
   - Бизнес-метрики на отдельном дашборде

4. **Настройка алертинга:**
   - Алерты на критические метрики (доля ошибок, задержка)
   - Мультиоконные алерты для Burn Rate
   - Маршрутизация уведомлений по командам

### Сценарий 3: Корреляция данных при инциденте

**Пример:** Алерт сработал на высокую задержку (p99 > 2с).

**Корреляция через `trace_id`:**

```
Метрика (Prometheus) → trace_id=abc123
    ↓
Трассировка (Tempo) → span: payment-service (1.8с)
    ↓
Логи (Loki) → trace_id=abc123 → "Slow query: 1.5с"
    ↓
Профиль (Pyroscope) → payment-service.getPayment() → 80% CPU в SQL-запросе
```

**Вывод:** Проблема в отсутствии индекса в таблице платежей.
