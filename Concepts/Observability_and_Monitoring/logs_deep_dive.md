# Logs Deep Dive

## Определения

**Логи (Logs)** — неизменяемые, упорядоченные по времени записи о событиях в системе с временной меткой и контекстом.

**Назначение:**

- Детальный анализ инцидентов и отладка
- Аудит безопасности и комплаенс
- Расследование постфактум (forensics)
- Обогащение контекста при анализе проблем

**Примеры:** запись об ошибке в приложении, лог доступа к веб-серверу, запись о выполнении SQL-запроса, системные события ядра.

**Ключевой принцип observability:** логи должны быть структурированными (JSON) и содержать идентификаторы (`trace_id`, `request_id`) для корреляции с **[трассировками](./traces_deep_dive.md)** и **[метриками](./metrics_deep_dive.md)**.

**См. также:** [Четыре столпа Observability](./four_pillars_of_observability.md) — фундаментальные концепции наблюдаемости.

## Базовые концепции

### Характеристики логов

| Характеристика | Описание | Следствие |
| :--- | :--- | :--- |
| **Точность** | Сбор на каждое событие | Полная детализация до единичного запроса |
| **Пропорциональность** | Трафик логов ∝ трафику приложения | Сложно прогнозировать нагрузку |
| **Структура** | Часто не структурированы (plain text) | Сложности с парсингом и индексацией |
| **Избыточность** | Много лишних данных | Ухудшение обработки и агрегации |
| **Масштабируемость** | Отправка на каждое событие | Плохо масштабируется из-за объёма |

**Подход:** «Пишем всё, потом думаем» — ценой трафика и сложности обработки получаем полную детализацию.

### Уровни логирования

| Уровень | Описание | Когда использовать |
| :--- | :--- | :--- |
| **ERROR** | Ошибка, требующая внимания | Сбои, исключения, неудачные операции |
| **WARN** | Предупреждение о потенциальной проблеме | Нестандартные ситуации, деградация |
| **INFO** | Информационное сообщение о нормальном ходе работы | Старт/остановка сервиса, важные события |
| **DEBUG** | Отладочная информация для разработчиков | Детали выполнения, промежуточные значения |
| **TRACE** | Максимально детальная трассировка | Пошаговое выполнение, все вызовы |

### Форматы логов

| Формат | Преимущества | Недостатки |
| :--- | :--- | :--- |
| **Plain text** | Человекочитаемый, простота | Сложен для парсинга, нет структуры |
| **JSON** | Структурированный, машиночитаемый | Больше объём, требует парсера |
| **Key-Value** | Компактный структурированный формат | Менее распространён |
| **Syslog** | Стандартизированный (RFC 5424) | Сложнее в обработке |

**Рекомендация:** использовать **JSON** для production-систем — упрощает парсинг, индексацию и поиск в **[Loki](../../../Loki/loki_overview.md)** / **Elasticsearch**.

### Архитектура сбора логов

```
Приложение → Агент (Vector/Fluent Bit) → Транспорт (Kafka) → Обработка → Хранилище
```

**Компоненты:**

| Компонент | Назначение | Инструменты |
| :--- | :--- | :--- |
| **Сбор** | Чтение логов с хостов/контейнеров | Vector, Fluent Bit, Filebeat |
| **Транспорт** | Буферизация и доставка | Kafka, RabbitMQ |
| **Обработка** | Парсинг, трансформация, обогащение | Logstash, Vector, Fluent Bit |
| **Хранение** | Долгосрочное хранение и поиск | Loki, Elasticsearch, OpenSearch, ClickHouse |

**См. также:** **[Проектирование высоконагруженного мониторинга](./designing_high-load_monitoring_in_distributed_systems.md)** — типовая архитектура с Kafka и Loki.

## Практические сценарии

### Сценарий 1: Сбор логов в Kubernetes

**Задача:** организовать централизованный сбор логов из подов Kubernetes.

**Решение:** DaemonSet с Fluent Bit на каждой ноде.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluent-bit
  namespace: logging
spec:
  selector:
    matchLabels:
      app: fluent-bit
  template:
    metadata:
      labels:
        app: fluent-bit
    spec:
      containers:
      - name: fluent-bit
        image: fluent/fluent-bit:latest
        volumeMounts:
        - name: varlog
          mountPath: /var/log
        - name: containers
          mountPath: /var/lib/docker/containers
          readOnly: true
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
      - name: containers
        hostPath:
          path: /var/lib/docker/containers
```

**Конфигурация Fluent Bit (parsers.conf):**

```ini
[PARSER]
    Name        json
    Format      json
    Time_Key    time
    Time_Format %Y-%m-%dT%H:%M:%S.%L
```

### Сценарий 2: Корреляция логов с трассировками

**Задача:** связать логи с трассировками для быстрого анализа инцидентов.

**Решение:** добавление `trace_id` в каждый лог.

**Пример JSON-лога:**

```json
{
  "timestamp": "2025-03-24T10:15:30.123Z",
  "level": "ERROR",
  "service": "payment-service",
  "trace_id": "abc123def456",
  "span_id": "span789",
  "message": "Payment gateway timeout",
  "duration_ms": 5000,
  "user_id": "user_42"
}
```

**Поиск в Loki:**

```logql
{service="payment-service"} | json | trace_id="abc123def456"
```

### Сценарий 3: Фильтрация и агрегация логов

**Задача:** снизить объём хранимых логов без потери полезной информации.

**Методы:**

| Метод | Описание | Эффект |
| :--- | :--- | :--- |
| **Сэмплирование** | Сбор только доли логов (например, 10% INFO) | Снижение объёма в 10 раз |
| **Фильтрация по уровню** | Отбрасывание DEBUG в production | Снижение на 30–50% |
| **Агрегация повторяющихся** | Группировка одинаковых ошибок | Уменьшение дубликатов |
| **Исключение шумных источников** | Отключение логов от неважных компонентов | Точечное снижение |

**Пример конфигурации Vector:**

```toml
[transforms.filter_errors]
type = "filter"
inputs = ["kubernetes_logs"]
condition = ".level == \"error\" || .level == \"warn\""

[transforms.sample]
type = "sample"
inputs = ["kubernetes_logs"]
rate = 0.1
```

**Production-рекомендации по сэмплированию и хранению:**

| Аспект | Рекомендация |
|---|---|
| **Сэмплирование по уровню** | DEBUG/TRACE при >1000 RPS — не более 10%; ERROR/FATAL — всегда 100% (не сэмплировать) |
| **Retention** | Hot (оперативный поиск) — 7 дней; Cold (аудит, compliance) — до 90 дней, выгрузка в S3 / object storage |
| **Парсинг JSON** | Разбирать логи в структурированный формат на уровне агента (Fluentbit / Vector), а не в Logstash или системе хранения. Это снижает нагрузку на хранилище и упрощает дальнейшую обработку |
| **Единый UI** | Grafana как единый интерфейс для метрик (Prometheus) и логов (Loki) — корреляция через `trace_id` без переключения систем |

Retention настраивается: в Loki через `retention_period` и `retention_stream`; в Elasticsearch — ILM (Index Lifecycle Management) с политикой rollover → warm → cold → delete.

## Additional Information

### Инструменты экосистемы

| Категория | Инструменты | Описание |
| :--- | :--- | :--- |
| **Агенты сбора** | Vector, Fluent Bit, Filebeat | Лёгкие агенты для чтения логов |
| **Обработка** | Logstash, Vector, Fluentd | Парсинг, трансформация, обогащение |
| **Транспорт** | Kafka, RabbitMQ, NATS | Буферизация и надёжная доставка |
| **Хранение** | Loki, Elasticsearch, OpenSearch | Поиск и анализ логов |
| **Визуализация** | Grafana, Kibana | Дашборды и поиск |

### Сравнение хранилищ логов

| Хранилище | Преимущества | Недостатки | Когда использовать |
| :--- | :--- | :--- | :--- |
| **Loki** | Лёгкий, экономичный, интеграция с Grafana | Ограниченный полнотекстовый поиск | Cloud Native, Kubernetes |
| **Elasticsearch** | Мощный полнотекстовый поиск, гибкость | Ресурсоёмкий, сложная эксплуатация | Полнотекстовый анализ, SIEM |
| **OpenSearch** | Форк ES с открытой лицензией | Меньше комьюнити | Альтернатива ES |
| **ClickHouse** | Высокая производительность аналитики | Сложнее для логов | Аналитика в реальном времени |

### Best Practices

1. **Структурированное логирование:** всегда использовать JSON в production
2. **Единый формат:** стандартизировать поля (`timestamp`, `level`, `service`, `trace_id`)
3. **Контекст:** добавлять `trace_id`, `request_id`, `user_id` для корреляции
4. **Ротация:** настроить ротацию файлов логов (logrotate)
5. **Сэмплирование:** применять для снижения объёма в высоконагруженных системах
6. **Безопасность:** не логировать чувствительные данные (пароли, токены, PII)
