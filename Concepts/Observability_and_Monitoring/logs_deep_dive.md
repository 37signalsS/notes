# Логирование: глубокое погружение

## Определения

**Логи (Logs)** — неизменяемые, упорядоченные по времени записи о событиях в системе с временной меткой и контекстом. Каждый лог — это фиксированный снимок состояния системы в конкретный момент времени. Логи являются одним из четырех столпов наблюдаемости наряду с метриками, трассировками и профилями.

**Структурированное логирование** — метод записи логов в машиночитаемом формате (обычно JSON), где каждое поле имеет определенный тип и имя. Это позволяет выполнять высокоэффективный поиск и агрегацию без сложного регулярного парсинга. Структурированные логи критичны для автоматизации: они позволяют агентам (Vector, Fluent Bit) извлекать поля без регулярных выражений, что снижает нагрузку на CPU и исключает ошибки парсинга.

**Пайплайн логирования (Logging Pipeline)** — последовательность этапов обработки лога от момента его генерации приложением до сохранения в хранилище. Типичные этапы: *Capture (Захват) → Transform (Трансформация/Обогащение) → Buffer (Буферизация) → Route (Маршрутизация) → Sink (Хранилище)*. Каждый этап может вносить задержку (latency) и создавать точку отказа (single point of failure), поэтому архитектура пайплайна требует баланса между надежностью и производительностью.

**Backpressure (Обратное давление)** — механизм управления потоком данных, при котором потребитель (хранилище) сигнализирует производителю (агенту) о невозможности обработать данные с текущей скоростью. В контексте логирования backpressure возникает при переполнении буфера агента или недоступности хранилища. Правильная обработка backpressure критична: агент должен либо буферизовать данные на диске (risking задержкой доставки), либо отбрасывать логи (risking потерей данных), либо блокировать источник (risking деградацией приложения).

**Correlation ID (Идентификатор корреляции)** — уникальный идентификатор (обычно `trace_id` или `request_id`), который передается через все компоненты распределенной системы и позволяет связать логи, трассировки и метрики, относящиеся к одному запросу. Без correlation ID диагностика проблем в микросервисной архитектуре становится практически невозможной.

**Structured Metadata (Структурированные метаданные)** — механизм (введен в Loki 3.x), позволяющий прикреплять контекст к строкам логов без создания новых лейблов. Это решает проблему взрыва кардинальности (high cardinality): уникальные значения (session_id, trace_id, user_id) хранятся как метаданные, а не как лейблы, что позволяет фильтровать и искать по ним без увеличения индекса.

**Назначение логов:**

- Детальный анализ инцидентов и отладка.
- Аудит безопасности и комплаенс.
- Расследование постфактум (forensics).
- Обогащение контекста при анализе проблем.
- Построение SLI (Service Level Indicators) на основе лог-метрик.

**Примеры:** запись об ошибке в приложении, лог доступа к веб-серверу, запись о выполнении SQL-запроса, системные события ядра,审计-логи Kubernetes API.

**Ключевой принцип Observability:** логи должны быть структурированными и содержать идентификаторы (`trace_id`, `request_id`) для корреляции с **[трассировками](./traces_deep_dive.md)** и **[метриками](./metrics_deep_dive.md)**. Отсутствие корреляционных идентификаторов делает логи изолированными островками информации, которые невозможно связать в единый контекст.

**См. также:** [Четыре столпа Observability](./four_pillars_of_observability.md) — фундаментальные концепции наблюдаемости.

## Базовые концепции

### Решения для агрегации логов

Агрегация логов необходима для централизации данных из множества источников (особенно в динамических средах вроде Kubernetes), что позволяет быстро анализировать поведение системы и инфраструктуры.

**Критические функции агрегаторов:**
- **Централизованное хранилище:** Объединение логов в единый ресурс с мощными возможностями полнотекстового или структурированного поиска (Kibana, Grafana, Splunk).
- **Обработка в реальном времени:** Анализ данных по мере их поступления для оперативного реагирования.
- **Поиск и фильтрация:** Возможность выполнять сложные запросы по критериям (временной диапазон, уровень лога, конкретные ключевые слова).
- **Визуализация:** Инструментальные панели и диаграммы для анализа тенденций, понимания поведения системы и выявления аномалий.
- **Оповещения (Alerting):** Генерация уведомлений на основе предварительно определенных правил (например, частое появление ошибок или внезапный всплеск объема логов).

**Этапы агрегации:**
1.  **Сбор (Collection):** Агенты (Fluent Bit, Filebeat, Promtail, Logstash) читают логи из источников (файлы, stdout, системные журналы).
2.  **Централизация и обработка:** Пересылка в центральный узел (Elasticsearch/OpenSearch, Loki), где данные могут очищаться от конфиденциальной информации, приводиться к единому формату и обогащаться метаданными.
3.  **Анализ и хранение:** Индексация для быстрого поиска и применение политик хранения (retention).

### Характеристики логов

| Характеристика | Описание | Следствие |
| :--- | :--- | :--- |
| **Точность** | Сбор на каждое событие | Полная детализация до единичного запроса |
| **Пропорциональность** | Трафик логов пропорционален трафику приложения | Сложно прогнозировать нагрузку |
| **Структура** | Часто не структурированы (plain text) | Сложности с парсингом и индексацией |
| **Избыточность** | Много лишних данных | Ухудшение обработки и агрегации |
| **Масштабируемость** | Отправка на каждое событие | Плохо масштабируется из-за объёма |
| **Backpressure** | Сопротивление при переполнении буфера | Риск потери логов или замедления приложения |

**Подход:** «Пишем всё, потом думаем» — ценой трафика и сложности обработки получаем полную детализацию.

### Управление backpressure

Backpressure — одна из ключевых проблем в пайплайнах логирования. Когда хранилище (Loki, Elasticsearch) не справляется с потоком данных, агент оказывается перед выбором: буферизовать, отбрасывать или блокировать источник.

**Стратегии обработки backpressure:**

| Стратегия | Механизм | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Disk Buffer** | Агент записывает логи на диск при недоступности хранилища | Гарантия доставки (at-least-once) | Задержка доставки, расход диска |
| **Memory Buffer** | Буферизация в оперативной памяти | Быстродействие | Потеря данных при переполнении RAM |
| **Drop (Отбрасывание)** | Удаление старых событий из кольцевого буфера | Предотвращение блокировки | Потеря данных, но стабильность приложения |
| **Block (Блокировка)** | Приостановка чтения из источника | Полная гарантия доставки | Деградация приложения (timeout, OOM) |

**Рекомендация для production:** Использовать персистентный disk-backed буфер (Vector, Fluent Bit) с разумным лимитом. Для критичных логов (аудит, безопасность) — block-режим с контролируемым таймаутом. Для остальных — drop с мониторингом потерь.

**Мониторинг backpressure:** Агенты предоставляют метрики состояния буферов:
- Vector: `component_buffer_*` (bytes, events, utilization)
- Fluent Bit: `fluentbit_output_retries_total`, `fluentbit_output_errors_total`

### Multiline-логи и склейка строк

Многие приложения (Java, Python, Go) генерируют многострочные логи — стеки вызовов, stack traces, составные сообщения. Без склейки каждая строка попадает в хранилище как отдельное событие, что делает чтение невозможным.

**Типичные проблемы:**
- Java stack trace занимает 20-50 строк, каждая попадает как отдельный лог
- Python traceback разбит на несколько строк
- Составные JSON-объекты, записанные построчно

**Механизм склейки (Concat/Merge):**
Агенты (Vector, Fluent Bit, Fluentd) используют регулярные выражения для определения границ события:
1. `multiline_start_regexp` — паттерн начала нового события (например, `^\d{4}-\d{2}-\d{2}`)
2. `flush_interval` — таймаут ожидания следующей строки (если не пришла — сбрасываем накопленное)
3. `timeout_first_line` — максимальное время ожидания первой строки многострочного блока

**Пример во Fluent Bit:**
```ini
[FILTER]
    Name multiline
    Match *
    multiline.key_content log
    multiline.parser java,python
```

**Пример в Vector (VRL):**
```toml
[transforms.multiline]
type = "remap"
inputs = ["in"]
source = '''
  if includes(["java", "python"], .service) {
    .message = join(.multiline_lines, "\n")
  }
'''
```

### Correlation ID и распределенная трассировка

В микросервисной архитектуре один запрос может проходить через 5-20 сервисов. Без общего идентификатора диагностика проблемы требует ручного поиска логов в каждом сервисе по временным меткам — крайне неэффективно и ошибочно.

**Механизм работы:**
1. API-шлюз или ingress генерирует `trace_id` (OpenTelemetry) или `request_id`
2. Идентификатор передается через HTTP-заголовки (`traceparent`, `X-Request-ID`)
3. Каждый сервис добавляет `trace_id` в структурированный лог
4. При расследовании инцидента один запрос к Loki/Tempo находит все логи и трассировку

**Формат передачи (W3C Trace Context):**
```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```
Где:
- `00` — версия протокола
- `4bf92f3577b34da6a3ce929d0e0e4736` — trace_id
- `00f067aa0ba902b7` — span_id (конкретный вызов)
- `01` — флаги (sampled)

**Интеграция с логами:** При добавлении `trace_id` в лог_Enable_linking_logs_to_traces借助 Derived Fields в Loki или через Tempo Service Graph. Это позволяет из Grafana перейти от графика метрик → к логам → к трассировке за три клика.

### Обогащение логов (Enrichment)

Сырой лог часто не содержит достаточно контекста для быстрой диагностики. Процесс обогащения (enrichment) добавляет метаданные на этапе сбора.

**Типы метаданных для обогащения:**

| Тип | Источник | Примеры полей |
| :--- | :--- | :--- |
| **Инфраструктурные** | Kubernetes API, cloud metadata | `pod_name`, `node_name`, `namespace`, `cluster` |
| **Пользовательские** | Контекст запроса, JWT | `customer_id`, `plan_type`, `tenant_id` |
| **Географические (GeoIP)** | IP-адрес клиента | `geo_city`, `geo_country`, `geo_asn` |
| **Технические** | Заголовки HTTP, метрики приложения | `user_agent`, `http_method`, `response_time_ms` |
| **Сетевые** | Ядро Linux, iptables | `src_ip`, `dst_port`, `network_namespace` |

**Методы обогащения:**
1. **Lookup Tables (Vector):** Загрузка CSV/JSON в память агента для быстрого сопоставления IP → город.
2. **Kubernetes Metadata (Fluent Bit):** Запрос к K8s API для получения labels пода.
3. **Enrichment Tables (Vector):** Динамические таблицы, обновляемые без перезапуска агента.
4. **GeoIP (MaxMind):** Локальная база данных для определения геолокации по IP.

**Важно:** Обогащение должно выполняться как можно ближе к источнику (в агенте), чтобы чувствительные данные (IP-адреса, email) не покидали хост в открытом виде. См. раздел "Безопасность логов".

### Паттерны сбора логов

Выбор паттерна зависит от требований к надежности, ресурсам и сложности эксплуатации.

1.  **Node-level Agent (DaemonSet):**
    - **Суть:** На каждой ноде работает один агент, который собирает логи всех контейнеров из стандартных путей (`/var/log/pods`).
    - **Плюсы:** Минимальный overhead, простота управления.
    - **Минусы:** Сложно реализовать разную логику обработки для разных приложений.
2.  **Sidecar Container:**
    - **Суть:** В каждый Pod добавляется контейнер-агент (например, Fluent Bit), который читает логи основного приложения через shared volume или по сети.
    - **Плюсы:** Изоляция, возможность сложной специфичной обработки для конкретного сервиса.
    - **Минусы:** Удвоение количества контейнеров, значительное потребление ресурсов в больших кластерах.
3.  **Application-level (Direct Logging):**
    - **Суть:** Приложение само отправляет логи напрямую в хранилище (Loki, Elasticsearch) или брокер (Kafka) через сетевой протокол (HTTP/gRPC).
    - **Плюсы:** Отсутствие промежуточных агентов на хосте, высокая скорость.
    - **Минусы:** Усложнение кода приложения, риск потери логов при недоступности сети (если нет локальной очереди).

### Уровни логирования

| Уровень | Описание | Когда использовать |
| :--- | :--- | :--- |
| **ERROR** | Ошибка, требующая внимания | Сбои, исключения, неудачные операции |
| **WARN** | Предупреждение о потенциальной проблеме | Нестандартные ситуации, деградация |
| **INFO** | Информационное сообщение о нормальном ходе работы | Старт/остановка сервиса, важные события |
| **DEBUG** | Отладочная информация для разработчиков | Детали выполнения, промежуточные значения |
| **TRACE** | Максимально детальная трассировка | Пошаговое выполнение, все вызовы |

### Форматы логов

| Формат | Преимущества | Недостатки |
| :--- | :--- | :--- |
| **Plain text** | Человекочитаемый, простота | Сложен для парсинга, нет структуры |
| **JSON** | Структурированный, машиночитаемый | Больше объём, требует парсера |
| **OTLP** | Унифицированный формат OpenTelemetry | Требует поддержки SDK или Collector |
| **Syslog** | Стандартизированный (RFC 5424) | Сложнее в обработке |

**Рекомендация:** использовать **JSON** или **OTLP** (OpenTelemetry Line Protocol) для Production-систем. OTLP позволяет объединить логи, метрики и трейсы в единый поток данных.

### Архитектура сбора логов

```bash
Приложение (Log SDK) → Агент (Vector/Fluent Bit) → Транспорт (Kafka) → Обработка → Хранилище
```

**Компоненты:**

| Компонент | Назначение | Инструменты |
| :--- | :--- | :--- |
| **Сбор** | Чтение логов с хостов или контейнеров | Vector, Fluent Bit, Filebeat |
| **Транспорт** | Буферизация и доставка | Kafka, RabbitMQ, NATS |
| **Обработка** | Парсинг, трансформация, обогащение | Vector, Logstash, Fluent Bit |
| **Хранение** | Долгосрочное хранение и поиск | Loki, ClickHouse, Elasticsearch |

### Сравнение хранилищ логов

| Хранилище | Преимущества | Недостатки | Когда использовать |
| :--- | :--- | :--- | :--- |
| **Loki** | Экономичный, интеграция с Grafana, LogQL (близок к PromQL), Bloom-фильтры (3.x) для ускорения поиска | Ограниченный полнотекстовый поиск (только по лейблам и filter expressions) | Kubernetes, Cloud Native, стек Grafana |
| **VictoriaLogs** | Высокое сжатие, быстрый полнотекстовый поиск, schema-less, низкое потребление RAM | Меньшая экосистема по сравнению с ELK, молодой проект | Высоконагруженные системы, замена ELK/Loki, Bare-metal |
| **Elasticsearch** | Мощный полнотекстовый поиск, развитая экосистема (Kibana, Beats, Logstash) | Ресурсоёмкий (RAM/CPU), сложная эксплуатация, лицензирование (SSPL) | SIEM, compliance, сложный полнотекстовый анализ |
| **ClickHouse** | Высочайшая скорость аналитики,列式 storage, 효과ное сжатие | Сложнее в настройке схемы для логов, нет нативного LogQL | Аналитика больших объёмов,隐式-аналитика |
| **Graylog (OpenSearch)** | Встроенный Web UI, alerting, корреляция событий (SIGMA-правила) | Ресурсоёмкий, сложная кластеризация | SIEM, compliance,_SECURITYteams |

**Критерии выбора хранилища:**

| Критерий | Рекомендация |
| :--- | :--- |
| **Стоимость владения (TCO)** | Loki или VictoriaLogs (меньше ресурсов) |
| **Полнотекстовый поиск** | Elasticsearch или VictoriaLogs |
| **Интеграция с Grafana** | Loki (нативная) или VictoriaLogs (через плагин) |
| **Compliance / SIEM** | Elasticsearch (отраслевой стандарт) |
| **Простота эксплуатации** | VictoriaLogs (schema-less) или Loki (Simple Scalable mode) |
| **Высокая нагрузка (>1TB/день)** | ClickHouse или распределенный Loki |

### Жизненный цикл логов (Log Lifecycle)

Управление логами требует баланса между стоимостью хранения и скоростью доступа. Правильная стратегия retention критична для контроля стоимости и compliance.

| Этап | Срок | Хранилище | Доступ | Назначение |
| :--- | :--- | :--- | :--- | :--- |
| **Hot (Горячие данные)** | 7–14 дней | Быстрые диски (NVMe/SSD), object storage с hot tier | Мгновенный полнотекстовый поиск, алертинг | Оперативная диагностика, реагирование на инциденты |
| **Warm (Тёплые данные)** | 15–30 дней | Индексы с пониженной плотностью, HDD | Поиск с задержкой (секунды-минуты) | Расследование инцидентов за прошлую неделю |
| **Cold (Холодные данные)** | 30–90 дней | Объектные хранилища (S3, MinIO) | Медленный поиск или rehydration | Аналитика, отчеты, долгосрочные тренды |
| **Frozen/Archive (Архив)** | 1 год+ | Сжатые архивы (Parquet, gzip) | Требует предварительного восстановления | Комплаенс, аудит, юридические требования |

**Политики retention в Loki:**
```yaml
limits_config:
  retention_period: 744h  # 31 день
  max_query_length: 721h  # Максимальный диапазон запроса

storage_config:
  boltdb_shipper:
    active_index_directory: /loki/index
    cache_location: /loki/cache
  aws:
    s3:
      s3: s3://loki-data
    bucketnames: loki-data
    s3forcepathstyle: true

compactor:
  compaction_interval: 10m
  retention_enabled: true
  retention_delete_delay: 2h
  retention_delete_worker_count: 150
```

```json
        "min_age": "90d",
        "actions": {
          "delete": {}
        }
      }
    }
  }
}
```

**Рекомендации по retention:**

| Тип данных | Срок хранения | Обоснование |
| :--- | :--- | :--- |
| **Оперативные логи (INFO/DEBUG)** | 7–14 дней | Достаточно для диагностики большинства инцидентов |
| **Логи ошибок (ERROR/WARN)** | 30–90 дней | Повторяющиеся ошибки могут обнаруживаться через недели |
| **Аудит/Комплаенс** | 1–3 года | Требования PCI DSS, SOC 2, HIPAA |
| **Системные логи (syslog)** | 30–90 дней | Диагностика инфраструктурных проблем |

### Сэмплирование логов (Log Sampling)

В высоконагруженных системах запись каждого события может перегрузить сеть и хранилище. Сэмплирование — компромисс между полнотой данных и стоимостью хранения.

**Типы сэмплирования:**

| Тип | Механизм | Когда использовать | Риск |
| :--- | :--- | :--- | :--- |
| **Head-based (Статическое)** | Решение о сбросе принимается в момент генерации (например, писать только 10% INFO-логов) | Простые системы, предсказуемая нагрузка | Потеря редких, но важных событий |
| **Adaptive (Динамическое)** | Агент отслеживает частоту событий и начинает сбрасывать при превышении порога (RPS) | Системы с пиковыми нагрузками | Сложность настройки порогов |
| **Tail-based (На основе контекста)** | Система анализирует цепочку событий (в рамках `trace_id`) и сохраняет все логи, если в цепочке есть ошибка | Микросервисы с распределенной трассировкой | Требует интеграции с трассировщиком |
| **Rule-based (По правилам)** | Сохраняются логи определенных уровней (ERROR, WARN) или содержащие ключевые слова | Аудит, безопасность, compliance | Пропуск информативных INFO-сообщений |

**Пример adaptive-сэмплирования во Vector:**
```toml
[transforms.sample_info]
type = "sample"
inputs = ["app_logs"]
rate = 10        # Пропускать 1 из 10 событий
exclude.type = "log"
exclude.condition = '.level == "ERROR" || .level == "WARN"'
```

**Tail-based сэмплирование в OpenTelemetry:**
OpenTelemetry Collector поддерживает processor `tail_sampling`, который анализирует полную трассировку перед принятием решения:
```yaml
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errors
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: slow-traces
        type: latency
        latency: {threshold_ms: 1000}
```

**Рекомендация:** Начинайте с head-based сэмплирования для простых систем. При переходе на микросервисы с распределенной трассировкой — мигрируйте на tail-based, чтобы сохранять полные цепочки для ошибок и медленных запросов.

### Обогащение и безопасность логов

Сырой лог часто не содержит достаточно контекста для быстрой диагностики. Процесс обогащения (enrichment) добавляет метаданные на этапе сбора.

**Типы метаданных для обогащения:**
- **Инфраструктурные:** Имя пода, ноды, пространства имен (из API Kubernetes).
- **Пользовательские:** `customer_id`, `plan_type` (из контекста запроса).
- **Географические (GeoIP):** Город и страна пользователя на основе IP-адреса.
- **Технические:** Версия User-Agent, метод запроса, время ответа.

**Безопасность (Data Masking):**
Логи не должны содержать PII (Personal Identifiable Information) или секреты.
- **Маскирование:** Замена части данных (например, `4242 **** **** 4242` для банковских карт).
- **Хеширование:** Замена данных их необратимым хешем (например, для email-адресов при сохранении аналитической ценности).
- **Удаление (Dropping):** Полное исключение поля из записи.
- **Рекомендация:** Выполняйте маскирование как можно ближе к источнику (в агенте), чтобы чувствительные данные не покидали хост в открытом виде.

**Типичные PII-поля, требующие маскирования:**

| Тип данных | Пример в логе | Метод маскирования |
| :--- | :--- | :--- |
| **Номера карт** | `card=4242-1234-5678-9012` | `card=4242-****-****-9012` |
| **Email** | `user@example.com` | `user@***.***` или SHA-256 хеш |
| **IP-адреса** | `192.168.1.100` | Оставить для геолокации, замаскировать для privacy |
| **Токены** | `Bearer eyJhbGciOi...` | Полное удаление или замена на `[REDACTED]` |
| **Пароли** | `password=secret123` | Полное удаление перед записью |

**Пример маскирования во Vector (VRL):**
```toml
[transforms.mask_pii]
type = "remap"
inputs = ["in"]
source = '''
  # Маскирование номеров карт (Visa, Mastercard)
  .message = replace(.message, r'\b\d{4}[- ]?\d{4}[- ]?\d{4}[- ]?\d{4}\b', "XXXX-XXXX-XXXX-XXXX")
  
  # Маскирование email
  .message = replace(.message, r'\b[\w.-]+@[\w.-]+\.\w+\b', "[EMAIL_REDACTED]")
  
  # Маскирование токенов
  .message = replace(.message, r'Bearer\s+[A-Za-z0-9\-._~+/]+=*', "Bearer [REDACTED]")
'''
```

**Важно:** Маскирование должно выполняться ДО отправки логов в сеть (в агенте на хосте), чтобы чувствительные данные никогда не покидали пределы машины. Это критично для compliance (PCI DSS, GDPR).

### Экономика логирования

Извлечение метрик из журналов (log-based metrics) обходится значительно дороже нативного сбора метрик через код приложения. 
- Для одной метрики приходится хранить полнотекстовый журнал.
- В среднем метрики на основе логов **на 200% дороже** метрических данных (при долгосрочном хранении разрыв может быть еще больше).
- **Рекомендация:** Реализуйте как можно больше метрик непосредственно в коде приложения и используйте систему мониторинга для их сбора.

### Лучшие практики

1. **Структурированное логирование:** всегда использовать JSON в Production.
2. **Единый формат:** стандартизировать базовые поля (`timestamp`, `level`, `service`, `trace_id`).
3. **Экономика мониторинга (Cost Optimization):** Извлечение метрик из логов обходится значительно дороже (на **200% и более**), чем нативный сбор метрик через код приложения. Рекомендуется реализовывать как можно больше метрик непосредственно в коде, оставляя логи для детальной отладки.
4. **Контекст:** добавлять метаданные (`node_name`, `pod_name`, `customer_id`) для ускорения фильтрации.
5. **Сэмплирование:** применять для INFO/DEBUG логов в высоконагруженных системах (>1000 RPS).
6. **Безопасность:** маскировать PII (Personal Identifiable Information) и секреты перед отправкой в хранилище.
7. **Correlation ID:** генерировать `trace_id` на edge-уровне (API-шлюз, ingress) и передавать через все сервисы для диагностики распределенных систем.
8. **Backpressure:** использовать disk-backed буфер в агентах (Vector, Fluent Bit) для гарантии доставки при кратковременных сбоях хранилища.
9. **Retention Policies:** настраивать автоматическое удаление старых данных (hot → warm → cold → delete) для контроля стоимости.
10. **Мониторинг агентов:** отслеживать метрики буферов и rates агентов (Vector: `component_buffer_*`, Fluent Bit: `fluentbit_output_*`) для раннего обнаружения проблем.
11. **Multiline:** настраивать склейку строк для приложений, генерирующих многострочные логи (Java, Python, Go).
12. **Версионирование конфигурации:** хранить конфигурации агентов и retention policies в Git для воспроизводимости.

## Практические сценарии

### Сценарий 1: Сбор логов в Kubernetes (Modern)

**Задача:** собрать логи контейнеров в кластере, использующем `containerd`.

**Решение:** DaemonSet с Fluent Bit, настроенным на чтение `/var/log/pods/`.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluent-bit
  namespace: logging
spec:
  selector:
    matchLabels:
      app: fluent-bit
  template:
    metadata:
      labels:
        app: fluent-bit
    spec:
      containers:
      - name: fluent-bit
        image: fluent/fluent-bit:5.0.9 # Актуальная версия на 2026 год
        volumeMounts:
        - name: varlog
          mountPath: /var/log
        - name: varlibcontainerd
          mountPath: /var/lib/containerd
          readOnly: true
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
      - name: varlibcontainerd
        hostPath:
          path: /var/lib/containerd
```

Подробная конфигурация парсеров приведена в основном разделе: [Парсинг логов во Fluent Bit](../../Kubernetes/MonitoringLogging/EFK/fluentbit/parsing.md).

**Валидация:**
1. Проверить статус DaemonSet: `kubectl get ds fluent-bit -n logging`.
2. Убедиться, что логи читаются: `kubectl logs -n logging -l app=fluent-bit`.
3. Проверить поступление логов в хранилище (Loki/Elasticsearch) через UI (Grafana/Kibana).

### Сценарий 6: Склейка многострочных логов (Java Stack Traces)

**Задача:** настроить Fluent Bit для склейки многострочных Java stack traces в единое событие.

**Проблема:** Без настройки multiline каждая строка stack trace попадает в Loki как отдельное событие, что делает чтение невозможным.

**Конфигурация Fluent Bit:**

```ini
[FILTER]
    Name multiline
    Match *
    multiline.key_content log
    multiline.parser java

[OUTPUT]
    Name loki
    Match *
    labels job=java-app
    label_keys $service_name
    auto_kubernetes_labels on
```

**Парсер Java во Fluent Bit (встроенный):**
```
[PARSER]
    Name java
    Format regex
    Regex ^(?<time>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}\.\d{3})\s+(?<level>\w+)\s+(?<thread>\[.*?\])\s+(?<logger>\S+)\s*[:\-]\s*(?<message>.*)$
```

**Валидация:**
1. Отправить Java stack trace в приложение
2. Проверить в Loki: `{job="java-app"} |= "Exception"`
3. Убедиться, что весь stack trace — единое событие (одна строка в JSON)

### Сценарий 7: Structured Metadata в Loki 3.x

**Задача:** добавить `trace_id` и `customer_id` к логам без создания новых лейблов (чтобы избежать взрыва кардинальности).

**Проблема:** Если добавить `trace_id` как лейбл в Loki, количество уникальных комбинаций лейблов станет огромным (high cardinality), что приведет к переполнению индекса и деградации производительности.

**Решение:** Использовать Structured Metadata — метаданные, которые хранятся вместе с логом, но не индексируются как лейблы.

**Конфигурация Fluent Bit (Loki Output):**
```ini
[OUTPUT]
    Name loki
    Match *
    labels job=my-app,env=prod
    structured_metadata trace_id=$trace_id customer_id=$customer_id
    remove_keys trace_id,customer_id
```

**Запрос в LogQL с фильтрацией по structured metadata:**
```
{job="my-app"} | json | trace_id="4bf92f3577b34da6a3ce929d0e0e4736"
```

**Валидация:**
1. Отправить лог с `trace_id` в приложении
2. Проверить в Loki: `{job="my-app"} | json | trace_id="<your-trace-id>"`
3. Убедиться, что `trace_id` не отображается как лейбл в Grafana

### Сценарий 8: Централизованное логирование Bare-metal серверов (Vector + Loki)

**Задача:** собрать логи с 50 bare-metal серверов (Debian/Ubuntu) в централизованное хранилище.

**Компоненты:**
- **Агент:** Vector (Daemon Mode) на каждом сервере
- **Хранилище:** Loki (Simple Scalable mode)
- **Визуализация:** Grafana

**Конфигурация Vector на сервере (agent mode):**
```toml
[sources.journald]
type = "journald"
include_units = ["nginx", "postgresql", "sshd"]

[sources.syslog]
type = "file"
include = ["/var/log/syslog", "/var/log/auth.log"]

[sinks.loki]
type = "loki"
inputs = ["journald", "syslog"]
endpoint = "http://loki.internal:3100"
labels.job = "{{ env.HOSTNAME }}"
labels.env = "production"
encoding.codec = "json"
batch.max_bytes = 1048576
batch.timeout_secs = 5
buffer.type = "disk"
buffer.max_size = 5368709120  # 5GB
buffer.when_full = "drop_newest"
```

**Валидация:**
1. Проверить статус Vector: `systemctl status vector`
2. Проверить метрики: `curl http://localhost:9598/metrics`
3. Проверить поступление логов в Loki через Grafana

## Диагностика и устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Потеря логов (Log Loss)** | Переполнение буфера агента, backpressure от хранилища | Увеличить размер буфера (disk buffer), настроить ретраи, масштабировать хранилище. |
| **Ошибки парсинга** | Изменение формата лога в приложении | Проверить регулярные выражения, использовать JSON-логирование для исключения парсинга. |
| **Высокая стоимость хранения** | Избыточное логирование (DEBUG в Prod), отсутствие сэмплирования | Настроить сэмплирование, уменьшить срок хранения (retention), перевести INFO в метрики. |
| **Задержка появления (Latency)** | Большая очередь в брокере (Kafka), медленная индексация | Мониторить `consumer lag` в Kafka, оптимизировать шардинг в Elasticsearch. |
| **Multiline-логи разбиты** | Не настроена склейка строк | Включить multiline-парсер (Fluent Bit: `multiline.parser`, Vector: `remap` с condition). |
| **Взрыв кардинальности (High Cardinality)** | Уникальные значения (user_id, trace_id) как лейблы в Loki | Использовать Structured Metadata (Loki 3.x) вместо лейблов для уникальных значений. |
| **Дублирование логов** | Несколько агентов читают один источник | Убедиться, что DaemonSet работает в single-instance режиме, проверить пути чтения. |
| **Высокое потребление RAM агентом** | Слишком большой буфер в памяти или сложные парсеры | Уменьшить `buffer.max_size`, оптимизировать VRL/регулярные выражения, перейти на disk-backed буфер. |
| **Логи не появляются в Loki** | Проблемы с подключением, неверные labels, rate limiting | Проверить endpoint Loki, метрики агента, rate limits в Loki (`limits_config`). |
| **Старые логи не удаляются** | Не настроены retention policies | Включить `retention_enabled: true` в Loki, настроить ILM в Elasticsearch. |
| **Потеря логов при restaring пода** | Агент не успевает прочитать лог до удаления | Увеличить `containerLogMaxSize` в kubelet, настроить disk-backed буфер агента. |

### Мониторинг пайплайна логов

Критично отслеживать не только прикладные логи, но и сам пайплайн сбора. Проблемы с агентом или хранилищем должны обнаруживаться до потери данных.

**Ключевые метрики для мониторинга:**

| Метрика | Что показывает | Инструмент |
| :--- | :--- | :--- |
| `component_buffer_utilization` | Заполненность буфера агента | Vector internal metrics |
| `fluentbit_output_retries_total` | Количество повторных попыток отправки | Fluent Bit metrics |
| `loki_ingester_streams_created_total` | Потоки, создаваемые в Loki | Loki metrics |
| `loki_query_duration_seconds` | Время выполнения запросов к Loki | Loki metrics |
| `log_lines_received_total` | Объем получаемых логов | Агент metrics |

**Алерты для пайплайна логов:**

```yaml
# Пример Prometheus alerting rule для Vector
groups:
  - name: logging-pipeline
    rules:
      - alert: VectorBufferHighUtilization
        expr: vector_buffer_utilization > 0.8
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Buffer utilization > 80%"
          
      - alert: VectorBufferFull
        expr: vector_buffer_utilization > 0.95
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Buffer utilization > 95% - risk of log loss"
```

### Архитектурные паттерны

#### Паттерн 1: Agent → Storage (Простой)
Каждый агент отправляет логи напрямую в хранилище. Подходит для небольших систем (<10 серверов).

#### Паттерн 2: Agent → Aggregator → Storage (С агрегацией)
Агенты отправляют логи в централизованный агрегатор (Vector Aggregator, Kafka), который выполняет обогащение, дедупликацию и маршрутизацию. Подходит для средних систем (10-500 серверов).

#### Паттерн 3: Agent → Kafka → Aggregator → Storage (Высокая нагрузка)
Промежуточная очередь Kafka обеспечивает буферизацию и обработку backpressure. Подходит для высоконагруженных систем (>500 серверов, >1TB логов/день).

**Сравнение паттернов:**

| Паттерн | Сложность | Отказоустойчивость | Стоимость | Рекомендация |
| :--- | :--- | :--- | :--- | :--- |
| Agent → Storage | Низкая | Низкая | Низкая | Dev/test, малые системы |
| Agent → Aggregator → Storage | Средняя | Высокая | Средняя | Production (10-500 серверов) |
| Agent → Kafka → Aggregator → Storage | Высокая | Очень высокая | Высокая | Высоконагруженные системы, compliance |
