# Четыре столпа Observability

## Определения

**Четыре столпа Observability** — фундаментальная концепция наблюдаемости распределённых систем, объединяющая четыре типа телеметрических данных (сигналов) для получения полной картины состояния системы:

1. **Логи (Logs)** — записи об атомарных событиях.
2. **Метрики (Metrics)** — агрегированные числовые показатели (временные ряды).
3. **Трассировки (Traces)** — путь запроса через цепочку микросервисов.
4. **Профилирование (Profiling)** — детализация потребления ресурсов кодом.

**Ключевой принцип:** Наблюдаемость (Observability) — это не просто сумма четырех инструментов, а **возможность корреляции** между ними. Эффективная система позволяет мгновенно перейти от аномалии в метрике к соответствующему трейсу, а от него — к конкретным логам и профилю функции.

**См. также:** [Определения Observability](./observability_definitions.md) — базовые понятия мониторинга и наблюдаемости.

## Базовые концепции

### 1. Логи (Logs)

**Логи** — неизменяемые, упорядоченные по времени записи о событиях в системе с временной меткой и контекстом.

**Назначение:** детальный анализ инцидентов, аудит безопасности, расследование постфактум.

**Характеристики:**

| Характеристика | Описание |
| :--- | :--- |
| **Точность** | Сбор на каждое событие — полная детализация. |
| **Пропорциональность** | Трафик логов растёт пропорционально нагрузке на приложение. |
| **Структура** | Рекомендуется использовать **JSON** для автоматизированного парсинга. |
| **Масштабируемость** | Ресурсоёмкий процесс из-за объёма индексации и хранения. |

**Инструменты:** **[Loki](../../Loki/loki_overview.md)**, **Elasticsearch**, **[Vector](../../Vector/vector_overview.md)**, **Fluent Bit**.

Подробнее: **[Логи: детали](./logs_deep_dive.md)**.

### 2. Метрики (Metrics)

**Метрики** — числовые значения, измеряемые через интервалы времени (временные ряды), агрегирующие информацию о поведении системы.

**Назначение:** мониторинг производительности в реальном времени, алертинг, анализ трендов и SLA/SLO.

**Характеристики:**

| Характеристика | Описание |
| :--- | :--- |
| **Эффективность** | Компактное хранение, быстрая обработка запросов. |
| **Агрегация** | Позволяют видеть общую картину (RPS, Error Rate, Latency). |
| **Детализация** | Низкая — не показывают детали конкретных запросов. |
| **Кардинальность** | Критически важно избегать слишком большого количества уникальных меток (labels). |

**Инструменты:** **[Prometheus](../../Prometheus/overview.md)**, **[VictoriaMetrics](../../VictoriaMetrics/overview.md)**, **Grafana Mimir**.

Подробнее: **[Метрики: детали](./metrics_deep_dive.md)**.

### 3. Трассировки (Traces)

**Трассировка** — отслеживание пути выполнения запроса через все компоненты распределённой системы.

**Назначение:** выявление задержек в микросервисах, анализ зависимостей, поиск «затыков» в каскадных вызовах.

**Ключевой стандарт:** **W3C Trace Context** обеспечивает сквозную передачу заголовков `trace_id` между разнородными системами.

**Сэмплирование (Sampling):** механизм отбора доли трейсов (например, 10% или только ошибки) для снижения нагрузки на хранилище.

**Инструменты:** **Jaeger**, **[Grafana Tempo](../../Tempo/index.md)**, **[OpenTelemetry](../../OpenTelemetry/opentelemetry_overview.md)**.

Подробнее: **[Трассировки: детали](./traces_deep_dive.md)**.

### 4. Профилирование (Profiling)

**Профилирование** — анализ производительности кода для определения потребления CPU, памяти или времени ожидания (блокировок) конкретными функциями.

**Назначение:** оптимизация «горячих» участков кода, снижение затрат на инфраструктуру.

**Continuous Profiling:** Постоянный сбор профилей в Production с минимальным оверхедом. Позволяет увидеть «Flame Graph» приложения в любой момент времени.

**Инструменты:** **Pyroscope** (интегрирован в Grafana), **Parca**.

**Технология eBPF:** Позволяет собирать профили на уровне ядра без инструментирования кода. Подробнее: [**eBPF — виртуальная машина ядра**](../../Linux/Core/kernel/ebpf.md).

Подробнее: **[Профилирование: детали](./profiling_deep_dive.md)**.

## Практический сценарий: Корреляция сигналов

Современная система наблюдаемости строится на базе **OpenTelemetry (OTel)** — унифицированного стандарта для сбора всех типов сигналов.

### Алгоритм расследования инцидента

| Этап | Сигнал | Действие | Механизм связи |
| :--- | :--- | :--- | :--- |
| **1. Обнаружение** | **Метрики** | Видим всплеск Latency на графике в Grafana. | **Exemplars** (точки на графике) |
| **2. Локализация** | **Трассировки** | Кликаем на точку (Exemplar) → открывается Трейс с этим `trace_id`. Видим медленный спан в БД. | **Derived Fields** в логах |
| **3. Контекст** | **Логи** | Прямо из трейса переходим к логам сервиса за это время по `trace_id`. Видим ошибку таймаута. | — |
| **4. Анализ кода** | **Профили** | Если причина в коде — открываем профиль за этот период. Видим функцию, которая «съела» CPU. | **Span-to-Profile** |

**Принципы интеграции:**
- **Единый стандарт:** Использование OpenTelemetry для всех сигналов.
- **Семантические конвенции:** Одинаковые имена атрибутов (`service.name`, `instance.id`) во всех системах.
- **Единый UI:** Grafana как "зонтичный" интерфейс для коррелированных данных.
