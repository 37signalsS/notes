# Four Pillars of Observability

## Определения

**Четыре столпа Observability** — фундаментальные концепции наблюдаемости распределённых систем, включающие четыре типа телеметрических данных:

1. **Логи (Logs)** — неизменяемые записи о событиях
2. **Метрики (Metrics)** — числовые временные ряды
3. **Трассировки (Traces)** — путь запроса через систему
4. **Профилирование (Profiling)** — анализ потребления ресурсов

**Ключевой принцип:** ценность представляет не просто сбор данных, а их **взаимосвязь и корреляция**. Возможность перехода от аномалии в метриках к логам и трассировкам позволяет быстро находить корневые причины проблем.

**См. также:** [Определения Observability](./observability_definitions.md) — базовые понятия мониторинга и наблюдаемости.

## Базовые концепции

### 1. Логи (Logs)

**Логи** — неизменяемые, упорядоченные по времени записи о событиях в системе с временной меткой и контекстом.

**Назначение:** детальный анализ инцидентов, отладка, аудит безопасности.

**Характеристики:**

| Характеристика | Описание |
| :--- | :--- |
| **Точность** | Сбор на каждое событие — полная детализация до единичного запроса |
| **Пропорциональность** | Трафик логов пропорционален трафику приложения |
| **Структура** | Часто не структурированы, сложны для парсинга и индексации |
| **Избыточность** | Много лишних данных, ухудшает обработку и агрегацию |
| **Масштабируемость** | Плохо масштабируется из-за объёма и стоимости обработки |

**Подход:** «Пишем всё, потом думаем» — ценой трафика получаем полную детализацию.

**Инструменты:** **[Loki](../../../Loki/loki_overview.md)**, **Elasticsearch**, **[Vector](../../../Vector/vector_overview.md)**, **Fluent Bit**.

**Важно:** логи должны быть структурированными (JSON) и содержать `trace_id` для корреляции с трассировками. Подробнее: **[Логи: детали](./logs_deep_dive.md)**.

### 2. Метрики (Metrics)

**Метрики** — числовые значения, измеряемые через интервалы времени (временные ряды), агрегирующие информацию о поведении системы.

**Назначение:** мониторинг производительности, обнаружение аномалий, алертинг, анализ трендов.

**Типы метрик (Prometheus):**

| Тип | Описание | Примеры |
| :--- | :--- | :--- |
| **Counter** | Монотонно растущее значение (только увеличение или сброс до 0) | Запросы, ошибки, байты |
| **Gauge** | Значение может увеличиваться и уменьшаться | Память, температура, задержки |
| **Histogram** | Распределение значений по бакетам, вычисление перцентилей | Время ответа, размер ответов |
| **Summary** | Перцентили вычисляются на клиенте | Длительность операций |

**Характеристики:**

| Характеристика | Описание |
| :--- | :--- |
| **Общая картина** | Агрегированные данные, выжимка без деталей |
| **Масштабируемость** | Хорошо масштабируется, быстрая реакция на алерты |
| **Детализация** | Низкая — для деталей нужно добавлять метрики |
| **Трафик** | Зависит от количества метрик, а не от трафика приложения |
| **Минимализм** | Пишем только необходимое для снижения нагрузки |

**Подход:** «Думаем и пишем только что надо» — ценой потери деталей получаем эффективность.

**Инструменты:** **[Prometheus](../../../Prometheus/overview.md)**, **[VictoriaMetrics](../../../VictoriaMetrics/overview.md)**, **Grafana Mimir**, **Thanos**. Подробнее: **[Метрики: детали](./metrics_deep_dive.md)**.

### 3. Трассировки (Traces)

**Трассировка** — способ отслеживания полного пути выполнения запроса через все компоненты распределённой системы.

**Назначение:** анализ производительности в микросервисах, выявление узких мест (bottlenecks), понимание зависимостей между сервисами.

**Основные компоненты:**

| Компонент | Описание |
| :--- | :--- |
| **Trace** | Весь путь одного запроса, уникально идентифицируется `TraceID` |
| **Span** | Отдельная операция внутри трейса (HTTP-вызов, запрос к БД), имеет `SpanID` |
| **Trace Context** | Механизм передачи контекста между сервисами (W3C `traceparent` заголовок) |

**Сэмплирование (Sampling):** сбор данных для доли запросов (например, 1% или только ошибки) для снижения нагрузки.

**Инструменты:** **Jaeger**, **Zipkin**, **[Grafana Tempo](../../../Tempo/index.md)**, **[OpenTelemetry](../../../OpenTelemetry/opentelemetry_overview.md)**. Подробнее: **[Трассировки: детали](./traces_deep_dive.md)**.

**Важно:** корреляция трассировок с логами через `trace_id` — краеугольный камень observability-платформы.

### 4. Профилирование (Profiling)

**Профилирование** — динамический анализ производительности программ для получения детальной информации о потреблении ресурсов (CPU, память, I/O).

**Назначение:** выявление узких мест в коде, оптимизация ресурсов, отладка производительности.

**Типы профилирования:**

| Тип | Описание |
| :--- | :--- |
| **On-demand** | Запускается вручную на короткие периоды для исследования проблемы |
| **Continuous** | Постоянный сбор в продакшене для отслеживания регрессий и оптимизации |

**Continuous Profiling** — «секретный навык» компаний высшего эшелона (Авито, Ozon, Wildberries, Rambler, Yandex). Позволяет отвечать на вопрос «почему система работает медленно» с детализацией до функции или строки кода.

**Визуализация:** Flame Graphs (графы пламени).

**Инструменты:** **Pyroscope**, **Periscope** (на базе Grafana).

**eBPF (extended Berkeley Packet Filter):** технология для глубокого анализа на уровне ядра без изменения кода приложения. Позволяет строить Flame Graphs на основе системных вызовов. Подробнее: **[Непрерывное профилирование](../../../continuous_profiling.md)**.

## Практический сценарий: Корреляция данных

### Пример работы с инцидентом

**Сценарий:** Пользователи жалуются на замедление загрузки страниц интернет-магазина.

| Шаг | Действие | Инструмент |
| :--- | :--- | :--- |
| **1** | Обнаружение аномалии в метриках задержки (99-й перцентиль) | Grafana + Prometheus |
| **2** | Определение затронутых сервисов через дашборд | Grafana |
| **3** | Переход к трассировкам для анализа пути запроса | Tempo/Jaeger |
| **4** | Выявление узкого места (медленный вызов БД или внешнего API) | Span-анализ |
| **5** | Поиск логов по `trace_id` для детального анализа | Loki/Elasticsearch |
| **6** | Профилирование проблемного сервиса для поиска причины | Pyroscope |

### Принципы интеграции

1. **Единый контекст:** все сигналы связываются через общие идентификаторы (`trace_id`, `service_name`, `instance_id`)
2. **Двусторонний переход:** от метрик → к логам/трассировкам и обратно
3. **Автоматическая корреляция:** дашборды Grafana показывают связанные данные из разных источников

## Additional Information

### Сравнительная таблица столпов

| Критерий | Логи | Метрики | Трассировки | Профилирование |
| :--- | :--- | :--- | :--- | :--- |
| **Детализация** | Очень высокая (каждое событие) | Низкая (агрегация) | Высокая (путь запроса) | Очень высокая (до функции) |
| **Стоимость хранения** | Высокая | Низкая | Средняя | Средняя |
| **Влияние на приложение** | Среднее | Минимальное | Среднее | Зависит от типа |
| **Основное применение** | Отладка, аудит | Мониторинг, алертинг | Анализ зависимостей | Оптимизация кода |
| **Масштабируемость** | Низкая | Высокая | Средняя | Средняя |
