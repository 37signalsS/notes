# Четыре столпа Observability

## Определения

**Четыре столпа Observability** -- фундаментальная концепция наблюдаемости распределённых систем, объединяющая четыре типа телеметрических данных (сигналов) для получения полной картины состояния системы:

1.  **Логи (Logs)** -- записи об атомарных событиях.
2.  **Метрики (Metrics)** -- агрегированные числовые показатели (временные ряды).
3.  **Трассировки (Traces)** -- путь запроса через цепочку микросервисов.
4.  **Профилирование (Profiling)** -- детализация потребления ресурсов кодом в рантайме.

**Ключевой принцип:** Наблюдаемость (Observability) -- это не сумма инструментов, а **возможность корреляции** между ними. Эффективная система позволяет мгновенно перейти от аномалии в метрике к соответствующему трейсу, а от него -- к конкретным логам и профилю функции. В 2026 году основой этой интеграции является стандарт **OpenTelemetry (OTel)** и протокол **OTLP**.

**Observability 2.0** -- подход, при котором сигналы телеметрии связаны через единый `trace_id`, а не собираются изолированно. Каждая метрика может содержать **Exemplar** (ссылку на трейс), каждый лог -- `trace_id`/`span_id`, каждый профиль -- привязку к спану. Это позволяет ответить на любой вопрос о системе без предварительных гипотез.

**См. также:** [Определения Observability](./observability_definitions.md) -- базовые понятия мониторинга и наблюдаемости. [Концепции SRE: SLA, SLO, SLI](../sre_concepts_main.md) -- методология измерения надежности.

## Базовые концепции

### 1. Логи (Logs)

**Логи** -- неизменяемые, упорядоченные по времени записи о событиях с временной меткой и контекстом.

**Назначение:** детальный анализ инцидентов, аудит безопасности, расследование постфактум (forensics).

**Характеристики 2026:**
- **Структура:** Исключительно **JSON** или **OTLP**. Текстовые логи без структуры (Plain Text) считаются устаревшими из-за сложности парсинга.
- **Log Bridge API:** Современные SDK (Java, Python) не требуют замены логгера, а используют "мост", который автоматически добавляет `trace_id` и `span_id` ко всем записям.
- **Эффективность:** Использование **[Loki](../../Loki/loki_overview.md)** позволяет хранить петабайты логов без полной индексации текста, ориентируясь на метаданные (лейблы).
- **Structured Metadata (Loki 3.x):** Механизм прикрепления контекста к строкам логов без создания новых лейблов. Решает проблему взрыва кардинальности: уникальные значения (`session_id`, `trace_id`, `user_id`) хранятся как метаданные, а не как лейблы.

**Пример структурированного лога:**

```json
{
  "timestamp": "2026-08-27T14:32:01.123Z",
  "level": "error",
  "service": "billing-api",
  "trace_id": "abc123def45678901234567890123456",
  "span_id": "7890fedcba98765",
  "method": "POST",
  "path": "/v1/billing/charge",
  "status": 500,
  "error": "connection refused to postgres:5432",
  "duration_ms": 2340,
  "user_id": "u-12345"
}
```

**Когда использовать логи:**
- Расследование конкретного инцидента (что произошло и почему).
- Аудит безопасности и compliance.
- Отладка ошибок, не воспроизводимых через метрики.
- Построение SLI на основе лог-метрик (доля ошибок в логах).

**Подробнее:** **[Логи: детали](./logs_deep_dive.md)**.

### 2. Метрики (Metrics)

**Метрики** -- числовые значения, агрегирующие информацию о поведении системы через равные интервалы времени.

**Назначение:** мониторинг производительности в реальном времени, алертинг на базе SLO, анализ трендов.

**Характеристики 2026:**
- **Native Histograms:** Стандарт Prometheus 3.x и VictoriaMetrics. Позволяют собирать высокоточные перцентили (p99, p99.9) с минимальной кардинальностью. Все бакеты хранятся в одном временном ряду вместо десятков `_bucket` метрик.
- **OTLP/Arrow:** Метрики передаются в сжатом колончатом формате, что снижает нагрузку на сеть в 10 раз по сравнению со старым Protobuf.
- **Exemplars:** Каждая точка на графике метрики может содержать ссылку на конкретный `trace_id`, вызвавший всплеск. Кликабельные точки в Grafana мгновенно открывают трейс.

**Типы метрик:**

| Тип | Описание | Когда использовать |
| :--- | :--- | :--- |
| **Counter** | Значение только растёт (счётчик). | Подсчёт событий: запросы, ошибки. Используется с `rate()`. |
| **Gauge** | Текущее значение ("термометр"). | Использование RAM, размер очереди, температура. |
| **Histogram** | Распределение по бакетам. | Латентность, размеры запросов. |
| **Native Histogram** | Экспоненциальные бакеты (v3.0+). | **Стандарт 2026.** Точные перцентили без ручной настройки. |
| **Summary** | Квантили на стороне клиента. | Не агрегируется между инстансами. Используйте Native Histogram. |

**Пример PromQL-запросов:**

```promql
# Rate ошибок за 5 минут (Counter)
sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))

# P99 латентность через Native Histogram (Prometheus 3.x)
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))

# Аномалия: отклонение от baseline через 2sigma
abs(avg_over_time(http_requests_total[1h]) - avg_over_time(http_requests_total[1h] offset 1d)) > 2 * stddev_over_time(http_requests_total[1h] offset 1d)
```

**Когда использовать метрики:**
- Проактивный мониторинг и алертинг (что происходит прямо сейчас).
- Анализ трендов и прогнозирование (когда закончится бюджет ошибок).
- SLI/SLO -- метрики являются основой для измерения надежности.
- Дашборды для понимания общего состояния системы.

**Подробнее:** **[Метрики: детали](./metrics_deep_dive.md)**.

### 3. Трассировки (Traces)

**Трассировка** -- отслеживание пути выполнения запроса через все компоненты распределённой системы.

**Назначение:** выявление задержек в микросервисах, анализ зависимостей, поиск "затыков" в каскадных вызовах.

**Характеристики 2026:**
- **W3C Trace Context:** Стандарт де-факто (заголовок `traceparent`), обеспечивающий совместимость между Envoy, Istio, Java-сервисами и сторонними SaaS.
- **Span Links:** Механизм связывания независимых транзакций (например, продюсера и консьюмера в Kafka). В отличие от parent-child, Span Links сохраняют причинно-следственную связь при асинхронной обработке.
- **Tail-based Sampling:** Решение о сохранении трейса принимается *после* его завершения. Это позволяет сохранять 100% ошибок, сэмплируя "здоровый" трафик до 0.1%.

**Анатомия трассировки:**

```
Trace ID: abc123def45678901234567890123456
│
├─ Span: POST /api/checkout (250ms) — Server
│  ├─ Span: validate-cart (12ms) — Internal
│  ├─ Span: SELECT * FROM inventory (85ms) — Client (DB)
│  ├─ Span: POST /billing/charge (140ms) — Client
│  │  └─ Span: INSERT INTO transactions (35ms) — Client (DB)
│  └─ Span: publish-event Kafka (8ms) — Producer
```

**Когда использовать трассировки:**
- Диагностика проблем в микросервисных архитектурах (где именно тормозит).
- Анализ каскадных отказов и long tail latency.
- Построение топологии сервисов (service map).
- Корреляция с метриками через Exemplars (переход от графика p99 к конкретному трейсу).

**Подробнее:** **[Трассировки: детали](./traces_deep_dive.md)**.

### 4. Профилирование (Profiling)

**Профилирование** -- анализ производительности кода для определения потребления CPU, памяти или времени ожидания (блокировок) конкретными функциями.

**Назначение:** оптимизация "горячих" участков кода (Hotspots), снижение затрат на ресурсы (FinOps).

**Характеристики 2026:**
- **Continuous Profiling:** Постоянный сбор профилей в Production с оверхедом <1% (через eBPF или нативные механизмы рантайма).
- **Span-to-Profile:** Прямая связь между конкретным спаном в трейсе и снимком CPU/Memory этого же процесса в этот же момент времени.
- **eBPF-инструментация:** Сбор данных без изменения кода и sidecar-контейнеров. Параллельный сбор профилей всех процессов на ноде без интеграции в каждый сервис.

**Типы профилей:**

| Профиль | Что измеряет | Когда использовать |
| :--- | :--- | :--- |
| **CPU Time** | Время процессора в функции. | Оптимизация вычислений, парсинга, сериализации. |
| **Wall-clock Time** | Общее время (включая I/O, сеть). | Поиск задержек при работе с БД, внешними API. |
| **Heap Memory** | Объекты в куче (in-use). | Поиск утечек памяти и неэффективных аллокаций. |
| **Allocations** | Все выделения памяти. | Снижение нагрузки на GC, уменьшение фрагментации. |
| **Contention** | Ожидание блокировок (mutex). | Анализ проблем многопоточности. |

**Когда использовать профилирование:**
- Оптимизация производительности при высоком потреблении CPU.
- Поиск утечек памяти, не выявляемых через метрики.
- Снижение затрат на инфраструктуру за счёт оптимизации горячих путей.
- Дополнение трассировок: "где задержка" (trace) + "почему код тормозит" (profile).

**Подробнее:** **[Профилирование: детали](./profiling_deep_dive.md)**.

### Рекомендации по началу работы

1. **Метрики** -- начните всегда. Они дают мгновенную обратную связь и алертинг.
2. **Логи** -- добавьте сразу. Структурированные логи с `trace_id` обеспечивают детализацию.
3. **Трассировки** -- вводите по мере роста числа сервисов (от 3-5 микросервисов).
4. **Профилирование** -- добавляйте при необходимости оптимизации или при высоких затратах на ресурсы.

## Стоимость и накладные расходы

| Критерий | Логи | Метрики | Трассировки | Профили |
| :--- | :--- | :--- | :--- | :--- |
| **Объём данных** | Очень высокий (GB/час на ноду) | Низкий (KB/час) | Средний (MB/час) | Средний (MB/час) |
| **Хранилище** | HDD/SSD (Loki, Elasticsearch) | TSDB (Prometheus, VictoriaMetrics) | TSDB (Tempo, Jaeger) | Object Storage (Pyroscope) |
| **Retention** | 7-30 дней (логи дороги) | 30-90 дней (метрики компактны) | 7-30 дней | 7-14 дней |
| **CPU overhead** | Низкий (парсинг JSON) | Минимальный (счётчики) | Средний (сэмплирование, baggage) | Низкий (<1% через eBPF) |
| **Сетевой overhead** | Высокий (сырые логи) | Низкий (сжатые ряды) | Средний (取决于 sampling rate) | Низкий (профили по запросу) |
| **Стоимость анализа** | Высокая (полнотекстовый поиск) | Низкая (агрегация на ingestion) | Средняя (поиск по trace_id) | Низкая ( Flame Graph) |

**Оптимизация затрат:**
- **Логи:** Используйте采样 (sampling) для debug-логов, храните только ошибки в долгосрочном хранилище.
- **Метрики:** Native Histograms снижают кардинальность и объём хранилища до 40%.
- **Трассировки:** Tail-based sampling сохраняет 100% ошибок, сэмплируя здоровый трафик.
- **Профили:** Continuous profiling с eBPF имеет минимальный overhead, но требуетretain профилей в Object Storage.

## Практический сценарий: Корреляция сигналов

Современная наблюдаемость -- это способность быстро переключаться между слоями данных.

### Алгоритм расследования инцидента

| Этап | Сигнал | Действие | Механизм связи (2026) |
| :--- | :--- | :--- | :--- |
| **1. Обнаружение** | **Метрики** | Видим всплеск Latency или Error Rate на графике. | **Exemplars** (кликабельные точки) |
| **2. Локализация** | **Трассировки** | Кликаем на Exemplar -> открывается Трейс. Видим, что 80% времени занял вызов БД. | **Resource Attributes** (общие лейблы) |
| **3. Контекст** | **Логи** | Прямо из медленного спана переходим к логам сервиса по `trace_id`. Видим SQL-ошибку. | **Log Bridge** / **Derived Fields** |
| **4. Анализ кода** | **Профили** | Если причина в потреблении CPU (например, парсинг) -- открываем профиль. | **Span-to-Profile** |

### Корреляция через Exemplars

**Exemplar** -- это точка-метка на временном ряде метрики, хранящая ссылку на конкретный `trace_id`. В Grafana кликабельные точки на графике задержек мгновенно открывают трейс в Tempo/Jaeger.

**Как это работает:**
1. Приложение передаёт метрику с `trace_id` как атрибутом (через OTel SDK или Prometheus client).
2. Prometheus хранит `trace_id` как **Exemplar**, а не как лейбл (это критично -- `trace_id` высококардинален).
3. На графике в Grafana отображаются маленькие кружки -- кликабельные Exemplars.
4. Клик по точке -> переход к трейсу -> анализ спана -> переход к логам.

**Пример PromQL с Exemplars:**
```promql
# Метрика с привязкой к трейсу
http_request_duration_seconds_bucket{le="0.5"} # 0.95=1
# Exemplar: trace_id="abc123..." (хранится отдельно от лейблов)
```

### Корреляция через trace_id

Все сигналы связаны через единый `trace_id`:
- **Метрики -> Трассировки:** Через Exemplars.
- **Трассировки -> Логи:** Через Derived Fields в Grafana Tempo (автоматический переход по `trace_id`).
- **Трассировки -> Профили:** Через Span-to-Profile (Pyroscope/Parca).
- **Логи -> Трассировки:** Через `trace_id` в JSON-логах (Grafana автоматически создаёт ссылки).

**Принципы интеграции:**
- **Единый стандарт:** Использование OpenTelemetry для всех сигналов.
- **Семантические конвенции:** Одинаковые имена атрибутов (`service.name`, `k8s.pod.name`) во всех системах.
- **Единый UI:** Grafana как "зонтичный" интерфейс для коррелированных данных.

## Модель зрелости Observability

### Уровень 0: Базовый мониторинг
- **Что есть:** Метрики CPU/RAM/Disk на нодах, uptime-проверки.
- **Что нет:** Логи не централизованы, алерты на ресурсы (не на SLO).
- **Действия:** Настройте структурированное логирование, включите `trace_id` в логи.

### Уровень 1: Метрики + Логи
- **Что есть:** Метрики сервисов (RED), централизованные логи (Loki), базовые алерты.
- **Что нет:** Нет трассировок, нет профилирования, корреляция через `trace_id`.
- **Действия:** Внедрите OpenTelemetry SDK, настройте Exemplars в Prometheus.

### Уровень 2: Полная корреляция
- **Что есть:** Метрики + Логи + Трассировки, связаны через `trace_id`. Tail-based sampling.
- **Что нет:** Нет профилирования, нет Span-to-Profile.
- **Действия:** Добавьте Continuous Profiling (Pyroscope/Parca), настройте Span-to-Profile.

### Уровень 3: Observability 2.0
- **Что есть:** Все 4 сигнала связаны. Автоматическая корреляция. SLO-based alerting.
- **Что нет:** -- (полная наблюдаемость).
- **Действия:** Оптимизируйте затраты, автоматизируйте Runbooks, настройте AIOps.

## Диагностика и устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Разорванная корреляция** | Разные форматы `trace_id` или отсутствие передачи заголовков (Propagators). | Принудительно использовать **W3C Trace Context**. Проверить наличие инъекции заголовков в Load Balancer / Ingress. |
| **Взрыв кардинальности** | Попытка добавить `user_id` или `order_id` в лейблы метрик. | Использовать трассировки для данных с высокой кардинальностью. Удалить "тяжелые" лейблы через `relabel_configs`. |
| **Отсутствие Exemplars** | Несоответствие форматов между приложением и Prometheus. | Убедиться, что приложение пишет Exemplars в формате OpenMetrics. Включить `native_histograms` в Prometheus. |
| **Log Loss (Пропуски)** | Переполнение буфера `stdout` или агента сбора. | Увеличить лимиты памяти агента (Alloy/OTel). Использовать дисковую буферизацию. |
| **Высокий overhead трассировок** | 100% сэмплирование в production. | Включить tail-based sampling: сохранять 100% ошибок, сэмплировать здоровый трафик до 0.1-1%. |
| **Профили не показывают проблему** | Слишком низкая частота сбора (например, 1 раз в минуту). | Увеличить частоту до 10-30 секунд или использовать eBPF-based профилирование. |
| **Логи не содержат trace_id** | Приложение не использует Log Bridge API. | Интегрировать OTel Log Bridge (Java: Log4j Appender, Python: logging handler). |
| **Grafana не показывает Exemplars** | `exemplar-storage` не включен в Prometheus. | Добавить `--enable-feature=exemplar-storage` в Prometheus v2.x, или использовать Prometheus v3.x (включено по умолчанию). |
