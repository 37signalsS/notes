# Политики вытеснения в кэше

## Определения

**Политика вытеснения (Eviction Policy)** — это алгоритм, который определяет, какие записи должны быть удалены из кэша для освобождения места под новые данные при достижении лимита памяти. Правильный выбор политики напрямую влияет на **Hit Rate** (коэффициент попаданий) и производительность системы под нагрузкой.

Для понимания общего контекста работы кэша рекомендуется ознакомиться с [обзором кэширования](./caching_overview.md).

## Основные концепции

### LRU (Least Recently Used — Наиболее давно использованный)

*   **Принцип:** Вытесняется элемент, к которому не обращались дольше всего. Основан на гипотезе о временной локальности данных.
*   **Преимущества:** Эффективен для большинства типовых нагрузок.
*   **Недостатки:** Уязвим для «сканирующих» запросов (однократный полный обход данных вытесняет «горячие» записи).

### LFU (Least Frequently Used — Наименее часто используемый)

*   **Принцип:** Вытесняется элемент с наименьшим количеством обращений.
*   **Преимущества:** Устойчив к случайным всплескам и сканированию данных; защищает стабильно популярные записи.
*   **Недостатки:** Требует больше ресурсов для хранения счетчиков; медленно адаптируется к резкой смене популярности (старые популярные ключи долго остаются в кэше).

### FIFO (First-In, First-Out — Первым пришел, первым ушел)

*   **Принцип:** Удаляются самые старые записи по времени их добавления в кэш. Реализует простую очередь.
*   **Преимущества:** Минимальные накладные расходы на управление.
*   **Недостатки:** Не учитывает популярность данных, что приводит к низкой эффективности при неравномерном доступе.

### Random (Случайное вытеснение)

*   **Принцип:** Выбирается случайный элемент для удаления.
*   **Преимущества:** Отсутствие накладных расходов на отслеживание порядка или частоты.
*   **Применение:** Используется как база для сравнения или в условиях, когда паттерн доступа к данным абсолютно случаен.

### TTL-based (Вытеснение по сроку жизни)

*   **Принцип:** Вытесняются ключи с наименьшим оставшимся временем жизни (Time-To-Live).
*   **Применение:** Полезно, когда в кэше хранятся данные с разной степенью актуальности.

## Сравнение алгоритмов

| Критерий | LRU | LFU | FIFO | Random |
| :--- | :--- | :--- | :--- | :--- |
| **Адаптация к трендам** | Быстрая | Средняя | Отсутствует | Отсутствует |
| **Устойчивость к сканам**| Средняя | Высокая | Низкая | Высокая |
| **Накладные расходы** | Низкие | Умеренные | Минимальные | Нулевые |
| **Основной сценарий** | Общие нагрузки | Стабильные топы | Потоковая обработка | Тестирование |

## Практические сценарии

### Конфигурация в Redis

Redis предоставляет набор политик через параметр `maxmemory-policy`, разделяя их по области действия: `allkeys` (все ключи) и `volatile` (только ключи с установленным TTL).

1.  **`allkeys-lru`:** Аппроксимированный LRU для всех ключей. Рекомендуется по умолчанию.
2.  **`allkeys-lfu`:** Вытеснение по частоте использования для всего набора данных.
3.  **`volatile-ttl`:** Удаление ключей, у которых срок жизни истекает раньше всего.
4.  **`noeviction`:** Возврат ошибки при попытке записи в полный кэш. Используется, когда удаление данных недопустимо (например, Redis как БД).

**Пример настройки:**
```sh
# Установка лимита памяти 4 ГБ
CONFIG SET maxmemory 4gb
# Установка политики LFU для защиты популярных данных
CONFIG SET maxmemory-policy allkeys-lfu
```

### Конфигурация в Memcached

Memcached реализует LRU в рамках каждого **Slab Class** (сегмента памяти для объектов схожего размера).

```bash
# Запуск с поддержкой фонового обслуживания LRU (lru_maintainer)
memcached -m 1024 -o lru_maintainer,lru_crawler
```

### Современные подходы

В современных высокопроизводительных библиотеках (например, Caffeine для Java или Ristretto для Go) используются комбинированные алгоритмы:
*   **TinyLFU / W-TinyLFU:** Объединяет преимущества LRU и LFU, обеспечивая высокую эффективность при минимальных затратах памяти на хранение метаданных.
*   **ARC (Adaptive Replacement Cache):** Саморегулирующийся алгоритм, который динамически меняет баланс между LRU и LFU в зависимости от текущей нагрузки.

## Дополнительная информация

**Критерии выбора:**
*   Если данные имеют «срок годности» и их популярность быстро затухает — используйте **LRU**.
*   Если есть ядро данных, которое всегда должно быть в кэше из-за высокой частоты запросов — используйте **LFU**.
*   Для критических систем всегда отслеживайте метрику `evictions` в мониторинге: резкий рост вытеснений при стабильном трафике сигнализирует о нехватке памяти.
