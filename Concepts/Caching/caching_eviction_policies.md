# Политики вытеснения в кеше (Eviction Policies)

Политика вытеснения определяет, какие ключи удаляются из кеша при достижении лимита памяти. Выбор алгоритма влияет на коэффициент попаданий (hit rate), устойчивость к «шумным» запросам и предсказуемость задержек.

## LRU (Least Recently Used)

**Идея:** вытесняется самый давно не использованный ключ. Предполагается, что данные, использованные недавно, с большей вероятностью понадобятся снова (локальность по времени).

**Особенности:**
*   Хорошо работает при ярко выраженной временной локальности.
*   Подвержен «сканирующим» нагрузкам (однократные чтения большого множества ключей могут вытеснить полезные).

### Реализация
*   **Redis:** Применяется **приближённый LRU** с выборкой по образцам (`maxmemory-samples`) для снижения накладных расходов. Режимы: `allkeys-lru`, `volatile-lru` (только для ключей с TTL).
*   **Memcached:** Базовый механизм — **сегментированный LRU** в рамках «slab»-классов, с обслуживающими потоками `lru_maintainer` и `lru_crawler`.

## LFU (Least Frequently Used)

**Идея:** вытесняется ключ с наименьшей частотой обращений. Делает ставку на стабильную популярность данных.

**Особенности:**
*   Устойчив к сканирующим шаблонам: единичные обращения не повышают «ценность» ключей.
*   Медленнее адаптируется к внезапным изменениям популярности, чем LRU.

### Реализация
*   **Redis:** Используется компактный логарифмический счётчик с настраиваемым распадом (`lfu-log-factor`, `lfu-decay-time`). Режимы: `allkeys-lfu`, `volatile-lfu`.
*   **Memcached:** Отдельной политики LFU нет.

## FIFO (First-In, First-Out)

**Идея:** вытесняется самый «старый» по времени вставки ключ. Реализует простую очередь.

**Особенности:**
*   Проста и предсказуема в реализации.
*   Не учитывает ни недавнюю активность, ни частоту; склонна к «засорению» редко используемыми данными.
*   Подходит для потоков с равномерной полезностью и фиксированным «окном» недавних элементов (например, буферов).

### Реализация
*   Ни в Redis, ни в Memcached **нет глобальной FIFO-политики** вытеснения при заполнении памяти. Поведение FIFO может быть реализовано на уровне структур данных (например, списки в Redis) или через прикладную логику с TTL.

## Сравнение

| Критерий | LRU | LFU | FIFO |
| :--- | :--- | :--- | :--- |
| **Адаптация к трендам** | Быстрая | Средняя | Отсутствует |
| **Устойчивость к сканам**| Средняя | Высокая | Низкая |
| **Накладные расходы** | Низкие (аппроксимации) | Умеренные (счётчики, распад) | Низкие |
| **Применимость в Redis** | Полная поддержка | Полная поддержка | Нет как `maxmemory-policy` |
| **Применимость в Memcached**| Стандартная | Нет | Нет |

## Примеры настройки

### Redis
Переключение на LFU и настройка параметров:
```
CONFIG SET maxmemory 2gb
CONFIG SET maxmemory-policy allkeys-lfu
CONFIG SET lfu-log-factor 10
CONFIG SET lfu-decay-time 120
CONFIG SET maxmemory-samples 10
```

Переключение на LRU с выборкой из 5 ключей:
```
CONFIG SET maxmemory-policy allkeys-lru
CONFIG SET maxmemory-samples 5
```

### Memcached
Включение обслуживания LRU и ползучей очистки протухших ключей:
```bash
memcached -m 2048 -o lru_maintainer,lru_crawler,slab_automove
```

**Вывод:** Выбор политики следует базировать на профиле нагрузки: яркая временная локальность — **LRU**; стабильная популярность и защита от сканирования — **LFU**.
