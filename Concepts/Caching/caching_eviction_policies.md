# Политики вытеснения в кэше (Eviction Policies)

## Определения

**Политика вытеснения** — это алгоритм, который определяет, какие данные следует удалить из кэша, когда в нем заканчивается свободное место. Правильный выбор политики напрямую влияет на эффективность кэша (hit rate).

Для понимания общего контекста работы кэша рекомендуется ознакомиться с [обзором кэширования](./caching_overview.md).

## Основные концепции (Алгоритмы)

### LRU (Least Recently Used — Наиболее давно использованный)

* **Принцип:** Вытесняется элемент, к которому дольше всего не обращались. Основан на гипотезе о *временной локальности* данных: если к данным обращались недавно, скорее всего, к ним обратятся снова.
* **Преимущества:** Хорошо работает для большинства общих нагрузок.
* **Недостатки:** Уязвим для "сканирующих" запросов, когда один долгий обход данных может вытеснить все полезные "горячие" записи.

### LFU (Least Frequently Used — Наименее часто используемый)

* **Принцип:** Вытесняется элемент, к которому обращались реже всего. Основан на гипотезе, что есть стабильно популярные и непопулярные данные.
* **Преимущества:** Устойчив к сканирующим нагрузкам и случайным всплескам обращений.
* **Недостатки:** Может медленно адаптироваться к изменению популярности данных. Требует хранения счетчика обращений для каждого элемента.

### FIFO (First-In, First-Out — Первым пришел, первым ушел)

* **Принцип:** Вытесняется элемент, который был добавлен в кэш раньше всех. Реализует простую очередь.
* **Преимущества:** Очень прост в реализации и имеет минимальные накладные расходы.
* **Недостатки:** Не учитывает популярность или частоту использования данных, что часто приводит к низкой эффективности.

### Сравнение Алгоритмов

| Критерий | LRU | LFU | FIFO |
| :--- | :--- | :--- | :--- |
| **Адаптация к трендам** | Быстрая | Средняя | Отсутствует |
| **Устойчивость к сканам**| Средняя | Высокая | Низкая |
| **Накладные расходы** | Низкие (особенно в аппроксимациях) | Умеренные (счётчики) | Минимальные |
| **Основной сценарий** | Общие нагрузки, временная локальность | Стабильно популярные данные, защита от сканирования | Простые буферы, потоки данных |

## Практические сценарии

### Настройка в Redis

Redis предоставляет гибкие возможности для настройки политик вытеснения через параметр `maxmemory-policy`.

**Пример 1: Включение LFU**

```sh
# Установить лимит памяти
CONFIG SET maxmemory 2gb
# Установить политику LFU для всех ключей
CONFIG SET maxmemory-policy allkeys-lfu
```

**Пример 2: Включение аппроксимированного LRU**
Redis использует не классический LRU, а его аппроксимацию для экономии ресурсов.

```sh
CONFIG SET maxmemory-policy allkeys-lru
# Установить количество сэмплов для выбора "кандидата" на вытеснение
# Большее значение — точность выше, но и нагрузка больше
CONFIG SET maxmemory-samples 5 
```

### Настройка в Memcached

Memcached по умолчанию использует LRU в рамках каждого `slab class`.

**Пример: Запуск Memcached с настройками LRU**

```bash
# -o lru_maintainer: включает отдельный поток для управления LRU
# -o lru_crawler: включает фоновое удаление просроченных (expired) ключей
memcached -m 2048 -o lru_maintainer,lru_crawler
```

## Дополнительная информация

**Вывод:** выбор политики должен основываться на профиле нагрузки приложения.

* **LRU** — безопасный выбор по умолчанию для большинства систем.
* **LFU** — предпочтителен, когда есть четко выраженные "горячие" данные, которые нужно защитить от вытеснения из-за сканирующих запросов.
* Другие политики, такие как `volatile-ttl` (вытеснение ключей с TTL с наименьшим оставшимся временем жизни), также доступны в Redis и могут быть полезны в специфичных сценариях.
