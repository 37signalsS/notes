# Политики вытеснения в кэше

## Определения

**Политика вытеснения (Eviction Policy)** — это алгоритм, определяющий правила удаления записей из кэша для освобождения места под новые данные при достижении лимита памяти. Правильный выбор политики критичен для поддержания высокого **Hit Rate** (коэффициента попаданий) и минимизации нагрузки на основные хранилища данных.

Для понимания общего контекста работы кэша рекомендуется ознакомиться с [обзором кэширования](./caching_overview.md).

## Основные концепции

### Базовые алгоритмы

#### FIFO (First-In, First-Out)

Удаляются самые старые записи по времени их добавления. Реализуется через простую очередь. Малоэффективен, так как не учитывает частоту или новизну обращений.

#### LRU (Least Recently Used)

Вытесняется элемент, к которому не обращались дольше всего. Основан на временной локальности.
*   **Аппроксимированный LRU:** В системах типа Redis LRU реализуется через сэмплирование (случайный выбор N ключей и удаление «худшего» среди них) для экономии памяти на хранение связных списков.

#### LFU (Least Frequently Used)

Вытесняется элемент с наименьшим количеством обращений.
*   **Проблема:** Старые популярные ключи («зомби») могут долго занимать место.
*   **Оптимизация:** Использование **Count-Min Sketch** для компактного хранения частоты запросов без выделения памяти под полноценные счетчики для каждого ключа.

#### Random (Случайное вытеснение)

Выбирается случайная запись. Не требует метаданных, эффективен при абсолютно непредсказуемом паттерне доступа.

### Продвинутые алгоритмы

#### Segmented LRU (SLRU)

Кэш делится на несколько очередей (обычно HOT, WARM и COLD):
*   Новые данные попадают в COLD или HOT. При повторном обращении данные перемещаются в WARM. Это защищает кэш от «сканирующих» запросов, которые обращаются к данным один раз.
*   Широко применяется в **Memcached**.

#### S3-FIFO (Simple Scalable Static-like FIFO)

Современный алгоритм, использующий три очереди:
1.  **Small:** Очередь для новых объектов (FIFO).
2.  **Main:** Основное хранилище (FIFO с битом доступа, как в Clock).
3.  **Ghost:** Очередь для идентификаторов недавно удаленных объектов. Помогает понять, стоит ли перемещать объект в Main при повторном появлении.
*   Часто превосходит LRU по эффективности при меньших накладных расходах на CPU.

## Сравнение политик

| Алгоритм | Учет времени (Recency) | Учет частоты (Frequency) | Сложность | Устойчивость к сканам |
| :--- | :---: | :---: | :---: | :---: |
| **FIFO** | Да (запись) | Нет | Минимальная | Нет |
| **LRU** | Да (чтение) | Нет | Низкая | Средняя |
| **LFU** | Нет | Да | Средняя | Высокая |
| **SLRU** | Да | Частично | Средняя | Высокая |
| **S3-FIFO** | Да | Да | Средняя | Максимальная |

## Практические сценарии

### Конфигурация в Redis

Redis использует сэмплирование для аппроксимации LRU/LFU.

```sh
# Настройка Redis для использования аппроксимированного LRU для всех ключей
CONFIG SET maxmemory 2gb
CONFIG SET maxmemory-policy allkeys-lru
# Точность сэмплирования (5 - стандарт, 10 - близко к честному LRU, но выше CPU)
CONFIG SET maxmemory-samples 5
```

### Конфигурация в Memcached (Segmented LRU)

Memcached разделяет Slab Class на сегменты для защиты «горячих» данных.

```bash
# Запуск Memcached с фоновой очисткой и поддержкой Segmented LRU
memcached -m 1024 -o lru_maintainer,lru_crawler,slab_automove
```

### Современные библиотеки и Java/Go

В высоконагруженных приложениях (например, в API-шлюзах на базе Go или Java) используются:

*   **W-TinyLFU (Window TinyLFU):** Алгоритм, применяемый в библиотеке **Caffeine** (Java).
    *   Использует небольшое окно (Admission Window) для новых данных и основной кэш.
    *   Решение о приеме нового объекта в основной кэш принимается на основе фильтра частоты (TinyLFU), который сравнивает популярность «кандидата» и «жертвы» на вытеснение.
*   **ARC (Adaptive Replacement Cache):**
    *   Автоматически балансирует между двумя очередями: одна для недавно использованных данных (Recency), другая для часто используемых (Frequency).
    *   Динамически подстраивается под тип нагрузки (сканирующая vs точечная).

## Дополнительная информация

### Критерии выбора

1.  **Общие нагрузки:** `allkeys-lru` (Redis) или SLRU (Memcached) являются стандартом де-факто.
2.  **Стабильные "топы" данных:** Если 5% ключей генерируют 90% трафика, используйте `LFU` или `W-TinyLFU`.
3.  **Защита от сканирования:** Если в системе часто проходят фоновые задачи (например, выгрузка всей таблицы), выбирайте `SLRU` или `S3-FIFO`, чтобы сканирование не вымыло «горячие» данные пользователей.

### Мониторинг вытеснения

Резкий рост метрики `evictions` при стабильном трафике почти всегда означает нехватку оперативной памяти или неэффективный выбор TTL.

*   В Redis: `redis-cli info stats | grep evicted_keys`
*   В Memcached: `echo "stats" | nc localhost 11211 | grep evictions`
