# Кэширование: Обзор

## Определения

**Кэширование** — это процесс хранения копий данных в специализированном, более быстром и доступном слое (кэше) для ускорения обработки последующих запросов. Основная цель — радикальное снижение задержки (Latency) и минимизация нагрузки на основной источник данных: базу данных (Database), дисковую подсистему или внешний API.

Использование кэша всегда вводит компромисс между скоростью доступа и гарантией актуальности данных (*Data Freshness*). В распределенных системах это напрямую связано с теоремой CAP (Consistency, Availability, Partition tolerance).

## Основные концепции

### Уровни кэширования

Кэширование пронизывает всю архитектуру современной системы:

1.  **Аппаратный уровень (CPU Cache):**
    *   *L1/L2/L3:* Сверхбыстрая память внутри процессора для хранения инструкций и данных, необходимых для немедленного выполнения.
2.  **Клиентское кэширование (Browser/App Cache):**
    *   Хранение статических ресурсов (CSS, JS, изображения) локально. Управляется через HTTP-заголовки (`Cache-Control`, `ETag`).
3.  **CDN (Content Delivery Network) и Edge:**
    *   Кэширование на границе сети для доставки контента из географически ближайшего узла.
4.  **Прокси-слой (Reverse Proxy / API Gateway):**
    *   Кэширование ответов бэкенда (Nginx, Angie, Varnish).
    *   **AI Gateway:** Кэширование промптов и ответов LLM (Large Language Models) для экономии токенов и снижения задержки.
5.  **Прикладное кэширование (Application Cache):**
    *   *In-memory:* Внутри процесса приложения (HashMap, LRU-библиотеки).
    *   *Distributed Cache:* Внешние системы (Redis, Memcached, Dragonfly), доступные нескольким узлам.
6.  **Кэширование базы данных:**
    *   Buffer Pool (PostgreSQL/MySQL), Materialized Views.

### Ключевые метрики

*   **Hit Ratio (Коэффициент попаданий):** Процент запросов, обслуженных из кэша. Рассчитывается как `Hits / (Hits + Misses)`.
*   **Miss Penalty (Штраф за промах):** Дополнительные затраты времени на получение данных из источника и их запись в кэш.
*   **Eviction Rate (Частота вытеснения):** Количество записей, удаленных из-за нехватки места. Высокий показатель при низком Hit Ratio — сигнал о дефиците памяти.
*   **TTFB (Time to First Byte):** Основной показатель эффективности кэша на уровне сети.

### Жизненный цикл и управление данными

*   **TTL (Time-To-Live):** Время жизни записи. Может быть фиксированным или «скользящим» (продлевается при чтении).
*   **Инвалидация (Invalidation):** Процесс удаления данных при их обновлении в источнике.
*   **Прогрев кэша (Cache Warmup):** Принудительное наполнение кэша популярными данными до начала активного трафика (например, после деплоя или перезагрузки).
*   **Согласованность (Consistency):**
    *   *Eventual Consistency:* Данные в кэше могут временно отличаться от БД.
    *   *Strong Consistency:* Кэш обновляется или инвалидируется атомарно вместе с источником.
*   **[Паттерны кэширования](./caching_patterns.md):** Cache-Aside, Read-Through, Write-Through, Write-Back.
*   **[Политики вытеснения](./caching_eviction_policies.md):** Алгоритмы освобождения места (LRU, LFU, FIFO, ARC).

## Практические сценарии

### Типовые проблемы и стратегии решения

*   **Кассовая давка (Cache Stampede / Thundering Herd):** Множество параллельных запросов пытаются обновить кэш для одного и того же ключа при его истечении (TTL).
    *   *Решение 1 (Mutex/Locking):* Только один поток (запрос) идет в БД для восстановления записи, остальные ждут или кратковременно получают старое значение.
    *   *Решение 2 (Stale-while-revalidate):* Отдача старых данных, пока один фоновый процесс обновляет значение.
    *   *Решение 3 (Поэтапный TTL):* Обновление «горячих» записей до их фактического истечения.
*   **Cache Avalanche (Лавина кэша):** Одновременное истечение TTL у миллионов ключей (например, если они были записаны одновременно при старте системы).
    *   *Решение:* **Джиттер (Jitter / Staggered TTL)** — добавление небольшого случайного смещения к TTL каждой записи, чтобы они не исчезали одновременно.
*   **Cache Penetration (Проникновение):** Запросы к несуществующим данным, нагружающие БД в обход кэша.
    *   *Решение:* **Негативное кэширование** (сохранение факта отсутствия данных с коротким TTL) или использование фильтров Блума.

### Оптимизация хранения и сериализация

Выбор формата данных критичен для CPU и памяти:

| Формат | Скорость | Компактность | Особенности |
| :--- | :--- | :--- | :--- |
| **JSON** | Низкая | Низкая | Читаемость, универсальность. |
| **MessagePack** | Высокая | Высокая | Бинарный формат, не требует схемы. |
| **Protobuf** | Максимальная| Максимальная | Требует `.proto` схему, идеален для gRPC. |

Для больших объектов (более 10 КБ) рекомендуется использовать сжатие (Zstd, LZ4).

## Дополнительная информация

### Мониторинг и эксплуатация

Критически важные параметры для алертинга:
1.  **Memory Usage:** Приближение к лимиту `maxmemory`.
2.  **Hit Rate Stability:** Резкое падение коэффициента попаданий.
3.  **Latency Spikes:** Задержки на стороне самого кэша (например, из-за блокирующих операций в Redis типа `KEYS *`).
4.  **Serialization Overhead:** Нагрузка на CPU приложения при парсинге тяжелых объектов.

**Пример проверки статуса Redis:**
```bash
redis-cli info stats | grep keyspace
# → keyspace_hits:150234, keyspace_misses:4521, avg_ttl:3600000
```
