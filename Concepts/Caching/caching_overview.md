# Кэширование: Обзор

## Определения

**Кэширование** — это процесс хранения копий данных в специализированном, более быстром и доступном слое (кэше) для ускорения обработки последующих запросов. Основная цель — радикальное снижение задержки (Latency) и минимизация нагрузки на основной источник данных: базу данных (Database), дисковую подсистему или внешний API.

Эффективность кэширования базируется на двух фундаментальных принципах **локальности ссылок (Locality of Reference)**:
*   **Временная локальность (Temporal Locality):** Если данные были запрошены один раз, с высокой вероятностью они понадобятся снова в ближайшее время.
*   **Пространственная локальность (Spatial Locality):** Если данные были запрошены, с высокой вероятностью потребуются данные, расположенные рядом (актуально для кэширования дисковых блоков и строк БД).

Использование кэша всегда вводит компромисс между скоростью доступа и гарантией актуальности данных (*Data Freshness*). В распределенных системах это напрямую связано с теоремой CAP (Consistency, Availability, Partition tolerance). Большинство систем кэширования (Redis, Memcached) ориентированы на **AP**, обеспечивая высокую доступность и производительность ценой временной несогласованности (*Eventual Consistency*).

## Основные концепции

### Типы архитектур кэширования

1.  **Локальный кэш (In-process/Local Cache):**
    *   Данные хранятся в оперативной памяти самого приложения.
    *   **Плюсы:** Нулевая сетевая задержка, максимальная скорость.
    *   **Минусы:** Память ограничена процессом, данные теряются при перезагрузке, сложность синхронизации между несколькими экземплярами приложения.
2.  **Распределенный кэш (Distributed Cache):**
    *   Внешняя система (Redis, Dragonfly, Memcached), доступная всем узлам приложения по сети.
    *   **Плюсы:** Общее состояние для всех узлов, независимое масштабирование, сохранение данных при перезагрузке приложения.
    *   **Минусы:** Сетевые задержки (hop), накладные расходы на сериализацию/десериализацию.
3.  **Многоуровневый кэш (Near Cache / L1-L2):**
    *   Комбинация локального кэша (L1) для «горячих» данных и распределенного (L2) для основного объема. L1 инвалидируется через механизм Pub/Sub или короткий TTL.

### Уровни кэширования

Кэширование пронизывает всю архитектуру современной системы:

1.  **Аппаратный уровень (CPU Cache):**
    *   *L1/L2/L3:* Сверхбыстрая память внутри процессора для хранения инструкций и данных, необходимых для немедленного выполнения. Оперирует кэш-линиями (обычно 64 байта).
2.  **Клиентское кэширование (Browser/App Cache):**
    *   Хранение статических ресурсов (CSS, JS, изображения) локально. Управляется через HTTP-заголовки (`Cache-Control`, `ETag`, `Last-Modified`).
3.  **CDN (Content Delivery Network) и Edge:**
    *   Кэширование на границе сети для доставки контента из географически ближайшего узла. Идеально для видео, изображений и статических API-ответов.
4.  **Прокси-слой (Reverse Proxy / API Gateway):**
    *   Кэширование ответов бэкенда (Nginx, Angie, Varnish). Позволяет «срезать» нагрузку до того, как она попадет на сервер приложений.
    *   **AI Gateway:** Кэширование промптов и ответов LLM (Large Language Models) для экономии токенов и снижения задержки. Используется семантическое кэширование (поиск похожих векторов).
5.  **Прикладное кэширование (Application Cache):**
    *   Использование библиотек (Guava, Caffeine для Java) или внешних хранилищ (Redis) непосредственно в бизнес-логике.
6.  **Кэширование базы данных:**
    *   *Internal:* Buffer Pool (PostgreSQL/MySQL), кэш планов выполнения запросов.
    *   *External:* Материализованные представления (Materialized Views) и индексы.

### Ключевые метрики

*   **Hit Ratio (Коэффициент попаданий):** Процент запросов, обслуженных из кэша. Рассчитывается как `Hits / (Hits + Misses)`. Целевой показатель для «горячих» данных — >90%.
*   **Miss Penalty (Штраф за промах):** Дополнительные затраты времени на получение данных из источника и их запись в кэш. Если пенальти слишком высок, кэширование может замедлить систему.
*   **Eviction Rate (Частота вытеснения):** Количество записей, удаленных из-за нехватки места. Высокий показатель при низком Hit Ratio — сигнал о дефиците оперативной памяти или неэффективном TTL.
*   **TTFB (Time to First Byte):** Основной показатель эффективности кэша на уровне сети.
*   **Object Age:** Возраст объекта в кэше. Помогает отслеживать «протухание» данных.

### Жизненный цикл и управление данными

*   **TTL (Time-To-Live):** Время жизни записи. Может быть фиксированным или «скользящим» (продлевается при чтении).
*   **Инвалидация (Invalidation):** Процесс удаления данных при их обновлении в источнике.
*   **Прогрев кэша (Cache Warmup):** Принудительное наполнение кэша популярными данными до начала активного трафика (например, после деплоя или перезагрузки).
*   **Согласованность (Consistency):**
    *   *Eventual Consistency:* Данные в кэше могут временно отличаться от БД.
    *   *Strong Consistency:* Кэш обновляется или инвалидируется атомарно вместе с источником.
*   **[Паттерны кэширования](./caching_patterns.md):** Cache-Aside, Read-Through, Write-Through, Write-Back.
*   **[Политики вытеснения](./caching_eviction_policies.md):** Алгоритмы освобождения места (LRU, LFU, FIFO, ARC).

## Практические сценарии

### Типовые проблемы и стратегии решения

*   **Кассовая давка (Cache Stampede / Thundering Herd):** Множество параллельных запросов пытаются обновить кэш для одного и того же ключа при его истечении (TTL).
    *   *Решение 1 (Mutex/Locking):* Только один поток (запрос) идет в БД для восстановления записи, остальные ждут или кратковременно получают старое значение.
    *   *Решение 2 (Stale-while-revalidate):* Отдача старых данных, пока один фоновый процесс обновляет значение (например, `proxy_cache_use_stale` в Nginx).
    *   *Решение 3 (Поэтапный TTL):* Программное обновление «горячих» записей до их фактического истечения.
*   **Cache Avalanche (Лавина кэша):** Одновременное истечение TTL у миллионов ключей (например, если они были записаны одновременно при старте системы).
    *   *Решение:* **Джиттер (Jitter / Staggered TTL)** — добавление небольшого случайного смещения к TTL каждой записи (например, `TTL = base_ttl + rand(0, 300)`).
*   **Cache Penetration (Проникновение):** Запросы к несуществующим данным, нагружающие БД в обход кэша.
    *   *Решение:* **Негативное кэширование** (сохранение ключа со значением `null` на короткий срок) или использование **фильтров Блума (Bloom Filters)** для быстрой проверки отсутствия ключа без обращения к БД.
*   **Hot Keys (Горячие ключи):** Один или несколько ключей получают непропорционально большую долю трафика, перегружая конкретный узел распределенного кэша.
    *   *Решение:* Репликация горячих ключей на все узлы или использование локального L1-кэша на стороне приложения для таких ключей.
*   **Big Keys (Большие ключи):** Хранение слишком крупных объектов (десятки/сотни МБ) в одном ключе.
    *   *Проблема:* Приводит к задержкам при чтении/удалении и блокировкам однопоточных систем (Redis).
    *   *Решение:* Разбиение объекта на части или хранение в объектном хранилище (S3) с кэшированием только метаданных.

### Стратегии прогрева кэша (Cache Warmup)

Прогрев необходим для предотвращения деградации производительности после перезапуска системы:
1.  **Массовая загрузка (Bulk Load):** Скрипт считывает самые популярные ID из аналитики/логов и записывает их в кэш перед запуском трафика.
2.  **Зеркалирование трафика (Shadow Traffic):** Перенаправление копии реального трафика на новую систему кэширования без отдачи ответов пользователям.
3.  **Ленивый прогрев с длинным TTL:** Постепенное наполнение в процессе работы, но с защитой от Stampede.

### Пример: Микрокэширование в Nginx

Микрокэширование (Microcaching) — эффективный метод защиты API от всплесков трафика (Spikes), когда динамический контент кэшируется на очень короткое время (1–5 секунд).

```nginx
proxy_cache_path /data/nginx/cache levels=1:2 keys_zone=api_cache:10m max_size=1g inactive=60m use_temp_path=off;

server {
    location /api/v1/status {
        proxy_cache api_cache;
        proxy_cache_valid 200 1s; # Кэшируем успешные ответы на 1 секунду
        proxy_cache_lock on;      # Защита от Thundering Herd
        proxy_pass http://backend;
    }
}
```

### Оптимизация хранения и сериализация

Выбор формата данных критичен для CPU и памяти:

| Формат | Скорость | Компактность | Особенности |
| :--- | :--- | :--- | :--- |
| **JSON** | Низкая | Низкая | Читаемость, универсальность. Требует много CPU на парсинг. |
| **MessagePack** | Высокая | Высокая | Бинарный формат, не требует схемы. |
| **Protobuf** | Максимальная| Максимальная | Требует `.proto` схему, идеален для межсервисного взаимодействия. |

Для больших объектов (более 10 КБ) рекомендуется использовать сжатие (Zstd, LZ4).

## Дополнительная информация

### Мониторинг и эксплуатация

Критически важные метрики (Prometheus/Grafana):
*   `cache_hit_ratio_percent`: Эффективность конфигурации.
*   `cache_evictions_total`: Сигнал о нехватке памяти (Memory Pressure).
*   `cache_ops_latency_seconds`: Задержка операций самого кэша.
*   `cache_connected_clients`: Количество активных соединений (для Redis).

**Пример проверки статуса Redis:**
```bash
# Общая статистика
redis-cli info stats | grep keyspace

# Поиск горячих ключей (требует включенного LFU/LRU)
redis-cli --hotkeys

# Поиск больших ключей
redis-cli --bigkeys
```

### Валидация и тестирование кэша

Перед внедрением или изменением стратегии необходимо провести бенчмаркинг:
1.  **Тестирование прогретого кэша:** Замер Latency/Throughput при 100% Hit Rate.
2.  **Тестирование холодного старта:** Симуляция запуска без кэша для определения «точки отказа» БД.
3.  **Проверка инвалидации:** Тестирование скорости распространения обновлений и отсутствия Stale-данных там, где это критично.
4.  **Инструменты:** `redis-benchmark`, `memtier_benchmark`, `k6` с модулями для работы с Redis.

### Ограничения и Edge Cases

*   **Динамический TTL:** Использование разных TTL в зависимости от популярности контента (Popularity-aware caching).
*   **Кэш-бастинг (Cache Busting):** Атака или ошибка, генерирующая бесконечное количество уникальных ключей, что приводит к 0% Hit Rate и вымыванию полезных данных.
*   **Проблема первого запроса:** Первый пользователь всегда платит `Miss Penalty`. Решается через предварительный прогрев.
