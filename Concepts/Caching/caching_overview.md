# Кэширование: Обзор

## Определения

**Кэширование** — это процесс хранения копий данных в более быстром и доступном слое (кэше) для ускорения обработки последующих запросов. Основная цель — значительно уменьшить задержку (Latency) и снизить нагрузку на основной, более медленный источник данных: базу данных (Database), диск или внешний API (Application Programming Interface).

Использование кэша всегда вводит компромисс между скоростью доступа и риском использования устаревших данных (*Staleness*).

## Основные концепции

### Уровни кэширования

Кэширование применяется на разных этапах прохождения запроса:

1.  **Клиентское кэширование (Browser Cache):** Хранение ресурсов на стороне пользователя. Управляется через HTTP-заголовки.
2.  **CDN (Content Delivery Network):** Кэширование на границе сети (Edge) для доставки контента из ближайшего к пользователю узла.
3.  **Обратный прокси (Reverse Proxy / API Gateway):** Кэширование ответов бэкенда на серверах типа Nginx, Angie или Varnish.
4.  **Прикладное кэширование (Application Cache):**
    *   *Local Cache:* В памяти самого приложения (например, HashMap в Java, Dictionary в Python).
    *   *Distributed Cache:* Внешние системы (Redis, Memcached), доступные нескольким экземплярам приложения.
5.  **Кэширование базы данных:** Внутренние механизмы БД (Buffer Pool в PostgreSQL, Query Cache) для ускорения доступа к данным на диске.

### Ключевые метрики

*   **Hit Ratio (Коэффициент попаданий):** Доля запросов, успешно обслуженных из кэша. Рассчитывается как `Hits / (Hits + Misses)`. Целевое значение зависит от типа данных (для статики — >95%).
*   **Miss Penalty (Штраф за промах):** Дополнительное время и ресурсы, затрачиваемые на обращение к источнику при отсутствии данных в кэше.
*   **Latency (Задержка):** Время ответа при попадании в кэш (обычно <1-10 мс) против времени ответа от источника.

### Управление жизненным циклом данных

*   **TTL (Time-To-Live):** Срок жизни записи в кэше. По истечении TTL данные считаются просроченными (*Expired*) и подлежат обновлению.
*   **Инвалидация (Invalidation):** Принудительное удаление или пометку данных как недействительных при их изменении в источнике. Это одна из самых сложных задач («There are only two hard things in Computer Science: cache invalidation and naming things»).
*   **[Паттерны кэширования](./caching_patterns.md):** Стратегии взаимодействия приложения с кэшем (Cache-Aside, Read-Through, Write-Through).
*   **[Политики вытеснения](./caching_eviction_policies.md):** Алгоритмы освобождения места при заполнении кэша: LRU (Least Recently Used), LFU (Least Frequently Used), FIFO (First-In-First-Out).

### Важные аспекты

*   **Сериализация:** Формат хранения данных (JSON, Protobuf, MessagePack, Binary). Влияет на скорость (CPU) и объем занимаемой памяти.
*   **Пространства имен (Namespaces):** Использование префиксов в ключах (`user:123:profile`) для логической группировки и упрощения массовой очистки.

## Практические сценарии

### Типовые проблемы и решения

*   **Cache Stampede (Dog-piling) / Thundering Herd:** Лавинообразная нагрузка на источник, когда популярный ключ истекает, и тысячи запросов одновременно уходят в БД.
    *   *Решение:* Использование блокировок (Mutex), «вечный кэш» с фоновым обновлением или [джиттер](#jitter).
*   **Cache Avalanche (Лавина кэша):** Массовое одновременное истечение TTL у большого количества ключей (например, если они были записаны одновременно при старте системы).
    *   *Решение:* <a id="jitter"></a>**Джиттер (Jitter)** — добавление случайной вариативности к TTL (например, `300с + random(-30, 30)`).
*   **Cache Penetration (Проникновение):** Запросы к данным, которых нет ни в кэше, ни в БД. Каждый такой запрос «прошивает» кэш насквозь и нагружает БД.
    *   *Решение:* **Негативное кэширование** (кэширование пустых ответов на короткое время) или фильтры Блума (Bloom Filters).

### Оптимизация хранения

*   Храните в кэше только «горячие» данные, доступ к которым требуется часто.
*   Избегайте хранения «тяжелых» объектов целиком; лучше хранить компактные структуры или идентификаторы.
*   Используйте сжатие для объемных текстовых данных (например, больших JSON-ответов).

## Дополнительная информация

### Мониторинг

Для стабильной работы системы кэширования необходимо отслеживать:
*   `Hit/Miss Ratio` — общая эффективность.
*   `Eviction Rate` — частота вытеснения ключей. Высокий показатель при низком Hit Ratio говорит о нехватке памяти.
*   `Memory Fragmentation` — фрагментация памяти, особенно критично для Redis.
*   `CPU Usage` — нагрузка на процессор при сериализации/десериализации.
