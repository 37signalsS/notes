# Кэширование: Обзор

**Актуально для:** Общая теория кэширования + Redis 8.x / Valkey 8.x / Memcached 1.6.x

## Определения

**Кэширование** — это процесс хранения копий данных в специализированном, более быстром и доступном слое (кэше) для ускорения обработки последующих запросов. Основная цель — радикальное снижение задержки (Latency) и минимизация нагрузки на основной источник данных: базу данных (Database), дисковую подсистему или внешний API.

Эффективность кэширования базируется на двух фундаментальных принципах **локальности ссылок (Locality of Reference)**:
*   **Временная локальность (Temporal Locality):** Если данные были запрошены один раз, с высокой вероятностью они понадобятся снова в ближайшее время.
*   **Пространственная локальность (Spatial Locality):** Если данные были запрошены, с высокой вероятностью потребуются данные, расположенные рядом (актуально для кэширования дисковых блоков и строк БД).

Использование кэша всегда вводит компромисс между скоростью доступа и гарантией актуальности данных (*Data Freshness*). В распределенных системах это напрямую связано с теоремой CAP (Consistency, Availability, Partition tolerance). Большинство систем кэширования (Redis, Memcached) ориентированы на **AP**, обеспечивая высокую доступность и производительность ценой временной несогласованности (*Eventual Consistency*).

## Основные концепции

### Типы архитектур кэширования

1.  **Локальный кэш (In-process/Local Cache):**
    *   Данные хранятся в оперативной памяти самого приложения.
    *   **Плюсы:** Нулевая сетевая задержка, максимальная скорость.
    *   **Минусы:** Память ограничена процессом, данные теряются при перезагрузке, сложность синхронизации между несколькими экземплярами приложения.
2.  **Распределенный кэш (Distributed Cache):**
    *   Внешняя система (Redis, Dragonfly, Memcached), доступная всем узлам приложения по сети.
    *   **Плюсы:** Общее состояние для всех узлов, независимое масштабирование, сохранение данных при перезагрузке приложения.
    *   **Минусы:** Сетевые задержки (hop), накладные расходы на сериализацию/десериализацию.
3.  **Многоуровневый кэш (Near Cache / L1-L2):**
    *   Комбинация локального кэша (L1) для «горячих» данных и распределенного (L2) для основного объема. L1 инвалидируется через механизм Pub/Sub или короткий TTL.

### Уровни кэширования

Кэширование пронизывает всю архитектуру современной системы:

1.  **Аппаратный уровень (CPU Cache):**
    *   *L1/L2/L3:* Сверхбыстрая память внутри процессора для хранения инструкций и данных, необходимых для немедленного выполнения. Оперирует кэш-линиями (обычно 64 байта).
2.  **Клиентское кэширование (Browser/App Cache):**
    *   Хранение статических ресурсов (CSS, JS, изображения) локально. Управляется через HTTP-заголовки (`Cache-Control`, `ETag`, `Last-Modified`).
3.  **CDN (Content Delivery Network) и Edge:**
    *   Кэширование на границе сети для доставки контента из географически ближайшего узла. Идеально для видео, изображений и статических API-ответов.
4.  **Прокси-слой (Reverse Proxy / API Gateway):**
    *   Кэширование ответов бэкенда (Nginx, Angie, Varnish). Позволяет «срезать» нагрузку до того, как она попадет на сервер приложений.
5.  **Прикладное кэширование (Application Cache):**
    *   Использование библиотек (Guava, Caffeine для Java) или внешних хранилищ (Redis) непосредственно в бизнес-логике.
6.  **Кэширование базы данных:**
    *   *Internal:* Buffer Pool (PostgreSQL/MySQL), кэш планов выполнения запросов.
    *   *External:* Материализованные представления (Materialized Views) и индексы.

### Ключевые метрики

*   **Hit Ratio (Коэффициент попаданий):** Процент запросов, обслуженных из кэша. Рассчитывается как `Hits / (Hits + Misses)`. Целевой показатель для «горячих» данных — >90%.
*   **Miss Penalty (Штраф за промах):** Дополнительные затраты времени на получение данных из источника и их запись в кэш. Если пенальти слишком высок, кэширование может замедлить систему.
*   **Eviction Rate (Частота вытеснения):** Количество записей, удаленных из-за нехватки места. Высокий показатель при низком Hit Ratio — сигнал о дефиците оперативной памяти или неэффективном TTL.
*   **TTFB (Time to First Byte):** Основной показатель эффективности кэша на уровне сети.
*   **Object Age:** Возраст объекта в кэше. Помогает отслеживать «протухание» данных.

### Жизненный цикл и управление данными

*   **TTL (Time-To-Live):** Время жизни записи. Может быть фиксированным или «скользящим» (продлевается при чтении).
*   **Инвалидация (Invalidation):** Процесс удаления данных при их обновлении в источнике.
*   **Прогрев кэша (Cache Warmup):** Принудительное наполнение кэша популярными данными до начала активного трафика (например, после деплоя или перезагрузки).
*   **Согласованность (Consistency):**
    *   *Eventual Consistency:* Данные в кэше могут временно отличаться от БД.
    *   *Strong Consistency:* Кэш обновляется или инвалидируется атомарно вместе с источником.
*   **[Стратегии инвалидации через CDC](../../Databases/Concepts/cdc_architectural_patterns.md):** Гарантированная консистентность через Debezium + Kafka.
*   **[Keyspace Notifications](./caching_keyspace_notifications.md):** Реактивное инвалидирование через Pub/Sub.
*   **[Распределенные блокировки](./caching_distributed_locks.md):** Redlock для критических секций.
*   **[HTTP-кэширование](../../Networking/Protocols/HTTP/http_caching.md):** Cache-Control, ETag, Vary, CDN-Cache-Control.

## Практические сценарии

### Типовые проблемы и стратегии решения

*   **Кассовая давка (Cache Stampede / Thundering Herd):** Множество параллельных запросов пытаются обновить кэш для одного и того же ключа при его истечении (TTL).
    *   *Решение 1 (Mutex/Locking):* Только один поток (запрос) идет в БД для восстановления записи, остальные ждут или кратковременно получают старое значение.
    *   *Решение 2 (Stale-while-revalidate):* Отдача старых данных, пока один фоновый процесс обновляет значение (например, `proxy_cache_use_stale` в Nginx).
    *   *Решение 3 (Поэтапный TTL):* Программное обновление «горячих» записей до их фактического истечения.
*   **Cache Avalanche (Лавина кэша):** Одновременное истечение TTL у миллионов ключей (например, если они были записаны одновременно при старте системы).
    *   *Решение:* **Джиттер (Jitter / Staggered TTL)** — добавление небольшого случайного смещения к TTL каждой записи (например, `TTL = base_ttl + rand(0, 300)`).
*   **Cache Penetration (Проникновение):** Запросы к несуществующим данным, нагружающие БД в обход кэша.
    *   *Решение:* **Негативное кэширование** (сохранение ключа со значением `null` на короткий срок) или использование **фильтров Блума (Bloom Filters)** для быстрой проверки отсутствия ключа без обращения к БД.
*   **Hot Keys (Горячие ключи):** Один или несколько ключей получают непропорционально большую долю трафика, перегружая конкретный узел распределенного кэша.
    *   *Решение:* Репликация горячих ключей на все узлы или использование локального L1-кэша на стороне приложения для таких ключей.
*   **Big Keys (Большие ключи):** Хранение слишком крупных объектов (десятки/сотни МБ) в одном ключе.
    *   *Проблема:* Приводит к задержкам при чтении/удалении и блокировкам однопоточных систем (Redis).
    *   *Решение:* Разбиение объекта на части или хранение во внешнем объектном хранилище с кэшированием только метаданных.
*   **Потеря сессий при рестарте (Session Loss on Restart):** При перезагрузке узла кэша все сессии/состояния теряются.
    *   *Решение:* Персистентность (RDB/AOF для Redis, Extstore для Memcached) или вынос состояния в внешнее хранилище с репликацией.

### Стратегии прогрева кэша (Cache Warmup)

Прогрев необходим для предотвращения деградации производительности после перезапуска системы:
1.  **Массовая загрузка (Bulk Load):** Скрипт считывает самые популярные ID из аналитики/логов и записывает их в кэш перед запуском трафика.
2.  **Зеркалирование трафика (Shadow Traffic):** Перенаправление копии реального трафика на новую систему кэширования без отдачи ответов пользователям.
3.  **Ленивый прогрев с длинным TTL:** Постепенное наполнение в процессе работы, но с защитой от Stampede.

**Пример: Bulk Load через Redis Pipeline**
```bash
#!/bin/bash
# warmup.sh — массовый прогрев Redis-кэша из CSV-файла с популярными ключами
REDIS_HOST="127.0.0.1"
REDIS_PORT="6379"
CSV_FILE="/opt/cache/warmup_keys.csv"

while IFS=, read -r key value ttl; do
  echo "SET $key $value EX $ttl"
done < "$CSV_FILE" | redis-cli -h "$REDIS_HOST" -p "$REDIS_PORT" --pipe
```
*Ожидаемый результат:* Все ключи записаны в кэш. Проверка: `redis-cli INFO keyspace` — количество ключей увеличилось.

**Пример: Ленивый прогрев с защитой от Stampede (Python)**
```python
import redis
import random

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

def get_or_warm(key, fetch_fn, base_ttl=3600):
    value = r.get(key)
    if value:
        return value
    lock_key = f"lock:{key}"
    acquired = r.set(lock_key, "1", nx=True, ex=10)
    if acquired:
        try:
            value = fetch_fn()
            # Джиттер для предотвращения Cache Avalanche
            ttl = base_ttl + random.randint(-300, 300)
            r.set(key, value, ex=ttl)
            return value
        finally:
            r.delete(lock_key)
    else:
        import time
        time.sleep(0.05)
        return get_or_warm(key, fetch_fn, base_ttl)
```

### Пример: Микрокэширование в Nginx

Микрокэширование (Microcaching) — эффективный метод защиты API от всплесков трафика (Spikes), когда динамический контент кэшируется на очень короткое время (1–5 секунд).

```nginx
proxy_cache_path /data/nginx/cache levels=1:2 keys_zone=api_cache:10m max_size=1g inactive=60m use_temp_path=off;

server {
    location /api/v1/status {
        proxy_cache api_cache;
        proxy_cache_valid 200 1s; # Кэшируем успешные ответы на 1 секунду
        proxy_cache_lock on;      # Защита от Thundering Herd
        proxy_pass http://backend;
    }
}
```

**Валидация конфигурации:**
```bash
nginx -t && nginx -s reload
curl -sI "http://localhost/api/v1/status" | grep X-Cache-Status
# → X-Cache-Status: MISS (первый запрос) или HIT (повторный)
```

### Оптимизация хранения и сериализация

Выбор формата данных критичен для CPU и памяти:

| Формат | Скорость | Компактность | Особенности |
| :--- | :--- | :--- | :--- |
| **JSON** | Низкая | Низкая | Читаемость, универсальность. Требует много CPU на парсинг. |
| **MessagePack** | Высокая | Высокая | Бинарный формат, не требует схемы. |
| **Protobuf** | Максимальная| Максимальная | Требует `.proto` схему, идеален для межсервисного взаимодействия. |

Для больших объектов (более 10 КБ) рекомендуется использовать сжатие (Zstd, LZ4).

### Конфигурация Redis для кэширования (оптимальные параметры)

**Базовый конфиг (redis.conf):**
```conf
# Лимит памяти
maxmemory 4gb
maxmemory-policy allkeys-lru

# Персистентность (для кэша обычно отключается или используется RDB)
save ""                    # Отключить автоматические снапшоты
appendonly no              # Отключить AOF для чистого кэша

# Производительность
hz 10                      # Частота фоновых задач (TTL-очистка)
dynamic-hz yes             # Динамическая частота при простое
io-threads 4               # Потоки I/O (Redis 6+)
io-threads-do-reads yes    # Многопоточное чтение

# Соединения
maxclients 10000
timeout 300                # Закрытие неактивных соединений

# Безопасность
bind 127.0.0.1
protected-mode yes
requirepass <strong_password>
```

**Валидация конфигурации:**
```bash
redis-cli CONFIG GET maxmemory
# → maxmemory 4294967296

redis-cli CONFIG GET maxmemory-policy
# → maxmemory-policy allkeys-lru
```

### Конфигурация Memcached для кэширования (оптимальные параметры)

```bash
# Запуск с оптимальными параметрами для кэширования
memcached \
  -m 4096 \                 # 4 ГБ RAM
  -c 2048 \                 # Макс. соединений
  -t 8 \                    # Потоков (равно числу ядер)
  -l 127.0.0.1 \            # Только локальный доступ
  -o lru_maintainer,lru_crawler,slab_automove \
  -f 1.1 \                  # Фактор роста слабов (меньше = компактнее)
  -n 48                     # Минимальный чанк (байты)
```

**Валидация:**
```bash
memcached-tool localhost:11211 stats | grep -E "curr_items|get_hits|get_misses"
# → curr_items: <number>
# → get_hits: <number>
```

## Лучшие практики

### Архитектура и проектирование
*   Используйте многоуровневое кэширование (L1 + L2) для разделения «горячих» и «теплых» данных.
*   Для защиты от Cache Stampede применяйте `proxy_cache_lock` (Nginx) или механизмы блокировки на уровне приложения.
*   Используйте негативное кэширование или фильтры Блума для защиты БД от запросов к несуществующим данным.

### Производительность
*   Для сериализации предпочитайте MessagePack или Protobuf JSON; для объектов >10 КБ используйте сжатие Zstd/LZ4.
*   В Redis используйте `SCAN` вместо `KEYS`, `SSCAN` вместо `SMEMBERS` для избежания блокировок основного потока.
*   Настройте `hz 10` и `dynamic-hz yes` для оптимального баланса между точностью TTL-очистки и CPU.

### Сеть
*   Размещайте экземпляры Redis/Memcached в том же дата-центре, что и приложение. Локальный доступ (<0.1 мс) значительно эффективнее междатацентрового (1–50 мс).
*   Используйте `keepalive` для TCP-соединений для предотвращения разрыва неактивных соединений.
*   Настройте `tcp-keepalive 300` (Redis) или `-o tcp_keepalive` (Memcached).

### Безопасность
*   Привязывайте Redis и Memcached к `127.0.0.1` или внутреннему интерфейсу. Никогда не expose порт 6379/11211 в интернет.
*   Используйте `requirepass` или ACL (Redis) для аутентификации. В Memcached ограничьте доступ firewall.
*   Включите TLS 1.3 для шифрования трафика (Redis: `tls-port`, `tls-cert-file`, `tls-key-file`).
*   Логируйте опасные команды: `CONFIG`, `FLUSHALL`, `FLUSHDB`.

### Эксплуатация
*   Настраивайте мониторинг hit rate, evictions, latency, fragmentation ratio. Пороги: hit rate <80%, fragmentation >1.5.
*   Перед внедрением проводите бенчмаркинг: `redis-benchmark`, `memtier_benchmark`, `k6`.
*   Настройте персистентность (RDB/AOF для Redis) только если данные нельзя потерять. Для чистого кэша персистентность отключается.
*   Используйте `maxmemory` не более 70% от лимита контейнера/хоста, чтобы оставить место для overhead.

## Устранение неисправностей (Troubleshooting)

| Симптом | Вероятная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Hit rate < 80% | Недостаточный объем кэша или неэффективный TTL | `redis-cli INFO stats`, `memcached-tool stats` | Увеличить `maxmemory` или оптимизировать TTL |
| Рост latency операций | Фрагментация памяти или блокировки | `redis-cli INFO memory`, `redis-cli SLOWLOG GET` | Включить `activedefrag yes`, проверить bigkeys |
| `OOM command not allowed` | Исчерпан лимит `maxmemory` | `redis-cli INFO memory \| grep used_memory` | Увеличить `maxmemory` или сменить eviction policy |
| Сессии теряются после рестарта | Нет персистентности | `redis-cli INFO persistence` | Настроить RDB/AOF или вынести сессии в другой сервис |
| Memory pressure в контейнере | Лимит `memory.limit_in_bytes` слишком низок | `cat /sys/fs/cgroup/memory/memory.limit_in_bytes` | Увеличить `memory` limits в Kubernetes/Docker |
| Свопинг (Swap usage) | Нехватка RAM, кэш не помещается | `redis-cli INFO memory \| grep used_memory_rss` | Увеличить RAM или уменьшить `maxmemory` |
| Слишком много соединений | Утечка соединений на клиенте | `redis-cli INFO clients` | Проверить connection pooling, установить `timeout` |
| `ERR max number of clients reached` | Достигнут `maxclients` | `redis-cli CONFIG GET maxclients` | Увеличить `maxclients`, проверить утечки соединений |
| Потеря данных при crash | Кэш без персистентности | Проверить конфиг персистентности | Настроить RDB/AOF, использовать replica |

## Дополнительная информация

### Планирование ресурсов и размер (Capacity Planning)

**Формула оценки потребления памяти:**
```
RAM (MB) = (Средний размер объекта × Количество ключей) / 1 048 576
```

**Минимальные ресурсы для Redis/Valkey:**

| Нагрузка | CPU | RAM | Disk (при персистентности) |
| :--- | :--- | :--- | :--- |
| До 10K RPS | 1-2 core | 2-4 GB | SSD 20 GB |
| 10K-100K RPS | 2-4 core | 8-16 GB | SSD 50 GB |
| 100K+ RPS | 4-8 core | 32-64 GB | NVMe 100 GB+ |

**Минимальные ресурсы для Memcached:**

| Объем кэша | CPU | RAM | Примечания |
| :--- | :--- | :--- | :--- |
| До 10 GB | 2 core | 12 GB | Метаданные + overhead |
| 10-100 GB | 4 core | 128 GB | Рассмотреть Extstore на NVMe |
| 100 GB+ | 8 core | 256 GB+ | Sharding обязателен |

**Фактор overhead:** Redis потребляет ~1.5x от реально хранимого объема из-за аллокатора и фрагментации. Memcached — ~1.3x из-за Slab Allocator.

### Мониторинг и эксплуатация

Критически важные метрики (Prometheus/Grafana):
*   `cache_hit_ratio_percent`: Эффективность конфигурации.
*   `cache_evictions_total`: Сигнал о нехватке памяти (Memory Pressure).
*   `cache_ops_latency_seconds`: Задержка операций самого кэша.
*   `cache_connected_clients`: Количество активных соединений (для Redis).
*   `cache_used_memory_bytes`: Текущее потребление памяти.
*   `cache_fragmentation_ratio`: Отношение системной памяти к потребляемой (Redis). Значение >1.5 — фрагментация, <1.0 — свопинг.
*   `cache_blocked_clients`: Заблокированные клиенты (Redis) — рост блокировок опасен.

**Пример проверки статуса Redis:**
```bash
# Общая статистика
redis-cli info stats | grep keyspace

# Поиск горячих ключей (требует включенного LFU/LRU)
redis-cli --hotkeys

# Поиск больших ключей
redis-cli --bigkeys

# Проверка фрагментации памяти
redis-cli info memory | grep mem_fragmentation_ratio
# → mem_fragmentation_ratio: 1.08 (норма: 1.0-1.5)

# Проверка slow log (долгие команды)
redis-cli slowlog get 10
```

**Пример проверки статуса Memcached:**
```bash
# Общая статистика
memcached-tool localhost:11211 stats

# Просмотр slab-классов (внутренняя фрагментация)
memcached-tool localhost:11211 display

# Проверка hit rate
echo "stats" | nc localhost 11211 | grep -E "get_hits|get_misses"
# → STAT get_hits <number>
# → STAT get_misses <number>
```

### Ограничения и Edge Cases

*   **Динамический TTL:** Использование разных TTL в зависимости от популярности контента (Popularity-aware caching).
*   **Кэш-бастинг (Cache Busting):** Атака или ошибка, генерирующая бесконечное количество уникальных ключей, что приводит к 0% Hit Rate и вымыванию полезных данных.
*   **Проблема первого запроса:** Первый пользователь всегда платит `Miss Penalty`. Решается через предварительный прогрев.
*   **Однопоточность Redis (основной поток):** Даже с I/O threading, долгие команды (SORT, KEYS, большие множества) блокируют основной поток. Использовать `SCAN` вместо `KEYS`, `SSCAN` вместо `SMEMBERS`.
*   **Ограничение Memcached на размер объекта:** Максимум 1 МБ (по умолчанию). Увеличивается через `-I` (например, `-I 4m`), но это снижает эффективность Slab Allocator.
*   **Гонка данных при инвалидации (Race Condition):** Параллельные потоки могут записать устаревшее значение в кэш. Решение — `Delayed Double Deletion` (см. [паттерны кэширования](./caching_patterns.md)).
*   **Ограничение количества ключей:** Redis — теоретически 2^32, практически ограничено памятью. Memcached — 2^32, но на практике рекомендуется не более 10M ключей на инстанс.

### Бэкап и восстановление (Backup & Recovery)

**Redis (при использовании как кэш-хранилища):**
*   RDB-снапшоты: автоматические (`save 900 1`) или ручные (`BGSAVE`).
*   AOF-файлы: `BGREWRITEAOF` для компактности.
*   Восстановление: копирование dump-файла в каталог данных и перезапуск.

**Memcached:**
*   Полная потеря данных при перезапуске — это нормальное поведение для кэша.
*   Recovery strategy: прогрев кэша (Cache Warmup) после перезапуска.

**Пример: Ручной снапшот Redis:**
```bash
# Сохранение снапшота
redis-cli BGSAVE

# Проверка статуса
redis-cli LASTSAVE
# → 1234567890 (Unix timestamp последнего снапшота)
```

### Чек-лист: Миграция кэширования с Redis на Valkey

При необходимости миграции (лицензионные причины):
1.  Проверить совместимость API (Valkey 8.x — полная совместимость с Redis 7.x).
2.  Запустить Valkey с тем же конфигом (`valkey-server redis.conf`).
3.  Настроить репликацию Redis → Valkey.
4.  Переключить приложение на Valkey.
5.  Удалить Redis после стабилизации.

**Валидация после миграции:**
```bash
valkey-cli INFO server | grep redis_version
# → redis_version: 8.0.0
```
