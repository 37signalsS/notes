# Паттерны кэширования

## Определения

**Паттерны кэширования** — это проверенные стратегии взаимодействия приложения с кэшем и основным хранилищем данных. Выбор паттерна определяет, как и когда данные попадают в кэш и как они синхронизируются с источником.

Для ознакомления с базовыми понятиями, такими как TTL и политики вытеснения, обратитесь к [общему обзору кэширования](./caching_overview.md).

## Основные концепции (Паттерны)

* **Cache-aside (Lazy Loading):**
  * Приложение сначала пытается прочитать данные из кэша.
  * При промахе (cache miss) оно читает данные из источника, сохраняет их в кэш и возвращает результат.
  * **Плюсы:** Прост в реализации, устойчив к сбоям кэша (приложение продолжает работать, хотя и медленнее).
  * **Минусы:** Неконсистентность данных до следующей записи или инвалидации; код чтения "загрязнен" логикой кэширования.

* **Read-through:**
  * Приложение обращается напрямую к кэшу, который инкапсулирует логику чтения из источника.
  * При промахе кэш сам загружает данные из основного хранилища, сохраняет у себя и возвращает приложению.
  * **Плюсы:** Более чистый код приложения.
  * **Минусы:** Требует провайдера кэша, поддерживающего данную функцию; повышенная связность между кэшем и хранилищем.

* **Write-through:**
  * Приложение записывает данные синхронно и в кэш, и в основное хранилище. Операция завершается только после успеха в обеих системах.
  * **Плюсы:** Высокая консистентность данных между кэшем и хранилищем.
  * **Минусы:** Увеличивает задержку операции записи.

* **Write-back (Write-behind):**
  * Приложение записывает данные только в кэш, который немедленно подтверждает операцию.
  * Данные записываются в основное хранилище асинхронно, через некоторое время или по накоплению.
  * **Плюсы:** Очень низкая задержка записи.
  * **Минусы:** Высокий риск потери данных при сбое кэша, если они еще не были сохранены в хранилище.

* **Refresh-ahead:**
  * Система автоматически обновляет "горячие" данные в кэше до истечения их TTL.
  * **Плюсы:** Снижает вероятность промаха и задержки для популярных ключей.
  * **Минусы:** Может приводить к лишним запросам, если данные перестали быть востребованными.

## Практические сценарии

### Пример: Cache-aside с защитой от Cache Stampede (Python + Redis)

Этот пример реализует паттерн `cache-aside` с использованием блокировки, чтобы предотвратить множественные одновременные запросы к базе данных при истечении срока действия ключа.

```python
import time
import redis

# Условные redis и db клиенты
redis_client = redis.Redis()
db_client = ...

def get_user_profile(user_id):
    key = f"user:{user_id}:profile"
    
    # 1. Попытка чтения из кэша
    data = redis_client.get(key)
    if data:
        return decode(data)

    # 2. При промахе — попытка установить блокировку
    lock_key = f"lock:{key}"
    # nx=True: установить, только если не существует
    # ex=5: TTL для блокировки, чтобы избежать вечной блокировки
    is_lock_acquired = redis_client.set(lock_key, "1", nx=True, ex=5)
    
    if is_lock_acquired:
        try:
            # 3. Если блокировка получена — читаем из БД
            record = db_client.fetch_user(user_id)
            ttl_with_jitter = 300 + random.uniform(-30, 30) # Джиттер
            redis_client.set(key, encode(record), ex=int(ttl_with_jitter))
            return record
        finally:
            # 4. Освобождаем блокировку
            redis_client.delete(lock_key)
    else:
        # 5. Если блокировку получил кто-то другой — ждем и пробуем снова
        time.sleep(0.05)
        return get_user_profile(user_id) # Рекурсивный вызов или повторное чтение
```
