# Паттерны кэширования

## Определения

**Паттерны кэширования** — это типовые архитектурные стратегии взаимодействия приложения с кэшем и основным хранилищем данных (Database). Выбор паттерна определяет баланс между производительностью (Latency), согласованностью данных (Consistency) и устойчивостью системы к сбоям.

Основная сложность паттернов заключается в решении проблемы **Dual Writes** (двойной записи), когда обновление двух независимых систем (БД и кэша) не является атомарным, что может привести к рассинхронизации данных.

Для ознакомления с метриками и общими уровнями кэширования обратитесь к [общему обзору кэширования](./caching_overview.md).

## Основные концепции

### Стратегии чтения (Read Patterns)

*   **Cache-aside (Lazy Loading):**
    *   Приложение сначала проверяет кэш. Если данных нет (*Cache Miss*), оно читает их из БД, записывает в кэш и возвращает пользователю.
    *   **Преимущества:** Устойчивость к сбоям кэша (приложение идет в БД), гибкость данных.
    *   **Недостатки:** Задержка при первом запросе, риск рассинхронизации.
*   **Read-through:**
    *   Приложение запрашивает данные только у кэша. Кэш-библиотека или прокси сами загружают данные из БД при их отсутствии.
    *   **Преимущества:** Чистый код приложения, упрощенная логика.

### Стратегии записи (Write Patterns)

*   **Write-through (Сквозная запись):**
    *   Данные записываются в кэш и БД одновременно в рамках одного запроса.
    *   **Преимущества:** Высокая согласованность, данные всегда актуальны в кэше.
    *   **Недостатки:** Увеличенная задержка записи (две сетевые операции).
*   **Write-around:**
    *   Данные записываются только в БД. В кэш они попадают только при последующем чтении (обычно через Cache-aside).
    *   **Преимущества:** Кэш не забивается данными, которые могут никогда не понадобиться.
*   **Write-back (Write-behind):**
    *   Данные пишутся только в кэш и мгновенно подтверждаются. В БД они сбрасываются асинхронно (пачками или по событию).
    *   **Преимущества:** Максимальная производительность записи.
    *   **Недостатки:** Риск потери данных при сбое кэша до момента их записи в БД.

### Проблемы согласованности и их решение

1.  **Гонка данных (Race Condition) при Cache-aside:**
    *   *Сценарий:* Поток А читает из БД (промах кэша), Поток Б обновляет БД и удаляет из кэша, Поток А записывает в кэш старое значение, которое прочитал ранее.
    *   **Решение:** **Delayed Double Deletion** (Отложенное двойное удаление) — приложение удаляет ключ из кэша, обновляет БД и через короткий интервал (например, 500 мс) удаляет ключ повторно, чтобы затереть возможные «грязные» записи от параллельных потоков.

2.  **Проблема Dual Writes:**
    *   Если запись в БД прошла успешно, а удаление из кэша прервалось сетевой ошибкой, в кэше останутся старые данные.
    *   **Решение (Modern Approach):** **Change Data Capture (CDC)**. Использование инструментов типа Debezium для чтения логов БД (Transaction Log) и автоматического обновления или инвалидации кэша через брокер сообщений (Kafka). Это гарантирует, что кэш будет обновлен вслед за БД.

## Сравнение паттернов

| Паттерн | Согласованность | Latency (Чтение) | Latency (Запись) | Сложность |
| :--- | :--- | :--- | :--- | :--- |
| **Cache-aside** | Слабая (Eventual) | Высокая (Hits) | Низкая | Низкая |
| **Read-through** | Средняя | Высокая (Hits) | Средняя | Средняя |
| **Write-through** | Высокая (Strong) | Высокая | Высокая | Средняя |
| **Write-around** | Средняя | Средняя | Низкая | Низкая |
| **Write-back** | Низкая | Максимальная | Максимальная | Высокая |

## Практические сценарии

### Реализация Cache-aside с защитой от Thundering Herd (Python)

```python
import time
import random
import redis
from contextlib import contextmanager

# Использование Redis как распределенной блокировки
redis_client = redis.Redis(host='localhost', port=6379, db=0, decode_responses=True)

@contextmanager
def distributed_lock(lock_name, timeout=10):
    """Простая реализация Mutex на базе Redis SET NX EX."""
    acquired = redis_client.set(lock_name, "locked", nx=True, ex=timeout)
    try:
        yield acquired
    finally:
        if acquired:
            redis_client.delete(lock_name)

def get_user_profile(user_id):
    cache_key = f"user:{user_id}:profile"
    
    # 1. Попытка чтения из кэша
    profile = redis_client.get(cache_key)
    if profile:
        return profile # Cache Hit

    # 2. Cache Miss — защищаемся от наплыва запросов к БД
    lock_key = f"lock:{cache_key}"
    with distributed_lock(lock_key) as acquired:
        if acquired:
            # Повторная проверка кэша (Double-checked locking)
            profile = redis_client.get(cache_key)
            if profile:
                return profile
            
            # Имитация запроса к основной БД
            profile = db_query(user_id)
            
            # Запись в кэш с джиттером (Jitter) для предотвращения Cache Avalanche
            ttl = 3600 + random.randint(-60, 60)
            redis_client.set(cache_key, profile, ex=ttl)
            return profile
        else:
            # Если не получили блокировку — ждем и повторяем
            time.sleep(0.05)
            return get_user_profile(user_id)

def db_query(user_id):
    # Тяжелый запрос к БД
    return f"profile_data_for_{user_id}"
```

### Архитектура инвалидации через CDC (Debezium + Kafka)

Это наиболее надежный современный способ реализации **Write-Through/Write-Behind** эффекта без усложнения кода приложения.

1.  Приложение пишет только в **PostgreSQL**.
2.  **Debezium** (CDC-коннектор) читает WAL (Write Ahead Log) базы данных.
3.  Событие изменения попадает в топик **Kafka**.
4.  **Consumer** (инвалидатор) читает Kafka и удаляет соответствующий ключ в **Redis**.

**Результат:** Гарантированная консистентность без распределенных транзакций.

## Дополнительная информация

### Выбор паттерна под нагрузку

*   **Read-heavy (Чтение >> Запись):** Однозначно `Cache-aside` или `Read-through`.
*   **Write-heavy (Запись >> Чтение):** `Write-back` с буферизацией в кэше, если допустима небольшая потеря данных.
*   **Strong Consistency:** `Write-through` в транзакции или `Cache-aside` с паттерном `Delayed Double Deletion`.

### Мониторинг паттернов

При использовании `Write-back` критически важно мониторить **размер очереди (Lag)** на запись в БД. Если кэш заполняется быстрее, чем БД успевает принимать данные, произойдет переполнение памяти или потеря данных.
