# Паттерны кэширования

## Определения

**Паттерны кэширования** — это типовые стратегии взаимодействия прикладного программного интерфейса (API) или приложения с кэшем и основным хранилищем данных. Выбор конкретного паттерна определяет баланс между производительностью, консистентностью (согласованностью) данных и сложностью реализации.

Для ознакомления с базовыми понятиями, такими как TTL (Time-To-Live) и политики вытеснения, обратитесь к [общему обзору кэширования](./caching_overview.md).

## Основные концепции

### Стратегии чтения (Read Patterns)

*   **Cache-aside (Lazy Loading — ленивая загрузка):**
    *   Приложение сначала проверяет наличие данных в кэше.
    *   При отсутствии данных (*Cache Miss*) оно читает их из базы данных (Database), сохраняет в кэш и возвращает пользователю.
    *   **Применение:** Самый распространенный паттерн для общих задач.
*   **Read-through (Сквозное чтение):**
    *   Приложение всегда запрашивает данные у кэша. Кэш сам отвечает за загрузку данных из источника при их отсутствии.
    *   **Применение:** Позволяет полностью скрыть логику работы с хранилищем от кода приложения.

### Стратегии записи (Write Patterns)

*   **Write-through (Сквозная запись):**
    *   Данные записываются одновременно и в кэш, и в основное хранилище. Операция считается успешной только после подтверждения от обеих систем.
    *   **Применение:** Высокая согласованность данных, защита от потери при сбоях.
*   **Write-around (Запись в обход):**
    *   Данные записываются напрямую в основное хранилище, минуя кэш. В кэш они попадают только при последующем чтении (обычно через Cache-aside).
    *   **Применение:** Защита кэша от «засорения» данными, которые читаются редко.
*   **Write-back (Write-behind — запись с запаздыванием):**
    *   Данные записываются только в кэш, который мгновенно подтверждает операцию. Запись в основное хранилище происходит асинхронно.
    *   **Применение:** Максимальная производительность записи (Write-heavy нагрузки), но есть риск потери данных при сбое кэша.

### Продвинутые паттерны

*   **Refresh-ahead (Упреждающее обновление):**
    *   Кэш автоматически обновляет популярные данные до того, как истечет их TTL.
    *   **Применение:** Снижение задержек для «горячих» данных.

## Сравнение паттернов

| Паттерн | Консистентность | Производительность чтения | Производительность записи | Сложность |
| :--- | :--- | :--- | :--- | :--- |
| **Cache-aside** | Слабая (возможен stale) | Высокая | Высокая | Низкая |
| **Read-through** | Средняя | Высокая | Средняя | Средняя |
| **Write-through** | Высокая (Strong) | Высокая | Низкая (Latency) | Средняя |
| **Write-around** | Средняя | Средняя (первый промах) | Высокая | Низкая |
| **Write-back** | Низкая | Максимальная | Максимальная | Высокая |

## Практические сценарии

### Реализация Cache-aside с блокировкой (Python + Redis)

Этот пример демонстрирует защиту от проблемы «стада бизонов» (Thundering Herd) с помощью распределенной блокировки.

```python
import time
import random
import redis

# Клиент Redis и условный клиент базы данных
redis_client = redis.Redis(host='localhost', port=6379, db=0)
db_client = ...

def get_data_with_lock(key_id):
    cache_key = f"data:{key_id}"
    
    # 1. Проверка кэша
    result = redis_client.get(cache_key)
    if result:
        return result

    # 2. Попытка захвата блокировки (Mutex)
    lock_key = f"lock:{cache_key}"
    # nx=True: установить только если ключа нет
    # ex=10: TTL блокировки на случай падения процесса
    if redis_client.set(lock_key, "1", nx=True, ex=10):
        try:
            # 3. Чтение из источника
            data = db_client.query_expensive_data(key_id)
            # Добавление джиттера (Jitter) к TTL
            ttl = 3600 + random.randint(-60, 60)
            redis_client.set(cache_key, data, ex=ttl)
            return data
        finally:
            # 4. Освобождение блокировки
            redis_client.delete(lock_key)
    else:
        # 5. Если заблокировано — короткое ожидание и рекурсивный повтор
        time.sleep(0.1)
        return get_data_with_lock(key_id)
```

## Дополнительная информация

### Выбор стратегии

*   Если важна **строгая согласованность**: используйте `Write-through` в паре с `Read-through` или `Cache-aside` с короткой инвалидацией.
*   При **огромном потоке записей** (логи, метрики): оптимален `Write-back`.
*   Для **статичного контента** или редко меняющихся данных: стандарт — `Cache-aside`.

Специфические реализации для распределенных систем на границе сети описаны в [обзоре Edge Computing](../edge_computing_overview.md).
