# Обзор API Gateway

## Определения

**API Gateway** (Шлюз API) — это критический архитектурный паттерн в микросервисных системах, представляющий собой специализированный сервер, который выступает единой точкой входа (Single Point of Entry) для всех внешних клиентов. Шлюз абстрагирует внутреннюю структуру системы, обеспечивая безопасность, маршрутизацию и управление трафиком на прикладном уровне.

В модели OSI API Gateway работает преимущественно на **L7 (прикладном уровне)**, что позволяет ему анализировать содержимое запросов (пути, заголовки, тела) для принятия решений о маршрутизации. Он обрабатывает **North-South трафик** (внешний клиент ↔ кластер), в то время как взаимодействие между сервисами внутри кластера (**East-West**) обычно возлагается на Service Mesh.

### Отличия от Load Balancer и Reverse Proxy
*   **Load Balancer (L4):** Работает на транспортном уровне, распределяя TCP/UDP соединения между серверами. Не анализирует содержимое запроса.
*   **Reverse Proxy (L7):** Проксирует HTTP-запросы, может кэшировать контент и модифицировать заголовки. Но не предоставляет средств управления API (rate limiting, аутентификация, versioning).
*   **API Gateway (L7):** Специализированный reverse proxy с функциями управления API: аутентификация, rate limiting, versioning, мониторинг, маршрутизация и др.

## Архитектура и компоненты

Современные API Gateways (по состоянию на 2026 год) строятся на принципе разделения ответственности, аналогичном программно-определяемым сетям (SDN):

### Уровень управления (Control Plane)
Центральный узел администрирования, отвечающий за:
*   **Управление конфигурацией:** хранение и распространение правил маршрутизации, политик безопасности и настроек плагинов.
*   **Management API:** интерфейс (REST, gRPC или CLI) для взаимодействия администраторов и систем CI/CD со шлюзом.
*   **Интеграция с Service Discovery:** автоматическое обнаружение доступных экземпляров бэкенд-сервисов. Шлюз реализует паттерн **Server-side discovery** (через Consul, etcd или Kubernetes API). Подробнее см. в [обзоре Service Discovery](./service-discovery-overview.md).
*   **Certificate Management:** автоматическая выдача и ротация TLS-сертификатов (Let's Encrypt, cert-manager).
*   **Secrets Management:** интеграция с vault для безопасного хранения API-ключей и токенов.

### Уровень обработки данных (Data Plane)
Высокопроизводительные прокси-инстансы (например, на базе Envoy, Nginx или Rust-движков), которые:
*   **Принимают запросы:** обеспечивают терминацию TLS и первичную валидацию.
*   **Исполняют логику:** применяют цепочки фильтров и плагинов (аутентификация → ограничение скорости → трансформация → маршрутизация).
*   **Проксируют трафик:** передают запрос выбранному бэкенду и возвращают ответ клиенту.
*   **Собирают метрики:** предоставляют детальную статистику по запросам, ошибкам и латентности.
*   **Генерируют логи:** записывают access logs для анализа и отладки.

### Система плагинов (Middleware)
Модульная архитектура позволяет динамически расширять функционал без перезагрузки шлюза. Плагины могут быть написаны на Lua, Go или скомпилированы в WebAssembly (WASM) для максимальной производительности.

Типичные плагины и их порядок выполнения (execution order):
1.  **IP Restriction:** Ограничение доступа по IP-адресам.
2.  **Rate Limiting:** Ограничение количества запросов.
3.  **Authentication (Key Auth, JWT, OAuth2):** Аутентификация клиента.
4.  **Authorization (ACL, RBAC):** Авторизация доступа к ресурсам.
5.  **Request Transform:** Модификация заголовков и тела запроса.
6.  **Proxy:** Перенаправление на бэкенд.
7.  **Response Transform:** Модификация ответа бэкенда.
8.  **Logging (File, HTTP, TCP):** Запись логов.

## Базовые концепции

API Gateway централизует сквозную функциональность (Cross-Cutting Concerns), избавляя разработчиков микросервисов от рутинных задач:

### Поддерживаемые протоколы
Современные API Gateway работают с различными протоколами на L7 уровне:
*   **HTTP/1.1:** Классический текстовый протокол. Используется по умолчанию для большинства REST API.
*   **HTTP/2:** Бинарный протокол с мультиплексированием потоков и сжатием заголовков (HPACK). Позволяет эффективнее использовать TCP-соединения и снижает latency.
*   **gRPC:** Высокопроизводительный RPC-протокол на базе HTTP/2 и Protocol Buffers. API Gateway обеспечивает маршрутизацию, балансировку и трассировку gRPC-вызовов.
*   **WebSocket:** Протокол для полноценного двустороннего общения. Шлюз поддерживает upgrade HTTP-соединения и маршрутизацию WS-фреймов.
*   **TCP/UDP (L4):** Некоторые шлюзы (например, Envoy Gateway через TCPRoute/UDPRoute) поддерживают транспортную маршрутизацию для не-HTTP протоколов.

### Маршрутизация и композиция
*   **Динамическая маршрутизация:** перенаправление на основе `Host`, `Path`, `Method` или специфичных заголовков (например, `X-API-Version`).
*   **API Composition (Агрегация):** шлюз может выполнить параллельные запросы к нескольким сервисам (например, `Service User` + `Service Orders`) и собрать единый JSON-ответ для мобильного клиента, экономя заряд батареи и время RTT.
*   **Версионирование API:** поддержка различных стратегий версионирования — через URL path (`/v1/`, `/v2/`), заголовки (`Accept: application/vnd.api.v2+json`) или query parameters (`?version=2`).
*   **Canary-развертывание:** постепенное перенаправление процента трафика на новую версию сервиса для тестирования в production.

### Алгоритмы балансировки нагрузки
API Gateway выбирает целевой экземпляр бэкенд-сервиса с помощью алгоритмов балансировки:
*   **Round Robin:** Поочередная отправка запросов на каждый экземпляр. Простой и предсказуемый.
*   **Least Connections:** Выбор экземпляра с наименьшим количеством активных соединений. Оптимален при разной обработке запросов.
*   **Weighted Round Robin:** Поочередная отправка с учетом весовых коэффициентов. Используется при разных мощностях серверов.
*   **IP Hash:** Хеширование IP-адреса клиента для привязки к конкретному экземпляру. Обеспечивает session affinity.
*   **Random:** Случайный выбор экземпляра. Эффективен при большом количестве серверов.
*   **Maglev:** Алгоритм Google для распределения нагрузки с минимальными потерями при изменении набора бэкендов.

### Безопасность и контроль доступа
*   **Централизованная аутентификация:** проверка JWT, OAuth2 токенов или сессий на периметре. Внутренние сервисы получают уже «очищенный» запрос с подтвержденным ID пользователя.
*   **WAF (Web Application Firewall):** защита от SQL-инъекций, XSS и других атак L7.
*   **Zero Trust Edge:** реализация принципа «никому не доверяй», где шлюз является единственной точкой, имеющей доступ к секретам для связи с бэкендами.
*   **mTLS (mutual TLS):** взаимная аутентификация клиента и сервера через сертификаты. Используется для связи шлюза с бэкендами и клиентской аутентификации.
*   **CSRF Protection:** защита от подделки межсайтовых запросов через валидацию заголовка `Origin`.

### Управление нагрузкой и отказоустойчивость
*   **Rate Limiting & Throttling:** ограничение количества запросов в секунду (RPS) для защиты от DDoS и недобросовестных потребителей.
*   **Circuit Breaker:** автоматическое «размыкание цепи» при обнаружении деградации бэкенда, чтобы предотвратить каскадные сбои.
*   **Retry Budget:** определение допустимого количества повторных попыток для предотвращения «шторма запросов» при сбоях.
*   **Admission Control:** контроль нагрузки на основе исторических данных об успешности запросов к бэкенду.
*   **Семантическое кэширование:** кэширование ответов не по точному совпадению строки, а по смысловой близости запросов.

### Алгоритмы Rate Limiting
*   **Token Bucket:** Алгоритм с фиксированной скоростью пополнения «ведра» токенов. Каждый запрос забирает токен; если токенов нет — запрос отклоняется. Гибкий, допускает всплески.
*   **Sliding Window Log:** Подсчет запросов в скользящем окне с хранением временных меток. Точный, но требует памяти.
*   **Sliding Window Counter:** Приближенный подсчет с весовым коэффициентом для текущего окна. Эффективен по памяти.
*   **Fixed Window:** Подсчет запросов в фиксированном интервале (например, минута). Простой, но может приводить к всплескам на границах окон.

### Наблюдаемость (Observability)
Шлюз является идеальным местом для сбора **Golden Signals**:
1.  **Latency:** время обработки запроса.
2.  **Traffic:** объем передаваемых данных и количество запросов.
3.  **Errors:** процент ответов 4xx/5xx.
4.  **Saturation:** загруженность ресурсов шлюза.
Интеграция с OpenTelemetry позволяет отслеживать путь запроса через всю систему (Distributed Tracing).

## Практические сценарии

### Backend for Frontend (BFF)
Создание специализированных шлюзов для разных типов потребителей.
*   *Пример:* Шлюз для мобильного приложения отдает сжатый JSON и минимум полей, а шлюз для Web-админки предоставляет полные данные и расширенные возможности фильтрации.
*   *Преимущества:* Оптимизация под конкретные клиенты, уменьшение количества запросов, улучшение UX.

### Паттерн «Фиговое дерево» (Strangler Fig)
Постепенная миграция с монолита на микросервисы.
*   *Сценарий:* Шлюз по умолчанию направляет весь трафик на монолит. По мере готовности новых микросервисов, правила маршрутизации в шлюзе меняются, перенаправляя отдельные эндпоинты (`/api/v1/orders`) на новые сервисы.
*   *Преимущества:* Минимальные риски, постепенная миграция, возможность отката.

### API Composition (Агрегация)
Шлюз выполняет параллельные запросы к нескольким сервисам и собирает единый ответ.
*   *Сценарий:* Мобильное приложение запрашивает профиль пользователя. Шлюз параллельно обращается к сервису пользователей, сервису заказов и сервису рекомендаций, собирая единый JSON.
*   *Преимущества:* Снижение количества запросов, экономия батареи мобильного устройства, уменьшение RTT.

### Rate Limiting для Multi-Tenant APIs
Ограничение использования API для разных клиентов с разными лимитами.
*   *Сценарий:* Бесплатные пользователи — 100 запросов в минуту, платные — 1000, enterprise — без ограничений.
*   *Реализация:* Использование `consumer` в Kong для привязки лимитов к конкретным потребителям.

### Canary-развертывание через API Gateway
Постепенное перенаправление трафика на новую версию сервиса.
*   *Сценарий:* 90% трафика идет на v1, 10% — на v2. По мере стабильности v2, процент увеличивается до 100%.
*   *Реализация:* Использование traffic splitting в Gateway API или weighted routing в Kong.

### API Versioning
Управление различными версиями API без нарушения обратной совместимости.
*   *Сценарий:* Клиенты используют API v1, но новые функции доступны только в v2. Шлюз маршрутизирует запросы на разные версии.
*   *Стратегии:* URL path versioning (`/v1/`, `/v2/`), header versioning (`Accept: application/vnd.api.v2+json`), query parameter versioning (`?version=2`).

### Integration Testing Environment
Создание тестовой среды с помощью API Gateway.
*   *Сценарий:* Шлюз маршрутизирует трафик на разные окружения (dev, staging, prod) в зависимости от заголовков или cookies.
*   *Реализация:* Использование header-based routing для переключения между окружениями.

### Circuit Breaker для Legacy Services
Защита от каскадных сбоев при работе с ненадежными legacy сервисами.
*   *Сценарий:* Legacy сервис время от времени отвечает с задержкой 30 секунд. Circuit Breaker автоматически перенаправляет трафик на fallback-сервис.
*   *Настройка:* Порог ошибок 50% за 30 секунд, timeout 5 секунд, half-open после 60 секунд.

## Практическая реализация

### Kong Gateway

Kong является одним из самых популярных решений в 2026 году благодаря своей производительности и расширяемости. Текущая версия — **3.15** (выпущена 14 июля 2026), LTS-версия — **3.14** (поддержка до апреля 2029).

#### Предварительные требования
*   Установленный Docker или Kubernetes-кластер.
*   Доступ к базе данных PostgreSQL (для режима с БД) или YAML-файл конфигурации (для DB-less режима).
*   Порты: 8000 (HTTP), 8443 (HTTPS), 8001 (Admin API).

#### Шаг 1: Установка (Docker)
Запуск Kong в DB-less режиме (наиболее простой для старта):
```bash
docker run -d --name kong-gateway \
     -e "KONG_DATABASE=off" \
     -e "KONG_PROXY_LISTEN=0.0.0.0:8000, 0.0.0.0:8443 ssl" \
     -e "KONG_ADMIN_LISTEN=0.0.0.0:8001" \
     -p 8000:8000 \
     -p 8443:8443 \
     -p 8001:8001 \
     kong:3.15
```
Для production рекомендуется использовать дистрибьютивный образ (distroless) на базе Wolfi для уменьшения attack surface:
```bash
docker run -d --name kong-gateway \
     -e "KONG_DATABASE=off" \
     -e "KONG_PROXY_LISTEN=0.0.0.0:8000, 0.0.0.0:8443 ssl" \
     -e "KONG_ADMIN_LISTEN=0.0.0.0:8001" \
     -p 8000:8000 \
     -p 8443:8443 \
     -p 8001:8001 \
     kong/kong-gateway:3.15-distroless
```

#### Шаг 2: Настройка сервиса и маршрута
Создание декларативной конфигурации `kong.yaml`:
```yaml
_format_version: "3.0"
services:
  - name: example-service
    url: http://httpbin.org
    connect_timeout: 5000
    write_timeout: 5000
    read_timeout: 5000
    retries: 5
    routes:
      - name: example-route
        paths:
          - /test
        strip_path: true
        preserve_host: false
```
Примените конфигурацию:
```bash
curl -i -X POST http://localhost:8001/config -F config=@kong.yaml
```

#### Шаг 3: Добавление плагина Rate Limiting
Ограничим доступ до 5 запросов в минуту:
```bash
curl -i -X POST http://localhost:8001/services/example-service/plugins \
    --data "name=rate-limiting" \
    --data "config.minute=5" \
    --data "config.policy=local" \
    --data "config.fault_tolerant=true" \
    --data "config.hide_client_headers=false"
```

#### Шаг 4: Добавление плагина аутентификации (Key Auth)
```bash
curl -i -X POST http://localhost:8001/services/example-service/plugins \
    --data "name=key-auth" \
    --data "config.key_names=apikey" \
    --data "config.hide_credentials=false"
```

#### Шаг 5: Создание потребителя и ключа
```bash
# Создание потребителя
curl -i -X POST http://localhost:8001/consumers \
    --data "username=example-user"

# Генерация API-ключа
curl -i -X POST http://localhost:8001/consumers/example-user/key-auth
```

#### Валидация
Проверьте работу маршрута, плагина rate limiting и аутентификации:
```bash
# Без API-ключа → 401 Unauthorized
curl -i http://localhost:8000/test

# С API-ключом → 200 OK
curl -i http://localhost:8000/test -H "apikey: YOUR_API_KEY"

# При превышении лимита → 429 Too Many Requests
for i in {1..6}; do curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8000/test -H "apikey: YOUR_API_KEY"; done
```

### Envoy Gateway

[Envoy Gateway](https://gateway.envoyproxy.io) — официальная CNCF-реализация Kubernetes Gateway API, построенная на базе Envoy Proxy. Текущая версия — **1.9.0** (выпущена 14 августа 2026).

#### Предварительные требования
*   Kubernetes-кластер (версия 1.27+).
*   Установленный `kubectl` и `helm`.
*   CRD Gateway API (v1.5+).

#### Шаг 1: Установка через Helm
```bash
# Добавление репозитория
helm repo add envoy-gateway https://gateway.envoyproxy.io
helm repo update

# Установка в системное пространство имён
helm install envoy-gateway oci://docker.io/envoyproxy/gateway-helm \
  --namespace envoy-gateway-system \
  --create-namespace \
  --version v1.9.0
```

#### Шаг 2: Создание GatewayClass
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: envoy-gateway
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
```

#### Шаг 3: Создание Gateway
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: production-gateway
  namespace: default
spec:
  gatewayClassName: envoy-gateway
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same
    - name: https
      protocol: HTTPS
      port: 443
      tls:
        mode: Terminate
        certificateRefs:
          - name: tls-secret
      allowedRoutes:
        namespaces:
          from: Same
```

#### Шаг 4: Создание HTTPRoute
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: example-route
  namespace: default
spec:
  parentRefs:
    - name: production-gateway
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api/v1
      backendRefs:
        - name: api-service
          port: 8080
      filters:
        - type: RequestHeaderModifier
          requestHeaderModifier:
            add:
              - name: X-Request-Source
                value: gateway
```

## Диагностика и устранение неисправностей

### Типичные коды ошибок
*   **400 Bad Request:** Невалидный синтаксис запроса. Проверьте формат JSON/XML и обязательные поля.
*   **401 Unauthorized:** Неверный или отсутствующий токен (проверьте плагины аутентификации и валидность ключа).
*   **403 Forbidden:** У токена недостаточно прав (проверьте ACL/RBAC и политики доступа).
*   **404 Not Found:** Маршрут не найден. Проверьте конфигурацию маршрутов и paths в шлюзе.
*   **408 Request Timeout:** Клиент не отправил запрос за отведенное время. Увеличьте `client_timeout` на стороне клиента или шлюза.
*   **413 Payload Too Large:** Тело запроса превышает допустимый размер. Увеличьте `client_max_body_size` или используйте стриминг.
*   **429 Too Many Requests:** Сработал лимит Rate Limiting. Проверьте политики и при необходимости увеличьте лимиты.
*   **500 Internal Server Error:** Внутренняя ошибка бэкенда. Проверьте логи целевого сервиса.
*   **502 Bad Gateway:** Шлюз не может связаться с бэкендом (проверьте [Service Discovery](./service-discovery-overview.md), health checks и сетевую доступность).
*   **503 Service Unavailable:** Бэкенд перегружен или недоступен. Проверьте scaling и Circuit Breaker.
*   **504 Gateway Timeout:** Бэкенд отвечает слишком долго (проверьте таймауты `connect_timeout`, `read_timeout`, `write_timeout`).

### Инструменты отладки
*   **Логи доступа:** Анализируйте `access.log` на наличие задержек (Latency) и кодов ответов. В Kong логи доступны через плагин `file-log` или `http-log`.
*   **Prometheus Metrics:** Отслеживайте ключевые метрики:
    *   `kong_http_status` / `envoy_http_downstream_rq_total` — общее количество запросов по кодам.
    *   `kong_upstream_target_health` / `envoy_cluster_health_check_healthy` — здоровье бэкендов.
    *   `kong_latency` / `envoy_http_downstream_service_time` — латентность обработки.
*   **Tracing:** Используйте Jaeger или Zipkin для визуализации прохождения запроса через шлюз в конкретный сервис.
*   **Envoy Proxy Admin Interface:** Для Envoy-based шлюзов доступен admin API ( порт 9901) для получения current config, stats и clusters:
    ```bash
    # Получение текущей конфигурации
    curl http://localhost:9901/config_dump

    # Получение статистики
    curl http://localhost:9901/stats

    # Проверка здоровья кластеров
    curl http://localhost:9901/clusters
    ```
*   **Kong Admin API:** Для Kong доступен admin API ( порт 8001) для проверки конфигурации и 상태:
    ```bash
    # Список сервисов
    curl http://localhost:8001/services

    # Список маршрутов
    curl http://localhost:8001/routes

    # Список плагинов
    curl http://localhost:8001/plugins

    # Статус шлюза
    curl http://localhost:8001/status
    ```

### Типичные проблемы и решения
*   **Проблема: Каскадные сбои**
    *   *Симптомы:* Один медленный бэкенд замедляет все запросы через шлюз.
    *   *Решение:* Включить Circuit Breaker и настроить таймауты. Проверить Retry Budget для предотвращения шторма запросов.
*   **Проблема: Утечка соединений**
    *   *Симптомы:* Постепенное увеличение количества active connections, исчерпание worker connections.
    *   *Решение:* Проверить keep-alive настройки, настроить max keep-alive requests и idle timeout.
*   **Проблема: Некорректная маршрутизация**
    *   *Симптомы:* Запросы попадают не на тот бэкенд.
    *   *Решение:* Проверить порядок правил (первое совпадение), использовать prefix matching вместо regex, проверить strip_path и preserve_host.

## Лучшие практики и ограничения

### Высокая доступность (HA)
*   **N+1 Резервирование:** Всегда запускайте минимум 2 инстанса Data Plane в разных зонах доступности.
*   **Внешний Load Balancer:** Используйте L4 балансировщик (например, HAProxy или Keepalived) перед группой инстансов API Gateway.
*   **Health Checks:** Настройте active health checks для обнаружения нездоровых экземпляров шлюза.
*   **Graceful Shutdown:** При обновлении шлюза используйте process draining для завершения активных соединений перед остановкой.

### Безопасность (Security Hardening)
*   **TLS Only:** Отключите HTTP на внешнем интерфейсе, используйте только HTTPS (порт 8443).
*   **Certificate Management:** Используйте автоматическую ротацию сертификатов (cert-manager, Let's Encrypt).
*   **Secrets Management:** Храните API-ключи и токены в vault (HashiCorp Vault, Kubernetes Secrets с шифрованием).
*   **Rate Limiting на нескольких уровнях:** Настройте глобальный (per-IP) и персональный (per-consumer) rate limiting.
*   **Audit Logging:** Включите логирование всех изменений конфигурации и попыток доступа.
*   **Regular Updates:** Обновляйте шлюз и его зависимости для исправления уязвимостей (CVE). Используйте LTS-версии для стабильности.

### Производительность
*   **Минимизация цепочек плагинов:** Каждый плагин вносит небольшую задержку. Используйте только необходимые.
*   **Кэширование на периметре:** Максимально используйте плагины кэширования для статических или редко меняющихся данных.
*   **HTTP/2 и gRPC:** Используйте бинарные протоколы для снижения overhead и улучшения multiplexing.
*   **Connection Pooling:** Настройте пул соединений с бэкендами для переиспользования TCP-соединений.
*   **Keep-Alive:** Включите keep-alive для снижения overhead установки соединений.

### Ограничения (Edge Cases)
*   **Payload Size:** Слишком большие тела запросов (например, загрузка видео) могут перегрузить память шлюза. Используйте стриминг или прямую загрузку в хранилище через предварительно подписанные URL.
*   **Large Context (AI):** При работе с LLM длинные контексты могут приводить к таймаутам на уровне шлюза. Увеличивайте `proxy_read_timeout` для AI-маршрутов.
*   **Webhook Delivery:** Шлюзы не гарантируют доставку webhook'ов. Для guaranteed delivery используйте очереди сообщений (Kafka, RabbitMQ).
*   **Long Polling:** При использовании long polling настройте соответствующие таймауты на шлюзе и бэкенде.

## Современные тренды (2026)

### Kubernetes Gateway API
Стандарт `Ingress` признан устаревшим. В 2026 году доминирует **Gateway API (v1.5+)**, который обеспечивает ролевую модель разделения ответственности между администраторами (ресурс `Gateway`) и разработчиками (ресурс `HTTPRoute`).

Основные преимущества Gateway API перед Ingress:
*   **Ролевая модель:** Четкое разделение ответственности между инфраструктурной командой (создание шлюзов) и командами разработки (создание маршрутов).
*   **Универсальность:** Поддержка HTTP, gRPC, TCP и UDP маршрутизации через стандартные CRD.
*   **Портативность:** Стандартная спецификация, поддерживаемая различными implementers (Envoy Gateway, Kong, Traefik, Cilium).
*   **Политики:** Механизм policy attachment для настройки безопасности, rate limiting и других аспектов.
*   **Namespaced:** Маршруты привязаны к пространствам имён, обеспечивая изоляцию между командами.

### WebAssembly (WASM) плагины
Расширение функционала шлюзов без перезагрузки. WASM обеспечивает:
*   **Безопасность:** Изоляция плагинов в sandbox-окружении.
*   **Производительность:** Близка к нативному коду.
*   **Портативность:** Один плагин работает на разных платформах (Envoy, HAProxy, Traefik).
*   **Языки:** Поддержка Go, Rust, C/C++, AssemblyScript.

### GitOps для конфигурации шлюзов
Управление конфигурацией API Gateway через Git:
*   **ArgoCD/Flux:** Автоматическая синхронизация конфигурации из Git в Kubernetes.
*   **Декларативность:** Все изменения описываются в YAML-файлах и версионируются.
*   **Review process:** Изменения проходят code review перед применением.
*   **Rollback:** Быстрый откат к предыдущей версии конфигурации.

### Distributed Tracing и OpenTelemetry
Интеграция с OpenTelemetry для полной наблюдаемости:
*   **Context Propagation:** Передача trace context через HTTP-заголовки.
*   **Span Attributes:** Добавление метаданных шлюза (route, service, consumer) в трассировки.
*   **Sampling:** Стратегии семплирования для снижения overhead.

### Infrastructure as Code (IaC)
Управление инфраструктурой API Gateway через код:
*   **Terraform/Pulumi:** Программное создание и управление ресурсами шлюзов.
*   **Ansible/Chef:** Автоматизация настройки и конфигурации шлюзов в bare-metal средах.
*   **Immutable Infrastructure:** Создание новых образов шлюза вместо изменения существующих.
