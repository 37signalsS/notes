# Инструменты управления конфигурацией — Обзор

## Определения

**Инструменты управления конфигурацией** (Configuration Management Tools, далее — CM) — программное обеспечение для автоматизации процесса приведения систем к желаемому состоянию и поддержания этого состояния. Решают задачи установки программного обеспечения (ПО), настройки сервисов, управления пользователями, файлами конфигурации и секретами на множестве серверов.

### Ключевые принципы
*   **Идемпотентность (Idempotency):** Ключевое свойство CM-инструментов. Гарантирует, что повторный запуск конфигурации на уже настроенной системе не приведет к изменениям или ошибкам. Это позволяет безопасно запускать автоматизацию неограниченное количество раз.
*   **Дрифт конфигурации (Configuration Drift):** Постепенное отклонение реального состояния сервера от описанного в коде из-за ручных правок. CM-инструменты призваны обнаруживать и исправлять такой дрифт.
*   **Инфраструктура как код (IaC):** Подход, при котором конфигурация описывается в виде текстовых файлов, что позволяет использовать системы контроля версий (Git) для управления изменениями.

Более широкий контекст: [модели управления конфигурацией](./configuration_management_models.md), [Инфраструктура как код (Infrastructure as Code, IaC)](./iac_overview.md).

## Базовые концепции

### Классификация инструментов

Инструменты CM различаются по нескольким ключевым характеристикам:

| Критерий | Описание | Примеры |
| :--- | :--- | :--- |
| **Архитектура** | Agentless (без агентов) vs Agent-based (с агентами) | Ansible (agentless), Puppet/Chef (agent-based) |
| **Модель доставки** | Push (контроллер инициирует) vs Pull (агент запрашивает) | Ansible (push), Puppet (pull), SaltStack (оба) |
| **Язык описания** | YAML, Ruby, **DSL (Domain Specific Language — предметно-ориентированный язык)**, Python | Ansible (YAML), Puppet (Puppet DSL), Chef (Ruby DSL) |
| **Парадигма** | Декларативная vs Императивная | Ansible (процедурно-декларативная), Puppet (декларативная) |

## Основные представители

### Ansible

**Ansible** — система управления конфигурациями с открытым исходным кодом (Red Hat / IBM). Работает без агентов, использует **SSH (Secure Shell)** для подключения к управляемым узлам и Python для выполнения модулей.

- **Архитектура:** Agentless (без агентов), Push-модель (есть режим Ansible Pull).
- **Язык:** **YAML (YAML Ain't Markup Language)** (плейбуки) + Jinja2 (шаблоны).
- **Парадигма:** Процедурно-декларативная (плейбук — упорядоченный список задач, каждый модуль идемпотентен).
- **Управление состоянием:** Stateless (не хранит состояние, собирает факты при каждом запуске).
- **Порог входа:** Низкий — достаточно знания YAML и SSH.
- **Экосистема:** Огромное сообщество, тысячи модулей, Ansible Galaxy для обмена ролями.
- **Специфика (2025-2026):** Стандартом является использование **FQCN (Fully Qualified Collection Name)**, например `ansible.builtin.copy` вместо `copy`. Это обеспечивает бесконфликтность модулей из разных коллекций.
- **Применение:** Управление конфигурацией, оркестрация развертываний, подготовка инфраструктуры (provisioning).

Подробная документация: [Ansible: Введение](../Ansible/ansible_introduction.md), [Основные концепции](../Ansible/ansible_core_concepts.md).

### Puppet

**Puppet** — зрелая система управления конфигурациями (Perforce). Работает по модели Pull с агентом на каждом узле, использует декларативный язык на основе Ruby DSL.

- **Архитектура:** Agent-based (с агентами), Pull-модель (есть Push через Bolt).
- **Язык:** Puppet DSL (декларативный, на основе Ruby).
- **Парадигма:** Декларативная — описывается конечное состояние ресурсов.
- **Управление состоянием:** Stateful — Puppet Master хранит каталог конфигураций.
- **Порог входа:** Средний/высокий — требуется изучение DSL и **инфраструктуры открытых ключей (Public Key Infrastructure, PKI)**.
- **Экосистема:** Puppet Forge (готовые модули), сильная корпоративная поддержка.
- **Применение:** Управление большим парком серверов, аудит соответствия (compliance), поддержание стандартов и борьба с дрифтом.

**Пример манифеста:**

```puppet
# site.pp — декларативное описание состояния
package { 'nginx':
  ensure => installed,
}

service { 'nginx':
  ensure  => running,
  enable  => true,
  require => Package['nginx'],
}
```

### Chef

**Chef** — система управления конфигурациями (Progress). Использует подход IaC с Ruby DSL для описания рецептов и поваренных книг (cookbooks).

- **Архитектура:** Agent-based, Pull-модель (есть Push через Chef Push Jobs).
- **Язык:** Ruby DSL (императивно-декларативный).
- **Парадигма:** Смешанная — рецепты выполняются последовательно, но ресурсы внутри идемпотентны.
- **Управление состоянием:** Stateful — Chef Server хранит данные об узлах и книгах (cookbooks).
- **Порог входа:** Высокий — требуется знание Ruby.
- **Экосистема:** Chef Supermarket, сильная интеграция с облачными провайдерами.
- **Применение:** Управление сложной инфраструктурой, автоматизация соответствия (compliance), конвейеры **CI/CD (Continuous Integration / Continuous Deployment)**.

**Пример рецепта:**

```ruby
# recipe.rb
package 'nginx' do
  action :install
end

service 'nginx' do
  action [:enable, :start]
end
```

### SaltStack (Salt)

**SaltStack** — система управления конфигурациями и оркестрации, принадлежащая **Broadcom** (после поглощения VMware). Поддерживает как Push, так и Pull модели, использует ZeroMQ для высокоскоростной коммуникации.

- **Архитектура:** Master-Minion (agent-based) или Masterless (agentless через SSH).
- **Язык:** YAML (SLS-файлы, Salt State File) + Jinja2 + Python.
- **Парадигма:** Декларативная (highstate) + императивная (execution modules).
- **Управление состоянием:** Stateful (хранит состояние миньонов) + событийная шина (Event Bus).
- **Порог входа:** Средний — YAML для простых задач, Python для сложной логики.
- **Экосистема:** Активная поддержка сетевого оборудования и облачных платформ. Актуальная ветка в 2026 году — **Salt 3008 LTS**.
- **Применение:** Оркестрация масштабных развертываний, событийная автоматизация (event-driven), управление контейнерами и IoT.

Архитектура и концепции: [SaltStack: Архитектура](../SaltStack/Architecture.md), [Highstate](../SaltStack/Highstate_and_Execution_Order.md).

### CFEngine

**CFEngine** — одна из старейших систем управления конфигурациями (Northern.tech). Разработана для автономной работы в больших масштабах с минимальным потреблением ресурсов.

- **Архитектура:** Agent-based, Pull-модель.
- **Язык:** Промисы (Promises) — собственный декларативный язык.
- **Парадигма:** Декларативная — описываются «обещания» (promises) желаемого состояния.
- **Управление состоянием:** Полностью автономный агент, работает без постоянного соединения с сервером.
- **Порог входа:** Высокий — специфичная терминология и модель.
- **Применение:** Крупные корпоративные инфраструктуры, системы с жесткими требованиями к надежности (embedded, edge).

## Прочие инструменты

| Инструмент | Особенности | Применение |
| :--- | :--- | :--- |
| **Fabric** | Python-библиотека для SSH-оркестрации, императивный подход | Быстрые скрипты развертывания, администрирование |
| **Rudder** | **Графический интерфейс пользователя (Graphical User Interface, GUI)**, основан на CFEngine | Средние компании, аудит соответствия (compliance) |
| **Ansible Semaphore** | Open-source GUI для Ansible | Команды, нуждающиеся в визуальном управлении задачами и RBAC |
| **Pulumi** | IaC на общих языках программирования (Python, TypeScript, Go) | Мультиоблачные развертывания, разработка инфраструктуры |
| **Crossplane** | Управление ресурсами через API Kubernetes | K8s-native Infrastructure Management, превращение K8s в Control Plane |

## Практические сценарии

### Выбор инструмента

| Сценарий | Рекомендуемый инструмент | Обоснование |
| :--- | :--- | :--- |
| **Небольшая инфраструктура, быстрый старт** | Ansible | Низкий порог входа, отсутствие агентов, YAML |
| **Огромный парк серверов (>5000), compliance** | Puppet | Pull-модель с автоматической коррекцией отклонений (drift) |
| **Сложная логика настройки, команда Ruby-разработчиков** | Chef | Мощь полноценного Ruby DSL |
| **Событийная оркестрация, высокая скорость** | SaltStack | Событийная шина, ZeroMQ для мгновенного выполнения |
| **Автономные системы (Edge, IoT)** | CFEngine | Минимальные ресурсы, работа без центрального сервера |

### Комбинирование инструментов и гибридные подходы

На практике часто используется сочетание различных инструментов для оптимизации жизненного цикла инфраструктуры:

1.  **Provisioning + Configuration:** **Terraform** или **OpenTofu** (создание ресурсов) + **Ansible** (финальная настройка ПО).
2.  **Mutable vs Immutable:** Создание базовых образов (Golden Images) с помощью **Packer** и **Ansible**, с последующим развертыванием в неизменяемой (Immutable) среде.
3.  **Bootstrap + Compliance:** **Ansible** используется для начальной настройки (bootstrap) и установки агентов **Puppet**, которые далее следят за соблюдением стандартов.
4.  **Orchestration:** **SaltStack** управляет высокоуровневой оркестрацией и реакцией на события, используя **Salt states** для приведения узлов к состоянию.

Подробнее о взаимодействии инструментов: [IaC обзор — Terraform vs Ansible](./iac_overview.md#сравнение-инструментов-terraform-vs-ansible).

## Дополнительная информация

### Сравнение с неизменяемой инфраструктурой (Immutable Infrastructure)

Современный подход часто предполагает отказ от изменения конфигурации работающих серверов в пользу полной замены инстансов.

*   **Mutable (CM):** Мы меняем конфиг на лету (Ansible, Puppet). Плюс: скорость правок. Минус: дрифт конфигурации, сложность отката.
*   **Immutable:** Мы собираем новый образ (Docker, AMI) и заменяем старый сервер. Плюс: предсказуемость, легкий откат, отсутствие дрифта. Минус: время на сборку и передеплой.

### Эволюция инструментов управления конфигурацией

| Период | Событие |
| :--- | :--- |
| **1993** | Появление CFEngine — рождение концепции «обещаний» (promises) и идемпотентности |
| **2005** | Релиз Puppet — популяризация декларативного подхода в Open Source |
| **2009** | Релиз Chef — начало эпохи Infrastructure as Code |
| **2011** | Релиз SaltStack — фокус на скорость, событийность и шину ZeroMQ |
| **2012** | Релиз Ansible — успех благодаря простоте, YAML и agentless-архитектуре |
| **2015** | Red Hat приобретает Ansible |
| **2020+** | Смещение к GitOps (ArgoCD, Flux) и Kubernetes операторам |
| **2023** | Broadcom завершает покупку VMware (включая SaltStack) |
| **2024-2026** | Интеграция AI-ассистентов в CM-инструменты для автоматической генерации и валидации конфигураций |

### Тренды и направления развития

-   **GitOps:** Дальнейшая эволюция модели Pull. Git становится единственным источником правды, а специализированные операторы (ArgoCD) синхронизируют состояние.
-   **Kubernetes Operators:** В контейнерных средах традиционные CM заменяются операторами, которые управляют Custom Resources (CRD).
-   **Policy as Code:** Автоматическая проверка конфигураций на соответствие безопасности (Security Compliance) с помощью **Open Policy Agent (OPA)** или HashiCorp Sentinel.
-   **Secrets Management:** Глубокая интеграция с внешними хранилищами секретов (HashiCorp Vault, AWS Secrets Manager) вместо локального хранения (Ansible Vault).
-   **Crossplane:** Управление облачной инфраструктурой через API Kubernetes, что делает K8s универсальным инструментом управления. Подробнее: [Обзор Crossplane](../GitOps/Crossplane/overview.md).
