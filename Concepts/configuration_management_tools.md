# Инструменты управления конфигурацией (Configuration Management Tools)

## Определения

**Инструменты управления конфигурацией (Configuration Management Tools)** — программное обеспечение для автоматизации процесса приведения систем к желаемому состоянию и поддержания этого состояния. Решают задачи установки ПО, настройки сервисов, управления пользователями, файлами конфигурации и секретами на множестве серверов.

Более широкий контекст: [модели управления конфигурацией](./configuration_management_models.md), [инфраструктура как код](./iac_overview.md).

## Базовые концепции

### Классификация инструментов

Инструменты CM различаются по нескольким ключевым характеристикам:

| Критерий | Описание | Примеры |
| :--- | :--- | :--- |
| **Архитектура** | Agentless (без агентов) vs Agent-based (с агентами) | Ansible (agentless), Puppet/Chef (agent-based) |
| **Модель доставки** | Push (контроллер инициирует) vs Pull (агент запрашивает) | Ansible (push), Puppet (pull), SaltStack (оба) |
| **Язык описания** | YAML, Ruby, DSL, Python | Ansible (YAML), Puppet (Ruby DSL), Chef (Ruby DSL) |
| **Парадигма** | Декларативная vs Императивная | Ansible (процедурно-декларативная), Puppet (декларативная) |

### Основные представители

#### Ansible

**Ansible** — система управления конфигурациями с открытым исходным кодом (Red Hat). Работает без агентов, использует SSH для подключения к управляемым узлам и Python для выполнения модулей.

- **Архитектура:** Agentless, Push-модель (есть режим Ansible Pull)
- **Язык:** YAML (плейбуки) + Jinja2 (шаблоны)
- **Парадигма:** Процедурно-декларативная (плейбук — упорядоченный список задач, каждый модуль идемпотентен)
- **Управление состоянием:** Stateless (не хранит состояние, собирает факты при каждом запуске)
- **Порог входа:** Низкий — достаточно знания YAML и SSH
- **Экосистема:** Огромное сообщество, тысячи модулей, Ansible Galaxy для обмена ролями
- **Применение:** Управление конфигурацией, оркестрация развертываний, provisioning (ограниченно)

Подробная документация: [Ansible Introduction](../Ansible/ansible_introduction.md), [основные концепции](../Ansible/ansible_core_concepts.md)

#### Puppet

**Puppet** — зрелая система управления конфигурациями (Perforce). Работает по модели Pull с агентом на каждом узле, использует декларативный язык на основе Ruby DSL.

- **Архитектура:** Agent-based, Pull-модель (есть Push через Bolt)
- **Язык:** Puppet DSL (декларативный, на основе Ruby)
- **Парадигма:** Декларативная — описывается конечное состояние ресурсов
- **Управление состоянием:** Stateful — Puppet Master хранит каталог конфигураций
- **Порог входа:** Средний/высокий — требуется изучение DSL и PKI-инфраструктуры
- **Экосистема:** Puppet Forge (тысячи готовых модулей), сильная enterprise-поддержка
- **Применение:** Управление большим парком серверов, compliance-аудит, поддержание стандартов

**Типичный манифест:**

```puppet
# site.pp — декларативное описание состояния
package { 'nginx':
  ensure => installed,
}

service { 'nginx':
  ensure  => running,
  enable  => true,
  require => Package['nginx'],
}
```

#### Chef

**Chef** — система управления конфигурациями (Progress). Использует подход «Infrastructure as Code» с Ruby DSL для описания рецептов и поварённых книг (cookbooks).

- **Архитектура:** Agent-based, Pull-модель (есть Push через Chef Push Jobs)
- **Язык:** Ruby DSL (императивно-декларативный)
- **Парадигма:** Смешанная — рецепты выполняются последовательно, но ресурсы внутри идемпотентны
- **Управление состоянием:** Stateful — Chef Server хранит данные о нодах и cookbook'ах
- **Порог входа:** Высокий — требуется знание Ruby
- **Экосистема:** Supermarket (cookbook'и), сильная интеграция с облачными провайдерами
- **Применение:** Управление сложной инфраструктурой, автоматизация compliance, CI/CD-пайплайны

**Типичный рецепт:**

```ruby
# recipe.rb
package 'nginx' do
  action :install
end

service 'nginx' do
  action [:enable, :start]
end
```

#### SaltStack (Salt)

**SaltStack** — система управления конфигурациями и оркестрации (VMware). Поддерживает как Push, так и Pull модели, использует ZeroMQ для высокоскоростной коммуникации.

- **Архитектура:** Master-Minion (agent-based) или Masterless (agentless через SSH)
- **Язык:** YAML (SLS-файлы) + Jinja2 + Python
- **Парадигма:** Декларативная (highstate) + императивная (execution modules)
- **Управление состоянием:** Stateful (хранит состояние миньонов) + событийная шина
- **Порог входа:** Средний — YAML для простых задач, Python для сложной логики
- **Экосистема:** Интеграция с VMware, модули для облачных платформ
- **Применение:** Оркестрация大规模 развертываний, event-driven автоматизация, управление контейнерами

Архитектура и концепции: [SaltStack Architecture](../SaltStack/Architecture.md), [Highstate](../SaltStack/Highstate_and_Execution_Order.md)

#### CFEngine

**CFEngine** — одна из старейших систем управления конфигурациями (коммерческая и open-source). Разработана для автономной работы в больших масштабах с минимальным потреблением ресурсов.

- **Архитектура:** Agent-based, Pull-модель
- **Язык:** Промисы (Promises) — собственный декларативный язык
- **Парадигма:** Декларативная — описываются «обещания» желаемого состояния
- **Управление состоянием:** Полностью автономный агент, работает без постоянного соединения с сервером
- **Порог входа:** Высокий — специфичная терминология и модель
- **Применение:** Крупные enterprise-инфраструктуры, системы с жёсткими требованиями к надёжности

#### Другие инструменты

| Инструмент | Особенности | Применение |
| :--- | :--- | :--- |
| **Fabric** | Python-библиотека для SSH-оркестрации, императивный подход | Быстрые скрипты развертывания, администрирование |
| **Rudder** | Web-интерфейс, основан на CFEngine, compliance-focused | Средние компании, compliance-аудит |
| **Ansible Semaphore** | Web-UI для Ansible с управлением задачами и аудитом | Команды, нуждающиеся в GUI для Ansible |
| **Pulumi** | IaC на общих языках (Python, TypeScript, Go), декларативный | Мультиоблачные развертывания, разработчики |

## Практические сценарии

### Выбор инструмента

| Сценарий | Рекомендуемый инструмент | Обоснование |
| :--- | :--- | :--- |
| **Небольшая инфраструктура, быстрое развертывание** | Ansible | Низкий порог входа, agentless, YAML |
| **Большой парк серверов, постоянный compliance** | Puppet | Pull-модель с автоматической коррекцией дрейфа |
| **Сложная логика, разработчики знают Ruby** | Chef | Гибкость Ruby DSL, мощные cookbook'и |
| **Event-driven оркестрация, высокая скорость** | SaltStack | Событийная шина, ZeroMQ для массовой рассылки |
| **Enterprise, автономная работа агентов** | CFEngine | Надёжность, минимальное потребление ресурсов |
| **Команда Python-разработчиков** | Fabric | Прямое управление через SSH-скрипты |

### Комбинирование инструментов

На практике часто используется несколько инструментов совместно:

1. **Terraform** (provisioning инфраструктуры) + **Ansible** (настройка ПО на созданных серверах)
2. **Ansible** (bootstrap серверов) → **Puppet** (постоянное управление конфигурацией)
3. **SaltStack** (оркестрация) + **Salt states** (управление конфигурацией)

Подробнее о взаимодействии инструментов: [IaC обзор — Terraform vs Ansible](./iac_overview.md#сравнение-инструментов-terraform-vs-ansible)

## Дополнительная информация

### Эволюция инструментов CM

| Год | Событие |
| :--- | :--- |
| 2005 | CFEngine 2 — одна из первых систем CM |
| 2005 | Puppet 1.0 — популяризация declarative approach |
| 2009 | Chef 1.0 — Infrastructure as Code с Ruby DSL |
| 2012 | Ansible 1.0 — agentless революция, YAML |
| 2011 | SaltStack 1.0 — event-driven архитектура, высокая скорость |
| 2014 | Red Hat приобретает Ansible |
| 2020+ | Смещение к GitOps и Kubernetes операторам для CM в контейнерных средах |

### Тренды и направление развития

- **GitOps:** Управление конфигурацией через Git-репозитории с автоматическим применением изменений (ArgoCD, Flux для Kubernetes)
- **Kubernetes Operators:** CM для контейнерных сред через декларативные Custom Resources
- **Policy as Code:** Проверка compliance через код (OPA, HashiCorp Sentinel)
- **Immutable Infrastructure:** Переход от CM к созданию новых образов вместо изменения существующих серверов (Packer, Docker)
