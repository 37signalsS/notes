# Stateful vs Stateless

## Определения

**Stateful (состояний)** — приложение или сервис, которое хранит состояние (данные, сессию, контекст) между запросами. Состояние может храниться в памяти, на диске или во внешнем хранилище.

**Stateless (без состояния)** — приложение или сервис, которое не хранит состояние между запросами. Каждый запрос обрабатывается независимо и содержит всю необходимую информацию для выполнения.

## Базовые концепции

### Ключевые различия

| Критерий | Stateless | Stateful |
| :--- | :--- | :--- |
| **Хранение состояния** | Не хранит между запросами | Сохраняет состояние между запросами |
| **Масштабирование** | Горизонтальное — простое, любой экземпляр обрабатывает запрос | Требует синхронизации состояния или sticky sessions |
| **Отказоустойчивость** | Отказ экземпляра не влияет на сессию | Требуется репликация состояния для failover |
| **Идентификация** | Экземпляры взаимозаменяемы | Требуется стабильная идентификация экземпляров |
| **Хранилище** | Общее (RWX) или временное | Персистентное, привязанное к экземпляру (RWO) |
| **Примеры** | Веб-серверы, API-шлюзы, функции | Базы данных, брокеры сообщений, кэши |

### Stateless-архитектура

**Принципы:**

1. **Независимость запросов** — каждый запрос содержит полный контекст
2. **Взаимозаменяемость экземпляров** — любой сервер может обработать запрос
3. **Внешнее хранение состояния** — сессии, кэш, данные выносятся во внешние сервисы

**Преимущества:**

- Простое горизонтальное масштабирование
- Высокая отказоустойчивость
- Упрощенное развертывание и обновления

**Недостатки:**

- Избыточность данных в запросах
- Требуется внешняя система для хранения сессий
- Дополнительные сетевые вызовы к хранилищам состояния

**Механизмы эмуляции состояния:**

- [Cookies](../Networking/Protocols/HTTP/http_authentication.md#cookies) — хранение сессии на клиенте
- **Токены (JWT, OAuth)** — передача контекста в заголовках
- **Внешние хранилища сессий** — Redis, Memcached

### Stateful-архитектура

**Принципы:**

1. **Сохранение контекста** — приложение помнит предыдущие взаимодействия
2. **Стабильная идентификация** — каждый экземпляр уникален и идентифицируем
3. **Привязка хранилища** — данные закреплены за конкретным экземпляром

**Преимущества:**

- Производительность (данные локальны)
- Упрощенная логика (состояние доступно в памяти)
- Поддержка транзакций и консистентности

**Недостатки:**

- Сложное масштабирование (требуется синхронизация)
- Риск потери данных при сбое
- Требует механизмов репликации и восстановления

**Типичные представители:**

- Базы данных (PostgreSQL, MySQL, MongoDB)
- Брокеры сообщений (Kafka, RabbitMQ)
- Распределённые координаторы (ZooKeeper, etcd, Consul)
- Кэши с персистентностью (Redis)

## Практические сценарии

### Kubernetes: Deployment vs StatefulSet

В Kubernetes концепция stateful/stateless реализуется через контроллеры [Deployment](../Kubernetes/Base/Deployment/index.md) (stateless) и [StatefulSet](../Kubernetes/Base/StatefulSet/statefulset_core_concepts.md) (stateful).

**Deployment** управляет stateless-приложениями: поды взаимозаменяемы, имеют случайные имена и IP, используют общее хранилище (RWX) или временное.

**StatefulSet** управляет stateful-приложениями: поды получают стабильные имена (`app-0`, `app-1`), уникальные DNS-записи через [Headless Service](../Kubernetes/Networking/Service/service_type_headless.md), индивидуальное персистентное хранилище (RWO), упорядоченное развертывание.

> Подробное сравнение: **[StatefulSet vs Deployment](../Kubernetes/Base/StatefulSet/statefulset_vs_deployment.md)**

### Сетевая фильтрация: Stateless vs Stateful Firewall

В сетевой безопасности применяется [stateful-фильтрация](../Networking/Concepts/firewall_concepts.md#stateless-vs-stateful-фильтрация) — отслеживание состояния соединений (`NEW`, `ESTABLISHED`, `RELATED`, `INVALID`) через таблицу `conntrack`. Stateful-файрволы обеспечивают более высокий уровень безопасности по сравнению со stateless.

> Детально: **[Концепции файрволов](../Networking/Concepts/firewall_concepts.md)**

### HTTP-протокол

[HTTP](../Networking/Protocols/HTTP/http_basics.md) — stateless-протокол: каждый запрос независим, сервер не хранит информацию о предыдущих запросах. Для эмуляции состояния используются [Cookies](../Networking/Protocols/HTTP/http_authentication.md#cookies), заголовки авторизации (Bearer, JWT), [токены](../Networking/Protocols/HTTP/http_basics.md#stateless-протокол).

> Подробнее: **[HTTP Basics](../Networking/Protocols/HTTP/http_basics.md)**

### IaC: Terraform vs Ansible

В Infrastructure as Code: [Terraform](iac_overview.md) использует stateful-подход (state file для хранения соответствия ресурсов), [Ansible](iac_overview.md) — stateless (сбор фактов при каждом запуске).

> Сравнение: **[IaC Overview](iac_overview.md#сравнение-инструментов-terraform-vs-ansible)**

### Высокая доступность

Шаблоны кластеризации: **Active-Active** для stateless-сервисов (все узлы обрабатывают трафик), **Active-Passive** для stateful-сервисов (один узел активен, остальные в резерве).

> Детали: **[HA Clustering](High_Availability/ha_clustering_and_load_balancing.md)**

### Микросервисы: масштабирование

В микросервисной архитектуре stateless-сервисы масштабируются горизонтально простым добавлением экземпляров. Stateful-сервисы требуют синхронизации состояния, механизмов консистентности, шардирования или репликации.

> Контекст: **[Monolith vs Microservices](monolith_vs_microservices.md)**

## Дополнительная информация

### Выбор архитектуры

**Stateless предпочтительно когда:**

- Требуется простое горизонтальное масштабирование
- Важна высокая доступность без сложной репликации
- Состояние можно вынести во внешние сервисы (БД, кэш)

**Stateful необходимо когда:**

- Требуется низкая задержка (данные локальны)
- Приложение по природе сохраняет состояние (БД, очереди)
- Транзакционная целостность критична

### Паттерны работы с состоянием

1. **Externalization** — вынос состояния во внешние хранилища (Redis, БД)
2. **Replication** — репликация состояния между экземплярами
3. **Sharding** — разделение состояния по экземплярам (шардам)
4. **Sticky Sessions** — привязка клиента к конкретному экземпляру
