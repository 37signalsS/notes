# Сравнение Stateful и Stateless архитектур

## Определения

**Stateful (с состоянием)** — архитектурный подход, при котором приложение или сервис сохраняет контекст взаимодействия (состояние, сессии, данные) между последовательными запросами. Состояние может храниться в оперативной памяти, на локальном диске или в специализированных хранилищах.

**Stateless (без состояния)** — подход, при котором сервис не хранит никакой информации о предыдущих взаимодействиях. Каждый запрос обрабатывается как независимая транзакция, содержащая весь необходимый контекст для выполнения операции.

## Базовые концепции

### Ключевые различия

| Критерий | Stateless | Stateful |
| :--- | :--- | :--- |
| **Хранение данных** | Во внешних системах (БД, кэш) | Локально (память, диск) или репликация |
| **Масштабирование** | Горизонтальное (простое) | Сложное (требует координации) |
| **Отказоустойчивость** | Высокая (узлы взаимозаменяемы) | Требует механизмов failover и восстановления |
| **Идентификация узлов** | Эфемерная (случайные имена/IP) | Стабильная (уникальные ID, DNS-имена) |
| **Тип хранилища** | Общее (RWX) или временное | Персистентное (RWO) |

### Принципы Stateless-архитектуры

Методология **12-Factor App** (фактор VI) предписывает запускать приложение как один или несколько процессов без состояния. 
*   **Взаимозаменяемость:** любой экземпляр сервиса может обработать любой входящий запрос.
*   **Внешнее хранилище:** данные сессий выносятся в распределенные хранилища (Redis, Memcached).
*   **Токены (JWT):** контекст авторизации передается внутри самого запроса, избавляя сервер от необходимости помнить клиента.

**Преимущества:**
*   Мгновенное горизонтальное масштабирование.
*   Упрощенное обновление (Rolling Update) без риска потери данных.
*   Идеально подходит для Cloud Native и Serverless сред.

### Принципы Stateful-архитектуры

Необходима для систем, чья основная задача — управление данными и обеспечение их консистентности.
*   **Стабильность:** узлы имеют фиксированную идентичность, что критично для алгоритмов консенсуса (Raft, Paxos).
*   **Локальность данных:** хранение состояния в памяти или на быстрых локальных дисках минимизирует сетевые задержки.

**Типичные представители:**
*   Системы управления базами данных (PostgreSQL, MongoDB).
*   Брокеры сообщений (Kafka, RabbitMQ).
*   Распределенные координаторы (etcd, Consul).

## Практические сценарии

### Kubernetes: Deployment vs StatefulSet

В Kubernetes разделение на stateless/stateful закреплено на уровне контроллеров:
*   **[Deployment](../Kubernetes/Base/Deployment/index.md):** управляет stateless-подами. Поды эфемерны, используют общее сетевое хранилище (RWX) или не используют его вовсе.
*   **[StatefulSet](../Kubernetes/Base/StatefulSet/statefulset_core_concepts.md):** управляет stateful-подами. Обеспечивает стабильные сетевые идентификаторы (`pod-0`, `pod-1`) и привязку персональных томов (Persistent Volume) через механизм **Volume Claim Templates**.

> Детальное сравнение: **[StatefulSet vs Deployment](../Kubernetes/Base/StatefulSet/statefulset_vs_deployment.md)**.

### Сетевая безопасность (Firewall)

*   **Stateless Firewall:** фильтрует каждый пакет отдельно на основе ACL (Access Control List). Не видит связи между пакетами одного соединения.
*   **Stateful Firewall:** отслеживает состояние соединений через таблицу **conntrack**. Позволяет автоматически пропускать ответный трафик для установленных (ESTABLISHED) сессий.

> Подробнее: **[Концепции файрволов](../Networking/Concepts/firewall_concepts.md)**.

### Управление инфраструктурой (IaC)

*   **Ansible:** работает по модели stateless. Не хранит информацию о предыдущих запусках, собирает факты о системе в реальном времени.
*   **Terraform:** stateful-инструмент. Использует **state file** (`.tfstate`) как единственный источник правды для отслеживания созданных ресурсов и их параметров.

> См. также: **[Обзор IaC](./iac_overview.md)**.

## Дополнительная информация

### Паттерны перехода к Stateless

1.  **Session Externalization:** перенос данных пользовательских сессий из памяти приложения в Redis.
2.  **Sidecar Offloading:** использование sidecar-контейнеров (например, Envoy в Service Mesh) для обработки сетевого состояния (retry, mTLS) вне кода приложения.
3.  **Sticky Sessions (Session Affinity):** временная мера на уровне балансировщика L7 для привязки клиента к узлу, если приложение еще не готово к полной stateless-модели.
