# Модели управления конфигурацией — Теоретический обзор

## Определения

**Управление конфигурацией** (Configuration Management, далее — CM) — это системный процесс приведения и поддержания систем, программного обеспечения (ПО) и серверов в заранее определенном, желаемом состоянии. CM автоматизирует процессы настройки и развертывания, обеспечивая консистентность, воспроизводимость и надежность инфраструктуры.

### Основные термины
*   **Желаемое состояние (Desired State):** Описание того, как система должна выглядеть (какие пакеты установлены, какие службы запущены, какие права доступа настроены).
*   **Текущее состояние (Actual State):** Реальное состояние системы в данный момент времени, полученное путем инспекции (facts gathering).
*   **Цикл сверки (Reconciliation Loop):** Непрерывный или периодический процесс сравнения *желаемого* и *текущего* состояний с последующим применением корректирующих действий.

Обзор доступных инструментов: [Инструменты управления конфигурацией](./configuration_management_tools.md).

## Базовые концепции

### Императивная и Декларативная модели

Существуют две фундаментальные парадигмы описания конфигурации:

*   **Императивная («как делать»):** описывает последовательность конкретных команд для достижения цели.
    *   *Пример:* выполнить `apt-get install nginx`, затем отредактировать файл через `sed`, затем запустить службу через `systemctl`.
    *   *Недостаток:* не является идемпотентной по своей природе. Требует ручной реализации проверок «если уже сделано, не делай снова».
*   **Декларативная («что должно быть»):** описывает конечное желаемое состояние системы. Инструмент сам анализирует текущее состояние и определяет необходимые шаги (Diff).
    *   *Пример (YAML):* указать, что пакет `nginx` должен иметь статус `present`, а служба — `running`.
    *   *Преимущество:* Идемпотентность и предсказуемость. Инструмент вносит изменения только в том случае, если текущее состояние отличается от желаемого.

### Модели доставки: Push и Pull

Описывают способ передачи конфигурации от центрального узла к управляемым серверам:

*   **Push (проталкивание):** Центральный сервер (контроллер) инициирует соединение с узлами (обычно по SSH или WinRM) и «проталкивает» на них изменения.
    *   *Примеры:* Ansible, Terraform.
*   **Pull (вытягивание):** На каждом сервере установлен агент, который периодически обращается к центральному серверу, запрашивает свою конфигурацию и применяет ее локально.
    *   *Примеры:* Puppet, Chef, SaltStack (в режиме миньонов).
    *   *Эволюция — GitOps:* Модель, где агенты (ArgoCD, Flux) отслеживают состояние Git-репозитория и автоматически синхронизируют его с кластером (обычно Kubernetes).

Подробное сравнение: [Сравнение Push и Pull моделей](./configuration_management_push_vs_pull.md).

### Изменяемая и Неизменяемая инфраструктура

*   **Изменяемая (Mutable):** Серверы обновляются «на лету». Мы меняем файлы и пакеты на работающих машинах.
    *   *Риск:* **Дрейф конфигурации (Configuration Drift)** — постепенное отклонение состояния серверов от эталона из-за ручных правок или сбоев.
*   **Неизменяемая (Immutable):** Вместо изменения существующих серверов создаются новые (из новых образов), а старые удаляются.
    *   *Примеры:* Образы Docker, образы ВМ, созданные через Packer.
    *   *Преимущество:* Исключение дрейфа конфигурации и полная воспроизводимость.

### Управление состоянием (State Management)

*   **Stateless (Без хранения состояния):** Инструмент не хранит информацию о прошлых запусках. При каждом старте он заново опрашивает систему (собирает факты). Пример: Ansible.
*   **Stateful (С хранением состояния):** Инструмент хранит файл состояния (State File) или базу данных, где записано, что он сделал в прошлый раз. Это позволяет быстрее вычислять разницу (diff) и отслеживать удаленные ресурсы. Пример: Terraform, Puppet (через каталоги).

## Практические сценарии

### Борьба с дрейфом конфигурации

Для предотвращения «загрязнения» инфраструктуры используются:

1.  **Автоматическое исправление (Self-healing):** Агенты (Pull) регулярно перезаписывают локальные изменения, возвращая систему к эталону.
2.  **Аудит соответствия (Compliance Audit):** Запуск инструментов в режиме `dry-run` для выявления расхождений без их исправления.
3.  **Policy as Code:** Интеграция проверок (OPA, Sentinel) на этапе CI/CD, чтобы не допустить деплоя некорректных конфигураций.

### Выбор модели под задачу

*   **Оперативные задачи (Ad-hoc):** Императивный подход + Push (Ansible) для быстрого исправления или сбора данных.
*   **Стабильный парк серверов (Enterprise):** Декларативный подход + Pull (Puppet/SaltStack) для долгосрочного поддержания стандартов.
*   **Облачные среды (Cloud Native):** Неизменяемая инфраструктура + GitOps для максимальной автоматизации и безопасности.

### Хранение конфигурации приложения

Один из ключевых архитектурных выборов — где хранить конфигурацию приложения (переменные окружения, конфиг-файлы):

1.  **В одном репозитории с кодом:**
    *   **Плюсы:** Максимальная скорость поставки (Time to Market); код и конфиг всегда синхронизированы; упрощение CI/CD пайплайна.
    *   **Минусы:** Любое изменение конфига требует прохождения полного цикла сборки/деплоя приложения; риск утечки секретов при отсутствии надлежащих инструментов (Sops, Vault).
2.  **В отдельном репозитории:**
    *   **Плюсы:** Разделение ответственности; возможность изменять настройки без пересборки приложения; более гибкое управление доступом (Access Control).
    *   **Минусы:** Риск рассинхронизации (код ожидает новую переменную, которая еще не добавлена в конфиг-репо); усложнение пайплайнов (нужно связывать события в двух репозиториях).

**Рекомендация:** Для высокодинамичных команд (Trunk-Based) часто удобнее хранение в одном репозитории для минимизации задержек. Для крупных Enterprise-систем с жестким разделением ролей предпочтителен вариант с отдельным репозиторием конфигураций.

## Дополнительная информация

### Иерархия и наследование конфигурации

Для эффективного управления тысячами серверов конфигурация строится по слоям:
1.  **Глобальный уровень:** Общие политики безопасности, ключи доступа, системные репозитории.
2.  **Групповой уровень (Слои):** Настройки для конкретных окружений (`prod`, `stage`) или дата-центров.
3.  **Ролевой уровень:** Специфические настройки для типа сервиса (`web`, `app`, `db`).
4.  **Секреты:** Отдельный слой зашифрованных данных с ограниченным доступом.

Данные модели являются теоретическим фундаментом для [Инфраструктуры как кода (IaC)](./iac_overview.md).
