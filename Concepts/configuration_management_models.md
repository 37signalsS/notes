# Модели Управления Конфигурацией

## Определения

**Управление конфигурацией (Configuration Management, CM)** — это процесс поддержания систем, программного обеспечения и серверов в заранее определенном, желаемом состоянии. CM автоматизирует управление и развертывание, обеспечивая консистентность, воспроизводимость и надежность инфраструктуры.

## Базовые концепции

### Императивная vs. Декларативная модель

Две фундаментальные парадигмы описания конфигурации:

* **Императивная ("как делать"):** Описывает последовательность конкретных шагов для достижения цели.
  * *Пример:* `apt-get install nginx`, `sed -i '...'`, `systemctl start nginx`.
  * *Минус:* Не является идемпотентной по своей природе. Повторный запуск может привести к ошибкам.
* **Декларативная ("что должно быть"):** Описывает конечное желаемое состояние системы. Инструмент сам определяет, какие действия нужно совершить.
  * *Пример (YAML):* `package: nginx, state: present`.
  * *Плюс:* Идемпотентность. Повторные запуски безопасны и приводят систему в то же самое состояние.

### Push vs. Pull модель

Описывает, как конфигурация доставляется на управляемые узлы:

* **Push (проталкивание):** Центральный сервер (контроллер) инициирует соединение с узлами и "проталкивает" на них изменения.
* **Pull (вытягивание):** Агенты на узлах периодически обращаются к центральному серверу, "вытягивают" свою конфигурацию и применяют ее.

Детальное сравнение с примерами: [сравнение Push и Pull моделей](./configuration_management_push_vs_pull.md).

### Изменяемая vs. Неизменяемая инфраструктура

* **Изменяемая (Mutable):** Серверы обновляются "на лету" путем установки пакетов, изменения конфигов и т.д. Традиционный подход.
  * *Риск:* **Дрейф конфигурации** — состояние сервера со временем отклоняется от эталона.
* **Неизменяемая (Immutable):** Вместо изменения существующих серверов создаются новые, уже с обновленной конфигурацией, а старые выводятся из эксплуатации.
  * *Пример:* Создание нового образа VM или контейнера для каждого изменения.
  * *Плюс:* Полная воспроизводимость, атомарные обновления и легкий откат.

### Конвергенция и Идемпотентность

* **Идемпотентность:** Свойство операции, при котором ее повторное применение к одному и тому же объекту не изменяет его состояния после первого применения. Ключевое свойство декларативных систем.
* **Конвергенция:** Процесс, в ходе которого инструмент управления конфигурацией постепенно приводит систему к желаемому состоянию.

## Практические сценарии

### Контроль дрейфа конфигурации

Дрейф — главная проблема изменяемой инфраструктуры. Методы борьбы:

* Использование **Pull-модели** с частыми запусками агента для автоматической коррекции.
* Регулярные аудиты в режиме "проверки" (check mode), которые только сообщают об отклонениях, но не вносят изменений.
* Переход к модели **неизменяемой инфраструктуры**.

### Выбор комбинации моделей

* **Быстрые, срочные задачи:** Императивный подход + Push-модель (например, Ansible для экстренного патча).
* **Поддержание стабильного состояния большого парка:** Декларативный подход + Pull-модель (например, Puppet или Chef).
* **Максимальная надежность и воспроизводимость в облаке:** Декларативный подход + Неизменяемая инфраструктура (например, Terraform + Packer).

## Дополнительная информация

Конфигурация редко бывает монолитной. Обычно она строится из слоев с разным приоритетом:

1. **Глобальный слой:** базовые настройки безопасности, пакеты мониторинга.
2. **Слой окружения:** настройки для `prod` или `staging`.
3. **Слой роли:** конфигурация для `веб-сервера` или `базы данных`.
4. **Слой узла:** специфичные для конкретной машины параметры (используется редко).
