# Системы хранения данных (СХД): Обзор

**Актуально для:** Linux kernel 6.1+, mdadm 4.2+, LVM 2.03.22+, ZFS on Linux 2.2.6+, Ceph Reef (18.x) / Squid (19.x), NVMe 2.0, PCIe 5.0/6.0, RoCE v2, NVMe-oF, iSCSI, NFS 4.1/4.2, S3 API, S3-совместимые реализации: MinIO, Ceph RGW

## Определения

**Система хранения данных (СХД)** — специализированная инженерно-программная инфраструктура для централизованного хранения, защиты и управления информацией в компьютерных сетях.

СХД может быть реализована аппаратно (как RAID-массив или выделенный сервер) или как программно-определяемая среда (SDS). Основная цель СХД — обеспечение сохранности данных, высокой скорости передачи и их доступности для пользователей или сервисов.

**Ключевые метрики производительности СХД:**
- **IOPS (Input/Output Operations Per Second)** — количество операций ввода-вывода в секунду. Критична для транзакционных нагрузок (СУБД, виртуализация). Значение зависит от размера блока: 4КБ random write на SSD даёт десятки тысяч IOPS, тогда как sequential write на HDD — сотни.
- **Throughput (Пропускная способность)** — объём данных, передаваемых в секунду (МБ/с или ГБ/с). Определяет производительность для потоковых операций: резервное копирование, миграция данных, стриминг.
- **Latency (Задержка)** — время от момента отправки запроса до получения ответа (мкс или мс). Для NVMe-решений в 2026 году стандарт — менее 100 мкс для случайного чтения. Высокая задержка критична для OLTP-систем и real-time приложений.
- **Размер блока (Block Size)** — минимальная единица данных при чтении/записи. Влияет на соотношение IOPS и Throughput: мелкие блоки (4КБ) нагружают контроллер числом операций, крупные (256КБ+) — пропускной способностью.

**Zoned Storage (ZNS)** — стандарт интерфейса NVMe, который разделяет адресное пространство накопителя на зоны. Данные в зоны должны записываться последовательно, что исключает необходимость в сложной логике Garbage Collection на стороне контроллера SSD, снижает Write Amplification и повышает предсказуемость задержек.

**Quality of Service (QoS) в СХД** — механизмы ограничения и гарантирования производительности (IOPS, Bandwidth) для конкретных LUN или приложений. Позволяет избежать проблемы «шумного соседа» (Noisy Neighbor) в мультиарендных средах. Реализуется через выделение гарантированных лимитов (minimum IOPS/bandwidth) и потолков (maximum IOPS/bandwidth) для каждого потребителя.

**Change Management** — процесс внесения изменений в production-инфраструктуру с минимальным риском. Включает: планирование, тестирование в staging, approval workflow, выполнение в maintenance window, валидацию и rollback-план.

**Runbook** — пошаговая инструкция для SRE/SysAdmin на случай инцидента. Содержит: симптомы проблемы, диагностические команды, возможные причины, пошаговые решения, escalation path.

**Idempotency** — свойство операции, при котором повторное выполнение не изменяет результат. В контексте storage: повторный запуск Ansible/Puppet playbook для настройки LUN/бакета не должен создавать дубликаты или изменять уже корректную конфигурацию.

**Disaster Recovery (DR)** — комплекс мер по восстановлению работы систем после катастрофического сбоя. Оценивается метриками RPO и RTO.

**Immutable Infrastructure** — подход, при котором серверы/хранилища не изменяются после деплоя; любые изменения выполняются через повторное развёртывание. Снижает risk configuration drift.

**Configuration Drift** — неконтролируемое отклонение фактического состояния инфраструктуры от желаемого. Противодействие: configuration management (Ansible/Puppet/Chef) + регулярный audit.

## Базовые концепции

### Задачи современных СХД

*   **Хранение данных:** Гарантия целостности информации. СХД защищает данные от аппаратных поломок, программных сбоев, системных ошибок и случайного удаления. Современные системы также обеспечивают защиту от атак через неизменяемые снапшоты (Immutable Snapshots) для защиты от **Ransomware**.
*   **Доступ к данным:** Оптимизация путей ввода-вывода (I/O) и минимизация задержек (Latency), что критично для приложений реального времени и СУБД. Стандарт задержек для NVMe-решений в 2026 году — менее 100 мкс.
*   **Управление данных:** Встроенные инструменты для структурирования, создания мгновенных снимков (снапшотов), резервного копирования (бэкапов), архивации и быстрого восстановления.
*   **Масштабирование:** Гибкое наращивание емкости и производительности пула хранения "на лету", без остановки работающих сервисов. Поддерживается как вертикальное (Scale-Up), так и горизонтальное (Scale-Out) масштабирование.
*   **Оптимизация и тиринг (Tiering):** Автоматическое распределение данных между разными накопителями.
    *   **Hot Storage:** Для транзакционных, часто используемых данных. Обычно SSD/NVMe.
    *   **Cold Storage:** Для архивов и редко используемых данных. Обычно HDD или объектные хранилища (S3).
    *   **Стратегии охлаждения данных:**
        1.  **Дублирование при записи:** Данные пишутся одновременно в оба типа хранилищ. *Минус:* Избыточное потребление места в период актуальности данных (дублирование петабайтов).
        2.  **Миграция (Background Move):** Данные сначала попадают в Hot Storage, а затем отдельным процессом перемещаются в Cold Storage по истечении времени (TTL). Это наиболее ресурсоэффективный способ для петабайтных объемов, позволяющий избежать дублирования.
    *   В рамках **ILM (Information Lifecycle Management)** данные могут автоматически перемещаться в облако или ленточные библиотеки.

### Компоненты СХД

Аппаратная структура системы хранения данных имеет сложную архитектуру и включает следующие компоненты:

*   **Массив накопителей (HDD или SSD):** Физические диски, используемые для хранения данных. HDD — для долгосрочного хранения и архивов; SSD — для высокоскоростных операций. Современные высокопроизводительные системы используют **NVMe SSD** для минимизации задержек. Ключевые параметры дисков:
    - **HDD:** Время доступа 3–10 мс ( seek time), пропускная способность 150–250 МБ/с, плотность записи определяется технологией CMR/SMR. Подходят для sequential-нагрузок (бэкапы, архивы, видеонаблюдение).
    - **SATA SSD:** Время доступа ~0.1 мс, IOPS до 100К (random 4K). Компромисс между стоимостью и производительностью.
    - **NVMe SSD:** Время доступа <0.1 мс, IOPS до 1–3 млн, пропускная способность до 7 ГБ/с (PCIe 5.0). Стандарт для high-performance хранилищ.
*   **Кэш-память:** Многоуровневая система ускорения доступа:
    - **Read Cache (DRAM/Flash):** Хранит копии часто запрашиваемых данных. Реализуется аппаратно (DRAM на контроллере) или программно (operating system page cache).
    - **Write Cache (DRAM + battery/supercap):** Буферизует записи для снижения задержки. Требует защиты от потери питания (BBU — Battery Backup Unit или Supercap) для гарантии целостности данных. В отсутствие backup-энергии кэш записи отключается (write-through), что снижает производительность.
    - **Tiered Cache:** Иерархия кэширования: DRAM (L1) → NVMe read/write cache (L2) → основные диски (L3).
*   **Контроллер дискового массива (RAID-контроллер):** Управляет работой массива дисков. Объединяет диски в логические группы (LUN), отвечает за резервирование, контроль целостности и управление доступом. В SDS роль контроллера выполняет специализированное ПО на стандартных серверах. Ключевые функции:
    - Вычисление и проверка контрольных сумм (parity) для RAID 5/6.
    - Управление записью (write-back/write-through) и политиками кэширования.
    - Фоновое восстановление (rebuild) при выходе диска из строя.
    - Обнаружение и исправление ошибок ( patrol read, patrol scrub ).
*   **Внешний корпус (шасси):** Физическая оболочка, размещающая диски, контроллеры и кэш-память. Включает	backplane (плату обратной связи) с горячей заменой (hot-swap) накопителей.
*   **Блоки питания:** Обеспечивают отказоустойчивое питание. Используются дублированные (redundant) блоки с автоматическим переключением. Supercap-модули обеспечивают запись кэша контроллера при внезапном отключении электричества.
*   **Сетевые интерфейсы и коммутаторы:** Обеспечивают передачу данных между серверами и СХД. Современные стандарты:
    - **Fibre Channel (FC):** 32/64 Gbps FC, выделенная сеть с минимальными задержками и потерями. Стек: FC HBA → FC switch (mesh/top-of-rack) → FC target ports на СХД.
    - **Ethernet 25/100/200G:** Для iSCSI, NVMe-oF/RoCE v2, NFS. Требует настройки PFC (Priority Flow Control) и DCBX для无损ной работы RoCE.
    - **InfiniBand (HDR/NDR):** Высокопроизводительная сеть для HPC и кластеров хранения. RDMA через IBverbs.

### Архитектура программно-определяемых систем (SDS)

SDS отделяет логику управления от аппаратного обеспечения (Control Plane от Data Plane):
*   **Control Plane:** Отвечает за оркестрацию, управление политиками доступа, создание снимков, дедупликацию и мониторинг. Примеры: Ceph Manager, MinIO Console, LINSTOR Controller.
*   **Data Plane:** Непосредственный путь прохождения данных от клиента к накопителю. В SDS он распределен между множеством узлов, использующих протоколы RDMA (Remote Direct Memory Access) для минимизации нагрузки на CPU серверов.
*   **Преимущества SDS перед аппаратными СХД:**
    - Независимость от вендора (vendor lock-in) — стандартные x86-серверы вместо проприетарного оборудования.
    - Горизонтальное масштабирование (Scale-Out) — добавление узлов увеличивает и ёмкость, и производительность.
    - Гибкость политик — автоматическое создание пулов, тиринг, репликация между узлами/дата-центрами.
    - Интеграция с оркестраторами — CSI-драйверы для Kubernetes, API для автоматизации.
*   **Реализации SDS:** Ceph (объектное/блочное/файловое), GlusterFS (файловое), LINSTOR (блочное для DRBD), Longhorn (Kubernetes-native), MinIO (объектное S3).

### Защита данных: RAID vs Erasure Coding

В современных системах используются два основных подхода к обеспечению отказоустойчивости при выходе накопителей из строя:

| Характеристика | **RAID (10, 5, 6, RAID-TP)** | **Erasure Coding (EC)** |
| :--- | :--- | :--- |
| **Принцип** | Репликация или вычисление контрольных сумм в группе дисков. | Разделение данных на $k$ блоков + $m$ блоков четности. |
| **Эффективность** | Ограничена размером RAID-группы; высокая нагрузка при rebuild. | Высокая (регулируемая избыточность, например 4+2 или 8+3). |
| **Масштабируемость** | Scale-Up (внутри одной полки/массива). | Scale-Out (распределенно между узлами кластера). |
| **Сценарии** | Классические блочные СХД, базы данных. | Объектные хранилища (S3), Big Data, Ceph. |

**Ключевые нюансы:**
*   **Write Penalty в RAID 5/6:** Каждая случайная запись малого блока требует чтения старого блока данных + старого блока четности, вычисления нового и записи обоих. Это увеличивает количество операций I/O в 4 раза (для RAID 5) или более (для RAID 6), что критично для random-write нагрузок. На SSD-массивах этот эффект менее выражен из-за высоких IOPS.
*   **RAID 10 — рекомендация для СУБД:** Зеркалирование + чередование обеспечивает предсказуемую производительность без write penalty, но снижает полезный объём в 2 раза.
*   **Rebuild Penalty:** При выходе диска из RAID 5/6 процесс восстановления (rebuild) нагружает все оставшиеся диски. На HDD 20ТБ+ это может занимать 24–72 часа, в течение которых вероятность второго отказа критически высока. Для массивов >100ТБ рекомендуется RAID 6/RAID-TP или EC.
*   **Write Hole в RAID 5:** Аварийное отключение питания во время записи контрольной суммы может привести к рассинхронизации данных и четности. Решения: journaling на контроллере, BBU/Supercap, ZFS/Btrfs с CoW.

## Классификация СХД

### По типу организации доступа

1.  **DAS (Direct Attached Storage):**
    Набор дисков, подключенный к серверу напрямую (через USB, Thunderbolt, eSATA, SCSI/SAS) без использования локальной сети. Отличается высокой скоростью, но локализован в рамках одного сервера.

2.  **NAS (Network Attached Storage):**
    Устройство, предоставляющее централизованное файловое хранилище, доступное клиентам по сети. Управляется специализированным ПО и работает по сетевым протоколам (FTP, SMB/CIFS, NFS). Поддерживает разграничение прав доступа, удобную работу с каталогами и резервное копирование.

    **Протоколы NAS:**
    *   **NFS (Network File System):** Стандарт для UNIX/Linux-сред. Версии:
        - NFSv3: Stateless, порты динамические (через rpcbind). Не работает через NAT без дополнительных настроек.
        - NFSv4: Stateful, фиксированный порт 2049/TCP. Встроенные блокировки (lease-based), Kerberos-аутентификация (RPCSEC_GSS), ACL. Рекомендуется для production-сред.
        - NFSv4.1+: pNFS (Parallel NFS) для параллельного доступа к данным с нескольких серверов.
    *   **SMB/CIFS (Server Message Block):** Протокол для Windows-сред. SMB 3.0+ поддерживает шифрование, параллельные операции (SMB Multichannel), масштабируемость (Scale-Out через кластерные файловые системы типа CSV — Cluster Shared Volumes).
    *   **FTP/SFTP:** Простой протокол для передачи файлов. Используется для bulk-загрузки/выгрузки, но не подходит для монтирования как ФС.

3.  **SAN (Storage Area Network):**
    Специализированная высокоскоростная сеть для блочного доступа к системам хранения. Используя виртуализацию ресурсов, коммутаторы и адаптеры SAN предоставляют СХД серверу таким образом, как если бы диски были подключены к нему локально (напрямую).

    **Протоколы SAN:**
    *   **Fibre Channel (FC):** Выделенная сеть на 32/64 Gbps. Преимущества: минимальные задержки (<10 мкс), lossless среда, изолированность от corporate LAN. Компоненты: FC HBA (host bus adapter) → FC switch (N-port/M-port) → FC target (ports на СХД). Адресация: WWN (World Wide Name) или FC-ID.
    *   **iSCSI (Internet SCSI):** Блочный доступ поверх TCP/IP (порт 3260). Экономичная альтернатива FC — работает на стандартном Ethernet без специализированного оборудования. Требует настройки Jumbo Frames (MTU 9000) и VLAN для изоляции трафика. Оптимален для малых и средних сред. Подробнее: [iSCSI](../../Linux/Networking/iSCSI/index.md).
    *   **SAS (Serial Attached SCSI):** Прямое подключение сервера к СХД через кабели SAS. Ограничен расстоянием (до 10 м), но обеспечивает максимальную скорость и минимальную задержку. Используется для DAS-сценариев и High-Performance кластеров.

    **Современный стандарт — NVMe-oF (NVMe over Fabrics):**
    Переносит команды NVMe через сетевую фабрику, обеспечивая производительность локального NVMe-диска по сети. Реализации:
    *   **NVMe/FC:** Использование существующей инфраструктуры Fibre Channel (32/64G FC).
    *   **NVMe/RoCE v2:** Использование RDMA поверх Ethernet. Требует поддержки PFC (Priority Flow Control) и DCBX на коммутаторах для исключения потерь пакетов (lossless Ethernet). Использует UDP для инкапсуляции.
    *   **NVMe/TCP:** Работает поверх стандартного стека TCP/IP. Не требует специализированного оборудования, но создает более высокую нагрузку на CPU клиента по сравнению с RoCE. Подходит для сред, где RDMA недоступна.

4.  **SDS (Software-Defined Storage):**
    Программно-определяемая СХД отделяет логику управления хранением от физического оборудования. В отличие от аппаратных SAN/NAS с привязкой к вендору, SDS строится на базе стандартных x86-серверов. Специальное ПО объединяет локальные диски независимых узлов в единый распределенный пул по сети (Ethernet, RoCE, InfiniBand). Масштабируется путем простого добавления серверов и служит базисом для HCI. Популярные примеры: **Ceph**, **GlusterFS**, **Linstor**, **Longhorn** (для Kubernetes).

### По типу работы с данными

*   **Файловые хранилища:** Работают с файлами и папками. Доступ осуществляется по протоколам NFS (UNIX/Linux) и SMB/CIFS (Windows). Характерны для NAS-систем. Файловые системы на сервере хранения:
    - **ext4:** Стабильная, проверенная. Ограничение: максимум 1 ЭБ, нет встроенного checksumming.
    - **XFS:** Высокая производительность для large files и parallel I/O. Ограничение: без сжатия, difficult shrink.
    - **ZFS:** Встроенное журналирование, checksumming, сжатие, снапшоты, RAID-Z. Оптимален для NAS/_SAN_ сценариев. Требует много RAM (рекомендуется 1 ГБ на 1 ТБ данных).
    - **Btrfs:** CoW (Copy-on-Write), checksumming, снапшоты, сжатие, подvolume. Используется в Synology и некоторых Linux-дистрибутивах. RAID 5/6 до сих пор считается экспериментальным.
*   **Блочные хранилища:** Предоставляют доступ к данным в виде блоков фиксированного размера (по протоколам Fibre Channel, iSCSI, SCSI). Оптимальны для приложений с низкими задержками и высокими IOPS: баз данных и виртуализации. Виды блочных томов:
    - ** Thick Provisioning:** Полный объём выделяется сразу при создании. Предсказуемая производительность, но неэффективное использование места.
    - ** Thin Provisioning:** Объём выделяется динамически по мере заполнения. Экономит место, но требует мониторинга (переполнение пула приводит к I/O ошибкам на всех томах).
*   **Объектные хранилища:** Данные организованы в виде объектов (с самими данными, метаданными и уникальным ID). Отличаются гибкостью и бесконечной масштабируемостью. Идеальны для Big Data, архивов, CDN и распределенных систем.

### Сравнение: Block, File и Object Storage

| Тип | Организация данных | Интерфейс доступа | Ключевые сценарии |
| :--- | :--- | :--- | :--- |
| **Block Storage** | Данные разбиваются на блоки; сервер получает хранилище в виде отдельного тома. Поверх него создаётся файловая система, после чего с диском работает ОС, база данных или приложение. | Блочное устройство (Fibre Channel, iSCSI, NVMe-oF, SAS) | Диски виртуальных машин, базы данных, приложения, чувствительные к задержкам |
| **File Storage** | Данные организованы в привычную структуру файлов и каталогов. Доступ обычно идёт по NFS или SMB. Одно хранилище могут использовать несколько серверов или пользователей. | Файловые протоколы (NFS, SMB/CIFS) | Общие сетевые папки, документы, медиаданные, рабочие каталоги |
| **Object Storage** | Данные хранятся как отдельные объекты вместе с метаданными. Доступ к ним обычно идёт через API. | S3 API (HTTP/REST) | Резервные копии, архивы, логи, статические файлы, большие объёмы данных |

**Коротко:**

- Block — сервер получает диск.
- File — система работает с файлами и каталогами.
- Object — приложение работает с объектами через API.

**На практике:**

- Нужен диск для ВМ или базы данных — используется Block Storage.
- Нескольким пользователям или серверам нужны одни и те же файлы — подойдёт File Storage.
- Нужно хранить бэкапы, архивы, логи или много файлов — в ход идёт Object Storage.

Одна инфраструктура может использовать все три варианта одновременно.

**Важно:** выбор хранилища без учёта нагрузки, способа доступа к данным и того, как с ними работает приложение, может привести к лишней задержке, неудобному доступу к данным, ограничениям при масштабировании или переплате за характеристики, которые для этой задачи не нужны.

### Глубокое погружение: Объектное хранилище (S3)

Объектное хранилище — это технология (изначально разработанная AWS в 2006 году) для надежного хранения большого объема данных с доступом по HTTP/HTTPS API. Фактически это KV-хранилище (Key-Value) для больших кусков данных (BLOB). Любое хранилище, поддерживающее обращения по S3 API, принято называть **S3-совместимым**.

**Как устроены объекты:**
Данные хранятся в контейнерах (бакетах). Пространство имен является плоским, без вложенной иерархии папок (в отличие от файловых систем). Каждый объект состоит из:
1.  **Самих данных** произвольного формата (от текстовых логов до образов ОС и медиа).
2.  **Метаданных** (информация о формате, дате, пользовательские теги).
3.  **Уникального идентификатора** (URL-адрес для доступа к объекту).

**Ключевые особенности и преимущества:**
*   **Защита от Ransomware (WORM / Object Lock):** Возможность запретить изменение или удаление объектов на определенный срок на уровне протокола. Это гарантирует неизменяемость данных даже при компрометации учетных записей.
*   **S3 Select:** Технология, позволяющая фильтровать данные (CSV, JSON, Parquet) внутри объекта на стороне СХД. Это радикально снижает объем передаваемого трафика и нагрузку на клиентское приложение.
*   **Доступность и целостность:** Географически распределенное хранение (обычно данные хранятся в трех экземплярах на разных серверах/стойках).
*   **Неограниченный объем:** В отличие от блочных и файловых хранилищ, S3 масштабируется практически бесконечно (до петабайтов) без усложнения структуры. За счет плоского пространства имен алгоритмы и время доступа остаются предсказуемыми даже при огромном количестве файлов.
*   **Классы хранения:** Разделяются на **Стандартный** (дорогое хранение, но дешевые и быстрые запросы/трафик) и **Холодный** (дешевое хранение для бэкапов и архивов, но дорогие запросы/трафик).
*   **Гибкое управление доступом (IAM):** Для каждого контейнера можно задать гранулярные права доступа (чтение/запись), создать сервисные учетные записи для API, а также настроить лимиты на размер и количество файлов.
*   **Модель оплаты:** Оплата по модели *pay-as-you-go* за фактически потребленные ресурсы (место, запросы, исходящий трафик).

**Популярные сценарии использования S3:**
1.  **Хранение личных данных и бэкапы:** Хранение резервных копий с поддержкой *версионирования* (сохранение старых версий файла при перезаписи).
2.  **Доставка статического контента (CDN):** Размещение медиафайлов для сайтов, где распределенная инфраструктура S3 ускоряет раздачу контента пользователям.
3.  **Статические сайты:** Размещение HTML/CSS/JS файлов в контейнере с привязкой пользовательского домена (простейший веб-хостинг).
4.  **Big Data и аналитика:** Использование S3 как транзитного слоя для обмена данными между узлами вычислительных кластеров (ML, Hadoop).

**Инструменты для работы с S3:**
Взаимодействие осуществляется через S3 API с помощью специализированного ПО:
*   [aws-cli](https://aws.amazon.com/ru/cli/) — официальный инструмент AWS, ставший де-факто стандартом. Поддерживает все операции S3 API, включая multipart upload, lifecycle policies, bucket replication.
*   [Rclone](https://rclone.org/) — мощная утилита для синхронизации данных между локальной машиной и объектным хранилищем. Поддерживает 40+ бэкендов (S3, MinIO, Ceph RGW, Yandex Object Storage). Рекомендуется для больших объемов данных благодаря parallel transfer.
*   [S3cmd](https://s3tools.org/s3cmd) — легковесный клиент для командной строки. Удобен для простых операций (ls, cp, sync).
*   **CSI-драйверы для Kubernetes:** использование S3 как файловой системы внутри кластеров (Mountpoint for S3, s3fs-fuse). Подходит для read-heavy нагрузок (статический контент, медиа-архивы). См. [S3 CSI-драйверы](../../Kubernetes/Storage/CSI/s3-csi-drivers.md).
*   **MinIO:** S3-совместимое объектное хранилище с открытым исходным кодом. Развертывается как self-hosted альтернатива, обеспечивает полную совместимость с S3 API.

В крупных СХД могут применяться гибридные конфигурации, поддерживающие сразу несколько типов доступа.

## Интеграция с контейнерами (CSI)

В современных инфраструктурах управление СХД осуществляется через стандарт **CSI (Container Storage Interface)**. Это позволяет оркестраторам (Kubernetes, Nomad) управлять жизненным циклом данных:
- **Dynamic Provisioning:** Автоматическое создание LUN/томов при запросе приложения через `PersistentVolumeClaim` (PVC).
- **Снапшоты и клонирование:** Управление снимками данных через стандартные манифесты Kubernetes API.
- **Расширение томов:** Увеличение размера диска "на лету" без остановки приложения.

Подробнее: **[Обзор CSI](../../Kubernetes/Storage/CSI/csi_overview.md)**.

## Практическое руководство: Работа с СХД

Для эффективного управления и диагностики СХД в Linux используются специализированные утилиты.

### Работа с NVMe (nvme-cli)

Основной инструмент для взаимодействия с NVMe-накопителями и фабриками.

*   **Список локальных устройств:**
    ```bash
    nvme list
    ```
    *Пример вывода:* показывает модель, серийный номер, фреймворк, размер, использование.

*   **Проверка здоровья и SMART-данных:**
    ```bash
    nvme smart-log /dev/nvme0n1
    ```
    Ключевые поля: `temperature`, `available_spare`, `percentage_used` (процент ресурса TBW), `data_units_read/written`.

*   **Получение информации о контроллере:**
    ```bash
    nvme id-ctrl /dev/nvme0n1
    # Подробная информация о возможностях контроллера
    nvme id-ns /dev/nvme0n1
    # Информация о namespace (размер, формат, ECC)
    ```

*   **Форматирование NVMe-диска:**
    ```bash
    # Формат с erase-all (стирание всех данных)
    nvme format /dev/nvme0n1 -s 1
    # Сброс controller
    nvme reset /dev/nvme0n1
    ```

*   **Подключение к NVMe-oF Target (TCP):**
    ```bash
    # Discovery
    nvme discover -t tcp -a 192.168.1.10 -s 4420
    # Подключение
    nvme connect -t tcp -a 192.168.1.10 -s 4420 -n nqn.2014-08.org.nvmexpress:uuid:fedcba98-7654-3210-fedc-ba9876543210
    ```
    *Примечание:* Для NVMe/TCP порт по умолчанию — 4420. Для NVMe/RoCE — 4420 (UDP).

*   **Проверка статуса контроллеров и подключений:**
    ```bash
    nvme list-subsys
    # Показывает все subsystems и их связь с носителями
    nvme connect-list
    # Текущие подключения NVMe-oF
    ```

*   **Отключение от NVMe-oF:**
    ```bash
    nvme disconnect -n nqn.2014-08.org.nvmexpress:uuid:fedcba98-7654-3210-fedc-ba9876543210
    ```

### Блочный доступ через iSCSI (open-iscsi)

*   **Обнаружение Target-ов (Discovery):**
    ```bash
    iscsiadm -m discovery -t sendtargets -p 192.168.1.20
    # → 192.168.1.20:3260,1 iqn.2024-01.com.example:storage.lun0
    ```

*   **Подключение (Login) ко всем найденным target'ам:**
    ```bash
    iscsiadm -m node --login
    ```

*   **Подключение к конкретному target'у:**
    ```bash
    iscsiadm -m node -T iqn.2024-01.com.example:storage.lun0 -p 192.168.1.20 --login
    ```

*   **Статус сессий (детальный):**
    ```bash
    iscsiadm -m session -P 3
    # Показывает: pathname, IP, port, state, interface
    ```

*   **Отключение (Logout):**
    ```bash
    iscsiadm -m node --logout
    # Или от конкретного target'а
    iscsiadm -m node -T iqn.2024-01.com.example:storage.lun0 -p 192.168.1.20 --logout
    ```

*   **Удаление записи о target'е:**
    ```bash
    iscsiadm -m node -o delete -T iqn.2024-01.com.example:storage.lun0 -p 192.168.1.20
    ```

*   **Полезные операции:**
    ```bash
    # Просмотр всех discovery-записей
    iscsiadm -m discoverydb
    # Перезапуск сервиса (после изменения конфигурации)
    systemctl restart iscsid
    systemctl restart iscsi
    ```

Подробнее: **[iSCSI: Индекс](../../Linux/Networking/iSCSI/index.md)** — настройка Target/Initiator, производительность, диагностика.

### Многопутевой ввод-вывод (Multipath)

Используется для обеспечения отказоустойчивости при подключении к SAN через несколько адаптеров (HBA) или сетевых интерфейсов. Также позволяет агрегировать пропускную способность (failover + load balancing).

*   **Список путей и статусы:**
    ```bash
    multipath -ll
    # Пример вывода:
    # mpatha (3600508b400105e21) dm-0 PURE,FlashArray
    # size=1.0T features='1 queue_if_no_path' hwhandler='0' wp=rw
    # |-+- policy='service-time 0' prio=1 status=active
    # | `- 2:0:0:0 sda 8:0    active ready running
    # `-+- policy='service-time 0' prio=1 status=enabled
    #   `- 3:0:0:0 sdb 8:16   active ready running
    ```

*   **Обновление конфигурации (после изменений на СХД):**
    ```bash
    multipath -r
    # Принудительное обновление таблицы путей
    ```

*   **Принудительный failover на резервный путь:**
    ```bash
    multipathd failover mpatha
    ```

*   **Просмотр detailed информации о пути:**
    ```bash
    multipathd show paths format "%d %t %T %s %z"
    # Показывает: dev, target, LUN, host, size
    ```

*   **Конфигурация (`/etc/multipath.conf`):**
    ```bash
    defaults {
        polling_interval    30
        path_grouping_policy  multibus
        path_selector       "round-robin 0"
        failback            immediate
        no_path_retry       5
        uid_attribute       ID_SERIAL
    }

    devices {
        device {
            vendor "PURE"
            product "FlashArray"
            path_grouping_policy "group_by_prio"
            path_checker "tur"
            fast_io_fail_tmo 10
            dev_loss_tmo 60
        }
    }

    blacklist {
        devnode "^(ram|raw|loop|fd|md|dm-|sr|scd|st)[0-9]*"
        devnode "^sd[a-b]$"   # Исключить локальные диски
    }
    ```
    *Параметры:*
    - `path_grouping_policy`: `multibus` (все пути активны) или `failover` (только.primary).
    - `path_checker`: метод проверки доступности (`tur` — Test Unit Ready, `readsector0`, `cciss`).
    - `fast_io_fail_tmo`: время ожидания перед пометкой пути как failed (сек).
    - `dev_loss_tmo`: максимальное время восстановления пути (сек).

### Работа с объектными хранилищами (S3)

*   **Настройка профиля AWS CLI:**
    ```bash
    aws configure --profile my-s3
    # AWS Access Key ID: <your-key>
    # AWS Secret Access Key: <your-secret>
    # Default region name: <region>
    # Default output format: json
    ```
    Для S3-совместимых хранилищ (MinIO, Ceph RGW) — указывать endpoint:
    ```bash
    aws configure set aws_access_key_id $S3_ACCESS_KEY --profile minio
    aws configure set aws_secret_access_key $S3_SECRET_KEY --profile minio
    aws configure set default.s3.endpoint_url http://minio.local:9000 --profile minio
    ```

*   **Базовые операции с бакетами:**
    ```bash
    # Создание бакета
    aws s3 mb s3://my-bucket --profile my-s3

    # Список бакетов
    aws s3 ls --profile my-s3

    # Список объектов в бакете
    aws s3 ls s3://my-bucket --recursive --human-readable
    ```

*   **Копирование и синхронизация данных:**
    ```bash
    # Копирование файла
    aws s3 cp ./data.tar.gz s3://my-bucket/backups/ --storage-class STANDARD_IA

    # Рекурсивное копирование директории
    aws s3 cp ./data-dir/ s3://my-bucket/data/ --recursive

    # Синхронизация (загружает только измененные файлы)
    aws s3 sync ./data-dir/ s3://my-bucket/data/ --delete
    # --delete удаляет файлы в S3, которых нет локально
    ```

*   **Копирование данных с помощью Rclone (рекомендуется для больших объемов):**
    ```bash
    # Конфигурация Rclone
    rclone config
    # → n (new remote) → name: my-s3 → S3 → Other → endpoint → access/secret keys

    # Копирование с parallel transfer
    rclone copy /local/path my-s3:my-bucket --progress --transfers 8 --checkers 16

    # Синхронизация с проверкой целостности (checksum)
    rclone sync /local/path my-s3:my-bucket --checksum --progress
    ```

*   **Включение версионирования в бакете (через aws-cli):**
    ```bash
    aws s3api put-bucket-versioning --bucket my-bucket --versioning-configuration Status=Enabled
    # Проверка статуса
    aws s3api get-bucket-versioning --bucket my-bucket
    ```

*   **Политика доступа (Bucket Policy):**
    ```bash
    # Пример: разрешить чтение всем (для статических сайтов)
    aws s3api put-bucket-policy --bucket my-bucket --policy file://policy.json
    # policy.json:
    # {
    #   "Version": "2012-10-17",
    #   "Statement": [{
    #     "Effect": "Allow",
    #     "Principal": "*",
    #     "Action": "s3:GetObject",
    #     "Resource": "arn:aws:s3:::my-bucket/*"
    #   }]
    # }
    ```

*   **Lifecycle Policies (автоматическая ротация данных):**
    ```bash
    aws s3api put-bucket-lifecycle-configuration --bucket my-bucket --lifecycle-configuration '{
      "Rules": [{
        "ID": "MoveToIA",
        "Status": "Enabled",
        "Transitions": [{"Days": 30, "StorageClass": "STANDARD_IA"}],
        "Expiration": {"Days": 365}
      }]
    }'
    ```

## Диагностика и устранение неполадок

### Диагностика производительности (Latency/IOPS)

*   **Мониторинг в реальном времени:**
    ```bash
    iostat -xz 1
    ```
    Ключевые столбцы:
    - `%util` — процент времени, когда диск был занят (>%80 — проблема).
    - `await` — общее время задержки запроса (мс). >10мс для SSD — проблема, >1мс для NVMe — проблема.
    - `avgqu-sz` — средний размер очереди запросов. >4 для SSD — перегрузка.
    - `r_await/w_await` — раздельная задержка чтения/записи.

*   **Детальный анализ (iostat с расширенным выводом):**
    ```bash
    iostat -d -x -y -k 1 10
    # -d: только устройства (без CPU)
    # -x: расширенная статистика
    # -y: пропустить первый отчет (средние с момента загрузки)
    # -k: в килобайтах
    ```

*   **Поиск процесса-виновника:**
    ```bash
    iotop -o
    # Только процессы с активным I/O
    # Пример: PID 1234 mysqld TOTAL 250 MB/s READ 200 MB/s
    ```

*   **Мониторинг дисковой статистики по времени:**
    ```bash
    sar -d -p 1 60
    # Запись активности дисков каждую секунду в течение 60 секунд
    ```

*   **Тестирование производительности (FIO):**
    ```bash
    # Тест случайного чтения (Random Read) с глубиной очереди 32
    fio --name=randread --ioengine=libaio --iodepth=32 --rw=randread --bs=4k --direct=1 --size=1G --numjobs=1 --runtime=60 --group_reporting

    # Тест случайной записи (Random Write) для эмуляции нагрузки БД
    fio --name=randwrite --ioengine=libaio --iodepth=16 --rw=randwrite --bs=8k --direct=1 --size=1G --numjobs=4 --runtime=60 --group_reporting

    # Тест последовательного чтения (SEQ Read) для оценки Throughput
    fio --name=seqread --ioengine=libaio --iodepth=1 --rw=read --bs=1M --direct=1 --size=4G --numjobs=1 --runtime=30
    ```

*   **ПроверкаSMART-здоровья дисков (для профилактики):**
    ```bash
    # Проверка общего состояния
    sudo smartctl -H /dev/sda
    # Расширенная информация (атрибуты)
    sudo smartctl -A /dev/sda | grep -E "Reallocated|Pending|Uncorrectable|CRC|Temperature|Hours"
    # Запуск short-теста
    sudo smartctl -t short /dev/sda
    # Просмотр результатов
    sudo smartctl -l selftest /dev/sda
    ```
    Подробнее: [Диагностика дисков (smartctl)](../../Linux/Diagnostics/Hardware/smartctl/index.md).

### Мониторинг NVMe-дисков

```bash
# Терпература и ресурс
sudo nvme smart-log /dev/nvme0n1 | grep -E "temperature|percentage_used|available_spare"

# Проверка ошибок
sudo nvme error-log /dev/nvme0n1 | head -20
```

### Типичные ошибки и решения

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **Высокий await в iostat (>10мс)** | Перегрузка контроллера СХД или сетевого канала. | Проверить QoS лимиты на СХД, утилизацию каналов 10/25G. Выполнить `iostat -xz 1` для идентификации устройства. |
| **Input/Output Error (E/O)** | Потеря всех путей в SAN или аппаратный сбой диска. | Проверить `multipath -ll`, состояние кабелей и HBA. Для iSCSI: `iscsiadm -m session -P 3`. |
| **Низкий IOPS на SSD** | Истощение кэша записи или высокая фрагментация (WA). | Проверить `nvme smart-log` (Percentage Used), выполнить `fstrim`. Для HDD — проверить фрагментацию. |
| **S3 403 Forbidden** | Ошибка в IAM политиках или неверное системное время. | Проверить `date` на сервере (синхронизировать NTP) и политики доступа. Для S3-совместимых — endpoint URL. |
| **iSCSI session disconnects** | Проблемы с сетью (потеря пакетов, MTU mismatch). | Проверить `ping -M do -s 8972 <target_ip>` (Jumbo Frames). Проверить `iscsiadm -m session -P 3` и логи `/var/log/messages`. |
| **Multipath path thrashing** | Нестабильный путь ( регулярные переключения active/failed). | Проверить `multipathd show paths`. Увеличить `fast_io_fail_tmo`. Использовать `path_grouping_policy "group_by_prio"`. |
| **NFS mount hangs** | Проблемы с сетью или NFS server. | Проверить `showmount -e <nfs_server>`. Использовать `mount -o intr,nolock` для отладки. Для NFSv4 — проверить `rpc.statd`. |
| **Thin Pool full (LVM)** | Логический том переполнен thin pool. | Проверить `lvs`. Расширить thin pool через `lvextend`. Для Ceph: проверить `ceph osd df`. |

### По типу железа

*   **All-Flash массивы (AFA):** Системы исключительно на твердотельных накопителях (SSD с SAS/NVMe). Максимальная скорость, минимальные задержки. Применяются для СУБД, бизнес-аналитики и высоконагруженных приложений.
*   **HDD-массивы:** Системы на магнитных жестких дисках. Низкая стоимость за гигабайт. Отличный вариант для резервных копий, архивов и систем видеонаблюдения.
*   **Гибридные СХД:** Комбинация HDD и SSD. При помощи кэширования и тиринга система держит "горячие" данные на SSD, а "холодные" переносит на HDD. Баланс скорости и цены.
*   **Гиперконвергентные системы (HCI):** Вычислительные мощности (CPU, RAM) и хранение (SDS) объединены на стандартных серверах, которые одновременно выполняют роль хостов виртуализации и узлов хранения в распределенном кластере.

## Практические сценарии

### Как СХД помогает бизнесу

Переход на централизованную СХД решает множество задач:

*   **Защита от простоев:** Сбой диска или контроллера отрабатывается системой автоматически (без остановки сервисов).
*   **Снижение затрат на ИТ-персонал:** Администрирование одной СХД проще управления локальными дисками на сотнях серверов.
*   **Безопасность и контроль:** Разграничение прав, шифрование и физическая централизация снижают риски утечек информации.

### Как выбрать СХД

При проектировании архитектуры учитываются следующие параметры:

1.  **Профиль нагрузки и тип данных:** СУБД требуют AFA/NVMe, корпоративные файлопомойки — NAS-решений, бэкапы — HDD-массивов или гибридных систем.
2.  **Производительность:** Оценивается не только IOPS (операций ввода-вывода), но и задержка (Latency), а также размер блока (100k IOPS на блоках 4 КБ и 64 КБ дают разную нагрузку).
3.  **Отказоустойчивость:** Если простой недопустим, используется архитектура без единой точки отказа (No Single Point of Failure) с дублированием контроллеров и путей, а также современные технологии вроде RAID 2.0+ для сверхбыстрого восстановления дисков.
4.  **Эффективность хранения:**
    *   **Дедупликация и компрессия:** Уменьшают занимаемый объем на All-Flash массивах в 2–5 раз.
    *   **Thin Provisioning ("тонкие" диски):** Выделение емкости динамически по мере заполнения.
5.  **Интерфейсы подключения:** Fibre Channel (FC) — для выделенных SAN-сетей (максимальная стабильность); iSCSI — блочный доступ поверх дешевого Ethernet (выше нагрузка на CPU); SAS — быстрое прямое подключение в рамках соседних стоек.
6.  **Масштабируемость и форм-фактор:** Наращивание (Scale-Up или Scale-Out). Использование высокоплотных решений (до 100 дисков в 4U) экономит место в ЦОД, но требует мощного питания и охлаждения на стойку.

### Масштабирование сетевого хранилища

СХД спроектированы под динамические и микросервисные среды, позволяя выделять LUN или тома "на лету".

*   **Вертикальное (Scale-Up):** Добавление дисковых полок к текущей системе (характерно для аппаратных СХД).
*   **Горизонтальное (Scale-Out):** Добавление новых полнофункциональных серверов в распределенный кластер (характерно для SDS/HCI).

### Отказоустойчивость и восстановление (RPO и RTO)

Способность СХД переносить сбои оценивается метриками:

*   **RPO (Recovery Point Objective):** Максимально допустимая потеря данных при аварии (например, время с момента создания последней резервной копии/реплики). RPO = 0 означает zero data loss (синхронная репликация). RPO = 1 hour — допустима потеря данных за последний час.
*   **RTO (Recovery Time Objective):** Допустимое время простоя сервисов, необходимое для восстановления системы в работоспособное состояние. Зависит от сложности системы и метода восстановления (full rebuild vs. failover).

**Стратегии резервного копирования (3-2-1 Rule):**
1. **3 копии данных:** Оригинал + минимум 2 резервные копии.
2. **2 разных типа носителей:** Например, локальный NAS + удалённое对象ное хранилище (S3) или ленточная библиотека.
3. **1 копия вне сайта:** Удалённый дата-центр или объектное хранилище для защиты от локальных катастроф.

**Типы бэкапов:**
- **Полный (Full):** Копирование всех данных. Самый быстрый восстановление, но большой объём хранилища.
- **Инкрементальный:** Копирование только изменений с момента последнего бэкапа (любого типа). Экономит место, но восстановление медленнее.
- **Дифференциальный:** Копирование изменений с момента последнего полного бэкапа. Компромисс между объёмом и скоростью восстановления.

**Инструменты для бэкапов:**
- **Restic/Borgbackup:** Дедуплицирующие бэкапы с шифрованием. Поддерживают S3, NFS, SFTP.
- **Bacula/Bareos:** Enterprise-уровень. Полный контроль, каталогизация, проверка целостности.
- **pgBackRest/WAL-G:** Для PostgreSQL — физические бэкапы с инкрементальной поддержкой.

### СХД и законодательство РФ

*   **ФЗ-152 (О персональных данных):** Требует физической локализации баз данных россиян на территории страны. Размещение СХД в отечественных ЦОД (Selectel и др.) решает эту задачу.
*   **ГИС и КИИ:** Информационные системы государства и критическая инфраструктура требуют размещения в аттестованных сегментах ЦОД, защищенных по стандартам ФСТЭК (УЗ-1 – УЗ-4) и ФСБ.
*   **Импортозамещение:** Для госсектора доступна аренда СХД на базе оборудования из реестра Минпромторга и российского ПО.

## Практические руководства для SRE/SysAdmin

### Шифрование данных в хранении и при передаче

**Encryption at Rest (шифрование на диске):**
- **LUKS (Linux Unified Key Setup):** Стандарт шифрования блочных устройств в Linux. Использует AES-256-XTS.
  ```bash
  # Шифрование диска
  cryptsetup luksFormat /dev/sdb
  cryptsetup luksOpen /dev/sdb encrypted_data
  mkfs.ext4 /dev/mapper/encrypted_data
  mount /dev/mapper/encrypted_data /mnt/encrypted
  # Автоматическое открытие при загрузке: добавить в /etc/crypttab
  ```
- **SED (Self-Encrypting Drives):** Аппаратное шифрование на уровне SSD/HDD (TCG Opal 2.0). Не нагружает CPU, но требует поддержки со стороны контроллера.
- **Сетевые хранилища:** Многие СХД поддерживают шифрование LUN на уровне контроллера (AES-256). Уточняйте у вендора.

**Encryption in Transit (шифрование при передаче):**
- **iSCSI:** использует IPSec или CHAP для аутентификации. Для шифрования — VPN (WireGuard/IPsec) между инициатором и таргетом.
- **NFS:** Kerberos + RPCSEC_GSS (NFSv4). Для NFSv3 — IPsec.
- **SMB/CIFS:** SMB 3.0+ поддерживает AES-128/256-CCM шифрование (включается на уровне share).
- **S3:** HTTPS (TLS 1.2+) для транспорта. Для S3-совместимых — проверять поддержку TLS на endpoint.

### Планирование емкости (Capacity Planning)

**Формула расчёта необходимого объёма:**
```
Требуемый объём = (Текущий объём × (1 + Рост в год × Срок жизни)) × Коэффициент избыточности
```
- **Рост в год:** типично 30–100% для активных данных, 10–20% для архивов.
- **Коэффициент избыточности:** 2× для RAID 10, 1.33× для RAID 6 (4+2), 1.5× для тройного копирования.

**Мониторинг использования:**
```bash
# Локальные ФС
df -hT
# Детализация по директориям
du -sh /var/log/* | sort -rh | head -10
# Мониторинг роста по времени (cron +sar)
sar -F 1 3600 > /tmp/disk_usage.log
```

**Ключевые метрики для алертинга:**
- Использование >80% — предупреждение (warning).
- Использование >90% — критическое (critical).
- Рост >10% в неделю — тревога (anomaly detection).

### Общие рекомендации по бэкапам

1. **Регулярно проверяйте восстановление:** Бэкап, который не проверен — не бэкап. Тестируйте restore минимум раз в квартал.
2. **Шифруйте бэкапы:** Используйте `restic` или `borg` с AES-256. Храните ключи шифрования отдельно.
3. **Контролируйте сроки хранения:** Настройте lifecycle policies для S3 (автоматическое удаление/архивация).

5. **Изоляция бэкапов:** Используйте отдельные учётные записи с minimal permissions (principle of least privilege).

### Управление конфигурацией и идемпотентность

Всё управление storage должно быть описано в коде и версионироваться в Git. Ниже — минимальные паттерны для распространённых инструментов.

**Ansible (декларативный подход):**

```yaml
- name: Гарантировать наличие LUN
  ansible.builtin.uri:
    url: "https://{{ storage_api }}/api/v1/luns"
    method: POST
    body_format: json
    body:
      name: "{{ lun_name }}"
      size_gb: "{{ lun_size }}"
      storage_pool: "fast_ssd"
    status_code: 200,201,409  # 409 = already exists — идемпотентно
  register: lun_result

- name: Проверить, что LUN уже существует
  ansible.builtin.assert:
    that:
      - lun_result.status == 200 or lun_result.status == 201
    fail_msg: "Неожиданный статус при создании LUN: {{ lun_result.status }}"
```

**Проверка идемпотентности:**
- Повторный запуск playbook не должен менять состояние (`ok` вместо `changed`).
- Для ресурсов, которые не поддерживают `GET` для проверки существования, используйте `register` + `assert`.
- Никогда не используйте `shell`/`command` для операций, которые можно сделать через модули — это нарушает идемпотентность.

**Puppet (декларативный подход):**

```puppet
# Модуль storage/lun
storage_lun { 'db_lun':
  ensure      => present,
  size_gb     => 500,
  pool        => 'fast_ssd',
  target_port => 'iqn.2024-01.com.example:storage.lun0',
}
```

Puppet apply должен быть идемпотентен: повторный запуск без изменений в манифесте не вызывает `changes`.

**Chef (императивный → декларативный):**

```ruby
# recipe lun
lun 'db_lun' do
  size_gb 500
  pool 'fast_ssd'
  action :create
end
```

### Change Management

Любое изменение production storage должно проходить через формализованный процесс:

1. **Planning:** Описать изменение, риски, окно выполнения, rollback-план.
2. **Testing:** Выполнить в staging-среде, идентичной production.
3. **Approval:** Получить одобрение отTechnical Lead/SRE.
4. **Execution:** Выполнить в maintenance window с extended monitoring.
5. **Validation:** Проверить, что изменение достигло цели и не вызвало регресса.
6. **Documentation:** Обновить runbook и архитектурную документацию.

**Maintenance Window Checklist:**
- [ ] Уведомление stakeholders минимум за 48 часов.
- [ ] Наличие rollback-плана с проверенными командами.
- [ ] Extended monitoring (1-2 часа до и после).
- [ ] Наличие всех участников на связи (Slack/Zoom war room).
- [ ] Проверка backups — свежий backup доступен и проверен.

### Disaster Recovery Runbooks

**Сценарий 1: Отказ диска в RAID-массиве**

```bash
# 1. Диагностика
cat /proc/mdstat
# → md0: active raid6 sdd1[3] sde1[4] sdf1[5] sdb1[1] sdc1[2]
#    [====>................]  resync = 25.3% (292M/1152M) finish=12.3min

# 2. Ожидание завершения rebuild (не отключать питание)
watch -n 5 cat /proc/mdstat

# 3. Проверка SMART нового диска
smartctl -H /dev/sdd
smartctl -A /dev/sdd | grep -E "Reallocated|Pending|Uncorrectable"

# 4. Если диск маркирован как failed — замена
mdadm --manage /dev/md0 --fail /dev/sdd1
mdadm --manage /dev/md0 --remove /dev/sdd1
# Физическая замена диска
mdadm --manage /dev/md0 --add /dev/sdd1
```

**Сценарий 2: Ошибка пути в multipath**

```bash
# 1. Проверка статуса путей
multipath -ll
# mpatha (3600508b400105e21) dm-0 PURE,FlashArray
# size=1.0T features='1 queue_if_no_path' hwhandler='0' wp=rw
# |-+- policy='service-time 0' prio=1 status=active
# | `- 2:0:0:0 sda 8:0    active ready running
# `-+- policy='service-time 0' prio=1 status=enabled
#   `- 3:0:0:0 sdb 8:16   failed ready running

# 2. Принудительный failover
multipathd failover mpatha

# 3. Проверка, что путь восстановился
multipathd show paths format "%d %t %T %s %z"

# 4. Если путь не восстанавливается — проверка сети и HBA
lspci | grep -i hba
dmesg | grep -i "fiber\|hba\|scsi"
```

**Сценарий 3: Падение OSD в Ceph**

```bash
# 1. Проверка состояния кластера
ceph -s
ceph osd tree

# 2. Проверка статуса OSD
systemctl status ceph-osd@15
journalctl -u ceph-osd@15 --since "10 minutes ago"

# 3. Если OSD down — попытка restart
systemctl restart ceph-osd@15
sleep 10
ceph osd tree | grep 15

# 4. Если не помогает — удаление и повторное добавление
ceph osd out 15
ceph osd crush remove osd.15
ceph auth del osd.15
ceph osd rm 15
# Создание нового OSD на новом диске
ceph-volume lvm create --data /dev/vg/data --osd-id 15 --osd-fsid $(ceph fsid)
```

**Сценарий 4: Утечкаthin pool (LVM/Ceph)**

```bash
# 1. Проверка использования thin pool
lvs
# LV         VG   Attr       LSize   Pool   Origin Data%  Meta%  Move Log
# thinpool   vg0  twi-a-tz-- 500.00g       100.00

# 2. Проверка, какие тома потребляют место
lvs -o+devices
# Найти тома с high data%

# 3. Расширение thin pool
lvextend -L +100G vg0/thinpool
lvextend -L +100G vg0/thinpool_tmeta

# 4. Для Ceph — проверка OSD
ceph df
ceph osd df
# Найти OSD с high used_%
```

### Резервное копирование: процедуры валидации

**Автоматическая проверка backup:**

```bash
#!/bin/bash
# /usr/local/bin/backup-validate.sh
BACKUP_DIR="/backup/daily"
RESTORE_DIR="/tmp/backup-restore-test"
MOUNT_POINT="/mnt/test-restore"

# 1. Проверка размера backup
du -sh "$BACKUP_DIR"
# → 120G /backup/daily

# 2. Проверка последнего backup
ls -lht "$BACKUP_DIR" | head -5

# 3. Тест восстановления в отдельный каталог
mkdir -p "$RESTORE_DIR"
restic restore latest --target "$RESTORE_DIR" --verify

# 4. Проверка целостности
find "$RESTORE_DIR" -type f | wc -l
# → 15234

# 5. Сравнение контрольных сумм
cd "$RESTORE_DIR" && sha256sum -c /backup/manifest.sha256
# → OK: 15234/15234

# 6. Очистка
rm -rf "$RESTORE_DIR"
```

**Ротация бэкапов (lifecycle policies):**
- **Daily:** хранить 7 дней.
- **Weekly:** хранить 4 недели.
- **Monthly:** хранить 12 месяцев.
- **Yearly:** хранить 7 лет (compliance).

### Capacity Planning Automation

**Автоматический мониторинг роста:**

```bash
#!/bin/bash
# /usr/local/bin/capacity-check.sh
THRESHOLD=80

df -hT | awk -v threshold=$THRESHOLD '
$6 ~ /%/ {
  gsub(/%/, "", $6)
  if ($6 > threshold) {
    print "WARNING: " $6 " на " $7
  }
}'
```

**Прогноз роста на основе исторических данных:**

```bash
# Использование sar для анализа роста
sar -F 1 3600 > /var/log/sar/disk_usage.log

# Анализ роста
python3 -c "
import pandas as pd
df = pd.read_csv('/var/log/sar/disk_usage.log', delim_whitespace=True)
# Прогноз на 90 дней
# ...
"
```

**Capacity Planning Formula:**

```
Требуемый объём = (Текущий объём × (1 + Рост в год × Срок жизни)) × Коэффициент избыточности
```

- **Рост в год:** типично 30–100% для активных данных, 10–20% для архивов.
- **Коэффициент избыточности:** 2× для RAID 10, 1.33× для RAID 6 (4+2), 1.5× для тройного копирования.
