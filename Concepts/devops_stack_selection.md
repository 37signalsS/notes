# Методология выбора стека DevOps

## Определения

**Стек DevOps** — минимальный набор инструментов, покрывающих четыре базовых слоя: облачная инфраструктура, инфраструктура как код (IaC), CI/CD и оркестрацию контейнеров. Безопасность и наблюдаемость пронизывают все слои сквозным образом.

**Менеджер-сервисы (Managed Services)** — модель потребления облачных ресурсов, при которой провайдер берёт на себя эксплуатацию Control Plane, обновления, резервное копирование и мониторинг. Примеры: AWS Fargate, Google Cloud Run, Amazon RDS, Yandex Managed Kubernetes.

**Собственная сборка (Self-hosted / DIY)** — модель, при которой команда самостоятельно разворачивает, настраивает и сопровождает все компоненты стека. Подходит, когда требуется тонкая кастомизация, закрытый периметр или специфические паттерны работы.

## Базовые концепции

### Принцип: сначала просто, потом умно

Выбор стека начинается с целей, а не с логотипов в резюме. Каждый инструмент должен решать существующую проблему, а не гипотетическую. Остальное добавится, когда появится боль и масштаб.

**Фильтр принятия решений:**
> «Смогу ли я через полгода спокойно обновить этот инструмент, не останавливая работу?»
> 
> Если ответ неуверенный — откатитесь к более простому варианту.

### Критерии выбора

#### Команда и найм

Стек подбирается под людей, а не наоборот.
- Если в команде нет опыта с Kubernetes, начинать с Kubernetes «для взрослости» — верный путь к ночным сменам с инцидентами.
- Нужны быстрые поставки — берите менеджер-сервисы.
- Нужна тонкая кастомизация — собственные агенты, приватные сети, закрытый периметр — тогда self-hosted более уместен.
- Важно: если берёте сложный инструмент, убедитесь, что есть человек, которому это не в тягость поддерживать, и желательно с опытом, а не просто рвением изучать технологию.

#### Облако: менеджер против самоделки

Малые и средние команды выигрывают от менеджер-сервисов.
- **Контейнеры без кластерной боли:** ECS, Fargate, Cloud Run, App Runner.
- **Базы данных:** RDS, Cloud SQL, Yandex Managed Databases — не делайте свой зукипер «потому что мы можем».
- **Статистика и файлы:** S3 + CDN.

**Мультиоблако** нужно редко: юридические требования, локальные зоны, особые скидки. Во всех остальных случаях вы удваиваете сложность счёта и количество способов сломаться.

#### Инфраструктура как код

Один инструмент, один стиль, модули.
- **Обязательно:** блокировка состояния (state locking) при любых изменениях.
- **Переменные:** минимум в модулях, максимум читаемости в окружениях (dev/stage/prod).
- **Правило красного флага:** если модуль понимает только автор, который его написал — это прямой красный флаг.
- **Правило читаемости:** инфраструктурный код — это договор между людьми. Если договор нельзя прочитать за 5 минут, он сорвётся в первый же инцидент, потому что ночью вы не поймёте, что там надо чинить.

#### CI/CD

Нужен быстрый старт и готовой интеграции — берите GitHub Actions, GitLab CI.
- Минуты дешёвые, кэш сборок элементарные, секреты нормальные.
- Поддержка почти не нужна, команда сконцентрирована на релизах.

Нужны экзотические агенты, собственные сети, тонкая оркестрация, либо собираете что-то вообще непонятное — Jenkins.
- Но помните: Jenkins — это постоянные апгрейды, плагины, агенты, бэкапы и свой мониторинг. Заложите на него время инженера.

**Правило читаемости пайплайна:**
Сборка → Тесты → Скан → Пуш образа → Plan/Apply по IaC → Откат.
Логи пайплайна — это артефакт, а не то, что надо вычитать в консолях.

#### Оркестрация и Kubernetes

Kubernetes нужен там, где он, конечно же, окупается.
- Много сервисов, сложные паттерны взаимодействия, sidecar-подходы, тонкий автoscale.
- Появился общий платформенный слой.
- Требуются strict-политики и продвинутая маршрутизация.
- Есть человек, которому это не в тягость поддерживать, и желательно с опытом, а не просто рвением изучать Kubernetes.

**Признаки, что пора в Kubernetes:**
1. Компонентов 10 и больше.
2. Появился общий платформенный слой.
3. Требуются strict-политики и продвинутая маршрутизация.
4. Есть dedicated-инженер с опытом.

Кластер имеет смысл, когда он решает уже существующие, а не гипотетические проблемы, о которых вы можете только подумать. Нет проблемы — не нужен кластер.

#### Безопасность

- Принцип наименьших привилегий.
- Секреты в менеджере секретов, а не в Git.
- Ключи и токены регулярно ротируем.
- Если вам скучно от этих пунктов — вы всё делаете правильно.

#### Наблюдаемость

Собираем метрики, логи, трассировки и всё в одном месте.
- Формулируем SL человеческим языком: «Sentinel 99-й по API меньше 800 мс. Ошибок не выше 1% за 5 минут».
- Алерты привязываем к SL, а не к CPU. «У нас там где-то скакнуло» — не повод для пинга в 3 часа ночи.

**Стартовый набор метрик:**
- Latency (P99)
- Error Rate
- CPU / Memory
- Глубина очередей

Скрин дашборда и правила алертов в репозитории рядом с кодом — это правильный путь. Так любой видит, что для вас красная зона. Когда заходите в репозиторий, понимаете, где там и что.

#### Деньги: скорость против TCO

1 час инженера дороже сотни минут вычислений. Если GitHub Actions экономит неделю — это прибыль. Если Jenkins требует админа Jenkins, — это расход.

Менеджер-сервисы кажутся дороже, но они не звонят ночью, не просят апдейт в отпуск. Это не только счёт в облаках, это ещё время команды и предсказуемость релизов.

## Практические сценарии

### Матрица выбора

Чтобы не спорить вкусовщиной, считаем баллами.

| Критерий | Вес | GitHub Actions + Serverless | Jenkins + EKS |
| :--- | :--- | :--- | :--- |
| Скорость | 5 | 5 | 3 |
| Стоимость | 4 | 4 | 2 |
| Сложность | 5 | 5 | 2 |
| Найм | 3 | 4 | 2 |
| Безопасность | 4 | 4 | 4 |
| **Сумма** | | **22** | **13** |

Сумма — это ориентир, а не истина.

### План на 2 дня (типичный старт для команды из 4 человек)

**День первый:**
1. Собрать образ.
2. Деплоить один сервис в дефолтное окружение.
3. Включить автопереключение (автоподъём) при деградации.

**День второй:**
1. Симулировать деградацию.
2. Сделать откат одной командой.
3. Снять метрики и тайминги.

Выводы в коротком ритме: что получилось, что болит и сколько это стоит.

### Типичные итоги

- **GitHub Actions + Serverless (Fargate/Cloud Run):** даёт скорость и меньше сопровождения.
- **Jenkins + EKS:** гибче, но сложнее и дороже в уходе.

Если цель time-to-market — берём первый вариант. Если нужна тонкая кастомизация, закрытый периметр — берём второй.

### Мини-история: старт без кластера

Есть сервис: API, фронт и платежи. Днём пик, ночью спад. Цель: релизы без просадок и без ночных звонков.

**Стартовое решение:**
- API: Fargate.
- База: RDS.
- Статистика: S3 + Cloud Front.
- CI: GitHub Actions собирает образ.
- IaC: Terraform поднимает сервис.
- Автoscale: включён.

Итог: за неделю вы в production без кластера, без сетевых плясок.

## Дорожка роста без зоопарка

| Фаза | Состояние | Стек |
| :--- | :--- | :--- |
| **Фаза 0** | Один сервис | Managed Services, CI/CD |
| **Фаза 1** | Несколько сервисов | Модули IaC для окружений |
| **Фаза 2** | Менеджмент | Kubernetes, общий платформенный слой, централизованная наблюдаемость |
| **Фаза 3** | Платформа как продукт | SSO, self-service, политики и бюджеты |

Каждый шаг закрывает конкретную боль. Не бегите вперёд, пока проблема не появилась, и не держитесь за инструмент, который перестал окупаться.
