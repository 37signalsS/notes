# Обнаружение сервисов (Service Discovery)

## Определения

**Обнаружение сервисов (Service Discovery)** — автоматизированный процесс определения сетевых координат (IP-адресов и портов) экземпляров приложений в распределенной системе. В динамических средах (Kubernetes, Docker Swarm, микросервисные кластеры), где жизненный цикл инстансов эфемерен, Service Discovery устраняет необходимость в ручном обновлении конфигураций и обеспечивает бесперебойную связь между компонентами.

**Реестр сервисов (Service Registry)** — высокодоступная база данных («телефонная книга»), хранящая актуальную информацию о доступных экземплярах сервисов, их состоянии (Health) и метаданных (версия, регион, теги).

**Метаданные сервиса** — дополнительные атрибуты, привязанные к инстансу (например, `version=v1.2`, `env=prod`, `weight=10`). Используются для сложной маршрутизации, канареечных релизов и фильтрации трафика.

**Endpoint** — конкретная сетевая точка (IP + порт), по которой доступен экземпляр сервиса. Термин используется в Kubernetes (EndpointSlice), Consul и API-балансировщиках.

## Базовые концепции

### Механизмы обнаружения (Discovery Mechanisms)

Существует три основных способа получения адресов:

1.  **DNS-based Discovery:**
    *   **Принцип:** Клиент делает стандартный DNS-запрос по имени сервиса. Резолвер возвращает один или несколько IP-адресов (A/AAAA записи) или детальную информацию (SRV-записи с портами).
    *   **Примеры:** Kubernetes CoreDNS, HashiCorp Consul (DNS-интерфейс), Docker встроенный DNS.
    *   **Особенность:** Требует осторожности с кэшированием (TTL), так как клиенты могут продолжать обращаться к удаленным инстансам.
    *   **SRV-записи:** Помимо IP, содержат порт, вес и приоритет. Формат: `_service._proto.name TTL IN SRV priority weight port target`. Используются в Consul, Kubernetes (головные сервисы) и LDAP.

2.  **API-based Discovery:**
    *   **Принцип:** Клиент или прокси-сервер обращается к REST/gRPC API реестра для получения актуального списка узлов.
    *   **Примеры:** Consul HTTP API, etcd, Kubernetes API (для Prometheus SD).
    *   **Особенность:** Позволяет получать богатые метаданные и использовать сложные алгоритмы выбора на стороне клиента.

3.  **Environment Variables (Устаревший):**
    *   **Принцип:** Оркестратор пробрасывает адреса зависимых сервисов в переменные окружения при старте контейнера.
    *   **Особенность:** Не поддерживает динамические изменения после запуска. Используется как fallback в Docker Compose (когда контейнеры в одной сети) и некоторых оркестраторах.
    *   **Проблема:** При обновлении сервиса переменные не пересоздаются. Клиенты с кэшированными адресами продолжают обращаться к старым инстансам.

### Модели обнаружения (Discovery Patterns)

#### 1. Обнаружение на стороне клиента (Client-side Discovery)
Клиент самостоятельно запрашивает список адресов у реестра и выбирает конкретный узел для запроса.
*   **Механизм:** Приложение использует клиентскую библиотеку (например, `grpc-go` с DNS-резолвером) для связи с реестром.
*   **Плюсы:** Меньше сетевых задержек (прямой вызов), возможность реализации «умной» балансировки на основе локальных данных приложения.
*   **Минусы:** Зависимость кода приложения от конкретного реестра; необходимость поддержки библиотек для разных языков программирования.
*   **Когда использовать:** Микросервисы на одном языке, системы с жесткими требованиями к латентности, gRPC-сервисы.

#### 2. Обнаружение на стороне сервера (Server-side Discovery)
Клиент обращается к сервису через посредника (Load Balancer или API Gateway), который берет на себя задачу поиска эндпоинтов.
*   **Механизм:** Балансировщик опрашивает реестр или напрямую API оркестратора и перенаправляет трафик на «живой» инстанс.
*   **Плюсы:** Абстракция инфраструктуры от приложения; легкость внедрения Service Mesh; поддержка любых языков программирования без специальных библиотек.
*   **Минусы:** «Лишний хоп» (дополнительная сетевая задержка); балансировщик — критический узел системы.
*   **Примеры:** Kubernetes Services (ClusterIP), Nginx/Angie с upstream-модулями, HAProxy с consul-плагином.

#### 3. Обнаружение через прокси / Sidecar (Service Mesh)
Прокси-сервис (sidecar) развернут рядом с каждым инстансом приложения и берет на себя всю сетевую логику: обнаружение, балансировку, шифрование (mTLS) и наблюдаемость.
*   **Механизм:** Приложение общается только с локальным прокси (`127.0.0.1`), который обращается к реестру и маршрутизирует трафик.
*   **Плюсы:** Полная изоляция сетевой логики от бизнес-кода; единая точка для мониторинга и безопасности; zero-trust между сервисами.
*   **Минусы:** Дополнительные ресурсы (CPU/RAM на каждый sidecar); увеличение задержки на один хоп.
*   **Примеры:** Istio (Envoy), Linkerd (linkerd2-proxy), Consul Connect (Envoy).
*   **Подробнее:** **[Service Mesh: Концепции](../Service_Mesh/service_mesh_concepts.md)**.

---

### Механизмы регистрации (Registration Patterns)

*   **Самостоятельная регистрация (Self-Registration):** Сервис сам отправляет запрос в реестр при старте и регулярно подтверждает свою активность (Heartbeat). При выключении отправляет сигнал `DEREGISTER`. *Риск:* Если процесс убит некорректно (SIGKILL), запись может остаться в реестре до истечения TTL.
*   **Сторонняя регистрация (Third-party Registration):** Внешний агент (Registrar) следит за состоянием платформы (Docker API, K8s API) и автоматически обновляет реестр. Примеры: `Registrator` для Docker, `Kubelet` для Kubernetes, `consul-k8s` для синхронизации.

### Выбор реестра: сравнение инструментов

| Инструмент | CAP-класс | Язык API | Встроенный DNS | Health Checks | Мультикластерность |
| :--- | :---: | :--- | :---: | :--- | :--- |
| **Consul** | CP (Raft) | HTTP, gRPC | Да (порт 8600) | HTTP, TCP, gRPC, TTL, Script, Alias | Cluster Peering, Sameness Groups |
| **etcd** | CP (Raft) | gRPC | Нет (требует CoreDNS) | Нет (нужны внешние скрипты) | Нет (только Watch) |
| **ZooKeeper** | CP (ZAB) | Java API | Нет | Нет (нужны внешние скрипты) | Нет |
| **Eureka** | AP (Gossip) | REST | Нет | HTTP, TCP | Репликация между дата-центрами |
| **CoreDNS** | N/A | N/A | Да | Нет (resolver) | Federation |

## Согласованность и CAP-теорема

Выбор инструмента Service Discovery часто определяется требованиями к согласованности данных при сетевом разделении (Partition):

| Инструмент | CAP-класс | Механизм консенсуса | Особенности |
| :--- | :---: | :--- | :--- |
| **Consul** | **CP** | Raft | Строгая согласованность. При сбое кворума запись недоступна. |
| **etcd** | **CP** | Raft | Используется в K8s. Очень надежен, но требует настройки для SD. |
| **Eureka** | **AP** | Gossip / Replication | Приоритет доступности. Может вернуть старый IP, но система не «ляжет». |
| **ZooKeeper** | **CP** | ZAB | Сложный в эксплуатации, классика для Hadoop/Kafka. |

## Практические сценарии

### 1. Регистрация сервиса через REST API (Consul)
Пример ручной регистрации инстанса через HTTP-интерфейс:

```bash
curl --request PUT \
  --data '{
    "ID": "web-v1-1",
    "Name": "web-api",
    "Tags": ["v1", "production"],
    "Address": "192.168.1.50",
    "Port": 8080,
    "Check": {
      "HTTP": "http://192.168.1.50:8080/health",
      "Interval": "10s"
    }
  }' http://localhost:8500/v1/agent/service/register
```

### 2. Обнаружение через DNS SRV-записи
SRV-записи позволяют узнать не только IP, но и порт сервиса. Пример запроса к Consul DNS:

```bash
dig @127.0.0.1 -p 8600 web-api.service.consul SRV
# → Ответ содержит: IP 192.168.1.50, Port 8080, Weight 10, Priority 1
```

### 3. Логика обнаружения на стороне клиента (Псевдокод)
```python
def get_service_endpoint(service_name):
    # 1. Запрос к реестру
    instances = registry.get_instances(service_name)
    # 2. Фильтрация только здоровых (healthy)
    healthy_ones = [i for i in instances if i.status == "passing"]
    # 3. Балансировка (например, Round Robin)
    target = load_balancer.pick(healthy_ones)
    return target.address, target.port
```

### 4. Проверка здоровья и динамическая маршрутизация (Nginx + Consul)
Автоматическое обновление списка бэкенд-серверов без перезагрузки конфигурации:

```nginx
http {
    # Указываем Consul как источник DNS
    resolver 127.0.0.1:8600 valid=5s;

    upstream backend {
        # Запрос DNS выполняется при каждом обращении
        zone backend_zone 64k;
    }

    server {
        location /api/ {
            # Динамическая переменная: DNS-резолв при каждом запросе
            set $upstream http://web-api.service.consul;
            proxy_pass $upstream;
        }
    }
}
```

### 5. Автоматическая регистрация в Docker (Registrator)
Запуск Registrator, который автоматически регистрирует все контейнеры в Consul:

```bash
docker run -d \
  --name registrator \
  --net host \
  --volume /var/run/docker.sock:/tmp/docker.sock \
  gliderlabs/registrator:latest \
  consul://localhost:8500
```

Контейнеры с меткой `SERVICE_NAME=myapp` автоматически регистрируются в Consul.

## Сравнение Service Discovery по платформам

### Kubernetes (нативный)

В Kubernetes Service Discovery реализован через DNS и API-объекты:

- **CoreDNS** разрешает имена вида `<service-name>.<namespace>.svc.cluster.local`.
- **Service** — стабильная точка входа (VIP + DNS-имя) для группы подов.
- **EndpointSlice** — масштабируемый ресурс, содержащий актуальные IP-адреса подов.
- **Headless Service** (`clusterIP: None`) — DNS возвращает IP-адреса всех подов напрямую (для StatefulSet, Cassandra, Kafka).
- **Проверки готовности** (`readinessProbe`) определяют, включает ли Kubernetes под в список Endpoints.

### Docker Swarm

Docker Swarm использует встроенный DNS-резолвер (`127.0.0.11`) для обнаружения сервисов:

- Имя сервиса (`my-service`) резолвится в VIP (Virtual IP), который балансирует трафик между репликами.
- **DNS Round-Robin** работает через `--endpoint-mode dnsrr` (без VIP, прямой возврат IP).
- **Routing Mesh** обеспечивает доступность сервиса через опубликованный порт на любом узле кластера.

### Proxmox

Proxmox Service Discovery — инструмент для автоматического обнаружения виртуальных машин в кластере Proxmox через DNS. Опрос API Proxmox с периодичностью (по умолчанию 60 секунд), генерация A-записей для VM по именам и тегам, запуск встроенного DNS-сервера для ответов.

- **Подробнее:** **[Proxmox Service Discovery](../Proxmox/proxmox_service_discovery.md)**

### Consul (cross-platform)

Consul работает как независимая платформа Service Discovery, не привязанная к конкретному оркестратору:

- **DNS-интерфейс** (порт 8600) с поддержкой A, AAAA и SRV-записей.
- **HTTP API** для программного доступа с фильтрацией по метаданным.
- **Catalog Sync** для интеграции с Kubernetes (трансляция K8s Services в Consul).
- **Prepared Queries** для сложной маршрутизации с failover.
- **Подробнее:** **[Каталог служб Consul](../Consul/consul_service_catalog.md)**.

### Prometheus (мониторинг)

Prometheus использует Service Discovery для автоматического обнаружения целей (targets):

- **`consul_sd_configs`** — опрос каталога Consul.
- **`kubernetes_sd_configs`** — опрос Kubernetes API (поды, сервисы, ноды, ingress).
- **`dns_sd_configs`** — DNS-записи (A, AAAA, SRV) как источник целей.
- **`file_sd_configs`** — чтение целей из JSON/YAML файлов.
- **Подробнее:** **[Service Discovery и Relabeling в Prometheus](../Prometheus/service_discovery_and_relabeling.md)**.

## Проверки жизнеспособности (Health Checking)

Реестр не просто хранит IP, он гарантирует их работоспособность через проверки:

| Тип проверки | Описание | Применение | Инструменты |
|:---|:---|:---|:---|
| **HTTP Check** | Запрос `GET /health`. Статус 200 — OK. | Проверка готовности бизнес-логики. | Consul, Kubernetes, Prometheus Blackbox |
| **TCP Check** | Попытка установить TCP-соединение на порт. | Проверка доступности порта (БД, кэш). | Consul, Nagios |
| **gRPC Check** | Вызов стандартного метода Health в gRPC сервисе. | Современные микросервисы. | Consul (grpc_health_check), Envoy |
| **Script Check** | Выполнение локального скрипта на узле. | Сложные проверки (свободное место, нагрузка). | Consul, Zabbix |
| **TTL / Heartbeat** | Сервис сам «стучится» в реестр. | Односторонние каналы связи, cron-задачи. | Consul, Eureka |
| **Alias** | Статус зависит от здоровья другого сервиса. | Sidecar-контейнеры, связанные компоненты. | Consul |

### Разделение Liveness и Readiness

В оркестрируемых средах (Kubernetes, Nomad) критически важно разделять два типа проверок:

*   **Liveness:** «Жив ли процесс?» Если проверка падает, контейнер перезапускается (kill + restart). Используйте для обнаружения зависаний (deadlock, infinite loop).
*   **Readiness:** «Готов ли сервис принимать трафик?» Если проверка падает, под исключается из списка Endpoints (трафик не поступает), но процесс продолжает работать. Используйте для проверки готовности кapses (загрузка кэша, подключение к БД, прогрев JIT).

**Антипаттерн:** Использовать один и тот же эндпоинт для Liveness и Readiness. Если сервис «прогревается» долго (например, загружает массивные индексы), readiness-проверка будет падать, а liveness-проверка вызовет бесконечные рестарты.

## Безопасность Service Discovery

Реестр сервисов — это карта всей вашей инфраструктуры. Утечка данных реестра позволяет злоумышленнику точно определить топологию сети, адреса всех сервисов и их зависимости.

### Угрозы

| Угроза | Описание | Последствия |
| :--- | :--- | :--- |
| **Утечка каталога** | Доступ к реестру без аутентификации. | Полная карта сети для атакующего. |
| **Подмена сервиса** | Регистрация ложного инстанса в реестре. | Перехват трафика, внедрение вредоносного кода. |
| **DNS-спуфинг** | Подмена DNS-ответов Service Discovery. | Перенаправление трафика на враждебные серверы. |
| **Отказ в обслуживании** | Засорение реестра ложными записями. | Отказ Service Discovery, недоступность сервисов. |

### Защитные меры

1.  **Аутентификация и авторизация:**
    *   **Consul:** Система ACL (Default Deny). Каждый токен имеет ограниченные права. Подробнее: **[Consul ACL](../Consul/consul_acl.md)**.
    *   **etcd:** RBAC-политики, клиентские TLS-сертификаты, JWT-аутентификация.
    *   **Kubernetes:** RBAC + ServiceAccount для каждого компонента.

2.  **Шифрование:**
    *   **TLS для API:** Все запросы к реестру (HTTP, gRPC) должны передаваться по TLS.
    *   **mTLS в Service Mesh:** Шифрование трафика между сервисами и sidecar-прокси.

3.  **Ограничение доступа к реестру:**
    *   Реестр должен быть доступен только из внутренней сети.
    *   Используйте firewall-политики: Consul (8500/8600), etcd (2379), ZooKeeper (2181).
    *   Отключайте внешний доступ к реестру даже через VPN.

4.  **Иммутабельность записей:**
    *   Регистрация только через CI/CD пайплайны (не через SSH-сессии).
    *   Audit-логирование всех операций регистрации/дерегистрации.

## Диагностика и типичные проблемы

### 1. Проблема «Flapping» (Мерцание)
Сервис постоянно переходит из `Healthy` в `Critical` из-за слишком агрессивных тайм-аутов или перегрузки CPU.

*   **Симптомы:** Алерты регулярно срабатывают и отключаются; трафик «дёргается» между инстансами.
*   **Диагностика:** Проверьте интервалы health check и логи агента.
*   **Решение:** Увеличить `Interval` (минимум 5s), настроить пороги срабатывания (`success_before_passing: 3`, `failures_before_critical: 2`). Подробнее: **[Проверки состояния Consul](../Consul/consul_health_checks.md#пороги-срабатывания-thresholds)**.

### 2. Зависание TTL
Сервис упал, но реестр считает его живым до истечения TTL.

*   **Симптомы:** Клиенты получают ошибки `connection refused` на «живом» по данным реестра адресе.
*   **Диагностика:** Сравните реальное состояние с данными реестра: `curl http://consul:8500/v1/health/service/my-service?passing=false`.
*   **Решение:** Использовать `DeregisterCriticalServiceAfter` (Consul) для автоматической очистки. Уменьшить TTL.

### 3. DNS-кэширование
Клиент (или Java JVM) кэширует DNS-ответ навсегда, игнорируя изменения в реестре.

*   **Симптомы:** После переключения сервиса часть клиентов продолжает обращаться к старому IP.
*   **Диагностика:** Проверьте TTL на стороне клиента (`dig`, `resolvectl status`).
*   **Решение:** Настроить TTL на уровне ОС/приложения на минимальное значение (0-60 секунд). Для Java: `networkaddress.cache.ttl=30`. Для Go: используйте собственный резолвер с кэшированием.

### 4. Split-Brain
Разделение кластера реестра (например, Consul), при котором разные части сети видят разные списки сервисов.

*   **Симптомы:** Два сервиса не могут найти друг друга; разные инженеры видят разные данные в реестре.
*   **Диагностика:** Проверьте кворум: `consul operator raft list-peers`.
*   **Решение:** Использовать нечетное количество серверов (3, 5); мониторить здоровье кворума; настроить изоляцию сетевых сегментов.

### 5. Сервисы-призраки (Ghost Services)
В каталоге отображаются инстансы, которые физически не существуют (старые поды в K8s, остановленные VM).

*   **Симптомы:** Health check возвращает `critical`, но запись не удаляется из каталога.
*   **Диагностика:** Проверьте, настроен ли `deregister_critical_service_after`.
*   **Решение:** В Consul: `deregister_critical_service_after = "5m"`. В Kubernetes: проверьте лайфсайкл подов и finalizers.

### 6. Низкая производительность DNS
DNS-резолвер перегружен запросами при большом количестве сервисов.

*   **Симптомы:** Высокий latency на DNS-запросы (сотни миллисекунд вместо миллисекунд).
*   **Диагностика:** `dig @consul-dns time=5000` — замерьте реальное время ответа.
*   **Решение:** Кэширование DNS на стороне клиента (Systemd-resolved, Nginx resolver), горизонтальное масштабирование DNS-серверов, использование DNS-кэша (NodeLocal DNSCache в Kubernetes).

### Пример: Consul ACL для Service Discovery

Базовая политика для сервиса, который может регистрировать себя и читать каталог:

```hcl
# Политика для веб-сервиса
service "web-api" {
  policy = "write"    # Регистрация, обновление, дерегистрация
}

# Чтение каталога всех сервисов (для обнаружения зависимостей)
service_prefix "" {
  policy = "read"
}
```

### Защита DNS-интерфейса

Consul DNS (порт 8600) по умолчанию доступен без аутентификации. Рекомендации:

1.  Ограничьте доступ через firewall: только доверенные хосты.
2.  Включите `allow_stale = false` для гарантии актуальности DNS-ответов (цена — нагрузка на серверы).
3.  Используйте DNS-over-TLS, если резолверы находятся в незащищенной сети.

## Лучшие практики

*   **Graceful Shutdown:** Всегда отправляйте сигнал дерегистрации при остановке приложения (используйте хуки завершения в коде — `SIGTERM` → дерегистрация → `SIGKILL`).
*   **Использование Метаданных:** Помечайте инстансы версией (`version`) и окружением (`env`). Это критично для Canary-деплоев и фильтрации трафика.
*   **Разделение Health и Readiness:** Liveness для обнаружения зависаний, Readiness для контроля поступления трафика. Не используйте один эндпоинт для обоих.
*   **Безопасность:** Ограничивайте доступ к API реестра (ACL, TLS). Утечка реестра — это карта всей вашей сети для злоумышленника.
*   **Мониторинг лага:** Если реестр использует асинхронную репликацию (Eureka), мониторьте задержку синхронизации между узлами.
*   **DeregisterCriticalServiceAfter:** Всегда настраивайте автоматическое удаление «призраков» — записей о сервисах, которые давно не проходят health check.
*   **Уникальные ID:** Всегда задавайте уникальный `id` для каждого инстанса (включая hostname или UUID), чтобы избежать конфликтов при регистрации нескольких экземпляров на одном узле.
*   **Graceful degradation при недоступности реестра:** Реализуйте fallback на кэшированный список адресов, если реестр временно недоступен. Это предотвратит полный отказ системы.

## Антипаттерны

*   **Hardcoded IP-адреса:** Использование прямых IP вместо DNS-имен. При миграции сервисов все клиенты ломаются.
*   **Регистрация без health check:** Сервис зарегистрирован, но не проверяется. Реестр содержит «мёртвые» записи.
*   **Слишком частые проверки:** Интервал менее 1s создаёт «шторм» запросов в крупных кластерах. Оптимально: 5-30s.
*   **Проверка внешних зависимостей:** Сервис не должен помечать себя как `critical`, если недоступна БД. Используйте Circuit Breaking на уровне приложения.
*   **Единый реестр для всего:** Попытка использовать один Consul-кластер для production, staging и development без изоляции (namespaces/partitions) приводит к взаимовлиянию сред.
