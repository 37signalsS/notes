# Сценарии использования Unikernel

**Актуально для:** Unikraft v0.21.0, KraftKit v0.12.15; примеры для on-premise развёртываний

## Определения

**Сценарии использования юникернелов** (Unikernel Use Cases) — это совокупность практических областей применения, где архитектурные особенности технологии (минимализм, отсутствие переключения контекста, аппаратная изоляция) обеспечивают критическое преимущество перед традиционными виртуальными машинами и контейнерами.

Основные технические характеристики и архитектура Library OS описаны в [Обзоре Unikernel](./unikernel_overview.md).

## Требования для реализации

Для развертывания и тестирования описанных сценариев требуется:
- **Гипервизор:** KVM (рекомендуется для on-premise), Xen (для MirageOS) или QEMU для локальной разработки.
- **Инструментарий сборки:** `kraft` (для Unikraft), `ops` (для Nanos) или `dune` (для MirageOS).
- **Сетевой стек:** Поддержка `virtio-net` или специализированных драйверов типа DPDK для высокопроизводительных сценариев.
- **Аппаратная поддержка:** Intel VT-x или AMD-V (обязательно); Intel SGX/AMD SEV для сценариев доверенных вычислений.
- **Операционная система хоста:** Linux 5.10+ (ядро с включённым KVM); Windows/macOS — только для разработки через QEMU.
- **Дисковое пространство:** Минимум 2 ГБ свободного места для инструментария сборки и образов.

## Основные концепции выбора технологии

Эффективность применения юникернелов определяется следующими архитектурными факторами:

- **Минимальная база доверия (TCB):** Отсутствие шелла, SSH и лишних драйверов минимизирует поверхность атаки. В юникернеле просто негде запустить сторонний код или скрипты.
- **Мгновенный старт (Just-in-Time):** Время загрузки (10–50 мс) позволяет развертывать инфраструктуру в ответ на конкретный сетевой пакет или запрос к API.
- **Экстремальная плотность:** Возможность запускать тысячи изолированных инстансов на одном физическом сервере благодаря потреблению памяти <10 МБ на инстанс.
- **Предсказуемость производительности:** Отсутствие фоновых процессов ОС общего назначения (cron, syslog, kswapd) гарантирует детерминированные задержки (low jitter).

## Практические сценарии применения

### 1. Граничные вычисления и Интернет вещей (Edge & IoT)
Юникернелы являются стандартом для устройств с жесткими ограничениями по ресурсам и узлов, находящихся вне защищенного периметра.

- **Космические технологии и робототехника:** Использование формально верифицированных систем (например, на базе MirageOS) для управления критическими нагрузками. Это исключает целые классы ошибок памяти.
- **Телекоммуникации (5G/6G):** Развертывание Virtual Network Functions (VNF). Юникернелы позволяют динамически масштабировать сетевые функции (firewalls, DPI) за миллисекунды при изменении нагрузки.
- **Сетевые службы:** DNS, NTP и DHCP серверы в образах размером 1–5 МБ. Минимальный размер позволяет хранить тысячи вариантов конфигураций в кэше гипервизора.

### 2. Доверенные вычисления (Confidential Computing)
Минимальный размер кода позволяет проводить полный аудит системы, что критично для безопасности финансовых и медицинских данных.

- **Изоляция баз данных:** Запуск выделенного инстанса БД (например, Redis или SQLite) для каждого клиента внутри отдельного юникернела (Unikraft). Это обеспечивает изоляцию уровня VM при производительности bare-metal.
- **Защищенные анклавы (TEE):** Выполнение кода внутри Intel SGX с минимальной доверенной базой, что снижает риск утечки ключей через уязвимости в ядре ОС.
- **Архитектура Zero Trust:** Юникернел выступает как микро-сегмент сети, где запрещено всё, что не разрешено на этапе компиляции.

### 3. Serverless и эфемерные нагрузки (FaaS / Scale-to-Zero)
Юникернелы решают проблему «холодного старта» (cold start), делая платформы Function-as-a-Service более экономичными и предсказуемыми.

- **Мгновенное масштабирование (Instance Branching):** Современные платформы виртуализации (Firecracker, Unikraft) поддерживают клонирование запущенной микро-ВМ за миллисекунды для параллельной обработки запросов. Это позволяет реализовать паттерн «hot clone» — создание копии работающего инстанса без повторной инициализации.
- **Scale-to-Zero:** Юникернел полностью завершается при отсутствии нагрузки и перезапускается за 10–50 мс при поступлении запроса. В отличие от контейнеров (где холодный старт занимает 200–500 мс), это делает юникернелы пригодными для сервисов с неравномерной нагрузкой (Healthcheck-эндпоинты, webhook-обработчики, API-шлюзы).
- **Экономия ресурсов:** Потребление <10 МБ RAM на инстанс позволяет запускать тысячи функций на одном сервере, что критично для on-premise сред с ограниченным бюджетом на инфраструктуру.

### 4. Высокопроизводительные сети и CDN
Отсутствие переключений между User Space и Kernel Space (Zero-copy) позволяет обрабатывать трафик на скорости физической линии.

- **Кэширующие прокси:** Узлы с экстремально низкой задержкой, работающие напрямую с сетевым стеком через `io_uring` или DPDK.
- **Балансировщики нагрузки:** Программные решения, интегрированные в юникернел, способные обрабатывать миллионы запросов в секунду на минимальном оборудовании.

### 5. CI/CD-интеграция и автоматизация развёртывания (DevOps)
Юникернелы требуют иного подхода к CI/CD по сравнению с контейнерами из-за иммутабельности образов и отсутствия runtime-конфигурации.

#### Сборка в CI/CD-пайплайне
Основная проблема — сборка юникернела занимает больше времени, чем сборка Docker-образа (из-за компиляции всего стека ОС). Рекомендуется использовать кэширование артефактов сборки:

```yaml
# Пример GitLab CI для Unikraft
stages:
  - build
  - test
  - deploy

build-unikernel:
  stage: build
  image: unikraft/kraft:latest
  cache:
    key: unikraft-build-${CI_COMMIT_REF_SLUG}
    paths:
      - .build/
  script:
    - kraft build --target qemu --arch x86_64 --cache-dir .build
  artifacts:
    paths:
      - .build/
      - build/
    expire_in: 1 week

deploy-unikernel:
  stage: deploy
  script:
    - kraft run --headless --background -p ${DEPLOY_PORT}:80
  only:
    - main
```

#### Ключевые особенности CI/CD для юникернелов
- **Нет «logs inside»:** Логи доступны только через stdout гипервизора. В CI-тестах необходимо перехватывать вывод через `--log-file` или `--headless --log-level debug`.
- **Сборка = упаковка:** В отличие от Docker (где `docker build` — это по сути «сборка + упаковка»), в юникернеле этапы компиляции и упаковки в образ гипервизора разделены. `kraft build` создаёт ELF-бинарник, `kraft run` — упаковывает в bootable disk.
- **Реверсивность:** Если приложение не запустилось (Kernel Panic), нет возможности «залезть внутрь» для отладки. В CI должны быть обязательные smoke-тесты с проверкой HTTP-ответа или лога.

### 6. Наблюдаемость (Observability) и мониторинг
Традиционные агенты мониторинга (Node Exporter, Prometheus agent, Zabbix Agent) не могут быть запущены внутри юникернела. В 2026 году стандартным подходом является **Sidecar-less Observability**:

#### Мониторинг на стороне хоста
```bash
# Сбор метрик через eBPF на хосте (Linux 5.10+)
# Мониторинг сетевых вызовов юникернела через TAP-интерфейс
sudo bpftrace -e '
kprobe:virtio_net_xmit {
    printf("virtio_net: %s -> %d bytes\n", comm, arg1);
}'
```

#### OpenTelemetry в приложении
Приложение внутри юникернела должно самостоятельно экспортировать метрики и трейсы:

```python
# Пример интеграции OTel в Python-приложение внутри юникернела
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import OTLPExporter

provider = TracerProvider()
exporter = OTLPExporter(endpoint="http://host-ip:4317")  # Коллектор на хосте
provider.add_span_processor(BatchSpanProcessor(exporter))
trace.set_tracer_provider(provider)
```

#### Стоги наблюдаемости (2026)
| Слой | Инструмент | Место сбора |
| :--- | :--- | :--- |
| **Метрики** | OpenTelemetry SDK → Grafana Alloy/Prometheus | Коллектор на хосте |
| **Логи** | stdout → гипервизор → Loki/Vector | Агрегатор на хосте |
| **Трейсы** | OTel SDK → Jaeger/Tempo | Коллектор на хосте |
| **Сетевой аудит** | eBPF (bpftrace/tc) | Ядро хоста |

### 7. Безопасность и комплаенс (Security Hardening)
Минимальная поверхность атаки юникернела — это ключевое преимущество, но оно требует специфичных подходов к аудиту.

#### Аудит образа перед развёртыванием
```bash
# Проверка состава образа (Unikraft)
kraft image list --json | jq '.[] | {name: .name, size: .size, libs: .libraries}'

# Проверка открытых портов (nmap с внешнего хоста)
nmap -sT -p- <IP_юникернела>
# Ожидаемый результат: открыты только порты, явно прописанные в приложении
```

#### Валидация isolation
```bash
# Проверка, что юникернел изолирован от хоста
# 1. Процесс юникернела не должен иметь доступа к /dev/kvm напрямую
ls -la /proc/$(pgrep -f "qemu.*unikernel")/fd | grep kvm
# → должно вернуть пустой результат или только virtio-устройства

# 2. Проверка seccomp/ AppArmor профиля хоста
aa-status | grep qemu
```

#### Compliance-чеклист
- [ ] Образ скомпилирован из проверенного источника (SBOM)
- [ ] Отсутствуют отладочные символы (`strip` при сборке)
- [ ] Используется аппаратная изоляция (KVM/Xen), не QEMU-эмуляция
- [ ] Сетевые порты минимальны и документированы
- [ ] Логи экспортируются в централизованную систему
- [ ] Версия гипервизора и библиотек зафиксирована в SBOM

### 9. Disaster Recovery и резервное копирование
Восстановление юникернелов после сбоя отличается от контейнеров: нет overlay-файловых систем, нет persistent volume в привычном понимании.

#### Стратегии восстановления
- **Rebuild from Source (рекомендуется):** Юникернел — это компилируемый артефакт. Источник кода + конфигурация сборки = воспроизводимый образ. Храните `kraft.yaml` / `ops.json` в Git.
- **Snapshot-восстановление:** Firecracker и аналогичные платформы snapshot'инга позволяют создавать снимки состояния запущенных инстансов и восстанавливать их за миллисекунды.
- **Image Registry:** Хранение скомпилированных образов в registry (аналог Docker Registry, но для bootable images).

```bash
# Создание снапшота (Firecracker / платформы с поддержкой snapshot'инга)
# Конкретный синтаксис зависит от платформы: Firecracker, QEMU с dirty-bitmaps,
# или встроенные средства гипервизора. Принцип: сохранить память + диск
# инстанса в атомарный артефакт для последующего восстановления.
```

#### RPO/RTO для юникернелов
| Стратегия | RPO (Recovery Point) | RTO (Recovery Time) | Комментарий |
| :--- | :--- | :--- | :--- |
| **Rebuild from Source** | 0 (Git) | 1–5 мин (сборка) | Требует наличия CI/CD и кэша сборки |
| **Snapshot Restore** | Момент снапшота | 10–50 мс | Требует хранилища снапшотов |
| **Image Registry** | Последний push | 5–10 сек (запуск) | Образ должен быть заранее собран |

## Пример реализации: Веб-сервер на Unikraft

Типичный процесс развертывания легковесного сервиса на on-premise сервере с KVM:

### Предварительные требования (хост)
```bash
# Проверка аппаратной виртуализации
grep -E 'vmx|svm' /proc/cpuinfo
# → должно показать vmx (Intel) или svm (AMD)

# Проверка доступности KVM
ls -la /dev/kvm
# → crw-rw---- 1 root kvm 10, 232 ...

# Добавление пользователя в группу KVM (если не root)
sudo usermod -aG kvm $USER
```

### Шаг 1: Подготовка проекта
```bash
# Установка kraft (если не установлен)
curl -sSf https://get.kraftkit.sh | bash

# Создание нового проекта
kraft init -p python3 my-service
cd my-service

# Просмотр доступных библиотек
kraft pkg list
```

### Шаг 2: Конфигурация (`kraft.yaml`)
```yaml
spec: v0.6
name: my-service
    unikraft: v0.21.0

# Целевая платформа
targets:
  - name: qemu
    architecture: x86_64

# Необходимые библиотеки
libraries:
  - name: python3
    version: latest
  - name: lwip
    version: latest

# Маршрутизация портов
networks:
  - name: bridge0

# Переменные окружения (внедряются при сборке, не в runtime)
env:
  PYTHONUNBUFFERED: "1"
```

### Шаг 3: Сборка образа
```bash
# Сборка с выводом логов
kraft build --target qemu --arch x86_64 --log-level debug

# Проверка размера образа
ls -lh build/my-service*
# → -rw-r--r-- 1 user staff 4.2M ... my-service-qemu-x86_64
```

### Шаг 4: Запуск
```bash
# Запуск с привязкой порта
kraft run -p 8080:80

# Результат: система загружается за ~20 мс, потребляя <8 МБ RAM
# Проверка:
curl http://localhost:8080/
# → Hello from Unikraft!
```

### Шаг 5: Headless-запуск (для серверов)
```bash
# Запуск в фоне (без интерактивного терминала)
kraft run --headless --background \
  --name my-service-prod \
  -p 8080:80 \
  --log-file /var/log/unikernel/my-service.log

# Проверка статуса
kraft ps
# → NAME              STATE   PID    PORTS        MEMORY
# → my-service-prod   Running 12345  0.0.0.0:8080 6.4M
```

## Валидация и мониторинг

Для подтверждения успешного развертывания и корректной работы используются следующие методы:

### Проверка времени старта
```bash
# Замер времени от команды запуска до готовности порта
time kraft run --headless --background -p 9090:80 2>/dev/null &
PID=$!
sleep 0.1  # юникернел уже должен быть готов
time curl -s http://localhost:9090/ > /dev/null
# → Ожидаемый результат: <100 мс от запуска до первого ответа
kill $PID 2>/dev/null
```

### Анализ поверхности атаки
```bash
# Проверка состава бинарного файла
file build/my-service-qemu-x86_64
# → ELF 64-bit LSB executable, x86-64, ... statically linked

# Проверка отсутствия отладочных символов
readelf -S build/my-service-qemu-x86_64 | grep debug
# → (пусто = символы удалены)

# Проверка использованных библиотек
nm -u build/my-service-qemu-x86_64 | head -20
# → только необходимые функции
```

### Мониторинг ресурсов
```bash
# Мониторинг процесса юникернела на хосте
ps aux | grep qemu | grep my-service
# →  user  12345  ...  -m 64M -smp 2 ...  (64 МБ RAM, 2 vCPU)

# Мониторинг через virt-top (если установлен)
sudo virt-top -d 1
# → показывает все запущенные юникернелы и их потребление

# Проверка сетевых соединений
ss -tlnp | grep 8080
# → LISTEN  0  128  0.0.0.0:8080  0.0.0.0:*  users:(("qemu-system-x86_64",pid=12345,fd=5))
```

### Валидация через Prometheus (экспортер на хосте)
```yaml
# Конфигурация Prometheus для сбора метрик гипервизора
scrape_configs:
  - job_name: 'unikernel-host'
    static_configs:
      - targets: ['host-ip:9100']  # Node Exporter на хосте
  - job_name: 'unikernel-app'
    static_configs:
      - targets: ['host-ip:4318']  # OTel Collector (HTTP)
```

## Устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Kernel Panic при загрузке** | Несоответствие драйвера гипервизора (например, Virtio) | Проверить флаги компиляции и поддержку гипервизора в `kraft.yaml`. Убедиться, что target и arch совпадают с архитектурой хоста. |
| **Сетевая недоступность** | Отсутствие библиотеки сетевого стека (lwip/musl) | Добавить `lib-lwip` в конфигурацию сборки. Проверить наличие TAP-интерфейса: `ip link show tap0`. |
| **Низкая производительность** | Использование медленного эмулятора вместо KVM | Убедиться, что аппаратная виртуализация включена (`/dev/kvm` доступен). Проверить: `kvm-ok` (из пакета `cpu-checker`). |
| **Ошибка сегментации** | Попытка выполнить системный вызов, не реализованный в Library OS | Использовать `strace` на стороне гипервизора для поиска отсутствующих syscalls. Проверить POSIX-совместимость в документации фреймворка. |
| **"Silent crash" (молниеносное падение)** | Нехватка выделенной RAM или отсутствие драйвера консоли | Проверить логи гипервизора: `dmesg | tail -20`. Увеличить `-m` (RAM) в параметрах запуска. |
| **Тайм-аут при подключении** | Сетевой стек не инициализирован или конфликт портов | Проверить логи: `kraft logs <имя>`. Убедиться, что порт не занят другим процессом: `ss -tlnp | grep <порт>`. |
| **Сборка завершается нехваткой памяти** | Сложные библиотеки требуют много RAM при компиляции | Увеличить лимит памяти для процесса сборки (если в контейнере) или использовать swap на хосте. |
| **Юникернел не отвечает на HTTP** | Приложение слушает на 127.0.0.1 вместо 0.0.0.0 | Убедиться, что приложение привязано к `0.0.0.0:80`, а не `localhost:80`. |
