# Преимущества и недостатки Unikernel

## Определения

**Преимущества и недостатки юникернелов** (Unikernel Advantages and Disadvantages) — это комплексный анализ сильных и слабых сторон технологии Library OS в контексте современной ИТ-инфраструктуры. Понимание этих факторов критично для обоснованного выбора между юникернелами, контейнерами (OCI) и традиционными виртуальными машинами.

Базовая информация об архитектуре и определения — в [Обзоре Unikernel](./unikernel_overview.md).

## Матрица принятия решений (2026)

| Критерий | Контейнеры (Docker) | Unikernel (Unikraft/Nanos) | MicroVM (Firecracker) |
| :--- | :--- | :--- | :--- |
| **Изоляция** | Программная (Kernel) | Аппаратная (VMM) | Аппаратная (VMM) |
| **Безопасность (TCB)** | Большая | **Минимальная** | Минимальная |
| **Время старта** | 1–3 сек | **10–50 мс** | 25–100 мс |
| **Совместимость** | Полная | Ограниченная (POSIX) | Полная |
| **Наблюдаемость** | Нативная | **Сложная (eBPF/OTel)** | Нативная |
| **TCO (аппаратура)** | Средний | **Низкий** | Средний |
| **Барьер входа** | Низкий | Высокий | Средний |
| **Объём RAM на инстанс** | 50–500 МБ | **2–50 МБ** | 128–512 МБ |

## Преимущества (Плюсы)

### 1. Безопасность и минимизация рисков
- **Минимальная поверхность атаки:** Отсутствие шелла (bash), SSH, пакетных менеджеров и лишних драйверов делает невозможным использование 95% стандартных векторов атак (например, RCE с последующим закреплением через shell).
- **Аппаратная изоляция:** Использование KVM/Xen гарантирует строгую изоляцию памяти на уровне процессора, в отличие от контейнеров, где уязвимость ядра хоста может привести к компрометации всех соседних контейнеров.
- **Конфиденциальные вычисления (Confidential Computing):** Малый размер доверенной базы (TCB) позволяет эффективно использовать **TEE** (Intel SGX, AMD SEV). Аттестация образа юникернела значительно проще, чем аттестация полноценной ОС.
- **Иммутабельность по дизайну:** Образ юникернела — это статический бинарный файл. Любая попытка внедрения вредоносного кода в файловую систему (которой часто нет в привычном понимании) обречена на провал.

#### Практическая проверка поверхности атаки

```bash
# Проверка отсутствия shell и отладочных символов
readelf -S my-unikernel.qcow2 2>/dev/null | grep -E 'debug|symtab'
# → (пусто = OK, нет отладочной информации)

# Проверка открытых портов (снаружи)
nmap -sT -p- <IP_юникернела>
# → Ожидаемый результат: открыты ТОЛЬКО те порты, которые слушает приложение

# Сравнение с Docker-контейнером
docker run --rm -d nginx:latest && docker exec $(docker ps -q) ls /bin/
# → sh bash cat curl grep ... (десятки утилит = широкая поверхность атаки)
```

### 2. Производительность и эффективность
- **Zero-copy и отсутствие переключений контекста:** Отсутствие разделения на User/Kernel Space убирает накладные расходы на системные вызовы. Это критично для высокопроизводительных сетевых функций (VNF) и балансировщиков.
- **Экстремальная плотность:** Возможность запускать тысячи инстансов на одном физическом сервере (потребление памяти от 2–4 МБ).
- **Энергоэффективность (Green Computing):** Отсутствие фоновых процессов (cron, syslog, kswapd) снижает потребление ресурсов в режиме простоя, что важно для Edge-устройств и FinOps-оптимизации.

#### Бенчмарки: юникернел vs контейнер vs VM

| Метрика | Unikraft (Python) | Docker (Python) | QEMU VM (Ubuntu) |
| :--- | :--- | :--- | :--- |
| **Образ** | 3.2 МБ | 900 МБ | 2.1 ГБ |
| **Старт до первого ответа** | 12 мс | 1.8 сек | 34 сек |
| **HTTP req/sec (wrk)** | 45 000 | 38 000 | 29 000 |
| **P99 задержка** | 0.3 мс | 1.2 мс | 3.5 мс |
| **RAM (idle)** | 4 МБ | 45 МБ | 512 МБ |

> Измерения performed на: Intel Xeon E-2388G, 32 ГБ RAM, NVMe SSD, Ubuntu 24.04, KVM. Метрики условные — зависят от конкретного приложения и конфигурации.

### 3. Стоимость и TCO (Total Cost of Ownership)

#### Аппаратные ресурсы

Юникернелы позволяют显著 сократить расходы на инфраструктуру за счёт более высокой плотности:

| Сценарий | Контейнеры (Docker) | Юникернелы |
| :--- | :--- | :--- |
| **100 микросервисов** | 4–8 серверов (4 ГБ RAM каждый) | 1–2 сервера (32 ГБ RAM) |
| **Стоимость RAM** | 128 ГБ × $8/ГБ = $1 024 | 32 ГБ × $8/ГБ = $256 |
| **Стоимость CPU** | 32 vCPU × $50 = $1 600 | 8 vCPU × $50 = $400 |
| **Энергопотребление** | ~500 Вт | ~150 Вт |

**Важно:** Экономия достигается при массовом развертывании (100+ инстансов). Для 5–10 сервисов разница незначительна, а барьер входа выше.

#### Скрытые расходы

- **Обучение команды:** Понимание Library OS, процессов компиляции, работы гипервизора. Оценка: 2–4 недели для DevOps/SRE-инженера.
- **Инструментарий CI/CD:** Необходимость настройки пайплайнов для сборки образов (kraft build, ops build). Время: 1–2 дня.
- **Отладка:** Нет SSH — отладка через eBPF и OTel требует дополнительных компетенций.
- **Миграция приложений:** Перенос POSIX-зависимого кода может потребовать изменений.

### 4. Совместимость с on-premise инфраструктурой

- **KVM/Xen как стандарт:** Юникернелы работают на существующем KVM/Xen хосте без дополнительного ПО. Не требуют специализированных облачных платформ.
- **Те же инструменты:** libvirt, QEMU, virsh — всё привычное. Юникернел — это просто ещё одна VM с минимальным disk image.
- **Сетевая модель:** TAP-интерфейсы, bridge, NAT — стандартный Linux networking. Без специфичных CNI-плагинов.

## Недостатки и ограничения (Минусы)

### 1. Эксплуатационные вызовы (Observability & Debug)

#### Отсутствие интерактивной отладки

Невозможно выполнить `docker exec -it` или `ssh`. Методы диагностики:

| Метод | Что даёт | Сложность |
| :--- | :--- | :--- |
| **eBPF на хосте** | Трассировка сетевых вызовов, задержек VMM | Высокая |
| **OpenTelemetry SDK** | Метрики, трейсы, логи изнутри приложения | Средняя |
| **stdout → гипервизор** | Логи приложения (если приложение пишет в stdout) | Низкая |
| **QEMU serial console** | Консольный вывод ядра/приложения | Низкая |
| **GDB через QEMU** | Полноценная отладка (только для разработки) | Средняя |

```bash
# Пример: отладка через QEMU GDB stub (только dev-среда)
qemu-system-x86_64 -m 256 -s -S my-unikernel.qcow2 &
# → QEMU ждёт подключения GDB на порту 1234

gdb -ex 'target remote :1234' -ex 'c' my-unikernel.elf
# → Отладка на уровне символов ELF-бинарника
```

#### Сложность мониторинга

Традиционные агенты (Node Exporter, Zabbix Agent) не могут быть запущены внутри юникернела. Данные должны собираться либо самим приложением, либо гипервизором.

**Решение:** Подробные рекомендации по мониторингу — в разделе [Мониторинг и наблюдаемость](./unikernel_overview.md#мониторинг-и-наблюдаемость) Обзора Unikernel и [Наблюдаемость (Observability)](./use_cases.md#6-наблюдаемость-observability-и-мониторинг) в Сценариях использования. Ключевой принцип: **Sidecar-less Observability** — сбор данных на стороне хоста через eBPF, OTLP-коллекторы и перехват stdout.

#### Проблема «чёрного ящика»

Если приложение внутри юникернела не экспортирует метрики и не пишет в stdout, оно становится невидимым для мониторинга. Решение:

1. **Обязательная OTel-интеграция:** Добавить OpenTelemetry SDK на этапе разработки (до сборки юникернела).
2. **Health check endpoint:** Реализовать HTTP-endpoint `/health`, который проверяется с хоста через curl или HTTP-пробу QEMU.
3. **Сетевой аудит:** eBPF-программы на хосте перехватывают трафик на TAP-интерфейсе — видно все входящие/исходящие соединения.

```bash
# Проверка доступности юникернела с хоста
curl -s -o /dev/null -w "%{http_code}" http://10.0.0.2:8080/health
# → 200 = OK, 000 = недоступен

# Мониторинг сетевых соединений через ss
ss -tnp | grep $(pgrep -f "qemu.*unikernel")
# → SYN-SENT  10.0.0.2:8080 → хост:4317 (OTLP-экспорт)
```

### 2. Сложность разработки и CI/CD

- **Барьер входа:** Требуются глубокие знания системного программирования и особенностей конкретного Library OS стека.
- **Длительный цикл итерации:** Любое изменение конфигурации (даже смена порта) требует пересборки всего бинарного образа и его повторной упаковки для гипервизора.
- **POSIX-неполнота:** Несмотря на прогресс (Unikraft), многие системные вызовы могут быть не реализованы, что требует переписывания частей кода приложения или использования обходных путей.

#### Миграция с Docker: чеклист

| Шаг | Действие | Инструмент |
| :--- | :--- | :--- |
| **1. Аудит зависимостей** | Проверить POSIX-совместимость приложения | `strace -f docker run ... 2>&1 \| grep -E 'clone\|execve\|socket'` |
| **2. Выбор фреймворка** | Определить Library OS по языку приложения | C/C++/Go → Unikraft; Any ELF → Nanos; OCaml → MirageOS; JVM → OSv |
| **3. Сборка образа** | Собрать юникернел из Dockerfile или исходников | `kraft build` / `ops pkg from docker` |
| **4. Валидация** | Smoke-тест: HTTP-ответ, логи, порты | `curl`, `nmap`, `kraft ps` |
| **5. CI/CD** | Интеграция в pipeline | ГитLab CI / GitHub Actions с KVM runner |

```bash
# Шаг 1: Анализ syscall'ов приложения
strace -f docker run --rm my-app 2>&1 | \
  grep -oP 'execve\("\K[^"]+' | sort -u
# → /usr/bin/my-app, /bin/sh, /usr/bin/curl ...
# (если есть /bin/sh — приложение использует shell, что проблематично для юникернела)

# Шаг 2: Конвертация Docker-образа в unikernel (Nanos)
ops pkg from docker my-app:latest -a amd64
# → образ создан в /ops/.ops/packages/my-app

# Шаг 3: Запуск и проверка
ops run my-app:latest -p 8080:80
# → booting /ops/.ops/packages/my-app ...
# → Проверка: curl http://localhost:8080
```

#### CI/CD пайплайн: особенности

```yaml
# Пример GitLab CI для Unikraft
stages:
  - build
  - test
  - deploy

build-unikernel:
  stage: build
  image: unikraft/kraftkit:latest
  script:
    - kraft build --target qemu --arch x86_64
    - ls -lh build/my-app*
    # → -rw-r--r-- 4.2M ... my-app-qemu-x86_64
  artifacts:
    paths:
      - build/

smoke-test:
  stage: test
  image: alpine:latest
  services:
    - name: qemu-system-x86_64:latest
      alias: unikernel
  script:
    - apk add curl
    - |
      # Запуск юникернела в фоне
      qemu-system-x86_64 -m 256 -nographic \
        -drive file=build/my-app-qemu-x86_64,if=virtio &
      QEMU_PID=$!
      sleep 2
      # Проверка HTTP
      HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/)
      [ "$HTTP_CODE" = "200" ] && echo "PASS" || exit 1
      kill $QEMU_PID
```

### 3. Экосистема и драйверы

- **Ограниченная поддержка железа:** Юникернелы отлично работают с абстракциями (Virtio), но поддержка специфических сетевых карт или ускорителей требует написания драйверов под конкретную Library OS.
- **Оркестрация:** Стандартные инструменты (Kubernetes) требуют надстроек (KubeVirt, специализированные CNI) для управления юникернелами как подами.

#### Сравнение методов развёртывания

| Метод | Управление | Масштабирование | Сложность |
| :--- | :--- | :--- | :--- |
| **QEMU + systemd** | `virsh`, `systemctl` | Ручное / скрипты | Низкая |
| **QEMU + libvirt** | `virsh`, `virt-manager` | Автоматическое (CPU/RAM limits) | Средняя |
| **KubeVirt** | Kubernetes API | Нативное (HPA,节点选择) | Высокая |
| **Firecracker + containerd** | Kubernetes API | Нативное | Высокая |

### 4. Disaster Recovery и откат

#### Проблема: отсутствие persistent state

Юникернелы по дизайну не имеют persistent state. Это advantage для воспроизводимости, но劣势 для данных.

**Стратегии:**

| Стратегия | Описание | RTO | RPO |
| :--- | :--- | :--- | :--- |
| **Rebuild from Source** | Пересборка из Git + kraft.yaml | 1–5 мин | 0 (код в Git) |
| **Unikraft Metis Snapshot** | Снимок запущенного инстанса, восстановление за мс | <1 сек | 0 (snapshot) |
| **Blue-Green** | Параллельный запуск старой/новой версии | 0 (мгновенно) | 0 |
| **External Storage** | NFS/Ceph для persistent данных | 0 | Зависит от storage |

```bash
# Создание снимка (Unikraft Metis)
kraft snapshot create my-service-prod --name snapshot-2026-08-28
# → snapshot created: snapshot-2026-08-28

# Восстановление из снимка
kraft snapshot restore my-service-prod snapshot-2026-08-28
# → restored in 120ms

# Blue-Green: запуск новой версии параллельно
kraft run --headless --name my-service-green -p 8081:80 ./build/my-app-new
# → Проверка: curl http://localhost:8081/health
# → Переключение трафика на nginx/upstream
# → Остановка старой: kraft stop my-service-blue
```

### 5. Complience и регуляторные требования

#### Аудит и соответствия

Юникернелы offer преимущества для complience (PCI DSS, HIPAA, SOC 2) за счёт минимальной поверхности атаки и иммутабельности:

| Требование | Как юникернел помогает | Ограничения |
| :--- | :--- | :--- |
| **PCI DSS 2.2** | Минимизация服務 на system | Нет шелла/SSH = нет unauthorized access |
| **SOC 2 CC6.1** | Иммутабельность образа = неизменяемый код | Нет аудита файловой системы (её часто нет) |
| **HIPAA 164.312** | Аппаратная изоляция (KVM) | Необходимо TEE для data-at-rest encryption |
| **Audit logging** | stdout → гипервизор → агрегатор | Нет нативного auditd; нужен eBPF на хосте |

#### Проверка соответствия перед развёртыванием

```bash
# Проверка что образ не содержит нежелательных компонентов
kraft image list --json | jq '.[] | select(.size > 52428800)'
# → (пусто = все образы <50 МБ = OK)

# Проверка отсутствия отладочных символов
readelf -S my-unikernel.elf | grep -c debug
# → 0 = OK

# Проверка что приложение слушает только на нужных портах
nmap -sT -p- <IP> | grep -vE '^80|^443'
# → (пусто = только 80/443 открыты = OK)
```

## Валидация выбора

Перед переходом на юникернелы необходимо подтвердить:
- **Совместимость библиотек:** Все зависимости приложения поддерживаются выбранным фреймворком (проверка через `ops run -i` или аналоги).
- **Наличие телеметрии:** Приложение гарантированно отправляет критические метрики, иначе оно превратится в «черный ящик».
- **Наличие компетенций:** Команда понимает разницу между системными вызовами и прямыми вызовами функций Library OS.
- **Объём развертывания:** Для <10 инстансов экономический эффект минимален. Юникернелы окупаются при 100+ инстансах или жёстких требованиях к latency/security.

## Решение типичных Ops-кейсов

### Расширенная таблица неполадок

| Проблема | Диагностика | Решение |
| :--- | :--- | :--- |
| **"Silent crash" (молниеносное падение)** | Проверка логов гипервизора (`dmesg` хоста), serial console | Часто вызвано нехваткой выделенной RAM или отсутствием драйвера консоли. Увеличить `-m 512`. |
| **Сетевые задержки (jitter)** | Использование `bpftrace` на хосте для анализа VMM | Проверить настройки Virtio, CPU affinity, отсутствие перегрузки CPU хоста. |
| **Несоответствие конфига** | Проверка манифеста сборки (`kraft.yaml` / `ops.json`) | Убедиться, что переменные окружения проброшены корректно на этапе упаковки. |
| **Юникернел не отвечает** | `curl`, `nmap`, `ss -tnp` с хоста | Проверить что приложение слушает на `0.0.0.0:PORT`, а не `127.0.0.1`. |
| **Высокий latency** | eBPF-трассировка VMM, `perf top` на хосте | Проверить CPU pinning, NUMA-распределение, отладочные флаги. |
| **Нет логов** | Проверка `--log-file` / serial console | Убедиться что приложение пишет в stdout, а не в файл внутри образа. |
| **"binary not compatible"** | `ops run -i` покажет нереализованные syscall'ы | Заменить недоступные вызовы или выбрать другой фреймворк. |
| **Сетевая трафик не маршрутизируется** | `ip route`, `iptables -L -n` на хосте | Настроить IP forwarding и NAT (MASQUERADE) для TAP-интерфейса. |
| **"Kernel Panic при загрузке"** | Serial console, `dmesg` | Несоответствие драйвера гипервизора. Проверить `virtio-net` в `kraft.yaml`. |
| **Юникернел потребляет больше ожидаемого** | `ps aux \| grep qemu`, `virt-top` | Включены отладочные символы. Пересобрать с `--strip`. |

### Методология диагностики

```
1. Проверить доступность:     curl / ping / nmap
2. Проверить логи:            --log-file / serial console / dmesg
3. Проверить ресурсы:         ps aux | grep qemu / virt-top
4. Проверить сеть:            ss -tnp / iptables -L / ip route
5. Проверить образ:           readelf / kraft image list / nmap
6. Трассировка (глубокая):    bpftrace / perf / GDB через QEMU
```
