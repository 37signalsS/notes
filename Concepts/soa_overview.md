# Сервис-ориентированная архитектура (SOA)

## Определения

**Сервис-ориентированная архитектура (Service-Oriented Architecture, SOA)** — это архитектурный стиль проектирования программного обеспечения, в котором система строится из набора независимых сервисов, взаимодействующих через четко определенные интерфейсы (контракты). 

В классическом корпоративном исполнении SOA ориентирована на интеграцию разнородных (heterogeneous) систем и приложений внутри предприятия, часто используя центральное связующее ПО — **сервисную шину предприятия (Enterprise Service Bus, ESB)**.

### Ключевые термины
*   **Сервисный контракт (Service Contract):** Формализованное описание интерфейса сервиса (например, через WSDL), включающее входные/выходные параметры, политики безопасности и гарантии качества (SLA).
*   **SOA Governance (Управление SOA):** Набор политик, процессов и инструментов для контроля жизненного цикла сервисов: от проектирования и публикации до вывода из эксплуатации.
*   **Композитный сервис (Composite Service):** Сервис, объединяющий функциональность нескольких атомарных сервисов для реализации сложного бизнес-процесса.

## Базовые концепции

### Ключевые принципы

*   **Слабая связанность (Loose Coupling):** Потребители зависят только от контракта сервиса, а не от его внутренней реализации или платформы (Java, .NET, Mainframe).
*   **Абстракция:** Детали реализации скрыты. Потребителю доступно только описание интерфейса.
*   **Автономность:** Сервисы обладают полным контролем над логикой и данными в рамках своей бизнес-функции.
*   **Многократное использование (Reusability):** Сервис проектируется как универсальный кирпичик, который может быть использован в разных бизнес-процессах организации.
*   **Обнаруживаемость (Discoverability):** Сервисы публикуются в реестрах, где их могут найти потенциальные потребители.

### Роль Сервисной шины предприятия (ESB)

ESB является «интеллектуальным центром» классической SOA. В отличие от микросервисов, где каналы связи «глупые», ESB реализует паттерн **VETRO**:
1.  **V (Validate):** Проверка входящего сообщения на соответствие схеме (XML/JSON).
2.  **E (Enrich):** Обогащение данных (добавление информации из других источников).
3.  **T (Transform):** Преобразование форматов (например, SOAP в REST или старый бинарный протокол в XML).
4.  **R (Route):** Маршрутизация запроса на основе содержимого (Content-based routing).
5.  **O (Operate):** Вызов целевого сервиса.

### Протоколы и стандарты

SOA опирается на открытые стандарты для обеспечения интероперабельности:
*   **SOAP (Simple Object Access Protocol):** XML-протокол обмена данными с поддержкой сложных транзакций и безопасности (WS-Security).
*   **WSDL (Web Services Description Language):** XML-язык для формального описания «что делает сервис» и «как к нему обратиться».
*   **UDDI (Universal Description, Discovery, and Integration):** Стандарт для создания реестров сервисов (в 2026 году вытеснен современными Service Catalogs типа Backstage).
*   **REST/JSON:** Широко применяется в современных «легковесных» реализациях SOA.

## Практические сценарии

### Когда использовать SOA
*   **Интеграция унаследованных систем (Legacy Integration):** Когда нужно объединить современные облачные приложения с банковским мейнфреймом или ERP-системой.
*   **B2B-взаимодействие:** Организация надежных каналов обмена данными с партнерами через стандартизированные SOAP-интерфейсы.
*   **Сложная оркестрация:** Когда бизнес-логика требует последовательного вызова 10-15 сервисов с откатами и компенсациями.

### Сравнение: SOA vs Микросервисы

| Характеристика | SOA (Классика) | Микросервисы |
| :--- | :--- | :--- |
| **Центр управления** | Умная шина (ESB) | Интеллектуальные сервисы, простая сеть |
| **Стиль интеграции** | Оркестрация (централизовано) | Хореография (событийная модель) |
| **Данные** | Общие БД для групп сервисов | Database-per-Service (строгая изоляция) |
| **Гранулярность** | Крупная (бизнес-функция) | Мелкая (один домен / контекст) |
| **Управление** | Централизованное (Governance) | Децентрализованное (Self-service) |

## Дополнительная информация

### Эволюция в 2026 году
Классическая SOA трансформировалась. Современные корпоративные архитектуры используют:
*   **API Management (Apigee, Kong):** Как облегченную версию ESB для управления внешними контрактами.
*   **Service Mesh (Istio):** Как распределенную замену шине для управления внутренним (East-West) трафиком.
*   **Event Mesh:** Эволюция шины событий для асинхронного взаимодействия.
