# Сервис-ориентированная архитектура (SOA)

## Определения

**Сервис-ориентированная архитектура (Service-Oriented Architecture, SOA)** — это архитектурный стиль проектирования программного обеспечения, в котором система строится из набора независимых сервисов, взаимодействующих через четко определенные интерфейсы (контракты). 

В классическом корпоративном исполнении SOA опирается на использование центрального связующего звена — **сервисной шины предприятия (Enterprise Service Bus, ESB)** — для интеграции разнородных систем.

**Сервисный контракт (Service Contract)** — формализованное описание интерфейса сервиса, включающее входные и выходные параметры, протоколы взаимодействия и гарантии качества обслуживания (QoS).

## Базовые концепции

### Ключевые принципы

*   **Слабая связанность (Loose Coupling):** сервисы минимизируют зависимости друг от друга, полагаясь только на контракты, а не на детали внутренней реализации.
*   **Абстракция:** внутренняя логика сервиса скрыта от потребителей.
*   **Многократное использование (Reusability):** сервисы проектируются как универсальные бизнес-функции, которые могут быть востребованы различными частями организации.
*   **Автономность:** сервисы контролируют логику, которую они инкапсулируют.

### Компоненты инфраструктуры SOA

1.  **Потребители (Consumers):** приложения или другие сервисы, вызывающие функции провайдеров.
2.  **Провайдеры (Providers):** сервисы, реализующие бизнес-логику и публикующие свои контракты.
3.  **Реестр сервисов (Service Registry):** централизованный каталог (например, UDDI), где провайдеры публикуют свои интерфейсы, а потребители могут их найти.
4.  **Сервисная шина предприятия (ESB):** «умная» инфраструктура, которая берет на себя:
    *   **Маршрутизацию:** направление запроса к нужному сервису.
    *   **Трансформацию:** преобразование форматов данных (например, XML в JSON).
    *   **Оркестрацию:** объединение нескольких простых сервисов в сложный бизнес-процесс.

### Протоколы и стандарты

Исторически SOA тесно связана с семейством стандартов **WS-* (Web Services)**:
*   **SOAP (Simple Object Access Protocol):** протокол обмена сообщениями на базе XML.
*   **WSDL (Web Services Description Language):** язык описания интерфейсов и способов доступа к сервису.
*   **REST:** хотя SOA чаще ассоциируется с SOAP, современные реализации могут использовать RESTful-сервисы.

## Практические сценарии

### Когда использовать SOA

*   **Корпоративная интеграция (EAI):** объединение старых (legacy) и новых систем разных вендоров в единый ландшафт.
*   **Сложные бизнес-процессы:** автоматизация цепочек действий, требующих участия множества департаментов и различных баз данных.
*   **Стандартизация:** внедрение единых правил взаимодействия и безопасности в масштабе всей организации.

### Сравнение: SOA vs Микросервисы

Микросервисы часто называют «SOA, сделанной правильно», но между ними есть концептуальные различия:

| Характеристика | SOA (Классика) | Микросервисы |
| :--- | :--- | :--- |
| **Связующее звено** | Умная шина (ESB) | Простые каналы (API Gateway, брокеры) |
| **Управление данными** | Общая база данных (часто) | Изолированная база на каждый сервис |
| **Стиль интеграции** | Оркестрация через ESB | Хореография и асинхронность |
| **Размер сервиса** | Крупный (бизнес-функция) | Мелкий (одна задача / домен) |
| **Протоколы** | Тяжелые (SOAP, XML) | Легкие (REST, gRPC, JSON) |

## Дополнительная информация

В современном DevOps-мире классическая SOA с тяжелыми ESB считается избыточной для гибких систем. Однако её принципы «контрактного» взаимодействия легли в основу современного проектирования API.
