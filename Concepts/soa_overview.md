# Сервис-ориентированная архитектура (SOA)

## Определения

**Сервис-ориентированная архитектура (Service-Oriented Architecture, SOA)** — это архитектурный подход, при котором система состоит из независимых, слабо связанных сервисов, взаимодействующих друг с другом через стандартизированные протоколы и центральный компонент — **сервисную шину предприятия (Enterprise Service Bus, ESB)**.

В отличие от микросервисов, сервисы в SOA могут быть более крупными и охватывать широкие бизнес-функции.

## Базовые концепции

### Компоненты классической SOA

- **Потребители (Consumers):** Клиентские приложения, браузеры или другие сервисы, которые инициируют запросы.
- **Сервисная шина предприятия (ESB):** Центральный компонент, который выступает в роли "умного" посредника. ESB отвечает за маршрутизацию, преобразование протоколов, оркестрацию и координацию взаимодействия между сервисами.
- **Провайдеры (Providers):** Сервисы, которые реализуют конкретные бизнес-функции (например, управление счетами, заказами).
- **Общая база данных:** В классической SOA сервисы часто используют общие хранилища данных, что является одним из ключевых отличий и недостатков по сравнению с микросервисами.

### Проблемы и недостатки SOA

- **Зависимость от ESB:** Центральная шина становится единой точкой отказа и "узким местом". Если ESB выходит из строя, все взаимодействие в системе парализуется.
- **Общая база данных:** Нарушает инкапсуляцию и слабую связанность. Изменение схемы данных для одного сервиса может "сломать" другие сервисы, которые зависят от тех же таблиц.
- **Сложность масштабирования:** Из-за тесной связи через ESB и общую БД, масштабировать отдельные сервисы изолированно практически невозможно. Чаще всего приходится масштабировать всю инфраструктуру целиком.
- **Низкая гибкость:** Замена технологии в одном сервисе (например, СУБД) — сложная задача, так как это может затронуть всю систему.

## Сравнение SOA и микросервисов

| Аспект | Сервис-ориентированная архитектура (SOA) | Микросервисная архитектура |
|:---|:---|:---|
| **Коммуникация** | Через центральную шину (ESB) — "умные трубы". | Напрямую через API или брокеры сообщений — "глупые трубы". |
| **База данных** | Часто общая для нескольких сервисов. | Отдельная, приватная для каждого сервиса. |
| **Гранулярность** | Крупные сервисы, широкие бизнес-функции. | Мелкие сервисы, узкие бизнес-функции. |
| **Масштабируемость** | Масштабирование всей системы целиком. | Независимое масштабирование отдельных сервисов. |
| **Связанность** | Более высокая из-за ESB и общей БД. | Низкая (слабая связанность). |
| **Отказоустойчивость**| Низкая (ESB — единая точка отказа). | Высокая (изоляция сбоев). |
| **Технологии** | Ограничена стандартами, навязанными ESB. | Полиглотная, свободный выбор стека для каждого сервиса. |

## Дополнительная информация

Хотя микросервисная архитектура во многом является эволюционным развитием идей SOA, она решает ключевые проблемы своего предшественника, делая акцент на полной автономии, децентрализации и независимом развертывании сервисов.
