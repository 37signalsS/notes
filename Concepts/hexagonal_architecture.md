# Гексагональная архитектура (Порты и Адаптеры)

## Определения

**Гексагональная архитектура (Hexagonal Architecture)**, также известная как **архитектура портов и адаптеров (Ports and Adapters)**, — это архитектурный паттерн, направленный на изоляцию доменной (бизнес) логики от внешних зависимостей. Паттерн обеспечивает независимость ядра приложения от технологий передачи данных (HTTP, gRPC, CLI) и способов их хранения (SQL, NoSQL, In-memory).

**Ключевая идея:** Бизнес-логика («Ядро») не знает о существовании внешнего мира. Она взаимодействует с ним через абстрактные интерфейсы («Порты»), реализация которых («Адаптеры») подключается извне.

В 2026 году гексагональная архитектура является стандартом для построения микросервисов и serverless-приложений, где ядро должно оставаться стабильным при частой смене инфраструктурных компонентов (например, переход от AWS Lambda к Wasm-воркерам).

## Базовые концепции

### Ключевые компоненты

- **Ядро (Core / Domain):**
  - Содержит чистую бизнес-логику, сущности (Entities), доменные службы и правила.
  - Это самая стабильная часть приложения, не зависящая от библиотек ввода-вывода или фреймворков.
  - Использует тактические паттерны **DDD (Domain-Driven Design)**: агрегаты, стоимостные объекты (Value Objects).
- **Порты (Ports):**
  - Это интерфейсы (в контексте ООП), определенные внутри Ядра.
  - **Входящие порты (Driving Ports):** Интерфейсы, через которые внешние системы управляют Ядром (например, `OrderService`).
  - **Исходящие порты (Driven Ports):** Интерфейсы, через которые Ядро запрашивает данные или отправляет уведомления (например, `OrderRepository`, `NotificationService`).
- **Адаптеры (Adapters):**
  - **Входящие адаптеры (Driving Adapters):** Преобразуют внешние запросы в вызовы Ядра. Примеры: REST-контроллер, GraphQL-резолвер, обработчик сообщений Kafka, CLI-команда.
  - **Исходящие адаптеры (Driven Adapters):** Реализуют исходящие порты, инкапсулируя работу с конкретной технологией. Примеры: PostgreSQL Repository, AWS S3 Client, SMTP-клиент.

### Правило зависимостей и маппинг

Все зависимости направлены **внутрь** (от адаптеров к Ядру). Это обеспечивается механизмом **Dependency Inversion (Инверсия зависимостей)**.

Важным аспектом является разделение моделей данных:
- **API DTO:** Модели для входящих адаптеров (JSON, Protobuf).
- **Domain Model:** Модели Ядра (бизнес-сущности).
- **Persistence Model / Entity:** Модели исходящих адаптеров (ORM-классы).

**Маппинг (преобразование)** моделей происходит исключительно внутри адаптеров. Ядро никогда не должно видеть ORM-аннотации или JSON-декораторы.

## Внедрение зависимостей и Composition Root

Для сборки всех компонентов используется **Composition Root** (Точка сборки) — обычно это главный файл приложения (`main.go`, `App.java`, `index.ts`).
1. Создаются экземпляры исходящих адаптеров (например, `SqlOrderRepository`).
2. Создается экземпляр Ядра (`OrderUseCase`), куда через конструктор передаются адаптеры в качестве портов.
3. Создаются входящие адаптеры (например, `HttpOrderHandler`), которым передается экземпляр Ядра.
4. Запускается сервер.

Это позволяет легко заменять реализации в тестах: вместо `SqlOrderRepository` подставляется `InMemoryOrderRepository` без изменения кода Ядра.

## Типовая структура проекта

Пример организации директорий для Golang/TypeScript проекта:
```text
/src
  /domain          # Ядро (бизнес-логика, сущности)
    /models        # Доменные модели
    /ports         # Интерфейсы (Repository, Service)
  /application     # Use cases (координация доменной логики)
  /infrastructure  # Исходящие адаптеры (DB, Redis, API)
    /db
    /aws
  /presentation    # Входящие адаптеры (HTTP, CLI, gRPC)
    /http
    /grpc
  main.ts          # Composition Root (точка сборки)
```

## Практические сценарии

### Пример: Добавление нового канала взаимодействия
**Ситуация:** Приложение работало только через REST API. Требуется добавить обработку команд через Telegram-бота.
**Действия:**
1. Создается новый **входящий адаптер** для Telegram.
2. Входящий адаптер преобразует сообщения бота в вызовы существующих **входящих портов** Ядра.
3. **Результат:** Бизнес-логика не меняется, тесты Ядра остаются прежними.

### Пример: Миграция базы данных
**Ситуация:** Система переезжает с PostgreSQL на ClickHouse для аналитических данных.
**Действия:**
1. Создается новый **исходящий адаптер**, реализующий интерфейс (порт) репозитория.
2. В точке сборки (Composition Root) меняется инициализация: вместо SQL-адаптера подключается ClickHouse-адаптер.
3. **Результат:** Код Ядра, отвечающий за расчеты, остается нетронутым.

## Дополнительная информация

### Преимущества и тренды 2026 года

- **Serverless и Wasm:** Гексагональная архитектура позволяет писать ядро приложения, которое одинаково успешно запускается в Docker-контейнере и как легковесный Wasm-модуль на границе сети (**Edge Computing**).
- **Тестируемость:** Возможность достижения 100% покрытия бизнес-логики чистыми Unit-тестами без использования Docker Compose или Testcontainers.
- **Масштабируемость команд:** Разные инженеры могут работать над адаптерами (фронтенд-интеграция, БД) и Ядром параллельно, опираясь на зафиксированные контракты портов.
