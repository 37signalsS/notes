# Атомарные операции

## Определения

**Атомарная операция (Atomic Operation)** — это операция, которая выполняется как единое неделимое целое. С точки зрения любого внешнего наблюдателя (другого потока, процесса или узла сети), операция либо еще не началась, либо уже полностью завершена. Промежуточные, частично измененные состояния системы в процессе выполнения атомарной операции недоступны.

**Атомарность (Atomicity)** — фундаментальное свойство надежных систем, гарантирующее, что никакое стороннее вмешательство или сбой (питание, падение процесса) не оставят систему в промежуточном (полуизменённом) состоянии. Это буква «A» в аббревиатуре [ACID](../Databases/Concepts/acid.md), лежащая в основе конкурентных и распределенных систем.

## Уровни реализации атомарности

### 1. Аппаратный уровень (CPU)
Обеспечивается архитектурой процессора и протоколами когерентности кэшей.
*   **Атомарность шины и LOCK:** Процессор может захватывать шину памяти (через сигнал `LOCK` в x86), предотвращая доступ других ядер к определенному адресу на время выполнения инструкции.
*   **Инструкции RMW (Read-Modify-Write):** Класс операций, выполняющих чтение, изменение и запись за один такт шины.
    *   **CAS (Compare-and-Swap):** Записывает новое значение только если текущее совпадает с ожидаемым. Основа большинства lock-free алгоритмов.
    *   **LL/SC (Load-Link / Store-Conditional):** Пара инструкций (ARM, RISC-V). `LL` помечает адрес, а `SC` выполняет запись только если адрес не изменялся. Эффективнее CAS, так как защищает от проблемы ABA на аппаратном уровне.
    *   **Fetch-and-Add / Test-and-Set:** Простейшие примитивы для счетчиков и спинлоков.
*   **Выравнивание памяти (Alignment):** Чтение/запись выровненного слова (например, 8 байт на 64-битной системе) атомарны по умолчанию. Невыровненный доступ может потребовать двух циклов шины и **не является атомарным**.

### 2. Уровень операционной системы (Ядро)
Системные вызовы, гарантирующие неделимость операций над ресурсами ОС.
*   **rename(2):** Атомарная замена пути к файлу в пределах одной точки монтирования.
*   **link(2):** Создание жесткой ссылки (часто используется для реализации файловых блокировок).
*   **open(2) с флагом O_EXCL:** Атомарная проверка существования и создание файла.
*   **O_TMPFILE:** (Linux 3.11+) Создание временного файла без имени, который невозможно подменить извне до момента его привязки к ФС.

### 3. Уровень файловой системы
*   **Copy-on-Write (CoW):** Механизм в ZFS, Btrfs, APFS. Данные пишутся в новые блоки, а указатель (Root Pointer) переключается атомарно только после успешной записи.
*   **Journaling (Журналирование):** Предварительная запись намерения в журнал (JBD2 в ext4) перед изменением основных структур метаданных. Позволяет восстановить консистентность после сбоя питания.

### 4. Уровень баз данных
Реализуется через транзакции и протоколы WAL (Write-Ahead Logging). Подробнее см. [ACID](../Databases/Concepts/acid.md).

### 5. Уровень распределённых систем
*   **Протоколы консенсуса:** Raft, Paxos обеспечивают атомарное изменение состояния кластера.
*   **Двухфазная фиксация (2PC):** Классический протокол для атомарности транзакций между несколькими узлами.

## Теоретические основы

### Барьеры памяти (Memory Fences)
Атомарности самой по себе недостаточно из-за **переупорядочивания (reordering)** инструкций процессором и компилятором для оптимизации.
*   **Acquire/Release семантика:** 
    *   *Release* гарантирует, что все записи, сделанные до него, станут видимы другим потокам, когда они выполнят *Acquire*.
    *   *Acquire* гарантирует, что все последующие чтения увидят значения, актуальные на момент *Release*.
*   **Memory Barrier:** Инструкция, принуждающая процессор завершить все предыдущие операции чтения/записи перед выполнением последующих.

### Линеаризуемость (Linearizability)
В распределенных системах атомарность операции часто связывают с линеаризуемостью. Это гарантия того, что операция кажется мгновенной для любого внешнего наблюдателя и происходит строго между моментом её вызова и моментом получения ответа. Линеаризуемость обеспечивает "свежесть" данных, гарантируя глобальный порядок реального времени.

## Практические сценарии

### Сценарий 1: Атомарное обновление конфигурации (метод rename)
Используется для предотвращения чтения «битых» или наполовину записанных файлов.
1.  Записать новые данные во временный файл в той же директории: `config.new`.
2.  Вызвать `fsync()` для `config.new` (гарантия записи на физический носитель).
3.  Выполнить `mv config.new config.conf` (вызов `rename(2)`).
*   *Реализация в Ansible:* Модули управления файлами используют этот паттерн по умолчанию. См. [ansible_file_management_modules.md](../Ansible/Modules/ansible_file_management_modules.md).

### Сценарий 2: Атомарные счетчики и Lock-free в программировании
Использование атомарных типов позволяет избежать тяжелых блокировок (мьютексов).
```go
// Атомарный инкремент в Go
import "sync/atomic"

var ops uint64
atomic.AddUint64(&ops, 1) // Выполняется одной процессорной инструкцией LOCK XADD
```
Это предотвращает **Race Conditions** на уровне CPU при одновременном обращении сотен потоков.

### Сценарий 3: Защита от TOCTOU (Безопасность)
**TOCTOU (Time-of-Check to Time-of-Use)** — уязвимость, возникающая при изменении ресурса между проверкой и использованием.
*   *Плохо:* `if (access(path, R_OK)) { fd = open(path, O_RDONLY); }` (Злоумышленник может заменить файл симлинком сразу после `access`).
*   *Хорошо:* Использование атомарных вызовов `openat` с флагами `O_NOFOLLOW` или работа через дескрипторы.

### Сценарий 4: Обновление ConfigMap в Kubernetes
Kubernetes обновляет данные в подах атомарно через механизм симлинков:
1.  Создается новая директория с данными (`..2026_08_02_12_00`).
2.  Симлинк `..data` переключается на новую директорию одной командой `ln -sfn`.
3.  Приложение всегда видит либо старую, либо новую версию файлов целиком.

### Сценарий 5: Блокировки в Shell-скриптах (flock)
Для предотвращения двойного запуска задач.
```bash
(
  flock -x -n 200 || { echo "Уже запущено"; exit 1; }
  # Критическая секция
  /usr/local/bin/my_sync_job.sh
) 200>/var/lock/my_job.lock
```

## Диагностика и типичные проблемы

### Инструменты проверки
*   **strace:** Позволяет увидеть, действительно ли операция выполняется атомарно (через `rename`, `link`) или через опасный `truncate` + `write`.
    ```bash
    strace -e trace=rename,link,openat my_script.sh
    ```

### Проблема ABA
В lock-free алгоритмах на базе CAS возможна ситуация:
1. Поток A читает значение `X`.
2. Поток B меняет `X` на `Y`, а затем обратно на `X`.
3. Поток A делает CAS, видит `X` и считает, что ничего не изменилось, хотя состояние было модифицировано.
*   *Решение:* Использование версионирования (тегированные указатели) или LL/SC.

## Ограничения атомарности

*   **Междисковые операции:** `mv` между разными разделами/дисками **не атомарен** (превращается в `cp` + `rm`). В системном вызове это вернет ошибку `EXDEV`.
*   **Сетевые ФС (NFS):** Атомарность `rename()` и `flock` зависит от версии протокола (в v4 надежнее) и настроек сервера. Часто возникают «фантомные» блокировки.
*   **Отсутствие fsync:** Даже атомарный `rename` не гарантирует сохранение данных при сбое питания, если они не были сброшены из кэша ОС на диск.

## Атомарность в современных языках (2026)

*   **Rust:** Система типов (`Send`, `Sync`) гарантирует безопасность при работе с атомарными примитивами, исключая ошибки упорядочивания памяти (Memory Ordering) на этапе компиляции.
*   **Go:** Предоставляет как низкоуровневый `sync/atomic`, так и высокоуровневые каналы, обеспечивающие атомарную передачу владения данными.
