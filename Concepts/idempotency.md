# Идемпотентность

## Определения

**Идемпотентность** — это свойство операции, при котором её многократное повторение приводит к тому же результату, что и однократное выполнение. В контексте ИТ это означает, что если клиент отправит один и тот же запрос несколько раз (например, из-за сетевого сбоя или повтора в очереди), состояние системы изменится только один раз.

Математически: `f(x) = f(f(x))`.

## Основные концепции

Идемпотентность критически важна для построения надежных распределенных систем, где гарантия доставки сообщений обычно соответствует уровню **At-least-once** (хотя бы один раз).

### Типы операций

1. **Естественно идемпотентные:**
   - Чтение данных (`GET` в HTTP).
   - Удаление по идентификатору (`DELETE` в HTTP).
   - Установка конкретного значения (`SET status = 'active'`).
2. **Неидемпотентные:**
   - Инкремент значения (`UPDATE counter = counter + 1`).
   - Добавление в список без проверки уникальности (`INSERT` без ключа).
   - Создание нового ресурса без проверки дубликатов (`POST` в HTTP).

## Практические сценарии

### 1. Идемпотентность в API (Idempotency Key)

Клиент генерирует уникальный идентификатор (UUID) для каждой операции и передает его в заголовке (например, `X-Idempotency-Key`).
- **Сервер:**
  1. Проверяет, есть ли такой ключ в базе/кэше.
  2. Если есть — возвращает сохраненный результат предыдущего выполнения.
  3. Если нет — выполняет операцию, сохраняет результат и ключ.

Этот механизм обязателен для платежных систем и критических бизнес-процессов.

### 2. Идемпотентность в БД (Upsert)

Использование конструкций `INSERT ... ON CONFLICT DO UPDATE` (PostgreSQL) или `INSERT ... ON DUPLICATE KEY UPDATE` (MySQL). Это позволяет гарантировать корректное состояние независимо от количества повторов вставки.

### 3. Идемпотентность в очередях сообщений (Kafka/RabbitMQ)

Обработчик сообщений (Consumer) должен проверять `message_id` или бизнес-ключ (например, номер заказа) перед выполнением логики.
- Если заказ уже помечен как «Оплачен», повторное сообщение об оплате просто игнорируется (событие считается обработанным).

Подробнее см. **[Гарантии доставки в Kafka](../Kafka/delivery_guarantees.md)**.

### 4. Роль в распределенных транзакциях

В паттернах **TCC (Try-Confirm-Cancel)** и **Сага (Saga)** методы `Confirm`, `Cancel` и компенсирующие транзакции **обязаны** быть идемпотентными, так как оркестратор может вызывать их повторно при таймаутах.
