# Идемпотентность

## Определения

**Идемпотентность (Idempotency)** — это свойство операции, при котором её многократное выполнение приводит к тому же результату, что и однократное, без изменения состояния системы после первого успешного вызова.

Математическая формула: $f(x) = f(f(x))$.

В инженерном контексте идемпотентность является фундаментом надежности распределенных систем, так как позволяет безопасно повторять запросы при сетевых сбоях, таймаутах или дублировании сообщений в очередях.

## Основные концепции

### Типы операций по уровню идемпотентности

1.  **Естественно идемпотентные:**
    *   **Чтение (Safe methods):** `GET`, `HEAD`, `OPTIONS` в протоколе HTTP. Они не меняют состояние сервера.
    *   **Удаление по ID:** `DELETE /orders/123`. Если ресурс удален, повторные вызовы вернут тот же результат (отсутствие ресурса).
    *   **Установка значения (Absolute assignment):** `SET status = 'cancelled'`. Повторная установка того же статуса не меняет состояние системы.
2.  **Неидемпотентные (Опасные):**
    *   **Инкремент:** `counter = counter + 1`. Каждый вызов изменяет состояние.
    *   **Добавление в список:** `POST /comments`. Без специальных механизмов создаст дубликат при повторе.
    *   **Относительные изменения:** `UPDATE account SET balance = balance - 100`.

### Ложная идемпотентность
Ситуация, когда инструмент сообщает об успешном «применении» изменений, но фактически состояние системы не соответствует коду, или когда повторный запуск вызывает ошибку из-за плохой реализации логики проверки («drift»).

## Практические сценарии реализации

### 1. Идемпотентность в API (Idempotency Key)
Стандарт для платежных шлюзов (Stripe, Adyen) и критических микросервисов.
*   **Механизм:** Клиент генерирует уникальный `X-Idempotency-Key` (обычно UUID) для конкретной бизнес-операции.
*   **Жизненный цикл на сервере:**
    1.  **Проверка:** Сервер ищет ключ в быстром хранилище (Redis/Memcached) с TTL (например, 24 часа).
    2.  **Выполнение:** Если ключа нет, выполняется логика, результат сохраняется в БД и кэшируется вместе с ключом.
    3.  **Возврат:** Если ключ найден, сервер возвращает сохраненный HTTP-код и тело ответа без повторного выполнения бизнес-логики.

### 2. Идемпотентность в БД (Upsert)
Предотвращение дубликатов на уровне хранения.
*   **SQL:** `INSERT INTO users (email) VALUES ('test@ex.com') ON CONFLICT (email) DO NOTHING;`
*   **Преимущество:** Гарантирует консистентность даже при конкурентных запросах (Race Conditions).

### 3. Инфраструктура как код (IaC)
Идемпотентность — ключевое требование к инструментам автоматизации.
*   **Terraform:** Сравнивает описание в коде с файлом состояния (`.tfstate`) и реальной инфраструктурой. Если ресурс уже создан и его параметры совпадают — Terraform ничего не делает.
*   **Ansible:** Модули (например, `ansible.builtin.package`) сначала проверяют текущее состояние («установлен ли пакет?»). Если да — модуль сообщает `ok`, если нет — `changed`.
*   **Антипаттерн:** Использование модуля `shell` или `command` в Ansible без параметров `creates` или `removes` нарушает идемпотентность, так как скрипт будет запускаться при каждом прогоне.

### 4. Очереди сообщений и события
Необходима для реализации семантики **At-least-once**.
*   **Consumer Side:** Обработчик должен сохранять ID обработанных сообщений.
*   **Outbox Pattern:** Гарантирует, что сообщение будет отправлено в очередь только после успешного коммита транзакции в БД, что упрощает достижение идемпотентности на стороне получателя.

## Проектирование и ограничения

### Дизайн идемпотентных систем
*   **Детерминизм:** При одинаковых входных данных и ключе идемпотентности результат должен быть идентичным.
*   **Обработка конкурентности:** Использование распределенных блокировок (Distributed Locks) при проверке ключа идемпотентности, чтобы два идентичных запроса, пришедших одновременно, не выполнились параллельно.
*   **Статус ответа:** При повторном вызове рекомендуется возвращать тот же HTTP-статус, что и в первый раз (например, `201 Created`), чтобы клиент понимал, что его исходное намерение выполнено.

### Ограничения
*   **Хранение ключей:** Требует дополнительных ресурсов (RAM/Disk) для хранения истории операций.
*   **Сложность отладки:** Ошибки в реализации кэширования результатов могут приводить к тому, что клиент будет получать устаревшие данные при повторных запросах.
