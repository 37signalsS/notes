# Паттерны отказоустойчивости и масштабируемости микросервисной архитектуры

## Определения

*   **Отказоустойчивость (Resilience)** — свойство системы продолжать работу при отказе части компонентов. Ключевой момент: система заранее рассчитана на то, что какие-то элементы выйдут из строя.
*   **Частичная деградация (Graceful Degradation)** — режим, при котором часть функциональности отключается, но основной сценарий остаётся живым. Это тот самый магазин без блока рекомендаций, где кнопка «купить» продолжает работать.
*   **Масштабируемость (Scalability)** — способность принять рост нагрузки за счёт добавления ресурсов. Нагрузка выросла в 10 раз, добавили 10 экземпляров, время ответа осталось прежним.
*   **Каскадный отказ (Cascading Failure)** — отказ одного сервиса, который сквозь границы сервисов проходит к другим из-за общего ресурса (пул потоков, соединений).
*   **Бюджет времени (Time Budget)** — у каждого звена цепочки вызовов есть жёсткое ограничение времени, строго меньшее, чем у вызывающего звена.
*   **Скользящее окно (Sliding Window)** — механизм учёта статистики за последние N вызовов или секунд, позволяющий оценить текущее состояние зависимости.
*   **Circuit Breaker (Предохранитель)** — паттерн, который размыкает цепь вызовов при превышении порога ошибок, защищая вызывающий сервис от исчерпания ресурсов.
*   **Bulkhead (Перегородка)** — изоляция ресурсов в пулы по зависимостям, чтобы сбой одного не исчерпал все соединения или потоки.
*   **Fallback (Запасное поведение)** — ответ на отказ зависимости: кэш, значение по умолчанию, пустой блок, очередь.
*   **Load Balancing (Распределение нагрузки)** — механизм распределения запросов между экземплярами сервиса.
*   **Auto Scaling (Автомасштабирование)** — изменение числа экземпляров под нагрузку.
*   **Data Replicas (Реплики данных)** — слой данных, масштабируемый отдельно от приложений.

## Базовые концепции

### Характер отказа в распределённых системах

В монолите отказ очевиден: процесс падает, недоступны сразу все функции. В распределённой системе отказ частый, не сразу и не одинаковый для всех функций. Например, оформление заказа сломалось, каталог жив, поиск работает, уведомления накапливаются в очереди.

Эта частичность даёт пространство для манёвра: систему можно удержать в рабочем состоянии, пожертвовав второстепенным функционалом. Но сложность в том, что состояний становится много, и каждый из них надо продумать заранее.

### Виды отказа сетевого вызова

Каждый сетевой вызов добавляет свои виды отказа:

1.  **Недоступность** — ответа нет вообще.
2.  **Высокая латентность** — ответ приходит слишком поздно, когда остальная логика его уже не ждёт.
3.  **Частичный ответ** — данные пришли не целиком или с устаревшим пакетом.

Важный момент: задержка и частичный ответ формально не считаются в распределённой системе ошибками (код ответа 200 и тело есть). Метрика ошибок чистая. Но для пользователя сценарий уже сломанный. Именно эти два отказа обнаруживаются позже и обходятся дороже всего.

### Арифметика доступности

Числа по цепочке перемножаются. Если взять пять звеньев, каждое доступное на 99%, получаем примерно 95% доступности сценария целиком. Каждый двадцатый запрос уходит в отказ.

### Каскадный отказ

Ломается одна зависимость (например, сервис оплаты, отвечающий 8 секунд вместо 200 миллисекунд). Из-за общего пула потоков заказ занял все ресурсы, и каталог с поиском с корзиной остались без потоков. Отказ прошёл сквозь границы сервисов.

### Медленный сервис опаснее упавшего

Медленный ответ порождает повторы, повторы увеличивают нагрузку, увеличенная нагрузка замедляет систему, а система разгоняет собственный отказ. Получается петля с положительной обратной связью, остановка которой требует внешнего вмешательства.

### Бюджет времени в цепочке вызовов

У каждого следующего звена бюджет времени строго меньше. Звено получило время от вызывающей стороны и обязано уложиться в него вместе с собственными накладными расходами. Значит, на свою зависимость оно может выделить только часть полученного бюджета.

Если нарушить это правило, шлюз оборвёт соединение первым, пользователь получит ошибку, а сервис заказов продолжит ждать оплату ещё секунду и удерживать поток ради ответа, который уже никто не передаст.

### Разделение зависимостей по критичности

Четыре зависимости сервиса равнозначны по риску и совершенно разные по смыслу. Без оплаты заказ оформить невозможно. Без рекомендаций пользователь спокойно доживёт до кнопки «купить». Разделение зависимостей по критичности становится основой всех решений по отказоустойчивости.

### Карта решений

Рабочий вопрос архитектора: что произойдёт, когда зависимость откажет? Если задать этот вопрос по каждой зависимости, большая часть материала превратится в конкретный список задач.

Паттерны делятся на две группы:
*   **Отказоустойчивость** — сдержать отказ, привести к частичной деградации вместо полного отказа.
*   **Масштабируемость** — принять нагрузку, изменить число экземпляров.

Обе дороги ведут к одному результату — достижению целевой доступности. В реальной системе нужны оба подхода.

## Паттерны отказоустойчивости

### Тайм-аут (Timeout)

Тайм-аут — ограничение времени, которое вызывающая сторона готова потратить на ожидание. Главная функция таймаута: превращает бесконечное ожидание в управляемую ошибку. Управляемая ошибка — это состояние, в котором сервис получает отказ, освобождает ресурс и переходит к следующему шагу сценария.

Тайм-аут защищает вызывающую сторону. Сервис оплаты от таймаута жарко не жарко, он продолжает работать в своём темпе. Мы лишь ограничиваем собственные потери: сколько своих ресурсов согласны потратить на чужую медлительность.

Значение таймаута выводится из целевого времени ответа сценария. Отправная точка — обещание пользователю. Из целевого времени вычитаются накладные расходы и распределяются между звеньями цепочки.

Не стоит копировать значения из успешных практик или ставить круглую секунду по привычке. Каждое число должно иметь конкретное объяснение и начинаться с фразы: «потому что целевое время сценария равно X».

### Бюджет повторов (Retry Budget)

Бюджет повторов — механизм, который считает отношение повторов к общему числу запросов. При превышении порога повторы прекращаются полностью. Пока сбои единичные, ретрай работает. Когда зависимость лежит целиком, повторы отключаются и перестают её добивать.

Бюджет измеряет ситуацию по всему потоку и поэтому останавливает лавину. Ограничение вроде трёх попыток на запрос остаётся справедливым при массовом отказе. Но каждый отдельный клиент будет соблюдать правила, а суммарная нагрузка расти кратно. Бюджет сюда и помешает.

### Заголовок Retry-After

Сервис возвращает заголовок Retry-After вместе с ответом и прямо сообщает, когда он будет готов принимать запросы. Это уже точечная информация от того, кто знает своё состояние.

### Ретрай (Retry)

Ретрай — повтор запроса после неудачной попытки. Этот паттерн выглядит безобидным и при этом чаще остальных превращается в причину отказов.

Повтор оправдан при сетевом сбое и тайм-ауте, потому что пакет мог просто потеряться, соединение могло на какое-то время оборваться, ответ мог прийти чуть позже. Общая черта этих ситуаций: сбой носит временный характер, и вторая попытка имеет высокий реальный шанс успеха.

При ошибке логики повтор смысла не лишён, потому что запрос с некорректными параметрами становится некорректным при второй, третьей и сотой попытке. Отсутствие прав доступа тоже сохранится.

Повторяем по типу ответа. Ошибки на стороне клиента разбирать повтором бесполезно. Нужно исправлять сам запрос. Сетевые сбои, тайм-ауты и временная недоступность зависимости — законный способ для повтора.

### Цена бесконтрольного повтора

Три клиента по три повтора делают девятикратную нагрузку на сервис. Три клиента по три попытки — девять запросов вместо трёх. Умножение работает каскадно без согласования между клиентами.

Повторы приходят синхронно: все клиенты получили ошибки примерно в один момент и через одинаковый интервал начинают сыпаться второй волной. Сервис получает плотные волны запросов, каждая из которых сбивает его попытку подняться.

### Экспоненциальная задержка с jitter

Экспоненциальная задержка — нарастающая пауза перед повтором, которая должна увеличиваться с каждой попыткой: 100 мс, 200 мс, 400 мс. Зависимость получает дискретное увеличение паузы, и давление на падающий сервис падает с каждым шагом.

Вторая половина рецепта — случайный разброс (jitter). К рассчитанной паузе добавляется некая случайно вычисленная величина. Клиенты выходят на повтор в разные моменты, и единого каскадного сбоя, который может свалить любую стену, не возникает.

Обе части работают вместе: экспоненциальная задержка без разброса сохраняет синхронность, а разброс без нарастания паузы удерживает нагрузку на прежнем уровне.

### Порочный цикл повторов

Зависимость отвечает ошибками устойчиво, повторять бессмысленно, каждая попытка заведомо обречена. Клиенты повторяют, нагрузка растёт кратно, отказ закрепляется. Зависший отказ возвращает нас к состоянию зависимости, которая отвечает с ошибками, и круг замыкается. Система в таком цикле самостоятельно выйти не сможет.

### Circuit Breaker (Предохранитель)

Circuit Breaker — предохранитель, который размыкает цепь вызовов при перегрузке, защищая вызывающий сервис от исчерпания ресурсов. Название взято из электротехники: автомат в защите, который размыкает цепь при перегрузке и защищает проводку от перегорания.

Механика работы:
*   Обёртка считает долю неуспешных ответов в скользящем окне.
*   Предохранитель оборачивает вызов зависимости и фиксирует исход каждого обращения.
*   При превышении порога ошибок цепь размыкается, и все последующие вызовы отклоняются мгновенно.

Состояния Circuit Breaker:
*   **Closed (Замкнута)** — нормальный режим, вызовы идут.
*   **Open (Разомкнута)** — вызовы отклоняются сразу. Поток вызывающего сервиса освобождается мгновенно.
*   **Half-Open (Полуоткрыта)** — через фиксированный интервал предохранитель пропускает несколько запросов для проверки состояния. Если они успешны — цепь замыкается. Если нет — обратно в Open.

### Параметры Circuit Breaker

Пять ключевых параметров:
1.  **Окно (Window)** — сколько последних вызовов или секунд учитывается при подсчёте.
2.  **Минимум вызовов (Minimum Calls)** — сколько обращений нужно накопить, прежде чем принимать решение.
3.  **Порог (Threshold)** — доля неуспешных ответов для размыкания.
4.  **Интервал (Wait Duration)** — время в разомкнутом состоянии.
5.  **Пробные вызовы (Permitted Calls)** — сколько запросов пропускается на проверку состояния при полуоткрытом состоянии.

### Правило: один предохранитель на каждую зависимость

Сервис заказов обращается к оплате, складу и рекомендациям. Эти зависимости работают по-разному, ломаются независимо и различаются по критичности. Если использовать один общий предохранитель на весь сервис, отказ рекомендации перекроет вообще доступ к оплате, что является критичным.

Границы предохранителя должны совпадать с границами того, что может ломаться по отдельности.

### Порог срабатывания

Порог 90% срабатывает уже после исчерпания ресурсов. 9 из 10 запросов должны провалиться, прежде чем цепь разомкнётся. К этому моменту потоки сервиса уже заняты ожиданием, и предохранитель включается фактически на руинах.

Рабочие значения порога — в районе 30–50%. Половина неуспешных ответов уже является поломкой, продолжать нагружать зависимость смысла нет. Точное число выбирается по критичности зависимости.

### Интервал восстановления

Короткий интервал ожидания превращает предохранитель в генератор нагрузки. Интервал в одну секунду означает, что каждую секунду подобные вызовы будут уходить к лежащему сервису, и передышки для восстановления фактически не будет.

Ориентир для интервала — время, за которое зависимость реально поднимается. Это время вычисляется в рамках нагрузочных испытаний и называется recovery time.

### Правила подсчёта

Тайм-аут засчитывается как неуспех. Медленный ответ вредит не меньше явной ошибки, потому что ресурс занимается, держит систему, увеличивает связанность. Предохранитель, реагирующий только на код ошибок, пропускает именно тот сценарий, ради которого мы его ставим.

### Наблюдаемость состояния цепи

Размыкание предохранителя — событие, о котором дежурная смена должна узнавать немедленно. С точки зрения пользователя часть функции уже фактически отключена. При этом привычные метрики ошибок могут выглядеть достаточно спокойно.

## Fallback (Запасное поведение)

Fallback — ответ на отказ зависимости. Варианты запасного ответа:

*   **Кэш** — отдать последние известные данные с пометкой о возможной неактуальности.
*   **Значение по умолчанию** — зараннее подготовленный ответ, например базовая ставка доставки, стандартная подборка товаров.
*   **Пустой блок** — тихая деградация функции.
*   **Очередь** — отложить обработку до восстановления зависимости.

### Критическая и некритичная зависимости

Развилка:
*   **Критическая зависимость** — честная ошибка сценария. Оплата отвечать перестала, провести платёж невозможно. Подделать этот результат уже нельзя ничем. Пользователю сообщается о том, что оплата временно недоступна, заказ сохранён, попробуйте позднее.
*   **Некритичная зависимость** — тихая деградация функции. Пользователь ничего не замечает. Сообщение об ошибке сервиса рекомендаций внимания не привлекает, а пользы не приносит.

Скрывать отказ критичной зависимости за оптимистичным сообщением опасно: человек может уйти с сайта в уверенности, что заказ был оплачен, а на самом деле это не так.

### Сквозной пример

В магазине рекомендации скрыты, оформление заказа продолжается. Блок с этим товаром покупать просто отсутствует на странице. Карточка товара, корзина и кнопка оплаты работают как обычно. Конверсия чуть снизится, но при этом сохраняется определённый уровень выручки.

### Требования к запасному поведению

Запасной путь согласуется с продуктом и тоже тестируется. Согласование с продуктом означает, что решение о скрытии блока принимает владелец продукта, а не разработчик.

Запасной путь проверяется на каждом релизе: тест с отключенной зависимостью, ручная проверка на тестовом контуре, эксперимент с отказом на боевом окружении.

## Bulkhead (Перегородка)

Bulkhead — изоляция ресурсов в пулы по зависимостям. Общий пул потоков сервиса разрезается на части, каждый закрепляется за конкретной зависимостью. Обращение к оплате берут потоки из своей части, обращение к рекомендации из своей, пересекаться эти потоки не могут.

Если вернуться к первому примеру занятия: восьмисекундная задержка в оплате заняла все 200 потоков сервиса заказов, потому что пул был общим. Каталог, поиск и корзина остались без ресурсов, хотя к оплате отношения не имели.

### Свойства изоляции

Отказ становится локальным по построению. Ограничения работают независимо от того, насколько плохо ведёт себя зависимость. Даже полностью зависшая зависимость дальше своего пула не пойдёт, потому что взять чужие слоты она физически не сможет.

### Два способа реализации

1.  **Лимит одновременных вызовов** — счётчик. К этой зависимости одновременно уходит не больше десяти запросов. Одиннадцатый ждёт освобождения слота или получает отказ. Реализация лёгкая, дополнительные потоки не создаются, накладные расходы практически равны нулю.
2.  **Отдельный пул потоков** — вызов выполняется в потоке из выделенного пула, изоляция получается физической. Плата — расход памяти на потоке и переключения контекста.

Для асинхронных вызовов достаточно счётчика одновременных ображений. Потоки при ожидании ответа не блокируются. Для блокирующих вызовов надёжнее использовать отдельный пул потоков, поскольку ожидание удерживает поток целиком.

### Размер пула

Размер пула выводится из пропускной способности и времени ответа. Нужное число одновременных вызовов равно ожидаемому числу запросов в секунду, умноженному на время ответа в секундах. Например, 20 запросов в секунду при ответе за 200 мс дают четыре одновременных вызова. Слоты берут с небольшим запасом.

Пулы получаются разными по размеру. Критическая зависимость с высоким потоком запросов получает больше слотов. Та, которая используется реже, получает меньше. Одинаковые пулы на все зависимости означают, что расчёт не выполнялся.

### Связь с Circuit Breaker

Изоляция держит удар, пока цепь предохранителя ещё замкнута. Между началом сбоя и размыканием цепи проходит время, и предохранителю нужно накопить статистику в скользящем окне. А в эти секунды защиту обеспечивает изоляция, ограничивая потери заданной величины.

Изоляция срабатывает мгновенно и постоянно, ограничивая аппетит каждой зависимости по построению. Предохранитель включается позже, по накопленной статистике, и прекращает обращения полностью.

## Паттерны масштабируемости

### Load Balancing (Распределение нагрузки)

Распределение нагрузки между экземплярами сервиса. При росте нагрузки добавляют экземпляры, и балансировщик распределяет запросы между ними.

### Auto Scaling (Автомасштабирование)

Автоматическое изменение числа экземпляров под нагрузку. При росте нагрузки добавляют экземпляры, при спаде — убирают. Механизм реагирует на метрики (CPU, память, длина очереди, количество запросов в секунду).

### Data Replicas (Реплики данных)

Слой данных масштабируется своими собственными средствами отдельно от приложений. Реплики позволяют распределять чтения между несколькими экземплярами базы данных, не нагружая основной узел записями.

## Практические сценарии

### Порядок работы паттернов при вызове

В реальном коде паттерны отказоустойчивости оборачивают один и тот же вызов по мере вложенности друг в друга, как определённые слои. Порядок слоёв — самостоятельное архитектурное решение. Один и тот же набор паттернов при разном порядке даёт разное поведение системы под нагрузкой.

1.  **Outer layer: Bulkhead** — проверка свободного слота в пуле. Если слотов нет, вызов отклоняется сразу. Это самая дешёвая проверка, без обращения к остальным слоям, без единого сетевого пакета.
2.  **Circuit Breaker** — проверка состояния цепи. Если цепь разомкнута, управление уходит в fallback немедленно, слот при этом освобождается сразу.
3.  **Retry with Backoff** — повтор запроса с нарастающей паузой и jitter.
4.  **Timeout** — ограничение времени одной попытки.
5.  **Fallback** — запасное поведение при исчерпании попыток.

### Бюджет времени в действии

Оплате выделено 800 мс суммарно. Три попытки по 800 мс дают уже 2,5 секунды с паузами. Значит, при трёх попытках тайм-аут одной попытки уменьшается, либо число попыток сокращается до одной-двух. Правило: сумма всех попыток вместе с паузами укладывается в бюджет, отведённый на всю зависимость.

### Наблюдаемость

Каждый слой даёт свою метрику:
*   **Bulkhead** — число отказов по отсутствию свободного слота.
*   **Circuit Breaker** — состояние цепи и время в разомкнутом состоянии.
*   **Retry** — доля повторных запросов.
*   **Timeout** — доля вызовов, оборванных по времени.
*   **Fallback** — количество срабатываний.

## Troubleshooting

### Типичные ошибки

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Тайм-аут на угад** | Значение таймаута не связано с целевым временем сценария | Вывести тайм-аут из целевого времени ответа, вычесть накладные расходы, согласовать бюджет между звеньями |
| **Ретрай без backoff** | Повторы идут синхронно, создавая волну нагрузки | Добавить экспоненциальную задержку и jitter |
| **Ретрай при ошибке логики** | Повторяем запрос с неверными параметрами или отсутствием прав | Повторять только при сетевых сбоях и тайм-аутах, а не при 4xx |
| **Circuit Breaker всегда Open** | Слишком агрессивный порог срабатывания | Установить порог в районе 30–50%, настроить интервал восстановления по реальному recovery time |
| **Один общий пул потоков** | Отказ одной зависимости исчерпывает все ресурсы | Разделить пул по зависимостям, рассчитать размер каждого по пропускной способности |
| **Fallback отсутствует** | Предохранитель даёт быстрый отказ, но пользователь видит сломанный сервис | Реализовать запасное поведение: кэш, значение по умолчанию, пустой блок |
| **Каскадный отказ** | Общий ресурс (пул потоков) используется всеми зависимостями | Изолировать ресурсы, настроить таймауты и Circuit Breaker на каждую зависимость |

## Best Practices

1.  **Согласованный бюджет времени** — каждое звено цепочки получает часть общего deadline, строго меньшее, чем у вызывающего звена.
2.  **Тайм-аут на каждой зависимости** — даже если сервис «надежный», сеть — нет.
3.  **Предохранитель на каждую зависимость** — границы предохранителя совпадают с границами того, что может ломаться по отдельности.
4.  **Изоляция ресурсов** — разделить пул потоков по зависимостям, рассчитать размер каждого пула.
5.  **Fallback согласован с продуктом** — решение о скрытии блока принимает владелец продукта.
6.  **Ретрай с exponential backoff + jitter** — без backoff повторы создают синхронную волну.
7.  **Бюджет повторов** — останавливает лавину повторных запросов при массовом отказе.
8.  **Наблюдаемость** — выводить состояние цепи, долю повторов, таймаутов и fallback в метрики и алерты.
9.  **Тестирование** — проверять паттерны на каждом релизе: отключать зависимость, смотреть на fallback, смотреть на поведение под нагрузкой.

## Дополнительная информация

### Связанные паттерны

*   **Load Shedding (Сброс нагрузки)** — паттерн, при котором сервис сознательно отказывает части входящих запросов при исчерпании собственной ёмкости. Отличается от Circuit Breaker: breaker защищает от сломанной зависимости, shedding — от перегрузки самого сервиса.
*   **Rate Limiting (Ограничение скорости)** — механизм контроля количества запросов, обрабатываемых сервисом за единицу времени. Защищает от «шторма» запросов и DDoS-атак.
*   **Chaos Engineering** — контролируемые эксперименты по разрушению компонентов для выявления слабых мест и проверки паттернов.
