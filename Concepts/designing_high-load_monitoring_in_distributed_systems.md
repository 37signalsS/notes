# Проектирование высоконагруженного мониторинга в распределенных системах

## Обзор систем мониторинга и наблюдаемости

*   **Мониторинг vs. Наблюдаемость ([Observability](../Concepts/observability_overview.md))**
    *   **Мониторинг:** Сбор метрик с системы. Фокус на "известных неизвестных".
    *   **Наблюдаемость:** Более широкое понятие, включающее метрики, логи, трассировки и профилирование. Позволяет глубже понимать внутреннее состояние системы (поиск "неизвестных неизвестных").
*   **Типы данных наблюдаемости:**
    *   **Метрики:** Численные данные о состоянии системы. Отвечают на вопрос "Что происходит?".
    *   **Логи:** Записи событий, происходящих в системе. Отвечают на вопрос "Почему это произошло?".
    *   **Трассировки (Traces):** Информация о прохождении запроса через различные компоненты распределенной системы. Отвечают на вопрос "Как запрос проходит через систему?". Инструменты: OpenTelemetry, Jaeger, Zipkin, Tempo.
    *   **Профилирование:** Детализация выполнения функций в коде. Отвечает на вопрос "Где система тратит время?". Инструменты непрерывного профилирования (например, Parca, Pyroscope).
*   **Представление системы:** Для SRE-инженеров система должна представляться как поток данных. В высоконагруженных системах "вторичные" данные (логи, метрики, трассировки, профилирование) могут быть значительно объёмнее "полезных" бизнес-данных.

## Организация высокопроизводительной доставки логов с помощью Kafka

*   **Kafka как распределенный журнал:**
    *   Представляет собой распределенную систему для публикации, подписки и надежного хранения записей.
    *   Обеспечивает высокую пропускную способность и отказоустойчивость.
    *   API-интерфейс включает **продюсеров** (генерируют данные) и **консьюмеров** (потребляют данные).
*   **Основные концепции Kafka:**
    *   **Запись (Record):** Элементарная единица данных (ключ-значение, timestamp, заголовки).
    *   **Топик (Topic):** Категория или имя потока данных. Топик может быть разбит на партиции и иметь несколько копий (репликация).
    *   **Партиция (Partition):** Упорядоченный, неизменяемый набор записей. Логический сегмент топика, повышающий параллелизм чтения/записи. Каждая партиция привязана к конкретному брокеру.
    *   **Офсет (Offset):** Уникальная, последовательная позиция записи в партиции.
    *   **Репликация:** Каждая партиция имеет несколько реплик на разных брокерах для обеспечения отказоустойчивости. Консьюмеры всегда читают из мастер-партиции.
    *   **Группы консьюмеров (Consumer Groups):** Консьюмеры в одной группе распределяют чтение из партиций топика. Каждый консьюмер в группе читает уникальный набор партиций.
*   **Масштабирование Kafka:**
    *   Пропускная способность топика определяется эмпирическим путем и зависит от ресурсов и конфигурации.
    *   Количество партиций существенно влияет на параллелизм и производительность. Увеличение числа консьюмеров сверх числа партиций не дает прироста производительности.
    *   **Важно:** Количество партиций топика нельзя изменить "на лету" без пересоздания топика. Планируйте количество партиций заранее.
*   **Параметры хранения (Retention Policies):**
    *   Журнал Kafka может быть усечен (удалены старые записи) по достижении определенного размера (байтов) или времени хранения.
    *   Поддерживается сжатие топиков (log compaction), при котором для каждого ключа сохраняется только последнее значение.
*   **Надежность записей (Acks) и чтений (Offsets):**
    *   `Acks` (acknowledgements): Настройка продюсера, определяющая, когда он получает подтверждение о записи сообщения (0 - без подтверждения, 1 - подтверждение от лидера партиции, `all` - подтверждение от всех реплик). Для высоких нагрузок без критической потери данных можно отключать `acks` (`acks=0`) для повышения производительности.
    *   `Offsets`: Консьюмеры отслеживают свое смещение в партиции, что позволяет им возобновлять чтение с последнего известного места после сбоя.
*   **[Kafka без ZooKeeper (Kraft)](../Kafka/kafka_for_monitoring.md#kraft-vs-zookeeper-современный-стандарт-для-kafka):**
    *   Современные кластеры Kafka могут работать без ZooKeeper, используя алгоритм **Kraft** (Kafka Raft Metadata Mode).
    *   **Преимущества Kraft:** Упрощение архитектуры (меньше компонентов), уменьшение числа точек отказа, снижение задержек, экономия ресурсов, повышение стабильности и более быстрый старт контроллеров.
    *   **Рекомендация для высоконагруженных систем:** Использовать Kafka на Kraft.
*   **Транспорт логов:**
    *   Для передачи логов в Kafka рекомендуется использовать легковесные агенты-коллекторы, такие как Fluent Bit, Fluentd, Vector.
    *   Logstash, будучи более ресурсоемким, обычно используется для обогащения и преобразования логов, а не для простой пересылки в Kafka.

## Высокопроизводительный мониторинг с [Prometheus](../Prometheus/overview.md)

*   **Prometheus как промышленный стандарт:**
    *   Написан на Go. Изначально разработан Soundcloud, поддерживается Cloud Native Computing Foundation (CNCF).
    *   Является Open Source проектом с лицензией Apache 2.0.
    *   **Мониторинг:** Поддерживает Whitebox (мониторинг изнутри системы, доступ к внутренним метрикам) и Blackbox (мониторинг снаружи, через внешние API, например, с помощью Blackbox Exporter).
    *   **Модель сбора метрик:** Ориентирован на **pull-модель** (Prometheus сам опрашивает цели по HTTP), но поддерживает и **push-модель** (через Pushgateway) для недолговечных заданий (например, cron-задачи). Pull-модель предпочтительнее, так как система-источник не зависит от доступности системы мониторинга.
    *   **Экосистема:** Развитая экосистема экспортеров для различных систем, а также возможность написания собственных.
    *   **Сервис-дискавери (Service Discovery):** Автоматическое обнаружение целей мониторинга (например, через DNS, Kubernetes API, EC2).
    *   **Сравнение с Zabbix:** Prometheus более гибок, микросервисен и ориентирован на облачные среды. Zabbix, как правило, использует реляционные БД и имеет ограничения по масштабированию под высокой нагрузкой из-за модели хранения и обработки данных.
*   **Архитектура [Prometheus](../Prometheus/prometheus_monitoring_architecture.md):**
    *   **Prometheus Server:** Основной компонент, состоящий из движка для опроса таргетов (Retrieval Engine), хранилища метрик (Time Series Database, TSDB) и веб-интерфейса.
    *   **Вспомогательные компоненты:**
        *   **Pushgateway:** Промежуточный шлюз для приема метрик по push-модели.
        *   **Alertmanager:** Для обработки, группировки, дедупликации и маршрутизации оповещений.
        *   **Экспортеры:** Специализированные программы, преобразующие метрики различных систем в формат Prometheus.
        *   **Инструменты Service Discovery.**
        *   **Remote Write/Read:** Интерфейсы для интеграции с внешними хранилищами метрик.
*   **[Федерация Prometheus (Federation)](../Prometheus/scaling/federation.md):**
    *   Механизм для сбора метрик с нескольких нижестоящих Prometheus-серверов в один вышестоящий агрегирующий Prometheus.
    *   Обеспечивает дедупликацию метрик и агрегированное представление.
    *   Простая настройка через конфигурационный файл, позволяет создать иерархическую структуру мониторинга из разных контуров.

## Масштабируемые хранилища метрик

*   **Проблемы встроенного хранилища Prometheus:**
    *   Ограниченный retention period (время хранения данных).
    *   Потенциальная потеря данных при внезапных сбоях (Write-Ahead Log - WAL).
    *   Не предназначен для долгосрочного хранения или очень больших объемов в условиях горизонтального масштабирования.
*   **Внешние хранилища для Prometheus (Remote Storage):**
    *   **Thanos:** Расширяет Prometheus для долгосрочного хранения, горизонтального масштабирования и глобального представления данных. Включает компоненты Sidecar, Ruler, Querier, Store Gateway, Compactor, Receiver.
    *   **[VictoriaMetrics](../VictoriaMetrics/overview.md):** Высокопроизводительная, масштабируемая Time Series Database, написанная на Go. Может выступать как самостоятельный сборщик метрик (поддерживает Prometheus-совместимый API) или как удаленное хранилище для Prometheus (remote write/read). Поддерживает мульти-тенанси (разделение данных для разных пользователей/команд).
    *   **[Mimir](../Mimir/mimir_overview.md):** Разработан Grafana Labs, является эволюцией идей Thanos и VictoriaMetrics.
        *   **Преимущества Mimir:** Обладает лучшими чертами Thanos и VictoriaMetrics. Предлагает горизонтальное масштабирование, долгосрочное хранение, мульти-тенанси (разделение по командам/клиентам) из коробки.
        *   **Архитектура Mimir:** Распределенная, микросервисная архитектура. Использует S3-совместимое объектное хранилище (например, MinIO, Ceph, облачные провайдеры) для долговременного хранения. Включает компоненты Distributor, Ingester, Compactor, Store Gateway, Querier, Query Frontend. Активно использует кэширование (например, Memcached).
        *   **Рекомендация для высоконагруженных систем:** Mimir предпочтительнее для построения глобальной, масштабируемой, отказоустойчивой и мульти-тенанси системы хранения метрик.
*   **S3-совместимые хранилища:**
    *   Для долговременного хранения метрик Mimir/Thanos используют объектные хранилища.
    *   Примеры: Ceph, MinIO (для on-premise), AWS S3, Google Cloud Storage, Azure Blob Storage.
    *   Для продакшен-среды рекомендуется использовать надежные и масштабируемые решения, такие как Ceph.

## Высокодоступная визуализация и оповещения

*   **[Grafana](../Grafana/grafana_overview.md):**
    *   Мощный инструмент для визуализации данных из различных источников (Prometheus, Mimir, Loki, OpenSearch и т.д.).
    *   **[Высокая доступность](../Grafana/high_availability.md):** Может быть развернута в кластере за балансировщиком нагрузки.
    *   **Хранение конфигурации:** Дашборды и настройки Grafana рекомендуется хранить в реляционной базе данных (например, PostgreSQL) вместо встроенного SQLite. Это позволяет кластеризовать Grafana и обеспечить ее отказоустойчивость.
*   **Alertmanager:**
    *   Основной компонент для обработки оповещений, полученных от Prometheus.
    *   **Функции:** Группировка схожих алертов, дедупликация, подавление (silencing) повторяющихся или неактуальных алертов, маршрутизация оповещений в различные приемники (email, Slack, PagerDuty, кастомные вебхуки).
    *   **Высокая доступность:** Alertmanager может быть развернут в кластере для обеспечения отказоустойчивости и репликации состояния между экземплярами с помощью gossip-протокола.
*   **Alerta:**
    *   Альтернативная или дополнительная панель управления алертами, предоставляющая централизованный и ориентированный на оператора вид алертов. Может использоваться для отображения бизнес-алертов для менеджеров.

## Построение комплексной высоконагруженной системы мониторинга

*   **Основные принципы:**
    *   **Распределенность:** Все компоненты системы мониторинга должны быть распределенными, масштабируемыми и отказоустойчивыми.
    *   **Асинхронность:** Для сбора и обработки больших потоков логов используйте асинхронные механизмы (Kafka).
    *   **Независимость мониторинга:** Системы, генерирующие данные, не должны зависеть от доступности самой системы мониторинга (особенно при pull-модели для метрик).
    *   **Дедубликация и агрегация:** На всех уровнях для снижения шума, повышения эффективности и экономии ресурсов.
*   **Типовая архитектура:**
    1.  **Источники данных:** Приложения, инфраструктура (хосты, сеть, базы данных), облачные сервисы.
    2.  **Сборщики логов:** Легковесные агенты (Fluent Bit, Vector) для сбора логов и отправки их в Kafka.
    3.  **Транспорт логов:** Кластер Kafka (на Kraft) для надежной и высокопроизводительной транспортировки логов.
    4.  **Хранение логов:** Loki (для агрегированного хранения логов и запросов через Grafana), OpenSearch/Elasticsearch (для полнотекстового поиска и аналитики, если требуется).
    5.  **Сборщики метрик:** Высокодоступные пары Prometheus-серверов (HA-пары) в каждом контуре/кластере. Они опрашивают экспортеры и локально хранят метрики короткое время (например, 30 минут - 2 часа).
    6.  **Внешнее хранилище метрик:** Кластер Mimir для долгосрочного хранения, горизонтального масштабирования, мульти-тенанси. Локальные Prometheus пишут в Mimir через remote write.
    7.  **Alerting:** Кластер Alertmanager для обработки, группировки и маршрутизации оповещений из Prometheus.
    8.  **Визуализация:** Кластер Grafana (с PostgreSQL в качестве бэкенда для дашбордов) для создания дашбордов и просмотра метрик/логов/трассировок.
    9.  **Экспортеры:** Специализированные экспортеры (Node Exporter, cAdvisor, Kafka Exporter, database exporters, Blackbox Exporter и т.д.) для предоставления метрик Prometheus. Должны быть высокодоступными и мониториться.
*   **Особенности эксплуатации:**
    *   **Короткий Retention Period локальных Prometheus:** Локальные Prometheus хранят данные очень короткое время, пересылая все в долгосрочное хранилище (Mimir). Это снижает их ресурсные требования и повышает отказоустойчивость (при падении Prometheus теряются только последние минуты метрик, которые уже продублированы в Mimir).
    *   **Гибкие правила оповещения:** Возможность настройки правил оповещения в Alertmanager для фильтрации критических событий, отключения неважных алертов в нерабочее время (например, на выходных).
    *   **Централизованная визуализация:** Единый кластер Grafana, подключенный к Mimir и Loki, позволяет видеть полную картину мониторинга.
