# Инфраструктура как код (IaC): обзор

## Определения

**Инфраструктура как код (Infrastructure as Code, IaC)** — это инженерный подход к управлению и подготовке вычислительной инфраструктуры (серверы, сети, хранилища, базы данных, балансировщики) через машинно-читаемые файлы определений, а не через ручную настройку или интерактивные инструменты.

IaC позволяет применять к инфраструктуре те же практики, что и к разработке программного обеспечения: **версионирование** (Git), **автоматическое тестирование**, **непрерывную интеграцию и доставку** (CI/CD) и **Code Review**. Любые изменения вносятся сначала в код, а затем автоматически применяются к среде.

## Базовые концепции

### Ключевые принципы

1.  **Декларативность:** Описание *желаемого состояния* системы («что должно быть»), а не последовательности шагов. Инструмент самостоятельно вычисляет разницу (delta) и применяет изменения.
2.  **Идемпотентность:** Гарантия того, что повторный запуск одного и того же кода приведет к идентичному результату, независимо от начального состояния.
3.  **Воспроизводимость:** Возможность мгновенно создать идентичные окружения (dev, staging, prod), исключая эффект «снежинок» (уникальных серверов с ручными правками).
4.  **Самодокументированность:** Код является актуальной и точной документацией текущего состояния инфраструктуры.
5.  **Централизованное управление:** Код в репозитории является единственным источником правды. Ручные изменения (Manual Drift) должны устраняться через обновление кода.

### Декларативный против Императивного подхода

Это фундаментальное различие в способе описания инфраструктуры:

| Аспект | Декларативный (IaC-стандарт) | Императивный (Скриптовый подход) |
| :--- | :--- | :--- |
| **Что описываем?** | Конечное состояние (Цель) | Последовательность действий (Шаги) |
| **Пример** | `resource "server" { count = 3 }` | `for i in 1..3; do create_server; done` |
| **Управление ошибками** | Встроено в инструмент (библиотеки провайдеров) | Требует ручной обработки исключений в скрипте |
| **Масштабируемость** | Высокая (изменение одного параметра) | Сложная (необходимость переписывания логики циклов) |
| **Проверка (Plan)** | Позволяет увидеть изменения до их применения | Практически невозможна без запуска кода |

### Уровни абстракции и инструменты

Выбор инструмента IaC зависит от уровня инфраструктуры, которым необходимо управлять (согласно моделям NIST):

1.  **IaaS (Infrastructure as a Service):** Управление «фундаментом» (ВМ, сети, хранилища).
    *   **Terraform / OpenTofu:** Стандарт де-факто. OpenTofu — открытый форк Terraform.
    *   **Pulumi:** Использование языков общего назначения (Python, Go, TS) для управления облаками.
    *   **Cloud-specific:** CloudFormation (AWS), ARM/Bicep (Azure).
2.  **PaaS (Platform as a Service):** Управление платформами и контейнеризацией.
    *   **Kubernetes (манифесты/Kustomize):** Декларативное описание ресурсов внутри кластера.
    *   **Helm:** Менеджер пакетов для Kubernetes.
    *   **Crossplane:** Управление внешними облачными ресурсами через Kubernetes API (Cloud Control Plane).
3.  **SaaS (Software as a Service):** Управление настройками готовых сервисов.
    *   Провайдеры Terraform/OpenTofu для управления пользователями GitHub, ролями Datadog, настройками Cloudflare и т.д.

### Синергия инструментов: Terraform vs Ansible

Несмотря на наличие пересекающихся функций, эти инструменты чаще всего используются в связке для обеспечения полного жизненного цикла.

| Характеристика | Terraform / OpenTofu | Ansible |
| :--- | :--- | :--- |
| **Тип задачи** | **Provisioning** (Создание ресурсов) | **Configuration Management** (Настройка ОС) |
| **Управление состоянием** | **Stateful**: хранит `terraform.tfstate` | **Stateless**: собирает факты при запуске |
| **Жизненный цикл** | Полный: Create → Update → Destroy | Частичный: только изменение состояния ПО |
| **Сильная сторона** | Глубокая интеграция с API облаков | Настройка софта внутри ОС, оркестрация задач |

**Типовой паттерн (Синергия):** Terraform создает инфраструктуру (ВМ, VPC, DB), после чего Ansible подключается к ним для установки пакетов, настройки пользователей и финального деплоя приложения.

## Практические сценарии

### Жизненный цикл изменений (IaC Workflow)

1.  **Написание кода:** Инженер вносит изменения в конфигурацию.
2.  **Статический анализ (Linting):** Автоматическая проверка синтаксиса и безопасности (например, `tflint`, `checkov`).
3.  **План (Dry Run):** Инструмент сравнивает текущее состояние с кодом и показывает список изменений (`terraform plan`).
4.  **Применение (Apply):** Автоматическое внесение изменений после одобрения Code Review.
5.  **Контроль дрейфа (Drift Detection):** Регулярная проверка соответствия реальных ресурсов коду. Если кто-то изменил настройки вручную, пайплайн должен это обнаружить и исправить.

### Неизменяемая инфраструктура (Immutable Infrastructure)

IaC позволяет реализовать подход, при котором серверы никогда не модифицируются после создания:
*   Вместо обновления софта на работающем сервере (Mutable), IaC запускает процесс сборки нового образа (через **Packer**).
*   Создаются новые инстансы из этого образа, а старые удаляются.
*   Это гарантирует полную предсказуемость среды и легкий откат (Rollback).

### Безопасность инфраструктуры (IaC Security)

Интеграция проверок на этапе написания кода (**Shift Left**):
*   **Secret Management:** Запрещено хранить секреты в коде. Используется интеграция с **HashiCorp Vault** или AWS Secrets Manager.
*   **Policy as Code (PaC):** Автоматическая проверка соблюдения стандартов с помощью **Open Policy Agent (OPA)** или Kyverno (например, запрет на создание S3-бакетов без шифрования).
