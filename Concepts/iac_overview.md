# Инфраструктура как код (IaC): обзор

## Определения

**Инфраструктура как код (Infrastructure as Code, IaC)** — это методология управления и подготовки вычислительной инфраструктуры через машинно-читаемые файлы определений. Вместо ручной настройки серверов или использования интерактивных консолей облачных провайдеров, инженеры описывают желаемое состояние системы в коде.

IaC переносит лучшие практики разработки ПО в мир системного администрирования:
*   **Версионирование (Git):** Полная история изменений инфраструктуры, возможность отката (Rollback).
*   **Code Review:** Проверка инфраструктурных изменений коллегами до их внедрения.
*   **Автоматизированное тестирование:** Проверка синтаксиса, безопасности и логики конфигурации в пайплайнах.
*   **CI/CD для инфраструктуры:** Автоматическое применение изменений после прохождения тестов.

## Базовые концепции

### Ключевые принципы

1.  **Декларативность:** Описание *желаемого состояния* («что должно быть»), а не последовательности команд. Инструмент IaC сам вычисляет разницу (delta) между текущим и целевым состоянием и применяет минимально необходимые изменения.
2.  **Идемпотентность:** Гарантия того, что многократный запуск одного и того же кода приводит к идентичному результату. Если система уже находится в целевом состоянии, повторный запуск ничего не изменит.
3.  **Воспроизводимость:** Возможность быстро и точно воссоздать идентичные окружения (Production, Staging, Dev) на любой площадке.
4.  **Самодокументированность:** Код является актуальной спецификацией инфраструктуры, устраняя разрыв между документацией в Wiki и реальным состоянием серверов.
5.  **Единственный источник истины (SSoT):** Все изменения вносятся только через репозиторий. Ручные правки («Manual Drift») считаются ошибкой и должны устраняться автоматикой.

### Декларативный против Императивного подхода

| Характеристика | Декларативный (IaC-стандарт) | Императивный (Скриптовый) |
| :--- | :--- | :--- |
| **Фокус** | Конечное состояние (Цель) | Процесс (Шаги) |
| **Пример** | Terraform: `resource "instance" { count = 5 }` | Bash: `aws ec2 run-instances --count 5 ...` |
| **Управление состоянием** | Инструмент отслеживает созданные ресурсы | Инженер должен сам проверять наличие ресурсов |
| **Масштабируемость** | Изменение `count` на 10 добавит 5 новых | Скрипт может упасть или создать лишние 10 |
| **Надежность** | Встроенная обработка зависимостей и ошибок | Требует сложной логики `if/else` в коде |

### Эволюция и технологический стек (2026)

В 2026 году IaC прошел путь от простых скриптов до полноценных управляющих платформ (**Control Planes**).

1.  **Инструменты провижининга (Provisioning):**
    *   **Terraform:** Индустриальный стандарт на языке HCL. После смены лицензии на BUSL сохраняет лидерство в Enterprise.
    *   **OpenTofu:** Полностью открытый форк Terraform (лицензия MPL), поддерживаемый сообществом и CNCF. Совместим с большинством провайдеров.
    *   **Pulumi:** Позволяет писать IaC на языках общего назначения (TypeScript, Python, Go). Удобен для разработчиков, так как позволяет использовать циклы, условия и библиотеки тестирования из экосистемы языка.
2.  **Configuration Management (CM):**
    *   **Ansible:** Лидер в настройке ОС и приложений. Stateless-подход и отсутствие агентов делают его стандартом для пост-провижининга.
    *   **SaltStack:** Выбор для высокомасштабируемых сред благодаря событийной модели управления.
3.  **Cloud Control Planes:**
    *   **Crossplane:** Расширяет Kubernetes API для управления внешними облачными ресурсами (RDS, S3, VPC). Позволяет реализовать полноценный **GitOps для инфраструктуры**.
4.  **Cloud-Specific:**
    *   AWS CloudFormation / CDK, Azure Bicep, Google Cloud Deployment Manager. Используются в моновендорных проектах для максимальной поддержки новых фич провайдера
    
### Синергия инструментов: Terraform vs Ansible

Несмотря на наличие пересекающихся функций, эти инструменты чаще всего используются в связке для обеспечения полного жизненного цикла.

| Характеристика | Terraform / OpenTofu | Ansible |
| :--- | :--- | :--- |
| **Тип задачи** | **Provisioning** (Создание ресурсов) | **Configuration Management** (Настройка ОС) |
| **Управление состоянием** | **Stateful**: хранит `terraform.tfstate` | **Stateless**: собирает факты при запуске |
| **Жизненный цикл** | Полный: Create → Update → Destroy | Частичный: только изменение состояния ПО |
| **Сильная сторона** | Глубокая интеграция с API облаков | Настройка софта внутри ОС, оркестрация задач |

**Типовой паттерн (Синергия):** Terraform создает инфраструктуру (ВМ, VPC, DB), после чего Ansible подключается к ним для установки пакетов, настройки пользователей и финального деплоя приложения.

## Практические сценарии

### Жизненный цикл изменений (IaC Workflow)

Современный пайплайн IaC включает следующие этапы:
1.  **Локальная разработка:** Написание манифестов, форматирование (`terraform fmt`), валидация (`terraform validate`).
2.  **Статический анализ (Linting/Security):**
    *   `tflint`: поиск логических ошибок и неоптимальных конструкций.
    *   `checkov` / `tfsec`: сканирование на уязвимости (например, открытый 22 порт на весь мир).
    *   `infracost`: оценка стоимости ресурсов до их создания.
3.  **Plan (Dry Run):** Генерация плана изменений. Инструмент показывает, что будет создано, изменено или удалено.
4.  **Approval (Code Review):** Ревью кода и плана изменений.
5.  **Apply (Deployment):** Применение изменений через CI-раннеры с использованием временных учетных данных (например, OIDC).
6.  **Drift Detection:** Периодический запуск `plan` в фоне. Если реальное состояние облака отличается от кода, генерируется алерт или запускается авто-исправление.

### Управление состоянием (State Management)

Состояние (`tfstate`) — самый критичный компонент IaC.
*   **Remote Backends:** Хранение состояния в защищенных хранилищах (S3, GCS, Terraform Cloud) с обязательным шифрованием.
*   **State Locking:** Блокировка состояния при выполнении изменений (через DynamoDB или аналоги), чтобы предотвратить коллизии при одновременной работе нескольких инженеров.
*   **State Separation:** Разделение состояния на слои (Layers) по окружениям или компонентам системы. Изменение в тестовой сети не должно иметь доступа к состоянию продакшена.

### Тестирование инфраструктурного кода

1.  **Unit-тесты:** Проверка логики формирования манифестов (например, встроенные тесты в Terraform 1.6+).
2.  **Интеграционные тесты:**
    *   **Terratest (Go):** Создание реальной инфраструктуры, проверка её работоспособности (например, доступность HTTP-порта) и последующее удаление.
    *   **Molecule (для Ansible):** Запуск роли в Docker/ВМ и проверка итогового состояния системы.
3.  **Compliance-тесты:** Проверка на соответствие стандартам компании (например, наличие тега `Project` у всех ресурсов).

### Неизменяемая инфраструктура (Immutable Infrastructure)

IaC позволяет реализовать паттерн, при котором серверы не обновляются «по живому»:
*   **Packer:** Сборка золотого образа (Golden Image) с предустановленным софтом.
*   **IaC:** Развертывание новых серверов из этого образа.
*   **Обновление:** Создание новой группы серверов и постепенное переключение трафика (Blue-Green или Canary), после чего старые серверы уничтожаются.

## Рекомендации и лучшие практики

*   **Модульность:** Выносите типовые конструкции (настройка VPC, создание RDS) в переиспользуемые модули.
*   **Тегирование:** Внедряйте строгую политику тегов (`Environment`, `Owner`, `CostCenter`) через IaC. Это критично для FinOps и мониторинга.
*   **Least Privilege:** CI/CD пайплайны должны иметь минимально необходимые права для создания конкретных ресурсов.
*   **Избегайте секретов в коде:** Используйте интеграции с HashiCorp Vault, AWS Secrets Manager или SOPS для шифрования секретов в Git.
*   **Version Pinning:** Всегда фиксируйте версии провайдеров и модулей, чтобы избежать неожиданных изменений при обновлении инструментов.
