# Инфраструктура как код (IaC): обзор

## Определения

**Инфраструктура как код (Infrastructure as Code, IaC)** — подход к управлению и подготовке вычислительной инфраструктуры (серверы, сети, балансировщики, базы данных), при котором конфигурация описывается в виде машинно-читаемых файлов определений, а не настраивается вручную или с помощью интерактивных инструментов.

Код инфраструктуры хранится в системе контроля версий (Git) наравне с кодом приложения, что обеспечивает автоматизацию, аудит и воспроизводимость среды на всех этапах жизненного цикла ПО.

## Базовые концепции

### Ключевые принципы

1.  **Декларативность:** описание *желаемого состояния* системы («что должно быть»), а не последовательности шагов для его достижения. Инструмент IaC самостоятельно вычисляет разницу (delta) и применяет необходимые изменения.
2.  **Идемпотентность:** свойство, при котором повторное применение одного и того же кода приводит к идентичному результату, независимо от начального состояния системы. Это делает операции предсказуемыми и безопасными.
3.  **Версионируемость:** использование Git позволяет отслеживать историю изменений, проводить Code Review и быстро откатываться к предыдущим стабильным состояниям инфраструктуры.
4.  **Единый источник истины (Single Source of Truth, SSoT):** код в репозитории является единственным достоверным описанием текущей инфраструктуры. Любые ручные изменения (Manual Drift) запрещены и должны устраняться через обновление кода.

### Декларативный vs Императивный подходы

| Аспект | Декларативный (IaC-стандарт) | Императивный (Скриптовый подход) |
| :--- | :--- | :--- |
| **Что описываем?** | Конечное состояние (Цель) | Последовательность действий (Шаги) |
| **Пример** | `resource "server" { count = 3 }` | `for i in 1..3; do create_server; done` |
| **Управление ошибками** | Встроено в инструмент | Требует ручной обработки исключений |
| **Масштабируемость** | Высокая (изменение одного параметра) | Сложная (переписывание логики циклов) |

### Уровни абстракции и инструменты

Выбор инструмента IaC зависит от уровня инфраструктуры, которым необходимо управлять (согласно моделям NIST):

1.  **IaaS (Infrastructure as a Service):** управление «фундаментом» (ВМ, сети, хранилища).
    *   *Инструменты:* **Terraform**, OpenStack, CloudFormation (AWS).
2.  **PaaS (Platform as a Service):** управление платформами и контейнеризацией.
    *   *Инструменты:* **Kubernetes** (манифесты), **Helm**, **Ansible** (для установки рантаймов).
3.  **SaaS (Software as a Service):** управление настройками готовых сервисов.
    *   *Инструменты:* Провайдеры Terraform для управления пользователями GitHub, ролями Datadog и т.д.

### Сравнение инструментов: Terraform vs Ansible

Несмотря на наличие пересекающихся функций, эти инструменты решают принципиально разные задачи и чаще всего используются в связке.

| Характеристика | Terraform | Ansible |
| :--- | :--- | :--- |
| **Тип задачи** | **Provisioning** (Создание ресурсов) | **Configuration Management** (Настройка ОС) |
| **Управление состоянием** | **Stateful**: хранит `terraform.tfstate` | **Stateless**: собирает факты при запуске |
| **Жизненный цикл** | Полный: Create → Update → Destroy | Частичный: только изменение состояния ПО |
| **Сильная сторона** | Создание облачной инфраструктуры | Настройка софта внутри ОС, оркестрация задач |

**Типовой паттерн (Синергия):** Terraform создает виртуальные машины и сеть, после чего Ansible подключается к ним для установки пакетов, настройки пользователей и деплоя приложения.

## Практические сценарии

### Жизненный цикл изменений IaC

1.  **Код:** написание конфигурации (например, HCL-код в Terraform).
2.  **План (Dry Run):** инструмент сравнивает текущее состояние с кодом и показывает список изменений (`terraform plan`).
3.  **Применение (Apply):** автоматическое внесение изменений в инфраструктуру.
4.  **Контроль дрейфа (Drift Detection):** регулярная проверка соответствия реальных ресурсов коду. Если кто-то изменил настройки вручную, IaC-пайплайн должен это обнаружить и исправить.

### Безопасность инфраструктуры (IaC Security)

Интеграция проверок безопасности на этапе написания кода (**Shift Left**):
*   **Сканирование IaC:** использование инструментов (например, **Checkov**, **tfsec**) для поиска открытых портов, отсутствия шифрования или небезопасных конфигураций до деплоя.
*   **Policy as Code (PaC):** автоматическая проверка соблюдения корпоративных стандартов с помощью **Open Policy Agent (OPA)** или Kyverno.

### Эволюция IaC: GitOps

**GitOps** — это современная операционная модель для IaC, где Git является единственным источником правды для управления инфраструктурой и приложениями. 
*   **Pull-модель:** специальный агент (например, ArgoCD или Flux) внутри кластера постоянно опрашивает Git-репозиторий и применяет изменения, если они появились.
*   **Автоматическое устранение дрейфа:** если состояние системы изменилось вручную, GitOps-контроллер немедленно вернет его к описанному в Git.
