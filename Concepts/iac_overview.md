# Основная идея инфраструктуры как кода

Инфраструктура как код (Infrastructure as Code, IaC) — это подход, при котором вычислительные ресурсы, сети, балансировщики, политики безопасности и конфигурации описываются машинно‑читаемыми файлами, а не создаются вручную в консоли. Эти описания становятся частью базового кода проекта и управляются через систему контроля версий, обеспечивая предсказуемость и воспроизводимость.

## Зачем описывать инфраструктуру кодом

-   **Повторяемость**: Любое окружение (dev/stage/prod) собирается из одинаковых шаблонов без «ручных» отклонений.
-   **Прозрачность**: Изменения видны в диффах, проходят код‑ревью и аудит.
-   **Скорость**: Развёртывание автоматизируется, уменьшаются ошибки и время отклика.
-   **Надёжность**: Идемпотентное применение конфигураций предотвращает дрейф и непреднамеренные модификации.
-   **Согласованность с практиками разработки**: Инфраструктура проходит те же циклы CI/CD, тесты и проверки качества.

## Ключевые принципы IaC

-   **Источник истины — репозиторий**: Инфраструктура изменяется через коммиты и pull/merge‑запросы.
-   **Декларативность**: Описывается желаемое состояние, а система определяет порядок операций.
-   **Идемпотентность**: Повторное применение приводит к тому же результату, если состояние уже достигнуто.
-   **Детерминизм**: Один и тот же код при одинаковых входных данных даёт одинаковый результат.
-   **Обнаружение дрейфа**: План изменений выявляет расхождения между кодом и фактическим состоянием.
-   **Параметризация и модульность**: Переиспользование шаблонов, чёткое разделение общих и средовых настроек.

## Декларативный и императивный подходы

| Аспект          | Декларативный             | Императивный                    |
| --------------- | ------------------------- | ------------------------------- |
| **Формулировка**| Что должно быть           | Как это сделать                 |
| **Порядок действий** | Определяет движок         | Определяет автор скрипта        |
| **Идемпотентность** | Встроенная цель           | Требует ручной проработки       |
| **Обслуживание**| Проще поддерживать       | Сложнее предсказывать эффекты   |

Оба подхода встречаются на практике, но в управлении инфраструктурой предпочтение обычно за декларативной моделью благодаря предсказуемости и встроенной оптимизации плана.

## Жизненный цикл изменений

1.  **Проектирование**: Определение модулей, переменных, политик и зависимостей.
2.  **Описание кода**: Добавление/изменение ресурсов и параметров.
3.  **Планирование**: Генерация плана изменений и анализ влияния.
4.  **Ревью и проверки**: Политика веток, статический анализ, тесты.
5.  **Применение**: Транзакционное выполнение и запись состояния.
6.  **Мониторинг дрейфа**: Периодическая сверка факта с желаемым состоянием.

## Минимальные примеры

Декларативное описание виртуальной машины и сети в облаке:

```hcl
variable "env" { default = "stage" }

resource "cloud_network" "vpc" {
  cidr = "10.10.0.0/16"
  name = "vpc-${var.env}"
}

resource "cloud_instance" "app" {
  name       = "app-${var.env}"
  image      = "ubuntu-22.04"
  size       = "2cpu-4gb"
  subnet_id  = cloud_network.vpc.main_subnet_id
  tags       = { role = "web", env = var.env }
}
```

Идемпотентная конфигурация пакета и службы в конфигурационном менеджменте:

```yaml
- hosts: web
  become: true
  tasks:
    - name: Установить nginx
      apt:
        name: nginx
        state: present
        update_cache: true

    - name: Обеспечить автозапуск и запуск
      service:
        name: nginx
        state: started
        enabled: true
```

В обоих случаях исходники можно версионировать, параметризовать переменными окружений, интегрировать в CI/CD и сопроводить политиками проверки (например, форматирование, lint, policy as code). Такой подход превращает инфраструктуру в предсказуемый, воспроизводимый и управляемый артефакт разработки.
