# Infrastructure as Code (IaC): обзор

## Определения

**Инфраструктура как код (Infrastructure as Code, IaC)** — подход к управлению и предоставлению вычислительной инфраструктуры (серверы, сети, балансировщики, базы данных), при котором конфигурация описывается машинно-читаемыми файлами (кодом), а не настраивается вручную.

Код хранится в системе контроля версий (Git) наравне с кодом приложения, что позволяет автоматизировать, версионировать и воспроизводить инфраструктуру.

## Базовые концепции

### Уровни абстракции инфраструктуры

Инфраструктуру принято делить на уровни абстракции, каждый из которых решает свой класс задач:

1. **IaaS (Infrastructure as a Service)** — низший уровень: виртуальные машины, диски, сети, маршрутизаторы. Предоставляется cloud-провайдерами (Яндекс.Облако, AWS, GCP) или внутренними облачными платформами. Это «фундамент» инфраструктуры — объекты, имеющие прямые железные аналоги. Инструменты: Terraform, OpenStack.
2. **PaaS (Platform as a Service)** — средний уровень: платформы для развёртывания приложений — Kubernetes, OpenShift, managed-сервисы (БД, очереди, кеши). Инструменты: Ansible (для кастомных платформ), Helm, операторы Kubernetes.
3. **SaaS (Software as a Service)** — высший уровень: готовые сервисы для приложений — managed PostgreSQL, Redis, Object Storage, middleware-фреймворки (Django, Spring Boot). Инструменты: Docker Compose, Kubernetes Deployment, PaaS-провайдеры.

> **Рекомендация:** Ansible оптимален для уровней PaaS и SaaS (настройка ПО, деплой приложений). Для IaaS предпочтительнее Terraform. Ansible на уровне IaaS допустим только для тестирования provisioning-кода (поднять ВМ → запустить playbook → проверить результат).

### Ключевые принципы

* **Декларативность:** Вы описываете *желаемое состояние* инфраструктуры ("что должно быть"), а инструмент IaC сам определяет, *как* этого достичь.
* **Идемпотентность:** Повторное применение одного и того же кода не приводит к изменению состояния, если оно уже соответствует описанному. Это делает операции безопасными и предсказуемыми.
* **Версионируемость:** Вся история изменений инфраструктуры хранится в Git. Любое изменение можно отследить, проанализировать и, при необходимости, откатить.
* **Источник истины (Source of Truth):** Код в репозитории является единственным достоверным источником информации о том, какой должна быть инфраструктура. Ручные изменения на серверах запрещены.

### Декларативный vs. Императивный подходы

| Аспект | Декларативный (IaC-подход) | Императивный (Скриптовый подход) |
| :--- | :--- | :--- |
| **Что описываем?**| **Что** должно быть (цель) | **Как** это сделать (шаги) |
| **Пример** | `resource "server" { state = "running" }` | `if !server_exists(); then create_server(); fi` |
| **Идемпотентность**| Встроена в инструмент | Требует ручной реализации |
| **Предсказуемость**| Высокая (план изменений) | Низкая (зависит от текущего состояния) |

Хотя императивный подход полезен для одноразовых задач, декларативный является стандартом для IaC благодаря своей надежности.

### Сравнение инструментов: Terraform vs. Ansible

Хотя оба инструмента являются ключевыми в IaC, они решают разные задачи и часто используются вместе.

| Аспект | Terraform | Ansible |
| :--- | :--- | :--- |
| **Основная цель** | **Provisioning (Предоставление)**: Создание, изменение и версионирование инфраструктуры (VM, сети, БД). | **Configuration Management (Управление конфигурацией)**: Установка ПО, настройка сервисов, управление пользователями на существующих машинах. |
| **Парадигма** | **Декларативная**: Описывается конечное состояние инфраструктуры. Terraform сам строит граф зависимостей и план достижения этого состояния. | **Процедурно-декларативная**: Плейбук — это упорядоченный список задач (процедурность), но каждый модуль внутри задачи — декларативен и идемпотентен. |
| **Управление состоянием** | **Stateful**: Terraform ведет **state file**, где хранится соответствие между кодом и реальными ресурсами. Это критично для планирования изменений. | **Stateless**: Ansible не хранит состояние. Он динамически получает факты с управляемых узлов при каждом запуске для определения текущего состояния. |
| **Аналог "роли"** | **Модули (Modules)**: Способ группировки и переиспользования кода для создания сложных ресурсов. | **Роли (Roles)**: Основная единица переиспользования для инкапсуляции задач, шаблонов и переменных. |
| **Жизненный цикл** | Управляет полным жизненным циклом ресурса: `create`, `read`, `update`, `delete`. | Работает с уже существующими ресурсами. |

> Концепция stateful/stateless в контексте инструментов — см. **[Stateful vs Stateless](./stateful_vs_stateless.md)**.

**Области пересечения и синергия:**

*Пересечение:*
* **Provisioners в Terraform:** Terraform может выполнять скрипты на созданных ресурсах (например, через `remote-exec`). Это можно использовать для простой конфигурации, но это считается "запахом" и усложняет декларативный подход.
* **Модули провайдеров в Ansible:** Ansible имеет модули для работы с облачными API (например, `aws_ec2_instance`), что позволяет ему создавать инфраструктуру. Однако его возможности в этой области уступают Terraform.

*Синергия (стандартный паттерн):*

1. **Terraform** создает базовую инфраструктуру: виртуальные машины, сети, балансировщики.
2. **Terraform** генерирует **инвентарь** для Ansible (например, с помощью [шаблонов](https://developer.hashicorp.com/terraform/language/functions/templatefile) или простого скрипта, который парсит `terraform output`).
3. **Ansible** подключается к созданным машинам и выполняет их детальную настройку: устанавливает приложения, настраивает конфигурационные файлы, запускает сервисы.

## Практические сценарии

### Паттерны структуры IaC-проектов

Для соблюдения принципа DRY (Don't Repeat Yourself) и модульного переиспользования кода применяются следующие паттерны организации репозиториев:

| Паттерн | Описание | Когда применять |
| :--- | :--- | :--- |
| **Монолитный стек (Monorepo)** | Вся инфраструктура, плейбуки, инвентарь и Terraform-код — в одном репозитории. | Небольшие проекты, одна команда. Упрощает координацию, но затрудняет масштабирование. GitLab позволяет ограничить запуск jobs по изменённым файлам (`rules:changes`). |
| **Стек группы приложений** | Отдельный репозиторий для группы связанных сервисов (например, «веб-фронтенд + балансировщик + БД»). Playbook'и: `init.yml`, `update-app.yml`, `update-db.yml`. | Несколько команд, каждая отвечает за свой стек. Баланс между изоляцией и переиспользованием. |
| **Сервисный стек** | Репозиторий под конкретный сервис (например, `nginx-deploy`). Содержит playbook, inventory и, возможно, Terraform-код для ВМ этого сервиса. | Микросервисная архитектура, независимый деплой каждого сервиса. |
| **Микростек** | Минимальный репозиторий для одного компонента. Роли вынесены в отдельные репозитории и подключаются через Git submodules или Ansible Galaxy. | Крупные организации, зрелая DevOps-культура, максимальное переиспользование ролей. |

**Управление версиями ролей:** При разделении на репозитории роли версионируются через Git-теги (`v1.0`, `v2.1`). При клонировании указывается конкретный тег (`git clone --branch v1.2 ...`), что гарантирует воспроизводимость и контроль изменений.

**Хранение ролей:**
* **Ansible Galaxy** — централизованный реестр, установка через `ansible-galaxy install -r requirements.yml`.
* **Git-репозитории** — собственные роли, подключение через `requirements.yml` с указанием `src: git@...` или Git submodules.
* **GitLab CI Job Token** — для доступа к приватным репозиториям из пайплайна.

### Зачем нужен IaC?

* **Воспроизводимость:** Гарантия того, что окружения для разработки, тестирования и продакшена идентичны.
* **Автоматизация:** Полное устранение ручного труда при создании и обновлении инфраструктуры, что многократно ускоряет процесс.
* **Прозрачность и аудит:** Все изменения проходят через code review, и всегда известно, кто, когда и зачем изменил инфраструктуру.
* **Надежность:** Автоматическое обнаружение "дрейфа" (расхождения между кодом и реальным состоянием) и его исправление.

### Жизненный цикл изменений

1. **Код:** Разработчик описывает инфраструктуру в виде кода (например, в HCL для Terraform).
2. **План:** Инструмент IaC анализирует код и создает "план" — список изменений, которые нужно внести.
3. **Ревью:** План проверяется коллегами.
4. **Применение (Apply):** После одобрения инструмент автоматически применяет изменения.

### Drift Detection: Обнаружение ручных изменений

**Drift (дрейф)** — расхождение между реальным состоянием инфраструктуры и тем, что записано в коде/state-файле. Возникает, когда кто-то вручную изменяет ресурсы (через консоль облака, CLI, API), минуя IaC-инструмент.

**Механизмы обнаружения в разных инструментах:**
* **Terraform:** `terraform plan` сравнивает state-файл с реальными ресурсами и показывает расхождения.
* **Ansible:** Каждый запуск плейбука автоматически сравнивает фактическое состояние хоста с желаемым. Режимы `--check` и `--diff` позволяют обнаружить drift без внесения изменений. Подробнее: [Ansible: обнаружение drift](../Ansible/ansible_core_concepts.md#обнаружение-drift-рассинхронизации-конфигурации).
* **Kubernetes:** Контроллеры постоянно сравнивают текущее состояние кластера с desired state из etcd и автоматически исправляют расхождения (self-healing).

### Пример 1: Создание VM (Terraform)

Декларативное описание виртуальной машины и сети.

```hcl
// main.tf
resource "yandex_vpc_network" "default" {
  name = "app-network"
}

resource "yandex_vpc_subnet" "default" {
  name           = "app-subnet"
  zone           = "ru-central1-a"
  network_id     = yandex_vpc_network.default.id
  v4_cidr_blocks = ["10.5.0.0/24"]
}

resource "yandex_compute_instance" "app" {
  name        = "web-app-server"
  platform_id = "standard-v3"  // Актуальная платформа (2026)
  zone        = "ru-central1-a"

  resources {
    cores  = 2
    memory = 4
  }

  boot_disk {
    initialize_params {
      image_id    = "fd8vj3j1l015********" // Ubuntu 22.04 LTS
      type        = "network-ssd"
      size        = 20
    }
  }

  network_interface {
    subnet_id = yandex_vpc_subnet.default.id
    nat       = true
  }
}
```

**Подробнее:** [Yandex Compute Cloud](../Yandex/Compute-Cloud.md), [Yandex VPC](../Yandex/VPC.md)

### Пример 2: Настройка сервера (Ansible)

Декларативное описание состояния пакета и сервиса.

```yaml
# playbook.yml
- hosts: webservers
  become: yes
  tasks:
    - name: Ensure nginx is at the latest version
      apt:
        name: nginx
        state: latest
    
    - name: Ensure nginx is running and enabled on boot
      service:
        name: nginx
        state: started
        enabled: yes
```

## Дополнительная информация

Применение IaC превращает инфраструктуру из набора хрупких, настроенных вручную серверов в предсказуемый, воспроизводимый и управляемый программный артефакт, который развивается вместе с приложением.

См. также: [модели управления конфигурацией](./configuration_management_models.md) (управление состоянием серверов в рамках IaC).
