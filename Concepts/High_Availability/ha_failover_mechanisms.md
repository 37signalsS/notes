# Механизмы Failover и Heartbeat

## Определения

**Failover (Переключение при отказе)** — это автоматический процесс передачи функций от сбойного компонента системы к резервному. Это ключевой механизм для обеспечения высокой доступности.

**Heartbeat (Сигнал жизнеспособности)** — это регулярный сигнал, посылаемый компонентом системы для демонстрации своей работоспособности. Отсутствие heartbeat-сигнала в течение определенного времени является триггером для запуска процесса failover.

Основы высокой доступности изложены в [общем обзоре HA](./ha_overview.md).

## Основные концепции

### Процесс Failover

1. **Обнаружение сбоя:** Система мониторинга (например, через heartbeat) фиксирует отказ основного узла.
2. **Выбор резерва:** Кластерный менеджер определяет, какой из резервных узлов должен стать новым активным.
3. **Переконфигурация:** На новый активный узел переносятся ресурсы (например, виртуальный IP-адрес) и запускаются необходимые сервисы. Трафик перенаправляется на него.

### Проблема Split-Brain

**Split-Brain ("Расщепление мозга")** — это критическая ситуация в кластере, когда из-за потери связи между узлами несколько из них решают, что они являются активными (master). Это может привести к одновременной записи в разные места и, как следствие, к повреждению или потере данных.

### Механизмы защиты от Split-Brain

* **Кворум (Quorum):** Решение в кластере принимается, только если с ним согласно большинство узлов (или взвешенное большинство). Если узел не видит большинство, он переходит в пассивный режим.
* **Fencing (Изоляция):** Принудительное отключение сбойного узла от общих ресурсов (сети, диска), чтобы он гарантированно не мог ничего испортить.
  * **STONITH (Shoot The Other Node In The Head):** Наиболее надежный вид fencing, который физически отключает питание или перезагружает сбойный узел через контроллер (например, IPMI).

## Практические сценарии

### Сценарий 1: IP Failover с помощью Keepalived (VRRP)

Простой и быстрый способ организовать failover для виртуального IP-адреса (VIP).

**Конфигурация `keepalived.conf`:**

```keepalived
vrrp_script check_app {
  script "/usr/local/bin/check_app.sh" # Скрипт проверки работоспособности приложения
  interval 2                           # Проверять каждые 2 секунды
  fall 3                               # Считать узел упавшим после 3 неудач
  rise 2                               # Считать поднявшимся после 2 удач
}

vrrp_instance VI_WEB {
  state MASTER          # Или BACKUP на резервном узле
  interface eth0        # Сетевой интерфейс
  virtual_router_id 51  # Уникальный ID для VRRP-группы
  priority 150          # Приоритет (у MASTER он выше)
  advert_int 1          # Интервал анонсов

  virtual_ipaddress {
    192.168.1.100/24    # Виртуальный IP-адрес
  }

  track_script {
    check_app           # Привязать скрипт проверки
  }
}
```

*В `check_app.sh` обычно размещается команда, проверяющая, что приложение отвечает, например, `curl` или `systemctl status`.*

### Сценарий 2: Управление ресурсами с Pacemaker/Corosync

Более мощное и комплексное решение для управления кластером из множества ресурсов с зависимостями и гарантированной изоляцией.

**Пример команд для настройки кластера:**

```bash
# 1. Настроить базовый кластер
pcs cluster setup my_cluster node1 node2
pcs cluster start --all
pcs property set stonith-enabled=true

# 2. Настроить STONITH (важнейший шаг!)
pcs stonith create fence_node1 fence_ipmilan pcmk_host_list=node1 ...
pcs stonith create fence_node2 fence_ipmilan pcmk_host_list=node2 ...

# 3. Создать ресурсы: виртуальный IP и веб-сервер
pcs resource create vip IPaddr2 ip=192.168.1.100
pcs resource create web_server apache

# 4. Задать правила: запускать веб-сервер на том же узле, что и VIP
pcs constraint colocation add web_server with vip INFINITY
pcs constraint order vip then web_server
```

## Дополнительная информация

* **Тайминги:** Тщательно подбирайте интервалы heartbeat и таймауты. Слишком короткие могут привести к ложным failover'ам при кратковременной нагрузке на сеть, а слишком длинные — к увеличению времени простоя.
* **Тестирование:** Регулярно тестируйте механизмы failover, имитируя отказы (отключение сети, "убийство" процессов, выключение питания), чтобы быть уверенным в их работоспособности.
