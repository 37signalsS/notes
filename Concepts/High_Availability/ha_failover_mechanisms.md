# Механизмы Failover и Heartbeat

## Определения

**Failover (Переключение при отказе)** — автоматический процесс передачи функций от сбойного компонента к резервному. Ключевой механизм обеспечения [высокой доступности](./ha_overview.md). Напрямую влияет на показатель **RTO** (время восстановления).

**Методы контроля состояния:**
- **Heartbeat (Пульс):** пассивный метод, при котором компонент сам периодически отправляет сигнал «я жив».
- **Health Checks (Проверки здоровья):** активный метод, при котором внешняя система опрашивает компонент (например, по HTTP или TCP).

**Split-Brain (Расщепление мозга)** — критическая ситуация, при которой несколько узлов кластера одновременно считают себя активными (master) из-за потери связи между ними. Это приводит к конфликтам записи и рассинхронизации данных. Подробный сценарий возникновения описан в [репликации БД](../../Databases/Concepts/replication.md#проблема-split-brain-и-решение-через-кворум).

## Базовые концепции

### Процесс Failover

Процесс переключения обычно состоит из трех этапов:
1. **Обнаружение сбоя:** Система мониторинга фиксирует отказ через потерю heartbeat или провал health check.
2. **Выбор резерва:** Алгоритм выбора (или кворум) определяет узел для активации.
3. **Переконфигурация:** Перенос ресурсов (VIP, диски) и перенаправление трафика.

### Типы переключений

| Тип | Название | Описание |
| :--- | :--- | :--- |
| **Graceful** | Плавное (Switchover) | Инициируется вручную (плановое обслуживание). Старый узел корректно завершает сессии перед передачей роли. |
| **Ungraceful** | Аварийное (Failover) | Происходит при внезапном отказе. Возможно повреждение данных или обрыв активных соединений. |

### Механизмы реализации на разных уровнях

#### Сетевой уровень (IP Failover)
Использование виртуального IP (VIP), который перемещается между узлами (Keepalived/VRRP). Эффективно в пределах одной L2-подсети.

#### Уровень DNS (GSLB)
Переключение трафика на уровне DNS-записей.
- **Плюсы:** работает между регионами и ЦОД.
- **Минусы:** зависимость от **TTL (Time To Live)**. Клиенты и промежуточные провайдеры могут кешировать старый IP, что приводит к простою до истечения TTL.

#### Уровень клиента (Client-side Failover)
Логика переключения заложена в клиентской библиотеке или приложении.
- **Retries:** повторные попытки запроса к альтернативным адресам при ошибке.
- **Service Discovery:** клиент получает список активных узлов от Consul или etcd.

#### Уровень Service Mesh
Использование прокси (Envoy, Istio) для автоматического перенаправления трафика от «больных» экземпляров (Outlier Detection) к здоровым.

### Механизмы защиты от Split-Brain

Для предотвращения одновременной работы нескольких мастеров используются механизмы согласования и изоляции.

**Кворум (Quorum)** — принцип, при котором решение в кластере (например, выбор лидера) принимается только при согласии большинства узлов (`floor(N/2) + 1`). Узел или сегмент сети, оказавшийся в меньшинстве, автоматически переходит в пассивный режим или блокирует операции записи.

- Детали реализации: [алгоритм Raft](../../etcd/raft_consensus.md), [консенсус в Consul](../../Consul/consul_consensus.md).

**Fencing (Изоляция)** — принудительное исключение сбойного или изолированного узла из доступа к общим ресурсам (хранилищу, сети).

- **STONITH (Shoot The Other Node In The Head):** Метод физического отключения питания или принудительной перезагрузки узла через контроллер управления (IPMI, BMC, PDU). Гарантирует, что сбойный узел не сможет повредить данные на общем хранилище.

## Практические сценарии

### IP Failover с Keepalived (VRRP)

Обеспечение отказоустойчивости на уровне сетевого адреса (VIP). При сбое мастера VIP «переезжает» на backup-узел.

**Пример конфигурации `keepalived.conf`:**

```keepalived
vrrp_script check_app {
  script "/usr/local/bin/check_app.sh"  # Внешний скрипт проверки
  interval 2                            # Интервал проверки
  fall 3                                # Порог объявления отказа
  rise 2                                # Порог восстановления
}

vrrp_instance VI_1 {
  state MASTER                          # Начальное состояние
  interface eth0                        # Интерфейс для VIP
  virtual_router_id 51                  # ID группы
  priority 150                          # Приоритет (MASTER > BACKUP)
  advert_int 1                          # Интервал анонсов (heartbeat)

  virtual_ipaddress {
    192.168.1.100/24                    # Плавающий IP
  }

  track_script {
    check_app
  }
}
```

### Кластерное управление ресурсами (Pacemaker + Corosync)

Используется для управления сложными сервисами с учетом зависимостей и STONITH.

**Основные команды настройки:**

```bash
# Инициализация и запуск кластера
pcs cluster setup my_cluster node1 node2
pcs cluster start --all

# Настройка STONITH (обязательно для production)
pcs property set stonith-enabled=true
pcs stonith create fence_node1 fence_ipmilan pcmk_host_list=node1 ...

# Создание ресурсов и ограничений
pcs resource create vip IPaddr2 ip=192.168.1.100
pcs resource create web_server apache
pcs constraint colocation add web_server with vip INFINITY
pcs constraint order vip then web_server
```

## Дополнительная информация

### Настройка таймингов

Тайминги heartbeat определяют баланс между скоростью восстановления и стабильностью:

- **Короткие интервалы:** Минимизируют MTTR, но могут привести к «флаппингу» (ложным переключениям) при кратковременных сетевых задержках.
- **Длинные интервалы:** Повышают стабильность, но увеличивают время простоя сервиса при реальном сбое.

### Методы тестирования Failover

Регулярная проверка механизмов переключения обязательна для поддержания надежности:

1. **Сетевая изоляция:** Имитация обрыва связи через `iptables` или `tc`.
2. **Остановка процессов:** Принудительное завершение сервисов через `kill -9`.
3. **Hard Reboot:** Отключение питания через IPMI для проверки STONITH.
