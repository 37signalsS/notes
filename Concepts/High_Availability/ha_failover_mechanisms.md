## Определения

**Failover (Переключение при отказе)** — автоматический процесс передачи функций от сбойного компонента (сервера, сервиса, сетевого интерфейса) к резервному. Это ключевой механизм обеспечения **[высокой доступности](./ha_overview.md)**, напрямую влияющий на показатель **RTO** (Recovery Time Objective — целевое время восстановления).

**Методы контроля состояния:**
- **Heartbeat (Пульс):** пассивный метод, при котором компонент сам периодически отправляет сигнал «я жив» управляющему узлу или соседям по кластеру.
- **Health Checks (Проверки здоровья):** активный метод, при котором внешняя система (балансировщик, мониторинг) опрашивает компонент по протоколам HTTP, TCP, gRPC или выполняет локальный скрипт.

**Split-Brain (Расщепление мозга)** — критическое состояние распределенной системы, при котором из-за потери сетевой связности между узлами кластер распадается на изолированные сегменты, каждый из которых считает себя активным (Master). Это приводит к конфликтам записи, порче данных и нарушению целостности. Подробный сценарий возникновения описан в разделе **[Репликация баз данных](../../Databases/Concepts/replication.md#проблема-split-brain-и-кворум)**.

## Базовые концепции

### Процесс автоматического переключения (Failover Process)

Типовой жизненный цикл переключения состоит из следующих этапов:
1. **Обнаружение сбоя (Detection):** Фиксация отказа через пропуск N пакетов Heartbeat или провал Health Check.
2. **Изоляция (Fencing):** Принудительное исключение сбойного узла из работы для предотвращения Split-Brain.
3. **Выбор резерва (Election):** Определение нового активного узла на основе приоритетов или алгоритма консенсуса.
4. **Переконфигурация (Promotion/Remapping):** Перенос ресурсов (VIP, монтирование дисков) и обновление маршрутизации трафика.

### Типы переключений

| Тип | Название | Описание |
| :--- | :--- | :--- |
| **Graceful** | Плавное (Switchover) | Инициируется администратором для обслуживания. Старый узел корректно завершает сессии, синхронизирует остатки данных и передает роль. |
| **Ungraceful** | Аварийное (Failover) | Происходит при внезапном отказе (Hardware failure, Kernel panic). Сопровождается обрывом активных TCP-соединений и возможной потерей несинхронизированных данных. |

### Механизмы реализации на разных уровнях

#### Сетевой уровень (L2/L3)
- **IP Failover (VIP):** Использование виртуального IP-адреса, который перемещается между узлами с помощью протоколов **VRRP** (Keepalived) или **CARP**. Эффективно в пределах одной L2-подсети.
- **Anycast (BGP/ECMP):** Анонсирование одного и того же IP-адреса из разных точек сети через протокол BGP. При отказе узла маршрут автоматически исчезает из таблиц BGP, и трафик перенаправляется на следующий ближайший узел.

#### Уровень DNS (GSLB)
Переключение трафика на уровне глобальной балансировки DNS.
- **Плюсы:** Работает между регионами и облачными провайдерами.
- **Минусы:** Зависимость от **TTL (Time To Live)**. Клиентские ОС и провайдеры могут кешировать старый IP, что приводит к простою до истечения срока жизни записи. В 2026 году рекомендуется использование TTL 10-60 секунд.

#### Уровень клиента (Client-side Failover)
Логика закладывается непосредственно в приложение или клиентскую библиотеку.
- **Retries & Backoff:** Повторные попытки запроса к альтернативным адресам при ошибке связи.
- **Service Discovery:** Получение списка активных эндпоинтов от динамических реестров (Consul, etcd, Kubernetes API).

#### Уровень Service Mesh
Использование интеллектуальных прокси (Envoy) для автоматического перенаправления трафика.
- **Outlier Detection (Istio/Linkerd):** Автоматическое временное исключение («вышибание») конкретных экземпляров сервиса, которые начинают возвращать ошибки (например, 5xx) или имеют аномальные задержки.

### Сравнение архитектурных подходов к резервированию

Выбор метода зависит от критичности данных и допустимого времени простоя:

| Подход | Механизм | Синхронизация данных | Управление | Плюсы / Минусы |
| :--- | :--- | :--- | :--- | :--- |
| **DNS-based** | A/SRV записи | Нет (независимые узлы) | TTL в DNS | (+) Простота. (-) Задержки кэширования DNS, нет контроля состояния. |
| **Keepalived + Warmspare** | VIP (VRRP) | Отложенная (Backup/Rsync) | Скрипты `notify` | (+) Простота, независимые ФС. (-) Потеря данных между синхронизациями. |
| **Pacemaker + DRBD** | VIP + Resources | Реальное время (Блочная) | CRM (Pacemaker) | (+) Актуальные данные, полный контроль. (-) Сложность, риск Split-Brain. |

### Механизмы защиты от Split-Brain

**Кворум (Quorum)** — принцип принятия решений большинством голосов (`floor(N/2) + 1`). Сегмент кластера, оставшийся в меньшинстве, обязан прекратить обслуживание запросов на запись.
- Реализации: **[Алгоритм Raft](../../etcd/raft_consensus.md)**, **[Консенсус в Consul](../../Consul/consul_consensus.md)**.

**Fencing (Изоляция ресурсов)** — гарантированное лишение узла возможности влиять на общую инфраструктуру.
- **STONITH (Shoot The Other Node In The Head):** Метод принудительного отключения питания или жесткой перезагрузки узла через контроллеры управления (IPMI, BMC, iDRAC, управляемые PDU). Это гарантирует, что «зависший» мастер не начнет писать в общие диски одновременно с новым мастером.
- **Storage Fencing:** Блокировка доступа к LUN на уровне FC-коммутатора или использование SCSI-3 Persistent Reservations.

## Практические сценарии

### Настройка IP Failover с Keepalived (VRRP)

Пример конфигурации `/etc/keepalived/keepalived.conf` для обеспечения отказоустойчивости балансировщика с проверкой состояния сервиса.

```keepalived
vrrp_script check_service {
  script "/usr/bin/pgrep nginx"       # Проверка наличия процесса nginx
  interval 2                          # Каждые 2 секунды
  fall 3                              # 3 неудачи = переход в BACKUP
  rise 2                              # 2 успеха = возврат в строй
}

vrrp_instance VI_1 {
  state MASTER                        # Узел-лидер
  interface eth0                      # Сетевой интерфейс для VIP
  virtual_router_id 51                # ID группы (одинаковый в паре)
  priority 150                        # Приоритет (на BACKUP должен быть ниже, например 100)
  advert_int 1                        # Интервал анонсов (Heartbeat)

  authentication {
    auth_type PASS
    auth_pass secure_password         # Пароль для VRRP-трафика
  }

  virtual_ipaddress {
    192.168.1.100/24                  # Плавающий виртуальный IP
  }

  track_script {
    check_service
  }
}
```

### Кластерное управление ресурсами (Pacemaker + Corosync)

Стек для управления сложными Stateful-сервисами (PostgreSQL, NFS, iSCSI).

**Основные операции администрирования (pcs):**

```bash
# Инициализация кластера на двух узлах
pcs cluster setup my_ha_cluster node1 node2
pcs cluster start --all

# Настройка STONITH (Критически важно для защиты от Split-Brain)
pcs property set stonith-enabled=true
pcs stonith create fence_node1 fence_ipmilan ipaddr="10.0.0.1" login="admin" passwd="password" pcmk_host_list="node1"

# Создание ресурсов: VIP и Apache
pcs resource create virtual_ip IPaddr2 ip=192.168.1.100 cidr_netmask=24
pcs resource create web_app ocf:heartbeat:apache configfile="/etc/httpd/conf/httpd.conf"

# Установка ограничений (Constraints)
# 1. Colocation: Веб-приложение должно быть там же, где и VIP
pcs constraint colocation add web_app with virtual_ip INFINITY
# 2. Order: Сначала запускается VIP, затем приложение
pcs constraint order virtual_ip then web_app
```

## Дополнительная информация

### Настройка таймингов и предотвращение Flapping

Тайминги Heartbeat определяют баланс между скоростью обнаружения отказа и стабильностью системы:
- **Интервал (Interval):** Частота отправки сигналов (обычно 1 секунда).
- **Таймаут (Timeout/Dead interval):** Время, после которого узел считается мертвым.
- **Flapping (Дребезг):** Ситуация, когда из-за нестабильной сети узел постоянно переходит из MASTER в BACKUP. 
    * *Решение:* Увеличение `fall` (количества пропусков) и использование `hold-off` таймеров, предотвращающих мгновенный возврат роли мастеру после восстановления.

### Методы тестирования Failover (Chaos Engineering)

Механизмы переключения должны регулярно проверяться:
1. **Сетевая изоляция:** Блокировка UDP-порта 5405 (Corosync) или VRRP-пакетов через `iptables -A INPUT -p vrrp -j DROP`. Проверка перехода ролей.
2. **Hard Reboot:** Принудительная перезагрузка мастера через `echo c > /proc/sysrq-trigger` (Kernel Panic). Проверка срабатывания STONITH и корректного захвата ресурсов резервом.
3. **Ресурсный сбой:** Остановка процесса через `kill -9`. Проверка способности Pacemaker/Kubernetes перезапустить сервис локально перед выполнением Failover.
