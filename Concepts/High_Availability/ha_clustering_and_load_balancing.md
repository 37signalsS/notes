# Кластеризация и балансировка нагрузки для высокой доступности

## Определения

**Кластеризация** — объединение нескольких серверов (узлов) в единую логическую систему, которая воспринимается внешним пользователем как единый ресурс. Используется для обеспечения отказоустойчивости (**High Availability**) и повышения производительности через горизонтальное масштабирование.

**Балансировка нагрузки (Load Balancing)** — процесс оптимального распределения входящего трафика между группой бэкенд-серверов. Основные цели: предотвращение перегрузки отдельных узлов, минимизация времени ответа и обеспечение непрерывной доступности сервиса при отказе части инфраструктуры.

## Основные концепции

### Модели кластеризации

| Модель | Принцип работы | Применение |
| :--- | :--- | :--- |
| **Active-Active** | Все узлы одновременно обрабатывают трафик. Обеспечивает максимальную утилизацию ресурсов и высокую пропускную способность. | [Stateless-сервисы](../stateful_vs_stateless.md), API-шлюзы, CDN. |
| **Active-Passive** | Один узел активен, остальные в «горячем» резерве (Standby). При отказе лидера резерв принимает нагрузку. | [Stateful-сервисы](../stateful_vs_stateless.md), базы данных (Primary-Replica). |
| **N+M** | Группа из `N` активных узлов подстраховывается `M` резервными, готовыми заменить любой отказавший узел. | Облачные платформы, кластеры виртуализации (Proxmox, VMware). |

Для предотвращения конфликтов в Active-Passive моделях используются механизмы кворума и изоляции (Fencing). Подробнее: **[Механизмы Failover и Heartbeat](./ha_failover_mechanisms.md)**.

### Уровни балансировки (OSI)

#### 1. Уровень L4 (Транспортный)
Балансировка на основе IP-адресов и TCP/UDP портов без разбора содержимого пакетов.
- **Особенности:** Максимальная производительность, низкая нагрузка на CPU балансировщика, прозрачность для шифрования (TLS-терминация на бэкендах).
- **Технология DSR (Direct Server Return):** Метод, при котором балансировщик (например, IPVS) обрабатывает только входящий трафик, а бэкенд отвечает клиенту напрямую. Это устраняет «бутылочное горлышко» на исходящем канале балансировщика при больших объемах данных.
- **Инструменты:** **IPVS (LVS)**, **HAProxy** (режим `tcp`), Cloud NLB (AWS, GCP).

#### 2. Уровень L7 (Прикладной)
Балансировка с анализом HTTP-заголовков, URL, Cookies и методов API.
- **Особенности:** Умная маршрутизация (Path-based routing), терминация SSL/TLS, кэширование контента, защита от L7-атак (WAF). В 2026 году обязательна поддержка **HTTP/3 (QUIC)** и **gRPC**.
- **Инструменты:** **Nginx**, **Envoy**, **Angie**, **HAProxy** (режим `http`), Cloud ALB.

### Алгоритмы распределения нагрузки

- **Round Robin (Поочередный):** Запросы распределяются циклично. Подходит для серверов с идентичной мощностью.
- **Least Connections (Минимум соединений):** Запрос направляется на сервер с наименьшим числом активных сессий. Эффективно для запросов с разным временем обработки.
- **Sticky Sessions (Привязка сессий):** Направление всех запросов одного клиента на один и тот же сервер (через IP Hash или Cookie). Требуется для приложений, хранящих состояние в локальной памяти.
- **Consistent Hashing (Согласованное хеширование):** Алгоритмы (например, **Maglev** или **Ketama**), минимизирующие перераспределение трафика при добавлении или удалении серверов из пула. Критично для кэширующих прокси и распределенных БД для сохранения высокого *Cache Hit Ratio*.

### Проверки состояния (Health Checks)

- **TCP Check:** Проверка доступности порта (открытие/закрытие соединения).
- **HTTP Check:** Запрос к эндпоинту (например, `/healthz`) с ожиданием статус-кода `200 OK`.
- **gRPC Check:** Проверка работоспособности по нативному протоколу gRPC.
- **Passive Health Check (Outlier Detection):** Анализ реального трафика. Балансировщик исключает узел, если тот начинает возвращать аномальное количество ошибок (например, 5xx) без специальных проверочных запросов.

## Практические сценарии

### Подходы к управлению состоянием (State)

* **Shared-Nothing:** Каждый узел автономен. Состояние синхронизируется через внешнее хранилище или репликацию (например, Redis, Cassandra). Это наиболее масштабируемый подход.
* **Shared-Disk:** Узлы используют общее блочное или файловое хранилище (SAN, Ceph, NFS). Упрощает переключение (Failover) данных, но создает риск **SPOF** на уровне дисковой системы.

### Современные среды развертывания

#### 1. Kubernetes
- **kube-proxy:** Базовая L4 балансировка внутри кластера через iptables или высокопроизводительный **IPVS**.
- **Ingress Controller:** Традиционная L7 точка входа (Nginx Ingress, Traefik).
- **Gateway API:** Современный стандарт Kubernetes (v1.30+), приходящий на смену Ingress. Обеспечивает разделение ролей (инфраструктура vs приложение) и нативную поддержку L4/L7 маршрутизации через `HTTPRoute` и `TCPRoute`. См. **[Обзор Gateway API](../../Kubernetes/Networking/gateway_api/definitions.md)**.

#### 2. Service Mesh (Envoy / Istio / Linkerd)
Балансировка переносится на сторону клиента (**Client-side Balancing**).
- **Sidecar-модель:** Балансировка через прокси Envoy внутри каждого пода.
- **Ambient-модель (Sidecar-less):** Разделение на легкий L4-прокси (**Ztunnel**) на каждом узле и Waypoint-прокси для L7-логики. Обеспечивает mTLS и сложную балансировку с минимальным оверхедом.

#### 3. Глобальная балансировка (GSLB)
Распределение трафика между географически удаленными ЦОД:
- **DNS-based:** Выдача разных IP-адресов на основе Geo-IP или загрузки регионов.
- **Anycast BGP:** Использование одного IP-адреса, анонсируемого из разных точек мира. Сеть (BGP) направляет пользователя к ближайшему узлу.

## Практический пример: HAProxy (L7)

Пример конфигурации для распределения HTTP-трафика с активными проверками:

```haproxy
backend app_pool
    mode http
    balance leastconn
    # Адаптивное хеджирование и таймауты
    option httpchk GET /health
    http-check expect status 200
    
    server srv1 10.0.1.10:8080 check inter 2s fall 3 rise 2 weight 10
    server srv2 10.0.1.11:8080 check inter 2s fall 3 rise 2 weight 5
```
