# Кластеризация и балансировка нагрузки для высокой доступности

## Определения

**Кластеризация** — архитектурный подход, заключающийся в объединении группы независимых серверов (узлов) в единую логическую систему. С точки зрения клиента кластер выглядит как единый высоконадежный ресурс. Основная цель кластеризации — обеспечение **[высокой доступности](./ha_overview.md)** (HA) и горизонтальное масштабирование производительности.

**Балансировка нагрузки (Load Balancing)** — процесс распределения входящего сетевого трафика или вычислительных задач между узлами кластера. Балансировщик выступает в роли «регулировщика», который предотвращает перегрузку отдельных серверов, минимизирует задержки (Latency) и гарантирует непрерывность обслуживания при выходе из строя части инфраструктуры.

## Основные концепции

### Модели кластеризации

Выбор модели зависит от требований к RTO (время восстановления) и стоимости ресурсов.

| Модель | Принцип работы | Почему это важно |
| :--- | :--- | :--- |
| **Active-Active** | Все узлы одновременно принимают трафик. | Максимальное использование ресурсов. Идеально для **Stateless** систем. Требует внешнего балансировщика. |
| **Active-Passive** | Один узел («Мастер») работает, остальные («Standby») ждут. | Необходима для **Stateful** систем (БД), где запись в несколько точек одновременно может привести к конфликтам. Требует механизмов выбора лидера. |
| **N+M** | Группа из `N` активных узлов страхуется `M` резервными. | Экономически эффективнее, чем 1+1. Часто применяется в облачных фермах и гипервизорах (Proxmox/VMware). |

**Важный нюанс:** В моделях с переключением ролей (Failover) критически важно предотвратить состояние **Split-Brain** («раскол мозга»). Для этого используются механизмы кворума и изоляции (Fencing). Подробнее: **[Механизмы Failover и Heartbeat](./ha_failover_mechanisms.md)**.

### Уровни балансировки по модели OSI

#### 1. Уровень L4 (Транспортный)
Балансировка на основе IP-адресов и портов (TCP/UDP). Балансировщик не «смотрит» внутрь пакета (не видит HTTP-пути или Cookies).
*   **Преимущества:** Экстремально высокая производительность, низкая нагрузка на CPU. Не требует расшифровки TLS (SSL Passthrough).
*   **Технология Direct Server Return (DSR):** Метод, при котором балансировщик (например, IPVS) обрабатывает только входящие пакеты, а ответные пакеты бэкенд отправляет клиенту напрямую. 
    *   *Зачем:* В веб-трафике ответ обычно в десятки раз больше запроса. DSR устраняет «бутылочное горлышко» на исходящем канале балансировщика.
*   **Инструменты:** **IPVS (LVS)**, **HAProxy** (mode `tcp`), Cloud NLB.

#### 2. Уровень L7 (Прикладной)
Балансировка с анализом содержимого протокола (HTTP, gRPC, MySQL).
*   **Преимущества:** Умная маршрутизация на основе URL (например, `/api` на один пул, `/static` на другой), привязка сессий (Sticky Sessions), терминация SSL/TLS, WAF-фильтрация.
*   **Вызов 2026 года:** Обязательная поддержка **HTTP/3 (QUIC)** и мультиплексирования в **gRPC**, где одно TCP-соединение несет множество запросов, требуя балансировки каждого стрима отдельно.
*   **Инструменты:** **Nginx**, **Envoy**, **HAProxy** (mode `http`), Cloud ALB.

### Алгоритмы распределения нагрузки

#### 1. Классические алгоритмы
1.  **Round Robin (Поочередно):** Простой циклический перебор. Идеально подходит для пулов с идентичными по мощности серверами и короткими запросами.
2.  **Weighted Round Robin:** Версия с весами. Сервер с `weight=2` получит в два раза больше запросов, чем сервер с `weight=1`. Применяется при разной производительности бэкендов.
3.  **Least Connections (Минимум соединений):** Направляет запрос на узел с наименьшим количеством активных сессий. Эффективен, когда время обработки запросов сильно варьируется («тяжелые» отчеты vs «легкие» API-вызовы).
4.  **Source IP Hash:** Хеширование IP-адреса клиента для привязки к конкретному бэкенду. Обеспечивает простейшую **Session Affinity**, но плохо масштабируется при использовании NAT (множество клиентов за одним IP).

#### 2. Согласованное хеширование (Consistent Hashing)
В отличие от простого `Hash(key) % N`, где изменение количества узлов `N` приводит к перераспределению почти всех ключей, согласованное хеширование минимизирует перемещение данных.
*   **Hash Ring (Кольцо хешей):** Узлы и ключи располагаются на виртуальном кольце (диапазон значений хеш-функции). Ключ назначается первому узлу, встреченному при движении по часовой стрелке.
*   **Виртуальные узлы (Vnodes):** Для борьбы с неравномерным распределением (hotspots) каждый физический сервер представляется сотнями виртуальных точек на кольце. Это обеспечивает балансировку с точностью до 1-5% (реализовано в **Ketama** для кэшей).
*   **Maglev (Google):** Алгоритм, использующий фиксированную таблицу соответствия (lookup table) большого размера. Каждый узел имеет свой список предпочтений для заполнения ячеек таблицы. 
    *   *Преимущество:* Нулевое время поиска (O(1)) и экстремально равномерное распределение даже при частых отказах узлов. Применяется в Google Maglev и Facebook Katran.

#### 3. Power of Two Choices (P2C)
Решает проблему «стадного поведения» (Thundering Herd) в распределенных системах.
*   **Принцип:** Вместо выбора абсолютно лучшего узла (как в Least Conn), балансировщик выбирает **два случайных** узла и направляет запрос на лучший из них.
*   **Почему это важно:** В системах с несколькими независимыми балансировщиками классический Least Connections может привести к тому, что все балансировщики одновременно отправят трафик на один и тот же «самый свободный» узел, перегрузив его. P2C математически гарантирует экспоненциально лучшее распределение нагрузки при минимальных вычислительных затратах.
*   **Реализация:** `random two least_conn` в **Nginx/Angie**, балансировка по умолчанию в **Envoy**.

#### 4. Адаптивная балансировка по латентности (Latency-based)
Самый современный подход, основанный на реальной производительности бэкендов «здесь и сейчас».
*   **Least Time / Least Response Time:** Выбор узла с минимальным временем ответа (RTT + время обработки).
*   **EWMA (Exponentially Weighted Moving Average):** Экспоненциально взвешенное скользящее среднее. Придает больший вес недавним замерам латентности, позволяя мгновенно реагировать на деградацию производительности узла (например, из-за GC-пауз или переполнения очереди).
*   **Peak EWMA:** Вариант, учитывающий количество запросов в полете (in-flight), чтобы не отправлять трафик на узел, который отвечает быстро, но уже близок к насыщению.
*   **Инструменты:** **Linkerd** (EWMA), **Nginx Plus** (`least_time`), **Envoy** (Adaptive Concurrency).

### Проверки состояния (Health Checks)

- **TCP Check:** Проверка доступности порта (открытие/закрытие соединения).
- **HTTP Check:** Запрос к эндпоинту (например, `/healthz`) с ожиданием статус-кода `200 OK`.
- **gRPC Check:** Проверка работоспособности по нативному протоколу gRPC.
- **Passive Health Check (Outlier Detection):** Анализ реального трафика. Балансировщик исключает узел, если тот начинает возвращать аномальное количество ошибок (например, 5xx) без специальных проверочных запросов.

## Практические сценарии

### Подходы к управлению состоянием (State)

* **Shared-Nothing:** Каждый узел автономен. Состояние синхронизируется через внешнее хранилище или репликацию (например, Redis, Cassandra). Это наиболее масштабируемый подход.
* **Shared-Disk:** Узлы используют общее блочное или файловое хранилище (SAN, Ceph, NFS). Упрощает переключение (Failover) данных, но создает риск **SPOF** на уровне дисковой системы.

### Современные среды развертывания

#### 1. Kubernetes
- **kube-proxy:** Базовая L4 балансировка внутри кластера через iptables или высокопроизводительный **IPVS**.
- **Ingress Controller:** Традиционная L7 точка входа (Nginx Ingress, Traefik).
- **Gateway API:** Современный стандарт Kubernetes (v1.30+), приходящий на смену Ingress. Обеспечивает разделение ролей (инфраструктура vs приложение) и нативную поддержку L4/L7 маршрутизации через `HTTPRoute` и `TCPRoute`. См. **[Обзор Gateway API](../../Kubernetes/Networking/gateway_api/definitions.md)**.

#### 2. Service Mesh (Envoy / Istio / Linkerd)
Балансировка переносится на сторону клиента (**Client-side Balancing**).
- **Sidecar-модель:** Балансировка через прокси Envoy внутри каждого пода.
- **Ambient-модель (Sidecar-less):** Разделение на легкий L4-прокси (**Ztunnel**) на каждом узле и Waypoint-прокси для L7-логики. Обеспечивает mTLS и сложную балансировку с минимальным оверхедом.

### Глобальная балансировка (GSLB)

Распределение трафика между географически удаленными ЦОД для защиты от катастрофических сбоев целого региона.

| Метод | Механизм | Применение |
| :--- | :--- | :--- |
| **DNS-based** | DNS-сервер отдает IP ближайшего к пользователю ЦОД. | Простота реализации, поддержка Geo-IP. Ограничено TTL кэширования DNS. |
| **Anycast BGP** | Один IP анонсируется из разных точек мира. Сеть (BGP) сама направляет пользователя к ближайшему узлу. | Минимальные задержки, мгновенное переключение при сбое узла. Требует собственного диапазона IP и поддержки BGP. |

### Балансировка на стороне клиента (Client-side)

В современных распределенных системах (gRPC, микросервисы) балансировка часто переносится с центрального узла на самого клиента.
*   **Почему:** Устранение центральной точки отказа и «лишнего хопа» сети. Клиент получает список IP из Service Discovery (Consul/etcd/K8s) и сам выбирает узел.
*   **Пример:** Балансировка `grpc-go` через `xDS` или `Lookaside` балансировщик.

## Диагностика и устранение неисправностей

| Проблема | Вероятная причина | Первые шаги |
| :--- | :--- | :--- |
| **Неравномерная нагрузка (Skew)** | Использование Round Robin для запросов разной тяжести или долгоживущие соединения (gRPC). | Перейти на **Least Connections**. Проверить поддержку балансировки стримов (L7) для HTTP/2. |
| **Flapping (Дребезг)** | Нестабильная сеть или слишком агрессивные таймауты Health Checks. | Увеличить `fall` (кол-во провалов до исключения) и `interval`. Проверить логи бэкенда на GC-паузы. |
| **Потеря сессий** | Отсутствие Sticky Sessions при наличии локального состояния (Auth/Cart) в приложении. | Включить Cookie-based persistence. В 2026 году рекомендуется вынос состояния в **Redis Cluster**. |
| **Задержки на L7** | Высокая нагрузка на CPU балансировщика из-за TLS-терминации или WAF. | Использовать аппаратное ускорение TLS или перенести терминацию на отдельный слой (Edge). |
