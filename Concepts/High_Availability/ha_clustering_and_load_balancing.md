# Кластеризация и балансировка для HA

## Определения

**Кластеризация** — объединение нескольких серверов (узлов) в единую систему для обеспечения отказоустойчивости и/или повышения производительности.

**Балансировка нагрузки** — распределение входящего трафика между узлами кластера для предотвращения перегрузок и эффективного использования ресурсов.

Эти механизмы тесно связаны и часто используются вместе. Базовые принципы высокой доступности описаны в [обзоре HA](./ha_overview.md).

## Базовые концепции

### Шаблоны кластеризации

* **Active-Active:** Все узлы одновременно обслуживают трафик.
  * *Применение:* [stateless-сервисы](../stateful_vs_stateless.md), API-шлюзы, веб-серверы.
  * *Преимущества:* Отличная утилизация ресурсов, горизонтальное масштабирование.
* **Active-Passive:** Один узел активен, остальные в резерве.
  * *Применение:* [stateful-сервисы](../stateful_vs_stateless.md), базы данных (в классическом варианте).
  * *Преимущества:* Простота управления состоянием, предсказуемый failover.
* **N+1 / N+M:** Пул из `N` рабочих узлов и `M` резервных.
  * *Применение:* Крупные пулы однотипных приложений.
  * *Преимущества:* Экономия ресурсов по сравнению с дублированием 1-к-1.
* **Shared-nothing vs Shared-disk:**
  * *Shared-nothing:* Узлы не имеют общих ресурсов (диска, памяти) и синхронизируют состояние по сети. Лучше масштабируется.
  * *Shared-disk:* Узлы имеют доступ к общему хранилищу. Упрощает failover, но хранилище может стать узким местом или SPOF.

### Балансировка нагрузки

* **Уровни балансировки:**
  * **L4 (Transport Layer):** Работает на уровне TCP/UDP (порты, IP-адреса). Быстрый, но не "видит" содержимого запросов.
  * **L7 (Application Layer):** Работает на уровне приложения (HTTP-заголовки, URL). Позволяет реализовать сложную логику маршрутизации (канареечные развертывания, A/B-тесты), терминировать TLS.
* **Алгоритмы балансировки:**
  * **Round Robin (Поочередный):** Распределяет запросы последовательно между всеми доступными серверами. Подходит для однородных серверов с равномерной нагрузкой.
  * **Weighted Round Robin (Взвешенный поочередный):** Вариация Round Robin с учётом веса сервера. Более мощные узлы получают больше запросов, слабые — меньше.
  * **Least Connections (Наименьшее количество соединений):** Направляет новый запрос на сервер с наименьшим количеством активных соединений. Эффективен при неравномерной нагрузке и запросах с разной длительностью обработки.
  * **Least Response Time (Наименьшее время ответа):** Трафик направляется на сервер с наименьшим средним временем ответа. Учитывает текущее состояние системы, а не только количество соединений.
  * **IP Hash (Хеш IP-адреса):** Распределяет запросы на основе хеша IP-адреса клиента. Обеспечивает "липкость" сессий (sticky sessions) — запросы от одного клиента всегда направляются на один сервер.
  * **Random (Случайный):** Случайным образом выбирает сервер для каждого нового запроса. Полезен при наличии нескольких балансировщиков без обмена информацией о нагрузке.
  * **Weighted (Взвешенный):** Может применяться к Round Robin или Least Connections. Серверам назначаются веса, и трафик распределяется пропорционально этим весам, что позволяет направлять больше трафика на более мощные или менее загруженные серверы.

Подробная реализация алгоритмов в Nginx: **[Nginx Load Balancing: Алгоритмы](../../WebServers/Nginx/Proxy/Load_Balancing/algorithms.md)**.

Подробная реализация алгоритмов в HAProxy: **[HAProxy: Алгоритмы балансировки](../../WebServers/haproxy_overview.md#алгоритмы-балансировки-нагрузки)**.

### Мониторинг балансировки нагрузки

Для контроля эффективности балансировки и своевременного выявления проблем необходимо отслеживать следующие метрики:

| Метрика | Описание | Критичность |
| :--- | :--- | :--- |
| **Задержка (Latency)** | Время обработки запроса. Отслеживайте перцентили (p95, p99), а не среднее значение. | Высокая |
| **Время ответа (Response Time)** | Время от получения запроса до отправки ответа клиенту. Включает время обработки бэкендом. | Высокая |
| **Активные соединения** | Количество текущих подключений к каждому бэкенд-серверу. Помогает выявить неравномерное распределение. | Средняя |
| **Запросов на сервер** | Число запросов, обрабатываемых каждым бэкендом в единицу времени. | Средняя |
| **Ошибки 5xx** | Количество ошибок сервера (500, 502, 503, 504). Рост указывает на проблемы с бэкендами. | Критическая |
| **Процент недоступных бэкендов** | Доля серверов, исключённых из ротации по health check. | Критическая |

**Дополнительные метрики:**

* **RPS (Requests Per Second)** — общий трафик запросов через балансировщик
* **Throughput** — объём передаваемых данных в единицу времени
* **Health Check Failures** — частота неудачных проверок работоспособности
* **Connection Queue Length** — длина очереди соединений (при перегрузке)

**Инструменты мониторинга:**

* **Nginx:** VTS-модуль, nginx-prometheus-exporter, **[модуль metric в Angie](../../WebServers/Angie/angie_monitoring/angie_monitoring_pro.md)**
* **HAProxy:** встроенная страница статистики, haproxy-exporter
* **Универсальные:** Prometheus + Grafana для визуализации и алертинга

Пример PromQL для мониторинга балансировки:

```promql
# p95 latency по всем бэкендам
histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, backend))

# Ошибки 5xx на бэкенд
sum(rate(http_requests_total{status=~"5.."}[5m])) by (backend)

# Активные соединения на сервер
avg(active_connections) by (server)

# Процент недоступных серверов
(count(up{job="backend"} == 0) / count(up{job="backend"})) * 100
```

Подробно о методологиях мониторинга: **[Monitoring Methodologies](../Observability_and_Monitoring/monitoring_methodologies.md)**.

### Пример: L7 балансировщик на HAProxy

Конфигурация для распределения HTTPS-трафика между двумя серверами приложений с проверкой их работоспособности.

```haproxy
defaults
  mode http
  timeout client 30s
  timeout server 30s
  timeout connect 5s

frontend https_frontend
  bind :443 ssl crt /path/to/your/cert.pem
  default_backend app_backend

backend app_backend
  balance leastconn # Использовать алгоритм "Least Connections"
  option httpchk GET /health # Проверять работоспособность через GET /health
  http-check expect status 200 # Ожидать ответ HTTP 200 OK

  # Определяем серверы с разным весом и лимитом соединений
  server app1 10.0.1.10:8080 check weight 10 maxconn 500
  server app2 10.0.1.11:8080 check weight 5  maxconn 250
```

### Глобальная балансировка (GSLB)

Для распределения трафика между несколькими географически распределенными дата-центрами:

* **DNS-based:** Балансировщик на основе DNS, который возвращает IP-адреса в зависимости от местоположения клиента, задержки или веса региона.
* **Anycast:** Один и тот же IP-адрес анонсируется из нескольких точек в сети. Трафик автоматически маршрутизируется до ближайшего узла с помощью BGP.

## Дополнительная информация

---

Ключевым элементом балансировки является **проверка работоспособности (health checks)**. Балансировщик должен регулярно опрашивать серверы и автоматически исключать из ротации те, что не отвечают корректно, чтобы не направлять трафик на неработающие узлы.
