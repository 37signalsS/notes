# Кластеризация и балансировка для HA

## Определения

**Кластеризация** — объединение нескольких серверов (узлов) в единую систему, которая воспринимается пользователем как единый ресурс. Используется для обеспечения отказоустойчивости (High Availability) и повышения производительности через горизонтальное масштабирование.

**Балансировка нагрузки (Load Balancing)** — процесс распределения входящего трафика между группой бэкенд-серверов. Основные цели: предотвращение перегрузки отдельных узлов, минимизация времени ответа и обеспечение доступности сервиса при отказе части инфраструктуры.

## Основные концепции

### Модели кластеризации

| Модель | Принцип работы | Применение |
| :--- | :--- | :--- |
| **Active-Active** | Все узлы одновременно обрабатывают трафик. Обеспечивает максимальную утилизацию ресурсов. | [Stateless-сервисы](../stateful_vs_stateless.md), API-шлюзы. |
| **Active-Passive** | Один узел активен, остальные в горячем резерве (Standby). | [Stateful-сервисы](../stateful_vs_stateless.md), базы данных (Master-Slave). |
| **N+M** | Группа из `N` активных узлов подстраховывается `M` резервными. | Облачные платформы, гипервизоры. |

Для предотвращения конфликтов в Active-Passive моделях используются механизмы кворума и изоляции (Fencing). Подробнее: [Механизмы Failover и Heartbeat](./ha_failover_mechanisms.md).

### Уровни балансировки

1. **L4 (Транспортный уровень):** балансировка на основе IP и TCP/UDP портов. Высокая скорость, низкая нагрузка на CPU.
   - **Инструменты:** IPVS (LVS), HAProxy (в режиме tcp), Cloud NLB.
   - **Технология DSR (Direct Server Return):** метод, при котором балансировщик обрабатывает только входящий трафик, а бэкенд отвечает клиенту напрямую. Это устраняет бутылочное горлышко на исходящем канале балансировщика.
2. **L7 (Прикладной уровень):** балансировка на основе HTTP-заголовков, URL, Cookies. Позволяет терминировать SSL, выполнять кэширование и умную маршрутизацию.
   - **Инструменты:** Nginx, Envoy, HAProxy (в режиме http), Cloud ALB.

### Проверки состояния (Health Checks)

Для исключения сбойных узлов балансировщики используют активные проверки:
- **TCP Check:** проверка возможности установления соединения на определенный порт.
- **HTTP Check:** запрос к эндпоинту (например, `/health`) с ожиданием конкретного статус-кода (200 OK).
- **Script Check:** выполнение кастомного скрипта для глубокой проверки логики приложения.
- **Passive Health Check:** анализ реального трафика (например, подсчет ошибок 5xx) без отправки специальных запросов.

### Алгоритмы балансировки нагрузки

- **Round Robin:** поочередное распределение. Хорошо для идентичных бэкендов.
- **Least Connections:** на узел с минимальным числом активных сессий. Эффективно для «тяжелых» запросов.
- **IP Hash / Sticky Sessions:** привязка клиента к конкретному серверу по IP или Cookie.
- **Consistent Hashing (Согласованное хеширование):** алгоритм (например, Maglev), минимизирующий перераспределение ключей при добавлении/удалении узлов. Критично для кэширующих прокси и распределенных хранилищ.

## Практические сценарии

### Подходы к ресурсам (Storage)

* **Shared-Nothing (Без разделения):** каждый узел автономен. Данные реплицируются по сети. Наиболее масштабируемый подход.
* **Shared-Disk (Общий диск):** узлы используют общее внешнее хранилище (SAN/NFS). Упрощает Failover, но создает риск SPOF на уровне дисковой полки.

### Балансировка в современных средах

1. **Облачные балансировщики (Cloud LB):** управляемые сервисы (AWS ELB, GCP LB), обеспечивающие бесшовную интеграцию с автомасштабированием и защитой от DDoS.
2. **Kubernetes:**
   - **Service (kube-proxy):** L4 балансировка внутри кластера (iptables или IPVS).
   - **Ingress Controller:** L7 балансировка входящего трафика (Nginx Ingress, Traefik).
3. **Service Mesh (Envoy/Istio):** балансировка на стороне клиента (Client-side), позволяющая реализовать сложные стратегии (Canary, Blue-Green) и Outlier Detection.

### Пример: L7 балансировщик на HAProxy

Конфигурация для распределения трафика с проверкой состояния (health checks):

```haproxy
backend app_pool
  mode http
  balance leastconn
  option httpchk GET /health
  http-check expect status 200
  
  server srv1 10.0.1.10:8080 check weight 10
  server srv2 10.0.1.11:8080 check weight 5
```

### Глобальная балансировка (GSLB)

Используется для распределения трафика между дата-центрами в разных регионах:

* **DNS-based:** Возврат разных IP-адресов в зависимости от геопозиции клиента или загрузки ЦОД.
* **Anycast BGP:** Использование одного IP-адреса, анонсируемого из разных точек мира. Сеть направляет трафик к ближайшему узлу по кратчайшему пути.
