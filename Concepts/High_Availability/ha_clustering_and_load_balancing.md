# Шаблоны кластеризации и балансировка нагрузки

Высокодоступные системы опираются на два взаимосвязанных механизма: правильную кластеризацию сервисов и эффективную балансировку нагрузки. Кластеризация отвечает за отказоустойчивость и согласованность состояния, а балансировка — за распределение трафика и использование ресурсов без перегрузок и «горячих точек».

## Шаблоны кластеризации

*   Active-Active. Несколько реплик одновременно обслуживают запросы. Позволяет масштабировать пропускную способность горизонтально. Требует безсессионного дизайна или продуманной репликации/шардинга состояния.
*   Active-Passive. Одна активная нода, одна или несколько — в горячем/тёплом резерве. Проще согласовывать состояние, но нет масштабирования чтений/записей и сложнее тестировать фейловер без перерыва.
*   N+1 / N+M. Планирование резервов на уровне пула: N рабочих нод и M резервных. Баланс между затратами и отказоустойчивостью, важно правильно оценивать «что случится, если выпадут сразу k нод».
*   Shared-nothing vs Shared-disk. Локальное состояние и репликация против общего хранилища. Shared-nothing лучше масштабируется и изолирует сбои, но усложняет согласованность. Shared-disk снижает сложность репликации, однако добавляет общий SPOF и ограничения по производительности/блокировкам.
*   Лидер/кворум. В распределённых системах лидер координирует записи, избирается через кворум (Raft/Paxos-класс). Точки внимания: split-brain, чёткая конфигурация кворума и таймингов сети.

Таблица сопоставления:

| Шаблон | Где уместен | Сильные стороны | Ограничения |
| :--- | :--- | :--- | :--- |
| Active-Active | Статлесс фронтенды, API, кэши | Масштабирование, высокая доступность | Сложность состояния/сессий |
| Active-Passive | БД, монолиты, stateful сервисы | Простота, предсказуемый фейловер | Недоиспользование ресурсов |
| N+1/N+M | Пулы приложений, брокеры | Контроль затрат, гибкость | Планирование ёмкости |
| Shared-nothing | Микросервисы, шардинг | Производительность, изоляция | Сложная согласованность |

## Балансировка нагрузки

*   Уровни и места применения:
    *   L4 (TCP/UDP): высокая производительность, независимость от протокола приложений. Подходит для базовых прокси и gRPC на TCP.
    *   L7 (HTTP/HTTPS): маршрутизация по URI/заголовкам, канареечные маршруты, A/B. Терминация TLS, инспекция запросов.
    *   L3/ECMP/Anycast: распределение на уровне сети; используется для глобальной балансировки и DDoS-устойчивости.
*   Алгоритмы:
    *   round-robin/weighted round-robin — равномерное распределение с приоритизацией мощных нод;
    *   least-connections/least-load — минимизация очередей;
    *   hash/consistent hashing — устойчивость к перераспределению ключей и сессиям.
*   Здоровье и деградация:
    *   активные/пассивные health checks, outlier detection, circuit breaker;
    *   slow start и ограничение maxconn для плавного ввода нод.
*   Сессии и состояние:
    *   sticky sessions (cookie, source IP) упрощают работу stateful-компонентов, но ухудшают ребалансировку;
    *   предпочтительнее выносить состояние: кэш/сессии в Redis, файлы в объектное хранилище, транзакции — идемпотентные.
*   Устранение SPOF в балансировщиках:
    *   пара LBs с VRRP/Keepalived или литеральный кластер с общим IP/anycast;
    *   в облаках — managed Load Balancer плюс health checks и многозонность.

## Минимальный пример конфигурации HAProxy (L7 HTTPS с проверками)

```haproxy
global
  maxconn 10000

defaults
  mode http
  timeout client 30s
  timeout server 30s
  timeout connect 5s

frontend https_in
  bind :443 ssl crt /etc/ssl/certs/bundle.pem
  option http-server-close
  default_backend app_pool

backend app_pool
  balance leastconn
  option httpchk GET /health
  http-check expect status 200
  server app1 10.0.0.11:8443 check verify none weight 2 maxconn 200 slowstart 10s
  server app2 10.0.0.12:8443 check verify none weight 1 maxconn 150 slowstart 10s
```

## Глобальная балансировка

*   DNS-based (weighted/latency/geolocation): просто, но TTL и кэширование замедляют реакцию.
*   Anycast: один IP анонсируется из нескольких локаций, трафик течёт к ближайшей по BGP; важна консистентность конфигурации и телеметрии.
*   Переключение регионов с помощью health checks и политик трафика, репликация данных с учётом RPO/RTO и топологии (multi-primary или асинхронные реплики).
