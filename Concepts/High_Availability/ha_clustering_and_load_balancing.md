# Кластеризация и балансировка для HA

## Определения

**Кластеризация** — объединение нескольких серверов (узлов) в единую систему, которая воспринимается пользователем как единый ресурс. Используется для обеспечения отказоустойчивости (High Availability) и повышения производительности через распределение нагрузки.

**Балансировка нагрузки (Load Balancing)** — процесс распределения входящего сетевого трафика между группой бэкенд-серверов. Основные цели: предотвращение перегрузки отдельных узлов, минимизация времени ответа и обеспечение доступности сервиса при отказе части инфраструктуры.

Эти механизмы являются фундаментальными компонентами [высокой доступности](./ha_overview.md).

## Базовые концепции

### Модели кластеризации

| Модель | Принцип работы | Применение |
| :--- | :--- | :--- |
| **Active-Active** | Все узлы одновременно принимают и обрабатывают трафик. Требует балансировщика перед кластером. | [Stateless-сервисы](../stateful_vs_stateless.md), API-шлюзы, веб-серверы. |
| **Active-Passive** | Один узел («Primary») активен, остальные («Standby») находятся в резерве и принимают нагрузку только при сбое основного. | [Stateful-сервисы](../stateful_vs_stateless.md), базы данных, системы хранения. |
| **N+1 / N+M** | Группа из `N` активных узлов подстраховывается `M` резервными узлами. При отказе любого активного его функции берет на себя свободный резервный. | Крупные пулы виртуализации, контейнерные платформы. |

### Подходы к ресурсам

* **Shared-nothing (Без разделяемых ресурсов):** Каждый узел имеет собственные диски и память. Состояние синхронизируется по сети (репликация). Обладает лучшей масштабируемостью и отсутствием единой точки отказа на уровне хранения.
* **Shared-disk (С общим диском):** Все узлы имеют доступ к одному внешнему хранилищу (SAN, NFS). Упрощает процесс переключения при отказе (failover), так как данные не нужно реплицировать, но хранилище становится потенциальной единой точкой отказа (SPOF).

### Уровни балансировки

* **L4 (Транспортный уровень):** Балансировка на основе данных протоколов TCP/UDP (IP-адреса и порты). Не анализирует содержимое пакетов, что обеспечивает высокую скорость и низкую нагрузку на CPU.
* **L7 (Прикладной уровень):** Балансировка на основе данных протокола приложения (HTTP-заголовки, URL, Cookies). Позволяет реализовать сложную маршрутизацию, терминировать SSL/TLS и выполнять кэширование, но требует больше вычислительных ресурсов.

Подробное сравнение уровней OSI: [Модель OSI — Балансировщики нагрузки L4 и L7](../../Networking/OSI_TCP_IP_Model/osi_model.md#балансировщики-нагрузки-l4-и-l7).

### Алгоритмы балансировки нагрузки

1. **Round Robin (Поочередный):** Запросы распределяются последовательно по списку серверов. Подходит для однородных бэкендов.
2. **Weighted Round Robin:** Вариация с учетом «веса» (производительности) сервера. Более мощные узлы получают больше запросов.
3. **Least Connections (Наименьшее количество соединений):** Направляет запрос на сервер с минимальным числом активных сессий. Эффективен для запросов с разным временем обработки.
4. **Least Response Time:** Учитывает как количество соединений, так и среднее время ответа сервера. Направляет трафик на самый «быстрый» узел.
5. **IP Hash:** Выбор сервера на основе хеша IP-адреса клиента. Гарантирует, что запросы от одного клиента попадут на один и тот же сервер (Sticky Sessions).
6. **Random (Случайный):** Распределяет запросы случайным образом. Эффективен в распределенных системах, где узлы не обмениваются статусом нагрузки.

## Практические сценарии

### Мониторинг балансировки

Для обеспечения надежности HA-кластера необходимо отслеживать ключевые метрики производительности и связности:

| Метрика | Значение для HA |
| :--- | :--- |
| **Latency (p95, p99)** | Время обработки запроса. Рост перцентилей указывает на деградацию отдельных узлов. |
| **Error Rate (5xx)** | Доля ошибок бэкендов. Сигнализирует о необходимости исключения узла из ротации. |
| **Active Connections** | Распределение соединений по узлам. Помогает выявить перекосы (skew) в работе алгоритма. |
| **Backend Health Status** | Состояние проверок работоспособности (Health Checks). Показывает количество доступных реплик. |

**Пример алертинга (PromQL):**

```promql
# Уведомление при падении доли доступных бэкендов ниже 50%
(count(up{job="backend"} == 0) / count(up{job="backend"})) * 100 > 50
```

### Пример: L7 балансировщик на HAProxy

Конфигурация для распределения трафика с проверкой состояния (health checks):

```haproxy
backend app_pool
  mode http
  balance leastconn
  option httpchk GET /health
  http-check expect status 200
  
  server srv1 10.0.1.10:8080 check weight 10
  server srv2 10.0.1.11:8080 check weight 5
```

### Глобальная балансировка (GSLB)

Используется для распределения трафика между дата-центрами в разных регионах:

* **DNS-based:** Возврат разных IP-адресов в зависимости от геопозиции клиента или загрузки ЦОД.
* **Anycast BGP:** Использование одного IP-адреса, анонсируемого из разных точек мира. Сеть направляет трафик к ближайшему узлу по кратчайшему пути.
