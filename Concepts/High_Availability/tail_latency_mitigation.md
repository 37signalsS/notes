# Управление задержками (Tail Latency Mitigation)

## Определения

**Tail Latency (Хвост задержек)** — метрика, описывающая время ответа для наихудших 5% (p95) или 1% (p99) запросов в системе. В распределенных архитектурах итоговая задержка пользователя складывается из цепочки вызовов; даже небольшая вероятность медленного ответа на одном этапе значительно повышает риск деградации всего запроса.

**Связанные метрики:** p50 (медиана), p95, p99, p99.9. Детали расчёта в [перцентилях и квантилях](../Observability_and_Monitoring/monitoring_methodologies.md).

## Базовые концепции

Проблема «хвостов» в микросервисах часто приводит к **Retry storms** (штормам повторных запросов): зависший запрос провоцирует автоматические ретраи, что экспоненциально увеличивает нагрузку (Concurrency) и задержку по [Закону Литтла](./scalability_laws.md#закон-литтла-littles-law).

Стратегии борьбы делятся на две группы:

1. **Уменьшение хвоста:** архитектурное снижение вероятности возникновения медленных ответов.
2. **Маскировка хвоста:** изоляция медленных ответов, чтобы они не влияли на общую стабильность системы.

*Диагностика причин задержек на уровне ядра Linux (планировщик, блокировки, сеть) описана в [диагностике Tail Latency](../../Linux/Diagnostics/Performance/diagnosing_tail_latency.md).*

## Практические сценарии

### Сценарии уменьшения задержек

| Паттерн | Принцип работы | Ограничения |
| :--- | :--- | :--- |
| **Hedged Requests (Подстраховка)** | Если запрос не завершился за время p95, параллельно отправляется дубликат на другую реплику. Используется первый успешный ответ. | Только для **идемпотентных** операций (чтение). |
| **Tied Requests (Связанные запросы)** | Запрос отправляется на несколько нод сразу. Первая освободившаяся нода берет его в работу и сообщает остальным об отмене. | Требует поддержки протокола координации между нодами. |
| **Request Coalescing (Объединение)** | При одновременных запросах одного «горячего» ресурса сервер делает один запрос к БД/кэшу, раздавая результат всем ожидающим. | Повышает сложность логики обработки запросов. |
| **Queue-based Leveling (Очереди)** | Сглаживание пиков нагрузки через буфер (очередь). Воркеры обрабатывают запросы с фиксированной скоростью. | Увеличивает среднюю задержку (Latency) в пользу стабильности. |

### Сценарии маскировки задержек

#### 1. Circuit Breaker (Предохранитель)

Автоматическое размыкание цепи при превышении порога ошибок или таймаутов от зависимости. Система перестает слать запросы к «больному» сервису, возвращая фолбэк (кэшированные данные или ошибку).

- **Реализация в Service Mesh:** [Circuit Breaker в Istio](../../Service_Mesh/traffic_management.md#сценарий-7-circuit-breaking-istio-destinationrule).

#### 2. Backpressure (Обратное давление)

Система ограничивает входной поток, когда перестает справляться. При перегрузке сервер возвращает `429 Too Many Requests` или `503 Service Unavailable`, защищая уже обрабатываемые запросы от деградации.

#### 3. Deadline Propagation (Передача дедлайна)

Установление лимита времени на выполнение всей цепочки вызовов. Балансировщик передает дедлайн в заголовках; любой сервис в цепочке может прервать обработку, если лимит исчерпан, экономя ресурсы.

#### 4. Паттерн Good Enough (Достаточно хорошо)

При задержке критичного, но тяжелого сервиса (например, персональных рекомендаций), система отдает упрощенный ответ (статический список популярных товаров). Это позволяет сохранить работоспособность UI ценой временного снижения качества данных.

## Дополнительная информация

Эффективная борьба с хвостами задержек невозможна без:

- **Распределенной трассировки:** для поиска узких мест в цепочках вызовов. См. [Jaeger и трассировка](../Observability_and_Monitoring/traces_deep_dive.md).
- **Корректных таймаутов:** установка таймаутов на основе реального p99, а не догадок.
- **Идемпотентности API:** для безопасного применения ретраев и Hedged Requests.
