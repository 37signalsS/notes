# Граничные вычисления (Edge Computing)

## Определения

**Граничные вычисления (Edge Computing)** — это распределенная вычислительная модель, в которой обработка данных и выполнение логики приложения происходят максимально близко к источнику данных или конечному пользователю. 

В отличие от традиционной облачной модели, где вычисления сосредоточены в централизованных дата-центрах, Edge Computing переносит их на «границу» сети: на оборудование пользователя, **IoT (Internet of Things)**-шлюзы или инфраструктуру **CDN (Content Delivery Network)**.

**Цели использования:**
*   Минимизация задержек (latency) для приложений реального времени.
*   Снижение нагрузки на магистральные каналы связи.
*   Обеспечение автономности работы при отсутствии связи с центром.
*   Соблюдение требований по локализации и защите данных.

## Базовые концепции

### Ключевые свойства

*   **Низкая задержка:** ответ формируется за единицы миллисекунд, так как запрос не проходит путь до удаленного региона облака.
*   **Эфемерность:** среды выполнения (воркеры) обычно легковесны и имеют короткий жизненный цикл.
*   **Ограничение ресурсов:** узлы на границе имеют строгие лимиты по CPU и оперативной памяти по сравнению с облачными серверами.

| Характеристика | Облако (Центр) | Edge (Граница) |
| :--- | :--- | :--- |
| **Задержка** | 50–200 мс | **1–10 мс** |
| **Модель вычислений** | VM, контейнеры, серверы | **Функции, WASM-модули** |
| **Работа с состоянием**| СУБД, кэши, очереди | **Stateless, KV-хранилища** |

### Туманные вычисления (Fog Computing)

Часто Edge Computing путают с **Fog Computing**. 
*   **Edge** фокусируется на устройствах и точках присутствия (PoP), непосредственно подключенных к пользователю.
*   **Fog** — это промежуточный уровень иерархии (локальные сети, микро-ЦОД), который объединяет ресурсы нескольких Edge-узлов перед отправкой данных в облако.

### Данные и согласованность

*   **Паттерн «Read-at-Edge, Write-at-Center»:** запросы на чтение обслуживаются локально, а запись проксируется в центральный регион для обеспечения консистентности.
*   **Кэширование:** критически важный компонент. Используется не только для контента, но и для результатов вычислений. Подробнее: [Обзор кэширования](Caching/caching_overview.md).
*   **Итоговая согласованность (Eventual Consistency):** из-за распределенной природы достижение строгой синхронизации между всеми точками присутствия на границе практически невозможно без огромных задержек.

## Практические сценарии

### Типичные задачи

*   **Персонализация «на лету»:** адаптация контента (язык, валюта) на основе геоданных без обращения к бэкенду.
*   **Трансформация медиа:** сжатие изображений и изменение формата видео под устройство пользователя на границе сети.
*   **Безопасность на периметре:** блокировка DDoS-атак, фильтрация ботов и валидация **JWT (JSON Web Token)**.
*   **Индустриальный IoT:** предварительная фильтрация и агрегация данных с датчиков на заводе, чтобы отправлять в облако только аномалии.

### Пример Edge-обработчика (JavaScript)

Современные платформы (Cloudflare Workers, Fastly Compute) позволяют запускать код на границе. Пример простой маршрутизации:

```javascript
async function handleRequest(request) {
  const country = request.cf?.country || 'US';
  const cache = caches.default;
  
  // Поиск в локальном кэше точки присутствия
  let response = await cache.match(request);
  if (response) return response;

  // Динамический выбор бэкенда
  const origin = country === 'RU' ? 'api-ru.example.com' : 'api-us.example.com';
  response = await fetch(`https://${origin}${new URL(request.url).pathname}`, request);
  
  return response;
}
```

## Дополнительная информация

### Безопасность на границе

*   **Zero Trust:** каждый Edge-узел должен рассматриваться как потенциально скомпрометированный. Необходима взаимная проверка подлинности (mTLS).
*   **Шифрование:** данные должны быть зашифрованы как при передаче (TLS), так и при хранении на граничных узлах.

### Наблюдаемость и производительность

*   **WASM (WebAssembly):** становится стандартом для Edge из-за мгновенного старта и изоляции. В отличие от Docker, WASM-модули запускаются за микросекунды, что устраняет проблему «холодного старта».
*   **Сквозная трассировка:** важно передавать идентификаторы трассировки (Trace ID) от границы до глубоких слоев бэкенда для анализа задержек.
