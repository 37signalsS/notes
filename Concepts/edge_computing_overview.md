# Edge Computing: Обзор

## Определения

**Edge Computing (Граничные вычисления)** — это распределенная вычислительная модель, в которой обработка данных и выполнение части логики приложения происходят как можно ближе к источнику этих данных или конечному пользователю. В отличие от традиционной облачной модели, где все вычисления сосредоточены в централизованных дата-центрах, edge computing переносит их на "границу" сети (например, на инфраструктуру CDN, IoT-шлюзы или оборудование пользователя).

Основная цель — уменьшить задержку (latency), снизить нагрузку на магистральные каналы связи и центральные серверы, а также обеспечить соблюдение требований по локализации данных.

## Основные концепции

### Ключевые свойства

* **Близость к пользователю:** Задержка ответа измеряется миллисекундами, а не десятками или сотнями, как при обращении к удаленному облачному региону.
* **Эфемерность вычислений:** Среды выполнения на границе сети обычно легковесны, короткоживущие и имеют строгие ограничения по CPU и памяти.
* **Ограниченное состояние (Stateless):** Предпочтение отдается обработчикам без состояния и активному использованию кэша. Хранение "тяжелого" состояния на границе избегается.

| Характеристика | Облако (Центральный регион) | Edge (Граница сети) |
| :--- | :--- | :--- |
| **Задержка** | Средняя / Высокая | **Низкая** |
| **Модель вычислений** | Долгоживущие сервисы, VM, контейнеры | **Легковесные функции/воркеры** |
| **Работа с состоянием**| Полноценные БД, кластеры, очереди | Кэши, KV-хранилища, stateless |

### Данные и согласованность

* **Модель "Читай на границе, пиши в центре":** Запросы на чтение обслуживаются на границе, а запросы на запись проксируются в центральный регион для обеспечения консистентности.
* **Кэширование:** Активно используется для хранения данных на границе. Важно правильно управлять ключами кэша и политиками инвалидации (не только по TTL, но и по событиям). Подробнее о паттернах кэширования см. [Обзор кэширования](Caching/caching_overview.md).
* **Eventual Consistency:** Для геораспределенного состояния применяются модели итоговой согласованности, так как достижение строгой консистентности между множеством удаленных точек является сложной и медленной задачей.

## Практические сценарии

### Типичные задачи для Edge

* **Персонализация контента:** Адаптация страницы (язык, валюта, A/B-тесты) на основе гео-данных пользователя еще до обращения к основному бэкенду.
* **Умная маршрутизация:** Выбор ближайшего и наиболее здорового бэкенда для обработки запроса.
* **Трансформация запросов/ответов:** Оптимизация изображений, сжатие данных, модификация HTTP-заголовков.
* **Безопасность на периметре:** Раннее обнаружение ботов, ограничение частоты запросов (rate limiting), валидация JWT-токенов.
* **API-агрегация:** Объединение нескольких запросов к разным микросервисам в один на границе сети, чтобы уменьшить нагрузку на бэкенд.

### Пример Edge-обработчика (JavaScript, Cloudflare Workers-style)

Этот воркер перехватывает запрос, пытается найти ответ в кэше и, в случае промаха, направляет запрос к ближайшему бэкенду.

```javascript
async function handleRequest(request) {
  // 1. Получаем гео-данные пользователя из контекста
  const country = request.cf.country;
  const backend = routeToNearestBackend(country);

  // 2. Создаем ключ кэша и ищем ответ
  const cacheKey = new Request(request.url, request);
  const cache = caches.default;
  let response = await cache.match(cacheKey);

  if (response) {
    // 3. Если нашли в кэше — возвращаем
    console.log(`Cache HIT for: ${request.url}`);
    return response;
  }
  console.log(`Cache MISS for: ${request.url}`);

  // 4. Если в кэше нет — идем на ближайший бэкенд
  response = await fetch(`https://${backend}${new URL(request.url).pathname}`, request);
  
  // 5. Клонируем ответ, чтобы положить его в кэш и вернуть клиенту
  response = new Response(response.body, response);
  response.headers.append("Cache-Control", "s-maxage=60"); // Кэшировать на 60с

  // Используем `waitUntil` для неблокирующей записи в кэш
  event.waitUntil(cache.put(cacheKey, response.clone()));
  
  return response;
}

addEventListener("fetch", event => {
  event.respondWith(handleRequest(event.request));
});
```

## Дополнительная информация

### Наблюдаемость и развертывание

* **Версионирование:** Код на границе требует тщательного версионирования и поэтапного развертывания (canary deployments) по разным точкам присутствия (PoPs).
* **Метрики:** Важно собирать метрики именно с границы: p95/p99 задержки, cache hit ratio, количество ошибок.
* **Трассировка:** Сквозная трассировка запросов (distributed tracing) должна инициироваться на границе для полного понимания пути запроса.

### Производительность и ограничения

* **Холодный старт:** Время первого запуска функции может быть критичным. Для его уменьшения оптимизируют размер кода, используют pre-warming и технологии вроде WebAssembly (WASM).
* **Ограничения среды:** Код на границе работает в строго изолированном окружении с жесткими лимитами на время выполнения, потребление памяти и доступные API.
