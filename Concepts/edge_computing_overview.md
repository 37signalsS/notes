# Edge computing: перенесение вычислений ближе к пользователю

Edge computing — это модель, в которой часть логики приложения исполняется на узлах, географически близких к конечному пользователю (точках присутствия), чтобы уменьшить задержку, снизить нагрузку на централизованные регионы и соблюдать требования к локализации данных. В отличие от традиционного подхода с единственным регионом, здесь вычисления распределяются по периферии сети, часто на инфраструктуре CDN.

## Ключевые свойства и сравнение

- **Близость к пользователю**: миллисекунды против десятков/сотен миллисекунд до центрального региона.
- **Эфемерность**: короткоживущие изолированные среды выполнения, строгие лимиты CPU/памяти.
- **Ограниченное состояние**: предпочтение stateless-обработчиков и кэшей поверх «тяжёлого» состояния.

| Характеристика      | Облако (регион)            | Edge (PoP)                                |
| ------------------- | -------------------------- | ----------------------------------------- |
| Задержка            | Средняя/высокая            | Низкая                                    |
| Модель вычислений   | Полноценные сервисы        | Лёгкие функции/воркеры                    |
| Состояние           | БД, кластеры, очереди      | Кэши, KV/сессии с ограничениями           |
| Сценарии            | Тяжёлые бэкенды, аналитика | Персонализация, маршрутизация, трансформации |

## Типичные сценарии

- **Персонализация на первом байте ответа**: локализация, валюты, фичи по гео/сегменту.
- **Умная маршрутизация**: выбор ближайшего бэкенда, гео-шардинг, канареечные маршруты.
- **Трансформации запросов/ответов**: нормализация заголовков, re-write URL, сжатие, оптимизация изображений.
- **API-агрегация и кэширование**: защита бэкенда от пиков, request coalescing, TTL/Surrogate-Key инвалидация.
- **Безопасность на периметре**: ранний бот-фильтр, rate limiting, проверка токенов и mTLS.

## Данные и согласованность

- Предпочтительно «прочитать на периферии, записать в регионе»; для записи используйте идемпотентные методы и ретраи.
- **Кэши**: выбирайте ключи с учётом Vary-заголовков; инвалидация по событиям быстрее, чем только по TTL.
- Для геораспределённого состояния применяются подходы eventual consistency и CRDT там, где это приемлемо; избегайте жёстких кросс-POP транзакций.
- **Сессии**: липкие сессии к ближайшему бэкенду или полностью stateless с JWT.

## Наблюдаемость и доставка

- Версионирование воркеров и поэтапный rollout по группам PoP.
- **Метрики на периметре**: p50/p95 латентности, доля кэш-хитов, ошибки происхождения и квоты блокировок.
- **Трассировка сквозных запросов**: проброс корреляционных заголовков и sampling на границе.

## Производительность и ограничения

- **Холодный старт**: уменьшайте размер бандла, используйте prefetch/прогрев и WASM при CPU-нагрузке.
- **Потоковая обработка**: стриминг тела запроса/ответа, backpressure к медленным источникам.
- **Таймауты и бюджет задержки**: жёсткие лимиты на I/O, короткие таймауты к бэкендам, деградации и кэшированные фолбэки.
- **Секьюрность**: изолированные рантаймы, контроль исходящего трафика, секреты через KMS/конфигурацию, соблюдение резидентности данных.

## Минимальный пример edge-обработчика

```javascript
function handle(request, context) {
  // Геоданные и выбор ближайшего кластера
  const country = context.geo.country || 'US';
  const pop = routeTable.closest(country);

  // Нормализация ключа кэша с учетом персонализации
  const vary = ['Authorization', 'Accept-Language'];
  const cacheKey = edgeCache.key(request.url, vary);

  let response = edgeCache.get(cacheKey);
  if (response) return response;

  // Проксирование к ближайшему бэкенду с небольшим TTL
  const upstreamUrl = `https://${pop}.api.internal` + new URL(request.url).pathname;
  const upstreamReq = request.clone({ url: upstreamUrl, timeout: 800 });

  response = fetch(upstreamReq);
  edgeCache.put(cacheKey, response, { ttl: 60 });

  // Маркируем ответ для наблюдаемости
  response.headers.set('X-Edge-PoP', pop);
  return response;
}
```
