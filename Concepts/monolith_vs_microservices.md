# Монолитная и микросервисная архитектуры

## Определения

**Монолитная архитектура** — архитектурный паттерн, при котором все компоненты приложения (бизнес-логика, пользовательский интерфейс, доступ к данным) разрабатываются, развертываются и масштабируются как единое целое в рамках одного процесса.

**Микросервисная архитектура** — подход, при котором приложение строится как набор небольших, автономных сервисов, взаимодействующих по сети. Каждый сервис решает узкую бизнес-задачу, имеет собственную базу данных и независимый цикл развертывания.

## Базовые концепции

### Типы монолитной архитектуры

1.  **Однопроцессный монолит (Single-Process Monolith):** классическая форма, где все модули работают в одном адресном пространстве. Сбой в одном модуле (например, утечка памяти) может привести к падению всего приложения.
2.  **Модульный монолит (Modular Monolith):** архитектура с четким разделением на логические модули с формализованными интерфейсами внутри одного процесса. Это упрощает поддержку и будущую декомпозицию.
3.  **Распределенный монолит (Distributed Monolith):** анти-паттерн, при котором система разделена на сервисы, но они настолько сильно связаны, что не могут работать или развертываться независимо. Это сочетает недостатки распределенных систем и монолитов.

### Принципы микросервисов

*   **Независимое развертывание:** возможность обновить один сервис, не затрагивая остальные.
*   **Инкапсуляция данных (Database-per-Service):** каждый сервис владеет своими данными. Прямой доступ к БД чужого сервиса запрещен.
*   **Моделирование вокруг бизнес-доменов:** использование **Domain-Driven Design (DDD)** для определения границ сервисов.
*   **Децентрализованное управление:** команды вольны выбирать технологический стек, оптимальный для их конкретной задачи.
*   **Закон Конвея:** структура программного обеспечения отражает структуру коммуникаций в организации. Для эффективных микросервисов требуются автономные кросс-функциональные команды.

### Сравнение характеристик

| Характеристика | Монолит | Микросервисы |
| :--- | :--- | :--- |
| **Связанность** | Сильная (Tight Coupling) | Слабая (Loose Coupling) |
| **Масштабирование** | Всего приложения целиком | Индивидуальное для каждого сервиса |
| **Отказоустойчивость**| Низкая (единая точка отказа) | Высокая (изоляция сбоев) |
| **Операционная сложность** | Низкая (на старте) | Высокая (требует автоматизации) |
| **Консистентность** | Строгая (ACID транзакции) | Итоговая (Eventual Consistency) |

## Практические сценарии

### Выбор архитектуры

*   **Выбирайте монолит**, если: вы запускаете стартап (MVP), у вас небольшая команда, бизнес-логика проста или нет экспертизы в DevOps и распределенных системах.
*   **Выбирайте микросервисы**, если: над проектом работают десятки команд, требуются независимые темпы релизов для разных фич, необходима экстремальная масштабируемость отдельных компонентов.

### Паттерны миграции и управления

1.  **Паттерн «Фиговое дерево» (Strangler Fig Pattern):** постепенная замена функциональности монолита новыми микросервисами. Трафик перехватывается на уровне прокси (API Gateway) и направляется либо в старый монолит, либо в новый сервис.
2.  **Паттерн «Сага» (Saga Pattern):** управление распределенными транзакциями через цепочку локальных транзакций.
    *   *Хореография:* сервисы обмениваются событиями без центрального координатора.
    *   *Оркестрация:* центральный сервис управляет последовательностью шагов саги.
3.  **Паттерн Sidecar:** вынос вспомогательной логики (логирование, мониторинг, безопасность) в отдельный контейнер, работающий рядом с основным приложением (основа для **Service Mesh**).

## Дополнительная информация

### Вызовы и инфраструктура

Микросервисы требуют зрелого инфраструктурного фундамента:
*   **Обнаружение сервисов (Service Discovery):** механизмы для динамического поиска адресов сервисов (Consul, etcd, K8s DNS).
*   **Наблюдаемость (Observability):** централизованные логи и распределенная трассировка (Jaeger, Tempo).
*   **API Gateway:** единая точка входа для управления трафиком и безопасностью.
