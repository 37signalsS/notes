## Монолитная архитектура

**Монолит** — это архитектурный паттерн, при котором все компоненты приложения развертываются как единое целое. Все функции, модули и ресурсы тесно связаны и работают в рамках одного процесса.

### Преимущества

*   **Простота разработки и развертывания:** На начальных этапах проект проще разрабатывать, тестировать и развертывать, так как все компоненты находятся в одной кодовой базе.
*   **Надежность транзакций:** Операции, затрагивающие несколько модулей (например, в базе данных), выполняются в рамках одной транзакции, что гарантирует консистентность данных.
*   **Производительность:** Внутрипроцессное взаимодействие между компонентами происходит быстрее, чем сетевые вызовы в микросервисах.

### Недостатки

*   **Сложность масштабирования:**
    *   **Вертикальное масштабирование** (увеличение CPU/RAM) возможно, но имеет свои пределы.
    *   **Горизонтальное масштабирование** (запуск нескольких экземпляров монолита) затруднено. Если хотя бы один компонент системы не поддерживает горизонтальное масштабирование (например, из-за состояния), то все приложение масштабируется с трудом.
*   **Низкая отказоустойчивость:** Сбой в одном компоненте может привести к отказу всего приложения.
*   **Технологическая связанность:** Все приложение привязано к одному технологическому стеку. Обновление фреймворков или языков программирования становится сложной и рискованной задачей.
*   **Замедление разработки:** По мере роста кодовой базы сложность увеличивается, а время сборки и запуска приложения растет, что замедляет циклы разработки.

## Микросервисная архитектура

**Микросервисы** — это архитектурный подход, при котором приложение строится как набор небольших, независимо развертываемых сервисов. Каждый сервис решает узкую бизнес-задачу и общается с другими по сети (обычно через HTTP/REST API или gRPC).

### Преимущества

*   **Независимое масштабирование:** Можно масштабировать только те сервисы, которые испытывают высокую нагрузку, что позволяет эффективно использовать ресурсы.
*   **Повышенная отказоустойчивость:** Сбой одного сервиса не приводит к отказу всей системы. Остальные сервисы продолжают работать.
*   **Технологическая гибкость:** Разные сервисы могут быть написаны на разных языках программирования и использовать разные технологии, наиболее подходящие для их задач.
*   **Упрощение разработки:** Команды могут работать над отдельными сервисами независимо, что ускоряет разработку и упрощает понимание кодовой базы.

### Недостатки

*   **Повышенная сложность:**
    *   **Операционная сложность:** Вместо одного приложения необходимо управлять десятками или сотнями сервисов. Требуются развитые инструменты для развертывания, мониторинга и оркестрации.
    *   **Сетевое взаимодействие:** Задержки и сбои в сети становятся частью архитектуры, которую необходимо учитывать.
*   **Проблемы с транзакциями:** Обеспечение консистентности данных в распределенных транзакциях (например, с использованием паттерна Saga) — нетривиальная задача.
*   **Сложности масштабирования Stateful-сервисов:**
    *   **Stateless-сервисы** (не хранящие состояние, например, конвертер данных) легко масштабируются горизонтально.
    *   **Stateful-сервисы** (хранящие состояние, например, в оперативной памяти или локальной базе данных) масштабировать сложнее. При запуске нескольких экземпляров могут возникать коллизии и проблемы с консистентностью данных.
*   **Сложность мониторинга:** Требуются продвинутые инструменты **[наблюдаемости (observability)](Observability_and_Monitoring/observability_overview.md)**, включая распределенную трассировку, для отслеживания запросов и выявления узких мест.

## Сравнение подходов

| Аспект | Монолитная архитектура | Микросервисная архитектура |
| :--- | :--- | :--- |
| **Масштабируемость** | Ограниченная, в основном вертикальная. | Высокая, независимое горизонтальное масштабирование. |
| **Отказоустойчивость** | Низкая (единая точка отказа). | Высокая (изоляция сбоев). |
| **Развертывание** | Простое (один артефакт). | Сложное (множество сервисов, требуется оркестрация). |
| **Технологический стек** | Единый для всего приложения. | Полиглотный (разные технологии для разных сервисов). |
| **Консистентность данных** | Простая (ACID-транзакции). | Сложная (распределенные транзакции, паттерн Saga). |
| **Операционная сложность** | Низкая. | Высокая (требует автоматизации и DevOps-практик). |
