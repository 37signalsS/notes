# Монолитная и микросервисная архитектуры

## Определения

### Монолитная архитектура

**Монолит** — это традиционный архитектурный паттерн, при котором все компоненты приложения (бизнес-логика, UI, доступ к данным) разрабатываются, развертываются и масштабируются как единое целое. Все функции, модули и ресурсы тесно связаны (сильно сцеплены) и работают в рамках одного процесса.

### Микросервисная архитектура

**Микросервисы** — это архитектурный подход, при котором приложение строится как набор небольших, независимо развертываемых сервисов. Каждый сервис решает узкую бизнес-задачу, имеет собственную кодовую базу, собственные данные и общается с другими по сети (через API или брокеры сообщений). Сервисы слабо связаны, но обладают высокой функциональной связностью.

## Базовые концепции

### Типы монолитной архитектуры

Монолитная архитектура может быть реализована в нескольких вариантах, отражающих разную степень зрелости и подготовки к возможной декомпозиции.

1. **Однопроцессный монолит (Single-Process Monolith):**
    * **Описание:** Классическая форма, где все компоненты упакованы в единый, неразрывный процесс. Границы между модулями и функциями размыты, что часто приводит к "спагетти-коду".
    * **База данных:** Единая для всего приложения.
    * **Плюсы:** Максимальная простота в разработке и развертывании на начальных этапах.
    * **Минусы:** Низкая отказоустойчивость, сложность в поддержке и внедрении новых технологий с ростом проекта.

2. **Модульный монолит (Modular Monolith):**
    * **Описание:** Более продвинутая форма, где приложение разделено на логические модули (например, "Каталог", "Оплата", "Доставка"). Каждый модуль инкапсулирует свою часть логики, но все они по-прежнему развертываются как единый процесс.
    * **База данных:** Все еще общая.
    * **Плюсы:** Упрощается параллельная разработка, код становится более структурированным.
    * **Минусы:** Общая база данных остается "узким местом" и источником сильной связанности. Изменения в схеме данных могут затронуть несколько модулей.

3. **Модульный монолит с разделенной базой данных:**
    * **Описание:** Логическое развитие модульного монолита, где каждый модуль получает собственную, изолированную базу данных (или схему). Это последний шаг перед переходом к микросервисам.
    * **База данных:** Разделена по модулям.
    * **Плюсы:** Минимизирует зависимости между модулями, упрощает будущий переход на микросервисы (база данных уже готова к выделению). Позволяет использовать разные технологии баз данных для разных модулей (например, PostgreSQL для транзакций, Redis для кэша).
    * **Минусы:** Усложняется обеспечение консистентности данных между модулями (требуется внутренняя интеграция).

### Анти-паттерн: Распределенный монолит

**Распределенный монолит** — это система, которая выглядит как микросервисная (состоит из нескольких сервисов), но ведет себя как монолит. Сервисы формально разделены, но из-за сильной зависимости (tight coupling) их необходимо развертывать и изменять одновременно.

**Признаки:**

* **Синхронные вызовы:** Сервисы постоянно обращаются друг к другу по сети в синхронном режиме, создавая каскадные сбои.
* **Общая база данных:** Несколько сервисов напрямую работают с одной и той же таблицей или схемой.
* **Связанность бизнес-логикой:** Изменение в одном сервисе требует немедленных изменений в других для поддержания работоспособности системы.

Это худшее из двух миров: сложность распределенной системы (сетевые задержки, проблемы с консистентностью) сочетается с проблемами монолита (жесткая связанность, сложность развертывания).

### Ключевые концепции микросервисов

* **Независимое развертывание:** Каждый микросервис может быть обновлен и развернут без остановки и изменения других частей системы. Это ключевое преимущество, позволяющее ускорить time-to-market.
* **Моделирование вокруг бизнес-возможностей:** Сервисы должны строиться не вокруг технических слоев (UI, backend, DB), а вокруг конкретных бизнес-доменов (например, "Управление заказами", "Профиль пользователя").
* **Инкапсуляция данных:** Каждый сервис владеет своими данными и предоставляет к ним доступ только через публичный API. Прямой доступ к базе данных другого сервиса категорически запрещен. Это гарантирует слабую связанность.
* **Размер не главное:** Приставка "микро" относится не столько к количеству строк кода, сколько к ограниченной зоне ответственности. Сервис должен быть достаточно маленьким, чтобы им могла управлять одна команда, но достаточно большим, чтобы реализовывать целостную бизнес-функцию.
* **Закон Конвея:** "Архитектура системы повторяет коммуникационную структуру организации". Чтобы успешно строить микросервисы, команды должны быть организованы соответствующим образом: небольшие, автономные, кросс-функциональные группы, отвечающие за свои сервисы от разработки до эксплуатации.

### Ключевые отличия

| Аспект | Монолитная архитектура | Микросервисная архитектура |
| :--- | :--- | :--- |
| **Масштабируемость** | Ограниченная, в основном вертикальная. Горизонтальное масштабирование всего приложения целиком. | Высокая, независимое горизонтальное масштабирование отдельных сервисов. |
| **Отказоустойчивость**| Низкая (единая точка отказа). Сбой в одном компоненте может нарушить работу всего приложения. | Высокая (изоляция сбоев). Сбой одного сервиса не приводит к отказу всей системы. |
| **Развертывание** | Простое (один артефакт, один процесс). | Сложное (множество сервисов, требуется оркестрация и автоматизация). |
| **Технологический стек**| Единый для всего приложения. | Полиглотный (разные технологии, оптимально подобранные для каждого сервиса). |
| **Консистентность данных** | Простая (ACID-транзакции в рамках одной базы данных). | Сложная (требует паттернов для распределенных транзакций, например, Saga). |
| **Организация команд** | Одна большая команда работает над всей кодовой базой. | Небольшие, автономные команды отвечают за полный жизненный цикл своих сервисов (Закон Конвея). |
| **Операционная сложность** | Низкая на старте, но экспоненциально растет с развитием проекта. | Высокая с самого начала из-за распределенной природы системы. |

## Практические сценарии: Что и когда выбирать?

### Когда выбирать монолит?

* **MVP (Minimum Viable Product) и стартапы:** Когда главная цель — быстро проверить гипотезу и выйти на рынок с минимальными затратами.
* **Небольшие проекты:** Для приложений с простой и четко определенной бизнес-логикой.
* **Маленькая команда:** Когда одна команда может эффективно управлять всей кодовой базой.
* **Отсутствие экспертизы в DevOps:** Микросервисы требуют зрелых DevOps-практик, которых может не быть на старте.

### Когда выбирать микросервисы?

* **Крупных и сложных систем:** Когда приложение состоит из множества доменов, которые сложно поддерживать в рамках одной кодовой базы.
* **Больших команд разработчиков:** Позволяет распараллелить разработку и дать командам автономию.
* **Высокие требования к масштабируемости и отказоустойчивости:** Когда разные части системы требуют разного уровня масштабирования, а сбой одной части не должен влиять на другие.
* **Потребность в технологической гибкости:** Когда для разных задач необходимо использовать разные языки программирования или технологии.

### Гибридный подход и миграция

Необязательно делать выбор "все или ничего". Многие успешные проекты начинались как монолиты, и по мере роста и выявления узких мест, наиболее нагруженные или изменяемые части системы постепенно выносились в отдельные микросервисы.

## Дополнительная информация: Вызовы микросервисной архитектуры

Переход к микросервисам решает одни проблемы, но создает другие, связанные с распределенной природой системы.

* **Распределенные транзакции:** Гарантировать консистентность данных между несколькими сервисами без традиционных ACID-транзакций сложно. Для этого используются паттерны вроде **Saga**, где транзакция разбивается на серию локальных транзакций с возможностью отката через компенсирующие операции.

* **Наблюдаемость (Observability):** Отладка и мониторинг становятся значительно сложнее. Вместо анализа одного лог-файла требуется комплексный подход, включающий:
  * **Распределенную трассировку:** Для отслеживания пути запроса через несколько сервисов.
  * **Централизованное логирование:** Сбор логов со всех сервисов в единую систему.
  * **Агрегацию метрик:** Сбор и визуализация метрик со всей системы.
    Подробнее см. в [**обзоре Observability**](Observability_and_Monitoring/observability_definitions.md).

* **Обнаружение сервисов (Service Discovery):** В динамической среде сервисы постоянно появляются и исчезают. Необходим механизм (например, Consul, etcd), который позволяет сервисам находить друг друга.

* **API Gateway:** Часто используется в микросервисных архитектурах для маршрутизации, агрегации запросов и безопасности. Подробнее см. [API Gateway](./api_gateway_overview.md).

* **Очередь сообщений (Message Queue):** Механизм связи, используемый в распределенных системах для обеспечения асинхронной связи между различными компонентами. Обычно используются в микросервисных архитектурах для повышения отказоустойчивости, масштабируемости и уменьшения связанности между сервисами.

* **Кэширование:** Критически важный паттерн для распределенных систем. Подробнее см. [Обзор кэширования](./Caching/caching_overview.md).

* **Stateful vs. Stateless сервисы:** Горизонтально масштабировать **Stateless-сервисы** (не хранящие состояние) просто. Масштабирование **Stateful-сервисов** (хранящих состояние, например, в памяти) требует сложных решений для синхронизации и обеспечения консистентности данных. Подробнее см. **[Stateful vs Stateless](./stateful_vs_stateless.md)**.
