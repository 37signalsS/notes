# Монолитная и микросервисная архитектуры

## Определения

**Монолитная архитектура** — архитектурный паттерн, при котором все компоненты приложения (бизнес-логика, пользовательский интерфейс, доступ к данным) разрабатываются, развертываются и масштабируются как единое целое в рамках одного процесса.

**Микросервисная архитектура** — подход, при котором приложение строится как набор небольших, автономных сервисов, взаимодействующих по сети. Каждый сервис решает узкую бизнес-задачу, владеет собственной базой данных и имеет независимый жизненный цикл.

## Базовые концепции

### Эволюция монолитов
1.  **Однопроцессный монолит (Single-Process Monolith):** Все модули работают в одном адресном пространстве. Сбой в одном компоненте (например, утечка памяти в PDF-генераторе) может привести к отказу всего приложения.
2.  **Модульный монолит (Modular Monolith):** Современный стандарт (2025-2026). Архитектура с жесткой изоляцией логических модулей внутри одного процесса. Модули общаются через формализованные интерфейсы, а не напрямую через данные. Позволяет быстро перейти к микросервисам при необходимости.
3.  **Распределенный монолит (Distributed Monolith):** Анти-паттерн. Система разделена на сервисы, которые сильно связаны: требуют одновременного деплоя, имеют общую БД или используют синхронные вызовы, приводящие к каскадным сбоям.

### Принципы микросервисов
*   **Инкапсуляция данных (Database-per-Service):** Прямой доступ к таблицам чужого сервиса запрещен. Обмен данными только через API.
*   **Моделирование по DDD:** Границы сервисов определяются границами **Bounded Context** (ограниченных контекстов) из Domain-Driven Design.
*   **Умные эндпоинты, глупые каналы:** Логика маршрутизации и обработки находится в сервисах, а не в транспортной шине (в отличие от ESB в SOA).
*   **Закон Конвея:** Архитектура системы должна соответствовать структуре коммуникаций в организации. Одной команде — один или несколько сервисов.

### Сравнение характеристик

| Характеристика | Монолит | Микросервисы |
| :--- | :--- | :--- |
| **Связанность** | Сильная (Tight Coupling) | Слабая (Loose Coupling) |
| **Масштабирование** | Всего приложения (Вертикальное/Горизонтальное) | Индивидуальное для каждого сервиса |
| **Отказоустойчивость**| Низкая (единая точка отказа) | Высокая (Bulkhead паттерн, изоляция сбоев) |
| **Сложность разработки**| Низкая (единый контекст, IDE) | Высокая (распределенная трассировка, сетевые задержки) |
| **Консистентность** | Строгая (ACID транзакции) | Итоговая (Eventual Consistency, паттерн Saga) |
| **Технологический стек**| Единый (Vendor lock-in) | Полиглотность (выбор под задачу) |

## Паттерны коммуникации и управления

### Синхронная vs Асинхронная связь
*   **Синхронная (REST, gRPC):** Проста в реализации, но создает цепочки зависимостей. Требует паттернов **Circuit Breaker** и **Retry** для предотвращения каскадных сбоев.
*   **Асинхронная (Kafka, RabbitMQ):** Максимальная независимость. Сервисы обмениваются событиями. Обеспечивает лучшую масштабируемость и устойчивость.

### Продвинутые архитектуры 2026
*   **Cell-based Architecture (Ячеистая архитектура):** Группировка связанных микросервисов в «ячейки» (Cells) с единым входом. Позволяет масштабировать систему целыми блоками и ограничивать радиус поражения при авариях.
*   **Macroservices:** Поиск баланса (Right-sizing). Отказ от слишком мелких сервисов («наносервисов») в пользу более крупных, но функционально законченных блоков для снижения операционной нагрузки.
*   **Serverless Microservices:** Использование FaaS (AWS Lambda, Cloud Functions) для реализации логики сервисов, что исключает управление серверами и обеспечивает оплату только за время выполнения.

## Практические сценарии

### Выбор под задачу
*   **Монолит (Modular):** Идеален для MVP, систем с неопределенными бизнес-границами и команд до 10-15 человек. 
    > **Совет:** Начинайте как монолит. Разделяйте его только тогда, когда для этого есть веская причина. Например, размер команды или потребность в независимом масштабировании: в монолите нельзя масштабировать только «Ленту», приходится дублировать всё приложение. В микросервисах можно запустить 10 серверов для чтения ленты и только 2 для загрузки фото, что дешевле и эффективнее. Ошибочный выбор микросервисов на старте ведет к тому, что команда тратит больше времени на отладку сети, чем на разработку продукта (реальный пример: 30 микросервисов для приложения на 50 пользователей — это только лишняя сложность).
*   **Микросервисы:** Необходимы при количестве инженеров >50, необходимости независимых релизов разных частей системы или при разных требованиях к ресурсам.

### Стратегии тестирования
1.  **Unit-тесты:** Для бизнес-логики модулей.
2.  **Contract Testing (Pact):** Обязателен для микросервисов. Гарантирует, что изменения в API поставщика не сломают потребителей.
3.  **End-to-End (E2E):** Минимальное количество, только для критических путей, так как они нестабильны в распределенных средах.

### Паттерны миграции
*   **Strangler Fig (Фиговое дерево):** Постепенный «захват» функций монолита новыми сервисами.
*   **Anti-Corruption Layer (ACL):** Прослойка между новым микросервисом и старым монолитом для предотвращения «протекания» старой модели данных в новую систему.

## Дополнительная информация

### Необходимая инфраструктура
Для успешных микросервисов в 2026 году обязательны:
*   **Service Mesh (Istio, Linkerd):** Для управления East-West трафиком, mTLS и наблюдаемости.
*   **API Gateway (North-South):** Точка входа с авторизацией и rate-limiting.
*   **Distributed Tracing (OpenTelemetry + Jaeger/Tempo):** Единственный способ понять, где «застрял» запрос.
