# Монолитная и микросервисная архитектуры

## Определения

**Монолитная архитектура** — архитектурный паттерн, при котором все функциональные компоненты приложения (бизнес-логика, пользовательский интерфейс, доступ к данным, интеграционные модули) разрабатываются, развертываются и масштабируются как единый артефакт в рамках одного процесса.

**Микросервисная архитектура** — архитектурный стиль, при котором приложение строится как набор небольших, слабосвязанных и автономных сервисов. Каждый сервис реализует конкретный бизнес-процесс (Bounded Context), владеет собственным состоянием (Shared-Nothing Architecture) и взаимодействует с другими сервисами через легковесные протоколы (HTTP/REST, gRPC, очереди сообщений).

## Базовые концепции

### Закон Конвея (Conway's Law)
**Архитектура системы повторяет коммуникационную структуру организации.** Если у вас одна команда из 50 человек — будет монолит. Если у вас 10 автономных команд по 5 человек — будут микросервисы. Это не техническое ограничение, а социальное: архитектура, которая противоречит структуре команды, обречена на провал.

**Практическое следствие:** Переход к микросервисам требует реорганизации команд. Нельзя просто «порезать монолит на сервисы» без изменения структуры Ownership.

### Decision Framework: когда выбирать монолит, а когда микросервисы

| Критерий | Монолит | Микросервисы |
| :--- | :--- | :--- |
| **Размер команды** | 1–15 человек | 15+ человек (хотя бы 3–5 автономных команд) |
| **Стадия продукта** | MVP, стартап, проверка гипотезы | Зрелый продукт с устоявшейся архитектурой |
| **Требования к масштабированию** | Предсказуемые, умеренные | Непредсказуемые, точечные (отдельные компоненты) |
| **Частота деплоя** | 1–5 раз в неделю | 10–100+ раз в день (независимые команды) |
| **Требования к отказоустойчивости** | Допустимы кратковременные сбои | Высокая доступность (99.9%+) |
| **Технологическое разнообразие** | Один стек технологий | Разные команды — разные оптимальные стеки |
| **Культурная зрелость** | Нет DevOps-культуры | «You build it, you run it» |
| **Стоимость владения** | Низкая (один процесс, одна БД) | Высокая (оркестрация, трассировка, Service Mesh) |

**Правило «Start Monolith, Evolve to Microservices»:** Если вы сомневаетесь — начинайте с монолита. Микросервисы можно добавлять по мере роста. Обратный переход (микросервисы → монолит) крайне болезнен.

### Эволюция и типы монолитов
1.  **Однопроцессный монолит (Single-Process Monolith):** Классическое приложение. Все модули работают в одном адресном пространстве. Сбой в одном компоненте (например, утечка памяти в PDF-генераторе) может привести к отказу всего приложения.
2.  **Модульный монолит (Modular Monolith):** Современный стандарт (2025-2026). Архитектура с жесткой изоляцией логических модулей внутри одного процесса. Модули общаются через формализованные API внутри кода, а не напрямую через данные. Позволяет быстро перейти к микросервисам при необходимости без рефакторинга бизнес-логики.
3.  **Распределенный монолит (Distributed Monolith):** **Анти-паттерн**. Система разделена на сервисы, которые сильно связаны: требуют одновременного деплоя, имеют общую БД или используют синхронные вызовы без механизмов устойчивости, что приводит к каскадным сбоям.

### Принципы микросервисов
*   **Инкапсуляция данных (Database-per-Service):** Сервис полностью владеет своей БД. Прямой доступ к таблицам чужого сервиса категорически запрещен. Изменения схемы БД одного сервиса не должны ломать другие.
*   **Моделирование по DDD:** Границы сервисов определяются границами **Bounded Context** (ограниченных контекстов) из Domain-Driven Design.
*   **Умные эндпоинты, глупые каналы (Smart endpoints and dumb pipes):** Логика маршрутизации, трансформации и обработки находится внутри сервисов, а не в транспортной шине (в отличие от Enterprise Service Bus в SOA).
*   **Децентрализованное управление (Decentralized Governance):** Команды свободны в выборе технологий (полиглотность), подходящих для решения конкретной задачи.

### Теоретический базис распределенных систем
Переход к микросервисам означает переход от локальных вызовов функций к сетевым взаимодействиям, что вводит новые ограничения:
*   **CAP-теорема:** В распределенной системе при наличии сетевого разделения (Partition tolerance) приходится выбирать между строгой консистентностью (Consistency) и доступностью (Availability). Микросервисы обычно выбирают **AP** (Availability + Partition Tolerance) с использованием **Eventual Consistency** (итоговой согласованности).
*   **Заблуждения распределенных вычислений (Fallacies of Distributed Computing):**
    1. Сеть надежна (нет).
    2. Задержка равна нулю (нет).
    3. Пропускная способность бесконечна (нет).
    4. Сеть безопасна (нет).
    5. Топология не меняется (нет).

### Сравнение характеристик

| Характеристика | Монолит | Микросервисы |
| :--- | :--- | :--- |
| **Связанность** | Сильная (Tight Coupling) | Слабая (Loose Coupling) |
| **Масштабирование** | Вертикальное или горизонтальное всего приложения | Индивидуальное для каждого сервиса |
| **Отказоустойчивость**| Низкая (единая точка отказа) | Высокая (изоляция сбоев через Bulkhead) |
| **Консистентность** | Строгая (ACID транзакции) | Итоговая (Eventual Consistency, Saga) |
| **Деплой** | Редкий, тяжелый, рискованный | Частый, независимый, атомарный |
| **Операционная сложность**| Низкая | Высокая (требует автоматизации CI/CD, K8s) |
| **Стоимость владения** | Низкая (один процесс, одна БД) | Высокая (оркестрация, трассировка, Service Mesh) |
| **Отладка** | Простая (стек вызовов в одном процессе) | Сложная (распределенная трассировка, корреляция логов) |

## Управление данными в микросервисах

### Паттерн Transactional Outbox
**Проблема:** Два действия (запись в БД + отправка сообщения в шину) не могут быть выполнены атомарно в распределенной среде. Если БД обновилась, а сообщение не отправилось — данные рассинхронизируются.

**Решение:** Сохраняем сообщение в таблицу `outbox` в той же транзакции, что и бизнес-данные. Отдельный процесс (CDC или poller) доставляет сообщения в шину.

```sql
-- Внутри одной транзакции:
BEGIN;
  INSERT INTO orders (id, user_id, total) VALUES (1001, 42, 5000);
  INSERT INTO outbox (id, aggregate_id, event_type, payload, created_at)
    VALUES (gen_random_uuid(), 1001, 'OrderCreated', '{"order_id":1001,"total":5000}', NOW());
COMMIT;
```

Подробнее: **[Паттерн Outbox](../Databases/Concepts/distributed_transactions.md)**.

### Паттерн Saga
**Проблема:** Дistributed транзакция跨越多个 сервисов не может использовать 2PC (Two-Phase Commit) из-за производительности и доступности.

**Решение:** Разбиваем транзакцию на серию локальных транзакций. Каждая транзакция имеет компенсирующую операцию (откат). Если одна транзакция не удалась — выполняются компенсирующие операции для всех предыдущих.

**Типы Saga:**
- **Choreography (Хореография):** Каждый сервис слушает события и реагирует на них. Простая реализация, но сложно отслеживать общий flow.
- **Orchestration (Оркестрация):** Оркектор управляет последовательностью транзакций. Явная логика, но оркектор — потенциальная точка отказа.

Подробнее: **[Saga и распределенные транзакции](../Databases/Concepts/distributed_transactions.md)**.

### Event Sourcing
**Принцип:** Вместо хранения текущего состояния храним последовательность событий, которые привели к этому состоянию. Текущее состояние — это результат воспроизведения всех событий.

**Плюсы:**
- Полная история изменений (аудит)
- Возможность восстановить состояние на любой момент времени
- Идеально для event-driven архитектур

**Минусы:**
- Сложность запросов (нужны проекции/read models)
- Размер хранилища событий растет бесконечно (нужна компактификация)

Подробнее: **[Event-Driven Architecture](./event-driven-architecture.md)**.

### CQRS (Command Query Responsibility Segregation)
**Принцип:** Разделение модели записи (Command) и модели чтения (Query). Запись и чтение оптимизируются независимо друг от друга.

**Когда использовать:**
- Соотношение чтений/записей > 10:1 (read-heavy)
- Разные модели данных для записи и чтения
- Необходимость масштабирования чтения и записи независимо

Подробнее: **[Event-Driven Architecture](./event-driven-architecture.md)**.

## Тестирование микросервисов

### Пирамида тестирования для микросервисов
В микросервисной архитектуре классическая пирамида тестов (unit → integration → e2e) не работает из-за большого числа внешних зависимостей. Вместо неё используется **Testing Honeycomb (Модель «соты»)** с фокусом на Contract Testing.

### Contract Testing (Контрактное тестирование)
**Проблема:** Сервис A вызывает API сервиса B. Если B изменит формат ответа — A сломается. Интеграционные тесты требуют запуска обоих сервисов, что медленно и ненадежно.

**Решение:** Контрактное тестирование (Pact) проверяет, что API одного сервиса соответствует ожиданиям потребителя, без запуска зависимых сервисов.

**Как работает Pact:**
1. **Consumer (потребитель):** Пишет тест, описывающий ожидаемый формат ответа от провайдера.
2. **Pact Broker:** Хранит контракты и версии.
3. **Provider (провайдер):** Запускает тесты верификации против Pact Broker.

```python
# Consumer side (Pact Python)
from pact import Consumer, Provider

pact = Consumer('order-service').has_parranty_with(Provider('payment-service'))
pact.given('payment exists').upon_receiving('get payment').with_request(
    'get', '/payments/1001'
).will_respond_with(200, body={'id': 1001, 'status': 'completed'})
```

Подробнее: **[Тестирование микросервисов](../Testing/testing_types_unit_integration_e2e.md)**.

### Тестирование на границах
- **Health Check тесты:** Проверка доступности всех сервисов (HTTP 200 / readiness probe).
- **Chaos тесты:** Инъекция сбоев (отключение сервиса, рост latency) для проверки отказоустойчивости.
- **Performance тесты:** Проверка tail latency (P99, P999) в распределенной среде.

## Безопасность микросервисов

### Модель Zero Trust
В микросервисной архитектуре сетевое периметр не существует. Каждое взаимодействие должно аутентифицироваться и авторизоваться.

**Ключевые механизмы:**
1. **mTLS (Mutual TLS):** Клиент и сервер проверяют сертификаты друг друга. Реализуется через Service Mesh (Istio, Cilium) или API Gateway.
2. **Service-to-Service Auth:** JWT-токены с коротким TTL для идентификации вызывающего сервиса.
3. **Policy as Code:** Правила авторизации описываются декларативно (Istio AuthorizationPolicy, OPA Rego).

```yaml
# Istio AuthorizationPolicy: разрешаем orders-service читать из payments-service
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: payments-read
  namespace: production
spec:
  selector:
    matchLabels:
      app: payments-service
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/production/sa/orders-service"]
    to:
    - operation:
        methods: ["GET"]
        paths: ["/api/v1/payments/*"]
```

Подробнее: **[Безопасность Istio](../Service_Mesh/istio-security-policies.md)**, **[Zero Trust](../Networking/Concepts/zero_trust_overview.md)**.

### Secrets Management
В микросервисах секреты (API-ключи, токены, пароли) не должны храниться в коде или конфигах. Используйте **HashiCorp Vault** для централизованного управления секретами с автоматической ротацией.

Подробнее: **[Vault: Обзор](../Vault/overview.md)**, **[Vault Auth AppRole для микросервиса](../Vault/guides/vault_auth_approle.md)**.

## Наблюдаемость (Observability) микросервисов

### Три столпа наблюдаемости
В монолите достаточно логов и метрик. В микросервисах необходимы все три столпа:

| Столп | Инструменты | Зачем |
| :--- | :--- | :--- |
| **Метрики (Metrics)** | Prometheus + Grafana | RED-метрики (Rate, Errors, Duration) для каждого сервиса |
| **Логи (Logs)** | Loki / ELK + Fluentd | Централизованный сбор с корреляцией по trace_id |
| **Трассировка (Traces)** | OpenTelemetry + Tempo/Jaeger | Визуализация пути запроса через 10+ сервисов |

### RED-метод для микросервисов
**RED** (Rate, Errors, Duration) — метод мониторинга, предложенный Томом Уилки (Tom Wilkie):

- **Rate:** Количество запросов в секунду (RPS)
- **Errors:** Доля ошибочных запросов
- **Duration:** Распределение времени обработки (P50, P95, P99)

Каждый микросервис должен экспортировать эти метрики. В Kubernetes это делается через Prometheus ServiceMonitor или PodMonitor.

### Типичные проблемы микросервисной наблюдаемости
- **Fan-out задержки:** Если один запрос зависит от 100 параллельных вызовов — P99 latency каждого сервиса умножается. Решение: кэширование, асинхронные вызовы, circuit breaker.
- **Дисперсия логов:** Логи разрознены по десяткам сервисов. Решение: корреляция по trace_id (OpenTelemetry), централизованный сбор (Loki).
- **Отсутствие трассировки:** Без распределенной трассировки невозможно понять, где «висит» запрос. Решение: OpenTelemetry SDK, auto-instrumentation.

Подробнее: **[Наблюдаемость в микросервисах](./Observability_and_Monitoring/observability_definitions.md)**, **[Service Mesh: наблюдаемость](../Service_Mesh/istio_observability_and_tools.md)**.

## Командная структура

### Team Topologies для микросервисов
Микросервисы требуют автономных команд, каждая из которых владеет полным циклом разработки (frontend, backend, БД, инфраструктура).

**Идеальная структура:**
- **Stream-aligned team:** 3–8 человек, владеет 2–5 сервисами, деплоит независимо
- **Platform team:** Предоставляет Internal Developer Platform (CI/CD, мониторинг, Service Mesh)
- **Enabling team:** Помогает освоить новые технологии

**Закон Конвея в действии:** Если у вас 5 команд по 10 человек, но архитектура требует 20 сервисов — одна команда будет управлять 4 сервисами, что приведет к bottleneck. Слишком мало сервисов на команду — сложная коммуникация, слишком много — перегрузка.

4.  **Contract Testing:** Настроенная инфраструктура для проверки контрактов между сервисами.
5.  **Secrets Management:** Решение для безопасного хранения и ротации секретов (Vault).
6.  **Service Discovery:** Механизм обнаружения сервисов (Consul, Kubernetes DNS).

### Пошаговая миграция (Паттерн Strangler Fig)
Сценарий выноса функционала «Заказы» из монолита:

1.  **Анализ:** Определить границы модуля в монолите и его зависимости в БД.
2.  **Создание Anti-Corruption Layer (ACL):** Прослойка внутри монолита, которая перехватывает вызовы к будущему сервису.
3.  **Реализация нового сервиса:** Создание отдельного приложения и новой БД для заказов.
4.  **Миграция данных:** Пошаговый перенос данных с Dual Write / CDC.
5.  **Маршрутизация (API Gateway):** Настройка шлюза для перенаправления части трафика.
6.  **Валидация:** Параллельный запуск старого и нового пути, сравнение результатов.
7.  **Переключение:** Полный переход трафика на новый сервис.
8.  **Удаление старого кода:** Удаление модуля из монолита.

**Пример конфигурации Nginx (API Gateway) для постепенной миграции:**
```nginx
upstream monolith {
    server 10.0.0.1:8080;
}

upstream orders_service {
    server 10.0.0.2:8080;
}

server {
    listen 80;
    
    # Старый функционал идет на монолит
    location / {
        proxy_pass http://monolith;
    }

    # Новый функционал направляется на микросервис
    location /api/v1/orders {
        proxy_pass http://orders_service;
    }
}
```

### Миграция базы данных при декомпозиции
Самый сложный этап миграции — разделение общей БД монолита на Database-per-Service.

**Стратегия 1: Expand-Contract (Расширение-Сжатие)**
Паттерн для безопасной миграции схемы БД без даунтайма:

1. **Expand:** Добавляем новые колонки/таблицы для нового сервиса (старые остаются).
2. **Migrate:** Синхронизируем данные между старыми и новыми таблицами (CDC или dual write).
3. **Contract:** Удаляем старые колонки/таблицы после полного перехода.

Подробнее: **[Expand-Contract](../Databases/Concepts/migrations/expand_contract.md)**.

**Стратегия 2: Dual Write + Verification**
Временный период, когда монолит и новый сервис записывают данные одновременно:

```sql
-- В монолите (старый код):
BEGIN;
  INSERT INTO monolith_orders (id, user_id, total) VALUES (1001, 42, 5000);
  -- Одновременно пишем в новую таблицу для нового сервиса:
  INSERT INTO orders_new (id, user_id, total) VALUES (1001, 42, 5000);
COMMIT;
```

После верификации данных переключаем чтение на новую таблицу и удаляем старую.

**Стратегия 3: CDC (Change Data Capture)**
Используем Debezium для репликации изменений из БД монолита в БД нового сервиса в реальном времени:

```
Monolith DB → Debezium (CDC) → Kafka → orders-service → Orders DB
```

Подробнее: **[CDC паттерны](../Databases/Concepts/cdc_architectural_patterns.md)**.

### Валидация архитектурных границ
Как понять, что вы сделали микросервисы правильно:
*   **Автономный деплой:** Вы можете выкатить сервис заказов в пятницу вечером, не уведомляя команду сервиса пользователей.
*   **Отсутствие Shared DB:** В логах БД сервиса заказов не должно быть запросов от других сервисов.
*   **Contract Testing:** Запуск тестов `Pact` показывает, что API сервиса соответствует ожиданиям потребителей.

## Устранение неполадок (Troubleshooting)

### Типичные проблемы и решения
| Проблема | Симптомы | Решение |
| :--- | :--- | :--- |
| **Распределенный монолит** | Для изменения одной фичи нужно деплоить 5 сервисов одновременно | Пересмотреть границы Bounded Context. Объединить мелкие сервисы в Macroservice |
| **Каскадный сбой** | Сервис А тормозит → в сервисе Б забивается пул потоков → вся система ложится | Circuit Breaker (Istio, Resilience4j), таймауты, bulkhead изоляция |
| **Потеря консистентности** | Заказ оплачен, но в сервисе доставки его нет | Паттерн Outbox + CDC, Saga с компенсирующими транзакциями |
| **Fan-out задержка** | P99 latency выросла в 10 раз после добавления нового сервиса | Кэширование результатов, асинхронные вызовы, объединение мелких сервисов |
| **Дисперсия логов** | Невозможно найти причину сбоя — логи разрознены по 20 сервисам | Централизованный сбор (Loki), корреляция по trace_id (OpenTelemetry) |
| **Split-brain при сетевом partition** | Два сервиса видят разные данные | CAP: выбрать AP (Eventual Consistency) или CP (сynchronized replicas) |
| **Токсичные зависимости** | Один legacy-сервис блокирует развитие всей системы | Anti-Corruption Layer, постепенная замена, стрangler fig |
| **Неравномерная нагрузка** | Один сервис перегружен, остальные простаивают | Auto-scaling (HPA), load balancing, шардирование данных |
| **Проблема с деплоем** | Канарейка «отравлена» — бага затронула всех пользователей | Progressive delivery (canary → analysis → rollback), feature flags |

## Граничные случаи (Edge Cases)

*   **Системы с ультра-низкой задержкой (Low-Latency):** В высокочастотном трейдинге или real-time обработке сигналов сетевой оверхед микросервисов (даже gRPC) может быть недопустим. Здесь предпочтителен **Модульный монолит** с LMAX Disruptor архитектурой.
*   **Малые команды (2-3 человека):** Накладные расходы на поддержку Kubernetes, трассировки и Service Mesh перекроют все выгоды от архитектуры. MVP всегда лучше начинать как монолит.
*   **Сложные транзакции:** Если бизнес-процесс требует 100% ACID в рамках 20 таблиц, разделение его на микросервисы создаст «Saga-ад». Проще оставить этот блок монолитным внутри распределенной системы.
*   **Legacy-системы:** Если монолит написан на COBOL или ancient Java без тестов — переход к микросервисам требует длительного рефакторинга. Начните с модульного монолита и постепенно выносите функционал.
*   **Гибридные архитектуры:** Допустима комбинация: микросервисы для нового функционала + монолит для legacy. Важно: граница между ними должна быть явной (ACL, API Gateway).
*   **Real-time стриминг:** Для систем обработки видео/аудио в реальном времени сетевая задержка между сервисами может быть критичной. Рассмотрите модульный монолит с shared memory.

## Дополнительная информация

### Необходимая инфраструктура 2026
*   **Service Mesh (Istio, Cilium):** Для mTLS безопасности, управления трафиком и L7-наблюдаемости без изменения кода.
*   **API Gateway (APISIX, Kong):** Входная точка с аутентификацией, rate-limiting и трансформацией протоколов.
*   **Distributed Tracing (OpenTelemetry + Tempo/Jaeger):** Необходим для визуализации пути запроса через 10+ сервисов.
*   **Secrets Management (Vault):** Централизованное управление секретами с автоматической ротацией.
*   **Contract Testing (Pact):** Проверка контрактов между сервисами без запуска зависимых компонентов.
