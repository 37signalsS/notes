# Непрерывное профилирование (Continuous Profiling) — Обзор

## Определения

**Непрерывное профилирование (Continuous Profiling / Always-on Profiling)** — это метод постоянного динамического анализа производительности приложений в производственной среде с минимальными накладными расходами (обычно <1-2% CPU).

В отличие от традиционного профилирования (On-demand), которое запускается вручную во время инцидентов, непрерывное профилирование работает 24/7, сохраняя исторические данные о потреблении ресурсов (CPU, память, блокировки, I/O) на уровне функций кода.

### Ключевые преимущества
*   **Анализ инцидентов в прошлом:** Возможность увидеть Flame Graph системы за 5 минут до сбоя или в момент пиковой нагрузки, которая уже прошла.
*   **Обнаружение регрессий:** Сравнение профилей между разными версиями приложения для выявления неэффективного кода до того, как он вызовет проблемы.
*   **Оптимизация затрат:** Идентификация «горячих» участков кода для снижения потребления облачных ресурсов (CPU/Memory).
*   **Zero-day Observability:** Обнаружение аномалий в поведении сторонних библиотек или системных вызовов ядра.

## Базовые концепции

### Механизм сбора: eBPF против Агентов
Современные системы непрерывного профилирования (2025-2026) используют два основных подхода:

1.  **eBPF-профилирование (Sidecar-less):**
    *   **Как работает:** Агент работает на уровне ядра Linux, периодически сэмплируя стек вызовов всех процессов на хосте.
    *   **Плюсы:** Нулевое изменение кода приложения, поддержка всех языков (Go, Rust, C++, Python и даже Java через JIT-карты), видимость системных вызовов и работы ядра.
    *   **Инструменты:** **Parca**, **Pyroscope eBPF agent**.
2.  **Языковые агенты (SDK / Runtime-level):**
    *   **Как работает:** Библиотека интегрируется в код приложения или среду выполнения (JVM, Go Runtime).
    *   **Плюсы:** Максимально детальная информация об объектах в памяти (Heap), блокировках (Mutex) и специфичных для рантайма метриках.
    *   **Инструменты:** **py-spy** (Python), **async-profiler** (Java), **pprof** (Go).

### Хранение и эффективность (OTLP/Arrow)
Профили генерируют огромный объем данных. Для обеспечения «непрерывности» используются технологии сжатия:
*   **Колоночное хранение:** Профили эффективно сжимаются, так как многие стеки вызовов повторяются.
*   **OTLP Profiles:** Стандарт OpenTelemetry для передачи профилей, обеспечивающий совместимость между разными вендорами.
*   **Apache Arrow:** Использование формата Arrow для передачи данных (OTLP/Arrow) снижает нагрузку на сеть в 5-10 раз.

### Flame Graphs и Diff-анализ
Основной способ визуализации — ** Flame Graphs (Графы пламени)**. Для непрерывного профилирования критически важен **Diff-анализ**:
*   Сравнение профилей «сейчас» и «вчера».
*   Сравнение профилей Canary-релиза и Stable-версии.
*   Визуализация: Зеленые зоны (улучшение), Красные зоны (регрессия).

## Практические сценарии

### Сценарий 1: Обнаружение регрессии производительности
После деплоя новой версии сервиса на Go потребление CPU выросло на 15%.
1.  В Pyroscope открывается **Comparison View**.
2.  Выбираются теги `version=1.2.0` и `version=1.2.1`.
3.  На Flame Graph красным выделяется новая функция `ProcessDataV2`, которая тратит 80% времени на неэффективную регулярку.
4.  **Результат:** Откат или исправление одной строки кода за 5 минут.

### Сценарий 2: Span-to-Profile (Связь с трассировкой)
В Tempo обнаружен медленный HTTP-запрос (Latency > 2s).
1.  В Grafana нажимается кнопка **«View Profile»** для этого конкретного `trace_id`.
2.  Открывается Flame Graph, отфильтрованный именно по этому запросу.
3.  Видно, что время тратится на ожидание `db.Lock` внутри приложения.
4.  **Результат:** Понимание, что проблема не в БД, а в логике блокировок приложения.

### Сценарий 3: Анализ утечек памяти в продакшене
Сервис медленно наращивает потребление памяти (Memory Leak) в течение 3 дней.
1.  Выбирается профиль `alloc_objects` за последние 72 часа.
2.  Используется функция **Reconciliation**, чтобы увидеть, какие объекты создаются, но не удаляются Garbage Collector-ом.
3.  **Результат:** Идентификация кэша, который не очищается по TTL.

## Дополнительная информация

### Рекомендации по внедрению
1.  **Начинайте с CPU:** Это самый простой профиль с минимальным оверхедом.
2.  **Используйте тегирование:** Профили без тегов `service_name`, `version` и `region` практически бесполезны для анализа.
3.  **Настройка оверхеда:** Для высоконагруженных систем снижайте частоту сэмплирования (например, с 100Гц до 19Гц).
4.  **Символизация:** Настройте автоматическую загрузку `debug symbols` (или не удаляйте их из бинарников), иначе вместо имен функций вы увидите адреса памяти `0x45f2a1`.
