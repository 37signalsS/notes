# Service Mesh: Обзор

## Определения

- **Service Mesh**: Выделенный инфраструктурный слой для управления, обеспечения безопасности и мониторинга сетевого взаимодействия между сервисами в распределенной системе, чаще всего в [архитектуре микросервисов](../monolith_vs_microservices.md#микросервисная-архитектура).

- **Data Plane (Плоскость данных)**: Отвечает за непосредственную обработку сетевого трафика. Состоит из множества легковесных прокси-серверов, которые развертываются рядом с каждым экземпляром сервиса.

- **Control Plane (Плоскость управления)**: "Мозг" Service Mesh. Централизованный компонент, который конфигурирует все прокси-серверы в плоскости данных, применяет политики и собирает телеметрию.

- **Sidecar**: Паттерн развертывания, при котором вспомогательный контейнер (прокси) запускается в том же сетевом окружении (например, в одном Pod'е Kubernetes), что и основной контейнер приложения. Это фундаментальный механизм, на котором строятся большинство Service Mesh. Подробнее см. в [**описании паттерна Sidecar**](../../Kubernetes/Base/pod.md#паттерн-сайдкар-sidecar).

## Базовые концепции

### Проблема, которую решает Service Mesh

С переходом от монолитной архитектуры к микросервисной резко возрастает сложность сетевого взаимодействия. Задачи, которые необходимо решать для каждого сервиса, включают:

- **Обнаружение сервисов (Service Discovery)**
- **Балансировка нагрузки**
- **Отказоустойчивость** (таймауты, повторные попытки, прерывание цепи)
- **Мониторинг и трассировка**
- **Безопасность** (шифрование, аутентификация, авторизация)

Реализация этой логики внутри каждого сервиса приводит к дублированию кода и сильной зависимости от конкретных библиотек. Service Mesh выносит всю эту функциональность на отдельный, невидимый для приложения инфраструктурный уровень.

### Архитектура: Control Plane и Data Plane

1. **Data Plane перехватывает трафик**: Каждый экземпляр приложения развертывается вместе с **прокси-сайдкаром** (чаще всего **Envoy Proxy**). Этот прокси перехватывает весь входящий и исходящий сетевой трафик приложения.
2. **Control Plane управляет прокси**: Оператор задает высокоуровневые правила в Control Plane (например, "направлять 10% трафика на новую версию сервиса `users`"). Control Plane транслирует эти правила в конкретные низкоуровневые конфигурации и распространяет их на все прокси-сайдкары в Data Plane.

Таким образом, логика приложения остается "чистой", а вся сложность сети управляется централизованно.

## Практические сценарии: Ключевые возможности

Service Mesh предоставляет мощные инструменты для управления распределенной системой "из коробки".

### Наблюдаемость (Observability)

- **Метрики (Golden Signals)**: Автоматический сбор метрик L4/L7 для каждого сервиса: частота запросов, частота ошибок, задержка.
- **Распределенная трассировка**: Сквозное отслеживание одного запроса через все сервисы, в которых он был обработан.
- **Топология сервисов**: Визуализация карты зависимостей и потоков трафика между сервисами.

### Управление трафиком (Traffic Management)

- **Динамическая маршрутизация**: Гибкое управление трафиком без изменения кода или переразвертывания.
  - **Канареечные выкатки (Canary Releases)**: Плавное направление небольшой части трафика (например, 1%) на новую версию сервиса.
  - **A/B-тестирование**: Маршрутизация на разные версии сервиса на основе HTTP-заголовков, cookie и т.д.
- **Инъекция ошибок и задержек**: Искусственное внесение сбоев для тестирования отказоустойчивости системы (Chaos Engineering).

### Безопасность (Security)

- **Взаимная TLS-аутентификация (mTLS)**: Автоматическое шифрование всего трафика между сервисами внутри сетки и взаимная проверка подлинности. Service Mesh берет на себя всю работу по выпуску, ротации и отзыву сертификатов.
- **Политики доступа**: Создание правил, разрешающих или запрещающих взаимодействие между определенными сервисами (например, "сервис `frontend` может обращаться только к сервису `auth` и `products`").

### Надежность (Reliability)

- **Повторные попытки (Retries) и таймауты**: Автоматическое применение политик для повторных запросов при временных сбоях.
- **Прерывание цепи (Circuit Breaking)**: Изоляция неисправных экземпляров сервиса. Если сервис начинает возвращать слишком много ошибок, Service Mesh временно прекращает направлять на него трафик, предотвращая каскадные сбои.

## Дополнительная информация

### Примеры реализаций

| Service Mesh | Ключевые особенности |
| :--- | :--- |
| **Istio** | Самый функциональный и зрелый. Использует Envoy Proxy. Обладает высокой сложностью, но предоставляет максимум возможностей. |
| **Linkerd** | Фокусируется на простоте, производительности и низком потреблении ресурсов. Использует собственный легковесный прокси, написанный на Rust. |
| **Consul Connect** | Интегрирован в экосистему HashiCorp Consul. Хороший выбор, если Consul уже используется для обнаружения сервисов. |
| **OSM (Open Service Mesh)** | Легковесный и расширяемый Service Mesh от Microsoft, также использующий Envoy. |
