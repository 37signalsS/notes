# Событийно-ориентированная архитектура (Event-Driven Architecture — EDA)

**Событийно-ориентированная архитектура (EDA)** — это архитектурный паттерн, в котором состояние системы изменяется и синхронизируется через поток дискретных событий. В отличие от традиционных запрос-ответных систем, EDA строится на принципе «выстрелил и забыл» (fire-and-forget) и обеспечивает максимальную развязку (decoupling) между компонентами.

---

## Определения

- **Событие (Event):** Значимое изменение состояния (например, «Заказ создан», «Датчик температуры сработал»). Событие является фактом, который **уже произошел**, и оно неизменяемо (immutable).
- **Сообщение (Message):** Обобщенный термин для данных, передаваемых через шину. Сообщение может быть событием или командой.
- **Команда (Command):** Намерение выполнить действие («Создать заказ»). В отличие от события, команда может быть отклонена, а её отправитель ожидает подтверждения выполнения.
- **Продюсер (Producer):** Источник события. Он не знает, кто будет обрабатывать событие и как. Его задача — зафиксировать факт изменения.
- **Консьюмер (Consumer):** Получатель события. Он реагирует на него, выполняя свою бизнес-логику.
- **Канал событий (Event Channel):** Инфраструктура для передачи событий (брокеры сообщений: Kafka, RabbitMQ, NATS).

---

## Базовые концепции

### Модели взаимодействия
1. **Event Notification (Уведомление о событии):** Продюсер отправляет минимальное сообщение (например, только ID заказа). Консьюмер, получив его, должен сделать обратный запрос к продюсеру за деталями.
   - *Плюсы:* Малый объем сообщений, высокая безопасность (консьюмер видит только то, что ему разрешено).
   - *Минусы:* Высокая нагрузка на продюсера из-за обратных вызовов, риск потери связности.
2. **Event-Carried State Transfer (Передача состояния в событии):** Событие содержит все необходимые данные для обработки (снапшот состояния).
   - *Плюсы:* Консьюмер автономен, не нужны обратные вызовы.
   - *Минусы:* Большой объем сообщений, риск версионности данных (данные в событии могут устареть к моменту обработки).
3. **Event Sourcing (Источник событий):** Состояние объекта не сохраняется как текущий снимок, а вычисляется путем повторного воспроизведения всей истории его событий.
   - *Подробнее:* См. раздел «Архитектурные паттерны».

### Координация: Оркестрация vs Хореография
Координация сложной бизнес-логики, затрагивающей несколько сервисов.

#### 1. Оркестрация (Orchestration)
Централизованный подход, где специальный сервис-контроллер («оркестратор») управляет процессом, давая команды другим сервисам.
- **Как работает:** Оркестратор вызывает сервис A, ждет ответа, затем вызывает сервис B.
- **Плюсы:** Легко отслеживать текущее состояние процесса, простота реализации сложной логики компенсации (Saga pattern).
- **Минусы:** Оркестратор становится «узким местом» и единой точкой отказа; высокая связность между оркестратором и сервисами.
- **Инструменты:** [SaltStack Orchestration](../SaltStack/Orchestration_and_Automation_Methods.md), [Ansible Playbooks](../Ansible/PlaybookStructure/examples.md).

#### 2. Хореография (Choreography)
Децентрализованный подход, где каждый сервис знает только о своих задачах и реагирует на события других сервисов без центрального управления.
- **Как работает:** Сервис A выпускает событие «Данные сохранены». Сервис B видит это событие и начинает свою работу.
- **Плюсы:** Максимальная масштабируемость, отсутствие единой точки отказа, сервисы полностью независимы.
- **Минусы:** Сложно отследить сквозной путь процесса (требуется Distributed Tracing); риск возникновения циклических зависимостей.
- **Применение:** Реактивная автоматизация, например, [Event-Driven Ansible](../Ansible/event-driven-ansible.md).

### Согласованность в конечном счете (Eventual Consistency)
В EDA данные в разных компонентах могут быть временно рассогласованы.
- **Суть:** Вместо строгой транзакционности (ACID) используется модель **BASE** (Basically Available, Soft state, Eventual consistency).
- **Почему это важно:** Обеспечивает высокую доступность и производительность, но требует от бизнеса готовности к тому, что изменения видны не мгновенно.

### Надежность и отказоустойчивость
1. **Exactly-once семантика:** Гарантия обработки события ровно один раз. Требует транзакционных брокеров (Kafka) и идемпотентности консьюмеров.
   - *Подробнее:* [Гарантии доставки и надежность данных](../Kafka/delivery_guarantees.md).
2. **Идемпотентность:** Способность системы выдавать одинаковый результат при повторном получении одного и того же события.
   - *Подробнее:* [Идемпотентность в EDA](../Concepts/idempotency.md).
3. **Dead Letter Queues (DLQ):** Очередь для сообщений, которые не удалось обработать после N попыток.
   - *Управление:* Мониторинг DLQ критичен для предотвращения потери данных. См. [Паттерн Воркеры + Очередь](../Kubernetes/Autoscaling/workers_queue_pattern.md).
4. **Schema Registry:** Контракт данных между сервисами. Предотвращает поломки при изменении структуры событий.
   - *Подробнее:* [Интеграция ClickHouse с Schema Registry](../Databases/ClickHouse/clickhouse_kafka_integration.md).

## Архитектурные паттерны

### CQRS (Command Query Responsibility Segregation)
Разделение модели записи (Command) и модели чтения (Query).
- **Связь с EDA:** События из модели записи транслируются в модель чтения для синхронизации. Позволяет использовать разные БД (например, PostgreSQL для записи, ElasticSearch для поиска).

### Transactional Outbox
Решает проблему дуальной записи (Dual Write): как гарантировать, что событие будет отправлено, если данные в БД успешно сохранены.
- **Workflow:**
  1. В одной транзакции обновляются бизнес-данные и записывается событие в таблицу `outbox`.
  2. Отдельный процесс (Relay/CDC) читает таблицу `outbox` и отправляет события в брокер.
  3. После подтверждения от брокера событие в `outbox` помечается как отправленное или удаляется.
- **Два подхода к чтению outbox:**
    - *Polling (Опрос):* Периодический `SELECT` из таблицы `outbox` с фильтром по `sent_at IS NULL`. Просто в реализации, но создаёт нагрузку на БД (лишние запросы) и имеет задержку (интервал опроса). Подходит для низких нагрузок (<100 EPS).
    - *CDC (Change Data Capture) — рекомендуемый подход:* **[Debezium](https://debezium.io/)** подключается к **[WAL (Write-Ahead Log)](../Databases/Concepts/write_ahead_log.md)** PostgreSQL/MySQL и в реальном времени транслирует изменения таблицы `outbox` в Kafka. Нулевая нагрузка на приложение, задержка <100ms, guaranteed At-Least-Once доставка. Debezium коннектится как replication slot (PostgreSQL) или binlog subscriber (MySQL).
- **Проблема sequences:** Если в outbox используется sequence-based ID, то при replay CDC могут возникнуть gaps (пропущенные ID из-за откатов транзакций). Решение: использовать UUID или монотонный sequence без gaps.
- *Подробнее:* [Паттерн Transactional Outbox](../Kafka/delivery_guarantees.md), [Архитектурные паттерны CDC](../Databases/Concepts/cdc_architectural_patterns.md).

### Saga Pattern
Управление распределенными транзакциями через последовательность локальных транзакций.
- **Суть:** Если на одном из шагов произошла ошибка, выполняются «компенсирующие транзакции» для отката предыдущих успешных шагов.
- **Реализация:** Может быть через Оркестрацию или Хореографию.
- *Подробнее:* [Паттерн Сага](../Databases/Concepts/distributed_transactions.md).

### Event Sourcing (Источник событий)
Паттерн хранения состояния как последовательности событий, а не текущего снимка.
- **Суть:** Каждое изменение состояния записывается как неизменяемое событие в Event Store. Текущее состояние вычисляется путём replay всех событий (проекция). События — это факт, который уже произошёл; они неизменяемы и не удаляются.
- **Event Store:** Хранилище событий. Типичные реализации: Kafka (с log-compaction или без), EventStoreDB, PostgreSQL (с таблицей events). Каждое событие имеет уникальный ID, порядковый номер (sequence) и временную метку.
- **Snapshots (Снимки):** Оптимизация для агрегатов с длинной историей. Периодически сохраняется снимок текущего состояния, и replay начинается не с начала, а с последнего снимка. Без snapshots при 100 000 событиях на агрегат replay будет выполняться секунды; со snapshots — миллисекунды.
- **Projections (Проекции):** Представления данных, созданные из потока событий. Могут быть materialized (обновляются в реальном времени) или lazy (вычисляются при запросе). Проекции создаются отдельно и могут быть пересозданы из scratch (rebuild) при ошибке в логике.
- **Replay:** Пересчёт состояния из событий. Используется для: восстановления после бага в проекции, создания нового представления данных, миграции данных при изменении схемы.
- **Связь с CQRS:** Event Sourcing часто применяется совместно с CQRS — модель записи работает через Event Store, модель чтения — через проекции.
- **Проблемы:** Рост размера Event Store (решение: archiving, snapshots), сложность изменения схемы событий (решение: upcasting, event versioning), eventual consistency проекций (read-your-writes могут требовать реализации через read-through cache).
- *Подробнее:* [Архитектурные паттерны CDC](../Databases/Concepts/cdc_architectural_patterns.md), [Event Sourcing в Kafka](../Kafka/message_queues_principles.md).

### Backpressure (Обратное давление)
Механизм контроля потока данных, когда консьюмер не успевает обрабатывать события с той скоростью, с какой они поступают.
- **Зачем нужно:** Без backpressure происходит переполнение очереди/buffer, потеря сообщений или снижение производительности всей системы.
- **Проявление в Kafka:** Консьюмер обрабатывает медленнее, чем продюсер записывает. `fetch.max.bytes` и `max.poll.records` ограничивают объём данных за один poll. При превышении `max.poll.interval.ms` консьюмер исключается из группы и происходит rebalance.
- **Проявление в RabbitMQ:** Брокер может задушить (throttle) продюсера через `flow` control при переполнении очереди. `credit_flow` механизм останавливает приём сообщений от продюсера.
- **Стратегии:**
    - *Buffering:* Увеличение размера буфера (временное решение, не решение корневой проблемы).
    - *Rate Limiting:* Ограничение скорости продюсера (token bucket, leaky bucket).
    - *Batching:* Группировка обработки для повышения throughput на стороне консьюмера.
    - *Scaling:* Вертикальное (больше CPU/RAM) или горизонтальное (больше консьюмеров в группе) масштабирование.
    - *Drop/Reject:* Отбрасывание избыточных сообщений (допустимо для телеметрии, недопустимо для платежей).
- **Мониторинг:** Consumer lag — основной индикатор backpressure. Рост lag = консьюмер не справляется.

### Гарантии упорядоченности (Ordering Guarantees)
- **Внутри одной партиции Kafka:** Гарантируется строгий порядок (offset монотонно возрастает). Порядок сообщений определяется ключом: все сообщения с одним `key` попадают в одну партицию.
- **Между партициями:** Порядок не гарантируется. Если бизнес-логика требует порядка для разных ключей — нужен дополнительный механизм (сериализация через один топик или consuming с timestamps).
- **Глобальный порядок:** Требует одного консьюмера (single partition) — жертва масштабируемостью. На практике глобальный порядок требуется редко; обычно достаточно partition-level ordering.
- **При ребалансировке:** Консьюмер может получить новую партицию и начать читать с последнего committed offset. Если offset не был закоммичен — будут повторные обработки (at-least-once семантика).
- **RabbitMQ:** Порядок гарантирован в пределах одной очереди. При использовании Exchange с routing key — порядок сохраняется для одного key. Headers exchange не гарантирует порядок.

## Практические сценарии

### Реализация наблюдаемости (Observability)
В EDA прохождение одного бизнес-процесса может затрагивать десятки сервисов и очередей.
1. **Distributed Tracing (Распределенная трассировка):**
   - Использование `Trace ID` и `Span ID`, которые передаются в заголовках сообщений (Metadata).
   - Инструменты: Jaeger, OpenTelemetry (OTel).
2. **Correlation ID:** Уникальный идентификатор процесса, позволяющий склеить логи разных сервисов в одну цепочку.

### Мониторинг ключевых метрик
- **Consumer Lag (Задержка консьюмера):** Разница между последним записанным сообщением в брокере и последним обработанным консьюмером. Рост лага — главный индикатор проблем с производительностью. В Kafka: `kafka-consumer-groups.sh --describe --group my-group` или метрики `kafka_consumergroup_lag` в Prometheus.
- **Throughput (Пропускная способность):** Количество событий в секунду (EPS) или байт/сек. Мониторить на обоих концах: продюсер (produce rate) и консьюмер (consume rate).
- **Error Rate:** Процент неуспешных обработок (события, ушедшие в DLQ). Алерт при error rate > 0.1% для критических сервисов.
- **End-to-End Latency:** Время от записи события продюсером до обработки консьюмером. В Kafka измеряется как разница между timestamp сообщения и временем обработки.
- **Broker Health:** Under-replicated partitions, active controller count, disk utilization. В Kafka: JMX метрики `kafka.server:type=BrokerTopicMetrics`.

### Тестирование в EDA
- **Consumer-Driven Contracts (CDC):** Консьюмеры определяют ожидания от формата события, а продюсеры обязаны их соблюдать. При нарушении контракта — автоматический отказ в CI/CD.
- **Инструменты:** Pact, Spring Cloud Contract.
- **Интеграционные тесты:** Запуск реального брокера (Testcontainers) в CI для проверки end-to-end сценариев.

### Деплой и обновление консьюмеров
- **Blue/Green деплой:** Запуск новой версии консьюмера параллельно со старой. Новый инстанс начинает читать с того же committed offset. После проверки — отключение старого. Риск: дублирование обработки при overlaps.
- **Canary деплой:** Новая версия получает часть трафика (например, 5% партиций). Мониторинг error rate и consumer lag перед полным rollout.
- **Rolling update в Kubernetes:** `maxUnavailable: 0`, `maxSurge: 1` для поочерёдного обновления подов. Важно: корректный `SIGTERM` → завершение текущей обработки → коммит offset → выход.

### Управление Dead Letter Queues (DLQ)
- **Мониторинг:** Алерт при росте размера DLQ > 0. DLQ = потерянные данные или баг в консьюмере.
- **Обработка:** Регулярный скрипт (CronJob в K8s) ретраит сообщения из DLQ в основной топик с увеличивающимся backoff.
- **TTL:** Настройка времени жизни сообщений в DLQ (7–30 дней). По истечении — удаление или архивирование.
- **Изоляция:** DLQ должен быть отдельным топиком/очередью с отдельной группой консьюмеров, чтобы проблемное сообщение не блокировало основной поток.

### Масштабирование консьюмеров
- **Consumer Groups:** Добавление инстансов в группу автоматически перераспределяет партиции. В Kafka при добавлении консьюмера > числа партиций — лишние инстансы простаивают.
- **Партиционирование:** Количество партиций = максимальный параллелизм. Перепартиционирование (repartitioning) — болезненная операция (миграция данных). Изначально закладывайте запас (например, 2x ожидаемого параллелизма).
- **Sticky partitioning:** Минимизация перераспределения при rebalance (Kafka 2.4+ по умолчанию).

## Дополнительная информация

### Сравнение инструментов
| Инструмент | Тип | Сильные стороны | Ограничения | Основное применение |
| :--- | :--- | :--- | :--- | :--- |
| **Kafka** | Log-based Broker | Хранение данных (Retention), высокая нагрузка, стриминг, транзакции | Тяжёлый (ZooKeeper → KRaft), сложная настройка | Event Sourcing, аналитика, high-throughput |
| **RabbitMQ**| Traditional Broker | Гибкая маршрутизация (Exchanges), простота, Publisher Confirms | Ограниченная retention, lower throughput | Классические очереди задач, RPC |
| **NATS / JetStream**| Cloud Native Broker | Легкость, производительность, low latency, Core NATS | Меньше ecosystem, limited retention (JetStream helps) | Микросервисы, IoT, edge |
| **Redis Streams** | Log-based (in-memory) | Простота, nano-latency, встроен в Redis | Ограничен RAM, нет durable persistence по умолчанию | Кэширование, lightweight eventing |

### Лучшие практики
1. **Версионирование схем:** Никогда не делайте ломающих изменений в существующих схемах. Используйте Schema Registry с `BACKWARD` или `FULL` compatibility mode.
2. **Именование топиков:** Используйте четкую структуру, например: `domain.subdomain.event_type.version` (например, `orders.payment.payment_completed.v2`).
3. **Минимализм в событиях:** Не передавайте лишние данные, но обеспечьте достаточную информацию для принятия решения консьюмером. Для тяжёлых payload — передавайте ссылку (URL/ID), а не сами данные.
4. **Безопасность:** Шифруйте чувствительные данные (PII) в событиях или передавайте только ссылки на них. Используйте ACL для контроля доступа к топикам.
5. **Идемпотентность консьюмеров:** Всегда предполагайте at-least-once доставку. Реализуйте дедупликацию через ID события (Inbox pattern).
6. **Мониторинг DLQ:** Алерт при появлении сообщений в DLQ. Рассматривайте DLQ как индикатор проблем, а не как мусорное ведро.
7. **Consumer Group isolation:** Используйте отдельные consumer groups для критических и некритических обработчиков, чтобы slowdown в одном не влиял на другой.

### Диагностика и типичные проблемы

| Симптом | Вероятная причина | Решение |
|:---|:---|:---|
| Consumer lag растёт линейно | Консьюмер не справляется с нагрузкой | Увеличить число консьюмеров или партиций; оптимизировать обработку |
| Consumer lag резко скачет | Rebalance в consumer group | Проверить `max.poll.interval.ms`; увеличить таймаут или уменьшить `max.poll.records` |
| Дублирование обработки | At-least-once + отсутствие идемпотентности | Реализовать Inbox pattern (таблица processed IDs в БД) |
| Событие не доходит до консьюмера | Ошибка в маршрутизации (wrong routing key/exchange) | Проверить binding в RabbitMQ; проверить key в Kafka |
| Ошибка Schema Registry | Ломающее изменение схемы | Использовать `BACKWARD` compatibility; создать новую версию топика |
| Under-replicated partitions | Один из брокеров Kafka недоступен | Проверить сетевую связность, состояние брокера, ISR |
| `CoordinatorNotAvailable` | Координатор consumer group недоступен | Проверить健康ность брокера-координатора; перезапустить если нужно |
| Message ordering нарушен | Сообщения с разными key попали в разные партиции | Убедиться, что related messages используют один key |
| DLQ растёт постоянно | Баг в консьюмере или невалидные данные | Проверить логи консьюмера; проанализировать сообщения в DLQ |
| Высокий latency end-to-end | Медленный консьюмер или проблемы с сетью | Профилировать обработку; проверить задержки сети между DC |
