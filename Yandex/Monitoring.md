# Yandex Cloud DevOps - Monitoring

## Мониторинг и логирование: использование Yandex Monitoring

### Роль Yandex Monitoring в DevOps-потоке

Мониторинг и логирование решают разные задачи, но в продакшене они работают совместно. Мониторинг фиксирует состояние системы как набор метрик во времени и позволяет визуализировать тренды и настраивать оповещения. Логи содержат детальные события для расследования причин инцидентов. В Yandex Cloud базовые элементы — Yandex Monitoring для метрик и Cloud Logging для логов; между ними легко выстраивается интеграция, чтобы превращать события в измеримые SLI.

Сравнение подходов:

- **Мониторинг**: агрегированные численные ряды (латентность, ошибки, использование ресурсов), дашборды, алерты.
- **Логирование**: подробные записи запросов/ошибок, контекст и трассировка, поиск по шаблонам.

### Модель данных Yandex Monitoring

- **Метрика**: именованный временной ряд (например, custom.http_requests_total).
- **Точки (points)**: пары метка времени — значение.
- **Метки (labels)**: ключи/значения, описывающие источник (service, env, zone).
- **Типы**: gauge (снимок состояния), counter (монотонный счётчик), histogram/summary (распределение).
- **Агрегации**: sum, avg, min/max, rate/delta для счётчиков, квантиль/percentile для латентности.
- **Гранулярность и downsampling**: агрегирование в окна (1m, 5m) для устойчивых графиков и алертов.

### Сбор метрик: паттерны

- **Push API**: приложения и скрипты отправляют пользовательские метрики напрямую.
- **Экспортеры**: системные и прикладные метрики через прометеус-экспортеры и шлюзы.
- **Интеграции**: сервисы облака публикуют системные метрики, доступные в одном пространстве наблюдаемости.
- **Гибрид**: вычисляете производные метрики из логов/трасс и публикуете их как time series.

Пример отправки метрики через HTTP API с IAM-токеном:

```bash
TOKEN=$(yc iam create-token)
FOLDER_ID=<FOLDER_ID>
ENDPOINT=https://<monitoring-endpoint>/v2/timeseries:write

curl -sS -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -X POST "$ENDPOINT?folderId=$FOLDER_ID" \
  -d '{
    "timeseries": [
      {
        "name": "custom.http_requests_total",
        "labels": { "service": "checkout", "env": "prod", "status": "200" },
        "points": [
          { "ts": '"'$(date -u +"%Y-%m-%dT%H:%M:%SZ")'"', "value": 42 }
        ]
      }
    ]
  }'
```

Рекомендуется стабилизировать метки (фиксированные ключи, ограниченное кардинальное множество значений), чтобы избежать «взрыва кардинальности».

### Логи → метрики

Технологический приём «log-based metrics» позволяет использовать логи для построения SLI/алертов:

- Cloud Logging собирает записи в группы логов.
- Log Router направляет поток в конвейер обработки (например, безсерверная функция).
- Функция агрегирует события по окну (количество 5xx, перцентиль latency) и публикует результат в Yandex Monitoring как метрику.

Этот подход позволяет выделять ключевые метрики надежности из сырого потока логов, не нагружая дашборды сложными запросами.

### Запросы, дашборды и оповещения

Запросы к временным рядам поддерживают фильтрацию по меткам, агрегации и оконные функции. Примеры:

```
metric("custom.http_requests_total")
| filter(service="checkout", env="prod")
| rate(1m)
| group_by(["status"])
```

```
metric("custom.http_request_duration_seconds")
| filter(service="checkout", env="prod")
| percentile(0.99, 5m)
```

Дашборды собираются из графиков, числовых виджетов и таблиц. Настраиваются переменные (env, service) и единицы измерения. Для сложных сценариев Yandex Monitoring можно подключить как источник данных в Grafana.

Алертинг строится на выражениях поверх метрик с порогами и окнами устойчивости. Пример декларации условия в виде псевдо-YAML:

```yaml
alert: "High 99p latency"
expr: |
  metric("custom.http_request_duration_seconds")
  | filter(service="checkout", env="prod")
  | percentile(0.99, 5m)
  | gt(0.5)            # > 0.5s
for: 10m               # устойчиво 10 минут
labels:
  severity: critical
notifications:
  - channel: email
  - channel: webhook
silence:
  schedule: night-maintenance
```

Практика: задавайте безопасные окна (for) и гистерезис, группируйте оповещения по сервису/региону, используйте метки для маршрутизации и приоритезации.
