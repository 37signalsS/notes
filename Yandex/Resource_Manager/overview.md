# Yandex Resource Manager: Обзор

## Definitions

**Resource Manager** — сервис управления иерархией ресурсов и доступом в Yandex Cloud. Определяет базовые сущности для организации инфраструктуры: облака, каталоги, метки и привязки прав.

**Cloud (Облако)** — верхний уровень изоляции с единым биллингом и квотами.

**Folder (Каталог)** — логическая единица развёртывания внутри облака. Соответствует окружению (dev, stage, prod) или продукту.

**Service Account** — учётная запись для аутентификации приложений и сервисов в Yandex Cloud.

**Labels** — пары ключ-значение для маркировки ресурсов (группировка, биллинг, политики).

## Basic Concepts

### Иерархия ресурсов

```
┌─────────────────────────────────────────┐
│              Cloud (Облако)             │
│         Биллинг, квоты, лимиты          │
└─────────────────────────────────────────┘
                   │
    ┌──────────────┼──────────────┐
    │              │              │
┌───▼────┐   ┌────▼────┐   ┌────▼────┐
│ Folder │   │ Folder  │   │ Folder  │
│  (dev) │   │ (stage) │   │  (prod) │
└────────┘   └─────────┘   └─────────┘
```

### Ключевые сущности

| Сущность | Назначение | Пример |
| :--- | :--- | :--- |
| **Cloud** | Изоляция, биллинг, квоты | `my-company-cloud` |
| **Folder** | Окружение, продукт, команда | `dev`, `stage`, `prod`, `analytics` |
| **Labels** | Метки для группировки, биллинга, политик | `env=prod`, `owner=team-a`, `cost-center=123` |
| **Service Account** | Аутентификация приложений | `sa-deploy`, `sa-monitoring` |
| **Access Bindings** | Привязки ролей к субъектам | `editor → sa-deploy` |

### Управление доступом

Роли и права доступа описаны в [IAM Roles](./iam_roles.md). Ключевые принципы:

- Принцип минимальных прав — узкие сервисные роли вместо `editor`
- Назначение ролей на уровне каталога, а не облака
- Разделение прав для dev/stage/prod

### Автоматизация и IaC

Декларативное управление через [Terraform](./terraform_automation.md) и [Crossplane](../../GitOps/Crossplane/provider_yandex_cloud_setup.md):

- Каталог и сервисные аккаунты описываются как код
- Версионирование изменений прав в Git
- Аудит через историю коммитов

## Practical Scenarios

### Паттерн: разделение окружений

- Один каталог = одно окружение или сервис
- Каждый каталог — отдельный контур развёртывания с изолированными правами
- Обязательные метки: `env`, `owner`, `cost-center`
- Избегать более 10 каталогов на облако (лимит — до 50)

### Паттерн: bootstrap через сервисный аккаунт

- CI/CD работает от имени сервисного аккаунта ([GitLab CI](../../CI-CD/GitLab_CI/Concepts/gitlab_ci_basics.md))
- Ограниченные права только на необходимые ресурсы
- Ротация ключей каждые 90 дней, хранение в secrets manager
- Один аккаунт = одна цель (`sa-deploy`, `sa-monitoring`)

### Паттерн: метрики и биллинг

- Метки `env`, `owner`, `cost-center` — обязательные для всех ресурсов
- Дополнительные: `service`, `team`, `project`
- Автоматическое применение через Terraform
- Группировка затрат по меткам, регулярный аудит неиспользуемых ресурсов

## Additional Information

### Лимиты и квоты (2025–2026)

- До 50 каталогов на облако
- До 20 меток на ресурс
- IAM: поддержка OIDC для федерации идентити

### Безопасность

Принцип минимальных прав и ротация ключей описаны в [IAM Roles](./iam_roles.md). Аудит — логирование всех операций через Cloud Logging. Обязательная маркировка ресурсов метками.
