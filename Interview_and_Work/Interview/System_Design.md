# Проектирование систем (System Design)

## Определения

**System Design** — это процесс проектирования программного обеспечения и инфраструктуры с учетом компонентов и их взаимодействия, а также требований по функциональности, масштабируемости, надежности, безопасности и стоимости.

**Согласованность в конечном счете (Eventual Consistency)** — модель согласованности в распределенных системах, гарантирующая, что при отсутствии обновлений все реплики со временем станут идентичными. Подробнее см. **[AP-системы в CAP-теореме](../../Databases/Concepts/cap_theorem.md#ap-система-availability--partition-tolerance)**.

## Базовые концепции

### Этапы System Design интервью

1. **Сбор требований (Функциональные и Нефункциональные):**
    * **Функциональные:** Что система должна делать (например, публикация твитов, просмотр ленты, лайки, бронирование самоката, оплата).
    * **Нефункциональные:** Атрибуты качества системы — как система выполняет свои функции (например, DAU, задержка, доступность, масштабируемость, производительность, надежность).
    * **Вопросы для уточнения:**
      * Какой охват планируется? (один город или федеральная сеть)
      * Требования к реальному времени? (как часто обновлять геоданные: каждые 5 сек → WebSocket, каждые 30 сек → REST API)
      * Ожидаемое количество пользователей и рост?
      * Количество попыток при входе для блокировки пользователя?
2. **Оценка нагрузки (Back-of-the-envelope estimation):** Приблизительный подсчет ключевых метрик (RPS, трафик, объем хранения), чтобы обосновать архитектурные решения.
3. **Проектирование API:** Определение эндпоинтов и методов взаимодействия с системой (REST, gRPC, WebSocket).
4. **Схема данных:** Проектирование структуры таблиц/документов в базе данных.
5. **Высокоуровневая архитектура (High-Level Design):** Описание основных компонентов системы и их взаимодействия (микросервисы, базы данных, кэши, очереди, балансировщики нагрузки).
6. **Детальное проектирование (Deep Dive):** Детальное рассмотрение сложных частей системы (например, "проблема знаменитостей" в ленте, инвалидация кэша).
7. **Масштабирование и отказоустойчивость:** Обсуждение шардирования, репликации, балансировки нагрузки.

### Свойства систем (System Qualities)

При проектировании необходимо обеспечить следующие свойства:

1. **Масштабируемость (Scalability):** Способность системы справляться с растущей нагрузкой. Подробнее см. раздел [Масштабирование: Horizontal vs Vertical](#масштабирование-horizontal-vs-vertical).
2. **Производительность (Performance):** Минимальное время отклика и высокая пропускная способность.
    * *Пример:* Мгновенная разблокировка самоката (<3 сек).
3. **Надежность (Reliability):** Гарантия сохранности данных и корректности выполнения операций.
    * *Пример:* Информация о поездках и платежах хранится в БД с репликацией.
4. **Отказоустойчивость (Fault Tolerance):** Способность системы оставаться доступной при выходе из строя отдельных компонентов.
    * *Пример:* При падении одного дата-центра запросы перенаправляются в другой.
5. **Консистентность (Consistency):** Согласованность данных во всех узлах распределенной системы.
    * *Пример:* Если самокат арендован, он не может отображаться как свободный для других пользователей.
6. **Безопасность (Security):** Защита системы от несанкционированного доступа и утечки данных.
    * *Пример:* OAuth2, шифрование данных (AES), TLS.

### Ключевые компромиссы

При проектировании всегда приходится выбирать между противоречивыми требованиями:

* **Read-heavy vs. Write-heavy:** Системы с преобладанием чтения (например, Twitter) требуют кэширования и денормализации. Системы с частой записью (логи, метрики) требуют оптимизации под запись (LSM-деревья, очереди).
* **Consistency vs. Availability (CAP Theorem):** Выбор между строгой консистентностью и постоянной доступностью при сетевом разделении. Подробнее: **[CAP-теорема](../../Databases/Concepts/cap_theorem.md)**.
* **Latency vs. Throughput:** Минимизация времени отклика одного запроса против максимизации количества запросов в секунду.
* **Latency vs. Cost:** Снижение задержки часто требует дорогостоящей инфраструктуры (In-memory БД, CDN, NVMe).

### Архитектурные паттерны

1. **Монолит (Monolith):** Единое приложение. Просто в начале, сложно масштабировать и поддерживать при росте команды.
    * Подробнее: [Монолитная и микросервисная архитектуры](../../Concepts/monolith_vs_microservices.md).
2. **Микросервисная архитектура:** Разделение на независимые сервисы. Обеспечивает гибкость и независимое масштабирование, но усложняет эксплуатацию.
    * Подробнее: [Монолитная и микросервисная архитектуры](../../Concepts/monolith_vs_microservices.md).
3. **Бессерверная архитектура (Serverless):** Запуск кода (FaaS) без управления серверами. Оплата только за время исполнения.

### Хранение данных

Для высоконагруженных систем используется комбинация различных типов хранилищ:

1. **Реляционные БД (PostgreSQL, MySQL):** Для структурированных данных с поддержкой ACID.
   * Подробнее: [PostgreSQL Overview](../../Databases/PostgreSQL/overview.md).
2. **NoSQL БД (MongoDB, Cassandra):** Для гибких схем данных и высокой горизонтальной масштабируемости.
   * Подробнее: [SQL vs NoSQL](../../Databases/Concepts/sql_vs_nosql.md).
3. **In-memory хранилища (Redis):** Для кэширования и работы с данными в реальном времени.
   * Подробнее: [Redis Overview](../../Databases/redis_overview.md).
4. **Объектные хранилища (S3):** Для хранения медиафайлов и неструктурированных данных.

## Практические сценарии

### Проектирование ленты Twitter

#### 1. Сбор требований

* **Функциональные:** Публикация твитов, просмотр ленты подписок (обратный хронологический порядок), подписки, лайки.
* **Нефункциональные:** 100 млн DAU, задержка <2 сек на чтение, высокая доступность (99.99%), хранение данных без срока EOL.

#### 2. Оценка нагрузки

* **Запись:** ~70 твитов/сек (пик).
* **Чтение:** ~6000 запросов на ленту/сек.
* **Хранение:** ~3.6 TB текстовых данных в год + PB медиафайлов.

#### 3. Высокоуровневая архитектура (High-Level Design)

* **Media Service:** Загрузка медиафайлов в S3-хранилище.
* **Tweet Service:** Создание и хранение твитов (NoSQL).
* **Follow Service:** Управление связями между пользователями (RDBMS).
* **Timeline Service:** Формирование ленты. Использует Redis для хранения пред-сгенерированных лент.

#### 4. Детальное проектирование: "Проблема знаменитостей" (Fan-out on write)

* **Проблема:** Публикация твита пользователем с миллионами подписчиков перегружает систему при попытке обновить кэши всех подписчиков одновременно.
* **Решение (Гибридный подход):**
    1. Для обычных пользователей: **Fan-out on write** (проталкивание в кэши лент подписчиков).
    2. Для знаменитостей: **Fan-out on read** (твиты не проталкиваются, а подгружаются в момент запроса ленты подписчиком).
* **Оптимизация:** Флаг `is_following_celebrity` в профиле пользователя для быстрого принятия решения о подгрузке.

## Дополнительная информация

### Масштабирование: Horizontal vs Vertical

| Характеристика | Вертикальное (Scale Up) | Горизонтальное (Scale Out) |
| :--- | :--- | :--- |
| **Суть** | Увеличение мощности одного узла (CPU, RAM) | Добавление новых узлов в кластер |
| **Масштабируемость** | Ограничена физическим пределом железа | Практически неограниченная |
| **Надежность** | Единая точка отказа (SPOF) | Высокая отказоустойчивость |
| **Стоимость** | Растет экспоненциально | Растет линейно |
| **Сложность** | Минимальная (архитектура не меняется) | Высокая (требует балансировщика, stateless) |

### Оптимизация работы с медиафайлами

* **Очистка "мусорных" файлов:**
  * Использование временного хранилища с периодической очисткой (Background Job).
  * Подсчет ссылок (Reference Counting) для удаления неиспользуемых объектов.
* **CDN (Content Delivery Network):** Кэширование статики ближе к пользователю для снижения задержек.

### Пагинация и навигация

* **Offset-based:** Простая реализация (`LIMIT`, `OFFSET`), но медленно работает на больших объемах данных.
* **Cursor-based (Keyset):** Использование указателя на последний элемент. Быстро и стабильно при добавлении новых данных.
