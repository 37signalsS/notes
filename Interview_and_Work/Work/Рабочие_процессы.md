# Командная работа и рабочие процессы

## Определения

* **Product Owner / Product Manager:** отвечает за развитие продукта, сбор гипотез и приоритизацию фичей. Подробнее — в **[Управление продуктом и аналитика](./Управление_продуктом_и_аналитика.md)**.
* **Project Manager:** управляет командами, сроками, ресурсами и бюджетом.
* **Team Lead:** технический лидер команды. Сочетает техническую экспертизу (архитектура, ревью IaC и скриптов) и управление людьми.
* **Аналитик (Системный/Бизнес-аналитик):** связующее звено между бизнесом и технической командой; формализует требования в технические задачи.
* **Agile:** гибкая методология разработки.
* **Scrum:** фреймворк для реализации методологии Agile через итерации.
* **Kanban:** методология управления потоком задач, фокусирующаяся на визуализации и ограничении WIP (Work in Progress).
* **Sprint (Спринт):** фиксированный промежуток времени (1–2 недели) для завершения определенного функционала.
* **Story Points (Стори-поинты):** абстрактная единица оценки сложности, рисков и объема работы.
* **MVP (Minimum Viable Product):** минимально жизнеспособный продукт для сбора обратной связи с минимальными усилиями.
* **Backlog (Бэклог):** приоритезированный список задач и требований к продукту.

## Базовые концепции

### Иерархия управления в BigTech и FinTech

В крупных компаниях структура часто многоуровневая для масштабирования процессов:

1. **Линейный менеджер (Line Manager):** руководитель над несколькими командами/проектами. Занимается стратегией и бюджетами.
2. **Лид стрима (Stream Lead):** руководитель крупного технического направления (стрима), объединяющего несколько продуктов (например, «Кредитование»).
3. **Лид подстрима (Sub-stream Lead):** руководитель конкретного поднаправления (например, «Автокредитование»).
4. **Team Lead:** руководитель конкретной кросс-функциональной команды.

**Особенности работы инженера:**

* **Инженерное мышление:** участие в обсуждении бизнес-требований, а не только выполнение ТЗ.
* **Прозрачность:** доступ к коду и документации соседних отделов (часто через монорепозитории).
* **Самостоятельность:** ориентация на решение бизнес-задач, а не на трекинг часов.

### Кросс-функциональные команды

**Кросс-функциональная команда** — это автономная группа специалистов (инженеры, QA, аналитики, DevOps), обладающая всеми компетенциями для полного цикла запуска фичи.

* **Автономность:** минимизация внешних зависимостей.
* **Взаимодействие:** регулярные синхронизации через общие чаты.
* **Масштабируемость:** в микросервисной архитектуре команды обычно компактные, в монолитных проектах — более крупные.

### Мероприятия Scrum

* **Sprint Planning (Планирование):** команда оценивает задачи из бэклога и формирует план на спринт. Используется техника **Planning Poker** для анонимного голосования по сложности.
* **Daily Scrum (Дейлик):** ежедневная 15-минутная встреча для синхронизации (что сделано, что планируется, какие есть блокировщики).
* **Backlog Refinement (Груминг):** уточнение и предварительная оценка задач для будущих спринтов.
* **Sprint Review (Демо):** презентация инкремента продукта стейкхолдерам.
* **Sprint Retrospective (Ретроспектива):** анализ процессов спринта и поиск путей улучшения.

### Окружения и стенды (Environments)

Перед выпуском в Production код проходит через несколько сред:

1. **Тестовый стенд (Test/Dev):** среда для первичной проверки функционала разработчиками и QA.
2. **Предпродовый стенд (Pre-prod/Staging):** среда, максимально идентичная Production, для финального интеграционного тестирования.
3. **Production (Прод):** финальная среда, доступная пользователям.

## Практические сценарии

### Цикл работы над задачей

1. **Постановка:** задачи фиксируются в Jira (или аналогах) на основе требований аналитиков.
2. **Оценка (Estimation):**
   * **Относительная:** сравнение с эталонной «базовой задачей».
   * **В часах:** часто используется для упрощения планирования в классических структурах.
3. **Распределение:** назначение лидом или самовыдвижение разработчика на планировании.
4. **Сопровождение:** ежедневный фидбек на дейликах и переоценка рисков при необходимости.

### Гибридные процессы (Scrum + Kanban)

В DevOps-командах часто сочетаются два подхода:

* **Scrum:** для плановых задач по развитию платформы (60–70% времени).
* **Kanban:** для оперативных инцидентов и запросов поддержки (30–40% времени).

Это позволяет системно развивать инфраструктуру, сохраняя высокую скорость реакции на инциденты.

### Модели ветвления в Git

Для управления кодом используются различные стратегии:

* **Git Flow:** строгая модель с ветками `develop`, `feature`, `release` и `hotfix`.
* **Trunk-Based Development:** работа в одной основной ветке с использованием **Feature Flags**.

> Подробное сравнение моделей ветвления приведено в основном разделе: **[Рабочие процессы в Git](../../Git/git_workflows.md)**.

### Типичные проблемы процессов

* **Агрессивные эстимейты:** нереалистичные сроки без учета рисков.
* **Недостаточная формализация:** отсутствие четких критериев приемки (Acceptance Criteria).
* **Перегруженный бэклог:** затрудняет приоритизацию и фокус команды.
* **Отсутствие инфраструктуры:** проблемы с доступами и окружениями, замедляющие разработку.
