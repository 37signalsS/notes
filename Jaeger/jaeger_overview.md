# Jaeger

**Jaeger** — это распределенная система трассировки с открытым исходным кодом для мониторинга и устранения неполадок в микросервисных архитектурах. Проект CNCF, изначально разработанный в Uber.

Его основная задача — помочь разработчикам и SRE-инженерам понимать потоки выполнения запросов, выявлять узкие места производительности и анализировать задержки. Ключевые концепции, такие как Trace и Span, описаны в документе [**Концепции распределенной трассировки**](./distributed_tracing_concepts.md).

---

## Определения

### Ключевые компоненты

Архитектура Jaeger состоит из нескольких ключевых компонентов:

1.  **Jaeger Client:** Библиотека для инструментирования кода приложения. Отвечает за создание спанов и их отправку на Jaeger Agent. Современный подход — использование [OpenTelemetry SDK](../OpenTelemetry/opentelemetry_overview.md).
2.  **Jaeger Agent:** Сетевой демон, который слушает спаны, отправленные клиентами. Обычно развертывается как sidecar. Буферизует спаны и отправляет их в Collector.
3.  **Jaeger Collector:** Сервис, который принимает спаны от агентов, выполняет их валидацию, индексацию и сохраняет в хранилище.
4.  **Storage:** Бэкенд для постоянного хранения данных трассировки. Jaeger поддерживает **Elasticsearch**, **Cassandra** и другие NoSQL-решения.
5.  **Jaeger Query:** Сервис, предоставляющий API для извлечения трасс из хранилища. Используется пользовательским интерфейсом.
6.  **Jaeger UI:** Веб-интерфейс для поиска, визуализации и анализа трассировок.

## Основные концепции

### Поток данных

Типичный поток данных в Jaeger выглядит следующим образом:
1.  **Инструментированный сервис** с помощью **Jaeger Client** (или OTel SDK) создает спаны.
2.  Спаны отправляются на локальный **Jaeger Agent**.
3.  **Agent** батчами пересылает спаны в **Jaeger Collector**.
4.  **Collector** обрабатывает и сохраняет трассы в **Storage**.
5.  **Jaeger UI** через **Jaeger Query** запрашивает и отображает данные из **Storage**.

### Интеграция с OpenTelemetry

Jaeger полностью совместим со стандартом [OpenTelemetry](../OpenTelemetry/opentelemetry_overview.md). **OpenTelemetry Collector** может заменить Jaeger Agent и Collector, собирая телеметрию и отправляя ее напрямую в бэкенд Jaeger. Это позволяет унифицировать сбор данных в полиглотных системах.

### Сравнение с Grafana Tempo

Jaeger и [Grafana Tempo](../Tempo/tempo_overview.md) — ключевые решения для трассировки, но с разной философией:
*   **Индексация и поиск:** Jaeger индексирует метаданные спанов (теги), что обеспечивает мощный и гибкий поиск. Tempo индексирует только по `trace_id`, что делает его более экономичным для хранения больших объемов данных.
*   **Зависимости:** Jaeger требует внешнюю базу данных (например, Elasticsearch). Tempo опирается на объектное хранилище (S3, GCS, MinIO).
*   **Экосистема:** Jaeger имеет свой UI. Tempo тесно интегрирован с Grafana, что позволяет бесшовно коррелировать трассы с метриками и логами.

## Практические сценарии

### Анализ производительности

Представим, что пользователи жалуются на медленную обработку заказов.
1.  **Поиск:** Разработчик открывает Jaeger UI и фильтрует трассы по сервису `orders` и эндпоинту `/checkout` со статусом "error" или высокой длительностью.
2.  **Анализ:** На диаграмме Ганта для медленной трассы видно, что 90% времени занимает спан, соответствующий вызову сервиса `inventory`.
3.  **Локализация:** Дальнейший анализ показывает, что внутри `inventory` выполняется очень медленный запрос к базе данных.
4.  **Результат:** Проблема локализована. Jaeger позволил быстро найти корневую причину, не требуя последовательной отладки каждого сервиса вручную.
