# Обзор Jaeger

> **Важно:** Документация описывает **Jaeger v2**. Jaeger v1 достиг **EOL (End of Life)**.

**Jaeger** — распределенная система трассировки с открытым исходным кодом для мониторинга и устранения неполадок в микросервисных архитектурах. Проект **CNCF (Cloud Native Computing Foundation)**, изначально разработанный в Uber.

В версии v2 Jaeger претерпел фундаментальную трансформацию, став специализированным дистрибутивом **OpenTelemetry Collector**. Это обеспечило нативную поддержку протокола OTLP, упростило развертывание и расширило возможности обработки данных.

Основная задача — помочь разработчикам и **SRE-инженерам (Site Reliability Engineering)** понимать потоки выполнения запросов, выявлять узкие места производительности и анализировать сложные каскадные сбои.

## Определения

| Термин | Описание |
| :--- | :--- |
| **Распределенная трассировка** | Метод мониторинга приложений, позволяющий отслеживать путь запроса через множество микросервисов |
| **Trace (Трасса)** | Полный путь прохождения запроса через систему, состоящий из набора спанов, связанных общим идентификатором |
| **Span (Спан)** | Единица работы в рамках трассы (например, HTTP-запрос, запрос к БД). Содержит имя, время начала, длительность, теги и логи |
| **Context Propagation** | Механизм передачи идентификаторов трассировки (TraceID, SpanID) между сервисами через заголовки (например, W3C Trace Context) |
| **Baggage** | Пользовательские данные (key-value), которые передаются вместе с контекстом трассировки через все звенья цепи вызовов |
| **Сэмплирование (Sampling)** | Процесс отбора подмножества трасс для сохранения в хранилище с целью снижения нагрузки и затрат на хранение |
| **Unified Binary** | Концепция Jaeger v2, при которой один бинарный файл может выполнять роли агента, коллектора и сервиса запросов в зависимости от конфигурации |
| **W3C Trace Context** | Отраслевой стандарт для распространения контекста трассировки. Заголовок `traceparent` содержит четыре поля: `version-traceid-parentid-flags`. Гарантирует корреляцию спанов между сервисами независимо от языка программирования |
| **Span Kind** | Тип спана, определяющий его роль в распределенной системе: `Server`, `Client`, `Producer`, `Consumer`, `Internal` |
| **Span Events** | Временные метки внутри спана для фиксации атомарных действий или ошибок (например, `exception.stacktrace`, `cache.hit`) |
| **Span Links** | Связи между спанами, которые не являются родительскими. Критичны для асинхронных сценариев (Kafka, Batch), где один запрос порождает независимые ветки обработки |
| **Span Status** | Статус завершения спана: `Unset`, `Ok` (код 0) или `Error` (код 1 с описанием). Используется для автоматического обнаружения ошибок в UI |
| **Clock Skew** | Рассинхронизация времени между серверами. Приводит к искажению временной шкалы трейса: спаны могут отображаться в будущем или иметь отрицательную длительность. Требуется синхронизация через NTP/chrony |
| **Backpressure** | Механизм обработки перегрузки при переполнении буферов агента или коллектора. Спаны отбрасываются на уровне Collector; метрики `spans_dropped_total` позволяют отследить потерю видимости |

## Базовые концепции

### Трансформация в Jaeger v2

Jaeger v2 полностью базируется на фреймворке **OpenTelemetry Collector**. Это принесло следующие ключевые изменения:

*   **Нативный OTLP:** Данные обрабатываются в формате **OTLP (OpenTelemetry Protocol)** без промежуточных преобразований.
*   **Гибкие пайплайны:** Возможность использования любых стандартных процессоров OpenTelemetry (фильтрация, модификация атрибутов, батчинг) непосредственно внутри Jaeger.
*   **Единый бинарный файл:** Заменяет разрозненные компоненты v1 (Agent, Collector, Query), упрощая эксплуатацию.
*   **Расширения (Extensions):** Использование механизмов расширений OTel для интеграции с хранилищами и реализации специфичных для Jaeger функций (например, Adaptive Sampling).

### Анатомия спана и трассы

Каждый спан в модели OpenTelemetry (используемой Jaeger v2) содержит:

| Компонент | Описание | Пример |
| :--- | :--- | :--- |
| **trace_id** | Уникальный идентификатор всей трассы (16 байт). Общий для всех спанов одного запроса | `4bf92f3577b34da6a3ce929d0e0e4736` |
| **span_id** | Уникальный идентификатор спана (8 байт) | `00f067aa0ba902b7` |
| **parent_span_id** | Идентификатор родительского спана. Отсутствует у корневого спана | `00c4711b5e7a9f1a` |
| **name** | Имя операции | `POST /v1/orders` |
| **start_time / end_time** | Временные метки в наносекундах (Unix epoch) | `start=1710000000000000000` |
| **attributes** | Метаданные (ключ=значение) для фильтрации и аналитики | `http.status_code=200`, `db.system=postgresql` |
| **events** | Атомарные события внутри спана с временными метками | `exception.stacktrace`, `cache.hit` |
| **links** | Связи с другими спанами (асинхронные сценарии) | Связь producer-trace → consumer-trace |
| **status** | Результат выполнения: `Ok`, `Error`, `Unset` | `Error: connection timed out` |

Правильная типизация спанов через **Span Kind** критична для построения корректной топологии сервисов:
*   **Server:** Входящий синхронный запрос (например, HTTP-handler).
*   **Client:** Исходящий синхронный вызов (например, запрос к БД или внешнему API).
*   **Producer:** Отправка сообщения в асинхронную очередь (Kafka, RabbitMQ).
*   **Consumer:** Получение и обработка сообщения из очереди.
*   **Internal:** Внутренняя операция процесса (вызов тяжелой функции, вычисления).

### Распространение контекста (Context Propagation)

Без передачи идентификаторов между сервисами невозможно восстановить дерево вызовов. В Jaeger v2 используются два механизма:

1.  **W3C Trace Context:** Стандарт по умолчанию. Заголовок `traceparent` передается через все границы сервисов. Поддерживается всеми современными SDK OpenTelemetry.
2.  **Baggage:** Пользовательские метаданные (например, `customer_tier=gold`), передаваемые через всю цепочку вызовов в заголовках HTTP. Влияет на безопасность: данные передаются между границами доверия, поэтому в Baggage запрещено хранить секреты или чувствительные данные (PII).

**Требование к инфраструктуре:** Все посредники (Proxy, Load Balancers, Ingress-контроллеры, брокеры сообщений) должны явно пропускать заголовки `traceparent`, `tracestate` и `baggage`.

### Хранилища и бэкенды

Jaeger v2 использует расширение **Storage Extension** для интеграции с базами данных. Выбор бэкенда определяет производительность поиска, стоимость владения (TCO) и сложность эксплуатации:

| Бэкенд | Типичное применение | Особенности |
| :--- | :--- | :--- |
| **ClickHouse** | Production (рекомендуется с v2.20+) | Первоклассный гражданин (first-class citizen) в v2. Хранит миллиарды спанов с минимальными ресурсами. Лучшая производительность для аналитических запросов по сравнению с Elasticsearch. |
| **Elasticsearch / OpenSearch** | Корпоративные среды с требованиями к безопасности | Поддерживает полную индексацию атрибутов. Требует больше ресурсов (RAM/CPU) на больших объемах. |
| **Cassandra** | Legacy-системы, распределенные кластеры | Хорошо масштабируется, но уступает ClickHouse в скорости сложных запросов. |
| **Badger / In-memory** | Локальная разработка, CI/CD | Данные теряются после перезапуска. Badger — embedded LSM-tree БД, не требующая отдельного сервиса. |

**Важно:** При нагрузке выше 10,000 спанов в секунду рекомендуется архитектура с **Kafka** для буферизации и **Ingester** для асинхронной записи. Это защищает от потери данных при сбоях хранилища.

### Интеграция с Service Mesh

При использовании Istio или Linkerd необходимо обеспечить корректную передачу заголовков трассировки:
*   **W3C Trace Context (`traceparent`):** Стандарт по умолчанию для Jaeger v2 и OpenTelemetry.
*   **B3 Propagation:** Исторически использовался в Istio. Jaeger v2 может принимать B3 и конвертировать его в W3C для внутреннего хранения, но рекомендуется перевести mesh на нативный W3C.

Sidecar-инъекция Envoy автоматически добавляет атрибуты Kubernetes (имя пода, неймспейс, узел) в спаны через процессор `k8sattributes`.

### Ограничения и крайние случаи

*   **Стоимость хранения:** Бэкенды с индексацией (Elasticsearch, ClickHouse) требуют значительных ресурсов. При бюджете, ограничивающем TCO, рассмотрите **[Grafana Tempo](../Tempo/index.md)** с объектным хранилищем.
*   **Сложность Tail-based Sampling:** Требует значительного объема RAM на коллекторе для ожидания завершения всех спанов трейса (decision_wait). При memory_limiter превышении происходит отбрасывание неполных трейсов.
*   **Потеря данных при переполнении:** При превышении `send_batch_size` или недоступности Kafka/хранилища спаны отбрасываются. Мониторинг метрики `spans_dropped_total` обязателен.
*   **Clock Skew:** В распределенных системах без синхронизации NTP временные метки разных сервисов могут расходиться. Jaeger UI корректирует смещение, но точность ограничена.
*   **Ограничения поиска в UI:** Jaeger v2 не поддерживает язык запросов уровня TraceQL (в отличие от Tempo). Поиск ограничен фильтрацией по тегам, сервисам и операциям.

## Стратегии сэмплирования в v2

Jaeger v2 поддерживает расширенные методы управления объемом данных:

1.  **Head-based:** Решение принимается в начале трассы (на стороне SDK или первого коллектора). Самый дешевый способ с точки зрения ресурсов.
2.  **Adaptive (Адаптивное):** Система автоматически подстраивает частоту сэмплирования для каждого сервиса и операции, чтобы достичь целевого количества трасс в секунду (настраивается через `sampling` extension).
3.  **Tail-based:** Решение принимается после завершения всей трассы на основе ее характеристик (наличие ошибок, высокая задержка). Реализуется через стандартный `tailsamplingprocessor`.

| Стратегия | Где принимается решение | Плюсы | Минусы | Рекомендуемое применение |
| :--- | :--- | :--- | :--- | :--- |
| **Head-based** | SDK / первый Collector | Минимальные ресурсы, простота | Потеря редких, но важных трейсов | Локальная разработка, стабильные сервисы с низким RPS |
| **Adaptive** | Collector (extension) | Автоматическая балансировка объема данных | Требует настройки целевых метрик, сложнее в отладке | Production-среды с переменной нагрузкой |
| **Tail-based** | Collector (tailsamplingprocessor) | 100% ошибок и медленных запросов | Высокое потребление RAM, задержка до решения (decision_wait) | High-load системы, где стоимость потери аномалий выше стоимости хранилища |

### Сравнение с Grafana Tempo

Jaeger и **[Grafana Tempo](../Tempo/index.md)** — ключевые решения для трассировки, различающиеся архитектурным подходом:

| Критерий | Jaeger | Grafana Tempo |
| :--- | :--- | :--- |
| **Индексация** | Индексирует метаданные спанов (теги). Позволяет выполнять мощный поиск по произвольным атрибутам в UI | Индексирует минимальный набор данных. Поиск осуществляется в основном по `trace_id` или через TraceQL |
| **Хранение** | Требует внешнюю БД с поддержкой индексации (Elasticsearch, Cassandra, ClickHouse) | Опирается на дешевое объектное хранилище (S3, GCS, Azure Blob) |
| **Поиск и UI** | Развитый собственный интерфейс с графами зависимостей и сравнением трасс | Тесная интеграция с Grafana, использование корреляции с метриками и логами |
| **Язык запросов** | Фильтрация по тегам, сервисам и операциям | TraceQL (мощный поиск по атрибутам, метрикам и статусам) |
| **Стоимость (TCO)** | Высокая из-за накладных расходов на БД | Минимальная (RF1, объектное хранилище) |
| **Генерация метрик** | Span Metrics через процессоры OTel | TraceQL Metrics (динамически, без предварительной настройки) |

### Возможности визуализации в Jaeger UI

*   **Timeline Diagram (Gantt Chart):** Визуализация критического пути запроса и задержек в каждом компоненте.
*   **Dependency Graph:** Автоматически генерируемая карта связей между микросервисами на основе накопленных трасс.
*   **Trace Comparison:** Инструмент для сравнения двух трасс, помогающий выявить причины регрессий производительности.
*   **Deep Dependency Graph:** Углубленный анализ графа вызовов для понимания косвенных зависимостей.
*   **Trace Statistics:** Агрегированная статистика по типам спанов и сервисам внутри одного трейса, помогающая быстро найти компоненты с наибольшим вкладом в задержку.
*   **Side Panel Details:** Детали спана (теги, логи, метаданные) открываются в боковой панели, не перекрывая временную шкалу трейса.

## Практические сценарии

### Сценарий 1: Диагностика критического пути (Critical Path)

**Ситуация:** Сервис `api-gateway` показывает высокую задержку, но логи не указывают на конкретный сбой.

| Шаг | Действие | Результат |
| :--- | :--- | :--- |
| **1** | В **Jaeger UI** найти трассы для `api-gateway` с максимальной длительностью | Список подозрительных запросов |
| **2** | Открыть трассу и найти спаны, занимающие большую часть временной шкалы | Выявление сервиса-виновника (например, `auth-service`) |
| **3** | Анализ тегов спана `auth-service` | Обнаружен атрибут `db.statement` с долгим запросом к LDAP |
| **4** | Решение | Добавление кэширования ответов LDAP в `auth-service` |

### Сценарий 2: Поиск причин ошибок через распределенный контекст

**Ситуация:** Клиент получает ошибку 500. В логах входного шлюза пусто, ошибка происходит глубоко в цепочке вызовов.

| Шаг | Действие | Результат |
| :--- | :--- | :--- |
| **1** | Поиск в Jaeger по тегу `error=true` и временному интервалу | Нахождение соответствующей трассы |
| **2** | Переход к самому глубокому спану, помеченному красным цветом | Локализация сервиса, где возникло исключение |
| **3** | Просмотр раздела **Logs/Events** внутри спана | Чтение Stack Trace и сообщения об ошибке (например, `Connection timeout`) |
| **4** | Анализ Baggage (если используется) | Проверка пользовательских метаданных, которые могли повлиять на логику обработки |

### Сценарий 3: Локальная валидация инструментирования через Docker Compose

**Ситуация:** Необходимо быстро проверить, что приложение отправляет спаны в правильном формате, без развертывания production-инфраструктуры.

```yaml
# compose.yml
services:
  jaeger:
    image: jaegertracing/jaeger:2.0
    ports:
      - "16686:16686" # UI и Query API
      - "4317:4317"   # OTLP gRPC (основной порт для v2)
      - "4318:4318"   # OTLP HTTP
    environment:
      - SPAN_STORAGE_TYPE=memory
      - METRICS_STORAGE_TYPE=prometheus
```

**Валидация:**

1.  Отправить тестовый спан из приложения на `localhost:4317` (gRPC) или `localhost:4318` (HTTP).
2.  Открыть `http://localhost:16686` и убедиться, что сервис отображается в выпадающем списке.
3.  Выполнить поиск по `service=имя-сервиса` и проверить, что спан содержит корректные атрибуты (`http.method`, `http.status_code`).

**Ожидаемый результат:** Трасса появляется в UI в течение 1–2 секунд после отправки. При использовании in-memory хранилища данные исчезают после перезапуска контейнера.

### Сценарий 4: Настройка Tail-based Sampling для захвата аномалий

**Ситуация:** При нагрузке 5,000 RPS нужно сохранять 100% ошибок и всех запросов дольше 2 секунд, для остального трафика — сэмплировать 1%.

```yaml
# collector-config.yaml
receivers:
  otlp:
    protocols:
      grpc:
      http:

processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 512
  batch:
  tail_sampling:
    decision_wait: 10s
    num_traces: 1000
    policies:
      - name: sample-errors
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: sample-slow-traces
        type: latency
        latency: {threshold_ms: 2000}
      - name: sample-probabilistic
        type: probabilistic
        probabilistic: {sampling_percentage: 1}

exporters:
  jaeger_storage_exporter:
    trace_storage:
      type: clickhouse
      options:
        clickhouse:
          endpoint: "tcp://clickhouse:9000"
          database: jaeger_v2

service:
  extensions: [jaeger_storage]
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, tail_sampling, batch]
      exporters: [jaeger_storage_exporter]
```

**Валидация:**

```bash
# 1. Вызвать ошибку в приложении и убедиться, что трейс сохранен
curl -X POST http://app:8080/fail

# 2. Вызвать задержку >2s и убедиться в сохранении
curl -X POST http://app:8080/slow

# 3. Проверить метрики коллектора на корректную работу Tail-sampling
curl http://jaeger-collector:8888/metrics | grep processor_tail_sampling
# → processor_tail_sampling_sampling_decision_latency_count{policy="sample-errors"} 1
# → processor_tail_sampling_traces_seen{policy="sample-errors"} 1
```

### Типичные проблемы и устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Разорванные трейсы** | Отсутствие передачи заголовков `traceparent` в одном из узлов | Проверить наличие Propagators в SDK всех сервисов. Проверить конфигурацию Ingress/Proxy (должны пропускать заголовки) |
| **Clock Skew (Сдвиг времени)** | Рассинхронизация NTP на разных серверах | Спаны могут отображаться в будущем или иметь отрицательную длительность. Требуется синхронизация через `chrony` или `systemd-timesyncd` |
| **Высокая нагрузка на сеть** | Слишком большой объем атрибутов или отсутствие сжатия | Использовать OTLP/Arrow. Ограничить размер атрибутов (не писать полные тела запросов/ответов в теги) |
| **Missing Spans (Пропуски)** | Переполнение буфера (Backpressure) | Увеличить `send_batch_size` в коллекторе, проверить метрики `spans_dropped_total` и доступность Kafka/хранилища |
| **Дублирование спанов** | Несколько инстансов Collector отправляют данные в одно хранилище без идемпотентности | Включить дедупликацию на уровне хранилища или использовать Kafka с ключом `trace_id` |
| **Медленный поиск в UI** | Отсутствие индексов при росте объема данных в ClickHouse/Elasticsearch | Настроить TTL на старые трейсы, добавить индексы по часто используемым тегам (`service_name`, `operation_name`) |

### Лучшие практики и очистка

1.  **Семантические конвенции:** Используйте стандартные атрибуты OpenTelemetry (`http.method`, `http.status_code`, `db.system`) вместо кастомных имен. Это обеспечивает совместимость с Jaeger UI, Tempo и автоматическими дашбордами.
2.  **OTLP везде:** Используйте порты 4317 (gRPC) и 4318 (HTTP) как единственные точки входа для трейсов. Устаревшие порты Jaeger (14268, 14250) оставьте только для обратной совместимости.
3.  **Очистка окружения после тестов:**
    ```bash
    # Остановка Docker Compose
    docker compose down

    # Удаление volumes с чувствительными данными
    docker volume rm jaeger_data

    # Очистка in-memory данных (перезапуск контейнера)
    docker restart jaeger
    ```
4.  **Мониторинг самого Jaeger:** Настройте алерты на метрики `jaeger_processor_spans_success_total` (прием данных) и `jaeger_span_store_write_errors_total` (ошибки записи). Отсутствие спанов в хранилище часто является результатом падения экспортера, а не проблем в инструментации приложений.
