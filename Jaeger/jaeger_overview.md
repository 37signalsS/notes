# Обзор Jaeger

> **Важно:** Документация описывает **Jaeger v2** (текущая версия). Jaeger v1 достиг **EOL (End of Life)**.

**Jaeger** — распределенная система трассировки с открытым исходным кодом для мониторинга и устранения неполадок в микросервисных архитектурах. Проект **CNCF (Cloud Native Computing Foundation)**, изначально разработанный в Uber.

В версии v2 Jaeger претерпел фундаментальную трансформацию, став специализированным дистрибутивом **OpenTelemetry Collector**. Это обеспечило нативную поддержку протокола OTLP, упростило развертывание и расширило возможности обработки данных.

Основная задача — помочь разработчикам и **SRE-инженерам (Site Reliability Engineering)** понимать потоки выполнения запросов, выявлять узкие места производительности и анализировать сложные каскадные сбои.

---

## Определения

| Термин | Описание |
| :--- | :--- |
| **Распределенная трассировка** | Метод мониторинга приложений, позволяющий отслеживать путь запроса через множество микросервисов |
| **Trace (Трасса)** | Полный путь прохождения запроса через систему, состоящий из набора спанов, связанных общим идентификатором |
| **Span (Спан)** | Единица работы в рамках трассы (например, HTTP-запрос, запрос к БД). Содержит имя, время начала, длительность, теги и логи |
| **Context Propagation** | Механизм передачи идентификаторов трассировки (`TraceID`, `SpanID`) между сервисами через заголовки (например, W3C Trace Context) |
| **Baggage** | Пользовательские данные (key-value), которые передаются вместе с контекстом трассировки через все звенья цепи вызовов |
| **Сэмплирование (Sampling)** | Процесс отбора подмножества трасс для сохранения в хранилище с целью снижения нагрузки и затрат на хранение |

## Базовые концепции

### Архитектура Jaeger v2

Jaeger v2 полностью базируется на фреймворке **OpenTelemetry Collector**. Ключевые особенности и возможности:

*   **Происхождение:** Изначально разработан в Uber Technologies для мониторинга сложных распределенных систем.
*   **Единый бинарный файл:** В отличие от v1, где были отдельные компоненты (Agent, Collector, Query), v2 поставляется в виде одного файла `jaeger`.
*   **Распределенное распространение контекста (Distributed Context Propagation):** Позволяет отслеживать запросы через множество границ сервисов.
*   **Поддержка хранилищ:** Совместимость с различными бэкендами для хранения трасс, включая Cassandra, Elasticsearch и Kafka.
*   **Интеграция:** Поддержка множества фреймворков и библиотек для инструментирования приложений.
*   **Нативный OTLP:** Данные обрабатываются в формате **OTLP (OpenTelemetry Protocol)** без промежуточных преобразований.

### Стратегии сэмплирования

Jaeger поддерживает три основных типа сэмплирования:

1.  **Head-based:** Решение принимается в начале трассы (например, сохранять 1% запросов). Самый экономичный метод.
2.  **Adaptive:** Система автоматически подстраивает частоту сэмплирования для каждого сервиса, чтобы достичь целевого количества трасс в секунду.
3.  **Tail-based:** Решение принимается после завершения всей трассы. Позволяет гарантированно сохранять трассы с ошибками или высокой задержкой, отбрасывая успешные "быстрые" запросы.

### Сравнение версий

| Характеристика | Jaeger v1 | Jaeger v2 |
| :--- | :--- | :--- |
| **Основа** | Кастомная архитектура | OpenTelemetry Collector Framework |
| **Формат данных** | Внутренняя модель Jaeger | Native OTLP |
| **Развертывание** | Множество бинарных файлов | Единый бинарный файл |
| **Управление в K8s** | Jaeger Operator | OpenTelemetry Operator (рекомендуется) |
| **Сэмплирование** | Head-based, Adaptive | Head, Adaptive, Tail-based |

### Сравнение с Grafana Tempo

Jaeger и **[Grafana Tempo](../Tempo/index.md)** — ключевые решения для трассировки с разной философией:

| Критерий | Jaeger | Grafana Tempo |
| :--- | :--- | :--- |
| **Индексация и поиск** | Индексирует метаданные спанов (теги). Мощный и гибкий поиск в UI | Индексирует только по `trace_id`. Экономичен для огромных объемов |
| **Зависимости** | Требует внешнюю БД (Elasticsearch, Cassandra, ClickHouse) | Опирается на объектное хранилище (S3, GCS, Azure Blob) |
| **Интеграция** | Имеет развитый собственный **UI (User Interface)** | Тесно интегрирован с Grafana для корреляции с метриками и логами |

## Практические сценарии

### Сценарий 1: Анализ задержек (Latency)

**Ситуация:** Пользователи жалуются на медленную обработку заказов.

| Шаг | Действие | Результат |
| :--- | :--- | :--- |
| **1** | В **Jaeger UI** отфильтровать трассы по сервису `orders` и эндпоинту `/checkout` с длительностью > 2с | Список аномально медленных запросов |
| **2** | Открыть диаграмму Ганта для выбранной трассы | Визуально видно, что 90% времени занимает спан сервиса `inventory` |
| **3** | Изучить детали спана `inventory` | Обнаружен медленный SQL-запрос. В тегах спана виден сам текст запроса |
| **4** | Исправление | Оптимизация индекса в БД или добавление кэширования |

### Сценарий 2: Поиск причин ошибок (Root Cause Analysis)

**Ситуация:** Сервис возвращает HTTP 500, логи разрознены и не дают полной картины.

| Шаг | Действие | Результат |
| :--- | :--- | :--- |
| **1** | Поиск в Jaeger по тегу `error=true` для проблемного сервиса | Список трасс, завершившихся ошибкой |
| **2** | Переход к самому глубокому спану в цепочке, помеченному красным | Обнаружен сервис-источник ошибки (например, `payment-gateway`) |
| **3** | Просмотр раздела **Logs** (Events) внутри спана | Виден Stack Trace исключения или детали сообщения об ошибке от API |
| **4** | Анализ тегов | Тег `http.status_code=402` указывает на проблемы с балансом клиента в сторонней системе |
