# Обзор Jaeger

> **Важно:** Документация описывает **Jaeger v2**. Jaeger v1 достиг **EOL (End of Life)**.

**Jaeger** — распределенная система трассировки с открытым исходным кодом для мониторинга и устранения неполадок в микросервисных архитектурах. Проект **CNCF (Cloud Native Computing Foundation)**, изначально разработанный в Uber.

В версии v2 Jaeger претерпел фундаментальную трансформацию, став специализированным дистрибутивом **OpenTelemetry Collector**. Это обеспечило нативную поддержку протокола OTLP, упростило развертывание и расширило возможности обработки данных.

Основная задача — помочь разработчикам и **SRE-инженерам (Site Reliability Engineering)** понимать потоки выполнения запросов, выявлять узкие места производительности и анализировать сложные каскадные сбои.

---

## Определения

| Термин | Описание |
| :--- | :--- |
| **Распределенная трассировка** | Метод мониторинга приложений, позволяющий отслеживать путь запроса через множество микросервисов |
| **Trace (Трасса)** | Полный путь прохождения запроса через систему, состоящий из набора спанов, связанных общим идентификатором |
| **Span (Спан)** | Единица работы в рамках трассы (например, HTTP-запрос, запрос к БД). Содержит имя, время начала, длительность, теги и логи |
| **Context Propagation** | Механизм передачи идентификаторов трассировки (TraceID, SpanID) между сервисами через заголовки (например, W3C Trace Context) |
| **Baggage** | Пользовательские данные (key-value), которые передаются вместе с контекстом трассировки через все звенья цепи вызовов |
| **Сэмплирование (Sampling)** | Процесс отбора подмножества трасс для сохранения в хранилище с целью снижения нагрузки и затрат на хранение |
| **Unified Binary** | Концепция Jaeger v2, при которой один бинарный файл может выполнять роли агента, коллектора и сервиса запросов в зависимости от конфигурации |

## Базовые концепции

### Трансформация в Jaeger v2

Jaeger v2 полностью базируется на фреймворке **OpenTelemetry Collector**. Это принесло следующие ключевые изменения:

*   **Нативный OTLP:** Данные обрабатываются в формате **OTLP (OpenTelemetry Protocol)** без промежуточных преобразований.
*   **Гибкие пайплайны:** Возможность использования любых стандартных процессоров OpenTelemetry (фильтрация, модификация атрибутов, батчинг) непосредственно внутри Jaeger.
*   **Единый бинарный файл:** Заменяет разрозненные компоненты v1 (Agent, Collector, Query), упрощая эксплуатацию.
*   **Расширения (Extensions):** Использование механизмов расширений OTel для интеграции с хранилищами и реализации специфичных для Jaeger функций (например, Adaptive Sampling).

### Стратегии сэмплирования в v2

Jaeger v2 поддерживает расширенные методы управления объемом данных:

1.  **Head-based:** Решение принимается в начале трассы (на стороне SDK или первого коллектора). Самый дешевый способ с точки зрения ресурсов.
2.  **Adaptive (Адаптивное):** Система автоматически подстраивает частоту сэмплирования для каждого сервиса и операции, чтобы достичь целевого количества трасс в секунду (настраивается через `sampling` extension).
3.  **Tail-based:** Решение принимается после завершения всей трассы на основе ее характеристик (наличие ошибок, высокая задержка). Реализуется через стандартный `tailsamplingprocessor`.

### Сравнение с Grafana Tempo

Jaeger и **[Grafana Tempo](../Tempo/index.md)** — ключевые решения для трассировки, различающиеся архитектурным подходом:

| Критерий | Jaeger | Grafana Tempo |
| :--- | :--- | :--- |
| **Индексация** | Индексирует метаданные спанов (теги). Позволяет выполнять мощный поиск по произвольным атрибутам в UI | Индексирует минимальный набор данных. Поиск осуществляется в основном по `trace_id` или через TraceQL |
| **Хранение** | Требует внешнюю БД с поддержкой индексации (Elasticsearch, Cassandra, ClickHouse) | Опирается на дешевое объектное хранилище (S3, GCS, Azure Blob) |
| **Поиск и UI** | Развитый собственный интерфейс с графами зависимостей и сравнением трасс | Тесная интеграция с Grafana, использование корреляции с метриками и логами |

### Возможности визуализации в Jaeger UI

*   **Timeline Diagram (Gantt Chart):** Визуализация критического пути запроса и задержек в каждом компоненте.
*   **Dependency Graph:** Автоматически генерируемая карта связей между микросервисами на основе накопленных трасс.
*   **Trace Comparison:** Инструмент для сравнения двух трасс, помогающий выявить причины регрессий производительности.
*   **Deep Dependency Graph:** Углубленный анализ графа вызовов для понимания косвенных зависимостей.

## Практические сценарии

### Сценарий 1: Диагностика критического пути (Critical Path)

**Ситуация:** Сервис `api-gateway` показывает высокую задержку, но логи не указывают на конкретный сбой.

| Шаг | Действие | Результат |
| :--- | :--- | :--- |
| **1** | В **Jaeger UI** найти трассы для `api-gateway` с максимальной длительностью | Список подозрительных запросов |
| **2** | Открыть трассу и найти спаны, занимающие большую часть временной шкалы | Выявление сервиса-виновника (например, `auth-service`) |
| **3** | Анализ тегов спана `auth-service` | Обнаружен атрибут `db.statement` с долгим запросом к LDAP |
| **4** | Решение | Добавление кэширования ответов LDAP в `auth-service` |

### Сценарий 2: Поиск причин ошибок через распределенный контекст

**Ситуация:** Клиент получает ошибку 500. В логах входного шлюза пусто, ошибка происходит глубоко в цепочке вызовов.

| Шаг | Действие | Результат |
| :--- | :--- | :--- |
| **1** | Поиск в Jaeger по тегу `error=true` и временному интервалу | Нахождение соответствующей трассы |
| **2** | Переход к самому глубокому спану, помеченному красным цветом | Локализация сервиса, где возникло исключение |
| **3** | Просмотр раздела **Logs/Events** внутри спана | Чтение Stack Trace и сообщения об ошибке (например, `Connection timeout`) |
| **4** | Анализ Baggage (если используется) | Проверка пользовательских метаданных, которые могли повлиять на логику обработки |
