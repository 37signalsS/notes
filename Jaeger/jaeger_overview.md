# Jaeger

## Определения

**Jaeger** — это распределенная система трассировки (distributed tracing system) с открытым исходным кодом, предназначенная для мониторинга и устранения неполадок в сложных микросервисных архитектурах. Изначально разработанный компанией Uber Technologies и выпущенный в опенсорс в 2017 году, Jaeger стал инкубируемым проектом Cloud Native Computing Foundation (CNCF).

Система помогает разработчикам и операторам понимать потоки выполнения запросов между множеством сервисов, выявлять узкие места производительности, анализировать задержки и отлаживать распределенные транзакции.

## Основные концепции

* **Трассировка (Trace):** Представляет собой полный жизненный цикл одного запроса или транзакции, проходящего через различные сервисы. Трассировка состоит из одного или нескольких спанов.
* **Спан (Span):** Фундаментальная единица работы. Спан представляет собой одну операцию, например, HTTP-вызов или запрос к базе данных. Каждый спан имеет имя, время начала, длительность и теги (контекст). Спаны формируют иерархическую структуру (родитель-потомок).
* **Контекст трассировки (Trace Context):** Информация (`trace_id`, `span_id`), которая передается между сервисами (обычно через HTTP-заголовки) для связывания спанов в одну трассировку.

### Архитектура

1. **Jaeger Client (Клиент Jaeger):**

    * **Описание:** Библиотеки для инструментирования приложений на различных языках программирования (Go, Java, Python, Node.js, C++ и др.).
    * **Функция:** Создают спаны, устанавливают контекст трассировки и передают его между сервисами, а затем отправляют собранные спаны на Jaeger Agent или Collector.
    * **Стандарт:** Изначально использовал OpenTracing API, но активно переходит на поддержку [OpenTelemetry](../OpenTelemetry/opentelemetry_overview.md) в соответствии с новыми стандартами.

2. **Jaeger Agent (Агент Jaeger):**

    * **Описание:** Сетевой демон, который обычно запускается как sidecar-контейнер рядом с приложением (например, в Kubernetes) или как локальный процесс на хосте.
    * **Функция:** Принимает спаны от Jaeger Client, буферизует их, выполняет локальную обработку (например, сэмплирование) и пересылает их на Jaeger Collector.
    * **Преимущества:** Снижает нагрузку на клиентские библиотеки и инкапсулирует логику отправки данных.

3. **Jaeger Collector (Коллектор Jaeger):**

    * **Описание:** Серверный компонент, который получает трассировки от агентов (или напрямую от клиентов), выполняет валидацию, обработку, индексацию и сохраняет их в постоянное хранилище.
    * **Функция:** Может быть развернут в нескольких экземплярах для обеспечения высокой доступности и масштабируемости.

4. **Storage (Хранилище):**

    * **Описание:** Jaeger поддерживает различные бэкенды для хранения трассировок.
    * **Примеры:** Elasticsearch, Cassandra, Kafka (как промежуточный буфер), Badger (для небольших инсталляций). В отличие от реляционных баз данных, Jaeger использует NoSQL-решения, оптимизированные для больших объемов данных.

5. **Jaeger Query (Сервис запросов):**

    * **Описание:** Серверный компонент, который предоставляет API для извлечения трассировок из хранилища.
    * **Функция:** Отвечает на запросы UI или внешних инструментов для поиска и отображения трассировок.

6. **Jaeger UI (Пользовательский интерфейс):**

    * **Описание:** Веб-интерфейс для поиска, просмотра и анализа трассировок. Написан на React.
    * **Функция:** Позволяет визуализировать трассировки в виде "диаграмм Ганта" (Gantt chart), показывать временные рамки, зависимости между спанами, атрибуты и логи.

## Практические сценарии

### Анализ производительности в микросервисной архитектуре

Представим систему, где запрос пользователя проходит через несколько сервисов: `Frontend` -> `API Gateway` -> `Auth Service` -> `Order Service` -> `Database`.

1. **Проблема:** Пользователи жалуются на медленную обработку заказов.
2. **Действие:**
    * Разработчик открывает Jaeger UI и ищет трассировки, связанные с эндпоинтом создания заказа.
    * Он находит медленную трассировку и видит ее визуализацию в виде диаграммы Ганта.
3. **Анализ:**
    * На диаграмме видно, что спан, соответствующий вызову `Order Service`, занимает 90% времени всей операции.
    * Развернув спаны внутри `Order Service`, разработчик обнаруживает, что долгий запрос к `Database` является причиной задержки.
4. **Результат:** Проблема локализована. Теперь можно оптимизировать либо сам запрос к базе данных, либо структуру данных. Jaeger позволил быстро найти узкое место, не требуя последовательной отладки каждого сервиса.

## Дополнительная информация

### Интеграция с OpenTelemetry

Мир трассировки активно переходит на стандарт [OpenTelemetry](../OpenTelemetry/opentelemetry_overview.md). Jaeger полностью совместим с ним: OpenTelemetry Collector может использоваться для сбора данных и их последующей отправки в бэкенд Jaeger. Это позволяет использовать единый стандарт для инструментирования приложений, оставляя свободу в выборе бэкенда для хранения и анализа трасс.

### Сравнение с Grafana Tempo

Jaeger и [Grafana Tempo](../Tempo/tempo_overview.md) — конкурирующие решения.

* **Архитектура и хранение:** Tempo оптимизировано для хранения огромных объемов трассировок в объектных хранилищах (S3, MinIO), что делает его более экономичным. Jaeger использует индексирующие хранилища (Elasticsearch, Cassandra), что обеспечивает более гибкий поиск.
* **Поиск:** Tempo находит трассировки в основном по их `trace_id`. Jaeger позволяет выполнять поиск по тегам и атрибутам спанов, что упрощает отладку.
* **Интерфейс:** Jaeger имеет собственный UI. Tempo интегрируется с Grafana, позволяя коррелировать трассировки с метриками и логами в едином интерфейсе.
