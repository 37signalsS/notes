# Архитектура Jaeger

> **Важно:** Документация описывает **Jaeger v2**. Jaeger v1 достиг EOL.

**Архитектура Jaeger v2** — спроектирована на базе OpenTelemetry Collector, что обеспечивает унификацию пайплайнов телеметрии и интеграцию с экосистемой OpenTelemetry.

Общий обзор компонентов: **[Jaeger Overview](./jaeger_overview.md)**.

---

## Определения

| Компонент | Назначение |
| :--- | :--- |
| **OpenTelemetry Collector** | Основной компонент сбора v2. Заменяет Jaeger Agent + Collector из v1. Принимает данные в форматах OTLP, Jaeger, Zipkin |
| **Jaeger Collector (v2)** | Специализированный OTel Collector с возможностями для работы с данными Jaeger. Выполняет валидацию, обогащение, экспорт |
| **Kafka** | Опциональный буфер для сглаживания пиковых нагрузок между Collector и Ingester |
| **Jaeger Ingester** | Сервис для чтения данных из Kafka и записи в хранилище. Используется при наличии Kafka |
| **Storage** | Бэкенд для долговременного хранения трасс: Elasticsearch, OpenSearch, Cassandra, ClickHouse (v2), Badger (all-in-one) |
| **Jaeger Query** | Statelesss-сервис, предоставляющий API для извлечения трасс из хранилища |
| **Jaeger UI** | Веб-интерфейс для поиска, визуализации и анализа трассировок |
| **Jaeger Spark Dependencies** | Spark-задание для построения графа зависимостей сервисов. В Kubernetes развертывается как `CronJob` |

## Базовые концепции

### Поток данных

Стандартный путь прохождения трассировки в Jaeger v2:

`Приложение (OTel SDK) → OTel Collector → [Kafka → Ingester] → Storage → Query/UI`

1. **Приложение**, инструментированное с помощью OpenTelemetry SDK, создает спаны.
2. Спаны отправляются в **OpenTelemetry Collector** — основной компонент сбора в v2.
3. Collector выполняет валидацию, обработку и экспорт в хранилище. Для высоких нагрузок используется **[Kafka](../Kafka/kafka_overview.md)** как буфер между Collector и Ingester.
4. **Ingester** считывает данные из Kafka и записывает в хранилище.
5. **UI** через **Query** запрашивает данные из **Storage** для визуализации.

### Детальный обзор компонентов

**OpenTelemetry Collector** — легковесный, расширяемый компонент, поддерживающий множество форматов входных данных. Разворачивается как DaemonSet или sidecar в Kubernetes.

**Kafka** используется как централизованный буфер для сглаживания пиковых нагрузок. Collector отправляет данные в Kafka, что отделяет процесс приема данных от процесса записи в хранилище, повышая отказоустойчивость.

**Jaeger Ingester** считывает данные из Kafka и надежно записывает их в постоянное хранилище. Активно используется в v2 при наличии Kafka.

**Storage** — выбор хранилища является ключевым архитектурным решением:

* **Elasticsearch / OpenSearch** — обеспечивают мощный поиск по метаданным (тегам). OpenSearch — полностью открытый форк Elasticsearch.
* **Cassandra** — гарантирует высокую пропускную способность на запись.
* **ClickHouse** — новая опция в v2. Открытая колоночная база данных, оптимизированная для OLAP-нагрузок. Отличается высокой эффективностью при больших объемах трассировок.
* **Badger** — локальное хранилище, используется только в режиме `all-in-one`.

**Jaeger Query & UI** — Query предоставляет API для извлечения и анализа трасс из хранилища. UI использует Query API для визуализации данных.

**Jaeger Spark Dependencies** — отдельное Spark-задание для построения графа зависимостей сервисов. Периодически запускается, анализирует сохраненные спаны в хранилище и агрегирует информацию о вызовах между сервисами. Результаты сохраняются в отдельный индекс.

### Стратегии сэмплирования

Подробное описание стратегий сэмплирования: **[Traces Deep Dive](../Concepts/Observability_and_Monitoring/traces_deep_dive.md#сэмплирование-sampling)**.

| Стратегия | Описание |
| :--- | :--- |
| **Head-based Sampling** | Решение о сохранении трассы принимается на стороне клиента (в SDK или агенте) до завершения трассы. Простой и дешевый метод, но может пропустить редкие или ошибочные трассы |
| **Tail-based Sampling** | Решение принимается после сбора всех спанов трассы (обычно в OpenTelemetry Collector). Позволяет гарантированно сохранять все ошибочные или медленные трассы, но требует больше ресурсов для буферизации |
| **Remote Sampling** | Collector централизованно предоставляет агентам конфигурацию сэмплирования, что позволяет динамически управлять им без перезапуска приложений |

### Хранилище и производительность

Для обеспечения высокой производительности и надежности в Jaeger используются следующие подходы:

| Механизм | Назначение |
| :--- | :--- |
| **Батчинг** | Спаны группируются в батчи на уровне агента и коллектора для снижения накладных расходов |
| **Очереди** | Kafka используется для буферизации пиков и разделения процессов приема и записи |
| **Масштабирование** | Collector и Query являются stateless-сервисами и легко масштабируются горизонтально |
| **Управление данными** | Для хранилищ применяются политики TTL (Time-To-Live) для автоматического удаления старых данных |

### Сравнение архитектур бэкендов

Выбор бэкенда для хранения и визуализации трейсов определяет архитектуру всего пайплайна сбора данных.

**Классическая архитектура с Jaeger:**

* **Пайплайн:** `Приложение -> Jaeger Agent -> Jaeger Collector -> Бэкенд (напр., Elasticsearch)`
* **Компоненты:**
  * `Jaeger Agent` — `DaemonSet`, работающий на каждой ноде для приема спанов по UDP.
  * `Jaeger Collector` — центральный компонент, который валидирует, обрабатывает и сохраняет трейсы в хранилище.
  * `Jaeger UI` — интерфейс для запросов и визуализации.
* **Принцип работы:** Jaeger-клиент в приложении отправляет спаны агенту, который перенаправляет их в коллектор для сохранения. Jaeger UI напрямую читает данные из того же бэкенда.

**Архитектура с OpenSearch Observability:**

* **Пайплайн:** `Приложение -> OTLP Collector -> Data Prepper -> OpenSearch`
* **Принцип работы:** Этот подход используется, когда бэкенд (в данном случае плагин OpenSearch Observability) требует данные в определенном формате (OTLP), несовместимом с нативным форматом хранения Jaeger.
* **Компоненты:**
  * `OTLP Collector` — заменяет `Jaeger Agent` и `Collector`. Принимает данные в разных форматах (включая Jaeger) и экспортирует их в OTLP.
  * `Data Prepper` — компонент OpenSearch, который принимает данные в OTLP, обрабатывает их и сохраняет в формате, понятном для дашбордов Observability.

**Пользовательский опыт (UX):**
Помимо архитектурных различий, важен и пользовательский опыт взаимодействия с UI. По субъективным оценкам, интерфейс **Jaeger UI** часто считается более интуитивным для анализа трейсов (в частности, благодаря двумерной диаграмме для поиска трейсов по времени и задержке) по сравнению с дашбордами **OpenSearch Observability**, которые могут показаться менее привычными.

## Практические сценарии

### Конфигурация OpenTelemetry Collector для Jaeger

Минимальный пример конфигурации OpenTelemetry Collector для приема OTLP-данных и экспорта в Jaeger:

```yaml
receivers:
  otlp:
    protocols:
      http:
      grpc:

processors:
  batch:

exporters:
  jaeger:
    endpoint: jaeger-collector:14250
    tls:
      insecure: true

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [jaeger]
```
