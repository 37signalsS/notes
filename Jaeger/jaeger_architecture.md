# Архитектура Jaeger

> **Важно:** Документация описывает **Jaeger v2**. Jaeger v1 достиг **EOL (End of Life)**.

**Архитектура Jaeger v2** спроектирована как нативное расширение **OpenTelemetry Collector**. Это означает, что компоненты Jaeger теперь интегрированы непосредственно в бинарный файл OpenTelemetry, что обеспечивает унификацию пайплайнов телеметрии, нативную поддержку протокола OTLP и бесшовную интеграцию с экосистемой OpenTelemetry.

Общий обзор возможностей системы: **[Обзор Jaeger](./jaeger_overview.md)**.

---

## Определения

| Компонент | Назначение |
| :--- | :--- |
| **OpenTelemetry SDK** | Библиотека для инструментирования кода приложения. Генерирует спаны и передает их в коллектор по протоколу OTLP. Рекомендуется как замена устаревшим Jaeger Clients |
| **Jaeger Binary (v2)** | Единый бинарный файл, который может запускаться в различных ролях (Collector, Query, All-in-one). Построен на базе OTel Collector |
| **OTEL_COLLECTOR_ROLE** | Концепция v2, где роль компонента определяется конфигурационным файлом YAML, а не отдельными исполняемыми файлами |
| **Storage Extension** | Специализированный модуль Jaeger v2 для взаимодействия с бэкендами хранения (Elasticsearch, ClickHouse и др.) в рамках OTel Collector |
| **Kafka** | Опциональный промежуточный буфер для сглаживания пиковых нагрузок и обеспечения гарантированной доставки данных |
| **Jaeger Ingester** | Компонент (роль), считывающий данные из Kafka и записывающий их в Storage с использованием Jaeger Storage API |
| **Jaeger Query** | Сервис, предоставляющий **API (Application Programming Interface)** для извлечения данных из хранилища для UI или внешних систем |

## Базовые концепции

### Поток данных в Jaeger v2

В версии v2 путь прохождения трассировки стал более прямолинейным благодаря нативной поддержке OTLP:

`Приложение (OTel SDK) → [OTel Collector (Agent Mode)] → Jaeger v2 (Collector Mode) → [Kafka → Ingester] → Storage → Query → UI`

1.  **Инструментированное приложение** отправляет трейсы по OTLP (gRPC или HTTP).
2.  **OTel Collector (Agent Mode):** Заменяет устаревший `jaeger-agent`. Развертывается как Sidecar или DaemonSet для локального приема данных и их агрегации.
3.  **Jaeger v2 (Collector Mode):** Центральный узел обработки. Принимает данные, применяет процессоры (фильтрация, атрибуция) и сохраняет их.
4.  **Kafka & Ingester:** Используются в высоконагруженных (High Load) системах для изоляции приемника данных от хранилища.
5.  **Storage:** Постоянное хранилище данных.
6.  **Query & UI:** Слой визуализации и доступа к данным.

### Эволюция компонентов: v1 vs v2

Ключевое изменение архитектуры — отказ от специализированных бинарных файлов и переход к расширениям OpenTelemetry Collector.

*   **Jaeger Agent:** В v1 это был отдельный процесс для приема данных по UDP. В v2 рекомендуется использовать стандартный **OpenTelemetry Collector** в режиме агента, принимающий данные по OTLP.
*   **Jaeger Collector:** В v2 это экземпляр `jaeger`, настроенный с соответствующими `receivers`, `processors` и `exporters` (через Jaeger storage extension).
*   **Конфигурация:** Вместо сотен флагов командной строки используется единый структурированный YAML-файл в формате OTel Collector.

### Хранилище (Storage)

Выбор бэкенда определяет производительность и возможности поиска:

*   **ClickHouse:** В v2 считается одним из приоритетных хранилищ. Идеально подходит для огромных объемов данных благодаря колоночному формату. Позволяет эффективно выполнять аналитические запросы.
*   **Elasticsearch / OpenSearch:** Классический выбор для систем, где важен полнотекстовый поиск и мощная индексация тегов.
*   **Cassandra:** Традиционное хранилище для Jaeger, обеспечивающее высокую скорость записи, но имеющее ограничения по гибкости поиска.
*   **Badger / Memory:** Используются только для тестирования или в режиме `all-in-one`.

### Стратегии сэмплирования

Подробный разбор механизмов: **[Traces Deep Dive](../Concepts/Observability_and_Monitoring/traces_deep_dive.md#сэмплирование-sampling)**.

В Jaeger v2 сэмплирование реализуется через OTel-процессоры или специализированное расширение `sampling`:

| Тип | Описание в контексте v2 |
| :--- | :--- |
| **Head-based** | Выполняется на уровне SDK приложения. Решение о сохранении принимается сразу. |
| **Adaptive** | Настраивается через расширение `sampling`. Система анализирует входящий поток и динамически меняет вероятность сэмплирования для удержания целевого RPS. |
| **Tail-based** | Реализуется через `tailsamplingprocessor` в OTel Collector. Позволяет сохранять 100% трейсов с ошибками, даже если общий процент сэмплирования мал. |

## Практические сценарии

### Конфигурация Jaeger v2 (Collector Mode)

Пример конфигурации единого бинарного файла Jaeger v2 для приема данных по OTLP и сохранения в Elasticsearch:

```yaml
# jaeger-v2-config.yaml
receivers:
  otlp:
    protocols:
      grpc:
      http:

processors:
  batch:
    timeout: 5s
    send_batch_size: 1000

exporters:
  # Используется специализированное расширение для Jaeger Storage
  jaeger_storage_exporter:
    trace_storage:
      type: elasticsearch
      options:
        elasticsearch:
          server-urls: ["http://elasticsearch:9200"]

service:
  extensions: [jaeger_storage]
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [jaeger_storage_exporter]
```

### Сравнение пайплайнов сбора

1.  **Прямая запись (Direct to Storage):**
    `Collector -> Storage`. Подходит для малых и средних нагрузок. Простота в эксплуатации.
2.  **Асинхронная запись (через Kafka):**
    `Collector -> Kafka -> Ingester -> Storage`. Необходима при риске пиковых нагрузок или нестабильности хранилища. Предотвращает потерю трейсов при кратковременном отказе БД.
