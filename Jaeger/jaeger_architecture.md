# Архитектура Jaeger

Архитектура Jaeger спроектирована как модульная система, слои которой (сбор, транспорт, хранение, визуализация) можно масштабировать независимо. Это позволяет адаптировать ее под различные требования к производительности, объему данных и стоимости.

Общий обзор компонентов представлен в [**Jaeger Overview**](./jaeger_overview.md). Этот документ подробно описывает их внутреннее устройство и взаимодействие.

---

## Основные концепции

### Поток данных

Стандартный путь прохождения трассировки в распределенной архитектуре Jaeger выглядит так:

`Приложение (SDK) → Agent → Collector → [Kafka → Ingester] → Storage → Query/UI`

1. **Приложение**, инструментированное с помощью SDK (например, OpenTelemetry), создает спаны.
2. Спаны отправляются на локальный **Agent**, который буферизует их.
3. Agent передает спаны в **Collector**.
4. Collector валидирует, обрабатывает и сохраняет их в **Storage**. Для высоких нагрузок между Collector и Storage может использоваться **[Kafka](../Kafka/kafka_overview.md)** как буфер.
5. **UI** через **Query** запрашивает данные из **Storage** для визуализации.

### Детальный обзор компонентов

* **Клиентская инструментализация (SDK):** Внедряется в код приложения. Отвечает за создание спанов, управление контекстом и его передачу. Современной практикой является использование [OpenTelemetry SDK](../OpenTelemetry/opentelemetry_overview.md).

* **Jaeger Agent:** Легковесный демон, который обычно разворачивается как `DaemonSet` в Kubernetes или как sidecar-контейнер. Его основная задача — принимать спаны от клиентов по UDP, буферизовать их и отправлять батчами в Collector. Это снижает сетевые накладные расходы для приложения.

* **Jaeger Collector:** Горизонтально масштабируемый, stateless-сервис. Он принимает батчи трасс от агентов, выполняет их валидацию и обогащение, а затем записывает в хранилище. При высоких нагрузках Collector может быть настроен на запись в очередь Kafka вместо прямого сохранения в базу данных.

* **Kafka (Опционально):** Используется как централизованный буфер для сглаживания пиковых нагрузок. Collector отправляет данные в [Kafka](../Kafka/kafka_overview.md), что отделяет процесс приема данных от процесса их записи в хранилище, повышая отказоустойчивость системы.

* **Jaeger Ingester:** Сервис, который считывает данные из Kafka и надежно записывает их в постоянное хранилище (например, Elasticsearch или Cassandra).

* **Storage (Хранилище):** Бэкенд для долговременного хранения трасс. Выбор хранилища — ключевое архитектурное решение:
  * **Elasticsearch:** Обеспечивает мощный поиск по метаданным (тегам).
  * **Cassandra:** Гарантирует высокую пропускную способность на запись.
  * **Badger:** Локальное хранилище, используется только в режиме `all-in-one`.

* **Jaeger Query & UI:** Query — это stateless-сервис, предоставляющий API для извлечения и анализа трасс из хранилища. UI — это веб-интерфейс, который использует Query API для визуализации данных.

### Стратегии сэмплирования

* **Head-based Sampling:** Решение о сохранении трассы принимается на стороне клиента (в SDK или агенте) до того, как трасса будет полностью завершена. Простой и дешевый метод, но он может пропустить редкие или ошибочные трассы.
* **Tail-based Sampling:** Решение принимается после сбора всех спанов трассы (обычно в OpenTelemetry Collector). Это позволяет гарантированно сохранять все ошибочные или медленные трассы, но требует значительно больше ресурсов для буферизации.
* **Remote Sampling:** Collector централизованно предоставляет агентам конфигурацию сэмплирования, что позволяет динамически управлять им без перезапуска приложений.

### Хранилище и производительность

Для обеспечения высокой производительности и надежности в Jaeger используются следующие подходы:

* **Батчинг:** Спаны группируются в батчи на уровне агента и коллектора.
* **Очереди:** Kafka используется для буферизации пиков и разделения процессов приема и записи.
* **Масштабирование:** Collector и Query являются stateless-сервисами и легко масштабируются горизонтально.
* **Управление данными:** Для хранилищ применяются политики TTL (Time-To-Live) для автоматического удаления старых данных.

## Практические сценарии

### Конфигурация OpenTelemetry Collector для Jaeger

Это минимальный пример конфигурации OpenTelemetry Collector, который принимает OTLP-данные и экспортирует их в Jaeger.

```yaml
receivers:
  otlp:
    protocols:
      http:
      grpc:

processors:
  batch:

exporters:
  jaeger:
    endpoint: jaeger-collector:14250
    tls:
      insecure: true

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [jaeger]
```
