# Архитектура Jaeger

> **Важно:** Документация описывает **Jaeger v2**. Jaeger v1 достиг EOL.

Архитектура Jaeger v2 спроектирована на базе OpenTelemetry Collector. Это обеспечивает максимальную гибкость, унификацию пайплайнов телеметрии и тесную интеграцию с экосистемой OpenTelemetry.

Общий обзор компонентов представлен в [**Jaeger Overview**](./jaeger_overview.md). Этот документ подробно описывает их внутреннее устройство и взаимодействие.

---

## Основные концепции

### Поток данных

Стандартный путь прохождения трассировки в Jaeger v2:

`Приложение (OTel SDK) → OTel Collector → [Kafka → Ingester] → Storage → Query/UI`

1. **Приложение**, инструментированное с помощью OpenTelemetry SDK, создает спаны.
2. Спаны отправляются в **OpenTelemetry Collector**, который является основным компонентом сбора в v2.
3. Collector выполняет валидацию, обработку и экспорт в хранилище. Для высоких нагрузок может использоваться **[Kafka](../Kafka/kafka_overview.md)** как буфер между Collector и Ingester.
4. **Ingester** (новый компонент v2) считывает данные из Kafka и записывает в хранилище.
5. **UI** через **Query** запрашивает данные из **Storage** для визуализации.

### Детальный обзор компонентов

* **OpenTelemetry Collector (заменяет Jaeger Agent + Collector в v1):** Основной компонент сбора данных в v2. Является легковесным, расширяемым и поддерживает множество форматов входных данных (OTLP, Jaeger, Zipkin). Обычно разворачивается как DaemonSet или sidecar в Kubernetes.

* **Jaeger Collector:** В v2 это специализированный OTel Collector с дополнительными возможностями для работы с данными Jaeger. Выполняет валидацию, обогащение и экспорт в хранилище.

* **Kafka (Опционально):** Используется как централизованный буфер для сглаживания пиковых нагрузок. Collector отправляет данные в [Kafka](../Kafka/kafka_overview.md), что отделяет процесс приема данных от процесса их записи в хранилище, повышая отказоустойчивость системы.

* **Jaeger Ingester:** Сервис, который считывает данные из Kafka и надежно записывает их в постоянное хранилище. Активно используется в v2 при наличии Kafka.

* **Storage (Хранилище):** Бэкенд для долговременного хранения трасс. Выбор хранилища — ключевое архитектурное решение:
  * **Elasticsearch / OpenSearch:** Обеспечивают мощный поиск по метаданным (тегам). OpenSearch является полностью открытым форком Elasticsearch.
  * **Cassandra:** Гарантирует высокую пропускную способность на запись.
  * **ClickHouse:** Новая опция в v2. Открытая колоночная база данных, оптимизированная для OLAP-нагрузок. Отличается высокой эффективностью при больших объемах трассировок.
  * **Badger:** Локальное хранилище, используется только в режиме `all-in-one`.

* **Jaeger Query & UI:** Query — это stateless-сервис, предоставляющий API для извлечения и анализа трасс из хранилища. UI — это веб-интерфейс, который использует Query API для визуализации данных.

* **Jaeger Spark Dependencies:** Это отдельное Spark-задание, отвечающее за построение графа зависимостей сервисов (Service Dependency Graph).
  * **Принцип работы:** Задание периодически запускается, анализирует сохраненные спаны в хранилище (например, OpenSearch) и агрегирует информацию о вызовах между сервисами. Результаты сохраняются в отдельный индекс.
  * **В Kubernetes** обычно развертывается как `CronJob`.
  * **Примечание:** В v2 данный компонент может быть заменен или расширен новыми возможностями анализа.

### Стратегии сэмплирования

Подробное описание стратегий сэмплирования и их сравнение приведено в документе [**Концепции распределенной трассировки**](./distributed_tracing_concepts.md#сэмплирование-sampling).

* **Head-based Sampling:** Решение о сохранении трассы принимается на стороне клиента (в SDK или агенте) до того, как трасса будет полностью завершена. Простой и дешевый метод, но он может пропустить редкие или ошибочные трассы.
* **Tail-based Sampling:** Решение принимается после сбора всех спанов трассы (обычно в OpenTelemetry Collector). Это позволяет гарантированно сохранять все ошибочные или медленные трассы, но требует значительно больше ресурсов для буферизации.
* **Remote Sampling:** Collector централизованно предоставляет агентам конфигурацию сэмплирования, что позволяет динамически управлять им без перезапуска приложений.

### Хранилище и производительность

Для обеспечения высокой производительности и надежности в Jaeger используются следующие подходы:

* **Батчинг:** Спаны группируются в батчи на уровне агента и коллектора.
* **Очереди:** Kafka используется для буферизации пиков и разделения процессов приема и записи.
* **Масштабирование:** Collector и Query являются stateless-сервисами и легко масштабируются горизонтально.
* **Управление данными:** Для хранилищ применяются политики TTL (Time-To-Live) для автоматического удаления старых данных.

## Практические сценарии

### Конфигурация OpenTelemetry Collector для Jaeger

Это минимальный пример конфигурации OpenTelemetry Collector, который принимает OTLP-данные и экспортирует их в Jaeger.

```yaml
receivers:
  otlp:
    protocols:
      http:
      grpc:

processors:
  batch:

exporters:
  jaeger:
    endpoint: jaeger-collector:14250
    tls:
      insecure: true

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [jaeger]
```
