# Анализ производительности с помощью Jaeger

Анализ производительности в Jaeger — это процесс интерпретации данных трассировки для выявления узких мест, анализа задержек и диагностики ошибок. Этот документ описывает практические методики использования Jaeger UI и API для этих целей.

---

## Основные концепции

### Ключевые элементы Jaeger UI

1.  **Панель поиска:** Позволяет фильтровать трассы по сервису, операции, тегам (`error=true`, `http.status_code=500`), диапазону времени и длительности.
2.  **Визуализация трейса (Timeline/Gantt Chart):** Каскадная диаграмма, показывающая последовательность и длительность спанов. Является основным инструментом для визуального анализа задержек.
3.  **Детали спана:** Панель, отображающая всю информацию о выбранном спане: атрибуты (теги), события (логи) и метаданные процесса.

### Методика анализа трейса

1.  **Оцените общую длительность:** Найдите корневой спан и посмотрите на общую задержку запроса.
2.  **Определите критический путь:** Это последовательность спанов, которая напрямую влияет на общую длительность. Оптимизация спанов вне критического пути не даст эффекта.
3.  **Ищите "длинные" спаны:** Найдите спаны, которые вносят наибольший вклад в задержку.
4.  **Анализируйте параллелизм:** Ищите спаны, которые могли бы выполняться параллельно, но выполняются последовательно (эффект "водопада").

### Типовые паттерны проблем

*   **Проблема N+1:** Множество одинаковых коротких запросов (например, к БД), которые можно было бы объединить в один.
*   **"Болтливые" вызовы (Chatty I/O):** Большое количество мелких последовательных сетевых вызовов между двумя сервисами.
*   **Каскадные повторы (Retries):** Несколько попыток выполнить один и тот же спан, что указывает на проблемы с доступностью или нестабильностью зависимого сервиса.

## Практические сценарии

### Сценарий 1: Фильтрация и поиск аномалий

Используйте панель поиска для быстрого нахождения проблемных трейсов.

*   **Найти все ошибочные трейсы для сервиса `checkout`:**
    *   `Service`: `checkout`
    *   `Tags`: `error=true`
*   **Найти медленные запросы на создание заказа:**
    *   `Service`: `orders`
    *   `Operation`: `createOrder`
    *   `Min Duration`: `1.5s`

### Сценарий 2: Корреляция с метриками и логами

*   **От метрик к трейсам:** Если на графике в Grafana вы видите всплеск задержки, а ваша система мониторинга поддерживает exemplars, вы можете перейти напрямую к трейсу, вызвавшему этот всплеск.
*   **От логов к трейсам:** Включите `trace_id` в логи вашего приложения. При анализе логов в Loki или Elasticsearch вы можете скопировать `trace_id` и вставить его в Jaeger UI для просмотра полного контекста запроса.

### Сценарий 3: Автоматизация через API

Jaeger Query API позволяет автоматизировать анализ. Например, можно получить список последних 20 медленных и ошибочных трейсов для сервиса `checkout`:
```bash
curl 'http://jaeger-query:16686/api/traces?service=checkout&operation=PlaceOrder&lookback=1h&limit=20&minDuration=500ms&tags=%7B%22error%22%3Atrue%7D'
```

### Сценарий 4: Настройка Tail-based Sampling для ценных трейсов

Чтобы анализировать только самые важные трейсы (ошибочные, медленные), настройте Tail-based Sampling в OpenTelemetry Collector. Это сэкономит место в хранилище.

```yaml
# processors:
  tail_sampling:
    policies:
      # Сохранять все ошибочные трейсы
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      # Сохранять трейсы дольше 800мс
      - name: slow_requests
        type: latency
        latency: { threshold_ms: 800 }
```

## Дополнительная информация

### Рекомендуемые атрибуты для анализа

Чтобы сделать трейсы более информативными, добавляйте в спаны следующие атрибуты:
*   `http.method`, `http.route`, `http.status_code`
*   `db.system`, `db.statement` (без чувствительных данных)
*   `messaging.system`, `messaging.destination`
*   Бизнес-контекст: `user.id`, `tenant.id` (в хешированном виде).
