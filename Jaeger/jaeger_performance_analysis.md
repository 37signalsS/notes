# Анализ производительности с помощью Jaeger

## Ключевые элементы интерфейса Jaeger

*   **Поиск**: Позволяет сузить множество трейсов по сервису, операции, тегам, диапазону времени и минимальной/максимальной длительности. Сортировка по длительности и числу спанов помогает быстро найти аномальные случаи.
*   **Таймлайн (waterfall)**: Визуализирует последовательность и параллелизм. Важны:
    *   родительские/дочерние связи (ChildOf, FollowsFrom),
    *   перекрытия спанов (параллельные вызовы),
    *   вклад каждого спана в общую задержку.
*   **Детали спана**: Анализируют теги (атрибуты), логи/события и процессные метаданные.
*   **Dependencies**: Строит карту сервисных зависимостей и подсвечивает узкие места между сервисами.

## Методика чтения трейса

1.  Найти корневой спан и оценить общую длительность.
2.  Определить **критический путь** — последовательность спанов, суммарная длительность которых равна задержке запроса. Именно он определяет перформанс.
3.  Идентифицировать «широкие» спаны на таймлайне и проверить, не перекрываются ли они с другими (низкий параллелизм).
4.  Сверить внешние вызовы (DB, кэши, очереди) по латентности и частоте.

### Типовые паттерны

*   **N+1**: множество однотипных коротких спанов к одной зависимости, суммарно дающих большую задержку.
*   **Chatty I/O**: серия мелких последовательных RPC.
*   **Каскадные ретраи**: повторяющиеся одинаковые спаны с увеличивающейся задержкой и тегом `retry_count`.
*   **Сериализация/десериализация**: значимый вклад CPU-спанов без внешних I/O.
*   **Проблемы сети/DNS**: длительный `connect`/`resolve`, высокая разбежка latency.

## Быстрая фильтрация и поиск

Используйте поиск по тегам и длительности: например, `http.method=GET`, `error=true`, `minDuration=500ms`. Через HTTP API можно автоматизировать выгрузку:

```rust
curl 'http://jaeger-query:16686/api/traces?service=checkout&operation=PlaceOrder&lookback=1h&limit=20&minDuration=500ms&tags=%7B%22error%22%3Atrue%7D'
```

Полученные `traceID` можно далее агрегировать офлайн для построения распределений латентности.

## Корреляция с метриками и логами

*   **Из метрик к трейсам**: при наличии экземпларов на графике задержки щелчок по точке открывает конкретный трейс с соответствующим `trace_id`.
*   **Из логов к трейсам**: включайте в логи `trace_id` и `span_id`. В системах агрегации логов применяйте фильтр по `trace_id` для мгновенного перехода к трейсу.

## Полезные теги и события

Рекомендуемые атрибуты для диагностируемости:

*   `http.method`, `http.route`, `http.status_code`
*   `db.system`, `db.operation`; `db.statement` в обезличенном виде
*   `net.peer.name`/`port`, `retry_count`, `cache.hit`, `queue.name`
*   `feature_flag`, `user.anonymous_id` (хэшированный)

События в спанах фиксируют важные точки: `event="timeout"`, `event="fall-back"`, вместе с атрибутами причины.

## Отбор релевантных трейсов (tail-based sampling)

Чтобы видеть именно медленные/ошибочные запросы, применяют «хвостовую» выборку в OpenTelemetry Collector. Политики на основе атрибутов и длительности отфильтруют шум:

```yaml
processors:
  tail_sampling:
    decision_wait: 5s
    num_traces: 50000
    policies:
      - name: errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: slow_end_to_end
        type: latency
        latency:
          threshold_ms: 800
      - name: important_routes
        type: string_attribute
        string_attribute:
          key: http.route
          values: ["/checkout", "/payment"]
```

Такой подход концентрирует хранилище на ценных для анализа трейcах и облегчает поиск регрессий.
