# Концепции распределенной трассировки

> **Важно:** Описанные концепции являются общими для всех систем трассировки. **Jaeger v1** достиг EOL 31 декабря 2025 года. **Jaeger v2** является текущей версией.

**Распределенная трассировка** — это процесс отслеживания полного пути запроса через множество сервисов, баз данных и очередей в распределенной системе. Ее главная задача — обеспечить наблюдаемость, позволяя разработчикам и SRE-инженерам понимать поведение системы, находить узкие места и быстро диагностировать ошибки.

---

## Определения

* **Трасса (Trace):** Полная история обработки одного запроса, которая проходит через систему. Состоит из одного или нескольких спанов и уникально идентифицируется с помощью `trace_id`.
* **Спан (Span):** Атомарная единица работы в трассе (например, обработка HTTP-запроса, вызов БД). Имеет `span_id`, имя, временные метки, статус и метаданные. Спаны организованы в иерархию (дерево), где у каждого спана, кроме корневого, есть родитель.
* **Контекст спана (Span Context):** Набор данных (`trace_id`, `span_id`, флаги сэмплирования), который передается между сервисами для корреляции спанов в единую трассу.
* **Атрибуты (Attributes/Tags):** Метаданные в формате «ключ-значение», описывающие спан (`http.method="GET"`, `db.system="postgres"`). Используются для фильтрации и анализа.
* **События (Events/Logs):** Метки времени с описанием, привязанные к спану, которые фиксируют события в процессе его выполнения (например, "cache_miss").
* **Статус (Status):** Итог выполнения операции, представленной спаном (`Ok`, `Error`). Ошибочный статус обычно содержит дополнительную информацию об исключении.
* **Вид спана (Span Kind):** Указывает на роль спана в межсервисном взаимодействии (`CLIENT`, `SERVER`, `PRODUCER`, `CONSUMER`, `INTERNAL`). Помогает правильно интерпретировать диаграммы задержек.

| Сущность | Назначение | Пример |
| --- | --- | --- |
| `trace_id` | Группировка всех спанов одного запроса | Один клик пользователя |
| `span_id` | Уникальный идентификатор операции | SQL-запрос `SELECT * FROM users` |
| Атрибуты | Контекст для диагностики | `db.system=postgres`, `http.status_code=500` |
| События | Точки на временной шкале спана | `retry_started` |
| Статус | Итог операции | `ERROR` с кодом `timeout` |

## Основные концепции

### Структура трассы

Трасса представляет собой ориентированный ациклический граф (DAG) спанов. Корневой спан (root span) представляет начальную операцию (например, входящий HTTP-запрос), а дочерние спаны — последующие операции, такие как вызовы других сервисов или запросы к базе данных. Эта структура позволяет визуализировать причинно-следственные связи и задержки в системе.

### Пропагация контекста

Для объединения спанов из разных сервисов в одну трассу **контекст** должен передаваться вместе с каждым сетевым вызовом. Этот механизм называется пропагацией контекста и обычно реализуется через HTTP-заголовки.

Основные стандарты заголовков:

* **W3C Trace Context (рекомендованный):** `traceparent` и `tracestate`.
* **B3 (Zipkin-стиль):** `x-b3-traceid`, `x-b3-spanid`, `x-b3-sampled`.

### Сэмплирование (Sampling)

Сбор данных о каждом запросе может быть избыточным и дорогостоящим. Сэмплирование позволяет собирать только часть трассировок, снижая нагрузку.

* **Head-based Sampling:** Решение о сборе трассы принимается в самом начале (на корневом спане). Просто и дешево, но можно пропустить важные, но редкие ошибочные трассы.
* **Tail-based Sampling:** Решение принимается после завершения всей трассы. Позволяет собирать все ошибочные или медленные трассы, но требует больше ресурсов для буферизации.

## Практические сценарии

### Пример инструментирования кода

Современные фреймворки и библиотеки часто инструментируются автоматически, но для бизнес-логики может потребоваться ручное создание спанов.

```python
# Пример с использованием OpenTelemetry SDK
from opentelemetry import trace

tracer = trace.get_tracer("my_app.checkout_logic")

def process_checkout(user_id: str):
    # Корневой спан для операции
    with tracer.start_as_current_span("process_checkout", kind=trace.SpanKind.SERVER) as root_span:
        root_span.set_attribute("user.id", user_id)
        
        # Вложенный спан для вызова БД
        with tracer.start_as_current_span("get_cart_from_db") as db_span:
            db_span.set_attribute("db.system", "postgres")
            # ... логика запроса к БД ...

        # Вложенный спан для вызова платежного шлюза
        with tracer.start_as_current_span("charge_payment") as payment_span:
            try:
                # ... вызов внешнего API ...
                payment_span.set_status(trace.StatusCode.OK)
            except Exception as e:
                payment_span.record_exception(e)
                payment_span.set_status(trace.StatusCode.ERROR, description="Payment failed")
                root_span.set_status(trace.StatusCode.ERROR)

```

### Асинхронные взаимодействия

* **Очереди сообщений:** Производитель создает спан при отправке сообщения и внедряет контекст трассировки в метаданные сообщения. Потребитель извлекает контекст и создает дочерний спан, связывая две операции в одну трассу.
* **Service Mesh:** Прокси-серверы (например, Envoy) автоматически создают спаны для входящего и исходящего трафика и управляют пропагацией контекста, что снижает необходимость в ручной инструментации.

## Дополнительная информация

* **Реализация:** Концепции трассировки реализуются с помощью таких инструментов, как [**Jaeger**](./jaeger_overview.md) и **Zipkin**. Они предоставляют бэкенд для сбора, хранения и визуализации трасс.
*   **Стандарт:** [**OpenTelemetry**](../OpenTelemetry/opentelemetry_overview.md) является современным стандартом для инструментирования кода. Он предоставляет единые API и SDK для сбора телеметрии (трассировок, метрик, логов), позволяя легко интегрироваться с различными бэкендами.

### Сравнение архитектур бэкендов

Выбор бэкенда для хранения и визуализации трейсов определяет архитектуру всего пайплайна сбора данных.

*   **Классическая архитектура с Jaeger:**
    *   **Пайплайн:** `Приложение -> Jaeger Agent -> Jaeger Collector -> Бэкенд (напр., Elasticsearch)`
    *   **Компоненты:**
        *   `Jaeger Agent`: `DaemonSet`, работающий на каждой ноде для приема спанов по UDP.
        *   `Jaeger Collector`: Центральный компонент, который валидирует, обрабатывает и сохраняет трейсы в хранилище.
        *   `Jaeger UI`: Интерфейс для запросов и визуализации.
    *   **Принцип работы:** Jaeger-клиент в приложении отправляет спаны агенту, который перенаправляет их в коллектор для сохранения. Jaeger UI напрямую читает данные из того же бэкенда.

*   **Архитектура с OpenSearch Observability:**
    *   **Пайплайн:** `Приложение -> OTLP Collector -> Data Prepper -> OpenSearch`
    *   **Принцип работы:** Этот подход используется, когда бэкенд (в данном случае плагин OpenSearch Observability) требует данные в определенном формате (OTLP), несовместимом с нативным форматом хранения Jaeger.
    *   **Компоненты:**
        *   `OTLP Collector`: Заменяет `Jaeger Agent` и `Collector`. Принимает данные в разных форматах (включая Jaeger) и экспортирует их в OTLP.
        *   `Data Prepper`: Компонент OpenSearch, который принимает данные в OTLP, обрабатывает их и сохраняет в формате, понятном для дашбордов Observability.

#### Пользовательский опыт (UX)

Помимо архитектурных различий, важен и пользовательский опыт взаимодействия с UI. Например, по субъективным оценкам, интерфейс **Jaeger UI** часто считается более интуитивным для анализа трейсов (в частности, благодаря двумерной диаграмме для поиска трейсов по времени и задержке) по сравнению с дашбордами **OpenSearch Observability**, которые могут показаться менее привычными.
