# Основные концепции распределённого трассинга

Распределённый трассинг — это способ наблюдения пути запроса через множество сервисов, подсистем и очередей. Он помогает восстановить причинно-следственные связи между операциями, понять структуру задержек и локализовать узкие места.

Распределённый трейсинг фиксирует путь обработки запроса через множество сервисов. Корректное понимание терминов позволяет интерпретировать диаграммы в Jaeger, связывать логи с метриками и выявлять узкие места в цепочке вызовов.

## Определения и ключевые сущности

*   **Трасса (trace)** — целостное представление запроса от начала до конца. Идентифицируется `trace_id`. Полная история обработки одного запроса, объединяющая все связанные операции в разных сервисах.
*   **Спан (span)** — атомарная единица работы в трейсе: обработка HTTP-запроса, вызов БД, публикация сообщения. Имеет `span_id`, временные метки начала/конца и метаданные (атрибуты, статус).
*   **Иерархия**: у каждого спана один родительский спан, кроме корневого (связь `ChildOf`). Допустимы связи `FollowsFrom` для ослабленной причинности (например, асинхронные очереди) и `link` для ситуаций fan-in/fan-out.
*   **Контекст спана (span context)** — минимальный набор идентификаторов и флагов, необходимый для корреляции: `traceId`, `spanId`, флаг `sampled`, а также `tracestate`.
*   **Багаж (baggage)** — произвольные ключ-значение, путешествующие с контекстом через все сервисы. Предназначен для маршрутизации и аналитики, не для больших данных.
*   **Атрибуты (tags/attributes)** — ключ-значение, описывающие спан: `http.method`, `db.system`, `net.peer.ip` и т.д.
*   **События (events/logs/annotations)** — точечные метки во времени внутри спана: ретраи, кеш-промахи, сериализация.
*   **Статус/ошибка** — код состояния и описание ошибки; критично для фильтрации в UI и алертов.
*   **Вид спана (span kind)**: `client`, `server`, `producer`, `consumer`, `internal` — помогает интерпретировать диаграммы времени и агрегировать задержки по ролям.

| Сущность | Назначение | Пример |
| --- | --- | --- |
| trace_id | Группировка цепочки | Один пользовательский клик |
| span_id | Единица работы | SQL SELECT к users |
| атрибуты | Диагностика контекста | db.system=postgres |
| события | Точки на временной линии | retry_started |
| статус | Итог операции | ERROR с кодом timeout |
| links | Слабая причинная связь | Сообщение из Kafka |

## Пропагация контекста

Чтобы коррелировать спаны в разных сервисах, контекст трассы передаётся вместе с запросом через заголовки.

*   **W3C Trace Context**: заголовки `traceparent` и `tracestate`.
*   **B3 (Zipkin стиль)**: заголовки `x-b3-traceid`, `x-b3-spanid`, `x-b3-sampled` и др.
*   **Baggage**: заголовок `baggage` для передачи бизнес-контекста.

| Сущность | Пример | Назначение |
| --- | --- | --- |
| traceparent | 00-4bf92f...e4736-00f067aa0ba902b7-01 | traceId-spanId-флаги |
| tracestate | vendor=foo,congo=t61rcWkgMzE | доп. сведения провайдера |
| baggage | user_id=42,plan=premium | пользовательские ключи |

Примеры заголовков:
```makefile
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
tracestate: vendorA=foo,vendorB=bar
```
```less
x-b3-traceid: 463ac35c9f6413ad48485a3953bb6124
x-b3-spanid: a2fb4a1d1a96d312
x-b3-sampled: 1
```
```http
GET /checkout HTTP/1.1
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
tracestate: vendor=foo,congo=t61rcWkgMzE
baggage: user_id=42,plan=premium
```

## Сэмплирование

Полное отслеживание каждого запроса дорого. Сэмплер решает, какие трассы собирать.

*   **Head-based**: решение на старте корневого спана (до обработки): всегда/никогда/по вероятности/по правилам. Просто и дешево, но не учитывает исход.
*   **Tail-based**: решение после завершения трассы с учётом ошибок и латентности. Точнее, но требует буферизации.
*   **Стратегии**: probabilistic (p=0.01), per-operation (повышенная доля для редких/критичных), rate limiting (не более N трасс/сек).
*   **Consistent sampling**: согласованность решения между сервисами по одному traceId.

Важно сохранять согласованность: если корневой спан выбран, дочерние тоже должны быть записаны.

## Структура трейса и практические сценарии

Трейс формируется как ориентированный ациклический граф: корневой спан отражает входной запрос, дочерние — локальные операции и удалённые вызовы.

### Атрибуты, события и статус
*   **Атрибуты (key=value)** описывают параметры выполнения: `http.method`, `net.peer.ip`, `messaging.system`.
*   **События** фиксируют значимые точки во времени: «cache_miss», «retry», «circuit_open».
*   **Статус спана** отражает успех/ошибку и код причины. Ошибки полезно сопровождать стеком и типом исключения.

Пример кода с типовым шаблоном:
```python
tracer = get_tracer("checkout")

with tracer.start_as_current_span("HTTP GET /checkout", kind="server") as root:
    root.set_attribute("user.id", user_id)
    root.add_event("cache_lookup")
    with tracer.start_as_current_span("select cart", kind="client") as db_span:
        db_span.set_attribute("db.system", "postgres")
        rows = db.query("SELECT ...")
    with tracer.start_as_current_span("charge", kind="client") as pay:
        try:
            call_payment_gateway()
        except TimeoutError as e:
            pay.record_exception(e)
            pay.set_status("ERROR")
            root.set_attribute("error", True)
```

### Асинхронные и кросс-сервисные сценарии
*   **Очереди**: producer создает спан при публикации, consumer — при обработке. Связь оформляется через `links` или сохранение context в метаданных сообщения.
*   **Service Mesh**: прокси автоматически прокидывают заголовки и создают спаны `client`/`server` без изменения кода.
*   **Batch и fan-out**: несколько дочерних спанов могут выполняться параллельно; для объединения результатов применяются `links`.

## Использование в Jaeger
Инструментация в приложении создаёт спаны, добавляет атрибуты, события и статус, пропагирует контекст через заголовки. Агенты/коллекторы Jaeger принимают спаны, индексируют по `traceId` и обеспечивают реконструкцию графа трейса. Метаданные (атрибуты, `kind`, статус) позволяют фильтровать и визуализировать критические участки цепочки вызовов.
