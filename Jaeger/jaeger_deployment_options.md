# Варианты развертывания Jaeger

> **Важно:** Документация описывает **Jaeger v2** (текущая версия). Jaeger v1 достиг **EOL (End of Life)**.

Jaeger v2 радикально упрощает процесс развертывания за счет перехода на архитектуру единого бинарного файла. В зависимости от масштаба системы и требований к надежности, Jaeger может быть запущен как в упрощенном режиме "все-в-одном", так и в виде распределенной масштабируемой системы.

---

## Определения

| Вариант | Описание | Основные характеристики |
| :--- | :--- | :--- |
| **All-in-one** | Запуск всех компонентов Jaeger (Collector, Query, UI) в одном процессе | Идеально для локальной разработки. Использует In-memory или Badger хранилище |
| **Production (Распределенный)** | Развертывание компонентов как независимых, горизонтально масштабируемых сервисов | Использует внешние отказоустойчивые БД (Elasticsearch, Cassandra, ClickHouse). Подходит для высоких нагрузок |
| **Unified Binary** | Концепция v2, при которой один и тот же исполняемый файл `jaeger` выполняет разные функции в зависимости от конфигурации | Позволяет гибко менять роль узла (например, только Collector или только Query) |

---

## Базовые концепции

### Сравнение моделей развертывания

| Критерий | All-in-one | Production |
| :--- | :--- | :--- |
| **Назначение** | Локальная отладка, **CI/CD (Continuous Integration / Continuous Deployment)**, демо-стенды | Среды промышленной эксплуатации, высоконагруженные системы |
| **Хранение данных** | In-memory (кратковременно) или локальный файл (Badger) | Внешние кластеры баз данных. Подробности: **[Архитектура Jaeger](./jaeger_architecture.md)** |
| **Масштабируемость** | Только вертикальная (ограничена ресурсами одного узла) | Полная горизонтальная масштабируемость всех компонентов |
| **Настройка** | Минимальная, часто через переменные окружения | Глубокая настройка через YAML-конфигурацию в стиле OpenTelemetry Collector |

### Выбор стратегии развертывания

**Выбирайте All-in-one**, если:
- Вы только начинаете знакомство с трассировкой.
- Вам нужно проверить работоспособность инструментирования приложения на локальной машине.
- Вы запускаете тесты в CI/CD, где данные не нужно сохранять после завершения пайплайна.

**Переходите к Production-модели**, если:
- Объем входящих трейсов превышает возможности одного сервера.
- Требуется анализ исторических данных за длительный период (недели/месяцы).
- Необходима высокая доступность (**High Availability**) системы мониторинга.
- Вы используете сложные политики сэмплирования и обработки данных.

## Практические сценарии

### Сценарий 1: Локальный запуск в Docker (OTLP-native)

В Jaeger v2 рекомендуется использовать нативный протокол **OTLP (OpenTelemetry Protocol)**. Пример запуска через единый образ `jaegertracing/jaeger`:

```bash
docker run -d --name jaeger \
  -p 16686:16686 \   # Jaeger UI
  -p 4317:4317 \     # OTLP gRPC приемник
  -p 4318:4318 \     # OTLP HTTP приемник
  jaegertracing/jaeger:latest
```

**Порты для обратной совместимости (опционально):**
- `14268`: Прием спанов в формате Jaeger Thrift (HTTP).
- `9411`: Прием спанов в формате Zipkin (HTTP).

### Сценарий 2: Развертывание в Kubernetes через OpenTelemetry Operator

С выходом Jaeger v2 основным инструментом управления становится **OpenTelemetry Operator**, который нативно поддерживает объекты типа `Jaeger`.

**Преимущества использования Operator:**
1.  **Автоматизация:** Управление жизненным циклом (обновления, масштабирование).
2.  **Sidecar Injection:** Автоматическое добавление OTel Collector (агента) в поды приложений через аннотации.
3.  **Конфигурация как код:** Использование **CRD (Custom Resource Definitions)** для описания состояния системы.

Пример и детали настройки: **[Интеграция с Kubernetes](./jaeger_kubernetes_integration.md)**.
