# Варианты развертывания Jaeger: all-in-one vs. production

Jaeger поддерживает два базовых подхода к развертыванию: **all-in-one** и **production**. Они отличаются составом компонентов, устойчивостью к нагрузке, требуемыми ресурсами и операционными практиками. Выбор модели определяет, насколько трассировка будет пригодна для быстрой отладки, тестовых стендов или высоконагруженного продакшена с длительным хранением следов.

## Когда применять

*   **All-in-one**: локальная разработка, демо, временные окружения в CI, быстрая проверка интеграции OpenTelemetry SDK/Collector. Основной упор — минимальная сложность и скорость старта, допускается потеря данных и ограниченная ретенция.
*   **Production**: стейджинг и продакшен, где важны горизонтальное масштабирование, отказоустойчивость, долговременное хранение в Elasticsearch/Cassandra, контроль ретенции, отказоустойчивые апгрейды и безопасность.

## Ключевые различия

| Критерий | All-in-one | Production |
| --- | --- | --- |
| Компоненты | Все в одном процессе: agent, collector, query, UI, память/Badger | Отдельные сервисы: agent/collector/query/ingester, внешнее хранилище |
| Хранилище | Память или встроенный Badger, без HA | Elasticsearch или Cassandra, HA и масштабирование |
| Масштабирование | По факту отсутствует, 1 инстанс | Горизонтально: collector/query/ingester отдельно |
| Устойчивость к сбоям | Низкая | Высокая при корректной архитектуре |
| Производительность | Подходит для малой нагрузки | Подходит для высоких RPS трасс |
| Безопасность | Базовая, часто без TLS | TLS, аутентификация, контроль доступа |
| Операции | Минимальная поддержка | Ротация индексов, ретенция, бэкапы, мониторинг |

## Пример развертывания all-in-one (Docker)

Быстрый старт для локальной отладки и интеграционных проверок:

```bash
docker run -d --name jaeger 
  -e COLLECTOR_ZIPKIN_HOST_PORT=:9411 
  -e SPAN_STORAGE_TYPE=memory 
  -p 16686:16686 \   # UI
  -p 14268:14268 \   # HTTP ingest
  -p 14250:14250 \   # gRPC ingest
  -p 6831:6831/udp \ # Thrift compact
  -p 9411:9411 \     # Zipkin
  jaegertracing/all-in-one:1.50
```

Ключевые моменты: хранение в памяти означает потерю данных при рестарте; производительность и объём следов ограничены; настройки sampling лучше держать агрессивными (низкая доля) во избежание переполнения памяти.

## Пример production-развертывания (Jaeger Operator, Kubernetes)

Оператор упрощает жизненный цикл и обеспечивает корректную схему компонентов. Пример CR c Elasticsearch:

```yaml
apiVersion: jaegertracing.io/v1
kind: Jaeger
metadata:
  name: jaeger-prod
spec:
  strategy: production
  storage:
    type: elasticsearch
    options:
      es:
        server-urls: http://elasticsearch:9200
    esIndexCleaner:
      enabled: true
      numberOfDays: 7
  collector:
    replicas: 3
    options:
      log-level: info
  query:
    replicas: 2
  agent:
    strategy: DaemonSet
```

Такой вариант позволяет:
*   Масштабировать collector по нагрузке, query — по числу пользователей UI/API.
*   Управлять сроком хранения (esIndexCleaner) и издержками.
*   Разводить ресурсы и задавать лимиты на уровне Pod.

Для высоких объёмов трасс добавляют стриминг через Kafka и ingester, чтобы разгрузить collectors и обеспечить буферизацию. В качестве альтернативы используется Cassandra; выбор диктуется операционными практиками и доступной экспертизой.

## Практические соображения выбора

*   **Продуктовая готовность**: нужны ретенция, поиск и целостность — берите production.
*   **Стоимость**: all-in-one дешевле на старте, но плохо масштабируется; production требует внешнего хранилища и наблюдаемости самих компонентов.
*   **Миграция**: начинать с all-in-one для разработки; при росте нагрузки вынести хранилище, разделить collector/query, затем добавить стриминг и тонкую настройку sampling на стороне SDK/Collector.
*   **Безопасность**: в production применяются TLS, аутентификация к UI/API и ограничения на приём от внешних источников.
