# VPN: чек-лист приёмки развёртывания

**Актуально для:** WireGuard (wireguard-tools 1.0.x) / Keepalived 2.4.x (блок HA) / Prometheus 3.x (блок мониторинга); подход применим и к mesh-VPN с оговорками на контроллер

## Определения

**Приёмка (acceptance)** — формальная процедура проверки нового или изменённого VPN-развёртывания по заранее заданным критериям до передачи в эксплуатацию; фиксируется результатом «принято / принято с оговорками / откатить».

**Smoke-тест** — минимальный набор проверок (поднялся ли туннель, ходит ли трафик, работает ли DNS), выполняемый сразу после выката.

**Soak-тест** — наблюдение за системой в штатной нагрузке длительное время (типично 24–72 ч) для вылова периодических проблем: деградация handshake, утечки памяти, флапанье переподключений.

**Canary-узел** — контрольный клиент/пир, чьё рукопожатие и трафик отслеживаются как индикатор живости контура для всей популяции ([vpn-monitoring.md](./vpn-monitoring.md)).

**Baseline** — измерение производительности и маршрутизации до вмешательства (или по эталонному узлу), с которым сравниваются результаты после выката.

## Основные концепции

Приёмка закрывает шесть измерений; пропуск любого из них — типичная причина «работает, но в проде ломается»:

| Измерение | Что проверяем | Основные файлы |
|---|---|---|
| Связность | Handshake, пинг по туннелю и LAN, полный путь MTU, DNS | [wireguard.md](./wireguard.md), [vpn-dns.md](./vpn-dns.md) |
| Маршрутизация | Split/full tunnel, таблицы/fwmark, IPv6, возвратный трафик | [wireguard-routing.md](./wireguard-routing.md), [vpn-ipv6.md](./vpn-ipv6.md) |
| Отказоустойчивость | Фейловер VIP/резерва, восстановление, клиентский failover | [wireguard-ha.md](./wireguard-ha.md) |
| Безопасность | Инвентарь ключей ↔ живые пиры, AllowedIPs минимальны, firewall scope, kill switch | [wireguard-key-management.md](./wireguard-key-management.md), [wireguard-security.md](./wireguard-security.md) |
| Наблюдаемость | Метрики в Prometheus, алерты, canary, аудит-снапшоты | [vpn-monitoring.md](./vpn-monitoring.md), [vpn-session-audit.md](./vpn-session-audit.md) |
| Производительность | iperf3 к baseline, CPU/softirq, UDP-счётчики ядра | [wireguard-performance.md](./wireguard-performance.md) |

Принципы процедуры:

1. **Проверять снаружи, а не с сервера.** Клиенты живут за домашним NAT, в офисной Wi-Fi сети, на LTE — проверки только «с самого шлюза» не отражают реальность.
2. **Каждый пункт — команда с ожидаемым результатом.** Пункт без наблюдаемого результата не проверка, а ритуал.
3. **Откат планируется до выката.** Критерии отката (см. § «Критерии провала») формулируются заранее; процедура отката проговаривается, а не импровизируется.
4. **Изменение одного параметра за раз** при тюнинге по результатам приёмки — иначе невозможно понять, что помогло.

## Практические сценарии

### 0. Перед выкатом

- [ ] Инвентарь актуален: каждому клиенту/пику соответствует владелец и VPN-IP (`inventory.csv` или эквивалент — [wireguard-key-management.md](./wireguard-key-management.md)).
- [ ] Бэкап конфигов шлюза сделан: `sudo tar czf /backup/wireguard-$(date +%F).tar.gz /etc/wireguard/`.
- [ ] План отката: прежний конфиг, команда отката (`wg-quick down wg0 && cp /backup/... && wg-quick up wg0`), ответственный.
- [ ] Алерты мониторинга настроены **до** выката, а не после (иначе первые инциденты пройдут мимо).

### 1. Smoke: связность (сразу после выката)

```bash
# На шлюзе: поднят ли интерфейс и слушает ли порт
sudo wg show wg0
# → interface: wg0 ... listen port: 51820
ss -ulnp | grep 51820
# → UNCONN 0 0 0.0.0.0:51820

# Рукопожатия пиров (выполнить через ~30 с после подключения клиентов)
sudo wg show wg0 latest-handshakes
# → <pubkey>  <epoch>   # epoch свежий (не старше 2–3 минут при активных клиентах)

# С клиента: туннельный IP шлюза и хост в целевой LAN
ping -c3 10.0.0.1
ping -c3 192.168.1.10

# Полный путь MTU (чёрные дыры не уходят в прод)
ping -M do -s 1400 192.168.1.10
# → 64 bytes from ...  (без "Message too long" и зависаний)

# DNS через туннель (если push/split DNS настроен)
resolvectl status wg0 | grep -A2 "DNS Servers"
# → DNS Servers: 10.0.0.1
nslookup internal.example 10.0.0.1
```

### 2. Маршрутизация

```bash
# Куда реально уходит трафик к ресурсу (split tunnel)
ip route get 192.168.1.10
# → 192.168.1.10 dev wg0 src 10.0.0.2

# Полный туннель: default ушёл в wg, но утечек нет
ip route get 1.1.1.1
# → 1.1.1.1 dev wg0 ...

# fwmark-политика (если используется)
ip rule show
# → 50: from all fwmark 0xca6c lookup 100
```

Если задействован IPv6 — дополнительные пункты: [vpn-ipv6.md](./vpn-ipv6.md) (адреса, firewall, PMTUD-счётчики).

### 3. HA: drill фейловера

```bash
# На Active: имитация отказа туннеля (VIP должен уехать на Backup)
sudo systemctl stop wg-quick@wg0
# С клиента (1–5 с): handshake обновится через VIP
ping -c5 10.0.0.1

# Где сейчас VIP
ip addr show eth0 | grep 203.0.113.50
# → inet 203.0.113.50/32 ...        (на Backup)

# Восстановление
sudo systemctl start wg-quick@wg0
```

Критерий: трафик восстановился в пределах объявленного SLA переключения (для Keepalived/VRRP — типично 1–3 с, см. [wireguard-ha.md](./wireguard-ha.md)). Замерьте фактическое время и зафиксируйте.

### 4. Безопасность

```bash
# Живые пиры == инвентарь (расхождения = неучтённый доступ)
sudo wg show wg0 peers | sort > /tmp/live.txt
cut -d, -f3 inventory.csv | grep -v '^pubkey$' | sort > /tmp/inv.txt
diff /tmp/inv.txt /tmp/live.txt
# → пусто (только заведомые пиров)

# AllowedIPs не шире политики
sudo wg show wg0 allowed-ips
```

- [ ] Kill switch проверен на выборочном клиенте: при остановке туннеля наружу не уходит ничего (`curl --max-time 5 ifconfig.me` → timeout).
- [ ] Firewall шлюза: UDP-порт открыт только для доверенных источников/с rate limiting ([wireguard-security.md](./wireguard-security.md)).
- [ ] Приватные ключи на шлюзе: `sudo ls -l /etc/wireguard/*.key` → `-rw------- root root`.

### 5. Наблюдаемость и аудит

- [ ] Prometheus видит экспортер/сборщик: `curl -s localhost:9100/metrics | grep wireguard_` → метрики присутствуют ([vpn-monitoring.md](./vpn-monitoring.md)).
- [ ] Алерт на возраст handshake см. в тестовом вычислении: правило Prometheus загружено (`/api/v1/rules` → success), canary-пир отвечает.
- [ ] Таймер аудита срабатывает: `systemctl list-timers wg-audit-snapshot.timer` → `NEXT ... PASSED` в прошлом; в JSONL-выгрузке свежие строки ([vpn-session-audit.md](./vpn-session-audit.md)).
- [ ] Retention на центральном хранилище логов задан явно.

### 6. Производительность (сравнение с baseline)

```bash
# С клиента до сервера в туннеле (несколько потоков, пропустить прогрев)
iperf3 -c 10.0.0.1 -t 30 -P 4
# Сравнить с baseline "без VPN" того же пути; глубина тюнинга — wireguard-performance.md

# Перекос на ядра / softirq
mpstat -P ALL 1 3
# → искать ядро с ~100% soft
```

Порог деградации задаётся политикой (например, падение к baseline более чем на 15–20 % — сигнал тюнинга MTU/очередей, а не «нормально так»).

### 7. Soak-наблюдение (24–72 ч)

- [ ] Возраст handshake всех активных пиров обновляется (выборка `wg show latest-handshakes` дважды с интервалом суток).
- [ ] `nstat -az | grep -i udp` — `UdpInErrors`/`UdpRcvbufErrors` не растут линейно.
- [ ] Память процессов/ядра и load average стабильны (графики node_exporter).
- [ ] В логах шлюза/аудита нет массовых переподключений (одиночные — норма).

### 8. Клиентский флот

- [ ] Выборка клиентов по ОС (Windows/macOS/Android): туннель поднимается, DNS резолвится, нужные подсети доступны — [wireguard-client-deployment.md](./wireguard-client-deployment.md).
- [ ] Мобильные клиенты за LTE: handshake живёт при смене сети (роуминг) — [wireguard.md](./wireguard.md) (Граничные случаи).
- [ ] Инструкция пользователя и канал поддержки определены.

## Критерии провала (основания для отката)

- Handshake нестабилен на большинстве тестовых клиентов (>50 % без свежего рукопожатия в течение 10 минут).
- Обнаружена чёрная дыра MTU: мелкие пакеты проходят, крупные сессии (scp/бэкапы) висят.
- Failover не укладывается в SLA или после восстановления трафик не возвращается сам.
- Трафик утекает мимо туннеля при активном kill switch/full tunnel.
- Неучтённые пиры в `wg show`, отсутствующие в инвентаре.

Процедура отката: остановить туннель, восстановить бэкап конфига, поднять, оповестить пользователей, разобрать причину в копии среды.

## Очистка

- Удалить тестовые пиры/конфигы, созданные только для приёмки (`wg set wg0 peer <тестовый_pubkey> remove` либо перезапись конфига).
- Убрать временные firewall-правила и NFLOG-цепочки, добавленные для проверок.
- Тестовые снапшоты аудита и метрики пометить/удалить согласно политике retention.
- Зафиксировать результат приёмки (протокол: что проверено, замеры, решения) — это же сокращает время следующей.
