# Внутреннее устройство хранения etcd (BoltDB, bbolt, CoW)

**Актуально для:** etcd 3.7.x (движок bbolt v1.5.1; офлайн defrag через `etcdutl` — 3.6+)

**etcd** хранит данные в двух слоях: `treeIndex` (в памяти) и `BoltDB`/`bbolt` (на диске). Понимание внутреннего устройства критично для диагностики фрагментации, дефрагментации и планирования maintenance.

## Определения

| Термин | Описание |
| :--- | :--- |
| **BoltDB / bbolt** | Встроенная база данных (B+ tree), используемая для персистентного хранения MVCC-данных на диске. `bbolt` — форк BoltDB с оптимизациями для etcd. |
| **Page** | Минимальная единица хранения в bbolt. Размер по умолчанию равен размеру системной страницы ОС (`os.Getpagesize()`, обычно 4 КБ; на части ARM-систем — 64 КБ) и фиксируется при создании БД. |
| **Copy-on-Write (CoW)** | При каждом изменении BoltDB создает новые страницы, а старые помечает как "мертвые" (неиспользуемые). |
| **Freelist** | Список свободных страниц, готовых для повторного использования. Персистится на диске (freelist-страница, адресуемая из meta-страницы); при открытии БД загружается в память целиком. |
| **Freelist backend** | Способ организации freelist: `array` (отсортированный список pgid, бинарный поиск) или `map`/hashmap (аллокация O(1) через хеш-таблицы спанов). Выбор через `--backend-bbolt-freelist-type`; в etcd 3.5.0+ по умолчанию `map`. |
| **Page id (pgid)** | Внутренний идентификатор страницы — 8-байтовое целое (`uint64`). При дефрагментации страницы получают новые id. |

**Prerequisites:** работающий кластер etcd, доступ к client-эндпоинту (`:2379`) и к `/metrics`, `etcdctl`/`etcdutl`, права на чтение `data-dir/member/snap/db`.

## Основные концепции

### Page size и layout страницы

- **Page size:** по умолчанию равен размеру системной страницы ОС (`os.Getpagesize()`; обычно 4 КБ, на части ARM-систем — 64 КБ). Размер записан в meta-странице и не меняется в течение жизни БД.
- **Layout:** страница содержит 16-байтовый заголовок и упакованные подряд leaf/branch-элементы (заголовок элемента — 16 байт: флаги, позиция, размеры ключа и значения). Ключи и значения НЕ выравниваются по границам страниц — они упакованы внутри неё.
- **Overflow pages:** объекты больше page size (ключ + значение) занимают несколько последовательных страниц. Это влияет на fragmentation и скорость чтения.

### Copy-on-Write (CoW) в действии

При выполнении `put /key "value"`:
1. bbolt создает новые страницы с ключом и значением.
2. Старые страницы, содержащие предыдущую версию, становятся "мертвыми".
3. Индекс B+ дерева обновляется, указывая на новые страницы.
4. Мертвые страницы добавляются в Freelist.

**Последствия:**
- **Нет in-place updates:** Старые данные остаются на диске до defrag.
- **Фрагментация:** Разница между физическим размером файла и реальным объемом данных.
- **Write amplification:** Каждое изменение генерирует новые страницы + обновление индекса.

### Freelist: устройство и стоимость открытия БД

Freelist персистится на диске как отдельная страница (или цепочка overflow-страниц при большом числе свободных страниц), адресуемая из meta-страницы. При открытии БД bbolt читает freelist со диска и строит in-memory-структуру — в память загружаются ВСЕ свободные pgid:

- **array backend** (дефолт bbolt): отсортированный список pgid, бинарный поиск O(log N); при большом числе фрагментированных страниц деградирует производительность аллокации.
- **map/hashmap backend** (дефолт etcd с 3.5.0, флаг `--backend-bbolt-freelist-type`): аллокация и поиск O(1) через хеш-таблицы спанов (последовательных страниц); быстрее почти во всех случаях, но не гарантирует выдачу минимального pgid и может занимать больше места в db-файле (наблюдение etcd-druid для малых БД).

**Стоимость открытия:** для 100 ГБ БД с 50% «мёртвых» страниц это ~12.5 млн pgid — десятки секунд на чтение со диска и сотни мегабайт RAM на каждом старте. Это основная причина медленного старта etcd на сильно фрагментированных БД.

**Изменения bbolt v1.5.x (etcd 3.7):** оптимизация merge спанов в hashmap backend (batch contiguous IDs), лимит размера файла БД (`MaxSize` — записи отклоняются до компакции или смены лимита), опция `NoStatistics` (меньше блокировок). Радикального перепроектирования freelist в v1.5 не было.

### Defragmentation: как это работает

`etcdctl defrag` (online):
1. Создается новый временный BoltDB файл.
2. Из старого файла читаются только "живые" страницы (на которые ссылается B+ tree индекс).
3. Живые страницы записываются в новый файл.
4. Старый файл заменяется новым.
5. **Блокировка:** чтение и запись блокируются на время выполнения (официальная документация: "defragmentation to a live member blocks the system from reading and writing data"). Время зависит от объёма перестраиваемых данных — практика AWS EKS: до ~10 с на ГБ.
6. **Freelist reset:** После defrag freelist очищается, так как все мертвые страницы удалены.

**Важно:** defrag НЕ реплицируется по кластеру — применяется только к локальному узлу. Для всех членов используйте `--cluster` (последовательный обход) или перечислите `--endpoints`. Есть также флаг `--bootstrap-defrag-threshold-megabytes`: defrag при старте etcd, если он освободит не менее указанного числа МБ (0 = выключено).

**Офлайн defrag (`etcdutl defrag --data-dir`):**
- Требует остановки etcd (3.6+; в 3.5 offline defrag был через `etcdctl defrag --data-dir`, в 3.6 удалён).
- Полезно, если online defrag не помогает (например, при критической фрагментации и нехватке RAM).

### Формула фрагментации

```text
fragmentation = (db_total_size - db_total_size_in_use) / db_total_size
```

Официальная документация etcd порогов не задаёт; ниже — рабочая эвристика (не из документации etcd):
- **< 30%:** Норма.
- **30–50%:** Требуется планирование defrag.
- **> 50%:** Критично. Выполните `etcdctl defrag`.

Defrag нужен, когда: (a) БД приближается к `quota-backend-bytes` и место должно быть возвращено файловой системе; (b) разрыв между `total` и `in_use` велик и растёт. Сама по себе фрагментация не вредит latency — мёртвые страницы переиспользуются через freelist; вред — в неосвобождённом месте на диске и медленном старте (загрузка freelist).

### Сколько места вернет defrag?

Пример:
```
db_total_size = 4 GB
db_total_size_in_use = 1.5 GB
fragmentation = (4 - 1.5) / 4 = 62.5%
```
После defrag:
```
db_total_size ≈ 1.5 GB + overhead (индексы) ≈ 1.6–1.8 GB
```
**Выигрыш:** ~2.2–2.4 GB.

## Практические сценарии

### Диагностика фрагментации

```bash
# Метрики
curl -s http://localhost:2379/metrics | grep etcd_mvcc_db_total_size
# etcd_mvcc_db_total_size_in_bytes{...} 4294967296      # 4 GB
# etcd_mvcc_db_total_size_in_use_in_bytes{...} 1610612736  # 1.5 GB

# Расчет
fragmentation = (4294967296 - 1610612736) / 4294967296 = 0.625 (62.5%)

# Альтернатива: dbSize и dbSizeInUse через endpoint status
etcdctl -w json endpoint status --cluster
# → "dbSize": 4294967296, "dbSizeInUse": 1610612736

# Размер файла на диске напрямую
ls -l ${ETCD_DATA_DIR}/member/snap/db
```

### Мониторинг роста БД

```bash
# История размера БД (prometheus)
rate(etcd_mvcc_db_total_size_in_bytes[1h])
# Рост зависит от workload (в K8s — от churn ресурсов и retention истории ревизий);
# универсальной нормы нет — отслеживайте тренд и приближение к quota-backend-bytes
```

### Defragmentation timing

Время зависит от объёма живых данных, которые нужно перестроить (практика AWS EKS — до ~10 с на ГБ):
- **Online defrag для 8 ГБ БД на NVMe:** от единиц до десятков секунд блокировки.
- **Offline defrag:** сопоставимо, плюс время остановки etcd.

**Рекомендация:** Выполняйте в часы минимальной нагрузки. Для кластера 3 узлов — поочередно (defrag применяется к одному члену за раз).

## Troubleshooting

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| БД растет, несмотря на compaction | Высокая фрагментация CoW | Выполнить `etcdctl defrag` |
| Defrag занимает > 30 секунд | БД > 20 ГБ или медленный диск | Используйте offline defrag или перейдите на NVMe |
| `etcdserver: database space exceeded` | Достигнут `quota-backend-bytes` | Compaction → defrag → disarm alarm; при необходимости увеличить квоту (макс. 8 ГБ) |
| `etcdserver: mvcc: database corruption` | Повреждение страниц (аппаратный сбой) | Восстановить из снапшота, проверить диски |
| Высокое использование RAM при старте | Большой freelist (много мёртвых страниц) загружается в память при открытии БД | Defrag (уменьшает число свободных страниц); убедиться в достаточном RAM; bbolt v1.5.x оптимизирует merge спанов |

## Best Practices

- **Defrag перед увеличением квоты:** Если БД приближается к `quota-backend-bytes`, сначала compaction + defrag, потом увеличивайте квоту (макс. 8 ГБ).
- **Не превышайте 8 ГБ:** `quota-backend-bytes` по умолчанию 2 ГБ, максимум 8 ГБ. bbolt memory-maps db-файл — большая квота = больше виртуальной памяти процесса. При упирании в 8 ГБ — разделите keyspace между кластерами.
- **NVMe для WAL и db:** HDD и сетевые диски создают нестабильную задержку `fdatasync`, что повышает latency записи и риск потери лидерства (см. ./proposal_pipeline.md).
- **Мониторьте `etcd_mvcc_db_total_size_in_use_in_bytes`:** Это реальный размер данных. Если он растет, а `total` не уменьшается — пора defrag.

## Edge Cases

- **CoW на SSD:** SSD имеют ограниченное количество перезаписей. Высокая фрагментация CoW может сократить срок службы диска. Defrag снижает количество "мертвых" страниц, но сам является write-heavy операцией (перезаписывает все живые данные).
- **Page id overflow:** В bbolt `pgid` — 8-байтовое целое (`uint64`). При 4 КБ страницах адресное пространство ~75 ЗБ — практически неограничено.
- **Defrag во время massive write:** Блокировка чтения и записи может вызвать таймауты на клиентах. Используйте defrag follower'ов или поочередный defrag (`--cluster`).
- **Сбой посреди online defrag (etcd 3.5.0–3.5.5):** была известна проблема рассогласованности данных при падении члена во время online defrag (etcd blog, Jan 2023). На затронутых версиях используйте заплатанные релизы или офлайн defrag через `etcdutl`.
