# Внутреннее устройство хранения etcd (BoltDB, bbolt, CoW)

**etcd** хранит данные в двух слоях: `treeIndex` (в памяти) и `BoltDB`/`bbolt` (на диске). Понимание внутреннего устройства критично для диагностики фрагментации, дефрагментации и планирования maintenance.

## Определения

| Термин | Описание |
| :--- | :--- |
| **BoltDB / bbolt** | Встроенная база данных (B+ tree), используемая для персистентного хранения MVCC-данных на диске. `bbolt` — форк BoltDB с оптимизациями для etcd. |
| **Page** | Минимальная единица хранения в BoltDB (4 КБ). Все операции выровнены по границам страниц. |
| **Copy-on-Write (CoW)** | При каждом изменении BoltDB создает новые страницы, а старые помечает как "мертвые" (неиспользуемые). |
| **Freelist** | Список свободных страниц, готовых для повторного использования. |
| **bbolt v1.5.1 Freelist** | Оптимизированный до O(1) алгоритм управления свободными страницами (по сравнению с O(N) в старом BoltDB). |
| **Page id** | Внутренний идентификатор страницы (4-байтовый). При дефрагментации страницы получают новые id. |

## Основные концепции

### Page size и alignment

- **Page size:** 4 КБ (фиксировано в bbolt).
- **Alignment:** Все ключи, значения и metadata выровнены по границам страниц.
- **Impact:** Объекты > 4 КБ занимают несколько страниц. Это влияет на fragmentation и скорость чтения.

### Copy-on-Write (CoW) в действии

При выполнении `put /key "value"`:
1. bbolt создает новые страницы с ключом и значением.
2. Старые страницы, содержащие предыдущую версию, становятся "мертвыми".
3. Индекс B+ дерева обновляется, указывая на новые страницы.
4. Мертвые страницы добавляются в Freelist.

**Последствия:**
- **Нет in-place updates:** Старые данные остаются на диске до defrag.
- **Фрагментация:** Разница между физическим размером файла и реальным объемом данных.
- **Write amplification:** Каждое изменение генерирует новые страницы + обновление индекса.

### Freelist: old vs new (bbolt v1.5+)

В старом BoltDB:
- Freelist — это B-дерево в памяти.
- При открытии БД загружаются ВСЕ свободные страницы в память.
- Для 100 ГБ БД с 50% фрагментацией это может занять секунды и гигабайты RAM.

В bbolt v1.5+ (используется в etcd 3.7):
- **Freelist — это список страниц в самой БД (на диске).**
- Загружается только номер страницы с freelist (1 страница).
- Доступ к конкретной свободной странице — O(1) через `pgid`.
- **Impact:** etcd может работать с БД > 100 ГБ без пиковых нагрузок на RAM при старте.

### Defragmentation: как это работает

`etcdctl defrag` (online):
1. Создается новый временный BoltDB файл.
2. Из старого файла читаются только "живые" страницы (на которые ссылается B+ tree индекс).
3. Живые страницы записываются в новый файл.
4. Старый файл заменяется новым.
5. **Блокировка:** Запись и чтение блокируются на время выполнения (обычно 1–5 секунд для 8 ГБ БД).
6. **Freelist reset:** После defrag freelist очищается, так как все мертвые страницы удалены.

**Офлайн defrag (`etcdutl defrag --data-dir`):**
- Требует остановки etcd.
- Полезно, если online defrag не помогает (например, при критической фрагментации и нехватке RAM).

### Формула фрагментации

```text
fragmentation = (db_total_size - db_total_size_in_use) / db_total_size
```

- **< 30%:** Норма.
- **30–50%:** Требуется планирование defrag.
- **> 50%:** Критично. Выполните `etcdctl defrag`.

### Сколько места вернет defrag?

Пример:
```
db_total_size = 4 GB
db_total_size_in_use = 1.5 GB
fragmentation = (4 - 1.5) / 4 = 62.5%
```
После defrag:
```
db_total_size ≈ 1.5 GB + overhead (индексы) ≈ 1.6–1.8 GB
```
**Выигрыш:** ~2.2–2.4 GB.

## Практические сценарии

### Диагностика фрагментации

```bash
# Метрики
curl -s http://localhost:2379/metrics | grep etcd_mvcc_db_total_size
# etcd_mvcc_db_total_size_in_bytes{...} 4294967296      # 4 GB
# etcd_mvcc_db_total_size_in_use_in_bytes{...} 1610612736  # 1.5 GB

# Расчет
fragmentation = (4294967296 - 1610612736) / 4294967296 = 0.625 (62.5%)
```

### Мониторинг роста БД

```bash
# История размера БД (prometheus)
rate(etcd_mvcc_db_total_size_in_bytes[1h])
# Ожидаемый рост: ~10–50 MB/час в production K8s (зависит от workload)
```

### Defragmentation timing

Для 8 ГБ БД на NVMe SSD:
- **Online defrag:** 2–5 секунд блокировки.
- **Offline defrag:** 10–20 секунд (зависит от I/O).

**Рекомендация:** Выполняйте в часы минимальной нагрузки. Для кластера 3 узлов — поочередно.

## Troubleshooting

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| БД растет, несмотря на compaction | Высокая фрагментация CoW | Выполнить `etcdctl defrag` |
| Defrag занимает > 30 секунд | БД > 20 ГБ или медленный диск | Используйте offline defrag или перейдите на NVMe |
| `etcdserver: database space exceeded` | Достигнут `quota-backend-bytes` | Defrag + compaction + увеличить квоту |
| `etcdserver: mvcc: database corruption` | Повреждение страниц (аппаратный сбой) | Восстановить из снапшота, проверить диски |
| Высокое использование RAM при старте | Старый BoltDB freelist | Обновитесь до bbolt v1.5+ (etcd 3.7) |

---

## Best Practices

- **Defrag перед увеличением квоты:** Если БД > 8 ГБ, сначала defrag, потом увеличивайте `quota-backend-bytes`.
- **Не превышайте 8 ГБ:** bbolt стабильно работает до 8 ГБ. При превышении — разделяйте кластер или масштабируйте через прокси.
- **NVMe обязателен:** HDD и сетевые диски создают нестабильную задержку `fdatasync`, что ускоряет рост фрагментации из-за retry.
- **Мониторьте `etcd_mvcc_db_total_size_in_use_in_bytes`:** Это реальный размер данных. Если он растет, а `total` не уменьшается — пора defrag.

---

## Edge Cases

- **CoW на SSD:** SSD имеют ограниченное количество перезаписей. Высокая фрагментация CoW может сократить срок службы диска. Defrag снижает количество "мертвых" страниц.
- **Page id overflow:** В bbolt page id — 4-байтовое число. Максимум ~4 миллиарда страниц. На 4 КБ странице это ~16 ТБ. Практически не достижимо.
- **Defrag во время massive write:** Блокировка записи на 2–5 секунд может вызвать таймауты на клиентах. Используйте follower defrag или поочередный defrag.
