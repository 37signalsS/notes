# Управление памятью etcd

**Актуально для:** etcd 3.7.x / 3.6.x / 3.5.x

## Определения

**RSS (Resident Set Size)** — физическая память, занимаемая процессом etcd и учитываемая ОС. Именно она важна для cgroup-лимитов и OOM-killer. Виртуальная память (VSZ) больше RSS из-за memory-mapping файла bbolt и резервирования адресного пространства.

**GOGC** — параметр сборщика мусора Go: процент роста live heap, после которого запускается следующая сборка. Значение по умолчанию — `100` (целевой heap ≈ 2× live heap). `GOGC=off` полностью отключает сборщик.

**GOMEMLIMIT** — мягкий лимит памяти Go runtime (Go 1.19+), включающий Go heap и прочую память под управлением runtime. По умолчанию — `math.MaxInt64` (фактически отключён). Может задаваться как `512MiB`, `8GiB` и т. п.

**Page cache** — кэш страниц файлов ОС. bbolt memory-maps файл БД, поэтому прочитанные страницы учитываются в page cache; при нехватке памяти ядро вытесняет их. Значения ключей из БД читаются через этот кэш, а не держатся в heap etcd целиком.

**treeIndex** — B-дерево в heap, сопоставляющее ключ с историей ревизий. Его размер пропорционален **числу ключей**, а не объёму значений (см. [Внутреннее устройство хранения](./storage_internals.md)).

**Watcher** — подписка клиента на изменения ключей. Каждый watcher потребляет память на сервере; при тысячах подписок это становится одной из главных статей расхода.

**memory-mlock** — флаг etcd 3.7+ (`--memory-mlock`, ранее `--experimental-memory-mlock`). Вызывает `mlock(2)`-блокировку страниц etcd (в частности bbolt), удерживая их в RAM и предотвращая выгрузку на диск при memory pressure; повышает tail latency в условиях свопинга или нестабильной задержки диска. Требует повышения `RLIMIT_MEMLOCK` (или `CAP_IPC_LOCK`).

## Предварительные требования

- **etcd** 3.5+ — для `GOMEMLIMIT` и управляемого heap; 3.7+ — для `--memory-mlock`, RangeStream и cgroup-aware `GOMAXPROCS` (Go 1.26).
- **Доступ к метрикам** `/metrics` (клиентский порт, 2379): `process_resident_memory_bytes`, `go_memstats_heap_inuse_bytes`, `go_memstats_next_gc_bytes`, `etcd_mvcc_db_total_size_in_bytes`.
- **Доступ к `etcdctl`/`etcdutl`** и к журналу ядра (`dmesg`/`journalctl -k`) для диагностики OOM.
- **Контейнеры:** заданный `memory limit`; при `--memory-mlock` — повышенный `ulimit -l` (memlock).

## Из чего складывается память etcd

| Компонент | Где живёт | От чего зависит |
| :--- | :--- | :--- |
| treeIndex | Go heap | Число ключей (практическая оценка 150–300 байт/ключ) |
| Watchers и их буферы | Go heap | Количество подписок и скорость изменений |
| Буферы gRPC / входящие запросы | Go heap | Размер и число одновременных запросов; в 3.7+ RangeStream снимает зависимость от размера выборки |
| Значения ключей | page cache (mmap bbolt) | Объём и «горячесть» данных; вытесняется ОС при давлении |
| Freelist bbolt | Go heap + ОС | Число свободных страниц (растёт с фрагментацией, грузится при старте) |
| WAL, снапшоты, запасы | ОС/runtime | Настройки Raft-истории (`--snapshot-count`) |

Ключевой вывод: **основной управляемый вклад в фиксированную память — treeIndex и watcher'ы; значения ключей в основном reside в page cache и не «весят» столько же в heap.** Отсюда рост памяти при увеличении числа ключей и подписок, а не только объёма данных.

Формула оценки treeIndex и таблица «ключи → RAM» приведены в [Лимитах и ограничениях](./limits_and_constraints.md). Косвенные механизмы, освобождающие память (компакция MVCC, дефрагментация, снижение `--snapshot-count`), — в [Хранении](./storage_internals.md) и [MVCC и компакции](./mvcc_versioning_and_compaction.md).

## Рекомендации по объёму (официально)

Официальная документация etcd (op-guide/hardware, v3.7):

- «etcd агрессивно кеширует key-value данные и тратит почти всю остальную память на отслеживание watcher'ов. Обычно достаточно **8 GB**. Для тяжёлых развёртываний с тысячами watcher'ов и миллионами ключей выделяйте **16–64 GB**.»
- Классы кластеров (GCE):

| Класс | Профиль (клиенты / req/s / данные) | GCE | vCPU | RAM |
| :--- | :--- | :--- | :--- | :--- |
| Small | < 100 / < 200 / ≤ 100 MB | n1-standard-2 | 2 | 7.5 GB |
| Medium | < 500 / < 1000 / ≤ 500 MB | n1-standard-4 | 4 | 15 GB |
| Large | < 1500 / < 10 000 / ≤ 1 GB | n1-standard-8 | 8 | 30 GB |
| xLarge | > 1500 / > 10 000 / > 1 GB | n1-standard-16 | 16 | 60 GB |

Важно: RAM выделяется с запасом над прогнозируемым RSS. Кластер Kubernetes с массой контроллеров и информеров держит много watcher'ов на стороне `kube-apiserver`, но подписки на самом etcd тоже растут.

## Тюнинг сборщика мусора Go

etcd — Go-приложение, и его heap управляется стандартным GC. Диапазон настройки задают `GOGC` и `GOMEMLIMIT`.

Начиная с Go 1.25 рантайм по умолчанию подстраивает `GOMAXPROCS` под лимит CPU cgroup (в etcd 3.7 используется **Go 1.26.x**, см. `go.mod`), поэтому `GOMAXPROCS` задавать вручную обычно не требуется. `GOMEMLIMIT` при этом **не** выставляется автоматически и требует явной установки — см. ниже.

### GOGC

- Значение по умолчанию `100`: следующая сборка запускается, когда heap вырастает примерно вдвое от live heap.
- **Понижение** (`GOGC=50`) уменьшает пиковую память, но увеличивает частоту сборок и потребление CPU.
- **Повышение** (`GOGC=200`) сокращает CPU-затраты на GC, но увеличивает пиковую память до ~3× live heap.

Для etcd это существенный компромисс: тяжёлые кластеры и так CPU-bound (см. [Тюнинг ОС](./kernel_tuning.md)), поэтому агрессивное снижение GOGC может ухудшить latency. Понижайте GOGC только при реальном давлении на память и наличии запаса CPU.

### GOMEMLIMIT

- Мягкий потолок памяти runtime; при приближении к нему GC начинает работать чаще, не давая перерасти лимит.
- По умолчанию отключён (`math.MaxInt64`). etcd не устанавливает его автоматически.
- **Практика для контейнеров (Kubernetes):** задавать `GOMEMLIMIT` чуть ниже жёсткого лимита контейнера, чтобы Go не позволил heap выйти за него и процесс не был убит OOM-killer'ом:

```yaml
# фрагмент манифеста etcd (kind/StatefulSet)
env:
  - name: GOMEMLIMIT
    value: "6GiB"     # ниже memory limit контейнера, оставляя запас
resources:
  limits:
    memory: "8Gi"
```

`GOMEMLIMIT` можно задать и как `GOGC=off` + лимит: тогда GC фактически управляется только порогом памяти. Это допустимо, но требует точного лимита и мониторинга — при неверной настройке latency растёт из-за частых сборок.

**Важно:** GOMEMLIMIT не учитывает внешнюю память (page cache, управляемый ОС, mmap-файлы вне учёта runtime). Ориентируйтесь на RSS, а не только на Go-heap.

## Почему память не возвращается после компакции

Частый вопрос при эксплуатации: «сделали компакцию/дефрагментацию, а RSS не упал». Причины:

1. **Компакция MVCC освобождает версии в логике**, но heap, выделенный аллокатором Go, не возвращается ОС мгновенно — освобождённые объекты остаются доступны аллокатору и отдаются ОС лениво.
2. **treeIndex уменьшается** только при сокращении числа ключей, а не версий (`deleted`-версии хранятся до компакции, потом удаляются).
3. **Дефрагментация уменьшает файл bbolt**, что снижает будущий page cache и freelist при рестарте, но не обязательно снижает текущий RSS.
4. **Freelist грузится целиком при старте** — дефрагментация уменьшает его и ускоряет/облегчает запуск (см. [Хранение](./storage_internals.md)).

Практический ориентир: сравнивайте RSS с **числом ключей**, а не с размером всей истории; после массовых удалений проверяйте defrag и перезапуск узлов по очереди (rolling restart), чтобы вернуть память ОС.

## Контейнеры и cgroup-лимиты

- **Не занижайте memory limit** ниже потребности etcd: OOM-kill процесса etcd приводит к смене лидера и возможной потере доступности записи.
- **Оставляйте запас** над прогнозируемым RSS (обычно 20–30%) для пиков (снапшоты, всплески watcher'ов, компиляция GC).
- **Учитывайте mmap:** bbolt memory-maps файл БД; при большой `--quota-backend-bytes` виртуальная память растёт, а при активном чтении — и page cache. `GOMEMLIMIT` эти страницы не ограничивает.
- **`GOGC`/`GOMEMLIMIT` задавайте через переменные окружения** в unit-файле systemd или в манифесте пода; не путайте с серверными флагами etcd.

Пример для systemd:

```ini
[Service]
Environment=GOGC=80
Environment=GOMEMLIMIT=12GiB
ExecStart=/usr/local/bin/etcd --config-file=/etc/etcd/etcd.conf.yml
```

## Мониторинг памяти

- **RSS:** `process_resident_memory_bytes` — основной сигнал для алерта (например, > 80–90% лимита). Задаётся в [Мониторинге](./etcd_monitoring.md).
- **Go heap:** `go_memstats_alloc_bytes`, `go_memstats_heap_inuse_bytes`, `go_memstats_sys_bytes` — разница между alloc и sys показывает запас/фрагментацию heap.
- **Данные и фрагментация:** `etcd_mvcc_db_total_size_in_bytes` против `etcd_mvcc_db_total_size_in_use_in_bytes`.
- **Число ключей и watchers:** диагностика «что именно выросло» — `etcdctl endpoint status` (dbSize) и подсчёт подписок на стороне приложения.
- **OOM-события:** `dmesg`/`journalctl -k` (OOM-killer), события Kubernetes `OOMKilled` для пода etcd.

## Практический сценарий: подбор и валидация лимитов памяти

Пошаговый алгоритм настройки памяти etcd в контейнере:

1. **Оцените нагрузку.** Посчитайте число ключей и активных watchers; сравните `db_size` с квотой (см. [Лимиты](./limits_and_constraints.md)).
2. **Выберите класс hardware** по рекомендациям в разделе «Рекомендации по объёму (официально)» — на выделенной машине/поде с запасом.
3. **Задайте лимиты:** `memory limit` контейнера — сверху; `GOMEMLIMIT` — чуть ниже лимита; при `--memory-mlock` — повысьте `ulimit -l`.
4. **Валидируйте** настройки и текущее потребление.

```bash
# 1) Лимит памяти контейнера (cgroup v2; в v1 — memory.limit_in_bytes)
cat /sys/fs/cgroup/memory.max
# → 8589934592   # 8 GiB

# 2) GOMEMLIMIT, применённый к процессу etcd (через /proc/<pid>/environ)
tr '\0' '\n' < /proc/$(pidof etcd)/environ | grep GOMEMLIMIT
# → GOMEMLIMIT=6GiB

# 3) RSS и heap в метриках etcd
curl -s http://localhost:2379/metrics | grep -E 'process_resident_memory_bytes|go_memstats_heap_inuse_bytes'
# → process_resident_memory_bytes 6291456000   # чуть ниже memory limit — ок
# → go_memstats_heap_inuse_bytes 268435456      # 256 MiB живого heap

# 4) Размер БД и фрагментация
curl -s http://localhost:2379/metrics | grep -E 'etcd_mvcc_db_total_size(_in_use)?_in_bytes'
# → etcd_mvcc_db_total_size_in_bytes 1288490188        # ~1.2 ГБ выделено
# → etcd_mvcc_db_total_size_in_use_in_bytes 966367640  # ~0.9 ГБ живые данные
```

**Критерий нормы:** `GOMEMLIMIT` равен заданному значению (env‑переменная применилась); `process_resident_memory_bytes` держится **ниже** `memory limit` контейнера с запасом ~20–30%; `go_memstats_heap_inuse_bytes` растёт пропорционально числу ключей и watchers, а не объёму значений; фрагментация БД (разница `total − in_use`) — ниже 30%.

**Контроль после изменений:** после правки `GOMEMLIMIT`/`memory limit` подождите один–два GC‑цикла — при приближении к лимиту `go_memstats_next_gc_bytes` снижается (GC срабатывает чаще), а `process_resident_memory_bytes` не должен приближаться к лимиту более чем на 90%. Если RSS не снимается после `defrag` — выполните rolling restart по очереди.

## Troubleshooting

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| etcd-под убит `OOMKilled` | memory limit контейнера ниже RSS | Поднять лимит; задать `GOMEMLIMIT` ниже лимита; снизить число ключей/watcher'ов |
| RSS растёт, ключей не прибавилось | Утечка watcher'ов/подписок, всплеск запросов | Проверить клиентов (не создают ли лишние watch), ограничить буферы |
| Память высокая после удаления ключей | Фрагментация heap/freelist, treeIndex не уменьшился | Дождаться компакции, выполнить defrag, rolling restart |
| Высокий CPU после снижения GOGC | Слишком частые сборки | Вернуть GOGC ближе к 100 или выше; использовать GOMEMLIMIT вместо агрессивного GOGC |
| Медленный старт + высокий RSS при старте | Большой freelist загружается целиком | Дефрагментация БД; пересмотреть квоту |
| Пики памяти на больших `get --prefix` | Полная буферизация ответа (до 3.7) | Обновиться до 3.7 (RangeStream) или использовать `--limit` / пагинацию |

## Best Practices

- Планируйте RAM от **числа ключей и watcher'ов**, а не от объёма значений.
- Держите `GOMEMLIMIT` **ниже** memory limit контейнера; не выключайте GC без явного лимита.
- Не понижайте `GOGC` агрессивно на CPU-bound кластерах.
- Регулярно дефрагментируйте узлы по очереди; выполняйте rolling restart для возврата памяти после массовых удалений.
- Уберите устаревшие override, снижающие оптимизации 3.6 (`--snapshot-count=100000`) — см. [Лимиты](./limits_and_constraints.md).
- Настройте алерт на `process_resident_memory_bytes` и OOM-события заранее.
