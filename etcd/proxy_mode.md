# Прокси-режим и масштабирование etcd

**etcd Proxy** — это режим работы узла, при котором он не участвует в Raft-консенсусе как голосующий член, а выступает в качестве "прозрачного" посредника для клиентских запросов. Используется для снижения нагрузки на основной кластер и разделения read/write трафика.

## Определения

| Термин | Описание |
| :--- | :--- |
| **Proxy Mode** | Режим работы узла, при котором он пересылает клиентские запросы на лидер или follower без участия в Raft-консенсусе. |
| **ReadOnly Proxy** | Прокси, который обслуживает только read-запросы (including linearizable reads через ReadIndex). |
| **Leader Proxy** | Прокси, который пересылает все запросы (включая writes) на текущего лидера. |
| **Fan-out** | Паттерн, при котором один прокси обслуживает множество клиентов, снижая нагрузку на основной кластер. |
| **Capacity Planning** | Процесс расчета требуемых ресурсов (диск, RAM, CPU) и архитектуры кластера для anticipated load. |

---

## Основные концепции

### Архитектура прокси

etcd поддерживает два режима прокси:

1. **`--proxy=readonly` (рекомендуется для read-heavy workloads):**
   - Кластер состоит из 3-5 голосующих узлов + N прокси.
   - Прокси обслуживает read-запросы (Get, Watch, Txn с reads).
   - Для линейного чтения прокси отправляет ReadIndex на лидера, но не участвует в кворуме.
   - Write-запросы пересылаются на лидер.
   - **Преимущество:** read-нагрузка масштабируется горизонтально без увеличения кворума.

2. **`--proxy=on` (leader proxy):**
   - Прокси пересылает все запросы (read и write) на лидера.
   - Используется для load balancing client traffic и сокрытия лидера от клиентов.
   - **Ограничение:** не обеспечивает read scalability (все reads идут на лидера).

### Когда использовать прокси

| Сценарий | Режим | Обоснование |
| :--- | :--- | :--- |
| > 1000 подов K8s, read-heavy | `readonly` | Снижает нагрузку на лидера; масштабирует reads |
| > 5000 подов K8s, mixed workload | `readonly` + external LB | Разделяет read/write трафик; прокси — дешевые узлы |
| Скрытие лидера от клиентов | `on` | Клиенты подключаются к прокси, unaware of leader |
| Geo-распределенный кластер | `readonly` в каждом ДЦ | Локальные прокси обслуживают reads из ближайшего ДЦ |

### Ограничения прокси

- **Линеаризуемость:** ReadOnly proxy обеспечивает линейность, но добавляет 1 RTT (proxy → leader → proxy).
- **Watch:** Прокси поддерживает Watch, но при reconnect клиент должен использовать `--rev` для resume.
- **Голосование:** Прокси не участвует в выборах и не влияет на кворум.
- **Alarm:** Прокси не поднимает алармы NOSPACE/CORRUPT, так как не хранит данные.

## Практические сценарии

### Развертывание ReadOnly Proxy

```bash
# На прокси-узле (не имеет права голоса, не требует data-dir с данными)
etcd --proxy=readonly \
  --listen-client-urls=https://10.0.2.10:2379 \
  --advertise-client-urls=https://10.0.2.10:2379 \
  --initial-cluster=node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380,node3=https://10.0.1.12:2380 \
  --listen-peer-urls=https://10.0.2.10:2380 \
  --peer-urls=https://10.0.2.10:2380
```

**Валидация:**
```bash
# Проверить, что узел не является членом кластера
etcdctl member list
# → Прокси отсутствует в списке

# Проверить, что запрос проходит через прокси
curl -s http://10.0.2.10:2379/metrics | grep etcd_server_has_leader
# → etcd_server_has_leader 1
```

### Развертывание Leader Proxy (Load Balancer)

```bash
etcd --proxy=on \
  --listen-client-urls=https://10.0.2.10:2379 \
  --advertise-client-urls=https://10.0.2.10:2379 \
  --listen-peer-urls=https://10.0.2.10:2380 \
  --initial-cluster=node1=https://10.0.1.10:2380,node2=... \
  --peer-urls=https://10.0.2.10:2380
```

### Capacity Planning: Формулы и расчеты

**Пример:** Кластер K8s на 5000 узлов с ~50 000 подов и ~200 000 секретов/configmap.

**Размер БД:**
- Средний размер ключа (key + value + metadata): ~150–300 байт.
- 300 000 объектов × 200 байт ≈ 60 МБ чистых данных.
- С учетом версионирования и истории (compaction retention 5m): ~2–3× overhead.
- **Итого:** ~180–200 МБ. Даже при росте до 1M объектов — ~600 МБ.

**Требования к кластеру:**
- **3 узла** достаточно для HA.
- **Диск:** 20–30 ГБ (с запасом на рост, snapshot, WAL).
- **RAM:** 8 ГБ (treeIndex для 300K ключей займет ~1–2 ГБ).
- **CPU:** 4 cores (etcd требует выделенных ядер).

**Правило:**
- **< 100 000 ключей:** 3 узла, 8 ГБ RAM, 20 ГБ SSD.
- **100 000 – 1 000 000 ключей:** 3 узла, 16 ГБ RAM, 50 ГБ NVMe.
- **> 1 000 000 ключей:** Рассмотреть external etcd + прокси или разделение на несколько кластеров (Events vs Critical resources).

### Scaling to 5000+ nodes: Architecture Pattern

```
[ API Server ] → [ External LB ] → [ Proxy Pool (readonly) ]
                                          ↓
                                    [ etcd Cluster ] (3-5 nodes, NVMe)
```

**Прокси-пул:**
- 2–5 прокси-узлов на 5000+ подов.
- Deploy как DaemonSet или Deployment с `hostNetwork: false`.
- Клиенты (API-сервер) подключаются к LB, который распределяет по прокси.

**Best Practices:**
- Размещайте прокси в тех же AZ, что и клиенты, чтобы минимизировать RTT.
- Используйте локальные прокси в каждом ДЦ для geo-распределенных кластеров.
- Мониторьте `etcd_server_compact_index_gap` и `etcd_mvcc_db_total_size_in_bytes` на основном кластере.

## Troubleshooting

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| Прокси не может подключиться к кластеру | Неверный `--initial-cluster` или TLS | Проверить `--initial-cluster`, `--peer-urls`, сертификаты |
| Read latency высокая через прокси | Прокси → leader RTT большой | Разместить прокси ближе к лидеру или использовать follower proxy (если supported) |
| Клиенты получают stale reads | Прокси использует serializable read вместо linearizable | Убедиться, что прокси в `readonly` режиме (не `on`), и лидер доступен |
| Прокси не появляется в `member list` | Ожидаемо: прокси не является членом | Это корректное поведение; проверять доступность через `endpoint status` |

---

## Best Practices

- **Не используйте прокси для writes-heavy workloads:** Прокси добавляет latency; лучше напрямую подключаться к лидеру.
- **Не размещайте прокси на тех же узлах, что и etcd-члены:** Изолируйте ресурсы (CPU, network).
- **Мониторьте лидера через прокси:** `etcd_server_has_leader` на прокси должен быть 1.
- **Capacity planning:** Ориентируйтесь на 300–500 байт на объект K8s (с учетом версионирования). При приближении к 8 ГБ — масштабируйте через прокси или разделяйте кластеры.
- **Backup:** Резервное копирование выполняется на голосующих узлах, не на прокси.
