# Архитектура etcd: концепция key-value

## Пространство ключей и логическая модель

etcd — распределённое, согласованное хранилище пар ключ-значение. Ключи представляют собой байтовые строки, обычно записываемые как иерархические пути вида `/app/env/service/config`. Пространство ключей упорядочено лексикографически, что позволяет эффективно выполнять операции по префиксу и диапазону.

Базовый элемент — пара key-value. Значения — произвольные байтовые данные (часто JSON/YAML), но сами по себе etcd не интерпретирует их структуру. Важнейшая идея — версионность данных через механизм MVCC (multi-version concurrency control). Каждое изменение создает новую глобальную ревизию, а записи в ключах получают атрибуты create_revision, mod_revision и version.

## MVCC, ревизии и компактирование

MVCC обеспечивает неизменяемую историю состояний: чтения могут указывать конкретную ревизию, получая срез данных в точке времени. Это критично для детерминизма и повторяемости конфигураций.

- revision — монотонно возрастающий номер глобального состояния кластера;
- version — счётчик изменений конкретного ключа;
- mod_revision — ревизия, в которой ключ был изменён в последний раз.

История не бесконечна: периодически выполняется compact(rev), отбрасывающий старые версии до заданной ревизии. Компактирование поддерживает размер хранилища и ускоряет операции, сохраняя при этом актуальные данные.

## Согласованность и Raft

Гарантии линейаризуемых операций обеспечиваются консенсусом Raft: записи проходят через лидера и реплицируются на большинство узлов. Чтения могут быть:

- линейаризуемыми (по умолчанию), когда чтение подтверждается лидером;
- сериализуемыми (быстрее, допускают stale-данные при сетовых аномалиях).

## Иерархия ключей и диапазоны

Иерархическая структура — соглашение на уровне ключей. Часто используются шаблоны:

- /configs///...
- /locks/
- /leases/

Лексикографический порядок позволяет:

- get c префиксом для “дерева” настроек;
- диапазоны [start, end) для сканирования сегментов пространства.

## Транзакции и сравнения

Транзакции строятся на сравнении текущего состояния (Compare) и условных действиях (Then/Else). Типичный паттерн — CAS (compare-and-swap) по полям version или mod_revision, исключающий гонки при конкурентных обновлениях.

## Лизы и TTL

Лиз (lease) — серверный объект со сроком жизни. Значения, привязанные к лизу, удаляются автоматически при истечении TTL, что удобно для регистраций сервисов, временных флагов и сессий. Клиент может продлевать lease keep-alive, поддерживая актуальность данных.

## Наблюдения (watch)

Watch подписывает клиента на события изменений ключа или префикса, начиная с заданной ревизии. Это ключевой механизм реактивных конфигураций и сервис-дискавери: клиенты мгновенно получают уведомления об обновлениях.

## Краткая сводка понятий

| Понятие | Назначение |
|---|---|
| key/value | Единица данных; ключ — индекс, значение — полезная нагрузка |
| revision | Глобальная точка состояния для линейаризуемых операций |
| version | Число изменений конкретного ключа |
| lease (TTL) | Временная привязка для автоудаления данных |
| watch | Стрим событий изменений для ключа/префикса |
| compact | Сжатие исторических версий до заданной ревизии |

## Минимальные примеры с etcdctl

```bash
# запись и чтение
etcdctl put /configs/api/url https://svc.local
etcdctl get /configs/api/ --prefix

# транзакция CAS по version
etcdctl txn <<'EOF'
cmp
version("/configs/api/url") = 1
then
put /configs/api/url https://new-svc.local
else
get /configs/api/url
EOF

# lease и TTL
lease_id=$(etcdctl lease grant 60 | awk '{print $2}')
etcdctl put --lease=$lease_id /sessions/user123 alive
etcdctl lease keep-alive $lease_id

# наблюдение за изменениями
etcdctl watch /configs/api/ --prefix
```
