# Архитектура и основные концепции etcd

### Определения

**etcd** — это распределённое, согласованное и отказоустойчивое хранилище данных в формате "ключ-значение". Оно служит центральным источником истины (Single Source of Truth) для конфигураций, обнаружения сервисов (service discovery) и координации распределённых систем.

| Концепция | Назначение |
|---|---|
| **Key-Value Store** | Основная модель данных. Ключ — байтовая строка (часто в виде пути), значение — произвольные байтовые данные. |
| **Lease (Аренда)** | Механизм для создания эфемерных (временных) ключей, которые автоматически удаляются по истечении срока жизни (TTL). |
| **Watch (Наблюдение)** | API для подписки на изменения ключей или их диапазонов в реальном времени. |
| **Revision (Ревизия)** | Глобальный номер версии всего хранилища, который делает возможным чтение данных "на момент времени". |
| **Transaction (Транзакция)** | Атомарная операция "сравнить и выполнить" (compare-and-swap), позволяющая безопасно изменять данные в конкурентной среде. |

---

### Основные концепции

#### Пространство ключей

Ключи в etcd лексикографически упорядочены. Хотя etcd не имеет встроенной концепции "папок", принято использовать иерархическую структуру имён, разделяя компоненты слэшем, например: `/services/production/api/config`. Этот подход позволяет эффективно запрашивать целые "каталоги" с помощью запросов по префиксу.

#### Аренда (Lease) и эфемерные ключи

Lease — это объект на стороне сервера etcd с заданным временем жизни (TTL). Ключи можно привязать к аренде. Пока аренда активна (клиент должен периодически отправлять keep-alive сигналы), связанные с ней ключи существуют. Как только TTL аренды истекает, все привязанные ключи автоматически удаляются. Это основной механизм для регистрации сервисов и реализации блокировок.

#### Наблюдение за изменениями (Watch)

Клиенты могут устанавливать "наблюдателей" за ключами или диапазонами ключей (по префиксу). etcd будет в реальном времени отправлять поток событий (создание, обновление, удаление) по всем изменениям, соответствующим подписке. Это позволяет системам динамически реагировать на смену конфигурации без постоянных опросов (polling).

#### Согласованность и версионирование

* **Консенсус**: Надёжность и согласованность данных в кластере обеспечивается [**алгоритмом Raft**](raft_consensus.md). Все операции записи проходят через лидера и реплицируются на большинство узлов.
* **Версионирование**: Каждое изменение в хранилище создаёт новую глобальную ревизию. Это реализуется через механизм [**MVCC (Multi-Version Concurrency Control)**](mvcc_versioning_and_compaction.md), который хранит множество версий данных и позволяет читать состояние на любой момент времени.

### Практические сценарии

Примеры использования основных команд `etcdctl`.

**Запись и чтение по префиксу:**

```bash
# Запись ключа
etcdctl put /configs/api/url https://svc.local

# Чтение всех ключей с префиксом /configs/api/
etcdctl get /configs/api/ --prefix
```

**Транзакция (Compare-and-Swap):**
Обновить URL, только если его версия (`version`) равна 1.

```bash
etcdctl txn <<'EOF'
cmp
version("/configs/api/url") = 1
then
put /configs/api/url https://new-svc.local
else
get /configs/api/url
EOF
```

**Использование аренды (Lease) для регистрации сервиса:**

```bash
# Создать аренду на 60 секунд
lease_id=$(etcdctl lease grant 60 | awk '{print $2}')

# Привязать ключ к аренде и периодически обновлять TTL
etcdctl put --lease=$lease_id /services/api/node1 "10.0.1.10:8080"
etcdctl lease keep-alive $lease_id
```

**Наблюдение за изменениями конфигурации:**

```bash
# Наблюдать за всеми изменениями в /configs/api/
etcdctl watch /configs/api/ --prefix
```

### Мониторинг ETCD

Мониторинг ETCD является критически важным для обеспечения стабильности и надежности Kubernetes-кластера, поскольку ETCD служит центральным хранилищем состояния кластера. Проблемы с производительностью или доступностью ETCD напрямую влияют на работоспособность всего Kubernetes.

**Ключевые аспекты мониторинга ETCD:**

1.  **Работоспособность и лидерство (Health & Leader Status)**:
    *   Проверка того, что ETCD-узлы находятся в состоянии `healthy` и что в кластере выбран лидер. Отсутствие лидера или нездоровые узлы указывают на серьезные проблемы консенсуса.
    *   Метрики: `etcd_server_has_leader`, `etcd_server_health_failures`.
2.  **Производительность (Performance)**:
    *   Мониторинг задержек запросов на чтение/запись (`read/write latency`) для оценки отклика ETCD на операции. Высокие задержки могут замедлять работу API-сервера Kubernetes.
    *   Метрики: `etcd_network_peer_round_trip_time_seconds`, `etcd_disk_wal_fsync_duration_seconds`, `etcd_disk_backend_commit_duration_seconds`.
3.  **Использование ресурсов (Resource Utilization)**:
    *   Мониторинг использования CPU, памяти и дискового пространства ETCD-процессами. Чрезмерное потребление ресурсов может указывать на утечки или неэффективную работу.
    *   Метрики: `process_cpu_seconds_total`, `process_virtual_memory_bytes`, `etcd_debugging_mvcc_db_total_size_in_bytes`.
4.  **Размер базы данных (Database Size)**:
    *   Контроль размера базы данных ETCD. Постоянный рост размера может привести к проблемам с производительностью и исчерпанием дискового пространства. Важно регулярно проводить `compaction` для освобождения места.
    *   Метрики: `etcd_mvcc_db_total_size_in_bytes`.

**Вызовы при мониторинге ETCD:**

*   **TLS-аутентификация**: ETCD по умолчанию использует TLS для безопасности. Инструменты мониторинга (например, Prometheus) должны быть настроены на использование клиентских сертификатов для доступа к конечным точкам метрик ETCD.
*   **Динамические IP-адреса**: Если ETCD запускается как Pods в Kubernetes, его IP-адреса могут меняться, что требует использования механизмов Service Discovery (например, Kubernetes Service и Endpoint) для надежного сбора метрик.
