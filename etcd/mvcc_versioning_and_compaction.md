# MVCC, версионирование и транзакции в etcd

## Определения

**MVCC (Multi-Version Concurrency Control)** — это механизм управления параллельным доступом, который etcd использует для надёжной и предсказуемой работы с данными. Вместо того чтобы блокировать данные при чтении или записи, MVCC создаёт новую версию записи при каждом изменении. Это обеспечивает "снимок" данных во времени, позволяя клиентам читать согласованное состояние хранилища без блокировок.

| Термин | Описание |
|---|---|
| **Revision (Ревизия)** | Глобальный, монотонно возрастающий номер, который инкрементируется при любой операции записи в кластере. Функционирует как логические часы. |
| **modRevision** | Ревизия, в которой ключ был последний раз изменён. |
| **createRevision** | Ревизия, в которой ключ был создан. |
| **Version** | Счётчик количества изменений для конкретного ключа. Увеличивается при каждом `put` или `delete`. |
| **Compaction (Компакция)** | Процесс очистки устаревших версий (ревизий) данных для освобождения места и поддержания производительности. |

## Basic Concepts

### Модель данных

Каждая пара "ключ-значение" в etcd хранит не только свои данные, но и метаданные MVCC. Это позволяет запрашивать историю изменений и выполнять условные операции. Когда ключ удаляется, он не исчезает физически, а помечается как удалённый (tombstone) до момента компакции.

### Чтение данных по ревизии

Клиенты могут запрашивать значение ключа, каким оно было на определённую ревизию. Это ключевая возможность для синхронизации состояний и отладки, так как позволяет получить детерминированный срез данных.

```bash
# Получить значение ключа на момент ревизии 12
etcdctl get /cfg/app/db --rev=12
```

Если запрошенная ревизия уже была удалена в ходе компакции, etcd вернёт ошибку `etcdserver: mvcc: required revision has been compacted`.

### История изменений и её очистка

Поскольку каждая операция создаёт новые данные, хранилище может быстро расти. **Компакция** решает эту проблему, удаляя информацию о ревизиях, предшествующих указанной. После компакции до ревизии `R` становится невозможно прочитать состояние ключей на ревизиях `< R`.

## Practical Scenarios

### Атомарные операции "Compare-and-Swap" (CAS)

Транзакции в etcd позволяют выполнять атомарные операции на основе текущего состояния ключа. Это предотвращает состояние гонки (race conditions) при конкурентных обновлениях. Чаще всего сравнение идёт по `modRevision` или `version`.

Пример: обновить ключ, только если его никто не изменял с момента прочтения (версия `3`).

```bash
etcdctl txn <<'EOF'
cmp
version("/feature/flag") = "3"
then
put /feature/flag "enabled"
else
get /feature/flag
EOF
```

Если условие в `cmp` истинно, выполнится блок `then`, иначе — `else`.

### Настройка автоматической компакции

Рекомендуется настраивать автоматическую компакцию на сервере etcd, чтобы избежать ручного вмешательства.

* **По времени (`periodic`)**: Удалять ревизии старше определённого периода. Удобно для систем, где важно хранить историю за последние N часов.

    ```
    --auto-compaction-mode=periodic --auto-compaction-retention=24h
    ```

* **По ревизиям (`revision`)**: Сохранять только последние N ревизий. Подходит для высоконагруженных систем, где время не так важно, как количество изменений.

    ```
    --auto-compaction-mode=revision --auto-compaction-retention=10000
    ```

Выбор стратегии зависит от требований клиентов. Например, если у вас есть `watch`-подписчики, которые могут временно отключаться или медленно обрабатывать события, слишком агрессивная компакция приведёт к разрыву их сессии. Они не смогут возобновить `watch` с последней известной ревизии, если она уже была удалена, и получат ошибку `etcdserver: mvcc: required revision has been compacted`.

## Additional Information

### Взаимосвязь с другими подсистемами etcd

Механизм MVCC тесно связан с другими подсистемами etcd:

* **Watch (Наблюдение)**: Наблюдатели получают поток изменений, начиная с определённой ревизии.
* **Lease (Аренда)**: Истечение аренды вызывает операцию удаления, которая также создаёт новую ревизию.
