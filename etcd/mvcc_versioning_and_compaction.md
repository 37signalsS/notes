# MVCC, версионирование и компакция в etcd

**MVCC (Multi-Version Concurrency Control)** — это механизм управления параллельным доступом, который etcd использует для обеспечения строгой согласованности и возможности чтения исторических данных. Вместо перезаписи данных etcd создает новую версию (ревизию) для каждого изменения.

## Определения

| Термин | Описание |
| :--- | :--- |
| **Revision (Ревизия)** | Глобальный, монотонно возрастающий номер версии всего хранилища. Каждая операция записи инкрементирует ревизию. |
| **modRevision** | Номер ревизии последнего изменения конкретного ключа. |
| **createRevision** | Номер ревизии, при которой ключ был создан. |
| **Version** | Счетчик количества изменений (версий) конкретного ключа. Сбрасывается при удалении. |
| **Consistent Index** | Внутренний индекс, отслеживающий последнюю примененную операцию Raft. Гарантирует атомарность между логом Raft и MVCC-хранилищем. |
| **Compaction (Компакция)** | Процесс удаления устаревших ревизий из истории для освобождения места и поддержания производительности. |

## Основные концепции

### Модель MVCC и хранение на диске

etcd хранит данные в двух структурах:
1. **treeIndex (в памяти)**: B-дерево, сопоставляющее ключ пользователя с историей его ревизий.
2. **BoltDB (на диске)**: B+ дерево, где ключом является номер ревизии, а значением — метаданные и само значение пользователя.

Такая архитектура позволяет выполнять эффективные запросы "на момент времени" (Point-in-time reads), просто обращаясь к нужной ревизии в BoltDB.

### Ревизии как логические часы

Ревизия служит "логическим временем" для всего кластера. Любая запись (Put, Delete, Txn) гарантированно увеличивает ревизию на 1. Это позволяет клиентам:
- Убедиться, что они читают данные не старее, чем те, что они видели ранее.
- Получать согласованные снимки (snapshots) всего пространства ключей.

### Компакция и фрагментация

При каждом изменении в BoltDB добавляются новые записи, а старые помечаются как неактуальные (tombstones). Без очистки база данных будет расти бесконечно.
* **Компакция**: Удаляет ссылки на старые ревизии в `treeIndex` и помечает страницы в BoltDB как "свободные".
* **Фрагментация**: После компакции физический размер файла БД (`db_total_size`) не уменьшается, но внутри появляются пустые страницы (`db_total_size_in_use` уменьшается).
* **Дефрагментация (Defrag)**: Физически пересобирает файл БД, удаляя пустоты и уменьшая его размер на диске.

## Стратегии обслуживания в больших кластерах (5000+ узлов)

Для кластеров с высокой интенсивностью изменений стандартные настройки обслуживания могут быть недостаточны.

1.  **Агрессивное сжатие (Compaction):**
    В крупных кластерах история изменений растет стремительно, что замедляет чтение и увеличивает размер БД. Рекомендуется настроить автоматическое сжатие **каждые 5 минут** (на основе истории ревизий), чтобы минимизировать фрагментацию и нагрузку на хранилище. Это предотвращает ситуацию, когда объем накопленных ревизий начинает мешать производительности Raft.

2.  **Периодическая дефрагментация:**
    Сжатие только помечает место как свободное, но не уменьшает размер файла базы данных на диске. Для физического освобождения места необходима дефрагментация.
    - **Блокирующая операция:** Дефрагментация блокирует запись и чтение на конкретном узле на время выполнения.
    - **Реализация через CronJob:** Рекомендуется настроить автоматизированный процесс (например, Kubernetes CronJob), который будет выполнять команду `etcdctl defrag` поочередно на каждом участнике кластера.
    - **График:** Выполнение в периоды с минимальной сетевой активностью (например, раз в неделю).

**Реальный пример:** Автоматизация дефрагментации участников кластера по одному в выходные дни в сочетании с переходом на быстрые диски (NVMe) позволила значительно улучшить надежность всей плоскости управления Kubernetes при росте числа узлов до 4000+ и выше.

## Практические сценарии

### Чтение истории и ревизий

```bash
# Прочитать текущее значение и метаданные ключа
etcdctl get /config/db -w json
# → "mod_revision": 152, "version": 4

# Прочитать значение, каким оно было на ревизии 100
etcdctl get /config/db --rev=100
```

### Атомарные транзакции (Compare-and-Swap)

Использование `mod_revision` в транзакциях гарантирует, что ключ не был изменен между чтением и записью.

```bash
etcdctl txn <<'EOF'
cmp
mod_revision("/config/db") = 152
then
put /config/db "new-connection-string"
else
get /config/db
EOF
```

### Управление компакцией (etcd 3.6+)

В etcd 3.6 оптимизирован механизм очистки логов. Рекомендуется использовать автоматическую компакцию:

```bash
# Авто-компакция раз в час (режим periodic)
etcd --auto-compaction-mode=periodic --auto-compaction-retention=1h

# Сохранение последних 1000 ревизий (режим revision)
etcd --auto-compaction-mode=revision --auto-compaction-retention=1000
```

**Ручная компакция (если база быстро растет):**
```bash
# Удалить все ревизии до 5000
etcdctl compaction 5000

# Очистка физического места (Дефрагментация)
etcdctl defrag --cluster
```

## Дополнительная информация

### Влияние на Watch-подписчиков

Если клиент подписан на события (`watch`) и отключается, он может возобновить подписку с последней известной ревизии. Однако, если за время отсутствия произошла компакция и эта ревизия была удалена, клиент получит ошибку `required revision has been compacted`. В этом случае клиенту необходимо перечитать все данные заново.
