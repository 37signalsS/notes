# MVCC, версионирование и компакция в etcd

**MVCC (Multi-Version Concurrency Control)** — это механизм управления параллельным доступом, который etcd использует для обеспечения строгой согласованности и возможности чтения исторических данных. Вместо перезаписи данных etcd создает новую версию (ревизию) для каждого изменения.

## Определения

| Термин | Описание |
| :--- | :--- |
| **Revision (Ревизия)** | Глобальный, монотонно возрастающий номер версии всего хранилища. Каждая запись (Put, Delete, Txn) инкрементирует ревизию. |
| **modRevision** | Ревизия последнего изменения конкретного ключа. |
| **createRevision** | Ревизия, при которой ключ был создан. |
| **Version** | Счетчик изменений конкретного ключа в рамках его текущего жизненного цикла (сбрасывается при удалении). |
| **Consistent Index** | Внутренний индекс, связывающий лог Raft с MVCC-хранилищем. Гарантирует, что операция будет применена к BoltDB ровно один раз. |
| **Compaction (Компакция)** | Процесс логического удаления старых ревизий из истории. Освобождает страницы в BoltDB, но не уменьшает размер файла на диске. |
| **Keys-only Optimization** | (v3.7+) Режим чтения, при котором etcd извлекает данные только из `treeIndex` (в памяти), полностью пропуская обращение к BoltDB. |
| **Snapshot** | Полный снимок состояния MVCC на конкретной ревизии, используемый для усечения лога и быстрой синхронизации отставших узлов. |
| **Alarm (Аларм)** | Сигнал нештатного состояния узла. Типы: `NOSPACE` (превышена квота диска) и `CORRUPT` (поврежден файл данных). Алармы не распространяются автоматически между участниками. |
| **Lease (Аренда)** | Механизм привязки ключей к временному контракту (TTL). Если TTL истекает без keep-alive, ключ автоматически удаляется. |

## Основные концепции

### Модель MVCC и хранение данных

etcd использует двухслойную архитектуру хранения для реализации многоверсионности:

1. **treeIndex (в памяти)**: B-дерево, которое сопоставляет ключ пользователя с историей его ревизий. Позволяет мгновенно находить актуальную версию данных без дискового ввода-вывода. Структура узла: `key -> []revision`, где каждая ревизия содержит указатель на запись в BoltDB. При поиске etcd находит самый новый revision для ключа и извлекает значение по этому номеру.

2. **BoltDB (на диске)**: B+ дерево (движок `bbolt v1.5.1`), где ключом является номер ревизии. Это гарантирует, что данные записываются последовательно, что оптимально для SSD. BoltDB работает по принципу copy-on-write (CoW): при каждом изменении создаются новые страницы, а старые становятся "мертвыми" (неиспользуемыми) и попадают в Freelist.

   * **Page size**: 4 КБ. Все операции чтения/записи выровнены по границам страниц.
   * **Freelist (Список свободных страниц)**: После компакции страницы не удаляются физически, а заносятся в Freelist. В BoltDB v1.5.1 алгоритм управления этим списком оптимизирован до O(1), что позволяет эффективно работать с БД размером более 100 ГБ.
   * **Фрагментация**: Разница между физическим размером файла (`db_total_size`) и реальным объемом данных (`db_total_size_in_use`). Высокая фрагментация замедляет чтение, так как файл становится больше, хотя полезных данных меньше.

### Consistent Index и связь с Raft

**Consistent Index** — это внутренний счетчик, который Raft использует для отслеживания последней примененной записи. Когда лидер коммитит запись в Raft-логе, он увеличивает Consistent Index. Модуль MVCC применяет запись к BoltDB только один раз, используя этот индекс как идемпотентный ключ. Это предотвращает дублирование данных при перезапуске узла.

### Оптимизации чтения в v3.7.1

* **Keys-only Range Optimization**: При запросах, требующих только названия ключей (напр., для проверки существования), etcd извлекает данные напрямую из `treeIndex`, полностью пропуская фазу чтения из BoltDB. Это снижает IOPS и задержки в разы.
* **RangeStream**: Вместо полной буферизации результата в памяти (что часто приводило к OOM при LIST-запросах в K8s), etcd 3.7 использует потоковую передачу данных из BoltDB сразу в gRPC-канал.

### Механизм снапшотов и усечения лога

etcd создает снапшоты для двух целей:
1. **Быстрая синхронизация**: отстающий follower запрашивает снапшот вместо пере replay всего WAL.
2. **Усечение WAL**: после создания снапшота старые сегменты WAL удаляются, так как их содержимое уже сохранено в снапшоте.

Снапшот создается автоматически каждые `--snapshot-count` ревизий (по умолчанию 10 000 в v3.6+, 100 000 в v3.5).

### Алармы (NOSPACE и CORRUPT)

* **NOSPACE**: Возникает, когда размер БД достигает `--quota-backend-bytes` (по умолчанию 2 ГБ). etcd блокирует ВСЕ операции записи и переходит в режим только для чтения. Для восстановления требуется компакция, дефрагментация и сброс аларма.
* **CORRUPT**: Возникает при аппаратных сбоях, некорректном завершении или повреждении файлов данных. Требуется восстановление из снапшота (offline restore).

## Стратегии обслуживания в больших кластерах (5000+ узлов)

Для кластеров с высокой интенсивностью изменений стандартные настройки обслуживания могут быть недостаточными.

1.  **Агрессивное сжатие (Compaction):**
    В крупных кластерах история изменений растет стремительно, что замедляет чтение и увеличивает размер БД. Рекомендуется настроить автоматическое сжатие **каждые 5 минут** (на основе истории ревизий), чтобы минимизировать фрагментацию и нагрузку на хранилище. Это предотвращает ситуацию, когда объем накопленных ревизий начинает мешать производительности Raft.

2.  **Периодическая дефрагментация:**
    Сжатие только помечает место как свободное, но не уменьшает размер файла базы данных на диске. Для физического освобождения места необходима дефрагментация.
    - **Блокирующая операция:** Дефрагментация блокирует запись и чтение на конкретном узле на время выполнения.
    - **Реализация через CronJob:** Рекомендуется настроить автоматизированный процесс (например, Kubernetes CronJob), который будет выполнять команду `etcdctl defrag` поочередно на каждом участнике кластера.
    - **График:** Выполнение в периоды с минимальной сетевой активностью (например, раз в неделю).

    **Диагностика фрагментации:** Фрагментация > 30% требует планирования дефрагментации. > 50% — немедленного выполнения. Вычисляется через метрики:
    ```
    fragmentation = (db_total_size - db_total_size_in_use) / db_total_size
    ```

**Реальный пример:** Автоматизация дефрагментации участников кластера по одному в выходные дни в сочетании с переходом на быстрые диски (NVMe) позволила значительно улучшить надежность всей плоскости управления Kubernetes при росте числа узлов до 4000+ и выше.

## Практические сценарии

### Чтение истории и ревизий

MVCC позволяет получать состояние данных на любой момент в прошлом, пока эта ревизия не была удалена компакцией.

```bash
# Прочитать текущее значение и метаданные ключа
etcdctl get /config/db -w json
# → "mod_revision": 152, "version": 4

# Прочитать значение, каким оно было на ревизии 100
etcdctl get /config/db --rev=100
```

**Edge Cases:**
- Чтение по compacted revision возвращает ошибку: `mvcc: required revision has been compacted`.
- Чтение по ревизии за пределами истории (слишком старой) возвращает ошибку: `mvcc: required revision is beyond the range`.

### Атомарные транзакции (CAS)

Использование `mod_revision` в транзакциях гарантирует, что ключ не был изменен между чтением и записью.

```bash
etcdctl txn <<'EOF'
cmp
mod_revision("/config/db") = 152
then
put /config/db "new-connection-string"
else
get /config/db
EOF
```

### Автоматическое обслуживание (etcd 3.7+)

Рекомендуется настраивать автоматическую компакцию для предотвращения бесконечного роста БД.

```bash
# Режим periodic: Авто-компакция каждые 5 минут (K8s standard)
etcd --auto-compaction-mode=periodic --auto-compaction-retention=5m

# Режим revision: Сохранение последних 10 000 ревизий
etcd --auto-compaction-mode=revision --auto-compaction-retention=10000
```

### Диагностика фрагментации и дефрагментация

Если разница между `db_total_size` и `db_total_size_in_use` > 30%, требуется планирование дефрагментации. > 50% — немедленное выполнение.

```bash
# Онлайн дефрагментация конкретного узла (рекомендуется поочередно)
etcdctl defrag --endpoints=https://10.0.0.11:2379

# Онлайн дефрагментация всего кластера (поочередно, не параллельно)
etcdctl defrag --cluster

# Офлайн дефрагментация файла БД (через etcdutl, требует остановки etcd)
etcddutl defrag --data-dir /var/lib/etcd
```

**Валидация через метрики:**
```bash
curl -s http://localhost:2379/metrics | grep etcd_mvcc_db_total_size
# etcd_mvcc_db_total_size_in_bytes{...} 3221225472
# etcd_mvcc_db_total_size_in_use_in_bytes{...} 1610612736
# fragmentation = (3221225472 - 1610612736) / 3221225472 = 0.5 (50%)
```

### Обработка NOSPACE Alarm

При превышении квоты (`--quota-backend-bytes`) etcd блокирует запись и устанавливает аларм `NOSPACE`.

```bash
# 1. Получить текущую ревизию
rev=$(etcdctl endpoint status --write-out="json" | egrep -o '"revision":[0-9]*' | egrep -o '[0-9]*' | head -n 1)

# 2. Выполнить компакцию
etcdctl compaction $rev

# 3. Дефрагментация (поочередно на каждом узле)
etcdctl defrag --cluster

# 4. Сброс аларма
etcdctl alarm list
etcdctl alarm disarm
```

### Офлайн-инспекция БД через etcdutl

```bash
# Проверка статуса снапшота
etcdutl snapshot status backup.db -w table
# → Hash: 1a2b3c4d, Revision: 512340, Total key count: 1254300

# Валидация снапшота
etcdutl snapshot verify /backup/etcd-snapshot-2026-08-23.db
# → snapshot verify passed, revision: 512340

# Экспорт ключей в формате JSON (offline)
etcdutl db --data-dir /var/lib/etcd get /config/ -w json

# Проверка здоровья базы данных (offline)
etcdutl health --data-dir /var/lib/etcd
# → health check passed
```

### Проверка производительности (etcdctl check perf)

```bash
etcdctl check perf --load="s"  # s (small), m (medium), l (large), xl (x-large)
# → PASS: Throughput is 150 writes/s
```

**Интерпретация порогов (ориентировочно для NVMe):**
- **Small (s):** PASS при > 100 writes/s.
- **Medium (m):** PASS при > 50 writes/s.
- **Large (l):** PASS при > 20 writes/s.
- **X-Large (xl):** PASS при > 5 writes/s.

**Troubleshooting:**
- FAIL на `s` или `m` указывает на проблемы с диском (HDD вместо SSD, высокий iowait) или сетью между участниками.
- При высокой вариативности запускайте тест 3–5 раз и считайте медиану.

### Управление Lease и TTL

```bash
# Создать аренду на 60 секунд
etcdctl lease grant 60
# → lease 694d5765fc71500b granted with TTL(60s)

# Привязать ключ к аренде
etcdctl put /tmp/key "val" --lease=694d5765fc71500b

# Продлить аренду (keep-alive)
etcdctl lease keep-alive 694d5765fc71500b

# Принудительный отзыв аренды
etcdctl lease revoke 694d5765fc71500b
```

**Best Practices:**
- В Kubernetes контроллеры используют leases для лидерских выборов и keep-alive. Прерывание keep-alive приведет к потере лидерства.
- TTL аренды не должен быть меньше, чем heartbeat интервал контроллера, чтобы избежать ложного истечения при временных проблемах.

## Дополнительная информация

### Влияние на Watch-подписчиков

Если клиент подписан на события (`watch`) и отключается, он может возобновить подписку с последней известной ревизии. Однако, если за время отсутствия произошла компакция и эта ревизия была удалена, клиент получит ошибку `required revision has been compacted`. В этом случае необходимо:
1. Выполнить полный `GET` ресурсов.
2. Начать новый `WATCH` с текущей ревизии.

### Устранение неполадок (Troubleshooting)

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `mvcc: required revision has been compacted` | Watcher отстал от процесса компакции | Увеличить `--auto-compaction-retention`; оптимизировать контроллеры, чтобы они не отставали |
| `mvcc: required revision is beyond the range` | Запрошена ревизия старше самой старой доступной | Выполнить полный GET вместо чтения по старой ревизии |
| `etcdserver: mvcc: watch store is out of space` | Клиент не успевает обрабатывать события | Уменьшить буфер обработки на стороне клиента; переподключиться с `--rev` |
| `database space exceeded` / `NOSPACE` | Достигнут лимит `quota-backend-bytes` | Выполнить compaction + defrag; увеличить квоту или освободить место в ОС |
| `etcdserver: request is too large` | Объект > `max-request-bytes` (по умолчанию 1.5 MB) | Разбить объект (ConfigMap/Secret) или увеличить лимит |
| `CORRUPT` | Поврежден файл данных (аппаратный сбой, некорректное завершение) | Восстановление из снапшота через `etcdutl snapshot restore` |

### Best Practices

* **Размер БД:** Держите `db_total_size_in_bytes` ниже 8 ГБ (максимум для стабильной работы BoltDB). При приближении к 6 ГБ начинайте агрессивную компакцию.
* **Дефрагментация:** Выполняйте поочередно на узлах в часы минимальной нагрузки. Никогда не дефрагментируйте все узлы одновременно — это может привести к потере кворума.
* **Автоматизация:** Настройте Kubernetes CronJob для дефрагментации и CronJob/Sidecar для регулярного создания снапшотов.
* **Lease TTL:** Используйте TTL, которые в 2–3 раза превышают интервал keep-alive контроллера. Это предотвращает ложное удаление ключей при кратковременных проблемах с сетью.
* **Compact перед Defrag:** Всегда выполняйте `compaction` перед `defrag`, иначе дефрагментация не вернет значительного объема места.

### Edge Cases

* **Счетчик Version:** Сбрасывается при удалении ключа. При повторном создании ключа с тем же именем `createRevision` будет новым, а `version` начнется с 1.
* **Consistent Index:** При аварийном перезапуске etcd восстанавливает Consistent Index из WAL, чтобы избежать дублирования записей в BoltDB. Если WAL поврежден, требуется восстановление из снапшота.
* **RangeStream и большие ключи:** При запросе очень большого диапазона (миллионы ключей) RangeStream эффективен, но может создавать высокую нагрузку на сеть. Используйте `--limit` для ограничения.
* **Defrag во время записи:** `etcdctl defrag` блокирует узел на время выполнения. В HA-кластере это безопасно, если операция выполняется на follower или поочередно на участниках.
