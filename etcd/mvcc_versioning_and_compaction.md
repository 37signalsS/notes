# Настройки версионности ключей

В etcd реализовано многоверсионное хранилище (MVCC), где каждая операция изменяет глобальную ревизию, а ключи имеют собственные счётчики версий. Это позволяет выполнять согласованные чтения на конкретной ревизии, строить оптимистичные блокировки и безопасно синхронизировать конфигурацию между сервисами.

## Термины и модель MVCC

| Поле | Смысл |
|---|---|
| revision | Глобальный монотонно возрастающий номер состояния хранилища на каждую запись/удаление. |
| createRevision | Ревизия, на которой ключ был создан в текущем поколении. Меняется при повторном создании после удаления. |
| modRevision | Ревизия последней модификации ключа (put/delete). |
| version | Счётчик модификаций ключа в текущем поколении; инкремент при каждом put/delete. При удалении ключ исчезает; новое создание начинает version=1. |
| lease | Привязка TTL. Истечение lease приводит к удалению ключа, что создаёт новую модификацию (новая revision). |

Такая схема делает возможным чтение «на момент времени» и корректные транзакции «сравнить-и-установить».

## Чтение по ревизии и история

Чтение по конкретной ревизии полезно для воспроизводимости и отладки гонок. Пример с etcdctl:

```applescript
etcdctl put /cfg/app/db "postgres://..."
etcdctl get /cfg/app/db --write-out=json

# Чтение на заданной ревизии
etcdctl get /cfg/app/db --rev=12

# Просмотр метаданных
etcdctl get --prefix /cfg/app --write-out=fields
```

Если запрошенная ревизия была скомпактирована, сервер вернёт ошибку о недоступности истории на этой ревизии. Наблюдатели (watch) должны начинать с ревизии не старее точки компакции:

```swift
etcdctl watch --rev=latest /cfg/app --prefix
```

## Транзакции и сравнения

Оптимистичные блокировки строятся на сравнении modRevision или version:

```bash
# Обновить значение только если никто не менял ключ после rev=25
etcdctl txn <<'EOF'
cmp
mod("/cfg/app/db") = "25"
then
put /cfg/app/db "postgres://new"
else
get /cfg/app/db
EOF
```

Сравнение по version удобно, когда важно число модификаций, а не конкретная ревизия:

```bash
etcdctl txn <<'EOF'
cmp
version("/feature/flag") = "3"
then
put /feature/flag "enabled"
else
get /feature/flag
EOF
```

## Компакция и удержание истории

История растёт вместе с ревизиями. Компакция удаляет старые версии и оставляет логически «последние» записи и надгробия (tombstones) для согласованности.

-   **Ручная компакция:**
    ```yaml
    # Скомпактировать до ревизии 5000
    etcdctl compact 5000 --physical
    ```
-   **Автоматическая компакция на сервере:**
    -   `ETCD_AUTO_COMPACTION_MODE=periodic|revision`
    -   `ETCD_AUTO_COMPACTION_RETENTION=1h` или число ревизий
-   **Дополнительно связаны:**
    -   `ETCD_SNAPSHOT_COUNT` — периодичность снапшотов по числу операций
    -   `ETCD_QUOTA_BACKEND_BYTES` — предел размера backend

При выборе политики учитывают отставание клиентов и длительность watch. Слишком агрессивная компакция приведёт к `ErrCompacted` у медленных потребителей.

## Взаимодействие с арендами (lease) и TTL

Привязка ключа к lease делает его «самоудаляющимся». Истечение lease:

-   инкрементирует глобальную revision;
-   фиксирует новую modRevision для ключа и завершает поколение;
-   при повторном создании ключа получаем новый createRevision и version=1.

```bash
# Создать lease на 60s и привязать ключ
LEASE_ID=$(etcdctl lease grant 60 | awk '/lease/{print $3}')
etcdctl put --lease=$LEASE_ID /locks/job "holder-1"
```

## Рекомендации по настройке

-   Для конфигураций с длительными watch выбирайте periodic компакцию с retention 1–24h, исходя из максимального отставания клиентов.
-   Для высоконагруженных кластеров с активной записью используйте revision-режим компакции, подбирая порог по скорости роста backend.
-   В транзакциях предпочитайте сравнивать modRevision для гарантии «не менялось с момента X»; version применяйте для контроля числа изменений.
-   Следите за размером backend и частотой снапшотов, чтобы ускорять восстановление без потери нужной глубины истории.
