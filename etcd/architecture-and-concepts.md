# Архитектура и основные концепции etcd

**etcd** — это высоконадежное распределенное хранилище данных в формате "ключ-значение", использующее [алгоритм консенсуса Raft](./raft_consensus.md). Служит централизованным хранилищем для конфигураций, обнаружения сервисов и координации состояния в распределенных системах (например, в Kubernetes).

## Определения

| Термин | Описание |
| :--- | :--- |
| **gRPC API** | Основной интерфейс взаимодействия с etcd (начиная с v3). Обеспечивает высокую производительность и потоковую передачу данных. |
| **Lease (Аренда)** | Механизм создания временных ключей с TTL. Используется для регистрации сервисов и liveness-проверок. |
| **Watch (Наблюдение)** | Подписка на поток изменений ключей в реальном времени. Позволяет мгновенно реагировать на смену конфигурации. |
| **Revision (Ревизия)** | Глобальный счетчик версии всего хранилища. Каждая запись инкрементирует ревизию, позволяя читать "снимки" данных. |
| **WAL (Write-Ahead Log)** | Журнал предзаписи на диске. Каждая операция сначала фиксируется в WAL для обеспечения надежности при сбоях. |
| **BoltDB (bbolt)** | Встроенная база данных (B+ tree), используемая etcd для хранения данных MVCC на диске. |
| **treeIndex** | B-дерево в оперативной памяти, которое сопоставляет пользовательские ключи с их ревизиями в BoltDB. |

## Основные концепции

### Внутренняя архитектура и путь записи (Write Flow)

etcd работает как "реплицируемый автомат" (Replicated State Machine). Процесс записи в etcd 3.6 выглядит следующим образом:

1. **Предложение (Proposal):** gRPC-сервер получает запрос и передает его модулю Raft.
2. **Фиксация в WAL:** Лидер записывает операцию в свой WAL-файл и вызывает `fdatasync`.
3. **Репликация:** Лидер рассылает операцию фолловерам. Они также фиксируют её в своих WAL.
4. **Коммит (Commit):** Как только большинство (кворум) подтвердили запись в WAL, лидер помечает операцию как "закоммиченную".
5. **Применение (Apply):** Операция передается в слой применения:
   - Обновляется **treeIndex** в памяти (создается новая ревизия).
   - Данные записываются в **BoltDB** (под ключом ревизии).
6. **Ответ:** Клиент получает подтверждение успеха.

### API v3 vs v2

*   **etcd 3.6+**: API v2 полностью **удален**. Флаг `--enable-v2` больше не поддерживается.
*   **gRPC**: v3 использует gRPC вместо HTTP/JSON, что значительно снижает нагрузку на CPU и сеть.
*   **Бинарные данные**: В отличие от v2, ключи и значения в v3 — это байтовые массивы (не только строки).

### Иерархия и префиксы

Ключи упорядочены лексикографически. etcd не имеет "папок", но структура `/dir/subdir/key` эмулируется с помощью запросов по префиксу. Это позволяет эффективно получать все ключи в "директории" одним запросом.

### Аренда (Lease) и эфемерные ключи

Ключи можно привязать к объекту аренды (Lease).
- Клиент должен отправлять `KeepAlive`, чтобы продлевать аренду.
- Если аренда истекает (например, сервис упал), все привязанные ключи удаляются автоматически.
- Это критично для механизмов **Service Discovery** и **Leader Election**.

### Согласованность и MVCC

etcd обеспечивает **строгую согласованность** (Linearizability). Благодаря механизму [**MVCC**](./mvcc_versioning_and_compaction.md), etcd хранит историю изменений. Это позволяет:
- Читать данные на конкретную ревизию из прошлого.
- Реализовывать атомарные транзакции "сравнить и выполнить" (Compare-and-Swap).

## Аппаратные требования и производительность

etcd чувствителен к задержкам. Для стабильной работы production-кластера необходимо соблюдать следующие требования:

### Процессор (CPU)
- Рекомендуется от 2–4 ядер. etcd активно использует CPU для gRPC-сериализации и вычисления хешей Raft.
- В 3.6 оптимизированы алгоритмы компакции, что снижает пиковое потребление CPU.

### Память (RAM)
- Объем зависит от размера данных. В среднем 8 ГБ достаточно для большинства K8s кластеров.
- **Оптимизация 3.6**: Потребление памяти снижено на ~50% за счет уменьшения `snapshot-count` по умолчанию до 10 000.

### Дисковая подсистема (Критично)
- **Только SSD/NVMe**. Задержка `fdatasync` должна быть **менее 10 мс** (в идеале < 2 мс).
- **Выделенный диск**: Крайне рекомендуется выделять отдельный физический диск под `data-dir` etcd, чтобы избежать влияния I/O других приложений.
- **Тестирование**: Используйте `fio` для проверки задержки диска перед развертыванием.

## Практические сценарии

Примеры использования `etcdctl` (подробнее в [шпаргалке](./etcdctl_cheatsheet.md)):

**Атомарная запись (Транзакция):**
Обновить конфигурацию, только если она не менялась (проверка по `mod_revision`).

```bash
etcdctl txn <<'EOF'
cmp
mod_revision("/config/api") = 123
then
put /config/api "new_value"
else
get /config/api
EOF
```

**Регистрация сервиса с TTL:**

```bash
# Создать аренду
lease_id=$(etcdctl lease grant 30 | awk '{print $2}')
# Привязать сервис
etcdctl put /services/worker-1 "10.0.0.5" --lease=$lease_id
```

#### Высокая доступность и Raft (HA Cluster)

Для обеспечения отказоустойчивости в production-средах используется кластер из **3 или 5 узлов**, распределенных по разным зонам доступности.

-   **Роли узлов:** В любой момент времени один узел является **Лидером (Leader)**, остальные — **Последователями (Followers)**.
-   **Консенсус Raft:**
    -   **Выбор лидера:** Если последователи перестают получать "пульс" (heartbeat) от лидера, они инициируют новые выборы. Стабильность сети между участниками критична для предотвращения частых перевыборов, которые парализуют запись.
    -   **Репликация журнала:** Лидер принимает запросы, записывает их в свой WAL и реплицирует на последователей. Запись считается успешной только после подтверждения кворумом (большинством).
-   **Мониторинг через Prometheus:** Для поддержания здоровья HA-кластера необходимо отслеживать:
    -   `etcd_server_leader_changes_seen_total`: Частота выборов (индикатор нестабильности сети).
    -   Задержки репликации между участниками.

Стабильность сети и низкая задержка локального постоянного хранилища являются фундаментом надежности, необходимой для управления тысячами узлов.

### Масштабирование и производительность (Scale 5000+ узлов)

Оптимизация etcd для кластеров большого масштаба требует комплексного подхода к аппаратному обеспечению и конфигурации плоскости управления.

#### 1. Аппаратное обеспечение (Hardware Requirements)
etcd чрезвычайно чувствителен к задержке ввода-вывода (I/O latency). Для стабильной работы в больших кластерах:
- **Тип дисков:** Использование локальных **NVMe SSD** является обязательным. Сетевые хранилища или обычные SSD часто не справляются с нагрузкой при записи транзакций Raft.
- **Задержка fsync:** Для журнала упреждающей записи (WAL) задержка `fsync` должна быть постоянно низкой. В здоровом кластере показатель **p99 должен быть < 10 мс**.

**Реальный пример:** При масштабировании кластера с 1000 до 4000 узлов задержка `fsync p99` возросла до сотен миллисекунд из-за использования дисков общего назначения. Переход на инстансы, оптимизированные для ввода-вывода с локальными NVMe, позволил снизить задержку до < 10 мс и стабилизировать время запуска подов.

#### 2. Кэширование на стороне API-сервера
Для снижения нагрузки на чтение в etcd необходимо правильно настроить **Watch Cache** в `kube-apiserver`. 
- **Watch Cache Size:** Увеличение размера кэша позволяет обслуживать большинство запросов на получение состояния объектов напрямую из памяти API-сервера, минуя прямое обращение к базе данных etcd. Это критично для систем мониторинга и контроллеров, которые постоянно "наблюдают" за изменениями ресурсов.

#### 3. Мониторинг ключевых показателей
Для проактивного выявления проблем следует отслеживать следующие метрики Prometheus:
- `etcd_disk_wal_fsync_duration_seconds`: Индикатор проблем с дисковой подсистемой.
- `etcd_mvcc_db_total_size_in_bytes`: Общий размер БД (сигнал о необходимости сжатия).
- `etcd_server_leader_changes_seen_total`: Частота смены лидеров (признак нестабильности сети между узлами).
