# Архитектура и основные концепции etcd

**Актуально для:** etcd 3.6.x / 3.7.x (RangeStream, FastLeaseKeepAlive, keys-only, Unix socket — 3.7+; `--snapshot-count` default 10 000 в 3.6+, 100 000 в 3.5)

**etcd** — высоконадёжное распределённое хранилище данных в формате «ключ-значение», использующее [алгоритм консенсуса Raft](./raft_consensus.md). Служит централизованным хранилищем для конфигураций, обнаружения сервисов и координации состояния в распределённых системах (например, в Kubernetes).

**Prerequisites:** работающий кластер etcd (3.6+/3.7), `etcdctl` той же мажорной версии, что и сервер, доступ к client-эндпоинту (`:2379`) и `/metrics`.

## Определения

| Термин | Описание |
| :--- | :--- |
| **gRPC API** | Основной интерфейс взаимодействия (v3). Использует HTTP/2 и Protobuf для высокой производительности и двунаправленной потоковой передачи. |
| **RangeStream (v3.7+)** | gRPC-only RPC потоковой передачи больших range-запросов чанками. Снижает пиковое потребление памяти сервера и клиента на больших выборках (вместо полной буферизации ответа). |
| **Keys-only Optimization (v3.7+)** | Режим чтения, при котором etcd извлекает ключи только из `treeIndex` в памяти, полностью пропуская обращение к BoltDB (исключение — сортировка по значению). |
| **Linearizability (Линейизуемость)** | Самая строгая гарантия согласованности. Читатель гарантированно получает результат самой последней завершённой записи. |
| **Lease (Аренда)** | Механизм создания временных ключей с TTL. Используется для регистрации сервисов и liveness-проверок. |
| **Watch (Наблюдение)** | Подписка на поток изменений ключей в реальном времени через gRPC-стримы. |
| **Revision (Ревизия)** | Глобальный логический счётчик времени всего хранилища. Каждая запись инкрементирует ревизию. |
| **WAL (Write-Ahead Log)** | Журнал предзаписи на диске. Каждая операция сначала фиксируется в WAL для обеспечения надёжности при сбоях. |
| **BoltDB (bbolt)** | Встроенная база данных (B+ tree), используемая для персистентного хранения MVCC-данных на диске. Движок `bbolt` является форком BoltDB с оптимизациями для etcd. |
| **treeIndex** | B-дерево в оперативной памяти, которое сопоставляет пользовательские ключи с их ревизиями в BoltDB. |
| **Snapshot** | Полный снимок состояния MVCC на конкретной ревизии, используемый для усечения лога и быстрой синхронизации отставших узлов. |
| **Alarm** | Сигнал нештатного состояния узла. Типы: `NOSPACE` (превышена квота backend — размер БД) и `CORRUPT` (повреждён файл данных). Алармы не распространяются автоматически между участниками. |
| **Endpoint** | Адрес узла для взаимодействия: Client URL (2379) для клиентов, Peer URL (2380) для Raft-коммуникации. |
| **Quota (Backend Bytes)** | Максимальный размер файла BoltDB (по умолчанию 2 ГБ, рекомендуемый максимум 8 ГБ). При превышении etcd переходит в режим обслуживания и поднимает alarm `NOSPACE`. |
| **Consistent Index** | Внутренний индекс, связывающий Raft-лог с MVCC-хранилищем. Гарантирует идемпотентность применения записи к BoltDB. |

## Основные концепции

### Внутренняя архитектура и путь записи (Write Flow)

etcd работает как «реплицируемый автомат» (Replicated State Machine). Процесс записи:

1. **Предложение (Proposal):** gRPC-сервер получает запрос (Put/Delete/Txn). Запрос, пришедший на follower, автоматически перенаправляется на лидера.
2. **WAL и репликация (параллельно):** лидер записывает entry в свой WAL с вызовом `fdatasync()` и одновременно рассылает его фолловерам (AppendEntries); фолловеры также фиксируют entry в своих WAL. (Raft thesis 10.2.1: лидер пишет на диск параллельно с репликацией — не последовательно.)
3. **Коммит (Commit):** как только большинство (кворум) подтвердили запись в WAL, entry помечается committed.
4. **Применение (Apply):** entry применяется к MVCC: обновляется **treeIndex** в памяти (создаётся новая ревизия, сопоставляющая ключ с версией), а изменения буферизуются и сбрасываются в **BoltDB** пакетами (не чаще чем раз в 100 мс или при накоплении 10 000 операций — `--backend-batch-interval` / `--backend-batch-limit`).
5. **Ответ:** клиент получает подтверждение только после Apply — раннего acknowledgement в etcd нет.

Детальный разбор каждого этапа (включая forwarding, pending proposals и Raft Index Gap) — в [Proposal Pipeline](./proposal_pipeline.md).

### Путь чтения (Read Path)

etcd поддерживает два типа чтения с разными гарантиями:

1. **Линейизуемое чтение (Linearizable Read, по умолчанию):** лидер подтверждает свой статус через механизм **ReadIndex** — обменивается пустыми heartbeats с большинством узлов перед ответом. Это гарантирует, что лидер не изолирован (не произошло split-brain) и читается самая свежая запись. Линейизуемые чтения в etcd всегда проходят через ReadIndex — отдельного «lease read» быстрого пути в etcd нет.
2. **Сериализуемое чтение (Serializable Read):** запрос выполняется локально с любого узла (включая фолловеров) без обращения к лидеру. Быстрее, но может вернуть устаревшие данные (stale reads).

### Хранилище данных: BoltDB и treeIndex

etcd использует двухслойную архитектуру хранения:

1. **treeIndex (в памяти):** B-дерево, сопоставляющее пользовательские ключи с историей их ревизий. Позволяет мгновенно находить актуальную версию данных без дискового ввода-вывода. Размер treeIndex пропорционален количеству ключей, а не объёму значений.
2. **BoltDB (на диске):** B+ дерево (движок `bbolt`), где ключом является номер ревизии. Данные записываются последовательно, что оптимально для SSD. BoltDB использует copy-on-write: при каждом изменении создаются новые страницы, а старые становятся «мёртвыми» и попадают в Freelist.

**Фрагментация:** при удалении ключей или compaction-операциях физический размер файла не уменьшается автоматически. Разница между `db_total_size` и `db_total_size_in_use` показывает уровень фрагментации. Официальная документация etcd порогов не задаёт; ниже — рабочая эвристика (детали, page size и устройство freelist — в [Внутреннее устройство хранения](./storage_internals.md)):
- **< 30%**: норма.
- **30–50%**: требуется планирование дефрагментации.
- **> 50%**: критично. Выполните `etcdctl defrag`.

### WAL (Write-Ahead Log)

WAL гарантирует, что сбой питания не приведёт к повреждению данных. Каждая операция фиксируется в WAL на диске с вызовом `fdatasync()`.

- **Сегментация:** WAL разбит на сегменты по 64 MiB (размер зашит в код etcd, не настраивается). Когда сегмент заполняется, создаётся новый.
- **Ротация:** при создании снапшота старые сегменты WAL, предшествующие snapshot-index, удаляются; хранится не более `--max-wals` файлов (default 5, `0` = без ограничения).
- **Повреждение:** если `fdatasync` не успел завершиться при сбое питания, WAL может быть повреждён. etcd фиксирует это в логах (`etcdserver: corrupted WAL`) и поднимает alarm CORRUPT (`etcdctl alarm list`). Для восстановления требуется восстановление из снапшота/бэкапа; целостность снапшота проверяется через `etcdutl snapshot status`.

### RangeStream (v3.7+) и потоковая передача

До версии 3.7 большие запросы (напр., получение всех подов в кластере) требовали полной буферизации результата в памяти сервера перед отправкой — пиковое потребление RAM росло с размером выборки.
- **Потоковый RPC:** `RangeStream` (gRPC-only, REST-маппинга нет) разбивает ответ на чанки и отправляет их клиенту по мере чтения из BoltDB; сервер внутренне пагинирует с адаптивным размером чанка.
- **Константная память:** потребление RAM сервером больше не зависит от размера выборки.
- **Снимок ревизии:** весь поток данных привязан к единой MVCC-ревизии на момент начала запроса. Если ревизия будет скомпактирована во время стрима, сервер закрывает стрим с ошибкой `ErrCompacted` — клиент должен повторить запрос.
- **Ограничения:** RangeStream не поддерживает нестандартную сортировку и фильтры по revision — для таких запросов сервер возвращает `Unimplemented`, и клиент использует обычный unary Range. В etcdctl: `--stream` не поддерживает `--order`, `--sort-by` и фильтры revision.
- **Keys-only оптимизация (3.7):** запросы `keys_only` (`etcdctl get --keys-only`) читаются только из treeIndex в памяти, без загрузки значений из bbolt (исключение — сортировка по значению, SortTarget=VALUE).

### Гарантии согласованности

etcd обеспечивает различные уровни согласованности для операций чтения:
- **Linearizability (Линейизуемость):** стандарт по умолчанию. Использует механизм **ReadIndex**. Гарантирует отсутствие «грязных чтений».
- **Serializable (Последовательная):** быстрее, но может вернуть устаревшие данные (stale reads).
- **Watch:** etcd **не** гарантирует linearizability для watch-операций — клиент должен проверять revision событий, чтобы обеспечить корректное упорядочивание с другими операциями.

### Аренда (Lease)

Механизм аренды позволяет привязывать TTL к набору ключей.
- **FastLeaseKeepAlive (v3.7):** продление аренды происходит по ускорённому пути, не дожидаясь индекса применения в Raft-логе. Это предотвращает ложное истечение аренды при высокой нагрузке на диск или процессор.
- **Приоритизация LeaseRevoke (v3.7):** запросы отзыва аренды приоритизируются при перегрузке, обеспечивая своевременное истечение TTL.

### Снапшот (Snapshot) и усечение лога

Raft-лог не может расти бесконечно. Когда количество записей достигает порога (`--snapshot-count`, по умолчанию 10 000 в v3.6/v3.7; 100 000 в v3.5), etcd выполняет:
1. **Снимок (Snapshot):** текущее состояние данных сохраняется на диск в `member/snap/`.
2. **Усечение (Truncation):** записи в WAL, предшествующие снимку, удаляются (с учётом `--max-wals`). Усечение ограничено applied index — записи не удаляются из лога до применения к MVCC.
3. **Передача снапшота:** если новый узел (Follower или Learner) сильно отстал и нужных записей в логе лидера уже нет, лидер отправляет ему полный снимок плюс до `--snapshot-catchup-entries` записей (default 5000) для догона.

### Алгоритм компакции и дефрагментация

- **Компакция (Compaction):** логически удаляет старые ревизии из `treeIndex` и удаляет старые записи из BoltDB пакетами; освободившиеся страницы переходят в Freelist и переиспользуются. Не уменьшает физический размер файла. Режимы и retention — в [Сборка мусора и компакция](./garbage_collection.md).
- **Дефрагментация (Defrag):** единственный способ физически уменьшить файл БД и вернуть место ОС. Процедура создаёт новый файл BoltDB, копируя в него только «живые» данные. Блокирует чтение и запись на узле на время выполнения. Механика (CoW, freelist, offline defrag через `etcdutl`) — в [Внутреннее устройство хранения](./storage_internals.md).

### Алармы (Alarms)

etcd поддерживает два типа алармов:
- **NOSPACE:** превышен `quota-backend-bytes`. etcd переходит в режим обслуживания: разрешены чтения и удаления, новые записи отклоняются с ошибкой `mvcc: database space exceeded`.
- **CORRUPT:** повреждён файл данных (WAL или BoltDB) из-за аппаратного сбоя или некорректного завершения.

Алармы не распространяются автоматически между участниками. Каждый узел поднимает alarm независимо — проверяйте `etcdctl alarm list` на каждом узле. Восстановление: compaction → defrag → `etcdctl alarm disarm` (см. ниже и [Maintenance API](./maintenance_api.md)).

### Полное удаление v2 Store

Начиная с версии 3.7, etcd полностью очищен от наследия API v2.
- Флаг `--enable-v2` удалён в 3.6 — включить v2 API больше нельзя.
- В 3.7 v2store удалён полностью: etcd загружается только из v3store, механизм самообнаружения (v2 discovery) не поддерживается.
- Перед апгрейдом на 3.7 проверьте отсутствие v2-данных: `etcdutl check v2store` (доступна с 3.5.18).
- Полная хронология совместимости — в [Совместимость версий](./version_compatibility.md).

### Сеть, порты и TLS

- **Client port 2379:** используется клиентами (etcdctl, kube-apiserver) для операций чтения/записи.
- **Peer port 2380:** используется для Raft-коммуникации и передачи снапшотов между узлами.
- **Metrics port:** по умолчанию совпадает с client port (2379), эндпоинт `/metrics`.
- **Unix socket (3.7+):** поддержка unix-сокетов для client-эндпоинтов.
- Включение peer TLS обязательно для production. Отсутствие шифрования peer-соединений раскрывает чувствительные данные (снапшоты, Raft-лог) на сетевом уровне.
- Рекомендуется разделять Peer- и Client-трафик на разных интерфейсах или через балансировщик, чтобы всплеск клиентского трафика не влиял на канал синхронизации Raft.

## Аппаратные требования и производительность

etcd чрезвычайно чувствителен к задержкам ввода-вывода и процессора. Для стабильной работы production-кластера необходимо соблюдать следующие требования:

### Процессор (CPU)
- **Производительность:** минимум 2–4 физических ядра с высокой тактовой частотой. etcd активно использует CPU для сериализации Protobuf и вычисления хешей Raft.
- **Изоляция:** в высоконагруженных средах рекомендуется использовать `isolcpus` или CPU Pinning, чтобы предотвратить переключение контекста и гарантировать мгновенную обработку heartbeat-сообщений.

### Память (RAM)
- **Объём:** 8–16 ГБ для средних кластеров K8s. В v3.7+ механизм `RangeStream` позволяет удерживать потребление памяти стабильным даже при массовых операциях чтения.
- **Кэширование:** etcd эффективно использует системный кэш для BoltDB (bbolt memory-maps db-файл). Чем больше RAM, тем меньше обращений к диску при чтении.
- **Файловые дескрипторы:** etcd сам мониторит `/proc/self/fd` и предупреждает при 80% лимита (сообщение `etcdserver: 80% of the file descriptor limit is used`); лимит определяется ожидаемым числом клиентов и watchers (распространённое production-значение — 65536, см. [тюнинг ОС](./kernel_tuning.md)). Дефицит дескрипторов приводит к отказу новых подключений.

### Дисковая подсистема (Критический фактор)
- **Тип носителя:** исключительно **локальные NVMe SSD** (Gen4/Gen5). Использование сетевых дисков (блочные сетевые хранилища, Ceph) или обычных SATA SSD считается антипаттерном из-за высокого джиттера.
- **Задержка fdatasync:** p99 метрики `etcd_disk_wal_fsync_duration_seconds` должен быть **< 10 мс** (порог etcd-perf / OpenShift). Устойчивые значения > 20 мс — диск не рекомендуется для etcd; систематический джиттер вызывает перевыборы лидера и дестабилизацию кластера.
- **Выделенный диск:** крайне рекомендуется выделять отдельный физический диск (или раздел с гарантированным IOPS) под `data-dir` etcd; при необходимости WAL выносится на отдельный диск (`--wal-dir`).
- **Файловая система:** рекомендуется `ext4` или `xfs` с опцией `noatime`. Избегайте `btrfs` и `zfs` из-за нестабильной задержки `fdatasync`.

## Практические сценарии

### Атомарные транзакции (Txn)
Использование транзакций позволяет обновлять конфигурацию согласованно, выполняя проверку текущей ревизии (`mod_revision`) для предотвращения конфликтов.

```bash
etcdctl txn <<'EOF'
cmp
mod_revision("/config/api") = 123
then
put /config/api "new_value"
else
get /config/api
EOF
```

### Регистрация сервиса с TTL
Используется для обнаружения сервисов. Если `KeepAlive` перестаёт поступать, ключи удаляются автоматически.

```bash
# Создать аренду на 30 секунд
lease_id=$(etcdctl lease grant 30 | awk '{print $2}')
# Привязать сервис к аренде
etcdctl put /services/worker-1 "10.0.0.5" --lease=$lease_id
```

### Высокая доступность и кворум (HA Cluster)
Для production-сред стандартом является кластер из **3 или 5 узлов**, распределённых по разным стойкам/дата-центрам.
- **Консенсус Raft:** лидер реплицирует WAL на последователей и подтверждает запись только после получения кворума.
- **Мониторинг стабильности:** частота смены лидеров (`etcd_server_leader_changes_seen_total`) является первичным индикатором сетевых проблем или перегрузки CPU.

### Масштабирование крупных кластеров Kubernetes
При росте кластера Kubernetes нагрузка на etcd смещается с объёма данных на количество Watch-соединений и частоту обновлений.

1. **Оптимизация чтения (RangeStream):** в v3.7+ механизм `RangeStream` позволяет API-серверу инициализировать кэши без риска OOM, что критично при десятках тысяч подов (в Kubernetes v1.37+ — feature gate `EtcdRangeStream`).
2. **Watch Cache в API-сервере:** watch cache включён по умолчанию и автоматически масштабируется (флаг `--default-watch-cache-size` устарел); большинство запросов на чтение обслуживается из памяти API-сервера, минуя прямое обращение к BoltDB. Мониторинг попаданий/промахов — `etcd_helper_cache_hit_count` / `etcd_helper_cache_miss_count` на стороне API-сервера.
3. **Требования к дискам (NVMe):** для WAL задержка `fdatasync` p99 должна быть постоянно **< 10 мс**. При масштабирии с 1000 до 5000 узлов переход на локальные NVMe SSD (Gen4+) является обязательным условием стабильности.

### Тюнинг конфигурации

Ключевые параметры для настройки производительности и стабильности:

```bash
# Компакция: в Kubernetes выполняет kube-apiserver (--etcd-compaction-interval, дефолт 5m).
# На стороне etcd авто-компакция выключена по умолчанию (--auto-compaction-retention=0).
# Включайте её только если компакция НЕ выполняется на стороне API-сервера:
# конкурирующие компакторы вызывают "mvcc: required revision has been compacted"
# на длинных watch-потоках (см. ./garbage_collection.md, ./kubernetes_integration.md)

# Ограничение размера БД (рекомендуемый максимум 8 ГБ)
--quota-backend-bytes=8589934592

# Максимальный размер запроса (дефолт 1.5 MiB). При повышении поднимите
# клиентские лимиты MaxCallSendMsgSize (clientv3, дефолт 2 MiB) и
# MaxCallRecvMsgSize (grpc-go, дефолт 4 MiB) — см. ./limits_and_constraints.md
--max-request-bytes=33554432

# Порог создания снапшота (дефолт 10 000 в 3.6+; 100 000 в 3.5)
--snapshot-count=10000
```

**Валидация:**
```bash
# Проверить текущий размер БД и квоту
curl -s http://localhost:2379/metrics | grep etcd_mvcc_db_total_size_in_bytes
curl -s http://localhost:2379/metrics | grep etcd_server_quota_backend_bytes
```

### Дефрагментация и управление дисковым пространством

После массового удаления ключей или расширения кластера выполняйте дефрагментацию для возврата неиспользуемых страниц операционной системе.

```bash
# Онлайн дефрагментация всего кластера (поочередно, не параллельно)
etcdctl defrag --cluster

# Онлайн дефрагментация конкретного узла
etcdctl defrag --endpoints=https://10.0.0.11:2379
```

**Валидация:**
```bash
# Вычислить фрагментацию через метрики
curl -s http://localhost:2379/metrics | grep etcd_mvcc_db_total_size
# fragmentation = (total - in_use) / total
# Если > 50% — требуется дефрагментация
```

**Best Practices:**
- Выполняйте `etcdctl defrag` по очереди на узлах (не одновременно) в часы минимальной нагрузки.
- Это возвращает свободное место в ОС и ускоряет чтение (меньший файл = меньше дисковых операций).

### Обработка NOSPACE Alarm

```bash
# 1. Проверить алармы (на каждом узле — алармы не реплицируются)
etcdctl alarm list
# → memberID: 1234567890abcdef, alarm: NOSPACE

# 2. Получить текущую ревизию и выполнить компакцию
rev=$(etcdctl endpoint status --write-out="json" | egrep -o '"revision":[0-9]*' | egrep -o '[0-9].*')
etcdctl compact $rev
# → compacted revision 1516

# 3. Дефрагментация (поочередно, не параллельно)
etcdctl defrag --cluster

# 4. Сброс аларма (disarm принимает НОЛЬ аргументов и сбрасывает ВСЕ алармы)
etcdctl alarm disarm
```

**Важно:** квота ограничивает размер файла БД, а не свободное место на диске — удаление старых снапшотов и логов не снимает NOSPACE. `alarm disarm` без предварительной компакции и дефрагментации приведёт к немедленному возврату аларма. `defrag` блокирует чтение и запись на узле на время выполнения (обычно несколько секунд). Подробный playbook — в [Систематический troubleshooting](./troubleshooting.md).


## Troubleshooting

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `etcdserver: database space exceeded` / NOSPACE | Достигнут `quota-backend-bytes` | Compaction → defrag → `etcdctl alarm disarm` (см. выше) |
| `etcdserver: corrupted WAL` | Сбой питания до завершения `fdatasync` | Восстановление из снапшота/бэкапа (см. [Аварийное восстановление](./emergency_recovery.md)) |
| `mvcc: required revision has been compacted` | Чтение/watch по скомпактированной ревизии | Полный GET; новый watch с текущей revision |
| `failed to send out heartbeat on time` | Медленный диск или CPU starvation | Проверить `etcd_disk_wal_fsync_duration_seconds` p99 и `etcd_network_peer_round_trip_time_seconds` |
| `80% of the file descriptor limit is used` | Много клиентов/watchers | Поднять `LimitNOFILE` (см. [Тюнинг ОС](./kernel_tuning.md)) |

Полный пошаговый playbook (медленный etcd, потеря кворума, коррупция данных) — в **[Систематический troubleshooting](./troubleshooting.md)**.

## Best Practices

- **Не ждите NOSPACE:** алерт на 70–85% заполнения квоты (`etcd_mvcc_db_total_size_in_bytes / etcd_server_quota_backend_bytes`).
- **Compact перед defrag:** без компакции дефрагментация вернёт мало места.
- **Defrag по очереди:** дефрагментируйте узлы поочередно в часы минимальной нагрузки — каждый узел блокируется на время выполнения.
- **Выделенный диск:** отдельный физический диск (или раздел) под `data-dir`; при необходимости вынесите WAL на отдельный диск (`--wal-dir`).
- **Мониторьте фрагментацию:** разрыв между `etcd_mvcc_db_total_size_in_bytes` и `etcd_mvcc_db_total_size_in_use_in_bytes`.
- **Убирайте устаревшие override:** явное `--snapshot-count=100000` от 3.5 отключает оптимизацию памяти 3.6+.

## Граничные случаи

- **Watch не линейизуем:** etcd не гарантирует linearizability для watch-операций — проверяйте revision событий для корректного упорядочивания с другими операциями.
- **Serializable reads:** могут вернуть устаревшие данные — не используйте для чтения конфигурации сразу после записи без проверки revision.
- **RangeStream и сортировка:** запросы с нестандартной сортировкой или фильтрами по revision автоматически падают обратно на unary Range (`Unimplemented`).
- **Чётные кластеры:** 4 узла не дают преимущества перед 3 — кворум 3 из 4; при равном расколе сети кворум теряется. Используйте нечётное число узлов (см. [Кластеризация и восстановление](./clustering_and_recovery.md)).
- **Снапшот не усекает WAL мгновенно:** усечение WAL ограничено applied index — записи не удаляются из лога до применения к MVCC (см. [Proposal Pipeline](./proposal_pipeline.md)).
- **Дефолт `--snapshot-count` различается между мажорными версиями:** 100 000 (3.5) vs 10 000 (3.6+) — учитывайте при апгрейде и при сравнении поведения кластеров.

## Дополнительная информация

### Взаимосвязь с другими подсистемами

etcd состоит из тесно связанных компонентов:
- **Raft** обеспечивает логическую согласованность и репликацию (детали — в [Алгоритм Raft](./raft_consensus.md)).
- **MVCC** (через BoltDB и treeIndex) обеспечивает версионирование и историю данных.
- **gRPC API** предоставляет интерфейс для клиентов и встроенный Prometheus exporter на порту 2379.
