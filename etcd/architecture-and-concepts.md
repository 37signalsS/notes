# Архитектура и основные концепции etcd

## Определения

**etcd** — распределённое, согласованное и отказоустойчивое хранилище данных в формате "ключ-значение". Служит центральным источником истины для конфигураций, обнаружения сервисов (service discovery) и координации распределённых систем.

| Концепция | Назначение |
|---|---|
| **Key-Value Store** | Основная модель данных. Ключ — байтовая строка (часто в виде пути), значение — произвольные байтовые данные. |
| **Lease (Аренда)** | Механизм для создания эфемерных (временных) ключей, которые автоматически удаляются по истечении срока жизни TTL (Time To Live). |
| **Watch (Наблюдение)** | API (Application Programming Interface) для подписки на изменения ключей или их диапазонов в реальном времени. |
| **Revision (Ревизия)** | Глобальный номер версии всего хранилища, который делает возможным чтение данных "на момент времени". |
| **Transaction (Транзакция)** | Атомарная операция "сравнить и выполнить" (compare-and-swap). Основана на [механизме MVCC](./mvcc_versioning_and_compaction.md). |

## Основные концепции

### API v3 vs v2

Современные системы используют API (Application Programming Interface) v3, который является стандартом де-факто. v2 считается устаревшим и не рекомендуется к использованию.

* **Производительность**: v3 значительно быстрее и эффективнее благодаря переработанному бэкенду и gRPC (gRPC Remote Procedure Call) протоколу.
* **Функциональность**: v3 ввёл ключевые возможности, такие как транзакции, компакция и эффективные `watch`-уведомления. API v2 имеет ограниченные возможности и страдает от проблем с производительностью.
* **Хранилище**: Данные, созданные через API v2, недоступны через v3, и наоборот. Миграция требует специальной процедуры.

> **Важно:** Начиная с etcd 3.6 (2025), API v2 полностью удалён. Флаг `--enable-v2` больше не поддерживается.

### Пространство ключей

Ключи в etcd лексикографически упорядочены. Хотя etcd не имеет встроенной концепции "папок", принято использовать иерархическую структуру имён, разделяя компоненты слэшем, например: `/services/production/api/config`. Этот подход позволяет эффективно запрашивать целые "каталоги" с помощью запросов по префиксу.

### Аренда (Lease) и эфемерные ключи

Lease — это объект на стороне сервера etcd с заданным временем жизни TTL (Time To Live). Ключи можно привязать к аренде. Пока аренда активна (клиент должен периодически отправлять keep-alive сигналы), связанные с ней ключи существуют. Как только TTL аренды истекает, все привязанные ключи автоматически удаляются. Это основной механизм для регистрации сервисов и реализации блокировок.

Подробности реализации — в [кластеризации и восстановлении](./clustering_and_recovery.md).

### Наблюдение за изменениями (Watch)

Клиенты могут устанавливать "наблюдателей" за ключами или диапазонами ключей (по префиксу). etcd будет в реальном времени отправлять поток событий (создание, обновление, удаление) по всем изменениям, соответствующим подписке. Это позволяет системам динамически реагировать на смену конфигурации без постоянных опросов (polling).

Подробные примеры использования — в [практических сценариях etcd](../Kubernetes/Concepts/etcd_operations.md).

### Согласованность и версионирование

* **Консенсус**: Надёжность и согласованность данных в кластере обеспечивается [**алгоритмом Raft**](./raft_consensus.md), который является фундаментом для репликации и отказоустойчивости. Все операции записи проходят через лидера и реплицируются на большинство узлов.
* **Версионирование**: Каждое изменение в хранилище создаёт новую глобальную ревизию. Реализуется через механизм [**MVCC (Multi-Version Concurrency Control)**](./mvcc_versioning_and_compaction.md), который хранит множество версий данных и позволяет читать состояние на любой момент времени.

## Производительность и аппаратные требования

Производительность etcd критически зависит от задержек дисковой подсистемы и сети, так как каждая операция записи требует фиксации на диске (fsync) и достижения консенсуса между узлами.

### Требования к дискам

* **Тип накопителя**: Только SSD (Solid State Drive) или NVMe (Non-Volatile Memory Express). Использование HDD (жестких дисков) в production недопустимо из-за высоких задержек позиционирования головок.
* **IOPS и задержка**:
  * Минимально: последовательная запись 50 IOPS (Input/Output Operations Per Second) размером 8 Кб с задержкой `fdatasync` менее **10 мс**.
  * Для высоких нагрузок: 500 IOPS (8 Кб) с задержкой менее **2 мс**.
* **Выделенные ресурсы**: Рекомендуется использовать выделенные диски для etcd, чтобы избежать влияния "шумных соседей" (других процессов, активно пишущих на диск). Не используйте эти диски для хранения логов.
* **Сетевые хранилища (NAS/SAN)**: Избегайте использования iSCSI, NFS (Network File System) или Ceph Rados, так как они вносят непредсказуемую сетевую задержку. В облачных средах используйте локальные SSD или высокопроизводительные блочные хранилища с гарантированным IOPS.

### Тестирование производительности

Перед запуском кластера необходимо проверить дисковую подсистему с помощью утилиты `fio`:

```bash
fio --rw=write --ioengine=sync --fdatasync=1 --directory=./etcd-data --size=22m --bs=2300 --name=etcd-test
```

Значение `fdatasync` в результатах должно соответствовать вышеуказанным требованиям.

## Практические сценарии

Базовые примеры использования `etcdctl` (API v3). Подробные сценарии — в [практических сценариях etcd](../Kubernetes/Concepts/etcd_operations.md).

**Запись и чтение по префиксу:**

```bash
# Запись ключа
etcdctl put /configs/api/url https://svc.local

# Чтение всех ключей с префиксом /configs/api/
etcdctl get /configs/api/ --prefix
```

**Транзакция (Compare-and-Swap):**
Обновить URL (Uniform Resource Locator), только если его версия (`version`) равна 1.

```bash
etcdctl txn <<'EOF'
cmp
version("/configs/api/url") = 1
then
put /configs/api/url https://new-svc.local
else
get /configs/api/url
EOF
```

**Использование аренды (Lease) для регистрации сервиса:**

```bash
# Создать аренду на 60 секунд
lease_id=$(etcdctl lease grant 60 | awk '{print $2}')

# Привязать ключ к аренде и периодически обновлять TTL (Time To Live)
etcdctl put --lease=$lease_id /services/api/node1 "10.0.1.10:8080"
etcdctl lease keep-alive $lease_id
```

**Наблюдение за изменениями конфигурации:**

```bash
# Наблюдать за всеми изменениями в /configs/api/
etcdctl watch /configs/api/ --prefix
```
