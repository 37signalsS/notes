# Архитектура и основные концепции etcd

**etcd** — это высоконадежное распределенное хранилище данных в формате "ключ-значение", использующее [алгоритм консенсуса Raft](./raft_consensus.md). Служит централизованным хранилищем для конфигураций, обнаружения сервисов и координации состояния в распределенных системах (например, в Kubernetes).

## Определения

| Термин | Описание |
| :--- | :--- |
| **gRPC API** | Основной интерфейс взаимодействия (v3). Использует HTTP/2 и Protobuf для высокой производительности и двунаправленной потоковой передачи. |
| **RangeStream (v3.7+)** | Механизм потоковой передачи больших диапазонов ключей (server-side streaming). Устраняет OOM-аварии при выборке тысяч объектов. |
| **Linearizability (Линеаризуемость)** | Самая строгая гарантия согласованности. Читатель гарантированно получает результат самой последней завершенной записи. |
| **Lease (Аренда)** | Механизм создания временных ключей с TTL. Используется для регистрации сервисов и liveness-проверок. |
| **Watch (Наблюдение)** | Подписка на поток изменений ключей в реальном времени через gRPC-стримы. |
| **Revision (Ревизия)** | Глобальный логический счетчик времени всего хранилища. Каждая запись инкрементирует ревизию. |
| **WAL (Write-Ahead Log)** | Журнал предзаписи на диске. Каждая операция сначала фиксируется в WAL для обеспечения надежности при сбоях. |
| **BoltDB (bbolt)** | Встроенная база данных (B+ tree), используемая для персистентного хранения MVCC-данных на диске. Движок `bbolt` является форком BoltDB с оптимизациями для etcd. |
| **treeIndex** | B-дерево в оперативной памяти, которое сопоставляет пользовательские ключи с их ревизиями в BoltDB. |
| **Snapshot** | Полный снимок состояния MVCC на конкретной ревизии, используемый для усечения лога и быстрой синхронизации отставших узлов. |
| **Alarm** | Сигнал нештатного состояния узла. Типы: `NOSPACE` (превышена квота диска) и `CORRUPT` (поврежден файл данных). Алармы не распространяются автоматически между участниками. |
| **Endpoint** | Адрес узла для взаимодействия: Client URL (2379) для клиентов, Peer URL (2380) для Raft-коммуникации. |
| **Quota (Backend Bytes)** | Максимальный размер файла BoltDB (по умолчанию 2 ГБ, максимум 8 ГБ). При превышении etcd блокирует запись и поднимает alarm `NOSPACE`. |
| **Consistent Index** | Внутренний индекс, связывающий Raft-лог с MVCC-хранилищем. Гарантирует идемпотентность применения записи к BoltDB. |

## Основные концепции

### Внутренняя архитектура и путь записи (Write Flow)

etcd работает как "реплицируемый автомат" (Replicated State Machine). Процесс записи в etcd v3.7 выглядит следующим образом:

1. **Предложение (Proposal):** gRPC-сервер получает запрос и передает его модулю Raft.
2. **Фиксация в WAL:** Лидер записывает операцию в свой WAL-файл и вызывает `fdatasync`.
3. **Репликация:** Лидер рассылает операцию фолловерам. Они также фиксируют её в своих WAL.
4. **Коммит (Commit):** Как только большинство (кворум) подтвердили запись в WAL, лидер помечает операцию как "закоммиченную".
5. **Применение (Apply):** Операция передается в слой применения (MVCC):
   - Обновляется **treeIndex** в памяти (создается новая ревизия, сопоставляющая ключ с версией).
   - Данные записываются в **BoltDB** (B+ дерево на диске), где ключом является ревизия.
6. **Ответ:** Клиент получает подтверждение успеха.

### Путь чтения (Read Path)

etcd поддерживает два типа чтения с разными гарантиями:

1. **Линейaризуемое чтение (Linearizable Read):** Лидер подтверждает свой статус через механизм **ReadIndex** — обменивается пустыми heartbeats с большинством узлов перед ответом. Это гарантирует, что лидер не был изолирован (не произошло split-brain).
   - **Оптимизация Lease Read:** Если лидер уверен в своей аренде (Lease), он может вернуть ответ без обмена heartbeats с кворумом. Это снижает задержку чтения, но требует идеально синхронизированного времени (NTP).
2. **Сериализуемое чтение (Serializable Read):** Запрос выполняется локально с любого узла (включая фолловеров) без обращения к лидеру. Быстрее, но может вернуть устаревшие данные (stale reads).

### Хранилище данных: BoltDB и treeIndex

etcd использует двухслойную архитектуру хранения:

1. **treeIndex (в памяти):** B-дерево, сопоставляющее пользовательские ключи с историей их ревизий. Позволяет мгновенно находить актуальную версию данных без дискового ввода-вывода. Размер treeIndex пропорционален количеству ключей, а не объему значений.
2. **BoltDB (на диске):** B+ дерево (движок `bbolt`), где ключом является номер ревизии. Данные записываются последовательно, что оптимально для SSD. BoltDB использует copy-on-write: при каждом изменении создаются новые страницы, а старые становятся "мертвыми" и попадают в Freelist.

**Фрагментация:** При удалении ключей или compaction-операциях физический размер файла не уменьшается автоматически. Разница между `db_total_size` и `db_total_size_in_use` показывает уровень фрагментации:
- **< 30%**: Норма.
- **30–50%**: Требуется планирование дефрагментации.
- **> 50%**: Критично. Выполните `etcdctl defrag`.

### WAL (Write-Ahead Log)

WAL гарантирует, что сбой питания не приведет к повреждению данных. Каждая операция сначала записывается в WAL на диске с вызовом `fdatasync()`, и только потом реплицируется на фолловеры.

- **Сегментация:** WAL разбит на файлы сегментов. Когда сегмент достигает определенного размера, создается новый.
- **Ротация:** При создании снапшота старые сегменты WAL, предшествующие snapshot-index, удаляются или архивируются.
- **Повреждение:** Если `fdatasync` не успел завершиться при сбое питания, WAL может быть поврежден. Метрика `etcd_disk_wal_corruption_total` фиксирует такие случаи. Для восстановления требуется `etcdutl wal verify` и восстановление из снапшота.

### RangeStream (v3.7+) и потоковая передача

До версии 3.7 большие запросы (напр., получение всех подов в кластере) требовали полной буферизации результата в памяти сервера перед отправкой. Это вызывало OOM-аварии на крупных масштабах.
- **Потоковый RPC:** `RangeStream` разбивает ответ на чанки и отправляет их клиенту по мере чтения из BoltDB.
- **Константная память:** Потребление RAM сервером больше не зависит от размера выборки.
- **Снимок ревизии:** Весь поток данных привязан к единой MVCC-ревизии на момент начала запроса.

### Гарантии согласованности

etcd обеспечивает различные уровни согласованности для операций чтения:
- **Linearizability (Линеаризуемость):** Стандарт по умолчанию. Использует механизм **ReadIndex**. Гарантирует отсутствие "грязных чтений".
- **Serializable (Последовательная):** Быстрее, но может вернуть устаревшие данные (stale reads).

### Аренда (Lease) и FastLeaseKeepAlive

Механизм аренды позволяет привязывать TTL к набору ключей.
- **FastLeaseKeepAlive (v3.7):** Продление аренды теперь происходит по ускоренному пути, не дожидаясь индекса применения в Raft-логе. Это предотвращает ложное истечение аренды при высокой нагрузке на диск или процессор.

### Снапшот (Snapshot) и усечение лога

Raft-лог не может расти бесконечно. Когда количество записей достигает порога (`--snapshot-count`, по умолчанию 10 000 в v3.6/v3.7), etcd выполняет:
1. **Снимок (Snapshot):** Текущее состояние данных сохраняется на диск в `member/snap/`.
2. **Усечение (Truncation):** Все записи в WAL, предшествующие снимку, удаляются.
3. **Передача снапшота:** Если новый узел (Follower или Learner) сильно отстал и нужных записей в логе лидера уже нет, лидер отправляет ему полный снимок (Snapshot transfer).

### Алгоритм компакции и дефрагментация

- **Компакция (Compaction):** Логически удаляет старые ревизии из `treeIndex` и помечает соответствующие страницы в BoltDB как свободные для повторного использования. Не уменьшает физический размер файла.
- **Дефрагментация (Defrag):** Единственный способ физически уменьшить файл БД и вернуть место ОС. Процедура создает новый файл BoltDB, копируя в него только "живые" данные. Блокирует запись и чтение на узле на время выполнения.

### Алармы (Alarms)

etcd поддерживает два типа алармов:
- **NOSPACE:** Превышен `quota-backend-bytes`. etcd переходит в режим только для чтения и блокирует новые записи.
- **CORRUPT:** Поврежден файл данных (WAL или BoltDB) из-за аппаратного сбоя или некорректного завершения.

Алармы не распространяются автоматически между участниками. Каждый узел поднимает alarm независимо. Для восстановления требуется ручное вмешательство на каждом узле.

### Полное удаление v2 Store

Начиная с версии 3.7, etcd полностью очищен от наследия API v2.
- Флаг `--enable-v2` удален.
- Механизм самообнаружения (v2 discovery) больше не поддерживается.
- Снижение объема кодовой базы повысило общую стабильность и безопасность.

### Сеть, порты и TLS

- **Client port 2379:** используется клиентами (etcdctl, kube-apiserver) для операций чтения/записи.
- **Peer port 2380:** используется для Raft gossip и передачи снапшотов между узлами.
- **Metrics port:** по умолчанию совпадает с client port (2379), эндпоинт `/metrics`.
- Включение peer TLS обязательно для production. Отсутствие шифрования peer-соединений exposes sensitive data (snapshots, Raft log) на сетевом уровне.
- Рекомендуется разделять Peer- и Client-трафик на разных интерфейсах или через балансировщик, чтобы всплеск клиентского трафика не влиял на канал синхронизации Raft.

## Аппаратные требования и производительность

etcd чрезвычайно чувствителен к задержкам ввода-вывода и процессора. Для стабильной работы production-кластера в 2026 году необходимо соблюдать следующие требования:

### Процессор (CPU)
- **Производительность:** Минимум 2–4 физических ядра с высокой тактовой частотой. etcd активно использует CPU для сериализации Protobuf и вычисления хешей Raft.
- **Изоляция:** В высоконагруженных средах рекомендуется использовать `isolcpus` или CPU Pinning, чтобы предотвратить переключение контекста и гарантировать мгновенную обработку heartbeat-сообщений.

### Память (RAM)
- **Объем:** 8–16 ГБ для средних кластеров K8s. В v3.7+ оптимизация `RangeStream` позволяет удерживать потребление памяти стабильным даже при массовых операциях чтения.
- **Кэширование:** etcd эффективно использует системный кэш для BoltDB. Чем больше RAM, тем меньше обращений к диску при чтении.
- **Файловые дескрипторы:** Лимит ОС (`ulimit -n`) должен быть не менее 40 000. При большом количестве Watch-соединений дефицит дескрипторов приводит к отказу новых подключений.

### Дисковая подсистема (Критический фактор)
- **Тип носителя:** Исключительно **локальные NVMe SSD** (Gen4/Gen5). Использование сетевых дисков (EBS, Ceph) или обычных SATA SSD в 2026 году считается антипаттерном из-за высокого джиттера.
- **Задержка fdatasync:** Должна быть **< 1 мс** (p99). Пики > 10 мс вызывают перевыборы лидера и дестабилизацию кластера.
- **Выделенный диск:** Крайне рекомендуется выделять отдельный физический диск (или раздел с гарантированным IOPS) под `data-dir` etcd.
- **Файловая система:** Рекомендуется `ext4` или `xfs` с опцией `noatime`. Избегайте `btrfs` и `zfs` из-за нестабильной задержки `fdatasync`.

## Практические сценарии

### Атомарные транзакции (Txn)
Использование транзакций позволяет обновлять конфигурацию согласованно, выполняя проверку текущей ревизии (`mod_revision`) для предотвращения конфликтов.

```bash
etcdctl txn <<'EOF'
cmp
mod_revision("/config/api") = 123
then
put /config/api "new_value"
else
get /config/api
EOF
```

### Регистрация сервиса с TTL
Используется для обнаружения сервисов. Если `KeepAlive` перестает поступать, ключи удаляются автоматически.

```bash
# Создать аренду на 30 секунд
lease_id=$(etcdctl lease grant 30 | awk '{print $2}')
# Привязать сервис к аренде
etcdctl put /services/worker-1 "10.0.0.5" --lease=$lease_id
```

### Высокая доступность и кворум (HA Cluster)
Для production-сред 2026 года стандартом является кластер из **3 или 5 узлов**, распределенных по разным зонам доступности (Multi-AZ).
- **Консенсус Raft v3.7:** Лидер реплицирует WAL на последователей и подтверждает запись только после получения кворума.
- **Мониторинг стабильности:** Частота смены лидеров (`etcd_server_leader_changes_seen_total`) является первичным индикатором сетевых проблем или перегрузки CPU.

### Масштабирование до 5000+ узлов
При росте кластера нагрузка на etcd смещается с объема данных на количество Watch-соединений и частоту обновлений.

1. **Оптимизация чтения (RangeStream):** В v3.7.1 механизм `RangeStream` позволяет API-серверу инициализировать кэши без риска OOM, что критично при десятках тысяч подов.
2. **Watch Cache в API-сервере:** Увеличение размера `Watch Cache` позволяет обслуживать >90% запросов на чтение из памяти API-сервера, минуя прямое обращение к BoltDB.
3. **Требования к дискам (NVMe):** Для WAL задержка `fdatasync` p99 должна быть постоянно **< 1 мс**. При масштабировании с 1000 до 5000 узлов переход на локальные NVMe SSD (Gen4+) является обязательным условием стабильности.

### Тюнинг конфигурации

Ключевые параметры для настройки производительности и стабильности:

```bash
# Автоматическая компакция (Kubernetes standard)
--auto-compaction-mode=periodic --auto-compaction-retention=5m

# Ограничение размера БД (максимум 8 ГБ)
--quota-backend-bytes=8589934592

# Максимальный размер запроса (по умолчанию 1.5 MB)
--max-request-bytes=33554432

# Порог создания снапшота (по умолчанию 10 000)
--snapshot-count=10000
```

**Валидация:**
```bash
# Проверить текущий размер БД и квоту
curl -s http://localhost:2379/metrics | grep etcd_mvcc_db_total_size_in_bytes
curl -s http://localhost:2379/metrics | grep etcd_server_quota_backend_bytes
```

### Дефрагментация и управление дисковым пространством

После массового удаления ключей или расширения кластера выполняйте дефрагментацию для возврата неиспользуемых страниц операционной системе.

```bash
# Онлайн дефрагментация всего кластера (поочередно, не параллельно)
etcdctl defrag --cluster

# Онлайн дефрагментация конкретного узла
etcdctl defrag --endpoints=https://10.0.0.11:2379
```

**Валидация:**
```bash
# Вычислить фрагментацию через метрики
curl -s http://localhost:2379/metrics | grep etcd_mvcc_db_total_size
# fragmentation = (total - in_use) / total
# Если > 50% — требуется дефрагментация
```

**Best Practices:**
- Выполняйте `etcdctl defrag` по очереди на узлах (не одновременно) в часы минимальной нагрузки.
- Это возвращает свободное место в ОС и ускоряет чтение (меньший файл = меньше дисковых операций).

### Обработка NOSPACE Alarm

```bash
# 1. Проверить alarms
etcdctl alarm list
# → memberID: 1234567890abcdef, alarm: NOSPACE

# 2. Освободить место на диске (удалить старые снапшоты, логи)
# 3. Выполнить дефрагментацию на каждом узле (по очереди)
etcdctl defrag --cluster=true
# 4. Disarm alarm
etcdctl alarm disarm NOSPACE
```

**Важно:** `alarm disarm` без предварительного освобождения места может привести к немедленному возврату alarms. `defrag` блокирует операции на время выполнения (обычно несколько секунд). Выполняйте дефрагментацию последовательно, узел за узлом.

### Валидация снапшотов и WAL

```bash
# Проверить валидность снапшота
etcdutl snapshot status backup.db -w table
# → Hash: 1a2b3c4d, Revision: 512340, Total key count: 1254300

# Проверить целостность WAL
etcdutl wal verify /var/lib/etcd/wal/
# → WAL verify passed, records: 15420

# Статистика WAL
etcdutl wal show /var/lib/etcd/wal/
# → WAL records: 15420, file size: 1.2GB
```

### Проверка производительности

```bash
# Тест производительности записи
etcdctl check perf --load="s"  # s (small), m (medium), l (large), xl (x-large)
# → PASS: Throughput is 150 writes/s
```

**Интерпретация порогов (ориентировочно для NVMe):**
- **Small (s):** PASS при > 100 writes/s.
- **Medium (m):** PASS при > 50 writes/s.
- **Large (l):** PASS при > 20 writes/s.
- **X-Large (xl):** PASS при > 5 writes/s.

## Дополнительная информация

### Взаимосвязь с другими подсистемами

etcd состоит из нескольких tightly coupled компонентов:
- **Raft** обеспечивает логическую согласованность и репликацию.
- **MVCC** (через BoltDB и treeIndex) обеспечивает версионирование и историю данных.
- **gRPC API** предоставляет интерфейс для клиентов и встроенный Prometheus exporter на порту 2379.
