# Мониторинг etcd

Мониторинг **etcd** критически важен для стабильности кластера, особенно в Kubernetes. Задержки или сбои в работе etcd напрямую приводят к деградации производительности Control Plane и невозможности изменения состояния кластера.

## Определения

**Prometheus Exporter** — встроенный в etcd HTTP-сервер, предоставляющий метрики в формате Prometheus (обычно на порту `2379/metrics`).

**Health Check** — механизм проверки работоспособности узла. Узел считается `healthy`, если он успешно зафиксировал проверочное предложение (proposal) в журнале.

**Leader Election (Выборы лидера)** — процесс в протоколе Raft, гарантирующий наличие одного активного лидера в кластере для обработки операций записи.

**Fsync** — системный вызов, заставляющий ОС сбросить данные из кэша на физический диск. Критичен для WAL (Write-Ahead Log).

## Основные концепции

### Доступность и кворум

Для работы кластера etcd необходим кворум (большинство узлов: `(n/2)+1`). Потеря лидера или отсутствие кворума делает кластер доступным только на чтение или полностью неработоспособным.

* **Наличие лидера**: `etcd_server_has_leader`. Должно быть всегда равно **1**. Значение **0** на всех узлах означает критический сбой.
* **Изменения лидерства**: `etcd_server_leader_changes_seen_total`. Частое изменение (flapping) указывает на нестабильность сети или перегрузку диска.
* **Неудачные предложения**: `etcd_server_proposals_failed_total`. Рост метрики сигнализирует об ошибках записи (например, из-за потери лидерства в процессе).

### Производительность диска и сети

etcd крайне чувствителен к задержкам. Каждая запись должна быть подтверждена большинством и зафиксирована в WAL.

* **WAL Fsync**: `etcd_disk_wal_fsync_duration_seconds`.
    * **Норма**: p99 < 10 мс.
    * **Критично**: p99 > 100 мс.
* **Backend Commit**: `etcd_disk_backend_commit_duration_seconds`. Время фиксации данных в основном хранилище (db).
    * **Норма**: p99 < 25 мс.
* **Network Latency**: `etcd_network_peer_round_trip_time_seconds`. RTT между узлами.
    * **Норма**: p99 < 50 мс.

### Использование ресурсов и квоты

etcd имеет жесткую квоту на размер БД (по умолчанию 2 ГБ, максимум 8 ГБ). При достижении лимита etcd переходит в режим `NOSPACE` и блокирует запись.

* **Размер БД**: `etcd_mvcc_db_total_size_in_bytes`.
    * **Alert**: при достижении 80% от настроенной квоты.
* **Использование БД**: `etcd_mvcc_db_total_size_in_use_in_bytes`. Реальный объем данных. Разница между `total` и `in_use` показывает уровень фрагментации.
* **Дефрагментация**: Если фрагментация > 50%, рекомендуется выполнить `defrag`.

### Версионные особенности (3.5 и 3.6)

* **etcd 3.5**: Версии 3.5.0–3.5.2 имели критические баги повреждения данных. Рекомендуется использовать **3.5.26+**.
* **etcd 3.6**: Введена значительная оптимизация памяти (~50%) за счет снижения `snapshot-count` по умолчанию со 100 000 до 10 000.
* **Метрики gRPC**: В современных версиях метрики клиентского трафика отслеживаются через `etcd_network_client_grpc_received_bytes_total` и `sent_bytes_total`.

## Практические сценарии

### Ручная диагностика здоровья

Использование `etcdctl` для быстрой проверки состояния:

```bash
# Проверка здоровья всего кластера
etcdctl endpoint health --cluster
# → 127.0.0.1:2379 is healthy: successfully committed proposal: took = 1.52ms

# Проверка статуса и размера БД
etcdctl endpoint status --write-out=table
# → +----------------+------------------+---------+---------+-----------+------------+-----------+------------+--------------------+
# → |    ENDPOINT    |        ID        | VERSION | DB SIZE | IS LEADER | IS LEARNER | RAFT TERM | RAFT INDEX | RAFT APPLIED INDEX |
# → +----------------+------------------+---------+---------+-----------+------------+-----------+------------+--------------------+
# → | 127.0.0.1:2379 | 8e9e05f54f240d12 |  3.5.16 |  25 MB  |    true   |    false   |        12 |     450123 |             450123 |
# → +----------------+------------------+---------+---------+-----------+------------+-----------+------------+--------------------+
```

### Проверка метрик через TLS

Если etcd требует сертификаты (стандарт в K8s):

```bash
curl --cacert /etc/etcd/ca.crt --cert /etc/etcd/server.crt --key /etc/etcd/server.key \
     https://127.0.0.1:2379/metrics | grep etcd_server_has_leader
# → etcd_server_has_leader 1
```

### Настройка алертов (Prometheus)

Рекомендованные условия для алертинга:

| Алерт | Выражение (PromQL) | Описание |
| :--- | :--- | :--- |
| **EtcdNoLeader** | `etcd_server_has_leader == 0` | Узел потерял лидера |
| **EtcdHighFsyncIter** | `histogram_quantile(0.99, rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])) > 0.1` | Медленный диск (WAL) |
| **EtcdDbQuotaNearFull** | `etcd_mvcc_db_total_size_in_bytes / etcd_server_quota_backend_bytes > 0.8` | БД заполнена на 80% |

### Ключевые метрики производительности (Performance Metrics)

Для кластеров большого масштаба (5000+ узлов) мониторинг должен быть сфокусирован на задержках дисковой подсистемы и стабильности кворума.

| Метрика | Описание | Целевое значение / Порог |
| :--- | :--- | :--- |
| **`etcd_disk_wal_fsync_duration_seconds`** | Длительность выполнения `fsync` для WAL. Ведущий индикатор проблем с дисковым вводом-выводом. | **p99 < 10 мс**. Пики > 100 мс критичны. |
| **`etcd_mvcc_db_total_size_in_bytes`** | Общий физический размер базы данных BoltDB на диске. | Должен быть стабильным после настройки агрессивного сжатия. |
| **`etcd_server_leader_changes_seen_total`** | Счетчик изменений лидера в кластере etcd. | Высокий темп роста указывает на проблемы в сети или перегрузку CPU. |
| **`etcd_disk_backend_commit_duration_seconds`** | Длительность коммитов в backend хранилище. | p99 < 25 мс. |

### Рекомендации по алертингу (Alerting)

В крупных средах алертинг должен срабатывать до того, как деградация etcd приведет к отказу API-сервера.

1.  **Высокая задержка fsync:**
    - **Условие:** `histogram_quantile(0.99, sum(rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])) by (instance)) > 0.01`
    - **Действие:** Проверить нагрузку на дисковую подсистему, убедиться в отсутствии влияния соседних процессов (I/O Wait).

2.  **Частая смена лидера:**
    - **Условие:** `rate(etcd_server_leader_changes_seen_total[15m]) > 3`
    - **Действие:** Проверить стабильность сетевых соединений между узлами etcd и нагрузку на CPU Control Plane.

3.  **Приближение к лимиту размера БД:**
    - **Условие:** `etcd_mvcc_db_total_size_in_bytes > 7.5 * 1024 * 1024 * 1024` (для стандартного лимита 8GB)
    - **Действие:** Выполнить принудительное сжатие и дефрагментацию. Проверить настройки `auto-compaction`.

### Оптимизация производительности etcd

Для стабильной работы etcd в высоконагруженных кластерах необходимо проводить тюнинг на нескольких уровнях:

#### 1. Аппаратный уровень и ОС
*   **Дисковая подсистема:** Использование SSD или NVMe является обязательным. Рекомендуется выделять отдельный физический диск под WAL (Write-Ahead Log) для минимизации задержек `fsync`.
*   **Приоритеты процессов:** Установите высокий приоритет для процесса etcd с помощью `nice` и `ionice` (например, `ionice -c2 -n0`), чтобы гарантировать доступ к ресурсам даже при общей нагрузке на узел.

#### 2. Тюнинг параметров etcd
*   **`--snapshot-count`:** В etcd 3.6+ значение по умолчанию снижено до 10 000. Слишком частое создание снимков нагружает диск, слишком редкое — замедляет восстановление узла.
*   **`--heartbeat-interval`:** Интервал между сообщениями лидера. Для сетей с задержками может потребоваться увеличение значения (стандарт 100мс).
*   **`--election-timeout`:** Время ожидания перед новыми выборами. Должно быть в 5-10 раз больше `heartbeat-interval` (стандарт 1000мс).
*   **`--quota-backend-bytes`:** Увеличьте лимит БД до 8 ГБ, если кластер содержит десятки тысяч объектов.

#### 3. Архитектурные оптимизации
*   **Разделение трафика:** Вынесение ресурса `Events` в отдельный кластер etcd. События в Kubernetes генерируют огромный поток записей, которые могут замедлять работу API-сервера с критическими ресурсами (`Pods`, `Secrets`).
*   **Компакция и дефрагментация:** Настройте автоматическую компакцию (`--auto-compaction-retention`) и периодически выполняйте `etcdctl defrag` для возврата свободного места в ОС.
