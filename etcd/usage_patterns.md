# Паттерны использования etcd

**Актуально для:** etcd 3.7.x / 3.6.x / 3.5.x (API v3; примеры на clientv3)

## Определения

**Coordination pattern** — типовой способ применения распределённого хранилища для решения задач координации: конфигурация, обнаружение сервисов, выборы лидера, блокировки, очереди, ограничение скорости.

**Session** — долгоживущая аренда (lease) в clientv3-пакете `concurrency`, привязанная к контексту. Пока сессия жива, созданные через неё ключи существуют; при разрыве или истечении — удаляются. Внутри — lease с TTL по умолчанию **60 секунд**, авто-продлеваемый; доступен через `Session.Lease()`, `Session.Done()`.

**Campaign / Election** — механизм выборов лидера: кандидаты создают последовательные ключи под общим префиксом, лидером становится владелец ключа с наименьшей ревизией.

**Mutex** — распределённая взаимная блокировка на lease: владелец — держатель ключа с минимальной ревизией, остальные ждут освобождения.

**STM (Software Transactional Memory)** — API для безопасного выполнения набора операций над несколькими ключами с изоляцией и автоматическим повтором при конфликте.

**Fencing token** — монотонно растущий маркер (в etcd — ревизия), который внешний ресурс сверяет, чтобы отвергнуть запись от «просроченного» владельца блокировки.

Пакет `go.etcd.io/etcd/client/v3/concurrency` предоставляет готовые реализации: `Session`, `Election`, `Mutex`, `NewLocker`, `STM` (проверено по исходникам v3.7.2).

## Предварительные требования

- **etcd 3.5+** (API v3); для `RangeStream` и `--stream` в etcdctl — **3.7+**. Рекомендуемая production‑ветка — **3.7.x** (на 2026‑09‑22: v3.7.2). Обновление до 3.7 требует предварительного перехода всех узлов на **3.6.11+** (см. [Версионную совместимость](./version_compatibility.md)).
- **clientv3** — `go get go.etcd.io/etcd/client/v3`; для concurrency‑паттернов `go.etcd.io/etcd/client/v3/concurrency`. Go‑версия в etcd 3.7 — 1.26.x (см. `go.mod` etcd repo).
- **Тонкой настройки не требуется:** паттерны работают поверх стандартного TLS + сертификатов клиента. Lease/TTL по умолчанию — 60 секунд (`concurrency.NewSession`), переопределяется `concurrency.NewSession(cli, concurrency.WithTTL(seconds))`.
- **Доступ:** клиент подключается к 2379 (client URL); для выборов/блокировок требуется quorum (большинство узлов доступно).

## Валидация паттернов (как проверить, что паттерн «сработал»)

- **Централизованная конфигурация:** `etcdctl get --prefix /config/app/` возвращает актуальные значения; приложение логирует их применение без перезапуска.
- **Обнаружение сервисов:** `etcdctl get --prefix /services/api/` показывает только живые инстансы; при `sess.Close()` ключ исчезает немедленно.
- **Лидерство:** на лидере `e.Campaign()` возвращается без ошибки; `e.Leader(ctx)` возвращает ваш `val`; на followers — `Campaign()` блокируется. `etcd_server_has_leader == 1` на всех узлах.
- **Блокировка:** `mu.Lock()` завершается; `etcdctl get --prefix /locks/resource-1/` возвращает ваш ключ; `mu.Unlock()` удаляет его. `mu.IsOwner()` → `true` только у держателя.
- **STM:** транзакция либо применяется целиком, либо откатывается и повторяется при конфликте (clientv3 возвращает `nil` error, если `stm.Get`‑условие не выполнено — транзакция не пишет).
- **Аллюрный singleton:** `last_run` обновляется ровно один раз в интервал; при падении лидера новый лидер видит предыдущее `last_run` и продолжает с него.

## Основные концепции

Общий принцип всех паттернов: **etcd хранит не сами данные, а состояние координации**. Значения должны быть небольшими (метаданные, адреса, идентификаторы), так как весь KV-объём держится в памяти и реплицируется по Raft. Крупные объекты (файлы, блобы, тела сообщений) в etcd не хранят — только ссылки на внешнее хранилище.

Второй принцип: **любая привязка к времени (lease/session) не гарантирует владение внешним ресурсом**. Клиент может «зависнуть» (долгий GC, stop-the-world, пауза ВМ), а lease истечёт и блокировка перейдёт другому. Для корректности нужен fencing-токен.

## Паттерны

### 1. Централизованная конфигурация

Конфигурация сервисов хранится под префиксом, приложения подписаны на изменения через watch и перечитывают значения без рестарта.

```go
resp, _ := cli.Get(ctx, "/config/app/", clientv3.WithPrefix())
watchCh := cli.Watch(ctx, "/config/app/", clientv3.WithPrefix())
for wresp := range watchCh {
    for _, ev := range wresp.Events {
        // применить ev.Kv
    }
}
```

**Практика:** версионируйте конфигурацию (`/config/app/v2/...`), читайте по revision для воспроизводимости. Для раздачи в файлы на хостах используют `confd` (имеет etcd‑backend) или `consul-template` — учтите, что **consul-template официально поддерживает только Consul/Vault/Nomad**, etcd‑backend у него отсутствует (см. [HashiCorp consul-template](https://developer.hashicorp.com/consul/docs/automate/consul-template)). Модели push/pull описаны в [Модели управления конфигурацией](../Concepts/configuration_management_models.md).

### 2. Обнаружение сервисов и реестр

Инстансы сервиса регистрируются как ключи с TTL, привязанные к lease; потребители читают список и подписываются на изменения. Ключ исчезает автоматически, когда инстанс перестаёт продлевать lease.

```go
sess, _ := concurrency.NewSession(cli) // TTL 60s, авто-продление
key := "/services/api/" + instanceID
cli.Put(ctx, key, addr, clientv3.WithLease(sess.Lease()))
// при graceful shutdown: sess.Close() -> ключ удаляется
```

**Ограничения:** etcd не даёт health checking и DNS-интерфейса из коробки — это «сырой» реестр. Для полноценного service discovery с проверками и DNS выбирайте Consul (см. [Сравнение с Consul и ZooKeeper](./alternatives_comparison.md)) либо полагайтесь на Kubernetes-механику (`kube-apiserver` + endpoint controllers).

### 3. Выборы лидера (leader election)

Только один процесс выполняет роль активного (например, планировщик или контроллер). Остальные — standby и следят за сменой лидера.

```go
sess, _ := concurrency.NewSession(cli)
e := concurrency.NewElection(sess, "/election/scheduler/")

// блокируется, пока не станет лидером; val — идентификатор кандидата
if err := e.Campaign(ctx, "node-1"); err != nil {
    // handle error
}
// лидерство получено
```

- `e.Observe(ctx)` — канал с текущим лидером; при смене приходит новое значение.
- `e.Resign(ctx)` — добровольно сложить полномочия (например, при плановом обслуживании).
- `e.Proclaim(ctx, val)` — обновить значение лидера, оставаясь им.
- `concurrency.ResumeElection(...)` — восстановить наблюдение за лидерством после рестарта процесса по известному ключу.

**Важно:** лидерство в etcd — это гарантия **до** момента истечения lease. Лидер, «зависший» дольше TTL, теряет ключ, но может продолжать работу, не зная об этом. Все действия, требующие эксклюзивности, должны проверять актуальность (revision) на стороне ресурса.

### 4. Распределённая блокировка (mutex)

Взаимное исключение для критической секции, выполняемой на одном узле в каждый момент.

```go
sess, _ := concurrency.NewSession(cli)
mu := concurrency.NewMutex(sess, "/locks/resource-1/")

if err := mu.Lock(ctx); err != nil { // ждёт освобождения
    // handle error
}
defer mu.Unlock(ctx)
// критическая секция
```

- `mu.TryLock(ctx)` — не блокируясь, вернуть ошибку, если занято.
- `mu.IsOwner()` — `Cmp` для условной транзакции: проверить, что мы всё ещё владелец, перед записью.
- `concurrency.NewLocker(sess, prefix)` — обёртка, реализующая стандартный `sync.Locker`.

Подробный разбор семантики и типичных ловушек — в [Распределённые блокировки](../Concepts/Caching/caching_distributed_locks.md); внутреннее устройство lease и предупреждение о mutual exclusion — в [Watch и Lease](./watch_lease_internals.md).

### 5. Транзакционные обновления нескольких ключей (STM)

Когда нужно атомарно изменить несколько ключей с проверкой условий, используется `STM`: операции накапливаются, затем применяются единой транзакцией; при конфликте и смене revision — автоматический повтор.

```go
_, err := concurrency.NewSTM(cli, func(stm concurrency.STM) error {
    state := stm.Get("/service/state")
    if state == "degraded" {
        return nil // условие не выполнено — транзакция не пишет
    }
    stm.Put("/service/state", "degraded")
    stm.Put("/service/changed_at", time.Now().UTC().Format(time.RFC3339))
    return nil
})
```

**Практика:** STM подходит для согласованных обновлений реестров, пересылки «заданий» между очередями. При высокой конкуренции частые повторы снижают пропускную способность — уменьшайте долю конфликтующих ключей.

### 6. Кластерный планировщик / singleton-задачи

Комбинация election + STM: активный узел регулярно выполняет задачу, результат или отметка о времени последнего запуска пишется в etcd, чтобы при перевыборе новый лидер продолжил с корректного состояния.

```go
// псевдокод: активный лидер раз в минуту выполняет задачу и фиксирует run_ts
putTxn := clientv3.OpPut("/jobs/cleanup/last_run", timestamp)
cli.Txn(ctx).Then(putTxn).Commit()
```

Убедитесь, что задача идемпотентна: перевыбор лидера может привести к повторному запуску (см. [Идемпотентность](../Concepts/idempotency.md)).

### 7. Feature flags и динамические лимиты

Флаги как ключи с watch позволяют включать/выключать функциональность и менять лимиты без релиза. Читайте один раз при старте и подписывайтесь на изменения; кешируйте значение, чтобы не делать Get на каждый запрос.

### 8. Ограничение скорости (rate limiting) и квоты

Счётчики под ключом с TTL («token bucket в etcd») применимы для **грубого** ограничения между несколькими узлами, но конкурирующие CAS-операции создают давление на Raft. Для высокочастотного rate limiting используйте Redis (см. [Caching](../Concepts/Caching/caching_overview.md)) или локальные лимитеры; etcd оставляйте для редких квот и распределённых «разрешительных» счётчиков.

### 9. Распределённая очередь заданий

Очередь на ключах с последовательным префиксом: производители создают ключи, воркеры захватывают их через `Txn` с проверкой отсутствия значения. Такой паттерн (часто на базе STM) даёт at-least-once доставку; для больших объёмов и приоритетов применяйте специализированные брокеры (Kafka, NATS, RabbitMQ).

## Антипаттерны и подводные камни

| Антипаттерн | Почему плохо | Как правильно |
| :--- | :--- | :--- |
| Блокировка без fencing-токена | Просроченный владелец может писать после перехода блокировки | Проверять revision на стороне ресурса |
| Хранение крупных значений | Всё KV в памяти, репликация больших entry'ов повышает latency | Хранить ссылки, данные — во внешнем хранилище |
| Watch без обработки `ErrCompacted` | После компакции watch закрывается, информер молча перестаёт обновляться | Полный GET + новый watch с актуальной ревизии |
| Короткий TTL и агрессивный keep-alive | Частые продления нагружают Raft; короткий TTL даёт ложные срабатывания | TTL ≥ нескольких секунд, баланс между скоростью обнаружения и нагрузкой |
| Один watch-стрим на большое число ключей | Перегрузка клиента и сервера | Разделять по префиксам, использовать `WithPrefix` и фильтры |
| Ожидание, что lease = владение ресурсом | Часы клиента и сервера расходятся, истечение непредсказуемо | Идемпотентные операции + fencing |
| Частые конкурентные CAS-счётчики | Драки за revision, повторы, рост latency | Redis/локальные лимитеры для высокочастотных счётчиков |

## Практические рекомендации

- **Минимум ключей на одной сессии.** Одна `Session` на процесс, а не на операцию — иначе лавина lease и продлений.
- **Именование префиксами.** `/services/`, `/config/`, `/locks/`, `/election/` — облегчает права (RBAC) и декларацию диапазонов.
- **Graceful shutdown.** Явно `sess.Close()` и `mu.Unlock()` при остановке, чтобы не ждать TTL.
- **Проверяйте актуальность через `Txn`.** Перед записью по результату блокировки — `Cmp` на `mod_revision` или `IsOwner()`.
- **Мониторьте паттерн.** Для выборов — `etcd_server_leader_changes_seen_total` (частота переизбраний) и `etcd_server_proposals_failed_total`; для реестра — размер префикса и частоту изменений. Пороги и алерты — в [Мониторинге etcd](./etcd_monitoring.md).

## Граничные случаи (lease, session, election)

- **Клиентский clock skew / GC‑пауза:** lease продлевается сервером по **серверным** часам. Если клиент долго не отвечает (GC `Stop-the-world`, пауза ВМ), lease может истечь и блокировка перейти к другому, тогда клиент продолжает работать «вслепую». Именно поэтому взаимное исключение без fencing‑токена — антипаттерн (см. таблицу выше).
- **Long partition к лидеру:** клиент, удерживающий keepalive к недоступному лидеру, может оставаться в «слепом» состоянии до истечения lease; `Session.Done()` сигнализирует об обрыве — переподключайтесь и проверяйте `Done()`.
- **Короткий TTL при высокой нагрузке:** TTL 1–2 s + агрессивный keepalive = шторм lease renewal в Raft. TTL ≥ 10 s и `KeepAlive` каждые `TTL/2–TTL/3` дают лучшую устойчивость.
- **Concurrent `Campaign` от «бывшего» лидера:** после `Resign()`/`Close()` старый лидер может попытаться `Proclaim` — сервер отклонит (revision‑based CAS), поэтому не полагайтесь на клиентский state.
- **Watch без `ErrCompacted`:** если watcher отстаёт от compaction, сервер закрывает поток с `mvcc: required revision has been compacted`; клиент должен выполнить `Get` с актуальной ревизией и открыть новый watch.
- **STM под очередью конфликтов:** при >70% конфликтов throughput падает — сокращайте конфликтующее ключевое пространство или выносите очередь в выделенный etcd.
- **DB‑specific:** для `Mutex`‑ключей лучше короткие префиксы (`/locks/r-1/` + hash), т.к. имя ключа попадает в каждый `Txn`‑commit; длинные имена растут `etcd_mvcc_db_total_size_in_use_in_bytes`.
