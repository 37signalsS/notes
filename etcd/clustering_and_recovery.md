# Кластеризация и восстановление etcd

**Актуально для:** etcd 3.6.x / 3.7.x (Learner — 3.4+; Pre-Vote — добавлен в 3.4, по умолчанию с 3.5; offline restore через `etcdutl` — 3.6+)

Кластеризация обеспечивает высокую доступность и отказоустойчивость хранилища за счет репликации данных и автоматического выбора лидера через [алгоритм Raft](./raft_consensus.md). Теория консенсуса и loss of majority — в [Raft-консенсус](./raft_consensus.md); поведение при сетевых разделениях и gray failures — в [Сетевые разделения](./network_partitions.md).

## Определения

| Термин | Описание |
| :--- | :--- |
| **Кластер etcd** | Группа узлов, работающих совместно для обеспечения согласованности данных через [алгоритм Raft](./raft_consensus.md). |
| **Кворум (Quorum)** | Минимальное количество голосующих узлов для принятия решений: `(n/2) + 1`. |
| **Learner (v3.4+)** | Неголосующий участник кластера. Получает данные от лидера, но не влияет на кворум и не может стать лидером. Используется для безопасного расширения кластера. |
| **Pre-Candidate / Pre-Vote (3.4+)** | Состояние узла перед выборами. Проверяет доступность кворума без увеличения `Term`, что предотвращает «дребезг» лидера при сетевых миганиях. Добавлен в 3.4 (флаг `--pre-vote`, по умолчанию выключен), включён по умолчанию с 3.5 (флаг удалён). |
| **Member** | Узел кластера с уникальным `id` и набором `peer URLs`. |
| **Peer URL** | Адрес, по которому узел взаимодействует с другими участниками кластера (Raft gossip, передача снапшотов). |
| **Client URL** | Адрес, по которому клиенты (etcdctl, kube-apiserver) подключаются для операций чтения/записи. |
| **Initial Cluster** | Полный список `name=peer URL` для первичной инициализации или восстановления кластера. |
| **Cluster Token** | Идентификатор кластера, предотвращающий случайное слияние кластеров при восстановлении из общего снапшота. |
| **Term** | Номер эпохи в Raft. Увеличивается при каждой выборке лидера. |
| **Log Index / Commit Index / Applied Index** | Индексы в Raft-логе: последний записанный, подтверждённый кворумом, применённый к состоянию машины. |
| **Снапшот (Snapshot)** | Полный снимок состояния базы данных на конкретную ревизию. Требуется для аварийного восстановления и предотвращения бесконечного роста WAL. |
| **Split-Brain** | Ситуация разделения сети. В etcd «классический» split-brain (двое пишущих лидеров) невозможен благодаря Raft, однако возможна потеря кворума. |
| **CheckQuorum** | Механизм, при котором лидер добровольно слагает полномочия при потере связи с большинством. Включён в etcd 3.4+ во всех режимах запуска (настройка raft-уровневая, CLI-флага нет). |
| **StrictReconfigCheck** | Защита конфигурации по умолчанию: `member add`/`remove` отклоняется, если изменение ведёт к потере кворума или кластер нездоров. |
| **HealthInterval** | Минимальное время (5 с), в течение которого кластер должен быть здоров, прежде чем etcd примет `member add`/`remove`. |
| **Multi-zone развёртывание** | Стратегия развертывания узлов в разных зонах отказа/дата-центрах для защиты от катастрофических сбоев дата-центра. |
| **WAL (Write-Ahead Log)** | Журнал предзаписи. Гарантирует сохранность операций при сбое питания узла. |

## Основные концепции

### Топология и кворум

etcd требует нечётного количества узлов (3, 5, 7) для максимизации отказоустойчивости. Использование чётного количества узлов (например, 4) не повышает устойчивость к сбоям по сравнению с меньшим нечётным числом (3), но увеличивает накладные расходы на сеть.

| Узлов | Кворум | Допустимый отказ | Сценарий применения |
| :--- | :--- | :--- | :--- |
| 1 | 1 | 0 | Тестирование, малые кластеры (Edge). |
| 3 | 2 | 1 | Стандарт для малых и средних кластеров. |
| 5 | 3 | 2 | Production baseline. Устойчивость к потере AZ + 1 узла. |
| 7 | 4 | 3 | Очень крупные кластеры с высокими требованиями к HA. |

### Сетевые задержки и RTT

Производительность Raft напрямую зависит от задержек между узлами.
* **Норма**: Peer RTT < 50 мс.
* **Критично**: Peer RTT > 100 мс (при дефолтном `election-timeout` 1000 мс — предел `election-timeout / 10`; может вызывать частые перевыборы).
* **Multi-zone**: При размещении в разных зонах убедитесь, что `heartbeat-interval` сопоставим с RTT, а `election-timeout` минимум в 10 раз больше RTT.

### Raft Log Replication

При записи клиент отправляет запрос на лидер. Лидер записывает запись в локальный WAL, рассылает `AppendEntries` по всем узлам кластера и ждет подтверждения от кворума. После получения подтверждения от большинства запись фиксируется (committed) и применяется к состоянию машины (applied). Ответ клиенту отправляется только после фиксации. Этот механизм гарантирует, что запись не будет потеряна при сбое отдельного узла.

Важно: запись не возвращает успех клиенту, пока не получит подтверждение от большинства узлов. Поэтому при высокой задержке между узлами latency записи растет пропорционально round-trip времени до самого медленного узла в кворуме.

### Snapshotting и WAL

etcd периодически создает фоновые снапшоты для предотвращения бесконечного роста WAL. Снапшот создается, когда в Raft-логе накапливается более `--snapshot-count` записей (default: 10 000 в 3.6+, 100 000 в 3.5). При создании снапшота лидер отправляет его отставшим узлам, после чего старые записи WAL удаляются. Снапшот не блокирует операции чтения и записи. При восстановлении из снапшота данные загружаются в BoltDB, а WAL применяется только за снапшот.

### Learner lifecycle

1. Узел добавляется через `etcdctl member add --learner`. Он не имеет права голоса и не может стать лидером. Кластер может иметь не более `--max-learners` learner'ов (default 1; флаг 3.6+, в 3.5 — `--experimental-max-learners`).
2. Лидер передает новому узлу снапшот и последующие записи лога. При сильном отставании лидер отправляет снапшот плюс до `--snapshot-catchup-entries` записей (default 5000) для догона.
3. Узел синхронизируется, его `RAFT INDEX` стремится к значению лидера.
4. Узел повышается до голосующего участника через `etcdctl member promote`. etcd проверяет готовность автоматически: **learner должен иметь `Match` ≥ 90% от `Match` лидера** (`readyPercentThreshold = 0.9`, хардкод в `etcdserver`, не настраивается). При отставании промоут отклоняется с ошибкой `etcdserver: can only promote a learner member which is in sync with leader`.
5. Перед `member add`/`remove`/`promote` etcd проверяет, что кластер был здоров минимум `HealthInterval` (5 с) и что изменение не ведёт к потере кворума (`StrictReconfigCheck`, включён по умолчанию).

### Pre-Candidate (Pre-Vote)

Перед началом полноценных выборов узел переходит в состояние Pre-Candidate и отправляет `MsgPreVote` без увеличения `Term`. Если активный лидер отвечает, выборы отменяются. Это предотвращает «дребезг» лидера при кратковременных сетевых сбоях, когда узел временно теряет связь с большинством. Механизм добавлен в etcd 3.4 (флаг `--pre-vote`, по умолчанию выключен) и включён по умолчанию с 3.5 (флаг удалён).

### Реальность "Split-Brain"

В etcd невозможен сценарий, когда две изолированные части кластера одновременно принимают записи (Linearizability). Однако при разделении сети:
1. **Меньшинство (Minority)**: Переходит в состояние поиска лидера и блокирует операции записи.
2. **Большинство (Majority)**: Продолжает работу, если в нем остался лидер или он может быть выбран.

**Важно**: кластер из 2 узлов (n=2) имеет кворум 2. При потере одного узла второй не может набрать кворум, и кластер останавливается. Поэтому 2 узла непригодны для production.

### Сеть, порты и TLS

* **Client port 2379**: используется клиентами (etcdctl, kube-apiserver) для чтения и записи.
* **Peer port 2380**: используется для Raft gossip и передачи снапшотов между узлами.
* Включение peer TLS обязательно для production. Отсутствие шифрования peer-соединений в дата-центре открывает доступ к чувствительным данным (снапшоты, Raft-лог) на сетевом уровне.

### Bootstrap кластера

Начальное формирование кластера возможно тремя способами. Динамические способы нужны, когда peer-адреса неизвестны заранее (облако, DHCP).

**1. Static bootstrap (рекомендуется).** Все участники знают друг друга: каждый узел запускается с полным списком в `--initial-cluster` и `--initial-cluster-state new`. Параметры, начинающиеся с `--initial-*`, применяются только при первом запуске и игнорируются в дальнейшем — их можно удалить после успешного формирования кластера. Пример — в разделе восстановления ниже.

**2. DNS discovery (`--discovery-srv`).** Узлы находят друг друга через SRV-записи. Для `--discovery-srv example.com` выполняются запросы в порядке:

- `_etcd-server-ssl._tcp.example.com`, затем `_etcd-server._tcp.example.com` — при находке SSL-записи bootstrap идёт по TLS;
- для клиентов: `_etcd-client._tcp.example.com`, затем `_etcd-client-ssl._tcp.example.com` (при контроле доступа/шифровании).

Правила и подводные камни:

- Разрешённый адрес из `--initial-advertise-peer-urls` **должен совпадать** с одним из адресов SRV-целей, иначе узел не распознает свою принадлежность к кластеру.
- С 3.2 `--listen-peer-urls` и `--listen-client-urls` **не принимают доменные имена** для привязки интерфейса — только IP/`0.0.0.0`.
- При TLS домен discovery (`example.com`) должен присутствовать в SAN сертификата и совпадать с доменом SRV-записей, иначе кластеризация падает с `tls: bad certificate`.
- Флаг `--discovery-srv-name` добавляет суффикс к имени SRV-записи (например, `_etcd-server-ssl-foo._tcp.example.com`) для нескольких кластеров в одном домене.
- Служебные флаги: `--discovery-fallback` (`exit` или `proxy`) и `--discovery-proxy` (HTTP-прокси до discovery-сервиса).

**3. etcd discovery service (`--discovery`) — недоступен на 3.6+.** Классический discovery-сервис (`discovery.etcd.io` или self-hosted через `/v2/keys/discovery/<token>`) регистрирует узлы через v2 API. v2 API полностью удалён в 3.6, а в 3.7 удалены v2 store и v2 discovery service (см. [совместимость версий](./version_compatibility.md)). Для новых кластеров используйте static bootstrap или DNS discovery. Замечание: официальный clustering-гайд v3.7 всё ещё описывает etcd discovery на v2 API — это устаревший фрагмент документации, не применяйте его на 3.6+.

## Стратегии обеспечения высокой доступности (HA)

### 1. Multi-zone топология (2-2-1 или 1-1-1)

Для защиты от отказа целого дата-центра узлы распределяются по зонам доступности.
- **3 узла (1-1-1)**: Позволяет пережить отказ **одной зоны**.
- **5 узлов (2-2-1)**: Рекомендуемый паттерн. Позволяет пережить отказ **одной зоны** и **одного дополнительного узла** во второй зоне.

### 2. Внешний кластер (External etcd)

Вынос etcd за пределы Control Plane узлов Kubernetes.
- **Плюсы**: Изоляция от ресурсов API-сервера, независимое масштабирование, упрощенное восстановление.
- **Минусы**: Требует управления отдельной инфраструктурой и TLS.
- **Рекомендация**: Для production сред из 5+ Control Plane узлов используйте внешний etcd-кластер из 3 или 5 узлов.

### 3. Автоматизация резервного копирования

Снапшот — единственный способ восстановления при полной потере кворума.
- **Периодичность**: Каждые 15 минут (см. [Стратегии резервного копирования](./backup_strategies.md)).
- **Хранение**: Обязательная копия вне текущего сайта (сетевой том, удаленный сервер).
- **Инструменты**: `gardener/etcd-backup-restore` или системный `CronJob` с использованием `etcdctl snapshot save` (см. [etcd Operator и автоматизация](./etcd_operator.md)).
- **Валидация**: После каждого снапшота выполняйте `etcdutl snapshot status`, чтобы убедиться в его целостности.

## Практические сценарии

### Безопасное добавление узла (через Learner)

При добавлении нового узла в большой кластер лидер должен передать ему снапшот. Если добавить узел сразу как голосующий, кворум увеличится мгновенно, и если новый узел медленно синхронизируется, кластер станет уязвимым к отказу еще одного участника.

```bash
# 1. Добавить узел как learner на текущем лидере
etcdctl member add node4 --peer-urls=https://10.0.1.13:2380 --learner

# 2. Запустить etcd на новом узле с флагом --initial-cluster-state existing
etcd \
  --name node4 \
  --initial-cluster-state existing \
  --initial-cluster "node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380,node3=https://10.0.1.12:2380,node4=https://10.0.1.13:2380" \
  --peer-urls https://10.0.1.13:2380 \
  --data-dir /var/lib/etcd

# 3. Проверить синхронизацию: RAFT INDEX нового узла должен стремиться к лидеру
etcdctl endpoint status --cluster -w table

# 4. Повысить до голосующего (проверка готовности — автоматическая)
etcdctl member promote 8e9e05f54f240d12

# 5. Валидация: убедиться, что новый узел участвует в выборах
etcdctl member list -w table
```

**Валидация**: `etcdctl endpoint health --cluster -w table` показывает `true` для всех узлов. `RAFT INDEX` нового узла ≥ 90% от `RAFT INDEX` лидера.

**Edge Cases**:
- Если `member promote` возвращает ошибку `etcdserver: can only promote a learner member which is in sync with leader` — learner ещё не догнал лидера: проверьте сетевые задержки, iowait и `--snapshot-catchup-entries`; дождитесь синхронизации.
- При потере связи с learner во время синхронизации удалите его через `etcdctl member remove`, если он не был промоутирован.

### Замена узла (Rolling Upgrade / Node Replacement)

```bash
# 1. Добавить новый узел как learner
etcdctl member add node5 --peer-urls=https://10.0.1.14:2380 --learner

# 2. На новом узле запустить etcd с --initial-cluster-state existing
etcd \
  --name node5 \
  --initial-cluster-state existing \
  --initial-cluster "node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380,node3=https://10.0.1.12:2380,node4=https://10.0.1.13:2380,node5=https://10.0.1.14:2380" \
  --peer-urls https://10.0.1.14:2380 \
  --data-dir /var/lib/etcd

# 3. Дождаться синхронизации и промоутить
etcdctl endpoint status --cluster -w table
etcdctl member promote <NODE5_ID>

# 4. Убедиться, что кворум сохранен (5 узлов → кворум 3)
etcdctl member list -w table

# 5. Удалить старый узел
etcdctl member remove <OLD_NODE_ID>
```

**Валидация**: после удаления старого узла количество голосующих членов уменьшается, но кворум остается достижимым. Проверьте `etcdctl endpoint health`.

**Best Practice**: Удаление лидера безопасно, но вызывает краткий даунтайм на время выборов (период `election-timeout`). Для минимизации даунтайма передайте лидерство (`move-leader`) перед удалением.

### Передача лидерства (Transfer Leader)

```bash
# Посмотреть текущего лидера и его MEMBER ID
etcdctl endpoint status --cluster -w table

# Передать лидерство на узел с ID 8e9e05f54f240d12 (указывается ID, не имя)
etcdctl move-leader 8e9e05f54f240d12

# Валидация: проверить, что leader изменился
etcdctl endpoint status --cluster -w table
```

**Edge Cases**: `move-leader` отказывает, если цель — learner или недоступный участник (`etcdserver: bad leader transferee`). В этом случае дождитесь синхронизации или выберите другой voter-узел. При graceful stop (`systemctl stop etcd`) etcd сам передаёт лидерство одному из voter'ов перед остановкой (`TryTransferLeadershipOnShutdown`).

### Проверка здоровья и кворума

```bash
# Проверить здоровье всех узлов
etcdctl endpoint health --cluster -w table
# → +----------------+--------+-------+-------+
# → |    ENDPOINT    | HEALTH |  TOOK | ERROR |
# → +----------------+--------+-------+-------+
# → | 10.0.1.10:2379 |  true  | 2.1ms |       |
# → | 10.0.1.11:2379 |  true  | 1.8ms |       |
# → | 10.0.1.12:2379 |  true  | 2.3ms |       |
# → +----------------+--------+-------+-------+

# Детальный статус каждого участника
etcdctl endpoint status --cluster -w table
# → ID, VERSION, DB SIZE, LEADER ID, RAFT INDEX, RAFT TERM

# Список членов кластера (колонка IS LEARNER показывает learner'ов)
etcdctl member list -w table
```

**Валидация**: количество healthy узлов >= кворума. `LEADER ID` совпадает у большинства узлов. Разница в `RAFT INDEX` между лидером и отставшими узлами минимальна.

**Troubleshooting**:
- Если узел показан `false` или `error`: проверьте сетевую доступность порта 2379, TLS-сертификаты и статус службы etcd (`systemctl status etcd`).

### Graceful Removal

```bash
# 1. Убедиться, что узел не является лидером
etcdctl endpoint status --cluster -w table

# 2. Если узел — лидер, передать лидерство (минимизация даунтайма)
etcdctl move-leader <OTHER_MEMBER_ID>

# 3. Удалить узел из кластера
etcdctl member remove <MEMBER_ID>

# 4. На удаляемом узле остановить etcd
systemctl stop etcd
```

**Валидация**: `etcdctl member list` больше не содержит удаленного узла. Кворум остается достижимым.

### Диагностика отставания Learner

```bash
# Сравнить RAFT INDEX learner с лидером
etcdctl endpoint status --cluster -w table

# Разница существенна: проверить сетевые задержки, TLS handshake time, iowait
# Проверить alarms на learner
etcdctl --endpoints=https://10.0.1.14:2379 alarm list
```

**Решение**: проверьте пропускную способность сети между зонами, iowait (`iostat`) и ресурсы learner'а; при сильном отставании лидер отправляет снапшот плюс до `--snapshot-catchup-entries` (default 5000) записей — убедитесь, что флаг не занижен. Увеличение `--snapshot-count` не помогает learner'у догнать лидера.

### Обнаружение и обработка NOSPACE Alarm

```bash
# 1. Проверить alarms
etcdctl alarm list
# → memberID: 1234567890abcdef, alarm: NOSPACE

# 2. Выполнить компакцию (удалить историю ревизий)
etcdctl compact <REVISION>

# 3. Выполнить дефрагментацию на каждом узле (по очереди)
etcdctl defrag --cluster

# 4. Disarm alarm (сбрасывает ВСЕ алармы; аргументов не принимает)
etcdctl alarm disarm
```

**Важно**: `alarm disarm` без предварительной компакции и дефрагментации приведёт к немедленному возврату аларма. `defrag` освобождает неиспользуемые страницы в BoltDB, но блокирует операции на время выполнения (обычно несколько секунд). Выполняйте дефрагментацию последовательно, узел за узлом. Подробнее — [MVCC и компакция](./mvcc_versioning_and_compaction.md), [Maintenance API](./maintenance_api.md).

## Аварийное восстановление (Disaster Recovery)

Если большинство узлов потеряны (кворум невозможен), кластер «умирает». Требуется создание нового кластера из снапшота. Полный алгоритм DR, fencing и `--force-new-cluster` — в [Аварийное восстановление](./emergency_recovery.md).

```bash
# 1. Изоляция (Cluster Fencing): убедиться, что старые узлы выключены или физически изолированы
# 2. Проверить снапшот перед восстановлением
etcdutl snapshot status backup.db
# → hash: 1234567890abcdef, revision: 48291, total key: 12500, size: 12.5 MB

# 3. Восстановление (Offline) на каждом узле будущего кластера
etcdutl snapshot restore backup.db \
  --name node1 \
  --initial-cluster node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380,node3=https://10.0.1.12:2380 \
  --initial-cluster-token new-cluster-token \
  --data-dir /var/lib/etcd-restored

# 4. Запустить etcd с восстановленной директорией
etcd \
  --name node1 \
  --initial-cluster-state new \
  --data-dir /var/lib/etcd-restored \
  --peer-urls https://10.0.1.10:2380

# 5. В Kubernetes: обновить hostPath в манифесте Static Pod на /var/lib/etcd-restored
```

**Для Kubernetes**: добавьте `--bump-revision=<N> --mark-compacted` (etcd 3.6+) — поднимает ревизию и помечает её скомпактированной, чтобы watches контроллеров не ждали ревизии, которой больше не будет (инвалидация informer-кэшей).

**Валидация**:
- `etcdctl endpoint health --cluster -w table` показывает все узлы healthy.
- `etcdctl get --prefix --keys-only` возвращает ожидаемые ключи.
- `etcdctl alarm list` пустой.

**Troubleshooting**:
- Ошибка `mvcc: required revision has been compacted`: восстановите более свежий снапшот.
- Ошибка `data-dir %q not empty or could not be read` при `etcdutl snapshot restore`: укажите новую/пустую директорию для restore.
- Ошибка TLS: убедитесь, что сертификаты с SAN/CN соответствуют новому `--name` и `--peer-urls`.
- Снапшот, скопированный из `data-dir/member/snap/db`, не содержит integrity hash — restore возможен только с `--skip-hash-check`.

## Поведение при недоступности etcd

**Если etcd становится недоступным на несколько минут:**

1. **API-сервер** переходит в read-only режим или становится полностью недоступным — не может читать/писать состояние кластера.
2. **Существующие Podы продолжают работать** — они уже запущены и не зависят от etcd для текущей работы.
3. **Планирование новых подов прекращается** — scheduler не может получить информацию о ресурсах узлов.
4. **Контроллеры перестают работать** — не могут сравнить желаемое и фактическое состояние.
5. **Обновления и удаления Podов не применяются** — изменения в API не сохраняются.

**После восстановления etcd:**
- Все изменения, произошедшие во время недоступности, **будут обработаны**.
- Контроллеры получают обновления через Watch-механизм и начинают сверку (reconciliation).
- Если Pod был удален из API, но kubelet не получил уведомление — kubelet получит обновление при переподключении и удалит Pod.
- **Исключение:** если Pod был удален физически (например, узел перезагрузился), а etcd был недоступен — kubelet не сможет подтвердить удаление, и Pod может остаться в API как "orphaned".

**Важно:** etcd хранит состояние, а не события. При восстановлении контроллеры видят текущее состояние и приводят его к желаемому. Потери событий нет — есть задержка в обработке.

## Восстановление после коррупции данных

```bash
# 1. Проверить целостность снапшота
etcdutl snapshot status backup.db

# 2. Проверить содержимое WAL на проблемном узле (etcdutl не имеет wal-команды)
etcd-dump-logs /var/lib/etcd

# 3. Если WAL поврежден, восстановиться из последнего валидного снапшота
etcdutl snapshot restore last-good-backup.db \
  --name node1 \
  --initial-cluster node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380 \
  --data-dir /var/lib/etcd-restored

# 4. Запустить кластер и проверить данные
etcdctl get --prefix --keys-only | wc -l
```

**Edge Cases**:
- **Коррупция на части узлов, кворум жив**: НЕ восстанавливайте из снапшота — это создаст новый кластер и потеряет записи после снапшота. Удалите проблемный узел (`etcdctl member remove`) и добавьте новый через learner → promote; новый член синхронизируется с лидера автоматически. Логический бэкап с живого узла (`etcdctl get "" --prefix --keys-only > all_keys.txt`) — только как страховка. Полный сценарий — [Аварийное восстановление](./emergency_recovery.md).

## Troubleshooting

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `member already exists` | ID или peer URL конфликтуют с существующим членом | Проверьте `etcdctl member list`, используйте уникальный `--name` и peer URL |
| `etcdserver: can only promote a learner member which is in sync with leader` | Learner отстает от лидера (Match < 90% от Match лидера) | Проверьте сеть, iowait, `--snapshot-catchup-entries`; дождитесь синхронизации |
| `etcdserver: bad leader transferee` | `move-leader` на learner или несуществующий участник | Передайте лидерство voter-follower |
| `no such member` при `remove`/`promote` | Неверный MEMBER ID | Получите ID через `etcdctl member list` |
| `required revision has been compacted` | Снапшот устарел, ревизия удалена компакцией | Используйте более свежий снапшот |
| `mvcc: database space exceeded` (NOSPACE) | Достигнут `quota-backend-bytes` | Compaction → defrag → `etcdctl alarm disarm`; при необходимости увеличить квоту (макс. 8 ГБ) |
| `connection refused` на 2380 | Фаерволл блокирует peer port, или etcd не слушает | Проверьте `ss -tlnp \| grep 2380`, правила фаерволла, конфиг `--listen-peer-urls` |
| TLS handshake failure | Неверный сертификат, CN/SAN, срок действия | Проверьте `openssl s_client -connect host:2380`, сроки сертификатов, соответствие `--name` CN |
| Лидер переизбирается каждые несколько секунд | Высокий Peer RTT, проблемы с сетью или disk I/O | Убедитесь, что Peer RTT < 50 мс, проверьте iowait (`iostat`), настройте `heartbeat-interval` и `election-timeout` |

## Best Practices

* **Размер кластера**: используйте 3 или 5 узлов. 7 узлов оправданы только при экстремальных требованиях к HA и низких задержках.
* **Learner для всех изменений**: в production добавляйте все новые узлы через `--learner` и промоутите только после проверки `RAFT INDEX`.
* **Сеть**: размещайте узлы в одном регионе с RTT < 50 мс. Для multi-zone развёртывания настройте `heartbeat-interval` с запасом на межзонные задержки.
* **TLS**: включите peer и client TLS. Ротируйте сертификаты до истечения срока: листовые — подменой файлов (hot-reload, etcd перечитывает их при каждом соединении с v3.2.0), CA — rolling restart. Автоматизация: `kubeadm certs renew`, `cert-manager`, `cfssl`. Подробнее — [Безопасность etcd](./security.md).
* **Encryption at Rest**: etcd не поддерживает шифрование на диске нативно — реализуется на уровне хранилища (LUKS/dm-crypt) или, в Kubernetes, через encryption at rest для secrets (KMS). Снапшоты содержат все данные в открытом виде — шифруйте их перед отправкой в offsite-хранилище (см. [Стратегии резервного копирования](./backup_strategies.md)).
* **Резервное копирование**: сочетайте периодические снапшоты (`etcdctl snapshot save`) с логическим бэкапом (`etcdctl get --prefix --keys-only`) для критичных ключей.
* **Восстановление**: проводите restore drills минимум раз в квартал. Время восстановления (RTO) должно быть задокументировано.
* **Мониторинг**: отслеживайте `etcd_server_has_leader`, `etcd_server_leader_changes_seen_total`, `etcd_server_proposals_failed_total`, `etcd_server_heartbeat_send_failures_total`, `etcd_server_proposals_applied_total`.

## Edge Cases

* **Восстановление на другую архитектуру**: снапшоты etcd переносимы между архитектурами с одинаковым порядком байт (amd64, arm64, ppc64le — все little-endian). При смене endianness (например, amd64 → s390x, big-endian) используйте логическое резервное копирование через `etcdctl get` или промежуточный etcd-кластер.
* **2 узла**: не используйте в production. При потере одного узла второй не набирает кворум (2/2), и кластер полностью останавливается.
* **Четное количество узлов**: 4 или 6 узлов не повышают отказоустойчивость по сравнению с меньшим нечётным числом, но увеличивают риск потери кворума при равном расколе (2-2) и накладные расходы на репликацию.
* **Снапшот версии**: снапшот можно восстановить на версию etcd >= версии создания. Для downgrade используйте промежуточный кластер с последующей логической миграцией данных.
* **v2-данные перед апгрейдом**: перед обновлением на 3.6+ убедитесь в отсутствии v2-данных (`etcdutl check v2store`) — в 3.6 удалён флаг `--enable-v2`, в 3.7 v2store удалён полностью. Хронология и миграция — [Совместимость версий](./version_compatibility.md).
* **Learner во время обновления**: при rolling upgrade добавляйте новую версию как learner, промоутите, затем удаляйте старую версию. Это исключает потерю кворума.
