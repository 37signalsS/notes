# Кластеризация и восстановление etcd

Кластеризация обеспечивает высокую доступность и отказоустойчивость хранилища за счет репликации данных и автоматического выбора лидера.

## Определения

| Термин | Описание |
| :--- | :--- |
| **Кластер etcd** | Группа узлов, работающих совместно для обеспечения согласованности данных через [алгоритм Raft](./raft_consensus.md). |
| **Кворум (Quorum)** | Минимальное количество голосующих узлов для принятия решений. Рассчитывается как `(n/2) + 1`. |
| **Learner (v3.4+)** | Неголосующий участник кластера. Получает данные от лидера, но не влияет на кворум. Используется для безопасного расширения кластера. |
| **Pre-Candidate (v3.5+)** | Состояние узла перед выборами. Проверяет доступность кворума, не увеличивая `Term`, что предотвращает "дребезг" лидера при сетевых миганиях. |
| **Снапшот (Snapshot)** | Полный снимок состояния базы данных на конкретную ревизию. Требуется для аварийного восстановления. |
| **Split-Brain** | Ситуация разделения сети. В etcd "классический" split-brain (двое пишущих лидеров) невозможен благодаря Raft, однако возможна потеря кворума. |
| **Multi-AZ** | Стратегия развертывания узлов в разных зонах доступности для защиты от катастрофических сбоев дата-центра. |
| **WAL (Write-Ahead Log)** | Журнал предзаписи. Гарантирует сохранность операций при сбое питания узла. |

## Основные концепции

### Топология и кворум

etcd требует нечетного количества узлов (3, 5, 7) для максимизации отказоустойчивости. Использование четного количества узлов (например, 4) не повышает устойчивость к сбоям по сравнению с меньшим нечетным числом (3), но увеличивает накладные расходы на сеть.

| Узлов | Кворум | Допустимый отказ | Сценарий применения |
| :--- | :--- | :--- | :--- |
| 1 | 1 | 0 | Тестирование, малые кластеры (Edge). |
| 3 | 2 | 1 | Стандарт для малых и средних кластеров. |
| 5 | 3 | 2 | **Production baseline (2026)**. Устойчивость к потере AZ + 1 узла. |
| 7 | 4 | 3 | Очень крупные кластеры с высокими требованиями к HA. |

### Сетевые задержки и RTT

Производительность Raft напрямую зависит от задержек между узлами.
* **Норма**: Peer RTT < 50 мс.
* **Критично**: Peer RTT > 100 мс (может вызывать частые перевыборы).
* **Multi-AZ**: При размещении в разных зонах убедитесь, что `heartbeat-interval` сопоставим с RTT, а `election-timeout` минимум в 10 раз больше.

### Реальность "Split-Brain"

В etcd невозможен сценарий, когда две изолированные части кластера одновременно принимают записи (Linearizability). Однако при разделении сети:
1. **Меньшинство (Minority)**: Переходит в состояние поиска лидера и блокирует операции записи.
2. **Большинство (Majority)**: Продолжает работу, если в нем остался лидер или он может быть выбран.

## Стратегии обеспечения высокой доступности (HA)

### 1. Multi-AZ топология (2-2-1 или 1-1-1)
Для защиты от отказа целого дата-центра узлы распределяются по зонам доступности.
- **3 узла (1-1-1)**: Позволяет пережить отказ **одной зоны**.
- **5 узлов (2-2-1)**: Рекомендуемый паттерн. Позволяет пережить отказ **одной зоны** и **одного дополнительного узла** во второй зоне.

### 2. Внешний кластер (External etcd)
Вынос etcd за пределы Control Plane узлов Kubernetes.
- **Плюсы**: Изоляция от ресурсов API-сервера, независимое масштабирование, упрощенное восстановление.
- **Минусы**: Требует управления отдельной инфраструктурой и TLS.

### 3. Автоматизация резервного копирования
Снапшот — единственный способ восстановления при полной потере кворума.
- **Периодичность**: Минимум раз в час.
- **Хранение**: Обязательная копия вне текущего региона/облака (S3, удаленный сервер).
- **Инструменты**: `etcd-backup-operator` или системный `CronJob` с использованием `etcdctl snapshot save`.

## Практические сценарии

### Безопасное добавление узла (через Learner)

При добавлении нового узла в большой кластер лидер должен передать ему снапшот. Если добавить узел сразу как голосующий, кворум увеличится мгновенно, и если новый узел медленно синхронизируется, кластер станет уязвимым к отказу еще одного участника.

1. **Добавить узел как learner:**
   ```bash
   etcdctl member add node4 --peer-urls=https://10.0.1.13:2380 --learner
   ```

2. **Запустить etcd** на новом узле с флагом `--initial-cluster-state existing`.

3. **Проверить синхронизацию**: Сравните `RAFT INDEX` нового узла с лидером через `etcdctl endpoint status`.

4. **Повысить до голосующего**:
   ```bash
   etcdctl member promote <MEMBER_ID>
   ```

### Аварийное восстановление (Disaster Recovery)

Если большинство узлов потеряны (кворум невозможен), кластер "умирает". Требуется создание нового кластера из снапшота.

1. **Изоляция (Cluster Fencing)**: Перед восстановлением убедитесь, что старые узлы физически изолированы или выключены, чтобы предотвратить их случайное вмешательство в новый кворум.
2. **Снятие снапшота**: Используйте последний доступный `backup.db`.
3. **Восстановление (Offline)**: Выполняется на каждом узле будущего кластера.
   ```bash
   # etcdutl обязателен для офлайн-восстановления в v3.6/3.7
   etcdutl snapshot restore backup.db \
     --name node1 \
     --initial-cluster node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380,node3=https://10.0.1.12:2380 \
     --initial-cluster-token new-cluster-token \
     --data-dir /var/lib/etcd-restored
   ```
4. **Запуск**: Используйте восстановленную директорию данных. В Kubernetes обновите `hostPath` в манифесте Static Pod.

## Дополнительная информация

### Безопасность и соответствие (2026)

* **Encryption at Rest**: Согласно стандартам безопасности 2026 (GDPR/PCI-DSS), данные etcd должны быть зашифрованы на диске. Используйте KMS-провайдеры (Vault, AWS KMS) для управления ключами.
* **Restore Drills**: Наличие бэкапа не гарантирует восстановление. Рекомендуется проводить ежеквартальные учения по восстановлению кластера в изолированной среде.

### Обслуживание

* **Замена узла**: Всегда сначала добавляйте новый узел (через learner), а затем удаляйте старый. Это поддерживает стабильность кворума.
* **Обновление**: При переходе на v3.7 убедитесь в полном отсутствии v2-данных. v3.7 окончательно удаляет поддержку v2 store.
