# Кластеризация и восстановление etcd

Кластеризация обеспечивает высокую доступность и отказоустойчивость хранилища за счет репликации данных и автоматического выбора лидера.

## Определения

**Кластер etcd** — группа узлов, работающих совместно для обеспечения согласованности данных через [алгоритм Raft](./raft_consensus.md).

**Quorum (Кворум)** — минимальное количество голосующих узлов, необходимых для принятия решений (записи данных или выбора лидера). Рассчитывается как `(n/2) + 1`.

**Learner (Узел-обучающийся)** — тип участника кластера, который получает данные от лидера, но не участвует в голосовании. Используется для безопасного добавления новых узлов без риска для доступности кворума.

**Snapshot (Снапшот)** — компактный снимок состояния базы данных на определенную ревизию. Необходим для аварийного восстановления и быстрой синхронизации новых узлов.

**WAL (Write-Ahead Log)** — журнал предзаписи, гарантирующий сохранность операций при внезапном сбое питания или перезагрузке узла.

## Основные концепции

### Топология и кворум

etcd рекомендует использовать нечетное количество узлов (3, 5, 7). Это максимизирует отказоустойчивость при минимальных затратах ресурсов.

| Кол-во узлов | Кворум | Допустимый отказ |
| :--- | :--- | :--- |
| 1 | 1 | 0 |
| 3 | 2 | 1 |
| 5 | 3 | 2 |
| 7 | 4 | 3 |

**Почему нечетное число?** Четное количество узлов (например, 4) требует кворума в 3 узла, что позволяет пережить отказ только одного участника — так же, как и в кластере из 3 узлов, но с большими затратами на сеть и диск.

**Важное примечание по производительности:** Хотя добавление большего количества узлов повышает отказоустойчивость, оно также приводит к увеличению задержек при записи и росту сетевого трафика (из-за необходимости репликации на большее число узлов). Обычно рекомендуется начинать с кластера из трех узлов.

## Стратегии обеспечения высокой доступности (HA)

Для достижения максимальной надежности etcd в критически важных средах (таких как Kubernetes) следует придерживаться следующих стратегий:

1.  **Развертывание в виде кластера**: Минимум три узла для обеспечения кворума. Это позволяет etcd продолжать работу при отказе одной ноды.
2.  **Использование внешнего кластера etcd**: Развертывание etcd на выделенных узлах, отдельно от плоскости управления (Control Plane) Kubernetes. Это:
    *   Улучшает масштабируемость.
    *   Изолирует etcd от сбоев в компонентах Control Plane (например, утечек памяти в API-сервере).
    *   Гарантирует сохранность состояния кластера даже при проблемах с управляющими узлами.
3.  **Регулярное резервное копирование**: Использование `etcdctl snapshot save` для создания снимков состояния. Резервные копии критически важны для восстановления при полной потере кворума или повреждении данных на диске.

## Практические сценарии
При добавлении нового узла в большой кластер лидер должен передать ему огромный объем данных (снапшот). Если добавить узел сразу как голосующий:
1. Кворум увеличивается на 1.
2. Если новый узел медленно синхронизируется или настроен неверно, кластер становится более уязвимым к отказу еще одного узла.

**Best Practice (etcd 3.4+):** Сначала добавить узел как `learner`, дождаться полной синхронизации и только затем повысить его до голосующего участника.

## Практические сценарии

### Развертывание нового кластера (Bootstrap)

Пример конфигурации первого узла (`node1`) в новом кластере из 3-х нод:

```bash
etcd --name node1 \
  --initial-advertise-peer-urls https://10.0.1.10:2380 \
  --listen-peer-urls https://10.0.1.10:2380 \
  --listen-client-urls https://10.0.1.10:2379,https://127.0.0.1:2379 \
  --advertise-client-urls https://10.0.1.10:2379 \
  --initial-cluster node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380,node3=https://10.0.1.12:2380 \
  --initial-cluster-token my-etcd-token \
  --initial-cluster-state new
```

### Безопасное добавление узла (через Learner)

1. **Добавить узел в кластер как learner:**
   ```bash
   etcdctl member add node4 --peer-urls=https://10.0.1.13:2380 --learner
   ```

2. **Запустить etcd на новом узле** с флагом `--initial-cluster-state existing`.

3. **Проверить синхронизацию:**
   Сравните `RAFT INDEX` и `RAFT APPLIED INDEX` нового узла с лидером:
   ```bash
   etcdctl endpoint status --cluster -w table
   ```

4. **Повысить узел до голосующего:**
   ```bash
   etcdctl member promote <MEMBER_ID>
   ```

### Аварийное восстановление (Disaster Recovery)

Если более половины узлов потеряны (кворум невозможен), необходимо создать новый кластер на базе последнего живого снапшота.

1. **Снять снапшот** (если есть доступ хотя бы к одному узлу):
   ```bash
   etcdctl snapshot save backup.db
   ```

2. **Восстановить данные** (выполняется на каждом будущем узле кластера):
   ```bash
   # Используйте etcdutl в версии 3.6+
   etcdutl snapshot restore backup.db \
     --name node1 \
     --initial-cluster node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380,node3=https://10.0.1.12:2380 \
     --initial-cluster-token new-token \
     --initial-advertise-peer-urls https://10.0.1.10:2380 \
     --data-dir /var/lib/etcd-restored
   ```

3. **Запустить etcd** на всех узлах, используя новую директорию данных (`/var/lib/etcd-restored`).

## Дополнительная информация

### Обслуживание и мониторинг

* **Удаление узла:** Перед физическим выключением узла всегда удаляйте его из кластера программно (`etcdctl member remove <ID>`), чтобы корректно уменьшить размер кворума.
* **Замена узла:** Рекомендуется сначала добавить новый узел, а затем удалить старый.
* **Обновление версий:** При обновлении с 3.5 на 3.6 убедитесь, что версия 3.5 обновлена до последнего патча (3.5.26+), чтобы избежать проблем с синхронизацией членства в кластере.
