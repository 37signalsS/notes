# Кластеризация и восстановление etcd

Кластеризация обеспечивает высокую доступность и отказоустойчивость хранилища за счет репликации данных и автоматического выбора лидера через алгоритм Raft.

## Определения

| Термин | Описание |
| :--- | :--- |
| **Кластер etcd** | Группа узлов, работающих совместно для обеспечения согласованности данных через [алгоритм Raft](./raft_consensus.md). |
| **Кворум (Quorum)** | Минимальное количество голосующих узлов для принятия решений. Рассчитывается как `(n/2) + 1`. |
| **Learner (v3.4+)** | Неголосующий участник кластера. Получает данные от лидера, но не влияет на кворум. Используется для безопасного расширения кластера. |
| **Pre-Candidate (v3.5+)** | Состояние узла перед выборами. Проверяет доступность кворума, не увеличивая `Term`, что предотвращает "дребезг" лидера при сетевых миганиях. |
| **Member** | Узел кластера с уникальным `id` и набором `peer URLs`. |
| **Peer URL** | Адрес, по которому узел взаимодействует с другими участниками кластера (Raft gossip, передача снапшотов). |
| **Client URL** | Адрес, по которому клиенты (etcdctl, kube-apiserver) подключаются для операций чтения/записи. |
| **Initial Cluster** | Полный список `name=peer URL` для первичной инициализации или восстановления кластера. |
| **Cluster Token** | Идентификатор кластера, предотвращающий случайное слияние кластеров при восстановлении из общего снапшота. |
| **Term** | Номер эпохи в Raft. Увеличивается при каждой выборке лидера. |
| **Log Index / Commit Index / Applied Index** | Индексы в Raft-логе: последний записанный, подтвержденный кворумом, примененный к состоянию машины. |
| **Снапшот (Snapshot)** | Полный снимок состояния базы данных на конкретную ревизию. Требуется для аварийного восстановления и предотвращения бесконечного роста WAL. |
| **Split-Brain** | Ситуация разделения сети. В etcd "классический" split-brain (двое пишущих лидеров) невозможен благодаря Raft, однако возможна потеря кворума. |
| **Multi-AZ** | Стратегия развертывания узлов в разных зонах доступности для защиты от катастрофических сбоев дата-центра. |
| **WAL (Write-Ahead Log)** | Журнал предзаписи. Гарантирует сохранность операций при сбое питания узла. |

## Основные концепции

### Топология и кворум

etcd требует нечетного количества узлов (3, 5, 7) для максимизации отказоустойчивости. Использование четного количества узлов (например, 4) не повышает устойчивость к сбоям по сравнению с меньшим нечетным числом (3), но увеличивает накладные расходы на сеть.

| Узлов | Кворум | Допустимый отказ | Сценарий применения |
| :--- | :--- | :--- | :--- |
| 1 | 1 | 0 | Тестирование, малые кластеры (Edge). |
| 3 | 2 | 1 | Стандарт для малых и средних кластеров. |
| 5 | 3 | 2 | **Production baseline (2026)**. Устойчивость к потере AZ + 1 узла. |
| 7 | 4 | 3 | Очень крупные кластеры с высокими требованиями к HA. |

### Сетевые задержки и RTT

Производительность Raft напрямую зависит от задержек между узлами.
* **Норма**: Peer RTT < 50 мс.
* **Критично**: Peer RTT > 100 мс (может вызывать частые перевыборы).
* **Multi-AZ**: При размещении в разных зонах убедитесь, что `heartbeat-interval` сопоставим с RTT, а `election-timeout` минимум в 10 раз больше.

### Raft Log Replication

При записи клиент отправляет запрос на лидер. Лидер записывает запись в локальный WAL, рассылает `AppendEntries` по всем узлам кластера и ждет подтверждения от кворума. После получения подтверждения от большинства запись фиксируется (committed) и применяется к состоянию машины (applied). Ответ клиенту отправляется только после фиксации. Этот механизм гарантирует, что запись не будет потеряна при сбое отдельного узла.

Важно: запись не возвращает успех клиенту, пока не получит подтверждение от большинства узлов. Поэтому при высокой задержке между узлами latency записи растет пропорционально round-trip времени до самого медленного узла в кворуме.

### Snapshotting и WAL

etcd периодически создает фоновые снапшоты для предотвращения бесконечного роста WAL. По умолчанию снапшот создается, когда в WAL накапливается более 10 000 записей. При создании снапшота лидер отправляет его отставшим узлам, после чего старые записи WAL удаляются. Снапшот не блокирует读写 операции. При восстановлении из снапшота данные загружаются в BoltDB, а WAL применяется только за снапшот.

### Learner lifecycle

1. Узел добавляется через `etcdctl member add --learner`. Он не имеет права голоса и не может стать лидером.
2. Лидер передает новому узлу снапшот и последующие записи лога.
3. Узел синхронизируется, его `RAFT INDEX` стремится к значению лидера.
4. При разнице в индексах менее порога (по умолчанию 1000) узел может быть повышен до голосующего участника через `etcdctl member promote`.
5. В etcd 3.5+ проверка готовности выполняется автоматически: промоут отклоняется, если отставание превышает порог.

### Pre-Candidate (v3.5+)

Перед началом полноценных выборов узел переходит в состояние Pre-Candidate и отправляет `RequestVote` без увеличения `Term`. Если активный лидер отвечает, выборы отменяются. Это предотвращает "дребезг" лидера при кратковременных сетевых сбоях, когда узел временно теряет связь с большинством.

### Реальность "Split-Brain"

В etcd невозможен сценарий, когда две изолированные части кластера одновременно принимают записи (Linearizability). Однако при разделении сети:
1. **Меньшинство (Minority)**: Переходит в состояние поиска лидера и блокирует операции записи.
2. **Большинство (Majority)**: Продолжает работу, если в нем остался лидер или он может быть выбран.

**Важно**: кластер из 2 узлов (n=2) имеет кворум 2. При потере одного узла второй не может набрать кворум, и кластер останавливается. Поэтому 2 узла непригодны для production.

### Сеть, порты и TLS

* **Client port 2379**: используется клиентами (etcdctl, kube-apiserver) для读写.
* **Peer port 2380**: используется для Raft gossip и передачи снапшотов между узлами.
* Включение peer TLS обязательно для production. Отсутствие шифрования peer-соединений в дата-центре exposes sensitive data (snapshots, Raft log) на сетевом уровне.

## Стратегии обеспечения высокой доступности (HA)

### 1. Multi-AZ топология (2-2-1 или 1-1-1)

Для защиты от отказа целого дата-центра узлы распределяются по зонам доступности.
- **3 узла (1-1-1)**: Позволяет пережить отказ **одной зоны**.
- **5 узлов (2-2-1)**: Рекомендуемый паттерн. Позволяет пережить отказ **одной зоны** и **одного дополнительного узла** во второй зоне.

### 2. Внешний кластер (External etcd)

Вынос etcd за пределы Control Plane узлов Kubernetes.
- **Плюсы**: Изоляция от ресурсов API-сервера, независимое масштабирование, упрощенное восстановление.
- **Минусы**: Требует управления отдельной инфраструктурой и TLS.
- **Рекомендация**: Для production сред из 5+ Control Plane узлов используйте внешний etcd-кластер из 3 или 5 узлов.

### 3. Автоматизация резервного копирования

Снапшот — единственный способ восстановления при полной потере кворума.
- **Периодичность**: Минимум раз в час.
- **Хранение**: Обязательная копия вне текущего региона/облака (S3, удаленный сервер).
- **Инструменты**: `etcd-backup-operator` или системный `CronJob` с использованием `etcdctl snapshot save`.
- **Валидация**: После каждого снапшота выполняйте `etcdutl snapshot status`, чтобы убедиться в его целостности.

## Практические сценарии

### Безопасное добавление узла (через Learner)

При добавлении нового узла в большой кластер лидер должен передать ему снапшот. Если добавить узел сразу как голосующий, кворум увеличится мгновенно, и если новый узел медленно синхронизируется, кластер станет уязвимым к отказу еще одного участника.

```bash
# 1. Добавить узел как learner на текущем лидере
etcdctl member add node4 --peer-urls=https://10.0.1.13:2380 --learner

# 2. Запустить etcd на новом узле с флагом --initial-cluster-state existing
etcd \
  --name node4 \
  --initial-cluster-state existing \
  --initial-cluster "node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380,node3=https://10.0.1.12:2380,node4=https://10.0.1.13:2380" \
  --peer-urls https://10.0.1.13:2380 \
  --data-dir /var/lib/etcd

# 3. Проверить синхронизацию: RAFT INDEX нового узла должен стремиться к лидеру
etcdctl endpoint status --cluster -w table

# 4. Повысить до голосующего (требуется v3.5+ для автоматической проверки готовности)
etcdctl member promote 8e9e05f54f240d12

# 5. Валидация: убедиться, что новый узел участвует в выборах
etcdctl member list
```

**Валидация**: `etcdctl endpoint health --cluster -w table` показывает `true` для всех узлов. Разница в `RAFT INDEX` между лидером и новым узлом < 1000.

**Edge Cases**:
- Если `member promote` возвращает ошибку `learner is not synced`, увеличьте `--snapshot-count` или проверьте сетевые задержки.
- При потере связи с learner во время синхронизации удалите его через `etcdctl member remove`, если он не был промоутирован.

### Замена узла (Rolling Upgrade / Node Replacement)

```bash
# 1. Добавить новый узел как learner
etcdctl member add node5 --peer-urls=https://10.0.1.14:2380 --learner

# 2. На новом узле запустить etcd с --initial-cluster-state existing
etcd \
  --name node5 \
  --initial-cluster-state existing \
  --initial-cluster "node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380,node3=https://10.0.1.12:2380,node4=https://10.0.1.13:2380,node5=https://10.0.1.14:2380" \
  --peer-urls https://10.0.1.14:2380 \
  --data-dir /var/lib/etcd

# 3. Дождаться синхронизации и промоутить
etcdctl endpoint status --cluster -w table
etcdctl member promote <NODE5_ID>

# 4. Убедиться, что кворум сохранен (5 узлов → кворум 3)
etcdctl member list

# 5. Удалить старый узел (не лидера!)
etcdctl member remove <OLD_NODE_ID>
```

**Валидация**: после удаления старого узла количество голосующих членов уменьшается, но кворум остается достижимым. Проверьте `etcdctl endpoint health`.

**Best Practice**: Никогда не удаляйте узел, если он является лидером, без предварительной передачи лидерства (`move-leader`).

### Передача лидерства (Transfer Leader)

```bash
# Посмотреть текущего лидера
etcdctl endpoint status --cluster -w table

# Передать лидерство на узел node3
etcdctl move-leader node3

# Валидация: проверить, что leader изменился
etcdctl endpoint status --cluster -w table
```

**Edge Cases**: Если целевой узел отстает по `RAFT INDEX`, `move-leader` может завершиться ошибкой. В этом случае используйте `etcdctl member promote` для сначала повышения узла, или дождитесь синхронизации.

### Проверка здоровья и кворума

```bash
# Проверить здоровье всех узлов
etcdctl endpoint health --cluster -w table
# → +----------------+--------+-------+-------+
# → |    ENDPOINT    | HEALTH |  TOOK | ERROR |
# → +----------------+--------+-------+-------+
# → | 10.0.1.10:2379 |  true  | 2.1ms |       |
# → | 10.0.1.11:2379 |  true  | 1.8ms |       |
# → | 10.0.1.12:2379 |  true  | 2.3ms |       |
# → +----------------+--------+-------+-------+

# Детальный статус каждого участника
etcdctl endpoint status --cluster -w table
# → ID, VERSION, DB SIZE, LEADER ID, RAFT INDEX, RAFT TERM

# Список членов кластера
etcdctl member list
```

**Валидация**: количество healthy узлов >= кворума. `LEADER ID` совпадает у большинства узлов. Разница в `RAFT INDEX` между лидером и отставшими узлами минимальна.

**Troubleshooting**:
- Если узел показан `false` или `error`: проверьте сетевую доступность порта 2379, TLS-сертификаты и статус службы etcd (`systemctl status etcd`).

### Graceful Removal

```bash
# 1. Убедиться, что узел не является лидером
etcdctl endpoint status --cluster -w table

# 2. Если узел — лидер, передать лидерство
etcdctl move-leader <OTHER_MEMBER_ID>

# 3. Удалить узел из кластера
etcdctl member remove <MEMBER_ID>

# 4. На удаляемом узле остановить etcd
systemctl stop etcd
```

**Валидация**: `etcdctl member list` больше не содержит удаленного узла. Кворум остается достижимым.

### Диагностика отставания Learner

```bash
# Сравнить RAFT INDEX learner с лидером
etcdctl endpoint status --cluster -w table

# Разница > 1000: проверить сетевые задержки, TLS handshake time, iowait
# Проверить alarms на learner
etcdctl --endpoints=https://10.0.1.14:2379 alarm list
```

**Решение**: Увеличьте `--snapshot-count` на лидере, проверьте пропускную способность сети между зонами, убедитесь, что learner имеет достаточные ресурсы CPU/Disk.

### Обнаружение и обработка NOSPACE Alarm

```bash
# 1. Проверить alarms
etcdctl alarm list
# → memberID: 1234567890abcdef, alarm: NOSPACE

# 2. Освободить место на диске (удалить старые снапшоты, логи)
# 3. Выполнить дефрагментацию на каждом узле (по очереди)
etcdctl defrag --cluster=true
# 4. Disarm alarm
etcdctl alarm disarm NOSPACE
```

**Важно**: `alarm disarm` без предварительного освобождения места может привести к немедленному возврату alarms. `defrag` освобождает неиспользуемые страницы в BoltDB, но блокирует операции на время выполнения (обычно несколько секунд). Выполняйте дефрагментацию последовательно, узел за узлом.

## Аварийное восстановление (Disaster Recovery)

Если большинство узлов потеряны (кворум невозможен), кластер "умирает". Требуется создание нового кластера из снапшота.

```bash
# 1. Изоляция (Cluster Fencing): убедиться, что старые узлы выключены или физически изолированы
# 2. Проверить снапшот перед восстановлением
etcdutl snapshot status backup.db
# → hash: 1234567890abcdef, revision: 48291, total key: 12500, size: 12.5 MB

# 3. Восстановление (Offline) на каждом узле будущего кластера
etcdutl snapshot restore backup.db \
  --name node1 \
  --initial-cluster node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380,node3=https://10.0.1.12:2380 \
  --initial-cluster-token new-cluster-token \
  --data-dir /var/lib/etcd-restored

# 4. Запустить etcd с восстановленной директорией
etcd \
  --name node1 \
  --initial-cluster-state new \
  --data-dir /var/lib/etcd-restored \
  --peer-urls https://10.0.1.10:2380

# 5. В Kubernetes: обновить hostPath в манифесте Static Pod на /var/lib/etcd-restored
```

**Валидация**:
- `etcdctl endpoint health --cluster -w table` показывает все узлы healthy.
- `etcdctl get --prefix --keys-only` возвращает ожидаемые ключи.
- `etcdctl alarm list` пустой.

**Troubleshooting**:
- Ошибка `mvcc: required revision has been compacted`: восстановите более свежий снапшот.
- Ошибка `data-dir already exists`: удалите или используйте новую директорию.
- Ошибка TLS: убедитесь, что сертификаты с SAN/CN соответствуют новому `--name` и `--peer-urls`.

## Поведение при недоступности etcd

**Если etcd становится недоступным на несколько минут:**

1. **API-сервер** переходит в read-only режим или становится полностью недоступным — не может читать/писать состояние кластера.
2. **Существующие Podы продолжают работать** — они уже запущены и не зависят от etcd для текущей работы.
3. **Планирование новых подов прекращается** — scheduler не может получить информацию о ресурсах узлов.
4. **Контроллеры перестают работать** — не могут сравнить желаемое и фактическое состояние.
5. **Обновления и удаления Podов не применяются** — изменения в API не сохраняются.

**После восстановления etcd:**
- Все изменения, произошедшие во время недоступности, **будут обработаны**.
- Контроллеры получают обновления через Watch-механизм и начинают сверку (reconciliation).
- Если Pod был удален из API, но kubelet не получил уведомление — kubelet получит обновление при переподключении и удалит Pod.
- **Исключение:** если Pod был удален физически (например, узел перезагрузился), а etcd был недоступен — kubelet не сможет подтвердить удаление, и Pod может остаться в API как "orphaned".

**Важно:** etcd хранит состояние, а не события. При восстановлении контроллеры видят текущее состояние и приводят его к желаемому. Потери событий нет — есть задержка в обработке.

## Восстановление после коррупции данных

```bash
# 1. Проверить целостность снапшота
etcdutl snapshot status backup.db

# 2. Проверить целостность WAL на проблемном узле
etcdutl wal verify --data-dir /var/lib/etcd

# 3. Если WAL поврежден, восстановиться из последнего валидного снапшота
etcdutl snapshot restore last-good-backup.db \
  --name node1 \
  --initial-cluster node1=https://10.0.1.10:2380,node2=https://10.0.1.11:2380 \
  --data-dir /var/lib/etcd-restored

# 4. Запустить кластер и проверить данные
etcdctl get --prefix --keys-only | wc -l
```

**Edge Cases**:
- Если коррупция произошла на части узлов, а кворум еще жив, можно выполнить логическое резервное копирование (`etcdctl get --prefix --keys-only > all_keys.json`) с живого узла, а затем импортировать данные после восстановления кластера из снапшота.

## Дополнительная информация

### Безопасность и соответствие (2026)

* **Encryption at Rest**: Согласно стандартам безопасности 2026 (GDPR/PCI-DSS), данные etcd должны быть зашифрованы на диске. Используйте KMS-провайдеры (Vault, AWS KMS) для управления ключами.
* **Restore Drills**: Наличие бэкапа не гарантирует восстановление. Рекомендуется проводить ежеквартальные учения по восстановлению кластера в изолированной среде.
* **Peer TLS**: Обязательно включите шифрование peer-соединений. Нешифрованный трафик между узлами exposes WAL и снапшоты.

### Обслуживание

* **Замена узла**: Всегда сначала добавляйте новый узел (через learner), а затем удаляйте старый. Это поддерживает стабильность кворума.
* **Обновление**: При переходе на v3.7 убедитесь в полном отсутствии v2-данных. v3.7 окончательно удаляет поддержку v2 store.
* **Defragmentation**: После массового удаления ключей или расширения кластера выполняйте `etcdctl defrag --cluster=true` для возврата неиспользуемой страниц операционной системе.

### Troubleshooting

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `member already exists` | ID или peer URL конфликтуют с существующим членом | Проверьте `etcdctl member list`, используйте уникальный `--name` и peer URL |
| `learner is not synced` | Learner отстает по RAFT INDEX | Проверьте сеть, iowait, увеличьте `--snapshot-count`, дождитесь синхронизации |
| `no such member` при `remove`/`promote` | Неверный MEMBER ID | Получите ID через `etcdctl member list` |
| `required revision has been compacted` | Снапшот устарел, ревизия удалена компакцией | Используйте более свежий снапшот, убедитесь, что `etcdctl snapshot save` создается до компакции |
| `mvcc: database space exceeded` (NOSPACE) | Диск заполнен, BoltDB не может выделить страницу | Освободите место, выполните `etcdctl defrag --cluster=true`, disarm alarm |
| `connection refused` на 2380 | Фаерволл блокирует peer port, или etcd не слушает | Проверьте `ss -tlnp | grep 2380`, правила фаерволла, конфиг `--listen-peer-urls` |
| TLS handshake failure | Неверный сертификат, CN/SAN, срок действия | Проверьте `openssl s_client -connect host:2380`, сроки сертификатов, соответствие `--name` CN |
| Лидер переизбирается каждые несколько секунд | Высокий Peer RTT, проблемы с сетью или disk I/O | Убедитесь, что Peer RTT < 50 мс, проверьте iowait (`iostat`), настройте `heartbeat-interval` и `election-timeout` |

### Best Practices

* **Размер кластера**: используйте 3 или 5 узлов. 7 узлов оправданы только при экстремальных требованиях к HA и низких задержках.
* **Learner для всех изменений**: в production добавляйте все новые узлы через `--learner` и промоутите только после проверки `RAFT INDEX`.
* **Сеть**: размещайте узлы в одной региона с RTT < 50 мс. Для Multi-AZ настройте `heartbeat-interval` с запасом на меж-AZ задержки.
* **TLS**: включите peer и client TLS. Используйте автоматическое обновление сертификатов (e.g., `cert-manager` с `etcd-certificates`).
* **Резервное копирование**: сочетайте периодические снапшоты (`etcdctl snapshot save`) с логическим бэкапом (`etcdctl get --prefix --keys-only`) для критичных ключей.
* **Восстановление**: проводите restore drills минимум раз в квартал. Время восстановления (RTO) должно быть задокументировано.
* **Мониторинг**: отслеживайте `etcd_server_has_leader`, `etcd_server_leader_changes_seen_total`, `etcd_server_proposal_failed_total`, `etcd_server_heartbeat_send_failures_total`, `etcd_server_compact_index_gap`.

### Edge Cases

* **Восстановление на другую архитектуру**: снапшоты etcd несовместимы между архитектурами (amd64 → arm64). Для миграции используйте логическое резервное копирование через `etcdctl get` или промежуточный etcd-кластер.
* **2 узла**: не используйте в production. При потере одного узла второй не набирает кворум (2/2), и кластер полностью останавливается.
* **Четное количество узлов**: 4 или 6 узлов не повышают отказоустойчивость по сравнению с меньшим нечетным числом, но увеличивают риск split-brain (равный раскол 3-3 без кворума) и накладные расходы на репликацию.
* **Снапшот версии**: снапшот можно восстановить на версию etcd >= версии создания. Для downgrade используйте промежуточный кластер с последующей логической миграцией данных.
* **Learner во время обновления**: при rolling upgrade добавляйте новую версию как learner, промоутите, затем удалите старую версию. Это исключает потерю кворума.
