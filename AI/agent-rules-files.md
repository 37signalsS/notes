# Файлы инструкций агента (AGENTS.md, CLAUDE.md, GEMINI.md)

**Актуально для:** Codex CLI 0.160.x / Claude Code 2.1.x / Gemini CLI

Механика того, как агентный инструмент находит и объединяет проектные инструкции.
Практики работы с этими файлами — как накапливать правила, где их размещать, как проверять,
что они действительно загрузились — вынесены в
**[Инженерные практики работы с ИИ](./ai-engineering-practices.md)**.

## Определения

**Файл инструкций проекта** (project instruction file) — текстовый файл в репозитории, который
агент читает при старте сессии, до начала работы. Содержит команды сборки и проверок, структуру
репозитория, архитектурные соглашения и правила завершения задачи. Живёт под контролем версий,
поэтому инструкции действуют для всей команды и для всех агентов, а не только для того, кто их написал.

**Глобальный файл инструкций** — личный файл пользователя (вне репозитория), который действует
для всех проектов. Место для стиля общения, личных предпочтений и личных ярлыков инструментов,
которые не должны попадать в репозиторий.

**Харнесс (harness)** — неформальный термин, обозначающий весь комплект оснастки вокруг модели:
файлы инструкций, навыки, хуки, субагенты, MCP-серверы, режимы песочницы. Никакой отдельной
сущности за словом нет — это всё то, что описано в этом репозитории по отдельности
(см. [ИИ-агенты](./ai-agents.md) и [Методология AI-First разработки](./ai-first-development.md)).
Термин полезен тем, что позволяет мыслить уровнями: «не хватает харнеса» означает не «нужен
какой-то новый продукт», а «какая-то часть оснастки не настроена».

**Файл переопределения** (override) — второе имя того же файла в том же каталоге, которое
имеет приоритет над основным. Позволяет оставить в репозитории командные соглашения, а локально
переопределить их под свою машину или ветку работы.

## Базовые концепции

### 1. Зачем нужны файлы инструкций

Инструкции в репозитории переживают сессию: это единственное место, где зафиксировано то, что
иначе пришлось бы объяснять заново в каждом промпте. Три практических следствия:

- **Правило пишется один раз и применяется ко всем.** Агент узнаёт его до начала работы, а не
  после того, как сделал не то.
- **Правила едут вместе с кодом.** Смена сопровождающего в команде не обнуляет договорённости:
  он закоммичен и виден в ревью diff'а правил так же, как код.
- **Агент может расширять инструкции сам.** Официальная рекомендация Codex — фиксировать повторяющиеся
  замечания на ревью и велить агенту обновлять `AGENTS.md` при каждой вашей правке, чтобы
  последующие сессии наследовали исправление. У Claude Code для того же есть auto memory:
  агент сам накапливает выводы о сборке, отладке и предпочтениях и складывает их в
  `MEMORY.md` с тематическими файлами.

### 2. Соглашение об именовании

Разные инструменты — разные имена при одном и том же назначении:

| Инструмент | Файл проекта | Глобальный файл | Каталог навыков |
|---|---|---|---|
| Codex | `AGENTS.md` | `~/.codex/AGENTS.md` | `.agents/skills` (репозиторий), `$HOME/.agents/skills` (личный) |
| Claude Code | `CLAUDE.md` (или `./.claude/CLAUDE.md`) | `~/.claude/CLAUDE.md` | `.claude/skills` |
| Gemini CLI | `GEMINI.md` | `~/.gemini/GEMINI.md` | — |

Имя не защищено стандартом: Codex поддерживает список запасных имён
(`project_doc_fallback_filenames`), поэтому репозиторий с `TEAM_GUIDE.md` или `.agents.md`
подключается к Codex без переименования. Для Gemini CLI и `.gemini/GEMINI.md` как файл с
повышенным приоритетом см. [Google Gemini CLI](./gemini_cli.md).

### 3. Обнаружение и объединение в Codex

Порядок зафиксирован в исходном коде (`codex-rs/core/src/project_doc.rs`,
`codex-rs/core/src/agents_md.rs`) и в официальном руководстве:

1. **Глобальный уровень.** В каталоге Codex (`~/.codex`, либо `CODEX_HOME`) читается
   `AGENTS.override.md`, если он есть, иначе `AGENTS.md`. Берётся только первый непустой файл.
2. **Уровень проекта.** От корня проекта вниз до текущего рабочего каталога. Корень определяется
   подъёмом вверх до первого маркера из `project_root_markers` (по умолчанию `.git`); если маркер
   не найден, проверяется только текущий каталог. В каждом каталоге берётся **не более одного**
   файла в порядке `AGENTS.override.md` → `AGENTS.md` → запасные имена.
3. **Объединение.** Файлы конкатенируются от корня вниз и соединяются пустыми строками. Файл,
   ближайший к рабочему каталогу, читается последним и потому оказывается в более выгодной
   позиции, но **не переопределяет** вышестоящий — правила складываются.
4. **Лимит.** Пустые файлы пропускаются; добавление прекращается, когда суммарный объём
   достигает `project_doc_max_bytes` — по умолчанию 32 KiB.
5. **Границы обхода.** Выше корня проекта не поднимаемся. Ниже текущего рабочего каталога
   тоже не спускаемся: вложенный `AGENTS.md` попадёт в контекст, только если сессия стартовала
   внутри этого поддерева.

Пункт 5 — главная практическая ловушка в монорепозиториях. Формально стандарт рекомендует
вложенные `AGENTS.md` («Agents automatically read the nearest file in the directory tree»), но
текущая реализация Codex читает их только при старте из поддерева или при явном `--cd`. Способы
обойти:

- запускать агента из корня общего пакета, а не из корня монорепозитория;
- указать в корневом файле инструкцию вида «перед изменением файлов в `services/payments/`
  сначала прочитай `services/payments/AGENTS.md`» — работает, но требует поддерживать корневой
  файл в синхроне с деревом;
- поднять `project_doc_max_bytes` и разложить инструкции по вложенным каталогам вместо того,
  чтобы раздувать корневой файл.

### 4. Обнаружение и объединение в Claude Code

1. **При старте** читаются `CLAUDE.md` и `CLAUDE.local.md` из каждого каталога на пути от корня
   файловой системы вниз до рабочего каталога. Эти файлы загружаются **полностью**, независимо
   от длины.
2. **По требованию** подгружаются файлы из подкаталогов ниже рабочего: они попадают в контекст
   тогда, когда агент читает файлы в этом поддереве. Из-за этого правила поддерева иногда
   «не срабатывают» — агент ещё не заходил туда.
3. **Объединение.** Файлы конкатенируются, а не переопределяют друг друга, в порядке от корня
   к рабочему каталогу; ближайшие читаются последними. Внутри каталога `CLAUDE.local.md`
   дописывается после `CLAUDE.md`, то есть личные заметки — последнее, что прочитает агент.
4. **Исключения и добавление каталогов.** `claudeMdExcludes` исключает файлы по пути или маске;
   для каталогов вне рабочего (`--add-dir`) файлы инструкций по умолчанию не загружаются —
   это меняется переменной `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD`.
5. **Правила по маскам путей.** В `.claude/rules/` лежат файлы с полем `paths:` — инструкция
   подключается, когда агент работает с файлом подходящим глобом. Альтернатива файлам
   в подкаталогах: все соглашения в одном месте, применимость — по маске.
6. **Комментарии.** Блочные HTML-комментарии вырезаются до попадания в контекст
   (комментарии внутри блоков кода сохраняются). Это бесплатный способ оставлять заметки
   для человека, не расходуя токены агента.
7. **Auto memory.** Агент сам пишет заметки в `~/.claude/projects/<путь-к-репозиторию>/memory/`:
   `MEMORY.md` — индекс, тематические файлы (`debugging.md`, `patterns.md`) читаются по
   требованию. В сессию загружаются первые 200 строк или 25 KB `MEMORY.md` — что наступит раньше.
   Хранилище локально для машины: все worktree и подкаталоги одного репозитория его разделяют,
   но в git оно не попадает.

Официальная рекомендация по размеру — держаться примерно 200 строк: более длинные файлы
загружаются целиком, но соблюдение инструкций падает.

### 5. Проверка: какие файлы реально загрузились

Оба инструмента умеют отчитаться о собранных инструкциях — это обязательный шаг валидации,
а не отладочная роскошь.

```bash
# Codex: из корня репозитория — ждём перечисление инструкций по порядку приоритета
codex --ask-for-approval never "Summarize the current instructions."

# Codex: из подкаталога — проверяем, что вложенный файл действительно подхватился
codex --cd services/payments --ask-for-approval never "Show which instruction files are active."
```

Ожидаемый порядок: глобальный файл, затем файл корня репозитория, затем самый глубокий
(в последнюю очередь). В интерактивной сессии Claude Code тот же список показывает команда
`/context` (раздел Memory files), а `/memory` перечисляет все места инструкций — и создаёт
отсутствующий файл, если его нет.

Если в списке окажется не тот файл, инструкции будут неверными при полном их наличии: см.
раздел «Устранение неполадок».

### 6. Размещение правил по директориям

| Подход | Где лежит | Когда подключается | Когда применять |
|---|---|---|---|
| Файл в подкаталоге | Рядом с кодом, версионируется вместе с ним | При старте из этого каталога или по требованию — при чтении файлов внутри | Поддерево владеет своими соглашениями |
| Правило по маске пути | Центральный `.claude/rules/*.md` с `paths:` | Когда агент работает с файлом под маску | Одно соглашение разбросано по многим путям |

Корень задаёт общее для репозитория, подкаталоги — локальное. Разделение работает, пока
правила не начинают противоречить друг другу: при конкатенации побеждает не «правильное»
правило, а последнее прочитанное, поэтому расхождения устраняются явно, а не «кто последний
записан».

Что выносить из корневого файла: команды, которые агент запускает чаще всего; критерии
завершённости задачи; архитектурные инварианты, действующие везде. Что выносить в навыки:
процедуры, нужные для отдельного класса задач, — они не должны занимать контекст каждой сессии.

### 7. Практика: правила накапливаются из замечаний

Рабочий порядок, который даёт результат быстрее, чем предварительное проектирование правил:

1. **Начать пусто.** Файл создаётся как заготовка; пытаться заранее описать все правила —
   потеря времени: вы ещё не знаете, какие решения принимает проект на практике.
2. **Работать без оглядки на перфекционизм.** Замечание в чате («не трогай соседние сервисы»,
   «используй наш helper, а не стандартную библиотеку») исправляет текущий дифф.
3. **В конце сессии зафиксировать.** Попросить агента по этой сессии сформулировать правила из
   всех внесённых правок и записать их в файл инструкций:

   ```text
   По этой сессии сформулируй правила из всех правок, которые я тебе давал,
   и добавь их в файл инструкций проекта. Правило должно быть инструкцией
   в одно предложение, без описания того случая, из которого оно выросло.
   ```

4. **Положить правило как можно ближе к коду.** Правило про фронтенд — в файле фронтенда;
   корневой файл должен оставаться коротким, иначе он перестанет работать.
5. **Периодически вычищать.** Правила накапливаются, поэтому дубли и устаревшие записи
   появляются неизбежно: пройдитесь по файлу после каждой крупной вехи проекта.

Такой порядок даёт то, чего не даёт чтение статей: правило рождается из конкретной неудачи,
поэтому оно формулируется проверяемо. Правило, написанное заранее, чаще всего оказывается
пересказом идеи («пиши чисто»), которое ничем не отличается от просьбы «старайся».

### 8. Агент как фильтр внешних материалов

Существует обходной путь, снимающий необходимость разбирать каждую статью вручную: передать
материал агенту и получить не пересказ, а конкретные изменения.

```text
Вот документ с практиками работы агентов. Разбери его и выдели то, что применимо
к нашему проекту: какие пункты стоит внедрить, какие уже покрыты нашими правилами,
а какие относятся к задачам, которых у нас нет. По каждому пункту, который стоит внедрить,
сформулируй правило для нашего файла инструкций. Правки в файле не вноси — покажи их.
```

Ценность подхода не в экономии чтения, а в фильтре: он отсекает практики, рассчитанные на
другой масштаб или другой стек, и превращает документ в дифф, который можно обсудить.
Проверять всё равно нужно: агент склонен соглашаться с материалом, поэтому формулировка
«что из этого нам реально нужно» работает лучше, чем «что хорошего в этом документе».

## Практические сценарии

### Сценарий. Правила перестали действовать в подкаталоге

Симптом: правило из вложенного файла не применяется, агент продолжает нарушать его.

1. Выполнить проверку загрузки (§5) из корня и из подкаталога и сравнить списки файлов.
2. Если вложенный файл отсутствует при старте из корня — причина в границах обхода
   (Codex) либо в том, что агент ещё не читал файлы этого поддерева (Claude Code).
3. Быстрое решение — стартовать сессию в подкаталоге. Устойчивое — вынести правило в
   центральный файл с маской пути либо добавить в корневой файл инструкцию прочитать
   вложенный файл перед работой в этом поддереве.

### Сценарий. Инструкции обрезаны

Симптом: часть правил не применяется, объём вырос до десятков килобайт.

1. Проверить фактический объём объединённых инструкций (Codex обрезает по
   `project_doc_max_bytes`, Claude Code — по собственному бюджету контекста).
2. Поднять лимит (Codex) либо разложить инструкции по вложенным каталогам — второй путь
   предпочтителен, он попутно повышает точность попадания правил.
3. Проверить, не содержит ли корневой файл правил, которые никогда не срабатывают: они
   стоят контекста, но не дают эффекта.

## Устранение неполадок

| Симптом | Причина | Решение |
|---|---|---|
| Вложенный файл инструкций не действует | Обход ограничен текущим каталогом; поддерево ещё не читалось | Запускать сессию внутри поддерева либо вынести правило в корневой файл с маской пути |
| Применяются не те соглашения | В дереве есть файл переопределения выше по пути | Проверить список загруженных файлов, переименовать или удалить переопределение |
| Правила «не работают» в длинной сессии | Инструкции — мягкий слой; контекст замусорен | Вынести критичное в детерминированный слой (хуки, CI), см. [Инженерные практики работы с ИИ](./ai-engineering-practices.md) |
| Правила противоречат друг другу | Файлы конкатенируются, а не переопределяются | Развести по подкаталогам или устранить противоречие явно |
| Соблюдение падает по мере роста файла | Перегруженный контекст инструкций | Держать корневой файл коротким, детали выносить в навыки и правила по маскам |
| Личные правки попадают в командные файлы | Глобальный и проектный уровни не разделены | Личные предпочтения — в глобальный файл, командные — в репозиторий |
