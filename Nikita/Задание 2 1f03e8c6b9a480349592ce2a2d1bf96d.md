## **Шаг 2: Настроить SSH-доступ**

### **Для user1 — только по ключу:**

1. На клиентской машине (откуда будет логиниться user1) сгенерируйте SSH-ключ, если он не создан:

```
ssh-keygen -t rsa -b 4096
```

1. Скопируйте **публичный ключ** на сервер:

```
ssh-copy-id user1@<ip_сервера>
```

1. Отключите вход по паролю только для user1:
    
    Создайте файл настроек в SSH:
    

```
sudo nano /etc/ssh/sshd_config.d/user1.conf
```

1. Добавьте:

```
Match User user1
    PasswordAuthentication no
```

1. Затем перезапустите SSH:

```
sudo systemctl restart ssh
```

### **Для user2 — только по паролю:**

Убедитесь, что общий вход по паролю разрешен в:

```
sudo nano /etc/ssh/sshd_config
```

Параметр должен быть:

```
PasswordAuthentication yes
```

Перезапустите SSH:

```
sudo systemctl restart ssh
```

### **1. Что значит цифра `1` в выводе:**

```bash
-rw------- 1 user1 user1 5 May 12 14:59 secret.txt

```

Цифра `1` — это **количество жёстких ссылок** (hard links) на этот файл.

Обычно:

- У обычных файлов — `1`, если к нему нет других жёстких ссылок.
- У директорий — `2` и больше (одна для самой директории, одна — из родительской `..`, плюс по одной от каждой вложенной директории).

---

### **1. Жесткая ссылка (Hard Link)**

- **Что это:** ещё одно имя для **того же самого файла**.
- **Ссылается на:** **inode** (физическую запись файла на диске).
- **Работает только в пределах одного раздела.**
- **Файл удаляется только когда удалены все жесткие ссылки на него.**
- Обе ссылки **одинаково полноценны** — не различимы.

### **Пример:**

```
ln file1 hardlink
```

- file1 и hardlink — два разных имени **одного и того же файла** (один и тот же inode).
- Изменения в одном — видны в другом.
- Удаление одного не удалит файл, если осталась другая ссылка.

---

### **2. Мягкая ссылка (Symbolic Link, Soft Link)**

- **Что это:** отдельный файл, который содержит **путь к другому файлу**.
- **Ссылается на имя (путь) файла**, а не на его содержимое.
- Может указывать на файл **на другом разделе** или **вне файловой системы.**
- Если оригинальный файл удалён — **мягкая ссылка “ломается” (становится висячей).**

### **Пример:**

```
ln -s file1 symlink
```

- symlink — это “указатель” на file1.
- Изменения в file1 будут видны при доступе через symlink.
- Если удалить file1 — symlink останется, но будет битым (ls -l покажет ошибку No such file or directory).

---

### **🔍 Таблица сравнения:**

| **Характеристика** | **Жесткая ссылка** | **Мягкая ссылка** |
| --- | --- | --- |
| Тип | Второе имя файла | Отдельный файл |
| Ссылается на | inode (данные) | имя файла (путь) |
| Работает между разделами | Нет | Да |
| Ломается при удалении оригинала | Нет | Да |
| Удаляет файл при удалении? | Только если удалены все hard ссылки | Нет |
| Может ссылаться на директории | По умолчанию нет (только с флагами) | Да (с осторожностью) |

### **2. Разбор строки `/etc/passwd`**

```
daemon:x1:1:daemon:/usr/sbin:/usr/sbin/nologin
```

Это одна запись в файле `/etc/passwd`. Поля разделены `:`:

| Поле № | Значение | Описание |
| --- | --- | --- |
| 1 | `daemon` | Имя пользователя |
| 2 | `x` | Пароль (обычно `x`, означает, что пароль хранится в `/etc/shadow`) |
| 3 | `1` | UID (user ID) — уникальный идентификатор пользователя |
| 4 | `1` | GID (group ID) — идентификатор основной группы |
| 5 | `daemon` | Полное имя или комментарий |
| 6 | `/usr/sbin` | Домашняя директория (может быть фиктивной) |
| 7 | `/usr/sbin/nologin` | Shell входа — запрещает вход (используется для системных пользователей) |

### **4. Sticky bit / SetUID / SetGID**

**Sticky bit (`t`)**:

- Применяется к директориям (чаще всего `/tmp`).
- **Разрешает удалять файлы в каталоге только их владельцам**, даже если другие пользователи имеют права на запись в директорию.

```bash
chmod +t /some/dir
```

Признак: `drwxrwxrwt` (в конце `t`)

---

**SetUID (`s` для владельца):**

- Если установлен у **исполняемого файла**, процесс будет исполняться **от имени владельца файла**, а не запускающего пользователя.
- Часто используется в `passwd`, чтобы позволить обычным пользователям менять свой пароль.

```bash
chmod u+s file
```

Признак: `-rwsr-xr-x`

---

**SetGID (`s` для группы):**

- Если у файла: программа запускается с **правами группы файла**.
- Если у **директории**: файлы, созданные внутри, наследуют группу директории.

```bash
chmod g+s dir
```

Признак:

- Для файлов: `rwxr-sr-x`
- Для директорий: `drwxrwsr-x`

## **3. Key Exchange**

Цель этого этапа — безопасно согласовать параметры шифрования, создать общий секрет для шифрования и предотвратить MITM-атаки.

### **Подэтапы:**

1. **Обмен алгоритмами:**
    - Клиент и сервер обмениваются списками поддерживаемых алгоритмов:
        - Алгоритмы шифрования (AES, ChaCha20)
        - Алгоритмы MAC (HMAC-SHA2)
        - Алгоритмы сжатия
        - Алгоритмы ключевого обмена (например, ECDH, Curve25519)
        - Алгоритмы хост-ключей (RSA, ED25519 и др.)
2. **Выбор общих алгоритмов:**
    - Выбирается наиболее предпочтительный (первый в списке, который поддерживают обе стороны) для каждого типа.
3. **Диффи-Хеллман или ECDH:**
    - Клиент и сервер выполняют алгоритм ключевого обмена (например, ECDH), чтобы вычислить общий **секретный ключ (shared secret)**.
    - Этот ключ потом используется для симметричного шифрования.
4. **Аутентификация сервера:**
    - Сервер подписывает exchange своим приватным хост-ключом.
    - Клиент проверяет эту подпись, используя публичный хост-ключ сервера (если он известен или доверен).

## **4. Аутентификация клиента**

После установки зашифрованного канала происходит проверка личности клиента.

Возможны методы:

1. **Парольная аутентификация:**
    - Клиент отправляет зашифрованный пароль.
2. **Аутентификация по публичному ключу (наиболее распространённый и безопасный метод):**
    - Клиент предоставляет свой публичный ключ.
    - Сервер проверяет, есть ли он в ~/.ssh/authorized_keys.
    - Если да, сервер отправляет challenge.
    - Клиент подписывает его своим приватным ключом.
    - Сервер проверяет подпись.
3. **GSSAPI/Kerberos и др. (редко):**
    - Используются в корпоративных и доменных сетях.

## Обмен ключами

### **1. Клиент предлагает серверу свой публичный ключ**

Сервер проверяет: есть ли такой ключ у него в authorized_keys.

Если ключ найден, он:

- **Генерирует случайный challenge (данные)**
- **Шифрует их и отправляет клиенту** (точнее, формирует challenge, который клиент должен подписать)

### **2. Клиент подписывает challenge своим приватным ключом**

**Потому что только владелец приватного ключа может корректно подписать данные так, чтобы подпись была валидной при проверке с использованием соответствующего публичного ключа.**

Это работает благодаря **криптографии с открытым ключом (асимметричной)**:

- У клиента есть:
    - Приватный ключ: id_rsa, id_ed25519 (секрет)
    - Публичный ключ: id_rsa.pub (может быть на сервере)
- Подпись создаётся с помощью **приватного** ключа.
- Проверка подписи выполняется с помощью **публичного** ключа.

---

## **Зачем нужна подпись?**

Это позволяет серверу **удостовериться, что именно клиент владеет приватным ключом**, не передавая сам ключ и не раскрывая его.

Таким образом:

- Приватный ключ **никогда не передаётся по сети**.
- Сервер проверяет подпись — если она верна, значит клиент действительно знает приватный ключ.
- Это и есть аутентификация клиента.
