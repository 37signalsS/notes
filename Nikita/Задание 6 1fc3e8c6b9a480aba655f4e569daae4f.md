Узел-бастион — так называют специально отведенный компьютер в сети, обычно расположенный на внешней стороне демилитаризованной зоны организации. Такой узел полностью открыт для атак, так как он не защищен ни фаерволом ни фильтрующим маршрутизатором.

**Общая картина**

Представим два сервера:

- **Сервер A** (A): IP 10.0.0.1
- **Сервер B** (B): IP 10.0.0.2

---

## **1. Генерация ключей**

Каждый сервер генерирует пару ключей:

- **Приватный ключ** (private key) — хранится в секрете, используется для дешифрования и подписания.
- **Публичный ключ** (public key) — может быть передан другим участникам, используется для шифрования и верификации.

```
wg genkey | tee privatekey | wg pubkey > publickey
```

Каждый сервер сохраняет свой приватный ключ и передаёт свой публичный ключ другому участнику.

---

## **2. Настройка интерфейса**

Каждый сервер настраивает виртуальный интерфейс wg0, указывая:

- свой **приватный ключ**
- свой **виртуальный IP** (например, 10.0.0.x/24)
- публичный ключ и endpoint второго сервера

**Пример конфигурации для сервера A** (/etc/wireguard/wg0.conf):

```
[Interface]
PrivateKey = <A_private_key>
Address = 10.0.0.1/24
ListenPort = 51820

[Peer]
PublicKey = <B_public_key>
AllowedIPs = 10.0.0.2/32
Endpoint = <B_public_ip>:51820
PersistentKeepalive = 25
```

---

## **3. Аутентификация и обмен ключами**

WireGuard **не использует традиционный процесс обмена ключами (как в TLS/SSL)**. Вместо этого:

- Аутентификация основана на **предварительном обмене публичными ключами**.
- Обе стороны знают публичный ключ друг друга заранее.
- Приватные ключи **никогда не покидают** серверы.

WireGuard использует **протокол Noise** (конкретно: Noise_IK), который обеспечивает:

- Аутентификацию через публичные ключи
- Перфектную прямую секретность (Perfect Forward Secrecy) благодаря ephemeral ключам
- Минимальный поверхностный след (не требует handshake до попытки обмена)

---

## **4. Установление соединения**

### **1. Инициация:**

Когда сервер A хочет отправить пакет на сервер B:

- A формирует зашифрованный пакет с использованием публичного ключа B.
- Внутри используется временный ключ (ephemeral key) для обмена.

### **2. Ответ:**

Сервер B принимает пакет, расшифровывает его с помощью своего приватного ключа и отвечает.

### **3. Установка туннеля:**

После первого обмена пакеты шифруются и дешифруются в режиме **peer-to-peer** без необходимости посредников.

---

## **5. Типы шифрования**

WireGuard использует **современные и минималистичные криптографические примитивы**, включённые в **библиотеку CryptoBlake2s**:

| **Назначение** | **Алгоритм** |
| --- | --- |
| Ключевой обмен | Curve25519 |
| Аутентификация пакетов | Poly1305 |
| Шифрование | ChaCha20 |
| Хеш-функции | BLAKE2s |
| KDF (ключ. производная) | HKDF на основе BLAKE2s |

---

## **6. Безопасность и преимущества**

- **Статически малый код** — облегчает аудит безопасности.
- **Нет renegotiation и сессий как в TLS** — соединение всегда “просто работает”.
- **Быстрый роуминг и переброс через NAT** — полезно для DevOps и мобильных устройств.

---

## **WireGuard использует симметричное шифрование для шифрования трафика между пирами** после первоначальной аутентификации

1. **Асимметричное шифрование (Curve25519)** используется на этапе установления соединения (handshake):
    - Обмениваются ephemeral (временными) ключами.
    - Производится согласование общего симметричного ключа (через протокол Noise_IK и алгоритм **ECDH на Curve25519**).
    - Этот симметричный ключ **уникален для каждой сессии**.
2. **Симметричное шифрование (ChaCha20)** используется для **основного шифрования трафика** между пирами:
    - После завершения обмена ключами, весь пользовательский трафик (IP-пакеты) шифруется ChaCha20 с тем самым сессионным ключом.
    - Аутентификация производится **Poly1305**, прикреплённой к каждому пакету (MAC).

---

## **Почему так?**

- Асимметричное шифрование (ECDH/Curve25519) дорого по ресурсам, поэтому используется **только для начального обмена ключами**.
- После установления соединения всё шифруется **быстро и эффективно** с использованием **симметричного ключа**, полученного из асимметрического обмена.

---

| Шифрование трафика | ChaCha20 | **Симметричное** |
| Аутентификация пакетов | Poly1305 | MAC (симметричное) |

### **1. Что такое демон (daemon)?**

**Демон** — это фоновый процесс в операционных системах UNIX/Linux, который выполняется без взаимодействия с пользователем. Он запускается системой или вручную и продолжает работать в фоне, обычно для предоставления каких-либо сервисов (например, sshd, cron, nginx).

**Характеристики демона:**

- Не имеет управляющего терминала (отделяется от shell’а).
- Часто стартует при загрузке системы.
- Журналирует свою работу в syslog или другие лог-файлы.
- Имеет PID и может быть управляем через systemd, init, supervisord и пр.

**Примеры демонов:**

- sshd — обеспечивает SSH-доступ.
- cron — планировщик задач.
- nginx — веб-сервер.

### **2. Как дебажить bash-скрипт?**

Есть несколько способов отладки bash-скриптов:

### **Включение режима отладки:**

Добавь в начало скрипта:

```
#!/bin/bash -x
```

или запусти так:

```
bash -x script.sh
```

Это включит **трассировку**: каждый выполняемый шаг будет выводиться в терминал.

### **Более подробный режим:**

```
bash -xe script.sh
```

- x — трассировка команд.
- e — выход при ошибке (если какая-то команда завершится с ошибкой, скрипт завершится).

### **Временное включение отладки:**

```
set -x   # включить трассировку
...      # код для отладки
set +x   # выключить трассировку
```

### **Проверка синтаксиса без выполнения:**

```
bash -n script.sh
```

## **Что такое seq и ack**

TCP (в отличие от UDP) — это **потоковый протокол**, он отслеживает байты, а не пакеты.

### **seq (Sequence Number)**

- Это **порядковый номер первого байта** в этом сегменте.
- У каждого соединения свои независимые счётчики: клиент и сервер начинают с **случайного** стартового значения (для безопасности).

### **ack (Acknowledgment Number)**

- Это **номер байта, который ожидается следующим**.
- То есть: ack = последний полученный байт + 1.

---

## **Пример из твоего вывода:**

```
10.0.0.2.ssh > compute-vm: Flags [S.], seq 1821467501, ack 888060224
```

Расшифруем:

| **Поле** | **Значение** | **Значение** |
| --- | --- | --- |
| seq | 1821467501 | Сервер начал свою нумерацию с этого байта |
| ack | 888060224 | Сервер **получил SYN от клиента** с seq=888060223, и теперь **ждёт байт #888060224**(следующий) |
| Flags | S. | Это SYN+ACK — подтверждение соединения |

---

### **Почему такие большие числа?**

- TCP выбирает **случайные начальные sequence numbers**, чтобы:
    - Уменьшить риск подделки (spoofing),
    - Не конфликтовать с прошлым соединением.

---

## **Полная строка:**

```
11:51:38.598591 IP compute-vm > 10.0.0.2.ssh: Flags [P.], seq 1:44, ack 1, win 507, options [...], length 43: SSH: SSH-2.0-OpenSSH_9.6p1 Ubuntu-3ubuntu13.11
```

---

## **Расшифровка**

| **Поле** | **Значение** | **Объяснение** |
| --- | --- | --- |
| **Время** | 11:51:38.598591 | Время захвата пакета |
| **IP** | compute-vm > 10.0.0.2.ssh | Исходный и целевой адрес+порт |
| **Flags** | [P.] | PUSH + ACK — это обычные данные, которые надо немедленно передать |
| **seq 1:44** |  | В этом сегменте передаётся **байты с 1 по 43 включительно** |
| **ack 1** |  | Подтверждение, что клиент получил байт #0 от сервера |
| **win 507** |  | Размер окна — сколько байтов клиент готов принять в ответ |
| **options** | TS val 2832456588 ecr 3500639150 | TCP timestamp (для расчёта RTT и защиты от повторов) |
| **length 43** |  | Полезная нагрузка — 43 байта данных |
| **SSH:** | SSH-2.0-OpenSSH_9.6p1 Ubuntu-3ubuntu13.11 | Стартовая строка SSH-протокола клиента (баннер) |

---

## **Что происходит**

1. Клиент уже установил TCP-соединение.
2. Отправляет **первые настоящие данные** — это **SSH-баннер** (всегда текстовая строка).
3. Этот баннер — обязательная часть SSH: он сообщает серверу, какой протокол и реализация используются.

---

## **Что такое Flags [P.]**

- P (PUSH) говорит, что данные нужно немедленно передать, **не ждать** накопления буфера.
- . (ACK) — подтверждение получения предыдущего пакета.

Давай подробно разберём **все этапы установления SSH-соединения через один jump host (или bastion)**.

## **Исходные данные**

Предположим у нас есть:

- **Локальная машина (ты)** — you@local
- **Jump host (промежуточный сервер)** — jump@jump-host.com
- **Целевой сервер (внутренний)** — admin@target.internal

Ты хочешь подключиться **из локальной машины на target.internal через jump-host**, используя SSH.

---

## **Общий путь:**

```
ssh -J jump@jump-host.com admin@target.internal
```

---

## **Подробные этапы соединения**

---

### **1. Подготовка на клиенте (локально)**

- SSH клиент проверяет, указан ли параметр -J или ProxyJump в конфиге.
- Понимает, что **соединение к target.internal должно идти через jump-host.com**.
- Генерируется пара **эпизодических (ephemeral) ключей** для аутентификации, если необходимо.

---

### **2. Установление SSH-соединения к jump-host**

- Обычный SSH-handshake:
    - Клиент устанавливает TCP-соединение на jump-host.com:22
    - Получает баннер сервера (например, OpenSSH_9.3)
    - Выбирается алгоритм шифрования (обычно ECDSA или ED25519)
    - Обмениваются ключами (Diffie-Hellman или Curve25519)
    - Проводится проверка known_hosts
    - Происходит аутентификация:
        - Либо по паролю
        - Либо по публичному ключу (если ~/.ssh/authorized_keys содержит нужный ключ)
- После успешной аутентификации клиент **открывает туннель** к следующему хосту (target.internal).

---

### **3. Создание туннеля через jump-host к целевому хосту**

- На jump-host выполняется команда:

```
ssh -W target.internal:22 admin@target.internal
```

- или аналог через ProxyJump.
- Это означает:
    - **Ввод и вывод сессии (stdin/stdout) проксируются** между you@local и target.internal через jump-host.
    - jump-host **не дешифрует и не “видит” содержимое SSH** между тобой и target.

> Это не “двойной вход по SSH”, а
> 
> 
> **транспортный туннель через jump-host**
> 

---

### **4. Установление SSH-сессии с target.internal**

Теперь ты подключаешься к target.internal:

- SSH клиент **отправляет данные через туннель**, как будто напрямую подключается к target.internal:22.
- Происходит вторая сессия:
    - SSH-рукопожатие
    - Обмен ключами
    - Аутентификация (пароль, ключ, 2FA и т.д.)
    - Начало интерактивной сессии (bash и т.п.)

> При этом с точки зрения target.internal ты выглядишь как обычный SSH-клиент, пришедший с IP-адреса jump-host.
> 

---

### **5. Начало интерактивной сессии**

- Если всё прошло успешно:
    - Ты получаешь shell (bash, zsh, и т.д.)
    - Можешь выполнять команды
    - Трафик шифруется между всеми узлами
