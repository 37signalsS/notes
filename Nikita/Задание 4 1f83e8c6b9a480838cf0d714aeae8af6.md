# Задание 4

```
^/image1/(?<file>.+\.jpg)$
```

---

### 1. `^`

- **Начало строки**.
- Это означает, что шаблон должен совпадать **с самого начала URI**.

---

### 2. `/image1/`

- Просто **буквальный текст**: означает, что URI должен начинаться с `/image1/`.
- Например: `/image1/cat.jpg` — подходит, а `/img/cat.jpg` — нет.

---

### 3. `(?<file>.+\.jpg)`

Это — **именованная группа** захвата. Давай её подробно разберём:

### `(?<file>...)`

- Открывает **группу с именем `file`**.
- Всё, что внутри скобок, будет **сохранено** в переменную `$file`, которую можно использовать в Nginx.
- Пример: если URI — `/image1/cat.jpg`, то `$file` будет `cat.jpg`.

### `.+`

- `.` — любой символ, **кроме новой строки**.
- `+` — один или более раз.
- Это означает: захватываем **одно или больше любых символов**.

### `\.jpg`

- `\.` — экранированная точка (иначе `.` обозначает «любой символ»). Здесь она означает **буквально точку**.
- `jpg` — буквенная последовательность.
- Вместе `\.jpg` — это **расширение `.jpg`**.

**Всё вместе `(?<file>.+\.jpg)` означает:**

> Захватить всё, что заканчивается на .jpg после /image1/, и сохранить как $file.
> 

---

### 4. `$`

- **Конец строки**.
- Указывает, что после `.jpg` **ничего больше в URI быть не должно**.

---

### **Порядок обработки location в Nginx**

---

### **1. Точное совпадение: location = /path**

- Срабатывает **только если URI полностью совпадает**.
- Самый высокий приоритет.
- Например: location = /admin — сработает **только** на /admin, но **не** на /admin/ или /admin/panel.

---

### **2. Префиксные (location /path)**

- Совпадение по **началу строки URI**.
- Nginx выбирает **самую длинную** подходящую строку.
- Например: если есть location / и location /images/, а URI — /images/cat.jpg, будет выбран location /images/.

---

### **3. Регулярные выражения (~, ~*)**

- Используются, если **нет точного совпадения**, и если включены регулярные блоки.
- Проверяются **после префиксных**.
- Среди нескольких совпавших рег. выражений Nginx выбирает **первое** в конфиге.

---

### **4. Блок по умолчанию (location /)**

- Если ничего другого не подошло — используется этот.

---

## **Символы и их значение**

### **= — точное совпадение**

- Самый высокий приоритет.
- Пример:

```
location = /about {
    return 200 "About page";
}
```

---

### **~ — регулярное выражение с учётом регистра**

- Используется, если URI **совпадает по регулярке**.
- Например:

```
location ~ \.php$ {
    fastcgi_pass ...;
}
```

---

### **~* — регулярное выражение без учёта регистра**

- Аналогично ~, но регистр игнорируется.
- Например:

```
location ~* \.(jpg|jpeg|png)$ {
    root /images;
}
```

- Обработает и image.JPG, и image.jpg.

---

### **^~ — префиксное совпадение с высоким приоритетом**

- Если путь совпал по префиксу — **регулярные выражения больше не проверяются**.
- Используется, чтобы “защитить” часть URI от перебора регулярных выражений.
- Например:

```
location ^~ /static/ {
    root /var/www/static;
}
```

---

## **Краткий приоритет**

1. = — точное совпадение
2. ^~ — префикс, блокирующий regex
3. ~ и ~* — регулярки
4. Простое префиксное совпадение (без модификатора)
5. location / — по умолчанию

Отлично! Понимание **порядка обработки server блоков** в Nginx — это ключ к правильной маршрутизации между сайтами и доменами.

## **Как Nginx выбирает server блок**

Когда приходит HTTP-запрос, Nginx выбирает подходящий server блок по **двум этапам**:

---

### **ЭТАП 1: Выбор по listen**

Nginx сначала выбирает **все server блоки**, у которых listen порт совпадает с портом запроса (например, 80 или 443).

Пример:

```
server { listen 80; server_name site1.com; }
server { listen 80; server_name site2.com; }
server { listen 443 ssl; server_name site1.com; }
```

Если запрос на порт 80, выбираются первые два блока.

---

### **ЭТАП 2: Выбор по server_name**

Среди выбранных на первом этапе блоков, Nginx ищет **наиболее подходящее значение server_name**, сравнивая его с заголовком Host из запроса.

### **Правила приоритета:**

1. **Точное совпадение** с server_name — приоритет №1
2. **Подстановки** (*.example.com) — менее приоритетны
3. **Регулярные выражения (~)** — ещё ниже
4. **Если ничего не подошло** — используется **первый объявленный server блок**, он считается **default**

---

### **Что если server_name не совпал ни с одним?**

Тогда срабатывает **первый блок с нужным listen портом** — он считается **по умолчанию**.

---

### **default_server — явное указание на сервер по умолчанию**

Ты можешь **вручную указать**, какой server использовать по умолчанию:

```
server {
    listen 80 default_server;
    server_name _;
}
```

---

## **Как работает с HTTPS?**

С TLS (порт 443) выбор server работает так же, **но только после того, как завершена TLS-рукопожатие**. Используется SNI (Server Name Indication) — клиент сообщает имя хоста ещё до расшифровки HTTPS.

---

## **Резюме: Порядок выбора server**

1. Nginx ищет все server блоки с подходящим listen портом.
2. Среди них выбирает:
    - Сначала **точное совпадение по server_name**
    - Затем подстановки (*.)
    - Затем регулярки (~)
    - Если нет совпадений — берёт **первый** или тот, что указан как default_server.

## **Что делает `alias` в примере:**

```
location ~ ^/image1/(?<file>.+\.jpg)$ {
    image_filter rotate 180;
    alias /var/www/images/$file;
    add_header Content-Type image/jpeg;
}

```

Здесь `alias` указывает, **где на диске реально лежит запрошенный файл**.

### Пример запроса:

**URI:** `/image1/cats/kitty.jpg`

- Регулярное выражение захватывает часть `cats/kitty.jpg` в переменную `$file`.
- Внутри блока `location`, Nginx интерпретирует:
    
    ```
    alias /var/www/images/cats/kitty.jpg;
    
    ```
    
- Значит, файл будет прочитан с пути **`/var/www/images/cats/kitty.jpg`**.

---

## **Важно: `alias` заменяет весь путь `location`**

В отличие от `root`, `alias` **не добавляет** часть URI к указанному пути — **он подменяет весь путь**.

### Пример отличия:

```
location /images/ {
    alias /data/pics/;
}

```

**Запрос:** `/images/dog.jpg`

**Реальный путь:** `/data/pics/dog.jpg`

(а не `/data/pics/images/dog.jpg`)

---

## **Когда использовать `alias` вместо `root`:**

- Когда ты хочешь, чтобы физический путь **не соответствовал URI** напрямую.
- Особенно полезен с регулярными выражениями или динамическими частями пути.
- Обязателен, когда путь не должен включать `location`префикс.

---

## **Внимание с `/` на конце**

Убедись, что ты правильно расставляешь `/`:

- В `alias` путь обычно **должен** заканчиваться `/`, если ты хочешь сохранить вложенные папки.

## **Что такое `upstream` в Nginx?**

Блок `upstream` позволяет задать **группу серверов-бэкендов**, к которым Nginx может проксировать запросы.

Он используется вместе с `proxy_pass`, `fastcgi_pass`, `uwsgi_pass` и т.д.

Пример:

```
upstream backend {
    server backend1.example.com;
    server backend2.example.com;
}

location / {
    proxy_pass http://backend;
}
```

---

## **Виды балансировки нагрузки в Nginx**

Вот основные механизмы (алгоритмы), которые Nginx поддерживает **встроенно**:

---

### 1. **Round-robin (по умолчанию)**

**Что делает:**

- Просто перебирает сервера по очереди: сервер 1, потом 2, потом снова 1 и т.д.

**Пример:**

```
upstream backend {
    server srv1;
    server srv2;
}

```

**Особенности:**

- Простой, но не учитывает нагрузку или скорость ответа.

---

### 2. **Least Connections (наименьшее количество соединений)**

**Что делает:**

- Отдаёт запрос серверу, у которого сейчас **меньше всего активных соединений**.

**Пример:**

```
upstream backend {
    least_conn;
    server srv1;
    server srv2;
}
```

**Полезно:**

- При неравномерной нагрузке на серверы или когда запросы имеют разную «тяжесть».

---

### 3. **IP Hash (по IP клиента)**

**Что делает:**

- Один и тот же клиент (по IP) всегда попадает на **один и тот же сервер**.

**Пример:**

```
upstream backend {
    ip_hash;
    server srv1;
    server srv2;
}
```

**Полезно для:**

- **Сессий**, когда важно, чтобы пользователь попадал на один и тот же сервер (если нет общей сессии).

---

### 4. **Hash (настраиваемый хеш)**

> Только в коммерческой версии NGINX Plus или через сторонние модули.
> 

Позволяет использовать любую хеш-функцию на основе, например, URI, cookie и т.д.

---

## **Дополнительные опции для серверов**

Внутри `upstream` можно указывать настройки для каждого сервера:

```
server srv1 weight=3 max_fails=2 fail_timeout=10s;

```

- **`weight=N`** — вес сервера (чем больше — тем чаще используется).
- **`max_fails=2`** — если сервер дважды не ответил — помечается как недоступный.
- **`fail_timeout=10s`** — на сколько секунд исключить сервер после `max_fails`.
- **`backup`** — использовать сервер **только если все остальные недоступны**.

---

## **Пример с несколькими настройками:**

```
upstream backend {
    least_conn;
    server 10.0.0.1 weight=3;
    server 10.0.0.2 max_fails=2 fail_timeout=5s;
    server 10.0.0.3 backup;
}
```
