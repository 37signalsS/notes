# GitOps: Управление секретами

> **Надежность: 10** (Подтверждено SSoT и актуальными данными на февраль 2026)
> **Актуальные версии:** SOPS v3.9, Sealed Secrets v0.28, Vault v1.18.

Хранение секретов — одна из главных проблем в GitOps. Поскольку Git является источником истины, хранить в нем пароли и ключи в открытом виде недопустимо. Эта заметка описывает ключевые подходы для безопасного управления секретами в рамках методологии GitOps.

## Определения

- **Секрет (Secret)**: Любые чувствительные данные, необходимые приложению для работы: пароли от баз данных, API-ключи, TLS (Transport Layer Security)-сертификаты.
- **Шифрование в Git (Encryption-in-Git)**: Подход, при котором зашифрованная версия секрета коммитится в Git. Расшифровка происходит непосредственно в кластере в момент развертывания.
- **KMS (Key Management Service)**: Облачный сервис для управления ключами шифрования (например, AWS KMS, Azure Key Vault, Google Cloud KMS).

## Базовые концепции

### Проблема: Секреты в Git

Стандартный ресурс **Kubernetes** `Secret` — это данные в формате Base64, что не является шифрованием. Коммитить такие манифесты в Git-репозиторий эквивалентно публикации паролей в открытом доступе. Это нарушает принципы безопасности и затрудняет прохождение аудита.

### Ключевые подходы

1. **Шифрование в Git (Sealed Secrets, SOPS)**: Зашифрованный секрет хранится в Git. Специальный контроллер в кластере с доступом к ключу расшифровывает его перед применением.
   - **Преимущество**: вся конфигурация (включая секреты) находится в Git.
   - **Недостаток**: необходимость управления ключами шифрования вне Git.
2. **Внешнее хранилище (HashiCorp Vault)**: Секреты хранятся в специализированной системе. В Git хранится только ссылка на секрет или конфигурация для его инъекции в поды.
   - **Преимущество**: централизованное управление, автоматическая ротация, детальный аудит.
   - **Недостаток**: усложнение архитектуры, зависимость от доступности внешней системы.

### Сравнение инструментов

| Инструмент | Алгоритм шифрования | Управление ключами | Тип интеграции | Сложность |
| :--- | :--- | :--- | :--- | :--- |
| **Sealed Secrets** | Асимметричное (RSA — Rivest-Shamir-Adleman) | Приватный ключ внутри кластера | Полный GitOps | Низкая |
| **SOPS** | Симметричное (AES — Advanced Encryption Standard) + KMS/PGP/age | Внешние (KMS, PGP — Pretty Good Privacy, age) | Полный GitOps (Flux нативно) | Средняя |
| **Vault** | Динамические секреты | Transit Engine | Агент или оператор | Высокая |

## Практические сценарии

### Сценарий 1: Bitnami Sealed Secrets

Подходит для небольших команд и быстрого старта.

- **Механизм работы**: В кластере работает `sealed-secrets-controller`, хранящий приватный ключ. С помощью CLI (Command Line Interface) `kubeseal` обычный `Secret` шифруется публичным ключом контроллера. В Git коммитится только **CRD (Custom Resource Definition)** `SealedSecret`. Контроллер в кластере обнаруживает этот ресурс и создает на его основе стандартный `Secret`.
- **Пример `SealedSecret` в Git**:

    ```yaml
    apiVersion: bitnami.com/v1alpha1
    kind: SealedSecret
    metadata:
      name: my-secret
      namespace: my-app
    spec:
      encryptedData:
        # Зашифрованные данные (нечитаемы без приватного ключа контроллера)
        DATABASE_PASSWORD: AgA...
      template:
        metadata:
          name: my-secret
    ```

> **Подробное руководство:** см. **[Sealed Secrets](../../Kubernetes/Security/sealed_secrets_overview.md)**.

### Сценарий 2: Mozilla SOPS

Универсальный инструмент с поддержкой облачных KMS и локальных ключей (age/PGP).

- **Механизм работы**: С помощью CLI `sops` шифруются только значения конкретных полей внутри YAML/JSON-файлов. В Git коммитится файл с зашифрованными значениями и метаданными о ключах. GitOps-инструмент (например, Flux) с доступом к мастер-ключу расшифровывает данные "на лету" перед применением в кластер.
- **Пример конфигурации для Flux + SOPS**:

    ```yaml
    # Kustomization ссылается на ключ для расшифровки
    apiVersion: kustomize.toolkit.fluxcd.io/v1
    kind: Kustomization
    metadata:
      name: my-app
    spec:
      # ...
      decryption:
        provider: sops
        secretRef:
          name: sops-age-key # Secret с приватным ключом age в кластере
    ```

> **Подробное руководство:** см. **[SOPS](../../Security/Tools/sops_overview.md)**.

### Сценарий 3: HashiCorp Vault (Внешнее хранилище)

Промышленный стандарт для крупных инфраструктур и строгих требований безопасности.

- **Механизм работы**: Секреты хранятся в Vault. В манифесте `Deployment` указываются аннотации. Специальный компонент (**Vault Injector**) в Kubernetes перехватывает запросы на создание подов и добавляет в них sidecar-контейнер, который аутентифицируется в Vault и монтирует секреты в файловую систему пода.
- **Основная концепция**: GitOps-инструмент оперирует только метаданными, секреты попадают в приложение только на этапе выполнения (runtime).

> **Подробное руководство:** см. **[HashiCorp Vault](../../Vault/overview.md)** и **[Интеграция ArgoCD с Vault](../ArgoCD/argocd_vault_integration.md)**.

**Рекомендации:**

- **Ротация ключей**: Установите регламент регулярной смены ключей шифрования (для SOPS и Sealed Secrets) и токенов доступа.
- **Политики безопасности**: Используйте Kubernetes-политики (например, Kyverno) для запрета ручного создания `Secret` в обход GitOps-пайплайна.
- **Аудит**: Включайте логирование доступа к секретам как в Git (через историю коммитов), так и во внешних хранилищах.
