# GitOps: Управление секретами

Хранение секретов — одна из главных проблем в GitOps. Поскольку Git является единственным источником истины, хранить в нем пароли и ключи в открытом виде недопустимо. Эта заметка описывает ключевые подходы для безопасного управления секретами в рамках методологии GitOps.

## Определения

- **Секрет (Secret)**: Любые чувствительные данные, необходимые приложению для работы: пароли от баз данных, API-ключи, TLS-сертификаты.
- **Шифрование в Git (Encryption-in-Git)**: Подход, при котором зашифрованная версия секрета коммитится в Git. Расшифровка происходит непосредственно в кластере в момент развертывания.
- **KMS (Key Management Service)**: Облачный сервис для управления ключами шифрования (например, AWS KMS, Azure Key Vault, Google Cloud KMS).
- **External Secrets Operator (ESO)**: Оператор Kubernetes, синхронизирующий секреты из внешних систем (Vault, AWS Secrets Manager) в нативные объекты Secret.

## Базовые концепции

### Проблема: Секреты в Git

Стандартный ресурс **Kubernetes** `Secret` — это данные в формате Base64, что не является шифрованием. Коммитить такие манифесты в Git-репозиторий эквивалентно публикации паролей в открытом доступе. Это нарушает принципы безопасности и затрудняет прохождение аудита.

### Ключевые подходы

1. **Шифрование в Git (Sealed Secrets, SOPS)**: Зашифрованный секрет хранится в Git. Специальный контроллер в кластере с доступом к ключу расшифровывает его перед применением.
2. **Синхронизация извне (External Secrets Operator)**: Секреты хранятся во внешней системе, а в кластере создается декларативная ссылка на них. Оператор автоматически создает нативный Secret.
3. **Runtime-инъекция (Vault Injector)**: Секреты попадают в приложение только в момент запуска пода через sidecar-контейнеры, не создавая нативных Secret в Kubernetes.

### Сравнение инструментов

| Инструмент | Хранение данных | Рабочий процесс (Dev) | Разделение ответственности | Сложность |
| :--- | :--- | :--- | :--- | :--- |
| **Sealed Secrets** | В Git (зашифровано) | Локальное шифрование через CLI (`kubeseal`) | Низкое (секреты и код в одном репо) | Низкая |
| **SOPS** | В Git (зашифровано) | Прозрачное шифрование (через age/KMS) | Среднее | Средняя |
| **External Secrets** | Вне Git (Vault/Cloud) | Только ссылка на внешний секрет в манифесте | **Высокое** (в Git нет конфиденциальных данных) | Средняя/Высокая |
| **Vault Injector** | Вне Git (динамически) | Описание аннотаций в поде | Максимальное | Высокая |

## Практические сценарии

### Сценарий 1: Bitnami Sealed Secrets

Подходит для небольших команд и быстрого старта.

- **Механизм работы**: В кластере работает контроллер, хранящий приватный ключ. С помощью CLI `kubeseal` обычный Secret шифруется публичным ключом. В Git коммитится только `SealedSecret`. Контроллер обнаруживает его и создает стандартный Secret.
- **Преимущество**: Не требует внешней инфраструктуры или облачных KMS.

> **Подробное руководство:** см. **[Sealed Secrets](../../Kubernetes/Security/sealed_secrets_overview.md)**.

### Сценарий 2: Mozilla SOPS

Универсальный инструмент с поддержкой облачных KMS и локальных ключей (age).

- **Механизм работы**: Шифруются только значения полей внутри YAML/JSON. В Git попадает файл с зашифрованными данными и метаданными о ключах. GitOps-инструмент (например, Flux) расшифровывает данные перед применением.
- **Пример конфигурации для Flux + SOPS**:

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: my-app
spec:
  decryption:
    provider: sops
    secretRef:
      name: sops-age-key
```

### Сценарий 3: External Secrets Operator (ESO)

Рекомендуемый подход для гибридных и облачных инфраструктур.

- **Механизм работы**: Вы описываете `ExternalSecret`, который ссылается на `SecretStore` (коннектор к Vault, AWS и т.д.). Оператор опрашивает внешний API и создает Secret в Kubernetes.
- **Преимущество**: Разделение ответственности — DevOps управляет доступом к хранилищу, разработчик описывает потребность в секрете.

> **Подробное руководство:** см. **[External Managers](../../Kubernetes/Base/secrets/external_managers.md)**.

### Сценарий 4: HashiCorp Vault Injector

Для сред с высокими требованиями безопасности и динамическими секретами.

- **Механизм работы**: Vault Injector перехватывает создание подов и добавляет sidecar, который монтирует секреты прямо в файловую систему (tmpfs).
- **Особенности**: Секреты никогда не сохраняются в etcd кластера в виде объектов Secret.

**Рекомендации:**
1. **Принцип минимизации привилегий**: GitOps-контроллер должен иметь доступ только к тем ключам KMS, которые необходимы для его окружения.
2. **Аудит**: Включайте логирование доступа к секретам. В GitOps источником аудита изменений конфигурации секретов является история коммитов.
3. **Запрет ручных правок**: Используйте политики (Kyverno/OPA) для блокировки создания нативных Secret вручную.
