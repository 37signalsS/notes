# GitOps: Обзор Методологии

## Определения

**GitOps** — это методология управления инфраструктурой и приложениями, при которой Git-репозиторий является единственным источником истины (**Single Source of Truth**) для всей декларативной конфигурации. Основная цель — автоматизация, создание версий и отслеживание изменений с использованием Git как надежной базы, что обеспечивает более быструю, надежную и полностью проверяемую (auditable) доставку программного обеспечения.

В рамках GitOps любые изменения в состоянии системы — будь то конфигурация приложения, обновление инфраструктуры или политики безопасности — производятся через коммиты в Git-репозиторий.

## Эволюция подхода

GitOps не появился в вакууме, а стал результатом развития инструментов автоматизации:

1.  **Системы управления конфигурациями (Ansible, Puppet, Chef):** Позволили специалистам DevOps настраивать инфраструктуру внутри виртуальных машин с помощью кода, обеспечивая повторяемость настроек.
2.  **Инфраструктура как код (IaC) (Terraform, CloudFormation):** Сделали возможным создание целых инфраструктур (облачных ресурсов, сетей) с помощью кода. Git стал стандартным хранилищем для этих конфигураций.
3.  **GitOps:** Применил принципы IaC к управлению не только инфраструктурой, но и приложениями, используя Git как единственный источник истины и декларативный способ управления всем стеком.

**GitOps и Kubernetes:** Появление Kubernetes стало катализатором развития GitOps. Его декларативная природа и встроенные циклы согласования идеально подошли для реализации GitOps-принципов, сделав этот подход основным для доставки приложений в кластеры K8s.

## Базовые концепции

### Модели развертывания

Существует две основные модели развертывания в **CI/CD**:

* **Push Model (Традиционный CI/CD):** Внешние системы (GitLab CI, Jenkins) инициируют изменения и "проталкивают" их в кластер. У этих систем должны быть прямые доступы к среде исполнения.
* **Pull Model (GitOps):** Оператор, установленный внутри кластера (например, ArgoCD), непрерывно отслеживает ("pull") состояние Git-репозитория и самостоятельно приводит кластер в соответствие с желаемым состоянием. Эта модель считается более безопасной, так как учетные данные для доступа к кластеру не выходят за его пределы.

**Подробнее:** [Стратегии развертывания](../CI-CD/Core_Concepts/deployment_strategies.md#основные-концепции).

### Ключевые принципы (OpenGitOps)

На техническом уровне GitOps строится на четырех фундаментальных принципах:

1.  **Декларативные описания:** Вся система (инфраструктура и приложения) описывается декларативно — вы указываете желаемое состояние, а не шаги по его достижению. Это создает единое и четкое определение целевого состояния.
2.  **Контроль версий в Git:** Желаемое состояние хранится в Git, который служит единственным источником истины (**SSoT**). Все изменения вносятся через Pull Requests (PR), проходят аудит/ревью и объединяются в основную ветку, обеспечивая полную прослеживаемость.
3.  **Автоматическое применение изменений:** Как только изменения попадают в основную ветку Git, они автоматически применяются к системе. Это реализуется через CD-пайплайны или специализированных агентов, исключая ручные операции в кластере.
4.  **Непрерывная сверка (Continuous Reconciliation):** Программные агенты постоянно сравнивают фактическое состояние системы с желаемым (описанным в Git). При обнаружении расхождений (дрейфа) система автоматически возвращается к целевому состоянию.

### Детекция дрейфа (Drift Detection)

Одной из ключевых особенностей GitOps является способность контроллера обнаруживать расхождения (дрейф) между желаемым и фактическим состоянием системы. 
* Если ресурс изменен вручную (например, через `kubectl edit`), GitOps-оператор пометит его как `OutOfSync`.
* В зависимости от настроек (Self-healing), оператор автоматически перезапишет ручные изменения, возвращая систему к состоянию, описанному в Git.

### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- |
| **Надежность и предсказуемость:** Возможность быстрого отката и восстановления всей системы из Git. | **Управление секретами:** Хранение секретов в Git требует специальных инструментов для шифрования, таких как [SOPS](../Security/Tools/sops_overview.md) или интеграции с [Vault](../Vault/overview.md). |
| **Автоматическое устранение дрейфа:** Гарантия того, что реальное состояние всегда соответствует описанному в коде. | **Зависимость от Git:** Недоступность Git-сервера может заблокировать любые изменения в системе. |
| **Прозрачность и аудит:** Полная история всех изменений, их авторов и ревьюверов через Pull/Merge Requests. | **Строгий регламент:** Все изменения, даже срочные, должны производиться через Git, что может замедлить реакцию в экстренных ситуациях. |
| **Повышенная безопасность:** Сокращение прямых доступов к кластеру («No kubectl access in prod»). | **Динамические окружения:** Создание временных окружений может потребовать сложной автоматизации подготовки конфигурации в Git. |
| **Самообслуживание (Self-service):** Разработчики могут управлять инфраструктурой через знакомые инструменты Git, снижая нагрузку на Ops-команды. | |
| **Упрощение комплаенса:** Версионирование в Git упрощает прохождение внешних аудитов безопасности. | |

## Неизменяемая инфраструктура (Immutable Infrastructure)

Неизменяемая инфраструктура — краеугольный камень GitOps. В отличие от традиционного подхода, где компоненты обновляются «на лету» (in-place updates), здесь компоненты полностью заменяются при каждом развертывании.

*   **Роль контейнеризации:** Контейнеры упаковывают приложения со всеми зависимостями в неизменяемые образы. Новая версия — это новый образ, а не изменение старого.
*   **Снижение дрейфа:** Поскольку работающая инфраструктура не меняется вручную, вероятность расхождения конфигураций (configuration drift) между узлами сводится к минимуму.
*   **Надежный откат:** Если развертывание новой версии вызвало ошибку, откат заключается в простой замене текущих компонентов на предыдущие проверенные образы.

## Внедрение и рабочие процессы

Реализация GitOps начинается с настройки взаимодействия между Git и кластером Kubernetes.

### Шаги настройки (Workflow Setup)

1.  **Инициализация репозитория:** Создание Git-репозитория, который станет единственным источником истины (SSoT) для манифестов и конфигураций.
2.  **Интеграция CI/CD:** Настройка пайплайнов (GitLab CI, GitHub Actions) для автоматической валидации манифестов и сборки артефактов.
3.  **Развертывание GitOps-оператора:** Установка ArgoCD или Flux внутри кластера для мониторинга Git-репозитория.
4.  **Настройка Webhooks:** Конфигурация уведомлений от Git-сервера к оператору для мгновенного запуска синхронизации при пуше. Вебхуки ускоряют реакцию (обнаружение), но модель остается Pull-ориентированной (согласование выполняется агентом).
5.  **Мониторинг и оповещение:** Использование Prometheus и Grafana для отслеживания статуса синхронизации и производительности контроллеров.

### Структура репозиториев (Repo Patterns)

Выбор структуры зависит от масштаба организации и требований к изоляции:

| Модель | Плюсы | Минусы |
| :--- | :--- | :--- |
| **Монорепозиторий (Monorepo)** | Упрощенное управление зависимостями, атомарные изменения во всех сервисах, общий инструментарий. | Большой объем CI-задач, «зашумленная» история коммитов, сложность разграничения прав доступа. |
| **Мультирепозиторий (Multi-repo)** | Изоляция команд, автономность, детальное управление правами доступа (RBAC). | Сложность координации изменений, затрагивающих несколько репозиториев. |

**Рекомендуемый подход:** Использование отдельных репозиториев для кода приложений и выделенного централизованного репозитория для инфраструктурных манифестов.

### Стратегии продвижения и внедрения (Promotion Strategies)

Продвижение изменений между окружениями (Dev -> Staging -> Prod) реализуется двумя способами:

1.  **На базе веток (Branch-based):** Каждое окружение — отдельная ветка (`main`, `staging`, `develop`). Продвижение через Merge Requests. Это позволяет использовать `git diff` для сравнения сред, но несет риск дрейфа между ветками.
2.  **На базе репозиториев (Repo-based):** Каждое окружение — отдельный Git-репозиторий. Обеспечивает **максимальную изоляцию** и безопасность (ограничение доступа к продакшену на уровне прав Git), гарантирует, что изменения в одной среде не повлияют случайно на другую.

## Управление манифестами

Эффективное управление сложностью конфигураций достигается через шаблонизацию и модульность.

### Helm vs Kustomize в GitOps

Это ключевой архитектурный выбор при проектировании системы доставки:

*   **Helm:** Пакетный менеджер с мощной шаблонизацией (Go templates). Идеален для сторонних приложений (инфраструктурные аддоны).
    *   *Совет для GitOps:* Всегда закрепляйте версии чартов (pinning versions) для обеспечения детерминированности развертывания.
*   **Kustomize:** Инструмент композиции YAML через базы (bases) и наложения (overlays). Прост, детерминирован и нативен для Kubernetes.
    *   *Совет для GitOps:* Используйте наложения для специфичных настроек окружений (dev/prod), сохраняя базовые манифесты неизменными.

**Комбинированный подход:** Использование Helm для вендорских чартов и Kustomize для тонкой настройки (patches) собственных приложений поверх сгенерированных манифестов.

### Валидация и тестирование

Для предотвращения деплоя некорректных конфигураций в CI-пайплайн встраиваются проверки:
*   **Декларативная валидация:** Проверка синтаксиса YAML.
*   **Схематическая проверка:** Использование **[kubeconform](../Kubernetes/ToolsUtilities/kubeconform_overview.md)** или `kubeval` для проверки манифестов на соответствие схемам Kubernetes API.
*   **Static Analysis:** Использование `kube-score` для проверки манифестов на соответствие лучшим практикам (лимиты ресурсов, пробы).

## Прогрессивная доставка (Progressive Delivery)

GitOps отлично сочетается со стратегиями постепенного выпуска, такими как **Canary** и **Blue/Green**.

*   **Canary-выпуски:** Постепенное переключение части трафика на новую версию для проверки стабильности.
*   **Argo Rollouts:** Специализированный контроллер, расширяющий возможности Kubernetes Deployment. Он позволяет описывать шаги канареечного развертывания (например, 10% -> 50% -> 100%) непосредственно в манифестах.

## Практические сценарии

### Сценарий 1: Выбор GitOps-инструмента

| Критерий | ArgoCD | Flux | Fleet |
| :--- | :--- | :--- | :--- |
| **Назначение** | CD для Kubernetes | CD для Kubernetes | Мультикластерный GitOps (Rancher) |
| **Интерфейс** | Веб-UI + CLI | CLI-only | Rancher UI + CLI |
| **Подход** | Монолитный оператор | Модульный toolkit | Масштабируемый контроллер |
| **Когда использовать** | Визуальный контроль, мультикластер | "Unix-way", автоматизация обновлений | Управление тысячами кластеров |

**Подробнее:** [ArgoCD](./ArgoCD/argocd_overview.md), [Flux](./flux.md), [сравнение ArgoCD и Flux](./argo_vs_flux_manifests.md).

### Сценарий 2: Инфраструктурный GitOps

Принципы GitOps применимы не только к приложениям, но и к инфраструктуре (**IaC**):
* **Crossplane:** Управление облачными ресурсами (AWS, GCP, Yandex Cloud) через Kubernetes API в GitOps-цикле. Подробнее: [Обзор Crossplane](./Crossplane/overview.md).
* **Terraform-контроллеры:** Использование Flux TF-controller для выполнения Terraform-планов на основе изменений в Git.

### Сценарий 3: Monitoring as Code (MaC)

Управление ресурсами мониторинга через GitOps-цикл.
* **Grafana:** Хранение JSON-дашбордов в Git, упаковка в ConfigMap и автоматическая синхронизация с кластером через ArgoCD. См. подробнее: **[Monitoring as Code (MaC)](../Grafana/monitoring_as_code.md)**.
* **Alertmanager:** Декларативное описание правил оповещения и маршрутизации.

### Сценарий 4: Управление и безопасность (Governance)

GitOps позволяет внедрять политики безопасности на разных этапах:
* **Валидация манифестов:** Проверка YAML-файлов в CI через `kubeconform` или `conftest`.
* **Runtime-политики:** Использование **Kyverno** или **OPA** для контроля ресурсов, развернутых через GitOps.

### Сценарий 5: Управление секретами

Хранение секретов в Git — критическая проблема. В 2026 году используются два основных подхода:

| Критерий | Sealed Secrets (Bitnami) | External Secrets Operator (ESO) |
| :--- | :--- | :--- |
| **Механизм** | Асимметричное шифрование. В Git попадает `SealedSecret`. | Указатель на внешнее хранилище (`ExternalSecret`). |
| **Хранилище** | Внутри Git (зашифровано). | Вне Git (Vault, AWS Secrets Manager). |
| **Безопасность** | Зависит от защиты приватного ключа в кластере. | **Максимальная:** данные никогда не покидают KMS. |
| **Сложность** | Низкая (не требует внешних систем). | Высокая (требует настройки KMS и прав доступа). |
| **Рекомендация** | Небольшие проекты, отсутствие внешнего KMS. | **Enterprise-стандарт**, гибридные облака. |

Для локального шифрования также используется **[SOPS](../Security/Tools/sops_overview.md)**. Подробнее: [Управление секретами в GitOps](./secrets_encryption.md).

### Сценарий 6: Загрузка кластера (Cluster Bootstrapping)

Argo CD позволяет автоматизировать развертывание и обновление системных дополнений (add-ons) в масштабах от десятков до тысяч кластеров.
*   **Гибкое таргетирование:** Использование меток (labels) и селекторов для выбора подмножеств кластеров, которым нужны специфические конфигурации.
*   **Динамическое управление:** Применение **ApplicationSet** с различными генераторами (Git, Cluster, List) для автоматического обнаружения новых кластеров и создания приложений.
*   **Аудит и версии:** Все манифесты аддонов хранятся в Git, обеспечивая полную историю изменений и детерминированность состояния флота.

### Сценарий 7: Самообслуживание для разработчиков (Self-service)

Модель, позволяющая командам разработки самостоятельно управлять жизненным циклом своих приложений без прямого участия администраторов.
*   **Автономия:** Разработчики описывают манифесты в своих репозиториях, сохраняя контроль над конфигурацией.
*   **Безопасность:** Ресурс **AppProject** и правила RBAC ограничивают доступ разработчиков только к разрешенным кластерам и пространствам имен, обеспечивая изоляцию.
*   **Скорость:** Автоматическая подготовка (provisioning) ресурсов Argo CD при появлении новых манифестов в Git ускоряет цикл доставки (Time-to-Market).

## Стратегии продвижения (Promotion Strategies)

Продвижение изменений между окружениями (Dev -> Staging -> Prod) — это процесс перемещения версии приложения через цепочку проверок. Типовой рабочий процесс включает:

1.  **Feature Branch:** Внесение изменений в код и манифесты в отдельной ветке.
2.  **Тестирование и Merge:** Слияние в основную ветку после успешных тестов и Code Review.
3.  **Авто-деплой в Dev:** Argo CD обнаруживает изменения и автоматически обновляет среду разработки.
4.  **Продвижение в Staging/Prod:** После подтверждения стабильности в Dev, конфигурация Argo CD обновляется (через ветки или теги) для указания на новую версию в следующих средах.
5.  **Контроль версий:** Гарантия того, что в каждой среде развернута именно та версия, которая была протестирована на предыдущем этапе.
6.  **Простой откат:** Возврат конфигурации приложения к предыдущей версии (commit/tag) в Git немедленно инициирует синхронизацию кластера к стабильному состоянию.

**Поддержка веток и тегов:** Argo CD нативно поддерживает работу с различными ревизиями Git, что делает процесс продвижения прозрачным и управляемым.

### Сценарий 8: Аварийное восстановление (Disaster Recovery)

GitOps обеспечивает надежный механизм восстановления кластеров с нуля (Zero-touch Recovery).
*   **Процесс:** Подготовка нового кластера через IaC -> Установка Argo CD -> Подключение к Git-репозиториям -> Автоматическая синхронизация всех приложений и аддонов.
*   **Требования:** Высокая доступность Git-сервера, использование внешних хранилищ секретов (ESO/Vault) и регулярное тестирование процедуры восстановления (Game Days).

### Сценарий 9: Мультикластерное управление (Multi-cluster)

Централизованное управление развертываниями во множестве кластеров из одного экземпляра Argo CD.
*   **Региональное распределение:** Развертывание идентичных копий приложения в разных географических регионах для минимизации задержек.
*   **Компонентное распределение:** Разнос частей одного приложения (например, фронтенд и бэкенд) по разным кластерам в целях безопасности или оптимизации ресурсов.

## Вопросы для собеседования

### Опишите план аварийного восстановления на базе GitOps для кластера EKS

1.  **IaC:** Использование Terraform/OpenTofu для воссоздания VPC, кластера EKS и необходимых облачных ресурсов.
2.  **Bootstrapping:** Автоматическая установка Argo CD (например, через Helm) сразу после готовности кластера.
3.  **Синхронизация:** Подключение Argo CD к «инфраструктурному» репозиторию, который содержит описания аддонов и приложений.
4.  **Секреты и данные:** ESO восстанавливает секреты из внешнего KMS. Данные Persistent Volumes восстанавливаются из снимков (snapshots) или бэкапов внешних баз данных.
5.  **Верификация:** Проверка работоспособности по заранее подготовленному Runbook.

### Что такое AppProject и как он обеспечивает мультитенантность?

**AppProject** — это Custom Resource в Argo CD, который создает логическую границу для приложений и команд. Он обеспечивает мультитенантность через следующие ограничения:
1.  **Источник (Source):** Список разрешенных Git-репозиториев.
2.  **Назначение (Destination):** Разрешенные кластеры и пространства имен для деплоя.
3.  **Типы ресурсов:** Ограничение на создание определенных объектов (например, запрет на `ClusterRole` или `Namespace` для обычных приложений).
4.  **Ресурсные квоты:** Установка лимитов на потребление ресурсов внутри проекта.
5.  **Окна синхронизации (Sync Windows):** Ограничение времени, когда деплой разрешен (например, запрет на деплой в выходные).
6.  **RBAC:** Детальное управление правами доступа пользователей к ресурсам проекта в UI/CLI.

### Как Argo CD обнаруживает и применяет изменения после слияния в Git?

Это важный процессный вопрос для понимания механики GitOps:
1.  **Обнаружение (Detection):** После слияния PR Argo CD либо получает **Webhook** от Git-сервера, либо обнаруживает новый коммит в ходе периодического опроса (**Polling**).
2.  **Генерация манифестов:** Сервер API запрашивает у `argocd-repo-server` получение новой ревизии и рендеринг манифестов (Helm, Kustomize или YAML).
3.  **Сравнение (Diff):** `argocd-application-controller` сравнивает желаемое состояние из Git с фактическим состоянием в кластере.
4.  **Синхронизация (Sync):** Если состояния различаются и включена автосинхронизация (`Automated Sync`), контроллер применяет изменения в кластер, соблюдая **Sync Waves** и **Hooks**. 
    *   При включенном `SelfHeal` он также перезапишет ручные правки в кластере.
    *   При включенном `Prune` удалит лишние ресурсы.
5.  **Мониторинг (Health Checks):** После применения контроллер наблюдает за проверками работоспособности ресурсов. Приложение считается синхронизированным только при достижении статуса `Healthy`. При сбоях выполняется повторная попытка с отложенным интервалом (**Backoff**).

### Почему Pull-модель предпочтительнее Push-модели?

1.  **Безопасность (Security):** Кластер не требует входящих соединений извне. Учетные данные для доступа к API Kubernetes не покидают периметр кластера и не хранятся в CI-системе.
2.  **Аудит и логирование:** GitOps-агенты (ArgoCD, Flux) логируют все свои действия внутри кластера, обеспечивая дополнительный слой прослеживаемости помимо истории Git. Агенты ведут детальные журналы применения каждой конфигурации.
3.  **Масштабируемость:** Агенты локально согласовывают состояние, используя механизмы отложенных повторов (backoff) и очередей (retries), что снижает нагрузку на центральную CI-систему при управлении сотнями кластеров.
4.  **Устойчивость к сбоям:** Даже если Git или CI временно недоступны, агент внутри кластера продолжает поддерживать текущее состояние и автоматически синхронизируется, как только связь восстановится.

### 4 фундаментальных принципа GitOps

1.  **Декларативность:** Описание желаемого состояния, а не шагов.
2.  **Версионируемость:** Хранение состояния в неизменяемом хранилище (Git).
3.  **Автоматическая сверка:** Программные агенты для доставки изменений.
4.  **Непрерывное обнаружение отклонений:** Постоянный мониторинг и устранение дрейфа.

### Как реализовать Canary-развертывание с помощью Argo Rollouts и Argo CD?

1.  **Определение ресурса Rollout:** Заменяем стандартный `Deployment` на `Rollout`, указывая шаги (steps) и стратегию канарейки.
2.  **Маршрутизация:** Настройка Ingress или Service Mesh (Istio, Linkerd) для управления долями трафика.
3.  **Анализ метрик:** Использование `AnalysisTemplates` для автоматической проверки здоровья (Prometheus/Grafana) на каждом шаге.
4.  **Синхронизация:** Argo CD применяет `Rollout` как любой другой CRD. Если анализ метрик провален, Argo Rollouts выполняет **автоматический откат**, а Argo CD фиксирует статус `Degraded`.
