# GitOps: обзор методологии

## Определения

**GitOps** — это методология управления инфраструктурой и приложениями, при которой Git-репозиторий является основным и единственным источником конфигурации для всей декларативной среды. Основная цель — автоматизация, версионирование и прослеживаемость изменений с использованием Git как надежной базы, что обеспечивает быструю, надежную и полностью проверяемую (auditable) доставку программного обеспечения.

В рамках GitOps любые изменения в состоянии системы — будь то параметры приложения, описание инфраструктуры или политики безопасности — производятся исключительно через коммиты в Git-репозиторий.

Ключевые термины, используемые далее:

| Термин | Определение |
| :--- | :--- |
| **Желаемое состояние (Desired State)** | Полное декларативное описание системы, хранящееся в Git (или OCI-реестре). Единственный авторитетный источник правды (SSoT). |
| **Фактическое состояние (Actual State)** | Реальное состояние объектов в кластере, наблюдаемое через Kubernetes API. |
| **Реконсиляция (Reconciliation)** | Цикл сверки желаемого и фактического состояния с автоматическим применением недостающих изменений. |
| **Дрейф (Drift)** | Расхождение между фактическим состоянием кластера и описанием в Git (ручные правки, аварийные изменения, действия других контроллеров). |
| **GitOps-контроллер (агент)** | Программный агент внутри кластера (ArgoCD, Flux), выполняющий непрерывную реконсиляцию. |
| **SSoT (Single Source of Truth)** | Принцип единого источника правды: конфигурация существует в одном каноническом месте — Git. |

## Эволюция подхода

GitOps не появился в вакууме, а стал результатом развития инструментов автоматизации:

1.  **Системы управления конфигурациями (Ansible, Puppet, Chef):** Позволили настраивать инфраструктуру внутри виртуальных машин с помощью кода, обеспечивая повторяемость настроек.
2.  **Инфраструктура как код (IaC) (Terraform, CloudFormation):** Сделали возможным создание облачных ресурсов и сетей с помощью кода. Git стал стандартным хранилищем для этих конфигураций.
3.  **GitOps (2017+):** Применил принципы IaC к управлению не только инфраструктурой, но и приложениями, используя Git как активный элемент системы доставки, а не просто хранилище манифестов.
4.  **Формализация стандартов (2021+):** Рабочая группа CNCF выпустила спецификацию [OpenGitOps Principles v1.0.0](https://github.com/open-gitops/documents/blob/main/PRINCIPLES.md) — вендор-нейтральное определение методологии, позволяющее оценивать соответствие инструментов (ArgoCD, Flux, Fleet) формальным критериям.

**GitOps и Kubernetes:** Появление Kubernetes стало катализатором GitOps. Его декларативная природа и встроенные циклы согласования (Reconciliation Loops) идеально подошли для реализации GitOps-принципов, сделав этот подход основным для доставки приложений в современные кластеры.

## Базовые концепции

### Модели доставки: Push против Pull

Это фундаментальное различие в архитектуре систем CD (Continuous Delivery). В контексте GitOps доминирует Pull-модель, но понимание обеих необходимо для правильного проектирования системы.

| Критерий | Push-модель (Традиционная) | Pull-модель (GitOps) |
| :--- | :--- | :--- |
| **Механизм** | Внешняя система (CI-сервер) инициирует соединение с кластером. | Агент внутри кластера опрашивает внешний источник (Git). |
| **Безопасность** | Ключи доступа к кластеру хранятся в CI-системе (риск компрометации). | Ключи не покидают кластер. Агент использует внутренний RBAC. |
| **Сетевой доступ** | Требуется входящий доступ к API-серверу Kubernetes извне. | Кластеру нужен только исходящий доступ к Git/OCI. |
| **Детекция дрейфа** | Происходит только в момент запуска пайплайна. | Непрерывная сверка в реальном времени. |
| **Масштабируемость** | CI-сервер может стать узким местом при сотнях кластеров. | Каждый кластер синхронизируется автономно. |
| **Инструменты** | GitLab CI, GitHub Actions, Jenkins, Ansible. | ArgoCD, Flux, Fleet. |

**Глубокое погружение в Pull-модель:**
В Pull-модели агент (контроллер) выполняет бесконечный цикл: `Считать Git -> Считать состояние кластера -> Вычислить Diff -> Применить изменения`. Это гарантирует, что кластер всегда стремится к состоянию, описанному в Git, даже если изменения в репозиторий не вносились (например, при попытке ручного исправления в кластере).

**Гибридные варианты на практике:**
- **Webhook + Poll:** Webhook от Git-сервера ускоряет реакцию (событие приходит мгновенно), но периодический опрос остается обязательным механизмом — триггеры не могут быть единственным способом синхронизации (требование OpenGitOps «Pulled Automatically»). Если webhook потерян (сбой сети, ошибка конфигурации), опрос все равно обнаружит новый коммит: у ArgoCD это `timeout.reconciliation` (по умолчанию 180 секунд), у Flux — `spec.interval` (по умолчанию 1 минута).
- **Push-GitOps через CI:** Пайплайн сам выполняет `kubectl apply` после рендеринга (Helm/Kustomize). Это быстрее внедряется, но теряет главные преимущества: непрерывную детекцию дрейфа и отсутствие креденшилов кластера в CI. Такой подход иногда называют «CI-driven deployment», а не полноценным GitOps.

### Ключевые принципы (OpenGitOps)

На техническом уровне GitOps строится на четырех фундаментальных принципах (спецификация OpenGitOps v1.0.0):

1.  **Декларативность (Declarative):** Вся система описывается декларативно — вы указываете желаемое состояние, а не шаги по его достижению. Это создает четкое определение целевого состояния.
2.  **Версионируемость и неизменяемость (Versioned and Immutable):** Желаемое состояние хранится в Git. Любое изменение — это новая ревизия в истории коммитов, что обеспечивает «машину времени» для всей инфраструктуры. Нюанс: ссылка на плавающий тег (`latest`) фактически нарушает этот принцип — откат становится невозможен, поскольку ревизия не фиксируется.
3.  **Автоматическое применение через Pull (Pulled Automatically):** Как только одобренное состояние зафиксировано в Git, оно автоматически применяется программными агентами, которые сами извлекают состояние из источника. Человек не должен использовать императивные команды (`kubectl apply`) в production. Нюанс: вебхуки допустимы как ускоритель, но не как единственный триггер.
4.  **Непрерывная сверка (Continuously Reconciled):** Программные агенты постоянно сравнивают фактическое состояние с желаемым и приводят систему к нему. Это обеспечивает автоматическое устранение отклонений без участия оператора.

Спецификация является частью проекта [OpenGitOps](https://opengitops.dev/) (CNCF Sandbox) и сопровождается глоссарием терминов.

### Детекция и устранение дрейфа (Drift Detection)

Дрейф — это расхождение между желаемым (Git) и фактическим (Cluster) состоянием.
*   **Статус OutOfSync:** Ресурс помечается контроллером как расходящийся с эталоном.
*   **Self-healing (Самовосстановление):** Механизм, при котором контроллер автоматически перезаписывает ручные правки в кластере, возвращая систему к состоянию в Git.
*   **Pruning:** Автоматическое удаление ресурсов из кластера, если они были удалены из Git-репозитория.

**Источники дрейфа и как с ними работать:**

| Источник | Пример | Корректное решение |
| :--- | :--- | :--- |
| **Человеческий фактор** | `kubectl edit`, `kubectl scale` в обход Git | Self-healing перезапишет правку; доступ к кластеру ограничивается RBAC |
| **«Легитимный дрейф»** | HPA меняет `spec.replicas`; мутационные вебхуки добавляют поля (sidecar injection) | Исключить поле из сверки: ArgoCD `ignoreDifferences`, Flux `.spec.ignore` — иначе контроллер и другой компонент будут бесконечно конфликтовать |
| **Императивные операции** | Автоматические миграции, job'ы, создающие объекты | Перенести создание объекта в Git либо исключить его из области управления контроллера |

Процесс разбора инцидентов дрейфа и журналирование ручных изменений описаны в [GitOps: Журналы аудита](./Concepts/audit_logs.md). Механика трёхстороннего согласования (3-way merge), из-за которой ручные правки «прилипают» к объектам и не видны в Git, и спираль страха автоматизации разобраны в [декомпозиции GitOps](./Concepts/gitops_decomposition.md#трёхстороннее-согласование-3-way-merge).

### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- |
| **Надежность:** Возможность быстрого отката всей системы через `git revert`. | **Управление секретами:** Требует специальных инструментов шифрования (SOPS, ESO). |
| **Автоматизация дрейфа:** Гарантия соответствия реальности коду. | **Зависимость от Git:** Недоступность VCS блокирует изменения. |
| **Прозрачность и аудит:** Полная история изменений через Pull/Merge Requests. | **Строгий регламент:** Даже мелкие правки требуют коммита и ревью. |
| **Безопасность:** Сокращение прямых доступов сотрудников к кластеру. | **Сложность отладки:** Труднее отслеживать промежуточные состояния рендеринга. |
| **Self-service:** Разработчики управляют ресурсами через знакомый Git. | **Версионирование:** Требует жесткой дисциплины тегирования образов. |

Замечание к недостатку «сложность отладки»: проблема решается паттерном «Rendered Manifests» (см. раздел [Стратегии продвижения](#стратегии-продвижения-promotion-strategies)) — финальные манифесты сохраняются в Git или OCI до применения, и то, что видит ревьюер, совпадает с тем, что попадет в кластер.

## Неизменяемая инфраструктура (Immutable Infrastructure)

Неизменяемая инфраструктура — краеугольный камень GitOps. Компоненты полностью заменяются при каждом развертывании, а не обновляются «на лету».

*   **Роль контейнеризации:** Контейнеры упаковывают приложения в неизменяемые образы. Новая версия — это новый образ, а не патч старого.
*   **Снижение дрейфа:** Поскольку работающая инфраструктура не меняется вручную, вероятность расхождения конфигураций между узлами сводится к минимуму.
*   **Надежный откат:** Откат заключается в простой замене текущего тега образа на предыдущий проверенный в манифесте Git.

Практическое следствие: в GitOps идентификатором версии приложения служит **digest образа** (неизменяемый хеш), а не тег, который может быть перезаписан. Подробнее — в [жизненном цикле образов](./Concepts/containerization_and_image_storage.md).

## Внедрение и рабочие процессы

### Шаги настройки (Workflow Setup)

1.  **Инициализация репозитория:** Создание Git-репозитория для манифестов и конфигураций.
2.  **Интеграция CI:** Настройка пайплайнов для автоматической валидации манифестов (`kubeconform`, `lint`) и сборки образов.
3.  **Развертывание GitOps-оператора:** Установка ArgoCD или Flux внутри кластера.
4.  **Настройка Webhooks:** Конфигурация уведомлений от Git-сервера к оператору для мгновенного запуска синхронизации (ускоряет детекцию коммитов).
5.  **Мониторинг и оповещение:** Настройка алертинга на статусы синхронизации и ошибки реконсиляции.

Конкретизация каждого шага:

| Шаг | Команды / инструменты | Результат |
| :--- | :--- | :--- |
| 1. Репозиторий | `git init` + структура каталогов (см. ниже), защита ветки `main` | Пустой инфраструктурный репозиторий с branch protection |
| 2. CI | `kubeconform`, `conftest`, `kube-score`, сборка и пуш образа с digest | Пайплайн блокирует некорректные манифесты до мерджа |
| 3. Оператор | Flux: `flux bootstrap github --owner=my-org --repository=fleet-infra`; ArgoCD: `helm install argocd argo/argo-cd` или декларативно | Контроллер работает, корневой объект указывает на репозиторий |
| 4. Webhooks | Flux Receiver / ArgoCD webhook-секрет в настройках Git-форджа | Синхронизация стартует за секунды после мерджа |
| 5. Наблюдаемость | Экспорт метрик контроллера в Prometheus; алерты на `OutOfSync`, `Degraded`, неудачные реконсиляции | Дежурные узнают о проблеме раньше пользователей |

Подробное руководство по установке Flux — в [Flux: обзор](./flux.md), ArgoCD — в [ArgoCD: установка и настройка](./ArgoCD/argocd_installation_and_setup.md). Сквозной пример конвейера — в [примере GitOps-пайплайна](./gitops_pipeline_example.md).

### Структура репозиториев (Repo Patterns)

| Модель | Плюсы | Минусы |
| :--- | :--- | :--- |
| **Монорепозиторий** | Общий инструментарий, атомарные изменения. | Большой объем CI-задач, сложность RBAC. |
| **Мультирепозиторий** | Изоляция команд, автономность, четкие границы. | Сложность координации кросс-сервисных правок. |

**Рекомендация:** Использование отдельных репозиториев для кода приложений и выделенного централизованного репозитория для инфраструктурных манифестов (Infrastructure Repo).

Типовая структура инфраструктурного репозитория (Kustomize overlays):

```text
fleet-infra/
├── apps/                      # Приложения (по командам или сервисам)
│   └── web-app/
│       ├── base/              # Общие манифесты (Deployment, Service)
│       └── overlays/
│           ├── dev/           # kustomization.yaml с патчами окружения
│           ├── staging/
│           └── prod/
├── platform/                  # Системные аддоны (Ingress, Monitoring, Cert-manager)
└── clusters/                  # Корневые Kustomization/Application на каждый кластер
    ├── dev-eu/
    └── prod-us/
```

Такая структура естественно поддерживает стратегию продвижения через overlays (см. ниже) и мультитенантность: права на каталоги регулируются CODEOWNERS и правилами веток.

### Организация репозиториев под Helm-чарты

При использовании Helm в GitOps возникает вопрос организации хранения чартов:

| Подход | Описание | Когда использовать |
| :--- | :--- | :--- |
| **Один репозиторий на все чарты** | Все чарты в одном репозитории (`charts/`). Версионирование через теги. | Небольшие команды, единый цикл релизов. |
| **Отдельный репозиторий на каждый чарт** | Каждый чарт — отдельный репозиторий с собственной версией. | Микросервисная архитектура, независимые релизы команд. |
| **Репозиторий чартов + OCI-реестр** | Чарты хранятся в Git (код) и публикуются в OCI-реестр (артефакты). | Production-среда, требуется стабильность и воспроизводимость. |

**Рекомендация:** Для production-сред рекомендуется использовать OCI-реестры (Docker Hub, Harbor, GHCR) как источник Helm-чартов в GitOps-контроллерах (ArgoCD, Flux). Это обеспечивает версионирование, быструю загрузку и единое хранилище для всех артефактов (образов и чартов). В Git хранится только код чартов, а собранные артефакты публикуются в OCI.

**Риск зависимости от внешних реестров:** политика публичного реестра может стать частью вашей production-архитектуры в один день — показательный пример: заморозка бесплатного каталога Bitnami компанией Broadcom (2025). Ответственная практика — зеркалирование используемых чартов и образов в собственный реестр (для Flux существует декларативный плагин Flux Mirror с проверкой подписей Cosign).

### Инструменты доставки приложений в Kubernetes

Основные инструменты для доставки приложений в Kubernetes в парадигме GitOps:

| Инструмент | Архитектура | Применение |
| :--- | :--- | :--- |
| **ArgoCD** | Централизованный оператор с UI | Визуальный контроль, мультикластерное управление |
| **Flux** | Набор независимых контроллеров (Unix-way) | Модульность, автоматизация через OCI, интеграция с инфраструктурой |
| **Fleet** | Масштабируемый контроллер от Rancher | Управление тысячами Edge-кластеров |

**Flux vs ArgoCD — когда использовать:**
- **Flux** предпочтителен, когда требуется модульность, независимое масштабирование компонентов, глубокая интеграция с OCI-реестрами и инфраструктурными инструментами (Terraform через TF-controller, Kustomize). Flux хорошо подходит для команд, практикующих «чистый» GitOps с минимальным UI-взаимодействием.
- **ArgoCD** предпочтителен, когда требуется визуальный контроль состояния кластеров, мультикластерное управление из одной точки, встроенный RBAC с SSO. ArgoCD удобен для команд, где важна визуализация расхождений (diff) и откатов.

Оба инструмента являются Graduated-проектами CNCF и соответствуют принципам OpenGitOps. Состояние экосистемы на текущий момент (версии, политика поддержки) — в разделе [Состояние экосистемы](#состояние-экосистемы-и-ключевые-тренды).

### Стратегии продвижения (Promotion Strategies)

Продвижение изменений между окружениями (Dev -> Staging -> Prod):

1.  **На базе веток (Branch-based):** Каждое окружение — ветка (`main`, `staging`, `develop`). Продвижение через Merge Requests. Риск дрейфа между ветками при долгих релизах.
2.  **На базе репозиториев (Repo-based):** Каждое окружение — отдельный репозиторий. Максимальная изоляция и безопасность доступа.
3.  **На базе тегов/ревизий:** Использование Kustomize overlays в одном репозитории, где версии фиксируются в конкретных файлах для каждой среды.

Автоматизация продвижения новых версий образов: ArgoCD Image Updater (обновляет теги в Git по политикам), встроенная Image Automation во Flux (ImageRepository/ImagePolicy/ImageUpdateAutomation), Renovate (PR-бот обновлений образов, чартов и зависимостей с ревью и гейтами — [детальный разбор](./Concepts/renovate_dependency_updates.md)), Kargo (полноценные promotion-пайплайны с этапами верификации).

### Паттерн «Rendered Manifests» (рендеринг до кластера)

Отдельная практика продвижения, закрывающая главный недостаток GitOps — непрозрачность промежуточного рендеринга: вместо того чтобы позволять контроллеру рендерить Helm/Kustomize в момент синхронизации, финальные манифесты рендерятся заранее и сохраняются в неизменяемом виде в Git или OCI-реестре. То, что проходит ревью в PR, в точности соответствует тому, что будет применено в кластере.

Четыре реализации паттерна (от простой к полной):

| Подход | Механика | Особенности |
| :--- | :--- | :--- |
| **CI-рендеринг** | Пайплайн рендерит манифесты и коммитит их в ветку окружения | Не требует изменений в контроллере; логика живет в CI |
| **Argo CD Source Hydrator** | Встроенный механизм (beta с v3.5): `drySource` (шаблоны) → гидратация → `syncSource` (ветка с готовыми манифестами); поддерживает разные репозитории и паттерн `hydrateTo` — промоушен через PR | Декларативная настройка в Application CR; не решает отслеживание образов |
| **Kargo** | Специализированный инструмент promotion: Warehouse следит за новыми артефактами, Stage описывают этапы продвижения с верификацией | Полноценные пайплайны промоушена между окружениями |
| **OCI-артефакты** | Отрендеренные манифесты публикуются как OCI-артефакт (`flux push artifact`, нативная поддержка OCI-источников в Argo CD с v3.1) | Неизменяемость digest'ов, нативная подпись (Cosign), удобно для air-gapped |

Компромиссы: Git-ветки удобнее для `git diff` между окружениями; OCI выигрывает в неизменяемости и безопасности цепочки поставок. Многие команды комбинируют оба способа.

## Управление манифестами

### Helm против Kustomize в GitOps

Это ключевой архитектурный выбор при проектировании системы доставки:

*   **Helm:** Пакетный менеджер с мощной шаблонизацией. Идеален для вендорских приложений.
    *   *Совет:* Всегда фиксируйте версии чартов (`version pinning`) для детерминированности.
    *   *Подробности:* синтаксис чартов и структура — в [структуре Helm-чартов](../Kubernetes/ToolsUtilities/Helm/helm_chart_structure.md), library charts и зависимости — в [соответствующем разделе Helm](../Kubernetes/ToolsUtilities/Helm/helm_dependencies_and_library_charts.md).
*   **Kustomize:** Инструмент композиции YAML через базы (bases) и наложения (overlays). Прост и нативен для K8s.
    *   *Совет:* Используйте overlays для специфичных настроек окружений, сохраняя базу неизменной.
    *   *Подробности:* механика наложений и патчей разобрана в [Kustomize: наложения и патчи](../Kubernetes/ToolsUtilities/kustomize/kustomize_overlays_and_patches.md).

**Комбинированный подход:** Использование Helm для генерации манифестов и Kustomize для точечных патчей поверх результата. Оба контроллера поддерживают его нативно: ArgoCD — через несколько источников или плагины, Flux — через поле `postBuild` в Kustomization поверх HelmRelease.

### Валидация и тестирование

Для предотвращения деплоя некорректных конфигураций в CI встраиваются:
*   **Схематическая проверка:** `kubeconform` для проверки соответствия Kubernetes API.
*   **Политики (Policy as Code):** `conftest` или `kyverno` для проверки соответствия стандартам безопасности (например, отсутствие запуска от root).
*   **Static Analysis:** `kube-score` для проверки лимитов ресурсов и проб (probes).

Пример стадии проверки в CI-пайплайне:

```yaml
# .gitlab-ci.yml (фрагмент стадии валидации манифестов)
manifest-validate:
  stage: test
  script:
    - kustomize build overlays/prod > rendered.yaml
    - kubeconform -strict -summary rendered.yaml          # Схемы Kubernetes API
    - conftest test --policy policies/ rendered.yaml      # Rego: запрет :latest, обязательные limits
    - kube-score score rendered.yaml                      # Лимиты, probes, анти-аффинити
```

Runtime-контроль (Kyverno/Gatekeeper в кластере) дополняет CI-валидацию — см. [управление политиками через GitOps](./Concepts/gitops-policy-management.md).

## Прогрессивная доставка (Progressive Delivery)

GitOps отлично сочетается со стратегиями постепенного выпуска:

*   **Canary-выпуски:** Постепенное переключение трафика (1% -> 10% -> 50% -> 100%) на новую версию.
*   **Blue/Green:** Создание новой версии рядом со старой и мгновенное переключение трафика.
*   **Argo Rollouts:** Контроллер, позволяющий описывать шаги канареечного развертывания и автоматически анализировать метрики (Prometheus) для принятия решения о продолжении деплоя.
*   **Flagger:** Контроллер прогрессивной доставки из экосистемы Flux: управляет канареечными релизами поверх обычного Deployment, автоматически создает канареечные ресурсы, переключает трафик через Ingress/service mesh (Nginx, Istio, Gateway API) и откатывает релиз при деградации SLI. Работает в связке и с ArgoCD, и с Flux.

Ключевой момент интеграции с GitOps: контроллер прогрессивной доставки получает новую версию из Git через обычную синхронизацию (обновление тега образа в манифесте `Rollout`/`Deployment`), а дальнейшее переключение трафика выполняется им автономно. Состояние процесса отражается в статусе ресурса и алертах. Рабочие конфигурации обоих контроллеров, кастомные health-check'и и ручные гейты — в [Прогрессивной доставке в GitOps](./Concepts/progressive_delivery_gitops.md). Разделение deploy и release через фиче-флаги — ортогональный механизм управления рисками: [Feature Flags в GitOps](./Concepts/feature_flags_gitops.md).

## Состояние экосистемы и ключевые тренды

Актуальные версии основных инструментов (август 2026):

| Проект | Актуальная ветка | Последний релиз | Политика поддержки |
| :--- | :--- | :--- | :--- |
| **Argo CD** | 3.5 | 3.5.1 (август 2026) | Патчи для трех последних минорных веток (3.3–3.5); ветки 2.x полностью EOL |
| **Flux** | 2.9 | 2.9.4 (август 2026) | Три последние минорные ветки; устаревшие API удаляются из CRD (миграция `flux migrate`) |

Ключевые тренды, влияющие на проектирование GitOps-систем:

1.  **OCI как канал доставки («Gitless GitOps»):** желаемое состояние путешествует как OCI-артефакты (`OCIRepository` во Flux, нативный OCI-источник в Argo CD с v3.1). Git остается местом совместной работы людей, реестр — интерфейсом доставки: единая модель транспорта, подписи и зеркалирования для образов, чартов и манифестов.
2.  **Безопасность цепочки поставок внутри контроллеров:** Argo CD 3.5 добавил Source Integrity (блокировку синхронизации неподписанных GPG-подписью коммитов) и взаимный mTLS между внутренними компонентами; Flux развивает зеркалирование артефактов с верификацией подписей Cosign, проверкой provenance и минимальным возрастом подписи («supply-chain diode» — задержка свежих артефактов до окончания окна активных атак).
3.  **Rendered Manifests Pattern** (описан выше) переходит из практики энтузиастов в стандартные функции инструментов (Source Hydrator, Kargo, OCI).
4.  **Мультитенантность на уровне серверных операций:** impersonation в Argo CD (beta с 3.5) — все операции сервера выполняются от имени пользователя, запросившего действие, что упрощает аудит в общих кластерах.
5.  **Поддержка Helm 4** в Argo CD 3.5 при обратной совместимости с чартами Helm 3.

## Практические сценарии

### Сценарий 1: Выбор GitOps-инструмента

| Критерий | ArgoCD | Flux | Fleet |
| :--- | :--- | :--- | :--- |
| **Интерфейс** | Веб-UI + CLI. Отличная визуализация. | CLI-only. Модульный подход. | Rancher UI + CLI. |
| **Подход** | Монолитный оператор. | Набор специализированных контроллеров. | Масштабируемый контроллер. |
| **Когда использовать** | Визуальный контроль, мультикластер. | Unix-way, автоматизация через OCI. | Управление тысячами Edge-кластеров. |

Практическая проверка перед выбором: разверните оба инструмента в тестовом кластере и сравните на своих сценариях — готовые наборы манифестов для сравнения есть в [ArgoCD vs Flux: манифесты](./argo_vs_flux_manifests.md).

### Сценарий 2: Инфраструктурный GitOps

Принципы GitOps применимы к инфраструктуре через IaC:
* **Crossplane:** Управление облачными ресурсами (RDS, S3) через Kubernetes API. Git — источник правды для всего облака.
* **Terraform-контроллеры:** Использование Flux TF-controller для выполнения Terraform-планов внутри кластера на основе изменений в Git.

Рабочее сочетание двух уровней: приложение и его инфраструктурные зависимости (БД, очередь, бакет) объявляются декларативно и попадают в кластер одним коммитом — GitOps-контроллер доставляет манифесты, Crossplane создает облачные ресурсы. Пошаговые инструкции — в [Crossplane: интеграция с GitOps](./Crossplane/gitops_integration.md).

### Сценарий 3: Monitoring as Code (MaC)

Управление ресурсами мониторинга через GitOps.
* **Grafana:** Хранение дашбордов в Git, упаковка в ConfigMap и автоматическая синхронизация через Sidecar.
* **Alertmanager:** Декларативное описание правил маршрутизации алертов в Git.

Пример подключения дашборда через sidecar-паттерн:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-dashboard
  labels:
    grafana_dashboard: "1"   # Sidecar grafana обнаруживает метку и загружает дашборд
data:
  app-dashboard.json: |
    { /* JSON дашборда */ }
```

Тот же принцип применяется к PrometheusRule (правила алертинга) — правила живут в Git и доставляются контроллером вместе с остальными манифестами.

### Сценарий 4: Управление и безопасность (Governance)

Политики безопасности внедряются на этапе GitOps-цикла:
* **Валидация:** Проверка YAML в CI через `kubeconform` или `conftest`.
* **Runtime:** Использование Kyverno для контроля ресурсов, развернутых через GitOps (например, обязательное наличие меток).

Эшелонированная схема governance: pre-commit hooks -> CI-политики -> admission-контроль в кластере -> аудит. Централизованное управление политиками для всего флота кластеров — в [GitOps-мозге (policy brain)](./Concepts/gitops-policy-management.md).

### Сценарий 5: Управление секретами

Хранение секретов в Git требует особого подхода:

| Решение | Описание | Когда использовать |
| :--- | :--- | :--- |
| **Sealed Secrets** | Асимметричное шифрование. В Git попадает `SealedSecret`. | Малые проекты, отсутствие внешнего KMS. |
| **External Secrets (ESO)** | Синхронизация из внешних хранилищ (Vault, AWS SM). | Enterprise-стандарт, безопасность данных. |
| **SOPS** | Шифрование полей в YAML через KMS/age. | Локальное управление, гибкость ключей. |

Пример декларативного запроса секрета из Vault через ESO (в Git попадают только ссылки):

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: db-credentials
  data:
    - secretKey: password
      remoteRef:
        key: secret/data/app/db
        property: password
```

Сравнение решений, схемы шифрования и типовые ошибки — в [управлении секретами в GitOps](./secrets_encryption.md).

### Сценарий 6: Загрузка кластера (Cluster Bootstrapping)

Автоматизация развертывания системных аддонов:
* **ApplicationSet:** Генераторы (Git, Cluster) позволяют ArgoCD автоматически обнаруживать новые кластеры и устанавливать в них базовый стек (Ingress, Monitoring).
* **Группировка:** Использование меток кластеров для таргетирования специфичных конфигураций.

Пример ApplicationSet с генератором кластеров:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: platform-stack
  namespace: argocd
spec:
  generators:
    - clusters: {}              # Автоматически обнаруживает зарегистрированные кластеры
  template:
    metadata:
      name: '{{name}}-platform'
    spec:
      project: platform
      source:
        repoURL: https://github.com/my-org/fleet-infra.git
        targetRevision: main
        path: 'platform/{{metadata.labels.env}}'   # Маршрутизация по метке кластера
      destination:
        server: '{{server}}'
        namespace: platform
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

Эквивалент во Flux: команда `flux bootstrap` устанавливает контроллеры и корневую Kustomization; дальнейшие аддоны подключаются обычными Kustomization/HelmRelease в репозитории. Новый кластер получает полный стек без единого ручного действия: создать кластер -> зарегистрировать -> реконсиляция доставит всё из Git.

### Сценарий 7: Самообслуживание для разработчиков (Self-service)

Разработчики управляют своими приложениями через PR в свои репозитории:
* **Автономия:** Разработчики контролируют манифесты без доступа к `kubectl`.
* **Изоляция:** `AppProject` в ArgoCD ограничивает доступ команд только к их неймспейсам.
* **Скорость:** Автоматический провижининг ресурсов при появлении манифестов в Git.

Во Flux аналогичную роль играет мультитенантность с impersonation (ServiceAccount на команду). Детали настройки изоляции — в [ArgoCD: мультитенантность](./ArgoCD/argocd_multi_tenancy.md).

### Сценарий 8: Аварийное восстановление (Disaster Recovery)

GitOps обеспечивает надежный механизм восстановления (Zero-touch Recovery):
* **Процесс:** Создание кластера через IaC -> Установка ArgoCD -> Подключение к Git -> Автоматическая синхронизация всех приложений и политик.
* **Преимущество:** Кластер восстанавливается в точности до последнего коммита.

Что GitOps НЕ восстанавливает автоматически — данные: Persistent Volumes требуют отдельной стратегии (снимки EBS/Velero, восстановление managed-БД из бэкапов). RTO/RPO планируются раздельно для состояния (быстро — из Git) и данных (по расписанию бэкапов). Разбор полного плана восстановления — в [ArgoCD: disaster recovery](./ArgoCD/argocd_disaster_recovery.md); процедура восстановления кластера под управлением Flux — в [сценарии 11 обзора Flux](./flux.md).

### Сценарий 9: Мультикластерное управление (Multi-cluster)

Централизованное управление из одного экземпляра ArgoCD:
* **Региональность:** Развертывание идентичных копий приложения в разных регионах.
* **Связность:** Управление связями между компонентами (Frontend в одном кластере, Backend в другом).

Распространенные топологии:

| Топология | Механика | Когда выбирать |
| :--- | :--- | :--- |
| **Hub-and-Spoke** | Один центральный ArgoCD регистрирует spoke-кластеры и рулит ими | До ~десятков кластеров, нужна единая точка контроля и UI |
| **Pull-per-cluster (Flux-style)** | Каждый кластер самостоятельно тянет свою конфигурацию из Git/OCI | Сотни кластеров, edge, требования автономности при потере связи |
| **Гибрид** | Hub распространяет базовые политики, кластеры добирают локальную специфику | Крупные флоты с региональными особенностями |

Детальный разбор — регистрация spoke-кластеров, изоляция fleet-репозитория, поэтапные раскатки и восстановление отдельного кластера парка — в [мульти-кластерных паттернах](./Concepts/multi_cluster_patterns.md).

## Вопросы для собеседования

### Опишите план аварийного восстановления на базе GitOps для кластера EKS
1.  **IaC:** Использование Terraform для воссоздания VPC и кластера EKS.
2.  **Bootstrapping:** Автоматическая установка ArgoCD (через Helm) сразу после готовности кластера.
3.  **Синхронизация:** Подключение ArgoCD к инфраструктурному репозиторию (Root App).
4.  **Секреты:** ESO восстанавливает секреты из внешнего Vault/KMS.
5.  **Данные:** Восстановление Persistent Volumes из снимков (EBS Snapshots).

### Что такое AppProject и как он обеспечивает мультитенантность?
**AppProject** — это CRD в ArgoCD, создающий логическую границу для команд. Он ограничивает:
1.  **Source:** Разрешенные Git-репозитории.
2.  **Destination:** Разрешенные кластеры и пространства имен.
3.  **Resources:** Список разрешенных типов объектов (например, запрет на `ClusterRole`).
4.  **RBAC:** Права пользователей на действия в UI/CLI.
5.  **Sync Windows:** Временные окна, когда деплой разрешен.

### Как ArgoCD обнаруживает и применяет изменения после слияния в Git?
1.  **Обнаружение:** Через Webhook (мгновенно) или Polling (опрос репозитория каждые 3 минуты по умолчанию — параметр `timeout.reconciliation`).
2.  **Генерация:** `repo-server` извлекает ревизию и рендерит манифесты (Helm/Kustomize).
3.  **Diff:** Контроллер сравнивает желаемое состояние из Git с фактическим в кластере.
4.  **Sync:** Если включена автосинхронизация, контроллер применяет изменения, соблюдая `Sync Waves` и `Hooks`.
5.  **Health:** Контроллер следит за готовностью ресурсов (Health Checks).

### Почему Pull-модель предпочтительнее Push-модели?
1.  **Безопасность:** Кластер не требует входящих соединений. Секреты не выходят за периметр.
2.  **Аудит:** Агент ведет журналы применения каждой конфигурации внутри кластера.
3.  **Масштабируемость:** Снижение нагрузки на центральную CI-систему (каждый кластер тянет сам).
4.  **Устойчивость:** Агент продолжает поддерживать состояние, даже если связь с Git временно потеряна.

### Назовите 4 фундаментальных принципа GitOps
1.  **Декларативность:** Описание *что*, а не *как*.
2.  **Версионируемость:** Хранение в неизменяемом хранилище (Git).
3.  **Автоматическая сверка:** Агенты для доставки изменений.
4.  **Непрерывность:** Постоянный мониторинг и устранение дрейфа.

### Как реализовать Canary-развертывание через GitOps?
Используется **Argo Rollouts** в связке с ArgoCD.
1. Замена `Deployment` на `Rollout` с описанием шагов (steps).
2. Настройка Ingress (Nginx, Istio) для управления трафиком.
3. Определение `AnalysisTemplates` для проверки метрик (Prometheus) во время деплоя.
4. ArgoCD доставляет ресурс `Rollout`, а контроллер Rollouts управляет процессом переключения трафика и откатом при ошибках.

Альтернатива — **Flagger**: работает поверх обычного `Deployment`, не требует смены типа ресурса, интегрируется как с ArgoCD, так и с Flux, и сам создает канареечные копии, управляя трафиком через service mesh или Ingress.
