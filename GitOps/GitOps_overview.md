# GitOps: Обзор Методологии

## Определения

**GitOps** — это методология управления инфраструктурой и приложениями, при которой Git-репозиторий является единственным источником истины для всей декларативной конфигурации. Основная цель — автоматизация и упрощение развертывания и эксплуатации систем, в первую очередь в Kubernetes.

В рамках GitOps любые изменения в состоянии системы — будь то конфигурация приложения, обновление инфраструктуры или политики безопасности — производятся через коммиты в Git-репозиторий.

## Базовые концепции

### Модели развертывания

Существует две основные модели развертывания в **CI/CD**:

* **Push Model (Традиционный CI/CD):** Внешние системы (GitLab CI, Jenkins) инициируют изменения и "проталкивают" их в кластер. У этих систем должны быть прямые доступы к среде исполнения.
* **Pull Model (GitOps):** Оператор, установленный внутри кластера (например, ArgoCD), непрерывно отслеживает ("pull") состояние Git-репозитория и самостоятельно приводит кластер в соответствие с ним. Эта модель считается более безопасной, так как учетные данные для доступа к кластеру не выходят за его пределы.

**Подробнее:** [Стратегии развертывания](../CI-CD/Core_Concepts/deployment_strategies.md#основные-концепции).

### Ключевые принципы (OpenGitOps)

1. **Декларативность:** Желаемое состояние системы должно быть описано декларативно.
2. **Версионируемость и неизменяемость:** Состояние хранится в Git, обеспечивая полную историю изменений и возможность аудита.
3. **Автоматическое получение (Pulled Automatically):** Программные агенты автоматически извлекают декларативное описание состояния из источника.
4. **Непрерывная сверка (Continuous Reconciliation):** Программные агенты непрерывно отслеживают расхождения между желаемым и реальным состоянием и принимают меры по их устранению.

### Детекция дрейфа (Drift Detection)

Одной из ключевых особенностей GitOps является способность контроллера обнаруживать расхождения (дрейф) между желаемым и фактическим состоянием системы. 
* Если ресурс изменен вручную (например, через `kubectl edit`), GitOps-оператор пометит его как `OutOfSync`.
* В зависимости от настроек (Self-healing), оператор автоматически перезапишет ручные изменения, возвращая систему к состоянию, описанному в Git.

### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- |
| **Надежность и предсказуемость:** Возможность быстрого отката и восстановления всей системы из Git. | **Управление секретами:** Хранение секретов в Git требует специальных инструментов для шифрования, таких как [SOPS](../Security/Tools/sops_overview.md) или интеграции с [Vault](../Vault/overview.md). |
| **Автоматическое устранение дрейфа:** Гарантия того, что реальное состояние всегда соответствует описанному в коде. | **Зависимость от Git:** Недоступность Git-сервера может заблокировать любые изменения в системе. |
| **Прозрачность и аудит:** Полная история всех изменений, их авторов и ревьюверов через Pull/Merge Requests. | **Строгий регламент:** Все изменения, даже срочные, должны производиться через Git, что может замедлить реакцию в экстренных ситуациях. |
| **Повышенная безопасность:** Сокращение прямых доступов к кластеру («No kubectl access in prod»). | **Динамические окружения:** Создание временных окружений может потребовать сложной автоматизации подготовки конфигурации в Git. |
| **Консистентность окружений:** Гарантия идентичности настроек dev, staging и production сред. | |

## Практические сценарии

### Сценарий 1: Выбор GitOps-инструмента

| Критерий | ArgoCD | Flux | Fleet |
| :--- | :--- | :--- | :--- |
| **Назначение** | CD для Kubernetes | CD для Kubernetes | Мультикластерный GitOps (Rancher) |
| **Интерфейс** | Веб-UI + CLI | CLI-only | Rancher UI + CLI |
| **Подход** | Монолитный оператор | Модульный toolkit | Масштабируемый контроллер |
| **Когда использовать** | Визуальный контроль, мультикластер | "Unix-way", автоматизация обновлений | Управление тысячами кластеров |

**Подробнее:** [ArgoCD](./ArgoCD/argocd_overview.md), [Flux](./flux.md), [сравнение ArgoCD и Flux](./argo_vs_flux_manifests.md).

### Сценарий 2: Инфраструктурный GitOps

Принципы GitOps применимы не только к приложениям, но и к инфраструктуре (**IaC**):
* **Crossplane:** Управление облачными ресурсами (AWS, GCP, Yandex Cloud) через Kubernetes API в GitOps-цикле. Подробнее: [Обзор Crossplane](./Crossplane/overview.md).
* **Terraform-контроллеры:** Использование Flux TF-controller для выполнения Terraform-планов на основе изменений в Git.

### Сценарий 3: Управление и безопасность (Governance)

GitOps позволяет внедрять политики безопасности на разных этапах:
* **Валидация манифестов:** Проверка YAML-файлов в CI через `kubeconform` или `conftest`.
* **Runtime-политики:** Использование **Kyverno** или **OPA** для контроля ресурсов, развернутых через GitOps.

### Сценарий 4: Управление секретами

Для хранения секретов в Git используются инструменты шифрования:
* **[SOPS](../Security/Tools/sops_overview.md)** — шифрование значений в YAML/JSON.
* **[Sealed Secrets](../Kubernetes/Security/sealed_secrets_overview.md)** — шифрование Kubernetes Secret для хранения в публичных репозиториях.
* **[Vault](../Vault/overview.md)** — внешнее хранилище, интегрируемое через External Secrets Operator.
