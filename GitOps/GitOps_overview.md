# GitOps: Обзор Методологии

## Определения

**GitOps** — это методология управления инфраструктурой и приложениями, при которой Git-репозиторий является **единственным источником истины** (Single Source of Truth) для всей декларативной конфигурации. Основная цель — автоматизация и упрощение развертывания и эксплуатации систем, в первую очередь в Kubernetes.

В рамках GitOps любые изменения в состоянии системы — будь то конфигурация приложения, обновление инфраструктуры или политики безопасности — производятся через коммиты в Git-репозиторий.

## Базовые концепции

### Модели развертывания

Существует две основные модели развертывания в CI/CD:

* **Push Model (Традиционный CI/CD):** Внешние системы (GitLab CI, Jenkins) инициируют изменения и "проталкивают" их в кластер. У этих систем должны быть прямые доступы к среде исполнения.
* **Pull Model (GitOps):** Оператор, установленный внутри кластера (например, ArgoCD), непрерывно отслеживает ("pull") состояние Git-репозитория и самостоятельно приводит кластер в соответствие с ним. Эта модель считается более безопасной, так как учетные данные для доступа к кластеру не выходят за его пределы.

**Подробнее:** [**Deployment Strategies**](../CI-CD/Core_Concepts/deployment_strategies.md#базовые-концепции).

### Ключевые принципы

1. **Декларативность:** Всё состояние системы должно быть описано декларативно в файлах конфигурации (например, YAML-манифесты Kubernetes), хранящихся в Git.
2. **Версионирование в Git:** Git является единственным источником истины. Вся история изменений, ревью кода (через Pull/Merge Requests) и аудит производятся с помощью стандартных механизмов Git.
3. **Автоматическая синхронизация:** Специальный агент (оператор) в кластере автоматически обеспечивает соответствие фактического состояния системы тому, что описано в Git.
4. **Самовосстановление (Self-Healing):** Агент непрерывно отслеживает расхождения между желаемым и реальным состоянием. Любые изменения, внесенные в обход Git, будут автоматически отменены и возвращены к состоянию, описанному в репозитории.

### Преимущества и недостатки

| Преимущества                                                                                              | Недостатки                                                                                                                                                                                           |
| :-------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Надежность и предсказуемость:** Возможность быстрого отката и восстановления всей системы из Git.         | **Управление секретами:** Хранение секретов в Git требует специальных инструментов для шифрования, таких как [SOPS](../Security/Tools/sops_overview.md) или интеграции с [Vault](../Vault/overview.md). |
| **Прозрачность и аудит:** Полная история всех изменений, их авторов и ревьюверов.                          | **Зависимость от Git:** Недоступность Git-сервера может заблокировать любые изменения в системе.                                                                                                |
| **Повышенная безопасность:** Сокращение прямых доступов к кластеру, все изменения проходят через ревью.     | **Строгий регламент:** Все изменения, даже срочные, должны производиться через Git, что может замедлить реакцию в экстренных ситуациях.                                                       |
| **Высокая скорость развертывания:** Автоматизация и унификация процессов ускоряют доставку изменений.       | **Динамические окружения:** Создание новых или временных окружений может потребовать ручной подготовки конфигурации в Git.                                                                       |
| **Консистентность окружений:** Гарантия того, что dev, staging и production окружения настроены идентично. |                                                                                                                                                                                                    |

## Практические сценарии

### Сценарий 1: Выбор GitOps-инструмента

| Критерий | ArgoCD | Flux | Crossplane |
| :--- | :--- | :--- | :--- |
| **Назначение** | CD для Kubernetes | CD для Kubernetes | IaC за пределами K8s |
| **Интерфейс** | Веб-UI + CLI | CLI-only | Kubernetes API |
| **Подход** | Монолитный оператор | Модульный toolkit | Расширение K8s API |
| **Когда использовать** | Визуальный контроль, мультикластер | "Unix-way", автоматизация | Управление облачной инфраструктурой |

**Подробнее:** [ArgoCD](./ArgoCD/argocd_overview.md), [Flux](./flux.md), [Crossplane](./Crossplane/overview.md).

### Сценарий 2: Типичный GitOps-пайплайн

1. **CI-этап:** Сборка Docker-образа, публикация в реестр с неизменяемым тегом (SemVer или digest).
2. **Обновление манифеста:** CI-пайплайн обновляет тег образа в Git-репозитории с манифестами.
3. **CD-этап:** GitOps-оператор обнаруживает изменения и синхронизирует кластер.

**Подробнее:** [Пример GitOps-пайплайна](./gitops_pipeline_example.md), [Образы контейнеров](./Concepts/containerization_and_image_storage.md).

### Сценарий 3: Управление секретами

Для хранения секретов в Git используются инструменты шифрования:

* **[SOPS](../Security/Tools/sops_overview.md)** — шифрование значений в YAML/JSON
* **[Sealed Secrets](../Kubernetes/Security/sealed_secrets_overview.md)** — шифрование Kubernetes Secret
* **[Vault](../Vault/overview.md)** — внешнее хранилище с динамическими секретами
