# GitOps: Пример пайплайна

> **Надежность: 10** (Подтверждено SSoT и практическими внедрениями на май 2026)

## Определения

**GitOps-пайплайн** — это конвейер доставки программного обеспечения, реализующий [GitOps-подход](./GitOps_overview.md), при котором система **CI (Continuous Integration — непрерывная интеграция)** отвечает за сборку артефактов, а система **CD (Continuous Delivery — непрерывная доставка)** декларативно управляет состоянием кластера на основе манифестов в Git.

## Базовые концепции

### Разделение ответственности

Пайплайн разделен на две независимые части с четкой границей ответственности:

1. **CI (Continuous Integration):** Проверка исходного кода, запуск тестов, сборка и публикация артефактов (Docker-образ и Helm-чарт).
2. **CD (Continuous Delivery):** Синхронизация фактического состояния кластера с желаемым через GitOps-агент (например, [ArgoCD](./ArgoCD/argocd_overview.md)).

### Используемые инструменты

- **CI-инструмент:** GitHub Actions
- **CD-инструмент:** ArgoCD
- **Хранилище артефактов:** **OCI (Open Container Initiative)** реестр

## Практические сценарии

### Поток выполнения (Workflow)

#### 1. Работа в ветке функциональности (Feature Branch)

- **Триггер:** `git push` в фича-ветку или создание **PR (Pull Request — запрос на слияние)** в ветку `main`.
- **Действия (GitHub Actions):**
  - Линтинг (статический анализ кода).
  - Модульное тестирование (Unit-тесты).
  - (Опционально) Сборка образа для предварительного просмотра (Preview environments), артефакт не публикуется в основной реестр.

#### 2. Слияние в основную ветку (CI-часть)

- **Триггер:** Слияние (Merge) PR в ветку `main`.
- **Действия (GitHub Actions):**
  1. Интеграционные тесты.
  2. Сборка Docker-образа с неизменяемым тегом (например, на основе семантической версии `v1.2.3` или краткого **SHA (Secure Hash Algorithm)** коммита).
  3. Публикация Docker-образа в OCI-реестр (Docker Hub, Harbor, GHCR).
  4. Сборка и публикация Helm-чарта:
     - Поле `appVersion` в `Chart.yaml` обновляется до версии созданного Docker-образа.
     - Версия самого чарта (`version`) инкрементируется.
     - Чарт упаковывается и отправляется в OCI-реестр.
  5. Обновление конфигурационного репозитория (Handoff to CD):
     - CI-пайплайн клонирует репозиторий с манифестами Kubernetes (GitOps-репозиторий).
     - Обновляется файл `values.yaml` или манифест `Application` для ArgoCD ссылкой на новую версию чарта.
     - Изменения фиксируются коммитом и отправляются (push) в GitOps-репозиторий.

#### 3. Развертывание в кластере (CD-часть)

- **Триггер:** ArgoCD обнаруживает новый коммит в GitOps-репозитории.
- **Действия (ArgoCD):**
  1. Сравнение текущего состояния ресурсов в кластере с конфигурацией в Git.
  2. Обнаружение расхождения (новая версия чарта) и запуск процесса синхронизации.
  3. Получение Helm-чарта из OCI-реестра, рендеринг шаблонов и применение манифестов в Kubernetes.
  4. Kubernetes выполняет плавное обновление (**Rolling Update**) подов с новой версией образа.

### Преимущества подхода

- **Безопасность:** У CI-системы нет прямого доступа к API Kubernetes; учетные данные кластера хранятся только внутри него.
- **Прозрачность и аудит:** Все изменения в инфраструктуре зафиксированы в истории коммитов GitOps-репозитория.
- **Быстрое восстановление:** Для отката достаточно выполнить `git revert` в конфигурационном репозитории.
- **Версионирование артефактов:** Четкая связь между версией кода, образом в реестре и состоянием кластера.
