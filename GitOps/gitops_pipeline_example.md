# GitOps: Пример пайплайна

## Определения

**GitOps-пайплайн** — это конвейер доставки программного обеспечения, реализующий [GitOps-подход](./GitOps_overview.md), при котором система **CI (Continuous Integration — непрерывная интеграция)** отвечает за сборку артефактов, а система **CD (Continuous Delivery — непрерывная доставка)** декларативно управляет состоянием кластера на основе манифестов в Git.

## Базовые концепции

### Разделение ответственности

Пайплайн разделен на две независимые части с четкой границей ответственности:

1. **CI (Continuous Integration):** Проверка исходного кода, запуск тестов, сканирование безопасности, сборка и публикация артефактов (Docker-образ и Helm-чарт).
2. **CD (Continuous Delivery):** Синхронизация фактического состояния кластера с желаемым через GitOps-агент (например, [ArgoCD](./ArgoCD/argocd_overview.md)).

### Используемые инструменты

- **CI-инструмент:** GitHub Actions
- **CD-инструмент:** ArgoCD
- **Безопасность:** Trivy (сканирование образов и манифестов)
- **Хранилище артефактов:** **OCI (Open Container Initiative)** реестр (поддержка образов и Helm-чартов)

### Преимущества подхода

- **Безопасность:** У CI-системы нет прямого доступа к API Kubernetes; учетные данные кластера хранятся только внутри него.
- **Прозрачность и аудит:** Все изменения в инфраструктуре зафиксированы в истории коммитов GitOps-репозитория.
- **Быстрое восстановление:** Для отката достаточно выполнить `git revert` в конфигурационном репозитории.
- **Версионирование артефактов:** Четкая связь между версией кода, образом в реестре и состоянием кластера.

## Практические сценарии

### Поток выполнения (Workflow)

#### 1. Работа в ветке функциональности (Feature Branch)

- **Триггер:** `git push` в фича-ветку или создание **PR (Pull Request — запрос на слияние)** в ветку `main`.
- **Действия (GitHub Actions):**
  - Линтинг (статический анализ кода и YAML-манифестов).
  - Модульное тестирование (Unit-тесты).
  - Сканирование кода на наличие секретов (gitleaks).
  - (Опционально) Сборка образа для предварительного просмотра (Preview environments), артефакт помечается временным тегом.

#### 2. Слияние в основную ветку (CI-часть)

- **Триггер:** Слияние (Merge) PR в ветку `main`.
- **Действия (GitHub Actions):**
  1. Интеграционные тесты.
  2. Сборка Docker-образа с неизменяемым тегом (на основе семантической версии `v1.2.3` или краткого **SHA (Secure Hash Algorithm)** коммита).
  3. **Сканирование безопасности:** Проверка собранного образа инструментом Trivy. Если обнаружены критические уязвимости (CRITICAL), пайплайн прерывается.
  4. Публикация Docker-образа в OCI-реестр (GHCR, Harbor).
  5. Сборка и публикация Helm-чарта:
     - Поле `appVersion` в `Chart.yaml` обновляется до версии созданного Docker-образа.
     - Версия самого чарта (`version`) инкрементируется.
     - Чарт упаковывается и отправляется в OCI-реестр как артефакт.
  6. **Передача управления в CD (Handoff):**
     - **Вариант А (Git Push):** CI-пайплайн клонирует GitOps-репозиторий, обновляет версию чарта в `values-staging.yaml` и делает коммит.
     - **Вариант Б (Image Automation):** CI только публикует образ, а ArgoCD Image Updater (или Flux Image Automation) обнаруживает новый тег и сам обновляет GitOps-репозиторий.

#### 3. Развертывание в кластере (CD-часть)

- **Триггер:** ArgoCD обнаруживает изменения в GitOps-репозитории или новый образ (при использовании Image Updater).
- **Действия (ArgoCD):**
  1. Сравнение состояния ресурсов в кластере с конфигурацией в Git.
  2. Обнаружение расхождения (`OutOfSync`) и запуск процесса синхронизации.
  3. Получение Helm-чарта из OCI-реестра, рендеринг шаблонов и применение в Kubernetes.
  4. **Staging:** Автоматическое обновление. После успешного деплоя запускаются автоматизированные **E2E (End-to-End)** тесты.
  5. **Production:** После подтверждения в Staging, PR на обновление `values-prod.yaml` сливается в GitOps-репозитории, и ArgoCD применяет изменения в продуктивный кластер.
  6. **UI (User Interface):** Визуализация статуса деплоя и здоровья ресурсов в реальном времени.
