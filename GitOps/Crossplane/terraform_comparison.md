# Crossplane: сравнение с Terraform и OpenTofu

## Определения

**Crossplane** — это Kubernetes-native решение для управления инфраструктурой, превращающее кластер в полноценную платформу управления (Control Plane). Оно расширяет API Kubernetes для декларативного управления облачными ресурсами через контроллеры и систему непрерывной сверки.

**Terraform** — индустриальный стандарт **IaC (Infrastructure as Code)**. После приобретения HashiCorp компанией IBM в 2024 году, инструмент стал частью портфеля IBM Cloud Pak, сохраняя доминирующее положение в Enterprise-секторе. Использует язык HCL и ориентирован на событийное выполнение (workflow-based).

**OpenTofu** — открытый форк Terraform под эгидой Linux Foundation (MPL 2.0). Возник как ответ на изменение лицензии HashiCorp на BSL. К 2026 году проект развился в независимую экосистему, внедрив уникальные функции, такие как нативное шифрование состояния и улучшенная итерация провайдеров.

## Базовые концепции

### Ключевые различия (актуально на 2026 год)

| Характеристика | Crossplane (v2.x) | Terraform (v1.10+) | OpenTofu (v1.12+) |
| :--- | :--- | :--- | :--- |
| **Модель управления** | Pull (Continuous Reconciliation) | Push (Plan/Apply Workflow) | Push (Plan/Apply Workflow) |
| **Среда выполнения** | Kubernetes Cluster | CLI / CI-CD / Runner | CLI / CI-CD / Runner |
| **Хранение состояния** | etcd (встроено в объекты) | Файл `.tfstate` (Remote Backend) | Файл `.tfstate` (Remote Backend) |
| **Исправление дрейфа** | **Автоматическое** (Self-healing) | Ручное (через запуск пайплайна) | Ручное (через запуск пайплайна) |
| **Логика и шаблоны** | **Composition Functions** (Go, Python) | HCL Logic / Terraform Stacks | HCL Logic / State Encryption |
| **Интерфейс** | K8s API (kubectl, GitOps) | CLI / UI (HCP Terraform) | CLI / Open Source UI |
| **Безопасность** | RBAC K8s, OPA/Kyverno | Sentinel, Vault, OPA | OPA, KMS State Encryption |

### Управление состоянием и дрейфом (Drift)

*   **Crossplane:** Не имеет внешнего state-файла. "Состояние" — это статус ресурса в Kubernetes. Контроллер сверяет состояние каждые несколько секунд. Если ресурс изменен вручную в консоли облака (например, изменен размер инстанса БД), Crossplane обнаружит расхождение и автоматически вернет параметр к значению, описанному в YAML.
*   **Terraform / OpenTofu:** Состояние хранится как статический снимок (snapshot). Дрейф обнаруживается только при запуске `plan`. Несмотря на появление в 2026 году функций "Continuous Health Checks" в облачных версиях, автоматическое исправление без запуска рабочего процесса (Workflow) остается ограниченным.

### Логика композиции vs HCL

*   **HCL (Terraform/OpenTofu):** Предоставляет мощный DSL для описания инфраструктуры с поддержкой условий, циклов и модулей. В 2026 году **Terraform Stacks** позволяет оркестровать сложные зависимости между множеством модулей и регионов.
*   **Composition Functions (Crossplane):** Позволяет использовать полноценные языки программирования (Go, Python) или CEL (Common Expression Language) для формирования графа ресурсов. Это решает проблему "многословного YAML" и позволяет реализовывать сложную логику, недоступную в HCL (например, динамические запросы к внешним API в процессе рендеринга).

## Практические сценарии

### Выбор инструмента

**Выбирайте Crossplane, когда:**
*   Вы строите **Internal Developer Platform (IDP)** и внедряете подход "Infrastructure as a Product".
*   Приложения и их инфраструктурные зависимости (БД, очереди) должны иметь единый жизненный цикл в рамках GitOps (ArgoCD/Flux).
*   Требуется строгая гарантия отсутствия ручных изменений (Zero Drift).
*   Команда глубоко интегрирована в экосистему Kubernetes.

**Выбирайте Terraform / OpenTofu, когда:**
*   Нужно управлять "фундаментальной" инфраструктурой (сети, Peering, IAM, сами кластеры K8s).
*   Проект требует использования редких провайдеров, которых нет в экосистеме Crossplane (хотя Jet-провайдеры Crossplane закрывают 95% потребностей).
*   Инфраструктура статична и не требует постоянной сверки.
*   Команде требуется визуальный "план" изменений перед их применением для критически важных систем.

### Гибридный подход (Стандарт 2026 года)

Современная архитектура SRE-платформ предполагает разделение ответственности:

1.  **OpenTofu (или Terraform):** Создание базового уровня (VPC, Subnets, IAM, K8s Clusters). Используется как "bootstrap" инструмент.
2.  **Crossplane:** Разворачивается внутри созданных кластеров для предоставления "Self-Service" инфраструктуры разработчикам (Managed Databases, S3, Pub/Sub).

Этот подход объединяет надежность HCL для фундаментальных изменений и гибкость Kubernetes-native API для сервисов приложений.
