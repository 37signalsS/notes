# Crossplane: Обзор

## Определения

**Crossplane** — это решение класса "инфраструктура как код" (IaC) с открытым исходным кодом, которое расширяет Kubernetes API для управления облачной инфраструктурой от различных провайдеров. Он устанавливается в кластер Kubernetes и позволяет определять и настраивать облачные ресурсы (базы данных, сети, виртуальные машины) с помощью декларативных YAML-манифестов, используя нативный подход Kubernetes.

## Базовые концепции

### Ключевые возможности

* **Унифицированное управление:** Использование знакомого синтаксиса и инструментов Kubernetes (`kubectl`, GitOps) для управления приложениями и инфраструктурой.
* **Представление облачных сервисов как CRD:** Автоматическое создание Custom Resource Definitions (CRD) для облачных сервисов, делая их нативными ресурсами кластера.
* **Интеграция с GitOps:** Полная совместимость с Argo CD и Flux для реализации цикла управления инфраструктурой через Git.
* **Политики управления:** Использование RBAC и Open Policy Agent (OPA) для гранулярного контроля доступа к облачным ресурсам.
* **Расширяемость:** Поддержка множества провайдеров (AWS, Azure, GCP, Yandex Cloud) и возможность создания собственных расширений.

### Компоненты Crossplane

* **Managed Resources (MR):** Представляют конкретный ресурс в облаке (например, инстанс БД).
* **Providers:** Пакеты, которые обучают Crossplane взаимодействию с API конкретного облака.
* **ProviderConfig:** Конфигурация, содержащая учетные данные для доступа провайдера к облачному API.

### Уровни абстракции и композиция

Crossplane позволяет строить собственные платформы управления (Control Planes) через систему композиции:

1. **Composite Resource Definition (XRD):** Описание схемы вашего собственного API (абстрактного ресурса, например "PostgreSQL-Cluster").
2. **Composition:** Реализация XRD, определяющая, из каких Managed Resources (MR) состоит ваш абстрактный ресурс и как они должны быть настроены.
3. **Composite Resource (XR):** Экземпляр ресурса, созданный на основе XRD и Composition. Может быть как глобальным, так и ограниченным пространством имен (Namespaced).
4. **Claim (XRC):** Запрос на создание ресурса пользователем из конкретного namespace, аналогично PersistentVolumeClaim в Kubernetes.

### Архитектура

1. Пользователь или CI/CD-система применяет YAML-манифест в кластере (`kubectl apply -f ...`).
2. Манифест сохраняется в etcd как кастомный ресурс Kubernetes.
3. **Crossplane Core** (набор контроллеров) обнаруживает создание или изменение ресурса.
4. На основе `ProviderConfig` Crossplane взаимодействует с API облачного провайдера.
5. Облачный сервис создается или обновляется на стороне провайдера.
6. Crossplane получает статус операции и обновляет поле `status` ресурса в Kubernetes, обеспечивая непрерывную сверку (reconciliation).

### Ключевые особенности v2.x (актуально на 2026 год)

| Функция | Описание |
| :--- | :--- |
| **Namespaced Composite Resources** | Поддержка XRs в пространствах имен для лучшей изоляции и RBAC. |
| **Composition Functions** | Использование gRPC-функций (на Go, Python и др.) для сложной логики шаблонизации вместо статического YAML. |
| **AI-инфраструктура** | Оптимизация API для автономного управления инфраструктурой через AI-агентов. |
| **Inspector Sidecars** | Встроенные инструменты для отладки и трассировки выполнения функций композиции. |
| **Function-KRO** | Возможность использования CEL (Common Expression Language) для создания графов ресурсов без написания кода. |

### Статус проекта

* **CNCF Status:** Graduated (октябрь 2025)
* **Текущая версия:** v2.3.x (май 2026)
* **Сообщество:** Более 3800 контрибьюторов и поддержка крупнейших облачных вендоров.
