# Crossplane: Обзор

## Определения

**Crossplane** — это решение класса "инфраструктура как код" (IaC) с открытым исходным кодом, которое расширяет Kubernetes API для управления облачной инфраструктурой от различных провайдеров. Он устанавливается в кластер Kubernetes и превращает его в универсальную платформу управления (Control Plane), позволяя определять и настраивать облачные ресурсы (базы данных, сети, виртуальные машины) с помощью декларативных YAML-манифестов.

## Базовые концепции

### Ключевые возможности

* **Унифицированное управление:** Использование знакомого синтаксиса и инструментов Kubernetes (`kubectl`, GitOps) для управления приложениями и инфраструктурой в едином цикле.
* **Представление облачных сервисов как CRD:** Автоматическое создание Custom Resource Definitions (CRD) для облачных сервисов, делая их нативными ресурсами кластера.
* **Непрерывная сверка (Reconciliation):** Контроллеры Crossplane постоянно следят за соответствием реального состояния ресурсов в облаке их описанию в Kubernetes, автоматически устраняя дрейф конфигурации (configuration drift).
* **Интеграция с GitOps:** Полная совместимость с Argo CD и Flux для реализации модели "Git как единственный источник правды" для инфраструктуры.
* **Политики управления:** Использование RBAC и Open Policy Agent (OPA) для гранулярного контроля доступа к облачным ресурсам на уровне Kubernetes API.

### Основные компоненты

* **Crossplane Core:** Набор контроллеров, отвечающих за жизненный цикл ресурсов, композицию и управление пакетами.
* **Providers:** Пакеты, которые обучают Crossplane взаимодействию с API конкретного облака (AWS, Azure, GCP, Yandex Cloud).
* **Provider Families:** Современная архитектура провайдеров (введена в v1.x, стандарт в v2.x), разделяющая огромные провайдеры на более мелкие пакеты по сервисам (например, `provider-aws-s3`, `provider-aws-rds`) для снижения нагрузки на API-сервер.
* **ProviderConfig:** Конфигурация, содержащая учетные данные (секреты) для доступа провайдера к облачному API.
* **Managed Resources (MR):** Низкоуровневые ресурсы, представляющие конкретный объект в облаке (например, `Instance` в Yandex Compute Cloud).

### Уровни абстракции и композиция

Crossplane позволяет строить собственные внутренние платформы разработчика (IDP) через систему композиции:

1. **Composite Resource Definition (XRD):** Описание схемы вашего собственного высокоуровневого API (например, абстрактный ресурс "PostgreSQL-Cluster").
2. **Composition:** Реализация XRD, определяющая, из каких Managed Resources (MR) состоит ваш абстрактный ресурс и как они связаны. Может включать логику на базе **Composition Functions** (Go, Python, CEL).
3. **Composite Resource (XR):** Экземпляр ресурса, созданный платформенной командой. Обычно является глобальным (Cluster-scoped) ресурсом.
4. **Composite Resource Claim (XRC или Claim):** Запрос на создание ресурса пользователем из конкретного namespace (Namespace-scoped), аналогично `PersistentVolumeClaim`.

### Архитектура и поток данных

Интеграция Crossplane в GitOps-пайплайн обеспечивает автоматизацию полного цикла:

```text
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│     Git     │────▶│   ArgoCD    │────▶│ Crossplane  │────▶│  Облачный   │
│  Repository │     │  (Sync)     │     │ (Reconcile) │     │ Провайдер   │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
```

1. **Применение манифеста:** Пользователь фиксирует YAML в Git, Argo CD синхронизирует его в кластер Kubernetes.
2. **Обработка Core:** Crossplane Core видит новый ресурс (MR или Claim) в etcd.
3. **Композиция:** Если это Claim, Crossplane на основе `Composition` разворачивает его в набор Managed Resources.
4. **Взаимодействие с провайдером:** Соответствующий Provider-контроллер использует `ProviderConfig` для вызова API облака.
5. **Создание ресурса:** Облачный сервис создается или обновляется.
6. **Обратная связь:** Crossplane обновляет поле `status` ресурса в Kubernetes. Если в облаке произойдут изменения вручную, Crossplane вернет их к желаемому состоянию при следующей итерации сверки.

## Передовые возможности v2.x (актуально на 2026 год)

| Функция | Описание |
| :--- | :--- |
| **Namespaced Composite Resources** | Возможность создавать XRs внутри пространств имен для лучшей изоляции между командами. |
| **Composition Functions** | Переход от статических YAML-шаблонов к gRPC-функциям. Позволяет использовать циклы, условия и внешние запросы при формировании инфраструктуры. |
| **Real-time Drift Detection** | Улучшенные механизмы мгновенного обнаружения изменений в облаке через Webhooks/Events провайдеров. |
| **AI-инфраструктура** | Нативные интерфейсы для взаимодействия с AI-агентами, позволяющие автономно масштабировать и оптимизировать инфраструктуру. |
| **Inspector Sidecars** | Инструменты трассировки, позволяющие видеть процесс выполнения функций композиции в реальном времени. |

## Безопасность и наблюдаемости

### Безопасность

* **RBAC Manager:** Компонент Crossplane, который автоматически управляет ролями Kubernetes для доступа к новым CRD, создаваемым провайдерами.
* **Secrets Management:** Интеграция с **External Secrets Operator (ESO)** и HashiCorp Vault для безопасной передачи учетных данных провайдерам.
* **Composition-level RBAC:** Возможность ограничивать, какие команды могут использовать конкретные `Compositions`.

### Наблюдаемость

* **Crossplane CLI:** Инструмент `crossplane` для отладки ресурсов, проверки пакетов и визуализации графа композиции (`crossplane beta trace`).
* **Metrics:** Экспорт метрик в формате Prometheus о времени сверки, ошибках API провайдеров и статусе ресурсов.
* **Events:** Использование стандартных Kubernetes Events для уведомления о критических изменениях или сбоях в процессе создания ресурсов.
