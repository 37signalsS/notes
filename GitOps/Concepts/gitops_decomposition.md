# GitOps: декомпозиция методологии и апгрейд CIOps

**Актуально для:** Flux 2.x, Argo CD 3.x, OpenGitOps Principles v1.0.0

Файл разбирает GitOps на составляющие и оценивает ценность каждой компоненты отдельно: критический анализ принципа «Git как единый источник истины», практические схемы перехода от CI-ориентированной доставки (CIOps) к GitOps с минимальными усилиями, анализ безопасности push-схем и механика непрерывного согласования. Общая теория методологии — в [GitOps: обзор методологии](../GitOps_overview.md).

## Определения

| Термин | Определение |
| :--- | :--- |
| **Декомпозиция GitOps** | Разбор методологии на независимые компоненты (декларативность, версионирование, pull-агент, непрерывное согласование) с оценкой пользы каждого по отдельности и в совокупности. |
| **CIOps** | Условное название текущей практики доставки, где развёртывание выполняет CI-система на стадии deploy пайплайна; отдельного агента в кластере нет. |
| **Reconciliation loop (цикл согласования)** | Механизм: если фактическое состояние отличается от желаемого, система приводит его к желаемому. |
| **Configuration drift (дрейф конфигурации)** | Неконтролируемое расхождение фактического состояния с описанным в коде в результате ручных изменений. |
| **Трёхстороннее согласование (3-way merge)** | Способ применения манифестов, при котором поля, не описанные в манифесте, не удаляются из живого объекта. |
| **Server-Side Apply (SSA)** | Механизм применения манифестов на стороне API-сервера Kubernetes с отслеживанием владельцев полей (`managedFields`); современная альтернатива клиентскому 3-way merge. |
| **Спираль страха автоматизации** | Ситуация, когда операторы отключают GitOps-агентов, чтобы вручную исправить инцидент, и боятся включить их обратно. |
| **Автоматизация обновления образов** | Механизм отслеживания новых образов в реестре и автоматического обновления ссылок на них в Git-репозитории. |

## Базовые концепции

### Декомпозиция GitOps

GitOps не монолит: он складывается из независимых компонентов, и каждый можно применять отдельно:

1. Декларативное описание состояния.
2. Версионирование описания.
3. Агент в кластере, работающий по pull-схеме.
4. Непрерывное согласование состояния.

Ценность компонентов в общем важнее, чем ценность каждого по отдельности, но разбор позволяет понять, какая именно проблема решается и какой компонент для этого нужен (см. раздел [Декомпозиция по задачам](#декомпозиция-по-задачам-когда-gitops-нужен-а-когда-нет)).

### Проблемы «Git как единого источника истины»

Идея «Git — единый источник истины» (все окружения и все изменения оперируются из Git) имеет три фундаментальные проблемы:

1. **Артефакты вне Git.** Образы контейнеров и Helm-чарты живут в реестрах, а не в Git. Тег мутабелен: перезалив образа или чарта с тем же тегом коренным образом меняет работу приложения, а Git об этом не знает и не отражает изменение.
2. **Секреты.** Секреты нельзя хранить в Git в открытом виде, значит, часть состояния всегда вне Git.
3. **Git не отражает состояние.** У Git нет статуса «применено / не применено»: описанная в Git инфраструктура может никогда не попасть в кластер, и Git этого не покажет.

Вывод: Git — хорошее хранилище описания, но не полноценный источник истины о состоянии системы.

### Принципы OpenGitOps (механика)

Спецификация OpenGitOps v1.0.0 (CNCF) формулирует четыре принципа и при этом заменяет принцип «Git как единый источник истины» на более строгий принцип версионирования:

1. **Декларативность.** Под каждым декларативным описанием есть императивный фреймворк, который это описание применяет. Kubernetes — идеальный императивный фреймворк: ему на вход нужен только YAML. Промежуточное сохранение конфигурации в Git очень способствует внедрению подхода «инфраструктура как данные».
2. **Версионирование.** Git — канонический пример системы версионирования, но принцип не привязан к Git: подходит любая система, удовлетворяющая критериям (например, SVN-сервер с конфигурацией, разложенной по именованным папкам).
3. **Работа по pull-схеме.** GitOps-агенты должны сами скачивать конфигурацию. Это жёстче, чем первоначальная формулировка Weaveworks («pull приоритетнее push»): в OpenGitOps pull — обязательное требование, а не рекомендация.
4. **Непрерывное согласование.** Ключевой принцип: агенты постоянно сверяют фактическое состояние с желаемым. Ради него, по сути, всё и строится (разбор механики — в разделе [Непрерывное согласование конфигурации](#непрерывное-согласование-конфигурации)).

### Определения вендоров: единого решения нет

Крупные вендоры понимают GitOps по-разному. GitLab описывает его как операционный фреймворк с лучшими практиками построения доставки кода и подчёркивает: единого решения, подходящего всем, не существует. Три ключевых компонента по GitLab:

1. Инфраструктура как код (Git как источник истины для определений).
2. Доставка изменений через merge/pull requests (ревью, аппрувы, аудит).
3. Выстроенные CI/CD-процессы (автоматическое применение изменений после мерджа).

Практический вывод: методология состоит из составных частей, которые можно использовать по отдельности, подбирая решение под бизнес-процессы.

### Что не является GitOps

Типичный пример «практики без теории»: студент через веб-интерфейс ArgoCD создаёт объект `Application`, прописывает Helm-чарт (запушенный на предыдущем уроке), на вкладке params передаёт values для чарта, описывает образы и таким образом обновляет приложение. По определениям Weaveworks и GitLab это не GitOps; по OpenGitOps — лишь отчасти: объект `Application` декларативен и пригоден для версионирования в Git (паттерн app-of-apps), но в описанном сценарии он создаётся и живёт вне Git. ArgoCD — инструмент, с помощью которого можно делать как GitOps, так и не-GitOps: инструмент не определяет методологию.

### Каноническая реализация: Flux

Каноническая реализация GitOps от первопроходов методологии — Flux CD. Схема: git-репозиторий и docker-реестр; в репозиторий скидывают YAML с Custom Resource `HelmRelease`; в кластере работают контроллеры Flux (модульный набор):

- Чтобы YAML попал внутрь кластера, описывается `GitRepository` и раздаются права — `source-controller` скачивает YAML из Git.
- Чтобы применить YAML, описывается `Kustomization` — `kustomize-controller` берёт артефакт source-контроллера и деплоит его в Kubernetes.
- `helm-controller` видит `HelmRelease`, идёт в source-контроллер за чартом; для этого описывается `HelmRepository` — source-контроллер скачивает чарт, helm-контроллер деплоит релиз.
- `notification-controller` алертит, если что-то пошло не так; состояние в любой момент доступно через CLI (`flux get sources git`, `flux get kustomizations`, `flux get helmreleases`) — в отличие от сообщений CI-пайплайна, которые теряются. Встроенного веб-интерфейса у Flux нет: это CLI-only набор контроллеров.
- Для разделения доступа (multi-tenancy) Flux использует не отдельный механизм, а Kubernetes namespaces и RBAC: контроллеры имперсонируют сервис-аккаунт тенанта, указанный в `spec.serviceAccountName` (`Kustomization`, `HelmRelease`), а lockdown-флаги (`--no-cross-namespace-refs`, `--no-remote-bases`) запрещают кросс-неймспейсные ссылки и remote bases.

Всё происходит внутри кластера: извне нельзя судить, хорошо или плохо, что-то задеплоилось или нет — зелёные галочки пайплайна CI/CD этого не покажут. Полная архитектура, CRD и жизненный цикл объектов — в [Flux: обзор и ключевые концепции](../flux.md).

## Практические сценарии

### Разрыв между демо и реальностью

Все демо CD сводятся к одному: человек пушит что-то в репозиторий — и приложение задеплоилось, «магия». Реальность внедрения: к разработчику приходят и говорят «вы собрали образ, молодцы, теперь поправьте этот YAML и обновите приложение в prod, если всё хорошо прошло и все предыдущие стадии прошли». CI покрывает только стадии сборки, CD — стадии выкатки; хочется, чтобы пайплайн проходил плавно, без участия оператора и ручных операций.

### Схема с автоматическим обновлением образов и её проблемы

Решение, предлагаемое первопроходами GitOps: разделить git-репозитории — репозиторий с кодом приложения и инфраструктурный репозиторий. В инфраструктурный репозиторий записывается первая версия конфигурации приложения, дальше работает автоматизация образов Flux: `image-reflector-controller` замечает новый docker-образ в реестре, `image-automation-controller` идёт править инфраструктурный репозиторий, и таким образом деплоится новая версия приложения. Для поддержки схемы достаточно задеплоить два контроллера и записать три кастомных ресурса (`ImageRepository`, `ImagePolicy`, `ImageUpdateAutomation`) — и при появлении нового образа репозиторий обновляется, а дальше работает стандартная схема синхронизации с кластером.

Проблемы схемы:

1. **Сложность и хрупкость.** Политики обновления нужно настраивать очень тщательно: зафиксированы случаи в нескольких независимых командах, когда джун неправильно выставил policy и в итоге упал prod. Не давать схеме шалить — обязательное условие.
2. **Перенос версий из dev в prod.** Нельзя сразу же обновить prod-репозиторий: инфраструктурный код для stage обычно отличается от инфраструктурного кода для prod.
3. **Согласование версий.** Нельзя просто взять и обновить версию образа без синхронизации с версией чарта: добавляются новые сервисы, ingress и прочее — версия образа и версия чарта связаны.
4. **Аудит изменений.** Image-оператор работает под технической учётной записью, все изменения в репозитории обезличены: нельзя посмотреть, кто триггерил изменение, положившее образ в prod. Для этого нужна вся CD-система и разбор её логов.

Автоматизация обновления образов в экосистеме: Argo CD Image Updater, встроенная Image Automation во Flux (`ImageRepository`/`ImagePolicy`/`ImageUpdateAutomation`), Renovate — см. [Renovate: автоматизация обновлений](./renovate_dependency_updates.md) и [стратегии продвижения](../GitOps_overview.md#стратегии-продвижения-promotion-strategies).

### Подход ArgoCD: скрипт в CD-пайплайне

Базовый рецепт ArgoCD: клонировать репозиторий, изменить в нём нужное и запушить — простой скрипт, встроенный в CD-пайплайн. У ArgoCD тоже есть нечто вроде image updater, но канонический рецепт — именно скрипт «clone → change → commit → push».

### Базовый паттерн CIOps (состояние до GitOps)

Как доставляют до появления GitOps:

- **Монорепозиторий.** Лучшая практика — хранить инфраструктурный код и код приложения в одном репозитории, избегая проблемы согласования версий.
- **Деплой со stage-специфичными настройками.** На стадии деплоя передаются настройки, специфичные для случая: для Helm — `helm upgrade` с директивой `--set`; имя приложения и docker-образ, собранный в пайплайне — весь контекст уже есть в CI-системе.
- **Секреты на этапе деплоя.** Секреты передаются непосредственно на этапе деплоя: сохранены в CI-системе или в интеграции с хранилищем паролей.
- **Трекинг релиза.** Ключ трекинга релиза даёт зелёные галочки или алерт в почту: релиз прошёл в prod или всё сломалось.

Схема достаточна для достаточно простых проектов; из неё можно вырасти, а можно изначально иметь проект слишком сложным для неё — тогда возвращаются к этим рекомендациям.

### Апгрейд CIOps до GitOps своими силами

Чтобы CIOps выглядел как GitOps, не внедряя оператор:

1. **Helm-чарт под версию образа.** Сделать Helm-чарт, соответствующий версии docker-образа, который соберётся из монорепозитория.
2. **Values под окружение.** Подготовить values, специфичные для окружения (stage и т. д.).
3. **Генерация HelmRelease.** Клонировать инфраструктурный репозиторий и при помощи CLI Flux на основе сгенерированных values сделать Custom Resource `HelmRelease`:

```bash
# Генерация HelmRelease на основе values (запись на диск без применения в кластер)
flux create helmrelease my-app \
  --source=GitRepository/my-app \
  --chart=./charts/my-app \
  --values=./values-prod.yaml \
  --export > my-app-release.yaml
# → файл my-app-release.yaml с Custom Resource HelmRelease готов к коммиту
```

CLI Flux в докладе характеризуется как достаточно неудобная утилита, но для этой задачи достаточная.

4. **Коммит.** Всё это дело коммитится в git-репозиторий.
5. **Деплой.** Раннер внутри кластера применяет манифест из репозитория, используя `kubeconfig` (push-модель), либо агент в кластере тянет конфигурацию сам (pull-модель).

**Валидация:** после коммита проверьте, что релиз синхронизирован:

```bash
flux get helmreleases -n apps
# → NAME    REVISION        SUSPENDED  READY  MESSAGE
# → my-app  my-app 1.2.3    False      True   Release reconciliation succeeded
```

Готовность подтверждается статусом `Ready=True`; в pull-модели тот же результат достигается без участия раннера — `helm-controller` сам обнаруживает новый `HelmRelease` в Git и деплоит релиз.

### Безопасность push-схемы: риски и митигации

Почему схему с CI считают небезопасной: считается, что токен, сохранённый в CI-системе, пользователи CI-системы могут злоупотребить им внутри кластера, и никто к этому кластеру доступа не имеет. Но все забывают, что в рамках GitOps непосредственный доступ к кластеру заменён на опосредованный — и у опосредованного доступа свои проблемы:

1. **Force-push.** Кто-то пушит свои изменения в инфраструктурный git-репозиторий, а потом reset'ит историю. Это может сделать любой с админскими правами на репозиторий — или просто при забытом запрете force-push. **Митигация:** запрещать force-push в инфраструктурном репозитории.
2. **Опосредованное выполнение кода.** Люди могут запускать свой код с правами GitOps-агента и потерять за собой историю. **Митигация:** изолировать пайплайн деплоя в отдельном проекте — пользователям дать только права на просмотр репозитория, а пуш выполняет техническая учётная запись.
3. **Хранение токена.** Доступ к целевой системе всё равно хранится где-то, и команда поддержки системы теоретически может его забрать и злоупотребить. **Митигация:** развернуть раннер внутри Kubernetes и дать ему сервис-аккаунт с минимальными правами вместо статического токена в CI-системе; защищённость схемы при этом равна схеме с Flux, а применение идёт через нативный `kubectl`, а не CLI Flux.
4. **Выполнение произвольного кода на раннере.** GitOps-конфигурация (CI-файл) лежит в том же репозитории, где инфраструктурный код, и пользователи теоретически могут его изменить — и выполнить на раннере произвольный код. **Митигация:** в GitLab — защита пайплайнов (pipeline execution policies): часть jobs определяется в отдельном policy-проекте, выполняется в изолированном pipeline и не может быть переопределена правкой `.gitlab-ci.yml` проекта; policy игнорирует директиву `[skip ci]`.

Итог: автоматический pull защищённых пайплайнов выглядит так, будто его легко сделать, а непрерывное согласование инфраструктуры — отдельная тема (см. ниже).

## Непрерывное согласование конфигурации

### Цикл реконсиляции

Reconciliation loop (кольцо самосогласования): если фактическое состояние различается с желаемым, оно приводит текущее состояние к описанному как желаемое. Так работает любимый всеми Kubernetes: все контроллеры следят за тем, что в кластере, и восстанавливают его (упала нода — поды пересозданы и т. д.).

Ключевое свойство механизма — он level-triggered (реагирует на текущее состояние, а не на событие): контроллер не «пропускает» изменение, случившееся между двумя итерациями, — на каждом проходе он сверяет объект целиком с желаемым описанием. Именно поэтому реконсиляция самовосстанавливается после сбоев и ручных правок без журнала событий. Интервал сверки по умолчанию: Flux — 1 минута (`spec.interval`), Argo CD — 180 секунд (`timeout.reconciliation`); вебхуки ускоряют реакцию, но периодический опрос остаётся обязательным (требование OpenGitOps «Pulled Automatically»).

### Дрейф конфигурации и снежные кластеры

Ручные операции — плохо, все об этом знают: ручные операции приводят к configuration drift, когда конфигурация становится неконсистентной, никто не понимает, что внутри, и это боятся трогать. В контексте GitOps проблема выходит на более высокий уровень: появляются «кубернетес-кластеры-снежинки». Что не описано кодом — подвержено configuration drift.

### Трёхстороннее согласование (3-way merge)

Способ, по которому работает Kubernetes при применении манифестов. Пример: вы задеплоили в Kubernetes объект, в котором есть секция с описанными переменными окружения. Вы вручную правите объект и описываете там ещё одну переменную, а потом делаете YAML, в котором описываете первую и одну дополнительную переменную окружения. После деплоя в кластере окажутся все три переменные: то, что не описано в манифесте, Kubernetes при переприменении не трогает. Так работают Kubernetes (`kubectl apply`) и Argo CD (стратегия diff по умолчанию — Legacy). Flux применяет манифесты через server-side apply — механизм владения полями вместо аннотации; практический итог для ручных правок разобран в граничных случаях ниже.

```yaml
# Манифест описывает переменные A и C
env:
  - name: A
    value: "1"
  - name: C
    value: "3"
# После apply в кластере останутся A, B (добавлена вручную) и C:
# B никогда не фигурировала в last-applied-configuration, поэтому Kubernetes не удаляет её
```

Следствие: при клиентском применении (`kubectl apply`, Argo CD Legacy) ручные правки «прилипают» к объектам и не видны в Git — дрейф обнаруживается только через сверку контроллером (status OutOfSync, self-healing).

Границы применимости и конфликты Server-Side Apply (SSA):

- **Лимит аннотации.** Клиентское применение (`kubectl apply`) хранит последнее состояние в аннотации `kubectl.kubernetes.io/last-applied-configuration` с лимитом 256 KB: крупные манифесты не помещаются в неё, и diff деградирует. Flux этим не страдает — `kustomize-controller` применяет манифесты через server-side apply (сверка dry-run + патч по владельцам полей), без аннотации и её лимита; Argo CD поддерживает SSA через sync-опцию `ServerSideApply=true`.
- **Конфликты FieldManager (Field Ownership Conflict):** В SSA каждое поле в объекте Kubernetes принадлежит конкретному менеджеру (зафиксировано в `metadata.managedFields`). Если сторонний контроллер (например, HPA управляет `spec.replicas`, или Cert-Manager обновляет аннотацию ингресса) захватил поле, а GitOps-агент пытается применить манифест с другим значением того же поля, API-сервер возвращает ошибку:
  ```text
  Apply failed with 1 conflict: conflict with "k8s-controller": .spec.replicas
  ```
  **Диагностика:** инспекция владельца поля:
  ```bash
  kubectl get deployment billing-service -o jsonpath='{.metadata.managedFields}' | jq .
  ```
  **Решение:**
  1. *Декларативное разделение:* удалить поле `spec.replicas` из манифеста в Git, если масштабированием управляет HPA, оставив HPA единственным владельцем.
  2. *Исключение из сверки:* добавить поле в `spec.ignoreDifferences` в манифесте Argo CD `Application`.
  3. *Принудительный захват:* во Flux указать аннотацию `kustomize.toolkit.fluxcd.io/ssa: merge`, в Argo CD включить `ServerSideApply=true` в связке с `Force=true` (эквивалент флага `--force-conflicts`).
- **Мутирующие вебхуки.** Поля, добавленные вебхуками (sidecar injection, дефолтные метки), воспринимаются контроллером как дрейф и бесконечно откатываются. Решение — исключить поле из сверки (`ignoreDifferences` в Argo CD, `spec.ignore` во Flux), а не бороться с контроллером.
- **Недоступность Git.** Агент продолжает реконсиляцию по последнему загруженному артефакту: кластер остаётся в последнем синхронизированном состоянии, но новые изменения не приходят, пока связь не восстановится.

### Аварийные регламенты: Break-Glass и Rollback при включенном Auto-Sync

Классическая аварийная ситуация: релиз привел к падению сервиса в Production, но в Argo CD включен автоматический синк (`automated.selfHeal: true`).

**Почему стандартный Rollback терпит фиаско:**
- Нажатие кнопки **Rollback** в веб-интерфейсе Argo CD или выполнение `kubectl rollout undo` возвращает предыдущий ReplicaSet только в рантайме Kubernetes.
- Через интервал сверки (по умолчанию 3 минуты в Argo CD или немедленно по триггеру самоисцеления) контроллер обнаруживает, что живое состояние кластера расходится с коммитом в Git (Target State по-прежнему указывает на сбойный тег образа).
- Контроллер выполняет самоисцеление и принудительно накатывает сбойную версию обратно!

**Регламент безопасного аварийного отката (Break-Glass Protocol):**

```bash
# Шаг 1: Приостановка автоматической синхронизации (Suspend / Manual Mode)
# Для Argo CD:
argocd app set billing-service --sync-policy none
# Для Flux v2:
flux suspend kustomization billing-service -n flux-system

# Шаг 2: Экстренное купирование сбоя в рантайме (если секунды критичны)
kubectl rollout undo deployment/billing-service -n billing

# Шаг 3: Обязательная синхронизация SSoT в Git (Canonical Rollback)
# Локально или в веб-интерфейсе GitLab/GitHub:
git revert HEAD -m 1 --no-edit
git push origin main
# → коммит отката зафиксирован в Git; аудит и трассируемость сохранены

# Шаг 4: Возврат GitOps-агента в автоматический режим
# Для Argo CD:
argocd app set billing-service --sync-policy automated --auto-prune --self-heal
argocd app sync billing-service
# Для Flux v2:
flux resume kustomization billing-service -n flux-system
```

### Спираль страха автоматизации

Представьте: вы приходите в компанию и видите, что операторы Flux в кластере упали в ноль и не работают. Ваши действия? Первым делом думаешь, что ребята фиксят какую-то проблему вручную и отключили операторы Flux, чтобы они просто не мешали. Включить их обратно — не факт, что они не сломают то, что в кластере случилось. Это и есть спираль страха автоматизации: чем больше ручных правок накопилось, тем опаснее включать автоматику.

### Почему реконсиляция не строится в CI-системе

Непрерывное согласование инфраструктуры в рамках CI-системы построить нельзя. Это требование находится в статусе суперпозиции: оно вроде как выглядит разумным, но борется скорее со следствиями, чем с причинами. Чтобы исправить следствия, нужно продумать процессы, которые существуют в команде, правильно разграничить доступы и развивать техническую культуру, чтобы коллеги не ломали что-то в кластере вручную.

## Устранение неисправностей

| Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Агенты отключены или упали (спираль страха)** | Операторы остановлены вручную «для безопасного фикса»; ручные правки накопились | `flux get kustomizations -A` — статус `Suspended` или не `Ready`; `kubectl get pods -n flux-system`; в Argo CD — статус приложений и `argocd app diff` | Зафиксировать ручные правки в Git (или откатить их коммитом), включить агенты (`flux resume kustomization <name>`), дать реконсиляции вернуть кластер к желаемому состоянию; алертить на недоступность агентов, чтобы отключение было заметно |
| **Image-автоматизация обновила prod нежелательным образом** | Слишком широкая политика в `ImagePolicy` (фильтр тегов, semver-диапазон) | `flux get images policy`, `flux get images update` (команды в preview); история коммитов инфраструктурного репозитория — коммиты от image-automation-controller | `flux suspend image update <name>`; откатить коммит в Git; сузить политику (фильтр, диапазон); `flux resume image update <name>` |
| **Force-push в инфраструктурном репозитории** | История переписана; агент синхронизирует «неправильное» состояние | `flux get sources git` — ревизия не совпадает с ожидаемой; `git reflog` в локальном клоне | Восстановить историю из форка/локального клона; включить branch protection (запрет force-push); ротировать deploy-key |
| **Ручные правки «прилипли» к объектам** | 3-way merge не удаляет поля, не описанные в манифесте | `flux diff kustomization <name>`; `argocd app diff <app>`; статус `OutOfSync` | Перенести изменение в Git; если поле принадлежит другому контроллеру (HPA, вебхуки) — исключить его из сверки (`ignoreDifferences` / `spec.ignore`) |
| **Реконсиляция завершается ошибками Forbidden** | Impersonation сервис-аккаунта тенанта без RoleBinding | Статус `Kustomization`/`HelmRelease` — сообщение `Forbidden` | Создать RoleBinding для сервис-аккаунта тенанта в его namespace (см. [Flux: обзор и ключевые концепции](../flux.md)) |
| **Ошибка конфликта SSA (FieldManager Conflict)** | Поле занято другим контроллером или ручным `kubectl apply` | Логи синхронизации: `Apply failed with 1 conflict: field is owned by ...` | Добавить поле в `ignoreDifferences`, удалить конфликтное поле из Git (если им владеет HPA) либо включить `ServerSideApply=true` с опцией принудительного перезаписывания. |
| **UI Rollback откатывается обратно к сбойному состоянию** | Включен `selfHeal: true`; UI откат не изменил коммит в Git | `SyncStatus` временно становится `Synced`, затем возвращается в сбойный тег | Не использовать UI Rollback при Auto-Sync. Выполнять аварийный `suspend` либо фиксировать откат коммитом `git revert` в ветку `main`. |

## Лучшие практики

### Декомпозиция по задачам: когда GitOps нужен, а когда нет

Инженерные принципы борьбы со сложностью: не тащи новое, не тащи лишние технологии и тулинги. Инструмент не внедряет — инструмент решает задачи. Не надо внедрять GitOps, Docker и Kubernetes — надо решать задачи, которые стоят перед бизнесом и командой:

| Ваша задача | Решение |
| :--- | :--- |
| Покрывается версионированием конфигурации в Git | Git как единый источник истины — легко сделать парой несложных команд |
| Улучшить безопасность | Посмотреть на текущую инфраструктуру и процессы: возможно, путём несложных изменений можно значительно улучшить |
| Коллеги постоянно лезут в кластер руками, процесс и культуру отстроить не удаётся | Flux и ArgoCD — хороший вариант; обязательно обмониторить агентов, чтобы коллеги по-тихому не отключили операторы и не сделали что-нибудь руками в кластере |

## Дополнительная информация

**Ответы на вопросы из дискуссии:**

- **Push или pull?** Зависит от того, где находится агент: если GitOps-раннер помещён внутрь Kubernetes — это pull-модель; если агент вынесен из кластера (например, Flux-оператор снаружи или CI-раннер) — он точно так же работает по push. Иногда разделяют два кластера: один управляет CI, второй — prod.
- **ChatOps.** Если задачи решаются через chatops — используйте его.
- **Составные части.** ArgoCD — лишь один из элементов Argo Project; методология может разрастаться (Kargo и подобные проекты). Составные части GitOps можно использовать по отдельности; собирать сложные схемы имеет смысл только тогда, когда они нужны.
- **«Всегда используйте GitOps».** Ответ автора Flux («GitOps настолько прекрасен, что его нужно использовать всегда») — не ответ профессионального инженера: нужно понимать степень применимости и решать задачи здравым смыслом.
- **Мультикластер и мультикоманда.** Чудес не будет: часть вещей выносится за рамки GitOps, часть решается на уровне создания кластера; придётся что-то жертвовать.

## Вопросы для собеседования

### 1. Чем принципиально отличается механизм 3-way merge от Server-Side Apply (SSA) в GitOps?
**Ответ:** Классический клиентский **3-way merge** (`kubectl apply`) вычисляет разницу между тремя состояниями: манифестом в Git, текущим живым объектом в кластере и аннотацией `kubectl.kubernetes.io/last-applied-configuration`. Главные недостатки: лимит аннотации в 256 KB (деградация на больших манифестах/CRD) и сохранение полей, добавленных вручную вне аннотации. **Server-Side Apply (SSA)** выполняется непосредственно API-сервером Kubernetes. Вместо аннотации каждое поле отслеживается в блоке `metadata.managedFields` с указанием конкретного владельца (`fieldManager`). SSA предотвращает случайное затирание полей другими контроллерами и обходит лимит размера аннотации.

### 2. Что произойдет, если в кластере работает HPA, а в GitOps-репозитории в манифесте Deployment явно указано `spec.replicas: 3` при использовании Server-Side Apply?
**Ответ:** Возникнет конфликт владения полями (**FieldManager Conflict**). Контроллер HPA пытается динамически изменять `spec.replicas` под нагрузкой, являясь владельцем этого поля, а GitOps-агент (Argo CD или Flux) при каждом цикле реконсиляции пытается вернуть `spec.replicas: 3`. При включенном SSA API-сервер заблокирует применение манифеста с ошибкой конфликта. Для устранения проблемы поле `spec.replicas` необходимо полностью удалить из YAML-манифеста в Git (оставив поле во владении HPA), либо добавить `replicas` в секцию `ignoreDifferences` манифеста Application.

### 3. Почему попытка отката релиза кнопкой Rollback в веб-интерфейсе Argo CD считается антипаттерном и не работает при включенном `auto-sync`?
**Ответ:** Потому что фундаментальный принцип GitOps гласит: единственным источником правды является Git. Кнопка Rollback в UI пытается вернуть предыдущий ReplicaSet исключительно в рантайме кластера. Если в Argo CD включена автоматическая синхронизация с самоисцелением (`selfHeal: true`), контроллер при очередном тике реконсиляции обнаружит, что фактическое состояние кластера не совпадает с коммитом в Git (в котором всё еще зафиксирован дефектный образ), и немедленно накатит сбойную версию обратно. Правильный откат выполняется через создание коммита `git revert` в Git, либо через временный `suspend` синхронизации на время аварийных работ.

### 4. В каких ситуациях push-модель (CIOps) объективно превосходит pull-модель (GitOps)?
**Ответ:** 
1. **Эфемерные окружения (Review / Preview Environments):** создание динамических тестовых сред на каждый Pull Request разработчика и их автоматическое удаление по таймеру проще реализовать императивным шагом CI-пайплайна (`helm install / uninstall`), чем порождать тысячи временных коммитов в конфигурационном GitOps-репозитории.
2. **Сложные синхронные последовательности:** если процедура деплоя требует строгого чередования шагов: «запустить тесты $\to$ развернуть сервис $\to$ выполнить интеграционный прогон $\to$ при успехе развернуть второй сервис», push-пайплайн CI предоставляет прямолинейную оркестрацию, тогда как pull-агент асинхронен и реагирует только на факт коммита.
3. **Очень маленькие проекты и команды:** внедрение GitOps-контроллеров требует ресурсов узлов и экспертизы в поддержке операторов, что избыточно для простых монолитов на 1–2 серверах.

### 5. Что такое «спираль страха автоматизации» и как системному инженеру из нее выйти?
**Ответ:** «Спираль страха» возникает, когда инженеры отключают автоматическую реконсиляцию операторов (делают `suspend`), чтобы вручную починить сбой в кластере через `kubectl edit`. Со временем количество ручных правок накапливается, и команда боится включить авто-синхронизацию обратно, опасаясь, что GitOps снесет все их исправления и уронит прод. Выход из спирали:
1. Выполнить `argocd app diff` или `flux diff`, чтобы зафиксировать полный перечень расхождений между живым кластером и Git.
2. Перенести все необходимые рабочие изменения в манифесты Git ветки `main`.
3. Убедиться, что статус `diff` показывает только желаемые исправления.
4. Включить реконсиляцию (`resume sync`), восстановив статус Git как единственного источника правды.
