# GitOps: Образы контейнеров и их жизненный цикл

В GitOps образ контейнера является ключевым артефактом, который связывает процессы непрерывной интеграции (CI) и непрерывной доставки (CD). Правильное управление образами — основа предсказуемости, прослеживаемости и безопасности всей системы.

## Определения

- **Образ контейнера (Container Image)**: Неизменяемый (immutable) бинарный пакет, включающий приложение и его зависимости. В GitOps-конвейере образ является «грузом» (payload), который доставляется в кластер на основе изменений в Git.
- **OCI (Open Container Initiative) Артефакты**: Стандарт упаковки, позволяющий хранить в реестрах не только образы, но и Helm-чарты, манифесты, SBOM и подписи.
- **OCI 1.1 Referrers API**: Механизм, позволяющий связывать дополнительные артефакты (подписи, результаты сканирования) с основным образом через граф зависимостей без изменения digest образа.
- **Реестр образов (Image Registry)**: Централизованное хранилище артефактов (например, Harbor, GitHub Container Registry, Amazon ECR). В 2026 году реестры выполняют роль Unified Artifact Hub.
- **Дайджест (Digest)**: Уникальный неизменяемый SHA256-хеш содержимого образа. Использование дайджестов (`image@sha256:...`) вместо тегов гарантирует побайтовую идентичность развернутого кода.
- **Мульти-архитектурный образ (Multi-arch Image)**: Группа образов для разных архитектур (amd64, arm64), объединенных под одним манифестом (Manifest Index).
- **SBOM (Software Bill of Materials)**: Формализованный список всех компонентов и зависимостей внутри образа.
- **SLSA (Supply-chain Levels for Software Artifacts)**: Фреймворк для обеспечения целостности цепочки поставок ПО.

## Базовые концепции

### Разделение ответственности CI и CD

GitOps устанавливает четкую границу между сборкой артефакта и его развертыванием:

- **CI (Build & Push)**: Пайплайн собирает код, создает мульти-архитектурный образ, генерирует SBOM, подписывает его и публикует в OCI-реестр. Результат CI — **новый неизменяемый артефакт**.
- **CD (Pull & Reconcile)**: GitOps-контроллер (Argo CD, Flux) обнаруживает новый образ или изменение тега в Git и синхронизирует состояние кластера. Результат CD — **обновленное состояние Runtime**.

### OCI-центричный подход (2026)

Современный GitOps переходит от хранения всех манифестов в Git к гибридной модели:
1. **Реестр как SSoT для артефактов**: Helm-чарты и Kustomize-пакеты хранятся в OCI-реестре рядом с образами.
2. **Referrers API**: Проверки безопасности (аттестации) прикрепляются к образу. GitOps-контроллер проверяет наличие валидной подписи перед деплоем, используя Referrers API реестра.
3. **Эффективность**: Пуллинг OCI-артефактов значительно быстрее клонирования тяжелых Git-репозиториев.

### Управление тегами и неизменяемость

Использование плавающих тегов (mutable tags), таких как `latest` или `stable`, является критическим анти-паттерном в GitOps:
- **Нарушение детерминизма**: Два разных кластера могут скачать разные образы под одним тегом `latest`.
- **Отсутствие прослеживаемости**: Git-история не дает ответа на вопрос, какой именно код работал вчера, если тег был перезаписан.

**Рекомендация**: Используйте SemVer (`v1.2.3`) или хеш коммита (`sha-abc1234`). Для критических сред (Production) применяйте **Digest Pinning** — фиксацию образа по его SHA256-дайджесту.

## Практические сценарии

### Сценарий 1: Мульти-архитектурные образы в GitOps

**Проблема**: В инфраструктуре используются узлы как на `amd64`, так и на `arm64` (например, Apple Silicon или AWS Graviton).
**Действия**:
1. Соберите образ для нескольких платформ (используя `docker buildx` или `kaniko`):
   ```bash
   docker buildx build --platform linux/amd64,linux/arm64 -t registry.com/app:1.2.3 --push .
   ```
2. В Git-манифесте укажите тег `1.2.3`. Kubernetes при пуллинге автоматически выберет нужный слой на основе архитектуры узла, сохранив единый источник истины в Git.

### Сценарий 2: Продвижение образов через Kargo

**Проблема**: Необходимо безопасно переносить изменения из `Staging` в `Production`, не пересобирая образ.
**Действия**:
1. **Kargo** (или аналогичные инструменты) отслеживает появление новых образов в реестре.
2. При успешном прохождении тестов в `Staging`, Kargo обновляет манифесты в Git для `Production`, используя тот же Digest образа, который был проверен в `Staging`.
3. Это гарантирует, что в продакшене работает побайтово идентичный артефакт.

### Сценарий 3: Автоматизация обновления (Image Automation)

Автоматическая синхронизация тегов в Git при появлении новых версий в реестре.

- **Flux Image Automation**:
  - `ImageRepository`: Сканирует реестр.
  - `ImagePolicy`: Определяет правила (например, `semver: 1.x.x`).
  - `ImageUpdateAutomation`: Создает коммит в Git с обновленным тегом.
- **Argo CD Image Updater**: Работает на основе аннотаций в ресурсе `Application`, обновляя параметры без непосредственного коммита в Git (рекомендуется для Dev/QA сред).

### Сценарий 4: Зеркалирование в закрытых контурах (Air-gapped)

В изолированных сетях GitOps-контроллер не имеет доступа к публичным реестрам.
**Реализация**:
1. Используйте `skopeo` или встроенные функции **Harbor** для зеркалирования (Replication) образов из внешнего реестра во внутренний.
2. В Git-манифестах используйте внутренние адреса или настройте `ImagePullSecrets` и `registry-mirrors` в конфигурации рантайма (containerd/docker).
