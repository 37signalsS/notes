# GitOps: Журналы Аудита и Трассируемость

В GitOps-подходе, где Git является единым источником истины, журналы аудита обеспечивают критически важную возможность отслеживать все изменения от коммита до работающего в кластере приложения.

## Определения

- **Журнал аудита (Audit Log)**: Неизменяемая, хронологически упорядоченная запись о событиях в системе. В контексте GitOps, это ответ на вопросы "кто, что, когда и где изменил".
- **Трассируемость (Traceability)**: Способность проследить полный жизненный цикл изменения — от автора коммита и Pull Request'а до конкретного `Pod`, запущенного в кластере.

## Основные концепции

### Зачем нужен аудит в GitOps?
1.  **Безопасность**: Расследование инцидентов, обнаружение неавторизованных изменений.
2.  **Соответствие требованиям (Compliance)**: Предоставление доказательств для аудиторов (например, для SOX, PCI-DSS), подтверждающих, что все изменения контролируются и авторизованы.
3.  **Отладка**: Быстрый поиск коммита, который привел к ошибке в работе приложения.

### Ключевые источники данных для аудита

Эффективный аудит в GitOps строится на корреляции данных из нескольких источников:

- **История Git**: Главный источник правды о *намерениях*. Показывает, *кто* предложил изменение и *когда*. Использование подписанных коммитов (`GPG`) обязательно для высокого уровня доверия.
- **Логи GitOps-инструмента (ArgoCD/Flux)**: Журналы, которые связывают *намерение* (коммит) с *действием* (синхронизация). Они показывают, когда инструмент обнаружил изменение и начал его применение.
- **Журналы аудита Kubernetes API**: Фундаментальный источник правды о том, что *фактически* произошло в кластере. Фиксирует каждый запрос к API-серверу.
- **Логи Policy-движков (OPA Gatekeeper, Kyverno)**: Записи об отклоненных (или разрешенных) действиях, которые нарушают заданные политики безопасности.

## Практические сценарии

### Сценарий 1: Расследование инцидента в Argo CD

**Проблема**: В production-окружении неожиданно изменилось поведение сервиса.
**Действия**:
1.  Откройте UI Argo CD, найдите приложение и перейдите во вкладку "History & Rollback".
2.  Найдите последнюю операцию синхронизации, которая совпадает со временем инцидента.
3.  Скопируйте хеш коммита (`Revision`) из деталей синхронизации.
4.  В Git-репозитории найдите этот коммит (`git show <hash>`) и связанный с ним Pull Request, чтобы определить автора, ревьюеров и причину изменения.

### Сценарий 2: Сбор логов аудита в Flux

**Проблема**: Необходимо собрать все события синхронизации за последний час для отчета.
**Действия**:
1.  Используйте CLI Flux для просмотра логов всех его контроллеров:
    ```bash
    flux logs --all-namespaces --since=1h
    ```
2.  Проверьте события Kubernetes, сгенерированные контроллерами Flux, чтобы увидеть высокоуровневую картину:
    ```bash
    # Посмотреть события, связанные с Kustomization
    kubectl get events -A --field-selector involvedObject.kind=Kustomization
    ```

### Сценарий 3: Настройка аудита K8s для GitOps-агента

**Проблема**: Необходимо логировать все изменения, которые GitOps-инструмент (например, Argo CD) вносит в `Deployments` и `Secrets`.
**Действия**: Настройте политику аудита Kubernetes API Server, чтобы отслеживать запросы от сервисного аккаунта Argo CD.

```yaml
# Фрагмент audit-policy.yaml
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  # Логировать запросы на изменение от ServiceAccount Argo CD
  - level: RequestResponse
    users: ["system:serviceaccount:argocd:argocd-application-controller"]
    verbs: ["create", "update", "patch", "delete"]
    resources:
      - group: "apps"
        resources: ["deployments", "statefulsets"]
      - group: "" # Core API group
        resources: ["secrets", "configmaps"]
```
