# GitOps: Журналы аудита и трассируемость

В GitOps-подходе, где Git является единым источником истины, журналы аудита обеспечивают критически важную возможность отслеживать все изменения от коммита до работающего в кластере приложения.

## Определения

- **Журнал аудита (Audit Log)**: Неизменяемая, хронологически упорядоченная запись о событиях в системе. В контексте GitOps это ответ на вопросы "кто, что, когда и где изменил".
- **Трассируемость (Traceability)**: Способность проследить полный жизненный цикл изменения — от автора коммита и Pull Request (Запрос на слияние, PR) до конкретного `Pod`, запущенного в кластере.
- **SLSA (Supply-chain Levels for Software Artifacts)**: Фреймворк безопасности для обеспечения целостности артефактов и цепочки поставок программного обеспечения.
- **OIDC (OpenID Connect)**: Протокол идентификации поверх OAuth 2.0, используемый в GitOps для привязки действий в инструментах (Argo CD, Flux) к реальным учетным записям пользователей.
- **Отклонение (Drift)**: Расхождение между состоянием инфраструктуры, описанным в Git, и фактическим состоянием ресурсов в кластере.

## Базовые концепции

### Зачем нужен аудит в GitOps?

1. **Безопасность**: Расследование инцидентов, обнаружение неавторизованных изменений.
2. **Соответствие требованиям (Compliance)**: Предоставление доказательств для аудиторов (например, Sarbanes-Oxley Act (SOX) или Payment Card Industry Data Security Standard (PCI-DSS)), подтверждающих, что все изменения контролируются и авторизованы.
3. **Отладка**: Быстрый поиск коммита, который привел к ошибке в работе приложения.
4. **Целостность (Integrity)**: Гарантия того, что в кластер попадает только проверенный и подписанный код.

### Трехуровневая модель аудита

Эффективный аудит в 2026 году строится на корреляции данных из трех уровней:

- **Уровень Git (Намерение)**: Главный источник правды. Показывает, *кто* предложил изменение. Использование GPG (GNU Privacy Guard)-подписей обязательно для подтверждения авторства.
- **Уровень контроллера (Действие)**: Логи Argo CD или Flux, которые связывают коммит с процессом синхронизации. Показывают, *кто* и *когда* инициировал деплой (через SSO/OIDC).
- **Уровень кластера (Реальность)**: Журналы аудита API (Application Programming Interface) Kubernetes. Фундаментальный источник правды о том, что *фактически* произошло в кластере.

### Целостность цепочки поставок (SLSA)

Для высокого уровня соответствия (SLSA Build Level 3) аудит должен включать:
- **Аттестация происхождения (Provenance)**: Подписанные метаданные о том, как и где был собран образ.
- **Проверка подписей**: GitOps-оператор (например, Flux с Cosign) проверяет подпись образа перед его развертыванием.

## Практические сценарии

### Сценарий 1: Расследование инцидента в Argo CD (SSO и JSON логи)

**Проблема**: В production-окружении изменилось поведение сервиса. Необходимо найти инициатора.
**Действия**:

1. В системе сбора логов (например, Grafana Loki) выполните поиск по событиям синхронизации. В 2026 году рекомендуется использовать JSON-формат логов для Argo CD.

    ```bash
    # Пример запроса в Loki для поиска действий пользователя
    {container="argocd-server"} |= "sync" |= "user@example.com"
    # → result: 
    # {"time":"2026-07-21T10:00:00Z","level":"info","msg":"User initiated sync","user":"user@example.com","app":"payments-api","revision":"a1b2c3d"}
    ```

2. В UI (User Interface) Argo CD перейдите во вкладку "History & Rollback", найдите `Revision` и связанный с ним Pull Request в Git.

### Сценарий 2: Сбор логов и событий в Flux

**Проблема**: Аудит событий синхронизации за последний час.
**Действия**:

1. Используйте CLI (Command Line Interface) Flux для просмотра логов:

    ```bash
    flux logs --all-namespaces --since=1h
    # → result: 
    # 2026-07-21T09:00:00Z info Kustomization/flux-system.flux-system - server-side apply completed
    # 2026-07-21T09:05:00Z info GitRepository/flux-system.flux-system - fetched revision main@sha256:4f5e6d...
    ```

2. Экспортируйте события в SIEM (Security Information and Event Management) через `notification-controller` для долгосрочного хранения (рекомендуется 1 год и более).

### Сценарий 3: Настройка аудита K8s для GitOps-агента

**Проблема**: Логирование изменений, вносимых Argo CD в `Secrets` и `Deployments`.
**Действия**: Настройте политику аудита API-сервера Kubernetes.

```yaml
# Фрагмент audit-policy.yaml
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  # Логировать запросы на изменение от ServiceAccount Argo CD
  - level: RequestResponse
    users: ["system:serviceaccount:argocd:argocd-application-controller"]
    verbs: ["create", "update", "patch", "delete"]
    resources:
      - group: "apps"
        resources: ["deployments", "statefulsets"]
      - group: "" # Core API group
        resources: ["secrets", "configmaps"]
```

### Сценарий 4: Обнаружение отклонений (Drift Detection)

**Проблема**: Кто-то внес изменения в кластер вручную через `kubectl`.
**Действия**: 
1. Настройте алертинг на состояние `OutOfSync` в Argo CD или оповещения о дрифте в Flux.
2. Логи самовосстановления (Self-healing) должны фиксироваться как инциденты безопасности:
   - "Drift Corrected": Контроллер обнаружил ручное изменение и откатил его к состоянию в Git.
