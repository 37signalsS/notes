# Организация Flux CD monorepo: кейс миграции с Flux v1 на ~20 кластерах

**Актуально для:** Flux v2.2–v2.4 (legacy — кейс доклада; организационные практики и структура репозитория применимы и к текущей линейке v2.9.x)

Файл систематизирует опыт команды (доклад Алексея Кругляка и Светозара с конференции DevOps), которая перевела гибридную инфраструктуру — Google Kubernetes Engine плюс собственный дата-центр — с Flux v1 на Flux v2 и организовала единый monorepo для всех кластеров. Справочник по контроллерам, CRD и сценариям Flux — в [обзоре Flux](../flux.md); топологии мультикластерных парков — в [мульти-кластерных паттернах](./multi_cluster_patterns.md).

## Определения

- **Monorepo Flux** — единый Git-репозиторий, хранящий и конфигурацию самих кластеров, и шаблоны всех компонентов; в кейсе состоит всего из двух директорий верхнего уровня: `clusters/` и `components/`.
- **`clusters/`** — директория с конфигурацией кластеров: по одной поддиректории на кластер, внутри — `custom-resources/` и `sync-code/`.
- **`components/`** — директория с шаблонами компонентов (приложений, аддонов, политик), переиспользуемыми во всех кластерах.
- **custom-resources/** — поддиректория кластера с ресурсами и значениями конкретного кластера: ConfigMap, патчи, кастомные ресурсы.
- **sync-code/** — поддиректория кластера с объектами `Kustomization`, которые «подключают» компоненты из `custom-resources/`; внутри команды называется «подключение компонентов».
- **Сквозной нейминг** — конвенция: `Kustomization`, подключающий компонент, и сам ресурс (например, `HelmRelease`) носят одно и то же имя.
- **Заглушка невалидного ключа** — приём в шаблонах NetworkPolicy: ключ `namespace` с заведомо невалидным значением, чтобы шаблон нельзя было случайно применить напрямую.

## Базовые концепции

### Откуда выросла задача

Исходное состояние (за три года до момента доклада):

- Flux v1 на ~20 кластерах; под каждый кластер — отдельная маленькая репа.
- Гибридная инфраструктура: часть кластеров в Google Cloud, часть — в собственном дата-центре (Kubernetes 1.14).
- Два Terraform-модуля использовались как шаблоны (git-субмодули), поверх них — код кластера.
- Технический долг: Flux v1 на подходе к EOL (достигнут в ноябре 2022), старый софт в старых кубах, автообновление подгоняло софт под свежие кластеры GKE, нет единых стандартов NetworkPolicy и RBAC, git-субмодули.
- Требование сертификации ISO 27001: возможность пройти disaster recovery — а при прогоне DR создаются свежие кластеры GKE, под которые софт не подходит.

Требования к решению: наблюдаемость, версионирование, наборы шаблонов, простота для новых людей, возможность обновлять компоненты через код.

### Почему не Argo CD

Рассматривались два варианта: обновиться до Flux v2 или перейти на Argo CD. Argo CD отклонён:

- в компании не было production-опыта с Argo CD;
- Continuous Delivery уже был организован на другом инструменте (с удобным GUI для разработчиков), и ломать этот процесс не хотели;
- у команды была экспертиза именно во Flux.

Разработчикам оставлен привычный инструмент (зона комфорта), платформенная команда работает во Flux. Это частный случай выбора инструмента — сравнение архитектур и манифестов обоих инструментов — в [сравнении ArgoCD и Flux](../argo_vs_flux_manifests.md).

### Чем Flux v1 отличается от v2

- **Flux v1** — монолит: поднимал поду, рекурсивно выкачивал репозитории вместе с git-модулями, делал собственный customize и применял голые манифесты.
- **Flux v2** — полноценный оператор из набора GitOps Toolkit: шесть контроллеров (source, kustomize, helm, notification, image-reflector, image-automation). В кейсе используются только первые три; notification и image-automation не задействованы, потому что не требовались.

### Проблемы апгрейда v1 → v2

Накатили Flux v2 на один кластер и столкнулись:

1. Старые шаблоны не подходят: v2 не выкачивает весь репозиторий рекурсивно с субмодулями — другая архитектура работы с источником.
2. Разные настройки для старых и новых кубов: новые правила NetworkPolicy, RBAC и прочее.
3. **CRD не обновлялись при апгрейде чарта Prometheus.** Причина — в дизайне Helm: `helm upgrade` устанавливает CRD только при их отсутствии и не обновляет существующие (явное решение сообщества Helm из соображений защиты от случайной потери данных). Обходной путь в кейсе: зависимость одного компонента от другого — CRD чарта Prometheus устанавливаются отдельной Kustomization, а сам чарт подключается через `dependsOn` после неё. Этот паттерн (CRD → оператор → кастомные ресурсы) документирован в [управлении порядком развертывания](../flux.md).

Вывод: развивать v1 и обновлять 20 репозиториев до v2 — значит заблокировать работу со всеми кластерами; нужна другая организация кода.

### Первая попытка monorepo и почему она не взлетела

Скопировали структуру из примеров fluxcd (директории `clusters/`, `apps/`, `infrastructure/`). Проблемы:

- **Копипаста**: новый инженер копирует конфигурацию из соседнего кластера и меняет параметры; конфигурации большие (особенно Prometheus — десятки листов), в результате где-то компоненты сконфигурированы неправильно, где-то запрашивают больше ресурсов, чем есть в кластере.
- **Сломанная синхронизация** — отчасти связана с CRD (см. выше).
- Отсутствие реального референса: доклады на конференциях ограничивались хайлайтами, внутренности организаций не показывались.

Реакция команды была взрывной («верните первый флагс», «лучше бы аргу затащили») — сигнал, что monorepo влечёт рост сложности и порогов входа, и его нужно проектировать под людей: команда всегда обновляется, кто-то уходит, кто-то приходит.

### Текущая структура: две директории

```text
flux-monorepo/
├── clusters/                      # конфигурация кластеров
│   ├── prod-cluster/
│   │   ├── custom-resources/      # значения, патчи, ConfigMap; поддиректория = namespace
│   │   └── sync-code/             # Kustomization, подключающие компоненты
│   └── stage-cluster/
│       ├── custom-resources/
│       └── sync-code/
└── components/                    # шаблоны компонентов (переиспользуются)
    ├── flux/                      # манифесты bootstrap Flux (по версиям на окружение)
    ├── network-policies/          # базовый шаблон политик
    ├── monitoring/                # Prometheus и т.п.
    └── nginx/                     # шаблон приложения
```

Принципы:

- **Плоская структура**: каждая поддиректория в `custom-resources/` и `sync-code/` — это имя namespace; всё, что относится к namespace `monitoring`, всегда лежит в `monitoring/` в обоих местах.
- **sync-code — «подключение компонентов»**: объект `Kustomization` ссылается на `custom-resources/<namespace>` и рендерит компоненты. Именно с объекта `Kustomization` (в терминологии доклада — «customization»), указывающего на Git-репозиторий, ветку и путь, начинается вся цепочка синхронизации.
- **Относительные пути из custom-resources в components/**: внутри `custom-resources/<namespace>/` лежит `kustomization.yaml`, который подключает базу из `components/` по относительному пути и накладывает патчи кластера. Это известный неудобный момент схемы: относительные пути неизбежны, альтернатива — разносить базу и оверлеи по разным репозиториям (как в документации Flux), но тогда приходится прыгать между репозиториями; в одном monorepo всё видно сразу.
- **Ветка как переключатель**: `Kustomization` указывает ветку репозитория — кластер может синхронизироваться не с master, а с веткой техобслуживания или эксперимента, что даёт гибкость без отдельной инфраструктуры.
- Окружения разделены кластерами: внутри одного кластера нет смешения prod/stage/dev — кластер либо продакшен, либо стейджинг.

## Практические сценарии

### Сценарий 1: Bootstrap Flux и версионирование по окружениям

Три способа bootstrap (из документации Flux):

1. Бинарник: `flux install` — установка в текущий контекст.
2. Отрендеренные манифесты: `flux install --export` → `kubectl apply` (или любой внешний CD/IaC).
3. Flux Operator: описание Flux как объекта `FluxInstance`.

В кейсе выбран второй путь. В `components/` хранятся три набора манифестов Flux — по версии на окружение (на момент доклада):

| Окружение | Версия Flux | Назначение |
| :--- | :--- | :--- |
| prod | самая старая стабильная линейка | максимальная стабильность |
| stage | v2.2.3 | промежуточная |
| dev | v2.4 (самая свежая на момент доклада) | тестирование новинок |

Это позволяет платформенной команде управлять группами кластеров: dev-кластеры всегда на свежей версии Flux, на них всё тестируется, прод держит проверенное. Манифесты применяются Terraform-модулем при создании кластера: модуль применяет код bootstrap нужного окружения (prod или stage) сразу после раскатки мастеров и воркеров. Та же структура даёт контролируемый upgrade/downgrade Flux — в демо для наглядности как раз поднят кластер со старой версией, чтобы показать обновление.

Современная альтернатива (упомянута в докладе): Flux Operator — декларативное управление версией и составом контроллеров через `FluxInstance`; докладчики рекомендуют использовать его. Подробности — в [управлении жизненным циклом через Flux Operator](../flux.md).

Проверка после bootstrap:

```bash
flux check
# ► checking components
# ✔ source-controller is healthy
# ✔ kustomize-controller is healthy
# ✔ helm-controller is healthy
# ✔ all components are healthy

flux get kustomizations --namespace flux-system
# -> NAME         REVISION              SUSPENDED  READY  MESSAGE
# -> flux-system  main@sha1:<hash>      False      True   Applied revision: main@sha1:<hash>
```

### Сценарий 2: Подключение компонента в кластере

Пример: Prometheus в namespace `monitoring`.

`clusters/<cluster>/custom-resources/monitoring/` — значения и патчи кластера, включая ConfigMap с переменными (без которой реконсиляция Prometheus не взлетит — см. раздел «Устранение неполадок»).

`clusters/<cluster>/sync-code/monitoring/` — Kustomization, ссылающийся на custom-resources и подключающий компонент:

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: monitoring        # сквозной нейминг: имя = имя компонента/namespace
  namespace: flux-system
spec:
  interval: 5m            # в реальных кластерах кейса — 5–10 минут
  sourceRef:
    kind: GitRepository
    name: flux-monorepo
  path: ./clusters/<cluster>/custom-resources/monitoring
```

Диагностика без выхода из контекста кластера:

```bash
flux get kustomizations
# -> NAME        REVISION              SUSPENDED  READY   MESSAGE
# -> monitoring  main@sha1:<hash>      False      True    Applied revision: main@sha1:<hash>

kubectl describe kustomization monitoring -n flux-system   # события и причины неудач
kubectl logs -n flux-system deploy/kustomize-controller --tail=100
```

Наблюдение из демо: после добавления недостающей ConfigMap реконсиляция Prometheus прошла за ~70 секунд; интервалы в демо подрезаны до 10 секунд, в реальных кластерах — 5–10 минут (часть подобрана опытным путём, часть — подобрана «с потолка», как признают докладчики).

### Сценарий 3: Network Policies — базовый шаблон + кластерные значения

Боль: стандартизация NetworkPolicy по всем кластерам. Решение — один базовый шаблон, перекрываемый значениями каждого кластера.

Базовый набор политик (катится во все кластеры кроме особых случаев):

- разрешить подам общаться внутри namespace;
- запретить весь входящий трафик (deny-all ingress);
- разрешить DNS (как подам, так и сервисом — но не открывать всю подсеть по умолчанию).

Кластерные значения собираются отдельно: pod CIDR, service CIDR, CIDR мастеров/воркеров, приватные сети, локальный DNS. Это нужно из-за гибридной инфраструктуры: в дата-центре свои сети и нарезки, а дефолтный DNS Google открывать не хочется — разрешается только туда, куда надо.

Приём «заглушки невалидного ключа»: в каждом шаблоне NetworkPolicy присутствует ключ `namespace` с заведомо невалидным значением — специально, чтобы никто не применил шаблон точечно по ошибке. Если политика нужна в каждом кластере по умолчанию — она в базовом шаблоне; если нужна точечно — собирается из конструктора базовых политик (разрешить интернет / интернет только с лейблами / deny-all и т.п.).

Альтернативная реализация NetworkPolicy в GitOps (отдельные файлы base/overlays, валидация conftest/kuttl) — в [NetworkPolicy: CI/CD и GitOps](../../Kubernetes/Networking/Network/NetworkPolicy/gitops_ci_cd.md).

### Сценарий 4: Шаблон приложения и сквозной нейминг

Максимально упрощённый пример из кейса — nginx: `components/nginx/` содержит один файл, `HelmRelease` обычного nginx из репозитория bitnami (иллюстративная реконструкция):

```yaml
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: nginx1          # имя = имя Kustomization, подключающего компонент
  namespace: monitoring # поддиректория custom-resources с патчами
spec:
  interval: 10m
  chart:
    spec:
      chart: nginx
      repository: https://charts.bitnami.com/bitnami
      version: ">=20.0.0"
  values:
    # ...
```

В кластере два разных nginx с разными конфигами: базовый `HelmRelease` патчится через файл в `custom-resources/<namespace>/` — патч фиксирует, например, версию и специфичные значения.

Конвенции кейса:

- **Сквозной нейминг**: `Kustomization` называется X → подключающий его `Kustomization` в sync-code называется X → `HelmRelease` (или другой ресурс) тоже X. Всё одинаково — иначе рано или поздно забывается поправка где-то в цепочке.
- **README рядом с компонентом**: рядом с шаблоном кладётся README со всеми возможными значениями и ссылкой на оригинальный чарт (например, ссылка на bitnami/nginx chart values), чтобы инженеру не нужно было догадываться, какие файлы создать: «создайте в custom-resources файл X, сделайте в нём kustomize-изменения, подключите в sync-code».
- Кастомизация Kustomize очень гибка — и потому легко превращается в «абсолютную грязь»; конвенции существуют именно как противовес.

### Сценарий 5: Наблюдаемость и контроль

- Графана-дашборд: что влито в master и состояние синхронизации кластеров.
- Статусы объектов Flux (`flux get kustomizations`, `flux get sources git`) дают ответ «что сейчас синкается и с какой ветки» без лазания в репозиторий.
- Ошибки читаются из статуса объекта: например, «не удалось подставить переменные из ConfigMap cluster-variables» — сразу понятно, чего нет и на каком этапе сломалось (контроллеров несколько, сломаться можно на разных этапах: кривые лейблы, неотделанный kustomize, ошибка рендера).

## Устранение неполадок

Проблемы, с которыми столкнулась команда в кейсе, и их решения:

| Проблема | Причина | Решение в кейсе |
| :--- | :--- | :--- |
| CRD Prometheus не обновлялись при апгрейде чарта | Helm по дизайну не обновляет CRD при `helm upgrade` | Отдельная Kustomization для CRD + `dependsOn` (см. [flux.md](../flux.md)) |
| Копипаста между кластерами → неправильная конфигурация, перерасход ресурсов | Отсутствие шаблонов и конвенций | Базовые шаблоны в `components/`, патчи в `custom-resources/`, сквозной нейминг |
| Сломанная синхронизация части компонентов | Частично CRD, частично ошибки конфигурации | Чтение статуса объекта (`kubectl describe`, логи контроллеров) |
| Обновление Flux v1 → v2 на 20 репозиториев блокирует работу | Переписывание компонентов и шаблонов в каждом кластере | Monorepo: шаблоны в одном месте, кластеры — тонкие конфигурации |
| Многорепозиторий приложений: репозиторий bitnami весит почти гигабайт (оценка докладчиков), 30 компонентов → ~30 ГБ трафика | Один общий «apps»-репозиторий на все компоненты | Открытый вопрос кейса: жертвовать трафиком ради гарантии синхронизации или искать готовое решение; готового решения «из коробки» у команды нет |

## Рекомендации

Вынесенные из кейса практики:

1. **Две директории** (`clusters/` + `components/`) вместо копирования структуры из примеров — меньше поверхности для копипасты.
2. **Плоская структура по namespace**: поддиректория = namespace, одинаково в `custom-resources/` и `sync-code/`.
3. **Сквозной нейминг** всех связанных объектов.
4. **README с ссылкой на оригинальный чарт** рядом с каждым шаблоном компонента.
5. **Версионирование самого Flux по окружениям** (prod/stage/dev) — платформенная команда управляет группами кластеров, свежее тестируется на dev.
6. **Окружения — отдельные кластеры**, без смешения внутри кластера.
7. **Базовые NetworkPolicy как шаблон** с кластерными значениями (CIDR, локальный DNS) и заглушкой невалидного ключа против точечного применения.
8. **CRD выносить в отдельный компонент** с `dependsOn` — Helm их не обновляет при upgrade.
9. **Bootstrap через отрендеренные манифесты** (`flux install --export`), применяемые Terraform-модулем при создании кластера.
