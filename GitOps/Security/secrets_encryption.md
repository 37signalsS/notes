# GitOps: Управление секретами

> **Актуальные версии (февраль 2026):** SOPS v3.9, Sealed Secrets v0.28, Vault v1.18.

Хранение секретов — одна из главных проблем в GitOps. Поскольку Git является источником истины, хранить в нем пароли и ключи в открытом виде недопустимо. Эта заметка описывает ключевые подходы для безопасного управления секретами.

## Определения

- **Секрет (Secret)**: Любые чувствительные данные, необходимые приложению для работы: пароли от баз данных, API-ключи, TLS-сертификаты.
- **Шифрование в Git (Encryption-in-Git)**: Подход, при котором зашифрованная версия секрета коммитится в Git. Расшифровка происходит непосредственно в кластере в момент развертывания.

## Базовые концепции

### Проблема: Секреты в Git

Стандартный ресурс Kubernetes `Secret` — это просто строка в Base64, а не шифрование. Коммитить такие манифесты в Git-репозиторий — все равно что публиковать пароли в открытом доступе. Это нарушает принципы безопасности и затрудняет аудит.

### Ключевые подходы

1. **Шифрование в Git (Sealed Secrets, SOPS)**: Зашифрованный секрет хранится в Git. Специальный контроллер в кластере с доступом к ключу расшифровывает его перед применением. **Плюс**: вся конфигурация по-прежнему в Git. **Минус**: нужно управлять ключами шифрования.
2. **Внешнее хранилище (HashiCorp Vault)**: Секреты хранятся в специализированной системе (Vault, AWS Secrets Manager). В Git хранится только ссылка на секрет или конфигурация для его инъекции. **Плюс**: централизованное управление, ротация, аудит. **Минус**: усложнение архитектуры, зависимость от внешней системы.

### Сравнение инструментов

| Инструмент | Шифрование | Ключи | GitOps | Сложность |
| :--- | :--- | :--- | :--- | :--- |
| **Sealed Secrets** | Асимметричное (RSA) | Один приватный ключ в кластере | Полная | Низкая | [Sealed Secrets](../../Kubernetes/Security/sealed_secrets_overview.md) |
| **SOPS** | Симметричное (AES) + KMS/PGP/age | KMS, PGP, age | Полная (Flux нативно) | Средняя | [SOPS](../../Security/Tools/sops_overview.md) |
| **Vault** | Динамические секреты | Transit Engine | Через агент/интеграцию | Высокая | [Vault](../../Vault/overview.md) |

## Практические сценарии

### Сценарий 1: Bitnami Sealed Secrets

Идеально для старта. Прост в настройке и использовании.

- **Как работает**: В кластере работает `sealed-secrets-controller`, который хранит приватный ключ. Локально с помощью CLI `kubeseal` обычный `Secret` шифруется публичным ключом контроллера. В Git коммитится только CRD `SealedSecret`. Контроллер в кластере "видит" этот ресурс и расшифровывает его в обычный `Secret`.
- **Пример `SealedSecret` в Git**:

    ```yaml
    apiVersion: bitnami.com/v1alpha1
    kind: SealedSecret
    metadata:
      name: my-secret
      namespace: my-app
    spec:
      encryptedData:
        # Зашифрованные данные
        DATABASE_PASSWORD: AgA...
      template:
        metadata:
          name: my-secret
    ```

> **Подробное руководство:** см. **[Sealed Secrets](../../Kubernetes/Security/sealed_secrets_overview.md)**.

### Сценарий 2: Mozilla SOPS

Более гибкий инструмент, интегрируется с облачными KMS, PGP и age. Flux поддерживает SOPS "из коробки".

- **Как работает**: С помощью CLI `sops` шифруются не целые файлы, а только конкретные поля (`values`) внутри YAML-файлов. В Git коммитится YAML-файл с зашифрованными полями. GitOps-инструмент с доступом к ключу (например, через `Secret` в кластере) расшифровывает поля во время рендеринга манифестов.
- **Пример для Flux + SOPS**:

    ```yaml
    # Kustomization ссылается на ключ для расшифровки
    apiVersion: kustomize.toolkit.fluxcd.io/v1
    kind: Kustomization
    metadata:
      name: my-app
    spec:
      # ...
      decryption:
        provider: sops
        secretRef:
          name: sops-age-key # Secret с приватным ключом age
    ```

> **Подробное руководство:** см. **[SOPS](../../Security/Tools/sops_overview.md)**.

### Сценарий 3: HashiCorp Vault (Внешнее хранилище)

Промышленный стандарт для крупных инсталляций.

- **Как работает**: Секреты хранятся в Vault. В Git-репозитории в манифесте `Deployment` указываются аннотации, которые описывают, какие секреты и откуда из Vault нужно получить. Специальный агент (`vault-agent-injector`) в Kubernetes "на лету" модифицирует создаваемые поды, добавляя в них init- или sidecar-контейнер, который аутентифицируется в Vault и инжектирует секреты в под.
- **Основная идея**: GitOps-инструмент не знает о самих секретах, он лишь деплоит "заглушку", которая будет заполнена секретами в runtime.

> **Подробное руководство:** см. **[HashiCorp Vault](../../Vault/overview.md)** и **[ArgoCD Vault Integration](../ArgoCD/argocd_vault_integration.md)**.
