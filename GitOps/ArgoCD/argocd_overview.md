# ArgoCD — декларативный CI/CD для Kubernetes

 Установка: `kubectl apply -n argocd --server-side --force-conflicts -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml`

См. также: [Сравнение с Flux](../argo_vs_flux_manifests.md), [Установка и настройка](./argocd_installation_and_setup.md), [Troubleshooting](./argocd_troubleshooting_and_monitoring.md)

## Определения

**ArgoCD** — это декларативный [GitOps-инструмент](../GitOps_overview.md) непрерывной доставки (CD) для Kubernetes. Он автоматизирует развертывание приложений и синхронизирует состояние кластера с Git-репозиторием, который выступает как основной источник конфигурации.

Вся архитектура и функциональность Argo CD — от базовых ресурсов `Application` до сложных шаблонов вроде `ApplicationSet` — базируется на **возможности расширения API Kubernetes** через механизмы пользовательских определений ресурсов (CRD) и операторов. Именно это делает его нативным и глубоко интегрированным решением для экосистемы Kubernetes.

## Основные концепции

### Назначение ArgoCD

- **Автоматизация развертывания:** устраняет ручное управление развертыванием через `kubectl apply`.
- **Мониторинг расхождений:** постоянно следит за отклонением (drift) между состоянием Git и кластера и корректирует его.
- **Мультикластерность:** управление несколькими кластерами из одного экземпляра ArgoCD.
- **Контроль версий:** использование Git как единственного источника правды для аудита и отката.
- **Поддержка форматов:** работа с нативными манифестами Kubernetes, Helm-чартами, Kustomize и Jsonnet.

### Ключевые возможности

- **Веб-интерфейс и CLI:** визуальное отслеживание ресурсов и расширенное управление через терминал.
- **Интеграция с SSO:** поддержка OpenID Connect (OIDC), OAuth2, LDAP, SAML 2.0, а также провайдеров GitHub, GitLab (**[инструкция по настройке](./argocd_sso_gitlab.md)**), Microsoft и LinkedIn.
- **Интеграция с RBAC:** детальное управление правами доступа через внутренние политики или внешние IdP.
- **ApplicationSet:** автоматизация создания приложений на основе шаблонов (генераторы: git, cluster, list, matrix).
- **Система уведомлений:** отправка оповещений через **[ArgoCD Notifications](./argocd_notifications.md)**.
- **Самообслуживание (Self-service):** предоставление разработчикам возможности развертывать приложения в рамках разрешенных лимитов и неймспейсов без участия администраторов.
- **Source Hydrator (v3.1+):** механизм для обработки "сырых" манифестов перед их применением, что упрощает работу с динамическими данными.

### Двунаправленная синхронизация

ArgoCD не только применяет изменения, но и защищает кластер от ручных правок. Если ресурс изменен в обход Git, ArgoCD пометит его как `OutOfSync` и (при включенном `SelfHeal`) вернет к эталонному состоянию. Подробности: **[Синхронизация в ArgoCD](./synchronization.md)**.

### Ключевые абстракции

- **Application:** Основная единица управления, представляющая собой организованную группу ресурсов Kubernetes (Deployment, Service и т.д.), которые развертываются и управляются как единое целое. Внутри кластера ArgoCD каждое приложение является **экземпляром Custom Resource Definition (CRD)**. Это позволяет целостно управлять зависимостями и состоянием всей группы ресурсов.
- **ApplicationSet:** Инструмент для массового управления приложениями на основе шаблонов.
- **AppProject (Project):** Логическая группа для реализации **мультитенантности**. Ограничивает ресурсы, кластеры и права доступа.

## Продвинутые шаблоны (Advanced Patterns)

### Шаблон «App-of-Apps»

Решает проблему управления самими объектами `Application` через GitOps. Вместо того чтобы создавать каждое приложение вручную через CLI или UI, вы создаете одно «корневое» приложение.

*   **Как это работает:**
    1.  **Корневое приложение (Root App):** Указывает на директорию в Git, содержащую манифесты других приложений Argo CD (дочерних).
    2.  **Дочерние приложения (Child Apps):** Каждый манифест дочернего приложения указывает на директорию с фактическими ресурсами Kubernetes (Deployment, Service и т.д.).
    3.  **Рекурсивная синхронизация:** Argo CD синхронизирует корневое приложение, которое создает дочерние приложения, а те, в свою очередь, развертывают микросервисы в кластер.
*   **Преимущества:** Централизованное управление всей средой из одного источника, логическая группировка связанных сервисов и эффективный мониторинг статуса всей системы через один родительский объект.
*   **Когда использовать:**
    *   Начальная загрузка (bootstrapping) новых кластеров с фиксированным набором приложений.
    *   Группировка логически связанных микросервисов в единый блок управления.
    *   Реализация GitOps для самих ресурсов Argo CD при ограниченном количестве приложений.

#### Пример реализации

**1. Создание корневого приложения (root-app):**
Этот манифест отслеживает директорию `root-apps` в репозитории, где будут лежать описания других приложений.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: 'https://github.com/your-org/your-repo.git'
    targetRevision: HEAD
    path: root-apps
  destination:
    server: 'https://kubernetes.default.svc'
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

**2. Определение дочерних приложений:**
В директории `root-apps` создаются манифесты для каждого сервиса (например, `child-app1.yaml`):

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: child-app1
  namespace: argocd
spec:
  project: default
  source:
    repoURL: 'https://github.com/your-org/your-repo.git'
    targetRevision: HEAD
    path: apps/child-app1
  destination:
    server: 'https://kubernetes.default.svc'
    namespace: default
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

**3. Мониторинг и синхронизация:**
После применения корневого приложения Argo CD автоматически начнет отслеживать изменения в директории `root-apps`. При добавлении туда новых манифестов дочерних приложений Argo CD создаст их автоматически. Статус здоровья всей системы можно отслеживать через `root-app`.

### Шаблон «ApplicationSet»

Основан на концепции App-of-Apps, но обеспечивает более гибкий и автоматизированный способ создания приложений. Он позволяет определять **шаблоны** и генерировать приложения динамически на основе различных параметров.

*   **Как это работает:**
    1.  **Ресурс ApplicationSet:** Определяет структуру шаблона и правила генерации.
    2.  **Генераторы (Generators):** Используются для поставки параметров (List, Cluster, Git, Matrix). Например, генератор `Git` может сканировать папки в репозитории, а `Cluster` — список подключенных кластеров.
    3.  **Подстановка параметров:** Параметры из генератора подставляются в шаблон `Application`.
    4.  **Синхронизация:** Argo CD автоматически создает, обновляет или удаляет приложения при изменении параметров в источнике (например, при добавлении нового кластера или папки в Git).
*   **Преимущества:**
    *   Масштабируемость: управление сотнями приложений в разных кластерах из одного манифеста.
    *   Динамичность: автоматическое создание временных сред (preview environments) для каждого Pull Request.
    *   Сокращение ручного труда и минимизация ошибок конфигурации.
*   **Когда использовать:**
    *   Развертывание во множество кластеров или сред (dev/staging/prod) с идентичной структурой.
    *   Автоматизация на основе структуры Git-репозитория (например, в больших монорепозиториях).
    *   Реализация самообслуживания (self-service) для команд, где приложения создаются динамически.

#### Пример реализации

**Определение ресурса ApplicationSet:**
В данном примере используется генератор списка (`list`) для динамического развертывания приложения в два разных кластера.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: multi-cluster-apps
  namespace: argocd
spec:
  generators:
  - list:
      elements:
      - cluster: cluster-a
        url: 'https://cluster-a.example.com'
      - cluster: cluster-b
        url: 'https://cluster-b.example.com'
  template:
    metadata:
      name: '{{cluster}}-app'
    spec:
      project: default
      source:
        repoURL: 'https://github.com/your-org/your-repo.git'
        targetRevision: HEAD
        path: apps/{{cluster}}
      destination:
        server: '{{url}}'
        namespace: default
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

**Мониторинг и синхронизация:**
Argo CD будет динамически генерировать и синхронизировать объекты `Application` для каждого кластера, определенного в генераторе. Это обеспечивает высокую степень автоматизации и согласованности при управлении парком кластеров.

### Сравнение подходов

| Критерий | App-of-Apps | ApplicationSet |
| :--- | :--- | :--- |
| **Сложность** | Низкая (простая иерархия). | Средняя (требует настройки генераторов). |
| **Автоматизация** | Ручное добавление дочерних манифестов. | Полностью динамическая генерация. |
| **Гибкость** | Ограничена статическим списком. | Максимальная (поддержка Matrix, Git-директорий). |
| **Масштабируемость** | Для небольших, известных наборов приложений. | Для крупных инфраструктур и динамических сред. |

**Совет:** Используйте App-of-Apps для простых сценариев и начальной загрузки кластера. Переходите на ApplicationSet, если вам нужно масштабироваться на множество кластеров или автоматизировать создание приложений на основе изменений в Git.

## Безопасность и мультитенантность

Для обеспечения надежной работы в продуктивных средах необходимо:
- **Принцип минимальных привилегий:** ArgoCD должен иметь доступ только к тем пространствам имен, которыми он управляет. Избегайте предоставления прав `cluster-admin` в production.
- **Использование AppProject:** для изоляции команд и проектов внутри одного экземпляра ArgoCD.
- **Аудит:** регулярный мониторинг журналов доступа и изменений конфигураций.

### Механизмы отката (Rollback)

В ArgoCD существует два подхода к откату изменений:

1.  **Git-откат (Рекомендуемый):** Выполнение `git revert` в репозитории. ArgoCD видит изменение в Git и синхронизирует кластер с предыдущим стабильным состоянием. Это сохраняет историю изменений в Git (SSoT).
2.  **UI-откат (Экстренный):** В веб-интерфейсе ArgoCD есть кнопка **Rollback**, позволяющая мгновенно откатиться к одной из предыдущих ревизий.
    - **Нюанс:** При UI-откате ArgoCD переходит в состояние `OutOfSync` относительно Git, так как версия в кластере больше не совпадает с версией в репозитории. Автоматическая синхронизация (`SelfHeal`) при этом временно отключается для этого приложения, чтобы не "перетереть" откат новым комитом из Git.

### Архитектурные компоненты

Система состоит из следующих микросервисов:

- **ArgoCD Repo Server (`argocd-repo-server`):** отвечает за работу с Git-репозиториями и рендеринг манифестов. Поддерживает **локальный кеш**, что оптимизирует производительность и снижает частоту операций выборки (git fetch).
- **ArgoCD Application Controller (`argocd-application-controller`):** сердце системы, установленное в кластере. Реализует стандартный **Kubernetes controller pattern** для непрерывного мониторинга и согласования состояний.
- **ArgoCD API Server (`argocd-server`):** API-сервер, обслуживающий UI и CLI через **RESTful API**, что упрощает автоматизацию и интеграцию с внешними системами.
- **ArgoCD Dex Server (`argocd-dex-server`):** обеспечивает интеграцию с внешними системами аутентификации.
- **Redis (`argocd-redis`):** используется для кеширования данных и оптимизации запросов к API Kubernetes.

### Манифест приложения (Application)

Основной ресурс ArgoCD, связывающий источник в Git с целевым окружением:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: guestbook
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
    - CreateNamespace=true
```

**Примечание по API:** Несмотря на то, что `v1alpha1` может выглядеть как предварительная версия, для Argo CD это стабильная и основная версия API, поддерживаемая в течение длительного времени для обеспечения обратной совместимости. Использование этой версии является стандартной практикой для ресурсов `Application` и `ApplicationSet`.

### Управление секретами

Для GitOps-подхода критически важно не хранить секреты в открытом виде:

- **[Sealed Secrets](../../Kubernetes/Security/sealed_secrets_overview.md):** асимметричное шифрование для хранения в Git.
- **[ArgoCD Vault Plugin (AVP)](./argocd_vault_integration.md):** динамическая подстановка данных из HashiCorp Vault.
- **[SOPS](../../Security/Tools/sops_overview.md):** шифрование YAML-файлов.

### Автоматическое обновление образов (Image Updater)

Компонент для автоматизации обновления тегов образов (v1.2.x). Позволяет отслеживать изменения в реестрах контейнеров и автоматически вносить изменения в конфигурацию приложения.

**Детальное руководство:** **[Argo CD Image Updater](./argocd_image_updater.md)**.

**Принцип работы:**
1. Мониторинг реестров образов (Docker Hub, Harbor, Quay) на наличие новых версий.
2. Обновление манифестов через Git write-back (создание файла `.argocd-source-...`) или динамическое переопределение через API.
3. В версии v1.x перешел на использование **Custom Resources (ImageUpdater CRD)** вместо аннотаций (в режиме расширенной конфигурации).

Подробнее: [GitOps: Образы контейнеров](../Concepts/containerization_and_image_storage.md).

## Дополнительная информация

### Основные изменения в ветке v3.x

- **Progressive Sync:** постепенное развёртывание ApplicationSets на группы кластеров.
- **Server-Side Apply:** использование нативного механизма Kubernetes для разрешения конфликтов.
- **PreDelete Hooks (v3.3):** выполнение Jobs перед удалением приложения.
- **OCI-нативность (v3.1):** улучшенная поддержка OCI-репозиториев для Helm и манифестов.

### Стратегии развертывания

ArgoCD интегрируется с инструментами для продвинутого деплоя:
- **Canary Deployment:** постепенное переключение трафика (через Argo Rollouts).
- **Blue/Green Deployment:** быстрое переключение между двумя идентичными окружениями.
