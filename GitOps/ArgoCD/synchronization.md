# ArgoCD — синхронизация и политики

## Определения

**Желаемое состояние (Desired State)** — эталонная конфигурация ресурсов (YAML, Helm, Kustomize), хранящаяся в Git.

**Фактическое состояние (Live State)** — текущее состояние объектов в кластере Kubernetes.

**Цикл сверки (Reconciliation Loop)** — непрерывный процесс сравнения состояний и устранения расхождений. Состоит из фаз **Refresh** (обнаружение) и **Sync** (применение).

**Дрейф конфигурации (Configuration Drift)** — расхождение между тем, что описано в Git, и тем, что реально запущено в кластере (например, после `kubectl edit`).

**Волны синхронизации (Sync Waves)** — механизм управления очередностью деплоя ресурсов на основе их готовности.

**Хуки (Hooks)** — запуск эфемерных задач (Jobs) на определенных этапах жизненного цикла синхронизации.

## Основные концепции

### Детальный цикл сверки

ArgoCD Application Controller работает по событийной модели (Webhook) или по расписанию (по умолчанию 3 минуты):

1.  **Фаза Refresh (Обнаружение):**
    - `argocd-repo-server` извлекает манифесты из Git.
    - Выполняется рендеринг (Helm, Kustomize или **[кастомные плагины](./argocd_custom_tooling.md)**).
    - Контроллер получает текущее состояние из API-сервера K8s.
2.  **Фаза Diff (Сравнение):**
    - Выполняется попарное сравнение объектов.
    - Учитываются настройки **[игнорирования различий](./synchronization/ignore_differences.md)**.
3.  **Фаза Sync (Применение):**
    - Если статус `OutOfSync` и включена автоматизация, контроллер инициирует деплой.
    - Ресурсы применяются согласно **Sync Waves**.

### Методы отслеживания ресурсов (Resource Tracking)

Для того чтобы ArgoCD знал, какими ресурсами он управляет, используется механизм отслеживания. В v3.x поддерживаются следующие методы (настраиваются в `argocd-cm`):

- **Labels (Стандарт):** Использование метки `app.kubernetes.io/instance`. Ограничение: длина значения метки ограничена 63 символами.
- **Annotations (Рекомендуемо):** Использование аннотации `argocd.argoproj.io/tracking-id`. Позволяет избежать проблем с длиной имен и конфликтов с Helm.
- **Tracking Method Settings:** Рекомендуется использовать `annotation+label` для максимальной совместимости.

### Фазы синхронизации

Процесс применения ресурсов разделен на этапы, что позволяет встраивать логику (Hooks) в процесс:

1.  **PreSync:** Выполнение до применения основных ресурсов (например, бэкап БД).
2.  **Sync:** Применение ресурсов из Git.
3.  **PostSync:** Выполнение после того, как все ресурсы стали `Healthy` (например, smoke-тесты).
4.  **SyncFail:** Выполнение только при сбое (уведомления).

### Современные методы синхронизации (v3.x)

- **Server-Side Apply (SSA):** Логика слияния переносится на сторону Kubernetes. Это стандарт в 2026 году, так как SSA лучше обрабатывает конфликты полей (особенно с HPA) и обходит лимит аннотации `last-applied-configuration`.
- **Progressive Sync:** Поэтапная раскатка `ApplicationSets` по группам кластеров. Позволяет остановить деплой на всю инфраструктуру, если первая группа (Canary) ушла в `Degraded`.
- **Reconciliation Pause:** Полная остановка сверки для кластера через аннотацию `argocd.argoproj.io/reconciliation-pause: "true"` в секрете кластера. Полезно при проведении глобальных технических работ.

## Параметры синхронизации (Sync Options)

В манифесте `Application` (секция `spec.syncPolicy.syncOptions`) настраивается поведение контроллера:

| Параметр | Описание |
| :--- | :--- |
| **CreateNamespace=true** | Автоматическое создание целевого Namespace, если он отсутствует. |
| **Prune=true** | Удаление ресурсов в кластере, которых больше нет в Git. |
| **SelfHeal=true** | Автоматический откат ручных правок в кластере к состоянию в Git. |
| **AllowEmpty=false** | Запрет синхронизации, если Git-репозиторий пуст (защита от случайного удаления всего кластера). |
| **ServerSideApply=true** | Использование Server-Side Apply вместо Client-Side Apply. |
| **RespectIgnoreDifferences=true** | Использование настроек `ignoreDifferences` не только для визуализации, но и при синхронизации. |
| **SkipDryRunOnMissingResource=true** | Пропуск проверки `dry-run` для ресурсов, чьи CRD еще не созданы (важно для первой установки). |
| **Replace=true** | Использование `kubectl replace` вместо `apply` (для ресурсов с неизменяемыми полями). |
