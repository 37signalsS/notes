# Argo CD — ручная синхронизация

> **Актуально для:** Argo CD v3.4.x

Ручная синхронизация — режим по умолчанию: контроллер Argo CD отслеживает состояние ресурсов и сигнализирует о расхождениях (статус `OutOfSync`), но не вносит изменения до явного подтверждения оператором. Перед применением доступны средства предварительной оценки: **Server-Side Diff** (стабилен с v3.1.0), Dry Run и `--preview-changes` — показ diff перед синхронизацией с ожиданием подтверждения оператора.

## Предварительные требования

Перед выполнением ручной синхронизации необходимо убедиться в следующем:

1. **Версия Argo CD:** базовый механизм ручной синхронизации работает во всех версиях; Server-Side Diff стабилен с v3.1.0; аннотация `skip-reconcile` — Alpha с v2.7.0. Рекомендуется v3.4.x.
2. **Проект (AppProject):** Приложение должно быть привязано к проекту с разрешенными целевыми кластерами и namespaces.
3. **Доступ:** У вас есть доступ к Argo CD UI или CLI (`argocd`).
4. **Источник кода:** Репозиторий доступен для Argo CD (настроены credentials или публичный доступ).
5. **Понимание рисков:** Синхронизация с `--prune` может удалить ресурсы; `Force=true` удаляет и пересоздает ресурс. Убедитесь, что вы понимаете последствия.
6. **Текущий статус:** Приложение находится в статусе `OutOfSync` (или `Synced` — для принудительного повторного применения).

## Определения

**Ручная синхронизация (Manual Sync)** — режим работы Argo CD Application, при котором автоматическое применение изменений из Git отключено. Контроллер отслеживает состояние ресурсов и сигнализирует о расхождениях (статус `OutOfSync`), но не вносит изменения до явного подтверждения оператором.

**Селективная синхронизация (Selective Sync / partial sync)** — возможность выбора конкретных ресурсов (`GROUP:KIND:NAME`) или групп ресурсов (по меткам) для деплоя, оставляя остальные компоненты приложения в текущем состоянии. Документированные ограничения: такая синхронизация **не** записывается в историю (откат невозможен), хуки **не** выполняются, ресурсы вне выборки не затрагиваются.

**Dry Run (Пробный запуск)** — режим имитации синхронизации (`--dry-run`): применение манифестов в кластер имитируется через API-сервер Kubernetes в режиме dry-run, фактические ресурсы не изменяются. Позволяет проверить валидность манифестов и получить результат от API-сервера без фактических изменений.

**Server-Side Diff** — механизм сравнения ресурсов на стороне Kubernetes API, учитывающий работу мутирующих вебхуков и Server-Side Apply менеджеров перед отображением разницы в Argo CD. Включается явно (флаг `--server-side-diff` у `argocd app diff` или аннотация `argocd.argoproj.io/compare-options: ServerSideDiff=true`); стратегия diff по умолчанию — Legacy (3-way diff).

**Принудительная синхронизация (Force Sync)** — выполнение синхронизации с флагом `--force` (sync option `Force=true`), при которой ресурс удаляется и пересоздается (`kubectl delete/create`). Используйте только когда `Replace=true` недостаточно (например, ресурс некорректно обновляется обычным apply).

**Ревизия (Revision)** — конкретный коммит в Git-репозитории, который был применен к кластеру. Argo CD сохраняет историю ревизий для каждого приложения (`argocd app history`), что позволяет выполнять откаты.

## Базовые концепции

### Особенности и преимущества ручного режима

Ручная синхронизация является режимом по умолчанию. Она рекомендуется для:
- **Production-сред:** где требуется дополнительное подтверждение (Peer Review) перед деплоем.
- **Сложных миграций:** когда порядок обновления ресурсов требует ручного контроля, выходящего за рамки Sync Waves.
- **Экспериментов:** проверка новых версий ПО без риска автоматического каскадного обновления.
- **Аудита:** необходимость документирования каждого шага деплоя с указанием оператора и времени.
- **Отладки:** диагностика проблем, когда автоматическая синхронизация не работает корректно.

### Механика выполнения Manual Sync

1. **Обнаружение:** Контроллер Argo CD сравнивает `Live State` (текущее состояние в кластере) и `Desired State` (описание в Git). Интервал сверки — 120 секунд + jitter до 60 секунд.
2. **Статус:** Если состояния различаются, приложение получает статус `OutOfSync`.
3. **Ожидание:** Контроллер ждет явного подтверждения оператором (кнопка "Sync" в UI или команда `argocd app sync` в CLI).
4. **Применение:** Оператор выбирает параметры синхронизации (ресурсы, флаги) и запускает процесс. По умолчанию ресурсы применяются через `kubectl apply` (client-side); при `ServerSideApply=true` — `kubectl apply --server-side --force-conflicts`.
5. **Валидация:** После применения проверяется здоровье ресурсов (Health Checks).
6. **Логирование:** Каждая синхронизация логируется с указанием оператора, времени и результатов.

### Матрица состояний: Sync Status vs Health Status

В Argo CD статус синхронизации (**Sync Status**) и статус работоспособности (**Health Status**) являются двумя строго **ортогональными (независимыми)** измерениями. Понимание их комбинаций — ключевой навык SRE при диагностике инцидентов и частый вопрос на технических собеседованиях.

| Sync Status | Health Status | Значение в Production | Пример из практики |
| :--- | :--- | :--- | :--- |
| **Synced** | **Healthy** | Идеальное целевое состояние системы. | Манифесты применены, все поды работают, Readiness probes успешны. |
| **Synced** | **Degraded** | **Сбой в раскатке / приложении.** Манифест доставлен в API, но рабочая нагрузка не функционирует. | Образ успешно обновлен в Deployment, но контейнеры падают в `CrashLoopBackOff` из-за ошибки в коде или нехватки памяти (OOMKilled). |
| **Synced** | **Progressing** | **Штатный процесс раскатки.** Манифест применен, контроллер K8s создает новые поды. | RollingUpdate запущен: старые поды еще гасятся, новые только стартуют и проходят readiness probe. |
| **OutOfSync** | **Healthy** | **Штатный дрейф / ожидание релиза.** В проде стабильно работает старая версия, в Git появился новый коммит (ручной режим синка). | Разработчик влил Pull Request в `main`. В кластере крутится версия v1.0, а в Git описана v1.1. Инцидента нет. |
| **OutOfSync** | **Missing** | **Ресурс еще не развернут.** Манифест описан в Git, но в кластере физически отсутствует. | Создан манифест нового `Service` или `ConfigMap`, синхронизация еще не производилась (или ресурс удален вручную из кластера). |
| **OutOfSync** | **Degraded** | **Комбинированный сбой.** Ресурсы в кластере сломаны, и их спецификация расходится с Git. | Попытка синхронизации завершилась ошибкой (например, `PreSync Hook` упал, либо предыдущая версия сервиса уже была неработоспособна). |
| **Synced** | **Suspended** | **Принудительно приостановленный ресурс.** | Ресурс `Argo Rollout` или `Workflow` находится на паузе по шагу канареечного деплоя. |

> [!IMPORTANT]
> **Собеседование / SRE-контекст:** Статус `OutOfSync` сам по себе **не является аварией**. Он означает лишь несовпадение между декларацией в Git и фактом в кластере. Напротив, статус `Synced` + `Degraded` — это прямой повод для PagerDuty алерта, так как с точки зрения GitOps изменения доставлены успешно, но сервис лежит.

### Взаимодействие с другими механизмами

- **Sync Windows:** Если настроены [Окна синхронизации](./sync_windows.md) типа `deny`, ручная синхронизация будет заблокирована в указанный период — окна влияют и на ручные, и на автоматические синхронизации (`deny` перекрывает `allow`). Для разрешения ручного синка в запрещающем окне используется опция окна `manualSync: true` (поле в `spec.syncWindows` AppProject, а не флаг синхронизации): `argocd proj windows enable-manual-sync PROJECT ID`. Текущее состояние окна видно в `argocd app get <name>` (поле `SyncWindow`).
- **Sync Waves и Hooks:** Ручная синхронизация учитывает [волны и хуки](./sync_waves_hooks.md) — ресурсы применяются в порядке, определенном аннотациями `argocd.argoproj.io/sync-wave`. Хуки выполняются при обычном (полном) синке; при селективной синхронизации и при `--strategy apply` хуки пропускаются.
- **Ignore Differences:** Если настроено [игнорирование различий](../ignore_differences.md), эти поля не отображаются в Diff. Чтобы синхронизация не перезаписывала их на этапе применения, включите `RespectIgnoreDifferences=true`.
- **ApplicationSet:** В ApplicationSet ручная синхронизация выполняется для каждого приложения отдельно. Контроллер ApplicationSet не управляет ручными синхронизациями.
- **Progressive Sync:** При использовании [Прогрессивной синхронизации](./progressive_sync.md) ручной синк приложения, которое еще не подошло по очереди, возможен, но нарушает логику `maxUpdate` текущего шага.
- **Audit Logs:** Каждая ручная синхронизация записывается в журнал аудита Argo CD. При интеграции с SSO логи содержат `email` или `username` оператора. Оператор может добавить произвольные пары `ключ=значение` к записи об операции через `--info key=value` (например, номер тикета).

## Практические сценарии

### Сценарий 1: Базовая настройка в манифесте

Для активации ручного режима достаточно не указывать секцию `automated` в `syncPolicy` (или явно задать `automated.enabled: false`).

```yaml
spec:
  syncPolicy:
    syncOptions:
    - CreateNamespace=true
    - PruneLast=true # Удалять старое только после успеха нового
    retry:
      limit: 2
```

**Пояснения:**
- Отсутствие `automated` означает, что синхронизация будет выполняться только вручную.
- `PruneLast=true` гарантирует, что удаление старых ресурсов произойдет только после успешного применения новых.
- `retry.limit: 2` позволяет повторить попытку при временных сетевых ошибках.

То же через CLI:

```bash
# Явно установить ручную политику (алиасы: manual, none)
argocd app set my-app --sync-policy manual

# Добавить sync option и настройки retry (сохраняются в спецификации)
argocd app set my-app --sync-option PruneLast=true --sync-retry-limit 2
```

### Сценарий 2: Селективная синхронизация через CLI

Позволяет точечно обновить компоненты системы (например, только `Job` или `ConfigMap`).

```bash
# Синхронизация конкретного ресурса (Format: Group:Kind:Name)
argocd app sync my-app --resource apps:Deployment:api-server

# Синхронизация всех ресурсов конкретного типа
argocd app sync my-app --resource :Service:

# Синхронизация по селектору меток (Labels) ресурсов приложения
argocd app sync my-app --label tier=backend

# Исключение ресурса из выборки
argocd app sync my-app --resource '!apps:Deployment:api-server'
```

**Важно (документированные ограничения селективной синхронизации):**
- Селективная синхронизация **не** записывается в историю приложения — откат через `argocd app rollback` для такой операции невозможен.
- Хуки (PreSync/PostSync и т.д.) **не** выполняются при селективной синхронизации.
- Ресурсы вне выборки не затрагиваются — в том числе не удаляются, даже если указан `--prune`.
- `-l/--selector` у `argocd app sync` выбирает **приложения** по меткам (синк сразу нескольких приложений), а `--label` — **ресурсы** внутри приложения.

### Сценарий 3: Глубокий анализ расхождений (Diff)

Перед синхронизацией всегда проверяйте, что именно будет изменено.

```bash
# Текстовый diff (локальный, стратегия Legacy — по умолчанию)
argocd app diff my-app

# Diff на стороне сервера (учитывает SSA-менеджеров и мутирующие вебхуки)
argocd app diff my-app --server-side-diff

# Diff против конкретной ревизии Git
argocd app diff my-app --revision <commit-sha>

# Diff против локальных манифестов
argocd app diff my-app --local path/to/manifests

# Принудительное обновление данных приложения перед diff
argocd app diff my-app --refresh        # обычный refresh
argocd app diff my-app --hard-refresh   # refresh + кеш целевых манифестов
```

**Выходные коды `argocd app diff`:** `0` — различий нет, `1` — различия найдены, `2` — общая ошибка. Kubernetes Secrets исключены из diff. Для кастомного инструмента diff задайте переменную окружения `KUBECTL_EXTERNAL_DIFF`.

**Замечания:**
- У `argocd app diff` **нет** флагов `--resource`/`--label`: фильтрация diff по конкретному ресурсу в CLI не поддерживается. Для просмотра статуса отдельного ресурса используйте `argocd app get <name> -o wide` (секция ресурсов) или `argocd app get <name> -o tree`.
- Стратегия diff по умолчанию — **Legacy** (3-way diff через аннотацию `last-applied-configuration`). Server-Side Diff включается явно — он нужен, когда на ресурсы влияют мутирующие вебхуки или они управляются через Server-Side Apply; для обычных client-side приложений Legacy достаточно.
- Server-Side Diff включается явно: флагом `argocd app diff <name> --server-side-diff` (v3.5+) или аннотацией приложения `argocd.argoproj.io/compare-options: ServerSideDiff=true`; в новых версиях — автоматически для ресурсов с sync option `ServerSideApply=true`. Глобального переключателя в `argocd-cmd-params-cm` нет.

### Сценарий 4: Пробный запуск (Dry Run)

`--dry-run` имитирует применение манифестов: запросы идут к API-серверу Kubernetes в режиме dry-run, фактические ресурсы не изменяются. Валидация манифестов при синхронизации включена по умолчанию (sync option `Validate=true`; отключается как `Validate=false`).

```bash
# Полная проверка через API-сервер
argocd app sync my-app --dry-run

# Server-side dry-run (серверная сторона apply, admission-вебхуки отрабатывают в dry-run режиме)
argocd app sync my-app --dry-run --server-side

# Предварительный diff перед синхронизацией с ожиданием подтверждения оператора
argocd app sync my-app --preview-changes

# Асинхронный запуск (CLI не ждет завершения) — для долгих синхронизаций
argocd app sync my-app --async

# Автоподтверждение промптов (CI/CD)
argocd app sync my-app --assumeYes

# Метаданные операции (сохраняются в приложении, полезно для аудита)
argocd app sync my-app --info ticket=INC-1234 --info owner=sre-team
```

**Сравнение Dry Run и Diff:**

| Критерий | Dry Run (`--dry-run`) | Diff (`argocd app diff`) |
| :--- | :--- | :--- |
| **Что делает** | Имитирует применение (kubectl apply --dry-run) | Показывает различия target vs live |
| **Валидация** | Полная (включая валидацию схем через API-сервер) | Сравнение полей |
| **Производительность** | Медленнее (запросы к API) | Быстрее (локальное сравнение) |
| **Точность** | Учитывает admission-вебхуки (в server-side режиме) | Legacy не учитывает вебхуки; Server-Side Diff учитывает |
| **Использование** | Перед критическими деплоями | Ежедневная проверка, аудит |

**Примечание:** Dry Run не проверяет Health Checks — он проверяет применимость манифестов, но не прогнозирует работоспособность ресурсов после применения.

### Сценарий 5: Управление откатами (Rollback)

В Argo CD существует два подхода к откату:

1.  **Argo-Rollback:** Быстрый возврат к предыдущей успешной ревизии из истории Argo CD.
    - *Плюс:* Скорость (не требует коммитов в Git).
    - *Минус:* Создает расхождение с Git (`OutOfSync`). **Не рекомендуется для Production.**
    - *Ограничение:* Откат невозможен для приложения с включенным automated sync — `argocd app rollback` отвергается.
2.  **Git-Revert (Рекомендуемый):** Выполнение `git revert` в репозитории.
    - *Плюс:* Соответствие принципам GitOps, сохранение истории изменений.
    - *Минус:* Требует времени на коммит и синхронизацию.

**Пример Argo-Rollback через CLI:**
```bash
# Посмотреть историю ревизий
argocd app history my-app

# Откатиться к ID ревизии 5 (без ID — к предыдущей версии)
argocd app rollback my-app 5

# Откат с удалением ресурсов, которых нет в целевой ревизии
argocd app rollback my-app 5 --prune

# Проверить статус после отката
argocd app get my-app

# Дождаться завершения операции и здоровья ресурсов
argocd app wait my-app --operation --health
```

**Пример Git-Revert:**
```bash
# 1. Найти коммит, который нужно отменить
git log --oneline

# 2. Выполнить revert
git revert <commit-hash>

# 3. Запушить изменения
git push origin main

# 4. Дождаться автоматической синхронизации (или запустить вручную)
argocd app sync my-app
```

**Важно:** После `argocd app rollback` приложение перейдет в статус `OutOfSync`, так как Git-состояние не изменилось. Это нормальное поведение.

### Сценарий 6: Полная приостановка обработки приложения (Skip Reconcile)

Если во время ручных работ в кластере нужно гарантировать, что Argo CD не будет обрабатывать приложение вообще (ни сверку, ни ручной синк), используется аннотация `skip-reconcile`:

```bash
# Пауза обработки (Alpha-фича, с v2.7.0)
kubectl annotate application my-app -n argocd argocd.argoproj.io/skip-reconcile="true"

# Снятие паузы
kubectl annotate application my-app -n argocd argocd.argoproj.io/skip-reconcile-
# или
kubectl annotate application my-app -n argocd argocd.argoproj.io/skip-reconcile="false" --overwrite
```

**Поведение (документация Argo CD):** при `skip-reconcile: "true"` вся обработка приложения останавливается — поле `status` не обновляется, дрейф не детектируется, ручные синхронизации не выполняются. Аннотация — Alpha-фича (с v2.7.0), предназначена для интеграции со сторонними проектами; может быть изменена или удалена в будущих релизах. С v3.4 аннотация также поддерживается на Cluster Secret — приостанавливает обработку всех приложений, нацеленных на кластер.

**Более легкие альтернативы:**
- **Sync Windows** (`deny`-окно) — блокирует синхронизации, но дрейф продолжает детектироваться (приложение остается `OutOfSync`).
- Для разового отключения автосинка на время работ — `argocd app set my-app --sync-policy manual` (или `automated.enabled: false` в манифесте).

**Применение skip-reconcile:**
- Ручные миграции базы данных, когда любой синк нежелателен.
- Временное отключение обработки приложения контроллером (например, при обновлении CRD).
- Проведение работ в кластере, которые могут затронуть ресурсы приложения.

#### Аварийный регламент (Break-Glass Protocol) при инцидентах в Production

Если сервис в кластере упал, внешний Git-сервер (GitLab/Gitea) недоступен, либо требуется восстановить работоспособность за секунды в обход GitOps-пайплайна:

1. **Шаг 1: Заморозка сверки приложения в Argo CD**
   Исключает попытки Argo CD отслеживать и откатывать экстренные ручные правки:
   ```bash
   kubectl annotate application my-app -n argocd argocd.argoproj.io/skip-reconcile="true" --overwrite
   # → application.argoproj.io/my-app annotated
   ```

2. **Шаг 2: Отмена зависшей операции синхронизации (если sync завис в Progressing)**
   ```bash
   argocd app terminate-op my-app
   # → Operation terminated
   ```

3. **Шаг 3: Экстренный откат нагрузки на уровне Kubernetes**
   Выполняется откат деплоймента средствами самого кластера без ожидания коммита:
   ```bash
   kubectl rollout undo deployment/my-app-backend -n production
   # → deployment.apps/my-app-backend rolled back
   kubectl rollout status deployment/my-app-backend -n production
   # → deployment "my-app-backend" successfully rolled out
   ```

4. **Шаг 4: Фиксация исправления в Git-репозитории**
   После стабилизации сервиса дежурный инженер обязан зафиксировать рабочее состояние в Git (через `git revert` сбойного коммита либо коммит хотфикса) и запушить в ветку.

5. **Шаг 5: Снятие заморозки и возврат под управление GitOps**
   ```bash
   # Снятие аннотации
   kubectl annotate application my-app -n argocd argocd.argoproj.io/skip-reconcile-
   # → application.argoproj.io/my-app annotated (removed)

   # Контрольный ручной синк для подтверждения согласованности
   argocd app sync my-app
   argocd app wait my-app --health
   ```

### Сценарий 7: Ручная синхронизация в мультикластерной среде

Каждое приложение синхронизируется в направление, зафиксированное в его спецификации (`spec.destination`). Ручной синк применяется к конкретному приложению и, соответственно, к его кластеру назначения.

```bash
# Просмотр приложений во всех кластерах
argocd app list

# Просмотр приложений конкретного кластера (по имени или URL)
argocd app list --cluster prod-cluster.example.com

# Синхронизация конкретного приложения (в его кластер назначения)
argocd app sync my-app

# Синхронизация всех приложений конкретного кластера
argocd app list --cluster prod-cluster.example.com -o name | xargs -I {} argocd app sync {}
```

**Смена кластера назначения** — это изменение спецификации приложения, а не флаг синхронизации:

```bash
# По URL кластера
argocd app set my-app --dest-server https://prod-cluster.example.com
# или по имени кластера в Argo CD
argocd app set my-app --dest-name prod-cluster
```

**Важно:** В ApplicationSet ручная синхронизация выполняется для каждого приложения отдельно. Контроллер ApplicationSet не управляет ручными синхронизациями.

### Сценарий 8: Синхронизация с хуками (Pre/Post Sync)

Хуки (PreSync, Sync, PostSync, SyncFail) выполняются автоматически при обычной (полной) синхронизации — дополнительных флагов не требуется. Если PreSync Hook завершается неуспешно, синхронизация прерывается и помечается как failed.

```bash
# Обычный синк: PreSync -> применение ресурсов -> PostSync
argocd app sync my-app

# --strategy apply: хук-аннотированные ресурсы пропускаются целиком
# (не применяются и не выполняются), остальные ресурсы — обычный kubectl apply
argocd app sync my-app --strategy apply

# --strategy hook — стратегия по умолчанию: ресурсы синхронизируются
# с учетом хук-аннотаций (эквивалент обычного синка)
argocd app sync my-app --strategy hook

# Диагностика хуков: логи подов приложения (в т.ч. hook-Jobs)
argocd app logs my-app -f
argocd app logs my-app --kind Job --name db-migrate -f
```

**Важно:**
- Отдельного флага "выполнить только хуки" или "пропустить хуки" у `argocd app sync` **нет**. Единственный способ не запускать хуки при полном синке — `--strategy apply` (хук-аннотированные ресурсы пропускаются целиком); при селективной синхронизации хуки тоже не выполняются.
- Для долгих хуков (миграции БД) увеличьте таймаут ожидания: `argocd app sync my-app --timeout 1800`.
- Если операция "зависла" на хуке — принудительная остановка: `argocd app terminate-op my-app`.

### Сценарий 9: Принудительное обновление неизменяемых полей

Если в Git изменилось поле, которое Kubernetes запрещает обновлять (например, `spec.selector` в `Service` или `spec.clusterIP`), синхронизация завершится ошибкой.

**Решение через CLI:**

```bash
argocd app sync my-app --force
```

**Решение в коде (использовать с осторожностью):**

```yaml
spec:
  syncPolicy:
    syncOptions:
    - Force=true # Приведет к удалению и пересозданию ресурса
```

> **Внимание:** `Force=true` удаляет и пересоздает ресурс (`kubectl delete/create`). Это может привести к даунтайму для Stateless-приложений и потере данных для StatefulSet. Используйте только когда `Replace=true` недостаточно.

**Альтернатива — `Replace=true`:**

```yaml
spec:
  syncPolicy:
    syncOptions:
    - Replace=true # Использует kubectl create/replace вместо apply
```

`Replace=true` выполняет `kubectl create/replace` вместо `apply` — подходит для ресурсов, которые не поддерживают apply (отклоняют PATCH). Имейте в виду: `replace` — это обновление (PUT), оно **не** обходит неизменяемые поля: для `spec.selector`/`spec.clusterIP` потребуется именно `Force=true` (удаление и пересоздание). `Replace=true` имеет приоритет над `ServerSideApply=true`.

### Сценарий 10: Интеграция с cert-manager

cert-manager автоматически добавляет и обновляет аннотации и TLS-секреты. Используйте `managedFieldsManagers` для игнорирования изменений от cert-manager.

```yaml
spec:
  ignoreDifferences:
  - group: cert-manager.io
    kind: Certificate
    managedFieldsManagers:
    - cert-manager-certificates-issuer
  - group: ""
    kind: Secret
    jqPathExpressions:
    - .metadata.annotations["cert-manager.io/certificate-name"]
    - .metadata.annotations["cert-manager.io/issuer-name"]
```

| Флаг | Описание | Когда использовать |
| :--- | :--- | :--- |
| `--server-side-diff` | Server-Side Diff (учитывает вебхуки и SSA-менеджеров) | Когда Legacy diff недостаточен |
| `--server-side-generate` | С `--local`: отправить локальные манифесты на сервер для diff | Diff локальных манифестов с учетом серверной стороны |
| `--refresh` | Обновить данные приложения перед diff | Актуальный diff без отдельного refresh |
| `--hard-refresh` | Refresh + обновление кеша целевых манифестов | После изменения source (path, параметры chart) |
| `--revision` | Diff против конкретной ревизии Git | Сравнение с конкретным commit |
| `--local` | Diff против локальных манифестов | Быстрая проверка до коммита |
| `--local-include` | Шаблоны файлов для `--server-side-generate` (default `*.yaml,*.yml,*.json`) | Фильтрация локальных файлов |

### Флаги команды `argocd app rollback` (v3.4.x)

| Флаг | Описание | Когда использовать |
| :--- | :--- | :--- |
| `--prune` | Удаление ресурсов, которых нет в целевой ревизии | При откате на старую версию с чисткой |
| `--timeout` | Таймаут ожидания (секунды) | Для долгих откатов |
| `-N, --app-namespace` | Приложение в конкретном namespace | Multi-namespace Argo CD |
| `-o, --output` | Формат вывода: wide/id | Скриптовая обработка (id) |

Без ID ревизии откат выполняется к предыдущей версии. Откат отвергается для приложений с включенным automated sync.

### Настройка логики Retry

```bash
# Базовый retry (3 попытки) при синхронизации
argocd app sync my-app --retry-limit 3

# Экспоненциальный backoff (5 попыток) — factor: integer
argocd app sync my-app --retry-limit 5 --retry-backoff-duration 5s --retry-backoff-factor 2 --retry-backoff-max-duration 3m

# То же через app set (сохраняется в спецификации приложения)
argocd app set my-app --sync-retry-limit 5 --sync-retry-backoff-duration 5s --sync-retry-backoff-factor 2 --sync-retry-backoff-max-duration 3m

# При retry брать последнюю ревизию из Git, а не ту, что была в начале операции
argocd app sync my-app --retry-refresh
```

**Значения по умолчанию (из исходного кода):** `duration: 5s`, `factor: 2` (integer), `maxDuration: 3m`, `limit: 0` (0 = без повторов; `-1` = без ограничений). Формула интервала: `duration × factor^retryCount`, ограничена сверху `maxDuration`.

## Диагностика и устранение неисправностей

### Типичные проблемы

| Проблема | Симптомы | Вероятная причина | Решение |
| :--- | :--- | :--- | :--- |
| **Sync заблокирован** | Ошибка при попытке синхронизации | Активно `deny`-окно Sync Windows | Проверьте окно в `argocd app get <name>` (поле `SyncWindow`); разрешите ручной синк: `argocd proj windows enable-manual-sync PROJECT ID` или `manualSync: true` в AppProject |
| **Diff не отображает изменений** | Нет различий в Diff, но ресурс изменен | Поле игнорируется в `ignoreDifferences` | Проверьте `ignoreDifferences` в манифесте; используйте `--hard-refresh` |
| **Dry Run завершается ошибкой** | Ошибка валидации манифестов | Некорректный YAML или отсутствует CRD | Исправьте манифест или добавьте `SkipDryRunOnMissingResource=true` |
| **Rollback не работает** | Нет истории ревизий / отвергается | Приложение не синхронизировалось успешно или включен automated sync | Выполните успешный ручной синк; для automated-синка используйте Git-Revert |
| **Синхронизация медленная** | Синхронизация занимает >5 минут | Много ресурсов, нет `ApplyOutOfSyncOnly` | Используйте `--apply-out-of-sync-only` или разбейте приложение |
| **Ошибка "shared resource"** | Синхронизация падает | Ресурс используется другим приложением | `FailOnSharedResource=false` (sync option) или разделите ресурсы между приложениями; `--force` не помогает — он удалит и пересоздает общий ресурс |
| **Ошибка "resource not found"** | Синхронизация падает | Ресурс удален из кластера вручную или устарел кеш | Синк воссоздает ресурс из Git; обновите данные: `argocd app get <name> --refresh` (или `--hard-refresh`) и повторите синк. `--prune` здесь не поможет — он для ресурсов, удаленных из Git |
| **Прерывание PreSync Hook** | Синхронизация прерывается | PreSync Hook завершился неуспешно | Логи хука: `argocd app logs <name> --kind Job -f`; исправьте ошибку и повторите синк |
| **Операция зависла** | Sync длится бесконечно | Долгий хук или таймаут ресурса | `argocd app terminate-op <name>`, затем повторный синк |

### Диагностические команды

```bash
# Просмотр статуса приложения (в т.ч. SyncWindow и Sync Policy)
argocd app get <app-name>

# Принудительное обновление данных (без синхронизации)
argocd app get <app-name> --refresh
argocd app get <app-name> --hard-refresh

# Текущая операция
argocd app get <app-name> --show-operation

# Дерево ресурсов
argocd app get <app-name> -o tree

# Просмотр логов контроллера
kubectl logs -n argocd -l app.kubernetes.io/name=argocd-application-controller -f

# Просмотр событий синхронизации
kubectl get events -n argocd --field-selector reason=Synced

# Просмотр деталей последней синхронизации
argocd app history <app-name>

# Просмотр diff перед синхронизацией
argocd app diff <app-name>
argocd app diff <app-name> --server-side-diff

# Логи подов приложения (включая hook-Jobs)
argocd app logs <app-name> -f

# Ожидание завершения операции / здоровья
argocd app wait <app-name> --operation --health

# Принудительная остановка зависшей операции
argocd app terminate-op <app-name>

# Просмотр managedFields ресурса
kubectl get <resource> <name> -o jsonpath='{.metadata.managedFields}' | jq

# Просмотр событий для конкретного ресурса
kubectl describe <resource> <name> | grep -A 10 Events
```

### Пошаговая диагностика

1. **Проверьте статус:** `argocd app get <name>` — убедитесь, что статус `OutOfSync` или `Synced`, и поле `SyncWindow` (не заблокировано ли окном).
2. **Просмотрите diff:** `argocd app diff <name>` — проверьте, какие именно поля различаются.
3. **Проверьте Sync Windows:** Если есть ограничения по времени, дождитесь окончания блокировки или разрешите ручной синк в окне (`argocd proj windows enable-manual-sync PROJECT ID`).
4. **Просмотрите логи:** `kubectl logs -n argocd -l app.kubernetes.io/name=argocd-application-controller` — найдите ошибки.
5. **Проверьте Credentials:** Убедитесь, что Argo CD имеет доступ к Git-репозиторию и кластеру.
6. **Проверьте CRD:** Если используются кастомные ресурсы, убедитесь, что CRD установлены.
7. **Проверьте Health Checks:** Убедитесь, что ресурсы проходят проверку здоровья.

## Валидация и проверка работоспособности

### Проверка ручной синхронизации

```bash
# 1. Проверьте статус приложения
argocd app get <name>

# 2. Просмотрите diff
argocd app diff <name>

# 3. Выполните Dry Run
argocd app sync <name> --dry-run

# 4. Выполните синхронизацию
argocd app sync <name>

# 5. Дождитесь завершения и проверьте здоровье
argocd app wait <name> --operation --health
argocd app get <name>
```

### Проверка селективной синхронизации

```bash
# 1. Просмотрите список ресурсов
argocd app get <name> --refresh

# 2. Выберите конкретный ресурс для синхронизации
argocd app sync <name> --resource apps:Deployment:api-server

# 3. Проверьте статус (помните: операция не попадет в историю)
argocd app get <name>
```

### Проверка отката

```bash
# 1. Просмотрите историю ревизий
argocd app history <name>

# 2. Выполните откат к конкретной ревизии
argocd app rollback <name> 5

# 3. Проверьте статус после отката
argocd app get <name>

# 4. Просмотрите diff (должен показать расхождение с Git)
argocd app diff <name>
```

### Проверка Dry Run

```bash
# 1. Выполните Dry Run (валидация включена по умолчанию)
argocd app sync <name> --dry-run

# 2. Dry Run с отключенной валидацией (для некорректных CRD) — через sync option
argocd app set <name> --sync-option Validate=false
argocd app sync <name> --dry-run
argocd app set <name> --sync-option '!Validate=false'   # вернуть валидацию

# 3. Server-side dry-run (учет admission-вебхуков)
argocd app sync <name> --dry-run --server-side

# 4. Подробный вывод
argocd app sync <name> --dry-run --loglevel debug
```

## Лучшие практики

### Приоритет настроек

1. **Для Production:** Перед критическими деплоями — `--preview-changes` (diff с подтверждением) или связка `argocd app diff` + `--dry-run`. Используйте `--prune-last` для удаления старых ресурсов только после успеха нового деплоя.
2. **Для Staging:** Можно использовать `--dry-run` для ускорения итераций.
3. **Для Development:** Можно использовать `--force` для быстрого исправления ошибок (с пониманием удаления/пересоздания ресурса).

### Безопасность

- **Проверяйте перед применением:** `--preview-changes` или `argocd app diff` + `--dry-run` перед критическими деплоями.
- **Используйте `--prune-last`:** Удаление старых ресурсов должно происходить только после успешного применения новых.
- **Настройте Sync Windows:** Блокируйте синхронизацию в критические периоды.
- **Ревью через PR:** Любые изменения в манифестах должны проходить code review.
- **Аудит:** Проверяйте журналы аудита; передавайте контекст операции через `--info key=value` (тикет, владелец).

### Масштабирование

- **`--apply-out-of-sync-only`:** Используйте для приложений с большим числом ресурсов — снижает нагрузку на API-сервер.
- **`--server-side` (SSA):** Опционально — переносит слияние на сторону Kubernetes; default в Argo CD v3.x — client-side apply. Включайте для приложений с крупными манифестами (лимит аннотации `last-applied-configuration` ~256 КБ) или при конфликтах менеджеров.
- **`--async`:** Используйте для долгих синхронизаций, чтобы не блокировать CLI (проверяйте статус через `argocd app wait`).
- **Разбиение приложений:** Если приложение содержит >1000 ресурсов, рассмотрите разбиение на несколько ApplicationSets.

### Интеграция с CI/CD

- **Git-Triggered Sync:** Автоматическая синхронизация запускается после коммита в Git (для приложений с `automated` policy — см. [auto_sync.md](./auto_sync.md)).
- **PR-Triggered Sync:** Для dev/staging можно настроить синхронизацию при мерже PR.
- **Manual Sync для Prod:** Рассмотрите возможность использования ручной синхронизации для Production с аудитом.
- **Webhook Integration:** Настройте вебхуки для уведомления о ручных синхронизациях.
- **CI без прямого доступа к API:** синк из пайплайна — `argocd app sync <name> --assumeYes --info pipeline=$CI_PIPELINE_ID`.

## Ограничения и edge cases

### Ограничения

1. **Manual Sync блокируется Sync Windows:** Если настроены `deny` окна, ручная синхронизация будет заблокирована (если окно не разрешает ручной синк через `manualSync: true`).
2. **Selective Sync:** не записывается в историю (откат невозможен), хуки не выполняются, ресурсы вне выборки не затрагиваются (включая prune).
3. **Rollback не изменяет Git:** После `argocd app rollback` приложение перейдет в статус `OutOfSync`, так как Git-состояние не изменилось. Откат невозможен при включенном automated sync.
4. **Dry Run не проверяет Health Checks:** Dry Run только проверяет применимость манифестов, но не проверяет, будут ли ресурсы здоровы после применения.
5. **Skip-reconcile — Alpha:** Аннотация `argocd.argoproj.io/skip-reconcile` — экспериментальная фича (с v2.7.0), может измениться или исчезнуть.

### Edge Cases

1. **Конфликт с HPA:** Если в Git указано `replicas: 3`, ручной синк восстановит это значение и будет конфликтовать с HPA (при `selfHeal` — автоматически). Используйте `ignoreDifferences` для `replicas`.
2. **Множественные ApplicationSets на один ресурс:** Если ресурс управляется несколькими ApplicationSets, возникает конфликт (shared resource). Используйте `FailOnSharedResource=false` или разделите ресурсы.
3. **Удаление Application во время синхронизации:** Если Application удален во время выполняющейся синхронизации, операция завершится, но ресурсы в кластере могут остаться в промежуточном состоянии.
4. **Helm Chart с mutable-полями:** Некоторые Helm-чарты используют поля, которые невозможно обновить через `apply`. Используйте `--replace` (create/replace); для неизменяемых полей Kubernetes — `--force`.
5. **Cross-namespace ресурсы:** Приложение может управлять ресурсами в нескольких namespaces (включая cluster-scoped), если это разрешено AppProject и RBAC. Отдельные ApplicationSets нужны для логической группировки, а не из-за технического ограничения.
6. **PreSync Hook с долгой миграцией:** Если PreSync Hook (миграция базы данных) выполняется дольше таймаута синхронизации, операция прервется. Настройте `--timeout` (CLI) — учтите, что это таймаут ожидания CLI, а не отмена операции в кластере; зависшую операцию остановите через `argocd app terminate-op`.

## Дополнительная информация

- **Зависшие операции:** Если процесс синхронизации "завис" (например, из-за PreSync Hook), новые изменения не будут применяться до завершения или принудительной остановки текущей операции: `argocd app terminate-op <name>`.
- **Лимит ресурсов:** Argo CD имеет внутренние лимиты на количество управляемых ресурсов. Для очень больших приложений (>1000 ресурсов) рекомендуется разбивать на несколько ApplicationSets.
- **Временные интервалы:** Интервал сверки (Reconciliation Interval) по умолчанию составляет 120 секунд + jitter до 60 секунд (`timeout.reconciliation` в `argocd-cm`). Ручная синхронизация не зависит от этого интервала — она запускается оператором. Self-heal timeout (при `selfHeal: true`) — 5 секунд.
