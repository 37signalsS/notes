# Argo CD — ручная синхронизация

> **Актуальность (2026):** В версии Argo CD v3.x ручная синхронизация остается основным инструментом для критических обновлений и отладки. Новые функции, такие как **Server-Side Diff** и расширенный контроль **Selective Sync**, позволяют более точно оценивать влияние изменений перед их применением в кластере.

## Предварительные требования

Перед выполнением ручной синхронизации необходимо убедиться в следующем:

1. **Версия Argo CD:** v2.6+ (рекомендуется v3.x для полной поддержки SSA и расширенного Diff).
2. **Проект (AppProject):** Приложение должно быть привязано к проекту с разрешенными целевыми кластерами и namespaces.
3. **Доступ:** У вас есть доступ к Argo CD UI или CLI (`argocd`).
4. **Источник кода:** Репозиторий доступен для Argo CD (настроены credentials или публичный доступ).
5. **Понимание рисков:** Ручная синхронизация с `--prune` может удалить ресурсы. Убедитесь, что вы понимаете последствия.
6. **Текущий статус:** Приложение находится в статусе `OutOfSync` или `Synced` (для принудительного обновления).

## Определения

**Ручная синхронизация (Manual Sync)** — режим работы Argo CD Application, при котором автоматическое применение изменений из Git отключено. Контроллер отслеживает состояние ресурсов и сигнализирует о расхождениях (статус `OutOfSync`), но не вносит изменения до явного подтверждения оператором.

**Селективная синхронизация (Selective Sync)** — возможность выбора конкретных ресурсов (GVK — Group, Version, Kind) или групп ресурсов (по меткам) для деплоя, оставляя остальные компоненты приложения в текущем состоянии.

**Dry Run (Пробный запуск)** — режим имитации синхронизации. Позволяет проверить валидность манифестов и получить результат от API-сервера Kubernetes без фактического изменения ресурсов.

**Server-Side Diff** — механизм сравнения ресурсов на стороне Kubernetes API, учитывающий работу мутирующих вебхуков и Server-Side Apply менеджеров перед отображением разницы в Argo CD.

**Принудительная синхронизация (Force Sync)** — выполнение синхронизации с флагом `--force`, который использует `kubectl apply --force`. Приводит к удалению и пересозданию ресурса. Используйте только когда `Replace=true` недостаточно.

**Ревизия (Revision)** — конкретный коммит в Git-репозитории, который был применен к кластеру. Argo CD сохраняет историю ревизий для каждого приложения, что позволяет выполнять откаты.

## Базовые концепции

### Особенности и преимущества ручного режима

Ручная синхронизация является режимом по умолчанию. Она рекомендуется для:
- **Production-сред:** где требуется дополнительное подтверждение (Peer Review) перед деплоем.
- **Сложных миграций:** когда порядок обновления ресурсов требует ручного контроля, выходящего за рамки Sync Waves.
- **Экспериментов:** проверка новых версий ПО без риска автоматического каскадного обновления.
- **Аудита:** необходимость документирования каждого шага деплоя с указанием оператора и времени.
- **Отладки:** диагностика проблем, когда автоматическая синхронизация не работает корректно.

### Механика выполнения Manual Sync

1. **Обнаружение:** Контроллер Argo CD сравнивает `Live State` (текущее состояние в кластере) и `Desired State` (описание в Git).
2. **Статус:** Если состояния различаются, приложение получает статус `OutOfSync`.
3. **Ожидание:** Контроллер ждет явного подтверждения оператором (кнопка "Sync" в UI или команда `argocd app sync` в CLI).
4. **Применение:** Оператор выбирает параметры синхронизации (ресурсы, флаги) и запускает процесс.
5. **Валидация:** После применения проверяется здоровье ресурсов (Health Checks).
6. **Логирование:** Каждая синхронизация логируется с указанием оператора, времени и результатов.

### Взаимодействие с другими механизмами

- **Sync Windows:** Если настроены [Окна синхронизации](./sync_windows.md) типа `deny`, ручная синхронизация будет заблокирована в указанный период. Флаг `manualSync: true` позволяет обходить это ограничение в экстренных случаях.
- **Sync Waves и Hooks:** Ручная синхронизация учитывает [волны и хуки](./sync_waves_hooks.md) — ресурсы применяются в порядке, определенном аннотациями `argocd.argoproj.io/sync-wave`.
- **Ignore Differences:** Если настроено [игнорирование различий](../ignore_differences.md), эти поля не будут отображаться в Diff и не будут изменяться при синхронизации.
- **ApplicationSet:** В ApplicationSet ручная синхронизация выполняется для каждого приложения отдельно. Контроллер ApplicationSet не управляет ручными синхронизациями.
- **Progressive Sync:** При использовании [Прогрессивной синхронизации](./progressive_sync.md) ручная синхронизация применяется к конкретному кластеру, а не ко всем группам.
- **Audit Logs:** Каждая ручная синхронизация записывается в журнал аудита Argo CD. При интеграции с SSO логи содержат `email` или `username` оператора.

## Практические сценарии

### Сценарий 1: Базовая настройка в манифесте

Для активации ручного режима достаточно не указывать секцию `automated` в `syncPolicy`.

```yaml
spec:
  syncPolicy:
    syncOptions:
    - CreateNamespace=true
    - PruneLast=true # Удалять старое только после успеха нового
    retry:
      limit: 2
```

**Пояснения:**
- Отсутствие `automated` означает, что синхронизация будет выполняться только вручную.
- `PruneLast=true` гарантирует, что удаление старых ресурсов произойдет только после успешного применения новых.
- `retry.limit: 2` позволяет повторить попытку при временных сетевых ошибках.

### Сценарий 2: Селективная синхронизация через CLI

Позволяет точечно обновить компоненты системы (например, только `Job` или `ConfigMap`).

```bash
# Синхронизация конкретного ресурса (Format: Group:Kind:Name)
argocd app sync my-app --resource apps:Deployment:api-server

# Синхронизация всех ресурсов конкретного типа
argocd app sync my-app --resource :Service:

# Синхронизация по селектору меток (Labels)
argocd app sync my-app --label tier=backend
```

**Важно:** Селективная синхронизация не удаляет ресурсы (даже с `--prune`). Она только обновляет указанные ресурсы.

### Сценарий 3: Глубокий анализ расхождений (Diff)

Перед синхронизацией всегда проверяйте, что именно будет изменено.

```bash
# Текстовый diff (локальный)
argocd app diff my-app

# Diff на стороне сервера (учитывает SSA и вебхуки)
argocd app diff my-app --server-side

# Diff с фильтрацией по конкретному ресурсу
argocd app diff my-app --resource apps:Deployment:api-server

# Diff с игнорированием определенных полей (если настроено ignoreDifferences)
argocd app diff my-app --ignore-resource-differences apps:Deployment:api-server
```

**Рекомендация:** Всегда используйте `--server-side` для Diff в v3.x — это учитывает работу мутирующих вебхуков и SSA менеджеров.

### Сценарий 4: Пробный запуск (Dry Run)

Существует два уровня проверки:

1.  **Client-side:** Проверка синтаксиса на стороне Argo CD.
2.  **Server-side:** Отправка манифеста в K8s API с флагом dry-run (рекомендуется).

```bash
# Полная проверка через API-сервер
argocd app sync my-app --dry-run --server-side

# Проверка только конкретного ресурса
argocd app sync my-app --dry-run --resource apps:Deployment:api-server

# Проверка с валидацией (по умолчанию включена)
argocd app sync my-app --dry-run --validate
```

**Сравнение Dry Run и Diff:**

| Критерий | Dry Run | Diff |
| :--- | :--- | :--- |
| **Валидация** | Полная (включая валидацию схем) | Только сравнение |
| **Производительность** | Медленнее (запрос к API) | Быстрее (локальное сравнение) |
| **Точность** | Выше (учитывает вебхуки) | Ниже (учитывает только текущее состояние) |
| **Использование** | Перед критическими деплами | Ежедневная проверка |

### Сценарий 5: Управление откатами (Rollback)

В Argo CD существует два подхода к откату:

1.  **Argo-Rollback:** Быстрый возврат к предыдущей успешной ревизии из истории Argo CD.
    - *Плюс:* Скорость (не требует коммитов в Git).
    - *Минус:* Создает расхождение с Git (`OutOfSync`). **Не рекомендуется для Production.**
2.  **Git-Revert (Рекомендуемый):** Выполнение `git revert` в репозитории.
    - *Плюс:* Соответствие принципам GitOps, сохранение истории изменений.
    - *Минус:* Требует времени на коммит и синхронизацию.

**Пример Argo-Rollback через CLI:**
```bash
# Посмотреть историю ревизий
argocd app history my-app

# Откатиться к ID ревизии 5
argocd app rollback my-app 5

# Проверить статус после отката
argocd app get my-app
```

**Пример Git-Revert:**
```bash
# 1. Найти коммит, который нужно отменить
git log --oneline

# 2. Выполнить revert
git revert <commit-hash>

# 3. Запушить изменения
git push origin main

# 4. Дождаться автоматической синхронизации (или запустить вручную)
argocd app sync my-app
```

**Важно:** После `argocd app rollback` приложение перейдет в статус `OutOfSync`, так как Git-состояние не изменилось. Это нормальное поведение.

### Сценарий 6: Заморозка синхронизации (Reconciliation Pause)

Если во время ручных работ в кластере нужно гарантировать, что Argo CD не будет пытаться ничего менять (даже при нажатии Sync).

```bash
# Пауза через аннотацию
kubectl annotate app my-app -n argocd argocd.argoproj.io/reconciliation-pause="true"

# Снятие паузы
kubectl annotate app my-app -n argocd argocd.argoproj.io/reconciliation-pause-
```

**Применение:**
- При ручных миграциях базы данных.
- При временном отключении контроллеров (например, при обновлении CRD).
- При проведении работ в кластере, которые могут повлиять на ресурсы.

### Сценарий 7: Ручная синхронизация в мультикластерной среде

В мультикластерных средах ручная синхронизация выполняется для каждого кластера отдельно.

```bash
# Просмотр приложений во всех кластерах
argocd app list

# Синхронизация конкретного приложения в конкретном кластере
argocd app sync my-app --dest-server https://prod-cluster.example.com

# Синхронизация всех приложений в конкретном кластере
argocd app list --cluster prod-cluster | xargs -I {} argocd app sync {}
```

**Важно:** В ApplicationSet ручная синхронизация выполняется для каждого приложения отдельно. Контроллер ApplicationSet не управляет ручными синхронизациями.

### Сценарий 8: Ручная синхронизация с Hooks (Pre/Post)

Для приложений, требующих миграций баз данных или инициализации перед деплоем.

```bash
# Синхронизация с выполнением PreSync Hooks
argocd app sync my-app --force

# Пропуск PreSync Hooks (опасно!)
argocd app sync my-app --no-hooks

# Синхронизация только PreSync Hooks (без основных ресурсов)
argocd app sync my-app --sync-option NoAutoFinalize=false
```

**Важно:** PreSync Hooks выполняются перед применением основных ресурсов. Если Hook завершается неуспешно, синхронизация прерывается.

### Сценарий 9: Принудительное обновление неизменяемых полей

Если в Git изменилось поле, которое Kubernetes запрещает обновлять (например, `spec.selector` в `Service` или `spec.clusterIP`), синхронизация завершится ошибкой.

**Решение через CLI:**

```bash
argocd app sync my-app --force
```

**Решение в коде (использовать с осторожностью):**

```yaml
spec:
  syncPolicy:
    syncOptions:
    - Force=true # Приведет к удалению и пересозданию ресурса
```

> **Внимание:** `Force=true` удаляет и пересоздает ресурс. Это может привести к даунтайму для Stateless-приложений и потере данных для StatefulSet. Используйте только когда `Replace=true` недостаточно.

**Альтернатива — `Replace=true`:**

```yaml
spec:
  syncPolicy:
    syncOptions:
    - Replace=true # Использует kubectl replace вместо apply
```

`Replace=true` выполняет `kubectl replace`, который перезаписывает весь ресурс. Подходит для ресурсов с неизменяемыми полями, но не приводит к удалению.

### Сценарий 10: Интеграция с cert-manager

cert-manager автоматически добавляет и обновляет аннотации и TLS-секреты. Используйте `managedFieldsManagers` для игнорирования изменений от cert-manager.

```yaml
spec:
  ignoreDifferences:
  - group: cert-manager.io
    kind: Certificate
    managedFieldsManagers:
    - cert-manager-certificates-issuer
  - group: ""
    kind: Secret
    jqPathExpressions:
    - .metadata.annotations["cert-manager.io/certificate-name"]
    - .metadata.annotations["cert-manager.io/issuer-name"]
```

## Технический справочник

### Полный перечень флагов команды `argocd app sync`

| Флаг | Описание | Когда использовать |
| :--- | :--- | :--- |
| `--prune` | Удаляет ресурсы, которых нет в Git. | Всегда при полной синхронизации. |
| `--force` | Использует `kubectl apply --force`. | Для неизменяемых (immutable) полей. |
| `--replace` | Использует `kubectl replace`. | Для ресурсов, не поддерживающих патчи. |
| `--strategy` | Метод применения: `apply` или `server-side`. | `server-side` для Argo CD v3.x. |
| `--dry-run` | Пробный запуск без фактического изменения. | Перед критическими деплами. |
| `--server-side` | Diff и Dry Run на стороне Kubernetes API. | Всегда в v3.x. |
| `--validate` | Валидация манифестов через K8s API. | По умолчанию включен. |
| `--no-validate` | Пропуск валидации манифестов. | Только для некорректных CRD. |
| `--resource` | Синхронизация конкретного ресурса (G:K:N). | Селективная синхронизация. |
| `--label` | Синхронизация по селектору меток. | Групповая синхронизация. |
| `--prune-last` | Удаление старых ресурсов после успеха. | Рекомендуется для Production. |
| `--apply-out-of-sync-only` | Пропуск неизмененных ресурсов. | Для приложений с >100 ресурсами. |
| `--async` | Асинхронное выполнение (не ждать завершения). | Для долгих синхронизаций. |
| `--retry-limit` | Количество повторных попыток. | При временных сетевых ошибках. |
| `--retry-backoff-duration` | Начальный интервал между попытками. | Настройка politики retry. |
| `--retry-backoff-factor` | Множитель интервала. | Экспоненциальный backoff. |
| `--retry-backoff-max-duration` | Максимальное время ожидания. | Ограничение времени retry. |
| `--force` | Использует `kubectl apply --force`. | Для неизменяемых полей. |
| `--cascade` | Каскадное удаление зависимых ресурсов. | При удалении namespace. |
| `--wait` | Ожидание завершения синхронизации. | По умолчанию включен. |
| `--timeout` | Таймаут ожидания (в секундах). | Для долгих операций. |
| `--diff` | Показать diff перед синхронизацией. | Рекомендуется всегда. |
| `--diff-local` | Локальный diff (без запроса к API). | Быстрая проверка. |
| `--manifests` | Локальные манифесты вместо Git. | Для отладки. |
| `--local` | Локальный путь к манифестам. | Для отладки. |
| `--local-repo-root` | Корневой путь репозитория. | Для локальных манифестов. |

### Полный перечень флагов команды `argocd app diff`

| Флаг | Описание | Когда использовать |
| :--- | :--- | :--- |
| `--server-side` | Diff на стороне Kubernetes API. | Всегда в v3.x. |
| `--resource` | Diff конкретного ресурса (G:K:N). | Селективная проверка. |
| `--label` | Diff по селектору меток. | Групповая проверка. |
| `--ignore-normalized` | Игнорирование нормализованных полей. | Для полей, изменяемых API. |
| `--local` | Локальный diff (без запроса к API). | Быстрая проверка. |
| `--local-repo-root` | Корневой путь репозитория. | Для локальных манифестов. |
| `--manifests` | Локальные манифесты вместо Git. | Для отладки. |

### Полный перечень флагов команды `argocd app rollback`

| Флаг | Описание | Когда использовать |
| :--- | :--- | :--- |
| `--prune` | Удаление ресурсов, которых нет в целевой ревизии. | При откате на старую версию. |
| `--force` | Использует `kubectl apply --force`. | Для неизменяемых полей. |
| `--replace` | Использует `kubectl replace`. | Для ресурсов, не поддерживающих патчи. |
| `--wait` | Ожидание завершения отката. | По умолчанию включен. |
| `--timeout` | Таймаут ожидания (в секундах). | Для долгих операций. |

### Настройка логики Retry

```bash
# Базовый retry (3 попытки)
argocd app sync my-app --retry-limit 3

# Экспоненциальный backoff (5 попыток)
argocd app sync my-app --retry-limit 5 --retry-backoff-duration 5s --retry-backoff-factor 2 --retry-backoff-max-duration 3m

# Агрессивный retry (для критичных сервисов)
argocd app sync my-app --retry-limit 10 --retry-backoff-duration 2s --retry-backoff-factor 1.5 --retry-backoff-max-duration 10m
```

## Диагностика и устранение неисправностей

### Типичные проблемы

| Проблема | Симптомы | Вероятная причина | Решение |
| :--- | :--- | :--- | :--- |
| **Sync заблокирован** | Ошибка при попытке синхронизации | Настроены Sync Windows типа `deny` | Проверьте Sync Windows или используйте `manualSync: true` |
| **Diff не отображает изменений** | Нет различий в Diff, но ресурс изменен | Игнорируется поле в `ignoreDifferences` | Проверьте `ignoreDifferences` в манифесте |
| **Dry Run завершается ошибкой** | Ошибка валидации манифестов | Некорректный YAML или отсутствует CRD | Исправьте манифест или добавьте `SkipDryRunOnMissingResource=true` |
| **Rollback не работает** | Нет истории ревизий | Приложение не синхронизировалось успешно | Сначала выполните успешную синхронизацию |
| **Синхронизация медленная** | Синхронизация занимает >5 минут | Много ресурсов, нет `ApplyOutOfSyncOnly` | Используйте `--apply-out-of-sync-only` или разбейте приложение |
| **Ошибка "shared resource"** | Синхронизация падает | Ресурс используется другим приложением | Используйте `--force` или разделите ресурсы |
| **Ошибка "resource not found"** | Синхронизация падает | Ресурс был удален из кластера | Используйте `--prune` или проверьте Git |
| **Прерывание PreSync Hook** | Синхронизация прерывается | PreSync Hook завершился неуспешно | Проверьте логи Hook-а и исправьте ошибку |

### Диагностические команды

```bash
# Просмотр статуса приложения
argocd app get <app-name>

# Принудительное обновление (без синхронизации)
argocd app get <app-name> --refresh

# Просмотр логов контроллера
kubectl logs -n argocd -l app.kubernetes.io/name=argocd-application-controller -f

# Просмотр событий синхронизации
kubectl get events -n argocd --field-selector reason=Synced

# Просмотр деталей последней синхронизации
argocd app history <app-name>

# Просмотр diff перед синхронизацией
argocd app diff <app-name>

# Просмотр diff с учетом SSA
argocd app diff <app-name> --server-side

# Просмотр managedFields ресурса
kubectl get <resource> <name> -o jsonpath='{.metadata.managedFields}' | jq

# Просмотр событий для конкретного ресурса
kubectl describe <resource> <name> | grep -A 10 Events
```

### Пошаговая диагностика

1. **Проверьте статус:** `argocd app get <name>` — убедитесь, что статус `OutOfSync` или `Synced`.
2. **Просмотрите diff:** `argocd app diff <name>` — проверьте, какие именно поля различаются.
3. **Проверьте Sync Windows:** Если есть ограничения по времени, дождитесь окончания блокировки или используйте `manualSync: true`.
4. **Просмотрите логи:** `kubectl logs -n argocd -l app.kubernetes.io/name=argocd-application-controller` — найдите ошибки.
5. **Проверьте Credentials:** Убедитесь, что Argo CD имеет доступ к Git-репозиторию и кластеру.
6. **Проверьте CRD:** Если используются кастомные ресурсы, убедитесь, что CRD установлены.
7. **Проверьте Health Checks:** Убедитесь, что ресурсы проходят проверку здоровья.

## Валидация и проверка работоспособности

### Проверка ручной синхронизации

```bash
# 1. Проверьте статус приложения
argocd app get <name>

# 2. Просмотрите diff
argocd app diff <name> --server-side

# 3. Выполните Dry Run
argocd app sync <name> --dry-run --server-side

# 4. Выполните синхронизацию
argocd app sync <name>

# 5. Проверьте статус после синхронизации
argocd app get <name>
```

### Проверка селективной синхронизации

```bash
# 1. Просмотрите список ресурсов
argocd app get <name> --refresh

# 2. Выберите конкретный ресурс для синхронизации
argocd app sync <name> --resource apps:Deployment:api-server

# 3. Проверьте, что только указанный ресурс обновился
argocd app diff <name> --resource apps:Deployment:api-server
```

### Проверка отката

```bash
# 1. Просмотрите историю ревизий
argocd app history <name>

# 2. Выполните откат к конкретной ревизии
argocd app rollback <name> 5

# 3. Проверьте статус после отката
argocd app get <name>

# 4. Просмотрите diff (должен показать расхождение с Git)
argocd app diff <name>
```

### Проверка Dry Run

```bash
# 1. Выполните Dry Run с валидацией
argocd app sync <name> --dry-run --validate

# 2. Выполните Dry Run без валидации (для некорректных CRD)
argocd app sync <name> --dry-run --no-validate

# 3. Просмотрите вывод Dry Run (в UI или CLI)
argocd app sync <name> --dry-run --server-side --loglevel debug
```

## Лучшие практики

### Приоритет настроек

1. **Для Production:** Всегда используйте `--dry-run --server-side` перед синхронизацией. Используйте `--prune-last` для удаления старых ресурсов.
2. **Для Staging:** Можно использовать `--dry-run` без `--server-side` для ускорения итераций.
3. **Для Development:** Можно использовать `--force` для быстрого исправления ошибок.

### Безопасность

- **Всегда используйте `--dry-run`:** Перед критическими деплами всегда проверяйте изменения.
- **Используйте `--prune-last`:** Удаление старых ресурсов должно происходить только после успешного применения новых.
- **Настройте Sync Windows:** Блокируйте синхронизацию в критические периоды.
- **Ревью через PR:** Любые изменения в манифестах должны проходить code review.
- **Аудит:** Проверяйте журналы аудита для отслеживания всех синхронизаций.

### Масштабирование

- **`--apply-out-of-sync-only`:** Используйте для приложений с >50 ресурсами — снижает нагрузку на API-сервер.
- **`--server-side`:** Используйте для всех приложений в v3.x — переносит логику слияния на сторону Kubernetes.
- **`--async`:** Используйте для долгих синхронизаций, чтобы не блокировать CLI.
- **Разбиение приложений:** Если приложение содержит >1000 ресурсов, рассмотрите разбиение на несколько ApplicationSets.

### Интеграция с CI/CD

- **Git-Triggered Sync:** Автоматическая синхронизация запускается сразу после коммита в Git.
- **PR-Triggered Sync:** Для dev/staging можно настроить синхронизацию при мерже PR.
- **Manual Sync для Prod:** Рассмотрите возможность использования ручной синхронизации для Production с аудитом.
- **Webhook Integration:** Настройте вебхуки для уведомления о ручных синхронизациях.

## Ограничения и edge cases

### Ограничения

1. **Manual Sync не работает во время Sync Windows:** Если настроены `deny` окна, ручная синхронизация будет заблокирована (если нет `manualSync: true`).
2. **Selective Sync не удаляет ресурсы:** Даже с `--prune`, селективная синхронизация не удаляет ресурсы, не указанные в `--resource`.
3. **Rollback не изменяет Git:** После `argocd app rollback` приложение перейдет в статус `OutOfSync`, так как Git-состояние не изменилось.
4. **Dry Run не проверяет Health Checks:** Dry Run только проверяет валидность манифестов, но не проверяет, будут ли ресурсы здоровы после применения.

### Edge Cases

1. **Конфликт с HPA:** Если в Git указано `replicas: 3` и включен `selfHeal`, ручная синхронизация будет конфликтовать с HPA. Используйте `ignoreDifferences` для `replicas`.
2. **Множественные ApplicationSets на один ресурс:** Если ресурс управляется несколькими ApplicationSets, возникает конфликт. Используйте `--force` или разделите ресурсы.
3. **Удаление Application во время синхронизации:** Если Application удален во время выполняющейся синхронизации, операция завершится, но ресурсы в кластере могут остаться в промежуточном состоянии.
4. **Helm Chart с mutable-полями:** Некоторые Helm-чарты используют поля, которые невозможно обновить через `apply`. Используйте `--replace`.
5. **Cross-namespace ресурсы:** Ручная синхронизация работает только в рамках одного namespace. Для кросс-namespace ресурсов настройте отдельные ApplicationSets.
6. **PreSync Hook с долгой миграцией:** Если PreSync Hook (миграция базы данных) выполняется дольше таймаута синхронизации, операция прервется. Настройте `--timeout`.

## Дополнительная информация

### Ограничения

- **Зависшие операции:** Если процесс синхронизации "завис" (например, из-за PreSync Hook), новые изменения не будут применяться до завершения или принудительной остановки текущей операции.
- **Лимит ресурсов:** Argo CD имеет внутренние лимиты на количество управляемых ресурсов. Для очень больших приложений (>1000 ресурсов) рекомендуется разбивать на несколько ApplicationSets.
- **Временные интервалы:** Интервал сверки (Reconciliation Interval) по умолчанию составляет 3 минуты. Ручная синхронизация не зависит от этого интервала.
