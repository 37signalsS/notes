# Окна синхронизации (Sync Windows)

**Актуально для:** Argo CD v3.4.x / master (v3.5+)

Окна с `syncOverrun`, полем `description`, командами `enable-sync-overrun`/`disable-sync-overrun`
и метриками окон доступны начиная с master (v3.5+); в v3.4.x их нет. Различия отмечены в тексте.

## Предварительные требования

1. **Версия Argo CD:** v3.4.x для базовых полей (`kind`, `schedule`, `duration`, `manualSync`,
   `timeZone`, `andOperator`). Для `syncOverrun` и `description` требуется master (v3.5+).
2. **AppProject:** Окна настраиваются в объекте `AppProject` (поле `spec.syncWindows`),
   а не в `Application`. Проект должен существовать.
3. **Доступ:** Доступ к Argo CD UI, CLI (`argocd`) или API для управления AppProject.
4. **Время:** Расписание вычисляется в `timeZone` окна (по умолчанию UTC). Часы на узлах
    Argo CD должны быть синхронизированы (NTP).

## Определения

**Окно синхронизации (Sync Window)** — интервал времени, в течение которого синхронизации
разрешены или запрещены. Задаётся типом (`allow`/`deny`), расписанием в формате cron,
длительностью и селекторами приложений/namespace/кластеров. Связь «окно — приложение»
many-to-many: одно окно может покрывать много приложений, и на одно приложение может
действовать несколько окон.

**Deny Window** — окно, в которое синхронизации запрещены. Используется для «заморозки»
инфраструктуры (праздники, технические работы).

**Allow Window** — окно, в которое синхронизации разрешены. Ключевой нюанс: если для
приложения определено хотя бы одно окно `allow`, то синхронизация возможна **только** в
периоды активности таких окон (вне их — запрещена).

**Manual Sync Bypass (`manualSync: true`)** — переопределение для ручных синхронизаций:
позволяет оператору синхронизировать вручную, когда окна блокируют синхронизацию.
Полезно для экстренных фиксов и для случаев, когда нужно блокировать только автоматику.

**Sync Overrun (`syncOverrun: true`, v3.5+)** — разрешение уже запущенной синхронизации
дойти до конца, когда она выходит за границы своего разрешённого окна.

## Базовые концепции

### Как работают окна

Правила проверки (официальная документация):

1. Если для приложения **не подходит ни одно окно** — все синхронизации разрешены.
2. Если подходят **окна `allow`** — синхронизация разрешена только когда активно
   хотя бы одно из них.
3. Если подходят **окна `deny`** — все синхронизации запрещены, пока эти окна активны.
4. Если активно и подходящее `allow`, и подходящее `deny` — синхронизация **запрещена**:
   `deny` перекрывает `allow`.
5. Окна влияют и на **ручные**, и на **автоматические** синхронизации; `manualSync: true`
   задаёт исключение для ручных.

### Выборка приложений

Окно применяется к приложению по трём механизмам (можно комбинировать в одном окне):

- **Имя приложения** (`applications`) — glob-маски поддерживаются (`prod-*`).
- **Кластер назначения** (`clusters`) — маска проверяется и по имени кластера
  (`Application.spec.destination.name`), и по URL сервера (`Application.spec.destination.server`).
- **Namespace назначения** (`namespaces`) — `Application.spec.destination.namespace`.

По умолчанию механизмы объединяются по **OR** (совпал любой — окно применяется).
Флаг `andOperator: true` требует совпадения **всех** указанных условий.
Пустой список селектора означает **отсутствие ограничения по этому измерению**
(не «ни одно приложение»).

### Параметры конфигурации (`spec.syncWindows`)

| Параметр | Описание | По умолчанию |
| :--- | :--- | :--- |
| `kind` | Тип окна: `allow` или `deny`. | - |
| `schedule` | Начало окна, cron в классическом 5-польевом формате (`0 22 * * 5-7`). `@every` не поддерживается. | - |
| `duration` | Длительноста окна, формат Go duration (`1h`, `30m`, `168h`). | - |
| `applications` | Список имён/масок приложений. Пустой — без ограничений. | - |
| `namespaces` | Список namespace'ов назначения. Пустой — без ограничений. | - |
| `clusters` | Список имён/URL кластеров (маски). Пустой — без ограничений. | - |
| `manualSync` | Разрешить ручные синхронизации, когда окна блокируют синхронизацию. | `false` |
| `timeZone` | Часовой пояс расписания (IANA, например `Europe/Moscow`). Невалидное значение молча превращается в UTC (warning в логах). | `UTC` |
| `andOperator` | Требовать совпадения всех селекторов (AND) вместо OR. | `false` |
| `description` | Произвольная заметка (например, номер тикета), до 255 символов. **v3.5+** | - |
| `syncOverrun` | Разрешить запущенным синхронизациям завершиться за пределами окна. **v3.5+** | `false` |

### Логика проверки (алгоритм)

Для приложения выбираются **подходящие** окна (`Matches`), затем они разбиваются на
активные и неактивные `allow`-окна, и применяется:

1. **Есть активные `deny`:** синхронизация разрешена, если это ручная синхронизация
   **и все** активные deny-окна имеют `manualSync: true`; иначе — запрещена.
2. **Нет активных deny, есть активные `allow`:** разрешена.
3. **Нет активных окон, но есть неактивные `allow`:** разрешена только для ручной
   синхронизации, если **все** эти allow-окна имеют `manualSync: true`; иначе запрещена.
4. **Подходящих окон нет:** разрешена.

Важно: `manualSync` и `syncOverrun` имеют **ALL-семантику** — для переопределения
должны быть включены во всех подходящих окнах соответствующего типа, а не хотя бы в одном.

## Sync Overrun (v3.5+)

`syncOverrun` позволяет уже запущенной синхронизации продолжиться, когда она выходит
за границы разрешённого периода. Новые синхронизации при этом по-прежнему блокируются.

**Deny Window Overrun** (`syncOverrun: true` на deny-окне):

- Синхронизации, начатые **до** активации deny-окна, могут завершиться.
- Новые синхронизации в deny-окне заблокированы.
- **Все** активные deny-окна должны иметь `syncOverrun`.

**Allow Window Overrun** (`syncOverrun: true` на allow-окне):

- Синхронизации, начатые **во время** allow-окна, могут продолжиться после его завершения.
- **Все** неактивные allow-окна должны иметь `syncOverrun`.
- Продолжение возможно, пока не активируется deny-окно без `syncOverrun`.

**Сценарии переходов** (официальная документация):

| Переход | Результат |
| :--- | :--- |
| Нет окна → Deny с overrun | Продолжается |
| Нет окна → Deny без overrun | Заблокирована |
| Allow с overrun → Deny с overrun | Продолжается |
| Allow с overrun → Deny без overrun | Заблокирована |
| Allow без overrun → Deny с overrun | Разрешена (deny поддерживает overrun, синк был разрешён при старте) |
| Allow без overrun → Deny без overrun | Заблокирована |
| Allow с overrun → конец Allow | Продолжается |
| Несколько Allow с overrun → все закончились | Продолжается |
| Несколько Allow, одно без overrun → все закончились | Заблокирована |

## Практические сценарии

### Сценарий 1: Глобальная заморозка (Code Freeze)

Блокировка всех изменений на время праздников для всего проекта:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: production-project
spec:
  syncWindows:
  - kind: deny
    schedule: '0 0 31 12 *'   # 31 декабря, 00:00
    duration: 168h            # 7 дней
    timeZone: "Europe/Moscow"
    applications: ["*"]
    manualSync: false         # даже админы не смогут деплоить вручную
```

### Сценарий 2: Рабочие часы с экстренным доступом

Деплой разрешён только в рабочие часы, но ручной деплой доступен всегда (для хотфиксов):

```yaml
spec:
  syncWindows:
  - kind: allow
    schedule: '0 10 * * 1-5'  # Пн-Пт с 10:00
    duration: 8h
    applications: ["*-api"]
    manualSync: true          # ручной деплой разрешен вне окна
```

### Сценарий 3: Длинные деплои и миграции (v3.5+)

Деплой, начатый в окне, должен дойти до конца даже после закрытия окна:

```yaml
spec:
  syncWindows:
  - kind: allow
    schedule: '30 23 * * *'   # ежедневно в 23:30
    duration: 1h
    syncOverrun: true         # запущенный синк завершится после 00:30
```

### Сценарий 4: Разные окна для разных сред

```yaml
spec:
  syncWindows:
  # Dev: деплой разрешён всегда
  - kind: allow
    schedule: '0 0 * * *'
    duration: 24h
    applications: ["dev-*"]
    manualSync: true
  # Staging: рабочие часы
  - kind: allow
    schedule: '0 9 * * 1-5'
    duration: 10h
    applications: ["staging-*"]
    manualSync: true
  # Prod: только окно обслуживания по средам
  - kind: allow
    schedule: '0 10 * * 3'
    duration: 2h
    applications: ["prod-*"]
    manualSync: true
```

### Сценарий 5: Мультикластерные окна

```yaml
spec:
  syncWindows:
  # Prod-кластер: рабочие часы
  - kind: allow
    schedule: '0 10 * * 1-5'
    duration: 8h
    clusters: ["prod-cluster"]     # маска проверяется и по имени, и по URL
    manualSync: true
  # Принудительная блокировка prod-кластера в праздники
  - kind: deny
    schedule: '0 0 31 12 *'
    duration: 168h
    clusters: ["prod-cluster"]
    manualSync: false
```

### Сценарий 6: Комбинирование условий (andOperator)

```yaml
spec:
  syncWindows:
  # Деплой разрешён только для backend-api в staging-кластере
  - kind: allow
    schedule: '0 10 * * 1-5'
    duration: 8h
    applications: ["backend-api"]
    clusters: ["staging-cluster"]
    andOperator: true         # ВСЕ условия должны совпасть
```

Без `andOperator: true` условие будет OR (достаточно совпадения любого измерения).

### Сценарий 7: Управление окнами через CLI

Окна можно создавать и менять без правки манифеста:

```bash
# Добавить окно
argocd proj windows add production-project \
    --kind allow \
    --schedule "0 22 * * *" \
    --duration 1h \
    --applications "*"
# → окно добавлено в AppProject

# Обновить namespaces существующего окна (ID из list)
argocd proj windows update production-project 0 --namespaces default,kube-system,prod1
# → поле namespaces заменено целиком (нужен полный список значений)

# Разрешить ручные синхронизации в окне
argocd proj windows enable-manual-sync production-project 0
# → MANUALSYNC: Enabled

# Запретить ручные синхронизации в окне
argocd proj windows disable-manual-sync production-project 0
# → MANUALSYNC: Disabled

# Включить/выключить overrun для существующего окна (v3.5+)
argocd proj windows enable-sync-overrun production-project 0
argocd proj windows disable-sync-overrun production-project 0

# Список окон проекта
argocd proj windows list production-project
# → ID  STATUS    KIND   SCHEDULE    DURATION  APPLICATIONS  NAMESPACES  CLUSTERS  MANUALSYNC
# → 0   Active    allow  * * * * *   1h        -             -           prod1     Disabled
# → 1   Inactive  deny   * * * 1     3h        -             default     -         Disabled
```

Все поля окна обновляются через CLI или UI; поля `applications`, `namespaces` и `clusters`
при обновлении заменяются **целиком** — в запросе должен быть полный список значений.
Удалить окно через CLI нельзя — окна удаляются правкой манифеста AppProject:

```bash
# Удаление всех окон проекта (вместо несуществующего "windows delete --all")
kubectl patch appproject production-project -n argocd --type merge -p '{"spec": {"syncWindows": []}}'
```

### Сценарий 8: Проверка состояния синхронизации

UI и CLI показывают состояние окон. В UI панель окрашена:
**Red** — синхронизация запрещена, **Orange** — разрешена только ручная, **Green** — разрешена.

```bash
argocd app get guestbook
# → Name:               guestbook
# → Project:            default
# → Server:             in-cluster
# → Namespace:          default
# → SyncWindow:         Sync Denied
# → Assigned Windows:   deny:0 2 * * *:1h,allow:0 2 3 3 3:1h
# → Sync Policy:        Automated
# → Sync Status:        Synced to  (5c2d89b)
# → Health Status:      Healthy
```

## Диагностика и мониторинг

### Просмотр активных окон

```bash
# Список окон проекта (STATUS: Active/Inactive — актуально на текущий момент)
argocd proj windows list <project>

# Состояние окон конкретного приложения
argocd app get <app>          # строки SyncWindow и Assigned Windows

# Манифест проекта
kubectl get appproject <project> -n argocd -o yaml | sed -n '/syncWindows:/,$p'
```

### Метрики Prometheus (v3.5+)

Application controller эмитирует метрики окон на endpoint `/metrics` (включаются отдельной
опцией контроллера):

| Метрика | Тип и лейблы | Смысл |
| :--- | :--- | :--- |
| `argocd_app_sync_window` | gauge, лейбл `window_kind` = `allow`/`deny` | `1` — хотя бы одно подходящее окно этого типа активно сейчас |
| `argocd_app_sync_blocked` | gauge `0`/`1` | `1` — автоматическая синхронизация прямо сейчас была бы отклонена; `0` — когда окна не настроены; также `1` при невозможности вычислить окна (fail-closed) |
| `argocd_app_sync_window_error` | gauge `0`/`1` | `1` — окна не удалось вычислить: не определён AppProject или у подходящего окна не парсится `schedule`/`duration` |

Лейблы всех трёх метрик: `namespace`, `name`, `project`.

```promql
# Приложения, чьи автоматические синхронизации сейчас заблокированы окнами
argocd_app_sync_blocked == 1

# Приложения с невалидными окнами (синхронизации заблокированы fail-closed)
argocd_app_sync_window_error == 1

# Приложения с активным deny-окном
argocd_app_sync_window{window_kind="deny"} == 1
```

### Пошаговая диагностика блокировки синхронизации

1. **Проект:** `kubectl get appproject <project> -o yaml` — есть ли секция `syncWindows`.
2. **Окна:** `argocd proj windows list <project>` — типы, расписание, STATUS.
3. **Приложение:** `argocd app get <app>` — `SyncWindow` и `Assigned Windows` (подходят ли
   окна данному приложению вообще).
4. **Время:** `date` в namespace Argo CD (`kubectl exec -n argocd deploy/argocd-application-controller -- date`)
   и `timeZone` окна — расписание вычисляется в UTC, если `timeZone` не указан.
5. **Попытка синка:** `argocd app sync <app>` — сообщение об ошибке прямо укажет на окно.
6. **Логи контроллера:** `kubectl logs -n argocd -l app.kubernetes.io/name=argocd-application-controller`
   — поиск по `sync window`.

## Технические нюансы

### Формат расписания и длительности

- **Cron:** классический 5-польевой формат (минута, час, день месяца, месяц, день недели).
  Дескрипторы вроде `@every 1h` не поддерживаются.
- **Duration:** формат Go duration (`1h`, `30m`, `168h`). Окно активно от момента
  срабатывания расписания в течение `duration`.
- **`duration: 0s`** — окно никогда не становится активным (валидно, но бесполезно).
- **Гранулярность:** расписание вычисляется с минутной точностью.

### Fail-closed на невалидных окнах

Если у окна, **подходящего приложению**, не парсится `schedule` или `duration`,
синхронизации этого приложения **заблокированы** с ошибкой — контроль не «пропускает»
приложение при ошибке конфигурации (v3.5+: это видно по метрике
`argocd_app_sync_window_error == 1`). Невалидный `timeZone` ошибкой не является:
окно молча переходит в UTC (warning в логах контроллера).

### Взаимодействие с другими механизмами

- **Автоматическая синхронизация:** в deny-окне (или вне allow-окон) автосинк не
  запускается; приложение остаётся `OutOfSync`, синхронизация произойдёт, когда окно
  снова разрешит.
- **Волны и хуки:** окно проверяется при старте операции (до PreSync-хуков) и на каждом
  проходе контроллера во время операции. Если окно закрылось в процессе **без**
  `syncOverrun`, операция **приостанавливается** (контроллер ставит сообщение
  `Sync operation blocked by sync window`) и возобновляется, когда окно разрешит —
  она не прерывается и не откатывается. С `syncOverrun: true` (v3.5+, на всех подходящих
  окнах) операция идёт до конца.
- **Прогрессивная синхронизация (ApplicationSet):** окна проверяются для каждого
  приложения отдельно по его собственному проекту; контроллер ApplicationSet окна
  не управляет.
- **Селективная синхронизация:** это обычная операция sync — окна проверяются так же.
- **Skip-reconcile:** при аннотации `argocd.argoproj.io/skip-reconcile` вся обработка
  приложения остановлена, включая проверки окон.

## Лучшие практики

- **Явный `timeZone`:** всегда указывайте IANA-пояс — иначе расписание считается в UTC,
  что в мультирегиональных командах приводит к неожиданному времени деплоя.
- **`manualSync: true` для экстренных фиксов:** особенно полезно, когда нужно блокировать
  только автоматику. Помните про ALL-семантику: если активны несколько deny-окон, ручной
  синк разрешён только когда `manualSync: true` во всех них.
- **`syncOverrun: true` для длинных миграций (v3.5+):** для приложений с долгими
  PreSync-хуками (миграции БД), чтобы операция не зависла на границе окна.
- **Deny для Production, Allow для рабочих часов:** deny-окна — для форс-мажоров и
  праздников; allow-окна — когда деплой должен быть строго в регламентированное время.
- **Мониторинг (v3.5+):** алерт на `argocd_app_sync_blocked == 1` (автосинки под
  заморозкой дольше ожидаемого) и на `argocd_app_sync_window_error == 1` (битая
  конфигурация окон = заблокированные деплои).
- **Аудит (v3.5+):** используйте `description` для номера тикета/причины заморозки.

## Ограничения и edge cases

1. **Нет «кроме праздников»:** cron не поддерживает исключения по датам — для праздников
   создаются отдельные deny-окна.
2. **Наложение Allow и Deny:** при одновременной активности Deny побеждает.
3. **Manual Sync во время Deny:** ручная синхронизация разрешена (при `manualSync: true`),
   автоматическая остаётся заблокированной.
4. **ALL-семантика `manualSync`/`syncOverrun`:** переопределение работает только когда
   включено во всех подходящих окнах соответствующего типа; одно окно с `false` блокирует.
5. **Пустые списки селекторов:** `applications: []` (или `namespaces`/`clusters`) означает
   «без ограничений по этому измерению», а не «ни одно приложение». Эквивалентно `["*"]`
   по эффекту, но не по записи.
6. **Удаление окон:** CLI-команды удаления нет — только правка манифеста AppProject.
7. **Обновление через CLI:** `applications`/`namespaces`/`clusters` заменяются целиком.
8. **`description`:** до 255 символов (v3.5+).
9. **Удаление AppProject во время активной операции:** текущая операция завершится,
   но новые синхронизации станут невозможны (проект — контекст разрешений и окон).
10. **ApplicationSet создаёт приложения во время Deny:** приложения создаются, но не
    синхронизируются до открытия Allow-окна.
