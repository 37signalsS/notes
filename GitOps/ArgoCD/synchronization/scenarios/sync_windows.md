# Argo CD — окна синхронизации

> **Актуальность (2026):** В версии Argo CD v3.x управление окнами синхронизации стало более гибким благодаря поддержке часовых поясов (IANA Time Zones) и расширенному сопоставлению ресурсов через `andOperator`. Механизм остается ключевым инструментом для обеспечения безопасности деплоя в критические периоды (праздники, ночные смены).

## Предварительные требования

Перед настройкой окон синхронизации необходимо убедиться в следующем:

1. **Версия Argo CD:** v2.4+ (рекомендуется v3.x для полной поддержки `timeZone` и расширенных фильтров).
2. **Доступ:** У вас есть доступ к Argo CD UI, CLI (`argocd`) или API для управления AppProject.
3. **AppProject:** Окна настраиваются в объекте `AppProject`, а не в `Application`. Убедитесь, что проект создан.
4. **Понимание иерархии:** Deny окна приоритетнее Allow окон. Manual Sync может обходить Deny (при `manualSync: true`).
5. **Текущее время:** Убедитесь, что время на сервере Argo CD корректно синхронизировано (NTP).

## Определения

**Окна синхронизации (Sync Windows)** — функционал Argo CD, позволяющий регламентировать время выполнения операций синхронизации (автоматических и ручных) на основе расписания. Политики окон настраиваются в объекте **AppProject**.

**Deny Window (Запрещающее окно)** — интервал времени, в течение которого любые попытки синхронизации будут заблокированы. Используется для "заморозки" инфраструктуры.

**Allow Window (Разрешающее окно)** — интервал времени, в течение которого деплой разрешен. Важно: если в проекте определено хотя бы одно окно `Allow`, синхронизация возможна **только** в периоды активности таких окон.

**Sync Overrun** — параметр, позволяющий синхронизации, начатой *внутри* разрешенного окна, успешно завершиться, даже если время окна истекло в процессе деплоя.

**Manual Sync Bypass** — флаг `manualSync: true`, позволяющий операторам выполнять ручную синхронизацию в UI/CLI даже в запрещенные периоды (полезно для экстренных фиксов).

## Базовые концепции

### Иерархия и логика проверки (Precedence)

При проверке возможности деплоя Argo CD следует алгоритму:
1.  **Deny приоритетнее всего:** Если текущее время попадает в активное окно `kind: deny`, синхронизация запрещена безусловно.
2.  **Обязательность Allow:** Если в проекте есть хотя бы одно правило `kind: allow`, текущее время должно совпадать хотя бы с одним из них. Если правил `allow` нет, считается, что деплой разрешен всегда (при условии отсутствия `deny`).
3.  **Manual Sync:** Флаг `manualSync: true` позволяет операторам выполнять ручную синхронизацию в UI/CLI даже в запрещенные периоды (полезно для экстренных фиксов).

### Взаимодействие с другими механизмами

- **Само-синхронизация (Auto Sync):** Если настроена [автоматическая синхронизация](./auto_sync.md), окна `deny` блокируют автоматические деплобы. Автоматическая синхронизация не запускается, пока окно `deny` активно, даже если в Git появились изменения.
- **Синхронизирующие волны и хуки:** Окна проверяются только перед запуском синхронизации. Если синхронизация уже выполняется и используется [Sync Waves](./sync_waves_hooks.md), окно не проверяется повторно для каждой волны. Это означает, что длинный деплой с несколькими волнами может продолжаться после закрытия окна.
- **Прогрессивная синхронизация (Progressive Sync):** В ApplicationSet окна проверяются для каждого приложения отдельно. Контроллер ApplicationSet не управляет окнами синхронизации.
- **Ignore Differences:** Если настроено [игнорирование различий](../ignore_differences.md), это не влияет на проверку окон. Окна проверяются только по времени.

### Параметры конфигурации (AppProject)

| Параметр | Описание | По умолчанию |
| :--- | :--- | :--- |
| `kind` | Тип окна: `allow` или `deny`. | - |
| `schedule` | Расписание в формате Cron (`0 22 * * 5-7`). | - |
| `duration` | Длительность окна (например, `2h`, `30m`). | - |
| `timeZone` | Часовой пояс (например, `Europe/Moscow`). По умолчанию используется время сервера Argo CD. | UTC |
| `applications` | Список приложений или масок (`prod-*`). `["*"]` — все приложения. | `["*"]` |
| `namespaces` | Целевые пространства имен в Kubernetes. `["*"]` — все namespace. | `["*"]` |
| `clusters` | Названия или URL целевых кластеров. `["*"]` — все кластеры. | `["*"]` |
| `andOperator` | Если `true`, окно применится только при совпадении всех условий (App AND Namespace AND Cluster). | `false` |
| `manualSync` | Разрешить ручную синхронизацию во время Deny окон. | `false` |
| `syncOverrun` | Разрешить завершение синхронизации после закрытия окна. | `false` |

### Особенности фильтрации приложений

- **Маски (Glob patterns):** В поле `applications` поддерживаются маски: `*-api`, `prod-*`, `*-staging`.
- **Конкретные имена:** Можно указать конкретные имена приложений: `["my-app", "backend-api"]`.
- **Все приложения:** `["*"]` — применяется ко всем приложениям проекта.
- **Сочетание:** Можно комбинировать конкретные имена и маски: `["my-app", "*-api"]`.

## Практические сценарии

### Сценарий 1: Глобальная заморозка (Code Freeze)

Блокировка всех изменений на время новогодних праздников для всех приложений проекта.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: production-project
spec:
  syncWindows:
  - kind: deny
    schedule: '0 0 31 12 *' # 31 декабря
    duration: 168h        # 7 дней
    timeZone: "Europe/Moscow"
    applications: ["*"]
    manualSync: false     # Даже админы не смогут деплоить вручную
```

### Сценарий 2: Окна обслуживания (Maintenance Windows)

Разрешить деплой только в рабочие часы по будням.

```yaml
spec:
  syncWindows:
  - kind: allow
    schedule: '0 10 * * 1-5' # Пн-Пт с 10:00
    duration: 8h
    timeZone: "Europe/Prague"
    applications: ["*-api"]
    manualSync: true         # Ручной деплой разрешен вне окна для хотфиксов
```

### Сценарий 3: Защита от прерывания длинных деплоев

Если деплой занимает 15 минут, а до конца окна осталось 5 минут, параметр `syncOverrun` предотвратит прерывание процесса.

```yaml
spec:
  syncWindows:
  - kind: allow
    schedule: '30 23 * * *' # Ежедневно в 23:30
    duration: 1h
    syncOverrun: true      # Разрешить завершение после 00:30
```

### Сценарий 4: Разные окна для разных сред (Multi-Environment)

Настройка разных окон для dev, staging и prod в одном проекте.

```yaml
spec:
  syncWindows:
  # Dev: деплой разрешен всегда
  - kind: allow
    schedule: '0 0 * * *'
    duration: 24h
    applications: ["dev-*"]
    manualSync: true

  # Staging: деплой в рабочие часы
  - kind: allow
    schedule: '0 9 * * 1-5'
    duration: 10h
    timeZone: "Europe/Moscow"
    applications: ["staging-*"]
    manualSync: true

  # Prod: деплой только в окно обслуживания
  - kind: allow
    schedule: '0 10 * * 3'  # Среда в 10:00
    duration: 2h
    timeZone: "Europe/Moscow"
    applications: ["prod-*"]
    manualSync: true         # Ручной деплой разрешен для хотфиксов
```

### Сценарий 5: Мультикластерные окна

Настройка окон для разных кластеров.

```yaml
spec:
  syncWindows:
  # Prod кластер: деплой только в рабочие часы
  - kind: allow
    schedule: '0 10 * * 1-5'
    duration: 8h
    timeZone: "Europe/Moscow"
    clusters: ["prod-cluster"]
    manualSync: true

  # Dev кластер: деплой разрешен всегда
  - kind: allow
    schedule: '0 0 * * *'
    duration: 24h
    clusters: ["dev-cluster"]
    manualSync: true

  # Принудительная блокировка prod кластера в праздники
  - kind: deny
    schedule: '0 0 31 12 *'
    duration: 168h
    timeZone: "Europe/Moscow"
    clusters: ["prod-cluster"]
    manualSync: false
```

### Сценарий 6: Окна с комбинированием условий (andOperator)

Использование `andOperator: true` для точной фильтрации.

```yaml
spec:
  syncWindows:
  # Разрешить деплой только для backend-api в staging кластере
  - kind: allow
    schedule: '0 10 * * 1-5'
    duration: 8h
    timeZone: "Europe/Moscow"
    applications: ["backend-api"]
    clusters: ["staging-cluster"]
    andOperator: true       # ВСЕ условия должны совпасть
    manualSync: true
```

**Важно:** Без `andOperator: true` условие будет OR (любое из совпавших).

### Сценарий 7: Временное отключение окон

Отключение всех окон для проекта (удаление или комментирование).

```bash
# Через CLI: удаление всех окон
argocd proj windows list production-project
argocd proj windows delete production-project --all

# Через kubectl: комментирование секции syncWindows
kubectl patch appproject production-project -n argocd --type merge -p '{"spec": {"syncWindows": []}}'

# Через API: обновление AppProject
argocd proj update production-project --sync-window kind=allow,schedule="0 0 * * *",duration=24h,applications="*"
```

**Рекомендация:** Вместо удаления лучше временно установить `duration: 24h` с `kind: allow` для всех приложений.

### Сценарий 8: Взаимодействие с Hooks

Окна проверяются перед запуском PreSync Hooks. Если Hook уже выполняется и окно закрывается, Hook не прерывается.

```yaml
spec:
  syncWindows:
  - kind: allow
    schedule: '0 10 * * 1-5'
    duration: 2h
    timeZone: "Europe/Moscow"
    applications: ["migration-app"]
    syncOverrun: true      # Важно для долгих миграций
    manualSync: true
```

**Пояснение:** Если PreSync Hook (миграция базы данных) начинается в 10:00 и выполняется 1.5 часа, `syncOverrun: true` гарантирует, что основные ресурсы будут применены после завершения Hook, даже если окно закрылось в 12:00.

## Технические нюансы и ограничения

### Визуальная индикация
В интерфейсе Argo CD активные окна отображаются индикаторами:
- **Красный баннер:** Синхронизация заблокирована (на странице приложения и в настройках проекта).
- **Зеленый баннер:** Синхронизация разрешена (только если есть окна `Allow`).
- **Желтый баннер:** Активно окно `allow`, но `manualSync: false` (ручной деплой заблокирован).

### Особенности часовых поясов
Всегда явно указывайте `timeZone`. В мульти-региональных командах это предотвращает путаницу, когда расписание Cron срабатывает в неожиданное время из-за настроек системного времени в поде `argocd-application-controller`.

**IANA Time Zones (рекомендуемые):**
- `Europe/Moscow`
- `Europe/Prague`
- `America/New_York`
- `Asia/Tokyo`
- `UTC` (по умолчанию)

**Важно:** Время сервера Argo CD может отличаться от времени в Cron-расписании. Всегда проверяйте время на сервере: `date` или `timedatectl`.

### Особенности иерархии (важно!)

1. **Deny приоритетнее Allow:** Если текущее время попадает в любое активное Deny окно, синхронизация запрещена, даже если есть активное Allow окно.
2. **Manual Sync обходит Deny:** Флаг `manualSync: true` позволяет ручную синхронизацию во время Deny окон. Это полезно для экстренных фиксов.
3. **Sync Overrun не проверяется повторно:** Если синхронизация уже выполняется и окно закрывается, `syncOverrun: true` позволяет завершить процесс. Если `syncOverrun: false`, процесс прерывается.
4. **Нет правил Allow = все разрешено:** Если в проекте нет ни одного Allow окна, деплой разрешен всегда (при условии отсутствия Deny).

### Гранулярность расписания

- **Минимальный интервал:** Cron-расписание проверяется каждую минуту. Минимальный интервал окна — 1 минута.
- **Максимальная длительность:** Ограничена только Cron-расписанием. Можно настроить окно на несколько дней или недель.
- **Наложение окон:** Можно создать несколько окон для одного приложения. Например, одно Allow окно для рабочих часов и одно Deny окно для обеденного перерыва.

## Диагностика и мониторинг

### Просмотр активных окон

```bash
# Через CLI: список окон для проекта
argocd proj windows list production-project

# Через kubectl: просмотр AppProject
kubectl get appproject production-project -n argocd -o yaml | jq '.spec.syncWindows'

# Через API: HTTP-запрос
curl -s https://argocd.example.com/api/v1/projects/production-project | jq '.spec.syncWindows'
```

### Проверка доступности синхронизации

```bash
# Попытка синхронизации (покажет ошибку, если окно закрыто)
argocd app sync my-app

# Просмотр статуса приложения (включая информацию об окнах)
argocd app get my-app

# Просмотр логов контроллера (поиск ошибок, связанных с окнами)
kubectl logs -n argocd -l app.kubernetes.io/name=argocd-application-controller | grep -i "sync window"
```

### Мониторинг через Prometheus

Argo CD предоставляет метрики для мониторинга:

| Метрика | Описание |
| :--- | :--- |
| `argocd_app_info` | Информация о приложении (включая статус). |
| `argocd_app_sync_total` | Общее количество синхронизаций. |
| `argocd_app_reconcile_total` | Количество реконсиляций. |
| `argocd_app_health_status` | Статус здоровья приложения. |

**Пример PromQL-запроса для поиска заблокированных приложений:**
```promql
argocd_app_info{sync_status="OutOfSync"} * on(name) group_left()
(argocd_app_sync_total{phase="Error"} > 0)
```

### Пошаговая диагностика

1. **Проверьте AppProject:** `kubectl get appproject <name> -o yaml` — убедитесь, что секция `syncWindows` существует.
2. **Просмотрите окна:** `argocd proj windows list <project>` — проверьте расписание и типы окон.
3. **Проверьте текущее время:** `date` — убедитесь, что время соответствует расписанию.
4. **Попробуйте синхронизацию:** `argocd app sync <app>` — проверьте, блокируется ли синхронизация.
5. **Просмотрите логи:** `kubectl logs -n argocd -l app.kubernetes.io/name=argocd-application-controller` — найдите ошибки.

## Лучшие практики

### Приоритет настроек

1. **Для Production:** Всегда используйте Deny окна для блокировки деплоев в нерабочее время. Разрешайте ручную синхронизацию (`manualSync: true`) для экстренных фиксов.
2. **Для Staging:** Используйте Allow окна для рабочих часов. Manual Sync может быть отключен.
3. **Для Development:** Allow окна на 24 часа. Manual Sync разрешен.

### Безопасность

- **`manualSync: false` для критических систем:** Блокируйте ручную синхронизацию для production-приложений, требующих approvals.
- **`syncOverrun: true` для длинных миграций:** Используйте для приложений с PreSync Hooks (миграции базы данных).
- **Комбинируйте с Rollback:** Настройте Allow окна для откатов (или используйте `manualSync: true`).
- **Мониторинг:** Настройте алерты на основе Prometheus-метрик для отслеживания заблокированных приложений.

### Масштабирование

- **Глобальные окна:** Используйте `applications: ["*"]` для блокировки всех приложений проекта.
- **Частные окна:** Используйте конкретные имена приложений или маски для точечной настройки.
- **Мультикластер:** Используйте `clusters: ["prod-cluster"]` для блокировки только определенных кластеров.
- **Комбинируйте:** Используйте несколько окон для одного проекта (например, Allow для dev, Deny для prod).

### Интеграция с CI/CD

- **Git-Triggered Sync:** Автоматическая синхронизация запускается сразу после коммита в Git, но блокируется окнами.
- **PR-Triggered Sync:** Для dev/staging можно настроить синхронизацию при мерже PR (с учетом окон).
- **Manual Sync для Prod:** Рассмотрите возможность использования ручной синхронизации для Production с аудитом.
- **Webhook Integration:** Настройте вебхуки для уведомления о блокировках синхронизации.

## Ограничения и edge cases

### Ограничения

1. **Manual Sync не работает во время Deny окон:** Если настроены `deny` окна, ручная синхронизация будет заблокирована (если нет `manualSync: true`).
2. **Sync Overrun не влияет на новые синхронизации:** Если синхронизация уже выполняется и окно закрывается, `syncOverrun: true` позволяет завершить процесс. Но новые синхронизации будут заблокированы.
3. **Нет поддержки праздников:** Окна не поддерживают расписание "кроме праздников". Нужно создавать отдельные Deny окна для праздников.
4. **Время сервера Argo CD:** Время в Cron-расписании зависит от времени сервера Argo CD. Если сервер настроен неправильно, окна могут работать некорректно.

### Edge Cases

1. **Наложение Allow и Deny окон:** Если текущее время попадает в оба окна (Allow и Deny), Deny приоритетнее. Синхронизация будет заблокирована.
2. **Manual Sync во время Deny окна с `manualSync: true`:** Ручная синхронизация разрешена. Автоматическая синхронизация остается заблокированной.
3. **Sync Overrun и Retry:** Если синхронизация завершилась неуспешно и включен Retry, попытка повтора будет заблокирована окном (если окно уже закрылось).
4. **Multiple Allow окна для одного приложения:** Если для приложения настроено несколько Allow окон, деплой разрешен в любое время, попадающее хотя бы в одно окно.
5. **Пустые списки applications/clusters:** `applications: []` или `clusters: []` означает "ни одно приложение/кластер". Это не эквивалентно `["*"]`.
6. **Удаление AppProject во время активного окна:** Если проект удален во время выполняющейся синхронизации, операция завершится, но новые синхронизации будут невозможны.
7. **Конфликт с ApplicationSet:** Если ApplicationSet создает новые приложения во время Deny окна, эти приложения не будут синхронизированы до открытия Allow окна.

## Дополнительная информация

### Ограничения

- **Зависшие операции:** Если процесс синхронизации "завис" (например, из-за PreSync Hook), новые изменения не будут применяться до завершения или принудительной остановки текущей операции. Окна не влияют на уже выполняющиеся синхронизации.
- **Лимит окон:** Argo CD не ограничивает количество окон синхронизации. Но слишком много окон может усложнить управление.
- **Временные интервалы:** Окна проверяются каждую минуту. Минимальный интервал окна — 1 минута.
