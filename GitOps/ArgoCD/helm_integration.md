# Интеграция Argo CD с Helm

## Определения

**Helm** — пакетный менеджер для Kubernetes, использующий формат чартов для описания приложений.

**Helm-чарт (Chart)** — набор файлов, описывающих связанные ресурсы Kubernetes.

**Файлы значений (Values)** — параметры конфигурации чарта, которые позволяют настраивать приложение под конкретное окружение.

**Интеграция Argo CD с Helm** — набор механизмов, позволяющих Argo CD использовать Helm-чарты в качестве источника для манифестов приложений.

## Базовые концепции

Argo CD поддерживает несколько основных подходов к интеграции с Helm, обеспечивая гибкость между простотой использования и строгостью GitOps.

### Подход 1: Нативная поддержка Helm-репозиториев

Argo CD напрямую обращается к Helm-репозиторию (традиционному HTTP/HTTPS или OCI-совместимому) и выполняет рендеринг чарта «на лету» во время синхронизации.

#### Традиционный репозиторий
```yaml
spec:
  source:
    repoURL: 'https://charts.bitnami.com/bitnami'
    chart: 'redis'
    targetRevision: 16.8.9
```

#### OCI-репозиторий
Argo CD нативно поддерживает Helm-чарты в OCI-реестрах (Harbor, Quay, GitHub Packages).
```yaml
spec:
  source:
    repoURL: 'ghcr.io/argoproj/charts'
    chart: 'argo-cd'
    targetRevision: 5.x.x
```

**Преимущества:**
- Низкий порог вхождения.
- Не требуется сторонний CI для генерации манифестов.
- Автоматическое уведомление об обновлениях (при использовании диапазонов версий).

**Недостатки:**
- Изменения параметров требуют редактирования ресурса `Application`.
- Сложность аудита конкретных изменений в YAML до их применения.

### Подход 2: Использование нескольких источников (Multiple Sources)

Современный стандарт (v2.6+), позволяющий объединять публичный Helm-чарт и приватные конфигурации (`values.yaml`) из разных репозиториев в одном приложении.

```yaml
spec:
  sources:
    - repoURL: 'https://charts.bitnami.com/bitnami'
      chart: 'redis'
      targetRevision: 16.8.9
      helm:
        valueFiles:
          - $values/charts/redis/values-prod.yaml
    - repoURL: 'https://github.com/my-org/gitops-repo.git'
      targetRevision: HEAD
      ref: values
```

**Преимущества:**
- Четкое разделение стороннего кода (чарт) и собственной конфигурации (Git).
- Идеально для GitOps: все изменения `values` отслеживаются в Git.

### Подход 3: Генерация манифестов (helm template и Git)

Манифесты генерируются заранее (обычно в CI) и сохраняются в Git как «плоские» YAML-файлы.

**Процесс:**
1. Разработчик меняет `values.yaml` в репозитории.
2. CI-пайплайн запускает `helm template` и записывает результат в отдельную директорию.
3. Argo CD отслеживает только директорию со сгенерированными манифестами.

**Преимущества:**
- Полная прозрачность: в Git виден конечный результат.
- Возможность «патчить» любые ресурсы через Kustomize поверх Helm.
- Совместимость со сканерами безопасности (Trivy, Checkov).

## Ключевые функции и настройки

### Server-side Apply (SSA)
Использование Server-side Apply (стандарт в v3.x) позволяет Argo CD корректно обрабатывать огромные манифесты и сосуществовать с другими контроллерами (например, HPA), которые изменяют те же ресурсы.

### Использование масок (Glob patterns)
Начиная с версии v3.4, Argo CD поддерживает маски в поле `valueFiles`. Это позволяет автоматически подхватывать новые файлы конфигураций без изменения объекта `Application`.

```yaml
helm:
  valueFiles:
    - values.yaml
    - env/values-*.yaml
```

### Проверка схем данных
Если Helm-чарт содержит файл `values.schema.json`, Argo CD автоматически валидирует вводимые параметры. Это предотвращает применение некорректных конфигураций еще на этапе рендеринга.

## Практические сценарии

### Сценарий 1: Развёртывание из Helm-репозитория через CLI

```bash
argocd app create redis \
  --helm-chart redis \
  --repo https://charts.bitnami.com/bitnami \
  --revision 16.8.9 \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace redis \
  --helm-set replica.replicaCount=2 \
  --sync-policy automated
```

### Сценарий 2: Применение разных конфигураций для окружений

В Git-репозитории создаются файлы `values-dev.yaml`, `values-prod.yaml`. В манифестах `Application` указывается путь к конкретному файлу или используется механизм `ApplicationSet` для массовой генерации приложений.

### Сценарий 3: Комбинирование чартов (Паттерн App of Apps)

Использование одного «головного» приложения для управления группой других приложений. Каждый дочерний элемент может быть отдельным Helm-чартом со своими настройками.

## Дополнительная информация

### Сравнение подходов

| Критерий | Нативный Helm | Несколько источников | Генерация (CI) |
| :--- | :--- | :--- | :--- |
| **Сложность** | Низкая | Средняя | Высокая |
| **GitOps-чистота** | Низкая | Высокая | Максимальная |
| **Гибкость** | Ограничена | Высокая | Максимальная |

### Рекомендации

- **Фиксация версий:** Всегда указывайте конкретную версию чарта в `targetRevision`. Использование `latest` или веток запрещено для стабильных окружений.
- **Безопасность секретов:** Никогда не храните пароли в `values.yaml`. Используйте [интеграцию с Vault](./argocd_vault_integration.md) или External Secrets Operator.
- **Helm 4:** Argo CD v3.x нативно поддерживает Helm 4. Рекомендуется переход на новую версию для повышения производительности и безопасности (отказ от устаревших API).
- **Проверка в CI:** Запускайте `helm lint` перед коммитом изменений, чтобы избежать ошибок синтаксиса.
