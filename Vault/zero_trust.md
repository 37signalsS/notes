# Подход Zero Trust к управлению секретами

## Определения

**Подход Zero Trust ("нулевого доверия")** в управлении секретами — это парадигма безопасности, которая исходит из того, что в системе нет "доверенных зон" (например, внутренних сетей). Каждый запрос на доступ к секрету должен проходить строгую, многофакторную проверку подлинности и авторизации, основанную на сильной идентичности и контексте запрашивающего.

Центральным элементом этого подхода является **брокер доступа** (такой как **[HashiCorp Vault](./overview.md)**), который выдает **краткоживущие, минимально привилегированные** учетные данные по запросу.

## Основные концепции

### Принципы Zero Trust для секретов

* **Сильная идентичность:** Каждая рабочая нагрузка (приложение, сервис) должна иметь криптографически подтвержденное удостоверение (например, через OIDC/JWT, SPIFFE/SPIRE). Это реализуется через **[методы аутентификации](./concepts.md#методы-аутентификации-и-токены)** в Vault.
* **Контекстная проверка:** Решение о доступе принимается на основе контекста: `namespace`, метки `pod`-а, среда выполнения, IP-адрес источника.
* **Минимальные привилегии:** Доступ предоставляется только к необходимым путям и операциям с помощью **[политик доступа](./concepts.md#политики-доступа-policies)**.
* **Краткоживущие секреты:** Все секреты и **[токены](./concepts.md#жизненный-цикл-секрета-токены-lease-и-revoke)** имеют короткое время жизни (TTL), требуют периодического продления (`lease`) и могут быть отозваны в любой момент.
* **Защищенные каналы:** Коммуникация между клиентами и Vault защищена с помощью TLS.
* **Политики как код (Policies as Code):** Правила доступа описываются декларативно, хранятся в системе контроля версий и применяются автоматически.
* **Непрерывный аудит:** Все операции доступа к секретам протоколируются с помощью **[устройств аудита](./concepts.md#аудит-audit-devices)** для отслеживания аномалий.

### Сравнение подходов

| Аспект | Традиционный подход | Подход Zero Trust с Vault |
| :--- | :--- | :--- |
| **Хранение** | В `.env` файлах, Git, долгоживущие ключи | Динамическая выдача по запросу через брокер секретов |
| **Срок жизни** | Недели, месяцы, бессрочно | Минуты, часы; автоматическое продление и отзыв |
| **Проверка доступа** | По принадлежности к "доверенной" сети | По идентичности и контексту каждого запроса |
| **Компрометация** | Долговременный неконтролируемый доступ | Ущерб ограничен коротким TTL и узкими привилегиями |

## Практические сценарии

### Интеграция с Kubernetes

В Kubernetes рабочая нагрузка (pod) может подтвердить свою личность, используя токен своего `ServiceAccount`, который проверяется Vault.

1. **Настройка аутентификации `kubernetes` в Vault:** Vault настраивается так, чтобы доверять OIDC-провайдеру Kubernetes API.
2. **Создание роли в Vault:** Роль связывает `ServiceAccount` из определенного `namespace` с политиками Vault.

    ```hcl
    # Роль 'web' разрешает аутентификацию для ServiceAccount 'web-sa' 
    # в namespace 'prod' и привязывает политику 'web-readonly'
    vault write auth/kubernetes/role/web \
      bound_service_account_names=web-sa \
      bound_service_account_namespaces=prod \
      policies=web-readonly \
      ttl=30m
    ```

3. **Доставка секрета:** Vault Agent, запущенный как sidecar-контейнер, аутентифицируется в Vault, получает динамические учетные данные для базы данных и записывает их во временный том (`tmpfs`), доступный основному приложению.

## Дополнительная информация

* **[Sealed Secrets](../Kubernetes/Security/sealed_secrets_overview.md):** Альтернативный подход для безопасного хранения секретов в Git, который реализует часть принципов Zero Trust. Секрет шифруется для конкретного кластера и может быть расшифрован только в нем.
