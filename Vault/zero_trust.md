# Подход Zero Trust к управлению секретами

## Определения

**Подход Zero Trust ("нулевого доверия")** в управлении секретами — это парадигма безопасности, которая исходит из того, что в системе нет "доверенных зон" (например, внутренних сетей). Вместо этого каждый запрос на доступ к секрету должен проходить строгую, многофакторную проверку подлинности и авторизации, основанную на сильной идентичности и контексте запрашивающего.

## Основные концепции

Вместо долгоживущих ключей и статически распределенных конфигураций используется **брокер доступа** (такой как HashiCorp Vault), который выдает **краткоживущие, минимально привилегированные** учетные данные по мере необходимости. Такой подход снижает "радиус поражения" (blast radius) в случае компрометации, упрощает отзыв доступа и делает атаку менее результативной.

### Принципы Zero Trust для секретов

*   **Сильная идентичность:** Каждая рабочая нагрузка (приложение, сервис) должна иметь криптографически подтвержденное удостоверение (например, через OIDC/JWT, SPIFFE/SPIRE).
*   **Контекстная проверка:** Решение о доступе принимается на основе контекста: `namespace`, метки `pod`-а, среда выполнения, время, IP-адрес источника запроса.
*   **Минимальные привилегии:** Доступ предоставляется только к конкретным путям/ролям, необходимым для выполнения задачи, без использования "wildcard" (`*`).
*   **Краткоживущие секреты:** Все секреты и токены имеют короткое время жизни (TTL), требуют периодического продления (`lease`) и могут быть отозваны в любой момент.
*   **Защищенные каналы:** Коммуникация между приложением, агентом и хранилищем секретов защищена с помощью mTLS.
*   **Запрет на хранение секретов:** Секреты не должны храниться в Git-репозиториях и образах контейнеров. Предпочтение отдается динамической выдаче или шифрованию (например, `Sealed Secrets`).
*   **Политики как код (Policies as Code):** Правила доступа описываются декларативно, хранятся в системе контроля версий, проходят ревью и применяются автоматически.
*   **Непрерывный аудит:** Все операции доступа к секретам протоколируются для отслеживания аномалий и расследования инцидентов.

### Сопоставление подходов

| Аспект | Традиционный подход | Подход Zero Trust |
| :--- | :--- | :--- |
| **Хранение** | В `.env` файлах, Git, долгоживущие ключи | Брокер секретов, шифрованные манифесты, выдача по запросу |
| **Срок жизни** | Недели, месяцы, бессрочно | Минуты, часы; автопродление и отзыв |
| **Проверка доступа** | По принадлежности к "доверенной" сети/зоне | По идентичности и контексту каждого запроса |
| **Компрометация** | Долговременный неконтролируемый доступ | Ущерб ограничен коротким TTL и узкими привилегиями |

## Практические сценарии

### Интеграция с Kubernetes

В Kubernetes рабочая нагрузка (pod) может подтвердить свою личность, используя токен своего `ServiceAccount`, который проверяется Vault.

1.  **Настройка аутентификации `kubernetes` в Vault:** Vault доверяет OIDC-провайдеру Kubernetes API.
2.  **Создание роли в Vault:** Роль связывает `ServiceAccount` из определенного `namespace` с политиками Vault.

    ```bash
    # Роль 'web' разрешает аутентификацию для ServiceAccount 'web-sa' в namespace 'prod'
    vault write auth/kubernetes/role/web 
      bound_service_account_names=web-sa 
      bound_service_account_namespaces=prod 
      policies=web-readonly 
      ttl=30m
    ```
3.  **Создание политики минимальных привилегий:**

    ```hcl
    # Политика 'web-readonly'
    path "database/creds/readonly" {
      capabilities = ["read"]
    }
    ```
4.  **Доставка секрета:** Vault Agent, запущенный как sidecar-контейнер, аутентифицируется в Vault, получает динамические учетные данные для базы данных и записывает их во временный том (`tmpfs`), доступный основному приложению. Секрет не попадает в переменные окружения и не сохраняется на диске.

### Использование с Sealed Secrets

[Sealed Secrets](../Kubernetes/Security/sealed_secrets_overview.md) реализуют часть принципов Zero Trust, не доверяя системе контроля версий (Git). Секрет шифруется публичным ключом контроллера, что позволяет безопасно хранить его в репозитории. Расшифровка возможна только в целевом кластере, что разрывает связь между хранилищем кода и средой исполнения.
