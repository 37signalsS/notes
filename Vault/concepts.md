# Архитектура и основные концепции

Общее описание технологии — в [Vault Overview](overview.md).

## Определения

**Основные концепции Vault** — фундаментальные компоненты и механизмы, составляющие архитектуру и логику работы системы. Ключевые элементы: процесс Seal/Unseal, бэкенды хранения, методы аутентификации, политики, движки секретов, жизненный цикл токенов.

## Основные концепции

### Процесс запечатывания (Seal) и распечатывания (Unseal)

Это ключевой механизм безопасности Vault, который гарантирует, что даже при получении доступа к физическому хранилищу данных, злоумышленник не сможет их расшифровать.

#### Состояния Vault

Vault может находиться в одном из двух состояний:

1. **Запечатанное (Sealed):** Состояние по умолчанию при запуске. Vault знает расположение хранилища, но не может расшифровать данные. Все операции, кроме проверки статуса и распечатывания, заблокированы. Автоматически переходит в это состояние при каждом перезапуске.
2. **Распечатанное (Unsealed):** Рабочее состояние. Главный ключ (master key) загружается в оперативную память для расшифровки данных и обслуживания запросов. Ключ **никогда не хранится** в постоянном хранилище и собирается при распечатывании.

#### Как работает распечатывание: Алгоритм Шамира

При инициализации (`vault operator init`) Vault генерирует главный ключ шифрования и, вместо его сохранения, использует **алгоритм разделения секрета Шамира (Shamir's Secret Sharing)**.

1. **Разделение ключа:** Главный ключ делится на `N` частей (по умолчанию `N=5`), которые называются **ключами распечатывания (Unseal Keys)**.
2. **Пороговое значение (Threshold):** Устанавливается пороговое количество ключей `K` (по умолчанию `K=3`), необходимое для восстановления исходного главного ключа.

Для распечатывания Vault необходимо предоставить `K` **любых** из `N` сгенерированных ключей. Это лежит в основе важной операционной практики — **распределения ответственности** ("кворум"), когда ключи раздаются разным сотрудникам, и для перезапуска сервиса требуется участие нескольких человек.

#### Auto-unseal

Для упрощения эксплуатации в production-средах используется механизм **Auto-unseal**, который интегрируется с внешними доверенными сервисами (облачными KMS, аппаратными HSM) для автоматического распечатывания узлов при старте, избавляя от необходимости ручного ввода ключей.

### Бэкенды хранения (Storage Backends)

Vault делегирует хранение зашифрованных данных внешнему персистентному хранилищу, называемому **бэкендом хранения**. Vault всегда шифрует данные перед записью, поэтому бэкенд отвечает только за их физическое хранение.

Выбор бэкенда критически влияет на надежность и масштабируемость. Основные типы:

| Бэкенд | Тип | HA | Рекомендация |
| :--- | :--- | :--- | :--- |
| **Raft (встроенный)** | Локальное хранилище | ✅ | Рекомендуется для большинства сценариев, не требует внешних зависимостей |
| **Consul** | Координационная система | ✅ | Проверенное решение, рекомендуется для сложных распределённых систем |
| **Etcd** | Координационная система | ✅ | Альтернатива Consul, часто используется в Kubernetes-средах |
| **AWS S3 / GCS / Azure Blob** | Облачное хранилище | ❌ | Только для single-node, требует внешнего HA-механизма |
| **PostgreSQL / MySQL** | Реляционная БД | ⚠️ | Поддерживается, но требует дополнительной настройки для HA |
| **Filesystem (`file`)** | Локальное хранилище | ❌ | **Не для production**, только для разработки и тестирования |

**Подробная настройка Consul в качестве бэкенда:** [Использование Consul в качестве бэкенда для Vault](./guides/vault_with_consul_backend.md)

### Методы аутентификации и Токены

**Методы аутентификации** проверяют личность клиентов (людей, приложений) и выдают им **токен**. Токен — это основной объект для взаимодействия с Vault, к которому привязаны политики доступа.

Основные типы методов аутентификации:

| Для кого | Методы | Описание |
| :--- | :--- | :--- |
| **Люди** | `userpass`, `ldap`, `oidc`/`jwt`, `github`, `okta` | Аутентификация через существующие системы управления учётными данными |
| **Машины и приложения** | `approle`, `kubernetes`, `aws`, `gcp`, `azure`, `jwt` | Автоматическая аутентификация через метаданные платформы или OIDC-токены |

**Рекомендуемый метод для приложений:** [AppRole](./guides/vault_auth_approle.md) — безопасная аутентификация без долгоживущих секретов. Автоматизация — через [Vault Agent](./guides/vault_agent/basics.md).

### Политики доступа (Policies)

**Политики** — декларативные правила на языке HCL, определяющие, **что** аутентифицированный субъект может делать в Vault.

```hcl
# Разрешить чтение и листинг всех секретов в 'secret/project-alpha'
path "secret/project-alpha/*" {
  capabilities = ["read", "list"]
}
```

Основные `capabilities`:

| Capability | Описание |
| :--- | :--- |
| `create`, `read`, `update`, `delete` | CRUD-операции |
| `list` | Листинг путей |
| `sudo` | Доступ к привилегированным путям |
| `deny` | Явный запрет (наивысший приоритет) |

### Движки Секретов (Secret Engines)

**Движки секретов** — это компоненты, которые хранят, генерируют или шифруют данные. Каждый движок предоставляет свой набор путей и операций.

| Движок | Тип | Описание |
| :--- | :--- | :--- |
| **`kv` (v1/v2)** | Статические секреты | Хранилище «ключ-значение». v2: версионирование, TTL, metadata |
| **`database`** | Динамические секреты | Временные учётные данные для БД (PostgreSQL, MySQL, MongoDB) |
| **`pki`** | Динамические сертификаты | Внутренний CA для выдачи TLS-сертификатов |
| **`transit`** | Шифрование как сервис | Шифрование/дешифрование без хранения ключей у приложения |
| **`aws`/`gcp`/`azure`** | Облачные секреты | Временные IAM-учётные данные для облачных провайдеров |
| **`totp`** | Одноразовые пароли | Генерация и валидация TOTP-кодов для MFA |
| **`ssh`** | SSH-сертификаты | Управление SSH-ключами и сертификатами для доступа к серверам |

Подробнее о политиках для Transit Engine — в [политике доступа для Transit Engine](./guides/transit-encryption-policies.md).

Сравнение статической и динамической моделей:

| Критерий | KV (статические) | Динамические |
| :--- | :--- | :--- |
| Источник | Хранятся в Vault | Генерируются на лету |
| Время жизни | Без TTL | TTL/lease обязательно |
| Отзыв | Перезапись/удаление | Мгновенный revoke |
| Ротация | Ручная/автоматизация внешняя | Встроенная через роли |

### Жизненный цикл секрета: Токены, Lease и Revoke

Любой динамический секрет или токен, выданный Vault, сопровождается **lease** — договором аренды с ограниченным временем жизни (TTL). Это основа безопасности Vault, позволяющая автоматически отзывать доступ.

* **Токены**: Несут идентичность и политики. Могут быть с разным TTL, **продлеваемыми** (`renewable`), **периодическими** (`periodic`), а также `batch`-токенами для сценариев с высокой пропускной способностью.
* **Продление (`renew`)**: Клиент может запрашивать продление lease до истечения TTL, если это разрешено ролью.
* **Отзыв (`revoke`)**: Секрет или токен можно отозвать досрочно. Для динамических секретов это запускает процедуру удаления соответствующей учетной записи в целевой системе (например, пользователя в БД).

### Response Wrapping

Этот механизм повышает безопасность доставки секрета. Вместо самого секрета Vault возвращает одноразовый временный токен, который оборачивает собой итоговый секрет. Этот токен можно безопасно передать конечному получателю, который затем "развернет" его, чтобы получить доступ к данным. Это снижает риск перехвата секрета в процессе передачи.

### Аудит (Audit Devices)

Vault позволяет включить один или несколько **устройств аудита** для записи всех запросов и ответов. Аудит-логи являются неизменяемыми и содержат важную информацию для анализа безопасности и расследования инцидентов. Чувствительные поля в логах хэшируются для предотвращения утечек. Устройствами могут быть файл, сокет или syslog.

## Практические сценарии

### Инициализация и распечатывание Vault

Подробное руководство — в [установке и базовой настройке](./guides/vault_installation.md).

1. **Инициализация (один раз):**

    ```bash
    export VAULT_ADDR='http://127.0.0.1:8200'
    vault operator init
    ```

    Генерируются 5 ключей распечатывания и начальный корневой токен. **Сохранить в надёжных раздельных местах.**

2. **Проверка статуса:** `vault status` → `Sealed: true`

3. **Распечатывание:** выполнить `vault operator unseal` с разными ключами до достижения порога (по умолчанию 3):

    ```bash
    vault operator unseal <unseal_key_1>  # Progress: 1/3
    vault operator unseal <unseal_key_3>  # Progress: 2/3
    vault operator unseal <unseal_key_5>  # Sealed: false
    ```

4. **Вход:** `vault login <root_token>`

### Создание и управление политиками

Подробнее об AppRole — в [аутентификации через AppRole](./guides/vault_auth_approle.md).

#### Через CLI

1. Сохранить HCL-политику в файл, например `consul-policy.hcl`.
2. Загрузить в Vault:

    ```bash
    vault policy write consul-policy consul-policy.hcl
    ```

#### Через UI

1. Раздел `Policies` → `Create ACL policy`.
2. Ввести имя и HCL-код → `Create policy`.

После создания политика привязывается к токену или методу аутентификации (например, AppRole).
