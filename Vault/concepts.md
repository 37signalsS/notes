# Архитектура и основные концепции

Vault построен на нескольких ключевых концепциях, которые вместе обеспечивают безопасное управление секретами.

## Бэкенды хранения (Storage Backends)

Vault не хранит данные самостоятельно. Вместо этого он делегирует хранение зашифрованных данных другому персистентному хранилищу, которое называется **бэкендом хранения (Storage Backend)**.

**Важно:** Vault всегда шифрует свои данные перед записью в бэкенд хранения. Бэкенд отвечает только за надежное хранение этой зашифрованной информации и не имеет доступа к секретам в открытом виде.

Выбор бэкенда является критически важным шагом при развертывании Vault, так как он напрямую влияет на надежность, отказоустойчивость и масштабируемость системы.

### Основные типы бэкендов

Vault поддерживает множество бэкендов, которые можно разделить на несколько категорий:

1.  **Высокодоступные координационные системы:**
    *   **Consul:** Рекомендуемый выбор для production-окружений. Обеспечивает высокую доступность и распределенную блокировку.
    *   **ZooKeeper, Etcd:** Альтернативы Consul со схожими гарантиями.

2.  **Облачные хранилища:**
    *   **AWS S3, Google Cloud Storage, Azure Blob Storage:** Позволяют использовать управляемые облачные сервисы для хранения данных.

3.  **Базы данных:**
    *   **PostgreSQL, MySQL, CockroachDB:** Могут использоваться в качестве бэкенда, хотя требуют тщательной настройки для обеспечения высокой доступности.

4.  **Локальное хранилище:**
    *   **Raft (встроенный):** Начиная с версии 1.4, Vault включает встроенный бэкенд `raft`, который позволяет создавать высокодоступный кластер без внешних зависимостей. Это значительно упрощает развертывание.
    *   **Filesystem (`file`):** Хранит данные на локальной файловой системе. **Не рекомендуется для production**, так как не обеспечивает отказоустойчивости. Подходит только для разработки и тестирования.

## Secret Engine

Компоненты, которые управляют различными типами секретов. Например, `kv` (key-value), `database` (для динамических секретов БД), `pki` (для сертификатов).

## Методы аутентификации в Vault

Vault использует несколько методов для аутентификации клиентов (пользователей, приложений, систем), которые хотят получить доступ к секретам. Каждый метод аутентификации имеет свои преимущества и предназначен для различных сценариев использования.

Основная задача метода аутентификации — проверить личность клиента и выдать ему токен с привязанными политиками, которые определяют его права доступа.

### Основные типы методов аутентификации

*   **Для людей:**
    *   `userpass`: Простой метод с использованием логина и пароля.
    *   `ldap`: Интеграция с существующими LDAP-серверами.
    *   `oidc` / `jwt`: Интеграция с провайдерами идентификации через OpenID Connect или JWT.
    *   `github`: Аутентификация с использованием учетных записей GitHub.

*   **Для машин и приложений:**
    *   `AppRole`: Предпочтительный метод для автоматизированных рабочих процессов, использующий пару `RoleID` и `SecretID`.
    *   `Kubernetes`: Позволяет подам в Kubernetes аутентифицироваться с помощью своих сервисных аккаунтов.
    *   `AWS` / `GCP` / `Azure`: Интеграция с механизмами IAM облачных провайдеров.

## Политики доступа в Vault

Политики (Policies) — это декларативный способ предоставления или запрета доступа к определенным путям и операциям в Vault. Политики определяют, **что** аутентифицированный субъект (пользователь, приложение) может делать.

Политики пишутся на языке HCL (HashiCorp Configuration Language).

### Структура политики

Политика состоит из одного или нескольких правил `path`.

```hcl
path "path/to/secret/*" {
  capabilities = ["read", "list"]
}
```

*   `path "..."`: Определяет путь, к которому применяется правило. Может содержать wildcards (`*`).
*   `capabilities = [...]`: Список разрешенных операций.

#### Основные `capabilities`

*   `create`: Создание секрета по указанному пути.
*   `read`: Чтение секрета.
*   `update`: Обновление существующего секрета.
*   `delete`: Удаление секрета.
*   `list`: Получение списка секретов по указанному пути (если путь является "директорией").
*   `sudo`: Доступ к привилегированным путям.
*   `deny`: Явный запрет на доступ. Имеет наивысший приоритет.

Полный список и описание `capabilities` можно найти в [официальной документации](https://developer.hashicorp.com/vault/docs/concepts/policies#capabilities).

### Создание и управление политиками

Политики можно создавать через UI или CLI.

#### Через CLI (рекомендуемый способ)

1.  Сохраните HCL-код в файл, например, `consul-policy.hcl`.
2.  Используйте команду `vault policy write`:

    ```bash
    vault policy write consul-policy consul-policy.hcl
    ```
    Где:
    *   `consul-policy` — имя, под которым политика будет храниться в Vault.
    *   `consul-policy.hcl` — файл с кодом политики.

#### Через UI

1.  Перейдите в раздел `Policies`.
2.  Нажмите `Create ACL policy`.
3.  Введите имя политики и вставьте HCL-код в текстовое поле.
4.  Нажмите `Create policy`.

После создания политика может быть привязана к токену или методу аутентификации (например, AppRole), чтобы предоставить соответствующие права доступа.

## Процесс "запечатывания" (Seal) и "распечатывания" (Unseal)

Одной из ключевых концепций архитектуры безопасности Vault является механизм "Seal" / "Unseal". Этот механизм гарантирует, что даже если злоумышленник получит доступ к физическому хранилищу данных Vault, он не сможет их расшифровать.

### Состояния Vault

Vault может находиться в одном из двух состояний:

#### 1. Запечатанное (Sealed)
Это состояние по умолчанию при запуске сервера Vault. В этом состоянии Vault знает, где находится его хранилище данных, но не знает, как их расшифровать.

Когда Vault запечатан:
*   **Доступ к данным невозможен:** Почти все операции с секретами (чтение, запись) блокированы.
*   **Доступны только системные операции:** Можно проверить статус, выполнить распечатывание или эскалацию до `root`.

Vault автоматически переходит в состояние `Sealed` при каждом перезапуске.

#### 2. Распечатанное (Unsealed)
Чтобы Vault мог выполнять свои функции, его необходимо "распечатать". В этом состоянии Vault получает в оперативной памяти главный ключ (master key), который позволяет ему расшифровывать данные из хранилища и выполнять запросы клиентов.

Этот главный ключ **никогда не хранится в постоянном хранилище**. Он собирается "на лету" в момент распечатывания.

### Как работает распечатывание: Алгоритм Шамира

При инициализации (`vault operator init`) Vault генерирует главный ключ шифрования. Затем, вместо того чтобы сохранить этот ключ где-либо, Vault использует **алгоритм разделения секрета Шамира (Shamir's Secret Sharing)**.

1.  **Разделение ключа:** Главный ключ делится на `N` частей (по умолчанию `N=5`), которые называются **ключами распечатывания (Unseal Keys)**.
2.  **Пороговое значение (Threshold):** Устанавливается пороговое количество ключей `K` (по умолчанию `K=3`), необходимое для восстановления исходного главного ключа.

Это означает, что для распечатывания Vault необходимо предоставить `K` **любых** из `N` сгенерированных ключей. Даже если злоумышленник получит доступ к одному или двум ключам, он не сможет восстановить главный ключ и получить доступ к данным.

#### Операционная безопасность
Этот механизм лежит в основе важной операционной практики:
*   **Распределение ответственности:** `N` ключей распечатывания раздаются разным ответственным сотрудникам (например, системным администраторам, DevOps-инженерам, офицерам безопасности).
*   **Кворум для распечатывания:** Для перезапуска и распечатывания Vault требуется участие нескольких человек ("кворум"). Это предотвращает несанкционированные действия со стороны одного сотрудника.

### Процесс в командах

1.  **Инициализация (выполняется один раз):**
    ```bash
    export VAULT_ADDR='http://127.0.0.1:8200'
    vault operator init
    ```
    В результате будут сгенерированы 5 ключей распечатывания (`Unseal Key 1`...`5`) и начальный корневой токен (`Initial Root Token`). **Их необходимо сохранить в нескольких надежных и раздельных местах.**

2.  **Проверка статуса:**
    ```bash
    vault status
    ```
    ```
    Key             Value
    ---             -----
    Sealed          true  # Vault запечатан
    Total Shares    5
    Threshold       3
    ...
    ```

3.  **Распечатывание:**
    Нужно последовательно выполнить команду `vault operator unseal` с разными ключами, пока не будет достигнуто пороговое значение.
    ```bash
    vault operator unseal <unseal_key_1>
    # Progress: 1/3
    vault operator unseal <unseal_key_3>
    # Progress: 2/3
    vault operator unseal <unseal_key_5>
    # Progress: 3/3. Sealed: false
    ```

4.  **Финальный статус:**
    ```bash
    vault status
    ```
    ```
    Key             Value
    ---             -----
    Sealed          false # Vault распечатан и готов к работе
    ...
    ```
После этого можно входить в систему с помощью токена (`vault login <root_token>`) и работать с секретами.

## Токены (Tokens)

Основной механизм для аутентификации в Vault. После успешной аутентификации клиент получает токен с привязанными к нему политиками.
