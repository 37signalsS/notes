# Архитектура и основные концепции

Общее описание технологии и ее роли в системе управления секретами доступно в основной заметке [Vault Overview](overview.md).

## 1. Определения

**Основные концепции Vault** — это фундаментальные компоненты и механизмы, составляющие архитектуру и логику работы системы. Понимание этих концепций необходимо для правильного развертывания, использования и обеспечения безопасности Vault. Ключевыми из них являются процесс "Seal/Unseal", бэкенды хранения, методы аутентификации, политики и движки секретов.

## 2. Основные концепции

### Процесс "запечатывания" (Seal) и "распечатывания" (Unseal)

Это ключевой механизм безопасности Vault, который гарантирует, что даже при получении доступа к физическому хранилищу данных, злоумышленник не сможет их расшифровать.

#### Состояния Vault

Vault может находиться в одном из двух состояний:

1. **Запечатанное (Sealed):** Состояние по умолчанию при запуске. Vault знает, где находится его хранилище, но не знает, как расшифровать данные. Почти все операции, кроме проверки статуса и распечатывания, заблокированы. Vault автоматически переходит в это состояние при каждом перезапуске.
2. **Распечатанное (Unsealed):** Рабочее состояние. Vault получает в оперативной памяти главный ключ (master key), который позволяет ему расшифровывать данные и обслуживать запросы клиентов. Этот ключ **никогда не хранится** в постоянном хранилище и собирается "на лету" в момент распечатывания.

#### Как работает распечатывание: Алгоритм Шамира

При инициализации (`vault operator init`) Vault генерирует главный ключ шифрования и, вместо его сохранения, использует **алгоритм разделения секрета Шамира (Shamir's Secret Sharing)**.

1. **Разделение ключа:** Главный ключ делится на `N` частей (по умолчанию `N=5`), которые называются **ключами распечатывания (Unseal Keys)**.
2. **Пороговое значение (Threshold):** Устанавливается пороговое количество ключей `K` (по умолчанию `K=3`), необходимое для восстановления исходного главного ключа.

Для распечатывания Vault необходимо предоставить `K` **любых** из `N` сгенерированных ключей. Это лежит в основе важной операционной практики — **распределения ответственности** ("кворум"), когда ключи раздаются разным сотрудникам, и для перезапуска сервиса требуется участие нескольких человек.

#### Auto-unseal

Для упрощения эксплуатации в production-средах используется механизм **Auto-unseal**, который интегрируется с внешними доверенными сервисами (облачными KMS, аппаратными HSM) для автоматического распечатывания узлов при старте, избавляя от необходимости ручного ввода ключей.

### Бэкенды хранения (Storage Backends)

Vault делегирует хранение зашифрованных данных внешнему персистентному хранилищу, называемому **бэкендом хранения**. Vault всегда шифрует данные перед записью, поэтому бэкенд отвечает только за их физическое хранение.

Выбор бэкенда критически влияет на надежность и масштабируемость. Основные типы:

1. **Высокодоступные координационные системы:** **[Consul](../Consul/consul_overview.md)** (рекомендуемый), ZooKeeper, **[Etcd](../Kubernetes/Concepts/control_plane_architecture.md)**.
2. **Облачные хранилища:** AWS S3, Google Cloud Storage, Azure Blob Storage.
3. **Базы данных:** **[PostgreSQL](../Databases/PostgreSQL/overview.md)**, **[MySQL](../Databases/MySQL/overview.md)**.
4. **Локальное хранилище:**
    * **Raft (встроенный):** Позволяет создавать высокодоступный кластер Vault без внешних зависимостей. Рекомендуется для упрощения развертывания.
    * **Filesystem (`file`):** Хранит данные в локальной файловой системе. **Не для production**, подходит только для разработки.

### Методы аутентификации и Токены

**Методы аутентификации** проверяют личность клиентов (людей, приложений) и выдают им **токен**. Токен — это основной объект для взаимодействия с Vault, к которому привязаны политики доступа.

Основные типы методов аутентификации:

* **Для людей:** `userpass`, [LDAP (Lightweight Directory Access Protocol)](../Linux/SystemAdministration/users_management.md#LDAP-Lightweight-Directory-Access-Protocol), `oidc`/`jwt`, `github`.
* **Для машин и приложений:** **[`AppRole`](../guides/vault_auth_approle.md)** (предпочтительный), `Kubernetes`, `AWS`/`GCP`/`Azure`.

### Политики доступа (Policies)

**Политики** — это декларативные правила, написанные на языке HCL, которые определяют, **что** аутентифицированный субъект может делать в Vault.

```hcl
# Пример: разрешить чтение и листинг всех секретов в 'secret/project-alpha'
path "secret/project-alpha/*" {
  capabilities = ["read", "list"]
}
```

Основные `capabilities`:

* `create`, `read`, `update`, `delete`: CRUD-операции.
* `list`: Листинг "директорий" с секретами.
* `sudo`: Доступ к привилегированным путям.
* `deny`: Явный запрет (имеет наивысший приоритет).

### Движки Секретов (Secret Engines)

**Движки секретов** — это компоненты, которые хранят, генерируют или шифруют данные. Каждый движок предоставляет свой набор путей и операций. Примеры:

* `kv`: Простое хранилище "ключ-значение".
* `database`: Динамически генерирует учетные данные для баз данных с ограниченным сроком жизни.
* `pki`: Может выступать в роли центра сертификации (CA) для генерации и управления сертификатами.
* `transit`: Предоставляет шифрование как сервис (encryption-as-a-service), не сохраняя сами данные.

Сравнение статической и динамической моделей:

| Критерий | KV (статические) | Динамические |
| :--- | :--- | :--- |
| Источник | Хранятся в Vault | Генерируются на лету |
| Время жизни | Без TTL | TTL/lease обязательно |
| Отзыв | Перезапись/удаление | Мгновенный revoke |
| Ротация | Ручная/автоматизация внешняя | Встроенная через роли |

### Жизненный цикл секрета: Токены, Lease и Revoke

Любой динамический секрет или токен, выданный Vault, сопровождается **lease** — договором аренды с ограниченным временем жизни (TTL). Это основа безопасности Vault, позволяющая автоматически отзывать доступ.

* **Токены**: Несут идентичность и политики. Могут быть с разным TTL, **продлеваемыми** (`renewable`), **периодическими** (`periodic`), а также `batch`-токенами для сценариев с высокой пропускной способностью.
* **Продление (`renew`)**: Клиент может запрашивать продление lease до истечения TTL, если это разрешено ролью.
* **Отзыв (`revoke`)**: Секрет или токен можно отозвать досрочно. Для динамических секретов это запускает процедуру удаления соответствующей учетной записи в целевой системе (например, пользователя в БД).

### Response Wrapping

Этот механизм повышает безопасность доставки секрета. Вместо самого секрета Vault возвращает одноразовый временный токен, который оборачивает собой итоговый секрет. Этот токен можно безопасно передать конечному получателю, который затем "развернет" его, чтобы получить доступ к данным. Это снижает риск перехвата секрета в процессе передачи.

### Аудит (Audit Devices)

Vault позволяет включить один или несколько **устройств аудита** для записи всех запросов и ответов. Аудит-логи являются неизменяемыми и содержат важную информацию для анализа безопасности и расследования инцидентов. Чувствительные поля в логах хэшируются для предотвращения утечек. Устройствами могут быть файл, сокет или syslog.

## 3. Практические сценарии

### Инициализация и распечатывание Vault

1. **Инициализация (выполняется один раз):**

    ```bash
    export VAULT_ADDR='http://127.0.0.1:8200'
    vault operator init
    ```

    В результате будут сгенерированы 5 ключей распечатывания и начальный корневой токен. **Их необходимо сохранить в нескольких надежных и раздельных местах.**

2. **Проверка статуса:**

    ```bash
    vault status
    # Вывод покажет 'Sealed: true'
    ```

3. **Распечатывание:**
    Последовательно выполните команду `vault operator unseal` с разными ключами до достижения порогового значения (по умолчанию 3).

    ```bash
    vault operator unseal <unseal_key_1>
    # Progress: 1/3
    vault operator unseal <unseal_key_3>
    # Progress: 2/3
    vault operator unseal <unseal_key_5>
    # Progress: 3/3. Sealed: false
    ```

4. **Вход в систему:**
    После распечатывания можно войти с помощью корневого токена.

    ```bash
    vault login <root_token>
    ```

### Создание и управление политиками

Политики можно создавать через CLI (рекомендуется) или UI.

#### Через CLI

1. Сохраните HCL-код политики в файл, например, `consul-policy.hcl`.
2. Загрузите политику в Vault командой `vault policy write`:

    ```bash
    vault policy write consul-policy consul-policy.hcl
    ```

    * `consul-policy`: Имя, под которым политика будет храниться в Vault.
    * `consul-policy.hcl`: Файл с кодом политики.

#### Через UI

1. Перейдите в раздел `Policies`.
2. Нажмите `Create ACL policy`.
3. Введите имя политики и вставьте HCL-код в текстовое поле.
4. Нажмите `Create policy`.

После создания политика привязывается к токену или методу аутентификации (например, AppRole) для предоставления прав.
