# Авторизация в HashiCorp Vault

В Vault аутентификация отвечает за проверку личности (кто вы), а **авторизация** — за управление доступом (что вам разрешено делать). Основным механизмом авторизации являются политики.

## Определения

**Авторизация (Authorization)** — процесс проверки прав доступа аутентифицированного субъекта (Entity) к конкретным путям и операциям в Vault.

**Политика (Policy)** — декларативный набор правил, написанный на языке HCL, который определяет разрешенные возможности (capabilities) для путей в API Vault.

## Основные механизмы

### 1. ACL-политики (Access Control Lists)

Это базовый и наиболее распространенный механизм авторизации, доступный во всех версиях Vault (Open Source и Enterprise).

* **Модель:** Deny-by-default (запрещено всё, что явно не разрешено).
* **Синтаксис:** HCL (HashiCorp Configuration Language).
* **Привязка:** Политики привязываются к токенам или ролям в методах аутентификации.

#### Возможности (Capabilities)

Для каждого пути можно указать одну или несколько возможностей:

| Capability | Описание |
| :--- | :--- |
| `create` | Создание данных по пути |
| `read` | Чтение данных |
| `update` | Изменение существующих данных |
| `delete` | Удаление данных |
| `list` | Просмотр списка ключей в директории |
| `sudo` | Доступ к защищенным путям (например, настройка системных бэкендов) |
| `deny` | Явный запрет доступа (приоритет над всеми остальными правилами) |

#### Пример политики

```hcl
# Разрешить чтение секретов в приложении app1
path "secret/data/app1/*" {
  capabilities = ["read", "list"]
}

# Разрешить полный доступ к своим собственным данным в KV
path "secret/data/users/{{identity.entity.name}}/*" {
  capabilities = ["create", "read", "update", "delete", "list"]
}

# Запретить доступ к конфиденциальным настройкам
path "secret/data/app1/config/admin" {
  capabilities = ["deny"]
}
```

### 2. Sentinel (Policy as Code) — Enterprise

**Sentinel** — это более продвинутый фреймворк для реализации логики управления доступом. Он позволяет создавать правила, которые выходят за рамки простых путей и возможностей.

* **Логические условия:** Использование циклов, регулярных выражений и сложных условий.
* **Контекстная осведомленность:** Проверка времени запроса, IP-адреса клиента, использование MFA или конкретных параметров API.
* **Типы политик:**
  * **EGP (Endpoint Governing Policies):** Применяются к конкретным путям для всех пользователей.
  * **RGP (Role Governing Policies):** Применяются к конкретным токенам или сущностям.

### 3. Control Groups (Группы контроля) — Enterprise

Механизм, реализующий принцип "четырех глаз" (dual authorization) для критически важных операций.

* **Принцип:** Вместо немедленного выполнения действия, Vault требует одобрения от одного или нескольких авторизованных лиц.
* **Рабочий процесс:** Пользователь инициирует запрос → Vault возвращает wrapping-токен → Одобряющие лица подтверждают запрос → Пользователь "разворачивает" токен и получает результат.

### 4. Ограничения на уровне токенов и методов

Дополнительные механизмы авторизации могут быть настроены при выдаче токена:

* **CIDR Restrictions:** Ограничение IP-адресов, с которых может использоваться токен.
* **Token Bound Claims:** (например, в Kubernetes или JWT auth) проверка соответствия атрибутов внешней системы (namespace, service account) заданным правилам.

## Иерархия и приоритеты

1. **Deny:** Если хотя бы одна политика, привязанная к токену, содержит `deny` для данного пути, доступ будет запрещен, независимо от других разрешений.
2. **Sudo:** Требуется для операций, помеченных в API как защищенные.
3. **Наиболее специфичный путь:** Vault ищет наиболее точное совпадение пути в политиках.
4. **Слияние политик:** Если к токену привязано несколько политик, их возможности суммируются (за исключением `deny`).

## Практические рекомендации

* **Принцип наименьших привилегий (Least Privilege):** Выдавайте только те права, которые необходимы приложению или пользователю.
* **Использование шаблонов (Templating):** Используйте переменные типа `{{identity.entity.name}}` для создания универсальных политик.
* **Разделение обязанностей:** Создавайте отдельные политики для администраторов (управление движками, методами аутентификации) и потребителей (чтение/запись секретов).
* **Проверка политик:** Используйте команду `vault token capabilities` для проверки того, какие права имеет текущий токен на конкретный путь.
