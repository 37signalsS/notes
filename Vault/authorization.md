# Авторизация в HashiCorp Vault

В архитектуре Vault аутентификация отвечает за проверку личности (кто вы), а **авторизация** — за управление доступом (что вам разрешено делать). Основным механизмом авторизации являются политики, которые определяют права доступа к путям API.

## Определения

**Авторизация (Authorization)** — процесс проверки прав доступа аутентифицированного субъекта (Entity) к конкретным путям, операциям и ресурсам в Vault.

**Политика (Policy)** — декларативный набор правил на языке HCL (HashiCorp Configuration Language), определяющий разрешенные возможности (capabilities) для путей в API Vault. Политики реализуют принцип наименьших привилегий и модель управления жизненным циклом безопасности (SLM).

**ACL (Access Control List)** — список контроля доступа, базовая форма политик в Vault, сопоставляющая пути API с разрешенными действиями.

**Capabilities (Возможности)** — набор атомарных операций (create, read, update, patch, delete, list, sudo, deny), которые могут быть разрешены или запрещены для конкретного пути.

## Основные механизмы

### 1. ACL-политики и возможности

ACL-политики являются основным инструментом управления доступом. Они работают по принципу **Deny-by-default**: любой доступ, который явно не разрешен, считается запрещенным.

#### Набор возможностей (Capabilities)

| Возможность | Описание | Применение |
| :--- | :--- | :--- |
| `create` | Создание новых данных по пути. | Запись нового секрета. |
| `read` | Чтение данных. | Получение значения секрета. |
| `update` | Изменение существующих данных. | Перезапись секрета целиком. |
| `patch` | Частичное обновление (Vault 1.13+). | Изменение отдельных полей в KV v2 без чтения всего секрета. |
| `delete` | Удаление данных. | Удаление версии или ключа. |
| `list` | Просмотр списка ключей. | Навигация по иерархии секретов. |
| `sudo` | Доступ к защищенным путям. | Системные настройки, управление движками. |
| `deny` | Явный запрет. | Имеет высший приоритет над любыми разрешениями. |

#### Глобальные и системные политики

*   **`default`:** Автоматически привязывается к каждому токену. Содержит базовые права (например, доступ к собственным токенам субъекта).
*   **`root`:** Обладает неограниченным доступом. Не может быть изменена или удалена. Использование root-токенов в продуктивных средах является критическим нарушением безопасности.

### 2. Шаблонизация политик (Policy Templating)

Vault позволяет создавать универсальные политики, используя переменные Identity Store. Это избавляет от необходимости создавать отдельную политику для каждого пользователя.

**Пример шаблона:**
```hcl
# Доступ к персональному хранилищу на основе имени сущности
path "secret/data/users/{{identity.entity.name}}/*" {
  capabilities = ["create", "read", "update", "patch", "delete", "list"]
}

# Доступ на основе метаданных группы
path "secret/data/teams/{{identity.entity.metadata.team}}/*" {
  capabilities = ["read", "list"]
}
```

### 3. Sentinel и продвинутая авторизация (Enterprise)

Для сложных сценариев комплаенса используются механизмы "Policy as Code":

*   **Sentinel:** Позволяет проверять контекст запроса (время суток, IP-адрес, использование MFA, параметры API).
*   **Endpoint Governing Policies (EGP):** Применяются ко всему эндпоинту, независимо от токена.
*   **Role Governing Policies (RGP):** Применяются к конкретным токенам или ролям.

### 4. Визуальный генератор политик (Visual Policy Generator)

Начиная с версий 2.0+, Vault предоставляет графический интерфейс для создания политик. Он позволяет выбирать пути и действия в UI, автоматически генерируя корректный HCL-код, что снижает риск синтаксических ошибок и упрощает онбординг команд.

## Иерархия и приоритеты

При расчете итоговых прав (effective capabilities) для субъекта Vault следует алгоритму:

1.  **Deny:** Если хотя бы одна политика содержит `deny` для данного пути, доступ запрещен.
2.  **Наиболее специфичный путь:** Vault ищет правило с самым длинным совпадением префикса пути. Правило для `secret/data/app1/config` приоритетнее, чем для `secret/data/app1/*`.
3.  **Слияние (Merge):** Если для одного и того же пути определено несколько политик, их возможности суммируются (кроме `deny`).
4.  **Параметры пути:** Кроме возможностей, можно ограничивать TTL токенов (`min_wrapping_ttl`, `max_wrapping_ttl`) и разрешенные параметры запроса (`allowed_parameters`, `denied_parameters`).

## Практические сценарии

### Настройка политики для приложения с KV v2

Сценарий: приложению нужно обновлять только пароль базы данных в JSON-секрете, не имея прав на изменение других параметров.

```hcl
# Разрешить чтение и частичное обновление (patch)
path "secret/data/production/db-creds" {
  capabilities = ["read", "patch"]
  allowed_parameters = {
    "password" = []
  }
}
```

### Управление политиками через CLI

1.  **Создание/Обновление:**
    ```bash
    vault policy write my-app-policy my-app-policy.hcl
    ```
2.  **Проверка прав текущего токена:**
    ```bash
    vault token capabilities secret/data/app1/config
    ```
3.  **Просмотр списка политик:**
    ```bash
    vault policy list
    ```

### Использование Групп контроля (Control Groups)

Для критических операций (например, экспорт ключей шифрования) настраивается политика, требующая одобрения администратора. При попытке выполнения такой операции Vault возвращает `wrapping_token`, который должен быть одобрен через API `sys/control-group/authorize`.
