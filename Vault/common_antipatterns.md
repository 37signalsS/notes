# Антипаттерны управления секретами

## Определения

**Антипаттерн управления секретами** — это распространенная, но неэффективная или опасная практика обработки конфиденциальных данных (паролей, ключей, токенов). В современной парадигме управления жизненным циклом безопасности (SLM) антипаттерном считается любое статическое хранение секрета, который может быть заменен динамической выдачей или федерацией идентичности.

**Радиус поражения (Blast Radius)** — объем ресурсов и данных, к которым злоумышленник получает доступ при компрометации одного секрета. Главная цель борьбы с антипаттернами — минимизация этого радиуса.

**Секрет Зеро (Secret Zero)** — антипаттерн, при котором для получения доступа к хранилищу секретов используется другой статический секрет (например, токен в конфигурационном файле), создавая бесконечную цепочку доверия.

## Основные концепции

Современное управление секретами (2024–2025) перешло от модели «надежного хранилища» к модели **«приоритета идентичности»**. Ключевая проблема большинства антипаттернов — статичность данных и избыточность прав.

### Принципы предотвращения антипаттернов

1.  **Исключение Secret Zero:** Использование [федерации идентичности (WIF)](./zero_trust.md#федерация-идентичности-wif-для-облачных-нагрузок) вместо статических токенов аутентификации.
2.  **Динамическая генерация (Just-in-Time):** Секреты должны создаваться в момент запроса и иметь минимальный срок жизни (TTL < 1 часа).
3.  **Непрерывное обнаружение (Continuous Discovery):** Использование инструментов класса **Vault Radar** для поиска секретов не только в Git, но и в Slack, Jira, S3-бакетах и логах.
4.  **Изоляция сред выполнения ИИ (AI Agent Security):** Защита от семантических атак (Prompt Injection), предотвращающая выгрузку секретов из контекста ИИ-агентов.

## Практические сценарии

### 1. Распространение секретов (Secret Sprawl)

Секреты попадают в системы контроля версий, вики-страницы, мессенджеры и логи.

*   **Риск:** Бессрочная утечка данных. Даже удаление коммита в Git оставляет данные в истории и кэше.
*   **Решение:**
    *   **Vault Radar:** Потоковое сканирование всей инфраструктуры (не только кода) на наличие активных секретов.
    *   **Pre-commit хуки:** Блокировка коммита при обнаружении паттернов секретов локально.
    *   **Мгновенная ротация:** Если секрет попал в Git, он считается скомпрометированным и должен быть немедленно отозван через Vault.

### 2. Использование Secret Zero

Приложение хранит статический токен Vault в файле или переменной окружения, чтобы пройти аутентификацию.

*   **Риск:** Компрометация одного токена дает доступ ко всем секретам приложения.
*   **Решение:**
    *   **Kubernetes Auth:** Использование JWT-токенов сервисных аккаунтов.
    *   **Cloud Auth (AWS/GCP/Azure):** Использование метаданных экземпляра и OIDC для подтверждения личности.
    *   **Workload Identity Federation (WIF):** Прямой обмен доверием между Vault и платформой исполнения.

### 3. Передача секретов ИИ-агентам (Prompt Injection)

Передача API-ключей напрямую в переменные окружения ИИ-агента или в системный промпт.

*   **Риск:** Злоумышленник может через текстовый запрос заставить ИИ вывести значение переменных окружения (семантическая атака).
*   **Решение:**
    *   **Injection Layer:** Использование SDK или прокси-сервиса, который внедряет секрет только в момент вызова конкретного инструмента (Tool Call), не раскрывая его основному контексту ИИ.
    *   **Краткоживущие токены:** Выдача токена на одну операцию.

### 4. Секреты в слоях образов и переменных окружения

Хранение паролей в `Dockerfile` или использование `ENV` в Kubernetes.

*   **Риск:** Секреты видны через `docker history`, `kubectl describe pod` или `/proc/1/environ`.
*   **Решение:**
    *   **BuildKit Secrets:** `RUN --mount=type=secret` для сборки.
    *   **Vault Secrets Operator (VSO):** Нативное монтирование секретов в память пода (`tmpfs`) без создания объектов `Secret` в Kubernetes.
    *   **Vault Agent Sidecar:** Рендеринг секретов в файлы внутри эфемерных томов.

### 5. Статическая синхронизация секретов

Автоматическое копирование статических паролей из Vault в AWS Secrets Manager или другие облачные хранилища.

*   **Риск:** Создание дубликатов долгоживущих секретов, что усложняет аудит и ротацию.
*   **Решение:** Прямое использование динамических движков Vault или механизмов [Secrets Sync](./overview.md#ключевые-преимущества) только для тех систем, которые не поддерживают нативную интеграцию.

#### Миграция на безопасную модель (WIF + VSO)

1.  **Анализ Идентичности:** Определить, какую платформенную идентичность (OIDC, K8s SA) использует приложение.
2.  **Настройка доверия:** Настроить метод аутентификации в Vault (например, `auth/kubernetes`).
3.  **Внедрение VSO:** Установить Vault Secrets Operator в кластер.
4.  **Создание ресурсов:** Описать `VaultAuth` и `VaultStaticSecret`/`VaultDynamicSecret` в YAML. Секреты будут автоматически монтироваться как файлы.
5.  **Удаление статики:** Удалить переменные окружения и статические файлы конфигурации после подтверждения успешного перехода.

## Дополнительная информация

### Сравнение рисков и стратегий защиты (2025)

| Антипаттерн | Уровень риска | Современное решение | Инструментарий |
| :--- | :--- | :--- | :--- |
| **Секреты в Git** | Критический | Vault Radar + Pre-commit | Gitleaks, Radar |
| **Secret Zero** | Высокий | Workload Identity Federation | OIDC, K8s Auth |
| **AI Passthrough** | Средний | Credential Injection Layer | Custom SDK, Tool Proxies |
| **ENV переменные** | Средний | Монтирование в tmpfs / VSO | Vault Secrets Operator |
| **IaC State (открытый)** | Высокий | Remote State Encryption | Terraform Cloud, S3+KMS |
| **Синхронизация статики** | Низкий | Динамические секреты (JIT) | Database Engine |
