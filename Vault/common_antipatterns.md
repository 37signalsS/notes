# Антипаттерны управления секретами

## Определения

**Антипаттерн управления секретами** — это распространённая, но неэффективная или опасная практика обработки конфиденциальных данных (паролей, ключей, токенов). В современной парадигме управления жизненным циклом секретов (SLM — Secret Lifecycle Management) антипаттерном считается любое статическое хранение секрета, который может быть заменен динамической выдачей или федерацией идентичности.

**Радиус поражения (Blast Radius)** — объем ресурсов и данных, к которым злоумышленник получает доступ при компрометации одного секрета. Главная цель борьбы с антипаттернами — минимизация этого радиуса.

**Секрет Зеро (Secret Zero)** — антипаттерн, при котором для получения доступа к хранилищу секретов используется другой статический секрет (например, токен в конфигурационном файле), создавая бесконечную цепочку доверия.

## Основные концепции

Современное управление секретами (2025–2026) перешло от модели «надёжного хранилища» к модели **«приоритета идентичности»**. Ключевая проблема большинства антипаттернов — статичность данных и избыточность прав. Облачные и Kubernetes-инструменты (Vault Radar, Vault Secrets Operator, Secrets Sync) позволяют устранить статические секреты как класс: генерировать их динамически и раздавать по федерации идентичности.

### Принципы предотвращения антипаттернов

1.  **Исключение Secret Zero:** Использование [федерации идентичности (WIF)](./zero_trust.md#федерация-идентичности-wif-для-облачных-нагрузок) вместо статических токенов аутентификации.
2.  **Динамическая генерация (Just-in-Time):** Секреты должны создаваться в момент запроса и иметь минимальный срок жизни (TTL < 1 часа).
3.  **Непрерывное обнаружение (Continuous Discovery):** Использование инструментов класса **Vault Radar** для поиска секретов не только в Git, но и в Slack, Jira, Confluence, S3-бакетах и логах. Радар находит активные (валидные) секреты и умеет импортировать их в Vault для дальнейшей ротации.
4.  **Изоляция сред выполнения ИИ (AI Agent Security):** Защита от семантических атак (Prompt Injection), предотвращающая выгрузку секретов из контекста ИИ-агентов.

## Практические сценарии

### 1. Распространение секретов (Secret Sprawl)

Секреты попадают в системы контроля версий, вики-страницы, мессенджеры и логи.

*   **Риск:** Бессрочная утечка данных. Даже удаление коммита в Git оставляет данные в истории и кэшах всех, кто клонировал репозиторий. Секреты, обнаруженные в коде, статистически живут в среднем **неделю**, и этого времени достаточно для автоматизированной компрометации аккаунтов.
*   **Решение:**
    *   **Vault Radar (GA, 2025):** Потоковое сканирование всей инфраструктуры (Git, GitHub, GitLab, Slack, Jira, Confluence, S3, Terraform) на наличие активных секретов с приоритизацией по критичности (валидность, наличие в истории, связь с Vault).
    *   **Vault Import:** Автоматический импорт найденных радаром секретов в Vault с последующей ротацией — замкнутый контур «обнаружение → изоляция → ротация».
    *   **Pre-commit хуки (Gitleaks, TruffleHog):** Локальная блокировка коммита при обнаружении паттернов секретов ещё до push.

    ```bash
    # Пример: Gitleaks — блокировка коммита при обнаружении секрета
    gitleaks protect --staged --redact
    # → 1 leaks detected. Commit blocked.
    ```

    *   **Мгновенная ротация:** Если секрет попал в Git, он сразу считается скомпрометированным и должен быть немедленно отозван через Vault (ротация пароля, отзыв токена, revocation). Нельзя полагаться только на удаление файла или коммита.

### 2. Использование Secret Zero

Приложение хранит статический токен Vault в файле или переменной окружения, чтобы пройти аутентификацию.

*   **Риск:** Компрометация одного токена дает доступ ко всем секретам приложения.
*   **Решение:**
    *   **Kubernetes Auth:** Использование JWT-токенов сервисных аккаунтов.
    *   **Cloud Auth (AWS/GCP/Azure):** Использование метаданных экземпляра и OIDC для подтверждения личности.
    *   **Workload Identity Federation (WIF):** Прямой обмен доверием между Vault и платформой исполнения.

### 3. Передача секретов ИИ-агентам (Prompt Injection)

Передача API-ключей напрямую в переменные окружения ИИ-агента или в системный промпт.

*   **Риск:** Злоумышленник может через текстовый запрос заставить ИИ вывести значение переменных окружения (семантическая атака).
*   **Решение:**
    *   **Injection Layer:** Использование SDK или прокси-сервиса, который внедряет секрет только в момент вызова конкретного инструмента (Tool Call), не раскрывая его основному контексту ИИ.
    *   **Краткоживущие токены:** Выдача токена на одну операцию.

### 4. Секреты в слоях образов и переменных окружения

Хранение паролей в `Dockerfile` или использование `ENV` в Kubernetes.

*   **Риск:** Секреты видны через `docker history`, `kubectl describe pod` или `/proc/1/environ`. Во время сборки секреты попадают в слои образа; в рантайме — в конфигурацию пода и окружение процессов.
*   **Решение:**
    *   **BuildKit Secrets:** `RUN --mount=type=secret` для сборки — секрет не остаётся в слоях образа.
    *   **Vault Secrets Operator (VSO):** Синхронизация секретов из Vault в нативные Kubernetes `Secret` (`volumeMounts`/`envFrom`). Подходит для приложений, которые уже умеют читать `Secret`.
    *   **Secrets Store CSI Driver + Vault Provider:** Монтирование секретов в том пода (`tmpfs`, в памяти) без создания объектов `Secret`, с опциональной ротацией базового ключа.
    *   **Vault Agent Sidecar:** Рендеринг секретов в файлы внутри эфемерных томов.
    *   Подробные примеры и сравнение YAML-манифестов: **[Интеграция Vault с Kubernetes](./guides/vault_kubernetes_integration.md)**.

### 5. Статическая синхронизация секретов

Автоматическое копирование статических паролей из Vault в AWS Secrets Manager, Google Cloud Secret Manager или другие облачные хранилища.

*   **Риск:** Создание дубликатов долгоживущих секретов, что усложняет аудит и ротацию.
*   **Решение:** Прямое использование динамических движков Vault или механизмов [Secrets Sync](./overview.md#ключевые-преимущества) только для тех систем, которые не поддерживают нативную интеграцию. Secrets Sync поддерживает hub-and-spoke модель репликации в AWS/GCP/Azure, GitHub Actions и Vercel; работает при передаче данных из Vault без ручного копирования.

#### Миграция на безопасную модель (WIF + VSO)

1.  **Анализ Идентичности:** Определить, какую платформенную идентичность (OIDC, K8s SA) использует приложение.
2.  **Настройка доверия:** Настроить метод аутентификации в Vault (например, `auth/kubernetes`).
3.  **Внедрение VSO:** Установить Vault Secrets Operator в кластер.
4.  **Создание ресурсов:** Описать `VaultAuth` и `VaultStaticSecret`/`VaultDynamicSecret` в YAML. Секреты будут автоматически монтироваться как файлы.
5.  **Удаление статики:** Удалить переменные окружения и статические файлы конфигурации после подтверждения успешного перехода.

### 6. Логирование чувствительных данных

Вывод паролей, токенов, заголовков `Authorization` и полей конфигурации в `stdout`/`stderr` (включая отладочный режим).

*   **Риск:** Секреты попадают в системы сбора логов (ELK, Loki, CloudWatch), становятся доступны широкому кругу лиц и часто записываются в долгосрочные архивы без ограничений доступа. Данные в логах при этом могут дублироваться в неограниченном количестве без истечения срока действия.
*   **Решение:**
    *   **Маскирование/редактирование:** Использование санитайзеров и структурированного логирования, которые скрывают секреты ДО записи в лог-бэкенд (например, detections в Vector/Fluent Bit, `redact`-процессоры).
    *   **Строгий аудит (Audit Devices):** Мониторинг собственных логов Vault (аудит) как отдельного канала, не дублируемого в прикладные логи.
    *   **Проверка утечек:** Регулярная ротация секретов, обнаруженных средствами Vault Radar в логах, как скомпрометированных.

### 7. Избыточные права доступа (IAM/RBAC)

Широкие политики (например, `*` на пути `secret/*` или роль администратора в облаке) или унаследованные учетные записи.

*   **Риск:** Даже короткоживущий секрет или скомпрометированная SaaS-учётка даёт злоумышленнику весь радиус действия политики. Избыточные права напрямую расширяют радиус поражения при компрометации одного секрета.
*   **Решение:**
    *   **Принцип наименьших привилегий (Least Privilege):** Тонкие ACL-политики Vault ([Авторизация и политики](./authorization.md)) с ограничением путей и возможностей.
    *   **Гранулярные роли:** Раздельные сервисные аккаунты и политики для каждого приложения (роль `auth/kubernetes` на уровне namespace).
    *   **Регулярный аудит:** Использование `vault token capabilities` и каналов аудита для выявления избыточных прав.

## Дополнительная информация

### Сравнение рисков и стратегий защиты (2026)

| Антипаттерн | Уровень риска | Современное решение | Инструментарий |
| :--- | :--- | :--- | :--- |
| **Секреты в Git** | Критический | Vault Radar + Pre-commit | Gitleaks, Vault Radar |
| **Secret Zero** | Высокий | Workload Identity Federation | OIDC, K8s Auth |
| **AI Passthrough** | Средний | Credential Injection Layer | Custom SDK, Tool Proxies |
| **ENV переменные** | Средний | Монтирование в tmpfs / VSO | Vault Secrets Operator, CSI Driver |
| **Слои образа** | Высокий | BuildKit Secrets, multi-stage | BuildKit |
| **IaC State (открытый)** | Высокий | Remote State Encryption | Terraform Cloud, S3+KMS |
| **Синхронизация статики** | Низкий | Динамические секреты (JIT) | Database Engine |
| **Логирование секретов** | Средний | Маскирование, санитайзеры | Логи в структуры, экранирование значений |
