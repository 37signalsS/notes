# Интеграция Vault с Docker

## Определения

**Интеграция Vault с Docker** — использование [HashiCorp Vault](../overview.md) как внешнего хранилища для управления секретами в контейнеризированных приложениях на базе [Docker](../../Docker/docker_overview.md) или [Docker Compose](../../Docker/Docker_compose/docker_compose_cli_commands.md). Позволяет отделить секреты от кода и конфигурации контейнеров.

## Основные концепции

Общий workflow:

1. **Настройка Vault:** Установка и настройка [Vault](./vault_installation.md).
2. **Хранение секретов:** Запись секретов в хранилище (например, `kv-v2`).
3. **Политики доступа:** Ограничение доступа к секретам (например, сервис `webapp` читает только `secret/webapp/*`).
4. **Аутентификация:** Приложение аутентифицируется (например, через [AppRole](./vault_auth_approle.md)), получает токен с политиками и запрашивает секреты.

### Методы интеграции

| Метод | Описание | Когда использовать |
| :--- | :--- | :--- |
| **Vault Agent** | Sidecar- или init-контейнер для доставки секретов | Рекомендуется для большинства сценариев |
| **Прямой доступ к API** | Приложение использует библиотеки Vault | Кастомная логика работы с секретами |
| **Entrypoint-скрипт** | Скрипт получает секреты до запуска приложения | Простые сценарии без динамической ротации |

## Практические сценарии

### Vault Agent (рекомендуемый подход)

[Vault Agent](./vault_agent/basics.md) — клиентский демон для:

1. **Аутентификации:** автоматический вход в Vault и управление жизненным циклом токена.
2. **Рендеринга секретов:** запрос секретов и запись в файлы через шаблоны.

Варианты запуска:

- **Sidecar-контейнер:** работает рядом с основным приложением в Docker Compose или [Kubernetes](../../Kubernetes/kubernetes_overview.md).
- **Init-контейнер:** запускается до основного приложения, получает секреты и завершает работу.

Преимущества:

- Приложение не знает о Vault — читает готовые файлы.
- Автоматическая ротация секретов без перезапуска (если приложение поддерживает перечитывание конфигов).

### Прямой доступ к API

Использование официальных библиотек Vault для прямого обращения к API.

- **Плюсы:** полный контроль.
- **Минусы:** усложнение кода (логика аутентификации, хранение токена, запрос секретов).

### Entrypoint-скрипт

Скрипт-обертка (`entrypoint.sh`) получает секреты до запуска приложения:

1. Скрипт обращается к Vault (через `curl` или `vault-cli`), получает секреты.
2. Экспортирует секреты как переменные окружения.
3. Запускает основной процесс (`exec "$@"`).

Пример `entrypoint.sh`:

```bash
#!/bin/sh
set -e

# Аутентификация через AppRole
VAULT_TOKEN=$(curl -s --request POST \
  --data '{"role_id": "'"$APP_ROLE_ID"'", "secret_id": "'"$APP_SECRET_ID"'"}' \
  $VAULT_ADDR/v1/auth/approle/login | jq -r .auth.client_token)

# Запрос секретов
export DB_PASSWORD=$(curl -s --header "X-Vault-Token: $VAULT_TOKEN" \
  $VAULT_ADDR/v1/secret/data/myapp/database | jq -r .data.data.password)

# Запуск приложения
exec "$@"
```

## Дополнительная информация

Рекомендации по безопасности:

- **Минимизируйте TTL** токенов и динамических секретов для снижения ущерба при утечке.
- **Сегментируйте доступ** — принцип наименьших привилегий: каждый сервис читает только нужные секреты.
- **Ведите журнал аудита** — отслеживание обращений к секретам.
- **Обновляйте секреты без перезагрузки** — при поддержке приложением горячего перечитывания конфигов (например, [Nginx](../../WebServers/Nginx/Core/nginx_overview.md), [Prometheus](../../Prometheus/overview.md)) используйте Vault Agent.

Принципы Zero Trust — [подход Zero Trust](../zero_trust.md). Типичные ошибки — [антипаттерны управления секретами](../common_antipatterns.md).
