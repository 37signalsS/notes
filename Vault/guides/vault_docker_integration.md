# Интеграция с Docker и Docker Compose

Когда у вас десятки микросервисов и окружений (dev, staging, production), Vault позволяет централизовать управление секретами и гибко настраивать политики доступа.

**Общая схема работы:**
1.  **Настройка Vault:** Устанавливается и настраивается Vault (как отдельный сервис).
2.  **Хранение секретов:** Секреты помещаются в хранилище Vault (например, `kv-v2`).
3.  **Политики доступа:** Создаются политики, ограничивающие доступ к секретам. Например, сервис `webapp` может читать секреты только по пути `secret/webapp/*`.
4.  **Аутентификация приложения:** Приложение при старте аутентифицируется в Vault (например, через механизм [AppRole](./vault_auth_approle.md) или [Kubernetes](./vault_gitlab_integration_kubernetes.md)), получает токен с нужными политиками и запрашивает свои секреты.

### Варианты интеграции

Существует несколько подходов для передачи секретов из Vault в контейнеры:

#### 1. [Vault Agent](./vault_agent_and_templates.md) (Рекомендуемый подход)

**Vault Agent** — это легковесный клиентский демон, который решает две основные задачи:
1.  **Аутентификация в Vault:** Автоматически аутентифицируется и управляет жизненным циклом токена.
2.  **Рендеринг секретов:** Запрашивает секреты из Vault и записывает их в файлы, используя шаблоны.

Он может быть запущен как:
-   **Sidecar-контейнер:** В Kubernetes или Docker Compose, работая рядом с основным приложением.
-   **Процесс-инициализатор:** Запускается перед основным приложением, получает секреты и завершает работу.

**Преимущества:**
-   Приложение становится "неосведомленным" о Vault. Ему не нужно содержать логику для аутентификации или запроса секретов; оно просто читает готовые файлы.
-   Автоматическая ротация секретов. Vault Agent может отслеживать истечение срока действия секрета и обновлять его без перезапуска основного приложения (если приложение умеет "на лету" перечитывать конфигурационные файлы).

#### 2. Прямой доступ к API

Приложение может использовать официальные библиотеки Vault для вашего языка программирования, чтобы напрямую обращаться к API Vault.

-   **Плюсы:** Полный контроль над процессом.
-   **Минусы:** Усложняет код приложения, так как в нем появляется логика для аутентификации, хранения токена и запроса секретов.

#### 3. Использование с Docker Compose

В окружениях без Kubernetes или Swarm, где используется `docker-compose up`, можно применять следующий "entrypoint" подход:

1.  Создается скрипт-обертка (`entrypoint.sh`), который будет точкой входа для контейнера.
2.  Этот скрипт сначала обращается к Vault (например, с помощью утилиты `curl` или `vault-cli`), получает необходимые секреты и экспортирует их как переменные окружения.
3.  После этого скрипт запускает основной процесс приложения (`exec "$@"`).

**Пример `entrypoint.sh`:**
```bash
#!/bin/sh
set -e

# Получаем токен для доступа к секретам (например, через AppRole)
VAULT_TOKEN=$(curl -s --request POST \
  --data '{"role_id": "'"$APP_ROLE_ID"'", "secret_id": "'"$APP_SECRET_ID"'"}' \
  $VAULT_ADDR/v1/auth/approle/login | jq -r .auth.client_token)

# Запрашиваем секреты и экспортируем их
export DB_PASSWORD=$(curl -s --header "X-Vault-Token: $VAULT_TOKEN" \
  $VAULT_ADDR/v1/secret/data/myapp/database | jq -r .data.data.password)

# Запускаем основной процесс приложения
exec "$@"
```

### Практические советы
-   **Минимизируйте время жизни (TTL):** Для динамических секретов или токенов устанавливайте короткое время жизни. Это снижает ущерб в случае утечки.
-   **Сегментируйте доступ:** Принцип наименьших привилегий — каждый сервис должен иметь доступ только к необходимому ему набору секретов.
-   **Ведите журнал аудита:** Включайте и регулярно просматривайте логи аудита Vault, чтобы отслеживать, кто, когда и к каким секретам получал доступ.
-   **Обновляйте секреты без перезагрузки:** Если ваше приложение поддерживает "горячую" перезагрузку конфигурации (например, Nginx, Prometheus), используйте Vault Agent для обновления секретов без простоя.
