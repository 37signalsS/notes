# Политика доступа для Transit Engine

## Определения

**Политика доступа к ключам шифрования** — это набор правил в Vault, которые определяют, кто (пользователь, приложение) и какие криптографические операции может выполнять с помощью движка секретов **[`transit`](../concepts.md#движки-секретов-secret-engines)**.

Цель — реализовать принцип наименьших привилегий и разделение обязанностей для "шифрования как сервиса" (encryption-as-a-service).

## Основные концепции

Движок `transit` позволяет приложениям шифровать и подписывать данные, не получая прямого доступа к криптографическим ключам. Ключи хранятся в Vault и никогда его не покидают.

### Принципы построения политик для `transit`

* **Минимально необходимый доступ:** Роли должны получать права только на те операции, которые им необходимы (например, `encrypt` и `decrypt`, но не `export` или `delete`).
* **Разделение обязанностей:** Администраторы, управляющие жизненным циклом ключей, и приложения, использующие их, должны иметь разные роли и политики.
* **Невозможность извлечения ключей:** Ключи в `transit` по умолчанию создаются как неизвлекаемые (`exportable=false`).
* **Аудит:** Все криптографические операции протоколируются через **[устройства аудита](../concepts.md#аудит-audit-devices)**.

### Пути и операции

Политики строятся вокруг путей API движка `transit`:

* `/transit/keys/<name>`: Управление ключом (создание, чтение метаданных).
* `/transit/encrypt/<name>`: Шифрование данных.
* `/transit/decrypt/<name>`: Расшифровка данных.
* `/transit/rewrap/<name>`: Перешифрование данных новой версией ключа.
* `/transit/sign/<name>`: Создание цифровой подписи.
* `/transit/verify/<name>`: Проверка подписи.
* `/transit/keys/<name>/rotate`: Ротация ключа.

## Практические сценарии

### Сценарий 1: Политика для приложения

Приложению, которому нужно шифровать и расшифровывать данные, выдается политика, разрешающая только эти операции для конкретного ключа.

* **Имя ключа:** `payments`
* **Задача:** Шифровать и расшифровывать данные.

```hcl
# Политика 'app-payments-policy.hcl'

# Разрешить шифрование с использованием ключа 'payments'
path "transit/encrypt/payments" {
  capabilities = ["update"] # 'update' для POST-запросов
}

# Разрешить расшифровку с использованием ключа 'payments'
path "transit/decrypt/payments" {
  capabilities = ["update"]
}
```

**Результат:** У этой роли нет прав на ротацию, удаление или изменение ключа.

### Сценарий 2: Политика для администратора ключей

Администратор может управлять жизненным циклом ключей, но ему не обязательно иметь доступ к расшифровке конфиденциальных данных.

* **Задача:** Управлять ключом `payments`.

```hcl
# Политика 'admin-payments-policy.hcl'

# Управление ключом (создание, чтение, обновление, листинг)
path "transit/keys/*" {
  capabilities = ["create", "read", "update", "list"]
}

# Разрешить ротацию ключа
path "transit/keys/payments/rotate" {
  capabilities = ["update"]
}

# Явный запрет на расшифровку данных
path "transit/decrypt/payments" {
  capabilities = ["deny"]
}
```

**Результат:** Этот пример демонстрирует **разделение обязанностей**.

## Дополнительная информация

* **Безопасная доставка секрета:** Для безопасной передачи зашифрованного значения можно использовать механизм **[Response Wrapping](../concepts.md#response-wrapping)**. Vault помещает ответ в одноразовый токен, который можно безопасно передать получателю.
